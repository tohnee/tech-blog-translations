# 解密 AI 智能体评估（evals）

> 原文：[Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) · Anthropic Engineering Blog

## 引言

好的评估（evaluation）帮团队更有底气地发布 AI 智能体。没有评估，团队很容易陷入被动循环——问题只在上生产后才被发现，而修复一个失败又制造出别的失败。评估让问题和行为变化在影响用户之前就变得可见，其价值在智能体的整个生命周期中不断复利。

正如我们在[《构建高效智能体》](https://www.anthropic.com/engineering/building-effective-agents)中所描述的，智能体运行在许多轮次之上：调用工具、修改状态、根据中间结果调整。让 AI 智能体有用的那些能力——自主性、智能与灵活性——同时也让它们更难评估。

通过内部工作以及与站在智能体开发前沿的客户合作，我们学会了如何为智能体设计更严谨、更有用的评估。以下是经真实部署中多种智能体架构和用例检验、确实有效的方法。

## 评估的结构

一次**评估**（eval）是对 AI 系统的一场测试：给 AI 一个输入，然后对其输出应用打分逻辑来度量成功与否。本文聚焦可以在开发期间运行、无需真实用户的**自动化评估**。

**单轮评估**很直接：一条提示、一个响应、一套打分逻辑。对早期 LLM 而言，单轮、非智能体的评估是主要评估方式。随着 AI 能力进步，**多轮评估**日益普遍。

![](https://www.anthropic.com/_next/image?url=https%3A%2F%2Fwww-cdn.anthropic.com%2Fimages%2F4zrzovbb%2Fwebsite%2Fbd42e7b2f3e9bb5218142796d3ede4816588dec0-4584x2834.png&w=3840&q=75)

在简单评估中，智能体处理一条提示，一个评分器（grader）检查输出是否符合预期。在更复杂的多轮评估中，一个编码智能体拿到工具、一个任务（此例为构建一个 MCP 服务器）和一个环境，执行「智能体循环」（工具调用与推理），并用实现更新环境。随后打分环节用单元测试验证这个可工作的 MCP 服务器。

**智能体评估**更复杂。智能体跨多轮使用工具，修改环境状态并随机应变——这意味着错误会传播和累积。前沿模型还能找到超越静态评估限制的创造性解法。例如，Opus 4.5 在解一道 [𝜏2-bench](https://github.com/sierra-research/tau2-bench) 订机票题时，[发现](https://www.anthropic.com/news/claude-opus-4-5)了政策中的一个漏洞。按题目原文它「失败」了，但实际上为用户找到了更好的方案。

构建智能体评估时，我们使用以下定义：

- **任务**（task，又称**问题** problem 或**测试用例** test case）是一个有明确输入和成功标准的单独测试。
- 对任务的每次尝试是一个**试验**（trial）。因为模型输出在每次运行之间有波动，我们运行多个试验以产生更稳定的结果。
- **评分器**（grader）是给智能体表现的某个方面打分的逻辑。一个任务可以有多个评分器，每个评分器包含多条断言（有时称为**检查项** checks）。
- **记录**（transcript，又称 trace 或 trajectory）是一次试验的完整记录，包括输出、工具调用、推理、中间结果和所有其他交互。对 Anthropic API 而言，它就是评估运行结束时的完整 messages 数组——包含评估期间所有对 API 的调用和所有返回的响应。
- **结果状态**（outcome）是试验结束时环境的最终状态。一个订机票智能体可能在记录结尾说「您的航班已预订」，但结果状态指的是环境的 SQL 数据库里是否真的存在一条预订。
- **评估执行框架**（evaluation harness）是端到端运行评估的基础设施。它提供指令和工具、并发运行任务、记录所有步骤、给输出打分、并汇总结果。
- **智能体执行框架**（agent harness，或称**脚手架** scaffold）是让模型得以作为智能体行动的系统：它处理输入、编排工具调用、返回结果。我们评估「一个智能体」时，评估的是执行框架*与*模型的联合体。例如，[Claude Code](https://claude.com/product/claude-code) 是一个灵活的智能体执行框架，我们通过 [Agent SDK](https://platform.claude.com/docs/en/agent-sdk/overview) 使用其核心原语构建了我们的[长时运行智能体框架](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)。
- **评估套件**（evaluation suite）是为度量特定能力或行为而设计的一组任务。套件中的任务通常共享一个宽泛目标。例如，一个客服评估套件可能测试退款、取消和升级转接。

## 为什么要建评估？

团队刚开始构建智能体时，靠手动测试、[吃自己的狗粮（dogfooding）](https://en.wikipedia.org/wiki/Eating_your_own_dog_food)和直觉，可以走得惊人地远。更严格的评估甚至显得像拖慢发布的额外负担。但过了早期原型阶段，一旦智能体上了生产并开始规模化，没有评估的构建就开始失灵。

崩溃点往往出现在用户报告「改完之后智能体变差了」，而团队在「盲飞」、除了猜测验证别无他法之时。没有评估，调试是被动的：等投诉、手动复现、修 bug、祈祷没有别的东西退化。团队无法区分真正的退化与噪声，无法在发布前自动针对数百个场景测试改动，也无法度量改进。

我们目睹这条路径上演过很多次。例如，Claude Code 起初基于 Anthropic 员工和外部用户的反馈快速迭代。后来我们加入了评估——先覆盖简洁性和文件编辑等窄领域，再扩展到过度工程等更复杂的行为。这些评估帮助发现问题、指导改进、聚焦研究-产品协作。结合生产监控、A/B 测试、用户研究等手段，评估为持续改进规模化的 Claude Code 提供信号。

在智能体生命周期的任何阶段写评估都有用。早期，评估迫使产品团队明确智能体的「成功」意味着什么；后期，评估帮助守住一致的质量底线。

[Descript](https://www.descript.com/) 的智能体帮助用户剪辑视频，于是他们围绕成功剪辑工作流的三个维度构建评估：不弄坏东西、照我说的做、做得漂亮。他们从人工打分演进到由产品团队定义标准、并定期做人工校准的 LLM 评分器，如今定期运行两套独立的套件做质量基准测试和回归测试。[Bolt](https://bolt.new/) AI 团队起步较晚——在他们已经有广泛使用的智能体之后。他们用 3 个月建起一套评估系统：运行智能体并用静态分析给输出打分、用浏览器智能体测试应用、对指令遵循等行为使用 LLM 评审。

有的团队在开发之初就建评估；有的等到规模化、评估成为改进瓶颈时才补上。评估在智能体开发初期尤其有用——它把期望行为显式编码下来。两个工程师读同一份初始规格，可能对 AI 应如何处理边界情况得出不同理解。评估套件消除这种歧义。无论何时创建，评估都能加速开发。

评估还决定你采用新模型的速度。更强的模型发布时，没有评估的团队要花数周测试，而有评估的对手能快速判断新模型的长处、调整提示，几天内完成升级。

评估一旦建立，基线和回归测试就是免费送的了：延迟、token 用量、单任务成本、错误率都可以在一组静态任务上持续跟踪。评估还能成为产品团队与研究团队之间带宽最高的沟通渠道，定义出研究者可以优化的指标。显然，评估的收益远不止跟踪退化与改进。它的复利价值容易被忽视——因为成本 upfront 可见，而收益是后置累积的。

## 如何评估 AI 智能体

我们看到如今规模化部署的智能体有几种常见类型：编码智能体、研究智能体、计算机使用智能体和对话智能体。每种类型可能部署在形形色色的行业中，但都可以用相似的技术评估。你不必从零发明评估。下文描述针对几种智能体类型的经过验证的技术。以这些方法为基础，再扩展到你的领域。

### 面向智能体的评分器类型

智能体评估通常组合三类评分器：基于代码的、基于模型的和人工的。每个评分器评估记录（transcript）或结果状态（outcome）的某一部分。有效评估设计的关键一环，是为活儿选对评分器。

基于代码的评分器

| **方法** | **优势** | **劣势** |
| --- | --- | --- |
| • 字符串匹配检查（精确、正则、模糊等） • 二值测试（fail-to-pass、pass-to-pass） • 静态分析（lint、类型、安全） • 结果状态验证 • 工具调用验证（用了哪些工具、参数） • 记录分析（轮次数、token 用量） | • 快 • 便宜 • 客观 • 可复现 • 易调试 • 可验证特定条件 | • 对不完全匹配预期模式的合法变体很脆弱 • 缺乏细腻度 • 对评估较主观的任务作用有限 |

基于模型的评分器

| **方法** | **优势** | **劣势** |
| --- | --- | --- |
| - 基于量规（rubric）的打分 - 自然语言断言 - 成对比较 - 参照标准评估 - 多评审共识 | - 灵活 - 可规模化 - 捕捉细腻差异 - 应对开放式任务 - 处理自由格式输出 | - 非确定性 - 比代码贵 - 需与人工评分器校准才能保证准确 |

人工评分器

| **方法** | **优势** | **劣势** |
| --- | --- | --- |
| - 领域专家（SME）评审 - 众包判断 - 抽样检查 - A/B 测试 - 标注者间一致性 | - 黄金标准质量 - 契合专家用户的判断 - 用于校准基于模型的评分器 | - 昂贵 - 慢 - 常需大规模获取人类专家 |

对每个任务，打分可以是加权的（各评分器得分合计需过阈值）、二值的（所有评分器必须通过）或混合的。

### 能力评估 vs. 回归评估

**能力评估**（capability eval，或称「质量」评估）问的是：「这个智能体能把什么做好？」它们的通过率起步应当很低，瞄准智能体表现吃力的任务，给团队一座可以爬的坡。

**回归评估**（regression eval）问的是：「智能体还处理得了它过去能处理的全部任务吗？」通过率应接近 100%。它们防止倒退——分数下滑意味着哪里坏了、需要改进。团队在能力评估上爬坡时，同时跑回归评估也很重要，确保改动不在别处引发问题。

智能体上线并优化之后，通过率很高的能力评估可以「毕业」为持续运行、捕捉任何漂移的回归套件。曾经度量「我们到底能不能做到？」的任务，开始度量「我们还能稳定做到吗？」

### 评估编码智能体

**编码智能体**写代码、跑测试、调试，像人类开发者一样浏览代码库、运行命令。对现代编码智能体有效的评估，通常依赖定义良好的任务、稳定的测试环境，以及对生成代码的全面测试。

确定性评分器对编码智能体是天然契合的，因为软件通常易于评估：代码能跑吗、测试过不过？两个广泛使用的编码智能体基准——[SWE-bench Verified](https://www.swebench.com/SWE-bench/) 和 [Terminal-Bench](https://www.tbench.ai/)——都遵循这个思路。SWE-bench Verified 给智能体来自热门 Python 仓库的 GitHub issue，并通过运行测试套件给方案打分；只有修复了失败测试又不破坏既有测试的方案才算通过。短短一年间，LLM 在这个评估上从 40% 涨到了 >80%。Terminal-Bench 走的是另一条路：它测试端到端的技术任务，比如从源码构建 Linux 内核或训练一个 ML 模型。

一旦有了一组通过/失败测试来验证编码任务的关键*结果状态*，对记录（transcript）打分通常也有用。例如，基于启发式的代码质量规则可以超越「测试通过与否」来评估生成代码，而有清晰量规的基于模型的评分器可以评估智能体调用工具、与用户交互等行为。

**示例：编码智能体的理论评估**

设想一个编码任务：智能体必须修复一个身份验证绕过漏洞。如下面的示意 YAML 文件所示，可以同时用评分器和指标来评估这个智能体。

```
task:
  id: "fix-auth-bypass_1"
  desc: "Fix authentication bypass when password field is empty and ..."
  graders:
    - type: deterministic_tests
      required: [test_empty_pw_rejected.py, test_null_pw_rejected.py]
    - type: llm_rubric
      rubric: prompts/code_quality.md
    - type: static_analysis
      commands: [ruff, mypy, bandit]
    - type: state_check
      expect:
        security_logs: {event_type: "auth_blocked"}
    - type: tool_calls
      required:
        - {tool: read_file, params: {path: "src/auth/*"}}
        - {tool: edit_file}
        - {tool: run_tests}
  tracked_metrics:
    - type: transcript
      metrics:
        - n_turns
        - n_toolcalls
        - n_total_tokens
    - type: latency
      metrics:
        - time_to_first_token
        - output_tokens_per_sec
        - time_to_last_token
```

注意，这个示例为了展示而罗列了全部可用的评分器类型。实践中，编码评估通常靠单元测试做正确性验证，靠一个 LLM 量规评估整体代码质量，其他评分器和指标按需添加。

### 评估对话智能体

**对话智能体**在支持、销售、辅导等领域与用户交互。与传统聊天机器人不同，它们维持状态、使用工具、并在对话中途采取行动。虽然编码和研究智能体也涉及与用户的多轮交互，但对话智能体提出了一个独特的挑战：交互本身的质量就是你要评估的东西的一部分。对对话智能体有效的评估，通常依赖可验证的终态结果（end-state outcomes）和同时捕捉任务完成与交互质量的量规。与大多数其他评估不同，它们往往还需要第二个 LLM 来模拟用户。我们在[对齐审计智能体](https://alignment.anthropic.com/2025/automated-auditing/)中就用这种方法，通过长时间、对抗性的对话来压测模型。

对话智能体的成功是多维的：工单解决了吗（状态检查）？是否在 10 轮内完成（记录约束）？语气得体吗（LLM 量规）？体现多维性的两个基准是 [𝜏-Bench](https://arxiv.org/abs/2406.12045) 及其后续 [τ2-Bench](https://arxiv.org/abs/2506.07982)。它们模拟零售支持、航空订票等领域中的多轮交互：一个模型扮演用户角色，智能体在真实场景中应对。

**示例：对话智能体的理论评估**

设想一个支持任务：智能体必须处理一位愤怒客户的退款。

```
graders:
  - type: llm_rubric
    rubric: prompts/support_quality.md
    assertions:
      - "Agent showed empathy for customer's frustration"
      - "Resolution was clearly explained"
      - "Agent's response grounded in fetch_policy tool results"
  - type: state_check
    expect:
      tickets: {status: resolved}
      refunds: {status: processed}
  - type: tool_calls
    required:
      - {tool: verify_identity}
      - {tool: process_refund, params: {amount: "<=100"}}
      - {tool: send_confirmation}
  - type: transcript
    max_turns: 10
tracked_metrics:
  - type: transcript
    metrics:
      - n_turns
      - n_toolcalls
      - n_total_tokens
  - type: latency
    metrics:
      - time_to_first_token
      - output_tokens_per_sec
      - time_to_last_token
```

与编码智能体的例子一样，这个任务为了示例而展示了多种评分器类型。实践中，对话智能体评估通常用基于模型的评分器同时评估沟通质量与目标完成度，因为许多任务——比如回答一个问题——可能有多个「正确」解法。

### 评估研究智能体

**研究智能体**收集、综合、分析信息，然后产出回答或报告之类的输出。与编码智能体有单元测试提供二值通过/失败信号不同，研究质量只能相对任务本身来判断。什么算「全面」、「来源可靠」、甚至「正确」，取决于上下文：市场扫描、收购尽调和科学报告各自需要不同的标准。

研究评估面临独特挑战：专家对某个综合是否全面可能有分歧；ground truth 随参考内容不断变化而漂移；更长、更开放的输出留出更大的犯错空间。例如 [BrowseComp](http://arxiv.org/abs/2504.12516) 这样的基准，测试 AI 智能体能否在开放网络的大海里捞针——题目被设计得易于验证但难以求解。

构建研究智能体评估的一个策略是组合评分器类型：groundedness（有据性）检查验证论断是否被检索到的来源支撑；覆盖度检查定义好答案必须包含的关键事实；来源质量检查确认查阅的来源是权威的，而不仅仅是最先检索到的。对有客观正确答案的任务（「X 公司第三季度营收是多少？」），精确匹配就够了。LLM 可以标记无支撑论断和覆盖缺口，同时验证开放性综合的连贯性与完整性。

鉴于研究质量的主观性，要有效评估这些智能体，基于 LLM 的量规应当频繁地与专家人工判断校准。

### 计算机使用智能体

**计算机使用智能体**通过与人类相同的界面与软件交互——截图、鼠标点击、键盘输入和滚动——而不是通过 API 或代码执行。它们能使用任何有图形界面（GUI）的应用，从设计工具到老旧的企业软件。评估需要在真实或沙箱环境中运行智能体，让它使用软件应用，然后检查它是否达成了预期结果。例如，[WebArena](https://arxiv.org/abs/2307.13854) 测试基于浏览器的任务，用 URL 和页面状态检查验证智能体导航正确，并对修改数据的任务做后端状态验证（确认订单真的下了，而不只是确认页出现了）。[OSWorld](https://os-world.github.io/) 把这一点扩展到完整操作系统控制，其评估脚本在任务完成后检查多种产物：文件系统状态、应用配置、数据库内容和 UI 元素属性。

浏览器使用智能体需要在 token 效率与延迟之间平衡。基于 DOM 的交互执行快但耗 token，基于截图的交互更慢但更省 token。比如，让 Claude 总结 Wikipedia 时，从 DOM 提取文本更高效；在 Amazon 上找一款新笔记本壳时，截图更高效（提取整个 DOM 太费 token）。在我们的 Claude for Chrome 产品中，我们开发了评估来检查智能体是否为每种上下文选对了工具。这让我们更快、更准确地完成基于浏览器的任务。

### 如何看待智能体评估中的非确定性

无论智能体类型如何，智能体行为在每次运行之间都有波动，这让评估结果比表面看起来更难解读。每个任务都有自己的成功率——可能一个任务 90%，另一个 50%——某次评估运行中通过的任务，下一次可能失败。有时候，我们想度量的是智能体对某任务的成功*频率*（试验中成功的比例）。

两个指标有助于捕捉这种细微差别：

[**pass@k**](https://proceedings.neurips.cc/paper/2019/file/7298332f04ac004a0ca44cc69ecf6f6b-Paper.pdf) 度量智能体在 *k* 次尝试中至少得到一个正确解的可能性。*k* 越大，pass@k 越高：「射门次数」越多，至少进一球的概率越大。50% 的 pass@1 意味着模型第一次尝试就能完成评估中一半的任务。在编码场景，我们最关心的通常是智能体一次找到解——pass@1。在其他场景，只要有一个可用，提出多个解就是合理的。

[**pass^k**](https://arxiv.org/abs/2406.12045) 度量*全部 k 次*试验都成功的概率。*k* 越大，pass^k 越低——要求更多次试验都保持一致是更高的门槛。如果你的智能体单次成功率 75%，跑 3 次试验，三次全过的概率是 (0.75)³ ≈ 42%。对面向用户的智能体，这个指标尤其重要，因为用户期待每次都有可靠的表现。

![](https://www.anthropic.com/_next/image?url=https%3A%2F%2Fwww-cdn.anthropic.com%2Fimages%2F4zrzovbb%2Fwebsite%2F3ddac5be07a0773922ec9df06afec55922f8194a-4584x2580.png&w=3840&q=75)

随着试验次数增加，pass@k 与 pass^k 分道扬镳。k=1 时二者相同（都等于单次成功率）。到 k=10 时，它们讲述相反的故事：pass@k 趋近 100%，而 pass^k 跌向 0%。

两个指标都有用，选哪个取决于产品需求：一次成功就够的工具用 pass@k，一致性至上的智能体用 pass^k。

## 从零到一：智能体优秀评估的路线图

本节给出我们从零建评估到建出可信评估的实操、实战检验过的建议。把它当作评估驱动智能体开发的路线图：尽早定义成功，清晰度量它，持续迭代。

### 为初始评估数据集收集任务

**第 0 步：尽早开始**

我们见过团队迟迟不建评估，以为需要几百个任务。实际上，从真实失败中提炼的 20-50 个简单任务就是极好的起点。毕竟在智能体开发早期，系统的每次改动往往都有清晰、显著的影响，这么大的效应量意味着小样本就够用。更成熟的智能体可能需要更大、更难的评估来检测更小的效应，但起步阶段最好走 80/20 路线。评估拖得越久越难建：早期，产品需求会自然转化为测试用例；拖太久，你就是在从一个已上线的系统反向工程成功标准。

**第 1 步：从你已经在手动测试的东西开始**

从你开发期间跑的手动检查入手——每次发布前你验证的行为、终端用户常试的任务。如果你已上生产，翻一翻 bug 跟踪器和支持队列。把用户报告的失败转化为测试用例，确保套件反映真实用法；按用户影响排优先级，把力气花在刀刃上。

**第 2 步：写出无歧义的任务并附参照解**

把任务质量做好比看起来难。好任务的判据是：两个领域专家会独立得出相同的通过/失败结论。他们自己能完成任务吗？不能的话，任务需要打磨。任务规格中的歧义会变成指标中的噪声。这同样适用于基于模型的评分器的标准：模糊的量规产生不一致的判断。

每个任务都应当可以被一个正确遵循指令的智能体完成。这一点很微妙。例如，审计 Terminal-Bench 时发现：如果任务要求智能体写一个脚本却没指定文件路径，而测试假定脚本在某个特定路径，智能体就可能无过错失败。评分器检查的一切都应能从任务描述中看清楚；智能体不应因规格含糊而失败。对前沿模型来说，多次试验 0% 通过率（即 0% pass@100）多半是任务坏了的信号，而不是智能体不行的信号——该复查你的任务规格和评分器了。为每个任务创建一个参照解（reference solution）很有用：一个已知的、能通过所有评分器的正确输出。它证明任务可解，也验证评分器配置正确。

**第 3 步：构建均衡的题目集**

既测行为*应该*发生的情形，也测它*不应该*发生的情形。单边评估造就单边优化。例如，如果你只测智能体在应该搜索时搜索，最后可能得到一个什么都搜的智能体。尽量避免[类别不均衡](https://developers.google.com/machine-learning/crash-course/overfitting/imbalanced-datasets)的评估。我们在为 [Claude.ai](http://claude.ai/redirect/website.v1.256df65f-28af-45fc-b99f-00a65edfbf16) 的网页搜索建评估时深有体会。挑战在于防止模型不该搜的时候乱搜，同时保住它在合适时机做深入研究的能耐。团队构建了双向覆盖的评估：模型应当搜索的查询（比如查天气）和应当凭既有知识回答的查询（比如「谁创立了 Apple？」）。在欠触发（该搜不搜）与过触发（不该搜乱搜）之间找到恰当平衡很难，对提示和评估做了许多轮打磨。随着新的示例问题出现，我们持续为评估扩充覆盖面。

### 设计评估执行框架与评分器

**第 4 步：用稳定的环境构建健壮的评估执行框架**

评估中的智能体必须与生产中的智能体大体一致，环境本身也不应引入额外噪声。每次试验都应从干净环境开始，做到「隔离」。运行之间不必要的共享状态（遗留文件、缓存数据、资源耗尽）可能因基础设施不稳定而非智能体表现造成相关联的失败。共享状态也可能人为抬高表现。例如，在一些内部评估中，我们观察到 Claude 通过翻看之前试验的 git 历史在部分任务上占了便宜。如果多个不同的试验因为环境的同一个限制（如 CPU 内存不足）而失败，这些试验就不是独立的——它们受同一因素影响——评估结果对度量智能体表现就不可靠了。

**第 5 步：深思熟虑地设计评分器**

如上所述，好的评估设计在于为智能体和任务选对评分器。我们建议：能用确定性评分器就用确定性评分器，必要时或需要额外灵活性时用 LLM 评分器，并审慎地用人工评分器做额外验证。

有一种常见直觉是检查智能体是否遵循了非常具体的步骤，比如一串按正确顺序排列的工具调用。我们发现这种做法过于僵硬、产生过度脆弱的测试，因为智能体常常找到评估设计者没料到的有效路径。为了不无谓地惩罚创造力，更好的做法往往是给智能体*产出*的东西打分，而不是它走的路径。

对多组件任务，要内置部分得分（partial credit）。一个正确识别问题、验证了客户身份、却没处理退款的客服智能体，明显好过一个立刻失败的。在结果中呈现这个成功的连续谱很重要。

模型打分往往需要仔细迭代来验证准确性。LLM-as-judge 评分器应当与人类专家紧密校准，以确信人工打分与模型打分之间分歧很小。为避免幻觉，给 LLM 留一条退路，比如指示它在信息不足时返回「Unknown」。创建清晰、结构化的量规、为任务的每个维度分别打分也很有帮助——用各自独立的 LLM-as-judge 评每个维度，而不是用一个评所有维度。系统足够健壮后，人工审查偶尔做做就够。

有些评估存在微妙的失败模式：即便智能体表现良好，分数也偏低——因为打分 bug、智能体执行框架限制或歧义导致智能体无法解题。再成熟的团队也会漏掉这些问题。例如，[Opus 4.5 在 CORE-Bench 上最初只得 42%](https://x.com/sayashk/status/1996334941832089732?s=46&t=c5pEvnVdVbMkcR_rcCHplg)，直到一位 Anthropic 研究员发现多个问题：僵硬的打分在期待「96.124991…」时惩罚了「96.12」、含糊的任务规格、以及无法精确复现的随机性任务。修完 bug、换用一个限制更少的脚手架后，Opus 4.5 的分数跳到 95%。类似地，[METR 发现](https://x.com/metr_evals/status/2001473506442375645?s=46)其时间跨度基准中有几个配置错误的任务：要求智能体优化到某个声明的分数阈值，但打分却要求*超过*该阈值。这惩罚了像 Claude 这样遵循指令的模型，而无视既定目标的模型反而拿了高分。仔细复查任务和评分器可以避免这些问题。

让你的评分器抵抗绕过和作弊。智能体不应能轻易「骗过」评估。任务与评分器的设计应当让通过必须真正解题，而不是钻规则的空子。

### 长期维护和使用评估

**第 6 步：查阅记录（transcripts）**

不去读大量试验的记录和打分，你不会知道你的评分器是否工作良好。在 Anthropic，我们投入建设了查看评估记录的工具，并定期花时间阅读它们。当任务失败时，记录会告诉你：是智能体真的犯错了，还是你的评分器误杀了一个有效方案。它还常常揭示智能体与评估行为的关键细节。

失败应当「服人」：智能体错在哪里、为什么错，一目了然。当分数不再上涨时，我们需要确信这是智能体表现的问题而不是评估的问题。读记录是你验证评估正在度量真正重要之事的方式，是智能体开发的关键技能。

**第 7 步：监控能力评估的饱和**

100% 的评估只能跟踪退化，不能提供改进信号。**评估饱和**（eval saturation）发生在智能体通过了所有可解任务、再无提升空间之时。例如，SWE-Bench Verified 分数今年从 30% 起步，前沿模型如今已逼近 >80% 的饱和区。评估接近饱和时，进步也会放缓，因为只剩最困难的任务。这会让结果显得失真：巨大的能力提升只体现为分数的小幅上涨。例如，代码审查公司 [Qodo](https://www.qodo.ai/) 最初对 Opus 4.5 不以为然，因为他们的一次性（one-shot）编码评估捕捉不到它在更长、更复杂任务上的进步。于是他们开发了一个新的智能体式评估框架，得到了清晰得多的进展图景。

作为一条规则，在有人深挖评估细节、读过一些记录之前，我们不把评估分数当作定论。如果打分不公、任务含糊、有效方案被误罚、或执行框架限制了模型，评估就应当修订。

**第 8 步：通过开放贡献与维护让评估套件长期健康**

评估套件是一个活物，需要持续的关注和清晰的归属权才能保持有用。

在 Anthropic，我们试验过多种评估维护方式。最有效的是：设立专门的评估团队负责核心基础设施，而领域专家和产品团队贡献大多数评估任务、并自行运行评估。

对 AI 产品团队而言，拥有并迭代评估应当像维护单元测试一样日常。团队可能在一个「早期测试能跑」的 AI 功能上浪费数周——它满足不了那些一份设计良好的评估本可及早暴露的隐含期待。定义评估任务是压力测试产品需求是否具体到可以动工的最佳方式之一。

我们推荐实践评估驱动开发（eval-driven development）：在智能体尚不具备某能力之前先建评估来定义它，然后迭代直到智能体表现良好。在内部，我们常常构建今天「够用」、实则押注于几个月后模型能做到什么的功能。从低通过率起步的能力评估让这一切可见。新模型发布时，跑一遍套件立刻揭示哪些押注兑现了。

离产品需求和用户最近的人最有资格定义成功。以当前模型的能力，产品经理、客户成功经理或销售人员可以用 Claude Code 以 PR 的形式贡献评估任务——让他们来！更好的是，主动为他们创造条件。

## 评估如何与其他方法配合，形成对智能体的整体理解

自动化评估可以在数千个任务上对着智能体运行，无需上生产、不影响真实用户。但这只是理解智能体表现的方式之一。完整的图景还包括生产监控、用户反馈、A/B 测试、人工记录审查和系统性人工评估。

理解 AI 智能体表现的各类方法总览

| 方法 | 优势 | 劣势 |
| --- | --- | --- |
| **自动化评估** *以程序方式运行测试，无真实用户参与* | - 迭代更快 - 完全可复现 - 不影响用户 - 每次提交都可运行 - 无需生产部署即可大规模测试场景 | - 前期投入更大 - 需要随产品和模型演进而持续维护以防漂移 - 若与真实使用模式不符，会造成虚假信心 |
| **生产监控** *跟踪在线系统中的指标与错误* | - 大规模揭示真实用户行为 - 捕捉合成评估漏掉的问题 - 提供智能体实际表现的 ground truth | - 被动；问题先到达用户再被你知晓 - 信号可能嘈杂 - 需要埋点投入 - 打分缺少 ground truth |
| **A/B 测试** *用真实用户流量对比变体* | - 度量真实用户结果（留存、任务完成） - 控制混杂因素 - 可规模化且系统化 | - 慢；达到显著性要数天数周，且需要足够流量 - 只能测你部署的改动 - 在无法彻底审查记录时，对指标变化的底层「为什么」信号较弱 |
| **用户反馈** *点踩、bug 报告等显式信号* | - 浮现你没想到的问题 - 附带真实用户的真实例子 - 反馈常与产品目标相关 | - 稀疏且自选择 - 偏向严重问题 - 用户很少解释*为什么*失败 - 无法自动化 - 主要依赖用户发现问题会对用户造成负面影响 |
| **人工记录审查** *人类通读智能体对话* | - 建立对失败模式的直觉 - 捕捉自动化检查漏掉的微妙质量问题 - 帮助校准「好」的标准、把握细节 | - 耗时 - 无法规模化 - 覆盖不一致 - 审查者疲劳或审查者不同会影响信号质量 - 通常只给定性信号而非清晰的定量打分 |
| **系统性人工研究** *由受训评分员对智能体输出做结构化打分* | - 来自多位人类评分员的黄金标准判断 - 应对主观或含糊任务 - 为改进基于模型的评分器提供信号 | - 相对昂贵、周期慢 - 难以高频运行 - 评分员间分歧需要调解 - 复杂领域（法律、金融、医疗）需要人类专家开展研究 |

这些方法对应智能体开发的不同阶段。自动化评估在上线前和 CI/CD 中尤其有用——随每次智能体改动和模型升级运行，是抵御质量问题的第一道防线。生产监控在上线后接管，检测分布漂移和意想不到的真实失败。流量足够后，A/B 测试验证重大改动。用户反馈与记录审查是持续性实践，用来填补空隙：持续分诊反馈、每周抽样阅读记录、按需深挖。系统性人工研究留给校准 LLM 评分器、或评估那些以人类共识为参照标准的主观输出。

![](https://www.anthropic.com/_next/image?url=https%3A%2F%2Fwww-cdn.anthropic.com%2Fimages%2F4zrzovbb%2Fwebsite%2Fb77b8dbb7c2e57f063fbc8a087a853d5809b74b0-4584x2580.png&w=3840&q=75)

正如安全工程中的[瑞士奶酪模型](https://en.wikipedia.org/wiki/Swiss_cheese_model)：没有任何单一评估层能拦住所有问题。多种方法组合后，从一层漏掉的失败会被另一层接住。

最有效的团队组合使用这些方法：自动化评估用于快速迭代，生产监控提供 ground truth，定期人工审查用于校准。

## 结语

没有评估的团队深陷被动循环——修一个失败、造出另一个，分不清真退化与噪声。尽早投入评估的团队则相反：失败变成测试用例，测试用例防止退化，指标取代猜测，开发随之加速。评估给整个团队一座清晰的坡可以爬，把「智能体好像变差了」变成可行动的事。其价值不断复利——但前提是你把评估当作核心组件，而不是事后补丁。

模式因智能体类型而异，但本文所述的基本原则是不变的。尽早开始，别等完美的套件。从你看到的失败中汲取真实的任务。定义无歧义、健壮的成功标准。深思熟虑地设计评分器并组合多种类型。确保题目对模型足够难。迭代评估以提升信噪比。去读记录！

AI 智能体评估仍是一个新兴、快速演化的领域。随着智能体承担更长任务、在多智能体系统中协作、处理越来越主观的工作，我们需要调整技术。我们会随着学习的深入持续分享最佳实践。

## 附录：评估框架

若干开源与商业框架可以帮助团队实现智能体评估，而无需从零搭建基础设施。正确选择取决于你的智能体类型、现有技术栈，以及你需要离线评估、生产可观测性、还是两者都要。

[Harbor](https://harborframework.com/) 专为在容器化环境中运行智能体设计，提供跨云厂商大规模运行试验的基础设施，以及定义任务和评分器的标准化格式。Terminal-Bench 2.0 等流行基准通过 Harbor registry 分发，便于在自定义评估套件之外运行现成基准。

[Braintrust](https://www.braintrust.dev/) 是一个把离线评估与生产可观测性、实验追踪结合起来的平台——适合既要在开发期迭代、又要在生产中监控质量的团队。其 `autoevals` 库包含事实性、相关性等常见维度的预制评分器。

[LangSmith](https://docs.langchain.com/langsmith/evaluation) 提供追踪、离线与在线评估、数据集管理，并与 LangChain 生态紧密集成。[Langfuse](https://langfuse.com/) 提供类似能力，是对有数据驻留要求的团队而言可自托管的开源替代。

[Arize](https://arize.com/) 提供开源的 Phoenix——LLM 追踪、调试与离线/在线评估平台——以及在其之上扩展规模化、优化与监控能力的 SaaS 产品 AX。

许多团队组合多个工具、自研评估框架，或从简单的评估脚本起步。我们发现，框架虽能加速进展、推动标准化，但其价值取决于你跑过其中的评估任务。通常最好的做法是：快速选一个契合你工作流的框架，然后把精力投在评估本身——迭代高质量测试用例与评分器。
