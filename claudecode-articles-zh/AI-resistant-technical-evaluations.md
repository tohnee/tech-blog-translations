# 设计抗 AI 的技术评估

> 原文：[Designing AI-resistant technical evaluations](https://www.anthropic.com/engineering/AI-resistant-technical-evaluations) · Anthropic Engineering Blog

*作者 Tristan Hume，Anthropic 性能优化团队负责人。Tristan 设计——并一再重新设计——那道帮 Anthropic 招到数十位性能工程师的回家作业（take-home test）。*

随着 AI 能力提升，评估技术候选人变得越来越难。一份今天还能有效区分人类水平的回家作业，明天就可能被模型轻松解决——从而失去评估价值。

自 2024 年初以来，我们的性能工程团队一直使用一道回家作业：候选人优化跑在模拟加速器上的代码。已有超过 1,000 名候选人完成了它，其中数十人如今在这里工作，包括把我们的 Trainium 集群建起来的工程师，以及自 Claude 3 Opus 以来每个模型的发布参与者。

但每一个新的 Claude 模型都迫使我们重新设计这道测试。在同样的时间限制下，Claude Opus 4 的表现超过了大多数人类申请者。这仍能让我们区分最强的候选人——可随后 Claude Opus 4.5 连他们比下去了。在无限时间里，人类仍能胜过模型，但在回家作业的约束下，我们已经无法区分顶尖候选人的产出与我们最强模型的产出。

为了让这道回家作业继续保持信号，我已迭代了三个版本。每一次，我都学到了一些关于什么让评估对 AI 辅助保持鲁棒、什么不能的新东西。

本文描述最初的回家作业设计、每个 Claude 模型如何攻克它，以及我为确保测试领先于我们最强模型能力而不得不采取的越来越不寻常的做法。虽然我们的工作随模型共同演化，我们仍需要更多优秀的工程师——只是需要越来越有创意的方式去找到他们。

为此，我们将最初的回家作业作为一个公开挑战发布，因为在无限时间下，最优秀的人类成绩仍超过 Claude 所能达到的水平。如果你能胜过 Opus 4.5，我们非常乐意收到你的消息——详情见本文末尾。

## 回家作业的起源

2023 年 11 月，我们正准备训练并发布 Claude Opus 3。我们已经拿到了新的 TPU 和 GPU 集群，大型 Trainium 集群也即将到位，我们在加速器上的开销远超以往，但我们没有足够多的性能工程师来支撑新的规模。我在 [Twitter 上发帖](https://x.com/trishume/status/1730386529997238605?s=20)请大家给我们发邮件，这带来了超出我们标准面试流程所能消化的优秀候选人——那个流程对员工和候选人都要耗费大量时间。

我们需要一种更高效评估候选人的方式。于是，我花了两周设计了一道回家作业，力求充分捕捉这个岗位的要求，并识别出最有能力的申请者。

### 设计目标

回家作业名声不佳。它们通常充斥着工程师觉得无聊的通用问题，筛选效果也差。我的目标不同：做出真正让人投入的东西，让候选人兴奋地参与，并让我们以高分辨率捕捉他们的技术能力。

在评估性能工程技能方面，这种形式相比现场面试还有几个优势：

**更长的时间跨度：** 工程师写代码时很少面对小于一小时的截止期限。4 小时的窗口（后来缩短到 2 小时）更贴近工作的实际性质。它仍比大多数真实任务短，但我们需要与负担程度相平衡。

**真实的环境：** 没有人在旁观看、也不期待边做边讲。候选人在自己的编辑器里不受干扰地工作。

**理解与工具有时间：** 性能优化要求理解既有系统，有时还要构建调试工具。这两样在常规的 50 分钟面试里都很难真实评估。

**与 AI 辅助兼容：** Anthropic 的[通用候选人指引](https://www.anthropic.com/candidate-ai-guidance)要求候选人在无特别说明的情况下不使用 AI 完成回家作业。而在这道作业中，我们明确表示可以用。

时间跨度更长的问题 AI 更难完全解决，所以候选人可以像在工作中那样使用 AI 工具，同时仍需展示自己的功力。

除了这些形式层面的目标，我还套用了自己设计任何面试时的相同原则，让回家作业：

**贴近真实工作：** 题目应让候选人尝到这份工作实际要做的事。

**高信号：** 回家作业应避免只押一个灵感的问题，确保候选人有充分机会展示全部能力——尽量少留 chance 成分。它还应有宽广的分数分布，并保证足够的深度，让强者也做不完全部。

**不依赖特定领域知识：** 基本功扎实的人在岗位上能学会具体细节。要求狭窄的专业知识会无谓地缩小候选人池。

**有趣：** 快速的开发循环、有深度的问题、以及创造力的空间。

### 模拟机器

我为一个虚构的、特性神似 TPU 的加速器构建了一个 Python 模拟器。候选人优化跑在这台机器上的代码，使用一个热更新的 [Perfetto](https://perfetto.dev/) trace，它显示每一条指令，类似[我们在 Trainium 上的工具](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/tools/neuron-explorer/overview-device-profiles.html)。

这台机器包含让加速器优化变得有趣的特性：手工管理的暂存内存（scratchpad；与 CPU 不同，加速器常要求显式内存管理）、VLIW（每周期多个执行单元并行运行，需要高效的指令打包）、SIMD（每条指令对多个元素做向量运算）和多核（把工作分布到多个核心）。

![](https://www.anthropic.com/_next/image?url=https%3A%2F%2Fwww-cdn.anthropic.com%2Fimages%2F4zrzovbb%2Fwebsite%2Febebb22ddbba7103f3af4e8a55a13245d3897802-2149x831.png&w=3840&q=75)

任务是并行树遍历——刻意不带深度学习色彩，因为当时多数性能工程师还没做过深度学习，领域细节可以在岗学。题目灵感来自无分支 SIMD 决策树推理，这个经典 ML 优化挑战算是对过去的一次致意，只有少数候选人以前接触过。

候选人从一个完全串行的实现起步，逐步开发机器的并行能力。热身是多核并行，然后候选人可以选择做 SIMD 向量化还是 VLIW 指令打包。最初的版本还埋了一个需要候选人先行调试的 bug，考验他们构建工具的能力。

## 早期成效

最初的回家作业运转良好。Twitter 那批人里有一个人比所有人都高出一大截。他在 2 月初入职，比我们通过标准流程招到的第一批人晚了两周。这道测试证明了预测力：他一上来就开始优化 kernel，还为一个阻塞发布的编译器 bug（张量索引运算溢出 32 位）找到了绕行方案。

在随后的一年半里，约 1,000 名候选人完成了这道作业，它帮我们招到了当前性能工程团队的大部分成员。对纸面经验有限的候选人，它尤其有价值：我们几位最强的工程师本科毕业直接过来，但在回家作业上展现了足够的功力，让我们放心录用。

反馈是积极的。许多候选人做着做着就超过了 4 小时限制，因为他们乐在其中。最强的无限时间提交包括完整的优化型迷你编译器，以及好几个我没想到的巧妙优化。

### 然后 Claude Opus 4 攻克了它

到 2025 年 5 月，Claude 3.7 Sonnet 已经悄然爬升到这样的程度：超过 50% 的候选人如果完全委派给 Claude Code，成绩会更好。接着我在回家作业上测试了一个 Claude Opus 4 的预发布版本。在 4 小时限制内，它给出了几乎胜过所有人类的优化方案。

这不是我的面试第一次被 Claude 模型攻破。2023 年我设计过一个现场面试题，恰恰是因为我们当时的题目都围绕早期 Claude 模型有大量知识储备、因而轻松可解的常见任务。我试图设计一个比拼解题能力而非知识量的问题，仍基于我在工作中解决过的一个真实（但冷门）的问题。Claude 3 Opus 攻克了该题的第一部分；Claude 3.5 Sonnet 攻克了第二部分。我们至今还在用它，因为我们的其他现场题也谈不上抗 AI。

对回家作业而言，有一个直截了当的修法。这个问题的深度远超任何人 4 小时内能探索的范围，所以我用 Claude Opus 4 找出它开始吃力的地方。那就是第 2 版的新的起点。我写了更干净的起始代码，为机器添加新特性以增加深度，并移除了多核（Claude 已经解决了它，而且它只拖慢开发循环、不增加信号）。

我还有把时间限制从 4 小时缩到 2 小时。最初选 4 小时是基于候选人反馈——他们更希望降低因卡在 bug 或困惑上而沉没的风险——但排期的开销让我们的招聘流程拖延了数周。2 小时更容易塞进一个周末。

第 2 版强调巧妙的优化洞见，而不是调试和代码量。它很好地服务了我们——好几个月。

### 然后 Claude Opus 4.5 又攻克了它

当我测试一个预发布的 Claude Opus 4.5 checkpoint 时，我看着 Claude Code 在这道题上工作 2 小时，逐步改进它的方案。它解决了初始瓶颈，实现了所有常见的微优化，并在不到一小时达到我们的及格线。

然后它停下了，深信自己撞上了不可逾越的内存带宽瓶颈。大多数人也会得出同样的结论。但存在利用题目结构绕过该瓶颈的巧妙技巧。当我告诉 Claude 可能达到的周期数后，它思考了一阵，找到了那个技巧。接着它调试、调优、实现更多优化。到 2 小时节点，它的分数追平了该时限内最好的人类成绩——而那个人重度使用 Claude 4 并全程引导（steering）。

我们把它放进内部测试时计算 harness 里做了更严格的验证，确认它既能在 2 小时内胜过人类，也能随时间继续攀升。发布后我们甚至以通用方式改进了 harness，拿到了更高的分数。

![](https://www.anthropic.com/_next/image?url=https%3A%2F%2Fwww-cdn.anthropic.com%2Fimages%2F4zrzovbb%2Fwebsite%2F378256f8023fc3d48f2992b9ee9884a4658e3ab1-1681x463.png&w=3840&q=75)

我遇到了麻烦。我们即将发布这样一个模型：在这道回家作业上，最优策略就是把活儿整个委派给 Claude Code。

## 权衡选项

有同事建议禁用 AI 辅助。我不想这么做。除了执法层面的困难，我有一种直觉：既然人在我们的工作中持续扮演关键角色，我应当能找到*某种*办法让他们在*有 AI* 的环境中脱颖而出——就像他们在工作中的处境。我还不想接受那个[观点](https://metr.org/blog/2025-03-19-measuring-ai-ability-to-complete-long-tasks/)——人类只在超过几小时的任务上占优。

另一些人建议把门槛提高到「显著超越 Claude Code 单独所能达到的水平」。顾虑在于 Claude 干活很快。人类通常要花 2 小时中的一半读题、理解题，然后才开始优化。一个想引导 Claude 的人很可能一直落在后面，只能在事后理解 Claude 做了什么。占优策略可能变成袖手旁观。

如今 Anthropic 的性能工程师仍有很多工作要做，但那些工作更像艰难的调试、系统设计、性能分析、弄清如何验证我们系统的正确性、以及如何让 Claude 的代码更简洁优雅。遗憾的是，这些东西很难在客观测试中检验，除非有大量时间或共同上下文。设计能代表真实工作的面试一直很难，如今难上加难。

但我也担心：如果我投入设计一道新的回家作业，要么 Claude Opus 4.5 把它也解了，要么它难到人类根本无法在两小时内完成。

### 尝试 1：换一个优化问题

我意识到 Claude 可以帮我把设计的任何东西快速实现出来，这促使我尝试开发一道更难的回家作业。我选了一个基于我在 Anthropic 做过的较棘手的 kernel 优化的问题：在 2D TPU 寄存器上做高效数据[转置（transposition）](https://en.wikipedia.org/wiki/Transpose)，同时避免 [bank 冲突](https://feldmann.nyc/blog/smem-microbenchmarks)。我把它提炼成模拟机器上的一个更简单的问题，并让 Claude 在一天内实现了改动。

Claude Opus 4.5 找到了一个我根本没想到的绝妙优化：通过细致分析，它意识到可以转置整个计算，而不是琢磨怎么转置数据，然后相应重写了整个程序。

在我真实的场景里这条路走不通，所以我修补了题目，封掉这个思路。Claude 随后取得了进展，但找不到最高效的解。看起来我的新题目有着落了，接下来只需祈祷人类候选人能足够快地解开它。但我心里有些挥之不去的疑虑，于是用 Claude Code 的「ultrathink」功能和更长的思考预算复核了一遍……它解出来了。它甚至知道修 bank 冲突的那些技巧。

事后看来，这不是该尝试的问题。众多平台上的工程师都与数据转置和 bank 冲突搏斗过，所以 Claude 有大量训练数据可以借鉴。我是从第一性原理推出来的解法，而 Claude 可以调用一个更大的经验工具箱。

### 尝试 2：走向更怪

我需要一个人类推理能胜过 Claude 庞大经验库的问题：某种足够出分布（out of distribution）的东西。遗憾的是，这与「一眼看上去像这份工作」的目标相冲突。

我想了想自己最享受过的最不寻常的优化问题，落在了 [Zachtronics 游戏](https://www.zachtronics.com/)上。这些编程解谜游戏使用非常规、强约束的指令集，逼你用非传统方式编程。例如在 [Shenzhen I/O](https://www.zachtronics.com/shenzhen-io/) 中，程序被拆分到多颗相互通信的芯片上，每颗只装约 10 条指令和一两个状态寄存器。巧妙的优化往往要把状态编码进指令指针或分支标志位。

我设计了一道新的回家作业：用一个小而强约束的指令集做谜题，以最少的指令数为目标优化解法。我实现了一个中等偏难的谜题并在 Claude Opus 4.5 上测试。它失败了。我又补齐了更多谜题，并请同事验证：没有像我这样浸淫此道的人也能胜过 Claude。

与 Zachtronics 游戏不同，我刻意不提供可视化或调试工具。起始代码只检查解法是否合法。构建调试工具本身就是被考察的一部分：你可以精心插入 print 语句，也可以让编码模型在几分钟内生成一个交互式调试器。如何投资工具建设的判断本身就是信号的一部分。

我对新作业相当满意。它的方差可能比原版更低，因为它由更多相互独立的子问题构成。早期结果令人振奋：分数与候选人过往作品的水平相关性良好，而且我最有能力的一位同事的分数超过了迄今所有候选人。

放弃原作的真实感与多样的深度，我仍感遗憾。但真实感可能是我们不再享有的奢侈品。原版有效，因为它像真实的工作。替代版有效，因为它模拟了新颖的工作。

## 一个公开挑战

我们发布最初的回家作业，欢迎任何人在无限时间内尝试。在足够长的时间跨度上，人类专家[仍然保有优势](https://metr.org/blog/2025-03-19-measuring-ai-ability-to-complete-long-tasks/)。有史以来最快的人类解法大幅超越 Claude 即便投入大量测试时计算所取得的成绩。

发布版从零开始（像第 1 版），但采用第 2 版的指令集和单核设计，因此周期数可与第 2 版直接比较。

性能基准（以模拟机器的时钟周期数计）：

- **2164 周期**：Claude Opus 4 在测试时计算 harness 中运行数小时
- **1790 周期**：Claude Opus 4.5 在一次随意的 Claude Code 会话中，约等于人类在 2 小时内的最好成绩
- **1579 周期**：Claude Opus 4.5 在我们的测试时计算 harness 中运行 2 小时
- **1548 周期**：Claude Sonnet 4.5 经历远超 2 小时的测试时计算
- **1487 周期**：Claude Opus 4.5 在 harness 中运行 11.5 小时
- **1363 周期**：Claude Opus 4.5 在改进后的测试时计算 harness 中运行数小时

[到 GitHub 下载](https://github.com/anthropics/original_performance_takehome)。如果你的优化低于 1487 周期——超过 Claude 发布时的最好成绩——请把代码和简历发到 [performance-recruiting@anthropic.com](mailto:performance-recruiting@anthropic.com)。

或者你也可以[走我们的常规招聘流程](https://www.anthropic.com/careers/jobs)，它用的是我们（如今）抗 Claude 的回家作业。我们很好奇它能撑多久。
