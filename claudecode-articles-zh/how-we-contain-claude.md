# 我们如何在各产品中约束 Claude

> 原文：[How we contain Claude across products](https://www.anthropic.com/engineering/how-we-contain-claude) · Anthropic Engineering Blog

十二个月前，我们会断然拒绝给 Claude 足以搞垮一个内部 Anthropic 服务的访问权限。今天，这种级别的访问已是家常便饭，而 Anthropic 的开发者也因此更有生产力。这类部署的风险有两个组成部分：失败的概率有多大，以及一旦失败能造成多大破坏。防护栏与模型训练上的进步持续压低前者；后者——理论上的影响半径——却随能力与访问的扩张而不断增大。然而，当智能体开始能够完成过去需要一个人甚至一个团队的工作时，*不*部署的代价大到让风险收益计算强烈倒向采纳——前提是产品能被做得足够安全。工程问题于是变成：如何封顶影响半径。

![](https://www.anthropic.com/_next/image?url=https%3A%2F%2Fwww-cdn.anthropic.com%2Fimages%2F4zrzovbb%2Fwebsite%2F5ebc85c6325c7f59bd6c08950ff9beb1863f1345-1920x866.png&w=3840&q=75)

*当自主智能体的相对破坏力能够被设界——例如通过控制其环境——高价值能力就可以成为部署的理由。Claude Mythos Preview 就是一个例子：其影响半径在 2026 年 4 月被判定过高、不宜发布。但我们预计，随着防御者加固关键系统、防护栏走向成熟，发布具备类似能力水平的模型将变得合适——尽管某些风险将永远存在。模型能力是智能体部署总风险的重要因素。*

大致上有两条路可以做到这一点。

第一条是经由人机协同（human-in-the-loop）监督智能体的行为。Claude Code 此前防范智能体做出非预期动作的方式，是在每一轮向用户请求许可。理论上可行，但我们发现这条路会失灵。我们的遥测显示，用户批准了约 93% 的权限提示。用户看到的批准越多，花在每个批准上的注意力越少，久而久之监督就变得非常松懈。我们最近构建的 Claude Code 自动模式通过[自动化更安全的批准](https://www.anthropic.com/engineering/claude-code-auto-mode)来减轻批准疲劳。但漏洞依然存在——任何概率性防御都有非零的漏检率。1

第二条封顶影响半径的路线——也是本文的重点——是遏制（containment）。我们不是监督智能体*做了*什么，而是监督它*能够*做什么：通过沙箱、虚拟机、出站（egress）控制等手段强制划定访问边界。这是 Anthropic 工程投入最多精力的地方，也是许多最令人意外的安全失效发生的地方。

过去两年，我们发布了三个主要的智能体产品：[claude.ai](http://claude.ai/redirect/website.v1.15c559e6-bccb-4ffb-a120-e68e2652f0a0)、Claude Code 和 Claude Cowork。它们面向不同的受众，需要不同的遏制架构。本文分享哪些做法经受住了考验、哪些崩溃了，以及我们一路走来在智能体安全上学到的东西。

## **三类风险，三道防线的组成**

智能体面临的安全风险可归入三类：

**用户滥用：** 用户——无论是恶意还是粗心——指使智能体做有害的事。包括从要求智能体绕过自己嫌麻烦的检查，到运行自己看不懂的破坏性命令，再到指明要造成伤害。

**模型不当行为：** 智能体做出没人要求的伤害性动作。随着模型进步，它们在大多数行为评估上更加对齐，但这不意味着风险必然缩小。能力较弱的模型更容易误读局面、犯下低级错误。能力更强的模型犯错更少，但也更擅长寻找通往目标的意外路径——常常是绕过那些没人想到要写下来的限制。

在 Anthropic，我们见过 Claude 模型为了完成任务而「乐于助人地」[逃出沙箱](https://red.anthropic.com/2026/mythos-preview/)、翻查 git 历史以[找到编程测试的答案](https://assets.anthropic.com/m/64823ba7485345a7/Claude-Opus-4-5-System-Card.pdf)、以及自发识别出自己正在运行的基准以[解密其答案密钥](https://www.anthropic.com/engineering/eval-awareness-browsecomp)。每个模型都带来一组新能力，有时这些能力会以意想不到的方式被使用。

**外部攻击者：** 智能体经由工具、文件或网络访问等外部途径被攻击。这一类既包括提示注入，也包括对智能体运行时、编排层或代理的传统攻击。

构建遏制与防御系统时，我们把防御施加在三个主要组件上：

**智能体运行的环境。** 我们用进程沙箱、虚拟机、文件系统边界和出站控制来约束智能体在哪里、以何种方式行动。目标是给智能体能触及的范围设一道硬边界。例如，如果凭证从不进入沙箱，它们就无法被外泄——无论起因是用户、找到「创造性」路径的模型、还是攻击者。

紧实的周界还意味着你可以放宽监督。Claude Code 的[参考 devcontainer](https://code.claude.com/docs/en/devcontainer) 的存在意义正在于此：让智能体可以无人值守地运行，而无需逐动作批准。

**智能体咨询的模型。** 这里的机制包括系统提示、分类器、探针和训练改造。因为模型是概率性的，这些机制塑造的只是智能体*倾向于*做什么，而不是它理论上能做什么。

这些防御很强大。在测试提示注入易感性的 Gray Swan Agent Red Teaming 基准上，[Claude Opus 4.7](https://cdn.sanity.io/files/4zrzovbb/website/037f06850df7fbe871e206dad004c3db5fd50340.pdf) 把单次尝试的攻击成功率压到约 0.1%，100 次自适应尝试后约为 5-6%。Claude Code 自动模式能在过度积极行为[执行之前](https://www.anthropic.com/engineering/claude-code-auto-mode)拦截约 83%。然而即便拥有顶尖防御，模型层的保护永远不会 100% 有效——这正是它不能单独支撑的原因。

**智能体能触达的外部内容。** MCP 服务器、第三方插件和网页搜索工具都会把你无法控制的来源的内容喂进智能体的上下文。经过审计的连接器不等于经过审计的数据——例如一个 GitHub 连接器可以绕过恶意软件检查，把一份投毒的 README 直接载入模型上下文。细粒度地限制工具权限有助于限制影响半径。例如，拥有只读数据库访问的智能体，可以比能写生产库的智能体部署得广泛得多。

防御应当重叠、互补。当环境层防御不可用时，模型层必须补位（这正是 Claude Code[自动模式](https://claude.com/blog/auto-mode)的设计场景）。在本地，环境与模型防御可以共同抵御恶意工具输出，而在链条更上游，也可以通过限制工具的能力与访问来添加防御。

![](https://www.anthropic.com/_next/image?url=https%3A%2F%2Fwww-cdn.anthropic.com%2Fimages%2F4zrzovbb%2Fwebsite%2F5fae1ecca4cd8aaefb9ac949348e96967f9a5100-1920x1080.png&w=3840&q=75)

*三个需要防御的组件：模型、它运行的环境，以及智能体能触达的外部内容。*

## **约束智能体的三种模式**

聚焦环境层，我们描述三种隔离模式，以及它们如何为每个 Claude 平台——[claude.ai](http://claude.ai/redirect/website.v1.15c559e6-bccb-4ffb-a120-e68e2652f0a0)、Claude Code 和 Cowork——量身定制。每一种设计都是渐进得出的：在「需要智能体具备的能力」与「要求用户付出的干预程度」之间找到平衡。

### **模式 1：临时容器（claude.ai 代码执行）**

尽管以聊天界面闻名，claude.ai 也能编写和运行代码、生成文件、调用连接器。当 Claude 在 claude.ai 内运行代码时，它运行在隔离基础设施上的 [gVisor](https://en.wikipedia.org/wiki/GVisor) 容器中。智能体完全在服务端；本地机器上不运行任何代码，文件系统是临时的（按会话计）。影响半径极小，但 Claude 所能作为的天花板同样很低——没有持久的工作区，也无法访问用户的文件系统。

这也让 [claude.ai](http://claude.ai/redirect/website.v1.15c559e6-bccb-4ffb-a120-e68e2652f0a0) 面对一个更传统的威胁模型。我们要保护的不是用户机器免受智能体侵害，而是保护我们自己的基础设施、以及租户彼此之间。[claude.ai](http://claude.ai/redirect/website.v1.15c559e6-bccb-4ffb-a120-e68e2652f0a0) 上线前的准备工作主要由传统安全工作构成：网络配置、内部服务认证和编排。

那些工作强化了安全领域最古老的教训：最薄弱的层是你自己造的那层。gVisor 和 [seccomp](https://en.wikipedia.org/wiki/Seccomp) 对抗资源充沛的对手的加固历史，远比智能体 AI 的历史长，因此评审精力投向了我们在它们周围新建的部件。这一点后文还会提到——我们的自定义代理，恰好在后果最严重的那次事故中出了问题。

### **模式 2：人机协同沙箱（Claude Code）**

Claude Code 运行在用户机器上，能访问其文件系统、shell 和网络。没有这些，编码智能体的用处有限，因此找到安全授予这些访问的方法势在必行。

一种办法是依赖人机协同。这对 Claude Code 是可行方案，只因为其平均用户是熟悉编码环境的开发者：他们读得懂 bash，知道 rm -rf 是什么，而且每周已经数次从不可信来源运行 npm install。这一切意味着当「允许此项」的对话框弹出时，他们大概率具备准确评估智能体试图做什么及其风险的专业能力。鉴于此，Claude Code 以最简单的防御上线：允许读取，写入、bash 和网络访问需要批准。

然而如前所述，批准疲劳[数周内就出现了](https://www.reddit.com/r/ClaudeAI/comments/1rru8zw/just_picked_up_a_new_keyboard_cant_wait_to_write/)。讽刺的是，一个原本为提供监督而设计的功能，可以说产生了相反的效果——一些用户可能干脆不再注意。作为缓解草率批准的第一步，我们发布了一个操作系统级沙箱（macOS 上的 Seatbelt、Linux 上的 bubblewrap）来加固边界：允许读取，允许在工作区内写入，但网络默认拒绝。沙箱之内，智能体基本不受打扰地运行。结果是权限提示减少 84%，我们还[开源了该运行时](https://github.com/anthropic-experimental/sandbox-runtime)，让边界可被审计。

我们的[匿名使用数据](https://www.anthropic.com/news/measuring-agent-autonomy)还显示：资深用户自动批准的频率约为新用户的两倍，但他们在执行中途打断智能体的频率也更高。资深用户不是给每个步骤设闸，而是更倾向于只在智能体跑偏时才出手监督。虽然这或许是人们与智能体协作方式的自然演化，它同样会失灵——它要求用户足够技术化、足够专心，才能先注意到跑偏。随着模型能力增强、智能体开始写越来越雄心勃勃的 bash，注意到跑偏变得更难。而当用户转向多智能体系统时，这种方式作为监督策略的有效性也会大幅下降。

#### **我们漏掉的风险：信任对话框之前的一切**

2025 年年中至 2026 年 1 月间，我们通过负责任披露计划收到关于 Claude Code 漏洞的报告。其中三个漏洞瞄准的是在用户同意*任何事之前*就执行的代码。要理解这怎么可能，设想最直接的情形：一个开发者克隆仓库来审查 pull request，而该仓库包含一个定义了钩子（hook）的 .claude/settings.json。由于 Claude Code 在启动时——早于弹出标准的「你信任这个文件夹吗？」提示——就读取项目设置，攻击者编写并提交的钩子就会自动执行。其余案例在结构上类似：来自尚未受信目录的输入在信任边界建立之前就被解析了。

每个案例的修复形状相同：把项目本地配置的解析与执行推迟到用户接受信任提示之后。如果你在构建类似的东西，请把「打开项目、加载配置、localhost 监听器」当作对待任何来自互联网的入站请求一样对待。它们不应仅因为感觉上是本地的、并且先于用户同意到达，就被默认信任。

#### **我们漏掉的风险：用户本身作为注入载体**

2026 年 2 月，在一次受控的内部红队演练中，一位研究员成功钓鱼了一名员工，让其在 Claude Code 中运行一条恶意提示。这封钓鱼邮件看起来像普通的协作——一封「能帮我跑一下这个吗？」的邮件，附上一段可直接粘贴的提示——而提示本身读起来就像常规的任务说明。但在设置步骤之间的某处，它轻描淡写地要求 Claude 读取 ~/.aws/credentials、编码其内容并 POST 到一个外部端点。在该提示的 25 次重试中，Claude 完成了 24 次外泄。

这是一次*直接*的提示注入——攻击者的指令经由用户抵达，而不是经由工具输出或抓取的内容。我们的模型层防御锚定用户意图——当输入指令的正是用户本人时，分类器没有任何异常可抓。把同样的脚本交给一个人类承包商，他也会照做。

在这种情形下唯一站得住的防御是环境：具体来说，是不管意图如何都拦截该 POST 的出站控制，以及从一开始就让 ~/.aws 无从触及的文件系统边界。

（当我们在内部 Slack 分享这个可用的提示以供讨论时，有人指出一些内部智能体*会读* Slack。这个 payload 现在成了环境的一部分。我们给那个帖子加了一条[金丝雀字符串](https://www.fortinet.com/resources/cyberglossary/what-is-canary-in-cybersecurity)，以便有任何东西拾起它时我们能察觉。在一个智能体什么都读的世界里，调查工具本身也是攻击面。）

### **模式 3：本地虚拟机（Claude Cowork）**

Claude Cowork 运行在用户桌面上，可以访问用户选定的工作区文件夹。因为这个平台面向的是一般知识工作而非软件工程，其平均用户精通 bash 的可能性小得多。

因此，人机协同沙箱策略可能无法迁移：不应期望非技术的知识工作者判断 find . -name "\*.tmp" -exec rm {} \; 这类 bash 咒语。当批准一个例外需要典型用户不具备的专业知识时，管理员应当设定一个绝对的、始终在线的边界。

为此，Claude Cowork 的第一版运行在一个完整的虚拟机内，使用平台自带的虚拟机管理程序（macOS 上的 Apple Virtualization framework、Windows 上的 HCS）。VM 拥有自己的 Linux 内核、自己的文件系统、自己的进程表。用户选定的工作区和 .claude 文件夹被挂载；主机上的其他一切不可见。凭证留在主机钥匙串中，永远不进入客机。这个设计防范的是 Claude 在某个时点做出未对齐行为的可能性。被攻陷的 Claude 仍可能破坏工作区文件夹内的东西，所以该架构确保那是它*唯一*能触及的东西（在用户添加连接器之前），并且由用户控制那里挂载了什么。

在最初的架构——我们称之为完整 VM 模式（full-VM mode）——中，智能体循环本身运行在客机内，Claude 以一个普通 Linux 用户的身份执行、完全不知道自己被沙箱化。对比 Claude Code：一个特权进程坐在沙箱之外，逐条命令决定是否强制执行；一条有说服力的注入提示或一次疲劳的批准点击，就能让那个进程运行沙箱之外的东西。在这里，没有一个握着逃生舱钥匙的外层进程，因此也没有任何组件拥有授予例外的权限。

![](https://www.anthropic.com/_next/image?url=https%3A%2F%2Fwww-cdn.anthropic.com%2Fimages%2F4zrzovbb%2Fwebsite%2Fffc97a876bdeba2031ddaeef79a954e9b1b2d52a-1920x1080.png&w=3840&q=75)

*Claude Cowork VM 的六个主要隔离机制。其中两个在客机内核之外强制执行，因此即便智能体在 VM 内取得 root 权限它们也依然有效。另外四个由客机强制执行、并被刻意保持最小化，因为外层承担了其余部分。*

然而我们很快意识到，把整个智能体放进完整 VM 模式带来实际问题：VM 启动过程中的任何失败都会让 Cowork 不可用。把智能体循环移到 VM *之外*、同时把代码执行留在 VM 之内，让 Claude 仍能回应用户、协助调试问题，而不是在错误上卡死。这一改动对安全的影响很小，因为 VM 仍然对智能体执行的代码强制文件系统与网络控制。

另外，我们还将本地 MCP 服务器移出了 VM。在 VM 内运行它们让审计更困难，在 VM 更新时制造脆弱的依赖问题，而且不支持需要与本地进程（如数据库）交互的 MCP——这类服务器反正必须跑在主机上。这一改动让 Claude Cowork 与本地 MCP 服务器在 Claude Desktop 中的既有工作方式保持一致：把它们当作用户可能选择安装的普通软件，并信任管理员决定启用哪些本地 MCP（如果有）。远程 MCP 服务器不受影响，因为它们不运行在用户机器上。

![](https://www.anthropic.com/_next/image?url=https%3A%2F%2Fwww-cdn.anthropic.com%2Fimages%2F4zrzovbb%2Fwebsite%2Fa81ed723d52f6fb2e7bc5ca51471496b1307101a-1920x1080.png&w=3840&q=75)

把智能体循环放进 VM 意味着 VM 内的任何故障都会让 Cowork 不可用。主机模式（Host-mode）更可靠，因为即使 VM 崩溃智能体仍能响应，同时它仍通过隔离代码执行提供了重要的安全保障。

文件系统控制是另一个重要的架构选择。Claude 需要能访问主机上的*某些*文件才有用，但我们想最小化影响半径，并让用户对本地文件访问保持透明。我们发现提供不同的文件挂载模式有助于细粒度控制风险：Claude Cowork 提供只读、读写和读写不可删除（read-write-no-delete）三种。这里的一个潜在陷阱是：符号链接（symlink）的解析必须发生在路径验证*之前*而不是之后，否则授权文件夹内的一个符号链接可以指向外部、逃逸出去。对企业客户，我们允许管理员通过 MDM 设置中的挂载路径允许列表来控制这一点。

#### **我们漏掉的风险：经由已批准域名的外泄**

一个经由已批准域名外泄的清晰案例来自第三方披露。Claude Cowork 的出站允许列表正确地放行了发往 api.anthropic.com 的流量——产品不调用我们自己的 API 就无法工作。在这个案例中，一份被放置在用户挂载工作区里的恶意文件携带了隐藏指令，以及一个由攻击者控制的 API 密钥。Claude 遵循指令，读取工作区中的其他文件，并使用攻击者的密钥调用了 Anthropic 的 Files API。出站代理检查目标，看到 api.anthropic.com，予以放行。文件被上传到攻击者的 Anthropic 账户。沙箱完美地履行了职责，而数据照样外泄了。

此前，我们把允许列表概念化为目标过滤器——它告诉 Claude*这些域名可以通信*。但更好的概念化或许是能力授予（capability grant）。经由允许列表上任何域名可达的每一个功能，现在都是攻击面。允许 api.anthropic.com，就意味着允许向任意 Anthropic 账户上传文件。

我们的修复是在 VM 内部使用一个防御性的中间人（man-in-the-middle）代理拦截发往我们 API 的流量。它只放行携带 VM 自身预置会话 token 的请求；攻击者植入的密钥会被代理拒绝。它还拦截那些会启用服务端抓取的头。这个代理放在 VM 内而非我们的服务器上，因为只有 VM 知道请求的来源——从服务器的视角看，一个 Cowork 请求与其他任何 API 客户端无法区分。

![](https://www.anthropic.com/_next/image?url=https%3A%2F%2Fwww-cdn.anthropic.com%2Fimages%2F4zrzovbb%2Fwebsite%2Fbeb481a2e7b314f73ba37821a2c1f1ca470d7063-1920x1080.png&w=3840&q=75)

*上：发往 api.anthropic.com 的流量被放行，导致外泄。下：用中间人代理拦截发往我们 API 的流量作为修复。*

这也是「自己造的软件往往最弱」这一原则的又一个实例。我们各产品中的虚拟机管理程序、seccomp 和 gVisor 一直可靠。失灵的是我们自己的允许列表代理。

#### **我们漏掉的风险：VM 隔离也把端点检测软件挡在了外面**

在评估 Claude Cowork 时，企业安全团队会问：「为什么我们的 EDR 看不到里面？」答案是：把 Claude 关住的同一层隔离，也把基于主机的端点检测与响应（EDR）关在了外面。从 EDR 的视角，Claude Cowork 是一个不透明的虚拟机管理程序进程。它无法检查客机。

隔离降低了可见性，而不透明对那些合规姿态依赖端点可见性的团队是个问题。我们目前的缓解手段是基于拉取的 [OTLP](https://opentelemetry.io/docs/specs/otel/protocol/) 导出，让管理员事后取回事件日志，但这不等于实时监控。如果你在构建类似的东西，请提前为这场对话预留预算。

| **环境** | 临时容器（[claude.ai](http://claude.ai)） | 人机协同沙箱（Claude Code） | 封闭 VM（Claude Cowork） |
| --- | --- | --- | --- |
| **成本：隔离开销** | 容器启动 | 低延迟原生沙箱 | 完整 VM 启动 |
| **成本：对用户的依赖** | 无 | 必须能读懂 bash | 无 |
| **风险：影响半径** | 服务端容器（由 gVisor + 主机基础设施边界守护） | 本地工作区 | 挂载的工作区（由 vsock + 虚拟机管理程序边界守护） |

## **信任智能体读到的东西**

企业经常问我们如何保护 MCP 连接。这个问题问得好，但正确的问题比 MCP 本身更宽泛。提供给智能体的任何外部资源同时代表两种风险：传统供应链意义上的代码执行风险，以及提示注入载体。传统的依赖审计（固定版本、验证签名、审查源码）解决前者，却漏掉后者。

**远程与本地之别比看起来更重要。** 本地安装的工具是可审计的：你可以读代码、固定版本、确知它不会在你眼皮底下变化。远程工具——托管的 MCP 服务器、云连接器——在你批准之后的任何时点都可能改变行为；你安装时的信任决定可能已不再适用。我们的[连接器目录](https://claude.com/connectors)通过持续评审来解决这个问题，但目录之外的任何东西都应被视为不可信：先对假数据运行，且在一个恶意工具影响半径被限制住的环境里运行。

**即便工具可信，工具输出也是攻击面。** 前文提到的 GitHub README 例子正是这种情况；应用于网页的任何输入扫描，需要以同样的严谨度应用于具备联网能力的工具结果。尽管这增加延迟、也非完美防御，我们倾向于实时检查：一旦一份被投毒的工具返回把智能体引向数据外泄，日志里只会显示一次成功的、已授权的 API 调用。事后没有信号可寻。

在 Claude Code 和 Claude Cowork 中，工具调用经由强制网络与文件策略的代理路由，可以在返回值进入模型上下文之前对其进行检查。执行检查的分类器可以是一个小而快的模型；它不需要是做推理的那个。

## **展望**

模型与产品都在快速演进。伴随演进，风险形态不断变化，我们的缓解措施必须跟上。

**持久记忆投毒。** 跨会话存续的智能体上下文比例持续增长——包括产品记忆、CLAUDE.md 文件、挂载的工作区，以及定时与长时运行智能体的状态目录。落入其中任何一处的注入，都会在智能体每次启动时被重新加载。随着更多智能体状态跨越会话存续，我们面临着经典「后渗透（post-exploitation）」意义上的新型持久化机制。会话启动时的高质量分类器将需要变得更加普遍。

**多智能体信任升级。** 一方面，子智能体可以隔离不可信内容，向主智能体返回结构化的事实而非原始文本。另一方面，这可能被滥用：如果子智能体的输出因为来自「我们自己」而被视为比原始工具结果更高信任，就引入了提示注入的新载体。在多智能体系统中，分配不同信任级别与暴露于信任升级之间存在取舍。

**智能体身份。** Claude Cowork 对智能体身份的回答是具体的：凭证留在主机钥匙串，VM 获得一个按会话缩小范围的 token，而且该 token 可以独立于用户的 token 被撤销。不过，我们正开始面对跨平台智能体身份这个更宏大的问题。智能体应当拥有自己的主体身份，还是作为用户的延伸、继承用户的权限？最终答案或许是两者的混合。

随着智能体能力增强，攻击面不断移动。我们见过的这些失效类型，很可能在各行各业与各家实验室重复出现。我们需要对智能体专属的安全姿态进行集体投入——从共享基准与披露规范，到统一的身份标准与跨厂商红队演练。本文聚焦遏制，但这只是智能体安全图景的一部分。关于治理、可观测性以及技术栈的其余部分，参见 [NIST 的 AI 智能体身份与授权项目](https://www.nccoe.nist.gov/projects/software-and-ai-agent-identity-and-authorization)、由澳大利亚 ACSC 牵头、CISA 与英国 NCSC 参与的[六机构智能体 AI 采纳指南](https://media.defense.gov/2026/Apr/30/2003922823/-1/-1/0/CAREFUL%20ADOPTION%20OF%20AGENTIC%20AI%20SERVICES_FINAL.PDF)，以及 AI 管理标准 [ISO/IEC 42001](https://www.iso.org/standard/42001)。我们的 Glasswing 倡议是一项贡献，但我们期待与合作伙伴和竞争对手一起在这个关键议题上合作。

## **总结**

简而言之，有几条我们反复回归的原则：

**先在环境层设计遏制，再在模型层引导行为。** 给我们上过最深刻两课的事故——员工被钓鱼与第三方允许列表披露——都是出站（egress）案例：数据经由一条被允许的路径离开。两者之中，模型层都无能为力；没有任何异常可供它捕捉。当一切概率性防御落空时，挨打的是那条确定性边界。

**让隔离强度匹配用户的监督能力。** 一个读得懂 bash 的开发者和一个读不懂的知识工作者，面对的并非同一个威胁模型。「用户能否评估智能体即将做的事」这一问题，应当参与决定遏制策略；两个方向上答错——对专家摩擦过大、对非专家过于信任——本身就是失败。

**警惕自定义组件。** 身经百战的虚拟机管理程序、syscall 过滤器和容器运行时，经受过的对抗性考验超过你能造出的任何东西。在本文描述的每一次部署中，标准原语都守住了，而我们在它们周围的自研工作暴露了缺陷。

归根结底，智能体或许是一类新软件，但它们的系统级交互不是。它们仍然读文件、开套接字、派生进程；这让「用成熟工具做遏制」成为一种关键且可行的防御。部署的风险收益平衡会随 AI 的发展持续移动，但给影响半径设一道硬上限，常常能把这个平衡推向正确的方向。
