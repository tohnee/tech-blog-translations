# 面向 AI 智能体的高效上下文工程

> 原文：[Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) · Anthropic Engineering Blog

在提示工程（prompt engineering）成为应用 AI 焦点的几年之后，一个新术语开始崭露头角：**上下文工程**（context engineering）。用语言模型构建应用，正变得越来越不只是为提示找到合适的词句，而是要回答一个更宏观的问题：「什么样的上下文配置最有可能让模型产生我们想要的行为？」

**上下文**指的是从大语言模型（LLM）采样时纳入的那组 token。这里的**工程**问题，就是在 LLM 固有约束下优化这些 token 的效用，以稳定达成期望结果。驾驭 LLM 往往需要*在上下文中思考*——也就是说：通盘考虑 LLM 在任一时刻可获得的整体状态，以及这种状态可能引发哪些行为。

本文将探讨上下文工程这门新兴技艺，并为构建可操控、高效的智能体提供一个更精炼的心智模型。

## 上下文工程 vs. 提示工程

在 Anthropic，我们把上下文工程视为提示工程的自然延伸。提示工程指为获得最优结果而编写和组织 LLM 指令的方法（概述与实用策略见[我们的文档](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview)）。**上下文工程**指的是在 LLM 推理期间策划并维护最优 token（信息）集合的一整套策略，包括那些可能经由提示之外途径进入上下文的所有信息。

在 LLM 工程的早期，提示是 AI 工程工作中最大的组成部分，因为日常聊天之外的多数用例都需要为一次性分类或文本生成任务优化提示。正如其名，提示工程的首要焦点是如何写出有效的提示，尤其是系统提示。然而，随着我们转向构建在多轮推理和更长时间跨度上运行的更强智能体，我们需要管理整个上下文状态的策略（系统指令、工具、[模型上下文协议](https://modelcontextprotocol.io/docs/getting-started/intro)（MCP）、外部数据、消息历史等）。

循环运行的智能体会产生越来越多的、*可能*与下一轮推理相关的数据，这些信息必须被循环地精炼。上下文工程就是从那个不断演化的信息宇宙中，策划哪些内容进入有限上下文窗口的[艺术与科学](https://x.com/karpathy/status/1937902205765607626?lang=en)。

![Prompt engineering vs. context engineering](https://www.anthropic.com/_next/image?url=https%3A%2F%2Fwww-cdn.anthropic.com%2Fimages%2F4zrzovbb%2Fwebsite%2Ffaa261102e46c7f090a2402a49000ffae18c5dd6-2292x1290.png&w=3840&q=75)

*与「写好一条提示」这种离散任务不同，上下文工程是迭代式的——每当我们决定向模型传递什么时，策划环节就会发生一次。*

## 为什么上下文工程对构建强能力智能体至关重要

尽管 LLM 速度飞快、能管理越来越大的数据量，我们观察到它们和人类一样，会在某个临界点上失焦或混乱。对大海捞针式基准的研究揭示了一个概念——[上下文腐化（context rot）](https://research.trychroma.com/context-rot)：随着上下文窗口中 token 数量的增加，模型从上下文中准确回忆信息的能力在下降。

虽然有些模型的退化比其他模型平缓，但这一特性在所有模型上都会出现。因此，上下文必须被视为一种边际收益递减的有限资源。就像人类[工作记忆容量有限](https://journals.sagepub.com/doi/abs/10.1177/0963721409359277)一样，LLM 在解析大量上下文时也要消耗一份「注意力预算」。每引入一个新 token 都会消耗一定预算，这更凸显了为 LLM 精心策划可用 token 的必要。

这种注意力稀缺源于 LLM 的架构约束。LLM 基于 [transformer 架构](https://arxiv.org/abs/1706.03762)，其中每个 token 可以[关注](https://huggingface.co/blog/Esmail-AGumaan/attention-is-all-you-need)整个上下文中的每个其他 token，对 n 个 token 产生 n² 个成对关系。

随着上下文长度增加，模型捕捉这些成对关系的能力被摊薄，上下文规模与注意力焦点之间形成天然张力。此外，模型的注意力模式学自训练数据分布，而训练数据中短序列通常远多于长序列。这意味着模型对全上下文依赖关系的经验更少、专门参数也更少。

像[位置编码插值](https://arxiv.org/pdf/2306.15595)这样的技术让模型能把更长序列适配到原先训练的较小上下文上，但对 token 位置的理解会有所退化。这些因素形成的是一条性能梯度而非断崖：模型在长上下文下仍然能力很强，但信息检索和长程推理的精度可能低于短上下文时的表现。

这些现实意味着，深思熟虑的上下文工程对构建强能力智能体必不可少。

## 高效上下文的解剖

鉴于 LLM 受限于有限的注意力预算，*好的*上下文工程意味着找到*尽可能小的*高信号 token 集合，使期望结果出现的可能性最大化。实践起来说来容易做来难，但在接下来的小节中，我们概述这条指导原则在上下文各个组成部分中的具体含义。

**系统提示**应当极其清晰，使用简单直接的语言，以*合适的高度*呈现想法。合适的高度是两种常见失败模式之间的「刚刚好」区间。一个极端是，工程师在提示里硬编码复杂、脆弱的逻辑，以期引出精确的智能体行为——这会带来脆弱性并随时间推高维护复杂度。另一个极端是，工程师给出模糊、泛泛的指导，无法给 LLM 提供指向期望输出的具体信号，或错误地假设了共享上下文。最优高度在于平衡：足够具体以有效引导行为，又足够灵活以给模型提供强启发式来指导行动。

![Calibrating the system prompt in the process of context engineering.](https://www.anthropic.com/_next/image?url=https%3A%2F%2Fwww-cdn.anthropic.com%2Fimages%2F4zrzovbb%2Fwebsite%2F0442fe138158e84ffce92bed1624dd09f37ac46f-2292x1288.png&w=3840&q=75)

*光谱的一端是脆弱的 if-else 硬编码提示；另一端是过于笼统、或错误假设共享上下文的提示。*

我们建议把提示组织成不同的区块（如 `<background_information>`、`<instructions>`、`## Tool guidance`、`## Output description` 等），并使用 XML 标签或 Markdown 标题来划分这些区块——尽管随着模型能力增强，提示的确切格式正变得没那么重要。

无论你决定如何组织系统提示，都应追求用最小信息集完整勾勒你期望的行为。（注意「最小」不等于「短」；你仍需要预先给智能体足够的信息，确保它遵守期望的行为。）最好的做法是：先用最小提示搭配现有最强的模型，看它在你的任务上表现如何，然后根据初测发现的失败模式，补充清晰的指令和示例来改进。

**工具**让智能体能与所处环境交互，并在工作中引入新的上下文。由于工具定义了智能体与其信息/行动空间之间的契约，工具必须促进效率——既返回省 token 的信息，也鼓励高效的智能体行为。

在[《为 AI 智能体编写高效工具——用 AI 智能体来写》](https://www.anthropic.com/engineering/writing-tools-for-agents)中，我们讨论过构建 LLM 容易理解、功能重叠最少的工具。与设计良好的代码库中的函数一样，工具应当自包含、对错误鲁棒、用途极其明确。输入参数同样应当描述性强、无歧义，并顺应模型的固有优势。

我们最常见的失败模式之一是臃肿的工具集：覆盖的功能太多，或在使用哪个工具的决策点上留下歧义。如果人类工程师都无法断言给定情况下该用哪个工具，就不能指望 AI 智能体做得更好。正如后文将讨论的，为智能体策划一个最小可行工具集，也有助于在长交互中更可靠地维护和修剪上下文。

提供示例——又称少样本提示（few-shot prompting）——是公认的最佳实践，我们仍然强烈建议使用。但团队常常把一长串边界情况塞进提示，试图穷举 LLM 在特定任务上应遵循的每一条规则。我们不推荐这样做。更好的做法是精心策划一组多样的、典范的示例，有效刻画智能体的期望行为。对 LLM 而言，示例是「值一千字」的图片。

我们对上下文各组成部分（系统提示、工具、示例、消息历史等）的总体建议是：深思熟虑，让上下文信息丰富而紧凑。接下来深入运行时的动态上下文检索。

## 上下文检索与智能体搜索

在[《构建高效 AI 智能体》](https://www.anthropic.com/research/building-effective-agents)中，我们强调过基于 LLM 的工作流与智能体的区别。自那篇文章之后，我们逐渐倾向一个[简洁的定义](https://simonwillison.net/2025/Sep/18/agents/)：智能体就是「在循环中自主使用工具的 LLM」。

与客户合作的过程中，我们看到整个领域正在向这个简单范式收敛。随着底层模型能力增强，智能体的自主程度可以扩展：更聪明的模型让智能体能够独立驾驭微妙的问题空间、从错误中恢复。

我们现在看到工程师为智能体设计上下文的思路正在转变。今天，许多 AI 原生应用采用某种基于嵌入的推理前检索，为智能体浮现重要上下文供其推理。随着领域转向更智能体的方式，我们越来越多地看到团队在这些检索系统之上叠加「按需加载」（just in time）的上下文策略。

「按需加载」方式构建的智能体不是预先处理所有相关数据，而是维护轻量的标识符（文件路径、存储的查询、网页链接等），并在运行时借助工具用这些引用把数据动态加载进上下文。Anthropic 的智能体编码方案 [Claude Code](https://www.anthropic.com/claude-code) 就用这种方式对大型数据库执行复杂的数据分析：模型可以编写有针对性的查询、存储结果，并利用 head、tail 等 Bash 命令分析海量数据，而从不把完整的数据对象载入上下文。这一路径与人类认知相仿：我们通常不会记住整个信息语料，而是建立外部组织与索引系统——文件系统、收件箱、书签——按需检索相关信息。

除了存储效率，这些引用的元数据还提供了一种高效精炼行为的机制，无论其是显式给出还是直观可感的。对一个在文件系统中工作的智能体来说，`tests` 文件夹里出现一个名为 `test_utils.py` 的文件，与 `src/core_logic/` 目录下同名文件的用途暗示截然不同。文件夹层级、命名约定、时间戳都提供了重要信号，帮助人类和智能体理解如何以及何时利用信息。

让智能体自主导航和检索数据还支持渐进式披露（progressive disclosure）——换句话说，智能体可以通过探索逐步发现相关上下文。每次交互产出的上下文又为下一步决策提供信息：文件大小暗示复杂度；命名约定暗示用途；时间戳可以充当相关性的代理。智能体可以层层组装理解，只在工作记忆中保留必要内容，并借助记笔记策略做额外持久化。这种自我管理的上下文窗口让智能体聚焦于相关子集，而不是溺死在穷举却可能无关的信息里。

当然这里有取舍：运行时探索比取回预计算数据更慢。不仅如此，还需要有主见、有心思的工程，确保 LLM 拥有正确的工具和启发式来高效导航其信息版图。缺乏恰当引导时，智能体会因滥用工具、追逐死胡同、或识别不出关键信息而浪费上下文。

在某些场景下，最有效的智能体可能采用混合策略：预先取回部分数据以保证速度，再自行决定是否继续自主探索。「恰当」自主度的决策边界取决于任务。Claude Code 就是采用这种混合模型的智能体：[CLAUDE.md](http://claude.md) 文件被简单地预先放入上下文，而 glob、grep 这些原语让它能按需导航环境、取回文件，有效绕过了索引过期和复杂语法树的问题。

混合策略可能更适合内容动态性较低的场景，例如法律或金融工作。随着模型能力提升，智能体设计将趋向于「让聪明的模型聪明地行动」，人类策划的成分逐渐减少。鉴于这个领域的进展速度，「做最简单的可行方案」很可能仍是我们给在 Claude 之上构建智能体的团队的最佳建议。

### 面向长周期任务的上下文工程

长周期任务要求智能体在动作序列中保持连贯性、上下文和目标导向行为，而其 token 数量超出了 LLM 的上下文窗口。对于横跨数十分钟到数小时连续工作的任务——如大型代码库迁移或综合研究项目——智能体需要专门技术来绕开上下文窗口大小的限制。

等更大的上下文窗口出现看似是显然的对策。但很可能在可预见的未来，各种尺寸的上下文窗口都逃不开上下文污染和信息相关性问题——至少在追求最强智能体表现时如此。为了让智能体能在延展的时间跨度上高效工作，我们开发了几个直接应对上下文污染约束的技术：压缩（compaction）、结构化笔记（structured note-taking）和多智能体架构。

**压缩（Compaction）**

压缩是指：当对话接近上下文窗口上限时，总结其内容，并用摘要重新初始化一个新的上下文窗口。压缩通常是上下文工程中改善长期连贯性的第一根杠杆。其核心是以高保真的方式提炼上下文窗口的内容，使智能体能在最小的性能损失下继续工作。

以 Claude Code 为例，我们把消息历史传给模型，让它总结并压缩最关键的细节。模型保留架构决策、未解决的 bug 和实现细节，丢弃冗余的工具输出或消息。随后智能体带着这份压缩上下文加上最近访问的五个文件继续工作。用户获得连续性，而无需担心上下文窗口的限制。

压缩的艺术在于取舍——留什么、弃什么，因为过度激进的压缩会丢失那些微妙却关键、重要性日后才显现的上下文。对实现压缩系统的工程师，我们建议在复杂的智能体轨迹上仔细调优提示：先最大化召回，确保压缩提示捕捉轨迹中每一条相关信息；然后迭代改进精确度，剔除冗余内容。

一个立竿见影的冗余内容是清除工具调用及其结果——当某个工具早已在消息历史深处被调用过，智能体为什么还需要再看一遍原始结果？最安全、最轻量的压缩形式之一就是工具结果清除，最近已作为 [Claude 开发者平台的一项功能](https://www.anthropic.com/news/context-management)上线。

**结构化笔记（Structured note-taking）**

结构化笔记，又称智能体记忆（agentic memory），是一种让智能体定期把笔记写入上下文窗口之外持久存储的技术。这些笔记会在之后被拉回上下文窗口。

这一策略以极小的开销提供持久记忆。就像 Claude Code 创建待办清单，或你的自定义智能体维护一个 NOTES.md 文件，这个简单模式让智能体能在复杂任务间跟踪进度，保住那些否则会在几十次工具调用中丢失的关键上下文和依赖关系。

[Claude 玩宝可梦](https://www.twitch.tv/claudeplayspokemon)展示了记忆如何在非编码领域改变智能体能力。这个智能体在数千个游戏步骤中维护精确的计数——追踪诸如「过去 1,234 步我一直在 1 号道路训练我的宝可梦，皮卡丘已升到目标 10 级中的第 8 级」之类的目标。在没有任何关于记忆结构的提示下，它自行发展出已探索区域的地图、记住自己解锁了哪些关键成就，并维护着战斗策略的战略笔记，帮助它学会对不同的对手哪种攻击最有效。

上下文重置之后，智能体读取自己的笔记，继续长达数小时的训练序列或地牢探索。这种跨越摘要步骤的连贯性，使长周期策略成为可能——只靠 LLM 的上下文窗口保存全部信息是做不到这些的。

作为 [Sonnet 4.5 发布](https://www.anthropic.com/effective-context-engineering-for-ai-agents)的一部分，我们在 Claude 开发者平台上发布了[记忆工具](http://anthropic.com/news/context-management)公开测试版，通过基于文件的系统更轻松地在上下文窗口之外存储和查阅信息。这让智能体能够逐步积累知识库、跨会话维护项目状态、引用此前的工作，而不必把一切都留在上下文里。

**子智能体架构**

子智能体架构提供了绕开上下文限制的另一条路。与其让一个智能体试图在整个项目中维持状态，不如让专门的子智能体以干净的上下文窗口处理聚焦任务。主智能体依据一份高层计划进行协调，子智能体执行深入的技术工作或使用工具查找相关信息。每个子智能体可能大举探索，消耗数万乃至更多 token，但只返回一份浓缩的、蒸馏后的工作摘要（通常 1,000-2,000 token）。

这种做法实现了清晰的关注点分离——详细的搜索上下文被隔离在子智能体内部，主智能体专注于综合与分析结果。这个模式在[《我们如何构建多智能体研究系统》](https://www.anthropic.com/engineering/multi-agent-research-system)中讨论过，在复杂研究任务上比单智能体系统有显著优势。

如何在几种方案之间选择取决于任务特性。例如：

- 压缩为需要大量往复对话的任务保持会话流畅；
- 记笔记擅长有清晰里程碑的迭代式开发；
- 多智能体架构处理复杂研究与分析——并行探索在那里最有回报。

即便模型持续进步，在长时间交互中保持连贯性的挑战仍将是构建更强智能体的核心命题。

## 结语

上下文工程代表着我们用 LLM 构建应用方式的一次根本转变。随着模型能力增强，挑战不再只是写出完美的提示，而是在每一步都深思熟虑地策划哪些信息进入模型有限的注意力预算。无论你是在为长周期任务实现压缩、设计省 token 的工具，还是让智能体按需探索环境，指导原则始终如一：找到使期望结果可能性最大化的最小高信号 token 集合。

随着模型改进，我们概述的这些技术还会继续演化。我们已经看到更聪明的模型需要更少的规定性工程，智能体能够以更多自主性运作。但即便能力不断扩展，把上下文当作珍贵且有限的资源来对待，仍将是构建可靠、高效智能体的核心。

今天就在 Claude 开发者平台上开始上下文工程，并通过我们的[记忆与上下文管理](https://platform.claude.com/cookbook/tool-use-memory-cookbook) cookbook 获取实用技巧与最佳实践。
