# 量化智能体编码评估中的基础设施噪声

> 原文：[Quantifying infrastructure noise in agentic coding evals](https://www.anthropic.com/engineering/infrastructure-noise) · Anthropic Engineering Blog

SWE-bench 和 Terminal-Bench 这类智能体编码基准常被用来比较前沿模型的软件工程能力——排行榜上头部名次之间的差距往往只有几个百分点。这些分数常被当作模型相对能力的精确度量，并越来越多地影响「部署哪个模型」的决策。然而我们发现，仅基础设施配置一项就能产生超出这些差距的差异。在内部实验中，Terminal-Bench 2.0 上资源最充足与最拮据的配置之间相差 6 个百分点（p < 0.01）。

静态基准直接给模型的输出打分——运行环境不进入结果。智能体编码评估不同：模型拿到一个完整的环境，在其中写程序、跑测试、装依赖、多轮迭代。运行时不再是一个被动的容器，而是解题过程的组成部分。两个拥有不同资源预算和时间限制的智能体，考的已经不是同一张卷子。

评估开发者已经开始正视这一点。例如 Terminal-Bench 在最新的 2.0 版本中按任务规定了推荐的 CPU 和内存。但「规定资源」不等于「一致地强制执行」。此外我们发现，强制执行的方法论本身会改变这个基准实际度量的东西。

## **我们是怎么发现的**

我们在一个 Google Kubernetes Engine 集群上运行 Terminal-Bench 2.0。校准配置时，我们注意到我们的分数与基准的官方排行榜对不上，而且基础设施错误率高得惊人：多达 6% 的任务因 pod 错误而失败，其中大多数与模型解题能力无关。

分数的差异归结为强制执行方式。我们的 Kubernetes 实现把每任务资源规格同时当作下限和硬上限：每个容器保证获得指定的资源，但一超过就立刻被杀。容器运行时通过两个独立参数强制资源：一个保证分配（预先预留的资源）和一个硬限制（达到即杀容器）。当两者设为同一值时，瞬时尖峰没有任何余量：一次短暂的内存波动就可能 OOM 杀掉一个本可成功的容器。为了应对这一点，Terminal-Bench 的排行榜使用了另一个沙箱提供商，其实现更宽松，允许临时超额分配而不终止容器，以换取基础设施的稳定性。

这一发现引出一个更大的问题：资源配置对评估分数的影响到底有多大？

为了量化脚手架的影响，我们在六种资源配置下运行 Terminal-Bench 2.0：从严格强制每任务规格（1x，同时作为下限和上限），到完全不设上限。其余一切保持恒定：同一个 Claude 模型、同一个 harness、同一组任务。

在我们的实验中，成功率随资源余量增加而上升。这主要由基础设施错误率在每一步单调下降驱动：从严格强制下的 5.8% 降到不设上限时的 0.5%。从严格强制到 3 倍余量之间的下降（5.8% 到 2.1%）在 p < 0.001 水平显著。余量越大，因超出分配被杀的容器越少。

从 1x 到 3x，成功分数在噪声区间内波动（p=0.40）。1x 下崩溃的大多数任务无论如何都会失败——这一点我们在数据中观察到了。智能体探索、撞上资源之墙、被抢占，但它本来就走在一条通向正确解的路上。

然而从 3x 左右开始，趋势变了：成功率的攀升快于基础设施错误的下降。

从 3x 到不设上限，基础设施错误再降 1.6 个百分点，而成功率跳升近 4 个百分点。额外的资源让智能体可以尝试那些只有充足分配才可行的做法，例如拉取大型依赖、派生昂贵的子进程、运行吃内存的测试套件。在不设上限的资源下，相对 1x 的总提升为 +6 个百分点（p < 0.01）。在临界处，`rstan-to-pystan` 和 `compile-compcert` 这类任务在获得内存余量后成功率显著改善。

## **这如何影响测量**

在大约 3 倍 Terminal-Bench 规格以内，额外的资源修复的是基础设施可靠性问题，即瞬时资源尖峰。Terminal-Bench 维护者使用的沙箱提供商实际上在幕后做的就是这件事：评估变得更稳定，但没有变得更简单。

超过 3 倍之后，额外资源开始主动帮助智能体解出以前解不出的问题，这说明限制确实会改变评估所度量的东西。紧的限制无意中奖励极其高效的策略，而宽松的限制更宽容、奖励更能充分利用全部资源的智能体。

一个写得精炼高效、速度极快的智能体会在紧约束下表现良好。一个用重型工具暴力破解的智能体会在宽松约束下表现良好。两者都是合理的考察点，但把它们压缩成单一分数而不注明资源配置，会让差异——以及真实世界中的可迁移性——难以解读。

在 `bn-fit-modify` 这个要求做贝叶斯网络拟合的 Terminal-Bench 任务上，一些模型的第一步是安装标准 Python 数据科学全家桶：`pandas`、`networkx`、`scikit-learn` 以及整个工具链。在宽松限制下这行得通；在紧限制下，pod 在安装期间、智能体还没写一行解题代码时就内存耗尽了。存在一条更精炼的路线（只用标准库从零实现数学），一些模型确实默认走这条路线，另一些不走。不同模型有不同的默认路径，而资源配置决定了哪条路径恰好能成功。我们在不同的 Anthropic 模型上复现了这一核心发现。效应方向一致，幅度各异。同样的趋势似乎也适用于 Claude 之外的其他模型，但我们尚未严格测试。

我们还在 Terminal-Bench 之外的评估上检验了这一模式是否成立，方法是在 SWE-bench 上做交叉实验。我们在 227 个问题上把可用总内存最高调到基线的 5 倍，每个问题 10 个样本。同样的效应成立，只是幅度更小：分数仍随内存单调上升，但 5x 只比 1x 高 1.54 个百分点。SWE-bench 任务对资源的要求较低，效应更小在预期之内，但这说明资源分配在那里同样不是中性的。

## **其他方差来源**

资源分配不是唯一的隐藏变量。在某些配置下，时间限制也开始扮演角色。

原则上，评估设置的每一个元素都可能影响最终分数：从集群健康到硬件规格，从并发级别到出口带宽。智能体评估从构造上就是端到端系统测试，该系统的任何组件都可能成为混杂因素。我们曾趣闻式地观察到通过率随一天中的时段波动，很可能是因为 API 延迟随流量模式和事故变化。我们没有正式量化这一效应，但它说明了一个更大的道理：「模型能力」与「基础设施行为」之间的边界，比单一基准分数所暗示的更模糊。模型提供商可以通过专用硬件把评估基础设施与这些影响隔离开，外部评估者却难以做到同样的事。

公开基准的本意通常是度量纯粹模型能力，但实践中它们有把能力与基础设施怪癖混为一谈的风险。有时这或许是可取的——它让整条技术栈都能端到端测试——但更多时候并非如此。对打算公开共享的编码评估，在多个时间点、多天运行有助于把噪声平均掉。

## **我们的建议**

理想情形是在完全相同的硬件条件下运行每次评估——包括运行评估的脚手架和推理栈——这将确保全面的完美可复现。但这并不总是可行。

鉴于容器运行时实际强制资源的方式——一个保证分配加上一个独立的硬性击杀阈值——我们建议评估按任务同时规定这两个参数，而不是单一固定值。单一精确规格会让保证分配等于击杀阈值，余量为零：我们在 1x 记录到的瞬时内存尖峰就足以让评估失稳。把两个参数分开，可以让容器有足够的呼吸空间避免虚假的 OOM 击杀，同时仍维持一个防止分数膨胀的硬上限。

两者之间的区间应当经过校准，使下限和上限处的分数落在彼此的噪声范围内。例如在 Terminal-Bench 2.0 上，把每任务规格乘以 3 作为上限，把基础设施错误率削减了约三分之二（5.8% 到 2.1%，p < 0.001），而分数提升温和、完全在噪声范围内（p = 0.40）。这是一个合理的折中：基础设施混杂因素被大体中和，同时保留了有意义的资源压力。具体乘数会因基准和任务分布而异，因此应当报告出来，但经验校准的原则是通用的。

## **我们为何关心**

这些发现的影响超出了评估基础设施。基准分数正日益被用作决策输入，但这种日益增长的关注（和依赖）并不总伴随着运行与报告上相应的严谨。就现状而言，排行榜上 2 个百分点的领先，可能反映真实的能力差距，也可能反映一次评估跑在更强的硬件上，甚至只是赶上了更走运的时段，或两者兼有。在配置没有公布（或没有标准化）的情况下，除非有关各方格外卖力、在完全相同的条件下复现客观结果，外界很难分辨。

对 Anthropic 这样的实验室而言，其含义是：智能体评估的资源配置应被当作一等实验变量，以与提示格式或采样温度同等的严谨程度来记录和控制。对基准维护者而言，公布推荐的资源规格（如 Terminal-Bench 2.0 所做的那样）已大有裨益，而写明强制执行的方法论将弥合我们识别出的缺口。对所有消费基准结果的人来说，核心结论是：智能体评估上的小分差，比报告数字的精度所暗示的更不确定——尤其当某些混杂因素根本无法控制时。

在资源方法论标准化之前，我们的数据表明：排行榜上低于 3 个百分点的差距，在评估配置被记录并比对之前，值得保持怀疑。我们在 Terminal-Bench 适度资源配置范围内观察到的差距略低于 2 个百分点。朴素的二项置信区间本就有 1-2 个百分点的跨度；我们在这里记录的基础设施混杂因素是叠在其上，而不是含在其中。在分配范围的极端处，差距达到 6 个百分点。

几分的领先，可能意味着真实的能力差距——也可能只是更大的一台虚拟机。
