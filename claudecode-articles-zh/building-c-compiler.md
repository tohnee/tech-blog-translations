# 用一支并行 Claude 团队构建 C 编译器

> 原文：[Building a C compiler with a team of parallel Claudes](https://www.anthropic.com/engineering/building-c-compiler) · Anthropic Engineering Blog

*作者 Nicholas Carlini，我们 Safeguards 团队的研究员。*

我一直在试验一种监督语言模型的新方法，我们称之为「agent teams（智能体团队）」。

在 agent teams 模式下，多个 Claude 实例在一个共享代码库上并行工作，无需人类持续干预。这种方法极大扩展了 LLM 智能体所能达成的事情的范围。

为了压力测试它，我给 16 个智能体布置了任务：从零开始写一个基于 Rust 的 C 编译器，要求能够编译 Linux 内核。经过近 2,000 个 Claude Code 会话和 2 万美元 API 成本，这支智能体团队产出了一个 10 万行的编译器，可以在 x86、ARM 和 RISC-V 上构建 Linux 6.9。

[这个编译器本身就是一个有趣的产物](https://github.com/anthropics/claudes-c-compiler)，但我在这里聚焦的是关于为长时运行自主智能体团队设计执行框架的经验：如何编写无需人类监督也能让智能体保持正轨的测试，如何组织工作让多个智能体得以并行推进，以及这条路线的天花板在哪里。

## 让 Claude 长时间运行

现有的智能体脚手架（如 Claude Code）要求操作者在线并随时可以协同。如果你请求解决一个又长又复杂的问题，模型可能解决其中一部分，但最终它会停下来等待继续输入——一个问题、一条状态更新，或一个澄清请求。

为了引出持续的、自主的进展，我构建了一个把 Claude 塞进简单循环的 harness（如果你见过 Ralph-loop，这应该看着眼熟）。它每完成一个任务，就立刻领起下一个。*（请在容器里运行，别在你的真实机器上跑。）*

```
#!/bin/bash

while true; do
    COMMIT=$(git rev-parse --short=6 HEAD)
    LOGFILE="agent_logs/agent_${COMMIT}.log"

    claude --dangerously-skip-permissions \
           -p "$(cat AGENT_PROMPT.md)" \
           --model claude-opus-X-Y &> "$LOGFILE"
done
```

在智能体提示中，我告诉 Claude 要解决什么问题，并要求它把问题拆成小块、跟踪自己正在做什么、弄清下一步做什么，以及实际上持续工作直到完美为止。（关于最后一点，Claude 没得选：这个循环永远运行——不过有一次，我确实看到 Claude 误敲了 `pkill -9 bash`，把自己杀掉、终止了循环。哎哟！）

## 并行运行 Claude

并行运行多个实例可以弥补单智能体 harness 的两个短板：

- 一个 Claude Code 会话一次只能做一件事。随着项目范围扩大，并行调试多个问题要高效得多。
- 运行多个 Claude 智能体允许专业化。当一部分智能体负责解决手头的实际问题时，可以调用其他专门的智能体去（比如）维护文档、盯紧代码质量、或解决专门的子任务。

我的并行 Claude 实现非常朴素。新建一个裸 git 仓库，为每个智能体启动一个 Docker 容器，把仓库挂载到 `/upstream`。每个智能体克隆一份本地副本到 `/workspace`，完成工作后从自己的本地容器推送到 upstream。

为防止两个智能体同时解决同一个问题，harness 用了一个简单的同步算法：

1. Claude 通过向 current_tasks/ 写一个文本文件来对任务「上锁」（例如，一个智能体锁定 current_tasks/parse_if_statement.txt，另一个锁定 current_tasks/codegen_function_definition.txt）。如果两个智能体试图认领同一个任务，git 的同步机制会迫使第二个智能体另选一个。
2. Claude 处理任务，然后从 upstream 拉取、合并其他智能体的改动、推送自己的改动、移除锁。合并冲突很频繁，但 Claude 足够聪明，能处理。
3. 无限的智能体生成循环在全新容器里派生一个新的 Claude Code 会话，循环往复。

这是一个非常早期的科研原型。我还没有实现任何其他智能体间通信机制，也没有强制任何管理高层目标的流程。我不使用编排智能体。

相反，我把决定权交给每个 Claude 智能体自己。大多数情况下，Claude 会捡起「下一个最显然」的问题。被 bug 卡住时，Claude 常常会维护一份记录失败尝试和剩余任务的滚动文档。在项目的 [git 仓库](https://github.com/anthropics/claudes-c-compiler)里，你可以通读历史，看它对各种任务上锁的过程。

## 与 Claude 智能体团队协作编程的教训

脚手架让 Claude 在循环中运行，但这个循环只有在 Claude 知道如何取得进展时才有用。我的大部分精力花在设计 Claude 周围的环境——测试、环境、反馈——让它无需我也能自我定位。以下是我发现对编排多个 Claude 实例最有帮助的做法。

### 编写极高质量的测试

Claude 会自主解决我给它的任何问题。所以任务验证器必须近乎完美，否则 Claude 会解错问题。改进测试 harness 需要寻找高质量的编译器测试套件、为开源软件包编写验证器和构建脚本、观察 Claude 犯的错，然后在我识别出这些失败模式时设计新的测试。

例如，临近项目尾声时，Claude 开始频繁地在每次实现新功能时破坏既有功能。为此，我搭建了一条持续集成流水线，实施了更严格的强制检查，让 Claude 能更好地测试自己的工作，确保新提交不会破坏既有代码。

### 置身 Claude 的位置

我必须不断提醒自己：这个测试 harness 是为 Claude 写的，不是为我自己写的。这意味着要重新审视许多关于「测试应该如何呈现结果」的假设。

例如，每个智能体都被丢进一个没有任何上下文的全新容器，会花大量时间自我定位，在大项目上尤其如此。在谈到测试之前，为了帮 Claude 自助，我加入了维护详尽 README 和进度文件的指示，要求它们随当前状态频繁更新。

我还时刻记着语言模型的固有局限——在这个场景里，需要围绕它们来设计。包括：

- **上下文窗口污染：** 测试 harness 不应打印成千上万无用的字节。它最多打印几行输出，并把所有重要信息记录到文件，让 Claude 需要时能找到。日志文件应易于自动处理：有错误时，Claude 应写下 ERROR 并把原因放在同一行，以便 grep 找到。预先计算好聚合统计也有帮助，省得 Claude 重新计算。
- **时间盲：** Claude 不会看表，放任不管的话，它会开心地花几个小时跑测试而不是取得进展。harness 以较低频率打印增量进展（避免污染上下文），并带一个默认的 `--fast` 选项，运行 1% 或 10% 的随机抽样。这个子样本对每个 agent 是确定性的、但在 VM 之间随机，因此 Claude 仍能覆盖全部文件，而每个智能体都能完美识别回归。

### 让并行变容易

当存在许多互不相同的失败测试时，并行化是平凡问题：每个智能体挑一个不同的失败测试去做。测试套件达到 99% 通过率后，每个智能体负责让一个不同的小型开源项目（如 SQlite、Redis、libjpeg、MQuickJS、Lua）编译通过。

但当智能体开始编译 Linux 内核时，它们卡住了。与有数百个独立测试的测试套件不同，编译 Linux 内核是一整块巨型任务。每个智能体都会撞上同一个 bug、修掉它，然后互相覆盖对方的改动。跑 16 个智能体也无济于事，因为每个都卡在同一个任务上。

解决办法是用 [GCC](https://gcc.gnu.org/) 作为在线的已知良好编译器 oracle 来对照。我写了一个新的测试 harness：用 GCC 随机编译内核的大部分文件，只用 Claude 的 C 编译器编译其余文件。如果内核能跑，问题就不在 Claude 那部分文件里；如果跑不起来，就再用 GCC 重编译其中一些文件来进一步收窄。这让每个智能体得以并行工作、修不同文件里的不同 bug，直到 Claude 的编译器最终能编译所有文件。（在这招奏效之后，还需要用 delta debugging 技术找出那些合在一起失败、各自独立却正常的文件对。）

### 多种智能体角色

并行化还让专业化成为可能。LLM 写的代码经常重复实现既有功能，于是我派一个智能体专门合并它发现的重复代码。另一个负责提升编译器自身的性能，第三个负责让它输出高效的编译产物。我还让一个智能体从 Rust 开发者的视角批评项目设计、并对项目做结构性改动以提升整体代码质量，再让一个专注文档。

## 压测 agent teams 的极限

这个项目被设计成一个能力基准。我有兴趣压测 LLM 今天*勉强*能达成的极限，帮助我们为模型未来稳定达成的水准做好准备。

我一直在把 C 编译器项目作为横跨 Claude 4 整个模型系列的基准。与之前的做法一样，我先起草我想要的东西：一个从零开始的、无依赖的优化编译器，GCC 兼容，能编译 Linux 内核，并设计为支持多后端。我规定了设计的某些方面（例如它应当有一个 SSA IR 以支持多个优化 pass），但没有写任何实现细节。

此前的 Opus 4 系列模型勉强能产出一个功能正常的编译器。Opus 4.5 是第一个跨过门槛的——能产出可以通过大型测试套件的功能性编译器——但仍无法编译任何真实的大型项目。Opus 4.6 上我的目标是再次试探极限。

### 评估

两周内近 2,000 个 Claude Code 会话中，Opus 4.6 消耗了 20 亿输入 token、生成了 1.4 亿输出 token，总成本略低于 2 万美元。即便与最贵的 Claude Max 套餐相比，这也是一个极其昂贵的项目。但这个总额只是我自己亲手做出来所需成本的零头——更别提一整个团队了。

这是一个净室实现（Claude 在整个开发期间任何时候都无法访问互联网）；它只依赖 Rust 标准库。这个 10 万行的编译器可以在 x86、ARM 和 RISC-V 上构建可启动的 Linux 6.9。它还能编译 QEMU、FFmpeg、SQlite、postgres、redis，在包括 [GCC torture 测试套件](https://gcc.gnu.org/onlinedocs/gccint/Torture-Tests.html)在内的大多数编译器测试套件上达到 99% 的通过率。它还通过了开发者的终极试金石：能编译并运行 Doom。

不过这个编译器并非没有局限，包括：

- 它缺少从实模式（real mode）启动 Linux 所需的 16 位 x86 编译器。这部分它调用 GCC（x86_32 和 x86_64 编译器是它自己的）。
- 它没有自己的汇编器和链接器；这是 Claude 最后才开始自动化的部分，仍有不少 bug。演示视频是用 GCC 的汇编器和链接器制作的。
- 编译器能成功构建很多项目，但不是全部。它还不是真实编译器的即插即用替代品。
- 生成的代码效率不高。即使开启全部优化，它输出的代码也不如*关闭*全部优化的 GCC 高效。
- Rust 代码质量尚可，但离专家级 Rust 程序员的水准还差得远。

最终的编译器已逼近 Opus 能力的极限。我努力尝试修复上述几个局限，但没有完全成功。新功能和 bugfix 经常破坏既有功能。

举一个特别有挑战性的例子：Opus 无法实现从 16 位实模式启动所需的 16 位 x86 代码生成器。虽然编译器可以通过 66/67 操作码前缀输出正确的 16 位 x86，但最终编译产物超过 60KB，远超 Linux 强制的 32K 代码上限。于是 Claude 在这里干脆取巧，这一阶段调用 GCC。（只有 x86 如此。对 ARM 或 RISC-V，Claude 的编译器可以完全靠自己编译。）

[编译器的源代码已开放](https://github.com/anthropics/claudes-c-compiler)。下载它、通读代码、在你喜欢的 C 项目上试试。我始终认为，理解语言模型能做什么的最好方式，就是把它们推到极限，然后研究它们在哪里开始崩坏。接下来的几天，我会继续让 Claude 推送新的改动——如果你想跟进 Claude 应对这些局限的持续尝试。

## 展望

每一代语言模型都会开启与之协作的新方式。早期模型在 IDE 里做 tab 补全。不久之后，模型能根据 docstring 写出函数体。Claude Code 的发布把智能体带向主流，让开发者能与 Claude 结对编程。但以上每种产品都建立在同一个假设之上：用户定义任务，LLM 运行几秒或几分钟返回答案，然后用户提供后续输入。

agent teams 展示了自主完成整个复杂项目的可能性。这让我们这些工具的使用者可以对自己的目标更有雄心。

我们仍处于早期，完全自主的开发伴随着真实的风险。当人类在开发过程中坐在 Claude 旁边，可以保证一致的质量、实时捕捉错误。对自主系统来说，很容易看到测试通过就假定大功告成——而实际情况很少如此。我以前做渗透测试，利用大公司产品里的漏洞，一想到程序员部署自己从未亲自验证过的软件，就真的令人担忧。

所以，这个实验既让我兴奋，也让我不安。构建这个编译器是我最近玩得最开心的项目之一，但我没想到这在 2026 年初就几乎成为可能。语言模型与我们与之交互的脚手架的快速进步，为写下海量新代码打开了大门。我预计正面应用会多于负面，但我们正在进入一个需要新策略才能安全导航的新世界。
