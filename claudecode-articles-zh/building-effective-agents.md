# 构建高效智能体

> 原文：[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) · Anthropic Engineering Blog

*注：本文所描述的许多工具生态自 2024 年 12 月以来已发生变化。关于我们当前的做法，请参见[「我们如何构建 Claude Managed Agents」](https://www.anthropic.com/engineering/managed-agents)* *以及 [**Managed Agents 文档**。](https://platform.claude.com/docs/en/managed-agents/overview)*

过去一年里，我们与数十个跨行业的团队合作构建大语言模型（LLM）智能体。一个始终一致的观察是：最成功的实现并没有使用复杂的框架或专门的库，而是用简单、可组合的模式来构建。

在这篇文章中，我们分享与客户合作以及亲手构建智能体的经验，并为开发者提供构建高效智能体的实用建议。

## 什么是智能体？

「智能体」（agent）有多种定义方式。一些客户把智能体定义为能在较长时间内独立运行、使用各种工具完成复杂任务的完全自主系统；另一些人则用这个词指代遵循预定义工作流、更具规范性的实现。在 Anthropic，我们把上述所有形态都归为**智能体系统**（agentic systems），但在架构上区分**工作流**（workflow）与**智能体**（agent）：

- **工作流**：LLM 和工具通过预定义代码路径进行编排的系统。
- **智能体**：LLM 动态主导自身流程和工具使用的系统，自行掌控完成任务的方式。

下面我们将详细探讨这两类智能体系统。在附录 1（「实践中的智能体」）中，我们描述了客户从这类系统中获得特殊价值的两个领域。

## 何时（以及何时不）使用智能体

用 LLM 构建应用时，我们建议先寻找尽可能简单的方案，只在必要时增加复杂度。这可能意味着完全不构建智能体系统。智能体系统常用延迟和成本换取更好的任务表现，你需要权衡这种交换何时是值得的。

当确实需要更多复杂度时：对于定义明确的任务，工作流提供可预测性和一致性；而当需要大规模的灵活性与模型驱动的决策时，智能体是更好的选择。但对许多应用而言，通过检索和上下文示例优化单次 LLM 调用通常就足够了。

## 何时以及如何使用框架

有许多框架能让智能体系统更容易实现，包括：

- [Claude Agent SDK](https://platform.claude.com/docs/en/agent-sdk/overview)；
- [AWS 的 Strands Agents SDK](https://strandsagents.com/latest/)；
- [Rivet](https://rivet.ironcladapp.com/)，一个拖拽式 GUI LLM 工作流构建器；
- [Vellum](https://www.vellum.ai/)，另一个用于构建和测试复杂工作流的 GUI 工具。

这些框架通过简化调用 LLM、定义和解析工具、串联调用等标准底层任务，让上手变得容易。但它们往往会增加额外的抽象层，遮蔽底层的提示与响应，使调试更困难；也会诱使你在更简单的配置就够用时引入不必要的复杂度。

我们建议开发者从直接使用 LLM API 开始：许多模式用几行代码就能实现。如果你确实要用框架，请确保理解其底层代码。对底层机制的错误假设是客户出错的常见根源。

示例实现见我们的 [cookbook](https://platform.claude.com/cookbook/patterns-agents-basic-workflows)。

## 构件、工作流与智能体

本节探讨我们在生产环境中见到的智能体系统常见模式。我们从基础构件——增强型 LLM（augmented LLM）——出发，逐步增加复杂度，从简单的组合式工作流到自主智能体。

### 构件：增强型 LLM

智能体系统的基本构件是经过检索、工具、记忆等增强的 LLM。我们当前的模型能够主动使用这些能力——自行生成搜索查询、选择合适的工具、决定保留哪些信息。

![](https://www.anthropic.com/_next/image?url=https%3A%2F%2Fwww-cdn.anthropic.com%2Fimages%2F4zrzovbb%2Fwebsite%2Fd3083d3f40bb2b6f477901cc9a240738d3dd1371-2401x1000.png&w=3840&q=75)

增强型 LLM

我们建议关注实现上的两个关键点：让这些能力贴合你的具体用例，并确保它们为 LLM 提供简单易用、文档完善的接口。实现这些增强的方式有很多，其一是我们最近发布的 [Model Context Protocol（模型上下文协议）](https://www.anthropic.com/news/model-context-protocol)，它让开发者通过简单的[客户端实现](https://modelcontextprotocol.io/tutorials/building-a-client#building-mcp-clients)接入不断增长的第三方工具生态。

在本文余下部分，我们假设每次 LLM 调用都能使用这些增强能力。

### 工作流：提示链（prompt chaining）

提示链把任务分解为一系列步骤，每次 LLM 调用处理上一步的输出。你可以在任意中间步骤加入程序化检查（见下图中的「gate/门」），确保流程仍在正轨上。

![](https://www.anthropic.com/_next/image?url=https%3A%2F%2Fwww-cdn.anthropic.com%2Fimages%2F4zrzovbb%2Fwebsite%2F7418719e3dab222dccb379b8879e1dc08ad34c78-2401x1000.png&w=3840&q=75)

提示链工作流

**何时使用这种工作流：** 当任务可以轻松、干净地分解为固定子任务时，提示链是理想选择。它的主要目标是用延迟换取更高准确率——让每次 LLM 调用都变成更简单的任务。

**提示链的适用示例：**

- 生成营销文案，再将其翻译成另一种语言。
- 先写文档大纲，检查大纲是否满足特定标准，再基于大纲撰写文档。

### 工作流：路由（routing）

路由对输入进行分类，并将其导向专门的后续任务。这种工作流实现了关注点分离，便于构建更专业的提示。若无路由，针对某一类输入的优化可能损害其他输入上的表现。

![](https://www.anthropic.com/_next/image?url=https%3A%2F%2Fwww-cdn.anthropic.com%2Fimages%2F4zrzovbb%2Fwebsite%2F5c0c0e9fe4def0b584c04d37849941da55e5e71c-2401x1000.png&w=3840&q=75)

路由工作流

**何时使用这种工作流：** 路由适用于存在明显类别区分、分开处理效果更好的复杂任务，且分类可以由 LLM 或更传统的分类模型/算法准确完成。

**路由的适用示例：**

- 把不同类型的客服问询（一般问题、退款请求、技术支持）导入不同的下游流程、提示和工具。
- 把简单/常见的问题路由给 Claude Haiku 4.5 这样更小、更省成本的模型，把困难/罕见的问题路由给 Claude Sonnet 4.5 这样更强的模型，以优化整体表现。

### 工作流：并行化（parallelization）

LLM 有时可以同时处理一项任务，再由程序汇总它们的输出。并行化工作流有两个关键变体：

- **切分（sectioning）**：把任务拆成可并行运行的独立子任务。
- **投票（voting）**：多次运行同一任务以获得多样化的输出。

![](https://www.anthropic.com/_next/image?url=https%3A%2F%2Fwww-cdn.anthropic.com%2Fimages%2F4zrzovbb%2Fwebsite%2F406bb032ca007fd1624f261af717d70e6ca86286-2401x1000.png&w=3840&q=75)

并行化工作流

**何时使用这种工作流：** 当切分出的子任务可以并行以提速，或需要多个视角/多次尝试以获得更高置信度的结果时，并行化很有效。对于有多重考量的复杂任务，让每个考量由独立的 LLM 调用分别处理通常表现更好，使每个具体方面都能得到专注处理。

**并行化的适用示例：**

- **切分**：
  - 实现防护栏（guardrail）：一个模型实例处理用户查询，另一个实例筛查不当内容或请求。这通常比让同一次 LLM 调用同时负责防护栏和核心回答表现更好。
  - 自动化评估 LLM 表现：每次 LLM 调用评估模型在给定提示上表现的不同侧面。
- **投票**：
  - 审查代码漏洞：多个不同提示各自审查代码，发现问题即标记。
  - 判断某内容是否不当：多个提示从不同侧面评估，或设置不同的投票阈值，以平衡误报与漏报。

### 工作流：编排者-执行者（orchestrator-workers）

在编排者-执行者工作流中，中心 LLM 动态分解任务，将其委派给执行者 LLM，并综合它们的结果。

![](https://www.anthropic.com/_next/image?url=https%3A%2F%2Fwww-cdn.anthropic.com%2Fimages%2F4zrzovbb%2Fwebsite%2F8985fc683fae4780fb34eab1365ab78c7e51bc8e-2401x1000.png&w=3840&q=75)

编排者-执行者工作流

**何时使用这种工作流：** 它适合无法预测所需子任务的复杂任务（例如编码任务中，需要改动的文件数量和每个文件改动的性质往往取决于具体任务）。它在拓扑结构上与并行化相似，关键区别在于灵活性——子任务不是预先定义的，而是由编排者根据具体输入确定。

**编排者-执行者的适用示例：**

- 每次都要对多个文件做复杂改动的编码产品。
- 需要从多个来源收集并分析信息以寻找相关内容的搜索任务。

### 工作流：评估者-优化者（evaluator-optimizer）

在评估者-优化者工作流中，一次 LLM 调用生成回答，另一次调用在循环中提供评估与反馈。

![](https://www.anthropic.com/_next/image?url=https%3A%2F%2Fwww-cdn.anthropic.com%2Fimages%2F4zrzovbb%2Fwebsite%2F14f51e6406ccb29e695da48b17017e899a6119c7-2401x1000.png&w=3840&q=75)

评估者-优化者工作流

**何时使用这种工作流：** 当有明确的评估标准、且迭代改进能带来可度量的价值时，这种工作流特别有效。契合的两个标志：一是当人类清楚表达反馈时，LLM 的回答能被证实得到改善；二是 LLM 自身也能提供这样的反馈。这类似于人类写作者打磨一篇文稿时经历的迭代过程。

**评估者-优化者的适用示例：**

- 文学翻译：译文中存在翻译 LLM 初次可能捕捉不到的细微之处，而评估 LLM 能给出有用的批评。
- 需要多轮搜索与分析才能收集全面信息的复杂搜索任务：由评估者判断是否需要继续搜索。

### 智能体

随着 LLM 在关键能力上日趋成熟——理解复杂输入、进行推理与规划、可靠地使用工具、从错误中恢复——智能体正走向生产环境。智能体的工作始于人类用户的指令或交互式讨论。一旦任务明确，智能体便独立规划并执行，过程中可能回到人类处获取更多信息或判断。执行期间，智能体必须在每一步从环境中获得「 ground truth 」（如工具调用结果或代码执行结果）来评估进展，这一点至关重要。智能体可以在检查点或遇到阻塞时暂停以等待人类反馈。任务通常在完成时终止，但加入停止条件（如最大迭代次数）以保持控制也很常见。

智能体能处理复杂任务，但其实现往往很简单。它们通常就是在循环中基于环境反馈使用工具的 LLM。因此，清晰而周到地设计工具集及其文档至关重要。我们在附录 2（「对工具做提示工程」）中进一步展开工具开发的最佳实践。

![](https://www.anthropic.com/_next/image?url=https%3A%2F%2Fwww-cdn.anthropic.com%2Fimages%2F4zrzovbb%2Fwebsite%2F58d9f10c985c4eb5d53798dea315f7bb5ab6249e-2401x1000.png&w=3840&q=75)

自主智能体

**何时使用智能体：** 智能体适用于难以或无法预测所需步骤数的开放性问题，以及无法硬编码固定路径的场景。LLM 可能运行许多轮，你必须对其决策能力有一定程度的信任。智能体的自主性使其非常适合在可信环境中规模化执行任务。

智能体的自主特性意味着更高的成本和错误累积的可能。我们建议在沙箱环境中充分测试，并配备适当的防护栏。

**智能体的适用示例：**

以下示例来自我们自己的实现：

- 一个用于解决 [SWE-bench 任务](https://www.anthropic.com/research/swe-bench-sonnet)的编码智能体，这类任务需要根据任务描述对多个文件进行修改；
- 我们的[「计算机使用」（computer use）参考实现](https://github.com/anthropics/anthropic-quickstarts/tree/main/computer-use-demo)，Claude 操作计算机来完成任务。

## 组合与定制这些模式

这些构件并非硬性规定，而是开发者可以塑造和组合以适配不同用例的常见模式。成功的钥匙与其他 LLM 特性一样：度量表现，迭代实现。再强调一遍：只有当复杂度能被证实改善结果时，你*才*应该增加复杂度。

## 总结

在 LLM 领域取得成功，不在于构建最精密复杂的系统，而在于为你的需求构建*恰当的*系统。从简单的提示开始，用全面的评估来优化它们，只有在更简单的方案力不从心时才引入多步智能体系统。

实现智能体时，我们努力遵循三条核心原则：

1. 保持智能体设计的**简洁性**。
2. 通过显式展示智能体的规划步骤来保证**透明性**。
3. 通过充分的工具**文档与测试**，精心打磨你的智能体-计算机接口（ACI）。

框架可以帮你快速起步，但在走向生产时，不要犹豫减少抽象层、用基础组件来构建。遵循这些原则，你就能创建不仅强大，而且可靠、可维护、被用户信任的智能体。

## 附录 1：实践中的智能体

我们与客户的合作揭示了 AI 智能体两个特别有前景的应用方向，印证了上述模式的实用价值。这两个应用都表明：智能体在同时需要对话与行动、有清晰成功标准、支持反馈循环、并融入有意义的人类监督的任务中，能创造最大价值。

### A. 客户支持

客户支持把大家熟悉的聊天机器人界面与工具集成带来的增强能力结合起来。它天然适合较为开放式的智能体，因为：

- 支持交互天然遵循对话流，同时需要访问外部信息和执行操作；
- 可以集成工具来拉取客户数据、订单历史和知识库文章；
- 退款、更新工单等操作可以程序化处理；
- 成功与否可以通过用户自定义的「解决」标准清晰度量。

多家公司已经通过与解决结果挂钩的按用量计费模式（只为成功解决收费）证明了这条路线的可行性，显示出对其智能体效力的信心。

### B. 编程智能体

软件开发领域已展现出 LLM 特性的巨大潜力，能力从代码补全一路演进到自主解决问题。智能体在这里尤其有效，因为：

- 代码方案可以通过自动化测试来验证；
- 智能体能以测试结果为反馈迭代方案；
- 问题空间定义良好且结构化；
- 输出质量可以客观度量。

在我们自己的实现中，智能体如今仅凭 pull request 描述就能解决 [SWE-bench Verified](https://www.anthropic.com/research/swe-bench-sonnet) 基准中的真实 GitHub issue。不过，虽然自动化测试有助于验证功能，人工审查对于确保方案符合更广泛的系统要求仍然至关重要。

## 附录 2：对工具做提示工程

无论你构建哪种智能体系统，工具都可能是智能体的重要组成部分。[工具](https://www.anthropic.com/news/tool-use-ga)让 Claude 能够与外部服务和 API 交互，方式是在我们的 API 中指定其精确的结构和定义。当 Claude 计划调用某个工具时，它会在 API 响应中包含一个[工具使用块（tool use block）](https://docs.anthropic.com/en/docs/build-with-claude/tool-use#example-api-response-with-a-tool-use-content-block)。工具定义和规范应当获得与整体提示同等的提示工程投入。在这个简短的附录中，我们说明如何对工具做提示工程。

同一个动作往往有多种指定方式。例如，文件编辑既可以通过写 diff 来指定，也可以重写整个文件；结构化输出既可以放在 markdown 里，也可以放在 JSON 里。在软件工程中，这类差异是表面性的，可以无损地相互转换。但对 LLM 而言，有些格式比其他格式难写得多：写 diff 需要在写出新代码之前就知道 chunk 头部中有多少行在变；在 JSON 里写代码（相比 markdown）需要对换行符和引号做额外转义。

我们对工具格式选择的建议如下：

- 给模型足够的 token 去「思考」，避免它把自己写进死角。
- 让格式尽量接近模型在互联网文本中天然见过的样子。
- 确保没有格式「开销」，比如必须精确数清数千行代码的行数，或对自己写的代码做字符串转义。

一条经验法则：想想人机界面（HCI）需要投入多少心力，然后计划在创建良好的*智能体*-计算机接口（ACI）上投入同样的心力。以下几点思考供参考：

- 置身于模型的位置想一想：仅凭描述和参数，这个工具的用法是否一目了然？还是需要你仔细琢磨？如果是后者，对模型多半也是如此。好的工具定义通常包含用法示例、边界情况、输入格式要求，以及与其他工具的清晰界限。
- 如何修改参数名或描述能让事情更直观？把这当作给团队里的初级开发者写一份出色的 docstring。使用许多相似工具时尤其重要。
- 测试模型如何使用你的工具：在我们的 [workbench](https://console.anthropic.com/workbench) 里运行大量示例输入，观察模型犯什么错，然后迭代。
- 给你的工具做[防错设计（Poka-yoke）](https://en.wikipedia.org/wiki/Poka-yoke)：调整参数，让犯错变得更难。

在为 [SWE-bench](https://www.anthropic.com/research/swe-bench-sonnet) 构建智能体时，我们花在优化工具上的时间实际上超过了整体提示。例如，我们发现当智能体离开根目录后，模型在使用相对文件路径的工具时会出错。为修复这个问题，我们把工具改成始终要求绝对文件路径——结果发现模型完美地使用了这种方式。
