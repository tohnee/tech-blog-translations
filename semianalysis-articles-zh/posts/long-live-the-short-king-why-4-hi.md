# 矮堆叠之王万岁：为什么 4-hi HBM 胜出

> 原文：[Long Live the Short King: Why 4-hi HBM Wins](https://newsletter.semianalysis.com/p/long-live-the-short-king-why-4-hi) · SemiAnalysis

> ⚠️ 付费订阅文章：以下为公开可见的预览部分翻译，正文在付费墙处截断，并非全文。

**同样的带宽，更少的裸片：4-hi HBM 如何降低推理成本、让稀缺的 DRAM 物尽其用**

高带宽内存（HBM）一直是支撑 AI 革命的关键技术之一。尽管 HBM 相对其他形式的内存成本高昂，芯片设计者仍在 AI 加速器中封装了越来越多的 HBM。客户一方面推动在设计中导入更新一代的 HBM，另一方面又通过增加 HBM 堆叠（cube）数量、采用更高密度和更高的堆叠来提升每颗 XPU 的容量。这导致 HBM 消耗的总 DRAM 晶圆产能份额不断攀升，最终造成了我们当下所处的极端 DRAM 短缺。

如今我们正处在这一趋势被打破的临界点，原因既有技术层面的，也有供应链层面的。当下的标准是 12 层堆叠，而下一代加速器正转向以 8 层堆叠为新基准。Nvidia 已决定在 Rubin Ultra 上这么做——相比标准版 Rubin 和 B300，每 GPU 容量从 288GB 下调至 192GB，[SemiAnalysis 最先报道了这一变化](https://semianalysis.com/memory-model/)。供应链目前正在为 8-hi 成为新标准做准备，而就在不到一年前，业界还在预期迈向 16-hi 甚至更高。

不过，正如我们在 [Memory Model](https://semianalysis.com/memory-model/) 中所论述的，我们认为这一趋势还会走得更远。对于内存带宽最为关键的推理工作负载而言，4 层堆叠（4-hi）HBM 提供了最优的 $/带宽，因而每个 token 的成本最低。容量在达到某个阈值之前很重要，超过该阈值后，更多 HBM 容量带来的边际收益递减，而这些增量比特给物料清单（BOM）带来的成本惩罚却分毫不少。这正是各大实验室的硬件团队希望从下一代 HBM4 起在自己的 ASIC 项目中落地方向。就像硬件设计师在数据中心电力受限的世界里专注于最大化每瓦特 token 数（tokens/Watt）一样，4-hi 是最大化每片 HBM 晶圆 token 数的方法——晶圆同样是稀缺资源。

本报告将梳理容量方程式到底发生了什么变化，论证 HBM 容量经常处于「搁浅」状态，并说明这如何成为实验室 TCO 与内存供应商盈利能力的双赢。

# **每芯片 HBM 容量持续增长的趋势已被打破**

HBM 一直是 AI 工作负载的主要工作内存形式，因为它在容量与带宽之间取得了良好平衡，可同时服务于训练和推理的通用芯片。SRAM 虽然速度极快，却受限于容量不足，因而昂贵且只能用于特定任务。传统 DDR DRAM 每美元能买到的容量多得多，但带宽又太差。

AI 是如此吃内存的工作负载，因此每颗加速器的 HBM 容量一代代持续攀升也就不足为奇：每颗加速器堆叠更多、单叠密度更高、堆叠层数更高。

![](https://substack-post-media.s3.amazonaws.com/public/images/cdf2cf49-36cb-4efc-815d-e6357e31380f_2048x1241.png)
*来源：SemiAnalysis、Nvidia*

每颗芯片搭载的 HBM 数量不断增加，也是成本上升的一大推手。然而过去几个月，这一趋势已经被打破。下一代 Rubin Ultra 每颗加速器将只配备 192GB HBM，而标准版 Rubin 乃至 Blackwell Ultra 都是 288GB！相比不到一年前的预期，这是巨大的倒退——当时业界预期 Rubin Ultra 每 GPU 会配备 1TB HBM！平心而论，那是因为当时 Rubin Ultra 预计有 4 颗计算裸片，而现在只有 2 颗。即便按此归一化，这也意味着每颗计算裸片的容量从 256GB 降到了仅 96GB。

![](https://substack-post-media.s3.amazonaws.com/public/images/9c8c4f19-2116-4b81-821d-eb0f1b054624_1929x538.png)
*来源：SemiAnalysis、Nvidia*

下调 HBM 密度的决定在很大程度上是供给驱动的。HBM 晶圆极度稀缺。现有晶圆根本不足以供应与 Nvidia 明年锁定的 N3 逻辑产能和 CoWoS 产能相匹配所需的 12 层堆叠数量。转向 8-hi 意味着从有限的晶圆中产出多得多的堆叠，有助于弥合缺口。

明年 HBM 成本的大幅上涨更是雪上加霜，[尽管 Nvidia 拿到的条件已经比其他大客户更好](https://newsletter.semianalysis.com/i/213613469/expanding-beyond-memory-across-the-ai-infrastructure-stack-comes-at-a-cost)。即便在 GPU 需求远超供给的时期，Nvidia 也不得不让出一部分利润率，因为其组件成本在上涨，而其中内存是最大头。

HBM 密度持续增长的趋势正在被打破，而且不仅仅是供给原因，还有架构原因和工作负载需求的变化。供给和成本固然是非常重要的因素，但如果这部分额外容量对客户不可或缺、并能明确带来更好的性能/TCO，Nvidia 是不会做这个决定的。本文的核心论点是：在很多情况下，每 GPU 增加 HBM 容量并不值这个成本，未来 4-hi HBM 往往才是最优配置。

# **更矮的堆叠，同样的带宽**

我们想提醒读者的一个重要动态是：通过降低堆叠高度来削减每 GPU 容量，完全不以牺牲带宽为代价。无论堆叠高度如何，每个 HBM 堆叠可用的带宽是相同的。每颗 HBM4 或 HBM4e 堆叠有 2048 个数据 I/O，这些数据通路被平均分配给堆叠中的全部核心 DRAM 裸片，每颗裸片最多 512 个 I/O。这意味着 4-hi 是能够用满全部 2048 个 I/O、实现最大带宽的最低堆叠高度。然而，供应商和终端客户的成本主要由每个堆叠中的 DRAM 容量决定。HBM 定价主要按每堆叠的 GB 数计算，而客户从 HBM 中获得的价值却往往是带宽。因此，更低的堆叠高度对终端客户意味着低得多的 $/带宽——选择更矮的堆叠几乎是免费的午餐。

![](https://substack-post-media.s3.amazonaws.com/public/images/60418044-6f62-4f41-a607-7c5ee52c61ea_1588x946.png)
*来源：SemiAnalysis*

# **带宽 vs 容量？带宽为王**

不同的 AI 工作负载虽然同时需要容量和带宽，但究竟哪个更重要，取决于具体工作负载。我们可以把 AI 计算分为三大类：预训练计算、后训练/强化学习计算、推理计算。强化学习与推理非常相似，因此需要相似的架构。在这三类中，推理解码主要受带宽约束：每生成一个 token，都需要读取全部处于活跃状态的模型参数，以及存储在内存中的用户 KV 缓存。强化学习（类似推理）同样偏向带宽约束，但由于注重大批次（batch），其容量需求高于推理。与此同时，预训练对容量敏感得多，因为训练过程中 HBM 要存放权重、梯度和激活值，而不只是推理前向传递所需的权重和用户 KV。

一个重大变化是，随着终端 token 需求激增、后训练技术成为模型扩展的主要抓手，分配给预训练的计算份额已显著缩水。结果是：如今分配出去的算力中，大部分已变成对带宽敏感，而非对容量敏感。

![](https://substack-post-media.s3.amazonaws.com/public/images/0327e1f0-2057-4961-b0ba-d7eb63abac64_1935x1212.png)
*来源：SemiAnalysis Tokenomics 模型*

这并不是说容量对推理无关紧要，容量在达到一定程度之前是重要的。Cerebras 和 Groq 的 SRAM 机器的一大弱点正是容量不足——尽管充裕的 SRAM 带宽能实现极快的 token 服务。简言之，存在一个容量阈值：一套推理系统必须有足够的高带宽内存容量来容纳模型权重以及用户的 KV 缓存。超过该阈值后，更多容量的边际收益递减，下文将予以展示。

另一个要点是：这里说的不是单芯片内存，而是单系统聚合内存。前沿模型的规模早已超出单颗芯片内存所能容纳的范围，必须分片（shard）到多颗芯片的内存上。这正是网络成为 AI 系统设计核心组成部分的原因。对于当今所有前沿模型都采用的 MoE 架构来说，最优系统往往是一个具备快速低延迟通信（例如整个机柜内的 NVLink）的单一纵向扩展域，能够支持宽泛的专家并行——每颗 GPU 上只加载少数几个专家。这种设置让每个专家能处理更大的 token 批次，提升计算与内存带宽利用率，代价则是 GPU 之间多得多的 all-to-all 通信开销。

![](https://substack-post-media.s3.amazonaws.com/public/images/73333702-e5df-41c1-9333-a24a9b51b6cf_2048x1503.png)
*来源：SemiAnalysis、Nvidia、Hugging Face*

虽然模型权重和用户 KV 缓存的容量需求都在增长，但纵向扩展域规模的大幅扩张让每节点聚合内存游刃有余地跟上了需求。在 Hopper 时代，一套 H100 HGX 系统提供 640GB 聚合 HBM。Llama 3.1 405B（当时最好的开源模型）的权重要占掉其中 63% 的容量，留给 KV 缓存的空间有一些（但不多）。这正是 H200 每 GPU 额外增加的 61GB 如此重要的原因：每服务器 1,128GB 内存带来了可观的增量空间，能容纳更多 KV 缓存、服务更多并发用户。

到了 GB300 NVL72 机柜级方案，Nvidia 在通过 12-hi HBM 和增加每 GPU 的 HBM 堆叠数使每 GPU HBM 翻倍的同时，把纵向扩展域规模做到了 9 倍。相对 H200 HGX，聚合 HBM 容量因此提升了 18 倍。这显著跑赢了当今最大开源模型 Kimi K3 2.8T 接近 7 倍的参数增长。从 16/8 比特量化到 4 比特低位宽也大幅减轻了容量负担。以 MXFP4 存储的一份 2.8T Kimi K3 副本仅占 1,561GB，**不到** GB300 NVL72 上近 21TB HBM 的 **8%**。纵向扩展域规模的扩张也没有放缓：Rubin Ultra 的大升级是转向 NVL576，相对 NVL72 再增 8 倍，足以抵消每 GPU HBM 容量三分之一的缩减还有余。

![](https://substack-post-media.s3.amazonaws.com/public/images/f8d0072e-9856-4d4d-96d7-f05cff1662cc_2048x438.png)
*来源：SemiAnalysis、Moonshot、Nvidia、AMD*

在机柜级服务器时代及以后，可用内存容量已远超模型权重所需，为用户 KV 缓存留出了非常宽裕的空间。[如今的系统已经能从容支持超长上下文的推理请求，并发度也足以支撑非常高的推理利润率](https://newsletter.semianalysis.com/p/spacex-10gw-in-2027-why-its-real)。这大大缓解了 HBM 容量压力，让每芯片 HBM 密度得以放松。这与此前小规模部署时代的范式截然不同——那时模型权重会吃掉总内存的相当部分，提高每 GPU HBM 密度是获取宝贵容量空间的关键手段。

「更矮的堆叠、更便宜的带宽」这一论点一直成立，但直到现在我们才看到更高堆叠的趋势逆转，因为每芯片最低 HBM 容量阈值直到最近才大幅下移。我们认为这一趋势还会走得更远：前沿实验室的芯片和硬件团队将 4-hi HBM 视为许多推理工作负载的最优 SKU，因为它能带来最佳的性能/TCO。下面我们将深入探讨原因。

# **带宽与容量的最优配比**

带宽与容量之间存在一个最优配比，而现实中容量往往被过度配置或「搁浅」——每 token 可用带宽不足以读完全部可用 HBM 容量。

先从一个简单的例子开始。每个 HBM4E 堆叠提供 3,328 GB/s 的标称峰值带宽（假设 2048 个引脚、每引脚 13 Gbps）。对 HBM4E 而言，每颗核心裸片为 32-Gb，因此 4-hi、8-hi、12-hi 堆叠分别对应 16 GB、32 GB、48 GB。以单条序列 100 tokens/s 为例：3,328/100=33.28GB，即每 token 可用 33.28GB 的内存带宽。再用每 token 可用带宽除以堆叠容量，就得到每个 token 能把堆叠总容量读几遍。当每 token 恰好读 1 遍堆叠时，容量与带宽完美匹配：每个 token 拥有的带宽恰好够把存放在 HBM 中的全部工作数据读一遍——不多也不少。

比值大于 1 意味着带宽相对容量「过度配置」，因为一个 token 只需把工作集读一遍（即一次前向传递）。但带宽很少是真正的「多余」，因为额外带宽预算总可以通过提高每秒 token 数消耗掉。比值小于 1 则意味着一个 token 的可用带宽不足以读完所有可用 HBM 容量。要以该吞吐率供给 token，工作集不能大于每 token 可用带宽所对应的大小，因此必然低于总内存容量——于是产生了被过度配置的多余内存容量。

![](https://substack-post-media.s3.amazonaws.com/public/images/2643b2ce-3705-4e72-b9a6-01a0a88dae6f_2014x399.png)
*来源：SemiAnalysis*

如上面的示例表格所示，tokens/s 的提升会降低每 token 可用带宽，压低「每 token 堆叠读取次数」比值，从而加大容量被过度配置的可能。这就形成了一种不对称性：拥有大量带宽优于拥有大量容量。带宽通常能被全部用掉，而富余的容量却不总能被用掉，其成本还在不断抬高。

当然，这是一个忽略了通过批处理（batching）合并请求以服务多并发用户的简化分析。批处理在推理经济学中扮演关键角色：在给定交互性水平下，批处理能最大化总 token 吞吐。批处理最大的节省在于把一次权重读取分摊到多个用户的请求上。更高的并发也会消耗内存容量，因为每个用户的 KV 缓存都要加载进内存。推理工作负载从带宽受限转为内存容量受限，往往正是通过加大批量实现的。当 HBM 容量轻松装下模型权重后，额外 HBM 容量的好处就是带来更高的 token 吞吐——这也是为什么这些增量比特可能值得计入 BOM。

![](https://substack-post-media.s3.amazonaws.com/public/images/d93801de-a193-483d-b6ec-26807a208797_1600x900.png)
*来源：SemiAnalysis*

把批处理纳入考量后，就得到了上面这条概括性曲线。在其他条件相同的情况下，更高的 HBM 堆叠能带来更高吞吐，直到某个每用户延迟 SLA 之后，额外容量就变得多余——这些转折点正是不同曲线相互重合之处。

「每用户延迟 SLA」是一个最低交互性假设，是下限而非实际交互性。当并发被容量封顶时，意味着还有富余带宽可用于支撑更高的每用户 tokens/s。因此，即便 4-hi 只能提供较低的并发，更快的每用户 token 速度也能全部或部分抵消更小批量的影响，维持总 token 吞吐。

并发数取两个上限中的较低者：容量受限时，是能装进内存的单用户 KV 缓存组数的最大并发；带宽受限时，是在我们的最低交互性下能服务的最大用户数（其中用到了上面的每 token 可用带宽计算）。用户数乘以每用户 tokens/s，即每秒生成的总 token 数，也就是吞吐。

这些曲线能告诉我们额外容量在推理性能上的价值：展示更多容量（通过更大批量）能把 token 吞吐提升多少；同时也展示在哪些最低交互性点位上，额外容量不再增值。

这在很大程度上取决于模型规模——换言之，取决于必须划给模型权重的 HBM 容量占比。一般而言，模型越大，曲线越右移，更高的堆叠就能在更高交互性点位上提供更多吞吐；此外，更高的堆叠带来的峰值吞吐提升也更大。这又回到批处理经济学：无论批量多大，每一步都要把权重读一遍，因此权重占位越大，每个新增并发用户解锁的吞吐就越多。

代入实际数字，看看这对当今最大的开源模型 Kimi K3 意味着什么。这是一次屋顶线（roofline）分析；现实中实际达到的内存带宽显著低于峰值带宽，实际结果会将最低交互性阈值左移，但总体结论不变。另外，本练习只针对分离式 PD（prefill/decode）架构中的解码池。[实际交付结果请参见我们的 InferenceX 和 AgentX 基准测试。](https://inferencex.semianalysis.com/)

我们采用 Rubin Ultra NVL576 系统，因为这将是 HBM4E 时代更有代表性的纵向扩展域规模。假设 HBM 为 13Gbps 速率的 HBM4E，4-hi、8-hi、12-hi 分别对应每 GPU 128GB、256GB、384GB。对于运行在该 NVL576 系统上的 Kimi K3，每颗 GPU 承载 16.8GB 权重，即每个 HBM 堆叠 2.1GB。可以看到：在 105 tok/s/user 的最低 SLA 下，12-hi HBM 带来的吞吐已不超过 8-hi HBM；而当交互性进一步翻倍到 213 tok/s/user 时，高于 4-hi 的堆叠已毫无益处。就最大吞吐增益而言，8-hi 相对 4-hi 将最大总 tokens/s 提高 8%，12-hi 提高 10%。然而，退回到 4-hi 所能交付的最大吞吐，可换来超过两倍的交互性。我们再次强调：现实中并非全部原始内存带宽都能被利用，实际结果会将这些曲线左移，意味着更高配置的交互性盈亏平衡点会更低，甚至可能跌入用户无法接受的低速度区间。

![](https://substack-post-media.s3.amazonaws.com/public/images/7608023b-e2a4-4c9e-bf39-b5273dda376c_2037x1261.png)
*来源：SemiAnalysis、Moonshot*

可以看到，对这些模型而言，更多容量确实能带来略高的 token 吞吐（先不论更快 token 的好处）。于是问题变成：这点额外吞吐，值不值得为之付出更多内存带来的额外 BOM 成本？HBM 占加速器 BOM 成本的比重可观，而在 HBM 如此紧张的情况下，每 GB 成本明年将大幅上涨。

把成本纳入考量，我们针对 Rubin Ultra NVL576 系统建模：终端所有者相对以 HBM4E 4-hi 为基线的 Rubin Ultra 所需多付的 BOM 成本。8-hi 的全系统成本增幅（由于全系统成本占 TCO 的绝大部分，我们以之代理 TCO）相对 4-hi 基线系统为 12.1%，12-hi 则为 26.3% 的溢价。然后我们对比不同最低交互性点位上 token 吞吐增幅与成本增幅，检验更多内存能否在任一点位上带来更低的单 token 成本。

![](https://substack-post-media.s3.amazonaws.com/public/images/34b7a95f-f8af-4fa6-9b4c-d1de65036ce6_2001x1204.png)
*来源：SemiAnalysis*

总体来看，12-hi 或 8-hi HBM 带来的吞吐增益小于更多内存带来的系统成本增幅。换言之，在这样的内存价格（叠加 Nvidia 的利润率）下，12-hi 与 8-hi HBM 的单 token 成本高于 4-hi HBM。这还没有计入更省 HBM 的技术，即把 KV 缓存卸载到更低层级的内存。下一节将展示我们实际执行的一次生产级运行，说明更少的内存如何影响实际吞吐。

# **一个真实实验：KV 缓存卸载缓解容量压力**

只要模型权重仍能装下，削减 HBM 容量就只是压缩了可存储的 KV 缓存量，而第二层级的 DRAM 可以用来存放不那么「热」、无需即时读取的 KV 缓存。这在智能体（agentic）工作负载中正变得越来越常见：其上下文长度极高，对 HBM 容量形成压力，但轮次之间又有很长的停顿，因此把 KV 缓存驱逐（expel）到 DRAM 甚至存储中、而不是事后整体重算，是划算的。[在我们近期的 AgentX 基准测试中，许多工作负载在高于特定并发度后，其帕累托最优结果正是借助 KV 缓存卸载取得的](https://newsletter.semianalysis.com/p/agentx-inferencexv3-does-cuda-moat)。

为测试削减 HBM 对真实工作负载的影响，我们在削减 HBM 的条件下对 Kimi K3 运行了 InferenceX 基准测试。系统由 16 颗 GB300 GPU 组成，采用分离式部署：8 颗 GPU 组成预填充池，8 颗组成解码池。受限内存工作负载以 85% 的 HBM 利用率运行，而正常情况为 92%。是的，这只是削减 8% 的 HBM，与从 8-hi 降到 4-hi 的 50% 削减相去甚远，但这里 Kimi K3 只部署在 8 颗 GPU 上，权重已占掉内存的相当部分。折算下来相当于每颗 GPU 减少 20GB 的 KV 缓存存储。具体而言，在聚合服务模式下，每 GPU 的 KV 预算从 53GB 降至 34GB，降幅 36%；在分离式配对模式下，从 44GB 降至 24GB，降幅 44%。总体上，这是 KV 缓存可用 HBM 预算的一次可观削减。

从结果看，在曲线上直到大部分点位，HBM 受限运行都交付了非常接近的吞吐（如红色虚线所示）。然而一旦并发超过 70，吞吐相对高 HBM 运行骤降近 30%。这正是受限内存版本 GPU KV 占用峰值触及 100% 的点位。从那一刻起，抢占（preemption）、反复加载与排队开始拖累吞吐。注意，这一崩落也发生在曲线上高并发但交互性极低的区段。我们知道 DRAM 卸载被用得更多：在相同并发下，低 HBM 受限配置对 DRAM KV 缓存的读取次数是高 HBM 配置的 10 倍以上。

![](https://substack-post-media.s3.amazonaws.com/public/images/fb82a986-d735-4e0f-bc62-4288f520bea1_2048x1300.png)
*来源：SemiAnalysis*

我们在真实工作负载中看到，把 KV 缓存卸载到 DDR DRAM 能非常有效地缓解 HBM 容量压力。这是针对 Kimi K3 的结果，尚未计入最新 DeepSeek v4.1 Flash 模型引入的一些更极端的缓存缩减技术——相对 v4 Flash，其活跃 KV 缓存规模缩小约 75%。在这样的 KV 缓存水平下，把并发提高到用满全部 HBM 容量，很可能意味着工作负载变成算力和网络受限，而非容量受限，从而进一步削弱更高 HBM 堆叠的价值。

# **4-hi 是否放弃了面向未来的选择权？**

在我们采用 HBM4E 与 NVL576 的 K3 屋顶线分析中，明显的缺陷是：我们用当下工作负载在未来的系统上论证 4-hi 已足够。这些更大的纵向扩展域要到一年后才会与 HBM4E 一同就绪，届时前沿模型的规模只会更大。此外，AI 服务器的部署寿命超过 5 年，必须在整个周期内持续供给 token。

如果未来工作负载的模型规模大得多，被牺牲的容量可能严重低估未来工作负载的最优容量需求。例如，假设一个未来模型是 Kimi K3 的 3 倍大（每用户 KV 缓存也增至 3 倍），更高 HBM 堆叠带来的吞吐增益就好得多：12-hi 能比 4-hi 多交付 47% 的总 token，8-hi 多 36%，不过速度只有一半。在这一情景下，额外容量开始变得更有理由，决策就归结为更快的 token 究竟价值几何。

![](https://substack-post-media.s3.amazonaws.com/public/images/a7d9df92-0ad7-4cc2-b4b1-427ff3fcc49e_2038x1240.png)
*来源：SemiAnalysis*

把成本计入该分析后：这一情景下，在低于 180 tok/s/user 的区间，8-hi 的吞吐增益超过其 TCO 增幅。

![](https://substack-post-media.s3.amazonaws.com/public/images/5447656a-15b3-45b9-8b96-2c17b1cb5812_2023x1287.png)
*来源：SemiAnalysis*

但从 8-hi 再加到 12-hi 就不值得了：曲线上的任何点位，12-hi 的 token 吞吐增益都不大于其 BOM 成本增幅。

![](https://substack-post-media.s3.amazonaws.com/public/images/d232f683-16e8-46ea-a275-86ec7f6a7e2a_2048x1247.png)
*来源：SemiAnalysis*

对此有若干反驳。第一，扩展参数量、进而扩展模型权重，对模型能力已不再那么重要。大规模使用强化学习以及更长的推理/思考时间，是带来更高效模型架构的关键进展。此外，[GPT-6 Astra 使用循环 transformer（looped transformer）已基本得到证实](https://x.com/merettm/status/2095023204993490967)，也有大量猜测认为 Anthropic 的最大模型同样如此。循环 transformer 实质上是把输入多次通过 transformer 层——通过深度而非增加权重来扩展模型。

第二，如果 4-hi 加速器成为 AI 服务器加速器存量装机的重要部分，研究者会调整模型，使之能够在这类硬件上被高效服务。而且据我们了解，最支持 4-hi HBM 的恰恰是前沿实验室的硬件团队。这些团队对软硬协同设计极为执着，他们对 4-hi 的呼吁本身就反映出未来模型正朝着不再需要那种容量的方向演进。

最后，从大局看：所有构建和服务模型的人，目标都是服务尽可能多的 token。走向 4-hi 堆叠，正是确保这一点的路径……

# **最大化 ~~每瓦特 token 数~~ 每 HBM 晶圆 token 数**

最优硬件架构，就是让每种稀缺资源的产出最大化的架构。在建设 AI 基础设施这件事上，我们身处一个多重短缺的世界。电力是关键短缺之一，这正是[优化 tokens/W 如此重要、成为推理服务商和硬件架构师的核心优化指标](https://newsletter.semianalysis.com/i/212647373/performance-analysis)的原因。当然，资金也是有限资源，这就是性能/TCO 长期以来一直是驱动硬件决策的金标准的原因。

如前所述，另一大约束是 HBM 晶圆的供给。虽然少有人讨论，但优化每 HBM 晶圆 token 数可以与 tokens/W、tokens/TCO 等量齐观。方法很简单：用 4-hi HBM。既然一个 4-hi 堆叠与 8-hi 或 12-hi 堆叠提供的带宽相同，简单地说，4-hi 意味着每片 HBM 晶圆可收割的内存带宽是用于 12-hi HBM 时的三倍、用于 8-hi 时的两倍。若再计入 4-hi 更高的封装良率，实际数字还要更好。由于内存带宽大体等同于 token 吞吐，这意味着要榨干有限的 HBM 供给，4-hi 就是正解。

转向 4-hi 后，相对 8-hi 可收割的 HBM 堆叠数量可以翻倍以上。但这些堆叠只有能与加速器合并封装、装入系统才有价值。这意味着瓶颈将从 HBM 晶圆转移到供应链的其他环节：逻辑晶圆（加速器和 HBM 基础裸片 base die 都算）、封装基板、PCB、下游集成产能，以及介于其间的众多其他组件——更别忘记部署更多系统所需的全部电力。不过总体而言，我们相信未来几年供应链其余环节的产能爬坡速度能够快于 DRAM 供给。即使 AI 服务器供应链跟不上 HBM 堆叠翻倍所需的供给，这也会为传统 DRAM 腾出晶圆——HBM 对整体 DRAM 供给的蚕食已让其他应用陷入「内存饥荒」，这些晶圆可以去服务它们。最先想到的就是服务器 DRAM：为了最大限度利用有限的服务器 DRAM 供给，每路（socket）DRAM 配置正被大幅削减。这也与支撑智能体工作负载密切相关——其中有大量时间其实花在等待 CPU 侧的执行上，而不是等待 GPU 解码 token。

付费墙之后，我们将讨论这对内存供应商的影响、4-hi 如何令他们受益，以及他们正在如何应对。我们的 [Memory Model](https://semianalysis.com/memory-model/) 中有远多于此的洞察、产品 SKU/供应商决策，以及供需细节。
