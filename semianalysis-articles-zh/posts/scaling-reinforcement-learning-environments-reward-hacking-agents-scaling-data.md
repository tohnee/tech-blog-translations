# 扩展强化学习：环境、奖励作弊、智能体、数据扩展

> 原文：[Scaling Reinforcement Learning: Environments, Reward Hacking, Agents, Scaling Data](https://newsletter.semianalysis.com/p/scaling-reinforcement-learning-environments-reward-hacking-agents-scaling-data) · SemiAnalysis

**基础设施瓶颈与变革、蒸馏、数据即护城河、递归自我改进、o4 与 o5 的 RL 训练、中国加速器生产**

测试时扩展（test time scaling）范式正蓬勃兴起。推理模型持续快速进步，正变得更强大、更便宜。衡量真实世界软件工程任务的评测（如 SWE-Bench）正以更低的成本取得更高的分数。下图展示了模型如何同时变得更好、更便宜。

![](https://substack-post-media.s3.amazonaws.com/public/images/5364998d-14d0-4d67-89be-15e96792906b_1604x866.png)
*来源：SemiAnalysis*

强化学习（RL）正是这一进步的根源。我们在之前的报告中对此有过讨论，阐述了 RL 如何让模型通过生成思维链（Chain of Thought, CoT）获得推理能力。我们预计这一范式将持续下去。

除了思维链本身的创新之外，模型能够保持连贯（思考）的时间更长了，这解锁了智能体（agentic）能力。搜索等工具使用、用 Python 做计算以及其他能力，都是规划、推理和长时间运行这一能力的下游产物。更好的推理给了模型更多「思考」时间，从而让它们从简单的聊天机器人进化为规划者。这反过来又催生了更连贯的智能体。随着机器学习研究人员在可验证领域扩展 RL 的规模，这些连贯的智能体将开始胜任更复杂的、涉及计算机使用（computer use）的任务，例如全自动化远程办公和系统工程/架构设计。

尽管进展强劲，扩展 RL 算力在整个基础设施栈上都面临新的瓶颈与挑战。RL 可能是通向 AGI 之前的最后一个范式。机会巨大，投资也因而巨大。数十亿美元正被轻松地投向模型预训练。未来还会有更多资金投向 RL 扩展，但其基础设施需求与预训练大不相同。让我们看看要实现这一目标需要些什么。

## 强化学习的工作原理

强化学习（RL）在概念上很简单。强化模型从任意环境中获取其当前状态的信息，生成一组选择某个动作的概率，然后执行该动作。模型的目标是达成某个目标，这一目标由「奖励函数」定义。当改变模型权重，使得生成的最高概率更可能带来更高奖励时，强化学习就发生了。

强化学习并非新事物。RL 是一种比大语言模型更早出现的老技术。例如，它是那些征服围棋和国际象棋的系统背后的技术基础。但如今 RL 终于在 LLM 这类通用技术上奏效了，这在能力和技术扩散两方面都有重大意义。

## 可验证奖励

LLM 中的 RL 在具有可验证奖励的领域效果最好。这意味着任务（如编程和数学）具有 RL 所需的清晰奖励定义。而在奖励函数定义较为模糊的领域，推理模型的提升则较为艰难。当 OpenAI 对 GPT-4o 进行 RL 训练以得到 o1 时，最大的收益正是来自那些可验证的领域。

![](https://substack-post-media.s3.amazonaws.com/public/images/38dd2c98-c131-4b6b-95d8-a91f440dced1_1594x993.png)
*来源：OpenAI*

随着领域的发展，工具使用等新领域正在打开。OpenAI 的 o3 可以放大图片、对所见内容进行推理、执行一些计算、再继续推理，然后给出答案。这解锁了一大批模型如今能做得很好的任务，例如识别一张照片的拍摄地点。这类任务在技术上是可验证的，但模型并没有被明确地训练过。然而，尽管收益惊人，各家实验室在 RL 上的投入金额总体上仍然很小，尤其是相对于预训练的投入而言。让 RL 算力追上并超越预训练算力的瓶颈是什么？不可验证领域会被攻克吗？

## RL 是重推理负载的

研究最流行的 RL 算法之一，可以让我们看清 RL 到底有多吃推理。组相对策略优化（Group Relative Policy Optimization, GRPO）是一种常用算法，也是 DeepSeek 用来训练 R1 的算法。

在 GRPO 中，模型被要求回答一个问题。模型会为该问题生成多个答案。每个答案可以被视作一次「rollout」，本质上就是模型在尝试寻找解法。换言之，一个 rollout 是模型生成答案或解决问题的一次独立尝试。每个问题的 rollout 数量可以从几个到数百次不等。技术上没有上限，但使用的 rollout 越多，占用的内存和算力就越多。

由于每个问题要生成如此多的答案，RL 因此成为重推理负载的工作。这一点影响重大，我们在报告中会多次提及。

![](https://substack-post-media.s3.amazonaws.com/public/images/2c77912a-c2cb-40a4-b01d-6db896d0574e_1959x620.png)
*来源：SemiAnalysis、TogetherAI、Nvidia*

然后，这些答案会对照标准答案（ground truth）打分。具体到 GRPO，每个答案都会得到一个奖励分数。正确性并非唯一因素——奖励函数确实可以有多种调整方式——其他因素还包括格式和语言一致性。

奖励计算完成后，模型会通过梯度下降进行更新，以提高生成更可能获得正奖励答案的概率。GRPO 是近端策略优化（Proximal Policy Optimization, PPO）的一种变体，它去掉了对 critic 模型（在 PPO 中用于预测未来奖励）的需求，因而内存效率更高。PPO 和 GRPO 都可以使用学习得到的奖励模型或基于规则的奖励系统来评判答案质量。GRPO 因内存需求更低而在开源社区被广泛采用，但我们预计各家实验室会继续使用 PPO 的各种变体。PPO 由 OpenAI 发明，实验室内部可用的版本如今已与 GRPO 常被拿来比较的公开版本有实质性差异。而且实验室面临的算力约束也更少。

![](https://substack-post-media.s3.amazonaws.com/public/images/36185df7-64bb-427b-8675-b8da6dd139c0_2560x1130.png)
*来源：Shao 等*

核心思想是：RL 通常需要一个问题、一个用于比对的答案，以及一种向模型指示其行为应朝哪个方向改变的方式。模型探索寻找答案的方式可以多种多样，但它需要以不同 rollout 的形式生成多个答案，因此对推理侧的要求很高。随后模型被更新，使正确答案更可能出现，所以其中也隐含着训练的成分。

## 奖励函数很难定义

如前所述，可验证奖励方面已经取得了强劲进展。原因之一是奖励函数易于定义：数学题的答案非对即错。但理论上，奖励函数可以是用户想要优化的任何东西。

从概念上讲，模型在 RL 之下的首要目标是最大化总奖励。举个例子，如果一个模型在被训练下国际象棋，它的首要目标就是在不违反规则的前提下赢下棋局。模型可以通过下棋并不断发现哪些走法有助于它在不同局面下获胜，从而持续进步。模型可以通过其运行所处的环境获得反馈。这一点我们稍后会深入讨论；在国际象棋的例子中，环境可以被理解为模型与之交互的棋盘和棋子。

为不那么狭窄的任务定义奖励被形容为一种「[黑暗艺术](https://lilianweng.github.io/posts/2024-11-28-reward-hacking/)」（dark art），因为要把它做对非常困难。即便在规则清晰的环境中，设置正确的奖励函数也需要大量研究、测试和优化。芯片设计就是一个例子。AlphaChip 是 Google 设计的用于辅助芯片设计、并以 RL 训练的模型。该模型助力设计了 Google 使用的 TPUv6 芯片，使 TPUv6 的布线长度（wirelength）减少了 6.2%。此例中的奖励函数被明确定义为：

![](https://substack-post-media.s3.amazonaws.com/public/images/2de039de-6e7a-4b77-a438-a7ea5c340766_2389x253.png)
*来源：Mirhoseini 等*

这引导模型精确地最小化那些重要因素：布线长度、拥塞（congestion）和密度。值得注意的是，即便是这样一个相对简单的奖励函数，设置起来也并不轻松。拥塞和密度都有用于调整其权重的标量值（分别由 Alpha 和 Gamma 表示）。这些数值是在大量实验之后、根据工程师想要做出的取舍推导出来的，最终认定布线长度是最重要的因素。

## 如何在不可验证领域设置奖励？

不可验证领域包括写作或战略等不存在明确正确答案的领域。对于究竟能否在这些领域做 RL，业界一直有些怀疑。我们认为可以。事实上，已经有人做到了。

这需要改变奖励机制。不再依赖形式化的验证器来检查，而是用其他模型依据评分标准（rubric）来判断答案正确与否。

OpenAI 用 RL 来改变模型行为——这比数学更不显性。OpenAI 的[审慎对齐论文](https://arxiv.org/pdf/2412.16339)（deliberative alignment paper）在其流程中使用 RL，在以 LLM 为裁判、以评分标准为依据的同时，确保模型更安全、误拒绝更少。此外，该过程只使用了合成数据。正如之前[所指出的](https://www.interconnects.ai/p/why-reasoning-models-will-generalize?utm_source=publication-search)，他们还发现该方法「在分布外安全场景上实现了强大的泛化」。这种针对不可验证方法的 RL 已进入 o1、o3-mini 和 o4-mini 的训练，并将继续用于未来的推理模型。

具备推理能力不仅有助于做数学，还有助于许多其他任务，包括不可验证的任务。例如，在许多情况下，推理帮助模型更好地分辨哪些情况需要拒绝、哪些不需要。不过无可否认，在不可验证领域中，某些因素比其他因素更重要。例如，模型个性会严重影响写作风格。

![](https://substack-post-media.s3.amazonaws.com/public/images/961ea4b1-eae0-4b57-abc1-f34e7fd478e7_2560x1273.png)
*来源：OpenAI*

不可验证领域的 RL 也更不稳定——GPT-4o 的谄媚行为部分源于 OpenAI 对用户偏好数据进行 RL。这是一个善意的奖励函数却导致不良且非预期行为的例子。

## RL 助你做出更好的 RL

改进模型的 RL 可以直接增强 RL 流程本身，形成良性反馈循环。这源于上文提到的、常见的以带评分标准的 LLM 裁判来提供 RL 信号的做法。用推理模型充当 LLM 裁判，意味着模型能更好地理解评分标准，并从给定回答中辨别出更细微的差别。

OpenAI 的 Deep Research 也被吹捧为不可验证领域因 RL 而取得进展的例子。实际上，OpenAI 既使用了带标准答案的可验证任务，也使用了不可验证任务。需要理解的是，与前面的例子一样，这些不可验证任务是由另一个带评分标准的 LLM 来评判的。

阿里巴巴 Qwen-3 的开发也用到了 LLM 裁判：它利用大量合成数据语料，并结合 LLM 裁判在没有参考答案的情况下提供信号。

我们认为评分标准打开了大量新领域。再举一例，OpenAI 展示了模型在多种医疗健康任务上的表现。OpenAI 汇集了 260 多位医生来编写评分标准，供裁判模型在评估回答时使用。

![](https://substack-post-media.s3.amazonaws.com/public/images/685bf464-3b9b-44de-a3f0-052bb9bd8921_2560x1281.png)
*来源：OpenAI*

HealthBench 是一个出色的评测，OpenAI 将其公开发布值得称赞。

该评测还反映出 LLM 裁判在衡量不可验证奖励上的表现时多么有用。而凡是可衡量的，就可以通过 RL 来改进。这凸显了 RL 与评测之间一个被低估的关系——后者可以反映 RL 训练运行进展如何。

## 环境

要进行 RL，你需要强化某个动作或结果。模型或智能体必须有一个环境来获得反馈，从而理解下一步该采取什么行动。由此催生了 **RLEF（reinforcement learning execution feedback，强化学习执行反馈）**，即我们在环境中运行模型产出的代码，并将结果用作奖励信号。

环境是模型采取行动并接收反馈的场所或仿真。国际象棋和围棋这类棋盘游戏是极好的环境范例：目标定义明确、规则清晰。随着通用性递增，我们会遇到诸如智能体在视频游戏中赛车、或在生物反应器仿真中控制一组特定参数的领域。再往外，就是数学、代码、甚至浏览器这样的领域。

环境的不同配置可能导致智能体的不同行为。配置不当的环境会让模型误解任务或无法正确泛化。这可能导致「奖励作弊」（reward hacking），我们将在本报告后面讨论。

因此，要工程化出**稳健**（robust）的环境、使奖励函数被精确地按需定义，是极其困难的。即便在编程这类只需简单环境的领域，大量使用单元测试会让模型关注的不是写好代码，而是通过单元测试。因此，一项工程挑战就是搭建一个忠于预期目标（写出好代码）的环境。

让环境拥有正确的奖励函数是一回事，把它工程化好则是另一回事。打造可扩展、稳健的环境是一项关键技术挑战。

环境有很多要求。延迟就是一例。从智能体采取行动到环境受影响之间的延迟很重要，智能体能否快速获得反馈同样重要。否则，rollout 的大量时间会花在智能体等待执行下一步上。其他考量还包括：建立持续可靠的连接以免崩溃中断进程，并配合容错和检查点机制使故障优雅降级；对多个不同 rollout 或轨迹的处理也必须做好、做精。此外还需要一整套安全基础设施作为支撑，以保护模型免受外部渗透，或防止其试图逃出环境。

模型自身也会带来若干失效模式，使事情变得更难，例如采取耗尽机器可用资源的行动。环境工程既涉及保护模型免受其自身之害、维护足够安全的基础设施，也涉及围绕延迟和可靠性的一大堆工程挑战。环境还需要准确呈现仿真或场景，让智能体正确理解该改进什么，同时又无法被钻空子。

所有这些要求使得扩展环境相当困难，尤其是第一次上手时。后文会谈到，模型连贯时间的变长甚至会让简单环境也难以维护。计算机使用这类场景尤其如此，我们将在后面的章节重点考察。

尽管基础设施工程看似平淡无奇，它却是 RL 成功的关键。如果 rollout 耗时过长，验证模型就会闲置、浪费资源。因此，想办法让这些模型同时干点别的（例如评判另一个 rollout）非常重要。

这些软件层面的限制还必须叠加在硬件约束之上。例如，大多数环境运行在纯 CPU 服务器而非 GPU 上。这意味着要在外部的专用机器上运行，这又增加了一层工程复杂度。

需要记住的是，大多数公开的 RL 环境聚焦于与评测挂钩的**单轮问题**（single turn problems）以衡量性能。而 OpenAI 的 o3 这类模型构建在利用**多次工具调用**（multiple tool calls）的环境之上。我们会在后面的章节拆解如何打造一个 o3 级别的模型，但随着工具调用增多、环境复杂度上升，这也带来了另一批挑战。

## 奖励作弊

如前所述，设置正确的奖励可能很困难，因为模型可能误解目标、以不理想的方式进行优化。奖励作弊（reward hacking）指模型利用环境或奖励结构中的漏洞获取高分，却并未真正完成既定任务。奖励作弊长期以来被公认为一个重大问题，早在 2016 年就由 Dario Amodei（现任 Anthropic CEO）等研究者重点[指出](https://arxiv.org/pdf/1606.06565)。举个例子：一个机械臂因把红色方块放到蓝色方块上方高处而获得奖励，结果它钻了奖励的空子——把红色方块翻过来倒扣，而不是规规矩矩地叠上去。这是因为奖励是以方块底面的高度来评判的。

![](https://substack-post-media.s3.amazonaws.com/public/images/97fc4de2-a289-46d8-a62e-c942fa79fa24_430x360.gif)
*来源：Popov 等*

另一个失效模式的例子：在一个用于教机器人走路的物理仿真中，智能体发现了一个软件漏洞，可以在不实际迈步的情况下实现水平移动。

![](https://substack-post-media.s3.amazonaws.com/public/images/06e1e94d-65c8-46e2-a1f5-71acfb9eb508_616x342.gif)
*来源：Code Bullet*

在 LLM 方面，Claude 3.7 Sonnet 也出现过奖励作弊：它不去改进代码以通过原始测试，而是篡改测试用例。例如，一家第三方评估机构[发现](https://metr.github.io/autonomy-evals-guide/claude-3-7-report/#reward-hacking)，Claude 会直接编辑「tests」文件让所有测试通过，而不是编写能通过原始测试的代码。Anthropic 发现了这个问题，虽然他们实施了部分[缓解措施](https://assets.anthropic.com/m/785e231869ea8b3b/original/claude-3-7-sonnet-system-card.pdf)，但在 Claude 3.7 中这一模式依然可见。

这些案例固然有趣，但问题在于：工程师总是无法准确描述奖励函数，或者直到智能体已经钻了空子才发现环境中的 bug。许多奖励作弊行为走的是设计者从未想到要考虑的路径；虽然训练过程中可以迭代修正，但对 LLM 来说很难做到。机器人环境在其目前尚处襁褓期的发展阶段还相对容易调整，而大语言模型的动作空间庞大且复杂，使奖励作弊更难防范。

解决奖励作弊是所有实验室的头等大事，并将借鉴安全导向团队的许多思路。这是安全与对齐工作助推企业及商业落地的又一例证。

在 Claude 4 的发布中，Anthropic 通过改进环境、明确奖励信号和实施主动监控，显著减少了奖励作弊。这不是一件轻而易举的事，需要大量的专业知识和经验诀窍。

![](https://substack-post-media.s3.amazonaws.com/public/images/ea87c092-9642-4092-a225-63696fcbd431_2560x1254.png)
*来源：Anthropic Claude 4 系统卡*

但 RL 和奖励作弊并非唯一的瓶颈，基础设施本身就是一大瓶颈。这要从 RL 所需的数据说起。

## 数据与样本效率

乍看之下，RL 似乎样本效率很高：在训练 Qwen 模型的「推理 RL」阶段，使用的问答对不到 4 千个。这带来了相对基座模型的显著性能提升，也引出了强样本效率的说法。

然而，真实情况更为模糊。那 4,000 个问答对中的每一个都有着极严格的要求：不能是模型冷启动阶段（训练中更早的一个阶段）已经用过的；必须尽可能具有挑战性；要覆盖宽泛的子领域范围；同时又要在模型能力范围之内。

这些要求并不简单。生成合适的合成数据需要大量过滤和反复的模型推理。此外，「问题对模型要有挑战性但又不能太难」这一要求，需要通过实验与验证来确认题目恰好落在那条窄带里。在一些数据并非合成生成的场景中，实验室正在招募 STEM 博士来帮助编写对模型而言足够有挑战性的问题和答案。这些博士还被请来为 LLM 裁判编写参考用的评分标准。

ScaleAI、Mercor、Handshake 等公司如今从 AI 实验室获得了大量业务，帮助其完成这类招募。

![](https://substack-post-media.s3.amazonaws.com/public/images/faaa0461-2629-4259-9475-f81c08959b66_2560x1465.png)
*来源：Mercor*

Qwen 之后*又*做了一轮 RL 阶段。尽最大可能营造高效率的印象符合他们的利益，所以他们没有公布下一阶段的样本数量。原因很简单：这个数字远大于 4,000。

在这一阶段，他们在 20 多个不同领域开展了 RL。他们还用上了全部三类奖励模型（基于规则的、带标准答案的 LLM 裁判、不带标准答案的 LLM 裁判）。这需要复杂的工程和算力投入。

放眼长期，我们预计各实验室将在数百个专业领域进行 RL，以大幅提升模型性能。质量比数量更重要——模型会精确地向其训练数据优化——因此对这类数据的精心挑选与过滤至关重要。

所以，虽然使用的样本只有 4,000 个，但达到这一步耗费了可观的算力。可以说 RL 在数据上是样本高效的，但在算力上它绝对是样本*低效*的。与预训练相比，RL 需要规模大得多的工程团队才能有效搭建。

## 数据就是护城河

归根结底，Qwen 传递的信号是：高质量数据是扩展 RL 的一项独一无二的重要资源。高质量数据有助于提供足够清晰的 RL 信号，让模型在恰好所需的任务上变得更好。而生成这类数据往往需要海量的推理。

更广义地说，公司或企业可以聚合并利用自己的数据，使用 OpenAI 的[强化微调（Reinforcement Fine Tuning, RFT）](https://platform.openai.com/docs/guides/reinforcement-fine-tuning)等服务。RFT 允许使用自定义评分器（grader），让企业依据评分器或数据的结果来更新模型。我们认为这仍是一个被低估的发布，即便不考虑模型的进一步进步，它也可能产生巨大影响。

事实上，拥有一个能聚合并收集用户行为的产品极具价值，因为这终究是最重要的数据集。由此带来的一个有趣推论是：手握用户数据的 AI 初创公司可以对定制模型做 RL，而不需要巨额算力预算去合成数据。如果企业能搭建正确的 RL 环境，企业定制模型的时代或许真的说得通。此前，与基础模型势不可挡的进击相比，面向企业的模型微调总体上是失败的。

## 智能体任务的时间跨度正在变长

如今模型能够保持连贯的时间越来越长。更长的任务要求环境与基础设施能在长时间内可靠运行，这加剧了工程上的挑战。

下图显示，自包含编程任务的任务时长呈现约 7 个月翻一倍的趋势，但我们预计编程之外的任务翻倍速度会更快。OpenAI 的 Deep Research 是首个能连贯工作超过几分钟的模型范例，我们预计这一上限还会显著且快速地抬升。

![](https://substack-post-media.s3.amazonaws.com/public/images/67b2124e-f300-44d0-b98b-423f8dfd1aa0_2560x1392.png)
*来源：METR*

然而这里存在一种张力。智能体任务具有极高的经济价值，但由于其复杂性和资源强度，也给 RL 带来了重大挑战。

任务持续时间的拉长意味着每次 RL 迭代也要花更久，从而拖慢整个训练过程。

计算机使用是说明长时程任务诸多问题的一个好例子。首先，作为一项智能体任务，它更接近真实世界的问题和行为，带来了新的挑战。在计算机使用中，智能体会遇到大量反机器人网页脚本、验证码（captcha）以及冷僻的 Cloudflare 防护功能，而且这些出现得相当零散。这类细节给环境增加了一层此前不存在的调试工作。计算机使用还需要大量基础设施，如虚拟机（VM）和浏览器连接。这些现在必须长时间保持稳定可用，同时还需满足前文讨论过的环境工程要求。

计算机使用任务常常持续数小时。这意味着 rollout 变长、[奖励变得更稀疏](https://www.dwarkesh.com/p/timelines-june-2025?manualredirect=)。换言之，智能体多走了十倍的步骤，却只在最后一个 token 上获得奖励。这削弱了 RL 信号。计算机使用还依赖图像和视频来向模型*展示*正在发生什么。虽然已有[研究](https://arxiv.org/pdf/2307.13854v4)尝试通过流式传输 HTML 文件或建立网页的文本表示来做计算机使用，但模型在这种语境下并不理解图像所代表的内容。让文本表示真正可用，将降低计算机使用的内存需求。

## 环境计算

我们看到在*环境计算（environment compute）*而非单纯 RL 算力上投入的巨大潜力。一个例子是用数十乃至数百颗 CPU 协同构建高度逼真、难以被奖励作弊的环境。这是一个完全崭新、亟待扩展的领域。逼真度带来的干净信号可实现惊人的性能提升。

未来的这些环境也将运行在用于模拟真实世界数字孪生（digital twin）的 GPU 上。值得注意的是，这类 GPU 的需求有所不同——它们仍需具备图形/渲染能力，例如 RTX Pro GPU 或客户端 GPU。而 H100、B200、TPU、Trainium 等 AI 专用 GPU 和 ASIC 缺少足够的图形/渲染相关硬件。因此，业界也在投入大量资源，为 RL 环境构建 AI 世界模型，而非本文其他地方描述的常规 RL 环境。这会让扩展更容易，否则环境的复杂度会因各类异构软硬件而爆炸式增长。

可靠、可扩展、易于实现的环境将有极端旺盛的需求，我们预计这会成为初创公司日益活跃的领域。已经[有一些](https://www.mechanize.work/)公司先行入场。有些能力的瓶颈不在于模型能力——o3 已经聪明到足以完成大多数任务——而在于与世界交互并收集上下文的能力。

我们认为这在 AI for science（科学 AI）领域尤其令人兴奋——例如，可以搭建与实验室中任何可测量对象相连的环境。这样的设置会让 AI 智能体掌控物理世界，在接收环境反馈的同时操纵和改变不同因素。在某些场景下，比如控制炉温，反馈回路可以相对很快，模型也能快速迭代。

然而，在其他实验耗时漫长的高价值任务中，模型需要具备与之匹配的连贯时间。再加上需要多次 rollout，最终可能形成在算力和物理层面都要求苛刻的配置。

在生物学、半导体制造以及其他材料科学领域，必须仔细考虑模型所运行和测试的 rollout/消融实验（ablation）的反馈回路。这些生物、制造和工业流程的运行与验证速度存在上限。

某些领域要等 RL 算力发挥作用会慢得多，而另一些领域会因快速反馈回路而迅速改变。物理 AI（Physical AI）的反馈回路天生慢于数字世界，因此才需要真正强大的数字孪生环境。

## 与评测的类比

打个不太精确的比方：概念上更简单的模型评测，跑起来同样困难。Docker 镜像频频失败，选择题中简单的格式改动（例如从 (A) 改成 (1)）就能让模型的评测成绩变化最多达 5%。在评测基础设施刚刚开始扩张时，Anthropic 就[公开谈论过](https://www.anthropic.com/research/evaluating-ai-systems)评测的工程挑战。GPQA 是一个常用评测，以物理、化学、生物的研究生级题目测试模型，它似乎存在一道「噪声天花板」：尽管它显示模型成绩陷入停滞，但由于答案标注错误，拿到 100% 是不可能的。

![](https://substack-post-media.s3.amazonaws.com/public/images/03d927d7-2490-4dd9-a995-46d34948b280_2304x1357.png)
*来源：SemiAnalysis*

随着智能体任务时长增加，这个问题在很多方面正在恶化。模型可采取的动作空间大幅扩大，连贯时间持续增长，而创建能评估这些长时间跨度能力的评测本身就充满挑战，也让评测贵得多。

评测基础设施并非新生事物、概念也简单，却已经是「千刀万剐」式的死法（death by a million paper cuts）。搭建大规模 RL 基础设施并将其扩展，则是在此基础上再挨数百万刀。

## RL 改变硬件与数据中心建设的平衡

面向 GB200 和 GB300 的 Nvidia NVL72 系统在推理（reasoning）领域带来了关键进展。更强的算力实现了更低延迟下的更高吞吐，共享内存则允许用更大的 world size 来分摊 KV 缓存。这不仅让推理阶段的推理模型能更好地做批处理，对 RL 也有重大意义。

对 RL 而言，增加的内存带来了许多不同能力。首先，它允许对给定问题做更多 rollout。其次，它能更好地处理长时程智能体任务。第三，它能更好地容纳更大或更强的推理模型充当裁判，这对不可验证领域尤其有帮助。第四，这一范式高度依赖合成数据的生成与过滤，而这依赖推理——正是 NVL72 系统的强项。算力利用不足是这一过程中令人头疼的一环。

![](https://substack-post-media.s3.amazonaws.com/public/images/e35899d2-a1c2-44b1-8acd-3239e608a323_1959x620.png)
*来源：SemiAnalysis、Nvidia*

在在线 RL 中，最后一个 rollout 与第一个 rollout 的完成时间之间可能存在差异。要对所有不同的采样副本做负载均衡很困难。权重的广播也可能导致显著的算力利用不足，因为不同的采样器和训练器有着不同的拓扑。

RL 的所有阶段都需要推理，但推理**不像预训练时代那样必须集中部署**。RL 需要大量算力，但不必集中在同一地点。

例如，某个领域的合成数据可以在一个数据中心生成并验证，而训练过程可以在完全另一个数据中心进行。随着 RL 主导算力格局，我们可能会看到数据中心建设方式的转变。虽然预训练扩展仍需要最大的多 GW 级数据中心，但 RL 究竟能去中心化到什么程度，尚无定论。

预训练可以一次性占用数万张 GPU，与之不同，为 RL 投入的推理时间可以根据容量灵活调整。这意味着实验室如今可以在非高峰时段利用 GPU，例如在其 RL 管线中生成合成数据。

事实上，我们了解到至少有一家实验室正在利用利用率不足的推理集群执行这一流程，相当于把免费算力通过合成数据生成输送给训练。在实验室内部，推理与训练的界限将继续模糊，使输送给模型的算力超出最大训练集群本身。这些闲置算力之所以能「免费」输送给训练，是因为推理集群本来就必须按峰值需求配置。

RL 的去中心化特性已被 Prime Intellect 的 [Intellect-2 模型](https://arxiv.org/abs/2505.07291)所证明——那是一次面向推理模型的全球分布式 RL 训练。

在硬件设计方面，推理量的增加和长时程智能体任务让内存变得更加重要。RL 消耗的 FLOPs 少于预训练，但内存负载依然沉重。长期来看，硬件研发将为此做出调整，网络拓扑等其他因素也包括在内。我们认为 RL 改变的不只是硬件设计，它还在改变研究的组织方式。

## RL 正在改变实验室的组织结构

面向语言模型的 RL 是首批让推理真正与训练过程交织在一起的场景之一。**推理性能如今直接影响训练速度。**这意味着生产级推理（快速、高效、便宜）已成为模型训练过程不可或缺的组成部分。

每家实验室过去都将「产品服务推理」与「内部推理」（例如用于评测）区分开来。但考虑到 RL 所需的海量推理，必须把超优化的推理栈直接构建在训练栈「之中」。

我们已经在公司组织结构上看到这一点。OpenAI 合并了研究团队与应用研究团队的推理团队。类似地，Anthropic 和 Google 也因此对其生产团队与内部团队进行了重大重组。

## RL 是一场推理的竞赛，但中国缺芯片

这一范式转变的一个后果是推理需要大量算力。就中国而言，出口管制严重限制了可用算力资源，拖慢了他们的研究测试。对 RL 来说，算力有限意味着更少的 rollout、更慢的数据生成与过滤，以及被推迟的实验与验证。短期内这并不致命，因为今年投向 RL 的算力仍停留在数万张 GPU 的量级。

中期来看，中国生态仍将受制于算力。H20 和 H20E（内存更大的 H20 变体）被禁售，严重削弱了推理能力——而推理对 RL 至关重要。正如我们此前指出的，H20 的推理性能优于 H100。

除了部署新模型更慢之外，中国公司还会在向客户提供服务时遇到问题。DeepSeek 应对算力约束的方式是以极慢的速率（每秒 20 个 token）提供模型服务、牺牲用户体验，从而把尽可能多的响应打包成批。这为内部使用保留了尽可能多的算力。DeepSeek 目前在生产中并未使用华为昇腾（Ascend）芯片，出于性能和体验考虑只用 Nvidia，但他们将会开始用。

这件事的影响怎么强调都不为过。由于这项禁令，中国错失了数百万张芯片。

![](https://substack-post-media.s3.amazonaws.com/public/images/edfb9f08-67a9-4879-afae-29837afbb96c_1416x923.png)
*来源：SemiAnalysis 加速器模型*

华为正在激进地扩大昇腾 910B 和 910C 系列的应用。华为昇腾系列的主要客户是阿里巴巴和字节跳动，它们已采购华为芯片，并深度参与为下一代产品的研发过程提供反馈。

除了华为通过规避出口管制从台积电（TSMC）获得的 290 万颗裸片之外，我们还看到国内中芯国际（SMIC）的产量正在显著爬坡：我们目前估计 2025 年国内将生产 38 万颗昇腾 910C，而随着良率改善、加上中芯国际北京 N+2 晶圆厂在上海厂之外投产，明年产量将达到数百万颗。

字节跳动和阿里巴巴也都在推进各自的自研定制芯片，我们正在加速器模型中密切追踪。

## RL 使频繁的模型更新成为可能

预训练体制与当下体制的一个显著区别是：RL 可以在模型发布之后进行。这意味着模型可以先发布，再继续通过 RL 扩展能力，然后再次更新模型。这种迭代式开发可以逐步增强现有模型。DeepSeek R1 的新版本正是这么做的。

这适用于后训练（post-training）整体——如今的 GPT-4o 已经更新过很多次，早已不是最初发布时的那个 GPT-4o 模型。

我们预计，由于这一新范式，Anthropic 对其 Claude 模型的更新频率将远超以往。

## 递归自我改进已经在发生

前面谈到过「更好的模型成为更好的裁判」这种 RL 过程中的自我改进，但还有另一个重要维度。即模型本身帮助训练并编写下一个模型。Claude 4 系统卡为了解实验室的思路提供了具体窗口。Anthropic 做了编译器开发、内核工程，甚至四足机器人 RL 的评估。

![](https://substack-post-media.s3.amazonaws.com/public/images/dd1bcdcc-81ad-43b3-a9eb-87b48f4854c3_2560x1258.png)
*来源：Anthropic Claude 4 系统卡*

事实是，实验室所做的巨量工作是艰难的工程工作，为的是把可用硬件的每一分性能都榨出来。编译器、内核、内存管理优化、超参数调优等，都是可衡量、可改进的编码任务，而它们每一个都对模型效率有巨大影响。递归自我改进常被当作一个带有炫目前景的诱人术语，但现实是它在某种程度上已经发生。实验室还可以对这些任务本身开展 RL 来进一步加码，并且已经拥有不少专门干这个的内部模型变体。

其中大部分起初将围绕那些不起眼的枯燥苦活，并逐步深入到新架构的研究之中。

当前模型并不会让开发速度大幅提升。但 OpenAI 的 Codex 工具已经在帮助员工构建下一个版本。对自我改进的正确理解是：模型会让工程师把更少时间花在写代码上，把更多时间花在思考研究与数据相关的问题上。在模型研发受限于工程投入的范围内，这些瓶颈会被解决。但现实是，模型研发还受制于多种其他因素，包括算力获取。真正的递归自我改进将极大地加速研究和数据环节。

## 工具使用与 o3

o3 模型清楚地展示了 RL 的效果，尤其是它对外部工具的进阶使用。o3 证明智能很有用，但能获取工具并善用工具更有用。OpenAI 做了几件事来实现这一能力。首先是确保模型能访问工具。这可以作为报告中谈到的更广泛基础设施的一部分（例如环境访问）。在模型层面，可以通过特殊 token 来触发访问，模型用它们来调用工具。例如，模型使用 `<search>` 之类的特殊 token 来触发外部搜索，搜索返回结构化结果，可直接用于其推理过程。让模型能使用多种不同的特殊 token，可以让它快速便捷地访问不同环境。

```
USER
“What’s the population density of Zürich in people /km²?”
───────────────────────────────────────────────────────────────
ASSISTANT  (turn 1)
<think>
Need population and area → then divide.
</think>
<answer>
<tool>search_web{"query":"Zürich population"}</tool>
</answer>
────────────────────────────────────────────────────────────────
RUNTIME  (executes the first <tool>)
# observation[0]: "Population of Zürich: 402 762"
────────────────────────────────────────────────────────────────
ASSISTANT  (turn 2 – sees observation[0])
<think>
Population = 402 762. Next: fetch area.
</think>
<answer>
<tool>search_web{"query":"Zürich area km²"}</tool>
</answer>
────────────────────────────────────────────────────────────────
RUNTIME
# observation[1]: "Area of Zürich: 87.88 km²"
────────────────────────────────────────────────────────────────
ASSISTANT  (turn 3)
<think>
Now compute density = 402 762 / 87.88.
</think>
<answer>
<tool>python{"code":"402762 / 87.88"}</tool>
</answer>
────────────────────────────────────────────────────────────────
RUNTIME
# observation[2]: "4586.4"
────────────────────────────────────────────────────────────────
ASSISTANT  (turn 4 – final reply)
<think>
Compose prose answer and cite both search results.
</think>
<answer>
Zürich’s population density is **≈ 4 586 people /km²**
(using population = 402 762 and area = 87.88 km²).
Sources: search result [0], search result [1].
</answer>
```

另一个挑战是挑选合适的问题集用于训练。即便模型能使用工具，如果不需要，它也可能完全不去用。有效的模型训练需要提供足够难、必须借助工具的问题，确保模型学会自然而然地利用外部资源。这非常难拿捏，需要大量测试来验证。不过，过度使用工具也会损害性能，使奖励信号复杂化，降低整体效果。

![](https://substack-post-media.s3.amazonaws.com/public/images/0b194305-36b5-4a16-96ae-a44faa7e3424_2560x839.png)
*来源：Wang 等*

其他因素还包括：确保 rollout 拥有大量初始状态、且每个起点有多个响应，以帮助稳定性和学习效率；对格式错误的输出施加惩罚；对正确使用的标签给予奖励。

打造 o3 需要让模型能访问多种工具（例如通过特殊 token），并用迫使模型使用这些工具的问题来训练。

## o3 为什么会产生幻觉

o3 虽然拥有强大的检索和钻研能力，却以产生幻觉而臭名昭著。这个模型会非常频繁地编造内容。而且随着 RL 算力的扩大，这个问题变得更糟了。为什么会这样？

我们认为这要追溯到这些模型的训练方式。模型通常只因结果正确而获得奖励，却不因推理错误而受罚，这使它们能够通过有缺陷的逻辑达到准确。

例如，一个模型可能误解了某个简单棋类游戏的规则却仍然获胜，从而错误地「学到」其有缺陷的推理是可以接受的。这不仅没有惩罚模型的错误思考，反而在积极奖励这种行为。

![](https://substack-post-media.s3.amazonaws.com/public/images/058b2cd7-44e9-4149-bee0-92ac7a3c16bc_1682x1772.png)
*来源：Wang 等*

我们预计这种行为并不止于棋类游戏。这在无意之中教会了模型在新的、未经训练的场景中产生幻觉，把有缺陷的推理扩散到更广泛的情境中。使用推理模型充当裁判会有一定帮助，因为它们能修正整条推理轨迹。其他思路包括更精细的奖励信号——对每个 token 区别对待，在奖励正确答案的同时惩罚错误逻辑。

需要说明的是，这种不正确的奖励行为也会影响代码之类的东西。一个模型可能写出糟糕透顶的代码，却仍能通过单元测试。这再次凸显了拥有正确奖励函数的必要性。
