# 引言：重新思考 GPU 集群的总成本

现代 GPU 贵得令人难以置信。单颗 Blackwell GPU 的价格超过一辆普通汽车，耗电量则超过一栋独栋住宅。如今，独角兽创业公司拥有成千上万颗这样的 GPU 日夜不停地为自己工作，已是司空见惯。许多基础模型公司在 GPU 上的花费已经比在员工身上的花费高出一个数量级。我们知道有多家公司把超过 80% 的初始融资投在了 GPU 上。创业公司创始人在为公司制定财务规划时，如今需要考虑四大类重要开支：

> 1. GPU 集群
>
> 2. token
>
> 3. 员工
>
> 4. 其他一切

传统上，在决定从哪里获取集群来解决第一类开支时，企业会以每小时成本为基础来评估各家新兴 GPU 云（neocloud），聚焦于最昂贵的开支项：GPU。然而，只盯着提供商给出的每 GPU 小时价格可能会产生误导。实际上，一旦把训练模型或搭建推理端点所涉及的一切都算进来，两个每 GPU 小时定价完全相同的云产品，其总拥有成本（TCO）可能相差甚远。停机时间、搭建时间、调试时间，以及对网络和存储进行必要性能调优等因素，都会显著影响用户每花一美元能完成多少有效工作。CPU 算力、网络、存储、编排软件和支持服务等非 GPU 开销也可能被隐藏起来、未被纳入考量。换句话说，表面上更便宜的集群在很多情况下最终反而更贵。

SemiAnalysis ClusterMAX™ 研究的核心前提是：不同 GPU 云提供商的集群质量差异巨大，而这些差异会对最终用户体验、生产力乃至 TCO 产生实质性的影响。其中许多因素并不会体现在硬件规格、参考架构或一次性性能基准测试中。可靠性、网络行为、存储性能和支持服务的差异，影响的才是唯一真正重要的指标：达成研究目标所需的时间（time-to-research-objective）。

在本文中，我们提出一套超越每 GPU 小时原始价格的 GPU 集群 TCO 计算方法论。我们定义了一个框架，既纳入算力、存储、网络和支持等直接成本，也纳入与可靠性、调试和搭建相关的间接成本。使用这一框架，我们比较三类获得 ClusterMAX 评级的提供商：一家金级（gold-tier）新兴 GPU 云、一家银级超大规模云厂商，以及一家银级新兴 GPU 云。我们将这一方法论应用于三种代表性集群配置，涵盖大型 LLM 预训练、多模态 RL 研究和推理端点。

为了进行这项比较，我们使用了我们的 [GPU 集群 TCO 计算器](https://www.clustermax.ai/tco)和[有效吞吐计算器](https://www.clustermax.ai/tco)，这两个工具已在 ClusterMAX 网站上免费发布。任何读者都可以代入自己的数值构建自定义场景并查看结果。我们会在本文后面解释计算器背后的公式，并介绍我们的「有效吞吐大统一理论」。

这些计算器的输入数据来自我们的 [GPU 租赁定价](https://semianalysis.com/semianalysis-data-products/#gpu-rental-pricing)数据系列、对 80 多家新兴 GPU 云的实测经验，以及在 [ClusterMAX 1.0](https://newsletter.semianalysis.com/p/the-gpu-cloud-clustermax-rating-system-how-to-rent-gpus)、[ClusterMAX 2.0](https://newsletter.semianalysis.com/p/clustermax-20-the-industry-standard) 研究过程中开展的、并延续至今（服务于 ClusterMAX 3.0）的对 [150 多位终端用户客户](https://www.clustermax.ai/quotes)的访谈。

我们的研究结果说明了为什么 ClusterMAX 金级提供商能够获得定价溢价（或者能在同等价格下赢得订单）。具体而言，我们发现，在保持 GPU 定价不变的情况下，在一组具有代表性的大型训练负载上，金级提供商的 TCO 比银级提供商低大约 5-15%；但在单节点推理集群这类容错负载上，这一差距会缩小到接近于零。换句话说，我们为用户在理解容错益处过程中所形成的直觉，赋予了真实的美元量化价值。

# 定义与关键术语

为了在同等基础上评估各种 GPU 云产品，我们将 GPU 集群的 TCO 拆解如下。

1. **GPU [$/GPU-hr]：** GPU 集群的招牌租金价格。它从提供商的目录价出发，再计入因合同期限承诺或采购量而获得的折扣、对竞价/可抢占实例的计划使用，以及编排溢价。所谓编排溢价（orchestration premium），是指超出基础实例之外的加价——例如在 AWS 上通过 SageMaker HyperPod Slurm 使用 Kubernetes 或 Slurm 时，即使底层 GPU 机器完全相同，客户为 SageMaker 实例类型支付的价格通常也高于标准 EC2 实例类型。我们将这些折扣与溢价计入，以推导出准确的每 GPU 小时成本。至关重要的是，本报告使用的数据来自我们的两款机构级产品：[AI 云 TCO 模型](https://semianalysis.com/ai-cloud-tco-model/)和 [GPU 租赁定价数据系列](https://semianalysis.com/semianalysis-data-products/#gpu-rental-pricing)。我们默认的 GPU 定价是 2025 年 8 月的历史快照。我们在[近期的一篇文章](https://newsletter.semianalysis.com/p/the-great-gpu-shortage-rental-capacity)中描述了此后的变化。如需获取我们的 GPU 定价数据系列，请联系 [sales@semianalysis.com](mailto:sales@semianalysis.com)。

2. **存储 [$/GB-mo]：** 存储数据的成本。这包括高性能的「热」存储（例如基于 NVMe 的并行文件系统）、面向较低频访问数据的低层「温」存储或对象存储，以及「冷」归档存储。我们还将所有数据访问成本计入其中：例如对象存储的 API 调用费用，或数据离开该云时的数据流出（egress）费用。在训练期间移动大规模数据集和模型检查点时，以及推理期间考虑存储日志和指标（如今还包括图像、视频和音频数据）时，这些费用可能相当可观。基于客户调研，我们在不同集群场景中将假设调整到低至每 GPU 2TB、高至每 GPU 25TB 的区间。我们还跟踪各提供商的公开定价（标准化为每 GB 每月），并在集群 TCO 计算器中以免费下拉菜单的形式发布这些数据。值得注意的是，即使是同一提供商的不同产品之间，存储性能也可能天差地别。例如，AWS FSx for Lustre 有 4 个不同的吞吐量档位（从 125 MB/s/TiB 到 1,000 MB/s/TiB），目录价下 4 倍吞吐量要多收约 3 倍的费用。在后面讨论的有效吞吐计算中，我们允许在输入阶段（例如作业初始化时间）考虑这一差异。

3. **网络 [$/hr 或 $/GB-mo]：** 前端/南北向（N-S）网络功能的成本。网络服务包括公网 IP、防火墙/安全组、负载均衡器、数据流出和数据传输。例如，将训练数据或模型权重移出 AWS 或在 AWS 各区域之间传输，可能产生可观的费用。对于后端/东西向（E-W）网络，我们做一个简化假设：所有集群在完成搭建后，最终都能凭借高带宽互连（即 InfiniBand、RoCE、EFA 等）达到相近的性能水平。因此相关成本差异将在后文的「搭建开销」和「调试开销」中考虑。

4. **控制平面 [$/hr]：** 管理集群的成本。就编排软件控制平面而言，指用于登录、代码开发和作业提交的节点。用于数据处理的额外 CPU 节点以及 RL rollout 环境，也可以归入这里。

5. **支持 [% 加价]：** 支持服务的成本。例如在 AWS 上，这是对整张云账单的额外收费，共有三种不同方案，随月度支出逐步升档，费率从最初的 10% 一路降到最终的 3%。当然，不同档位的支持意味着在发生故障或性能问题时的响应也更及时。

6. **有效吞吐开销（Goodput Expense）[% 加价]：** 第一项不会出现在月度账单上的成本，是使用较低档提供商所伴随的隐性成本。我们用这个百分比来计入集群停机带来的额外成本——表现为需要更多的租用时间，或完成的有效工作更少。实践中，实际的停机时长或作业中断次数取决于提供商、具体数据中心、硬件和负载。用于计算这项开销的输入包括中断/故障总数、识别故障所需时间，以及修复/更换节点的时间。单次故障/中断的影响还取决于集群设计，例如故障的影响范围（blast radius）、训练初始化时间、平均作业规模、检查点保存频率和/或是否使用容错软件框架。计算器的这部分输入，也是用户以总百分比的形式、把不良 SLA 带来的风险定价进去的机会。例如，提供商承诺 95% 的集群正常 uptime SLA，就意味着 5% 的停机时间既不需要响应，也没有任何赔偿积分。由于这项输入非常复杂，我们专门做了一个包含多种场景的第二个标签页。后文详述。

7. **搭建开销 [$/hr]：** 让工程师搭建集群并调优性能的成本。例如在 AWS 上，POC 不是免费的，而且用户反馈，要调优 NCCL + EFA 参数以达到与 InfiniBand 或 RoCE 网络同等的性能水平，可能需要多名工程师数周到数月的工作。由于在很多情况下这需要占用整个集群专门从事这项工作，因此额外的费用项既包括工程工时，也包括用于性能调优的集群时间。

8. **调试开销 [$/hr]：** 让工程师长期调试集群的成本，也就是「工程上的头疼」的成本。例如在 AWS 上，用户反馈，调试 NCCL + EFA 问题需要穿透 4 到 5 层间接环节——从他们的 PyTorch 代码，一路穿过驱动栈，深入到 NIC/交换机的固件/硬件配方。换句话说，这些费用项包括持续投入的工程时间，以及浪费在失败作业上的集群时间。

# 有效吞吐大统一理论

首先，什么是有效吞吐（goodput）？

在训练语境下，有效吞吐被定义为用户在其集群上能完成的有效工作量。Goodput 这个词脱胎于 throughput（吞吐量），意在说明并非所有吞吐都是「有效」的。如果有 GPU 从总线上掉卡、NCCL 卡死，或者下一次保存检查点时随时可能触发 OOM，那么再高的训练吞吐也可能是「无效」的。

这些问题在规模化之后会显著放大。正如下文所展示的，集群越大、作业越大，单次故障或中断造成的影响也越大。如果你 80% 的集群在跑同一个作业，而这个作业不得不重启（取决于存储、网络、CPU、缓存配置等，这一过程可能需要 10-15 分钟），那么这 10-15 分钟的集群时间就全部浪费在作业初始化上，再加上从上一次检查点到故障/中断/崩溃时刻之间所有白费的计算。

正如我们在 [ClusterMAX 2.0](https://newsletter.semianalysis.com/i/178057384/monitoring-and-health-checks) 中所解释的，集群级 MTBF（平均无故障时间）在这里也起作用。既然所有 GPU 终究会坏，你的作业越大，两次故障之间可用来做有效工作（有效吞吐）的时间就越少。

这里用一张便捷的表格来说明这个概念。随着节点故障越来越常见（沿图表 y 轴向下），集群规模越来越大（沿图表 x 轴向右），故障间隔时间（MTBF）变得越来越短。

## TorchFT

TorchFT 是容错训练框架的开源标准。该框架可以轻松集成到现有 torchtitan 代码中，让大规模集群上的训练作业在发生硬件故障时继续运行。无需检查点（或者说，实际上可以降低保存检查点的频率）。但故障影响范围（blast radius）是整个副本组。

![灯塔示意图
AI 生成的内容可能不正确。](https://substack-post-media.s3.amazonaws.com/public/images/47a9d347-63ee-40aa-b9c4-cec6ae6704c9_632x633.png)

来源：[PyTorch 官方博客关于 TorchFT 的文章](https://pytorch.org/blog/fault-tolerant-llama-training-with-2000-synthetic-failures-every-15-seconds-and-no-checkpoints-on-crusoe-l40s/)

由于 TorchFT 的影响范围是整个副本组（即 HSDP 作业中的一个 FSDP 分片），当组内任何 GPU 或节点发生故障时，整组的 torchrun 进程都会崩溃。这意味着该组内的所有 GPU 在恢复完成之前都处于空闲状态。因此，在 FSDP shard=16 下，单颗 GPU 故障会让 16 颗 GPU 全部停摆；shard=32 时则是 32 颗，以此类推。

具体到 FSDP，相关的故障域是通信组，而不只是集群的原始规模。由于参数在计算前要 all-gather，梯度在反向传播中要 reduce-scatter，单个失效或挂起的 rank 就可能让整个参与组停摆。在实践中，HSDP 让这一点更加显性：影响范围变成了副本组层面的拓扑决策，而不再是整个集群的属性。

这里存在一个权衡。当某个副本组挂掉时，在该节点被更换之前，你会失去整组的 GPU；一个存活的组通过 `state_dict()` 序列化其完整的模型 + 优化器状态，经 HTTP 提供给正在恢复的组，后者调用 `load_state_dict()`，同步步数计数器，然后重新加入仲裁组（quorum）。整个过程由 TorchFT 的 lighthouse 服务器编排，你必须把它安装在集群上。

![](https://substack-post-media.s3.amazonaws.com/public/images/c1691f96-d240-4f0a-bd5f-4816491156db_2090x606.png)
*来源：Meta，https://arxiv.org/abs/2410.21680v2*

并非所有大规模故障都以 GPU 或节点死亡的形式呈现。相当一部分事件最初表现为集合通信卡死或 watchdog 超时，而这些只是症状。从 TCO 的角度看，这意味着有效吞吐损失不仅包括修复或更换时间，还包括在各参与 rank 之间检测、归因并解开一个挂起的集合通信所需的时间。

保存检查点本身也可能是故障税的一部分。在 FSDP2 上，把 DTensor state dict 转回完整张量用于保存，会跨 rank 触发一次 all-gather。检查点保存频率既是一个可靠性参数，也是一个通信与故障暴露面的参数。

不过，这种容错是有性能代价的。由于 TorchFT 要求跨副本组通信使用 GLOO 而非 NCCL，每次迭代都要通过 CPU、经前端 TCP 执行 allreduce，而不是走后端 RDMA 网络，由此产生开销。在初步测试中，我们在可比的 HSDP 作业上看到了超过 10% 的性能差异。因此，在考虑有效吞吐开销时，如果用户选择运行 TorchFT，我们允许把这一性能差异计入「网络开销（%）」这一项。

容错影响的不仅是恢复延迟，还可能影响训练语义。随着副本组的掉线与重新加入，健康参与者的数量（从而有效 batch 大小）可能在每一步之间变化。在把 TorchFT 与检查点重启或在线迁移方案相比较时，有些方法通过接受暂时性的降级参与来保持前向进展，这可能影响优化器动态和吞吐的核算。

值得注意的是，TorchFT 与调度器无关，因此同时支持 Kubernetes 和 Slurm。

## AWS SageMaker HyperPod 无检查点训练（Checkpointless Training）

AWS 于 2025 年 12 月为其 SageMaker HyperPod EKS 集群推出了无检查点训练（checkpointless training）。这是针对前述同一容错问题的纯 Kubernetes、纯 NeMo Megatron 方案。亚马逊内部开发这项技术用于训练其 Nova 模型，并已在 1k+ GPU 规模上得到验证。

无检查点训练的核心是模型冗余（model redundancy）概念。也就是说，模型和优化器状态被限制在副本组内，然后跨副本组同步（不过 AWS 把它们称为节点组）。与 TorchFT 类似，正是这种跨组同步的存在，使得故障节点和故障组可以在不中断运行中作业的情况下恢复。影响范围与该组相对于整个作业规模的占比成正比。运行时，每颗 GPU 都在对端 GPU 上维护其模型分片的冗余副本，这意味着故障发生时，恢复进程通过 EFA 上的 RDMA 加载状态。该过程由 CheckpointManager 管理，只要你通过 SageMaker HyperPod Training Operator 调度作业，这就是一个相对简单的代码改动。

这里有一个明确的内存开销权衡。引用 AWS 文档：「高精度主模型权重/梯度和优化器状态会受到影响。增加一个冗余模型副本，会使设备内存占用增加大约相当于一个 DCP 检查点大小的量。」换句话说，采用这种容错方式会引入 GPU 内存压力（与副本组相对总作业规模的大小成正比）以及 OOM。其结果是不得不以更小的 batch size 或不同的并行策略运行，相对检查点重启作业而言通常意味着性能损失。因此，在考虑有效吞吐开销时，如果用户选择采用无检查点训练，我们允许把这一性能差异计入「内存开销（%）」这一项。

## Clockwork TorchPass

与前两个框架直接对比，TorchPass 是唯一的商业授权软件产品，也是唯一能与无容错作业保持相同训练性能的选项。换句话说，代码改动极小，也没有性能开销。其成本体现为集群中的空闲节点，或用于抢占较低优先级作业的时间。

TorchPass 通过插件在调度器层面实现。在我们的实测中，这是一个 8 节点的 GKE 集群，通过 PyTorchJob（KubeFlow）和原生 Kubernetes 调度器运行 torchtitan 作业。我们主要测试了「计划内迁移」场景，适用于集群节点升级或维护等中断，以及与 ECC 相关的各类 Xid、GPU 掉卡、电源故障、链路抖动等。在这些场景下，TorchPass 通过 get_state() 支持一种简单的「即时（just-in-time）」检查点概念，允许即将故障的节点通过 RDMA 把状态转移到空闲备节点。值得注意的是，这类软故障场景是大型训练集群中最常见的故障类型——节点随时间缓慢劣化，但仍能工作。

与带有性能开销的检查点重启和 TorchFT 相比，结果一目了然。计划内迁移的恢复时间相近，作业性能也相近。

此外，「计划外迁移」或硬故障（即 GPU、内存、网络或其他硬件故障、突然重启、内核崩溃等）也可以通过与前述 TorchFT 或无检查点训练章节中类似的方法来支持。也就是说，同样的「即时」检查点方法可以把状态从另一个副本组中的健康 worker 迁移到正在加入集群以替换故障节点的空闲节点上。

TorchPass 编排器安装在集群层面，与一个集成到现有训练脚本中的 Manager 类交互。只需在现有训练脚本中添加几行代码，上手相对简单。

总体而言，可供选择的容错框架有很多；随着集群规模扩大，应对这些可靠性挑战已成为必然，用户不能只依赖提供商来处理每一次故障。1k+ GPU 规模的训练代码库，确实需要按照其所运行集群的现实情况来设计。

## 金级（Gold-tier）

通常，我们看到金级提供商的折扣比超大规模云厂商更激进，对于大型集群和长期合同，价格可逼近我们 [GPU 定价数据](https://semianalysis.com/semianalysis-data-products/#gpu-rental-pricing)的第 25 百分位。在我们的测试中，其存储性能强劲，文件和对象存储均有量购折扣。网络方面，InfiniBand 或 RoCE 开箱即用即可达到预期性能，几乎不需要搭建时间。编排软件（Slurm 或 Kubernetes）通常配置得当，设置和使用都很简单。POC 一般免费。支持服务全部为 24x7，响应及时，无需开工单即可直接找到有才华的工程师。这种支持体验已包含在价格中，没有额外隐藏收费。最后，监控仪表盘随集群一并搭好，健康检查默认配置，并提供热备节点池以便故障时快速替换——实际上保证了硬件一旦损坏就会有快速更换。

## 超大规模云厂商（Hyperscaler）

通常，超大规模云厂商提供的量购折扣位于我们 [GPU 定价数据](https://semianalysis.com/semianalysis-data-products/#gpu-rental-pricing)的第 50 至第 75 百分位之间。签有主服务协议（MSA）的大型企业由于额外的隐藏成本，实际价格应预期高于第 75 百分位。开箱默认状态下，我们实测发现存储性能不佳是常态，折扣有限，要提升性能还需额外付费。网络性能通常也需要大量搭建时间，且随时间推移不断出现需要调试的问题，导致大量集群时间浪费在非生产性工作上。此外，POC 通常不免费，这抬高了搭建开销。超大规模云厂商的支持服务还要额外收一笔溢价，不同档位对应不同的响应时间和月度费用。这些费用通常随月度支出的增长，从账单的 10% 逐级下降到 3%。最后，监控仪表盘通常默认并未搭好、也未必默认可访问，还可能伴随额外收费。不过，健康检查一般易于配置，数据中心运营良好（减少了故障和中断的总量），而且既有热备节点池，也有产能保证。

## 银级（Silver-tier）

典型的银级新兴 GPU 云是对不同公司所提供特性的一个代表性综合。通常，我们看到银级 neocloud 的定价高端在第 50 百分位，低端则低于第 25 百分位。买家应当警惕过于激进的折扣，那是低质的信号。存储性能取决于提供商在 VAST 或 Weka 上的经验，量购折扣有一些。InfiniBand 或 RoCEv2 性能通常开箱即用表现良好，但在 Slurm 或 Kubernetes 等编排软件的搭建和调试上可能浪费时间，POC 也并非总是免费。支持服务一般包含在内，但 24x7 响应加上直连工程师的模式并不常见。关键在于，监控仪表盘和健康检查通常不会默认配置。热备节点池可能有，但一般没有产能保证。我们看到冷备才是典型做法，因为银级提供商倾向于依赖其服务器 OEM 代为处理维修。

## 场景 2：多模态 RL 研究

值得注意的是，在上一场景中我们让各提供商的每 GPU 小时价格保持一致。通常情况并非如此。在本场景中，我们假设作业较小，但没有容错。我们假设存储量巨大，即 TB/GPU 配比很高。我们还假设不需要太多搭建/调试时间即可在各提供商处获得同等性能，因为该负载主要受算力或内存带宽限制，而非集合通信限制。

具体而言，我们：

- 选择一个 2,048 颗 B200 的集群，并使用 [GPU 租赁定价](https://semianalysis.com/semianalysis-data-products/#gpu-rental-pricing)追踪器中 2025 年 8 月的真实定价数据：新兴 GPU 云第 25 百分位为 $2.40，超大规模云厂商约在第 50 百分位，为 $3.10。换言之，我们假设超大规模云厂商在 p6.b200.48xlarge 实例按需目录价的基础上提供 75% 的折扣。
- 假设超大规模云厂商对 Slurm 和 Kubernetes 等编排软件收取 10% 的实例定价溢价
- 假设由于这些是研究性作业，客户没有在代码中实现容错，因此提供商是否有热备节点，将影响失败作业在从检查点重启前需要等待多久。
- 假设异步检查点保存频率为 1 小时。我们假设约 12TB/GPU 的高存储配比，具体为 25PB 热档存储，用于多模态训练数据、合成数据生成和模型检查点，额外的冷档存储则托管在远端

再详细解释一下有效吞吐计算：我们假设客户基于 llm-d 或 SGLang OME 等现代 LLM 服务框架实现了容错。发生硬件中断或集群自动扩缩容时，正在处理中的请求会在负载均衡器上重试。因此，一旦发生故障，提供商是否有热备节点只会影响故障节点的正常运行时间，作业仍在继续。新节点重新加入集群后，基本上没有初始化时间或冷启动——只需把模型加载进 GPU 显存即可运行。

# 结论、本研究的局限，以及对未来研究方向的展望

本文的意图是为用户和提供商双方基于直觉形成的判断——即运行可靠、高性能且易用的集群非常重要——提供真实数据支撑。换句话说：即使在每 GPU 小时定价相同的场景下，存储、网络、控制平面、支持、有效吞吐、搭建和调试这些环节始终存在隐藏成本。我们用三个真实场景证明：即使每 GPU 小时定价相同，按 TCO 调整后，超大规模云厂商也可能比金级提供商贵 10% 以上；我们还证明，在每 GPU 小时定价持平时，银级新兴 GPU 云可能贵 15% 以上。

在 ClusterMAX 的范围之外，我们继续与运营大型集群的用户合作，比较各家新兴 GPU 云之间的性能差异。具体来说，[NVIDIA DGXC 基准测试仓库](https://github.com/NVIDIA/dgxc-benchmarking)及相关的 NCP/DGXC 认证流程显示，即使是遵循 NVIDIA 参考架构的提供商，在不同负载上也会出现性能差异。在比较集合通信受限操作下的互连网络时尤其如此——而随着 wide EP、PDD（预填充/解码分离）以及其他在纵向扩展域和横向扩展域上充分利用海量互连带宽的并行技术被广泛采用，这类操作正变得越来越普遍。

关于定价：本分析的所有输入以及计算器上显示的默认值，应被视为基于 2025 年 8 月历史定价数据的时点分析。我们在 [GPU 定价数据](https://semianalysis.com/semianalysis-data-products/#gpu-rental-pricing)中追踪全球所有主要 GPU 在不同集群规模和承诺期限下的新兴 GPU 云定价。而且正如我们在[近期文章](https://newsletter.semianalysis.com/p/the-great-gpu-shortage-rental-capacity)中所述，这些价格正在上涨。我们会持续为订阅客户更新这一数据系列：竞价实例定价按日更新，集群定价按月更新。

容错框架的功能仍需完善。如今 TorchFT 是唯一的开源选项，且在训练领域尚未被广泛采用。同时，本文探讨的三个方案（TorchFT、HyperPod 无检查点训练和 TorchPass）都在通信开销、内存开销、硬故障处理和空闲节点成本上各有取舍。这使得容错训练成为前沿实验室或愿意支付软件许可费者的「秘方」。与此同时，容错推理已成为单机 8 卡系统的标准，并且正被积极内建到 PDD 和 WideEP 框架（如 [NVIDIA Dynamo](https://github.com/ai-dynamo/dynamo)）之中，包括在 KV 缓存卸载层面，通过 [LMCache](https://github.com/LMCache/LMCache) 和 [Mooncake](https://github.com/kvcache-ai/Mooncake) 等框架实现。

## 推理端点利润率的敏感性分析
