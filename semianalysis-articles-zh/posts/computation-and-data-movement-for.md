# 推理中的计算与数据搬运

> 原文：[Computation and Data Movement for Inference](https://newsletter.semianalysis.com/p/computation-and-data-movement-for) · SemiAnalysis

> ⚠️ 付费订阅文章：以下为公开可见的预览部分翻译，正文在付费墙处截断，并非全文。

**将 MoE 模型映射到推理硬件：结构、流程与高效服务**

混合专家（Mixture of Experts，MoE）如今已广泛应用于前沿模型，它不仅改变了服务的结构，也改变了有效推理的经济学。它的作用不只是增加参数量：它改变了每个 token 会激活哪些张量、哪些数据必须紧邻放置、哪些传输需要强大的本地带宽、哪些可以容忍较弱的网络链路，以及内存搬运、存储和调度如何共同贡献有效吞吐量。

最好的切入点是把服务当作一个整体来看。推理运行在一个集群之内，由编排层（orchestration layer）协调，例如 NVIDIA Dynamo、Mooncake 或自研调度器。这些编排层与 vLLM、SQlang 等推理服务器紧密协作，而后者自身也带有编排功能。本文不会深入讲解如何使用某款编排软件或应该如何选型，而是旨在给出整体流程的概览，并解释你可能用到的各种功能背后的原因。

用户（或其智能体）以一个请求（query）开启一段对话，收到回答后还可能继续发起新请求。一次「请求—回答」构成一个轮次（turn）。在现代 AI 系统中，用户通常运行在某个客户端应用里（无论 GUI 还是命令行），而 AI 返回的部分回答会被该应用拦截，作为它自己要执行的指令——例如编辑你的代码，或在某个 HR 问题上检索公司内部规范。

AI 系统也可以在数据中心一侧自行完成其中一些动作，例如搜索网页。这些被拦截的工具动作的结果同样会作为请求返回给 AI，从而产生更多轮次。服务器会维护一份上下文（通常称为 KV 缓存或简称缓存），它是整个会话的浓缩，使来自用户或工具的每个新请求都能被正确解读，保证整体向前推进。当用户让智能体执行一项长任务时，每小时可能出现数千个轮次。对话也可以暂停，数小时甚至数天后再恢复。

当请求到达推理服务器时，编排层将其放入队列，队列随后会送入一个输入填充（input-fill）工作器，并附带系统提示词以及对话中先前轮次的上下文。查询随后被转换为新上下文，追加到对话上。这份新的上下文状态再被移动到一个解码工作器。解码反复读取累积的状态，生成回答 token，而这些回答 token 也会被追加到对话状态中。整个过程可能在工具、智能体、用户和更多输入填充工作之间循环。运行在 GPU 上的模型工作器只是这座 token 工厂的一部分；存储、网络和编排把它的各个阶段连接起来。

在工作器内部，有四种运行状态（operating regime）从一开始就值得区分：

1. **预填充（Prefill）**：初始的一整块新 token 被一起处理。
2. **中间填充（Midfill）**：一个续写请求被追加到已有的缓存上下文上。
3. **解码注意力（Decode attention）**：利用上下文生成新 token 的基础表征。
4. **解码专家（Decode experts）**：每个新 token 的基础表征再由从一大组候选专家中选出的一部分专家精炼。

这些运行状态对算力、内存和网络的要求各不相同。预填充与中间填充关系密切——预填充就是零先前上下文的中间填充。不过预填充是一个常见的特例，对应经典「聊天机器人」式的一次性提问，其优化方式可以与中间填充略有不同。预填充能达到很高的算术强度（arithmetic intensity，即计算量与数据搬运量之比），而且不需要等待上下文的定位和读取。中间填充则从一个已有的 KV 缓存（先前状态）出发，追加一段新的请求输入序列。它的算术强度通常低于预填充，因为新 token 更少，而每个 token 需要搬运的既有数据更多。

解码注意力与解码专家的算术强度通常很低，因为与先前上下文或专家权重相比，新 token 太少——而在解码状态下，这些上下文和权重都是需要搬运的数据。与此同时，在全部四种状态中，注意力张量和专家张量与 token 的取值无关，因此让尽可能多的 token 共享同一次张量读取是有收益的，哪怕这些 token 来自其他用户的不相关请求——只要它们恰好同时运行、且网络距离近到可以共享。把四种模式一概当成同一种工作负载处理，就等于放弃了 MoE 模型在不同算术强度与不同共享模式上的大部分结构性优势。

本文将分别讨论这 4 个阶段，并且在部分讨论中假设它们是分离式（disaggregated）部署的。聚合式（aggregated，模型留在同一台服务器上，随请求推进在各个阶段之间重配置）与分离式（由编排器在另一台已配置妥当的机器上找到空闲槽位）之间各有取舍。总体上，我们把各阶段当作分离式来讨论，聚合式则作为一种特例——即前一个阶段结束时，当前节点总是恰好可用。文末会在更完整地介绍完各项工作之后，专门讨论这些取舍。

transformer 模型是一个由重复层组（layer group）构成的深栈。一个层组可以只包含一种层，也可以包含一个全注意力（full-attention）层加上若干线性注意力、局部注意力、选择性注意力或其他经优化的注意力层（这就是混合层组）。在每一层内部，注意力、共享变换、路由、被选中的专家与重组依次发生。这些步骤事先已知并不断重复，因此同一批硬件资源可以在不同时刻服务于流程的不同部分。

机器同样可以描述为同样简单的重复单元。一个节点（node）是一组加速器，通常是机柜里的一个托盘（tray），每个加速器将算力与本地快速内存配对。节点由 CPU 协调，并通过 NIC（网络接口控制器）连接到其他节点。节点堆叠成机柜。当需要处理超大张量时，一个机柜可以充当单一的纵向扩展域，也可以是若干个更小的纵向扩展岛，或一组流水线阶段。数据中心网络随后把有边界的各个工作器连接到存储与编排，而不参与每一次内部张量运算。

本文正是沿着这条脉络展开。它从全局服务与各运行状态开始，然后把模型展开成宽阔的层组切片，并映射到加速器节点与机柜上。在此基础上，本文进一步展开流水线并行、张量并行与专家并行，KV 缓存内存带来的限制，批处理在预填充、中间填充与解码中的不同价值，以及调度在一座多机柜 token 工厂中的角色。

## 1. 编排层经由队列把请求送入各工作器池

推理服务是一个集群：先前的请求与不可变状态在空闲时被存储起来；当新请求引入上下文、或先前请求重新唤醒需要续写时，它们再排队送入专门的工作器。进入队列的请求还不是批次。每个请求携带提示词 token、对可复用上下文的引用、服务目标，通常还有既有的会话或智能体状态。编排器可以把它放入预填充、中间填充或解码批次；请求完成后可以独立地加入或离开该批次，把容量让给新工作。当调度器知道哪些工作器拥有与请求上下文长度和服务目标相匹配的槽位时，连续批处理（continuous batching）的效果最好。

预填充工作器从一整块新 token 创建上下文。它们的输出是模型每一层的新 KV 状态，独立于创建它的工作器存储。KV 状态沿模型各层移动：上一轮第 K 层的输出成为下一轮第 K 层的输入。在流水线化服务器中，这自然形成了输出与输入分别从不同 NIC 进出的「种子式并发传输（torrenting）」。

中间填充工作器扩展先前已处理过的上下文。缓存的前缀可能包含系统与用户提示词、记忆、更早的对话轮次、智能体步骤或检索到的文档。庞大的根（root）可能已经缓存，而增量输入则可能远小于同等规模的无缓存请求：一个五十万 token 的上下文，可能只需接收几百或几千个新 token。

解码工作器消费已处理、已累积的上下文，每趟生成一个或少数几个 token（多 token 预测已相当常见）。每个生成的 token 都会追加少量新状态。当用户、工具或智能体再贡献一块输入时，同一份上下文之后可以回到某个中间填充工作器。使用工具的智能体工作会形成「上下文扩展—生成」的反复序列，而不仅仅是一次预填充加一次解码。

一个工作器可以占据一个节点、一个托盘或一个机柜。服务通过运行大量有边界的工作器并在其间搬运请求与状态而变大。取决于精度与工作状态的要求，即使是数万亿参数的模型也能装进现代机柜级系统的总内存里。数据中心网络仍然不可或缺，因为工厂必须把许多这样的工作器连接到共享存储，并持续让工作器配置与需求相匹配。KV 传输可能以 GB 计，但它们可以条带化或以 torrent 方式分散到多条链路和多个目的地；其搬运时间仍可远低于一个长解码任务的生存期。

这种分离对性能和运维都有好处。一旦缓存前缀长度、新 token 数量与工作器配置已知，预填充和中间填充就是可预测的。解码的完成时间是随机的，因为最终输出 token 何时出现无法提前预测。池之间的共享内存与存储让每个阶段按自己的节奏运行。本文后面的章节会讨论队列、就绪缓冲（ready buffer）与工作器重配置。目前的关键点是：服务是一个由可移动状态衔接起来的阶段环路。

## 2. KV 状态以不可变 blob 的形式移动

在数据中心规模下，可复用上下文变成一个由不可变 blob 组成的共享对象存储，而不再是依附于某台机器的文件。系统提示词、项目上下文、先前的用户轮次、工具输出和已生成的 token 可以分属不同的 blob。新操作读取它需要的 blob 并追加新 blob；既有 blob 通常保持不变。这种只前进（forward-only）的结构与因果（causal）transformer 本身一致。变更可以通过回溯并创建新分支来处理，而不是重写公共路径。

这些 blob 的持久源头是一个快速、并行、横向扩展的内存与存储池。它需要足够的总带宽与网络覆盖范围，使得预填充、中间填充与解码工作器可以按适配性与可用性来挑选，而不是因为只有某台机器握有上下文的唯一副本。新近空闲的 blob 可以先移入共享的网络挂载 DRAM，包括节点 CPU 内存和专用内存设备。当这一层快满时，分类器可以丢弃不太可能被复用的 blob，或将存活更久的状态提升到 SSD。底层文本和引用通常比展开后的 KV 表示小若干个数量级，因此如果分级处置（triage）决定复用空间并丢弃已展开的内嵌状态，也可以从较小的文本重建 KV blob。AI 计算可能存在细微差异，因此虽然重建出的状态可以预期是有效上下文，但各家服务在「多随意地丢弃与重建」以及「多努力保留重要不可变状态」上会采取不同策略。

想深入了解 blob 的管理方式，推荐阅读 [Unified Radix Cache: One Tree for Hybrid Model Prefix Caching - LMSYS Org](https://www.lmsys.org/blog/2026-08-11-unified-radix-cache)。它不是最终定论，但写得清楚，并且会为你指向更多资料。

长时运行的智能体会不断把上下文累积到上限，因此状态压缩十分频繁；一般来说，一次压缩之后会有许多先前的 blob 被废弃，让位于新的上下文。压缩前上下文占用的空间多半会被回收用于新工作。

可以看到，当上下文接近各模型的实际上下文上限（Opus 4.8 为 250k token，Fable 为 1MT）时，压缩出现在这些对话的右半段。两条曲线中还存在着一些转瞬即逝的「钟乳石」，它们反映了 Anthropic 模型的一些专有行为。

加速器的 HBM 是「热」工作层。它太贵、供应也太紧张，不适合作为被动上下文存储的默认选择。活跃的前缀与后缀应当在使用前不久才进入 HBM，并在工作器用完后尽快离开。CPU DRAM 是有用的暂存与组装层，尤其对流出状态而言：工作器完成工作后可以先把新生成的 blob 移入 CPU 内存，同时存储系统选择放置位置与冗余策略，之后 NIC 再把它们送入共享池。

对流入数据而言，支持 RDMA 的系统可以让网络把数据直接放进加速器内存，避免经 CPU DRAM 做一次完整拷贝。CPU 内存对元数据、协调、部分组装、兜底路径、副本与流出暂存仍然有用。当一个工作器使用多张 GPU 时，流入的上下文可以并行地条带化直写到各自的目标内存。

机柜级热 blob 缓存也很有用，可以用内存/存储设备实现，也可以利用被划入分布式存储池的 CPU 内存。系统提示词这类极常见的对象是天然候选。这些缓存应当保持为共享的横向扩展资源，而不是把请求绑死在某台解码机上的私有状态。HBM 比 DDR 贵数倍、供应也更紧张。HBM 的最佳用途，是正在创造收入的活跃批次中的数据。

数据输入通常大于输出。中间填充通常读取一个大前缀、追加一个有意义但更小的后缀。解码读取累积的上下文，只追加一个或少数几个生成 token 的状态。读取是重复的，写入通常只发生一次。系统设计应当直接用每条数据路径的宽度体现这些差异。

## 3. 预填充、中间填充与解码形成各自不同的运行状态

全局服务包含若干种计算状态。它们之间的差异比「算力受限（compute-bound）」「内存受限（memory-bound）」这类泛化标签更有用，因为每一种都有不同的复用机会、也自然地映射到不同的硬件。

### 3.1 预填充

经典预填充从很少或没有可复用 KV 状态开始，处理一整块新 token。这些 token 共享权重加载、高效利用矩阵运算，并产生足够的路由激活，形成有用的共享专家批次。注意力与稠密变换可以达到很高的算术强度，因此预填充往往主要受算力约束。很长的初始输入上下文会抬高内存流量，但它们很少达到 100,000 token 的长度，而中间填充则常常超过这个数。

### 3.2 中间填充

中间填充把新 token 追加到一个长得多的缓存前缀上。新块仍能提供数百到数千个激活，用于共享权重与专家复用，把算术强度提升到每字节数据数千次运算的水平。注意力还必须读取一份庞大的既有 KV 状态，可能达到几十 GB。因此它处于一种混合状态：算术复用多于解码，但缓存状态流量又远大于同等新 token 数量的初始预填充。

### 3.3 解码注意力

解码以每个查询一到几个 token 的输入推进。每个查询自带自己的 KV 状态，其长度与中间填充所处理的相当。如果说预填充与中间填充的差别在缓存长度，那么解码与中间填充的差别就在输入序列长度。这一到几个输入 token 使算术强度保持在低位，这项工作显然由围绕 KV 缓存的内存搬运主导。

对长上下文而言，注意力的读取量可能超过与模型权重相关的张量运算规模。因此，尽管模型的大部分参数位于专家中，注意力仍是现代解码中最大的运算之一。Delta、top-k 或线性注意力等算法层可以减轻负担，但周期性出现的全注意力层依然是一项沉重的内存负载。每个查询自带上下文，因此对查询做批处理并不会改变注意力的算术强度。

### 3.4 解码专家

专家并非解码阶段独有。模型在哪里运行，专家就在哪里运行，而且除了单个 token 的嵌入之外，它们不需要任何上下文。查询的历史已经被压缩进呈现给专家的激活里。这使得各种跨全部可用 GPU 共享专家的设计成为可能：降低单 GPU 内存占用，提高内存带宽/内存容量（即内存强度）之比。你可以把 GPU 读完全部自身专家所需的时间间隔视为最佳交互性（每个用户看到的 token 速率）——若内存带宽不变而 GPU 负责的专家更少，交互性就可以更高。麻烦在于网络需求也随之上升，而且路由到专家所需的 all-to-all 模式是出了名的难搞。

在（预填充、中间填充或解码的）注意力末端，一次路由计算（作用在未经精炼 token 上的小张量运算）为每个新 token 选出若干专家。选中同一专家的 token 即便来自不同请求，也能共享一次张量权重加载——前提是能及时把它们汇集到一起、赶上同一次权重加载。实际上全部层加起来可能有 15,000 个专家，要利用这种巧合，需要刻意的同步——例如等到批次内所有查询都完成注意力之后，再切换到把它们送去执行专家工作；而这又可以通过让附近不同机器上的多个实例也同步到同一时间表来进一步改善。如果你曾疑惑 Nvidia 为什么如此费劲地把 72 个 GPU 连得这么紧，这就是很大一部分原因。在一座大型 token 工厂里，让这 72 台机器全部同步运行是可行的，从而一层内的专家最多可被切分成 72 份。如果模型一层有 256 个专家，那么每张 GPU 在每层只需处理 3 或 4 个，就能极快地完整轮询全部专家。代价则是海量的 all-to-all 流量。

如果你的专家全部能放进 SRAM，有趣的事情就发生了。你需要数量庞大的加速器和一张怪兽级网络，把所有激活 all-to-all 地收回到各 GPU，但此时几乎没有理由再等待批次成形——每个专家一有输入就可以运行。每加载一字节的能耗最多可比从 HBM 加载好 100 倍，因此单个 token 的运行效率可以媲美此前约 100 个排队的 token。作为这种 DAF（disaggregated attention-FFN，分离式注意力-FFN，专家即 FFN）的回报，你可以让各实例摆脱同步的束缚。这一优势对预填充或中间填充帮助没那么大——它们本来就轻而易举地拥有一批 token、可以按层分拣进共享队列——但它仍可能把全部专家权重从这些 GPU 上卸载下来，让它们把本地内存优化用于其他用途，比如更长的上下文。网络依旧是那个坑：基于 SRAM 的加速器可以在不到一微秒内完成一次专家计算，而现在你可能会让数百万 token 的 all-to-all 流量灌满一台连接数百个节点的交换机。这张网络烧掉的钱和电，可能比它所连接的专家还多。

推理工作器可以通过协调同一模型层上的众多注意力实例来改善共享。它们的路由激活从同一层的专家库中提取，减少了每个目的地必须加载的不同专家数量。在流水线服务器中，这也意味着用于专家并行的网络连接可以局部于机器的该阶段——永远不会出现需要其他层专家的路由。即便如此，每个解码请求每趟只贡献一个新 token、典型地路由到 8 到 16 个专家，而一层可能包含数百个专家。在小批次下，共享依然有限，内存带宽继续主导 KV 扫描与活跃专家加载，每加载一字节权重只伴随极少的计算。无论使用哪种内存，专家内存都必须做到极低的每比特能耗。

这些运行状态解释了：为什么预填充、中间填充与解码可能偏好不同的工作器配置；为什么解码注意力与解码专家可能偏好节点内的不同摆放；为什么批处理对每个阶段的帮助各不相同。随着现代智能体工作中的预填充迅速扩展到 500k token 量级，内存搬运量巨大，尤其是在 token 解码——模型生成有用中间与最终结果的阶段。又快又大的 3D RAM 将对效率起决定性作用。快速内存对中间填充同样有用。不过，对于如今已被视为常态的大上下文，容量必须达到一个下限。如果内存容量太小，网络损耗和过多的芯片集群反而会浪费电力，不如那些通过 3D 容量扩展又不牺牲吞吐量的未来内存类型。

![](https://substack-post-media.s3.amazonaws.com/public/images/a138a4da-0245-453d-8d93-dbeca158f2f6_1171x592.png)
*图 7：在 500k token 上下文缓存长度下，更快内存（混合键合 DRAM、超高速 3D RAM）对中间填充与解码的预估影响。来源：SemiAnalysis 模型模拟器，采用预估的加速器与 GPU 性能。*

虽然 Vera Rubin 72 在算术强度高的中间填充层可以大杀四方，但切换到内存密集的解码后就没那么有效了——Rubin 无法完全施展其算力。在大上下文下，把解码工作与中间填充留在同一节点内非常有价值，可避免把上下文跨网络送到另一个节点。这可能有利于那种兼具超强内存吞吐与真正高效算力的全能型芯片。

## 4. MoE 预填充层内的流程

经典预填充从注意力开始。一块新的查询 token 关注系统提示词等可复用前缀，以及新块内更早的位置。注意力运算为每个新 token 产出一个激活，共享变换再把这些激活准备好，送入路由专家阶段。

路由器为每个 token 指派若干专家。如果模型选择 8 个路由专家，那么每个输入 token 在一个可能包含 256 个或更多专家的专家库上产生约 8 条路由。按 token 顺序看，这些记录稀疏且交错：相邻 token 的目的地可能完全不同。但纵观整个输入块，每个专家都能累积出一张被指派 token 的短清单。

工作器按专家标识符对这些路由记录排序或入队。所有被指派给专家 037 的激活构成一条消息流；指派给 142 的构成另一条。一次专家权重加载即可服务该桶内的全部激活。多个请求可以贡献到相同的桶，运行同一层的多个注意力实例也可以在专家目的地汇合各自的路由工作。把 token 顺序转换为专家顺序，是 MoE 预填充的核心效率来源之一。NVLink 这类纵向扩展网络可以组织成内存映射连接，于是「向特定专家发送请求」可以映射为「把消息推进一个特定的内存映射位置」，该位置被配置为硬件队列。启动与停止开销极小。专家可以借助等价于 RDMA CIQ 的机制监听——同样利用硬件加速来交付消息流，无需复杂的协议启停。消息内联的简单头部标识发送方与接收方。从专家返回解码工作器的回流也可以建立类似连接。

专家输出被还原回 token 顺序，加权、合并后传入下一层。与此同时，注意力为被追加的 token 创建新的 K、V 状态。纵观整个模型，这些值构成一段不可变的 KV 后缀，用于解码下一个 token，并最终作为下一个 blob 存入上下文，供对话的下一个轮次使用。

因此预填充结合了两种权重复用：注意力和稠密变换在许多 token 间复用权重；路由专家则在各自桶内收集的 token 间复用每个被选中的专家。随着激活流量、KV 流量与输出处理相对张量计算占用越来越多时间，收益最终会趋平。批处理会推迟首 token 时间，但一个包含数千新 token 的请求本身已提供可观的算术强度；预填充并不总需要每个批次汇聚大量请求才能高效运行。现代单插槽 GPU 即便是小批次、大模型，也可能在大约一秒内完成预填充。

## 5. MoE 解码层内的流程

解码每次前向传播的新工作量要小得多。查询是当前 token，或 MTP（多 token 预测）中一小批推测 token。注意力读取先前的 KV 状态，连同新 token 的 KV 条目。新条目追加到结果中，也被追加进供下一趟使用的 KV 状态。

对智能体上下文而言，先前 KV 状态的读取负担往往比该 token 用到的注意力权重和专家权重更重。新查询及其本地投影权重则相对紧凑。注意力可以在 KV 头、上下文区间、内存通道或加速器单元之间切分，随后部分结果被归约成一个 token 激活。这个激活小到可以廉价搬运，尽管它将在下一阶段触发规模大得多的本地张量运算。

激活经过共享变换与路由。路由器从可用专家库中选出少数专家，只有这些专家的张量对当前 token 变为活跃。它们的输出被加权、合并、投影后继续向后传递。

在每一层，注意力为新 token 创建并保留该层的 K/V 条目。激活随后进入下一层的注意力，同样的序列重复上演。当最后一层产出下一个 token 时，每一层都已追加了自己的那一小块 K/V 更新。这些更新可以被组装成一段新的不可变 KV 后缀，与此同时 token 被流式传给客户端或智能体。

因此这一流程既包含宽泛的运算，也包含稀疏的运算。注意力宽范围地读取私有查询状态；专家只激活模型总容量的一小部分。硬件映射应当同时支持两者，而不是强迫整层使用同一种并行策略。

## 6. 中间填充是一种独立的运行状态

中间填充把一段很长的缓存前缀与一块新 token 组合起来，为对话或智能体工作准备下一个轮次。轨迹显示，缓存输入比增量查询大很多倍，而增量查询的新输入 token 通常在 50 到 5,000 个之间。缓存中的系统提示词、会话根、记忆、先前的智能体步骤与检索到的文档，会很快把会话与智能体上下文推高到百万上限。AgentX 数据集显示，前沿模型的专家用户在反复压缩上下文，以维持在百万 token 上限之下。

这使中间填充既不是小型预填充，也不是大型解码。像解码一样，它必须读取一份可观的私有 KV 缓存；像预填充一样，它处理的新 token 足以复用权重、并把路由激活分拣成有用的专家批次。它的算术强度可以比单 token 解码高数百倍，而其缓存状态流量又可能比同等规模的初始预填充大几十倍。

现代加速器通常能吃满数百 token 一块所带来的算术复用，因此难点常常在于大 KV 读取与路由专家流量突发之间的平衡。这种突发与解码流水线的平滑节奏并不合拍：一次中间填充占用某个阶段的时间，可能远长于相邻阶段中的解码批次，使那些阶段闲置。

理想的并行方式也可能不同。本文后文的算例会找到与解码采用不同流水线、张量与专家并行设置的中间填充配置。在一条运行中的解码流水线中途重配置 GPU，代价高昂甚至不切实际。因此，服务可能受益于一个专门的中间填充优化节点池。硬件可以与解码池完全相同，只是加载的模型阶段、并行方式与批处理策略不同。

## 7. 模型是重复层组的高栈

模型的参数量刻画了习得状态的总规模，但服务取决于这些状态如何组织与使用。模型是一个由层构成的栈，而把这些层组织成重复出现的架构单元正变得愈发有用。

在某些 MoE 模型中，一个层组就是一层。在另一些模型中，一个组包含一个全注意力层，外加若干线性、delta、top-k 或其他经优化的注意力层。通常最初 1 到 3 层可能是稠密层或经过特殊设计以获得干净的起点，其余部分则一般重复同一个组模式。

又宽又薄的可丽饼（crêpe）是层组的一种有用表示。宽阔的表面为注意力、共享变换、路由、专家容量与残差流提供了空间；浅薄的厚度则标示这个组只是高得多、不断重复的模型中的一片切片。它也呼应了加速器的物理形态：一层极薄的有源层铺在宽阔的封装之上。「可丽饼」为把宽阔的算法流程映射到宽阔的硬件表面提供了有用的直觉。

重复结构简化了功能规划。为一个组建立的映射可以复用于下一个组；对应的内存区域可以存放下一组的权重；同一套计算与通信计划可以反复执行。这种一致性不仅关乎运行时效率，也关乎编译器、kernel 与运维工具链。

解码期间，对给定 token 而言一次只有一层处于活跃。层内若干运算依次发生。相邻层可能被预取，不同的流水线阶段也可能同时处理不同的查询，但单个 token 的逻辑路径仍然按顺序逐级爬升穿过整个栈。

## 8. 并行应当切分的是模型的窄数据流

并行不是一个单一决策。流水线并行、张量并行与专家并行切分模型的不同维度，也应当用不同的通信模式来评判。

### 流水线并行沿层栈展开

层的结构天然指向流水线。层间传递的激活很紧凑——常常是一个嵌入 token、一小块多 token 预测、或先前混合组结果的简短摘要——而层内使用的权重与 KV 状态则大得多。因此一个流水线阶段可以持有一个或多个完整层组，把相对较小的激活传给下一阶段，而不需要超强网络。

流水线干净地切分模型权重，并把层内热点通信保持在本地。它的主要缺点是多批次占用：一条满负荷流水线的每个阶段里都跑着不同的查询或批次。因此每个阶段都要为所有活跃流持有自己那份 KV 状态，随着上下文增长，内存收益最终不再改善。

### 张量并行适合本质上宽阔的单个运算

注意力可能需要把权重与 KV 状态分散到多个加速器上。可以按 KV 头、上下文区间或另一线性维度切分，让每个加速器处理自己的份额，再对 token 结果做一次紧凑的归约。张量并行也可以服务于特别大的稠密变换。

不应让 TP 自动蔓延到层内的每个张量。对一个宽阔注意力运算合理的集合通信，其代价可能超过一个小专家张量的计算量本身。

### 专家并行跟随相互独立的专家张量

MoE 的大部分参数内存可能位于专家中。专家自身不保留查询历史——上下文随激活抵达。因此专家库可以广泛分布在一个对等集（peer set）上，并由多个工作器实例共享。

宽的专家并行之所以有用，是因为专家既独立又众多。路由器把紧凑的激活发送到选定的目的地，目的地再返回变换后的激活。即使流水线阶段变小，专家并行的宽度仍可保持很大，从而使交换机端口数（radix）与本地内存摆放可以独立选择。

总规则很直接：纵向的层序列用流水线并行，大型不可分割的运算用张量并行，无上下文的路由专家库用专家并行。当一个阶段的可用快速内存明显超过其本地权重、活跃批次状态与工作缓冲时，该阶段就能从容地放进一个纵向扩展域：

`M_{free,node}>\frac{W}{P}+M_{batch}+M_{working}`

现代 GPU 节点往往以数倍余量超过该阈值。此时，那些苛刻的带宽、功耗与时延需求可以留在节点之内，而较细的流水线激活与 KV 搬运则走横向扩展链路。其余的快速内存多半没有在创造收入。闲坐在内存里的数据是成本，正在搬运以待处理的数据才是收入。

## 9. 逻辑加速器节点

把逻辑节点理解为排成环状的对等集，比理解为字面的电路板布局更容易。环中大约有十六个加速器。每个加速器把一块计算区域与本地快速内存配对。各单元通过一张强大的纵向扩展网络（fabric）互连。CPU 协调负载与内存管理，NIC 则把节点连接到机柜与数据中心资源。

环只是一种可视化，把加速器画成地位平等的对等方。我并不是说节点内网络应当是环形。它可以是 hub-and-spoke、轨道式（rail）、all-to-all、torus、超立方体……只要合适就行——前提是它能以低时延、低每比特能耗承载机柜内最高的数据流。为了简洁，我就把它画成环。

这种表示避免了过早绑定封装摆放、板级走线或交换机实现。实际机器可以采用中央交换机、多台交换机、直连链路或分层 fabric。逻辑上的要求是一个有边界、具备可预测快速本地通信的对等集。

加速器设计可以各有不同。一个版本可以采用重 SRAM 的存内计算（processing-in-memory）单元；另一个可以用混合键合 DRAM，或在 BEOL 工艺中叠于顶部的 IGZO 存储单元；再一个可以用混合键合的高带宽真 3D 内存。内存容量与带宽可以变化，而这个逻辑模型依然适用。

节点是存放高频重复工作的天然场所。注意力分片之间交换紧凑的部分结果；路由专家激活前往本地目的地；专家输出返回以供重组；共享状态与调度元数据留在 CPU 近旁；NIC 则把流水线激活、KV blob 与工作指派送出节点之外。

节点可以小于机柜——例如配备 8 张 GPU 的 SGX 节点；纵向扩展系统也可以覆盖整个机柜——例如 NVL72。两种情况下这个逻辑符号都成立。如果纵向扩展已覆盖整个机柜，单独的机柜骨干层便消失，下一层边界直接就是横向扩展网络。

## 10. 节点堆叠成机柜

把环倾斜成又宽又浅的硬件可丽饼后，表达力更强。多个单元可以在机柜中垂直堆叠，就像模型层组沿模型深度堆叠一样。

这种重复形态让模型与硬件的关系一目了然。一个层组可丽饼可以放到一个硬件可丽饼上；若内存允许，多个层组可以占据一个节点；若注意力或专家容量需要，一个层组也可以横跨多个紧耦合节点。映射可以伸缩，而无需改变基本的图示语言。

机柜可以按多种方式组织：

- 一个覆盖整个机柜的纵向扩展域；
- 若干节点规模的岛，由机柜骨干互连；
- 流水线阶段分布在各岛之间；
- 每个阶段内进行宽的专家摆放；
- 或阶段本地纵向扩展与共享横向扩展链路的混合。

因此机柜骨干是一个可选的中间层。有些系统把纵向扩展 fabric 延伸到整个机柜，不需要单独的节点间连接；另一些则使用强大的本地节点 fabric，外加独立的机柜顶部（top-of-rack）或共享轨道网络。机柜之上，横向扩展网络连接存储、预填充池、解码池与其他机柜。

重复的机柜单元还有助于区分两种规模问题。模型可以装进一个有边界的机柜级工作器，而工厂则通过增加许多工作器来扩展。前者是功能摆放问题，后者是工作器编排问题。

## 11. 一个层组随时间复用节点

一个层组并不要求算法中的每个运算同时以峰值强度运行。它的运算构成一个重复序列，在解码周期内用同一批硬件做不同的工作。

注意力可能铺开到环的大半，占用许多内存通道和若干计算单元。查询与输出变换在更紧凑的运算中使用模型权重。共享前馈工作可能占用一段稠密区域。随后，被选中的专家激活环上各处的本地内存-计算区域。重组则交回一个紧凑结果。

同一批物理加速器在每一步的参与方式可以不同。计算注意力的执行单元，下一刻可能在执行一个或多个专家；刚才还在流式读取 KV 状态的内存通道，随后可以用来供给专家权重。随着 token 前进，缓冲区与本地链路都被反复复用。

这种分时复用是高效设计的核心。静态图会让机器显得利用率低下，因为并非每个模块同时活跃。现实中，硬件是在服务一串不同的运算，目标是让这串运算不停顿地流动，把启动与同步开销压到最小。

宽阔的层组可丽饼与加速器对等集互为补充：可丽饼展示算法流程，环展示其下可复用的物理资源。映射，就是把流程的每个阶段对齐到环中一个合适子集的动作。

## 12. 把吞吐边界放在流量最小的地方

一旦把模型和机器都画成相连的流，摆放规则就清晰了：频繁、对时延敏感的通信应留在最强的本地 fabric 之内，而较弱的链路应承载紧凑或可摊销的传输。

![Figure 16. The general flow of operation of an MoE pipeline stage (animated).](https://substack-post-media.s3.amazonaws.com/public/images/faccb4c8-8dad-4d10-b414-ac79c068e9bd_800x944.gif)
*图 17：MoE 流水线阶段的一般运作流程（动图）。*

注意力分片可能每层都要交换部分结果；专家路由把激活送往选中的专家并取回输出。这类流量按字节数未必最大，但频繁、突发且对同步敏感。只要可行，它就应当留在选定的纵向扩展域之内。

层与层组之间传递的激活要小得多。因此流水线边界可以跨越较弱的链路，而不必搬运该层的完整内部工作集。KV blob 更大，但它们在工作器边界处移动，并摊销在许多生成 token 之上。它们的路径可以使用条带化或 torrent 式的横向扩展网络与共享存储，而不必消耗最内层的张量 fabric。

路由器到专家的边界通常是承载数据紧凑激活的中等吞吐 all-to-all。其难点往往不在原始字节量，而在端点数量、同步与路由效率。把它限制在节点或机柜的纵向扩展域内，可以同时控制时延与运维复杂度。

这种层级结构，比每条链路都同样强的机器更容易建造、也更便宜。纵向扩展路径环抱着每层内交换嵌入与部分结果的运算；横向扩展链路则承载流水线激活、KV 搬运、调度流量以及有边界工作器之间的流量。

各层级的时延要求也不同。层组之间的流水线传输，只要吞吐充足，可能几乎察觉不到几微秒的差异；相反，当一次专家加载与乘法只需几微秒时，每个路由跳上多出的 100 ns 都举足轻重。因此最近的链路应当与加速器 fabric 紧密集成，而较低频的传输则可以容忍横向扩展网络。

## 13. 尽可能按层组做流水线

层组是流水线摆放的天然首选。在经典 MoE 模型中，组重复同一种层；在更新的结构中，一个组可能包含一个全注意力层，后接若干优化注意力或局部注意力层。

把一个组保持完整可以保留内部依赖，并让同一套摆放与编译计划在各阶段间复用。统一的计划降低工具链成本、简化部署。当每个阶段都运行相同的重复结构时，kernel、内存布局、通信时间表、监控与故障恢复都变得更容易。

在组中间切流水线仍然是可能的，只是摆放会更复杂。如果各层没有特殊的跨层依赖，紧凑的激活边界仍是一条适合网络的低流量链路。一个阶段可以包含多个完整组、一个组，或一个大组的一部分，取决于内存与吞吐需求。

指导原则不是绝对禁止拆分组，而是优先选择规整的边界，并理解何时非均匀拆分值得。工具链与运维的简洁性，可能与小小的理论摆放收益同等重要。

## 14. 流水线深度终止于 KV 缓存交叉点

流水线并行干净地切分模型权重。如果模型权重占用为（W）、使用（P）个阶段，则理想情况下每阶段的权重占用趋近（W/P）。

KV 缓存需求的行为则不同。满负荷流水线的每个阶段都跑着不同的查询或批次。在八阶段流水线中，每个阶段为八条活跃流各持有逐层 KV 值的八分之一。每阶段层数的减少被并发流的数量抵消，因此活跃 KV 需求得不到像权重那样的（1/P）缩减。

一个有用的阶段内存估计是：

`M_{stage}\approx \frac{W}{P}+M_{KV,stage}+M_{working}+M_{slack}`

一旦每阶段权重降到与 KV 及工作状态内存同一量级，更深的流水线就几乎不再带来容量收益，反而增加协调开销与时延。

交叉点高度依赖模型设计。经典全注意力方案在全部层上可能要求每 token 数百 KB 的 KV 状态；类 MLA 设计通常在数十 KB；而以线性、循环或局部注意力为主的新近混合层组还可以更低。对某些新混合架构，每 token 约 25 kB 的工作平均值可能合理；对久经考验的压缩注意力设计，每 token 约 70 kB 是一个保守参考点。

作为粗略的设计目标：取每 token 70 kB、分配给单个阶段的聚合活跃上下文为两百万 token，即约 140 GB KV 状态。双缓冲允许一个工作集在搬运时另一个继续运行，把 KV 预算抬高到约 280 GB。再加上模型权重、激活、瞬态缓冲、路由表、碎片与运行裕量，一个阶段约 400–500 GB 本地快速内存的目标，就成了对 2027 年有用的基准。

其他设计可以通过流式化、压缩、部分驻留或更多层级来降低需求。这一估计不是普适要求，而是一个务实的前沿系统在无需激进假设下就应能容纳的标准。

如果多个加速器插槽共享一张纵向扩展 fabric，阶段就可以把这份内存分散到它们之上。大型 MoE 中超过 95% 的权重内存位于路由专家中，而专家天然可以在插槽间切分。KV 状态可以按头、上下文或注意力实例划分，由此产生的集合通信匹配到同一张本地 fabric。

## 15. 预填充与中间填充把稀疏路由变成稠密专家批次

预填充与中间填充拥有很强的批处理机会，因为输入序列中的许多 token 会在专家执行开始之前先完成注意力。路由器可以为所有 token 打分、为每个 token 发出若干目的地，然后按专家对路由记录排序。

一个实际的输入块所包含的指派数量，可以让几乎每个专家都接到活。如果 128 个新 token 各选 8 个专家，路由器就在一个 256 专家的库上发出 1,024 条指派。对每个 token 而言路由仍是稀疏的；排序改变的是执行顺序，使专家 e000 处理完所有指派给它的 token，再轮到 e001，依此类推。每个专家只加载一次，并为自己那张紧凑的 token 清单复用，而不是按 token 顺序反复加载。

对一个权重为（W）的专家，设权重流量为（B_W）、每个路由 token 的激活流量为（B_A）、输出流量为（B_O）、被指派 token 数为（n），一个粗略的算术强度表达式为：

`AI_{expert}\approx \frac{2nW}{B_{W}+nB_{A}+B_{O}}`

当权重流量占主导时，增大（n）能迅速改善复用。最终，激活、输出与路由流量变得不可忽视，收益趋平。

排序并非没有代价。路由记录必须被构建、计数、置换、发往专家目的地，再还原回 token 顺序。专家容量上限可能导致溢出或重路由。即便如此，预填充与中间填充起始的 token 数量足够多，这项优化通常是有意义的。

这就是与解码的关键区别。专家是一样的，变化的只是工作器执行它们时可用的路由激活数量。

## 16. 解码从批处理中获益更少

解码注意力几乎得不到直接的跨查询复用。每增加一个查询，就多一份 KV 缓存、多一次上下文扫描。共享的查询投影权重可以复用，软件开销可以摊销，但占主导的长上下文读取仍为该查询私有。

解码专家因为权重与上下文无关而具备共享潜力，但实际限制在于共享概率。一个模型可能每层包含数百个路由专家、全模型数千个层-专家。每个查询每趟只贡献一个新 token，且只选中少数目的地。在小批次下，可用的路由 token 很少，大多数活跃专家只接到来自单个 token 的工作。共享确实会发生，但只随每趟 token 数量缓慢增长。

共享变换提供了更常规的权重复用，但它们只占 MoE 模型的一小部分。因此，扩大解码批次带来的总吞吐收益，与延迟和 KV 内存压力的增加相比可能并不划算。

当上下文长度达到 100,000 token 或更多时，批次为 1 也绝不是轻量工作负载——注意力扫描本身已占用可观的内存带宽。最优批次大小未必是 1（软件启动、分配、路由与硬件利用率仍然重要），但它可能更接近 1 或 5，而不是面向吞吐的服务所惯用的大批次。

这在经济上很重要。交互式 token 可能比大批量延迟型 token 更值钱。把延迟翻倍去换取一点吞吐提升，可能是笔糟糕的交易。软硬件应当为有用的小批次运行扫清障碍，而不是把大批次当作效率的前提。

## 17. 调度让分离式部署产生价值

分离式部署作为一套统计系统，在云规模下最为有效。一个大池可以包含为长预填充、短预填充、长上下文解码、短上下文解码或其他有用类别配置的工作器。编排器把每项作业分配给合适的空闲工作器，并通过共享存储搬运所需的 KV blob。

一旦前缀长度、新 token 数与工作器配置已知，预填充与中间填充就是可预测的。解码则是随机的，因为输出长度不确定。各池之间的存储把可预测的生产与不规则的消费解耦。一个装着已完成预填充与中间填充工作的就绪缓冲，可以在各查询完成时间参差不齐时，保证解码工作器不断粮。

调度器应当观察客户工作负载与日内模式，预判已知的爬坡，并随负载构成变化重配置工作器。重配置可能意味着加载不同的模型阶段、改变流水线基数、重新分配专家容量，或在预填充、中间填充与解码之间调配整个机柜。

规模很重要。在一个小型固定基准里，一个输入填充阶段可能直连一个解码阶段，慢的阶段会让另一阶段中的产能搁浅。而在一个大池中，工作器独立完成、独立启动，不会有工作器被搁浅。

因此，高交互性与高利用率并非天然对立。只要拥有足够多的工作器、足够的存储带宽、对工作足够强的可见性，以及足以跟上当下变化的响应速度，调度器就能在保持小批次的同时让机器忙碌。

## 18. 反馈可能把微小的不平衡变成振荡

紧耦合系统会放大寻常的波动。假设输入填充的准入直接由解码查询的完成（retirement）来门控：一个长时运行的解码查询推迟了完成，输入填充准入随之下降；解码随后排干就绪队列、陷入吃不饱的状态；准入于是激进放开，产生一波输入填充作业的突发和新一轮拥堵。

这是一个延迟反馈回路：控制信号在系统状态已经改变之后才到达。大批次恢复会加剧这个回路，因为它推高 KV 内存压力与响应延迟。工厂在「满」与「空」之间来回摆动，而不是运行在稳态点附近。

没有哪一个单一调度策略能解决这个问题。若干常见的控制技术会有所帮助：

- 在各阶段之间使用就绪工作缓冲；
- 用平滑后的积压与预测服务速率来调节准入，而不是依据单次查询完成；
- 把快速的本地控制与较慢的容量控制分开；
- 对工作器重配置施加迟滞（hysteresis）；
- 为短交互式工作预留容量；
- 以及避免以快于系统观测其影响的速度改变批次大小。

同样的原则跨越多个时间尺度。微秒级的工作器调度、毫秒级的 token 流、秒级缓冲、分钟级的工作器重配置、小时级的需求规划，不应全都响应同一个噪声信号。

## 19. 聚合式与分离式之比较

既然我们已经详尽描述了分离式推理，那么聚合式是否也有一席之地？在某种程度上，是的。显然，既然对话可以暂停几分钟甚至几小时，把整段对话绑在一个系统上并不合理。这些 HBM 在一个轮次结束后的几秒内就能派上更好的用场，而现代横向扩展网络可以在不到一秒内，把数 GB 的 KV 缓存搬进并行存储系统中更便宜的位置——该系统可以对 DRAM 与 SSD 分层。

然而，在一个轮次内部，我们真的需要调度多个地方来完成工作吗？服务器设计种类太多代价高昂，既增加运维成本也增加设计工作量。如果只有一种设计、且以中间填充场景为中心呢？请求可以被调度到那个空闲工作器上，并在那里完成预填充、中间填充与解码。这台机器需要有为预填充与中间填充准备的足够算力，以及为解码准备的足够内存带宽。取决于模型正在运行的阶段，算力或内存传输总会有一些被搁浅的产能——但我们本来就在容忍 GPU 上的低 MFU。我们试图用聪明的 kernel 去克服，但实践中集群一直在带着被搁浅的功能运行。

复杂的编排总会造成一些搁浅。如果一个轮次在单个聚合式工作器上运行，其中一部分可以避免：预填充/中间填充交接给解码时没有调度空隙；宽并行专家集天然共享一份副本；上下文从填充传到解码没有网络开销。编排器仍然会看请求的形状——缓存大小、输入序列长度、模型类型、客户交互级别——并做一次决定：由哪个空闲工作器在该轮次的全部阶段处理它。然后就撒手不管，直到停止 token 出现、轮次交付给用户并缓存进快速并行文件系统。这唯一的工作器在该轮次的所有阶段中，使用为给定请求形状适配的 kernel 与数据流。

聚合式工作器自有其魅力与拥护者。

现实使用中，所有系统都会搁浅加速器的部分能力。在分离式系统里，可以制造两种（或更多）机型，把投资聚焦于实际用到的算力、内存与网络——可以说这是投资的最佳用途。预填充机型可以重仓算力，解码机型可以重仓内存。如果工作器是聚合式的，一台机器要贯穿所有阶段，就必须同时投资最强的算力与最强的内存吞吐，也许还有强网络。如果它不是全能尖子，就会被较弱的环节拖累，整体沦为「平庸」。所以说，聚合式有优势，但也意味着在交付全面最佳性能时无处可藏。如果你能造出那颗魔法般的全能之星，那么把整个轮次聚合在一个工作器里可能就是最优解。

## 20. 内存带宽与内存容量是不同的目标

人们常把内存当作两个待最大化的独立标量来讨论。实践中，容量与带宽相互此消彼长，它们的经济价值必须放在一起考量。

数据在移动中创造收入，在闲置中产生成本。内存吞吐极高的加速器，能以低带宽内存无法匹敌的速率产出 token——即便低带宽配置容量更大。容量的价值止于活跃权重、KV 状态、激活与运行裕量干净放下的那一刻；超过这一点，额外的本地容量可能只增加成本而不增加收入。

容量曲线不是垂直悬崖。在有效上限之下，增加加速器同时带来更多内存与更多带宽。当其他限制出现时，优势便终结：纵向扩展宽度的上限、糟糕的模型切分、时延的主导地位、额外同步或网络争用。

一个安全容量的设计点必须高于上述限制，并为真实的上下文分布、双缓冲、碎片、故障与瞬态峰值留出裕量。收入-容量曲线在此之前陡峭上升，随后平滑转圆，最终到达一个主要由带宽与算力决定的较平缓天花板。如果过剩产能沦为沉没成本、运维试图用高吞吐但低价值的大而慢的批次来为其正名，收入甚至可能下降。

加速器 HBM 太贵，不能用来存放没有即时用途的闲置数据。已完成的 KV blob 应先移入 CPU DRAM 做流出暂存，再进入横向扩展存储。频繁复用的公共 blob 可以在共享 CPU 内存或近旁缓存设备中保留副本。只有活跃工作集才配得上最昂贵的内存。

高容量内存的高堆叠可能在功耗、信号质量、封装与频率上带来成本。容量恰到好处而带宽出众的设计，其交互式推理的利润率可能高于那种把每加速器容量做到最大、却带着闲置冗余的设计。

## 21. 一套实用的映射方法

前文各节可以浓缩成一套可复用的方法，用于把模型映射到机器上。

1. **区分运行状态。** 独立测量预填充、中间填充、解码注意力与解码专家。每一种还可以按上下文长度或工作负载类别进一步细分——例如智能体、编程、媒体或内容创作。它们成为编排器可以在生产中混用的预备配置。
2. **描述重复的层组。** 识别全注意力与优化注意力、共享变换、路由专家以及任何跨层依赖。
3. **测量活跃状态而非仅看总参数。** 把阶段权重、活跃专家、存活激活、KV 状态与瞬态缓冲分开。
4. **为每个运算选择天然的并行维度。** 层栈用流水线，宽阔不可分割的工作用张量并行，独立的专家广泛分布。
5. **先映射最宽阔的运算。** 长上下文注意力常常决定内存条带化与最小的有用纵向扩展参与规模。
6. **把专家权重放进规整的本地目的地。** 让路由在已知的对等位置之间选择，而不是为每个 token 制造一次全局事件。一个大模型可能包含约 15,000 个层-专家，每个都可以参照其所在层的其他专家与预期路由分布来摆放。目标是内存容量与带宽的均匀使用。
7. **让重复的高吞吐协作留在最强的 fabric 内。** 让较细的激活与可摊销的 KV 搬运跨越较弱的边界。像尊重吞吐悬崖一样尊重时延与功耗悬崖。
8. **在 KV 内存交叉点处停止加深流水线。** 一旦模型与目标上下文在安全裕量下放得下，更多阶段几乎不再带来内存收益，反而增加阶段切换时延。
9. **区别对待输入填充与解码。** 把预填充与中间填充的路由分拣成专家批次；保持解码小批次的交互性。
10. **与工作器一起设计存储与调度。** KV 搬运、准入控制、就绪缓冲与工作器重配置，决定了物理映射能否产出平稳吞吐。短批次与连续批次更新让编排器可以替换单个请求，而不必等待整个批次完成。

这套方法并不选出唯一的普适拓扑，它让取舍变得可见。一个对等集可以是一个封装、一块板，或一个机柜级纵向扩展域；一个层组可丽饼可以映射到一个或多个节点。关键在于：通信层级跟随模型的实际流程。

## 22. 下一个视角是时间

到目前为止的图描述的是结构与流程。下一步是把时间叠加到它们之上。

交互式解码的端到端预算很紧。一层的执行通常需要落在约 50 微秒到 1 毫秒之内，在典型的 60 层模型上对应约每秒 15 到 300 个生成 token。每层包含若干顺序阶段，因此单次算术运算与交接处于数十微秒、微秒、有时是亚微秒的量级。

在这个尺度上，张量运算只是结果的一部分。kernel 启动、排队、同步、内存设置、路由、归约与链路时延，都必须相对它们所支持的运算保持足够小。一次只需几分之一微秒的专家乘法，如果调度与数据搬运各花几微秒，其价值就被稀释了。

时间视角也让网络层级更锐利。一条高带宽路径如果建立时延太大，仍可能不合适。对于亚微秒级的交接，一个小的本地缓冲可能比一个遥远的大内存层更有价值。一个制造毫秒级波动的调度器，可以压垮工作器内部精心打磨的微秒级工程。

工厂横跨多个控制时间尺度：

- 本地算术与链路交接：亚微秒到微秒级；
- 层执行：约 50 微秒到 1 毫秒；
- token 生成：毫秒级；
- 就绪缓冲与准入控制：约 0.1 到 10 秒；
- 编排器的工作器重配置：数秒到数分钟；
- KV blob 在快速并行文件系统中的留存与生命周期：数分钟到数天；
- 以及客户需求规划：数小时到数天。

这些回路应当分开设计、谨慎衔接。快速控制不应去追逐缓慢的需求噪声，慢速控制也不应对每一次瞬态队列波动做出反应。

第四张图展示每 GPU 的预估峰值网络流量。预填充与中间填充为专家并行密集使用网络，因为同时有大量路由激活在途。因此流水线并行在 B200 与 B300 系统上特别有用：把一个阶段放进节点内，可以让它的专家 all-to-all 流量留在本地 NVLink fabric 上。

## 结语

推理的有效分析单元不只是总参数量，而是模型的活跃流程与机器内存、通信和时间层级的结合。

MoE 提供了结构。层组不断重复；专家众多但个体可控；注意力宽阔，且日益被 KV 状态塑形；运算顺序发生、可以复用硬件；流水线、张量与专家并行各自跟随其最自然的维度；预填充与中间填充可以把路由分拣成高效的专家批次，而解码可以保持短批次与高交互性。

硬件可以反映这种结构。逻辑加速器对等集提供有边界的纵向扩展域；节点堆叠成机柜；一个机柜可以是一个纵向扩展工作器或若干流水线阶段；共享存储让 KV blob 可移动；数据中心网络连接有边界的工作器，而不是承载每一次内部张量运算；调度让可预测与随机的阶段保持平稳流动。

以这种方式把握问题并不能消除它的规模，但让规模更容易切分。模型、工作器、机柜、存储系统与调度器，成为同一个连贯设计中可以被测量、图示与改进的部分。
