# 让私有 MCP 服务器可达，而不必将其公开

> 原文：[Making private MCP servers reachable without making them public](https://developers.openai.com/blog/connect-private-mcp-servers-to-openai-products/) · OpenAI 开发者博客

我们构建 [Secure MCP Tunnel](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels) 的原因是：团队最关心的 MCP 服务器，往往正是他们最不愿意暴露到互联网上的那些。

我们想分享我们是如何应对这一约束的：既让私有服务器保持私有，又让 ChatGPT、Codex 及其他 OpenAI 产品走上一条正常的 MCP 请求路径。

[Model Context Protocol](https://modelcontextprotocol.io/)（模型上下文协议）让 AI 系统连接外部工具与数据变得更容易。但许多最有价值的 MCP 服务器运行在企业内网、私有服务网格（service mesh）、开发者笔记本以及其他天生拒绝公网入站流量的环境中。要把这些服务器接入托管式 AI 产品，团队过去往往不得不创建公开端点、部署额外的代理基础设施，或在敏感路径上引入新的网络运营方。

Secure MCP Tunnel 提供了一种更简单的做法：客户在自己的私有环境中运行一个小型客户端，建立一条到 OpenAI 的出站 HTTPS 连接。该客户端：

1. 接收 MCP 请求
2. 将其转发给经过批准的本地服务器
3. 通过同一条连接返回响应与通知

OpenAI 产品可以使用标准的 MCP 请求与响应模型，而底层服务器仍处于客户既有网络控制之后。

要让这件事可靠且安全地运转，意味着要同时解决几个工程问题：保持服务器的私有网络边界、支持 MCP 的流式传输与身份验证流程，并给团队一个可审查、可运维的客户端。本文将逐一介绍这些决策。

隧道的设计围绕着一小组原则展开：仅出站（outbound-only）连接、明确的目标配置、与 MCP 流式传输和通知的兼容性，以及一个团队可以自行审查与运维的客户侧客户端。

这些原则合在一起，让私有工具与数据能够轻松接入 OpenAI 产品，而不必把私有 MCP 服务器变成公共服务。

## 错误的默认做法

如今，团队让一项私有服务变得可达，通常有三种方式：暴露公开端点、运行第三方隧道，或通过 VPN 或对等连接（peering）扩展网络。

- 公开端点通过削弱边界来让访问变容易。
- 第三方隧道服务商可以让私有服务器快速可达，但它也在连接路径上增添了另一个需要审查、签约、运维并给予信任的供应商。对企业团队而言，这不是一个小细节：隧道提供商会成为一个系统的安全审查、采购流程、运维手册（runbook）与元数据暴露面的一部分——而这个系统的目的恰恰是让私有工具保持私有。
- VPN 与网络对等连接通过创建广泛的网络连通性来解决可达性问题，但对于一个狭窄的 MCP 集成来说，这往往是过于庞大的机制。

Secure MCP Tunnel 采取了一种更聚焦的做法。它不要求客户迁移 MCP 服务器、扩展网络边界，或引入另一家连接供应商，而是在私有服务器旁边放置一个小型、可审查的开源客户端，并让该客户端发起并控制到 OpenAI 的连接。

Secure MCP Tunnel 把可达性逻辑彻底反转：由私有一侧迈出第一步。OpenAI 产品把 MCP 请求发送到一个由 OpenAI 托管的隧道端点。隧道服务将工作排入特定隧道的队列，而已经在私有 MCP 服务器旁运行的客户侧客户端通过出站 HTTPS 取走这些工作。客户端在本地转发请求，并通过同一路径返回响应。

这样一来，OpenAI 产品获得了一条正常的 MCP 请求路径，而无需私有服务器接受公网入站流量，也无需创建更广泛的网络连通性。

## 为什么从长轮询（long-poll）起步？

我们刻意选择了一种运维上平淡无奇的传输方式起步。出站 HTTPS 对企业防火墙、代理环境与平台团队来说早已司空见惯。长轮询让隧道客户端只请求它所能处理的工作量，这为客户端侧队列提供了天然的背压（backpressure）点，而不是鼓励无界缓冲。

这一选择也让交付形态易于推理：

1. 产品向 OpenAI 托管的端点发送 MCP JSON-RPC。
2. 隧道服务保持或流式传输该请求，直到客户侧客户端返回最终响应
3. 当请求流式结果时，隧道可以转发中间的服务器发送事件（server-sent events）。

最终结果是：产品获得正常的 MCP 请求/响应路径，而 MCP 服务器及其地址保持私有。请求、响应与中间事件都通过 OpenAI 托管的隧道端点中继。

## 让安全边界保持明确

隧道不是用来抹除网络边界的，而是用来让边界变得明确。客户侧隧道客户端向隧道控制平面进行身份验证，产品侧使用 OpenAI 托管的隧道端点，而私有 MCP 地址只在客户环境内部使用。隧道访问与客户既有的 OpenAI 组织与工作区上下文以及已配置的隧道身份绑定，而不是成为一条拥有自己访问模型的独立网络路径。

这一设计依赖的不只是选对网络方向。由于隧道客户端运行在客户环境内部，其行为必须可审查且刻意保持狭窄：客户应当能够理解正在运行什么代码、它打开了什么出站路径、它被允许访问哪些私有服务。

## 让 MCP 开发感觉如同本地开发

我们希望隧道客户端感觉起来像一个开发者工具，而不是一个网络工程。开发者应当能够在笔记本上运行一个 MCP 服务器，在旁边启动隧道客户端，然后把该服务器连接到 ChatGPT 或 Codex——无需创建公开端点，也无需等待 VPN、防火墙规则或对等连接的变更。

当服务器从笔记本迁移到 Kubernetes、虚拟机或其他客户可控环境时，同样的流程应当延续下去。重要的是心智模型保持不变：把客户端运行在私有 MCP 服务器附近，验证客户端能够访问它，然后让客户端发起面向 OpenAI 的路径。健康检查、就绪探针（readiness）、日志与本地管理 UI 的存在，是为了在出现问题时让这一循环可审查，而不是要把隧道变成一个运维项目。

开发者体验也内置于 Codex 本身。隧道客户端包含一个 [Codex 插件](https://github.com/openai/tunnel-client/tree/master/plugins/tunnel-mcp)，把配置过程变成一个引导式工作流，而不要求开发者预先学会 tunnel-client 的每一个旗标（flag）、配置档（profile）与控制平面细节。目标不是制造一个一次性的本地捷径：插件产出的配置形态，应当与服务器从笔记本迁移到 Kubernetes、虚拟机或其他生产环境时团队可以沿用的形态完全一致。

同样的理念也体现在随 tunnel-client 打包的助手工作流中：由于助手可以读取 tunnel-client 暴露的本地隧道上下文，它能够帮助开发者从实际配置出发进行推理，而不是依赖通用说明——当前激活的是哪个配置档、生成了什么配置、本地 MCP 服务器是否可达、隧道客户端处于启动路径的哪一步。这让故障排查成为开发者循环的一部分，而不是一条单独的升级（escalation）路径。

## 为什么开源隧道客户端很重要

隧道客户端是开源的、由客户运行的软件，位于客户边界之内、私有 MCP 服务器旁边。这让客户与安全审查人员能够审查运行在自己环境中的代码。客户与安全审查人员可以检查客户端做什么、它打开什么出站连接、它如何在本地转发 MCP 请求，以及什么配置控制着它的可达范围。

这种透明性让信任模型与架构保持一致：OpenAI 托管隧道服务，但运行在客户环境内部的代码体量小、可审查，并处于客户的控制之下。

## 无需广泛网络访问的企业级身份验证

私有 MCP 服务器很少只是匿名的内部 HTTP 端点。它们可能依赖 OAuth、私有证书颁发机构、出站代理，或 MCP 一跳上的客户端证书。支持这些服务器，意味着把企业网络假设作为隧道设计的一部分来对待，而不是当作客户必须自行绕开的例外。

关键约束是 MCP 服务器仍然保持私有。MCP 服务器的 OAuth 发现流程经由隧道路径进行，因此托管产品可以了解如何进行身份验证，而无需 MCP 服务器监听公网。在客户一侧，隧道客户端可以针对本地环境进行配置：自定义 CA 证书包、代理设置，以及 MCP 侧的 mTLS。

我们也让边界保持明确。隧道不会自动让每一个相关的企业端点都能从 OpenAI 侧访问。如果授权服务器是私有的，它仍然必须能够被执行 OAuth 流程的组件访问到。这一边界是有意为之：Secure MCP Tunnel 提供的是通往已配置私有工具的一条狭窄路径，而不是一座通用的网络桥。

## 超越 MCP

MCP 是模型工具的主要形态，但早期的客户 alpha 测试表明，还存在一个密切相关的问题：并非每个客户私有工作流都已经被封装为 MCP 服务器。一些重要的工作流是同一防火墙边界之后的既有 REST API。如果 Secure MCP Tunnel 只解决 MCP 可达性，团队仍然需要为那些相邻的私有 API 单独创建公开端点、隧道供应商、VPN 路径或对等连接项目。

Harpoon 把同样的窄连接模型扩展到经过批准的 REST 目标。客户无需暴露任意 URL，而是在隧道客户端上注册带标签的目标。OpenAI 侧的调用者通过 Secure MCP Tunnel 调用这些标签，而实际的 HTTP 请求仍然发源于客户环境内部、紧邻私有服务。

关键约束在于标签不是一座通用的网络桥。调用始终受限于客户自主的目标注册、允许的方法、响应大小限制、超时、重定向行为与隧道访问控制。这为经过批准的 OpenAI 工作流提供了一条通往客户私有 API 的受控路径，既不要求客户开放入站网络访问，也不赋予 OpenAI 类似 VPN 的身份。
