# 构建 ChatGPT Apps 的 15 条经验

> 原文：[15 lessons learned building ChatGPT Apps](https://developers.openai.com/blog/15-lessons-building-chatgpt-apps/) · OpenAI 开发者博客

在 [Alpic](https://alpic.ai)，我们相信下一代产品与服务将围绕 **AI 优先的体验**构建：用户与模型协作，而不是在传统、预先设定的 UI 工作流中导航的界面。

当 OpenAI 发布 **Apps SDK** 时，我们立刻开始用它构建。在三个月里，我们开发了二十多个 ChatGPT Apps，既供内部使用，也服务于我们在**旅游、零售与 SaaS** 等 B2B 和 B2C 领域的客户。

我们很早就发现：**构建 ChatGPT Apps 与构建传统 Web 或移动应用有着根本的不同**。在 Web 上运行良好的模式（即时数据获取、UI 驱动的状态、显式的用户配置等）在智能体环境中常常失效，甚至直接损害体验。

本文提炼了我们在构建真实 ChatGPT Apps 过程中总结的 **15 条最重要的经验**，随后介绍我们如何把这些经验融入面向社区的开源框架 [**Skybridge**](https://github.com/alpic-ai/skybridge)，以及一个帮助开发者大幅加快构思、构建、测试与上线 Apps 速度的 [**Codex Skill**](https://github.com/alpic-ai/skybridge/tree/main/skills/chatgpt-app-builder)。

## 三体问题

在传统 Web 应用中，事情很简单：你只有**用户**和 **UI** 两方。而在 ChatGPT 应用中，第三个「天体」进入了系统：**模型**。

为 ChatGPT 构建应用最困难的部分之一，是管理信息如何在这三者之间流动。如果用户点击了你小组件（widget）中的「选择」按钮，UI 在视觉上更新了，但作为对话大脑的模型并不知情，除非你显式地把这份上下文呈现给它。如果用户接着问：*「给我更多关于这个产品的细节」*，模型根本不知道用户正在看的是什么。

我们把这种情况称为**上下文不对称（context asymmetry）**：每一方都只掌握系统的部分知识，没有任何一方拥有全貌。构建优秀的 ChatGPT Apps 不是要把一切都保持同步，而是要决定*哪些*信息应该共享、*何时*共享，以及*谁*需要看见它。能否解决这个问题，决定了一个应用是笨拙还是拥有流畅的智能体体验。

### 1. 并非所有上下文都该共享

我们最初的直觉是「把所有东西共享到所有地方」。结果证明这是我们最早犯的错误之一。

在实践中，ChatGPT App 的不同部分常常需要*刻意不同*的同一状态视图。为什么？

- **出于性能：** UI 小组件需要的数据往往远多于模型需要的：例如，在一个旅游预订应用中，可能是图片、价格变体、预加载的选项。把所有这些发给模型会增加 token 用量、延迟和认知噪音。
- **出于逻辑：** 某些信息按设计必须保持不对称。在我们最早的应用之一——一款名为 *Murder in the Valleys* 的悬疑推理游戏中，模型需要知道凶手是谁才能正确进行角色扮演，而 UI 和用户则绝不能知道。在一款 *Time's Up* 风格的游戏里，情况正好相反：UI 把秘密词展示给用户，而模型必须保持不知情。

经验教训不是「永远同步一切」，而是：**显式决定谁需要知道什么**。我们用不同的*工具输出*字段把它形式化：

| 字段 | 用途 | 谁可见 |
|---|---|---|
| structuredContent | 面向小组件与模型的类型化数据 | 小组件与模型皆可见（通过 toolOutput 与 callTool 函数） |
| _meta | 响应元数据 | 仅小组件可见，对模型隐藏 |

例如，在 Time's Up 游戏中，我们把秘密词只通过 `_meta` 字段传给小组件，让模型根据用户的提示去猜这个词。

### 2. 懒加载在 AI 应用中行不通

出身 Web 开发的我们默认采用懒加载（lazy-loading）：用户点击时才取数据；按需加载详情；把首屏负载优化到最小。

在 ChatGPT 中，范式反转了：工具调用意味着延迟，由于安全沙箱与模型推理，往往要花上好几秒。

在实践中，我们学会了激进地前置加载：把尽可能多的数据塞进初始工具响应里，并通过 *window.openai.toolOutput* 来为小组件注水（hydrate）。这几乎总是带来更快、更跟手的体验。

当然，如果小组件能够安全地从公开 API 端点获取数据，且不需要与模型共享信息，那么在小组件内部使用经典的 XHR 调用始终是可行的；但大多数时候，你会希望模型能够自主调用工具，以保持对话式的体验。

### 3. 模型需要可见性

一个微妙但关键的问题是：当用户与小组件交互（例如在列表中选中某个特定产品），然后在聊天中提问时，如果模型不知道用户指的是 UI 的哪个部分，它就无法正确回答。

为此我们使用了 `window.openai.setWidgetState(state)`，它允许你存储特定的状态数据，这些数据会在下一次用户与模型交互时加入模型的上下文。

随着应用越来越复杂，我们发现自己为了帮模型追踪导航而在很多地方添加 `setWidgetState`。于是我们决定引入一种声明式的方式来描述 UI 上下文：不再在每次交互时以命令式的方式更新模型，而是把 `data-llm` 属性直接附加到组件上：

```
<div
  data-llm={
    selectedTab === "details"
      ? "User is viewing product details"
      : "User is viewing reviews"
  }
>
```

为了让这一切在幕后运作，我们构建了一个 Vite 插件，它会抓取这些属性并自动更新 widgetState。从模型的角度看，它只是在恰当的时机收到了相关的 UI 上下文，而开发者无需手动同步每一次交互。

你可以在我们为与社区分享经验而创建的[开源框架](https://github.com/alpic-ai/skybridge)中找到这个 Vite 插件（以及本文分享的许多其他技巧）。

### 4. 不同的交互需要不同的 API

ChatGPT Apps 涉及小组件、服务器与模型之间的多条交互路径。这些路径不可互换：每一条都为支持某一种交互而生。

构建 ChatGPT Apps 的关键经验之一，是把这些通信路径明确化，并有意识地决定哪种机制负责体验的哪个部分。

## 为 AI 重新发明 UI

ChatGPT Apps 是一个全新的环境，所以我们很快学会了搁置关于 UI 的固有成见，充分利用新能力。本节介绍我们为了构建有效的应用而需要学习（以及需要摒弃）的界面设计假设。

### 5. UI 必须适应多种显示模式及其约束

ChatGPT Apps 并不生活在单一布局里。根据调用方式与时机的不同，同一个小组件可以用三种不同的显示模式渲染。

应用可以以**内联（inline）**方式出现在对话中，以**画中画（picture-in-picture，PiP）**方式悬浮其上，或在需要更多空间时进入**全屏（fullscreen）**。PiP 与全屏能支持更丰富的界面，但也带来了小组件无法控制的 UI 覆盖层。考虑设备特定的安全区域（例如移动端上持续存在的关闭按钮）至关重要，这样才能避免内容被裁切并优化交互。

随着时间推移，我们总结出围绕显示模式及其适用时机的模式：

|  | 外观 | 何时使用 |
|---|---|---|
| **内联（Inline）** | 默认显示模式。小组件留在对话历史中。 | 用于快速交互 |
| **全屏（Fullscreen）** | 小组件占据整个屏幕，聊天栏位于底部。 | 当你的小组件复杂且需要大量空间时（例如地图） |
| **画中画（Picture-in-Picture）** | 与内联尺寸相同，但小组件悬浮在对话之上 | 当你的小组件在生成之后的对话追问期间仍然相关时 |

### 6. 在嵌入式环境中 UI 一致性很重要

早期我们遇到的一个不确定性是：ChatGPT App 应当在视觉上拥有多大的自由度。作为一种面向用户的新界面，它需要让人感到熟悉且一致——无论在我们自己的应用内部，还是在整个 ChatGPT 生态中。与独立产品不同，小组件生活在一个既有界面之中，任何视觉上的不一致都会立刻显眼。

幸运的是，[OpenAI Apps SDK UI Kit](https://github.com/openai/apps-sdk-ui) 给了我们清晰的基准。

它构建在 Tailwind CSS 之上，提供与 ChatGPT 设计系统对齐的开箱即用组件、图标与设计令牌（design tokens）。使用它让我们既能快速推进，又能确保小组件感觉原生、与周围界面视觉一致，即使是在构建自定义组件时（例如我们的 Mapbox 集成）也是如此。

### 7. 语言优先的筛选

传统仪表盘建立在塞满复选框与范围滑块的侧边栏之上。在智能体 UI 中，这往往是一种倒退。当用户可以直接用自然语言表达意图时——例如「200 美元以内阳光充足的欧洲目的地」——强迫他们穿过多个 UI 控件只会增加摩擦。他们应该能够直接说出来。

因此我们决定在大多数应用中走「无筛选器」路线。我们不再提供带筛选与排序选项的侧边栏，而是为工具参数向模型提供一份**值列表（List of Values，LOV）**。

这让模型可以直接把用户的消息作为输入，避免它去「猜测」有哪些可用选项。换句话说，它让模型能够把自然语言直接映射为我们后端的 API 要求。如果用户说「阳光充足」，模型就知道要以 weather="sunny" 调用工具。

### 8. 文件可以解锁更丰富的交互

在构建更复杂的应用时我们得到的一条经验是：文件不应被视为次要输入。在 ChatGPT Apps 中，文件可以解锁新的交互。体验可以不从表单或筛选器出发，而是从用户已有的东西出发。

例如，在一个电商应用中，用户可以在聊天中上传一张产品照片，让模型识别它，然后直接在小组件中继续进行产品匹配或发现。

之所以能实现这一点，是因为让文件在系统两侧流动。在模型一侧，工具可以通过 `openai/fileParams` 直接消费聊天中上传的文件，让模型能够对图像或其他用户提供的素材进行推理。在 UI 一侧，小组件也可以使用 `window.openai.uploadFile` 与 `window.openai.getFileDownloadUrl` 直接处理文件，从而可以把上传请求作为 UI 流程的一部分，或生成用户可下载并复用的文件。

## 走向生产环境

接下来，当应用走出本地开发，围绕安全、配置与工具的另一组考量就会登场。这就是第三组经验要讲的内容。

### 9. CSP 是新的 CORS

出于安全考虑，OpenAI 在双层嵌套的 iframe 中渲染 Apps。内容安全策略（Content Security Policy，CSP）是 iframe 隔离的原生机制，这套设置会严格执行 CSP，问题常常表现为经典的「本地能跑、上线就挂」综合征。

与传统 Web 开发中策略宽松一点也能蒙混过关不同，Apps SDK 要求你精准施策。

在应用清单（manifest）中，这意味着要仔细声明每种交互类型允许哪些域名：

| 字段 | 用途 | 示例 | 常见错误 |
|---|---|---|---|
| **connectDomains** | API 与 XHR 请求 | [https://api.weather.com](https://api.weather.com) | 忘记预发（staging）API 与生产环境的区别。 |
| **resourceDomains** | 图片、字体、脚本 | [https://cdn.jsdelivr.net](https://cdn.jsdelivr.net) | 使用 delivr.net 这类通用 CDN 却没有将其列入白名单 |
| **frameDomains** | 嵌入 iframe | [https://www.youtube.com](https://www.youtube.com) | 嵌入 YouTube 视频或 Mapbox 实例却没有将其列入白名单。 |
| **redirectDomains** | 无警告打开的外部链接 | [https://app.alpic.ai](https://app.alpic.ai) | 忘记结账或 OAuth 回调域名。 |

早期就把 CSP 配置当作一等公民来对待，为我们省去了后来大量的生产环境调试。

### 10. 小组件的细小开关有着超比例的影响

除了 CSP 之外，还有一小组件级设置决定着控制权如何在小组件、模型与宿主环境之间分配。这些开关很容易被忽视，但它们为导航、工具访问与发布定义了关键边界。

#### 宿主与导航边界

- **`widgetDomain`** 是提交时的必填项。它定义了全屏模式下「在 \<App\> 中打开」按钮默认指向的位置，并参与来源（origin）白名单——因为小组件渲染在 `<widgetDomain>.web-sandbox.oaiusercontent.com` 之下。我们使用 `setOpenInAppUrl` 根据上下文把用户路由到合适的路径。

#### 模型与工具边界

- **工具注解（tool annotations）** 必须遵循发布指南。像 `readOnly`、`destructiveHint`、`openWorldHint` 这样的标记是必填的，并会在提交时被校验。
- **工具可见性**很重要：不应被模型调用的工具必须显式标记为私有（private）。

#### 小组件执行边界

- **`widgetAccessible`** 控制小组件能否自行使用 `callTool` 调用工具。

单独看这些设置都很小，但合在一起，它们决定了一个应用发布之后能否正确运转。

## 为快速迭代优化

Apps SDK 正在快速演进，我们也很高兴能伴随它一起构建。为了支持顺畅高效的开发工作流，我们决定开发自己的开源框架并与社区分享。以下是一些经验，帮助你避开我们在起步阶段遇到的那些开发者体验问题。

### 11. 快速迭代需要热重载

我们最早解决的问题之一就是迭代速度。长 TTL 的资源缓存与使用 JSON-RPC 转发资源的做法叠加在一起，使得标准的热模块重载（hot module reload，如 Vite 或 Next.js 中所见）开箱即用时无法兼容 ChatGPT Apps。

在花了相当多时间理解 Vite 内部机制之后，我们构建了一个 Vite 插件，能在 ChatGPT 内部直接实时重载小组件。这个插件拦截发往 MCP 服务器的资源请求，并把实时更新注入 ChatGPT 的 iframe。在 IDE 里做的修改立刻反映到 ChatGPT 中，这大大缩短了我们的反馈回路。

### 12. 并非每个测试都该在 ChatGPT 里做

在 ChatGPT 上测试是黄金标准，但对于最初的几轮迭代，一个本地模拟器（emulator）能帮你更快推进，尤其是当你在编写需要开发者模式（Developer Mode）下重载应用才能生效的工具定义时。

为了加速早期迭代，我们构建了一个轻量的本地模拟器，它 mock 了 ChatGPT 宿主环境，并配有调试工具和应用专属日志。这让我们能在毫秒级迭代 React 状态与布局，把真正的 ChatGPT 测试留给验证模型交互和边界情况。

### 13. 移动端测试需要显式支持

移动端测试带来了另一个挑战：虽然要把本地服务器通过隧道（tunnel）暴露出去才能在 ChatGPT 中测试，但 Vite 默认使用 localhost，导致同一个 URL 无法从其他设备访问。

我们通过扩展 Vite 插件、支持在隧道端口上进行域名转发解决了这个问题，这让 iOS 与 Android 设备上的测试畅通无阻，也让移动端验证成为我们日常工作流的一部分。

### 14. 熟悉的抽象（如 React hooks）能加速前端工作

Apps SDK 暴露了强大的能力，但主要是通过底层的 JavaScript API。作为多年的 React 用户，我们希望贴近那些早已掌握的概念。

于是我们引入了一些对 React 友好的抽象——`useCallTool`、`useWidgetState`、`useLocale` 等 hooks，以及建立在 Zustand 之上、面向复杂数据流的 `createStore` 这类更高级的状态管理。重新引入熟悉的前端模式减少了样板代码，让小组件开发感觉更接近现代 Web 工作流。

## 把经验变成一个 Codex Skill

### 15. 把经验变成可复用的工具

当这些模式在多个应用中反复浮现时，我们清楚地意识到：一再重新发现它们正在拖慢我们的速度。为了让 ChatGPT App 开发更快、更可预期，我们决定把这些经验直接编码进我们的工具中——不仅是为自己，也是为社区。

这带来了两项互补的工作：

1. **[Skybridge 框架](https://github.com/alpic-ai/skybridge)：** 一个开源的 React 框架，把本文描述的许多模式打包成可复用的构件，包括我们的 hooks（`useCallTool`、`useToolInfo`）、开发工具（HMR 与本地模拟器），以及 data-llm 属性。
2. **chatgpt-apps-builder [Codex Skill](https://github.com/alpic-ai/skybridge/tree/main/skills/chatgpt-app-builder)：** 在框架之上，我们构建了一个专门的 Codex Skill 来支持应用的完整生命周期：

   **构思（Ideation）：** 头脑风暴如何让应用真正「智能体化」，而不是仅仅把 Web 应用移植过来。
   **代码生成：** 同时编写 React 前端与 MCP 服务器后端，并预置所有恰当的 UX 与 UI 模式。
   **本地测试：** 启动开发服务器并把本地应用连接到 ChatGPT，通过热重载实时迭代。
   **QA 与发布：** 依照 OpenAI 的提交指南运行结构化检查，包括 CSP 校验、安全区域考量与生产环境测试。
   **应用部署：** 协助完成应用上线与迭代所需的最后步骤。

要安装并使用这个 Skill，只需使用以下命令：

```
npx skills add alpic-ai/skybridge
```

## 结语

构建 ChatGPT Apps 需要重新思考上下文如何流动、界面如何表现，以及用户与模型如何协作。本文的许多经验都来自熟悉的 Web 模式与智能体系统现实之间的落差。

通过分享这些经验，并把它们编码进我们的开源框架与 Codex skill，我们希望帮助团队少花时间重新发现同样的问题，多花时间探索这种新交互模式所能带来的可能。最有吸引力的 ChatGPT Apps 不会是现有产品的简单移植，而是围绕这种全新 AI 优先体验刻意设计的体验。
