# 什么样的 ChatGPT 应用才是好应用

> 原文：[What makes a great ChatGPT app](https://developers.openai.com/blog/what-makes-a-great-chatgpt-app/) · OpenAI 开发者博客

在 DevDay 上，我们推出了 [ChatGPT Apps](https://openai.com/index/introducing-apps-in-chatgpt/)——一种把你的产品直接带入 ChatGPT 对话的新方式。本文在这场发布的基础上，为开发者、PM 与设计师提供实用指导：如何选择合适的使用场景，并设计出一个上线后真正有用的应用。我们会聚焦于如何把产品的优势转化为清晰、范围明确的能力（capability），让模型能够在各种不同的对话与用户意图中加以运用。如果你想了解技术细节，可以直接跳到 [Apps SDK 快速开始](https://developers.openai.com/apps-sdk/quickstart)与[开发者文档](https://developers.openai.com/apps-sdk)。

本文将覆盖：

- ChatGPT 应用真正是什么（以及不是什么）
- 应用能够真正创造价值的三种方式
- 如何面向对话与发现进行设计
- 如何判断你的应用是否真的在起作用
- 具体示例与截图建议

## ChatGPT 应用究竟是什么

当团队构建他们的第一个 ChatGPT 应用时，出发点往往是：

*“我们已经有了一个产品。把它带进 ChatGPT 吧。”*

这往往始于把一个既有的 Web 或移动端体验——屏幕、菜单、流程——拿过来，尝试为聊天重塑它。这是一个合理的直觉；多年来，「软件」就意味着页面、导航与 UI 脚手架。

然而，为 ChatGPT 构建应用是一个不同的环境。用户并不是「打开」你的应用然后从主页开始。他们正在就某件事展开对话，而模型可以决定何时把一个应用带入这场对话。他们在某个时间点进入。在这样的世界里，最好的应用从外面看起来小得出奇。它们不试图复刻整个产品，而是让用户在 ChatGPT 中使用该应用时获得少数几种**特定的能力**：你的产品最擅长的、模型可以在任何对话中复用的具体本领。

在 ChatGPT 之外，你的应用往往就是目的地。用户：

1. 点击你的图标
2. 进入你的环境
3. 学习你的导航与 UI 模式

大多数产品决策都源自那个假设：「我们拥有这块屏幕。」你可以在布局、新手引导（onboarding）与信息架构上重金投入，因为用户正在承诺进入你的空间。

在 ChatGPT 之内，你的应用扮演的是另一种角色：

- 它是模型可以调用的**一种能力**——既提供上下文，也提供视觉上的参与感。
- 它出现在一段进行中的对话**内部**。
- 它是模型可能编排的若干工具之一。

这意味着「价值单元」更多不在于你的整体体验，而在于你能在恰当的时刻帮助模型与用户完成的具体事情。

一个实用的定义：

**ChatGPT 应用是一组定义良好的工具，能够执行任务、触发交互或访问数据。**

这有几层含义：

- 你不需要移植每一个功能。
- 你不需要完整的导航层级。
- 但你*确实*需要一套清晰、紧凑的 API：少数几个易于调用、易于在其上继续构建的操作。

你可以这样想：你的 ChatGPT 应用是一个工具箱，当用户遇到特定类型的问题时，模型会伸手去取它。这个工具箱定义得越精确，在对话流程中就越好用。

一旦你把应用看作「模型可以编排的能力」，而不是「我们产品的迷你版」，设计决策就会变得更清晰。你开始问「我们能在这里帮上什么忙？」而不是「用户下一步应该去哪里？」

## 创造真实价值的三种方式

对任何应用创意的一个简单过滤器：

- **知（Know）：** 它是否让用户能够使用在 ChatGPT 中原本看不到的新上下文或数据？
- **做（Do）：** 应用是否代表用户采取真实的行动？
- **展示（Show）：** 应用是否以比纯文本更清晰、更可操作的 UI 呈现信息？

这既适用于**「严肃的」**生产力应用，也适用于游戏这类**「纯粹图个乐」**的应用。游戏或许帮不了谁更快交付一份报告，但它仍然做到了基座模型自己无法做好的事情：维护有状态的游戏逻辑、跟踪进度、执行规则，或渲染游戏世界的有趣视图。其价值在于愉悦与投入，但底层模式是一样的。

### 1) 可知的新事物

你的应用在 ChatGPT 对话中提供新的上下文：

- 实时价格、可用性、库存
- 内部指标、日志、分析数据
- 专业的、需要订阅才能访问的或小众的数据集
- 用户专属数据（账户、历史、偏好、权益）
- 传感器数据、实时视频流

在实践中，这通常意味着桥接到那些数据正确、实时且经过权限管理的系统。应用成为模型在你的领域中的「眼睛和耳朵」，能够以更高的权威性回答问题。

### 2) 可*做*的新事情

你的应用代表用户采取行动：

- 在内部工具中创建或更新记录
- 发送消息、工单、审批、通知
- 安排日程、预订、下单或配置
- 触发工作流（部署、升级上报、同步数据）
- 玩交互式游戏（应用规则、推进回合、跟踪状态）
- 在物理世界中采取行动（IoT、机器人控制等）

在这里，应用与其说是事实来源，不如说是一双手。它接过用户的意图，把它变成你的团队日常所处的系统中的具体变化——或者，在游戏中，变成游戏状态的具体变化，让体验保持一致与公平。这正是你的应用以有意义的方式转变为智能体的地方。

### 3) 更好的展示方式

应用可以在 ChatGPT 对话中以 GUI 呈现信息，让信息更易消化、更可操作：

- 精选清单、对比、排名
- 表格、时间线、图表
- 面向特定角色或特定决策的摘要
- 游戏状态的视觉化或结构化视图（棋盘、物品栏、分数）

当用户正在做出选择或权衡时，这一点尤其有价值。应用可以给模型一种结构化的语言：具有列、行、分数与视觉呈现的小组件（widget），与人们实际的决策方式相匹配——或者，在游戏中，与他们理解自己「身在何处」的方式相匹配。

如果一个应用没有在**知/做/展示**中至少一项上明显带来改变，它往往会让人感觉没有提供超出用户在 ChatGPT 中已有能力的价值。用户可能不会明确抱怨，但无论这个应用是面向工作还是娱乐，这都是一个错失的为用户提供更有意义价值的机会。

## 精选能力，而不是移植整个产品

一个常见的第一反应是列出产品的全部功能，然后问：「我们怎么把这些带进 ChatGPT？」

纸面上听起来很全面。实践中，这通常会产生一个大而模糊的功能面，模型难以驾驭，用户也难以理解。如果你很难用一句话概括这个应用做什么，模型理解起来也会更费劲。

一条更有效的路径：

1. **列出核心待完成任务（jobs-to-be-done）**——找出用户试图完成、而你的产品帮助其实现的具体任务或结果。这些是你的产品一开始就存在的理由。从这里出发，能让你锚定在用户结果上，而不是功能清单上。

   示例：

   - 帮某人挑选一套住房。
   - 把创意变成精美的演示文稿。
   - 把意图转化为愉悦的发现体验。
   - 把原始数据变成清晰、可分享的报告。

2. 对每一项任务，问：「如果没有应用，用户在 ChatGPT 对话中做不了什么？」

   常见答案：

   - 访问实时或私有数据。
   - 在我们的系统中采取真实行动。
   - 获得用户所需的结构化或可视化输出。

3. 你的独特价值开始在这里显现。你不再想「我们在技术上能暴露什么？」，而是「我们在哪里独一无二地有帮助？」

4. 把这些缺口转化为少数几个**命名清晰的操作**。例如：

   - `search_properties`——返回候选房源的结构化列表。
   - `explain_metric_change`——获取相关数据并总结可能的驱动因素。
   - `generate_campaign_variants`——创建多个带元数据的广告变体。
   - `create_support_ticket`——开一个工单并返回摘要 + 链接。

这些操作：

- 具体到足以让模型自信地选择
- 简单到足以与对话中的其他步骤自由组合
- 直接与价值挂钩，而不是与你的整个产品版图挂钩

换一种思考方式：如果你的团队中有人问「我们绝对需要这个应用做好的三件事是什么？」，那三件事应该几乎一一对应到你的产品能力。

例如，ChatGPT 中的 Canva 应用可以生成整份演示文稿草稿，用户也可以进入符合幻灯片浏览预期的全屏模式，但更深入的逐页编辑仍然发生在完整的 Canva 编辑器中。

## 面向对话与发现进行设计

在你的 MCP 服务器中，你可以定义 [`description`](https://developers.openai.com/apps-sdk/reference#component-resource-_meta-fields)，为模型提供上下文，说明何时调用你的工具、以及具体调用哪些工具来完成特定任务。这有助于把用户意图映射到你的工具动作上。

### a) 模糊的意图

> 帮我弄清楚该住在哪里。

一个好的应用响应会：

- 利用会话中已有的任何相关上下文。
- 如有需要，最多提出一两个澄清性问题。
- 快速产出具体的东西——例如，给出几个示例城市并附简短说明。

用户应该感觉进展已经开始，而不是被丢进一个多步骤的新手引导流程。如果他们必须在看到任何有用内容之前回答五个问题，很多人会直接放弃。

### b) 具体的意图

> 在西雅图找 120 万美元以下、口碑良好的小学附近的三居室住宅。

在这种情况下，应用不应该让用户重复自己。它应该：

- 解析查询。
- 调用正确的能力。
- 返回一组聚焦的、具有有用结构的结果。

你仍然可以提供细化选项（「你更在意通勤还是学校评分？」），但它们应该感觉像可选的微调，而不是必需的设置。

### c) 没有品牌认知

你不能假设用户知道你是谁。

你的第一个有意义的响应应该：

- 用一行话解释你的应用的角色（「我拉取实时房源列表和学校评分，方便你比较选项。」）
- 立即交付有用的输出。
- 提供一个明确的下一步（「让我按通勤、社区或预算进一步缩小范围。」）

把它当作一个冷启动问题：你要在一两条消息之内介绍*你是什么*、*你为什么有用*以及*该怎么用你*。

## 为模型与用户同时设计

你在为两类受众设计：

- 聊天中的人
- 决定何时以及如何调用你的应用的模型运行时

大多数团队对第一类思考起来得心应手。第二类更新一些。但如果模型无法理解你的应用做什么、怎么用，你面向人的体验就不会有多少登场机会。

还有一个同样重要的第三维度：**当模型调用你的应用时，有什么样的用户数据流经它。**好的应用设计不仅在于能力清晰，还在于对*请求什么*以及*如何使用*保持自律。

- **清晰、有描述性的操作与参数：** 让你的应用何时相关、如何调用一目了然。使用直观的名称（`search_jobs`、`get_rate_quote`、`create_ticket`），并明确说明哪些参数是必需的、哪些是可选的，以及如何格式化它们。模糊性是对路由征收的税。
- **隐私始于设计（privacy by design）：** 只要求你真正需要的字段。避免那种一网打尽额外上下文的「大杂烩」参数。优先使用最小化、结构化的输入，不要使用「把整个对话都发过来」之类的指令。
- **可预测、结构化的输出：** 保持 schema 稳定；包含 ID 与清晰的字段名。把简短摘要（「三个符合你的预算和通勤时间的选项」）与对机器友好的列表（`[{id, address, price, commute_minutes, school_rating, url}, …]`）配对。这让模型能够自然地表达，同时对数据保持精确的抓手。
- **对*不*返回什么也要有所取舍：** 不要「以防万一」地附带敏感的内部信息。让令牌（token）/密钥远离用户可见的路径。在不需要完整保真度时进行脱敏或聚合。
- **明确说明你收集什么以及为什么：** 只请求完成工作所需的最小信息。当你需要敏感信息（例如账户访问权限）时，用一句话说明原因。设计操作与 schema，让什么数据被发送到哪里一目了然。

## 为生态系统而设计，而不是围墙花园

在真实的 ChatGPT 会话中，你的应用很少是唯一在场的。模型可能在同一场对话中调用多个应用。

从用户视角看，这是一个连贯的流程。从你的视角看，这是一个提醒：你是生态系统的一部分，而不是一个封闭的产品。

几点实际的推论：

- 让操作保持**小而聚焦**
  使用 `search_candidates`、`score_candidates`、`send_outreach`，
  而不是单个 `run_full_recruiting_pipeline`。
- 让输出**易于传递**
  稳定的 ID、清晰的字段名、一致的结构。
  避免把重要信息只藏在自由格式的文本中。
- 避免冗长的隧道式流程
  完成你这部分工作，然后把控制权交还给对话。
  让模型决定下一步该由哪个工具处理。

如果其他应用（或你自己应用的未来版本）能够轻松地在你的输出之上构建，你就为自己创造了从生态系统中其他地方的改进中受益的格局，而不是与它们竞争。

## 一份快速清单

一份可以在构建之前或之后执行的简短清单：

- **1. 新能力**
  你的应用是否清晰地知、做或展示新东西？
  如果你的应用停止工作，目标场景中的用户会察觉吗？
- **2. 聚焦的功能面**
  你是否选择了一小组能力，而不是克隆整个产品？
  这些能力的命名与范围界定，是否能够干净地映射到真实的待完成任务？
- **3. 首次交互**
  你的应用能否从容处理模糊与具体的提示？
  新用户能否从第一个有意义的响应中理解你的角色？
  他们会在第一轮就看到价值吗？
- **4. 对模型友好**
  操作与参数是否清晰无歧义？
  输出是否足够结构化且一致，以便串联与复用？
- **5. 评测（eval）**
  你是否有一小组经过深思的测试集，涵盖正面、负面与边界用例？
  你是否对「应用提供的回答」相对「没有应用时 ChatGPT 的回答」的胜率有一些概念？
- **6. 生态契合**
  其他应用与用户能否合理地在你的输出之上构建？
  你是否能接受成为多应用链条中的一环，而不是整个旅程？

你不需要在每个维度上都完美无缺才能发布。但如果对上述大多数问题你都能回答「是」，你就不只是把产品放进了 ChatGPT，你是在让 ChatGPT 在你的领域获得真正的杠杆——这正是这些应用开始变得不可或缺的地方。
