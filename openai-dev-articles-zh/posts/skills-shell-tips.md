# Shell + Skills + Compaction：让长时间运行的智能体真正干活的技巧

> 原文：[Shell + Skills + Compaction: Tips for long-running agents that do real work](https://developers.openai.com/blog/skills-shell-tips/) · OpenAI 开发者博客

我们正在从单轮助手转向能够处理真实知识工作的长时间运行智能体：读取大型数据集、更新文件、编写应用。

基于开发者反馈以及我们构建 Codex 和内部智能体的自身经验，我们发布了一组新的智能体原语（agentic primitives），让长时程工作更加切实可行：

- [**Skills**](https://developers.openai.com/api/docs/guides/tools-skills)（与 Agent Skills 开放标准对齐）：可复用、带版本的指令集，可以挂载到容器中，让智能体更可靠地执行任务。
- 升级版 [**shell**](https://developers.openai.com/api/docs/guides/tools-shell) 工具：一个由 OpenAI 托管、具有受控互联网访问权限的容器，智能体可以在其中安装依赖、运行脚本、写入输出（例如报告与产物）。
- [**服务端压缩（server-side compaction）**](https://developers.openai.com/api/docs/guides/context-management)：一种简单的方式，可自动压缩长时程的智能体运行，让你永远不会触及上下文上限。

文档与 API 参考会逐项介绍上述内容。本文聚焦于那些不那么显眼、但我们看到效果最好的技巧与模式——既来自我们在 OpenAI 的工作，也来自早期 Skills 客户 Glean 的生产实践。

## 一个简明的心智模型

### Skills：模型可按需加载的「操作规程」

Skill 是一组文件加上一个包含 frontmatter 与指令的 `SKILL.md` 清单。可以把它理解为：一份带版本的行动手册（playbook），模型在需要真正干活时可以查阅。

当 skills 可用时，平台会把每个 skill 的 `name`、`description` 和 `path` 暴露给模型。模型利用这些元数据来决定是否调用某个 skill。如果决定调用，它会读取 `SKILL.md` 获取完整工作流。

### Shell 工具：智能体的「执行环境」

Shell 工具让模型可以在真实的终端环境中工作，方式有两种：

- 由 OpenAI 管理的托管容器。
- 由你自行执行的本地 shell 运行时（工具语义相同，但机器由你掌控）。

托管 shell 通过 Responses API 运行，这意味着你的请求自带有状态工作、工具调用、多轮续接以及产物（artifacts）。

### Compaction：让长时间运行持续前进

随着工作流变长，它们会撞上上下文窗口上限。服务端 compaction 通过管理上下文窗口并自动压缩会话历史，让长时间运行保持前进。

Responses API 中的 compaction 提供两种处理方式：

- **服务端 compaction（新）：** 当上下文越过阈值时，compaction 会在流中自动运行，无需单独调用 compaction。
- **独立 compact 端点：** 当你想显式控制 compaction 发生的时机时，使用 `/responses/compact`。

### 为什么三者配合使用效果更好

- Skills 把稳定的操作规程和示例移入可复用的包中，减少提示词的「面条式」混乱。
- Shell 提供完整的执行环境，让你可以安装代码、运行脚本、写入输出。
- Compaction 在长时间运行中保持连续性，让同一个工作流无需手动做上下文手术就能持续执行。
- 三者结合，你就能获得具备真实执行能力的可复现工作流，而不必把系统提示词变成一个脆弱的巨型文档。

## 技巧与窍门

### 1）像写路由逻辑一样写 skill 描述（而不是写营销文案）

Skill 的描述实际上就是模型的决策边界。它应该回答：

- 什么时候该用这个？
- 什么时候不该用这个？
- 输出是什么？成功标准是什么？

一个实用的模式是直接在描述中加入一段简短的「何时使用 vs. 何时不用」，并保持具体（输入、涉及的工具、预期产物）。

### 2）加入反例与边界用例，减少误触发

一个出人意料的失败模式是：让 skills 可用，最初反而可能降低正确触发率。我们见过有效的一种修正是：反例（negative examples）加边界用例覆盖。

在实践中，这意味着写出几条明确的「不要在……时调用这个 skill」的用例（以及此时应该怎么做）。这能帮助模型更干净地进行路由，尤其是当你有多个乍看之下很相似的 skills 时。

Glean 直接经历了这一点：在针对性评测（evals）中，基于 skill 的路由最初使触发率下降了约 **20%**，在他们在描述中加入反例与边界用例覆盖后才恢复。

### 3）把模板与示例放进 skill 里（不用时基本零成本）

如果你一直把模板硬塞进系统提示词，请停下来。

Skill 内的模板与完整示例有两大优势：

- 恰好在需要时可用（即 skill 被调用时）。
- 不会为无关查询膨胀 token。

这对知识工作类输出尤其有效，例如：

- 结构化报告。
- 升级分诊摘要。
- 客户账户计划。
- 数据分析报告。

Glean 反馈，这一模式给他们带来了生产环境中一些最大的质量与延迟收益，因为这些示例只在 skill 触发时才被加载。

### 4）趁早为长时程设计：容器复用与 compaction

长时程智能体很少能靠一次性提示词取得成功。从一开始就要为连续性做好规划：

- 当你需要稳定的依赖、缓存的文件和中间输出时，在多个步骤间复用同一个容器。
- 传入 `previous_response_id`，让模型可以在同一线程中继续工作。
- 把 compaction 当作默认的长时程原语来用，而不是紧急备用手段。

这一组合能减少重启行为，并在线程不断增长时保持多步骤任务的前后连贯。

### 5）需要确定性时，明确告诉模型使用某个 skill

默认行为是模型自行决定何时使用 skill。这通常正是你想要的。

但当你运行的是有明确契约的生产工作流时（宁要确定性，不要小聪明），只需说：

「使用 `<skill name>` 这个 skill。」

这是你能拉动的最简单的可靠性杠杆。它把模糊的路由变成明确的契约。

### 6）把 skills 加联网视为高风险组合（按遏制思路设计）

这条安全建议现在容易被一带而过，日后却难以补救。

**将 skills 与开放网络访问相结合，会为数据外泄（data exfiltration）创造高风险通道。** 如果你使用联网功能，请保持网络允许列表严格、假定工具输出不可信，并避免在面向消费者的流程中同时使用开放互联网与强大的操作规程——在这些场景中，用户期待强确认控制。

一个稳健的默认姿态：

- Skills：**允许**
- Shell：**允许**
- 网络：**仅在最小允许列表下启用**，按请求粒度，用于范围狭窄的任务

### 7）把 `/mnt/data` 作为产物的交接边界

对于托管 shell 工作流，请把 `/mnt/data` 当作标准位置，用于写入你之后要取回、审阅或传回后续步骤的输出。例如报告、清洗后的数据集和完成的电子表格。

一个好用的心智模型：工具写盘，模型基于磁盘内容推理，开发者从磁盘取回。

### 8）把允许列表理解为两层体系（组织级与请求级）

联网控制在两个层面：

- 组织级允许列表（由管理员配置），设定允许访问的目标上限。
- 请求级 `network_policy`，必须是组织允许列表的子集。

两条在运维上很重要的推论：

1. 保持组织级允许列表小而稳定（「你信任的已批准目标」集合）。
2. 让请求级允许列表更小（「这一项任务所需的目标」集合）。

如果请求包含组织允许列表之外的域名，将会报错。

### 9）需要鉴权的调用使用 `domain_secrets`（避免凭据泄露）

如果某个允许的域名需要鉴权头，请使用 `domain_secrets`，让模型永远看不到原始凭据。

在运行时，模型看到的是占位符（例如 `$API_KEY`），sidecar 只为已批准的目标注入真实值。只要你的智能体需要在容器内调用受保护的 API，这就是一个稳健的默认做法。

### 10）在云端与本地使用同一套 API

你可以使用这两类原语，而不必承诺把一切都托管：

- Skills 同时适用于托管 shell 与本地 shell 模式。
- Shell 有本地执行模式：由你自行执行 `shell_call`，并把 `shell_call_output` 返回给模型。
- 如果你使用 Agents SDK，还可以接入自己的 shell 执行器。

一个实用的开发循环如下：

1. 从本地开始（快速迭代、可访问内部工具、易于调试）。
2. 当你需要可复现性、隔离性与部署一致性时，迁移到托管容器。
3. 在两种模式下保持 skills 一致（即使执行环境迁移，工作流依然稳定）。

## 三种构建模式

尽管你可以随意试验这些新的智能体原语，这里给出三个如何组合它们来构建实用应用的例子。

### 模式 A：安装 -> 获取 -> 写出产物

这是从托管 shell 中获益的最简单方式：智能体安装依赖、获取外部数据，并产出一份具体的交付物。

例如：

- 安装几个库。
- 抓取网页或调用 API。
- 把报告写入 `/mnt/data/report.md`。

这一模式是真实工作智能体的基础，因为它创建了一个干净的审阅边界：你的应用可以把产物展示给用户、记录日志、做差异对比，或将其送入后续步骤。

### 模式 B：Skills + shell 打造可复现的工作流

在你成功构建一两个 shell 工作流之后，会注意到下一个问题：它能跑，但当提示词发生漂移时，可靠性会下降。

这正是 skills 登场的地方。以下是一个经得起时间考验的结构：

1. 把工作流（步骤、护栏、模板）编码进一个 skill。
2. 把 skill 挂载到你的 shell 环境中。
3. 让智能体遵循该 skill，确定性地产出产物。

这对以下类型的工作流尤其有效：

- 电子表格分析或编辑。
- 数据集清洗加摘要生成。
- 为周期性业务流程生成标准化报告。

### 模式 C（进阶）：Skills 作为企业工作流的载体

我们早期观察到的一个模式是：在单次工具调用与多工具编排之间的空档地带会出现准确率损失。Skills 可以弥合这一空档，让工具推理更有章法，而不必膨胀系统提示词。

来自 Glean 的具体例子：

- 一个面向 Salesforce 的 skill 将评测准确率从 **73% -> 85%** 提升，并把**首 token 时间（time-to-first-token）**降低了 **18.1%**。
- 实用策略包括细致的路由、反例，以及在 skill 内嵌入模板/示例。
- Glean 还使用 skills 在企业工作流中编码周期性任务，包括客户账户规划、升级分诊以及符合品牌调性的内容生成。

这就是事情开始变得强大的样子。Skills 成为「活」的 SOP（标准操作规程）：随着你的组织演进不断更新，并由智能体一致地执行。

## 一次构建，处处运行

当长时间运行的智能体既能遵循操作规程、又能在计算机上真正干活时，它们的用处会大幅提升。Skills、托管 shell 与 compaction 正是这一基础的基石。回顾一下：

- 用 skills 编码「怎么做」（操作规程、模板、护栏）。
- 用 shell 执行「去做」（安装、运行、写出产物）。
- 用 compaction 保持长时程运行的前后连贯（无需手动管理上下文）。
- 快速迭代时从本地开始。
- 需要可复现、隔离的执行时，迁移到托管容器。
- 用组织级与请求级允许列表锁死联网，鉴权调用使用 domain secrets。

在你自己的应用中开始使用吧。参阅 [skills 文档](https://developers.openai.com/api/docs/guides/tools-skills)、[shell 文档](https://developers.openai.com/api/docs/guides/tools-shell)与 [compaction 文档](https://developers.openai.com/api/docs/guides/context-management)了解具体做法。
