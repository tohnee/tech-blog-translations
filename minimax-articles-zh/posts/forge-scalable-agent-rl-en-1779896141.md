# Forge：可扩展的智能体强化学习框架与算法

AI强化学习Forge

![Forge RL framework hero](https://filecdn.minimax.chat/public/forge-hero-1779895280980.jpeg)

Forge RL 框架主视觉图

为真实世界的智能体（Agent）扩展强化学习（RL），会陷入一场三方拉锯：**系统吞吐量**、**训练稳定性**与**智能体灵活性**各自朝不同方向使劲，而这种张力长期阻碍着工业级 RL 的落地。

这篇文章介绍我们的内部 RL 框架 **Forge** 如何打破这一「不可能三角」：它组合了灵活的系统架构、专为长时程智能体调优的算法、尊重训练分布的异步调度，以及激进的训练/推理优化。标准化的交互协议让 Forge 能够大规模训练任意智能体脚手架（scaffold），而这正是 MiniMax M2.5 模型突破性能力的来源。

在构建 MiniMax M2.5 的过程中，Forge 与超过十万个各不相同的真实世界智能体脚手架和环境协同工作。在上下文长度达到 200k、日吞吐量达到百万级样本的情况下，系统在奖励上保持收敛，并切实提升了底层模型的能力。结合我们的 CISPO 算法与复合奖励设计，M2.5 推进了高效、可靠的真实世界生产力的形态——也让我们的使命 *Intelligence with Everyone*（与大众共享智能）更进一步。

## 1. 问题形式化

在深入架构之前，我们先框定目标。智能体 RL 系统旨在最大化**有效智能体训练产出** **J**：

\begin{aligned} \max_{\theta} J(\theta) = & \text{Throughput}(\mathcal{A}) \times \text{Sample Efficiency}(\mathcal{A}) \\ \text{s.t.} \quad & \forall \mathcal{A} \in \Omega_{\text{agent}} \quad (\text{Arbitrary Agent}) \\ & \mathbb{E}[\text{Update Variance}] < \delta \quad (\text{Stability}) \\ & \mathbb{E}[\|J^{(T)} - J^*\|] < \epsilon \quad (\text{Convergence}) \end{aligned}

其中 **System Throughput（系统吞吐量）** 是每秒处理的原始 token 数，受四个组件制约—— rollout、训练、数据处理、I/O。**Sample Efficiency（样本效率）** 是每个样本带来的平均改进，由数据分布、数据质量、算法效率以及离策略程度（off-policy-ness）驱动。公式中的约束项是稳定性与收敛性的代理信号。有三个结构性问题阻碍着 J 的最大化；我们接下来逐一讨论。

### 1.1 智能体可扩展性与框架灵活性

当今的 RL 范式出于两个结构性原因，给智能体复杂度盖上了一块玻璃天花板：

**智能体自主性受限。** 标准框架把智能体当作白盒函数处理，并在智能体与训练器之间共享状态。这种刚性使得建模复杂的认知架构变得困难——例如动态上下文管理或多智能体协作——并且使训练出的能力无法泛化到不满足这些假设的任意黑盒智能体上。

**Token 一致性壁垒。** 既有的 token 进 / token 出（TITO）架构将智能体与底层 token 逻辑紧密耦合。一旦引入任何非平凡的上下文管理，让推理侧抽象（高层循环）与训练侧表示（token 级数据）保持步调一致，在计算上就非常昂贵。

### 1.2 系统效率与算力冗余

智能体 rollout 时间的方差极大——简单的一次 API 调用只需几秒，而长推理链可能长达数小时。这造成了一种调度死锁：

**异步控制器。** 硬件效率与训练稳定性之间存在尖锐的取舍。严格的 FIFO/同步调度会暴露「掉队者效应」：一个慢任务就会造成队头阻塞，让整个集群闲置。贪心 / 先完成先出模式能挽回吞吐量，但代价是严重的分布偏移——训练早期数据被简短容易的任务主导，后期又被扎堆的困难任务主导。这种非平稳性会破坏优化的稳定，使梯度来回震荡。

**前缀冗余。** 在智能体场景中，分词器与内置上下文管理的交互意味着相当大比例的请求共享相同的前缀。在训练中反复重算这些前缀既浪费算力，也带来各自的工程难题。

### 1.3 算法挑战：信用分配与优化稳定性

**稀疏奖励，高梯度方差。** 智能体任务是长时程、反馈延迟的：单个结果取决于数千个动作构成的链条。在 200k 的上下文窗口内把信用分配到具体 token 或工具调用上，在统计上是脆弱的。回报估计中偏低的信噪比带来高梯度方差，在大规模训练时破坏稳定性。

**对延迟无感知的优化。** 经典 RL 目标只优化正确性——步级或结果奖励——而忽略墙上时钟成本。真实的智能体场景中，由于工具执行和串行处理，往往存在多条都正确但延迟特征迥异的有效轨迹。如果没有对并行性或高效工具使用的激励，得到的智能体虽然正确，实际却很慢。

## 2. 系统架构与智能体 RL 范式

为了缓和「效率 vs 离策略程度」的取舍并削减冗余，我们做出如下架构决策。

### 2.1 RL 系统设计

我们没有把系统绑死在某个具体实现上，而是采用通用化的中间件设计，将智能体的推理逻辑与底层训练基础设施解耦。系统包含三个模块：

![Forge RL 三模块系统架构](https://filecdn.minimax.chat/public/forge-rl-system-1779895280981.png)

Forge RL 三模块系统架构

**智能体侧（Agent Side）。** 这一层抽象出通用智能体——同时涵盖白盒与黑盒脚手架——及其环境。它驱动递归的环境交互，让智能体扮演纯粹的轨迹生产者。通过将环境反馈与系统开销隔离，智能体可以专注于自己的核心逻辑（上下文管理、推理链），而对训练/推理管线保持无感知。

**中间件抽象层。** 智能体侧与训练/推理侧之间的桥梁，由 Gateway 服务器和数据池（Data Pool）组成。

- **Gateway 服务器：** 一个标准化的通信端点，处理智能体与 LLM 之间的补全请求。它使用通用协议，把真实的底层模型隐藏在智能体的行为逻辑之外。
- **数据池（Data Pool）：** 一个分布式存储，异步收集智能体产生的 rollout 轨迹与报告。它在生成与训练之间起到缓冲作用，为提升效率和算法实验提供灵活的数据处理与组批策略。

**训练与推理侧。** 承载重计算——LLM（Rollout）引擎和训练引擎。

- **Rollout 引擎：** 针对高吞吐 token 生成优化，服务于中间件转发来的请求。
- **训练引擎：** 消费来自数据池的处理后 token 序列并更新策略，同时与 Rollout 引擎保持同步，使智能体始终在最新策略分布下探索。

离线评测显示，脚手架而非模型本身导致了巨大的性能差距。得益于模块化框架，我们无需触碰智能体内部即可跨多种脚手架训练，让模型跨脚手架——也就是跨环境——泛化。引擎与智能体完全解耦，接入新智能体只是机械性操作。我们总共集成了数百种脚手架类型和数千种工具调用格式。

### 2.2 面向上下文管理（CM）的白盒智能体 RL

对于白盒智能体，完整的脚手架设计与增强让我们能够在特定智能体架构下直接观察和优化模型。构建 MiniMax M2.5 的过程暴露了几个问题，它们损害了早期模型在需要主动上下文管理的长时程任务（如 DeepSearch）上的表现：

**上下文腐化（Context Rot）。** 随着轮数增长，累积的中间推理和冗余观测造成注意力稀释。即使严格处于绝对上下文窗口之内，模型也会失去对关键信息的聚焦。

**推理-训练失配。** 上下文管理确实在推理时扩展了有效交互视界，也有助于长上下文性能，但只在推理时应用它，会造成与 RL 训练分布的严重偏移。模型被迫临场吸收意想不到的上下文切换，拖累整体表现。

为了消除这种分布偏移并保持推理的忠实性，我们把 CM 折叠进 RL 交互循环本身，将上下文管理视为驱动状态转移的功能性动作：

**CM 驱动的状态转移。** CM 成为一个显式的智能体动作；上下文切换自然地处于环境动力学之内。从 S_t 到 S_{t+1} 的转移隐式携带了上下文切换逻辑，于是上下文适应被直接折叠进训练目标。

**自适应推理模式。** 在这一框架下优化 π，让模型把分布偏移内化，并涌现出优先关注状态关键 token 的鲁棒推理模式。

**上下文感知的管理策略。** 模型学会在 RL 生成过程中预判上下文管理操作与切换。通过保留任务关键信息、修剪噪声，当模型运行在带上下文管理的智能体框架内时，性能显著提升。

### 2.3 黑盒智能体 RL：跨异构脚手架的鲁棒性

在真实部署中，我们相当一部分用户群运行的是专有的或复杂的智能体架构，它们表现为黑盒。模型表现往往随底层脚手架剧烈波动，因为标准训练范式无法跨认知架构泛化。为此，我们用一个专门的黑盒智能体实验验证了该框架，确保无论智能体多么不透明，优化都能保持一致。

**非侵入式集成。** Forge 对智能体内部完全无感知。智能体只需把请求路由到 RL 服务 Gateway，框架在幕后完成数据收集与训练。因此在真实 RL 训练中，Forge 支持任意的上下文操纵——记忆压缩、历史重写——以及任何复杂的内部智能体循环（Deep Think、多智能体架构）。

**多脚手架泛化。** 将训练循环与智能体内部状态解耦，使 MiniMax M2.5 与广泛的黑盒智能体兼容。覆盖范围从重度依赖 Sandbox 和 MCP 环境的代码型智能体——包括完全以黑盒方式训练我们的 OpenCode Agent——到采用激进上下文缩减策略（如 Truncate BC）的智能体。从经验上看，即使对完全不透明的系统，收益也保持一致且稳定。

## 3. 工程优化

### 3.1 混合调度策略：窗口化 FIFO

为了在吞吐量与分布一致性之间架桥，我们采用 **Windowed FIFO（窗口化 FIFO）**——一种施加于训练调度器上的滑动约束，位于严格同步排序与贪心异步执行之间。

核心规则约束训练调度器如何从全局生成队列中拉取样本。即使一批大小为 N 的大批次正在执行中，调度器也只能看到一个大小为 W 的窗口（例如 W = 0.3N）。

**受限可见性。** 设队列为 Q = [T_0, T_1, …, T_{N-1}]，队头索引为 i。调度器只能从切片 [T_i, T_{i+W-1}] 中获取已完成的轨迹。

**窗口内的局部贪心乱序。** 在 [T_i, T_{i+W-1}] 内，调度器可以立即抓取任意已完成的轨迹。这打破了队头阻塞效应：窗口内的快任务不必等待绝对的第一名任务完成。

**全局严格阻塞（窗口边界）。** 即使索引 j > i+W（窗口外）的任务已经完成——这在大生成批次中对简短容易的任务很常见——调度器也被禁止提取它。

**滑动约束。** 窗口只随队列头部的消费而向前滑动（i → i+1）。这迫使调度器在当前窗口内等待掉队者——那些复杂的长时程任务——防止训练分布向队列更后方的快而容易的样本漂移。

### 3.2 用前缀树合并加速智能体轨迹训练

智能体训练数据集通常是重叠严重的长多轮对话。

### 朴素方法的冗余

**前缀重叠。** 在一段直接的多轮对话中，消息一条接一条地追加。在分词器一致的前提下，共享同一历史的多个补全原则上可以合并。

**复杂的上下文管理。** 智能体常常部署精细的上下文策略——丢弃无关的中间结果、自我总结——因此不同的补全经常共享大段公共前缀。

**朴素方法的局限。** 传统训练把每个样本视为独立，反反复复重算那些共享前缀。在长上下文训练中，浪费的 TFLOPS 是巨大的，吞吐量随之受损。

![前缀树合并示意图](https://filecdn.minimax.chat/public/forge-prefix-tree-1779895280984.png)

前缀树合并示意图

### 前缀树合并

为了消除这种冗余，我们从线性样本处理转向树状结构处理。

**前缀树合并。** 对于智能体场景中常见的复杂上下文管理（如上文的长公共上下文所示），只要多个补全共享同一底层前缀——即使它们后续的回复略有分歧或来自不同的采样分支——就可以在样本级合并成一棵前缀树。

利用 Magi Attention 等注意力原语，我们让逻辑执行与标准前向传播完全一致。前向传播之后，再从元数据中展开前缀树，正常计算损失，下游逻辑无需改动。

通过跳过冗余的前缀预填充，该方案带来 **40 倍训练加速**，并显著降低显存压力，从而支持更长的序列或更大的 batch size，同时在损失和指标上与标准方法保持严格的数学等价。

### 3.3 极致推理加速

生成管线上的三个架构动作：

**基于 MTP 的投机解码。** 我们不用静态草稿模型，而是使用以 Top-K KL 损失持续微调的 Multi-Token Prediction（MTP）头。这让草稿与不断演化的 RL 策略保持对齐，在分布漂移下仍维持高接受率和有意义的加速。

**异构 PD 分离。** 将 Prefill 与 Decode 解耦，消除混合 MoE 调度中的 PD 干扰，并允许每个实例采用独立的并行策略，共同最大化全局吞吐量与长时程任务的尾延迟表现。

**全局 L3 KV Cache 池。** 为了避免多轮智能体 RL 中的冗余预填充，并借助组级 rollout 推高前缀缓存命中率，我们采用 DFS 支撑的全局 L3 缓存。一个成本感知的调度器通过权衡排队延迟与缓存迁移成本来路由请求，在不压垮单个实例的前提下最大化缓存局部性。

## 4. 可扩展的智能体 RL 算法

### 4.1 RL 算法

我们使用 **CISPO** 作为核心算法，并针对长时程智能体的特点做了适配。

**统一混合域训练。** 多阶段 RL 常在域之间产生负迁移或干扰，我们反其道而行之，在单次训练中混合 Reasoning、General QA 与 Agent 域的任务。这种联合设置消除了顺序阶段的退化，并提升了跨多样任务的泛化。

\mathcal{J}_{\text{CISPO}}(\theta) = \mathbb{E}_{(q,a)\sim\mathcal{D}, \{o_i\}_{i=1}^G \sim \pi_{\theta_{\text{old}}}(\cdot|q)} \left[ \frac{1}{\sum_{i=1}^G |o_i|} \sum_{i=1}^G \sum_{t=1}^{|o_i|} \mathbf{sg}(\hat{r}_{i,t}(\theta)) \hat{A}_{i,t} \log \pi_\theta(o_{i,t} \mid q, o_{i,<t}) \right]

其中：

\begin{aligned} \hat{r}_{i,t}(\theta) &= \text{clip}\left( r_{i,t}(\theta), 0, 1 + \epsilon_{high}^{IS} \right) \\ \widehat{A}_{i,t} &= \sum_{p=t}^T (r_p^{\text{speed}} + r_p^{\text{perf}}) - B_i \end{aligned}

### 4.2 稠密且效率感知的奖励

为了在超长上下文（最长 200k）中解决信用分配问题并保持训练稳定，我们采用复合奖励框架：

**过程奖励（Process Reward）。** 为了获得稠密反馈，我们针对中间行为施加奖励——例如惩罚语言混杂或特定的工具调用错误——而不是只依赖最终结果。

**任务完成时间奖励（Task Completion Time Reward）。** 在智能体场景中，多条轨迹都能完成任务，总时长不仅取决于 token 生成，还取决于工具执行与子智能体调用延迟。由于完成时间是用户体验的核心，我们把相对完成时间纳入奖励信号，激励智能体使用并行并加速执行。

**用于方差缩减的 Reward-to-go。** 稀疏奖励在长时程任务上带来高梯度方差。我们使用 Reward-to-go 形式对回报归一化，降低梯度方差、锐化信用分配并稳定优化。

## 5. 结论

借助 Forge，我们解决了智能体 RL 扩展的不可能三角：RL 系统吞吐量的突破，加上跨任意智能体脚手架的鲁棒泛化。将这一灵活架构接入我们稳定的 CISPO 算法，支撑了 MiniMax M2.5 背后的大规模训练。这套整体方法移除了此前的种种约束，交付了高效的真实世界智能体能力，也把我们的使命 *Intelligence with Everyone*（与大众共享智能）推得更远。
