## 1. 为什么我们需要 Agent Team

即使你可以通过迭代 Skills 让单个 Agent 交付得不错，当最终结果由单个 Agent 产出时，它不可避免地既是裁判又是选手。这一矛盾正是 Agent Team 的出发点。

Agent Team 把原本压在一个 Agent 身上的复杂任务，变成一个有前台有后台、有验收、有记忆的流程。用户仍然只发一条消息，但 Agent Team 系统会决定是否拆分任务、哪些角色可以并行、哪些结果必须校验、哪些经验应该沉淀。

继续上面的场景。

> 「帮我写一篇关于 Agent Team 的长文。信息必须基于 2026 年的最新数据，并同时交付 Markdown 和 HTML 两个版本。」

单个 Agent 或许能顺利搞定，就像坐在用户旁边的一位同事。用户说「润色这一段」，它马上改；用户说「这里格式不对」，它立刻确认。但几个问题会暴露出来：1) 如果用户不下指令，Agent 就停下来，用户必须不断告诉它「确认」或「继续」。

- **单个 Agent 会在用户意想不到的时刻停下。**

用户经常看到有 7 件事要做的 Agent 在改完 3 处后暂停并开始汇报：「我已完成第 1、2、3 处修改——要我继续处理剩下的 5 项吗？」

出现这种情况，是因为模型普遍存在上下文焦虑，而且超长任务的训练本身就需要巨额的资金、时间和算法投入。模型对「任务何时可以停止」的判断是模糊的。

- **单个 Agent 会随时间推移变笨——在长任务上退化明显。**

用户常常感觉，Agent 跑着跑着就从「聪明的助手」变成了「管理一个忙忙碌碌却容易分心的人」。用户不断追问：你还记得我之前的要求吗？你怎么把调研任务做成产品营销文案了？

只要一步发生漂移，**下游的一切都会沿着漂移持续生成**。

更糟的是，单个 Agent 很难形成天然的「制衡」。它也许会老老实实地自查，但检查的仍然是它刚刚亲手构建的那个场景。

- **单个 Agent 也无法对长周期任务做出快速响应。**

尤其是在 IM 场景（通过即时通讯应用驱动 Agent）中，用户的耐心非常短。在 IM 里发出消息后，用户期待几秒内得到回应。哪怕任务再复杂，用户也希望先收到一句「收到，我打算这么做，做完回来找你」，而不是盯着聊天框干等十分钟、半小时甚至更久，只为了确认任务已经启动。

**「为什么我的 Agent 不回我消息」是我们收到的用户反馈中最大的一类。**

Agent Team 提供了不同的体验。主 Agent 先快速回应用户：任务已收到，目标已确认，我将在后台拆分并执行。任务被拆成多个板块组合或多个版本，并行执行。

用户不再需要等待每个子步骤完成，而是在关键节点收到汇报：任务已启动、已阻塞、需要决策、已完成。

他们还可以随时和主 Agent 聊天：「我刚又有个想法，能不能顺便调研一下」，主 Agent 可以回应：「可以，我现在拉起另一个 Agent 组，有进展就汇报。顺便说一句，进行中的任务 2/5 已完成，剩下 3 个里 2 个在验证阶段，最后一个我继续盯着。」

就像一个几秒内必回你微信的贴心朋友。

- 跳出任何单一任务，我们还必须接受**用户需求的多样性与跨领域的角色分工。**

同一天里，一个用户可能让 Agent 写代码、查资料、做幻灯片、总结会议、读 PDF、处理表格、报销、规划项目、生成周报。每一类任务都有不同的输入结构、工具权限、质量标准、风险等级和交付格式。

单个 Agent 可以通过 Skills 临时扮演不同角色，但角色扮演不等于角色专业化。真正的专业化，仅从上下文角度就至少有四个维度：不同的工具、不同的上下文、不同的记忆、不同的技能。从结果侧看，输出协议和验收标准也不同。假设我们已经建好了上面的 Agent Team 系统——承担不同职责的 Agent 可以反复遇到自己领域的任务，把踩过的坑变成记忆、把有价值的动作变成 Skills，就像一群与用户长期共事、各自越来越精通本职的同事。

## 3. MiniMax Agent Team：在受约束的多智能体循环之上，给每个 Agent 更多自由

MiniMax 的 Agent Team 是一个由主 Agent 领导的多智能体系统：主 Agent 把复杂任务拆分为并行子任务、派发给一批 Agent，并内置对抗式质量关卡——一个由确定性代码逻辑驱动的智能体循环。受 Ralph-Loop 和 Harness 启发，我们认识到模型上下文非常宝贵；通过拆分任务、划分职责，每一步都获得上下文隔离，从而整体提升 Agent 的产出质量。

![](https://filecdn.minimax.chat/public/agent-team-team-overview-r-1779893281296.jpeg)

- **Leader、Worker、Verifier 的基本协作流程**

要让多智能体从概念变成可用的产品，需要一条基本的协作流程。我们把它简化为三种角色：Leader、Worker 和 Verifier。

Leader 把用户目标翻译成任务结构。

Worker 执行具体子任务。不同 Worker 可以有不同的工具、上下文和输出要求。有的 Worker 做调研，有的改代码。Worker 的价值在于专业化：角色越清晰，Worker 的产出就越容易被复用、比较和检查。

Verifier 把「做完了」变成「可以交付」。它可以核查来源、覆盖清单和风险边界，也可以对 Worker 的结果提出修改建议。这体现了 Agent Team 的设计逻辑：Worker Agent 与 Verifier Agent 处于对抗关系。两者都以完成为目标，但一方的完成会触发另一方开工——很像公司里的研发与 QA，通过多轮对抗式迭代交付高质量结果，而不需要 CEO（人类用户）事必躬亲。

![](https://filecdn.minimax.chat/public/agent-team-lwv-l-1779893281297.jpeg)

![](https://filecdn.minimax.chat/public/agent-team-lwv-r-1779893281298.jpeg)

- 与只能创建任务、接收单轮结果的 Task 工具相比，**Agent Team 是一个你随时可以互动的团队。**

传统 Task 工具通常位于模型工具调用层：主 Agent 调用一个 task / dispatch / spawn 式的工具，传入一段提示词，然后等待子 Agent 返回一段文本或摘要。这种机制适合短生命周期、低风险、局部探索性的任务——比如让另一个模型快速搜文件、总结材料、验证想法或生成候选答案。即便今天已经有在后台运行的 SubAgent，Agent 之间的通信本质上仍是一次性的输入/输出——没有多轮对话，没有实时的问题与冲突上报。

为了让团队稳定运行，我们选择用**一个可靠的状态机**管理每个 Agent 的运行生命周期。一个生命周期就是一个 Session，而这个状态机就是 Team Engine。Team Engine 通过 producing、verifying、done 管理每个任务。验证失败时，Team Engine 会再次唤醒 producing 节点继续修改。Leader 全程可以获得 Team Engine 的最新状态，可以主动确认任务细节，甚至可以向正在运行的 producing 或 verifying Agent 发送补充提示词。协作关系不再被约束在一次函数调用里，而是变成多轮交互中的「主动推送 + 按需查询」。

每次 Agent Team 运行都携带长期价值。这次运行的经验可以沉淀为记忆和 **Skills**，让每个具体的 Agent 在如何与用户协作、如何高效完成任务上变得更主动，也让所有 Agent 更懂用户。

- **Agent 间通信设计：Agent 与人权利对等**

在设计 Agent 应该如何协作时，最直接的思路是看看今天人类与 Agent 是怎么协作的。用户可以通过前端 UI 提示、生成、中止和终止一个 Agent，这意味着 Agent 本身也应该能对另一个 Agent 执行这些操作。我们把用户对 Agent 的操作抽象成一个接口，而这些操作的实际执行者可以是用户、另一个 Agent，或 Agent Team 引擎。

![](https://filecdn.minimax.chat/public/agent-team-comm-l-1779893281301.jpeg)

![](https://filecdn.minimax.chat/public/agent-team-comm-r-1779893281302.jpeg)

当然，这一设计必须守住边界：「权利对等」不等于 Agent 获得无限权限，也不等于人类退出问责链条。恰恰相反——只有当 Agent 与人类共享同一个可审计的协作面时，权限、责任和风险才变得更容易看清。

### 3.1. 核心场景一：IM 集成，快速响应的异步执行

IM 的交互约束很特别。用户发出消息后，期待几秒内就有反馈，但很多任务天然需要几分钟甚至几小时来执行：调研、写会议纪要、做幻灯片、跑测试。如果系统让用户苦等最终结果，体验就变成「Agent 在聊天框里失踪了」。

单个 Agent 在这里很容易陷入两难：要么为了快速回复交付一个浅薄的答案，要么以长时间沉默为代价完成完整任务。更糟的是，IM 会话会持续进行——用户可能在任务执行中途提出新要求、切换话题或追问别的问题。如果长任务和当前会话绑定在同一个上下文里，系统既保不住响应速度，也保不住后台任务不被新消息污染。

这与 Google A2A 协议中关于长时任务、状态更新和人机协同（human-in-the-loop）的设计原则相呼应。Anthropic 的 Managed Agents 博客主张「session 不等于模型的上下文窗口」，长任务需要可恢复的会话日志作为外部上下文对象。

行业共识正在形成：IM 异步执行的底层逻辑是，当一个任务跨越多条消息、多个工具、多个 Agent 时，你不能指望任何一个模型的当前上下文保持完好。系统必须把任务状态、事件日志、文件产物和决策记录持久化为可恢复的对象。智能体协作是一项有状态的长期任务。

### 3.2. 核心场景二：Coding Harness（编码护架）

Agent Team 项目大量借鉴了 Harness 的思路。Harness 在「Agent 写代码」的基础上更进一步：Agent 必须遵循完整的开发生命周期——代码在分支上、执行在沙箱里、修改以 diff 呈现、测试可重跑、评审留记录、失败可回放，需要时任务可按角色拆分。Agent 的停止条件绑定到确定性、可观测的外部系统上。

- **编码任务中开发者 / 测试者 / 评审者的角色分工**

一个工程化的 Coding Harness 至少包含四类角色。

Leader 是控制平面。它首先判断任务是否值得开一个 Team：**改错别字、换常量，用单个 Agent 或脚本可能更便宜；跨文件理解和多方案并行比较才是 Team 的用武之地**。它还决定粒度：先读代码还是先并行探索方案、是否先写复现测试、失败重试几次、何时升级给人类。

Developer 负责实现，有明确的工作简报：**需求、相关文件、项目约束和禁止行为**。它的产出不仅是自然语言解释，还包括改动理由、潜在风险和验证建议。

Tester 把「看起来能跑」变成「有外部证据」。它定位既有测试入口、压缩失败日志、必要时添加最小复现。关键在于工具落地：验证结果来自命令、测试或可执行的检查。

Reviewer 与 Tester 不同。测试回答的是「是否通过了已知检查」；Review 关心的是「是否应该这样改」。它审视抽象边界、兼容性、错误处理、引入的依赖、权限扩张、日志是否泄露敏感信息。Reviewer 还可以**按专业并行**：一个通用评审者看可维护性，一个安全评审者看输入/凭证/网络边界，一个领域评审者看业务语义。

- **自动化测试、代码评审与人工验收如何接入**

第一层是自动化测试和静态检查。Harness 把测试、lint、构建和格式检查当作一等公民。Developer 改完代码后，Tester 运行验证；失败时，Leader 决定是让 Developer 修复、让 Tester 提供更多日志，还是把环境问题上报。

第二层是代码评审。Reviewer Agent 可以做自动初筛，抓住未使用的变量、漏掉的异常分支、公共 API 破坏、危险的 shell 调用、日志中的密钥、超出范围的文件修改等等。

### 3.3. 核心场景三：并行信息检索与调研

单个 Agent 做调研会遇到速度慢、上下文被污染甚至被注入、证据在上下文里丢失、调研方向偏倚等问题。Agent Team 的价值在于把调研拆分为多条并行的信息通道，再通过 verifier 和 synthesizer 把结果合并为结构化结论。重点在于设计一条既快、又能跳出单个 Agent 思路的研究管线——从不同角度、从正反两方收集并确认信息。

- **独立的 verifier 如何降低引用错误和事实幻觉**

Verifier 首先检查来源的可验证性。正式来源应使用稳定的 URL：官方页面、会议页面、作者博客。搜索缓存和聚合页只能作为线索，不能作为正式结论的证据。Verifier 还会检查来源状态是否过期，以及是否存在反证推翻该论断。

### 3.4. 核心场景四：流水线式办公文档写作

单个 Agent 写文档时，最容易产生的错觉是：只要模型会写，就能交付。当用户说「帮我做一份报告 / Excel / PDF」时，单个 Agent 往往先生成一大段文字，然后试图一次性完成排版、检查和修复。短文档可以靠一个上下文窗口撑过去；一旦任务变成长报告、正式合同或财务表格，问题很快暴露：内容规划、资料来源、结构一致性、图表对象、页眉页脚、导出质量全部挤进同一个上下文和同一个执行循环。

- **Agent Team 把结果从「可生成」带到「可交付」**

多智能体协作把文档交付拆分为多个可验证的阶段。Planner 先确定文档目标和结构；Writer 产出正文；Formatter 处理排版和文件对象；Evaluator 独立检查内容、格式和文件完整性。这种拆分把「文档生成」从一次性的文本生成变成更接近 CI/CD 构建流水线的东西：每一步产出中间产物，每一步有检查，每一步失败时可以局部重试。

## 4. 开发过程中的难题与反思

- **团队协作带来的上下文成本**

一群协作的 Agent 暴露出一类新的成本：交接成本、共享成本和聚合成本。这些成本没有一个是「模型上下文窗口再大一点就能解决」的。

交接成本：同一段信息必须在 Agent 之间重新组织。调研 Agent 收集了几十页材料后交给写作 Agent，写作 Agent 需要的是已经过初步调研的文档；写作 Agent 还要把写作结果交给格式检查 Agent。我们目前的做法是制造交接产物：1) 可读的交接文件，2) 跨 Agent 共享的记事本文件。Worker 之间通过文件路径加摘要进行缓慢而不打扰的沟通，避免把所有东西一次性塞进上下文。

共享成本：「让每个 Agent 看到所有信息」的代价。每多一个共享段落，每个 Worker 每一轮都要多花 token。当某个 Agent 在执行中途遇到问题时，它应该以正确的方式写入记忆，让经验可以广播给所有正在运行和即将启动的 Agent 上下文。我们用三种方式维护这类共享信息：1) Agent 内记忆——本 Agent 本次运行的经验；同一 Agent 的后续运行会得到提示，正在运行的其他 Agent 也会被立即通知；2) Agent 间通信 CLI——Agent 可以直接与其他运行中的节点对话，进行中断式通信；3) 前面提到的白板——相比 1 和 2（主动通知），白板支持持久化更大的体量，其他 Agent 需要时可以更优雅地按需拉取。

聚合成本：把多个 Worker 的输出合并成一份可交付成果所需的工作。并行收集 10 个版本的素材很容易，把它们合并成一篇事实一致、引用对齐、风格统一的文章却很难。在这一步，Leader 的职责是「把 10 合成 1」，而不是「再叫几个人来攒更多素材」。承认这件事很贵，是设计一个 Team 的第一步。

- **时间 / token 消耗与结果 ROI 之间的取舍**

既有研究中，多智能体很少与高 ROI 划等号。论文 Cost of Consensus 声称，在特定模型和同质辩论设置下，消耗可达孤立自我修正的 2.1–3.4 倍 token，而准确率没有提升，有时反而更差。结论很清楚：没有结构、没有停止条件的「更多」，只会把不确定性并行扩散——一个简单的 AI 聊天室很难保证最终产出的质量。

ROI 还包括用户等待。尽管我们让长任务异步化、让用户随时能与 Leader Agent 交谈——降低了用户对即时交互的需求——整体交付时间仍然变长了。与单个 Agent 一口气做完相比，Agent Team 不可避免地按 1-2-3-4 顺序执行。我们想了很久如何控制合理的拆分粒度，在「大任务做不好」与「拆太细交付太慢」之间平衡。我们相信，随着模型智能的提升，让团队在后台运行、完成时主动汇报，是用一种任务结构换取「盯着 Agent 在同一会话里慢慢生成」的心理成本。多智能体的价值与成本在这里同时显现：用户愿意为可验证、可恢复、可审计的结果等待更久——只要过程透明。

而且我们相信，一旦用户看到 Agent Team 交付的高质量结果，**他们对 Agent 的信任会上升，从而腾出自己的带宽去做更深、更广的思考——做一个有人性温度的思考者，把执行思考和交付结果的任务交给 Agent Team**。

- **Verifier、重试与 Leader 决策的成本**

Verifier 是一个团队从 demo 走向交付的关键。

第一项成本是验证本身。编码任务要跑测试；调研任务要交叉核对来源、确认引用边界；验证越严格，成本越高；走个过场的验证只留下「似乎通过了」的错觉。

第二项成本是重试策略。如果一个 Worker 一直在「改一点——被 verifier 拒绝——再改一点」里打转，整个计划只会越来越贵。

第三项成本是 Leader 决策不能含糊。在高风险动作面前——合并代码、覆盖生产数据——最终裁决必须由人类签字。GitHub Copilot cloud agent 的官方文档把整个流程都留在 GitHub 内：计划、提交、日志和 PR 都可供团队审阅；更新日志还提到，在 PR 定稿之前会先运行安全与质量分析。

它指向的方向很清楚：Agent 的交付不仅包括结果，还包括一份可回放、可问责的轨迹。

- **多智能体系统是一个运行时（runtime），而不是提示词编排**

跳出模型和上下文，回到我们如何构建这个系统：多智能体常被简化为「写几个提示词 / 技能，让模型角色扮演」。在我们实际的代码里，这种简化只是最初的 demo；真正的复杂度藏在细节里，而这一切都是为了让用户享受「聊一句就行」的流畅体验。Team Engine 需要管理大量复杂对象和状态转移，让 Agent Team 的运行足够自动化、可观测。渲染层必须吸收多个操作方——用户、Agent、Team Engine 等——对同一概念的操作：比如「创建任务」可能来自很多来源。渲染复杂度的另一个来源是消息出处分身。除了用户与 Agent 的对话，还有 Agent 之间的对话、定时任务的消息、Team Engine 的周期性监控、来自 IM 的用户消息。幕后沉重的软件工程，都是为了让用户从一个干净的 UI 里浏览一组精心编排的信息源。

行业材料指向同一个方向。OpenAI Agents SDK 的官方文档强调 sandbox、workspace、handoff 和 tracing；AWS AgentCore 的官方发布把 Runtime、Memory、Identity、Gateway、Browser 列为企业级模块。它们共同传递一个信号：Agent 产品的重心正从「写提示词」转向「维护控制平面」。

承认 Agent Team 是一个运行时，会改变产品判断。新功能不能只靠提示词打补丁——它们需要运行时中的事件和可观测性；权限、运行时约束和记忆写入约束不能只依赖 Agent 自律——它们需要合适的软/硬门禁和拦截器。把多智能体当作运行时来维护，比当作提示词模板来维护重得多，但只有这样它才能可靠地服务真实工作。

## 5. 经验教训

### 5.1 多智能体是为了更可靠地完成复杂任务

多智能体的核心是结构。没有结构的多智能体只是更昂贵的并发；有结构的多智能体是一套可委托、可并行、可验证的执行系统。

所以判断一个**多智能体产品是否有价值**，不要看它能同时拉起多少个 Agent。要看它能否回答几个问题：为什么拆分、如何验证、何时停止、失败如何恢复、记忆如何管理。答案越清晰，多智能体越像生产系统；答案越含糊，它越像一个 demo 群聊。

### 5.2 团队的价值取决于复杂度，但 ROI 不能只看短期

Team 只是一个选项。任务越长、链条越深、风险越高、经验越可复用——Team 的收益越可能盖过成本；任务越短、风险越低、越确定，单个 Agent 或经典自动化越占优。我们不应鼓励用户「事事拉一个 Team」，而应帮他们判断什么时候值得协作、什么时候应该保持简单。

无论你选择 Team 还是单个 Agent 来执行，都仍然需要记忆、Skills 及类似机制，让 Agent 长期持续进步。即使 Team 用了更多 token 和更多时间，Agent 也应该带着更多经验和更多记忆离场。从长期看，一个更懂用户、更老练的 Agent 的成长，本身就应计入 ROI。因为一旦我们相信一个 Agent 拥有足够的记忆和 Skills，Team 就应该是这个 Agent 最省心的执行模式。

### 5.3 未来的 Agent 会更像一支长期共事的数字团队

沿着「Agent 间通信设计：Agent 与人权利对等」中的设计，未来的 Agent 产品将向人类和 Agent 同时开放完全对等的控制接口与数据流。人类将更多依赖一个管理面板来配置 Agent 的角色、能力和边界并分派任务，在关键节点上尊重人的裁决。而这个面板本身也可以由一个 Agent 来操控。整体运行时的样子可能更接近前文提到的低效 AI 聊天室。AI 能否完全接管管理和调度、让管理面板 / Team Engine 变得越来越轻——这仍然取决于更强的模型出现。

多智能体的存在，是为了让 AI 从「一次性工具」走向「长期伙伴」——从提升个体效率，走向把人类从执行的具体事务中解放出来。
