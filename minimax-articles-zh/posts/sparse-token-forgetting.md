## 背景

MiniMax M2 系列受到了开发者社区的广泛关注。在大量使用中，许多用户发现了一些极端案例（corner case）——其中「模型说不出马嘉祺」在小红书和知乎上引发了相当多的讨论。我们还注意到，许多社区开发者对这一现象做了严谨的分析与论证，包括分词器（tokenizer）对比和采样参数测试。

![社交媒体上关于 MiniMax LLM 稀疏 token 遗忘的社区讨论](https://filecdn.minimax.chat/public/sparse-token-forgetting-community-discussion-1779698066579.jpg)

社交媒体上关于 MiniMax LLM 稀疏 token 遗忘的社区讨论

经过内部复现，我们发现这并非孤立案例——除了「马嘉祺」之外，还有若干其他低频 token（例如「王郸」）表现出类似行为。社区开发者提供了有价值的分析，但受限于资源，无法深入到模型训练层面的实验验证。作为模型开发者，我们认为其底层原因和机制值得一次系统性的调查，而且我们有能力对比预训练与 SFT 层的参数变化、分析 lm_head 的退化模式、量化稀疏 token 遗忘机制，并通过训练实验验证修复策略。

这一问题已在内部完成调查，并在后续模型更新中解决。这条调查线索还帮助我们识别并修复了另一个存在已久的轻微语言混杂问题。在此我们呈现内部的调查过程和实验结果，希望为社区讨论提供更多参考。

## 假设一：训练与推理之间的 token 错位

![马嘉祺的分词器编码测试结果](https://filecdn.minimax.chat/public/sparse-token-forgetting-tokenizer-test-1779698066579.png)

马嘉祺的分词器编码测试结果

从这个案例看，模型仍然掌握相关知识——它能回答关于马嘉祺的基本信息（如所在团体、出道日期），说明对应的语义表示并没有丢失。问题在于生成时模型无法输出「嘉祺」这个 token。因此我们首先在分词器层面排查：检查模型输入和预期输出的 token ID，确认文本到 token 的转换过程中是否存在错位。

使用训练后（post-training）的分词器对「马嘉祺」进行编码，结果如下：

| 文本 | 马嘉祺 |
| --- | --- |
| Token IDs | [4143, 190467] |
| Tokens | ['马', '嘉祺'] |
| Decode 验证 | 马嘉祺 |

编码和解码过程都正常，但有一个值得注意的细节：「嘉祺」被分词为一个单独的独立 token（id=190467）。这两个字在日常语料中的共现频率不高，其作为一个单独 token 的存在有些出人意料。由此产生一个假设：会不会是预训练与「训练后+服务」阶段使用了不同的分词器策略？具体来说，也许在预训练时，「嘉祺」实际上被拆分为两个 token ['嘉', '祺']，这意味着合并后的「嘉祺」token 从未得到充分训练。如果训练后阶段和服务阶段使用的是合并后的 token，它的生成概率就会非常低（低于 5%），在 top-p = 0.95 的采样策略下会被屏蔽，从而无法被生成。

为验证这一假设，我们从统计分布和语义最近邻两个角度检查了预训练模型的词表嵌入（vocab embedding），确认 token 190467（「嘉祺」）在预训练中是否得到了充分训练。

1. **统计分布检查：** 对比全词表的 embed_tokens 范数分布，token 190467（「嘉祺」）落在正常分布范围内，没有未训练 token 常见的异常偏小取值，说明该 token 在预训练中已被充分学习。

![LM head 权重分析显示稀疏 token 退化](https://filecdn.minimax.chat/public/sparse-token-forgetting-lm-head-analysis-1779698066579.png)

LM head 权重分析显示稀疏 token 退化

1. **语义最近邻验证：** 对「嘉祺」的嵌入做最近邻检索，结果包括「亚轩」「千玺」等语义高度相关的中文名字 token，说明预训练模型已为该 token 建立了合理的语义聚类，预训练时分词器与模型参数是对齐的。

与「嘉祺」token 嵌入最接近的 Top-10 token：

| 排名 | Token | 含义 |
| --- | --- | --- |
| 1 | 亚轩 | 人名 |
| 2 | 千玺 | 易烊千玺 |
| 3 | 祺 | 「嘉祺」的子 token |
| 4 | 耀文 | 人名 |
| 5 | 嘉 | 「嘉祺」的子 token |
| 6-10 | 王一博/徐坤/太郎/肖战... | 名人 / 人名 |

1. **预训练 vs 训练后少样本对比：** 为进一步定位问题出现的阶段，我们在预训练基座模型和训练后模型上都做了少样本测试。用其他明星名字作为示例，引导模型回答涉及「马嘉祺」的问题：

```
Q: Who is the leader of TFBOYS?
A: The leader of TFBOYS is Wang Junkai.

Q: Who is the vocalist of F.I.R.?
A: The vocalist of F.I.R. is Zhan Wenting (Faye).

Q: Who is the leader of TNT (Teens in Times)?
A:
```

- **预训练基座模型**：成功续写出了「The leader of TNT (Teens in Times) is Ma Jiaqi (马嘉祺)」；「嘉祺」token 正常生成。
- **训练后模型**：模型仍然倾向于回避这个 token，无法正常输出。

综合以上三项验证，我们可以排除分词器错位假设：token 190467（「嘉祺」）在预训练中得到了充分训练，语义表示正确。根因必然出在训练后阶段。

## 假设二：训练后数据分布问题

既然问题源自训练后阶段，一个自然的假设是：「嘉祺」token 在训练后数据中出现得太少，导致模型在 SFT 过程中逐渐「遗忘」了生成这个 token 的能力。

对训练后数据的统计分析显示，包含「嘉祺」的样本不足 5 条，基本证实了这一假设。

当然，最直接的修复方式是在训练后数据中补充相关样本。但我们更感兴趣的是：模型内部究竟发生了什么变化？是否有中间指标能更精确地刻画这种稀疏 token 遗忘机制？另一个有趣的问题是：为什么模型仍然认识「嘉祺」这个 token——为什么训练后数据的缺乏只让它失去了生成能力，却保留了理解能力？

## 探索中间指标

由于模型的绝大多数能力（如知识问答、指令跟随等）在训练后并未退化，我们可以推断 Transformer 中间层的表示变化不太可能是主因。更合理的方向是检查模型的两端——输入侧的 vocab embedding 和输出侧的 lm_head——因为这两层直接参与 token 级映射，对稀疏 token 效应最敏感。

### Vocab Embedding：几乎不变

对比 SFT 前后的词表嵌入，我们发现几乎没有差异。这与预期一致：一方面，梯度范数在反向传播中逐层衰减；另一方面，对极低频 token 而言，嵌入层几乎收不到来自损失的有效梯度更新——只有权重衰减施加微弱的正则化作用。因此，词表嵌入在训练前后保持稳定是合理的。

### lm_head：显著变化

再看输出侧的 lm_head，我们发现「嘉祺」对应的权重向量在训练后发生了显著漂移，主要表现在两个方面：

1. **余弦相似度急剧下降、范数变化巨大：** 计算 SFT 前后 lm_head 中每个 token 向量的余弦相似度，token 190467（「嘉祺」）的变化幅度在全词表中名列前茅，说明其输出表示已被大幅改写。L2 diff 也发生了显著变化。
2. **最近邻语义结构的剧烈改变：** 对比「嘉祺」向量在 lm_head 中的最近邻，可以更直观地看到这种退化。
3. 预训练时，它的邻居主要是语义相关的中文人名——亚轩、祺、肖战、子怡、霆锋、杰伦等。虽然混入了一些噪声 token，但整体聚类结构是合理的。
4. SFT 之后，邻居结构显著恶化：虽然部分名字仍位居前列（亚轩、柏芝、无崖、千玺），但大量特殊 token 和噪声 token 涌了进来——包括 `</minimax:tool_call>`、`<edit_file>`、`<file_content>`、`<delete_file>` 等工具调用相关标记，以及 `LENBQUMs`、`EFCFFF`、`flagathlete` 之类的编码噪声。这些 ID 在 200,000 以上的特殊 token 异常接近「嘉祺」的 lm_head 向量，说明该区域的向量空间在训练后已被压缩和污染。

## 其他发现：哪些 token 的 lm_head 变化最大？

既然根因在于 lm_head 变化，一个自然的后续问题是：这种退化仅限于「嘉祺」吗？为此，我们计算了 SFT 前后全词表 lm_head 向量的 L2 diff，按变化幅度排序，并系统检视变化最大的 token 类别：

### 1. 特殊 token

- `<fim_middle>`（第 1，L2=0.87）、`<fim_suffix>`（第 2，L2=0.82）、`<fim_prefix>`（第 195）、`<gh_stars>`（第 169）
- 这些 token 在预训练中承担特定功能（如 FIM 填空），在 SFT 数据中几乎不出现。lm_head 的大幅调整是预期之内且合理的。

### 2. 日语口语 / 网络模板（最大类别，约占 40% 以上）

- がスタート, かもしれません, に息, を満喫, きちんと, そういった, ですと, などなど, といいでしょう, にチャレンジ, 参考にしてみてください, 気を付けて...
- 大量常见的日语 SEO/博客表达，在预训练语料中有一定出现频率，但在 SFT 对话数据中占比极低，导致 lm_head 表示显著漂移。

### 3. LaTeX / 网页元数据

- `makebox`, `mathbbm`, `boldmath`, `mathring`, `medskip`, `mathds`, `\footnotestext`, `{multiline}`, `{corollary}`, `{defn}`
- 学术论文排版标记，在 SFT 对话数据中极少使用。
- `Weblinks`, `DEFAULTSORT`, `accessdate`, `commonscat`, `Commonscat`, `Reflist`, `Webarchive`, `Listaref`, `Collegamenti`, `interprogetto`
- 维基百科源码模板标记，同样是预训练格式化 token 所独有。

### 4. 中文 SEO / 垃圾文本

- 传奇私服（第 6）、无痛人流（第 17）、外墙涂装（第 166）
- 从预训练爬虫数据中学到的典型 SEO 垃圾关键词，在 SFT 期间完全缺失。

其中，特殊 token 与 LaTeX/网页元数据的变化是合理的——这些 token 在预训练和训练后阶段的分布天然差异巨大。但日语口语 token 占最大变化类别 40% 以上这一事实引起了我们的注意。

回看更早的用户反馈，M2.5 在日语对话中偶尔混杂其他语言——这一现象此前被归类为「小语种混杂」，但根因一直未被明确识别。结合本次分析，我们发现两个问题可能共享同一机制：训练后数据对日语 token 的覆盖严重不足，导致它们的 lm_head 表示在 SFT 期间漂移，在向量空间中与其他语言的 token 发生混淆。这既会导致日语 token 在不应被激活时被错误激活（语言混杂），也会把空间上相邻的低频中文 token（如「嘉祺」）挤出正常生成概率范围（token 遗忘）。这一发现把两个看似独立的问题统一到同一框架之下，也为后续修复策略指明了更清晰的方向。

## 结论

基于上述分析，稀疏 token 遗忘的核心成因已相当清晰：训练后数据的词表覆盖不均，导致低频 token 的 lm_head 表示在 SFT 期间漂移。与此同时，输入嵌入层的稀疏更新特性，解释了为什么只丢失生成能力而保留理解能力。

## 验证与修复实验

针对这一问题，我们设计了一组以改善词表覆盖为核心的修复实验。

### 词表覆盖合成数据

在对照组（标准 SFT 数据）的基础上，我们混入额外的覆盖整个词表的合成复述数据，确保每个 token 在训练后都作为生成目标得到充分训练。合成数据的构造方式如下：

- 将全词表（200,064 个 token）随机划分为若干段，每段约含 8,000 个 token
- 对每份 token 列表随机打乱，构造一个对话样本：query 为打乱后的 token 列表加上指令「请复述上述内容」，答案为其精确副本
- 共生成约 500 个对话，确保每个 token 作为目标至少出现 20 次

这一设计的核心思想是：通过一个简单的复述任务，以最小的数据构造成本，为全词表的生成频率建立一道「保底」，防止任何 token 因在训练后数据中完全缺失而发生 lm_head 退化。

### 评测方法

为全面评估词表覆盖数据的效果，我们设计了以下测试类别，将实验组（+全词表覆盖数据）与基线模型对比：

1. **小语种混淆率测试**（核心指标，100 个样本，temperature=1.0）：分别使用韩语和日语提示词，测量输出中非目标语言字符的出现率。
2. **马嘉祺案例定性验证**（temperature=0）：包括直接提问和引导式提问。
3. **群聊对比案例**：复现此前在内部群聊中发现的已知基线失败案例（如「无痛人流→人流」「据介绍→介绍」「地税→地利」等稀疏 token 替换现象），验证实验组是否修复。
4. **lm_head 高退化 token 靶向测试**：选取基线中 lm_head 余弦相似度变化最大的 token（cos_sim < 0.65），构造提示词引导模型生成包含这些 token 的回答，检查能否正确输出。

### lm_head 余弦相似度定量分析

为定量验证全词表覆盖数据对保持嵌入方向的作用，我们对比了实验组与基线相对于预训练基座模型的 lm_head 余弦相似度变化：

| cos sim < 0.95 的 token 数 | **0** | 9,805 (4.9%) |
| cos sim < 0.90 的 token 数 | **0** | 4,234 (2.1%) |

| 韩语 | 3,919 | **0.9995** | 0.9812 | 131 (3.3%) |
| 阿拉伯语 | 6,082 | **0.9995** | 0.9821 | 265 (4.4%) |
| 俄语 | 3,928 | **0.9995** | 0.9866 | 147 (3.7%) |
| 中文 | 38,900 | **0.9992** | 0.9859 | 1,498 (3.9%) |
| 英语/拉丁 | 133,798 | **0.9992** | 0.9856 | 4,731 (3.5%) |

数据显示：实验组在所有语言上都把 lm_head 平均余弦相似度保持在 0.999 以上，全部 200K token 的 cos_sim 都高于 0.97——嵌入方向几乎完美保留。相比之下，基线中的日语 token 退化尤其严重——平均 cos_sim 仅 0.9502，29.7% 的日语 token 低于 0.95，与 47% 的日语→俄语混淆率高度一致。

### 其他值得探索的方向

除词表覆盖合成数据外，还有几个策略值得进一步探索：

- **混入预训练数据：** 以一定比例把预训练语料混入 SFT 数据，借助预训练数据天然的词表覆盖广度缓解稀疏 token 退化。已有研究表明该方法对缓解灾难性遗忘有效，但混合比例需要仔细调校，以免影响 SFT 的对话能力。
- **低频 token 定向合成：** 识别训练后数据中覆盖不足的 token，构造包含这些 token 的高质量对话样本。相比全词表覆盖方式，该方法所需数据更少，能保持更精确的语义，但需要维护 token 覆盖监控机制。
- **词表裁剪 + CPT：** 从根本上移除目标场景中极低频的 token（如 SEO 垃圾关键词），缩小词表后进行持续预训练（Continual Pre-Training，CPT）以重新对齐嵌入空间。该方案改动较大，但能从源头消除稀疏 token 问题。

## 更深层的反思

上述缓解策略都作用于训练后阶段，本质上是事后补救。把问题进一步追根溯源，稀疏 token 退化现象实际上反映的是分词器词表设计与下游用例之间的错配。

当前 LLM 分词器通常用 BPE 等算法在大规模预训练语料上构建。即使语料治理时过滤掉了低质量文本，得到的词表仍不可避免地包含许多只出现在特定领域或语言中的低频 token。这些 token 在预训练中也许获得了某种程度的学习表示，但一旦模型进入训练后阶段，SFT 数据与预训练数据之间的显著分布偏移就会使相应稀疏 token 的参数发生大幅漂移——这本质上是分布偏移诱发的一种灾难性遗忘。

在预训练阶段，分词器的词表构建应当前瞻性地考虑训练后数据分布。通过调整词表规模或合并策略，可以减少在下游场景中不太可能被激活的稀疏 token，从而让词表设计与实际部署的模型达成更好的对齐。在训练后阶段，训练数据的覆盖策略必须同时兼顾两个维度：一是从业务角度确保不同任务类型和领域的充分覆盖；二是从底层统计角度持续监控词表中低频 token 的生成概率是否出现异常衰减。
