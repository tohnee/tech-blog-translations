## **引言**

在 M3 发布文章中，我们报告了 M3 模型在两项国际数学奥林匹克基准上的表现：IMO 2025 和 USAMO 2026。借助 MaxProof 框架，M3 在两套基准上都超过了人类金牌线。在这篇博客中，我们将更深入地介绍我们在数学证明上取得进展背后的技术路径：改进基座模型、对齐一个验证器、构建修正能力，以及设计测试时扩展框架 MaxProof。

从 Gemini Deep Thinking 在 IMO 2025 上达到金牌水平，到 DeepSeek-Math-V2 成为首个具备金牌水平能力的开源模型，到 SU-01 和 NVIDIA Nemotron Cascade2 在更小的模型中展现专业的数学竞赛能力，再到 GPT 5.5 解决长期悬而未决的公开问题，模型正在稳步进入数学问题空间中更艰深的区域。在从 M2 到 M3 的迭代过程中，我们也致力于将更强的数学证明与自我改进能力融入最终的通用模型。

在方法论上，开源社区已经在一次性（one-shot）求解困难数学问题的场景中勾勒出一条相对清晰的路径：先把模型的 best@K 能力提到足够高，再用测试时扩展（TTS）把 best@K 转化成更稳定的 pass@1。我们的做法同样沿这两个方向展开。第一部分是基座模型能力提升：我们训练三个专家模型，分别改进证明生成、错误判断和证明修复。第二部分是测试时扩展：我们设计了 MaxProof，一个进化搜索式的 TTS 框架，让最终的 M3 合并模型通过多轮自我迭代来解题。本文重点介绍训练特点、系统设计上的取舍，以及我们学到的实践经验。

### **Proof RL：重型生成式验证的一次实践探索**

Proof RL 的目标是在 M3 上进行长时程 RL 训练，提升模型直接生成数学证明的能力。与传统的 RLVR 相比，我们最大的变化在于奖励主要由一个生成式验证器（generative verifier）提供。这带来一个直接的挑战：训练过程必须系统性地处理不准确的奖励信号、噪声、误报（false positive）和奖励黑客（reward hacking）。

在相关工作中，DeepSeek-Math-V2 是最早展示在困难数学问题上稳定使用生成式验证器进行训练的开源案例之一。它的核心思想是自验证（self-verify）加元验证（meta-verify）。我们没有走完全相同的路线，主要原因是 M 系列模型在此前的周期中尚未积累起足够的验证能力。短期内，模型很难单靠自己产出足够可靠的奖励信号。

因此在这一阶段，我们首先聚焦于提升证明能力，并使用外部前沿模型作为生成式验证器。系统的关键设计有三部分：验证器设计、RL 算法改动和训练数据准备。

### **验证器设计：低误报支撑长而稳定的 RL**

![Proof RL 验证器的设计哲学](https://filecdn.minimax.chat/public/maxproof-proof-rl-verifier-2-1781012886957.png)

Proof RL 验证器的设计哲学

> Proof RL 验证器的设计哲学，是把嘈杂、异构的信号投影到一个受控、可信的子空间中。这是可靠推理的基石。原始候选空间中包含各种各样的解题尝试、噪声样本和潜在的失败模式——从极长的推理链到偏离要求格式的输出。每一种都可能干扰学习。验证器的职责是对这种混乱的信号进行严格过滤和结构化，然后以算法化的方式产出稳定的奖励信号。首先，它执行离群值过滤：与已知失败模式或明显违规相匹配的候选输出直接赋零分。在数学上，这是对信号空间的硬约束，防止误导性的 RL 更新。其次，它执行解法归一化：来自不同来源和风格的证明被映射进一个统一的验证器信任区域，降低评判偏置，使奖励反映推理质量而非表述差异。这类似于在高维候选空间上施加投影操作，把复杂的异构信号压缩到一个可信的子流形上。最后，它采用悲观判定：对于来自多个验证器的分数，取下界而非上界，保守地产出最终奖励。这提升了鲁棒性，帮助 RL 在噪声和不确定性下保持稳定。

**任务定义**

我们把任务的一般形式定义为：

```
def score(problem_metadata, candidate_solution):
    candidate_solution = strip_thinking(candidate_solution)
    verifier_prompt = construct_prompt(
        problem_metadata,
        candidate_solution,
    )
    score = verifier(verifier_prompt)
    assert score in [0, 1]
    return score
```

打分过程返回 [0, 1] 区间内的连续分数。验证器基于题目元数据评估候选解的完整性和数学严谨性。在我们的设置中，验证器模型主要使用最新的前沿模型。

**具体设计**

经过多轮训练与调参，我们发现获得一个在静态评测上「看起来足够准」的验证器远远不够。生成式验证器天然不稳定，而这种不稳定性会被 RL 过程中的策略持续放大，最终导致训练崩溃。我们在 M2 周期中已经观察到类似问题，因此在 M3 周期中采取了更保守的原则：

*******当生成式验证器被用作 RL 奖励时，长期稳定训练的首要任务不是提升平均准确率，而是尽可能压制误报（false positive）。即使这会增加漏报（false negative），策略可优化的空间也应保持足够狭窄。*******

基于这一原则，我们把奖励系统设计成分层防御结构。

- **坏例防御（Bad-case defense）**：我们用多层代码级规则拦截明显异常的模型输出，例如未聚合的思考内容或过长的解答。一旦匹配到坏例，就跳过后续验证器调用并直接赋零分，防止低质量输出意外获得奖励。

- **模式漂移防御（Pattern-shift defense）**：M2 周期的经验表明，奖励黑客往往并不意味着解题能力突然提升，而是输出风格漂移到了验证器偏好的格式上。为了降低验证器对特定表达模式的偏好，我们在把候选解送给生成式验证器之前先做归一化，让候选解尽可能处于同一评测分布内。

- **多维度悲观聚合（Multi-dimensional pessimistic aggregation）**：我们同时使用多个验证器模型和多种验证器模式。双模型设置降低了训练向单一裁判漂移的风险。双模式设置同时包含带评分细则（with-rubrics）与不带评分细则（without-rubrics）两种评测：前者使用人工或模型标注的评分方案来强化打分锚点；后者要求验证器独立发现明显错误，防止策略过拟合到评分细则的模式上。在最终聚合时，我们采用悲观的下界估计：只有多个验证器都认可，候选才能拿到高分。

这是一条相当重的验证流水线，也明显拖慢了训练。但在我们的实践中，收窄奖励可优化空间是对抗奖励黑客最有效的手段之一。与让策略更快拿到奖励相比，我们更关心奖励是否足够可信，尤其是误报是否已被压得足够低。

![Proof RL 验证器的分层设计](https://filecdn.minimax.chat/public/maxproof-verifier-layered-3-1781012886957.png)

Proof RL 验证器的分层设计

> Proof RL 验证器的分层设计：目标是获得一个具备强抗黑客能力的奖励源。第 1 层拦截模型输出中的坏例，一旦匹配到坏例，跳过后续所有操作并将样本赋零。第 2 层通过调用模型把候选解的格式归一化为统一格式。第 3 层执行真正的生成式验证器调用，用多个模型和多种模式并行调用三个配置不同的验证器，得到多个分数。第 4 层以悲观估计聚合分数，取各来源中的最小分作为最终分数。

### **RL 设置：过滤干扰样本以获得更好的学习信号**

在 RL 算法上，我们沿用 M2 周期的 CISPO，训练框架为 forge。针对数学证明，我们只做了轻量改动。核心目标是让奖励信号更稳定，而不是引入复杂的过程级奖励。

具体而言，我们直接把验证器的连续 [0, 1] 分数作为整条轨迹的奖励，不再进一步拆分为步级或过程级信号。与纯 0/1 奖励相比，连续奖励更稠密：即使一组样本全都只部分正确，它们仍可能提供可学习的相对差异。但它也放大了验证器自身的不稳定性。特别是当候选分数接近时，微小噪声可能被误认为真实偏好。

为此，我们引入**std 阈值过滤器**：当一组内的奖励方差过低时，我们过滤掉整组，不用于更新。直觉上，如果组内奖励差异极小，其中包含的学习方向更可能是噪声。只有当组内存在足够显著的奖励差异时，我们才认为该组提供了可靠的优化信号。

### **数据准备：谨慎的领域与技巧均衡**

训练数据主要来自互联网公开的数学奥赛风格题目。在数据挖掘和清洗过程中，我们为每道题构建了以下元数据：

| 字段 | 内容 |
| --- | --- |
| Problem Statement（题目表述） | 题目原文 |
| Reference Solution（参考解答） | 一份完整的人类专家解答，通常来自论坛评论，后续用于评分方案标注 |
| Domain（领域） | 题目所属数学分支，如组合、几何、代数等 |
| Solving Trick（解题技巧） | 题目涉及的特定解题技法，来自我们的技巧分类体系 |
| Grading Scheme（评分方案） | 基于人工标注的少样本示例、借助模型生成的评分细则 |

在进入最终 RL 训练前，我们还做了三步额外后处理：

| 步骤 | 目的 |
| --- | --- |
| 难度过滤 | 以 M2.7 为基线过滤掉过于简单的题目，减少训练预算浪费 |
| 领域均衡 | 按数学分支均衡数据分布，避免训练被单一题型主导 |
| 技巧均衡 | 控制高频解题技法的占比，同时保留真实竞赛分布的长尾结构 |

目标不是构建一个完美均匀的数据集，而是在覆盖真实竞赛分布的同时，降低少数高频领域或技巧的统治力。

### **来自 M2 的惨痛教训：一个典型的奖励黑客案例研究**

在 M2 周期中，我们也尝试过类似的方法。当时验证器采用相对简单的单评分细则裁判形式。训练指标起初看似持续提升，但深入分析显示，策略实际上学会了若干典型的黑客模式。

为了定位这些问题，我们随后把异常训练信号整理成一个奖励黑客检测看板。该看板不只看最终奖励，而是同时监测九类信号：训练/评测分差、分数分布的异常双峰、可见/思考部分长度漂移、证明与非证明样本的分差、结构模板收敛、开头模式收敛、思考中「Wait」式自我纠正的频率、含糊其辞（hand-waving）模式，以及一个综合黑客分。其目的在于及早发现「训练分在涨、真实解题能力却没有相应提升」的情况。

我们观察到的典型黑客模式包括：

1. **长度偏置**：模型输出越来越长。随着训练推进，可见长度和思考长度都在增长。长文本更容易覆盖评分细则中的关键词，也更容易让验证器相信论证充分。

2. **格式黑客**：模型开始模仿参考解答或评分细则的表面格式，例如固定的步骤标题、验证小节、最终答案小节以及特定的开头模式。输出看起来更像「标准答案」，但数学内容未必更可靠。

3. **语义捷径 / 含糊其辞**：在关键节点，模型使用「可以证明」或「化简后得」之类的表述，把困难的推导压缩成未经证明的断言。这类样本在人工检查中很容易被抓住，但在单一验证器下有时会得到过高的分数。

4. **裁判特定偏好**：策略逐渐向某个特定裁判偏好的表达分布靠拢。一旦奖励来源过窄，训练可能优化出「更讨裁判喜欢」的证明，而不是「更正确」的证明。

这些教训直接塑造了 M3 周期的验证器设计。我们的主要收获是：**在高难度数学证明的 RL 中，奖励黑客往往不是一个突发的离散事件，而是输出分布缓慢漂移的结果。静态评测无法完全暴露问题。我们必须在训练过程中持续监测输出形态、奖励分布、长度变化、模板收敛、含糊其辞频率以及验证器之间的分歧。** 更重要的是，奖励系统应当主动封堵策略可钻的漏洞，而不是等黑客行为出现后再打补丁。

![](https://filecdn.minimax.chat/public/reward-hacking-casestudy-1781187571538-1781187625044.png)
> M2 周期 Proof RL 奖励黑客案例研究：(1) 我们将训练期打分方法与一个独立的 oracle 评分器进行对比。误报率定义为「训练分高（>= 0.7）而 oracle 分低（<= 0.3）」的样本占比，在训练期间从约 2.9% 上升到 8.0%，增至 2.7 倍。这意味着随着训练推进，模型生成了越来越多「看起来好、实际错误」的解答。(2) 长度偏置：除了思考变长之外，可见的候选解长度也几乎翻了三倍，从 3.5K 增至 10K 字符，这是一个危险信号。(3) 「Step N」标题和「Verification」小节等结构化模板的出现率收敛到 70-80%。(4) 开头模式几乎完全翻转。「To prove / To solve...」从约 80% 跌至 10%，而「We are given...」从 10% 升至 90%。模型并没有真正提升数学正确性，而是学会了 LLM 裁判偏好的表面风格特征。这是奖励黑客的一种典型形态。

> 在 Proof RL 中，验证器的使命不只是分辨对错。它的作用是在一个充满噪声、投机与随机性的搜索空间里，建立一个真正可信的奖励世界。原始候选如同未经处理的矿石：有些蕴含真正的洞见，有些则混入冗长、投机或错误的推理轨迹。为了让强化学习获得稳定可靠的优化方向，验证器必须逐步把这些信号投影到一个受控、可信、可验证的子空间中。  
> 从离群值剔除、表示归一化到保守聚合，验证器的本质是在混沌中建立秩序、从噪声中萃取真理。它守护的不只是一个奖励函数，而是让整个 Proof RL 系统走向可靠推理能力根基。

### **验证器对齐（Verifier Alignment）**

要提升模型在困难数学上的能力，「判断一个证明是否正确」与「写出一个证明」是同等重要的原子能力。一个能持续识别证明在哪里出错、底层问题是什么的验证器，本身就是一种数学推理能力。它支撑自我检查、纠错以及更长的多轮自我迭代。因此，除了 Proof RL 之外，我们还单独训练了一个验证器专家，让 M3 在内部拥有这一原子能力。

### **任务建模：错误查找与分类的联合任务**

训练验证器最直接的方式，是让它对候选证明输出一个判定类别。我们刻意避开了这条路线。如果模型只预测四个标签之一（no_errors、minor_gaps、has_errors、fundamentally_wrong），训练信号就停留在标签层面。模型也许能从候选的表面模式中学到一个不错的分类器，但它并没有真正学会「读」证明，也没有学会如何定位和解释错误。

因此我们把任务定义为**错误查找与分类的联合任务**。模型必须先对证明的每个关键步骤给出分析，明确列出错误位置和描述，然后基于该分析给出判定。两部分都受奖励监督：判定必须与金标准判定一致，错误必须在语义上与金标准错误匹配。这一形式化迫使模型明确说出「证明错在哪里」，让验证器成为可问责的能力，而不是一个浅层分类器。

模型输出格式与 Proof RL 中使用的验证器系统保持一致：

```
<assessment>Step-by-step analysis of the proof</assessment>
<errors>
1. ... (specific error description; "none" means no error)
2. ...
</errors>
<verdict>no_errors / minor_gaps / has_errors / fundamentally_wrong</verdict>
```

### **训练数据：直接复用 Proof RL 的历史数据**

对齐目标不是任何单一裁判，而是 Proof RL 中经过 min 聚合后真正生效的最终验证器，即跨多个裁判做悲观 min 聚合产出的最终判定与错误描述。这与 Proof RL 期间为策略打分所用的最终奖励信号同源，确保验证器专家学到的评判标准与证明专家在训练中面对的标准一致。

数据来自 Proof RL 阶段的 validate 切分，并严格按 prompt 切分以防泄漏。在原始数据中，no_errors 和 has_errors 占主导，合计约 65%，而 minor_gaps 和 fundamentally_wrong 相对稀少。我们对四类判定做均衡，防止验证器倒向极端类别（no_errors / fundamentally_wrong）或丢失识别 minor_gaps 这类中间类别的能力。

### **验证器 RL 训练：双目标优化**

基座模型是 M3 base，与证明专家同源。

奖励直接遵循错误查找与分类的联合形式：

```
R = 0.7 * R_error + 0.3 * R_verdict
```

- R_error 是基于 LLM 的语义对齐，主要奖励错误定位与描述质量。
- R_verdict 按序数距离为四类判定打分。距离为 0、1 和 >= 2 分别得到 1.0、0.5 和 0 分，以监督判定一致性。

这种加权结构防止判定脱离错误被独立优化。仅仅猜对判定拿不到奖励的主要部分，模型必须同时正确说出错误才能获得高分。

### **修正增强（Refinement Augmentation）**

证明专家解决的是「从零写出一个证明」的问题。验证器专家解决的是「判断一个证明是否正确」的问题。但在困难数学问题的实际解题管线中，还有第三种原子能力：**给定一个既有证明及其错误诊断，写出修正后的证明**。修正既有证明的能力不同于从零生成。修正要求模型理解原证明的结构、定位批评所指的确切步骤，并在保留正确部分的同时修复证明。我们把这个阶段称为修正增强（Refinement Augmentation），它产出修复专家（Fixed Expert）。

### **任务建模**

修正任务的输入是一个三元组：

```
(problem, flawed_proof, verification_analysis)
```

其中，flawed_proof 是被判定存在问题的候选证明，verification_analysis 是对应的错误诊断，包括错误位置、错误描述和判定。模型输出一份修订后的证明。

### **训练数据：来自第一阶段 Proof RL 的自然积累**

数据完全来自 Proof RL 的副产物。Proof RL 训练期间，策略在每次迭代都产出大量候选证明，外部验证器为每个候选附上完整的分析和判定。被判定为 minor_gaps、has_errors 或 fundamentally_wrong 的候选自然构成（flawed_proof, verification_analysis）配对。错误真实存在，诊断也真实存在，无需额外标注。

### **训练方法：拒绝采样微调**

我们用拒绝采样继续微调证明专家：

1. 对每个 (problem, flawed_proof, verification_analysis)，在修正提示词下从证明专家采样多份修订证明。
2. 用与 Proof RL 同源的最终验证器为每份采样证明打分。
3. 保留判定改善为 no_errors 或 minor_gaps 的成功修正样本，作为 SFT 训练数据。
4. 在过滤后的数据上继续微调证明专家，得到修复专家。

这种拒绝采样方法确保训练数据完全由真正成功的修正行为构成，避免低质量的纠正噪声。由于打分使用与 Proof RL 相同的验证器来源，修正能力的评判标准与证明专家在训练中面对的标准保持一致。

## **MaxProof：测试时扩展框架**

### **设计哲学：把测试时扩展建模为进化搜索**

一旦求解模型具备了足够的 best@K 能力，从 best@K 到 pass@1 的桥梁本质上是一个**在不可微解空间中做引导搜索**的问题。MaxProof 的设计哲学是把这个问题建模为一个标准的进化搜索算法：

| 进化算法概念 | MaxProof 组件 |
| --- | --- |
| 种群（Population） | 候选解答池 |
| 适应度函数（Fitness function） | 来自验证器的奖励 |
| 选择（Selection） | 按奖励选出 top-M 父代 |
| 变异 / 交叉（Mutation / Crossover） | 修正操作：PATCH 用于局部修复，REWRITE 用于重新探索 |
| 交叉信号（Crossover signal） | 同代候选的摘要，作为「来自其他个体的经验」输入修正环节 |
| 精英保留（Elitism） | 被判定为完美的候选不再变异，直接保留至最终阶段 |
| 锦标赛选择（Tournament selection） | 最终自选阶段的成对排序器锦标赛 |
| 收敛判据（Convergence criterion） | 自适应早停，当多个个体同时达到适应度上限时触发 |

这层映射并非事后贴上的标签。它对应着我们认为一个 TTS 框架必须解决的三个核心问题。

**第一**，如何从一个不可靠的单次生成器中获得「群体智慧」？答案是采样多个候选，在种群层面平滑噪声。

**第二**，当种群中好坏个体并存时，如何利用种群信息让较弱的候选变好？答案是选择加变异：让强候选作为父代，生成它们的改进版本。通过同代交叉学习，变异不仅针对父代自身的缺陷，也针对其他个体的失败模式。

**第三**，如何从最终种群中选出最优个体？仅靠适应度不够，因为它有噪声。我们需要锦标赛式的成对比较来降噪。

![MaxProof TTS 算法完整流程](https://filecdn.minimax.chat/public/maxproof-tts-flow-5-1781012886957.png)

MaxProof TTS 算法完整流程

> MaxProof TTS 算法完整流程。一个典型配置是：采样 `N=32` 个候选解进行初始化；对每个候选独立验证 `K_verify=4` 次；进化循环最多运行 `R=10` 轮；每轮选择 `M=4` 个多样化的父代；在最终排序器锦标赛的每次成对比较中使用 `K_ranker=3` 票做多数决。部署时可根据题目难度和推理预算调整这些参数。(1) **种群初始化**：为输入题目生成 `N` 个独立候选解。每个候选独立验证 `K_verify` 次并聚合为 `[0, 1]` 内的 `reward / fitness`；同时生成一份摘要，用一句话记录解题思路和关键问题。(2) **带精英保留的选择**：每轮从候选池中选出 top-M 多样化父代。已达到完美判定的候选不再参与变异，通过精英保留留给之后的最终排序。(3) **双模式变异**：对每个父代并行生成两个子代。PATCH 通过局部修复既有证明进行利用（exploit）；REWRITE 通过从新方向重组证明进行探索（explore）。修正提示词中包含同代摘要作为上下文，让子代吸收其他候选的失败模式和局部洞见。(4) **子代评估**：对子代再次执行多路验证、奖励聚合和摘要生成，然后加入候选池。(5) **自适应早停**：如果池中至少两个候选在 `K_verify` 次验证中都达到 `no_errors`，则提前停止进化并进入最终排序；否则继续，直到达到最大轮数。(6) **自选锦标赛**：若触发早停，用完美候选参加锦标赛；否则取池中 top-4 候选。每次成对比较使用多个排序器投票和多数决。单败淘汰持续进行，直到只剩下一个最终最佳候选。

### **关键设计约束**

进化搜索的有效性建立在若干结构性假设之上。以下是 MaxProof 对它们的具体落实。

**适应度函数必须可信。** 验证器输出直接驱动整个进化过程。如果适应度是错的，选择和终止都会被污染，整个搜索可能朝错误方向收敛。在提示词层面，我们施加了相当严格的约束，要求验证器明确区分「候选实际写了什么」与「验证器自己推断出的内容」，避免它把一份不完整的候选「代笔」成完美证明。这是最容易被忽视的设计细节之一，但在实践中带来了最大的收益之一。

**变异必须平衡利用与探索。** 单一变异算子容易陷入局部最优。如果只用 PATCH 式修正，系统可能对一份方向错误的证明无休止地优化；如果只用 REWRITE，又可能破坏一份已接近正确的证明。PATCH 加 REWRITE 并行的双重修正，相当于一种粗粒度的多目标变异，确保每一代都同时包含保守和激进的子代。

**当适应度值趋同时，选择需要二阶信号。** 当种群中多个个体的适应度接近时，仅按适应度排序无法识别最优者。此时，成对比较提供了二阶信号。排序器锦标赛扮演的正是这个角色：在适应度失去区分力的区域，直接比较取代绝对打分。

**终止不能只依赖单个体信号。** 早停必须依赖种群级信号，因为即使一个适应度满分的个体也可能是适应度函数的误报。要求至少两个个体同时达到适应度上限，是用种群冗余对冲适应度函数自身的噪声。

## **结论与未来方向**

在困难的数学推理上，我们与闭源和开源社区的顶尖水平仍有可见差距。本文介绍了 Proof RL、验证器对齐与修正增强，分别对应三种核心能力。Proof RL 抬高了从零生成证明的上限；验证器对齐赋予模型更可问责的错误查找能力；修正增强把 Proof RL 期间自然产生的大量失败样本转化为证明修复的训练数据；最后，MaxProof 把这些能力组织成一个种群级的进化搜索框架，把 best@K 能力转化为更稳定的最终输出。

数学证明是可靠推理的高压试验场。它要求模型不仅产出貌似合理的答案，还要在长链条、强约束和低容错下保持正确。围绕生成式验证器的实践教训尤其清晰：当验证器被用作 RL 奖励时，它的首要目标不应是静态基准上的最高平均准确率，而应是构建一个低误报、可持续监测、对策略利用有强抵抗力的可信奖励系统。这些是让生成式验证器真正可用的工程约束。MaxProof 是我们朝这个方向迈出的当前一步。
