# 所有代码皆垃圾（除了我的）

> 演讲者：Lauren Tan（SpaceXSI 首席工程师） · AI Engineer Code Summit 2026 · 2026-11-14 · [视频](https://www.youtube.com/watch?v=O_zcc6Xl12g)

**[00:12]** 好。呃，再说一次，我叫 Potato（土豆），在 SpaceXSI 做「Grok Bot」。能请大家快速举个手吗？你们有多少人看过别人写的代码，然后觉得那简直是一堆胡言乱语？我也是。但今天我要说服你们：你可以把那堆胡言乱语变成金子。上个月我干了件疯事，往生产环境发了 3000 个 PR（拉取请求）。在智能体（agent）出现之前，除了极个别情况，我们其实不太在意规模。在我上一家公司，我们管这种人叫「编程机器」。比如 Bret Taylor，一个周末就把 Google Maps 整个重写了。那种驱动力爆棚的产品工程师。现在有了智能体，人人都能当「编程机器」。我的论点是：软件工程师的工作，乃至作为工程师的本质，在于懂得如何在把生产力大幅提升的同时，维持甚至提高代码的质量。

**[01:22]** 要做到这一点，有人喜欢把它叫做「软件工厂」。但我喜欢简单一点，我把它看成一个信任问题。这不是盲目信任，而是投资智能体所处的环境，好让你能信任它们会做正确的事。走到这一步要花很多功夫，我用了六个月才到能发出几千个 PR 的程度，其中很多是我睡觉的时候发的。但这件事肯定是可行的，而且你会比我快得多。所以，我们先从如何把置信度从低水平提升到高水平说起。

**[02:03]** 这个倒金字塔，是我用来思考应该把时间花在智能体环境哪一层的方式。最下面两层是强制项，这样才能确保被使用的是你自己的代码。比如良好的 API 设计、架构、代码重组，或者使用 lint 规则、类型系统、断言，以及不同类型的测试。你可以把这两层结合起来，限制智能体能做什么，并默认迫使它们做正确的事。

**[02:32]** 验证，无论是运行时验证还是形式化验证，都是发现错误、检查系统中你希望维持的性质与不变量的绝佳工具，也能帮你确认智能体是否理解了你的目标和意图。最后，你还要加上一层说明性文字：规则、技能、AGENTS.md 文件，以及任何需要人类判断的东西。但先从代码库说起。智能体的输出基于它的输入产生，所以输入的质量至关重要；而巧的是，你的代码库正是其中最大的输入之一。因此，每当你调试智能体时，都要想一想如何把它变成一项必然执行的检查，而不是往规则或 AGENTS.md 文件里再加一行——因为写在代码里更可迭代，也让你更信任它。我喜欢用的类比是：代码库有点像一座花园。你知道，以前代码是一次几个 PR 地过来的。我记得 2024 年去上班，评审同事写的三个 PR。今天，这个数字已经接近 300。

**[03:47]** 所以，现在每个工程师都相当于带着几百甚至几千个智能体的团队，代码来得太快，看起来像一股连续的流，感觉像活物一样有机。在这个类比里，你的代码库、你施加的约束、你设置的防护措施，是智能体所写的新代码生长其间的坚实基础，就像这张图里的建筑。于是，从很多方面说，软件工程师的工作已经变得有点像园艺。

**[04:24]** 既然代码是智能体最大的输入，这就意味着任何替代方案、坏模式、废弃代码或技术债，现在都很可能被下一个智能体照着抄，因为它们在代码库里看起来就像被认可的范式。这就像花园里长出了杂草或害虫，等你发现时已经蔓延得到处都是。所以，你要尽可能让代码库保持干净，让智能体总是抄到好的东西。

**[04:57]** 好，我们来看一些真实世界的例子。Dune 是我们为 Grok Bot 创建的客户端框架，用来实现这种「有机工程」的理念。从技术角度讲它其实没什么意思，你可以把 Dune 大致看成 Electron 应用版的 Next.js。但 Dune 有意思的地方在于，它内置了大量限制和审计规则，我们把构建桌面应用时学到的很多教训都编码进去了。

**[05:26]** 其中一条教训是：任何在使用时需要精确拿捏的东西，往往都会带来混乱。最经典的例子就是 React 里的 useEffect，对吧？它有用，但经常被误用。有人开玩笑说，用 useEffect 得有博士学位。换句话说，要用对确实需要很高的精确度。而智能体并不擅长用它。所以我们的做法是在产品代码里完全封禁它，只允许在 Dune API 内部的有限区域使用。

**[06:02]** 实际上，这个问题已经被彻底消除了，我们在代码评审时再也不用盯着它。我们用的另一个有意思的模式，是通过文件夹结构提供上下文。我们在 Cursor——一个基于 Electron 的应用——里看到的一种有缺陷的模式是：智能体经常把主线程代码导入到渲染线程，导致任务又长又慢。所以在 Grok Bot 和 Dune 应用里，我们把这件事做得非常规范：我们有两个主文件夹，分别叫「Electron renderer」和「Electron main」，两者之间的文件导入会被依赖关系解析器和 lint 规则拦截。再说一次，这些都是简单的设置规则，但它们意味着我们在评审代码时少了一件要操心、要考虑的事。

**[06:56]** 我注意到的另一件令人意外的事，是智能体对 Markdown 的使用。比如文档、代码注释、规则或技能，它们把这些地方当作给「不做正确的事」找理由的场所。或者，不知道你们见没见过这种情况：你随手做的一处小修正，它们会极其当真，把它当成不可打破的规则。再举一个 Cursor 里的例子。智能体喜欢用各种定时器，比如 setTimeout、requestAnimationFrame 和 requestIdleCallback。它们把这些当作快速修复手段，因为它们试图化解 VS Code 的命令式风格与 React 的声明式风格之间的架构冲突。

**[07:44]** 结果，我们对结构的选择让客户端和智能体的性能都变得差了很多。如果你做过 JavaScript 性能优化，就会知道：快速创建和销毁大量定时器会造成大量垃圾堆积，带来很多延迟和卡顿。但最糟的是，智能体写了大量代码注释——就是这里标红的部分——来为这种权宜之计辩护。不知不觉间，定时器就蔓延到各处，应用的性能大受影响。

**[08:20]** 如今在 Grok Bot，我们吸取了教训，决定屏蔽 99% 的注释，因为它们太容易过时了。反正人类也懒得去读注释。再说一遍，这给了智能体一条逃生通道，让它可以为「因为难所以不做正确的事」找理由。注释最糟糕的地方在于它不可强制执行。所以，那些看似出于好意的东西——比如「我要告诉下一个智能体别这么干」——最终从来都不是你能信任的东西。所以在「Grok Bot」和「Dune」里，我们现在有 lint 规则，会给出非常有用的错误信息，告诉智能体去修根本原因和真正的问题，而不是只做临时修补。我们的一般原则是：每次调试智能体，都要把它变成这类必然检查之一，或者去思考如何通过更好的 API 设计或更好的工程，在代码里彻底消除这个问题。这样做个几次，你会发现代码评审时要找的东西变少了。到某个时刻，你会意识到已经没什么可评审的了。

**[09:34]** 你完全可以让智能体自己合并它们的大部分 PR。好，接着换个话题：验证是让智能体更独立、也让我们对它们的工作更有信心的一个非常重要的部分。我们的代码评审流程现在已经被简化为：直接看验证材料。比如视频、截图、示意图和形式化验证。最简单的例子是运行时验证，说白了就是给你的智能体一个自己运行代码的办法，并让它用上人类开发者也在用的调试工具，比如 Chrome DevTools 协议。在我们的验证技能里，有个东西叫「功能地图」。它很像从用户视角看到的、你应用里所有可用功能的站点地图。有了它，当你说「左边侧栏那个东西」时，智能体不用猜，它提供的是一套共同的词汇。

**[10:37]** 我们还在这些技能里用了自定义命令行界面（CLI），这样智能体每次都能复用同一套命令接口和操作，减少 token 消耗，也让它们可测试。最近我们还开始研究形式化验证。我们现在用 TLA+ 对关键用户流程做一些模型检验，比如跨多设备、多平台的通知。我们也用 Lean 来验证某些算法。比如我们自己写了一个虚拟化库，就用 Lean 检查闪烁或抖动问题。是的，总体上我们还在试验这种方法。它看起来非常有前景。我们已经用形式化验证找出了不少错误。

**[11:25]** 但它肯定不是灵丹妙药，我们只把它当作另一个工具，智能体环境里多加的一层。这段视频很短，不过还有一件我们开始研究的事，就是对用户界面做基于属性的测试。我们用的是一个叫 Bombadil 的库。它也已经帮我们发现了一些界面错误。嗯，往大处看，六个月前我看到 Cindy 发的一条推文，她说自己没法信任智能体，因为总有一些细微的错误被混进来。

**[12:04]** 她当时真正缺的、能让她信任智能体的东西，是验证流程。六个月后的现在，她说自己每天 70% 的 token 都花在验证流程上。我可以说，这跟我看到的情况一致，因为我用智能体的大部分时间也都花在验证上。如果你仔细看它的流程，你会发现这些东西没有一样是前所未见的新技术或创新技术。

**[12:30]** 它们不过是优秀的软件工程工具，只是过去用起来很贵，因为难以理解、难以编写、难以维护。但智能体大幅降低了这个成本。事实上，我们正在进入软件测试与验证的黄金时代，因为智能体让我们能够以远超以往经济可行程度的规模去测试一切。形式化验证还能帮你更清晰地思考产品是如何运作的，以及你的智能体是否真正理解了你的意图和目标。我在我的「B-Stack」插件里做了一个叫「状态图」的新技能，帮你从用户视角把状态机可视化出来。我发现把它和我们提供的视频、截图放在一起看，评审起来更容易。那真是太棒了。

**[13:20]** 抱歉，刚才闪回了。好，现在我们来看看应许之地是什么样子。所有这些投入，回报是什么？对「Grok Bot」团队来说，我们的交付节奏正在起飞，而且增长飞快。上个月，我们团队向生产阶段发了 11000 个 PR，这个数字很疯狂。我们面向客户发版的频率也提高了，大约每天发布一个新的稳定版本。核心团队也执行了多得多的发布。我们还有很多零散贡献者，他们未必了解很多上下文，但也在贡献。十月份，大约有 227 人至少贡献了一个 PR。

**[14:14]** 随着节奏加快，你可能会想：这不会导致混乱吗？你知道的，这不会造成大量糟糕的工作吗？但实际上，被撤销的 PR 数量相对下降了，稳定在 0.5% 左右。不过我觉得，真正有意思的是：在这种发布节奏和 PR 数量下，「Grok Bot」的表现一直保持稳定，甚至在多个方面比刚发布时还提升了。启动、打字、打开新会话、在会话之间切换，所有这些都变快了。别忘了，「Grok Bot」目前仍然是一个「Electron」应用，所以性能是有天花板的，对吧？但它已经比目前现有的许多其他代理界面快得多。

**[15:02]** 在如此高的节奏、如此多的贡献者下，这个 Electron 应用能保持这样，我觉得非常不错。所以，在你急着去建软件工厂、把能自动化的都自动化之前，调试智能体时永远先试着改进你的代码库。从 lint 规则入手，阻止新的坏编程模式出现，然后再把旧的坏模式清理掉。另外，确保你的验证机制真的健壮。

**[15:32]** 这些工作本来就是自动化的前提。如果你的内层编程循环产出的是糟糕的工作，把这个循环自动化只会产出更多糟糕的工作，迫使你花越来越多的 token 去解决问题——众所周知，那非常昂贵。一旦你在代码库、静态分析和非形式化的运行时验证上做了这些投入，你会发现很多事情都因为这些基础而变得可能，你可以在它们之上轻松搭起自己的工厂。准备好的时候，Grok Bot 是搭建那层外环的好办法。我们有很多连接器和流程，可以运行 Cursor 和 Claude 的智能体与项目，让你能协调几百甚至几千个智能体。举个简单的例子：现在每次我们发布新版本，Grokbot 都会自动给我们创建一个新的 Cursor 项目，它会扫描整个应用和构建产物，像真实用户一样运行和使用应用来发现错误。然后它会开 PR 去修它发现的每一个错误，并自动合并——听起来可能很疯狂。这是因为我们的代码库足够好，PR 默认就是好的，我们用到的大部分产品代码已经不再需要深入的人工评审。

**[16:55]** 所以，当你有了坚实的基础和良好的组织结构，你就能把平庸变成金子，就能在不牺牲质量的前提下，以高质量和极快的速度发布。我叫 Potato（土豆），也叫 Lauren。再次感谢各位听我讲这些。
