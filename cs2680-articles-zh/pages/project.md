# 期末项目

在期末项目中，你自选一个问题，构建一个系统或设计一项实验来解决它，并用测量结果支撑一个论断。

在作业中，课程规定了问题和评估方式。在项目中，两者都由你决定。你可以选择两条路线之一：[产品路线](#product-track)，构建一个解决实际问题的工具；或[研究路线](#research-track)，就智能体或运行智能体的系统提出原创性论断。两条路线有相同的截止日期、交付物和评分标准。研究路线在新颖性和证据方面适用更高的标准。

项目为个人项目，占**课程成绩的 20%**。每名学生提交一份提案、展示一次海报与演示，并发表一篇博客文章和一个代码仓库。你可以在提案截止日期之前就开始。如果你希望就某个想法或其范围获得反馈、需要计算资源分配，或希望有人阅读草稿，请发邮件给授课教师。

# 选择路线

选择与你想要提出的论断相匹配的路线，并在提案中注明。之后可以通过发邮件给授课教师来更换路线。

## 产品路线：构建有用的工具

构建一个 AI 系统，以优于现有最强替代方案的方式解决一个真实问题。差距可能来自缺失的上下文、可靠性差、成本高、响应慢、隐私约束，或现有工具不支持的工作流程。

适合的方向包括：

* **研究工作流。** 自动化实验、复现结果、分析论文，或管理研究产物。
* **学习。** 构建一个有依据支撑的学习工具，或一个练习某项技能的系统。
* **个人工作流。** 改善你自己的工作或日常生活中重复性的任务。
* **课程延伸。** 将某次作业大幅推进到超出其评分要求的程度。你已提交的作业是起点，提案必须说明新在哪里。

## 研究路线：开展原创研究

研究路线要求就智能体或 AI 系统提出原创的、可证伪的论断。工作必须确立一个最接近的已发表工作未能给出的结果，解释该结果为何出现，并界定其成立的条件。一个打磨良好的实现、一次复现、一个基准测试，或一组测量，本身都达不到这一标准。

你可以选择课程的任一侧：

* **智能体侧研究。** 研究或改进规划、工具使用、记忆、上下文管理、验证、多智能体协调、评估，或智能体循环的其他部分。你所测量的量是智能体的行为、能力、可靠性或成本。
* **系统侧研究。** 研究或改进推理、批处理、调度、缓存、路由、量化、压缩、内核，或运行智能体或模型的其他层。你所测量的量是系统性能、效率、可扩展性或可靠性。

在任一侧，贡献可以采取以下四种形式之一：

* **测量。** 报告先前工作未报告的行为、瓶颈或权衡，然后解释其成因及其出现的条件。在不同模型或机器上运行现有基准测试不算数，除非它导向新的结论。
* **机制。** 提出一种方法、策略或设计，并与最强的已发表替代方案进行比较。通过消融实验隔离该机制，并解释它在何时有帮助、何时没有，以及原因。
* **复现与边界。** 复现一个已发表的结果，然后找出该论断不再成立的工作负载或条件。仅复现本身不算作贡献。
* **工具。** 构建一个基准测试、追踪工具或测量框架，使此前无法回答的问题变得可回答。验证该工具，然后用它回答问题。

#### 该选哪条路线

如果主要贡献是一个有用的应用，请选择产品路线并对它进行严格评估。如果你能够陈述新的论断、指出最接近的已发表论断，并设计一个能区分二者的受控实验，请选择研究路线。

# 提案

|  |  |
| --- | --- |
| 截止时间 | **10 月 28 日（周三）晚 11:59** |
| 权重 | 课程成绩的 2% |
| 提交方式 | 在 Canvas 上提交一份 PDF |
| 长度 | 不限页数 |

提案让课程团队在大部分工作开始之前确认：项目具体、能在五周内完成，并且会对照正确的基线进行评估。请按以下顺序包含九个部分。每一部分都列出了两条路线都必须包含的内容，并在二者不同时分别说明各自的额外要求。

1. **标题与摘要。** 给出标题、你的姓名和你的路线。对于研究路线，还要说明工作是智能体侧还是系统侧。然后用一段话概述问题、你的方法以及你将如何评估它。
2. **问题。** 描述你要解决的问题或要回答的问题、谁面临这个问题，以及它为何重要。对于产品路线，描述目前这项任务如何手工完成，以及它在时间、金钱或错误方面付出什么代价。对于研究路线，用一个你可以测量的量来陈述问题。
3. **现有工作与缺口。** 找出最接近的现有系统或已发表结果，并报告你实际测试了什么。对于产品路线，在你自己的任务上运行至少三个最接近的商业工具、开源系统或研究原型，将同样的输入直接交给一个前沿模型，并描述每一个如何失败。对于研究路线，引用最接近的已发表工作，说明它留下了什么未决问题，并报告你目前已经复现了什么，或你将如何在你的环境中复现最接近的结果。以一句话总结缺口，这句话必须可检验。对于产品路线，这句话说明你的系统将做到哪些最强替代方案做不到的事。对于研究路线，这句话说明你的实验将确立哪些最接近的已发表结果未能确立的内容。[寻找缺口](#the-gap)一节说明了如何开展这项调研。
4. **论断。** 陈述评估将要检验的论断。对于产品路线，用一个指标陈述你预期相对基线取得的改进。对于研究路线，陈述一个可证伪的假设：你预期的结果、你预期它在何种条件下成立，以及什么结果将表明该假设错误。
5. **设计。** 描述你将构建的系统或实验：其主要组件、哪些部分由你编写、哪些部分你将复用（模型、框架或作业代码），以及你预计的技术挑战。对于课程延伸，说明超出作业评分要求的新内容。对于研究路线，描述机制、测量或工具，以及你将如何隔离其效果。
6. **评估计划。** 指明你所在路线的两个基线（见[使用正确的基线](#baselines)）、工作负载或任务集及其规模、指标以及每个指标与论断的关系，以及实验协议，包括重复试验次数和消融实验。如果你将在示例上调优，请指明留出集。对于研究路线，还要指明你将检验的边界条件，并说明该计划如何满足[研究证据标准](#research-bar)。
7. **目标。** 陈述三个层次的结果，每个都要是具体的产物或测量。**75% 目标**是即使主要想法不奏效你也有信心交付的最低结果，例如一个可端到端运行的原型及其基线测量。**100% 目标**是你计划交付的结果。**125% 目标**是如果你提前达到 100% 目标将尝试的扩展。博客文章报告你达到了哪个目标。
8. **计划与资源。** 给出五周的逐周计划（见[按五周规划](#pacing)），包括首次端到端测量所在的周次。指明来自[计算资源表](#resources)的计算资源、所用模型，以及 API 成本或 GPU 小时数的估计。描述你将使用的数据、数据在调用托管 API 时的去向，以及对数据的任何限制。列出主要风险，以及每种风险发生时你将如何应对。
9. **参考文献。** 引用提案中提到的每一个系统、论文和数据集。

提案按完整性和具体性评分：九个部分是否齐全、缺口是否有你报告的测试或复现作为支撑，以及基线、工作负载和指标是否具体到足以执行。路线和计划不具有约束力。如果项目在提案之后改变方向，请发邮件告知授课教师新的路线或计划。

## 博客文章

以各次作业的书面报告为范本，面向一般技术读者写作。没有长度要求。文章必须涵盖以下八项内容：

1. 问题或疑问，以及相对于最接近的现有系统或已发表结果的缺口。
2. 系统或实验的设计。
3. 评估方法：基线、工作负载、指标和协议。
4. 结果，包括你的系统或假设表现更差的那些比较。
5. 局限性、失效模式以及对有效性的威胁。
6. 你达到了提案中哪个目标（75%、100% 或 125%），以及自提案以来发生了哪些变化。
7. 代码仓库以及任何公开演示的链接。
8. [AI 使用政策](policy.html#ai-policy)要求的说明：你将什么委托给了 AI、你自己做了什么、AI 在哪些地方有帮助、在哪些地方误导了你、你如何发现问题，以及代价是多少。

## 代码仓库

代码仓库必须让另一个人能够复现主要结果。包含安装与执行指南、每张图背后的原始测量数据、生成图表的脚本，以及每个报告数字所使用的硬件、软件版本和工作负载。为所有坐标轴和单位加标注，并确保图表在打印和灰度下仍然清晰可辨。

# 评分

提案按[提案](#proposal)一节所述评分，海报展示环节部分由同伴评分。博客文章和代码仓库按以下四个维度评分，权重相同。两条路线使用相同的维度。研究项目在新颖性、实验控制、可复现性和与已发表工作的对话方面适用更高的标准，因为它们声称对已发表的记录有所贡献。

| 维度 | 优秀工作所体现的 | 警示信号 |
| --- | --- | --- |
| **问题与动机** | 清晰的问题或疑问、对现有工作的充分调研，以及可检验的缺口 | 已有工具能解决该问题，或已有论文报告了答案 |
| **技术执行** | 实质性且技术上可靠的实现或测量 | 只能在一台机器、一个输入或一次运行上工作的代码 |
| **评估** | 恰当的基线与指标、受控比较，以及由实验支持的结论 | 单次运行的数字、弱基线，或将你的运行与论文中未复现的数字进行比较 |
| **报告** | 清晰的论断、可复现的证据，以及对局限性和负面结果的准确叙述 | 图表或论断无法得到底层测量数据的支持 |

如果博客文章解释了你预期什么、你测量了什么，以及两者为何不同，那么主要想法不奏效的项目仍可获得接近满分的成绩。测量结果无法支持的论断，无论结果有利还是不利，都会被扣分。

# 寻找缺口

在开始构建之前，先弄清楚已经存在什么，并用一句可检验的话说明其局限。请在提案之前完成这一步，这样如果已有工具或论文覆盖了你的想法，你还能及早调整项目。

## 对于产品项目

在你自己的任务上运行最接近的商业工具、开源系统和研究原型。同时把同样的输入直接交给一个前沿模型；即使这看起来过于简单，也算作一个基线。记录你观察到的具体失败。例如，“它无法读取我集群的作业队列”是一个可检验的缺口，而“没有类似的东西存在”则不是。

## 对于研究项目

阅读智能体侧或系统侧最接近的已发表工作，找出它未解决的论断。研究缺口通常有三个来源。第一，还没有人在你的工作负载、模型或硬件上测量过该行为。第二，某个已发表结果所依赖的条件，在你的条件下应当会改变答案。第三，两个已发表结果相互矛盾。一个“试试某个想法看看行不行”的计划还不是研究问题；请陈述你预期的结果及其原因。

**先复现最接近的结果。** 论文中报告的数字是用不同的模型、提示词、任务集、GPU、软件版本或工作负载测得的。将你的运行与该数字比较，会把你的改动与这些差异混在一起，因此在尝试改进之前，请先在你自己的环境中复现最接近的结果。如果已发表的产物无法复现，请记录原因，并构建你能合理辩护的最接近的对比。

**知道你的数据流向何处。** 托管 API 会将你的数据发送到你的机器之外。在使用未发表的结果、合作者的数据、人类受试者数据或私人通信之前，请查阅你所在实验室的规定和任何 IRB 条件。如果数据不能离开你的机器，请像[作业 4](assignments/index.html#assignment-4)那样自行提供模型服务。

# 评估

## 使用正确的基线

| 路线 | 基线 1 | 基线 2 |
| --- | --- | --- |
| **产品** | 在你的任务上运行的最强现有系统 | 你的工具改变它之前的当前手工工作流程，并记录其耗时 |
| **研究** | 未修改的智能体或系统 | 在你的环境中复现的最强已发表方法或结果 |

如果你引入了一种机制，请通过消融实验或其他受控比较将其隔离。既报告表现更差的配置，也报告表现更好的配置，并且即使你的系统输给最强的比较对象，也要把该比较包括在内。

## 研究证据标准

研究结果必须在产生它的那次运行之外仍然成立。在主要实验之前，陈述假设并固定协议。然后进行重复试验，报告变异或不确定性，隔离所提出的原因，检验至少一个边界条件，并保留复现结果所需的产物。

对于**智能体侧研究**，固定模型版本、提示词、工具、任务集和成功标准。如果你在示例上调优了方法，请使用留出任务，并将能力与 token 成本、延迟和运行之间的变异区分开来。对于**系统侧研究**，固定硬件和软件栈，描述工作负载，在受控负载下测量，并在适用时同时报告中心趋势和尾部行为。

单一的基准分数、一个有利的提示示例，或一个吞吐量数字，都达不到这一标准。

## 选择与论断匹配的指标

智能体项目可能需要成功率、延迟、成本、token 用量、步数、资源使用和人工投入。服务项目可能需要吞吐量、首 token 时间、每 token 延迟、尾延迟、内存使用、缓存命中率，以及所避免的预填充工作量。延迟结果必须说明测量时的请求速率。

**再深入测量一层。** 将顶层结果分解为解释它的各个组成部分。例如，“智能体花了 60 秒”报告了发生了什么，而“工具调用花了 40 秒，其中包括一次本可并行执行的 30 秒调用”则指出了应当改变什么。Ousterhout 的 [Always Measure One Level Deeper](https://cacm.acm.org/research/always-measure-one-level-deeper/) 解释了这一实践。

在主要实验之前固定工作负载、任务集和指标。对于产品路线，在你的工具改变它之前记录手工工作流程的耗时。对于研究路线，不要在看到了哪个工作负载能给出最强结果之后才选择工作负载。

# 按五周规划

1. **第 1 周。** 确定问题或疑问。测试最接近的系统或复现最接近的结果，并记录基线。
2. **第 2 周。** 运行端到端原型，或完整实验的小规模版本。
3. **第 3、4 周。** 改进系统并运行受控实验。
4. **第 5 周。** 分析结果，准备海报、演示、博客文章和代码仓库。

先完整跑通一次路径并完成首次测量，然后再构建更多基础设施。如果项目需要 GPU，请在计划中计入排队时间和重跑。

项目与[作业 4](assignments/index.html#assignment-4)（11 月 10 日周二截止）和[作业 5](assignments/index.html#assignment-5)（11 月 24 日周二截止）重叠。海报展示在 12 月 7 日（周一），博客文章在 12 月 8 日（周二）截止，因此请在最后一周之前就开始准备海报和博客文章。

| [课程模型 API](computing/api.html) | 你需要托管的前沿模型，但不需要控制服务栈 | 申请成本，以及数据离开你的机器 |
| [课程 HPC](computing/cluster.html) | 你需要 CPU 或 RTX PRO 4500 Blackwell GPU 资源；这是大多数服务项目的默认选择 | CPU 作业 3 天限制、GPU 作业 14 天限制，以及共享 GPU 池 |
| AWS | 你需要已宣布的课程配额所覆盖的云资源 | 在配额确认之前不要依赖额度 |
| [FASRC](https://www.rc.fas.harvard.edu/) | 你已有或能够获得研究用 CPU 节点或 H100、H200 等 GPU 的访问权限 | 访问审批和排队时间 |
| [CloudLab](computing/cloudlab.html) | 你需要裸金属、内核或网络访问权限，或需要与共享集群隔离 | 环境配置和实验可复现性 |

从最便宜的模型和最小的完整实验开始。在每次 API 运行之前设置支出上限，云作业完成后停止它们，并在完整扫描之前先做小规模扫描。GPU 分配迟到不能作为延期的理由，但课程团队可以帮助你排查访问问题并调整范围。
