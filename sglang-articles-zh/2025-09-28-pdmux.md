# PD 复用：借助 GreenContext 实现高 goodput 的大模型推理服务

> 原文：[PD-Multiplexing: Unlocking High-Goodput LLM Serving with GreenContext](https://lmsys.org/blog/2025-09-28-pdmux/) · LMSYS Blog · Weihao Cui, Yukang Chen, Xiaoze Fan, Han Zhao, Ziyi Xu, Xusheng Chen, Bingsheng He, Quan Chen

本文介绍我们在 **SGLang** 中支持**一种全新服务范式——PD 复用（PD-Multiplexing）**的初步工作。它旨在为 LLM 推理服务带来更高的 goodput。PD 复用利用了 [**GreenContext**](https://docs.nvidia.com/cuda/cuda-driver-api/group__CUDA__GREEN__CONTEXTS.html)——NVIDIA GPU 的一项新能力，允许在同一进程内跨任务对 GPU 资源进行轻量级的细粒度划分。我们预计这一范式将成为 LLM 服务部署的一条颇有前景的新路径，为模型即服务（MaaS）提供更强的 SLO 保障和更高的 goodput。

## LLM 推理服务中的 goodput：一个持续的挑战

大规模交付 MaaS 要求 LLM 推理系统在不牺牲吞吐量的前提下持续满足严格的服务级别目标（SLO）。在实践中，这意味着要同时满足推理两个阶段公认的延迟 SLO：预填充阶段的首 token 延迟（TTFT），以及解码阶段的每 token 间隔延迟（ITL）——也称为 token 间隔时间（TBT）。挑战在于，预填充和解码在同一个服务实例上交错执行，会争夺 GPU 资源。目前保障 SLO 达标的常见做法有两类：

1. **实例级 PD 分离（PD-disaggregation）**——将预填充和解码拆分到不同实例。但这伴随着代价：GPU 资源被静态划分，且实例间的 **KV 缓存迁移**带来额外的复杂度，需要高性能的互联与通信库。
2. **序列级分块预填充（chunked-prefill）**——把长序列切成较小的块，并将每个块与一次解码迭代融合执行，以控制 ITL。这同样引入了一个**微妙的权衡**：分块大小必须在严格的 ITL 保障与高 GPU 利用率之间取得平衡。

尤其当面向实际 LLM 服务设定严格的 SLO 阈值时，分离部署与分块两者的短板都会愈加明显。

## PD 复用：一种全新的服务范式

<img src="/images/blog/pdmux/1-overview.png" style="display:block; margin-top: auto; margin-left: auto; margin-right: auto; margin-bottom: auto; width: 80%; image-orientation: none;"></img>
<div style="text-align:center"><strong>图 1. PD 复用概览</strong></div>

为此，我们提出一种新的服务范式——**PD 复用（PD-Multiplexing）**，以实现更高的 goodput。它在同一实例内通过 GPU 内部空间共享来多路复用预填充和解码阶段。它带来几项重要收益：

1. 预填充和解码在同一实例内共享同一个 KV 缓存池，**免去了代价高昂的跨实例迁移。**
2. GPU 内空间共享使 GPU 计算资源（SM）能够随负载变化在预填充与解码之间**动态流动**。
3. 这种共享还**解耦了预填充与解码的执行**，确保在满足严格 ITL SLO 时预填充性能不受损害。

图 1 给出了 PD 复用的总体架构，它由两个核心模块组成：一个无气泡复用引擎，独立且高效地执行预填充和解码阶段；以及一个 SLO 感知调度器，迭代生成符合 SLO 约束的复用方案。

### 用 GreenContext 实现无气泡复用引擎

我们在 **GreenContext** 之上构建了这一新范式。GreenContext 是 NVIDIA GPU 自 CUDA 12.4 起引入的能力，支持轻量级的**进程内**空间共享。简言之，自 CUDA 12.6 起，我们可以创建多个具有专属 SM 配额的 CUDA 流来并发运行 GPU kernel。借助 GreenContext，GPU 资源可以在预填充和解码阶段之间动态划分，实时适应 SLO 要求、负载模式等各项服务需求。

为保留现有的服务架构，我们对预填充与解码的复用采用单线程调度，而不是为二者各自创建线程。这一选择也出于现实考虑：Python 的全局解释器锁（GIL）仍然阻碍真正的并行执行，且这一设计在后续版本中仍将保持默认。所幸预填充和解码都是异步的，这使得该设计可行。通过在预填充与解码各自的专属 GreenContext 流之间切换派发，即可实现复用。

<img src="/images/blog/pdmux/2-mux-engine.png" style="display:block; margin-top: auto; margin-left: auto; margin-right: auto; margin-bottom: auto; width: 100%; image-orientation: none;"></img>
<div style="text-align:center"><strong>图 2. 消除气泡，实现高效的预填充-解码复用</strong></div>

然而，这种 GreenContext 集成方式会引入 GPU 气泡。如图 2(a) 所示，气泡的产生有两个原因：(1) 预填充阶段的启动时间远长于解码阶段（后者只涉及单个 CUDA 图）。某些情况下，启动一个预填充阶段的耗时甚至超过执行一整个解码阶段，导致 GPU 资源闲置。(2) 解码阶段的迭代次数是不确定的。当解码批中的所有请求提前完成时，如果预填充已经启动，预分配的 SM 可能得不到充分利用。

为解决这一问题，我们将预填充阶段切分为更小的预填充块，如图 2(b) 所示。由于预填充通常远比解码更吃计算，这种块级切分开销可以忽略不计，同时有效消除了复用过程中的 GPU 气泡。

### 剖析（Profiling）与调度策略设计

无气泡复用引擎就绪后，下一个挑战是调度预填充块和解码批。离线剖析（profiling）显示，在 GreenContext 下两个阶段会争夺资源。根本原因在于 GreenContext 只划分 SM，并不划分内存带宽，使得资源争用难以建模。为此，我们对代表性负载进行离线剖析，并利用剖析结果训练一个延迟预测器，以驱动我们的 SLO 感知调度策略。由于该建模依赖于具体的模型和硬件环境，此处不展开细节，未来我们将提供一份包含实操分步指导的详细教程。

调度策略背后的直觉很简单：**给解码阶段分配刚好够保证 ITL SLO 的 SM 数量，再把其余全部 SM 都交给预填充；同时确定要启动的预填充块数量。**这样，解码始终在严格的 SLO 保障下运行，而预填充则尽快推进，以扩大解码批大小。


## 基准测试

总而言之，我们在多种负载和设备上将 PD 复用与多个基线进行了对比评估。我们先给出一个易于复现的实验，再用真实 trace 和多样化任务展示 PD 复用的优势，最后提供一张拉远视角的运行时调度细节可视化图。在我们的大规模评估中，PD 复用相比最先进的基线可将 goodput 最高提升 3.06 倍。

<small>* 以下结果仅用于研究目的。真实应用中的 SLO 要求往往更为具体。我们在此借助这些基准测试来展示 PD 复用的潜力。 </small>

### 不同分块大小下与分块预填充的对比

<div style="text-align:center"><strong>图 3. 单张 H200 上使用 CodeLlama-34b-hf 的 ShareGPT 与 LooGLE 结果</strong></div>

我们首先在单张 H200 GPU 上运行 CodeLlama-34b-hf，将 PD 复用与不同分块大小的分块预填充进行对比。图 3 报告了第 99 百分位（P99）的 TTFT 和 ITL。我们将 ITL 的 SLO 目标设为 60 ms。我们没有对 TTFT 施加 SLO 约束，而是报告 TTFT 的 P99，以体现 PD 复用的效率。图中，实心点表示相应基线满足 ITL SLO 要求，空心点表示违反。

结果凸显出明显优势：PD 复用在持续满足严格 ITL SLO 目标的同时，给出了最快的 TTFT。相比之下，分块预填充往往必须把分块大小降到 1024 以下才能满足如此严格的 ITL 要求，这会拖累预填充性能并导致 GPU 资源利用不足。对于 LooGLE 这类长上下文负载，分块的低效被进一步放大，这一优势也愈发明显。复现步骤见[此处。](https://github.com/sgl-project/sglang/pull/10692)

### 真实 Trace 上的结果

我们还在真实 trace Mooncake-Tool&Agent 上评估了 PD 复用，并与分块预填充和 PD 分离进行了对比。为保证公平比较，三者均基于 SGLang 代码库。该实验在一台配备 8 张 A100 的服务器上进行，分块预填充的分块大小为 512，分离部署中 P:D 的比例为 1:1。前缀缓存共享已启用。

图 4(a) 给出了 TTFT 和 ITL 的结果。与分块预填充相比，PD 复用在两项指标上都有提升。相对于 PD 分离，它取得了明显更短的 TTFT，同时两种方法都满足解码阶段的 SLO。为评估其对 goodput 的影响，我们逐步提高请求速率并测量 SLO 达标情况。如图 5 所示，PD 复用维持了显著更高的 goodput，相比分块预填充和 PD 分离分别最高提升 3.06 倍和 1.62 倍。

### 多样化任务上的结果与调度可视化

我们进一步在三个代表性任务上评估 PD 复用：**OpenThoughts**、**ShareGPT** 和 **LooGLE**。这些任务呈现出截然不同的负载模式：OpenThoughts 的预填充输入最短、解码输出最长；ShareGPT 的预填充输入较长但解码输出较短；LooGLE 则以最长的预填充输入和最短的解码输出对系统构成压力。

## 未来工作

PD 复用在 MaaS 部署中前景可观。我们将把下一步工作聚焦于以下方向：

* **MTP 与投机解码支持。**
具备 MTP 机制的模型（如 DeepSeek-V3）会同时解码多个 token，需要在 PD 复用中调整调度策略以保障 SLO。此外，采用多个协作 LLM 之间更复杂验证方法的投机解码方案，则需要另一种资源划分策略。我们将为它们扩展相应策略，并报告由此带来的端到端收益。
* **迈向更贴近实际的工业级 SLO 与细粒度参数控制。** 基于 PD 复用实现高 goodput 服务，需要对目标模型和硬件进行一次性的剖析（profiling）。简要参考文档见[此处](https://github.com/ykcombat/sglang/blob/e84aa1bdd055df93e603a46fa6ca5e60afd213f5/docs/advanced_features/pd_multiplexing.md)。我们还将发布一份详细的实操教程，帮助用户复现我们的剖析流程，并设计契合真实工业场景的有效调度策略。
* **与 PD 分离集成。** 虽然我们在上述评估中将 PD 复用与 PD 分离进行了对比，但二者并不互斥——它们可以结合起来进一步提升 goodput。例如，解码实例在不同负载下往往难以持续维持最大批大小，此时可以用一个 PD 复用实例来替代它，让系统通过让解码阶段与多路复用的预填充重叠执行，把原本被浪费的资源利用起来。
* **兼容 PyTorch \> 2.6。** 目前所有结果均在 PyTorch 2.6 上复现。在更新版本中，我们在组合 CUDA 图（CUDA Graphs）与 NCCL 时遇到了 NVIDIA 内部的问题。尤其是当 PyTorch \> 2.6 时，启动分布式 CUDA 图会产生显著开销。我们正与上游开发者密切合作修复该 bug，以实现对未来 PyTorch 版本的顺畅兼容。
* **MoE 模型支持。** 我们在 Qwen-235B 上的初步实验表明，PD 复用仍能带来一致的提升。我们计划发布在更大规模分布式环境中评估的更大 MoE 模型（如 DeepSeek-V3）的完整结果。

我们已提供 PD 复用的[概念验证实现](https://github.com/sgl-project/sglang/pull/10692)，完整集成进 SGLang 的[路线图](https://github.com/sgl-project/sglang/issues/10813)正在推进中。
