# 在 TCO 上取胜：AMD Instinct™ MI355X 如何通过 SGLang 与 MoRI 实现具备成本竞争力的分布式推理

> 原文：[Win on TCO: How AMD Instinct™ MI355X Achieves Cost-Competitive Distributed Inference Through SGLang with MoRI](https://lmsys.org/blog/2026-05-28-mori/) · LMSYS Blog · AMD & SGLang Team

SGLang 与 AMD 团队紧密协作，在 AMD Instinct™ MI355X GPU 上为大规模 DeepSeek-R1 分离式推理解锁了极具竞争力的总拥有成本（TCO）。基于 [SGLang](https://github.com/sgl-project/sglang) 的推理服务框架与 AMD 的 [MoRI](https://github.com/ROCm/mori) 通信库，我们证明 AMD 取得了与运行 Dynamo + TRT-LLM 的 NVIDIA B200 相当——且在关键工作点上更优——的 TCO。这些结果由 [InferenceX](https://github.com/SemiAnalysisAI/InferenceX) 验证——这是 SemiAnalysis 打造的开源持续基准测试平台，可在数百块 GPU 上进行测试，并提供[实时仪表盘](https://inferencex.com)。

本文将介绍我们取得了什么成果、如何实现，以及未来的规划。

**TL;DR**
- 在 **129 tok/s/user** 的交互性水平下，AMD Instinct™ MI355X 的成本为每百万 token **$0.169**——比 B200 TRT-LLM **低 5%**，比 B200 SGLang **低 40%**。
- 24 块 GPU 上达到 **2,436 tok/s/GPU**——每 GPU 吞吐量是 B200 SGLang（48 块 GPU）的 **1.25 倍**。
- 全栈优化：AITER GEMM 调优、MoRI 量化 all-to-all（带宽最多缩减 **2.56×**）、MoRI-IO KV 缓存后端（吞吐量比 Mooncake **高约 10%**）、结合 SDMA 的双批重叠（Two-Batch Overlap）、ROCm 上的 Specv2 MTP，以及 CPU 流式优化。

## 结果速览

在生产级编程助手和交互式聊天机器人所对应的典型工作点上——例如 **129 tok/s/user** 的交互性——我们观察到如下结果：

- **AMD Instinct™ MI355X（MoRI SGLang MTP）**：每百万 token **$0.169**，**2,436** tok/s/GPU（24 块 GPU）
- **NVIDIA B200（Dynamo TRT-LLM MTP）**：每百万 token $0.178，**3,128** tok/s/GPU（28 块 GPU）
- **NVIDIA B200（Dynamo SGLang MTP）**：每百万 token $0.284，**1,945** tok/s/GPU（48 块 GPU）

AMD Instinct™ MI355X 的成本比 B200 TRT-LLM **低 5%**、比 B200 SGLang **低 40%**，每 GPU 吞吐量是 B200 SGLang 的 **1.25 倍**——在成本与性能上同时胜出。

## 关键优化

这些成果来自一系列覆盖通信、计算算子与推理服务基础设施的全栈优化。下面各节将逐一详细介绍。


### 面向专家并行的 MoRI 量化 all-to-all



#### 混合 FP4/FP8 量化 all-to-all

我们通过一系列 PR 构建了混合量化 all-to-all：FP4 dispatch + FP8 combine direct cast（[#19757](https://github.com/sgl-project/sglang/pull/19757)）引入 MXFP4 dispatch 以降低通信延迟；FP8 blockwise combine（[#24879](https://github.com/sgl-project/sglang/pull/24879)）为 combine 路径添加了细粒度 FP8 分块量化，精度比直接转换（direct-cast）的 FP8 高约 2%；auto-select dispatch dtype（[#21040](https://github.com/sgl-project/sglang/pull/21040)）让 MoRI 能够从模型的 MoE 权重 dtype 自动检测正确的 dispatch 量化类型，免去了手动配置环境变量的麻烦。

在专家并行 MoE 推理中，每个 token 都要通过 dispatch 与 combine 通信原语发送到选中的 top-k 个专家。对于隐藏维度为 7,168、采用 top-8 专家路由的 DeepSeek-R1 而言，BF16 的通信量显著高于 FP8 和 FP4 量化通信。

关键洞察在于：对 dispatch 进行即时（on-the-fly）MXFP4 量化，可以在不损失精度的前提下获得更快的传输；类似地，专家输出（combine 阶段）也能容忍 FP8 量化而不产生明显的精度损失。

MoRI 支持多级量化通信：

*AMD Instinct™ MI355X 上的 MoRI-EP combine 算子微基准测试（EP8，BF16 输入，max_tokens=4096，hidden_dim=7168，scale_dim=56，zero-copy=0，dispatch=128/16，combine=128/16，10 轮平均，仅计 combine 延迟）：*

| 案例                                | 路径                      | Combine 延迟    |
|-------------------------------------|---------------------------|-----------------|
| Normal（无 scale）                  | fp8_blockwise specialized | **~736 µs**     |
| Uniform[−1024, 1024]（scale 激活）  | fp8_blockwise specialized | **~770 µs**     |
| 强制 scale 激活                     | fp8_blockwise specialized | **~769 µs**     |
| 参考基线                            | bf16 no-quant             | ~907 µs         |

对于 `amd/DeepSeek-R1-0528-MXFP4-v2` 这类 MXFP4 模型，系统采用 **FP4 dispatch + FP8 combine**，实现整体往返带宽 **2.56× 的缩减**（每 token 从 28,672 字节降至 11,200 字节）。

**分块量化（blockwise quantization）**通过细粒度缩放保持精度。默认情况下，FP8 分块量化使用每 128 个元素一个 FP32 缩放因子，在性能与精度之间取得良好折中。

量化模式会从模型的权重格式自动检测，也可通过 `SGLANG_MORI_DISPATCH_DTYPE` 和 `SGLANG_MORI_COMBINE_DTYPE` 环境变量覆盖。

#### 自适应算子选择

我们为 MoRI-EP 添加了节点间算子类型切换（[#18437](https://github.com/sgl-project/sglang/pull/18437)）——当每个 rank 的 token 数低于 256 时，新的 `InterNodeV1LL` 算子相比原有 `InterNodeV1` 可带来 **1.52× 的 dispatch 加速**和 **1.82× 的 combine 加速**。

MoRI 会根据负载特征动态选择最优的通信算子：

| 算子     | 条件                       | 优化目标                  |
|----------|----------------------------|---------------------------|
| `IntraNode` | 单节点（≤8 块 GPU）        | 共享内存 / P2P            |
| `InterNodeV1` | 多节点，>256 tokens/rank   | 高吞吐量，分段 RDMA       |
| `InterNodeV1LL` | 多节点，≤256 tokens/rank   | 低延迟                    |
| `AsyncLL` | 启用 SDMA 的路径           | 完全异步的 send/recv 拆分 |

切换阈值会根据解码批大小自动配置，确保预填充阶段（大批量）使用高吞吐量算子，而解码阶段（更小的每 rank 批量）使用低延迟算子。


### MoRI-IO KV 缓存后端

在 [#22665](https://github.com/sgl-project/sglang/pull/22665) 中，我们全面改造了 MORI-IO：新增状态传输支持（Mamba、SWA、NSA），引入无锁的内联（inline）传输模型以消除工作线程派发，并修复了高并发问题，使其在数千并发请求下依然稳定运行。

#### 面向高并发 KV 迁移的内联传输

- **无锁内联执行。** 传输请求直接在调用方路径中执行，而不是派发给工作线程。传输计划只需预计算一次，即可在所有层间复用，消除了逐层调度开销并减少锁竞争。
- **大规模下依然稳健。** 默认 RDMA 并行度提升至每次传输 **4** 个队列对（queue pair）和 **4** 个 worker，并采用线程安全的连接复用，避免数千并发请求下的端口耗尽。

#### 更广的模型覆盖

除基于 MLA 的标准 KV 缓存外，MoRI 还为混合架构添加了状态传输支持——包括 Mamba（SSM 状态）、SWA 和 NSA——使 Qwen3.5-397B-A17B 这类模型也能进行分离式推理服务。它还能处理预填充与解码采用不同张量并行度的 TP 不匹配场景，正确地在各 rank 间映射重复的注意力头。

*AMD Instinct™ MI355X 上的 MoRI-IO 基准测试（每节点 8 块 GPU，8× AMD Pensando Pollara 400 AI-NIC，DeepSeek-R1 671B FP8，TP=8，2048 个 prompt，ISL=8192，OSL=1024）：*

| 指标                    | MoRI-IO          | Mooncake         |
|-------------------------|------------------|------------------|
| 请求吞吐量              | **7.49 req/s**   | 6.80 req/s       |
| 输入 token 吞吐量       | **31,111 tok/s** | 28,257 tok/s     |
| 输出 token 吞吐量       | **3,775 tok/s**  | 3,428 tok/s      |
| 总 token 吞吐量         | **34,886 tok/s** | 31,685 tok/s     |

MoRI-IO 在所有指标上的吞吐量都比 Mooncake **高约 10%**，单请求延迟相当（TPOT 约 7 ms），且精度很高（GSM8K 5-shot：**0.970**）。


### 结合 SDMA 的双批重叠（TBO）

TBO 由三个 PR 构建：面向 MoRI EP 的双批重叠（[#19216](https://github.com/sgl-project/sglang/pull/19216)）基于 MoRI 的异步 API 引入了核心的双流流水线，在大批量下带来最高 **+25%** 的吞吐量提升；面向 MoRI EP 的 SDMA 路径（[#23929](https://github.com/sgl-project/sglang/pull/23929)）启用了 AMD 的 System DMA 引擎，通过拆分的 send/recv 实现零计算开销的数据搬运；ROCm 上的双流 MoE（[#24005](https://github.com/sgl-project/sglang/pull/24005)）在 ROCm 路径上激活了共享专家重叠流，将平均 TPOT 从 97 ms 降至 83 ms。

即便量化已带来 **2–4×** 的带宽缩减，all-to-all 通信开销依然可观。双批重叠（Two-Batch Overlap，TBO）通过在两个微批（micro-batch）之间交错通信与计算来隐藏这部分延迟：

1. **微批 A 的 dispatch** 在专用通信流上把量化后的 token 发送到网络
2. 在网络传输进行的同时，**微批 B 的注意力**在主计算流上执行计算
3. **微批 A** 到达，运行 MoE GEMM
4. **微批 A 的 combine** 在通信流上把结果发回
5. 与此同时，**微批 B 的 dispatch** 开始

dispatch 与 combine 操作被拆分为 A/B 两个阶段——`dispatch_a` 负责在计算流上进行本地量化，`dispatch_b` 负责在通信流上进行网络传输。由 `CommStreamPool` 管理专用流，并用事件（event）同步各交接点。

启用 SDMA（`MORI_ENABLE_SDMA=true`）后，数据传输运行在 AMD 专用的 System DMA 引擎上，在 GPU 内存与网络接口之间搬运数据且不占用任何计算单元。这实现了真正零计算开销的通信，在整个流水线中让每一个计算单元都可用于 GEMM 运算。

### 面向高性能 MoE 计算的 FlyDSL FusedMoE

传统上，AMD 上的 FusedMoE 算子完全依赖 Composable Kernel（CK）——性能出色但缺乏灵活性的手工调优模板。[AITER](https://github.com/ROCm/aiter) 引入了 **FlyDSL**（Flexible Layout Python DSL），这是一个由 MLIR 技术栈支撑的 Python DSL，用于以显式布局与分块（tiling）方式编写 GPU 算子，是 MI355X 上混合精度 MoE（如 A4W4）的一条有竞争力的 FusedMoE 算子实现路径。FlyDSL 让我们能够快速探索手工调优 CK 模板未覆盖的算子配置；在 512 的典型并发下，FusedMoE 计算的延迟最多缩减 **1.6×**。

MoE GEMM 的性能高度依赖矩阵形状，而主导形状因推理服务场景而异。在**低延迟纯 TP** 部署中，每块 GPU 以小批量处理所有专家，产生高瘦型（tall-skinny）GEMM；在**高吞吐量 DP+EP** 部署中，token 分布在专家并行的各个 rank 上，每个专家的 N/K 维度各不相同。FlyDSL 使我们能够为每种场景提供单独的调优配置，最大限度地发挥 MI355X 的利用率。

**Triton blockscale GEMM 调优**——与 FlyDSL 并行推进，A8W8 blockscale GEMM 路径针对 MI355X（gfx950）使用了按形状调优的配置。(N=7168, K=16384)、(N=16384, K=1536) 等与 DeepSeek-R1 专家维度对应的关键形状，均以优化后的块大小、warp 数量、流水线级数和 k 拆分参数进行调优。针对超小 M 值（≤8、≤256）的特殊情况调优，则瞄准 EP 解码中典型的每专家小批量。

此外，通过将 MoRI 的共享内存原语直接集成到 FlyDSL 中（[ROCm/mori#280](https://github.com/ROCm/mori/pull/280)），FusedMoE 算子可以在执行专家计算的同一个算子内部发起跨 GPU 数据传输——把计算与通信融合到一次启动（launch）中。这为 warp 级重叠打开了大门：部分 warp 负责计算、另一些 warp 负责搬运数据，从而消除算子间间隙，未来进一步降低 MoE 延迟。


### ROCm 上的 Specv2 MTP

DeepSeek-R1 通过 NEXTN 投机解码算法支持多 token 预测（MTP），每步额外预测 **3** 个 token。SGLang 的 **Specv2** 流水线将草稿与验证两个阶段重叠：在草稿模型执行的同时，在单独的 GPU 流上运行验证准备，从而隐藏调度开销。此前该路径仅支持 CUDA。在 [#17450](https://github.com/sgl-project/sglang/pull/17450) 中，我们通过为 AITER 注意力后端添加草稿模型 CUDA 图捕获与重叠计划流（overlap plan stream）支持，使 Specv2 得以在 ROCm 上运行，将完整的 Specv2 流水线带到了 AMD GPU。

MTP 还与量化通信形成了叠加效应：它使解码批大小变为原来的 **4 倍**（原始请求 + 3 个投机 token），改善了大批量下 all-to-all 的带宽利用率，而 FP4/FP8 量化则保证即便批量增大，每 token 通信成本依然保持在低位。

借助这一支持，与不启用 Specv2 相比，AMD Instinct™ MI355X 上的 MTP 带来 **+4%** 的总 token 吞吐量和 **-3.6%** 的 TPOT，且没有明显的精度损失（GSM8K 5-shot：0.923）。


### CPU 流式优化

在 [#22658](https://github.com/sgl-project/sglang/pull/22658) 中，我们优化了解码侧的 CPU 流式路径，包含两处改动：批量通知（将 asyncio 事件唤醒分组，而不是对每个请求调用 `event.set()`）和 SSE 快速路径（在流式输出的热点 yield 点上用直接的 `orjson.dumps()` 取代 Pydantic 序列化），在 2,048 并发下取得 **+20%** 的输出吞吐量和 **-16%** 的 TPOT。

在高并发 PD 分离场景下（例如 2,048 个并发请求），GPU 流水线不再是瓶颈——解码侧的 CPU 路径成为限制因素。我们优化了 SGLang tokenizer 管理器与 API 层中的 asyncio 通知批处理和 SSE 序列化热点路径，在不影响每 token 生成时间（inter-token latency）的前提下降低了 CPU 开销。


## 展望未来

分布式推理的下一个前沿正在从聊天式负载转向**智能体应用**——Claude Code、Codex、Cursor 这类工具会驱动深度多轮、工具增强的对话，具有长上下文窗口（最高 1M token）、极高的 KV 缓存复用率，以及并行派生子智能体（subagent）带来的密集请求突发。InferenceX 正在开发一个智能体编程基准测试来刻画这些模式，向真正的端到端系统基准迈进。我们未来针对 AMD Instinct™ MI355X 的优化将以这类负载为目标：利用更先进的异步并行策略（如 DWDP，Disaggregated Wide Data Parallelism），并挖掘 SDMA 等 ROCm 平台特有能力，实现完全异步、零计算开销的数据搬运——最终推动分离式 MoE 推理服务匹配大规模智能体推理的突发流量与高缓存需求。

在推理之外，SDMA 零计算开销的通信能力并不局限于推理服务负载。我们正在探索将 SDMA 扩展到 Miles 等**训练与强化学习框架**的潜力。在 DeepSpeed 训练框架中的早期验证已经展示了约 **10%** 的性能提升 [8]，这表明专用 DMA 引擎同样能够显著加速大规模分布式训练中的集合通信。


## 总结

本文展示了 AMD Instinct™ MI355X 搭配 MoRI 在 SGLang 上如何为大规模 DeepSeek 分离式推理实现具有竞争力的 TCO。在 129 tok/s/user 的交互性下，AMD Instinct™ MI355X 以每百万 token **$0.169** 的成本、**2,436** tok/s/GPU 的吞吐量提供推理服务——成本比 B200 TRT-LLM **低 5%**，每 GPU 吞吐量是 B200 SGLang 的 **1.25 倍**。

这一成果得益于横跨计算、通信与推理服务的全栈优化工作：

- **MoRI 量化 all-to-all**——混合 FP4/FP8 通信加自适应算子选择，往返带宽最多缩减 **2.56×**
- **MoRI-IO KV 缓存后端**——无锁内联传输配合高并发 RDMA，吞吐量比 Mooncake 高约 10%
- **结合 SDMA 的双批重叠**——借助 AMD 专用 DMA 引擎，把通信延迟隐藏在计算之后
- **AITER GEMM 调优 + FlyDSL FusedMoE**——面向 MI355X 上 TP 与 DP+EP 两种场景的平台级调优计算算子
- **ROCm 上的 Specv2 MTP**——多 token 预测的完整重叠调度，有效解码批大小增加 3×
- **CPU 流式优化**——asyncio 批处理与 SSE 快速路径，在 2,048 并发下释放 +20% 的输出吞吐量

叠加 AMD Instinct™ MI355X 的硬件成本优势（每 GPU 每小时 **$1.48**，B200 为 $1.95），这些软件优化将具有竞争力的吞吐量转化为了 TCO 上的胜局。

全部结果均已开源，并通过 [InferenceX](https://inferencex.semianalysis.com/) 持续验证。
