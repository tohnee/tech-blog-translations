# slime：面向 RL 扩展的 SGLang 原生后训练框架

> 原文：[slime: An SGLang-Native Post-Training Framework for RL Scaling](https://lmsys.org/blog/2025-07-09-slime/) · LMSYS Blog · The slime Team

## 驱动 slime 的愿景

我们相信 RL。我们相信 RL 是通往 AGI 的最后一块拼图。

如果你也这么认为，你会认同我们的愿景：

- 每个领域都应该被端到端地 RL 化，每项任务都应该成为一个智能体环境。
- 每次 RL 训练都应该跑得更久，每个模型都应该扩展得更大。
- RL 系统应该与现有基础设施无缝集成，让我们专注于新想法，而不是陷入重复的样板工程。

正因如此，我们推出了 [slime](https://github.com/THUDM/slime)，一个致力于做到以下几点的后训练框架：

- **功能全面**（Versatile）—— 提供完全可自定义的 rollout（采样生成）接口和灵活的训练配置（共置或解耦、同步或异步、RL 或 SFT 冷启动）。
- **高性能**（Performant）—— 原生集成 SGLang 做推理、Megatron-LM 做训练。
- **易于维护**（Maintainable）—— 代码库轻量，并支持从 Megatron 预训练到 SGLang 部署的平滑过渡。

简而言之：一个面向 RL 扩展的后训练框架。

下面讲讲我们是如何做到的。

## 可定制性带来自由

> 我们应当停止尝试用简单的方式去思考心智的内容，比如用简单的方式去思考空间、物体、多个智能体或对称性。
> 
> 
> —— *《苦涩的教训》（The Bitter Lesson）*
> 

RL 社区中一个普遍的误解是：不同任务需要不同的框架——一个用于纯数学任务，一个用于多轮工具调用，一个用于异步训练，一个用于智能体任务，诸如此类。分叉并维护多个框架是件苦差事，会把时间浪费在 bugfix 的 cherry-pick 上，更糟的是，漏打一个补丁就可能让训练崩溃。

事情本不必如此：没有人会为了换一个 dataloader 而分叉 PyTorch。我们认为，当前的乱象源于「规定人们应该如何构建应用」这一陷阱。如果我们坚持为每一种 rollout 场景定义一个通用模板，最终造出来的必然是一个只能满足现实需求中一小部分的 RL 框架。

slime 对 RL 中数据采样的理解与众不同。我们用 [sgl-router](https://github.com/sgl-project/sglang/tree/main/sgl-router) 管理 slime 内部的所有 SGLang 服务器，并为数据生成组件提供一个接口，**让用户能够注入自定义逻辑，并自由地与 SGLang 服务器交互**。释放他们的创造力。

![slime 架构](/images/blog/slime/slime-arch.png)

借助 sgl-router，用户只需向单一端点发送 HTTP 请求。通过暴露这个端点，复杂的智能体环境可以直接通过 OpenAI 兼容 API 与 slime 交互——无需修改环境，训练与部署的一致性也得以保持。

在训练方案上，slime 使用 Ray 进行资源管理，只需一个 flag（`--colocate`）即可启用**共置**（colocated，同一组 GPU）或**解耦**（decoupled，独立 GPU）的配置。

再加上 Ray 通过 `.remote()` 提供的异步执行能力，slime 天然支持异步训练。要改变同步行为，简单到只需移动一下 `ray.get` 的位置。为了让不同策略的实验变得容易，我们没有把代码包装进 trainer 类，而是直接在入口文件 `train.py` 中暴露训练循环。

## 为性能而生

**一个合格的 RL 框架必须快，而且要始终快。**

**快**，意味着使用最快的推理和训练框架。

与预训练不同，RL 负载在训练过程中涉及大量在线采样，这使得推理性能至关重要。因此，slime 只集成 SGLang，并有意识地提供 SGLang 原生体验。

那么「SGLang 原生」是什么意思？它意味着你可以充分利用 SGLang 的所有优化——在 slime 中使用 SGLang，感觉与单独使用它别无二致。为此：

- slime 内部以 **server-based 模式**启动 SGLang 服务器。
- slime 对所有 SGLang 参数实现了**无缝透传**（带 `--sglang` 前缀），确保所有优化选项都可以开启。例如，你可以传入 `--sglang-enable-ep-moe`、`--sglang-enable-dp-attention` 和 `--sglang-enable-deepep-moe`，以获得强大的多节点 MoE 推理能力。
- slime 提供 **SGLang-only 调试模式**（`--debug-rollout-only`），方便进行性能调优。

综上，我们可以在 slime 内复现 SGLang 单独运行时的性能。甚至连 slime 的基础镜像都基于 `lmsysorg/sglang:dev` 构建。

训练方面，slime 集成了久经考验的 Megatron-LM，同样追求原生的预训练体验：

- slime 同样对所有 Megatron 参数实现了**无缝透传**。
- slime 支持**所有 Megatron 并行方式**（TP、PP、EP、CP），并监控训练 MFU。
- slime 提供 **Megatron-only 调试模式**（`--debug-train-only`），并支持保存采样数据以保证可复现性。

Megatron 以复杂著称，因此我们还提供了 checkpoint 转换工具来简化它的使用。

**始终快**，意味着跟上推理和训练框架的演进步伐。

如果你关注过 [SGLang 的 PR 列表](https://github.com/sgl-project/sglang/pulls)，你会惊叹于它飞速的迭代。而 Megatron 往往被深度定制，每个组织都维护着自己的分叉。slime 的设计目标就是跟上 SGLang 上游的变化，并适配内部 Megatron 变体的优化。这也是我们追求 SGLang 与 Megatron 原生支持的另一个原因：参数透传让升级毫不费力。

除了优化推理和训练框架，我们还针对 RL 特有的负载做了工作。当 SGLang 需要改动以支持这些工作流时，我们会与 SGLang 团队紧密合作，把补丁合入上游——这样即使 RL 逻辑不断演进，slime 也能保持原生。例如：

**优化权重更新**：与推理任务不同，RL 训练涉及频繁的模型权重更新。为此，我们在 SGLang 中引入了多项优化：
    
  - 各种并行策略下 MoE 模型的参数更新（[#6265](https://github.com/sgl-project/sglang/pull/6265)、[#6308](https://github.com/sgl-project/sglang/pull/6308)、[#6311](https://github.com/sgl-project/sglang/pull/6311)）。
  - 分桶参数更新（bucketed parameter update）支持，以降低开销（[#7292](https://github.com/sgl-project/sglang/pull/7292)）。

**面向动态采样的 `/abort_request`**：在需要过采样（oversampling）的 RL 算法（如 [DAPO](https://arxiv.org/abs/2503.14476)）中，某些请求在收集到足够数据后可能仍在继续运行。我们与 [AReal](https://github.com/inclusionAI/AReaL) 团队合作设计了一个新端点：`/abort_request`。该端点可以：
    
  - 立即终止正在进行的请求。
  - 回收已部分生成的内容，从而支持部分 rollout。
    
实现于 [#6698](https://github.com/sgl-project/sglang/pull/6698)、[#6855](https://github.com/sgl-project/sglang/pull/6855)、[#6184](https://github.com/sgl-project/sglang/pull/6184)、[#5966](https://github.com/sgl-project/sglang/pull/5966)。
    

## 轻量且可扩展

围绕定制化与性能这两点，slime：

1. 提供可自定义的 rollout 接口。
2. 使用 Ray 进行 GPU 管理与异步执行。
3. 集成 SGLang 做推理、Megatron 做训练。
4. 提供训练与推理之间的权重更新。

相当简洁，对吧？slime 把复杂性从框架本身转移到用户自定义的流水线和核心库（SGLang 与 Megatron）上，从而形成一个轻量、易于维护的代码库。

但它并不止步于 RL。

得益于模块化设计和强大的后端，slime 只需极少的额外代码，就能自然扩展到其他后训练工作流：

- **SFT**：加载 Megatron，使用 token 预测损失。
- **拒绝采样**（Rejection Sampling）：先用 SGLang 做过滤，再用 Megatron 做 SFT。

*（注意：SFT 功能目前处于实验状态。）*

除此之外，slime 的原生集成**无缝打通了从预训练到在线服务**的链路。我们可以用 Megatron 做预训练，切换到 slime（同时集成了 Megatron 和 SGLang）做后训练，最后直接用 SGLang 做评估与部署。这免去了转换 checkpoint 格式、对齐框架间精度这些繁琐且容易出错的步骤。

统一流水线把我们从繁琐的胶水代码中解放出来，让我们专注于真正重要的事情：更好的 RL。太棒了！

## 路线图

RL 扩展之旅才刚刚开始，slime 也在持续进化。下一阶段，我们将专注于：

1. 与 SGLang 团队合作，探索大规模 MoE 模型的最优 RL 训练策略。
2. 支持更广泛的后训练工作流，强化从预训练到生产的桥梁。
3. 增加原生 PyTorch 训练后端支持，降低上手门槛。
