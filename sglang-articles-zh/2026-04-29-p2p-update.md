# 数秒内更新 1T 参数——大规模分布式 RL 中的 P2P 权重传输

> 原文：[Updating 1T parameters in seconds — P2P weight transfer in Large Scale Distributed RL](https://lmsys.org/blog/2026-04-29-p2p-update/) · LMSYS Blog · Jiadong Guo, Xin Ji, Letian Ruan, Teng Ma, Chenyang Zhao, Yueming Yuan, Zhichen Zeng

我们在 SGLang 中为 RL 工作负载引入了一种**基于 RDMA 的点对点（Peer to Peer，P2P）权重更新**机制，作为传统 NCCL 广播方法的补充，并兼容所有主流开源模型。通过在源侧利用 **CPU 引擎副本**，并借助 Mooncake TransferEngine 进行 **P2P RDMA 传输**，我们将 1T 参数 Kimi-K2 的权重传输速度提升了 7 倍（53 秒 -> 7.2 秒），代价是在 CPU 内存上为每个训练 rank 额外增加一份推理引擎副本（32G）。这些优化最大限度地减少了网络冗余，让推理服务器能够显著更快地恢复 rollout。

## 背景

NVIDIA 的 **NCCL** 通过自动检测硬件拓扑、并使用环形（ring）或树形（tree）算法协调数据流，来优化 `all-gather`、`broadcast` 等通信原语。作为 PyTorch FSDP、DeepSpeed 和 Megatron-LM 的默认通信后端，它是对称式训练的行业标准。然而，它依赖于集合通信（collective）语义，要求所有 rank 同时调用相同的操作、且数据形状完全匹配。这一设计对均衡负载非常高效，但在动态环境中会变成负担：NCCL 以锁步（lock-step）方式运行，这意味着单个接收方出现"慢启动"就可能让整个组挂起，导致资源闲置。

**RDMA**（远程直接内存访问）让机器可以访问远端内存，同时完全绕过远端的 CPU 和内核网络协议栈。它的高效源于三个核心特性：

- **内核旁路（Kernel Bypass）**：应用程序直接向 NIC 提交 Work Request，省去了开销高昂的系统调用和上下文切换。
- **零拷贝（Zero Copy）**：数据通过 DMA 在已注册的内存区域（Memory Region）与网络之间直接移动，避免了内核缓冲区内的中间拷贝。
- **单边操作（One-Sided Operations）**：RDMA READ/WRITE 操作由单侧发起，远端无需主动参与 CPU 处理或中断处理。

与 NCCL 的全局同步不同，RDMA 允许任意两个端点独立、并发地通信，这使它成为高速权重传输的理想基础。这也正是本文所述 P2P 权重更新机制采用基于 Mooncake TransferEngine 的 RDMA 传输作为底层基础的原因。

**RL 权重传输问题：** 在大规模分布式 RL 训练中，从训练侧向推理引擎传输权重是一项关键路径操作：权重传输期间，整个 RL 训练会陷入停顿——训练侧与推理侧都无法取得进展，资源通常处于闲置状态。随着模型规模增长，权重传输必须扩展到多台主机、多个机柜，而它们都在争夺有限的带宽。miles/slime/verl 等开源方案中现有的基于 NCCL 的工作流，依赖单个源 rank 发出的 `broadcast` 原语，这很快就会成为传输过程中的瓶颈。

<p style="text-align: left; color: #666; font-style: italic;"> 左：miles 当前在分布式训练/推理 RL 中的权重传输工作流。在源侧，所有节点参与 TP 和 EP 维度上的 all-gather，使得每个 PP rank 的头（head）rank 上得到聚合后的张量。头 rank 加入一个分布式更新组，通过 update_weight_from_distributed API 将完整权重广播给每个引擎 rank，各本地 rank 再加载自己对应的分片。该过程对每个 PP rank、每一批分桶权重张量都要执行一遍。
右：P2P 更新设计依赖源侧引擎副本作为中介。分桶权重更新的第一步 all-gather 与 miles 相同。但随后，权重被加载到 CPU 内存上的 sglang 引擎分片本地副本中，由副本以正确的形状把权重发送给 sglang。每个副本的权重可以发送给多个 sglang rank。每个目标 sglang TP rank 都需要从每个 pp 源接收权重。
</p>

## 现有 NCCL 广播方案的挑战

现有 NCCL 广播方案存在以下挑战：

- **冗余**：相同的数据会在网络上被重复发送多次。
- **闲置**：传输期间，大多数训练 rank 处于空闲状态，只有少数参与广播。
- **僵化**：NCCL 通信组一旦定义便固定不变，因此要随新创建的引擎实例进行动态扩缩，是一项牵一发而动全身的改动。

本对比评估了传输 1T 参数 FP8 Kimi K2 模型（约 1TB）的性能。注意：`update_weights_from_tensor` 接口因仅支持共置（colocated）场景而未纳入对比。

| 策略 | 效率 | 开源支持 | 动态性 | 训练侧支持 | 系统复杂度 | 架构灵活性 |
|---|---|---|---|---|---|---|
| 磁盘 I/O 策略（`update_weights_from_disk`） | 🆘 数分钟 | ✅ 是 | ✅ 是 | ✅ Megatron FSDP | 😊 简单 | 😊 单一 API |
| NCCL 广播（`update_weights_from_distributed`） | 🥵 约 50 秒 | ✅ 是 | 🚫 否（需要重建 NCCL 通信组） | ✅ Megatron FSDP | 😊 简单 | 😊 单一 API |
| Perplexity [fabric-lib](https://arxiv.org/abs/2510.27656) P2P | ⚡ 约 1.2 秒 | 🚫 否（仅 RDMA 库） | ✅ 是 | ❓ 仅 FSDP2 DTensor | 🥵 非常复杂 | 🥵 只写（write-only） |
| **RDMA P2P（我们的实现）** | **😊 约 7 秒** | **✅ 是** | **✅ 是** | **✅ Megatron FSDP** | **😥 复杂** | **😀 多个 API** |

虽然与 Perplexity 的方案相比在传输效率上有所取舍，但我们的方案相比 SGLang 现有接口带来了显著的性能提升。此外，我们通过将这些能力封装为新的 API 接口，实现了很高的架构灵活性。运行说明与完整支持的模型列表请参阅 [miles](https://github.com/radixark/miles/blob/main/docs/en/advanced/p2p-weight-transfer.md)。

## 设计

我们的设计从中心化广播转向基于 RDMA（远程直接内存访问）的分布式 P2P 映射；同时保持对所有现有开源模型和任意并行配置的兼容，并复用现有接口。

- **源侧引擎副本**：我们在训练 rank 的 CPU 内存中创建模型副本。这避免了浪费 GPU VRAM，也免去了反复注册与注销。
- **P2P 映射启发式策略**：我们在训练 rank 与推理 rank 之间实现点对点映射。不再由少数 rank 广播全部权重，而是每个训练 rank 都参与进来，把自己的特定分片直接发送给目标。
- **零拷贝传输**：借助 TransferEngine，内存在启动时只注册一次，避免了代价高昂的 CUDA IPC 句柄序列化和内核侧拷贝。

该实现大量依赖现有的基础设施与接口：

- [**TransferEngine**](https://kvcache-ai.github.io/Mooncake/python-api-reference/transfer-engine.html) 作为底层传输层，实现网络上 CPU 与 GPU 之间的 RDMA 零拷贝传输。
- 通过 [**Rfork**](https://www.lmsys.org/blog/2025-12-10-rfork/) 复用权重注册信息，这是 SGLang API 暴露的全新远程实例权重加载机制。
- 标准 SGLang API `load_weight(huggingface_tensor)`，支持所有量化与分片配置。

SGLang 侧还需要若干新接口：

- 为创建副本而暴露模型并行信息：[PR #20907](https://github.com/sgl-project/sglang/pull/20907)
- 将 Hugging Face 张量与其对应的 SGLang 张量分片建立映射：[PR #17326](https://github.com/sgl-project/sglang/pull/17326)
- 一个权重后处理引擎调用，用于 GPU 本地处理（如量化后处理），类似 [PR #15245](https://github.com/sgl-project/sglang/pull/15245)。

这些改动已合入面向 miles 的 `sglang-miles` 分支。权重更新期间，调用方的执行流程如下：

### 初始化

| 步骤 | 说明 |
|---|---|
| `get_remote_instance_transfer_engine_info` | 调用 SGLang API 获取权重注册信息 |
| `get_parallelism_info` | 调用 SGLang API 获取并行定义信息（tp、ep 等） |
| `build_transfer_plan` | 构建训练 -> 推理 rank 的映射关系 |
| `create_engine_replica` | 创建 CPU 引擎副本 |

### 每次更新期间

| 步骤 | 说明 |
|---|---|
| `pause_and_register_engine` | 调用 SGLang API 暂停引擎，并注册副本权重（仅一次） |
| `update_weight`（非专家与专家权重） | 分桶权重更新，先非专家权重后专家权重 |
| `post_process_weights` | 调用 SGLang API 对已加载权重做后处理，例如量化 |
| `update_weight_version` | 调用 SGLang API 更新权重版本 |
| `continue_generation` | 调用 SGLang API 恢复运行 |

最终得到的是一个通用的权重更新设计：它可处理任意模型和所有常见量化逻辑，同时实现无冗余的快速 RDMA 零拷贝传输，以及更高的带宽利用率。设想这样一个场景：训练侧有 M 个源 rank，SGLang 推理侧有 N 个目标 rank；源 rank 的 `pp_size` 为 `pp`，目标 rank 的 `ep_size` 为 `ep`；每个引擎 rank 有 P 个参数。我们还分配了 K 作为分桶 all-gather 的内存缓冲区。假设模型只包含专家权重：

|  | 参与的源 rank 数 | 每个推理 rank 接收的参数量 | 源侧额外分配的缓冲区 | 目标侧额外分配的缓冲区 |
|---|---|---|---|---|
| NCCL 广播 | pp | ep * P | K | K |
| RDMA P2P | M | P | K* + P | 0 |

<p style="text-align: left; color: #666; font-style: italic;">
表：RDMA P2P 设计如何在内存分配上做权衡，以实现更少的网络传输量和更高的利用率。所有源 rank 都参与传输（NCCL 方案中只有每个流水线并行组的头 rank 参与）；网络上只传输必要的张量（NCCL 则需要把完整的 all-gather 后张量发送给每个 rank）。RDMA P2P 以源侧 CPU 额外分配 P 大小内存为代价，换来接收侧不再需要任何额外内存分配。需要说明的是，实际中 K* 略大于 K，因为某些 Hugging Face 张量需要先在本地缓存，待完整的 SGLang 张量更新后才发送——这源于常见的多对一张量映射关系（如 sglang 中 q_proj、k_proj、v_proj → qkv_proj）。
</p>

## 使用方法

在 miles 中通过 `--update-weight-transfer-mode p2p` 启用 P2P 更新。它会让 SGLang 引擎通过 `--sglang-remote-instance-weight-loader-start-seed-via-transfer-engine` 注册权重内存，并选择 P2P 更新流程而非 NCCL 广播。Miles 依赖 SGLang 上的 `sglang-miles` 分支，其中包含支持 P2P 传输的更多高级实验特性。

## 未来计划

- **扩展支持**：为 GB200 等更新的硬件以及 SGLang 侧的流水线并行提供官方支持；支持更多量化方式；将 SGLang 侧的改动合入 main 分支。
- **试验大页内存分配**：与其永久性地分配 CPU 内存，可以考虑启用 Transfer Engine 的大页 GPU 内存分配，从而大幅降低注册与注销的成本。这可以在传输时实现原位（in-place）创建 GPU 副本并注册内存。

## 工程附录

### 设计迭代

我们最初的设计是把源侧副本放在 GPU 上。为了避免浪费训练期间的 GPU 显存利用率，我们在这一方向上投入了大量优化——如何以流水线方式完成注册、传输和注销？能否在把模型卸载到 CPU 的同时，借助虚拟内存机制让 NIC 上的内存注册保持不变？令人意外的是，考虑到现代集群可用的巨大带宽，传输本身反而是最不耗时的环节——在 RDMA 场景下，权重注册才是最大的时间开销，整个副本的注册要花掉数十秒。把副本迁移到 CPU 后，这个问题迎刃而解。

另一个障碍是最初 CPU 可能发生 OOM。多块 GPU 共享同一份 HBM，而在每个源 rank 上为每个目标 rank 都创建副本，很快就变得难以管理——但我们很快意识到，所有 SGLang rank 的构建方式是同构的，这意味着可以牺牲一点传输并发度，优先考虑内存复用。我们的最终设计复用同一块底层物理内存，并精心编排向不同引擎分片逐个传输的过程。

### 点对点传输计划

将每个训练 rank 映射到其目标 rollout 引擎 rank。采用带负载均衡的轮询（round-robin）分配：第一批 rank 获得 1:1 映射，剩余目标被均匀分配。这样可以最大限度减少每个源 rank 的 RDMA 会话数。

设想训练配置为 `pp=4`，共有 32 个训练 rank 和 2 个 SGLang 引擎实例，每个实例 16 个 rank。all-gather 之后，每个 pp 组中的每个 rank 都包含对应 pp rank 的完整聚合张量。每个目标 rank 都需要从每个 pp rank 接收权重。我们从 `pp_rank=0` 开始：此时需要把 8 个训练 rank 映射到全部 32 个目标 rank。

1. **轮询（Round-Robin）**：映射 `src_rank 0 -> tgt_rank 0`，……映射 `src_rank 7 -> tgt_rank 7`
2. 所有现有源 rank 的负载相同。再进行一轮轮询，分配 `src_rank 0 -> tgt_rank 8`，……`src_rank 7 -> tgt_rank 15`
3. 最后，注意到 `tgt_rank 16` 与 `tgt_rank 0` 完全相同。回看已有分配，把这个相同的引擎 rank 追加到它已有的源 rank 上。最终得到 `src_rank 0 -> [tgt_rank [0, 16], tgt_rank [8, 24]]` 等。

### 识别需要传输的 SGLang 张量

为了以分桶方式执行权重传输本身，我们需要在每次 `model.load_weight()` 之后识别出已就绪、可以发送的参数。我们首先构建 Hugging Face 张量与其对应 SGLang 张量或张量分片之间的映射。

```
sglang_name, shard_id, num_shards, expert_id, num_local_experts = parameter_mapper.map(hf_tensor)
```

其中，对每个模型、每个 Hugging Face 张量，我们都能得到它在 SGLang 内映射到的专家和张量分片。例如：

```
model.layers.0.mlp.experts.3.down_proj.weight -> model.layers.0.mlp.experts.w2_weight, w2, 2, 3, 5
```

只有当所有 `num_local_experts` 的全部 `num_shards` 都已更新完毕，才能发送一个 SGLang 张量。

### 共享副本下的传输流程

为了支持使用同一块底层内存向多个目标引擎实例传输，我们利用了基于线程池（Threadpool）的任务池，以及一个用于缓存部分更新张量的缓冲区。一个 SGLang 张量的传输任务要么处于关键路径上、必须等待完成，要么可以提交到任务池、只在最后检查是否完成。TransferEngine 库解除了 GIL 的限制，从而在多线程配置下实现并行。

<p style="text-align: left; color: #666; font-style: italic;">
图：一个训练源 rank 与 2 个目标 rank 之间使用同一底层副本的传输流程示例。
</p>

注意，图中的红色张量是 all-gather 之后的张量，包含所有专家和 TP 分片。然而，一次分桶更新可能并不包含某个 SGLang 张量的全部分片——如图所示，`q_proj` 和 `k_proj` 已被收集，但因上一次分桶更新而被缓冲在副本之外。这也是共享副本更新需要大于 1 的缓冲区大小的原因。最坏情况下，缓冲区可能是原始缓冲区的 `num_shard` 倍！不过，由于 `named_parameters` 通常会把相关张量排在一起，实际需要的额外缓冲区很小。

当一个 SGLang 张量收集齐所有必要分片后，我们更新副本，使用第一个目标引擎 rank（示例中为 SGLang 引擎 rank 0）自身的并行信息来加载对应权重。这次传输（send 1）位于关键路径上，必须完成（即目标权重已更新）之后，才能继续用同一个 Hugging Face 张量、但换用另一个引擎 rank 的并行信息，再次更新底层 CPU 分片。对于最后要更新的引擎 rank，已经没有人在等待同一个 SGLang 张量了，因此该任务（send 2）可以提交到线程池，我们随即继续执行下一次 all-gather。

### 其他量化与后处理

并非所有必要的张量都注册在 SGLang 的 `model.named_parameters()` 中。例如，在 DeepSeekV3 系模型中，MLA 包含本地张量 `w_kc` 和 `w_vc`，它们是在所有权重通过 `post_weight_load()` 调用完全加载之后才生成的。SGLang 中还包含大量依赖设备的自定义量化和硬件特定逻辑，无法在我们的 CPU 副本上执行。
