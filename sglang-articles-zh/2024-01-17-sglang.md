# RadixAttention 与 SGLang：快速且富有表达力的 LLM 推理

> 原文：[Fast and Expressive LLM Inference with RadixAttention and SGLang](https://lmsys.org/blog/2024-01-17-sglang/) · LMSYS Blog · Lianmin Zheng*, Liangsheng Yin, Zhiqiang Xie, Jeff Huang, Chuyue Sun, Cody Hao Yu, Shiyi Cao, Christos Kozyrakis, Ion Stoica, Joseph E. Gonzalez, Clark Barrett, Ying Sheng*

大语言模型（LLM）正越来越多地被用于各类复杂任务，这类任务往往需要多级串联的生成调用、高级提示技术、控制流，以及与外部环境的交互。然而，用于编程和执行这类应用的高效系统仍明显缺位。为填补这一空白，我们推出了 SGLang，一种面向 LLM 的结构化生成语言（<u>S</u>tructured <u>G</u>eneration <u>Lang</u>uage）。SGLang 通过后端运行时系统与前端语言的协同设计，增强了与 LLM 的交互，使其更快、更可控。

- 在后端，我们提出了 RadixAttention，一种跨多次 LLM 生成调用自动、高效复用 KV 缓存的技术。
- 在前端，我们开发了一种嵌入 Python 的灵活领域特定语言，用于控制生成过程。该语言既可以在解释器模式下执行，也可以在编译器模式下执行。

这些组件协同工作，共同提升了复杂 LLM 程序的执行效率与编程效率。

我们使用 SGLang 实现了常见的 LLM 负载，包括智能体（agent）、推理（reasoning）、信息抽取、对话和少样本学习任务，模型采用 Llama-7B 与 Mixtral-8x7B，硬件为 NVIDIA A10G GPU。下方的图 1 和图 2 显示，与现有系统（即 Guidance 和 vLLM）相比，SGLang 的吞吐量最高可提升 5 倍。我们已发布[代码](https://github.com/sgl-project/sglang/)和[技术报告](https://arxiv.org/abs/2312.07104)。

## 后端：使用 RadixAttention 实现 KV 缓存自动复用
在开发 SGLang 运行时的过程中，我们发现了一个对复杂 LLM 程序至关重要的优化机会，而现有系统对此处理得很差：KV 缓存复用。KV 缓存复用是指具有相同前缀的不同提示词（prompt）可以共享中间 KV 缓存，从而避免冗余的内存占用和计算。
在一个包含多次 LLM 调用的复杂程序中，可能存在各种各样的 KV 缓存复用模式。
下方的图 3 展示了其中四种模式，它们在 LLM 负载中十分常见。
虽然一些系统能够在某些场景下处理 KV 缓存复用，但这通常需要手动配置和临时调整。而且，由于可能的复用模式多种多样，即使借助手动配置，也没有任何现有系统能够自动覆盖所有场景。

<img src="/images/blog/sglang/sharing_wide.jpg" style="display: flex; margin-top: auto; margin-left: auto; margin-right: auto; margin-bottom: auto; width: 100%;"></img>
<p style="color:gray; text-align: center;">图 3：KV 缓存共享示例。蓝色框为可共享的提示词部分，绿色框为不可共享的部分，黄色框为不可共享的模型输出。可共享部分包括少样本学习示例、自洽性（self-consistency）中的问题、多轮对话中的聊天历史，以及思维树（tree-of-thought）中的搜索历史。</p>

为了系统性地利用这些复用机会，我们提出了 RadixAttention，一种在运行时自动复用 KV 缓存的新技术。我们的做法不是在完成一次生成请求后就丢弃 KV 缓存，而是将提示词和生成结果的 KV 缓存都保留在一棵基数树（radix tree）中。这种数据结构支持高效的前缀查找、插入和逐出。我们实现了最近最少使用（LRU）逐出策略，并辅以缓存感知的调度策略，以提高缓存命中率。

基数树是一种空间效率更高的 trie（前缀树）替代结构。与普通树不同，基数树的边不仅可以标注单个元素，还可以标注长度不一的元素序列，这一特性提升了基数树的效率。在我们的系统中，我们使用基数树来维护一个映射：以 token 序列作为键（key），其对应的 KV 缓存张量作为值（value）。这些 KV 缓存张量以分页布局存储在 GPU 上，每个页的大小等价于一个 token。考虑到 GPU 显存容量有限，我们无法无限保留 KV 缓存张量，因此需要一种逐出策略。为此，我们实现了一种递归逐出叶子节点的 LRU 逐出策略。
此外，RadixAttention 与连续批处理（continuous batching）、分页注意力（paged attention）等现有技术兼容。
对于多模态模型，RadixAttention 可以轻松扩展以处理图像 token。

下图展示了在处理多个传入请求时基数树是如何维护的。
前端总是将完整的提示词发送给运行时，由运行时自动完成前缀匹配、复用和缓存。
树结构存储在 CPU 上，维护开销很小。

<img src="/images/blog/sglang/radix_attn.jpg" style="display: flex; margin-top: auto; margin-left: auto; margin-right: auto; margin-bottom: auto; width: 100%;"></img>
<p style="color:gray; text-align: center;">图 4：采用 LRU 逐出策略的 RadixAttention 操作示例，共分九个步骤展示。</p>

图 4 展示了基数树响应各种请求的动态演化过程。这些请求包括两个对话会话、一批少样本学习查询和一次自洽性采样。树的每条边都带有标注，表示一个子串或 token 序列。节点用不同颜色标示不同状态：绿色表示新增节点，蓝色表示在该时间点被访问的缓存节点，红色表示已被逐出的节点。

在步骤 (1) 中，基数树初始为空。在步骤 (2) 中，服务器处理传入的用户消息 "Hello" 并以 LLM 输出 "Hi" 作为回应。系统提示词 "You are a helpful assistant"、用户消息 "Hello!" 和 LLM 回复 "Hi!" 被合并为一条边存入树中，并连接到一个新节点。在步骤 (3) 中，一个新的提示词到来，服务器在基数树中找到该提示词的前缀（即对话的第一轮）并复用其 KV 缓存，新一轮对话作为新节点追加到树中。在步骤 (4) 中，一个新的对话会话开始。来自 (3) 的节点 ``b'' 被拆分为两个节点，使两个对话会话能够共享系统提示词。在步骤 (5) 中，第二个对话会话继续进行。然而，由于内存限制，来自 (4) 的节点 "c" 必须被逐出，新一轮对话被追加在 (4) 中节点 "d" 之后。在步骤 (6) 中，服务器收到一个少样本学习查询，处理之后将其插入树中。由于新查询与现有节点不共享任何前缀，根节点被拆分。在步骤 (7) 中，服务器收到一批新的少样本学习查询。这些查询共享同一组少样本示例，因此我们将来自 (6) 的节点 'e' 拆分以实现共享。在步骤 (8) 中，服务器收到来自第一个对话会话的新消息。第二个对话会话的所有节点（节点 "g" 和 "h"）因最久未被使用而被逐出。在步骤 (9) 中，服务器收到一个请求，要求对来自 (8) 的节点 "j" 中的问题采样更多答案，这很可能是用于自洽性提示。为给这些请求腾出空间，我们逐出了 (8) 中的节点 "i"、"k" 和 "l"。

展望未来，我们预计还可以发展出更先进的多层存储策略和逐出策略。

## 前端：使用 SGLang 轻松进行 LLM 编程
在前端，我们推出了 SGLang，一种嵌入 Python 的领域特定语言。它让你能够轻松表达高级提示技术、控制流、多模态、解码约束和外部交互。
SGLang 函数可以通过多种后端运行，例如 OpenAI、Anthropic、Gemini 以及本地模型。

<img src="/images/blog/sglang/llm_judge.jpg" style="display: flex; margin-top: auto; margin-left: auto; margin-right: auto; margin-bottom: auto; width: 50%;"></img>
<p style="color:gray; text-align: center;">图 5：用 SGLang 实现的多维度文章评审器。</p>

图 5 给出了一个具体示例：它利用 [branch-solve-merge](https://arxiv.org/abs/2310.15123) 提示技术实现了一个多维度文章评审器。
该函数使用 LLM 从多个维度评估一篇文章的质量，合并各项评判结果，生成一段总结，并给出最终评分。
高亮区域展示了 SGLang API 的用法。
(1) `fork` 创建提示词的多个并行副本。
(2) `gen` 发起一次 LLM 生成调用并将结果存入变量。该调用是非阻塞的，因此允许多个生成调用在后台同时运行。
(3) `[variable_name]` 用于获取生成结果。
(4) `choices` 对生成结果施加约束。
(5) `run` 执行一个 SGLang 函数并传入其参数。

对于这样的 SGLang 程序，我们既可以通过解释器立即（eagerly）执行，也可以将其追踪为数据流图并用图执行器运行。后者为一些潜在的编译器优化留出了空间，例如代码移动、指令选择和自动调优。更多代码示例请见我们的 GitHub 仓库，编译器优化的细节请见我们的技术报告。

SGLang 的语法在很大程度上借鉴了 [Guidance](https://github.com/guidance-ai/guidance)。但在此之上，我们还引入了新的原语，并处理了程序内并行与批处理。所有这些新特性共同造就了 SGLang 的出色性能。
更多示例请见我们的 GitHub [仓库](https://github.com/sgl-project/sglang/tree/main?tab=readme-ov-file#quick-start)。

## 基准测试
我们在以下常见 LLM 负载上测试了系统，并报告所达到的吞吐量：
- **[MMLU](https://arxiv.org/abs/2009.03300)**：一个 5-shot、多选、多任务的基准测试。
- **[HellaSwag](https://arxiv.org/abs/1905.07830)**：一个 20-shot、多选的句子补全基准测试。
- **[ReAct Agent](https://arxiv.org/abs/2210.03629)**：一个智能体任务，使用从原始 ReAct 论文中收集的提示轨迹。
- **[Tree-of-Thought](https://arxiv.org/pdf/2305.10601.pdf)**：一个自定义的基于树搜索的提示，用于求解 GSM-8K 问题。
- **JSON Decode**：从 Wikipedia 页面抽取信息并以 JSON 格式输出。
- **Chat (short)**：一个合成的对话基准测试，每段对话包含 4 轮，LLM 输出较短。
- **Chat (long)**：一个合成的对话基准测试，每段对话包含 4 轮，LLM 输出较长。
- **[DSPy RAG](https://github.com/stanfordnlp/dspy)**：DSPy 教程中的一个检索增强生成（RAG）流水线。
- **[LLaVA Bench](https://github.com/haotian-liu/LLaVA)**：在 LLaVA-in-the-wild 基准测试上运行视觉语言模型 LLaVA v1.5。

我们测试了两种配置：在单块 NVIDIA A10G GPU（24GB）上运行 Llama-7B，以及在 8 块 NVIDIA A10G GPU 上以张量并行方式运行 Mixtral-8x7B，均使用 FP16 精度。基线系统采用 vllm v0.2.5、guidance v0.1.8 和 Hugging Face TGI v1.3.0。

如图 1 和图 2 所示，SGLang 在所有基准测试中都优于基线系统，**吞吐量最高可达 5 倍**。它在延迟方面同样表现出色，尤其是首 token 延迟——前缀缓存命中在这方面收益显著。这些提升归功于 RadixAttention 带来的 KV 缓存自动复用、解释器支持的程序内并行，以及前端与后端系统的协同设计。
此外，我们的消融实验表明，即使在缓存未命中的情况下也没有明显开销，因此我们在运行时中始终启用 RadixAttention 特性。

基准测试代码可在[此处](https://github.com/sgl-project/sglang/tree/main/benchmark)获取。

## 应用情况
SGLang 已被用于为 [LLaVA 在线演示](https://llava.hliu.cc/)提供推理服务。
它也已被集成为 [DSPy](https://github.com/stanfordnlp/dspy/pull/263) 的后端。
如果你有任何有趣的使用案例，欢迎告诉我们！

## 结论
随着 LLM 的不断演进，它们有望被无缝集成到复杂的软件栈中，革新软件开发实践。LLM 实际上可以充当智能的库函数。要确保其速度、灵活性、可靠性和可控性，关键在于对基于 LLM 的函数和程序的编程接口与运行时系统进行协同设计。SGLang 代表我们朝这一目标迈出的第一步。我们诚邀社区试用 SGLang 并向我们反馈。
