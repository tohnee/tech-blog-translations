# 在 GB200 NVL72 上以 PD 分离与大规模专家并行部署 DeepSeek（第二篇）：预填充吞吐 3.8 倍、解码吞吐 4.8 倍

> 原文：[Deploying DeepSeek on GB200 NVL72 with PD and Large Scale EP (Part II): 3.8x Prefill, 4.8x Decode Throughput](https://lmsys.org/blog/2025-09-25-gb200-part-2/) · LMSYS Blog · The SGLang Team

GB200 NVL72 是目前最强大的深度学习硬件之一。在[上一篇博客](https://lmsys.org/blog/2025-06-16-gb200-part-1/)之后，本文分享我们后续的进展：通过 FP8 注意力、NVFP4 MoE、大规模专家并行、PD 分离（预填充-解码分离）以及其他多项优化，持续提升 DeepSeek V3/R1 的推理性能。在使用 FP8 注意力与 NVFP4 MoE 时，对于 2000 token 输入序列的 DeepSeek V3/R1，SGLang 在预填充与解码阶段分别达到每 GPU 每秒 26,156 个输入 token 与 13,386 个输出 token，相比 [H100 配置](https://lmsys.org/blog/2025-05-05-large-scale-ep/)取得 3.8 倍与 4.8 倍的加速。即便沿用传统的 BF16 注意力与 FP8 MoE，SGLang 仍达到每秒 18,471 个输入 token 与 9,087 个输出 token。复现说明见[此处](https://github.com/sgl-project/sglang/issues/10903)。

**亮点**

* 对于 2000 token 输入序列的 DeepSeek V3/R1，SGLang 在预填充与解码阶段分别达到每块 NVIDIA Blackwell GPU 每秒 26,156 个输入 token 与 13,386 个输出 token，相比 H100 配置取得 3.8 倍与 4.8 倍的加速。
* 采用传统精度（注意力用 BF16、GEMM 用 FP8）时，SGLang 仍达到每秒 18,471 个输入 token 与 9,087 个输出 token。
* 与原始精度对应实现相比，注意力使用 FP8、GEMM kernel 使用 NVFP4 分别带来最高 1.8 倍与 1.9 倍的提升。
* FP8 注意力与 NVFP4 GEMM 带来的精度损失可以忽略不计。

## 方法

我们采用了以下策略：

* **FP8 注意力**：除传统 BF16 精度外，我们现在支持注意力中的 KV 缓存使用 FP8 精度。这大致将解码阶段的内存访问压力减半，并允许使用更快的 Tensor Core 指令，从而加速解码注意力 kernel。此外，这也让 KV 缓存能容纳更多 token，支持更长序列与更大 batch size，而后者又进一步提升了系统效率。
* **NVFP4 GEMM**：与经典的 FP8 GEMM 相比，新的 NVFP4 精度不仅降低了 GEMM 的内存带宽压力，还能利用更强大的 FP4 Tensor Core。其次，它将所需通信流量减半，从而加速 token 分发。最后同样重要的是，它降低了权重的内存占用，既可以缩小部署规模，也可以为 KV 缓存腾出更多空间。除了 MoE 专家以 NVFP4 精度执行之外，注意力中的输出投影 GEMM 也可选择量化为 NVFP4。与 NVIDIA 官方 checkpoint 不同，我们进一步将 q\_b\_proj 以 FP8 而非 BF16 执行，以提升性能。
* **通过卸载缩小规模（Scaling Down by Offloading）**：除扩大规模外，我们还支持缩小专家并行（EP）规模。当设备内存不足时，我们利用 GB200 在 CPU 与 GPU 之间的快速带宽（900GB/s，双向），配合预取（prefetch）将权重卸载到主机内存。这可以降低通信开销，当收益超过计算变慢的代价时即可带来性能提升，因此最优规模除模型配置外，还与当前使用的计算与通信 kernel 相关。由于每个预填充实例使用更少的 GPU，这也将故障爆炸半径降到最低。最后，它还可能减少等待最慢 rank 而浪费的时间。
* **计算与通信重叠**：鉴于通信带宽大幅提升，此前硬件上使用的双批次重叠（two-batch overlap）未必是最合适的方案，因此我们采用更细粒度的重叠方式。为简单起见，我们将 combine 通信与 down GEMM 以及共享专家重叠执行。在 GEMM 中实现信号通知时，我们在 TMA store wait 之后使用带 release 语义的原子指令，而该等待点距 TMA store 提交已有足够多的步骤。此外，我们使用 cp.async.bulk.wait\_group PTX 指令——它与 tma\_store\_wait 或等价流程属于同一指令族，但去除了[.read 后缀](https://docs.nvidia.com/cuda/parallel-thread-execution/#data-movement-and-conversion-instructions-cp-async-bulk-wait-group)。

在 kernel 层面，以下具体 kernel 已被集成进 SGLang 或经过优化：

* **NVIDIA Blackwell DeepGEMM**（用于预填充注意力）：NVIDIA Blackwell DeepGEMM 是一个在预填充与解码中都能达到高性能的统一 kernel。因此，除了自上一篇博客起在解码中使用它之外，我们还将该 kernel 集成进了预填充代码路径。
* **FlashInfer Blackwell CuTe DSL GEMM**（用于 NVFP4 解码）：该 kernel 使用 CuTe DSL 实现 NVFP4 精度、masked 布局的 GEMM。它利用 Tensor Memory Access（TMA）与 tcgen05.mma 指令（包括 2CTA MMA）进行高效计算，同时采用常驻分块调度（persistent tile scheduling）与 warp 特化（warp specialization）。
* **FlashInfer Blackwell CUTLASS GEMM**（用于 NVFP4 预填充）：该模块支持多种数据类型，基于 CUTLASS 实现，所应用的优化与 CuTe DSL 版本类似。它面向高吞吐负载设计，尤其适合预填充。
* **Flash Attention CuTe**（用于 BF16 KV 缓存预填充）：与上述 GEMM 类似，该 kernel 以 CuTe DSL 框架编写，在预填充阶段为 MHA 实现了高性能。
* **FlashInfer Blackwell TensorRT-LLM Attention**（用于解码与 FP8 KV 缓存预填充）：该 kernel 使用基于 cluster launch control 的常驻调度器，能够高效隐藏 prologue 与 epilogue，还实现了计算与内存加载之间更好的重叠，同时支持 BF16 与 FP8 精度。
* **在 DeepEP 中融合 NVFP4**：DeepEP 可选择在分发 token 之前对其进行量化，因此我们将 NVFP4 量化与原有 FP8 一并融合进其中，将所需网络流量减半。
* **更小的 kernel**：首先，量化、拼接等其他 kernel 也经过了优化与融合。其次，我们还优化了 FlashInfer 中的 MLA RoPE 量化 kernel。最后同样重要的是，我们还将 FlashInfer 中来自 TensorRT-LLM 的若干 kernel 作为原型做了轻微优化，带来 5% 的端到端加速和最高 2.5 倍的 kernel 加速。

## 实验

### 端到端性能

我们在 GB200 NVL72 上评估了 SGLang 中 DeepSeek 的端到端性能。为确保一致性，我们沿用此前博客系列（[大规模 EP](https://lmsys.org/blog/2025-05-05-large-scale-ep/) 与 [GB200 第一篇](https://lmsys.org/blog/2025-06-16-gb200-part-1/)）的实验设置，基线数字直接取自其中。我们同时评估了原始精度（注意力用 BF16、MoE 用 FP8）与降低精度（注意力用 FP8、MoE 与输出投影 GEMM 用 NVFP4）。解码使用 48 个 rank，即大规模 EP；预填充在高精度下每实例使用 4 个 rank，低精度下使用 2 个。由于所需的一个 bugfix 尚未公开发布，我们使用了 CuTe DSL 的抢先体验版本。

<img src="/images/blog/gb200_part_2/primary.png" style="display:block; margin-top: auto; margin-left: auto; margin-right: auto; margin-bottom: auto; width: 85%"></img>

实验显示，GB200 相比 H100 在预填充与解码上分别取得 3.8 倍与 4.8 倍的加速。这一加速可能主要归因于以下因素：

* **降低精度**：如上所述，注意力用 FP8 替代 BF16、各类 GEMM 用 NVFP4 替代 FP8 带来了加速。这既源于计算与内存访问量的减少，也得益于 KV 缓存能容纳更多 token 从而支持更大的 batch size。
* **更快的 kernel**：如上所示，我们集成了更快的注意力与 GEMM kernel，它们在端到端耗时中占相当大的比重。
* **多项优化**：重叠、卸载、小 kernel 加速与融合等优化以乘法方式叠加到最终加速上。
* **此前已述因素**：上一篇[博客](https://lmsys.org/blog/2025-06-16-gb200-part-1/)中提到的因素不仅适用于解码，也适用于新的预填充优化，此处不再重复。

需要说明的是，高精度与低精度代码路径之间的端到端性能差异并非仅仅源于精度变化，我们将在下一节对此进行更细致的考察。一方面，不同代码路径使用了不同的辅助 kernel 与策略，其中一些尚未完全优化；另一方面，各实验间的 EP 均衡程度也不相同，因为我们沿袭此前博客的做法，让数据保持同分布（in-distribution）。batch size 的选取以让 KV 缓存大致占满为准（因此 4k ISL 时为 768，2k ISL 时为 1408），但也可以调低（例如 2k ISL 时把 batch size 从 1408 降到 768，性能大约下降十分之一）。

### 深入低精度 kernel

在本小节中，我们考察从标准精度切换到低精度 kernel 带来的影响。具体而言，我们同时考虑注意力 kernel 与 GEMM kernel；对于后者，我们考察 MoE 中的 gate-up GEMM、MoE 中的 down GEMM，以及位于注意力中但同样耗时的输出投影 GEMM。为简单起见，我们只考察一个典型场景。

如下图所示，降低精度在很大程度上加速了相关 kernel。在所测场景中，注意力快了 1.8 倍，GEMM 最高快 1.9 倍。另一项从 kernel 视角看不出来的改进是 KV 缓存可容纳的 token 数增加，这使得 batch size 可以更大，从而提升性能。

### 精度

训练后量化（PTQ）不可避免地会损失信息，因此 NVFP4 能否带来与原始模型持平的表现仍是一个问题。从理论上讲，NVFP4 选择了较小的块大小（16），并使用 FP8 作为缩放因子的数据类型，使其能够以尽可能小的损失表示原始信息。实验上，我们观察到结果与 NVIDIA 的 [NVFP4 官方 checkpoint](https://huggingface.co/nvidia/DeepSeek-R1-0528-FP4-v2) 一致，精度变化极小：

## 未来工作

尽管我们的实现已展现出显著的性能提升，但仍有一些值得未来改进的方向：

* **多 token 预测（MTP）与重叠调度器**：这对解码有益，尤其在 kernel 侧 batch size 较小或注意力内存访问压力较大时。进行中的 PR 可在[此处](https://github.com/sgl-project/sglang/pull/9334)追踪。
* **kernel 优化**：部分 kernel 仍有改进空间，以充分释放硬件潜力。
* **更多模型**：其他强大的模型——无论已发布还是即将发布——也将得到优化，例如 Kimi-K2、Qwen 与 GLM 4.5。
* **OME 让使用更简单**：OME 是一个用于企业级 LLM 管理与服务的 Kubernetes operator，可简化模型的部署与运维。
