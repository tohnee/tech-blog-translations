# OME：以模型驱动架构革新大模型基础设施

> 原文：[OME: Revolutionizing LLM Infrastructure with Model-Driven Architecture](https://lmsys.org/blog/2025-07-08-ome/) · LMSYS Blog · The Oracle Team

## 两个团队的故事：模型服务为什么出了问题

在任何部署大语言模型（LLM）的大型组织中，都会出现两个诉求相互冲突的团队：

**机器学习工程师（MLE）** 花费数月时间对模型做基准测试、试验各种推理服务技术、打磨最优部署策略。每个模型都需要不同的配置——Llama 70B 需要张量并行（TP），DeepSeek V3/R1 需要专家并行（EP），多模态模型则需要专门的设置。参数多到数不清：批大小、KV 缓存配置、量化等级。更糟的是，这些配置还会随 GPU 型号（H100 还是 A100 还是 L40S）发生剧烈变化。

**生产工程师和数据科学家** 只想把模型部署上线。他们不应该需要理解张量并行的种种细节，也不应该关心为什么某个特定模型需要 4 块带 NVLink 的 GPU。他们有客户在等、有应用要开发、有业务价值要交付。

这道鸿沟造成了一个根本性问题：MLE 需要一种方式，把他们来之不易的服务知识沉淀为可复用的蓝图；生产团队则需要在不成为分布式系统专家的前提下部署模型。**缺失的那一环是什么？一个把模型当作一等公民来对待的系统。**

## OME 的诞生

Oracle 云基础设施（OCI）GenAI 团队大规模地遭遇了这一挑战。要在多种 GPU 硬件上支持大量模型，他们眼看着部署周期被拉长到数月。每接入一个新模型都意味着：

- MLE 要花数周做实验才能找到最优配置
- 生产团队难以遵循的复杂文档
- 配置错误导致的部署失败
- 相似模型之间无法复用已有经验

突破来自一个简单的洞见：**应该由模型本身来驱动部署。**

一个 Llama 模型不只是一个文件——它本身就携带了关于架构、参数量和需求信息的元数据。只要让系统"感知模型"，而不是"由部署驱动"，就能弥合 ML 专业知识与生产易用性之间的鸿沟。

由此诞生了 OME（Open Model Engine）：一个把模型视为一等资源的 Kubernetes operator。成效立竿见影：

- 模型接入时间：**数月 → 数天**
- 配置错误：**大幅减少**
- MLE 经验知识：**自动捕获、自动复用**
- 生产部署：**只需几行 YAML**

但它真正革命性的地方在于：模型驱动架构让复杂的部署策略变得易于编码和复用：

- **多节点服务**：通过简单配置，把 DeepSeek V3（685B）这样的超大模型部署到多个节点上
- **PD 分离（预填充-解码分离）**：将计算密集型的预填充与访存受限的解码分开，各组件独立扩缩
- **灵活架构**：预填充和解码都可以按需运行在单节点或多节点配置上
- **无服务器部署**：模型闲置时缩容到零，节省成本
- **业务驱动的扩缩**：基于 KV 缓存、每秒 token 数、延迟目标或任意自定义指标的复杂自动扩缩

模型驱动的方案不会束缚你，反而解放了你。正因为 OME 对模型理解得足够深，它既能支持 MLE 设计出的任何部署模式，又能为生产团队保持简单的接口。

**认识 OME**：一个让模型成为一等公民的 Kubernetes 原生平台。接下来让我们看看 OME 的架构如何把 LLM 部署的混乱，变成一个优雅、可扩展、能让从 ML 研究员到生产工程师的所有人都受益的系统。

## OME 架构：以模型为中心

![ome-architecture.svg](/images/blog/ome/ome-architecture.svg)

### **第 1 层：Kubernetes API 层**

用户——MLE、数据科学家、生产工程师以及各类应用——通过简单的接口与 OME 交互，而真正的魔法发生在下方的 Kubernetes API 层。

### **自定义资源——模型驱动架构的基石**

OME 的核心是其自定义资源定义（CRD），它把 Kubernetes 从一个通用容器编排器变成了一个 ML 平台。这些不只是配置文件——它们是你表达 ML 需求的语言。

### **BaseModel/ClusterBaseModel：作为一等公民的模型**

**什么是 Base Model？**

OME 中的 Base Model 是一种 Kubernetes 资源，代表你想用于推理负载的基础 AI 模型（如 GPT、Llama 或 Mistral）。可以把它理解为一张蓝图，告诉 OME 去哪里找到你的模型、如何下载它，以及把它存储在集群节点的什么位置。

当你创建一个 BaseModel 资源时，OME 会自动完成一系列复杂流程：下载模型文件、解析模型配置以理解其能力，并让它在集群各节点上可用，供 AI 负载使用。

**BaseModel 与 ClusterBaseModel**

OME 提供两类模型资源：

- **BaseModel** 作用域限定在命名空间内，即它只存在于特定的 Kubernetes 命名空间中。如果你在 "team-a" 命名空间创建一个 BaseModel，只有该命名空间中的负载可以使用它。这非常适合团队专属模型，或者需要隔离模型访问权限的场景。
- **ClusterBaseModel** 作用域覆盖整个集群，即集群中任何命名空间的负载都可以使用它。它适合组织级的、多个团队都需要访问的模型，比如大家共用的 Llama-3 模型。

两种类型使用完全相同的规范格式——唯一区别在于可见范围。

传统平台把模型当作需要下载和挂载的静态文件。OME 对此进行了革新，让模型成为智能的、带版本的、理解自身需求的资源：

```yaml
apiVersion: ome.io/v1beta1
kind: ClusterBaseModel
metadata:
  name: llama-3-70b-instruct
spec:
  vendor: meta
  modelType: llama
  modelArchitecture: LlamaForCausalLM
  modelParameterSize: "70B"
  quantization: fp16
  storage:
    storageUri: "hf://meta-llama/Llama-3.3-70B-Instruct"
    path: "/models/llama-3.3-70b"
    nodeSelector:
      gpu.memory: "80Gi"  # Only download to nodes with sufficient GPU memory
```

当你创建一个 BaseModel 资源时，OME 的控制平面和数据平面组件会协同工作，让模型在整个集群中可用。BaseModel CRD 充当声明式规范，而下载、解析和分发模型的具体工作由数据平面中的 Model Agent 完成。

### **ServingRuntime：运行时选择的"大脑"**

ClusterServingRuntime 是一种集群级资源，负责管理模型服务的运行时环境。一个 ClusterServingRuntime 定义了可用于服务一个或多个特定模型的 Pod 模板。每个 ClusterServingRuntime 都定义了关键信息，例如运行时的容器镜像，以及该运行时支持的模型列表。运行时的其他配置项可以通过容器规范中的环境变量传递。

这些 CRD 带来了更好的灵活性和可扩展性，让用户无需修改任何控制器代码或控制器命名空间中的任何资源，就能快速定义或定制可复用的运行时。ServingRuntime 与 ClusterServingRuntime 的唯一区别在于：前者是命名空间级的，后者是集群级的。

```yaml
apiVersion: ome.io/v1beta1
kind: ClusterServingRuntime
metadata:
  name: sglang-llama-70b
spec:
  supportedModelFormats:
    - modelFormat:
        name: safetensors
      modelArchitecture: LlamaForCausalLM
      modelSizeRange:
        min: "65B"
        max: "75B"
      autoSelect: true
      priority: 100
```

面向高级部署的完整运行时规范可以在 OME 仓库中找到：

- [Llama 4 Maverick PD Runtime](https://github.com/sgl-project/ome/blob/main/config/runtimes/srt/llama-4-maverick-17b-128e-instruct-fp8-pd-rt.yaml) - PD 分离（预填充-解码分离）配置
- [DeepSeek RDMA PD Runtime](https://github.com/sgl-project/ome/blob/main/config/runtimes/srt/deepseek-rdma-pd-rt.yaml) - 基于 RDMA 的多节点专家并行服务

ServingRuntime 定义了如何服务不同类型的模型，而实际的运行时选择逻辑在你创建 InferenceService 时由控制平面处理。

**高级部署架构**

ServingRuntime 充当 router、engine 和 decoder 组件如何部署的蓝图。每个组件（router 除外）都可以配置为单节点、无服务器或多节点部署。这种灵活性带来了最前沿的服务模式：

**PD 分离服务**——大规模高性能 LLM 服务的最先进方案

这不只是渐进式改进——而是服务架构上的根本性进步，而 OME 通过简单的运行时配置就能让你用上它。

### **InferenceService：编排模型部署与入口**

InferenceService 是 OME 中最核心的 Kubernetes 资源，负责编排模型服务的完整生命周期。它是一份声明式规范，描述你希望 AI 模型如何在集群中被部署、扩缩和服务。

可以把 InferenceService 看作 AI 负载的"部署蓝图"。它把模型（由 BaseModel/ClusterBaseModel 定义）、运行时（由 ServingRuntime/ClusterServingRuntime 定义）和基础设施配置整合在一起，构成完整的服务方案。正是 InferenceService 把模型、运行时，以及传统 Kubernetes service、复杂入口（ingress）、调度、自动扩缩和权限控制组合到一起，形成一个完整的集群服务舰队。

**架构总览**

OME 采用基于组件的架构，InferenceService 可以由多个专职组件组成：

- **Model**：引用要服务的 AI 模型（BaseModel/ClusterBaseModel）
- **Runtime**：引用推理服务运行时环境（ServingRuntime/ClusterServingRuntime）
- **Engine**：处理请求的主推理组件，通常是一个 OpenAI 兼容服务器，负责请求处理、工具解析和模型后端操作
- **Decoder**：分离式服务（预填充-解码分离）的可选组件
- **Router**：一个独立的高性能组件，可在多个推理实例之间实现数据并行，支持高级负载均衡算法（缓存感知、power of two、随机、轮询），并充当预填充-解码分离服务架构的专用负载均衡器

```yaml
apiVersion: ome.io/v1beta1
kind: InferenceService
metadata:
  name: production-chat-service
spec:
  model:
    name: llama-3-70b-instruct
  engine:
    minReplicas: 2
    maxReplicas: 10
  decoder:  # Only created for disaggregated deployments
    minReplicas: 4
    maxReplicas: 20
  router:  # Optional optimal serving routing layer
    minReplicas: 2
```

这种组件化架构带来了单体部署无法实现的精细优化：

- **独立扩缩**：计算密集的预填充与访存受限的解码可以分开扩缩
- **资源优化**：Router 不需要 GPU，节省宝贵的加速器资源
- **故障隔离**：单个组件故障不会拖垮整个服务
- **性能调优**：每个组件都可以针对自己的负载特性做优化

### **BenchmarkJob：把性能测试当作一等操作**

OME 是唯一把性能测试当作核心原语的平台：

```yaml
apiVersion: ome.io/v1beta1
kind: BenchmarkJob
metadata:
  name: llama-70b-production-benchmark
spec:
  # Target service to benchmark
  endpoint:
    inferenceService:
      name: llama-chat-optimized
  outputLocation:
    storageUri: "oci://n/benchmark-results/b/prod/o/llama-70b-bench"
```

这不只是跑个压力测试那么简单。BenchmarkJob 提供：

- **genai-bench 集成**：业界标准的基准测试工具
- **真实流量模式**：正态分布、固定模式、长上下文场景
- **全面的指标**：每秒 token 数、首 token 延迟（TTFT）、延迟分位数
- **多云存储**：结果持久保存，便于历史分析
- **服务元数据追踪**：记录 GPU 类型、引擎版本，保证对比公平

### **准入 Webhook：校验与变更**

OME 的准入 Webhook 充当 API 层的守门人：

1. **校验型 Webhook（Validating Webhooks）** 在资源创建前确保模型与运行时兼容，防止运行时失败
2. **变更型 Webhook（Mutating Webhooks）** 根据模型特征注入最优配置
3. **Pod 变更型 Webhook** 处理如下复杂场景：
    - 多节点部署的 RDMA 配置
    - 获得最优内存带宽的 GPU 亲和性规则
    - 用于模型加密的安全上下文

### **第 2 层：控制平面——编排者**

控制平面是 OME 主要逻辑的所在地。这不只是对 Kubernetes 资源做增删改查——而是一个能根据模型特征、硬件可用性和业务需求做出最优决策的精密系统。

### **OME Controller Manager：编排的大脑**

控制器管理器（controller manager）通过一个能够感知 ML 特有问题的调谐循环（reconciliation loop），协调所有 OME 操作。

**运行时选择算法**

当你通过 InferenceService 部署一个模型时，控制器会：

- 将模型特征与所有可用的 ServingRuntime 进行匹配
- 根据兼容性和优化潜力给每个运行时打分
- 使用**模型规模区间**（Model Size Range）匹配——当多个运行时都支持某个模型时，OME 会选择规模区间最接近的那个，以获得最优性能
- 处理各种边缘情况，例如量化模型或需要特定 GPU 特性的模型

**组件编排**

InferenceService 控制器根据你的部署需求编排多个组件：

```go
// Simplified reconciliation logic showing component-based orchestration
func (r *Reconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
    // 1. Fetch InferenceService and determine deployment mode
    inferenceService := &omev1beta1.InferenceService{}
    deploymentMode := r.inferDeploymentMode(isvc)
    
    // 2. Select optimal runtime if not specified
    if isvc.Spec.Runtime == nil {
        runtime := r.selectOptimalRuntime(isvc.Spec.Model, deploymentMode)
        isvc.Spec.Runtime = runtime
    }
    
    // 3. Reconcile components based on deployment mode
    switch deploymentMode {
    case PDDisaggregated:
        // Deploy separate engine (prefill) and decoder components
        r.reconcileRouter(isvc)    // Cache-aware routing
        r.reconcileEngine(isvc)    // Prefill processing
        r.reconcileDecoder(isvc)   // Token generation
        
    case MultiNode:
        // Deploy using LeaderWorkerSet for distributed serving
        r.reconcileMultiNodeComponents(isvc)
        
    default:
        // Standard single-component deployment
        r.reconcileEngine(isvc)    // Handles both prefill and decode
        if isvc.Spec.Router != nil {
            r.reconcileRouter(isvc) // Optional routing layer
        }
    }
}
```

**部署模式决策逻辑**

控制器会自动确定最优部署模式：

- **RawDeployment**：单引擎部署，适用于能装进单节点的模型
- **PDDisaggregated**：预填充/解码分离，适用于高吞吐场景
- **MultiNode**：面向超大模型（如 DeepSeek V3 685B）的分布式服务
- **Serverless**：通过 Knative 集成实现缩容到零，优化成本

### **第 3 层：数据平面——模型真正运行起来的地方**

数据平面是 OME 的架构决策真正产生价值的地方。这一层通过精细的优化处理实际的模型服务。

### **Model Agent：模型分发**

Model Agent 是 OME 的数据平面组件，负责让模型在整个集群中可用。当你创建 BaseModel 资源时，Model Agent 立即开始行动：

**模型分发为什么强大：**

1. **自动模型解析**：下载并解析模型的 `config.json` 和 `safetensors` 文件头，提取架构细节、参数量、支持的特性以及最优服务配置。再也不用手动指定模型特征。
2. **多云存储抽象**：BaseModel 中的 `hf://` 前缀不只是语法糖。OME 通过统一接口支持多种存储后端。只需改一行就能从 HuggingFace 切换到 OCI 对象存储——无需修改任何代码。
3. **节点感知分发**：模型不会被盲目地复制到所有地方。Model Agent 以 DaemonSet 形式运行，遵守节点选择器和亲和性规则，只把模型下载到符合规格的节点上。这既节省了宝贵的 NVMe 空间，又缩短了下载时间。
4. **生命周期管理**：模型会被追踪、版本化并进行健康检查。如果一个节点宕机，OME 会确保模型在其他节点上仍然可用。删除 BaseModel 时，清理工作会在所有节点上自动完成。

![mode-agent.svg](/images/blog/ome/mode-agent.svg)

**Scout-Gopher 架构**

OME 的 Model Agent 采用了精细的生产者-消费者模式：

**1. Scout 组件：分发层**

Scout 是模型分发的"大脑"，持续监控 Kubernetes API 中的 BaseModel 和 ClusterBaseModel 资源。

- **节点感知过滤**：Scout 评估节点选择器和亲和性规则，确保模型只被下载到合适的节点。
- **优雅删除处理**：删除模型时，Scout 会在释放资源前确保所有节点上的清理彻底完成，避免留下数 GB 的孤儿文件。

**2. Gopher 组件：任务引擎**

**存储后端性能**：

- **OCI 对象存储**：通过并行分块下载和 20 线程并发，达到 GB/s 级下载速度。一个 140GB 的 Llama 3 70B 模型几分钟内即可下载完成。
- **HuggingFace Hub**：生产级 Golang 客户端，支持自动重试、限流处理和断点续传。
- **统一接口**：只需改一个 URI 前缀即可在存储提供方之间切换——无需修改代码。

**3. 模型配置解析器**

解析器自动从 config.json 和 safetensors 文件中提取模型元数据，确定精确的参数量和能力。这让 30 多种受支持的模型架构无需手动配置。

**4. 状态管理与清理**

OME 通过以下机制提供自愈式的状态管理：

- **ConfigMap 调谐**：通过内部缓存自动重建被删除的 ConfigMap，确保模型状态永不丢失
- **节点标签**：通过诸如 `models.ome.io/basemodel.llama-3-70b=Ready` 之类的标签辅助 Pod 调度决策
- **基于 Finalizer 的清理**：确保删除前所有节点上的模型被彻底移除，即使节点故障也能优雅处理

**成果：生产级模型管理**

这种架构带来了传统方案无法比拟的能力：

- **规模**：在多个数 GB 级大模型上经过测试，支持多个节点同时下载多个模型
- **效率**：模型在每个节点只下载一次，而不是每个 Pod 下载一次——节省 PB 级带宽
- **可靠性**：自愈的 ConfigMap、自动重试和优雅的错误处理，确保模型始终可用
- **性能**：OCI 对象存储提供 GB/s 级下载速度，比朴素实现快 20 倍
- **智能**：自动理解模型，消除手动配置错误

### **推理负载**

根据你的 InferenceService 规范，OME 会部署针对特定负载模式优化的不同组件，包括 PD 分离服务、多节点服务、标准部署和无服务器部署。

| 组件 | 何时使用 | 主要功能 | 关键优化 |
| --- | --- | --- | --- |
| **Engine** | 所有部署 | 推理服务器（PD 模式下负责预填充，其他模式下负责完整推理） | • 计算优化 • 批处理 • 张量并行 |
| **Decoder** | 仅 PD 分离部署 | 使用来自 engine 的 KV 缓存生成 token | • 内存带宽优化 • 高效缓存管理 |
| **Router** | 显式指定或 PD 模式 | 优化后的请求分发 | • 缓存感知路由 • 连接池 • 健康监控 |
| **Ingress** | 自动创建 | 外部 API 访问 | • TLS 终止 • 限流 • 请求路由 |

这套架构的精妙之处在于其灵活性——从只含 engine 的简单部署起步，随着需求增长逐步采用高级模式。

### **第 4 层：外部集成——生态之力**

OME 不重复造轮子——它与 Kubernetes 生态深度集成：

**Kubernetes 生态集成：**与现代 Kubernetes 组件深度集成，包括用于多 Pod 负载成组调度（gang scheduling）的 [Kueue](https://kueue.sigs.k8s.io/)、用于高可用多节点部署的 [LeaderWorkerSet](https://github.com/kubernetes-sigs/lws)、用于基于高级自定义指标自动扩缩的 [KEDA](https://keda.sh/)、用于精细流量路由的 [K8s Gateway API](https://gateway-api.sigs.k8s.io/)，以及用于标准化推理端点的 [Gateway API Inference Extension](https://gateway-api-inference-extension.sigs.k8s.io/)。

## SGLang：一等运行时支持

SGLang 是 OME 的主要运行时，其深度原生集成充分展现了 OME 模型驱动架构的能力。

### 原生 Router 集成

OME 与 SGLang 的 router 组件实现了原生集成：

**Kubernetes 服务发现**：router 通过 Kubernetes API 自动发现 engine 和 decoder Pod，无需人工干预即可适应扩缩事件和 Pod 生命周期变化。

**最小权限 RBAC**：每个 router 只获得最小权限——仅能 list、get 和 watch 其所在命名空间中的 Pod。在支持动态发现的同时，防止跨租户信息泄露。

### 负载均衡能力

OME 支持 SGLang 的高级负载均衡策略：

**面向 PD 分离部署**：router 在预填充（engine）和解码（decoder）组件之间分发请求，保持 KV 缓存一致性并优化吞吐量。

**面向标准部署**：缓存感知负载均衡基于 RadixAttention 追踪各个 worker 的 KV 缓存状态，把请求路由到最可能拥有相关缓存前缀的 worker。

### 部署灵活性

通过 OME 的 ServingRuntime 配置，SGLang 支持：

- **单节点服务**：适用于能装进单块 GPU 的模型
- **多节点服务**：通过张量/流水线并行服务大模型
- **PD 分离服务**：将计算密集的预填充与访存受限的解码分开
- **专家并行**：面向 DeepSeek V3 等专家混合（MoE）模型

OME 与 SGLang 的集成展示了模型驱动架构如何在支撑复杂服务模式的同时保持运维简单。

## 生产级特性：为大规模而生

### 原生基准测试

OME 将 BenchmarkJob 作为核心 CRD 内置其中，支持以真实流量模式、并发扫描和自动化的结果存储进行系统化性能测试。团队可以用标准化、可复现的基准测试，来比较不同的模型配置、运行时设置和硬件选择。

### Multi-LoRA 服务：一个模型，多套适配器

部署单个基础模型，挂载多套面向不同用例的 LoRA 适配器：

每个请求都可以指定使用哪套适配器，从而用单一部署实现多租户服务。

### 大规模高性能服务

**预填充-解码分离（PD 分离）**：将计算密集的预填充与访存受限的解码操作分开，在混合负载下实现 2.5 倍吞吐量提升。

**多节点服务**：借助 RDMA 支持无缝跨多节点扩展模型，可以部署 DeepSeek V3（685B 参数）等前沿模型。

**GB/s 级下载速度**：原生 OCI 对象存储集成带来每秒数 GB 的下载速度，让模型更快进入生产环境。

### 企业级安全：纵深防御

**可选的模型双重加密**：OME 支持对模型进行双重加密，在需要增强安全性时与 OCI KMS 和 OCI Vault 集成。

**细粒度访问控制**：RBAC 策略控制谁可以部署哪些模型，并提供命名空间隔离和审计日志。

**安全的多租户**：不同团队的模型与服务基础设施之间完全隔离。

## 实际成效：从数月到数天

OME 目前正在 Oracle 云基础设施（OCI）上支撑生产负载，改变了他们的 LLM 运维方式：

### 大规模下的运维转型

**使用 OME 之前：**

- 模型接入：数月的手动配置
- 运行时选择：反复试错
- 基准测试：临时性、不一致的流程
- 服务配置：需要专门知识

**使用 OME 之后：**

- 模型接入：自动化流程，只需数天
- 运行时选择：自动且最优
- 基准测试：标准化且可复现
- 服务配置：声明式且简单

影响立竿见影——过去需要数月专门工程投入的工作，如今通过标准化、自动化的流程几天内即可完成。团队可以把精力放在评估模型能力上，而不是和基础设施的复杂性较劲。

## 弥合鸿沟：OME 如何连接两个世界

还记得开头提到的那两个团队吗？一方是精益求精打磨模型服务的 ML 工程师，另一方是急于快速部署模型的生产工程师。

OME 通过模型驱动架构弥合了这道鸿沟：

**对 ML 工程师**：你的优化被沉淀在 ServingRuntime 中。你的基准测试结果指导未来的部署。你的专业知识成为可复用的基础设施。

**对生产团队**：用一个简单的 InferenceService 就能部署任何模型。平台自动处理运行时选择、扩缩和优化。

**对组织**：标准化工作流、缩短上线时间，并且无需深厚专业知识就能用上最前沿的服务技术。

模型驱动的方案把 LLM 部署的混乱变成了系统化、可扩展的流程。通过让模型成为一等公民，OME 同时实现了创新与卓越运维。

## 未来的路：尚待应对的挑战

尽管 OME 已经改变了 OCI 的模型服务方式，在迈向真正通用的 LLM 平台的道路上，仍有重大挑战：

### 加速器感知的运行时选择

目前，混合 GPU 集群（H100、A100、L40S）需要为每种加速器类型单独配置运行时，导致运行时数量膨胀、运维复杂。我们正在开发 AcceleratorClass 抽象，让单一运行时能够自动适配可用硬件。

### 多云支持

OME 当前实现与 OCI 紧耦合。随着越来越多的组织采用多云策略，我们需要解耦特定云厂商的逻辑，创建统一接口，以支持 AWS、Azure、GCP 和本地部署，避免代码重复。

### 多集群管理

未来的架构将支持由一个运行 OME 的管理集群来编排跨多个工作集群的模型部署，实现跨区域、跨云厂商的联邦管理。

简化 LLM 部署的旅程仍在继续。每一个挑战都是一次机会，让世界各地的组织能够更容易、更高效、更强大地使用模型服务。
