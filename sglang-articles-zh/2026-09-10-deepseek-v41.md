# SGLang 与 Miles 为 DeepSeek-V4.1 提供 Day-0 支持

> 原文：[SGLang and Miles Add Day-0 Support for DeepSeek-V4.1](https://lmsys.org/blog/2026-09-10-deepseek-v41/) · LMSYS Blog · SGLang and Miles Teams

## 1. 架构总览

DeepSeek-V4.1 在架构上做出了多项设计选择，直接决定了推理服务栈的构建方式。

**低比率压缩与滑窗注意力（SWA）。** 每一层都为其最近的 128 个位置维护一份 fp8 滑动窗口缓存，同时由选定的源层生成 fp4 压缩表示，用于长程注意力。除前两层之外，每个 query 会同时关注其局部窗口以及由 indexer 选出的至多 512 个压缩位置。第 2-19 层采用成对压缩，因此 KV 源层必须在解码步之间保留不完整的配对。

压缩 KV 与检索选择结果会跨层共享，详见第 2 节。

**流形超连接（mHC）。** 每个子层都通过依赖于 token 的混合系数，从四条并行的残差流中读取并写入数据。一个子层会消费其前驱生成的系数，从而使下一个系数投影能够与当前的注意力或 FFN 计算重叠进行。

**Engram 记忆。** 第 1 层和第 14 层从两张大型 fp8 表中检索以哈希 token n-gram 为键的行，并通过门控将选中的行注入残差流。每一步只读取少量行，因此表的放置位置和查找开销比稠密计算更为关键。

## 2. 跨层共享与稀疏检索

**共享的 KV 与 indexer 键。** 四个 KV 源层负责生成压缩 KV 与 indexer 键。消费层从最近的 KV 源读取这些内容，避免了在每个消费层重复存储和生成。窗口 KV 则仍为各层独有。

**用于两级选择的共享候选集。** 第 20 层为每个 query 选择至多 2,048 个包含八个位置的块，并始终保留包含最新位置的那个块。它将这些候选发布给后续的 index 源层，同时从所有可达位置中选出自己的 top-512。后续的 index 源层则把各自的 top-512 限制在这些共享候选之内。当所有可达位置都在 16,384 个位置的预算之内时，候选过滤不会排除任何位置。

**跨层选择复用。** 八个 index 源层用自己的 query 对 indexer 键打分，并为每个 query 选出至多 512 个压缩位置。其余压缩注意力层直接复用最近一次的选择结果，无需再运行 indexer。

## 3. Engram 优化

Engram 是 DeepSeek-V4.1 的核心组件。它的两张 fp8 表共包含 189 GiB 权重，但每个解码步只读取少量行。SGLang 支持将这些表放置在 GPU 或主机内存中。将表分片到四块 GPU 上时，每块 GPU 的 HBM 中存储四分之一，并且需要一次 all-reduce 来汇总每次查找的结果。

### 3.1 主机内存放置

主机卸载（host offload）将 Engram 表移出 GPU 显存，为 KV 缓存腾出容量。反量化、门控和值投影仍留在 GPU 上。SGLang 支持两种通信开销不同的主机布局。

在**主机分片布局**中，每个 TP rank 在主机内存中持有一个分片，查找仍需执行 all-reduce。在**共享主机布局**中，所有 TP rank 访问同一份完整的主机内存表副本，每个 rank 直接收集自己所需的全部行，从而免去查找 all-reduce。

对大表的随机访问可能受限于地址转换。以大页（huge page）作为底层支撑可降低这一开销。在评测所用的 GB300 容器中，主机分片表使用了支持大页的匿名映射，而共享映射则不支持。因此自动布局选择选择了主机分片，保留 all-reduce 以换取更快的主机查找。最优放置方式取决于 CPU–GPU 互联、大页可用性以及工作负载。

### 3.2 性能评测

在 4x GB300（TP4/EP4）上的配对测试中，主机卸载使 KV 缓存容量增加了 **36%**，解码吞吐量与首 token 延迟（TTFT）保持相当。这些运行使用了由大页承载的主机分片表，并保留了查找 all-reduce。全部 28 个贪心探测补全的结果均与基线一致。

要将 Engram 表放入主机内存，请设置 `SGLANG_ENABLE_DSV41_ENGRAM_HOST_TABLE=1`。

## 4. SWA 有界重放

滑动窗口 KV 为各层独有。为前缀复用而保留它会消耗缓存容量，而全序列预填充计算出的窗口状态在后续解码中也不再被直接访问。该模型的部署说明提出了有界重放（bounded replay）来降低这些存储与计算开销。

### 4.1 编码器侧有界重放

标准的前缀复用需要缓存压缩 KV、indexer 键，以及一个有效的滑动窗口检查点。编码器侧有界重放移除了对检查点的要求：前缀缓存只保留压缩 KV 与 indexer 键，而每个活跃请求自行维护一个 128 位置的窗口。

缓存命中时，SGLang 重新计算缓存前缀的最后 128 个 token，以重建窗口 KV。已缓存的压缩 KV 与 indexer 键保持不变。这以有界的重算换取更低的缓存存储开销，使匹配位置无需窗口检查点即可实现前缀复用。

### 4.2 解码器侧仅尾部计算

第 20 层是最后一个压缩 KV 源层。第 21-39 层复用它的压缩 KV 与 indexer 键，同时计算各自的窗口 KV。对每个预填充 chunk，SGLang 让第 0-20 层处理全部 token，而第 21-39 层只处理每个请求末尾至多 128 个 token。

第 0-20 层保留全上下文计算。在后面的层中，局部注意力被限制在保留的尾部，因为该边界之前的窗口 KV 不会被计算。

### 4.3 正确性边界与结果

两种模式都会在重建边界处截断局部注意力。因此，即使已缓存的压缩 KV 不变，重算出的隐藏状态也可能与全量预填充有所不同。有界重放是一种近似，其质量必须通过实测加以评估。

在以 8 条 8K token 提示为一批的配对测试中，解码器侧重放使预填充吞吐量在 **8x H200 上提升 1.56x**，在 **4x GB300 上提升 1.37x**。在 4x GB300 上，配对的 AIME 2026 评测在重放关闭与开启时测得了相同的 pass@1（各自均为 453/480 个样本正确）。

两种模式均为可选开启（`--enable-encoder-swa-bounded-replay`、`--enable-decoder-swa-bounded-replay`），且可以组合使用。编码器重放不支持投机解码。解码器仅尾部计算不支持输入 logprobs 以及完整提示隐藏状态的捕获。

## 5. 算子与执行优化

**mHC 执行与数值一致性。** 前驱预混合（predecessor pre-mix）使下一个子层的混合系数能够与当前的注意力或 FFN 一并计算。SGLang 将这部分工作重叠执行，并把混合统计量归约与 Sinkhorn 迭代融合在一起。归约采用与 batch 大小无关的固定顺序，使每个 token 的混合系数在不同 batch 组成下保持一致。对于小 batch，HC=4 的后混合会沿隐藏维度分块（tiling），以暴露出更多可并行的工作。

**FP4 索引与 TP 布局。** Indexer 打分直接从 FP4 缓存读取。Indexer 头在 TP rank 间做复制，因为对这种 MQA 形状的操作做分片并不能减少键带宽，反而需要对规模随上下文长度增长的分数做 all-reduce。

**保留量化语义的融合。** Indexer 在融合 kernel 中组合了 RoPE、FP4 量化以及打包或缓存写入。融合必须保留原始计算中的中间舍入与缩放：省去一次中间内存写入，并不意味着可以抹掉其数值影响。这减少了 kernel 启动次数与中间内存流量，同时完整保留了量化序列。

**低比率压缩。** 压缩器投影使用 BF16 检查点权重，并以 FP32 做累加与输出。比率 2 的解码池化被融合进单个 kernel，将每一对补齐的位置合并起来。压缩与索引在其输入就绪后也会与注意力准备工作重叠执行，并在注意力消费这些输出之前完成汇合。

**单 token 投影与 Engram 融合。** 对于单 token 输入，分组输出投影使用专门的 BF16 矩阵-向量 kernel，因为此时通用矩阵乘路径的 GPU 利用率很低。融合的 Engram 门控减少了 FP32 临时存储，n-gram 哈希则在单个 kernel 中完成计算。这些优化瞄准的是每个解码步都会反复出现的小型投影和稀疏内存操作。

## 6. Miles 中的强化学习

Miles 为 DeepSeek-V4.1 提供了 Megatron-Core 插件，并使用 SGLang 进行 rollout。训练后端实现了该模型的共享注意力状态、mHC 与 Engram 记忆。一个核心目标是最小化训练器与 rollout 对相同响应计算出的 log-probability 之间的差异。

**并行与共享状态。** 该后端支持 DP、TP、SP、EP、PP 和 CP。TP 与 SP 对注意力投影和压缩器组进行划分。流水线边界需要传递全部四条 mHC 残差流、前驱混合系数，以及下游消费方仍需要的注意力状态。这些状态也让被重算的层能够在本地恢复各自的输入。上下文并行让 query 保持在本地，同时在各 rank 间收集窗口 KV、压缩 KV 与 indexer 键，用于全局稀疏检索。

**量化感知训练。** 训练前向复现了推理引擎的数值处理方式：对压缩潜在表示以及 indexer 的 query 与键采用 FP4 舍入，对窗口缓存采用 FP8 舍入。直通梯度（straight-through gradient）使优化得以穿过这些离散操作。窗口缓存的前向数值使用引擎的分页缓存 kernel，梯度则由一个可微仿真来传递。稀疏注意力与索引复用 DeepSeek-V4 插件的 TileLang kernel；RoPE 与伪量化遵循推理侧的公式。

**路由重放。** Rollout Routing Replay 将采样得到的专家分配结果送入训练器的 MoE 层，防止因路由平局而选择不同的专家路径。Indexer 的 top-k 则采用重算而非存储重放：只要其量化输入一致，重放并未带来可测的对齐收益。这避免了为每个 rollout token 保留逐层选择结果。

**数值一致性。** 压缩器门控、归一化统计量、mHC 混合、Engram 门控以及 attention-sink 累加均使用 FP32，并在操作边界处进行类型转换。压缩 KV 投影的梯度 all-reduce 同样使用 FP32。确定性的归约与矩阵乘设置使重复的前向计算可复现，有助于将执行层面的波动与训练器–rollout 之间的持续性差异区分开来。

**训练与 rollout 共置。** 训练与 rollout 在 16 块 GPU 上交替进行。优化器动量以流式方式写入节点本地 NVMe，rollout 引擎恢复运行前会先卸载训练器状态。每次训练步之后，更新后的 BF16 权重按桶（bucket）传输。冻结的 FP8 Engram 表由主机内存承载，不参与权重同步。后端通过其模型桥接（model bridge）直接加载 Hugging Face 检查点。

### 6.1 验证运行

图 4 展示了一次 DAPO 训练的第 0–80 步：在 16 块 GB300 GPU 上（TP4、EP16、每步 128 个样本）、于 DAPO-Math-17K 数据集上以 2K token 响应上限运行。最初与最后各五步的平均奖励分别为 0.51 和 0.78。在所绘制的区间内，训练器与 rollout 之间的每 token KL 介于 0.0012 到 0.0017 之间，平均绝对 log-probability 差距介于 0.017 到 0.025 nats 之间。

在本次运行期间，所测得的差异始终保持在小范围内，且没有持续增长。这些测量并未隔离其成因，也不能证明数值等价。本次运行无故障地完成了 120 多个训练步。
