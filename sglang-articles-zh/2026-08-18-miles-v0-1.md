# Miles v0.1：生产级后训练

> 原文：[Miles v0.1: Production-level Post-training](https://lmsys.org/blog/2026-08-18-miles-v0-1/) · LMSYS Blog · <a href="https://www.radixark.com/">RadixArk</a> 与生态合作伙伴

我们正式发布 **[Miles v0.1](https://github.com/radixark/miles)**，一个面向前沿模型后训练的全栈生产级系统，它是 Miles 首个发布版本的后续之作 [\[1\]](#ref-1)。在 [slime](https://github.com/THUDM/slime) 简洁设计的基础上，Miles 围绕一个简单的原则对 RL（强化学习）训练循环中的每个环节进行优化：**处处经过验证、处处干净、处处可定制**。Miles 将准确性、高效性、可靠性与可扩展性作为一等目标，致力于让前沿规模的 RL 对研究者和开发者都触手可及。在本文中，我们将对 Miles 进行端到端的完整介绍。

## Miles 的 RL 循环

Miles 中的一次 RL 训练任务是围绕以下几个阶段循环展开的：

1. **Rollout**（采样生成）— SGLang 引擎生成轨迹（trajectory）。在智能体强化学习（agentic RL）中，每个多轮 rollout 会话都会与一个自己专属的隔离环境交互，该环境执行动作并产生奖励。
2. **训练** — 已完成的轨迹组由训练器（NVIDIA Megatron-LM 或 FSDP）消费，由它计算 RL 损失并更新策略。
3. **权重更新** — 新权重同步回 rollout 机群，对在飞 rollout 的中断降至最低。

接下来，我们将逐一介绍循环中的每个环节，说明 Miles 是如何做到准确、高效、可靠且可扩展的。

## Rollout

Miles 中的每一次 rollout 都由 SGLang 生成。在 SGLang 原生推理效率的基础上，Miles 解锁了完整的智能体训练工作流：多轮会话、工具执行、沙箱环境，以及 token 级忠实的轨迹捕获。

### 由 SGLang 驱动的高速智能体 rollout

Miles 通过原生集成 [SGLang](https://github.com/sgl-project/sglang) 提供高速的智能体 rollout，后者针对长序列、多轮生成做了专门优化。智能体轨迹的长度差异极大，而每一新轮次都会复用绝大部分先前上下文。默认情况下，Miles 使用 SGLang 路由器，它会把一个会话的所有轮次保持在同一个 SGLang 引擎和 DP rank 上（如果启用了 DP 注意力），以复用已缓存的前缀；同时把新会话分配给负载最低的 rank，避免少数长轨迹压垮机群的一部分。SGLang 路由器还会预先为长会话预留 KV 缓存容量。这些特性共同保证了均衡而稳定的 rollout 并发，使智能体训练中的缓存命中率保持在高位。

### 完全异步 RL

对于长上下文、工具使用和智能体类负载，rollout 时间主要由少数几条特别慢的轨迹（straggler）决定。同步调度会加剧 straggler 问题：训练器必须空转等待，直到批中最慢的轨迹返回；而 rollout 引擎又必须等优化器完成模型更新。Miles 的[完全异步强化学习](https://miles.radixark.com/docs/user-guide/fully-async)消除了这种相互阻塞：rollout 引擎可以持续不断地生成，rollout 生成始终处于在飞状态，与此同时训练器消费已完成的轨迹组并更新模型。任何一方都不会阻塞另一方。

调度以样本为粒度进行：每条完成的轨迹立即释放一个槽位，因此即便轨迹长度差异巨大，生成并发也能保持稳定。已完成的轨迹组进入一个有界数据缓冲区，从而将 rollout 吞吐量与训练节奏解耦。这个缓冲区同时也构成一个可自定义的策略边界，用户可以在不改动调度或执行逻辑的情况下，决定哪些样本保留、重试、丢弃，或者作为过期样本予以拒绝。

为了让评估也异步化，Miles 提供三种评估模式，其区别在于模型权重来自哪里。

- **共享引擎评估**：复用 rollout 机群，临时暂停新请求的提交，适合在没有额外 GPU 的情况下跑小型调试集。
- **专用评估**：使用由检查点快照加载的独立 GPU 机群，训练与 rollout 均可继续、不中断。
- **外部评估**：将检查点目录交给任意用户自备的评估器，包括非 SGLang 的服务。

三种模式都会将评估结果与产生它的检查点和训练步关联起来。如果评估在若干步之后才完成，Miles 会如实报告这一滞后，而不是把结果错误地归到当前步；评估失败则跳过该评估点，而不是终止训练。

### 智能体环境

在智能体 RL 中，大部分工作都发生在隔离的环境中。例如训练一个编程智能体，意味着给模型分配每个任务专属的沙箱：它运行命令、编辑文件、读取返回结果，最后由测试套件判定任务是否被完成。环境负责维护这些状态、执行动作，并运行产生奖励的验证器。Miles 同时运行大量这样的回合（episode），把每条轨迹记录成训练器可用来学习的形式，并将验证器的结果一路传递为奖励。

环境通过插件接入点接入 Miles。Miles 在 rollout 技术栈的不同层级提供多个插件接入点，因此一个环境可以按需接管 rollout 中的任意多少环节。我们为现有生态提供了开箱即用的集成，包括 Harbor、HUD、NeMo Gym、OpenEnv 和 Prime Intellect Verifiers。你也可以自带环境，通过同样的接入点接入。

沙箱可以运行在你选择的任意后端上。我们支持多种后端，包括 AgentENV、Daytona、E2B 和 Modal。每个回合都会获得一个全新的沙箱，由该任务自己的镜像构建，因此回合之间不共享任何内容，一次运行结束后也不留任何驻留物。

Miles v0.1 附带了持续维护的端到端配方，覆盖智能体编程与终端任务。这些配方已在真实硬件上验证过，可以直接按原样启动使用。

### Token-In-Token-Out（TITO）

在多轮智能体 RL 中，模型输出在进入下一轮之前，要经过消息解析、工具执行和对话模板渲染。这一过程可能改变分词结果、裁剪历史推理内容，或对工具调用重新序列化，导致训练器看到的 token 上下文与 rollout 时实际使用的上下文不一致。

Miles 的 [TITO](https://miles.radixark.com/docs/user-guide/agentic-rollout) 会话服务器 [\[6\]](#ref-6) 完整保留模型生成的原始 token ID。每个新一轮到来时，它只对新追加的消息做分词，并与已有前缀合并。这样，完整轨迹可以被组装成一个连续的训练样本，既保留 rollout 时原始的 logprob，又对非模型生成的 token 施加损失掩码。对每个模型家族，TITO 都会通过 CPU 往返测试和真实的 SGLang GPU 会话进行验证，从而保障 R3、OPD 和 zero-KL 对齐所需的 token 级精确性。

在 TITO 之上，Miles 正在为 Claude Code 和 Codex 这类黑盒智能体执行框架（harness）开发训练配方。这些执行框架会在运行时派生子智能体并压缩上下文，因此每个任务的轨迹数量是动态的、事先未知。为此，Miles 通过会话服务器记录完整的轨迹树，并在训练侧应用针对可变 batch size 所需的损失归一化，保持梯度尺度的一致性。

### 高效 Rollout Routing Replay（R3）

MoE RL 对 rollout 与训练之间微小的数值差异非常敏感：哪怕只有一次 top-k 路由翻转，也会同时改变该 token 的计算路径和接收梯度的专家权重。为解决这一问题，Miles 的 [Rollout Routing Replay（R3）](https://miles.radixark.com/docs/advanced/miles-router)在 rollout 阶段记录 SGLang 的专家路由结果，并在训练阶段重放这些结果。这类重放在 SGLang 中被高效处理，相比正常路由只带来极小的额外开销。

## 训练

训练器是 RL 的支柱。在 Miles 中，我们内置了众多训练器优化，使 RL 训练稳定、快速且节省资源。

### 低精度训练

Miles 支持以 NVFP4、MXFP4、MXFP8 和 FP8 进行 rollout；提供 NVFP4、MXFP8 和 FP8 的端到端训练配方；并为大多数模型提供 INT4 量化感知训练（QAT）[\[3\]](#ref-3)。此前几篇博客深入介绍了 FP8 [\[2\]](#ref-2) 和 INT4 QAT [\[3\]](#ref-3) 配方。

要在 RL 中真正发挥 Blackwell 的低精度吞吐能力，仅仅更换 GEMM 的数据类型是不够的：rollout 侧和训练侧的量化必须保持一致，否则不匹配会随权重更新不断累积，最终演变为策略发散。为此，我们把 Blackwell 原生的 MXFP8 和 NVFP4 配方 [\[9\]](#ref-9) 构建为贯穿整个技术栈的端到端精度契约：MXFP8 在 rollout、前向以及两个梯度 GEMM 中都使用硬件分块缩放（blockwise scaling）；NVFP4 对 MoE 专家权重按 token 量化，并采用在线激活缩放，以避免依赖 batch 的量化伪影；一个比特级精确（bit-exact）的量化器契约保证训练与 rollout 内核看到的是相同的量化值，并提供细粒度开关让敏感层保持在 BF16。这些配方已通过 SGLang 与 Megatron-LM 之间较低的 KL 散度得到验证。所有低精度配置都能让奖励曲线紧密贴合 BF16 基线，同时缩短 rollout 时间。

### 内存效率与磁盘卸载

在 16 个节点上异步训练一个 744B 参数的模型，会带来严峻的内存挑战。Miles 内置了大规模运行所依赖的精细内存优化，首先从优化器入手：优化器状态可以卸载到 CPU 或节点本地 NVMe 上，并在每个优化器步骤中逐 bucket 流式读回，因此它们从不需要同时常驻 GPU。在本文末尾展示的示例中，正是这种 NVMe 优化器状态流式读回，让 GLM-5.2 的优化器得以与训练引擎一起装进 32 张 GB300 GPU。除卸载之外，Miles 还提供一系列其他降低 GPU 和 CPU 内存占用的手段：在示例的 GLM-5.2 运行中，每张 GPU 节省了 30+ GB HBM 显存；当训练器与 rollout 引擎共置（colocated）时，每个节点还能节省数百 GB 的 CPU 内存。

### 两种训练后端

Miles 在统一接口之下支持两种训练后端：NVIDIA Megatron-LM 和 PyTorch FSDP。只需一个启动 flag 即可选择由哪个后端在 GPU 上持有模型；每个后端只需实现五个方法，该边界之上的所有内容都不需要改动。

- **Megatron-LM** 是默认后端，模型配方都是针对它编写的。它在内部将模型按张量并行、流水线并行、上下文并行、专家并行和专家-张量并行切分，支持 CPU 与 NVMe 优化器卸载、逐 bucket 的优化器状态流式传输，以及与并行方式无关（parallelism-agnostic）的检查点——因此之后即使改变并行布局，也无需重新转换。
- **FSDP** 在 PyTorch FSDP2 下直接训练模型自带的 HuggingFace 实现。配置和权重直接从 HuggingFace 目录加载，因此没有转换步骤，也无需编写架构相关 flag；并行方式仅为数据并行。需要小修正的架构以适配规格（adaptation spec）的形式注册，而不必分叉模型代码。

## 权重更新

在每个训练步中，优化器更新完模型权重后，新权重需要同步到所有 rollout 引擎。当训练与 rollout 运行在不同的 GPU 上时，权重同步可能成为整条流水线的主要瓶颈。针对不同的部署形态，Miles 提供了两条优化路径。借助 [P2P 权重传输](https://miles.radixark.com/docs/advanced/p2p-weight-transfer) [\[5\]](#ref-5)，训练 rank 会按照目标 SGLang 布局对每个权重 bucket 重新分片，并通过 RDMA 只把所需的分片直接写入 rollout rank 的内存。这避免了向每个 rank 广播完整模型，并让多个训练 rank 并行充当发送方。这一收益随模型规模和专家并行的增大而增长：对于 Kimi-K2 1T，P2P 把权重更新时间从 53.3 秒缩短到 7.2 秒。

对于没有直接 NCCL 或 RDMA 连接的 rollout 机群，Miles 支持磁盘差量更新。相邻的 RL 步往往只改变模型字节中很小的一部分，因此 Miles 只需发布相对于上一策略版本的差量权重（delta-weights），而无需传输完整检查点。rollout 引擎在继续生成的同时应用并校验差量权重，之后仅在把合并后的权重加载进 SGLang 时短暂暂停。通常情况下，BF16 rollout 的差量权重只包含 2% 的参数，FP4 rollout 则只有 0.5%。在一次 GLM-4.7-Flash 运行中，这将每次更新的传输量从 62.4 GB 降低到 0.69–0.83 GB，同时把生成暂停时间控制在 3–5 秒以内。

## 经过验证的 Day-0 模型支持

Miles 与 SGLang 同步，在新前沿模型权重公开的当天即完成落地。Kimi-K3 [\[13\]](#ref-13)、DeepSeek-V4 [\[10\]](#ref-10)、Inkling [\[12\]](#ref-12)、Qwen3.8 [\[14\]](#ref-14) 和 NVIDIA Nemotron 3 Ultra [\[11\]](#ref-11) 都在发布当天即可在 Miles 中训练，因为 SGLang 中的推理路径与 Miles 中的 RL 配方是并行推进的，而不是先后串行。Day-0 覆盖也不局限于某一个架构家族：它跨越稠密与 MoE 模型、混合注意力以及多模态输入。在发布日之后，几乎所有开放的前沿模型都能在 Miles 上运行，包括 DeepSeek-V3.2、Kimi-K2.6、Qwen3.8、GLM-5.2、Gemma-4、GPT-OSS 等。针对每个支持的模型，我们都在 Miles 中提供了由 CI 把关的配方。完整列表见[这里](https://miles.radixark.com/docs/models)。

## 其他后训练配方

除核心 RL 循环之外，Miles 也是一个通用的后训练平台。上文介绍的 rollout 引擎、训练器和权重更新路径都是共享组件，而非 RL 专属的机制，它们可以组合出其他训练范式：LoRA RL、在线策略蒸馏（on-policy distillation，OPD），以及监督微调（SFT）——后者复用同一个训练器，采用 SFT 损失，并且完全不需要 rollout 引擎。本节先介绍 Miles 专属工作最集中的 LoRA RL 与 OPD，最后以 Zero-KL 对齐作结——它消除了 rollout 与训练之间的数值失配，使 on-policy 数据真正做到名实相符。

### LoRA RL

Miles 支持[端到端 LoRA](https://miles.radixark.com/docs/advanced/lora) 强化学习，贯通训练、权重同步和 SGLang rollout，同时适用于 LLM 和扩散模型。基座模型保持冻结并常驻内存，Miles 只训练并同步适配器（adapter），SGLang 则在 rollout 时应用最新的适配器。

Miles 支持稠密与 MoE 模型，包括 GPT-OSS、GLM、Kimi K2/K3 和 Inkling。对于 GLM-5.2 744B-A40B，可训练参数只占 212 MB，约为该模型 BF16 基座权重大小的 0.014%——显著降低了训练成本。

除了节省内存，LoRA 在 RL 训练中还带来效率上的优势：

- **每个训练器步骤耗时更少**：训练器只需为小型低秩适配器计算权重梯度并执行优化器更新，减少了梯度计算、优化器工作量、内存流量和分布式通信，从而提升整体训练效率。
- **轻量高效的权重同步**：Miles 只需同步更新过的 LoRA 适配器。它把分布式的 TP 和 EP 分片打包成少量的扁平集合通信（flat collectives），然后将可直接用于推理服务的张量直接传输到共置的 SGLang worker，无需在主机内存中中转。由于只传输 LoRA 权重，这种方式大幅缩短了传输时间。

Miles 还提供一个多 LoRA RL 后端，用于在共享基座模型上训练和服务各自独立配置的 LoRA 适配器。这个实验性后端只更新发生变化的适配器，并通过 SGLang 路由混合适配器的 rollout，为一个 Tinker 兼容平台奠定基础——后者能以更低的计算、内存、通信和运维成本运行。

### 在线策略蒸馏（OPD）

Miles 支持[在线策略蒸馏（on-policy distillation）](https://miles.radixark.com/docs/advanced/on-policy-distillation) [\[8\]](#ref-8)，让学生模型在自己的 rollout 分布上跟随教师模型的指导进行学习。反向 KL 被实现为一种“奖励”，因此用户可以选择性地用常规 GRPO/PPO 风格的奖励来补充蒸馏。在反向 KL 的近似方式上，用户也可以选择只基于学生采样出的 token 计算，或基于一组 top-K 概率的 token 计算。

对于长上下文负载，Miles 采用稀疏的按位置教师打分（sparse per-position teacher scoring）：教师只对每个生成位置所需的候选 token 打分，避免了不必要的构建、通信和解析开销。Miles 还提供可配置的候选选择与加权策略，以支持一系列 OPD 配方。

在 B200 节点上进行的 Qwen3.5-35B-A3B 自蒸馏实验中，仅使用反向 KL“奖励”时，OPD 把平均 rollout 长度从 18.6K 缩短到约 6K token，同时将留出集上的 DAPO 性能从 84.6% 提升到 89.5%。这表明 OPD 能够迁移行为风格，同时对基准测试性能的影响降到最低。

### Zero-KL 对齐

Miles 支持 Zero-KL 对齐（Zero-KL Alignment），除了模型权重之外，还通过统一注意力、GEMM、算子精度、批处理行为等执行细节，最大限度地缩小 rollout 与训练引擎之间的数值差异。在受支持的配置下，训练与 rollout 之间的 logprob 差异可以精确保持为零。

Zero-KL 对齐目前仅支持 Qwen 3 模型家族，但我们计划尽快支持更多模型架构、内核和并行配置。

## 代码质量原则

至此，我们已经完整介绍了 Miles 的 RL 训练循环，而所有这些特性都围绕我们的代码质量原则构建：Miles 应当易于阅读和扩展。训练驱动被刻意写成近似伪代码的风格，而主要组件——如 rollout 函数、数据源、损失和奖励——都藏在带类型的小接口之后。rollout 技术栈被划分为 agent、generation 和 rollout 三层，因此一个环境或智能体框架可以只替换自己需要的那一层，而复用其余一切。这使得用户无需分叉或重写 Miles，就能轻松构建自定义的 RL 训练循环。

## Miles-Diffusion

Miles 的设计理念并不局限于 LLM，还延伸到了扩散模型。在 [Miles-diffusion](https://github.com/radixark/miles_diffusion) 中，sglang-diffusion 扮演高性能 rollout 引擎的角色，返回完整的去噪轨迹及每步的 logprob。FSDP2 训练器消费所选的 SDE 步骤，在混合分片（hybrid shard）与序列并行（SP）下优化 RL 目标。继承自 Miles 的设计，Flow-GRPO、DiffusionNFT 和 SFT 统一在同一个训练器内，损失、rollout 和奖励组件均可插拔。首批支持的模型包括 SD3.5、Qwen-Image、Wan2.2、LTX-2.3、Cosmos3 和 Minimax-H3，每个模型都有经曲线验证的配方。

在 rollout 侧，sglang-diffusion 的 rollout 把生成任务组织成微组（microgroup），复用编码器结果并对样本做批处理。在 Qwen-Image 512×512、group size 16 的设置下，相比朴素的串行生成观测到了 5.87× 的加速。每个微组随后被反序列化，并作为独立的异步流进行奖励打分，与其他流重叠执行。在训练侧，可选的确定性模式提供比特级可复现性，与公开的曲线文档和端到端 CI 一起验证配方质量。为解决训练-推理不匹配并保留对精度敏感的 DiT 参数，我们对 FSDP2 打了补丁，实现了细粒度的逐参数 dtype 控制。

## 多硬件支持

Miles 在 NVIDIA 和 AMD GPU 上运行同一套训练循环。NVIDIA 覆盖范围从 A100 到 GB300，也就是本文的参考运行和 Blackwell 低精度配方所使用的硬件。AMD 支持是通过 HIP 和 RCCL 实现的原生 ROCm [\[4\]](#ref-4), [\[7\]](#ref-7)：Miles 可运行在 MI300X 到 MI355X 上，使用同样的 SGLang rollout 集成和专用 Docker 镜像；CI 对两家厂商一视同仁，在 NVIDIA 和 AMD runner 上都运行端到端训练测试。

## 示例：使用 64 张 NVIDIA GB300 GPU 在终端使用类任务上训练 GLM-5.2

作为智能体 RL 训练的端到端示例，我们演示如何使用 Miles，在 64 张 NVIDIA GB300 GPU 上以完全异步 RL 训练 GLM-5.2 744B-A40B 模型完成终端使用类编码任务，其中 32 张 GPU 用于 rollout，32 张用于训练。为获得最佳性能，我们将训练并行度设置为 TP 2 / PP 4 / CP 4 / EP 8，推理并行度设置为 TP 8 / EP 8，并启用多 token 预测（MTP）。每个多轮终端智能体都在自己的沙箱中运行，使用 Miles 中的 OpenEnv 集成。在这个参考运行中，我们使用 65k 的最大序列长度和 64 的 batch size。

- 该参考运行稳定完成了 100 个类 terminal-bench 编码任务的 rollout 步，保持约 **4.5 分钟的训练步**，rollout 权重平均落后训练器 1.7 步。
- 通过样本级异步调度、DP 感知且负载均衡的路由，以及均衡的 SGLang 服务器配置，rollout 与训练实现**几乎完全重叠**。rollout 在并发稳定的情况下达到 96% 的前缀缓存命中率。
- 得益于 Miles 提供的深度内存优化，我们能够把 **744B 模型的异步训练装进 64 张 GPU**，训练引擎仅占用 32 张 GB300 GPU。

本次运行的完整启动脚本见[这里](https://github.com/radixark/miles/tree/main/examples/experimental/openenv/glm52_tbench2)。
