## 模型关键特性与新能力

DeepSeek-V4（1.6T Pro、284B Flash）在上一代 DeepSeek-V3.2 的基础上沿三个方向进行了扩展：

- **混合稀疏注意力**：每一层将滑窗注意力与两种压缩机制之一（4:1 top-k 或 128:1 稠密）组合，使 1M token 的上下文窗口始终可处理。
- **mHC（流形约束超连接）**：对标准残差连接的泛化，可改善梯度流动和表示质量。
- **FP4 专家权重**：原生 FP4 MoE 专家，可在最新的 Blackwell 硬件上高效服务。

## 设计、特性与性能优化

### ShadowRadix：面向混合注意力的原生前缀缓存

DeepSeek-V4 的每一层都将 **SWA**（对最近 128 个原始 token 的滑窗注意力）与 **C4**（在 4:1 压缩 KV 上做 top-512 稀疏）或 **C128**（在 128:1 压缩 KV 上做稠密注意力）二者之一组合。此外，为了维护正在压缩中的 KV 槽位，每个压缩层还有一个状态池，用于存储进行中的压缩状态。这一复杂机制打破了传统前缀缓存的假设：三个异构 KV 池和两个压缩状态池必须在预填充、解码和投机解码之间始终保持一致。下图以 N = 1024 为例展示了逐层的混合注意力范围。

![Figure 1](/images/blog/deepseek_v4/fig1_attention_scope.png)

为了解决这个一致性问题，我们提出了 **ShadowRadix**——一种面向混合注意力的原生前缀缓存机制。

**一个核心思想。**基数树索引的是**虚拟的全量 token 槽位**——一个被所有层共享的统一坐标系。从每个槽位出发，我们把**影子（shadow）**（逐池的索引映射）投影到物理池（SWA / C4 / C128）中。压缩状态的环形缓冲区位于自己的池中，但通过一个二级算术影子，每个环形槽位可以从 SWA 页索引推导出来——逻辑上嵌套在 SWA 之内，物理上相互独立。这使得生命周期得以解耦：一旦滑动窗口滑过一个节点，**墓碑机制（tombstoning）**就会释放该节点的 SWA 槽位，而它的 C4/C128 影子仍然存活、可共享。因此，一个 10k token 的请求只需保留 128 个 SWA token 加上完整的 C4/C128 压缩 KV——而其他前缀匹配的请求复用的正是这部分压缩 KV。

![Figure 2](/images/blog/deepseek_v4/fig2_shadowradix_layout.png)
*图 2. ShadowRadix 存储布局。*

由于影子只是同一来源在各池上的投影，每个池都可以独立管理自己的生命周期。我们利用这一点，为每个节点引入**双计数器锁**——`full_lock_ref` 覆盖来源（因此也覆盖它的 C4/C128 影子），而 `swa_lock_ref` 只追踪该节点是否仍落在某个请求的滑动窗口内。当 SWA 计数器归零时，我们**丢弃该节点的 SWA 槽位，但节点仍保留在树中，其压缩影子继续服务于前缀匹配**。通过要求从匹配点起存在 128 个连续存活 token 才扩展进窗口，匹配始终保持 **SWA 安全**。

嵌套的环形影子则免费继承了这一性质：由于一个环形槽位的地址是 `swa_page * ring_size + pos % ring_size`，释放某个 SWA 页会自动使其中的环形缓冲区失效——无需任何额外追踪；同时环形大小的选取也保证了 MTP 回滚不会与回绕发生竞争。

投机解码**无需对该设计做任何改动即可工作**。唯一的问题在于，草稿 token 会在验证决定接受哪些之前**先写入环形缓冲区**，因此一个先被拒绝、随后重试的步骤可能发生回绕，覆盖仍属于活跃窗口的槽位。**在开启投机解码时将环形大小翻倍**（C4：8 -> 16，C128：128 -> 256）即可留出足够余量，使任何在途的投机写入都落在活跃窗口之外，因此 **EAGLE 可以开箱即用**。

### 投机解码

DeepSeek-V4 自带一个单层 MTP 头——一个单独训练的 DSv4 解码器层，只运行 SWA 注意力（没有压缩器，也没有索引器），以上一步的隐藏状态（`h_proj`）与下一个 token 的嵌入（`e_proj`）组合作为输入。我们在 Day-0 就支持了它；而真正的系统工程在更下面一层。混合注意力的元数据非常重，如果在调度器流上急切地准备这些元数据，它在投机解码下就会成为启动瓶颈——因此我们把这份准备工作融合进了 CUDA 图，对 draft 和 verify 两个阶段都生效。

两项优化带来了这一提速：

* **图内元数据准备。**混合注意力每一轮的元数据都很重——SWA 页索引、影子映射的池槽位、压缩器/索引器计划、各池的写入位置——但它们本质上都是围绕页表和长度的索引算术，可以干净地落到设备端算子上。因此每个捕获的图只需要把原始批状态（活跃请求、当前长度、新 KV 的目标位置）作为每次重放的输入拷贝进固定缓冲区；被捕获的算子在图内重建其余内容，重放期间 Python 完全不触碰每轮的执行路径。这消除了原本会在投机解码中占据主导地位的每步启动开销。
* **重叠调度。**CPU 侧工作（结果处理、批准备、内存释放）与 GPU 执行并行进行。

### HiSparse：用分层内存为稀疏注意力提速

我们近期发布的 [HiSparse](https://www.lmsys.org/blog/2026-04-10-sglang-hisparse/) 是一种**将不活跃的 KV 缓存卸载到 CPU 内存**的技术，可为稀疏注意力带来更大的批规模和更高的吞吐量。HiSparse 与 **C4 层**天然契合：每一步中，索引器的 top-k 只会触达一小部分压缩位置，因此**任意时刻大部分 C4 KV 都处于不活跃状态，可以驻留在 CPU 上**。C128 是稠密的（每个位置都会被触达），而 SWA 本身已经很小（128 个 token），所以二者都无法从卸载中获益。通过用 CPU 内存池只扩展 C4 KV 缓存池，我们将长上下文服务的整体 token 容量和吞吐量提升了**最高 3 倍**。

- **面向混合注意力的全新 FlashMLA 路径**：DeepSeek-V4 的混合注意力将局部窗口上的 SWA 与对 C4（压缩 KV 上的稀疏 top-k）或 C128（压缩 KV 上的稠密注意力）的「额外」注意力组合在一起。我们集成了更新后的 FlashMLA 接口，让 SWA 与这部分额外注意力在单次融合算子调用中运行（算子同时接收 `k_cache` 与 `extra_k_cache` 及各自索引），并在前向传播中共享元数据构建。目标 GPU 是支持相应算子的 Hopper/SM90 与 Blackwell/SM100。

- **FlashInfer TRTLLM-Gen 融合 MoE（MXFP8 x MXFP4）**：DeepSeek-V4 采用原生 FP4 专家权重，使小批量 MoE 解码对专家权重带宽十分敏感。我们通过 FlashInfer 集成 TRTLLM-Gen 融合 MoE 后端，将 MXFP8 激活与 MXFP4 专家权重配对，并把 SGLang 的权重/scale 布局适配为算子期望的格式。该路径面向 Blackwell GPU，依赖 Blackwell 特有的 FP4 张量核心机制以及分块/常驻（tiled/persistent）执行方式。

- **带 split-K 的 TileLang mHC 算子**：mHC 将残差流替换为对 `hc_mult` 条并行分支的逐 token 混合，混合权重由 GEMM 输出上的 Sinkhorn 归一化产生。在低延迟解码场景中，GEMM 之前的 TileLang 算子可能成为瓶颈，因为批规模小、并行度有限。为此，我们扩展了两阶段的 split-K TileLang 算子（`mhc_pre_gemm_sqrsum_splitk_kernel`），把 K 维划分到不同 CTA 上，提升小批量下的 GPU 利用率。我们还集成了融合的 `mhc_pre_big_fuse_tilelang` 路径，将 RMSNorm、Sinkhorn 和残差混合合并进一个算子，并启用了 PDL。

- **DeepGEMM Mega MoE 集成**：我们在 Blackwell 上集成了 DeepGEMM 的 Mega MoE 路径。该算子将 EP dispatch、第一个 FP8xFP4 专家 GEMM、SwiGLU、第二个 FP8xFP4 专家 GEMM 和 EP combine 融合为单个基于对称内存的巨型算子（mega-kernel），让 NVLink 通信与张量核心计算相互重叠。由于 Mega MoE 要求经过变换、带 UE8M0 scale 因子的 FP4 专家权重，我们适配了现有的 EP/MoE 激活路径，使其直接消费变换后的布局。这样既避免了在 GPU 内存中常驻两份专家张量，又能同时启用 DeepEP 路径和低延迟的 Mega MoE 路径。

关于算子级集成模式的背景，请参阅我们早先的博客 [Scaling DeepSeek on GB200](https://www.lmsys.org/blog/2025-09-25-gb200-part-2/)。

### 其他算子优化

下面我们详细展开两个有代表性的算子。

![Figure 5](/images/blog/deepseek_v4/fig5_kernel_opts.png)
*图 5. 两项通用的算子级优化。左：Flash Compressor 将朴素的 5 阶段压缩链融合为单次片上处理，把 HBM 往返次数从 5 降到 2。右：Lightning TopK 用 8 个 CTA 组成的 cluster 上的基数选择（radix-select）归约取代全局排序——每个 CTA 先构建本地 10 位基数直方图，cluster 对直方图做归约，选出一个恰好容纳 K = 512 个候选的阈值，随后每个 CTA 只散射自己高于阈值的条目。*

#### Flash Compressor：IO 感知的精确压缩

压缩注意力通过按 token 得分做 softmax 加权平均，把一组 token 压缩为一个 KV。朴素的实现**要访问 HBM 五次**，并且在非连续维度上运行 softmax，因此压缩本身的开销往往超过它所喂给的压缩注意力。我们把**整条流水线融合为单次片上处理**（图 5 左），C4 的 softmax 保持在 warp 内完成，C128 则做一次 CTA 范围的归约。在 H200 上，这可以达到**峰值内存带宽的 80%**，相比朴素的 PyTorch 流水线快**超过 10 倍**。

#### Lightning TopK

稀疏注意力依赖索引器中的 top-k 选择步骤。在 4:1 压缩下，1M token 的上下文仍会产生**每请求 256K 个候选**。在这个规模上，朴素实现即使 batch size 为 1 也可能耗时**超过 100 微秒**，超过上游索引器 GEMM 和下游稀疏注意力算子的延迟。我们用**定制的基数选择（radix-select）算子**来解决长上下文解码的这个问题。该算子不执行完整的全局排序，而是先收窄候选集，并利用**带异步拷贝的 CUDA cluster 启动**来提升并行度，让内存搬运与选择过程相互重叠。这避免了代价高昂的全局排序以及经由 HBM 的跨 CTA 同步，从而有效地将小批量下的 top-k 延迟降到**约 15 微秒**，并在大批量下依然保持高性能。

### 并行与部署

- **面向长上下文预填充的上下文并行（CP）。**DSv4 混合注意力路径的大部分组件——SWA、C4/C128 压缩器、索引器——都无法沿注意力头切分，因此 TP 在长提示上会遇到天花板。CP 以轮转方式把 token 分配到各个注意力 rank 上：每个 rank 拥有序列的 `1 / cp_size`，所有逐 token 元数据（SWA 页索引与长度、C4/C128 位置、页表、索引器 top-k 长度）都在本地重新索引，而压缩器的输出写入位置保持全局，从而保证产出的 KV 仍然连续落盘。这里的 CP 特指预填充阶段的 NSA 路径，也正是长上下文首 token 延迟（TTFT）得以扩展的关键。
- **高 TP 下的 FlashMLA 注意力头填充。**FlashMLA 要求 `num_heads` 在 Blackwell 上是 128 的倍数（Hopper 上是 64），而较大的 TP 度很容易违反这一约束。我们没有重写算子，而是在每次调用时在张量层面做填充：分配一个全宽的 Q 缓冲区，把该 rank 真实的注意力头拷贝进对应切片，其余部分填零，调用算子后再裁剪输出。额外的 FLOPs 带来的开销可以忽略不计，因为 MLA 解码通常受限于 KV 读取的内存带宽。
- **面向 PD 分离的分页 KV 传输。**我们在 SGLang 现有的 PD 传输协议上扩展了按页索引的 KV 传输。页通过标准路径按索引搬运，并在接收端通过它自己的影子映射重新解读，因此传输层完全无需感知 DSv4 不均匀的设备端布局（参见 ShadowRadix）。
- **基于 DeepEP + Mega MoE 的专家并行。**DSv4 的 MoE 构建在 **DeepEP** 之上，由其完成 all-to-all 专家路由。在此之上，我们集成了 DeepGEMM 的 **Mega MoE** 路径（见上文算子集成一节）。Mega MoE 期望的专家权重布局与标准 DeepEP 路径不同；我们将 Mega MoE 权重设置为 DeepEP 专家张量的别名视图（aliased view），这样大规模部署就无需在 GPU 内存中为专家权重支付两份拷贝的代价。完整路径还在 EP 侧配合了 SwiGLU-clamp 和 JIT 激活融合。

### 分层多流重叠

注意力准备工作是一大群小算子——Q/KV 投影、压缩器、索引器——在小批量下，每个算子都填不满 GPU。串行启动开销随即开始主导解码。

我们在两个层级上把它们展开到多条 CUDA 流上（图 6）。顶层让四个准备算子并行运行。索引器是其中最重的一个，因此在它内部我们又做了二次拆分——Q 投影、权重投影和压缩器 GEMM 也相互重叠。像 `q_lora_ready` 和 `q_scale_ready` 这样的事件会在依赖一完成时就跨流交接，因此任何工作都不必等待整条流排空。

*图 6. 注意力准备的两级流展开，细粒度的 `q_lora_ready` / `q_scale_ready` 事件跨流串联有依赖的工作。*

## 强化学习（RL）——Miles 支持

![Figure 4](/images/blog/deepseek_v4/fig4_day0_rl.png)
*图 4. DeepSeek-V4 的 Day-0 可验证 RL 流水线：Miles 与 SGLang 共同提供了稳定性（R3 与 indexer replay，Step-0 训练-推理 diff 约 0.02-0.03）、高效率（DP/TP/SP/EP/PP/CP、Tilelang 算子、FP8/BF16 rollout 与训练）以及广泛的硬件支持（Hopper、Blackwell、Grace Blackwell）。*

### 训练后端：在 Megatron-LM 中建模 DeepSeek-V4

对于 DeepSeek-V4，由于全新的模型架构，大部分算子都需要重新实现，例如复杂的压缩注意力、新的 sparse-MLA 与 indexer 模块，以及 mHC 层。

#### 并行：支持 DP/TP/SP/EP/PP/CP

Megatron 中的全部六种策略（DP/TP/SP/EP/PP/CP）均已支持。

- **TP 与 SP** 贯穿压缩注意力模块实现。
- **PP**：mHC 的四条流必须跨越流水线阶段边界保留下来，接收阶段才能在每个子层对它们做混合，因此我们通过 p2p 传输的是 `[seq, batch, hc_mult, hidden]`，而不是通常的 3 维张量。
- **CP**：我们在 DeepSeek-V4 压缩注意力上支持 all-gather CP。C4 压缩器的 overlap 变换会把每个压缩组的一半沿序列方向后移一个位置（相邻组因此能以零额外 KV 代价共享上下文），所以在 CP 下这个位移会跨越 rank 边界。仅就 overlap 而言，halo exchange 就能解决，但下游的索引器 top-k 反正需要所有压缩位置，因此我们把两个集合通信合并成一次 all-gather。举例来说，1024 token 的序列在 CP=4 时每个 rank 持有 256 个 token；我们在 CP 组内 all-gather 完整的压缩张量，在拼接好的序列上应用 overlap，再切回本地视图。C128 层没有 overlap 变换，完全跳过 all-gather。

#### 算子

得益于 Slime 为 GLM-5 提供的算子支持，我们采用并扩展了它们的算子以适配 DeepSeek-V4。

- 我们将 Tilelang DSA indexer 算子适配到 DeepSeek-V4 的索引器架构，并在 lightning indexer 中使用。
- 我们扩展了 sparse-MLA Tilelang 算子，在 softmax 分母中加入每头可学习的 attention-sink logits，以支持核心注意力。
- mHC 使用融合的 Tilelang Sinkhorn 算子。

### RL 特性

我们还在 DeepSeek-V4 训练栈中支持并测试了多项重要的 RL 特性，包括 Rollout Routing Replay（R3）、TIS/MIS、FP8 训练以及 FP8 注意力 QAT：

- **支持 FP8 rollout 与 FP8/BF16 训练。**我们支持 FP8 rollout，以及 BF16 和 FP8 两种训练精度，并在权重更新中加入了量化处理器。

- **注意力 QAT。**我们在 rollout 时以 FP8 服务的路径上（压缩器 KV、原始 KV、索引器查询）模拟 FP8 激活量化，以便在使用 FP8 rollout 精度时与 SGLang 在算子级数值上保持一致。

- **Rollout Routing Replay（R3）。**我们在 miles 中把 R3 处理器和 TIS/MIS 损失扩展为 `(b, s, h, d)` 格式，以支持 DeepSeek-V4 后端。

- **Indexer replay（实验性）。**除 MoE 路由之外，DeepSeek-V4 还有第二个随机算子——DSA 索引器对压缩 KV 的 top-k。我们实现了 indexer replay 机制：在 SGLang 的压缩注意力后端中捕获 rollout 的 top-k，通过现有的 rollout 通道传输，并在训练时逐 C4 层重新注入。*这是一个实验性特性——该流水线通过了短上下文正确性检查，但尚未经过端到端验证。*


### 混合精度技术栈上的数值精度

- 我们在整个训练、检查点转换和权重更新过程中，仔细维护敏感主权重及其梯度的 FP32 精度。
- 压缩器的反向传播是沿一个长轴做 softmax 加权求和，其中最小的加数也至关重要；跨 TP rank 累积的 BF16 舍入会使求和偏向幅值最大的贡献者。我们仅将这一处 all-reduce 切换为 FP32。
- 我们有选择地冻结了不稳定的路径：mHC 中的 Sinkhorn（作为*混合预言机*）、MoE 路由门控、每个专家的分数修正偏置，以及按哈希路由的早期层。
- 为避免 KL 损失中出现随机数值尖峰，我们固定了若干确定性设置：cuDNN 确定性模式、NCCL 使用 Ring 算法、TransformerEngine 关闭其非确定性路径、cuBLAS 使用固定工作区。代价是约 10–15% 的吞吐量。

此外还有多项 Megatron 层面的修复：

- 修复了分布式优化器在 FP32/BF16 混合参数组下的检查点精度问题。
- 为解决恢复检查点时遇到的 OOM，我们在加载期间将优化器状态分配在 CPU 上，以避免出现过高的峰值内存。


### 训练结果
我们用这套训练栈在 DAPO 上启动了 285B 模型的训练，最大响应长度为 4096，运行在 32 张 GB300 GPU 上，采用 TP/SP/EP/PP 并行、FP8 rollout + BF16 训练，并启用了 R3。训练动态保持稳定：第一步的 rollout/训练 log-prob 漂移约为 0.023，奖励和评测分数在整个训练过程中稳步增长。

## 基准测试说明

图 1 是 SGLang 在 DeepSeek-V4 上的 Day-0 快照，并非决定性的性能排名。基准测试的设置充满各种细节，我们可能遗漏了某些本可以缩小差距的配置项——如果你发现任何问题，欢迎提交 issue，我们很乐意重新跑一遍。

**测试设置。**B200 Pro（1.6T）使用 TP=8；H200 Flash（285B）使用 TP=4。单批解码，OSL=4096，前缀为从《红楼梦》截取的 30K token。解码吞吐量为 `1000 / TPOT (ms)`。

**投机解码**（按各引擎官方配方尽最大努力配置）：

- **SGLang**：EAGLE 3/1/4（`num-steps=3, eagle-topk=1, num-draft-tokens=4`）；Pro 和 Flash 上的接受长度均约为 2.5。
- **另一款开源引擎**：B200 Pro 上使用 MTP-3（接受长度约 1.19）。逐位置的分解高度偏斜——位置 0/1/2 分别接受 2226 / 354 / 55 个 token——因此投机路径看起来基本只在接受位置 0。这表明 MTP 路径在 Pro 上可能没有发挥出全部效果；我们未做进一步调查。在 H200 Flash 上，`num_speculative_tokens >= 2` 会在服务器启动时触发 `paged_mqa_logits_metadata` 算子断言，我们未能及时绕过，因此 H200 面板退回到 MTP-1（接受长度约 1.92）。

**长上下文。**我们把正面对比固定在 30K，因为这一轮我们在另一款开源引擎上没能跑出稳定的长上下文结果（200K 以上的输入在我们的超时时间内没有返回）。可能存在能够处理更长上下文的配置；只是我们没来得及找到。
