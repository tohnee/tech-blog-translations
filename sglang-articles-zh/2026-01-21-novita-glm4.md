# 面向生产优化 GLM4-MoE：借助 SGLang 将 TTFT 缩短 65%

> 原文：[Optimizing GLM4-MoE for Production: 65% Faster TTFT with SGLang](https://lmsys.org/blog/2026-01-21-novita-glm4/) · LMSYS Blog · Novita AI

## TL;DR

Novita AI 基于 SGLang 开发了一整套经过生产环境检验、收益显著的优化方案，用于部署 GLM4-MoE 模型。

我们提出了一套**端到端性能优化策略**，覆盖整条推理流水线上的各类瓶颈——从内核执行效率到跨节点数据传输调度。通过引入**共享专家融合（Shared Experts Fusion）**与 **Suffix Decoding（后缀解码）**，我们观察到关键生产指标的大幅提升，包括：

- 首 token 延迟（TTFT）最多降低 **65%**
- 每 token 生成时间（TPOT）改善 **22%**

以上提升均在智能体编程（agentic coding）负载下测得。

所有结果均在 **H200 集群、TP8 与 FP8 配置**下完成验证，为在严苛的生产环境中同时实现最优吞吐量与低延迟提供了一套经过实战检验的蓝图。

## 我们如何为 GLM-MoE 实现核心生产优化

### 1. 共享专家融合（Shared Experts Fusion）

- [SGLang PR #13873: Shared Experts Fusion](https://github.com/sgl-project/sglang/pull/13873)

![Shared Experts Fusion](/images/blog/novita-glm4/shared-experts-fusion.png)

这项优化完全要归功于针对 DeepSeek 模型的原始工作。如上图所示，GLM4.7 等 MoE 模型会将所有输入 token 送入一个共享专家（shared expert），同时每个 token 还会被模型的路由器（router）单独分配到各自选出的 top-k 个路由专家（routed experts），随后再对所有专家的输出进行加权聚合。以 GLM4.7 为例，它拥有 160 个路由专家和 1 个共享专家，每个 token 选取其中 8 个路由专家。在早期实现中，这两部分是分开处理的。鉴于二者的张量形状与计算流程完全相同，自然的做法就是将共享专家合并进路由 MoE 结构加以统一——即从总共 161 个专家中选取 top 9，并将共享专家固定放在第 9 位。

如该 PR 所记录，这项优化最多可将 TTFT 提升 23.7%、ITL 提升 20.8%。这些收益并不意外：在 TP8 和 FP8 配置下，中间维度（intermediate size）仅为 192——对 H200 硬件而言相当小——融合操作大幅提高了流式多处理器（SM）的利用率，并显著降低了内存 I/O 开销。

### 2. QK Norm 融合（Qknorm Fusion）

- [SGLang PR #15141: Qknorm Fusion](https://github.com/sgl-project/sglang/pull/15141)
- [SGLang PR #15305: Qknorm Fusion Fix](https://github.com/sgl-project/sglang/pull/15305)

![Qknorm Fusion](/images/blog/novita-glm4/qknorm-fusion.png)

这项移植工作建立在 Qwen-MoE 已有优化的基础上，其底层思路非常直接：由于两个算子都按注意力头（head）逐个进行计算，将它们融合为单个内核是一种自然的做法。我们的贡献在于对这一融合内核进行适配，以支持 GLM4-MoE 变体的特殊情况——其注意力头内只有一半维度参与旋转。

### 3. 异步传输（Async Transfer）

[SGLang PR #14782: Async Transfer](https://github.com/sgl-project/sglang/pull/14782)

![Async Transfer Schedule](/images/blog/novita-glm4/async-transfer-schedule.png)

在采用 PD 分离（预填充-解码分离）加重叠调度的场景中，吞吐量虽然能提升约 10%，但 TTFT 会显著恶化。我们观察到，在当前的预填充实现中，数据传输会被推迟到下一批（batch）的内核启动之后才开始。对于像 GLM4.7 这样拥有 92 层的模型来说，不启用 CUDA 图（CUDA Graph）时的内核启动可能非常耗时（往往需要数百毫秒，甚至超过 1 秒）。

为解决这一问题，我们在修改中将传输步骤适当提前，安排在与之对应的 GPU 操作完成后立即调度执行。此外，传输被放入一个独立线程；通过仔细处理潜在的数据竞争（data race）结构，传输可以不阻塞主线程地进行。

对于内核启动次数繁多的模型，这一优化带来的收益非常可观。在高负载下，该优化最多可节省约 1 秒的 TTFT，如下图所示。

![Async Transfer TTFT Gains](/images/blog/novita-glm4/async-transfer-ttft.png)

## Suffix Decoding（后缀解码）

智能体编程（agentic coding）场景（如 Cursor 和 Claude Code）中存在大量可复用的代码模式，这使得 Suffix Decoding 这类针对性性能优化成为可能。

### 背景：智能体编程中的推理瓶颈

LLM 智能体擅长代码生成任务，但延迟仍是一个重大挑战。传统的投机解码（speculative decoding）通过提前预测多个 token 来加速推理，但常见做法需要额外训练草稿模型（draft model），带来额外的工程复杂性。

### Suffix Decoding 的工作原理

![How Suffix Decoding Works](/images/blog/novita-glm4/suffix-decoding.png)

Suffix Decoding 采用了截然不同的思路——它完全不依赖任何模型：

- 不依赖任何额外的模型权重
- 利用先前生成输出序列中的模式来预测后续 token
- 当当前请求的后缀（suffix）与某个历史模式匹配时，便沿着该历史序列继续进行投机

### 数据验证：输出模式重复性分析

通过分析 22 个 Claude Code 会话（17,487 轮对话），我们发现：

- 39.3% 的输出存在模式重复：相似的工具调用与响应模式出现频率很高
- 高度结构化的智能体行为："Let me..."、"Now let me..." 等固定短语频繁出现

为支持后续研究，我们已在 Hugging Face 上开源该评估数据集：[Hugging Face 上的 Agentic Code Dataset](https://huggingface.co/datasets/novita/agentic_code_dataset_22)

### 性能对比

在已启用内置 MTP 加速的基础上，Suffix Decoding 进一步将 TPOT 降低了 22%（从 25.13ms 降至 19.63ms）：

| 指标 | MTP | Suffix Decoding | 变化 |
| :--- | :--- | :--- | :--- |
| 平均 TPOT | 25.13 ms | 19.63 ms | -21.90% |
| 中位数 TPOT | 25.95 ms | 20.05 ms | -22.70% |

## 结论

这些优化组合起来，为 SGLang 部署带来了全面的性能提升：

| 优化项 | 影响/收益 |
| :--- | :--- |
| 共享专家融合（Shared Experts Fusion） | 解决 MoE 模型中的计算效率问题 |
| QK-Norm-RoPE 融合 | 降低内核启动开销 |
| 异步传输（Async Transfer） | 优化分离式部署中的数据搬运 |
| Suffix Decoding | 利用模式重复为智能体编程实现投机解码 |

其中大部分组件已合并进上游主线或正在集成中，欢迎到 SGLang 仓库查看。

## 如何复现

此处仅展示与性能相关的关键参数。完整的启动脚本（基线 vs 优化版）、基准测试工具（harness）与性能剖析（profiling）数据已发布于 GitHub：[novitalabs/sglang（glm_suffix 分支）](https://github.com/novitalabs/sglang/tree/glm_suffix)。

### 核心优化 flag（SGLang 运行时）

```bash
--tp-size 8
--kv-cache-dtype fp8_e4m3
--attention-backend fa3
--chunked-prefill-size 16384
--enable-flashinfer-allreduce-fusion
--enable-fused-qk-norm-rope
--enable-shared-experts-fusion
--disaggregation-async-transfer
```

### 投机解码配置（智能体编程负载）

```bash
--speculative-algorithm NEXTN
--speculative-num-steps 3
--speculative-eagle-topk 1
--speculative-num-draft-tokens 4
```

### Suffix Decoding 配置（可选）

```bash
--speculative-algorithm SUFFIX
--speculative-suffix-cache-max-depth 64
--speculative-suffix-max-spec-factor 1.0
--speculative-suffix-min-token-prob 0.1
```
