# 使用多 token 预测（MTP）加速 SGLang

> 原文：[Accelerating SGLang with Multiple Token Prediction](https://lmsys.org/blog/2025-07-17-mtp/) · LMSYS Blog · Eigen AI Team

## TL;DR

SGLang 现已支持以下高级特性的平滑组合：**多 token 预测（MTP）**、**大规模专家并行（EP）**与 **PD 分离（预填充-解码分离）**。这一集成通过全新的解码范式、更优的并行策略和更高效的资源利用，带来**最高 60% 的输出吞吐量提升**，且不牺牲生成质量。如果你正在服务 DeepSeek V3 等模型，SGLang 现已将 MTP 作为即插即用特性提供，性能提升立即可用。复现步骤见[这里](https://github.com/sgl-project/sglang/issues/7998)。

运行在 NVIDIA GPU 上的 SGLang 推理框架，让 AI 从业者能够轻松实现规模化推理，赋能终端用户“聪明地思考”，以最高性能释放最先进语言模型的推理能力。

## 引言

尽管大语言模型的能力持续提升，其逐 token 的解码过程在本质上仍是串行的，这构成了推理吞吐量的关键瓶颈。这一限制在高需求应用中尤为明显——在这些场景下，最大化 GPU 利用率是实现高性能与低成本部署的关键。

为解决这一问题，SGLang 将多 token 预测（MTP）引入开源推理生态。这是一种先进的投机解码技术：用轻量级草稿模型预测多个草稿 token，再用完整模型单次前向传播并行验证。在我们的基准测试中，MTP 为 DeepSeek V3 带来最高 60% 的输出吞吐量提升，且生成质量没有任何损失。随着 MTP 的全面集成，SGLang 继续推动开源 LLM 推理服务的前沿，将此前仅存在于专有系统中的高级解码能力变得触手可及、可用于生产环境。

## 什么是多 token 预测（MTP）？

传统自回归解码一次只生成一个 token，且依赖之前已生成的全部 token。这种串行过程限制了并行度和速度。

MTP 是一种投机解码技术，它通过轻量级*草稿*模型快速提出多个未来 token，再由完整*目标*模型在单次前向传播中并行验证，从而加速生成。

MTP 将生成过程分为两个阶段：

-**草稿（Drafting）：** 轻量级草稿模型在单次快速前向中预测出包含 n 个 token 的短候选序列。这里以一个候选序列为例。  
   (1) *“Today is a sunny”* 是目标模型当前已生成的前缀。  
   (2) *“day” 由目标模型的 extend/预填充（prefill）阶段首先生成。*  
   (3) *“and” 是草稿模型的 extend/预填充阶段生成的第一个草稿 token。*  
   (4) *“it’s so hot” 是草稿模型解码迭代生成的三个额外草稿 token；在本例中，“and it’s so hot” 对应 n=4。*

-**验证（Verification）：** 完整目标模型随后并行验证全部 n 个草稿 token，接受与其自身输出匹配的最长前缀，必要时对剩余部分重新采样。  
   我们以 **n = 4** 为例走一遍流程：  
   - **目标模型**在 extend/预填充阶段之后首先生成初始 token：  
     → *“day”*  
   - **草稿模型**随后在 extend/预填充之后推测下一个 token，并在自回归解码中再推测 3 个 token：  
     → *“and it’s so hot”*  
   - **目标模型**验证完整序列：  
     → 它接受 *“and it’s”*  
     → 拒绝 *“so hot”*，改为重新采样 *“very”*

![解释 MTP 的流程图](/images/blog/mtp/flowchart_hr_v3.png)

### MTP 为什么快

MTP 加速的关键在于并行。至关重要的是，验证步骤在 GPU 上是**完全并行化**的，用一次并行验证取代了 *n* 个串行解码步骤。

MTP 的有效性取决于每个验证步骤能接受多少个草稿 token，这一指标称为**接受长度（acceptance length）**。例如，平均接受长度为 2.4 意味着每次平均跳过 2.4 个解码步骤，在长序列生成中会累积出可观的速度提升。

MTP 不以牺牲生成质量或确定性为代价。每个投机 token 仍由同一个完整模型验证和批准，确保输出与标准解码完全一致，没有任何近似或微调。

这项新能力与 SGLang 的高级特性全面集成，包括：
* 数据并行注意力（DP Attention）
* 专家并行负载均衡器（EPLB）
* DeepEP MoE
* 两批重叠（Two Batch Overlap）
* PD 分离（预填充-解码分离）
* CUDA 图（CUDA Graph）
* 多种注意力后端

## 性能评估

我们以 DeepSeek V3 模型为测试平台，对 MTP 全面集成进 SGLang 推理框架后带来的性能提升进行了全面评估。本节包含两个案例研究，分别展示小规模与大规模部署场景下的改进。

### 部署场景与设计动机

小规模部署配置参考了某知名生成式 AI 公司的生产需求，该公司运营一款延迟敏感、面向开发者的产品。具体而言，该公司要求每 rank 持续输出至少 60.4 tokens/sec，以满足应用层的服务水平协议（SLA）。这一要求决定了我们第一个案例研究所采用的配置。为评估更重负载下的可扩展性，我们还在大规模集群环境中评估了 MTP。

### 案例研究 1：小规模部署

在这个场景中，我们在 16 块 H200 GPU 上部署两个解码节点，每 rank 运行 2 个并发请求，输入序列长度为 65,536 token，输出序列长度为 4,096 token。作为基线，我们测试了不开启 MTP、不开启重叠调度的情况，系统实现了每 rank 51 tokens/sec 的输出吞吐量。仅使用 SGLang v0.4 引入的重叠调度功能，我们达到每 rank 60.4 tokens/sec，无需 MTP 即可满足生产阈值。
开启 MTP 后，系统显著超越了这一基准：
* 使用 3-token MTP 窗口和 topk=1，系统达到每 rank 81.5 tokens/sec 的吞吐量，平均接受长度为 2.18 token。
* 使用 4-token MTP 窗口和 topk=1，吞吐量提升至每 rank 82.0 tokens/sec，平均接受长度为 2.44 token。

![小规模吞吐量图](/images/blog/mtp/small_scale_throughput_hr_v2.png)

相比基线（即不开重叠调度、不开 MTP），这些结果实现了 +60% 的输出吞吐量提升。该案例表明，即便在并发水平适中的小规模集群中，MTP 也能带来可观的性能提升，让受限的 GPU 资源预算内同样能获得可扩展的性能。

| 重叠调度 | MTP       | 每 rank 吞吐量（tokens/sec） |
|--------------------|-----------|----------------------------------|
| ❌                 | ❌        | 51.0（基线）                  |
| ✅                 | ❌        | 60.4（+20.4% ↑）                  |
| ❌                 | ✅ 3-token| 81.5（+59.8% ↑）                  |
| ❌                 | ✅ 4-token| 82.0（+60.8% ↑）                  |

### 案例研究 2：大规模部署

为评估可扩展性并展示 MTP 对大规模 EP 与 PD 分离的支持，我们扩展到由 128 块 H200 GPU 组成的 16 节点集群，其中包含 4 个预填充节点和 12 个解码节点，每 rank 运行 128 个并发请求，输入序列长度为 2,000 token，输出序列长度为 100 token。在这一高吞吐环境中，我们将解码配置为 `topk = 1`、`step size = 1` 和 `draft_token_num = 2`。

将开启 MTP 的解码与基线（即不开重叠调度、不开 MTP）对比，我们观察到输出吞吐量提升 +14.2%，证明在生产级负载下的大规模场景中，MTP 同样能带来可衡量的性能提升。

![大规模吞吐量图](/images/blog/mtp/large_scale_throughput_hr.png)

## MTP 最佳实践

要在 SGLang 中启用多 token 预测，在配置中开启它并将 `draft_token_num` 设为 2——这是一个兼顾收益与风险的均衡选择，能在大多数负载下提供稳定的性能提升。如果 GPU 还有余量，可以将 `draft_token_num` 提高到 4 甚至更大以进一步推高吞吐量，但收益可能随系统维持 token 接受率的能力而递减。反之，如果 GPU 已经在处理大批量请求或接近满载，将草稿长度保持在 2 或 3 通常更高效，也能避免引入额外负载。

你可以通过日志监控接受率，随时间对这个参数进行微调。如果平均接受长度持续高于 2，就有尝试更长草稿的空间；但如果接受率开始下降，建议调回较小值，让系统保持在舒适区间内。

## 未来工作

-**大规模优化**
    我们正在持续优化大规模 MTP 部署的性能，重点是多节点系统上的调度效率与内存带宽利用率。

-**重叠调度兼容性**
    当前 MTP 实现尚不支持重叠调度。我们预计 MTP 与重叠调度集成后还会带来额外的性能提升。相关开发正在进行中。
