# 迈向 Blackwell 原生的 8-bit 与 4-bit RL：Miles 中的端到端 MXFP8 与 NVFP4 强化学习

> 原文：[Towards Blackwell-Native 8-bit and 4-bit RL: End-to-End MXFP8 and NVFP4 RL in Miles](https://lmsys.org/blog/2026-07-29-mxfp8-nvfp4-rl/) · LMSYS Blog · Ziang Li, humans& and Miles Team

> TL;DR：我们在 Miles 中实现了两种 Blackwell 原生的强化学习（RL）配方：端到端 MXFP8，以及面向 MoE 专家的每 token NVFP4。两者都得到贯穿检查点转换、Megatron 训练、SGLang rollout 与实时权重更新的细粒度精度控制的支持。MXFP8 覆盖 rollout、前向传播、权重梯度 GEMM 和数据梯度 GEMM。NVFP4 在其 MoE 专家路径上采用在线每 token 激活缩放，两种格式均支持高精度或反量化（dequantized）的反向传播模式。在 8x B200 上的 Qwen3-30B-A3B 配方消融中，BF16 与全部五种低精度配置的原始奖励曲线高度重叠，同时 MXFP8 与 NVFP4 缩短了 rollout 时间。

## 引言

在低精度 RL 中，rollout（采样生成）、训练、检查点转换与实时权重更新必须遵循同一份精度契约（precision contract），否则采样器与训练器的策略就会彼此偏离。Miles 与 SGLang RL 生态此前已经引入了低精度配方：LMSYS 的 [FP8 RL 博文](https://www.lmsys.org/blog/2025-11-25-fp8-rl)表明，在训练与采样中统一使用 FP8，相比「BF16 训练 + FP8 rollout」能降低不匹配；[INT4 QAT 博文](https://www.lmsys.org/blog/2026-01-26-int4-qat)则表明，训练期间的伪量化（fake quantization）配合 W4A16 rollout 可以让 INT4 变得实用。我们在这项工作的基础上扩展到 Blackwell 原生格式：在 Miles 中实现 MXFP8 与 NVFP4 配方，并向 SGLang、TransformerEngine、FlashInfer、Megatron 与 cuDNN frontend 贡献了配套组件。公开路线图见 [miles#615](https://github.com/radixark/miles/issues/615)。

主要贡献如下：

1. 端到端 MXFP8 RL：rollout、前向传播、权重梯度 GEMM 和数据梯度 GEMM 全部使用 MXFP8。
2. 面向 MoE 专家权重的每 token NVFP4 RL，采用在线每 token 激活缩放。
3. 细粒度精度控制：让选定的张量（例如末端各层）始终保持在 BF16。
4. TransformerEngine 与 FlashInfer 之间逐位一致的量化器契约（bit-exact quantizer contract），使权重更新不会引入本可避免的训练-推理不匹配（train-inference mismatch）。

## 为什么需要 Blackwell 原生配方？

此前的低精度方案并非围绕 MXFP8 或 NVFP4 设计。Miles 现有路径遵循 [DeepSeek-V3](https://arxiv.org/html/2412.19437v2) 风格的分块缩放 FP8 配方：权重使用 128x128 的块缩放，激活使用 1x128 的 tile 缩放，且每个 tile 或块的 scale 都是在线计算的。这是一套很强的 Hopper 世代配方，但在 Blackwell 上，其 FP32 scale 仍是在 Tensor Core 路径外围由软件施加的，而非经由原生微缩放（microscaling）硬件完成。

INT4 QAT 解决的是另一个问题：训练用伪量化让模型适应 INT4 权重，rollout 则使用 W4A16。这种方式虽然节省显存，但计算路径实际上仍是 BF16 激活配合反量化后的 INT4 权重。下表将 NVIDIA [HGX 平台](https://www.nvidia.com/en-us/data-center/hgx/)的稠密 Tensor Core 规格换算为单卡吞吐量：B200 与 B300 取自 8 卡 HGX 系统，Rubin 取自 HGX Rubin NVL8 表格。

| GPU | BF16 稠密 Tensor Core | FP8 稠密 Tensor Core | FP4 稠密 Tensor Core |
| --- | ---: | ---: | ---: |
| B200 | 2.25 PFLOPS | 4.5 PFLOPS | 9 PFLOPS |
| B300 | 2.25 PFLOPS | 4.5 PFLOPS | 13.5 PFLOPS |
| Rubin GPU (NVL8) | 4 PFLOPS | 17.5 PFLOPS | 35 PFLOPS |

对 RL 系统而言，精度契约覆盖：

- SGLang rollout。
- Megatron 与 TransformerEngine 训练。
- Hugging Face 检查点转换。
- Megatron 到 Hugging Face 的实时权重导出。
- 细粒度的高精度例外。

## 格式背景

### MXFP8

MXFP8 是一种微缩放 FP8 格式。TransformerEngine 的 [MXFP8 文档](https://docs.nvidia.com/deeplearning/transformer-engine/user-guide/features/low_precision_training/mxfp8/mxfp8.html)将其描述为 Blackwell 原生的分块缩放配方：每 32 个连续的 E4M3 值共享一个局部 E8M0 scale，且块是一维的。

由于 E8M0 scale 只能表示 2 的幂，解码后的 scale 通常会向上取整，以保证块内的最大值不被截断。

### NVFP4

NVFP4 是 Blackwell 的原生 FP4 格式。如 NVIDIA 的 [NVFP4 介绍](https://developer.nvidia.com/blog/introducing-nvfp4-for-efficient-and-accurate-low-precision-inference/)所述，它存储 FP4 E2M1 值，每 16 个值共享一个 FP8 E4M3 scale。由于 E4M3 的分辨率比 UE8M0 更细，其 scale 通常舍入到最近的可表示值。标准的 NVFP4 配方还会为更大的张量范围额外引入一个 FP32 scale，从而形成两级层级结构：

- 一个粗粒度的 FP32 scale，把张量或 token 映射到 NVFP4 的可表示范围内。
- 一个细粒度的 E4M3 scale，适配每个 1x16 块。

<p align="center">
  <img src="/images/blog/mxfp8-nvfp4-rl/nvfp4-two-level-scaling.png" alt="NVFP4 two-level scaling with FP32 tensor scale and E4M3 block scales" width="70%" style="background:#fff;" />
</p>

FP32 scale 可以选择在不同的张量范围上计算。这一选择属于配方层面的决策，而非格式本身的属性，而它在 RL 中尤为关键。

## 配方 1：端到端 MXFP8 RL

MXFP8 配方是此前端到端 FP8 工作最直接的 Blackwell 原生延伸。rollout、前向传播、权重梯度 GEMM 和数据梯度 GEMM 全部使用 MXFP8，而选定的张量则按照下文的精度控制规则保持 BF16。

### 训练

TransformerEngine 与 Megatron 将 MXFP8 实现为一等公民的、性能优化的 Blackwell 训练路径，包括 [deepseek-v3-gb200-optimization.md](https://github.com/NVIDIA/Megatron-LM/blob/eb0783b6d35607ef1953eaca60b37b886b1a25d0/docs/discussions/deepseek-v3-gb200-optimization/deepseek-v3-gb200-optimization.md) 中描述的 GB200 DeepSeek-V3 优化。在 Miles 集成中，我们把这条路径作为端到端 MXFP8 RL 在训练侧的基础。

与 [DeepSeek-V3 FP8 配方](https://arxiv.org/html/2412.19437v2)的一个差异在于反向激活的表示方式。DeepSeek-V3 把前向激活存储为 1x128 的 FP8 tile，并在反向 GEMM 之前将其转换到反向朝向。这种做法存储的 FP8 数据更少，但会在反向 GEMM 之前引入一次反量化加再量化（requantization）。TransformerEngine 的 MXFP8 文档指出，按行的 1x32 块与按列的 32x1 块在数值上并不相同，必须各自从全精度数据独立量化。因此 TransformerEngine 在量化时会同时物化（materialize）按行与按列两份量化副本。这会占用更多显存，但避免了额外的再量化步骤，也减少了反向路径中的额外量化误差。

这是 RL 中典型的系统层面权衡。我们采用 TransformerEngine 路径，以维持单一的端到端 MXFP8 契约，不引入新的不匹配来源。

### Rollout

在 rollout 侧，SGLang 使用来自 FlashInfer 和 Triton 的 Blackwell MXFP8 kernel。我们实现并将 rollout 路径上游化到了 FlashInfer 与 SGLang（[flashinfer#2581](https://github.com/flashinfer-ai/flashinfer/pull/2581)、[sglang#17449](https://github.com/sgl-project/sglang/pull/17449)、[sglang#19537](https://github.com/sgl-project/sglang/pull/19537)、[sglang#21576](https://github.com/sgl-project/sglang/pull/21576) 与 [sglang#28459](https://github.com/sgl-project/sglang/pull/28459)）。

几乎所有主要 GEMM 都可以量化为 MXFP8，包括注意力投影和 MoE 专家。主要例外是被显式控制的高精度层，例如下文描述的 BF16 MLA 投影。

## 配方 2：每 token NVFP4 RL

NVFP4 比 MXFP8 更激进，因此我们选择性地使用它。我们只量化 MoE 专家，因为它们占据了模型参数量与 rollout 显存流量的大头，模型的其余部分则保持 BF16，除非显式配置为其他精度。

例如，[DeepSeek-V3](https://arxiv.org/html/2412.19437v2) 的总参数量约为 671B，其中 MoE 专家占：

```text
(61 - 3) * (256 + 1) * 3 * 7168 * 2048 / 1e9 = 656.5B parameters
```

约占总量的 97.8%。因此，针对 MoE 专家做量化就能获得大部分显存收益，而不必把每一层都压到最激进的精度格式。

### 为什么不直接使用 NVFP4 预训练配方？

最初的 [NVFP4 预训练配方](https://arxiv.org/html/2509.25149v2)是为大规模预训练设计的：目标是在继续使用 FP4 GEMM 的同时，在大量 token 上保持粗粒度的优化方向。它将 FP4 线性层 GEMM 与若干稳定化手段结合：选定层保持在更高精度，权重缩放在前向与反向之间保持一致，训练路径使用随机舍入（stochastic rounding, SR）与随机 Hadamard 变换（Random Hadamard Transform, RHT）。论文中，SR 作用于梯度，以降低量化偏差、产生无偏的量化梯度；RHT 则用于分散大幅值的块级离群值，这对权重梯度 GEMM 的输入尤为重要。

<p align="center">
  <img src="/images/blog/mxfp8-nvfp4-rl/NVFP4-pretrain.png" alt="Original NVFP4 pretraining recipe" width="85%" style="background:#fff;" />
</p>

这是一个不错的起点，但 RL 的失效模式不同：

| 场景 | 数值特性 | 底线 |
| --- | --- | --- |
| 预训练 | 梯度信号稳定，权重更新幅度可观，模型权重具有自适应性，激活与梯度对精度敏感且动态范围大。 | 保持粗粒度的优化方向与收敛性。 |
| RL | 梯度噪声大，奖励方差高，有用的更新微小而脆弱。 | 把量化噪声压制在真实更新信号之下；否则量化噪声可能覆盖脆弱的能力，导致性能崩溃。 |

NVFP4 RL 配方并没有照搬预训练配方的全部内容。我们聚焦于 MoE 专家权重量化、每 token 激活缩放、一致的精度控制，以及反向操作数可在原始值与反量化值之间选择的 BF16 反向 GEMM。

### 每 token 激活缩放

NVFP4 的两级层级结构很强大，但 FP32 激活 scale 的作用范围必须谨慎选择。正如 [Cursor Composer 2 技术报告](https://arxiv.org/html/2603.24477v2)所讨论的，按张量（per-tensor）的 NVFP4 缩放会让训练结果随 batch 组成而变化，而跨 token 共享 scale 则可能把未来 token 的信息泄露进过去 token 的表示中。如果某个 token 与其他 token 共享 scale，它的量化表示就取决于 batch 的构成。这对 RL 尤其成问题，因为 rollout 调度和序列长度都是变化的。

因此，我们的配方在线地为每个 token 计算一个 FP32 激活 scale。这把激活离群值局部化到单个 token，消除了静态激活校准带来的伪影，并让 SGLang rollout 与 Megatron 训练使用相同的激活 scale 作用范围。

在 rollout 侧，每 token FP32 scale 的计算被融合进 FlashInfer 的激活量化 kernel 路径：同一个调用在输出打包 FP4 激活与 E4M3 块 scale 的同时，也返回每 token 的 FP32 scale。因此，每 token 激活缩放不需要单独的校准 scale 计算步骤。

训练与推理的一致性还要求并行方式相匹配。如果 FP32 scale 是在专家张量并行（ETP）分区内部按 token 计算的，那么 SGLang 与 Megatron 应使用相同的 ETP 大小；否则两侧看到的张量分区不同，算出的 scale 也会不同。

SwiGLU MoE 层还带来另一个关键契约。SGLang 与 Megatron 通常把 gate 与 up 投影融合成一个 GEMM，因此即使 Hugging Face 检查点分开存储这两个张量，在转换与实时权重更新时它们也必须共享同一个 FP32 scale。Miles 在 NVFP4 导出路径中把 gate/up 对一起量化，从而强制满足这一约束。

我们在整个技术栈中实现并上游提交了每 token NVFP4 配方：

- TransformerEngine 训练配方：[TransformerEngine#2931](https://github.com/NVIDIA/TransformerEngine/pull/2931)
- cuDNN frontend 训练 kernel：[cudnn-frontend#251](https://github.com/NVIDIA/cudnn-frontend/pull/251)
- FlashInfer rollout kernel：[flashinfer#3027](https://github.com/flashinfer-ai/flashinfer/pull/3027)
- SGLang 集成与权重更新修复：[sglang#22918](https://github.com/sgl-project/sglang/pull/22918)、[sglang#22204](https://github.com/sgl-project/sglang/pull/22204)

### 高精度反向与反量化反向

在高精度反向（high-precision backward）的 NVFP4 变体中，前向传播与 rollout 对 MoE 专家使用 NVFP4，而反向 GEMM 使用原始的 BF16 操作数。

  <img src="/images/blog/mxfp8-nvfp4-rl/NVFP4-hp.drawio.png" alt="NVFP4 with high-precision backward" width="85%" style="background:#fff;" />
</p>

反量化反向（dequantized backward）是第二种可选模式。反向 GEMM 仍以 BF16 运行，但其输入是前向产生的那些低精度操作数反量化回 BF16 的结果，而非原始 BF16 值。

<p align="center">
  <img src="/images/blog/mxfp8-nvfp4-rl/NVFP4-dq.drawio.png" alt="NVFP4 with dequantized backward" width="85%" style="background:#fff;" />
</p>

这两种模式都避免了低精度反向 GEMM，因此这些配置不使用原 NVFP4 预训练配方中的 RHT 或随机舍入。它们以反向吞吐量换取更高精度的计算，但 RL 通常瓶颈在 rollout，长上下文的注意力与通信开销会进一步稀释其对端到端的影响。

## 逐位一致的量化器契约

在 RL 中，量化不匹配会随权重更新不断累积。如果训练侧与 rollout 侧对同一个张量的量化方式不同，用于采样和学习的策略就不再是同一个低精度模型。因此，我们需要在 RL 技术栈两侧之间建立一份显式契约。

我们将 FlashInfer 与 TransformerEngine 的量化器对齐到同一份 MXFP8 与 NVFP4 位级契约。我们的 FlashInfer 单元测试以 TransformerEngine 风格的参考实现为基准，在随机数据、量化边界数据、全零张量与最大值张量（对应 `init_data = ["random", "boundary", "zeros", "maxes"]`）上检查字节级完全一致。我们在 [flashinfer#3387](https://github.com/flashinfer-ai/flashinfer/pull/3387) 中实现并上游提交了这一量化器对齐。

服务与 RL 之间有一个实际差异：对于纯服务负载，FlashInfer 出于性能考虑，可能在 FP4 量化路径的部分环节使用快速数学（fast math）。作为服务默认值这是合理的，但 RL 权重更新受益于与训练侧量化器的完全一致。本配方中我们设置：

```bash
FLASHINFER_DISABLE_FP4_QUANT_FAST_MATH=1
```

任何接触 rollout 权重的后端，都应当要么精确实现这份量化契约，要么把近似行为改为显式选择开启（opt-in）。

## 细粒度精度控制

在实践中，单一的全局精度开关不足以支撑低精度 RL。有些张量应当保持 BF16，但选出它们只是问题的一部分：同样的决策还必须在 Hugging Face 检查点转换、Megatron 训练、SGLang rollout 与实时权重导出中一致地强制执行。

我们在 Miles 中通过基于数量与基于名称的 BF16 例外，在检查点转换、训练、rollout 与实时导出中实现了这种张量级精度控制（[miles#614](https://github.com/radixark/miles/pull/614)、[miles#1054](https://github.com/radixark/miles/pull/1054) 与 [miles#1261](https://github.com/radixark/miles/pull/1261)）。我们还在 SGLang 中实现了对所得混合精度检查点的支持（[sglang#18742](https://github.com/sgl-project/sglang/pull/18742) 与 [sglang#20214](https://github.com/sgl-project/sglang/pull/20214)）。具体而言，转换使用 `--num-layers-at-start-in-bf16` 与 `--num-layers-at-end-in-bf16`；Megatron 训练将这些数量与 `--first-last-layers-bf16` 结合使用；SGLang 则直接服务所得的混合精度检查点。

### 层精度选择

正如 [NVIDIA NVFP4 预训练论文](https://arxiv.org/html/2509.25149v2)所建议的，我们让一小部分末尾层保持在更高精度。在我们的实验中，把最后 15% 的层保留为 BF16，能切实降低训练-推理不匹配并稳定梯度。

<p align="center">
  <img src="/images/blog/mxfp8-nvfp4-rl/mxfp8-last-2-4-8.png" alt="Effect of keeping final layers in BF16" width="70%" style="background:#fff;" />
</p>

在我们的实验中，对开头的层开启 BF16 并不会带来有意义的训练-推理不匹配下降：

<p align="center">
  <img src="/images/blog/mxfp8-nvfp4-rl/mxfp8-f1l6-vs-l6.png" alt="First-layer BF16 versus last-layer BF16" width="70%" style="background:#fff;" />
</p>

让共享专家（shared expert）保持高精度同样能降低训练-推理不匹配，且几乎不带来性能或显存开销。路由专家（routed expert）是被稀疏选中的，其输出会经过高精度的加权归约；共享专家则始终处于激活状态，其精度误差会影响经过该模块的每一个 token。

<p align="center">

</p>

#### 案例分析：MXFP8 MLA

对 MLA 模型而言，`kv_b_proj` 是 MXFP8 的一个重要案例。吸收（absorbed）与非吸收（non-absorbed）MLA 模式可能使用不同的缩并轴（contraction axis），而 MXFP8 使用一维微缩放块，因此改变缩并轴就会改变哪些元素共享同一个 scale。同样的顾虑也适用于包括 NVFP4 在内的其他一维格式。最初的 [DeepSeek-V3](https://arxiv.org/html/2412.19437v2) FP8 配方没有这个确切的权重侧问题，因为它使用 128x128 的权重 scale 块而非一维块。我们让这些投影张量保持 BF16，以避免隐藏的再量化并保持训练-推理一致性。

```yaml
configs:
  bf16:
    transformer_engine_config_type: "TEQuantizationParams"
    training_recipe: {}
matchers:
  mla_kv_up_proj_bf16:
    type: "glob"
    enabled: true
    pattern: "*.self_attention.linear_kv_up_proj"
    config: "bf16"
  absorbed_k_up_proj_bf16:
    type: "glob"
    enabled: true
    pattern: "*.self_attention.linear_k_up_proj"
    config: "bf16"
  absorbed_v_up_proj_bf16:
    type: "glob"
    enabled: true
    pattern: "*.self_attention.linear_v_up_proj"
    config: "bf16"
```

与之对应的基于名称的转换期与 rollout 期参数为：

```bash
--extra-high-precision-layers-hf .kv_b_proj.
--extra-high-precision-layers-megatron .linear_kv_up_proj .linear_k_up_proj .linear_v_up_proj
```

对 [DeepSeek-V3](https://arxiv.org/html/2412.19437v2) 风格的 MLA 来说，这一 BF16 例外的开销很小：形状为 `32768 x 512` 的 `kv_b_proj` 张量，61 层均以 BF16 存储时约占 1.90625 GB。

## 结果：8x B200 上的 Qwen3-30B-A3B 配方消融

为保证对比的一致性，所有实验都在 8x B200 上使用默认 Miles 设置运行同步的 Qwen3-30B-A3B RL。固定负载为在 `dapo-math-17k` 上进行 GRPO 风格训练，每个 prompt 生成 8 个 rollout 样本，最大响应长度为 8192 token。这只是一个配方消融设置，并非经过完整调优的训练或服务基准测试。KL 路径仅为诊断目的开启，其系数为 0.0，因此在该消融中 KL 并不作为优化惩罚项。

硬件划分为：4 张 GPU 负责 rollout，4 张 GPU 负责训练。

所有低精度配方均满足：

- 启用 MoE rollout 路由重放（rollout-routing replay）。
- 最后 15% 的层保持 BF16。
- 低精度权重使用 0 权重衰减以保证稳定性。
- SGLang rollout 使用 BF16 KV 缓存，并在低精度 MoE 路径上使用 FlashInfer 的 TRTLLM routed MoE 后端。

我们比较六种配置：

1. BF16 训练 + BF16 rollout。
2. 端到端 MXFP8 训练 + MXFP8 rollout。
3. MXFP8 rollout 与前向传播，高精度反向。
4. MXFP8 rollout 与前向传播，反量化反向。
5. 每 token NVFP4 MoE rollout 与前向传播，高精度反向。
6. 每 token NVFP4 MoE rollout 与前向传播，反量化反向。

### 训练-推理不匹配

与预期一致，两种低精度格式的训练-推理不匹配都高于 BF16，而在同一种格式内部，两种反向选择的表现相近。在该消融中，这些数值都处于合理范围内。

<p align="center">
  <img src="/images/blog/mxfp8-nvfp4-rl/hp-logprob.png" alt="Train-rollout logprob difference across backward modes" width="48%" style="background:#fff;" />
  <img src="/images/blog/mxfp8-nvfp4-rl/hp-kl.png" alt="KL loss comparison across backward modes" width="48%" style="background:#fff;" />
</p>

NVFP4 的参考 KL 起点高于 BF16 或 MXFP8。Miles 是相对一个 Megatron BF16 参考模型计算这一诊断指标的，因此该指标除了 RL 过程中的策略演化之外，还包含每种低精度策略与 BF16 参考之间的差异。不应把它单独解读为优化惩罚项。

### 奖励

尽管诊断层面的不匹配更高，全部五条低精度奖励曲线都与 BF16 奖励曲线高度贴合。

<p align="center">
  <img src="/images/blog/mxfp8-nvfp4-rl/hp-raw-reward.png" alt="Raw reward comparison across backward modes" width="70%" style="background:#fff;" />
</p>

这就是本次配方消融的关键结论：在这一 Qwen3-30B-A3B B200 设置中，Blackwell 原生低精度在提升 rollout 效率的同时，保住了所观测到的学习曲线。

### 性能

与 BF16 相比，MXFP8 与 NVFP4 都缩短了 rollout 时间：

<p align="center">
  <img src="/images/blog/mxfp8-nvfp4-rl/hp-rollout-time.png" alt="Rollout time comparison across backward modes" width="70%" style="background:#fff;" />
</p>

在 NVFP4 rollout 中，FlashInfer 直接在激活量化 kernel 路径内部计算每 token 的在线 FP32 scale，而不是作为单独的预处理步骤。因此，所报告的 rollout 性能已包含在线 scale 计算的开销。

在训练侧，MXFP8 变体比 BF16 更快，而 NVFP4 的 backward-override 变体在本文所测的实现中则更慢：

<p align="center">
  <img src="/images/blog/mxfp8-nvfp4-rl/hp-train-time.png" alt="Training time comparison across backward modes" width="70%" style="background:#fff;" />
</p>

训练侧的差距来自本消融所用的实现方式，而非 FP4 Tensor Core 的固有限制。我们的 TransformerEngine 路径把每 token FP32 缩放作为单独的 PyTorch 操作执行（[TransformerEngine#2931](https://github.com/NVIDIA/TransformerEngine/pull/2931)），而不是使用把缩放融合进 kernel epilogue 的原生每 token NVFP4 GEMM 路径。融合版 cuDNN frontend kernel 我们已实现并上游提交（[cudnn-frontend#251](https://github.com/NVIDIA/cudnn-frontend/pull/251)）；TransformerEngine 侧的集成仍在进行中。反量化反向还会增加前述的反量化步骤。由于该 RL 负载以 rollout 为主，即便训练路径尚未完全加速，rollout 的提速仍然很有意义。

在该消融之外，[humans&](https://humansand.ai/) 已在生产环境中将同一配方家族与组件用于大规模、长上下文、多智能体的异步强化学习研究。

## 在线 NVFP4 模型服务

同样的每 token NVFP4 配方可以通过在线后训练量化（PTQ）来服务 FP8/BF16 模型检查点，在没有校准伪影的情况下获得良好的模型质量，同时计算性能与传统 NVFP4 服务相当。

在线每 token 激活缩放把激活离群值局部化到每个 token，并免除了在校准阶段携带静态激活 FP32 scale 的需要。在 FlashInfer 中，该 FP32 scale 的计算被融合进激活量化 kernel 路径，因此在线缩放不需要单独的预处理 kernel。

结合 4/6（four-over-six）与零暴露解码延迟（zero exposed decode latency），后训练量化（PTQ）的模型质量还可以进一步提升，详见配套的 [humans&](https://humansand.ai/blog/nvfp4-rl) 博文。

我们在 [sglang#26083](https://github.com/sgl-project/sglang/pull/26083) 中实现并开源了这条 SGLang 在线 NVFP4 服务路径。在 SGLang 中使用该功能非常简单：只需在现有的 BF16/FP8 MoE 模型服务命令中加上 `--quantization nvfp4_online` 即可。

## 后续工作

### 去掉额外的 BF16 权重副本

尽管 rollout 与训练执行的是同一套低精度配方，Megatron 仍会额外保存一份 BF16 权重副本。这增加了显存消耗，也限制了低精度路径在显存上的实际收益。

Megatron 已有 `--fp8-param-gather` 与 `--fp4-param-gather`，但 Blackwell 原生路径仍在成熟过程中。Megatron-Bridge 的跟踪 issue [Megatron-Bridge#3801](https://github.com/NVIDIA-NeMo/Megatron-Bridge/issues/3801) 记录了实现稳健低精度参数 gather 所需的后续工作。NVFP4 的 `--fp4-param-gather` 尚不支持本配方所用的 1D 1x16 权重布局。

### 偶发的梯度尖峰

高精度反向的 NVFP4 变体仍可能出现偶发的梯度尖峰：

<p align="center">
  <img src="/images/blog/mxfp8-nvfp4-rl/nvfp4-hp-spike.png" alt="Occasional NVFP4 gradient spike" width="70%" style="background:#fff;" />
</p>

在本消融中，反量化反向能减小最大的尖峰，但无法将其完全消除。包括 4/6 与链式法则一致的反向选择在内的更高级技术，在配套的 [humans&](https://humansand.ai/blog/nvfp4-rl) 博文中有详细讨论。

### 重构权重更新接口

低延迟的 FlashInfer 后端通常要求填充（padding）、swizzle 重排（swizzling）、洗牌（shuffling）等后端特定的权重布局。这些变换对推理服务来说再自然不过，但它们让 RL 的实时权重更新与 RDMA 变得复杂，因为训练侧通常持有另一种规范化的张量布局。

Miles 与 SGLang 中的相关工作，目标是保留高性能的服务布局，同时让每一次权重变换都显式、可验证，并减少对后端私有细节的依赖。

## 在 Miles 中试用 NVFP4 配方

以下环境变量设置可复现每 token NVFP4 高精度反向的配置：

```bash
NVTE_NVFP4_ROW_SCALED_ACTIVATION=1
NVTE_BACKWARD_OVERRIDE=high_precision
NVTE_NVFP4_DISABLE_2D_QUANTIZATION=1
NVTE_NVFP4_DISABLE_RHT=1
NVTE_NVFP4_DISABLE_STOCHASTIC_ROUNDING=1
TRTLLM_DISABLE_FP4_QUANT_FAST_MATH=1
FLASHINFER_DISABLE_FP4_QUANT_FAST_MATH=1
SGLANG_FLASHINFER_NVFP4_PER_TOKEN_ACTIVATION=1
```

把 `NVTE_BACKWARD_OVERRIDE` 设为 `dequantized`，即可在不改变配方其余部分的情况下选择反量化反向变体。

在 Miles 启动脚本中，该配方将这些环境变量与 `--fp4-format e2m1`、`--fp4-recipe nvfp4`、检查点转换时使用的同一套 BF16 首/末层控制，以及以下 TransformerEngine 精度配置组合使用：

```yaml
configs:
    nvfp4:
        transformer_engine_config_type: "TEQuantizationParams"
        training_recipe:
            fp4_quantization_recipe: "nvfp4"
    bf16:
        transformer_engine_config_type: "TEQuantizationParams"
        training_recipe: {}
matchers:
    routed_experts_fc1_nvfp4:
        type: "glob"
        enabled: true
        pattern: "*.mlp.experts.linear_fc1"
        config: "nvfp4"
    routed_experts_fc2_nvfp4:
        type: "glob"
        enabled: true
        pattern: "*.mlp.experts.linear_fc2"
        config: "nvfp4"
    default_bf16:
        type: "glob"
        enabled: true
        pattern: "*"
        config: "bf16"
```
