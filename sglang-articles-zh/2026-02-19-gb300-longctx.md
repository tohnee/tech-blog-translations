# 在 GB300 NVL72 上部署 DeepSeek：长上下文推理的重大收益

> 原文：[Deploying DeepSeek on GB300 NVL72: Big Wins in Long-Context Inference](https://lmsys.org/blog/2026-02-19-gb300-longctx/) · LMSYS Blog · Nvidia & SGLang Team

## **TL;DR**

作为 Blackwell 家族的最新成员，**GB300 NVL72** 是目前长上下文 LLM 推理最强大的平台。在这篇博客中，我们分享了针对 128K/8K ISL/OSL（输入/输出序列长度，Input/Output Sequence Length）长上下文服务优化 DeepSeek R1-NVFP4 的最新进展，采用的技术包括：预填充-解码分离部署（PD 分离）、面向 prefill 的分块流水线并行（PP）、面向 decode 的大规模专家并行（Wide-EP）、多 token 预测（MTP）、重叠调度，以及由注意力 softmax 关键指令的 SFU（Special Function Unit，特殊功能单元）吞吐量翻倍所驱动的更快注意力算子。

在长上下文负载下，SGLang 在 GB300 NVL72 上达到最高 **226 TPS/GPU**（较 GB200 提升 **1.53×**）；在 GPU 吞吐量几乎相同的情况下，MTP 还能将单用户吞吐量（TPS/User）进一步提升 **1.87×**。

此外，在相同延迟条件下与配置对齐的 GB200 NVL72 相比，GB300 在各代表性场景下始终提供 **1.4×–1.6×** 的 TPS/GPU。

复现步骤见 [issue:18703](https://github.com/sgl-project/sglang/issues/18703)。


**亮点**

* 长上下文（128K/8K）峰值吞吐量：SGLang 在 GB300 NVL72 上达到 226.2 TPS/GPU，较 GB200 有 1.53× 的优势。在相同吞吐量下，MTP 可将 TPS/User 提升 1.87×。
* 对齐延迟条件下的 GB300 对 GB200：在对齐的工作负载下，GB300 相对 GB200 提供 1.38×–1.58× 的 TPS/GPU。
* EP decode 扩展：GB300 的 HBM 容量大 1.5×（288 GB 对 192 GB），使有效 decode batch size 提高 1.6×（40 对 24 请求/GPU），在 DEP8 下可扩展到 288 个并发请求且撤回极少。
* PP prefill 与优化的注意力算子：借助动态分块，128K prefill 的 TTFT 为 8.6 秒（比 GB200 低 1.07×–1.23×），其背后的 FMHA 算子快 1.35×，得益于注意力 softmax 关键指令的 2× SFU 吞吐量提升。

## **方法**

本节介绍使 GB300 获得长上下文收益的主要技术。

### **1. 部署与 NVIDIA Dynamo 集成**
本文中，DeepSeek-R1 在 GB300 NVL72 上的部署由 [**NVIDIA Dynamo**](https://github.com/ai-dynamo/dynamo) 编排，它是面向集群级预填充-解码（PD）分离推理的高性能控制平面。Dynamo 负责处理协调异构 prefill 与 decode worker 池的种种复杂性，提供 KV 缓存感知路由、worker 协调、生命周期管理，以及经过优化的前/后处理栈，从而在规模化场景下维持超高吞吐量。

* **低开销编排**：Dynamo 的主要性能优势在于其轻量的 KV 缓存感知请求调度与高效的元数据管理。在 PD 协调频繁的长上下文场景中，Dynamo 保证调度层引入近乎为零的延迟，让 SGLang 优化过的算子能够打满 GB300 的 HBM3e 带宽，而不受编排逻辑的瓶颈制约。
* **生产级扩展**：Dynamo 为多节点 PD 部署提供健壮的协调能力，包括动态 worker 发现、健康跟踪，以及跨异构 prefill 与 decode 池的生命周期管理，使部署在实例扩容、滚动或重启时保持稳定。


<img src="/images/blog/gb300_longctx/dynamo.png"
     style="display: block; margin: 20px auto 0; width: 75%; max-width: 100%; height: auto;">

对于想要在生产环境中部署这套方案的用户，Dynamo Kubernetes 栈提供对 GB200/GB300 的支持，具备推理感知的自动扩缩容，以及面向分离式部署的集群拓扑感知调度。

### **2. Prefill 路径：PP 预填充、长上下文 TTFT 与更快的算子**

对于长上下文推理（例如 128K token），TTFT（首 token 延迟）是首要约束，尤其是在前缀匹配很少或没有匹配的情况下，改善 TTFT 至关重要。我们通过面向 prefill 路径的分块流水线并行（PP）结合[动态分块（Dynamic Chunking）](https://lmsys.org/blog/2026-01-15-chunked-pipeline/)来解决这一问题，后者将 prompt 计算分布到各流水线阶段，并改善阶段之间的重叠。

<img src="/images/blog/gb300_longctx/chunked_pp.png"
     style="display: block; margin: 20px auto 0; width: 75%; max-width: 100%; height: auto;">

在 [GB200 系列](https://lmsys.org/blog/2025-09-25-gb200-part-2/)优化的基础上，我们全面启用了 FP8 注意力，并为 prefill 和 decode 引入了原生 FP8 KV 缓存支持。主要优势：
* 降低内存流量：相比 BF16 最大限度减少内存带宽瓶颈，提升吞吐量与稳定性。
* KV 容量翻倍：在固定内存占用下将 KV 缓存容量翻倍，从而支持更大的 batch size 或更长的序列。

我们还在注意力算子中利用了 GB300 特有的硬件加速 Softmax。Blackwell Ultra GPU 配备了升级版的特殊功能单元（SFU），对关键 softmax 操作提供 2× 的吞吐加速，这对注意力层可能至关重要。对于长上下文 prefill 这类注意力密集型负载，这直接缓解了计算瓶颈。

我们的基准测试表明，相比 GB200，这一升级为 FMHA 算子带来 1.35× 的加速，降低了整体 TTFT。

### **3. Decode 路径：长上下文推理中的内存瓶颈**
长上下文 decode 很快就会变成 KV 主导、访存受限的过程：每个新 token 都要反复读取完整的 KV 历史，因此 KV 容量（能同时驻留多少序列）和 HBM 带宽成为主要瓶颈。

SGLang 采用了一套专门的运行时栈与架构策略：
* **Wide-EP 扩展**：专家并行（EP）配合 DP 注意力，将 MoE 权重与 KV 缓存分布到更多 GPU 上（本工作中最多 32 卡），降低单卡内存压力，使 decode batch size 可以更大而不触发"撤回"（retraction，即重算）。
* **CuTe DSL nvfp4 算子**：专为 decode 阶段的高性能 nvfp4 MoE 运算定制。
* **DeepEP**：一套经过优化的 dispatch 与 combine 算子集合，用于高效 all-to-all 通信。

GB300（Blackwell Ultra）单卡配备 288 GB HBM3e——是 GB200 192 GB 的 1.5×。为了量化 GB300 的 288 GB HBM3e 能转化为多少有效 KV 容量，我们以 DEP16 为例评估最大 decode 并发。为了公平对比，两个平台均固定 mem_fraction_static = 0.75，尽管 GB300 更大的绝对内存在实践中允许设置更高的值。我们根据每 token 的 KV 占用（每 token 35,136 字节）和 128K+8K 负载（每请求约 136K 个缓存 token）计算最大 decode batch size。

<small>在 SGLang 中，`mem_fraction_static` 定义分配给模型权重与 KV 缓存的 GPU 内存比例，其余部分预留给激活值和运行时缓冲区。
KV 占用的计算方式：(kv_lora_rank + qk_rope_head_dim) × num_layers × num_kv_head * fp8_size = (512 + 64) × 61 × 1 × 1 = 每 token 35,136 字节</small>

| 项目 | 假设 / 指标 | GB300（@ mfs=0.75） | GB200（@ mfs=0.75） |
| :--- | :--- | :--- | :--- |
| **单卡 HBM** | HBM3e 总容量 | 288 GB | 192 GB |
| **静态预算** | HBM × mem_fraction_static | ≈ 216 GB | ≈ 144 GB |
| **单卡模型权重** | FP4 量化的 DeepSeek-R1，EP16/TP16 | ≈ 40 GB | ≈ 40 GB |
| **KV 池预算** | 静态预算 – 模型权重 | ≈ 176 GB | ≈ 104 GB |
| **工作负载** | 每请求缓存 token 数 | 136K (128K+8K) | 136K (128K+8K) |
| **KV 占用** | cell_size_per_token | 35,136 B | 35,136 B |
| **单卡每请求 KV** | 136K × cell_size | ≈ 4.45 GiB | ≈ 4.45 GiB |
| **理论上限** | KV 池 / 每请求 KV | ≈ 40 请求/GPU | ≈ 24 请求/GPU |
| **实际目标** | 上限的约 85%，以减少撤回 | ≈ 36 请求/GPU | ≈ 20 请求/GPU |
| **EP16 映射** | 请求/GPU × 16 GPU | ≈ 576 并发请求 | ≈ 320 并发请求 |

如表所示，GB300 更大的 HBM 几乎直接转化为更高的 decode 并发——理论上限分别为 40 与 24 请求/GPU。实践中，我们运行在上限的约 85%，以避免请求占满 KV 缓存而触发请求撤回，即在 GB300 上最多 36 请求/GPU，GB200 上为 20（即 DEP16 下 576 对 320 个并发请求）。


### **4. 由重叠调度器驱动的 MTP**
自 [v0.4](https://lmsys.org/blog/2024-12-04-sglang-v0-4/) 起，重叠调度器一直是 SGLang 默认的批调度策略，它通过让 CPU 调度与 GPU 计算重叠，实现零 CPU 开销。另一方面，多 token 预测（MTP）是最流行的投机解码方法之一，被包括 DeepSeek R1 在内的主流模型广泛采用。SGLang 中 MTP 实现的更多细节见[这篇博客](https://lmsys.org/blog/2025-07-17-mtp/)。

<img src="/images/blog/gb300_longctx/spec-1.png"
     style="display: block; margin: 20px auto 0; width: 75%; max-width: 100%; height: auto;">

<img src="/images/blog/gb300_longctx/spec-2.png"
     style="display: block; margin: 20px auto 0; width: 75%; max-width: 100%; height: auto;">

为了将 MTP 与重叠调度器无缝结合，SGLang 提出了 Spec-V2，通过精心设计的消息传递与重叠策略来缓解 MTP 批次之间的同步问题。

具体而言，Spec-V2 采用双流设计：一条 forward 流负责所有 GPU 计算，一条 schedule 流（这里用"流"一词是为了强调异步性）负责 CPU 侧操作，包括结果处理、内存释放、为下一批做准备等。

为避免元数据张量从设备传输到主机造成的同步屏障，Spec-V2 创建了一个 future 张量映射（future tensor map）：schedule 流先创建元数据张量的引用，直到最后一批将其具体化（materialize）后才真正读取。这样，CPU 操作就能与最后一批 MTP 的目标验证（target verify）或 draft extend 过程重叠进行。

此外，我们还从以下几个方面增强了重叠调度器对 MTP 的支持：
* 兼容 PD 分离与 WideEP，解锁更高并发下的性能。
* 为 MTP 前向过程的所有阶段（draft decode、target verify、draft extend）捕获 CUDA 图，进一步降低 CPU 开销。
* 对 MTP 层中的 MoE 权重做 FP8 量化，使其与 DeepGemm 和 DeepEP 的配合更加顺畅。



## **实验**
### **1. 最大吞吐量分析**
为了刻画 DeepSeek-R1 的最大吞吐量，我们在长上下文负载（ISL = 128K，OSL = 8K）下测量可达到的最大 TPS。

<img src="/images/blog/gb300_longctx/exp-1.png"
     style="display: block; margin: 20px auto 0; width: 75%; max-width: 100%; height: auto;">

不开启 MTP 时，GB300 达到 226.2 TPS/GPU——为 GB200（147.9 TPS/GPU）的 1.53×。在长上下文下，峰值吞吐量主要受 decode 侧 KV 缓存容量与内存带宽的制约，而非计算能力；GB300 更大的 HBM 容量支持更高的 decode batch size，让更多请求保持活跃而不触发撤回。

开启 MTP 后，GB300 保持 224.2 TPS/GPU，GB200 为 169.1（1.33×）。值得注意的是，MTP 的主要收益体现在单用户吞吐量上：GB300 的 TPS/User 从 23 几乎翻倍到 43（+87%），同时 TPS/GPU 保持在峰值水平，这意味着每个用户都能获得明显更快的响应，而不牺牲系统整体吞吐量。


### **2. 峰值容量与延迟约束**

<img src="/images/blog/gb300_longctx/exp-2.png"
     style="display: block; margin: 20px auto 0; width: 75%; max-width: 100%; height: auto;">

为了在贴近真实推理使用的条件下对比 GB300 与 GB200，我们在两个代表性场景下评估性能：
* 高吞吐导向场景（非 MTP 时 TPS/User = 30–40，MTP 时 40–50）：系统调优以最大化聚合吞吐量，延迟约束较为宽松。
* 延迟-吞吐均衡场景（非 MTP 时 TPS/User = 50–60，MTP 时 60–70）：反映更高的单用户吞吐量和更严格的响应性要求。

在高吞吐场景下，不开启 MTP 时 GB300 达到 204.7 TPS/GPU，GB200 为 147.9（+38.4%）。开启 MTP 后加速比更高，为 224.2 对 169.1 TPS/GPU（+44.9%）。

在延迟-吞吐均衡场景下，不开启 MTP 时 GB300 保持 1.58× 优势（167.9 对 106.5 TPS/GPU），开启 MTP 时为 1.40×（196.4 对 140.0 TPS/GPU）。

总体而言，GB300 持续领先 GB200 1.4×–1.5×，其中相对收益最大的是延迟敏感条件——在更高的单用户吞吐量下，GB300 对吞吐量退化表现出更强的韧性。

### **3. Prefill 延迟：分块策略与 TTFT 优化**
为评估分块策略与硬件对 prefill 延迟的影响，我们在长上下文负载（ISL = 128K，OSL = 8K）下、使用 8 GPU 的 1P/1D 分离部署测试平均 TTFT。我们对比三种分块方式：不分块（并发 = 1）、静态分块与动态分块，初始块大小分别为 16K、32K 和 64K。

<img src="/images/blog/gb300_longctx/exp-3.png"
     style="display: block; margin: 20px auto 0; width: 75%; max-width: 100%; height: auto;">

GB300 在 prefill TTFT 上始终优于 GB200。在所有分块配置下，相同设置的 GB300 的 TTFT 比 GB200 低 1.07×–1.23×。差距最大的是不分块基线（15.2 秒 对 18.6 秒），主要由 GB300 优化过的注意力算子驱动（见 4.4 节）。开启分块后，GB300 保持稳定优势，在 32K 动态分块下 128K prefill 的最优 TTFT 达到 8.6 秒。

分块与动态分块都有助于改善长上下文 TTFT。不分块时，两个平台的 TTFT 都超过 15 秒。启用带 PP 重叠的分块 prefill 可将 TTFT 降低 30–45%，其中较小的块大小（16K、32K）凭借更好的流水线利用率始终优于 64K。在所有测试过的块大小下，动态分块在静态分块基础上还能再降低 8–17%，因为它消除了固定调度导致的流水线气泡——这一效应在较大块大小时尤为明显，因为静态分块会留下大量空闲时间。采用 32K 初始块大小配合动态分块，我们在 GB300 上实现了 8.6 秒的 TTFT。对 [smooth factor](https://lmsys.org/blog/2026-01-15-chunked-pipeline/) 做更细粒度的调优可能进一步降低 TTFT。

### **5. 精度**
我们在 LongBench-v2 上评估了系统，以确保模型的完整性。非 MTP 配置取得了 57.2% 的分数。开启 MTP 后，在接受长度 accept length=2.37@MTP3 下取得 56.9%，与 DeepSeek-R1-0528 官方基准报告的 56.7% 完全一致。


## **未来工作**
尽管上述所有技术都已展示了 GB300 的优越性，我们仍有以下优化方向可以带来更好的性能：
* **上下文并行（Context Parallelism）**：与分块流水线并行相比，上下文并行也是降低 TTFT 的一个有前景且无气泡的选项。
* **算子优化**：可以启用对称内存（symmetric memory）来优化通信算子。MTP 的小型元数据准备算子也可以融合，以降低 CPU 开销。
* **DP 负载均衡器**：通过更好的 DP 负载均衡器，可以减少不同 DP rank 之间的等待时间。
* **Wide-EP 中更深的重叠**：可以以更精细的方式调度和组织 MoE 计算与 DeepEP 通信，实现更深的重叠和更高的加速。
* **面向长上下文与负载的投机感知调度**：draft token 的数量可以根据当前负载动态决定。
