# EPD 分离：SGLang 中为视觉语言模型实现编码器弹性伸缩

> 原文：[EPD Disaggregation: Elastic Encoder Scaling for Vision-Language Models in SGLang](https://lmsys.org/blog/2026-01-12-epd/) · LMSYS Blog · rednote hilab, Alibaba Cloud Computing, AntGroup SCT

## TL;DR

> 我们在 SGLang 中引入了编码器-预填充-解码分离（Encoder-Prefill-Decode，EPD）架构，将视觉语言模型（VLM）中的视觉编码与语言处理分离开来。它可以实现：

- **视觉编码容量独立伸缩**：编码器服务器可以独立水平扩展，而不影响语言模型的部署，使视觉密集型负载获得更好的资源利用率。
- **与现有 PD 分离兼容**：EPD 可与预填充-解码分离（PD 分离）组合，构成完整的三级架构。
- **灵活的传输后端**：支持多种传输机制（ZMQ、经由 Mooncake 的 GPU 直传），可针对不同部署场景进行优化。
- **视觉嵌入缓存**：高频使用的图像可在编码器服务器上缓存，避免冗余的 ViT 计算，并降低网络传输开销。

EPD 在**图像密集型场景**（如多图输入）中非常有效——此时视觉编码过程是主要计算瓶颈。例如，在这些场景下，我们利用 EPD 显著降低了负载下的请求 TTFT——在 1 QPS 时，延迟约为共置（colocation）方案的 1/6 到 1/8。反过来，在只有少量图像的**图像轻量场景**中，EPD 可能效率不高，甚至适得其反。这是因为跨节点传输嵌入（embedding）带来的额外网络延迟，可能超过卸载编码任务所节省的时间，导致 TTFT 反而高于共置方案。

## 引言
Qwen2.5-VL、Llama-Vision 等视觉语言模型（VLM）将视觉理解与语言生成结合在一起。然而，这类模型面临一些独特的扩展性挑战：

- 计算需求异构：视觉编码（CNN/ViT）所需的计算模式与语言解码（Transformer）不同
- 资源使用不均衡：视觉处理是计算密集型的，但只在预填充阶段需要
- 灵活性受限：传统的单体部署无法独立扩展视觉与语言组件
- 请求内并行：同一请求中的不同图像可以独立编码。
- 张量并行下扩展性差：视觉编码器的参数量远小于语言组件，对其应用张量并行效率低下，通常也没有必要。

SGLang 现有的预填充-解码（PD）分离已经把预填充与解码两个阶段分开。EPD 在此基础上进一步把视觉编码从语言预填充中分离出来，形成三级架构。

## ViT 扩展性问题：为什么张量并行并非总是有效

### 反直觉的发现

EPD 分离带来的关键洞见之一是：视觉 Transformer（ViT）**并不会**从提高张量并行度中获益，TP 越高反而可能越慢：

在 H20 上使用 Qwen2.5-VL-72B 的基准测试（每个请求 4 张图像）：

| tp  | ViT 平均耗时 |
|-----|---------------|
| 2   | 492.13ms      |
| 4   | 465.80ms      |
| 8   | 523.80ms      |

为什么会这样？

1. 通信开销主导了执行时间。
2. 视觉模型的权重参数通常很小。

EPD 通过水平扩展编码器数量而非提高 TP，绕开了这一问题。

### 架构总览
EPD 架构的请求流程如下：

1. **客户端请求**：多模态请求到达预填充服务器（经负载均衡器或直连）。
2. **图像分发**：预填充服务器识别出图像输入，并将其分发给一台或多台编码器服务器。图像可拆分到多个编码器上以实现负载均衡。
3. **视觉编码**：编码器服务器通过 ViT 处理图像，生成视觉嵌入与图像网格元数据。若开启缓存，结果会被缓存。
4. **嵌入传输**：视觉嵌入通过所配置的传输后端（ZMQ、Mooncake 等）传回预填充服务器。
5. **LLM 计算**：预填充服务器将视觉嵌入与文本 token 组合为包含预计算张量的 mm_inputs。LLM 基于这些嵌入执行预填充与解码计算。若启用 PD 分离，则复用现有的预填充-解码传输逻辑；否则 token 生成直接在预填充服务器上进行。

**编码器服务器**（`--encoder-only`）
- 仅包含视觉部分（不含语言模型权重）；执行预处理 + ViT 前向以生成视觉嵌入
- 支持多模态前缀缓存
- 可水平扩展，实现负载均衡与多图拆分并行推理

**预填充服务器**（`--language-only`）
- 仅包含语言模型
- 接收来自编码器的嵌入
- 启用 PD 时：将 KV 传输给解码服务器；未启用时：在本地解码

**解码服务器**
- 标准的纯解码实例
- 接收来自预填充的 KV 缓存

### 实现细节

#### 图像分发策略
张量并行是把单个模型切分到多张 GPU 上，而 EPD 采用数据并行：运行多个相互独立的编码器实例，并在它们之间分发图像。

分发示例：

```
Request with 7 images: [img0, img1, img2, img3, img4, img5, img6]
3 encoders available

Distribution (after shuffle):
├─ Encoder 0: [img0, img1, img2] (3 images)
├─ Encoder 1: [img3, img4] (2 images)
└─ Encoder 2: [img5, img6] (2 images)
```

#### 传输后端

EPD 支持三种视觉嵌入传输后端：

**zmq_to_scheduler（默认）**
- 直接通过 ZMQ socket 通信
- 嵌入从编码器经 RDMA 传输引擎发送至调度器
- 无阻塞

**zmq_to_tokenizer**
- 嵌入发送至 tokenizer 管理器
- 在分词阶段处理

**mooncake**
- 基于 RDMA 的多节点传输
- 将嵌入注册到共享内存
- 高带宽、低延迟传输


#### 视觉嵌入缓存
编码器支持多模态前缀缓存，以避免冗余的 ViT 计算：
- 消除冗余的视觉编码
- 降低重复图像的处理延迟
- 缓存大小可配置（通过 SGLANG_VLM_CACHE_SIZE_MB，默认 4GB）

### 使用示例
- 启动编码器实例：
```
MODEL=Qwen/Qwen2.5-VL-7B-Instruct
PORT=30002

CUDA_VISIBLE_DEVICES=2 taskset -c $1 python -m sglang.launch_server \
    --model-path $MODEL \
    --encoder-only \
    --enable-prefix-mm-cache \
    --port $PORT
```
- 启动预填充实例：
```
MODEL=Qwen/Qwen2.5-VL-7B-Instruct
PORT=30000
TP=1
MEM_FRACTION=0.5
CHUNK_SIZE=8192

SGLANG_VLM_CACHE_SIZE_MB=0 CUDA_VISIBLE_DEVICES=0 python -m sglang.launch_server \
    --model-path $MODEL \
    --disaggregation-mode prefill \
    --disaggregation-transfer-backend nixl \
    --tp $TP \
    --mem-fraction-static $MEM_FRACTION \
    --disable-radix-cache \
    --chunked-prefill-size $CHUNK_SIZE \
    --language-only \
    --encoder-urls http://127.0.0.1:30002 http://127.0.0.1:30003 http://127.0.0.1:30004 http://127.0.0.1:30005 http://127.0.0.1:30006 http://127.0.0.1:30007 \
    --port $PORT
```
- 启动解码实例：
```
MODEL=Qwen/Qwen2.5-VL-7B-Instruct
PORT=30001
TP=1

CUDA_VISIBLE_DEVICES=1 python -m sglang.launch_server \
    --model-path $MODEL \
    --disaggregation-mode decode \
    --disaggregation-transfer-backend nixl \
    --tp $TP \
    --port $PORT
```

- 启动 minilb：
```bash
python -m sglang_router.launch_router \
  --pd-disaggregation \
  --mini-lb \
  --prefill http://127.0.0.1:30000 \
  --decode http://127.0.0.1:30001 \
  --port 8000
```
## 基准测试
EPD 分离面向视觉密集型负载（多图请求），通过水平扩展编码器服务器来改善首 token 延迟（TTFT）。基准测试脚本如下：
```
python -m sglang.bench_serving \
    --random-image-count \
    --model ${MODEL_PATH} \
    --num-prompts 64 \
    --dataset-name image \
    --random-input-len 128 \
    --random-output-len 256 \
    --image-count 8 \
    --image-resolution 1080p \
    --host $HOST_IP \
    --port $port \
    --backend vllm-chat \
    --request-rate $request_rate 
```

### 实验设置

**环境**：8× H20 96GB GPU

**模型**：Qwen3-VL-235B-A22B-Instruct-FP8

**数据集**：随机多模态数据集
- 文本 token 数：128 / 256
- 每个请求图像数：1-8 张（随机数量，平均约 4 张）
- 图像分辨率：1080p
- QPS 范围：0.2-1.0

**部署配置**：
- **共置（Colocate）**：1 个 PD 实例，tensor-parallel-size=4，使用 4× H20 GPU
- **1E1P**（1 个编码器 + 1 个 PD 实例）：1 个 tensor-parallel-size=1 的编码器 + 1 个 tensor-parallel-size=4 的 PD 实例，使用 5× H20 GPU
- **2E1P**（2 个编码器 + 1 个 PD 实例）：2 个各自 tensor-parallel-size=1 的编码器 + 1 个 tensor-parallel-size=4 的 PD 实例，使用 6× H20 GPU

关键发现（对比共置）：
- 在负载下，编码器/预填充方案将 TTFT 保持在远低的水平（1 QPS 时约为共置方案的 1/6 到 1/8）。
- TPOT 远低于共置方案（约为其 1/8 到 1/10），延迟表现明显更紧凑。
- 高 QPS 下吞吐量约翻倍（0.8-1.0 QPS 时约为共置的 2 倍）。
- TTFT 的大幅下降得益于为编码器分配了专用 GPU 资源。尽管多用了 50% 的 GPU（2E1P 使用 6× H20，而共置为 4× H20），EPD 分离相比单纯扩展传统一体化架构仍能获得高得多的投入产出比（ROI），性能收益超过了额外的资源成本。
- 虽然对图像密集型任务非常有效，但在图像较少的场景下，专用编码器 GPU 的利用率可能偏低（出现空闲时间），这说明当视觉处理是主要瓶颈时，EPD 的资源效率最高。
