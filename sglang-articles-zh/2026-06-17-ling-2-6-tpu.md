# 用 SGLang-JAX 在 TPU 上优化 Ling-2.6-1T：以单个 Pallas kernel 将 MoE 数据搬运隐藏在计算之后

> 原文：[Optimizing Ling-2.6-1T on TPU with SGLang-JAX: Hiding MoE Data Movement Behind Compute with One Pallas Kernel](https://lmsys.org/blog/2026-06-17-ling-2-6-tpu/) · LMSYS Blog · Prayer, JamesBrianD, Haolin Fu, Haoguang Cai, Qinghan Chen

SGLang-JAX 现已支持在 TPU v7x 上高效服务 inclusionAI 的 Ling-2.6-1T。在基线跑通之后，性能剖析（profiling）显示专家混合（Mixture-of-Experts, MoE）路径是主要瓶颈：每一层都要把 token 分散（scatter）到 32 个 JAX 设备上（每颗 v7x 芯片两个设备），执行专家 FFN，再把输出收集（gather）回来。本文首先聚焦 Fused MoE V2——一个新的 Pallas kernel，它将 scatter、专家 FFN 和 gather 融合在一个 kernel 中，同时让 TPU 的计算与数据搬运相互重叠。

采用 Fused MoE V2 后，MoE 预填充（prefill）延迟从 **5.16 ms 降至 2.42 ms**；在同一个 SGLang 解码基准上，**16 块 TPU v7x 芯片的输出吞吐量达到 16 块 H200 GPU 的 1.29×–1.77×**。完整数据见下文。

<p style="text-align: center; color: #666; font-style: italic;">图 1. Ling-2.6-1T 在 TPU v7x-16 与 H200×16 上的解码吞吐量对比，使用 SGLang 默认的 `random` 基准数据集（从 ShareGPT 采样），输入 16,384 token，输出 1,024 token。</p>

## TL;DR

- **Fused MoE V2：** 相比 Fused MoE V1，MoE 预填充延迟降低 **53%**（**5.16 → 2.42 ms**）；解码 kernel 延迟降低约 **15%**（**0.249 → 0.211 ms**）。
- **端到端收益：** 仅替换 MoE kernel 即可将预填充吞吐量提升 **24.8%**，解码吞吐量提升 **18.5%–35.3%**。
- **TPU 对比 H200 解码：** 在 `mc=128` 时，TPU v7x-16 的解码输出吞吐量为 H200×16 的 **1.29×**；在 `mc=512` 时为 **1.77×**。
- **MoE 之外：** Ling-2.6-1T 的完整适配（bring-up）还包括混合 KV/循环状态内存池、GLA 线性注意力，以及单控制器数据并行。

**Ling-2.6-1T 速览：** 一个 **1T 稀疏 MoE** 模型，**每 token 激活 63B 参数**，**256 个路由专家（top-8 路由）外加 1 个共享专家**，**逐通道（per-channel）fp8 MoE 权重**，以及 **MLA + Lightning Linear** 混合主干。MoE 结构驱动了本文前半部分的 kernel 工作；混合主干则引出了后文的内存池与 GLA 适配章节。

## 背景与设置：优化 Fused MoE Kernel

本节所有 MoE 数据均来自 `jax.profiler` 的设备级 trace，除非另有说明。实验设置是一块 16 芯片的 TPU v7x slice：`ep=32`、2×2×4 的 ICI 环面（torus）拓扑、每颗芯片两个设备。负载为 Ling-2.6-1T，16,384 token 预填充与 512 token 解码批，使用逐通道 fp8 MoE 权重。本节所有下界均按单个设备计算，约为芯片级算力与带宽的一半；芯片规格见附录。

Fused MoE V2 的思路，是改变路由 token、专家权重和累加器在 VMEM、HBM 和 ICI 之间的搬运方式。

### 1. MoE kernel 成本模型

Ling-2.6-1T 每层有 256 个路由专家和 1 个共享专家，采用 top-8 路由。在 `ep=32` 下，每个设备持有 8 个本地路由专家。一个 token 选中的 8 个专家通常分布在多个设备上，因此每层的路由路径都是同样的形状：

```text
scatter tokens -> local expert FFN -> gather results
```

在这种结构下，MoE 的运行开销远不止 GEMM FLOPs。kernel 必须让数据经过三条昂贵的路径：跨芯片的 token 路由、专家权重从 HBM 读入 VMEM，以及矩阵乘法单元（MXU）周边的 fp8 布局 / scale 处理。

共享专家是一条本地稠密路径。它会增加本地 FFN 计算，但不参与路由的 all-to-all，对 token 路由负载的影响很小。

#### 计算下界

在预填充 16,384、top-8 路由、`ep=32` 的条件下，每个设备处理：

```text
16384 * 8 / 32 = 4096 routed rows / device
```

平均每个本地路由专家处理约 512 行。共享专家不经过 top-k 路由扇出，只在本地 4096 行上运行一次。路由 + 共享 FFN 的计算量为：

```text
FFN1: 8 experts * 2 matrices * (2 * 512 * 8192 * 2048) = 274.9 GFLOP
FFN2: 8 experts * 1 matrix  * (2 * 512 * 2048 * 8192) = 137.4 GFLOP
Routed total: 412.3 GFLOP / device
Shared expert: 3 matrices * (2 * 4096 * 8192 * 2048) = 412.3 GFLOP
Total: 824.6 GFLOP / device
```

TPU v7x 公开规格为每芯片约 4.614 PFLOP/s 的 fp8 算力。本部署中每颗芯片暴露为两个设备，因此粗略的单设备 fp8 峰值为 2.307 PFLOP/s。理想计算下界为：

```text
824.6 GFLOP / 2307 TFLOP/s = 0.36 ms
```

这是一个理想下界，未计入数据搬运、fp8 打包/解包，以及向量处理单元（VPU）上的 scale 处理。实测生产 trace 中的 **2.42 ms** 仍比该下界高约 **7×**，因此纯 GEMM FLOPs 无法解释这一延迟。

#### ICI token 路由下界

每个设备的 scatter 负载为：

```text
4096 rows * 8192 hidden = 33,554,432 elements
bf16: 67.1 MB
fp8 : 33.5 MB
```

TPU v7x 每颗芯片有 1.2 TB/s 的双向 ICI 带宽，折算下来每条链路每个方向约 100 GB/s。2×2×4 环面让每颗芯片拥有 4 条有效链路，因此芯片的有效单向带宽约为 4 × 100 GB/s = 400 GB/s。由于两个设备共享一颗芯片，粗略的单设备单向注入带宽约为 200 GB/s。

只看注入带宽、忽略跳数和争用时，下界为：

| 负载 | 一次 scatter | scatter + gather |
|---|---:|---:|
| fp8 33.5 MB | 0.17 ms | 0.34 ms |
| bf16 67.1 MB | 0.34 ms | 0.67 ms |

但 all-to-all 并不是单链路带宽测试。在 2×2×4 环面上，随机目的地的平均距离约为两跳：x 方向约 0.5 跳、y 方向约 0.5 跳、z 方向约 1.0 跳。计入这一跳数因子后，按拓扑修正的下界接近：

| 负载 | 一次 scatter（平均跳数修正） | scatter + gather |
|---|---:|---:|
| fp8 | 0.34 ms | 0.67 ms |
| bf16 | 0.67 ms | 1.34 ms |

这仍未计入链路争用、细粒度 DMA、运行时开销和 fp8 布局处理。即便如此，token 路由的开销已经与路由 + 共享的理想计算下界处于同一量级，并远高于仅路由的计算下界。

#### HBM 权重搬运下界

再来看路由专家权重的 HBM 读取开销。如果权重预取没有被流水线隐藏，这笔开销会立刻显现在关键路径上。

一个本地专家的 fp8 权重为：

```text
W1 + W3 + W2 = 3 * 8192 * 2048 bytes = 50.3 MB
8 local experts = 402 MB
```

共享专家额外增加一组本地 FFN 权重，规模约为一个本地专家，但不引入 all-to-all 流量。下文的估计聚焦于路由专家路径。

TPU v7x 的 HBM 带宽约为每芯片 7.38 TB/s，即每设备约 3.69 TB/s。完整读取 8 个本地专家各一次的下界为：

```text
402 MB / 3.69 TB/s = 0.11 ms
```

实际运行中，kernel 会按每个 token 暂存 tile 重新读取一次权重。tile 大小由 `bts`（block token staging size，token 暂存块大小）决定，即为一个专家 FFN tile 送入 VMEM 的路由 token 行数。Ling 预填充使用 `bts=160`。由于每个专家约处理 512 行，预填充需要 `ceil(512 / 160) = 4` 个 token 暂存 tile。V2 在这些 tile 之间对权重预取做了流水化，因此 HBM 读取下界大致为：

```text
4 * 402 MB / 3.69 TB/s = 0.44 ms
```

权重读取并非必须出现在关键路径上。V2 用双缓冲（double buffering）把它们隐藏在 MXU 计算窗口之后。这些数字也解释了为什么必须这样调度：如果把 HBM 读取串行排在 GEMM 之前，其开销已经超过纯计算下界。

#### 要点小结

TPU 上的 MoE 主要是一个数据搬运与重叠（overlap）问题：

- 路由 + 共享 FFN 计算下界：约 **0.36 ms**；
- fp8 scatter + gather 拓扑下界：约 **0.67 ms**；
- 专家权重 HBM 读取下界：每个 tile 约 **0.11 ms**，按 `bts=160` 计约 **0.44 ms**；
- fp8 打包、scale 广播和布局重排还会持续消耗 VPU 和 VMEM 带宽。

优化目标不是减少 FFN FLOPs，而是把 token 路由、权重预取和 fp8 重排隐藏到路由计算窗口之后。

### 2. 为什么这需要一个 Pallas 融合 kernel

本节剩余部分会用到一些 TPU 术语。简化图景是：一个 TensorCore 包含 MXU、VPU 和 VMEM；HBM 位于芯片之外；芯片之间通过 ICI 通信。

<img src="/images/blog/2026-06-17-ling-2-6-tpu/tpu_v7x_execution_model.png" alt="简化的 TPU 执行模型" style="display:block; margin: 2.5em auto 0.5em auto; width: 100%; max-width: 900px;" />
<p style="text-align: center; color: #666; font-style: italic;">图 2. 本节使用的简化 TPU 执行模型，改编自 <a href="https://jax-ml.github.io/scaling-book/tpus/">JAX Scaling Book 的 TPU 概览</a>。</p>

在 MoE kernel 中，这些硬件单元对应的工作如下：

| 硬件单元 | TPU 职责 | MoE 中的工作 |
|---|---|---|
| MXU | 矩阵乘法单元 | 路由专家的 W1/W3 gate-up GEMM 与 W2 down GEMM |
| VPU | 向量运算、归约、布局处理 | SiLU、门控相乘、scale 相乘、fp8 打包/解包、lane 重排 |
| VMEM | 紧邻 MXU/VPU 的片上暂存存储（scratchpad） | 路由 token tile、专家中间结果、输出累加器、预取权重 tile |
| HBM | 每颗芯片附带的大容量片外内存 | 专家权重、token 暂存缓冲区、大型中间缓冲区 |
| HBM-DMA | HBM ↔ VMEM 数据搬运 | 将当前/下一个专家权重预取进 VMEM；必要时移动暂存缓冲区 |
| ICI / ICI-DMA | TPU slice 内部的直连片间网络 | 在源芯片与目标芯片之间搬运路由 token 负载；scatter 到专家所在设备，再 gather 回 token 顺序 |

纯 JAX 的原生 MoE 实现可以正确表达路由、专家 FFN 和输出聚合，但它无法暴露单个 MoE 层内部的细粒度调度。一旦 scatter、专家 FFN、HBM 权重搬运、fp8 布局处理和 gather 跨越多个 JAX 算子或集合通信边界，XLA 就无法可靠地把 ICI-DMA、HBM-DMA、MXU 和 VPU 的工作安排到一条手工调度的流水线上。

这条路径也不能当作独立的稀疏查找交给 SparseCore 处理：scatter 产生的本地专家 token 布局、每个专家的偏移、专家输出和最终 token 顺序彼此依赖。真正有价值的优化空间就在 MoE kernel 内部。

<img src="/images/blog/2026-06-17-ling-2-6-tpu/native_fused_pipeline.png" alt="朴素的融合 MoE 流水线" style="display:block; margin: 2.5em auto 0.5em auto; width: 100%; max-width: 900px;" />
<p style="text-align: center; color: #666; font-style: italic;">图 3. 通信与计算阶段串行执行的朴素融合流水线。语义正确，但各引擎之间没有细粒度的重叠调度。</p>

理想的稳态是：当 MXU 在计算专家 *i* 时，HBM-DMA 在预取专家 *i+1* 的权重，ICI-out 在发送下一批路由 token，ICI-in 在接收上一批输出，VPU 在处理上一个矩阵乘留下的 scale 与布局工作。

要表达这种调度，scatter、专家 FFN 和 gather 必须落在同一个 Pallas kernel 里。融合的首要目的不是减少算子数量，而是创造一个调度空间，让相互依赖的各阶段可以在 MXU、VPU、HBM-DMA 和 ICI-DMA 之间手工排布。

### 3. V1：已融合，但 hidden 维度分块零碎

我们的起点是 Fused MoE V1，由 Jevin Jiang、Kyuyeun Kim 等人在 tpu-inference 项目中提出并优化 [4]，后经一些修改以 `FusedEPMoE` 的形式移植进 SGLang-JAX [5]。V1 已经把 scatter、专家 FFN 和 gather 放进一次 Pallas 调用，并在每个设备上执行 8 个本地专家。这满足了在 kernel 内做通信/计算调度的前提，但 V1 仍未达到上文描述的理想稳态。

问题出在专家内部。一个 MoE 专家需要的不仅仅是输入 token tile 和一个 GEMM 输出。为了让通信与计算重叠，kernel 还需要权重暂存缓冲区、中间激活、输出累加器和 DMA 双缓冲。Ling 的 hidden size 为 8192，若让整个 hidden 维度常驻内存，VMEM 会很快耗尽，尤其是 f32 累加器和 W1/W3/W2 暂存。

因此 V1 走了保守路线：切分 hidden 维度，让更小的工作集流经 VMEM。

对于 Ling 16,384 预填充，V1 的配置是：

```text
bf=1024 / bd1=512 / bd2=512 / bts=128 / btc=128
```

这组分块配置回答的是一个放置问题：哪些 token 行、中间通道和 hidden 通道留在 VMEM，哪些从 HBM 流入。

这些参数可以理解为沿 GEMM 各轴的 tile 大小：

| 参数 | 控制对象 | 性能含义 |
|---|---|---|
| `bts` | 每个专家 tile 送入 VMEM 暂存的路由 token 行数 | 控制 M；过小时 DMA / VPU / MXU 的固定开销无法摊薄 |
| `btc` | `bts` 内每次计算循环使用的 token 行数 | 内层 M 计算 tile；不能超过 `bts`，通常要能整除它 |
| `bf` | W1/W3/W2 的中间通道数 | 控制 FFN 中间 tile；越大通常 MXU 窗口越长，但占用更多 VMEM |
| `bd1` | FFN1 hidden 维度归约 K 切片 | V1 切分 hidden K；`bd1` 越小，FFN1 点积次数越多、每次越小 |
| `bd2` | FFN2 hidden 维度输出 N 切片 | V1 切分输出 hidden；`bd2` 越小，部分输出在 HBM 上的往返越频繁 |

因此 `bf/bd1/bd2` 主要控制特征 / hidden 维度，`bts/btc` 控制每个专家的 token 行数。二者共同决定一个 tile 是否装得进 64 MB 的 VMEM 预算，以及围绕 MXU 能重叠多少 HBM-DMA / VPU 工作。

V1 付出了三项结构性代价：

| 代价 | V1 的行为 | 为何有害 |
|---|---|---|
| FFN1 点积太小 | `bd1=512`；fp8 打包后有效 K 约为 256，因此 V1 要扫描 16 个 hidden 维度切片 | `vmatmul` 的固定开销摊薄效果差 |
| token 暂存过于频繁 | `num_bf * num_bd1 * num_token_tiles = 2 * 16 * 4 = 128` 次 HBM→VMEM 暂存 | 大量小 DMA 和布局步骤 |
| FFN2 部分结果溢出到 HBM | 部分输出先写入 `a2a_s_acc_x2_hbm`，之后再读回用于后续 `bf` 累加 | HBM 的读取-修改-写回（read-modify-write）割裂了关键路径 |

V1 有一些微观重叠，但 hidden 维度切片使重叠窗口很小。预取一次只覆盖一个小切片，FFN2 的部分输出仍要在 HBM 上往返。V1 的预填充延迟为 **5.16 ms**。

### 4. V2：VMEM 常驻与权重双缓冲

V2 不只是把 V1 的 tile 调大，而是改变了张量的生命周期。V1 的循环在 hidden 维度切片之间轮转；V2 则让路由 token、gate/up 中间结果和输出累加器在整个 FFN 循环期间常驻 VMEM，同时 W1/W3/W2 通过双缓冲从 HBM 流式读取。

这会把更多 VMEM 花在长生命周期张量上，但消除了大部分 hidden 切片暂存，并几乎根除了 FFN2 的 HBM 读取-修改-写回路径。

Ling 16,384 预填充的 V2 生产配置是：

```text
bf=512 / bts=160 / btc=80
```

V2 没有 `bd1` 和 `bd2`，因为它不再切分 hidden 维度。结构上的变化如下：

| 每个专家 | V1 | V2 | 效果 |
|---|---|---|---|
| FFN1 点积 | 每次硬件点积的有效 K 约 256 | fp8 分块 K 约 2048；4 个分块覆盖完整 hidden | K 约大 8× |
| W2 输出 | `bd2=512`，每次只产生一个窄 hidden 切片 | 输出分块约 4096 个 hidden 通道 | N 约大 16× |
| token 暂存 | 128 次小规模暂存 | 约 4 次完整 hidden 暂存 | 暂存次数约少 32× |
| FFN2 累加器 | 部分输出经 HBM 溢出 / 重载 | `b_y_acc_vmem` 在 VMEM 内跨 `bf` 累加 | HBM 读取-修改-写回基本消失 |

这也解释了为什么在 V1 里单纯调大 `bd1` / `bd2` 并不够。在 V1 中，更大的 hidden tile 会同时放大权重缓冲区、token 暂存缓冲区和部分输出暂存，很快撞上 64 MB 的 VMEM 上限。更重要的是，V1 仍在 hidden 切片之间轮转，并没有让 token 和输出累加器常驻。

有了这个 VMEM 常驻的工作集，V2 获得了更大的 MXU tile、更少的 HBM 溢出和更长的路由计算窗口。在启用激活量化之前，设备级 trace 显示 V2 已将预填充延迟从 **5.16 ms** 降到 **3.02 ms**。再启用激活量化和 kernel 内共享专家重叠后，生产 trace 达到 **2.42 ms**，比 V1 低约 **53%**。

解码遵循同样的逻辑，但提升空间较小。在 512 token 解码批下，kernel 延迟从 **0.249 ms** 降到 **0.211 ms**，约 **15%**。每个专家的有效 M 维度很小，MXU tile 难以充分摊薄固定开销；这条路径也更接近专家权重 HBM 读取下界——解码 trace 中 HBM 带宽利用率已达约 80%。因此 V2 对解码仍有帮助，但无法像预填充那样完全兑现 VMEM 常驻与路由计算窗口的收益。

### 5. V2 的针对性优化

#### 逐通道（per-channel）的 `direct_scaled_dot`

fp8 权重量化的 scale 粒度，决定了 MXU 看到的是一个大 GEMM 还是一串小 GEMM。

在 per-block（分块）量化下，scale 取决于 K 分块：

```text
out[m,n] = sum_k A[m,k] * W[k,n] * scale[block(k),n]
```

scale 无法从归约中提出来，所以 K 必须切成多个分块：每个分块做一次小的 fp8 点积，乘以该分块的 scale，再累加。一个大 GEMM 就变成了许多小 GEMM，中间穿插 VPU 工作。

在 per-channel（逐通道）量化下，scale 只取决于输出通道：

```text
out[m,n] = (sum_k A[m,k] * W[k,n]) * scale[n]
```

scale 可以在归约之后才施加。V2 的 `direct_scaled_dot` 把 fp8 token 和 fp8 权重直接送入 MXU，得到 f32 部分和，之后才应用 per-token / per-channel 的 scale。Ling 的 MoE 权重使用 per-channel scale，因此这条路径可用。

这保留了完整的 K 点积，避免把大 GEMM 切成 scale 分块。剩下的开销是 fp8 子字（sub-word）打包、scale 广播和 lane 重排。若改用 per-block 量化，还要在此基础上增加 K 切分和分块间的 scale 处理。

#### 激活量化

V2 在 scatter 之前把激活从 bf16 量化为 fp8，直接把路由 token 负载减半。在 Ling 16,384 预填充上，kernel 内 scatter 阶段从 **1.39 ms** 降到 **0.65 ms**。

这与上文 ICI 下界的推算一致：负载从 bf16 67 MB 降到 fp8 33.5 MB 时，通信下界几乎减半。

Ling-2.6-1T 支持激活量化，因此 V2 采用动态 per-token fp8，在我们的评测中未观察到精度回退（见附录中的 AIME 2026 验证）。

#### kernel 内共享专家

Ling 每层还有一个共享专家。如果它作为独立的稠密 MLP 运行，就会在关键路径上多出一段。V2 把共享专家移进同一个 kernel，复用路由专家的 token / 权重 VMEM 缓冲区，并把它调度进 scatter 窗口内。

共享专家自身的计算量约为 **0.159 ms**，但给关键路径只增加了 **0.068 ms**，约 **2.7%**。原因很简单：共享专家不需要跨芯片派发 token，所需的 token 全在本地，因此可以与路由 FFN 之前的 scatter 阶段重叠。

元数据块是路由相关的簿记工作：token 到专家/设备的映射、每个专家的偏移/计数，以及 scatter/gather 索引。它只搬运少量元数据，耗时几十微秒，不是预填充的主要开销。

| 消融 / 组件 | 结果 | 解读 |
|---|---:|---|
| 完整 V2 生产配置 | 2.42 ms | 本节使用的标准 MoE 预填充延迟 |

这与成本模型的分析吻合。即使算上共享专家，理想计算下界也只有约 **0.36 ms**，去掉矩阵乘对总延迟几乎没有影响。scatter/gather 的工作量接近 2.4 ms，但其中约 1.8 ms 被隐藏在路由计算窗口之下。

因此 V2 的收益来自三个机制：

- token 与累加器常驻 VMEM，减少 token 暂存和 HBM 读取-修改-写回；
- 专家权重采用双缓冲，让 HBM 读取隐藏在 MXU 工作之后；
- scatter/gather 使用分组缓冲（banked buffer）和出站/入站 ICI 通道，与路由计算重叠。

### 7. V2 之后还剩什么

完成重叠之后，图 5 中剩余的最长片段是路由计算窗口，约占 **2.42 ms** 总时长的 68%。这并不意味着问题回到了纯 FLOPs：Mosaic LLO 导出显示，剩余瓶颈主要是 fp8 打包 / lane 重排 / scale 广播，外加 VMEM 对 tile 大小的限制。

#### 通信受拓扑限制

在我们的测量中，扁平（flat）all-to-all 优于分层（hierarchical）all-to-all。扁平配置下，send/recv 划分直接根据最终专家归属构建，一次 32 路 all-to-all 就把路由 token 负载从源设备送到最终目标设备。

我们也测量了一种分层配置：把 32 设备间的交换沿 2×2×4 ICI 环面拆分，先在一个局部维度内重排，再沿下一个维度接力转发，直到每个 token 到达目标专家所在设备。每一轮的通信范围更小，但同样的路由 token 负载要经过多个接力阶段，增加了暂存缓冲区和同步边界，总搬运字节数接近翻倍。两种模式都是在融合 kernel 之外作为独立的 all-to-all 基准测量的，因此这些数字与 kernel 内 trace 不具备直接可比性。

| 模式（负载 = 16384 × 8192 × dtype_size） | bf16 | fp8 |
|---|---:|---:|
| 扁平 all-to-all | 2.09 ms | 1.34 ms |
| 分层 all-to-all | 3.12 ms | 1.88 ms |

因此，通信侧的实际杠杆不是更复杂的路由算法，而是更少的字节和更好的重叠。激活量化正是这样的手段。

#### 路由计算受 VPU / VMEM 限制

路由 FFN1（W1+W3）实测约 **0.72 ms**，而理想稠密 fp8 GEMM 下界约为 **0.12 ms**。这个差距并非由激活量化造成：开启激活量化时 FFN1 约 0.74 ms，关闭时约 0.71 ms。

tile 扫描（sweep）也表明当前配置已接近局部最优：

| `bts` / `btc` | kernel 延迟 | VMEM |
|---|---:|---:|
| **160 / 80** | **2.42 ms** | 47 MB |
| 160 / 160 | 2.44 ms | 47 MB |
| 128 / 128 | 3.12 ms | 44 MB |
| 256 / 128 | 3.19 ms | 54 MB |
| 256 / 256 | 3.23 ms | 54 MB |
| 384 / 128 | OOM | 62 MB |

Mosaic LLO 导出解释了原因。整个 kernel 只有 4096 条真正的 `vmatmul` 指令，而 fp8 布局和向量侧准备工作在指令流中占据主导：

| LLO 指令 | 数量 | 作用 |
|---|---:|---|
| `vselect` | 50880 | 子 lane 选择 / 混合 |
| `vbitcast` | 46566 | fp8 子字重解释 |
| `vcombine` | 36380 | 子 lane 合并 |
| `vpack_format` | 34368 | MXU 输入打包 |
| `slane` | 29960 | 子 lane 移动 |
| `vunpack` | 25600 | fp8 解包 |
| `matmul_data_format` | 25600 | MXU 前的格式转换 |
| `vrot` | 21524 | lane 旋转 |
| `vmatres` / `vmatprep` | 17408 / 10240 | MXU 排空 / 供数 |
| `vslreplicate` | 6032 | scale 广播 |
| **`vmatmul`** | **4096** | 实际的矩阵乘法 |

V2 避免了 per-block 量化的 K 切分，但 fp8 子字打包、scale 广播以及 MXU 供数/排空仍消耗大量 VPU / 布局工作。由于 VMEM 上限为 64 MB，`bts` 无法持续增大；tile 较小时，这些固定开销无法被摊薄。

#### 小结

V2 隐藏了大部分显式通信和 HBM 权重搬运之后，剩余瓶颈仍然是数据搬运，只是换了一种形式：fp8 布局工作、VMEM 容量压力，以及让 MXU 不断有数据可算。

- ICI all-to-all 受环面拓扑和链路争用限制。
- HBM 权重读取必须靠双缓冲来隐藏。
- fp8 打包和 scale 处理会让 MXU 等待数据成形。
- VMEM 容量限制了 tile 大小和可共存的缓冲区数量。

下一步必须改变约束本身：

- **Kernel 侧：** 减少 fp8 打包/解包和 scale 处理，但这越来越取决于让模型量化格式与 TPU 原生执行格式对齐：TPU 友好的 scale 粒度、fp8 布局，或未来 MXU 原生的低精度格式（如 FP4 或 MXFP8）。
- **负载侧：** 跨批次重叠，让路由窗口能与其他层的工作并行运行。
- **硬件侧：** 提供更支持 all-to-all 的互连拓扑，或提供更大的 VMEM / 更高的 ICI 带宽。

关于未来的 TPU 硬件，可参阅 Google Cloud 的 [TPU 8t 与 TPU 8i 技术深度解析](https://cloud.google.com/blog/products/compute/tpu-8t-and-tpu-8i-technical-deep-dive)。

## Ling-2.6-1T 的整体适配（bring-up）

要让 Ling-2.6-1T 在 TPU 上服务良好，MoE 融合只是其中一环。其余的适配工作在于让运行时匹配模型的混合主干：为全注意力层和线性注意力层分配不同的状态，让 GLA 的预填充和解码跑在对 TPU 友好的 kernel 上，并规划 DP/TP 映射使分组 RMSNorm 保持在单芯片内。

### 混合内存池

Ling-2.6-1T 并没有向运行时暴露单一统一的注意力状态。它的 10 个 MLA 全注意力层写入按 token 索引的 KV 缓存，而 70 个 Lightning / GLA 层携带按请求索引的循环状态（recurrent state）。因此内存分配器必须同时管理两种不同的容量：MLA 的常驻历史 token，以及线性注意力层的活跃请求槽位。

这种单位比较很容易误读。在 TP=4、bf16 KV、fp32 循环状态的条件下，MLA KV 缓存的开销在 10 个全注意力层上合计约为每设备每 token 12.5 KiB。Lightning 循环状态的开销在 70 个线性层上合计约为每设备每请求 70 MiB。这两个数字只有放回到单个请求中才有意义：一个 16K token 的 prompt 每请求约需 200 MiB 的 MLA KV，256K token 的 prompt 约需 3.1 GiB，而循环状态始终保持在 70 MiB 左右。循环状态是固定的并发成本；KV 缓存则是随上下文长度线性增长的 token 容量成本。

SGLang-JAX 把这两类状态分开管理，同时保持单一的请求生命周期：`HybridLinearKVPool` 只为 10 个全注意力层保存 KV（70 个线性层不占用 KV 槽位）；`RecurrentStatePool` 为每个活跃请求持有一个 fp32 循环状态槽位；`HybridReqToTokenPool` 把两者绑定在一起：请求在准入时同时获取两者，结束时同时释放。分块预填充（chunked prefill）和解码从同一个循环状态槽位继续，而不是每个 chunk 或每个 token 都分配新状态。HBM 预算也按同样方式切分：可配置的比例保留给循环状态槽位（由此限制并发上限），其余分给 KV 缓存（由此限制常驻 token 数）。

JAX 还增加了一个约束：运行时无法像 CUDA 路径那样原地更新这些缓冲区。SGLang-JAX 把 KV 池和循环状态池包进一个 `MemoryPools` pytree，作为 donated（捐献）JIT 参数传入模型。每次前向计算返回更新后的池缓冲区，运行时再通过 `replace_all()` 写回。这样，缓冲区捐献（buffer donation）、TP/DP 分片和未来的池扩展都留在容器层面处理，而不必在前向循环里散布特例。

### GLA（门控线性注意力）

每个 GLA 层 [7] 把历史保存在固定大小的循环状态中，而不是为每个历史 token 存一条 KV 记录。其更新可以写成：

$$
S_t = \gamma_t\, S_{t-1} + k_t^\top v_t, \qquad o_t = q_t\, S_t
$$

这让注意力历史从随 token 逐个增长的东西，变成每个活跃请求一个状态张量。在长上下文下，这就是主要收益：携带历史的计算量保持线性、状态体积保持固定，而不需要物化并读取不断膨胀的 KV 历史。

**预填充：让循环递推足够并行以适配 TPU。** 按字面理解，上面的循环递推是串行的：token *t* 依赖于 token *t−1* 经衰减和更新后的状态。这样跑预填充会把 16K 或 256K 的 prompt 变成漫长的逐 token 扫描，而这恰恰是 TPU 最不适合的计算形状。

SGLang-JAX 采用数学上等价的分块（chunk-wise）形式。序列被切成固定 64 token 的 chunk。在 chunk 之间，前一个 chunk 的最终状态作为下一个 chunk 的初始状态，长程依赖仍沿时间向前传递；而在 chunk 内部，循环递推被重排为对 token 块的稠密矩阵运算。只有 chunk 边界保持串行，chunk 内部的工作以块并行的方式在 TPU 上完成。

**解码：循环递推的自然形态。** 解码更简单：预填充已把 prompt 折叠进循环状态，每个新 token 只需读取该请求的当前状态，执行一次循环更新，产出注意力输出，再写回新状态。问题从长序列并行转为高效的小状态更新。

**推理服务集成：让 GLA 留在同一条运行时路径中。** GLA 是作为层级（layer-level）的后端选项集成的，而不是一个独立的调度器模式。全注意力层读写 KV 缓存；GLA 层读写循环状态；两者都在同一批预填充和解码批次中推进。调度器看到的仍然是一条生命周期：准入、预填充、解码、释放。

这套集成在功能上是完整的，但预填充 kernel 尚未调优到 Fused MoE V2 的程度。GLA 的数学不需要改变，需要改变的是执行调度。

### 单控制器数据并行支持

Ling-2.6-1T 的分组注意力后 RMSNorm 给张量并行带来了硬约束。每个 norm 组包含 8 个 head。如果一个组跨芯片，方差计算就会在每一层都变成跨芯片 reduce，直接落在解码关键路径上。因此纯 TP 没有好的设置：tp ≤ 8 能让 norm 组保持在单芯片内，但对万亿参数模型并行度不足；tp > 8 则会拆散 norm 组，付出 all-reduce 的代价。

单控制器 DP 把数据并行当作另一个 mesh 轴，化解了这一矛盾。mesh 被切成多个 DP 组；每组使用足够小的 TP 以保持分组 RMSNorm 在单芯片内，请求则分布在各 DP rank 上。权重在每个 DP 组内部仍按 TP 分片。每层的 norm reduce 消失了，腾出的 ICI/HBM 预算可以转投更高的并发。

关键的设计选择是：DP 属于 SPMD 运行时的一部分，而不是一群相互独立的服务副本。SGLang-JAX 只运行一个逻辑调度器，`dp_rank` 附加在请求、KV 分配和前缀缓存键上。这带来了基于同一份负载快照的全局准入控制、跨主机的确定性批次构建，以及一个全局前缀缓存结构——其条目以 `(dp_rank, prefix)` 为键。

这也与混合运行时的其他部分良好组合。把 mesh 扩展到更大配置（比如在每个数据并行组内部再加张量并行）只是改变 mesh 形状，而不是另起一套调度器，因此内存池、批处理路径和注意力后端的心智模型保持不变。

> **关于端到端预填充与 MoE kernel 加速比的说明：** Fused MoE V2 kernel 将 MoE 层的预填充延迟降低了约 53%（设备级 trace），但端到端预填充吞吐量只提升了约 25%（v1 → v2）。原因是 MoE 层已不再是预填充的主要开销：GLA（门控线性注意力）预填充 kernel 目前是主要瓶颈，尚未优化到同等程度，因此稀释了端到端预填充的加速效果。同样的瓶颈也解释了为什么图 6 中 TPU v7x-16 在预填充一栏落后于 H200×16，却在两个解码数据点上领先。把 GLA 预填充 kernel 提升到同等水平的工作正在进行中，我们预期这将释放更大的端到端预填充收益。

## 局限与后续工作

本次发布的 Ling-2.6-1T 支持是刻意收窄范围的；以下几项是我们正在积极跟进的后续工作：

- **GLA / 线性注意力预填充 kernel。** 如基准测试一节所述，GLA（Lightning Linear）预填充 kernel 现在是预填充的主要开销。通过更好的分块/tiling、融合门控与循环状态更新、以及对 MoE kernel 采用过的同一套 MXU/VPU/DMA 重叠手段，把它提升到同等水平，是改善端到端预填充最直接的抓手。
- **动态专家并行负载均衡（EPLB）。** 当前的 `FusedEPMoE` 路径使用静态的专家到设备放置，但真实负载在 256 个路由专家上的命中率并不均匀。一个根据观测流量周期性重平衡专家到 rank 映射的动态 EPLB 环节，可以缩小单设备峰值利用率与平均利用率之间的差距，在更大 batch 时尤其明显。
- **基于混合内存池的基数树缓存（radix cache）。** SGLang 的 RadixAttention [9] 前缀缓存假设存在单一的按 token 组织的 KV 池，而 Ling-2.6-1T 把按 token 的 KV 与按请求的循环状态混在一起，朴素的前缀共享会在线性层上悄悄把不同请求的状态混起来。我们正在设计一个扩展：按 token 前缀共享 MLA KV，同时对每个共享前缀快照并重新键控（re-key）循环状态，使共享的系统 prompt 和长智能体轨迹可以无损复用。
- **MTP / EAGLE 投机解码。** Ling-2.6-1T 的 checkpoint 自带一个 EAGLE 风格的 MTP 头（3 个投机步、4 个草稿 token、top-k 1）。当前路径只跑基座模型解码；把 MTP 头接入 SGLang-JAX 的投机解码运行时，是解码吞吐量的下一个里程碑。混合内存池层已经为草稿步状态预留了空间，剩下的工作在验证器与草稿接受 kernel 上。

## 附录

### 成本模型使用的 TPU v7x 规格

TPU v7x 公开规格为每芯片约 4.614 PFLOP/s 的 fp8 算力、7.38 TB/s 的 HBM 带宽和 1.2 TB/s 的双向 ICI 带宽。本部署中每颗芯片暴露为两个设备，因此成本模型一节中的单设备下界约使用芯片级算力与带宽的一半。关于 TPU 内存层级与执行单元（MXU、VPU、VMEM、HBM、ICI）的背景，可参阅 Google Cloud 的 [TPU 系统架构](https://cloud.google.com/tpu/docs/system-architecture-tpu-vm)。

### 性能复现

双方运行相同的模型和相同的 SGLang 基准负载：
预填充（输出 1，mc 128）· 解码（输出 1024，mc 128）· 解码（输出 1024，mc 512）。

**TPU：SGLang-JAX（Fused MoE V1 / V2）。** TPU v7x，16 芯片（2×2×4 ICI 环面 → 32 设备），tp = ep = 32, dp = 8，per-channel fp8 MoE 权重。

TPU 侧使用 sgl-jax 分支 `fused-moe-v2-with-sp-rs` @ `49c2ed1`，镜像 `jax-ai-image/tpu:jax0.8.1`。

V1/V2 消融只改动 MoE 相关 flag：Fused v1 = `--moe-backend fused`；v2 基础版 = `fused_v2 --no-moe-fused-act-quant --no-moe-fused-shared-experts`。

v2 +激活量化在此基础上加 `--moe-fused-act-quant`；v2 +激活 +共享专家重叠则两个都开。两个外部共享专家配置使用 `--mem-fraction-static 0.85`，因为在 0.88 下会 OOM。

**GPU：SGLang（H200×16，参照组）。** 2 节点 × 8× H200，tp = 8, pp = 2；与 TPU 侧相同的模型和基准负载。

性能测试的完整基准命令见 [SGLang-JAX cookbook][ling-26-cookbook]。

### 服务启动与精度复现

AIME 2026 验证使用 `MathArena/aime_2026`，30 道题，pass@1：**26 / 30 = 86.7%**。整个运行零请求错误，所有响应正常结束（`finish_reason=stop`，32768 token 内无截断）。这表明 fp8 融合 MoE 服务路径没有明显的精度回退。

完整的服务启动命令、请求与工具调用示例，以及 AIME 2026 精度复现，见同一份 [SGLang-JAX cookbook][ling-26-cookbook]。
