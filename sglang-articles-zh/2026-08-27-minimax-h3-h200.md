# 8×H200 上的 MiniMax-H3：无损加速 1.95×，SSIM 0.76–0.91 下最高 6.24×

> 原文：[MiniMax-H3 on 8×H200: 1.95× Lossless, Up to 6.24× at 0.76–0.91 SSIM](https://lmsys.org/blog/2026-08-27-minimax-h3-h200/) · LMSYS Blog · SGLang Diffusion Team, Cache-DiT Team, NVIDIA, Ant Group

## TL;DR

我们在 8× NVIDIA H200 上，使用 [SGLang Diffusion](https://github.com/sgl-project/sglang) 对 [MiniMax-H3](https://github.com/MiniMax-AI) 视频生成进行了基准测试，并在六种工作负载下保持提示词、随机种子、分辨率、帧率和去噪步数完全一致。

- **SGLang 的稠密无损路径比 Diffusers 快 1.85–1.95×**，不含任何近似：同样的去噪计算，跑在更快的运行时上。
- **叠加步间复用与稀疏注意力最高可达 6.24×，平均 SSIM 在 0.76–0.91。** 测试中最快的配置 SubBlock 0.80 + Cache-DiT stride 在 5 s/10 s 的 T2VA 上达到 **5.06×/5.72×**，在 FL2VA 上达到 **5.86×/6.24×**。代价并不均匀：同一配置下 FL2VA 保持 0.85–0.91 的 SSIM，而 T2VA 降至 0.76–0.78。
- **若追求质量优先的默认选择，单独使用 Cache-DiT**（最高 2.99×，平均 SSIM 0.90–0.92）。若要速度与质量的均衡折中，**SubBlock 0.75 + Cache-DiT stride** 可在 SSIM 0.79–0.90 下带来 4.90–5.93× 的加速。
- 这些收益来自三层可以相互叠加的机制：**融合算子**（在孤立的非 GEMM 站点上为 2.00–12.16×——是微基准数据，并非端到端可加），**步间复用**（Cache-DiT 跳过冗余的去噪步骤），以及 **SubBlock 稀疏注意力**（NVIDIA 的块稀疏前向计算，降低实际执行步骤的开销）。

**范围说明。** 本次对比只覆盖 SGLang Diffusion 的三项加速手段。它还支持更多有损路径——包含量化与渐进式分辨率——但这些*不在*本次测试范围内，因此这里的数字只是可用加速空间的一部分，而非上限。下文所有数据均为实测，而非推算；文末的视频片段可以让你自行判断质量代价。

## 背景

SGLang Diffusion 已经为 MiniMax-H3 提供了快速的无损路径，但更快的高质量视频*有损*生成一直是社区长期追求的目标。依托其长期积累的一整套多样化的有损加速手段，SGLang Diffusion 团队过去几周在这方面持续投入；本文首次以实测数据说明这些手段究竟能达到什么效果。

视频扩散生成的开销主要由两部分构成：去噪循环要把同一个 transformer 跑几十遍，而每一步的大部分计算预算都花在对超长 token 序列的注意力上。一段 5 秒、1344×768、24 FPS、50 步去噪的视频，早已超出单卡实际可行的范围，所以问题不在于要不要并行，而在于剩余的计算中还有多少可以省掉。

三项加速手段从不同方向入手，并且可以相互叠加：

- **融合算子**在不改变计算逻辑的前提下削减每一步的固定开销。
- **Cache-DiT** 在去噪步之间复用结果，让部分步骤完全不用执行。
- **SubBlock 稀疏注意力**通过跳过贡献低于阈值的注意力块，降低实际执行步骤的开销。

第一项是无损的。后两项用相似度换取速度，因此本文的每一个数字都附带相对于无损基线的 SSIM。

## 总览

答案取决于你选的基线。与同条件的 Diffusers 相比，SGLang 的稠密无损路径在两项任务、两种时长下已经快了约 2 倍。Cache-DiT 在去噪步之间复用计算，SubBlock 稀疏注意力则降低仍在执行的步骤的开销。二者叠加构成了本矩阵中最快的路径。

若要一个质量优先的加速默认配置，选**Cache-DiT conservative 或 Cache-DiT stride**，不叠加 SubBlock。
若要速度与质量的均衡折中，选 **SubBlock 0.75 + Cache-DiT stride**，在 5 s 时提供 4.90–5.64× 加速，10 s 时提供 5.44–5.93× 加速。

### 关键结论

- **SGLang 的稠密路径是第一份唾手可得的收益。** 在负载完全一致的前提下，它在两项任务、两种时长上相对 Diffusers 提供 1.85–1.95× 加速。
- **SubBlock 0.75 + Cache-DiT stride 是均衡型配置。** 它在保持良好输出质量的同时，在 5 秒时提供 4.90–5.64× 加速，10 秒时提供 5.44–5.93× 加速。
- **stride 缓存带来的吞吐提升最大。** 单独使用即可达到 3.99–4.46×，而 conservative 配置为 2.65–2.99×。
- **FL2VA 从缓存加稀疏的组合中受益略多。** FL2VA 最快达到 5.86×/6.24×，T2VA 为 5.06×/5.72×。
- **速度与质量的取舍清晰可见。** conservative 的 Cache-DiT 保留 0.8986–0.9771 的 SSIM；激进的 0.80 + stride 配置为换取最低延迟而让渡了部分质量余量。

## 加速来自哪里

配置层面的加速来自三种机制。

**融合算子**降低每个仍在执行的步骤的开销。H3 路径将按索引更新的 AdaLN、门控残差、SwiGLU 激活，以及 QK RMSNorm 与 3D RoPE 融合在一起，减少中间张量、内存流量和 kernel 启动次数。下一节给出这些孤立算子的测量结果；它们属于每步实现的一部分，而 Cache-DiT 和 SubBlock 决定这套实现实际执行多少。

**Cache-DiT** 在 MiniMax-H3 共享的 DiT 块堆栈上挂载一个 DBCache 上下文。在预热步之后，它会评估所配置的边界块，并将归一化后的残差变化与上一次缓存状态比较。如果变化低于阈值且连续缓存上限允许，中间块就复用缓存结果；否则重新计算整个堆栈并刷新缓存。所有缓存模式都使用 `Fn=1`、`Bn=0` 和四步预热：

- conservative：共享打包堆栈 RDT `0.04`，最大连续缓存步数 `1`；
- stride：共享打包堆栈 RDT `0.08`，最大连续缓存步数 `3`。

MiniMax-H3 只有一个 `MiniMaxH3DiTModel`，其块堆栈同时承载打包的视频与音频 token。因此 Cache-DiT 对整个打包堆栈做一个共享决策，不会分别维护视频和音频两套缓存。worker 记录的是一份合并的 Cache-DiT 步骤列表，下文 trace 图例也遵循这一执行模型。

**SubBlock 稀疏注意力**减少计算步骤中读取的 KV 块数量。它使用 `n_k=n_q=4`；前十步去噪使用稠密注意力，之后启用 SubBlock。最小序列长度为 `4096`。矩阵测试了稀疏度 `0.75` 和 `0.80`；后者更快，但在若干 T2VA 用例上 SSIM 更低。

配置层面的汇总结果反映的是各配置的端到端表现；它既不单独隔离 kernel 耗时，也不提供逐步的成本分解。下文的 trace 是请求级执行轨迹，而非算子计时测量。

### 一次实测的 49 步 trace

工作负载配置为 50 个推理步。由于 sigma 调度同时包含区间两个端点，去噪循环实际执行 49 次模型评估（`len(sigmas) - 1`）；「49 步 trace」指的就是这些模型评估。

为了让执行模式更具体，我们对一个 5 秒 T2VA 请求跑了六种配置：无损、Cache-DiT conservative、SubBlock 0.75、SubBlock 0.75 + conservative Cache-DiT、Cache-DiT stride，以及 SubBlock 0.80 + stride。worker 记录了每个请求实际的 `cached_steps` 列表。由于视频与音频 token 共享同一个打包的 H3 块堆栈，缓存命中时复用的是合并输出；这条路径上不存在「视频走缓存、音频重新计算」的独立状态。SubBlock 行中的蓝色格子标记前十步去噪之后使用稀疏注意力的计算步骤。

## Kernel 层

缓存决定运行多少去噪步骤；kernel 决定每个计算步骤跑多快。MiniMax-H3 将视频和音频 token 打包进同一个序列，因此非 GEMM 路径处处受益于同一条基本原则：更少的内存流量、更少的中间张量、更少的 kernel 启动。AdaLN 调制和门控残差按 token 索引查找参数，并在一遍遍历中完成激活更新。SwiGLU 直接在融合的 `gate_up` 缓冲区上运算。QK RMSNorm 与 3D RoPE 融合为单个 kernel，而不是作为独立的 eager 操作分别执行。

下表使用 5 秒 T2VA 请求（1344×768×124 帧）的实际每 rank 形状：SP/Ulysses-8 填充后为 4,722 行，隐藏维度 5,376，56 个注意力头，头维度 128，RoPE 维度 96，BF16 输入。每个数字是 10 轮、每轮 20 次调用的单次 CUDA 事件时间中位数。基线为对应的 eager 组合实现。

| 算子                                   | Eager 组合实现    | SGLang kernel | 加速比   |
| -------------------------------------- | -----------------:| -------------:| -------:|

## SubBlock 稀疏注意力的工作原理

SubBlock 是一个免训练的块稀疏注意力路由器。它把序列划分为 64 token 的 query 块和 key 块，再把两侧的每个块各拆成四个 16 token 的子块（`n_q=n_k=4`）。通过轻量级的池化和 log-sum-exp 打分，估计每个 key 块在每个 query 块、每个注意力头下的未归一化 softmax 质量。路由器保留得分最高的 key 块，并把它们的索引传给块稀疏注意力 kernel；完整的注意力矩阵从不显式构建。

`sparsity` 值表示允许丢弃的 key 块比例，而不是保留的比例。因此 `sparsity=0.75` 意味着每个 query 块大约保留 25% 的 key 块。更激进的 `0.80` 设置更快，但近似误差预算更大，这与最激进几行观察到的更低 SSIM 一致。

下图曲线展示得分分布；竖线标出两种展示预算下每行路由截断值的中位数。图中把 `sparsity=0.50` 作为诊断参考一并给出；基准配置使用的是 `0.75` 和 `0.80`。由于路由器对每个 query 块、每个注意力头独立地对 key 块排序，`sparsity=0.50` 和 `0.75` 大致保留该行可用 key 块的前一半和前四分之一（受 8 块预算取整约束）。在这些工作负载上，`0.75` 预算保留了行内中位数以上的大部分得分质量，同时把选择集中在高分尾部。

<img src="/images/blog/minimax-h3-h200/subblock-score-distribution.svg" alt="SubBlock 得分分布与截断区间" style="display:block; margin-left:auto; margin-right:auto; width:100%;"></img>
稀疏路径只对 kernel 支持的长序列、非因果 DiT 注意力调用启用：BF16 输入、头维度 128、序列长度至少 4096 token。前十步去噪使用稠密注意力；短片段、token refiner 以及不支持的调用走稠密回退。在 H200/SM90 上，选定的 64×64 路由方案由 SGLang 的 CuTe 块稀疏 FlashAttention kernel 执行。
