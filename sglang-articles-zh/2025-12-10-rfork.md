# 让 Tensor 飞起来——用 R-Fork 加速大模型权重加载

> 原文：[Let Tensors Fly — Accelerating Large Model Weight Loading with R-Fork](https://lmsys.org/blog/2025-12-10-rfork/) · LMSYS Blog · Ant Group DeepXPU Team, SGLang Team

## TL;DR

> 我们提出 **Tensor R-Fork**（Tensor Remote Fork 的缩写），这是一种全新的权重加载方法，利用**高效的节点间设备到设备互连**，以**零拷贝（zero-copy）**方式将 tensor 从一个运行中的 SGLang 实例加载到新实例。

我们的方法具有三大关键优势：

1. 显著加速权重加载性能；
2. 消除本地磁盘和/或 DRAM 上冗余的模型权重存储；
3. 确保推理服务在权重传输过程中不受干扰。

例如，应用于 DeepSeek-R1 模型时，加载时间从数分钟**缩短到仅仅数秒**，本地磁盘和/或 DRAM 的存储占用**减少约 600GB**，且模型传输期间推理服务质量保持不变。

## 背景

随着 LLM 服务规模和模型权重大小的持续增长，SGLang 实例的冷启动时间已成为制约生产效率的关键瓶颈。在冷启动的各个阶段中，权重加载始终是最耗时的任务。

以 DeepSeek-R1 为例，从本地磁盘加载权重通常需要几分钟，而从远程存储系统加载则可能耗时长达数十分钟。随着模型规模持续呈指数级增长，初始化和数据传输所需的时间还会进一步恶化。

如何优化权重加载性能？最直接的方法是最大化权重数据通路中的瓶颈带宽。业界常用的模型加载方式、其数据通路及对应的瓶颈带宽如下：

| 权重加载来源 | 数据通路                                                | 瓶颈 |
|-----------------------|----------------------------------------------------------|------------|
| 远程存储中心 | 远程存储 -> 远程以太网 NIC -> 以太网 -> 本地以太网 NIC -> 本地 DRAM -> 本地 GPU 显存   |            NVMe/以太网 NIC |
| 本地磁盘            | 磁盘 -> DRAM -> GPU 显存            | NVMe             |
| 本地 DRAM            | DRAM -> GPU 显存                    | PCIe             |


我们能否利用带宽更高的数据通路来传输 tensor？答案是**肯定的**——节点间设备到设备互连可提供每秒数百 GB 的吞吐量。然而，关键问题依然存在：如何在 SGLang 中充分利用这一互连的带宽，实现高效的权重加载？

为应对这一挑战，我们开发了**名为 Tensor R-Fork 的新型权重加载框架**（Tensor Remote Fork 的缩写），它将 DeepSeek-R1 模型的加载时间缩短至仅仅数秒，并已达到生产可用状态。

## 设计

<a href=https://github.com/sgl-project/sglang/blob/main/docs/advanced_features/rfork.md>Tensor R-Fork</a>[0] 的核心理念是**借助 GPU-Direct RDMA 构建点对点（P2P）的权重存储架构。**

传统方式的数据传输性能之所以低，是因为整条路径上总存在瓶颈，其带宽远小于节点间设备到设备互连。
从数据通路分析中我们发现，权重 tensor 本就存储在每块 GPU 上，可以经由 GPU-Direct RDMA 在节点之间直接传输。

为了最大化支持 RDMA 的 NIC 的带宽利用率，我们设计了按 GPU 配对的数据传输策略：本地 GPU 与其配对的远程 GPU 直接收发数据。这一设计有效绕过了 GPU 与 CPU 之间的 PCIe 瓶颈，无需依赖 CPU 或主机内存即可实现高吞吐通信。

## 实现

为了让每个运行中的实例都能充当模型权重的来源，供任何需要同一模型的新实例使用——同时将对运行中实例推理服务的干扰降到最低（理想情况下完全消除）——我们为该框架实现了两种后端：NCCL 和 TransferEngine。设 A 为一个运行中的实例（称为源实例），B 为一个待启动的新实例（目标实例）。下面我们将详细讲解这两种后端下权重传输机制的实现。

### NCCL 后端

使用 <a href=https://github.com/sgl-project/sglang/pull/8215>NCCL</a> 作为后端时[1]，流程包含两个阶段：
1. 在源实例与目标实例之间建立通信组。
2. 通过这些通信组把权重从源实例传输到目标实例。

目标实例初始化期间，会向指定的源实例发送 HTTP 请求，以发起通信组的创建。目标实例的每个 TPWorker 与源实例中对应的 TPWorker 建立一个 NCCL 通信组（即源 rank 0 与目标 rank 0 配对，依此类推）。每个通信组恰好包含两个成员：源 TPWorker 与目标 TPWorker。

通信组建立后，每个源 TPWorker 使用 NCCL broadcast，将其位于 GPU 显存上的权重 tensor 通过所在通信组广播出去。目标 TPWorker 将权重直接接收到自己的 GPU 显存中，中间不经过任何内存拷贝。

虽然 NCCL 借助 GPU-Direct RDMA 充当 Tensor R-Fork 的后端，但它有一个关键局限：权重传输会干扰源实例的推理服务，原因有两个关键因素：
1. **通信组建立**：源实例必须主动参与通信组的创建。
2. **CUDA 内核干扰**：NCCL broadcast 机制会触发 CUDA 内核执行，与生成任务争抢 GPU 资源，并造成延迟尖峰。

### TransferEngine 后端

为了实现无干扰的权重传输，我们引入了另一种后端：<a href=https://github.com/sgl-project/sglang/pull/14997>TransferEngine</a>，它利用 GPU-Direct RDMA 实现高效的数据搬运[2]。TransferEngine（TE）是一个轻量的基于 RDMA 的传输运行时，与源实例上的每个 TPWorker 并行运行，在不调用源端 CUDA 内核的前提下，把驻留在 GPU 上的权重 tensor 暴露给远程读取方。

源 SGLang 实例初始化期间：
1. 每个 TPWorker（张量并行 worker）都会启动一个 TransferEngine 实例。
2. TransferEngine 把权重的 GPU 显存地址注册到 RDMA 通道。

目标实例初始化时：
1. 它发送 HTTP 请求，获取源实例 TransferEngine 的元数据，其中包括映射到相应 GPU 显存地址的 RDMA key。
2. 借助这些 RDMA key，目标实例直接从源实例的 GPU 显存加载权重，不会中断源实例正在进行的服务。

*想进一步了解 TransferEngine？非常欢迎阅读附录中的 **TransferEngine** 一节 🚀

### NCCL 与 TransferEngine 对比

|                      | NCCL                           | TransferEngine |
|----------------------|--------------------------------|----------------|
| 部署复杂度| ✅ 无额外依赖。   |❌ 需要额外的 `mooncake` 库。 |
|传输建立开销 | ✅ 建立通信组只需数百毫秒 | ➖ 向 RDMA 通道注册内存区域可能耗时数秒，但可以与其他初始化阶段重叠进行。|
|对 GPU 工作负载无干扰 | ❌ tensor 传输会启动 CUDA 内核。 | ✅ 传输权重不启动任何 CUDA 内核。 | 

## 使用方法

详细用法请参考 <a href=https://github.com/sgl-project/sglang/blob/main/docs/advanced_features/rfork.md>R-Fork 文档</a>

### 使用 NCCL 作为后端

seed 实例：
```shell
python -m sglang.launch_server [args]
```

client 实例：
```shell
python -m sglang.launch_server [args] \
  --load-format remote_instance	\
  --remote-instance-weight-loader-seed-instance-ip [seed_instance_ip] \
  --remote-instance-weight-loader-seed-instance-service-port [seed_instance_service_port] \
  --remote-instance-weight-loader-send-weights-group-ports [send_weights_nccl_group_ports_list]  \
  --remote-instance-weight-loader-backend nccl
```

### 使用 TransferEngine 作为后端

seed 实例：
```shell
python -m sglang.launch_server [args] \
  --remote-instance-weight-loader-start-seed-via-transfer-engine
```

client 实例：
```shell
python -m sglang.launch_server [args] \
  --load-format remote_instance	\
  --remote-instance-weight-loader-seed-instance-ip [seed_instance_ip] \
  --remote-instance-weight-loader-seed-instance-service-port [seed_instance_service_port] \
  --remote-instance-weight-loader-backend transfer_engine
```

## 工业实践

在前面的章节中，我们展示了如何在 SGLang 服务器参数中为 Tensor R-Fork 手动配置 seed 实例。然而，这种手动方式在真实的工业部署中并不现实——识别可用的 seed 实例需要巨大的运维开销。

为应对这一挑战，我们提出 **<a href=https://github.com/sgl-project/sglang/issues/12910>Tensor R-Fork Planner</a>**[4]，一个用于编排源实例元数据的集群调度器。Planner 跟踪以下关键信息：
1. **模型兼容性**：实例当前运行的是哪个模型。
2. **并行配置**：实例采用的并行策略（如张量并行、流水线并行）。
3. **服务健康状态**：实例是否健康、是否适合作为 seed 实例。

每个实例完成初始化后，都会向 Planner 注册自身，提供其模型元数据和并行配置。当新实例启动时，会先查询 Planner，找出与其模型和并行策略都匹配的合格 seed 实例。如果找到兼容的 seed 实例，新实例就直接从该 seed 加载权重；否则回退到默认的加载格式。

## 未来工作

R-Fork 的实践打开了更多想象空间：R-Fork 的核心理念是让所有 SGLang 实例都能充当其他实例的数据存储中心。从权重 tensor 出发，未来我们将通过 Tensor R-Fork 机制管理更多类型的 tensor，让 GPU 集群不仅作为计算中心，也作为存储中心发挥作用。

## 附录

### TransferEngine

TransferEngine[5] 提供的关键优势：
* **多后端支持**：TE 支持多种后端，包括 RDMA（带 GPUDirect）、NVLink、GDS 和 TCP。它能为每个请求智能识别最佳后端，从而获得最高性能。
* **直接 RDMA 读取**：借助已发布的地址和 rkey，目标端执行 RDMA 操作（通常是 RDMA READ），直接读取到自身预先分配的 GPU 缓冲区中，利用 GPU-Direct RDMA，无需任何主机-设备或设备-主机的中间拷贝。
* **无干扰**：TE 执行纯 NIC 驱动的传输，避免在源 GPU 上启动 CUDA 内核。
* **生命周期与清理管理**：TE 维护注册的生命周期，直到 tensor 被逐出或进程退出。
* **并发与流控**：TE 协调并发读取（来自一个或多个目标端），并可施加节流或速率限制，避免打满实例的 NIC 或影响推理延迟。

当前 TransferEngine 实现中的已知局限：
* **内存注册（register_mr）速度慢**：<u>这是 RDMA 驱动导致的</u>。如果你对这一问题有任何见解或解决方案，我们将非常感激并乐于倾听。我们重视多元视角，期待与你共同探索创新方法。
