# 《Python Machine Learning》写作记

> 原文：[Writing ‘Python Machine Learning’](https://sebastianraschka.com/blog/2015/writing-pymle.html)

也该到时候了。我很高兴地宣布，《Python Machine Learning》（《Python 机器学习》）今天终于出版了！当然，我可以给所有对这本书感兴趣的人群发一封邮件了事，或者在 Twitter 上敲下那 140 个字符（还得扣掉插入超链接占用的额度）就算完事。即便如此，写《Python Machine Learning》的这几个月对我而言确实是一段不小的旅程，我想再一次坐进我最喜欢的咖啡馆，就这段经历说上几句。

![《Python Machine Learning》封面](https://sebastianraschka.com/images/blog/2015/writing-pymle/pymle_cover.webp)

ISBN-10: 1783555130  
ISBN-13: 978-1783555130  
平装：454 页，另有电子书  
Packt Publishing Ltd.（2015 年 9 月 24 日）

这段时间以来，有几个人问过我这本书到底讲什么，以及我是怎么挤出*时间*来……（1）写书，（2）读那些我发在 Twitter 上的有趣文章，（3）做研究，（4）放松享受生活，……严格来说，第 1 点我可以一句话概括：我相信所有技术书籍多少都是在*业余时间*写出来的。我寻思着自己可以"只要"减少几个月业余编程项目和博客更新，就能把这事办成。

> 写你所知的东西。这样你就能省下大量空闲时间。  
> — Howard Nemerov

不认同？也许我那套*效率小技巧*能说服你——如果你感兴趣，后面会细说。首先，让我多介绍一下这本书。

## "Python Machine Learning？"——这到底是本什么书？

一切都始于我的一个美好初衷：为有志于机器学习的实践者编一本实用的参考书。好吧，《Python Machine Learning》最后写得相当厚重，但"写"本身其实不是问题。恰恰相反，如果你对一个主题充满热情，可以一直写下去、写下去、再写下去。真正的挑战在于适可而止！

那么，"机器学习和 Python 到底有什么让人着迷的地方，让你决定把几乎全部空闲时间都投入进去？"如果我在我们最爱的社交网站上的那么多帖子都没能说服你，我想我只能借他人之口来说了：

> 我们生活在一場数据洪流之中。据近期估计，每天产生的数据量达 2.5×10^18 字节。数据量如此之大，以至于我们如今存储的信息中有超过 90% 是仅在最近十年间产生的。遗憾的是，这些信息大部分无法被人类直接利用：要么数据超出了标准分析方法的能力范围，要么它太过庞大，我们有限的头脑根本无从理解。  
> 借助机器学习，我们让计算机能够处理大数据、从中学习，并从这堵原本无法穿透的高墙中提取可操作的洞见。从支撑 Google 搜索引擎的大型超级计算机，到我们口袋里的智能手机，我们身边的世界大多依赖机器学习驱动——而我们常常毫无察觉。  
> 作为闯入大数据这个美丽新世界的现代拓荒者，我们理应更多地了解机器学习。什么是机器学习？它是如何工作的？我怎样才能用机器学习窥探未知、为我的业务赋能，或者只是查查整个互联网对我最喜欢的电影怎么看？所有这些以及更多内容，都将在接下来的章节中呈现，作者是我的好友兼同事 Sebastian Raschka。[…]  
> — [Dr. Randal S. Olson](http://www.randalolson.com)（前言节选）

![工程师三段论](https://sebastianraschka.com/images/blog/2015/writing-pymle/engineer_syllogism.webp)（[来源：https://xkcd.com/1570/](https://xkcd.com/1570/)）

诚然，如今机器学习火热的理由有很多，但"为什么是 Python？"我的简短回答是：它是一个直观且高效的开发环境，在许多层面上都很"能干"。说到"高效"，我想我马上又要岔开去聊那场老争论了，希望你不介意我把这个讨论委托给之前那篇文章：[Python、机器学习与语言之战：一个高度主观的观点](https://sebastianraschka.com/blog/2015/why-python.html)。

> 科技其实什么都不是。重要的是你对人有信心，相信他们本质上是善良而聪明的；如果你给他们工具，他们就会用工具做出美妙的事情。  
> — Steve Jobs

### 我们想把这本书带向何方

"这本书和市面上其他讲 Python 与机器学习的书有什么不同吗？"——如今这类书已经不少了。我认为有不同！出版社第一次来找我时，我礼貌地拒绝了，因为当时已经有几本书涉及这些主题。嗯，拒绝之后，我在有机会通读了其中几本之后又重新考虑了这件事。我不想评价其他书孰优孰劣，但我看到的那些，与我心目中一本带 Python 实战示例的机器学习书确实有些出入。

> […] 也就是说，有了机器学习，计算机可以自己给自己编程，这有点像科学方法，只不过是由计算机来执行，而且像是打了兴奋剂，因为它快得多，能处理的数据也多得多。  
> — Pedro Domingos（节选自[对 Pedro Domingos 的访谈](https://web.archive.org/web/20181116003746/http://modernnotion.com/a-master-algorithm-in-machine-learning-could-change-everything/)，谈其新书：A Master Algorithm in Machine Learning Could Change Everything）

市面上有不少专注于机器学习理论的优秀书籍。其中我最喜欢的有 C. Bishop 的 [Pattern Recognition and Machine Learning](http://www.springer.com/us/book/9780387310732) 以及 Duda、Hart 和 Stork 的 [Pattern Classification](https://www.wiley-vch.de/en/areas-interest/engineering/pattern-classification-978-0-471-05669-0)。这些书非常棒，真的非常棒。我认为没有必要再写类似的东西。然而，尽管它们被视为"入门"书，对这个领域的初学者来说却可能相当吃力。虽然我真心推荐所有认真对待机器学习的人都去读它们，但我更倾向于把它们归入"延伸阅读"，而不是作为第一本机器学习书来推荐。无论如何，我认为一边阅读理论、一边动手实现和摆弄机器学习算法，大概是在这个领域获得最佳性价比（=时间）的方式。

另外，还有一些非常实用的书，读起来就像 \* 的文档（\* 这里可以填入 scikit-learn、Vowpal Wabbit、caret 或任何其他机器学习库/API）。我觉得这些也是好书，但我同样认为，关于库的详细讨论应该留给（在线的）库文档本身，只有在那里才能持续保持最新，并作为可靠、可交互的参考。

> 写小说有三条法则。遗憾的是，没人知道它们是什么。  
> — W. Somerset Maugham

我对一本书的期望是三个基本构建块：（1）讲清大局概念，（2）用必要的数学直觉加以补充，（3）提供示例和应用。大局观帮助我们连接各个不同的部分，而数学是理解底层机制所必需的，还能帮我们绕开常见的坑。实际示例无疑有益于学习体验。最后，亲手"弄脏双手"非常重要，也就是说，写出代码把学到的东西付诸实践。我们想理解概念，但最终，我们也想用它们解决现实世界的问题。

![Constraints](https://sebastianraschka.com/images/blog/2015/writing-pymle/constraints.webp)（[来源：https://xkcd.com/1045/](https://xkcd.com/1045/)）

在整本书中，我们会使用 [scikit-learn](http://scikit-learn.org)、[Theano](https://theano.readthedocs.org) 等各种库，它们都是高效且经过充分验证的工具，正是我们在"真实世界"应用中想要使用的。不过，我们也会从零实现若干算法。这有助于我们理解这些算法、了解这些库的工作原理，并练习实现自己的算法——其中一些算法 scikit-learn 至今还没有收录。

### 这本书讲什么，不讲什么

这本书不是一本"数据科学"书。它讲的不是提出假设、收集数据，再从新奇数据集的分析中得出结论；它的重心是机器学习。不过，除了讨论各种学习算法之外，我认为同样重要的是讨论典型的机器学习与建模流程的其他环节，从数据集的预处理开始。我们会讲到诸如处理缺失值、把类别变量转换为适合机器学习的格式、选择有信息量的特征、把数据压缩到低维子空间等主题。还有一整章讨论模型评估，涵盖留出法交叉验证、k 折交叉验证、嵌套交叉验证、超参数调优以及各种性能指标。作为一点补充，我还加了一章，介绍如何把机器学习模型嵌入 Web 应用，与全世界分享。

![Manuals](https://sebastianraschka.com/images/blog/2015/writing-pymle/manuals.webp)（[来源：https://xkcd.com/1343/](https://xkcd.com/1343/)）

这本书也并不是又一本"scikit-learn 是这么用的"的书。我的目标是解释机器学习是如何工作的，把最佳实践和注意事项方面你需要知道的一切都告诉你，然后我们再学习如何用 NumPy、scikit-learn、Theano 等工具把这些概念付诸行动。
当然，这本书也会包含相当数量的"数学与公式"，在我看来，如果想要摆脱"黑盒思维"，这是绕不开的。不过，我希望我做到了让这些内容足够易读，使数学背景不强的人也能读懂。书中许多部分会给出 scikit-learn 示例——在我看来，它是最漂亮、最实用的机器学习库。

下面是各章的快速概览：

- **01** - 机器学习——赋予计算机从数据中学习的能力
- **02** - 为分类任务训练机器学习算法
- **03** - 使用 Scikit-Learn 畅游机器学习分类器
- **04** - 构建良好的训练集——数据预处理
- **05** - 通过降维压缩数据
- **06** - 学习模型评估与超参数优化的最佳实践
- **07** - 组合不同的模型进行集成学习
- **08** - 将机器学习应用于情感分析
- **09** - 将机器学习模型嵌入 Web 应用
- **10** - 用回归分析预测连续目标变量
- **11** - 处理无标签数据——聚类分析
- **12** - 训练人工神经网络进行图像识别
- **13** - 通过 Theano 并行化神经网络训练

### 一个或许有意义、或许没意义的封面

你觉得这个封面怎么样？我记得有位神经科学家问过我，为什么封面上画的是神经元。这是个好问题，也足够引发一场史诗级讨论，足以媲美最激烈的编程语言和文本编辑器大战。
出版社似乎偏爱建筑和自然题材。当他们把最初大约 20 张图库图片摆在我面前时，我能找到的最好的是波兰某个市政厅的玻璃屋顶。照片确实很漂亮，但作为书封面嘛，呃，作为书封面行吗？所以，当我们后来在"初版"定稿上又增加了大约 200 页内容之后，出版社自作主张地给我拿来了一个全新的封面。这一次我没得选，不过嘿，我很喜欢——它比之前那个封面好太多了。

> 有些书，书脊和封面就是它最好的部分。  
> — Charles Dickens（Oliver Twist，《雾都孤儿》）

不管怎样，回想机器学习的起源（我在第二章有简要介绍），我觉得神经元作为封面总体上是相当贴切的。
一切始于 W. S. McCulloch 和 W. Pitts 提出的 McCulloch-Pitt（MCP）神经元，这是关于哺乳动物大脑中的神经元如何工作的第一个模型（*A logical calculus of the ideas immanent in nervous activity*. The bulletin of mathematical biophysics, 5(4):115–133, 1943）。随后出现了最早的机器学习算法之一——感知机（F. Rosenblatt. *The perceptron, a perceiving and recognizing automaton*. Project Para. Cornell Aeronautical Laboratory, 1957）。不久之后，我们又有了基于梯度下降优化的 Adaline（自适应线性神经元）（B. Widrow. Adaptive ”Adaline” neuron using chemical ”memistors”. Number Technical Report 1553-2. Stanford Electron. Labs., Stanford, CA, October 1960）。大约在同一时期，研究者们开始把这些单一学习单元连接成强大的多层网络架构，用非线性代价函数取代线性代价函数。

这就是多层感知机在 20 世纪中叶某个时候诞生的简短故事。  
无论生物大脑与人工神经网络最终有多少共同点，我们至少可以说，前者是后者的火种，也是它的名字由来。
没错，理解并借鉴生物信息处理流程中的概念，至今仍是发明和改进机器学习算法的热门研究方向！

> 我属于这样一个阵营：先把人工神经网络做到真正好用，然后，当你理解了增加某种类脑特性所能带来的计算优势之后，再让它变得更像大脑。  
> — Geoff Hinton（来自他的 [Reddit AMA](https://www.reddit.com/r/MachineLearning/comments/2lmo0l/ama_geoffrey_hinton)）

## 于是，我决定写一本书

没错，事情发生在 2015 年 3 月，我重新考虑了出版社*最初*的邀约，最终决定写这本书。我知道，半年听起来时间很充裕，但是……

### 一天毕竟只有 24 小时

当然，我得先算笔账：我要做和想做的事总是太多，"写一本书"要怎么塞进我一天的（24 小时）里？

![一天 24 小时](https://sebastianraschka.com/images/blog/2015/writing-pymle/24h_day.webp)

没错，饼图被数据可视化专家视为"大忌"，但既然这充其量只是个非常粗略的估计，我觉得用在这里还挺合适。首先，我的一天以 8 小时的工作/研究为中心。此外，我无法想象没有朋友和家人陪伴的生活。当然，睡觉听起来是最无聊的一件事，但它（仍然）相当必要。在机器学习吞噬软件世界的同时，我的早餐、午餐和晚餐时间同样必不可少。为了保持神志清醒，我真的需要每天步行上下班，或者踢踢足球之类的运动，再加上偶尔的咖啡休息时间，让创意源源不断。

> 只有一种震惊比完全出乎意料更糟糕：那就是明明可以预料、却拒绝为之做准备的事。  
> — Mary Renault（The Charioteer）

最后，如果睡前不在一本好书构筑的虚构世界里神游一番，这一天怎么能算结束？这样一来，我每天只剩下大约三个小时的写作时间，有时多一点，有时少一点。哪怕到了万不得已的时候，也千万别打从睡眠里抠出宝贵时间的主意——在这一点上，我时常心怀愧疚。

> 你的时间就是你的生命。如何使用它，你拥有绝对的最终决定权。  
> — Anne Katherine

尽管我对饼图里可能漏掉了什么隐隐感到不安——嘿，拜托，它毕竟只是张饼图，你还能指望什么——但能有机会写下自己最爱的话题，我还是非常兴奋。于是，初步的章节提案在 4 月初就绪。那只是对我想写的 10 章的一个粗略构想，一堆标题加上简短的摘要。接下来，我每章大约有两周时间把它落到纸面上。有挑战的地方在于，按照出版社设想的形式（一套"Essentials"书），这本书本该只有 180 到 230 页。

> "写作瓶颈"是爱抱怨的人发明的漂亮说法，好给自己找个喝酒的借口。  
> — Steve Martin

后来我才发现，我大大低估了写一章需要多少（时间和）篇幅。起初我在大纲提案里写的是每章 20 页，结果后来变成了约 25 页。而这还是大幅精简之后的 25 页！听起来有点矛盾，但真正的挑战恰恰在于：必须仔细斟酌可以删掉哪些章节和段落，同时又不让这本书变成一本引发的问题比解答的还多的参考资料！好消息是，7 月我交完最后一章后，出版社非常喜欢这本书，给了我一些额外的页数；最终成书 454 页。当然，我本可以写、也确实想写多得多的内容，但总得在某处画下界线，对吧！？

> 没有真正的结局。结局只是你让故事停下来的地方。  
> — Frank Herbert

不管怎样，为了凑出初稿，我不得不深挖自己这些年积累下来的那箱效率技巧和习惯。它们肯定不是对每个人都有用，也许对谁都没用，但如果你感兴趣，我可以在后面稍微写一写。

## 我的效率技巧，未必适合所有人

我想说的差不多就是这些，但你还记得前面提到的那些"效率"技巧吗？我每天大约留出三小时写作，周末稍微多一点。就写一本书而言，这其实不算多，而且我有一些老习惯，在这个过程中的作用好坏参半。感兴趣的话请继续往下读。

### 让想法在纸上生长

嗯，想法总在奇怪的时间、奇怪的地点冒出来。最常发生在我步行上下班的路上。

> 每个人脑海里的那本书，总比自己能落到纸面上的更好。  
> — Michael Cunningham

虽然我有车，理论上可以开车上下班，每天省下来回的一个小时，但在一年中较暖和的时节，我真的很享受一段惬意的步行；这也是"读"书的好方式——当然，我指的是听有声书！尽管如此，我后裤兜里总是揣着这个用旧了的笔记本——想法总在奇怪的时间、奇怪的地点冒出来。

![Fieldnotes](https://sebastianraschka.com/images/blog/2015/writing-pymle/fieldnotes.webp)

然而，把这些零散想法记下来并不等于一本书。我不确定这是天赋还是负担，但我的德国基因喜欢深思熟虑的计划过程。下面是一个简短的三阶段清单，我在各种写作中都会（试着）使用。

#### 1. 拟大纲与创作

- 用思维导图梳理想法
- 写出各级标题
- 酌情添加子标题
- 写出段落标题（之后可以删掉）
- 为每个段落添加关键词
- 插入供进一步查阅的参考引用以限定范围
- 制作/插入有助于解释复杂概念的图示

> 你的直觉知道该写什么，所以别挡它的路。  
> — Ray Bradbury

![思维导图](https://sebastianraschka.com/images/blog/2015/writing-pymle/mindmap.webp)

思维导图是经典方法，但真的很管用！当我开始一个新主题时，我只需坐下来几分钟，把脑海中冒出的各种疯狂念头尽可能随性地填进思维导图。写机器学习这类主题是极具挑战的任务，因为所有概念都相互关联、彼此交织。在思维导图中连接它们既直观又轻松，至于把它们排成线性格式（比如写成一章），可以留到以后再操心。

这一步我通常用软件完成，因为对我来说这是个两步流程。第二步包括重新排序、清理修整，以及在各处补充内容。最终，我会得到一张涵盖我想写的主题的主思维导图。接下来，再考虑标题等等。

一图胜千言！这话听起来可能又是一句空洞的套话，但它是我真的信奉的东西。为最复杂的概念制作图示，确实对作者和读者都有帮助！

#### 2. 写作与重写

- （快速）充实各段落；先别管语法
- 重读全文，必要时调整组织结构
- 引言要回答"我为什么要在乎？"这个问题
- 在深入细节之前，先在开头给出阅读路线图
- 重读、重写，再重读、再重写……
- 在文中借助一些事物（比喻）来解释棘手的概念

在草稿的早期阶段就陷入细枝末节没有什么好处。修改语法和拼写、纠结句子结构，很可能是最大的陷阱和时间黑洞。反正之后我们多半会删掉或改掉其中大部分。文风糟糕没什么可难为情的，打个比方，要"关起门来写作"。

#### 3. 复查与定稿

- 删去不适合目标读者的行话
- 确保所有数学符号都有定义
- 确保图中所有重要元素都在正文中有描述
- 如果你使用了别人的算法和模型，确保注明出处
- （去掉口语化表达（don't -> do not））
- 删去冗余/重复/复述
- 优先使用主动语态而非被动语态
- 缩短冗长的句子
- 用行为动词替换部分副词
- 检查逗号使用是否正确
- 检查分号使用是否正确
- 检查圆括号使用是否正确
- 检查连字符 - 的使用是否正确
- 检查破折号 – 的使用是否正确
- 运行你的语法与拼写检查工具
- 检查拼写一致性，例如 "dataset" 与 "data set"
- 交给审阅者之前，完整地通读最后一遍

#### 3A. 图表相关

- 在散点图中使用颜色、深浅或大小，而不是 3D 图
- 图表坐标轴上用"平实的语言"，而不是 "x[1]" 这类变量名
- 确保色盲读者也能看懂图表
- 使用箱线图或条形图时，叠加散点
- 多面板图中所有坐标轴使用相同刻度
- 同一变量在不同图中的配色保持一致

#### 3B. 数据科学相关

- 在分析之前先说明分析目的
- 相关性分析中不应使用"导致"或"引起"

完成最初的"拟大纲"阶段，也就是当我觉得整体结构说得通之后，就该开始润色了。虽然这看起来有点小题大做，但我仍然喜欢用一份清单来确保不遗漏任何事项。

> 这里有一堂创意写作课。第一条规则：不要使用分号。它们是不男不女的异装者，什么也不代表。它们唯一的作用，就是暴露你上过大学。  
> — Kurt Vonnegut（A Man Without a Country）

### 用纯文本 GTD 保持清醒

我可能不时无视某些来自更精细的最佳实践研究的金科玉律，但这就是对我有效的方法。我认为工作流程因人而异、因任务而异，所以我不建议你太当真，但也许你会发现这一节里的一两条技巧对你有用。

> 我生命中最重要的东西都不花一分钱。很明显，我们每个人拥有的最宝贵资源就是时间。  
> — Steve Jobs

核心信息是：把未来从脑子里挪出去，给当下腾出空间。与每隔几年就翻倍的计算机内存不同，我们大脑的短期记忆平均只能同时应付 [4](http://www.ncbi.nlm.nih.gov/pubmed/11515286) 件"事情"（也有人说是 [7](http://www.ncbi.nlm.nih.gov/pubmed/20951219) 件，取决于你问谁）。遗憾的是，我们没法给自己的生物主板加内存条，因此，把宝贵的存储空间留给最重要的事情就格外重要。

我从 [David Allen 的 GTD](https://www.amazon.com/Getting-Things-Done-Stress-Free-Productivity/dp/0142000280) 方法中得到的关键教训是：把事情写下来。这就是为什么我总是随身携带一支小笔和一张纸或纸质笔记本。有时我也直接用智能手机给自己发一封简短的邮件，把想法写在主题栏里——尤其是当这件"事项"真的重要时，因为我的收件箱每天至少查看两次。在电脑前时，我就维护一个 `__inbox__` 目录和一个 `__inbox__.txt` 文件，随时把以后想看的东西丢进去。不言而喻，如果想确保没有任何事情漏掉，每天清空一次或两次这些纸质、邮件和数字收件箱是必须的。这些"收件箱事项"最终会去往以下三个地方之一：我的待办清单、我的 `notes` 目录，或者垃圾桶。

![Is it worth the time](https://sebastianraschka.com/images/blog/2015/writing-pymle/is_it_worth_the_time.webp)（[来源：https://xkcd.com/1205/](https://xkcd.com/1205/)）

说到我的待办清单，我保持得非常朴素简单。只要在你喜欢的搜索引擎里输入"GTD todo"，就会发现大量为此目的开发的工具。嗯，这些年我试过其中好几个，但没有一个让我满意。且不说独立软件和/或按月订阅的价格，它们从来没有真正长久地合过我的意。大多数工具都带有一堆便利的花哨功能，但每个都有自己的怪癖。记住，整理待办事项是一回事，真正把它们做完才是关键！

在项目和任务管理这件事上，我真的不喜欢专有格式。我希望保持灵活，并且相对独立于平台开发者。以 [Evernote](https://evernote.com) 为例，几年前我曾是它的重度用户。尽管它提供了一些还算有用的导出功能，但我可以告诉你，把数据从一个工具迁移到另一个工具是件相当麻烦的事。我一直有种不安的感觉：如果我使用某个专有工具，就必然要为最坏的情况做好准备；这个工具不再被支持的那一天，早晚一定会到来（[第一只死去的独角兽已经出现，只是你还不知道](https://syrah.co/joshdickson40/55e1beac15970d6c01395d9d)）。

顺便说一句：大多数花哨功能反正都是干扰。记住，整理待办是一回事，真正去做才重要！

待办清单最重要的环节就是打钩完成！没错！把任务划掉的感觉实在太满足了，就像在发球台上挥杆击球一样。老式的纸质待办清单干这个再合适不过。我喜欢纸质，但我也喜欢数字化记录和保存。我用一个简单的文本扩展工具，设置了快捷方式（`ddate`），输入后会展开成当前日期（2015-09-24），用来在纯文本待办清单上勾掉已完成的任务。没错，我就是用一个简单的文本文件来保持条理的。它就是好用（至少对我而言）！
配合这个，我还有一个用 Python 写的简单的 150 行小工具作为任务管理器，就叫它 `plaintext-gtd.py` 吧。

一天结束时，我只需在终端里执行 `plaintext-gtd.py`，所有已完成的任务就会被移入 `todolog.txt` 文件留档备查，终端里还会打印出一份当天效率的简要小结供我回顾。如果这些任务属于某个更大的项目，该项目也会被相应勾销，我还能看到一句励志名言作为奖励。由于我把这些都放在 Dropbox 里，所有电脑都能访问，也不必为特定平台的变通方案操心。

![Plain GTD 1](https://sebastianraschka.com/images/blog/2015/writing-pymle/plain-gtd-1.webp)

![Plain GTD 2](https://sebastianraschka.com/images/blog/2015/writing-pymle/plain-gtd-2.webp)

由于我的小工具是针对个人需求定制的，对其他人来说可能不太直观，我推荐去看看 [taskwarrior](https://taskwarrior.org)，它提供了这一思路更成熟的实现。
