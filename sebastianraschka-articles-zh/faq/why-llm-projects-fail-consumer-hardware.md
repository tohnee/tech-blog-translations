# 为什么 LLM 项目会在消费级硬件上失败

大多数在消费级硬件上失败的大语言模型（LLM）项目，都始于工作负载与硬件预算之间的错配。一个检查点可能装得进磁盘，但加载、微调或长上下文推理需要多得多的内存。一次运行也可能装进了内存，却慢得无法实用。

因此，有用的第一个问题比"这台机器能跑 LLM 吗"更具体。我会问：哪个模型、哪个任务、哪种精度、哪个上下文长度，以及目标是推理、微调还是预训练。

## 从工作负载入手

同一个检查点在不同工作负载下的要求差别很大。

| 工作负载 | 权重之外的额外状态 | 常见瓶颈 |
| --- | --- | --- |
| 单请求推理 | KV 缓存和临时缓冲区 | 权重容量或解码带宽 |
| 批量或长上下文推理 | 每条活动序列一个持续增长的 KV 缓存 | 设备内存 |
| LoRA 或 QLoRA 微调 | 激活值加上适配器梯度和优化器状态 | 激活内存 |
| 全量微调 | 完整模型的激活值、梯度和优化器状态 | 内存容量和训练时间 |
| 从零预训练 | 大 token 预算上的完整训练状态 | 计算时间、内存和数据管线 |

一块消费级 GPU 可能跑得动某个模型的量化推理，却无法微调它。LoRA 可以让适配训练变得可行，而全量微调仍远超内存预算。预训练一个教育用途的小模型可能是现实的，而预训练一个有竞争力的通用模型则是完全不同量级的项目。

"消费级硬件"也涵盖多种内存形态。带独立 GPU 的台式机有彼此分离的显存和系统内存。Apple 芯片和集成 GPU 使用共享或统一内存，但操作系统和其他应用会消耗其中一部分。无论哪种情况，标称容量都不会完全提供给模型使用。

## 检查点只是内存预算的一部分

未量化权重的内存下界约为：

`parameter count x bytes per parameter`

一个 70 亿参数的模型在权重以 `bfloat16` 或 `float16` 存储时需要约 14 GB，这还没有计入非参数缓冲区和运行时工作区。名义上的 4 位表示原始下界是 3.5 GB，但缩放系数、零点、打包元数据和未量化的张量都会使实际占用量增加。

检查点大小也可能低估加载峰值。一个朴素的加载器可能先构造一个已初始化的模型，再物化一份单独的状态字典，然后把检查点复制进模型。数据类型转换和设备传输还会产生更多临时副本。进程可能在到达更小的最终占用之前，就耗尽主机内存或显存。

## 训练增加多项大块分配

全量微调需要远多于一次前向传播的资源。每个可训练参数都可能需要一份梯度和优化器状态。Adam 通常维护两个 32 位矩量缓冲区。某些混合精度配置还会保留一份 32 位的主权重副本。

对于一个 7B 模型，仅两个 Adam 缓冲区就占用约 56 GB。模型权重、梯度、可能的主权重、激活值和临时缓冲区还要叠加在其上。因此，一块能服务该模型的 GPU 可能离装下全量微调相去甚远。

LoRA 通过冻结原始权重并优化小型低秩适配器来减少这部分常驻训练状态。普通 LoRA 仍要加载完整的基座模型。QLoRA 还会对冻结的基座做量化，可以减少这部分占用。两种方法都没有移除在网络中传播信息所需的激活值。[全量微调与 LoRA 对比](https://sebastianraschka.com/faq/docs/full-finetuning-vs-lora-cost.html) 更细致地拆分了这些成本。

激活值随模型维度、微批次大小、序列长度和层数增长。调小微批次或上下文通常能解决换优化器解决不了的显存溢出（OOM）错误。梯度累积跨多个微批次抬高有效批大小，但每个微批次自身仍必须装得下。激活检查点（activation checkpointing）通过在反向传播时重算选定操作来节省内存。

## 长上下文和批量可能压垮推理

自回归推理把较早 token 的键张量和值张量存储在 KV 缓存中。其逻辑大小随保留 token 数、产生缓存的层数、KV 头数、每值字节数和活动序列数增长。

这就是为什么一个模型能在 2,000 token 时正常生成，却在接近其标称上下文上限时耗尽内存。加大服务批量会成倍增加缓存，因为每条序列需要自己的状态。某些运行时还会按配置的最大值或内存利用率目标预留缓存内存，因此配置可能在请求尚未达到那个长度之前就影响分配。

[长上下文 KV 缓存 FAQ](https://sebastianraschka.com/faq/docs/kv-cache-long-context-bottleneck.html) 给出了具体计算：对 Qwen3 8B，一条 32,768 token 的序列需要约 4.5 GiB 的 bf16 逻辑缓存；八条这样的序列在计入运行时开销之前就需要约 36 GiB。

训练有类似的序列长度问题。全量自注意力关于序列长度是二次计算量，更长的序列还会为反向传播保留更多激活值。减小微批次可能让训练装得下，但一条长序列在批大小为 1 时仍可能超内存。

## 装进内存不保证有用的速度

把权重卸载到系统内存可以让模型在显存不足时完成加载。代价是反复跨越 CPU-GPU 互连搬运数据，这可能大幅降低生成速度。磁盘卸载则更慢。成功加载只证明了容量，不证明了可接受的延迟。

量化也有类似的边界。更小的权重降低了容量和内存流量压力。实际速度取决于设备和运行时是否为该格式提供优化的内核。当频繁反量化或回退到优化不足的操作时，量化路径可能反而更慢。

对于推理，我会分别记录首 token 时间和每秒生成 token 数。提示预填充并行处理大量位置，而解码则为每个新 token 反复读取权重和缓存状态。对于训练，当序列长度和批大小变化时，每秒 token 数比步时更能说明问题。

一个简单的墙上时间估算可以避免不切实际的运行：

`training time = training tokens / measured tokens per second`

使用在目标机器上一次短程代表性运行得到的吞吐量。笔记本散热、功率限制、后台内存占用、检查点写入和评估都会让长时间任务比理想化内核基准更慢。

## 宣传中的优化未必适用于这台机器

硬件和软件支持必须与确切的模型和配置匹配。`bfloat16` 只有在加速器高效支持它时才有用。FlashAttention 类内核在设备代际、数据类型、注意力布局和软件版本上有限制。量化检查点需要兼容的加载器和内核。一个新架构即使张量装得下，也可能需要更新的模型库。

回退行为值得检查。一个不支持的操作可能被移到 CPU、改用更慢的内核，或在编译阶段失败。`torch.compile` 可以改善稳定的工作负载，但其初始编译、重编译和临时内存本身就是成本。我会确认设备放置并对完整循环做基准测试，而不是假设打开某个开关就走上了预期的路径。

## 一个实用的恢复序列

当项目在本机失败时，我会按以下顺序排查：

1. 指明失败的阶段：加载、预填充、解码、前向传播、反向传播，还是优化器步。
2. 记录确切的模型、数据类型、量化格式、上下文长度、微批次和设备放置。
3. 用一个小的代表性输入测量设备内存峰值、主机内存峰值和吞吐量。
4. 每次只削减一个工作负载维度。从模型大小、上下文长度、微批次大小或并发序列数开始。
5. 使用针对实测分配的内存方法，例如流式加载、激活检查点、LoRA、QLoRA 或更小的 KV 缓存。
6. 逐个测试精度、优化注意力、编译和输入管线。
7. 在启动完整数据集或生成任务之前估算总运行时间。

阶段之所以重要，是因为各阶段的修复不可互换。FlashAttention 无法消除加载期间重复的检查点副本。LoRA 不会缩小推理的 KV 缓存。梯度累积无法让一条超大的训练序列装进内存。卸载可以解决容量问题，却同时制造延迟问题。
