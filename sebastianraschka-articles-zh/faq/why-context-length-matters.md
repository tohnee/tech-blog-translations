# 为什么大语言模型（LLM）的上下文长度很重要

**上下文长度（context length）**之所以重要，是因为它限制了大语言模型（LLM）在一个序列中能使用多少 token。更大的窗口能容纳更多原始材料、对话历史或代码。当这些 token 真的被处理时，成本随之增长，在全量自注意力和推理 KV 缓存中尤其如此。

这个限制以 token 而非词为单位计量。一个 token 可能是一个完整的词、词的一部分、标点或空白符，取决于分词器。因此，两份词数相同的文档可能占用不同量的上下文。

## 一个模型可以有多个上下文长度数字

宣传的上下文窗口只是图景的一部分。

| 量 | 含义 |
| --- | --- |
| 配置最大值 | 模型实现可接受的最大序列 |
| 训练序列长度 | 预训练、继续训练或上下文扩展期间遇到的长度 |
| 实际请求长度 | 一个请求实际处理的 token 数，包括保留在序列中的已生成 token |
| 有效上下文长度 | 模型在特定任务上能够可靠找到并使用信息的范围 |

这些量可能互不相同。改一个配置值或对旋转位置嵌入（RoPE）做重标定，也许能让前向传播在更大的位置索引上运行。但超出模型学过的长度之后，其检索或综合质量可能仍然很差。

一个最大值 128K 的模型在当前请求只有 2K token 时也不会为 128K 付费。实际序列长度决定了请求级的大部分计算和缓存分配。

## 提示与输出共享同一个 token 预算

对于一个 decoder-only 模型，活动序列可以包含多个组成部分：

`system prompt + conversation history + retrieved text + tool results + current request + generated response`

假设一个模型支持 8,192 个 token，应用为回答预留 1,500 个。输入就应保持在 6,692 个 token 及以下。如果输入已经用了 7,500 个 token，模型就无法在同一窗口内再产出 1,500 token 的回答。

有些 API 分别给出输入和输出限制，但仍需检查服务规则。面向用户的 `max_output_tokens` 选项并不意味着输出位于模型的位置约束或缓存约束之外。

当一个请求超出可接受的长度时，系统可能拒绝它、截断较旧的 token、删除检索到的段落，或对较早内容做摘要。静默的左侧截断很危险，因为它可能移除一条系统指令或文档中的第一个定义。截断策略应当显式并经过测试。

上下文也是临时的。当前请求之外的 token 不可用，除非应用把它们存储并重新引入。因此，大的上下文窗口不同于持久记忆。

## 上下文长度改变训练样本

在因果语言模型训练期间，分词后的文档被切分或打包成序列。长度为 \(T\) 的训练序列为窗口内的位置提供下一个 token 目标。模型无法让一个目标直接以被放进另一条独立序列的文本为条件。

![分词后的文本被切分为固定长度的输入和目标窗口，这决定了每个训练目标可用的前文 token](https://sebastianraschka.com/images/LLMs-from-scratch-images/ch02_compressed/13.webp)

更长的训练序列让模型接触到更远距离的关系。这有助于长文档、代码依赖、多轮对话以及必须跨章节整合的信息。但仅仅暴露并不保证模型学会同等好地使用每个位置。数据需要相关的长程结构，位置方法也必须在目标长度上有效。

序列长度还会改变训练系统。对于全量注意力，长度为 \(T\) 的序列在每层包含约 \(T^2\) 个查询-键得分对。长度从 4K 翻倍到 8K 会产生约四倍的得分对。逐 token 的投影和 MLP 层随 \(T\) 大致线性增长，因此完整的训练步并不一定恰好慢四倍。

激活内存同样增长。更长的序列可能需要更小的批次、激活检查点（activation checkpointing）、序列并行或更多加速器。如果批大小降得太多，优化器设置可能需要调整，以保持每次更新预期的 token 数。

FlashAttention 减少内存流量，并避免在高带宽内存中存储完整的注意力得分矩阵。它计算的是精确的全量注意力，因此它改进的是实现，而不会把底层的 \(T^2\) 得分计算变成线性的。

## 推理有预填充和解码两项成本

推理从**预填充（prefill）**开始，模型在这一阶段处理提示。提示的各个位置可以在一个 transformer 层内并行运行，而全量注意力的得分计算量随提示长度二次增长。

随后自回归解码一次生成一个新 token。KV 缓存存储来自提示和已生成 token 的键和值，避免每一步都完整重算前缀。

![解码期间，当前查询关注来自较早 token 的键和值，它们保留在 KV 缓存中](https://sebastianraschka.com/images/LLMs-from-scratch-images/bonus/kv-cache/kv-cache-attn-1.png)

对于批大小 \(B\)、产生缓存的层数 \(L\)、保留长度 \(T\)、键值头数 \(H\_{KV}\)、头维度 \(d\_h\) 和每元素 \(b\) 字节，逻辑缓存大小为

\[2BLTH\_{KV}d\_hb.\]

缓存随保留长度和批大小线性增长。每条活动序列需要自己的缓存，而加载的模型权重可以在请求间共享。因此长提示会减少能装进加速器内存的并发序列数。

解码延迟也随上下文变化。全量注意力层中每个新查询必须与保留前缀交互。KV 缓存免去了重复的键值投影，但读取长历史并不是免费的。生成的 token 延长了这一历史，使后续解码步略微更昂贵。

## 最大长度不保证有用长度

一个模型可以接受长序列却仍无法好好利用它。若干能力需要分别评估：

- 在不同位置检索单个确切事实
- 融合相距很远章节的证据
- 在许多后续 token 之后遵循早先的指令
- 解决相互冲突或重复的段落
- 在窗口末端保持生成质量

一个简单的隐藏事实测试度量的是检索。它对总结长报告或跨多份文档推理说明不了多少。位置也很重要。一个模型可能在开头或结尾附近可靠地检索信息，而当相关段落出现在中间时表现更差。

更多上下文也可能引入无关或冲突的证据。把所有检索到的段落都塞进提示可能降低回答质量并推高成本。检索、重排和结构化摘要往往能让实际上下文更短。这些组件需要各自的评估，因为检索器或摘要器可能丢弃重要内容。

## 架构决定成本如何随规模变化

长上下文方法削减的是成本中不同的项。

- **分组查询注意力（GQA）**：每个 token 存储更少的键头和值头，缩减 KV 缓存大小和带宽。
- **滑动窗口注意力（SWA）**：限制局部层可用的位置，减少得分计算量，并允许逐出旧的缓存条目。
- **KV 缓存量化**：降低每个键值元素存储的字节数。
- **潜在或跨层共享方法**：压缩缓存表示或在层间复用。

![随着上下文长度增长，分组查询注意力和滑动窗口注意力从不同维度减缓 KV 缓存增长](https://sebastianraschka.com/images/LLMs-from-scratch-images/bonus/swa-memory/4.webp)

这些方法有不同的信息通路。GQA 在每个注意力层保留全上下文访问。SWA 在局部层中移除了对足够旧的 token 的直接访问，不过周期性的全局层可以恢复全序列查找。[GQA 与 SWA 对比](https://sebastianraschka.com/faq/docs/when-gqa-and-swa.html)详细分析了这个设计选择。

位置编码是上下文支持的另一部分。学到的绝对嵌入有一张固定表，而 RoPE 可以为新索引计算旋转。两种方法都不保证在缺乏适当训练或缩放的情况下能有好的长度外推。[RoPE FAQ](https://sebastianraschka.com/faq/docs/rope-vs-absolute-positional-embeddings.html) 解释了这一区别。

## 选择能保留任务证据的最小上下文

对于一个要部署的系统，我会从提示长度分布而非宣传的最大值入手。为预期回复预留足够的 token，然后在多个输入长度下测量任务质量、首 token 延迟、每 token 解码延迟、缓存内存和并发批大小。

当重要关系会因过滤而丢失时（例如散布在合同各处的定义、或跨代码库的依赖），使用更长的实际上下文。当源材料的一小部分就包含证据时，使用检索或摘要。[短上下文与长上下文对比](https://sebastianraschka.com/faq/docs/short-context-vs-long-context-llms.html) 更详细地讨论了这些工作负载的权衡。
