# GQA 与滑动窗口注意力（SWA）的选择

当模型在其目标上下文上负担得起全量注意力，且主要瓶颈是 KV 缓存的容量或带宽时，单独使用**分组查询注意力（GQA）**即可。当保留的 token 位置数量仍让全量注意力过于昂贵时，再加入**滑动窗口注意力（SWA）**。

这两种机制削减的是注意力成本的不同维度。GQA 在每个保留位置上存储更少的键头和值头。SWA 允许局部层丢弃比其窗口更早的位置。它们可以独立使用，也可以一起使用。

## GQA 保留全上下文访问

标准多头注意力（MHA）使用相同数量的查询头和键值头。GQA 保留大量查询头，并在它们之间共享一组更少的键头和值头。一个有 32 个查询头和 8 个 KV 头的层，会为每个键值对分配 4 个查询头。

对于一层和单个保留 token，逻辑缓存大小为

`2 x KV heads x head dimension x bytes per element`

因子 2 对应键张量和值张量。把 KV 头数从 32 减到 8，就把这部分缓存缩减到四分之一。同样的缩减比例适用于任何上下文长度。

![分组查询注意力通过为每个保留 token 存储更少的键头和值头来减缓 KV 缓存增长](https://sebastianraschka.com/images/LLMs-from-scratch-images/bonus/gqa-memory/3.webp)

每个查询头仍可以注意到每个保留 token。因此 GQA 在每个注意力层中保留了直接的全局查找。这对于可能需要从提示的任意位置提取确切细节的工作负载很有用，比如比较一份文档中相距很远的章节，或在整个代码仓库中追踪一个符号。

GQA 并没有消除全量注意力对序列长度的依赖。在预填充（prefill）阶段，模型仍要在完整上下文上计算查询-键交互。在解码阶段，每个查询仍要关注整个保留前缀。更小的缓存减少了内存流量，但可访问的 token 位置数量仍在持续增长。

[GQA FAQ](https://sebastianraschka.com/faq/docs/grouped-query-attention.html) 更详细地解释了头共享和缓存计算。

## SWA 还限制了保留的 token 位置

在因果滑动窗口注意力中，一个查询只能访问最近的 (W) 个位置。一旦序列长度 (T) 超过 (W)，一个高效实现的局部层在预填充阶段只需计算约 (TW) 个注意力得分，而不是 (T^2)。在解码阶段，该层可以逐出比窗口更早的键和值。

例如，4,096 个位置的局部窗口把该层的缓存限制在 4,096 个 token，即使模型处理的是 32,768 个 token 的序列。这在该序列末尾把保留 token 项缩减为八分之一。

![滑动窗口注意力限界了局部层保留的上下文，因此其缓存优势在序列超过窗口之后才开始增长](https://sebastianraschka.com/images/LLMs-from-scratch-images/bonus/swa-memory/4.webp)

这种节省需要恰当的实现。一个带局部掩码的稠密 (T \times T) 注意力矩阵能得到正确的值，却保留了全量注意力的大部分计算量。一个只掩蔽旧 token 而不逐出其 KV 条目的运行时，也得不到缓存容量上的好处。检查点、局部注意力内核和缓存管理器都需要支持同一种窗口模式。

SWA 改变了模型的信息通路。一个局部层无法把当前查询与窗口之外的 token 直接比较。信息可以穿过连续的局部层逐层传播，但这不同于对完整前缀的直接内容查找。正因如此，许多架构会保留周期性的全局注意力层。

## 缓存公式给出实用的决策规则

对于一个所有注意力层具有相同 KV 维度的模型，逻辑缓存大小约为

`2 x batch size x layers x retained tokens x KV heads x head dimension x bytes per element`

GQA 减少的是 `KV heads`。SWA 减少的是局部层中的 `retained tokens`。一个有 (L\_g) 个全局层、(L\_l) 个局部层、完整上下文 (T)、局部窗口 (W) 的混合模型，其逻辑缓存大小为：

`2 x batch size x KV heads x head dimension x bytes per element x (L_g x T + L_l x min(T, W))`

这个公式让选择更容易评估。

- **只用 GQA 就够**，前提是得到的全上下文缓存能装进内存预算、解码带宽可以接受、全量注意力预填充满足延迟目标。
- **加入 SWA**，如果长序列仍超出缓存预算、过度压低服务批大小，或让预填充与解码的注意力过于昂贵。
- **保留更多全局层**，如果评估表明在以局部为主的排布下精确长程检索出现退化。
- **采用更局部的排布**，如果工作负载以邻近上下文为主，而额外的全局层几乎测不出收益。

阈值取决于完整的工作负载。上下文长度、并发序列数、输出长度、精度、硬件内存和延迟目标都有贡献。模型标称的 128K 上下文并不意味着在目标批大小下 128K 是经济的。

## 各选项如何比较

| 设计 | 每 token 的 KV 头数 | 每层保留的位置 | 单层的直接可达范围 | 主要优势 |
| --- | --- | --- | --- | --- |
| 全量 MHA | 与查询头相同 | 完整上下文 | 完整上下文 | 最大的每头 KV 容量 |
| 全量 GQA | 少于查询头 | 完整上下文 | 完整上下文 | 缓存更小且保留全局访问 |
| 带 SWA 的 MHA | 与查询头相同 | 局部层为局部窗口 | 局部窗口 | 更少的 token 位置和注意力得分 |
| 带 SWA 的 GQA | 少于查询头 | 局部层为局部窗口 | 局部窗口 | 同时缩减两个缓存维度 |

这个比较也说明了为什么 GQA 和 SWA 不是相互竞争的替代品。可以通过 KV 头共享把缓存缩减为四分之一，再在一个上下文比窗口长八倍的局部层里进一步缩减为八分之一。相对于该上下文下的全量 MHA，局部层的逻辑缓存此时小了 32 倍。

## 什么时候质量权衡值得在意

GQA 通常是一个更温和的架构改动，因为每个查询都保留了对完整上下文的访问。原始 [GQA 论文](https://arxiv.org/abs/2305.13245)发现，在其评估设置中，中间程度的 KV 共享可以逼近多头注意力的质量，同时保留多查询注意力的大部分推理收益。

SWA 引入了局部性偏置。这对自然语言和代码可能是很好的匹配，因为许多有用的依赖就在近处。但对于需要频繁、精确地从任意较早位置检索的任务，它可能并不合适。因此，长上下文评估应包括检索距离、多文档比较以及实际的局部-全局层排布，而不是只报告平均困惑度。

Gemma 3 提供了一个具体的混合示例。它使用 GQA，并且每五个局部层之后放置一个全局注意力层，局部窗口为 1,024 个 token。[Gemma 3 报告](https://arxiv.org/abs/2503.19786)在其报告的消融实验中发现，这种更激进的局部排布几乎没有带来困惑度变化。该结果适用于被测试的模型和设置；它并不保证在每个长程检索任务上都有同等表现。

## 这个选择属于模型架构层面

对于一个已有的检查点，GQA 和 SWA 一般不是可以随时切换的服务开关。投影矩阵的形状决定了 KV 头数，而训练时使用的注意力模式决定了模型如何学会在位置之间传递信息。把 MHA 转换为 GQA 通常需要额外训练，而对一个按全量注意力训练的模型强加局部窗口会改变其输出。

如果让我选择一个检查点，我会先在目标上下文和精度下计算其每序列缓存。然后我会基准测试预填充延迟、解码吞吐量和并发批大小。如果 GQA 能满足这些系统目标，全量注意力保留了更简单的信息通路。如果不能满足，GQA 加 SWA 的检查点是合理的下一步，随后应做窗口内外的检索测试。
