# SFT 期间何时掩蔽提示 token

当训练目标是最大化**在给定提示条件下助手回复**的似然时，应把提示 token 从损失中掩蔽掉。这是在提示-回复样本上做有监督指令微调（SFT）的常见选择。

当模型同样需要生成序列的那一部分时，应保留提示 token 的损失，例如普通语言模型预训练、对话记录补全，或一个辅助性的全序列目标。

"掩蔽"一词在这里需要小心理解。**损失掩码（loss mask）**是把选定的目标位置排除在交叉熵之外。它不会把提示从模型输入中移除，也不会阻止回复 token 关注提示。

## 仅回复损失在计算什么

假设一条训练记录被序列化为

`[system and user prompt] [assistant header] [response] [end token]`

对于仅回复的 SFT，标签序列具有如下的概念形式：

`[-100 ... -100] [-100] [response token IDs] [end-token ID]`

在 PyTorch 中，`CrossEntropyLoss` 默认使用 `ignore_index=-100`。带此标签的位置既不计入求和损失，也不计入均值归约所用的 token 数。实际的 `input_ids` 仍然包含系统消息、用户消息、角色标记和助手回复。

![提示 token 保留在输入中，但其目标标签被替换为忽略索引，于是只有回复 token 直接贡献损失](https://sebastianraschka.com/images/LLMs-from-scratch-images/ch07_compressed/mask-instructions.webp)

如果 `R` 是回复 token 位置的集合，目标函数为

\[\mathcal{L}\_{\text{response}}
= -\frac{1}{|R|}\sum\_{t \in R} \log p\_\theta(x\_t \mid x\_{<t}).\]

模型仍会处理提示以预测每个回复 token。回复损失的梯度经由回复 token 的计算流入提示 token 的隐藏状态以及产生这些状态的参数。因此，掩蔽移除的是提示区域中的**直接下一个 token 目标**，它并不阻止模型学习提示如何影响答案。

它也不会节省这些 token 的前向传播计算或激活内存。完整提示仍作为条件上下文被需要。

## 为什么提示掩蔽通常有用

指令样本通常包含很长的请求和短得多的回答。如果一条记录有 1,000 个提示 token 和 50 个回复 token，全序列损失会把大约 95% 的 token 级项分给提示。模型于是主要被优化来复现用户提供的上下文和模板套话。

仅回复损失让指标和梯度加权更贴合预期的条件任务。它在以下情形尤其有用：

- 系统与用户文本由应用在推理时提供
- 助手回复才是被评估的行为
- 提示长度在各样本间差异很大
- 固定的角色标记或模板文本原本会主导短回答
- 训练数据把多条提示-回复样本打包进同一序列

掩蔽还能让每 token 损失更易解读。报告值于是概括的是回答 token 的预测，而不是简单模板 token、随意用户措辞和回答 token 的混合。

## 什么时候全序列损失也合理

提示掩蔽是一种目标选择，而非普适要求。当每个片段都属于模型应当生成的分布时，全序列损失是合适的。

例子包括在普通文档上继续预训练、训练可生成对话任一侧的对话模型、以及没有固定用户-助手角色的对话记录补全。一个项目也可以把仅回复目标与一个较小的全序列语言建模项混合，以保留更宽泛的续写行为。

对于小而格式统一的数据集，不掩蔽提示可以作为实用的基线。它利用了每一个可用的下一个 token 目标。不过，表面上的损失可能由重复的模板文本驱动。我会比较保留集上的回复质量，而不是只凭训练损失来选择目标。

加权损失是另一种选择。提示位置可以获得较小的非零权重，而助手位置获得全权重。标准的 `ignore_index` 实现的是二元决策，因此 token 级加权需要先做未归约的交叉熵，再做一个显式的加权归约。

## 多轮对话需要感知片段的掩码

对于单轮记录，把助手回复之前的所有内容掩蔽掉很简单。多轮聊天数据则有多个用户和助手片段：

`system, user 1, assistant 1, user 2, assistant 2`

正确的掩码取决于训练样本本身。

- 如果两条助手消息都是模型应学会生成的示范，则在 `assistant 1` 和 `assistant 2` 上计入损失，同时掩蔽系统和用户片段。
- 如果较早的轮次只作为最终回答的上下文提供，则掩蔽所有较早的片段，只在 `assistant 2` 上计入损失。
- 如果模型应生成工具调用，则包含助手的工具调用 token。由环境提供的工具结果通常仍是上下文，应被掩蔽。

不要通过对 `assistant` 之类字符串做朴素文本搜索来定位这些区域。同一个词可能出现在消息内部，而角色标记也可能被分词成多个 ID。优先使用来自聊天模板渲染器的片段信息，或预处理阶段产生的 token 偏移。有些模板为此暴露了显式的生成片段。

回复结束 token 通常保持不被掩蔽。它教会模型何时停止。当应用在生成前插入助手角色头时，角色头通常被掩蔽。只有当模型需要自行发出这些头时才包含它们。

## 填充与打包需要单独检查

填充标签应当始终被排除在语言模型损失之外。这与提示掩蔽无关。因此，一个批次中可能同时存在标签为 `-100` 的提示位置和填充位置。

![忽略索引把重复的填充位置排除在交叉熵之外；同一标签机制也可以排除提示片段](https://sebastianraschka.com/images/LLMs-from-scratch-images/ch07_compressed/ignore-index.webp)

对于打包的训练样本，要用与 `input_ids` 相同的边界拼接损失掩码。在加入分隔符、结束 token 或填充后，每个回复片段必须保持对齐。如果实现使用块对角注意力来隔离打包的记录，注意力边界和损失边界应当一起测试。

标签移位是差一错误（off-by-one）的另一个来源。许多因果语言模型实现接受与 `input_ids` 对齐的 `labels`，并在内部移位 logit 和标签。在这种设置下，存储在第一个回复 token 位置的标签必须是第一个回复 token，而其前的提示位置使用 `-100`。再额外做一次手动移位可能丢掉第一个回复目标，或给错误的边界 token 计分。

## 一次小规模批次检查能抓住大多数 bug

在长时间 SFT 运行之前，我会解码一个批次并打印四行对齐的内容：

1. token 位置
2. 输入 token ID 或 token 字符串
3. 目标标签
4. 指示该位置是否计入损失的布尔值

检查第一个回复 token、最后一个回复 token 和结束 token 是否被包含。验证系统、用户、填充以及任何环境提供的工具结果片段在所选目标下被排除。还要确认每个批次至少包含一个有效目标，因为一个所有标签都为 `-100` 的样本在某些实现中会产生未定义的均值损失。

随后我会以未被掩蔽的 token 数为分母来报告回复 token 损失。跨掩蔽方案比较这个值仍不完美，因为被评估的 token 集合不同。在保留指令集上生成的回复才能提供更有用的比较。
