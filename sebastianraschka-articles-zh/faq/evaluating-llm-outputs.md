# 评估 LLM 输出与开放式回答

> 原文：[Evaluating LLM Outputs and Open-Ended Answers](https://sebastianraschka.com/faq/docs/evaluating-llm-outputs.html) · Sebastian Raschka's FAQ

LLM 的输出之所以难以评估，是因为一个开放式提示可以有许多可接受的答案。两个回答可能措辞不同却同样正确；第三个回答可能听起来很流畅，却包含一个不易察觉的事实性错误。

我会先问：这项评估需要检测的是哪类失败？如果输出具有可验证的结果，直接检查通常更为可取。例子包括：针对简短事实性答案的精确匹配（exact match）、针对生成代码的单元测试、针对 JSON 的 schema 校验，或者应用程序中的任务是否成功。这些检查可复现且成本低廉。

受约束的基准测试采用同样的思路。多项选择和简答题数据集可以大规模地衡量某种明确界定的能力。它们的分数易于比较，不过只能覆盖其题目所代表的行为。公开基准测试还可能存在训练数据污染的问题，或者随着模型不断针对它们调优而变得信息量下降。

参考答案重叠度（reference-overlap）指标是另一种自动化选项。当与参考答案的措辞匹配程度很重要时，它们效果最好。但对于一段解释或摘要，重叠度低的回答可能依然很好，而重叠度高的回答可能只是照抄了参考答案，却没有满足用户的实际请求。

当正确性或质量需要人工解读时，人工评估就很有用。评审者可以依据评分细则（rubric）打分、对单个回答评分，或者并排比较两个模型。成对比较往往比给出绝对分数更容易。但人工评审也有成本：评分者之间可能意见不一致，领域专家昂贵，而大规模的评估集合也很耗时。

**LLM 评审（LLM-as-a-judge）** 方式则用另一个语言模型来套用类似的评分细则。评审模型接收提示、候选输出，有时还有参考答案，然后返回一个分数或偏好判断。本书配套仓库的第 7 章演示了这一工作流，既用了通过 Ollama 提供服务的本地模型，也用了 OpenAI API 模型。

![仓库中的本地评估工作流通过 Ollama 使用一个外部 LLM 作为评审](https://sebastianraschka.com/images/LLMs-from-scratch-images/bonus/ollama-eval/ollama-serve.webp)

基于模型的评审便于对数千条输出反复运行同一套评估。但它的分数仍然是模型预测。评审模型可能偏爱某种特定的写作风格、更长的回答，或者与自己输出相似的答案；它也可能恰好漏掉与被评估模型相同的领域错误。

因此，我会先让评审模型在一个较小的人工评审集合上测试，评审者需是理解该任务的人。在比较不同系统之前，提示和评分细则应当固定下来。对于成对评审，交换两个回答的顺序是检验位置偏差的有效手段。隐藏模型名称也能避免一个不必要的偏差来源。

应用层面的评估可以补充离线基准测试捕捉不到的信号。一个检索助手可以用引用正确性以及被引用段落是否支持答案来衡量；一个编程助手可以通过测试通过率、编辑采纳率和节省的时间来评判。延迟和服务成本应与回答质量分开跟踪，因为一个更慢的模型可能只是靠大得多的推理预算换来了更好的质量分数。

因此，一套有用的评估组合应当包含多项测量。直接的任务检查覆盖可以自动验证的部分；人工评审建立一个可信的质量样本；LLM 评审在与该可信样本的一致性经过度量之后，可以把评分细则推广到更大的集合上。
