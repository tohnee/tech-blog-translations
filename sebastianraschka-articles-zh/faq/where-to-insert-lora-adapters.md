# LoRA 适配器应该插入在哪里

对于一个 decoder-only 的大语言模型（LLM），我会采用以下两个起点之一。当适配器预算紧张时，目标是**每个 transformer 块中的查询投影和值投影**。当目标是最强的通用 LoRA 基线、且更大的适配器在训练预算之内时，目标是**注意力块和 MLP 块中的所有线性层**。

并不存在一个总是影响最大的模块。插入位置控制的是 LoRA 能修改哪些预训练变换，而秩（rank）控制的是每次更新的容量。因此，有用的比较取决于任务、架构以及可训练参数的总预算。

## 把 LoRA 插入一个层意味着什么

对于一个冻结的线性权重矩阵 \(W \in \mathbb{R}^{d\_{out} \times d\_{in}}\)，LoRA 通过两个更小的矩阵学习一个低秩更新。该层计算

\[y = Wx + sBAx,\]

其中 \(A \in \mathbb{R}^{r \times d\_{in}}\)，\(B \in \mathbb{R}^{d\_{out} \times r}\)，\(r\) 是秩，\(s\) 是实现中的缩放因子。向该层添加 LoRA 会引入

\[r(d\_{in} + d\_{out})\]

个可训练参数。原始矩阵保持冻结。

![一个 LoRA 包装器在一条冻结的线性变换旁边添加了一条可训练的低秩通路](https://sebastianraschka.com/images/LLMs-from-scratch-images/appendix-e_compressed/lora-3.webp)

这个公式对插入位置很重要。MLP 投影往往比注意力投影更宽，因此在相同秩下适配它会增加更多参数。在分组查询注意力（GQA）模型中，键投影和值投影可能比查询投影更窄。一份包含七个目标模块名的列表并不意味着七个模块贡献相同的适配器大小。

## 常见的目标模块组

Llama 风格的实现让这些选择容易命名，不过其他代码库可能会融合或重命名同样的投影。

| 目标组 | 常见模块名 | 适配器可以改变什么 | 实际角色 |
| --- | --- | --- | --- |
| 查询和值 | `q_proj`, `v_proj` | 注意力查找和注意力返回的内容 | 小型历史基线 |
| 全部注意力 | `q_proj`, `k_proj`, `v_proj`, `o_proj` | 注意力得分、值和输出混合 | 更宽的注意力适配 |
| transformer 块全部线性层 | 所有注意力投影加上 `gate_proj`, `up_proj`, `down_proj` | 注意力行为和 MLP 特征变换 | 强力通用基线 |
| 嵌入或语言模型头 | `embed_tokens`, `lm_head` | 输入 token 表示或输出 logit | 专门的词表或输出适配 |

MLP 层占据 transformer 参数和计算量的很大份额。把它们排除在外会把每一次学习到的更新都限制在注意力通路上。当预训练模型已经具备所需特征、任务主要需要小幅行为调整时，这可能已经足够。较大的领域偏移则可能受益于同时适配 MLP 变换。

![LoRA 可以包装重复的注意力和前馈块中的线性变换，而模型其余部分保持冻结](https://sebastianraschka.com/images/LLMs-from-scratch-images/appendix-e_compressed/lora-4.webp)

## 原始 LoRA 与 QLoRA 研究发现了什么

2021 年的 [LoRA 论文](https://arxiv.org/abs/2106.09685)将其主要的 transformer 研究限制在注意力矩阵上。在 GPT-3 175B 固定 1,800 万参数的预算下，同时适配查询投影和值投影在 WikiSQL 和 MultiNLI 上的整体表现优于把全部预算投入查询或键投影。该比较在适配更多投影类型时降低了秩，因此它度量的是固定预算下的插入位置。

这一结果正是常见的 `q_proj` 和 `v_proj` 默认设置的来源。对于一个高效基线来说，这是有用的证据。该论文在那项实验中没有测试 MLP LoRA，而且其两个数据集并不能确立查询和值对每个现代指令微调任务都是最优的。

2023 年的 [QLoRA 论文](https://arxiv.org/abs/2305.14314)报告了在 Alpaca 上对 Llama 7B 的另一项消融。在该设置中，要把 LoRA 应用到 transformer 块的所有线性层才能追上全量微调的结果。该论文在其主要实验中使用了这种全线性配置。

这些发现回答的是不同的问题。查询加值是一个合理的低参数起点。全线性插入让适配器能触及模型更多部分，是当前 decoder-only LLM 微调中更面向质量的基线。

## 把选定的模块应用到整个堆栈

对于第一次实验，我会把选定的模块类型应用到**每一个 transformer 块**。只适配最后几个块可以省参数，但也会阻止 LoRA 改变较早层的表示。并不存在"顶层包含了所有任务相关变化"的一般规律。

原始 LoRA 研究还发现，在固定预算下，把较低秩的适配器分布到查询投影和值投影上，优于只对一种投影类型使用更高的秩。这提示了一个有用的操作顺序：先扩展模块覆盖面，再对一小撮模块赋予很高的秩。

深度仍然可以作为一个消融变量。如果全堆栈适配器超出预算，可以比较均匀层采样、堆栈上半部分、以及每个块都用更小的秩。若目的是隔离插入位置而非容量，就要保持可训练参数数量相近。

## 嵌入和输出头是特殊情况

在普通指令微调中，token 嵌入和语言模型头通常保持冻结。预训练的词表映射已经可用，而且这些矩阵可能很大，因为其中一个维度等于词表大小。

当适配引入新 token、强烈转向一种代表性不足的语言、或需要一个专门的输出空间时，它们才变得更相关。这里需要注意权重绑定（weight tying）。有些模型的输入嵌入和输出头使用相同的权重，另一些则保持独立。如果实现没有显式处理，只在一侧应用或合并适配器可能破坏预期的绑定行为。

对于分类任务，新初始化的分类头通常直接训练，而不是用 LoRA 来近似。LoRA 仍可以适配其下的 transformer 块。

归一化的缩放系数和偏置不是同样形式的矩阵乘法。它们可以作为一小组辅助参数被解冻，但它们不属于通常的 LoRA 目标模块选择。

## 模型架构会改变答案

不要在没有检查模块树的情况下从另一个模型复制目标名称。GPT 风格的实现可能使用 `c_attn` 这类融合名称，另一些模型把查询、键、值投影合并成一个矩阵。专家混合（MoE）模型可能暴露大量专家 MLP，使全线性适配器比预期大得多。多模态系统还会加入具有自身插入选择的投影器和编码器。

训练之前，我会打印每个匹配到的模块，并按注意力、MLP、嵌入和输出头对新增参数分组。然后验证只有预期的 LoRA 矩阵和显式选择的辅助参数具有 `requires_grad=True`。这能抓住子串匹配悄悄适配到错误层或漏掉融合投影的情况。

## 一个实用的消融顺序

对于一个指令微调项目，我会在同一数据划分上比较以下配置：

1. 每个 transformer 块中的查询投影和值投影
2. 全部四个注意力投影
3. 所有注意力和 MLP 线性投影

有两种运行这一比较的有用方式。保持相同秩可以看出额外的适配器容量在实践中能买到什么。调整秩使每个配置的参数量相近则能更干净地隔离插入位置。请同时报告秩和总可训练参数，因为仅凭秩并不能描述适配器预算。

如果全线性运行在保留任务指标上的提升足以证明其更大的优化器状态和检查点是合理的，就保留它。如果查询加值的表现相近，更小的适配器更易训练、存储和服务。当每一个调优良好的 LoRA 插入位置都到达相同的性能上限时，下一个实验可能需要更高的秩、更好的数据，或者[全量微调](https://sebastianraschka.com/faq/docs/lora-vs-full-finetuning.html)，而不是再换一组模块名组合。

[LoRA 秩与 alpha FAQ](https://sebastianraschka.com/faq/docs/lora-rank-alpha.html) 介绍了适配器容量和缩放惯例。[全量微调成本 FAQ](https://sebastianraschka.com/faq/docs/full-finetuning-vs-lora-cost.html) 解释了 LoRA 消除了哪些内存项、保留了哪些。
