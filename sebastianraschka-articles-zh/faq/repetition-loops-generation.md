# 为什么 LLM 会陷入重复循环

LLM 会陷入重复循环，是因为每一个已生成的 token 都会成为下一次预测的上下文的一部分。一旦某个短语被重复了一次，新的上下文可能会给「再来一份拷贝」分配更高的概率。而贪心解码或高度受限的解码就会不断选中同一个局部续写。

假设模型生成了两次 "The main reason is"。它的下一个 token 分布现在所依赖的前缀中已经包含了这种重复结构。如果概率最高的续写再次补全这个短语，序列就进入了一个自我强化的区域。解码循环每次只选择一个 token，并不会执行显式的段落级重复检查。

![自回归生成会把每个选中的 token 都回馈到上下文中，使重复的模式不断强化自身的续写。](https://sebastianraschka.com/images/LLMs-from-scratch-images/ch05_compressed/gpt-process.webp)

重复有几种可能的来源，它们需要不同的修复方法。

**解码方式可能暴露出一个过度集中的分布。** 贪心解码总是选择最大的 logit。非常低的温度会让分布更尖锐，而较小的 top-k 或过紧的 top-p 截断会排除其他备选。这些设置可能让本已存在的重复模式变成确定性的。

增加随机性并不是万能药。适中的温度或更宽的候选集也许能让生成走出循环。但过度的随机性可能把文本带进一个低概率的上下文，造成另一种退化。[温度、top-k 与 top-p FAQ](https://sebastianraschka.com/faq/docs/temperature-topk-topp-sampling.html) 解释了这些控制手段如何重塑 token 选择。

![解码从当前概率分布中选出一个 token，而这个选择会改变随后的每一个分布。](https://sebastianraschka.com/images/LLMs-from-scratch-images/ch05_compressed/proba-to-text.webp)

**模型或数据本身可能偏好重复文本。** 一个小模型或训练不足的模型可能严重依赖短的局部模式。过拟合可能使它复述来自某个狭窄数据集的重复段落。微调数据中的重复记录、模板化的合成回复，以及大量带有相同标题或过渡短语样本，也会提高这些模式出现的概率。

训练和生成让模型面对的前缀并不相同。在 teacher forcing 训练期间，下一次预测接收到的是数据集中真实的前序 token。而在生成期间，它接收到的是模型自己先前做出的选择。一次糟糕的选择可能把序列带入一个训练中很少出现的上下文。这种失配通常被称为**暴露偏差（exposure bias）**。

**提示词或对话模板也可能制造循环。** 以一个未完成列表结尾的提示可能诱使模型不断添加形式相似的条目。重复的指令可能被原样复读。对于指令微调的检查点，缺失的助手起始标记或错误的轮次结束 token 可能让模型无限地同时生成对话的双方。在更改采样设置之前，应当先应用正确的[对话模板](https://sebastianraschka.com/faq/docs/why-prompt-templates-matter.html)。

**生成代码可能复制或误读上下文。** 每个解码步骤都应当从最后位置的 logit 中进行选择，并恰好追加一个新的 token ID。如果代码把完整的解码响应再次追加进去、只送入不含最新 token 的原始提示、从错误的位置选取 logit，或者把 KV 缓存与错误的位置 ID 或注意力掩码组合使用，就可能出现循环。

分词器与检查点也必须匹配。模型应当以评估模式运行，使 dropout 处于关闭状态。当上下文达到最大长度时，截断策略应当保留预期的最近历史以及任何必须保持可见的指令。

**停止逻辑可能把重复变成一场看似无限的运行。** 生成器应当在输出检查点的序列结束 token 或轮次结束 token 时停止。它还需要一个最大新 token 数限制作为安全边界。应用层的停止字符串可能跨越多个 token ID，因此只检查最新一个 token 可能会漏掉它们。

我会按以下顺序调试重复循环：

1. 使用正确的检查点、分词器、对话模板和模型评估模式运行贪心解码。
2. 记录生成的 token ID，验证每一步都只追加一个 token、读取的是最后的 logit，并且缓存位置正确前进。
3. 确认结束 token、停止字符串和最大新 token 数限制。
4. 将贪心解码的输出与适中温度以及合理的 top-k 或 top-p 设置下的输出进行比较。
5. 测试多个提示，并检查验证损失、重复的训练记录和重复的回复模板。

贪心解码对调试很有用，因为它是确定性的。如果同一个输入和检查点下，某个实现产生了不同的贪心输出，可能存在非确定性内核或所示循环之外的隐藏状态。如果贪心解码会重复而适中采样通常能逃脱，那么解码分布很可能是问题的一部分。如果所有解码方法在许多提示上都重复，那么检查点、数据或模板就值得仔细检查。

在基本循环正确之后，抗重复控制手段可以提供帮助。**重复惩罚（repetition penalty）** 会降低已经出现过的 token ID 的概率。**存在惩罚（presence penalty）** 对用过的 token 只惩罚一次，而**频率惩罚（frequency penalty）** 随其出现次数增长。**禁止重复 n-gram 规则（no-repeat n-gram rule）** 会阻止任何会重现先前 n-gram 的下一个 token。

这些控制手段需要保守的设置。自然语言中合法地重复着人名、函数标识符、标点和常见词。过强的惩罚可能损害代码、引用文本、诸如 "New York" 这样的事实性名称，或带有循环出现字段名的结构化输出。n-gram 规则能阻止逐字复制，却对语义层面的重复无能为力。

当提示定义了一个有限的结构时，例如要求特定数量的条目或明确的结束条件，提示工程也能起到作用。对于反复出现的生产环境故障，更好的微调样本和偏好数据可能比激进的解码惩罚更可靠地改善响应分布。

通用的[自回归生成 FAQ](https://sebastianraschka.com/faq/docs/autoregressive-text-generation.html) 展示了完整的 token 循环。如果重复伴随着可疑的低训练损失或整体糟糕的文本，[训练与生成故障排查指南](https://sebastianraschka.com/faq/docs/low-loss-but-poor-text.html) 涵盖了目标泄漏、分词器失配和过拟合等内容。
