# 为什么 MoE 模型参数巨大、激活计算却更低

专家混合（MoE）模型存储大量前馈专家，而路由器只把每个 token 送入其中一小部分。**总参数（total parameters）**统计检查点里的每个专家。**激活参数（active parameters）**统计被选中的专家，加上为该 token 运行的模型共享部分。

这使 MoE 模型在存储容量与单 token 计算之间形成巨大落差。这个比较需要一条清晰的基线。MoE 模型比总参数相同的稠密模型使用的专家计算少得多。但它并不保证达到与"规模等于所报激活参数数的稠密模型"相同的速度或内存占用。

## 额外参数大部分在专家里

在稠密 transformer 块中，每个 token 都经过同一个前馈网络。MoE 块用多个备选的前馈网络（称为专家）替换该网络。注意力、归一化、残差连接以及解码器的其余部分通常保持共享。

对于一个 token 表示 \(x\)，路由器为每个专家计算一个得分，并保留前 \(k\) 个选择。一个简化的 MoE 层为

\[\operatorname{MoE}(x) = \sum\_{i \in \operatorname{TopK}(x)} g\_i(x) E\_i(x),\]

其中 \(E\_i\) 是第 \(i\) 个专家，\(g\_i(x)\) 是它的路由权重。路由是逐 token 执行的。两个相邻的 token 因此可以使用不同的专家。

![稠密前馈块对每个 token 应用同一个网络，而 MoE 块存储多个专家并把每个 token 路由到其中一个子集](https://sebastianraschka.com/images/LLMs-from-scratch-images/bonus/moe-memory/1.webp)

未激活的专家仍是模型的一部分。它们的权重占据检查点和设备内存，但不参与该 token 的前馈计算。

## 一个简单的参数量例子

假设模型的共享部分含 \(S\) 个参数。每个 MoE 层有 8 个专家，每个专家 \(P\) 个参数，路由器为每个 token 选择 2 个专家。暂时忽略很小的路由器，专家部分的贡献为

- 专家总参数：\(8P\)
- 每 token 的激活专家参数：\(2P\)

对完整模型而言，相关的计数更接近于总参数 \(S + 8P\)、激活参数 \(S + 2P\)。因此比值并不是简单的 8 除以 2，因为共享的注意力、嵌入、归一化层和输出头在两种情况下都是激活的。

同样的记账适用于所有 MoE 层。如果架构包含 \(L\) 个 MoE 层，每层存储自己的专家集合。在 \(k\) 不变的情况下，增加专家数量可以快速抬高总参数量，而激活专家数保持不变。

![当路由器每个 token 仍只选择少数几个专家时，增加存储的专家数对总参数的提升远快于对激活参数的提升](https://sebastianraschka.com/images/LLMs-from-scratch-images/bonus/moe-memory/2.webp)

一些架构还包括一个或多个**共享专家（shared expert）**。这些专家与被路由的专家一起为每个 token 运行。它们的参数同时计入总数和激活数。

## 激活参数是计算的代理

参数量与浮点运算量相关，尤其是每个专家内部的大型矩阵乘法。但它们不是同一个度量。精确 FLOPs 取决于专家维度、序列长度、注意力设计、复用的权重，以及专家周边的操作。

把五个量分开对待会有帮助。

| 量 | 描述什么 | 单凭它无法决定什么 |
| --- | --- | --- |
| 总参数 | 所有存储的权重，包括未激活专家 | 每 token 算术量 |
| 激活参数 | 一个 token 在被路由路径上的权重 | 精确 FLOPs 或延迟 |
| 每 token FLOPs | 对给定输入形状执行的算术 | 内存搬运或通信时间 |
| 权重内存 | 检查点在选定精度下所需的容量 | KV 缓存大小 |
| KV 缓存 | 为活动序列保留的注意力状态 | 专家权重存储 |

在长上下文下，即使专家路径保持稀疏，注意力也可能成为总工作量中可观的一部分。路由器也要为专家打分、分发 token、并合并返回的输出。这些开销通常小于评估所有专家，但它们是运行时的一部分。

这就是为什么一个 220 亿激活参数的模型未必表现得像一个 220 亿参数的稠密模型。两个模型可能在注意力维度、层数、专家形状、内存访问模式和内核上都不相同。

## 为什么额外容量仍有帮助

虽然一个 token 只造访少数专家，但不同 token 可以走不同路由。跨一个批次和整个训练数据集，所有专家都能收到更新。因此，相对于单 token 算术量相近的单条稠密前馈通路，模型可以存储更多学到的函数。

这种条件计算（conditional computation）正是构建 MoE 模型的主要原因。总容量的增长可以快于分配给单个 token 的计算量。它并不保证更高的质量。训练数据、优化过程、路由行为、模型维度和后训练配方仍然决定这些容量能变得多有用。

**专家**这个词也可能产生误导。专家不一定按数学、代码、语法这类人类类别干净分工。特化可能相互重叠，并可能随层或训练阶段而变化。

## 系统成本仍然可观

每个专家权重都必须存在某处。单个加速器必须装下分配给它的完整检查点，否则专家必须分布到多台设备上。量化可以减少这部分存储，但在计算权重内存时，总参数仍是正确的起点。

分布式专家执行带来通信。路由之后，token 表示被发送到拥有所选专家的设备，再返回其原序列位置。这种全互联（all-to-all）交换消耗的时间可能抵消相当一部分算术节省。

批次形状也有影响。每个专家处理路由到它的 token。大而均衡的批次可以形成高效的专家矩阵乘法。小批次或不均衡的路由可能让一些专家闲置，而另一些得到别扭的小负载。即使每个 token 只使用少数专家，一个批次合起来也可能触及许多专家。

因此路由器需要负载均衡机制。架构可能使用辅助目标、路由偏置、专家容量上限或其他方法，来防止一小撮专家接收大多数 token。糟糕的均衡既影响模型训练，也影响硬件利用率。

![共享专家为每个 token 运行，而路由器为依赖 token 的路径选择额外专家](https://sebastianraschka.com/images/LLMs-from-scratch-images/bonus/moe-memory/3.webp)

训练期间，反向传播沿着为每个 token 选中的专家进行。稀疏路由相对激活全部专家减少了专家算术量。但训练仍包括路由器学习、负载均衡、激活存储、完整参数集的优化器状态，以及专家分片时的通信。

## 如何解读报告的 MoE 规模

MoE 模型名称常常把总参数和激活参数放在一起报告。像 `235B-A22B` 这样的名称表示约 2,350 亿总参数和每 token 约 220 亿激活参数。完整的 2,350 亿参数检查点仍然必须被存储或分布。

DeepSeek V3 提供了另一个具体例子。它报告 6,710 亿总参数和每 token 370 亿激活参数。其 MoE 层把被路由专家与一个共享专家结合使用，因此激活数包含的不只是路由器的 top-k 选择。

这些标签是有用的概要，但惯例并未完全标准化。在比较两个 MoE 模型之前，我会检查所报激活数是否包含共享专家、稠密层、嵌入和输出头。然后我会在相同上下文长度、批大小、精度、运行时和硬件下比较实测 FLOPs、内存使用、延迟和吞吐量。

主要的记账规则很简单。用**总参数**估算检查点存储和设备容量。用**激活参数**作为每 token 计算的一阶近似。用实际基准测试来决定速度。
