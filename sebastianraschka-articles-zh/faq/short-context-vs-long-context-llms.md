# 短上下文与长上下文 LLM 之比较

**长上下文 LLM** 能够在单次请求中保留更多的可用 token。这对于大型文档、代码仓库、长对话以及大量检索段落很有用。而代价出现在这些 token 真正被使用的时候：更长的输入会增加 prefill 计算量、KV 缓存内存、解码开销，以及在干扰信息中找到相关内容的难度。

宣传的最大窗口不应与每次请求的实际长度混为一谈。一个支持 128K token 的模型照样可以处理 2K token 的提示，此时它的注意力计算使用的是这 2K 个 token，而不是一个虚构的 128K token 序列。因此，两个架构和参数量相同的模型，即使一个允许更大的最大窗口，在同一段短输入上的开销也可以相差无几。

「上下文长度」可以指三个相关的量：

- **配置上下文长度** 是实现所接受的最大位置或缓存长度。
- **训练上下文长度** 描述模型在预训练、继续训练或上下文扩展期间遇到的序列长度。
- **有效上下文长度** 是模型在特定任务上能够可靠检索并使用信息的范围。

这几个数值可能相差很大。扩展配置或对 RoPE 做重缩放可以让前向传播在更大的位置索引上运行，但模型仍可能损失检索精度、难以利用位于中部的信息，或者在答案需要组合提示中相距很远部分的细节时失败。

上下文预算通常包含系统提示、用户输入、对话历史、检索到的文本、工具结果，以及保留在序列中的已生成 token。有些 API 还会单独施加输出 token 上限。如果一个模型有 8K 窗口，收到了 7.5K 输入 token，那么除非服务系统截断或总结先前的内容，共享预算中留给生成的部分就所剩无几了。

对于全自注意力，查询-键得分对的数量随序列长度按平方增长。把提示从 8K 增加到 16K token，prefill 期间的注意力得分对大约变为四倍。这并不意味着整个模型恰好变慢四倍，因为前馈层和其他操作的增长方式各不相同。FlashAttention 减少了内存访问量，并避免在高带宽显存中存储完整的得分矩阵，但它计算出的注意力结果是完全一样的。

自回归解码的扩展模式则不同。每个注意力层都要为保留的前缀存储键和值。因此 **KV 缓存**随上下文长度、批次大小、产生缓存的层数、KV 头数、头维度以及每个元素的字节数线性增长。在全注意力层中，每个新的查询还必须读取或交互所有保留的键和值。

![GQA 内存曲线展示了 KV 缓存存储如何随保留的上下文长度增长，以及更少的 KV 头如何降低这种增长。](https://sebastianraschka.com/images/LLMs-from-scratch-images/bonus/gqa-memory/3.webp)

这个规模足以影响部署决策。例如 Qwen3 8B 在其 36 个 GQA 层上，每个序列的每个 token 会增加 144 KiB 的 bf16 逻辑缓存。在 32,768 token 处，单条序列在计入分配器开销和服务缓冲区之前就需要约 4.5 GiB。八条等长序列需要约 36 GiB 的逻辑缓存。模型权重可以在多个请求间共享，但每条活跃序列都需要自己的缓存。

长上下文架构使用多种方法来控制这些开销。分组查询注意力（GQA）和多查询注意力存储更少的键值头；缓存量化降低每个元素的字节数；多头潜在注意力（MLA）存储压缩后的表示。这些方法减少了缓存内存，但并不能消除 prefill 期间全注意力的二次方得分计算。

滑动窗口注意力改变了一层能访问哪些 token。局部层只在一个固定的近期窗口内做注意力，因此当窗口填满后，它的缓存和注意力计算就不再增长。模型常常混合使用局部层和全局层，使部分层保留对完整序列的访问。

![滑动窗口注意力限制了局部层保留的上下文量，而周期性的全局层保留了贯穿完整序列的路径。](https://sebastianraschka.com/images/LLMs-from-scratch-images/bonus/swa-memory/4.webp)

这种设计节省了内存和计算，不过一个 token 可能需要经过好几层才能接收到来自远处的信息。循环注意力与线性注意力的混合架构走得更远，它们用固定大小的状态替换了许多注意力层，其余的全注意力层则在技术栈的选定位置提供直接的 token 查找。

质量问题与系统开销是两回事。一个模型可以通过简单的「大海捞针」检索测试，却仍难以在同样长度上进行多步推理。位置也很重要：[Lost in the Middle](https://arxiv.org/abs/2307.03172) 发现，当相关信息出现在开头或结尾附近时，模型的表现可能好于出现在中间的情况。真实的提示还夹杂着重复的事实、相互冲突的段落、格式噪声和不相关文本。

因此，更大的窗口并不能替代提示构造。检索可以挑出少量相关片段，重排序可以剔除弱匹配；摘要和结构化状态可以让长对话或智能体轨迹保持紧凑。这些方法也有各自的失败模式——检索器或摘要器可能遗漏重要内容——但它们通常能改善延迟并减少干扰。

在以下情况我会使用较短的实际上下文：答案只依赖一小批已知段落、任务对延迟敏感，或者大量并发请求必须共享有限的加速器内存。而当过滤原始材料会丢失重要关联时——例如审查一份完整合同、在代码库中追踪定义、比较散布在长文档各处的证据——长上下文就很有用。

因此，有意义的比较取决于具体工作负载。请测量提示长度分布、首 token 延迟、每 token 解码延迟、每条活跃序列的缓存内存，以及任务质量在窗口中若干位置上的表现。最大 token 数只告诉我们什么装得下，并不能告诉我们模型对整个范围的利用有多好，也不说明发送这么多文本就是最好的系统设计。
