# 为什么 LLM 评估比分类更难

开放式的大语言模型（LLM）评估之所以更难，是因为评估者必须同时定义期望的行为和打分方式。在普通分类中，输出属于一个固定的标签集合。一旦参考标签被接受，计算准确率或 F1 是机械性的。

这个区分需要一个限定。一个在选择题、精确数值答案或可执行代码上被评估的 LLM 仍然可以有清晰的分数。困难的情形是自由格式生成，此时多个回复都可能是有效的，而质量又有多个维度。

## 分类的输出空间通常有界

考虑一个只有两个允许标签的垃圾邮件分类器。模型为 `not spam` 和 `spam` 各返回一个得分。取较大的得分即得到一个预测类别，可以与参考标签比较。

![文本分类器通过 argmax 把一组固定的输出得分转换为一个预测标签](https://sebastianraschka.com/images/LLMs-from-scratch-images/ch06_compressed/class-argmax.webp)

数据集仍可能包含歧义样本、错误标签、类别不平衡或分布偏移。这些都是重大的评估问题。然而，一旦标签和度量固定下来，两个评估者会从相同的预测计算出相同的准确率。

开放式生成把输出空间从一个小标签集变成了任意长度的序列。一个要求解释的提示可以有许多正确答案，措辞、组织、例子和详细程度各不相同。一条参考回复是有用的示例，但很少是唯一可接受的回复。

| 属性 | 分类 | 开放式生成 |
| --- | --- | --- |
| 输出空间 | 固定的标签集合 | 极大的 token 序列集合 |
| 参考答案 | 通常是一个类别标签 | 常常是众多有效回复之一 |
| 典型分数 | 准确率、精确率、召回率或 F1 | 多项任务检查或评分细则标准 |
| 部分得分 | 通过度量或标签结构定义 | 常需判断哪些部分正确、哪些缺失 |
| 评估者歧义 | 标签和度量固定后很低 | 即使有评分细则也可能仍然很高 |

## 一个生成回复可能一方面好、另一方面差

假设提示要求对一份技术报告做三条要点总结。一个回复可能事实正确却遗漏了主要局限。另一个可能用五条要点覆盖了所有结果，却违反了要求的格式。第三个可能简洁且结构良好，却把一个数字说错了。

单一的 `correct` 或 `incorrect` 标签掩盖了这些差异。有用的标准可能包括：

- 事实正确性以及对所给来源的依托
- 任务所需信息的覆盖度
- 与请求的相关性
- 指令和格式遵循
- 对目标读者而言的清晰度
- 适用场合下的安全或策略合规

这些标准可能相互冲突。添加限定语可能提升完整性，却让回复超出要求的长度。数值平均也可能掩盖一次严重失败。一个风格和覆盖度得分都高的回复，如果其核心主张是错的，就不应通过。

出于这个原因，我更倾向于分开的逐标准评分加上显式的硬失败检查，而不是一个无法解释的单一质量数字。

## 精确匹配往往过于严格

当答案有规范形式时，精确匹配（exact match）是有效的。它可以给分类标签、规范化后的短答案或已知标识符打分。但它无法处理有效的转述。`The capital is Madison` 与 `Madison` 作为字符串不同，尽管两者可能都正确回答了同一个问题。

参考重叠类度量不那么严格，因为它们比较的是词或子序列。当匹配参考措辞很重要时它们有用。但对于解释、摘要和改写，高重叠可能奖励照抄，低重叠则可能惩罚一个同样好的表述。

最好的自动评估器往往来自任务本身，而不是通用文本相似度。解析 JSON 并校验其 schema。用单元测试运行生成的代码。在指定容差内比较数值答案。检查被引用的段落是否包含所声称的证据。这些方法把开放式任务的一部分变成可复现的测试。

[精确匹配与 LLM 评审 FAQ](https://sebastianraschka.com/faq/docs/exact-match-vs-llm-as-a-judge.html) 给出了更多关于这条边界的例子。

## 语言模型损失回答的是另一个问题

交叉熵和困惑度度量模型分给观测参考 token 的概率。它们适合评估在固定语料上的预测拟合。它们并不直接度量一个生成的回复是否真实、是否遵循指令、或是否解决了用户的任务。

两个模型可以有相近的困惑度，而在后训练之后表现出不同的助手行为。反过来，一个指令微调模型可以变得更有用，而在一个无关预训练语料上的困惑度并没有改善。[困惑度 FAQ](https://sebastianraschka.com/faq/docs/perplexity-what-it-means.html) 介绍了该指标适用的受控比较。

## 生成结果可能因运行而异

一个确定性分类器通常对相同输入和相同检查点返回相同标签。LLM 生成可能从下一个 token 分布中采样。温度、top-k、top-p、最大输出长度、随机种子、停止条件、系统提示和聊天模板都可能改变回复。

因此，评估应当记录完整的生成配置。如果产品会采样回复，每个提示只取一个输出可能给出噪声很大的估计。多次采样可以度量成功的概率，不过 `pass@k` 和 best-of-k 结果给了模型比单次生产请求更多的尝试机会。尝试次数应写进报告的指标里。

托管模型的版本也可能变化。可复现的比较应尽可能固定模型版本并保留被评估的输出。

## 人类评审和模型评审本身也需要评估

人类评审可以对自由格式回复应用评分细则，但他们的判断并不是自动的ground truth。评审们可能对标准理解不一、漏掉一个领域错误，或偏爱熟悉的写作风格。技术正确性往往需要领域专家，这推高了大规模评估的成本。

成对比较可能比打绝对分更容易。评审回答的是在给定标准下两个回复哪个更好。这给出的是一个相对偏好，而不是"胜者好到足以部署"的证明。

**LLM-as-a-judge（LLM 评审）**可以以更大规模应用同一评分细则。其输出仍是一种模型预测。评审模型可能偏爱冗长、对候选顺序敏感，或漏掉其专长之外的错误。应当隐藏模型名称和其他无关的来源信息，并在成对测试中随机化回复顺序。

我会先在一个较小的人工评审集上校准模型评审，再把它用于完整评估。一致性应按每个标准和每个重要数据切片分别检查。一个在写作质量上一致的评审，在数学正确性或引用支撑上可能仍不可靠。

## 基准测试可能成为训练目标的一部分

公开的 LLM 基准测试容易受到污染，因为其提示和答案可能出现在预训练数据、微调数据或模型开发的反馈循环中。针对热门排行榜的反复优化也可能把设计决策过拟合到那个基准上，即便没有字面意义上的数据泄露。

基准覆盖面与污染同样重要。平均分可能掩盖在长提示、非英语输入、罕见领域或对抗性措辞上的失败。生产环境的评估应包含有代表性的私有样本，并按有意义的切片报告结果，而不是只给一个汇总分。

小的分数差异也需要不确定性估计。相同提示上的配对比较、置信区间或自助法（bootstrap）估计有助于区分可重复的提升与采样噪声。人工评审与模型评审之间的分歧应纳入这种不确定性，而不是被悄悄丢弃。

## 一个实用的评估栈

评估过程在生成模型输出之前就开始了。我会按以下顺序进行：

1. 定义任务分布、期望行为、硬失败和质量标准。
2. 冻结一个保留提示集，覆盖有代表性的难度、领域和输入长度。
3. 在结果可被直接解析、执行或验证的地方应用确定性检查。
4. 为其余开放式质量维度编写逐标准的评分细则。
5. 建立一个可信的人工评审子集并度量评审间一致性。
6. 在把 LLM 评审扩展到更多输出之前，先在该子集上校准。
7. 为对比冻结模型、提示模板、工具、检索语料和解码设置。
8. 分别报告逐标准得分、数据切片、不确定性、延迟、token 用量和成本。

![指令模型评估在模型训练完成后增加回复抽取、定性检查和打分](https://sebastianraschka.com/images/LLMs-from-scratch-images/ch07_compressed/22.webp)

最后一步是错误分析。检查确定性失败、评审与人类分歧的案例，以及决策边界附近的样本。这些案例能揭示下一次改进应针对模型、提示、检索系统、工具集成，还是评估器。
