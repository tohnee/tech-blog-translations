# 从简单 GPT 到生产环境

一个简单的 GPT 实现最好被视为一个**可执行的参考实现**。它让分词、因果注意力、损失计算和生成过程都易于检查。生产级技术栈应当保留这些行为，同时把教学用的代码路径替换为经过测试的数据、训练、推理和服务组件。

我不会把教学实现本身逐步改造成最终的生产服务器。保持它足够小巧，以便逐行核对每一个计算。用它来测试优化后的实现，并用它来理解失败的原因。

对于大多数应用来说，部署也是从一个经过测试的预训练检查点出发，而不是从零训练一个 GPT。预训练一个通用模型是一个独立的数据与算力工程。但从零实现的模型仍然是理解该检查点并验证其实现的正确基础。

这一演进过程可以组织为六个阶段，每个阶段都有一个通过检验（exit check）。

| 阶段 | 需要加入什么 | 进入下一阶段的证据 |
| --- | --- | --- |
| 参考模型 | 分词器、嵌入、因果注意力、前馈块、下一 token 损失、生成 | 在一个小批次上过拟合、复现一个已保存的检查点、验证因果掩码 |
| 模型质量流水线 | 数据验证、训练-验证集划分、检查点元数据、任务评估 | 面向目标任务的可复现损失曲线和留出集结果 |
| 适配 | 监督微调、LoRA 或全量微调、可选的偏好训练 | 任务专项评估取得提升，且没有不可接受的性能回退 |
| 推理运行时 | 高效加载、低精度、KV 缓存、批处理、优化注意力 | 数值或输出一致性，加上延迟、吞吐量和内存的测量 |
| 服务 | 请求模式（schema）、token 限制、流式输出、调度、超时、取消、访问控制 | 在预期并发和提示长度下的负载与故障测试 |
| 运维 | 监控、发布门禁、金丝雀发布、版本管理、回滚 | 一块仪表盘、一个固定的先前版本、一条演练过的回滚路径 |

## 建立一个可信的参考实现

第一个实现应当刻意保持朴素。它需要精确的分词器与位置处理、用于下一 token 预测的输入-目标错位（shift），以及防止目标泄漏的因果掩码。小批次过拟合测试尤其有用。如果模型都无法在几个序列上把损失降下来，那么更大规模的训练将很难调试。

保存-加载一致性要尽早重视。同一个检查点、分词器、提示、随机种子和解码设置，应当能复现出预期的 logit 或 token。把模型配置记录在权重旁边，这样层数、维度、词表、归一化和位置方法就不会悄悄发生漂移。

## 把模型开发与服务分开

训练和服务承担不同的职责。离线路径准备数据、更新权重、评估检查点，并发布一个不可变的模型工件（artifact）。在线路径加载该工件、对请求分词、调度推理、返回生成的 token，并上报运维指标。

这种分离让发布可复现。一个模型工件应当标明其检查点、分词器、对话模板、配置、代码版本和评估结果。即使权重保持不变，修改提示模板也可能改变行为，因此它应纳入带版本的工件或发布配置之中。

微调应当由可度量的差距驱动。监督微调教给模型期望的响应格式和任务行为。当全量更新并非必要时，LoRA 可以降低训练内存和检查点大小。DPO 等偏好方法会带来额外的数据与评估要求，因此只有当成对偏好能解决监督样本无法很好解决的问题时，我才会使用它们。

## 只有在重新训练可行时才现代化架构

RoPE、RMSNorm、SwiGLU 和分组查询注意力都是架构选择。可以逐个把它们引入一个将要用它们训练的模型中。但不能简单地把它们插入一个现成的 GPT-2 检查点还期望保持输出不变，因为学得的权重依赖于原本的计算方式。

![GPT 到 Llama 的演进保持了解码器-only 骨干，同时改变了归一化、位置处理、前馈块和注意力共享方式。](https://sebastianraschka.com/images/LLMs-from-scratch-images/bonus/gpt-to-llama/gpt2-to-llama2-llama3.webp)

加载现有检查点时，实现必须与该检查点的架构匹配。现代化改造于是发生在运行时。例子包括融合注意力核（kernel）、KV 缓存、低精度计算、内存高效的权重加载、量化和请求批处理。每一项改动都应当先在 logit 或固定的生成集合上与参考实现对比，然后才单凭速度下结论。

KV 缓存是最先值得做的推理改动之一。它避免在自回归解码中重复计算旧的键和值。缓存会增加内存占用，其大小随上下文长度和活跃序列数增长。动态或连续批处理可以提高总吞吐量，不过为组成或扩充一个批次而等待可能会增加单个请求的延迟。

量化是另一个需要权衡的改动。它可以降低权重内存，有时还能提升吞吐量。实际收益由算子支持情况、硬件、批次大小和所选精度决定。量化后的检查点应当通过与原检查点相同的应用评估，因为微小的数值变化就可能改变生成结果。

## 最后才添加服务边界

一个最小的服务只加载模型一次并暴露稳定的请求模式。它验证提示和生成参数，强制执行上下文与输出长度限制，并在客户端断开时支持取消。流式输出改善感知响应速度，但不会减少总的生成工作量。

调度器控制并发与内存。它应当在请求导致显存不足（OOM）故障之前就拒绝或排队请求。请求超时、速率限制、身份认证、就绪检查和有界队列都是普通的服务关注点，在 LLM 周围同样不可或缺。

如果模型可以调用工具，那么模型输出必须被视为不可信输入。工具名和参数需要做模式验证，运行时应只授予所需的最小权限。提示中的指令永远不应成为访问密钥或无关资源的授权依据。

## 度量用户实际体验到的行为

有用的推理指标包括首 token 时间、token 间延迟、总响应时间、请求吞吐量、排队时间、加速器峰值内存和 KV 缓存利用率。报告结果时应同时给出提示长度、输出长度、批次大小、模型精度和硬件。脱离这些背景的「每秒 token 数」很难比较。

运维日志应当能定位模型版本和错误类别，默认不保留敏感提示。监控无效请求、超时、取消、OOM 事件和评估回退。新模型或新运行时应先通过离线测试，再进行小规模金丝雀部署。保持上一个版本可加载，这样回滚只是改一下配置，而不是一次紧急重建。

这个顺序让失败保持局部化。如果优化后的运行时与参考 logit 不一致，问题就出在服务层以下。如果离线评估通过但请求在并发下失败，就应关注调度器或容量限制。只有当某个组件的通过检验表明它解决了预期问题时，才把它加入进来。

关于质量门禁，参见[为什么评估 LLM 输出很困难，常用评估方法有哪些？](https://sebastianraschka.com/faq/docs/evaluating-llm-outputs.html)。推理路径在[什么是 KV 缓存，它为什么能加速 LLM 推理？](https://sebastianraschka.com/faq/docs/kv-cache.html)中讲解，而[什么是内存映射权重加载，它何时有用？](https://sebastianraschka.com/faq/docs/memory-mapped-weight-loading.html)讨论检查点启动内存。
