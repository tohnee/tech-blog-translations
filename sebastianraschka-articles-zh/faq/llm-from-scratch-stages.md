# 从零构建 LLM 的主要阶段

从零构建 LLM，意味着随机初始化模型权重，并搭建把这份权重变成语言模型的数据与训练流水线。一个小型教学用 GPT 和一个有竞争力的基础模型遵循同样的大致阶段，只是它们在数据、算力和分布式系统需求上相差若干个数量级。

**1. 确定目标与预算。**

选定目标语言或领域、参数量、训练 token 预算、上下文长度和可用硬件。这些选择彼此制约。能塞进内存的模型，其训练算力需求仍可能不切实际；而更长的上下文会增加激活和注意力开销。

**2. 搭建数据与分词器流水线。**

收集来源和许可都允许预期用途的文本。清洗、去重、文档边界、质量过滤器和留出划分，都应在漫长的训练开始前敲定。训练或选定一个分词器，然后把 token 流变成定长的[输入-目标样本](https://sebastianraschka.com/faq/docs/input-target-pretraining-examples.html)。要检查解码后的样本，因为一条数值上正确的流水线仍可能含有损坏的文本或意料之外的文档混杂。

**3. 实现并测试模型。**

一个 GPT 风格的解码器组合了嵌入、位置信息、因果注意力、前馈层、归一化、残差路径和一个词表输出头。[构建模块 FAQ](https://sebastianraschka.com/faq/docs/gpt-style-model-building-blocks.html) 跟踪了张量形状在这一栈中的流转。单元测试应检查因果掩码、参数共享、输出维度，以及在适用的情况下带缓存与不带缓存的生成是否一致。

在扩大规模之前，我会先验证模型能否过拟合一个小批次。如果不能，更大的数据集或更多加速器通常只会掩盖 bug，而不是修复它。

**4. 让训练循环可恢复。**

训练系统需要交叉熵损失、优化器、学习率日程、梯度处理、混合精度、日志，以及检查点的保存与续训支持。对于一个 token 概率近似均匀的随机初始化模型，初始损失应接近 `log(V)`，其中 `V` 是词表大小。一次短程运行应能同时降低训练损失和留出损失，且不出现数值溢出。

更大规模的运行会加入数据并行、张量并行或流水线并行。这些技术分发的是同一个优化问题；它们并不能取代单设备上的正确性检查。

**5. 用下一 token 预测做预训练。**

预训练反复呈现 token 序列并更新模型，以提高观测到的后续内容出现的概率。跟踪验证损失、token 吞吐量、梯度范数和数据消耗量。保存足以复现一个检查点的元数据，包括模型配置、分词器、优化器状态、调度器状态和训练步数。

**6. 为预期用途添加后训练。**

基础检查点可以针对分类或[指令遵循](https://sebastianraschka.com/faq/docs/instruction-finetuning-practical-usefulness.html)进行适配。偏好优化、推理训练和工具使用轨迹是可选的后续阶段。保留原始基础检查点，就能度量每个阶段各改变了什么，也可以换一套后训练方案重新开始。

**7. 在优化部署之前先评估。**

评估应包括留出集语言建模、任务专项检查和定性生成。数据污染、记忆化、格式失败以及微调领域之外的退化，需要单独的测试。开放式输出可能需要人工评审或经过校准的评判模型，相关讨论见[评估 FAQ](https://sebastianraschka.com/faq/docs/evaluating-llm-outputs.html)。

**8. 搭建推理路径。**

生成需要加入 token 选择、停止规则、提示格式化和 [KV 缓存](https://sebastianraschka.com/faq/docs/kv-cache.html)。服务端还可以使用量化权重、批处理和高效内存内核。要在与应用预期相同的设置下，度量首 token 时延、解码吞吐量、峰值内存和输出质量。

这一顺序让失败保持局部化：数据样本可以在训练前检查，模型数学可以在分布式执行前测试，检查点可以在服务优化让系统更难调试之前完成评估。
