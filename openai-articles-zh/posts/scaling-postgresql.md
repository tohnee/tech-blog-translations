# 扩展 PostgreSQL，支撑 8 亿 ChatGPT 用户

> 原文：[Scaling PostgreSQL to power 800 million ChatGPT users](https://openai.com/index/scaling-postgresql/) · OpenAI 博客

多年来，PostgreSQL 一直是支撑 ChatGPT 和 OpenAI API 等核心产品最关键的底层数据系统之一。随着用户规模的快速增长，数据库承受的压力也呈指数级上升。过去一年，我们的 PostgreSQL 负载增长了 10 倍以上，而且仍在快速攀升。

在推进生产基础设施以支撑这一增长的过程中，我们有了一个新的认识：PostgreSQL 可以被扩展到可靠支撑远超许多人此前想象的更大的读密集型工作负载。这个系统（最初由加州大学伯克利分校的一组科学家创建）使我们能够用一个单一主库的 [Azure PostgreSQL flexible server 实例](https://learn.microsoft.com/en-us/azure/postgresql/overview)加上分布在全球多个区域的近 50 个读副本，支撑海量全球流量。这就是我们如何在 OpenAI 通过严格的优化和扎实的工程，把 PostgreSQL 扩展到为 8 亿用户支撑每秒数百万次查询的故事；我们还会分享在此过程中学到的关键经验。

## 初始设计中的裂缝

ChatGPT 发布后，流量以前所未有的速度增长。为了支撑它，我们迅速在应用层和 PostgreSQL 数据库层实施了大规模优化，通过增大实例规格进行纵向扩展，并通过增加更多读副本进行横向扩展。这一架构长期为我们提供了良好支撑。随着持续改进，它仍将为未来增长提供充足的空间。

单一主库架构能够满足 OpenAI 规模的需求，这听起来也许令人惊讶；然而要让它在实践中真正跑通并不简单。我们经历过数起由 Postgres 过载引起的事故（SEV），它们往往遵循同一个模式：某个上游问题导致数据库负载骤然飙升，比如缓存层故障引发的大面积缓存未命中（cache miss）、昂贵多路连接查询的激增使 CPU 饱和，或是新功能发布带来的写入风暴。随着资源利用率攀升，查询延迟上升，请求开始超时。重试进一步放大负载，触发恶性循环，有可能使整个 ChatGPT 和 API 服务降级。

尽管 PostgreSQL 对我们的读密集型工作负载扩展良好，但在高写入流量期间我们仍会遇到挑战。这在很大程度上归因于 PostgreSQL 的多版本并发控制（MVCC）实现，使它在写密集型工作负载下效率较低。例如，当一条查询更新一个元组（tuple）、甚至只是单个字段时，整行都会被复制以创建新版本。在高写入负载下，这会导致显著的写放大。它还会增加读放大，因为查询必须扫描多个元组版本（死元组）才能取回最新版本。MVCC 还带来其他挑战，例如表和索引膨胀、更高的索引维护开销，以及复杂的 autovacuum 调优。（你可以在我与卡内基梅隆大学 Andy Pavlo 教授合写的博客文章[*The Part of PostgreSQL We Hate the Most*](https://www.cs.cmu.edu/~pavlo/blog/2023/04/the-part-of-postgresql-we-hate-the-most.html)中深入了解这些问题，该文曾被 [PostgreSQL 的维基百科页面](https://en.wikipedia.org/wiki/PostgreSQL#cite_note-37)引用。）

## 将 PostgreSQL 扩展到每秒数百万 QPS

为了缓解这些限制并减少写入压力，我们已经、并且仍在继续把可分片（即可以水平分区）的写密集型工作负载迁移到 Azure Cosmos DB 等分片系统，同时优化应用逻辑以尽量减少不必要的写入。我们也不再允许向当前的 PostgreSQL 部署添加新表。新工作负载默认使用分片系统。

即便基础设施不断演进，PostgreSQL 始终保持不分片，由单一主库实例承担所有写入。主要理由是：对现有应用工作负载进行分片极其复杂且耗时，需要改动数百个应用端点，可能耗时数月甚至数年。由于我们的工作负载以读密集型为主，且已实施大量优化，当前架构仍有充足的余量支撑持续的流量增长。虽然我们不排除将来对 PostgreSQL 进行分片，但鉴于当前和未来增长仍有充足跑道，这并非近期优先事项。

在接下来的章节中，我们将深入探讨我们面临的挑战，以及为解决这些问题、防止未来中断而实施的大量优化——把 PostgreSQL 推到极限，将其扩展到每秒数百万次查询（QPS）。

### 减轻主库负载

*挑战：只有单个写入者时，单一主库架构无法扩展写入。沉重的写入尖峰可能迅速使主库过载，影响 ChatGPT 和我们的 API 等服务。*

解决方案：我们尽可能降低主库上的负载——读和写都是——以确保它有足够容量应对写入尖峰。读流量尽可能被分流到读副本。不过，有些读查询必须留在主库上，因为它们是写事务的一部分。对于这些查询，我们重点确保其高效并避免慢查询。在写入流量方面，我们已把可分片的写密集型工作负载迁移到 Azure CosmosDB 等分片系统。那些较难分片但仍产生高写入量的工作负载需要更长的迁移时间，这一过程仍在进行中。我们还大力优化应用以降低写入负载；例如，我们修复了导致冗余写入的应用缺陷，并在合适之处引入惰性写入（lazy write）来平滑流量尖峰。此外，在回填表字段时，我们执行严格的速率限制，防止过度的写入压力。

### 查询优化

*挑战：我们在 PostgreSQL 中发现了若干代价高昂的查询。过去，这些查询量的骤增会消耗大量 CPU，拖慢 ChatGPT 和 API 请求。*

解决方案：少数代价高昂的查询，例如将许多表连接在一起的查询，可能显著拖慢甚至拖垮整个服务。我们需要持续优化 PostgreSQL 查询，确保其高效，并避免常见的联机事务处理（OLTP）反模式。例如，我们曾发现一个连接了 12 张表的极其昂贵的查询，该查询的尖峰正是过去多起高严重度事故（SEV）的罪魁祸首。我们应尽可能避免复杂的多表连接。如果确实需要连接，我们学到要考虑把查询拆分，将复杂的连接逻辑移到应用层。这些有问题的查询许多是由对象关系映射框架（ORM）生成的，因此仔细审查它们产生的 SQL、确保其行为符合预期十分重要。在 PostgreSQL 中还常见长时间运行的空闲查询。配置 idle_in_transaction_session_timeout 之类的超时参数至关重要，可防止它们阻塞 autovacuum。

### 单点故障缓解

*挑战：如果某个读副本宕机，流量仍可路由到其他副本。然而，依赖单一写入者意味着存在单点故障——一旦它宕机，整个服务都会受到影响。*

解决方案：大多数关键请求只涉及读查询。为了缓解主库的单点故障，我们把这些读从写入者卸载到副本，确保即使主库宕机，这些请求也能继续提供服务。虽然写操作仍会失败，但影响已经降低；由于读仍可用，这不再构成 SEV0 事故。

为了进一步缓解主库故障，我们以高可用（HA）模式运行主库，并配备热备库（hot standby）——一个持续同步、随时准备接管流量的副本。如果主库宕机或需要下线维护，我们可以快速提升备库，以尽量减少停机时间。Azure PostgreSQL 团队做了大量工作，确保这些故障转移即使在极高负载下依然安全可靠。为应对读副本故障，我们在每个区域部署多个副本并保留足够的容量余量，确保单个副本的故障不会导致区域性中断。

### 工作负载隔离

*挑战：我们经常遇到某些请求在 PostgreSQL 实例上消耗不成比例资源的情况。这会导致运行在同一实例上的其他工作负载性能下降。例如，新功能发布可能引入低效查询，大量消耗 PostgreSQL 的 CPU，拖慢其他关键功能的请求。*

解决方案：为了缓解「邻居噪音」（noisy neighbor）问题，我们把工作负载隔离到专用实例上，确保资源密集型请求的骤然飙升不会影响其他流量。具体而言，我们把请求划分为低优先级和高优先级两层，并路由到不同的实例。这样，即使某个低优先级工作负载变得资源密集，也不会拖累高优先级请求的性能。我们还在不同产品和服务之间应用同样的策略，使一个产品的活动不会影响另一个产品的性能或可靠性。

### 连接池化

*挑战：每个实例都有最大连接数限制（Azure PostgreSQL 为 5,000）。连接很容易耗尽，或积累过多空闲连接。我们此前曾发生过由连接风暴耗尽所有可用连接而引发的事故。*

解决方案：我们部署了 PgBouncer 作为代理层来池化数据库连接。以 statement 或 transaction 池化模式运行，使我们能高效复用连接，大幅减少活跃客户端连接数。这也缩短了建立连接的延迟：在我们的基准测试中，平均连接时间从 50 毫秒（ms）降到 5 ms。跨区域的连接和请求代价高昂，因此我们把代理、客户端和副本共置在同一区域，以尽量减少网络开销和连接占用时间。此外，必须谨慎配置 PgBouncer。idle timeout 之类的设置对防止连接耗尽至关重要。

每个读副本都有自己运行多个 PgBouncer pod 的 Kubernetes 部署。我们在同一个 Kubernetes Service 后运行多个 Kubernetes 部署，由它在 pod 之间对流量进行负载均衡。

### 缓存

*挑战：缓存未命中的骤增可能触发 PostgreSQL 数据库上的读取激增，使 CPU 饱和并拖慢用户请求。*

解决方案：为了减轻 PostgreSQL 上的读压力，我们使用缓存层来服务大部分读流量。然而，当缓存命中率意外下降时，大量缓存未命中会把大批请求直接压到 PostgreSQL 上。数据库读取的骤增会消耗大量资源，拖慢服务。为了防止在缓存未命中风暴期间过载，我们实现了缓存锁定（及租约）机制，使得对某个特定键未命中的读取者中只有一个会从 PostgreSQL 取数据。当多个请求在同一个缓存键上未命中时，只有一个请求获得锁并去取回数据、重新填充缓存。其他所有请求都等待缓存更新，而不是同时涌向 PostgreSQL。这显著减少了冗余的数据库读取，保护系统免受级联负载尖峰的冲击。

### 扩展读副本

*挑战：主库会向每个读副本流式传输预写日志（WAL）数据。随着副本数量增加，主库必须把 WAL 传送给更多实例，加大网络带宽和 CPU 的压力。这会导致副本延迟更高、更不稳定，使系统难以可靠扩展。*

解决方案：我们在多个地理区域运行近 50 个读副本，以尽量降低延迟。然而在当前架构下，主库必须向每个副本流式传输 WAL。虽然目前凭借非常大的实例规格和高网络带宽扩展良好，但我们无法无限增加副本，否则最终会使主库过载。为解决这个问题，我们正与 Azure PostgreSQL 团队合作推进[级联复制](https://www.postgresql.org/docs/current/warm-standby.html#CASCADING-REPLICATION)，由中间副本把 WAL 中继给下游副本。这种方式使我们有可能扩展到超过一百个副本而不压垮主库。但它也带来额外的运维复杂性，尤其是在故障转移管理方面。该特性仍在测试中；在推广到生产之前，我们会确保其稳健、能够安全地完成故障转移。

### 速率限制

*挑战：特定端点上的流量骤增、昂贵查询的激增或重试风暴，都可能迅速耗尽 CPU、I/O 和连接等关键资源，造成大范围的服务降级。*

解决方案：我们在多个层面——应用、连接池、代理和查询——实现了速率限制，防止突发的流量尖峰压垮数据库实例并触发级联故障。同样关键的是避免过短的重试间隔，那会引发重试风暴。我们还增强了 ORM 层以支持速率限制，并在必要时完全阻断特定的查询摘要（query digest）。这种有针对性的负载卸载（load shedding）能从昂贵查询的骤增中快速恢复。

### 模式（Schema）管理

*挑战：即便是一个很小的模式变更，例如修改列类型，也可能触发[整表重写](https://www.crunchydata.com/blog/when-does-alter-table-require-a-rewrite)。因此我们对模式变更极为谨慎——只允许轻量操作，避免任何会重写整张表的操作。*

解决方案：只允许轻量的模式变更，例如添加或移除某些不会触发整表重写的列。我们对模式变更执行严格的 5 秒超时。允许以并发方式创建和删除索引。模式变更仅限于既有表。如果新功能需要额外的表，它们必须放在 Azure CosmosDB 等替代性的分片系统中，而不是 PostgreSQL。回填表字段时，我们执行严格的速率限制以防写入尖峰。虽然这一过程有时会超过一周，但它确保了稳定性，避免任何生产影响。

## 成果与未来的路

这项工作表明，只要设计与优化得当，Azure PostgreSQL 就可以扩展到承载最大规模的生产工作负载。PostgreSQL 为读密集型工作负载承载每秒数百万 QPS，支撑着 ChatGPT 和 API 平台等 OpenAI 最关键的产品。我们添加了近 50 个读副本，同时把复制延迟保持在接近零的水平，在跨地理分布的各区域维持低延迟读取，并构建了足够的容量余量来支撑未来增长。

这一扩展是在尽量压低延迟、同时提升可靠性的前提下实现的。我们在生产环境中持续提供低双位数毫秒的 p99 客户端延迟和「五个九」可用性。而在过去 12 个月中，我们只发生过一次 SEV-0 级别的 PostgreSQL 事故（它发生在 ChatGPT ImageGen [病毒式发布](https://newsletter.pragmaticengineer.com/p/chatgpt-images)期间——一周内超过 1 亿新用户注册，写入流量骤然飙升逾 10 倍）。

虽然我们对 PostgreSQL 已经带我们走过的路程感到满意，但我们仍在继续挑战它的极限，以确保为未来增长留出充足跑道。我们已把可分片的写密集型工作负载迁移到 CosmosDB 等分片系统。其余写密集型工作负载的分片难度更大——我们也在积极迁移它们，以进一步分担 PostgreSQL 主库的写入。我们还在与 Azure 合作启用级联复制，以便安全地扩展到多得多的读副本。

展望未来，随着基础设施需求的持续增长，我们将继续探索进一步的扩展方案，包括分片化的 PostgreSQL 或替代性的分布式系统。
