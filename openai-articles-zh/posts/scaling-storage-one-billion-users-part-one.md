# 快速扩展在线存储，服务超过 10 亿 ChatGPT 用户

> 原文：[Rapidly scaling online storage to serve over 1 billion ChatGPT users](https://openai.com/index/scaling-storage-one-billion-users-part-one/) · OpenAI 博客

每一款 OpenAI 产品都依赖快速、可靠的数据访问——无论是用户登录、查看 Codex 设置，还是在 ChatGPT 中开启一段新对话。在这些操作能够得到响应之前，每一步都可能需要许多次独立的数据查询。如果这些请求很慢，产品就显得慢；如果这些请求失败，产品就彻底无法工作。

Habitat 是我们构建的在线存储平台，让 OpenAI 产品能够快速、可靠地访问所需信息。Habitat 现在每秒处理超过 7,000 万次请求，支撑着每周有超过 10 亿人使用的多款产品，覆盖近 40 个地理区域。Habitat 最初在 2023 年 DevDay 上发布，用于支持 GPTs，起点是一个连接单个数据库的简单 Python 客户端库。如今，它已成为一个服务超过 500 PB 数据的复杂分布式系统。

在这一规模上构建并运营基础设施绝非易事，但也称不上特别艰难。让我们处境独特的是那前所未有的扩展速度：我们必须以惊人的速度扩展，以支撑惊人的用户增长和产品需求，同时还要同步打造一个成熟平台。通常，系统工程师会按 10 倍规模来构建，希望它能撑上几年，同时为下一个 10 倍做准备。而在我们的情况下，过去三年我们每年都增长 10 倍以上。因此，构建和运营 Habitat 成了一系列战术决策与排序安排：在最底层理解每个组件，以从现有技术栈中榨取最大价值，同时抵挡存储与算力容量危机，为基础性投资争取时间。

随着 OpenAI 的成长，Habitat 也不得不随之成长：先是要变得足够可靠，以承接任务关键型产品流量；然后要足够快，以服务全球用户；最后，还要能在海量规模下灵巧运转。本文是关于我们如何扩展在线存储的两篇系列文章中的第一篇。在这篇文章中，我们将分享 Habitat 的演进历程、我们为何把它从库改造成服务，以及我们如何把一个用并不多见的服务栈语言——Python——编写的服务，拉伸成一个可靠的存储平台层。

在未来的文章中，我们将详细讲解如何实现规模化下的多租户可靠性、优化读性能的分层策略，以及我们如何深化与 Azure Cosmos DB 的合作，以可靠应对前所未有的需求。

## Habitat 是什么？

Habitat 源于一个简单的想法：产品工程师不应该需要操心数据库管理。Habitat 在 2023 年 DevDay 上首次发布，用于支持 GPTs，当时是一个与 ChatGPT 主服务器交互的小型 Python 库。它支持一小组操作，这些操作在底层映射到数据库应用 Azure Cosmos DB。

这个库的职责，是给产品团队一种简单的数据存取方式，而无需掌握底层细节。Habitat 承担了必要的工作：弄清涉及的是哪类数据、它应当从哪里来（或到哪里去）、请求是否被允许，等等。

产品工程师无需关心 schema 查找、路由、鉴权、加密、序列化、请求整形和连接池化。他们甚至不需要考虑数据来自哪里：是 Azure Cosmos DB、缓存，还是其他类型的存储。

**图 02 · Habitat 服务** 简化后的 Habitat 请求流——通过把存储逻辑解耦为独立服务，我们为部署、可观测性和平台增强建立了单一控制点。

这个 Python 库工作良好，Habitat 在 OpenAI 的产品工程师中迅速普及，尽管我们从未从中央统一推动大家放弃自助式 Postgres 和 Azure Cosmos DB。

随着产品需求的演进，产品开发者甚至可以轻松地向这个共享库添加客户端缓存、压缩或加密等特性支持。

## 构建服务，以更好地支持多个复杂产品

到 2025 年年中，作为客户端实现，Habitat 已抵达自身极限。随着 Habitat 层日益复杂、OpenAI 的服务数量不断增加，向后兼容的协议变更已变得不可行。

举个例子，为了缩小单个区域宕机对我们最关键数据集的影响范围，我们想把它们迁移到一组按区域分布的 Azure Cosmos DB 账户。完成这一变更需要向客户端引入额外的路由逻辑，先禁用、藏在功能开关（feature flag）之后，确保它滚动发布到所有客户端，然后再启用该开关。

跨数十个服务协调部署、并与每个团队合作完成滚动发布，需要好几天。在启用之前，我们意识到还想引入一些影子流量（shadowing）来确保分片逻辑正确，这又花了几天才发布完成。要修复我们发现的某个 bug？又是几天。最终，当我们准备好启用这个开关时，其中一个团队却因为无关原因把他们的服务回滚到了此前有 bug 的客户端版本，导致我们极力避免的那场宕机还是发生了。

对客户端库的任何改动都需要跨数十个服务进行复杂协调，这一过程被证明越来越脆弱、低效、容易酿成运维故障。为了减少未来部署中的这种运维扇出，我们决定把 Habitat 拆成独立的服务。

通过把存储逻辑解耦为独立服务，我们为部署、可观测性和平台增强建立了单一控制点。不必再管理碎片化的更新，我们可以集中实施改进，让每一款 OpenAI 产品立即受益。

集中式服务还为我们提供了一个单一咽喉点，用以提供最强的数据安全与隐私原语。Habitat 服务是我们集中实施访问控制策略、执行审计日志、并限制对 Azure Cosmos DB 等底层存储资源访问的地方。Habitat 在保护用户数据、防止来自外部、内部和智能体行为者的未授权访问方面发挥着关键作用。

## 大规模上线 Python 服务

我们知道需要服务，但当时还不想从 Python 迁走，哪怕 Python 作为服务会带来额外开销。与本地库执行相比，用 Python 编写高吞吐服务会增加网络延迟，并带来可观的 CPU 和内存扩展成本。此外，我们意识到 Python 的低效在 100 倍规模下不可接受，因此最终重写几乎是必然的。

不过，我们把这笔技术债视为一次战略性的主动背负。当时我们的首要目标不是成本或资源优化，而是为产品开发者扫清障碍、实现平台稳定。通过在短期内接受 Python 服务的性能取舍，我们得以优先处理更紧迫的挑战、确立核心 API，并建设稳健的基础设施。

我们还做了一个经过盘算的押注：我们自己编程模型的快速进步，会在未来简化技术路径。我们赌的是，等到需要完全迁离 Python 时，Codex 和 GPT 会让那次迁移变得可行。这一押注最终被证明是正确的。

用 Python 服务来运行 Habitat，在性能上并非最优，但却是必要的选择。Python 让我们行动迅速，但这并不意味着我们可以无所顾忌、接受显著变差的延迟。当一个普通用户请求会引发数百次数据库调用时，用户感受到的是最慢的那次数据库调用。我们发现，在这一规模上运行 Python 服务的主要挑战，就在于管理这些尾延迟。

### 追踪 asyncio 延迟

Asyncio 帮助 Python 并发执行 I/O 密集型工作负载，但对绕开 Python GIL、提供 CPU 并行无能为力。除了 I/O 重的请求代理，Habitat 还承担许多 CPU 重的职责和后台任务：路由、压缩、加密、校验和计算、下游健康检查、请求影子化（request shadowing）和请求对冲（hedging）。

服务中有这么多 CPU 重的负载和后台任务，asyncio 调度延迟很容易主导请求的尾延迟。在为服务首次上线做调优之前，我们在 p99 及以上延迟请求的追踪中看到：尽管下游存储响应很快，请求却经常卡住，等待负责的协程被重新调度来解析响应。

对 OpenAI 的 Python 服务而言，我们发现除了测量内存、CPU、网络和磁盘使用等标准的利用率与饱和度指标之外，还必须监控 asyncio 事件循环及其繁忙程度，并据此进行调优。

通过周期性地调度后台任务、并记录预期与实际执行时间之间的差值，我们能够实时、经验性地测量事件循环调度延迟。在高利用率、昂贵任务很多的情况下，每个进程哪怕只有中等数量的并发请求，也足以产生显著的调度抖动，高达数百毫秒，某些边缘情况下可达数秒。

因此，我们选择让每个进程只服务少量并发请求，转而大规模横向扩展 Python 工作进程的数量。

### 降低功能开关配置中的尾延迟

在服务首次上线时，我们通过线上服务的 CPU 剖析发现了 asyncio 高延迟（进而导致高尾延迟）的一个根因：通过 Statsig（一个管理功能开关、也可用于运行 A/B 测试等用途的工具）周期性地对功能开关配置做 JSON 解析。

默认情况下，Statsig 被配置为每分钟无抖动地轮询刷新配置，而这份配置包含了每个服务的所有生产规则。另一方面，我们在架构上决定每个 pod 最多运行 8 个 Python 进程，以推高 CPU 使用率并提供更低延迟。两者叠加意味着，每一分钟每个 pod 都会有某个时刻，所有工作进程都停下正在处理的请求，把 CPU 周期花在解析一个巨大的配置文件上。

一旦 CPU 剖析帮助我们找到了问题的根因，修复就很直接：部署更小、更有针对性的配置，拉长刷新间隔，并为这类后台任务加入一些抖动（jitter）。

### 负载均衡与连接池管理

为了保持较低的 asyncio 延迟，在服务器进程之间保持良好的请求负载均衡同样关键；如果缺乏调优，连接池化最终可能与这一目标背道而驰。

在客户端连接池化的情况下，一个发起大量并发请求的客户端进程可能只建立少数几条服务器连接，结果把它全部负载都只发给少数几个进程。在调整负载均衡方式之前，我们服务的利用率差异很大，一些尾部进程承受的并发请求数达到平均水平的 5-10 倍。

我们是在一次偶然的事故中发现这一点的：即便已经停掉了正在压垮我们服务一部分的客户端，仍有一小部分进程在突发流量过去很久之后依然处于降级状态。实际上，我们注意到这些进程经历了失控式劣化，收到的请求越来越多，直到我们重启它们。一旦某个 pod 过载，某种行为就会把更多流量钉死在这个过载的 pod 上。这是我们一些队友在以往工作中非常熟悉的一类故障：[亚稳态故障](https://engineering.fb.com/2014/11/14/production-engineering/solving-the-mystery-of-link-imbalance-a-metastable-failure-state-at-scale/)（metastable failure）。

我们怀疑连接池是罪魁祸首，并通过限制最大连接复用时长来验证这一怀疑——这确实限制了劣化，证实了我们的排查方向。进一步调查发现，Python 的 aiohttp TCPConnector 默认采用 LIFO 连接复用：最近归还的连接会被选中处理下一个请求。这通常是个合理的默认值：复用最近的连接，可以让为应对突发流量而多建的连接逐渐空闲超时，降低维护多余连接的开销。但在我们的场景中，它制造了一场亚稳态故障。请求突发期间，发往较慢、过载服务器的请求更晚把连接归还给池，因而被后续请求更频繁地选中，逐渐把更多流量集中到本已苦苦挣扎的 pod 上。把连接池改成 FIFO 复用打破了这一反馈回路，甚至还降低了我们稳态下的请求方差。

如今，我们在整个 OpenAI 基础设施中主要依赖 Istio 和 Envoy 提供连接池化和更好的服务器负载感知均衡策略，从而完全避开这个问题。

### 避免冲垮下游资源

为低 asyncio 延迟做调优、并运行如此多的 Python 进程，带来一个副作用：很容易用海量连接压垮下游依赖（即所谓「惊群」效应，thundering herd）。

一次例行的日常部署——如果不刻意放缓节奏——就可能因连接反复建立与关闭而造成明显的 CPU 搅动；一次连接泄漏也可能因灌满 NAT 网关而拖垮网络。这些问题对其他服务来说也不罕见，但进程数量多出一个数量级显著降低了触发阈值，常常仅凭纯吞吐量就把客户端在稳定状态下并不预期需要处理的网络相关资源打到饱和。

我们还依赖 Envoy 来最大化连接扇入。我们用它把 Python 的 HTTP/1 连接升级为 HTTP/2 以利用多路复用，然后对这些连接做池化并延长连接寿命。Envoy 还为我们提供了一个中心位置来实现速率限制和熔断器——若放在每个独立的 Python 进程里，它们的效果会大打折扣。

## 为什么 Habitat 刻意做得更少

Python 之所以能被我们扩展到今天这一步，一个原因是 Habitat 克制的 API，它让每个请求的成本可预测。Habitat 不允许客户端构造任意 SQL 查询——那可能造成大范围表扫描或跨多表连接——而是暴露一个简单的 NoSQL API。缺少一个强大的 API，是 Habitat 设计中明确的取舍。

我们的目标是针对简单、可预测、工作量恒定的请求做优化。根据我们的经验，这类系统扩展起来容易得多，也不容易出错或被误用。扇出不可预测的请求在运维上是危险的：它们让隔离和负载均衡复杂化，并引入难以扩展的延迟断崖，无论对服务还是对它的客户端都是如此。

在我们迁移到 Habitat 和 Azure Cosmos DB 之前，OpenAI 的大部分在线数据存储在 Postgres 上。当时，审查所有查询与 schema 变更、确保其行为良好且作用于有索引的数据，然后才上线到生产环境，还是可行的。随着团队和产品的增长，这迅速变得无法管理，并频繁成为事故的起因——热路径上一个昂贵的新查询就可能拖垮整个数据库。

这里的问题在于成本不对称：写出昂贵、难以执行的 SQL 查询，既廉价又容易。在 Habitat 中，我们避免这一点，让昂贵的查询在客户端侧显露无遗。Habitat 中不存在可能使其过载的无边界查询；复杂的连接和图遍历则需要产品团队自己承担一部分繁重工作，这从整体上有助于大家优化出更高效的设计。

Habitat 暴露一个围绕客户端自定义的对象（object）与边（edge）类型建模的 NoSQL API，其灵感来自 [TAO](https://www.usenix.org/system/files/conference/atc13/atc13-bronson.pdf)。客户端预定义对象、边以及它们之间的关联方式，但不定义各类型的具体内容。由此形成的关系类似一张图，但除了查询特定对象的直接边之外，Habitat 本身并不支持典型的图遍历查询。

我们对这张图做分区，使每个对象及其相应的边共置于一个存储级分区中，但我们并未在数据库层面刻意把对象与其边所指向的远端对象放在一起。结果是，这一模型很容易为水平扩展而分区，但图遍历的效率不高，因为对象之间的任何一跳都可能需要从位于不同区域的两个完全不同的 Azure Cosmos DB 账户中取数。

对于有更复杂查询需求的客户端，我们确实提供了一个通过 Rockset 暴露的 Habitat 离线二级视图。我们使用变更数据捕获（CDC）把在线存储的变更以近实时的方式流式传送到相互隔离的 Rockset 实例。每个客户端团队负责为自己的复杂查询需求扩展自己的 Rockset 实例。

这种 Rockset 供给方式给客户端带来了额外摩擦，但我们认为这是当下正确的取舍：让简单查询成为默认，同时为需要复杂查询的人提供一个逃生舱口。这一设计把我们的在线存储与读密集的分析和搜索工作负载隔离开来。

## 从 Python 迁移到 Rust

把 Python 重写推迟一年，让我们能够在超高速增长期专注于更紧迫、更具影响力的挑战。随着平台成熟、增长继续加速，而且按核数计它已是 OpenAI 第二大的服务（按 Envoy 足迹计是第四大），终于到了告别 Python 的时候。在巅峰期，Python 版本帮助我们实现每秒服务超过 2,000 万次请求。

在 2026 年第二季度，仅凭 2 名工程师、Codex 和 GPT‑5.5，我们就用 Rust 重写了整个服务。这个新的 Rust 服务现在处理着我们 95% 的生产请求；未来几周内我们将彻底弃用 Python。我们的数据显示，Rust 服务的 CPU 效率是 Python 版本的 6 倍、内存效率是 15 倍，平均延迟和尾延迟都显著更低。我们计划在未来的博客中分享更多经验。
