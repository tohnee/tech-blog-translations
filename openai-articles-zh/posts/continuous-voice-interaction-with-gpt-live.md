# 我们如何在六个月内构建一套响应灵敏的语音 AI 实时系统

> 原文：[How we built a realtime system for responsive voice AI in six months](https://openai.com/index/continuous-voice-interaction-with-gpt-live/) · OpenAI 博客

对语音 AI 而言，判断什么时候该说话，比听起来要难得多。人类说话者能在不到一秒的时间内毫不费力地完成话轮交接，但以往的语音 AI 系统却跟不上这种节奏。它们的轮次制（turn-based）架构依赖一种被称为话轮检测器（turn detector）的小模型，而这些模型的处境相当尴尬：猜得太早，用户会被打断；猜得太晚，响应又显得迟钝。只有等检测器做出决定之后，那个庞大得多的 LLM 才能开始工作。

[GPT‑Live](https://openai.com/index/introducing-gpt-live/) 是我们的第三代语音系统，它把话轮检测器从音频通路上移除了。它的语音模型是全双工（full-duplex）的，也就是说可以同时听和说。这就免去了单独检测器的必要，让对话感觉更即时、更自然。当需要更深入的推理或工具调用时，GPT‑Live 还可以咨询我们的前沿模型（例如 GPT-5.5），而不打断对话的流畅进行。这些能力结合在一起，让 GPT‑Live 拥有了前所未有的「对话响应速度 + 智能水平」的组合。

要大规模交付这种体验，需要一套针对低延迟优化过的全新系统架构。与典型的请求-响应式推理不同，我们的系统把传入的音频流式送入语音模型，同时把输出的语音流式回传给用户，而将委派（delegation）放在一条单独的异步路径上处理。在过去六个月里，我们重构了模型推理、上下文管理和媒体传输，让语音从头到尾顺畅流动。

这套架构还在核心语音通路与应用逻辑之间划出了一条清晰的边界，使应用行为的定制变得容易，且不影响响应速度。这一基础正在支撑 ChatGPT 语音中日益丰富的能力，包括刚上线的、在 ChatGPT 桌面应用中控制你的电脑并协调你的智能体的功能。

在本文中，我们将解释为什么早期的轮次制系统无法满足我们的需求，以及我们如何在新系统的每一层都为响应速度做出工程设计。我们将介绍有状态推理（stateful inference）、动态上下文管理、异步委派以及协议层优化——所有这些协同配合，让 GPT‑Live 真正名副其实地 *live*。

## 从轮次交接转向流式

早期的语音架构继承了文本 LLM 的轮次制特性，只不过每个轮次表示为离散的音频块（audio blob）而非文本。在级联（cascaded）系统中，语音转文本、LLM、文本转语音依次串行运行。这种串行处理增加了延迟，并且忽略了语气、语速等线索。

语音到语音（speech-to-speech）模型通过直接处理音频改进了这一方法。训练模型原生地理解和生成语音，使其能够保留转写过程中丢失的细节，并更快地做出响应。但系统仍然依赖话轮检测器来决定何时可以开始推理。模型承担了交互中更多的部分，但交互本身依然是轮次制的。

GPT‑Live 让语音模型掌控对话：音频流入和流出模型，而更深入的推理与工具调用则异步进行。系统的首要任务是维持一个不间断的媒体循环。其他工作，比如调用前沿模型、持久化对话，都发生在实时通路之外。

## 实现连续推理

让这个媒体循环保持不间断并不总是那么简单。传输、处理或推理中的任何延迟都可能变成听得到的停顿或杂音。以前的轮次制系统尚可容忍音频块到达时间的些许波动，但实时媒体系统必须按计划送达每一帧音频。

此前在 ChatGPT 语音和 Realtime API 上的工作为我们打下了重要基础。我们已经[重建了语音基础设施](https://openai.com/index/delivering-low-latency-voice-ai-at-scale/)，能够以更低、更可预测的延迟将音频和视频直接流入流出我们的系统。GPT‑Live 在这一设计上更进一步，通过一套为连续对话打造的新型有状态推理系统，把媒体一路流式送达模型。

不过，流式推理只是解决方案的一部分。要让它很好地在生产环境中运转，我们还必须确保音频从客户端到推理栈的可靠送达，并应对有状态（statefulness）带来的种种挑战。

### 让媒体快速流动

我们早期做出的一个决策，是明确地把媒体流与应用和业务逻辑分离。音频在客户端与语音模型之间经由一条专用的快速通路流动；委派、工具调用和其他应用工作则在异步 RPC 边界之后进行。一次缓慢的工具调用或后端服务可以推迟它自己的结果，却无法让媒体的流动停滞。

这种分离也为系统提供了清晰的定制边界。应用可以更换自己的工具、策略和后端行为，而不会影响负责让音频持续流动的媒体前端。实时通路保持精简、可预测，专注于必须实时完成的工作。

我们用 Go 编写了媒体前端和推理逻辑，取代了此前基于 Python `asyncio` 的实现。这显著改善了帧传输的流畅度——新系统的 p95 达到了旧系统 p50 的水平。

传输基础由 WebRTC 提供。它专为低延迟媒体而设计，能够在丢包、时钟漂移和客户端连接变化的情况下继续运行。如果数据包迟到，WebRTC 可以细微地拉伸音频以避免出现空隙，然后再短暂加速播放，追回实时进度。

通过将整个系统中的缓冲与阻塞降到最低，我们得以提供人类对对话所期望的亚秒级响应速度。

### 让（有状态的）对话持续进行

有状态推理有它自己的运维权衡。一个语音会话可能会长时间保持活跃，但它的上下文会持续增长，而模型实例又会根据需求不断地启停。

为了解决这些问题，我们构建了一套跨模型实例的无缝交接机制。当需要切换时，我们可以在现有实例旁边预热一个替代实例，用当前会话上下文对其进行预填充（prefill），对两者并行运行推理，并在新实例完全就绪后切换过去。

同一基础机制还支持动态上下文压缩（compaction）。随着对话持续进行，累积的上下文最终可能超过模型的上下文上限。压缩可以把上下文缩减到上限以内，但这一操作需要时间。而且由于它会改变过去的上下文，也会使模型的键值（KV）缓存失效——该缓存存储着此前处理过的 token 的注意力键与值。重建这一状态需要一次新的预填充，从而引入额外的延迟。

因此，我们把压缩也当作一次受管理的切换来处理。在原模型实例继续聊天的同时，系统对上下文进行压缩，并准备好一个装载了新上下文的替代模型实例。一旦该实例就绪，我们就能在媒体完全不中断的情况下切换过去。这样，系统就能支持长时间运行的通话，并在必要时随时压缩。

这些繁重的工作都被挡在实时通路之外，因此即使在交接过程中，对话也不会漏掉一拍。

## 不阻塞对话的委派

GPT‑Live 能够调用现有的前沿模型，这赋予了它强大的能力，实际上把「说话」与更深入的「思考」解耦开来。但要让这种双模型架构感觉像一个系统，需要解决两个相互关联的工程问题。

### 更深入工作的委派

GPT-Live 提供快速、自然的响应，而 GPT-5.5 在后台处理搜索

首先，结果必须足够快地返回，才能在正在进行的交流中派上用场，因此我们必须把从路由、提示词处理到推理和工具调用的整条委派路径上的延迟降到最低。与此同时，产品中其他系统仍然需要离散的消息，所以我们还得把正在进行的对话表示成它们能理解的形式。

## 让委派快到感觉自然

当一次委派被派发出去时，我们优化的目标是：前沿模型多快能为对话产出有用的东西。在前沿模型进行推理或使用工具期间，语音模型可以短暂地维持交流不中断，但它无法掩盖任意缓慢的响应。因此，我们把完整的委派循环——路由、提示词处理、推理和工具调用——都纳入响应速度的预算之中。

第一项优化是在委派请求发出之前，就把前沿模型及其所需的工具准备好。当语音会话开始时，应用服务器会为前沿模型创建一个推理会话，并用初始对话上下文进行预填充，确保在第一个委派请求到来之前，提示词已被完整处理。

然后，在整个语音对话期间我们保持该推理会话可用，并对后续请求使用稳定的会话亲和性（session affinity）。结合提示词缓存（prompt caching），这些技术在改善延迟的同时，也让 worker 故障依然易于恢复。

推理力度（reasoning effort）、输出上限、工具模式（tool schema）以及模型与工具之间的往返次数，同样会影响对话多快能收到有用的结果，我们调整了这些杠杆来获得更快的响应。通过把委派路径上所需的工作降到最低，语音模型得以快速吸收前沿模型的产出。

### 从连续语音中还原出离散轮次

尽管语音模型处理的是连续的语音流，但它周围的许多系统仍以用户轮和助手轮为单位运作，包括 ChatGPT 的对话 UI 以及我们的分析、安全基础设施的一部分。因此，应用服务器要把这种交叠的、偶尔含混的对话梳理成离散的消息。

随着音频不断到达，服务器利用部分转写（partial transcripts）和时序信号来推断当前是哪位发言者在说话，并构建一个消息队列。最新的消息处于暂定状态：随着更多语音的到来，其文本、时序和发言者归属都可能改变。一旦某位发言者持续把持话轮足够久、足以让归属判定可靠，服务器就会将对应消息定稿。

发言者交叠让问题更加复杂。用户说话时助手给出的简短附和（比如「嗯哼」「好的」）不一定需要单独成一条消息，但助手中途实质性的插话往往应该如此。同样，即使用户中途插话，我们也会优先保证所展示的助手回复的连贯性。

任何切分策略都在新鲜度与确定性之间做取舍。过早定稿会产生碎片化的历史和不稳定的顺序；等待太久则会拖延转写文本以及依赖它的功能。因此，系统维护着对话的两个相关视图：一个关于当前状态的推测性视图，以及一份关于实际所说内容的权威记录。应用 UI 中的对话视图可以处理更新，因此使用推测性视图；而写入分析流水线的日志则需要最终转写文本。

这样一来，ChatGPT 的其他部分就获得了一个关于这段交流的稳定视图，同时不必把轮次交接强加给实时的语音通路。

## 用更快的协议启动会话

响应速度从用户点击按钮的那一刻就开始了。对于 GPT‑Live，系统必须先建立媒体通路、开始把音频送入模型，对话才能开始。这使得启动序列的每一环都处在关键路径上。

如前所述，WebRTC 提供了坚实的实时基础，但启动一个原生的 WebRTC 会话需要数量惊人的协议握手和网络往返。WebRTC 诞生于 QUIC 等后续协议所体现的「最小化往返」理念兴起之前，因此它的底层协议在一起使用时有时会重复劳动。例如，每个协议都自带一套防 DoS 机制，即便在整个 WebRTC 栈的语境下并不需要。

我们对整个协议栈进行了分析，并开发了 WebRTC Abridged Roundtrip Protocol（[WARP](https://datatracker.ietf.org/doc/draft-uberti-tsvwg-warp/)），把媒体与数据的启动从六次网络往返缩减到一次。WARP 通过一组向后兼容的协议改进实现这一点：让 DTLS 握手搭载在 ICE 之上（[SPED](https://datatracker.ietf.org/doc/draft-hancke-webrtc-sped/)）、使用更快的 [DTLS 1.3](https://www.rfc-editor.org/rfc/rfc9147.html) 握手、预先协商 SCTP 握手（[SNAP](https://datatracker.ietf.org/doc/draft-hancke-tsvwg-snap/)），以及预先协商数据通道而不再使用 [DCEP](https://www.rfc-editor.org/rfc/rfc8832.html)。

我们与 WebRTC 社区的合作者一起，把 WARP 设计成一组开放规范，让更广泛的生态能够从这项工作中受益。我们正在通过 IETF 的 TSVWG 工作组推进这些提案，libwebrtc 和 Pion 都已经加入了对 WARP 的支持，其他 WebRTC 实现的相关工作也在进行中。

优化完媒体握手之后，还剩下一个显眼的延迟：在 WebRTC 建立连接之前，用于交换 SDP 参数的信令交互。为了把这次交互从关键路径上移走，我们开发了我们称之为 Instant Connect 的机制。它提前协商这些参数，不预留服务器容量，也不需要对现有 WebRTC 实现做任何改动。

Instant Connect 与标准信令流程并行运行。如果预先协商的参数有效，服务器可以在第一个媒体包到达时实例化会话；如果参数过期或无效，标准信令流程也已经在进行中，客户端可以无缝回退，不产生额外延迟。

Instant Connect 与 WARP 合在一起，大幅缩短了从用户意图到媒体实时流动的时间。SDP 交换移出关键路径、WARP 压缩了传输握手之后，客户端现在只需一个 UDP 包就能启动会话。服务器可以立即响应，让系统的其余部分开始做用户真正关心的事：倾听与回应。

## 用真实数据在生产环境中安全地测试 GPT‑Live

一个系统在纸面上看起来很快，在真实语音流量下仍可能卡顿。在让 GPT‑Live 与用户聊天之前，我们进行了一次静默测试：把一小部分逐渐增加的生产 ChatGPT 语音会话同时路由到既有的 Advanced Voice Mode 体验和我们的新系统。Advanced Voice Mode 照常为用户服务，而影子路径以只读模式运行推理。这使系统接触到了真实的客户端、网络、会话时长和地理分布，却不改变用户听到的东西。

最早的教训之一是：容量不能被简化为 GPU 吞吐量。语音会话会长时间保持打开并持续发送帧，因此 CPU 侧的流处理器、队列和网络路径必须与推理一同扩展。在真实负载下，一个支撑组件比我们负载测试预估的更早饱和，导致推理请求堆积、延迟叠加。我们把容量问题从「*一块 GPU 能处理多少请求？*」改成了「*在保证每一帧按时送达的前提下，系统能支撑多少并发会话？*」

这次测试也让地理位置成为了一等公民的考量。把会话路由到远处的容量，会在启动和流式传输的多个环节增加延迟。我们开始把模型灰度发布与区域容量、流量调度配置放在一起验证，然后按来源地域分解延迟。把推理搬到离用户更近的地方确实有帮助，但也印证了一个更普遍的教训：端到端的响应速度取决于路径上的每一个服务，而不仅仅是模型服务器。

还有一些故障只在真实的会话生命周期中才会出现。长时间运行的会话暴露了内存与持久化方面的压力；重连会考验压缩与状态恢复；普通的客户端断开则暴露出关闭握手过程中的竞态。这些问题在短时负载测试中很少现身，因为它们依赖于时间、累积的状态以及跨服务边界的行为。

最后，生产测试迫使我们改进了可观测性和灰度控制。我们发现有些指标把不同来源的延迟混为一谈，有些仪表盘的聚合值掩盖了个别不健康的引擎，测试环境与部署环境之间还存在配置漂移。为此，我们增加了更细粒度的遥测、针对已知良好配置的校验、分阶段的放量，以及快速隔离或禁用单条路径的能力。静默测试成了一次提前的上线演练——不仅检验系统能承载多少流量，也检验我们能多快地检测、遏制故障并从中恢复。

## 从客户端到模型的全程响应

把 GPT‑Live 做到 ChatGPT 的规模，需要一套围绕一个基本原则构建的全新系统：语音必须持续流动。流式推理让全双工模型不断有音频可用；专用媒体通路确保帧的可靠送达；异步委派让更深入的思考并行进行；经过优化的传输让体验一路到用户端都保持响应。

GPT‑Live 背后的架构正在成为一个更广泛的实时交互平台。它支撑着 ChatGPT 语音从对话向智能体协作扩展，并将成为即将推出的 GPT‑Live API 的底层。假以时日，它将让语音体验跨越更多设备、应用和模态，同时不牺牲让语音对话显得「活」的那种即时性。
