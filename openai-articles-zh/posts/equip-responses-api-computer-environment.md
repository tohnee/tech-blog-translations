# 从模型到智能体：为 Responses API 装备计算机环境

> 原文：[From model to agent: Equipping the Responses API with a computer environment](https://openai.com/index/equip-responses-api-computer-environment/) · OpenAI 博客

我们正处在一场转变之中：从使用擅长特定任务的模型，转向使用能够处理复杂工作流的智能体。仅通过提示模型，你只能触及训练得来的智能；而给模型一个计算机环境，则可以实现广泛得多的用例，比如运行服务、从 API 请求数据，或生成更有用的产物（如电子表格或报告）。

当你尝试构建智能体时，一些实际问题会浮现：中间文件放在哪里、如何避免把大表格粘贴进提示词、如何在不制造安全难题的前提下给工作流网络访问权限，以及如何处理超时和重试而不必自己搭建一套工作流系统。

我们没有把构建执行环境的负担交给开发者，而是自己构建了必要的组件，为 [Responses API](https://developers.openai.com/api/docs/guides/migrate-to-responses) 装备上计算机环境，以可靠地执行真实世界的任务。

OpenAI 的 Responses API，连同 shell 工具和托管容器工作区，正是为解决这些实际问题而设计的。模型提出步骤和命令；平台在一个隔离的环境中执行它们——该环境带有用于输入输出的文件系统、可选的结构化存储（如 SQLite），以及受限的网络访问。

在本文中，我们将拆解我们如何为智能体构建计算机环境，并分享一些早期经验，说明如何利用它打造更快、更可复现、更安全的生产工作流。

## Shell 工具

一个好的智能体工作流始于一个紧凑的执行循环：模型提出一个动作（如读取文件或通过 API 获取数据），平台执行它，结果再输入到下一步。我们将从 shell 工具讲起——这是观察这个循环运转的最简单方式——然后介绍容器工作区、网络、可复用技能和上下文压缩。

要理解 shell 工具，先了解语言模型一般如何使用工具会有所帮助：去做诸如调用函数或与计算机交互之类的事情。在训练期间，模型会看到逐步展示的工具使用示例及其产生的效果。这帮助模型学会决定何时使用工具以及如何使用。当我们说「使用工具」时，模型实际上只是提出一次工具调用。它无法自己执行这次调用。

shell 工具让模型的能力大幅增强：它通过命令行与计算机交互，执行从搜索文本到在你的计算机上发送 API 请求等各类任务。我们的 shell 工具构建在大家熟悉的 Unix 工具之上，`grep`、`curl`、`awk` 等实用程序开箱即用，能做你期望的任何事情。

与我们现有的只能执行 Python 的代码解释器相比，shell 工具支持广泛得多的用例，比如运行 Go 或 Java 程序、启动 NodeJS 服务器。这种灵活性让模型能够完成复杂的智能体任务。

## 编排智能体循环

模型自己只能提出 shell 命令，那这些命令是如何执行的呢？我们需要一个编排器（orchestrator）来获取模型输出、调用工具，并把工具响应循环地传回模型，直到任务完成。

Responses API 是开发者与 OpenAI 模型交互的方式。当与自定义工具一起使用时，Responses API 会把控制权交还给客户端，客户端需要自己的执行框架（harness）来运行这些工具。不过，这个 API 也可以开箱即用地在模型与托管工具之间进行编排。

当 Responses API 收到一个提示词时，它会组装模型上下文：用户提示词、先前的会话状态以及工具指令。要让 shell 执行生效，提示词必须提到使用 shell 工具*，*并且所选模型必须经过「提出 shell 命令」的训练——GPT‑5.2 及之后的模型都为此受过训练。在具备所有这些上下文后，模型决定下一个动作。如果它选择 shell 执行，就会向 Responses API 服务返回一条或多条 shell 命令。API 服务把这些命令转发给容器运行时，流式取回 shell 输出，并在下一次请求的上下文中把它喂给模型。模型随后可以检查结果、发出后续命令，或产出最终答案。Responses API 不断重复这个循环，直到模型返回一个不再附带额外 shell 命令的补全（completion）。

当 Responses API 执行一条 shell 命令时，它会与容器服务维持一条流式连接。随着输出不断产生，API 近实时地把输出转达给模型，让模型可以决定是等待更多输出、运行另一条命令，还是进入最终回复。

模型可以在一步中提出多条 shell 命令，Responses API 可以使用独立的容器会话并发执行它们。每个会话独立地流式输出，API 再把这些流多路复用回结构化的工具输出作为上下文。换句话说，智能体循环可以并行化工作，比如搜索文件、获取数据、验证中间结果。

当命令涉及文件操作或数据处理时，shell 输出可能非常庞大，在不增加有用信号的情况下消耗上下文预算。为了控制这一点，模型会为每条命令指定一个输出上限。Responses API 强制执行该上限，并返回一个有界结果：保留输出的开头和结尾，同时标记被省略的内容。例如，你可以把输出限制在 1,000 个字符，并保留开头与结尾：

`text at the beginning ... 1000 chars truncated ... text at the end`

并发执行与有界输出合在一起，让智能体循环既快速又节省上下文，模型得以持续对相关结果进行推理，而不会被原始终端日志淹没。

## 当上下文窗口满时：压缩

智能体循环的一个潜在问题是任务可能运行很长时间。长时间运行的任务会填满上下文窗口，而上下文窗口对于跨轮次、跨智能体提供上下文非常重要。设想一个智能体调用技能、收到响应、再添加工具调用和推理摘要——有限的上下文窗口很快就被填满。为了避免智能体持续运行时丢失重要上下文，我们需要一种保留关键细节、剔除无关内容的方法。我们没有要求开发者设计和维护自定义的摘要或状态携带系统，而是在 Responses API 中加入了原生压缩（compaction），其设计旨在与模型的行为方式及其训练方式保持一致。

我们最新的模型经过训练，能够分析先前的会话状态，并产出一个压缩项（compaction item），以加密的、节省 token 的表示保留关键的先前状态。压缩之后，下一个上下文窗口由这个压缩项和先前窗口的高价值部分组成。这使得工作流能够跨越窗口边界连贯地继续，即便是在延长的多步骤、工具驱动的会话中也是如此。[Codex 依赖这一机制](https://openai.com/index/unrolling-the-codex-agent-loop/)来支撑长时间运行的编程任务和迭代式工具执行，而不损失质量。

压缩既可以内置于服务端，也可以通过独立的 `/compact` 端点使用。服务端压缩让你配置一个阈值，由系统自动处理压缩时机，免去了复杂的客户端逻辑。它允许一个稍大的有效输入上下文窗口，以容忍压缩前一刻出现的小幅超限，因此接近上限的请求仍能被处理并压缩，而不是被拒绝。随着模型训练的演进，原生压缩方案也会随每一次 OpenAI 模型发布同步演进。

Codex 一方面作为早期用户，一边帮助我们构建了压缩系统。当一个 Codex 实例遇到压缩错误时，我们会再起一个实例来调查。结果是，Codex 仅通过处理这个问题就得到了一个原生的、有效的压缩系统。Codex 这种检查并完善自身的能力，已经成为在 OpenAI 工作特别有趣的一部分。大多数工具只要求用户学习如何使用它们；而 Codex 与我们一起学习。

## 容器上下文

现在来谈谈状态与资源。容器不仅是运行命令的场所，也是模型的工作上下文。在容器内，模型可以读取文件、查询数据库，并在网络策略控制下访问外部系统。

#### 文件系统

容器上下文的第一部分是用于上传、组织和管理资源的文件系统。我们构建了[容器与文件](https://developers.openai.com/api/reference/resources/containers) API，为模型提供一张可用数据的地图，帮助它选择有针对性的文件操作，而不是进行宽泛而嘈杂的扫描。

一个常见的反模式是把所有输入直接塞进提示词上下文。随着输入增长，过度填充提示词既昂贵，也让模型难以驾驭。更好的模式是把资源放置在容器文件系统中，让模型决定用 shell 命令打开、解析或转换什么。与人类一样，面对组织有序的信息，模型工作得更好。

#### 数据库

容器上下文的第二部分是数据库。在很多情况下，我们建议开发者把结构化数据以 SQLite 的形式存入数据库并进行查询。例如，与其把整张电子表格复制进提示词，不如给模型一份表描述——有哪些列、各列含义是什么——然后让它自己拉取所需的行。

例如，如果你问「本季度哪些产品的销售额在下滑？」，模型可以只查询相关行，而不必扫描整张电子表格。这样更快、更便宜，对更大的数据集也更具可扩展性。

#### 网络访问

容器上下文的第三部分是网络访问，这是智能体工作负载的重要组成部分。智能体工作流可能需要获取实时数据、调用外部 API 或安装软件包。与此同时，给容器不受限制的互联网访问可能有风险：它可能把信息暴露给外部网站、无意中触及敏感的内部或第三方系统，或让凭据泄露和数据外泄更难防范。

为了在不限制智能体实用性的前提下解决这些顾虑，我们让托管容器使用 sidecar 出口代理。所有出站网络请求都流经一个集中式策略层，该策略层实施允许列表和访问控制，同时保持流量可观测。对于凭据，我们在出口处使用按域名限定范围的秘密注入（secret injection）。模型和容器只会看到占位符，原始秘密值保持在模型可见上下文之外，只对获得批准的目的地生效。这降低了泄露风险，同时仍能进行经过身份验证的外部调用。

## 智能体技能

Shell 命令很强大，但许多任务会重复相同的多步骤模式。智能体每次运行都必须重新发现工作流——重新规划、重新发出命令、重新学习惯例——导致结果不一致、执行被浪费。[智能体技能](https://agentskills.io/home)（Agent skills）把这些模式打包成可复用、可组合的构建块。具体来说，一个技能是一个文件夹包，包含「[SKILL.md](http://skill.md)」（内含元数据和指令）以及任何支持性资源，如 API 规范和 UI 资产。

这种结构与我们前面描述的运行时架构自然对应。容器提供持久化文件和执行上下文，shell 工具提供执行接口。两者就位后，模型可以在需要时用 shell 命令（`ls`、`cat` 等）发现技能文件、解读指令，并在同一个智能体循环中运行技能脚本。

我们提供 [API](https://developers.openai.com/api/reference/resources/skills) 来管理 OpenAI 平台上的技能。开发者把技能文件夹作为带版本的包上传并存储，之后可以按技能 ID 取回。在把提示词发送给模型之前，Responses API 会加载技能并将其纳入模型上下文。这个序列是确定性的：

1. 获取技能元数据，包括名称和描述。
2. 获取技能包，复制到容器中并解包。
3. 用技能元数据和容器路径更新模型上下文。

在判断某个技能是否相关时，模型会渐进地探索其指令，并通过容器中的 shell 命令执行其脚本。

## 智能体是如何炼成的

把所有部分拼在一起：*Responses API* 提供编排，*shell 工具*提供可执行动作，*托管容器*提供持久的运行时上下文，*技能*叠加可复用的工作流逻辑，而*压缩*让智能体能带着所需的上下文长时间运行。

有了这些原语，一个提示词就能展开成端到端的工作流：发现合适的技能、获取数据、把它转换为本地结构化状态、高效查询，并生成持久的产物。
