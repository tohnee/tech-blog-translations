# OpenAI 如何大规模交付低延迟语音 AI

> 原文：[How OpenAI delivers low-latency voice AI at scale](https://openai.com/index/delivering-low-latency-voice-ai-at-scale/) · OpenAI 博客

语音 AI 只有在对话以语音的速度推进时才显得自然。一旦网络拖了后腿，人们立刻就会听到尴尬的停顿、被截断的打断，或延迟的插话（barge-in）。这对 ChatGPT 语音、对使用 Realtime API 构建的开发者、对在交互式工作流中工作的智能体，以及对需要在用户还在说话时就开始处理音频的模型来说都很重要。

在 OpenAI 的规模下，这意味着三项具体要求：

- 面向超过 9 亿周活跃用户的全球覆盖
- 快速的连接建立，让用户在会话一开始就能开口说话
- 低且稳定的媒体往返时间，配合低抖动和低丢包，让话轮交接感觉干脆利落

OpenAI 负责实时 AI 交互的团队最近重构了我们的 WebRTC 栈，以解决在大规模下开始相互冲突的三个约束：「每会话一端口」的媒体终结方式不太适合 OpenAI 的基础设施，有状态的 ICE（Interactive Connectivity Establishment，交互式连接建立）和 DTLS（Datagram Transport Layer Security，数据报传输层安全）会话需要稳定的归属，而全局路由必须保持较低的首跳延迟。在本文中，我们将带你了解我们构建的 *中继（relay）+ 收发器（transceiver）* 分离架构：它为客户端保留了标准的 WebRTC 行为，同时改变了数据包在 OpenAI 基础设施内部的路由方式。

## WebRTC 让我们得以打造实时 AI 产品

WebRTC 是一个开放标准，用于在浏览器、移动应用和服务器之间传输低延迟的音频、视频和数据。它常与点对点通话联系在一起，但它也是客户端到服务器实时系统的实用基础，因为它把交互式媒体中困难的部分标准化了：用于连接建立和 NAT（Network Address Translation，网络地址转换）穿越的 ICE、用于加密传输的 DTLS 和 SRTP（Secure Real-time Transport Protocol，安全实时传输协议）、用于压缩和解码音频的编解码器协商、用于质量控制的 RTCP（Real-time Transport Control Protocol，实时传输控制协议），以及回声消除、抖动缓冲等客户端特性。

这种标准化对 AI 产品很重要。如果没有 WebRTC，每个客户端都需要为如何跨越 NAT 建立连接、如何加密媒体、如何协商编解码器（为传输和解压而选定的 coder-decoder）以及如何适应不断变化的网络条件，给出各自的答案。有了 WebRTC，我们就能在一个已在各大浏览器和移动平台上实现过的协议栈之上构建，把自己的工作聚焦在连接实时媒体与模型的基础设施上。

我们也构建在 WebRTC 生态本身之上，包括成熟的开源实现，以及让浏览器、移动应用和服务器保持互操作的标准工作。Justin Uberti（WebRTC 最初的设计者之一）和 Sean DuBois（Pion 的创造者和维护者）打下的基础性工作，让我们这样的团队能够构建在久经考验的媒体基础设施之上，而不必重新发明底层的传输、加密和拥塞控制行为。我们很幸运，Justin 和 Sean 现在都是 OpenAI 的同事，正帮助我们引导 WebRTC 与实时 AI 更紧密地结合。

对 AI 而言，最重要的特性是音频以连续流的方式到达。一个语音智能体可以在用户还在说话时就开始转写、推理、调用工具或生成语音，而不必等整段音频上传完毕。这就是「感觉像在对话」的系统与「感觉像按住说话的对讲机」之间的区别。

## 选择媒体架构

选定 WebRTC 之后，下一个问题是在哪里终结它（即在哪里接受并持有 WebRTC 连接——例如在边缘），以及如何把这些会话连接到推理后端。终结位置很重要，因为它决定了我们如何处理实时会话状态、媒体传输、路由、延迟和故障隔离。

*SFU*（selective forwarding unit，选择性转发单元）是一种媒体服务器，它从每个参与者那里接收一路 WebRTC 流，并有选择地把流转发给其他参与者。在这种模型中，SFU 为每个参与者终结一条单独的 WebRTC 连接，而 AI 则作为会话中的另一个参与者加入。对于天生多方的产品（如群聊通话、在线课堂或协作会议）来说，这可能是很好的选择。它把音频编解码器、RTCP 消息、数据通道、录制和按流策略都集中在一处。1

即便在客户端对 AI 的产品中，SFU 也常常是默认的起点，因为它让团队能够复用一套久经验证的系统来实现信令、媒体路由、录制、可观测性，以及人工接管或增加更多参与者等未来的扩展。

我们的工作负载则不同。大多数会话都是 1:1 的——一个用户与一个模型对话，或一个应用与一个实时智能体对话——并且每一轮都对延迟敏感。针对这种流量形态，我们选择了 *收发器（transceiver）* 模型：一个 WebRTC 边缘服务终结客户端连接，然后把媒体和事件转换成更简单的内部协议，供模型推理、转写、语音生成、工具使用和编排使用。

在这一设计中，收发器是唯一持有 WebRTC 会话状态的服务，包括 ICE 连接性检查、DTLS 握手、SRTP 加密密钥和会话生命周期。这里的「终结」是指收发器是完成这些握手、对媒体进行加解密的端点。把这类状态保存在一处，让会话归属更容易推理，也让后端服务可以像普通服务一样扩展，而不必充当 WebRTC 对等端。

## 核心部署问题：WebRTC 遇上 Kubernetes

在选择收发器模型之后，我们的第一个实现是一个基于 Pion 构建的单体 Go 服务，同时负责信令和媒体终结。它支撑着 ChatGPT 语音、Realtime API 的 WebRTC 端点，以及多个研究项目。

在运行层面，收发器服务承担两项工作：

- 信令：SDP 协商、编解码器选择、ICE 凭据和会话建立
- 媒体：终结下游的 WebRTC 连接，并维护通往后端服务（用于推理与编排）的上游连接

我们希望这个服务像我们其他基础设施一样运行：在 Kubernetes 上，工作负载可以随需求变化扩容、缩容并在主机之间迁移。但传统的「每会话一端口」WebRTC 模型很难适配这种环境，因为它依赖大段的公共 UDP 端口范围，而随着 pod 的增加、删除或重新调度，这些端口很难暴露、保护和保持。2

### 端口耗尽

第一个问题是「每会话一端口」模型本身。在高并发下，这意味着要暴露和管理非常大的 UDP 端口范围。

- 云负载均衡器和 Kubernetes service 的设计并不是围绕「每个服务数万个公共 UDP 端口」展开的。每增加一段端口范围，都会在负载均衡配置、健康检查、防火墙策略和发布安全方面增加运维复杂性。3
- 大段 UDP 端口范围很难保护，因为它们扩大了外部可达的暴露面，也让网络策略更难审计。
- 它们也不适合自动扩缩容。Kubernetes 中的 pod 不断地被增加、删除和重新调度。要求每个 pod 预留并对外宣告一大段稳定的端口范围，会让这种弹性变得脆弱。4

这就是为什么许多 WebRTC 系统转向「每服务器一个 UDP 端口」，并在该端口之后做应用层的多路分用。5

### 状态粘性

「每服务器一端口」的设计解决了端口数量问题，却引入了第二个问题：在整个集群中保持每个会话的归属。

ICE 和 DTLS 是有状态协议。创建会话的进程需要持续接收该会话的数据包，才能验证连接性检查、完成 DTLS 握手、解密 SRTP，并处理后续的会话变更（例如 ICE 重启）。如果同一会话的数据包落到另一个进程上，建立可能失败，媒体也可能中断。

这给了我们一个明确的目标：向公共互联网暴露一个小而固定的 UDP 面，同时仍把每一个数据包路由到持有对应 WebRTC 会话的收发器。

### WebRTC 媒体架构比较

我们评估了几种达成这一目标的途径，包括 TURN（Traversal Using Relays around NAT，基于中继的 NAT 穿越），即由边缘中继终结客户端的分配（allocation）并代为转发流量。2

| **方案** | **优点** | **缺点** |
|---|---|---|
| 每会话唯一 IP:端口（也称为原生直接 UDP） | 客户端到服务器的直接媒体路径；数据路径中没有转发层 | 每个会话需要一个公共 UDP 端口；大段端口范围难以暴露和保护；与 Kubernetes 和云负载均衡器适配不佳 |
| 每服务器唯一 IP:端口 | 公共 UDP 占用远小于每会话暴露；每台服务器一个共享套接字即可对多路会话分用 | 在单台主机上运行良好，但仅靠自身无法在共享的负载均衡集群上工作；单机上的会话分用只有在数据包到达该主机后才起作用——在负载均衡集群中，第一个数据包仍可能落到错误的实例上，因此仍需要一种确定性的方式把每个会话引导到持有它的进程 |
| TURN 中继（协议终结型） | 客户端只需到达 TURN 中继的地址和端口；可以把策略集中在边缘 | TURN 分配会增加建立的往返次数；在 TURN 服务器之间迁移或恢复分配仍然困难 |
| 无状态转发器 + 有状态终结器（OpenAI 的中继 + 收发器） | 公共 UDP 占用小；收发器仍持有完整的 WebRTC 会话 | 媒体到达持有会话的收发器之前多了一跳转发；需要在中继与收发器之间进行自定义协调 |

## 架构总览：中继 + 收发器

我们发布的这套架构把数据包路由与协议终结分离开来。信令仍然到达收发器以建立会话，而媒体则先经由中继进入。中继是一个公共占用很小的轻量级 UDP 转发层，收发器则是位于其后的有状态 WebRTC 端点。

中继不解密媒体、不运行 ICE 状态机、也不参与编解码器协商。它只读取足以选择目的地的数据包元数据，然后把数据包转发给持有该会话的收发器。收发器看到的仍然是一个正常的 WebRTC 流程，并仍然持有所有协议状态。从客户端的角度看，WebRTC 会话没有任何变化。

## 基于 ICE 凭据的路由

首包路由是这套架构中的关键一步。中继必须在任何会话存在之前就路由来自客户端的第一个数据包——依靠数据包路径自身，而不是在外部查询服务上停顿等待。

每个 WebRTC 会话本身就已经携带一个协议原生的路由钩子：ICE 用户名片段（username fragment），即 *ufrag*，一个在会话建立期间交换、并在 STUN 连接性检查中被回传的短标识符。我们生成服务端 ufrag 时，让它恰好包含足够的路由元数据，使中继能够推断出目标集群和持有会话的收发器。

在信令阶段，收发器分配会话状态，并在 SDP 应答中返回一个共享的中继 VIP 和 UDP 端口。VIP 是位于中继集群前端的虚拟 IP 地址；与端口结合后，它为客户端提供一个单一稳定的目的地（例如 `203.0.113.10:3478`），尽管其后有多个中继实例。客户端在媒体路径上的第一个数据包通常是一个 STUN（Session Traversal Utilities for NAT）binding 请求，ICE 用它来验证数据包可以到达所宣告的地址。

中继只解析这第一个 STUN 数据包中刚好够用的部分：读出服务端 ufrag、解码路由提示，然后把数据包转发给持有会话的收发器。每个收发器监听一个共享的 UDP 套接字，也就是一个绑定到内部 IP:port 的操作系统端点，而不是每个会话一个套接字。在中继建立了一个从客户端源 IP:port 到该收发器目的地的会话之后，后续的 DTLS、RTP 和 RTCP 数据包就在该会话内流动，无需再次解码 ufrag。

中继的会话被有意设计得极其精简：只包含一个用于指导数据包转发的内存会话，以及用于监控的必要计数器和用于会话过期与清理的定时器。这一设计选择让数据包路由直接保持在数据包路径上。如果中继重启并丢失会话，下一个 STUN 数据包会依据 ufrag 路由提示重建会话。为了进一步提高可靠性，一旦路由建立，还会使用一个 Redis 缓存来保存 *<客户端 IP + 端口, 收发器 IP + 端口>* 的映射，这样即使下一个 STUN 数据包尚未到达，也能更早地完成恢复。

## Global Relay 与地理导向的信令

当我们把公共 UDP 面缩减到少量稳定的地址和端口之后，就可以在全球范围内部署同样的中继模式。Global Relay 是我们分布在各地的中继入口点集群，它们都实现相同的数据包转发行为。

广泛的地理入口缩短了客户端到 OpenAI 的第一跳，因为数据包可以在地理和网络拓扑上都靠近用户的中继处进入我们的网络，而不必先穿越公共互联网到达遥远的区域。实际效果就是：更低的延迟、更少的抖动，以及在流量抵达我们的骨干网之前更少可避免的突发丢包。6

在信令层面，我们使用 Cloudflare 的地理与就近导向（geo and proximity steering），让最初的 HTTP 或 WebSocket 请求到达附近的收发器集群。请求上下文决定了会话的位置，以及向客户端宣告哪个 Global Relay 入口点。SDP 应答提供 Global Relay 的地址，而 ufrag 则包含足够的信息，让 Global Relay 能把媒体路由到指定的集群、让中继能路由到目的地的收发器。

地理导向的信令与 Global Relay 相配合，把会话建立和媒体都放在了附近的入口路径上，同时让会话始终锚定在同一台收发器上。这缩短了信令和首次 ICE 连接性检查的往返时间，直接减少了用户在开口说话之前的等待时长。

## 中继的实现与性能

我们用 Go 编写了中继服务，并有意保持实现的精简。在 Linux 上，内核网络栈从机器的网络接口接收 UDP 数据包，并将其交给一个套接字——即进程在绑定某个 IP:Port 之后读取的操作系统端点。中继运行在用户态，因此一个普通的 Go 进程从该套接字读取数据包头、更新少量流状态并转发数据包，而不终结 WebRTC。我们不需要任何内核旁路（kernel-bypass）框架——那类框架可以让用户态进程直接轮询网络队列以获得更高的包处理速率，但也会增加运维复杂性。

关键设计选择：

- **不做协议终结：** 中继只解析 STUN 头部/ufrag；对后续的 DTLS、RTP 和 RTCP，它使用缓存的状态，保持数据包不透明。
- **临时状态：** 它维护一个小的、短超时的内存映射（客户端地址到收发器目的地），用于流状态和可观测性。
- **水平扩展：** 多个中继实例在负载均衡器之后并行运行。其状态并非硬性 WebRTC 状态，因此重启只会造成极小的流量损失，流恢复也很快。

效率优化措施：

- `SO_REUSEPORT` 是一个 Linux 套接字选项，允许同一台机器上的多个中继 worker 绑定同一个 UDP 端口。内核随后会在这些 worker 之间分发传入的数据包，从而避免单个读取循环成为瓶颈。
- `runtime.LockOSThread` 把每个读取 UDP 的 goroutine 固定到特定的操作系统线程上。与 `SO_REUSEPORT` 结合使用，这往往能让同一流（源与目的 IP:Port 加协议）的数据包留在同一个 CPU 核上，改善缓存局部性并减少上下文切换。
- 预分配的缓冲区和最少化拷贝让解析与分配的开销保持在低水平，以避免触发 Go 的垃圾回收。

这一实现以相对较小的中继规模承载了我们的全球实时媒体流量，因此我们保留了更简单的设计，而没有走上内核旁路的路线。

## 结果与经验

这套架构让我们能够在 Kubernetes 中运行 WebRTC 媒体，而无需暴露数千个 UDP 端口。这一点很重要，因为更小且固定的 UDP 面更容易保护和做负载均衡，也让基础设施无需预留大段公共端口范围即可扩展。凭借 Kubernetes 更好的基础设施支持和更小暴露面带来的更高安全性，这套设计还为客户端保留了标准的 WebRTC 行为，并证实了「无 SFU」的设计对我们这种工作负载是正确的默认选择。我们的会话大多是点对点的、延迟敏感的，而且当推理服务不需要表现得像 WebRTC 对等端时，扩展起来更容易。

更普遍的教训是：增加复杂性的最佳位置是一个薄薄的路由层，而不是每个后端服务，也不是定制的客户端行为。把路由元数据编码进一个协议原生字段，为我们带来了确定性的首包路由、很小的公共 UDP 占用，以及把入口部署到全球用户附近的充分灵活性。

有几个选择尤为重要：

- 在边缘保留协议语义。客户端仍然讲标准 WebRTC，浏览器与移动端的互操作性得以完整保留。
- 把硬性会话状态保存在一处。收发器持有 ICE、DTLS、SRTP 和会话生命周期；中继只转发数据包。
- 利用建立阶段已有的信息做路由。ICE ufrag 为我们提供了首包路由钩子，而没有在热路径上增加查找依赖。
- 在诉诸内核旁路之前，先针对常见情形做优化。一个精简的 Go 实现，配合对 `SO_REUSEPORT` 的细致使用、线程绑定和低分配的解析，对我们的工作负载来说已经足够。

实时语音 AI 只有在基础设施让延迟变得几乎无感时才能成立。对我们而言，这意味着改变 WebRTC 部署的形态，而不改变客户端对 WebRTC 本身的期待。
