# 我们如何用 Codex 在 28 天内打造出 Sora Android 版

> 原文：[How we used Codex to build Sora for Android in 28 days](https://openai.com/index/shipping-sora-for-android-with-codex/) · OpenAI 博客

*截至 2026 年 4 月 26 日，Sora 产品已不再可用。*

---

去年 11 月，我们向全球发布了 Sora Android 应用，让任何 Android 设备的用户都能把一段简短的提示词变成生动的视频。发布当天，该应用登上了 Play Store 榜首。Android 用户在头 24 小时内生成了超过一百万条视频。

这次发布背后有一个故事：Sora 生产级 Android 应用的初始版本是在 28 天内构建完成的，而这一切要归功于任何团队或开发者都能使用的同一个智能体：Codex。

从 2025 年 10 月 8 日到 11 月 5 日，一支精干的工程团队与 Codex 协作、消耗了约 50 亿 token，把 Sora Android 版从原型一路推进到全球发布。尽管规模可观，该应用的崩溃率（crash-free rate）保持在 99.9%，并且拥有一套让我们引以为傲的架构。如果你想知道我们是否用了一个秘密模型：我们使用的是 GPT‑5.1‑Codex 模型的早期版本——与今天任何开发者或企业通过 CLI、IDE 扩展或 Web 应用所能使用的版本完全相同。

提示词：花样滑冰运动员头顶着一只猫完成三周半跳

### 拥抱 Brooks 定律：保持敏捷才能跑得快

当 Sora 在 iOS 上发布时，使用量呈爆炸式增长。人们立刻开始源源不断地生成视频。相比之下，Android 侧我们只有一个小的内部原型，以及 Google Play 上不断累积的预注册用户。

面对高风险、时间紧的发布，常见的应对方式是堆资源、加流程。一个这种规模和质量的生产级应用通常需要许多工程师数月的工作，并在协调中被拖慢。

美国计算机体系结构专家 Fred Brooks 有句名言：「向延期的软件项目增加人手只会让它更延期。」换句话说，在试图快速交付一个复杂项目时，增加更多工程师往往会因沟通开销、任务碎片化和集成成本而拖慢效率。我们没有忽视这条洞见，而是顺势而为：我们组建了一支四人强团队——每个人都配备 Codex，以大幅放大每名工程师的影响力。

以这种方式工作，我们在 18 天内向员工交付了 Sora Android 版的内部构建版本，并在 10 天后公开发布。我们坚持高标准的 Android 工程实践，投入于可维护性，并让这个应用达到与传统项目同等的可靠性标准。（今天我们仍在大量使用 Codex 来演进这个应用并为其带来新功能。）

### 带教一位新入职的高级工程师

要理解我们与 Codex 的协作方式，先了解它擅长什么、在哪些地方需要指导会有帮助。把它当作一位新入职的高级工程师来对待是个好办法。凭借 Codex 的能力，我们可以把更多时间花在指导和审查代码上，而不是自己动手写。

**Codex 需要指导的地方**

1. Codex 还不擅长推断没有被明确告知的东西（例如你偏好的架构模式、产品策略、真实用户行为，以及内部规范或捷径）。
2. 同样，Codex 看不到应用实际运行的样子：它无法在设备上打开 Sora，注意不到某次滚动体验不对劲，也察觉不到某个流程令人困惑。这些体验层面的任务只有我们的团队能覆盖。
3. 每个实例都需要入职引导。共享带有清晰目标、约束以及「我们怎么做事情」的指导的上下文，是让 Codex 执行到位的关键。
4. 同理，Codex 在深层架构判断上比较吃力：如果放任不管，它可能会引入一个多余的 view model，而我们其实想扩展现有的那个；或者把明显属于 repository 层的逻辑推进 UI 层。它的本能是把东西先跑起来，而不是优先考虑长期的整洁性。

我们发现让 Codex 在整个代码库中创建并维护大量 AGENT.md 文件很有用。这使得同一套指导和最佳实践可以轻松地跨会话应用。例如，为了确保 Codex 按照我们的风格指南写代码，我们在顶层 AGENTS.md 中加入了以下内容：

```
1## Formatting and static checks2- **Always run** `./gradlew detektFix` (or for the affected modules) **before committing**. CI will fail if formatting or detekt issues are present.
```

**Codex 擅长的地方**

1. 快速阅读和理解大型代码库：Codex 几乎通晓所有主流编程语言，这使得跨多个平台复用同一套概念变得更容易，无需复杂的抽象。
2. 测试覆盖：Codex（与众不同地）热衷于编写单元测试来覆盖各种各样的情况。并非每个测试都很深入，但覆盖面的广度有助于防止回归。
3. 吸收反馈：类似地，Codex 善于对反馈做出反应。当 CI 失败时，我们可以把日志输出粘贴进提示词，让 Codex 提出修复方案。
4. 大规模并行、可随时丢弃的执行：大多数人远没有用到他们同时可运行的会话数上限。并行测试多个想法、把代码视为用完即弃，是完全可行的。
5. 提供新视角：在设计讨论中，我们把 Codex 当作生成式工具，用来探索潜在故障点、发现解决问题的新途径。例如，在我们设计视频播放器内存优化时，Codex 翻阅了多个 SDK，提出了我们没时间去逐一研究的方法。Codex 的研究结论对于把最终应用的内存占用降到最低被证明是无价之宝。
6. 让更高杠杆的工作成为可能：实际上，我们最终花在审查和指导代码上的时间多于自己写代码的时间。话说回来，Codex 做 code review 也非常在行，经常在合并之前就抓住 bug，提升可靠性。

一旦我们承认了这些特性，我们的工作模式就变得清晰了。我们让 Codex 在理解充分、边界清晰的模式内承担大量繁重工作，而团队则专注于架构、用户体验、系统性变更和最终质量。

### 亲手打下地基

即便是最好的新入职高级工程师，也不具备立即做出长期权衡所需的视角。为了用好 Codex 并确保其工作健壮且可维护，关键在于我们亲自把控应用的系统设计和关键取舍。这包括塑造应用的架构、模块化、依赖注入和导航；我们还亲手实现了身份认证和基础网络流程。

在这个地基之上，我们端到端地编写了几个有代表性的功能。我们使用了希望整个代码库遵循的规则，并随手把项目级模式记录成文档。通过把 Codex 指向这些代表性功能，它能够在我们的标准之内更独立地工作。对于这个我们估计有 85% 代码由 Codex 编写的项目，一个精心规划的地基避免了代价高昂的返工和重构。这是我们做过的最重要的决定之一。

思路不是尽快做出「能跑的东西」，而是做出「懂得我们希望事情如何运转的东西」。写代码有许多「正确」的方式。我们不需要告诉 Codex 具体做什么；我们需要向 Codex 展示在我们团队里什么才算「正确」。一旦我们确立了起点和偏好的构建方式，Codex 就可以开工了。

为了看看会发生什么，我们确实尝试过直接提示：「基于 iOS 代码构建 Sora Android 应用。开始。」但很快放弃了这条路径。虽然 Codex 造出的东西在技术上能跑，但产品体验不佳。而且在对端点、数据和用户流程缺乏清晰理解的情况下，Codex 一次性生成的代码并不可靠。（即便不使用智能体，合并数千行代码也是有风险的。）

我们假设 Codex 会在一个充满良好范例的沙箱中茁壮成长；我们猜对了。在几乎没有上下文的情况下让 Codex「构建这个设置界面」并不可靠。而让 Codex「参照你刚看过的另一个界面，用相同的架构和模式构建这个设置界面」效果好得多。人类做出结构性决策并设定不变量（invariant），Codex 随后在这个结构内填充大量代码。

### 写代码之前先与 Codex 一起规划

我们在最大化 Codex 潜力上的下一步，是弄清楚如何让 Codex 能够长时间（最近可达[超过 24 小时](https://openai.com/index/gpt-5-1-codex-max/)）在无人监督的情况下工作。

刚开始使用 Codex 时，我们直接抛出诸如「这是功能。这是一些文件。请把它做出来。」之类的提示。这有时奏效，但产出的代码大多只是技术上能编译，却偏离了我们的架构和目标。

于是我们改变了工作流。对于任何非平凡的变更，我们先让 Codex 帮我们理解系统和代码如何运作。例如，我们会让它阅读一组相关文件并总结该功能如何工作；比如数据如何从 API 流经 repository 层、view model，再进入 UI。然后我们会纠正或完善它的理解。（例如，我们会指出某个抽象其实属于另一层，或者某个类只为离线模式而存在、不应被扩展。）

就像对待一位新的、能力很强的队友一样，我们与 Codex 一起制定一份扎实的实现计划。这份计划往往像一份小型设计文档，指明哪些文件需要改动、应引入哪些新状态、逻辑应如何流转。只有在那时，我们才让 Codex 开始执行计划，一步一步来。一个有用的技巧：对于非常长的任务，当我们触及上下文窗口上限时，会让 Codex 把它的计划保存到文件里，从而可以在不同实例间沿用同一份指令。

这个额外的规划环节后来被证明物有所值。它让我们敢于让 Codex 长时间「无人监督」地运行，因为我们了解它的计划。它让 code review 变得更轻松，因为我们可以对照计划检查实现，而不是去读一段没有上下文的 diff。而当出了问题时，我们可以先调试计划，再调试代码。

这种感觉就像一份好的设计文档能让技术负责人对项目充满信心。我们不只是在生成代码：我们产出的是支撑同一份路线图的代码。

### 分布式工程

在项目高峰期，我们常常并行运行多个 Codex 会话。一个在做播放，另一个在做搜索，还有一个在处理错误，有时再有一个在做测试或重构。这感觉不像在用一个工具，更像在管理一个团队。

每个会话会定期向我们汇报进展。一个可能说：「我已完成这个模块的规划；这是我的方案，」另一个则交出一个新功能的大 diff。每一个都需要关注、反馈和审查。这像极了带着几名新工程师的技术负责人：他们都在推进，也都需要指导。

结果是一种协作式的流动。Codex 原始的编码能力把我们从大量手工敲代码中解放出来。我们有更多时间去思考架构、仔细阅读 pull request、亲手测试应用。

与此同时，这种额外的速度意味着我们的审查队列里总有东西在排队。Codex 不会被上下文切换阻塞，但我们会。开发中的瓶颈从写代码转移到了做决策、给反馈和集成变更上。

这正是 Brooks 洞见以一种新方式落地的地方。你无法简单地堆加 Codex 会话就期待线性加速，正如你无法不断给项目加工程师还指望工期线性缩短。每一双额外的「手」，哪怕是虚拟的，都会增加协调开销。我们成了乐队的指挥，而不只是几个更快的独奏乐手。

### Codex 作为跨平台超能力

我们启动项目时有一块巨大的垫脚石：Sora 已经在 iOS 上发布。我们频繁地让 Codex 阅读代码库，以帮助它理解关键需求和约束。整个项目期间我们都在开玩笑说，我们重新发明了跨平台框架这个概念。忘掉 React Native 或 Flutter 吧；*跨平台的未来就是 Codex 本身。*

这句玩笑背后是两条原则：

1. 逻辑是可移植的。无论代码是用 Swift 还是 Kotlin 写的，底层应用逻辑——数据模型、网络调用、校验规则、业务逻辑——都是一样的。Codex 非常擅长阅读一份 Swift 实现，并产出一个语义等价的 Kotlin 版本。
2. 具体的范例提供强大的上下文。一个能看到「这是它在 iOS 上确切的实现方式」和「这是 Android 架构」的全新 Codex 会话，远比一个只靠自然语言描述工作的会话高效得多。

把这些原则付诸实践，我们把 iOS、后端和 Android 三个仓库放进了同一个环境。我们给 Codex 这样的提示：

「阅读 iOS 代码中的这些模型和端点，然后提出一个计划，使用我们现有的 API client 和 model 类在 Android 上实现等价行为。」

一个小而实用的技巧是在 `~/.codex/AGENTS.md` 中写明本地仓库的位置和内容。这让 Codex 更容易发现并浏览相关代码。

我们实际上是在通过翻译做跨平台开发，而不是通过共享抽象。由于大部分翻译工作由 Codex 完成，我们避免了实现成本翻倍。

更广的启示是：对 Codex 而言，上下文就是一切。当 Codex 理解了该功能在 iOS 上已有的实现方式，又了解我们 Android 应用的结构时，它的表现最好。当 Codex 缺乏这种上下文时，它不是「拒绝配合」，而是在瞎猜。我们越是把它当作一位新队友、越是投入于给它正确的输入，它的表现就越好。

### 明天的软件工程，就在今天

到为期四周的冲刺结束时，使用 Codex 已不再像一场实验，而成为我们默认的开发循环。我们用它理解既有代码、规划变更、实现功能。我们像审查队友的产出一样审查它的输出。这就是我们发布软件的方式。

显而易见的是，AI 辅助开发并没有降低对严谨性的要求，反而提高了它。Codex 再能干，它的目标也是立刻从 A 到 B。这就是为什么没有人类，AI 辅助编程行不通。软件工程师能够理解并应用系统的现实约束、架构软件的最佳方式，以及如何带着未来的开发与产品规划去构建。未来软件工程师的超能力，将是对系统的深刻理解，以及在长时间跨度上与 AI 协作的能力。

软件工程中最有趣的部分是构建引人入胜的产品、设计可扩展的系统、编写复杂的算法，以及在数据、模式和代码中做实验。然而，过去与现在软件工程的真实日常往往更加平凡：把按钮居中、接通端点、编写样板代码。现在，Codex 让我们得以专注于软件工程中最有意义的部分，也就是我们热爱这门手艺的原因。

一旦 Codex 在一个上下文丰富的环境中完成配置——它理解你的目标和你偏好的构建方式——任何团队都能成倍放大自己的能力。我们的发布复盘不是包治百病的配方，我们也不声称已经解决了 AI 辅助开发的所有问题。但我们希望我们的经验能让更多人更容易找到「赋能 Codex 以赋能你」的最佳方式。

七个月前 Codex 以研究预览版发布时，软件工程还是另一番模样。通过 Sora，我们得以探索工程的下一个篇章。随着我们的模型和执行框架（harness）持续改进，AI 将成为构建过程中愈发不可或缺的一部分。
