# Asana 用 GPT‑6.1 Sol 在浏览器测试中将模型成本降低 76 倍

> 原文：[Asana cuts model costs 76x in browser tests with GPT-6](https://openai.com/index/asana-browser-agent/) · OpenAI 博客

借助 Codex 中的 GPT‑6 Astra 运行实验，Asana 在 GPT‑6.1 Sol 上优化了其浏览器智能体的工作流，使其运行成本降低 76 倍、速度提升 5 倍。

Asana 通过 [StackAI](https://www.stackai.com/) 帮助客户实现跨业务应用的自动化办公，StackAI 是它[收购](https://asana.com/press/releases/pr/asana-acquires-stackai-adding-cross-system-execution-for-human-agent-teams/e7c73b97-ae8c-4e51-b927-189ccb184146)的一个平台。借助 StackAI，客户无需编写代码即可构建浏览网站、填写表单和收集信息的工作流。在 Asana 的规模下，这些工作流中细小的低效都会累积起来。

Asana 的 StackAI CTO、博士 Frank Hidalgo 着手让浏览器智能体运行得更快、更便宜。他指挥 Codex 中的 GPT‑6 Astra 调查该智能体、测试改进方案并比较结果。他估计这项工作若由人工完成需要一到两个月，实际只用了大约一周。

[Asana 的 144 次运行研究](https://asana.com/inside-asana/cut-browsers-agent-cost)测试了 GPT‑6.1 Sol 和另外三个前沿模型，本文将后三者称为模型 A、B 和 C。最终在 GPT‑6.1 Sol 上形成的优化工作流，估算模型成本平均为每次运行 0.47 美元、耗时约 4 分钟，比 Model B 上的原始生产配置便宜 76 倍、快 5 倍。

> 「这就是人与智能体团队在实践中协作的样子。一位工程师设定方向，GPT-6 Astra 运行实验，结果经由 Command 进入生产环境。这展示了 Asana 如何将人类与智能体协作团队变为现实。」

## 借助 GPT‑6 Astra 找出浏览器智能体的低效之处

为了快速推进，Hidalgo 首先使用 Codex 中的 GPT‑6 Astra 梳理代码库，并解释该智能体如何构建每一次模型请求。GPT‑6 Astra 发现，智能体缓存了固定的指令和工具定义，却没有缓存它不断累积的页面文本与截图历史，因此每次请求都要以全价重发这段历史。

该智能体还几乎在每一步都丢弃较早的截图并删减文本。每一次修改都会改变历史内容，因此仅缓存历史并无帮助，而丢失这些事实则可能迫使智能体重新访问它已经读过的页面。

## 借助 GPT‑6 Astra，从预计两个月的研究缩至一周

Hidalgo 审阅了 GPT‑6 Astra 提出的修复方案，选出三项进行测试：

- 将缓存扩展到智能体的浏览历史
- 提高其可保留的文本量
- 批量移除截图，而非每一步都移除

GPT‑6 Astra 先进行了快速测试，以确定哪些变量真正重要。由于代码最初并非为对照实验而设计，它随后重构了代码，让同一个前端和后端能够并行支持多个工作流，每个工作流都有各自的设置。

Astra 开展了完整研究：120,000 和 480,000 字符两档历史预算，以及六种缓存与截图策略，每种策略在四个模型上各测试三次（见下表）。表现最好的策略允许截图累积到 20 张之后，再削减到只保留最近一张。这使得两次移除之间的较早历史能在更长时间内保持不变。结合更大的历史预算，它就成了最终的优化工作流。每种配置执行的都是同一个任务：从一个公开的演示目录中收集 32 本书各自的六个字段，这代表了部分 Asana 客户在 StackAI 中运行的工作负载。

GPT‑6 Astra 运行这些工作流，检查请求、用量记录与输出，并有独立的模型会话复核这些工作。每个会话的请求、数据轨迹和结果都记录在 [Command](https://asana.com/product/command)——Asana 的软件交付平台——中，团队事后可以回顾完整的研究过程。研究结果从 Command 转化为工单，再变为 pull request，最终变更上线到生产环境。

> 「这项工作若由我人工完成需要一到两个月。借助 Codex 中的 GPT-6 Astra，它只花了大约一周：我会在睡前设好一个 /goal，早上再查看结果。」

## 把单次运行的模型成本压到 0.50 美元以下

对于 Model B，这次优化把估算模型成本从每次运行至少 36.21 美元（部分原始运行在完成之前就达到了步数上限）降到 1.24 美元，降幅为 29 倍。GPT‑6.1 Sol 上的优化工作流还要再便宜 2.6 倍，为 0.47 美元。优化工作流中的每一次运行都完成了任务并返回了正确答案。

仅在 GPT‑6.1 Sol 上、采用更大的历史预算时，新的缓存与截图策略将成本降低了 4 倍，从每次运行 1.97 美元降到 0.47 美元。每次调用便宜了约 3 倍，因为 89% 的输入来自缓存，而缓存输入的价格仅为未缓存价格的 5%。运行速度也提升了：Model B 上的原始配置至少需要 22.5 分钟，而 GPT‑6.1 Sol 上的优化工作流只需约 4 分钟。

这次调查还显示了历史管理如何影响智能体能否给出答案。给 GPT‑6.1 Sol 更多空间保留浏览历史后，能产出答案的运行次数从较小历史预算下的 18 次中的 3 次，提升到较大预算下的全部 18 次，且每次都给出了正确答案。在 Hidalgo 看来，其商业价值在于让客户用上更快、更强的模型，同时让运营成本保持在可持续水平。

> 「成本过去限制了我们能向客户提供哪些模型来运行这些工作负载。通过让智能体更高效，我们既能给客户更好、更快的模型，又能降低自己的运营成本。」

## 扩大实验与产品测试的规模

Asana 已在 StackAI 中发布了对浏览器导航的这些改动，并正在开发让类似实验更容易复现的工具。随着时间推移，团队计划把这种测试纳入平台的评测体系，让客户和内部团队在配置智能体时可以比较成本、运行时长和答案质量。

> 「交付速度不再是瓶颈；人的注意力才是。我们正在接近这样一个世界：每位工程师都是一名 PM，带领一支智能体舰队。」

Asana 现在正在使用 Codex 中的 GPT‑6 Astra 在发布前测试产品功能：Astra 在平台上导航、尝试不同输入，并为人工 QA 审查者报告 bug。Hidalgo 将此视为一种新型软件开发生命周期的基础——大量云端智能体会话并行测试各项功能。

*完整研究发布于 [Asana](https://asana.com/inside-asana/cut-browsers-agent-cost) 与 [StackAI](https://www.stackai.com/blog/how-stackai-by-asana-used-astra-codex-and-command-to-reduce-browser-agent-costs) 的博客。*
