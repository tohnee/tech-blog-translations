# 数据基础设施中的流行病学 bug | OpenAI Core Dump

> 原文：[Epidemiology bug in data infrastructure | OpenAI Core Dump](https://openai.com/index/core-dump-epidemiology-data-infrastructure-bug/) · OpenAI 博客

欢迎回到 Core Dump——我们的一个系列，分享 OpenAI 团队遇到的有趣 bug。本期：数据基础设施中的一个流行病学 bug。

有时候，我们发现的 bug 与代码有关。有时候，它们与信息如何传播有关。这一个两者皆是。

## 症状

一位数据工程师注意到，我们内部分析平台上的一个仪表盘在显示我们某个实验的计数时出现了错误。这些数字不只是略有偏差；它们以一种有规律的方式出错，仿佛一小部分事件在特定的分片（shard）边界上被重复复制了。

这个仪表盘的查询跑在一张按实验变体（variant）聚合事件的表上。变体 A 的计数看起来是正确的。变体 B 的计数被夸大了约 12%，而多出来的事件全部挂在少数几个摄取（ingestion）时间戳上，彼此间隔几乎精确地为一小时。

## 排查

第一个假设是重试循环：如果客户端在没有幂等键（idempotency key）的情况下重试一次失败的摄取请求，服务器会把该事件计数两次。但事件流水线要求每次写入都携带幂等键，而且去重是在存储层强制执行的。因此，重试本应被吸收掉。

深入查看摄取日志后，我们发现重复的事件并不是重试。它们是*重放（replay）*——一个流处理器在检查点（checkpoint）恢复之后重新发出的整批数据。在精确一次（exactly-once）架构中，重放是正常且安全的：下游的去重层应当丢弃任何它已经见过的事件。

bug 出在去重键的生成方式上。这个键由事件 ID 和一个从摄取时间戳导出的时间桶（time bucket）组成，该时间戳被截断到小时。通常这是无害的：一个事件到达一次，它的键是稳定的，重放会产生相同的键。

但摄取时间戳是由生产者在事件进入队列之前赋值的。当生产者的时钟发生漂移、随后又被 NTP 校正时，恰在校正之前入队的事件可能被赋予跨在小时边界两侧的时间戳。在重放时，流处理器会根据事件存储下来的时间戳重新生成时间桶——而这个时间戳是相同的——所以键本应仍然匹配。

然而它没有匹配。存储的时间戳在第一次写入时被规范化了：流水线把原始时间戳截断到小时，并把截断后的值存入事件负载（payload），但去重层拿存储的截断时间桶，去和它从重放批次中读到的*未截断*负载字段计算出的时间桶做比较。当两者不一致时——恰好是那些原始时间戳落在时钟校正窗口内的事件——去重层把重放的事件当作新事件，该事件于是被计数了两次。

## 修复

修复很小：用与存储时相同的规范化时间戳来计算去重键，而不是从原始负载重新推导。我们还增加了一个不变量检查：如果某个重放批次产生了原始写入中未见过的键，就让摄取过程大声失败；并增加了一个指标，按小时桶报告键不匹配的比率。

在重新推导受影响时间桶的回填（backfill）之后，仪表盘恢复了正常。重复事件总数：约 140 万个，占 120 亿的 0.012%——足以扭曲一个实验的读数，却不足以触发我们已有的任何粗粒度数据质量告警。

## 我们学到了什么

- **规范化一次，用规范化后的值生成键。** 任何时候，只要流水线为存储而规范化了某个字段，却从原始值推导其他产物，这两种表示就可能悄悄地分道扬镳。
- **时钟校正是一个流行病学事件。** 它会传播到每一个消费时间戳的组件，其影响范围（blast radius）只受校正精度和下游分桶敏感度的限制。
- **细粒度的不变量胜过粗粒度的告警。** 我们的仪表盘盯着总量和速率，而 bug 藏在两种表示之间的连接处。在写入时断言表示的一致性，比从一个倾斜的直方图里反推调试要便宜得多。
