# Codex 编排的开源规范：Symphony

> 原文：[An open-source spec for Codex orchestration: Symphony](https://openai.com/index/open-source-codex-orchestration-symphony/) · OpenAI 博客

作者：Alex Kotliarskyi、Victor Zhu 与 Zach Brock

六个月前，在开发一款内部生产力工具时，我们团队做出了一个（在当时）颇有争议的决定：用完全不含人写代码的方式构建我们的仓库。项目仓库里的每一行代码都必须由 Codex 生成。

为了让这个决定可行，我们从头重新设计了工程工作流。我们构建了一个对智能体友好的仓库，在自动化测试和护栏上大力投入，并把 Codex 当作一位正式的队友。我们在上一篇关于执行框架（harness）工程的[博客文章](https://openai.com/index/harness-engineering/)中记录了这段历程。

它奏效了，但随后我们撞上了下一个瓶颈：上下文切换。

为了解决这个新问题，我们构建了一个名为 *Symphony* 的系统。[Symphony](https://github.com/openai/symphony) 是一个智能体编排器，它把 Linear 这类项目管理看板变成编程智能体的控制平面。每个未关闭的任务都会获得一个智能体，智能体持续运行，人类负责评审结果。

本文解释我们如何创造了 Symphony——它使一些团队的合并 PR 数量增长了 500%——以及如何用它把你自己的 issue 跟踪器变成一个全天候运行的智能体编排器。

### 交互式编程智能体的天花板

尽管越来越好用，编程智能体——无论是通过 Web 应用还是 CLI 访问——仍然是交互式工具。

随着 OpenAI 内智能体工作规模的增长，我们发现了一种新的负担。每位工程师都要打开几个 Codex 会话、分配任务、评审输出、引导智能体，然后周而复始。实践中，大多数人能轻松管理三到五个会话，再多上下文切换就会变得痛苦。超过这个数，生产力就会下降。我们会忘记哪个会话在做什么，在多个终端之间跳来跳去把智能体拉回正轨，还要调试进行到一半就卡住的长时任务。

智能体很快，但我们有一个系统性瓶颈：人类的注意力。我们实际上打造了一支能力极强的初级工程师队伍，然后让自己的人类工程师去微观管理他们。这样是扩展不下去的。

### 视角的转变

我们意识到自己优化错了对象。我们把系统围绕编码会话和已合并 PR 来组织，而 PR 和会话其实只是达成目的的手段。软件工作流在很大程度上是围绕交付物组织的：issue、任务、工单、里程碑。

于是我们自问：如果我们不再直接监督智能体，而是让它们从任务跟踪器中自行领取工作，会发生什么？

这个想法成了 Symphony——一份书面规范，扮演监督者的角色来编排智能体工作。

### 把 issue 跟踪器变成智能体编排器

Symphony 始于一个简单的概念：任何未关闭的任务都应该由智能体接手并完成。我们没有在多个标签页中管理 Codex 会话，而是把 issue 跟踪器变成了控制平面。

在这一设置下，每个未关闭的 Linear issue 都映射到一个专属的智能体工作区。Symphony 持续监视任务看板，确保每个活跃任务都有一个智能体循环运行直至完成。如果智能体崩溃或卡住，Symphony 会重启它。如果出现新工作，Symphony 会接手并开始组织安排。

我们围绕工单状态构建了工作流，把任务管理器 Linear 当作一台状态机使用。

在实践中，Symphony 把工作与会话、与 PR 解耦。有些 issue 会在多个仓库中产出多个 PR；另一些则是纯粹的调研或分析，完全不碰代码库。

> 一旦工作被这样抽象，工单就可以代表大得多的工作单元。

我们经常用 Symphony 来编排复杂特性和基础设施迁移。例如，我们可能会建一个任务，让智能体分析代码库、Slack 或 Notion，并产出一份实施方案。当我们对方案满意后，智能体会生成一棵任务树，把工作分解成多个阶段并定义任务之间的依赖关系。

智能体只会开始处理未被阻塞的任务，因此执行会在这个 DAG（执行步骤序列）上自然且最优地并行展开。例如，我们把 React 升级标记为被 Vite 迁移阻塞。正如预期，智能体只在 Vite 迁移完成后才开始升级 React。

智能体也能自己创造工作。在实现或评审过程中，它们经常注意到超出当前任务范围的改进点：一个性能问题、一次重构机会，或一种更好的架构。发生这种情况时，它们会直接新建一个 issue，供我们稍后评估和排期——这些后续任务也有很多会被智能体领走。在我们监督整个过程的同时，智能体保持井然有序，让工作持续向前推进。

这种工作方式大幅降低了启动模糊性工作的认知成本。如果智能体搞错了什么，那仍然是有用信息，而我们的成本几乎为零。我们可以非常廉价地建工单让智能体去做原型和探索，然后把不喜欢的探索成果直接扔掉。

由于编排器运行在开发机上、永不停歇，我们可以从任何地方添加任务，并确信会有智能体把它领走。例如，我们团队的一位工程师曾在一家舒适的小木屋里、用糟糕的 wifi，通过手机上的 Linear 应用完成了三项重要变更。

### 这种工作方式带来的探索增量

在观察使用 Symphony 工作的效果时，最明显的变化是产出。在 OpenAI 的一些团队中，我们看到落地 PR 的数量在前三周增长了 500%。在 OpenAI 之外，Linear 创始人 Karri Saarinen 指出，随着我们发布 Symphony，[新建工作区的数量出现了一次激增](https://x.com/karrisaarinen/status/2031773828284919878)。然而，更深刻的变化在于团队如何看待工作。

当我们的工程师不再把时间花在监督 Codex 会话上时，代码变更的经济学被彻底改写。每次变更的感知成本下降了，因为我们不再投入人力去推动实现本身。

这改变了我们的行为。在 Symphony 中发起试探性任务变得轻而易举。试一个想法、探索一次重构、验证一个假设，然后只保留看起来有前景的结果。

它还拓宽了谁能发起工作。我们的产品经理和设计师现在可以直接向 Symphony 提交功能请求。他们不需要检出仓库，也不需要管理 Codex 会话。他们描述功能，然后收到一个评审包，其中包括该功能在真实产品中运行效果的视频演示。

Symphony 在大型 monorepo（比如 OpenAI 内部的那个）中也大放异彩——在那里，落地 PR 的「最后一公里」既缓慢又脆弱。系统会盯着 CI，在需要时变基，解决冲突，重试不稳定的检查，总之把变更一路护送过整条流水线。当工单到达 **Merging** 状态时，我们就非常有信心这项变更将无需人类看护即可进入主分支。

实现 Symphony 之后，我们把更多工作委派给智能体，自己专注于更难、更具探索性的任务。

### 进步伴随着新的、不同的问题

在这一层级运营伴随着取舍。当我们从交互式引导智能体转为在工单层面给它们分配工作时，我们失去了在半路不断推动它们、并在需要时纠正航向的能力。有时智能体产出的东西完全不着边际。这也有用——这些失败暴露了系统中的缺口，帮助我们把系统变得更稳健。

我们没有手动修补结果，而是添加护栏和技能，让智能体下次能够成功。随着时间推移，这促使我们为执行框架（harness）添加新能力，比如运行端到端测试、通过 Chrome DevTools 驱动应用，以及管理 QA 冒烟测试。我们大幅改进了文档，并明确了「好」是什么样子。

并非所有任务都适合 Symphony 的工作方式。有些问题仍然需要工程师直接使用交互式 Codex 会话，尤其是模糊的问题，或需要强判断力和专业知识的工作。实践中，这些往往正是我们的工程师最愿意花时间去做、也最有意思的任务。

区别在于，Symphony 能够承担大部分例行实现工作。这让工程师可以一次专注于一个难题，而不必在较小的任务之间不停切换上下文。

我们还学到，把智能体当作状态机中的僵硬节点行不通。模型越来越聪明，能解决比我们试图把它们塞进的框子更大的问题。我们早期的智能体工作只是让 Codex 实现任务。事实证明这种做法限制太大。Codex 完全有能力创建多个 PR、阅读评审意见并作出回应。于是我们给了它工具——`gh` CLI、读取 CI 日志的技能等——现在我们可以让 Codex 做更多事，比如关闭陈旧的 PR，或拉取已完成与被放弃工作的对比报告。这类任务远远超出了最初「实现功能」的框框。

于是我们最终转向给智能体下达*目标*（objectives），而不是严格的状态迁移，就像优秀的管理者给团队成员布置目标一样。模型的力量来自其推理能力，所以给它们工具和上下文，然后放手让它们施展。

### 用 Symphony 构建 Symphony

打开 [Symphony 仓库](https://github.com/openai/symphony)时，你首先注意到的是：Symphony 在技术上只是一个 `SPEC.md` 文件——对问题和预期解决方案的定义。我们没有构建复杂的监督系统，而是定义了问题和预期解决方案，给智能体提供高层引导。

参考实现用 Elixir 编写——因为当代码实际上免费时，你终于可以依据语言的长处来选型，比如 Elixir 的并发能力——但核心思想可以表达在一份简单的 Markdown 文档里。我们鼓励你把你最喜欢的编程智能体指向这份规范，让它实现自己的版本。

Symphony 的第一版只是一个跑在 `tmux` 里的 Codex 会话，轮询 Linear 并为新任务派生子智能体。它能用，但并不特别可靠。第二版住进了我们的主项目仓库——一个为智能体而建的仓库。我们已经构建了智能体执行框架（harness），赋予智能体在这个仓库中高质量工作所需的技能和上下文，所以 Symphony 只需把它们连接起来。

一旦基本功能就位，我们就用 Symphony 来构建 Symphony。

当我们在内部演示这个系统管理任务并附上其工作证明视频时，反响极为热烈：我们的 Symphony 项目频道不断壮大，组织内各团队开始自发使用它。在 OpenAI，内部产品市场契合是对外发布的前提。基于我们在 OpenAI 内部看到的使用情况，很明显我们应该把 Symphony 分享到公司高墙之外。

于是我们把这一想法抽取成一份独立的 `SPEC.md`，并让 Codex 去实现它。作为参考实现，我们选择了 Elixir——一门相对小众、但在编排和监督并发进程方面拥有出色原语的语言。Codex 一次性构建了 Elixir 实现，此后我们持续迭代规范与实现两者。为了打磨规范，我们甚至让 Codex 用其他几种语言——TypeScript、Go、Rust、Java、Python——实现它，并利用这些结果来发现歧义、简化系统。它在每一种语言上都成功了。

在构建 Symphony 的过程中，我们移除了许多附带的复杂性，比如对特定仓库或 Linear MCP 的依赖。Symphony 不再依赖我们的内部仓库或工作流。核心方法变得非常简单：

> 对每个未关闭的任务，保证有一个智能体在它自己的工作区中运行。

除了帮助推进当前工作之外，开发工作流如今也成了智能体知晓并遵循的东西。开发工作流——处理一个 issue、检出仓库、把任务置为进行中好让 PM 知道有人在处理、提交 PR、把状态移到 **Review**、附上视频等等——现在被记录在一份简单的 `WORKFLOW.md` 文件里。所有这些本来是人类遵循的流程，却从未被记录下来。现在我们不再依赖这套隐式步骤，而是把它写成文档，由 Symphony 确保智能体遵循它。这让我们得以构建与我们并肩工作的智能体。如果我们决定智能体还应在完成的工作上附上自我反思，我们就把这一点加进 `WORKFLOW.md`，Symphony 会引导智能体执行该步骤。

我们还得以在 [App Server 模式](https://developers.openai.com/codex/app-server/)下使用 Codex，这是 Codex 内置的无头（headless）模式。该模式让我们能够运行 Codex，并通过文档完善的 JSON-RPC API 以编程方式与它交互，完成诸如启动线程、响应轮次之类的事情。比起试图通过 CLI 或实时的 `tmux` 会话与 Codex 交互，这更方便、更可扩展。

Codex App Server 完美契合我们的用例：我们既利用了 Codex 提供的执行框架，又拥有可以接入的旋钮和钩子。例如，为了避免向子智能体暴露 Linear 访问令牌，我们使用[动态工具调用](https://developers.openai.com/codex/app-server/#dynamic-tool-calls-experimental)暴露原始的 `linear_graphql` 函数来执行对 Linear 的任意请求，而无需依赖 MCP、也无需把访问令牌暴露给容器。

### 接下来

Symphony 是一个刻意保持极简的编排层。我们把它开源，是为了展示 Codex App Server 与 Linear 这类不同工作流工具搭配时的威力。因此，我们不计划把 Symphony 作为独立产品来维护。把它当作一个参考实现。就像许多开发者把编程智能体指向执行框架工程那篇文章来搭建自己的仓库一样，我们希望你把最喜欢的编程智能体指向 Symphony 的[规范](https://github.com/openai/symphony/blob/main/SPEC.md)和[仓库](https://github.com/openai/symphony)，构建适合你自己环境的版本。

威力来自 Codex 及其 app server。Symphony 只是把 Codex 连接到 Linear——两个我们本来就在用的东西——以解决工作管理问题的一种方式。随着编程智能体在推理和遵循指令方面变得更强，我们猜测其他公司的瓶颈也将从编写代码转向管理智能体工作。令人兴奋的是，试验这些编程智能体系统的门槛如今低得惊人。你可以直接用 Codex 构建东西。
