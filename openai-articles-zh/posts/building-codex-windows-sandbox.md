# 构建一个安全而有效的沙箱，让 Codex 登陆 Windows

> 原文：[Building a safe, effective sandbox to enable Codex on Windows](https://openai.com/index/building-codex-windows-sandbox/) · OpenAI 博客

2025 年 9 月我加入 Codex 工程团队时，Windows 版 Codex 还没有沙箱实现，这意味着 Windows 用户在使用 OpenAI 的编程智能体时，被迫在两个都不理想的选项中做选择：

1. 批准编程智能体想运行的几乎每一条命令（哪怕是读取），这既低效又烦人。使用 Codex 的一大好处就是你不必亲自完成所有繁琐的工作。
2. 开启完全访问（Full Access）模式：让 Codex 无需批准、不受限制地运行所有命令，这消除了摩擦，却牺牲了监督。

我们的编程智能体 [Codex](https://openai.com/codex/) 运行在开发者笔记本上——无论通过 CLI、IDE 扩展还是桌面应用。它管理着键盘前的人类与云端处理推理的模型之间的对话。

Codex 默认以真实用户的权限运行，这意味着用户能做的它都能做。这很强大，也潜藏危险。编程模型可能会让执行框架（harness）在本地运行各种命令——从运行测试、读取或编辑文件，到创建 Git 分支——因此 Codex 的默认模式试图在有效性与安全性之间找到恰当的平衡。这一默认模式允许 Codex 几乎在任何位置读取文件、在你的工作区内写入文件（即你运行 Codex 时所在的目录），除非你明确要求，否则不接入互联网。要实现这种把文件写入和网络访问自动约束在安全范围内的效果，Codex 需要一个真正能强制执行这些约束的沙箱环境。

*沙箱*是一个受限的执行环境。当开发者使用 Codex 时，其计算机操作系统会以降级的权限启动命令，这些约束会沿着进程树向下传递。每条 Codex 命令从一开始就被沙箱化，每个后代进程都停留在同一边界之内。

Codex 需要由计算机操作系统强制执行的隔离特性来实现有效的沙箱。有些操作系统提供了能很好地做到这一点的工具（例如 macOS 上的 Seatbelt、Linux 上的 seccomp 或 bubblewrap）；然而，Windows 目前并没有开箱即用地提供这类能力。

为了让 Codex 在 Windows 上与其他平台一样安全、好用，我们需要自己实现一个沙箱。

## 现有 Windows 工具的不足之处

Windows 提供了一些用于隔离的工具和原语。虽然它们都没有完全满足我们的要求，但我们考察了若干潜在的解决方案——即 AppContainer、Windows Sandbox 和强制完整性控制（Mandatory Integrity Control）标记。

**AppContainer**

- **是什么：**AppContainer 是 Windows 原生的沙箱，一种基于能力（capability）的隔离模型，为那些事先确切知道自己需要访问什么的应用而构建。
- **为何有吸引力：**它提供的是真正的操作系统边界，而非尽力而为的限制。
- **为何不行：**Codex 并不是一个范围被严格圈定的应用。它驱动开放式的开发者工作流：shell、Git、Python、包管理器、构建工具，以及智能体自行决定需要的任何其他二进制程序。在实践中，这使得 AppContainer 的形态不适合这个问题。它的隔离很强，但面向的负载类别远比「让智能体像开发者一样工作」要窄。

**Windows Sandbox**

- **是什么：**Windows Sandbox 是微软的一次性轻量级虚拟机。你会得到一个带有强隔离边界的全新 Windows 桌面，会话结束后你在其中所做的一切都会消失。
- **为何有吸引力：**原因显而易见——对任意软件的兼容性远好于 AppContainer，而且从安全角度看它是一个强得多的盒子。
- **为何不行：**Codex 需要直接作用于用户真实的代码检出、工具和环境，而不是在一个需要额外设置和宿主/客户机桥接的一次性桌面里工作。它还有一个根本性的产品问题：Windows Sandbox 在 Windows Home 版本上根本不可用。

**强制完整性控制（MIC）完整性标记**

- **是什么：**Windows 有一个叫「完整性级别（integrity levels）」的概念，例如低、中、高，用于决定系统对对象和进程的信任程度。基本规则是：低完整性进程不能写入具有更高完整性级别的对象，即使普通 ACL 本来允许这样做。例如，低完整性进程被视为较不受信任，因此 Windows 会阻止它写入正常的中完整性对象，除非这些对象被显式重新标记以允许写入。
- **为何有吸引力：**MIC 在纸面上看起来很优雅——以低完整性运行 Codex，把可写根目录重新标记为低完整性，然后让 Windows 在其他所有地方强制禁止写入。这会给我们一条非管理员路径，背后有真正的操作系统机制支撑。
- **为何不行：**与 ACL 一样，完整性标记会修改真实的主机文件系统，而且在这种情形下语义变化尤其宽泛。把一个工作区标记为低完整性，并不只是意味着「Codex 可以写这里」，而是意味着低完整性进程*总体上*都可以写这里。在一台真实的开发者机器上，这会把用户真实的代码检出变成主机的一个低完整性倾倒区，比为一个沙箱设计精心定向的 ACL 风险大得多。即使中完整性的开发工具继续正常工作，工作区底层的信任模型也已发生变化——这种变化难以控制，更难以辩护。

在评估了所有这些选项、认定它们都行不通之后，我们开始设计自己的方案，为 Windows 用户带来良好的 Codex 体验。

## 第一个原型：「非提权沙箱」

我们第一个可用的原型组合使用了一些 Windows 概念和工具来实现所需的隔离。从一开始，目标之一就是让这一切无需*提权（elevation）*即可工作，也就是说，Codex 不应该仅仅为了搭建或运行沙箱就提示用户授予管理员权限。这意味着要弄清楚如何对两件事施加合理的限制：文件写入和网络访问。

### 限制文件写入

如果完全不限制文件写入，会有安全问题；如果限制得太严，沙箱就会损害用户生产力，需要不断地请求批准。为解决这个问题，我们依赖两个重要的 Windows 构件：SID 和写入受限令牌（write-restricted token）。

#### SID 让我们赋予沙箱一个身份

SID（security identifier，安全标识符）是 Windows 与权限绑定的身份。每个用户有一个 SID，每个组有 SID，甚至单个登录会话也有自己的 SID。例如，一个当前登录的会话可能有类似 `S-1-5-5-X-Y` 的 SID；分配给本地管理员组的 SID 可能是 `S-1-5-32-544`。

Windows 还允许你创建合成 SID：它们不对应任何真实用户，但仍然可以出现在定义谁可以读/写/执行特定文件或目录的 ACL（访问控制列表）中。这使得 SID 成为对我们沙箱很有用的原语：我们可以创建专供 Codex 沙箱使用的 SID，而不干扰机器上的任何其他东西。

#### 写入受限令牌限制 Codex 可以修改文件的位置

进程令牌是 Windows 中的安全对象，定义了运行中进程的身份与特权。它们决定进程能执行哪些动作。*写入受限令牌*是一种特殊的进程令牌，它让 Windows 对写操作执行额外的访问检查。

要让一次写入成功，必须通过两项检查：

1. 正常的用户身份（令牌的「所有者」）必须被允许执行该操作
2. 令牌的受限 SID 列表中至少有一个 SID 也必须被授予访问权

在实践中，这些检查让我们可以用 ACL 精确定义沙箱可以修改文件系统的位置，提供了我们在写操作上需要的粒度。

有了 SID 和写入受限令牌，我们的非提权沙箱是这样工作的：

1. 沙箱设置创建一个名为 `sandbox-write` 的合成 SID。
2. `sandbox-write` SID 被授予对以下位置的写入、执行和删除权限：
   - 当前工作目录
   - `config.toml` 中配置的任何额外 `writable_roots`
3. 沙箱设置显式拒绝该 SID 对「可写范围内的只读」位置的写入权限，例如：
   - `<cwd>/.git`
   - `<cwd>/.codex`
   - `<cwd>/.agents`
4. Codex 在写入受限令牌下启动命令，该令牌的受限 SID 列表包含 `Everyone`、当前登录会话 SID 以及 `sandbox-write` 合成 SID。

这套流程有效地解决了限制文件写入的问题，看起来很有希望。现在我们需要一个限制沙箱网络访问的方案。

### 限制网络访问

限制网络访问是沙箱的重要组成部分；没有它，恶意代码可能把机器上的数据窃取到互联网。由于我们想避免提权要求，我们强力阻断网络流量的选项很有限。我们想用的工具（如 Windows 防火墙）通常没有管理员权限就无法安装。

没有 Windows 防火墙这个选项，我们只能在自己能控制的范围内做文章。我们试图让子环境对开发者实际使用的各类联网工具「默认失败（fail-closed）」，让 Git 命令、包安装器等在沙箱中失败，从而用户必须批准任何面向互联网的操作。思路是给明显的逃生口下毒：把感知代理的流量送往一个死端点，让 Git 的 HTTP(S) 传输同样如此，并让基于 SSH 的 Git 立即失败。除此之外，我们在 PATH 前面加了一个小的 `denybin` 目录并重排了 `PATHEXT`，让占位（stub）SSH 和 SCP 脚本先于真正的二进制被解析到。

例如，以下是我们用来限制网络访问的一些具体环境变量覆盖：

- `HTTPS_PROXY=http://127.0.0.1:9`
- `ALL_PROXY=http://127.0.0.1:9`
- `GIT_HTTPS_PROXY=http://127.0.0.1:9`
- `NO_PROXY=localhost,127.0.0.1,::1`
- `GIT_SSH_COMMAND=cmd /c exit 1`

这拦截了大量由工具驱动的正常流量，但它仍然只是「建议性」的。一个进程可以无视环境变量、绕过 PATH，或者直接打开套接字——风险太大。

### 非提权方案伴随着取舍

与任何有趣的软件实现一样，第一个原型有一些优点和缺点。它只用几个标准的 Windows 能力就完成了任务、允许非常明确且细粒度的文件系统写入、并且以非提权方式运行——省去了用户接受过多提权提示或在本地机器上做管理员的需要——但它也有一些实实在在的缺点，其中一些使它失去了成为最终设计的资格：

- 设置速度：应用工作区 ACL 可能很昂贵，取决于工作区目录的拓扑结构。
- 系统足迹：我们在开发者的系统上应用了真实的 ACL，不过这个足迹并不算特别有侵入性，因为所有被应用的 ACL 都只涉及一个专门创建、仅由沙箱使用的合成 SID。
- 难以更改的语义：依赖 ACL 来实现基于文件的限制，意味着更改沙箱语义既昂贵又复杂。在 macOS 上，我们可以动态改变用于配置 Seatbelt 的 `.sbpl` 文件的生成方式；而 Windows 沙箱要调整 ACL 可能需要一个缓慢而沉重的操作。
- 网络防护薄弱。如前所述，它是「建议性」的，肯定会被某些自带网络栈的程序绕过，而且设计上就不是为了抵御对抗性代码。

前三个问题对于一个灵活到足以支撑智能体流程的自定义沙箱实现来说是固有的。但网络抑制的情况不同。

### 网络抑制太过重要

除了恶意智能体能轻易绕过基于环境的网络抑制之外，大量善意的代码/二进制程序也会轻易绕过它——只要它们不遵守环境代理变量，或者自己实现了基于套接字的网络代码。我们认为，仅这一方面就足以让我们考虑投资一种更好的沙箱模式。

为了获得更好的网络抑制，我们想使用 Windows 防火墙——它允许我们针对用户或程序阻断出站网络流量。遗憾的是，由于以下几个原因，我们无法有效创建一条只作用于 Codex 执行框架所启动命令的功能性防火墙规则：

- Windows 不允许把防火墙规则匹配到受限令牌的非主体身份。这意味着我们无法把防火墙规则应用于「任何在其受限 SID 列表中包含我们合成 SID 的令牌」。
- 虽然我们可以创建匹配特定二进制的防火墙规则，但那只能限制 `codex.exe` 本身的网络访问，无法作用于智能体代表用户启动的进程，比如 Git 或 Python 进程。
- 其他防火墙匹配维度也不合适。按用户限定的规则在非提权设计中仍然匹配真实的 Windows 用户，而不只是受限子进程。程序路径规则太粗：它们可以笼统地封锁 `codex.exe` 或 `python.exe`，却无法只封锁这一次被沙箱化的 `python.exe` 调用。基于端口或地址的规则则完全是错误的政策。例如，我们不想封锁端口 443；我们想封锁的是这个特定受限进程树的任意出站访问。

要把防火墙规则专门应用到我们的沙箱化命令上，我们需要以一个单独的主体（principal）来运行它们，而不是以「真实」用户运行。这个思路把我们引上了一条新路：放宽我们的「不提权」约束。

## 重新设计：「提权沙箱」

沙箱的下一次迭代（也是我们当前的实现）需要在设置阶段具备提权的管理员权限。因此我把它称为「提权沙箱」。在 Codex 于系统上启动命令的边界处，提权沙箱看起来和非提权沙箱一样：它仍在受限令牌下运行子进程——同样是 `write_restricted` 令牌，受限 SID 列表同样是 `[Everyone, Logon, Synthetic]`——然而，这个令牌的主体不再是实际的 Windows 用户，而是 Codex 自行创建的两个本地用户之一：

- `CodexSandboxOffline`（被防火墙规则针对的那个）
- `CodexSandboxOnline`（不被防火墙规则针对的那个）

这个看似很小的细节，实际上对沙箱本身、谁能使用它、以及其设置与运行时执行的复杂性都有很大影响。

它在形态上与非提权原型相似，只是引入了防火墙规则和一个实际运行命令的专用 Windows 用户。（不过，这些新概念的引入意味着，在沙箱能够开始运行并保护命令之前，还有更多的设置工作要做。）

### 我们现在需要一个正式的设置步骤

非提权沙箱设计有一个简单的设置步骤，工作量相对较小：

- 按需创建一个合成 SID
- 为 `sandbox-write` 合成 SID 应用 ACL

而提权沙箱要做的更多：

- 创建合成 SID（若尚未创建）
- 创建在线与离线沙箱用户（若尚未创建）
- 在本地存储新建用户的凭据，并使用 Windows 数据保护 API（DPAPI）加密，存放在沙箱用户实际无法读取的位置
- 创建防火墙规则以阻断 `CodexSandboxOffline` 用户的全部出站网络访问；若规则已存在，则验证其正确性

设置阶段还有一个额外的麻烦。Codex 沙箱的读取权限预期与实际 Windows 用户相当。在非提权沙箱中，受限令牌的主体 SID 就是 Windows 用户，这一点自然成立。但当主体变成一个新的 `CodexSandbox` 用户时，这就不是免费得来的了。Windows 上许多相关目录会向「经过身份验证的用户（Authenticated Users）」授予读/执行权限。一个显著的例子是用户的配置文件目录（profile directory）。默认情况下，Windows 用户无法读取其他 Windows 用户的配置文件目录，因此在许多场景下连简单的文件读取都会失败。

为了解决这个问题，我们在沙箱设置流程中又加了一层——用于在可能尚无此类 ACL 的地方向沙箱用户授予*读取* ACL。例如，针对一些常用的 Windows 目录：

- `C:\Users\<real-user>`
- `C:\Windows\`
- `C:\Program Files\`
- `C:\Program Files (x86)\`
- `C:\ProgramData\`

由于这份目录清单是尽力而为的，而且在每个目录上安装 ACL 都可能相当昂贵，我们以异步方式运行这段逻辑，让对用户造成阻塞的沙箱设置步骤不必等待它们完成。

我们把设置逻辑封装进独立的二进制文件，部分原因是为了只在需要时跨越 UAC 边界。但更深层的原因是架构性的：沙箱设置的工作与 `codex.exe` 有本质的不同。把沙箱设置逻辑放在一个专用二进制里，让 `codex.exe` 保持为一个普通的、非提权的执行框架；让仅限 Windows 的设置机制不至于使 `codex.exe` 在其他平台上变得臃肿；把耗时较长的设置工作与主进程的生命周期解耦；并且为我们提供了一个统一的地方来处理沙箱需要的不同设置路径。

### 命令运行器是实际运行用户命令的新二进制

由于 Windows 用户与令牌登录边界的工作方式，我们无法再像非提权沙箱那样创建受限令牌并在其下启动进程。要以另一个 Windows 用户的身份真正启动命令，我们的第一个想法是如下流程：

- `codex.exe` 以真实 Windows 用户身份运行。然后，Codex 按顺序执行以下步骤：
  - 为沙箱用户调用 `LogonUserW(...)`。
  - 在该沙箱用户令牌上调用 `CreateRestrictedToken(...)`。
  - 使用这个受限的沙箱用户令牌调用 `CreateProcessAsUserW(...)`，启动最终的子进程。

在实践中，这个理想流程行不通，因为 `CreateProcessAsUserW(...)` 处有一道特权墙。这意味着 `codex.exe` 可以为沙箱用户创建受限令牌，却无法从边界的真实用户一侧用它可靠地启动子进程。我们需要一个已经以沙箱用户身份运行的进程——这样限制步骤和最终启动就能发生在边界的沙箱用户一侧，而不是真实用户一侧。

这一需求催生了 `codex-command-runner.exe`——一个新的二进制，它唯一的职责就是铸造受限令牌并启动所请求的命令。我们没有让 `codex.exe` 独自完成整个流程（真实用户 → 沙箱用户 → 受限令牌 → 子进程），而是把它拆成两段：

**第一段**

- `codex.exe` 调用 `CreateProcessWithLogonW(...)`，以沙箱用户身份启动 `codex-command-runner.exe`，此时还不使用受限令牌。

**第二段**

- 在运行器内部，`OpenProcessToken(GetCurrentProcess(), ...)` 打开运行器自己的令牌——它已经属于沙箱用户。
- 运行器调用 `GetTokenInformation(...)` 提取沙箱登录 SID，然后调用 `CreateRestrictedToken(...)` 构建最终的受限令牌。
- 仍在运行器内部，它用这个受限令牌调用 `CreateProcessAsUserW(...)`，启动真正的子进程。

### 全景

Albert Einstein 说过：「凡事应尽可能简单，但不能过于简单。」本着这种精神，我们的设计恰如其分地解决了每个问题。最终架构包含我们前面讲过的四层：

- `codex.exe` 本身
- `codex-windows-sandbox-setup.exe`，负责处理所有与提权设置相关的工作
- `codex-command-runner.exe`，负责以受限令牌运行命令
- 子进程

当我最初着手这个项目时，我对它最终会走向哪里并没有清晰的概念。我的方法是从在 Codex 与操作系统之间的边界上加入沙箱能力开始。这一方法与 Codex 沙箱在 macOS 和 Linux 上的实现方式非常接近。

随着我更深入地了解 Windows 提供的具体工具，并经过数十次在安全性与易用性之间的权衡决策，这个系统长成了如今的形态——多个二进制文件、自定义用户、防火墙规则、一个提权设置步骤、异步进程，等等。

这并不是一个特别简单的系统，但每一处复杂度都是出于必要而添加的，为的是构建一个既安全、又尽可能不妨碍用户的沙箱。

## 在安全与实际可用性之间取得平衡

在为 Windows 上的 Codex 用户打造良好用户体验的过程中，我们的目标是做出安全而不牺牲可用性的东西——使用 Codex 的全部意义就在于让智能体能够在你不用时刻盯着的情况下完成工作。

这个项目最大的教训之一是：Windows 并没有直接递给我们一个能干净地对应到「安全的自主编程智能体」的原语。我们组合了多个工具和概念才构建出一个连贯的东西。一些早期想法走进了死胡同。最终设计是早期原型的混合体，每个原型都解决了问题的一部分。

另一个教训是：编程智能体的安全与更经典的应用安全是两回事。Codex 必须在真实的开发者工作流中可用。工程工作的核心在于，在对智能体负载的兼容性与真正的强制执行之间求得平衡。这种张力塑造了最终设计中的种种取舍。
