# 执行框架工程的经验教训

> 原文：[Lessons from harness engineering](https://openai.com/index/harness-engineering/) · OpenAI 博客

当人们谈论智能体性能时，通常指的是模型能力。但任何发布过智能体产品的人都知道，模型周边的软件——执行框架（harness）——至关重要。执行框架是包裹着模型的工具、环境脚手架、上下文管理与交互设计的集合，正是它把一个模型变成可用的智能体。同一个模型配上不同的执行框架，在真实任务上的表现可以相差数十个百分点。

过去一年，我们一直在打造我们的编程智能体 Codex，覆盖终端、IDE、网页与代码评审等多种形态。本文汇集了这项工作带来的经验——那些我们当初希望早已知晓的事情。

## 环境是模型的一部分

智能体的表现取决于它所处的环境。我们的云沙箱早期版本给模型的是一个全新的代码检出：没有构建缓存、没有安装好的依赖、也没有机密信息的访问权限——每个任务都是冷启动。智能体把大量 token 浪费在让自己进入能够运行测试的状态上。在智能体启动之前预先安装依赖、预热缓存，就在模型零改动的情况下大幅提高了任务完成率。

在投入提示词之前，先投入环境。一个 `make setup` 目标、一套预装好的工具链、一份可读性良好的测试运行输出，对智能体成功的帮助胜过大多数提示词工程。

## 反馈回路胜过指令

我们过去会写详细的指令，告诉模型如何验证自己的工作。现在我们更多地转而设计回路本身：让智能体以低廉、快速的方式运行相关测试、看到失败并加以修复。一个能把编译器错误、测试输出和 lint 结果以结构化工具响应形式呈现出来的执行框架，能让模型自我纠错。而一个让模型只能去猜测改动是否生效的执行框架，产出的则是自信却残缺的补丁。

具体而言：返回错误时带上文件路径和行号，对嘈杂输出做智能封顶而不是盲目截断，并且绝不吞掉 stderr——人类只会略读的调用栈回溯，模型往往真的会去读。

## 上下文是最稀缺的资源

模型的上下文窗口很大，但有效上下文要小得多：注意力会随距离衰减，花在样板内容上的每一个 token，都是没有花在问题本身的 token。杠杆率最高的执行框架工程，在于精心筛选进入上下文的内容。

- 大力压缩工具输出，但要保留错误信息——失败测试的最后 200 行，比成功构建的前 2,000 行更重要。
- 维护一份滚动更新的摘要，记录智能体尝试过什么、学到了什么，由智能体自己在步骤之间撰写。
- 给智能体提供检索的手段，而不是通读一切的手段。仓库地图和符号索引让模型无需吞下整个代码库也能在其中导航。

## Diff 评审是产品界面

编程智能体面向用户的时刻就是 diff 呈现的那一刻。此前的一切——规划、执行、自查——都是为了使这个 diff 值得信任。我们学会围绕变更评审来优化体验：界定好每个任务的范围，让 diff 易于理解；让智能体结合自己做出的变更来解释推理；支持增量式的后续请求（「顺便把文档也更新一下」），而不是推倒重来。

一条相关经验：智能体应当默认保守，并对不确定性直言不讳。一条写着「我无法验证这次重构保持了原有行为，因为测试没有覆盖 X」的 diff，远比一次无声无息的改动有用。

## 评测执行框架也是产品代码

我们内部的评测执行框架（eval harness）——负责在沙箱中运行任务、为 diff 打分、记录追踪信息——最初只是一个脚本，如今已成为我们维护的最承重的软件之一。现在，每一次执行框架的改动都按照评估模型改动的方式来评估：它是否提升了任务完成率？是否改变了 token 成本？是否改变了失败分布？

要把执行框架的改动与模型改动分开度量。收益明明来自回路的改动，却被归功于模型——这种情况太容易发生了。
