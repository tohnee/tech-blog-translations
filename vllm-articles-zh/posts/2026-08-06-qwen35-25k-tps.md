# vLLM 在 Qwen3.5 上达到 25K 总 TPS/GPU

> 原文：[vLLM Reaches 25K Total TPS/GPU on Qwen3.5](https://vllm.ai/blog/2026-08-06-qwen35-25k-tps) · vLLM 博客

作者：vLLM 团队

[#性能](https://vllm.ai/blog/tags/performance)[#qwen3.5](https://vllm.ai/blog/tags/qwen3.5)[#分离部署](https://vllm.ai/blog/tags/disaggregation)

## 引言

Qwen3.5 于 2026 年初发布，至今仍是客户中使用最广泛的模型之一。由于其新颖的混合注意力架构，以分离模式服务它会带来额外的挑战与性能优化机会。感谢 vLLM 社区持续的贡献，Qwen3.5 的分离服务路径如今已经成熟，我们很高兴汇报主要贡献、在 GB200 NVL72 系统上的最新性能，以及供你复现的配方与最佳实践。在这篇博客中，我们将展示 **你** 如何获得超过 25K 的总 TPS/GPU 性能。

## 挑战与关键优化

Qwen3.5 的混合架构把全注意力层与门控增量网络（Gated Delta Network，GDN）层结合在一起。这带来两个截然不同的优化挑战：在 Blackwell GPU 上加速 GDN 计算，以及在预填充与解码 worker 之间正确传输异构的注意力/GDN 状态。

P/D 服务的 SSM 支持由 vLLM 社区通过 [NIXL 分离路线图](https://github.com/vllm-project/vllm/issues/33702)推动。关于异构缓存布局、逻辑与物理块映射以及张量并行状态传输的更深入讨论，请参见详细的[混合 SSM 分离博客文章](https://vllm.ai/blog/2026-04-21-hybrid-ssm-disagg)。我们重点介绍以下对 Qwen3.5 性能尤为重要的贡献。

### 1. 针对 Blackwell 优化的 GDN 预填充

[FlashInfer: Add Blackwell GDN prefill kernel #3001](https://github.com/flashinfer-ai/flashinfer/pull/3001)

与之前的 FLA/Triton 实现相比，新的 GDN 内核在 Qwen3.5 的各模型规模、张量并行配置、序列长度和批次形状上带来约 1.02× 到 5.78× 的性能提升。

随后 [vLLM PR #40717](https://github.com/vllm-project/vllm/pull/40717) 在 vLLM 的预填充一侧启用了该内核。在一台运行 Qwen3.5-397B-A17B-NVFP4 的 8×B200 系统上，vLLM 集成带来了：

- 在所测微基准中 GDN 内核性能最高提升 5.92×。
- 在仅预填充工作负载（ISL/OSL = 8192/1）上端到端预填充吞吐提升 1.13×。
- 平均 TTFT 降低 12%（仅预填充工作负载 8K/1）。

在受支持的 Blackwell 配置上，当 GDN 后端设为 `auto` 时，vLLM 会自动选择 FlashInfer 路径。也可以显式指定：

```
--gdn-prefill-backend flashinfer

```

### 2. 混合缓存与 GDN 状态传输

混合 SSM-注意力模型的分离服务建立在 [[Core][KVConnector] Support HMA+NixlConnector #35758](https://github.com/vllm-project/vllm/pull/35758) 以及[混合 SSM 分离博客文章](https://vllm.ai/blog/2026-04-21-hybrid-ssm-disagg)中描述的一组连接器改动之上。这个 PR 是必要前提：它把 HMA 的逻辑块映射到正确的物理内存区域，使 NIXL 只传输属于各层类型的缓存区域，把传输描述符从 4,284 个减少到 1,650 个，并在小规模节点内 H100 设置中把吞吐最多提升约 7%。但 Mamba 风格状态在布局、大小和传输语义上的差异足够大，仅靠 HMA 支持不足以实现正确或高效的 P/D 服务。

混合 SSM-FA 分离的主 PR 是 [[PD][Nixl] Add support for hybrid SSM-FA models #36687](https://github.com/vllm-project/vllm/pull/36687)，它增加了双描述符视图与同构 TP 支持，使预填充与解码 worker 能够通过 NIXL 传输全注意力 KV 缓存和 Mamba 风格 SSM 状态。同一栈中的相关后续改动包括：

- [[Kernel] Mamba support different layout for Conv state #37416](https://github.com/vllm-project/vllm/pull/37416)
- [[NIXL][Mamba][3/N] Heterogeneous TP: 3-read conv state transfer #37635](https://github.com/vllm-project/vllm/pull/37635)
- [[SSM/Mamba] Follow-up: N-1 prefill for P/D disaggregation #37310](https://github.com/vllm-project/vllm/pull/37310)

双描述符视图、物理/逻辑块桥接与卷积状态传输如何协同工作，请参见[混合 SSM 分离博客文章](https://vllm.ai/blog/2026-04-21-hybrid-ssm-disagg)。

具体到 Qwen3.5，[PD disagg with NIXL Connector: GDN support (Qwen3.5) #41869](https://github.com/vllm-project/vllm/pull/41869) 把这条路径扩展到了 GDN 层。

### 3. 无竞态的异步调度

这两个补丁修复了 KV 块传输中的竞态条件——此前这些竞态使异步调度不可用：一旦启用，精度会直接跌到零。事实证明，异步调度是突破 25K tok/s/GPU 的关键特性之一，因此两处竞态都必须解决。

- [[KV Connector] Fix PD async scheduling race condition for hybrid attn models #48481](https://github.com/vllm-project/vllm/pull/48481)
- [[Bugfix] Defer block freeing until in-flight steps finish under async scheduling + PD KV consumer #45357](https://github.com/vllm-project/vllm/pull/45357)

## 性能

### 1. 环境配置

测量在通过 NVLink72 互连的 GB200 集群上进行。我们使用 ISL/OSL = 8192/1024。被评估的模型是 [Qwen3.5-397B-A17B-NVFP4](https://huggingface.co/nvidia/Qwen3.5-397B-A17B-NVFP4)。性能在固定的解码拓扑和恒定的解码端点数量上测得。在此配置中，解码侧使用一个 DEP8 端点（8 GPU 上的数据并行 + 专家并行）。预填充侧则评估了 4 到 8 个端点的配置，每个端点使用固定的 DEP2 拓扑。

要复现结果，请使用最新的 vLLM [vllm/vllm-openai:nightly-d223c90](https://hub.docker.com/layers/vllm/vllm-openai/nightly-d223c900d85224c02f2162ee2c757a769e99f519/images/sha256-987393f42c48b8a649961a3484d95d400db184b64e4e1bb7f77cb91536d0f05e) Docker 镜像、[Dynamo](https://github.com/ai-dynamo/dynamo) `1.2.0.dev20260526` 和 [srt-slurm](https://github.com/NVIDIA/srt-slurm) `v1.0.32`。本文使用的所有配方都可在 [srt-slurm-recipes](https://github.com/NVIDIA/srt-slurm-recipes) 仓库中获取。

### 精度结果

首先，我们测量了所有服务配置的精度，以确保性能结果有效。为此我们使用标准的 GSM8K（小学数学 8K）基准测试。用 srt-slurm 运行 GSM8K 很简单，只需在配方文件中加入以下基准测试块：

```
benchmark:
  type: "gsm8k"
```

全部五种配置的精度结果均为 **88%**，与我们在非分离（aggregated）Qwen3.5 运行中观察到的精度一致。

### 2. 关于配方设置选择的说明

性能测量使用定长输入序列/输出序列基准，在 `random_range_ratio=0.8` 的随机数据集上进行。配方本身以及最重要的设置将在下文[配方与最佳实践](#recipes--best-practices)一节介绍。

各配置的 Pareto 曲线见[图 1](#figure-1)，合并所有配置后得到的最终 Pareto 前沿见[图 2](#figure-2)。每 GPU 总 TPS 达到 **25,000** token/秒。并发从 64 扫到 5120。我们没有测量 1 到 32 范围内的低并发，因为这里的重点是 Pareto 曲线的左端——最大化每 GPU 总 TPS 指标。在另一端，我们没有超过 5120，因为在那里解码侧的 KV 缓存容量开始不够用——在整个测量过程中，我们有意把解码侧固定为单个 8×GB200 端点。把并发推得更高完全可行，但需要在解码侧增加 GPU。

## 配方与最佳实践

本文使用的所有配方都在 [srt-slurm-recipes](https://github.com/NVIDIA/srt-slurm-recipes/tree/main/recipes/multi-node/Qwen3.5/GB200/8k1k/vllm/disagg) 仓库中，每个配方都用一条命令启动：

```
srtctl run --file <recipe>.yaml
```

命名规则是 `NxDEP2-1xDEP8`，其中 N 是运行 DEP2 的预填充端点数量，对应单个 DEP8 解码端点；共有五个基础配置，从 4×DEP2 到 8×DEP2。每个配置都带三个派生变体：基础文件用 sa-bench 扫描 64…3072 的并发；`-acc` 变体在同一拓扑上运行五次 GSM8K；`-cc4096` / `-cc5120` 各自捕捉单个高并发点，并把解码侧的 `max-cudagraph-capture-size` 分别提高到 640 和 768。

配方中的大多数设置都是标准的、在所有配置间共享，但有几点值得单独说明：

- `VLLM_SSM_CONV_STATE_LAYOUT=DS` —— 分离服务中 SSM 模型的必设项；没有它，卷积状态传输无法工作。我们的配方还传入了 `--no-disable-hybrid-kv-cache-manager`；此后几个版本 vLLM 已默认启用 HMA，该标志不再需要。
- `--async-scheduling` —— 达到每 GPU 25K tok/s 的关键特性之一。它要求 vLLM 构建已包含上文讨论的竞态条件修复。
- `--mamba-ssm-cache-dtype bfloat16` —— 显著增加解码端点的有效 KV 缓存容量。
- `--language-model-only` —— Qwen3.5 是多模态模型，对于纯文本工作负载，该标志不仅禁用多模态输入，还解锁注意力层中融合的 QK-norm + RoPE + 门控路径。
- 预填充侧设置 `--max-num-batched-tokens 16384`，即 2× ISL。在预填充端点较少时（{4, 5, 6}×DEP2），预填充成为瓶颈，使解码侧闲置在峰值吞吐之下，因此我们让每个预填充步骤一次批处理两个完整提示而不是一个——在高并发下相当于每 GPU 总 TPS 约 **+8%**。
- 解码侧的 `--max-cudagraph-capture-size` —— 在两个最高并发点上提高到 `cc/8 + 128`（cc=4096 时为 640，cc=5120 时为 768），其中 8 是解码端点上的 DP rank 数。vLLM 默认把捕获的图上限设为 512，这对 cc=3072 以内已经足够。我们并不确定本文报告的 Pareto 数字是否真的需要这样做，只是出于谨慎而设置。
- 前缀缓存被禁用：在随机数据集上它毫无收益。
- `--stream-interval 100` —— 降低高并发下的前端开销。注意它会以 100 token 为单位缓冲流式输出，因此确实会影响测得的逐 token 延迟；如果你优化的是 ITL/TPOT 而非总吞吐，请牢记这一点。

最后，分享几件帮我们省下大量时间的实用经验。

在排查某个具体配置时，`--api-server-count 1` 非常有用。在数据并行端点上，vLLM 默认把 API 服务器数量设为数据并行大小，而当 API 服务器多于一个时，它会完全关闭默认的统计日志，以免报告不完整的数字。把数量强制设为 1 可以找回这些日志：每 10 秒——间隔可通过 `VLLM_LOG_STATS_INTERVAL` 配置——服务器会打印提示与生成吞吐以及 KV 缓存利用率。没有这些指标，我们几乎不可能定位各配置的瓶颈，也无法理解某个选项为何在我们的工作负载上有效。

另外值得设置三个环境变量：`DYN_LOG=error`、`DYN_SDK_DISABLE_ANSI_LOGGING=1` 和 `VLLM_LOGGING_COLOR=0`。第一个会大幅削减 Dynamo 日志的数量，另外两个则抑制日志输出中的部分（不是全部！）ANSI 转义序列。没有它们，你的日志文件很可能没法供人阅读，主要因为 Dynamo 默认会产生海量日志。

## 下一步

我们目前的测量主要集中在 Pareto 曲线的左端，尽可能榨取每 GPU 总 TPS。接下来，我们计划转而扫描能最大化每用户 Gen TPS 的 PD 配置。要进入那个区间，需要从 DEP 拓扑转向 TEP（张量并行 + 专家并行）或纯 TP——它们通常能提供更好的单用户性能。增加使用的 GPU 数量是另一个我们预期在此会有回报的杠杆。
