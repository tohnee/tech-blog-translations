# vime + ROCm：在 AMD Instinct™ GPU 上进行端到端 RL 后训练

> 原文：[vime + ROCm: End-to-End RL Post-Training on AMD Instinct™ GPUs](https://vllm.ai/blog/2026-07-10-vime-rocm) · vLLM 博客

作者：AMD 贡献者与 vime 社区

[#强化学习](https://vllm.ai/blog/tags/reinforcement-learning)[#硬件](https://vllm.ai/blog/tags/hardware)[#生态](https://vllm.ai/blog/tags/ecosystem)[#后训练](https://vllm.ai/blog/tags/post-training)

自 vime 发布以来，AMD 团队一直与 vime 团队紧密合作，为 ROCm 带来兼容性支持，在 AMD Instinct 硬件上验证端到端流水线，上游化 ROCm 专属修复，并发布预构建容器，让 AMD 用户无需从源码构建即可上手。

我们很高兴宣布 vime——vLLM 生态的强化学习框架——在 AMD Instinct MI355X GPU 上获得 ROCm 支持。这一支持让大规模 RL 后训练工作流可以在 AMD 硬件上原生运行，把完整的 vime 流水线带到 ROCm 生态。

本文涵盖：vime 及其架构概览、AMD Instinct GPU 为何适合 RL 负载、ROCm 支持现状与已验证特性，以及在 ROCm 上运行端到端 RL 训练任务的实操走读。

## vime 解析

vime 由 vLLM 团队于 2026 年 6 月[发布](https://vllm.ai/blog/2026-06-09-announcing-vime)，已迅速成为 vLLM 生态中 RL 后训练的焦点。借助 ROCm 支持，这些工作流现在开箱即可在 AMD Instinct GPU 上原生运行。

![vime 架构。](https://vllm.ai/blog-assets/figures/2026-07-10-vime-rocm/data-buffer.png)

vime 架构。

vime 采用 slime 的三阶段、训练-推理解耦设计，不同之处在于 rollout 后端是 vLLM 而非 SGLang：

- **训练（Megatron）：** 主训练循环，负责参数更新以及向 rollout 侧同步权重。
- **Rollout（vLLM + 路由器）：** 推理采样，产出带奖励或校验器信号的训练样本。
- **数据缓冲区（Data Buffer）：** 连接训练侧与 rollout 侧，管理 prompt 注入和自定义 rollout 逻辑。

这条完整流水线现已在 ROCm 上完成端到端验证。

## 为什么选择 AMD Instinct™ GPU

RL 后训练是现代机器学习中最吃显存的负载之一。每个训练步都要同时持有训练侧权重（Megatron 格式）和推理侧 KV 缓存（供 vLLM rollout 使用）。在共置（colocated）模式下，二者竞争同一个设备内存池。出于以下几个原因，AMD Instinct MI300X 和 MI355X GPU 非常适合这种负载形态。

- **大容量统一 HBM：** MI300X 每张 GPU 提供 **192 GB** HBM3，MI355X 进一步提升到 **288 GB**。这样的余量让大模型训练更容易装下，无需激进的张量并行来分摊显存压力，降低拓扑复杂度并提高集群利用率。
- **高显存带宽：** HBM3 在 MI300X 上提供超过 **5 TB/s** 的聚合带宽；借助 HBM3E，MI355X 达到 **8 TB/s**。RL rollout——大规模的自回归 token 生成——本质上受显存带宽约束：每个解码步都要从 HBM 加载完整 KV 缓存和模型权重。更高的带宽缩短每步延迟，并提升 rollout 阶段的吞吐量——在大多数 RL 流水线中，rollout 占据了整个训练步时间的大头。
- **开放的软件生态：** ROCm 是 AMD 的开源 GPU 计算平台，构建在开放标准（HIP、LLVM、MIOpen）之上。vLLM 和 PyTorch 都原生支持 ROCm，这意味着 vime 无需单独的代码路径即可继承完整的 vLLM rollout 栈。使用 ROCm 的团队已经拥有熟悉的工具链，可以直接扩展。

## 训练细节

让 vime 在 ROCm 上运行需要验证并集成栈中的多个组件。下面是你在 AMD GPU 上运行 vime 时底层发生的事情。

- **Megatron-LM 训练后端：** vime 使用 Megatron-LM 作为训练引擎。在 ROCm 上，Megatron 栈借助一个 ROCm 兼容的 fork 和一个小补丁即可干净构建——该补丁在非 CUDA 构建上保护 CUDA 融合内核的初始化。训练循环在 ROCm 兼容的 Megatron 补丁和 ROCm 专属启动标志下运行。梯度累积使用原生 PyTorch 路径，在 ROCm 上完全支持。从 HuggingFace 格式到 Megatron torch\_dist 格式的检查点转换在单张 GPU 上即可干净完成，产出的布局可被 Megatron 在每次训练开始时正确加载。
- **共置权重同步：** 共置模式下，Megatron 与 vLLM 共享同一个 GPU 池，而不是分别跑在不同的节点分区上。每个优化器步之后，Megatron 通过 IPC 把更新后的权重同步给 vLLM 引擎，rollout worker 始终基于最新策略生成，无需网络往返。在 ROCm 上，`torch.cuda.get_device_properties(i).uuid` 接口返回稳定、进程间一致的设备 UUID，因此 vime 以 UUID 为键的 IPC 路由无需修改即可正确工作。
- **GPU 可见性与 Ray 集成：** ROCm 用 `HIP_VISIBLE_DEVICES` 控制 GPU 分配。vime 启动脚本在设置 `CUDA_VISIBLE_DEVICES` 的同时设置它，使 Megatron 训练 actor 与 vLLM 子进程在整个作业中看到一致的设备序号。Ray 的 AMD GPU 管理器被配置为不覆盖这些可见性掩码，因此作业 driver 与所有 Ray actor——包括 Megatron 训练 actor 及其 worker 进程——都在正确的 GPU 集合上运行而不发生争用。容器还以调高的文件描述符上限启动（`--ulimit nofile=1048576:1048576`），这是 Ray 大规模拉起全部 actor worker 所要求的。

## 上手：在 AMD GPU 上运行 vime

vime 提供带预构建容器的 ROCm 就绪工作流，你只需极少的配置即可跑通完整 RL 流水线。

### 启动 vime ROCm 容器

```
# Pull the ROCm image
docker pull vllm/vime-rocm
# Start the container
docker run -d --name vime --ulimit nofile=1048576:1048576 \
  --ipc=host --network=host --device=/dev/kfd --device=/dev/dri \
  --security-opt seccomp=unconfined --group-add video --privileged \
  -e WANDB_API_KEY=$wandb_key vllm/vime-rocm
# The launch script enables W&B online mode, so a valid WANDB_API_KEY is required.

# Enter the container
docker exec -it vime bash
```

容器内预装了 vLLM 和 Megatron-LM，vime 代码库位于 `/root/vime`。

### 下载模型与数据集

```
# Download model weights (Qwen3-8B)
hf download Qwen/Qwen3-8B --local-dir /root/Qwen3-8B
# Download training dataset (dapo-math-17k)
hf download zhuzilin/dapo-math-17k --repo-type dataset --local-dir /root/dapo-math-17k
```

### 把权重转换成 Megatron 格式

加载 Qwen3-8B 的模型配置，然后运行转换。

```
cd /root/vime && source scripts/models/qwen3-8B.sh
HIP_VISIBLE_DEVICES=0 PYTHONPATH=/root/vime:/root/Megatron-LM \
  torchrun --nproc-per-node=1 tools/convert_hf_to_torch_dist.py "${MODEL_ARGS[@]}" \
  --no-gradient-accumulation-fusion --attention-backend flash \
  --hf-checkpoint /root/Qwen3-8B --save /root/Qwen3-8B_torch_dist
```

> **注意**：在 ROCm 上，用 HIP\_VISIBLE\_DEVICES 替代 CUDA\_VISIBLE\_DEVICES 来选择 GPU。

### 启动 RL 训练

```
NUM_ROLLOUT=100 VISIBLE_GPUS=0,1 bash scripts/run-qwen3-8B-amd.sh
```

这将启动一个训练与推理共置的完整 RL 流水线：

- vLLM rollout worker
- GRPO 训练循环
- On-policy rollout → 训练 → 权重同步循环

**配置说明：**

- `VISIBLE_GPUS` - 两个空闲的 GPU 序号；脚本把执行限制在这些 GPU 上并避免冲突。使用 TP=2、单个 vLLM 引擎、共置模式、DP=1。
- `NUM_ROLLOUT` - 训练步数（冒烟测试默认为 3）。
- 每次运行约需在所选两张 GPU 上合计 **230 GB**。只在空闲显存充足的 GPU 上启动。

> 一次运行结束后，如果要用不同的 `NUM_ROLLOUT` 重新运行，请清空保存目录以避免检查点不匹配：`rm -rf /root/Qwen3-8B_vime/`

## 性能结果

按照上面的操作手册，我们测试了多个模型，如 Qwen3-4B、Qwen3-8B（稠密）和 Qwen3-30B-A3B（MoE）。以下是我们运行上文 Qwen3-8B 示例得到的一些性能数据：

![在 MI355X 上运行 Qwen3-8B 模型时吞吐量呈缓慢上升趋势。](https://vllm.ai/blog-assets/figures/2026-07-10-vime-rocm/image.png)

在 MI355X 上运行 Qwen3-8B 模型时吞吐量呈缓慢上升趋势。

如图所示，MI355X 上的吞吐量在 100 个训练步中保持在约 4,100 `tokens_per_gpu_per_second`，并随时间略有上升。这一改善反映了策略在训练推进中学会产出更可预测的结果：更短或更均匀的生成降低了解码方差，让 vLLM rollout 引擎能更高效地批处理。

![在 MI355X 上运行 Qwen3-8B 模型时，训练-rollout logprob 绝对差稳定在 0.012 左右。](https://vllm.ai/blog-assets/figures/2026-07-10-vime-rocm/image-1.png)

在 MI355X 上运行 Qwen3-8B 模型时，训练-rollout logprob 绝对差稳定在 0.012 左右。

`train_rollout_logprob_abs_diff` 指标衡量训练侧对数概率与 rollout 侧对数概率之间的偏差，在整个运行中稳定在 0.012 左右并略有下降。Megatron 训练后端与 vLLM rollout worker 之间的权重同步让两侧保持一致，避免了原本会污染策略梯度信号的 logprob 漂移。稳定且低的 logprob 差是可靠 GRPO 更新的前提；如此低的数值与 NVIDIA 硬件上报告的结果相当。

![在 MI355X 上运行 Qwen3-8B 模型时，raw reward 从接近 0 爬升到第 100 步时约 0.5~0.6。](https://vllm.ai/blog-assets/figures/2026-07-10-vime-rocm/image-2.png)

在 MI355X 上运行 Qwen3-8B 模型时，raw reward 从接近 0 爬升到第 100 步时约 0.5~0.6。

`raw_reward` 在采样的训练 prompt 上测量：第 0 步接近 0，到第 100 步逐渐爬升至约 0.5~0.6。初始化时模型尚未被 RL 塑形，用基础预训练分布来应对数学题；面对 dapo-math-17k 数据集中的竞赛级问题，刚初始化的策略几乎解不出几道，奖励接近零。随着训练推进，策略从它部分或全部做对的问题上获得梯度信号，开始偏向校验器给予奖励的推理模式。训练奖励上升表明在采样训练 prompt 上的优化进展；注意 ROCm 启动器禁用了评估（`EVAL_ARGS=()`），因此需要 held-out 评估来衡量泛化能力。

## AMD 上的特性支持路线图

目前，vime 的核心功能已在 AMD 上获得支持，包括：

- GRPO 训练
- 训练与 rollout 共置
- 异步（非共置）训练，actor 与 rollout 使用互不重叠的 GPU 池
- Megatron-LM 训练后端
- vLLM rollout 后端
- Qwen3 稠密与 MoE 模型支持

展望未来，vime 与 AMD 团队致力于扩展更多能力支持，包括：

- 完整的 vLLM 路由器与 PD 分离支持
- FP8 流水线优化
- 面向 AMD MoE 负载的 R3（Rollout Routing Replay）
- 异步训练流水线的性能优化（改善训练-rollout logprob 偏差并解决内存泄漏问题）
- 面向多轮工具调用与多智能体场景的智能体 RL

我们的目标是随 vime 与 vLLM 路线图演进，持续提升性能与能力。
