# DeepSeek-V3.2-Exp 登陆 vLLM：细粒度稀疏注意力的实战

> 原文：[DeepSeek-V3.2-Exp in vLLM: Fine-Grained Sparse Attention in Action](https://vllm.ai/blog/2025-09-29-deepseek-v3-2) · vLLM 博客

作者：vLLM 团队

[#模型支持](https://vllm.ai/blog/tags/model-support)

### 引言

我们很高兴地宣布对 [DeepSeek-V3.2-Exp](https://huggingface.co/deepseek-ai/DeepSeek-V3.2-Exp) 的 Day 0 支持，其特色是专为长上下文任务设计的 DeepSeek Sparse Attention（DSA，DeepSeek 稀疏注意力）（[论文](https://github.com/deepseek-ai/DeepSeek-V3.2-Exp/blob/main/DeepSeek_V3_2.pdf)）。在这篇文章中，我们将展示如何在 vLLM 中使用该模型，并深入剖析在 vLLM 中支持 DSA 时遇到的各种挑战。

具体来说，DSA 的 lightning indexer 连同稀疏注意力给连续批处理和分页注意力带来了挑战。例如，我们需要对 indexer 模块分别处理预填充和解码，并小心管理不同的缓存布局。

在性能方面，vLLM 集成了 DeepGEMM 中的 lightning indexer CUDA 内核，以及 FlashMLA 中新的稀疏注意力内核。我们对 Blackwell 支持也感到兴奋。与 NVIDIA 合作，你可以直接在 B200 和 GB200 上运行该模型！

![](https://vllm.ai/blog-assets/figures/deepseek-v3-2/dsa-explained.png)

图 1：DeepSeek Sparse Attention（DSA）机制示意图。

### 使用指南

要开始使用 DeepSeek 3.2，请按照 [recipes 文档](https://docs.vllm.ai/projects/recipes/en/latest/DeepSeek/DeepSeek-V3_2-Exp.html)中的安装说明操作。我们仍在通过这个 [PR](https://github.com/vllm-project/vllm/pull/25869) 改进初始支持。已知问题请参见[跟踪 issue](https://github.com/vllm-project/vllm/issues/25877)。

安装完成后，在 16×H100、8×H200 或 8×B200 上，你可以用张量并行运行该模型（专家并行存在一个小 bug，我们正在修复）：

```
vllm serve deepseek-ai/DeepSeek-V3.2-Exp --tensor-parallel-size 8

```

对于大规模部署，我们期待在本周晚些时候分享基于 `llm-d` 的一键式 Kubernetes 部署方案。该方案使用 NIXL 以 PD 分离（Prefill-Decode 分离）方式启动 vLLM，然后针对每个 P 实例和 D 实例，将请求高效路由到不同的数据并行 rank。文档即将发布。

启动引擎后，我们建议用*长输入或预期长输出的提示*进行测试。我们建议与 V3.1-Terminus 进行对比，因为它是在相同的数据配比上持续预训练的。

我们仍在对照官方准确率结果验证 vLLM 的实现。在模型权重的前一个版本上，我们达到了预期的 GSM8K 和 GPQA-Diamond 分数，并表明其与 V3.1-Terminus 相近。

### vLLM 中 Top-K 稀疏注意力的实现

#### 新的缓存条目与量化方案

lightning indexer 模块缓存了专门用于索引的 K 值。这意味着对每个 token 来说，现在多了一个供 indexer 使用的 K 缓存。vLLM 分配了独立的缓冲区来保存 indexer K 缓存，与 MLA K 缓存分开。

![](https://vllm.ai/blog-assets/figures/deepseek-v3-2/mla-indexer-block.png)

另一个有意思的点是该模型所支持的 FP8 KV 缓存的处理方式。对于 MLA，每个 token 的 KV 缓存为 656 字节，结构如下：

- 前 512 字节：「量化后的 NoPE」部分，包含 512 个 `float8_e4m3` 值。
- 接下来 16 字节：缩放因子，包含 4 个 `float32` 值。第一个 `float32` 是前 128 个 `float8_e4m3` 值的缩放因子，第二个是接下来 128 个的，依此类推。
- 最后 128 字节：「RoPE」部分，包含 64 个 `bfloat16` 值。为保证准确性，这部分不做量化。

不过，indexer 的 key 缓存是按块（per-block）存储的。这也是我们对该模型只支持块大小 64 的原因之一；另一个原因是 FlashMLA 也是针对这一块大小定制的。前 `block_size * head_dim` 个条目存放数值，其余条目存放缩放因子：

```
x_fp8[ :, : block_size * head_dim] = x_scaled.view(num_blocks, block_size * head_dim).view(dtype=torch.uint8)
x_fp8[ :, block_size * head_dim :] = scales.view(num_blocks, block_size).view(dtype=torch.uint8)

```

在 indexer 中，单个 token 的缓存并不是连续存储的。

#### 掩码下的新计算方式

每个新的 query token 现在都要经过 indexer，计算出需要关注的前 2048 个 token。单个 token 的 query 是形状为 `(h, d)` 的张量，其中 `h` 是 query 头的数量，`d` 是头维度。大小为 `n` 的上下文是形状为 `(n, d)` 的 2D 张量。计算出的 logits（query 与上下文之间的相关性得分）是形状为 `(n, h)` 的张量。用形状为 `(h,)` 的头权重对 logits 加权，得到形状为 `(n,)` 的张量。我们需要产出一个 `(2048,)` 的整数张量，包含 top-2048 token 的索引；如果 token 不足 2048 个，则其余位置用 `-1` 填充。

单个 query token 如何选择要关注的索引一目了然，但批处理的情况要复杂一些。让我们逐步拆解。

新的 DeepGemm 函数调用方式如下：

```
logits = deep_gemm.fp8_mqa_logits(q_fp8, kv_fp8, weights, ks, ke)

```

对于来自同一请求的多个 query token（长度为 `q`，即预填充的情况），它们存储在形状为 `(q, h, d)` 的张量中。上下文仍然有 `n` 个 token，因此上下文仍是形状为 `(n, d)` 的 2D 张量。logits 是形状为 `(q, n, h)` 的张量。用头权重对 logits 加权后，得到形状为 `(q, n)` 的张量。我们需要产出一个 `(q, 2048)` 的整数张量，包含 top-2048 token 的索引。由于因果性，每个 query token 只关注它之前的 token。我们需要为每个 query token 标记上下文的起点和终点。我们用 `ks` 标记起点上下文，用 `ke` 标记终点上下文。`ks` 和 `ke` 都是形状为 `(q,)` 的整数张量。在这种情况下，`ks` 全为 0，而 `ke` 为 `list(range(n - q, n, 1))`。

最后，我们来看看如何对多个请求进行批处理。假设有 `b` 个请求，每个请求分别有 `q1, q2, ..., qb` 个 query token，以及 `n1, n2, ..., nb` 个上下文 token。query token 会被批处理成形状为 `(q1 + q2 + ... + qb, h, d)` 的张量。上下文会被批处理成形状为 `(n1 + n2 + ... + nb, d)` 的张量。logits 会被批处理成形状为 `(q1 + q2 + ... + qb, n1 + n2 + ... + nb, h)` 的张量。我们需要产出一个 `(q1 + q2 + ... + qb, 2048)` 的整数张量，包含 top-2048 token 的索引。

我们需要为每个 query token 标记上下文的起点和终点。我们用 `ks` 标记起点上下文，用 `ke` 标记终点上下文。`ks` 和 `ke` 都是形状为 `(q1 + q2 + ... + qb,)` 的整数张量。

在这种情况下，`ks` 为 `[0] * q1 + [q1] * q2 + ... + [q1 + q2 + ... + qb] * qb`。这里的 `*` 表示列表重复。`ke` 为 `list(range(n1 - q1, n1, 1)) + list(range(n2 - q2, n2, 1)) + ... + list(range(nb - qb, nb, 1))`，再加上 `ks` 的偏移量。

计算出 logits 后，我们需要执行 `topk` 操作。然而一个明显的挑战是：在大批大小、长上下文的情况下，logits 张量会在逐行 `topk` 运行之前被完整物化出来。

#### 融合优化、更多内核与 Blackwell 支持

开始优化性能时，我们先摘了一些「低垂的果实」：

- Top-K 可以用融合内核表达以获得更好的性能。DeepSeek 团队的 TileLang 内核就是一个绝佳的参考！
- 我们在 MLA 隐向量与 indexer key 向量写入 vLLM 页表时对其进行量化。事实证明这件事并不简单，正如前文所述，这套量化方案是全新的、与众不同的。

我们同样高兴地宣布该模型已获得开箱即用的 Blackwell 支持。我们将努力让 Blackwell 平台在今后的模型发布中成为一等公民，因为它的高效率有助于发挥最佳性能！

### 进行中的工作

对于 vLLM 中 DSA 及相关稀疏注意力的优化，我们才刚刚触及皮毛。在接下来的几周里：

- 我们计划将支持的架构扩展到 Hopper 和 Blackwell 之外。
- 我们将把支持扩展到 AMD、TPU 等其他硬件。借助 vLLM 可扩展的系统，开发者可以直接为模型添加支持。例如，[vllm-ascend](https://github.com/vllm-project/vllm-ascend/releases/tag/v0.11.0rc0) 和 [vllm-mlu](https://github.com/Cambricon/vllm-mlu) 已经支持 DeepSeek V3.2！
- 我们会持续测试大规模 wide EP 服务与分离部署。
- 你很快就可以用该模型运行端到端的强化学习（RL）闭环。
- 我们将探索 DeepSeek 提出的「短序列预填充的掩码 MHA 模式」。
- 在本版本中，我们移除了 Hadamard 变换，因为我们观察到它对准确率没有影响。我们会进一步研究！
