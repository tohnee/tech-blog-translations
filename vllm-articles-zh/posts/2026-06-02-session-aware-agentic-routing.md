# 会话感知的智能体路由：面向长程 LLM 智能体的连续性感知模型选择

> 原文：[Session-Aware Agentic Routing: Continuity-Aware Model Selection for Long-Horizon LLM Agents](https://vllm.ai/blog/2026-06-02-session-aware-agentic-routing) · vLLM 博客

作者：Xunzhuo Liu、Bowei He、Huamin Chen、Haichen Zhang（AMD）、Andy Luo（AMD）以及 vLLM Semantic Router 团队

[#生态](https://vllm.ai/blog/tags/ecosystem)[#性能](https://vllm.ai/blog/tags/performance)[#智能体路由](https://vllm.ai/blog/tags/agentic-routing)

长程 LLM 智能体带来了一种单轮提示路由器从未被设计去解决的路由问题。路由器仍然需要知道哪个模型最适合当前请求，但它还需要知道什么时候切换模型会破坏会话。

本文介绍**会话感知智能体路由（Session-Aware Agentic Routing, SAAR）**，这是 vLLM Semantic Router 中的一种会话感知模型选择策略。SAAR 保留了语义路由，但增加了路由器自有的会话记忆、围绕工具循环与不可移植 provider 状态的硬锁、安全的重置边界、前缀缓存感知的切换定价，以及可回放的轨迹。

在 **21,600** 个确定性回合中，SAAR 把模型切换次数减少 **79.29%**，消除 **3,836** 次不安全切换，并将估算的物理模型成本降低 **78.71%**。在 **2,896** 个真实的 AMD ROCm 请求中，它在观察到 **0** 次违规的情况下保持了会话连续性。

![](https://vllm.ai/blog-assets/figures/2026-06-02-session-aware-agentic-routing/hero-v2.png)
*图 1：长程智能体需要能理解会话轨迹的路由决策，而不仅仅是最新一条提示。*

## 从提示路由到会话路由

vLLM Semantic Router 始于一个简单的系统观察：并非每个请求都应该在推理栈中走同一条路径。一个简短的事实性问题、一个安全敏感的提示、一个多模态请求、一个艰难的推理任务和一个领域专属查询，可能都值得不同的处理。

这一理念的第一代是提示路由。路由器从当前请求提取信号、匹配路由决策、选择合适路径。Iris 让这些信号可组合。Athena 通过扩展模型选择、记忆、回放、长上下文信号、多模态原语和 AMD ROCm 部署路径，让路由器更具策略性。

智能体再次改变了路由的单元。

一个编码或研究智能体不是一条提示，而是一个会话。它会规划、调用工具、接收工具输出、编辑文件、运行测试、从错误中恢复、暂停、恢复，并且经常发送非常简短的后续消息，比如“继续”“修一下”“再跑一遍”或“用之前的结果”。这些回合之所以有意义，只是因为它们之前的那段轨迹。

这就是这个里程碑对 Semantic Router 重要的原因。路由器不再只回答：

> 哪个模型应该处理这个请求？

对于智能体流量，路由器还必须回答：

> 现在在这个会话内切换模型安全吗？

第二个问题正是 SAAR 被设计来处理的。

## 为什么单轮路由在智能体场景下会失效

单轮路由可以在局部正确，同时却对整个会话是错的。

看一个典型的使用工具的智能体循环：

| 回合 | 客户端发送的内容 | 提示路由器看到的 | 会话路由器必须记住的 |
| --- | --- | --- | --- |
| 1 | “重构这个模块并运行测试。” | 一个编码任务 | 会话已在某个物理模型上开始 |
| 2 | 模型发出一个工具调用 | 一个模型响应 | 下一个工具结果属于同一个模型 |
| 3 | 客户端发送工具结果 | 一段简短的观察 | 请求该工具的模型应接收这个结果 |
| 4 | 用户说“修复失败的那个用例” | 一条简短的后续 | 这条指令依赖于之前的代码、测试输出和路由状态 |
| 5 | 会话空闲并在稍后恢复 | 一条新的短消息 | 路由器可以重新考虑旧模型是否仍然值得保留 |

仅凭最新一条消息，包含的信息并不足够。提示路由器可能认为工具结果看起来很廉价，就把它发给更小的模型。它可能看到一个泛泛的“继续”，就重新运行常规选择器。它可能没注意到 provider 管理的续接状态只属于某一个物理后端。它可能因为当前消息很短，就丢弃了某个前沿模型的热前缀缓存。

这些错误各自有不同的失败模式：

- 工具结果可能被发给并非发起该工具调用的模型。
- 不可移植的续接 id 可能被发给错误的物理后端。
- 一个长而热的会话可能丢失前缀局部性，变得不必要地昂贵。
- 像 `auto` 这样的逻辑模型可能变得难以调试，因为用户不再知道究竟是哪个物理模型服务了这一回合。

重点不是智能体永远不该切换模型——它们应该切换。好的路由器在任务变难时仍应从便宜模型换到更强的模型，并在会话到达安全边界时切回来。问题在于，路由器需要会话上下文才能知道哪些时刻是安全的。

## SAAR 的设计

SAAR 保留了现有的 Semantic Router 决策流水线。信号仍然从请求中提取，决策仍然被匹配，模型选择算法仍然在匹配到的决策内部对候选模型排序。

SAAR 在这个结果外围增加了一个会话控制层。

![](https://vllm.ai/blog-assets/figures/2026-06-02-session-aware-agentic-routing/policy-flow.png)
*图 2：SAAR 在选择物理模型之前，组合了路由器记忆、硬锁、重置边界、切换经济学和可回放轨迹。*

它包含五个部分：

| 组成部分 | 存储或决定什么 | 为什么重要 |
| --- | --- | --- |
| 路由器记忆 | 上一个物理模型、匹配的决策、阶段、切换次数、空闲时间、缓存证据和回放元数据 | 给路由器提供会话上下文，又不会变成应用记忆 |
| 硬锁 | 防止在活跃工具循环或不可移植的 provider 托管状态期间切换 | 在优化成本或质量之前先保住正确性 |
| 重置边界 | 在空闲超时或决策漂移后允许重新选择 | 防止会话感知路由退化为粘性会话 |
| 切换经济学 | 为交接成本、切换历史、剩余回合先验和前缀缓存结账定价 | 让切换在不同模型层级与会话长度之间呈现非对称性 |
| 回放轨迹 | 记录路由器为什么保持、切换或拒绝切换 | 让 `auto` 这样的逻辑模型可被检视 |

这是一个模型选择策略，而不是端点负载均衡器。Semantic Router 可以通过网关契约选择模型或集群。端点成员关系、健康检查和集群内部的负载均衡仍然是基础设施的职责。

## 最重要的规则：有时路由器必须不切换

最安全的模型切换并不总是最新提示上得分最高的那个。对智能体流量而言，某些回合受到连续性约束。

![](https://vllm.ai/blog-assets/figures/2026-06-02-session-aware-agentic-routing/switch-boundaries.png)
*图 3：工具循环和 provider 托管的续接状态是硬连续性约束；空闲与决策漂移边界则允许安全的重新选择。*

SAAR 把两种情况视为硬锁：

- **工具循环连续性。** 如果一个物理模型发起了工具调用，工具结果应返回给同一个物理模型。后续观察不是一条新提示；它是本地执行循环的一部分。
- **Provider 托管状态。** 如果请求携带不可移植的续接状态，例如属于某个后端的响应标识符，SAAR 会保持上一个物理模型，而不是把状态悄悄移到别处。

这些规则有意强于成本规则。如果切换是不安全的，路由器不应该用更便宜的模型来“买”出一条出路。

SAAR 也定义了相反的边界：路由器何时可以再次切换。空闲超时与决策漂移会重新打开选择。如果智能体暂停得足够久，连续性的价值会衰减。如果匹配到的决策因为用户从代码编辑转向综合、或从检索转向调试而改变，旧的模型选择就不应该一直黏着。

这个区分是会话感知智能体路由的核心：

| 情形 | SAAR 行为 | 原因 |
| --- | --- | --- |
| 工具调用正在等待工具结果 | 保持上一个物理模型 | 工具结果属于该模型的本地推理循环 |
| 请求携带不可移植的 provider 状态 | 保持上一个物理模型 | 该状态在另一个后端上可能无效 |
| 会话空闲超过配置的边界 | 允许重新选择 | 连续性压力已经衰减 |
| 匹配的路由决策发生变化 | 允许重新选择 | 任务形态改变了 |
| 会话很长且在昂贵模型上保持热度 | 提高切换阈值 | 前缀局部性很有价值 |
| 在小模型上进行廉价的短重试 | 降低切换阈值 | 结账成本很小 |

## 路由器记忆不是用户记忆

“路由器记忆”这个词可能有误导性，所以这条边界很重要。

SAAR 记忆不是对话记忆、检索记忆或用户画像记忆。它不总结对话，也不试图替模型记住事实。它的职责更窄：保留足够的路由状态，让下一次模型选择决策是安全且可解释的。

对每个会话，路由器跟踪如下事实：

- 逻辑模型背后最后选择的物理模型；
- 上一次匹配的路由决策；
- 会话处于正常、工具循环、provider 状态、空闲重置还是漂移重置阶段；
- 最近发生了多少次切换；
- 最新的上下文长度和缓存证据；
- 一个把响应关联回路由器决策轨迹的回放 id。

这样的范围让系统在运维上有用，又不会把路由器变成第二个智能体记忆层。应用记忆应留在应用中，检索记忆应留在检索栈中。SAAR 记忆的存在只是为了让跨回合的路由保持连贯。

## 前缀缓存让模型切换变得非对称

对长的智能体会话而言，模型切换不只是质量决策，也是一个输入侧的系统决策。

![](https://vllm.ai/blog-assets/figures/2026-06-02-session-aware-agentic-routing/cache-checkout-discipline.png)
*图 4：同一次切换的成本因模型层级、会话长度和物理前缀复用而不同。*

在便宜模型上的一次简短重试，与在一个前沿模型上进行了 40 个回合的热会话，不应该被同等对待。后者已经积累了有价值的前缀。即便用户可见的消息很短，切换离开它也可能要求下一个物理模型付出大得多的输入成本。

因此 SAAR 为缓存输入的“结账差价”定价：即所考虑的物理模型的常规提示输入价格与缓存输入价格之间的差距。会话越长、越昂贵，策略对丢弃前缀局部性就越严格。

这也澄清了被路由的逻辑模型的缓存 token 记账问题。如果用户调用 `auto`，路由器可能随时间把这个逻辑名称映射到不同的物理模型。某个后端报告的缓存命中是那个后端的物理证据，不会自动可迁移到另一个后端。SAAR 把后端报告的缓存 token 与路由器估算的复用分开保存，并且不改写上游的 usage 字段。

这种分离在运维上很有用。运维人员仍可以检视物理缓存行为，而路由器用它自己的记忆来决定切换是否值得付出结账成本。

## 一个请求如何流经 SAAR

服务路径保持熟悉。客户端向 OpenAI 兼容网关发送请求，通常带有 `auto` 这样的逻辑模型名。要启用会话感知路由，它们还要发送一个稳定的会话标识符，例如 `x-session-id`。

然后 SAAR 按如下顺序处理每个回合：

1. 读取当前请求、会话 id、工具调用上下文、provider 状态标记和候选模型集合。
2. 运行常规的 Semantic Router 信号与决策流水线。
3. 用配置的方法（如混合评分）产生基础的模型选择结果。
4. 从路由器记忆加载之前的会话路由状态。
5. 对工具循环和 provider 托管状态应用硬锁。
6. 检查空闲超时和决策漂移边界。
7. 使用前缀缓存结账成本和切换历史调整切换得分。
8. 选择物理模型并输出诊断信息。
9. 更新路由器记忆并写入回放轨迹。

配置位于路由决策的模型选择算法内部：

```
routing:
  decisions:
    - name: agentic_routing
      modelRefs:
        - model: qwen3-8b
        - model: qwen3-32b
      algorithm:
        type: session_aware
        session_aware:
          base_method: hybrid
          idle_timeout_seconds: 300
          tool_loop_hard_lock: true
          context_portability_hard_lock: true
          decision_drift_reset: true
          prefix_cache_weight: 0.20
          switch_history_weight: 0.04
```

这些值是有意的策略旋钮，不是放之四海而皆准的常数。会话较短的客服助手可以使用更宽松的空闲边界；拥有长工具循环和昂贵上下文的编码智能体可以使用更严格的连续性与前缀缓存设置。

## 可观测性是功能的一部分

`auto` 背后的模型选择只有在运维人员能够解释它时才有用。

![](https://vllm.ai/blog-assets/figures/2026-06-02-session-aware-agentic-routing/observability-trace.png)
*图 5：SAAR 把逻辑模型背后隐藏的物理路由选择变成可检视的轨迹和响应头。*

SAAR 输出诸如所选模型、所选决策、回放 id、会话阶段、选择置信度和上下文 token 数之类的诊断信息。回放 id 把一个被服务的响应关联回解释该决策的路由器轨迹。

一条有用的轨迹可以回答这样的问题：

- 基础选择器本会选择哪个模型？
- 路由器是否因为工具循环锁而保持了上一个模型？
- provider 托管状态是否让切换变得不安全？
- 会话是否越过了空闲或漂移边界？
- 前缀缓存证据如何改变了调整后的候选得分？
- 最终决策是保持、切换，还是被锁定而保持？

这让会话感知路由变得可运营。没有回放，逻辑模型背后的路由器会变得难以调试；有了回放，运维人员可以审计路由器为什么保持连续性，或为什么判定某次切换是安全的。

## 我们如何评估它

这套评估围绕一个问题设计：该策略能否让路由对智能体更友好，同时不掩盖正确性问题？

我们使用三层证据。

第一，一个确定性的策略矩阵在大量合成会话上测试控制逻辑。这把路由策略与服务噪声隔离开来，让我们可以对工具循环、provider 状态、空闲边界、漂移边界、模型层级和切换历史做压力测试。

第二，真实的 OpenAI 兼容服务运行通过 AMD ROCm 上的路由器与后端服务路径检验同样的不变量。这检查请求头、会话 id、诊断信息和失败处理能否经受真实请求流。

第三，确定性的智能体任务轨迹增加了任务结构。这些轨迹不只统计切换次数，还包含模拟的工具观察和精确的最终答案评分。

目标不是让每张图都说“切换更少”了——粘性会话也能做到这一点。目标是展示 SAAR 移除了不安全切换、保留了有用的移动、尊重昂贵的前缀局部性，并且在真实服务中保持可观测。

## 结果 1：SAAR 把控制单元从回合移到会话

确定性策略矩阵覆盖均衡型、工具密集型、前沿模型密集型、空闲密集型、provider 状态密集型和漂移密集型会话。每个工作负载运行 5 个种子、每个种子 40 个会话、每个会话 18 个回合，总计 **21,600** 个回合。

![](https://vllm.ai/blog-assets/figures/2026-06-02-session-aware-agentic-routing/synthetic-headline.png)
*图 6：21,600 个确定性回合上的核心策略结果。*

核心结果是 SAAR 在减少模型搅动的同时保留了移动能力：

| 策略 | 切换次数 | 不安全切换 | 估算成本降低 | 质量差值 |
| --- | --- | --- | --- | --- |
| 单轮 | 9,709 | 3,836 | 0.00% | +0.0000 |
| 粘性会话 | 340 | 0 | 98.65% | -0.1433 |
| 初版 SAAR | 1,810 | 200 | 70.92% | -0.0122 |
| 完整 SAAR | 2,011 | 0 | 78.71% | -0.0453 |

单轮路由频繁切换并制造不安全移动。粘性会话几乎消除移动，但也放弃了太多质量，因为它们在任务改变后拒绝重新选择。完整 SAAR 出于正确的原因处于中间：它移除不安全移动，同时仍让空闲与漂移边界重新打开决策。

这就是从回合级控制到会话级控制的转变。路由器不再把每条消息当作全新的独立事件。

## 结果 2：硬锁消除正确性失败

第二个结果隔离出最重要的不变量：当切换不安全时，SAAR 不应切换。

![](https://vllm.ai/blog-assets/figures/2026-06-02-session-aware-agentic-routing/safety-effect.png)
*图 7：硬锁消除了工具循环和不可移植 provider 状态期间的不安全切换。*

工具循环切换违规从 **3,404 降到 0**。Provider 状态切换违规从 **432 降到 0**。

这些不是微小的调优收益，而是正确性边界。工具结果不是普通提示，不可移植的续接 id 也不是普通文本字段。如果路由器无视这些事实，它可能在破坏交互的同时，看起来仍在针对最新消息做出合理的语义选择。

SAAR 通过把连续性约束显式写进策略来解决这个问题。

## 结果 3：SAAR 不是换了名字的粘性会话

最明显的基线是粘性路由：为会话选定第一个模型并一直保持。

粘性路由很有吸引力，因为它易于推理。它也通过完全避免切换解决了许多不安全切换的情形。但这种简单性对智能体来说会变成产品问题。长的会话会漂移，用户会更换任务，最初便宜的模型可能不再合适，强模型可能不再必要。

![](https://vllm.ai/blog-assets/figures/2026-06-02-session-aware-agentic-routing/ablation-effect.png)
*图 8：SAAR 不只是粘性会话；它在连续性与移动之间取得平衡。*

消融实验展示了 SAAR 为什么需要多种机制：

| 变体 | 切换减少 | 不安全切换 | 成本降低 | 解读 |
| --- | --- | --- | --- | --- |
| 无工具锁 | 74.96% | 760 | 60.05% | 重新引入工具循环违规 |
| 无 provider 状态锁 | 77.98% | 200 | 69.82% | 重新引入不可移植状态违规 |
| 无漂移重置 | 83.14% | 0 | 81.31% | 任务漂移后过度黏着 |
| 无空闲边界 | 83.98% | 0 | 80.14% | 自然暂停后过度黏着 |
| 无前沿成本项 | 73.96% | 0 | 54.75% | 过于轻易地离开昂贵的热会话 |
| 完整 SAAR | 79.29% | 0 | 78.71% | 保留锁的同时保留安全重选 |

锁提供正确性，重置边界提供活性，前缀缓存结账定价提供经济纪律。去掉其中任何一项，行为都会发生指标上可见的变化。

## 结果 4：不变量在真实的 AMD ROCm 服务中成立

策略模拟有用，但路由器必须能在真实请求流中工作。真实服务运行使用通过路由器和 AMD ROCm 后端路径的 OpenAI 兼容流量，并为路由运行与直连后端运行使用匹配的调度。

![](https://vllm.ai/blog-assets/figures/2026-06-02-session-aware-agentic-routing/live-rocm-effect.png)
*图 9：真实 ROCm 运行在长会话和注入的后端故障下保持连续性。*

在长会话运行中，路由器完成 **2,896** 个真实请求，观察到 **0** 次连续性违规。

| 工作负载 | 请求数 | 成功率 | p95 开销 | 连续性违规 |
| --- | --- | --- | --- | --- |
| balanced-32x64 | 2,048 | 100.00% | 6.181 ms | 0 |
| stateful-16x48 | 768 | 100.00% | 26.805 ms | 0 |
| idle-16x5-75s | 80 | 100.00% | 283.463 ms | 0 |

空闲工作负载包含真实的墙上时钟休眠，因此它的 p95 开销应与热路径路由开销分开解读。重要的结果是连续性：真实路径保持了在确定性矩阵中测试过的硬锁与重置边界行为。

## 结果 5：后端故障后会话得以恢复

长程智能体需要会话级恢复，而不仅仅是单请求成功。后端可以对一个请求返回 HTTP 503，但会话应该在稍后继续，不丢失保持交互连贯的路由不变量。

| 故障阶段 | 请求数 | 注入的 503 | 受影响会话 | 恢复 | 连续性违规 |
| --- | --- | --- | --- | --- | --- |
| provider 状态 | 360 | 48 | 8 | 100.00% | 0 |
| 工具循环 | 360 | 72 | 8 | 100.00% | 0 |
| 话题漂移 | 432 | 48 | 8 | 100.00% | 0 |

在一次性干扰矩阵中，**32/32** 个受影响会话随后恢复。在重复失败矩阵中，在 **168** 次注入的 HTTP 503 响应之后，**24/24** 个受影响会话恢复。

这很重要，因为智能体会话比普通聊天回合更长。一次短暂的后端故障不应该让路由器忘记工具循环正在运行、provider 状态不可移植、或会话拥有可回放的历史。

## 结果 6：任务轨迹检验智能体循环

连续性计数器是必要的，但还不够。我们还运行带有模拟工具观察和精确最终答案评分的确定性多轮任务轨迹。回路中没有裁判模型：最终答案要么包含所需的标签，要么不包含。

在 AMD 服务任务运行中，**18/18** 个精确评分的任务实例全部完成，**96/96** 个被路由的回合都带有回放响应头，且未观察到连续性违规。

这仍然小于一个宽泛的真实编码智能体基准，但它比单纯的策略计数器是更强的信号，因为它检验了一个带有工具观察和最终答案检查的任务循环。

## 这对 vLLM 用户意味着什么

会话感知路由让 Semantic Router 在“逻辑模型名背后隐藏着一组模型组合”的智能体服务栈中更有用。

对用户来说，体验可以保持简单：调用 `auto` 这样的模型、发送稳定的会话 id，然后让路由器挑选物理模型。对运维人员来说，行为变得更可控：配置何时需要连续性、空闲会话何时可以重置、前缀局部性有多重要，以及路由决策如何被追踪。

这在以下情况尤其有用：

- 候选模型具有不同的成本、延迟和能力特征；
- 智能体跨多个回合使用工具；
- 客户端依赖 provider 托管的续接状态；
- 长会话积累了有价值的前缀缓存局部性；
- 运维人员需要检视逻辑路由背后是哪个物理模型服务了每个回合。

它还划出了一道清晰的基础设施边界。Semantic Router 负责策略级的模型选择；Envoy、Kubernetes 和服务后端仍然负责端点成员关系、健康检查和负载均衡。这种分离让 SAAR 专注于它能安全决定的事情：会话级别的模型连续性、模型切换和可追溯性。

## 更大的方向

这个里程碑延续了始于信号-决策路由的同一条主线。

Iris 让路由决策可组合。Athena 把 Semantic Router 推向面向模型混合与智能体部署的策略性系统大脑。多模态加固把证据面从文本提示拓宽到请求级信号。会话感知智能体路由则拓宽了时间视野：路由器现在不仅对一个请求进行推理，还对它位于一次长期交互中的哪个位置进行推理。

这个方向对现代服务栈很重要。智能体系统越来越希望在很多物理选项之上有一个统一的逻辑模型接口。它们希望简单的步骤用更便宜的模型、困难的步骤用更强的模型、在工具循环中保持连续性、对长上下文做缓存感知的处理，以及足够的可观测性来在生产环境中信任这个系统。

SAAR 是朝着那种运行模型迈出的一步。它没有把路由器变成智能体，而是让路由器感知到服务好智能体所需的最低限度的会话事实。

核心想法很简单：`auto` 背后的路由器应该知道模型切换何时被允许、何时被禁止，以及对于热的长期运行会话而言切换的代价是什么。
