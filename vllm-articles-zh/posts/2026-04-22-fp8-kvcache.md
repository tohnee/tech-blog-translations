# vLLM 中 FP8 KV 缓存与注意力量化的现状

> 原文：[The State of FP8 KV-Cache and Attention Quantization in vLLM](https://vllm.ai/blog/2026-04-22-fp8-kvcache) · vLLM 博客

## 引言

长上下文 LLM 服务越来越受内存约束：对于标准的全注意力解码器，在 128k 以上上下文时 KV 缓存往往占据 GPU 内存的主体，而且每个解码步都必须读取其中很大一部分。因此，用 FP8 将 KV 缓存的存储量减半，在硬件成本不变的情况下可以换来显著更高的并发或更长的支持上下文——前提是精度站得住脚。

vLLM 的 `--kv-cache-dtype fp8` 标志会量化 KV 缓存，并让整个注意力计算（QK 和 ScoreV 矩阵乘法）都在 FP8 下运行（本文通篇使用 e4m3 格式）。这个功能在 vLLM 中已存在一段时间，但它在预填充密集与解码密集两类压力测试下表现如何？我们在 decoder-only 与 MoE 模型、Hopper 与 Blackwell 两代架构上进行了全面验证。我们在 Flash Attention 3（FA3）后端中发现并修复了关键的精度与性能问题（示例见图 1）。在本文验证过的路径上，它能在降低解码成本和 KV 缓存内存占用的同时，保持接近基线的精度。主要注意事项有：带小滑动窗口层的混合注意力模型——跳过这些层往往更好；以及大 head 维度模型（`head_dim = 256`）——其预填充仍可能出现回退。此外，对于 head 维度 64 和 128，FP8 格式在预填充和解码两端都能带来加速。对于受内存限制的解码，最优情况下 KV 缓存的每 token 成本可降至其 BF16 对应值的 54%。对于 256 这类大 head 维度，FP8 也能降低 ITL；但目前默认的预填充性能仍略逊于 BF16。

![Figure 1: Needle-in-a-haystack at 128k on Hopper before and after the FP8 Flash Attention 3 fixes. The accumulation fix restores long-context accuracy from a severe FP8 regression back near the BF16 baseline, while the optimized FP8 path still preserves the decode-speed advantage.](https://vllm.ai/blog-assets/figures/2026-04-22-fp8-kvcache/fig1_niah_before_after_plot.png)

## 我们发现的问题

尽管 `--kv-cache-dtype fp8` 在 vLLM 中已经存在一段时间，我们的压力测试揭示了两类问题：

**精度：** 在 Hopper GPU 上，FP8 Flash Attention 3 内核在长上下文时存在累加精度损失。在 128k 大海捞针任务上，FP8 精度从 91%（BF16 基线）跌至仅 13%——这一回退被追溯到 Tensor Core 中不精确的 FP32 累加（见下文的两级累加修复）。

**性能：** 对于带滑动窗口注意力层的模型（如 gpt-oss-20b），FP8 的 ITL 斜率与 BF16 几乎相同（为 BF16 斜率的 96%），这意味着尽管内存减半，用户几乎没有获得解码加速。盈亏平衡点超过 700k token——远超大多数实际上下文长度。

下一节介绍我们为解决这些问题而发布的改进。

## 内核与 vLLM 改进

在调查过程中，我们发布了多项改进，以增强量化方案的灵活性、修复精度问题并提升性能。这里简要介绍。

**两级累加：**
文档记载 Hopper 的 FP8 Tensor Core 会累加到 FP32 寄存器，但实际上当收缩维度很大时，中间累加会损失精度——这是一个已知的硬件级问题，DeepSeek-V3 训练期间也遇到过（见 [DeepSeek-V3 技术报告](https://arxiv.org/abs/2412.19437)图 7(b)）。当收缩维度达到 100K 以上时，这种不精确的累加会导致剧烈的数值错误。具体来说，在长上下文推理中，`Softmax(AttnScore) * V` 矩阵乘法的收缩维度对应上下文长度。据我们实测，在长上下文大海捞针任务上，这会导致精度从 91%（BF16）回退到 13%（FP8）。
为缓解这一点，我们加入了两级累加策略（参见 [SageAttention2](https://arxiv.org/abs/2411.10958)），把部分累加的结果写入*真正的* FP32 寄存器（[flash-attention#104](https://github.com/vllm-project/flash-attention/pull/104)），把 FP8 精度拉回到 89%。不利的方面是，两级累加会增加寄存器压力，导致预填充变慢。我们通过优化分块（tiling）配置部分解决了这个问题（[flash-attention#125](https://github.com/vllm-project/flash-attention/pull/125)），但对于大于 128 的 head 维度，预填充性能仍落后于 BF16。

**跳过层：**
早先 vLLM 只允许用户为所有注意力层选择单一的数值格式。我们增加了 `--kv-cache-dtype-skip-layers`（[vllm#33695](https://github.com/vllm-project/vllm/pull/33695)）以支持混合配置。像 GPT-OSS 这样的模型有部分层使用滑动窗口注意力，token 只关注固定的窗口大小（例如 128 个 token）。在这些层上，FP8 的开销无法被摊薄。因此，让这些层保持在 BF16 实际上比量化它们更快，参见下文的实测结果。此外，如果某些层对量化特别敏感，这个功能也允许跳过它们。

**逐头（Per-Head）缩放因子**：
Flash Attention 3 内核允许为注意力操作的 FP8 量化指定一个缩放因子数组，每个缩放因子对应一个 KV head。要在 vLLM 中启用该功能，需要把静态量化的支持推广到所有分组形状（[vllm#30833](https://github.com/vllm-project/vllm/pull/30833)），并扩展 `reshape_and_cache_flash` 内核的适用范围（[vllm#30141](https://github.com/vllm-project/vllm/pull/30141)），使其处理缩放因子数组而不是单个标量。

**查询量化融合：**
我们把查询量化从注意力后端移到了一个简单的 torch 实现中，让 `torch.compile` 能把它融合进周围的操作，消除了固定的每 token 开销（[vllm#24914](https://github.com/vllm-project/vllm/pull/24914)）。

**优化的 FA3 FP8 分块大小：**
我们为 `head_dim = 64` 和 `head_dim = 128` 调优了预填充分块配置，以减少两级累加带来的寄存器溢出（[flash-attention#125](https://github.com/vllm-project/flash-attention/pull/125)）。此外，我们为受内存限制的解码工作负载添加了专门调优的配置，大幅降低了随上下文增长的 ITL 增幅，也就是斜率（[flash-attention#96](https://github.com/vllm-project/flash-attention/pull/96)、[flash-attention#91](https://github.com/vllm-project/flash-attention/pull/91)）。

## 性能基准测试

在长上下文 LLM 服务的解码过程中，注意力可能是主要的成本。每个生成的 token 都要对完整 KV 缓存做注意力计算，因此逐 token 延迟（ITL）随输入长度线性增长。把 KV 缓存从 BF16 量化到 FP8 会把每个缓存 token 的内存减半，从而把每步注意力的内存流量减半，这应当直接转化为更低的 ITL 斜率。由于 Hopper 和 Blackwell GPU 的 FP8 FLOPS 是 BF16 的两倍，理想情况下我们也预期预填充加速。然而在实践中，这些收益并不总是开箱即得，如下文所示。

### 单请求基准测试

为了干净地理解注意力行为，我们先给出并发为 1 的基准，之后再给出批处理推理的结果。在并发为 1 时，逐 token 延迟（ITL）与首 token 延迟（TTFT）完全解耦，我们可以对 ITL 与输入长度的关系拟合一个线性模型

`ITL = slope × input_len + intercept`

对 TTFT 拟合一个二次模型：

`TTFT = a × input_len² + b × input_len + c`

ITL 斜率直接反映每 token 的注意力成本——斜率越低，每个新增缓存 token 带来的额外延迟越小，这对长上下文工作负载至关重要。**盈亏平衡点**是 FP8 ITL 降到 BF16 ITL 之下的上下文长度；超过这一点，FP8 在解码上严格更快。二次 TTFT 模型刻画的是计算受限的预填充阶段，由于对输入做自注意力，成本随序列长度二次增长。

所有 Hopper 实验都在单张 H100 GPU 上运行，使用 [FlashAttention-3](https://openreview.net/forum?id=tVConYid20)（通过 [vLLM fork](https://github.com/vllm-project/flash-attention)），它提供带在线 softmax 重缩放的原生 FP8 KV 缓存支持。我们使用单 GPU、`vllm bench serve`、并发 1、128 个输出 token，输入长度从 256 扫到 125k token。

图 2 展示了 Llama-3.1-8B 模型的结果。

![Figure 2: Single-request H100 benchmark for Llama-3.1-8B. FP8 nearly halves the decode ITL slope relative to BF16 with almost no intercept penalty, bringing the decode break-even point down to about 7k tokens while preserving similar TTFT.](https://vllm.ai/blog-assets/figures/2026-04-22-fp8-kvcache/fig2_llama_8b.png)

图 2：Llama-3.1-8B 的单请求 H100 基准。FP8 相对 BF16 几乎把解码 ITL 斜率减半，而截距几乎没有代价，把解码盈亏平衡点拉低到约 7k token，同时保持相近的 TTFT。

拟合的 ITL 斜率从 `4.37e-05` 降到 `2.37e-05` ms/token，而截距仅从 `6.44` 变为 `6.58` ms。FP8 的斜率为 BF16 的 54%，已接近最优，截距差仅 0.14 ms。这将盈亏平衡点拉低到约 7k token。此外，即使开启两级累加，FP8 在长上下文下仍略有 TTFT 加速。

接下来看 gpt-oss-20b，这是一个 20B 参数、采用混合注意力架构的模型，同时具有全局层和滑动窗口层（窗口大小 128）。滑动窗口层的 KV 缓存大小有上限，因此对它们做量化在长上下文时收益递减。使用 `--kv-cache-dtype-skip-layers sliding_window`，我们让这些层保持 BF16，只把全局注意力层量化为 FP8。图 3 报告了该模型在 KV 缓存为 BF16、FP8、以及 FP8 并跳过滑动窗口层三种配置下的结果。

![Figure 3: Single-request H100 benchmark for gpt-oss-20b. Skipping sliding-window layers is the best FP8 variant because those layers have bounded KV-cache footprints, so they pay quantization overhead without getting much long-context benefit.](https://vllm.ai/blog-assets/figures/2026-04-22-fp8-kvcache/fig3_gptoss_20b.png)

图 3：gpt-oss-20b 的单请求 H100 基准。跳过滑动窗口层是最佳的 FP8 变体，因为这些层的 KV 缓存占用有限，量化它们只付出量化开销却换不到多少长上下文收益。

拟合的 ITL 斜率从 BF16 的 `8.94e-06` ms/token 降到完整 FP8 的 `7.14e-06` 和 FP8 跳过滑动窗口（skip-SW）的 `6.34e-06`，而截距紧密聚集在 `4.03` 到 `4.07` ms 之间。FP8 的斜率为 BF16 的 80%（完整 FP8）和 71%（skip-SW），使 FP8 成为很有吸引力的选择。而在我们改进之前，BF16 与 FP8 的斜率几乎相同。

跳过滑动窗口的变体是明显的赢家：通过让有上限的滑动窗口层保持 BF16（在那里量化只增加固定开销、长上下文下没有内存节省），它以极小的截距代价取得了最低的斜率。因此我们推荐使用该变体。

实践结论：对于长上下文、解码密集的服务，当 KV 缓存流量占主导时 FP8 最具吸引力；在 H100 上，它对 Llama 类模型已经明显有益，对混合模型而言只要跳过小的滑动窗口层同样有益。

下表汇总了我们改进前后的单请求性能，显示盈亏平衡点与 ITL 斜率都显著下降。

*表 3：两个受测模型与各 KV 缓存变体的改进汇总。*

| 模型 | 版本 | FP8 变体 | 盈亏平衡点（token） | FP8 斜率（占 BF16 的百分比） |
| --- | --- | --- | --- | --- |
| Llama-3.1-8B | 之前（v0.10.2） | FP8 | 24,889 | 63% |
| Llama-3.1-8B | 之后（v0.19.1） | FP8 | **7,010** | 54% |
| gpt-oss-20b | 之前（v0.10.2） | FP8 | 741,565 | 96% |

### 负载下的吞吐量

上面的扫描在并发 1 下隔离了每 token 注意力成本。为了在贴近现实的条件下测量端到端服务性能，我们运行了一个吞吐量基准：150 个请求、并发 8，每个请求约 20k 输入 token 和约 2k 输出 token（±15% 波动）。结果见表 4 与表 5。

*表 4：Llama-3.1-8B 模型在重吞吐负载下、KV 缓存分别为 BF16 与 FP8 格式时的性能结果。FP8 展现出 14.9% 更高的输出吞吐量、13.0% 更快的总运行时间和 14.8% 更低的中位 ITL。*

| 配置 | 中位 TTFT（ms） | 中位 ITL（ms） | 总时长（s） | 输出 tok/s |
| --- | --- | --- | --- | --- |
| BF16 | 763.6 | 15.18 | 672.6 | 450.3 |
| FP8 | 742.8 | 12.93 | 585.2 | 517.5 |

*表 5：gpt-oss-20b 模型在重吞吐负载下、KV 缓存分别为 BF16、FP8 与 FP8 并跳过滑动窗口时的性能结果。FP8 skip-SW 展现出 4.8% 更高的输出吞吐量、4.6% 更快的总运行时间和 4.8% 更低的中位 ITL。*

| 配置 | 中位 TTFT（ms） | 中位 ITL（ms） | 总时长（s） | 输出 tok/s |
| --- | --- | --- | --- | --- |
| BF16 | 468.9 | 8.09 | 364.2 | 831.6 |
| FP8 | 451.7 | 7.90 | 355.1 | 853.0 |
| FP8 skip-SW | 456.4 | 7.70 | 347.4 | 871.8 |

这些吞吐量结果证实，单请求的 ITL 改进确实转化为负载下的真实服务收益。对 Llama-3.1-8B，并发 1 时 54% 的 ITL 斜率下降转化为并发 8 时 14.9% 的输出吞吐量提升——FP8 不仅让每个 token 解码更快，2x 的内存缩减还让调度器能塞进更多并发请求。对 gpt-oss-20b，收益较小（4.8%），因为模型的滑动窗口层限制了内存节省；skip-SW 变体通过避免在不受益于量化的层上付出开销，恢复了最多的收益。

注意，这些基准使用并发 8 与约 20k token 的输入，属于中等偏重的负载。在更高并发或更长上下文下，FP8 的内存节省影响更大，因为 BF16 会撞上 OOM 或需要更激进的 KV 缓存驱逐。

### 大 head 维度的局限

通过 [flash-attention#104](https://github.com/vllm-project/flash-attention/pull/104)，我们默认启用了两级累加，以确保模型质量最高、避免用户遭遇意外的精度下降。但对大 head 维度，这会导致 TTFT 慢于 BF16。

为了说明这一点，图 4 报告了 gemma-4-E2B 在 H100 上的结果，该模型使用 `head_dim = 256`。它还有四分之三的层使用大小为 `512` 的滑动窗口：

![Figure 4: gemma-4-E2B on H100 (head_dim = 256). FP8 improves decode ITL, but prefill becomes slower because two-level accumulation raises register pressure enough to outweigh the FP8 arithmetic advantage.](https://vllm.ai/blog-assets/figures/2026-04-22-fp8-kvcache/fig4_gemma.png)

图 4：gemma-4-E2B 在 H100 上（head\_dim = 256）。FP8 改善了解码 ITL，但预填充变慢了，因为两级累加带来的寄存器压力足以抵消 FP8 的算术优势。

对 gemma-4-E2B，ITL 斜率从 `5.30e-05` 降到 `3.60e-05` ms/token，而 TTFT 二次项系数从 `6.93e-07` 升至 `1.12e-06` ms/token²。因此，在整个测量范围内，FP8 在解码上有明确的优势（斜率为 BF16 的 68%）。此外，由于 gemma-4-E2B 的滑动窗口大小（512）是 gpt-oss-20b（128）的 4 倍，每个窗口内足够的数据可以摊薄 FP8 开销，因此量化滑动窗口层也是值得的。这让它在对比"跳过滑动窗口层"时有一个固定偏移的优势。然而，FP8 的 TTFT 二次项系数约为 BF16 的 1.6 倍，意味着在 `head_dim = 256` 下，长上下文时预填充会显著*变慢*，原因是两级累加带来的寄存器压力。

目前有两种应对方法：1）用户可以禁用两级累加以换取更好的性能。但在此情况下，我们建议在相关工作负载上做充分的精度测试。2）可以让累加每 N 步进行一次而不是每步都做。一个可用的实现在这个开放的 PR [flash-attention#122](https://github.com/vllm-project/flash-attention/pull/122) 中，它可以恢复预填充的加速。注意，尤其对第一种方案，head 维度 64 和 128 也能获得更大的预填充加速。

### Blackwell（B200）GPU 上使用 FlashInfer 的性能

虽然我们的性能改进主要针对 H100 与 Flash-Attention 3，为完整起见，我们也提供 B200 上使用 FlashInfer 后端的基准。注意在 B200 上，累加问题已被修复，因此不需要显式的两级累加。
图 5 与图 6 分别展示 Llama-3.1-8B 和 gpt-oss-20b 的性能。

![Figure 5: Llama-3.1-8B on B200 with FlashInfer. FP8 again reduces the decode ITL slope to about 54% of BF16 with an almost negligible intercept penalty, so decode breaks even at roughly 4k tokens.](https://vllm.ai/blog-assets/figures/2026-04-22-fp8-kvcache/fig5_llama_b200.png)

图 5：Llama-3.1-8B 在 B200 上使用 FlashInfer。FP8 再次把解码 ITL 斜率降到 BF16 的约 54%，截距代价几乎可忽略，解码在约 4k token 处达到盈亏平衡。

## 精度基准测试

我们聚焦以下模型：Llama-3.3-70B-Instruct、Qwen3-30B-A3B-Instruct-2507、Qwen3-30B-A3B-Thinking-2507 和 Qwen3.5-27B。

对于长上下文（预填充密集）评估，我们使用 `openai/mrcr` 任务，测试序列长度最高到 1M。我们报告每个序列长度桶在 5 次重复上的平均 pass@1 分数，并把曲线下面积（AUC）作为跨所有测试长度的汇总指标（[Context Arena](https://contextarena.ai/)）。

对于推理能力（解码密集）评估，我们使用 AIME25、GPQA:Diamond、MATH500 和 LiveCodeBench-v6。我们报告平均 pass@1 分数：AIME25 与 LiveCodeBench-v6 重复 10 次，GPQA:Diamond 与 MATH500 重复 5 次。

所有评估都采用模型作者建议的默认非贪心采样参数，以模拟真实部署。

**重要：** 所有评估都使用逐张量（per-tensor）未校准的量化缩放因子（即 scale = 1.0）。这是最简单的配置——没有校准数据、没有逐头调优——代表了精度的最坏情况。我们选择这个设置有两个原因：1）任何 vLLM 用户通过 `--kv-cache-dtype fp8` 就能轻松复现；2）它确立了一个下界——使用校准缩放因子的结果只会更好。不过，我们也支持在目标数据上校准量化缩放因子，以及更高粒度的缩放因子（逐注意力头而不是逐张量）。关于这些功能的更多细节，请看下面几节。

### 结语

我们的主要结论是：FP8 KV 缓存量化如今已经可以作为许多长上下文 vLLM 部署和硬件环境的默认起点。如果你的工作负载是解码密集且受内存限制的，FP8 能以很小或可忽略的精度损失带来可观的延迟与容量收益。主要的例外是：`head_dim = 256` 上预填充占主导的工作负载、小滑动窗口层应留在 BF16 的混合模型，以及未校准时表现出持续精度损失的模型或后端——对这些，校准仍然重要。

虽然我们这里的重点是配置最简单（未校准缩放因子）的情形，我们还实现了两个额外功能，用于在特殊部署中更好地恢复精度：1）通过 [`vllm-project/LLM-Compressor`](https://github.com/vllm-project/llm-compressor) 使用用户提供的数据集进行缩放因子校准；2）支持更细粒度的[逐注意力头量化缩放因子](https://github.com/vllm-project/vllm/pull/30141)。详细示例请参见 [vLLM 示例文档](https://github.com/vllm-project/vllm/blob/4f436782afd0b21d6754ea6bc4b80639f737bbc1/docs/features/quantization/quantized_kvcache.md#3-recommended-calibration-using-a-dataset-with-llm-compressor)。

### 什么时候应该使用校准？

并非所有模型都适合未校准的 FP8 缩放因子。为了说明这一点，我们在 H200 GPU 上用未校准的 FP8 KV 缓存量化测试了 Kimi-K2.5 模型——它使用 Flash MLA 注意力后端，与上述模型不同的内核路径。

图 14 显示在所有序列长度桶上出现一致的向下偏移。虽然汇总 AUC 的下降不大、标准误差带相互重叠，但这种劣化是系统性的而非随机的。实践结论：从未校准的 FP8 开始，因为它简单且往往足够好；但如果你在真实工作负载上观察到这种持续的向下偏移——而不只是个别嘈杂的桶——就应当进行校准。这一点对使用非标准注意力后端（如 FlashMLA）的模型尤其相关，它们的 FP8 内核行为可能与经过充分验证的 FA3 和 FlashInfer 路径不同。

![Figure 14: MRCR results for Kimi-K2.5 with FlashMLA and uncalibrated FP8 KV-cache plus FP8 attention. The drop is modest in aggregate AUC but consistently negative across context lengths, which makes this a good example of when calibration is worth doing.](https://vllm.ai/blog-assets/figures/2026-04-22-fp8-kvcache/fig14_Kimi-K2.5_openai_mrcr_4_needles_H200_plot.png)

图 14：Kimi-K2.5 使用 FlashMLA、未校准的 FP8 KV 缓存加 FP8 注意力的 MRCR 结果。汇总 AUC 的下降不大，但在各上下文长度上一致为负，这使它成为"什么时候值得做校准"的绝佳例子。

## 什么时候应避免 FP8 KV 缓存

FP8 KV 缓存量化并非总是正确选择。以下情况建议继续使用 BF16：

- **你的上下文较短（< 约 7k token）：** FP8 有一个小的固定开销（截距差），因此短上下文下 BF16 的 ITL 可能略快。
- **你的模型使用 `head_dim = 256` 且预填充延迟很重要：** 两级累加的开销在长上下文时会把 TTFT 拉高约 1.6 倍。禁用两级累加可以恢复速度，但需要仔细的精度验证。
- **未校准的精度在你的工作负载上低于 95%：** 一些模型（如使用 FlashMLA 的 Kimi-K2.5）在未校准缩放因子下表现出一致的劣化，可能受益于在目标数据集上做校准。
- **你的模型有很多小的滑动窗口注意力层：** FP8 开销在这些层上可能难以摊薄；对混合注意力模型，建议使用 `--kv-cache-dtype-skip-layers sliding_window`。
