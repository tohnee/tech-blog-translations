# P-EAGLE：用 vLLM 中的并行投机解码加速 LLM 推理

> 原文：[P-EAGLE: Faster LLM inference with Parallel Speculative Decoding in vLLM](https://vllm.ai/blog/2026-03-13-p-eagle) · vLLM 博客

作者：Amazon 与 NVIDIA 团队

[#性能](https://vllm.ai/blog/tags/performance)[#投机解码](https://vllm.ai/blog/tags/speculative-decoding)

[EAGLE](https://arxiv.org/pdf/2503.01840) 是大语言模型（LLM）推理中投机解码的最先进方法，但它的自回归起草（drafting）方式带来一个隐藏瓶颈：推测的 token 越多，草稿模型需要的串行前向传播就越多。这些开销最终会侵蚀收益。**P-EAGLE** 通过在单次前向传播中生成全部 K 个草稿 token 消除了这一上限，在 NVIDIA B200 的真实工作负载上相比原版 EAGLE-3 实现最高 1.69x 的加速。

只需下载（或训练）一个支持并行的起草器头，并在 vLLM 服务管线中加上 `"parallel_drafting": true`，即可解锁这一性能提升。预训练的 P-EAGLE 头已在 HuggingFace 上为 [GPT-OSS 120B](https://huggingface.co/amazon/gpt-oss-120b-p-eagle)、[GPT-OSS 20B](https://huggingface.co/amazon/GPT-OSS-20B-P-EAGLE) 和 [Qwen3-Coder 30B](https://huggingface.co/amazon/Qwen3-Coder-30B-A3B-Instruct-P-EAGLE) 提供，今天就能上手！

在本文中，我们将解释 P-EAGLE 的工作原理、我们如何自 [v0.16.0](https://github.com/vllm-project/vllm/releases/tag/v0.16.0)（PR#32887）起把它集成进 vLLM，以及如何用我们的预训练检查点来服务它。以下是所用工件列表：

- [ArXiv 论文](https://www.arxiv.org/pdf/2602.01469)
- HuggingFace 模型（[GPT-OSS 120B](https://huggingface.co/amazon/gpt-oss-120b-p-eagle)、[GPT-OSS 20B](https://huggingface.co/amazon/GPT-OSS-20B-P-EAGLE)、[Qwen3-Coder-30B-A3B-Instruct](https://huggingface.co/amazon/Qwen3-Coder-30B-A3B-Instruct-P-EAGLE)）
- vLLM 集成 [统一并行起草](https://github.com/vllm-project/vllm/pull/32887)
- vLLM-Speculators（[RFC](https://github.com/vllm-project/speculators/issues/292)、[PR](https://github.com/vllm-project/speculators/pull/343)）

### 快速上手 P-EAGLE

只需在 `SpeculativeConfig` 类中改一处配置即可启用并行起草：

```
# vllm/config/speculative.py
   parallel_drafting: bool = True
```

下面是在 vLLM 中启用并行起草、以 P-EAGLE 为起草器的示例命令：

```
  vllm serve openai/gpt-oss-20b \
   --speculative-config '{"method": "eagle3", "model": "amazon/gpt-oss-20b-p-eagle", "num_speculative_tokens": 5, "parallel_drafting": true}'
```

## EAGLE 的起草瓶颈

EAGLE 相比标准自回归解码实现 2–3× 加速，已广泛部署于 vLLM、SGLang、TensorRT-LLM 等生产级推理框架。EAGLE 以自回归方式起草 token：要产生 K 个草稿 token，需要经过草稿模型 K 次前向传播。随着草稿模型起草长输出的能力增强，这种起草开销变得显著——起草器的延迟随推测深度线性增长，限制了我们可以推测的激进程度。

## 我们的方法：Parallel-EAGLE（P-EAGLE）

我们提出 P-EAGLE，把 EAGLE 从自回归起草转变为并行草稿生成。在 B200 GPU 上，针对 GPT-OSS 20B，P-EAGLE 在 MT-Bench、HumanEval 与 SpeedBench 上相比原版 EAGLE-3 取得 1.05×–1.69× 的加速。它现已集成进 vLLM 以解锁并行投机解码，随时可以加速真实部署。

P-EAGLE 在单次前向传播中生成 K 个草稿 token。图 2 展示了其架构，包含两个步骤。

**第 1 步：预填充。** 目标模型处理提示并生成一个新 token，与正常推理时一样。在此过程中，P-EAGLE 捕获模型的内部隐藏状态：每个提示位置的 h\_prompt，以及新生成 token 的 h\_context。这些隐藏状态编码了目标模型在每个位置"知道"什么，将引导起草器的预测。这一步与自回归 EAGLE 完全相同。

**第 2 步：P-EAGLE 起草器。** 起草器并行地为每个位置构建输入。每个输入由一个 token 嵌入与一个隐藏状态拼接而成。

对于提示位置，输入把每个提示 token 嵌入 emb(p) 与目标模型中对应的 h\_prompt 配对。遵循与自回归 EAGLE 相同的约定，位置整体偏移一位：位置 i 接收来自位置 i-1 的 token 与隐藏状态，从而预测位置 i 上的 token。

对于位置 1（下一 token 预测，NTP），输入把新生成的 token 嵌入 emb(new) 与 h\_context 配对。该位置的运作与标准自回归 EAGLE 完全相同。对于位置 2 到 K（多 token 预测，MTP），所需的输入——token 嵌入与隐藏状态——尚不存在。P-EAGLE 用两个可学习参数来填充：共享的掩码 token 嵌入 emb(mask) 与共享的隐藏状态 h\_shared。它们是训练中学到的固定向量，充当中性占位符。

这些位置一起经过 N 个 transformer 层，再经过语言模型头，在单次前向传播中预测草稿 token t1、t2、t3 和 t4。

## 在长序列上训练 P-EAGLE

现代推理模型会产生很长的输出。如图 3 所示，GPT-OSS 120B 在 UltraChat 数据集上生成的序列（含提示）中位长度为 3,891 个 token，P90 为 10,800 个 token。草稿模型必须在匹配的上下文长度上训练，才能在推理时有效。

![图 3：GPT-OSS 120B 在 UltraChat 数据集上的序列长度（提示 + 生成）分布。推理等级：Medium。](https://vllm.ai/blog-assets/figures/2026-03-13-p-eagle/fig3_sequence_length.png)

图 3：GPT-OSS 120B 在 UltraChat 数据集上的序列长度（提示 + 生成）分布。推理等级：Medium。

一个关键挑战是并行起草会放大训练期间的内存需求。在长度为 N 的序列上训练 K 个并行组，会产生 N × K 个位置。当 N = 8,192、K = 8 时，单个训练样本包含 65,536 个位置。注意力要求每个位置关注每个有效位置——65K × 65K 意味着超过 40 亿个元素，在 bf16 下消耗 8GB 内存。

位置采样 [[An et al., 2025](https://arxiv.org/pdf/2504.18583)] 通过随机跳过位置来减少内存，但跳得太多会降低草稿质量。梯度累积是内存受限训练的标准解法，但它是在不同训练样本之间切分的。当单个序列就超出内存时，便无从切分。

P-EAGLE 引入了一种用于序列内切分的序列划分算法。该算法把 N × K 的位置序列划分为连续的块，在块边界之间保持正确的注意力依赖，并在同一序列的各个块之间累积梯度。详情见 [P-EAGLE 论文](https://arxiv.org/pdf/2602.01469)。

## 在 vLLM 中的实现

### 并行起草的挑战

在许多投机解码配置中，起草与验证共享相同的每请求 token 布局。对 EAGLE 来说大体如此：起草器消费的窗口恰好与验证器将要检查的内容一致——K 个草稿 token 加一个额外采样的 token。

并行起草打破了这种一致性。为了让起草器在单次前向传播中预测 K 个 token，我们追加 MASK 占位符（例如 [token, MASK, MASK, …]）。这些额外位置只为起草而存在，因此草稿批次的形状不再与验证批次形状一致。由于无法复用验证元数据，我们必须重建批次元数据。我们扩展输入 token ID、隐藏状态与位置，为掩码 token/嵌入插入槽位，按请求递增位置，然后从更新后的位置重新计算槽位映射与每请求起始索引。

### Triton 内核

为了抵消重建批次元数据的开销，我们实现了一个融合 Triton 内核，通过复制并扩展目标模型批次，在 GPU 上直接填充起草器的输入批次。该内核一遍完成：把上一个 token ID 与位置从目标批次复制到新的目标槽位，并插入目标模型采样的每请求奖励 token；然后用特殊的 MASK token ID 填充额外的并行起草槽位；最后生成轻量元数据：被拒绝 token 掩码、并行起草槽位的掩码 token 掩码、用于采样草稿 token 的新 token 索引，以及一个隐藏状态映射。

这些逻辑原本需要多个 GPU 操作（复制/散布 + 插入 + 填充 + 掩码 + 重映射）。把它融合进一个内核可以降低启动开销与额外内存流量，让起草准备工作保持轻量。

### 隐藏状态管理

对于把隐藏状态传给草稿模型的 EAGLE 类方法，并行起草单独处理这些字段的填充。由于隐藏状态远大于输入批次的其余部分，我们把工作拆分：Triton 内核输出一个映射，再由一个专用复制内核把学到的隐藏状态占位符广播到掩码 token 槽位。

```
# Copy target hidden states to their new positions
 self.hidden_states[out_hidden_state_mapping] = target_hidden_states

# Fill masked positions with the learned Parallel Drafting hidden state
 mask = self.is_masked_token_mask[:total_num_output_tokens]
 torch.where(
     mask.unsqueeze(1),
     self.parallel_drafting_hidden_state_tensor,
     self.hidden_states[:total_num_output_tokens],
     out=self.hidden_states[:total_num_output_tokens],
 )
```

`parallel_drafting_hidden_state_tensor` 从模型的 `mask_hidden` 缓冲区加载，这是一个学到的表示，告诉模型这些位置应当预测未来的 token。

在 KV 缓存槽位映射中，有效 token 获得正常的槽位分配，而被拒绝的 token 被映射到 PADDING\_SLOT\_ID（-1），以防止虚假的缓存写入。对于 CUDA Graph，我们把捕获范围扩展 K × max\_num\_seqs，以容纳并行起草带来的更大草稿批次。

## P-EAGLE 的 vLLM 基准测试

我们在 GPT-OSS-20B 上训练 P-EAGLE，并在三个基准上评估：用于多轮指令跟随的 [MT-Bench](https://arxiv.org/abs/2402.14762)、用于长程代码生成的 [SPEED-Bench](https://huggingface.co/datasets/nvidia/SPEED-Bench) Code，以及用于函数级代码合成的 [HumanEval](https://github.com/openai/human-eval)。与公开可用的[原版 EAGLE-3 检查点](https://huggingface.co/RedHatAI/gpt-oss-20b-speculator.eagle3)相比，P-EAGLE 在低并发（c=1）下带来 55–69% 的吞吐量提升，并在高并发（c=64）下保持 5–25% 的增益。结果见图 4-6。

P-EAGLE 起草器是一个轻量的 4 层模型，训练目标是并行预测最多 10 个 token。为评估性能，我们在并发级别 C ∈ {1,2,4,8,16,32,64} 上扫过推测深度 K ∈ {3,5,7}。我们的目标是为 P-EAGLE 与原版 EAGLE-3 各自找到合适的部署配置。P-EAGLE 与原版 EAGLE-3 均采用线性起草。在本文语境中，"最佳 P-EAGLE"与"最佳 EAGLE-3"指达到峰值吞吐量的配置，以每秒 token 数（TPS）在给定推测深度 K 下衡量。对每种方法，我们选择在给定服务条件下使 TPS 最大的 K。

一个一致的模式浮现出来。P-EAGLE 在所有并发级别下都在 K=7 时达到峰值 TPS。相比之下，原版 EAGLE-3 在 K=3 时达到最高 TPS，其最佳深度偶尔会随并发水平偏向更高值。这一行为反映了并行起草的一个根本优势：P-EAGLE 在单次前向传播中生成全部 K 个草稿 token，因此能从更深的推测中获益而不产生额外的串行开销。相比之下，自回归起草器必须逐步生成推测 token，这限制了它们高效扩展到更大 K 的能力。

所有实验都在一块 NVIDIA B200（Blackwell）GPU 上使用 vLLM 并采用以下服务配置完成。

```
VLLM_USE_FLASHINFER_MOE_MXFP4_MXFP8=1 \
vllm serve openai/gpt-oss-20b \
    --speculative-config '{
      "method": "eagle3",
      "model": "amazon/GPT-OSS-20B-P-EAGLE",
      "num_speculative_tokens": 7,
      "parallel_drafting": true}' \
    --port 8000 \
    --max-num-seqs 1024 \
    --max-model-len 100000 \
    --max-num-batched-tokens 100000 \
    --max-cudagraph-capture-size 4096 \
    --no-enable-prefix-caching \
    --no-enable-chunked-prefill \
    --kv-cache-dtype fp8 \
    --async-scheduling \
    --stream-interval 20
```

> **注意。** 目前使用 EAGLE 起草器服务 GPT-OSS-20B 需要一个单行 vLLM 补丁（[PR#36684](https://github.com/vllm-project/vllm/pull/36684)）。请在启动前应用。该修复预计将进入即将发布的 vLLM 版本。

除了降低起草开销，P-EAGLE 的吞吐量收益还来自更好的接受长度（AL），即每轮推测中被验证器接受的草稿 token 平均数量。AL 越高，意味着越多起草工作转化为真实输出，直接提升有效 OTPS/TPS。

下表对比了 P-EAGLE 与原版 EAGLE-3 在 GPT-OSS-20B 上三个基准中的 AL：

**P-EAGLE（AL）：**

| 配置 | HumanEval | SPEED-Bench | MT-Bench |
| --- | --- | --- | --- |
| K=3 | 3.02 | 2.87 | 2.87 |
| K=7 | 3.94 | 3.38 | 3.70 |

**EAGLE-3（AL）：**

| 配置 | HumanEval | SPEED-Bench | MT-Bench |
| --- | --- | --- | --- |
| K=3 | 2.65 | 2.24 | 2.70 |
| K=7 | 3.03 | 2.59 | 3.27 |

在相同推测深度 K 下，P-EAGLE 的 AL 始终高于 EAGLE-3。在 K=7 时，P-EAGLE 在 HumanEval 上超出 EAGLE-3 30%（3.94 对 3.03），在 SPEED-Bench 上超出 31%（3.38 对 2.59），在 MT-Bench 上超出 13%（3.70 对 3.27）。值得注意的是，P-EAGLE 从更深推测中获益更多：从 K=3 到 K=7，P-EAGLE 的 AL 在 HumanEval 上增加 0.92（3.02 到 3.94），而 EAGLE-3 仅增加 0.38（2.65 到 3.03）。在更大 K 下不断扩大的差距，与 P-EAGLE 的单次前向传播并行起草一致——更深的推测不会带来额外成本。

## 结论

P-EAGLE 消除了投机解码中的串行瓶颈，在真实工作负载上相比原版 EAGLE-3 实现最高 1.69× 的加速。通过把草稿数量与前向传播次数解耦，我们现在可以探索更大的起草架构，甚至能相比单层基线提升接受率。该实现通过手写融合内核细致处理了输入准备、注意力元数据管理与 KV 缓存槽位映射的复杂性。虽然它需要专门训练的模型，但其性能收益使它成为 vLLM 投机解码能力的一个宝贵补充。

随着更多并行训练的模型可用，我们预期这一方法将成为生产级 LLM 部署的首选。P-EAGLE 的架构效率与 vLLM 成熟基础设施的结合，为追求极致推理性能与更低延迟的用户提供了一条清晰路径。

今天就试试：从 HuggingFace 下载一个预训练的 P-EAGLE 头，在 vLLM 配置中为任一受支持的模型设置 `"parallel_drafting": true`，亲自见证加速效果。
