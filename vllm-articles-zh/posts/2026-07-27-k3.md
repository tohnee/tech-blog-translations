# Kimi K3 来了：vLLM 上的高效 Day-0 支持

> 原文：[Kimi K3 Is Here: Efficient Day-0 Support on vLLM](https://vllm.ai/blog/2026-07-27-k3) · vLLM 博客

作者：vLLM 团队与 Inferact

[#模型](https://vllm.ai/blog/tags/models)[#性能](https://vllm.ai/blog/tags/performance)[#前缀缓存](https://vllm.ai/blog/tags/prefix caching)[#多模态](https://vllm.ai/blog/tags/multimodal)

我们很高兴宣布 vLLM 对 Kimi K3 的高效 Day-0 支持——Kimi K3 是迄今发布的最强大的开放权重模型之一。

上周，我们[预览](https://vllm.ai/blog/2026-07-22-kimi-k3-preview)了 Kimi K3 的生产级集成工作；今天，Moonshot AI 的权重已公开，支持也已上线。

![Kimi K3 day-0 support on vLLM](https://vllm.ai/blog-assets/figures/2026-07-27-k3/social-preview.png)

vLLM 对 Kimi K3 的 Day-0 支持

Kimi K3 是一个 2.8 万亿参数的混合专家（MoE）模型（每个 token 激活 896 个专家中的 16 个），构建于 Kimi Delta Attention（KDA）与 Attention Residuals（AttnRes）之上，具备 1M token 的上下文窗口和原生视觉能力。对我们来说，Kimi K3 带来的最令人兴奋的挑战，是让 KDA、MXFP4 MoE、KV 缓存管理、预填充/解码分离、投机解码和长上下文部署配方在同一个可运行的服务引擎中协同工作。

[预览文章](https://vllm.ai/blog/2026-07-22-kimi-k3-preview)讲解了内核与缓存架构，尤其是让前缀缓存作用于循环状态这一挑战。本文则是发布指南：vLLM 如何适配 Kimi K3 的架构、这些数字背后的内核工作，以及 Day 0 就绪的内容。

## 快速开始

```
# See the linked recipes for the exact Docker command.
vllm serve moonshotai/Kimi-K3 \
  --tensor-parallel-size 8 \
  --trust-remote-code \
  --load-format fastsafetensors \
  --enable-prefix-caching \
  --enable-auto-tool-choice \
  --tool-call-parser kimi_k3 \
  --reasoning-parser kimi_k3
```

运行 Kimi K3 最简单的方式，是使用 8 张 NVIDIA B300 GPU 或 8 张 AMD MI355X GPU 执行上述命令。

Inferact 还为 Kimi K3 训练并开源了一个 [DSpark 草稿模型（speculator）](https://huggingface.co/Inferact/Kimi-K3-DSpark)。在 serve 命令中加入以下选项即可启用：

```
--speculative-config '{"model":"Inferact/Kimi-K3-DSpark","method":"dspark","num_speculative_tokens":7,"attention_backend":"FLASHINFER_MLA","draft_sample_method":"probabilistic","rejection_sample_method":"block"}'
```

更多细节（包括各平台的 Docker 镜像和部署策略）请参阅详细的[配方](https://recipes.vllm.ai/moonshotai/Kimi-K3)。由于依赖较为复杂，目前只有 Docker 镜像可用。这些 Docker 镜像依赖若干预发布版本的依赖项，包括 [FlashInfer](https://github.com/flashinfer-ai/flashinfer)。

## TL;DR

- **2.8 万亿参数的多模态 MoE：** Kimi K3 每个 token 激活 896 个专家中的 16 个，支持高达 1M token 的上下文窗口，构建于 Kimi Delta Attention、Attention Residuals、LatentMoE 以及原生 MXFP4（4 比特）权重之上。
- **单用户最高 370 tok/s：** 得益于针对 Kimi K3 架构的大量优化，在 16 张 NVIDIA GB300 NVL72 GPU 上，vLLM 无投机解码时以 118 tok/s 服务 Kimi K3，启用 DSpark 后达到 370 tok/s（提升 3.14×）。
- **广泛的生产特性支持：** vLLM 支持投机解码、预填充/解码分离、基于 Mooncake 的智能体 KV 缓存、工具调用、推理输出和结构化输出，发布时即支持 NVIDIA（Hopper 与 Blackwell）和 AMD（MI355X）。
- **开源 DSpark 支持：** vLLM 支持面向 Kimi K3 的最先进块扩散投机解码算法，该草稿模型使用 vLLM 和 TorchSpec 训练，由 Inferact 开源。
- **混合前缀缓存：** 服务 Kimi K3 的循环 + 全注意力设计，需要针对循环 KDA 状态重新设计混合前缀缓存。这一改动如今惠及所有类似的混合线性模型。

## Kimi K3 的架构，以及 vLLM 如何服务它

![Kimi K3 architecture innovations](https://vllm.ai/blog-assets/figures/2026-07-27-k3/architecture.png)

Kimi K3 架构创新

*Kimi K3 架构创新，来自[官方发布博客](https://www.kimi.com/blog/kimi-k3)。*

Kimi K3 的架构在若干方面偏离了标准 Transformer，而每一处偏离都改变了服务引擎需要做的事情。[预览文章](https://vllm.ai/blog/2026-07-22-kimi-k3-preview)深入讲解了内部机制；这里我们回顾新特性，并聚焦 vLLM 如何适配以服务它。

### Kimi Delta Attention：循环注意力与全注意力的混合堆栈

**新特性：** Kimi K3 的大多数层是 KDA——一种线性注意力机制，用固定大小的循环状态取代不断增长的 KV 缓存，并与周期性插入的全注意力层交错，以保留精确的全局记忆。这正是 1M token 上下文变得可负担的原因。

**vLLM 如何服务它：** 一个统一的混合 KV 缓存管理器在同一调度器下并排管理两类内存：全注意力层使用分页 KV 块，KDA 层使用紧凑的循环状态块。专用的 KDA 注意力后端在预填充时运行 FlashKDA，在解码时运行融合 CUDA 内核（运行投机解码时则使用 Flash-Linear-Attention/Triton 路径）。

最难的部分是跨 Kimi K3 混合缓存的前缀缓存：全注意力层存储逐 token 的 KV，而 KDA 层在每个 token 都会更新循环与卷积状态，却不可能在每个可能的前缀边界都保留一份快照。vLLM 将大块物理 KDA 状态块与细粒度前缀匹配解耦：在这些块内登记状态快照，并在扩展之前复制它们，使长的共享提示能够同时复用 KDA 状态与分页 KV。这套混合缓存机制是 [vLLM 核心的新能力](https://vllm.ai/blog/2026-07-22-kimi-k3-preview)，如今惠及每一个与 Kimi K3 类似的混合模型。

![Kimi K3's hybrid KDA and full-attention cache](https://vllm.ai/blog-assets/figures/2026-07-27-k3/hybrid-cache.png)

Kimi K3 的混合 KDA 与全注意力缓存

*Kimi K3 将 Kimi Delta Attention 层与周期性的全注意力层交错；vLLM 的混合缓存将循环状态与分页 KV 一并管理。*

### Attention Residuals：跨深度学习到的残差贡献混合

**新特性：** 对每个 token，Block AttnRes 用沿深度的注意力取代普通的残差累加：每个 Transformer 子层用一个学习到的伪查询（pseudo-query）对来自前续层块的、经 RMS 归一化的残差状态加权，然后将对应的加权组合作为自身输入。

**vLLM 如何服务它：** vLLM 使用优化过的 Triton 与 CUDA 内核，在单次融合操作中计算沿深度的注意力 logits、softmax 和隐藏状态聚合。在支持的配置下，残差更新和输出 RMSNorm 也被折叠进同一个内核，从而减少预填充和解码中的中间内存流量与内核启动开销。

### Stable LatentMoE：16/896 稀疏度下的分位数均衡潜在空间专家

**新特性。** NVIDIA 提出的 [LatentMoE](https://research.nvidia.com/labs/nemotron/LatentMoE/) 将派发的 token 激活值投影到更窄的潜在维度上进行路由专家计算，再把合并后的专家输出投影回模型宽度——这降低了专家权重带宽和 all-to-all 流量，使得能在相近的推理成本下使用更多专家。Kimi K3 的 [Stable LatentMoE](https://www.kimi.com/blog/kimi-k3) 把这一设计扩展到 896 个专家、每个 token 激活 16 个，并使用[分位数均衡（Quantile Balancing）](https://kexue.fm/archives/11619)从路由分数的分位数推导专家分配，而不是启发式的均衡更新。

**vLLM 如何服务它：** 专家以专家并行方式分片。vLLM 提供两个针对不同拓扑调优的 MoE 后端：张量并行（TP > 1）用 TRT-LLM-Gen，分离式/专家并行（DEP）用 MegaMoE。它还支持可选的专家并行负载均衡（EPLB），确保每个 rank 的计算量相近。在 MoE 路径上，权重以 MXFP4 原生执行。

### 聊天模板：一个渲染程序，而非 Jinja 模板

**新特性：** Kimi K3 的聊天模板必须用精确的控制 token 对系统、用户与助手消息、多模态内容、工具定义和工具结果进行编码。常见的做法是使用 [Jinja 聊天模板](https://huggingface.co/moonshotai/Kimi-K2.7-Code/blob/main/chat_template.jinja)在分词之前把请求渲染为文本；Kimi K3 则改用一个 Python 程序直接构建提示 token 序列。它的输出同样包含推理、回答文本和工具调用等不同区域，需要解析成 API 响应。

**vLLM 如何服务它：** vLLM 在其 Python 与 Rust 前端中同时实现了输入渲染器和流式输出解析器，在保留控制 token 边界的同时，把用户与工具提供的文本当作普通内容处理。对于工具调用和结构化输出，vLLM 将 Kimi K3 的格式与 [XGrammar](https://xgrammar.mlc.ai/) 集成，使结构化区域在解码期间受到约束，并以推理、内容和工具调用等独立字段返回。

## 为生产环境而生

服务好一个 2.8T 的混合 MoE，意味着对每个用户都要快、对大量并发会话要高效、对智能体要可扩展。vLLM 确保这三点全部就绪。

### 超低延迟：使用 DSpark 的投机解码

要在 Kimi K3 这样的 2.8T 参数模型上实现不损失精度的超低延迟，投机解码是自然选择。因此 vLLM 从 Day 0 起就支持 DSpark 这一最先进的投机解码算法——我们也为 Kimi K3 训练并发布了 [DSpark 草稿模型](https://huggingface.co/Inferact/Kimi-K3-DSpark)。草稿模型使用 vLLM 与 [TorchSpec](https://github.com/lightseekorg/TorchSpec) 训练，使草稿模型的推理与训练在数值上完全一致。

DSpark 使用块扩散（block-diffusion）主干，基于 Kimi K3 丰富的中间状态在一次并行处理中生成多个草稿 token，因此随着块加深，起草成本保持平稳。低秩 Markov 头提供块内依赖，置信度头预测每个草稿被接受的可能性。我们把草稿模型做成 MLA 原生，与 Kimi K3 自身的注意力结构一致，使草稿模型与目标模型共享相近的 KV 布局，从而与高级 KV 管理和 P/D 分离部署最大程度兼容。

![Kimi K3 DSpark positional acceptance rates](https://vllm.ai/blog-assets/figures/2026-07-27-k3/dspark-acceptance-rates.png)

Kimi K3 DSpark 逐位置接受率

*Kimi K3 DSpark 在各数据集上的逐位置接受率。*

使用 DSpark，我们在单用户请求上取得 3.14× 的加速，从 118 tok/s 提升到 370 tok/s（使用 SPEED Bench 测得）。我们还在不同任务上对接受率和加速比做了基准测试，结果如上图所示。对编程等低熵任务，每步约接受 4.73 个 token；对创意写作等高熵任务，每步约接受 2.61 个 token。

基于 DSpark 的置信度调度是 vLLM 中正在进行的工作。启用后，它将利用 DSpark 模型内置的置信度头来预测每个草稿 token 被接受的可能性，优先处理强提案、剪除弱提案，从而不把验证算力浪费在注定无法存活的 token 上。

自本版本起，[草稿模型](https://huggingface.co/Inferact/Kimi-K3-DSpark)与推理支持均已开源。启用方法见下文的部署指南。

### TEP 预填充的序列并行

![Sequence parallelism for TEP prefill](https://vllm.ai/blog-assets/figures/2026-07-27-k3/sequence-parallelism.jpg)

TEP 预填充的序列并行

*序列并行把 token 所有权分片到各 rank；注意力残差按分片应用，随后一次 all-gather 在下一层的 QKV 投影前重建完整批次。*

在预填充阶段，我们把注意力张量并行与 MoE 专家并行结合（TEP）。与纯 TP 相比，TEP 降低了通信开销，并让每个 rank 保留完整的专家，从而获得更高效的专家 GEMM 形状。

然而，朴素的 TEP 实现每层要执行两次 all-reduce——一次在注意力输出投影之后，一次在 MoE 之后——因此每个 rank 都要物化完整批次，并对整个批次冗余地应用注意力残差。为解决这个问题，我们实现了[序列并行](https://arxiv.org/abs/2205.05198)：`o_proj` 之后的 all-reduce 替换为 reduce-scatter，使每个 rank 拥有一个 token 分片；注意力残差按分片应用；MoE 的 all-to-all 执行 dispatch 与 combine；最后由一次 all-gather 在下一层的 QKV 投影前恢复完整批次。

这一设计带来两个关键优势：

- **降低通信开销：** reduce-scatter + all-to-all dispatch + all-to-all combine + all-gather 在理论上比两次 all-reduce 更便宜。但在实践中，NCCL 的 reduce-scatter 和 all-gather 并未针对预填充的消息大小做优化，无法带来加速。因此我们实现了自定义的 reduce-scatter 与 all-gather 内核，比 NCCL 快 1.7×–4.5×，在中小消息规模下尤其明显。
- **分片的注意力残差：** 注意力残差在整个层内保持跨 rank 分片，因此每个 rank 只计算并维护自己那份 token 分片，而不是整个批次。这对 Kimi K3 尤为重要：AttnRes 把残差流变成了跨层持久状态，有自身的计算与内存开销。

序列并行在合适场景下默认启用：使用 TP 搭配 MegaMoE 内核时，或组合 TP + DP + EP 时。无需额外标志。

### 大规模服务：预填充/解码分离

在高吞吐场景下，vLLM 以跨节点的专家并行与数据并行、以及预填充/解码（PD）分离的方式服务 Kimi K3：偏预填充与偏解码的工作分别运行在不同的副本上，各自按自身瓶颈配置规模。我们验证过的拓扑之一，是把 TEP8 预填充路由到 DEP16 解码，并使用 NIXL 作为 KV 传输引擎。

PD 分离对混合模型毫不留情：循环 KDA 状态、全注意力分页 KV 和块表都必须正确抵达。NIXL 连接器把共享的 KV 缓存页视为两个逻辑视图：token 级的 MLA 缓存和请求级的 KDA 状态（包括卷积与循环状态）。在握手期间，它先交换 MLA/KDA 元数据，再为每次传输构建各自的传输描述符。

在异构 TP 下，vLLM 的混合分配器为预填充和解码使用不同的块大小。为支持这种情况，vLLM 的 NIXL 连接器跟踪逻辑块到物理块的映射，并将未传输的尾部区域清零，防止先前请求的陈旧数据经由填充或布局间隙泄漏进来。

### 协调部分块缓存命中与 KV 缓存卸载

正如 [Kimi K3 预览](https://vllm.ai/blog/2026-07-22-kimi-k3-preview)所述，vLLM 支持细粒度的前缀命中，命中可能结束于某个物理缓存块的中间。这给 KV 卸载带来了一个微妙挑战：vLLM 可能先在本地 GPU 上找到一个带部分尾部的命中，随后又在 Mooncake 之类的外部存储中发现更长的前缀。若是整块命中，远程复用可以干净地延伸到本地前缀之外；而部分尾部则可能与远程结果重叠。

因此，vLLM 调度器会比较两层各自可复用的精确 token 长度，并选择更长的前缀。如果远程命中胜出，它会释放为较短的本地尾部预留的块，并把所有缓存组调整到新的前缀长度。

重要的是，这一机制完全通过现有的 KV 连接器 API 构建，这些 API 已经提供了所需的全部语义。这让 `MooncakeStoreConnector`、`SimpleCPUOffloadConnector` 等连接器无需模型专属的集成路径，即可支持多层级的部分前缀复用。

该设计记录于 [RFC](https://github.com/vllm-project/vllm/issues/45702)，并由 [PR #45939](https://github.com/vllm-project/vllm/pull/45939)、[PR #46384](https://github.com/vllm-project/vllm/pull/46384) 和 [PR #49502](https://github.com/vllm-project/vllm/pull/49502) 实现。

### 智能体服务：更聪明的缓存保留策略

Kimi K3 的线性注意力层只需要常量大小的 KDA 状态，使其在长上下文长度下内存高效。单层的 KDA 状态大致相当于几千个 token 的 MLA 缓存。虽然不小，但与传统 KV 缓存不同，这一状态不会随序列长度增长。对于跨越数十万到一百万 token 的智能体工作负载，这一区别意义重大。

同样的设计也让前缀缓存变复杂。KDA 状态在解码时原地更新，因此 vLLM 必须在下一次前向传播覆盖它之前，把状态复制到选定的前缀边界处。在每个 token 位置都缓存是不可行的：每个 KDA 检查点远大于单个 token 的 MLA 缓存，很快就会耗尽即使是分布式缓存池。

为了在保留有用前缀的同时提升缓存空间效率，vLLM 支持两种互补的保留策略。

#### 基于区间的保留

缓存每个 KDA 状态很浪费，但缓存得太稀疏又会迫使下一个请求重新计算大段后缀。基于区间的保留通过把选定位置当作检查点来平衡这两种成本——例如每 32K token 一个。

提示边界是更好的检查点。在智能体工作负载中，下一轮通常以重放上一轮的提示开始，因此该提示末尾处的状态尤其可能被复用。vLLM 会自动检测并保留这些边界。

用户可以通过 `VLLM_PREFIX_CACHE_RETENTION_INTERVAL` 控制周期性检查点。设为 `0` 会禁用周期检查点、只保留提示结束状态，适合以多轮对话为主的工作负载。更大的区间则以一些重计算换取更低的缓存占用。

基于区间的保留最初在 [PR #43447](https://github.com/vllm-project/vllm/pull/43447) 中为 DeepSeek V4 和混合滑窗注意力模型引入；对 Kimi K3 与混合线性注意力模型的 Day-0 支持在 [PR #45845](https://github.com/vllm-project/vllm/pull/45845) 中加入。

![Interval-based KDA cache retention](https://vllm.ai/blog-assets/figures/2026-07-27-k3/interval-cache-retention.png)

基于区间的 KDA 缓存保留

*基于区间的缓存保留。MLA 为每个块缓存 KV，而 KDA 状态只在检查点保存：提示结束处（绿色）总是保留，固定区间检查点（橙色）可配置。*

#### Marconi 式选择性保留

提示结束保留对对话状态很有效，但有价值的共享前缀也可能出现在别处。系统提示、仓库快照或工具规范可能在大量请求间复用，却不与任何提示边界对齐。

[Marconi 式保留（MLSys '25）](https://mlsys.org/virtual/2025/poster/3260)用一条简单规则处理这些情况：第二次命中时才缓存。第一次观察提供了前缀存在的证据；第二次才说明它确实被共享。只有此时，vLLM 才会为其 KDA 状态投入缓存容量。

这让保留变成一个按需驱动的决策。一次性前缀不会挤占缓存，而反复出现的前缀会被自动提升——用户无需预测自己工作负载的哪些部分会变热。

选择性保留最初在 [PR #37898](https://github.com/vllm-project/vllm/pull/37898) 中引入；Kimi K3 的 Day-0 支持在 [PR #47782](https://github.com/vllm-project/vllm/pull/47782) 中加入。

![Selective KDA cache retention](https://vllm.ai/blog-assets/figures/2026-07-27-k3/selective-cache-retention.gif)

选择性 KDA 缓存保留

*选择性缓存保留。请求 1 只在自己的提示结束处（越过共享前缀）保存 KDA 状态，因此请求 2 命中 KV 却未命中 KDA。这第二次出现就是前缀被共享的证据，于是在前缀边界缓存一份状态，请求 3 即可复用它。*

两种策略共同覆盖了可预测与涌现的复用：区间保留在结构上重要的边界设置检查点，Marconi 式保留则学习哪些其他前缀值得保留。

## 性能优化

服务像 Kimi K3 这样的大模型，其规模本身就带来挑战。整个模型几乎塞满一台 NVIDIA DGX B300，在该代硬件上服务至少需要 16 张 NVIDIA B200/GB200 GPU。服务必须在交互性与系统总吞吐之间权衡：张量并行利于交互性，但由于有效 KV 缓存大小受限，总体吞吐较低；大规模专家并行则可能因网络带宽瓶颈限制单用户输出 token 速度。这里我们重点介绍能同时改善两种情况的优化，以便用户选择适合自身工作负载的配方。其中许多优化已在我们的[预览博客](https://vllm.ai/blog/2026-07-22-kimi-k3-preview)中介绍过。

### Attention Residuals

Kimi K3 使用 Block AttnRes：对最多八个缓存的块表示加上当前块内残差做注意力。对每个 token，vLLM 从 RMS 归一化的来源计算 logits，在这些沿深度的候选上做 softmax，并聚合它们的表示。其实现类似 FlashAttention 的在线 softmax 策略，但作用于模型深度而非序列位置，且来源最多九个。vLLM 在单个融合内核中完成这一混合，把输入端的残差更新纳入其中，并可选地对输出应用 RMSNorm。可移植的 Triton 实现覆盖通用路径，专用 CUDA 内核则为受支持的 Blackwell 配置加速。

### KDA 解码

![Fused KDA decode kernel](https://vllm.ai/blog-assets/figures/2026-07-27-k3/kda-decode.png)

融合 KDA 解码内核

*融合的 KDA 解码内核把因果卷积、循环更新和 RMSNorm 折叠进单次启动，而不是一串独立内核。*

一个 KDA 层涉及许多操作：输入投影、因果一维卷积、QK 归一化、门控计算、KDA 循环更新以及输出门控 RMSNorm。在受支持的配置上，vLLM 把投影之后的解码路径——从因果卷积直到门控 RMSNorm——融合进单个专用 CUDA 内核。该内核原地更新卷积与循环状态并直接写出归一化输出，避免了在 Kimi K3 大量 KDA 层上的中间张量、反复的状态读写和逐操作启动开销。不受支持的配置由可移植的 Triton 回退路径覆盖。

### KDA 预填充

KDA 预填充成了我们最喜欢的开源开发实践案例之一。Moonshot AI 首先发布了 [FlashKDA](https://github.com/MoonshotAI/FlashKDA)——KDA 的高性能 CUTLASS 实现。我们迅速将其集成进 vLLM，并处理了那些不那么光鲜的生产细节：更广的 GPU 覆盖、元数据 dtype、张量布局和可靠的 vendor 化。随后 [Shikhar Mishra](https://github.com/Itssshikhar) 为 H100 优化了这些内核，发布了 [Flash-Flash-KDA](https://github.com/Itssshikhar/Flash-Flash-KDA)，在保持数值正确性的同时改进了数据搬运。一天之内，我们在 GB300 NVL72 上验证了这些改进，完善了递推流水线与同步，并把它们并入我们的 FlashKDA 集成。结果不是一次单向交接，而是一个持续循环：一个开放内核由服务社区扩展、由独立贡献者改进，并迅速进入生产。

### KDA 元数据构建器

![Nsight Systems traces before and after KDA metadata preparation optimization](https://vllm.ai/blog-assets/figures/2026-07-27-k3/kda-metadata-builder.png)

KDA 元数据准备优化前后的 Nsight Systems 追踪

在 Kimi K3 DSpark 的调通过程中，KDA 元数据准备成为一个显著的开销来源。Kimi K3 最初复用通用的 GDN 元数据构建器，它会准备 K3 并不消费的 FLA 元数据，并用一串小的 eager PyTorch 操作来组装和暂存 GPU 元数据。我们引入了专用的 Kimi K3 KDA 元数据构建器，裁剪掉未使用的路径，并用融合的 Triton 内核取代那些操作序列，把每个序列缩减为一次启动。在批大小为 1 时，这将元数据准备延迟降低了 96%（从 870 μs 降到 34 μs），并将端到端 DSpark 延迟改善 6%。

### 低延迟 BF16 GEMM

在小批大小、延迟敏感的场景中，我们把若干线性投影层使用的通用 BF16 GEMM 替换为我们自己的 `skinnyGEMM` 实现。通用 cuBLAS 内核在这里达不到最佳性能，因为它们针对更通用的形状优化。在该内核中，我们绕过共享内存的数据暂存，把激活值和权重直接加载进寄存器，并用 CUDA Core FMA 指令完成计算，从而避免了为达成最大吞吐所需的繁重 TMA 与 Tensor Core 设置阶段。微基准测试显示内核级加速从 8% 到 100% 不等，小批场景下端到端延迟约降低 10%。

### 低延迟 MoE 尾部融合

![LatentMoE tail-fusion optimization](https://vllm.ai/blog-assets/figures/2026-07-27-k3/latent-moe-tail-fusion.png)

LatentMoE 尾部融合优化

*LatentMoE 尾部优化用三个内核取代两次 all-reduce、RMSNorm、潜在上投影和一次逐元素相加，以减少计算并更好地重叠通信与计算。*

vLLM 采用一种新策略来降低超低延迟服务中潜在 MoE 的尾部延迟。在 LatentMoE 的末尾，来自路由专家的归并激活必须先经 RMSNorm 归一化并做上投影，然后才能加到共享专家输出上。在常规 TP 情况下，这需要对路由专家与共享专家各做一次 all-reduce（或一次带拼接的 all-reduce），并复制上投影。

为了避免复制式线性投影中的冗余计算，vLLM 改为对共享专家执行 reduce-scatter，而对路由专家保留 all-reduce（因为其激活值需要归一化）。复制后的路由专家激活以列并行方式与上投影做矩阵乘法，再逐元素加到已分片的共享专家输出上。最后，结果通过 broadcast all-gather 到每个 rank。我们观察到该步骤延迟约降低 20%，端到端加速约 7%–8%。

## 质量与性能基准

### 精度与正确性评估

vLLM 对精度与速度同样重视。我们通过所服务的 OpenAI 兼容端点对 Kimi K3 做了端到端验证（配方中有精确配置），它干净利落地通过了精度评估。在最高推理努力等级下，vLLM 上的 Kimi K3 在 GSM8K 得分 0.976、GPQA-Diamond 得分 0.939、OCRBench 得分 0.889、MMMU Pro Vision 得分 0.818。

评估时值得注意的一点：Kimi K3 在回答之前会进行大量思考。低分更常见的原因是答案被截断而非答错，因此请提高推理努力、把 `max_tokens` 设得宽裕一些，并先检查生成是否被截断，再去排查其他问题。

### 服务性能

Kimi K3 单用户解码吞吐

## 重要的部署提示

1. **前缀缓存：** `--enable-prefix-caching` 用于开启前缀缓存。vLLM 中前缀缓存通常默认开启，但由于混合缓存设计仍在演进，Kimi K3 目前默认关闭。请显式传入该标志。
2. **工具调用：** 在依赖它之前，先在自己的流量上验证。我们偶尔观察到 K3 会发出其自身解析器未预期的工具调用格式，导致 `tool_calls` 结果为空，而同一环境下干净的探测请求却解析完美。这取决于提示与具体运行，并非普遍性失败，但生产智能体应对照你的 schema 做验证，在 `tool_calls` 返回为空时重试或回退，并考虑使用严格模式或结构化工具调用（在生成期间约束输出语法）。
3. **All-to-all 后端：** `--all2all-backend` 决定 MoE 后端在专家并行期间的通信方式。NVIDIA NVLink 用 `flashinfer_nvlink_one_sided`，RDMA 用 `deepep_v2`。
4. **MoE 后端：** vLLM 为不同场景提供多个 MoE 后端。我们建议任何 DEP 环境使用 `deep_gemm_mega_moe`。
5. **Rust 前端：** 设置 `VLLM_USE_RUST_FRONTEND=1` 启用 Rust 前端，它完整支持该模型。
6. **ViT 并行：** `--mm-encoder-tp-mode=data` 默认启用。K3 的视觉编码器 `head_size=12`，在 TP=8 下无法均匀分片。由于 K3 的视觉编码器参数量不足 1B 而主干约 2T，我们默认启用 ViT DP，以避免编码器带来的 all-reduce 开销。

## Kimi K3 vLLM 常见问题

### 服务 Kimi K3 需要多少张 GPU？

至少需要一个 8× B300（或 GB300 NVL72）节点；也支持 16× B200。大多数生产部署采用多节点，通过 RDMA 或 NVLink 互连，并结合专家并行与数据并行。

### 如何启用 DSpark 投机解码？

加入：

```
--speculative-config '{"model":"Inferact/Kimi-K3-DSpark","method":"dspark","num_speculative_tokens":7,"attention_backend":"FLASHINFER_MLA","draft_sample_method":"probabilistic","rejection_sample_method":"block"}'
```

它能把推理与编程任务上的单流解码速度大致提升到三倍。

### 应该使用哪个 MoE 与 all-to-all 后端？

分离式或专家并行（DEP）部署用 `deep_gemm_mega_moe`，TP > 1 用 `flashinfer_trtllm`。all-to-all 后端按互连选择：NVLink 用 `flashinfer_nvlink_one_sided`，RDMA 用 `deepep_v2`。

### Kimi K3 支持前缀缓存吗？默认开启吗？

它支持对全注意力 KV 和循环 KDA 状态的前缀缓存，但默认未开启，请传入 `--enable-prefix-caching`。

### vLLM 支持 AMD GPU 上的 Kimi K3 吗？

支持。ROCm 支持随发布一同提供，更广泛的调优已在路线图上。

### 这篇文章与 Kimi K3 预览文章有何不同？

[预览文章](https://vllm.ai/blog/2026-07-22-kimi-k3-preview)是架构与内核的深入剖析，包括 KDA 前缀缓存和各内核是如何构建的。本文则是实用的发布指南，包含成果物：vLLM 如何适配 Kimi K3、配方、标志、性能，以及 Kimi K3 在生产中已就绪的能力。
