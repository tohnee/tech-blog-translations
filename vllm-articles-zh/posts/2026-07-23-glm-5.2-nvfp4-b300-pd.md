在相同硬件上，我们的起点是 16K token 输入下接近 40 ms 的平均 TPOT——约为 SLA 上限的两倍。本文记录了从 40 ms 到 17 ms 的完整历程：每一步改了什么、每项改动贡献了多少，以及为什么我们最终采用的并行策略*不是*原始吞吐量最高的那一个。文末附有一套完整、可复现的 `vllm serve` 命令。

## 1. 为什么我们围绕 SLA 达标而不是峰值吞吐量做优化

在共置（colocated）服务中，预填充分块被穿插进解码批次，每个进入批次的长提示都会拉长所有正在解码请求的逐 token 延迟。因此 TPOT 尾延迟变成了输入提示长度分布的函数——而这是服务系统无法控制的。分离部署把预填充工作彻底移出解码关键路径，使 TPOT 只由解码批次构成决定。这正是紧凑 TPOT SLA 得以实现的前提，也是本文其余部分把 P/D 当作起点而非众多优化之一的原因。

生产服务的验收从来不只看峰值吞吐量。真正的问题是：在*不违反*延迟目标的前提下，系统能承受多少流量。我们的需求非常明确：

- 典型上下文长度：16K–256K token
- **平均 TTFT ≤ 2.5 s** —— 用户操作到首个可见 token 之间可接受的最大延迟
- **平均 TPOT ≤ 20 ms** —— 大约 50 token/s 的流式输出；低于这个速率，阅读体验会明显下降
- 在这两条硬约束下，最大化吞吐量

关于批大小的说明：我们没有固定它。负载以请求速率施加，并发数就是该速率在 SLA 约束下自然形成的值——刻意让它在延迟预算允许范围内尽量大。因为预填充成本随上下文长度增长，并发数随输入长度上升而下降：8K 时约 700 个并发请求，16K 时约 300 个，256K 时约 25 个，全部受 `--max-concurrency 1024` 上限约束。

这一目标贯穿了整个方法论：每一次配置搜索都是约束感知的。一个把吞吐量提高 30% 却把平均 TPOT 推过 SLA 的配置，对我们毫无用处。第 4 节有一个典型的例子。

GLM-5.2 是一个 744B 参数、40B 激活参数的 MoE 模型。它使用 DSA 稀疏注意力，原生支持 MTP 投机解码，而 vLLM 对这三者都已提供成熟支持。我们的工作是把它们与 P/D 分离部署有效结合，然后围绕生产 SLA 目标调优参数、拓扑与调度。

## 2. 起点：改善 P/D 分离下的解码性能

在初始配置下，预填充侧已经达标，TTFT 余量充足。瓶颈在解码：16K 输入 token、1K 输出 token 时，平均 TPOT 接近 40 ms，且 P99 抖动明显。

### 2.1 根因：P/D 交接处的混合批次

投机解码已经成为大型 MoE 模型的标准推理期优化，生产解码部署也越来越多地默认开启它。性能剖析揭示了一个恰好位于 P/D 分离与投机解码交互之处的问题。

一个请求通过 KVConnector 把提示 KV 缓存传输到解码节点后，它的第一个解码步骤只需要计算一个 token。但该解码节点上的既有请求在启用 MTP 时按每步 1 + N 个 token 调度。由于两类请求形状不同，这一步就变成了混合批次，无法再走均匀解码（uniform-decode）的完整 CUDA Graph 快速路径，而退回到更昂贵的分段（piecewise）或 eager 执行路径。

数据并行会放大影响。在 DP 下，CUDA Graph 模式与填充需要跨 rank 协调，因此只要任何一个 DP rank 收到新传输的请求，其余 rank 也会跟着走上同一条执行路径。在稳态 P/D 运行中，新请求源源不断地到达解码实例，慢路径因此被持续触发。

### 2.2 优化：解码侧的投机填充

修复在概念上很简单。在请求到达后的第一个解码步骤，用虚拟投机 token 把它的形状填充到 1 + N，与解码 worker 中已有的其他请求保持一致。这样既保住了均匀解码执行，也让工作负载继续留在完整 CUDA Graph 快速路径上。

它不需要从预填充节点传输任何已生成 token 或草稿 token。该优化已由 vLLM 社区在 [PR #45237](https://github.com/vllm-project/vllm/pull/45237) 中合并。

### 2.3 性能收益

混合批次造成的执行路径退化被消除后，端到端平均 TPOT 从约 40 ms 降到约 22 ms——这是整个工作中单项最大的改进。

这一结果给结合 P/D 分离与投机解码的部署带来一个更普遍的教训：最大的性能损失可能不在任何单个内核里，而是出现在子系统之间的边界上——请求状态、调度形状与 CUDA Graph 执行模式上的微小不一致，会被 DP 规模和持续流量放大。

## 3. 解码侧的进一步优化

22 ms 已接近 SLA 但毫无安全余量，于是我们进行了又一轮配置搜索。

### 3.1 Model Runner V2：TPOT 降低 11%

vLLM Model Runner V2（MRV2）重构了运行时执行路径。自 v0.25.0 起它是所有稠密模型的默认项；GLM-5.2 是 MoE 模型，因此默认不启用，必须通过 `VLLM_USE_V2_MODEL_RUNNER=1` 显式开启。

在我们的解码配置上，MRV2 比 MRV1 改善了约 11% 的 TPOT。除了更短的执行路径，MRV2 还带来了几项对可预测生产延迟至关重要的能力：

1. [PR #47285](https://github.com/vllm-project/vllm/pull/47285) 把 GLM-5.2 DSA 索引器的预填充元数据内核加入启动预热，首个生产请求不再触发 Triton JIT 编译和延迟尖峰。这一点在基准测试中很容易被忽略，因为预热会把它吸收掉；而在生产环境中，它表现为每次滚动部署后的冷启动尖峰。
2. [PR #46448](https://github.com/vllm-project/vllm/pull/46448) 为多 GPU MTP 增加了本地 argmax 归约。启用 `use_local_argmax_reduction` 后，草稿 token 生成不再 AllGather 全词表 logits，TP 通信量从与词表大小成正比降到约 2 × TP 规模。在 MRV2 下运行的 MTP、EAGLE、DFlash 及其他投机器都从中受益。
3. [PR #45953](https://github.com/vllm-project/vllm/pull/45953) 让动态投机长度与完整 CUDA Graph 兼容，减少了草稿长度变化导致的图未命中与 eager 回退。

### 3.2 All-to-All 后端：TPOT 再降 4%

由于 GLM-5.2 是 MoE 模型，解码侧运行 DEP8，把专家分发与合并（combine）通信直接放在了关键路径上。我们把默认的基于 AllGather/ReduceScatter 的 EP 后端换成了 FlashInfer NVLink A2A 后端；在我们的测量中，`flashinfer_nvlink_two_sided` 再把 TPOT 降低了 4%。

vLLM 现在也内置了更新的 `flashinfer_nvlink_one_sided` 后端，预计性能更好。本文保留双边（two-sided）后端，因为那是我们实际测量过的配置。在相同解码工作负载下评估单边（one-sided）后端已列入计划。

### 3.3 CUDA Graph 模式

解码实例运行 `--compilation-config '{"cudagraph_mode":"FULL_DECODE_ONLY"}'` 并配合 `--max-num-batched-tokens 1024`。解码侧不需要为预填充形状编译图，而 `FULL_DECODE_ONLY` 在显著缩短启动编译时间的同时，为解码路径提供了完整的图覆盖。

### 3.4 MTP 投机解码

我们在解码侧使用 `num_speculative_tokens=3`，预填充侧使用 `1`。（MTP 只有配合第 5 节讨论的 IndexerCache 才在 GLM-5.2 上划算。）这种不对称是有意为之：预填充节点应尽快产出并移交 KV 缓存，更深的投机在那里收益甚微；解码节点位于延迟关键路径上，更深的投机可以摊薄每个 token 的执行成本——前提是接受率保持高位。

## 4. 预填充并行：为什么我们没有选择吞吐量最高的配置

在预填充侧，我们在 8K 和 32K token 输入下比较了几种并行策略。由于各配置使用的 GPU 数量不同，TGS——单 GPU 吞吐量——才是有意义的指标。

![四种并行策略在 8K 与 32K 输入长度下的单 GPU 预填充吞吐量。](https://vllm.ai/blog-assets/figures/2026-07-23-glm-5.2-nvfp4-b300-pd/04-prefill-parallelism-tgs.svg)

四种并行策略在 8K 与 32K 输入长度下的单 GPU 预填充吞吐量。

从绝对值看，TP1 DP4 EP 是最快的实例——8K 输入下 47,806 tok/s——但这只是因为它使用的 GPU 数量是其他配置的两倍；按单 GPU 计算它只排第二。有两个结论值得注意：

1. **TP2 + EP 表现不如纯 TP2。** 在只有两 GPU 的规模上，EP 引入的 all-to-all 开销超过了它的收益。EP 需要足够多的专家分布在足够多的设备上，才能摊薄其通信成本。
2. **TP1 DP2 EP 取得了最佳 TGS，但我们上线的是 TP1 DP4 EP。**

第二点正是生产工程与刷榜的分野所在。TP1 DP2 EP 提供了最佳的单 GPU 效率，但每个实例只有两块 GPU，KV 缓存容量太小，承载不了 GLM-5.2 的 1M token 上下文能力。我们不愿为了 8% 的 TGS 优势放弃模型最重要的特性之一，于是选择了 TP1 DP4 EP——用约 8% 的单 GPU 效率换取每实例四块 GPU 的 KV 缓存容量。

## 5. MTP + IndexerCache：我们如何提高接受率

vLLM 在常规配置下的生产表现已经过广泛验证。而这次部署同时启用了三项相对较新的能力——P/D 分离、MTP 与 MRV2——让我们走上了一条较少被演练的组合路径，调优过程也暴露出若干长尾问题。大多数修复从报告到发布只用了几天；使用 v0.26.0 的用户已经拥有全部修复。本节记录这些工作，展示 MTP 接受率是如何一步步稳定下来的。

### 5.1 IndexerCache：让 MTP 在 DSA 下变得划算

IndexerCache（[PR #44420](https://github.com/vllm-project/vllm/pull/44420)）不是传统 KV 缓存——它复用 DSA 索引器产出的 Top-K 稀疏索引。朴素的实现会在每个 MTP 草稿步骤重跑索引器，而稀疏检索的成本随上下文长度增长，这会吞掉投机解码预期收益的很大一部分。PR #44420 引入了 `index_share_for_mtp_iteration`，让第一个草稿步骤计算 Top-K 索引、后续草稿步骤复用它们。这是 MTP 在 GLM-5.2 上划算的前提。

随后社区围绕这一机制完成了三项改进，共同稳住了高并发下的接受率：

- [PR #45895](https://github.com/vllm-project/vllm/pull/45895) 改进了跳过 Top-K 层时的索引器初始化，并修复了 GLM-5.2 MTP 的归一化循环。PR 报告称，在 TP=8 的 GLM-5.2-FP8 上，平均接受长度从约 3 提升到约 4，平均接受率约 60%，IFBench 稳定在 74.62。
- [PR #47238](https://github.com/vllm-project/vllm/pull/47238) 优化了批量请求共享索引缓冲区的布局：第一个草稿步骤之后，只保留与每个请求最终 query token 对应的 Top-K 索引。这是把索引共享从单请求执行扩展到高并发批处理的关键一步。
- [PR #47448](https://github.com/vllm-project/vllm/pull/47448) 确保 MTP 循环复用 final norm 之后的隐藏状态。

综合来看，IndexerCache 不仅仅是一项节省计算的优化，也是在高并发下维持 MTP 接受率的关键机制。

### 5.2 组合配置下的另外两个修复

**MRV2 调度分类。** 切换到 MRV2 后，我们在某个特定基准模式下观察到过大的 TPOT 方差，并在 [Issue #47239](https://github.com/vllm-project/vllm/issues/47239) 中报告。社区很快把它追溯到均匀解码排序：投机解码步骤被归类为预填充，从而走了更慢的执行路径。[PR #47381](https://github.com/vllm-project/vllm/pull/47381) 修复了它。

**P/D 部署中异步 KV 加载的前瞻处理。** [PR #46694](https://github.com/vllm-project/vllm/pull/46694) 改进了 GLM-5.2 + NIXL P/D + MTP 组合配置下的槽位分配时机。解码器现在会等到远程 KV 传输完成后再分配投机 token 槽位，正确处理最后一个 KV 块不完整的边界情形。这种部分块交接是 P/D 分离与投机解码交互特有的问题，修复它是让这条路径达到生产可用水平的又一步。

两项修复都包含在 v0.25.0 及之后的版本中。

### 5.3 精度验证

我们用最终配置运行了一组公开基准测试，验证 NVFP4 量化、MTP 与 P/D 分离的组合没有降低输出质量：

| 测试项 | 分数 |
| --- | --- |
| AIME 2025 | 86.67 |
| GPQA | 92.89 |
| LongBench V2 | 64.01 |
| MMLU-Pro | 86.3 |
| SWE-bench Verified（智能体） | 85.2 |

结果与社区报告的 GLM-5.2 分数一致。LongBench V2 对我们最重要，因为它直接检验长上下文下的 DSA 稀疏注意力与 IndexerCache 索引共享。64.01 的分数说明索引共享在长上下文工作负载中站得住脚，投机解码带来的加速没有以牺牲输出质量为代价。

## 6. 上游进展

本次部署使用的各项能力，建立在 vLLM 社区在 GLM-5.2 优化跟踪 issue（[Issue #46654](https://github.com/vllm-project/vllm/issues/46654)）下协调的一批更广泛的优化之上。除了上文引用的 PR，还有两项进展尤其相关。

**P/D 分离的二级缓存层。** [PR #42285](https://github.com/vllm-project/vllm/pull/42285) 引入了统一的 CPU KV 缓存布局作为中间层。`TieringManager` 协调主缓存层与 P/D 连接器，降低了传输后端与模型执行路径之间的耦合。已合并进 v0.25.0。

**面向长上下文预填充的 PCP 虚拟批处理。** [PR #46570](https://github.com/vllm-project/vllm/pull/46570) 把请求拆分为多个虚拟批次行，在上下文并行 rank 之间并行处理，只聚合 MLA 潜变量缓存与 DSA 索引器缓存。在初步的 4 GPU GLM-5.2-NVFP4 / 32K 预填充测试中，TP=2 配合 PCP=2 把提示吞吐量从约 20.1K tok/s 提升到约 27.3K tok/s。该 PR 已于 2026 年 7 月 19 日合并进 `main`，将随下一个版本发布。由于 KV 缓存容量正是我们在第 4 节放弃 TGS 最优配置的原因，PCP 可能改变这一权衡，它也是我们下一阶段验证的重点。

## 7. 可观测性：上线后验证 SLA

跑通一个基准测试并不意味着系统达到生产就绪。分离式 P/D 部署的可观测性比单实例更难，因为请求延迟被拆分到两个资源池：TTFT 主要由预填充池决定，TPOT 由解码池决定，中间还有一次 KV 传输。当任何环节退化时，用户只看到一个症状——服务变慢了。

我们用 Prometheus 和 Grafana 为 P/D 拓扑搭建了监控。在生产中我们关注以下指标组：

- **按池的 TTFT 与 TPOT 分位数**，而不只是端到端聚合值。这是判断问题属于预填充还是解码的第一入口。
- **MTP 接受率与平均接受长度。** 容易被忽视，却是最早的预警信号之一。接受率下降不会报错；TPOT 只是逐渐变差。实践中，这是我们遇到任何解码侧异常时最先打开的仪表盘，我们建议把 MTP 接受率当作一等告警指标。
- **KV 缓存利用率与 GPU 利用率的对比**，在预填充和解码两侧都要看。P/D 分离的核心收益是两类资源可以独立扩展；这两条曲线的相对水平就是扩容信号。
- **KV 传输延迟与队列深度**，用于判断节点间网络是否已成瓶颈。

### 7.1 只有长时间稳定性测试才能暴露的问题

短期基准测试验证的是性能，而不是长期稳定性。我们的生产验收流程包含连续多天的运行，正是这一环节暴露出持续的主机内存增长：vLLM 进程 RSS 在数十小时内线性上升，未见平台期。

![Grafana Memory Usage（WSS）面板：vLLM 容器内存在数十小时内从约 721 GiB 线性增长到约 800 GiB。](https://vllm.ai/blog-assets/figures/2026-07-23-glm-5.2-nvfp4-b300-pd/03-host-memory-growth.png)

Grafana Memory Usage（WSS）面板：vLLM 容器内存在数十小时内从约 721 GiB 线性增长到约 800 GiB。

以下几个特点解释了为什么这个问题需要生产监控而非基准测试才能发现：

- 增长速度很慢，只有以小时计才能看出来。持续几秒或几分钟的 `vllm bench serve` 无法暴露它。
- 增长影响的是主机内存而不是显存。所有 GPU 侧指标看起来都正常。
- 常规内存分析工具看不到它。`EngineCore` 在启动时调用 `gc.freeze()`，泄漏的对象从不出现在 `gc.get_objects()` 或 `tracemalloc` 中；症状看起来像分配器碎片化。

我们在 [PR #47723](https://github.com/vllm-project/vllm/pull/47723) 中向社区报告了这一行为和我们的初步诊断，一位维护者把它并入 [PR #44490](https://github.com/vllm-project/vllm/pull/44490)。

根因是生产者与消费者之间的门控不一致。[PR #35219](https://github.com/vllm-project/vllm/pull/35219) 引入了 `SingleTypeKVCacheManager.new_block_ids` 用于清除 Mamba SSM 缓存状态。条目按 KV 缓存 spec 类型记录——`FullAttentionSpec`、`MLAAttentionSpec` 等——但只有在模型包含 Mamba 层时才会被清除。对于没有 Mamba 层的模型——包括大多数标准注意力模型和带 MLA 的 GLM-5.2——每次块分配都会被记录，而列表从不排空，因此随请求量增长而无限增长。修复方案是在每个调度步骤无条件排空 `take_new_block_ids()`，只在确实需要清除时才使用其结果。Mamba 行为不变。

### 8.4 基准测试方法

所有性能数据都使用 `vllm bench serve` 的随机数据集采集。没有前缀缓存命中，因此 TTFT 数字代表最坏情况下的纯计算延迟。请求以固定的 `--request-rate` 注入，其值为目标 TPS 除以 `(input_len + output_len)` 再乘以一个调节系数。

```
vllm bench serve \
  --backend openai-chat \
  --model /mnt/model/glm/GLM-5.2-NVFP4 \
  --endpoint /v1/chat/completions \
  --dataset-name random \
  --random-input-len 16384 \
  --random-output-len 1000 \
  --request-rate <target TPS / (input + output) × tuning factor> \
  --percentile-metrics ttft,tpot,itl,e2el \
  --metric-percentiles 50,90 \
  --save-result
```

## 9. 下一步

对于 GLM-5.2 以及后续更大的 MoE 模型，我们看到解码优化的两个主要方向。以下是前瞻性判断，而非本文测得的结论。

**第一，降低每次目标前向计算的成本。** 除 GEMM、Attention 和 Indexer 等核心内核外，还包括探索 PDL、持久内核、局部化 megakernel，以及 MoE Dispatch、Expert GEMM 与 Combine 之间的计算通信协同。随着部署扩展到多节点，WideEP、分层 all2all，以及节点间通信与计算的重叠变得越来越重要。目标是缩短完整解码步骤的端到端关键路径。

**第二，推进面向投机解码的模型-运行时协同优化。** 模型侧，DSpark 等更强的草稿模型可以在更广的数据集上训练，以提高连续提案 token 的准确率。运行时侧，动态投机解码、按请求的提案长度与紧凑验证可以在不同工作负载下控制验证成本。草稿模型决定系统能预测多远；服务运行时决定预测真正划算到多远。

此外，第 6 节描述的 PCP 虚拟批次工作已进入 `main`。我们将评估它能否消除第 4 节讨论的 KV 缓存容量与单 GPU 效率之间的权衡。
