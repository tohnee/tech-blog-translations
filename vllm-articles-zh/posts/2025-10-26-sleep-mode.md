# vLLM 睡眠模式：零重载的模型切换

> 原文：[Zero-Reload Model Switching with vLLM Sleep Mode](https://vllm.ai/blog/2025-10-26-sleep-mode) · vLLM 博客

作者：Embedded LLM

[#性能](https://vllm.ai/blog/tags/performance)

## 引言

**多模型服务难题：** 你有两个 LLM，各自都能放进你的 GPU，但两个无法同时容纳。传统方案逼你做出糟糕的权衡：

1. **两个模型都常驻显存** → 需要双倍 GPU 显存（昂贵，且常常不可行）
2. **按需重新加载模型** → 每次切换需要 30-100 多秒（缓慢，浪费）

![vLLM Sleep Mode](https://vllm.ai/blog-assets/figures/2025-vllm-sleep-mode/sleepmode.png)

vLLM 睡眠模式（Sleep Mode）

**vLLM 睡眠模式提供了第三条路：** 模型几秒内进入休眠，又能快速唤醒——兼具按需加载的高效与常驻服务的速度。

### 两种睡眠等级，满足不同需求

- **Level 1：** 将权重卸载到 CPU 内存（唤醒快）
- **Level 2：** 完全丢弃权重（唤醒速度几乎同样快，内存占用极小）

两种等级都比完整重载**快 18-200x**，并且与张量并行（TP）、流水线并行（PP）和专家并行（EP）无缝协作。

### 为什么睡眠模式胜过快速权重加载器

即使权重加载快如闪电，每次冷启动仍要付出睡眠模式可以避免的隐性成本：

| 成本 | 说明 | 快速权重加载器 | 睡眠模式 |
| --- | --- | --- | --- |
| 1. 显存加载时间 | 将权重复制到 GPU | ✅ 已优化 | ✅ 保留 |
| 2. 内存分配器设置 | CUDA 分配器初始化 | ❌ 每次都要 | ✅ 保留 |
| 3. CUDA Graph 捕获 | 记录执行图 | ❌ 每次都要 | ✅ 保留 |
| 4. GPU 内核 JIT 编译 | DeepGEMM、FlashInfer、TorchInductor | ❌ 每次都要 | ✅ 保留（初始预热后） |
| 5. 缓存预热 | 首请求开销 | ❌ 每次都要 | ⚡ 快速重新预热 |

通过保持进程存活，睡眠模式保留了基础设施（第 2-4 项），避免了昂贵的重新初始化。这正是基准测试显示**睡眠模式下推理比冷启动快 61-88%** 的原因。

- 关于预热影响与 FP8 量化的消融实验

## 快速上手：使用睡眠模式

### 在线服务 API

启动两个开启睡眠模式的 vLLM 服务器：

```
# Terminal 1: Start Phi-3-vision
export VLLM_SERVER_DEV_MODE=1
vllm serve microsoft/Phi-3-vision-128k-instruct --enable-sleep-mode --port 8001

# Terminal 2: Start Qwen3-0.6B
export VLLM_SERVER_DEV_MODE=1
vllm serve Qwen/Qwen3-0.6B --enable-sleep-mode --port 8002
```

### 让模型休眠与唤醒

```
# Put Phi-3-vision to sleep (Level 2 - minimal RAM usage)
curl -X POST 'localhost:8001/sleep?level=2'

# Put Qwen3-0.6B to sleep (Level 2)
curl -X POST 'localhost:8002/sleep?level=2'

# Wake up Phi-3-vision for inference
curl -X POST 'localhost:8001/wake_up'
curl -X POST 'localhost:8001/collective_rpc' \
  -H 'Content-Type: application/json' \
  -d '{"method":"reload_weights"}'

# IMPORTANT: Reset prefix cache after waking (Level 2 only)
curl -X POST 'localhost:8001/reset_prefix_cache'

# Now run inference on Phi-3-vision...
# (your inference requests here)

# Put back to sleep when done
curl -X POST 'localhost:8001/sleep?level=2'

# Wake up Qwen3-0.6B
curl -X POST 'localhost:8002/wake_up'
# (Level 1 doesn't need reload_weights or reset_prefix_cache)

# Run inference on Qwen3-0.6B...
```

> **注意：** 对于 Level 2 睡眠，唤醒后必须调用 `reload_weights` 和 `reset_prefix_cache`。Level 1 睡眠则不需要这些额外步骤。

> **警告：** **安全性：** `/sleep`、`/wake_up`、`/collective_rpc` 和 `/reset_prefix_cache` 端点要求 `VLLM_SERVER_DEV_MODE=1`，且只应暴露在可信网络中。这些管理端点可能中断服务，适用于训练集群或后端应用等封闭环境。

#### 睡眠模式为何能提升推理速度

61-88% 的推理加速并非来自更快的权重加载，而是来自**保留了昂贵的基础设施**——冷启动必须从零重建这些东西。

**睡眠模式保留了什么：**

| 组件 | 是否保留？ | 冷启动必须付出 |
| --- | --- | --- |
| 内存分配器（CuMemAllocator） | ✅ 是 | ❌ 每次都要重新初始化 |
| CUDA Graph | ✅ 是 | ❌ 每次都要重新捕获 |
| 进程状态（Python、CUDA 上下文） | ✅ 是 | ❌ 每次都要重启 |
| GPU 内核 JIT 缓存 | ✅ 是（初始预热后） | ❌ 每次都要重新编译 |

**关键差异：**

- **不使用睡眠模式：** 卸载时进程死亡 → **你无法从预热中获益**

  - 必须重启 Python 进程和 CUDA 上下文
  - 必须重新初始化内存分配器
  - 必须重新捕获 CUDA Graph
  - 必须重新 JIT 编译内核（DeepGEMM、FlashInfer、TorchInductor）
  - **结果：** 首次推理**慢 4-7x**（见基准数据：唤醒 0.92s vs 冷启动 3.72s）
- **使用睡眠模式：** 进程保持存活 → **预热投入得到回报**

  - ✅ 初始预热后，分配器、执行图、进程状态和 JIT 内核全部保留
  - **结果：** 首次推理依然很快（约 1s），避免 3-4s 的冷启动惩罚

> **注意：** 具体时间因模型大小、GPU 世代和配置而显著不同。详细测量数据请参见[预热的影响](#impact-of-warm-up-on-sleep-mode)一节，其中显示无预热时会慢 5-7x。

## 睡眠等级：如何选择合适的模式

vLLM 睡眠模式提供两种等级，各有不同的权衡：

**Level 1（默认）：** 将模型权重卸载到 CPU 内存，丢弃 KV 缓存

- **唤醒最快**（小模型约 0.1-0.8s，大模型约 3-6s）
- **需要足够的 CPU 内存**来存放模型权重
- **最适用于：** CPU 内存充足、频繁切换模型的系统

**Level 2：** 丢弃模型权重和 KV 缓存，仅在 CPU 中保留少量缓冲区（rope 缩放张量等）

- **唤醒较慢**（小模型约 0.8-2.6s），因为需要从磁盘重新加载权重
- **CPU 内存占用极小**——只保留少量缓冲区
- **最适用于：** CPU 内存有限，或管理的模型很多、无法全部驻留内存的系统

- 由于权重重载，**Level 2 的唤醒比 Level 1 慢约 3x**（Qwen3-0.6B 为 0.85s vs 0.26s）
- 两种睡眠模式相比不睡眠都有**巨大改进**

#### 为什么 Level 2 仍比不睡眠模式更快

乍一看这似乎违反直觉：**Level 2 也要从 SSD 重新加载权重**（与「不睡眠模式」一样），那为什么整体上**快 23-45x**？

**答案：权重加载只是五项成本中的一项**

不使用睡眠模式重载模型时，你要付出以下全部成本：

| 成本 | Level 2 | 不睡眠模式 |
| --- | --- | --- |
| 1. 权重加载（SSD → 显存） | ❌ 必须付出 | ❌ 必须付出 |
| 2. 进程初始化 | ✅ **跳过** | ❌ 必须付出 |
| 3. 内存分配器设置 | ✅ **跳过** | ❌ 必须付出 |
| 4. CUDA Graph 捕获 | ✅ **跳过** | ❌ 必须付出 |
| 5. GPU 内核 JIT 编译 | ✅ **保留（已编译）** | ❌ 完整编译 + 预热 |

**Level 2 的策略：**

- 从 SSD 重载权重（与不睡眠相同）
- **其余全部保留：** 进程状态、分配器实例、CUDA Graph 和已编译的 JIT 内核均完好无损
- **无需重新编译：** 内核已在初始预热时编译完成并保持缓存
- **平均每次切换：约 2.6s**（见上文基准数据）

**不睡眠模式的现实：**

- 从 SSD 重载权重（与 Level 2 相同）
- **其余全部重建：** 进程重启 + 分配器初始化 + 执行图重新捕获
- **JIT 内核：** 完整编译 + 显式预热流程（`kernel_warmup()` + 空跑）
- **平均每次切换：约 48s**（见上文基准数据）

**基准数据证明了这一点：** 5 次模型切换：

- **Level 2：** 总计 124.6s（平均每次切换约 2.6s）
- **不睡眠：** 总计 357.1s（平均每次切换约 48s）

尽管两者都要从 SSD 重载权重，Level 2 整体上**快 2.9x**，因为它保留了昂贵的基础设施（进程状态、分配器、CUDA Graph），而不睡眠模式每次都要从零重建。

## 消融实验

### 预热对睡眠模式的影响

跳过预热阶段会影响性能吗？预热会在初始加载期间预编译 CUDA Graph，这可能耗时数秒。让我们对比有无预热的情况。

**模型 A：**Qwen3-0.6B | **模型 B：**Phi-3-vision-128k-instruct
GPU：A100（TP=1）| vLLM 0.11.0 | 睡眠等级：1 | 编译：`cudagraph_mode: FULL_AND_PIECEWISE`
对比有预热（预编译）与无预热（惰性编译）。悬停查看精确时间。

**关键发现：**

| 指标 | 有预热 | 无预热 | 差异 |
| --- | --- | --- | --- |
| **初始加载时间** | 108.7s（含 8.4s 预热） | 101.1s（无预热） | 初始多花 7.6s |
| **首次推理（A）** | 0.45s | 2.59s | 无预热时**慢 5.8x** |
| **首次推理（B）** | 0.93s | 6.61s | 无预热时**慢 7.1x** |
| **后续推理** | 平均 0.43s | 平均 0.41s | 无差异 |
| **总时间（5 次切换）** | 119.5s | 119.0s | 几乎相同 |

**洞察：**

- **预热只编译一次内核，惠及所有唤醒周期：** 有了初始预热，JIT 编译与 CUDA Graph 捕获在加载时只发生一次，并在后续所有休眠/唤醒周期中保留
- **没有预热，每次唤醒都要付出编译成本：** 5-7x 的减速出现在**每一次唤醒后**的首次推理上，而不是只有一次
- **已编译的内核在休眠/唤醒间得以保留：** 初始加载期间完成预热（8.4s）后，后续所有唤醒的首次推理都很快（0.45s、0.93s），证明内核一直保持在缓存中
- **极小的预热就足够：** 一次 1 token 的推理就足以触发完整的 JIT 编译与 CUDA Graph 捕获，因此预热成本很低
- **用初始加载时间换取一致的性能：** 8.4s 的预热成本只付一次，并分摊到所有模型切换中
- **建议：务必启用预热**——对于需要一致、快速推理的生产工作负载

- **FP8 唤醒操作更快**（快 13-33%），因为内存搬运量更少
- **FP8 提升较大模型的推理**（Phi-3-vision 快 30%），但对极小模型差异甚微
- **FP8 的初始加载耗时更长**，因为预热期间有量化开销

- 对于切换频繁的工作负载，FP8 更快的唤醒可以抵消更长的初始加载

## 决策指南：该用哪个睡眠等级？

### 以下情况使用睡眠等级 1：

- 你有足够的 CPU 内存来容纳所有模型权重
- 你需要尽可能快的唤醒时间（0.1-6s）
- 你非常频繁地切换模型（每几秒/几分钟一次）
- 推理延迟的一致性至关重要

### 以下情况使用睡眠等级 2：

- CPU 内存有限（无法容纳所有模型权重）
- 你在优化云成本（内存较小、价格更低的实例）
- 你要管理大量模型（10 个以上）

### 以下情况无需睡眠模式：

- 你只使用单个模型（无需切换）
- 模型切换极其罕见（每天/每周一次）
- 两个模型可以同时装进 GPU 显存

## 结论

vLLM 睡眠模式把多模型 GPU 服务从 30-100 秒的重载惩罚变成了亚秒级切换。基准数据不言自明：

- **模型切换快 18-200x**（取决于模型规模与硬件）
- 预热模型相比冷启动**推理快 61-88%**
- 完整工作负载**总时间节省 65-68%**
- **各种规模都有效：** 0.6B 到 235B 参数，大小 GPU 皆可

LLM 服务的未来是多模型。睡眠模式让这一未来在今天成为现实。
