# vLLM 携手 Novita AI：面向生产级外部 KV 缓存的 PegaFlow

> 原文：[vLLM x Novita AI: PegaFlow for Production-Grade External KV Cache](https://vllm.ai/blog/2026-05-18-pegaflow) · vLLM 博客

作者：Novita AI 与 vLLM 团队

[#KV缓存](https://vllm.ai/blog/tags/kv_cache)[#分离部署](https://vllm.ai/blog/tags/disaggregation)[#性能](https://vllm.ai/blog/tags/performance)[#生产服务](https://vllm.ai/blog/tags/production-serving)

**TL;DR：** 我们与 Novita AI 合作，将 [PegaFlow](https://github.com/novitalabs/pegaflow) 集成到 vLLM 中，作为 LLM 推理的外部 KV 缓存服务。它以独立的 Rust 进程实现，并通过外部 KV 连接器接口接入。它把 KV 缓存的生命周期从 vLLM worker 进程中移出，在本地实例与远程节点间汇集缓存，并将锁页主机内存、RDMA 可访问的远程内存和 SSD 组合成三级缓存层级。

在面向生产的评估中，这一设计实现了：

- 当 500 GiB 主机 KV 池已由外部缓存服务持有时，**vLLM 启动速度提升 2.15 倍**。
- 八个 Qwen3-8B 实例共享一个主机缓存（而非八个隔离缓存）时，**吞吐量提升 56%**。
- DeepSeek-V3.2 MLA 在 TP8 下，通过逻辑 KV 只存一份（而非每个 TP rank 各存一份），**吞吐量提升 72%**。
- 在每节点配备 8 x 400 Gbps 网卡的内部 RDMA 集群中，大规模前缀拉取的**平均远程读取吞吐量达 194 GB/s**。

核心思想很简单：KV 缓存应当是一项长期存在的服务资产，而不是绑定在单个推理进程上的临时状态。

对 vLLM 用户而言，重要之处在于这一集成通过现有的 `kv_transfer_config` 路径暴露。PegaFlow 可以作为外部缓存后端使用，无需修改 vLLM 源代码，也无需维护一个长期存在的 fork。

## 为什么 KV 缓存需要进程边界

KV 缓存是生产级 LLM 服务中最昂贵的运行时资产之一。它在每台主机上可占用数百 GiB，分配和预热都需要时间，而且其存续时间往往超过最初创建它的请求模式。

在传统的进程内设计中，这一资产与推理引擎进程紧密耦合。在引擎崩溃、滚动升级和模型切换时，这种耦合会变得非常痛苦。引擎重启时，主机 KV 池随之消失。当服务集群从一个模型部署切换到另一个时，可能需要重新分配并预热数百 GiB 的锁页内存，实例才能重新服务流量。

PegaFlow 通过把 KV 缓存运行时移入每台机器上的独立守护进程来解决这一问题。PegaFlow 服务器持有主机 KV 池、SSD 缓存、拓扑元数据、RDMA 资源、索引状态和后台任务。vLLM worker 在数据路径上通过 CUDA IPC、在本地控制路径上通过 gRPC 连接本地 PegaFlow 进程。

![Figure 1: PegaFlow runs as an external KV cache service next to vLLM. vLLM workers communicate with the local PegaFlow server through CUDA IPC and gRPC, while PegaFlow manages pinned memory, SSD cache, RDMA transfer, and optional cross-node indexing through the MetaServer.](https://vllm.ai/blog-assets/figures/2026-05-18-pegaflow/architecture.png)

图 1：PegaFlow 作为外部 KV 缓存服务运行在 vLLM 旁边。vLLM worker 通过 CUDA IPC 和 gRPC 与本地 PegaFlow 服务器通信，而 PegaFlow 管理锁页内存、SSD 缓存、RDMA 传输，并可通过 MetaServer 提供可选的跨节点索引。

这一设计围绕一个生产需求构建：一台缓存服务器应能服务于同一主机上的多个引擎和多个模型。不同模型、不同张量并行配置和不同引擎版本可以在一个 PegaFlow 进程中共存，并以命名空间隔离，同时共享同一个内存池、SSD 容量和跨节点网络带宽。

由此形成的故障域更加清晰。vLLM 进程可以崩溃、升级或切换模型，而缓存服务保持存活。反过来，缓存层的问题也不必拖垮推理引擎进程。

## 由外部持有缓存，实现更快的重启

为了隔离主机 KV 池归属对启动路径的影响，我们测量了以 TP8 运行 Qwen3-8B 的 8 x RTX 5090 环境。实验使用 dummy weights 和 eager 模式以消除权重加载与编译的影响，只关注约 500 GiB 主机 KV 池带来的效应。

在嵌入式 KV 缓存设计下，500 GiB 池由 vLLM worker 持有，vLLM 需要 **71.4 秒**才能达到就绪状态。

使用 PegaFlow 时，500 GiB 池由独立的 PegaFlow 服务器预先持有。服务器就绪后，vLLM 只用 **33.2 秒**即达到就绪状态。在这一环境中，vLLM 启动路径快了 **2.15 倍**，原因在于把长期存在的主机缓存分配与推理进程生命周期解耦。

![Figure 2: vLLM startup time with a 500 GiB host KV pool. Keeping the pool in the external PegaFlow server cuts the vLLM startup path from 71.4 seconds to 33.2 seconds in this setup.](https://vllm.ai/blog-assets/figures/2026-05-18-pegaflow/startup-time.svg)

图 2：配备 500 GiB 主机 KV 池时的 vLLM 启动时间。在该环境中，把池保留在外部 PegaFlow 服务器中，可将 vLLM 启动路径从 71.4 秒缩短到 33.2 秒。

## Rust 数据路径与尾延迟稳定性

把 KV 缓存移入外部进程，最初动机是生命周期管理、共享和 CPU 资源隔离。用 Rust 实现该进程还带来了一项重要的运维收益：延迟稳定性。

PegaFlow 的数据平面避免了 Python 解释器开销、GIL 争用和 stop-the-world 垃圾回收。这一点很重要，因为生产级缓存服务不只做关键路径上的字节搬运，还要运行统计收集、索引上传、预取、健康检查、指标上报、驱逐和 SSD 缓存管理等后台任务。

在 PegaFlow 中，这些任务都运行在同一个独立的 Rust 服务内，不与 vLLM 共享解释器运行时。这为系统运行控制平面和维护工作留出了更多空间，而不会干扰数据平面路径。

![Figure 3: Tail and average latency comparison under baseline and GIL-load conditions. The Rust Tokio path is much less affected by background load than the Python uvloop and Python ZMQ baselines.](https://vllm.ai/blog-assets/figures/2026-05-18-pegaflow/tail-latency.png)

图 3：基线条件与 GIL 负载条件下的尾延迟与平均延迟对比。Rust Tokio 路径受后台负载的影响远小于 Python uvloop 和 Python ZMQ 基线。

## 跨实例与跨节点汇集缓存

在生产部署中，相同的逻辑 KV 内容常常被复制多次，因为进程、模型或节点边界使各缓存彼此不可见。

这种模式出现在几种常见部署中：

- **一台主机上的多个小模型实例。** 在 8 GPU 主机上运行 8 个 Qwen3-8B 实例，可能把同一个系统提示词存储 8 次。
- **宽专家并行部署。** 同一台机器上的多个数据并行副本即使运行在同一物理主机上，也各自维护独立的前缀缓存。
- **张量并行下的 MLA。** 对于 DeepSeek-V3.2 这类模型，逻辑潜变量 KV 本可只存一份，但进程内 TP8 部署可能在每个 rank 上物理各存一份。
- **跨节点调度。** 一个请求可能在节点 A 上有缓存命中，但如果节点 A 过载、请求被路由到节点 B，该前缀可能需要从头重算。

PegaFlow 把这些彼此隔离的缓存碎片变成一个共享缓存池。

在单台主机上，所有本地实例连接到同一个 PegaFlow 服务器并共享一个 CPU KV 池。对于多实例小模型服务、WideEP 数据并行副本和 TP worker，相同的块只需物理存储一次，即可被多个引擎复用。

跨主机时，PegaFlow MetaServer 维护一个近似全局索引。节点可以通过单边 RDMA READ 获取远程 KV 块，连接建立之后远程侧 CPU 零参与。因此远程命中可以像本地命中一样被使用，避免昂贵的预填充重算。

## 结果

以下实验保持缓存预算不变，只改变这份缓存在 vLLM 进程、张量并行 rank 或节点之间的可见范围。

### 单节点多实例共享

我们在一台主机上以相同的 500 GiB 缓存预算评估了 8 个 Qwen3-8B 实例。

| 配置 | 缓存布局 | 吞吐量 | 平均 TTFT | 请求命中率 |
| --- | --- | --- | --- | --- |
| PegaFlow | 500 GiB 共享池 | 11.97 req/s | 5.26 s | 52.35% |
| 进程内 | 8 x 62.5 GiB 隔离池 | 7.68 req/s | 8.22 s | 11.77% |

重点不在于系统用了更多内存——事实并非如此。同样的 500 GiB 预算变得更有用，因为请求可以从一个共享池而不是八个隔离池中获取数据。吞吐量提升 **56%**，平均 TTFT 下降 **36%**，请求命中率提升 **4.4 倍**。

### MLA 逻辑 KV 去重

我们还在 500 GiB 缓存预算下评估了 TP8 的 DeepSeek-V3.2 MLA。

| 配置 | 缓存布局 | 吞吐量 | 平均 TTFT | 请求命中率 |
| --- | --- | --- | --- | --- |
| PegaFlow | 逻辑 KV 只存一份 | 1.81 req/s | 35.66 s | 97.23% |
| 进程内 | 每个 TP rank 各存一份 KV | 1.05 req/s | 60.88 s | 65.18% |

对于这一工作负载，避免跨 TP rank 的重复存储实际上扩大了可用缓存容量。吞吐量提升 **72%**，平均 TTFT 下降 **41%**，请求命中率接近该轨迹的实际上限。

![Figure 4: Summary of the two fixed-budget local sharing experiments. In both cases, PegaFlow improves effective cache capacity by making the same KV budget visible across isolation boundaries.](https://vllm.ai/blog-assets/figures/2026-05-18-pegaflow/results-overview.svg)

图 4：两个固定预算本地共享实验的总结。在两种情况下，PegaFlow 都通过让相同的 KV 预算跨隔离边界可见来提升有效缓存容量。

### 跨节点 RDMA 共享

在一个每节点配备 8 x 400 Gbps RDMA 网卡的内部生产推理集群中，我们对数千次近期在线远程读取进行了采样。对于至少 1 GiB 的大规模前缀拉取，PegaFlow 在生产流量下保持 **194 GB/s** 的平均有效吞吐量，P99 为 **250 GB/s**，峰值达 **261.6 GB/s**。

以这一传输速率，一个 24 GiB 的 KV 缓存段可以在约 100 毫秒内从远程节点拉取。这可以替代原本要消耗数秒 GPU 时间的预填充计算。在实践中，这正是远程命中的价值所在：它们不只是"比未命中好"，而是可以快到如同服务路径的一部分。

![Figure 5: Effective throughput for large remote KV cache reads in an internal production cluster. At the measured average throughput, a 24 GiB remote KV segment can be fetched in roughly 100 ms.](https://vllm.ai/blog-assets/figures/2026-05-18-pegaflow/rdma-throughput.svg)

图 5：内部生产集群中大规模远程 KV 缓存读取的有效吞吐量。按测得的平均吞吐量计算，一个 24 GiB 的远程 KV 段可在约 100 毫秒内取回。

## 三级缓存层级

汇集让缓存容量更有用，但主机内存仍然有限。重用距离较长的前缀可能在下次使用前被驱逐，而简单的 LRU 可能被扫描型流量严重扰乱——这类流量会让大量一次性块流经系统。

PegaFlow 用三级缓存层级来解决这一问题。热本地块保留在锁页 DRAM 中，远程命中可通过 RDMA 获取，较冷的可用复用块可以溢出到本地 SSD：

| 层级 | 介质 | 访问路径 | 典型角色 |
| --- | --- | --- | --- |
| L1 | 本地锁页 DRAM | 本地内存 | 快速本地 KV 复用 |
| L2 | 远程 DRAM | RDMA READ | 跨节点缓存共享 |
| L3 | 本地 SSD | io\_uring | 大容量溢出 |

SSD 缓存用 Rust 基于 `io_uring` 实现。在内部测试中，单块 SSD 的峰值读取吞吐量约为 **6.9 GB/s**。PegaFlow 把每块盘的在线稳态吞吐量保持在约 **6.5-6.6 GB/s**，用大约 5% 的峰值带宽换取更稳定的尾延迟。跨多块盘做 RAID0 时，总吞吐量近似线性扩展。

对于扫描密集型工作负载或缓存预算较小的主机，PegaFlow 可以启用 TinyLFU 准入策略。该策略只接纳可能被复用的块，保护缓存免受一次性流量的影响。

TinyLFU 默认关闭，因为最佳准入策略取决于工作负载形态。不过，在若干内部轨迹中，当缓存较小或扫描压力较高时，它显著优于 LRU。

![Figure 6: Cache-policy comparison under small cache sizes. Scan-heavy traces can make simple recency-based policies ineffective, while admission-aware policies such as TinyLFU can protect the cache from one-time blocks.](https://vllm.ai/blog-assets/figures/2026-05-18-pegaflow/cache-policy-comparison.png)

图 6：小缓存容量下的缓存策略对比。扫描密集型轨迹会使基于新近度的简单策略失效，而 TinyLFU 这类具备准入感知的策略可以保护缓存免受一次性块的影响。

## 衡量与理论命中率上限的距离

仅看在线命中率可能有误导性。3% 的命中率对于几乎无复用的工作负载来说可能已经不错；而 90% 的命中率若远低于该工作负载的理论上限，则仍有可观空间。

对运维人员来说，有用的问题不只是"命中率是多少？"，而是"我们距离这个工作负载合理可达到的最佳命中率还有多远？"

PegaFlow 使用 HyperLogLog 在线估计理论命中率上限：

```
r* = (N - U) / N

```

其中，`N` 是窗口内块请求的总数，`U` 是首次出现的唯一块数量。HyperLogLog 让这一估计非常廉价：24 小时窗口的内存占用不到 1 MiB，误差约 0.8%。

PegaFlow 导出滚动的 HLL 窗口，默认为 15 分钟、1 小时和 24 小时。把实测命中率与理论上限放在同一个仪表盘上，运维人员可以区分三种情况：

- 缓存已接近该工作负载的上限，增加容量可能帮助不大。
- 实测命中率远低于上限，说明在容量、准入、预取或跨节点发现方面还有改进空间。
- 理论上限本身就很低，说明该工作负载的复用有限，瓶颈主要不在缓存实现。

## 通过外部连接器与 vLLM 集成

外部 KV 缓存系统通常需要对调度器、块管理器或注意力内核做侵入式修改。PegaFlow 则通过 vLLM 的外部 KV 连接器机制进行集成。

连接器通过 `kv_transfer_config` 配置，外部包可通过 `kv_connector_module_path` 动态加载。这使 PegaFlow 能够在运行时接管关键的 KV 缓存操作，而无需修改 vLLM 源代码或维护长期 fork。

从 vLLM 的视角看，PegaFlow 不是服务引擎的替代品。它是通过 KV 传输接口接入的外部缓存后端，而 vLLM 继续负责调度、模型执行、批处理和 OpenAI 兼容服务路径。

这一边界对两个项目都有益。PegaFlow 可以独立迭代其 Rust 数据平面、SSD 缓存、RDMA 路径、索引和连接器逻辑。vLLM 则可以继续改进核心服务引擎，同时为外部缓存系统提供稳定的连接器契约。

## 快速开始

安装与你 CUDA 版本匹配的包：

```
uv pip install pegaflow-llm        # CUDA 12
uv pip install pegaflow-llm-cu13   # CUDA 13
```

启动一个带锁页主机内存和 SSD 缓存的单节点 PegaFlow 服务器：

```
pegaflow-server \
  --pool-size 30gb \
  --ssd-cache-path <ssd-cache-file-path> \
  --ssd-cache-capacity 512gb
```

对于在线部署，我们建议加上 `--use-hugepages`。大页应提前预留。它们可以加速 CPU 锁页内存分配，并通过降低注册与传输期间的地址翻译开销来减轻 RDMA MTT 压力。

多节点部署时，先启动 MetaServer，然后在每个节点上以 RDMA 配置启动一个 PegaFlow 服务器。启用 P2P 时，每个 PegaFlow 服务器的 `--addr` 必须是可路由的 IP 地址，不能是 `0.0.0.0` 或 `127.0.0.1`，因为其他节点要用它进行 gRPC 握手和块查询。

```
pegaflow-metaserver --addr 0.0.0.0:50056
```

```
pegaflow-server \
  --addr this-node:50055 \
  --pool-size 30gb \
  --ssd-cache-path <ssd-cache-file-path> \
  --nics mlx5_0 mlx5_1 \
  --metaserver-addr http://metaserver-host:50056
```

无需修改 vLLM 源代码即可连接 vLLM。本文示例使用 `vllm>=0.20.0`：

```
vllm serve <model> \
  --kv-transfer-config '{
    "kv_connector": "PegaKVConnector",
    "kv_role": "kv_both",
    "kv_connector_module_path": "pegaflow.connector"
  }'
```

`PEGAFLOW_HOST` 和 `PEGAFLOW_PORT` 环境变量把连接器指向 PegaFlow 服务。默认值为 `http://127.0.0.1` 和 `50055`。

## 公开参考基准

PegaFlow 仓库还包含一个公开的 KV 缓存基准：在 H800 上以 Llama-3.1-8B 运行，使用 8 个提示、10K token 预填充、1 token 解码、4.0 req/s。在该环境中，热缓存路径把平均 TTFT 从 **572.5 ms** 降至 **61.5 ms**，P99 TTFT 从 **1113.7 ms** 降至 **77.0 ms**。
