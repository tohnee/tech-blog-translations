# token 级真相：面向生产环境 LLM 的实时幻觉检测

> 原文：[Token-Level Truth: Real-Time Hallucination Detection for Production LLMs](https://vllm.ai/blog/2025-12-14-halugate) · vLLM 博客

vLLM Semantic Router 团队

[#生态](https://vllm.ai/blog/tags/ecosystem)

你的 LLM 刚刚调用了一个工具，拿到了准确的数据，但答案还是错了。欢迎来到**外在幻觉（extrinsic hallucination）**的世界——模型自信满满地无视了摆在眼前的真实依据。

在[信号决策架构](https://blog.vllm.ai/2025/11/19/signal-decision.html)的基础上，我们推出 **HaluGate**——一条条件触发的、token 级的幻觉检测流水线，能在缺乏依据的说法*到达用户之前*将其捕获。不需要 LLM 评审（LLM-as-judge），不需要 Python 运行时，只在交付节点进行快速、可解释的校验。

## 问题：幻觉阻碍生产部署

幻觉已成为 LLM 走向生产环境的最大障碍。在各行各业——**法律**（捏造的判例引用）、**医疗**（错误的药物相互作用）、**金融**（凭空编造的金融数据）、**客服**（并不存在的政策）——模式如出一辙：AI 生成的内容听起来头头是道、貌似权威，却在推敲之下不堪一击。

挑战并不在于那些显而易见的胡言乱语，而在于*藏在本大体准确的回答中的细微捏造*——这类错误需要领域专业知识或外部核验才能发现。对企业而言，这种不确定性让 LLM 部署从资产变成了负债。

## 场景：工具正常工作，模型却在出错

让我们把问题具体化。看一个典型的函数调用交互：

> **用户**：「埃菲尔铁塔是什么时候建成的？」
>
> **工具调用**：`get_landmark_info("Eiffel Tower")`
>
> **工具响应**：`{"name": "Eiffel Tower", "built": "1887-1889", "height": "330 meters", "location": "Paris, France"}`
>
> **LLM 响应**：「埃菲尔铁塔**建于 1950 年**，位于法国巴黎，高 **500 米**。」

工具返回了正确的数据。模型的回答里也包含事实。但其中两条「事实」是编造的——是与所提供上下文直接矛盾的**外在幻觉**。

这种失效模式尤其隐蔽：

- **用户会相信它**，因为他们看到工具被调用了
- **传统过滤器抓不住它**，因为其中并不含有毒或有害内容
- **评估代价高昂**，如果你依赖另一个 LLM 来做判断

如果我们能以毫秒级延迟、实时、自动化地检测这些错误呢？

## 洞察：函数调用就是真实依据

这里有一个关键认识：**现代函数调用 API 本身已经提供了接地（grounding）上下文**。当用户提出事实性问题时，模型会调用工具——数据库查询、API 调用、文档检索。这些工具结果在语义上等价于 RAG 中检索到的文档。

![](https://vllm.ai/blog-assets/figures/semantic-router/halugate-0.png)

我们不需要另建检索基础设施，也不需要调用 GPT-4 来当裁判。我们从既有的 API 流程中提取三个组成部分：

| 组成部分 | 来源 | 用途 |
| --- | --- | --- |
| **上下文（Context）** | 工具消息内容 | 用于核验的真实依据 |
| **问题（Question）** | 用户消息 | 意图理解 |
| **回答（Answer）** | 助手响应 | 待核验的主张 |

于是问题变成：**回答是否忠实于上下文？**

## 为什么不直接用 LLM 评审？

显而易见的方案——调用另一个 LLM 来核验——在生产环境中存在根本性问题：

| 方案 | 延迟 | 成本 | 可解释性 |
| --- | --- | --- | --- |
| GPT-4 评审 | 2-5 秒 | $0.01-0.03/请求 | 低（黑盒） |
| 本地 LLM 评审 | 500ms-2s | GPU 算力 | 低 |
| **HaluGate** | **76-162ms** | **仅 CPU** | **高（token 级 + NLI）** |

LLM 评审还存在以下问题：

- **位置偏差**：倾向于偏好某些位置的答案
- **冗长偏差**：无论准确性如何，更长的答案评分更高
- **自我偏好**：模型偏好与自己风格相似的输出
- **不一致性**：相同输入可能得到不同判断

我们需要更快、更便宜、更可解释的东西。

## HaluGate：两阶段检测流水线

HaluGate 实现了一条**条件触发的两阶段流水线**，在效率与精度之间取得平衡：

![](https://vllm.ai/blog-assets/figures/semantic-router/halugate-1.png)

### 第一阶段：HaluGate Sentinel（提示分类）

并非每个查询都需要幻觉检测。看看这些提示：

| 提示 | 需要事实核验吗？ | 原因 |
| --- | --- | --- |
| 「爱因斯坦是什么时候出生的？」 | ✅ 是 | 可验证的事实 |
| 「写一首关于秋天的诗」 | ❌ 否 | 创作型任务 |
| 「调试这段 Python 代码」 | ❌ 否 | 技术协助 |
| 「你对 AI 有什么看法？」 | ❌ 否 | 观点征询 |
| 「地球是圆的吗？」 | ✅ 是 | 事实性主张 |

对创意写作或代码审查运行 token 级检测是一种浪费——还可能产生误报（「你的诗包含缺乏依据的主张！」）。

**预分类为何重要**：token 级检测的计算量随上下文长度线性增长。对于 4K token 的 RAG 上下文，检测耗时约 125ms；对于 16K token，约 365ms。在生产负载中约 35% 的查询是非事实性的，预分类可带来 **72.2% 的效率提升**——对创作、编程和观点类查询完全跳过昂贵的检测。

[HaluGate Sentinel](https://huggingface.co/llm-semantic-router/halugate-sentinel) 是一个基于 ModernBERT 的分类器，它只回答一个问题：*这条提示是否需要事实核验？*

![](https://vllm.ai/blog-assets/figures/semantic-router/halugate-2.png)

该模型在精心策划的混合数据上训练：

**需要事实核验（正类）**：

- **问答**：SQuAD、TriviaQA、Natural Questions、HotpotQA
- **真实性**：TruthfulQA（常见误解）
- **幻觉基准**：HaluEval、FactCHD
- **信息寻求型对话**：FaithDial、CoQA
- **RAG 数据集**：neural-bridge/rag-dataset-12000

**无需事实核验（负类）**：

- **创意写作**：WritingPrompts、故事生成
- **代码**：CodeSearchNet docstring、编程任务
- **观点/指令**：Dolly non-factual、Alpaca creative

这一二分类任务实现了 **96.4% 的验证集准确率**，并通过原生 Rust/Candle 集成达到**约 12ms 的推理延迟**。

### 第二阶段：token 级检测 + NLI 解释

对于被判定为事实寻询类的提示，我们运行一个双模型检测流水线。

#### token 级幻觉检测

与输出单一「幻觉/非幻觉」标签的句子级分类器不同，**token 级检测**能精确识别*哪些 token*缺乏上下文支持。

![](https://vllm.ai/blog-assets/figures/semantic-router/halugate-3.png)

模型架构：

```
Input: [CLS] context [SEP] question [SEP] answer [SEP]
                                          ↓
                              ModernBERT Encoder
                                          ↓
                    Token Classification Head (Binary per token)
                                          ↓
              Label: 0 = Supported, 1 = Hallucinated (for answer tokens only)
```

关键设计决策：

- **仅对回答分类**：我们只对回答片段中的 token 分类，而不处理上下文或问题
- **片段合并**：连续的幻觉 token 会被合并为片段（span）以便阅读
- **置信度阈值**：可配置的阈值（默认 0.8），用于平衡精确率/召回率

#### NLI 解释层

知道*某处*是幻觉还不够——我们还需要知道*为什么*。NLI（自然语言推理）模型针对上下文对每个被检出的片段进行分类：

![](https://vllm.ai/blog-assets/figures/semantic-router/halugate-4.png)

| NLI 标签 | 含义 | 严重度 | 动作 |
| --- | --- | --- | --- |
| **CONTRADICTION** | 主张与上下文冲突 | 4（高） | 标记为错误 |
| **NEUTRAL** | 主张缺乏上下文支持 | 2（中） | 标记为无法核验 |
| **ENTAILMENT** | 上下文支持该主张 | 0 | 过滤误报 |

**为什么这种组合有效**：单独的 token 级检测在幻觉类上只能达到 59% 的 F1——近一半的幻觉被漏掉，且三分之一的标记是误报。我们曾尝试训练一个统一的 5 分类模型（SUPPORTED/CONTRADICTION/FABRICATION 等），但它只达到 21.7% 的 F1——token 级分类根本无法区分*为什么*有问题。两阶段方法把一个平庸的检测器变成了可落地的系统：LettuceDetect 提供召回率（抓住潜在问题），NLI 提供精确率（过滤误报）和可解释性（归类*每个片段为什么*有问题）。

## 与信号决策架构的集成

HaluGate 并非孤立运行——它作为一种新的信号类型和插件，与我们的[信号决策架构](https://blog.vllm.ai/2025/11/19/signal-decision.html)深度集成。

### `fact_check` 作为信号类型

正如我们有关键词、嵌入和领域信号一样，`fact_check` 现在是一等信号类型：

![](https://vllm.ai/blog-assets/figures/semantic-router/halugate-5.png)

这使得决策可以依据查询是否为事实寻询而进行条件触发：

> **注意**：即使是前沿模型，其幻觉表现在不同版本之间也存在差异。例如，[GPT-5.2 的系统卡](https://cdn.openai.com/pdf/3a4153c8-c748-4b71-8e31-aecbde944f8d/oai_5_2_system-card.pdf)显示其与先前版本相比存在可测量的幻觉差异，这凸显了无论模型多么先进，持续核验的重要性。

```
decisions:
  - name: "factual-query-with-verification"
    priority: 100
    rules:
      operator: "AND"
      conditions:
        - type: "fact_check"
          name: "needs_fact_check"
        - type: "domain"
          name: "general"
    plugins:
      - type: "hallucination"
        configuration:
          enabled: true
          use_nli: true
          hallucination_action: "header"
```

### 请求-响应上下文传递

一个关键挑战：分类发生在**请求时**，而检测发生在**响应时**。我们需要让状态跨越这一边界传递。

![](https://vllm.ai/blog-assets/figures/semantic-router/halugate-6.png)

`RequestContext` 结构携带所有必要的状态：

```
RequestContext:
  # Classification results (set at request time)
  FactCheckNeeded: true
  FactCheckConfidence: 0.87

  # Tool context (extracted at request time)
  HasToolsForFactCheck: true
  ToolResultsContext: "Built 1887-1889, 330 meters..."
  UserContent: "When was the Eiffel Tower built?"

  # Detection results (set at response time)
  HallucinationDetected: true
  HallucinationSpans: ["1950", "500 meters"]
  HallucinationConfidence: 0.92
```

### `hallucination` 插件

幻觉插件按决策（per-decision）配置，支持细粒度控制：

```
plugins:
  - type: "hallucination"
    configuration:
      enabled: true
      use_nli: true  # Enable NLI explanations

      # Action when hallucination detected
      hallucination_action: "header"  # "header" | "body" | "block" | "none"

      # Action when fact-check needed but no tool context
      unverified_factual_action: "header"

      # Include detailed info in response
      include_hallucination_details: true
```

| 动作 | 行为 |
| --- | --- |
| `header` | 添加警告响应头，放行响应 |
| `body` | 向响应体注入警告 |
| `block` | 返回错误响应，不转发 LLM 输出 |
| `none` | 仅记录日志，不对用户可见 |

## 响应头：可行动的透明度

检测结果通过 HTTP 响应头传递，使下游系统能够实施自定义策略：

```
HTTP/1.1 200 OK
Content-Type: application/json
x-vsr-fact-check-needed: true
x-vsr-hallucination-detected: true
x-vsr-hallucination-spans: 1950; 500 meters
x-vsr-nli-contradictions: 2
x-vsr-max-severity: 4
```

对于未核验的事实性响应（当工具不可用时）：

```
HTTP/1.1 200 OK
x-vsr-fact-check-needed: true
x-vsr-unverified-factual-response: true
x-vsr-verification-context-missing: true
```

这些响应头可用于：

- **UI 免责声明**：在置信度低时向用户显示警告
- **人工审核队列**：将被标记的响应路由至人工审核
- **审计日志**：为合规跟踪未核验的主张
- **条件阻断**：阻断高严重度的矛盾

## 模型架构深入解析

来看看驱动 HaluGate 的三个模型：

![](https://vllm.ai/blog-assets/figures/semantic-router/halugate-8.png)

### HaluGate Sentinel：二分类提示分类

**架构**：ModernBERT-base + LoRA 适配器 + 二分类头

**训练**：

- **基础模型**：`answerdotai/ModernBERT-base`
- **微调**：LoRA（rank=16, alpha=32, dropout=0.1）
- **训练数据**：来自 14 个数据集的 50,000 个样本
- **损失**：带类别权重的 CrossEntropy（处理类别不平衡）
- **优化**：AdamW，lr=2e-5，3 个 epoch

**推理**：

- **输入**：原始提示文本
- **输出**：(class\_id, confidence)
- **延迟**：CPU 上约 12ms

LoRA 方法让我们得以高效微调，同时保留预训练知识。训练期间只有 2.2% 的参数（1.49 亿参数中的 340 万）被更新。

### HaluGate Detector：token 级二分类

**架构**：ModernBERT-base + token 分类头

**输入格式**：

```
[CLS] The Eiffel Tower was built in 1887-1889 and is 330 meters tall.
[SEP] When was the Eiffel Tower built?
[SEP] The Eiffel Tower was built in 1950 and is 500 meters tall. [SEP]
      ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
                    Answer tokens (classification targets)
```

**输出**：每个回答 token 的二分类标签（0=有支持，1=幻觉）

**后处理**：

1. 将预测过滤至仅回答片段
2. 应用置信度阈值（默认：0.8）
3. 将连续的幻觉 token 合并为片段
4. 返回带置信度分数的片段

### HaluGate Explainer：三分类 NLI

**架构**：在 NLI 上微调的 ModernBERT-base

**输入格式**：

```
[CLS] The Eiffel Tower was built in 1887-1889. [SEP] built in 1950 [SEP]
      ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^       ^^^^^^^^^^^^^^^
                    Premise (context)                Hypothesis (span)
```

**输出**：带置信度的三分类：

- **ENTAILMENT**（0）：上下文支持该主张
- **NEUTRAL**（1）：无法由上下文判定
- **CONTRADICTION**（2）：上下文与主张冲突

**严重度映射**：

| NLI 标签 | 严重度分数 | 解读 |
| --- | --- | --- |
| ENTAILMENT | 0 | 很可能是误报——过滤掉 |
| NEUTRAL | 2 | 主张无法核验 |
| CONTRADICTION | 4 | 直接的事实错误 |

## 为什么原生 Rust/Candle 很重要

这三个模型都通过 **Candle**（Hugging Face 的 Rust 机器学习框架）原生运行，并通过 CGO 绑定与 Go 互操作：

![](https://vllm.ai/blog-assets/figures/semantic-router/halugate-9.png)

这种方式的优点：

| 维度 | Python（PyTorch） | 原生（Candle） |
| --- | --- | --- |
| **冷启动** | 5-10s | <500ms |
| **内存** | 每模型 2-4GB | 每模型 500MB-1GB |
| **延迟** | +50-100ms 开销 | 近乎零开销 |
| **部署** | 需要 Python 运行时 | 单个二进制文件 |
| **扩展** | GIL 争用 | 真正的并行 |

这消除了对独立 Python 服务、sidecar 或模型服务器的需求——一切都在进程内运行。

### 延迟分解

以下是生产流水线中各组件的实测延迟：

| 组件 | P50 | P99 | 说明 |
| --- | --- | --- | --- |
| 事实核验分类器 | 12ms | 28ms | ModernBERT 推理 |
| 工具上下文提取 | 1ms | 3ms | JSON 解析 |
| 幻觉检测器 | 45ms | 89ms | token 分类 |
| NLI 解释器 | 18ms | 42ms | 逐片段分类 |
| **总开销** | **76ms** | **162ms** | 运行检测时 |

总开销（76-162ms）与典型的 LLM 生成时间（5-30 秒）相比可以忽略不计，使 HaluGate 适合同步请求处理。

## 配置参考

幻觉缓解的完整配置：

```
# Model configuration
hallucination_mitigation:
  # Stage 1: Prompt classification
  fact_check_model:
    model_id: "models/halugate-sentinel"
    threshold: 0.6  # Confidence threshold for FACT_CHECK_NEEDED
    use_cpu: true

  # Stage 2a: Token-level detection
  hallucination_model:
    model_id: "models/halugate-detector"
    threshold: 0.8  # Token confidence threshold
    use_cpu: true

  # Stage 2b: NLI explanation
  nli_model:
    model_id: "models/halugate-explainer"
    threshold: 0.9  # NLI confidence threshold
    use_cpu: true

# Signal rules for fact-check classification
fact_check_rules:
  - name: needs_fact_check
    description: "Query contains factual claims that should be verified"
  - name: no_fact_check_needed
    description: "Query is creative, code-related, or opinion-based"

# Decision with hallucination plugin
decisions:
  - name: "verified-factual"
    priority: 100
    rules:
      operator: "AND"
      conditions:
        - type: "fact_check"
          name: "needs_fact_check"
    plugins:
      - type: "hallucination"
        configuration:
          enabled: true
          use_nli: true
          hallucination_action: "header"
          unverified_factual_action: "header"
          include_hallucination_details: true
```

## 超越生产：作为评估框架的 HaluGate

虽然 HaluGate 是为实时生产用途设计的，同一条流水线也可以支撑**离线模型评估**。我们不是拦截实时请求，而是将基准数据集送入检测流水线，系统地测量各模型的幻觉率。

![](https://vllm.ai/blog-assets/figures/semantic-router/halugate-10.png)

### 评估工作流

评估框架将 HaluGate 用作幻觉评分器：

1. **加载数据集**：使用现有的问答/RAG 基准（TriviaQA、Natural Questions、HotpotQA），或带有上下文-问题对的企业自定义数据集
2. **生成响应**：让被测模型基于给定上下文回答每条查询
3. **检测幻觉**：将（上下文，问题，响应）三元组送入 HaluGate Detector
4. **归类严重度**：使用 HaluGate Explainer 对每个被标记的片段进行分类
5. **汇总指标**：计算幻觉率、矛盾比例以及按类别的细分数据

## 局限与适用范围

HaluGate 专门针对**外在幻觉**——即工具/RAG 上下文可为核验提供依据的场景。它存在已知局限：

### HaluGate 无法检测的情况

| 局限 | 示例 | 原因 |
| --- | --- | --- |
| **内在幻觉** | 模型说「爱因斯坦出生于 1900 年」，而没有任何工具调用 | 没有可供核验的上下文 |
| **无上下文场景** | 用户提出事实性问题，但未定义工具 | 缺少真实依据 |

### 透明的降级

对于被判定为事实寻询但缺少工具上下文的请求，我们会显式地将响应标记为「未核验的事实性内容」，而不是静默放行：

```
x-vsr-fact-check-needed: true
x-vsr-unverified-factual-response: true
x-vsr-verification-context-missing: true
```

这种透明度让下游系统能够恰当地处理不确定性。

## 结语

HaluGate 为生产级 LLM 部署带来了有原则的幻觉检测：

- **条件触发核验**：跳过非事实性查询，核验事实性查询
- **token 级精度**：确切知道哪些主张缺乏支持
- **可解释的结果**：NLI 分类告诉你问题*出在哪里*
- **零延迟集成**：原生 Rust 推理，无需 Python sidecar
- **可行动的透明度**：响应头支持下游策略执行

下一次当你的 LLM 调用了工具、拿到了准确数据、答案却依然出错时——HaluGate 会在你的用户察觉之前抓住它。
