# 在 AMD GPU 上探索 vLLM 中的投机解码

> 原文：[Exploring Speculative Decoding in vLLM on AMD GPUs](https://vllm.ai/blog/2026-08-23-speculative-decoding-amd-gpus) · vLLM 博客

作者：AMD 与 Embedded LLM

[#投机解码](https://vllm.ai/blog/tags/speculative-decoding)[#AMD](https://vllm.ai/blog/tags/amd)

**TL;DR：** 投机解码使 vLLM 能够在单次目标模型前向传播中验证多个草稿 token。在我们的实验中，它对输出 token 吞吐量的影响因起草方法与提议长度的不同而有所差异，同时也取决于模型家族、草稿检查点、工作负载与接受行为。

---

## 引言

大型语言模型支持广泛的应用，但要以大规模提供它们的服务则需要细致的优化。标准自回归解码是大多数 LLM 服务系统所采用的基线：模型生成一个 token，将其追加到序列中，然后使用更新后的序列生成下一个 token。这一过程简单可靠，但由于输出 token 必须以严格的从左到右顺序产生，服务循环每次仍然只能推进一个已提交的 token。

投机解码 [[1]](#ref-1) 在这一基线之上构建了「起草—验证」机制。一个轻量级的草稿组件提出候选的未来 token，目标模型在这些候选被提交之前对其进行验证。当多个草稿 token 被接受时，系统可以在一次目标模型验证步骤中提交多个输出 token，同时保持目标模型的输出行为。

本文探讨投机解码在 vLLM 中的工作方式，并分享来自我们测试环境的测量结果。我们首先回顾自回归解码基线与「起草—验证」流程，然后考察五种投机起草方法：原生 MTP、Gemma 4 MTP、EAGLE-3、DFlash 和 DSpark。这些方法的差异在于草稿组件如何从目标模型接收信息，以及候选 token 是顺序生成、自回归生成、并行生成，还是通过混合方式生成。最后，我们展示如何启用在我们环境中测试过的这些方法，报告在使用 ROCm™ 开源软件平台的 AMD Instinct™ MI300X 与 MI355X GPU 上开展实验的测量结果，并讨论实用的调优与可观测性考量。

在每个步骤之后，生成的 token 会被追加到序列中，并成为下一步骤输入的一部分。这使得解码循环非常直接，但它也要求每个输出 token 都对应一次模型解码步骤。在长生成过程中，这种逐 token 的循环可能主导延迟并限制服务吞吐量。

因此，投机解码背后的关键问题是：

我们能否在保持原始模型输出行为的同时，减少生成过程一次只推进一个 token 的频率？

投机解码通过将提议与验证分离来解决这个问题。草稿组件首先提出若干候选的未来 token，随后由原始模型充当目标模型，在这些候选被提交之前对其进行验证。

## 投机解码的核心思想

投机解码并不取代原始模型。相反，它让原始模型继续作为目标模型——仍然负责最终输出——并在其前面增加一个更快的提议阶段。

该过程包含两个部分：

- 起草（Draft）：提出若干候选的未来 token。
- 验证（Verify）：使用目标模型检查这些候选。

在每一轮投机解码中，如图 1 所示，轻量级草稿组件会提出一个或多个未来 token。这些 token 只是候选，不会被立即提交。随后，目标模型在一次验证过程中对候选 token 序列进行评估。

验证从左到右进行。每个草稿 token 都使用目标模型在对应位置的结果进行检查。被接受的 token 会提交到输出序列中。当某个草稿 token 被拒绝时，同一提议中位于其后的候选将不再被接受。

如果某个草稿 token 被拒绝，则由目标模型提供下一个 token。其余草稿 token 被丢弃，生成过程从更新后的序列继续。

## 起草方法的工作原理

尽管所有投机解码方法都遵循同样的「起草—验证」总体流程，但它们在草稿组件的设计方式以及与目标模型协同工作的方式上有所不同。

主要差异在于：

- 从目标模型接收的信息类型。
- 这些信息如何被纳入起草过程。
- 候选 token 是顺序生成还是并行生成。

基于这些差异，本文讨论的起草方法可以归为三大类：原生 MTP 模块、独立 MTP 起草器，以及专用的目标条件草稿网络（target-conditioned draft networks）。

- **原生 MTP 模块：** 直接内建于目标模型架构之中；使用模型原生的辅助预测路径；顺序生成候选 token。
- **独立 MTP 起草器：** 使用与特定目标模型配对的独立检查点；在推理期间使用目标模型的激活值和共享的 KV 缓存信息；顺序生成候选 token。
- **专用目标条件草稿网络：** 使用为特定目标模型训练的独立 speculator 模型，包括 EAGLE-3、DFlash 和 DSpark。EAGLE-3 基于目标模型的隐藏状态自回归地起草，DFlash 从目标模型隐藏状态并行地起草整个块，DSpark 则增加了轻量级的因果校正和基于置信度的前缀选择。

这些类别描述的是草稿组件的架构，而不是目标模型的家族。一个目标模型可以在支持原生 MTP 的同时，还拥有单独训练的 EAGLE-3、DFlash 或 DSpark 草稿模型。

草稿组件并非完全独立运行。根据方法的不同，草稿组件可能接收：

- 来自目标模型的隐藏表示。
- 来自若干选定目标层的隐藏状态。
- 目标模型的 KV 缓存。
- 由多个目标模型表示组合而成的特征。

下面几节将解释每种方法如何使用这些信息以及如何生成候选 token。

### 原生 MTP

多 token 预测（Multi-Token Prediction，MTP）指一类模型原生机制，用于预测紧随其后的下一个 token 之外的未来 token。在 vLLM 中，当目标模型包含兼容的辅助预测组件时即可使用原生 MTP [[2]](#ref-2)。MTP 的具体架构因模型家族而异，但每种实现都提供一条用于提议未来 token 的辅助路径。

在第一个投机步骤，MTP 组件将来自目标模型的隐藏表示与当前 token 的信息相结合，以预测第一个草稿 token。在后续步骤中，则使用新起草的 token 和上一步 MTP 产生的隐藏状态来预测下一个候选。在提议出配置数量的候选之后，目标模型在一次验证过程中统一评估它们。

### EAGLE-3

EAGLE-3 使用为特定目标模型训练的专用草稿网络。草稿组件拥有自己的执行路径，但它仍然紧密依赖于目标模型产生的信息 [[4]](#ref-4)。

### DSpark

DSpark 在并行起草的基础上增加了两个额外机制：

- 一个轻量级顺序头，用于在草稿块内的 token 之间引入依赖关系。
- 基于置信度选择提交给目标模型验证的前缀。

DSpark 使用经过修改的 DFlash 模型作为其并行主干（backbone）[[6]](#ref-6)。该主干在一次前向传播中完成对所有位置的主要起草计算，为每个草稿位置产生一个隐藏状态和一组基础 logits。因此，它继承了 DFlash 一节所描述的目标上下文条件化机制。

完全并行的草稿组件在预测每个位置时，并不先看到同一块中较早位置所选出的 token。当存在多种合理的续写时，这可能产生不一致的组合。例如，"of course" 与 "no problem" 都可能是合理的续写，但彼此独立的位置预测可能产生 "of problem"。

DSpark 通过在并行主干之后应用一个轻量级顺序头来解决这种行为。主干仍然一次性计算每个位置的基础 logits，然后顺序头从左到右选择 token，利用先前选出的草稿 token 的信息对每个位置进行调整。

## 如何在 vLLM 中启用投机解码

在 vLLM 中，投机解码通过 `--speculative-config` 进行配置。主要差异在于方法名称、是否需要单独的草稿检查点，以及请求的候选 token 数量。当前版本的 vLLM 支持 mtp、eagle3、dflash 和 dspark 作为 method 取值。

| 方法 | 需要单独的草稿检查点 | 典型配置 |
| --- | --- | --- |
| 原生 MTP | 否 | `"method": "mtp"`  `"num_speculative_tokens": <N>` |
| Gemma 4 MTP | 是 | `"method": "mtp"`  `"model": "<matching-assistant>"`  `"num_speculative_tokens": <N>` |
| EAGLE-3 | 是 | `"method": "eagle3"`  `"model": "<matching-speculator>"`  `"num_speculative_tokens": <N>` |
| DFlash | 是 | `"method": "dflash"`  `"model": "<matching-speculator>"`  `"num_speculative_tokens": <N>` |
| DSpark | 是 | `"method": "dspark"`  `"model": "<matching-speculator>"`  `"num_speculative_tokens": <N>` |

对于原生 MTP，草稿组件随目标模型一同提供，因此省略 model 字段：

```
vllm serve <target-model> \
  --speculative-config '{
    "method": "mtp",
    "num_speculative_tokens": <N>
  }'
```

对于 Gemma 4 MTP、EAGLE-3、DFlash 和 DSpark，model 字段通常指向为目标模型训练的检查点：

```
vllm serve <target-model> \
  --speculative-config '{
    "method": "<method>",
    "model": "<matching-draft-checkpoint>",
    "num_speculative_tokens": <N>
  }'
```

Gemma 4 助手检查点虽然通过 model 字段提供，但使用的仍是 MTP 路径。vLLM 会将助手组件连接到目标模型，并允许它共享目标的 KV 缓存。

在启用某种方法之前，请确认：

- 已安装的 vLLM 版本支持该方法和模型架构。
- 草稿检查点与目标模型和方法兼容。
- `num_speculative_tokens` 与该检查点兼容。
- 模型卡片支持目标硬件与推理后端。

### 内存考量

原生 MTP 不加载单独的草稿检查点，并且可能与目标模型共享嵌入表或输出头等组件。Gemma 4 MTP、EAGLE-3、DFlash 和 DSpark 则会加载额外的草稿权重，因此应预留充足的 GPU 显存余量。实际开销取决于草稿组件的大小、数值精度、张量并行配置以及运行时缓冲区。

## 实验设置与测量

启用投机解码之后，实际的问题就是：额外的起草工作是否能改善端到端服务性能。候选 token 不必在每个位置都正确，因为目标模型会在提交之前对它们进行评估。因此，性能取决于有多少提议的 token 被接受，以及节省下来的目标模型解码工作是否超过起草与验证的成本。

我们使用基于任务的基准测试而非随机 token 序列来评估模型质量与服务性能。接受行为取决于实际模型输出的结构和可预测性，因此基于任务的提示词能够更真实地反映实际性能。

主要性能指标包括：

- 输出 token 吞吐量，以及相对非投机基线的加速比。
- 在可得的情况下，平均接受长度与草稿 token 接受率。
- 相对非投机基线的模型质量。

### 主要观察结果

测量结果因目标模型、起草方法、工作负载和提议长度而异。

对于 gemma-4-26B-A4B-it，在所测试的扫描范围内测得的最大吞吐量比值是：Gemma 4 MTP 在 GSM8K 和 MBPP 上分别为 2.74× 和 2.62×，DFlash 在 MATH500 和 HumanEval 上分别为 2.87× 和 2.79×。EAGLE-3 在四个数据集上的测量值介于 2.11× 到 2.27× 之间。

对于 gemma-4-31B-it，Gemma 4 MTP 在 GSM8K 上达到 2.00×，在 MBPP 上达到 1.99×；DFlash 在 MATH500 上达到 2.34×，在 HumanEval 上达到 2.05×。EAGLE-3 与 DSpark 在四个受评数据集上的测量值也都高于基线。与最大测量吞吐量对应的提议长度因工作负载而异。

对于 Qwen3-8B，DSpark 的测量值从 MATH500 上的 1.15× 到 GSM8K 上的 1.63× 不等；DFlash 的测量值介于 1.08× 到 1.27× 之间。EAGLE-3 在 GSM8K、HumanEval 和 MBPP 上高于基线，而其在 MATH500 上测得的最大值仍低于基线。

对于 Qwen3.5-27B、Qwen3.5-122B-A10B 和 Qwen3.6-27B，在所测试的扫描范围内，原生 MTP 的最大测量值高于相应的 DFlash 最大值。该组中最大的比值是 Qwen3.5-122B-A10B 在 MATH500 上的 2.20×。与最大测量吞吐量对应的原生 MTP 提议长度在 N=4 到 N=7 之间，具体取决于模型和数据集。

对于 Qwen3.6-35B-A3B，DFlash 的测量值介于 1.77× 到 2.06× 之间，且四个数据集的最大值都出现在 N=7；原生 MTP 的测量值介于 1.28× 到 1.49× 之间，最大值出现在 N=6。与 Qwen3.6-27B 测量结果的差异表明，同一家族内不同模型的结果可能不同。

对于 MiniMax-M3-MXFP8，EAGLE-3 在 HumanEval 上于 N=4 时达到 2.09×。对于 Kimi-K2.5，EAGLE-3 最高达到 2.33×，DFlash 最高达到 2.68×。在所测试的扫描范围内，EAGLE-3 的最大值一般出现在 N=4，而 DFlash 的最大值出现在 N=7。

纵观各项实验，与最大测量吞吐量对应的提议长度并不是恒定的。对于顺序方法，吞吐量通常在 N 的前几个取值上上升，随后趋于平稳。对于 DFlash 和 DSpark，N=7 经常属于吞吐量较高的设置之一，而更大的取值并不能持续提升吞吐量。

这些观察结果反映的是本研究使用的硬件、软件、目标模型、草稿检查点、工作负载和扫描设置。

## 调优考量

投机解码应被视为一种运行时优化，而不是对每种工作负载都同样有效的固定设置。与最高吞吐量对应的 `num_speculative_tokens` 取值取决于有多少提议的 token 被接受，以及避免掉的目标模型解码工作量是否超过起草与验证的成本。

因此，可观测性非常重要。模型卡片上的建议或示例配置是有用的起点，但最终设置应根据有代表性的工作负载和端到端测量来选定。有用的信号包括吞吐量、平均接受长度、整体接受率和逐位置接受率。

更大的提议窗口让系统有更多机会在一次验证过程中提交多个 token。然而，靠后的草稿位置的接受率可能会下降。出现这种情况时，额外的候选贡献甚微，却仍会增加起草和验证工作，导致吞吐量持平甚至回落。

### 从受支持的配置开始

对于原生 MTP，N=1 是一个保守的起点，因为它引入的额外顺序起草工作最少：

```
{"method": "mtp", "num_speculative_tokens": 1}
```

在确认正确性和稳定性之后，再扫描更大的取值，例如 2、3、4、5、6 和 7。

在我们的测量中，与最大测量吞吐量对应的原生 MTP 设置因目标模型和工作负载而异。对于 Qwen3.5-27B，最大测量吞吐量出现在：GSM8K 和 MATH500 上为 N=5，HumanEval 和 MBPP 上为 N=4，MT-Bench 上为 N=3。对于 Qwen3.5-122B-A10B，所列出的四个推理与代码数据集上的最大测量吞吐量都出现在 N=7。

Qwen3.6 的测量结果也表明，这一设置在同一家族的不同模型之间可能不同。对于 Qwen3.6-27B，最大测量值出现在 N=4 或 N=5；而所测试的 Qwen3.6-35B-A3B 配置的吞吐量一直增加到 N=6。

对于 Gemma 4 MTP 和 EAGLE-3，增大 N 同样会增加顺序起草工作。因此，即使检查点提供了推荐配置，做一次简短的扫描仍然是有益的。在我们的 Gemma 4 与 EAGLE-3 实验中，测量吞吐量通常在 N 的前几个取值上上升，随后趋于平稳。

对于 DFlash，应从草稿检查点推荐或支持的提议长度开始。许多 DFlash 检查点以固定的块大小训练。例如，当：

```
block_size = 16
```

最大提议长度通常为：

```
num_speculative_tokens = 15
```

因为第一个位置是已确认的锚点 token，其余 15 个位置是草稿候选。

这是受支持的最大提议长度，并不一定是吞吐量最高的设置。在实践中，测试较小的取值会很有用，例如：

```
N = 3, 7, 11, 15
```

在我们的 DFlash 实验中，N=7 经常属于吞吐量较高的设置之一。在某些工作负载上，最大测量吞吐量出现在 N=11。

对于 DSpark，`num_speculative_tokens` 设置每轮投机生成的候选 token 数量。在我们的 vLLM 实验中，完整配置的提议都会提交给目标模型验证，因此应使用端到端吞吐量来比较 N=3 与 N=7 等取值。

### 监控接受行为

需要监控的相关信号包括：

| 信号 | 含义 |
| --- | --- |
| 吞吐量 | 端到端服务性能相对非投机基线的变化 |
| 平均接受长度 | 每轮投机平均提交多少草稿 token |
| 整体接受率 | 被接受的提议草稿 token 所占比例 |
| 逐位置接受率 | 提议中靠后的位置是否仍然有用 |

在调优提议长度时，逐位置接受率尤其有用。如果前几个位置经常被接受，而靠后的位置贡献很小，那么减小 `num_speculative_tokens` 可以通过避免不必要的起草工作来提升吞吐量。

接受指标应与吞吐量结合起来解读。当草稿生成的代价很低时，即使接受率较低，某种方法也可能表现出相对基线更高的吞吐量。反之，当草稿组件带来额外开销时，高接受率也不一定对应更高的吞吐量。

### 让扫描与工作负载相匹配

不同的工作负载可能产生不同的接受模式。

在我们的 GSM8K 与 MATH500 测量中，在所测试的扫描范围内，中等或更深的提议长度往往对应更高的测量吞吐量。对于 Qwen3.5-122B-A10B 上的原生 MTP，测量吞吐量一直增加到 N=7。对于 DFlash，较高的测量值经常出现在 N=7 或 N=11。

对于 HumanEval 与 MBPP，适中的提议长度往往属于吞吐量较高的设置。代码包含可预测的局部结构，但格式、标识符和实现选择都可能让本来看似合理的续写出现分歧。

### 调优工作流示例

1. 从该检查点受支持或被推荐的配置开始。
2. 使用有代表性的提示词与生成设置进行基准测试。
3. 记录吞吐量、平均接受长度和接受率。
4. 扫描若干较小和较大的提议长度。
5. 依据与目标工作负载最相关的指标选择设置。在这些实验中，端到端服务吞吐量是首要选择指标。

被选中的配置并不一定是提议最长、接受率最高或平均接受长度最大的那一个。选择时应权衡起草成本、验证成本、被接受的 token 数量以及与目标工作负载最相关的指标。

## 为新的目标模型训练 speculator

本指南不深入介绍 speculator 的训练。以下工作流概括了所引用的 vLLM Speculators 与 DeepSpec 资源 [[13]](#ref-13)、[[14]](#ref-14) 和 [[15]](#ref-15) 中的实践要点。

典型工作流如下：

1. 准备有代表性的提示词。
2. 使用目标模型生成回复。
3. 选择隐藏状态的生成模式。
4. 收集所需的目标模型隐藏状态。
5. 训练 speculator。
6. 测试接受情况与服务吞吐量。

### 准备有代表性的提示词

从能够反映预期工作负载的提示词入手，例如聊天、数学、代码生成、工具使用或多语言任务。另留一组提示词专用于评估。

用于训练的回复应由 speculator 将要支持的同一个目标模型生成。分词器、聊天模板、思考模式和生成配置也应与预期的部署相匹配。vLLM 文档强调：对已有回复套用目标模型的分词器或聊天模板，并不能让数据具有目标针对性；回复本身必须来自目标模型。

### 选择获取隐藏状态的方式

speculator 在训练期间接收来自目标模型的内部隐藏状态。vLLM Speculators 工作流支持三种提供方式：

| 训练模式 | 工作方式 | 主要考量 |
| --- | --- | --- |
| 在线（Online） | 隐藏状态由运行中的 vLLM 服务器在需要时生成，用后即弃 | 避免庞大的磁盘缓存，但需要同时承担目标模型推理与训练的资源 |
| 离线（Offline） | 隐藏状态在训练开始前生成并存储 | 之后可将所有 GPU 释放用于训练，但需要大量存储空间 |
| 混合（Hybrid） | 隐藏状态在第一个 epoch 期间生成并缓存，随后复用 | 只需支付一次生成成本，且无需单独的预处理阶段 |

所选模式改变的只是隐藏状态的来源；其余训练流程基本相同。

### 收集目标模型信息

vLLM 服务器可以运行目标模型，并暴露所选起草方法所需层的隐藏状态。如果选择了自定义目标层，那么在 speculator 训练配置中也必须使用相同的层选择。

收集的信息取决于所用方法：

- EAGLE-3 使用来自选定目标模型层的隐藏状态进行自回归起草。[[4]](#ref-4)
- DFlash 使用目标模型特征来训练一个并行预测整块未来位置的网络。[[16]](#ref-16)
- DSpark 在 DFlash 式草稿网络上添加轻量级顺序头与置信度头。[[6]](#ref-6)
- MTP 训练对目标模型自身的 MTP 组件进行微调，因此要求目标模型已经包含兼容的 MTP 层。[[13]](#ref-13)

### 训练并测试 speculator

speculator 的配置必须与目标模型的隐藏维度、词表、分词器和选定的目标层相匹配。还需要选择方法特定的设置，例如草稿网络深度、块大小、序列长度和学习率。

训练完成后，检查检查点，并在 vLLM 中将其与目标模型一起部署服务。仅凭训练损失不足以评判结果；重要的测量指标是接受长度、接受率、草稿延迟、GPU 显存使用量和端到端服务吞吐量。vLLM Speculators 教程涵盖了从数据准备、隐藏状态提取到检查点测试与部署服务的完整路径。

当 speculator 在特定工作负载上接受表现不佳时，可以调整提示词配比或训练配置，然后重复上述过程。核心原则是：使用 speculator 预期要支持的同一个目标模型、生成模式和有代表性的工作负载。

## 总结

本文探讨了作为 LLM 服务「起草—验证」方法的 vLLM 投机解码。草稿组件提出候选的未来 token，目标模型在任何 token 被提交之前对提议进行评估。

我们考察了五种起草方法：原生 MTP、Gemma 4 MTP、EAGLE-3、DFlash 和 DSpark。它们的主要差异在于如何使用来自目标模型的信息，以及候选 token 是顺序生成、并行生成，还是通过并行预测加轻量级顺序校正的组合方式生成。

实验在采用 ROCm™ 软件平台的 AMD Instinct™ MI300X 与 MI355X GPU 上，覆盖了选定的 Gemma、Qwen、MiniMax 和 Kimi 模型。测量吞吐量因目标模型、草稿检查点、工作负载、提议长度和服务配置而异。

在所测试的配置中，一些设置带来的变化较小，或吞吐量低于非投机基线，而若干模型-工作负载组合则取得了 2× 以上的吞吐量比值。处于观察范围上端的例子包括：DFlash 在 gemma-4-26B-A4B-it 上的 2.87×、Gemma 4 MTP 在同一目标模型上的 2.83×，以及 DFlash 在 Kimi-K2.5 上的 2.68×。

提议长度也是一个重要的实验变量。增大 `num_speculative_tokens` 有时会在前几个设置上提高吞吐量，而更大的取值可能导致吞吐量持平或降低。检查点推荐可以提供起点，但在选择部署配置时，仍需要有代表性的工作负载测量结果和接受指标。

## 未来工作

未来的基准测试可以纳入非学习类方法，例如 n-gram 投机和后缀解码（suffix decoding），尤其是对于代码编辑、智能体循环等具有重复 token 模式的工作负载。

在并发级别、提示词与输出长度、批大小和采样设置等更多维度上开展更广泛的评估，也有助于展现投机解码在不同服务条件下的表现。

另一个有用的方向是研究 speculator 训练数据如何影响代码、数学、聊天、多语言提示词、工具使用和结构化输出等场景的接受表现。这可以为针对特定工作负载选择或训练草稿检查点提供更明确的指导。

最后，对草稿生成、目标验证、KV 缓存行为、图执行和调度进行更深入的性能剖析，将有助于解释在不同目标模型和工作负载上观察到的性能差异。
