# vLLM 上生产级 Kimi K3 支持前瞻

> 原文：[A Preview of Production-Scale Kimi K3 Support on vLLM](https://vllm.ai/blog/2026-07-22-kimi-k3-preview) · vLLM 博客

作者：vLLM 团队

[#模型](https://vllm.ai/blog/tags/models)[#性能](https://vllm.ai/blog/tags/performance)[#前缀缓存](https://vllm.ai/blog/tags/prefix caching)[#多模态](https://vllm.ai/blog/tags/multimodal)

上周，Moonshot AI [发布了 Kimi K3](https://www.kimi.com/blog/kimi-k3)：一个 2.8 万亿参数的模型，原生支持视觉、拥有 100 万 token 的上下文窗口，采用 Kimi Delta Attention（KDA）、注意力残差（Attention Residuals，AttnRes）以及高度稀疏的混合专家架构。发布消息立刻引起了[全球关注](https://x.com/Kimi_Moonshot/status/2077830229968683203)，开源社区也为开放权重模型快速进步、追赶最强专有模型而倍感兴奋。

Moonshot AI 已宣布完整模型权重将于 2026 年 7 月 27 日前发布。与此同时，vLLM、Moonshot AI、NVIDIA、AMD 和更广泛的社区正在完成最后的集成与验证，让开源社区可以从 Day 0 开始服务 Kimi K3。

本文是一篇前瞻，性能优化仍在进行中，但核心模型路径、感知 KDA 的前缀缓存、多模态集成、工具调用解析器以及硬件特定优化都已初具规模。部分经 Moonshot AI 与 vLLM/Inferact 团队双方批准的可信合作伙伴，也已开始使用正在为开源准备的同一套代码进行部署验证。

正如发布公告所说，KDA 给传统前缀缓存带来了新挑战，Moonshot AI 团队已向 vLLM 项目贡献了相应的实现，将随模型权重一同发布。我们将在未来的博客文章中专门解释这一设计。

## TL;DR

- **Day-0 开源服务：** vLLM 正在为 Kimi K3 权重发布准备模型实现、Docker 镜像、部署配方和生产验证。
- **全新的混合架构：** Kimi K3 将以 KDA 为主的线性注意力与周期性全注意力层结合，深度方向使用 AttnRes，并配备 Stable LatentMoE 与原生视觉支持。
- **前缀缓存需要核心改动：** vLLM 现在把 KDA 状态的物理块大小与前缀匹配粒度分离开来，无需在每个小的注意力块上保存循环状态，就能获得有用的部分前缀缓存命中。
- **贯穿全栈的内核工作：** 发布分支包含 FlashKDA 集成、融合的 KDA 解码、融合的 KDA 投影与卷积、融合的 AttnRes、重新实现的 MLA 模块、支持 SiTU 的 MXFP4 MoE 执行，以及优化的专家路由。
- **NVIDIA 与 AMD 支持：** NVIDIA 专属内核正在最后调优，带有 FlyDSL MoE 内核的初步 AMD 实现已就位，正在接受更广泛的验证。

## Kimi K3 一览

Kimi K3 不是 Kimi K2 的放大版。Kimi K3 同时在多个维度上改变了服务问题。

| 属性 | Kimi K3 配置 | 对服务的影响 |
| --- | --- | --- |
| **模型规模** | **2.8T 参数** | 需要大规模专家并行和高带宽加速器域 |
| **上下文长度** | **1M token** | 使缓存容量、前缀复用、分块预填充和预填充/解码分离成为第一优先级问题 |
| **注意力** | **KDA 与全注意力混合** | 要求循环状态缓存与分页 KV 缓存在完全相同的逻辑前缀上同步推进 |
| **深度** | **注意力残差（AttnRes）** | 增加了需要专用内核的跨层表示读写 |
| **MoE** | **896 个路由专家，每个 token 激活 16 个，另有共享专家** | 使路由、分发、负载均衡和 MoE 内核成为端到端性能的核心 |
| **量化** | **提供的发布配置使用 MXFP4 权重** | 需要配合 Kimi K3 的 SiTU 激活的高效 FP4 MoE 路径 |
| **多模态** | **带视觉塔的原生视觉** | 需要多模态预处理（仅图像）和稳健的视觉并行策略 |

对推理系统来说，这些选择中的每一个都把成本挪到了新的地方。KDA 减少了对每个历史 token 保留传统 KV 对的需求，但引入了庞大的循环状态。AttnRes 缓解了单一残差流的局限，但带来了额外的跨层内存流量。极致的 MoE 稀疏性避免每个 token 都激活全部 2.8T 参数，但提高了对路由与通信的要求。vLLM 的任务就是让所有这些部分在一个熟悉的服务 API 背后协同工作。

## 最难的部分：KDA 的前缀缓存

传统的全注意力与 KDA 记住前缀的方式截然不同。

在全注意力中，前缀由逐 token 的键和值向量表示。vLLM 把这些向量存储在分页块中，对完整的 token 块做哈希，并可以为另一个请求复用匹配的块序列。

KDA 是循环式的。每个 KDA 层不是为每个 token 保留传统 KV 对，而是推进一个类似矩阵的循环状态，外加一个短卷积状态。要从缓存前缀恢复，引擎需要*正好位于前缀边界处*的 KDA 状态。靠重放更早的状态到达该边界，会抹掉前缀缓存的大部分收益。

![传统注意力与 KDA 如何表示缓存前缀](https://vllm.ai/blog-assets/figures/2026-07-22-kimi-k3-preview/kda-prefix-state.png)

传统注意力与 KDA 如何表示缓存前缀

直接的办法——在每个小的注意力缓存边界上都保存 KDA 状态——代价太高。一个 KDA 状态远大于一个普通 token 的 KV 条目，所以实现会采用相对较大的物理状态块来摊薄存储开销。在本次工作之前，这个物理块大小也约束了前缀缓存命中可以落在哪里。当一个状态块长达数千 token 时，两个共享几乎整个提示的请求仍可能错过可复用的前缀，因为它们的公共边界没有填满同一个物理块。

新的 vLLM 设计把过去绑在一起移动的三个概念分离开来：

- **物理块大小：** KDA 状态与全注意力 KV 在 GPU 上如何分配。
- **调度器对齐：** 执行必须停在何处，才能让所有缓存组保持一致。
- **前缀匹配单元：** 共享前缀被哈希并可能被匹配的更细的 token 区间。

![较大物理 KDA 状态块内部的细粒度前缀匹配](https://vllm.ai/blog-assets/figures/2026-07-22-kimi-k3-preview/fine-grained-prefix-cache.png)

较大物理 KDA 状态块内部的细粒度前缀匹配

这让 vLLM 可以在较大物理状态块内部的细粒度边界上注册有效的 KDA 状态。当后续请求命中这个部分块时，缓存状态会先复制到私有目的地，然后请求再对它进行扩展。这一写时复制（Copy-on-Write）规则在允许新请求安全继续生成的同时，保住了共享的缓存前缀。

实现还处理了一些容易忽略的细节：

- 调度器在正确的块和哈希边界停下，确保注册的循环状态确实与宣称的 token 前缀对应。
- 全注意力与 KDA 缓存组就同一个 `num_computed_tokens` 达成一致，即使它们的物理块大小不同。
- 部分缓存条目使用链式的细粒度哈希，因此一个边界能标识整个前缀，而不只是末尾的 token。
- 同步复用被推迟到状态复制安全之后，避免缓存注册与扩展之间的竞态。
- 缓存传输与分离式预填充/解码路径可以在 worker 之间携带同一个逻辑前缀。

这项工作由 Kimi K3 以及许多其他混合注意力模型驱动，但它是 vLLM 的核心基础设施，而不是某个模型专属的捷径。vLLM 团队与 Moonshot AI 团队在设计上深度合作。两个团队将另行发布一篇文章，更详细地介绍设计、不变量与基准测试。

## 性能工作：消除新的瓶颈

我们目前的进展可以总结为下表：

| 领域 | 当前状态 |
| --- | --- |
| **模型与配置** | Kimi K3 语言与视觉模型定义已集成；在硬件路径不同的地方分别提供 **NVIDIA** 与 **AMD** 实现 |
| **面向原生 PD 分离部署优化的 MLA 模块** | 经手工内核融合优化的 MLA 模块，预填充/解码路径分离。门控投影与注意力并行执行，解码路径支持多流，预填充路径使用融合的尾部计算（epilogue）——为 PD 分离部署高度优化。 |
| **服务语义** | Kimi K3 的聊天渲染、tokenizer 集成、流式解析、工具调用、推理输出与结构化输出路径均已实现，正处于**最后的端到端验证** |
| **KDA 预填充** | FlashKDA 与 Triton 路径已集成；最终后端选择与数值验证**进行中** |
| **KDA 解码** | 覆盖卷积、KDA 循环更新、门控与归一化的融合 **NVIDIA** 解码内核已集成，同时保留可移植的回退路径 |
| **前缀缓存** | 混合全注意力 + 循环状态缓存的细粒度部分前缀命中已集成；分离部署与卸载场景**验证中** |
| **注意力残差（AttnRes）** | Triton 与 **NVIDIA** 内核已集成，包括在受支持形状上融合残差相加与输出 RMSNorm |
| **MoE** | Kimi K3 的 **SiTU** 激活已接入 **MXFP4 TRTLLM-Gen** 与 **DeepGEMM** 路径；优化的分组 top-k 路由已集成。**AMD** 基于 FlyDSL 的 **MLIR** 内核栈实现硬件调优的 **A16W4/A8W4** 融合算子与 **SiTU** 激活 |
| **生产栈** | 非分离式服务已可运行；Dynamo + vLLM + Mooncake 分离式服务、专家并行与厂商验证正处于**最终验证循环** |

Kimi K3 改变了热路径，因此团队优化的不只是注意力内核本身。以下是各领域进展的细节。

### KDA 预填充与解码

预填充路径集成了 FlashKDA 与 Flash Linear Attention（FLA）。围绕核心循环计算，vLLM 融合了输入投影与因果卷积，并在一次操作中收集初始循环状态。

解码在受支持的架构与形状上使用融合的 NVIDIA 内核。融合路径把短卷积、KDA 状态更新、输出门控与归一化一起执行，而不是为每个生成的 token 分别启动独立操作。这一点尤其重要，因为 Kimi K3 包含大量 KDA 层；每层一点点启动或内存开销，很快就会累积成可观的 TPOT 损失。

### 注意力残差（AttnRes）

AttnRes 从更早层块写下的表示中读取，而不是只依赖一条均匀累积的残差流。朴素的实现会在整个 93 层网络中产生额外的读、写、归约和归一化启动。

发布分支包含一个 Triton 实现和一个 NVIDIA 内核，在受支持的情形下融合残差更新、AttnRes 混合与输出 RMSNorm。序列并行方面的工作还把注意力残差的流量在 rank 之间分片。早期的内核级结果令人鼓舞，端到端收益仍在不同的预填充长度与并行配置下测量中。

### 面向原生 PD 分离部署优化的 MLA 模块

Kimi K3 仍然每四层使用一次 MLA 注意力。在上一代模型中，vLLM 很大程度上依赖 `torch.compile` 的自定义融合路径把小内核映射为融合内核，这拖慢了启动，而且仍有许多内核未被融合。在本次发布中，我们实现了一个新的 MLA 模块，以手工方式融合这些内核。MLA 还要求预填充与解码使用不同的内核启动顺序，因此我们实现了两条采用不同融合模式的代码路径，专门为 PD 分离部署而设计。此外，Kimi K3 引入了一个可以与主注意力路径并行执行的门控投影。我们在解码路径中为门控投影选择性提供多流支持，而在预填充路径中——多流重叠并非最优——我们把逐元素乘法与 sigmoid 融合进门控投影的尾部计算（epilogue）。

### MXFP4 MoE

Kimi K3 的发布配置使用 MXFP4 权重和 SiTU 激活。在这项工作之前，MXFP4 TRTLLM-Gen 路径不支持 SiTU，会回退到较慢的实现。vLLM 现在把 Kimi K3 的 SiTU 参数映射进优化的 FP4 专家路径，并通过安全地对工作负载分块，处理 token×top-k 组合过大导致的启动网格。

这已经在 16 GPU 的 DP16+EP16 配置上完成验证，所有 rank 都选择了优化的 MXFP4 后端并通过了正确性检查。

在 AMD 一侧，Kimi K3 MoE 由 FlyDSL 的 MLIR Python 内核栈支持，包括硬件调优的 A16W4/A8W4 量化融合算子和 SiTU 激活实现，全部构建在 FlyDSL 的模块化抽象之上。

## One More Thing：为什么发布公告与开源发布是分开的

Kimi K3 还带来了一种我们希望更多模型供应商考虑的发布流程：先发布模型公告，稍后再放出权重与推理引擎支持。

这一分离由 vLLM 团队提议，Moonshot AI 同意并执行。原因很现实。前沿模型的发布公告不可避免地带有"最后一公里"的不确定性。模型团队同时在稳定自己的产品、API、评估、安全工作、文档与商业发布。如果开源权重与开源支持必须落在完全相同的时刻，vLLM 这样的社区项目就会被不断变动的截止日期拖累。

把两条时间线分开，给双方带来更好的契约：

1. 模型供应商可以专注于产品发布，并冻结最终的检查点、配置、tokenizer 与服务语义。
2. 开源推理引擎团队获得一个稳定的集成窗口，用于正确性测试、性能调优、Docker 构建与配方验证。
3. 社区得到一个公开、有边界的预期，而不是模糊的"敬请期待"。

这一分离不是从 Day-0 支持上的退缩。它是一种更可持续的方式，针对用户真正会下载的工件交付 Day-0 支持。我们鼓励更多模型供应商效仿！
