# vLLM 上的 TML Inkling：Day-0 支持与优化性能

> 原文：[TML Inkling on vLLM: Day-0 Support with Optimized Performance](https://vllm.ai/blog/2026-07-15-inkling) · vLLM 博客

作者：vLLM 团队

[#模型支持](https://vllm.ai/blog/tags/model-support)[#性能](https://vllm.ai/blog/tags/performance)[#多模态](https://vllm.ai/blog/tags/multimodal)[#投机解码](https://vllm.ai/blog/tags/speculative-decoding)

![](https://vllm.ai/blog-assets/figures/2026-07-15-inkling/image1.png)

我们非常高兴地宣布，vLLM 在 Day 0 正式支持 TML Inkling 模型。[`thinkingmachines/Inkling-NVFP4`](https://huggingface.co/thinkingmachines/Inkling-NVFP4) 与 [`thinkingmachines/Inkling`](https://huggingface.co/thinkingmachines/Inkling)（BF16）两个模型均已获得支持，并带有优化过的性能与完整的特性对齐。

TML Inkling 是由 [Thinking Machines Lab](https://thinkingmachines.ai/) 训练的 1T 参数多模态模型。该模型原生接受**文本、图像和音频输入**并生成文本，上下文长度最高达 **1M**。它引入了多个新颖的架构组件——相对注意力（relative attention）、短卷积（short convolution）和共享专家汇（shared expert sinks）——如今这些都已高效集成进 vLLM。

在 vLLM 上，该模型在 4 张 GB200 GPU 上可达到最高 **380 tok/s/user（使用 MTP）** 与 **140 tok/s/user（不使用 MTP）**。vLLM 还提供了完整的特性对齐，包括 LoRA、TP/DP/EP/PP 并行、前缀缓存和分离式服务。我们通过全面的基准测试验证了模型精度与工具解析。

集成的 PR 见[这里](https://github.com/vllm-project/vllm/pull/48768)。按如下方式运行模型：

```
export VLLM_USE_V2_MODEL_RUNNER=1
export FLASH_ATTENTION_CUTE_DSL_CACHE_ENABLED=1

vllm serve thinkingmachines/Inkling-NVFP4 \
      --tokenizer-mode inkling \
      --reasoning-parser inkling \
      --tool-call-parser inkling \
      --enable-auto-tool-choice \
      --tensor-parallel-size 8 \
      --speculative-config '{"method": "mtp", "num_speculative_tokens": 8}' \
      --kernel-config.enable_flashinfer_autotune=False \
      --trust-remote-code
```

## TL;DR

vLLM 为 TML Inkling 提供了强大的 Day-0 支持：

- **模型：** [`thinkingmachines/Inkling-NVFP4`](https://huggingface.co/thinkingmachines/Inkling-NVFP4) 与 [`thinkingmachines/Inkling`](https://huggingface.co/thinkingmachines/Inkling)（BF16）均受支持
- **硬件：** NVIDIA Blackwell 与 Hopper GPU
  - 更广泛的硬件支持正在进行中，敬请期待！
- **模态：** 文本/图像/音频输入 → 文本输出
- **上下文长度：** 原生最高 1M token（Tinker 提供 64K 和 256K 上下文窗口）
- **特性：** LoRA、投机解码（MTP）、TP/DP/EP/PP、前缀缓存、分离式服务等
- **优化：** 感知 Sconv 的 TP 分片、低延迟融合集合通信、内核融合、多流（multi-streaming）、PDL 等
- **性能：** 在 4 张 GB200 GPU 上最高 **380 tok/s/user（使用 MTP）** 与 **140 tok/s/user（不使用 MTP）**
- **精度：** 通过 MMAU、MMMU-Pro、BFCL、NIAH-1M 与 HLE 验证了模型质量与工具解析

## 模型架构

![图 1：TML Inkling 模型架构（省略了部分算子，如 RMSNorm 和残差连接）。](https://vllm.ai/blog-assets/figures/2026-07-15-inkling/inkling-model-architecture.png)

图 1. TML Inkling 模型架构（省略了部分算子，如 RMSNorm 和残差连接）。

**模态。** TML Inkling 是一个 1T 参数的原生多模态模型。除文本和图像外，它还接受**音频**输入并生成文本。正如 [TML 的交互模型预览](https://thinkingmachines.ai/blog/interaction-models/)所述，模型使用了极其轻量的图像编码器（hMLP）和音频嵌入（dMel）。得到的嵌入由一个仅解码器的 Transformer 主干处理。

**注意力。** 主干共有 66 层：11 层全注意力层和 55 层滑动窗口注意力层。正是这种对滑动窗口注意力的大量使用，才让模型的 **1M 上下文长度**保持高效。所有注意力层都使用头维度为 128 的分组查询注意力（GQA）。

Inkling 一个独特的设计选择是使用*相对注意力*（relative attention）作为位置机制。它不使用 RoPE，而是在 softmax 之前的注意力 logits 上加一个可学习的相对位置项。细节请参阅 TML 的博客文章。

**Sconv。** Inkling 大量使用窗口大小为 4 的*短卷积*（short convolution，sconv）。每一层包含四个 sconv 模块，分别作用于注意力的键、注意力的值、注意力输出和 MoE 输出。Sconv 的作用类似小型局部注意力，而计算和内存开销极小。

**MoE。** 每层有 256 个路由专家（top-6）外加 2 个共享专家，因此每个 token 总共由 8 个专家处理。与现有模型不同的是，Inkling 引入了*专家汇*（expert sink）的概念：两个共享专家参与路由分数的计算（吸收概率质量），但不作为候选参与 top-6 选择。

在 `thinkingmachines/Inkling-NVFP4` 中，只有路由专家被量化为 NVFP4；包括共享专家和 qkvr 线性层在内的所有其他参数都保持 BF16。在 `thinkingmachines/Inkling` 中，MoE 权重同样是 BF16。

**MTP。** Inkling 自带 **8 个 MTP 头**用于投机解码，使模型每步前向最多可生成 9 个 token。这些 MTP 头是*链式*的：每个头消费上一个头的隐藏状态和采样出的草稿 token。每个 MTP 头是一个单层 Transformer，带全注意力或滑动窗口注意力以及一个稠密 MLP。所有 MTP 权重均为 BF16。

## vLLM 集成与优化

vLLM 通过一系列优化高效地实现了该模型。重点包括：

**管理 sconv 缓存。** 短卷积需要保留最后 `W-1` 个 token 的隐藏状态。vLLM 把这个 sconv 缓存当作一个虚拟滑动窗口注意力层的 KV 缓存来管理。这样 vLLM 就能通过统一的 KV 缓存管理器优雅地处理 sconv 缓存：落在窗口之外的状态被标记为可淘汰，前缀缓存与 sconv 缓存无缝配合。

![图 2：感知 Sconv 的 TP 分片。](https://vllm.ai/blog-assets/figures/2026-07-15-inkling/sconv-tp-sharding.png)

图 2. 感知 Sconv 的 TP 分片。

**感知 Sconv 的 TP 分片。** 对该模型做一个直白的 TP 实现，流程会是：all-reduce（例如在 `o_proj` 之后）→ sconv → 残差连接 → RMSNorm。然而，这会让每张 GPU 都对完整的隐藏状态执行 sconv，使 sconv 的计算与缓存在各 rank 间重复。

为了消除这种重复，vLLM 采用了不同的分片方式。由于 sconv 沿通道维度独立运算，我们按通道对 sconv 分片：不用 all-reduce，而是沿通道维度做 reduce-scatter 和 all-gather。这样每张 GPU 只存储 sconv 缓存的一个分片，也只计算自己那部分通道。这个思路类似于序列并行，但分片作用在通道维度而非 token 维度。

**低延迟融合集合通信。** vLLM 还实现了多个融合内核来优化这套新的分片方案。特别是，我们通过扩展 FlashInfer 低延迟 all-reduce 内核的 Lamport 协议设计，构建了低延迟的 reduce-scatter 与 all-gather 内核（与周边算子融合）。Lamport 协议让内核通过数据值轮询而非显式 barrier 来同步，把批大小为 1 时的内核时间从 **40 µs 降到 8 µs（5x）**。

**带剪切偏置（sheared bias）的 FA4。** 相对注意力使内存访问模式变得复杂，显著拖慢注意力内核的计算流水线。为了解决这一问题，TML 与 Colfax Research 合作发布了采用剪切偏置技术的新 [FA4 内核](https://github.com/vllm-project/tml-fa4)，vLLM 直接集成了它。此外，vLLM 还会按配置选择 FA4 的 `num_splits` 因子——综合考虑批大小、TP 规模和 KV 长度——以最大化性能。

**重算 MTP KV 缓存。** 由于每个 MTP 头以上一个头的草稿 token 为输入，一旦草稿 token 被拒绝，其 KV 缓存就会失效。vLLM 对此处理得很细致：它缓存基础模型最后几个 token 的隐藏状态，并在拒绝采样之后用被接受的 token 重跑 MTP 头。

除此之外，vLLM 的模型实现还包含额外的内核融合、PDL 和多流（multi-streaming），以达到极致性能。详情请查看[我们的 PR](https://github.com/vllm-project/vllm/pull/48768)。

### 性能

得益于上述大量优化，vLLM 在 4× GB200 GPU 上实现了使用 MTP8（平均接受长度 4.5）时 **380 tok/s/user**、不使用 MTP 时 **140 tok/s/user** 的性能。测试基于从 SPEED-Bench 采样的 8K 输入 token 提示，每个请求生成 1K 输出 token。

## 精度评估

我们用覆盖所有模态和能力的全面基准测试验证了 vLLM 实现的正确性：

- **音频：** MMAU
- **视觉：** MMMU-Pro
- **工具调用：** BFCL
- **推理：** HLE
- **长上下文：** NIAH

vLLM 在各项上都与参考实现持平。在长上下文方面，vLLM 在 221K token 以内与参考实现完全一致，到 513K 以内差距保持在约 1 个百分点以内。在最极端的上下文长度（800K+）下，NIAH 分数在该基准上显示出较高的运行间波动，我们正在改进该区间的可复现性。

## 路线图

如上所述，vLLM 为 TML Inkling 提供了强大的 Day-0 支持。展望未来，我们看到几个可能的改进方向：

- **全局注意力使用 FP8：** Inkling 目前的全局注意力使用 BF16，这在计算和 KV 缓存容量上都可能成为瓶颈。我们计划通过修改新的 FA4 内核来探索 FP8。
- **图像与音频编码器使用 CUDA Graph：** 图像和音频编码器目前以 eager 模式运行。虽然由于它们在预填充期间运行，这通常不是大问题，但我们计划对其应用 CUDA Graph，以彻底消除 CPU 开销。
- **AMD GPU 支持：** 该模型目前尚不支持 AMD GPU，因为新的相对注意力机制需要专用内核。支持即将推出。
