# 追随瓶颈：在 AMD Instinct MI355X 上优化 MiniMax M3

> 原文：[Following the Bottleneck: Optimizing MiniMax M3 on AMD Instinct MI355X](https://vllm.ai/blog/2026-09-10-minimax-m3-mi355x) · vLLM 博客

作者：AMD 与 Embedded LLM 团队

[#硬件](https://vllm.ai/blog/tags/hardware)[#性能](https://vllm.ai/blog/tags/performance)[#MoE](https://vllm.ai/blog/tags/moe)[#投机解码](https://vllm.ai/blog/tags/speculative-decoding)[#分离部署](https://vllm.ai/blog/tags/disaggregation)

[MiniMax M3 Day-0 文章](https://vllm.ai/blog/2026-06-12-minimax-m3-vllm)介绍了首个可以运行的 vLLM 实现：MiniMax 稀疏注意力（MSA）、多模态输入、推理与工具输出、MXFP8 权重，以及在 AMD Instinct MI355X 上的 EAGLE3。

这篇后续文章讲的是模型跑起来之后发生的事情。有价值的产出不只是更高的吞吐量数字，更是一种方法：当瓶颈不断转移时，如何决定接下来优化什么。

## 一分钟看懂结果

[SemiAnalysis InferenceX 基准测试](https://inferencex.semianalysis.com/inference)的公开结果显示了 MiniMax-M3 如今在 AMD Instinct MI355X 上的表现：

- 在并发 32 下，固定拓扑的 MXFP8 标准服务从 **109.1 提升至 342.4 output tokens/s/GPU**，为 Day-0 结果的 **3.14×**。TTFT 中位数从 1.46 秒降至 0.67 秒，TPOT 均值从 69.1 毫秒降至 22.1 毫秒。
- 在并发 128 下，同样的 TP4/EP1 四卡路径从 **297.8 提升至 623.7 output tokens/s/GPU**，即 **2.09×**。TTFT 中位数从 3.53 秒降至 1.54 秒，TPOT 均值从 100.7 毫秒降至 48.8 毫秒。
- MXFP4 首先在同样的 TP4/EP1 四卡约定下，于并发 128 从 **212.1 提升至 716.8 output tokens/s/GPU**。随后的一个 TP2/EP1 结果达到 **943.5 output tokens/s/GPU**，比该 TP4 检查点高出 **31.6%**，是初始每 GPU 结果的 **4.45×**。
- 我们加入了 EAGLE3 投机解码，在 TP4/EP1、并发 128 下达到 **682.4 output tokens/s/GPU**。
- 我们加入了 P/D 分离部署并重新调整了预填充/解码拓扑，在并发 512 下达到 **6,370.5 total tokens/s/GPU**，TTFT 中位数为 **1.32 秒**。

![MiniMax M3 在 AMD Instinct MI355X 上的固定负载服务进度](https://vllm.ai/blog-assets/figures/2026-09-10-minimax-m3-mi355x/hero-fixed-workload-progress.svg)

MiniMax M3 在 AMD Instinct MI355X 上的固定负载服务进度

*图 1. 8K 输入、1K 输出下的标准解码。请只比较同一行内的各点。MXFP8 全程保持 TP4/EP1；最后一个 MXFP4 点从 TP4 移到了 TP2，因此它展示的是更高的部署密度，而不是固定拓扑下的加速。*

每个检查点都是累积结果，可能打包了多项改动。下面的章节用隔离的 PR 测量来解释各个单独的优化。

## 一次解码步，五个问题

这项优化工作遵循一条熟悉的工作流：估计主要开销，进行测量，批处理重复的工作，预计算不变量，当叶子内核的画像趋于平缓时向栈的更上层推进。

MiniMax M3 有 60 个解码层，其中 57 个使用稀疏 MoE 和稀疏注意力。对于一段 1K token 的回复，每层很小的开销在一个请求中可能出现数万次。这使得下面五个问题非常有用：

1. 到达这个 rank 的是什么本地形状？
2. 哪些工作在每一层或每个 token 上重复出现？
3. 移动的是哪些字节？能否改为只移动元数据？
4. 预期的快速路径是否真的执行了，并且使用了预期的计算方式？
5. 当内核不再占主导时，是哪个队列在变长？

![MiniMax M3 解码关键路径与 P/D 系统边界](https://vllm.ai/blog-assets/figures/2026-09-10-minimax-m3-mi355x/optimization-map.svg)

MiniMax M3 解码关键路径与 P/D 系统边界

*图 2. 上方的泳道按执行顺序跟踪一个稀疏解码层；AR 标记注意力与 MoE 之后的张量并行集合通信。下方泳道把同样的推理应用到 P/D：先验证 KV 交接，再在请求等待的地方增加容量。*

本文余下部分将用代码和基准测试证据来回答这些问题。

## 1. 到达这个 rank 的是什么形状？

模型架构图展示的是全局维度，但内核实际运行在经过张量并行、头复制、填充和 token 路由之后的本地 M、N、K 上。在 TP8 下，MiniMax M3 的 64 个查询头切分为每个 rank 8 个，而它的 4 个 KV 头和 4 个 index 头则复制为每个 rank 1 个。因此融合 QKV 投影看到的是本地 N=1536——而不是全局 N 除以 8。

预填充和解码到达时的 M 也不同。预填充一次处理大量 token；解码往往只有几行。[vLLM #45725](https://github.com/vllm-project/vllm/pull/45725) 把启动器拆分为大 M 和小 M 两种模式，将 TP8 下 8K/1K 输出的吞吐量提升了 7.8%–9.4%。[vLLM #46117](https://github.com/vllm-project/vllm/pull/46117) 随后基于完整的本地形状来选择分块（tile）：更窄的 N 分块在解码中暴露出更多可并行的工作，而更大的 K 步长减少了循环迭代次数。当 M 本身已提供足够并行度时，预填充则使用更宽的分块。

![TP 切分如何改变本地 GEMM 形状与分块方案](https://vllm.ai/blog-assets/figures/2026-09-10-minimax-m3-mi355x/local-shape-tile-selection.svg)

TP 切分如何改变本地 GEMM 形状与分块方案

*图 3. TP 切分和头复制决定本地 N；服务阶段决定 M。启动器针对每个 rank 实际运行的形状来选择分块。*

同一个 PR 还重排了分组 MoE 程序，让相邻程序可以从 GPU 缓存复用激活值行和专家权重分块，而不必再次从 HBM 获取。在其 TP4 端到端测试中，这些改动合计带来了 1.08×–1.46× 的收益。收益在低并发下最大，因为此时原始启动方式的并行工作量最少。

本地形状还决定哪些后端是合法的。最终 MXFP8 配方所用的 AITER 稀疏注意力路径要求每个 TP rank 恰好一个 KV 头。TP4 满足这一条件；TP2 则使用 vLLM 的 Triton 回退路径。因此，改变 TP 改变的不只是集合通信的规模，还可能改变整个算子图。

也不存在一个在所有情况下都最快的后端。[InferenceX #2003](https://github.com/SemiAnalysisAI/InferenceX/pull/2003) 最初在整个扫描中都选择了模拟（emulated）线性后端。[InferenceX #2187](https://github.com/SemiAnalysisAI/InferenceX/pull/2187) 中后续的测量表明，原生 MXFP8 线性在低和中并发下更快，而模拟方案只在长输入、高并发的运行中占优。稀疏分页注意力也有类似的交叉点。最终配方只在 8K 输入、并发 64 及以上时才同时启用这两者。

这就是第一条可复用的经验：要针对实际运行的形状分布来调优和分发。"预填充""解码"或"TP4"都只是一个标签。

## 2. 哪些工作在重复？

第一个容易被忽视的重复开销是启动开销。Day-0 配方是以即时执行（eager）方式运行的。[InferenceX #1754](https://github.com/SemiAnalysisAI/InferenceX/pull/1754) 和 [#1755](https://github.com/SemiAnalysisAI/InferenceX/pull/1755) 为标准服务和 EAGLE3 服务启用了图执行（graph execution）。这项改动是累积历史的一部分，尽管已发布的结果并未单独隔离出它的收益。

更大的结构性收益来自共享专家（shared expert）。最初，每个稀疏 MoE 层都把它当作一个单独的稠密 MLP 来运行：gate/up 投影、激活函数、down 投影、中间存储和加法。这些计算是必需的，但单独一条执行路径不是。

[vLLM #46545](https://github.com/vllm-project/vllm/pull/46545) 把共享专家追加到路由专家表中，并让每个 token 都选中它。分组 GEMM 随后一并处理路由专家和共享专家。这移除了启动和中间数据流量，却没有移除模型的 FLOPs。输出吞吐量在并发 1 下提升了 30.2%，在并发 128 下提升了 5.6%。收益递减本身就是有用的证据：这正是启动开销被摊销时的样子。

![MiniMax M3 共享专家在融合前后的执行方式](https://vllm.ai/blog-assets/figures/2026-09-10-minimax-m3-mi355x/shared-expert-fusion.svg)

MiniMax M3 共享专家在融合前后的执行方式

*图 4. 融合把共享专家作为一个被每个 token 选中的槽位追加进去。此后路由专家和共享专家使用相同的分组 GEMM，在保留模型计算的同时移除了单独的 MLP 路径及其中间数据流量。*

[vLLM #46474](https://github.com/vllm-project/vllm/pull/46474) 在 AITER 路径上应用了同样的思路。[vLLM #46184](https://github.com/vllm-project/vllm/pull/46184)（背后是 [AITER #3811](https://github.com/ROCm/aiter/pull/3811)）还把 MXFP8 权重和 scale 的重排移到了模型加载阶段。AITER 携带了从 1 到 32,768 token、并针对 TP4 和 TP8 所产生的本地中间宽度调优过的 MoE 配置。布局转换只发生一次；服务循环直接消费准备好的形式。

投机解码提供了批处理重复工作的一个干净示例。最初的 MSA 索引器为每个投机 token 启动一个 workgroup。[vLLM #45743](https://github.com/vllm-project/vllm/pull/45743) 改为每个请求启动一个 workgroup，把所有草稿位置放在一起处理，并复用 key 的加载。它还移除了一处正数 score 缩放，因为只有 top-k 的顺序才重要，把每个 score 乘以同一个正常数不会改变这个顺序。

索引内核的改进幅度高达 48.9%，而在 PR 测试中端到端服务大约提升了 3.3%。这个差距正是 Amdahl 定律在起作用：一个内核层面的大幅提升可以是真实的，但未必构成应用整体关键路径的全部。

## 3. 移动的是哪些字节？

稀疏注意力减少了注意力计算，但增加了一个控制平面：对 score 分块、选择 top-k、把逻辑块映射到物理页，并把这份元数据传给注意力内核。

[vLLM #47269](https://github.com/vllm-project/vllm/pull/47269) 观察到相邻的稀疏层往往选中几乎相同的块。启用 index 共享后，由一个层计算 top-k 决策，后续层复用它。TPOT 均值在并发 1 下下降约 10%，在高并发下下降约 4%。

跳过选择器只完成了一半工作。融合投影仍然会生成 index Q/K 值、做归一化、应用 RoPE 并写入 index 缓存。[vLLM #47287](https://github.com/vllm-project/vllm/pull/47287) 让复用决策对该融合内核可见，于是未被使用的生产分支会在编译时被消除。

同一个 PR 还在一个布局不匹配的鸿沟之上集成了 AITER 稀疏分页注意力。MiniMax M3 选择的是逻辑上的 128-token 块；而 AITER 消费的是 16-token 页。vLLM 没有复制 KV 数据，而是把每个被选中的块 ID 展开成 8 个页 ID，并构建一张紧凑的页表。KV 缓存留在原地不动。这相当于服务场景中的"传递视图而不复制容器"。

![vLLM 如何在不复制 KV 数据的情况下把 MiniMax M3 稀疏块适配为 AITER 页](https://vllm.ai/blog-assets/figures/2026-09-10-minimax-m3-mi355x/sparse-page-adapter.svg)

vLLM 如何在不复制 KV 数据的情况下把 MiniMax M3 稀疏块适配为 AITER 页

*图 5. 每个被选中的 128-token 块先解析到一个物理块，再展开为 8 个 16-token 的页表项。AITER 通过现有 KV 分配的一个视图来读取它们；重建的只有表本身。*

在其隔离的 A/B 测试中，该 PR 在 TP4、并发 256 下将输出吞吐量提升了 6.93%（MXFP4）和 5.56%（MXFP8）。

这里有一条重要的基准测试边界。InferenceX 的固定 8K/1K 评审规则排除了跨层 index 复用，因为它减少了模型架构本身的工作量。固定形状配方使用页适配器，但不使用 top-k 复用；AgentX 则在其工作负载规则下启用复用。我们不会把某条曲线没有运行过的工作算到固定约定曲线头上。

量化让"移动哪些字节？"这个问题变得更加重要。把三个平面区分开会很有帮助：

| 字节平面 | MiniMax M3 示例 | 需要证明什么 |
| --- | --- | --- |
| 权重与激活值 | MXFP8 或 MXFP4 GEMM/MoE | 打包方式、scale、激活值计算、后端布局 |
| 持久状态 | FP8 KV 与稀疏 index 缓存 | 平台 dtype、页布局、读/写几何结构 |
| 通信 | 量化的 all-reduce 或 KV 传输 | 资格条件、所选编解码器、所有权、完成状态 |

这三个平面各自有独立的分发与正确性契约。"这个模型是 MXFP4 的"并不能告诉我们 KV 的 dtype 或集合通信路径。

## 4. 快速路径执行了吗——结果正确吗？

这次审计修正了本文中的一个说法。我们最初以为一个约 1.5 MB 的解码集合通信用的是 INT4 QuickReduce，但现有证据并不能证明这一点。

[InferenceX #2104](https://github.com/SemiAnalysisAI/InferenceX/pull/2104) 配置了 INT4 和一个 256 KB 的 **codec** 阈值，但没有配置 QuickReduce 单独的资格阈值。对 BF16、TP4 而言，[内置表（固定提交版本）](https://github.com/vllm-project/vllm/blob/69715823df89b11ee684b84066390cbb9092d5c1/vllm/distributed/device_communicators/quick_all_reduce.py#L49-L61)要求 INT4 达到 16 MB。因此这个 1.5 MB 的集合通信根本走不到 codec 选择那一步；256 KB 阈值只有在 QuickReduce 具备资格之后才会被查询。

![QuickReduce 的配置、资格判定、codec 选择与执行门槛](https://vllm.ai/blog-assets/figures/2026-09-10-minimax-m3-mi355x/quickreduce-dispatch-gates.svg)

QuickReduce 的配置、资格判定、codec 选择与执行门槛

*图 6. QuickReduce 在选择 FP 还是 INT4 之前会先检查资格。此处该集合通信低于内置资格门槛，因此仅有配置无法证明它执行过。*

现有日志只能证明配置了 INT4，而不能证明 QuickReduce 内核运行过。因此我们把 #2104 视为一个累积的镜像与配方检查点，而不把它的曲线归功于 INT4 all-reduce。

这个区分可以推广：

```
configured  !=  eligible  !=  executed
```

在把收益归因给某个后端之前，先看分发追踪（dispatch trace）或性能分析器。

正确性也需要同样的纪律。三个例子分别抓到了不同类型的失效契约：

- [vLLM #45794](https://github.com/vllm-project/vllm/pull/45794) 把打包的 MXFP4 Q/K/V 和 gate/up 检查点张量映射到正确的融合参数切片中，并把 MiniMax M3 的 SwiGLU-OAI 参数传入 MoE。
- [vLLM #45720](https://github.com/vllm-project/vllm/pull/45720) 修复了 FNUZ ROCm 设备上的 FP8 KV 视图。在 MI300X 上，未打补丁的路径在 GSM8K 上严格匹配得分只有 0.0099；打过补丁的路径得分 0.9575。这是一个正确性修复，并不是宣称的 MI355X 提速。
- [vLLM #47158](https://github.com/vllm-project/vllm/pull/47158) 修复了传给 AITER 的专家并行掩码。有 bug 的路径余弦相似度只有 0.527；修正后的路径达到 1.0，并恢复了 GSM8K 准确率。

后两个例子并不能解释 TP4/EP1 的亮眼曲线；它们暴露的是其他配置必须满足的契约。对于性能工作来说，"通过"应该意味着三件事：输出正确、预期路径确实执行了、以及在相同约定下端到端指标有所改善。

## EAGLE3 增加了第二条解码循环

EAGLE3 引入了草稿模型、多 token 验证、接受行为，以及第二套注意力元数据。它不能被当作标准曲线上多加一个开关来对待。

[vLLM #45546](https://github.com/vllm-project/vllm/pull/45546) 把 AMD 模型接入了 EAGLE3 接口。随后 [vLLM #45564](https://github.com/vllm-project/vllm/pull/45564) 修复了一个隐蔽的缓存键 bug：目标模型和草稿模型使用的查询头数量不同，因此不能仅仅因为它们的注意力后端和 KV 类型相同，就共享同一个注意力组构建器。

这是一条通用的缓存规则：凡是会影响缓存对象的因素，都必须包含在键里。

在上述请求级 index 批处理之后，[InferenceX #2107](https://github.com/SemiAnalysisAI/InferenceX/pull/2107) 发现目标模型的注意力后端设置并没有配置到草稿模型上。把 TRITON\_ATTN 固定写在投机解码配置内部，避免了草稿模型落入较慢的回退路径。

最后，[vLLM #47984](https://github.com/vllm-project/vllm/pull/47984) 把 AITER 稀疏分页注意力从单 token 解码扩展到了多 token 验证。它把每个展平后的查询行映射回其所属请求与本地投机位置，复用现有的页表构建器，并保留了单 token 快速路径。其 TP4 测试在不明显改变接受率的情况下，将输出吞吐量提升了 8.32%（MXFP4）和 7.90%（MXFP8）。

这些工作共同带来了前文单独列出的 EAGLE3 结果：并发 128 下 682.4 output tok/s/GPU。

## 5. 哪个队列在变长？

预填充/解码分离部署把瓶颈移到了单个进程之上。在调整 worker 数量之前，必须先保证 KV 边界是正确的。

最初的 MoRIIO 路径假设第一层的 KV 布局代表了所有层。而 MiniMax M3 同时有分离的 K/V 张量、交错的 K/V 张量，以及只含 key 的 index 缓存。传输正常完成，吞吐量看起来也很健康，但 GSM8K 掉到了约 0.0008——输出的基本就是一堆乱码 token。

修复分三步完成：

- [vLLM #46039](https://github.com/vllm-project/vllm/pull/46039) 逐层推导出传输几何结构和字节偏移。
- [vLLM #46290](https://github.com/vllm-project/vllm/pull/46290) 统计每个请求实际排入计划的写入数量，在 forward 结束后封存该计数，并且只有在这些写入全部完成后才释放缓冲区。
- [vLLM #46332](https://github.com/vllm-project/vllm/pull/46332) 增加了异构 TP 的 rank 映射和确认消息的扇入聚合。当预填充为 TP4、解码为 TP8 时，两个解码 rank 可能消费同一个生产者 rank 的输出，因此必须等两者都确认之后，对应块才能被复用。

到这时，worker 分配才值得去调。

![两份独立调优的 MiniMax M3 P/D 系统画像](https://vllm.ai/blog-assets/figures/2026-09-10-minimax-m3-mi355x/pd-system-profiles.svg)

两份独立调优的 MiniMax M3 P/D 系统画像

*图 7. 两个 8K/1K 的 P/D 工作点。两端使用的 GPU 数量和并发不同，因此这是系统演进，而非受控对比下的提速。*

第一份公开画像使用一个 TP8 预填充 worker 和一个 TP8 解码 worker。在并发 1024 下它达到了 2,084.6 total tok/s/GPU，但 TTFT 中位数高达 223.20 秒（[InferenceX #1762](https://github.com/SemiAnalysisAI/InferenceX/pull/1762)）。吞吐量数字并不能让这套系统可用；真正说明问题的是提示队列。

[InferenceX #2144](https://github.com/SemiAnalysisAI/InferenceX/pull/2144) 把所有 worker 都改为 TP4，让它们与更快的单机配方保持同步，并搜索预填充/解码比例。对 8K/1K 而言，由两个 TP4 预填充 worker 喂给一个 TP4 解码 worker。在并发 512 下，结果达到 6,370.5 total tok/s/GPU，TTFT 中位数 1.32 秒。

TPOT 均值从 31.26 毫秒变成了 54.60 毫秒。这并不矛盾：增加的预填充容量清空了准入队列，而所选的解码工作点让每条活跃序列的生成变慢了。P/D 至少有两个延迟目标，两个都要公布。

一次高并发运行还耗尽了容器的文件描述符上限。调高 `nofile` 修复了 TCP 失败。当画像推进到栈的更上层时，一个操作系统层面的限制可能和 GEMM 分块一样真实。

## AgentX 展示了下一个瓶颈

固定 8K/1K 非常适合受控对比。而智能体编程流量并不是固定形状的：它有很长的多轮轨迹、可复用的前缀、不规则的输出，以及一个 KV 容量拐点。

[InferenceX #2487](https://github.com/SemiAnalysisAI/InferenceX/pull/2487) 是 MI355X 上 MiniMax M3 的第一个 AgentX 结果点，包含 MXFP4、EAGLE3-GQA、前缀缓存、可选的 TP 分片 LMCache，以及跨层 index 复用。吞吐量回放使用预先提交的合成接受长度，确保被比较的系统执行相同的投机工作量；评测则使用真实的目标模型验证。

在[这次成功的运行](https://github.com/SemiAnalysisAI/InferenceX/actions/runs/31558297538)中，TP4 在并发 28 下交付了 **127.4 output tok/s/GPU**、**509.5 total output tok/s**、**0.582 mean QPS**、**645 ms p50 TTFT** 和 **41.3 ms p50 TPOT**。

这些服务指标让这个结果不只是又一个分数：

- 理论前缀缓存命中率：96.7%
- 实际达成的 GPU 缓存命中率：92.1%
- GPU KV 缓存使用率：88.5%
- GPU KV 容量：6,264,960 tokens

到了这一步，再写一个 GEMM 内核并不自动就是最好的下一个项目。4.6 个百分点的缓存实现率差距和接近容量的工作点，把注意力引向前缀对齐、准入与驱逐策略、调度以及卸载。这些只是从一次运行得到的观察，还算不上优化结论。我们将把这个结果点用作下一轮智能体优化的基线。

## 给下一个模型的检查清单

当一条新的服务路径跑通了但还不够快时：

1. 记录切分后的本地形状直方图，包括被复制的头和路由 token 数量。
2. 估算重复次数：用层数、输出 token 数和活跃请求数去乘每层的工作量。
3. 区分字节平面：计算张量、持久状态和通信。
4. 为每条快速路径记录其资格条件，并验证它确实执行了。
5. 在每个性能关卡旁边都放一个正确性关卡。
6. 每次取得收益后重新做性能分析。如果叶子内核不再占主导，就去检查队列、所有权、缓存容量和操作系统限制。

这就是这项工作的主要成果。MiniMax M3 变快了，因为团队不断变换提问的层级——从分块，到重复路径，到稀疏元数据，再到分布式状态，最后到工作负载队列。
