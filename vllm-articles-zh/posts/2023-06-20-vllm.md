# vLLM：用 PagedAttention 实现简单、快速、低成本的 LLM 服务

> 原文：[vLLM: Easy, Fast, and Cheap LLM Serving with PagedAttention](https://vllm.ai/blog/2023-06-20-vllm) · vLLM 博客

作者：Woosuk Kwon\*、Zhuohan Li\*、Siyuan Zhuang、Ying Sheng、Lianmin Zheng、Cody Yu、Joey Gonzalez、Hao Zhang 和 Ion Stoica（\* 共同一作）

[#性能](https://vllm.ai/blog/tags/performance)

[**GitHub**](https://github.com/vllm-project/vllm) | [**文档**](https://vllm.readthedocs.io/en/latest/) | [**论文**](https://arxiv.org/pdf/2309.06180.pdf)

LLM 有望从根本上改变我们在所有行业使用 AI 的方式。然而，实际部署这些模型充满挑战，即使使用昂贵的硬件，速度也可能慢得出人意料。今天，我们很高兴地推出 vLLM——一个用于快速 LLM 推理与服务的开源库。vLLM 采用 **PagedAttention**，这是我们的新注意力算法，能够高效管理注意力的键（key）和值（value）。配备 PagedAttention 的 vLLM 重新定义了 LLM 服务的最先进水平（SOTA）：与 HuggingFace Transformers 相比，它可提供高达 24x 的吞吐量提升，且不需要对模型架构做任何改动。

vLLM 由 UC Berkeley 开发，并在过去两个月中部署于 [Chatbot Arena 和 Vicuna Demo](https://chat.lmsys.org)。它是让 LLM 服务变得可负担的核心技术，即使对 LMSYS 这样计算资源有限的小型研究团队也是如此。现在就可以通过一条命令在我们的 [GitHub 仓库](https://github.com/vllm-project/vllm)试用 vLLM。

### 超越最先进水平的性能

我们将 vLLM 的吞吐量与最受欢迎的 LLM 库 [HuggingFace Transformers (HF)](https://huggingface.co/docs/transformers/main_classes/text_generation) 以及此前的最先进方案 [HuggingFace Text Generation Inference (TGI)](https://github.com/huggingface/text-generation-inference) 进行了比较。我们在两种设置下进行评估：NVIDIA A10G GPU 上的 LLaMA-7B，以及 NVIDIA A100 GPU（40GB）上的 LLaMA-13B。请求的输入/输出长度从 ShareGPT 数据集中采样。在实验中，vLLM 相比 HF 实现了高达 **24x** 的吞吐量提升，相比 TGI 实现了高达 **3.5x** 的吞吐量提升。

![](https://vllm.ai/blog-assets/figures/perf_a100_n1_light.png)![](https://vllm.ai/blog-assets/figures/perf_a100_n1_dark.png)![](https://vllm.ai/blog-assets/figures/perf_a10g_n1_light.png)![](https://vllm.ai/blog-assets/figures/perf_a10g_n1_dark.png)
每个请求请求*一个输出补全*时的服务吞吐量。vLLM 比 HF 高 14x - 24x，比 TGI 高 2.2x - 2.5x。

![](https://vllm.ai/blog-assets/figures/perf_a100_n3_light.png)![](https://vllm.ai/blog-assets/figures/perf_a100_n3_dark.png)![](https://vllm.ai/blog-assets/figures/perf_a10g_n3_light.png)![](https://vllm.ai/blog-assets/figures/perf_a10g_n3_dark.png)
每个请求请求*三个并行输出补全*时的服务吞吐量。vLLM 比 HF 高 8.5x - 15x，比 TGI 高 3.3x - 3.5x。

### 秘密武器：PagedAttention

在 vLLM 中，我们发现 LLM 服务的性能瓶颈在于内存。在自回归解码过程中，输入 LLM 的所有 token 都会产生各自的注意力键（key）与值（value）张量，这些张量会保存在 GPU 内存中，用于生成后续 token。这些缓存的键值张量通常被称为 KV 缓存（KV cache）。KV 缓存具有以下特点：

- *大：* 在 LLaMA-13B 中，单个序列最多可占用 1.7GB。
- *动态：* 其大小取决于序列长度，而序列长度高度可变且不可预测。
  因此，高效管理 KV 缓存是一项重大挑战。我们发现，现有系统由于内存碎片和过度预留而浪费了 **60% – 80%** 的内存。

为了解决这个问题，我们提出了 **PagedAttention**，这是一种受操作系统中虚拟内存和分页的经典思想启发的注意力算法。与传统注意力算法不同，PagedAttention 允许将连续的键和值存储在不连续的内存空间中。具体而言，PagedAttention 将每个序列的 KV 缓存划分为块（block），每个块包含固定数量 token 的键和值。在注意力计算过程中，PagedAttention 内核会高效地识别并获取这些块。

![](https://vllm.ai/blog-assets/figures/annimation0.gif)
*PagedAttention：* KV 缓存被划分为块。这些块在内存空间中不必连续。

由于块在内存中不必连续，我们可以像操作系统的虚拟内存那样以更灵活的方式管理键和值：可以把块想象成页（page），把 token 想象成字节（byte），把序列想象成进程（process）。序列的连续*逻辑块*通过块表（block table）映射到不连续的*物理块*。物理块随着新 token 的生成按需分配。

![](https://vllm.ai/blog-assets/figures/annimation1.gif)
使用 PagedAttention 时一个请求的生成过程示例。

在 PagedAttention 中，内存浪费只发生在序列的最后一个块。在实践中，这带来了近乎最优的内存使用，浪费不足 4%。内存效率的提升带来了巨大收益：它允许系统将更多序列一起批处理，提高 GPU 利用率，从而显著提升吞吐量，正如上面的性能结果所示。

PagedAttention 还有另一个关键优势：高效的内存共享。例如，在*并行采样*中，多个输出序列从同一个提示（prompt）生成。在这种情况下，提示的计算和内存可以在这些输出序列之间共享。

![](https://vllm.ai/blog-assets/figures/annimation2.gif)
并行采样示例。

PagedAttention 通过其块表自然地实现了内存共享。类似于进程共享物理页的方式，PagedAttention 中不同的序列可以通过将各自的逻辑块映射到同一物理块来共享这些块。为确保共享安全，PagedAttention 会跟踪物理块的引用计数，并实现*写时复制*（Copy-on-Write）机制。

![](https://vllm.ai/blog-assets/figures/annimation3.gif)
对一个请求采样多个输出的生成过程示例。

PagedAttention 的内存共享大幅降低了复杂采样算法（如并行采样和束搜索）的内存开销，将其内存使用最多减少 55%。这可以转化为高达 2.2x 的吞吐量提升，使这类采样方法在 LLM 服务中变得切实可行。

PagedAttention 是 vLLM 的核心技术。vLLM 是我们的 LLM 推理与服务引擎，支持多种模型，兼具高性能和易用接口。欲了解 vLLM 和 PagedAttention 的更多技术细节，请访问我们的 [GitHub 仓库](https://github.com/vllm-project/vllm)，并敬请期待我们的论文。

### LMSYS Vicuna 和 Chatbot Arena 背后的无名英雄

今年四月，[LMSYS](https://lmsys.org) 开发了广受欢迎的 Vicuna 聊天模型并向公众开放。此后，Vicuna 一直在 [Chatbot Arena](https://arena.lmsys.org/) 上为数百万用户提供服务。最初，LMSYS FastChat 采用基于 HF Transformers 的[服务后端](https://github.com/lm-sys/FastChat/blob/main/fastchat/serve/model_worker.py)来支持聊天演示。随着演示越来越受欢迎，峰值流量增长了好几倍，使 HF 后端成为显著的瓶颈。LMSYS 与 vLLM 团队通力合作，很快完成了 FastChat-vLLM 集成，将 vLLM 用作[新的后端](https://github.com/lm-sys/FastChat/blob/main/fastchat/serve/vllm_worker.py)，以支撑不断增长的需求（流量最高增至 5x）。在 LMSYS 早期的[内部微基准测试](https://github.com/lm-sys/FastChat/blob/main/fastchat/serve/test_throughput.py)中，vLLM 服务后端**比最初的 HF 后端实现高达 30x 的吞吐量提升。**

自四月中旬以来，Vicuna、Koala 和 LLaMA 等最受欢迎的模型都已成功通过 FastChat-vLLM 集成提供服务——以 FastChat 作为多模型聊天服务前端、vLLM 作为推理后端，LMSYS 得以利用有限数量的校方资助 GPU，以*高吞吐量*和*低延迟*将 Vicuna 服务给数百万用户。LMSYS 正在把 vLLM 的使用扩展到更多模型，包括 Databricks Dolly、LAION 的 OpenAsssiant 以及 Stability AI 的 stableLM。[对更多模型的支持](https://vllm.readthedocs.io/en/latest/models/supported_models.html)正在开发中，即将推出。

![](https://vllm.ai/blog-assets/figures/lmsys_traffic.png)
四月至五月间，Chatbot Arena 中由 FastChat-vLLM 集成服务的请求数。事实上，Chatbot Arena 超过一半的请求都使用 vLLM 作为推理后端。

对 vLLM 的采用也显著降低了运营成本。借助 vLLM，LMSYS 将服务上述流量所用的 GPU 数量削减了 50%。vLLM 每天平均处理 3 万个请求，峰值达 6 万个，这充分展示了 vLLM 的稳健性。

### 开始使用 vLLM

使用以下命令安装 vLLM（更多内容请参阅我们的[安装指南](https://docs.vllm.ai/en/latest/getting_started/installation.html)）：

```
$ pip install vllm
```

vLLM 既可用于离线推理，也可用于在线服务。要使用 vLLM 进行离线推理，你可以在 Python 脚本中导入 vLLM 并使用 `LLM` 类：

```
from vllm import LLM

prompts = ["Hello, my name is", "The capital of France is"]  # Sample prompts.
llm = LLM(model="lmsys/vicuna-7b-v1.3")  # Create an LLM.
outputs = llm.generate(prompts)  # Generate texts from the prompts.
```

要使用 vLLM 进行在线服务，你可以通过以下命令启动一个与 OpenAI API 兼容的服务器：

```
$ python -m vllm.entrypoints.openai.api_server --model lmsys/vicuna-7b-v1.3
```

你可以使用与 OpenAI API 相同的格式查询该服务器：

```
$ curl http://localhost:8000/v1/completions \
    -H "Content-Type: application/json" \
    -d '{
        "model": "lmsys/vicuna-7b-v1.3",
        "prompt": "San Francisco is a",
        "max_tokens": 7,
        "temperature": 0
    }'
```

欲了解 vLLM 的更多用法，请查阅[快速入门指南](https://vllm.readthedocs.io/en/latest/getting_started/quickstart.html)。
