# vLLM Semantic Router v0.3 Themis：从信号到有状态的生产级路由

> 原文：[vLLM Semantic Router v0.3 Themis: From Signals to Stateful Production Routing](https://vllm.ai/blog/2026-06-05-v0.3-vllm-sr-themis-release) · vLLM 博客

作者：vLLM Semantic Router 团队

[#生态系统](https://vllm.ai/blog/tags/ecosystem)

vLLM Semantic Router v0.3，代号 **Themis**，是一个让语义路由变得有状态、可观测，并真正面向生产环境应对实际 AI 流量的版本。

前两个版本做好了铺垫。Iris 让路由决策变得可组合。Athena 重建了模型基础，并将路由器扩展到记忆、安全、模型选择、长上下文信号处理、OpenClaw 编排以及 AMD ROCm 部署。Themis 迈出了下一步：它让这些能力更易运维、更易检查，也更难被误用。

自 v0.2.0 以来，项目在路由器核心、CLI、仪表盘、DSL、Kubernetes、协议兼容性、模型选择、安全、回放以及发布就绪等方面新增了超过 **350 次提交**。v0.3 的最大价值不是某个单一功能，而是这些部分汇聚成一个稳定的契约：

> 信号变为投影，投影支撑决策，决策选择算法，算法选定模型。

这一契约如今在路由器、CLI、仪表盘、DSL、Helm chart 以及面向运维人员的部署界面中保持一致。

## 为什么叫 Themis？

Themis 代表秩序、规则与判断。这正是这个版本应有的象征。

语义路由只有在生产环境中能让运维人员回答一些基本问题时才有用：

- 哪些信号被触发了？
- 哪个决策匹配了？
- 哪个模型选择算法被运行了？
- 选中了哪个模型？
- 哪个安全或回放插件改变了路径？
- 哪个配置版本产生了这个行为？
- 同一份策略能否在本地、通过仪表盘、在 Kubernetes 中部署，而不变成三套不同的系统？

Themis 要做的就是把这些问题变得明确。v0.3 保留了 Athena 的雄心，但为运行时、API 表面和运维工作流加上了更严格的边界。

![图 2：发布价值不是某个孤立的功能，而是稳定契约、检查、运维、服务、长上下文与验证之间的连接。](https://vllm.ai/blog-assets/figures/2026-06-01-v0.3-vllm-sr-themis-release/release-value-map.png)

## v0.3 Themis 有哪些新特性？

### 1. 规范的 v0.3 配置契约

Themis 最重要的变化是新的规范配置形态：

```
version: v0.3
listeners: []
providers: {}
routing: {}
global: {}
```

在 v0.3 之前，用户可能在本地 Docker、仪表盘生成的配置、Helm values、CRD、示例与旧文档之间遇到相互重叠的布局。Themis 把 `config.yaml` 确立为稳态文件，并让系统在所有地方都围绕同一个顶层架构对齐。

这次清理还移除了 `vllm-sr init`。新流程更简单：

- 在空目录中使用 `vllm-sr serve`，走仪表盘优先的设置流程
- 直接编写规范的 `config.yaml`，走 YAML 优先的工作流
- 使用 `vllm-sr config migrate --config old-config.yaml` 迁移旧文件
- 使用 `vllm-sr config import` 导入受支持的提供商清单

这是一个破坏性变更，但对一个 1.0 之前的路由器来说，这正是应有的破坏性变更：更少的配置方言、更清晰的所有权，以及更耐用的公共契约。

配置路径在边缘处也更严格了。v0.3 会对未知的 YAML 字段发出警告，让规范配置加载保持测试覆盖，把 Python CLI 模型对齐到现代 Pydantic 配置，并更明确地把分类器资产置于门控之下。目标很简单：拼写错误和过时的配置形态应该在变成无声的路由漂移之前被捕获。

### 2. 信号、投影、决策、算法、模型

Themis 让路由器的思维模型更加明确：

| 层 | 负责的内容 |
| --- | --- |
| 信号 | 从请求、响应、工具、语言、领域、上下文、模态、身份或安全分类器中提取证据 |
| 投影 | 将原始证据规范化为策略可直接使用的概念，如验证、紧急程度、反馈或均衡 |
| 决策 | 按优先级和可解释的条件匹配命名路由策略 |
| 算法 | 在匹配到的决策内部从候选模型中做出选择 |
| 模型 | 通过选定的后端别名或提供商来服务请求 |

这一点很重要，因为 v0.3 引入了足够的路由智能，隐式行为已经不再可接受。路由器现在拥有更丰富的信号族、投影追踪、先进的模型选择算法以及响应侧插件。Themis 让这些表面保持可编程，同时避免路由策略沦为隐藏的应用代码。

当前的信号目录已经足够宽泛，不仅能描述最新的用户提示，还能描述安全态势、工具循环、用户角色、多模态意图、对话形态、结构化事件以及可回放的知识库证据：

| 信号族 | 捕获的内容 | 典型用途 |
| --- | --- | --- |
| `authz` | 来自用户或群组上下文的角色与主体绑定 | 高级/管理员路由、策略门控模型 |
| `complexity` | 来自学习型或组合型信号的推理难度 | 升级处理困难综合与多步推理 |
| `context` | 估计的上下文窗口需求 | 长上下文路由、成本与延迟决策 |
| `conversation` | 消息与工具循环形态 | 多轮、活跃工具调用、开发者消息、大量非用户上下文 |
| `domain` | 学习型或配置型领域标签 | 商业、法律、健康、计算机科学路由 |
| `embedding` | 与候选锚点的语义相似度，包括文本/图像/音频查询模态 | 支持意图、临床意图、多模态请求匹配 |
| `event` | 结构化事件元数据、严重程度、动作代码与时间紧迫性 | 事故、支付、审计或运维事件路由 |
| `fact_check` | 请求是否需要事实核查 | 升级处理法律、医学或事实性声明 |
| `jailbreak` | 提示注入与越狱证据，包括历史感知扫描 | 安全路由与响应侧安全护栏 |
| `kb` | 知识库分组或标签匹配 | 隐私策略、隔离、前沿推理、本地标准路由 |
| `keyword` | 字面、模糊、BM25 或 n-gram 关键词证据 | 快速路由守卫、紧急关键词、敏感词 |
| `language` | 检测到的语言及可配置置信度 | 语言区域感知路由与多语言模型选择 |
| `modality` | AR、扩散或混合文本/图像执行需求 | 选择纯文本、图像生成或多模态路径 |
| `pii` | 敏感实体策略，包括历史感知扫描 | 脱敏、拒绝/放行决策、隐私路由 |
| `preference` | 用户风格或行为偏好示例 | 简洁回答、详细回答、领域特定风格 |
| `reask` | 重复或改写的用户轮次 | 检测此前轮次中可能出现的不满 |
| `structure` | 正则、计数、序列或密度特征 | 多问题、编号工作流、格式繁重的提示 |
| `user_feedback` | 用户表示答案错误或需要澄清 | 从不满中恢复或路由到更强模型 |

投影输出以 `type: projection` 引用，但它们是派生的路由表面，而不是又一种原始信号族。这个区分很重要：信号提取证据，而投影把证据转化为命名的策略区间，例如 `support_fast`、`support_balanced` 或 `support_escalated`。

v0.3 的主要新增不只是更多的信号名称。这个版本让信号可组合：`conversation` 信号可以检测智能体请求形态；`event` 信号可以路由运维载荷；embedding 规则可以查询非文本模态；投影输出可以把嘈杂的证据转化为策略可直接使用的区间。

仪表盘拓扑视图、DSL 编辑器、编译器/反编译器以及运行时指标都已更新，可以理解这些 v0.3 表面，而不是默默丢弃或隐藏它们。

策略编写表面也更强了。路由 DSL 新增了冲突检测、`SIGNAL_GROUP`、`TEST` 和 `TIER` 编写构造、自然语言到 DSL 的流水线、`EMIT retention` 以及动态工具检索支持。这对生产团队很重要，因为 Themis 策略不只是被解析的 YAML；它们是带有测试、保留输出和更安全生成路径的、可审查的路由程序。

### 3. 会话感知的智能体路由

Themis 包含了**会话感知智能体路由（Session-Aware Agentic Routing，SAAR）**的首个生产就绪版本。

单轮路由只问：

> 哪个模型应该处理这条提示？

智能体路由还必须问：

> 此刻在这个会话中切换模型是否安全？

SAAR 增加了由路由器持有的会话记忆、围绕工具循环的硬锁、提供商状态可移植性检查、空闲与决策漂移重置边界、切换成本权衡，以及可回放的诊断。它保留正常的 Semantic Router 流水线，但在模型选择外层包上会话连续性规则。

这对编程智能体和长程工具循环尤为重要。工具结果通常应该返回给请求该工具的模型。提供商管理的续接 id 不应被发送到另一个物理后端。一个长时间的"热"会话不应仅仅因为最新的用户消息很短就丢掉前缀局部性。

Themis 把这些约束纳入模型选择策略，而不是让每个应用自己去重新发现它们。

![图 5：SAAR 通过组合路由器持有的会话记忆、硬锁、可移植性检查、切换成本权衡与回放诊断，让多轮智能体会话保持稳定。](https://vllm.ai/blog-assets/figures/2026-06-01-v0.3-vllm-sr-themis-release/session-aware-routing.png)

图 5：SAAR 通过组合路由器持有的会话记忆、硬锁、可移植性检查、切换成本权衡与回放诊断，让多轮智能体会话保持稳定。

关键的设计选择是 SAAR 并不取代语义路由。它在模型选择的"最后一公里"外加上一层有状态的守护：

- `conversation` 信号识别多轮形态、活跃工具调用、开发者消息以及大量非用户上下文。
- `session_aware` 选择在权衡质量差距、切换余量、驻留偏好、前缀局部性和剩余轮次先验之后，评估切换模型是否值得。
- 硬锁阻止在活跃工具循环或提供商状态续接期间进行不安全的切换。
- 路由器持有的记忆可以检索和存储路由本地的事实、偏好与上下文，而无需暴露一个单独的会话状态 DSL。
- 回放记录保留会话保持、切换或重置的原因。

路由器记忆是会话感知选择的持久补充。记忆插件可以在用户或会话范围下保留事实、偏好与检索到的上下文；`session_aware` 随之就能避免把每一轮都当作孤立请求。在实践中，这意味着智能体可以保持有用的连续性，而不必把每个请求永远钉在最昂贵的模型上。

参考策略刻意采用朴素的普通 YAML 形式：

```
routing:
  signals:
    conversation:
      - name: active_tool_use
        feature:
          type: count
          source:
            type: assistant_tool_cycle
        predicate:
          gte: 1

  decisions:
    - name: agentic_session_route
      rules:
        operator: AND
        conditions:
          - type: conversation
            name: active_tool_use
      algorithm:
        type: session_aware
        session_aware:
          base_method: hybrid
          tool_loop_hard_lock: true
          context_portability_hard_lock: true
          prefix_cache_weight: 0.20
          handoff_penalty_weight: 1.0
      plugins:
        - type: memory
          configuration:
            enabled: true
            retrieval_limit: 6
            auto_store: true
            hybrid_search: true
```

这就是 Themis 对智能体工作负载最重要的部分：路由器现在可以推理连续性，而不只是做分类。

### 4. 投影把证据转化为策略

信号是原始证据。投影则是 Themis 把这些证据转化为命名的、稳定的策略概念的地方。

没有投影时，复杂的策略必须在许多决策里重复底层信号细节：确切的 embedding 规则名、复杂度阈值、上下文边界和知识库分数。有了投影，路由器只需计算一次原始证据，派生出可复用的输出（如 `support_fast` 或 `support_escalated`），然后让决策基于这个派生概念来路由。

Themis 支持三种核心投影模式：

- `partitions`（分区）从互斥族中选出一个胜者，例如相互竞争的支持意图。
- `scores`（分数）把声明的信号或知识库指标组合成一个连续值。
- `mappings`（映射）通过校准后的阈值把这些值转化为策略区间。

对于需要多个派生输出的策略，v0.3 还增加了 `multi_emit` 投影映射。这让单个投影步骤可以发出多个命名路由概念，同时在回放中仍保持可追溯性。

![图 6：投影把嘈杂的信号证据转化为决策可以直接引用的命名输出。](https://vllm.ai/blog-assets/figures/2026-06-01-v0.3-vllm-sr-themis-release/projection-layer.png)

图 6：投影把嘈杂的信号证据转化为决策可以直接引用的命名输出。

一个紧凑的示例如下：

```
routing:
  signals:
    embeddings:
      - name: technical_support
        threshold: 0.75
        aggregation_method: max
        candidates:
          - installation guide
          - troubleshooting steps
      - name: account_management
        threshold: 0.72
        aggregation_method: any
        candidates:
          - password reset
          - billing information
    context:
      - name: long_context
        min_tokens: 32K
        max_tokens: 256K

  projections:
    partitions:
      - name: support_intents
        semantics: exclusive
        members:
          - technical_support
          - account_management
        default: technical_support
    scores:
      - name: request_difficulty
        method: weighted_sum
        inputs:
          - type: embedding
            name: technical_support
            weight: 0.18
            value_source: confidence
          - type: context
            name: long_context
            weight: 0.18
    mappings:
      - name: request_band
        source: request_difficulty
        method: threshold_bands
        outputs:
          - name: support_fast
            lte: 0.20
          - name: support_escalated
            gte: 0.45

  decisions:
    - name: escalated_support_route
      rules:
        operator: AND
        conditions:
          - type: projection
            name: support_escalated
```

投影追踪也会与回放记录一起存储，因此仪表盘不仅能解释哪个信号被触发，还能解释哪个派生策略区间导致了最终路由。

### 5. 协议兼容性成为发布表面

v0.3 把路由器的兼容性边界扩展到基础 OpenAI Chat Completions 之外。

本周期的协议工作包括：

- 通过内部请求信封提供原生 Anthropic `/v1/messages` 入口
- Anthropic 流式输出并转换为 OpenAI SSE
- 自定义 Anthropic 上游路由与工具调用支持
- 非流式路径的出站 Anthropic 响应输出
- 从请求路径与头部进行协议检测
- session-id 镜像与头部透传控制
- 用响应头说明协议转换何时有损
- Responses API 工具追踪保真度与对齐 OpenAI SDK 的消息处理
- OpenAI reasoning-effort 修改修复
- identity 编码的上游响应，避免透明解压缩带来的意外
- 更强的 Responses API 状态与持久化路径

目标不是让每个提供商看起来一模一样。目标是让转换显式、可观测且足够安全，使 `auto` 这样的逻辑路由模型可以坐在多个提供商协议之前，而不会让运维人员感到意外。

### 6. 仪表盘成为运维控制台

Themis 仪表盘不只是配置编辑器。

v0.3 周期收紧了首次运行设置流程、拓扑图、基于回放的洞察、日志、状态页、评估流程、认证行为与模型清单界面。运维人员可以在不离开仪表盘的情况下导入配置档案、验证、激活、发送测试提示、检查信号路径、读取路由器日志并核对回放记录。

![图 7：仪表盘成为实用的运维控制台，覆盖设置、拓扑检查、日志、playground 测试、回放与模型健康。](https://vllm.ai/blog-assets/figures/2026-06-01-v0.3-vllm-sr-themis-release/operator-console.png)

图 7：仪表盘成为实用的运维控制台，覆盖设置、拓扑检查、日志、playground 测试、回放与模型健康。

值得注意的仪表盘改进包括：

- 内置路由模式与缺失模型补全
- 展示匹配信号、投影、决策与模型的拓扑试运行路径
- 通过仪表盘代理进行路由器回放与聚合洞察
- 自然语言 DSL 构建器与评估流程修复
- playground 中的文件附件
- 认证服务无法初始化时的 fail-closed 行为
- 带有影子（shadow）、激活与回滚状态的策略版本生命周期
- 针对用户提供的 fetch/open-web 请求的更安全日志与 URL 脱敏
- 多语言内容的 UTF-8 安全显示处理
- 更精简的生产路由外壳与更小的后端运行时依赖
- 面向仪表盘的模型列表与状态界面

结果是更好的本地与远程运维工作流：首次运行用设置模式，策略检查用拓扑，运维用日志/状态，真实流量用洞察。

### 7. CLI 与部署更加可预测

Themis 还强化了 `vllm-sr` 作为受支持的运维界面。

CLI 现在拥有更清晰的运行时边界和更多实用的命令：

```
vllm-sr serve
vllm-sr serve --algorithm latency_aware
vllm-sr serve --algorithm session_aware
vllm-sr serve --platform amd
vllm-sr serve --platform nvidia
vllm-sr chat
vllm-sr eval
vllm-sr model list
vllm-sr config migrate --config old-config.yaml
```

本地 `vllm-sr serve` 仍是在 Linux、macOS 与 WSL2 上基于 Docker 的工作流。AMD ROCm 仍是经过发布验证的 GPU 路径，而 `--platform nvidia` 为已经配置好 NVIDIA 容器运行时的用户增加了本地 NVIDIA Docker 直通（passthrough）的便利。原生 Windows Docker 服务现在会被明确的支持信息拒绝，而不是稍后以不那么明显的方式失败。

CLI 还增加了更好的检查与冒烟测试命令。`vllm-sr model list` 列出已配置的模型清单，`vllm-sr chat` 提供一次性补全路径，`vllm-sr eval` 调用路由器评估端点，`VLLM_SR_DNS` 则允许本地容器在企业或实验室网络要求时加入自定义 DNS 环境。

在 Kubernetes 上，v0.3 对齐了 Helm、发布默认值、OpenShift 部署修复、多重 `IntelligentRoute` 调和行为、CRD 模态契约、可选的 Gateway API `HTTPRoute` 入口以及 AgentGateway 安装指南。在发布运维方面，Themis 还放弃了模糊的 `latest` 假设，转向明确的产物契约、升级与回滚文档以及发布检查。

### 8. 安全、回放、记忆与检索更可信

Athena 把这些能力中的许多带进了路由器。Themis 把它们加固。

关键的运行时修复与改进现在分为三组：

**回放与可观测性**

- 修复路由器回放 PostgreSQL 插入的正确性，让仪表盘洞察不会一直默默为空
- 投影追踪随回放记录存储，以获得更好的可解释性
- 响应侧越狱检测与回放路径的收紧

**存储与检索**

- Qdrant 向量搜索 provider 支持
- Valkey 缓存、向量存储与记忆后端支持，包括 TLS 与搜索模块预检查
- 更贴合真实本地与 Kubernetes 部署的 Redis 与 Responses API 存储默认值
- 混合缓存重建预分配的缩减
- 流式 Redis 语义缓存的正确性以及有界的流式分块内存行为
- 用常数时间的基于链表的实现替换 O(N) 的缓存 LRU 读取路径
- BM25 与 n-gram 分类缓存，避免放大的重复工作
- 混合 HNSW 入口点传播修复
- 在回放、缓存、记忆与向量存储路径之间共享 Milvus 生命周期处理

**运行时与安全加固**

- 跨此前用户轮次的历史感知 PII 与越狱信号扫描
- 针对上一模型填充的模型切换门修复
- extproc 后台路径中的 goroutine panic 恢复
- 选择随机性中的并发竞态修复
- 针对配置回滚版本的路径穿越防护
- 覆盖 Python、Go、Rust 与前端表面的依赖安全更新

这是本次发布中不那么夺目的部分，但恰恰是 Themis 的意义所在：让系统在真实流量、长提示、回放存储与运维驱动的配置变更下更加安全。

### 9. 长上下文路由变得更便宜

Themis 增加了三个重要的长上下文控制。

首先，上下文 token 估计现在可以从观测到的响应用量中学习在线校准比例，因此在无法精确分词时，上下文敏感路由仍能改进。回退行为保持保守，但路由器可以随时间适应真实流量。

其次，原生 mmBERT embedding 路径现在能限制内存，而不会把长输入变成静默截断问题。针对长输入内存问题的 #2007 原生绑定修复改为按查询分块处理注意力，而不是为整个序列物化一个稠密注意力张量。这既让长上下文信号对路由器保持可用，又让该绑定在更大提示下可用。

![图 8：长上下文路径通过分块处理 mmBERT 注意力工作，既保留信号又限制原生内存。](https://vllm.ai/blog-assets/figures/2026-06-01-v0.3-vllm-sr-themis-release/long-context-binding.png)

图 8：长上下文路径通过分块处理 mmBERT 注意力工作，既保留信号又限制原生内存。

第三，提示压缩成为信号提取的命名 profile 表面：

| profile | 预期用途 |
| --- | --- |
| `default` | 面向通用路由的均衡压缩 |
| `coding` | 保留类代码与重实现的句子 |
| `medical` | 保留临床相关细节 |
| `security` | 保留安全与策略证据 |
| `multi_turn` | 保留对话连续性 |

压缩路径刻意只作用于信号评估。原始用户提示仍会发给选定的服务模型，除非决策自有的插件明确改变它。这一隔离让路由优化不会悄悄改写用户意图。

### 10. 硬件后端路径拓宽

Themis 把路由器自有模型执行的故事拓展到默认本地路径之外。

拓宽后的版图区分了四条路径：NVIDIA CUDA 与 AMD ROCm 用于被服务的 vLLM 后端，Intel OpenVINO 用于路由器自有的分类器与 embedding 推理，CPU/本地执行用于开发与冒烟测试。

在 Intel 基础设施上，v0.3 为 Semantic Router 增加了初步的 **OpenVINO 绑定**。新绑定提供 ModernBERT 序列分类、token 分类与 embedding 推理的原生 C++ 与 Go 集成，并带有比较 OpenVINO 与 Candle 在分类器和 embedding 工作负载上行为的基准入口。

这是一个后端与绑定里程碑，而非全面的"生产对等"声明。它为贡献者和硬件伙伴提供了一条具体路径，可以在 Intel OpenVINO 上验证 Semantic Router 的内部分类器与 embedding 模型，同时保持与 Themis 其余部分相同的路由契约。

![图 9：Themis 拓宽了硬件后端版图，同时在 NVIDIA CUDA、AMD ROCm、Intel OpenVINO 与 CPU/本地路径上保持同一个路由控制平面。](https://vllm.ai/blog-assets/figures/2026-06-01-v0.3-vllm-sr-themis-release/hardware-backend-paths.png)

## 开始使用

对于 macOS 或 Linux：

```
curl -fsSL https://vllm-semantic-router.com/install.sh | bash
```

手动安装：

```
pip install vllm-sr==0.3.0
vllm-sr serve
```

如果当前目录中没有 `config.yaml`，`vllm-sr serve` 会以设置模式启动仪表盘。对 YAML 优先的用户，可以直接创建规范的 v0.3 配置，或迁移旧文件：

```
vllm-sr config migrate --config old-config.yaml
vllm-sr serve --config config.yaml
```

对于 AMD ROCm：

```
vllm-sr serve --platform amd
```

对于本地 NVIDIA Docker 直通：

```
vllm-sr serve --platform nvidia
```

对于 Kubernetes：

```
helm install semantic-router oci://ghcr.io/vllm-project/charts/semantic-router
```

## 展望未来：v0.4 Hermes

下一个版本的代号是 **Hermes**。

Themis 让契约稳定到可以运维。Hermes 应当让路由器改进更快、评估更容易、在真实工作负载下适配更安全。Hermes 的核心目标是**自我改进的路由器**。这个循环是刻意设计的：以 GPU 规模自动研究路由器性能，用路由器评估调优 DSL 配方，再把验证过的证据反馈进代码库与编码器模型微调。最有价值的工作是：

- **自我改进的路由器作为 Hermes 核心目标**：打通 GPU 规模性能研究、DSL 配方调优与代码库及编码器模型微调之间的闭环。每一个生成的变更仍必须可审查、可回放、有版本并可安全回滚。
- **SAAR 作为智能体路由层**：继续收紧模型切换经济性、工具循环连续性、提供商状态可移植性、回放诊断与路由器记忆集成。
- **评估作为发布门槛**：构建系统级与信号级评估，让每个信号、投影、算法、插件与仪表盘路径都能在发布前对照代表性流量进行回放。
- **CLI 优先设计**：确保每项 Semantic Router 操作都能通过 `vllm-sr` 闭环，包括配置编写、迁移、服务、检查、评估、回放、策略生命周期、仪表盘导入/导出与发布冒烟测试。
- **更好的路由器自有模型**：提升路由器自身所用模型的准确率与延迟，包括 embedding、分类器、多模态与安全信号模型。
- **更有用的信号**：增加更丰富的请求、响应、工具、模态、身份、新鲜度、延迟、成本与运行时健康信号，同时不让 DSL 变成应用代码。
- **运维调试闭环**：让假设分析（what-if）路由、策略回放、评估驱动的调优与追踪对比成为一等仪表盘工作流。
