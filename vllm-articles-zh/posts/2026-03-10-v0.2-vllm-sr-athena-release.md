# vLLM Semantic Router v0.2 Athena：ClawOS、模型焕新与系统大脑

> 原文：[vLLM Semantic Router v0.2 Athena: ClawOS, Model Refresh, and the System Brain](https://vllm.ai/blog/2026-03-10-v0.2-vllm-sr-athena-release) · vLLM 博客

作者：vLLM Semantic Router 团队

[#生态](https://vllm.ai/blog/tags/ecosystem)

自 v0.1 Iris 以来，vLLM Semantic Router 实现了一次大跨越。在一个发布周期内，这个项目重建了模型栈，把路由能力扩展到安全、语义缓存、记忆、检索与长上下文信号处理，并开始迈向更宏大的目标：让语义路由成为模型组合（mixture-of-models）与多智能体部署的系统大脑。

Athena 正是这一转变的集中体现。v0.2 带来了彻底的模型焕新和强大得多的路由运行时，而其中最大胆的新尝试之一是 **ClawOS**：一个实验性的操作层，Semantic Router 可以在其中通过路由、记忆、安全与对话驱动的团队管理来编排多个 OpenClaw 系统。如果说 Iris 建立了用户与模型之间的桥梁，那么 Athena 则开始把这座桥变成模型团队的操作系统界面。

![](https://vllm.ai/blog-assets/figures/semantic-router/athena-0.png)

## 为什么叫 Athena？

在希腊神话中，Athena 代表智慧、策略与严谨的技艺。这一象征恰好契合本次发布。v0.2 不只是让请求路由得更快或增加更多插件，而是要让语义路由变得**更有战略**：学会选择哪个模型，协调 OpenClaw worker 团队，跨轮次记住重要信息，通过更好的工具呈现决策，并把一个强大的运行时变成团队真正可以运营的东西。

![](https://vllm.ai/blog-assets/figures/semantic-router/athena-1.png)

## v0.2 Athena 有哪些新特性？

### 1. 彻底的模型焕新重建 MoM 基础

Athena 中影响最深远的改动位于 UI 与路由 DSL 之下：**模型栈被重建了**。

Athena 现在以一个新的长上下文多语言基座 [`mmbert-embed-32k-2d-matryoshka`](https://huggingface.co/llm-semantic-router/mmbert-embed-32k-2d-matryoshka) 为中心，并以 [`mom-multilingual-class`](https://huggingface.co/collections/llm-semantic-router/mom-multilingual-class) 集合收纳一个新的分类器家族。在实践中，这意味着路由器的嵌入、意图、越狱、PII、反馈、事实核查等相关分类器模块将迁移到共享的 mmBERT 衍生基座上，取代此前较为分散的基座模型格局。同样重要的是，这个焕新后的家族如今对齐到了同一条 ONNX + Flash Attention 加速路径上。

Athena 还引入了 [`multi-modal-embed-small`](https://huggingface.co/llm-semantic-router/multi-modal-embed-small)——一个独立的嵌入模型，把**文本、图像和音频放进同一个 384 维共享空间**。它专为真正的跨模态检索而设计：系统可以用文本搜图像、用文字描述找音频，并在三种模态之间对齐内容。同样重要的是，它的部署方式保持简单：用 `transformers` 和 `torch` 即可加载，无需自定义运行时依赖。

![](https://vllm.ai/blog-assets/figures/semantic-router/athena-1b.png)

这个新的模型层带来三项立竿见影的变化：

- **Multi-Modal Embed Small** 为 Athena 提供了一个紧凑的跨模态原语：**约 120M 参数**，共享 **384 维**空间，**图像-文本对齐能力强**，支持 2D Matryoshka 控制，推理目标低于 100ms，报告的**音频-文本检索 R@1 = 36.4%**
- **mmBERT-Embed-32K-2D-Matryoshka** 为路由器提供了一个可用于生产的多语言长上下文骨干：**32K 上下文**、**1800+ 种语言**、**307M 参数**、**STS 80.5**、**768 维 -> 256 维**截断且**质量保留约 99%**，以及 **22 层 -> 6 层**早退（early exit）带来约 **3.3x** 的加速
- **mom-multilingual-class** 集合把这个骨干变成一个连贯的分类器家族，让长上下文多语言路由与安全任务共享同一套基座模型假设和同一条 ONNX 加速路径

在本次发布时，`mom-multilingual-class` 集合覆盖五项核心路由与安全任务，每个任务都同时提供 **merged** 与 **LoRA** 两种形式：

| 任务 | Merged 模型 | LoRA 模型 |
| --- | --- | --- |
| 意图 | `mmbert32k-intent-classifier-merged` | `mmbert32k-intent-classifier-lora` |
| 越狱 | `mmbert32k-jailbreak-detector-merged` | `mmbert32k-jailbreak-detector-lora` |
| PII | `mmbert32k-pii-detector-merged` | `mmbert32k-pii-detector-lora` |
| 事实核查 | `mmbert32k-factcheck-classifier-merged` | `mmbert32k-factcheck-classifier-lora` |
| 反馈 | `mmbert32k-feedback-detector-merged` | `mmbert32k-feedback-detector-lora` |

这个分类器集合只是焕新的一部分。Athena 还为它配备了新的嵌入骨干、新的多模态嵌入模型，以及一条强大得多的生产加速路径。从更高的层面看，v0.2 的模型焕新如下：

| 新基座 | Athena 带来的变化 |
| --- | --- |
| `multi-modal-embed-small` | 在一个 384 维语义空间中统一文本-图像-音频嵌入 |
| `mmbert-embed-32k-2d-matryoshka` | 32K 上下文、1800+ 种语言、2D Matryoshka 运行时控制 |
| ONNX + CK Flash Attention | 焕新后的模型栈在生产环境中实质变快，而不再只是纸面上更新 |

![](https://vllm.ai/blog-assets/figures/semantic-router/athena-2.png)

这一点之所以重要，是因为 Athena 的模型焕新同时也是运行时焕新。ONNX 路径、ROCm 支持与 CK Flash Attention 工作，把新基座变成了一个可部署的延迟故事。

在 **AMD Instinct MI300X** 上，沿着真实的路由路径 **Envoy (:8801) -> ext\_proc -> SR (:50051)** 进行的三方基准测试中，端到端延迟曲线发生了戏剧性变化：

| 请求大小 | ONNX + GPU 平均 | ONNX + CPU 平均 | Candle + CPU 平均 |
| --- | --- | --- | --- |
| 约 500 token | 22 ms | 853 ms | 1053 ms |
| 约 2000 token | 31 ms | 1814 ms | 1805 ms |
| 约 8000 token | 128 ms | 4796 ms | 1830 ms |

在信号层面，收益更加明显。对于**领域提取（domain extraction）**，ONNX+GPU 在约 500 token 时耗时 **10.2 ms**，约 2000 token 时 **16.3 ms**，约 8000 token 时 **36.1 ms**；相比之下，ONNX+CPU 分别为 **630.4 / 833.3 / 743.9 ms**，Candle+CPU 分别为 **849.0 / 1304.9 / 1311.5 ms**。对于 **PII 提取**，ONNX+GPU 在相同长度下分别达到 **8.4 ms**、**19.0 ms** 和 **118.8 ms**，而 ONNX+CPU 为 **729.5 / 1781.8 / 4783.9 ms**，Candle+CPU 为 **854.2 / 1299.8 / 1327.8 ms**。

Flash Attention 的表现同样重要。在 MI300X 上同时加载三个分类器时，旧的 SDPA 路径撞上了内存墙，而新的 CK Flash Attention 路径仍在继续扩展：

| 序列长度 | SDPA | CK Flash Attention | 结果 |
| --- | --- | --- | --- |
| 4096 | 167 ms | 51 ms | **快 3.3x** |
| 8192 | OOM | 105 ms | SDPA 失败，FA 正常 |
| 16384 | OOM | 259 ms | FA 在 16K 下正常 |
| 32768 | OOM | 756 ms | FA 达到完整 32K |

尤为关键的是 FA 支持**如何**实现。在 `onnx-binding/ort-ck-flash-attn` 下，Athena 新增了一个独立的 **ONNX Runtime 自定义算子库**，在 ROCm 上注册 `com.ck::CKFlashAttention` 并直接调用 AMD Composable Kernel 的分块 FMHA 内核。随后，一个图重写步骤逐层重写 mmBERT 的 ONNX 图，把稠密的 SDPA 注意力子图替换为单个 CK Flash Attention 节点。

这一步重写正是系统层面收益的主要来源。重写后的图不再物化稠密的 **`[1, 1, S, S]`** 注意力掩码，而是从 `attention_mask` 推导出轻量的 **`[B, 1, 1, S]`** 填充偏置，并把滑动窗口设置直接传入内核。局部注意力层使用 CK 内置的窗口参数，全局注意力层则切回无窗口限制的全注意力。换句话说，Athena 的 FA 路径不只是一个后端开关，而是一套**模型感知的 ONNX 重写加上专门为长上下文 mmBERT 推理构建的自定义 ROCm 内核路径**。

在更重的负载下，CK Flash Attention 仍然完成了 **20 个并发的 32K-token 请求**，中位数 **9872 ms**、p95 **14862 ms**，且**零 OOM**，并在验证查询上保持了完全一致的分类结果。这就是为什么模型重建被放在本次发布的最前面：Athena 不只是在路由器周围添加功能，而是更换了它底下的计算基础。

### 2. 模型选择成为一等路由原语

Athena 最大的飞跃在于：**模型选择不再只是路线图上的一项**。它现在已是系统的具体组成部分，涵盖**可训练的 ML 选择器**与**高级运行时选择策略**。

同样重要的是，Athena 明确了它在**路由管线中的位置**。模型选择**不会**取代信号提取或决策匹配。系统先提取信号，再评估决策，只有在**某个决策匹配之后**，才由**该决策专属的算法**在该决策的 `modelRefs` 中进行选择。换句话说，模型选择成为从"**该请求属于这个决策**"到"**应由哪个具体模型来服务它**"之间的最后一个战略步骤。

这一点很重要，因为现代 LLM 系统不仅要决定一个请求**是否**属于某条路由，还要在质量、延迟、成本与专业化的动态权衡之下决定由**哪个模型**来处理它。Athena 让这一战略层变得可见、可编程。

| 家族 | 方法 | 作用 |
| --- | --- | --- |
| 基于 ML | **KNN** | 查找相似的历史查询，由邻近样本投票选出最佳模型。 |
| 基于 ML | **KMeans** | 对请求聚类，并依据簇级别的质量与效率模式分配模型。 |
| 基于 ML | **SVM** | 使用 RBF 分类器学习模型偏好之间的非线性决策边界。 |
| 基于 ML | **MLP** | 使用神经路由器从嵌入预测最佳模型，并通过 Candle 高效推理。 |
| 高级 | **Static** | 当可预测性比适应性更重要时，使用固定的默认模型。 |
| 高级 | **Latency-Aware** | 当延迟预算占主导时，根据 TPOT 与 TTFT 百分位数据选择最快的候选。 |
| 高级 | **Elo** | 通过 Bradley-Terry 风格的评分更新，从用户反馈与成对偏好中学习。 |
| 高级 | **RouterDC** | 用双对比嵌入相似度将查询与模型描述匹配。 |
| 高级 | **AutoMix** | 从更便宜的模型起步，基于自我验证逐级升级，以平衡成本与质量。 |
| 高级 | **Hybrid** | 以可配置权重混合质量、相似度、成本等多种方法。 |
| 高级 | **Thompson Sampling** | 在线平衡探索与利用，让路由在服务生产流量的同时持续学习。 |
| 高级 | **GMTRouter** | 基于图的路由，从多轮交互历史中个性化模型选择。 |
| 高级 | **Router-R1** | 在选择下游模型之前，用外部路由器模型对请求进行推理。 |

![](https://vllm.ai/blog-assets/figures/semantic-router/athena-3.png)

Athena 还为这些算法补上了运营层：面向 ML 训练与配置生成的设置向导支持、CLI 与运行时集成、指标、端到端覆盖，以及仪表板中支持人在回路中持续改进的 Elo 反馈界面。

### 3. ClawOS 让 Semantic Router 成为 OpenClaw 的操作层

Athena 最大胆的新尝试之一是 **ClawOS**：一个实验性操作层，让 Semantic Router 能够编排多个 OpenClaw 系统。

在仓库内部，二者的区分很直接：

- **OpenClaw** 是底层的智能体平台
- **ClawOS** 是 Athena 在 Semantic Router 中构建于其上的编排与运营体验

v0.2 的重要之处在于，这已经是可触摸的现实，而不只是概念。通过内置的 MCP 工具与房间式聊天工作流，用户可以用自然语言对话启动不同的 OpenClaw 团队与 worker，在共享房间内实时协调它们，并从一个地方观察整个多 claw 系统的运行时状态。

这项功能的意义不只是给仪表板再添一个页面，而是探索 **Semantic Router 如何为多个 OpenClaw 系统提供动力**——把路由智能、记忆、安全与团队控制连接到同一个界面。

仪表板突出展示了我们希望带入这一形态的能力：

- 面向成本-质量模型选择的**智能路由**
- 抵御越狱、PII 泄露与幻觉风险的**安全护栏**
- 支持长周期、多步骤执行的**分层记忆存储**
- 智能体之间的**知识共享**
- 在同一共享编排层中支持多智能体运作的**隔离与团队管理**

![](https://vllm.ai/blog-assets/figures/semantic-router/athena-7.png)

Athena 增加了让这一实验变得具体的第一批产品界面：

- **自然语言 MCP 控制**，用户可以直接通过聊天启动并管理不同的 OpenClaw 团队与 worker
- 支持明确的"领导-worker"组成的**团队支持**
- **共享房间聊天**，团队可以在同一房间内实时交流、协调与执行
- **领导-worker 协作**，领导 claw 可以把 worker claw 作为一个运营单元来协调
- 直接在仪表板中**供应 worker**
- **运行时健康、团队组成与状态视图**
- 用于更安全的演示与公开测试式部署的**只读房间聊天**
- 共享运行时支持，让 Claw worker 与路由器共处同一运营环境

ClawOS 的重要性不在于它是一个完成的平台，而在于它是对一个更大问题的早期实验性回答：当语义路由不只是选择一个模型，而是**为整个构建在 OpenClaw 之上的多智能体操作层提供动力**时，会发生什么？

### 4. 记忆、RAG 与响应状态进入核心运行时

Athena 还把**状态**变成了核心关注点，而非附带功能。

在记忆侧，本次发布新增了**带 Milvus 存储的智能体记忆**、**混合记忆搜索**、**记忆评分**、**Llama Stack 向量后端**，以及用于监控与告警的**记忆指标**。在响应侧，Athena 深化了 **OpenAI Responses API** 支持，加入 **Redis 持久化**、对话链覆盖与更强的集成测试。在调试侧，Athena 推出了 **Router Replay**，具备**可插拔存储后端**、**按决策隔离**与仪表板可视化。

这项**混合搜索**工作值得更明确地点出。Athena 把检索变成一个融合搜索问题，而不是只查向量。在向量存储与记忆栈中，路由器现在可以组合**向量相似度**、**BM25** 与 **n-gram** 文本匹配，同时支持**加权融合**与 **RRF**。内存后端可以原生运行混合搜索，而 Milvus 类后端可以采用更宽的候选拉取，再在向量结果之上做**混合重排**。

其重要性与 BM25 和 n-gram 在信号层中的意义相同：检索变得更不易脆断。语义相似度仍是主干，但精确词项、稀疏相关性与容忍错字的匹配现在也能影响最终排序。Athena 还把这一点延伸到端到端 RAG 覆盖，包括加权混合搜索、RRF 模式，以及向量存储测试路径中可调的 **BM25 / n-gram** 参数。

![](https://vllm.ai/blog-assets/figures/semantic-router/athena-4.png)

同样重要的是，记忆层变得更加可信：

- 降低记忆注入攻击风险的 **MINJA 防御**
- 记忆存储之前的**响应级越狱门控**
- **跨模型缓存共享**与改进的缓存更新路径
- **按需 RAG**与面向向量存储的摄取工作流

Athena 把路由从一个无状态的决策点，变成了一个能够记忆、检索、验证与重放的系统。

### 5. 信号更丰富、更快、更安全

Iris 引入了"信号-决策"架构。Athena 对它进行了大幅扩展。

从高层看，信号层在三个方向上变得更宽：它对请求的理解更多，它支持更多确定性与语义匹配路径，它把更多这种智能以可复用的具名信号形式暴露在路由系统内部。

| 信号层面 | Athena 新增了什么 | 为什么重要 |
| --- | --- | --- |
| 核心请求理解 | **语言**、**延迟**、**上下文**与**复杂度感知**信号，包括少样本复杂度变体 | 路由器在评估决策时能考虑的不只是主题。 |
| 控制与路由上下文 | **模态**与 **authz** 信号 | 路由可以在管线更早处依据媒体意图与访问约束分支。 |
| 反馈回路 | **反馈**与**偏好**分类器 | 用户侧信号成为一等路由输入，而非附带元数据。 |
| 语义匹配路径 | **多模态嵌入支持**、**软嵌入规则**与 **HNSW 加速** | 语义匹配变得更宽更快，尤其是随着检索界面增多。 |
| 确定性快速路径 | 用于关键词路由的 **BM25**、**n-gram 模糊匹配**与 **regex** | 可审计的规则路径保持可解释性，但在真实流量中不再那么脆弱。 |
| 运行时置信度层 | 贯穿信号评估的**动态置信度评分** | 决策可以利用更丰富的信号质量，而不只是二值匹配。 |

安全也更靠近主信号路径，不再只是停留在旁路、仅靠插件做后处理：

| 安全层面 | Athena 新增了什么 | 为什么重要 |
| --- | --- | --- |
| 越狱检测 | 提升为并行信号，同时支持基于分类器与**对比式多轮**检测 | 路由器既能捕捉明显的单轮攻击，也能捕捉对话中逐步升级的攻击。 |
| PII 检测 | 并行信号处理，加上扩展的策略与披露控制 | 敏感数据处理成为同一路由与执行层的一部分。 |
| 工具安全 | 用于工具过滤的**置信度门控重排** | 工具感知的工作流可以保持选择性，而无需为每个边界情况硬编码。 |
| 幻觉处理 | 更灵活的**多级**响应处理 | 系统可以更细腻地警告、标注或呈现响应风险。 |

![](https://vllm.ai/blog-assets/figures/semantic-router/athena-5.png)

这里有一个重要细节：**关键词路由不再局限于精确的字面匹配**。Athena 用三种互补方法强化了关键词信号路径：

- **BM25** 用于在较大关键词集合上做主题式路由，天然的 TF-IDF 风格加权有助于浮现正确的确定性规则
- **n-gram 匹配**用于容忍错字的路由，使近似输入仍能触发预期规则，而不必立即回退到更重的模型路径
- **regex** 用于团队需要对合规与结构化检测做精确模式控制的场景

这一点很重要，因为它升级了路由器最可解释的原语之一。快速路径依然**可审计且确定**，但在真实流量中不再那么脆弱。带有噪声措辞、部分重叠或拼写错误的查询，不再仅仅因为不是完美的字符串匹配就错过关键词层。

Athena 不只是更广，也更快。信号并行化、更快的提取路径、更好的嵌入查找行为，以及更强的关键词与安全路径，都帮助运行时在不牺牲可解释性的前提下扩展。

### 6. 基于 NLP 的提示压缩成为一等长上下文原语

Athena 还引入了一个新的长上下文运行时原语：**信号提取前基于 NLP 的提示压缩**。

| 压缩层面 | Athena 做了什么 | 为什么重要 |
| --- | --- | --- |
| 压缩方法 | 使用 **TextRank**、**位置加权**、**TF-IDF** 与**新颖性评分** | 可以在不增加一次 LLM 调用的前提下压缩长提示。 |
| 运行时位置 | 仅针对**信号提取**压缩文本 | 原始请求仍发送给服务模型，路由优化不会改写实际的用户提示。 |
| 安全保留 | 让 `skip_signals` 使**越狱**与 **PII** 检测仍作用于原始文本 | 敏感分类器可以在需要时保留全保真检查。 |
| 端到端路径 | 与 **Envoy STREAMED body 模式**及快速 JSON 处理协同 | 压缩路径转化为可度量的生产延迟收益，而不只是更漂亮的架构图。 |

![](https://vllm.ai/blog-assets/figures/semantic-router/athena-5b.png)

Athena 现在不必让完整提示流经每个信号分类器，而是可以用这条纯 NLP 流水线**在信号提取之前压缩长提示**。压缩后的文本只用于信号提取。原始提示仍上游发送给实际的服务模型，而默认需要全保真输入的信号（如**越狱**与 **PII**）可以通过 `skip_signals` 继续读取未压缩的原始文本。

这也与围绕 **Envoy STREAMED body 模式**的运行时工作相关。在仓库的 MI300X 缓冲与流式对比基准中，STREAMED 路径结合快速 JSON 处理、半流式分块交付与提示压缩，把约 16K token 时的端到端延迟从 **143 ms 降到 103 ms**；当为信号路径把提示从 **16K 压缩到 512 token** 时，**越狱信号提取从 127 ms 降到 10 ms**。

关键在于，这不是一个加装在旁边的 LLM 摘要器，而是直接插入信号路径的确定性 NLP 流水线，让长上下文分类在成本上实质性下降，同时不掩盖路由器做出决策的过程。

### 7. 可编程的神经-符号配置语言

Athena 另一个标志性主题是：路由策略变成了一门真正的**语言**，而不只是一堆 YAML 片段。在项目白皮书中，我们把它称为**可编程神经-符号配置语言（Programmable Neural-Symbolic Configuration Language）**：一种带类型的配置语言，充当路由推理引擎的指令集，将神经信号提取与符号决策评估结合在一起。

这一框架之所以重要，是因为它改变了"路由配置"的含义。Athena 不再把路由器设置当作手工编辑的基础设施 YAML，而是把它推向一个**程序合成问题**：给定自然语言的路由规范，生成一个有效的路由程序。白皮书明确提出了这一点，认为这门语言的功能完备性使**基于 LLM 的编程智能体能够从自然语言规范合成路由策略**。

Athena 落地了这一想法的实践基础：

- 一个**完整的 DSL 编译器**
- 一个**可视化构建器**
- 更丰富的信号与决策仪表板 CRUD 流程
- 各配置界面之间更好的收敛
- 面向 Kubernetes 环境更强的部署期转换路径

![](https://vllm.ai/blog-assets/figures/semantic-router/athena-6.png)

这弥合了以下几者之间长期存在的鸿沟：

- 路由器使用的运行时配置
- 仪表板中暴露的编写界面
- CLI 驱动的配置工作流
- Kubernetes 环境中的部署期表示

Athena 还包含一些修复，让这种语言驱动的编写闭环在实践中更可靠，包括改进的配置重载行为，以及部署重载后 apiserver 分类服务的刷新。

简而言之，Athena 让语义路由不仅可执行，而且更容易**编程**、**检视**与**演进**。更重要的是，它让路由编写对人类和编程智能体都变得清晰可读：路由器变成你可以编译、校验、往返转换，并越来越多地可以交给智能体去编写的东西。

### 8. 零配置上手改变首次运行体验

Athena 还带来了项目迄今最重要的 UX 改进之一：**安装与首次运行设置现在构成一条连续流程**。你不再需要为了把系统跑起来而从一份预定义配置开始。

在 macOS 与 Linux 上，新的一行式安装器现在几乎无需手动设置，就能带用户从安装走到仪表板：

```
curl -fsSL https://vllm-semantic-router.com/install.sh | bash
```

该安装器会检测 Python，把 `vllm-sr` 安装到隔离的本地环境中，把启动器写入 `~/.local/bin/vllm-sr`，为你准备用于本地服务的 Docker 或 Podman（除非你选择退出），然后自动运行第一次 `vllm-sr serve`。在可能的情况下它还会打开仪表板；在远程机器上，它会打印访问与 SSH 隧道提示，而不是无声失败。

完成首次安装后，或以后任何时候用户运行：

```
vllm-sr serve
```

（在空目录下运行时）Semantic Router 可以：

- **自动引导一个最小工作区**
- 在后台创建 `.vllm-sr/router-defaults.yaml`
- 以**设置模式启动仪表板**
- 引导用户完成首次模型设置与路由起步选择
- 只有在激活之后才写入生成的 `config.yaml`

![](https://vllm.ai/blog-assets/figures/semantic-router/athena-8.png)

这是从"YAML 优先"的上手方式到"**仪表板优先**"首次运行体验的重大转变。YAML 编写仍对高级用户开放，但 `vllm-sr init` 现在是可选项，而不再是入门门槛。安装器还为首次运行增加了更清晰的操作模式：用户可以选择仅 CLI 模式、跳过自动启动、固定运行时版本，或用 `--platform amd` 强制首次启动走 AMD 路径。

这在实用层面改变了产品：从安装到路由器跑起来的最短路径变成 **安装、自动启动、打开仪表板、配置一个模型、激活**。

### 9. 仪表板成为真正的系统大脑

Athena 在仪表板 UX 上迈出了一大步。

本周期的亮点包括：

- 仪表板中的 **MCP 工具支持**
- 布局、移动端、落地页、管理器与监控方面的大量细化

![](https://vllm.ai/blog-assets/figures/semantic-router/athena-9.png)

其结果是，用户现在能做的远不止调整 YAML 和查看日志。他们可以直接从仪表板交互式地**观察**、**调试**、**评估**与**演示**系统行为。

### 10. AMD ROCm 成为一等 vllm-sr 部署路径

Athena 把 AMD 路径变成了**正规的 vllm-sr 部署流程**，而非边缘实验。项目现在拥有真正的 ROCm 版 `vllm-sr` 镜像、一份 AMD 部署手册，以及在 AMD GPU 上以 ONNX 加速运行路由器的清晰 CLI 界面。

本地镜像优先的流程如今是明确的：

```
vllm-sr serve --platform amd
```

`--platform amd` 这个标志不只是品牌展示。在仓库的 AMD 路径中，它会选择 **ROCm 镜像默认值**，把 AMD 平台传递给容器运行时，启用 **GPU 优先的配置默认值**（把 `use_cpu` 标志翻转为 `false`，除非显式禁用），并在主机上存在时挂载预期的 ROCm 设备（如 `/dev/kfd` 与 `/dev/dri`）。

![](https://vllm.ai/blog-assets/figures/semantic-router/athena-10.png)

在底层，ROCm 镜像也与本文前面描述的 ONNX 运行时方案保持一致。`vllm-sr` ROCm 镜像构建基于 ONNX 的路由器，安装 **ROCm ONNX Runtime**，并能加载 AMD **CK Flash Attention** 自定义算子。实际效果是：Athena 可以通过标准的 `vllm-sr serve --platform amd` 路径在 AMD ROCm 上运行 **FA + GPU**，而不必强迫用户搭建一套单独的定制栈。

项目现在还提供了面向真实部署的更清晰的**参考 AMD 配置文件**，包括对接 ROCm vLLM 后端的基于别名的路由。因此，部署故事不再只是"Semantic Router 理论上可以在 AMD 上运行"，而是：项目如今拥有一条端到端的 AMD 路径——专用镜像、有文档的服务流程、GPU 直通行为，以及内置于预期运维体验中的 ONNX + Flash Attention 加速。

Athena 不只是一个产品发布，也是一个研究与模型系统周期。在此期间，项目：

- 通过 **CK Flash Attention**、ONNX 图重写与面向 ROCm 的推理路径，把更长上下文的**模型加速**推进核心栈
- 加固了模型研究、训练产物与可部署运行时界面之间的桥梁

这种结合很重要。只有研究想法、模型训练与生产系统工作同步推进，语义路由才能成为持久的基础设施。Athena 是这一哲学迄今为止最清晰的表达。

```
curl -fsSL https://vllm-semantic-router.com/install.sh | bash
```

```
pip install vllm-sr
```

```
helm install semantic-router oci://ghcr.io/vllm-project/charts/semantic-router
```
