# 面向可扩展多模态模型服务的编码器分离部署

> 原文：[Encoder Disaggregation for Scalable Multimodal Model Serving](https://vllm.ai/blog/2025-12-15-vllm-epd) · vLLM 博客

vLLM 多模态工作组（Multimodality Workstream @ vLLM）

[#多模态](https://vllm.ai/blog/tags/multimodal)[#大规模服务](https://vllm.ai/blog/tags/large-scale-serving)

## 动机：为什么在 LMM 服务中分离编码器？

现代大型多模态模型（LMM）引入了一个独特的服务时瓶颈：**在任何文本生成开始之前，所有图像都必须先经过视觉编码器（例如 ViT）处理**。这一编码器阶段的计算特征与文本预填充和解码截然不同。在*同一个* GPU 实例上运行编码器 + 预填充 + 解码——这是当今的常见做法——会带来根本性的低效。

### 编码器与文本生成共置的问题

**1. 编码器-预填充-解码相互干扰**

当前的流水线（E+PD 共置在同一 GPU 上）：

- `[E PD] -> [E PD] -> [E PD]`
- 所有请求都必须完成*两个*阶段，下一个请求才能继续。
- 编码器工作无法与其他请求的预填充/解码重叠。

影响：

- 编码器既慢又波动大（取决于分辨率、图像数量、复杂度）。
- 与纯文本请求混合时，单个 LMM 输入可能拖住整个批次。
- 预填充与流式解码延迟变得抖动且不可预测。
- 计算受限的编码器与内存受限的解码必须共享同一硬件与并行策略，这对两者都不是最优。

**2. 耦合且低效的资源分配**

三个阶段各有不同的最优特征：

- **编码器：** 一次性、计算受限、高并行度。
- **预填充：** 高内存带宽、大型 GEMM。
- **解码：** 高度内存受限、长生命周期、顺序执行。

共置迫使所有阶段共用一套并行方案和一种资源配比，这意味着：

- 你无法在不为文本生成 GPU 过度配置的情况下扩展编码器吞吐量。
- 偶发的多模态请求会造成过高的成本与低效。

---

## 解决方案：编码器分离

将视觉编码器拆分为一个独立可扩展的服务，能够带来重大收益。

### 1. 流水线化执行与干扰消除

采用分离部署后：

```
E → P D   (Request 1)
......E → P D   (Request 2)
..........E → P D   (Request 3)

```

- 请求 N 的编码器可以在请求 N–1 已进入预填充或解码时运行。
- 纯文本请求完全绕过编码器，永远不必排在图像任务之后。
- 这消除了编码器导致的排队延迟。
- 系统变为流水线并行，吞吐量提升，延迟更平滑。

### 2. 独立、细粒度的扩展

每个阶段终于可以按自己的需求曲线扩展：

- 根据多模态图像量扩展**编码器 GPU**。
- 根据总请求速率和输出长度扩展**预填充/解码 GPU**。

这避免了浪费：

- 不再需要为了应对罕见的图像高峰而购买大型解码集群。
- 每个资源池都使用合适的硬件与并行策略。

### 3. 编码器输出缓存与复用

集中式的编码器服务天然支持跨请求缓存：

- 常用图像（例如徽标、图表、产品照片）的嵌入只需计算一次，即可在用户/请求之间复用。
- 命中缓存的请求**零编码器成本**，直接降低 TTFT。
- 随着缓存命中率的上升，编码器负载大幅下降。

## 设计

![](https://vllm.ai/blog-assets/figures/2025-12-15-epd/image.png)

### 组件

**代理与路由器（Proxy & Router）**

- 编排请求流。
- 将多模态（MM）输入发送给编码器实例。
- 等待编码器完成后，将原始请求（此时图像嵌入已存入远程存储）转发给预填充/解码（PD）实例。

**数据传输层（Data Transfer Layer）**

- 用于存放编码器产出的多模态嵌入的远程存储（编码器缓存，EC，嵌入）。
- 充当编码器 worker 与 PD worker 之间的共享传输介质。

**EC 连接器（EC Connectors）**

- 连接 worker/调度器与数据传输层。
- 负责编码器缓存的存取。

角色：

- **调度器侧连接器**：
  - 决定当前调度迭代中应加载或保存哪些多媒体嵌入。
  - 生成描述下游 worker 所需缓存操作的元数据。
- **worker 侧连接器**：
  - 执行实际的加载/保存操作（对远程存储的读/写）。
  - 管理每个 worker 的运行时嵌入传输。

## 工作流

### 数据流图

![](https://vllm.ai/blog-assets/figures/2025-12-15-epd/workflow.png)

### 请求生命周期

1. **代理接收请求**

   - 从原始请求中提取多模态输入。
   - 创建 N 个编码器任务（每个 MM 输入一个）并分发给编码器实例。
2. **编码器调度**

   - 编码器调度器运行这些任务，计算嵌入。
   - 通过 EC 连接器将计算得到的嵌入存入远程存储。
3. **编码器完成**

   - 所有嵌入存储完毕后，编码器 worker 通知代理。
4. **代理将请求转发给 PD 实例**

   - 原始请求（带图像哈希，但不带像素数据）被发送到预填充/解码节点。
5. **PD 执行**

   - PD 实例使用 EC 连接器从远程存储加载 MM 嵌入。
   - 正常执行预填充和解码，将嵌入直接注入模型运行器缓存。

## 实现

### 核心组件

#### 1. ECConnectorRole

定义连接器实例运行的位置：

```
class ECConnectorRole(enum.Enum):
    SCHEDULER = 0   # in scheduler process
    WORKER = 1      # in worker process

```

#### 2. ECConnectorMetadata

调度器侧与 worker 侧连接器之间共享的抽象同步/状态对象：

```
class ECConnectorMetadata(ABC):
    pass

```

#### 3. ECConnectorBase

所有连接器的抽象接口。

关键字段：

- `role`：调度器或 worker
- `config`：连接器专属配置
- `metadata`：ECConnectorMetadata

关键方法：

- `has_caches(request)`：检查远程嵌入是否已存在
- `build_connector_meta(sched_output)`：确定 worker 必须加载哪些缓存
- `update_state_after_alloc(request, item)`：根据缓存命中/未命中更新缓存分配
- `save_caches(encoder_cache)`：将编码器输出推送到远程存储
- `start_load_caches(metadata)`：在 PD 侧于预填充/解码执行前加载缓存

## 调度器侧行为

### 1. 连接器初始化

调度器：

```
if self.vllm_config.ec_transfer_config is not None:
    self.ec_connector = ECConnectorFactory.create_connector(
        config=self.vllm_config,
        role=ECConnectorRole.SCHEDULER,
    )

```

Worker：

```
def ensure_ec_transfer_initialized(vllm_config):
    global _EC_CONNECTOR_AGENT
    if vllm_config.ec_transfer_config is None:
        return
    if vllm_config.ec_transfer_config.is_ec_transfer_instance and _EC_CONNECTOR_AGENT is None:
        _EC_CONNECTOR_AGENT = ECConnectorFactory.create_connector(
            config=vllm_config,
            role=ECConnectorRole.WORKER,
        )

```

### 2. 远程缓存检查

调度媒体项时：

```
remote_cache_has_item = self.ec_connector.has_caches(request)

```

### 3. 缓存状态更新

调度完成后：

```
for i in external_load_encoder_input:
    self.encoder_cache_manager.allocate(request, i)
    if self.ec_connector:
        self.ec_connector.update_state_after_alloc(request, i)

```

### 4. 元数据构建

在调度器迭代结束时：

```
ec_meta = self.ec_connector.build_connector_meta(scheduler_output)
scheduler_output.ec_connector_metadata = ec_meta

```

## 执行集成

### 编码器侧（保存到远程存储）

计算完嵌入后：

```
for (mm_hash, pos_info), output in zip(mm_hashes_pos, encoder_outputs):
    self.encoder_cache[mm_hash] = scatter_mm_placeholders(...)
    self.maybe_save_ec_to_connector(self.encoder_cache, mm_hash)

```

### 预填充/解码侧（加载远程嵌入）

媒体编码器路径被一个加载器包裹，该加载器在运行本地编码器之前注入缓存嵌入：

```
with self.maybe_get_ec_connector_output(
        scheduler_output,
        encoder_cache=self.encoder_cache,
    ) as ec_connector_output:

    self._execute_mm_encoder(scheduler_output)
    mm_embeds, is_mm_embed = self._gather_mm_embeddings(scheduler_output)

```

## 性能结果

**环境：** 4×A100 80G
**数据集：** 随机多模态数据集（`vllm bench serve --dataset-name random-mm`）
**输入：** 400 / 2000 个文本 token；每请求 1–4 张图像（640×640 → 每张约 400 个视觉 token）
**输出：** 150 个 token
**QPS 范围：** 4–24
**模型：** Qwen3‑VL‑4B‑Instruct
**基线：** 1 个编码器 + 3 个 PD 实例（1E3PD）对比数据并行（`--data-parallel-size 4`）

生产级 LMM 服务系统需要严格的尾延迟保证——通常为 **P99 TTFT** 与 **P99 TPOT**——以保障最坏情况的可靠性。我们将 **goodput** 定义为同时满足这两项 SLO（在我们的评估中为 TTFT 20000 ms、TPOT 100 ms）的最大可持续请求速率。

## 短文本负载（约 400 token）

![](https://vllm.ai/blog-assets/figures/2025-12-15-epd/plot_len400_epd_vs_non_epd.png)

对于短文本请求，EPD 的收益随每请求图像数量的增加而急剧上升。

- **单图像：** goodput 有适度提升（23 → 24 QPS）。
- **四图像：** goodput **翻倍**（6 → 12 QPS）。

尾延迟显著改善：

- P99 TTFT/TPOT 通常比非 EPD 基线**低 20–50%**。

吞吐量-速率曲线显示：

- 不用 EPD 时，多图像负载在 **12–14 QPS** 附近失稳，P99 TPOT 飙升 **30–50%**，违反 SLO。
- EPD 将这一失稳阈值大幅上移，并保持更平滑、增长更慢的延迟曲线，这得益于编码器-解码干扰的消除，以及纯文本请求可以完全绕过视觉负载的能力。

---

## 长文本负载（约 2000 token）

![](https://vllm.ai/blog-assets/figures/2025-12-15-epd/plot_len2000_epd_vs_non_epd.png)

输入更长时，图像编码成本只占总工作量的很小一部分，系统进入解码主导的状态。即便如此，EPD 依然取得了可观的收益。

在 P99 违约之前的基线可持续 QPS：

- 1 张图像：**8 QPS**
- 3–4 张图像：**4 QPS**

EPD 分别保持：

- **18 / 11 / 9 / 8 QPS** —— goodput 提升 **2x 至 2.5x**。

其他改进：

- 在所有多模态设置下，有效解码吞吐量提升 **10–30%**。
- P99 TTFT 降低 **30–50%**。
- 在稳定运行区域内，P99 TPOT 降低 **20–40%**。

解耦的编码/文本流水线消除了模态争用，带来更高的并发、更好的吞吐量，以及即使在重度多模态负载下也更严格的 SLO 达标。

---

## 硬件可移植性：昇腾 NPU

我们在昇腾（Ascend）NPU 上以极少的改动复现了实验：

- **环境：** 4×Ascend 910B 32G
- **模型：** Qwen2.5‑VL‑7B‑Instruct
- **QPS：** 1–10

![](https://vllm.ai/blog-assets/figures/2025-12-15-epd/npu_plot_len400_epd_vs_non_epd.png)
![](https://vllm.ai/blog-assets/figures/2025-12-15-epd/npu_plot_len2000_epd_vs_non_epd.png)

在所有昇腾实验中，EPD 表现出**相同的硬件无关收益**：

- 吞吐量持续更高（稳定区域内提升 5–20%）。
- P99 TTFT 与 P99 TPOT 显著下降。
- 拥塞点被推迟，尾延迟曲线更紧凑。

这证实了 EPD 的收益源于架构解耦，而非硬件特性，使其可以移植到 GPU 与 NPU 平台。

## 结论

通过对 LMM 推理行为和生产负载需求的仔细分析，我们开发了一种**解耦的、流水线并行的多模态服务架构**，它：

- 降低 TTFT 与 TPOT，
- 提升吞吐量与稳定性，
- 消除跨模态干扰，并且
- 实现高效、可扩展的多模态服务。

该架构为下一代高性能 LMM 服务系统提供了切实可行的蓝图。接下来，我们将继续增强 vLLM，包括[优化编码器实例的参数加载](https://github.com/vllm-project/vllm/pull/30242)与[扩展 EC 连接器支持](https://github.com/vllm-project/vllm/pull/30468)。

## 相关工作

### ViT DP + LM TP

在探索编码器分离之前，vLLM 首先在单节点上为多模态模型引入了一种混合并行策略：[ViT 数据并行 + LLM 张量并行](https://github.com/vllm-project/vllm/issues/22743)方案，其中视觉编码器以数据并行方式跨 GPU 运行，而语言模型采用张量并行。这一混合策略大幅降低了 TTFT 并提升了整体吞吐量。该方法的有效性此后已得到验证，并被其他服务框架采纳，例如 [SGLang](https://github.com/sgl-project/sglang/pull/13126)。

### 先前工作与业界采用

NVIDIA Dynamo 团队率先基于 vLLM 支持了 [EPD 风格的分离部署](https://github.com/ai-dynamo/dynamo/blob/44a2cba976d12a79b2164ed11612c1bc7491a3d8/examples/backends/vllm/launch/agg_multimodal_epd.sh#L5)，不过文档较为有限。vLLM 原生的 EPD 实现（[PR #25233](https://github.com/vllm-project/vllm/pull/25233)）于 2025 年 11 月上旬合并，并自 0.11.1 版本起可用，为开源生态带来了一等公民级别的编码器分离支持。
