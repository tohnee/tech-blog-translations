# Model Runner V2：vLLM 更模块化、更快的核心

> 原文：[Model Runner V2: A Modular and Faster Core for vLLM](https://vllm.ai/blog/2026-03-24-mrv2) · vLLM 博客

作者：vLLM 团队

[#性能](https://vllm.ai/blog/tags/performance)[#工程](https://vllm.ai/blog/tags/engineering)

我们很高兴宣布 **Model Runner V2（MRV2）**——对 vLLM model runner 的从零重构。MRV2 带来更干净、更模块化、更高效的执行核心，且**没有任何 API 变更**。目标很简单：更好的代码与更好的性能。

与去年的 vLLM V1 发布一样，这是一次由 vLLM 庞大用户群体的宝贵经验与社区反馈驱动的架构升级。我们重新审视了持久化批处理、异步调度、输入准备与采样，然后围绕三条核心原则重建了 model runner：

- **保持模块化。** 把模型特定逻辑与公共执行路径隔离。
- **以 GPU 为本。** 把簿记工作从 CPU 移到 GPU。
- **异步优先。** 把 CPU/GPU 重叠执行当作设计约束，而非事后补丁。

MRV2 尚未功能完备，但你现在就可以试用：

```
export VLLM_USE_V2_MODEL_RUNNER=1
```

我们计划在不久的将来把 MRV2 设为默认。

## 为什么需要 Model Runner V2？

自去年 vLLM V1 发布以来，随着功能与优化逐步叠加，model runner 积累了大量技术债。这些改动单独看大多是有益的，但实现随时间推移越来越难以理清——尤其是在异步调度与投机解码成为执行模型核心之后。

在实践中，这带来了一些反复出现的问题：

- **持久化批次状态纠缠不清。** 持久化状态与每步模型输入紧耦合，使请求的插入、移除与重排比必要的更复杂。
- **异步执行脆弱。** 异步调度是事后加装到 V1 runner 上的，许多功能需要别扭且不必要的复杂逻辑才能与之共存。
- **簿记受限于 CPU。** 输入准备与采样依赖大量小的 CPU 侧操作，在 GPU 越来越快的同时浪费了本可获得的性能。
- **扩展困难。** 随着新模型与新功能到来，runner 整体变得更难理解和干净地扩展。

MRV2 通过更清晰的状态归属与更明确的抽象重新思考 model runner，从而解决这些问题。

## Model Runner V2 有哪些新特性？

### 1. 更好的持久化批次设计与 GPU 原生输入准备

vLLM 要为批处理、分页注意力、采样参数等做大量簿记。历史上，这些工作大多实现为许多小的 CPU 侧操作。

为了降低这类开销，vLLM V1 引入了持久化批处理：由于相邻批次通常相似，增量更新缓存状态远比每步从零重建大张量便宜。然而，V1 设计把持久化状态直接用作模型与采样器输入，这造成了别扭的布局约束和复杂的簿记。

![图 1：V1 中的持久化批次。请求顺序与块表布局紧耦合，添加或移除请求时需要复杂的重排序。](https://vllm.ai/blog-assets/figures/2026-03-24-mrv2/persistent_batch_v1.png)

图 1：V1 中的持久化批次。请求顺序与块表布局紧耦合，添加或移除请求时需要复杂的重排序。

MRV2 **把持久化请求状态与每步输入张量解耦**。每个活跃请求在其活跃生命周期内都会在一张固定大小的状态表中获得一个稳定的行。每一步，runner 按当前请求顺序从该持久化状态中收集本步所需的输入。这既保留了增量更新的性能收益，又去除了大量状态管理复杂度。它还消除了 `CachedRequestState` 之类的冗余备份状态，因为活跃请求不再依赖脆弱的全张量重排序。

![图 2：MRV2 中的持久化批次。稳定的状态表独立于每步输入布局维护。每步由 gather 操作生成顺序正确的输入块表。](https://vllm.ai/blog-assets/figures/2026-03-24-mrv2/persistent_batch_mrv2.png)

图 2：MRV2 中的持久化批次。稳定的状态表独立于每步输入布局维护。每步由 gather 操作生成顺序正确的输入块表。

MRV2 还借助 Triton 内核**把输入准备移到 GPU 上**。请求状态大部分保存在设备上，`input_ids`、`positions`、`query_start_loc`、`seq_lens` 等张量现在直接在 GPU 上构建。这带来三个具体好处：

- **更低的 CPU 开销**：避免大量 Python 与 CPU 张量操作。
- **更低的代码复杂度**：移除了 CPU 侧张量操作带来的约束。
- **更好的异步与投机解码兼容性**：驻留 GPU 的准备过程可以直接消费设备侧结果而无需同步（见下一节）。

### 2. 异步优先设计

异步调度如今已是 vLLM 的基石。调度器与 worker 在 GPU 执行第 `N` 步的同时准备第 `N+1` 步，让主机工作与设备工作重叠以最大化利用率。虽然 vLLM V1 已经支持这一点，但它更多是事后加装，而非一等设计约束。

![图 3：V1 中的异步调度。CPU 在 GPU 执行当前步的同时调度并准备下一步，CPU 与 GPU 工作重叠。](https://vllm.ai/blog-assets/figures/2026-03-24-mrv2/async_scheduling.png)

图 3：V1 中的异步调度。CPU 在 GPU 执行当前步的同时调度并准备下一步，CPU 与 GPU 工作重叠。

MRV2 把异步执行视为核心假设，目标是让 CPU 与 GPU 在所有受支持的模型与功能组合之间实现**零同步**。

重要的是，MRV2 天然支持异步调度与投机解码并用——这一组合在 V1 中很难干净地支持。由于 MRV2 的输入准备在设备上运行，准备内核可以直接消费 GPU 产生的拒绝采样结果。每步的输出通过单独的 CUDA 流异步传输到 CPU，与主计算流完全解耦。同样的设计也延伸到带结构化输出的投机解码。

![图 4：MRV2 中投机解码下的异步调度。GPU 侧准备内核直接消费拒绝采样结果，消除 CPU-GPU 同步点。](https://vllm.ai/blog-assets/figures/2026-03-24-mrv2/async_spec_decoding.png)

图 4：MRV2 中投机解码下的异步调度。GPU 侧准备内核直接消费拒绝采样结果，消除 CPU-GPU 同步点。

### 3. Triton 原生采样器

MRV2 用优化的 Triton 内核重做了采样，以更好地控制内存占用与数值行为。具体改进包括：

- **Gumbel-Max 采样内核**：避免显式物化 softmax，并使用内核内无状态随机数生成器。
- **更高效的 top-k logprobs**：先找出 top-k logits，再仅为选中的候选计算 logprobs。
- **更省内存的 prompt logprobs**：通过更细粒度的分块实现，包括单个提示内部的分块。
- **更好的投机解码兼容性**：在内核内部使用间接寻址（`idx_mapping`），而不是扩展请求状态去匹配每个 logits 向量。

这些改动共同降低了峰值内存占用，并让支持丰富的采样参数组合变得更容易。

### 4. 更强的模块化

vLLM 需要支持广泛的模型架构，现有 model runner 因此积累了相当的复杂度。MRV2 用一个新的抽象来解决这个问题：**`ModelState`**。

```
class ModelState(ABC):
    def add_request(self, ...):
    def remove_request(self, ...):
    def get_mm_embeddings(self, ...):
    def prepare_inputs(self, ...):
    def prepare_attn(self, ...):
    def prepare_dummy_inputs(self, ...):
    ...
```

`ModelState` 为模型特定逻辑定义了接口——多模态嵌入、额外模型输入、注意力元数据、CUDA Graph 捕获——让主 runner 可以专注于公共路径。这直接回应了用户与贡献者的一个常见抱怨：vLLM 支持的模型太多，共享代码会显得绕，尤其是对只关心某一个模型家族（如 DeepSeek、Qwen、Kimi 或某个私有内部模型）的开发者。

此外，MRV2 把 runner 拆分成职责更清晰的小文件。现有 runner（`gpu_model_runner.py`）已经长成超过 6,700 行的单个文件；MRV2 中最大的文件现在不到 1,300 行。

## 性能

MRV2 不只是一个清理项目。它已经带来可测量的收益。

我们用一台强大 GPU（`1×GB200`）运行一个很小的模型（`Qwen3-0.6B`）对 MRV2 进行压力测试——特意选择小模型，是为了让主机侧开销占比更大。在这一设置下，**MRV2 通过把输入准备卸载到 GPU，带来了 56% 的吞吐量提升**。

![图 5：Qwen3-0.6B 在 1×GB200 上 MRV1 与 MRV2 的吞吐量对比。MRV2 达到 25K 输出 tok/s，而 MRV1 为 16K，提升 56.2%。](https://vllm.ai/blog-assets/figures/2026-03-24-mrv2/throughput_comparison.png)

图 5：Qwen3-0.6B 在 1×GB200 上 MRV1 与 MRV2 的吞吐量对比。MRV2 达到 25K 输出 tok/s，而 MRV1 为 16K，提升 56.2%。

我们还测量了投机解码的收益：在 `4×GB200` 上用 `GLM-4.7-FP8` 与 `MTP=1` 时，**TPOT 降低 6.3%**。这一提升来自 MRV2 的零同步设计——启用投机解码时完全消除 CPU-GPU 同步点。

![图 6：GLM-4.7-FP8（MTP=1）在 4×GB200 上 MRV1 与 MRV2 的平均 TPOT 对比。MRV2 在各请求速率下 TPOT 降低 6.3%。](https://vllm.ai/blog-assets/figures/2026-03-24-mrv2/tpot_mtp.png)

图 6：GLM-4.7-FP8（MTP=1）在 4×GB200 上 MRV1 与 MRV2 的平均 TPOT 对比。MRV2 在各请求速率下 TPOT 降低 6.3%。

随着服务栈继续把异步调度、投机解码、多模态预处理与日益异构的模型状态组合在一起，我们预期这一架构基础会变得更加重要。

## 局限与现状

MRV2 仍处于实验阶段并在积极开发中。设计明显更干净，早期结果也很亮眼，但 MRV2 尚未功能完备。截至 v0.18.0，以下功能**不受支持**：

- 线性注意力模型（Qwen3.5、Nemotron 3 Super）
- Eagle/Eagle3/MTP 之外的投机解码方法
- EPLB 与 DBO
- Logits 处理器
- LoRA

完整列表见[设计文档](https://docs.google.com/document/d/1gFqtDkcoqhy9j-X0ndshzbhapX1uNey1-wBENwGPI80/edit?usp=sharing)第二页。

我们对 MRV2 设定了更高的质量门槛：把 V1 功能带进 MRV2 时，我们希望从第一性原理重新审视它，而不是机械地照搬复杂度。因此，涉及 MRV2 的改动落地可能比平时更久。

## 开始使用

1. 安装最新的 vLLM 构建版本。
2. 设置 `export VLLM_USE_V2_MODEL_RUNNER=1`。
3. 像往常一样使用现有的 vLLM API——Python API 或 `vllm serve`。

**无需任何面向用户的 API 变更**。
