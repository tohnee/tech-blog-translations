# DeepSeek V4 登陆 vLLM：高效的长上下文注意力

> 原文：[DeepSeek V4 in vLLM: Efficient Long-context Attention](https://vllm.ai/blog/2026-04-24-deepseek-v4) · vLLM 博客

vLLM 团队

[#模型支持](https://vllm.ai/blog/tags/model-support)

我们很高兴地宣布，vLLM 现已支持 DeepSeek V4 系列模型（[`deepseek-ai/DeepSeek-V4-Pro`](https://huggingface.co/deepseek-ai/DeepSeek-V4-Pro) 与 [`deepseek-ai/DeepSeek-V4-Flash`](https://huggingface.co/deepseek-ai/DeepSeek-V4-Flash)）。

这些模型配备了一种高效的长上下文注意力机制，专为涉及高达*一百万 token* 的任务量身打造。
初读时，新的注意力设计可能显得颇为繁复，但只要系统地梳理一番，其底层原理其实非常直白。

本文分为三个部分：

- 在 vLLM 上服务 DeepSeek V4 的快速上手指南
- 从第一性原理出发解释 DeepSeek V4 的新架构设计
- 概述我们在 vLLM 上实现该模型的方案与优化挑战：混合 KV 缓存、内核融合与分离式服务

这是我们对模型支持的初始版本，进一步的优化正在积极推进中。
我们希望接下来的技术解读能帮助开源社区既理解注意力机制本身，也理解我们当前实现决策背后的考量。

## 在 vLLM 上运行 DeepSeek V4

DeepSeek V4 包含 2 个模型：1.6T 参数的大模型 `DeepSeek-V4-Pro`，以及 285B 参数的小模型 `DeepSeek-V4-Flash`。两个模型都支持高达 100 万 token 的上下文，vLLM 对新注意力机制的实现也旨在扩展到该上下文长度。

### DeepSeek-V4-Pro

这里我们重点介绍一个为方便测试和原型验证而优化的单节点部署，并附带若干可选优化，如 FP4 indexer 与 MTP。
以下命令可在 8xB200 或 8xB300 上运行。

```
docker run --gpus all \
  --ipc=host -p 8000:8000 \
  -v ~/.cache/huggingface:/root/.cache/huggingface \
  vllm/vllm-openai:deepseekv4-cu130 deepseek-ai/DeepSeek-V4-Pro \
  --trust-remote-code \
  --kv-cache-dtype fp8 \
  --block-size 256 \
  --enable-expert-parallel \
  --data-parallel-size 8 \
  --compilation-config '{"cudagraph_mode":"FULL_AND_PIECEWISE", "custom_ops":["all"]}' \
  --attention_config.use_fp4_indexer_cache=True \
  --tokenizer-mode deepseek_v4 \
  --tool-call-parser deepseek_v4 \
  --enable-auto-tool-choice \
  --reasoning-parser deepseek_v4
```

更多部署策略，包括分离式服务/更多 GPU 架构，请参阅[recipes](https://recipes.vllm.ai/deepseek-ai/DeepSeek-V4-Pro)。

## DeepSeek V4 注意力机制详解

长上下文推理面临两大挑战：

- **KV 缓存内存增长**：KV 缓存随上下文长度线性增长。虽然 DeepSeek 系列模型使用[多头潜在注意力（Multi-head Latent Attention，MLA）](https://arxiv.org/abs/2405.04434)，其内存效率远高于标准的多头注意力（MHA）或多查询注意力（MQA），但考虑到 GPU 内存的有限容量，扩展到 100 万 token 仍然困难。
- **注意力计算成本**：在长上下文上计算注意力开销很大。即使有[DeepSeek 稀疏注意力（DeepSeek Sparse Attention，DSA）](http://arxiv.org/abs/2512.02556)这类先行技术，计算仍是显著的瓶颈。

为应对这些挑战，DeepSeek 团队设计了一种新的注意力机制，旨在同时压缩 KV 缓存并缩短注意力计算时间。

1. 共享键与值向量（节省 2x 内存）。为保证正确性，我们对注意力输出施加一个**逆 RoPE**操作。
2. 跨多个 token 压缩 KV 缓存（节省 4x 到 128x 内存）。在 DeepSeek V4 中有两种做法：
   - **`c4a`**：把 KV 缓存压缩到约 1/4。一个压缩 token 是 **8 个未压缩 token** 的加权和，**步长为 4**。
   - **`c128a`**：把 KV 缓存压缩到约 1/128。一个压缩 token 是 **128 个未压缩 token** 的加权和，**步长为 128**。
3. DeepSeek 稀疏注意力（有界的注意力计算成本）。即使用 `c4a` 注意力压缩了 KV 缓存，一段 100 万 token 的序列仍有 25 万个压缩 token。为加速注意力计算，我们可以使用 [DeepSeek 稀疏注意力（DSA）](http://arxiv.org/abs/2512.02556)只关注 top-$k$ 个压缩 token。
4. 保持局部性：短滑动窗口。DeepSeek V4 使用大小为 128 的滑动窗口来处理局部信息，它在未压缩的 token 上运行，使查询 token 在到达压缩边界之前仍能关注局部信息。

为了更好地说明这种新的注意力机制，这里有一段 `c4a` 注意力处理 13 个 token 的动画。记住上述细节后，`c128a` 的情形应该也不难看懂。可以打开[交互版本](https://vllm.ai/blog-assets/interactive_pages/c4a.html)，悬停在 token 上查看连接关系。

![Animation of c4a attention](https://vllm.ai/blog-assets/figures/2026-04-dsv4/c4a_animation.gif)

c4a 注意力动画

高效注意力设计带来了可观的 KV 缓存节省。使用 `bf16` KV 缓存时，DeepSeek V4 在 1M 上下文下每个序列的 KV 缓存只有 9.62 GiB。这比按 61 层 DeepSeek V3.2 风格堆叠估算的 83.9 GiB 小约 8.7x。实践中，我们为 indexer 缓存使用 `fp4`、为注意力缓存使用 `fp8`，相比 `bf16` 估算进一步把 KV 缓存大小缩减约 **2x**！

## vLLM 对 DeepSeek V4 的实现

尽管结构上已有节省，注意力机制本身仍带有固有的复杂性，而在 vLLM 中高效兑现这些节省是一个存在多项实现挑战的系统问题：

- 与 DeepSeek V3.2 模型类似，注意力内核在预填充时使用 bfloat16 KV 缓存，解码时部分使用逐 token 的 fp8。
- 模型混合使用 `c4a` 与 `c128a` 注意力，还有一些注意力层只使用滑动窗口处理局部信息、不做压缩。异构的注意力类型让 KV 缓存管理复杂得多。
- 批处理多条序列时，它们相对 KV 缓存压缩边界可能处于不同的状态。
- 模型自带原生 fp4 MoE 权重，这在 vLLM 中需要特殊处理。

除注意力机制本身外，还有若干其他更新，包括 [Manifold-Constrained Hyper-Connections](http://arxiv.org/abs/2512.24880) 等架构改动以及 MoE 模块的一些变化。本文不涉及这些内容，因为它们是较简单、较容易适配的模型改动。

vLLM 从两个方向应对这些挑战：内存管理与内核效率。

### 让 KV 缓存内存保持紧凑

vLLM 的 KV 缓存内存分配器必须把多种 KV 状态紧密地打包进 GPU 内存，同时还要兼容前缀缓存、预填充/解码分离、CUDA Graph 以及 vLLM 服务路径上的其余环节。三个设计选择让这一切 manageable。

#### (1) 单一逻辑块大小

不同层的压缩率不同（`c4a` 为 1/4，`c128a` 为 1/128，SWA 为 1/1）。一个显而易见的设计是让每层的块围绕整数个*压缩*条目来定大小。但这样一来，每层都有各自的页布局，分配器必须对它们分别推理。

相反，我们把每个压缩层的逻辑块固定为 **256 个原生 token 位置**。于是一个 `c4a` 块物理上容纳 `256 / 4 = 64` 个压缩条目，一个 `c128a` 块容纳 `256 / 128 = 2` 个。分配一个块始终意味着预留某请求上下文的下 256 个原生位置，而不管它属于哪一层。槽位映射、调度器记账和前缀命中检测都可以使用同一个单元，而不必在 `compress_ratio` 上做分支。

#### (2) 把压缩器状态当作滑动窗口

每个压缩器层还会为每个请求维护一个小的滚动残差：C4 是一个 8 token（有重叠）的部分状态，C128 是一个 128 token 的部分状态。一个自然的第一版设计是把该残差放在每请求的旁路缓冲区里。这在孤立场景下可行，但一旦要与服务栈其余部分交互，就会变得别扭。

有了旁路缓冲区，前缀缓存就需要在每个可缓存边界对滚动状态做快照，把它与前缀哈希一起作为键，命中时再恢复。分离式预填充则需要第二条传输路径，把残差连同 KV 块一起从预填充 worker 运送到解码 worker。每一项要求单独看都可控，但合在一起就多出一条要跨功能维护的状态管理路径。

vLLM 的做法是把压缩器状态当作滑动窗口 KV 来对待。运行时不变量是相同的：每请求固定大小，随解码推进而前移，窗口外的状态要么丢弃、要么通过缓存处理。于是我们把压缩器状态注册在滑动窗口 KV 缓存规范之下，取 `sliding_window = coff * compress_ratio`（C4 为 8，C128 为 128），并把它放进同一个混合 KV 缓存管理器下的 SWA 风格块中。

这样，多个服务功能就能复用同一套抽象：

- **前缀缓存**复用常规块语义。缓存命中落在 KV 缓存块边界上（即上面的 256 位置单元），而该边界处的压缩器状态本来就是正确的交接点。
- **分离式预填充**把压缩器状态当作 SWA 状态处理。只有窗口内的块会被传输，从而在不引入单独的残差专用传输路径的前提下保住传输量的节省。
- **CUDA Graph** 与 **MTP** 沿用与 SWA 相同的集成模式，同时保留压缩器状态特有的元数据与实现细节。

#### (3) 统一页大小

仅有上面两个选择还不够。一个 C4 indexer 块、一个 `c128a` KV 块和一个 `c4a` 压缩器状态块仍有不同的*页大小*（每块字节数不同）。如果每种缓存各有自己的块池，我们又会遇到本来想消除的跨池碎片问题。

幸运的是，每种缓存的页大小都是 `block_size * compress_ratio * per_entry_size` 这一乘积，而这三个因子都在我们掌控之中。只要精心选择，不同缓存就会坍缩进少数几个*页大小桶*，每个桶可以由一个共享块池支撑。

在我们的实现中，整个五路缓存栈只占**三种**页大小。每个池在加载时确定一次大小，分配就变成一次桶查找。没有运行时重新划分，没有按类别的记账，也没有缓存类别之间的碎片。

- *最大桶：* `c4a` 主 KV、SWA KV、`c4a` 压缩器状态、`c128a` 压缩器状态。
- *中间桶：* C4 indexer KV、C4 indexer 压缩器状态。
- *最小桶：* `c128a` 主 KV。

### 让 GPU 保持忙碌

内存布局只是运行时故事的一半；另一半是让 GPU 算力保持饱和。

vLLM 集成了 FlashMLA 与 FlashInfer，它们提供优化过的注意力和 MoE 内核。
但这个模型需要许多小型、大多受内存限制的内核。
我们必须避免额外的内核启动和 HBM 往返，否则它们会拖慢完整的解码路径。

![c4a decode path: operator graph with kernel fusions (colored outlines) and multi-stream partitioning (default stream = blue band, indexer stream = amber band).](https://vllm.ai/blog-assets/figures/2026-04-dsv4/decode-path.svg)

c4a 解码路径：带内核融合（彩色描边）与多流划分（默认流 = 蓝色条带，indexer 流 = 琥珀色条带）的算子图。

#### (1) 内核融合

我们部署了三种融合来削减内存往返。在下图中，它们表现为包围一组算子的彩色描边。

- **压缩器 + RMSNorm + RoPE + 缓存写入。** 压缩之后，压缩 K 立即依次经过 RMSNorm、RoPE，并被写入后续注意力的 KV 缓存——要么是主注意力，要么是 indexer。由于这些阶段几乎完全是逐元素的，我们把它们融合进一个内核。indexer K 缓存与主注意力 K 缓存各保留一个独立内核，以便并行化策略仍可按各自的 head 维度调优。总体上，相比未融合基线我们观察到约 1.4-3x 的加速。
- **逆 RoPE + fp8 量化。** 主注意力之后，输出经过逆 RoPE，随后进入 `o_lora` 投影的 fp8 批量矩阵乘。融合两者避免了背靠背的 HBM 往返并提高算术强度，相比未融合版本带来约 2-3x 的加速。
- **融合 Q norm + KV RoPE + K 写入。** 主注意力之前，我们需要为压缩路径与滑动窗口路径都做 KV 缓存写入。压缩路径已由第一个融合覆盖，剩下的就是对查询和未压缩 SWA 键的逐元素操作。我们把这部分工作水平融合进一个采用静态 `warpID` 分派的单一内核：每个 warp 独立处理一个 Q head 或一个 K head，因此不需要跨 warp 通信。相比朴素的未融合内核，这带来 10-20x 的加速。

我们还复用了 DeepSeek V3.2 工作中的融合，包括 Q RoPE + 量化 + 权重相乘，以及注意力开始处 QK 投影之后紧接的 QK norm 水平融合。

#### (2) 多流

主注意力之前的操作高度可并行。它们分成三块：indexer 计算、主注意力 KV 压缩，以及滑动窗口 token 写入。初始投影之后，这些分支几乎相互独立，因此我们在多条 CUDA 流上让它们重叠。同一张图还可以换个读法：蓝色条带标记默认流，琥珀色条带标记 indexer 流。

- 对于没有 indexer 的 `c128a` 层，我们让主 KV 压缩与 SWA token 写入并行运行。
- 对于 `c4a` 层，我们在自己的流上并行运行完整的 indexer 流水线，与主 KV 压缩和 SWA token 写入同时进行（后两者彼此保持串行）。

借助这些重叠，我们观察到低批大小下端到端延迟降低 5-6%，这是一个有用的信号，说明解码路径让 GPU 闲置的时间变少了。

在此之上，我们像对待其他所有模型一样，使用 CUDA Graph 来削减解码路径上的启动开销。

完整实现请见 [PR](https://github.com/vllm-project/vllm/pull/40760)。

## 附录：DeepSeek V4 注意力机制背后的数学

### 为什么共享键与值时需要逆 RoPE

给定位置 $i$ 上的一个查询 token，施加 [RoPE](http://arxiv.org/abs/2104.09864) 之后的查询表示为 $<q_{i},i>=R(i)q_{i}$，其中 $R(i)$ 是旋转角度由位置 $i$ 参数化的旋转矩阵。旋转矩阵的一些基本性质如下：

- $R(i)R(j)=R(i+j)$
- $R(i)^{-1}=R(i)^{T}=R(-i)$
- $R(i)$ 是正交矩阵，即 $R(i)R(i)^{T}=I$

给定一组位于位置 $j_{1},j_{2},j_{p},...,j_{n}$ 的键 token，施加 RoPE 之后的键表示为 $<k_{j1},j_{1}>=R(j_{1})k_{j1}$、$<k_{j2},j_{2}>=R(j_{2})k_{j2}$、……、$<k_{jp},j_{p}>=R(j_{p})k_{jp}$、……、$<k_{jn},j_{n}>=R(j_{n})k_{jn}$。

对于位于位置 $j_{1},j_{2},j_{p},...,j_{n}$ 的值向量，通常我们不对它们施加 RoPE。值表示就是简单的 $<v_{j1},j_{1}>=v_{j1}$、$<v_{j2},j_{2}>=v_{j2}$、……、$<v_{jp},j_{p}>=v_{jp}$、……、$<v_{jn},j_{n}>=v_{jn}$。

于是注意力输出为（为简洁起见，省略缩放因子等一些细节）：

$a_{i}=\sum p=1n\frac{exp⁡(<q_{i},i>^{T}<k_{jp},j_{p}>)}{\sum nr=1exp⁡(<q_{i},i>^{T}<k_{jr},j_{r}>)}<v_{jp},j_{p}>=\sum p=1n\frac{exp⁡(q_{T}^{i}R(j_{p}-i)k_{jp})}{\sum nr=1exp⁡(q_{T}^{i}R(j_{r}-i)k_{jr})}v_{jp}$

注意力输出的一个好性质是平移不变性。任何依赖位置的因子，即 $R(j_{p}-i)$ 与 $R(j_{r}-i)$，都只依赖查询与键之间的相对位置。这意味着如果把查询和键平移相同的量，注意力输出不变。

如果我们共享键与值向量，注意力输出将变为：

$a_{i}=\sum p=1n\frac{exp⁡(<q_{i},i>^{T}<k_{jp},j_{p}>)}{\sum nr=1exp⁡(<q_{i},i>^{T}<k_{jr},j_{r}>)}<k_{jp},j_{p}>=\sum p=1n\frac{exp⁡(q_{T}^{i}R(j_{p}-i)k_{jp})}{\sum nr=1exp⁡(q_{T}^{i}R(j_{r}-i)k_{jr})}R(j_{p})k_{jp}$

现在输出通过旋转矩阵 $R(j_{p})$ 直接携带了绝对位置信息。这不是我们想要的。修复方法很简单：对注意力输出施加一个逆 RoPE 操作：

$R(-i)a_{i}=R(-i)\sum p=1n\frac{exp⁡(<q_{i},i>^{T}<k_{jp},j_{p}>)}{\sum nr=1exp⁡(<q_{i},i>^{T}<k_{jr},j_{r}>)}<k_{jp},j_{p}>=\sum p=1n\frac{exp⁡(q_{T}^{i}R(j_{p}-i)k_{jp})}{\sum nr=1exp⁡(q_{T}^{i}R(j_{r}-i)k_{jr})}R(j_{p}-i)k_{jp}$

这样，输出只通过旋转矩阵 $R(j_{p}-i)$ 携带相对位置信息，重新恢复了平移不变性。

类似的讨论也可以在 <https://kexue.fm/archives/10862> 找到。

### 实现细节：精确的位置区间与因果性条件

处理压缩后的 KV 缓存时必须小心。对每个压缩索引 $j$，我们先合并一组固定的局部原始 token，然后用压缩 token 的锚点位置施加一次 RoPE，再把这个压缩 token 存入 KV 缓存。

对于 `c4a`，第 $j$ 个压缩 token 是位置区间 $[4j-4,4j+3]$ 内 token 的加权和，其中 $j$ 从 0 开始，负索引被视为值为 0 的 token。对压缩 token 施加 RoPE 时使用的位置是 $4j$。

对于 `c128a`，第 $j$ 个压缩 token 是位置区间 $[128j,128j+127]$ 内 token 的加权和，其中 $j$ 从 0 开始。对压缩 token 施加 RoPE 时使用的位置是 $128j$。

就因果性而言，我们需要保证位置 $i$ 上的查询 token 只关注位置区间 $[0,i]$ 内 token 产生的信息。这意味着对于位置 $i$ 的查询和 KV 缓存中的第 $j$ 个压缩 token，我们需要保证 $i\ge4j+3$（`c4a`）或 $i\ge128j+127$（`c128a`）。

### 实现细节：c4a 与 c128a 中 k 的确切取值

对 DeepSeek V4 的 `c4a` 注意力，$k$ 的默认值为 512；对 `c128a` 注意力，$k$ 的默认值为 8192。（作为对比，DeepSeek V3.2 中 $k$ 的默认值为 2048。）

`c128a` 注意力的压缩率更大。在 100 万 token 的上下文下，它至多拥有 8k 个压缩 token。8k token 对注意力计算来说不算什么，所以我们可以直接对 `c128a` 压缩 token 使用全注意力。在实现上，我们仍可以把 `c128a` 注意力框定为 top-$k$ 值为 8192 的稀疏注意力问题。

### 实现细节：为什么需要短滑动窗口

使用 `c128a` 时，位置 $100$ 上的查询 token 无法关注 KV 缓存中的任何压缩 token，因为第一个压缩 token 包含位置 $0$ 到 $127$ 的信息，而受因果性约束，查询 token 不能关注位置 $100$ 之后的信息。有了短滑动窗口，查询 token 可以关注位置区间 $[0,100]$ 内的未压缩 token，因此仍能访问局部信息。

### 8.7x 节省估算背后的算术

对一段 1M 上下文的序列：

DeepSeek V3.2，bf16 KV 缓存：

- 每层每 token 的 MLA 缓存：$(512+64)\times2=1152$ 字节。
- 每层每 token 的 indexer 缓存：$128\times2=256$ 字节。
- 每层每 token 的缓存状态总量：$1152+256=1408$ 字节。
- 按 1,048,576 个 token 计：每层 $1,048,576\times1408\approx1.375$ GiB。
- 61 层合计：约 $83.9$ GiB。

DeepSeek V4，61 层，bf16 KV 缓存：

- 每个共享 KV 缓存条目存储 $512\times2=1024$ 字节。
- 每个 `c4a` indexer 缓存条目存储 $128\times2=256$ 字节。
- `c4a` 层：共享 KV 缓存 $(128+1,048,576/4)\times1024$ 字节加上 indexer 缓存 $(1,048,576/4)\times256$ 字节，总计约 $320.1$ MiB。
- `c128a` 层：$(128+1,048,576/128)\times1024\approx8.1$ MiB。
- 30 个 `c4a` 层与 31 个 `c128a` 层合计：约 $9.62$ GiB。
