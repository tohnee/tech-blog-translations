# EAGLE 3.1：EAGLE 团队、vLLM 与 TorchSpec 携手推进投机解码

> 原文：[EAGLE 3.1: Advancing Speculative Decoding Through Collaboration Between the EAGLE Team, vLLM, and TorchSpec](https://vllm.ai/blog/2026-05-26-eagle-3-1) · vLLM 博客

作者：EAGLE 团队、vLLM 团队与 TorchSpec 团队

[#投机解码](https://vllm.ai/blog/tags/speculative-decoding)[#性能](https://vllm.ai/blog/tags/performance)

EAGLE 系列——包括 EAGLE 1、EAGLE 2 和 EAGLE 3——已成为在研究和生产系统中被最广泛采用、实际部署最多的投机解码算法家族之一。

今天，[EAGLE 团队](https://github.com/SafeAILab/EAGLE)、[vLLM 团队](https://github.com/vllm-project/vllm)和 [TorchSpec 团队](https://github.com/lightseekorg/TorchSpec)很高兴共同推出 **EAGLE 3.1**——投机解码在鲁棒性、效率和可部署性上向前迈出的重要一步。

## EAGLE 3.1 的创新

尽管投机解码在受控环境中表现良好，但在不同聊天模板、长上下文输入或分布外系统提示词下，性能常常退化。

EAGLE 团队把这种脆弱性追溯到一个我们称为[注意力漂移（attention drift）](https://arxiv.org/pdf/2605.09992)的现象——随着投机深度增加，起草器（drafter）逐渐把注意力从 sink token 转移到它自己生成的 token 上。

我们确定了两个深层问题。第一，融合输入表示日益失衡，因为更高层的隐藏状态主导了起草器的输入。第二，由于残差路径未归一化，隐藏状态的幅值随投机步数增长。这两个效应叠加，使起草器在更深投机深度下越来越不稳定。

![Figure 1: EAGLE 3 vs. EAGLE 3.1 architecture comparison. EAGLE 3.1 adds FC normalization after each target hidden state and feeds post-norm hidden states into the next decoding step.](https://vllm.ai/blog-assets/figures/2026-05-26-eagle-3-1/pre-norm-vs-post-norm.png)

图 1：EAGLE 3 与 EAGLE 3.1 的架构对比。EAGLE 3.1 在每个目标隐藏状态之后加入 FC 归一化，并把归一化后的隐藏状态馈入下一步解码。

为解决这一问题，EAGLE 3.1 引入了两项关键架构改进：

- 在每个目标隐藏状态之后、FC 层之前进行 FC 归一化
- 将归一化后的隐藏状态馈入下一步解码

直观地说，post-norm 设计让该方法更像是在解码步骤间递归调用起草器，而不是简单地在目标模型上追加额外层。

这些改动显著提升了各部署场景下的鲁棒性。与 EAGLE 3 相比，EAGLE 3.1 展现出：

- 更好的训练时到推理时外推能力
- 更强的长上下文鲁棒性
- 对聊天模板与系统提示词变化更强的适应力
- 在多样服务环境中更稳定的接受长度

在长上下文工作负载中，**EAGLE 3.1 的接受长度最高达到 EAGLE 3 的 2 倍**。

## 使用 TorchSpec 训练 EAGLE 3.1

[TorchSpec](https://github.com/lightseekorg/torchspec) 现已为 [EAGLE 3.1](https://github.com/lightseekorg/TorchSpec/pull/97) 及未来的投机解码算法提供高效训练支持。

通过降低训练开销和简化实验工作流，TorchSpec 有助于加速下一代投机解码研究与部署的迭代和探索。

基于 TorchSpec 和 vLLM，我们还训练并开源了一个面向 Kimi K2.6 的 EAGLE 3.1 草稿模型：

<https://huggingface.co/lightseekorg/kimi-k2.6-eagle3.1-mla>

该模型是在真实服务模型上结合 TorchSpec 训练与 vLLM 服务支持部署 EAGLE 3.1 的一个示例。

## EAGLE 3.1 与 vLLM 的集成

EAGLE 3.1 以[配置驱动的扩展](https://github.com/vllm-project/vllm/pull/42764)形式进入 [vLLM](https://github.com/vllm-project/vllm)，扩展现有的 EAGLE 3 实现。

集成内容包括：

- FC 归一化支持
- 归一化后隐藏状态的反馈
- 移除围绕目标隐藏状态的硬编码假设

同时，与现有 EAGLE 3 检查点的向后兼容得到完整保留。因此，EAGLE 3.1 草稿模型可以直接通过同一条投机解码代码路径接入，例如：

```
vllm serve nvidia/Kimi-K2.6-NVFP4 \
  --trust-remote-code \
  --tensor-parallel-size 4 \
  --tool-call-parser kimi_k2 \
  --enable-auto-tool-choice \
  --reasoning-parser kimi_k2 \
  --attention-backend tokenspeed_mla \
  --speculative-config '{"model":"lightseekorg/kimi-k2.6-eagle3.1-mla","method":"eagle3","num_speculative_tokens":3}' \
  --language-model-only
```

这使得生产 vLLM 服务中的草稿模型升级平滑而轻松。

该支持已合入 vLLM 当前 main 分支，并将在 vLLM 的 nightly 发布以及即将发布的 **v0.22.0** 版本中提供。

作为一个早期数据点，我们在 SPEED-Bench 编程数据集上，用 vLLM（TP=4，GB200，非分离部署）在 Kimi-K2.6-NVFP4 上对 Kimi K2.6 EAGLE 3.1 草稿模型进行了基准测试。EAGLE 3.1 在并发为 1 时带来 **2.03× 的单用户输出吞吐量提升**，并且随着并发扩展加速仍保持可观（C=4 时 1.71×，C=16 时 1.66×）。

## 跨生态的开源协作

EAGLE 团队、vLLM 团队与 TorchSpec 团队之间的这次合作，是横跨算法研究、系统优化和训练基础设施的开源协作的典范。

EAGLE 团队持续精进投机解码算法，vLLM 帮助把这些创新大规模带入生产推理系统，TorchSpec 则为未来的投机解码算法提供高效训练与快速实验能力。

我们也感谢 NVIDIA 提供的 GPU 支持和持续合作。这些支持对于把 EAGLE 3.1 从算法创新推向实际部署所需的开发、验证和基准测试工作起到了重要作用。

我们希望携手继续抬高投机解码的整体基线，推动整个更广泛的 LLM 生态在 token 效率上取得进一步改进。
