# DeepSeek-V3.2 登陆 GB300：性能突破

> 原文：[DeepSeek-V3.2 on GB300: Performance Breakthrough](https://vllm.ai/blog/2026-02-13-gb300-deepseek) · vLLM 博客

作者：DaoCloud 与 vLLM 团队

[#硬件](https://vllm.ai/blog/tags/hardware)[#量化](https://vllm.ai/blog/tags/quantization)[#性能](https://vllm.ai/blog/tags/performance)

# 摘要

**DeepSeek-V3.2**（NVFP4 + TP2）已在 **GB300**（SM103 - Blackwell Ultra）上成功平稳运行。借助 FP4 量化，它在纯预填充场景下实现了 **7360 TGS**（tokens / GPU / second）的单 GPU 吞吐量。在混合上下文场景 *(ISL=2k,OSL=1k)* 下，输出吞吐量为 **2816 TGS**。

不过，与 DeepSeek-R1 相比，DeepSeek-V3.2 在 vLLM 中的推理性能仍有很大提升空间。

与此同时，使用 2 张 GB300 GPU，**DeepSeek-R1**（NVFP4 + EP2）可在纯预填充场景下达到 **22476 TGS***(ISL=2K,OSL=1,batch=256)* 的吞吐量，在混合上下文场景 *(ISL=2k,OSL=1k)* 下达到 **3072 TGS**。

与 **Hopper** 系列相比，**B300** 系列在预填充上有 **8x** 的性能提升，在混合上下文场景中有 **10-20x** 的提升。

> **注意：** 本博客侧重于架构与部署验证，而非极限吞吐量调优，结果反映的是可复现的基线性能。
>
> 所有实验均可用以下软件栈复现：
>
> - **vLLM**：v0.14.1
> - **CUDA**：13.0

# 基准测试设置

在本文中，我们在三个有代表性的基准测试场景下评估性能：

- **纯预填充场景**
  > 该场景将输出序列长度设为 **OSL =1**，因此执行时间主要由预填充阶段主导。它主要用于测量预填充吞吐量，并比较不同架构与并行策略处理长输入上下文的表现。
- **混合上下文场景（短输出）**
  > 该场景使用短输出长度 **ISL=2k, OSL= 64/128**，搭配长输入上下文。
- **混合上下文场景（中等输出）**
  > 这代表更贴近真实的在线服务工作负载，预填充与解码两个阶段都对执行时间有实质贡献。我们通常使用 **ISL=2k, OSL=1k** 来评估混合执行下的吞吐量。

以下是用于生成这些基准测试的示例命令：

```
vllm bench serve --model nvidia/DeepSeek-R1-0528-NVFP4 \
  --seed $RANDOM \
  --dataset-name random \
  --base-url http://${PROXY_NODE_IP}:8000 \
  --tokenizer /mnt/models/DeepSeek-V3.2 \
  --num-prompts 1000 \
  --max-concurrency $MAX_CONCURRENCY \
  --random-input-len $ISL \
  --random-output-len $OSL \
  --ignore-eos
```

所有图表均使用 `vllm bench serve` 报告的指标：

- 预填充吞吐量
  > 总 token 吞吐量（tok/s）
- 解码吞吐量
  > 输出 token 吞吐量（tok/s）

# FP4 权重量化的基础配置

Blackwell 最显著的特性之一是第五代 Tensor Core 对 NVFP4 的原生支持。

### 1. 从 Hugging Face 下载 NVFP4 模型权重

- [DeepSeek-V3.2-NVFP4](https://huggingface.co/nvidia/DeepSeek-V3.2-NVFP4)
- [DeepSeek-R1-0528-NVFP4](https://huggingface.co/nvidia/DeepSeek-R1-0528-NVFP4)

### 2. 使用 FlashInfer 提供的 FP4 MoE 内核

在 Blackwell 上运行 FP4 MoE 模型需要显式设置 VLLM\_USE\_FLASHINFER\_MOE\_FP4=1 来启用 FlashInfer FP4 MoE 内核。

```
export VLLM_USE_FLASHINFER_MOE_FP4=1
```

### 3. 服务模型

GB300/B300 单 GPU 内存为 288GB。两张 GPU 即足以容纳 DeepSeek 系列模型的 NVFP4 格式权重。

```
vllm serve nvidia/DeepSeek-V3.2-NVFP4    -tp 2
# or
vllm serve nvidia/DeepSeek-R1-0528-NVFP4 -tp 2
```

### 4. 优化配置

以下是使用附加参数 `--max-num-batched-tokens` 为 TP2 获得更好预填充吞吐量的最大边界批参考值：

```
# DeepSeek-R1-0528-NVFP4
--max-num-batched-tokens 32768

# DeepSeek-V3.2-NVFP4
--max-num-batched-tokens 20480
```

# Blackwell 架构带来的性能提升

## FP8 与 FP4 对比（DeepSeek V3.2）

在 **GB300（B300）** 上部署 **DeepSeek V3.2** 时，我们观察到一个显著的性能特征：**NVFP4 量化带来可观的性能收益，即便只使用标准配置一半的硬件资源（GPU 数量），也能取得更优的整体性能**。不过，实验结果也清楚表明，仅靠低精度不足以完全释放性能潜力，并行策略的选择同样关键。

数据突出了 **NVFP4 + TP2** 的明显优势。在纯预填充场景 *(ISL=2k, OSL=1, batch=64)* 中，TP2 相比 FP8 有 **1.8×** 的提升，总吞吐量最高达 7360 TGS。在混合上下文场景 *(ISL=2k, OSL=1k)* 中，输出吞吐量提高到 **2816 TGS**（**8×** 增益）。相比之下，`TP4` 配置的收益更为有限——预填充仅有 **14%**，混合上下文场景为 **2×** 提升，这使 `TP2` 的结果明显更高效。

这些收益来自两个因素：**内存开销降低与计算逻辑简化**。NVFP4 大幅缓解了内存带宽压力，这对提高输出 token 吞吐量至关重要。此外，注意力层内计算的简化直接优化了预填充阶段的端到端延迟。

**为什么我们推荐 NVFP4 + TP2 组合？**

结果表明，权重量化只是等式的一部分；另一个性能驱动力在于**并行度与单 GPU 工作负载之间的平衡**。NVFP4 显著降低了模型与 KV 缓存的占用，减轻带宽压力并支持更大的批大小。

在 TP2 配置下，每 GPU 的工作负载仍然足够大，使 Tensor Core 能充分发挥 FP4 更高的 Tensor Core FLOPs 与带宽效率。相反，`TP4` 更细粒度的划分稀释了每 GPU 的工作负载，使系统无法充分获得 NVFP4 带来的效率增益。

![](https://vllm.ai/blog-assets/figures/2026-02-13-deepseek/dsv32-fp4-vs-fp8-throughput.png)
> **提示：** 要使用 `FP8`，请切换到 FP8 模型权重，然后使用 `VLLM_USE_FLASHINFER_MOE_FP8=1`。
> 在 FP8 下，DeepSeek-V3.2 需要 4 张 GPU，使用 `-tp 4`。

## Blackwell Ultra 与 Hopper 对比（DeepSeek R1）

下图展示了在相同请求与 vLLM 设置下，GB300（NVL72）、B300（HGX）与上一代 H200 的单 GPU 总吞吐量对比：

- 在纯预填充 *(ISL=2k)* 场景中，GB300 的单 GPU 吞吐量比 B300 高 **14%**，比 H200 高 **8x**。
- 在短输出混合上下文场景 *(ISL=2k,OSL=128)* 中，GB300 的单 GPU 吞吐量比 B300 高 **12%**，比 H200 高 **20x**。

![](https://vllm.ai/blog-assets/figures/2026-02-13-deepseek/dsr1-h200-b300-gb300-throughput.png)

原因是多方面的：除 FP4 之外，B300 的 FLOPs 是 Hopper 系列的 7.5 倍（峰值约达 ~15 PFLOPs）。SM 的 SFU 模块对注意力层计算的优化为预填充带来了效率收益。

其 288GB 内存也是 H200 的 2 倍，内存带宽几乎翻倍。此外，相比 Hopper 的 FP8，Blackwell Ultra 高密度的 NVFP4 FLOPs 加速了 MoE 前向计算。这些都促成了解码阶段的大幅性能跃升。

> 参考：[Inside NVIDIA Blackwell Ultra](https://developer.nvidia.com/blog/inside-nvidia-blackwell-ultra-the-chip-powering-the-ai-factory-era/)

即使在小规模的节点内 `TP2` 配置下，GB300 相比 B300 也有小幅提升。

# 部署调优

## EP2 与 TP2 的选择

鉴于 DeepSeek-R1 的权重可以放进仅两张 B300 GPU 的 HBM，我们探讨了通过 DP 扩展时，基于 `TP2` 与基于 `EP2` 哪种更好。

> **注意：** 切换到 EP2 的 CLI 参数是 `-dp=2 --enable-expert-parallel`。

**a. 纯预填充场景 *(ISL=2k, OSL=1)***

`EP2` *(蓝色曲线)* 达到 **22476 TGS** 的吞吐量上限，在吞吐量与 TTFT 增长斜率两方面都优于 `TP2` *(绿色曲线)*。这得益于 EP 典型的“大包低频”通信模式，能在高并发下更好地利用 RDMA/NVLink 的高带宽。

不过，由于专家路由不均衡，蓝色 EP 曲线呈现出一定波动：不同批次命中不同的专家分布，导致专家负载与 all-to-all 通信量出现变化。

![](https://vllm.ai/blog-assets/figures/2026-02-13-deepseek/dsr1-ep2-tp2-throughput-prefill-only.png)

![](https://vllm.ai/blog-assets/figures/2026-02-13-deepseek/dsr1-ep2-tp2-ttft-prefill-only.png)

**b. 短输出混合上下文场景 *(ISL=2k,OSL=64)***

在 `TP2` 下，每个解码步骤都会引入 **GPU 间通信开销**，与 `EP2` 相比导致 TPOT 劣化 **50% 到 2×**。

不过，TP 也将 TTFT 改善约 **50%**，加速了每一步的执行。这一改善抵消了 TPOT 的劣化，最终使输出 token 的整体吞吐量获得 **5%–20%** 的提升。

![](https://vllm.ai/blog-assets/figures/2026-02-13-deepseek/dsr1-ep2-tp2-pd-throughput.png)
![](https://vllm.ai/blog-assets/figures/2026-02-13-deepseek/dsr1-ep2-tp2-pd-ttft.png)
![](https://vllm.ai/blog-assets/figures/2026-02-13-deepseek/dsr1-ep2-tp2-pd-tpot.png)

### 结论

- 对于 GB300 上分离式预填充的 DeepSeek-R1，EP 更适合作为预填充器（随后只需增加 DP 数量进行扩展）。EP 在预填充中拥有更高的吞吐量上限（峰值比 TP2 高约 10% - 15%），且 TTFT 随并发的增长更平缓，更有利于控制排队与尾延迟。
- 在 P+D 一体化部署中，策略取决于工作负载：
  - 当 ISL 大而 OSL 小时，预填充阶段成为主导瓶颈，建议使用 `TP2`，以避免注意力层延迟过大挤占解码阶段的 GPU 时间。
  - 相反，对于输出繁重的场景，`EP2` 的 TPOT 优势占主导，因此是首选配置。

## MTP 的收益

**MTP 能为解码带来可观的改进，但并非总是灵丹妙药。**

如下所述，内置草稿模型每次推测 1 个 token，在接受率与计算负载之间取得平衡。

```
--speculative-config.method mtp \
--speculative-config.num_speculative_tokens 1
```

当上下文长度不长时，在 GB300 上为 DeepSeek R1-0528 启用 MTP（蓝色）在一定并发范围（<=256）内比禁用 MTP（绿色）获得更高吞吐量（接受率可达 > 80%）。然而，高并发下启用 MTP 时吞吐量会急剧下降。

在混合上下文场景 *(ISL=2k,OSL=64)* 中，解码占比极低。MTP 多 token 预测的开销无法被摊销，导致每 token 计算量、内存压力与调度复杂度增加。低并发时开销无法摊销；高并发时它进一步挤占预填充批处理与系统并发。

因此，无论低并发还是高并发，整体吞吐量都低于禁用 MTP 时的水平。

![](https://vllm.ai/blog-assets/figures/2026-02-13-deepseek/dsr1-mtp-throughput.png)
![](https://vllm.ai/blog-assets/figures/2026-02-13-deepseek/dsr1-mtp-ttft.png)

![](https://vllm.ai/blog-assets/figures/2026-02-13-deepseek/dsr1-mtp-peak-output-throughput.png)

# DeepSeek V3.2 - 仍有很长的路要走

如下图所示，在相同的 GB300 设置下，DeepSeek R1 的预填充吞吐能力约为 DeepSeek V3.2 的 **3x**。

- DeepSeek R1 在 EP2 下峰值预填充吞吐量约达 **22476 TGS**。
- DeepSeek V3.2 在 EP2 下相对较弱，预填充峰值吞吐量约 **7360 TGS**。
- 在 TTFT 方面，两个模型都使用 TP2 时，R1 相比 V3.2 将延迟降低约 **55%**。

不过，在混合上下文场景 *(ISL=2k,OSL=1k)* 中，两个模型在输出吞吐量与 TPOT 上的差距并不明显。

![](https://vllm.ai/blog-assets/figures/2026-02-13-deepseek/dsr1-vs-v32-throughput.png)
![](https://vllm.ai/blog-assets/figures/2026-02-13-deepseek/dsr1-vs-v32-ttft.png)

**为什么 R1 的吞吐量总体上胜过 V3.2？**

主要原因在于 V3.2 引入了 Indexer/稀疏 MLA（Indexer + SparseAttnIndexer），并使用带有专用缓存结构的 `DeepseekV32IndexerBackend`。在预填充阶段，这带来了额外的量化/索引计算，从而降低吞吐量。性能剖析还显示，单个 DSA 层步骤的内核执行时间是 MLA 的 2.7 倍。

从 vLLM 代码角度看，除 Indexer 路径外，V3.2 与 R1 的 NVFP4 MoE 内核选择完全相同。因此，预填充性能差异主要来自 V3.2 的 Indexer/稀疏注意力开销。

DSA 的优势更适用于超长上下文。如果你的上下文不需要充分的注意力计算，额外开销就会很明显。但随着上下文长度进一步增加，DSA 在解码阶段的 TPOT 优势便会显现，在 10k-20k token 之间超越 MLA，并以约陡 6 倍的斜率领先。

最后，`DeepseekV32IndexerBackend` 仍相对较新、不够成熟，有很大的优化潜力。

因此，我们认为 DeepSeek-V3.2 仍有很大的提升空间。

# 分离式预填充（DeepSeek-V3.2）

下面是通过 RDMA 横向扩展网络进行 1P+1D 分离式预填充的快速上手教程（下一篇博客将介绍跨 GB 系列托盘使用 NVLink72 的技巧）。

```
# Prefill Node
export VLLM_USE_FLASHINFER_MOE_FP4=1
export UCX_NET_DEVICES=mlx5_bond_0:1   # optional, tell NIXL to use specific RDMA interface
export VLLM_NIXL_SIDE_CHANNEL_HOST=${PREFILL_NODE_IP}
vllm serve nvidia/DeepSeek-V3.2-NVFP4 -tp 2 --max-num-batched-tokens 20480 \
  --kv-transfer-config \
  '{"kv_connector":"NixlConnector","kv_role":"kv_both","kv_load_failure_policy":"fail","kv_buffer_device":"cuda"}' \
  --port 8000

# Decode Node
export VLLM_NIXL_SIDE_CHANNEL_HOST=${DECODE_NODE_IP}
...
# Exactly the same environment variables and vLLM CLI as Prefill Node, except `VLLM_NIXL_SIDE_CHANNEL_HOST`


# Proxy Node
cd vllm # move to vLLM source code and may need to install necessary dependencies
python tests/v1/kv_connector/nixl_integration/toy_proxy_server.py \
  --port 8000 \
  --prefiller-hosts ${PREFILL_NODE_IP}   --prefiller-ports 8000 \
  --decoder-hosts ${DECODE_NODE_IP}      --decoder-ports   8000

# If you have multiple Prefillers or Decoders:
# just append to hosts list, like: `--prefiller-hosts ${IP1} ${IP2}  --prefiller-ports 8000 8000 `

# vLLM bench against the proxy (using a random dataset and ISL=4k,OSL=1k)
vllm bench serve --model nvidia/DeepSeek-V3.2-NVFP4 \
  --seed $RANDOM --dataset-name random \
  --base-url http://${PROXY_NODE_IP}:8000 \
  --tokenizer /mnt/models/DeepSeek-V3.2   \
  --num-prompts 500    --max-concurrency 100 \
  --random-input-len 4096  --random-output-len 1024 \
  --ignore-eos
```

> **注意：** **vLLM v0.14.1 上的 PD 分离**：要在 vLLM v0.14.1 上运行 PD 分离，需要手动应用来自 [PR #32698](https://github.com/vllm-project/vllm/pull/32698) 的补丁。
> 不过，该功能已合并进最新的 vLLM main 分支，如果你使用更新的版本，可能不需要这个补丁。

我们使用 Nixl KV 连接器来促成跨进程/节点的 KV 传输。P 与 D 两个角色都使用 `TP2` 策略。

随着并发负载增加，分离部署相比一体化部署展现出吞吐量优势，且差距不断扩大，同时保持更低的延迟（TTFT 与 TPOT 皆然）。延迟增长的斜率也更加稳定。

在 TPOT 方面，1P1D 与 3P1D 都优于非分离部署。在批大小为 256 时，分离部署将 TPOT 控制在 60ms 以内，而一体化部署超过 80ms。

![](https://vllm.ai/blog-assets/figures/2026-02-13-deepseek/dsv32-pd-disagg-throughput.png)
![](https://vllm.ai/blog-assets/figures/2026-02-13-deepseek/dsv32-pd-disagg-tpot.png)

当 ISL 持续增长（从 2K 到 8K）时，1P1D 配置的吞吐量开始吃紧，预填充成为瓶颈。请求在 P 节点排队等待，无法充分利用解码器的算力。增加 2 个 P 副本（3P1D）后，它们可以并行处理更多请求的预填充阶段，获得更好的总吞吐量。

尽管分离部署的单 GPU 吞吐量可能不是最高的，但通过投入更多硬件，可以获得更好的 Goodput 与 SLO 保障。

![](https://vllm.ai/blog-assets/figures/2026-02-13-deepseek/dsv32-pd-disagg-throughput-isl8k.png)
