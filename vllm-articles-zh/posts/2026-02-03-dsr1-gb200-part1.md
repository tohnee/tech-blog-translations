# 推动 vLLM WideEP 与大规模服务在 Blackwell 上走向成熟（第一部分）

> 原文：[Driving vLLM WideEP and Large-Scale Serving Toward Maturity on Blackwell (Part I)](https://vllm.ai/blog/2026-02-03-dsr1-gb200-part1) · vLLM 博客

作者：Meta 与 NVIDIA 团队

[#大规模服务](https://vllm.ai/blog/tags/large-scale-serving)[#性能](https://vllm.ai/blog/tags/performance)[#硬件](https://vllm.ai/blog/tags/hardware)

# 引言

在[此前的工作](https://blog.vllm.ai/2025/12/17/large-scale-serving.html)以 wide-EP 实现 2.2k tok/s/H200 解码吞吐量的基础上，vLLM 团队继续针对 NVIDIA GB200 平台开展性能优化。本文详细介绍使 vLLM 在 GB200 上、针对包括 DeepSeek R1/V3/V3.1 在内的 DeepSeek 风格 MoE 模型，在 **2K 输入 token 与 2K 输出 token** 工作负载下实现 **26.2K 预填充 TPGS（每 GPU 每秒 token 数）** 与 **10.1K 解码 TPGS** 的关键优化。上述数字通过如下部署测得：4 个预填充实例（每个 2 张 GB200）与 1 个解码实例（8 张 GB200），全部采用数据并行（DP）与专家并行（EP）的组合。

这些收益来自一系列新优化的组合：

**新优化：**

- 低精度运算（[NVFP4](https://developer.nvidia.com/blog/introducing-nvfp4-for-efficient-and-accurate-low-precision-inference/) GEMM、FP8 GEMM、NVFP4 MoE Dispatch）
- 内核融合（RoPE+Quant+Q 写入、RoPE+Quant、Concat K）
- 通过权重卸载缩减预填充规模
- 最小化分块开销

**此前已讨论的特性：**

- 异步调度
- 预填充/解码分离服务

GB200 更强的计算能力与这些针对性优化相结合，使吞吐量相较 H200 部署有显著提升。

# 结果

以下基准测试在 2K 输入 token 与 2K 输出 token 的固定工作负载下，比较了 vLLM 在 GB200 与 H200 上处理 DeepSeek-V3/R1 工作负载的性能。详细部署设置见下表。

![](https://vllm.ai/blog-assets/figures/2026-02-03-dsr1-gb200/topline_comparison.png)

| 部署设置 | H200 | GB200 |
| --- | --- | --- |
| 预填充 | 16 GPU | 8 GPU（4 实例 x 2 GPU） |
| 解码 | 32 GPU | 8 GPU（1 实例 x 8 GPU） |

GB200 更高的内存带宽（8 TB/s 对 4.8 TB/s）、借助 FP4 获得的更高计算吞吐量，以及 CPU 与 GPU 之间的 NVLink-C2C 互连，都为这些收益做出了贡献。我们通过应用下述优化将这一潜力发挥到最大。

我们还在 GB200 上对一系列标准工作负载测试了 DeepSeek-V3/R1 的解码吞吐量，在保持相同并行设置的同时，改变能充分利用 GPU 内存的解码批大小。

复现所有基准测试结果的说明可在[这里](https://github.com/vllm-project/vllm/issues/33583)找到。

# 关键优化

## 低精度运算

与 H200 相比，GB200 为 FP4 与 FP8 运算带来了显著更高的吞吐量。vLLM 通过多项精度优化来利用这些能力。

### NVFP4 GEMM（MoE GEMM、O-proj）

DeepSeek-V3/R1 模型的 MoE 专家权重与输出投影层可以量化为 FP4 精度。vLLM 集成了 FlashInfer 的 TRTLLM-Gen GEMM 内核，专门针对 GB200 的 FP4 Tensor Core 做了优化。

FP4 检查点格式以打包的 4 比特表示存储权重，并附带分组缩放因子。在运行时，TRTLLM-Gen 内核在 Tensor Core 内部即时反量化，在保持模型质量的同时实现接近原生的 FP4 吞吐量。

关键实现细节：

- 以打包格式存储的 FP4 权重与 FP8 或 FP16 缩放因子
- 针对 GB200 Tensor Core 调度优化的 FlashInfer TRTLLM-Gen 内核
- 应用于 MoE 专家 GEMM 与注意力输出投影（O-proj）

### 面向 MLA 的 FP8 GEMM

对于 DeepSeek 的多头潜在注意力（MLA），查询上投影（从潜在空间到完整查询维度）可从 FP8 量化中受益。与 FP4 能提供最佳吞吐/精度权衡的 MoE 层不同，注意力投影对量化更敏感，FP8 更高的精度有利于保证准确性。

vLLM 为这些投影使用优化的 FP8 GEMM 内核，在保持注意力质量的同时，相较 FP16 实现显著加速。

### NVFP4 MoE Dispatch

除专家 GEMM 本身之外，MoE dispatch 操作——将 token 路由到其被分配的专家——同样可以从更低精度中受益。vLLM 实现了 NVFP4 dispatch，在 all-to-all 通信之前将 token 激活值量化为 FP4。

与 FP16 dispatch 相比，这将 all-to-all 通信量降低 4 倍，显著减少了 EP 部署中 GPU 间的通信延迟。量化开销被通信节省所摊销，带来净吞吐量收益。

## 内核融合

我们采用了多种内核融合策略，通过将多个操作合并为单个 GPU 内核来降低内存带宽消耗与内核启动开销。

### RoPE + Quant + Q 写入（解码）

在解码过程中，查询投影需要：

1. 应用 RoPE（旋转位置编码）
2. 为后续 GEMM 进行量化
3. 写入查询缓冲区

vLLM 将这三个操作融合为单个内核，消除了两次中间内存往返。

![解码中的 RoPE+Quant+Q 写入融合](https://vllm.ai/blog-assets/figures/2026-02-03-dsr1-gb200/rope_quant_fusion_timeline.png)

解码中的 RoPE+Quant+Q 写入融合

### RoPE + Quant（预填充）

预填充阶段同理，RoPE 应用与量化被融合在一起。预填充路径处理更大的 token 批次，使融合带来的内存带宽节省更加可观。

### Concat K 优化

对于 MLA 键投影，vLLM 使用 FlashInfer 的 `concat_mla_k` 内核实现了一个优化的拼接操作。在 DeepSeek 的 MLA 架构中，键张量由两部分组成：非位置嵌入部分（k\_nope，每头一份）与旋转位置嵌入部分（k\_rope，所有头共享）。这两部分必须拼接起来才能构成完整的键张量。

朴素做法需要拷贝 k\_nope，并把 k\_rope 广播到全部 128 个头，导致大量内存带宽消耗。FlashInfer 的 `concat_mla_k` 内核实现了多项优化：

- **基于 warp 的处理**：每个 warp 处理一个 (token, head\_chunk) 对，一次处理 16 个头
- **向量化内存访问**：nope 数据使用 8 字节向量加载，rope 数据使用 4 字节加载，最大化内存吞吐
- **带 L2 预取的软件流水线**：在处理当前行的同时预取下一行，隐藏内存延迟
- **rope 值的寄存器复用**：由于 rope 为所有头共享，只需加载一次到寄存器，然后写入该块中全部 16 个头，避免冗余的内存加载

## 缩减预填充规模

### 为什么缩减规模是合理的

在为面向吞吐量的推理服务考虑 GPU 数量时，我们通常横向扩展以容纳模型，或对内存（专家、上下文）分片以增大批大小。然而，对于已经受计算限制的预填充工作负载，减少 GPU 数量反而可以通过降低通信开销来提升吞吐量。

我们的微基准测试显示，当批大小从 16K 增加到 64K token 时，MLA 后端的吞吐量开始趋于平稳。超过 64K token 后，MoE 吞吐量收益也可忽略不计。这意味着我们可以用适配 2 GPU 服务配置的批大小就让计算利用率饱和。

![MLA 与 MoE 吞吐量在约 64K 批大小时趋于平稳](https://vllm.ai/blog-assets/figures/2026-02-03-dsr1-gb200/mla_trtllm_ragged_prefill_prefill.png)

通过把 GPU 数量从 4 减少到 2，我们将 EP 通信所需的 NCCL 集合通信（all\_gather 与 reduce\_scatter）减半，显著降低通信开销。

### 权重卸载 v2

为了在保持性能的同时减少 GPU 内存占用，vLLM 实现了带异步预取的权重卸载 v2。这一 v2 实现受 [SGLang prefill](https://github.com/sgl-project/sglang/pull/8034) 中卸载方案的启发，并做了调整，以额外兼容 vLLM 内的 torch.compile 与 CUDA Graph。

在 vLLM 权重卸载 v1 中，被卸载的权重保留在 CPU 上，并通过统一虚拟寻址（UVA）访问，这会带来缓慢的 PCIe 传输延迟。这是为 GPU 资源受限情况下运行模型准备的最后手段。

权重卸载 v2 采用了不同思路：它提前显式地把权重拷贝（载入，onload）到 GPU。关键创新在于在单独的 CUDA 流上异步载入下一层的权重。通过精心地将权重载入与内核执行重叠，载入延迟可以被完全隐藏。

用户通过基于分组的配置来设置卸载：
![](https://vllm.ai/blog-assets/figures/2026-02-03-dsr1-gb200/layer_group.png)

- `group_size`：每 N 层为一组
- `num_in_group`：每组卸载这么多层（每组的最后 N 层）
- `prefetch_step`：向前预取的层数

对于 DeepSeek-R1 预填充服务，我们每两个 MoE GEMM 权重卸载一个，在保持满吞吐量的同时实现了可观的内存节省。

![显示权重载入与层执行重叠的 Trace](https://vllm.ai/blog-assets/figures/2026-02-03-dsr1-gb200/onloading_trace.png)

显示权重载入与层执行重叠的 Trace

GB200 在 CPU 与 GPU 之间的 NVLink-C2C 连接使权重卸载 v2 尤为有效，因为与基于 PCIe 的系统相比，载入延迟被降到最低。

## 最小化分块开销

MoE 模型的大批处理需要分块才能符合 GPU 内存限制。然而，较小的块会因反复的内核启动与同步带来开销，形成 GPU 气泡。vLLM 提供了块大小配置选项，以便在内存限制内最大化吞吐量。

### MoE DP 块

在使用数据并行加专家并行（DP+EP）时，token 以协调的块从每个 DP rank 派发。`VLLM_ENABLE_MOE_DP_CHUNK` 标志（默认启用）开启这一分块行为。

更大的块通过把派发/聚合开销分摊到更多 token 上来减少 GPU 气泡。块大小由 `VLLM_MOE_DP_CHUNK_SIZE` 控制（默认：256 token）。增大该值可通过降低同步频率来提升吞吐量。

对于 GB200，我们在预填充时禁用 MoE DP 分块（`VLLM_ENABLE_MOE_DP_CHUNK=0`），并在解码时把 `VLLM_MOE_DP_CHUNK_SIZE` 设置为与批大小一致。

### MoE 激活值块

对于大型预填充批次，vLLM 会对激活值张量分块，让 token 子集逐批通过 MoE 层。`VLLM_ENABLE_FUSED_MOE_ACTIVATION_CHUNKING` 标志控制这一行为（默认启用）。

更大的块通过降低启动开销、提供充足的工作量以充分利用 GPU 算力来提升吞吐量。块大小由 `VLLM_FUSED_MOE_CHUNK_SIZE` 控制（默认：16K token）。最优设置是在可用 GPU 内存内最大化块大小。

对于 GB200，我们禁用激活值分块（`VLLM_ENABLE_FUSED_MOE_ACTIVATION_CHUNKING=0`）以最大化吞吐量，因为更大的内存容量足以在不分块的情况下容纳完整批次。

### 输出处理块

在 V1 引擎的异步服务路径中，输出处理（logit 计算、采样、响应生成）是分块的。`VLLM_V1_OUTPUT_PROC_CHUNK_SIZE` 控制每次迭代处理的输出数量（默认：128）。

更大的块通过降低每块开销提升整体吞吐量。然而，对于流式工作负载，过大的块可能增大消息间延迟的波动。对于 GB200 上面向吞吐量优化的解码，我们把块大小设为 2048。

# 未来工作

vLLM 团队正在为 GB200 部署积极推进以下改进：

1. **改进负载均衡并扩大 EP 规模**：扩展专家负载均衡以应对更大的 EP 度与更动态的工作负载，并改进重均衡算法。
2. **优化 MoE dispatch 延迟**：通过内核优化与通信调度进一步降低 all-to-all dispatch 操作的延迟。
3. **通过计算-通信重叠隐藏通信延迟**：通过更激进的重叠策略，在受通信限制的场景中实现更高的 GPU 利用率。
4. **在 GB300 上扩展 WideEP 与大规模服务**：利用 GB300 更强的 HBM 与算力，我们希望进一步推进 WideEP 与大规模服务工作，以更小的主机占用实现更高的 TPGS。

最新参考请见 [roadmap.vllm.ai](http://roadmap.vllm.ai)。

# 总结

- vLLM 在 DeepSeek 风格 MoE 模型上实现 26.2K 预填充 TPGS 与 10.1K 解码 TPGS，相较 H200 提升 3-5 倍。
- 低精度运算（NVFP4 GEMM、FP8 GEMM、NVFP4 dispatch）充分利用了 GB200 增强的 Tensor Core 能力。
- 内核融合降低了内存带宽压力与内核启动开销。
- 通过权重卸载 v2 缩减预填充规模，在保持计算饱和的同时降低 EP 通信开销。
- 通过环境变量控制的分块优化将大批处理的开销降至最低。
