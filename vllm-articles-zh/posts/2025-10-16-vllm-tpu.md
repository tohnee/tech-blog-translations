# vLLM TPU：在 TPU 上同时支持 PyTorch 与 JAX 的全新统一后端

> 原文：[vLLM TPU: A New Unified Backend Supporting PyTorch and JAX on TPU](https://vllm.ai/blog/2025-10-16-vllm-tpu) · vLLM 博客

作者：Google 团队

[#硬件](https://vllm.ai/blog/tags/hardware)

![](https://vllm.ai/blog-assets/figures/vllm-tpu/vllm-tpu.png)

vLLM TPU 现在由 [tpu-inference](http://tpu.vllm.ai) 驱动——这是一个表现力强且功能强大的全新硬件插件，将 [JAX](https://docs.jax.dev/en/latest/index.html) 与 [PyTorch](https://pytorch.org/get-started/locally/) 统一到单一的 lowering 路径之下。它不仅比上一代 vLLM TPU 更快，还提供更广的模型覆盖与特性支持。vLLM TPU 是一个面向开发者的框架，可以：

1. 在开源中挑战 TPU 硬件**性能**的极限。
2. 为 JAX 和 PyTorch 用户提供更多**灵活性**：无需任何额外的代码修改即可在 TPU 上高性能地运行 PyTorch 模型定义，同时把原生支持扩展到 JAX。
3. 延续 vLLM 的**标准化**：保持一致的用户体验、遥测与接口。

![](https://vllm.ai/blog-assets/figures/vllm-tpu/whats-new.png)

### vLLM TPU

2025 年 2 月，就在 [vLLM 的 V1 集成](https://docs.vllm.ai/en/latest/usage/v1_guide.html)刚刚成型之际，一个由 Googlers 和 vLLM 核心贡献者组成的「小而强悍」团队给自己定下了一个目标：赶在 [Cloud Next 2025](https://cloud.withgoogle.com/next/25) 之前，为少量模型推出一个高性能的 TPU 后端。在随后的两个月里，他们遇到了若干挑战，包括：

- **vLLM V1 集成**：团队必须接入新的 V1 代码路径，这需要一个全新的 ragged paged attention 内核（[RPA v2](https://github.com/pytorch/xla/blob/master/torch_xla/experimental/pallas_kernels/ragged_paged_attention_v2.py)）。这主要是为了支持分块预填充与前缀缓存等特性。虽然这些 KV 缓存管理技术在 TPU 上并不新鲜，但要以「对 TPU 友好」的方式将它们与 vLLM 的分页注意力结合设计，颇具挑战。
- **多程序多数据（[MPMD](https://en.wikipedia.org/wiki/Flynn%27s_taxonomy#Multiple_programs,_multiple_data_streams_(MPMD))）**：当时 vLLM 完全使用 MPMD 来协调跨进程通信。这与 TPU 以编译器为中心的编程模型形成鲜明对比——后者大量依赖单程序多数据（[SPMD](https://en.wikipedia.org/wiki/Single_program,_multiple_data)）来重叠多设备、多主机之间的通信。
- **PyTorch/XLA（[PTXLA](https://github.com/pytorch/xla)）**：PyTorch/XLA 框架能够在 TPU 上原生运行 PyTorch 代码，因此让 vLLM 集成变得更容易；但在栈的更低层级进行优化时，团队遇到了不少挑战。

尽管有这些阻碍，团队仍将 v6e-1 上 Llama 3.1-8B 的吞吐量性能提升了 **3.6x**，将 v6e-8 上 Llama 3.1-70B 的吞吐量性能提升了 **2.1x**。vLLM TPU 也登上了 [Cloud Next 的大舞台](https://www.youtube.com/live/Md4Fs-Zc3tg?si=t3V52Kac5Y5VTNN0&t=1137)。你可以在[这里](#bringing-it-all-together)查看这些工作负载的性能演进。

### 由 TPU-inference 驱动的 vLLM TPU

虽然基于 PTXLA 的 vLLM TPU 是一项重大成就，但我们仍需在开源中继续挑战 TPU 性能的极限。我们还希望以尽可能高性能的方式在 TPU 上原生支持 PyTorch 和 JAX 模型，从而把 TPU 与 vLLM 两大生态汇聚起来。

#### PyTorch 与 JAX 的统一后端

这次基于 [tpu-inference](http://tpu.vllm.ai) 的 vLLM TPU 全新设计，旨在通过在单一的统一 JAX→XLA lowering 路径中支持 PyTorch（经 [Torchax](https://google.github.io/torchax/)）和 [JAX](https://docs.jax.dev/en/latest/index.html)，来优化性能与可扩展性。

与 PyTorch/XLA 相比，JAX 是一套更成熟的栈，其[原语（primitives）](https://docs.jax.dev/en/latest/jax-primitives.html)通常具有更好的覆盖与性能，在实现复杂并行策略时尤其如此。

因此，vLLM TPU 现在对所有 vLLM 模型都使用 JAX 作为 lowering 路径，从而获得显著的性能提升——即使模型定义是用 PyTorch 写的。这一决策让我们能更快、更聪明地前进：把更高层的框架抽象掉，专注于内核开发与编译器优化。请记住，对 XLA 而言，Torchax 和 JAX 在编译之前使用的是同一套高性能原语。更多细节见[这里](https://github.com/vllm-project/tpu-inference/blob/main/docs/developer_guides/torchax_model_development.md)。

虽然这是我们目前的设计，但我们始终会力求在 TPU 上实现尽可能好的性能，并计划在未来为 vLLM TPU 评估原生的 PyTorch 移植。

> **重要：** **要点 1**：vLLM TPU 现在用 JAX lowering 所有模型。无需对模型代码做任何改动（例如 [llama.py](https://github.com/vllm-project/vllm/blob/main/vllm/model_executor/models/llama.py)），vLLM TPU 的吞吐量性能就提高了约 20%——仅仅因为它现在利用 JAX 成熟、高性能的原语来生成随后由 XLA 编译的 HLO 图。

#### 细看内部机制

1. 安装

   ```
   pip install vllm-tpu # a single install path
   ```

   因为 Torchax 和 JAX 在底层本质上就是 JAX，所以无论模型代码是用 PyTorch 还是 JAX 写的，我们都可以使用同一条安装路径。这保证了依赖的一致性，用户不必为不同模型管理不同的依赖要求。
2. 服务一个模型

   ```
   MODEL_ID="google/gemma3-27b-it" # model registered in tpu-inference or vllm
   vllm serve $MODEL_ID
   ```

   在 TPU 上服务模型时，有两个可以拉取模型代码的模型注册表：

   1. tpu-inference（*默认，[列表](https://github.com/vllm-project/tpu-inference/tree/main/tpu_inference/models/jax)*）
   2. vllm（维护于 *vLLM 上游，[列表](https://github.com/vllm-project/vllm/blob/main/vllm/model_executor/models/registry.py)*）

让我们更近距离地看看底层发生了什么：

![](https://vllm.ai/blog-assets/figures/vllm-tpu/vllm-serve-model.png)

这一统一化工作通过复用 vLLM 社区的已有成果来减少重复，从而腾出更多时间优化 TPU 内核与 XLA 编译器。对 PyTorch（经 Torchax）和 JAX 模型来说，所有内核与编译器都是共享的。

> **重要：** **要点 2**：vLLM TPU 现在会默认运行 tpu-inference 中经过 TPU 优化的模型代码（如果存在），否则回退到 vLLM 上游的 PyTorch 模型代码（经 [Torchax](https://google.github.io/torchax/user_guide/how-it-works/) 用 JAX lowering）。对大多数用户来说，这只是实现细节。

*既然 Torchax 能够开箱即用地在 TPU 上运行 PyTorch 模型代码，而且仍是用 JAX JIT 编译，为什么我们还要在 tpu-inference 中重写一些模型？这难道不是重复劳动吗？*

我们提供了几个参考模型，帮助开发者缩短为 TPU 优化模型之前的上手曲线（见[这里](https://github.com/vllm-project/tpu-inference/tree/main/tpu_inference/models/jax)）。有趣的是，我们观察到经 torchax lowering 的模型与简单重写的 JAX 模型性能大致相同，这证明了 torchax 在转换高层模型方面非常高效。

真正的性能收益、以及我们支持重写模型的原因，来自针对 TPU 优化 JAX 代码并直接利用 TPU 架构的优势。

我们需要这种灵活性的原因是：vLLM 开发者在实现模型时所做的逻辑设计选择并不总是有利于 TPU。造成差异的不是 JAX 与 Torchax 之分，而是 GPU 与 TPU 本身不同，需要不同的优化策略。

> **重要：** **要点 3**：对任何模型来说，底层*全都是* JAX！除非实现中的逻辑差异导致 TPU 性能受损，否则模型不太可能从用 JAX 原生重写中获益。话虽如此，如果重写模型能让我们充分发挥 TPU 的潜力，保留这种重写的灵活性也很重要。

#### Ragged Paged Attention V3：开源中面向 TPU 推理最灵活、高性能的注意力内核

尽管 Ragged Paged Attention v2 内核带来了大幅的性能提升，但为了开箱即用（OOTB）地支持更多模型和用例，它需要变得更加灵活。

1. RPA v2 只能支持头维度为 128 的模型规格。
   - **更多模型**：RPA v3 灵活得多，支持任意模型规格、量化数据类型和任意张量并行（TP），开箱即用地支持更多模型。
2. RPA v2 由于要顺序执行 KV 缓存更新与注意力操作而存在流水线低效问题。
   - **更好的性能**：RPA v3 将 KV 缓存更新（scatter）融合进 RPA 内核，从而改善流水线效率。这一设计在内核执行期间能*完全*隐藏 scatter 延迟。
3. RPA v2 在解码为主或长度不一的预填充任务中可能造成显著浪费。
   - **更强的部署灵活性**：RPA v3 会编译成 3 个子内核，从而支持纯预填充、纯解码和混合批处理。该设计在运行时将正确的子内核配给相应的请求，大幅节省直接内存访问（DMA）与计算量。
   - 这还带来一个额外好处：解锁了更复杂的部署模式，如分离式服务。
4. 虽然 RPA v2 相比第一个 TPU 原型取得了显著的吞吐量提升，但它缺乏灵活性。
   - **毫无妥协**：RPA v3 没有为了灵活性牺牲性能；事实上，在 Trillium（v6e）上它的吞吐量比 RPA v2 提高了约 10%。模型现在也可以在 v5p 上运行（尽管还需要额外调优）。

我们很快会写一篇关于 RPA v3 的技术深度解析，敬请关注我们的文档。

> **重要：** **要点 4**：RPA v3 兼具灵活性与高性能，是开源中生产级 Pallas 内核开发的优秀范本。我们期待对 TPU 友好的 MoE 与 MLA 内核也能以同样方式很快进入开源。

#### 单程序多数据（SPMD）

本版本引入单程序多数据（[SPMD](https://en.wikipedia.org/wiki/Single_program,_multiple_data)）作为 vLLM TPU 的默认编程模型。与之前的多 worker 模型（改编自 GPU 范式）不同，SPMD 是 XLA 编译器的原生模型。开发者只需针对单个巨大的设备编写代码，XLA 编译器会自动划分模型与张量，并插入通信操作以实现最优执行。

> **重要：** **要点 5**：SPMD 支持让通信与计算重叠等高级优化。SPMD 代表着向更深入、更原生的 TPU 集成的战略性转变，有望通过以 TPU 为中心、编译器优先的运行模式带来更高性能。

从 2025 年 2 月的原型性能起步，vLLM TPU 已经走过了一条漫长的路：在相同工作负载上性能提升了近 **2x-5x**，同时模型覆盖与易用性也在不断改善。

### 模型、特性与未来计划

我们可以把这个版本视为奠基之作，因为 vLLM TPU 此后将在开源中定期发布版本。每个新版本都会由 CI/CD 发布经过审核的 vLLM 原生模型列表文档。我们还将维护一份经过压力测试的 tpu-inference 模型列表，主要作为 JAX 用户的参考。所有特性在发布前也都会经过严格测试。

支持的模型家族

- 稠密（Dense）模型
- 多模态（仅限 tpu-inference 模型）

> **注意：** **关于模型支持的说明**：在我们落地更多能力之前，建议从[这里](https://github.com/vllm-project/tpu-inference/blob/main/support_matrices/model_support_matrix.csv)的压力测试模型列表入手。我们仍在向 tpu-inference 添加组件，以提升更大规模、更高复杂度模型（XL MoE、视觉编码器、MLA 等）的性能。如果你希望我们优先支持某个特定方向，请在 GitHub 提交 feature request（[这里](https://github.com/vllm-project/tpu-inference/issues/new/choose)）。

支持/已验证的 TPU 世代

- Trillium（v6e）、v5e

特性

- 前缀缓存
- 分块预填充（Chunked Prefill）
- 多模态输入
- 单程序多数据（SPMD）
- 结构化解码
- 投机解码：Ngram
- 树外（out-of-tree）模型支持
- 优化的运行时采样（top k、top p、temperature、logit 输出）
- 量化（权重、激活值与 KV 缓存）

对 TPU 友好的内核

- Ragged Paged Attention V3
- 集合通信矩阵乘（Collective Communication Matmul）
- 量化的矩阵乘、注意力与 KV 缓存

实验性特性

- v5p
- 多模态（经 Torchax）
- 多 LoRA
- 投机解码：基于树的 Eagle 3
- 单主机 P/D 分离服务
