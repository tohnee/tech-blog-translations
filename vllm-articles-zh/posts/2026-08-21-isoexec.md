# IsoExec：统一执行以消除 SkyRL 中训练与推理的不一致

> 原文：[IsoExec: Unified Execution to Eliminate Trainer-Inference Mismatch in SkyRL](https://vllm.ai/blog/2026-08-21-isoexec) · vLLM 博客

作者：Alexander Jiang 与 SkyRL 团队

[#强化学习](https://vllm.ai/blog/tags/reinforcement-learning)[#性能](https://vllm.ai/blog/tags/performance)

## TL;DR

理论上，on-policy RL 假设 rollout 与训练评估的是同一个策略。实践中，RL 训练系统通常用两个独立的引擎分别负责 rollout 与训练，二者具有不同的模型定义、内核、批形状与并行布局。由于浮点运算不满足结合律，即便执行的是同一个策略，这些差异也可能改变 token 概率。这会让新的 RL 算法、对评测框架（harness）与环境的改动，以及 RL 基础设施与硬件内核的改进变得难以调试。

为解决这一问题，我们提出 **IsoExec**——一个跨框架的统一执行抽象，用于消除 RL 工作负载中训练引擎与推理引擎之间的不一致。IsoExec 包含两个组件：一个**执行契约**，规定并强制跨引擎影响浮点舍入的执行细节；以及一个**统一模型**，带有对齐的、批不变的内核，在训练与 rollout 之间逐位一致。我们在 SkyRL 中结合 vLLM 与 Megatron 实现了 IsoExec。在单台 8×H100 节点上，进行同步的 Qwen3.5-35B-A3B DAPO 训练时，我们把端到端的 rollout 相对训练的平均 logprob 差降低到 $10^{-6}$ 以下，50 步内相比当前 SkyRL 基线的开销为 25%。

我们的主要贡献是：

- **统一执行契约：** 训练与推理共用一份数值执行契约，以最小开销实现契约覆盖范围内零不一致，并为新 RL 算法、RL 环境与评测框架的改动以及内核改进带来低调试成本。
- **并行不变内核：** 在张量并行、专家并行与序列并行下保持数值一致。
- **分块并行递归（CPR）Gated DeltaNet：** 对齐训练、预填充与递归解码，而无需把长序列前向串行化。

## 引言

RL 工作负载需要把同一个策略执行两次：生成 rollout（rollout 引擎）与训练策略（训练器）。rollout 引擎在策略 $μ$ 下采样一个 token；训练器随后用相同的模型参数在策略 $π$ 下重新计算其 log 概率。在同步 RL 下，典型的 on-policy 训练假设 $μ=π$（无训练-推理不一致）。从系统视角看，由于浮点非结合性，真正的 on-policy 训练很难实现：

$(a+b)+c\ne a+(b+c).$

RL 系统通常在 Megatron 与 FSDP 等训练系统之外，搭配 vLLM 与 SGLang 等现有推理系统。这些系统针对不同工作负载优化，使用不同的内核、批形状、执行模式（训练、预填充与解码）与分布式布局。因此，在执行同一个数学模型时，它们可能使用不同的归约顺序，导致不同的输出 token 概率分布。

字节跳动的 [VeXact 研究](https://arxiv.org/abs/2605.14220)表明，仅不一致本身就足以让 REINFORCE 与 GRPO 运行失稳，在 KL 估计器反应之前就扭曲按优势加权的损失贡献，并让基于重要性采样或拒绝采样的修复对校准高度敏感。[Fireworks](https://fireworks.ai/blog/frontier-lab-training-infrastructure-as-a-service) 报告了一次训练-推理 KL 约为 0.013 的 GLM-5.2 运行，其中裁剪丢弃了约 45% 的 token，奖励在第 20 步左右崩溃；而一次逐位对齐的运行没有丢弃任何 token 并保持稳定。

此前关于系统确定性的工作只解决了问题的一部分。[Thinking Machines](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/) 形式化了批不变性：批次中的其他元素以及批大小都不应影响对特定元素的计算。[vLLM × TorchTitan](https://vllm.ai/blog/2025-11-10-bitwise-consistent-train-inference) 的逐位一致性工作表明，把匹配的内核导入两个引擎可以达到一致，但仍需要两份对齐的模型副本。更近期的 [Zero Train–Inference Mismatch for Linear Attention and Async RL](https://yichuan-w.github.io/blog/GDN-train-inference-mismatch-asyncRL/) 工作在 TorchTitan 训练器与 vLLM 生成器之间共享同一份模型定义，并把一致性扩展到 [Gated DeltaNet](https://arxiv.org/pdf/2412.06464)，所有前向计算都使用递归形式，同时为反向保留分块内核。[Tree-Based Invariant Kernels (TBIK)](https://arxiv.org/abs/2511.17826) 则专注于在不同并行配置下实现逐位一致。

IsoExec 用执行契约与统一模型消除训练-推理不一致。**执行契约**以框架无关的形式捕捉对舍入敏感的执行细节（例如内核实现、累加 dtype、归约顺序），并在每个运行时中强制执行。**统一模型**使用的内核经过验证，在训练、预填充与解码之间逐位一致。它与 vLLM 的引擎特性（例如调度器、KV 缓存管理器与 CUDA Graph 捕获）以及 Megatron 的训练栈集成。

## 统一执行契约

IsoExec 的核心是**执行契约**，它声明两个运行时都必须以相同方式指定的每一个影响比特的执行选择。

```
"ExecutionContract": {
  "cases": [ ... ],        // logprob computations: trainer_fwd, engine_decode, etc.
  "composition": [ ... ],  // (region, case) -> implementation + pinned constants
  "claims": { ... },       // topology invariance, state invalidation, tolerances
  "identities": { ... }    // semantic / numerical_policy / deployment digests
}
```

契约按**用例（case）**处理 token logprob 的每一次计算（例如 rollout 的 `engine_prefill` 与训练器的 `trainer_fwd`）。模型的前向算子被划分为**区域（region）**，即由一个内核实现的运算片段，一个内核可能融合多个操作。对每个（区域，用例）对，**组合（composition）**选择实现及其固定的常量。常量涵盖任何可能改变比特的参数，包括累加与边界 dtype，以及 split-K 和 split-KV 分区数等归约分解参数。每个算子区域都必须先在各用例间通过逐位精确性测试，其实现才能注册进组合。

例如：

```
"composition": [
  {
    "region": ["gdn.core", "gdn.gating", "norms.l2"],
    "cases": ["trainer_fwd", "trainer_fwd_no_autograd", "engine_prefill", "engine_decode"],
    "impl": {"id": "native_fused_sigmoid", "version": 1, "arch": "sm90"}
  },
  {
    "region": ["moe.combine"],
    "cases": ["engine_prefill", "engine_decode"],       // the trainer side is its own entry
    "impl": {"id": "pik_leaf_tree", "version": 2, "arch": "sm90"},
    "constants": {"leaves": 8, "leaf_dtype": "fp32"},
    "discharge": {"kind": "equivalence_proof", "ref": "gates/ep_invariant_combine"} // proved equivalence
  }
]
```

**声明（claims）**陈述组合的保证成立的条件，并在运行时强制执行。例如，一个拓扑声明列出某个归约树被证明逐位不变的并行尺寸。安装内核时，适配器会把运行时的实际并行尺寸与该列表比对，拒绝未经证明的尺寸。

**身份（identities）**是序列化契约的 SHA-256 摘要，用于验证训练器与 rollout 引擎之间的契约一致。`semantic` 验证两个运行时描述的是同一个逻辑模型；`numerical_policy` 涵盖每一个可能影响数值结果的执行选择（例如实现与版本）；`deployment` 涵盖被证明不影响比特的设置，例如内存尺寸与传输配置，契约不要求这些必须匹配。由于被允许进入组合的每个内核都经过预先验证、能在各用例间保持规定的舍入调度，因此 `semantic` 与 `numerical_policy` 摘要一致，再加上契约适配器的强制执行，即表明双方在被覆盖的区域上执行的是同一个经过验证的数值策略。

![IsoExec's unified execution contract across training and inference runtimes.](https://vllm.ai/blog-assets/figures/2026-08-21-isoexec/unified_execution_abstraction.png)

IsoExec 在训练与推理运行时之间的统一执行契约。

每个运行时各有一个**契约适配器**，把契约与实现安装进各自引擎，并在运行时强制执行契约。它把每个组合条目绑定到框架的扩展点，例如选择指定的注意力内核。随后它通过检查已安装的内核、已声明的声明以及跨进程身份摘要来监控运行时。

## 统一模型

在 SkyRL 中，我们采用一份统一的模型定义，由批不变的 GEMM、注意力与归一化内核，以及确定性的 MoE 路由与组合构成。该模型在张量并行、专家并行与序列并行配置下也逐位一致，并为 GDN 混合架构使用分块并行递归算法。在我们的实验中，我们将该抽象应用于稠密（MiMo-7B）、MLA MoE（GLM-4.7-Flash）、混合（Qwen3.5-9B）与混合 MoE（Qwen3.5-35B-A3B）模型的训练，实现了契约覆盖范围内零不一致。IsoExec 的实现见 <https://github.com/zanderjiang/SkyRL-IsoExec>。

### 并行不变内核

训练与推理从不同的分布式策略中受益。训练器必须装下优化器状态、激活值、梯度，对 MoE 模型还有分布式的专家权重。rollout 引擎则需要为 KV 缓存留出足够的内存容量，同时不损害解码延迟。

对于输入与权重固定的前向数值计算，六种常见并行轴对执行的影响如下：

- **数据并行（DP）** 改变批次划分；批不变内核保持每个样本的数值一致。
- **流水线并行（PP）** 把整层移动到不同设备，只要边界 dtype 固定，就不会拆分其归约。
- **张量并行（TP）** 把收缩（contraction）归约拆分到各 rank。
- **专家并行（EP）** 分布专家计算并改变专家输出的组合方式。
- **序列并行（SP）** 把行并行的归约从 all-reduce 改为 reduce-scatter。
- **上下文并行（CP）** 沿序列维度拆分注意力归约。

[TBIK](https://arxiv.org/abs/2511.17826) 通过在行并行 GEMM 与跨 GPU 归约上固定一棵全局归约树，实现了 TP 不变的推理。IsoExec 采用同样的固定归约思想，但沿 K 维应用。`pik` 不在 GEMM K-tile 上构建树，而是把 K 维划分为 $G$ 个连续的叶子。每个叶子使用带 FP32 累加的确定性 Tensor Core MMA。契约固定 rank 到叶子的映射与二叉运算调度，而由 NCCL 传输部分结果，无需自定义通信内核。

![The fixed binary reduction tree used by pik to preserve numerics across parallelism layouts.](https://vllm.ai/blog-assets/figures/2026-08-21-isoexec/pik_figure.png)

pik 用来在并行布局间保持数值一致的固定二叉归约树。

此外，IsoExec 把同样的原则应用于 EP 与 SP。对于专家并行，我们按固定的路由顺序而非 rank 顺序组合专家输出。对于序列并行，我们复用与非 SP 系统相同的归约树；每个 rank 保留自己的输出切片，而不是汇聚完整结果。这使得训练器 logits 在 SP 开启或关闭时都逐位相同。

### 分块并行递归（CPR）GDN

对线性注意力架构而言，消除不一致更加复杂，因为训练与推理使用不同的算法。现有 GDN 系统在训练与预填充时使用分块并行形式，在解码时使用递归形式。虽然数学上等价，但两种算法的浮点舍入特性不同。把 [FLA 的](https://github.com/fla-org/flash-linear-attention)分块并行内核的 GDN 层输出与 vLLM 的融合递归内核比较，我们观察到平均每元素绝对差约为 $1.7\times10^{-2}$，最大差为 0.25。

[TorchTitan 团队](https://yichuan-w.github.io/blog/GDN-train-inference-mismatch-asyncRL/)通过让 rollout 预填充与训练器前向都使用递归形式、仅反向计算使用分块形式来解决这个问题。虽然这消除了 GDN 的不一致，但它使 rollout 预填充与训练器前向在序列长度上串行。他们报告在数学类工作负载上减速约 2–3 倍，在终端智能体工作负载上约 5 倍，使得该方法对完整训练任务不切实际。

为了在预填充、训练与解码都保持高吞吐的同时确保契约覆盖范围内零不一致，我们设计了**分块并行递归（chunkwise-parallel recurrent, CPR）**。CPR 保持递归为主函数，但跨块并行地对它求值。对于训练与预填充，与分块并行形式一样，第一遍计算每个块边界处的递归状态；然后一次并行递归扫描计算每个块内的输出。对于解码，我们使用递归形式，但每解码 $C$ 个 token 就重新同步一次隐藏状态，其中 $C$ 是块大小。这确保了预填充、训练与解码之间一致的舍入调度。

每层成本：

| 阶段 | 形状 | 原生混合 | 处处分块 | 处处递归 | CPR |
| --- | --- | --- | --- | --- | --- |
| 逐位精确 | — | 否 | 是 | 是 | **是** |
| 训练器前向 + 反向 | 1 × 10,240 tokens | 5.177 ms | 5.177 ms (1.00×) | 22.863 ms (4.42×) | **7.386 ms (1.43×)** |
| Rollout 引擎预填充 | 5 × 2,048 tokens | 0.844 ms | 0.844 ms (1.00×) | 3.639 ms (4.31×) | **1.412 ms (1.67×)** |
| Rollout 引擎解码 | 256 序列 × 1 token | 0.0612 ms | 2.2374 ms (36.6×) | 0.0612 ms (1.00×) | **0.0846 ms (1.38×)** |

*H100 上的每层延迟（$C=64$）。训练器与 rollout 引擎使用其生产 TP 布局与内核。每个比值都相对该阶段的原生混合实现；越小越好。*

## 结果

在我们的实验中，我们在单台 8×H100 节点上用同步 RL 在 DAPO-Math-17k 上训练 **Qwen3.5-35B-A3B**，将 IsoExec 与 SkyRL 原生栈进行比较。在设置完全相同的情况下，在我们评估的最高吞吐同步 RL 配置下，与使用 vLLM 和 Megatron 的 SkyRL 原生栈相比，IsoExec 有 25% 的端到端开销。

Logprob 差异

![Rollout-versus-training absolute logprob differences for the native SkyRL stack and IsoExec.](https://vllm.ai/blog-assets/figures/2026-08-21-isoexec/result_logprob_diff.png)

原生 SkyRL 栈与 IsoExec 的 rollout 相对训练的绝对 logprob 差异。

在 50 步中，更新前 rollout 相对训练的平均绝对 logprob 差从 $1.648\times10^{-2}$ 降至 $6.744\times10^{-7}$，其标准差从 $4.035\times10^{-2}$ 降至 $6.821\times10^{-7}$，每步平均最大值从 $5.073$ 降至 $7.358\times10^{-6}$。
