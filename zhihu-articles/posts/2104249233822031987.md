大模型推理系统常被简化成一张“每秒 token 数”排行榜。但一次请求的体验同时受模型、量化、KV cache、调度器、Attention kernel、硬件和负载影响。所谓推理框架也并非同一类产品：有的面向多用户服务，有的面向单机本地运行，有的把模型管理、缓存和执行引擎打包成完整应用，还有的专注于特定芯片的执行优化。

本文从算法和系统结构出发，比较 SGLang、vLLM、llama.cpp、Strata、TensorRT-LLM、Text Generation Inference（TGI）、LMDeploy、NVIDIA Dynamo、MLC-LLM 与 MLX，并结合匿名化的实际部署测试说明适用边界。本文不构成跨硬件性能排名；框架功能和硬件支持随版本变化，部署前应核对相应版本的官方文档和兼容矩阵。

**先给选型结论：**常规 GPU 在线服务先比较 vLLM 与 SGLang；NVIDIA 平台需要深入控制执行栈时评估 TensorRT-LLM；多节点路由和 Prefill/Decode 分离属于 NVIDIA Dynamo 这类编排层的职责；本地量化、CPU/GPU 混合运行优先看 llama.cpp；特定 MoE 模型在统一内存或消费级设备上的分层驻留，可评估 Strata。它们解决的问题有交集，但并不是同一层的替代品。

### 先把“框架”拆成几层

一次生成请求大致经历以下路径：

```text
请求接入与排队
        ↓
Tokenizer / 模板 / 多模态预处理
        ↓
Prefill：处理输入上下文、写入 KV 和模型状态
        ↓
Decode：逐步生成输出，读取 KV 和模型权重
        ↓
采样、停止条件、流式返回
```

不同项目覆盖的层次不同。vLLM、SGLang、TGI 和 LMDeploy 更强调在线服务、批处理调度和 API；llama.cpp 提供紧凑的 C/C++ 执行引擎与服务端；Strata 将本地模型管理、缓存和专用执行引擎结合；TensorRT-LLM 是面向 NVIDIA GPU 的模型执行与服务工具链；NVIDIA Dynamo 面向分布式推理的路由和编排；MLC-LLM 强调模型编译到多种设备后端；MLX 是 Apple Silicon 上的数组和机器学习框架，MLX-LM 在其上提供 LLM 加载与生成工具。

因此，框架比较至少需要说明比较的是：

- **服务调度**：请求如何排队、批处理、隔离长 Prefill 与 Decode。
- **模型执行**：Attention、GEMM、MoE、采样和 KV 操作走什么 kernel。
- **内存管理**：权重、KV cache、混合状态和前缀缓存如何分配、复用或卸载。
- **模型格式与量化**：权重是否需要转换，KV 量化是否由目标硬件和 kernel 真正支持。
- **硬件适配**：设备架构、驱动、运行时、编译器及依赖是否齐全。
- **运维能力**：服务 API、指标、日志、升级、回滚和集群管理。

这些维度彼此相关，但不能互相替代。更好的调度器不会自动修复不兼容的 attention kernel；更低比特权重也不保证更快，若解量化、访存或算子覆盖不理想，速度可能下降。

### 推理服务的核心算法

### 连续批处理与迭代级调度

传统静态批处理通常要等一个 batch 中的请求都结束才重组批次。连续批处理会在生成迭代之间移除已完成请求、加入新请求，提高设备忙碌程度。它主要改善多请求吞吐，但调度器还必须平衡短请求延迟与长请求公平性。

“客户端同时提交 4 个请求”不等于 GPU 同时解码 4 个请求。请求可能在队列中等待，可能只在 Prefill 阶段并行，也可能因为显存或模型状态池限制而分批运行。比较并发时应报告服务端运行请求峰值、整组吞吐以及 TTFT/ITL 分位数，而不只报告客户端 concurrency。

### PagedAttention 与 RadixAttention：存储和复用是两类问题

PagedAttention 的核心是把 KV 按块分配和映射，降低连续显存分配造成的碎片，并让服务端能灵活容纳不同长度的请求。RadixAttention 的核心是把请求前缀组织成可匹配、可共享的结构，减少重复前缀的计算。前者主要回答“KV 如何存放和分配”，后者主要回答“哪些已计算状态可以复用”。两者并不冲突；现代服务引擎往往同时需要分页分配、前缀复用和调度。

因此，不能把 vLLM 简化成“只有分页”，也不能把 SGLang 简化成“只有 RadixAttention”。项目早期的代表性算法有助于理解设计重点，但今天的版本都在持续吸收相似能力，最终差异要落到实现版本、缓存策略和模型后端上。

### KV 容量、上下文长度与缓存命中

KV cache 随上下文和活动请求增长，长上下文时会直接限制并发数。前缀复用可以省去重复输入的计算，但缓存本身仍占用内存，且要与新请求争夺可用空间。命中率取决于 token 前缀是否完全匹配、缓存驻留时间和淘汰策略；仅仅启用缓存，不代表真实业务一定受益。一次冷请求测试与多轮对话热缓存测试必须分开报告。

### Chunked Prefill 与 Prefill/Decode 干扰

长输入的 Prefill 需要集中处理大量 token，可能暂时占用算力和带宽，影响已有 Decode 请求的逐 token 延迟。Chunked Prefill 将输入切成较小块，允许 scheduler 在块之间穿插 Decode。块过小会增加调度和 kernel 启动成本；块过大则会让 Decode 等待更久。不存在适用于所有模型、上下文和并发的固定最优块长。

Prefill/Decode 分离（PD disaggregation）把两个阶段放到不同 worker 或设备，降低相互干扰，并可分别扩容；代价是传输 KV 或中间状态、增加网络与部署复杂度。单机单卡环境下，通常先调好 chunked prefill、请求准入和并发上限，再评估跨设备分离是否值得。

### 投机解码

投机解码让草稿模型或辅助头提出候选 token，再由目标模型验证。DFlash2、DSpine、MTP、EAGLE 和 DSpark 属于不同方案，所需 checkpoint、验证方式、状态管理和参数语义并不相同。收益依赖目标/草稿分布接近程度、草稿成本、验证 kernel 和上下文状态。

应同时观察草稿接受率、平均接受长度、decode tok/s、请求延迟和输出质量。接受率高但平均一次只接受少量 token，仍可能没有明显加速；接受率下降也不必然代表更慢，因为每轮推进长度和验证成本同样重要。草稿模型还可能增加显存压力，缩小可容纳的 KV cache 或并发空间。

### 量化与 KV 精度

权重量化、激活量化和 KV cache 量化是不同的技术选择。NVFP4 权重并不意味着 KV 也是 FP4；FP8 KV 和 FP4 KV 对 kernel、硬件代际、scale 元数据和反量化路径有各自要求。降低 KV 位宽可能增加可容纳上下文或请求数，也可能带来量化误差或更高的 gather/dequant 开销。

评估量化应拆成两类问题：一是能否正确加载并启动；二是端到端是否更快且质量符合业务要求。模型精度、TTFT、Decode、峰值内存和并发容量需要一起报告。

### 主流推理系统比较

| 系统 | 核心定位与实现特点 | 适合人群/场景 | 主要权衡 |
| --- | --- | --- | --- |
| SGLang | 在线 serving；RadixAttention 前缀复用、连续调度、chunked prefill、投机解码和多模型/多模态支持 | 需要高吞吐服务、前缀复用或复杂请求编排的团队 | 新模型和新硬件的算子支持取决于具体 backend、kernel 和构建版本；参数很多，需按模型验证 |
| vLLM | 通用 serving engine；分页 KV、连续批处理、prefix caching、量化及多种 speculative decoding | 希望部署 OpenAI-compatible 服务、使用广泛模型生态和调度能力的团队 | 不同硬件与量化路径的成熟度不一；内存利用率参数与其他框架的参数不可直接等价 |
| llama.cpp | C/C++ 本地推理；GGUF 量化、CPU/GPU 混合卸载、跨平台后端与轻量 server | 本地运行、边缘设备、量化模型、快速验证和个人工作站 | API 和多租户服务能力不应仅凭单用户速度推断；格式转换、算子后端和模型特性会影响可用性 |
| Strata | 面向特定本地模型与消费级/统一内存设备的应用及执行引擎；集成模型管理、专家驻留/缓存和投机解码等路径 | 想快速在单机上运行特定 MoE/长上下文模型的个人或小团队 | 专用优化不等于通用 serving 能力；自动配置应以实际模型和设备验证，社区性能数据需审查测试口径 |
| TensorRT-LLM | NVIDIA GPU 专用优化栈；模型转换/构建、低精度执行、融合 kernel、in-flight batching 与运行时 | NVIDIA 数据中心或厂商支持的平台，需要性能工程和硬件级控制的团队 | 构建、兼容矩阵和版本耦合更重；并非所有模型/量化都能直接导入，需评估部署维护成本 |
| TGI | Hugging Face 的模型服务栈；生产服务、continuous batching、流式 API、量化与监控工具 | 已使用 Hugging Face 模型生态、需要标准化服务接口的团队 | 必须检查当前版本、模型和硬件的支持范围；底层 kernel 与 serving 版本仍决定性能 |
| LMDeploy | 面向部署的服务系统，提供 TurboMind 与 PyTorch 等执行路径，并覆盖量化和批处理 | 使用 OpenMMLab / InternLM 生态，或希望在 NVIDIA GPU 上比较不同执行后端的团队 | 模型格式、后端和量化支持要逐项核对；不同后端不可仅凭同一启动参数推断等价 |
| NVIDIA Dynamo | 分布式推理编排与服务层，覆盖路由、扩缩容及 Prefill/Decode 分离等部署模式 | 需要跨 GPU/节点组织推理 worker、独立扩缩 Prefill 与 Decode 的平台团队 | 它主要解决分布式编排和数据流，不应直接当作单 GPU kernel 引擎与 vLLM 做 tok/s 排名 |
| MLC-LLM | 基于机器学习编译的部署引擎；将模型编译到 CUDA、Metal、Vulkan 等后端 | 需要跨设备部署、边缘/消费级硬件或编译期专门优化的开发者 | 编译和模型适配需要工程投入；新架构功能覆盖可能落后于热门 serving 栈 |
| MLX / MLX-LM | 面向 Apple Silicon 的数组框架与 LLM 工具；利用统一内存和 Apple GPU 执行 | Mac 本地实验、个人助手、Apple Silicon 开发 | 主要针对 Apple 平台；不应拿单机体验直接推导 NVIDIA 服务端的并发能力 |

“核心算法”不是框架之间互斥的选项。多个系统都可能采用分页 KV、连续批处理、prefix cache 或 speculative decoding，但具体实现、kernel 和 scheduler 不同。框架名称本身不足以预测性能。尤其要区分**执行引擎、在线服务、模型应用和分布式编排**：llama.cpp、vLLM、SGLang、TensorRT-LLM、LMDeploy 更接近执行/服务系统；Strata 将本地应用和面向特定模型的执行优化结合；Dynamo 位于分布式服务与编排层。

### 轻量本地引擎与在线服务栈的区别

llama.cpp 与 Strata 常用于把模型放到一台机器上运行，尤其是量化模型、混合 CPU/GPU 执行、统一内存和本地应用集成。vLLM、SGLang、TGI 通常首先面向请求队列、持续在线服务、并发调度、指标与 API 生态。TensorRT-LLM 面向 NVIDIA GPU 的执行优化和部署工程；MLC-LLM、MLX 则强调各自的编译或设备生态。

这不是绝对边界：llama.cpp 可以提供 HTTP server，vLLM/SGLang 也可以只服务一个用户；区别在默认优化目标、生态工具和常见部署方式。若目标是交互式单用户代码助手，应看 TTFT、单流 Decode 和上下文能力；若目标是多租户服务，应看聚合吞吐、P95/P99 延迟、排队、公平性、缓存命中和故障隔离。若需要将 Prefill 与 Decode 放在不同 worker 或设备上，还要把 KV 传输、路由等待和资源利用率纳入端到端测量，这类问题通常属于系统编排，而非单一 attention kernel 调优。

Strata 需要单独理解。它不只是通用 API server，也不是与 vLLM 完全同类的“调度器替代品”；其价值在于将面向特定模型形态的执行优化、设备内存层级管理和用户可用的本地应用结合。涉及 SSD 专家缓存、CPU 专家执行或草稿解码时，必须看实际数据流和日志：SSD 只在缺页或冷读取时影响，不意味着每个生成 token 都从 SSD 读取；统一内存设备也不能简单套用“显存专家 + 主机内存专家”的独立 GPU 模式解释。

### 我们的匿名化实测：如何正确读数字

### SGLang 与 vLLM：一次同机代码检索案例

在一组匿名化的单机 27B 量化模型冻结 4K 代码检索请求中，两套服务各测 12 题：

| 服务组合 | 正确数 | TTFT 中位数 | Decode 中位数 | 整组吞吐 |
| --- | --- | --- | --- | --- |
| SGLang + DFlash2 | 8⁄12 | 3.77 秒 | 37.47 token/s | 19.22 token/s |
| vLLM + DFlash2 | 8⁄12 | 4.57 秒 | 36.33 token/s | 17.20 token/s |

两者结果方向上接近，SGLang 这组整套配置略快。但 SGLang 与 vLLM 使用的草稿量化格式、内存配置和部分 backend 不完全相同；每题集样本有限。因此这是**两套部署组合的对比**，不能宣称是框架本身的普遍胜负。

长上下文也揭示了调度的重要性：在一组 32K C3 测试中，客户端同时提交三条请求，但服务端采样到的实际运行峰值为 2，TTFT 和流式输出间隔显著恶化；另一组 64K 请求中，主要成本表现为首 token 前的排队和长 Prefill，已开始生成的流却较平稳。不同题集、输出长度、容量压力和 chunk 调度会改变表象，不能把这两组差异单独归因于上下文长度。

### DSpine 与 DFlash2：投机解码强烈依赖任务

在同一量化目标模型的 llama.cpp 单用户试验中，较长窗口 DSpine 在一个 Python 检索样例上达到 62.37 token/s，DFlash2 为 28.17 token/s；但在固定长代码生成中，DSpine 较长窗口为 28.44 token/s，DFlash2 为 24.00 token/s；中文生成中，DSpine 较短窗口为 17.64 token/s，较长窗口为 14.85 token/s，DFlash2 为 13.94 token/s。

每种配置只有一次运行，检索仅有一个 Python 样例，生成任务限制为固定输出长度。数字说明 DSpine 有任务相关潜力，不足以证明它全面更快。并且该 DSpine 结果来自 llama.cpp 实现；另一个 SGLang/SM121 组合只通过了配置和兼容性检查，没有完成端到端推理。因此不能把前一实现的速度当作后一实现的成绩。

### Strata：专用路径的收益要和适用范围一起看

在另一类长上下文 MoE 本地部署中，我们使用 Strata 对模型驻留、专家缓存和 DFlash2 草稿路径进行了调优。结果表明，单用户短测、C3 客户端提交和真实多槽同时解码是不同工作负载；增加执行槽不保证提高整组吞吐。不同模型量化、草稿包、缓存冷热状态、CPU 热限制和设备统一内存预算都会改变结果。由于这组工作负载与前述 27B 服务测试的模型、格式及执行路径不同，本文不引用其数值与 SGLang/vLLM 做横向速度比较。

因此，Strata 与 SGLang/vLLM 的结果不适合拼成一张“同模型框架排行榜”：这里模型家族、量化格式和缓存策略不同。更有价值的问题是，目标设备是否受专家搬运或显存容量限制，Strata 的专用缓存层是否改善该负载，以及模型质量是否可接受。

### 选择框架的实际决策树

| 首要需求 | 优先评估 | 验证重点 |
| --- | --- | --- |
| 多用户在线服务、标准 API、常见模型部署 | vLLM、SGLang、TGI | P95/P99、聚合吞吐、队列、缓存、模型覆盖和运维工具 |
| 重复长前缀、多轮 agent 请求 | SGLang、vLLM | 真实 token 前缀命中率、缓存驻留时间、缓存淘汰及冷/热对照 |
| NVIDIA GPU 上榨取特定模型性能 | TensorRT-LLM，也可对照 vLLM/SGLang | 引擎构建成本、模型转换支持、硬件版本匹配、端到端而非 kernel 峰值 |
| 单机本地量化模型、CPU/GPU 混合运行 | llama.cpp | 目标格式、offload 分布、单流速度、多个 server slot 的实际吞吐 |
| 特定 MoE 本地模型、专家分级缓存 | Strata | GPU/RAM/SSD 专家命中、磁盘读量、热状态、稳定性和输出质量 |
| 跨设备编译与边缘部署 | MLC-LLM | 后端算子覆盖、编译时间、二进制可移植性和目标芯片性能 |
| Apple Silicon 本地开发与推理 | MLX / MLX-LM | 内存压力、模型格式、并发需求和 macOS 生态限制 |
| 多节点推理编排或 Prefill/Decode 分离 | NVIDIA Dynamo，或相应引擎自带的分布式方案 | KV 传输时延、路由、worker 利用率、扩缩容和故障恢复 |

可以把评估流程压缩为六步：

1. **冻结目标任务**：记录输入长度分布、输出长度、工具调用、前缀重合和目标并发。
2. **验证兼容性**：先确认模型、草稿模型、量化、attention backend、KV 格式与硬件架构可以正确运行。
3. **建立无投机基线**：固定模型、tokenizer、采样、缓存状态和请求，记录质量、TTFT、Decode、ITL 与内存。
4. **一次只改变关键变量**：例如框架、草稿方法、KV 精度、chunk 或并发，避免同时换模型和量化。
5. **分开冷、热与并发测试**：客户端并发、服务端运行请求和实际同时 Decode 必须分别报告。
6. **重复并做质量评估**：保留逐请求结果，多轮交错测试，并使用适合业务的正确率、工具调用成功率或回归集。

### 结语

推理框架没有脱离工作负载的绝对冠军。SGLang 和 vLLM 的重点是在线调度、缓存与服务生态；llama.cpp 为本地量化和跨平台执行提供灵活路径；Strata 通过模型和设备特定的缓存、执行优化服务一类本地工作负载；TensorRT-LLM 深入优化 NVIDIA 执行栈；TGI 与 LMDeploy 提供面向模型生态的服务路径；Dynamo 处理分布式推理编排；MLC-LLM 与 MLX 分别覆盖跨后端编译和 Apple Silicon 生态。

真正可迁移的工程结论不是某个测试中谁快了几个百分点，而是明确瓶颈所在：Prefill 算力、Decode 带宽、KV 容量、专家访问、草稿验证、调度排队，还是硬件兼容。按业务分布建立可复现基线，再逐层优化，才能选出对实际用户更好的系统。
