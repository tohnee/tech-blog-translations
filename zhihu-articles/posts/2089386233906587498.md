Megatron 是 NVIDIA 开源的大规模分布式训练框架

## 历史动线 补全3D 并行的拼图

- **Megatron v1 (2019年9月)**：**提出张量并行（Tensor Parallelism, TP）**。核心贡献是解决了“单层模型无法放入单张 GPU”的问题，通过将 Transformer 层内的矩阵乘法沿特定维度切分到多张 GPU 上，并配合精心设计的通信模式，实现了层内并行。
- **Megatron v2 (2021年4月)**：**引入流水线并行（Pipeline Parallelism, PP）**。v1 的 TP 难以跨节点扩展，v2 通过将模型的不同层分配到不同 GPU 上，并采用**交错式 1F1B 调度**来减少流水线气泡，从而将 TP、PP 与数据并行（DP）组合，形成了经典的 **“3D 并行”** 范式，支撑了万亿参数模型的训练。
- **Megatron v3 (2022年5月)**：**引入序列并行（Sequence Parallelism, SP）**。随着序列变长，激活值显存成为瓶颈。v3 通过沿序列维度切分激活值，并配合**选择性激活重计算**技术，在不显著增加计算量的前提下，大幅降低了长序列训练的内存占用。

**v0.5.0 - v0.6.0 (2024年)**：**MoE 支持的奠基期**。v0.5.0 初步引入 MoE 支持，v0.6.0 则带来了重要的 **All-to-All 令牌分发器，**并针对 Hopper 架构优化了 GroupedMLP

GroupedMLP 的核心是 **GroupedGEMM（分组通用矩阵乘法）**。专家本质上是独立的 MLP，传统做法是为每个专家单独启动矩阵乘法内核，但专家网络通常较小，于是浪费算力。因此吧所有本地专家的 token 按照 M 维度拼，并为每个 Token 标记其对应的专家 ID，这样一次 GEMM 可以计算所有专家。同时还做了SwiGLU 激活与路由权重缩放的 kernel fusion。

**All-to-All 令牌分发器** 则解决了多卡间专家并行的通信问题。EP 里面每个 GPU 的 token 要分发 dispatch ，以及 combine，两次 all 2 all 的操作，

dispatch router 先算token 的 topk 专家 Id，本地做 permute 把 token 按照目标专家和目标 rank 分组，发往同一卡的 token 要连续存放，统计 input spilits，全局交换 input splits，得到outputsplits，执行 all2alldispatch原语收到后再次 permute。

**v0.7.0 - v0.9.0 (2024年)**：**功能拓展与 MoE 深化**。v0.7.0 开始支持**多模态训练**，v0.8.0 为 MoE 增加了**上下文并行（CP）** 支持，而 v0.9.0 则引入了**非均匀流水线并行**，允许首尾 rank 拥有更少的层，进一步提升资源利用率。

**v0.15.0 (2025年11月)**：**性能与 MoE 优化**。带来了 **Fused QKV 预处理**（实现 3 倍预处理加速和 10-14% 的端到端提升），并为 MoE 增加了 **DTensor 支持**和 **HybridEP 后端**，优化了专家并行的通信效率。

**v0.19.2 (2026年9月)**：**当前最新稳定版**。

MoE 是当前 Megatron-Core **最核心的研发焦点**

- **动态上下文并行 (Dynamic-CP)**：**最值得关注的进展之一**。它能为每个 micro-batch **动态选择上下文并行大小**，解决变长序列训练中的计算不均衡问题，相比固定 CP 可实现**最高 1.48 倍加速**。
- **Megatron-FSDP v2 (MFSDP v2)**：正在重构为**兼容 FSDP2 API** 的按模块分片实现，并扩展对 **MoE 和 ZeRO 模式**的支持，未来还将支持与流水线并行 (PP) 的兼容。
- **广义张量并行 (GTP)**：正在开发中，旨在为 MoE 模型提供**按权重的模型并行分片**和分组专家的预取能力。

**Blackwell 平台优化**：集成 **GEMM + SwiGLU 融合 MLP**、**mHC** 和 **batchedGEMM 融合**等技术，以充分发挥 GB200/GB300 的性能

**低精度训练**：在支持 FP8 的基础上，正在推进 **MXFP8** 和 **NVFP4** 的支持

Megatron-Core 正在积极集成和优化下一代优化器，以提升训练动态和效率。

**Muon 优化器**：已集成 **Muon**，并配套了**层级分布式优化器 (Layer-wise Distributed Optimizer)**，在 GB300 上实现了与 AdamW 接近的训练吞吐

TP4 PP 2 CP 1 EP 1 SP

注意力层喜欢高 **TP**（切分大矩阵），而 MoE 层喜欢高 **EP**（分散专家），但传统框架强制 EP ≤ DP，且要求注意力层和 MoE 层使用**相同的并行配置**，导致无法同时满足两者

Megatron-Core 通过 **MoE Parallel Folding** 技术，允许**注意力层和 MoE 层使用各自独立的并行映射**，但它们共享同一组物理 GPU

- **注意力层并行组**：`TP × CP × DP × PP`
- **MoE 层并行组**：`ETP × EP × EDP × PP`（其中 ETP 是专家内部的张量并行，通常设为

参考[https://docs.nvidia.com/nemo/megatron-bridge/0.6.2/training/moe-optimization.html#1](https://docs.nvidia.com/nemo/megatron-bridge/0.6.2/training/moe-optimization.html#1)

1. **显存优先**：首先确保模型能“装下”。显存是硬性门槛，如果放不下，任何配置都无法运行。
2. **最小化模型并行，最大化数据并行**：在显存允许的前提下，优先增大 DP。因为模型并行（TP/PP/EP）会引入额外通信开销，而 DP 的通信模式更简单，效率更高。
3. **将 EP 和 TP 保持在高速互联域内**：EP 和 TP 都是通信密集型操作，应将它们限制在 NVLink 等高速互联范围内，避免跨节点通信成为瓶颈。
4. **专家层优先用 EP 而非 TP**：对于 MoE 层，高 TP 会切碎专家的小矩阵，导致 GEMM 效率极低。使用 EP 能让每个专家在单个 GPU 上保持完整，计算效率更高。
5. **为长序列启用 CP**：当序列长度达到 8K 及以上时，激活值显存会成为主要矛盾，此时应启用 CP 来切分序列

## LM

Core 定义好了模型 量化 并行策略，LM 负责模型外的训练 loop，数据，前向，反向，更新参数，检查点以及 log，评估。

本质是个 py 脚本

一个典型的 `pretrain_gpt.py` 大致遵循这样的顺序：

**前五个函数是人（或 Bridge）可以定制的地方，而最后的 `pretrain()` 是框架提供的通用训练引擎**。

可以用 pretrain py 文件串起来整个 megatron 干的事情

```python
def model_provider(pre_process=True, post_process=True) -> GPTModel:
    args = get_args()
    # 从命令行参数构建 TransformerConfig
    config = core_transformer_config_from_args(args)
    
    # 选择 Transformer 层的实现规格（spec）
    # 如果是 MoE，这里会传入包含 MoE 的 spec
    transformer_layer_spec = get_gpt_layer_with_transformer_engine_spec(...)
    
    # 实例化 GPTModel
    model = GPTModel(
        config=config,
        transformer_layer_spec=transformer_layer_spec,
        vocab_size=args.padded_vocab_size,
        max_sequence_length=args.seq_length,
        pre_process=pre_process,
        post_process=post_process,
    )
    return model
```

`pre_process` 和 `post_process` 这两个布尔值，是**流水线并行（PP）** 的标志。PP 的第一个阶段 `pre_process=True`（负责嵌入层），最后一个阶段 `post_process=True`（负责输出层和损失计算），中间阶段两者都为 `False`。

def get_batch(data_iterator):

    data = next(data_iterator) if data_iterator is not None else None

    tokens = tensor_parallel.broadcast_data(["tokens"], data, torch.int64)["tokens"]

其中 TP 和 CP 会去切激活

`forward_step` 单次前向

**一个 micro-batch 如何流过模型**，并返回输出和损失函数

```python
def forward_step(data_iterator, model):
    tokens, labels, loss_mask, attention_mask, position_ids = get_batch(data_iterator)
    # 调用模型的前向传播
    output_tensor = model(tokens, position_ids, attention_mask,
                          labels=labels, ...)
    # 返回输出张量，以及一个绑定了 loss_mask 的损失函数
    return output_tensor, partial(loss_func, loss_mask)
```

`loss_func` 计算损失

比如交叉熵

```python
def loss_func(loss_mask, output_tensor):
    losses = output_tensor.float()
    loss_mask = loss_mask.view(-1).float()
    loss = torch.sum(losses.view(-1) * loss_mask) / loss_mask.sum()
    return loss, {'lm loss': loss}
```

如果是 RL 要改很多了，MOE 要加个负载均衡项

`train_valid_test_datasets_provider` 用BlendedMegatronDatasetBuilder构建构建训练、验证、测试三个数据集迭代器

主入口

```python
if __name__ == "__main__":
    pretrain(train_valid_test_datasets_provider,  # 数据集

             ModelType.encoder_or_decoder,

```

`pretrain()` 内部会执行：初始化分布式环境 → 构建模型 → 构建数据集 → **进入训练循环**（前向 → 反向 → 优化器更新）→ 保存检查点。

## 3D到5D 并行

简单回顾一下 TP PP DP

Tp 切单层的 W，MLP 第一个层列切第二个层行切，QKV 部分按头切。PP 拆模型的大层，而 DP 切数据的批次。

TP 是把模型W 变窄，PP 让模型变矮，DP 最灵活用来填余量

长序列会让激活成为新的瓶颈，CP的通信模式与TP/PP不同，通常采用**Ring Attention**等环形通信模式，在GPU之间传递KV块。Megatron还引入了**Dynamic-CP**，为每个micro-batch动态选择CP大小，解决变长序列训练中的计算不均衡问题。**当MoE模型同时使用EP和TP时，必须启用序列并行**。SP本质上是TP的补充，沿序列维度切分激活值，减少TP组内的激活值冗余。也就是经典的 TPSP。MOE 还会进行 EP，EP 两个all2all 是主要的通信开销，此外，ETP允许对专家使用独立的、通常更低的张量并行度。

**进程组管理**：核心逻辑在 `megatron/core/parallel_state.py` 文件中。它负责根据你设置的 `tensor_model_parallel_size` 等参数，调用 PyTorch 的分布式接口来创建和管理所有并行维度的通信组

**张量切分定义**：在 `megatron/core/tensor_parallel/layers.py` 等文件中，Python 代码定义了如何将 `nn.Linear` 等层替换为 `ColumnParallelLinear` 和 `RowParallelLinear`，从而在模型构建阶段就完成权重的逻辑切分。

**流水线调度**：复杂的流水线并行调度策略，如交错式 1F1B（Interleaved 1F1B），其算法逻辑也是在 Python 中实现的。代码会依据并行配置，决定何时进行前向、反向以及阶段间的通信。

**通信协调与优化**：Python 层负责协调所有通信操作。例如，它会读取配置文件来为不同的并行组（如 TP、DP、EP）设置不同的 NCCL 参数，并启用高优先级流（High-Priority Streams）来优化通信与计算的重叠。它甚至管理着 SHARP 这样的高级网络特性，以将集合通信操作卸载到 InfiniBand 交换机上。

**数据并行与梯度同步**：Megatron 的 DDP 包装器在 Python 中实现，它将梯度存储在连续的缓冲区中，并通过将梯度分桶（bucketing）来异步执行 All-Reduce/Reduce-Scatter，实现通信与反向传播计算的重叠。

然后就是 CUDA 和 C++执行关键的计算任务

所有 GPU 之间的通信，最终都通过 NVIDIA 的 **NCCL 库**执行。

为了减少内存访问和内核启动开销，Megatron 大量使用**融合内核**。例如，它会将 LayerNorm、Softmax、RoPE 等多个操作融合成一个 CUDA 内核。Megatron 的 Python 代码最终会调用 PyTorch 的 C++ 后端来执行 Autograd 引擎和底层的张量运算。

开发或魔改 Megatron，核心是理解其**分层架构**，并选择合适的“切入点”。根据改动深度，主要有三条路径：**非侵入式（Spec系统）、适配器模式（运行时注入）和侵入式修改（直接改源码）**。

非侵入的

Megatron 的模型构建依赖于 `ModuleSpec`（模块规格）。它允许你通过配置来指定每一层使用哪个类，而不是在代码里硬编码。你可以通过自定义 `Spec` 来“注入”自己的实现，而无需修改 Megatron 源码，假设你想为 Qwen 模型换上一个自定义的 Attention 层。你可以定义一个函数，它基于标准的 Decoder Block Spec，但将其中的 `self_attention` 字段指向你的自定义模块

```python
# 伪代码示意
from megatron.core.models.gpt.gpt_layer_specs import get_gpt_layer_with_transformer_engine_spec

def get_custom_qwen_spec():
    # 获取标准 Spec
    spec = get_gpt_layer_with_transformer_engine_spec()
    # 将 self_attention 替换为你的自定义模块
    spec.submodules.self_attention = ModuleSpec(module=MyCustomAttention, ...)
    return spec
```

运行时注入

当你需要**修改框架行为**而非仅仅是模型组件时（如自定义 DDP、扩展并行能力），适配器模式是绝佳选择。TeleTron 项目是此模式的典范。

## MoE 面向 qwen3 等现代架构的支持

GroupedGEMM，Megatron 通过 `TEGroupedMLP` 和 `GroupedMLP` 类来实现这一机制，并集成了 CUTLASS 2.8 的 Grouped GEMM 特性。该特性支持 FP8/MXFP8 精度，并可与 SwiGLU 激活函数融合，进一步减少内存访问

通信隐藏，Megatron 提供了 `--overlap-moe-expert-parallel-comm` 标志，在**批级别**将 EP 的 All-to-All 通信（token 分发与合并）隐藏在每个专家的计算过程中，这意味着当 GPU 正在为一批 token 计算专家 FFN 时，下一批 token 的路由通信已经在后台进行。为了实现这一点，通常需要启用虚拟流水线并行

**Flex Dispatcher，DeepEP** 是 DeepSeek 开源的高性能 token 分发与合并实现

**HybridEP** 是 NVIDIA 为**节点内和多节点 NVLink 场景**优化的 All-to-All 后端，能显著减少 SM（流式多处理器）资源占用。

具体做法在此不展开了。

## 定位，相比于Deepseed和FSDP

**只有 Megatron 原生支持EP**

FSDP2是 PyTorch 原生的**数据并行**实现，其思想与 DeepSpeed ZeRO-3 类似。它将模型参数、梯度和优化器状态全部分片到各 GPU 上，在计算时按需 AllGather 参数，计算后立即释放，以此实现内存效率。它的最大优势是**与 PyTorch 生态无缝集成**，API 简洁，是大多数常规训练任务在 2026 年的“默认选项”。学习和维护成本最低.

**DeepSpeed** 由 Microsoft 推出，核心是 **ZeRO，**ZeRO-Offload 和 ZeRO-Infinity 提供了最细粒度的内存管理选项。

大多数大模型 Infra 岗位会将三者打包，作为分布式训练能力的基线要求。

百度、腾讯、字节等公司的岗位明确要求“精通 Megatron-LM”或具备“二次开发经验”，LongCat - Pretrain Infra明确要改过 Megatron-LM / DeepSpeed / FSDP 源码，许多岗位的职责描述直接围绕 Megatron 展开，例如“基于 **Megatron-LM** / DeepSpeed / Verl 等框架，进行并行策略及显存的优化
