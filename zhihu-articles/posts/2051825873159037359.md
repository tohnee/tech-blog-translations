### DeepSpeed ZeRO-3 是模型并行吗？

很多人会下意识回答：是。

但这个答案要看你怎么定义“模型并行”。

假设你有一个 35B 模型，bf16 参数本身大约 70GB。现在用 16 张 H800 做全参 SFT，并且打开 DeepSpeed ZeRO-3：每张卡平时只保存参数的一部分。

这时候很多人会马上冒出两个判断：

```text
第一，ZeRO-3 应该就是模型并行吧？
第二，每张卡既然只存一部分参数，那它是不是只能计算模型的一部分？
```

这两个判断都很容易理解，但也都不够准确。

**如果把“模型并行”理解成 Tensor Parallel 或 Pipeline Parallel，那么 ZeRO-3 不是传统意义上的模型并行。它更准确的说法是：数据并行下的模型状态分片，也就是 sharded data parallel。**

最反直觉的地方在这里：

```text
每张卡都有完整模型结构；
每张卡平时只常驻一部分参数数据；
但计算某一层时，每张卡会临时拿到这一层完整参数；
算完这一层后，完整参数又会释放，回到分片状态。
```

所以 ZeRO-3 真正切开的不是“模型计算图”，而是“模型状态的存储”。它不是把第 1 到 10 层放在 A 卡、第 11 到 20 层放在 B 卡，也不是把一个 Linear 的矩阵乘法按行或列拆给多张卡长期共同计算。

这篇文章只围绕一个问题展开：

**ZeRO-3 到底是怎么让 16 张卡协作训练一个 35B 模型的？**

为了回答它，我们不先堆概念，而是沿着训练过程一层层拆：

1. 先看普通数据并行为什么浪费显存：16 张卡到底重复保存了什么。
2. 再看 ZeRO-1/2/3 分别切掉哪些冗余状态：optimizer states、gradients、parameters 是怎么一步步被分片的。
3. 接着讲 ZeRO 到底按什么原则切：不是按矩阵行列，而是按 flatten 后的一维连续区间。
4. 最后落到 16 张 H800 全参微调 35B SFT：一次 global batch 如何经历参数 all-gather、forward、loss、backward、reduce-scatter、梯度累积和 optimizer step。

为了避免把 ZeRO 讲成玄学，后文涉及 stage 定义、参数分片、梯度分片和参数调度的地方，我都按下面这些 DeepSpeed 源码路径做了核对：

```text
deepspeed/runtime/zero/config.py
deepspeed/runtime/engine.py
deepspeed/runtime/zero/stage_1_and_2.py
deepspeed/runtime/zero/stage3.py
deepspeed/runtime/zero/partition_parameters.py
deepspeed/runtime/zero/parameter_offload.py
deepspeed/runtime/zero/partitioned_param_coordinator.py
```

下面这张图来自 ZeRO 论文，它非常准确地表达了 ZeRO-DP 的三阶段思想：逐步消除数据并行中 optimizer states、gradients、parameters 的重复保存。

### 1. 大模型训练显存到底花在哪里

训练大模型时，显存不是只放 bf16/fp16 权重。

以 AdamW + bf16/fp16 全参训练为例，主要状态包括：

```text
parameters：模型参数
gradients：梯度
fp32 master weights：优化器更新用的 fp32 主权重
Adam momentum：Adam 一阶动量
Adam variance：Adam 二阶动量
activations：前向中间结果，反向传播要用
communication buckets / temporary buffers：通信和临时 buffer
```

粗略估算时，常把 AdamW 全参训练的模型状态按约 `16 bytes/参数` 估计。这个数不是严格常数，因为梯度 dtype、优化器实现、offload、contiguous gradients 等配置都会影响实际显存，但它足够解释为什么 35B、80B、235B 这种模型训练时显存压力巨大。

比如 35B 模型：

```text
bf16 参数本身：35B * 2 bytes = 70GB
AdamW 训练状态粗略估算：35B * 16 bytes = 560GB
```

如果普通数据并行让每张卡都复制一整份模型状态，16 张卡并不会把单卡模型状态显存降到 1/16。ZeRO 要解决的正是这个冗余。

### 2. ZeRO-1/2/3 的一句话定义

DeepSpeed 源码里，ZeRO stage 的含义可以核对到：

```text
Stage 0：disabled
Stage 1：optimizer state partitioning
Stage 2：optimizer + gradient state partitioning
Stage 3：optimizer + gradient + parameter partitioning
```

换成人话就是：

```text
ZeRO-0：什么都不切，普通数据并行
ZeRO-1：切 optimizer states
ZeRO-2：切 optimizer states + gradients
ZeRO-3：切 optimizer states + gradients + parameters
```

源码路径上也能对上这个结论：

```text
ZeRO-1/2：主要走 deepspeed/runtime/zero/stage_1_and_2.py
ZeRO-3：主要走 deepspeed/runtime/zero/stage3.py
参数分片：deepspeed/runtime/zero/partition_parameters.py
参数调度：deepspeed/runtime/zero/partitioned_param_coordinator.py
```

可以用一张表概括：

```text
方案          参数 parameters   梯度 gradients   optimizer states
普通 DDP      复制              复制             复制
ZeRO-1        复制              复制             分片
ZeRO-2        复制              分片             分片
ZeRO-3        分片              分片             分片
```

这张表就是理解 ZeRO 的主轴。

### 3. 从普通数据并行到 ZeRO-3

### 3.1 普通数据并行：每张卡都有完整模型状态

普通数据并行里，每张卡都有完整参数、完整梯度、完整 optimizer state。

16 张卡时，每张卡处理不同样本：

```text
rank0  处理 sample_0
rank1  处理 sample_1
...
rank15 处理 sample_15
```

每张卡得到自己的梯度后，通过 all-reduce 求平均。all-reduce 的结果是：

```text
每张卡都拿到完整平均梯度
每张卡都更新完整模型
```

它简单，但最大的问题是显存重复。

### 3.2 ZeRO-1：只把 optimizer states 切开

ZeRO-1 不切参数，也不切梯度。它只切 optimizer states。

对于 AdamW，optimizer states 主要包括：

```text
fp32 master weight
momentum
variance
```

所以 ZeRO-1 下：

```text
每张卡仍有完整参数
每张卡仍有完整梯度
每张卡只保存自己负责的 optimizer state shard
```

源码上，ZeRO-1⁄2 共用 `stage_1_and_2.py`，核心差别是是否打开 gradient partition。不开梯度分片时，就是 ZeRO-1。

### 3.3 ZeRO-2：继续把梯度切开

ZeRO-2 在 ZeRO-1 基础上继续切梯度。

所以 ZeRO-2 下：

```text
每张卡仍有完整参数
梯度被分片
optimizer states 被分片
```

普通 DDP 会让每张卡都拿完整平均梯度；ZeRO-2 不需要这么做。它可以用 reduce-scatter，让平均后的梯度直接分散到不同 rank 上。

也就是说：

```text
rank0 只保留平均梯度 shard0
rank1 只保留平均梯度 shard1
...
rank15 只保留平均梯度 shard15
```

但 ZeRO-2 仍然要求每张卡能放下完整模型参数。

### 3.4 ZeRO-3：参数也切开

ZeRO-3 再往前走一步：参数也分片。

ZeRO-3 平时每张卡只保存参数的一部分。计算某一层时，DeepSpeed 通过参数调度器触发 all-gather，把当前层需要的参数临时拼完整；这一层算完后，再释放完整参数，回到分片状态。

所以 ZeRO-3 的核心循环是：

```text
当前层 forward/backward 前：all-gather 参数
当前层计算时：每张卡临时有完整当前层参数
当前层计算后：释放完整参数，只保留 shard
梯度产生后：reduce-scatter 成梯度 shard
optimizer step：每张卡只更新自己负责的参数 shard
```

这就是为什么 ZeRO-3 能显著降低大模型全参训练的模型状态显存。

### 4. ZeRO 到底按什么维度切：行、列，还是别的？

这是一个非常容易误解的点。

**ZeRO 不是按矩阵的行切，也不是按矩阵的列切。ZeRO 是把参数或参数组看成一维连续元素，然后按 data parallel rank 切连续区间。**

比如一个参数矩阵：

```text
W shape = [4096, 4096]
```

ZeRO-3 不是理解成“按行切给 16 张卡”或“按列切给 16 张卡”，而是更接近：

```text
先把 W contiguous 后展平成一维：

W_flat = [w0, w1, w2, ..., w16777215]

然后按 data parallel rank 切连续区间：

rank0  保存 W_flat 的第 0 段
rank1  保存 W_flat 的第 1 段
...
rank15 保存 W_flat 的第 15 段
```

源码核对结论：

```text
partition_parameters.py：
  ZeRO-3 单个参数会记录原始 shape/numel
  必要时 padding 到可按 DP world size 切分
  参数 contiguous 后按一维 start/end 切出当前 rank 的 shard
  all-gather 后再按原始 shape 还原

stage_1_and_2.py：
  ZeRO-1/2 会把 optimizer parameter group 整理成 flat buffer
  再按 DP rank 切 flat partition

stage3.py：
  ZeRO-3 会把本 rank 拥有的参数 shard 组织成 flat partition
  fp32 master weight、梯度、optimizer state 与这个 flat partition 对齐
```

所以，如果某个矩阵刚好按行边界切开，看起来像“按行切”，那只是巧合。换个矩阵形状、换个 GPU 数量，某个 shard 完全可能跨越两行，或者只覆盖某一行的一部分。

这和 Tensor Parallel 的区别非常重要：

```text
Tensor Parallel：
  切的是计算。
  例如 Linear 的矩阵乘法按行/列拆，多张卡共同完成一个算子。

ZeRO-3：
  切的是模型状态存储。
  计算某层时参数临时聚合，每张卡仍对自己的 micro-batch 执行完整层计算。
```

所以 ZeRO-3 可以说“参数被分片存储”，但不应该简单说成“模型并行”。

### 5. 三个通信原语：all-reduce、all-gather、reduce-scatter

理解 ZeRO 的同步过程，只需要先抓住三个通信原语。

### 5.1 all-reduce：求平均后，每张卡都有完整结果

普通数据并行最常见的是 all-reduce。

```text
输入：
rank0: grad_0
rank1: grad_1
rank2: grad_2
rank3: grad_3

输出：
rank0: 完整 grad_avg
rank1: 完整 grad_avg
rank2: 完整 grad_avg
rank3: 完整 grad_avg
```

它适合普通 DDP，因为每张卡都要更新完整模型。

### 5.2 all-gather：每张卡各有一片，最后每张卡都拼完整

all-gather 不求和，只收集。

```text
输入：
rank0: W shard0
rank1: W shard1
rank2: W shard2
rank3: W shard3

输出：
rank0: 完整 W
rank1: 完整 W
rank2: 完整 W
rank3: 完整 W
```

ZeRO-3 用它临时拼出当前层参数。

### 5.3 reduce-scatter：先求平均，再把结果切片分给各卡

reduce-scatter 可以理解成 all-reduce 的省显存版本。

```text
先得到平均梯度 grad_avg
然后切成多个 shard：

rank0: grad_avg shard0
rank1: grad_avg shard1
rank2: grad_avg shard2
rank3: grad_avg shard3
```

ZeRO-2⁄3 用它同步梯度，因为每张卡只需要自己负责的梯度 shard。

### 5.4 communication bucket：把小通信打包

真实模型里有成千上万个张量。如果每个张量都单独通信，启动开销会很高。

所以 DeepSpeed 会把多个参数或梯度打包成 bucket：

```text
参数 bucket：常用于 all-gather
梯度 bucket：常用于 reduce-scatter 或 all-reduce
```

bucket 大，通信次数少，但临时显存更高；bucket 小，显存峰值低，但通信次数更多。

### 6. 35B 模型，16 张 H800，ZeRO-3 全参 SFT：一次 update 怎么跑

假设配置是：

```text
模型：35B
任务：SFT 全参微调
GPU：16 张 H800
精度：bf16
ZeRO：stage 3
micro_batch_size_per_gpu = 1
gradient_accumulation_steps = 8
global batch size = 128
offload：先不开
```

global batch 的计算是：

```text
global batch
= micro_batch_size_per_gpu * GPU 数 * gradient_accumulation_steps
= 1 * 16 * 8
= 128 条样本
```

也就是说：

```text
每个 micro-step：16 张卡各处理 1 条样本，共 16 条
连续 8 个 micro-step：累计 128 条样本的梯度
第 8 个 micro-step 后：optimizer step 一次
```

### 6.1 训练开始前：16 张卡先分工保存模型状态

35B bf16 参数本身大约 70GB。ZeRO-3 下，参数按 16 个 data parallel rank 分片，理想粗略估算：

```text
每张卡常驻参数 shard ≈ 70GB / 16 ≈ 4.4GB
```

AdamW 模型状态粗略按 560GB 算，分到 16 张卡：

```text
每张卡模型状态 shard ≈ 560GB / 16 ≈ 35GB
```

实际显存还要加上 activation、通信 bucket、临时 all-gather 参数、CUDA workspace、fragmentation 等，所以这不是最终显存占用，只是帮助理解量级。

更重要的是协作关系。训练开始后，16 张卡不是各自保存一份完整 35B 模型状态，而是共同保存同一个全局模型的 16 份 shard：

```text
rank0:
  常驻 parameter shard0
  常驻 gradient shard0
  常驻 optimizer state shard0

rank1:
  常驻 parameter shard1
  常驻 gradient shard1
  常驻 optimizer state shard1

...

rank15:
  常驻 parameter shard15
  常驻 gradient shard15
  常驻 optimizer state shard15
```

每张卡都有完整模型结构，但每张卡只常驻自己负责的那段模型状态。可以把 16 张卡理解成一个“分片存储的完整模型”：单卡不完整，合起来完整。

### 6.2 一个 micro-step：16 张卡并行处理 16 条样本

第一个 micro-step，数据是这样分给 16 张卡的：

```text
rank0  处理 sample_0，使用 parameter shard0 参与协作
rank1  处理 sample_1，使用 parameter shard1 参与协作
...
rank15 处理 sample_15，使用 parameter shard15 参与协作
```

注意这里有两个并行同时存在：

```text
数据并行：
  16 张卡处理 16 条不同样本

ZeRO-3 状态分片：
  16 张卡共同保存同一个模型的参数、梯度、optimizer state
```

### 6.3 forward：每一层参数临时拼完整，每张卡各算各的样本

假设现在要计算第 L 层。这一层的权重 `W_L` 平时不是每张卡都有完整一份，而是分布在 16 张卡上：

```text
rank0  常驻 W_L shard0
rank1  常驻 W_L shard1
...
rank15 常驻 W_L shard15
```

进入这一层 forward 前，16 张卡做一次 all-gather：

```text
rank0  收集 shard0..shard15，临时得到完整 W_L
rank1  收集 shard0..shard15，临时得到完整 W_L
...
rank15 收集 shard0..shard15，临时得到完整 W_L
```

然后每张卡用同一个完整 `W_L`，但处理自己的样本：

```text
rank0:  W_L(sample_0 的 hidden states)
rank1:  W_L(sample_1 的 hidden states)
...
rank15: W_L(sample_15 的 hidden states)
```

这一层算完后，完整 `W_L` 只是临时工作区，不需要长期留着。ZeRO-3 会释放完整参数，只保留本 rank 的 shard。下一层重复同样过程：

```text
all-gather 当前层参数
每张卡各算自己的样本
释放完整参数
进入下一层
```

### 6.4 loss：每张卡先在本地把自己样本的 token loss 聚合起来

一条 SFT 样本通常是：

```text
prompt + response
```

如果 response 有 2048 个有效 token，那么会有很多 token-level loss。SFT 通常只对回答部分算 loss：

```text
prompt token：label = -100，不参与 loss
padding token：label = -100，不参与 loss
response token：参与 loss
```

但这不代表 forward 2048 次。

训练时用 teacher forcing，完整序列一次送进模型：

```text
input_ids shape = [batch, seq_len]
logits shape = [batch, seq_len, vocab_size]
```

所有位置的 logits 会并行算出来，causal mask 保证第 i 个位置不能看未来 token。有效 response token 的 loss 最后聚合成一个 scalar loss。

所以在 `micro_batch_size_per_gpu = 1` 时：

```text
每张卡每个 micro-step：forward 1 次
每张卡每个 micro-step：backward 1 次
```

2048 个 token 都贡献梯度，但不是 2048 次 backward。

这一点放回 16 卡里看就是：

```text
rank0  从 sample_0 的有效 response tokens 得到一个 scalar loss
rank1  从 sample_1 的有效 response tokens 得到一个 scalar loss
...
rank15 从 sample_15 的有效 response tokens 得到一个 scalar loss
```

这些 loss 对应的是不同样本的数据贡献。后面反向传播和梯度同步会把它们变成同一个全局模型的平均更新方向。

### 6.5 backward：每张卡先得到本地梯度贡献，再 reduce-scatter 成梯度 shard

反向传播时，每张卡对自己的 scalar loss 做 backward。因为每张卡处理的样本不同，所以一开始得到的是本地梯度贡献：

```text
rank0  得到 sample_0 对参数的梯度贡献 grad_0
rank1  得到 sample_1 对参数的梯度贡献 grad_1
...
rank15 得到 sample_15 对参数的梯度贡献 grad_15
```

但 ZeRO-3 不会让每张卡长期保存完整平均梯度。它会通过 reduce-scatter 做两件事：

```text
第一步：跨 16 张卡把梯度求和/平均
第二步：把平均后的梯度按 shard 分给 16 张卡
```

结果是：

```text
rank0  只保留本 micro-step 的 grad_avg shard0
rank1  只保留本 micro-step 的 grad_avg shard1
...
rank15 只保留本 micro-step 的 grad_avg shard15
```

这一步体现了 ZeRO-3 的协作本质：

```text
每张卡的样本不同，所以梯度贡献不同
但 16 张卡共同求出同一个全局平均梯度
平均梯度不复制 16 份，而是分片保存
```

### 6.6 梯度累积：8 个 micro-step 合成一次 global batch

因为 `gradient_accumulation_steps = 8`，每张卡会连续做 8 个 micro-step：

```text
micro-step 1：16 条样本
micro-step 2：16 条样本
...
micro-step 8：16 条样本
```

合计：

```text
16 * 8 = 128 条样本
```

每个 micro-step 的 backward 都会把本次样本贡献的梯度累积到对应 shard 上。到第 8 个 micro-step 结束时，DeepSpeed 进入 gradient accumulation boundary，开始做 optimizer step。

更具体地说，每张卡只累积自己负责的那一片梯度：

```text
rank0:
  grad_total shard0 += micro-step 1 的 grad_avg shard0
  grad_total shard0 += micro-step 2 的 grad_avg shard0
  ...
  grad_total shard0 += micro-step 8 的 grad_avg shard0

rank1:
  grad_total shard1 += micro-step 1 的 grad_avg shard1
  grad_total shard1 += micro-step 2 的 grad_avg shard1
  ...
  grad_total shard1 += micro-step 8 的 grad_avg shard1

...

rank15:
  grad_total shard15 += micro-step 1 的 grad_avg shard15
  ...
  grad_total shard15 += micro-step 8 的 grad_avg shard15
```

从数学上看，目标通常是 global batch 的平均梯度：

```text
grad_avg = 128 条样本贡献梯度的平均
```

实现上可以等价地：

```text
每个 micro-step 先缩放 loss 再累积
或先累积梯度，step 前统一缩放
```

关键是不要重复除，也不要漏除。使用 DeepSpeed engine 的 backward/step 时，它会根据梯度累积边界管理这个过程。

### 6.7 optimizer step：16 张卡各自更新自己的那一片，再进入下一轮

到 optimizer step 时：

```text
rank0  更新参数 shard0 对应的 fp32 master weight、momentum、variance
rank1  更新参数 shard1 对应的 fp32 master weight、momentum、variance
...
rank15 更新参数 shard15 对应的 fp32 master weight、momentum、variance
```

更新完成后，每张卡仍然只保留自己的参数 shard。

下一轮 forward 需要某一层时，再通过 all-gather 临时拼出那一层的完整参数。这样 16 张卡看到的是同一份全局模型的不同状态 shard，不是 16 个各自漂移的模型。

把一次 global batch 串起来，就是：

```text
micro-step 1:
  16 卡各处理 1 条样本
  每层参数 all-gather 后各算各的 forward
  backward 后 reduce-scatter 得到梯度 shard
  每卡累积自己的梯度 shard

micro-step 2..8:
  重复同样过程
  每卡继续累积自己的梯度 shard

optimizer step:
  rank0 更新 shard0
  rank1 更新 shard1
  ...
  rank15 更新 shard15

下一轮:
  再通过 all-gather 使用更新后的参数 shard 组成完整层参数
```

---

### 7. 序列长度和 activation：为什么长上下文更吃显存

ZeRO 主要解决的是模型状态显存，也就是参数、梯度、optimizer state 的冗余。

但训练时还有一大块显存叫 activation：前向传播中间结果，反向传播要用它们计算梯度。

序列越长，activation 越大。因为 Transformer 里每层都要处理更长的 hidden states，attention 相关中间结果也会随序列长度增长。

所以：

```text
ZeRO-3 可以显著降低模型状态显存
但不能让 activation 消失
```

如果 35B SFT 序列很长，仍然可能需要：

```text
activation checkpointing
更小 micro batch
更短 seq_len
更小通信 bucket
必要时再考虑 offload
```

---

### 8. ZeRO-3 和 offload 的关系

ZeRO-3 不等于 offload。

```text
ZeRO-3：把参数、梯度、optimizer states 分片到不同 GPU rank
offload：把某些状态搬到 CPU 或 NVMe
```

DeepSpeed 配置含义上：

```text
optimizer offload：ZeRO-1/2/3 都可能使用
parameter offload：主要和 ZeRO-3 配合，因为只有 ZeRO-3 切参数
```

对于 35B、16 张 H800、bf16 全参 SFT，一个合理起点通常是：

```text
ZeRO-3
bf16
activation checkpointing
offload 先关闭
```

如果序列长度、bucket、activation 或 optimizer state 仍然导致显存紧张，再考虑打开 offload。offload 能省 GPU 显存，但会引入 CPU/NVMe 传输开销。

### 9. 最后把主线收回来

回到开头的问题：

**DeepSpeed ZeRO-3 是模型并行吗？**

如果“模型并行”指 Tensor Parallel / Pipeline Parallel，那么答案是：**不是。**

ZeRO-3 的核心是：

```text
每张卡都有完整模型结构
每张卡处理不同数据样本
参数、梯度、optimizer states 被分片存储
计算某层时临时 all-gather 参数
反向后用 reduce-scatter 得到梯度 shard
每张卡只更新自己负责的 optimizer state 和参数 shard
```

ZeRO-1/2/3 的区别也可以压缩成一句话：

```text
ZeRO-1：切 optimizer states
ZeRO-2：再切 gradients
ZeRO-3：再切 parameters
```

而 ZeRO 的“切”，也不是按矩阵行列切，而是按 flatten 后的一维连续元素区间切。这一点把 ZeRO-3 和 Tensor Parallel 区分开了。

在 16 张 H800、`micro_batch_size_per_gpu = 1`、`gradient_accumulation_steps = 8` 的 35B SFT 里，一次 optimizer update 可以理解为：

```text
8 个 micro-step
每个 micro-step 16 张卡各处理 1 条样本
每条样本一次 forward、一次 backward
token loss 聚合成 scalar loss
梯度跨 16 卡 reduce-scatter
第 8 个 micro-step 后 optimizer step
每张卡只更新自己负责的 shard
```

这就是 ZeRO-3 的本质：**不改变每张卡执行同一模型结构这件事，而是把训练所需的模型状态从“每卡完整复制”变成“跨卡分片协作”。**
