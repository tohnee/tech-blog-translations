调用`llm.generate()`后，文字是怎么出来的？读vLLM时，最容易迷路的地方，是入口、调度器、模型和KV cache分散在不同文件里。单看其中一个，很难知道它手里的数据从哪来、下一步又交给谁。

这篇沿着一次请求走完六站：进入引擎、调度、准备输入、执行模型、读写KV cache，最后采样和回收资源。代码只摘主线，文件位置留着，方便回头查。

版本固定为vLLM `v0.22.0`（`0b3ba88`）。示例使用单卡`facebook/opt-125m`，按未强制切换runner、未修改执行器的默认配置讲：V1 runner、主进程与EngineCore分离，普通生成开启异步调度。后面的数字和配图是源码机制示意，不是一次实际运行的trace。

## 先建立全局地图

这里先分清两个名字：`LLMEngine.step()`在主进程取结果；EngineCore在另一个进程安排和执行计算。它们不是同一个循环。

```text
主进程
LLM.generate() → 添加请求 → 通过IPC送到EngineCore
               ↓
循环LLMEngine.step() → 取输出 → 解码、组装结果
                         ↑ IPC
EngineCore进程            │
调度一个批次 → 准备输入、执行模型与采样 → 更新请求状态
       └── 默认使用批队列，可与前一批的执行重叠

单卡默认：Executor、Worker、GPUModelRunner都在EngineCore进程内
```

调度、执行、更新是三个逻辑环节。默认配置下，它们不一定在一次`EngineCore.step()`调用中串行做完：EngineCore可以先提交下一批，再收取前一批的输出。请求也不是每轮都会生成一个token；有的在处理prompt的一部分，有的本轮没有排上。

![](https://pic4.zhimg.com/v2-17c48bd308f617d1877ad11aa3cc096f_1440w.jpg)

图1上半部标出进程边界，下半部表示批队列允许的重叠关系，不表示两个批次的GPU计算必定同时执行。`Scheduler`管理调度与KV块分配，`Executor`调用worker执行模型，职责不同。

## 第1站：入口，一行generate背后

```python
from vllm import LLM, SamplingParams

llm = LLM(model="facebook/opt-125m")
outputs = llm.generate(
    ["话说天下大势"], SamplingParams(max_tokens=50)
)
```

`LLM`把参数交给`LLMEngine`。这次离线调用会先准备并添加传入的请求，再循环收结果，直到它们全部结束。

下面是主进程的概念骨架，省略了参数检查和输出排序：

```python
add_requests(prompts, sampling_params)
while llm_engine.has_unfinished_requests():
    outputs = llm_engine.step()
    collect_finished_outputs(outputs)
```

对应[offline_utils.py:326–349](https://github.com/vllm-project/vllm/blob/0b3ba88f165976e77ca5e6a7a3f5bba4562b80af/vllm/entrypoints/offline_utils.py#L326-L349)的“先添加、后运行”，以及[LLMEngine.step()](https://github.com/vllm-project/vllm/blob/0b3ba88f165976e77ca5e6a7a3f5bba4562b80af/vllm/v1/engine/llm_engine.py#L287-L321)的输出处理。

### 取结果与驱动计算，分在两边

最初读`LLMEngine.step()`时，把它理解成了“发请求、等后端算完、拿结果”。沿代码往下跟，才发现请求早在`add_request()`时就已发送，`step()`主要是在取输出。

主进程的`step()`会调用`engine_core.get_output()`，处理返回的token、解码文字、组装`RequestOutput`，必要时发送终止请求。真正的调度和模型执行由EngineCore自己的循环推进。

两边通过IPC，也就是进程间通信，传递请求和结果。这样主进程处理上一批输出时，EngineCore可以继续工作；但并不是“互不等待”：输出还没到，主进程的[outputs_queue.get()](https://github.com/vllm-project/vllm/blob/0b3ba88f165976e77ca5e6a7a3f5bba4562b80af/vllm/v1/engine/core_client.py#L818-L828)仍会阻塞。这次离线调用的输入在进入收结果循环之前就已准备好。

### 默认的异步调度，是另一件事

普通生成在兼容条件满足时默认开启异步调度。单卡`UniProcExecutor`允许两个在途批次，EngineCore据此走`step_with_batch_queue()`：队列有空位时先尝试调度并提交新批次，需要收结果时再取前一批的输出并更新状态。[批队列入口](https://github.com/vllm-project/vllm/blob/0b3ba88f165976e77ca5e6a7a3f5bba4562b80af/vllm/v1/engine/core.py#L187-L218)、[执行流程](https://github.com/vllm-project/vllm/blob/0b3ba88f165976e77ca5e6a7a3f5bba4562b80af/vllm/v1/engine/core.py#L469-L500)

再回头看日志里的`Asynchronous scheduling is enabled`，它说的是这层重叠关系。

进程边界要另看配置：本例单卡默认使用`uni`执行器，worker在EngineCore进程内创建，并没有再跨一道IPC去找worker。多卡或显式选择其他执行器时，进程布局可能改变。若设置`VLLM_ENABLE_V1_MULTIPROCESSING=0`，连主进程与EngineCore之间的这道边界也会消失。

### 这一站小结

- `LLM`提供外部接口，`LLMEngine`负责请求提交和输出处理。
- 离线`generate()`先添加这一批请求，再循环收齐结果。
- 主进程与EngineCore的分离、EngineCore内部的异步调度，是两件事。
- 本例worker与EngineCore同进程；批队列让跨批次的调度、执行和输出处理可以重叠。

## 第2站：调度，Continuous Batching的实现

EngineCore拿到请求后，调度器决定这一批让哪些请求前进，各处理几个token。主要入口是[scheduler.py:329的 schedule()](https://github.com/vllm-project/vllm/blob/0b3ba88f165976e77ca5e6a7a3f5bba4562b80af/vllm/v1/core/sched/scheduler.py#L329-L364)。开启异步调度后使用的`AsyncScheduler`继承这套主体逻辑，并补上在途输出的记账。

### 两个预算、两个队列

先看四样东西：

- token预算：这一批最多安排多少token计算，不是最多接多少个请求。
- KV块：显存里能否给这些计算提供缓存空间。
- `waiting`：等待接纳或恢复执行的请求。
- `running`：已经进入执行中的请求，里面也可能有尚未做完prefill的请求，不只包含decode。

V1调度器没有分成“先跑完整prefill阶段，再跑完整decode阶段”两套流程。它记录每个请求已经算到哪、还有多少token待处理，再给本批分配数量。

### 先安排running，再看waiting

源码先遍历`running`，再处理`waiting`。`running`里的核心计算节选如下：

```python
num_new_tokens = (
    request.num_tokens_with_spec
    + request.num_output_placeholders
    - request.num_computed_tokens
)
```

出处：[scheduler.py:385–389](https://github.com/vllm-project/vllm/blob/0b3ba88f165976e77ca5e6a7a3f5bba4562b80af/vllm/v1/core/sched/scheduler.py#L385-L399)。后面还会按长prefill阈值、剩余token预算和模型长度限制裁剪。

这里的`num_output_placeholders`是异步调度的记账：上一批已经提交，实际token结果还没收回，就先为预期输出占位。它不是用户输入的占位符，也不是额外生成了一份答案。

用一个小例子：B、C已经在decode，各需要处理1个token；A刚进入waiting，完整prompt只有4个token。假设本批预算为6，KV空间也够，B、C先各分到1，A再分到4。这个6只是便于算数的示意预算，不是默认配置值。

### 长prompt怎么分几次处理

如果A不是4个token，而是5000个，当前只剩2000的token预算，开启chunked prefill后可以先排一部分，后面再继续。调度侧的预算裁剪是：

```python
num_new_tokens = min(num_new_tokens, token_budget)
```

它位于[scheduler.py:650–670](https://github.com/vllm-project/vllm/blob/0b3ba88f165976e77ca5e6a7a3f5bba4562b80af/vllm/v1/core/sched/scheduler.py#L650-L670)。关闭chunked prefill时，整段装不进当前预算，就先停止从waiting接纳，留待后续尝试。

这行`min`只说明本批算多少，并不包办准入。调度器还要申请KV块；该版本默认会检查新请求的完整输入长度是否能放进KV cache，不能因为第一小段放得下，就认定请求一定能接进来。

![](https://pic1.zhimg.com/v2-64e74e746f5b3a6b04a76629b6c8011e_1440w.jpg)

图2中的running也可能包含未完成的prefill。若本轮发生抢占，源码会跳过waiting准入；因此不能把图读成“每轮都一定接新请求”。

### 抢占：释放占用，回队列准备重算

running请求需要新KV块，却申请不到时，调度器可能抢占一个请求。默认FCFS策略下，从running队尾选择；配置优先级策略时，选择规则不同。

`_preempt_request()`里的关键动作是：

```python
self.kv_cache_manager.free(request)
request.status = RequestStatus.PREEMPTED
request.num_computed_tokens = 0
# 中间省略了encoder缓存、投机token和统计的清理
self.waiting.prepend_request(request)
```

这是[scheduler.py:929–949](https://github.com/vllm-project/vllm/blob/0b3ba88f165976e77ca5e6a7a3f5bba4562b80af/vllm/v1/core/sched/scheduler.py#L929-L949)的节选：释放请求对KV块的占用，计算进度归零，再放回waiting队头。

这条路径不是把该请求的KV搬到CPU、之后再搬回来。重新接纳时需要重新准备计算；若存在可复用的前缀缓存，实际重算量还取决于命中情况。这里先不展开缓存复用，系列四专门讲。

我的理解是，选择重算，可以省去把KV搬到CPU、再搬回GPU的传输，但要付出重新计算的代价。哪边更划算取决于上下文长度、负载和硬件，不能只凭这段代码认定GPU总有富余算力。

![](https://pic3.zhimg.com/v2-0a71765656127f64f997c202beccee28_1440w.jpg)

### 调度结果交给执行层

调度器把决定装进`SchedulerOutput`：新接纳了哪些请求、已有请求有哪些增量、每个请求本批算多少token，以及块分配等信息。执行层再按这些信息准备张量。

操作系统类比可以帮忙记，但不要把两者当成同一套机制：

| 操作系统里熟悉的概念 | 这里可以对应理解的部分 |
| --- | --- |
| 就绪、运行队列 | waiting、running，但请求状态不等同于CPU线程状态 |
| 执行预算 | token预算，不是固定长度的CPU时间片 |
| 物理页帧管理 | KV块池与块分配 |
| 资源不足时暂停任务 | 抢占并回waiting，本文这条路径准备重算 |
| 调度结果 | SchedulerOutput，供执行层组织本批输入 |

### 这一站小结

- 调度按token数量和KV空间安排工作，预算不是请求数。
- running优先，但running不等于decode；waiting也不只放首次进入的请求。
- chunked prefill允许分段计算，`min`只是其中的预算裁剪。
- 调度结果写进`SchedulerOutput`；请求完成或被抢占后，占用的资源才有机会用于其他请求。

## 第3站：输入准备，变长请求压扁成一维

这一站使用OPT实际走的V1 runner：[gpu_model_runner.py:3955的execute_model()](https://github.com/vllm-project/vllm/blob/0b3ba88f165976e77ca5e6a7a3f5bba4562b80af/vllm/v1/worker/gpu_model_runner.py#L3955-L4000)，以及[_prepare_inputs():1863](https://github.com/vllm-project/vllm/blob/0b3ba88f165976e77ca5e6a7a3f5bba4562b80af/vllm/v1/worker/gpu_model_runner.py#L1863-L1899)。单卡默认仍在EngineCore进程内，不再跨一道IPC。

### 持久的请求状态，和本批输入分开看

V1的[InputBatch在gpu_input_batch.py:91](https://github.com/vllm-project/vllm/blob/0b3ba88f165976e77ca5e6a7a3f5bba4562b80af/vllm/v1/worker/gpu_input_batch.py#L91-L125)。它保存一组请求的持久状态，例如请求ID、token数据、计算进度和块表。每批先按调度结果增删、更新这些状态，再从中取本批要算的token。

`GPUModelRunner`另有预分配的输入缓冲区。持久请求状态、本批输入缓冲区和attention元数据分在不同结构里。读代码时可以按下面这张表找：

| 数据 | 本批用来做什么 |
| --- | --- |
| num_scheduled_tokens | 按执行层请求排列，各请求本批处理多少token |
| input_ids、positions | 本批送进模型的token与位置 |
| query_start_loc、seq_lens | 请求边界，以及包含本批输入后的序列长度 |
| slot_mapping | 新K/V写入哪些缓存槽 |
| logits_indices | 从模型输出里选哪些位置计算logits |

### 还是A、B、C，这次看输入长什么样

A的完整prompt为4个token，本批全部处理；B、C各做一次普通decode，本批输入的位置分别是50和30，下标从0开始。

为了让数字容易对照，下面假设执行层本批请求排列为A、B、C。这不是说调度器按A先、B后遍历；持久batch的行排列与调度遍历顺序要分开看。

```text
各请求本批token数 = [4, 1, 1]
input_ids的有效部分 = [A0, A1, A2, A3, B本步输入, C本步输入]
positions          = [ 0,  1,  2,  3,       50,       30]
query_start_loc    = [0, 4, 5, 6]
seq_lens           = [4, 51, 31]
```

6个有效token首尾相接，不需要先把三个请求都补到相同长度。`query_start_loc`标出每个请求在这一维输入里的起止位置，`seq_lens`告诉attention各请求已有多长的上下文。拼在一起不表示可以互相读对方的KV。

### 不按请求补齐，不等于完全没有padding

如果选中了CUDA Graph的某个执行档位，整批输入长度还可能被补大。上面6个有效token只是机制示例；若某次执行把整批补到8，后面多出的2个位置就不是新请求，也不应算进有效token工作量。

具体补到多少取决于图配置和执行路径，不能由这个示例断言。源码会同时保留实际数量和执行用的补齐数量，attention后端也区分有效输入范围。

![](https://picx.zhimg.com/v2-352ab75003afee5c451e0f53f20fe8b5_1440w.jpg)

### 这一站小结

- V1的`InputBatch`保存持久请求状态，runner据此准备本批输入。
- 有效token按本批请求排列拼成一维，不逐请求补到同一长度。
- `query_start_loc`和`seq_lens`让attention识别各自的边界与历史长度。
- 整批仍可能为执行档位padding；有效token数不一定等于实际送入计算的长度。

## 第4站：模型执行，attn_metadata如何传到attention层

模型拿到`input_ids`和`positions`后，依次经过各层。attention还需要刚才那些边界、长度和块表，它们合起来构成attention元数据，也就是`attn_metadata`。

这些信息没有逐层塞进每个模型的`forward`参数，而是由runner在执行期间放进`forward_context`：

```python
# 概念骨架，省略其他执行参数
with set_forward_context(attn_metadata, vllm_config, ...):
    model_output = model(input_ids=input_ids, positions=positions)
```

上下文入口是[forward_context.py:250](https://github.com/vllm-project/vllm/blob/0b3ba88f165976e77ca5e6a7a3f5bba4562b80af/vllm/forward_context.py#L250-L264)。它保存本次模型执行期间可访问的上下文。

attention层运行时，按自己的层名取回元数据、该层KV cache和写入映射。源码的[get_attention_context():648](https://github.com/vllm-project/vllm/blob/0b3ba88f165976e77ca5e6a7a3f5bba4562b80af/vllm/model_executor/layers/attention/attention.py#L648-L664)做这件事；`unified_attention_with_output()`再把它们交给后端。

```python
# attention.py:748–751节选
layer_name = _resolve_layer_name(layer_name)
attn_metadata, self, kv_cache, _ = get_attention_context(layer_name)
# 随后调用self.impl.forward(...)
```

![](https://pic4.zhimg.com/v2-8ca1e09bc1e58adcec0df3797a704f71_1440w.jpg)

到这里，只需记住数据怎么到达attention。编译还涉及custom op边界、分图和缓存写入的副作用；把对象放进上下文本身，并不保证编译器会忽略它。详细过程放在系列五，这里不再展开。

### 这一站小结

- runner在执行模型时建立`forward_context`。
- attention按层名取出本层所需的元数据与KV cache，再调用后端。
- 上下文传递解释了数据去向；编译是否能稳定复用，还需要其他机制配合。

## 第5站：PagedAttention，KV Cache的写与读

这里先限定普通的分页KV例子。每层缓存按固定大小的块管理，一个请求可以使用不连续的物理块。下面取`block_size=16`便于算数，不表示所有模型都固定使用16。

它减少了为每个请求预留整段连续显存的需要，但不是“碎片为零”：请求最后一块没填满时，仍会留下块内空位。这里的块也是KV存储单位，不是CUDA线程块。

### 写：slot_mapping给出每个新token的槽号

每个块能存16个token的KV，把块池所有位置统一编号后：

```text
槽号 = 物理块号 × 16 + 块内偏移
```

沿用A、B、C，假设块表如下。物理块号是为演示指定的，不是运行观测：

| 请求 | 物理块表 | 本批写入位置 | 槽号 |
| --- | --- | --- | --- |
| A | [7] | 逻辑位置0～3 | 112、113、114、115 |
| B | [2, 9, 4, 11] | 位置50，即逻辑块3、偏移2 | 178 |
| C | [6, 5] | 位置30，即逻辑块1、偏移14 | 94 |

于是按前面假定的执行排列，有效token对应：

```text
slot_mapping = [112, 113, 114, 115, 178, 94]
```

FlashAttention这条路径的KV写入会调用`reshape_and_cache_flash`，Python封装在[_custom_ops.py:2591](https://github.com/vllm-project/vllm/blob/0b3ba88f165976e77ca5e6a7a3f5bba4562b80af/vllm/_custom_ops.py#L2591-L2617)。它接收本步K/V、缓存和`slot_mapping`，按槽号写入。

在这里讲到的后端路径上，KV更新与attention计算是分开的步骤，两者通过dummy依赖表达写入与后续读取的关系。这部分编译处理见系列五。

### 读：block_table找到这个请求的历史KV

B本步处理位置50，attention要读取本请求到当前位置的KV。它的块表是`[2, 9, 4, 11]`，逻辑块0到3分别映射到这些物理块，不要求按物理编号连续存放。

新KV写入时，一个token对应一个槽；读取历史时，kernel按块表定位所需KV。它不需要先把整个请求的KV重新拼成连续的大张量。

[flash_attn.py:758–810](https://github.com/vllm-project/vllm/blob/0b3ba88f165976e77ca5e6a7a3f5bba4562b80af/vllm/v1/attention/backends/flash_attn.py#L758-L810)准备序列边界、长度和块表，再调用`flash_attn_varlen_func()`。核心参数可以这样读：

```python
# 参数关系示意，省略其他参数
flash_attn_varlen_func(
    q=query[:num_actual_tokens],
    k=key_cache,
    v=value_cache,
    cu_seqlens_q=attn_metadata.query_start_loc,
    seqused_k=attn_metadata.seq_lens,
    block_table=attn_metadata.block_table,
    ...
)
```

![](https://pic1.zhimg.com/v2-4a4c2e4689693f8ada3db133e08f93b4_1440w.jpg)

块表像页表，是因为都有“逻辑编号到物理位置”的间接映射；它并不是把操作系统的缺页处理、权限和换页机制完整搬到显存里。

### 这一站小结

- KV按块管理，请求不必占用一段连续的物理块，但仍可能有块内碎片。
- 写入靠`slot_mapping`，逐token指定缓存槽。
- 读取靠`block_table`，结合序列边界和长度定位本请求的KV。
- 页表类比帮助理解寻址，不代表两套内存系统完全相同。

## 第6站：输出，从logits到新token与块回收

模型产出hidden states后，还要经过词表投影和采样，才得到新的token ID。

### 选出要计算logits的位置

在普通、非投机解码路径里，runner按每个请求本批最后一个位置选择hidden state：

```python
logits_indices = query_start_loc[1:] - 1
```

出处：[gpu_model_runner.py:2128–2137](https://github.com/vllm-project/vllm/blob/0b3ba88f165976e77ca5e6a7a3f5bba4562b80af/vllm/v1/worker/gpu_model_runner.py#L2128-L2137)。对前面的输入，`query_start_loc=[0,4,5,6]`，选出的位置就是`[3,4,5]`。

A的4-token prompt已完整处理，可以从最后位置计算第一个生成token；B、C各用自己的decode位置继续生成。这里的数字示例不涉及投机解码。A、B、C是独立的token级示意，不对应开头那句中文的实际分词结果。

如果A只是长prompt的中间片段，这一步还不能给用户一个有效的生成token。该版本普通路径可能仍计算和采样这些位置，但随后会忽略未完成prefill请求的采样结果。不要把“选了最后位置”直接等同于“本步一定生成有效输出”。

### 采样、更新与回收

选中的hidden states经过词表投影得到logits，再按贪心、温度、top-p等采样配置得到token ID。模型执行结果以`ModelRunnerOutput`等结构交给EngineCore消费；默认单卡下，这里没有额外的worker进程IPC。异步路径可能先返回在途结果的封装，等批队列收取后再更新调度状态。

调度器把有效新token追加到请求，检查EOS、长度上限等结束条件。把`update_from_output()`里判断结束和释放的两段摘出来，可以接上前面的流程：

```python
# scheduler.py:1407–1410，节选
if new_token_ids:
    new_token_ids, stopped = self._update_request_with_output(
        request, new_token_ids
    )

# scheduler.py:1474–1480，省略中间其他处理
if stopped:
    finish_reason = request.get_finished_reason()
    finished = self._handle_stopped_request(request)
    if finished:
        kv_transfer_params = self._free_request(request)
```

出处：[更新token与停止判断](https://github.com/vllm-project/vllm/blob/0b3ba88f165976e77ca5e6a7a3f5bba4562b80af/vllm/v1/core/sched/scheduler.py#L1406-L1414)、[结束处理与释放](https://github.com/vllm-project/vllm/blob/0b3ba88f165976e77ca5e6a7a3f5bba4562b80af/vllm/v1/core/sched/scheduler.py#L1473-L1485)。

结束的请求释放对KV块的占用，并退出运行集合。共享或缓存的块按引用和缓存策略处理，不是把每个物理块的内容立即清零。

![](https://pic3.zhimg.com/v2-e44ff6848dbed2e42a73707222f3d202_1440w.jpg)

资源腾出后，后续批次就有机会接纳其他请求。没结束的请求继续留在运行集合，等下一次调度；不保证紧接着那一轮一定轮到它。

最后，`EngineCoreOutputs`跨IPC回到主进程，`LLMEngine.step()`处理输出、把token ID解码成文字，再组装成`RequestOutput`。`outputs[0].outputs[0].text`里的文本，就从这条路径返回。

### 这一站小结

- 普通非投机路径用`logits_indices`选每个请求本批的最后位置计算logits。
- 完整prefill之后可以生成新token，中间片段的采样结果不能直接作为有效输出。
- EngineCore消费执行结果、更新请求状态；完成请求释放占用，为后续调度腾出资源。
- 本例只有EngineCore到主进程这一步跨IPC，主进程负责输出解码和结果组装。

## 回头看这六站

调度器决定每个请求本批前进多少，runner把对应token准备成输入，attention按各自块表读写KV，结果再回到调度器更新进度。完成的请求退出，资源供其他请求使用。

读源码时，可以拿一个请求ID、一个token位置和一个KV槽号沿这条链找下去。类名会很多，但这三样数据的去向能把主线接起来。
