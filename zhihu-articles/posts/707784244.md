## 1. 为什么要使用和改进流水线并行训练？

### 1.1 简单流水线并行与流水线气泡

在使用 GPU 训练 Transformers 结构大模型的背景下，流水线并行对模型参数进行**水平**分割，使用多个设备（卡或机器，Rank or Node）构成一个保持完整模型参数的计算单元。每个计算单元内以流水线形式**异步**完成同一份批数据的前向过程和梯度的反向计算，并实现模型参数的**同步**更新。因为不同的并行分区以流水线形式进行异步计算，流水线并行的不同分区（具体到 Transformers 结构大模型就是不同的连续 Transformer Block）也习惯被称为 Stage。

流水线并行并不是新技术，在卷积神经网络把模型层数大幅加深的时代，流水线并行就已经被运用和改进了。

![](https://pic1.zhimg.com/v2-d6798800c7bd324b721347034b9397bc_r.jpg)
*Naive PP 与 GPipe，摘自：GPipi 原文。*

上图的（a）（b）示意了一个**在4个设备上被划分为4个 Stage 的简单流水线并行**（Naive PP，原文称作 Naive Model Parallelism，早年工作一般对TP和PP不加区分使用MP代指），各 Stage（并行分区）依次执行前向过程与反向过程，最后同时进行参数更新。

### 1.2 为什么要使用流水线并行训练

流水线并行对于模型参数的水平分割是非常简洁的操作。在 Batch Size 相同的前提下（单卡批数据量 vs 一条流水线一次参数更新的批数据量）对于单个设备，无论是 Model States 显存占用还是 Activations 显存占用，流水线并行都直接降低到原来的 1 / 流水线设备数。

这并不构成现如今要使用流水线并行训练的根本原因，优化的张量并行也能达到类似的显存占用效果。问题在于，由于张量并行产生的额外通信量巨大，实际运用中张量并行只能局限在单机（Node）内部（可参考[大模型效率工程（四）：张量并行训练及其优化详解](https://zhuanlan.zhihu.com/p/707623638)）。大模型的参数量越来越大，训练 Context Length 也被期望越大越好，Model States + Activations 的显存占用已经不是单机张量并行能满足的了。这就**需要 TP+PP 来共同保持一套完整的模型参数**。

![](https://pic1.zhimg.com/v2-f595a3048bd8c496f32a8cc4b1a1700a_r.jpg)
*摘自：Zero Bubble Pipeline Parallelism 原文。*

![](https://pic2.zhimg.com/v2-9116d138b39e0366474fef0be3dade99_r.jpg)
*摘自：Pipeline Parallelism with Controllable Memory 原文。*

### 1.3 为什么要改进流水线并行训练

**根本是因为流水线气泡（Pipiline Bubbles）的存在。**

还是以第1.1节图示（b）中的4设备4Stage简单流水线为例，计算设备的**空耗比是3**（空闲24消耗8），这都不能说是气泡了，而是空瓶子里面有1/4是水。这种计算能力的闲置，会大幅度降低计算吞吐量，白白消耗成倍的训练时间。大模型训练的高成本，使得改进流水线并行的动机更加充分，首要目标就是要减小流水线气泡。

在解决主要矛盾之余，流水线并行还提供了**进一步降低激活值显存占用**的可能，这是改进流水线并行的次要目标。

## 2. 记号与概念

### 2.1 Microbatch

这是一个 Naive PP 不存在的概念，改进的流水线并行一般在两次参数更新之间，会按照时间表输入多批次数据，每一批就是 Microbatch。一条流水线更新一次参数的批数据，就是对应于单卡模式的 Batch。

### 2.2 记号约定

本篇笔记延续着此前笔记的记号设定，针对流水线并行稍作调整。

假设 transformer 的层数是 $l$，transformer 输入输出的维度是 $d$，MHA 的头数是 $h$，query、key、value 的维度分别是 $d_q$、$d_k$、$d_v$（通常有 $d=hd_q=hd_k=hd_v$），GQA 头的分组数是 $g$ ，FFN 中间层的维度是 $d_{ffn}$ ，词表大小（决定了嵌入层和输出 softmax 的结构）是 $v$ 。

假设语料库总 Token 数是 $c$ ，单卡 Batch Size 是 $b$ ，流水线并行中的 Microbatch Size 是 $b_m$ ，设定 $b=m*b_m$ ，单序列 Token 数是 $t$ 。

定义构成一条流水线的设备数是流水并行度，记号是 $N_p$ ，模型划分的 Stage 数是 $N_s$ ，**并不总有 $N_p=N_s$** 。

假设不同 Stage 之间前向或反向过程需要的计算量一致，对于一个 Microbatch，前向过程计算量是 $\Theta_f$ ，反向过程获取激活值梯度计算量是 $\Theta_{a}$ ，反向过程获取参数梯度计算量是 $\Theta_w$ 。

### 2.3 构建流水线时间表的基本单元

![](https://picx.zhimg.com/v2-8755af6e0365c25d40723fd4ed06b099_r.jpg)
*Design pipeline schedule 的前两步，摘自：Pipeline Parallelism with Controllable Memory 原文。*

论文 [Pipeline Parallelism with Controllable Memory](http://arxiv.org/abs/2405.15362) 提出 **design pipeline schedules 的第一步是规划 building block**，这是构建流水间时间表的基本单元。

> It starts by laying out t**he passes for a single microbatch**, which we call a building block.<br>In this paper, we first demonstrate **all existing pipelines can be seen as repeating a basic building block in time**.

简单流水线并行的 pipeline schedule 就是 building block。

![](https://pic1.zhimg.com/v2-d09d8fe5ba9b95fab4f02d01674f2c16_r.jpg)
*构建1F1B时间表的第二步，摘自：Pipeline Parallelism with Controllable Memory 原文。*

**Design pipeline schedules 的第二步是无冲突的重复布置多个 Microbatch**。上图示意的是 1F1B 流水线并行的第二步（暂时不深究 1F1B），其 building block 与 Naive PP 相同，不同的就是能在一个 Batch 内无冲突布置多个 Microbatch。

上图中还包含两个重要概念：Lifespan 和 Interval。

Lifespan 是指一个 Microbatch 从开始前向过程到反向过程结束的时间跨度；Interval 是第二步操作中布置两个 Microbatch 的时间间隔。**Lifespan 和 Interval 对于流水线并行的 Activations 显存占用存在关键影响**。

## 3. GPipe 与 1F1B

### 3.1 GPipe 减小气泡

![](https://pic1.zhimg.com/v2-fd5806dca42694fd6edb6fecea362bf8_r.jpg)
*GPipe pipeline schedule，摘自：Efficient Large-Scale Language Model Training on GPU Clusters Using Megatron-LM*

先 Callback 一下记号

> 单卡 Batch Size 是 $b$ ，流水线并行中的 Microbatch Size 是 $b_m$ ，设定 $b=m*b_m$ 。<br>定义构成一条流水线的设备数是流水并行度，记号是 $N_p$ ，模型划分的 Stage 数是 $N_s$ 。<br>假设不同 Stage 之间前向或反向过程需要的计算量一致，前向过程计算量是 $\Theta_f$ ，反向过程获取激活值梯度计算量是 $\Theta_{a}$ ，反向过程获取参数梯度计算量是 $\Theta_w$

关于流水线并行的讨论一般都从 [GPipe](http://arxiv.org/abs/1811.06965) 讲起，上图示意的是一个 $N_s=N_p=4$ 、 $m=8$ 的 GPipe 流水线时间表。8个 Microbatch 依次从 Device 1 进入流水线，全部完成前向过程（上图中蓝色）后，顺次从 Device 4 开始反向过程（上图中绿色），全部完成反向过程后，最后进行参数更新（上图中粗黑竖线）。

GPipe 的 building block 表示如下：

![](https://pic3.zhimg.com/v2-7e7c0b7975eed80d6b12c4ac7fbd04de_r.jpg)
*摘自：Pipeline Parallelism with Controllable Memory 原文。*

下面来计算一下 **GPipe 流水线的空耗比**，俗称的流水线气泡大小。在同一设备上，可以用计算量代替时间来计算空耗比。

消耗： $m$ 个 Microbatch 的前向和反向过程， $m*(\Theta_f+\Theta_a+\Theta_w)$ 。

空闲：观察上图中的灰色部分， $(N_p-1)*(\Theta_f+\Theta_a+\Theta_w)$ 。

空耗比： $(N_p-1)/m$ ，可以看到，当 $N_p=4，m=1$ 时，也就是第1节图示的简单流水线，空耗比的计算结果也与第1.3节一致为3。

**结论：只要增大 $m$，就可以使 GPipe 的 Pipeline Bubble 变小。**

### 3.2 GPipe 的 Activations 显存占用

再 Callback 一下记号

> 假设 transformer 的层数是 $l$，transformer 输入输出的维度是 $d$ ，单序列 Token 数是 $t$ 。

**GPipe 中每一个并行分区最多都要保存所有 Microbatch 该 Device 所负责 Stage 的所有激活值。**

不同于论文的习惯，下面延续着之前笔记对于显存占用的计算设定和习惯（可以参考[大模型效率工程（二）：训练消耗评估纪要 - 知乎 (zhihu.com)](https://zhuanlan.zhihu.com/p/706675657)第3.2节和[大模型效率工程（四）：张量并行训练及其优化详解 - 知乎 (zhihu.com)](https://zhuanlan.zhihu.com/p/707623638)第2.5节），GPipe 流水线每个并行分区的 **Peak Activation Memory** 是：

$24*m*b_m*t*d*l/N_p=24btdl/N_p$ 。

按照论文的习惯，一般都会说 GPipe 的缺陷就是：随着 $m$ 增大，激活值显存占用增加。这要看怎么比，其实是可以调整 $b_m$ 大小的。如果按照刚才的计算习惯，当控制一条流水线的 Batch Size 等同于原本单卡 Batch Size 时，GPipe 的激活值显存占用实际不随 $m$ 变化而变化，受影响的反倒是 Microbatch Size，太小会降低浮点数计算能力的利用率，从而降低计算吞吐量。

### 3.3 1F1B 减小 Activations 显存占用

1F1B 是 one forward pass followed by one backward pass 的缩写，应该是大模型时代最基本的流水线并行方案。

想想为什么 GPipe 要保留所有 Microbatch 的激活值？因为是所有 Microbatch 前向过程完成后才开始反向过程。1F1B 就是打破了这个规则。

![](https://pic3.zhimg.com/v2-21f5347975125e77c4504486ef4caeb0_r.jpg)
*1F1B Schedule，摘自：Zero Bubble Pipeline Parallelism*

1F1B 的时间表被划分为3个阶段：

- Warm-up Phase（上图粉色框），和 GPipe 保持一致；
- Steady Phase（上图黄色框），执行 one forward pass followed by one backward pass；
- Final Phase（上图绿色框），执行所有剩余的反向过程。

**1F1B 的操作，使得新增一个 Microbatch 显存后马上就会释放一个 Microbatch 显存。**

仔细观察上图，在 1F1B 流水线中：

- Device 1 的 Peak Activation Memory 最大，是4个 Microbatch 所需的激活值显存；
- Device 4 的 Peak Activation Memory 最小，是1个 Microbatch 所需的激活值显存。

事实上，1**F1B 中每一个并行分区最多要保存 $N_p$ 个 Microbatch 该 Device 所负责 Stage 的所有激活值**。延续之前的计算设定和习惯，**1F1B 流水线每个并行分区的 Peak Activation Memory 是 GPipe 的 $N_p/m$** ：

$24btdl/N_p\div{m}\times{N_p}=24btdl/m$ 。与原始（[大模型效率工程（二）：训练消耗评估纪要](https://zhuanlan.zhihu.com/p/706675657)第3.2节）相比，通过增大 $m$ ，1F1B 流水线并行可以在 $1/N_p$ 的基础上进一步减少激活值显存占用。

1F1B 的 building block 表示如下：

![](https://pic3.zhimg.com/v2-8b027c13b46a998c2cc2b5f233df885e_r.jpg)
*摘自：Pipeline Parallelism with Controllable Memory 原文。*

### 3.4 1F1B 不同分区的显存不均衡

![](https://picx.zhimg.com/v2-616b50ebf791ab70cb5f4b56e1f6e7bf_r.jpg)
*1F1B 激活值显存与流水线次序线性相关，摘自：Reducing Activation Recomputation in Large Transformer Models*

通过刚才的计算已经发现，1F1B 不同并行分区的激活值显存占用峰值不同。如上图所示，1F1B 激活值显存与流水线次序线性相关，而且首个流水线分区由于一般额外包含 Embedding Layer，激活值显存峰值进一步增大。这使得流水线首个分区很容易成为大模型预训练过程中的瓶颈。

最基本的解决方案是采用不均等的流水线划分：

> both the initial and final pipeline stages possess one fewer transformer layer compared to the intermediate stages

这只能解决小部分问题。

Megatron-LM 团队通过 Microbatch 水平的激活重计算来平衡 1F1B 不同并行分区的激活值显存，详细可阅读论文 [Reducing Activation Recomputation in Large Transformer Models](http://arxiv.org/abs/2205.05198) 的 Appendix C，这里不做展开。

Sea AI Lab 则选择设计更优秀的 Pipeline Schedule 从根本上解决问题，详见第5.4节。

### 3.5 在更细的粒度上规划流水线时间表

从 Naive PP 到 GPipe，从 GPipe 到 1F1B，流水线并行的这两次升级具有相同的内核逻辑：在更细的粒度上规划流水线时间表。

**从 Naive PP 到 GPipe，是打破了单个 Microbatch 完整的梯度更新过程，实现了前向/反向过程维度上更细的规划粒度；从 GPipe 到 1F1B，又打破了 $m$ 个 Microbatch 整体进行的反向过程，实现了 Microbatch 维度上更细的规划粒度。**

**从 1F1B 往后，流水线并行的升级之路依然遵循着同一个内核逻辑**，更细粒度时间表规划的切入维度分为具体两种：

- 在前向/反向过程维度上进一步细化；
- 在流水线的 Stage 划分上细化。

## 4. 更细粒度的前向/反向过程划分 —— Zero Bubble

Sea AI Lab 提出的 [Zero Bubble Pipeline Parallelism](http://arxiv.org/abs/2401.10241)，将 Pipeline Bubble Rate 降低到了 1% 以下，Remarkable。

### 4.1 思考 GPipe 与 1F1B 的气泡是如何产生的？

部分原因是：**反向过程的计算量是前向过程的两倍**，导致耗时也是两倍关系。

![](https://pic3.zhimg.com/v2-e27f53d1dde91a355bcc67e4804dd75c_r.jpg)
*与3.3节中图示等价的 1F1B Schdule，摘自：Efficient Large-Scale Language Model Training on GPU Clusters Using Megatron-LM*

上图还是一个 $N_s=N_p=4$ 、 $m=8$ 的 1F1B 流水线时间表，本质上与3.3节中的图示等价，区别只有图中标记的部分。3.3节中的图示方便展示 1F1B 的三阶段，上图则方便展示 1F1B 气泡产生的原因。可以看到，进入 Steady Phase 之后，很多气泡都是因为反向过程耗时是前向过程耗时的两倍所产生。

### 4.2 反向过程的进一步划分

![](https://pic2.zhimg.com/v2-2d3b9e2502ebd4565f7884432acbb963_r.jpg)
*激活值梯度计算只依赖上层激活值梯度计算，摘自：Zero Bubble Pipeline Parallelism。*

如上图所示，反向过程对激活值梯度的计算（上图B）和对参数梯度的计算（上图W）并不是相互依赖的。这里的分析过程可以比原论文更进一步，把 $\sigma$ 视为独立的一层（这层只需要计算激活值梯度，没有参数不用计算参数梯度），也就是把上图中白色矩形忽略。激活值梯度计算与本层的参数梯度计算其实是独立的，只存在当前层激活值梯度计算对上层激活值梯度计算的依赖。理论上，甚至**可以先完成所有层的激活值梯度计算**，**再进行每一层的参数梯度计算**。

Zero Bubble Pipeline Parallelism 的核心就是：

> The key idea behind this improvement is to **split the backward computation into two parts, one that computes gradient for the input and another that computes for the parameters**.

遵循着1F1B 的法则，只不过B里只包含激活值梯度计算，参数梯度计算(W)可以非常灵活地在时间表中进行安排，以减小流水线气泡。

### 4.3 近似假设下的理论设计：ZB-H1 & ZB-H2

> For the sake of clarity in our initial design, **we assume that the time costs for F, B, and W are identical**, an assumption shared by earlier studies。

在上面 F、B、W 三过程耗时相同的近似假设下（实际上差不多），Sea AI Lab 团队给出了两种理论上的流水线时间表。

![](https://pica.zhimg.com/v2-b1cd1a537decbd1a630dc1367b3e367a_r.jpg)
*摘自：Zero Bubble Pipeline Parallelism 论文。*

ZB-H1 与 1F1B 非常类似，看下图的 building block 就非常清晰，就是在完成全部激活值梯度计算后，再进行参数梯度计算。在近似假设的条件下，**空耗比**从 GPipe 和 1F1B 的 $(N_p-1)/m$ ，下降为了 $(N_p-1)/3m$ 。ZB-H1 在**Activations 显存占用峰值**方面，也保持跟 1F1B 类似的特性：不同分区显存不均衡，峰值出现在首个分区，且与 1F1B 相同（ZB-H1 中 1 的含义）要能够保存 $N_p$ 个 Microbatch 该分区所负责 Stage 的所有激活值。

![](https://pica.zhimg.com/v2-4546abfa881961f5ff49729d7123f9ca_r.jpg)
*ZB-H1 的 building block，摘自：Pipeline Parallelism with Controllable Memory 原文。*

ZB-H1 的气泡好像也很好消除，把 Steady Phase 之前的气泡用新 Microbatch 的前向过程填满呗（我猜 Sea AI Lab 团队也是这么想的），配合**参数更新异步计算、同步效果**的特殊设计这就有了ZB-H2，可以看到理论上实现了 Zero Bubble，空耗比归0。

![](https://pic2.zhimg.com/v2-4d9517e4b32a59e6a9b92a7df626b8bd_r.jpg)
*ZB-H2 的 building block，摘自：Pipeline Parallelism with Controllable Memory 原文。*

ZB-H2 有什么问题？第一，激活值显存占用峰值翻倍（ZB-H2 中 2 的含义），因为首个并行分区最多要保存 $2N_p$ 个 Microbatch 该分区所负责 Stage 的所有激活值。第二，如果还坚持各并行分区参数同步更新，在 Steady Phase 填满的气泡会在 Final Stage 重新出现。Sea AI Lab 一定是左思右想后发现：必须突破参数同步更新的桎梏，才能实现气泡的进一步减小！

### 4.4 同步效果的异步参数更新

![](https://pica.zhimg.com/v2-281f824e37a687a51b714eca386f0502_r.jpg)
*同步效果的异步参数更新，摘自：Zero Bubble Pipeline Parallelism 原文。*

朴素地讲，原本是在参数更新前等待各并行分区完成同步通讯后执行参数更新，现在不等了，各分区完成参数梯度计算后就更新负责 Stage 的参数，异步完成所有分区的参数更新后，在下一轮的 Warmup Phase 执行更新检查，如果发现异步执行造成了问题，重新执行同步更新操作。

能这么做的关键点有两个：

- 异步更新参数出现问题的实际比例不高，事后诸葛亮的重新同步更新发生比例不高；
- 原来各分区的同步通讯变成了异步通讯，在最后一个分区前向过程完成后，原本同步通讯的效果就通过多次异步通讯达成了，这就为事后检查和回滚重新执行提供了依据。

可以查看 [Zero Bubble Pipeline Parallelism](http://arxiv.org/abs/2401.10241) 第4节获取更多细节。

### 4.5 实际条件下的 Almost Zero Bubble

在理论上打通了 Zero Bubble 的各环节后，Sea AI Lab 团队就开始尝试在实际件下的 Zero Bubble。

![](https://pic4.zhimg.com/v2-be5a106a3e54fdad6db228b5315415c5_r.jpg)
*GPT-3 F、B、W 的 FLOPS 和 激活值显存估算，摘自：Zero Bubble Pipeline Parallelism 原文。*

论文以 GPT-3 （本系列笔记的计算设定和习惯不同，并不影响定型结论）为例，给出了 F、B、W 三个过程的计算量与显存占用估计，重要的是：

- 参数梯度计算耗时<前向过程计算耗时<激活值梯度计算耗时；
- 反向过程计算耗时是前向过程计算耗时的2倍。

如何制定流水线时间表呢？论文首先给出了一个启发式策略，细节建议看原文，下面说下大致内容。

- Warm-up Phase：和 ZB-H2 类似，在各 Device 开始第一次激活值梯度计算前，尽可能塞入更多 Microbatch 的前向过程；
- Steady Phase：执行 1F1B 策略，在 Bubble 足够大的地方安排参数梯度计算，避免空闲，论文提到基本上实际执行会进入1F1B1W的循环模式；
- Final Phase：对于每个分区，前向过程和激活值梯度计算全部完成后，就依次完成剩余的参数梯度计算过程。

![](https://pic3.zhimg.com/v2-f88ab89d45f22d42c41090101e87ec68_r.jpg)
*启发式 Zero Bubble 流水线时间表制定策略，摘自：Zero Bubble Pipeline Parallelism 原文。*

启发式策略形成的时间表还可以作为整数线性规划的初始化，并且继续优化，这里就不展开了（运筹学上课没怎么听T.T），可以看原文 Appendix G。

论文汇报了在**两种不同分区激活值显存约束**条件下的实际结果，分区显存约束分别对应于理论设计中的 ZB-H1 和 ZB-H2。

- ZB-1p：约束激活值显存与 1F1B、ZB-H1 相当，$N_p$ 个 Microbatch 每个分区所负责 Stage 的所有激活值；
- ZB-2p：约束激活值显存与 ZB-H2 相当，$2N_p$ 个 Microbatch 每个分区所负责 Stage 的所有激活值。

![](https://pic3.zhimg.com/v2-bb1d9ab85e472bbc1e10c330b0de35ca_r.jpg)
*摘自：Zero Bubble Pipeline Parallelism 原文。*

气泡大小的实验结果与理论设计非常相符：

- ZB-1p 与ZB-H1 相当，回忆启发式规则的第一阶段，因为显存限制，ZB-1p 实际执行策略的效果就会和 ZB-H1 一样，在 Steady Phase 之前产生气泡；
- ZB-H1 相比 1F1B 大幅减小了流水线气泡，理论结果是1/3；
- ZB-2p 能够实现小于 1% 的空耗比，实际上 **ZB-2p 的显存约束是实现 Almost Zero Bubble 的最小值**，注意看下图的拐点。

## 5. 更细粒度的流水线 Stage 划分 —— Interleaved & V-shape

### 5.1 解耦流水线 Stage 的划分与分区布置

流水线 Stage 的划分（Model Partition），说的是对于模型结构按照自底向上如何水平切分；流水线 Stage 的分区布置（Device Placement），说的是确定每个并行分区执行哪个流水线 Stage。

本文之前提过的所有流水线并行方案，都默认流水线 Stage 的划分与分区布置是绑定的，每个分区执行一个Stage。这种思维惯性确实有理可循，从流水线分区间通信角度出发确实应该如此。暂时放开流水线分区间通讯的枷锁，流水线 Stage 的划分 $N_s$ 可以大于流水线并行度 $N_p$ ，不同的 Stage 可以随便布置在不同的并行分区上。现如今，已经存在有 $N_s=2N_p$ ，每个 Device/分区 部署两个 Stage 的流水线并行方案。

### 5.2 Interleaved 1F1B

这是 Megatron-LM 团队对 1F1B 的改进。

*从 1F1B 到 Interleaved 1F1B，摘自：Efficient Large-Scale Language Model Training on GPU Clusters Using Megatron-LM*

上图比较了 $N_p=4$ 、 $m=8$ 的 1F1B 和 Interleaved 1F1B，1F1B 有 $N_s=4$ ，Interleaved 1F1B 有 $N_s=8$ 。该 Interleaved 1F1B 各 Stage 在 Device 上部署的设置如下：

![](https://picx.zhimg.com/v2-717041e607c78cbef3ddf1695951ebf9_r.jpg)
*Interleaved 1F1B 流水线 Stage 的布置*

对于每一个 Microbatch 来说，其前向过程在依次通过 4 个分区后，会回到第一个分区，重新依次通过4个分区。

换个角度思考一下，这类似于每个 Microbatch 都变成了两个相互通信的 Microbatch，每个 Stage 的参数量减半，每个 Microbatch 单个 Stage 的计算量、耗时、激活值显存占用减半。如果能从这个角度想明白，就很容易得出： $N_s=2N_p$**的 Interleaved 1F1B 相比 1F1B 空耗比 $(N_p-1)/m$ （气泡大小）会减半，激活值显存占用峰值不变且仍出现在首个分区，分区间通信量翻倍。**

![](https://pic4.zhimg.com/v2-c6228936fa92487ef76c67ada2cd68b7_r.jpg)
*Interleaved 1F1B 的 building block，摘自：Pipeline Parallelism with Controllable Memory 原文。*

### 5.3 V-shape

Sea AI Lab 选择了与 Interleaved 不同的 Stage 布置设计。

**V-shape 不具体指某个 Pipeline Schedule**，只是指一种 Stage 的划分以及在 Device 上的布置设计；实际上 Interleaved 也是如此，Interleaved 1F1B 才是具体某一种 Pipeline Schedule。

![](https://pic4.zhimg.com/v2-dbd5d5d38964cba8d880cf9032d3784b_r.jpg)
*V-shape 流水线 Stage 的布置*

对于每一个 Microbatch 来说，其前向过程在依次通过 4 个分区后，会再倒序通过4个分区。

### 5.4 V-shape 能平衡并减小 Peak Activation Memory

回顾前文每次谈到激活值显存占用峰值时的文字：

- GPipe 中**每一个并行分区**最多都要**保存所有 Microbatch**该 Device 所**负责 Stage** 的所有激活值。
- 1F1B 中**每一个并行分区**最多要**保存 $N_p$ 个 Microbatch**该 Device 所**负责 Stage** 的所有激活值。
- ZB-H1 的**首个并行分区**要能够**保存 $N_p$ 个 Microbatch** 该分区所**负责 Stage** 的所有激活值。
- ZB-H2 **首个并行分区**最多要**保存 $2N_p$ 个 Microbatch** 该分区所**负责 Stage** 的所有激活值。

可以发现，分析流水线 Peak Activation Memory 包含三个要点：

- **要逐分区/Device分析；**
- **要确定需保存激活值显存的 Microbatch 的上限；**
- **要涵盖该分区/Device负责的所有 Stage。**

[Pipeline Parallelism with Controllable Memory](http://arxiv.org/abs/2405.15362) 指出：对于每个 Stage 而言，需保存激活值显存的 Microbatch 的上限由 Lifespan 和 Interval 所确定（详细内容可参考原文2.2节），具体就是： $\frac{Lifespan}{Interval}$ 。这其实也很好理解，Lifespan 决定了一个 Microbatch 需要保存其激活值显存的周期，在这个周期中能塞入几个 Microbatch，就代表了需要保存激活值显存的 Microbatch 的上限，不就是总时间/间隔。

我们再来观察5.3节中比较 Interleaved 与 V-shape 类流水线 building block 的图，解释为什么 V-shape 能在不同分区之间平衡 Peak Activation Memory。

- 首先，对于同一条流水线的不同分区，Interval 肯定是相同的，于是，问题退化为比较两类流水线各个分区所有 Stage 的 Lifespan 之和。
- 观察左侧 Interleaved（Parallel），第一个分区（第一行）两个 Stage 的 Lifespan 之和为 $l_1+l_4$ ，最后一个分区（第三行）两个 Stage 的 Lifespan 之和为 $l_3+l_6$ ，很显然 $l_1+l_4 > l_3+l_6$ ，Interleaved 理论上就无法在各分区见实现激活值显存峰值的均衡。
- 观察右侧 V-shape，第一个分区（第一行）两个 Stage 的 Lifespan 之和为 $l_1+l_6$ ，最后一个分区（第三行）两个 Stage 的 Lifespan 之和为 $l_3+l_4$ ，很显然 $l_1+l_6 \approx l_3+l_4$ ，因此，V-shape 理论上就可以实现 Peak Activation Memory 在各个分区间的均衡。

下面来不严谨的解释一下V-shape为什么能够减小 Peak Activation Memory。如下所示，三角形代表 Device 显存不均衡的流水线，长方形代表 V-shape 类流水线，在总激活显存占用相同的情况下，长方形的显存峰值是不是三角形的一半？

## 6. 额外的通讯量

流水线并行引入的额外通讯依次发生在 Stage 之间，前向过程向顶层传递激活值，反向过程向底层传递激活值梯度。Stage 的划分数决定了每个 Microbatch 通讯的次数（这里就不纠结分五段只需四刀了），每次传递的张量形状是 $b_m*t*d$ 。那么一个 Step 传递的浮点数总量就是 $m*b_m*t*d*N_s*2=2btdN_s$ ，平均到每个并行分区/Device 就是 $2btdN_s/N_p$ 。使用混合精度技术，流水线并行引入的分区平均通信量就是 $4btdN_s/N_p$ 。

跟之前的笔记保持一致，以 Llama-7B 为例（虽然用不上PP），不使用 Interleaved 或 V-shape 的额外通讯量是 $4*2K*4096\approx32M$ Bytes/Step，使用了也就是 64M Bytes/Step，相比于 TP 的额外通讯量确实小了太多，这也就是为什么在实际中可以运用多台机器构成 PP，因为节点间通讯带宽相对能够满足 PP 带来的额外通讯量。
