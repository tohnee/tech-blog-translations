MCP（Model Context Protocol）是一份"AI 应用"和"外挂能力"之间的通用接口标准。没有它的时候，每接一个新数据源（GitHub、数据库、公司内部系统），每个 AI 应用都要单独写一套代码；有了 MCP，数据源实现一次服务端、AI 应用实现一次客户端，就能互相连上。打个比方：它像 USB-C 那样的统一接口——插座端做一次，设备端做一次，谁插谁都能用。这一篇不讲条款，从一个具体例子开始，把 MCP 的几个基本角色讲清楚。

## 一、先看一个具体场景

用户在 AI 应用里说： **"帮我看看 langchain-ai/langgraph 这个仓库最近有哪些新 issue。"**

这个请求能完成，背后发生了这么一串事：

1. **AI 应用** （比如 Claude Desktop、Cursor，或者自己写的 agent）里其实有一个"连接器"，它连着一个专门访问 GitHub 的小程序——这就是 **MCP 服务器** 。
2. 连接器先问服务器："你能做什么？"服务器回答："我有一个工具叫 `list_issues` ，需要传仓库名。"
3. AI 判断该用这个工具，于是让连接器发出调用请求： `list_issues(仓库="langchain-ai/langgraph")` 。
4. 服务器收到后， **真的去调 GitHub 的 API** ，把拿到的 issue 列表返回。
5. AI 拿到这批数据，写成一段中文总结回给用户。

这五步里，没有任何一步是"AI 直接上网"。AI 只是决定"我要用一个叫 `list_issues` 的工具"；真正去访问 GitHub 的是那个 MCP 服务器。 **AI 负责判断，服务器负责执行** ——这是理解 MCP 的第一把钥匙。

## 二、三个角色：Host、Client、Server

刚才例子里出现的三个东西，在 MCP 里各有正式名字：

**Host（宿主）** ——你直接使用的那个 AI 应用。它负责：创建和维护连接、决定允许 AI 用什么、在有风险的操作前征求你的同意。例子里就是 Claude Desktop 或 Cursor 本身。

**Client（客户端）** ——宿主内部的一个"连接通道"， **一个通道对应一个服务器** 。宿主可能同时连着文件系统、GitHub、数据库三个服务器，那它内部就有三个客户端，彼此隔离。规范里特别强调这一点：每个客户端只跟一个服务器打交道， **服务器之间互相看不见** 。

**Server（服务器）** ——提供能力的那一头。可以是一个本地小程序（比如访问你电脑上文件的服务器），也可以是一个远程服务（比如公司内部的订单系统）。它对外只做一件事：告诉别人"我能提供什么"，然后按要求执行。

![](https://pic2.zhimg.com/v2-9c93f77591c0049afdcc7e3e32b46baf_1440w.jpg)

为什么要把"连接通道"单独拆成一层？因为 **安全边界画在这里** 。完整对话历史留在宿主里，服务器只能看到"你让我做的这件事"需要的参数——它看不到你和 AI 的完整聊天记录，也看不到别的服务器在做什么。这是 MCP 的硬设计原则，不是可选项。

## 三、服务器能提供三种东西

一个 MCP 服务器可以对外提供三类能力，区别用一句话就能分清：

| 类型 | 一句话 | 上面例子里对应的 | 谁来决定用它 |
| --- | --- | --- | --- |
| 工具（Tools） | AI 能做的事（执行函数） | list_issues——真的去查 GitHub | AI 模型自己判断 |
| 资源（Resources） | AI 能读的数据 | 某个 issue 的内容（有固定地址，可订阅变化） | 应用或用户挑选 |
| 提示（Prompts） | 用户能用的模板 | "帮我审查这个 PR"这样的固定指令模板 | 用户主动触发（比如斜杠命令） |

三者的关键区别在 **谁能发起、有没有副作用** ：

- **工具** 是唯一能"改变世界"的——它能创建订单、发消息、改文件。所以规范要求宿主在调用工具前必须获得用户同意。
- **资源** 是只读的，像是给 AI 的资料库；资源有固定地址（URI），还能订阅"变更通知"（数据变了主动告诉客户端）。
- **提示** 是给用户省事的模板，不涉及权限问题——用户点了才用。

## 四、客户端也能提供东西：把问题问回用户

反过来，客户端也能向服务器提供能力。目前最核心的一个叫 **Elicitation（引出）** ：服务器在处理请求时，可以 **反过来问用户要信息** 。

比如一个下单服务器，AI 让它下单但没说选哪个规格，它就可以问用户："蓝色还是黑色？"用户在界面上选完，服务器拿到答案继续干活。

这套"让用户做选择"的机制有个专门的选项定义方式（下拉框、单选、多选都能表达），是第 3 篇的主题。

顺带说一句演进：规范在最新版本里 **弃用了三个旧能力** （Roots、Sampling、Logging），建议新实现不要再添加——MCP 正把注意力集中到"工具和数据接入"这一件事上。

## 五、它们之间怎么说话

前面讲的都是"角色分工"，最后说说"说话格式"。MCP 的消息全部是 **JSON-RPC 2.0** 格式，就是一段约定好结构的 JSON，比如客户端问"有哪些工具"：

```text
{
  "jsonrpc": "2.0",
  "id": "req-1",
  "method": "tools/list",
  "params": {}
}

```

服务器就把工具清单放在响应的 `result` 里返回。请求、响应、单向通知，三种消息覆盖了所有交互。

这里有一个最新版本的重要设计： **MCP 是无状态的协议** ——每个请求都自带"我是谁、我支持什么版本、我有什么能力"，服务器不靠"之前的请求"来理解当前这个请求。规范里有一句很直白的话： **一个打开的连接不是一次会话** ，客户端可以在同一条连接上交错发送互不相关的请求。

为什么要把自己做成这样？因为状态意味着成本：服务器要记住每个连接的情况，就意味着扩容时得迁移状态、负载均衡得粘住同一个实例。无状态之后，任何一台服务器都能处理任何请求——这是 MCP 服务器能大规模部署的前提。

（这部分在最新规范里是一次大改：旧版本靠 `initialize` 握手建立会话，新版本直接移除了握手和会话 ID，新增了一个 `server/discover` 方法让客户端先问"你支持什么"。想深入的话，规范原文在 modelcontextprotocol.io。）

## 六、本质

MCP 解决的问题一句话就能说清： **让"AI 应用"和"外部能力"之间只需要实现一次接口** 。

三个角色分工明确：宿主负责安全和控制，客户端负责连接（一个对一个），服务器负责提供能力（工具/资源/提示）。消息用 JSON-RPC 说话，且每个请求自带上下文——这让服务器可以随便扩缩容。
