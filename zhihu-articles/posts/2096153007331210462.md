基础RAG搭建只是一个简单流程：用户问题->向量化->向量库检索top-k片段->把检索片段+问题丢给大模型生成答案。但是真实的业务中会遇到：检索噪声大、专有名词匹配差、上下文过长、需要多步推理等问题。所以我们需要使用新的方法，根据这些痛点做架构升级。

## **进阶**

在原有的向量检索流水线上增加若干优化模块，不改变“检索→生成”的基本范式，对检索、上下文环节增强。其中 **Hybrid Search、Rerank、Context Compression** 属于固定流水线内的增强模块； **Multi-hop RAG** 是动态多轮检索，流水线不固定，作为进阶到高阶的过渡单独展开。

1.Hybrid Search混合检索：是⼀种将向量检索与关键词检索结合的技术。

纯向量检索擅长语义理解、同义改写；但对专有名词、产品型号、编号、关键词精确匹配能力弱； 传统关键词检索（如：BM25）擅长精确关键词命中，但无法理解语义改写。混合检索是两路检索并行执行，再将结果融合排序。例如：向量检索召回语义相似的文档，关键词检索召回包含目标关键词的文档；两路结果合并后做融合排序，常用 RRF（只看排名、无需分值归一化）或加权分数融合（需先归一化再调参）。混合检索同时兼顾语义理解与关键词精准命中，企业知识库生产环境非常常用。

向量检索和关键词检索各给出一份排名，但两边的分数不是一个尺子量的，不能直接相加。RRF 的做法是“只看名次不看分数”——排第1给高分、排第2给次高分，两路名次加起来重排；加权分数融合则是先把两路分数换算到同一量纲，再按权重相加。前者省事、不用调参，后者更灵活但要人工调权重。

2.Rerank：重排序

Rerank 就是用更强的模型， **拿着原始 query 和文档放在一起，重新打分，纠正粗召回的错误顺序** 。在RAG系统中，向量检索通常会返回Top-K个候选文档，比如20个文档，但是这些文档并不完全准确，如果要直接丢给LLM则token开销大，噪声还会误导大模型生成错误答案，因此需要进一步进行Rerank。Rerank本质等于二次筛选然后重新排序，也就是先粗找，再重新排序，再输出分高的数据。

两种Rerank方法：

1).Cross Encoder：把查询的问题和文档拼接在一起同时送入模型，模型看到两边的全部内容，直接学习两者交互语义与相关性， **Cross-Encoder 精度通常高于 Bi-Encoder** 。

Bi-Encoder（Embedding）：双塔独立编码，预计算文档向量，检索快，适合百万级知识库粗召回；看不到 query 和文档的交互。

Cross-Encoder：单塔，query + 文档拼接一起输入，能做交叉注意力交互，打分准；无法预计算向量，只能少量候选精排。

2).LLM Rerank：大模型重排

直接让大模型当裁判：给prompt。让LLM输出query和这篇文档的相关分数。这种方法理解能力非常强，能看懂复杂逻辑，指代，长文本关联。但是成本也很高，token消耗大，速度最慢，很多LLM打分不稳定，分数标度漂移。在实际⼯程中，Rerank通常会将Top-K检索结果进⼀步缩⼩为Top-3或Top-5，从⽽ **降低噪声、提高输入上下文的精准度，但不能保证一定正确** 。

常用的Reranker模型：

BGE-Reranker：中文很强，体积不大。适合绝大多数中文知识库、企业内部 RAG。

Jina Reranker：采用 listwise 重排，把查询和一批候选文档一起送入模型，让文档之间互相参考、比较相对相关性，而不是逐篇独立打分。适合长文档、论文、合同、代码库等需要“批内比优劣”的检索场景。注意：单篇文档超出上下文窗口时仍需分块，listwise 解决的是批内互比，不是单篇不切。

Qwen3-Reranker：中文理解强，对表述绕、歧义强的难题效果突出；缺点是速度偏慢、显存占用较高，适合复杂业务问答、歧义多、对精度要求高的 RAG。

**Rerank不一定会有提升效果。如果粗召回里没有正确文档，Rerank再强也排不出来，它只能调整已有的候选顺序，不能凭空找到“正确文档”或“变出文档”！**

3.Context Compression：上下文压缩

大模型输入的长度是一个很重要的限制，塞不下几十条文档，无关内容还会带来幻觉、干扰。即使经过重排序，拿到的文档块依然很长，里面很多句子和用户问题无关，不可能将所有检索到的⽂档全部输⼊给模型。把一大堆资料塞给模型，它往往记得开头和结尾，中间那段容易“看漏”——这就是 **Lost‑in‑Middle（中间丢失）** 现象。所以不是塞得越多越好，塞多了反而可能把关键证据埋没，同时还会消耗大量 token、变慢、容易撞上下文窗口上限。

所以上下文压缩的目标就是： **在保留关键信息的前提下，减少输入文本的长度。**

常见的压缩方法：

1)段落筛选：只保留与用户问题高度相关的段落，而非整篇文档。

2)句子级过滤：通过模型判断哪些句子与问题最相关，然后只保留这些句子。

3)摘要压缩：使用模型对文档进行摘要，生成更短但是信息密度更高的文本。

通过压缩上下文可以显著减少模型输入的长度，同时避免无关信息干扰生成结果。

4.Multi-hop RAG：多跳/多轮检索(动态RAG，流水线不固定)

Multi-hop RAG：就是回答一个问题，要分好几次去知识库里面查资料，上一步查到的内容，用来帮你生成下一步该查什么。普通RAG只搜一次，query从头到尾不变，Multi-hop RAG边查边想，根据上一轮查到的内容动态生成下一轮的搜索词，反复检索，适合需要推理，信息分散在不同文档，一环套一环的链式嵌套。Multi-hop 的轮次和停止条件通常由架构预定义；若由模型自主规划、反思、选择工具和来源，则属于 Agentic RAG。

固定流水线的RAG：用户问题->一次向量召回+rerank->拿文档->LLM回答

Multi-hop RAG：用户问题->LLM思考缺什么信息，生成第一个检索词->第一跳检索+rerank->拿到信息A，思考缺什么信息如果缺，生成第二个检索词->第二跳+rerank->拿到信息B，思考缺不缺信息，缺就继续跳继续查，不缺就->停止检索，LLM汇总全部信息回答。

## 高级RAG架构

根据复杂业务场景的需求，在RAG基础之上构建更⾼级的检索和推理机制，让系统具备更加复杂的知识组织能⼒、更灵活的检索策略以及更强的推理能⼒。这些架构不是互斥层级，而是分别补“知识组织、索引粒度、来源融合、决策策略”四个维度的缺口，可以组合使用。

常见的高级RAG架构包括Graph RAG、Agentic RAG、Multi-source RAG、RAPTOR(递归摘要树RAG)。Graph RAG 改的是“知识怎么连起来”，RAPTOR 改的是“答案该在粗粒度还是细粒度上找”，Multi-source 改的是“从哪几个不同系统取数”，Agentic 改的是“谁来决定查不查、怎么查”。它们不是四个必须全上的台阶，而是四种不同病因对应的药。

Graph RAG：抽取文档实体与实体关系构建知识图谱，沿着实体关系链路检索；擅长实体关联、多跳关系类问题；短板是图谱构建成本高，实体抽取错误会持续影响效果，维护成本重。

Agentic RAG：以 LLM 作为规划 Agent，自主决策是否检索、调用检索 / 数据库 / API / 代码解释器等工具；适合检索叠加外部工具的复杂任务；短板是规划循环的收敛与停止条件设计难度高，流程不可控、延迟波动大、稳定性差。Multi-hop 像“按剧本演”：剧本写好了最多查三轮、每轮查完判断缺不缺，缺就按规则再查。Agentic RAG 像“演员自己决定怎么演”：查不查、查几轮、换不换工具、要不要回头重查，都由模型现场判断。前者可控但死板，后者灵活但容易跑偏、延迟和成本不可控。

Multi-source RAG：增加数据源路由模块，自动判断问题该向向量库、ES、关系数据库、文件接口等哪一类异构数据源查询；核心价值是统一多源数据入口，本身推理能力不强。

RAPTOR (递归摘要树 RAG)：自底向上对文本块聚类、逐层生成高层主题摘要，构建树形索引；专门弥补普通 RAG 全局归纳、跨文档汇总能力弱的短板，长文档汇总场景优势明显。
