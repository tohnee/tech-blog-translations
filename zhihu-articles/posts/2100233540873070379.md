作者: PyTorch Foundation

我们很高兴地宣布 PyTorch® 2.15 正式发布！

PyTorch 2.15 版本包含以下重要变更：

- **重写的 NCCL 后端成为默认后端**，附带在挂起时转储的 flight recorder，并以 `TORCH_DIST_USE_NCCL2=0` 或 `nccl-legacy` 作为回滚路径
- **torch.distributed 新增单边传输（one-sided transport）**，首个后端为 NIXL，传输可被 CUDA Graph 捕获
- **FSDP2 与流水线并行获得更精细的显存与通信控制**：精度敏感参数可保持 fp32，梯度累积可被 CUDA Graph 捕获，梯度规约可与计算重叠
- **NVIDIA Blackwell GPU 上 4-bit（NVFP4）LLM 解码更快**：NVGEMM 以更少、重叠更好的内核启动达成
- **Apple Silicon 获得 FP8 支持与更快的解码**：新增 `float8_e4m3fn` 与 `_scaled_mm`，带解码快速路径的新 grouped_mm（MoE 解码 tokens/s 提升 1.32–1.34 倍），以及公开的 `torch.mps.Stream` API
- **更广泛的平台支持**：AMD gfx950 上的 FlyDSL 内核、gfx1250（MI450）的 Tensor Data Mover 支持、ROCm 10.0 wheels、Intel GPU 上更简单的 SYCL 内核编写与多 GPU 性能分析、默认 wheel 升级到 CUDA 13.2（同时提供 CUDA 13.4），以及 torch.compile 支持 Python 3.15

自 PyTorch 2.14 以来，本次版本由 583 位贡献者贡献了 3,117 次提交。我们衷心感谢热忱社区的贡献。一如既往，欢迎大家试用并在 2.15 改进过程中反馈问题。关于如何开始使用 PyTorch 2 系列，更多信息请参见我们的 Getting Started 页面。

如果对 PyTorch 2.15 有任何疑问，欢迎参加我们的 Q&A 网络研讨会，时间为太平洋时间 2026 年 11 月 5 日星期四上午 11 点。Tristan Rice、Natalia Gimelshein、Huy Do 和 Jane Xu（均来自 Meta）将概述 2.15 版本并回答社区关于 PyTorch 及本版本新能力的问题。Chris Gottbrath（Gottbrath Tech）主持。立即注册。

在整个 2.x 系列中，PyTorch 正从一个研究优先的框架，演进为一个统一、硬件无关的大规模生产训练与推理平台。PyTorch 2.13 在 Apple Silicon 上落地了 FlexAttention，为 Inductor 提供了 CuTeDSL 代码路径，并引入了面向大规模集群训练的 torchcomms。PyTorch 2.14 将这条路径成熟为 NVGEMM，预览了重写的 NCCL 后端，并为 Apple Silicon 带来了原生线性代数。

PyTorch 2.15 在这些工作之上继续构建：重写的 NCCL 后端如今支撑每一个 `nccl` 进程组，NVGEMM 针对低精度解码做了调优，Apple Silicon 新增 FP8 与解码专用内核，AMD 支持扩展到新的编译器 DSL 以及（预览支持）下一代 Instinct，Intel GPU 获得更简单的内核编程模型与更深入的性能分析。

## 分布式训练

### 重写的 NCCL 后端成为默认

当一个模型跨多张 GPU 训练时，这些 GPU 需要通过通信后端不断交换数据，而在 NVIDIA 硬件上这个后端就是 NCCL。在 PyTorch 2.15 中，每个使用 `nccl` 的任务默认运行在我们重写的后端上。PyTorch 2.14 将从 torchcomms 移植而来的重写 NCCL 后端作为可选的 `nccl2` 后端预览。在 2.15 中，它成为每个 nccl 进程组的默认后端，并以 `TORCH_DIST_USE_NCCL2=0` 和 `nccl-legacy` 后端名作为回滚路径。通信器如今随进程组即时创建，重配置可以选择 shrink/grow 快速路径（NCCL 2.29 或更新版本），让存活的 rank 跳过完整的引导过程。在 ROCm 上，配合 RCCL 2.30.7 也启用了用于容错的重配置。

为了让后端在生产环境中可调试，一个后端无关的 flight recorder 会在集合通信挂起时将事后分析（post-mortem）写入磁盘，并将看门狗健康状态发布到调试服务器，这样任何 rank 上的超时都会触发所有 rank 的 flight recorder 转储。在集群规模下，单张停滞的 GPU 就可能让整个训练停止，而找到原因往往意味着手工复现故障。flight recorder 捕获挂起时刻每个 rank 正在做什么。

**API Unstable**

（PRs #192281、#192895、#199240、#198865 和 #198339 by Tristan Rice, Meta；#194774 by Chinmay Kuchinad, AMD；#192233 和 #199092 by Tushar Jain, Meta；#192075 by Atharva Kshirsagar, Red Hat）

### 基于 NIXL 后端的单边传输

torch.distributed 新增了一个用于单边数据移动的 Python 传输 API，NIXL 是第一个后端。传输通过 store 连接到对端，无需进程组或集合通信；`Transport.read_stream/write_stream` 将传输入队到 CUDA stream 上，从而可以被 `torch.cuda.graph` 捕获。

**API Unstable**

（PRs #195643、#197032、#198889 和 #198918 by Tristan Rice, Meta）

### FSDP2 与流水线并行：显存与通信控制

FSDP2 如今提供对精度与捕获的更精细控制。精度敏感参数——例如 MoE 路由门控和 norm 权重——可以保持 fp32，而模型其余部分以 bf16 训练，并且每次 `fully_shard` 仍只需一次 all-gather（`MixedPrecisionPolicy(param_dtype_override_fn=...)`）。一个完整的梯度累积步骤现在可以被单个 CUDA graph 捕获。梯度精度也可以按参数设置。梯度直接累积进 `.grad` 并遵循每个参数的 `grad_dtype`，这改变了 `reduce_dtype=None` 时的默认行为（参见"弃用与不兼容变更"）。

流水线并行现在在每次接收前才分配接收缓冲区，而非预先为每个 microbatch 分配，并在前向输出发送完成后立即释放。调度接受 `max_outstanding_sends` 预算，FSDP unshard 操作在每个 rank 的启动间隙中交错进行，而非在一个步骤开始时全部发出。流水线并行 rank 之间由调度确定的每条唯一边，如今都有专用的 P2P 通信器。FSDP 的梯度规约现在可以与后续计算重叠。这些改进让 PyTorch 流水线并行可被 CUDA Graph 捕获、确定性执行、显存布局经过优化，并暴露了用于最小化暴露通信的性能调节旋钮。

**API Unstable**

（PRs #196640、#196724、#196727、#196641 和 #196963 by Chien-Chin Huang, Meta；#196626 by Anshul Sinha, Meta；#198417 by Andrew Or, Apache Spark PMC；#194114 by Animesh Jain, Meta；#196463、#196464 和 #196706 by Sanket Purandare, Meta）

## 性能改进

### 更快的 MPS 解码与线性代数内核

在 2.14 迁移的基础上，更多 MPS 算子从 MPSGraph 迁移到原生 Metal 内核。对 128,256 条词表的单行 softmax 加速 8 倍，upsample 反向最高快 21.7 倍，reduction 如今共享一套内核，使 `norm` 全量 reduction 快 100 倍以上。

在解码方面，`F.linear` 如今使用现有的 gemv 内核（几何平均加速 1.23 倍，小投影上最高 5 倍）；新的 MPS `grouped_mm` 提供 gemv 路径，在 M3 Ultra 上使 MoE 解码吞吐提升 1.32–1.34 倍。若干线性代数求解器也被重写：512×512 矩阵的 QR 分解从约 7 秒降到 1.5 ms，三角求解如今采用分块（blocked）实现。

（PRs #196071、#199687、#198611、#198495、#194933、#198721、#198725、#198732、#195944 和 #196900 by Irakli Salia, Hugging Face；#196922、#196241 和 #195369 by Nikita Shulga, Thinking Machines Lab；#193153 by Sunghyun Choi, Tech University of Korea；#188473 by Shrivas Shankar, University of Wisconsin-Madison）

## 核心特性

### 默认 CUDA 13.2 并提供 CUDA 13.4 wheels

默认 PyTorch wheel 升级到 CUDA 13.2（13.2.2 toolkit），同时为 Linux x86_64、Linux aarch64 和 Windows 提供 CUDA 13.4 GA wheels。CUDA 13.4 wheels 新增对 NVIDIA Rubin GPU 的实验性支持。

（PRs #198913 和 #196014 by Andrey Talman, Meta；#194996 和 #198843 by Ashish Karale, NVIDIA；#196560、#199269 和 #196351 by Ting Lu, NVIDIA；#192653 by Wei Wang, NVIDIA；#186245 by Lakshay Garg, NVIDIA）

### ROCm 10.0 与 TheRock wheels

PyTorch 2.15 在 2.14 引入的 ROCm 7.14 wheels 之外，新增 ROCm 10.0 wheels。所有 ROCm wheels 如今基于 AMD 的 TheRock 包构建，并将 ROCm 作为 pip 依赖（匹配的 rocm 包）安装，而非内嵌 ROCm 库。

（PRs #194919、#198895 和 #196610 by Ethan Wee, AMD；#195672 by Andrey Talman, Meta）

### Python 3.11 至 3.15，以及 Python 3.15 上的 torch.compile

PyTorch 2.15 支持 Python 3.11 至 3.15，包括 free-threaded 的 3.14t 和 3.15t 构建。在 2.15 中，Dynamo 新增 Python 3.15 支持。

（PRs #178393、#194117 和 #198018 by Rob Timpe, OpenTeams；#198233、#199398 和 #199356 by Andrey Talman, Meta）

## 平台特性与更新

### CUDA

### 面向 NVFP4 解码的 NVGEMM

NVGEMM 是 2.14 加入的 CuTeDSL GEMM 后端，如今将 ModelOpt NVFP4 线性层的标量反量化因子折叠进 GEMM，去除了解码时每层一次独立的 pointwise 内核启动。一个有界、形状感知的候选策略覆盖了 nvMatmulHeuristics 遗漏的 Blackwell NVFP4 解码形状；NVGEMM 内核可使用程序化依赖启动（programmatic dependent launch），让 Triton consumer 与 producer GEMM 的尾部重叠。NVGEMM 同时迁移到了 CUTLASS Operators。

**API Unstable**

（PRs #194651、#194652、#197485、#194792 和 #194793 by Michael Lazos, Meta；#194364 by Masaki Kozuki, NVIDIA）

### ROCm

### gfx950 上的 FlyDSL 内核与 gfx1250 上的 Tensor Data Mover

FlyDSL 与 CuTeDSL、Triton 和 Helion 一道，成为 PyTorch 可使用的内核 DSL。在 gfx950 上，Inductor 对 GEMM、不规则 `F.grouped_mm` 以及 MXFP4/MXFP8 `scaled_mm` 的 FlyDSL 模板与 Triton、ATen 一起做自动调优；在 eager 模式下，FlyDSL 可以覆盖 RMSNorm 和 topk。FlyDSL 是可选的，需要 FlyDSL 0.3.x。

在 gfx1250（MI450）上，Inductor 对稠密 mm/addmm、pointwise 与 reduction 代码生成以及 FlexAttention 前向和解码使用 Tensor Data Mover。gfx1250 已加入 nightly wheel 架构列表。

**API Unstable**

（PRs #192877、#190903、#194032、#191446 和 #191447 by Xiaobing Zhang, AMD；#194981 by Yutao Xu, AMD；#196719 by Heng Yi, AMD；#191166、#196525 和 #197329 by Glen Cao, AMD；#196610 by Ethan Wee, AMD）

### MPS（Apple Silicon）

### Apple Silicon 上的 FP8、Streams 与更快的 MoE 推理

`torch.float8_e4m3fn` 如今在 MPS 上受支持，同时支持带 tensorwise 或 rowwise 缩放的 `_scaled_mm`，以及面向解码尺寸形状的 gemv 快速路径。MPS 还获得了一个仿照 CUDA 的公开 stream API：`torch.mps.Stream`、`current_stream`、`set_stream`、`torch.mps.stream` 上下文管理器，以及 `Tensor.record_stream`。

API Unstable（PRs #194074、#196916、#197862、#196945、#196918 和 #196955 by Irakli Salia, Hugging Face；#191415、#193464 和 #195867 by Kurt Mohler, OpenTeams；#196395 by Aditya Venkataraman, Meta）

### XPU（Intel GPU）

### 简化的 SYCL 内核编程

本版本为 XPU 后端引入了 SYCL free-function 内核支持，大多数现有 SYCL 内核已迁移到新的编程模型。通过用显式 free-function 内核替代冗长的基于 functor 的实现，开发者可以更直观地编写设备代码，降低为 Intel XPU 开发和移植自定义 GPU 内核的门槛。

（PRs #196387、#196932、#198200、#198720 和 #200223 by Yifeng Cui, Intel）

### 增强的 XPU 运行时能力

本版本扩展了 XPU 运行时能力：为 torch.xpu.Event 增加 IPC 支持，使事件可跨进程共享，并与 torch.multiprocessing 集成。此外，torch.xpu.MemPool 如今支持 use_on_oom 和 non_split 分配策略，为需要处理显存不足或利用分布式对称内存工作流的应用提供更大灵活性。

**API Unstable**

（PRs #191182、#192495、#192514、#192038 和 #192033 by Guangye Yu, Intel）

### 改进的 XPU 性能分析体验

本版本新增对 XPU Graph 回放的内核级可见性、XCCL 集合通信的跨 rank 关联，以及多 GPU 工作负载中所有 Intel GPU 的逐内核硬件计数器采集。这些增强为基于 graph、多 GPU 以及分布式训练与推理提供更深入的性能分析能力。

（PR #195128 by Chuanqi Wang, Intel；PR #5486 和 #1479 by Adrian Ostrowski, Intel）

### C++ ABI

### 扩展的稳定 ABI 与 Header-Only 接口

`torch::stable::sort` 加入稳定 ABI；Python 互操作 shim 在现有张量转换之外新增 dtype/device 转换和 `is_tensor` 探测。`c10/util` 的更多部分（irange、load、数学常量、类型转换与溢出检查）迁入 `torch/headeronly`，旧路径保留为转发 include。当扩展的 `TORCH_TARGET_VERSION` 比其 libtorch 头文件更新时，扩展现在会得到编译期错误；`load_inline` 可以生成在 free-threaded Python 上安全导入的 pybind11 模块。

（PRs #198038 by Adrian Abeyta, Red Hat；#194673、#194781 和 #193962 by Chris Leonard, Red Hat；#192774 by Paweł Gadziński, NVIDIA；#196802 by Alex Malyshev, Meta）

## 性能分析与调试

### 使用 Cuspy 进行 CUDA Graph 内核归因

从 CUDA graph 回放的内核如今可以归因回捕获它们的代码。内核注解从 CUPTI 节点创建回调记录，并由 `export_chrome_trace` 内联写出；配合 `record_py_stacks`，CUDA graph 为每个节点捕获 Python 启动栈。CUPTI monitor 更名为 Cuspy，并通过 `CuspyConfig` 启用。

**API Unstable**

（PRs #191999、#194854、#196528、#198419 和 #196529 by Natalia Gimelshein, Meta；#196066 by Ryan Zhang, Meta）

## 弃用与不兼容变更

- **不再支持 Python 3.10。** PyTorch 2.15 要求 Python 3.11 或更新版本：不再构建 3.10 wheels，CI 中也不再测试 3.10。不支持在 3.10 上从源码构建，后续版本将移除剩余的 3.10 代码路径，包括 torch.compile（Dynamo）中的部分。见 #198233 和 #199417。
- **nccl 如今选择重写的 NCCL 后端。** 设置 `TORCH_DIST_USE_NCCL2=0` 或使用 `nccl-legacy` 后端可恢复旧版 `ProcessGroupNCCL`。见 #192281。
- **来自 torch.ops 与自定义算子的 C++ 警告如今会传播到 Python。** 见 #193451。
- **不再支持 macOS 14。** PyTorch 2.15 的 MPS（Apple Silicon GPU）加速要求 macOS 15 或更新版本。macOS 14 已到达生命周期终点，针对它的 MPS 变通方案已移除。PyTorch 可能仍能在 macOS 14 上运行，但不再在该版本上测试，其上的问题也不会修复。见 #199261。
- **FSDP2 将分片与未分片的梯度 dtype 分离。** 见 #194434。
