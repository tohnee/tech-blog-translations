> 一个越狱 PlayStation 5 上的原生应用：把 llama.cpp 的 Vulkan 后端跑在游戏机的 GPU 上，用 27B 模型以每秒 20 token 的速度生成，并通过 OpenAI 兼容 API 服务于全家设备——而它对上游 llama.cpp 的全部改动只有 5 个补丁、286 行。

### 一、项目概览

### 核心定位

PS5LM Plus 回答的问题听起来像个玩笑：能不能让一台游戏机变成家里的 LLM 服务器？答案是可以，而且路径相当工程化。它是 [cobanov/PS5LM](https://github.com/cobanov/PS5LM) 的 fork：原项目证明了 llama.cpp 能在 PS5 的 Zen 2 CPU 上以载荷（payload）形式运行——27B 模型 streamed from disk，约每分钟 1 个 token；这个 fork 由 abhi245y 开发，把推理搬进一个原生应用（title），拿到 12 GiB 直接内存和整个 GPU，27B 模型加速到 20+ tok/s，并以 PR #12 回馈上游。

### 二、核心设计理念

### 理念一：移植引擎，而不是移植模型

README 的”Why llama.cpp”一节说得直白：此前的 PS5 LLM 工作（如 ProsperoAI）为每个模型手写 AGC GPU 内核，支持 Q4_0 一种量化——新模型或新量化意味着新内核。PS5LM 反其道而行，把 llama.cpp 本身移植过来，于是它支持的每一种架构、每一种量化（从 1-bit 到 8-bit）自动全部可用。

这个决策的代价与收益同样巨大：收益是引擎的进化免费获得（pin 在 `b11327`，理论上随上游更新）；代价是必须让一套为 Linux/Windows 设计的构建与运行时假设在 FreeBSD 血统的封闭主机上成立。项目把全部平台适配压缩在两处——`patches/` 下 5 个补丁共 286 行（对 llama.cpp），和 `ps5/app` 下约 6,205 行自有应用代码。这个”薄适配层”的比例本身就是设计宣言：平台知识的密度最高处不在补丁里，而在 harness（应用壳）里。

### 理念二：用进程边界管理不可控的内存

主机系统不给应用完整的控制权：标题不能真正 `exit()`、原地卸载模型会泄漏约 5 GiB 显存（11.01 GiB 空闲降到 5.77 GiB，项目实测且至今未定位）、读传感器返回 `0x80020002`。PS5LM 的应对不是 fight the platform，而是把操作系统提供的那一个干净原语用到底——`sceSystemServiceLoadExec` 让系统替换整个进程。于是模型切换 = 重启自身：把选择写进 `/data/PS5LM/model.txt`，LoadExec 自己的 `eboot.bin`，新进程从完整内存池开始。下载队列存在 `downloads.json` 里，跨重启续跑。这一理念贯穿全项目：**凡是平台不可靠的资源管理，都交给进程生命周期。**

### 理念三（贯穿性）：每一条平台限制都由一次崩溃发现，并被写成文档

`docs/CONSOLE.md` 列出标题与载荷的差异：不可 `exit()`（SIGSYS）、`isatty`/`getnameinfo`/`fork` 等 import 解析为空指针、SDK 的 `getaddrinfo` 永远失败、没有 `HOME` 会让 llama.cpp 抛异常。README 说”each was found by a crash”。这种把逆向过程本身当作一等资产的姿态，让这个仓库同时成为 PS5 homebrew 开发的公开参考文档。

### 三、架构总览

![](https://pic2.zhimg.com/v2-d89a525c9f1b97d1d965d02a76efb7d9_r.jpg)

整个系统是一个进程：llama-server、RADV、GL 界面栈全部链接进一个 fSELF `eboot.bin`（标题 ID PPSA99581）。五层从上到下：

### 第 1 层：用户界面层（TV 上的仪表盘）

`dashboard.cpp`（2,055 行，项目最大文件）实现 5 个页面（`dashboard.hpp:41` 的 `kPages = 5`）：仪表盘、设置、日志、获取模型、下载，外加一个模型库浮层。仪表盘是 bento 网格：生成速度与历史、GPU/CPU 占用、SoC 功耗与每 token 能耗、温度风扇、内存池拆分、上下文占用、每个驱动器的存储。绘制通过 ps5-homebrew-ui 工具链，其 GL 栈与 RADV 同进程——两套 Mesa 构建有 4,399 个同名符号，解法是 GL 栈只暴露 GL/EGL API 全局符号链接（`docs/CONSOLE.md`）。

### 第 2 层：应用编排层

`main.cpp`（912 行）：60 fps 主循环读取手柄、分发请求、绘制；`sceKernelSendNotificationRequest` 发系统通知；`quit_if_asked()` 轮询 `/data/PS5LM/quit` 文件实现优雅退出。模型加载的决策链是三级 fallback：`app-args.txt`（逐行覆盖规划器）→ `model.txt`（切换重启时写入、用后即删）→ 设置里的开机默认模型。

### 第 3 层：模型服务层

llama-server 作为应用内线程运行（`main.cpp:348` 的 `run_server` 直接调用 `llama_server(argc, argv)`），监听 8081 端口（`main.cpp:111` 的 `kPort`），同时服务 llama.cpp 自带 WebUI、OpenAI Chat Completions/Responses 和 Anthropic Messages 三种 API。规划器（`model_plan.cpp`）为每个模型计算装入方案。对上游的 5 个补丁都在这一层生效，后文详述。

### 第 4 层：平台服务层

`market.cpp`（622 行）实现 Hugging Face 模型市场与断点续传下载；`fetch.cpp`（192 行）封装 libSceHttp2；`stats.cpp`（442 行）每秒采集 llama-server 的 `/metrics` 与 `/slots`、直接内存池余量、传感器（经 ps5-exporter）。

### 第 5 层：系统与驱动层（仓库之外）

RADV（PS5_Vulkan 仓库，在 `.deps/src` 构建后被静态链接为 `libvulkan_radeon.ps5.a`）、Sony 系统库、越狱载荷链。应用不带 Vulkan loader——RADV 整体链入，`main.cpp:71-87` 手工导出 `vkGetInstanceProcAddr` 等 4 个入口，把 ICD 变成进程内驱动。

### 依赖可替换性

| 依赖 | 耦合程度 | 替换成本 |
| --- | --- | --- |
| llama.cpp(子模块 b11327) | hard-coupled(产品即其存在) | 升级需重放 5 补丁; 换引擎 = 重写项目 |
| ps5-homebrew-ui(子模块) | interface-abstracted | 通过 hui:: API 隔离; 换 UI 库重写 dashboard.cpp |
| PS5_Vulkan RADV(仓库外) | hard-coupled(静态链接 .a) | 最重的外部依赖: 需克隆三个仓库按 pin 版本构建 |
| libSceHttp2/libSceSsl | hard(平台唯一 HTTPS 通道) | 无替代; CHANGELOG 记录其 4 请求上限与限速已由实测摸清 |
| ps5-exporter(内置 v0.2.0) | optional | 不在时传感器显示为未知, 不阻塞功能 |
| nlohmann/json, sha256 | vendored(经 llama.cpp) | 无感知 |

关键抽象边界有两道：llama.cpp 与 harness 之间靠 `llama_server(argc, argv)` 这一个函数调用加环境变量（`LLAMA_TOOLS_ROOT`）——所以上游补丁才可能只有 286 行；UI 与应用逻辑之间靠 `Dashboard::Request` 这一个请求枚举（`dashboard.hpp:77`），界面层只发请求不理解执行。

### 四、数据流：从浏览器提问到 GPU 出 token

五层的职责划清之后，最快的检验方式是追踪一条真实请求。以一次最典型的使用为例——PC 浏览器里打开 `http://<PS5 IP>:8081` 发送一条消息：

```text
PC 浏览器
   │ HTTP :8081（局域网）
   ▼
llama-server 线程（第 3 层，独立 pthread，16 MiB 栈）
   │ Jinja 聊天模板 → 采样参数（规划器选的预设）
   ▼
llama.cpp → ggml-vulkan → RADV（第 5 层）
   │ 27B 权重与 KV 缓存全在 11.44 GiB 统一设备堆里
   ▼
AGC → PS5 GPU（RDNA 2）──token 流式回到浏览器
   ▲
   │ 每秒轮询 /metrics + /slots
stats.cpp（第 4 层）── Live 快照（互斥锁保护）
   ▲
   │ 每帧 set_live()
main.cpp 主循环（第 2 层）→ dashboard.cpp（第 1 层）在 TV 上画出速度曲线
```

而模型怎么进入内存是另一条流：用户在模型库按 Cross → `main.cpp` 写 `model.txt` 并 `sceSystemServiceLoadExec` 重启 → 新进程里规划器解析 GGUF 头、算出上下文与缓存方案 → `llama_server` 线程带着完整参数启动 → 82 秒后（27B 实测）仪表盘变 Ready。

这条链路上有四个节点值得停下细看：重启式模型切换对应第 2 层（5.1），GGUF 规划器对应第 3 层（5.2），与 llama.cpp 的 286 行边界（5.3），以及标题读不了传感器时的双进程协作（5.4）。

### 五、独特设计深度解析

### 5.1 模型切换 = 重启进程：LoadExec 作为内存管理器

**问题**：在运行中的应用里卸载模型，GPU 内存回不来。项目实测（`docs/CONSOLE.md`）：Qwen3.8-27B UD-IQ2_XXS 在 64k 上下文下，加载前内存池空闲 11.01 GiB，`llama_server` 返回后只剩 5.77 GiB，ggml 的 Vulkan 计数同步下降——下一个模型的 KV 缓存装不进去。泄漏点至今标注为 open。

**机制**：换模型时，应用把选择写入 `/data/PS5LM/model.txt`，显示三帧忙碌画面，然后调用 `sceSystemServiceLoadExec("/app0/eboot.bin", NULL)`（`main.cpp:793`）。系统杀掉旧进程、启动新进程，`model.txt` 被读一次后删除——所以普通启动不加载任何模型、直接打开模型库。内核日志里能看到 `Kill for LoadExec(0x11d)`，新进程从完整的 11.01 GiB 空闲开始。

**代码**（`main.cpp:863-868`）：

```cpp
// Unloading in place leaves part of its model's GPU memory held
// (about 5 GiB of a 6.8 GiB model, measured), so a model change
// restarts the app: the system replaces the process (LoadExec on
// our own eboot.bin, "Kill for LoadExec" in the log) and the new
// one starts from the whole pool, with model.txt saying what to load.
std::ofstream(kChoice) << (req.kind == Dashboard::Request::load ? req.path : std::string("none")) << "\n";

```

**权衡**：切换代价约 30 秒（卸载 + 重启 + 加载），期间服务中断；换来的是绝对的内存干净。这不是新思路——游戏机游戏换关卡本来就走 LoadExec——但把它作为 LLM 服务的资源策略，是对主机沙箱模型的准确理解。同一策略延伸到下载：模型占着内存时下载大文件会 OOM，应用同样以重启让路（`market_download_unload` 请求），队列文件保证重启后下载自动开始。

### 5.2 规划器：自己解析 GGUF 头，在下载之前就知道装不装得下

**问题**：一台 16 GB 共享内存的主机，每个模型能用的上下文和 KV 缓存量化方式都不同。用户需要的是”这个模型能跑吗、能跑多长上下文”在按下 Cross 之前就有答案——对市场里 9 GiB 的远程文件也一样。

**机制**：`model_plan.cpp` 包含一个独立的 GGUF 头解析器（`Reader` 结构支持文件与内存两种来源——PS5 的 libc 没有 `fmemopen`，注释写明），处理全部 13 种元数据值类型、跳过词表数组、取数值数组的最大值（逐层 `head_count_kv`）、减去 MTP 块（Qwen 3.8 的 UD-Q2_K_XL 带 65 块，主栈只有 64）、为混合注意力架构（Gated DeltaNet/Mamba）计算每层固定 f32 状态的体积。

规划本体（`model_plan.cpp:312-385`）是一个双循环择优：

```cpp
// The longest context first, and at each length the best cache that fits.
static const uint32_t ctxs[]  = { 131072, 65536, 32768, 16384, 8192, 4096 };
static const char *   types[] = { "f16", "q8_0", "q4_0" };

```

从 128k 到 4k 共 6 档上下文、从 f16 到 q4_0 共 3 档缓存，先最长上下文、再最优缓存，第一个装进剩余预算（`weights + kv + ssm 状态 + 0.75 GiB 保留`）的组合胜出；f16 缓存只在 8k 以下考虑（注释：q8_0 的质量损失测不出来）。保留项 0.75 GiB 是在主机上标定的。

**杀手锏在远处**：同一个解析器吃远程文件。市场页面对 Hugging Face 文件发 `Range: bytes=0-16777215` 请求（`market.cpp:196-197`），拿文件前 16 MiB 就能解析头并给出完整的装入方案——”下载之前就知道装不装得下”，Square 键按需触发。这是整个模型市场体验的地基。

**测试**也是围绕它建的：`model_plan_test.cpp` 是唯一的测试，在宿主机上对真实 GGUF 断言——qwen35 架构必须解出 64 层、16 个 KV 层、4 个 KV 头、f16 每 token 65536 字节；UD-Q2_K_XL 在 11.38 GiB 预算下必须给出 64k+q4_0（实机跑过的配置）。

**权衡**：规划器是 GGUF 格式的第二个实现（llama.cpp 里已有一个），格式演进时要跟着改；换来的是零依赖、可测、可对远程文件使用。

### 5.3 286 行的上游边界：五个补丁各管一件主机特有事

**问题**：跟上理念一——对 llama.cpp 的修改必须最小，否则 pin 的 `b11327` 之外寸步难行。

**机制**：五个补丁（`patches/`，合计 286 行）每个只做一件事：

| 补丁 | 行数 | 做什么 |
| --- | --- | --- |
| 0001 safe-cpu-defaults | 49 | __PROSPERO__ 下默认线程数 = 亲和性掩码 CPU 数减二, 轮询默认关(载荷只有 5⁄16 CPU, 默认值曾让主机关机两次) |
| 0002 thread-affinity | 99 | ggml 把 PS5 当”不支持平台”, -C/--cpu-strict/--prio 落空; 补丁映射到 scePthreadSetaffinity/setprio, 只降不升, 主线程永不钉核 |
| 0003 tools-root | 35 | LLAMA_TOOLS_ROOT 把聊天文件工具关进 /data/PS5LM/scratch: 相对路径从它开始, 外部路径被当作相对路径拉回来 |
| 0004 anthropic-system | 48 | Claude Code 在对话中段发 system 消息, Qwen 模板拒绝; 折叠进首条 system |
| 0005 listener-survives | 55 | 断网后 accept() 失败被 cpp-httplib 视为致命, 关掉监听套接字; 补丁让它每秒重绑直到成功 |

0004 和 0005 值得展开，因为它们展示了”真实用户逼出来的补丁”。0004 解决的是协议方言：Claude Code 的 Anthropic Messages 客户端会把 system 提示放进 `messages` 数组中段，而 llama.cpp 的 Anthropic 转换层原样透传，Qwen 的 Jinja 模板直接报错 “System message must be at the beginning”——于是 PS5 上每个 Claude Code 请求都 500。补丁在 `server_chat_convert_anthropic_to_oai` 里把所有非首位 system/developer 消息合并进首条。0005 解决的是主机网络现实：CHANGELOG v0.8.1 的”Found”小节考证了控制台网口几秒内 down/up 八次的内核日志，`SCE_NET_EINACTIVEDISABLED`（errno 163）让监听线程退出，模型还在内存里却无人能连。补丁加了 `std::atomic<bool> stopping` 和重绑循环，CHANGELOG 记录”几十次断网后监听都在一秒内恢复”。

**权衡**：补丁触到 llama.cpp 的 server 内部（`server-http.cpp`、`server-chat.cpp`、`server-tools.cpp`），上游重构时需要人工重放；但每个补丁都小到可以整体重写。0003 的沙箱化（一个环境变量 + 路径改写，35 行）对比操作系统级沙箱是弱隔离——逃逸路径（如 symlink）未在补丁中处理，这是”游戏机上的玩具工具”级别的务实选择。

### 5.4 标题与载荷的双进程协作：ps5-exporter 的自我部署

**问题**：标题被禁止读温度/风扇/功耗传感器（`0x80020002`），`statvfs` 是个桩（对任何路径都报告 64 GiB 总量 16 GiB 空闲，CHANGELOG v0.7.0 实测记录）——而载荷（payload）什么都能读。

**机制**：应用自带 ps5-exporter 的 ELF（GPL-3.0，pin v0.2.0，放在 `/app0/payloads/`）。`stats.cpp:340-348` 的逻辑：先试 `sceKernelGetSocSensorTemperature`（万一未来固件放行）；失败则 HTTP 请求本机 9100 端口的 `/metrics`；仍不通，就把内置 ELF 通过 socket 原始字节流推给 elfldr 的 9021 端口（`send_payload`，`stats.cpp:174-197`）——elfldr 会把它作为载荷进程启动，每分钟重试一次直到 elfldr 在线。传感器、真实磁盘余量（Prometheus 文本解析，`drives_from_metrics`）随之而来。

```text
标题进程(PPSA99581)                    载荷进程(ps5-exporter)
  stats.cpp ── HTTP GET :9100/metrics ──▶ Prometheus 文本
      │                                        ▲
      └─ 不通时: ELF 字节流 ──▶ elfldr :9021 ──┘ (启动载荷)
```

**权衡**：引入了对 elfldr 的软依赖（没有它传感器显示未知、不阻塞功能）；换来的是绕过标题沙箱最干净的合法路径。这个模式——**应用自我补给平台能力**——是主机 homebrew 生态里少见的工程化解法，也解释了为什么 README 的前置条件表里 elfldr 是”强烈推荐”而非”必需”。

### 六、生态定位：从载荷到标题，从浏览器到 API

四个独特设计分别解决了数据流上的关键节点，那么这个项目在更大的坐标系里处在什么位置？历史分析库中没有同类 LLM 推理引擎的深度分析可供对照；最接近的相邻分析是 new-api（Go 编写的 AI API 网关，聚合 40+ 上游、统一 OpenAI 兼容接口）。两者恰好构成互补关系而非竞争：PS5LM 是一个 OpenAI 兼容端点的**生产者**（模型在家里、数据不出局域网），new-api 一类网关是**路由者**（多供应商聚合、计费、密钥管理）。new-api 追求协议统一与渠道抽象，PS5LM 追求单设备上的引擎完整性和零隐私外泄——前者面向团队资产管理，后者面向个人硬件复用。把 PS5 的 8081 端口接入 new-api 做备用渠道，是两者天然的组合方式。

更有意义的对照其实是项目内部的时间线——fork 前后的架构演进：

| 维度 | 原 PS5LM(载荷, v0.1.x) | PS5LM Plus(标题, v0.2.0 起) |
| --- | --- | --- |
| 进程身份 | elfldr 启动的载荷, budget 0 | fSELF 标题, ShadowMountPlus 注册 |
| 内存 | 8 GiB flexible 池, 约 6 GiB 上限, 无直接内存 | 12 GiB 直接内存, RADV 统一为 11.44 GiB 单堆 |
| 计算 | Zen 2 CPU 5 逻辑核(0xea00 掩码) | 整个 RDNA 2 GPU(ggml-vulkan) |
| 27B 速度 | 约 1 token/分钟(磁盘流式) | 20.3-20.7 tok/s |
| 界面 | PS5 浏览器里的两个网页(ES5) | TV 上的原生仪表盘(ps5-homebrew-ui) |
| TLS | mbedTLS 3.6.7 + Mozilla CA 捆绑 | 系统 libSceHttp2/libSceSsl, 零自带证书 |
| 服务对象 | 本机浏览器 | 全局域网: WebUI + OpenAI/Anthropic API + 编码 Agent |

演进的主线不是”加了功能”，而是**换了一次进程身份**——载荷的所有限制（budget 0、无 GPU、无直接内存）源于 elfldr 启动进程的方式（`sys_budget_set(0)`，`docs/CONSOLE.md` 有逐条考证），标题身份一次性解开。fork 保留了上游的载荷代码（`ps5/ps5lm`、`ps5/compat`、`probes/`）作为可运行的对照组和探测工具，这个”不删旧路径”的做法让两个身份的实测数据可以随时互证。

### 七、代码质量分析

生态定位揭示了它作为推理端点的独特性，接下来从工程质量角度审视其内部实现。

### 优点

- **文档是项目的一部分，而不是事后补充**。`docs/RESEARCH.md` 有一张”其他 homebrew 的教训”表，12 条经验每条注明来源项目与具体 commit（如”pinned thread 的子线程继承其掩码——PS5SX2 f9abb4a”）；`docs/CONSOLE.md` 的每个数字都标了测量方法。`docs/plans/` 下 5 份设计笔记与 CHANGELOG 的”Checked on the console”段落构成可追溯的验证记录——CHANGELOG 里甚至有”Measured”小节专门记录下载速度的逐项实验。
- **并发边界清晰**。数据流经三处明确的所有权交接：UI 只通过 `Dashboard::Request` 单值枚举发请求；`StatsCollector::snapshot()` 互斥锁拷贝返回 `Live` 值对象；`Market` 的浏览/规划/下载各自单线程串行（`run()` 的 `flag.exchange(true)` 防重入）。6,205 行的应用代码里没有一处裸共享状态的即兴同步。
- **错误路径被认真设计过**。下载器把 4xx（除 408/429）判为致命、其余指数退避（4/8/16/32/60 秒，最多 20 次连续失败，`market.cpp:517-521`）；`fetch.cpp` 手动跟随重定向是因为实测”库自己跟随后报了长度但不给正文”（注释原文）；错误消息带十六进制错误码（如 `sceHttp2ReadData 0x804101a3`），可直接 grep。
- **债务显式标记**。全仓库 0 个 TODO/FIXME，但有 5 处 `ponytail:` 标记——作者的私有记号，标出诚实的未知（如”0.25 GiB 图像编码器缓冲是猜的，需实测”、”解码槽位运行期间 GPU 视为满载，无更细读数”）。CHANGELOG 的”Found”小节记录与项目无关的问题（网卡反复断开的内核日志考证），这是调试纪律而非营销文案。

### 潜在问题

- **无 CI，测试覆盖等于一个文件**。没有 `.github/`，唯一的自动化测试是宿主端规划器断言；其余验证是 `scripts/preview-app-ui.sh`（Mesa 离屏预渲染全部屏幕）加实机手工清单。对单人项目可以理解，但 5 个触到上游 server 内部的补丁没有任何自动回归检查——升级 pin 时风险集中。
- **供应链三重脆弱**。运行依赖越狱漏洞（Relapse 不活过重启、固件 14.00 已封堵，`docs/RESEARCH.md`）；构建依赖仓库外的 PS5_Vulkan 三仓库矩阵（README 自己标注需按其 pin 版本设置 `.deps/src`）；llama.cpp pin 在 `b11327`，上游演进越远补丁重放越贵。三者任何一个断裂，项目都无法原地工作。
- **原地卸载的显存泄漏未定位**。`docs/CONSOLE.md` 原文”Where the memory is held is still open”——重启式切换是绕过而非修复，若未来想支持常驻双模型或热切换，这是第一块挡路石。断网瞬间正在流式的回复仍会被切断（CHANGELOG 已承认）。

### 八、典型使用场景

- **客厅 LLM 一体机**：一台二手 PS5 + exFAT U 盘，成为家里所有设备的私有推理端点。模型、对话、文件全部不出局域网——这是任何云 API 都给不了的隐私属性，且电费之外的边际成本为零。
- **编码 Agent 的离线后端**：`docs/CLI.md` 实测 opencode（208 秒完成一次小编辑）、codex、Claude Code、aider 全部跑通。27B 的提示处理只有 35-50 tok/s，文档诚实建议 Agent 场景换 Gemma 4 E4B 等 4-9B 模型（快数倍）——一个知道自身硬件边界的推荐。
- **旧硬件的第二次生命**：16 GB GDDR6、448 GB/s 带宽的 RDNA 2 主机，二手价格远低于同等显存的 GPU。对想玩 2-bit 27B 量化实验的人，这是最便宜的整体方案之一。
- **PS5 homebrew 开发的参考实现**：就算不关心 LLM，`docs/RESEARCH.md` 的内存测绘、标题与载荷差异清单、12 条带 commit 出处的社区教训表，是这个生态里最系统的公开工程文档。PS5SX2、ProsperoAI 等项目的经验在这里被整合成了可执行的结论。
- **ggml-vulkan 移植性的极限测试**：RADV 无 cooperative matrix、无加速整数点积，矩阵乘法走 fp16 着色器（`docs/RESEARCH.md`）——在这种约束下 27B 仍到 20 tok/s，说明内存带宽（解码是带宽受限的）才是低比特量化的真正瓶颈，这个结论对任何 APU 推理都有参考价值。

### 九、实践指南

### 快速开始

```text
# 前提: 越狱 PS5 (固件 ≤ 13.60) + kstuff-lite + etaHEN + ShadowMountPlus 已加载
# 1. 从 releases 下载并校验 ps5lm-app-vX.Y.Z.zip (+ .sha256)
# 2. 解压后用任意 FTP 客户端 (ftpsrv, 端口 2121) 把 PPSA99581 目录
#    整体上传到主机的 /data/homebrew/, ShadowMountPlus 随即把它加到主屏幕
# 3. 主屏幕打开 PS5LM → Get models 页下载模型, 或拷 .gguf 到
#    /data/PS5LM/models 或 U 盘 PS5LM/models (exFAT)
# 4. 仪表盘显示 Ready 后, 局域网任意设备访问
open http://<PS5 IP>:8081        # WebUI 聊天
# 编码 Agent (例: Claude Code)
ANTHROPIC_BASE_URL=http://<PS5 IP>:8081 ANTHROPIC_AUTH_TOKEN=ps5lm \
ANTHROPIC_MODEL=ps5 claude
```

从 PC 遥控主机（无手柄调试）：`PS5_HOST=<IP> scripts/ps5lm-app.sh cycle|press r1|screenshot out.bmp`。

### 实际投入估算

| 阶段 | 时间 | 成本 | 产出 |
| --- | --- | --- | --- |
| 主机准备 | 2-4 小时 | 二手 PS5(无光驱版即可)+ U 盘 | 越狱环境 + 五个前置载荷 |
| 安装应用 | 15 分钟 | 0 | 主屏幕出现 PS5LM Plus |
| 下载首个模型 | 0.5-1.5 小时 | 1.9-9.2 GiB 流量 | Llama 3.2 3B(快)或 Qwen 27B(强) |
| 从源码构建 | 1-2 天 | 需 Linux + clang, 构建 PS5_Vulkan 矩阵 | 可改的 PPSA99581 标题目录 |

### 常见陷阱

- **固件版本是硬门槛**：Relapse 覆盖 7.00-13.60，14.00 已封堵；且不活过重启——每次开机要重新走漏洞加载载荷链。
- **模型选择要跟着用途走**：27B 的提示处理 35-50 tok/s，Agent 客户端自己的提示就有 10k-20k token，首答等几分钟是常态；聊天用 27B、Agent 用 4-9B 是文档明确背书的分工。
- **下载对内存敏感**：模型占着内存时下载大文件，应用会弹窗建议先卸载（重启）——这是特性不是 bug，队列会跨重启续跑。
- **别依赖原地卸载**：一切模型更换都走约 30 秒的重启；想在脚本里热切换模型的话，目前没有别的路径。

### 十、项目评价

PS5LM Plus 的核心价值主张可以压成一句话：**它证明了”推理引擎的可移植性”可以兑换成硬件上的自由**——llama.cpp 的全部架构与量化支持，通过 286 行补丁和一个进程身份的更换，落在了一台游戏机的 GPU 上。这个兑换比例（6,205 行应用代码撬动整个引擎生态）是项目最漂亮的地方。

它适合的人：拥有越狱 PS5 且重视数据本地化的技术爱好者、研究 APU/统一内存推理的工程师、以及任何 PS5 homebrew 开发者（哪怕只为读 `docs/RESEARCH.md`）。它不适合的人：想要开箱即用、稳定常驻服务的普通用户——越狱不活过重启、固件 14.00 已封堵漏洞、单模型单进程、30 秒切换，这些都是真实的使用成本。

往前看，项目的三个 open 问题决定天花板：显存泄漏的定位（决定能否热切换）、llama.cpp pin 的跟进节奏（决定引擎生态红利能吃多久）、以及主机固件与越狱的军备竞赛（决定项目的自然寿命）。但即便明天就停止演进，它已经留下了比应用本身更耐久的东西——一套把封闭主机当作可推理平台来对待的方法论，和一份每个数字都有出处的工程记录。这正是好的 homebrew 项目最后变成社区基础设施的方式。
