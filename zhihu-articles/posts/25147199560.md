最近半年在公司实习，由于计算资源紧张，实习生只能使用昇腾910B进行训练和开发。尽管910B的64G显存相比学校实验室里的3090、4090之流充裕了不少，但是迁移适配工作着实不是一件容易的事。这几天项目告一段落，终于有时间记录一下项目过程中适配昇腾NPU的踩坑记录。回想起来，每次遇到各种各样的问题和bug，在网上也很难查到对应的解决办法，有些问题最后还是求助于华为的运维工程师才得以解决。所以，希望这篇文章作为自己阶段性的工程经验总结之外，能够帮助到更多昇腾NPU的开发者们，一同助力国产计算生态的发展与进步。

下面的内容，我将首先简要介绍一下昇腾NPU的适配注意事项，接着分别以InternVL2和Qwen2-VL为例，完整的记录我的适配流程，最后，“疑难杂症”部分将会总结这段时间我遇到的所有问题以及解决方法

### 0.Quick Start：迁移到昇腾NPU需要做的

首先需要配置好昇腾NPU运行pytorch所需要的环境。在基本的pytorch环境配置之外，需要安装`torch_npu`库，注意库版本和`torch`、`torchvision`版本需要对应，一个例子如下

```text
pip install torchvision==0.16.0
pip install torch==2.1.0
pip install torch_npu==2.1.0 
```

此外，还需要安装[Ascend CANN Toolkit和Kernels](https://www.hiascend.com/developer/download/community/result?module=cann)，注意它们的版本和设备型号之间需要对应。可以参考[官方文档](https://www.hiascend.com/document/detail/zh/CANNCommunityEdition/80RC2alpha002/quickstart/quickstart/quickstart_18_0004.html)进行安装。这里参考[LLaMA-Factory](https://github.com/hiyouga/LLaMA-Factory/tree/main)给出Ascend 910B对应的CANN 8.0RC1安装命令

```text
# 请替换 URL 为 CANN 版本和设备型号对应的 URL
# 安装 CANN Toolkit
wget https://ascend-repo.obs.cn-east-2.myhuaweicloud.com/Milan-ASL/Milan-ASL%20V100R001C17SPC701/Ascend-cann-toolkit_8.0.RC1.alpha001_linux-"$(uname -i)".run
bash Ascend-cann-toolkit_8.0.RC1.alpha001_linux-"$(uname -i)".run --install

# 安装 CANN Kernels
wget https://ascend-repo.obs.cn-east-2.myhuaweicloud.com/Milan-ASL/Milan-ASL%20V100R001C17SPC701/Ascend-cann-kernels-910b_8.0.RC1.alpha001_linux.run
bash Ascend-cann-kernels-910b_8.0.RC1.alpha001_linux.run --install

# 设置环境变量
source /usr/local/Ascend/ascend-toolkit/set_env.sh
```

在训练代码的开头，加上以下两行命令，即可使用昇腾NPU作为device

```text
import torch_npu
from torch_npu.contrib import transfer_to_npu
```

由于昇腾NPU对`bfloat16`精度支持不完善，可以选用`float16`精度进行训练，只需将训练代码中的`dtype=torch.bfloat16`改成`dtype=torch.float16`

```text
# example
model = InternVLChatModel.from_pretrained(
            model_args.model_name_or_path, 
            torch_dtype=torch.float16, 
            config=config)  # torch.bfloat16 -> torch.float16 
```

并且在启动训练时设置`bf16=False`，`fp16=True`

```text
# example
torchrun \
  --nnodes=1 \
  --node_rank=0 \
  --master_addr=127.0.0.1 \
  --nproc_per_node=${GPUS} \
  --master_port=${MASTER_PORT} \
  internvl/train/internvl_chat_finetune.py \
...
  --bf16 False \  # set to False
  --fp16 True \  # set to True
```

在指定device时，使用`ASCEND_RT_VISIBLE_DEVICES`代替`CUDA_VISIBLE_DEVICES`，查看设备状态时使用`npu-smi info`代替`nvidia-smi`

### 1.实践1：Qwen2-VL系列

[Qwen2-VL](https://github.com/QwenLM/Qwen2.5-VL)系列支持使用[LLaMA-Factory](https://github.com/hiyouga/LLaMA-Factory/tree/main)进行训练，LLaMA-Factory库支持直接使用NPU启动训练和推理，官方的中文文档：[中文文档](https://github.com/hiyouga/LLaMA-Factory/blob/main/README_zh.md)

首先是环境配置，在我的实践中，发现按照文档中给出的昇腾NPU安装方法有些问题，总是无法解决依赖冲突问题，我的解决方案是按照默认方法安装环境，然后手动重新将对应版本的torch、torchvision和torch_npu安装上，最后安装deepspeed

```text
git clone --depth 1 https://github.com/hiyouga/LLaMA-Factory.git
cd LLaMA-Factory
pip install -e ".[torch,metrics]"

pip install torchvision==0.16  # 这个命令会自动安装torch==2.1.0
# pip install torch==2.1.0

pip install torch_npu==2.1.0
pip install deepspeed==0.15.4
```

LLaMA-Factory对NPU的支持较好，因此正常情况下，按照要求将数据配置好后就可以直接启动训练无需其他改动。

```text
FORCE_TORCHRUN=1 llamafactory-cli train examples/train_full/qwen2vl_full_sft.yaml
```

在这里提一下我遇到的两个小问题。

第一个问题是依赖安装不全问题，在环境配置时可能会出现一些依赖库未安装的error，按照error逐一补充安装即可。还有一些并未报error但是仍然未安装的依赖库，可以参考疑难杂症中的问题3。

第二个问题是llamafactory-cli有时会出现无法启动的问题，正常情况下，llamafactory-cli会在第一张计算卡上启动一个主进程，然后所有的计算卡上都会出现一个训练进程。但是我在实验过程中有时会发现主进程启动之后就卡住不动，终端上不再输出任何内容，每张计算卡的训练进程也不出现，整个程序完全卡住不动。我排查了很久也没有明白这个现象出现的原因是什么，解决办法是不使用llamafactory-cli启动训练，将yaml中的训练配置改写成一个sh脚本，直接使用torchrun启动训练。

### 2.实践2：InternVL2系列

InternVL2的开发者在GitHub issue上说明不会主动进行NPU适配，因此我只能自己摸索InternVL2的迁移适配工作。实际操作中，一个明显的感受是InternVL2的训练速度明显慢于使用LLaMA-Factory启动的Qwen2-VL，在同样的数据量下，Qwen2-VL-7B使用6.5h左右训练完毕，而InternVL2-8B需要16h，不知道是我的迁移问题还是其他的原因。

首先还是按照官方文档配置环境，不过涉及依赖库和版本控制问题，最好是手动修改一下`requirement.txt`文件，保证所有的依赖都被安装，同时版本也是对应的。在这里记录下我配置的一个小细节。首先是`bitsandbytes`库似乎不支持NPU，由于我的实验暂时不涉及量化，因此我直接删除了这个库。其次是`torch_npu`和`deepspeed`如果写在 `requirement.txt`内可能出现无法解决依赖冲突的问题，因此我在安装完`requirement.txt`内的依赖库后，再手动安装这两个库

```text
git clone https://github.com/OpenGVLab/InternVL.git
cd InternVL

pip install -r requirements/internvl_chat.txt
pip install torchvision==0.16  # 这个命令会自动安装torch==2.1.0
# pip install torch==2.1.0

pip install torch_npu==2.1.0
pip install deepspeed==0.15.4
```

环境安装完毕后需要对源代码进行一些修改以支持NPU训练

首先向`internvl_chat/internvl/train/internvl_chat_finetune.py` 中导入`torch_npu`模块

```text
import torch_npu
from torch_npu.contrib import transfer_to_npu
```

由于NPU不支持Flash Attention，如果需要使用Flash Attention相关特性，可以参考[官方文档](https://www.hiascend.com/document/detail/zh/Pytorch/60RC1/ptmoddevg/trainingmigrguide/performance_tuning_0027.html#ZH-CN_TOPIC_0000001889766765__section132951137183219)将Flash Attention的算子替换成Ascend FlashAttentionScore

```text
        causal = self.is_causal and query_length != 1

        #     max_seqlen_k=max_seqlen,
        #     dropout_p=dropout,
        #     softmax_scale=softmax_scale,
        #     causal=causal,
        # )
        head_num = query_states.shape[1]

                q=query_states,

                atten_mask=atten_mask_npu,
                scale=softmax_scale,
                keep_prob=1-dropout,
                input_layout="TND",
                actual_seq_qlen=tuple(cu_seqlens[1:].cpu().numpy().tolist()),
                actual_seq_kvlen=tuple(cu_seqlens[1:].cpu().numpy().tolist()),

        else:

                q=query_states,
```

### 3.疑难杂症

经过半年的使用和摸索，我遇到了各种各样的问题和bug，在此做一个完整的记录

```text

```

**2.fp16 training中OVERFLOW问题和CANN的bug**

910B对于`bfloat6`精度的支持并不好，需要手动将算子逐一替换。方便起见我的实验全程使用`float16`精度进行。使用`float16`训练时，deepspeed会使用梯度缩放机制以尽可能在计算中利用`float16`的精度， 缩放系数在deepspeed的ZeRO config文件中设置

```text
"fp16": {
    "enabled": "auto",
    "auto_cast": true,
    "loss_scale": 0,
    "initial_scale_power": 32,  # 缩放系数
    "loss_scale_window": 1000,  # 滑动窗口
    "hysteresis": 2,  # 滞后参数
    "min_loss_scale": 1  # 可接受的最小缩放系数
}
```

如果`initial_scale_power` 设置的过大，导致缩放后的梯度超过了`float16`可以表示的数值上限，就容易触发OVERFLOW warning

```text
OVERFLOW! Rank 0 Skipping step. Attempted loss scale: 32768, reducing to 16384 
```

deepspeed会自动减小缩放系数并应用于下一步的梯度计算。但是当前步的梯度会被丢弃，相当于这一个batch内的数据没有参与训练。因此为了保证数据的利用率，还是建议设置一个合理的缩放系数。

不过，在我的实验中遇到了一个更为诡异的现象曾让我百思不得其解。我的`initial_scale_power`无论设置成多少，在一段时间后，训练的梯度就开始爆炸增长，导致每一步都出现 OVERFLOW warning，直到程序将缩放系数降低到了最小值后出发了deepspeed的终止Error。

```text
Exception: Current loss scale already at minimum - cannot decrease scale anymore. Exiting run.
```

这个问题是发生在项目中途替换了一台服务器之后发生的，此前的代码和数据都没有变动。在排查了很久之后，终于确定了问题出在CANN Toolkit的版本上。此前正常运行的机器安装的CANN Toolkit版本是8.0RC1，而出现问题的机器安装的是7.0RC1，在我将CANN升级到8.0RC1后训练就恢复了正常，降低回7.0RC1又能稳定的复现这个bug。我猜测可能是7.0RC1存在某些数值计算上的bug，导致了这个问题。升级到新版的CANN Toolkit即可解决。

首先查看当前的CANN版本

```text

```

然后安装对应的CANN Toolkit和Kernels，这里直接参考LLaMA-Factory给出的相关命令


**3.坑人的依赖项问题**

有时驱动版本、torch、torchvision、deepspeed、CANN等版本都正确，在启动训练时还是会出现一个莫名其妙的NPU Error

```text
EH9999: Inner Error!
EH9999 [Init][Env]init env failed![FUNC:ReportInnerError][FILE:log_inner.cpp][LINE:145]
TraceBack (most recent call last):
build op model failed, result = 500001[FUNC:ReportInnerError][FILE:log_inner.cpp][LINE:145]
```

在上网查询一番后发现[这个issue](https://github.com/Ascend/pytorch/issues/7)记录了同样的问题，并给出了解决方案。这个问题主要是一些辅助库的依赖安装不全或者版本不对应导致的，需要检查下列依赖是否安装

```text
numpy>=1.19.2
decorator>=4.4.0
sympy>=1.5.1
cffi>=1.12.3
protobuf>=3.13.0
attrs，pyyaml，pathlib2，scipy，requests，psutil，absl-py
```

使用`pip show xxx`命令查看是否安装这些依赖库，并将缺失的库重新安装即可解决。

**4.时有时无的入参bug**

在启动训练的时候，模型的前向计算正常，在`loss.backward`时出现下面的Error：

```text
[Error]: Parameter verification failed.
        Check whether the input parameters of the interface are correct.
EE1001: The argument is invalid.Reason: Not need wait for event, flag=8!
        Solution: 1.Check the input parameter range of the function. 2.Check the function invocation relationship.
        TraceBack (most recent call last):
        Fail to recorder wait, retCode=0x7110001![FUNC:Wait][FILE:event.cc][LINE:1160]
        The argument is invalid.Reason: rtStreamWaitEvent execute failed, reason=[invalid value]
        stream wait event failed, runtime result = 107000[FUNC:ReportCallError][FILE:log_inner.cpp][LINE:161]
```

Error详情表述是入参问题，但是前向计算已经正常进行，说明参数实际上是没有问题的，这个问题困扰了我很久，网上也没有任何相关资料，最终在咨询了华为的运维工程师后，发现是deepspeed流同步的一个已知问题，一种解决方式是升级到最新的CANN版本，临时规避则可以通过修改deepspeed的源代码实现。

打开`deepspeed/utils/timer.py`，将第39行程序注释掉即可解决问题。

```text
class CudaEventTimer(object):

    def __init__(self, start_event: get_accelerator().Event, end_event: get_accelerator().Event):
        self.start_event = start_event
        self.end_event = end_event

    def get_elapsed_msec(self):
        # get_accelerator().current_stream().wait_event(self.end_event) 注释掉这一行代码
        self.end_event.synchronize()
        return self.start_event.elapsed_time(self.end_event)
```

奇怪的是，这个问题有时出现，有时又不出现。项目后期又更换了几次服务器，却再也没有遇到过这个问题了。
