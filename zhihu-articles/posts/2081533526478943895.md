### 一、一个图书馆的比喻

把一次对话的 KV cache 想成一位读者的**阅读笔记**：读完一段文字（prefill），笔记就写好了；之后每往下写一个字（decode），都要把整本笔记翻一遍。

- **显存**是阅览室的桌面：翻起来最快，但桌子很小。
- **PagedAttention**是把笔记从“一整本装订好的册子”改成“活页纸”：桌上放不下一整本没关系，一页一页地放，页之间不用挨着。
- **前缀缓存**是发现“这位读者的前 30 页笔记和上一位读者一模一样”（同一个系统提示词、同一轮对话的历史），直接把那 30 页借给他，不用重新读一遍原文。
- **分层卸载**是桌面放不下时，把暂时不翻的笔记挪到身后的书架（CPU 内存）、再挪到地下书库（SSD）。要用的时候再取回来——取回来的时间，得比重新读一遍原文短，否则不如重读。
- **分布式 KV 池**是整个图书馆的所有书架联网：任何一个阅览室需要的笔记，可以从别的阅览室的书架上调过来。
- **KV 感知路由**是前台分配阅览室时，优先把读者安排到**已经有他笔记**的那个阅览室。

下面每一节讲一层。

### 二、显存里怎么放：PagedAttention

### 2.1 问题：整本装订的浪费

早期推理系统给每个序列**预留一整块连续显存**，大小按最大可能长度算。结果是三种浪费：预留了但没用到的（一个 2K 的对话预留了 4K）、内部碎片（分配粒度太粗）、外部碎片（序列长短不一，释放后的空洞塞不进新序列）。vLLM 的论文测过，**这类系统浪费 60%~80% 的 KV 显存**。

### 2.2 解法：借操作系统的分页

PagedAttention 把 KV cache 切成固定大小的**块（block）**，vLLM 默认 16 个 token 一块，每个序列维护一张“块表”把逻辑位置映射到物理块——就是操作系统虚拟内存的页表。物理块不需要连续，序列增长时按需分配一块，结束时按块释放。**浪费只发生在每个序列的最后一块**，实测低于 4%。

机制上要多说一句代价：attention kernel 每读一个块都要先查块表拿物理地址，读取地址不再连续，vLLM 论文自己测的 PagedAttention kernel 比 FasterTransformer 的连续版本**慢 20%~26%**——这是用一点 kernel 效率换来 2~4 倍并发的交易，第四季第五篇讲地址生成时会再碰到。

以 Llama-3-70B 为例（每 token 320 KB）：一个 16-token 的块，所有层加起来约 5 MB，单层 64 KB。一张 80 GB 的卡在 TP=8 下放掉 17.5 GB 权重和约 5 GB 工作空间之后，剩 57 GB；TP=8 时每卡只存 1⁄8 的 KV 头，一个 8K 序列每卡 0.34 GB，**大约能放 170 个 8K 序列**——这个数就是 decode 的最大 batch，直接决定吞吐（第一季第六篇讲过这条因果链）。

分页还带来一个副产品：**写时复制的共享**。并行采样、beam search 里多个候选输出共享同一段 prompt 的块，只在分叉时才复制，vLLM 报告这能省最多 55% 的显存。这也是前缀缓存的基础。

### 三、怎么复用：前缀缓存

### 3.1 原理与两种数据结构

Attention 有个性质：**一个 token 的 K/V 只取决于它和它前面的 token**。所以两个请求只要前缀相同（从第 0 个 token 开始逐字相同），前缀部分的 KV 就完全相同，可以直接复用。

**块哈希链（vLLM 的自动前缀缓存）**：

```text
每个满块算一个哈希：h_i = hash(h_{i−1}, 本块 16 个 token 的 id，附加信息如 LoRA id)
   → 哈希天然包含了整个前缀，两个请求的第 i 块哈希相同 ⇔ 前 16i 个 token 完全相同
全局一张表：哈希 → 物理块 + 引用计数 + 最近访问时间
新请求：逐块算哈希、逐块查表；命中的块直接引用（引用计数 +1），从第一个未命中的块开始才真正跑 prefill
只有满块才能命中：最后不足 16 个 token 的部分总要重算
淘汰：引用计数为 0 的块按 LRU 逐出
```

**基数树（SGLang 的 RadixAttention）**：把所有已缓存序列的 token 串组织成一棵基数树，边上挂着对应的 KV 张量（仍然放在分页显存里），节点带引用计数；匹配是一次树上的最长前缀查找，淘汰是“先逐出最近最少使用的叶子”。它还多了一层**缓存感知调度**：等待队列不按先来先服务，而是按“已匹配的前缀最长者优先”排——论文证明这等价于对树做深度优先遍历，在显存够的前提下命中率最优。实测：八类负载（5-shot MMLU、20-shot HellaSwag、ReAct agent、思维树、JSON 解码、长短多轮对话、RAG、LLaVA）上**命中率 50%~99%，平均达到理论最优的 96%**，端到端吞吐比 vLLM / guidance 最高 6.4 倍、延迟最多降 3.7 倍（A10G / A100）。

### 3.2 命中在哪里发生

- **系统提示词**：同一个应用的所有请求共享几百到几千 token 的 system prompt。
- **多轮对话**：第 n 轮的 prompt = 前 n−1 轮的全部历史 + 新问题，前缀命中率天然很高。CachedAttention（ATC 2024）就是专门为这个场景把历史 KV 放到主机内存和磁盘上，逐层预取、与计算重叠，实测 **TTFT 最多降 87%、prefill 吞吐 7.8 倍、推理成本降 70%**。
- **Agent 工作流**：同一个任务反复带着同一份长文档、工具描述发请求。
- **少样本 / RAG 模板**：固定的示例段落。

### 3.3 生产系统里命中率是多少

三组公开数据：

| 系统 | 命中率 | 备注 |
| --- | --- | --- |
| DeepSeek（2025-02，一天） | 输入 6080 亿 token 中 56.3% 命中 | 磁盘上的上下文缓存，64 token 为单位 |
| Mooncake / Kimi（FAST 2025 的 trace） | 缓存 1,000 块时 30%，扩到 50,000 块 50%（LRU） | 平均输入 7,590 token、输出 182 token（输入输出比约 40 : 1，长上下文为主）；超过一半的块从未被复用，而少数块被访问上万次 |
| SGLang（论文基准） | 50%~99% | 取决于负载结构 |

Mooncake 那个“一半的块没人用、少数块被用上万次”是最重要的一条：**命中率不是均匀的，热点极端集中**——系统提示词那几十个块承担了大部分命中，这决定了淘汰策略（频率比 LRU 更合适）、路由（热点块要复制到多个实例）和落盘门槛（只有被命中过的块才值得写 SSD）。

### 3.4 它值多少钱

DeepSeek 在 2024 年 8 月把前缀缓存做成了 API 定价：**缓存命中的输入 token 价格是未命中的十分之一**，宣传的例子是 128K 的长 prompt 在高命中率下首 token 延迟从 13 秒降到 0.5 秒。价格差直接反映了成本差：命中的 token 不需要跑 prefill，只需要把 KV 从缓存里取出来。

这个定价还透露了一个工程事实：DeepSeek 的缓存是**放在磁盘上**的（“Context Caching on Disk”），以 64 token 为单位，几小时到几天后过期。也就是说前缀缓存不只是显存里的事——它已经是一个跨越显存、内存、磁盘的存储系统了。

### 四、装不下往哪搬：三级存储与盈亏平衡

### 4.1 三层的带宽和容量

| 层级 | 容量量级 | 到 GPU 的带宽量级 | 搬运机制 | 备注 |
| --- | --- | --- | --- | --- |
| GPU HBM | 80~288 GB / 卡 | 3.35 TB/s（本地） | — | 最快，最贵，被权重占掉一大块 |
| CPU DRAM | 1~2 TB / 节点 | PCIe 5.0 x16 标称 64 GB/s，实际约 50 GB/s | 固定页内存 + 异步拷贝，按块 | 能放几百个 8K 序列的 KV |
| 本地 NVMe SSD | 几十 TB / 节点 | 单盘约 7 GB/s，多盘并行 | GPUDirect Storage 或经 CPU | 容量大，但有写入寿命 |
| 远端（其他节点的 DRAM / SSD） | 集群级 | 一张 400G 网卡约 50 GB/s，8 张实测 190 GB/s（Mooncake Transfer Engine） | RDMA 直写显存 | 与其他流量争用 |

NVIDIA Dynamo 的 KVBM（KV Block Manager）就是这个结构：GPU → CPU → 本地磁盘 → 远端存储，按块粒度做写穿缓存，显存吃紧时自动往下卸，需要时往上取。为了保护 SSD 寿命，块要被命中至少一次（频率计数 ≥ 2）才允许从 CPU 落盘——正是 3.3 节那条“一半的块没人用”的对策。Mooncake（Kimi）则把整个集群的 CPU 内存和 SSD 组织成一个分布式 KV 池，靠 RDMA 传输引擎在节点之间搬。

### 4.2 一次命中请求的六步

把 Mooncake 论文里的调度算法和逐层加载合起来，一个前缀命中的请求是这样走的：

```text
① 分词后按块算前缀哈希链
② 对每个 prefill 实例：查它本地缓存里能匹配的前缀长度 → 估算 prefill 时间（按未命中的尾部长度）+ 排队时间 → 得到预期 TTFT
③ 选预期 TTFT 最短的实例；如果最长的前缀在别的节点上、而且“复制过来省的时间 > 传输时间”，就触发一次跨节点复制
④ 逐层加载：第 1 层的命中块从 CPU / 远端加载进显存的同时，GPU 已经开始算第 1 层未命中的尾部；第 2 层同理……
   加载被藏在计算后面，而且不需要为整段 KV 预留显存
⑤ 尾部 prefill 算完，新产生的块按写穿策略写回 CPU 池（成为别人的命中）
⑥ KV 逐层传给 decode 实例（第一季第六篇），decode 开始
```

第 ④ 步值得算一笔账。Llama-3-70B、8K prompt、8 × H100：全部重算约 290 ms；命中 50% 时，命中的 1.35 GB 从 CPU 以 50 GB/s 取回要 27 ms，尾部 4K token 重算 145 ms，两者重叠后 TTFT ≈ **145 ms**（串行也只有 172 ms）；命中 90% 时约 50 ms。**TTFT 因此是双峰的：命中的请求几十毫秒，未命中的几百毫秒，均值没有意义**（7.4 节）。

### 4.3 关键问题：取回来比重算快吗

搬出去容易，取回来才是问题。取回的时间要和**重新跑一遍 prefill** 比。还是 Llama-3-70B、8K prompt、8 × H100：

```text
KV 大小：            2.7 GB
重跑 prefill：       ≈ 290 ms（50% MFU）
从 CPU DRAM 取回：    2.7 GB / 50 GB/s ≈ 54 ms      ← 比重算快 5 倍
从单块 NVMe 取回：    2.7 GB / 7 GB/s ≈ 380 ms      ← 比重算还慢！
从远端节点取回：      2.7 GB / 50 GB/s ≈ 54 ms      ← 前提是那条 400G 链路没人挤；8 网卡并行 14 ms
```

这里有一个漂亮的推导。KV 大小和 prefill 时间都随 prompt 长度线性增长，两者相除得到一个**与 prompt 长度无关的盈亏平衡带宽**：

```text
取回值得，当且仅当  取回带宽 > 每 token KV 字节 × 有效算力 / (2 × 参数量)
```

把几种硬件和模型代进去（MFU 按 50%）：

| 模型 / 硬件 | 每 token KV | 有效算力（8 卡） | 盈亏平衡带宽 |
| --- | --- | --- | --- |
| Llama-3-70B，8 × H100 BF16 | 320 KB | 3.96 PFLOPS | 9.3 GB/s |
| Llama-3-70B，8 × H100 FP8 | 320 KB | 7.9 PFLOPS | 18.5 GB/s |
| Llama-3-70B，8 × H100 FP8，KV 也 FP8 | 160 KB | 7.9 PFLOPS | 9.3 GB/s |
| Llama-3-70B，8 × B200 FP8 | 320 KB | 18 PFLOPS | 42 GB/s |
| DeepSeek-V3（MLA，激活 37B），8 × H100 FP8 | 69 KB | 7.9 PFLOPS | 7.5 GB/s |

**任何总带宽低于盈亏平衡值的存储层，对这个模型、这套硬件来说，还不如重算。** 70B 在 H100 上是 9 GB/s：单块 NVMe 不达标，两块并行勉强够，CPU 内存和网络绰绰有余；换到 B200 上 FP8 就要 42 GB/s——**GPU 算力越强，SSD 层越难回本，连 PCIe 都开始吃紧**。反过来，MLA 把每 token KV 压到 69 KB，盈亏平衡点降到 7.5 GB/s，SSD 层又划算了；KV 量化到 FP8 的效果一样（同一行的 18.5 → 9.3）。CacheGen（SIGCOMM 2024）走得更远：把 KV 按分布特性编码成比特流，**体积再缩 3.5~4.3 倍**，从网络取回长上下文的总时延降 3.2~3.7 倍——本质上就是把盈亏平衡带宽再除以 4。

> **一句话**：分层卸载不是“有多少层用多少层”，每一层都要过盈亏平衡这一关，而这一关的位置由模型和硬件共同决定，压缩 KV 是把这一关往下挪的最直接手段。

### 4.4 搬运本身是流量

第一季第六篇讲 PD 分离时说过 KV 传输是一种新的网络流量。分层卸载把它扩大了：prefill 节点的 KV 要写到远端池，decode 节点要从池里取，命中的前缀要从池里调到当前实例……Mooncake 的 trace 平均一个请求 7,590 个 token，按 70B 的 320 KB 算就是 2.5 GB——每个请求 2.5 GB 的写入加上命中时的读取，在一个成熟的推理集群里，**KV 搬运可能是网络上最大的一股流量**，而且它和 EP 的 all-to-all、TP 的 AllReduce 共享同一张网。

### 五、请求该去哪个实例：KV 感知路由

有了跨实例的缓存，前台的分配逻辑就变了。传统负载均衡看的是“哪个实例最闲”；KV 感知路由看的是“哪个实例已经有这个请求的前缀”。

两者是冲突的：全部按前缀路由，热门系统提示词会把所有请求压到同一个实例上（3.3 节那些被访问上万次的块）；全部按负载路由，命中率归零。实际系统（SGLang 的 cache-aware router、Dynamo 的 KV router、Mooncake 的 4.2 节算法）都是**加权**：给每个实例算一个“预期前缀命中 token 数”和“当前负载 / 排队时间”，按预期 TTFT 选，并在收益超过传输代价时把热点前缀复制到多个实例。SGLang 在 v0.4 里报告的数字：缓存感知的负载均衡器把多实例部署的命中率提高 3.8 倍、吞吐提高 1.9 倍。

Mooncake 还测出了这个环上的一个陷阱：**过载时的早期拒绝**。只看当前负载拒绝请求，会因为 prefill 和 decode 两个池的时间差产生负载振荡（prefill 池拒了一批，decode 池随后空闲，再放一批，decode 池又爆）；解法是按“这批请求 prefill 完之后 decode 池会有多重”来预测性拒绝。它的过载实验：基线拒绝 4,183 个请求，早期拒绝 3,771 个，带预测的早期拒绝 3,589 个。

这一层再往前一步，就是 DeepSeek 那种“把缓存做进定价”：既然命中和未命中的成本差十倍，就让用户有动机把稳定的内容放在 prompt 前面。系统设计从后端一路影响到了 API 合同。

### 六、压 KV：从数据类型到模型结构

搬来搬去之前，还可以先让 KV 变小。按侵入程度从低到高：

| 手段 | 缩小倍数 | 代价 |
| --- | --- | --- |
| KV 量化到 FP8 | 2× | 精度损失很小，主流已默认 |
| KV 量化到 INT4 / 2-bit（KIVI 类，第四季第十六篇） | 4~8× | 需要按通道 / 按 token 的非对称量化，有精度风险 |
| 传输前编码（CacheGen） | 3.5~4.3× | 只对搬运有效，进显存前要解码 |
| GQA（减少 KV 头数） | 4~8× | 训练时就要定，Llama-3 已用 |
| MLA（低秩压缩 K/V） | 4~5×（相对 GQA） | 模型结构改变，DeepSeek 系列 |
| 跨层共享 KV | 2× 量级 | 模型结构改变，研究阶段较多 |
| 淘汰不重要的 token（H2O / StreamingLLM 类） | 视场景 | 有损，长文本任务风险 |

对存储系统来说，每缩小一倍，就是**所有层级的容量翻倍、所有搬运的带宽需求减半、盈亏平衡带宽减半**。这是为什么 MLA 这样的结构性改动，对推理系统的影响远大于它对模型精度的影响。

### 七、★ ESL 建模视角：把 KV 建成一个存储层级

前面都是铺垫，这一节是我真正想写的。

### 7.1 建模对象：一个多级缓存 + 一个决策函数

```text
层级 L_i：容量 C_i、到 GPU 的带宽 B_i、延迟 λ_i、（SSD）写入配额
块：      block_tokens × kv_bytes_per_token，带哈希链、引用计数、访问频率
请求：    prompt 的块序列 → 逐块查各层 → 命中前缀（到满块边界）+ 未命中尾部
决策：    对命中块：从层 i 取回（时间 = 块字节 / B_i + λ_i）还是重算（时间 = 块 token 数 × prefill 单价）
          逐层重叠：TTFT ≈ max(取回时间, 尾部 prefill 时间) + 未重叠部分
          对未命中：重算，并按写穿策略写入各层（落盘门槛：频率 ≥ 2）
淘汰：    LRU / 频率 / 时间衰减，按层独立；热点块可复制
```

这和 CPU 缓存层级的建模几乎同构，区别在于**“重算”是一个永远可用的兜底层**——它的“带宽”就是盈亏平衡带宽。任何层级只有在比重算快时才有意义，模型里应该把这个比较显式写出来，而不是假设“命中就一定更快”。

### 7.2 命中率不是参数，是工作负载的函数

最常见的错误是把命中率设成一个常数。命中率由三件事决定：

- **前缀共享结构**：系统提示词长度、多轮对话的轮数分布、Agent 任务的模板复用程度。这些要从真实 trace 里来（Mooncake 公开了它的 trace），或者用一个可参数化的生成器（比如“x% 的请求共享 y 个 token 的前缀”，再加一个 Zipf 型的热点分布来复现“一半的块没人用、少数块上万次”）。
- **容量与淘汰**：热数据集大小和各层容量的比值——1,000 块 30%、50,000 块 50% 那条曲线。
- **路由策略**：请求被分到哪个实例决定它能不能命中该实例的缓存。

所以命中率是仿真的**输出**，不是输入。输入是工作负载的结构和系统的容量、策略；校验点是 56.3%、30% → 50%、96% 最优比这几个数。

### 7.3 必须参数化的量

| 参数 | 含义 | 注意 |
| --- | --- | --- |
| kv_bytes_per_token | 每 token KV 字节 | 由模型结构与量化决定，是所有后续量的乘数 |
| block_tokens | 块大小 | 16 或 64；决定最后一块浪费与哈希粒度 |
| paged_kernel_penalty | 分页 kernel 的效率折扣 | 20%~26% |
| tier[i].{cap, bw, lat} | 各层容量、带宽、延迟 | 带宽要用实际可用值（PCIe 实际约 50 GB/s，不是标称；8 × 400G 实测 190 GB/s） |
| prefill_rate | 每 token 重算成本 | 由算力与 MFU 决定，给出盈亏平衡带宽（9.3 / 42 / 7.5 GB/s） |
| prefix_share_model、hotness_dist | 前缀共享结构与热点分布 | trace 驱动或参数化生成；Zipf |
| eviction_policy、disk_threshold | 各层淘汰策略与落盘门槛 | LRU / 频率 / 衰减；频率 ≥ 2 |
| router_policy、replicate_threshold | 前缀命中与负载的权重、热点复制 | 决定命中率与负载均衡的折中 |
| layerwise_overlap | 逐层加载与计算的重叠度 | 决定 TTFT 是 max 还是和 |
| xfer_contention | KV 搬运与其他流量的争用 | 接网络模型，不能用独占带宽 |
| ssd_write_budget | SSD 写入配额 | 寿命约束，决定落盘门槛 |
| admission_policy | 过载时的早期拒绝 / 预测 | 两池时间差引起的振荡 |

### 7.4 该盯的指标

- **各层命中率与“有效命中率”**：命中但取回比重算慢的块，不算有效命中。
- **TTFT 的双峰分布**：命中的请求（几十毫秒）和未命中的请求（几百毫秒）差一个量级，均值没有意义，要分开看。
- **HBM 中 KV 的占用率与最大 batch**：它决定 decode 吞吐；对照 170 个序列 / 卡。
- **KV 搬运流量占网络 / PCIe 总流量的比例**，以及它对其他流量（EP all-to-all、TP AllReduce）尾延迟的影响；对照每请求 2.5 GB。
- **块热度分布**：多少块从未复用、前 1% 的块承担多少命中；决定复制与落盘策略。
- **SSD 日写入量**：对照寿命预算。
- **路由的负载不均衡度与拒绝率**：前缀亲和带来的热点；过载时的振荡。

### 7.5 最常见的建模坑

1. **命中率当常数输入。** 它是工作负载结构、容量、淘汰和路由共同作用的输出，而且热点极端集中。
2. **命中即免费。** 取回要时间，要和重算比；SSD 层在高算力硬件上经常不值得，B200 上连 PCIe 都吃紧。
3. **搬运带宽用独占值。** KV 搬运和并行通信共享 PCIe 和网络，拥塞时“藏在计算后面”会失效。
4. **忽略块粒度与分页代价。** 部分命中只能到块边界；最后一块的浪费和哈希粒度都由块大小决定；分页 kernel 慢 20%~26%。
5. **取回和重算串行相加。** 逐层加载是重叠的，TTFT 是 max 而不是和；反过来不建重叠又会高估代价。
6. **路由和缓存分开建。** 路由决定命中，命中决定负载，负载又反过来影响路由——这是一个环，切开了就都不对；两池的时间差还会让环振荡。

### 八、小结

```text
KV cache 的一生：
  显存里：PagedAttention 活页化，浪费从 60%~80% 降到 <4%，块是一切的粒度；分页 kernel 慢 20%~26%；一张卡约 170 个 8K 序列
  复用：  块哈希链（只有满块能命中）/ 基数树（最长前缀优先调度，96% 最优）；系统提示词 / 多轮 / Agent 模板是命中来源
          生产命中率：DeepSeek 56.3%；Kimi 1,000 块 30% → 50,000 块 50%，一半的块没人用、少数块上万次；命中 token 价格 1/10
  卸载：  GPU → CPU → SSD → 远端，每层都要过“取回比重算快”这一关；六步：哈希 → 选实例 → 复制决策 → 逐层加载重叠 → 写穿 → 传 decode
          盈亏平衡带宽 = 每 token KV × 有效算力 / (2 × 参数量)：70B on 8×H100 9.3 GB/s、on B200 FP8 42 GB/s、MLA 7.5 GB/s
  路由：  前缀亲和 vs 负载均衡，按预期 TTFT 加权，热点复制；过载时预测性早期拒绝
  压缩：  FP8 / INT4 / CacheGen 3.5~4.3× / GQA / MLA，每缩一倍所有层级都受益

ESL 建模：多级缓存 + “重算”兜底层 + 决策函数 + 逐层重叠
  命中率是输出不是输入；TTFT 看双峰不看均值；搬运流量要进网络模型；路由和缓存是一个环
```
