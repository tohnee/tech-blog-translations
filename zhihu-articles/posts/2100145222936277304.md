“没有银弹架构，只有任务与架构的匹配。默认单循环，按需拆分。”

前言

开头那句不是引用，是我把这一年做的东西压了又压，最后剩下的一句话。写下来是为了提醒自己，别一上手就把架构往复杂里画。

如果用一句话概括过去一年智能体领域的变化，我会说，竞争重心从“谁的模型更聪明”，转向了“谁能把智能体真正装进业务流程”。

Anthropic 在《How we built our multi-agent research system》里披露，Deep Research 用的是“指挥官 + 工人”的多智能体结构，内部评测比单智能体高 90.2%。但只过了几个月，2026 年 10 月 22 日，同一个团队又发了《When to fold subagents into your main agent loop》，结论几乎反过来：很多场景下带 Skills 的单智能体质量更好，成本和延迟都更低，有客户把多智能体换回单循环，速度快了差不多一倍。

两个相反的结论摆在一起，才是这件事真实的形状。架构本身没有高下，只有和任务配不配。

我自己的体会是从一个很小的项目里长出来的。前段时间我在做校园网运维的智能体，最早那版很简单，一个提示词加四五个工具，跑起来效果还不错，同事看了也觉得能用。可真要交给值班的人长期用，问题就一个一个冒出来了：它有时候查到一半就说“已处理完成”；有时候把用户工单里的描述当成指令去执行；会话一长就忘了前面确认过的条件；出了错也说不清是错在哪一步。

我把这些问题摊开看了一遍，发现几乎没有一个是“模型不够聪明”造成的。它们都落在模型之外的那一层：上下文怎么给、工具怎么划、状态放在哪里、出错怎么兜、改动怎么验证。这一层东西，业界现在习惯叫它 harness。

所以这篇不谈智能体能干什么，谈它的架构该怎么搭。要回答三个问题：一个智能体在一次对话里到底做了什么，该选哪种形态，一个组织从 0 到 1 该怎么排工序。

前面几篇讲了大模型的基础概念、提示工程、RAG、Function Calling 和 MCP，那些都属于“单个能力”。这篇往上抬一层，讲这些能力怎么装成一套系统。信通院魏凯在今年 WAIC 上讲过一句我印象很深的话：个人提效不等于组织提效，企业不能零散地引入智能体，得有明确目标、建设路线图、评价体系和持续迭代机制。这句话说的是组织，其实也是架构，零散地加功能，永远长不成系统。

一、智能体在一次对话里做了什么

关于智能体的定义，我在前面写过：基于语言大模型的智能体，是通过计划（Planning）、记忆（Memory）、感知（Sensor）、执行（Tools）等模块来执行复杂任务的大模型应用程序，大模型在其中充当主控制器，也就是“大脑”。

放到工程上，我习惯把它压成一行：

**智能体 = 模型 + 上下文 + 工具 + 一个循环 + 一层环境。**

模型负责判断；上下文是它此刻能看到的全部信息；工具是它作用于外部世界的唯一手段；循环让它能连续行动；环境负责在它跑偏的时候刹车、在它出错的时候兜底。

下面这张图是我平时用的一张拆解，把“用户提一个问题”到“拿到答案”分成了 17 步。后面说的这些工程问题，基本都能在这张图上找到对应的位置。

图 1 一次完整对话的 17 个步骤

17 步看着复杂，工程上其实只有五个环节：

1.**意图与计划**（04—06）：模型弄清要做什么，产出可执行的计划。

2.**上下文装配**（03、15）：这一步最关键，它决定了模型“知道什么”。

3.**工具执行**（07—14）：生成参数、通过 MCP 发现工具、调用、结果回传。

4.**结果收敛**（16）：把工具结果和历史拼成答案。

5.**回写与记忆**（17）：这次的结论要不要留下、怎么留。

我见过的项目，出问题最多的是第 2 步和第 3 步，第 4 步反而最少。喂错了东西，模型再强也只能胡说；没兜住异常，模型就会编一个看起来合理的答案补上。这两个都是工程问题，不是模型问题。

这里还有一笔账值得算清楚：单步决策的正确率是 95%，走 20 步下来，整条链路的成功率只剩 35%（0.95 的 20 次方）。所以架构设计有一半的工作量，其实是在给错误兜底，让某一步偏了不至于把整件事带偏。

Anthropic 在 10 月的一篇工程总结里，把单上下文智能体的失败归成三类，我觉得比很多教材讲得都准：

-**偷懒**（Agentic laziness）：让它审 50 条记录，它审到第 35 条就宣布“全部完成”。

-**自我偏好**（Self-preference bias）：让它给自己的输出打分，它总是偏宽松。

-**目标漂移**（Goal drift）：长任务反复压缩上下文之后，“不要做某件事”这类约束会悄悄消失。

注：这三个词是他们的原话，我按字面直译。国内一些文章译成“懒惰性”“自偏好偏差”，意思是一样的。

这三类问题都不是靠换模型能解决的。第一类缺的是完成度校验，第二类缺的是独立评审，第三类缺的是约束持久化。都是 harness 该干的事。

所以我的看法是：**模型决定能力下限，harness 决定系统上限。**换一个更强的模型，能把某个任务从 70 分提到 78 分；但把审批、预算、幂等、回放补齐，能把它从“不敢用”变成“敢用”。这两件事的收益不在一个量级上，只是后者不显眼，写不进汇报材料。

二、五种形态：先问需要多高的自主性

工程上要回答的第一个问题，其实不是选哪个框架，而是这件事需要多高的自主性。按自主性从低到高，大致是五种形态，工作方式、代价和可控度见图 2。下面把场景和优劣摆出来对照：

图 2 五种形态：自主性、代价与可控度

1.**固定工作流**：适合分类、抽取、批处理这类活。可预测、便宜、出错好定位，缺点是流程一变就要改代码。

2.**工具型单循环**：适合客服问答、检索分析。灵活，能应对没预演过的情况，但容易跑偏、token 也容易失控。

3.**规划-执行**：适合多步办理、报告生成。过程可审计，单步可以重跑，代价是计划一错就全错。

4.**评审-优化**：适合代码审查、合规校验。质量上限能明显提高，前提是评审方不能是同一个模型。

5.**多智能体**：适合广度研究、并行探索。可并行、可隔离上下文，但协调开销常常压过收益。

图 2 里那两档代价来自 Anthropic 公开的数据：单循环大约是一次普通对话的 4 倍 token，多智能体系统大约 15 倍。中间两档是我的估计区间，它们本质上是单循环上又叠了额外的思考轮次，所以落在 4 倍到 15 倍之间。

还有一件事被低估得厉害：**上下文是预算，不是容量。**Anthropic 那篇讲上下文工程的文章说得很清楚，token 越多，模型准确召回的能力反而越差，他们把这个现象叫 context rot（上下文腐烂）。100 万 token 的窗口不是让你把 100 万 token 都塞进去，而是让你有空间做取舍。这一点我在做知识库问答时体会很深，塞满文档反而答得更差，删到三五个片段、把冲突的先挑出来，正确率明显好转。

所以选型的顺序应该是这样：先问这件事需不需要模型自己判断下一步，不需要就写死工作流；需要就用单循环；只有当单循环反复在同一个地方失败时，才考虑加角色。反过来的做法很常见，一上手就画组织图，最后发现大部分环节根本不需要判断。Anthropic 在《Building Effective Agents》里有句话我常引用：自主性是为不确定性支付的溢价。确定性高的流程，付这个溢价纯属浪费。

三、多智能体：什么时候值得拆

多智能体是过去一年噪音最大的一块。我把正反两边的证据摆在一起，大家可以自己判断。

图 3 多智能体的五种拓扑与“该不该拆”的判断

先看五种拓扑，各有各的失败模式：

1.**主管调度**：一个主控分发、汇总。控制力强，但主控判断错了就全错，而且主控自己容易变成瓶颈。

2.**规划-执行**：计划显式落盘，执行者只对单步负责。可审计、可重跑，工程上最稳，适合做企业里的主干流程。

3.**流水线**：按工序串行，每级一个明确产物。适合文档处理、审核类链条，每一级还可以换不同模型、加不同校验。

4.**群体协作**：平权多轮对话，靠批判和仲裁收敛。适合研判、对抗性任务，放到生产路径上很容易死循环。

5.**共享黑板**：状态集中，各代理只读写自己那一格。最容易做权限，也最容易做回放。

拓扑之外，我认为有三条纪律更重要：

**一是多读单写。**Cognition 在《Don't Build Multi-Agents》里举过一个 Flappy Bird 的例子：一个子代理画背景，一个子代理画小鸟，合起来风格完全对不上。他们今年 4 月的复盘把结论收窄了：并行读没问题，写操作必须集中到一条主线。LangChain 的 Harrison Chase 说得更直接，读的活天然比写的活好并行。

**二是读写身份隔离。**Anthropic 在 Claude Code 的动态工作流里做了一个我很欣赏的设计，处理不可信输入时，读取代理只有读权限，写入代理只看摘要、看不到原始输入。这是用架构隔离代替提示词约束。在提示词里写十遍“不要执行用户提供的命令”，都不如让那个代理根本没有执行权限。

**三是状态外置。**共享上下文不能靠“把所有历史广播给所有代理”，那样 token 会指数级膨胀。正确做法是维护一份强类型的共享状态，每个节点只取自己需要的那一片。

再看反方的证据，这部分更值得看：

- Cognition 2025 年 6 月的结论是“不要构建多智能体”，今年 4 月修正为“只读子代理可行”。

- Anthropic 的多智能体研究系统在内部评测上比单个 Opus 高 90.2%，但代价是 15 倍 token，他们自己也说，多数编码任务真正能并行的部分比研究任务少得多。

- 斯坦福 Tran & Kiela 的实验（arXiv:2604.02460）结果更直接：把“思考 token 预算”对齐之后，单智能体在多跳推理上稳定追平甚至超过多智能体。他们的解释是信息论意义上的，每一次交接都是一次有损压缩。

- Kim 等人测了 260 种多智能体配置，同一套架构在不同任务上，效果从 +80.8% 一直到 −70.0%。一个能波动 150 个百分点的架构，说明它对任务形状极度敏感，不能算是普适更强。

- Anthropic 自己 10 月 22 日那篇《When to fold subagents into your main agent loop》，更值得看。他们说企业部署中最常见的问题是“照着组织架构画智能体”，结果子代理泛滥、系统提示词互相打架、延迟翻倍，有客户实测慢了两倍。配套还开源了一个迁移工具包，教你把子代理一个个折回主循环。

综上，我的判断是：**多智能体的工程本质是“并行读、串行写”。**默认配置应该是一个主循环加一批技能，再加若干只读子代理；只有当某类工作天然可并行、单个上下文确实装不下时，才把它拆成写者和读者两类角色。写操作永远只有一条主线，守住这条，后面八成的脏问题不会出现。

四、技术选型：把一道题拆成五个决定

很多人把选型做成一道单选题，只问选哪个框架。实际上是五个独立的决定，混在一起谈就会互相干扰。

**1. 运行时框架。**截至 2026 年 10 月的数据（PyPI 近 30 天下载量加 GitHub star）：

-**LangGraph**（44.8M 下载 / 43k star）：需要持久化状态、断点续跑、人工审批的场合。

-**Strands**（37.1M / 8.8k）：在 Bedrock 上跑的时候用。

-**Claude Agent SDK**（29.8M / 8.2k）：想把 Claude Code 那套 harness 搬进自己的应用。

-**OpenAI Agents SDK**（12.4M / 30k）：轻量，handoff 和 guardrails 做得清爽，不过还是 0.x。

-**Google ADK**（10.1M / 21.8k）：Gemini 加 Vertex 这条路。

-**CrewAI**（2.4M / 59.5k）：角色化“班组”，起步快，深水区要自己补。

-**Microsoft Agent Framework**（0.19M / 14k）：.NET 和 Azure 技术栈。

这里要提醒两件事。AutoGen 已经进入维护模式，star 有 6 万多，但不再加新功能，新项目不要从它开始；Flowise 今年 8 月归档，OpenAI 的 Agent Builder 也宣布 11 月底关停。这一层的选型要看活跃度，不能只看 star 数。我的经验是看最近三个月的 release 频率和 issue 响应速度，比看总星数靠谱。

**2. 工具协议。**MCP 事实上已经统一了“智能体怎么连工具”，2026 年 7 月的规范去掉了握手和 session，走向无状态。A2A 在 3 月发布 v1.0，带签名的 Agent Card，8 月并入 Linux 基金会下的 Agentic AI Foundation，和 MCP、AGENTS.md 放在同一个治理体系里。

这句话落到工程上很实际：MCP 用来接工具，A2A 用来跨组织委派，AGENTS.md 用来约束代码仓库里的行为，三件事不要混着谈。绝大多数企业今年还用不到 A2A，但采购时应该要求供应商支持 MCP。

**3. 记忆。**今年一个明显的变化是记忆从“功能”变成了“基建”：Memory / Context 类目在 Agentic AI 融资中的占比从约 8% 涨到约 17%，增速排在第一位。工程上的共识也在收敛，不是存得越多越好，而是分层沉淀、按预算召回。L0 存原始对话，L1 存结构化事实，L2 存场景任务，L3 存用户画像，平时只把 L2 和 L3 放进上下文，需要细节再回捞 L1 和 L0。

**4. 执行环境。**只要模型能写代码或者调 shell，就必须有沙箱。这一条没什么可讨论的，代码执行、文件读写、外部 API 调用，都要在隔离环境里跑，并且带超时和配额。

**5. 可观测与评测。**最低要求是“能回放”，每一步的输入、输出、模型版本、检索版本都要留痕。不能回放的系统，出了问题只能靠猜。

最后补一条最直接的成本手段：**模型路由**。把分类、抽取、格式化这类判断交给便宜的小模型，把规划、疑难判断、最终成文交给旗舰模型，同一条链路上通常能省掉一半以上的钱，效果损失远小于换一个更弱的单一模型。Anthropic 的研究系统就是主代理用 Opus、子代理用 Sonnet 的搭配。

比路由更靠前的其实是预算本身。智能体跑飞刷爆账单，今年已经变成一种新的事故类型，我见过半夜被叫起来停服务的。预算熔断应该做成架构里的一个组件，而不是运维临时打补丁，单次任务的 token 上限、单日花费上限、连续失败自动停，这三条是底线。

五、组织级智能体：六层架构与三方分工

把上面这些零件装起来，我给的参考架构是六层，外面再横一层治理。

图 4 组织级智能体的六层参考架构

分层本身的道理很简单：**下层稳定，上层灵活。**模型会换、框架会换，但“一个业务动作一个工具”和“每一步可回放”这两件事不该跟着换。

真正决定这套架构能不能在组织里活下来的，是五条纪律：

1.**一个业务动作一个工具。**粒度太粗，模型没有机会在中间做判断；太细，多步规划的错误率会指数上升。判据是能不能被独立授权：创建工单、发起退款、更新客户资料，各算一个工具；查询用户信息这类读操作可以合并。

2.**状态放外部，上下文只放该知道的。**会话一长就失忆的项目，几乎都是把状态放在了上下文窗口里。正确做法是业务实体状态从数据库读，最近几轮放原文，早期历史定期做摘要。

3.**硬约束下沉到工具和运行时。**金额上限、审批门槛、可用工具范围，全部写成代码。写进提示词的约束，在长任务里迟早会被压缩掉，这就是前面说的目标漂移。

4.**读写分离，写操作串行。**理由见上一节。

5.**一切可回放。**trace 不是调试工具，是合规证据。审计要的不是“模型说它做了”，而是“第 7 步用了 A 的身份调用了接口 B，返回 C”。

这五条落地时有三个东西值得单独建起来：

-**Agent 注册表**：每个 Agent 有 owner、有版本、有可用工具清单、有评测基线。没有注册表，半年之后你不会知道组织里跑着多少个 Agent。

-**技能库**：把“一个团队怎么做这件事”写成可加载的技能目录，而不是塞进系统提示词。Anthropic 内部用几百个技能支撑这件事，他们的结论有点反直觉：校验类技能的投入产出比最高，值得让一个工程师花整周去打磨。

-**评测门禁**：每次改动，哪怕只改一句提示词，也要跑一遍黄金集。这是概率系统唯一可用的回归测试手段。

分工比架构更容易翻车。我见过最稳的一种切法，是三拨人各管一段：

-**平台团队**管编排层和治理层，负责运行时、权限、审计、评测工具链。他们不写业务逻辑，只保证别人能安全地跑。

-**业务团队**管能力层和技能库，把本部门的动作封装成工具，把本领域的做法写成技能。他们最懂边界条件，也最能写出高质量的 gotchas。

-**治理与安全**管审批矩阵和合规，决定哪些动作必须人工确认、哪些数据不能出域。这件事如果放在项目组里做，一定会被进度压力稀释掉。

三拨人之间用契约对接：工具签名、技能描述、评测基线。契约稳定了，换模型、换框架都不会牵动组织。

六、AI Native 的六步走法与五个坑

最后说工序。项目失败往往不是技术不行，而是顺序错了。

图 5 AI Native 的六步走法与过关条件

**第一步，选场景。**高频、结果可判定、有人愿意为结果负责，三个条件缺一个，后面都会很痛苦。第三个条件最容易被忽略，没有业务方认领的场景，做完没人用，也推不动。

**第二步，立评测。**先攒 10 条黄金用例，再扩到 100 至 200 条。这里有一条来自客服智能体复盘的经验：回归集必须来自真实语料，开发阶段自造问题的比例不要超过 30%，否则分数很好看，一上灰度就崩。

**第三步，跑单循环。**工具加技能加最小可用的记忆。这一步的目标不是惊艳，是端到端跑通，并拿到人工干预率的基线。

**第四步，加固 harness。**预算、审批、沙箱、幂等、熔断。这是能不能上生产的分水岭，也是最多团队跳过的一步。

**第五步，沉淀资产。**记忆分层、技能入库、工具可复用。衡量标准很硬：换一个场景，能不能复用 40% 以上的能力。

**第六步，扩到组织。**注册表、只读子代理、跨系统协作。到这一步，多智能体才真正有它的位置。

如果不想从零写，这几个仓库值得按顺序读一遍，比看十篇架构文章都管用：

-**anthropics/single-agent-loop-kit**：单循环的极简正确实现，还附了把子代理折回主循环的三步迁移法。

-**langchain-ai/deepagents**：规划、上下文卸载到文件系统、子代理派生的分层写法，上下文管理这块做得最细。

-**openai/openai-agents-python**：handoff、guardrails、tracing 三个原语，代码量不大，适合拿来先读懂结构。

-**langgraph**：有状态图、断点续跑、时间旅行调试，做生产可靠性可以对着它抄。

-**microsoft/agent-framework**：AutoGen 归档之后官方给的后继，.NET 和 Azure 栈就用它。

-**OpenClaw**：个人常驻 Agent 的渠道接入和技能生态，一个人做出来的样本，值得看看它怎么组织技能。

顺带记五个几乎都会踩的坑，按我遇到的频率排序：

1.**工具粒度设计不当**，Agent 表现忽好忽坏，很难定位。

2.**状态只放在上下文里**，会话一长就失忆。

3.**没有评测集**，换模型、改提示词全靠体感，准确率掉了两周之后才发现。

4.**审批点失衡**，要么每步都要点确认，Agent 形同虚设，要么高危操作没人把关。建议做一张动作风险矩阵：只读自动放行，常规写放行但记 trace，涉及资金、权限、外发消息的强制人审。

5.**把生成延迟当成网络卡顿**，用户疯狂重试，同一个任务被执行好几遍。要做过程可视化和幂等键。用户对系统的信任，很多时候不取决于模型多聪明，而取决于他觉不觉得可控。

还有一个具体的工程细节可以直接抄：**工具失败时禁止幻觉补偿。**所有工具调用都要捕获异常，把“工具不可用”作为一条状态回写上下文，并在系统提示里写死兜底话术。大模型宁可给一个看起来合理的答案，也不愿说“我不知道”。这一条不写死，投诉迟早会来。

七、接下来的趋势，我的四个判断

第一，**harness 会成为核心资产，模型退化成可替换件。**Anthropic 已经明确提出“把大脑和手解耦”，也有文章直白地说，harness 里大量代码其实是在弥补当前模型的缺陷，而模型在进步，昨天的补丁会变成明天的负担。所以架构上要让接口稳定、实现可换。

第二，**记忆会成为继算力、模型之后的第三块基建。**分层、可审计、可控召回的记忆系统，会比“更大的上下文窗口”更早成为企业的刚需。

第三，**竞争重心从“造”转向“管”。**身份、权限、审计、评测、成本，这些词过去属于 IT 治理，现在正在变成智能体的核心架构问题。IDC 预测到 2027 年，45% 的企业要同时管理跨渠道、跨应用、跨供应商的多个智能体。

第四，**组织形式会先变，技术架构后变。**Gartner 预测到 2030 年，80% 的企业会通过 AI 原生开发平台把大软件团队改造成更小的敏捷团队。真正难的从来不是模型，而是新流程归谁负责、决策权怎么切。

写在最后

绕了一圈，智能体架构设计的本质其实很朴素：在模型的不确定性和业务的确定性之间，搭一层工程化的翻译。这一层的原料只有三样，给模型看什么、让模型碰什么、模型错了怎么办。

模型能力每半年翻一倍，这三层工程的价值不降反升，因为能力越强，越需要精确的调度、隔离和验收。2026 年的赢家不是用了最多 Agent 的人，而是用最少的架构复杂度换到最高任务成功率的人。这句话我信，也正在拿它改自己的项目。

Takeaways

1. 智能体 = 模型 + 上下文 + 工具 + 一个循环 + 一层环境。前三样决定它能做什么，后两样决定它能不能被信任。

2. 模型决定能力下限，harness 决定系统上限。换模型提升的是分数，补 harness 改变的是敢不敢用。

3. 上下文是预算，不是容量。窗口越大，越要克制。

4. 多智能体的工程本质是并行读、串行写。默认配置是主循环加技能加只读子代理。

5. 组织级的分水岭不在多智能体，而在记忆和治理：能不能回放、能不能评测、能不能约束。
