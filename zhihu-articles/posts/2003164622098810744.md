## **IB报文结构与Opcode 分类**

理解路由机制需要理解报文结构。InfiniBand 报文采用分层设计，每一层都有明确的职责。

### **报文的分层结构**

一个完整的 InfiniBand 报文由四层组成：

**链路层（Link Layer）**：处理同一子网内的转发。LRH（Local Route Header）包含 VL、DLID、SLID 等字段，是交换机唯一关心的头部。

**网络层（Network Layer）**：处理跨子网路由。GRH（Global Route Header）包含 GID（Global Identifier），用于在不同子网之间路由。这一层在单一子网内通常不使用。

**传输层（Transport Layer）**：定义端到端的传输语义。BTH（Base Transport Header）包含 Opcode、PSN（Packet Sequence Number）、QPN（Queue Pair Number）等字段。

**扩展层**：包括 Payload 和 ICRC（Infiniband CRC），用于数据载荷和错误检测。

这种分层设计的好处是：**每一层只关心自己的职责**。交换机只解析 LRH，端点解析 BTH，各司其职，互不干扰。

### **Opcode 的角色定位**

Opcode 是 BTH 中最重要的字段之一，长度为 8 位。它定义了报文的**传输层语义**，告诉接收方"这个报文要做什么"。

Opcode 的位布局很有讲究：

- 高 4 位定义**服务类型**（RC、UC、UD、RD 等）
- 低 4 位定义**具体操作**（Send、Write、Read、Atomic 等）

**为什么 Opcode 不参与路由决策？**

因为路由是网络层的功能，而 Opcode 是传输层的概念。交换机不应该关心报文是 RDMA Write 还是 RDMA Read——它只需要把报文送到目的地。

**但 Opcode 影响"路由结果的使用方式"**。

以 RDMA Read 为例：发送方发起 Read 请求，接收方需要返回数据。请求报文和响应报文的路由路径可能不同（取决于网络拓扑和路由算法），但接收方必须能够正确区分这两种报文。Opcode 提供了这种区分能力。

不同 Opcode 类型的报文在交换芯片中受到的**处理优先级**也可能不同。例如，管理类报文（通常是 Vendor Specific 或 Subnet Administration 类）通常有最高优先级，以确保网络的可管理性。

### **各类型 Opcode 的结构共性**

虽然不同 Opcode 的具体含义不同，但它们共享相同的头部结构：

- 8 位 Opcode
- 8 位 Solicited Event 标志
- 8 位 Mig 标志
- 24 位 PSN（Packet Sequence Number）
- 24 位 QPN（Queue Pair Number）

这种结构一致性带来的好处是：**硬件可以用统一的流水线处理所有类型的报文**。解码 Opcode 的逻辑是共享的，不同的只是流水线后端的处理逻辑。

## **IB 报文详细格式**

### **直接参与路由的字段**

**DLID（Destination LID）**：这是路由决策的核心输入。交换机用 DLID 索引 LFT，得到输出端口。DLID 的长度为 16 位，范围是 1 到 0xBFFF。

**SLID（Source LID）**：源 LID。在大多数路由场景中，SLID 不参与转发决策，但可用于反向路径验证或流量工程。

**LNH（Local Network Header）**：2 位字段，告诉交换机如何解释剩余的头部：

- `00`：使用本地路由（LRH + BTH）
- `01`：使用全局路由（LRH + GRH + BTH）
- `1x`：保留

### **间接影响路径选择的字段**

**SL（Service Level）**：4 位字段，定义流量类别。SL 本身不参与路由决策，但 SM 在计算路径时可以将 SL 作为约束条件。不同的 SL 可以映射到不同的 VL（Virtual Lane），实现 QoS 隔离。

**VL（Virtual Lane）**：4 位字段，定义虚拟 Lane。VL 主要用于流量控制而非路由，但不同 VL 的流量在交换机内部可能受到不同的调度待遇。某些高优先级 VL（如 VL15）通常保留给管理流量。

### **不参与路由但影响流控的字段**

**P_Key（Partition Key）**：16 位字段，定义报文所属的分区。P_Key 主要用于访问控制和分区隔离，与路由决策无关。

**QPN（Queue Pair Number）**：24 位字段，标识通信端点。QPN 在端点处用于多路分解到正确的队列对，不参与网络转发。

**PSN（Packet Sequence Number）**：24 位字段，用于可靠传输中的顺序控制。与路由无关，但在可靠服务类型（RC、RD）中至关重要。

## **IB报文的路由方式**

InfiniBand 的路由机制看似复杂，但归根结底只做一件事：**根据报文头部的某个字段，查表得到输出端口**。这个字段通常是 DLID（Destination LID），这张表就是 LFT（Linear Forwarding Table）。

### **基于 LID 的路由（LID-Based Routing）**

这是 InfiniBand 最基础、也最常用的路由方式。

每个 InfiniBand 端口都被分配一个 LID（Local Identifier），范围是 1 到 0xBFFF。LID 的分配遵循网络的物理拓扑：SM（Subnet Manager）在初始化网络时，会根据交换机的连接关系计算每个端口的 LID。

**路由过程非常直接**：

1. 报文到达交换机
2. 交换机读取报文的 DLID 字段
3. 交换机用 DLID 索引 LFT（Linear Forwarding Table）
4. LFT 返回输出端口
5. 交换机将报文转发到该端口

为什么这样做是高效的？因为 LFT 就是一个简单的数组，查表操作是 O(1) 的。没有哈希碰撞的风险，没有最长前缀匹配的复杂性，没有任何需要学习的动态状态。

**代价是什么？** 灵活性。LID 在网络初始化时就已确定，报文走哪条路径是预先计算好的，不能根据实时流量状况动态调整。这种"静态路由"在流量模式稳定的 HPC 环境中是优点，但在流量模式多变的 AI 环境中可能成为瓶颈。

### **基于路径的路由与多路径支持**

InfiniBand 标准本身支持多路径路由，但在实践中用得不多。

**SL（Service Level）** 字段可以用于区分不同的流量类别。每个 SL 可以映射到不同的 VL（Virtual Lane），不同 VL 使用不同的缓冲区。这在某种程度上实现了 QoS 隔离。

**多路径转发的限制**在于：InfiniBand 的路由表是每个端口一份，而不是全局共享的。这意味着从不同入口进入的流量，即使目的地相同，走的路径也可能不同。这在某些场景下会导致路径不一致的问题。

相比之下，以太网的 ECMP（Equal-Cost Multi-Path）可以在整个网络范围内做负载均衡，代价是需要更复杂的硬件支持。InfiniBand 选择简化硬件，代价是牺牲一定的负载均衡能力。

**Up-Down 算法**是 InfiniBand 特有的路由算法。它的核心思想是：选择网络中的一个交换机作为根，然后为每条边分配方向（"上"或"下"），确保从任意节点到根的路径唯一。好处是消除了路由环路，简化了拥塞控制。

## **IB 报文在交换网络中的转发流程**

让我们追踪一个报文从 HCA 到目的端的完整旅程。

### **HCA 发送报文**

当应用程序提交一个 Work Request 到 Queue Pair 时，HCA（Host Channel Adapter）的硬件开始工作：

1. 构造完整的 IB 报文（包括 LRH、可能的 GRH、BTH、Payload）
2. 设置 DLID 为目的端口的 LID
3. 设置 SL 为预期的服务级别
4. 计算并附加 ICRC
5. 将报文发送到物理链路

在这个阶段，HCA 不关心报文会走哪条路径——那是交换机的事情。HCA 只负责把报文送到"正确的下一跳"（通常是连接在同一交换机上的第一个交换机）。

### **交换机查表转发**

报文到达交换机的某个端口后，转发流程开始：

1. **头部解析**：交换机解析 LRH，提取 DLID、LNH 等字段
2. **验证 LID 范围**：检查 DLID 是否在交换机的 LID 范围内
3. **查表**：用 `LFT[DLID]` 获取输出端口
4. **处理 LNH**：根据 LNH 决定是否需要 GRH（通常不需要）
5. **输出**：将报文发送到目标端口

**这个过程完全是无状态**的。交换机不维护任何"流表"或"连接跟踪"，只需要一个静态的 LFT。好处是转发延迟可预测，硬件实现简单。代价是缺乏动态负载均衡能力。

### **Subnet Manager 的预计算**

交换机之所以能够"无状态转发"，是因为 SM 在初始化时已经计算好了一切。SM 的工作流程如下：

1. **拓扑发现**：SM 通过 SMP（Subnet Management Packet）查询所有交换机和端口，构建拓扑图
2. **LID 分配**：为每个端口分配 LID，确保 LID 分配反映拓扑结构
3. **路径计算**：运行 Up-Down 算法，计算每个端口到每个目的端口的最短路径
4. **表编程**：将计算好的 LFT 下载到每个交换机

这个过程**只需要一次**，发生在网络初始化阶段。之后，网络可以运行数月甚至数年而不需要重新计算路径。

### **报文的最终交付**

经过若干跳交换机后，报文最终到达目的端口：

1. 目的 HCA 接收报文
2. 验证 ICRC
3. 根据 QPN 将报文放入对应的 Receive Queue
4. 通知应用程序数据已到达

整个过程中，**应用程序完全不感知路由的存在**。它只看到"数据已发送"或"数据已接收"，中间的网络细节完全被隐藏。

## **InfiniBand 路由 vs RoCEv2 路由机制对比**

InfiniBand 和 RoCEv2 代表了实现 RDMA 的两种不同思路。理解它们的差异，有助于我们更深刻地理解 IB 路由的设计选择。

### **设计的差异**

**InfiniBand**：从第一性原理出发，为 RDMA 设计完整的协议栈。路由、流控、可靠传输都是原生设计的组成部分。

**RoCEv2**：在以太网之上叠加 RDMA 能力。路由依赖 IP 基础设施，流控依赖 PFC/ECN，可靠传输依赖 RDMA 核心。

### **路由机制的对比**

| 维度 | InfiniBand | RoCEv2 |
| --- | --- | --- |
| 路由基础 | L2（基于 LID） | L3（基于 IP） |
| 转发决策位置 | 交换机 L2 查表 | 路由器 L3 查表 |
| 路径计算 | 静态（SM 预计算） | 动态（OSPF/BGP/ECMP） |
| 路径一致性 | 强（相同 DLID 走相同路径） | 弱（ECMP 可能导致路径变化） |
| 流量控制 | 原生信用机制 | PFC |
| 拥塞处理 | 硬件信用防拥塞 | ECN + CNP |
| 可预测性 | 高 | 中等 |
| AI 通信友好度 | 高（路径稳定） | 中等（需调优 ECMP） |

### **AI 集群的通信模式有其特殊性：**

- **AllReduce 需要多次迭代**：每次迭代都需要同步梯度，路径切换会导致同步不一致
- **流量模式不规则**：某些 GPU 之间的通信量远大于其他对
- **对延迟敏感**：即使是微秒级的延迟差异也会影响训练效率

InfiniBand 的**静态路由**在这种场景下是优势：路径在网络初始化时确定，整个训练过程中保持不变。这确保了迭代之间的行为一致性。

RoCEv2 的**动态 ECMP** 可能在某些情况下导致负载均衡，但路径的不确定性在 AllReduce 场景中可能是问题。通过配置静态路由或禁用 ECMP，可以缓解这个问题。

![](https://pic1.zhimg.com/v2-20d610876ac95f3414b6b3788c9618cc_r.jpg)

IP 路由是**无连接**的。每个数据包独立决策，路由器根据当前的网络状态选择最佳路径。这导致的结果是：同一个 TCP 连接的不同数据包可能走不同的路径，抵达顺序也可能乱序。应用程序需要自行处理这些问题。

RDMA 的语义要求**严格按序交付**。当应用程序发起一次 RDMA Read 操作时，它期待的是一次原子性的数据返回——数据必须完整、必须按序、不能有间隙。如果 IP 路由让数据包走了不同的路径，这种语义就很难保证。

更深层的问题是**流量控制**。以太网假设网络是"丢包可接受"的，所以它采用"发送后发现丢包再重传"的策略。但 RDMA 的目标是最小化延迟，"先发后检"的重传机制在很多场景下是不可接受的。

InfiniBand 采用**信用流量控制**：接收方在建立连接时就向发送方通告"我有多少缓冲区"，发送方只能在这个范围内发送数据。这种机制需要在硬件层面保证路径的一致性，否则信用计数就会失效。

### **端到端语义的约束**

RDMA 的核心价值在于**零拷贝**和**CPU 旁路**。应用程序只需描述"我要发送什么"，而不需要关心"数据如何到达"。这种抽象对路由机制提出了特殊要求。

路由必须**对应用程序透明**。应用程序不应该关心它的数据走哪条路径，也不应该关心路径是否变化。这意味着路由决策必须在网络层面完成，而不是像某些以太网方案那样依赖端点做路径选择。

这引出了 InfiniBand 路由的一个核心设计原则：**路径由网络决定，而非端点决定**。交换机根据预设的转发表转发数据包，端点只需要知道目标地址（LID 或 GID），不需要知道路径细节。
