大模型的语义理解和推理能力越来越强，但 RAG 系统的检索入口，依然主要依靠 BM25、Embedding 相似度或者两阶段召回与重排。这里有一个很容易被忽略的问题：**生成模型可能已经足够聪明，但它最终能够看到哪些证据，仍然取决于前面的 Retriever。**

如果正确证据在第一阶段就被遗漏，后续再强的 Reranker 或 Generator，通常也无从挽回。

这篇论文提出 **DecisionRAG**，尝试改变传统 RAG 的检索范式：不再主要依赖 BM25 或 Embedding 相似度来寻找证据，而是利用具备语言理解能力的 **Decision Model**，沿着语料的层级结构逐步判断：**哪些主题值得探索、哪些文档可能包含答案、哪些段落真正值得返回。**

先给出我对论文的核心理解：

**DecisionRAG 的关键贡献，不只是使用 LLM 做检索，而是将检索转化为一系列非生成式的相关性决策，再利用语料的层级结构控制搜索空间，使语言模型的理解能力能够低延迟地参与检索全过程。**

它试图同时回答三个问题：

1. 检索能力不足：BM25 和 Embedding 可能无法正确识别复杂查询真正需要的证据。
2. 检索入口受限：Reranker 只能重排第一阶段已经找到的候选，无法找回遗漏的相关文档。
3. LLM 检索效率低：Agentic Retrieval 可以逐步推理和探索，但多轮自回归生成的延迟与成本较高。

论文在四个 Benchmark 上验证了这条技术路线，尤其是在首位证据定位与检索延迟方面。但与此同时，它也引出了新的问题：**检索质量从依赖相似度匹配，转向依赖语料层级组织与路径决策质量。**

论文地址：

[https://arxiv.org/abs/2610.35868](https://arxiv.org/abs/2610.35868)

## 一、论文核心要解决什么问题？

### 1.1 传统 RAG 存在检索器与生成模型的能力不对称

目前很多 RAG 系统的基本流程是：

**Query → BM25 / Dense Retrieval → Reranker → Generator LLM**

![](https://pic2.zhimg.com/v2-88534a9e35fc7021ec163eb1e77fea91_r.jpg)

这里存在一个结构性问题：生成模型可能拥有很强的推理和语义理解能力，但它最终能够使用哪些信息，取决于前面的检索器。

例如，用户问：

“克里斯托弗·诺兰在 2000 年执导的电影，主角是谁？”

正确的证据链需要识别：

- 导演：Christopher Nolan；
- 年份：2000 年；
- 影片：《Memento》（《记忆碎片》）；
- 主角：Leonard Shelby。

传统词法检索可能因为《Gladiator》（《角斗士》）与“2000 年”“电影”等词高度匹配，而将它优先返回。Dense Retrieval 虽然具备一定语义匹配能力，但依然取决于编码器学到的相似度空间。

**语义相似，不等于能为当前问题提供正确证据。** 对于需要消歧、多条件约束、跨实体关系判断的问题，这种差异尤其明显。

即使后续接入强大的 LLM Reranker，它也只能在已有候选中排序，无法挽回根本没有进入候选池的正确证据。

这就是论文所强调的 *Capability Asymmetry*（能力不对称）：**Retriever 的能力成为 Generator 能力发挥的前置瓶颈。**

### 1.2 为什么不直接让 LLM 自己寻找文档？

实际上，已经有不少研究沿着这条路线探索。例如 MemWalker、PageIndex、LATTICE 等方法，会让 LLM 沿着文档目录或语义树逐层选择下一步要阅读的内容。

相比一次性进行相似度检索，这种方式能够利用语言模型理解问题约束、文档结构和候选之间的关系。

但问题在于，它们通常依赖**自回归生成**来做导航决策：先阅读候选，再生成文档编号、分析结果或者下一步动作；进入下一级后，再重复一次。

当一个层级包含大量候选，或者搜索需要跨越多个层级时，这些连续生成会带来明显的时间和计算成本。

DecisionRAG 的出发点因此非常直接：

**如果我们只是想判断“哪个候选更相关”，是否真的需要让 LLM 逐 Token 生成一段回答？**

如果模型能够直接输出候选相关性的概率，而不是先生成导航文本，就有机会兼顾强语义理解与高检索效率。

## 二、DecisionRAG 怎么解决？

DecisionRAG 的方法可以拆成三个核心设计：**层级化导航、非生成式决策、共享上下文联合判断**。

![](https://picx.zhimg.com/v2-e03715c91a3900d893b601692c1013f7_r.jpg)

### 2.1 第一个设计：把检索从相似度匹配改成层级导航

DecisionRAG 首先将语料组织成树形结构。

最简单的情况是 **文档 → 段落**；对于更大规模的语料，还可以继续向上增加 **主题 → 类别 → 文档 → 章节 → 段落** 等层级。

![](https://pic1.zhimg.com/v2-1d22488a5ad20682afc39a475b0b8404_r.jpg)

每一级，Decision Model 都会判断当前候选分支是否值得进一步探索，只保留其中最有希望的 Top-k，再展开这些候选的子节点。其余分支被剪枝，不再继续检查。

例如，系统先从多个主题中保留与问题最相关的主题，再从这些主题中选出若干文档，最后在选中文档内部寻找相关段落。

这种设计与传统 Dense Retrieval 的区别在于：

- **Dense Retrieval：通常直接针对全局候选计算相似度，再按分数筛选。**
- **DecisionRAG：先判断答案最可能位于哪些分支，再逐层缩小搜索范围。**

这样一来，文档标题、章节标题、所属主题以及上下层关系，都能够参与证据定位，而不只是段落文本本身。

需要强调的是，**层级检索本身并不是这篇论文首次提出的概念**。DecisionRAG 的主要创新，在于如何使用非生成式 Decision Model，高效地完成每一级导航判断。

### 2.2 第二个设计：使用 Decision Model 代替生成式 LLM 做导航决策

这是整篇论文最核心的技术点。

Decision Model 并不需要生成一段自然语言来回答“哪个文档相关”，而是针对预定义的答案选项直接输出概率。论文主要使用两种判断模式。

![](https://pic4.zhimg.com/v2-6ab59a26fc8109357a707820fbfcdf7d_r.jpg)

**模式 A：Parallel Binary Judgments（并行二元判断）**

将 Query 与一批候选放入共享上下文，针对每个候选分别提出“是否相关”的 Yes/No 问题。例如：

- Christopher Nolan：是否值得探索？
- Memento：是否值得探索？
- Gladiator：是否值得探索？

Decision Model 可以在一次前向计算中，同时给出各问题的 `P(Yes)`。

这里的概率是**各候选分别对应的二元判断结果**，并非互斥选择，因此所有候选的 `P(Yes)` 加起来不需要等于 1。

这种模式适合层级导航中的文档筛选和段落初筛：能够同时判断大量候选，也允许保留多个相关分支，优先保障证据覆盖。

**模式 B：Multiple-Choice Judgment（多选项竞争判断）**

当系统已经得到一批相关段落后，还可以提出一个多选问题：

“在这些候选段落中，哪一段最相关？”

模型对相互竞争的选项输出归一化概率：

$$ P(d_i\mid q,d_1,\ldots,d_m),\qquad \sum_{i=1}^{m}P(d_i\mid q,d_1,\ldots,d_m)=1 $$

这种方式更适合最终精排。论文的默认流程是：先使用 Binary Judgment 筛选候选，再对最后的 Top-m 段落使用 Multiple-Choice Judgment，改善首位证据排序。

可以简单理解为：

**中间层更关注 Recall，最终层更关注 Precision。**

值得注意的是，两种模式都不需要生成导航文本，而是直接进行概率判断。这是 DecisionRAG 能够缩短检索延迟的重要原因。

### 2.3 第三个设计：共享上下文，而不是独立判断每个候选

我认为这是论文另一个很值得关注的技术发现。

传统 Cross-Encoder Reranker 往往独立评估 Query–Passage Pair：

$$ s_i=f(q,d_i) $$

每个候选的分数主要由当前 Query 与这一候选决定。

DecisionRAG 则把一批候选放在同一个上下文中，对每个候选提出一个相关性问题：

$$ s_i=P(\mathrm{Yes}\mid q,d_1,\ldots,d_n,Q_i) $$

其中， $Q_i$ 表示针对候选 *i* 的判断问题。

这样，模型不只是看到候选 $ d_i$ ，还能够同时参考其他候选，对它们进行**相对比较**。

例如，单独评价《Gladiator》时，模型可能因为它符合“2000 年电影”而给出较高相关性；但当它同时看到《Memento》与 Christopher Nolan 相关文档时，就更容易判断哪个候选满足完整的查询约束。

这相当于引入了 *Contextual Comparative Relevance*（上下文比较式相关性）。

论文的消融实验支持了这一设计：

- **MultiDoc2Dial：**对已选文档的所有段落统一进行共享上下文评分，相比逐文档评分，R@1 从 36.7% 提升到 44.4%，提高 **7.7 个百分点。**
- **Natural Questions：**固定 200 个候选时，每个候选单独打分的 Hit@1 为**47.8%；**每个请求共同判断 50 个候选时提升到**54.3%。**
- **最终多选排序：**对同一组 200 个候选进行多选竞争判断，Hit@1 达到**60.6%。**

这说明 DecisionRAG 的收益并不只是来自使用了更强的模型，而与**候选能否在共享上下文中相互比较**直接相关。

但这里也埋下一个值得后续讨论的问题：当候选的分数依赖其他候选时，分数就具有集合条件性，其稳定性与跨批次可比性需要格外注意。

### 2.4 完整检索流程与工程实现

结合论文的 Algorithm 1，完整流程可以概括为：

```text
Query（可包含历史对话）
↓
主题 / 文档路由： Binary Judgment → Top-k
↓
逐级展开： 只进入保留分支，继续筛选
↓
段落相关性判断： 共享上下文 Binary Judgment → Top-r
↓
可选最终精排： Multiple-Choice Judgment
↓
Top-r Evidence → Generator LLM
```

这里有两个工程细节需要关注。

**第一，语料层级不一定天然存在。**

对于已有目录、产品分类或文档结构的语料，DecisionRAG 可以直接利用这些信息；对于缺乏上层层级的 Wikipedia，作者先用 `e5-base-v2` 对页面标题与首句进行 Embedding，再通过 K-means 聚成 1,000 个簇，最后让 Qwen3-8B 根据簇内页面标题生成类别描述。

因此，**Retriever-Free 不等于完全不使用 Embedding**。更准确的说法是：在线检索时不依赖传统的第一阶段召回器；离线层级构建仍然可以使用 Embedding。

**第二，大量候选可以拆成多个并行请求。**

某一层候选太多、无法一次放入上下文时，可以先拆成多个请求并行判断；在需要精细比较的最终阶段，再让缩小后的候选进入共享上下文。

这种设计让搜索的串行阶段数主要由层级深度决定，而不是每次都对整个语料进行一轮模型评分。

不过，论文所谓随语料规模近似对数增长的延迟，需要满足层级结构较平衡、每层请求能够充分并行、模型服务容量充足等前提；**串行深度增长较慢，不代表总计算量或者部署成本也必然按对数增长。**

## 三、实验说明带来了什么收益？

### 3.1 实验数据集

论文在四个 Benchmark 上评估 DecisionRAG，涵盖对话检索、复杂条件问答、技术文档检索与大规模开放域检索。

| Benchmark | 语料规模 | 主要考察 |
| --- | --- | --- |
| MultiDoc2Dial | 4,110 个段落 | 多轮对话中的证据定位 |
| ConditionalQA | 58,483 个段落 | 条件约束、场景化问答 |
| MTRAG（IBM Cloud） | 72,442 个段落 | 技术文档与多轮检索 |
| Natural Questions | 268 万个段落 | 大规模开放域检索 |

前三个数据集有较明确的文档组织结构；Natural Questions 需要额外构建聚类层级。需要注意，Natural Questions 的主实验使用 500 个测试问题，并非对全部潜在查询分布的验证。

### 3.2 收益一：显著提高 Top-1 证据定位能力

论文 Table 2 给出了不进行任务特定训练时的检索对比。下面只摘取最直接的基线与 DecisionRAG 结果，保持各数据集原有指标名称。

![](https://pic4.zhimg.com/v2-c939ffb76f9bab5915b0a914f806c627_r.jpg)

DecisionRAG 相比 Dense + Qwen3-Reranker-8B：

- **MultiDoc2Dial：**R@1 从 33.6% 提升至 47.4%，提高**13.8 个百分点。**
- **Natural Questions：**Hit@1 从 48.0% 提升至 65.4%，提高**17.4 个百分点。**
- **ConditionalQA：**Hit@1 提高**5.1 个百分点**，但仍低于 GPT-5 Reranker 的 73.4%**。**

这说明 DecisionRAG 在**把正确证据排到最前面**这件事上有明显优势。

但不能据此认为它在所有检索指标上都全面领先。例如在 Natural Questions 上，DecisionRAG 的 R@10 为 86.7%，低于 Dense + Qwen3-Reranker 的 89.0%。

**首位证据定位的提升，与候选集合的整体召回能力，需要分开评价。**

### 3.3 收益二：非生成式决策显著降低导航延迟

作者设计了一个很重要的对照实验：固定层级结构与导航预算，只替换决策机制。

一组使用 GPT-5 生成导航决策；另一组使用 Decision Model 输出概率。

![](https://picx.zhimg.com/v2-b4961868715a606b304e300b9515c1d7_r.jpg)

在相同导航结构下：

- **ConditionalQA：**GPT-5 需要 28.2 秒，DecisionRAG 只需 0.82 秒，约**34 倍**延迟差距**。**
- **Natural Questions：**GPT-5 需要 250.8 秒，DecisionRAG 为 1.73 秒，约**145 倍**延迟差距**。**

更值得关注的是，效率的大幅提升并没有带来一致性的精度退化。

Natural Questions 上，DecisionRAG 的 Hit@1 为 65.0%，高于 GPT-5 生成式导航的 59.0%；ConditionalQA 上则相反，GPT-5 的 73.8% 优于 DecisionRAG 的 69.7%。

这支持了论文的核心判断：

**大量检索导航决策并不一定需要自回归生成，直接输出相关性概率就能实现有竞争力的效果。**

但这里对比的是具体的 Jev Decision Model 与 GPT-5 生成式导航，以及论文中的特定 API 与硬件配置。因此，34～145 倍是该实验设置下的结果，不能理解成所有 Decision Model 都天然比生成式模型快这么多。

### 3.4 收益三：检索改善能够传递到最终 RAG 回答

检索指标更好，是否意味着最终回答也会更好？

论文固定生成模型为 **Qwen3.5-27B**，把每种检索系统返回的 Top-5 段落输入生成模型，再评价回答质量。

![](https://picx.zhimg.com/v2-514bad8e467dd8ea7e6e9465a8277c75_r.jpg)

其中最明显的提升来自 MTRAG：

- Dense + Qwen3-Reranker：**39.4%**；
- DecisionRAG：**44.1%**；
- DecisionRAG + Dense：**47.3%**。

这说明 DecisionRAG 的改进并不只是体现在检索排名上，在部分任务中，也确实能够提升最终生成结果。

但实验同时揭示了另一个现象：**检索 Top-1 的大幅提高，并不总能转化为同等幅度的回答质量提升。**

一个可能的原因是：只要 Top-5 中已经包含必要证据，首位排序的进一步改善对最终答案可能作用有限；另一方面，生成模型自身能力、证据的充分性以及多段证据间的互补关系，都会影响答案是否正确。

这也提醒我们，评价检索系统时不能只看 Hit@1 或 Recall@k，还应该同时评估下游任务效果。

### 3.5 收益四：层级导航与 Dense Retrieval 具有互补性

论文还发现，将 Dense Retrieval 的候选补充到 DecisionRAG 的最后排序阶段，可以进一步改善证据覆盖。

例如：

- ConditionalQA：R@10 从 **71.9%** 提升到 **76.3%**；
- Natural Questions：R@10 从 **86.7%** 提升到 **88.9%**；
- MultiDoc2Dial：R@10 从 **83.6%** 提升到 **84.7%**。

这说明两类检索方法可能找到不同的相关证据。

我的理解是，Dense Retrieval 擅长快速从全局找到语义相近的候选，而 DecisionRAG 更强调利用问题约束、文档上下文与结构路径完成证据定位。

所以，**DecisionRAG 与传统 Retriever 不一定是非此即彼的替代关系，也可以形成互补。**

## 四、哪些问题还没有真正解决？

论文中直接讨论了两个限制：**依赖高质量层级结构**，以及**剪枝后无法恢复相关分支**。在这两个问题之外，我认为还可以进一步从检索机制、复杂任务、实验设计与实际部署四个方面分析。

### 4.1 核心局限一：仍然存在不可逆的证据丢失

DecisionRAG 通过逐层剪枝降低搜索成本，但这也引入了新的召回瓶颈。

假设真正相关的段落位于主题 C 下，但系统在第一层错误地把主题 C 剪掉，那么无论后续的文档判断和段落排序有多准确，都不可能再找回这个证据。

可以概括为：

$$ P(\text{最终找到证据})\leq P(\text{相关路径被保留}) $$

**这实际上只是把原先的候选召回瓶颈，转移到了层级路由和路径选择阶段。**

论文的剪枝预算实验也反映出这一问题：

![](https://pic4.zhimg.com/v2-04454878f423654161ac368006c3f7ad_r.jpg)

在 Natural Questions 上，当顶层只保留 **1% 聚类**时，R@10 降至 **63.7%**；提高到 **15%** 时，R@10 达到 **86.2%**，与直接评分全部页面的 **84.5%** 已经接近甚至略高。

但增加探索预算意味着更多候选判断、更多成本。也就是说，导航搜索仍然要在**召回覆盖与计算开销**之间进行权衡。

我对这个问题的判断是：

**DecisionRAG 没有消除检索的召回上限，而是重新定义了召回上限的形成机制。**

传统 RAG 的瓶颈是第一阶段 Retriever 有没有召回正确证据；DecisionRAG 的瓶颈则是每一级导航有没有保留正确路径。

潜在改进包括保留次优分支、根据置信度动态扩展预算、允许回溯重新探索，或者利用 Dense / Sparse Retrieval 补充候选。它们可以缓解问题，但并不是原论文已经完整实现的能力。

### 4.2 核心局限二：对语料组织结构有较强依赖

DecisionRAG 的优势建立在一个重要前提之上：**上层节点的名称或描述，能够帮助模型识别下层哪些位置值得探索。**

例如，一个文档标题叫“退款政策”，实际段落讨论“跨境支付失败后的费用返还”，Decision Model 可能沿着标题找到相关证据。

但如果文档标题只是“其他说明”“补充材料”“附件 3”，上层节点就可能无法提供足够的导航线索。

对于组织混乱的私有知识库，这个问题尤其突出。

论文通过已有目录或离线聚类构建层级，但仍然有一些值得进一步研究的问题：

- 什么样的层级最适合检索？语义聚类是否优于原有文档目录？
- 一份文档涉及多个主题时，应该如何组织，才能避免单一路径归属造成漏检？
- 上层节点摘要没有覆盖下层关键细节时，能否继续被正确定位？
- 新文档加入、已有文档变化时，层级怎样维护而不破坏原有导航效果？

这里有一个更普遍的问题：**层级组织本身也是一种信息压缩，而压缩可能产生信息损失。**

当上层表示不能反映下层证据的真实用途时，Decision Model 再强，也可能在入口处走错方向。

### 4.3 核心局限三：树形导航不一定适合复杂多跳检索

DecisionRAG 虽然支持在每层保留多个 Top-k 分支，但本质上仍是沿着语料层级逐层选择候选。

一些复杂问题需要跨文档、跨主题的多个证据联合推理。例如：

“某家公司收购的企业，其创始人此前还创办过哪些公司？”

回答它，可能需要先找到收购事件，再确定被收购企业及其创始人，最后搜索这名创始人的其他创业经历。相关证据可能分布在完全不同的主题节点下。

在这类任务中，原始 Query 对某些中间证据的相关性可能并不明显：只有先找到前一跳的信息，后面一跳的检索目标才会变得清晰。

DecisionRAG 的当前方法更偏向于**从既有问题定位到相关文档和段落**，没有提供完整的多跳问题分解、证据链构建与迭代推理机制。

论文虽然评估了包含复杂约束的任务，但不能据此认为它已经解决一般意义上的跨文档多跳推理。

**能够检索具有复杂约束的证据，不等于能够主动发现与构建复杂证据链。**

### 4.4 核心局限四：共享上下文的分数依赖候选集合

论文证明，把多个候选放在共享上下文中比较，可以改善相关性判断。但这也带来了一个尚未被充分解决的问题：

**某个候选的评分不仅与它自身相关，还与同时出现的其他候选相关。**

例如，同一段落与大量明显无关的段落一起判断时，可能得到较高的相关性分数；与几个高度相关的段落同时出现时，分数则可能降低。

这种相对比较有助于排序，但也意味着分数具有**集合条件性**。

因此，还需要进一步研究：候选顺序是否影响判断？不同批次的概率是否真正可比？增加或删除一批难负例后，原有候选排名是否稳定？输出的 `P(Yes)` 又能否直接作为自动剪枝的可靠置信度？

论文验证了共享上下文的整体收益，也验证了拆分请求的可行性；但这些结果还不足以证明其概率在跨任务、跨候选集合时都经过严格校准。

从工业落地角度看，这将影响剪枝阈值、跨请求合并排序和系统鲁棒性。

### 4.5 核心局限五：检索效果提升不等于任务效用提升

DecisionRAG 主要优化和评估的是 **Retrieval Quality**，例如 Recall@k、Hit@1 和 nDCG@k。

但是，真正的 RAG 系统最终关心的是 **Downstream Task Utility**。

一段证据可能与问题非常相关，但不能充分支持最后的回答；另一段证据虽然表面相关性较低，却可能包含关键的例外条件。

对于多证据任务，还可能出现：

- 两个高相关段落表达的是重复信息；
- 一段低排序证据恰好补齐回答所必需的条件；
- 多段证据之间存在矛盾；
- 检索更多内容反而增加噪声，使生成模型答错。

论文的下游实验其实已经提示了这个差距：**检索首位命中率的大幅提升，并没有在最终回答质量上得到等比例提升。**

因此，DecisionRAG 仍然主要是**相关性驱动的检索方案**，还不是显式面向下游任务净收益的证据选择机制。

这并不削弱论文的贡献，而是说明：让模型更聪明地找到“相关内容”，与让模型找到“对当前任务真正有用的证据”，仍然是两个不同的问题。

最后，还有一个很容易被误读的理论结论：论文提出，层级较平衡时，查询的串行阶段数可以近似按 *O(log N)* 增长。

但这描述的是**顺序导航深度**，而不是总计算量或者总体成本。每层实际要评估多少候选、能否并行执行、模型的上下文长度与服务吞吐，都会影响最终表现。

综合来看，DecisionRAG 提供了一种值得关注的检索新范式：**不必始终通过相似度匹配找证据，也可以让具备语言理解能力的模型，直接决定哪些证据位置值得探索。**

但它也把检索的关键问题，从“Embedding 能否匹配到正确段落”，转移到了“语料能否被有效组织、上层导航是否可信、剪枝是否保留关键证据，以及检索到的内容最终能否帮助任务完成”。
