## **一个多模块系统的AI产研提效复盘 · 系列第二篇**

---

> 本文含完整架构图例与关键设计件示例，可直接对照落地。

这篇文章复盘的是我们产研中心最近的一次方案选型：给研发团队搭一条AI原生产研流水线，让需求从一句概念描述进来，AI 自动完成背景检索、PRD 生成、设计改动说明，一路到代码合并主干出去。

第一版方案是一套漂亮的多智能体架构：PRD 智能体、设计智能体、研发派发智能体、审核协调智能体，主智能体居中编排。评审前大家都挺满意，结果会上一个很朴素的问题，把整版架构掀了。最终胜出的方案说出来有点土：一堆 markdown 技能文件，加一个 YAML 状态文件。

多智能体为什么输给一个 YAML 文件？这篇复盘把推演过程完整摊开——越复盘越觉得，这里面每一条判断，对正在搭 AI 工程化体系的团队都成立。

## 先交代背景

我们产研中心维护着多条业务线的前后端工程，去年内部沉淀了一套自研的 AI 研发脚手架，代号向日葵——一个直接嵌进工程目录的协作文件夹，AI 编程工具打开工程就能识别它的规则入口。需求理解、技术方案、编码、自测这条工程内的链路，它已经管得很好。

但需求从哪来，一直靠人工。产品同学脑子里的一句话概念，要变成一份边界清晰、影响面明确的 PRD，中间隔着业务背景检索、历史需求翻旧账、跨系统影响分析。费人，又没什么技术含量。

于是新的目标很自然：往上再盖一层，让 AI 把整条生命周期接管掉。需求方只提了一条硬约束： **PRD 要人工审、设计要人工审、合并前要人工审，三个卡点，一个不能少。**

当时没人意识到，这三个卡点后来把整个方案的地基掀了。

## 一个朴素的问题，掀翻第一版架构

第一版方案产出得很快。PRD 智能体、设计智能体、研发派发智能体、审核协调智能体，主智能体做 A2A 编排——每个环节一个专家，职责单一，边界干净。评审会上最初的讨论全在"专家怎么拆更细"，没人质疑这个拓扑本身。

转折来自一个朴素的问题。一位平时不碰架构的同事问：这条流水线，从概念进来到代码合并，大概要多久？

认真一算，大家都不说话了。

PRD 出来要等人审，审核人可能明天才有空。设计改动说明要等一轮视觉意见。研发加自测跑完，又是半天一天。 **这条流程的天然时间尺度是天，不是分钟。**

而任何 AI Agent 工具的会话，都不是常驻进程。会话一关，上下文就没了。今天编排好的五个专家，明天早上全部失忆——不知道 PRD 审到哪了，不知道设计被驳回过一轮，甚至不知道这条需求存在。

架构图再好看，也掩盖不了一个致命前提： **多智能体编排只活在会话里，而这条流程，天生要睡一觉再接着干。**

## 会话不是常驻的，这才是第一性约束

把"会话非常驻"当成第一性约束重新推一遍，很多事就倒过来了： **流程的脊柱，不能是任何会话内的东西** ——不能是智能体记忆，不能是智能体间消息，必须是外置的、落盘的、重启之后还在的文件。

顺着这条往下走，方案朴素得评审都有点意外：一个主智能体，按当前阶段加载对应的技能文件（一堆 markdown，一个阶段一个文件夹），外加一个 YAML 状态文件给每条需求记台账。任何新会话启动，读一遍台账，就能无损续跑。

![](https://pic1.zhimg.com/v2-6164f25979d657d5f40bfd336cc7c836_r.jpg)

那个 YAML 台账长什么样？摘一段真实的字段设计，三个字段是灵魂：

```yaml
requirement_id: REQ-20260914-001
stage: DESIGN_PENDING_REVIEW        # 当前状态机位置——挂起恢复全靠它
concept: |                          # 原始概念描述，永久保留
  运营希望报表支持自定义条件批量导出，包含明细数据……
context_digest: |                   # 跨阶段关键决策摘要，防上下文丢失的脊柱字段
  涉及工程：后端主工程报表模块、管理后台前端；
  复用现有查询接口；不涉及数据同步链路；
  关键决策：导出走异步任务，CSV/XLSX 双格式。
review_records:                     # 审核历史，只追加不修改
  - gate: prd
    result: rejected
    reviewer: 张三
    comment: "导出格式补充 CSV 选项"
    at: 2026-09-14T18:00:00+08:00
```

`stage` 解决"走到哪了"， `context_digest` 解决"关键决策是什么"， `review_records` 解决"谁驳回过、为什么"。新会话只要读这三样，就等于把失忆的专家一夜之间救活。

人工卡点的交互也顺势变得极简——审核人在 **任何一个新会话** 里说一句话就行：

```text
REQ-20260914-001 设计审核 通过
REQ-20260914-001 PRD驳回 导出格式需要补充CSV选项
REQ-20260914-001 代码驳回 导出接口缺Swagger注解
```

主控技能解析指令、校验状态机、记录意见、推进到下一阶段。不用重建审批系统，一句自然语言加一次状态迁移，人机握手就完成了。

还有个容易被忽视的细节：驳回意见必须连同驳回人、时间、原文写进台账，修订稿里逐条响应。同一道卡点驳回超过两轮，系统该建议当事人线下对齐—— **流水线管流程，不管人和人的分歧。**

## 更准这件事，跟智能体数量无关

毙掉多智能体主干，还有第二层理由，不直观，但更接近本质： **多智能体拓扑，不会自动带来更高的生成准确度。**

把 PRD 质量拆开看，天花板由三件事决定：背景数据质量（知识库检索命中率）、上下文纯净度（当前阶段只加载该阶段需要的指令）、输出模板的约束强度（影响面分析拆成固定维度逐项填写）。这三件事，没有一件是多加几个专家能改善的。恰恰相反，每多一个专家就多一条交接边界，交接契约稍有松动，关键信息就从缝隙里漏掉。

![](https://pica.zhimg.com/v2-e0432ac94771b7b6eeb2caad31fc8056_r.jpg)

多智能体没有被全盘否掉。PRD 生成环节，主智能体会派两三个 **用完即销毁** 的子代理，并行去知识库查不同主题，检索结果汇总回来统一写 PRD。它该待的位置是干活的临时工，不是流程的主人。

技能文件的组织也是同一个逻辑——一个阶段一个文件夹，各管各的，互不稀释：

```text
skills/
├── pipeline-orchestrator/    # 主控：读状态→路由阶段→回写状态→通知
├── prd-generator/            # 概念+知识库背景 → PRD
├── ui-design-spec/           # PRD+设计稿 → 设计改动说明
├── dev-integration/          # 拉分支+文档放置+触发研发
└── review-merge/             # 完成校验+审核材料+合并出口
```

另外立了一条死规矩：检索没覆盖到的分析点，必须在 PRD 的开放问题一节显式标注成背景缺口， **禁止编造** 。这条规矩写出来很土，但它是人工审核最信任的一道防线——审核人可以接受"这里没查到"，无法接受"这里被编了"。

## 担心打架的两套框架，物理上碰不到

方案定型路上最惊险的一跳，是处理新流水线和向日葵的关系。直觉很容易滑向一个错误：新框架这么能干，要不要把技术方案、编码、自测也接管掉，一步到位？

我们专门做了次结构评估，结论是不仅不该接管，而且两套框架 **天然打不起来** ：新流水线住在通用智能体工具里，工作目录在工程外；向日葵嵌在工程内，靠 AI 编程工具的规则目录触发。两套加载机制互不识别， **永远不会在同一个宿主会话里同时生效** 。这层物理隔离，比任何协作设计都可靠。

![](https://pic2.zhimg.com/v2-9cd07cec24eb0a2cc47acec570cdf153_r.jpg)

于是层级关系收敛成一句话： **新框架管工程外的生命周期，旧框架管工程内的研发执行，交汇点收窄到三个接口——文档放置、git 分支、触发指令。** 落到具体契约上就是：

```text
PRD          →  {工程}/ai_collaboration/docs/sprints/REQ-xxx_标题_sprint.md
分支命名     →  feature/REQ-20260914-001
首个commit  →  [REQ-20260914-001] docs: 需求文档入库
触发指令     →  执行需求开发 workflow：需求文档已放入 docs/sprints/，按 WF 流程走
```

这里有个坑替后来的读者先踩了：对接前务必逐字核对双方的目录约定。我们最初凭印象写的落盘路径，跟旧框架实际的文档目录差了一层——就差这一层目录，研发侧的框架会完全消费不到那份 PRD。所有接口契约必须 **双侧文档同步冻结** ，谁要改就两边一起改，禁止单侧静默调整。

git 也划了界：开发过程的增量提交归旧框架，push、建 PR、合并主干统一归新流水线。合并永远以代码平台的 PR 审批作最后一道闸门—— **AI 可以把 PR 准备到只剩点一下合并的程度，但那一下的责任，在人。**

## 谁驱动谁，开关放在边界外面

还有个绕不开的现实：老业务线堆着多年人工逻辑、又直接连着客户，必须坚持以人为主的人机协作；新一些、容错度高的工程，才敢交给 AI 主导。

这个双策略如果让旧框架去适配，等于往稳定的执行层塞模式判断，污染面太大。解法是把开关放在新框架这层的工程映射表里，每个仓库标一个 `automation_level` ：

```yaml
repos:
  - key: legacy-core        # 老核心业务线
    automation_level: human_driven   # 建档时拦下，走人机协作
  - key: new-export-service # 新容错业务
    automation_level: ai_driven      # 默认自动流转
```

涉及"人驱动"工程的需求，建档时就拦下来，提示走原有的人机协作模式，人工确认后才放行；全部落在"AI 驱动"工程的需求，才默认自动流转。

这个设计最好的地方在于， **旧框架从头到尾不知道自己是被谁驱动的** 。哪天某个工程定级要变，动的只是一个 YAML 字段，两层架构一行代码都不用改。这大概是对"分层分对了"最硬的验证。

## 便宜到能随时搬家

最后说一个选型时权重拉满、却最少被讨论的维度：可迁移性。判断标准很粗暴—— **流程逻辑离平台私有设施越远，搬家成本越低。**

顺着这个标准检查最终方案：编排逻辑全是 markdown 技能文件和 YAML 台账；外部能力——知识库检索、消息通知、设计稿读取——全走 MCP 标准协议，接入就是一段通用配置：

```json
{
  "mcpServers": {
    "figma": {
      "command": "npx",
      "args": ["-y", "figma-developer-mcp", "--figma-api-key=TOKEN", "--stdio"]
    }
  }
}
```

阶段之间只通过文件通信；定时提醒这类增强件即使全部删掉，流程照样成立。哪天要迁去另一个同类智能体工具，本质上是拷贝文件夹、换一份配置的事，预估半天以内。

反过来验证：当初那版多智能体方案，智能体定义和编排协议全是平台私有物，迁一次等于重写一次。

## 三次否定，三次减法

回头看，整个推演不是在做加法，而是连续三次做减法：

![](https://pic1.zhimg.com/v2-846d53a6ee8b0f024544755c1c8991fe_r.jpg)

AI 流水线这件事，难的从来不是让 AI 干活，那是它天生会的。难的是让它知道自己在整条流程里站在哪一步，卡点前精准停下来，把状态原封不动存好，等审核人员回来说一句"通过"或者"驳回"。

你所在团队搭 AI 工程化体系时，有没有聊着聊着被推翻了的反直觉的方案？评论区聊聊，说不定能帮别人少走一段弯路。
