**"LLM Wiki"（受 Andrej Karpathy 那条著名 gist 启发：让 LLM 把知识"编译"进一张持久化、互相链接的 wiki，而不是在每次查询时用 RAG 重新推导）。**

## **1. OpenKB（VectifyAI）**

**定位**：CLI 工具，把原始文档"编译"成结构化、互链的 wiki，底层检索引擎是自家的 PageIndex。

**AI 框架/技术栈**

- Agent 框架：**OpenAI Agents SDK**（通过 LiteLLM 支持非 OpenAI 模型）
- 多模型网关：**LiteLLM**（可接 OpenAI / Claude / Gemini 等）
- 长文档索引：**PageIndex**（自家项目，向量数据库无关的"推理式检索"，把长 PDF 建成层级树索引，而不是切块+embedding）
- 文档转换：**markitdown**（微软开源，短文档转 Markdown）
- CLI 框架：Click；文件监听：watchdog

**特殊架构**

- **双层架构**：Wiki Foundation（编译/维护知识）+ Generators（query/chat/Skill Factory 等消费层）
- **无向量数据库（Vectorless）**：长文档不做 chunk+embedding，而是用 PageIndex 构建目录树，LLM 像人一样"翻目录"做推理式检索
- **Skill Factory**：可以从 wiki 中蒸馏出可移植的 Agent Skill（SKILL.md + references），供 Claude Code / Codex 等直接安装使用
- <br>

![](https://picx.zhimg.com/v2-39e884f0f7eac1a05fa938ca9f033a25_r.jpg)

**创新点**

1. 用 PageIndex 的"推理式检索"取代传统向量检索，解决长文档 context rot 问题
2. 把 wiki 页面反向"蒸馏"成 Agent Skill，实现"一本书 → 一个数字专家"
3. 遵循 Google 的 Open Knowledge Format（OKF）schema，便于知识互通
4. 原生兼容 Obsidian，wiki 即纯 Markdown + wikilink

## **2. SAG（Zleap-AI）**

**定位**：不是 wiki 类产品，而是一套"下一代 RAG"检索技术（论文 SAG）配套的开箱即用文档检索工作台。

**AI 框架/技术栈**

- 全 TypeScript 栈：React + Vite + Tailwind（前端）、**Fastify**（后端 HTTP API）
- **MCP TypeScript SDK**：项目可作为 MCP Server 供外部 Agent 调用
- 数据层：**PostgreSQL + pgvector**（全文检索 + 向量 + SQL 多跳查询）
- 模型：OpenAI 兼容的 LLM / Embedding / Rerank API（示例用 qwen3.6-flash + qwen3-rerank）

**特殊架构**

- 核心创新是检索结构：`chunk → event`，`chunk → entities`，`event ↔ entities`。每个 chunk 只抽取**一个完整事件**和**多个实体**，用实体做索引入口，用事件保留完整语义单元，从而支持"匹配事件后沿关系多跳召回"，而无需重建重量级知识图谱
- 提供 **Fast 模式**（纯 BM25/全文匹配 + 多跳扩展 + rerank，无需 LLM 抽取查询实体）和 **Standard 模式**（LLM 抽取查询实体 + 多路召回 + LLM rerank）回→LLMrerank带引用的回答+检索轨迹MCPServer暴露给外部Ag<br>

![](https://pica.zhimg.com/v2-cc190f32d107ae781d27b47bdf098f6e_r.jpg)

**创新点**

1. 用"事件+实体"轻量结构替代重量级知识图谱，兼顾多跳召回能力与更新/重建成本
2. Benchmark 数据显示相较 HippoRAG 2，在 HotpotQA / 2WikiMultiHop / MuSiQue 上 Recall@2 平均提升约 16.4%
3. 检索轨迹（trace）、原始模型调用日志全部可视化，便于调试 RAG pipeline
4. 每个项目自动暴露独立 MCP 配置，外部 Agent 可直接绑定项目 ID 调用

## **3. axiom-wiki**

**定位**：Node.js/TypeScript 实现的 LLM Wiki CLI + 交互式 Shell，"自己维护自己"的个人知识库。

**AI 框架/技术栈**

- 多 LLM 提供商：Gemini（推荐，免费额度）、OpenAI（含 OAuth）、Anthropic、OpenRouter、DeepSeek、Groq、Mistral、Ollama（本地）
- 混合语义检索：**Orama**（关键词+向量混合搜索库），支持 Gemini/OpenAI/Ollama embedding
- MCP：内置 MCP Server，供 Claude Code / Cursor 调用 wiki 工具

**特殊架构**

- **增量编译**：源文件按 SHA-256 哈希追踪，`ingest` 时跳过未变更文件
- **双层维护机制（Tier 1 / Tier 2）**：Tier 1 是确定性维护（重命名检测、标记过期），Tier 2 是基于 Agent 的重写（当底层代码/内容变化时让 wiki 内容跟着变）
- **autowiki**：让 Agent 自主探索一个项目/文档目录，自行决定要建哪些页面，批量构建 wiki（适用于代码库、公司文档、个人笔记等）
- 本地项目 wiki（`axiom/` 目录）与全局 wiki 可并存

![](https://pic3.zhimg.com/v2-ef01e45e42b758d59d70b8bfb98c6116_r.jpg)

**创新点**

1. Tier1/Tier2 混合维护策略，用确定性规则处理简单情况、Agent 只在真正需要理解语义时介入，降低成本
2. `autowiki` 让 wiki 构建从"人工投喂文档"进化为"Agent 主动探索代码/文档目录"
3. 完整的 REPL + 斜杠命令 + 成本追踪（`wiki/usage.log`）体验，工程化程度高

## **4. deepwiki-open（AsyncFuncAI）**

**定位**：面向"代码仓库"的 AI Wiki 生成器——输入一个 GitHub/GitLab/Bitbucket 仓库地址，自动生成带架构图的可视化 Wiki + Chat 问答。

**AI 框架/技术栈**

- 后端：Python + **FastAPI**，前端 Next.js + React
- RAG 引擎：使用 **AdalFlow**（作者自研/依赖的 RAG 框架，数据缓存在 `~/.adalflow`）
- 多模型 Provider 系统：Google Gemini / OpenAI / OpenRouter / Azure OpenAI / 本地 Ollama，可插拔切换
- Embedding：OpenAI / Google AI / Ollama 可选

**特殊架构**

- **克隆仓库 → 代码结构分析 → 代码 Embedding → RAG 问答 + 文档生成 → Mermaid 图**的流水线
- **Ask（RAG 问答）+ DeepResearch（多轮深度研究，最多迭代 5 轮，含研究计划/更新/结论三阶段）** 双模式
- 生成的架构图直接是 **Mermaid** 语法，前端用专门的 `Mermaid.tsx` 组件渲染

![](https://pic3.zhimg.com/v2-d069e30c067dbf035252bd99eaeeb47e_1440w.jpg)

**创新点**

1. 专注"代码仓库"这一垂直场景，把 RAG + 代码理解 + 自动生成 Mermaid 图三者打通，是所有项目里唯一"自动画图"的
2. DeepResearch 的多轮自动继续研究机制（计划→更新→结论），比一次性问答更适合复杂架构类问题
3. Provider 抽象层做得非常完整，是这批项目里模型可插拔性最强的实现之一

## **5. Graphiti（getzep）**

**定位**：不是 wiki 应用，而是给 Agent 用的**时序上下文图谱（Temporal Context Graph）**引擎——Zep 记忆系统的开源内核。

**AI 框架/技术栈**

- 纯 Python 核心库 `graphiti-core`，LLM 客户端支持 OpenAI（默认，且要求 Structured Output）、Anthropic、Gemini、Groq，以及任意 OpenAI 兼容端点（Ollama/vLLM/本地模型）
- 图数据库后端可插拔：**Neo4j / FalkorDB / Amazon Neptune**（Kuzu 已弃用）
- 提供 **MCP Server** 和 **FastAPI REST Service** 两种服务化形态

**特殊架构**

- **双时态（bi-temporal）事实管理**：每条事实（三元组 Entity→Relation→Entity）带有效窗口，信息变化时旧事实被"失效"而非删除，可查询"现在为真"或"历史某时刻为真"
- **Episode（情节）溯源**：所有派生实体/关系都能追溯回产生它们的原始 episode（原始数据流），保证可审计
- **Prescribed + Learned Ontology**：既可以用 Pydantic 模型预先定义实体/边类型（prescribed），也可以让结构从数据中自然涌现（learned）
- **增量式构图**：新数据实时并入图谱，无需批量重算——这是与传统 GraphRAG 最大的架构差异MCPServerFastAPIRESTService<br>

![](https://pic3.zhimg.com/v2-fd35fa85fd7ba8479618d2e24aaec7ce_r.jpg)

**创新点**

1. 双时态事实建模是本质创新——真正解决了"知识会变化"这一 GraphRAG 长期回避的问题
2. 增量式构图完全避免批量重算，查询延迟做到亚秒级，适合生产级 Agent 记忆场景
3. Prescribed/Learned 混合本体策略，兼顾工程可控性与灵活性
4. 论文实证支撑（Zep: A Temporal Knowledge Graph Architecture for Agent Memory, arXiv:2501.13956），已被证明是 SOTA Agent Memory 方案之一

## **6. GraWiki（maddataanalyst）**

**定位**：早期阶段的开源 Python 项目，把 GraphRAG 式知识抽取和 Karpathy 的"LLM Wiki 式 Agent 记忆"两个思路合并到一个图数据库facade中。

**AI 框架/技术栈**

- 纯 Python，核心 facade 类 `grawiki.GraphRAG`
- 图数据库后端：**FalkorDB**（含本地文件版 FalkorDBLite）或 **Memgraph**（Bolt协议，去重需 MAGE 镜像）
- 与 `pydantic_ai.Agent` 集成做记忆召回演示

**特殊架构**

- 模块化分层：`doc_processing`（切块）→`graph`（schema+LLM抽取+prompt）→`db`（后端无关 Cypher 引擎，工厂模式 `create_graph_db` 切换 FalkorDB/Memgraph）→`retrieval`（检索策略）→`similarity`（去重）→`rag`（对外 facade）
- **`__memory__` 节点**：Agent 的输出可作为专门的记忆节点写回图谱，并与已抽取实体关联，后续可"回忆"（recall）
- **去重工作流**：语义 key 碰撞检测 + 可插拔相似度匹配器 + facade 级合并操作，用于清理重复实体

![](https://pica.zhimg.com/v2-e6551586d324c9a9029850602747a116_r.jpg)

**创新点**

1. 把 GraphRAG 抽取流程和 Agent 记忆（`remember`/`recall`）显式统一为同一图谱，而非两套系统
2. 后端无关的 Cypher 引擎抽象，通过工厂函数一键切换 FalkorDB/Memgraph，工程上比较克制、干净
3. 项目虽小（早期阶段），但把"重复实体去重"作为一等公民能力单独暴露，是很多同类项目缺失的一环

## **7. Knowledge Catalog（GoogleCloudPlatform）**

**定位**：Google Cloud 官方的企业级数据目录/元数据管理平台（原 Dataplex）的工具与样例仓库，面向"给 AI Agent 提供企业数据语义上下文"。

**AI 框架/技术栈**

- 仓库本身是工具/Agent/样例集合：`agents/`、`okf/`（Open Knowledge Format）、`samples/`、`toolbox/`
- 与 **Gemini** 深度集成（"Gemini-powered data catalog"）
- 支持本地和远程 **MCP** 集成
- 语言构成：Python 61% / TypeScript 24% / HTML 15%

**特殊架构**

- 与前面几个"个人/项目级 wiki"完全不同的量级：面向**企业整条数据资产链**（BigQuery、AlloyDB、Spanner、Cloud SQL、Firestore、Looker 等结构化数据源 + 第三方目录如 Ab Initio/Collibra/Datahub）
- 自动从 schema、日志、BI 模型、非结构化文档中抽取语义，构建**动态上下文图谱（Context Graph）**，作为企业级"Ground Truth"供 Agent 查询
- 提出并推行 **Open Knowledge Format (OKF)** 作为跨系统知识共享的开放 schema——本报告中的 OpenKB 项目也遵循此 schema，说明这套体系正在成为业界事实标准<br><br>

![](https://pica.zhimg.com/v2-c92f1013f32505d683d11022c79108ac_r.jpg)

**创新点**

1. Discovery Agent 的"语义分解"检索超越普通语义相似度匹配，能拆解复杂查询意图后再检索
2. 推出 Open Knowledge Format 作为跨产品/跨厂商的知识共享标准，具有生态位意义（本报告其它开源项目已开始跟随）
3. 是唯一一个把"数据治理（governance/policy/lineage）"和"AI Agent 语义检索"结合在同一底座里的项目，定位企业级而非个人级

## **8. llm-wiki-agent（SamurAIGPT）**

**定位**：极简主义的"零依赖" LLM Wiki——没有独立的后端服务，直接把 **Claude Code / Codex / Gemini CLI / OpenCode 本身**当作运行时。

**AI 框架/技术栈**

- **没有专属 AI 框架**：不调用任何模型 API，而是依赖用户已经在用的编码 Agent（Claude Code 读 `CLAUDE.md`，Codex/OpenCode 读 `AGENTS.md`，Gemini CLI 读 `GEMINI.md`）
- 文档转换用 **markitdown**（自动把 PDF/DOCX/PPTX/XLSX 等转 Markdown 再摄取）
- 无需 API Key、无需 Python 环境搭建

**特殊架构**

- **"配置即程序"架构**：整个项目本质是一套 Markdown 指令文件（各 Agent 的入口说明）+ 一批独立 Python 脚本工具（`health.py` 确定性结构检查、`lint.py` 语义质量检查、`build_graph.py` 生成 wiki 关系图）
- Agent 直接按照约定的 frontmatter schema（`type: source|entity|concept|synthesis`）读写 `wiki/` 目录下的 Markdown 文件，无中间服务层
- 提供 Claude Code 专属斜杠命令（`/wiki-ingest`、`/wiki-query`、`/wiki-lint`、`/wiki-graph`），其它 Agent 用自然语言触发词等价替代<br>仅局部调用)从wiki综合回答<br>

![](https://picx.zhimg.com/v2-5418b2ae8932ca0a726815091950a9eb_r.jpg)

**创新点**

1. **"Agent-as-Runtime"** 架构：不写任何模型调用代码，把宿主编码 Agent 本身当作推理引擎，彻底省去 API Key/框架依赖，是这批项目里工程量最小、可移植性最强的实现思路
2. 用纯 Markdown 约定（而非代码）定义整个系统行为，天然跨 Agent 生态（同一套仓库同时兼容 Claude Code/Codex/Gemini CLI/OpenCode）
3. 确定性脚本（health.py）与 LLM 语义检查（lint.py）分离，降低不必要的模型调用成本

## **9. llmwiki（lucasastorian）**

**定位**：Karpathy LLM Wiki 概念的完整产品化实现——支持本地/托管双模式，配 Chrome 剪藏插件、Next.js 前端、MCP 集成。

**AI 框架/技术栈**

- 后端：Python API + **MCP Server**（`mcp/` 目录，独立进程）
- 前端：**Next.js** Web App
- 文档转换：LibreOffice（Word/PPT）、Mistral OCR（可选，用于高质量 PDF 表格识别）
- 存储：本地模式 SQLite + 文件系统；托管模式 **Supabase (Postgres) + S3**
- 通过 **MCP** 连接 Claude.ai / Claude Cowork / Claude Code / Codex 等任意 MCP 客户端

**特殊架构**

- **VaultFS 抽象层**是核心设计：同一套 wiki 操作（read/create/edit/append/delete/lint/search）在本地模式跑在 SQLite+文件系统上、在托管模式跑在 Postgres+S3 上，对 Claude 的工具调用完全透明
- **三类客户端、两个入口服务**：Claude 通过 MCP、Web App 通过 HTTP API、Chrome 插件通过 HTTP API，全部汇聚到 VaultFS
- **Claude Routine（定时任务）驱动"自我维护"**：设置夜间自动运行的 prompt，让 Claude 每晚自动读取新增的剪藏/上传，更新受影响页面并写入 log.md——这是"自维护"从功能变成基础设施能力的关键
- Chrome 插件带高亮和批注，批注与原文一起进入摄取管线，Wiki 记录的不只是"读了什么"，还有"当时怎么想的"<br>

![](https://pica.zhimg.com/v2-ea243cd2e6fcb4cf3b945f2b132b1d48_r.jpg)

ClaudeRoutine定时任务(夜间自动运行)<br>

**创新点**

1. VaultFS 一套接口两套后端的设计，让"自托管"和"云托管"在同一代码路径下无缝切换，工程成熟度在这批项目里最高
2. 把"定时任务（Claude Routine / Desktop Scheduled Task）"正式纳入产品架构，使 wiki 真正做到"自维护"而不依赖用户手动触发
3. Chrome 插件把高亮/批注也当作一等公民摄取内容，捕捉"阅读时的思考过程"而不仅是原文
4. 工具集设计克制（guide/list/search/read/create/edit/append/delete/lint 九个工具），且 `overview.md`、`log.md` 被保护禁止删除，体现了对 wiki 完整性的工程约束

## **10. obsidian-wiki（Ar9av）**

**定位**：和 llm-wiki-agent 同源思路——用"Skill 文件"驱动任意编码 Agent，在 **Obsidian vault** 里构建和维护"数字大脑"。

**AI 框架/技术栈**

- **没有独立后端/模型调用**：核心是 `.skills/` 目录下的一组 Markdown Skill 文件，被 Claude Code / Cursor / Windsurf / Codex / Gemini CLI / Kiro / GitHub Copilot 等十几种 Agent 读取执行
- 配套一个轻量 Python 包 `obsidian-wiki`（pip 安装），仅用于：写全局配置（`~/.obsidian-wiki/config`）、把 skill 文件**软链接**进各 Agent 的 skill 目录、提供 `doctor` 等本地诊断命令
- Obsidian 本身作为可视化层（图谱视图、wikilink 原生渲染）

**特殊架构**

- **Manifest 增量追踪**：`.manifest.json` 记录每个已摄取源文件的路径、时间戳、产出了哪些 wiki 页面，支持增量更新与状态查询
- **多 vault 管理**：`wiki-switch` 命令支持多个 `~/.obsidian-wiki/config.<name>` 配置文件，`@name` 前缀可在任意目录下把命令路由到指定 vault
- **"Dream Cycle"式自我巡检**（`wiki-lint --consolidate`）：Agent 自主修复断链、补齐孤儿页交叉引用、纠正生命周期状态、降级过期边缘页面、统一标签别名、添加矛盾标注——全部先 dry-run 展示 diff，用户确认后才写入
- **重要性分层（tier: core/supporting/peripheral）**：影响 `wiki-query`/`wiki-context-pack` 的相关性排序
- **Staged writes 模式**

：可选开启后所有写操作先进暂存区，最后合并成一次 commit，保持 git 历史干净<br>

![](https://pica.zhimg.com/v2-b418debe4e00e990544a68451595cc26_r.jpg)

**创新点**

1. 与 llm-wiki-agent 同属"Agent-as-Runtime"流派，但更进一步支持了近 15 种编码 Agent 的自动 skill 注册（symlink 到各 Agent 的 skill 目录，`pip install -U` 全局升级）
2. "Dream Cycle"式自我巡检是这批项目里对"wiki 自我修复/自我优化"抽象程度最高的实现，明确带 dry-run + 用户确认的安全阀
3. 重要性分层（tier）机制把"页面重要性"显式建模，用于相关性排序，是简单粗暴的全文检索之外少见的排序信号
4. 多 vault + `@name` 路由，解决了个人多身份（工作/生活）知识库隔离的实际痛点

## **11. Synthadoc（axoviq-ai）**

**定位**：定位为"传统 RAG 的透明、人类可读替代方案"，强调**摄取时编译（ingest-time compilation）而非查询时合成（query-time synthesis）**，四种接口齐全（CLI/Obsidian/Web UI/MCP）。

**AI 框架/技术栈**

- 多 Provider：Gemini Flash（默认，免费额度）、Ollama（本地）、DeepSeek，以及可以直接复用已有编码工具订阅的 **Claude Code / OpenCode CLI Provider**（无需单独 API Key）
- 前端：**Obsidian 插件**（TS 编译产物随包分发，也可 `synthadoc plugin upgrade` 单独升级）
- 支持中日韩多语言查询

**特殊架构**

- **Orchestrator + 子 Agent 编排**：Orchestrator 派发并行的 `IngestAgent` / `QueryAgent` / `LintAgent` 子 Agent，并带成本护栏（cost guards）和重试退避（retry backoff）
- **3 层懒加载能力体系（3-tier lazy-load capability system）**：允许通过插件式接口注入自定义 skill 和 hook，且保证核心系统稳定性不受扩展影响（按需加载，不常驻）
- **矛盾检测 + 孤儿页检测 + 引用生命周期过滤**：每个答案都带引用，wiki 页面有 lifecycle 状态，导出（5 种机器可读格式）时可按 lifecycle 过滤，仅导出"通过 lint 审核的活跃页"
- **完整溯源链导出**：与其它项目仅存储来源链接不同，Synthadoc 的导出携带完整 provenance chain（可再喂给下游 Agent/图分析工具）

**创新点**

1. "摄取时编译 vs 查询时合成"是全篇最鲜明的方法论旗帜，直接对标传统 RAG，强调预编译带来的矛盾检测、图遍历、离线可用等优势
2. Orchestrator 显式编排三类子 Agent 且带成本护栏，是这批项目里对"多 Agent 协作+成本控制"工程化最完整的实现之一
3. 可以直接复用已有 Claude Code/OpenCode 订阅作为 LLM Provider，免去单独计费，降低使用门槛
4. 导出携带完整溯源链，且按 lifecycle（是否通过 lint）过滤，是"可信知识资产"理念的具体落地

## **总体趋势与创新脉络**

1. **"编译时知识" vs "查询时检索"的范式转移**：OpenKB、axiom-wiki、llm-wiki-agent、llmwiki、obsidian-wiki、Synthadoc 六个项目全部明确宣称自己不是传统 RAG——知识在摄取阶段就被 LLM"编译"进结构化 wiki，交叉引用和矛盾检测提前完成，查询阶段只是"读书"而非"现推导"，这是这批项目共同的方法论根基（均可追溯到 Karpathy 的 LLM Wiki 构想）。
2. **"Agent-as-Runtime"的极简架构分支**：llm-wiki-agent 和 obsidian-wiki 走了一条更激进的路——完全不写模型调用代码，把宿主编码 Agent（Claude Code/Codex/Gemini CLI等）本身当作执行引擎，只用 Markdown 约定文件驱动，是"零基础设施"思路的代表。
3. **图谱底层技术的分化**：Graphiti（时序双态图）和 GraWiki（GraphRAG+记忆）代表的是给上层应用提供"知识图谱即服务"的基础设施层，而 SAG 则用更轻量的"事件+实体"结构规避了重量级图谱的更新成本，三者反映了知识图谱路线在"表达能力 vs 工程成本"上的不同取舍。
4. **MCP 成为事实标准接口**：除 deepwiki-open 和 Knowledge Catalog 外，几乎所有项目都把 MCP Server 作为核心对外接口，说明"给 Agent 提供可调用的知识库工具"已经收敛到 MCP 协议上。
5. **企业级与个人级的鲜明分层**：Knowledge Catalog 是唯一面向企业数据治理场景的项目，规模、合规性、多数据源联邦能力远超其余全部面向"个人/项目知识库"的项目，二者几乎不在同一竞争维度。
6. **多 Provider / 低成本策略普及**：新项目（axiom-wiki、Synthadoc）都主动支持免费额度模型（Gemini Flash）、本地模型（Ollama）以及"复用已有编码工具订阅"（Claude Code/OpenCode as Provider），反映出该品类正从"技术验证"走向"零成本可用性"竞争。
