triton repo中的hopper warp specialization实现代码路径如下：

[https://github.com/triton-lang/triton/blob/main/third_party/nvidia/hopper/lib/Transforms/WarpSpecialization.cpp](https://github.com/triton-lang/triton/blob/main/third_party/nvidia/hopper/lib/Transforms/WarpSpecialization.cpp)

总体来说，实现分如下几个步骤：

| 关键函数 | 备注 |
| --- | --- |
| doTaskPartition | 给关键的op分配taskId |
| doTaskIdPropagate | 将taskId沿着ud-chain传播 |
| doDataPartition | 将计算数据切分给每个consumer |
| doCodePartition | 建立 buffer/通信，生成各组独立代码 |
| doTokenLowering | 把抽象通信 token 下降为 barrier |

## 1. `doTaskPartition`

代码默认设置`numWarpGroup=3`，如果失败会尝试`numWarpGroup=2`：

![](https://pica.zhimg.com/v2-e17acd0e0cd600037dcb2de54aa95c50_r.jpg)

首先会遍历op，将其分为loads、stores、dots：

![](https://picx.zhimg.com/v2-868e6aeaa7e06ab20c4bc03178fd7c63_r.jpg)

接下来，producer的taskId为0，consumer的taskID为`[1,..., numWarpGroups-1]`，store op也是consumers。为producer和consumer设置taskIds：

- load：async_task_id=[0]
- dot：async_task_id=[1,2]
- store：async_task_id=[1,2]

这里的含义是，task0是producer，task1和task2是两个consumer

## 2. doTaskIdPropagate

经过第一步以后，计算图中的dot、`load`、store这些关键op的taskID确定了，不过计算图中还有其他op：`指针计算->load->layout-convert->dot->后处理->store` 。这一步的作用就是确定整个链路上其他op分别在那个task执行。

![](https://picx.zhimg.com/v2-57cec5f2f3ec69a8c26a6134f6a98bd9_r.jpg)
*有 result 的 op：合并所有 result 的 task 集合。没有 result 的 op：合并所有 operand 的 task 集合。最终写入 op 的 async_task_id 属性*

triton借助MLIR的稀疏数据流分析工具，定义了`TaskIdBackwardPropagation`， `Backward`是指向当前op/value的def端传播。 也即是说，如果某个Value被task1使用，那么产生这个Value的op也要在task1中执行，同时要继续传播给op的操作数。

那么如果一个计算同时被多个task需要呢，也就是说在传播过程中某个value可能有多个taskId，做法是取并集meet：

![](https://pic3.zhimg.com/v2-04d348335e1c4fe3c34514357cbb4d1c_r.jpg)

## 3. `doDataPartition`

针对dotOp，如果它的task_id有两个或者更多个，就是多个consumer共同计算这个dot，那么每个consumer计算哪部分呢？dot的A、B、acc、D需要怎么切？这是这个函数要解决的问题。

![](https://pic1.zhimg.com/v2-69110b25a42d80489ce923c86d9b9cf4_r.jpg)
*只针对task_ids &gt;=2的dotOp，这种才需要考虑切分*

![](https://pic4.zhimg.com/v2-1d653f8dcd2e1f90932fef42ae0e6253_r.jpg)
*使用 shapePerCTA，意味着候选检查依据的是一个 CTA 对应的 tile 大小，不直接拿整个 tensor 的 shape 判断*

Dot只考虑切分M或者N两个维度，要求每个slice的M不小于64，N不小于128，会优先尝试切M，调用`getSliceToPartition`，如果失败，再尝试切N。切分的份数等于consumer的个数：`numPartitions=asyncTaskIds.size()`

### `getSliceToPartition`

`getSliceToPartition` 这个接口分3个步骤进行：

1. `getBackwardSliceToPartition`

沿M切分Dot的输出时，那么A也应该切M，即dim0。继续追踪A的def（可能是各种类型的op），也应该规划def的切分dim。

2. `getForwardSliceToPartition`

Dot的D沿着M dim切分后，D的user，即D后续的elementwise和store也必须按照对应dim切分处理。

3. 补齐D的user的其他operand

D的user可能有多个operand， 需要继续处理其他operand

如果同一个op在不同的依赖路径上分别要求切不同的dim，即产生了冲突，那么会尝试`rematerializeOp`：也就是为不同切分方向分别构造所需对象。不能这样处理的冲突，会导致本候选方案失败。（当前只处理`LocalAllocOp`,`arith::ConstantOp`）

![](https://pica.zhimg.com/v2-f0bca03147348e7caebf43de14ed184e_r.jpg)
*右边代码可以看到：如果遇到这样的op，会撤销其def链上的op的切分方案*

### `rewriteRematerializedOps`

这个函数是在处理上述提到的`rematerializeOp`。具体来说，第一个方向会继续使用原来的op，所以for循环的迭代是从`i=1`开始；而另一个方向，则创建新版本，并替换：

![](https://pic3.zhimg.com/v2-4ddc2154fdfe70d91e0d73bcc7b4c310_r.jpg)

## 4. `doCodePartition`

这一步是把前面得到的 task id和数据切分方案，真正变成并发 warp-group 程序的阶段。它主要解决两件事：

1. 不同 task 之间原来的 SSA 数据依赖，怎样改成共享内存通信？
2. 怎样把混在一起的代码，放进各自的 `ttg.warp_specialize` region？

函数入口参数除了`funcOp`以外，还有一个`numBuffer`。调用时`numBuffer=numStages`. 函数内部分为如下几步：

### 4.1. `collectAsyncChannels` 找出跨 task 的通信边

`collectAsyncChannels` 主要从以下op出发：

- `LoadOp`
- `DescriptorLoadOp`
- 实现 `DotOpInterface` 的操作

然后查看users，将 producer 的 taskID 从使用者任务集合中移除：

![](https://pic1.zhimg.com/v2-45e293c023a00df2eadef1ad2cace190_r.jpg)

### 4.2. `groupChannels`

```cpp
  // Step 2: group channels
  // -  each entry of the channelsGroupedByProducers is keyed by the srcOp.
  // -  each entry of the channelsGroupedByConsumers is keyed by the dstOp.
  DenseMap<Channel *, SmallVector<Channel *>> channelsGroupedByProducers;
  DenseMap<Channel *, SmallVector<Channel *>> channelsGroupedByConsumers;
  SmallVector<Channel *> orderedChannels;
  groupChannels(channels, channelsGroupedByProducers,
                channelsGroupedByConsumers, orderedChannels);

```

按 producer/consumer op 分组，不是简单按 taskID 分组。分组有两种方式：

1. 按producer op：如果一个producer被多个consumer使用，那么多个channel共用同一个buffer
2. 按consumer op：如果load_A和load_B均用于同一个dot，A和B可以共用一组同步对象barrier

### 4.3. `reorderProducerOps` 调整 producer 的执行顺序

该函数是让某个 consumer 所需的数据尽早准备齐，减少它等待其他无关加载的时间。

1. 按 Channel 的第一个 consumer taskID 分组，小 taskID 优先。
2. 组内按 consumer 数量升序排序。
3. 移动 producer。
4. 将 producer 的反向依赖链移动到它前面。

![](https://pic1.zhimg.com/v2-da7795d65603be12bc6a8488b51f97ce_r.jpg)

例如：

```text
原顺序：
加载 consumer 1 的 A
加载 consumer 2 的 A
加载 consumer 1 的 B
加载 consumer 2 的 B

调整目标：
加载 consumer 1 所需数据
加载 consumer 2 所需数据
```

### 4.4. 给循环增加通信计数器

![](https://pic3.zhimg.com/v2-04793491349e891b056269cf0317b0da_r.jpg)

原始的for循环的循环变量有可能不从0开始，也可能按照BLOCK_K迭代，并不能代表buffer管理所需表征当次循环时该通信作用域第几次执行，所以需要加入独立的`AccumCnt`。那么：

```cpp
bufferIdx = accumCnt % numBuffers  // bufferIdx 选择槽位
phase     = (accumCnt / numBuffers) & 1 // phase 区分同一槽位的不同轮次，避免复用 barrier 时把旧完成状态当成新完成状态

```

### 4.5. `createBuffer`分配通信buffer

对每个 producer 分组创建一组 buffer，并将该组所有 Channel 映射到同一个 buffer。

### 4.6. `insertAsyncCopy` ：lowering load

按 producer 分组，把跨 task 的数据传递改成“producer 写共享 buffer，consumer 从共享 buffer 读取”，并记录新的生产、消费操作，供后续插入同步。

普通 `tt.load`：改成异步 global→shared copy：

```text
改写前：
producer：
    %x = tt.load(%ptr)
consumer：
    use(%x)

改写后：
producer：
    %writeView = memdesc_index(%buffer, %bufferIdx)
    async_copy_global_to_local(%ptr, %writeView)

consumer：
    %readView = memdesc_index(%buffer, %bufferIdx)
    %x_shared = local_load(%readView)
    use(%x_shared)
```

Descriptor load留给 TMA 通信阶段；非 load 的 tensor producer则通过 local store/load 传递：

```text
producer：
    %x = compute(...)

consumer：
    use(%x)

改写为：
producer：
    %x = compute(...)
    %writeView = buffer[idx]
    local_store(%x, %writeView)

consumer：
    %readView = buffer[idx]
    %x_shared = local_load(%readView)
    use(%x_shared)
```

### 4.7. `createToken`

为每个 consumer 通信分组创建同步资源：普通路径创建 NVWS token，TMA/Gen5 路径还会创建硬件 completion barrier，并把这些资源记录到`tokenMap`。

前面的`insertAsyncCopy`已经建立了数据通路：`producer → shared buffer → consumer`。但还缺两个条件：

- consumer 读之前：数据是否已经写完？
- producer 覆盖之前：consumer 是否已经用完？

### 4.8. `insertAsyncComm`插入Async通信op并lowering TMA loads

把`createToken`准备好的同步资源放到正确的生产、消费位置，建立“数据就绪”和“buffer 可复用”的协议，同时完成 TMA load 和 Gen5 MMA 的特殊同步改写。前面的`insertAsyncCopy`建立了数据通路，`createToken`创建同步资源，`insertAsyncComm`把同步操作接到数据通路上。

函数会找出同步区间的起止点：

```text
headProducer：第一处生产操作
tailProducer：最后一处生产操作
headConsumer：第一处消费操作
tailConsumer：最后一处消费操作

找到同步区间起止点后，同步协议围住整个区间：

acquire
  producer A
  producer B
commit

wait
  consumer 使用 A、B
release
```

![](https://pica.zhimg.com/v2-16e27da0928d7361db9c2bf4d6a9198a_r.jpg)

### 4.9. `foldLocalLoads` localLoad优化

![](https://picx.zhimg.com/v2-7cd0f77add62a40819fc3fe0d626d49f_r.jpg)
*属于同一个task的localLoad -&gt; localAlloc，让后面的op直接使用原shared-memory buffer，不必再使数据在shared与寄存器之间往返*

### 4.10. `specializeRegion`

按照已有的 `async_task_id` 标签，把混在一起的程序分进 `ttg.warp_specialize` 的不同 region，真正形成各 warp group 独立执行的代码。

```text
ttg.warp_specialize
├── default region：task 0，producer
├── partition 0：task 1
└── partition 1：task 2
```

## 5. `doTokenLowering`

`doTokenLowering`把抽象的 NVWS token 同步协议，展开成 shared-memory 中的 full/empty mbarrier，以及对应的等待、到达操作。

该函数首先会把先前创建的Token变为两组barrier：full和empty。其次将4个op lowering为barrier op：

| 原操作 | Lowering to ... | 备注 |
| --- | --- | --- |
| ProducerAcquire | WaitBarrier | 等待上一轮消费结束 |
| ProducerCommit | ArriveBarrier | 通知数据就绪 |
| ConsumerWait | WaitBarrier | 等待本轮数据就绪 |
| ConsumerRelease | ArriveBarrier | 通知槽位可复用 |

最终IR结构会变成：

```text
WS 外：
    分配 full/empty 数组
    初始化各 barrier
    CTA 同步

producer：
    wait empty
    生产数据
    通知 full

consumer：
    wait full
    使用数据
    arrive empty
```
