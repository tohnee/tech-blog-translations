前一篇讲了 FSDP1 的 FlatParameter 和 FSDP2 的 DTensor。

[FSDP 的演进：从 FSDP1 到 FSDP2](https://zhuanlan.zhihu.com/p/2068097867408005084?share_code=10z0PfGX6DQeL&utm_psn=2071112933996761791)

原语讲清楚了，问题就转到另一个层面：真训一个 70B 甚至 MoE 1T 的模型，光调一句 `fully_shard(transformer_block)` 是远远不够的。至少要回答下面这些问题：

- TP、CP、EP、PP、DP 这五个并行维怎么排布在同一组 GPU 上？
- TransformerBlock、Embedding、LayerNorm、LM Head 各自该不该 wrap？
- 混合精度、激活重算、`torch.compile`、MoE 的 all-to-all，这几件事之间的顺序怎么定？
- 反向时的 reduce-scatter、all-gather 怎么跟下一层重叠？
- MoE 的专家梯度和非专家梯度的通信组是不是一个？除数对不对？

这些问题的答案都在 TorchTitan 和 Megatron-LM 的源码里。

两个项目给出的答案几乎相反。TorchTitan 完全依赖 FSDP2、DTensor、torch.compile 这套 PyTorch 原语；Megatron 走的是手写连续 buffer、自研 DistributedOptimizer、TP 全部用 autograd.Function 加环境变量控制的路线。

这一篇拆成三段。

- 第一段看 TorchTitan 是怎么把 FSDP2 加 DTensor 落到一个能训 MoE 的框架里的。
- 第二段看 Megatron 走的那条几乎相反的路。
- 第三段做对比分析，看它们各自给了什么、什么场景该选哪个。

### 1. TorchTitan：把 FSDP2 原语拼装起来

FSDP2 只提供 mesh、DTensor、`fully_shard`、`parallelize_module` 这些原语。

TorchTitan 要把这些原语组合成能跑 TP + CP + FSDP + EP + PP 五维并行的流水，就得回答一长串”在哪一步做什么”的问题。

### 1.1 并行优化的顺序

打开 `torchtitan`中 llama3 中 `parallelize.py`文件，其中最重要的就是 `parallelize_llama` 这个函数。

![](https://picx.zhimg.com/v2-1b03e1a17fc1623143eb240285130fa1_r.jpg)

它把一个原始的 `nn.Module` 改造成可以跑五维并行的模型，按顺序做了这几件事：

```text
1. world_mesh = parallel_dims.world_mesh
   (从 ParallelDims 取出一个多维 mesh)

2. if tp > 1:
       apply_tp(model, world_mesh["tp"], ...)
       maybe_enable_async_tp(...)

3. if activation_checkpoint enabled:
       apply_ac(model, ...)

4. if torch.compile enabled:
       apply_compile(model, ...)

5. if FSDP enabled:
       apply_fsdp(model, world_mesh[...], MixedPrecisionPolicy(...), ...)
   elif dp_replicate > 1:
       apply_ddp(model, ...)
```

这个顺序不是任意的。

注释里写得很直白：”turn on per-TransformerBlock compile after AC wrapping and before FSDP”。原因是：

- AC 在最外层，编译看到的图是 `checkpoint_wrapper(TransformerBlock)`。
- compile 在中间，编译对象是一个完整的 TransformerBlock，因为它结构重复，缓存命中率高。
- FSDP 在最外层，它的 forward hook 不在编译图里，否则 Dynamo 看到 FSDP 的 all-gather 就会断图。

这个先后顺序是 TorchTitan 跑通 `compile + FSDP + AC` 同时启用的关键。TP 决定单层内部怎么切，AC 决定 block 怎么省显存，compile 优化稳定的 block 计算，FSDP 最后负责跨 rank 的参数生命周期。每一层只处理它该处理的那部分复杂度。

### 1.2 FSDP wrap 的粒度

`apply_fsdp` 的核心是这几行：

```text
if model.tok_embeddings is not None:
    fully_shard(model.tok_embeddings, **fsdp_config,
                reshard_after_forward=reshard_after_forward)

for layer_id, transformer_block in model.layers.items():
    fully_shard(transformer_block, **fsdp_config,
                reshard_after_forward=reshard_after_forward)

# 注释: 'do not reshard the last layers by default since FSDP would prefetch them
# immediately after the forward pass'
if model.norm is not None and model.output is not None:
    fully_shard([model.norm, model.output], **fsdp_config,
                reshard_after_forward=reshard_after_forward_policy == "always")

fully_shard(model, **fsdp_config)
```

四组 wrap，每组的考虑不一样。

embedding 单独一组，参数量级和 transformer block 差得多，单独一组通信效率更高。

每个 TransformerBlock 单独一组，粒度刚好。一个 block 100M 到 500M 参数，一次 all-gather 量足够大、又不至于把显存撑爆。

norm 加 output 合成一组，且默认不 reshard。这是个非常工程化的决定。

norm 和 output（lm_head）是 forward 链路的最后一层，跑完立刻进 backward，如果 reshard 释放掉下一秒又要 all-gather 回来。注释直接写”FSDP would prefetch them immediately after the forward pass”，默认不释放，省一次 all-gather。

整个 model 再套一层。这是 FSDP2 的”root call”约定。最外层这个 `fully_shard(model, ...)` 负责 lazy init、`train()` 模式切换时的初始 unshard 调度。不套这层会出现前 N-1 个 block 是 FSDP 管理的但 model 本身不是的状态不一致问题。

`reshard_after_forward` 这个参数还有个隐藏的”default”档：没有 PP 时是 True，启用 PP 时是 False。PP 的微批会多次走同一组 stage，关掉 reshard 才能避免每个 microbatch 一次额外 all-gather。

### 1.3 TP 计划：经典 Megatron 风格

![](https://pic2.zhimg.com/v2-d37e910511b3ecf803daf542da9c5767_r.jpg)

TP 通过 `parallelize_module` 加 parallel_plan dict 实现。每个 TransformerBlock 的 plan 长这样：

```text
layer_plan = {
    "attention_norm": SequenceParallel(),
    "attention": prepare_module_input(
        input_layouts=(Shard(1), None, None, None),
        desired_input_layouts=(Replicate(), None, None, None),
    ),
    "attention.wq": colwise_parallel(),
    "attention.wk": colwise_parallel(),
    "attention.wv": colwise_parallel(),
    "attention.wo": rowwise_parallel(output_layouts=Shard(1)),
    "ffn_norm": SequenceParallel(),
    "feed_forward": prepare_module_input(
        input_layouts=(Shard(1),),
        desired_input_layouts=(Replicate(),),
    ),
    "feed_forward.w1": colwise_parallel(),
    "feed_forward.w2": rowwise_parallel(output_layouts=Shard(1)),
    "feed_forward.w3": colwise_parallel(),
}
```

Q/K/V/W1/W3 是 colwise（按输出维切），O/W2 是 rowwise（按输入维切）。这是 Megatron 经典 pattern，一对 `column → row` 内部只需要一次 all-reduce，而不是两次 all-gather 加 reduce-scatter。

`attention_norm` 和 `ffn_norm` 用的是 `SequenceParallel()`。语义是 activation 在 sequence 维上 sharded，norm 是 element-wise on seq dim，直接在本地分片上算，不需要 all-gather。配合 `prepare_module_input` 把 sequence-sharded 的 hidden 在 attention 入口 all-gather 回来、出口再 reduce-scatter 回去，整个 attention 块的入口 AG 和出口 RS 自动配对。

这套 plan 的妙处在于，FSDP2 加 TP 的复合靠的是 mesh，而不是手写胶水。TP 先于 FSDP 应用，`fully_shard` 拿到的参数已经是 DTensor（在 TP 维上 Shard），FSDP2 只是在 DP 维上再加一层 Shard，最终形成 `[Shard(dp), Shard(tp)]` 的二维 placement。这是 DTensor 抽象最直接的收益。

### 1.4 MoE 与 EP：TorchTitan 真正复杂的地方

![](https://pic2.zhimg.com/v2-1e83fa4a552f52b15cc01649de93193f_r.jpg)

llama4 的 MoE 是 TorchTitan 复杂度的一个 peak，展开看看。

**专家怎么切**。`ExpertParallel._partition_fn` 长这样：

```text
@staticmethod
def _partition_fn(name, mod, device_mesh):
    for name, param in mod.named_parameters(recurse=False):
        dist_param = nn.Parameter(distribute_tensor(param, device_mesh, [Shard(0)]))
        mod.register_parameter(name, dist_param)
```

`GroupedExperts` 的 `w1/w2/w3` 形状是 `(num_experts, hidden, ...)`，专家轴在 dim 0。

`Shard(0)` 就是把专家平均分给 EP ranks。64 个专家、EP=8 的话，每个 rank 持有 8 个完整专家。注意不是把单个专家的权重切碎，而是按专家轴切。单个专家本身不大，切碎以后 grouped GEMM 的优势会被通信成本吃掉。

**EP 加 FSDP 共存的麻烦**。MoE Transformer 里的参数有两类：普通 dense / shared 参数（attention、norm、embedding、router、shared experts 等），以及 routed experts 参数。dense / shared 参数通常在 EP 维度上是复制的，routed experts 参数按 expert ownership 分布在 EP ranks 上。两类参数的所有权、复制关系、梯度同步范围和运行时通信模式不同，不能用同一个 FSDP group 一把包完。

TorchTitan 的做法：

```text
if transformer_block.moe_enabled and ep_degree > 1:
    fsdp_mod_ep_config = fsdp_config.copy()
    fsdp_mod_ep_config["mesh"] = dp_mod_ep_mesh
    if dp_mod_ep_mesh.size() * ep_degree > num_experts:
        _experts_shard_placement_fn = lambda param: Shard(1)
    fully_shard(
        transformer_block.moe.experts,
        **fsdp_mod_ep_config,
        reshard_after_forward=reshard_after_forward,
        shard_placement_fn=_experts_shard_placement_fn,
    )
    transformer_block.moe.experts.set_gradient_divide_factor(gradient_divide_factor)

fully_shard(transformer_block, **fsdp_config, ...)
```

- 非专家参数走常规 `dp_shard_cp` mesh。
- 路由专家走 `dp_mod_ep_mesh = ("dp_replicate", "dp_shard_mod_ep")`，不含 `dp_shard_in_ep`，这一维已经被借走当 EP 用了。
- 如果 `dp_mod_ep × ep > num_experts`，专家轴切不下了，改切 dim 1。
- `set_gradient_divide_factor` 手动修正专家梯度的除数，让它和非专家梯度量纲一致。

`set_gradient_divide_factor` 的作用值得单独说一下。EP 把一部分 DP 维度借去做 expert ownership，expert 参数实际使用的 FSDP mesh 小于普通 dense 参数。如果沿用默认 FSDP mesh-size averaging，expert 梯度和非专家梯度的 scale 会不一致，导致 expert 更新偏大或偏小，进而影响早期路由稳定性。

**token 路由要一次 D2H sync**。MoE 真正运行时是 token dispatch：

```text
num_tokens_per_expert_group = all_to_all_single(
    num_tokens_per_expert, None, None, group=device_mesh.get_group())
num_tokens_per_expert_group = torch.ops._c10d_functional.wait_tensor(
    num_tokens_per_expert_group)

input_splits = (num_tokens_per_expert.view(ep_degree, -1).sum(dim=1)
                .to(torch.device("cpu"), non_blocking=True))
output_splits = (num_tokens_per_expert_group.view(ep_degree, -1).sum(dim=1)
                 .to(torch.device("cpu"), non_blocking=False))
...
routed_input = all_to_all_single_autograd(
    routed_input, self.output_splits, self.input_splits,
    device_mesh.get_group())
```

注意倒数第二行注释：”this would incur a device-to-host sync”。

MoE 跑起来必然有一次 D2H：先用一次小的 all-to-all 把”每个 rank 要发给我多少 token”传过来，落到 CPU 才能作为下一次 `all_to_all_single` 的 `output_splits` 参数。这是 MoE 性能的硬瓶颈之一，所有 MoE 实现都绕不开。因为 all_to_all_single 函数的 output_splits 是 cpu 参数。

**显式 prefetch 是 MoE 必备**。D2H sync 会打乱 FSDP2 的隐式 prefetch 顺序。FSDP2 的默认 prefetch 是基于 forward 执行顺序的，但 D2H 一同步，CUDA 流的实际顺序就跟代码顺序不一样了，这是因为 cudaMemcpy 是强同步的操作。

所以，TorchTitan 在 EP 启用时放弃自动，改为显式接管 prefetch：

```text
# NOTE: set up explicit prefetching when EP is enabled, as D2H syncs
# in EP could interfere with implicit prefetching in FSDP
if ep_degree == 1:
    return
transformer_block.set_modules_to_forward_prefetch(
    [next_transformer_block, next_transformer_block.moe.experts])
transformer_block.set_modules_to_backward_prefetch(
    [prev_transformer_block, prev_transformer_block.moe.experts])
```

同时 prefetch 两个模块是因为 TorchTitan 里 MoE block 是两层 FSDP：

- 外层 `fully_shard(transformer_block)` 管 attention/norm/router/shared_experts，
- 内层 `fully_shard(transformer_block.moe.experts)` 管 routed experts。

它们是两个不同的 FSDP module（具体原因如上，复制关系和通信模式不同），所以只 prefetch `next_transformer_block` 不够。

你必须同步把外层和内存的权重都预取搬过来。

关键点在于：这两个预取是并行发起的。虽然它们处在不同的 FSDP 通信组，但通过显式指定，CUDA 流可以在同一个“隐式等待窗口”（即 D2H Sync 导致 CPU 卡住的那段时间）里，把下一层的所有权重（外层+内层）全部准备就绪。

### 1.5 Mesh 构建：dp2ep 借位

最后我们来看看 `ParallelDims.build_mesh`。带 EP 时：

```text
if self.etp == self.tp:
    dp_shard_mod_ep = self.dp_shard * self.cp // self.ep
    dp_shard_in_ep = self.ep // self.cp
else:
    assert self.etp == 1
    dp_shard_mod_ep = self.dp_shard * self.cp * self.tp // self.ep
    dp_shard_in_ep = self.ep // (self.cp * self.tp)
```

这就是 TorchTitan 文档里说的 dp2ep Expert Parallel。

EP 维不是凭空增加的，而是从 `dp_shard`（必要时还有 `cp`、`tp`）里借出来的。64 个 GPU、`dp_shard=8, ep=4`，那 `dp_shard_mod_ep=2, dp_shard_in_ep=4`。EP 维度上的 4 个 rank，原本就是 dp_shard 维度上的 4 个 rank，只是换了个用法。

这里的借的意思就是我们 dense 依然保留 dp_shard, 只有在 moe 层会缩小其他维度，比如 etp == tp，表示 MoE 的每个 expert 沿用跟 dense 相同的 TP 度，这时 TP 那一维度不能借；etp == 1，表示 expert 内部完全不做 TP。这时候 tp 那一维在 dense 那边被用了、在 MoE 那边空着，可以借出来给 EP 用。

![](https://pic2.zhimg.com/v2-c12020e5addaf6c9a106dcb210084793_r.jpg)

所以，物理上 GPU 数量不变，只是同一组进程在不同维度上被解读成不同的通信组。这是 DTensor 的 mesh 抽象带来的强大灵活性，不需要为 EP 新开一组进程，只要换一个 mesh 维度的解读方式。

之后通过 `_flatten` 把多维 mesh 合并成单一逻辑维：

```text
mesh[tuple(dp_shard_cp_mesh_dim_names)]._flatten(mesh_dim_name="dp_shard_cp")
mesh[tuple(ep_mesh_dim_names)]._flatten(mesh_dim_name="ep")
```

后续代码就可以用 `world_mesh["dp_shard_cp"]` 直接拿到 FSDP 用的 mesh、`world_mesh["ep"]` 拿到 EP 用的 mesh，完全不需要关心底层有几维。

![](https://pica.zhimg.com/v2-ef67a7e334c16e89a0360c885bbcd126_r.jpg)

### 1.6 一些工程细节

除此之外还有一堆”原来还得这样”的小细节：

- 梯度累积不走 `no_sync`，而是每次 microbatch 都 reduce-scatter，在 loss 上预先除以累积步数（`rescale_accumulated_loss`）。数学上等价，工程上显存峰值不积压。
- MoE 下 `torch.compile` 需要打几个补丁：`capture_scalar_outputs=True`（token-choice 路由器有 unbacked symint）、跳过 `experts` 子模块（FSDP hook 会让 Dynamo 破图）、给 `_run_experts_grouped_mm` 的 token 维标 `mark_dynamic`（all-to-all 后 token 数随 batch 变）。
- `NoParallel` 专门处理”什么都不并行但参数要转成 DTensor”的场景。否则 router gate 这种 replicate 计算的 plain Tensor 和 DTensor 混用，fused optimizer 和 gradient norm clipping 会崩。

### 2. Megatron-LM：把每一步都手写一遍

Megatron 走的是完全相反的哲学。

它不依赖 PyTorch 的分布式抽象，从参数 buffer 到 optimizer 到 TP 通信全部自己写。这一节看它是怎么解决同样一组问题的。

当然严格来说 Megatron 有三套 “FSDP”, DistributedOptimizer、Megatron-FSDP 和 TorchFullyShardedDataParallel。

### 2.1 DistributedOptimizer 不是 Megatron-FSDP

Megatron 传统数据并行路径的核心是 `_ParamAndGradBuffer` 加 `DistributedOptimizer`。

核心思想一句话：所有参数的 `data` 和 `main_grad` 都拼成一个超大的 1D 连续 buffer，每个参数变成 buffer 上的一段 view。

![](https://pica.zhimg.com/v2-5cc311c57f1a25ab5a78fb5891cb6614_r.jpg)

```text
# 简化版
for param in params[::-1]:        # 反向遍历，跟 backprop 顺序匹配
    this_numel = param.data.nelement()
    param_start_index = pad_if_needed(param_start_index)
    param_end_index = param_start_index + this_numel
    self.param_index_map[param] = (param_start_index, param_end_index, bucket_id)
    bucket_params.add(param)
    if (param_end_index - bucket_start_index) >= bucket_size:
        finalize_bucket()
```

然后把 `param.data` 重新指向 buffer 上的 view：

```text
new_param_data = self._get(param.data.shape, param_start_index, buffer_type=BufferType.PARAM)
old_param_data = param.data
param.data = new_param_data
param.data.detach().copy_(old_param_data)
del old_param_data
param.main_grad = self._get(param.data.shape, param_start_index, buffer_type=BufferType.GRAD)
```

看到这里可能会愣一下：”这不就是 FSDP1 的 FlatParameter 吗？”是有几分像，但本质区别：

- FSDP1 的 FlatParameter 是整组参数的扁平 1D 张量，跨 rank shard 之后每个 rank 持有 1/N。
- Megatron 的 `_ParamAndGradBuffer` 是一个 rank 上完整的参数副本，所有参数拼一起，配 main_grad 副本。

Megatron 默认是 DDP 的内存布局，每个 rank 都有完整参数和梯度。FSDP 等价物靠的是上面套一层 DistributedOptimizer：

```text
DistributedOptimizer 把 buffer 的字节范围按 dp_world_size 等分；
每个 rank 只持有自己那段的 fp32 master 副本和 optimizer state。

reduce-scatter 把 main_grad 按字节范围切到每个 rank；
optimizer step 在各自的 1/dp_world_size 段上跑；
all_gather 把更新后的 bf16 权重广播回完整 buffer。
```

注意”字节范围”四个字。`DistributedOptimizer` 把 buffer 切分给 DP rank 时完全不管参数边界，一个 fp32 master 范围可能跨越好几个原始参数。`distrib_optimizer.py` 的注释里直接写：

> This conceptual partitioning of the grad buffer does NOT respect parameter boundaries, and as such it is assumed that each created range references a shard (or subset) of the full parameter.

一个 rank 上每个 optimizer param group 的 entry 是 `param.view(-1)[range.start:range.end]`，是一个 plain CUDA tensor，不是 DTensor，连参数概念都没保留。

这是 Megatron 的设计哲学：把模型当成一段带元信息的字节流来切，而不是一个有结构的张量图。

所以，DistributedOptimizer 准确的说是 ZeRO-1 只切 optimizer state，不切参数、不切梯度，通信量比 FSDP2 少了一半。

### 2.2 手写通信重叠：Bucket 加 Hook

Megatron 的 backward 通信重叠走的是纯手写的路。

`_ParamAndGradBuffer` 把整个 buffer 切成若干 bucket（默认 40MB 一个）。每个参数初始化时挂一个 grad_acc hook：

```text
def _make_backward_post_hook(self, param):
    def hook(*unused):
        if param in self.param_to_bucket_group:
            if param.grad is not None and not param.grad_added_to_main_grad:
                param.main_grad.add_(param.grad.data)
            param.grad = None
            if self.ddp_config.overlap_grad_reduce:
                self.param_to_bucket_group[param].register_grad_ready(param)
    return hook
```

`register_grad_ready` 递增 bucket 的就绪计数。当 bucket 内所有参数 grad ready，触发 `start_grad_sync()`：

```text
with _coalescing_manager(comm_group, async_ops=True) as cm:
    for idx, bucket in enumerate(self.buckets):
        if self.ddp_config.use_distributed_optimizer:
            grad_reduce_handle = dist_reduce_scatter_func(
                local_data_view, bucket.grad_data,
                op=reduce_op, group=comm_group, async_op=True)
        else:
            torch.distributed.all_reduce(
                bucket.grad_data, op=reduce_op,
                group=comm_group, async_op=True)
```

注意 `_coalescing_manager`。它把同一上下文内的所有 NCCL 调用合并发起。一个 bucket 内 100+ 个参数原本是 100+ 次小 RS，coalesce 之后是一次大 RS。

前向 all-gather 重叠是对称的。`_make_forward_pre_hook` 会等住”本参数所在 bucket 的 AG 完成”。同时 Megatron 维护一个 `next_param_gather_bucket_group` 链表，按反向 bucket 顺序：

```text
for i in range(1, num_bucket_groups):
    bucket_groups[num_bucket_groups - i].next_param_gather_bucket_group = (
        bucket_groups[num_bucket_groups - i - 1])
```

某个 bucket 收到 forward_pre 时，顺手把下一个 bucket 的 AG 发起出去。这就是手写版的 prefetch。

整套机制非常清晰，但和 FSDP2 的差别也非常清晰。

FSDP2 是每个 submodule 的 pre / post hook 自己触发自己的通信，PyTorch autograd 引擎保证顺序。Megatron 是手维护 bucket 边界、手维护 prefetch 链、手调 `_coalescing_manager`。

后者的好处是想做什么样的重叠都行，链表自己改。坏处是每出一个新的 case（比如 MoE 的 expert grad 走另一个组），你得手写一条新的链。

DistributedOptimizer 保住 DP 维度的通信量（跟 DDP 一样 2P），只切下最贵的 optimizer state。这个取舍在 Megatron 的典型 5D 并行下几乎是最优的。当你的参数能通过 TP + DP 装进单张卡剩余的显存里，那么 DistributedOptimizer 几乎是最优的。

如果还是装不下，例如 DP 维度大，可以考虑用 –use-custom-fsdp 打开 Megatron-FSDP。

### 2.3 Megatron-FSDP 是什么

Megatron-FSDP 是 Megatron-Core 自己实现的 custom FSDP。

它不是 PyTorch FSDP2 的简单包装。在 Megatron Bridge 里通过 `use_megatron_fsdp` 开启。

Megatron-FSDP 的训练 runtime 不是以 PyTorch FSDP2 或 DTensor 作为核心调度抽象。但它的 checkpoint 与 state_dict 路径会使用 `fsdp_dtensor`，也就是 PyTorch DTensor 加 Distributed Checkpoint 来保存 sharded state。

开启 `optim_grads_params` 后，rank 平时只持有自己负责的参数 shard。

某个 FSDP unit module 要执行时，Megatron-FSDP 会把这个 unit 需要的参数 all-gather 出来。这个 unit 的 forward、backward 用完后，再把 unsharded 参数释放掉。

`MegatronFSDP` 支持 ZeRO 0/1/2/3 四档（`no_shard / optim / optim_grads / optim_grads_params`），forward 与 backward hook 长得跟 FSDP2 很像：

```text
def _pre_forward_param_unshard(module, args, kwargs):
    self.all_gather_and_wait_parameters_ready(
        params=param_list, prefetch=True,
        prefetch_order=PrefetchOrder.FORWARD_PASS_ORDER)
    return args, kwargs

def _post_backward(module, *unused):
    if isinstance(module, tuple(fsdp_unit_modules)):
        if self.ddp_config.data_parallel_sharding_strategy == "optim_grads_params":
            release_module_parameters(module)
    if grad_reduce_every_bprop or is_last_microbatch or self.model_auto_sync:
        self.grad_reduce_pipeline.reduce_gradients(param_list, ...)
```

但底下用的还是 `BucketingPolicy + AllGatherPipeline + GradReducePipeline + FixedPoolAllocator + StorageResizeBasedBucketAllocator`，没有任何 DTensor。

Megatron 哪怕做 ZeRO-3，也是按自己那套方法做的。不是因为 FSDP2 不能用，而是因为这套已经跟其他模块（TP overlap、TE user buffer）耦合得很深，整体替换成本太高。

### 2.4 Megatron-FSDP 的静态调度 buffer

FSDP 的难点不只是”能不能 shard 参数”，还有下面这几件事：

- all-gather 后的完整参数放哪里？
- 什么时候释放？
- 释放是否真的马上归还显存？
- 下一层参数 prefetch 时会不会顶出显存峰值？

如果每个 unit 都频繁 cudaMalloc、cudaFree，或者依赖 PyTorch caching allocator 自己回收临时大 buffer，大模型训练很容易出现显存碎片、峰值抖动和性能下降。

![](https://pic4.zhimg.com/v2-bb6672b2801fcdffba902e82e8b2f8ef_r.jpg)

Megatron-FSDP 因此引入了更显式的 buffer 管理：

- Storage resize based allocator：用底层 storage resize 更主动地释放临时 buffer。
- Double buffer：为交替执行的 FSDP units 准备两块持久 buffer，当前 unit 用一块，下一个被 prefetch 的 unit 用另一块。

代价是它要求 FSDP units 在尺寸上尽量规整，尤其依赖 depth-wise symmetry。如果相邻 unit 大小差异很大，double buffer 就没那么容易复用，运行时可能退回到 resize allocator 或其它 fallback 路径。

### 2.5 TP：手写 autograd 加 `CUDA_DEVICE_MAX_CONNECTIONS=1`

`ColumnParallelLinear` 和 `RowParallelLinear`负责 megatron TP 并行。表面上看跟 DTensor 的 `ColwiseParallel` / `RowwiseParallel` 是同一件事，但 Megatron 把 TP 当成一组自定义 `autograd.Function` 在写：

```text
@staticmethod
@custom_bwd
def backward(ctx, grad_output):
    if ctx.sequence_parallel:
        handle = dist_all_gather_func(all_gather_buffer, input,
                                       group=tp_group, async_op=True)
        # Here we rely on CUDA_DEVICE_MAX_CONNECTIONS=1 to ensure that the
        # gather is scheduled before the input gradient computation
        total_input = all_gather_buffer

    grad_input = grad_output.matmul(weight)

    if ctx.sequence_parallel and wgrad_compute:
        handle.wait()

    if ctx.allreduce_dgrad:
        handle = torch.distributed.all_reduce(grad_input,
                                               group=tp_group, async_op=True)
        # Here we rely on CUDA_DEVICE_MAX_CONNECTIONS=1 to ensure that the
        # all-reduce is scheduled before the weight gradient computation
    ...
```

注意那两行注释：”rely on `CUDA_DEVICE_MAX_CONNECTIONS=1`“。

CUDA 默认允许多个 stream 之间乱序调度。`CUDA_DEVICE_MAX_CONNECTIONS=1` 强制只用一个连接，于是 NCCL stream 和 compute stream 之间变成严格 head-of-line 顺序。这样上面代码里 `all_reduce(grad_input, async_op=True)` 一定会比下一行的 `wgrad_compute` 早进 NCCL 队列，AR 和 wgrad GEMM 才能重叠。

这种借环境变量来保证调度顺序的做法 DTensor 表达不出来。

DTensor 的 redistribute 是 lazy 的，调用顺序由 functional collective 决定。Megatron 用一组手写 `autograd.Function` 加一个环境变量，把 TP 的通信重叠精确控制到”NCCL 调用必须在 wgrad GEMM 之前 issue”。这是 Megatron 在 TP 上一贯比 TorchTitan 快的根本原因。

另外 Megatron 用 apex 的 `fused_weight_gradient_mlp_cuda.wgrad_gemm_accum_fp32`：

```text
fused_weight_gradient_mlp_cuda.wgrad_gemm_accum_fp32(
    grad_output, total_input, weight.main_grad)
```

这个 kernel 把 wgrad GEMM 和累加到 fp32 main_grad 融合成一个 kernel。DTensor 走不到这一步，它的 grad 累加是 PyTorch autograd 引擎的标准路径。

这块为什么要提一下 `CUDA_DEVICE_MAX_CONNECTIONS=1`，主要想解释清楚，为什么 megatron 使用环境变量绑定调度，而 FSDP 使用的是 stream + event 显示同步。

首先，event 主要是跨 stream 依赖同步点，表示的是依赖关系；而 megatron 主要想进行通算并行；

其次，TP 一般是在单机内进行，走 NVlink 高速带宽，而且具有 “launch 顺序确定 + kernel 并行执行”的现象，只有保证其严格的 overlap 才能互相掩盖, 所以需要严格保证”NCCL kernel launch 一定先进 queue、GEMM kernel launch 一定后进 queue”，才能可靠 overlap，避免调度乱序带来的耗时。这就是 CUDA_DEVICE_MAX_CONNECTIONS=1 存在的意义。

### 2.6 User-Buffer GEMM：跟 TE 深度绑定

H100 / H200 上最关键的 TP 优化叫 User-Buffer GEMM。它在 `transformer_engine` 里实现，通过 `ub_overlap_ag`、`ub_overlap_rs` 开关启用。

它让 GEMM 和 AG、RS 在同一个 kernel 内部交错，不是在 stream 上重叠：

```text
if self.config.tp_comm_overlap:
    extra_kwargs["ub_overlap_ag"] = (
        self.config.tp_comm_overlap_ag
        if hasattr(self.config, "tp_comm_overlap_ag")
        else self.config.tp_comm_split_ag or self.config.tp_comm_atomic_ag)
    extra_kwargs["ub_overlap_rs"] = (
        self.config.tp_comm_overlap_rs
        if hasattr(self.config, "tp_comm_overlap_rs")
        else self.config.tp_comm_split_rs or self.config.tp_comm_atomic_rs)
    if is_expert:
        extra_kwargs["ub_overlap_ag"] = False
        extra_kwargs["ub_overlap_rs"] = False
    extra_kwargs["ub_name"] = tp_comm_buffer_name  # "qkv", "proj", "fc1", "fc2"
```

TorchTitan 走不通这条路，它要兼容 `torch.compile` 和 DTensor 的 SPMD 表达，没法把 GEMM 替换成 TE 的私有 kernel。Megatron 选择了放弃 SPMD 表达，换 TE kernel 极致性能。

### 2.7 MoE：grouped GEMM 加 7 步 dispatch

Megatron 的 MoE 在 `megatron/core/transformer/moe/`。专家实现是 `GroupedMLP`：

```text
fc1_output_size = self.config.moe_ffn_hidden_size * self.num_local_experts
fc1_output_size_per_partition = divide(fc1_output_size, tp_size)
self.weight1 = Parameter(torch.empty(
    self.config.hidden_size, fc1_output_size_per_partition, ...))
```

所有 local 专家的权重打包成一个张量，shape 是 `(hidden, num_local_experts * ffn_hidden / tp)`。compute 时调 `gg.ops.gmm`（grouped GEMM）：

```text
w1 = self.weight1.view(self.num_local_experts, self.config.hidden_size, -1)
w2 = self.weight2.view(self.num_local_experts, -1, self.config.hidden_size)
fc1_output = gg.ops.gmm(permuted_local_hidden_states, w1,
                         tokens_per_expert, trans_b=False)
fc2_output = gg.ops.gmm(intermediate_parallel, w2,
                         tokens_per_expert, trans_b=False)
```

一个 CUDA kernel 处理所有 local 专家。TorchTitan 在 EP 模式下也走 grouped GEMM，但通过 PyTorch 接口（更高的抽象层），调用路径长一些。

token dispatch 走 `MoEAlltoAllTokenDispatcher`，源码里直接列了 7 步：

```text
(1) preprocess: 算 input_splits / output_splits
(2) dispatch process: permute tokens
(3) token dispatch: A2A(EP)
(4) dispatch postprocess: AG(TP) -> sort_chunk
(5) combine preprocess: sort_chunk -> RS(TP)
(6) token combine: A2A(EP)
(7) combine postprocess: unpermute tokens
```

最妙的是 D2H 同步点的处理。

MoE 必然要 D2H（把 `tokens_per_expert` 落到 CPU 当 `output_splits`），但 Megatron 把”在哪一步做这次 D2H”做成了可配置：

```text
cuda_sync_point ∈ {
    "before_permutation_1",
    "before_ep_alltoall",
    "before_permutation_2",
    "before_finish",
    "no_sync"
}
```

不同 sync point 对应不同的 overlap 策略：把 D2H 放在前向链路的某个位置，让它和某段 GPU 计算并行。这种微调级别的 CPU 与 GPU 同步控制，TorchTitan 没有暴露。

### 2.8 两个 RankGenerator 分别处理 attention 和 MoE

Megatron 在 `parallel_state.py` 里有个非常特殊的设计：两个 RankGenerator。

```text
order: str = "tp-cp-ep-dp-pp"

decoder_rank_generator = RankGenerator(
    tp=tensor_model_parallel_size, ep=1, dp=data_parallel_size,
    pp=pipeline_model_parallel_size, cp=context_parallel_size,
    order=order)

expert_decoder_rank_generator = RankGenerator(
    tp=expert_tensor_parallel_size, ep=expert_model_parallel_size,
    dp=expert_data_parallel_size, pp=pipeline_model_parallel_size,
    cp=1, order=order)
```

两个 generator 共享同一个 PP 切分，但内部对 PP 之内的 rank 解读不同：

- `decoder_rank_generator`：attention 的视角，`tp × cp × dp`，没有 EP。
- `expert_decoder_rank_generator`：MoE 的视角，`tp × ep × dp`，没有 CP。

注释里明确写：`ep == 1 or cp == 1` 是 hard assert。也就是说 Megatron 把”attention 和 MoE 的 TP / DP 配置可以不同”做成了一个核心抽象。你可以让 attention 跑 TP=8、MoE 跑 TP=1 加 EP=8。TorchTitan 也支持这个（`etp` 参数），但表达方式更隐式。

每一个 step 结束时的梯度同步有 5 个不同的 phase：

1. `model_chunk.finish_grad_sync()`：DP / EDP 的 RS 或 AR。
2. `_allreduce_conditional_embedding_grads`：DiT t-embedder 的梯度同步。
3. `_allreduce_non_tensor_model_parallel_grads`：LayerNorm 等 TP 复制参数的跨 TP 同步。
4. `_allreduce_word_embedding_grads` 加 `_allreduce_position_embedding_grads`：第一或最后一个 PP stage 的 tied weight。

每一个 phase 都是手写的。

FSDP2 加 DTensor 的话，至少前两个会被 DTensor 的 redistribute 自动处理，后两个仍然需要手写。Megatron 选择了全部手写、全部可控。

### 3. 对比分析：两种哲学，两种代价

到这一步可以做对比了。先用一张表列总览，再展开讨论。

| 维度 | TorchTitan（FSDP2 + DTensor） | Megatron-LM（自研栈） |
| --- | --- | --- |
| 参数分片表示 | 每个 nn.Parameter 是 DTensor | 一个连续 buffer 上的 view，配字节范围 |
| 优化器看到的 | DTensor，Adam 自然在分片上跑 | plain Tensor view，DistributedOptimizer 手切 |
| 通信触发 | submodule pre/post hook + autograd Function | 手写 grad_acc hook + bucket + 链表 prefetch |
| TP 表达 | ColwiseParallel / RowwiseParallel plan dict | 自定义 autograd.Function，外加 CUDA_DEVICE_MAX_CONNECTIONS=1 |
| TP 通信重叠 | 依赖 DTensor + Inductor micro-pipeline TP | 依赖 TE user-buffer GEMM（kernel 级） |
| MoE 专家分片 | Shard(0) over expert dim，DTensor | 所有 local 专家拼成大张量，grouped GEMM |
| MoE dispatch | all_to_all_single_autograd + 显式 prefetch | 7 步 dispatcher，可调 D2H sync point |
| Mesh 模型 | dp2ep 借位，多维 mesh + _flatten | 两个 RankGenerator 分别处理 attention/MoE |
| 跨维度梯度同步 | DTensor 自动处理大部分 | 5 个手写 phase 串起来 |
| 与 torch.compile 关系 | 一等公民，layer-wise compile 缓存命中 | 部分模块 compile，更多依赖 TE / apex kernel |

最大的差异在设计哲学：模型是张量图，还是字节流

TorchTitan 把模型视作一个张量图。每个张量都有自己的类型（`DTensor` 是 `Tensor` 的子类，带 mesh 和 placement），这个类型本身就承载分片信息。`fully_shard` 不是改变模型结构，而是给参数张量贴上标签，告诉它”你在 dp_shard_cp 这维上是 Shard(0)“。optimizer、checkpoint、loss 计算这些下游代码不需要任何改动，因为它们看到的还是 `nn.Parameter`，只不过这些参数恰好是有类型信息的 DTensor。

Megatron 把模型视作一段带元信息的字节流。`_ParamAndGradBuffer` 是一个大的 1D 字节范围，每个参数是这个范围里的一段 view。DistributedOptimizer 切的是字节范围而不是参数。每个 rank 上 optimizer 看到的是 `param.view(-1)[range.start:range.end]`，是个 plain CUDA tensor，连参数概念都不再保留。

张量图视角的代价是抽象层多了一层。DTensor 的 redistribute 比手写 NCCL 调用多了一层调度，融合 kernel 接入难（你没法轻易把 TE 的 user-buffer GEMM 塞进 DTensor 的 dispatch 链）。

字节流视角的代价是所有结构性操作都要手写。新增一个并行维（CP → EP）、新增一个跨维度同步 phase、新增一种参数类型（fp8、NF4），都要在 buffer 抽象上手写一遍。代码量大、改起来重。

### 3.1 性能优势

Megatron 在 H100 / H200 集群上是有明显优势的，但优势来源很集中：

1. TE 的 user-buffer GEMM，把 AG 或 RS 塞进 GEMM kernel 内部，硬件级 overlap。
2. apex 的 `wgrad_gemm_accum_fp32`，wgrad GEMM 直接累加到 fp32 main_grad，省一个 kernel。
3. grouped GEMM，一个 kernel 跑完所有 local 专家。
4. `CUDA_DEVICE_MAX_CONNECTIONS=1` 加手动 issue 顺序，精确控制 NCCL 调用何时进队列。
5. `_coalescing_manager` 加 buckets，把 100+ 个小 RS 合成一次大 RS。
6. DeepEP 等可插拔的融合 dispatch，MoE 路由路径的硬件优化。

前三项依赖手写或第三方 CUDA kernel，后三项是调度顺序的精确控制。TorchTitan 在前三项上做不到（FSDP2 加 DTensor 的抽象层不允许把 kernel 整体替换），在后三项上是部分做到（Inductor 的 micro-pipeline TP 是第 5 点的一种泛化）。

TorchTitan 也有自己的牌：

1. `torch.compile` 友好，layer-wise compile 缓存命中率高。
2. Async TP（Inductor 的 micro-pipeline TP），把 GEMM 和 AG 或 RS 拆成 micro-stage 交错。
3. fp8、NF4 通过 `fsdp_pre_all_gather` 协议自然接入。
4. DTensor 的自动 redistribute 让 TP + FSDP + EP 的组合不用手写胶水。

所以说，Megatron 在硬件极限性能上领先，TorchTitan 在新场景接入和组合灵活性上领先。

### 3.2 工程可维护性

Megatron 的代码风格是”每个并行维都有自己的几个文件，互相之间通过 process group 名字来连接”。新增一个并行维要写：

- 新的 process group 创建逻辑（`parallel_state.py`）。
- 新的 RankGenerator，或扩展现有 generator。
- 新的 autograd.Function 处理这个维上的通信。
- 新的 gradient sync phase 加进 `finalize_model_grads.py`。
- 可能还要加新的 bucket group 类型。

TorchTitan 的代码风格是”每个并行维都是 mesh 的一维，DTensor 自然处理”。新增一个并行维要：

- 在 `ParallelDims` 里加一维。
- 在 `parallelize_xxx.py` 里写一个 `apply_xxx`。
- 如果有新的通信模式（比如 EP 的 all-to-all），写一个 DTensor 加 functional collective 的封装。

第二种方式的复用率明显更高。CP 这种”沿 sequence 维切的奇怪并行”，在 TorchTitan 里就是 mesh 多一维加几行 plan dict 的事；在 Megatron 里需要单独写一组 `_AllGatherInContextDim`、`_ReduceFromContextDim` 这样的 autograd.Function。

反过来，Megatron 这种全部手写的代码反而更容易 review。每一个 collective 调用都在你眼前，没有 DTensor 那种 redistribute 自动触发 all-gather 的隐藏调度。出问题时，你能直接读 Python 代码定位到 NCCL 调用，不需要追到 PyTorch core 的 dispatch 链。

### 4. 小结

TorchTitan 和 Megatron 是两种截然不同的哲学：

一个把复杂性交给 DTensor 的类型系统，让每个张量自己知道自己怎么切；一个把复杂性完全暴露在 Python 代码里，每一个 collective 都手写。前者复用率高、扩展性好，后者性能极限高、可控性强。

到这里 FSDP 的演进讲了三个阶段：FSDP1 的 FlatParameter、FSDP2 的 DTensor、以及 TorchTitan 和 Megatron 这两种把 FSDP2 落到生产的方式。

下一篇讲下最近很火的 SimpleFSDP。它的思路更激进：把 FSDP2 里所有的 hook、状态机、prefetch 规则都干掉，只留两句 DTensor 操作，其余全部交给 `torch.compile` 的图变换来搞定。
