## 基本概念

### 图型处理单元GPU

GPU（Graphics Processing Unit）一开始是一种硬编码的硬件，用于3D图形渲染，到2003年已经可编程了。2006年，NV开始做CUDA（Compute Unified Device Architecture），往通用计算的方向走。

### CPU VS GPU

|  | 特点 |
| --- | --- |
| CPU | 单线程执行速度很快，但是可以并行执行的thread少 |
| GPU | 高指令吞吐，高内存带宽；可以大规模并行执行thread，牺牲单个thread处理速度，换来更高吞吐 |

下面是一张硬件资源分配的对比图，CPU有更多数据缓存和流控制单元，而GPU更多是数据处理单元

![](https://pic1.zhimg.com/v2-d4ca202465aa0c2b4061498af25a0e30_r.jpg)

### 编程语言

基本的cuda编程是使用一套基于C++的高级编程语言。在此基础上，NV提供针对一些常见计算的库，如cuBLAS，cuFFT，cuDNN，CUTLASS。另外，还有像NVIDIA的Warp和OpenAI的Triton语言，可以直接在CUDA平台上跑。

## 异构系统

CUDA的编程模型是假定系统是一个异构计算系统，通常是需要同时使用CPU和GPU。把CPU叫做host，CPU相连的内存叫做host内存，而GPU叫做device，GPU上的内存叫做device memory。有一些SoC（system-on-chip）系统，两者可能使用同一个物理硬件，不过一般还是分开作为CPU和GPU。

|  |  |  |
| --- | --- | --- |
| CPU | hos | 执行程序，下发命令给GPU（launch kernel），用cuda API传输数据 |
| GPU | device | GPU根据收到的指令，执行对应kernel（实际是一个函数，因为历史原因被称为kernel）；一个kernel会起大量thread并行去跑，这里的thread和CPU上的thread相似但不完全相同 |

## GPU硬件模型

![](https://pic3.zhimg.com/v2-89f183d14f16628644978d333b752b98_r.jpg)

上面是一个硬件模型：

1、CPU只有少量计算core；CPU通过PCIe或者NVLINK连接到GPU。

2、GPU基本的处理单元是SM（Streaming Multiprocessors），每个SM内部有自己的寄存器文件，统一的数据缓冲区（这块缓冲区由L1 cache和shared memory组成，可以在runtime调整两者大小），还有一些计算单元

3、SM组成若干个GPCs（Graphics Processing Clusters），GPU再由若干GPC组成，不同型号GPU的各部分内存大小和计算单元都不一样

## Thread block和Grid

对于kernel中thread的数量不做限制，那么thread数量极大时，需要一个更好的组织方式。若干thread会被组织成一个thread block，block再组织成grid。

![](https://pic4.zhimg.com/v2-78b2356eb248be12d79668f9f08767cd_r.jpg)

1、一个kernel对应一个grid

2、grid内部所有block的size相同

3、grid以及block的shape维度可以是1,2,3，便于对应矩阵、向量计算

**Q：上面的维度是否可以大于3**

**kernel launch参数：**当kernel下发时，会有参数指定grid和thread block的维度，除此之外，还有cluster size、stream、SM参数配置。

**thread内置参数：**每个thread有内置参数，可以用来获得在block中的位置、所属block在grid中的位置、对应的kernel是什么，同时，这些参数也可以作为thread的ID，以区分kernel中的其他thread，通过这个ID就能知道thread需要处理哪些数据。

### **block与SM的关系**

同一个block中的thread只能在一个SM上执行，这意味着这些thread可以高效通信和同步，可以访问同一块shared memory（smem）；不同block间的执行顺序是随机的、不确定的，因此不同的block不能有计算结果的依赖关系。这样的好处是GPU可以用有限的SM处理一个具有任意多thread/block的kernel。

**Q：这些thread的通信和同步具体是怎么在硬件上完成的，有哪些方式？**

### **thread block cluster**

在9.0以上的版本，cuda提供了一个新的组织层级cluster，作为可选项。cluster由一组block组成，维度也是可以为1,2,3。需要注意，cluster并不改变grid的维度，也不改变block在grid中的位置下标。cluster的作用是让同一个cluster下的不同的block可以同步和通信，具体的做法是让同一个cluster下的block在同一个GPC上执行（可以是相同SM，也可以是不同SM），在同一个cluster里的线程可以同步和通信，也可以跨SM访问smem。cluster的容纳的最大block数受硬件条件限制。

## warp和SIMT

在单个block里，线程还有一层组织方式warp，warp严格限定由32个thread组成。一个warp内的执行方式被称为SIMT（Single-Instruction Multiple-Threads），这是因为warp内的thread执行相同的代码，但是执行分支可能不同。

**warp lane：**warp内的thread从0到31有自己的编号，每个thread在warp内的编号都是可预测的。

**warp divergence：**一个warp内最好不要有分支，如果出现分支，意味着同一个warp内的thread可能需要执行不同的代码。如下图所示，会出现thread空闲等待的情况，这种问题被称为线程发散

![](https://pic4.zhimg.com/v2-6bd196c852e7e5f0f697bedff432900d_r.jpg)

**Q：上面走不同分支的thread是怎么实现的同步的，SIMT是怎么高效利用硬件的？**

在 SIMT模型中，一个 Warp里的所有线程在逻辑上是同步执行的，即每次一起执行同一条指令。当然，实际在硬件上也许不是，但是这属于硬件优化，每代架构会变化，不能把这些硬件上的优化作为可重用代码的一部分。

### **block内的thread数量**

由于warp限定32个thread，因此block内的thread数量最好是32的倍数，否则最后一个不完整的 Warp 依然会占用硬件的计算单元和内存访问通道，但因为大部分线程都在闲置，这会导致计算单元利用率低下，内存带宽也被白白浪费

### **SIMT vs SIMD**

在 SIMD 中，所有的处理单元必须执行单一的控制流路径，而Warp里的线程可以执行不同的分支

## Tile编程模型

### **Tile vs SIMT**

在tile编程模型里面，编程者能操作的最小单元是block，而SIMT模型最小单元是thread。

### **解决warp divergence**

由于block内走单一控制流，天然解决warp内线程发散的问题

### **标量操作与Tile 操作**

Tile编程模型中，有的操作是不需要所有thread一起做的，单个thread就可以完成，这种属于标量操作，比如计算索引、循环边界等。另一类是Tile操作，由 Block 里的所有线程集体并行执行的，比如两个 Tile 逐元素相加。

### **Tile和block的关系**

如下图所示，tile是针对数据切块，block是处理对应数据的thread的集合

![](https://picx.zhimg.com/v2-e4a0903e8b8b0a6ed99cb4c39258521d_r.jpg)

### **array与tile**

Tile编程模型中的两种核心数据结构是Array 和 Tile。Array作为全局的数据“仓库”，存在于device内存中，是可修改的，并且有自己的Shape和Dtype；

tile作为局部的“工作台”，它不一定有真实的内存表示，编译器会自动决定 tile 的数据存放在哪里，可能是寄存器（Registers）、共享内存（Shared Memory）。它仅存在于 tile 代码中，且局限于单个 Block 内部。

对 tile 的任何操作都不会修改原 tile，而是生成一个全新的 tile。这样不用担心原tile数据被修改，至于原tile空间使用编译器会自动优化，决定是否复用原tile空间

tile 的每个维度必须是 2 的幂，并且必须在编译时就确定下来，不能在运行时动态计算。

![](https://pic4.zhimg.com/v2-5481e7f1f3f3f4875aabd9b7a033758d_r.jpg)

**tile space：**以tile space方式ld/st数据，对array按tile大小切分，如果有边缘的块不能被填满，则可以指定处理方法，比如填充0，之后就可以按块ld/st数据。好处是可以避免去手动计算地址偏移，不用手动处理边界情况.

需要注意，st和ld情况不同，ld时可以padding，st时越界就需要默认丢弃，不然会导致越界写全局内存。出来ld和st，tile模型还支持gather（非连续读取）和scatter（非连续写入）

**tile内置操作：**tile模型提供一些常用的操作，如Elementwise arithmetic、Matrix multiplication、Reductions、Shape manipulation、Type conversion

**自动维度扩展：**会自动将较小的 Tile 扩展（expanded），使其形状与较大的 Tile完全匹配，然后再执行运算。类似于 Python 中 NumPy 或 PyTorch 的“广播（Broadcasting）”机制

### SIMT与Tile

- **SIMT（传统模式）**：提供对单个线程的细粒度控制。对于一些需要极致榨取硬件性能、或者逻辑极其复杂的底层算法，SIMT 依然是不可或缺的。
- **Tile Programming（新模式）**：提供了一种更高层次的抽象。它把繁琐的底层调度交给了编译器，极大地简化了kernel的开发难度。因为 Tile 编程将线程级别的决策（比如哪个线程算哪块数据）全部交给了编译器，所以同一份 Tile 内核代码可以直接在不同的 GPU 架构上运行，而无需修改源代码。这大大提升了代码的可移植性和生命周期。

## CUDA平台

CUDA平台包含一系列用于异构计算系统上的软硬件

### CC版本编号

每款 NVIDIA GPU 都有一个计算能力（Compute Capability，简称 CC）编号，该编号用于指示该 GPU 支持哪些特性，并指定了该 GPU 的部分硬件参数。所有 NVIDIA GPU的CC版本在链接中查看 [https://developer.nvidia.com/cuda/gpus](https://developer.nvidia.com/cuda/gpus)。

计算能力采用X.Y的格式表示，其中 X 为主版本号，Y 为次版本号。例如，CC 12.0 的主版本号为 12，次版本号为 0。计算能力与SM的版本号直接对应。例如，计算能力为 12.0 的 GPU，其内部的 SM 版本即为 sm_120。该版本号通常用于标记二进制文件。

### CUDA toolkit和NVIDIA driver

NVIDIA driver可以看作 GPU 的操作系统。它是一个必须安装在host侧操作系统上的软件组件，是所有 GPU 应用的基础。除了 CUDA 之外，driver还提供 Vulkan 和 Direct3D。NVIDIA 驱动程序的版本号格式通常为 r580 等。

CUDA Toolkit是一套用于编写、构建和分析 GPU 计算软件的库、头文件和工具集合。它是一个独立于 NVIDIA driver的软件产品。CUDA Runtime是 CUDA toolkit所提供库中的一个特例，提供了 API 用于处理常见任务，例如分配内存、在 GPU 之间或 GPU 与 CPU 之间复制数据，以及Launch Kernels。CUDA Runtime API是CUDA 运行时的 API 组件。

**CUDA Runtime API and CUDA Driver API：**CUDA Runtime API是基于CUDA Driver API构建的，两者可以一起使用，但部分功能仅由CUDA driver API提供。CUDA runtime API 函数参考文档[https://docs.nvidia.com/cuda/cuda-runtime-api/index.html](https://docs.nvidia.com/cuda/cuda-runtime-api/index.html)。CUDA driver API 参考文档[https://docs.nvidia.com/cuda/cuda-runtime-api/index.html](https://docs.nvidia.com/cuda/cuda-runtime-api/index.html)

关于不同 GPU、NVIDIA driver和 CUDA toolkit版本之间的兼容性信息查看链接[https://docs.nvidia.com/deploy/cuda-compatibility/latest/index.html](https://docs.nvidia.com/deploy/cuda-compatibility/latest/index.html)

### PTX

CUDA 平台中一个基础但有时不可见的层级是Parallel Thread Execution虚拟指令集架构（ISA），简称 PTX。PTX 是专为 NVIDIA GPU 设计的高级汇编语言，在真实的 GPU 硬件物理指令集之上提供了一个抽象层。

高级语言的编译器可以将 PTX 代码作为中间表示（IR）生成，随后利用 NVIDIA 提供的离线编译工具或即时（JIT）编译工具，生成可在 GPU 上执行的二进制代码。

PTX 虚拟指令集版本与 SM版本类似，PTX 的版本也对应着特定的计算能力，例如支持CC 8.0 所有特性的 PTX 版本被称为 compute_80。

### Cubin和Fatbin

CUDA 应用程序和库通常使用 C++ 等高级语言编写。这些高级语言代码首先会被编译为 PTX，PTX 再被编译为针对物理 GPU 的真实二进制代码，称为 CUDA 二进制文件，简称 cubin。cubin 具有针对特定 SM版本的特定二进制格式，例如 sm_120。

使用 GPU 计算的可执行文件和库二进制文件同时包含 CPU 代码和 GPU 代码。其中，GPU 代码存储在一个名为 fatbin（Fat Binary，胖二进制）的容器中。Fatbin 可以包含针对多个不同目标架构的 cubin 和 PTX 代码，即一个应用程序在构建时可以同时包含针对多种不同 GPU 架构（即不同的 SM 版本）的二进制代码。当应用程序运行时，其 GPU 代码会被加载到 GPU 上，系统会从 fatbin 中自动选择最适合该 GPU 的二进制代码来执行。

![](https://pica.zhimg.com/v2-fd31779a684bb9520974e88c7be27016_r.jpg)

**二进制兼容性：**在同一个CC主版本内，只要GPU的 CC次版本号大于或等于目标 cubin 的版本，该 GPU 就能加载并执行该 cubin。例如，针对CC 8.6 编译的 cubin可以在CC 8.6 或 8.9 的 GPU 上加载并执行。但是，它无法在CC 8.0 的 GPU 上加载。

NVIDIA GPU 在不同的CC主版本之间不保证二进制兼容，即针对CC 8.6 编译的 cubin 代码无法在CC 9.0 的 GPU 上加载。

**PTX兼容性：**GPU 代码可以以二进制或 PTX 的形式存储在可执行文件中。当应用程序存储了 GPU 代码的 PTX 版本时，该 PTX 可以在应用程序运行时进行即时（JIT）编译，以支持任何计算能力等于或高于该 PTX 代码计算能力的 GPU。例如，如果某个应用程序包含针对 compute_80 的 PTX 代码，那么在应用程序运行时，该 PTX 代码可以被即时编译为更新的 SM 版本（如 sm_120）。这使得应用程序与未来的 GPU 保持向前兼容。

**即时编译：**

PTX 代码由设备驱动程序编译为二进制代码，这被称为即时（JIT）编译。即时编译会增加应用程序的加载时间，但也是应用程序能够在未来GPU上运行的唯一方式。

当设备驱动程序为某个应用程序即时编译 PTX 代码时，它会自动缓存生成的二进制代码副本，以避免在应用程序后续调用时重复编译。这个缓存被称为计算缓存；当设备驱动程序升级时，计算缓存会自动失效。

有一些环境变量可用于控制即时编译行为，详见环境变量文档[https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/environment-variables.html#cuda-environment-variables](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/environment-variables.html#cuda-environment-variables)。

除了使用 nvcc 编译 CUDA C++ device代码外，还可以使用 NVRTC 在运行时将 CUDA C++ device代码编译为 PTX。NVRTC 是一个用于 CUDA C++ 的运行时编译库。
