## 从KV-Cache层面优化

### **从 MHA(Dense) 结构改进层面降低 KV Cache**

对于一个典型的 MHA 结构 KV Cache，大小为 $Batch \times SeqLen \times H \times D \times2$

KV Cache 的大小与 KV 的 `n_heads `强有关，现有对 MHA 的 KV Cache 优化也通常从多头注意力切入。

- **MQA：Multi-query Attention**<br>在 MHA 中，每个 Attn head 分别独立计算 QKV；在 MQA 中，每个 Attn Head 的 Query 是独立的，但 KV 是共享的。因此在 MQA 中，KV Cache 大小不再需要考虑多头开销；但相应的，MQA 会比 MHA 表现更弱，且无法做到有效的多卡并行。
- **GQA：MHA 与 MQA 中寻求平衡**<br>引入超参数 G 代表注意力头的分组数量，同分组的注意力头的 KV 是共享的。此时 KV Cache 只需考虑分组开销。在多卡推理环境下，可以根据卡的数量确定 G 的大小。
- **MLA: Multi-head Latent Attention**<br>MLA 认为 KV 矩阵存在大量冗余信息，于是不再存储巨大 KV，只 Cache 压缩后的 Latent Vector。简言之就是将 KV Cache 的压力转移到计算层，使用时通过还原矩阵做高效解压。但由于 RoPE 的问题，实际上需要存储的是压缩后 Latent Vector 和位置向量，但仍旧远小于 GQA/MHA 的缓存大小。

### **从显存管理和 KV 跨请求复用层面优化：Paged Attn& Prefix Caching**

建立 Block 维护管理既有显存，每个 block 可能会有若干 tokens。在 vllm 中，这样的显存管理也通过链式哈希，实现了基于 block 的 prefix caching 的用复。

对于 Prefix Caching，不同的推理框架中的实现各有不同：

- SGLang 通过 RadixAttention 实现 Prefix Caching<br>每次新请求到来时，调度器通过 RadixTree（保存了序列 token 到 kvcache 的映射关系）做前缀匹配，若新请求命中缓存则复用对应 KV Cache。使用 LRU least recently used 做 KV 驱逐。
- vLLM 通过前缀哈希进行 KV Block 的标识和匹配，来对应每一个 block，从而进行复用。
- DeepSeek 的 Context Caching 采用上下文硬盘缓存，将可复用内容还存在分布式的硬盘阵列中。

除此之外，对vLLM而言，LMCache可以做到跨实例的KV共享和动态加载。

### <br><br>**Copy-On-Write 机制保障： “读时共享，写时复制”**

采样策略中如 beam search 须为给定 prompt 一次性生成多个 completion，这类采样策略称为并行采样。多次输出可能存在相同的前缀，这类场景可通过共享 KV Cache 节省显存占用，共享前缀。

这里的 CoW 是为了处理修改，对于共享数据，如果需要修改，为了不影响 B，A 必须拷贝一份出去改。相比于 Prefix Caching，CoW 是在请求内进行的，Request 结束即释放，主要目的是防止显存不够而炸裂。

在 vLLM 中，BeamSearch 是通过 PagedAttn 的 Block 机制实现的 CoW。在生成下一个 token 时，如果最后一个 block 已满，那当然可以直接进行 block 复用，无需任何 copy 操作。但是如果最后一个 block 未满，beam a 和 beam b 都希望在这个物理块中写入，就会触发 CoW：如果当前 Block 引入计数>1，则由引擎分配一个新的 block 将当前 block 的既有 token 进行拷贝 **Copy**并在新 Block 上进行写入 **Write**，当前 Beam 的页表也将更新为新的 block。<br><br><br>简而言之，CoW 是为了 token 级别的处理，Prefix Caching 更加关注 Block 级的复用。Prefix Caching 通过 Block 实现 kv 复用，而 CoW 则是在最后那个“即将发生分歧”的 block 上通过复制来解耦，不会动到其他历史块，并可实现安全的 token 写入。

## 从显存管理和调度层面优化

### **Paged Attention**

老生常谈的基本技术，解决了非连续内存访问的问题，更加有效地利用了显存。

但实际上GPU中非连续内存访问不仅是带宽问题，还会导致 TLB Miss（页表缓存未命中）。也正因此，Paged Attn才会成为Chunked Prefill/Continuous Batching等重要优化的基础：当 Chunked Prefill 处理长序列时，如果 KV Cache 在物理显存上是碎片的，GPU 的内存管理单元（MMU）需要频繁查找页表来翻译虚拟地址到物理地址。PagedAttention 的核心贡献之一，其实是配合软件层的 Block Table 来减少这种硬件上的地址翻译开销。

### **EPD分离**

对于VLM而言，传统的流程是串行的：ViT&Projector - Prefill - Decoding。看起来前两者都是计算密集型。我们仍旧可以按照传统的PD分离思路来做。但实际上，E本身不生成KV Cache，纯粹计算密集型，Prefill还是需要做分配&填充KV Cache。E可能会占时间但不需要很贵的HBM高带宽显存，只需要算力；Prefill既需要算力也需要大HBM，放到一起可能会造成资源的浪费。并且会出现扩缩容比例Scaling Ratio不同。

同时，拆分EP可以避免GPU做Encoder时LLM权重闲置、做LLM时VisionEncoder权重闲置的问题。走EP分离的优势本质上是Pipeline Parallelism的优势。

### **从算术强度和访存层面看PD分离/EPD分离/FlowMatching分离**

PD分类这类将异构计算进行拆分的工作，其收益可以从算术强度和显存层面进行考虑。

混合部署所导致的最直接的问题是队列阻塞：Prefill处理长文本时计算得太久，会导致Decode被迫卡顿。但这样的问题已经极大程度被Continuous Batching和Chunked Prefill所缓解。但是，一方面这类软件层面的调度方案本质上是在做Trade-off，是以算术强度为代价进行的妥协；另一方面，软件调度无法做到GPU层面的状态隔离，会导致Cache污染等问题。

**软件调度方面：Trade-Off是对计算强度的妥协**

Prefill和Decode在算术强度( $$$AI = \frac{\text{Total FLOPs}}{\text{Total Memory Bytes}}$$$ )层面是截然不同的两种计算任务，Prefill是典型的Compute-Bound而Decode是典型的Memory-Bound。对此，为了在保证首字延迟的前提下将其进行混合部署时，Chunked Prefill就是做了这样的一个Trade-Off，将Prefill强行切分为多个Chunk，然后在Chunk间见缝插针地执行Decode。

这样的强行融合是有代价的，它破坏了原本FlashAttention建立的Tiling级Cache复用，需要更频繁地将模型权重重复从HBM搬运到SRAM，增加了访存开销，算术强度也就随之下跌。

而如果我们选择了PD分离，虽然为了首字延迟我们仍需通过切分Chunk来解决队头阻塞的问题，但我们可以把Chunk切得更大而无需照顾Decode，可以确保Tensor Core算力利用率足够大，成功保住我们的算术强度。同时，通过Global Scheduler根据文本长度进行路由也可以有效解决队头阻塞的问题。

**状态隔离方面：物理隔离实现访存优化与异构部署**

将异构计算任务进行物理隔离的另一个意义是访存层面。FlashAttention工作的关键就是建立了Tiling级KV-Cache复用，可以避免频繁地从HBM搬运到SRAM。我们是希望我们所需要的数据尽可能驻留在SRAM上的，而混合部署破坏了这一点。

一方面，混合部署往往会用到Chunked Prefill，而Chunked Prefill本身破坏了FlashAttn带来的提升。另一方面，混合部署本身就会带来SRAM的缓存污染，每次Decode好不容易将重要的KV Cache驻留在SRAM上（哪怕没走FlashAttn，也会在一定程度有这方面的优势），巨大的Prefill一进来，海量的Activation Tensors直接挤走了Decode的KVCache。这其实和Chunked Prefill带来的破坏是一致的。

物理隔离还能允许更灵活的异构部署，Prefill节点对算力需求大，Decode节点对显存需求大，我们可以选取对应合适的卡分给它们，缺什么就扩容什么，从而带来更高的性价比。

EPD分离的动机也主要是源于混合部署带来的显存问题。它除了显存污染以外，还有一个更简单的逻辑：一台机器存两套完全独立的模型权重是不划算的。

EPD分离中，虽然从算数强度上来看Encoder和Prefill是“同构”的——都是计算密集型。但是两者是完全独立的，如果混合部署同时加载ViT和LLM的模型权重，这会造成较大的显存浪费，挤兑KV Cache和Activation的空间，拉低能承载的Batch Size；而且Vision Encoder需要巨大的激活显存，本身也会对Prefill这边的Activation造成内部Cache挤兑，这个过程中也会有显存污染的产生。

**SM调度方面：异构计算强度造成可能的Cache Thrashing和发射端阻塞**

在一个SM内部，计算单元和访存单元是物理分离的，只要指令不冲突，SM完全可以一边让访存单元LD/ST Units去HBM拿数据、一边让执行单元Execution Units去用Tensor Core算乘法。

问题就出现在Warp调度器上。当Decode的Warp发出访存指令时，Decode进入等待数据的Stall休眠状态，Prefill开始执行GEMM任务，当Decode终于拿到所需的KV Cache时，完全可能抢不到任何计算资源，继续等待在Eligible就绪序列当中。

但这个过程中Prefill也有访存行为，当它将新的Activation从HBM塞到L2 Cache中时，Decode是数据可能也会被覆写。哪怕此时Prefill已经可以把Tensor Core让出，由于数据缺失，Decode也只能再次发出访存指令。这也就造成资源的浪费。

在异构计算的混合部署中，访存任务往往会是受害者。

但如果我们能够将访存任务进行物理隔离，没有Prefill的庞然大物时L2 Cache其实是相对可控的，并且由于每个Decode算得足够快，它们核心争抢的实际是HBM带宽和L2Cache空间，不用花很长时间去排队等待计算资源。也就避免了“互相洗Cache”的情况。而Prefill节点更是可以自然地通过Pipeline Hiding达到极高的TFLOPS。

相比之下，对FlowMatching而言，AR（即声学Token生成阶段，其实不止AR，这里做简称）与ODE分离的动机就比较简单了。相比于吞吐，实时语音对话对端到端延迟的要求更高。ODE要执行多次循环，每一次都可能被AR过程的巨大算子（持续时间较长的GEMM）所堵住，这就很像我们做Chunked Prefill的动机 。但由于我们对稳定的端到端延迟很敏感，并且ODE每次循环都可能面临这样的问题。物理分离就可以有效降低ODE的延迟。

如果我们不做物理分离，我们就可能需要Chunked AR这样的技术，但它会面临Chunked Prefill同样的问题——一旦与流式访存的ODE交替执行，每个AR Chunk都会遭遇完全的Cache Miss。

如果我们做了物理分离，AR方面的Chunk可以不必设得那么严苛；ODE方面哪怕遇到了“拥堵”那也一定是ODE堵ODE，此时还可以顺便在下一个Iteration做个Dynamic Batching，几乎是Free Lunch。而且物理分离后还可以做精准地扩容。

### **KV传输**

对于Dense模型，KV传输是较大的问题。为了让KV传输不作为大瓶颈，除了总线级别的NVLink方案，还可以使用Mooncake这类工作。Mooncake将KVCache看作共享资源，可以实现点对点传输，支持TCP、RDMA(Remote Direct Memory Access， 实现GPU和RDMA网卡间的P2P拷贝)/GPU Direct RDMA的高速传输。

若QPS不高，可做Prefill Rentention或全局资源池化后做动态路由，不过企业上应该不会遇到这种情况吧。

vLLM这边的实现还侧重于静态的角色分离。SGLang的Router则可做到更聪明的动态路由。

### **Chunked Prefill & Full Prefill**

对单序列而言Chunked Prefill算是对Prefill阶段的时间切分。常用于长序列推理，对长序列进行切分后进行Prefill。在过去如果不做PD分离，Prefill可能会卡住Decoding，但现在有了Chunked Prefill，可以将Prefill与其他请求的Decoding一起来做。虽然会增加Prefill总时间，但Decoding不会再感到明显卡顿，并且Inter-token Latency依旧很低。是一个很通用很值得做的Trade-off。

Chunked Prefill与Continuous Batching相结合，可以确保每次的Batch Size都处于满载状态。调度器先满足所有的Decode请求（延迟敏感），再用Prefill的Chunk把剩余的Token Budget填满。如果没有Chunked Prefill，当我们将长序列和短序列分开处理时，短序列哪怕做了continuous batching，可能也会因为算力闲置面临memory bound；长序列一次batch数过多（batch_size=token_num）导致OOM或短序列出现latency spike。

至于Trade-off方面：Chunked Prefill并非绝对的free lunch，它会带来：

- Kernel Launch和地址跳转（若无PagedAttn）的overhead
- <u>每次强制Chunk结束都需清空SRAM，造成更多的HBM到SRAM的来回搬运</u><br>如果走 Full Prefill，利用 Flash Attention 我们可以最大化数据的片上复用（Reuse）。虽然由于 SRAM 容量限制（如 A800 仅 192KB/SM），长序列的 KV 依然需要回写 HBM 并在后续计算中重读，但 Full Prefill 允许在一个 Kernel Launch 周期内，让加载到 SRAM 的 KV Block 被尽可能多的 Q Block 复用。 而 Chunked Prefill 由于强制打断了 Q 的处理序列，导致之前的 KV Block 必须在不同的 Kernel Call 之间被反复从 HBM 读取（Redundant Memory Access），这才是导致其带宽效率低于 Full Prefill 的根本原因.
- 考虑到Batching语境时：相比纯Decode Batch，Chunked Prefill轻微拖慢同Batch中其他Decode请求的速度<br>如果调度器把 Chunk 塞得太满，占用了过多的 SM 用于计算 Prefill 的 GEMM，那么 Decode 阶段的 Loading KV 这一步虽然不卡，但 Decode 的 Softmax/Reduction 计算步骤可能会因为拿不到足够的 SM 而变慢

其实最重要的仍是第二点，Chunked Prefill 打破了 Flash Attention原本通过 Tiling 建立的 KV-Cache-Reuse 机制，导致算术强度Arithmetic Intensity下降，从而无法像 Full Prefill 那样充分掩盖 HBM 的访问延迟。

### **SGLang Router的Cache Aware**

不论怎么切分，都可能会遇到负载均衡问题。虽然Chunked Prefill是一个很好的方法，但如果有个更高层面的均衡器会更聪明。SGLang Router支持常规&PD分离两种架构模式。负载均衡方面支持Random随机/Round Robin轮询/Power of Two双候选负载比较/Cache Aware缓存感知四种策略。Cache Aware可以根据Prefix Caching来做选择。

### **LLM服务中的常见并行策略/EP**

最朴素的是TP张量并行，可将单个模型的权重拆分到多个GPU上，每个GPU计算每层的一部分。

Deepseek则提出对于MoE模型可将不同专家Expert分布在GPU上，即EP专家并行。每个GPU负责一部分专家，仅为每个token激活所需的专家，减少每个token的计算量。大规模EP在Decoding阶段的提升比较大（[DeepSeek-V3 / R1 推理系统概览](https://zhuanlan.zhihu.com/p/27181462601#:~:text=DeepSeek%2DV3%20/%20R1%20%E6%8E%A8%E7%90%86%E7%B3%BB%E7%BB%9F%E6%A6%82%E8%A7%88&text=DeepSeek%2DV3%20/%20R1%20%E6%8E%A8%E7%90%86%E7%B3%BB%E7%BB%9F%E7%9A%84%E4%BC%98%E5%8C%96%E7%9B%AE%E6%A0%87%E6%98%AF%EF%BC%9A%E6%9B%B4%E5%A4%A7%E7%9A%84%E5%90%9E%E5%90%90%EF%BC%8C%E6%9B%B4%E4%BD%8E%E7%9A%84%E5%BB%B6%E8%BF%9F%E3%80%82%20%E4%B8%BA%E4%BA%86%E5%AE%9E%E7%8E%B0%E8%BF%99%E4%B8%A4%E4%B8%AA%E7%9B%AE%E6%A0%87%EF%BC%8C%E6%88%91%E4%BB%AC%E7%9A%84%E6%96%B9%E6%A1%88%E6%98%AF%E4%BD%BF%E7%94%A8%E5%A4%A7%E8%A7%84%E6%A8%A1%E8%B7%A8%E8%8A%82%E7%82%B9%E4%B8%93%E5%AE%B6%E5%B9%B6%E8%A1%8C%EF%BC%88Expert%20Parallelism%20/,%E5%BC%95%E5%85%A5%E8%B7%A8%E8%8A%82%E7%82%B9%E7%9A%84%E4%BC%A0%E8%BE%93%E3%80%82%20%E4%B8%BA%E4%BA%86%E4%BC%98%E5%8C%96%E5%90%9E%E5%90%90%EF%BC%8C%E9%9C%80%E8%A6%81%E8%AE%BE%E8%AE%A1%E5%90%88%E9%80%82%E7%9A%84%E8%AE%A1%E7%AE%97%E6%B5%81%E7%A8%8B%E4%BD%BF%E5%BE%97%E4%BC%A0%E8%BE%93%E5%92%8C%E8%AE%A1%E7%AE%97%E5%8F%AF%E4%BB%A5%E5%90%8C%E6%AD%A5%E8%BF%9B%E8%A1%8C%E3%80%82%20*%20EP%20%E6%B6%89%E5%8F%8A%E5%A4%9A%E4%B8%AA%E8%8A%82%E7%82%B9%EF%BC%8C%E5%9B%A0%E6%AD%A4%E5%A4%A9%E7%84%B6%E9%9C%80%E8%A6%81Data%20Parallelism%EF%BC%88DP%EF%BC%89%EF%BC%8C%E4%B8%8D%E5%90%8C%E7%9A%84DP%20%E4%B9%8B%E9%97%B4%E9%9C%80%E8%A6%81%E8%BF%9B%E8%A1%8C%E8%B4%9F%E8%BD%BD%E5%9D%87%E8%A1%A1%E3%80%82&text=%E5%A4%A7%E8%A7%84%E6%A8%A1%E8%B7%A8%E8%8A%82%E7%82%B9%E4%B8%93%E5%AE%B6%E5%B9%B6%E8%A1%8C%EF%BC%88Expert%20Parallelism%20/%20EP%EF%BC%89%20%E7%94%B1%E4%BA%8EDeepSeek%2DV3%20/%20R1,*%20Decode%EF%BC%9A%E8%B7%AF%E7%94%B1%E4%B8%93%E5%AE%B6EP144%E3%80%81MLA%20%E5%92%8C%E5%85%B1%E4%BA%AB%E4%B8%93%E5%AE%B6DP144%EF%BC%8C%E4%B8%80%E4%B8%AA%E9%83%A8%E7%BD%B2%E5%8D%95%E5%85%83%E6%98%AF18%20%E8%8A%82%E7%82%B9%EF%BC%8C32%20%E4%B8%AA%E5%86%97%E4%BD%99%E8%B7%AF%E7%94%B1%E4%B8%93%E5%AE%B6%EF%BC%8C%E6%AF%8F%E5%BC%A0%E5%8D%A12%20%E4%B8%AA%E8%B7%AF%E7%94%B1%E4%B8%93%E5%AE%B6%E5%92%8C1%20%E4%B8%AA%E5%85%B1%E4%BA%AB%E4%B8%93%E5%AE%B6)）。

DP数据并行则将Batch拆成更小的块，每个GPU处理不同的数据批次从而提升整体吞吐量。EP size=TP*DP。

在过去，EP往往是静态非弹性的，每次扩展都需要重启。对此vLLM也支持EEP弹性专家并行，允许动态DP扩展。每次希望扩容时，vLLM通过Ray在额外GPU启动新的引擎核心，系统进入扩展状态（正在进行的请求允许完成但是新请求可能被排队），所有引擎核心拆除旧的通信器并为新节点创建新的通信器，使用EPLB重新计算专家到GPU的分配，新引擎核心加载、旧核心可能卸载专家权重，再做新的KV缓存结构初始化，最终协调器标记扩展完成。

对于EP也可能出现专家间负载不均的情况，对此可引入EPLB (Expert Parallel Load Balancing，专家负载均衡)调度算法，静态+动态调整专家负载。

MTP/ Speculative Decoding

目前最快的Speculative Decoding方法是EAGLE3。

EAGLE模型的目标是预测目标模型的特征序列，而非直接预测token。预测出的特征再通过目标模型的LM Head转换为token概率分布。这样会更简单效果也会更好。

但是，LLM对token的采样本身也具有随机性，会对后续计算造成影响。虽然EAGLE是在预测当前的特征，但也需要考虑之前已采样的token序列，从而减少特征预测的不确定性。

须注意的是，自EAGLE2以后，EAGLE系列模型的一大特性就是context-aware的动态树构建，但vLLM并不支持相关特性。后者固定了输出字典树的结构，只能被draft_len进行控制，相当于论文中设计的简化版，只取实测得到的静态最优树结构。

**DSA: Deepseek Sparse Attention (Native Sparse Attention)**

DeepSeek在注意力机制上有两个重要里程碑：

1. MLA：DeepSeek V2/V3标配，解决显存问题（KV Cache压缩）
2. DSA(Deepseek Sparse Attention)：在DeepSeek V3.2面对长文本引入的新技术，主要解决计算量问题

MLA已经极大程度上压缩了KV Cache的大小，但也让长上下文面临更严重的计算受限问题。这导致长上下文请求的TPOT极高。考虑到在长文中绝大多数Token对当前生成都是噪音，DSA希望只计算“真正重要”的那一小部分 Token 的注意力。

DSA本质上就是一个动态剪枝，通过Indexer预测直接跳过不重要的Token，在Prefill和Decoding两个阶段都能大幅减少计算延迟，流程如下：

1. Lightning Indexer: 使用降维后的低精度QK，在计算Attention之前先快速扫描全局历史，计算一个粗粒度的相关性分数，判断哪些Block/Token对当前Query是有价值的
2. 筛选&路由：根据Indexer的打分选出Top-K个Token（固定常数K，使计算开销为O(K)），结合Local Window（最近邻必选，保证语言连贯性）的混合策略，进行筛选
3. 稀疏计算 Sparse Computation：主Attention层只加载&计算这K个被选中Token的精确Attention，计算复杂度从O(N^2)降低到O(NK)

这里的Sparse指的更多是Block-Level Sparse。理论上，最理想的稀疏是Token-Level。但GPU的全局内存Global Memory访问是按Transaction（通常32字节/128字节）进行的。如果我们走Token-Level，由于数据在物理显存上不连续，可能由于非合并访问造成极低的显存带宽利用率；Block-Sparse则将连续的B个Token打成一个Block，Indexer只需判断这个Block是否重要，做一个粗粒度筛选。对于选中的Block，Kernel将Block内所有Token的KV数据一次性搬到SRAM，由于Block内部是连续的，所以可以跑满HBM带宽。

这里有一个反直觉的point：非合并访问会将大量时间花在寻址和指令开销上，所以哪怕我们走Block-Sparse的合并访问，其实速度也会比Token-Level更快。与此同时，Block大小（稀疏粒度）最好满足Warp对齐（32，避免线程空转）、TensorCore对齐（16的倍数，矩阵计算时会减少补0的padding开销）、地址计算优化（2的幂次）、L2 Cache Line适配等要求。

除此之外，Warp Divergence线程束分歧也是一个问题。在MHA中，一个Warp可能负责处理32个Query Heads，在稀疏注意力中不同Query对历史Block的关注点是不同的，这个过程中可能会产生不同Query对应Thread的负载不均，整个Warp必须等待最慢的那个Thread（很可能就是选中Block最多的Thread）处理完后才能结束，其他更快的Thread只能在这个时间中空转Idle。

针对 Warp Divergence，Dpsk使用SGMV(Segmented Gather Matrix-Vector)算子，它打破了 Query 与 Thread 的静态绑定，将不规则的稀疏 Block 聚合成规则的任务块，配合负载均衡调度器，极大提升了 SM 的利用率，从而最小化Idle空转。SGMV的核心在于将非连续分布的 Block 索引（Gather 操作）与高效的矩阵计算（Gemm）在算子层融合，避免了中间变量在显存中的反复搬运。

最后，Indexer本身也会带来开销。对此，需要考虑Representative Vectors的降维，进行粗粒度打分（Block-Level做Top-K选择）和低量化精度（FP8甚至INT4）运算。Indexer的准确性至关重要，需要与主模型进行联合训练/蒸馏获得。

总体上，DSA 是为了解决 MLA 在长文本下 Compute-Bound（计算受限） 问题。它通过牺牲非必要的全局计算，利用 SGMV 算子在 GPU 上实现了接近稠密算子的硬件利用率。
