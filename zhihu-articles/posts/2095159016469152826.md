NVIDIA 这次又在 vLLM 发布了 Kimi K3 的新一轮推理优化， **16 张 GB300 在开启 DSpark 的时候，单请求 decode 达到 842 tokens/s，相比同配置的原版 vLLM 提高了 1.73 倍**，就算不用投机解码的情况下，不同的 batch 也有明显提升。

![](https://pic2.zhimg.com/v2-955df2686db406c224a8e7ad35095137_r.jpg)

**这次新增的是针对 GB300 的 specialized decode 执行路径**，把原本分散在一层里的操作重新组织，同时尽量让 GPU 计算、跨卡通信和权重读取同时进行。

> 这部分实现已经 10 月 16 日通过 [PR #61867](https://github.com/vllm-project/vllm/pull/61867) 合并，不过需要你主动打开。

## **以前慢在哪里？一个 MoE 层里有太多等待**

一般来说，Kimi K3 每生成一个 token，GPU 都要依次经过 Attention、跨卡归约、Attention Residual、MoE 路由、专家计算之类的步骤，模型虽然说是稀疏 MoE，每个 token 只选一部分专家，但是只要某个环节在等待跨卡结果，或者为了很小的一段运算单独启动 Kernel，后面的 GPU 工作就可能接不上。

> 特别是单请求 decode，矩阵本来就很小，光把算术做快，实际上也解决不了多次启动和反复读显存的问题。

比如这个图：

- 在 **TP16、batch 8、单个 KDA 层加 MoE 块**的跟踪里面，普通 vLLM 用 23 个 Kernel，130 微秒
- 新的执行路径只用 13 个 Kernel， 69 微秒

![](https://pic3.zhimg.com/v2-998ea7cb6c4d61d893266d5d58427eae_r.jpg)

> 这张图里面的数字是局部层耗时，不是整个模型生成一个 token 的时间，不过确实能解释后面为什么能看到端到端的 decode 提升。

## **怎么把这一层变快？**

首先是矩阵乘法，一个人等模型连续输出的时候，batch 可能只有 1 或 2，通用 GEMM 的准备成本会比较突出，所以作者给这些小矩阵单独设计了 Kernel，之后 batch 大一些后，又切换到 split-K，让更多 GPU 工作单元分担计算。

KDA decode 也做了对应的 CuTe DSL 实现，长上下文的 full-attention 也可以让多个 GPU 各自计算一部分 KV，然后再合并结果，也就是说：

> **它没有找一个最强 Kernel 用在所有输入上，而是根据当前任务的形状选择不同执行方式**。

然后第二步是 Attention 算完之后的优化，原本需要先做输出投影，再跨 GPU all-reduce，等数据收齐之后继续算 Attention Residual。

现在把这些操作衔接起来，**GPU 将部分结果直接放到 NVLink 可访问的缓冲区，接收端拿到结果就继续计算:**

- 小 batch 会把生产者和消费者合到一次 Kernel 执行里
- 大 batch 改用两阶段归约，先合并指定份额，再分发结果，避免所有 GPU 重复搬运同一批数据

> **这里省下的时间不仅来自少启动几个 Kernel，还有来自原本串行等待的步骤可以交错进行。**

然后到了 MoE，原版 TP 实现会在各张 GPU 上重复计算完整的 router 分数和 latent 输入投影，新版把这份工作拆到不同 TP rank，再交换各自结果。

同时共享专家被安排到另一条 GPU stream，在路由或被选中专家计算的时候执行，甚至还根据 batch 控制资源占用，避免看似并行的任务互相抢资源。

**最后在通信还没占满显存带宽的阶段，额外安排下一步权重的 L2 预取，让 GPU 结束等待后尽可能直接从缓存读取权重**。

用一条简化的 decode 路径来理解大概就是：

- 请求进入之后，运行时先根据 batch 和并行设置选好 Kernel
- Attention 投影和 KDA 计算时尽量减少启动开销，跨卡结果一就绪就衔接残差计算
- MoE 路由不再每卡重复做全量工作，共享专家同时执行，后续专家权重趁等待时间提前进入缓存

> **这些优化单独看都不是全新概念，价值珠海还是在于针对 K3 的具体数据形状，把多卡流水线真正排顺了。**

## **842 tokens/s**

**842 VS 488 算是这个优化里最亮点的结果了**，用的是 16 张 NVIDIA GB300、TP16、batch 1、输入只有 1 token、输出 1000 token，开启 DSpark（一次草拟 7 个 token），人为设定平均每步接受 6 个 token。

> 这里统计的是 decode 吞吐量，不包含 prefill，所以它很适合验证新版执行路径，应该不能直接当作真实 Agent 会话的平均体验。

![](https://pica.zhimg.com/v2-ec06247621f0bfef2c38ceb1a4356f56_r.jpg)

> 在 32K 输入、DSpark 平均接受长度大概 3.78，而混合 prefill 的情况下，纯 decode 提升也还在，但把其他请求的 prefill 算进去，最终输出吞吐量提升会表小。

就算关闭 DSpark，提升也不是靠投机解码凑出来的：

- TP16 的 batch 1 从 136 到 256.4 tokens/s，提升 1.88 倍
- batch 8 达到 1157.9 tokens/s，提升 1.79 倍
- batch 64 达到 3606.1 tokens/s，提升 1.62 倍。

> 这些是整个 TP 组的吞吐量，batch 变大后加速比例会逐渐降低，**说明这套做法特别擅长处理低并发时那些零碎、容易被启动和通信开销拖慢的操作。**

另外还用了 AgentX 测了更接近 Coding Agent 的请求：长上下文、多轮对话、工具调用停顿、并行 subagent 和 KV Cache 复用都在里面。

**它给出的 P90 interactivity 是 403.2 对 223.7 tokens/s/user，看起来提高约 1.8 倍，但前者使用 16 张 GB300，后者是之前的 8 张 GB300 结果**：

![](https://pic4.zhimg.com/v2-36c02314c7009589ede3741c875e6433_r.jpg)

**整体来看，英伟达为了卖卡，确实一直在给各种开源大模型提供针对性优化，毕竟对于算力卡来说，时间就是金钱。**

这次英伟达通过具体算子融合、跨卡通信重排和权重预取，让 Kimi K3 的小 batch decode 确实明显提速，加上之前的[NVIDIA 发布 KDA v0.6，把 KDA 在 B300 上相对 Moonshot 官方提升 2.96](h<i>ttp</i>s://zhuanlan.zhihu.com/p/2088949455374624110) ，感觉 K3 现在的性能和之前对比，完全就是成熟期和完全体的区别了。
