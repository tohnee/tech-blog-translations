Model Context Protocol 经历了 5 个版本迭代，从一个 Anthropic 的开源项目成长为 Linux 基金会下的开放标准。本文系统梳理 MCP 协议的完整演进历程，聚焦最新的 2026-07-28 版本带来的颠覆性变化。

## 一、MCP 协议背景：为什么需要它

2024 年 11 月，Anthropic 发布了 **Model Context Protocol（MCP）** ——一个开放标准，旨在解决 AI 模型与外部系统连接的碎片化问题。你可以把它理解为 **"AI Agent 世界的 USB-C 接口"** ：统一的插拔标准，让任何 AI 模型都能以一致的方式访问文件、数据库、API 和各类工具。

在此之前，每接一个数据源就要写一套定制集成，平均开发周期 3-4 周。MCP 把这个时间压缩到了 2-3 天。

## 二、版本演进时间线

MCP 从诞生到现在经历了 5 个主要版本，每次迭代都回应了真实的生产需求：

2024-11-05初始版本 
 MCP 首次发布。定义客户端-服务器架构、Tools/Resources/Prompts 三大原语，JSON-RPC 2.0 通信。 
 2025-03-26OAuth + Streamable HTTP 
 引入 OAuth 2.1 授权框架，HTTP+SSE 替换为 Streamable HTTP，新增工具注解、音频内容、参数补全。 
 2025-06-18安全 + 结构化输出 
 MCP 服务器定义为 OAuth 资源服务器，强制 Resource Indicators，新增 Elicitation，移除 JSON-RPC 批处理。 
 2025-11-25异步任务 + 扩展框架 
 一周年大版本。引入异步 Tasks、OIDC 发现、Client ID 元数据文档、Extensions 框架、带工具的采样。 
 2026-07-28无状态核心（最大修订） 
 移除握手和会话，无状态协议核心，MRTR，Header 路由，授权加固，正式弃用策略。

## 三、2026-07-28：史上最大修订（核心解读）

这是 MCP **自诞生以来最大的协议修订** 。官方的描述是： *"largest revision since launch"* 。核心变化可以概括为：无状态化、可路由、可缓存、可扩展。

### 1. 移除握手和会话 → 无状态协议 Breaking

这是最核心的变化。之前的 MCP 需要先握手再通信，现在彻底移除了：

之前（2025-11-25）

- 必须先完成 `initialize` / `initialized` 握手
- 服务器返回 `Mcp-Session-Id` ，后续请求必须携带
- 请求被绑定到特定服务器实例
- 水平扩展需要 sticky routing 或共享会话存储

之后（2026-07-28）

- 无握手——每个请求自描述，携带版本号和客户端能力
- 所有信息放在 `_meta` 字段中
- 可选的 `server/discover` RPC 用于按需发现服务器能力
- 任何请求可落在任意服务器实例上
- 普通 round-robin 负载均衡即可工作

参考 SEP-2575（移除握手）和 SEP-2567（移除 `Mcp-Session-Id` ）。

### 2. Multi Round-Trip Requests（MRTR）New

取代了之前的服务器端发起请求（roots、sampling、elicitation），引入 **Multi Round-Trip Requests** 机制：

- 服务器返回 `InputRequiredResult` ，暂停执行并请求输入
- 客户端收集用户输入后，用 `inputResponses` 和 `requestState` 重新发起原始调用
- 任何服务器实例都能处理重试——因为所有状态都在请求负载中
- **不再需要常开的双向流**

为什么 MRTR 重要

之前服务器要主动向客户端发请求（sampling、elicitation），需要保持双向流连接。MRTR 把这变成了"服务器返回一个需要输入的结果 → 客户端处理后再发一次请求"的模式，配合无状态核心，彻底消除了对长连接的依赖。

### 3. Header-based Routing New

Streamable HTTP 传输现在强制要求两个新 HTTP 头：

```text
Mcp-Method: tools/call
Mcp-Name: get_order_status
```

这意味着 **负载均衡器、网关、WAF、限流器** 可以直接基于 HTTP 头进行路由和授权，不需要解析 JSON-RPC body。服务器会拒绝头和 body 不一致的请求。

还可以用 `Mcp-Param-` 前缀把任意工具参数提升为 HTTP 头，进一步方便中间件处理。

### 4. 可缓存的列表结果 New

`tools/list` 、 `prompts/list` 、 `resources/list` 、 `resources/read` 的响应现在携带：

- `ttlMs` ：缓存生存时间
- `cacheScope` ：缓存范围

客户端可以智能缓存工具目录，减少不必要的重复获取。列表结果还保证 **确定性顺序** ，让上游 prompt cache 在重连后保持稳定。

### 5. 授权加固 New

授权是开发者花费最多时间的地方，此版本继续强化：

| SEP | 改进内容 |
| --- | --- |
| SEP-837 | 客户端在 DCR 时声明 OIDC application_type，避免桌面/CLI 客户端被默认为 "web" 而被拒绝 localhost 重定向 |
| SEP-2352 | 客户端凭证绑定到授权服务器的 issuer，资源迁移时重新注册 |
| SEP-2207 | 标准化从 OIDC 授权服务器请求 refresh token 的方式 |
| SEP-2350 | step-up 授权中的 scope 累积规则 |
| SEP-2351 | .well-known 发现后缀标准化 |
| 强制 iss 验证 | 协议层面防御 mix-up 攻击（一类让客户端把授权响应关联到错误身份服务器的攻击） |

### 6. Tasks 从核心协议移至扩展 Breaking

2025-11-25 引入的实验性 Tasks，在生产使用后促使了重新设计：

- 从核心协议移到 `io.modelcontextprotocol/tasks` 扩展
- `tasks/result` （阻塞式）→ `tasks/get` （轮询式）
- 新增 `tasks/update` （客户端向服务器发送输入）
- 移除 `tasks/list`
- 服务器可以主动返回任务句柄，不需要按请求 opt-in
- 变更通知从 HTTP GET 端点移至 `subscriptions/listen` 流

### 7. 正式弃用策略 + 三大功能弃用 Deprecated

引入正式的 **功能生命周期策略** （SEP-2596）：弃用功能必须保持至少 **12 个月** 的弃用期，之后才能移除。

以下三个功能被标记为弃用（SEP-2577）：

| 弃用功能 | 替代方案 |
| --- | --- |
| Roots | 使用工具参数传递 |
| Sampling | 直接使用 Provider API |
| Logging | 使用 stderr 或 OpenTelemetry |

此外，旧的 HTTP+SSE 传输也被正式弃用，同样有 12 个月的过渡期。

### 8. Extensions 框架正式化 New

扩展框架正式确立，包含：

- **反向 DNS 标识符** （如 `io.modelcontextprotocol/tasks` ）
- **独立版本号** ——扩展可以自己迭代，不依赖核心协议版本
- 已发布的扩展：Tasks、MCP Apps（已提前上线）
- **Enterprise-Managed Authorization（EMA）** 扩展已稳定，组织可集中管理 MCP 服务器授权

### 9. SDK 全面更新

四大 Tier 1 SDK 同步支持 `2026-07-28` ：

- **TypeScript SDK** ✅
- **Python SDK** ✅
- **Go SDK** ✅（与 Google 协作维护）
- **C# SDK** ✅（v2.0，Microsoft 维护）
- Rust SDK（beta）
- Ruby SDK（社区）

## 七、对开发者的影响

### 谁需要关注什么

| 角色 | 需要做什么 |
| --- | --- |
| MCP 服务器开发者 | 移除 initialize 握手逻辑；支持无状态请求；实现 server/discover；迁移 Tasks 到扩展 API；添加 HTTP 头路由支持 |
| MCP 客户端开发者 | 在每个请求的 _meta 中携带版本和能力信息；实现 MRTR 模式；利用缓存 TTL 优化性能；评估 Roots/Sampling/Logging 的迁移 |
| 企业架构师 | 利用无状态特性简化部署架构；评估 EMA 扩展实现集中授权；关注 AAIF 的 Agent Gateway 项目 |
| AI 应用开发者 | 探索 MCP Apps 实现富交互界面；利用 Tasks 支持长任务工作流；关注 Extensions 生态 |

### 迁移时间线

关键时间节点

- **现在** ：2026-07-28 规范已正式发布，SDK 已就绪
- **12 个月内** （~2027年7月）：Roots/Sampling/Logging 和 HTTP+SSE 传输可能被移除
- **建议** ：新实现不要采用已弃用功能；现有实现应在 12 个月内规划迁移
