上下文窗口是当前 AI 工程中最稀缺的资源。它不是存储器，而是工作记忆—— 有限、会腐化、需要主动管理。本章深入拆解上下文腐化的机制， 给出四层记忆架构与六种压缩策略，并以微软 Azure SRE Agent 为案例， 展示工业级上下文工程的真实面貌。

## 3.1 开篇案例，微软 Azure SRE Agent：从 100 个工具到一个文件系统

2025 年中，微软的 Azure 站点可靠性工程（SRE）团队面临一个令人沮丧的问题：他们构建了一个拥有超过 100 个工具调用接口的智能体，用于自动化处理生产环境告警——但在真实的轮班场景下，这个智能体在任务执行约 30 分钟后开始出现行为漂移：它会忘记早期的诊断结论，重复已经验证失败的操作，甚至在已有明确进展的情况下重新从零开始收集信息。

工程团队最初的直觉是"模型能力不足"。他们尝试更换更大的模型，调整系统提示词，增加重试逻辑——但问题依然存在。直到一名工程师提出了一个反直觉的假设：**不是模型忘记了，而是我们没有给它任何"记住"的地方。**

真正的根因是上下文腐化：随着诊断步骤的推进，早期的关键信息（"已确认 Pod A 内存正常"、"已排除网络分区"）被越来越多的工具输出和中间推理所稀释，最终滑出了有效注意力范围。模型不是忘记了——它从来就没有可靠的机制"记住"。

解决方案出乎意料地简单：他们引入了一个结构化的外部状态文件 `incident_progress.md`，记录每一步诊断的结论（而不是过程），并在每次推理调用前将这个文件注入上下文的最前端。工具数量从 100 多个削减到不足 15 个。结果：

![](https://pic4.zhimg.com/v2-76d7b924660b0b4c3bd7b216c7c151b3_r.jpg)

这个案例揭示了上下文工程的核心矛盾：**模型能看到什么，取决于 Harness 给它呈现什么；模型能记住什么，取决于 Harness 如何管理状态。**上下文窗口不会自动帮你做这件事。

> *上下文窗口是大脑的工作台，不是硬盘。你不能把所有东西都堆在上面，然后期待大脑记住所有细节。上下文工程的本质，是决定工作台上放什么、不放什么。*<br>上下文工程实践社区 · 2026

## 3.2 上下文腐化的解剖

在进入解决方案之前，我们需要准确理解问题。**上下文腐化（Context Decay）**是指：随着对话轮次或任务步骤的推进，早期注入的关键信息因被后续内容稀释、截断或注意力分散，逐渐失去对模型推理的有效影响，导致智能体行为出现退化、漂移或自我矛盾的现象。

上下文腐化不是单一机制，而是三种效应的叠加：

![](https://pic1.zhimg.com/v2-c44533faa9f65ab5134bfda158bc76ce_r.jpg)

### 上下文窗口的消耗解剖

一个典型的生产级智能体，其上下文窗口的消耗通常呈现以下分布。这张分布图展示了为什么"上下文总是不够用"：

![](https://pica.zhimg.com/v2-24b51710d18df1747a4be2136ce5a29e_r.jpg)
*图 3-2　典型智能体上下文窗口的消耗分布（以 128K token 窗口为例）*

这张图揭示了一个残酷的现实：在一个未经优化的 Harness 中，**真正可用于当前推理步骤的上下文空间可能只有整个窗口的 5%。**剩下的 95% 被系统提示、工具定义、RAG 检索结果、历史对话和工具输出占满。这正是上下文工程需要解决的核心问题。

> ⚠ Lost-in-the-Middle 效应<br>斯坦福大学 2024 年的研究证实：大语言模型对上下文窗口中段信息的注意力显著低于头部和尾部。这意味着将关键信息放置在上下文中间，是最糟糕的设计决策——即便它在窗口内，也可能被模型实质性地忽视。上下文工程的一个核心原则是：**最重要的信息，始终放在开头或结尾。**

## 3.3 四层记忆架构：给智能体一套完整的记忆系统

解决上下文腐化的根本方法，是为智能体设计一套**分层的记忆系统**，而不是试图把所有信息都塞进单一的上下文窗口。这套系统按照信息的生命周期和访问频率，分为四个层次：

![](https://pica.zhimg.com/v2-e2c6f43bc420c71198f4536c199c646c_r.jpg)
*图 3-3　四层记忆架构金字塔：从最快的上下文窗口到永久存储的归档层*

![](https://picx.zhimg.com/v2-834c3235df4f81e90dc40033fb60ad63_r.jpg)

> 💡 分层记忆的核心思想<br>四层记忆的本质是"冷热分离"：把频繁访问、高时效性的信息放在热层，把低频访问、高持久性的信息下沉到冷层。**Harness 的责任，是在每次推理调用前，从各层取出恰当的信息组合，高效地填充上下文窗口的热层。**这个过程称为"上下文构建"（Context Assembly），是上下文工程最核心的操作。

## 3.4 外部化状态：progress.md 模式

外部状态文件是 L2 温层记忆的核心实现，也是应对上下文腐化最直接、最有效的工程手段。其核心思想是：**将智能体的任务进度从上下文窗口中"卸载"到一个持久化的外部文件，再在每次推理前以精炼的形式重新注入。**

Mitchell Hashimoto 在他关于 Harness Engineering 的原始博客中，将这种模式命名为"Progress File Pattern"，并将其列为应对上下文腐化的第一优先级手段。Claude Code（Anthropic 的命令行智能体工具）在内部实现中大量使用了类似的机制。

### 一个生产级 progress.md 的真实结构

```text
## 任务摘要
生产集群 prod-east-2 中 Deployment `api-gateway` 出现间歇性 5xx。
目标：定位根因，给出修复建议或执行可逆修复操作。
开始时间：2026-05-18 14:32 UTC

## 已确认事实（无需重新验证）
- ✅ Pod 内存使用正常（avg 68%，无 OOM）
- ✅ 网络分区已排除（跨 AZ 延迟 <2ms）
- ✅ 数据库连接池正常（池化率 92%）
- ✅ 5xx 集中在 /api/v2/search 端点（占比 94%）
- ✅ 错误模式：超时，非逻辑错误

## 当前推断
高度可能（85%）：search 服务上游 Elasticsearch 集群响应慢
待验证：ES 集群 shard 分配状态，是否有 relocating shard

## 已尝试路径（失败，无需重试）
- ❌ 重启 api-gateway Pod（5xx 未改善，已回滚）
- ❌ 增加 HPA 副本数（无效，瓶颈不在计算）

## 下一步行动
1. 检查 ES 集群 _cluster/health 和 _cat/shards
2. 如发现 relocating shard，评估是否需要人工触发 reroute

## 禁止操作（需人工审批后方可执行）
- 任何生产数据库的 schema 变更
- 强制终止 ES 集群节点
```

这个文件的设计体现了几个关键原则：**已确认事实与推断分开**（避免模型将推断当作事实处理）；**失败路径明确标注**（避免重复无效操作）；**禁止操作显式声明**（确定性安全边界）；**下一步行动具体可执行**（为下一轮推理提供明确的起点）。

> 📋 Progress File 的七条设计规范<br>① 每次工具调用后立即更新，不在推理结束时批量更新。② 只记录**结论**，不记录推理过程。③ 已确认事实与当前推断严格分区。④ 失败路径用 ❌ 明确标注，禁止重试。⑤ 文件本身不超过上下文可用空间的 15%。⑥ 每次注入时放在上下文的最前端（利用头部注意力优势）。⑦ 文件名和格式在整个 Harness 中保持一致，便于自动化处理。

## 3.6 上下文构建：每次推理前的信息编排

有了分层记忆系统和压缩策略，下一个工程问题是：**在每次模型调用之前，如何将各层的信息按照最优的方式组装进上下文窗口？**这个过程称为"上下文构建"（Context Assembly），是 Harness 中 `_build_context()` 函数的核心职责。

一个精心设计的上下文构建函数，需要回答五个问题：

| 问题 | 设计决策 | 实践建议 |
| --- | --- | --- |
| 放什么？ | 信息选择 | 任务进度摘要 + 近期工具输出 + 当前步骤相关 RAG 结果 |
| 放多少？ | 预算分配 | 系统提示 ≤10%，进度文件 ≤15%，RAG ≤25%，历史 ≤30%，剩余给模型 |
| 放哪里？ | 位置策略 | 最重要信息放首尾（利用注意力分布），工具输出放末尾 |
| 何时更新？ | 更新时机 | 每次工具调用后立即更新外部状态，每轮推理前重新构建上下文 |
| 如何验证？ | 质量检查 | 检查 token 预算是否超限；关键信息是否在头部或尾部；无重复内容 |

### 上下文构建的代码骨架

```text
def _build_context(self, state: TaskState) -> ContextBundle:
    """
    上下文构建函数：在每次模型调用前组装最优上下文。
    遵循 预算分配 + 位置优先级 两个核心原则。
    """
    budget = ContextBudget(total=128_000)  # token 总预算

    # ── 第一区：系统提示（头部，固定，≤10%）──
    system = self.system_prompt.render()         # 支持 KV Cache 复用
    budget.allocate("system", system, limit=0.10)

    # ── 第二区：任务进度摘要（头部，≤15%，最高优先级）──
    progress = state.load_progress_file()       # 从外部状态文件读取
    progress_summary = self.compressor.summarize(
        progress,
        max_tokens=budget.remaining(0.15),
        strategy="key_facts_only"               # 只保留已确认事实
    )
    budget.allocate("progress", progress_summary, limit=0.15)

    # ── 第三区：动态 RAG 检索（≤25%，按当前步骤语义检索）──
    query = state.current_step_intent()         # 当前步骤的意图向量
    rag_chunks = self.vector_store.search(
        query=query,
        top_k=5,
        max_tokens=budget.remaining(0.25)
    )
    budget.allocate("rag", rag_chunks, limit=0.25)

    # ── 第四区：近期对话历史（滚动压缩后，≤30%）──
    history = self.history.get_compressed(
        window=10,                                # 最近 10 轮
        max_tokens=budget.remaining(0.30),
        strategy="rolling_summary"
    )
    budget.allocate("history", history, limit=0.30)

    # ── 尾部区：最近工具输出（尾部，利用尾部注意力优势）──
    tool_results = state.last_tool_outputs(max_tokens=budget.remaining(1.0))
    budget.allocate("tool_results", tool_results, limit=1.0)

    # 验证：确保未超预算，关键信息位于首尾
    budget.validate()

    return ContextBundle(
        sections=[system, progress_summary, rag_chunks, history, tool_results],
        token_count=budget.used,
        metadata=budget.allocation_report()
    )
```

## 3.7 跨会话状态桥接：让智能体不因重启而失忆

上下文工程的最后一道难题，是跨越会话边界的状态延续。大多数 LLM 接口是无状态的——每次新的 API 调用，都是一个全新的无记忆对话。对于跨越多个会话的长任务（比如一个需要数天时间的大型代码重构任务），这意味着智能体在每次重启后都面临完全的"失忆"。

跨会话状态桥接（Cross-Session State Bridge）是指：**通过 Harness 的持久化机制，在会话结束时自动保存任务状态，在下一个会话开始时自动恢复，使智能体在用户感知上实现"连续的记忆"。**

### 三种会话重连模式

| 模式 | 机制 | 适用场景 | 恢复延迟 |
| --- | --- | --- | --- |
| 检查点恢复 | 在每个重要步骤保存完整的任务状态快照；重启时加载最近一个检查点继续执行 | 有明确步骤边界的自动化任务（CI 流水线、数据处理） | < 5 秒 |
| 摘要重建 | 会话结束时，生成一段精炼的"交班摘要"；下一个会话将其注入上下文头部作为冷启动背景 | 对话式助手、客服场景；允许少量信息损失 | < 2 秒 |
| 混合模式 | 结构化状态（已完成步骤、关键决策）用检查点；非结构化历史（对话语气、偏好）用向量记忆；两者在重启时合并注入 | 复杂长任务，需要既保留精确进度又维持对话连贯性 | 10–30 秒 |

> 🔁 Meta REA 系统的休眠/唤醒设计<br>Meta 的 Research Engineering Agent（REA）在处理多日 ML 训练流水线时，实现了一套"休眠-唤醒"机制：任务在训练期间主动挂起智能体（节省计算资源），在训练完成后根据检查点自动唤醒，继续评估和下一步实验设计。每次唤醒时，智能体的上下文由四个文件重建：`experiment_plan.md`、`results_so_far.json`、`next_actions.md`、`constraints.md`。整个重建过程不超过 3 秒，智能体几乎感知不到中断。这正是混合模式跨会话桥接的生产级实现。

## 3.8 反模式警示: 上下文工程的五个常见反模式

理解正确的做法之后，我们来逐一审视实践中最常见的错误。这些错误在早期往往不会立即暴露，但随着任务复杂度的提升，会以成倍放大的形式造成系统失控。

| 反模式 | 表现 | 根本原因 | 正确做法 |
| --- | --- | --- | --- |
| 万物皆放进窗口 | 把所有背景文档、工具文档、历史记录一次性注入，导致窗口爆满 | 误以为"信息越多越好" | 分层记忆 + 动态 RAG，按需注入 |
| 系统提示堆砌 | 系统提示超过 8K tokens，包含大量案例、格式说明、边缘情况处理 | 用提示词替代工程约束 | 系统提示聚焦角色与原则，细节移至工具文档或状态文件 |
| 工具输出原文注入 | 将工具返回的原始 JSON（可能数千行）直接放入上下文 | 缺少工具输出的后处理层 | 工具输出经提取、摘要后注入；只保留推理所需的字段 |
| 对话历史无限增长 | 不做任何历史压缩，上下文随轮次线性增长，直到撞上窗口上限 | 没有设计历史管理策略 | 滚动摘要压缩，配合外部状态文件持久化结论 |
| 关键信息放中间 | 将任务目标、约束条件等关键信息放置在上下文中部，被工具输出前后包夹 | 不了解 Lost-in-the-Middle 效应 | 关键信息始终放在上下文的头部（系统提示）或尾部（最近输出） |

## 本章要点<br>

- 上下文腐化是长任务智能体失控的首要原因，由三种效应叠加构成：注意力稀释（Lost-in-the-Middle）、窗口截断（Hard Truncation）、语义漂移（Goal Drift）。
- 解决方案是四层分层记忆架构：热层（上下文窗口）、温层（外部状态文件）、冷层（向量记忆库）、归档层（结构化数据库）。不同信息按生命周期和访问频率分配到对应层次。
- progress.md 模式是对抗上下文腐化的第一优先级手段：每次工具调用后立即更新，只记录结论不记录过程，注入时放在上下文头部。
- 六种压缩策略各有适用场景：短任务用滚动摘要，长任务用层级摘要，知识库场景用动态 RAG，高频系统提示用 KV Cache 复用。大多数生产系统需要组合使用。
- 上下文构建（Context Assembly）是每次推理前的核心操作：遵循预算分配原则（系统提示≤10%、进度≤15%、RAG≤25%、历史≤30%）和位置优先级原则（最重要的信息放首尾）。
- 跨会话状态桥接使智能体在重启后无缝恢复：检查点恢复适合有明确步骤边界的任务，摘要重建适合对话场景，混合模式适合复杂长任务。

## Harness Checklist · 第 3 章

用以下问题诊断你当前系统的上下文管理成熟度：

- 你的系统有没有测量过上下文窗口的实际使用分布？知道工具定义、RAG、历史各占多少比例吗？
- 当任务执行超过 20 步后，智能体有没有出现过"重复已验证失败操作"的情况？这是上下文腐化的典型症状。
- 你有没有实现任何形式的外部状态文件？如果没有，跨步骤的关键结论存在哪里？
- 你的对话历史策略是什么？是无限积累、硬性截断，还是摘要压缩？
- 你的系统提示有多长？如果超过 4K tokens，有没有考虑 KV Cache 复用来降低延迟和成本？
- 在你的上下文构建函数中，关键信息（任务目标、核心约束）被放置在窗口的什么位置？

上下文工程解决的是"模型看到什么"的问题；下一章的工具编排，解决的是"模型能做什么"的问题。两者共同决定了一个智能体的行为边界——让我们继续深入第四章。
