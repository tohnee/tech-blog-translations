目的应该非常明确，而且**不应该是学会写 Triton**。

结合我现在的目标（LLM Serving、GPU 系统、AI Infra），我的目标暂时是：

> **看到一个 Triton kernel，5 分钟内知道它在优化什么、为什么这么写、瓶颈在哪里。**

因为现在绝大多数人已经是 AI 写 Triton 代码了，我真正需要的是：

- 能读懂 FlashAttention
- 能读懂 FlashInfer
- 能读懂 vLLM 里的 Triton kernel
- 能在 AI 生成代码之后判断有没有问题
- 能根据论文想到「这里是不是可以改成另一种 blocking」

这比自己从零写一个 matmul kernel 有价值得多。

---

### 所以只需要记住下面这套「Triton 阅读词典」。

以后看到任何 Triton 代码，几乎都能定位。

---

### ① 一个 Triton Kernel = GPU 上运行的一段程序

看到

```text
@triton.jit
def kernel(...):
```

脑子里立即翻译成

> **这是 GPU 上执行的一段代码。**

不是 Python。

不是 CPU。

而是一段 GPU Kernel。

---

### ② 一个 Program 负责一小块数据

这是最重要的。

看到

```text
pid = tl.program_id(0)
```

立即翻译：

> **我是第几个 Program。**

例如

```text
Vector

----------------------

Program0

0~1023

Program1

1024~2047

Program2

2048~3071
```

所有 Program

运行同样代码。

只是 pid 不一样。

---

### ③ BLOCK_SIZE = 一次处理多少数据

看到

```text
BLOCK_SIZE=128
```

不要想 CUDA Block。

直接翻译：

> **一个 Program 一次处理 128 个元素。**

---

### ④ tl.arange()

看到

```text
offsets =
block_start +
tl.arange(...)
```

立即翻译：

> **生成这一块所有元素的下标。**

例如

```text
pid=3

BLOCK_SIZE=4

offsets

12

13

14

15
```

就是这么简单。

---

### ⑤ tl.load()

看到

```text
x = tl.load(...)
```

不要理解成 Python load。

翻译成：

> **把这一块数据搬进 GPU。**

注意重点：

不是搬一个。

是搬

```text
128

256

512

1024
```

一起搬。

---

### ⑥ tl.store()

看到

```text
tl.store(...)
```

翻译：

> **计算结束，写回显存。**

---

### ⑦ mask

看到 `mask=...`

永远翻译成：

> **最后一块可能越界。**

例如

1000 个元素,BLOCK_SIZE=256

最后 Program实际上只有

```text
768~999
```

后面的

```text
1000~1023
```

不能访问。

mask 就负责这个。

---

### ⑧ grid

看到

```text
kernel[grid](...)
```

立即翻译：

> **启动多少个 Program。**

例如

```text
10000元素

BLOCK_SIZE=1024
```

就是10个 Program一起跑。

那么和前面的program_id的关系是什么呢？

这里和`program_id()` 是直接对应的， 可以理解为CUDA的：

`kernel<<<grid, block>>>();`

triton:

`kernel[grid](...)`

## 我们用最简单的例子。

假设有一个长度为 10000 的数组。

你规定：

```text
BLOCK_SIZE = 1024

```

那么：

**一个 Program 负责 1024 个元素。**

于是需要多少个 Program？

```text
10000 / 1024 ≈ 10

```

所以：

```text
grid = (10,)

```

然后：

```text
add_kernel[grid](...)

```

意思就是：

> **启动 10 个 Program，同时执行 add_kernel。**

## 那 `program_id()` 从哪里来的？

这里就连起来了。

假设 GPU 启动了 10 个 Program。

那么 GPU 会自动给它们编号：

```text
Program 0
Program 1
Program 2
...
Program 9

```

于是

```text
pid = tl.program_id(0)

```

对于每个 Program 来说：

```text
Program0
pid = 0

Program1
pid = 1

Program2
pid = 2

```

代码完全一样。唯一不同：pid

而 Program 是怎么知道自己负责哪一块的？

就是这一句：

```text
block_start = pid * BLOCK_SIZE
offsets = block_start + tl.arange(0, BLOCK_SIZE)
```

---

### ⑨ stride

这是第二重要的。

看到

```text
stride
```

翻译：

> **下一行距离当前行多远。**

例如

```text
1 2 3

4 5 6

7 8 9
```

第一行

到第二行

跳

```text
3
```

就是 stride。

GPU 全靠 stride 算地址。

---

### ⑩ Pointer

看到

```text
x_ptr
```

不要害怕。

翻译：

> **GPU 显存地址。**

所有 Kernel

其实都是

```text
地址

+

偏移

=

新地址
```

---

### ⑪ 为什么到处都是 BLOCK？

以后几乎所有 Triton 都会出现

```text
BLOCK_M

BLOCK_N

BLOCK_K
```

不要想复杂。

就是：

```text
不要一次处理整个矩阵。

切成小块。
```

GPU 最喜欢

```text
Tile

Tile

Tile
```

---

### ⑫ 为什么那么多 pid_m pid_n？

看到

```text
pid_m

pid_n
```

翻译：

> **我负责哪一个 Tile。**

例如

```text
矩阵

□□□□□□□□

□□□□□□□□

□□□□□□□□
```

Program

负责其中一块。

不是整个矩阵。

---

## 以后读 Triton 时，脑子里永远问这五个问题

任何 Kernel，先别看代码。

先问：

1.**一个 Program 在处理什么？**

（一个 Block？一行？一个 Tile？）

2.**数据是怎么切块的？**

（BLOCK_SIZE）

3.**Program 怎么知道自己负责哪块？**

（program_id）

4.**数据什么时候 load？**

（tl.load）

5.**数据什么时候 store？**

（tl.store）

如果这五个问题都能回答，这个 Kernel 你已经理解了 **70%**。

---

### 后面学习 Triton 时，完全不要去背 API，而是一直套用下面这个模型：

```text
Python 调用
        │
        ▼
Launch Grid（启动多少个 Program）
        │
        ▼
Program（每个负责一块数据）
        │
        ▼
program_id → 确定负责哪一块
        │
        ▼
tl.load → 从 HBM 读取这一块
        │
        ▼
寄存器 / SRAM 中完成所有计算
        │
        ▼
tl.store → 写回 HBM
```

把这张图牢牢记住，以后看 FlashAttention、FlashInfer、vLLM 或其他 Triton kernel，基本都能迅速判断它们是在做什么，而不用纠结每一个 API 的细节。
