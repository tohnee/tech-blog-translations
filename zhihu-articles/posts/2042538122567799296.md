## 01. 推理优化的第一步不是调参数

一个 LLM 服务变慢后，工程团队很容易先去改参数：调大 batch，调高并发，降低 `max_model_len`，换量化模型，或者把副本数加上去。这些动作都可能有用，但它们不是第一步。第一步应该是回答一个更基础的问题：你到底在优化 TTFT、TPOT、吞吐，还是成本？

LLM 推理服务最麻烦的地方，是这些目标经常互相拉扯。更大的 batch 往往提高 tokens/s，摊薄每 1000 token 成本，却可能增加排队时间，让用户等更久才看到第一个 token。更多副本能降低排队和 tail latency，却会拉高空闲成本。更长上下文能提升能力，却会占用更多 KV cache，让并发能力下降。更激进的张量并行能让大模型装进多卡，却引入跨卡通信，让小 batch 延迟不一定更好。

推理优化没有脱离场景的最优参数，只有围绕目标指标的取舍。实时对话、代码补全、批量文档处理、内部低频工具，对“快”的定义完全不同。实时对话里，首 token 500ms 和 2s 的用户感知差异很大；离线文档处理里，单个请求多等几秒不重要，整体 tokens/s 和成本更重要；代码补全甚至比聊天更看重 TTFT，因为用户正在编辑器里等待补全弹出。

所以做推理服务时，应该先写 SLO，再选引擎，再调参数，最后用压测和线上指标复核。没有 SLO 的调参，就像在没有坐标系的地图上移动瓶颈：你看到某个数字变好了，但不知道它是否是用户和业务真正关心的数字。

## 02. 先把推理指标拆开：TTFT、TPOT、吞吐和成本

LLM 服务不能只用一个“平均响应时间”描述。生成式服务是流式的，用户先看到第一个 token，再持续看到后续 token。一个请求的体验至少由几段组成：排队时间、prefill 时间、首 token 返回时间、每个输出 token 的 decode 时间、网络 streaming 时间和最终收尾时间。

TTFT，Time To First Token，表示从请求进入服务到第一个 token 返回的时间。它受队列长度、prefill、模型冷启动、prefix cache 命中、调度策略影响。TTFT 对交互体验非常敏感。用户打开聊天窗口后，第一下等待太久，会觉得系统“卡住了”；代码补全场景里，TTFT 过长则补全建议会错过编辑节奏。

TPOT，Time Per Output Token，表示生成阶段每个输出 token 的平均耗时。它主要受 decode batch、KV cache 访问、采样策略、跨卡通信和 GPU 利用率影响。TPOT 决定流式输出是否顺滑。TTFT 很短但 TPOT 很差，用户会看到答案像挤牙膏一样慢慢出来。

端到端延迟表示完整请求从进入到结束的时间。它适合描述非流式任务、批量处理任务和最终完成时间，但不能替代 TTFT/TPOT。两个请求端到端都是 8 秒，体验可能完全不同：一个 0.5 秒出首 token，后面慢慢流；另一个 7 秒才出首 token，然后一次性返回。

吞吐也要分清。QPS 是每秒请求数，tokens/s 是每秒生成或处理的 token 数。LLM 服务里，tokens/s 往往比 QPS 更有解释力，因为请求长度差异很大。10 个短请求和 10 个长请求对 GPU 的压力完全不同。若只看 QPS，容易把长上下文和长输出带来的成本藏起来。

成本指标常写成 $/1K tokens 或 $/1M tokens。它来自 GPU 时价、GPU 数量、实际吞吐、利用率、冗余副本和工程开销。一个服务 tokens/s 高，但为了低延迟长期保留大量空闲 GPU，真实成本仍然可能很高。成本不是财务部门最后算账的数字，它应该进入推理系统设计本身。

## 03. 延迟、吞吐、成本是一组三角关系

推理服务调优时，最常见的错法是只拿一个指标当方向盘。比如看到 tokens/s 低，就不断调大 batch；看到 TTFT 高，就不断扩副本；看到账单高，就直接上 INT4。每个动作都可能把另一个指标打坏。

![](https://pic2.zhimg.com/v2-c297c7341cd16a298329ac0d0472af13_r.jpg)
*推理优化三角：低延迟、高吞吐、低成本三个目标互相牵制，实时对话、文档批处理和内部工具落在不同区域*

低延迟通常需要更保守的排队策略、更小的 batch 等待时间、更多冗余副本、更短上下文或更小模型。它的代价是 GPU 可能没有被充分填满，单位 token 成本上升。实时对话、代码补全、语音交互等场景更靠近这个顶点。

高吞吐通常需要更大的 batch、更激进的 continuous batching、更高的 KV cache 利用率、更稳定的请求长度分布。它的代价是单个请求可能排队更久，TTFT 尤其容易变差。离线摘要、批量分类、文档重写、评测集批跑更靠近这个顶点。

低成本通常来自更高利用率、更便宜硬件、更小模型、量化、缓存复用、请求路由和排队容忍度。它的代价可能是延迟不够稳，或者质量边界更窄。内部低频工具、非实时运营任务、成本敏感的免费层服务更靠近这个顶点。

三角关系不是说三者必然只能选一个，而是提醒团队：每次优化都在移动落点。你可以用更好的引擎让三角整体变大，用 PagedAttention 降低显存浪费，用 prefix caching 降低重复 prefill，用量化降低权重显存；但在某个具体系统里，仍然要决定优先级。没有优先级，优化很容易只剩局部数字变漂亮。

## 04. SLO 要按场景写，不要按工具默认值写

SLO 是服务要对用户体验承担的指标承诺。它不是随手写一个 p95 latency，也不是把某个开源 benchmark 数字抄进文档。对 LLM 推理服务来说，SLO 至少要覆盖 TTFT、TPOT、端到端完成时间、错误率、限流行为和成本预算。质量指标也要另行评估，但本文先聚焦推理基础设施指标。

![](https://pic1.zhimg.com/v2-45fe3cece7e379d9c6135ed42a53766e_r.jpg)
*不同场景 SLO 速查：实时对话、代码补全、文档批处理和内部工具对 TTFT、TPOT、吞吐与成本有不同优先级*

实时对话可以把目标写成：TTFT p95 小于 500ms，TPOT p95 小于 50ms，端到端延迟按输出长度分桶统计，超过上下文预算时返回明确错误或降级策略。这里的数字是示例，不是通用承诺。不同模型、GPU、地域和业务体验要求会改变阈值。关键是指标要能表达用户是否觉得对话顺滑。

代码补全更极端。它常常输出较短，但首 token 必须非常快。TTFT 可能要压到 200ms 量级，甚至更低。为了这个目标，服务可能要用更小模型、更近的部署地域、更保守的 batch 等待时间，牺牲部分吞吐和成本。对补全场景来说，建议来晚了就等于没有建议。

文档批量处理的指标完全不同。它可以接受排队，甚至可以在夜间集中跑。SLO 可以写成每小时处理多少 token、单任务最长完成时间、失败重试次数、单位成本上限。这里盲目追求低 TTFT 没有意义，反而会让 GPU 利用率不够高。

内部工具则要看组织约束。某些内部工具每天只有几十次调用，可以接受排队和较慢响应，但需要成本可控、失败可解释、峰值有保护。此时 SLO 可以强调月度预算、单用户 token 上限、p95 端到端延迟和限流提示，而不是追求和面向用户的实时聊天一样的延迟。

写 SLO 的一个好方法，是把指标和动作绑定。TTFT 超过阈值时，是扩副本、减少 batch 等待、启用 prefix cache，还是降级到小模型？KV cache 水位超过阈值时，是拒绝超长请求、降低 max_tokens，还是把批处理任务挪到低优先级队列？没有动作的 SLO 只是报表。

## 05. 成本公式要先写清楚单位

推理成本常被写成 `$ / 1K tokens`。这个指标很有用，但公式必须带单位，否则容易算错一个 3600 倍。

若 GPU 价格按小时计，单卡价格是 `P` 美元/GPU-hour，使用 `N` 张 GPU，实际吞吐是 `T` tokens/s，那么粗略成本是：

`$/1K tokens ≈ P × N ÷ 3600 ÷ T × 1000`

如果你把 GPU 价格先换算成美元/GPU-second，公式就变成：

`$/1K tokens ≈ GPU 秒价 × N ÷ T × 1000`

这个公式只算了在线生成的 GPU 成本，真实账单还包括空闲冗余、网络、CPU、存储、日志、观测、负载均衡、工程人力和失败重试。它仍然有价值，因为它能让成本路径变清楚：提高吞吐 `T` 会降低单位 token GPU 成本；增加副本 `N` 会提高成本；减少长上下文和长输出可以提高有效吞吐；量化能通过降低显存占用和扩大 batch 间接降低成本。

举一个保守的算账方式。假设某服务使用 1 张 GPU，价格 3 美元/GPU-hour，实际稳定吞吐 300 tokens/s。只看 GPU 计算，成本约为：

`3 ÷ 3600 ÷ 300 × 1000 ≈ 0.00278 美元/1K tokens`

如果为了低延迟保留 2 个副本，但平均只有 1 个副本有活干，单位成本接近翻倍。若通过 continuous batching、prefix caching 或请求长度治理把稳定吞吐提高到 600 tokens/s，单位成本接近减半。若换成更大模型让吞吐下降到 80 tokens/s，即使质量提升明显，也要让业务知道成本数量级变了。

成本公式还会逼你区分“理论吞吐”和“有效吞吐”。benchmark 中的 tokens/s 可能来自固定长度、满载、无网络、无租户隔离的理想条件。线上有效吞吐要扣掉冷启动、空闲冗余、峰值预留、失败重试、低命中率缓存和长尾请求。平台做成本治理时，应记录实际输出 token、输入 token、GPU 使用时长和副本水位，而不是只引用压测峰值。

## 06. 引擎选型不是排行榜

vLLM、TGI、TensorRT-LLM、SGLang 都是推理服务里常见的名字。它们有重叠能力，也有不同设计重点。选型时直接问“哪个最快”，通常问错了。更好的问题是：我的模型是什么，硬件是什么，SLO 是什么，团队能维护多复杂的运行时，服务是否需要结构化输出，是否依赖 Hugging Face 生态，是否愿意为 NVIDIA 特定优化付出编译和适配成本。

![](https://pica.zhimg.com/v2-34c657c398af0318b4851fa3e8cdb226_r.jpg)
*推理引擎选型矩阵：vLLM、TGI、TensorRT-LLM 和 SGLang 在部署复杂度、生态、吞吐、结构化输出和硬件绑定上各有边界*

vLLM 的主场是通用高吞吐 serving。PagedAttention、continuous batching、OpenAI-compatible API、活跃社区和较直接的部署路径，让它适合作为很多团队的推理服务起点。若团队要快速把开源模型变成兼容 OpenAI API 的服务，vLLM 往往值得优先验证。

TGI，也就是 Hugging Face Text Generation Inference，适合已经围绕 Hugging Face 模型、Hub、容器和部署生态工作的团队。它的优势是生态顺手、工程路径清楚。若团队已有 HF 模型发布和运维流程，TGI 的整合成本可能更低。

TensorRT-LLM 更靠近 NVIDIA 生态的极致优化路线。它适合愿意做模型转换、编译、量化适配和硬件特定调优的场景。收益可能很高，但工程复杂度也更高。若团队没有能力维护这条链路，单次 benchmark 很亮眼也不代表长期可用。

SGLang 强调高性能 serving、结构化生成、程序化调用和相关调度能力。对强依赖 structured output、tool calling、复杂 prompt 程序的场景，它可能比通用 serving 引擎更贴近表达需求。选它之前，同样要用自己的模型和输出格式做压测，而不是只看通用榜单。

选型最稳妥的流程是：先用 SLO 和约束筛掉明显不合适的方案，再用同一模型、同一硬件、同一请求分布做压测。压测要覆盖 TTFT、TPOT、tokens/s、显存水位、错误率、冷启动、升级路径和回滚方式。引擎不是一次性选择，随着模型规模、业务流量和团队能力变化，答案也会变化。

## 07. 常见调参旋钮：每个都有副作用

推理引擎暴露的参数很多，但几个旋钮最容易影响延迟、吞吐和成本：`max_num_seqs`、`gpu_memory_utilization`、`tensor_parallel_size`、`max_model_len`。它们看起来像独立开关，实际上都在移动瓶颈。

![](https://pic1.zhimg.com/v2-c4fbbfd866cec9546a3ef2e386fa72da_r.jpg)
*关键调参参数影响热力图：max_num_seqs、gpu_memory_utilization、tensor_parallel_size 和 max_model_len 分别影响延迟、吞吐、成本和复测闭环*

`max_num_seqs` 控制同时活跃的序列数量上限。提高它可能提高吞吐，因为每轮 decode 有更多请求参与；也可能增加排队、竞争和每轮调度复杂度。若 KV cache 预算不足，提高这个值只会让更多请求争抢显存。

`gpu_memory_utilization` 控制引擎愿意把多少 GPU 显存用于模型和 KV cache 等工作区。调高它可以容纳更多 KV cache，降低因显存预算不足导致的排队；但安全边际变小，临时 buffer、峰值分配和碎片波动更容易触发 OOM。线上服务通常要留出保守余量，而不是追求水位贴满。

`tensor_parallel_size` 决定模型是否跨多张 GPU 做张量并行。它能降低单卡显存压力，让更大模型跑起来，也可能因为跨卡通信增加延迟。对大模型和长上下文，它可能是必要条件；对小模型和低并发，它未必划算。

`max_model_len` 决定服务允许的最大上下文长度。提高它会增强能力，尤其是长文档、长对话、复杂 RAG 场景；但它也会抬高最坏情况下的 KV cache 需求。若业务没有真正使用长上下文，把上限开得过大，相当于为罕见长请求牺牲了整体容量。

调参的纪律是一次只改少数变量，并且同时看 p50/p95/p99、TTFT、TPOT、tokens/s、显存水位和错误率。只看平均值很危险，因为很多推理问题最先伤害 tail latency。一个参数让平均 tokens/s 上升 20%，但 p99 TTFT 从 1 秒变成 8 秒，对实时服务可能是失败优化。

## 08. Benchmark 要模拟真实流量，而不是给引擎找好看数字

推理压测最容易犯的错误，是用过于整齐的输入输出长度。比如所有 prompt 都是 128 token，所有输出都是 128 token，并发固定，持续满载。这种压测能比较 kernel 和基础吞吐，但不能代表真实服务。真实流量里，prompt 长度有长尾，输出长度不可预测，用户到达不是整齐批次，RAG 可能塞入大段 context，某些租户会在短时间内提交大量请求。

一个更有用的 benchmark 至少要包含四组分布。第一是 prompt length 分布，按真实日志或预期业务构造短、中、长请求。第二是 output length 分布，区分短回答、长回答和异常长输出。第三是 arrival pattern，包含稳定流量、突发流量和低峰空闲。第四是模型与功能分布，区分聊天、摘要、代码、RAG、结构化输出等路径。

压测指标也要分桶。按输入长度分桶看 TTFT，按输出长度分桶看 TPOT 和端到端延迟，按租户或功能看错误率，按时间窗口看 GPU 利用率和 KV cache 水位。把所有请求混成一个平均数，会让长尾问题消失在报表里。

还要区分冷启动和热路径。模型刚加载、CUDA context 初始化、图捕获、prefix cache 为空时，前几次请求可能明显慢。线上服务需要 startup probe、预热请求和流量切换策略。压测只看预热后的 5 分钟，不代表发布时用户不会遇到冷启动毛刺。

benchmark 的目标不是证明某个引擎“赢了”，而是找出在你的 SLO 下，哪个组合更稳。结果应包含配置、版本、硬件、模型、输入输出分布、并发曲线和失败案例。没有这些上下文的性能数字很难复用，也容易误导后续容量规划。

## 09. 容量规划要把峰值和长尾请求算进去

容量规划不能只拿平均 QPS 乘以平均 tokens。LLM 服务的容量常常被长尾请求和峰值流量决定。一个 200 token prompt、输出 100 token 的请求，与一个 12000 token prompt、输出 2000 token 的请求，对 KV cache 和 GPU 时间的占用不是一个量级。若不限制长请求，少数请求就可能把服务推入排队。

容量规划可以从 token budget 开始。估算每秒输入 token、每秒输出 token、并发活跃序列、平均和 p95 上下文长度、平均和 p95 输出长度。再结合模型在目标硬件上的实际 tokens/s，计算需要多少副本满足 p95 或 p99 SLO。这里要使用实际压测吞吐，而不是供应商理论 FLOPS。

峰值策略也要写清楚。流量突然上升时，是排队、限流、降级到小模型，还是降低 max_tokens？长上下文请求是否进入独立队列？批处理任务是否让路给实时请求？免费用户和付费用户是否共用同一组 GPU？这些不是业务细节，它们直接决定推理调度是否稳定。

多模型服务还要考虑路由。简单任务可以走小模型，复杂任务走大模型；短上下文走低延迟队列，长文档走吞吐队列；RAG 召回文档过多时先压缩 context，再进入推理引擎。模型路由的价值不只是省钱，也是在保护大模型 GPU 不被简单请求占满。

容量规划最后要落到变更机制。模型升级、上下文上限调整、量化版本切换、引擎升级，都可能改变吞吐和显存画像。每次变更前做小流量压测，变更后监控 TTFT、TPOT、KV cache 水位和成本。推理服务不是部署一次就结束的 API，它的性能边界会随着模型和流量持续移动。

## 10. 常见反模式

**只看 QPS，不看 token。** 生成式服务的请求大小差异太大。QPS 不变，输入输出 token 翻倍，GPU 压力可能直接翻倍。容量规划必须以 token 为核心。

**用平均延迟掩盖 tail latency。** 用户抱怨通常来自 p95/p99，而不是平均值。长 prompt、长输出、低 cache 命中、冷启动都会先体现在尾部。

**把 batch 调大当成万能优化。** 大 batch 可能提高吞吐，也可能拉长 TTFT。实时服务需要控制 batch 等待和队列策略，不能只追求 tokens/s。

**把上下文上限开得过大。** 长上下文能力有价值，但上限越高，最坏情况下 KV cache 越贵。业务没有用到的长度，不应该免费占用服务容量。

**量化后只看能不能加载。** 量化可能降低显存和成本，也可能影响质量、kernel 路径和输出稳定性。它是需要评估的模型变更，不是单纯部署参数。

**同一队列混跑所有任务。** 实时对话、批量任务、内部低优先级任务混在一起，会让批处理长请求伤害交互体验。队列隔离和优先级是推理平台的基本能力。

**用单次 benchmark 决定长期选型。** 引擎版本、模型结构、硬件、量化格式、请求分布都会改变结论。选型要看可维护性和复测机制。

## 11. 推理服务上线前的检查清单

- 指标口径是否完整：TTFT、TPOT、端到端延迟、tokens/s、错误率、KV cache 水位、$/1K tokens。
- SLO 是否按场景拆分：实时对话、代码补全、批处理、内部工具是否有不同阈值和动作。
- 压测是否模拟真实流量：prompt length、output length、到达模式、租户和功能分布是否接近线上。
- 成本公式是否带单位：GPU hour 是否正确换算到 GPU second，是否区分理论吞吐和有效吞吐。
- 参数是否有变更记录：`max_num_seqs`、`gpu_memory_utilization`、`tensor_parallel_size`、`max_model_len` 改动后是否保存压测结果。
- 队列是否隔离：实时请求、批处理请求、长上下文请求、低优先级任务是否分开治理。
- 峰值策略是否明确：排队、限流、降级、扩容、拒绝超长请求分别在什么条件下触发。
- 引擎选型是否可维护：升级、回滚、模型转换、量化、监控和日志是否有人负责。

推理服务的成熟度，不体现在“跑起来”三个字上，而体现在指标、预算和动作是否闭环。能说清楚三角关系的团队，才有可能把延迟、吞吐和成本一起管住。
