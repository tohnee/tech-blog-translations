最近网络上关于 OpenRLHF 和 veRL 的讨论和争议比较多，作为原创作者不得不发一个声明。

> 一句话就是 OpenRLHF 是跑跑卡丁车 而 veRL FSDP 是 QQ飞车

## 1. OpenRLHF 和 veRL 的性能差异

veRL 的 FSDP RLHF 和 OpenRLHF (DeepSpeed) 并没有任何本质上的性能差异，因为都是用 vLLM 推理和 ZeRO3 训练，veRL原论文实验数据为基于 Megatron 的 RLHF vs OpenRLHF 0.2 老版本的对比。如果你觉得有性能差异大概就是没用对，目前 FSDP 比 Deepspeed略快，**但是随着 DeepSpeed 的 deepcompile 尤其是 AutoTP 功能的发布，性能目测会反超**。

## 2. 关于 Hybridflow 自由调度

任何用 Ray 开发的 RLHF框架都可以自由调度，因为 Ray 原生提供了 placement group 功能，这方面只要用 ray 的框架都行。**也就是 Hybridflow 只是 Ray Placement Group API 起了一个好听的名字而已**。 OpenRLHF 目前完整实现了 Hybridflow，反而 veRL 没有实现，比支持如独立部署 vLLM 和 Actor 防止大模型(32B+ 或者长文本)训练的时候 OOM。OpenRLHF 是第一个基于 Ray Placement Group API 去支持这个功能的框架。

## **3. Hybrid Engine**

Hybrid Engine 是 DeepSpeedChat 最早提出的设计概念，并不是 veRL 的原创贡献。目前 veRL 和 OpenRLHF 都支持这个功能。

## 4. Ray + vLLM + HF Transformers + ZeRO3 做 RLHF 训练

这套范式是目前最简洁易用的高性能 RLHF 训练方案之一，**在保证了易用性的同时实现了高性能**。**最早由 OpenRLHF开源**并提出 (2023.8月开源 2024.1 大部分功能完成)，veRL FSDP 完全移植了这套方案。当初的核心想法是以**HF权重格式为桥梁，基于 ZeRO3 / AutoTP 等机制实现无缝权重同步和高性能推理**，避免使用 Megatron 这种重量级框架。

## **5. Single Controller**

Update 2025/5

veRL论文中的 Single Controller 这个概念和 HybridFlow一样同样来自于Ray的设计范式。早期 OpenRLHF第一版实现 Ray RLHF的时候有一个 RayPPOActorGroup的概念，其想法是用一个Ray Group类管理一组Deepspeed ZeRO DP进程，且提供了一个 async_run_method 接口批量控制组内进程，这就是 Single Controller的核心想法。而这个接口早期没有被启用是因为当时一套代码需要同时兼容Ray和非Ray两个路径的 RLHF 实现，后来移除了非Ray的代码自然就启用了这个API。

[https://github.com/OpenRLHF/OpenRLHF/blob/494850f50342ed38d5ae76ef45a3207f3523b582/openrlhf/trainer/ray/launcher.py#L300](https://github.com/OpenRLHF/OpenRLHF/blob/494850f50342ed38d5ae76ef45a3207f3523b582/openrlhf/trainer/ray/launcher.py#L300)

**最后感谢字节能免费把自己内部的框架开源出来方便大家使用并持续维护，促进开源社区的蓬勃发展 (比如支持了 FSDP / Ulysses)，但希望相关朋友不要拉踩我们这些开源框架。**OpenRLHF 作为0经费纯开源项目开发进度无法和 veRL 这类大厂商业项目竞争~ 仅希望通过此文保留 OpenRLHF 对 RLHF开源社区做出的贡献。
