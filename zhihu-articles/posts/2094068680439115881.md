最近我们把 Rufus-Air 的技术报告挂上了 arXiv（ [http://arxiv.org/abs/2609.29421](http://arxiv.org/abs/2609.29421) ），这是我在 Amazon 的收官之作。报告里写的，是我们一个不大的研究团队在 Amazon Search 从零搭一整套后训练 recipe 的过程。

先说清楚一件事： **这不是一份冲 SOTA 的报告** 。团队的research算力并不宽裕（production算力另算，而且pre-training还占了大部分），我们一开始就没打算拼性能。况且现在各家的后训练 recipe 大同小异，报告里能看到的那些差别，很多都来自各自在算力限制下做的取舍。Rufus-Air 也一样，里面不少选择得结合我们手上的算力来看。

这份报告原本只是第一版。我们的计划是在它的基础上，把数据、infra 和 recipe 一直迭代下去。后来因为业务方向调整，项目没再继续，团队成员也陆续去了别处，它就成了第一版，大概也是最后一版。也正是因为这样，我们才能把这套 recipe 写得足够细，细到几十个节点的团队也能照着做，里面有很多平时不太会公开的一手训练细节。为了把它发出来，内部审核前后走了差不多五个月。

这篇文章不打算复述报告，细节都在原文里。我想换个角度，聊几件我觉得更重要的事：后训练到底难在哪，一个小团队是怎么做成这件事的，还有我们留下的遗憾。

### 我们做了什么

项目从 2025 年 9 月做到 2026 年 4 月，中间有两个月去支援 post-training的production，实际做了五六个月。base 用的是 GLM-4.5-Air-Base，总参数 106B、激活 12B 的 MoE。整条 pipeline 有八个阶段：先做 SFT，然后是 Reasoning RL、Coding RL 和 IF RL（指令遵循），再是 General Agent、Coding Agent 和 Search Agent 三个 agent 阶段，最后用 RLHF 收尾。说是”从零”，意思是数据都来自公开来源，框架用的都是开源组件，没有内部的 teacher 模型可以蒸馏，也没做新的人工标注。算力上，大多数时候不超过 400 张 H200。

至于结果，超过官方的 GLM-4.5-Air 说明不了太多，它毕竟是 2025 年夏天的模型。更值得看的，是跟我们做项目这段时间里发布的模型比。INTELLECT-3 是 Prime Intellect 在同一个 base 上做的后训练，起点完全相同，比的就是后训练本身。我们报告的 20 项 benchmark 里，Rufus-Air 项项领先。Nemotron-3-Super 那边，20 项里我们赢了 12 项；跟 Qwen3.5-122B 也不算落后（Qwen 用的是官方公布的数字）。对我们来说，这些结果已经足够说明 **这套数据和 recipe 是靠得住的** 。

### 后训练到底难在哪

从外面看，后训练挺简单的。SFT、RL、agent、RLHF，随便翻开一份技术报告，差不多都是这几步。所以很多人觉得，把开源框架搭起来、数据备好，剩下的就是把流程跑通。

真正上手之后才会发现，每一步背后都是一个复杂的系统。数据、reward、rollout 引擎、训练框架、agent 的沙箱环境互相牵连，一个地方出了问题，症状往往在别的地方冒出来。更麻烦的是，很多问题根本不报错，训练照样跑，只是不知不觉地变差了。

当然，数据是另一个大难题，而且更复杂。原始数据从哪来、怎么拿到、质量怎么把关，每一步都不简单。我们这次用的都是公开数据，报告里写的是怎么筛、怎么调，不涉及原始数据的获取。这块不是我们团队这次的主要目标，这篇文章也不展开。

在数据之外，我觉得最能拉开团队差距的，是 **出了问题，能不能在这么一个系统里找到病根，拿出管用的解决办法** 。而且还得在算力很紧的情况下做到。没条件靠大规模 sweep 把每个疑问都试一遍，每跑一次实验，都得回答一个明确的问题。这种能力论文里很少写，大家聊 research 的时候也很少提。不少人 research 做得很好，对这一块其实没什么概念。

报告里这样的例子不少，这里挑三个说说。

第一个是 Coding RL。训练过程中，模型的回复越来越长，每一轮都有一成到近三成的样本撞上 64K 的长度上限。被截断的样本不参与 loss，能贡献梯度的数据就在悄悄变少。问题出在长度上限这个配置上：模型的行为变了，配置没跟上。我们的处理很直接，第 23 步把上限提到 128K，从当时的 checkpoint 接着训。截断率降到千分之一以下，reward 也重新涨了起来。算法没动，也没从头再训。

第二个是多轮的 agent RL。最省事的写法，是每一轮都把对话拼成文本，再重新 tokenize 喂给模型。问题是，重新 tokenize 得到的序列，不一定就是模型当时采样出来的那一串；chat template 在越来越长的历史上反复套用，还可能把前面的轮次改掉，而且不留痕迹。训练不会报错，可模型学的已经不完全是它自己生成的东西，严格来说已经不是 on-policy 了。我们的做法是 token-in/token-out：rollout 引擎直接收 token ID、吐 token ID，环境把每一轮的 token 原样接到轨迹后面。训练只认这条 token 轨迹，文本只拿来看和做评测。

第三个是 Search Agent，也最能说明怎么用最少的实验做决定。这个阶段的 reward 来自 LLM judge，本身就有噪声：它会给部分分，同一个答案打两次分也不一定一样。GRPO 默认会用组内标准差去归一化 advantage。推一下就会发现，如果一组里只有一条轨迹成功，归一化之后，它的 advantage 跟它比别人高出多少分没有关系。真正答对的一条，和只多拿了 0.1 部分分的一条，拿到的 advantage 一模一样。偏偏我们的数据筛选会留下八次里只答对一次的难题，这种组很常见，judge 的一点打分噪声，就被放大成了跟真正答对一样大的信号。想清楚这一点之后，我们只做了一组 ablation，两边只差这一个开关。去掉标准差归一化的那一边，每个对应的评测点都领先，这事就定下来了。

这三个例子都谈不上新算法，靠的是同一种能力：从现象一路追到原因，找一个够用、能落地的办法，再用尽量少的实验确认它。算力越少，这种能力就越关键。这篇文章最想说的，其实就是这一点。

报告里总结了四条经验：SFT 要做足、做得多样，它打下的是模型的能力底子；RL 的算力只花在模型当前学得动的题上；阶段的先后，要看 reward 有多容易被 hack；infra 本身就是 recipe 的一部分。每条背后的细节和证据，报告里都有，这里就不展开了。

### 一个小团队是怎么做成这件事的

这种能力放到团队里，首先靠的是怎么组织人。我们团队人手没有冗余，也没有中间层，连专门的工程组都没有。每个阶段都有一个人从头管到尾，每个 scientist 写的代码自己负责，研究和工程一肩挑，平时大量用 AI coding 工具提效。这样一来， **从发现现象、追查原因到动手修好，整条链都在同一个人手里** ，不用等别的团队排期，也省了来回交接的沟通成本。上一节那几个问题，就是这么找出来、解决掉的。

人手少，只能互相借调，哪里吃紧就往哪里补。很多人的工作横跨好几个阶段，数据、训练、评测都参与过。八个阶段又是串行的，前面一个卡住，后面全得等，所以人和算力一直跟着瓶颈来回调。

做决定也尽量放在一线。关键的事由项目负责人和直接干这件事的 scientist 一起商量着定，没有谁一个人说了算。几位项目负责人会直接跟各阶段负责人讨论设计和实验，其他人更多是提建议。定下来以后，参与决定的人一起担着，只提了建议的人不用为结果负责，也没人甩锅。

定的时候主要看证据，偶尔也参考以前的经验。在这个团队里，拍脑袋做的决定是会掉信誉的，所以大家都很谨慎。证据不够，就先跑一个有针对性的小实验把证据补上，再做关键的决定。上一节 Search Agent 的那组 ablation，就是这种情况。

### 留下的遗憾

回头看，报告里有些选择其实是算力不够时的无奈之举。最明显的是 RL 的安排：Reasoning RL、Coding RL 和 IF RL 这三个阶段本可以合在一起训，三个 agent 阶段大概也能合并。我们估计合起来训会更稳，效果也可能更好。可算力有限，只能拆开，一个阶段接一个阶段地串着做。好在分阶段的 RL 也比较稳定，这么做行得通，但不是我们最想要的方案。Coding Agent 也一样，有多少算力就训多少，没训到收敛，手上还有一大批现成的任务没用上。

这些都不是方向上的问题。做到后面，我们心里越来越有底，下一步要做什么也很清楚。 **如果当时算力给够，这个团队能做的远不止这些** 。可惜第一版做完，项目就停在了这里。

### 写在最后

团队里已经有好几位去了 OpenAI、Anthropic、Google DeepMind、Meta 和 NVIDIA。能和这样一群人共事，我很自豪，以后有机会，我还想跟他们每个人再合作一次。
