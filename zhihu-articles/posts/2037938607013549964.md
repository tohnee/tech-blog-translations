### 一、从一个具体的内存压力场景出发

假设你在生产环境部署 Llama-3-70B，TP=4（4 张 H100 80GB）。

```text
模型权重：70B × FP16 = 140 GB（4 卡 TP，每卡约 35 GB）
每卡剩余显存：80 - 35 = 45 GB

单个请求的 KV Cache（序列长度 4096 token）：
  = 2（K+V）× 80层 × 8头（GQA）× 128维 × 2字节（FP16）× 4096
  ≈ 1.34 GB / 请求

4 卡合计 KV Cache 容量：45 × 4 = 180 GB
理论最大并发：180 / 1.34 ≈ 134 个请求
```

但实际并发数通常只有理论值的 20%~40%，主要因为两个碎片问题：

**内部碎片（Internal Fragmentation）**：无法预知每个请求的实际输出长度，只能按最大长度预分配。

```text
请求 A 按 max_output=4096 预分配：
┌──────────────────────────────────────────────────────────────────┐
│ ████████████░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░  │
│ 实际用了 512 tokens              ← 3584 tokens 的空间白白浪费 →    │
└──────────────────────────────────────────────────────────────────┘
```

**外部碎片（External Fragmentation）**：请求释放后留下大小不规则的空洞，新的大请求找不到连续空间。

```text
GPU 显存（总 180 GB，看似剩 80 GB，实则全是碎片）：

┌──┬──────┬──┬───────┬──┬──────────┬──┬──────────┬──┐
│用│空8GB │用│空15GB │用│  空20GB  │用│  空37GB  │用│
└──┴──────┴──┴───────┴──┴──────────┴──┴──────────┴──┘

新请求需要 40GB 连续空间 → 拒绝！虽然总空闲 80GB
```

### 二、PagedAttention：向操作系统借鉴智慧

### 2.1 OS 的解法：分页

操作系统早就解决了相同的问题——进程内存管理：

- 把物理内存切成固定大小的**页（Page，通常 4KB）**
- 每个进程看到**连续的虚拟地址空间**，实际映射到分散的物理页
- 维护**页表（Page Table）**做虚拟地址 → 物理地址的翻译

vLLM 把完全相同的思想搬到了 KV Cache：

```text
OS 概念                     PagedAttention 对应概念
──────────────────────────────────────────────────────
物理内存页（4KB）            KV Block（如 16 tokens 的 KV）
虚拟地址空间                 请求的逻辑 token 序列
页表（Page Table）           Block Table（逻辑块 → 物理块）
内存分配器（malloc/free）    BlockPool（预分配的 block 池）
LRU 页面置换                LRU/LFU KV 块驱逐
```

### 2.2 物理 Block 池与 Block Table

系统启动时，把所有可用 GPU 显存切成**固定大小的 block**（block_size = 16 tokens 的 KV 是常见配置），存入 BlockPool。之后不再做动态 malloc/free：

```text
BlockPool（GPU 显存预分配，共 N 个 block）：

Block#0  Block#1  Block#2  Block#3  Block#4  ... Block#N-1
┌─────┐  ┌─────┐  ┌─────┐  ┌─────┐  ┌─────┐     ┌─────┐
│16tok│  │16tok│  │16tok│  │16tok│  │16tok│ ...  │16tok│
│ KV  │  │ KV  │  │ KV  │  │ KV  │  │ KV  │     │ KV  │
└─────┘  └─────┘  └─────┘  └─────┘  └─────┘     └─────┘
  空闲     已用     空闲     已用     已用            空闲
```

每个请求维护一张 **Block Table**，记录逻辑 block → 物理 block 的映射（物理位置完全不需要连续）：

```text
请求 A（已生成 40 tokens，需要 3 个 block）：
  逻辑 Block 0 → 物理 Block #3   ←┐
  逻辑 Block 1 → 物理 Block #7    │  完全不连续！
  逻辑 Block 2 → 物理 Block #1   ←┘  (block#2 可能只填了 8/16 token)

请求 B（与 A 有相同 system prompt 前缀）：
  逻辑 Block 0 → 物理 Block #3   ← 和 A 共享！ref_count = 2
  逻辑 Block 1 → 物理 Block #12  ← B 自己的 block
```

**关键效果**：

- 外部碎片消失：不需要连续物理内存
- 内部碎片极小：最多浪费最后一个 block（< 16 tokens）
- 共享前缀：相同内容的 block 只存一份，用 ref_count 追踪引用

### 2.3 PagedAttention 在 GPU 上怎么做 Attention？

传统 Attention kernel 假设 KV 数据连续。PagedAttention 修改了 CUDA kernel，让它在计算时**查 block table** 而非直接寻址：

```text
当前 token 的 Q ──┐
                  ↓
  for 逻辑块 i = 0, 1, 2, ...:
      物理块 j = block_table[request][i]     ← 查表
      K = kv_cache[j, 0, :, :]             ← 从物理块取 K
      V = kv_cache[j, 1, :, :]             ← 从物理块取 V
      score_i = Q · K^T / √d_head

  output = softmax(所有 score) · 所有 V
```

代价：每次 attention 需要额外的随机内存访问（L1 cache miss），比连续 KV 有约 10~20% 的性能开销。vLLM 通过 CUDA Graph 和 block table 预取来缓解。

### 三、Prefix Caching：避免重复计算相同前缀

### 3.1 问题：相同的 system prompt 反复计算

客服系统、代码助手等场景中，所有用户的请求都以相同的 system prompt 开头。

```text
用户 1：[你是一个专业的代码助手...] [帮我写一个排序算法]
用户 2：[你是一个专业的代码助手...] [帮我实现二叉树]
用户 3：[你是一个专业的代码助手...] [解释递归是什么]
         ↑──────── 相同的 512 tokens ────────↑
              prefill 计算了 3 次，完全浪费！
```

Prefix Caching 的思路：把相同前缀的 KV Cache 缓存起来，后续请求直接复用。

### 3.2 Block Hash：内容寻址

Prefix Caching 的核心是用**内容的 hash**作为 block 的唯一标识（而不是内存地址）。用的是**链式哈希**：

```text
Block 0（tokens[0:16]）：
  hash_0 = hash(tokens[0:16])

Block 1（tokens[16:32]）：
  hash_1 = hash(prev=hash_0, tokens[16:32])   ← 带入上一个 block 的 hash！

Block 2（tokens[32:48]）：
  hash_2 = hash(prev=hash_1, tokens[32:48])
```

**为什么必须链式哈希？**

如果只哈希当前 block 的 token 内容，会产生致命误判：

```text
请求 A：[前言X] [摘要Y] [正文Z]
请求 B：[前言P] [摘要Y] [正文Z]
                 ↑ 两者 block_1 的 token 内容完全相同！

但 KV 值不同：Causal Attention 让 block_1 的 KV 依赖 block_0 的内容。
如果复用了 A 的 block_1 给 B，KV 是错误的，生成内容会出问题。
```

链式哈希让 hash_1 隐含了”前面所有 block 的历史”，确保：

> 相同的 token 内容 + 相同的历史前缀 → 相同的 hash → KV 确实可以复用

### 3.3 缓存查找与命中流程

```text
新请求：tokens = [t0..t15, t16..t31, t32..t47, t48..t63, t64..t79]
                   Block 0   Block 1   Block 2   Block 3   Block 4

Step 1: 计算 hash_0，查缓存
        → 命中！（有请求算过相同前缀）
        → Block #5 直接加入 block table，ref_count[#5]++

Step 2: 计算 hash_1（依赖 hash_0），查缓存
        → 命中！Block #12
        → ref_count[#12]++

Step 3: 计算 hash_2，查缓存
        → 未命中！→ 后续不再查，从 Block 2 开始做 prefill

────────────────────────────────────────
结果：
  Block 0、1：跳过 prefill（节省 32 tokens 的计算）
  Block 2~4：重新计算（48 tokens）
  TTFT 降低 40%（从 80 tokens → 48 tokens 的 prefill）
```

### 3.4 RadixAttention（SGLang）：树形管理前缀

vLLM 用 HashMap 管理缓存（hash → block），SGLang 用 **Radix Tree（基数树）** 管理，更适合多用户前缀复用场景：

```text
树的每个节点 = 一个 KV Block（含 block hash 和物理 block 指针）

                          根节点
                         /      \
               [hash_sys_A]    [hash_sys_B]
               system_prompt_A  system_prompt_B
               workers:{W1,W2}  workers:{W3}
              /              \
        [hash_q1]        [hash_q2]
        用户问题A1        用户问题A2
        workers:{W1}     workers:{W2}
             |
        [hash_q1_c2]
        问题A1 的续写
        workers:{W1}
```

**RadixTree 的关键优势**：

- 共享前缀自动去重（system_prompt 只存一份物理 block）
- 驱逐只发生在叶节点（父节点被多个分支共用，不能驱逐）
- 查找 O(前缀长度)，精确找到最长匹配前缀

### 四、Dynamo KVBM：打破单 GPU 内存上限

### 4.1 单 GPU 的天花板

PagedAttention + Prefix Caching 已经大幅提升显存利用率，但还受制于单卡容量（H100 = 80GB）。

典型瓶颈场景：

- **超长上下文**：128K tokens，单请求 KV Cache 就需要数十 GB
- **大量前缀热点**：几百个 system prompt 的 KV 都需要常驻 GPU
- **成本优化**：用廉价 SSD 替代昂贵 GPU 显存

Dynamo KVBM（KV Block Manager）的答案：**多级存储分层**，把 KV Cache 从 GPU 向下延伸。

### 4.2 四级存储层次（G1~G4）

```text
层级    名称           介质                 容量          带宽         特点
────────────────────────────────────────────────────────────────────────────
G1    Device Pool    GPU HBM              80 GB        3.35 TB/s   唯一可直接参与 GPU 计算
G2    Host Pool      CPU DRAM（Pinned）    512GB~2TB    50 GB/s     页锁定内存，CUDA DMA 直传
G3    Disk Pool      本地 NVMe SSD        4~16 TB      7 GB/s      GDS 可绕过 CPU
G4    Remote Store   远端存储/对象存储     近乎无限      10~100GB/s  RDMA 传输
────────────────────────────────────────────────────────────────────────────
访问速度：G1 >> G2 >> G3 >> G4
容    量：G1 << G2 << G3 << G4
```

**核心约束**：只有 G1 的 block 才能被 GPU Attention 计算直接使用。G2/G3/G4 的 block 在被请求使用前，必须先**搬运（Onboard）** 到 G1。

**为什么 G2 要用 Pinned Memory（页锁定内存）？**

```text
普通 CPU 内存（Pageable）：
  GPU DMA → OS 先拷到临时 pinned buffer → 再传 GPU
  带宽：~15 GB/s（经过两次拷贝）

Pinned Memory（cudaMallocHost 分配）：
  GPU DMA → 直接从 CPU 物理内存传到 GPU（OS 不介入）
  带宽：~50 GB/s（一次 DMA，无额外拷贝）
```

### 4.3 Block 的生命周期：四种状态

KVBM 的每个 block 在生命周期中经历四种状态：

```text
┌──────────────────────────────────────────────────────────────────────┐
│                         Block 状态一览                                │
├────────────┬─────────────────────────────┬──────────┬──────────────┤
│    状态     │         含义                │  谁持有   │ Router 可见？ │
├────────────┼─────────────────────────────┼──────────┼──────────────┤
│  Reset     │  完全空闲，无有效 KV 数据    │ ResetPool │      否       │
│  Mutable   │  正在被 GPU 写入 KV 数据     │ vLLM 调度 │      否       │
│  Registered│  数据写完，已全局注册        │ Registry  │    是 ✓      │
│  Inactive  │  注册过，但当前无请求引用    │InactivePool│   是 ✓      │
└────────────┴─────────────────────────────┴──────────┴──────────────┘
```

状态流转：

```text
分配给请求
   ┌──────────┐  ──────────────────→  ┌──────────────┐
   │ ResetPool│                        │ Mutable Block │
   │ （空闲） │  ←──────────────────── │ （写入中）    │
   └──────────┘    异常/取消，自动归还  └──────┬───────┘
        ↑                                      │ 填满 16 tokens
        │                                      ↓
        │                             ┌──────────────┐
        │                             │ Complete Block│
        │                             │（等待注册）  │
        │                             └──────┬───────┘
        │                                    │ register_block()
        │                                    ↓
        │                         ┌────────────────────┐
        │                         │ Registered/Active  │ ← Router 现在知道
        │                         │ （有请求正在用）   │   这个 worker 有此 KV
        │                         └──────────┬─────────┘
        │                                    │ 请求完成，引用归零
        │                                    ↓
        │                         ┌────────────────────┐
        │                         │   Inactive Pool    │ ← 可被新请求复用
        │  内存压力大，被驱逐 ←───  │ （有 KV 但无引用）│   也可被驱逐
        └─────────────────────────└────────────────────┘
```

**设计精髓**：Inactive Pool 中的 block 数据仍然有效。新请求来时，可以直接复用这些 block（Prefix Caching 的物理载体），完全不需要重新 prefill 计算。

### 4.4 三池分配策略

BlockManager 用三个”池”管理所有 block：

```text
┌─────────────────────────────────────────────────────────────────┐
│                   BlockManager 三池架构                           │
│                                                                 │
│  ResetPool          InactivePool              ActivePool         │
│  ┌──────────┐       ┌──────────────┐          ┌───────────┐     │
│  │  空闲    │       │ 已注册       │          │ 正在使用  │     │
│  │  block   │       │ 但无引用     │          │ 引用 > 0  │     │
│  │ （无数据）│       │ （有 KV）    │          │  （有 KV）│     │
│  └──────────┘       └──────────────┘          └───────────┘     │
│       ↑                  ↑│                        │            │
│       └──── 驱逐 ─────── ┘│                        │            │
│                            └────── 命中复用 ────────┘            │
└─────────────────────────────────────────────────────────────────┘
```

**当请求需要 N 个新 block 时**：

```text
Step 1：先从 ResetPool 取（零成本，无副作用）
         ├── 够 N 个？ → 完成
         └── 不够，差 k 个 → Step 2

Step 2：从 InactivePool 驱逐 k 个低频 block（TinyLFU 决定选哪些）
         ├── 够？ → 驱逐，发布 KV Removed 事件，完成
         └── InactivePool 也不够？ → 分配失败（触发 load shedding，拒绝请求）
```

**注意**：ActivePool 中的 block 永远不会被驱逐（有正在进行的请求在用）。

### 4.5 TinyLFU：比 LRU 更聪明的驱逐策略

驱逐 InactivePool 中的 block 时，选的是**访问频率最低**的，而不是最近最久未访问（LRU）。

**为什么不用 LRU？**

```text
场景：GPU 里有 100 个 block（80 个是高频 system prompt 的 KV）

突然来了 500 个临时批处理请求（各种不同的 system prompt）
→ LRU：把这 500 个新 block 全写入，高频的 80 个全被驱逐
→ 后续正常请求命中率暴跌，TTFT 飙升
```

**TinyLFU 的核心思想**：用访问**频率**而不是访问**时间**来决定驱逐。

核心数据结构 **Count-Min Sketch**：

```text
用 4 个哈希函数 h0~h3，对应 4 个计数数组（宽度 W）

访问 block X 时：
  counter_0[h0(X) % W] += 1
  counter_1[h1(X) % W] += 1
  counter_2[h2(X) % W] += 1
  counter_3[h3(X) % W] += 1

查询 block X 的访问频率：
  freq(X) = min(counter_0[h0(X)], counter_1[h1(X)],
                counter_2[h2(X)], counter_3[h3(X)])

（取最小值：利用多哈希减少碰撞误差，估计值只会高估，不会低估）
```

**衰减机制**（防止历史记录无限累积）：

```text
每访问 N 次后，所有计数器整体右移 1 位（÷2）

效果：
  高频 system prompt：访问 1000 次，衰减多次后仍有较高计数
  临时批处理：访问 500 次，之后不再访问，经几次衰减后接近 0
→ 历史上真正高频的 block 得到保护
```

**驱逐决策**（Window TinyLFU = SLRU + TinyLFU 组合）：

```text
InactivePool 分为两个区：
  Window 区（约 20%）：新来的 block，还未经过频率验证
  Main 区（约 80%）：通过频率验证的高频 block

驱逐流程：
  候选者 = Window 区中频率最低的 block
  竞争者 = Main 区中频率最低的 block

  比较频率：
    候选者 > 竞争者 → 候选者晋升 Main，竞争者被驱逐
    候选者 ≤ 竞争者 → 候选者直接被驱逐
```

### 五、跨层数据搬运：Offload 与 Onboard

### 5.1 Offload（向下卸载：G1 → G2 → G3）

触发条件：G1 使用率超过阈值（如 85%）

```text
G1（GPU）使用率过高
     ↓
选出 InactivePool 中频率最低的 block（TinyLFU 决定）
     ↓
G1 → G2（GPU → CPU Pinned Memory）：
  CUDA 异步 DMA（cudaMemcpyDeviceToHost, async）
  带宽 ~50 GB/s，搬运 1 GB 约 20ms
  搬运完成 → 发布 KV Stored（G2）事件，通知 Router G2 也有此 block
     ↓（如果 G2 也快满了）
G2 → G3（CPU → NVMe SSD）：
  NIXL 写入 NVMe
  若支持 GDS：GPU 数据直写 SSD，CPU 几乎不参与（零拷贝）
  带宽 ~7 GB/s，搬运 1 GB 约 143ms
  发布 KV Stored（G3）事件

注意：G1 的 block 不立即释放！
  等 G2 确认写入完成后，G1 的 block 才进入"可驱逐"状态
  → 如果很快又有请求命中，可以直接用 G1 的，避免 Onboard 开销
```

### 5.2 Onboard（向上加载：G2/G3 → G1）

触发条件：Router 路由到某 worker，KVIndexer 发现该 worker 的 G2/G3 有命中 block

```text
路由命中 G2 上的 block（不在 G1）
     ↓
在 G1 分配空间（可能先驱逐 G1 的低频 block）
     ↓
G2 → G1（CPU → GPU）：
  CUDA DMA（cudaMemcpyHostToDevice, async）
  带宽 ~50 GB/s，1 GB 约 20ms
     ↓（如果命中在 G3）
G3 → G1（SSD → GPU，最慢路径）：

  有 GDS（GPU Direct Storage）：
    NVMe → PCIe → GPU HBM（CPU 几乎不参与）
    带宽 ~7 GB/s，1 GB 约 143ms

  无 GDS：
    NVMe → CPU → PCIe → GPU（需要 CPU 中转）
    带宽 ~3 GB/s，1 GB 约 333ms，且占用 CPU 资源
```

### 5.3 NIXL：统一的传输抽象

NIXL（NVIDIA Inference Xfer Library）把所有传输路径统一抽象，调用方只需指定源和目标，NIXL 自动选择最优协议：

```text
src / dst               NIXL 选择的传输路径
──────────────────────────────────────────────────────
G1 ↔ G1（同机多卡）     NVLink（~600 GB/s，最快）
G1 ↔ G1（跨机）         RDMA（IB 或 RoCE，~100 GB/s）
G1 ↔ G2（本机）         CUDA DMA/PCIe（~50 GB/s）
G2 ↔ G3（本机）         POSIX read/write 或 GDS（~7 GB/s）
任意 ↔ G4（远端）       NIXL RDMA P2P（~10~100 GB/s）
```

### 六、KV Events：KVBM 与 Router 的通信桥梁

KVBM 的状态变化需要实时通知 Router 的 KVIndexer，以便路由时正确选 worker。

### 6.1 两种关键事件

```text
事件类型         触发时机                         Router 的响应
────────────────────────────────────────────────────────────────────
KV Stored     block 注册到 Registry              在 Prefix Tree 中插入：
              （填满 16 tokens，prefill 完成后）    worker W 缓存了 block_hash H
                                                  → 路由时可以选 W

KV Removed    block 从 Registry 被驱逐            在 Prefix Tree 中删除：
              （InactivePool 被驱逐时）             worker W 不再缓存 block_hash H
                                                  → 路由时不再为此 block 选 W
```

**为什么是 block 粒度，而不是请求粒度？**

因为一个请求对应多个 block，各个 block 的生命周期不一致（有的 block 被后续请求长期共享，有的很快就被驱逐）。block 粒度的事件让 Router 的 Prefix Tree 更精准，路由命中率更高。

### 6.2 负载上报：decode_blocks

除了”缓存了什么”，Router 还需要知道”worker 有多忙”。每个 worker 定期上报：

```text
kv_used_blocks = GPU KV Cache 使用率 × 总 block 数
              = "当前这个 worker 正在 decode 占用多少 block"

例：总 block = 1000，KV Cache 使用率 60%
    kv_used_blocks = 600
```

Router 用这个值作为代价函数中的”负载项”，防止把所有请求堆到命中率高但已过载的 worker 上。

### 七、完整场景演练：从冷启动到命中

**场景**：客服系统，100 个用户，相同 system prompt（前 3 个 block，即 48 tokens）

```text
时刻 T0：第一个请求到达 Worker W1
─────────────────────────────────────────────────────────────────
  match_blocks([h0, h1, h2, h_q1]) → 全部 miss（冷启动）
  分配 4 个新 block（ResetPool）
  prefill 计算全部 4 个 block（完整计算）
  注册 → 发布 KV Stored × 4
  KVIndexer 更新：W1 → 缓存了 [h0, h1, h2, h_q1]

时刻 T1：第 2 个请求到达（相同 system prompt，不同问题）
─────────────────────────────────────────────────────────────────
  Router 查 KVIndexer：W1 命中 3 个 block（h0, h1, h2）
  代价 = 1.0 × 1（只需 prefill 1 个 block）+ W1_load → 选 W1

  match_blocks([h0, h1, h2, h_q2]):
    h0, h1, h2 → 命中 InactivePool → 移到 ActivePool（ref++）
    h_q2 → miss

  只 prefill 1 个新 block（节省 75% 的 prefill 计算！）
  TTFT 大幅降低

时刻 T2：G1 内存使用率超过 85%
─────────────────────────────────────────────────────────────────
  触发 Offload：TinyLFU 选出低频 block 搬到 G2（CPU Pinned）
  发布 KV Stored（G2）事件 → KVIndexer 更新（G2 也有这些 block）

  新请求路由时，Router 可以选择：
    命中 G1 → 立即可用，最快
    命中 G2 → 需 Onboard（~20ms 延迟），但比全量 prefill 快很多
    全部 miss → 正常 prefill

时刻 T3：长期无访问的 block 被驱逐
─────────────────────────────────────────────────────────────────
  TinyLFU 判断某 block 频率极低
  从 InactivePool 驱逐 → 回到 ResetPool（数据丢失）
  发布 KV Removed 事件 → KVIndexer 移除路由信息
  下次同样前缀的请求 → 需要重新 prefill（但 system prompt 的频率高，通常不会被驱逐）
```
