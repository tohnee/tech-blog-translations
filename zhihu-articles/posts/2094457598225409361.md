## 最近在做一些推理实验，发现后端选择对于端到端性能来说挺重要的，有些时候推理框架的auto不一定是最优的选择。就想着写一篇文章写一下当前模型推理可选择的后端。（暂时先以VLLM为例）

### 一、先区分这三个参数

在 vLLM 里，“MoE 后端”也分两类：

- `--attention-backend`：选择 Attention 计算后端。
- `--moe-backend`：选择 MoE 专家计算所用的 kernel。
- `--all2all-backend`：选择 Expert Parallel（EP）中的专家通信后端。

其中，`--all2all-backend` 主要在启用 MoE 专家并行时需要考虑；不使用 EP 时，通常先不用调整它。

### 二、Attention 后端有哪些选择

Attention 后端可以分为标准 Attention（MHA、MQA、GQA）和 MLA 两类。DeepSeek 等使用 MLA 的模型，需要特别确认后端支持情况。

| 后端 | 适用场景 |
| --- | --- |
| FLASH_ATTN | NVIDIA GPU 上的常见选择。vLLM 会按硬件选择 FlashAttention 版本：当前文档列出的默认版本为 Blackwell 上 FA4、Hopper 上 FA3、其他架构上 FA2。 |
| FLASHINFER | NVIDIA GPU 上的另一个主要选择。当前自动选择顺序中，Blackwell 的标准 Attention 优先尝试它；具体性能仍要按模型和负载测试。 |
| TRITON_ATTN | Triton Attention 路径，适合需要特定兼容性或作为其他后端不适用时的选择。 |
| FLEX_ATTENTION | 更灵活的 Attention 路径，适合需要特殊注意力模式或掩码的场景；不必默认认为它是常规服务的最快选项。 |
| TURBOQUANT | 面向相应 TurboQuant 配置的专用路径，需确认模型和 KV Cache 格式支持。 |
| FLASHINFER_MLA、FLASHMLA、CUTLASS_MLA、TRITON_MLA 等 | 面向 MLA 模型的后端。选择时要结合 GPU 架构、KV Cache 类型和页面大小；Blackwell 上的自动选择有独立的 MLA 优先级。 |
| ROCm、XPU 等平台后端 | AMD ROCm 和 Intel XPU 各有平台专用选项，例如 AITER、ROCm Attention 或 XPU MLA 后端，应按对应硬件的支持文档选择。 |

一般先让 vLLM 自动选择。若要手动测试，可用 `--attention-backend` 指定后端；也可以检查 `--attention-config` 中的相关配置。对多模态模型，vLLM 还提供组合后端，例如在需要图像双向注意力时用 Triton、在文本因果注意力时用 FlashAttention 或 FlashInfer。不要只看后端名称，应该核对当前版本的支持表和启动日志。[Attention 后端支持表](https://docs.vllm.ai/en/stable/design/attention_backends/)

### 三、MoE 计算后端有哪些选择

`--moe-backend` 决定的是专家网络如何计算。当前常见选项可以按用途大致分组：

| 后端 | 适用场景 |
| --- | --- |
| auto | 建议作为起点。vLLM 根据模型和硬件选择可用的 MoE 后端。 |
| triton、batched_triton | Triton MoE 路径。batched_triton 面向特定的 batched activation 格式，通常要与兼容的通信路径配套。 |
| deep_gemm | 适用于支持的 FP8 block-quantized MoE 计算。精度格式不匹配时不能直接套用。 |
| deep_gemm_mega_moe | DeepGEMM 的 MegaMoE 路径，属于较专门的实现；应先确认模型、部署方式和 vLLM 版本支持。 |
| cutlass、flashinfer_cutlass、flashinfer_trtllm | NVIDIA GPU 上的计算路径，适用条件取决于架构、量化格式和所用 kernel。 |
| flashinfer_cutedsl | 当前文档将其列为 FP4 专用选项，适合对应精度格式的模型。 |
| marlin、humming | 面向特定权重压缩或混合精度场景，需按模型量化方式选择。 |
| flashinfer_b12x、b12x | 面向特定 SM12x GPU 的专用选项，例如 RTX PRO 6000 等环境。 |
| aiter、flydsl、rdna3 等 | AMD ROCm 平台专用或特定架构选项；应按 GPU 型号和格式核对支持情况。 |
| emulation | 用于测试或验证的慢速模拟路径，不适合作为生产性能配置。 |

这些选项的可用性会随 vLLM 版本、模型和量化格式变化。尤其是 FP8、NVFP4、MXFP4 等低精度配置，要确认 checkpoint 格式与目标 kernel 一致。vLLM 的 MoE kernel 指南会列出不同 kernel 支持的格式及通信组合。[Fused MoE Kernel 指南](https://docs.vllm.ai/en/latest/design/moe_kernel_features/)

### 四、MoE 通信后端怎么选

MoE 模型启用 EP 后，token 需要在不同 GPU 上的专家之间分发和回收，这部分由 `--all2all-backend` 处理。

| 后端 | 适用场景 |
| --- | --- |
| allgather_reducescatter | 默认选项，通用性较好，适合先跑通 EP 配置并建立基线。 |
| deepep_high_throughput | 面向 Prefill 吞吐较重要的场景，尤其是多节点部署。 |
| deepep_low_latency | 面向 Decode 延迟较重要的场景；支持 CUDA Graph。 |
| deepep_v2 | DeepEP 的新通信路径；依赖和 NCCL 版本等要求要按当前部署文档检查。 |
| flashinfer_nvlink_one_sided、flashinfer_nvlink_two_sided | 面向使用 NVLink 的多节点系统，具体选哪种取决于互联拓扑和负载。 |
| moonep、mori_high_throughput、mori_low_latency | 面向特定 EP 通信和硬件部署的专用路径。 |
| nixl_ep、pplx 等 | 专用通信后端；应根据当前版本的依赖、硬件和部署要求启用。 |

vLLM 文档将 DeepEP 的 high-throughput 和 low-latency 路径分别定位于 Prefill 和 Decode 场景。若请求既有长输入又有大量生成，最好用自己的请求分布测，而不是只根据其中一个阶段做选择。[Expert Parallel 部署指南](https://docs.vllm.ai/en/latest/serving/expert_parallel_deployment/)

### 总结

选择 vLLM 后端时，可以记住这三点：

- **Attention 后端**看模型结构、GPU 和 KV Cache 配置。
- **MoE 计算后端**看专家 kernel 支持的量化格式和硬件。
- **MoE 通信后端**主要在启用 EP 后考虑，并根据 Prefill、Decode 和集群互联来选。

vLLM 的自动选择适合建立基线；手动指定后端，则应以当前版本的支持表和真实服务负载测试为准。这些年后端更新挺快的，这玩意还得不断学习。
