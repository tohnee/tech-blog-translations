> 论文：TableTune: Measured, Self-Correcting Draft-Length Tables for Dynamic Speculative Decoding<br>作者：Abhishek Malvankar, Paul Castro, Nick Mitchell, Lionel Villard（IBM Research）<br>arXiv：2610.38968（cs.ET / cs.AI，2026-10-28）｜代码：[http://github.com/asm582/tabletune](http://github.com/asm582/tabletune)

## 一、先说结论

投机解码（speculative decoding）的加速比不是常数，它随**批量大小**反向变化：空载时一次猜 3 个 token 几乎免费，满负载时同样的 3 个猜测会把每一步都拖慢。vLLM 为此提供了「按批量大小查表决定草稿长度」的机制（Dynamic Speculative Decoding），但这张表要人**手写**——写得对不对，没人验证。

这篇论文做了一件很朴素的事：**把这张表变成测出来的，并且在服务过程中自己纠错**。

- tuner 在 vLLM 自己的服务路径上，把「批量 × 草稿长度」网格逐个计时，**8 分钟**（H100）算出一张表；
- controller 是一个 vLLM 插件，读 vLLM 已经发布的接受率计数器，在线重建表，**不需要改引擎**；
- 在 H100 上，调优后的表在最差负载处距离「事后才知道的最优固定长度」只差 3.0–5.7%（EAGLE-3 / 4-bit / n-gram / 对话），DFlash 上是 11.6%，而任何一个固定长度最差都要丢 19.1%；
- 在 llm-d 的官方 optimized-baseline 部署（2×Qwen3-32B，TP=2，4 张 H100）里，高负载下比固定长度 3 快 **32%**，比 vLLM 文档里的示例表快 **25%**；
- 从一张「错表」出发，controller 能把吞吐拉回 **+58%**；工作负载切换后能找回 **96%** 的损失。

一句话概括它的立场：**草稿长度不是一个超参，而是一张要按 GPU、引擎、模型、流量分别测量的配置表。**

## 二、背景：投机解码什么时候才赚

解码阶段每个新 token 都要把整个模型的权重从显存读一遍，所以单步时间由**显存带宽**决定，而不是算力。投机解码的做法是让小模型（drafter）先猜 k 个 token，目标模型一次前向并行验证，接受前缀里对得上的部分，再自己补一个。被接受的 token 一定是目标模型本来会生成的，所以**输出分布不变**。

问题是每次猜测都是额外的工作。设第 i 个猜测及其之前全部被接受的概率为 aᵢ，则每步期望产出的 token 数是：

τ(k) = 1 + Σᵢ aᵢ （i 从 1 到 k）

于是「有用吞吐」（goodput，每秒产出的被接受 token 数）可以写成：

G(B, k) = B × τ(k) / T(B, k)

其中 B 是批量大小（一次前向里的请求数），T(B, k) 是这一步的墙钟时间。投机解码同时抬高分子和分母，**赚不赚取决于哪个涨得更快**。

直觉在这里很关键：显存带宽是「每步读一遍权重」的固定开销，所以只要每步产出的 token 数还没到 roofline 的拐点（ridge point，论文给出 T4 约 200、A10G 210、H100 SXM 约 300 token/步），多猜几个 token 几乎是白送的；一旦批量大了，每步已经在处理几百个 token，算力开始吃紧，再猜就是纯亏。

![](https://pic1.zhimg.com/v2-fc227a0bbeedeac9f5cc507e30c00330_1440w.jpg)

图 1：H100（V2 runner）、Qwen3-4B + EAGLE-3、代码 prompt，各固定草稿长度的吞吐占「该负载下最优固定长度」的百分比。批量为 1 时长草稿最好，128 个请求时草稿长度 1 反超，固定长度 1 在低负载丢 15%，固定长度 3 在高负载丢 12%。

这条曲线就是整篇论文的动机：**没有任何一个固定草稿长度在所有负载下都最优**。而实际服务里批量是连续批处理（continuous batching）动态变化的，operator 只能写一张表去近似这条曲线。

## 三、vLLM 现在的做法：一张手写表，和两个真实事故

vLLM 的 Dynamic SD 接受一个参数 `num_speculative_tokens_per_batch_size`，格式是若干区间 [起始批量, 结束批量, 草稿长度]。文档里的示例是：

[[1, 64, 3], [65, 128, 1], [129, 512, 0]]

意思是「1–64 个请求猜 3 个，65–128 猜 1 个，再多就不猜」。这段配置通常是从文档复制到生产环境里的，**没有任何工具检查它是否匹配当前的 GPU、模型、drafter 和流量**。

论文引用了两个 vLLM issue 作为证据：

- 批量在表的分界线附近抖动时，聚合吞吐会**崩塌**（issue #49548）；
- 在 H100 上，Dynamic SD 比完全不投机慢 **21–31%**（issue #49986）。

第二个数字尤其值得注意：投机解码本来是为了加速，结果配置不当反而比不开更慢。原因有三类，论文逐一拆开：表本身写错了（区间或者长度不对）、引擎在这种模式下退化成低效的执行路径（下面第十一节）、以及表没有跟随流量变化。

## 四、关键拆分：步时间可以离线测，接受率必须在线学

TableTune 的设计出发点是一个观察，把两个混在一起的东西分开：

| 量 | 依赖什么 | 稳定性 | 该在哪测 |
| --- | --- | --- | --- |
| 步时间 T(B, k) | GPU、引擎、模型、批量 | 稳定（同一台机器重复测偏差 1.4% 中位 / 5.7% p95） | 离线，一次网格测量 |
| 接受率 aᵢ（进而 τ(k)） | 流量、任务、采样温度 | 会漂移（同一 drafter 在 7 个负载上 τ(3) 从 1.81 到 2.43） | 在线，持续跟踪 |

这个拆分是整篇论文最值得学的部分。它把「贵的测量」（要跑满负载扫描）压在离线一次，「便宜的估计」（只数计数器的比值）放在在线循环里——后者不占 GPU 任何算力。

**为什么不能「拟合」步时间？** 这是论文反复强调的：步时间曲线会在某个批量处出现**跳变**（典型原因是某个 kernel 的 tiling 或者 CUDA graph 形状切换），线性模型会把它抹平。实测证据在第六节：H100 上草稿长度 3 的步时间在批量 80 处实测 9.7 ms，而拟合值是 8.0 ms——正是这个 1.7 ms 的偏差让基于拟合的控制器一直不肯把长度从 3 降到 2，损失 9.3%。

## 五、设计（上）：tuner，用「强制拒绝」把批量钉住

![](https://picx.zhimg.com/v2-620423dbb9ffd6d30e9c8110242ff59f_1440w.jpg)

图 2：TableTune 总览。tuner 由步时间 profiler、接受率 profiler、表构造器组成，产出 vLLM 原生格式的表；controller 是 vLLM 插件，从线上计数重建表，引擎本身不用改。

### 5.1 测步时间：不能拿合成 benchmark 糊弄

测量步时间最容易犯的错，是用「单独跑一个 matmul」或者「用别的框架」去近似。TableTune 的做法是**让被测路径就是服务路径**：

- 对每个草稿长度 k（从 0 到 K，K 取 drafter 的最大值：EAGLE-3 是 3，n-gram 和 draft model 是 5，DFlash 是 8），用真实 drafter 启动 vLLM，表设成单区间 [[1, Bmax, k]]，这样连 CUDA graph 的形状都和线上一致；
- 对每个批量 B，发 B 条典型长度（默认 32 token）的 prompt **两次**，一次要 1 个输出 token，一次要 65 个，差值就是 64 个解码步：T(B,k) = (t65 − t1) / 64，重复三次取中位；
- 关键技巧：用 vLLM 的测试模式**拒绝所有猜测**。这样每步仍然做完整的 k 次 draft 和 verify 工作，但 B 个请求每步都只前进 1 个 token、同时结束，**批量在整个测量窗口里保持恒定**。否则被接受的 token 会让请求陆续结束，批量就塌了。

被拒绝掉的「收益」在下一步补回来：τ(k) 由接受率 profiler 单独测，goodput 公式里乘回去。

### 5.2 测接受率：一次跑最长长度就够

在 160 条样本 prompt 上，以服务实际使用的温度，用最长长度 K 跑一遍，读 vLLM 已经发布的两个指标：`vllm:spec_decode_num_drafts` 和 `vllm:spec_decode_num_accepted_tokens_per_pos`。两者相除就是 aᵢ。因为长度为 k 的草稿就是长度为 K 的草稿的前 k 个猜测，**一次运行覆盖所有更短的长度**。

### 5.3 造表：两条规则让表保持短

对每个批量算遍所有 k 的 goodput，取最大。然后两条工程规则：

- **近似打平不建边**：如果上一个批量的长度在新批量下只差 0.5% 以内，就沿用上一个长度；
- **窄区间合并**：如果某个区间宽度不到它起始批量的 25%，并进邻居。

还有两个细节值得记：对 n-gram 这种「只在文本里能匹配到时才猜」的 drafter，接受率要乘上**提案率**（有猜测的步所占比例），但步时间仍然收全额——因为只要批里有一个请求在猜测，这一步的成本就接近「全部都在猜」。另外，从同一份 profile 里可以顺手算出「每个固定长度的最坏损失」，这样 operator 能判断自己到底该不该上表（如果某个固定长度已经够好，就别折腾）。

产出直接落成 vLLM 的参数格式，因此**不需要改引擎**，只要能改配置。论文实现约 1,880 行 Python、104 个测试函数。

## 六、设计（下）：controller，用 vLLM 自己的计数器重建表

controller 的设计克制得有点让人意外——**它不增加任何 instrumentation**。每步之后，它直接拿 vLLM 调度器已经为该请求记录的两个数：猜了几个（d）、接受了几个（m）。因为验证在第一个错误猜测处停止，被接受的必然是前 m 个。于是按位置维护两个计数器：

- draftedᵢ：有多少次草稿走到了第 i 位（d ≥ i）
- acceptedᵢ：有多少次第 i 位被接受（m ≥ i）

比值 acceptedᵢ / draftedᵢ 就是 aᵢ 的估计。一个猜了 3 个、接受 2 个的请求，会给 drafted 的 1..3 各加一，给 accepted 的 1..2 各加一。

重建表时用贝叶斯式的混合：

âᵢ = (w × aᵢ_prior + acceptedᵢ) / (w + draftedᵢ)

其中 prior 来自 tuner，权重 w = 2000 次观测；线上计数在每次重建后**减半**，让近期流量占主导。

三个工程细节是论文用实验换来的，值得单独列出来：

- **探索（exploration）**：每 50 步有一步强制用最长允许长度。理由很实在：当表当前跑长度 1 或 0 时，controller 对后面几位**什么都学不到**，一旦流量变了就再也升不上去。
- **先验衰减（prior decay）**：prior 的权重每次重建也减半。这是工作负载切换时能不能「换表」的关键——论文在 A10G 上的对照实验里，不做这两件事的 controller 会卡在长度 0 上震荡，只能恢复 0%，做了之后恢复 72–85%。
- **迟滞（hysteresis）**：批量落在表边界 h（默认 8）以内时，保持当前长度，避免在边界上抖动——正好对应 vLLM issue #49548 报告的那种吞吐崩塌。

另外 controller 默认**只用起始表里出现过的长度**，因为 V2 runner 只为这些长度准备了完整的 CUDA graph。这条限制在后面变成了一个真实的工程约束。

## 七、实测：调优表 vs 各种固定长度

论文的主表（Table 1）比的是「最坏损失」：在 1–128 个并发请求的整个扫描里，调优表最多比「该负载下的最优固定长度」差多少。对照组是「事后挑一个最坏损失最小的固定长度」——这个长度 operator 只能靠把每个长度都 benchmark 一遍才找得到。

| 场景 | 调优表最坏损失 | 最优单个固定长度（长度） | V1 runner 下的表 |
| --- | --- | --- | --- |
| EAGLE-3，代码 | 4.0% | 3.4%（k=2） | 39.5% |
| EAGLE-3，4-bit AWQ 目标 | 3.0% | 4.6%（k=2） | 43.0% |
| n-gram，code-apply | 5.7% | 4.5%（k=5） | 5.2% |
| Qwen3-0.6B draft model | n/a（profile 无效） | 0.0%（k=1） | 35.6% |
| DFlash，代码 | 11.6% | 19.1%（k=3） | 29.5% |
| EAGLE-3，对话（Spec-Bench） | 3.1% | 3.9%（k=3） | 39.3% |

几点解读：

- 在**一张 H100、128 个请求以内**这个范围里，「挑一个足够好的固定长度」其实已经很接近最优（3.4%）。所以作者很诚实地写：此时表的价值主要是**不用你一个个 benchmark 就能找到那个长度**，而不是表本身更强。
- 真正拉开差距的是三类场景：MoE 目标、DFlash 这类「长草稿在高负载掉得更快」的 drafter、以及更老的 GPU。在 T4 和 A10G 上，调优表最坏损失 2.3–4.0%，而**每一个固定长度都会在某个负载掉 7.6–43.6%**。
- DFlash 是唯一没做好的：11.6%，而且这个差距有明确的物理原因（见第十二节）。

### MoE 为什么反过来：负载越高越该投机

这是全文最有意思的一段。Qwen3-30B-A3B（30B 参数、每 token 激活 3B）在 H100 上，**不投机的单步时间从批量 1 的 4.7 ms 涨到批量 128 的 19.7 ms**——因为批量越大，激活的专家越多。而加 3 个草稿 token 只让步时间涨 61%（批量 1）和 31%（批量 128），因为那时候这些专家已经被读进来了。

结果就是：MoE 上投机**在高负载仍然赚**，长度 3 从批量 2 到 96 都是最快，128 时才是长度 2 略胜。tuner 找出的表是 [[1, 3, 3], [4, 4, 2], [5, 128, 3]]，全程离最优固定长度不超过 2.9%；而 vLLM 文档里那张按稠密模型写的表在 64 个请求以上就切到长度 1，在 96 个请求处丢 **17.5%**，128 处丢 12.2%。

这就是「表不跨模型迁移」最直接的证据：**稠密模型的经验（高负载就关投机）在 MoE 上是错的。**

### 和 TurboSpec / Nightjar 这类自适应控制比

两个工作都没开源，作者按论文各自重实现成独立的 vLLM 插件（不共享代码），在同一引擎、同一批可用长度下比较：

| 方法 | EAGLE-3 最坏损失 | 说明 |
| --- | --- | --- |
| TableTune 表 | 3.3% | — |
| TableTune 表 + controller | 3.0% | — |
| TurboSpec 风格（每步决策） | 9.3% | 线性步时间模型抹平了长度 3 的跳变（批量 80：实测 9.7 ms vs 拟合 8.0 ms），一直用到批量 100 才降 |
| Nightjar 风格（bandit） | 11.8% | 每个批量独立探索，持续付出探索成本 |

![](https://pic4.zhimg.com/v2-b8f4f26178356cc62a275d07962d1907_1440w.jpg)

图 3：同一台 H100（V2）上 TableTune 表 / 表 + controller 与 TurboSpec 风格、Nightjar 风格控制的对比。(a) EAGLE-3，(b) DFlash；纵轴是该负载下最优固定长度的百分比。

DFlash 那一栏（图 3b）更微妙：三种方法在 32 个请求以上都落后固定长度 3 达 10–29%，因为**它们可选的长度集合里根本没有 3**（TableTune 起手是 2/4/6/8），而 TableTune 的损失最小（15.8% vs 17.1% / 28.5%）。这个细节说明：**表的「可选长度集合」本身就是一个超参**，而它由 drafter 的最大草稿长度和 CUDA graph 的预捕获决定。

## 八、controller 的真实价值：修错表、跟流量切换

![](https://pic3.zhimg.com/v2-aecd9f4252f362cbc8bd2829de326a1a_1440w.jpg)

图 4：controller 的两类作用。(a) 从同一张「错表」（vLLM 文档表把区间除以 4，32 个请求以上就关投机）出发，在 T4 / A10G / H100 V1 / H100 V2 上的增益，空心圈是该 GPU 调优表的位置；(b) DFlash 在 H100 上中途把 prompt 从代码切到数学，旧表失效后 controller 一分钟内重建。

| 起始表 | H100 V2 | H100 V1 | 老 GPU |
| --- | --- | --- | --- |
| 文档表把区间除以 4 | +58%（批量 40） | +45%（64） | T4 +36%（64）、A10G +14%（40） |
| 文档表原样 | +2%（16） | +8%（96） | T4 +15%（64）、A10G +16%（64） |
| DFlash 用 EAGLE-3 的表 | +23%（64） | +37%（64） | A10G +11%（4） |
| MoE 目标 + 错表 | +71% 到 +83%（40–96） | — | — |
| 工作负载切换（DFlash 代码→数学） | 旧表丢 10.8%，controller 找回 96% | — | A10G 找回 72–85% |

三个观察：

- **错得越狠，修得越多**。H100 上「投机 vs 不投机」的差距最大，所以一张错表最贵，修回来的收益也最大（+58%）。
- **MoE 上错表更贵**（+71–83%），因为那里投机在全程都赚，把投机关掉等于白扔钱。
- **controller 不能修「成本模型」的错误**。DFlash 的 profile 系统性偏低（见第十二节），controller 的先验本身是准的，但步时间错了，它无从纠正——所以 DFlash 在批量 34–87 仍然比固定长度 3 差 10–16%。

## 九、端到端：llm-d 里的 32%

最后一个实验是把它放进真实部署栈。用的是 llm-d 的 optimized-baseline 指南**原样**（2 个 Qwen3-32B 副本，TP=2，4 张 H100，Envoy 路由按 prefix-cache 亲和 + token 负载分发），只改配置：加 EAGLE-3 drafter、加调优表、换带 V2 runner 的 nightly 镜像、副本上限 256 条 4096-token 序列。

![](https://picx.zhimg.com/v2-8dd2edaf5a0664f6f0eeeb091d372c11_1440w.jpg)

图 5：llm-d optimized-baseline + EAGLE-3，相对固定草稿长度 3 的吞吐增益。(a) 指南原配置 2×Qwen3-32B（TP=2）；(b) 4×Qwen3-8B（TP=1）。256 个请求以上跨过表的边界切到长度 1，收益出现。

- 2×Qwen3-32B：128 个请求以内，调优表与固定长度 3、文档表在噪声内一致；从 256 个请求起副本跨过表的边界切到长度 1，此时比固定长度 3 快 **20–32%**，比文档表快 7–25%（文档表在每副本 128 批量以上直接切到 0，也就是关掉投机）；512/1024 请求时 TTFT 中位早 23–26%、TPOT 中位低 23–29%。
- 从文档表起步的 controller 在 256–1024 请求把吞吐抬升 **9–29%**，追平调优表；在调优表之上再加 controller 还能多 4%。
- 4×Qwen3-8B：表比固定长度 3 快最多 22%，比文档表快最多 40%；controller 在 512/1024 请求分别再加 14% 和 39%。
- 给 TP=2 的 32B 副本做一次 profile 约 **30 分钟**。

注意这里有一个容易被忽略的口径问题：投机本身相对「完全不开投机」的增益（64 请求以内 48–78%）**不能算在 tuner 头上**——那是 drafter 的功劳。论文明确把 tuner 的贡献限定在「相对其他投机配置」的差值上，这种自我约束在系统论文里并不多见。

## 十、我自己扒仓库复算：步时间真值表与边界噪声

论文只给了少量步时间数字，但仓库（`tables/` 下每个 GPU 一个目录）里有完整的 profile：每个草稿长度的 `costs_k*.json`（批量 → 步时间中位数 + 三次采样）和 `acceptance.json`（逐位接受率）。于是可以**不用 GPU**、直接把 tuner 的核心算术重算一遍：

G(B, k) = B × τ(k) / T(B, k)，τ 取 acceptance 里的 tokens_per_step_by_k。

H100 + Qwen3-4B + EAGLE-3（代码，温度 1.0）的实测步时间（ms）与算出的 goodput（千 token/s）：

| 批量 | k=0 | k=1 | k=2 | k=3 | k=3 / k=0 | G(k=0) | G(k=1) | G(k=2) | G(k=3) |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 4.44 | 4.46 | 4.67 | 4.90 | 1.10× | 0.23 | 0.36 | 0.41 | 0.42 |
| 16 | 4.67 | 4.81 | 5.16 | 5.13 | 1.10× | 3.4 | 5.3 | 6.0 | 6.5 |
| 32 | 5.03 | 4.92 | 5.45 | 5.66 | 1.13× | 6.4 | 10.4 | 11.3 | 11.7 |
| 64 | 5.21 | 5.51 | 6.20 | 6.86 | 1.32× | 12.3 | 18.5 | 19.9 | 19.3 |
| 96 | 5.81 | 6.26 | 7.52 | 8.63 | 1.49× | 16.5 | 24.5 | 24.5 | 23.0 |
| 128 | 6.10 | 7.08 | 8.73 | 10.43 | 1.71× | 21.0 | 28.8 | 28.2 | 25.4 |

这张表把整篇论文的机制压缩成了三行：

- 批量 1 时，3 个草稿只让步时间涨 10%，但每步产出从 1 个 token 变成 2.07 个（τ(3)=2.073），净赚 82%；
- 批量 128 时，从 k=1 走到 k=3，步时间涨 47%（7.08 → 10.43 ms），每步产出只涨 30%（τ 从 1.594 到 2.073），净亏 12%；
- 所以表的本质是一条「步时间涨幅 < token 产出涨幅」的分界线，而这条线的位置由 T 的斜率决定——**这就是为什么表必须在目标 GPU 上重测**（H100 的步时间从 4.4 涨到 6.1 ms，T4 从 35.7 涨到 92.3 ms，斜率完全不同）。

复现 MoE 那张表是**逐字命中**的：`tables/h100-moe-eagle3/schedule.json` 就是 [[1, 3, 3], [4, 4, 2], [5, 128, 3]]，而我从它的 profile 算出来 T(1,0)=4.74 ms、T(128,0)=19.72 ms、k=3/k=0 的比值 1.61（批量 1）和 1.31（批量 128），与论文正文的 4.7 / 19.7 / 61% / 31% 完全对上。

但 EAGLE-3 那张稠密表就没那么干净。我按「每个批量取最大 goodput」复算，得到的边界在 40–64 之间**来回跳**：

| 批量 | G(k=2) | G(k=3) | k=3 相对 k=2 |
| --- | --- | --- | --- |
| 40 | 13.8 | 13.4 | −2.8% |
| 48 | 15.6 | 16.0 | +2.6% |
| 56 | 17.9 | 16.6 | −7.1% |
| 64 | 19.9 | 19.3 | −2.6% |

也就是说，**长度 2 和 3 在这个区间里本来就在几个百分点的噪声里打平**，边界落在 50 还是 56 并不改变多少吞吐（论文自己写的「near-ties」和「同一 GPU 两次 profile 的步时间差 4–9%，足以移动一条边界，代价几个百分点」说的就是这件事）。真正稳的是大方向：**低负载长草稿、高负载短草稿；批量到 128 一定要切到 k=1**。这反过来也解释了作者为什么给表加了「0.5% 打平就沿用」的规则——不是为了精度，而是为了让表稳定、可运维。

## 十一、要落地，引擎必须给三样东西

这一节是全文对引擎开发者最直接的价值，也是很多人容易忽略的「隐性成本」：

**1. 每个草稿长度都要有完整的 CUDA graph。** vLLM 默认的 V1 runner 一旦设置了表，就把解码步换成「分段 CUDA graph」（piecewise），因为每步的 token 数不再固定。分段 graph 会在每步追加 CPU 侧 launch 工作：Nsight 在 T4 上显示 GPU 忙碌比例从 91%（完整 graph）掉到 60%。H100 的步太短（Qwen3-4B 约 6 ms），这个开销藏不住——在 1–32 个请求时固定长度 3 就要多付 24–34%，而且**加 CPU 核数（2/4/16）没用**。V2 runner 从 2026 年 10 月起为每个草稿长度保留完整 graph，这个损失才消失（表 1 里 V1 那两列 30–43% 的损失全是这个原因，不是 tuner 选错）。

**2. 长度切换不能卡住引擎。** 作者用的这版 vLLM nightly 里，只要表从长度 2 跳到长度 1，V2 runner 在负载下就会 stall（4-bit 目标的调优表、EAGLE-3 的 T4 表、翻译任务的表、llm-d 在 80/81 边界上的表都中招）。0/1/3 这种不出现 2→1 步进的表从不 stall。这是引擎 bug（已上报上游），但它直接影响能部署哪张表。

**3. 需要一个「真的关掉」。** 表里的 0 并不等于不投机：EAGLE 系 drafter 仍然会跑，还占着自己的 KV cache。结果是在 H100 上「长度 0 的表」比完全不投机低 19–22%，A10G 上低 5.6–6.7%。这一条是很多「关掉投机省显存」的经验失效的原因。

## 十二、批判性评估：这篇的边界在哪

作者自己列了限制，我按重要性重排并补几条读的时候值得警惕的地方：

- **只在一个 vLLM nightly 上验证**，而且这版 nightly 有 2→1 步进 stall 的 bug，导致部分结果只能用 0/1/3 表（比全长度表略差）。换一个版本，绝对数字会动。
- **DFlash 的 profile 有系统性偏差**：用「全部拒绝」计时，测不到「随接受 token 数增长的工作」。DFlash 在长度 8、实际批量 6–38 时，真实步时间是 profile 的 1.3–1.9 倍（长度 1 时只有 1.05–1.16 倍）。改用「按实测接受率」profiling 能修正步时间，但表几乎不变；作者加了一个「合并窄区间要看预测 goodput 损失是否小于 2%」的容差选项，才把 DFlash 在 64 请求处改善 6.5%。**换句话说，它的「测出来」在块式 drafter 上并不完全成立**，仍然是 10% 左右的差距。
- **draft model 的 V2 profile 直接无效**（Qwen3-0.6B 在 V2 下 profile 出来是平的 40 ms，实际服务是 9–37 ms），所以表 1 里那一行是 n/a。这类「profile 与线上不一致」的失败模式，任何自建 tuner 的人都会遇到，论文没有给出通用的检测手段（只有事后发现）。
- **规模有限**：稠密 4B/8B/32B + 一个 3B 激活的 MoE，单节点、TP≤2，prompt 大多 32 token（最长 3072），回答 ≤256 token，闭环保留并发，最多 72 req/s 的开环。**没有 PD 分离、没有多节点、没有 >4096 token 的上下文、没有混合/录制流量**。而 llm-d 那部分恰恰说明收益主要出现在 256+ 并发，所以大规模下的结论还需要补。
- **基线是重实现**：TurboSpec 和 Nightjar 都没开源，作者按论文重写（明确省略了 Nightjar 的 drafter 卸载和 TurboSpec 的 context-length 项）。9.3% / 11.8% 这两个数字是对「重实现」的测量，不能直接当成对原系统的结论。
- **指标只有吞吐**：没有 p99 延迟、没有 SLO 达成率。作者说得很清楚「我们优化吞吐」，但生产上真正决定能不能上线的是尾延迟——而草稿长度恰恰是拿延迟换吞吐的旋钮。
- 一个方法论上的加分项：论文披露了 AI 使用情况（Claude 用于文献摘要、提纲和画图脚本），并声明所有实验与结论由作者自己完成。这类披露在国内技术文章里很少见，值得效仿。

## 十三、给工程实践的几条

如果你在自建 vLLM 服务，这篇论文可以直接落成四条动作：

- **别抄文档里的表**。文档示例 [[1,64,3],[65,128,1],[129,512,0]] 是按「稠密模型 + 老引擎」写的，在 MoE 上会丢 17.5%，在 llm-d 这种多副本高负载场景会直接关掉投机。至少在自己的 GPU + 模型 + drafter 上重测一遍。
- **重测的成本可以接受**：H100 上 8 分钟（MoE 20 分钟，32B TP=2 约 30 分钟，T4 45 分钟），换工作负载只需 2 分钟的接受率 profile。这比「上线后靠猜」便宜太多。
- **先确认引擎支持**：没有「每草稿长度完整 CUDA graph」的版本，任何表都可能是负收益（V1 上 30–43%）。这是选 vLLM 版本时的硬条件。
- **online controller 只在两种情况下必要**：流量任务会变（比如白天代码、晚上对话），或者你没法保证表是最优的。如果流量稳定且表已经测准，controller 的增益在噪声内（H100 上 +2%），但它能挡住「表错了」这件事——而那件事的代价是 58%。

最后一个判断：这篇论文的贡献不在于算法有多新（τ、goodput、per-batch 长度都是前人提过的），而在于它把「表」当成一个**可测量、可运维的工程对象**，并且用一台 H100、三张卡、一个真实部署栈把「表能带来多少、需要引擎配合什么」量化清楚。对做推理服务的人来说，这比再提出一个自适应算法更有用。
