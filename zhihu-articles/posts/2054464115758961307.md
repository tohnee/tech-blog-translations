最近UCCL项目迎来了一波超大更新，包含了三个项目：

- mKernel: Fast Multi-GPU, Multi-Node Fused Kernels. [Blog](https://uccl-project.github.io/posts/mkernel/), [repo](https://github.com/uccl-project/mKernel)
- rdmatop: Cross-Provider htop for RDMA Traffic. [Blog](https://uccl-project.github.io/posts/rdma-monitoring/), [repo](https://github.com/uccl-project/rdmatop)
- CommBench: Can LLMs Write Correct and Efficient GPU Communication Code? [Blog](https://uccl-project.github.io/posts/commbench/), [repo](https://github.com/uccl-project/CommBench)

这些项目里面有些包含了一些非常激进的kernel design，有些关注非常practical的engineering，有些尝试explore LLM coding的能力到底如何。接下来就由我一一介绍一下！

## **mKernel: Fast Multi-GPU, Multi-Node Fused Kernels**

mKernel是UCCL-EP结束后我们产生的一些想法的落实。当时我们发现UCCL-EP的kernel写的非常花哨，虽然给我们的hacking带来了很大的挑战（尤其是遇到nvlink + IB 传输timeout的时候），但是却让我们了解到现在的GPU kernel可以做的事情实在是很多，基本可以当成event-driven CPU threads来用。

那这样子岂不是CPU上一堆性能雕花的技巧都可以应用上上去？这里主要指的是20年前大家在解决C10k TCP connection scalability，以及10年前大家在解决Network function virtualization efficiency时诞生的一些疯狂的performance engineering的ideas：big event loop，busy polling，thin isolation, etc.

于是我们在想能不能把各种compute和communication都fuse到一个kernel里面。这里面主要有两个benefits：

- 可以节省CUDA kernel launch的overhead，这部分其实在GB系列GPU下面非常严重，原因是因为GB的ARM CPU per-core performance是要比x86 CPU低的，（我之前测过大概是一半）。CUDA graph其实也不是一个perfect solution，原因是CUDA graph内部不同kernel trigger之前的overhead也不是完全free的。
- 可以解决大kernel内部不同tile计算的tail issues。关于这个问题，Thunderkitten (TK)之前有一个[blog](https://hazyresearch.stanford.edu/blog/2025-03-04-thundermla)的一张图解释得非常清楚：

![](https://pic4.zhimg.com/v2-a165400134c6526db457ee275e9a7019_r.jpg)

当然我们承认这个项目本身其实更多的是performance engineering，不过确实满足一下本performance nerd的喜好（逃）。最后的结果也非常好，[Ziming](https://maoziming.github.io/) 花了几个月从入门kernel到熟练掌握各种Hopper GPU雕花的技巧，同时基本drop掉任何externel kernel lib的dependency。比如我们不用nccl，nvshmem，所有的通信都是通过UCCL-EP style的proxy走的，这样我们可以既支持普通的IB网卡，也支持乱序的EFA网卡。最终fuse了好几种不同的compute-communication kernels across two H200x8 nodes，performance也非常好。

## **rdmatop: Cross-Provider htop for RDMA Traffic**

这个项目其实是我们在develop UCCL-EP认识的一个AWS小伙伴[crazyguitar](https://github.com/crazyguitar)贡献的，他发现UCCL-EP可以大幅提升EFA上多机推理的性能（当然后来发现是NCCL baseline走了TCP lol），然后提了不少PR和issues来帮忙维护UCCL-EP。后来他想开发一个rdmatop的工具用来弥补RDMA monitoring的一些缺陷，但是苦于没有机器，所以找到我们，想donate the tool to the UCCL community，并且使用我们的机器来继续开发。当然即使他不donate rdmatop，我们也愿意share机器，毕竟他之前提了不少PR和issues。

![](https://pic2.zhimg.com/v2-aa87db2e7116aad26ac92049a1c0da89_r.jpg)
*最后发现是NCCL baseline配错了lol*

我本人非常喜欢这个工具，UI设计的非常优雅，而且包含了各种各样RDMA网卡的支持：NV，Broadcom，EFA，并且非常易于安装：sudo apt install rdmatop or cargo install rdmatop，欢迎大家尝试并且提PR！这个项目不同于UCCL之前做的偏research一点的项目，而是纯粹engineering-oriented，但是满足了实际development过程中的关键需求。个人认为不论research还是engineering，只要能解决一部分人的实际问题，那就是好项目，就会有产生impact。

## CommBench: Can LLMs Write Correct and Efficient GPU Communication Code?

看Ion Stoica做了很多benchmark之后，我们当然也想做一个benchmark。Motivation源自于：mKernel里面很多代码是LLM写的，但是其实我们发现LLM基本很难写好communication相关的代码；UCCL-EP里的communication代码基本都是我们手敲的，因为LLM根本写不出来。在意识到这个问题后，我们大胆猜测是不是Dataset和benchmark的缺失造成这些：毕竟mlsys community全都在卷kernel，鲜少有人知道RDMA怎么用，nvlink怎么用最efficient。

于是我们找了一二十个 学生or已经工作的engineers（这里主要是我的非常靠谱的一年级PhD [Shuang Ma](https://github.com/monopodium)在drive这个项目），手动把在UCCL各个项目development过程中的与RDMA，NVLink，communication framework（NCCL，NVSHMEM，etc），customize communication kernel，compute-communication fusing相关的一些任务抽象出来，弄成individual self-contained tasks。并且我们自己写好reference solution，然后让LLM来generate solution和 我们的reference solution对比。这个项目非常labor-intensive：我们手搓了100+ tasks，在各种各样的models上都做了评测。最终结果其实和我们预想的非常一致，就算是最先进的闭源模型，他们也基本没法很顺利的写对GPU communication code，跟别提达到手写的efficiency。

可能下一步我们想要做的就是fine-tune一些OSS models，来看看能不能提升它们写GPU communication code的能力，从这个domain task入手来研究RL or coding agent。

![](https://pic4.zhimg.com/v2-541fcbb73db9b7a808d1edc9affb6bdd_r.jpg)
*不知道为什么gpt-5.5可以写的比claude还好，可能是因为它内部偷偷做了thinking？毕竟cost要高很多*

当然，我们blog发了不到两周后，我们就发现Together AI也发了一个类似work的blog：[https://www.together.ai/blog/parallelkernelbench](https://www.together.ai/blog/parallelkernelbench)，结论和我们很类似“Frontier LLMs can't write fast multi-GPU kernels (yet)”，这里感慨一句coding agent领域还真真是卷。

## 结语

我个人认为GPU compute and communication交叉领域是目前mlsys最重要也最promising的方向之一，它既代表了industry所最需要的技能点，也代表了academia欢迎见到的paper类型。如果小伙伴们想在这个领域深耕，欢迎加入UCCL community一起学习一起进步：[https://github.com/uccl-project/uccl](https://github.com/uccl-project/uccl)！
