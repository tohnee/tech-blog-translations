我家里有一套三节点的 Kubernetes 集群，平时拿它练手。最近我在折腾一个想法：能不能让 AI Agent 自己去看集群的状态——哪个节点 Ready、哪个挂了、版本对不对——而不是每次都我自己敲 kubectl？

折腾完发现，关键就一步：给 Agent 接一个 MCP 工具。这篇文章把完整过程写出来：先用 30 行 Python 搭一个最小 MCP Server，再把玩具工具换成真工具，让它真的去查集群。所有代码和输出都是我本地实测过的。

### 一、MCP 是什么，为什么 Agent 需要它

大模型只会说话，不会干活：不会查数据库、不会调接口、更不会敲 kubectl。MCP（Model Context Protocol）就是给它定的统一工具接口，常被比作「AI 生态的 USB 接口」——工具按 MCP 规范做成 Server，任何支持 MCP 的应用插上就能用，Agent 的“手”就是这么长出来的。

一个 Server 能提供三样东西：Tool（可执行函数）、Resource（可读数据）、Prompt（提示词模板）。先搭一个最小的把三样跑通：

```bash
pip install "mcp>=1.28,<2"
```

注意锁版本：官方 v2 已是稳定版，但市面教程大多是 v1 写法，不锁版本照抄就可能对不上——这是我踩的第一个坑。

```python
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("Demo")

@mcp.tool()
def add(a: int, b: int) -> int:
    """Add two numbers"""
    return a + b

@mcp.resource("greeting://{name}")
def get_greeting(name: str) -> str:
    """Get a personalized greeting"""
    return f"Hello, {name}!"

@mcp.prompt()
def greet_user(name: str, style: str = "friendly") -> str:
    """Generate a greeting prompt"""
    return f"Write a {style} greeting for someone named {name}."

if __name__ == "__main__":
    mcp.run(transport="stdio")
```

三个要点：装饰器即注册，不用手写协议代码；类型标注会被自动转成参数 Schema，模型靠它传参；函数下面的 docstring 是写给模型看的说明书，模型靠它判断该不该调用这个工具。

写个最小 Client 连上去验证，实测输出：

```text
tools: ['add', 'word_count']
add(3, 5) = 8
greeting = Hello, Zhihu!
```

骨架通了。接下来才是正题：把 add 这种玩具工具，换成能干真活的。

### 二、换上真工具：查集群节点状态

目标工具叫 get_cluster_nodes，职责一句话：返回集群里每个节点的名字、是否 Ready、kubelet 版本。选它当第一个真工具是刻意的——**它只读**。给 Agent 开工具的第一原则是最小权限：先给查询权，跑稳了再谈修改权，一上来就开放 delete、scale，出事只是时间问题。

动手前先定契约，后面照着填就行：

- **输入**：无参数。参数越少，模型越不容易传错。
- **执行**：调本机 kubectl get nodes -o json。用 JSON 不用表格，因为表格是给人看的，列宽顺序都可能变；JSON 结构稳定，是给程序看的。
- **输出**：一行一个节点的短文本。别把几百行原始 JSON 塞回给模型，既费 token，又让它抓不住重点。

节点是否 Ready，要去 status.conditions 里找 type 为 Ready 的那条看 status 是不是 True；版本在 status.nodeInfo.kubeletVersion。完整代码：

```python
import json
import shutil
import subprocess

from mcp.server.fastmcp import FastMCP

mcp = FastMCP("K8sHelper")

def format_nodes(nodes_json: str) -> str:
    """把 kubectl get nodes -o json 的输出整理成一行一个节点。"""
    data = json.loads(nodes_json)
    lines = []
    for item in data.get("items", []):
        name = item["metadata"]["name"]
        ready = next(
            (c for c in item["status"]["conditions"] if c["type"] == "Ready"),
            None,
        )
        status = "Ready" if ready and ready["status"] == "True" else "NotReady"
        version = item["status"]["nodeInfo"]["kubeletVersion"]
        lines.append(f"{name}: {status}, {version}")
    return "\n".join(lines) if lines else "集群里没有节点"

@mcp.tool()
def get_cluster_nodes() -> str:
    """Get the name, readiness and kubelet version of every node in the Kubernetes cluster"""
    kubectl = shutil.which("kubectl")
    if kubectl is None:
        return "未找到 kubectl：请先安装 kubectl，并确认它在 PATH 里"
    try:
        proc = subprocess.run(
            [kubectl, "get", "nodes", "-o", "json"],
            capture_output=True, text=True, timeout=15,
        )
    except subprocess.TimeoutExpired:
        return "kubectl 执行超时（15 秒）：集群可能不可达，请检查 kubeconfig 和网络"
    if proc.returncode != 0:
        return f"kubectl 执行失败（退出码 {proc.returncode}）：{proc.stderr.strip()}"
    return format_nodes(proc.stdout)

if __name__ == "__main__":
    mcp.run(transport="stdio")
```

这段代码和玩具版的区别，就三处，全是工程习惯：

1. **解析逻辑拆成纯函数**。format_nodes 只吃字符串吐字符串，不碰集群——测试时喂一份样例 JSON 就能验，不用为了测解析先搭集群。
2. **失败返回文本，不抛异常**。找不到 kubectl、超时、退出码非 0，都返回一句说清原因的话。调用方是模型：错误信息带回去，它能决定下一步；你抛个异常，它只会看到“工具调用失败”。
3. **外部命令必须加超时**。集群不可达时 kubectl 能挂很久，工具跟着挂死，整个 Agent 会话都被拖住。

### 三、没有集群，怎么测？

分两层，都不需要真集群。

第一层测解析：样例 JSON 里故意把第三个节点写成 NotReady，覆盖两条分支，实测输出：

```text
k8s-master: Ready, v1.30.14
k8s-node1: Ready, v1.30.14
k8s-node2: NotReady, v1.30.14
```

第二层测容错：在没装 kubectl 的机器上跑 Client，实测输出：

```text
tools: ['get_cluster_nodes']
未找到 kubectl：请先安装 kubectl，并确认它在 PATH 里
```

没崩、没抛栈，把原因说清楚返回——这就是“失败返回文本”的效果。

最后在我自己那套三节点集群上跑同一个工具，真实输出：

```text
k8s-master: Ready, v1.30.14
k8s-node1: Ready, v1.30.14
k8s-node2: Ready, v1.30.14
```

到这一步，把这个 Server 配进日常用的 Agent 客户端，模型在对话里就能自己调用它看集群了。

### 四、给 Agent 开工具前，守住三条边界

工具跑通只是开始，真接进日常使用前，这三条我建议先守住：

1. **只读优先，写操作后置**。get、list、describe 这类先上；delete、scale、apply 等改变状态的操作，等你对 Agent 的行为有把握了再逐个开放，最好加人工确认。
2. **权限收在凭证背后**。这个工具的实际权限，等于运行它的 kubeconfig 的权限。更稳妥的做法是给 Agent 单独备一份只读凭证，只授予查看节点的权限，别直接用自己的管理员凭证。
3. **输出先脱敏**。本文只输出节点名、状态和版本。以后扩展到查 Pod、查日志时同样要过一遍：工具输出会进模型的上下文，敏感信息一旦出去就收不回来。

### 五、总结

回头看，整件事的骨架小得意外：MCP Server 三十行，换工具只动 Server、Client 一行不改。真正花心思的地方不在协议，而在工具本身——契约先行、解析与调用分离、失败返回文本、外部命令加超时。这四件事换到任何工具上都成立：下次给它加查 Pod 状态、查命名空间资源的工具，照这个模子套就行。
