### 1. Triton 到底是什么？它解决什么问题？

你可以把 Triton 理解成：

- **一门用 Python 写 GPU 内核的 DSL**（领域专用语言），语法像 NumPy，但语义更像“矢量化的 SPMD 程序”；
- **一个编译器+运行时**：第一次调用时编译 kernel，生成底层代码（如 NVIDIA 的 PTX / AMD 的 amdgcn），并做缓存；后续直接复用编译结果；
- **一个“以块（tile）为中心”的编程模型**：你写的是“一个程序实例处理一个 tile”，而不是“一个线程处理一个元素”。

Triton 的价值在于：当你需要写 **自定义算子/融合算子**（比如奇怪的 layout、融合的归约、特定的注意力变体等），用 CUDA 写很费力、维护成本高；用现成库又不够灵活。Triton 试图在“性能”和“生产力”之间给一个更好的折中。

> **注意**：本文不做性能对比；只关注“你写的东西是怎么跑起来、怎么对”的。

### 2. Triton 的核心心智模型：不是“线程”，而是“程序实例”

Triton 的 kernel（被 `@triton.jit` 装饰的函数）在运行时会被 **复制很多份**并行执行。每一份叫一个 **program instance**（程序实例）。你在 kernel 里通过：

- `tl.program_id(axis)`：拿到“我是哪一个实例”（3D launch grid 的坐标轴之一）
- `tl.num_programs(axis)`：拿到“这个维度一共有多少实例”

来决定自己要处理的数据块。（`tl.program_id` 的定义见 Triton 文档 `https://triton-lang.org/main/python-api/generated/triton.language.program_id.html`）

### 2.1 SPMD：一个程序，多份数据

你写一个程序（kernel 里的代码），它会在很多实例上并行运行；每个实例处理不同数据区域。这就是 SPMD（Single Program Multiple Data）。

> **结论**：你写的不是“线程函数”，而是“**一个程序实例处理一个 tile**”。

### 2.2 program instance 和 CUDA block/warp 的关系（更精确的版本）

Triton 的 launch grid 在概念上和 CUDA 的 launch grid 类似（Triton 向量加法教程也明确说 *SPMD launch grid analogous to CUDA launch grids*，见 `triton/python/tutorials/01-vector-add.py` 中对 `grid` 的说明）。

在 NVIDIA GPU 上，你可以用下面这个“够精确、可用于推理”的对应关系建立直觉：

- **一个 program instance ≈ 一个 CUDA thread block（CTA）**

- **`num_warps` 决定一个 program instance 里大约有多少 warp 协作执行**

> **注意**：上面的“≈”很重要。Triton 不是让你直接写 `threadIdx` 的标量程序；你写的是一段带向量语义的 SPMD 代码，编译器会决定把你的向量/lane 映射到具体线程与指令序列上。

### 2.3 `tl.arange` 不是 `threadIdx`：它更像“实例内的向量索引”

很多新手会把 `tl.arange(0, BLOCK)` 理解成“每个线程一个索引”。更准确的理解是：

- `tl.arange` 生成的是**一组 lane 的索引向量**
- 编译器会把这些 lane 分配到一个 block 的 threads/warps 上去执行（可能是 1 lane/线程，也可能是 1 线程处理多个 lane，取决于形状、指令、寄存器压力等）

这也是为什么 Triton 的代码常常看起来像 NumPy（向量化），但运行时却是 GPU 并行。

### 2.4 为什么你仍然需要关心 `num_warps`

即使你暂时不做性能优化，`num_warps` 依然影响你对“运行机制”的理解：

- **并行度直觉**：一个 instance 内参与协作的 threads 大致随 `num_warps` 增加而增加（NVIDIA 上每 warp 32 threads）
- **资源占用直觉**：warps 多通常意味着更高的寄存器/共享资源占用风险，从而影响同一 SM 上能并行驻留多少个 instances（occupancy）

> **结论**：`grid` 决定“有多少个实例并行”；`num_warps` 决定“每个实例内部大概多大规模协作执行”。

### 3. 从一次 kernel 调用开始：Python 侧发生了什么？

Triton 的典型调用长这样：

```text
grid = (triton.cdiv(N, BLOCK),)   # 或者二维/三维 grid
my_kernel[grid](x_ptr, y_ptr, N, BLOCK=BLOCK)
```

如果你把这行代码拆开看，它其实同时表达了三件事：**怎么切工作（grid）**、**怎么绑定参数（args + meta）**、**怎么编译并 launch（JIT + cache + 异步执行）**。

### 本章你会得到什么

- **你将理解**：`kernel[grid](...)` 到底做了哪些工作，以及为什么它看起来像“函数调用”但实际上是一次 GPU launch。
- **你将能做**：遇到“第一次很慢/改了没生效/结果还在跑”的情况，知道优先从哪几处排查。

### 3.1 `my_kernel[grid]`：先把“函数”变成“可 launch 的 kernel”

- `@triton.jit` 把一个 Python 函数变成 Triton kernel。
- `my_kernel[grid]` 不是立刻执行；它会先根据 `grid` 生成一个“launcher”，然后你再用 `(...)` 把参数传进去。

> **关键点**：`grid` 在 Triton 里叫 *SPMD launch grid*，它“表示并行运行的 kernel instances 数量”，并且“类似 CUDA launch grids”（见 `triton/python/tutorials/01-vector-add.py` 里对 `grid` 的注释）。

### 3.2 `grid` 可以是 Tuple，也可以是 `lambda meta: (...)`

你会看到两种常见写法：

- **直接 Tuple**：`grid = (triton.cdiv(n, BLOCK),)`
- **可调用 grid**：`grid = lambda meta: (triton.cdiv(n, meta["BLOCK_SIZE"]),)`

第二种更常见于 autotune/多配置场景：因为 `meta` 会随配置变化，grid 也可以随之变化（同样见 `triton/python/tutorials/01-vector-add.py`）。

### 3.3 参数到底怎么传进去：args（运行时） vs meta（编译期）

把一次调用拆成两类参数会清楚很多：

- **运行时参数（args）**：张量指针、shape/stride、普通标量等（在 kernel 运行时才知道）
- **编译期参数（meta）**：用 `tl.constexpr` 声明的参数（必须以关键字形式传入；会参与特化编译）

Triton 教程里对这件事有一句非常“工程化”的提醒：

- **每个 `torch.Tensor` 会被隐式转换成“指向首元素的指针”**
- **别忘了把 meta 参数作为关键字传进去**

（见 `triton/python/tutorials/01-vector-add.py` 中 `# NOTE:` 的三条 bullet）

> **陷阱**：你把 `BLOCK_SIZE` 这种 `tl.constexpr` 参数当成普通位置参数传，往往会得到“能跑但行为怪/频繁重编译/直接报错”的混合体验。把它当成“编译开关”就不容易写错。

### 3.4 第一次为什么慢：JIT 编译 + 缓存命中

第一次调用某个 kernel 时，runtime 需要：

- 根据目标设备 + 参数类型 + `tl.constexpr`（以及一些编译选项）做**特化编译**
- 把编译产物缓存起来，后续调用优先走缓存

关于“缓存放哪”这件事，你可以直接在 Triton 仓库 README 里找到：

- `TRITON_HOME=/some/path` 可以改变 `.triton` 目录的位置（默认在用户 home）<br>（见 `triton/README.md` 的 *Tips for building* 部分）

### 3.5 为什么你感觉“我已经 return 了，但 GPU 还在跑”：异步执行

Triton kernel launch 和 CUDA kernel launch 一样，通常是**异步**的：

- 教程里明确写了：由于还没有调用 `torch.cuda.synchronize()`，所以 kernel 在 `return output` 后仍然“在异步运行”（见 `triton/python/tutorials/01-vector-add.py`）。

> **结论**：你在 Python 里拿到的 `torch.Tensor` 只是“结果的句柄”；真正的计算可能还在 GPU 上排队/执行。

### 3.6 你改了代码/参数但没生效：优先怀疑“缓存与重编译条件”

当你在调试/学习阶段，最常见的困惑之一是：

- “我改了 kernel，怎么没重新编译？”
- “我开了 dump，怎么输出不对？”

在 Triton 的 README 里有两个直接可用的排查手段：

- cache 可能影响 IR dump：如果 `MLIR_ENABLE_DUMP=1` 不生效，建议清理 `~/.triton/cache/*`<br>（见 `triton/README.md` 环境变量说明）
- `TRITON_ALWAYS_COMPILE=1` 可以强制编译，即使缓存命中也重新编译<br>（同样见 `triton/README.md`）

> **注意**：这不是“性能调参”，而是“学习/调试时确保你看到的是最新行为”的手段。

### 3.7 本章小结

- **`kernel[grid](...)` 做了三件事**：确定 launch grid、绑定参数（args + meta）、必要时 JIT 编译并异步 launch。
- **`grid` ≈ CUDA grid**：决定并行 instances 数量；可以是 Tuple，也可以依赖 `meta` 的 callable。
- **Tensor 会被隐式转指针**；`tl.constexpr` 这类 meta 参数要用关键字传入。
- **第一次慢很正常**：多半在编译；之后通常走缓存。
- **“没生效/没重编译”**：优先从缓存命中与强制编译/清 cache 去排查。

### 4. 内核里最重要的三件事：索引、访存、mask

### 本章你会得到什么

- **你将理解**：为什么 Triton kernel 的正确性几乎都可以归结为“索引、访存、mask”三件事。
- **你将能做**：看到一个 kernel 时，按固定顺序检查它是否会越界、是否会读/写错位置、以及 mask 是否能覆盖尾块/边界。

绝大多数 Triton kernel，本质都是在解决：

1. **索引（Indexing）**：这个 program instance 负责哪一块数据？块内每个 lane 对应哪一个元素？
2. **访存（Memory access）**：把全局内存（HBM）里的数据搬到寄存器/共享路径上，做计算，再写回。
3. **mask（边界与稀疏条件）**：不越界、不读写非法地址；可选地做 padding/分支选择。

> **结论**：性能优化可以非常复杂，但**正确性几乎总是由这三件事决定**。

### 4.1 索引：先回答“我处理哪一块”

索引这件事建议你永远先用同一个问题开场：

- **这个 program instance 对应输入/输出里的哪一段（哪一个 tile）？**

通常你会看到这套组合：

- `pid = tl.program_id(axis=0)`：我是哪一个实例
- `block_start = pid * BLOCK`
- `offsets = block_start + tl.arange(0, BLOCK)`

Triton 的向量加法教程把它写得非常直接（见 `triton/python/tutorials/01-vector-add.py`）：

- `offsets = block_start + tl.arange(0, BLOCK_SIZE)`
- `mask = offsets < n_elements`

> **关键点**：先在纸上/脑中把 `offsets` 写出来（例如 `BLOCK=64` 时第 3 块就是 `[192..255]`），你就不会在 stride、reshape、多维映射上迷路。

### 4.2 访存：把“索引”翻译成“地址”

当你有了 `offsets`（或者二维的 `offs_m/offs_n`）之后，下一步是把它们翻译为地址表达式：

- 1D 连续：`x_ptr + offsets`
- 2D（带 stride）：`x_ptr + pid_m * stride_xm + cols * stride_xn`

> **注意**：地址表达式本身不复杂，复杂的是“你是否在正确的 layout 上做了正确的映射”。因此一旦出现结果错，优先怀疑：stride 传错/单位混乱/轴顺序写反。

### 4.3 `tl.load`：mask 与 other 决定你是否“安全读”

Triton 官方 API 文档对 `tl.load(pointer, mask, other)` 的语义很明确（`https://triton-lang.org/main/python-api/generated/triton.language.load.html`）：

- **mask**：如果 `mask[idx]` 为 false，则不从 `pointer[idx]` 读取
- **other**：如果 `mask[idx]` 为 false，则返回 `other[idx]`

在实践中，你可以把它当作“无分支的安全读取”：

- 尾块越界（`offsets >= n_elements`）→ `mask=False` → 不读内存
- 返回值用 `other` 填上一个安全的默认值（例如 `0.0`）

> **陷阱**：如果你会在后续计算里用到被 mask 掉的位置，建议显式提供 `other`，否则这些位置可能是未定义值（不同后端可能表现不同；文档里也强调 padding_option 的 `""` 表示 undefined）。

### 4.4 `tl.store`：mask 决定你是否“安全写”

`tl.store(pointer, value, mask=...)` 的语义同样清晰（`https://triton-lang.org/main/python-api/generated/triton.language.store.html`）：

- **mask**：如果 `mask[idx]` 为 false，则不把 `value[idx]` 写到 `pointer[idx]`

这也是为什么向量加法教程在 store 时也加了同一个 `mask`（见 `triton/python/tutorials/01-vector-add.py`）：

```text
mask = offsets < n_elements
tl.store(output_ptr + offsets, output, mask=mask)
```

> **结论**：只要存在“最后一个 tile 不满”的可能性，`tl.store` 和 `tl.load` 通常都应该对称地使用同一个边界 mask。

### 4.5 mask 不只是防越界：它也是你的“条件执行”工具

除了边界，你还会用 mask 表达：

- padding 区域
- 条件写（例如只写某些 lane）
- 稀疏/过滤逻辑

> **关键点**：mask 的力量在于把“分支”变成“数据流”。这也是 Triton kernel 往往比 CUDA thread 代码更容易读的原因之一。

### 4.6 常见坑（看到就该反射性检查）

- **mask 形状不对**：`mask` 必须能 broadcast 到 `pointer.shape`（`tl.load/store` 文档里明确写了 broadcast 行为）
- **有 mask 却没 other**：如果后续计算依赖被 mask 的元素，结果可能不稳定/不可移植
- **索引对了但地址错了**：stride/轴顺序/展平顺序是最常见原因

### 4.7 本章小结

- **索引**：回答“这个实例负责哪一段”
- **访存**：把索引翻译成“正确的地址表达式”
- **mask**：保证读写安全，同时也是表达条件逻辑的工具

### 4.8 资料与出处

### 5. `grid` 与 `program_id`：把工作切块

### 本章你会得到什么

- **你将理解**：`grid` 和 `tl.program_id(axis)` 分别在回答什么问题，以及它们如何一起把“全局问题”切成“每个实例的一块工作”。
- **你将能做**：写出不会漏数据/不会越界的 `grid`，并在 kernel 内用 `program_id` 正确定位到自己的 tile。

### 5.1 一维 grid：从 `N` 个元素切成 `triton.cdiv(N, BLOCK)` 块

假设你要做向量加法 `y[i] = x[i] + bias`，长度为 `N`。我们用 `BLOCK` 大小切分：

- **实例数量（grid size）**：`grid = (triton.cdiv(N, BLOCK),)`

- **实例内定位**：

你在 `triton/python/tutorials/01-vector-add.py` 里能看到这个模式的完整形态：

```text
pid = tl.program_id(axis=0)
block_start = pid * BLOCK_SIZE
offsets = block_start + tl.arange(0, BLOCK_SIZE)
mask = offsets < n_elements
x = tl.load(x_ptr + offsets, mask=mask)
tl.store(output_ptr + offsets, output, mask=mask)
```

> **结论**：1D 场景里，`grid` 决定“有多少块”，`program_id(0)` 决定“我是哪一块”，`tl.arange` 决定“块内有哪些 lane/元素”。

### 5.2 二维 grid：把二维空间切成“行块 × 列块”

当你的问题是二维（比如矩阵、二维张量、或者“最后一维是列”的 batch 数据），更常见的切法是：

- `grid = (triton.cdiv(M, BLOCK_M), triton.cdiv(N, BLOCK_N))`
- 每个 program instance 负责一个 `BLOCK_M × BLOCK_N` 的 tile

在 kernel 内你通常会看到：

- `pid_m = tl.program_id(axis=0)`：第几块“行块”
- `pid_n = tl.program_id(axis=1)`：第几块“列块”
- `offs_m = pid_m * BLOCK_M + tl.arange(0, BLOCK_M)`
- `offs_n = pid_n * BLOCK_N + tl.arange(0, BLOCK_N)`
- `mask_m = offs_m < M`、`mask_n = offs_n < N`，再组合成二维 mask

> **关键点**：`axis=0/1/2` 只是在 3D launch grid 上取坐标（文档也明确 axis 只能是 0/1/2）。至于你把 0 当行、1 当列，是你在 kernel 里约定的——一旦约定了，就要在 `grid` 和地址映射里保持一致。

### 5.3 `tl.num_programs(axis)`：我这条轴上一共有多少实例？

有些时候你不仅要知道“我是谁”，还要知道“同一维上总共有多少个实例”，例如：

- 做分块规约/分块 scan，需要知道自己是不是最后一个块
- 做“尾块特殊处理”（比如最后一块做收尾写回）

这时用 `tl.num_programs(axis)`（文档：`https://triton-lang.org/main/python-api/generated/triton.language.num_programs.html`）：

- `n = tl.num_programs(axis=0)`：axis=0 上实例总数

### 5.4 常见坑（切块相关）

- **grid 维度和 `program_id(axis)` 不一致**：你只 launch 了 1D grid，却在 kernel 里取 `program_id(1)`，通常意味着“你在读不存在的维度语义”
- **轴语义写反**：把 `pid_m`/`pid_n` 互换，导致地址映射整体转置或乱序
- **只 mask 了一个维度**：2D tile 的尾块要同时 mask 行与列，否则仍可能越界
- **`BLOCK` 不是整除**：忘了 `cdiv` 或忘了边界 mask，尾块一定出事

### 5.5 本章小结

- `grid`：决定“并行实例的排布与数量”
- `program_id(axis)`：决定“我在 grid 里的坐标”（从而决定我负责哪一块）
- `num_programs(axis)`：决定“同一条轴上总共有多少块”（用于边界/收尾逻辑）

> 下一章我们会把“切到哪一块”进一步落到真实 Tensor 上：为什么你经常需要显式传 `stride`，以及如何用 stride 把二维/高维索引翻译成正确地址。

- 文档：`https://triton-lang.org/main/python-api/generated/triton.language.num_programs.html`（`num_programs(axis)` 的定义与 axis 约束）

### 6. 指针与 layout：Triton 如何“看见”你的 Tensor？

### 本章你会得到什么

- **你将理解**：为什么 Triton kernel 里常见的不是 “传一个 Tensor 就完事”，而是“指针 + shape + stride”的组合。
- **你将能做**：把多维索引稳定地翻译成地址表达式，并一眼识别“stride/轴顺序/展平方式”导致的读写错位。

Triton kernel 的入参常写成 `x_ptr`、`y_ptr`，看起来像指针。对于 PyTorch Tensor：

- `x` 在 Python 里是 `torch.Tensor`
- 传给 Triton 时，runtime 会把它暴露为指向底层 storage 的指针（并带上 dtype 信息）

但**一个指针不够描述 layout**。所以你在 kernel 里经常还会显式传入：

- shape（例如 `M, N`）
- stride（例如 `stride_xm, stride_xn`）

### 6.1 stride 是什么？它回答“相邻元素在内存里隔多远”

对一个二维张量 `X[M, N]`：

```text
X_ptr + i * stride_xm + j * stride_xn
```

就是元素 `(i, j)` 的地址（以 element 为单位还是以 byte 为单位，取决于 Triton 的指针语义；实践中把 stride 当作“元素步长”来用通常没问题，因为 runtime 会一致处理）。

**这也是 Triton 能处理任意 layout 的根本原因**：你不需要假设 contiguous，只要 stride 正确，你就能算对地址。

### 6.2 从“二维切块”到“二维地址”：最常见的指针算术形态

在第 5 章你已经学会了如何用 `pid_m/pid_n` 切出一个 `BLOCK_M × BLOCK_N` 的 tile。把它落到地址上，通常就是这类表达式：

- `offs_m = pid_m * BLOCK_M + tl.arange(0, BLOCK_M)`
- `offs_n = pid_n * BLOCK_N + tl.arange(0, BLOCK_N)`
- `ptrs = x_ptr + offs_m[:, None] * stride_xm + offs_n[None, :] * stride_xn`

你可以在 Triton 的矩阵乘教程里看到几乎同构的“指针块”写法（`triton/python/tutorials/03-matrix-multiplication.py` 的 Pointer Arithmetic 部分）：

- `a_ptrs = a_ptr + (offs_am[:, None]*stride_am + offs_k [None, :]*stride_ak)`
- `b_ptrs = b_ptr + (offs_k [:, None]*stride_bk + offs_bn[None, :]*stride_bn)`

> **关键点**：把 `ptrs` 当成“地址矩阵”来理解，你后面的 `tl.load(ptrs, mask=...)` 就会非常自然。

### 6.3 为什么 stride 经常必须显式传入

很多新手会期待：既然传的是 `torch.Tensor`，Triton 能不能自己知道 layout？从工程接口来说，Triton 确实能拿到指针与 dtype，但“如何从 `(i, j, ...)` 走到地址”这件事，在 kernel 里通常需要你显式指定（尤其当你不想假设 contiguous 时）。

最常见的做法就是把 `x.stride(0) / x.stride(1) ...` 作为参数传入 kernel。你同样能在矩阵乘教程的 kernel launch 里看到它把 `a.stride(0), a.stride(1)` 等作为实参传进去（`triton/python/tutorials/03-matrix-multiplication.py`）。

### 6.4 “看起来没错但结果错”的三大 layout 坑

- **轴顺序写反**：你以为 `stride_xm` 是行步长，实际却把列步长传进来了（或反过来）
- **展平方式不一致**：你用 `pid` 线性化了 2D grid，但地址映射仍按 2D 写；或者反过来
- **mask 用对了但 ptrs 算错了**：mask 只能防越界，不能防“读错位置”

> **结论**：只要结果错且不越界，优先怀疑 stride/轴语义/地址公式，而不是怀疑算子本身。

### 6.5 本章小结

- **指针**：告诉你“数据从哪里开始”
- **shape**：告诉你“合法索引范围是什么”（也影响 grid 与 mask）
- **stride**：告诉你“索引如何映射到地址”

> 下一章我们会回到 `tl.load/tl.store`：更系统地看 `mask/other/boundary_check` 等参数如何影响“安全读写”。

### 6.6 资料与出处

- 教程：`triton/python/tutorials/03-matrix-multiplication.py`（Pointer Arithmetic：如何用 stride 构造块指针/地址矩阵）

### 7. `tl.load` / `tl.store` 深挖：mask、other、边界与安全

### 本章你会得到什么

- **你将理解**：`tl.load/tl.store` 在“不同指针形态”下的语义差异（标量指针 / 指针张量 / block pointer）。
- **你将能做**：写出可移植、边界安全、不会因 broadcast/mask 细节而“看起来能跑但结果怪”的读写代码。

### 7.1 `tl.load`：三个“指针形态”，三套规则

`tl.load(pointer, mask=None, other=None, boundary_check=(), padding_option=..., ...)` 的文档把 `pointer` 分成三类（`https://triton-lang.org/main/python-api/generated/triton.language.load.html`）：

- **单元素指针（scalar pointer）**：读回一个标量

- **指针张量（N 维 pointers）**：读回一个 N 维张量

- **block pointer（`make_block_ptr` 创建）**：读回一个 block

> **关键点**：你前面章节写的 `x_ptr + offsets`、`x_ptr + offs_m[:, None]*... + offs_n[None, :]*...` 属于“指针张量”这一类，所以你看到的 `mask/other` 规则就是“broadcast 到 pointer.shape”。

### 7.2 `mask` + `other`：无分支的“安全读”

根据文档：

- 当 `mask[idx]` 为 false：不从 `pointer[idx]` 读
- 当 `mask[idx]` 为 false：返回 `other[idx]`

你可以把它当作一种“数据流式 if”：

- **边界安全**：尾块越界位置不发起真实读
- **数值安全**：越界位置用 `other` 填一个你能接受的默认值（例如 `0`、`-inf`、最大值等，取决于算法）

> **陷阱**：如果你后续计算会用到被 mask 掉的 lane，最好明确传 `other`。在 `padding_option` 里，空字符串 `""` 代表 undefined（文档原文），这类“未定义值”在跨后端时尤其容易踩坑。

### 7.3 `tl.store`：同样有三套规则（以及 value 的 broadcast）

`tl.store(pointer, value, mask=None, boundary_check=(), ...)` 的文档同样区分三类指针（`https://triton-lang.org/main/python-api/generated/triton.language.store.html`）：

- **单元素指针**：写标量（`mask` 也必须是标量）
- **指针张量**：写一个 N 维 block

- **block pointer**：

> **结论**：只要你在用“指针张量”，`tl.load/tl.store` 的心智模型就非常一致：**mask broadcast、value/other broadcast**，然后逐元素做“是否读/是否写”的决定。

### 7.4 `boundary_check` / `padding_option`：block pointer 的“越界策略”

当你进入 block pointer 模式（`make_block_ptr`）时：

- 你不能再用 `mask/other`
- 你需要通过 `boundary_check=(...)` 指明在哪些维度做边界检查
- 你可以用 `padding_option` 指定越界填充值（文档列出 `"" | "zero" | "nan"`，其中 `""` 是 undefined）

> **注意**：这就是为什么很多高性能 matmul/tma 类 kernel 会更偏向 block pointer：它把“块级越界处理”变成编译器能更好优化的形式。但代价是：你必须理解并遵守这里的规则。

### 7.5 cache/eviction/volatile：先知道它们“存在”，再决定要不要用

`tl.load`/`tl.store` 文档里还暴露了与 NVIDIA PTX 缓存相关的参数：

- `cache_modifier`：例如 `".ca" / ".cg" / ".cv"`（load）或 `".wb" / ".cg" / ".cs" / ".wt"`（store）
- `eviction_policy`
- `volatile`

> **关键点**：这些参数会影响访存行为，但它们属于“性能/一致性策略”层面。你在学习正确性时，优先把精力放在 **地址、mask、broadcast、越界策略** 上。

### 7.6 常见坑（读写语义）

- **mask 形状不对**：你以为是 1D mask，但 pointer 是 2D；最后 broadcast 方式和你想的不一样 → 结果错
- **store 的 value 被广播**：你以为写的是标量到一个位置，实际写到了整个 block（因为 pointer 是指针张量）
- **block pointer 仍然传了 mask/other**：会直接违反文档约束（应当用 `boundary_check/padding_option`）

### 7.7 本章小结

- 先判断你在用哪种 `pointer`：**标量指针 / 指针张量 / block pointer**
- **指针张量**：靠 `mask/other` 做安全读写（broadcast 是默认行为）
- **block pointer**：靠 `boundary_check/padding_option` 做越界策略（`mask/other` 必须为 `None`）

> 下一章我们会从“语义”走到“编译视角”：这些写法为什么会影响 TTIR/TTGIR 的生成与优化路径。

- 文档：`https://triton-lang.org/main/python-api/generated/triton.language.store.html`（`tl.store`：三类 pointer、mask、value broadcast、boundary_check、cache_modifier）

### 8. 编译链路高层视角：从 Python 到 GPU 指令

### 本章你会得到什么

- **你将理解**：Triton 从 `@triton.jit` 的 Python 代码出发，会经历哪些“IR 分层”，最终变成可执行的目标代码（如 PTX / AMDGCN）。
- **你将能做**：遇到“结果不对/性能不对/编译报错”时，知道如何把问题定位到更具体的阶段（前端语义、IR 变换、LLVM、目标后端）。

你不需要一上来就啃完 Triton 编译器源码，但你应该知道它大致分层（这会帮助你理解“为什么这个写法能优化/为什么那个写法会报错”）：

1. **Python 前端**：你写 `@triton.jit` 的 Python 函数；
2. **Triton IR（常被称为 TTIR）**：把 `tl.*` 操作变成 IR；
3. **Triton GPU Dialect / 更低层 IR（常见称呼 TTGIR / TritonGPU）**：做 tile 化、layout、向量化、流水等变换；
4. **LLVM IR**：再 lower 到 LLVM；
5. **目标 ISA**：NVIDIA PTX / AMDGCN 等；
6. **runtime 缓存与加载**：编译产物缓存下来，下次直接用。

对新手最实用的结论是：

- **`tl.constexpr` 会影响编译**（因为它是编译期常量，参与优化与特化）
- 很多“看起来是 Python 逻辑”的东西，其实会在编译期展开（比如 `tl.static_range`）

### 8.1 为什么 Triton 需要“分层 IR”：blocked program 需要强编译器参与

从动机上，你可以把 Triton 看成把“线程级并行”抬升到“块级程序”的范式：用 **blocked program** 来表达计算，再交给编译器做大量调度与优化。

Triton 文档在介绍动机时明确指出：它提出的是一种“programs — rather than threads — are blocked”的变体，并强调这会带来调度与优化上的挑战，编译器需要做大量工作（见 `triton/docs/programming-guide/chapter-1/introduction.rst` 的 Motivation/Challenges 部分）。

> **结论**：你写 Triton kernel 时，很多“看起来是高层表达”的代码，之所以能跑得像底层手写 kernel，一大部分原因在于中间 IR 层提供了足够的空间让编译器做变换与调度。

### 8.2 如何观测编译发生了什么：dump IR / timing / interpreter

当你想把“我写的代码”与“编译器生成的结果”对齐时，最直接的办法是让编译过程变得可观测。

Triton 仓库 README（Tips for hacking）列出了很多可用的环境变量，例如（见 `triton/README.md`）：

- **看 IR**：

- **看耗时**：

- **避免缓存干扰**：

- **强制重新编译**：

如果你正在排查“逻辑不对”而不是“后端生成问题”，Triton 的 Debugging 文档也建议使用解释器模式（见 `triton/docs/programming-guide/chapter-3/debugging.rst`）：

- `TRITON_INTERPRET=1`：绕过编译，在 CPU 上用 interpreter 模拟执行（并且会按 program instance 顺序逐个执行）

> **关键点**：学习阶段优先用 interpreter/IR dump 来“验证你的索引、mask、地址计算是不是你以为的那样”，再去纠结更底层的后端细节。

### 8.3 `tl.constexpr` vs 运行时参数：新手最重要的分界线

在 Triton 里，参数大致分两类：

- **运行时参数**：比如 `x_ptr`、`M`、`N`、stride 等。它们在 kernel 运行时才知道值。
- **编译期参数（`tl.constexpr`）**：比如 `BLOCK`、`BLOCK_M/BLOCK_N`、`num_warps` 等。它们会影响 IR 生成与优化，因此会参与“编译 key”。

实用结论：

- 想让编译器展开循环/消除分支/做更强特化 → 用 `tl.constexpr`
- 想让同一个编译产物适配更多输入 → 少用 `tl.constexpr`（但性能/可优化空间可能下降）

### 8.4 `tl.static_range`：告诉编译器“这是编译期循环”

如果你写：

- `for k in range(...):` → 这是 Python 运行时循环（通常不适合出现在 Triton kernel 里）
- `for k in tl.static_range(...):` → 这是编译期展开的循环（更符合 Triton 的优化模型）

你可以把 `tl.static_range` 理解为：把“循环次数”变成 IR 的结构，而不是 Python 的控制流。

### 8.5 本章小结

- Triton 的编译链路可以粗分为：Python 前端 → TTIR → TTGIR/TritonGPU → LLVM IR → 目标 ISA → runtime 缓存与加载。
- `tl.constexpr` 与 `tl.static_range` 这类写法之所以重要，是因为它们直接影响 IR 的形状与特化路径。
- 真要理解“发生了什么”，不要靠猜：优先用 `TRITON_INTERPRET`、IR dump 与 timing 把编译过程变得可观测。

### 9. `num_warps` 与 `num_stages`：它们究竟在控制什么？

你会经常见到 Triton kernel 配置类似：

- `num_warps=4/8/16`
- `num_stages=2/3/4`

先给新手一个可用的解释（不是硬件教科书，但够你做正确推理）：

### 本章你会得到什么

- **你将理解**：`num_warps` 与 `num_stages` 分别在影响“一个 program instance 内怎么并行”和“循环里 load/compute 怎么重叠”。
- **你将能做**：在不盲调的前提下，选出“合理默认值”，并在配置不合适时知道从哪些信号定位（寄存器压力、occupancy、pipeline 不生效等）。

### 9.1 `num_warps`：每个 kernel instance 用多少 warp 协作

可以把它理解为：**这个 program instance 在底层会用多少个 warp 协作**。warp 越多：

- 可能更高的吞吐（尤其是计算密集或需要更多并行加载时）
- 也可能更高的寄存器/共享资源占用，导致并发实例数下降（occupancy 降）

所以它不是“越大越快”，而是 trade-off。

更“可引用”的定义来自 `triton.Config` 文档（`https://triton-lang.org/main/python-api/generated/triton.Config.html`）：

- **`num_warps`**：GPU 编译时使用的 warps 数量。文档给的例子是：`num_warps=8` 时，每个 kernel instance 会“协作使用 `8 * 32 = 256` threads”来执行。

> **结论**：`num_warps` 不是一个“语法参数”，它决定了每个 instance 内部的协作规模；因此它会直接牵动资源占用与并发度。

### 9.2 `num_stages`：软件流水的深度（让 load/compute 更好重叠）

很多 kernel（尤其是 matmul 类）会在 K 维循环里：

- 先加载下一块数据
- 再计算当前块

`num_stages` 可以理解为：**允许编译器做多深的 pipeline（预取/双缓冲/多缓冲）**。stage 多可能更好隐藏内存延迟，但也会增加寄存器/共享占用。

同样，`triton.Config` 的定义非常直接：

- **`num_stages`**：编译器在对循环做 software-pipelining 时使用的 stage 数量；文档还指出它“主要对 SM80+ 的矩阵乘工作负载有用”（`https://triton-lang.org/main/python-api/generated/triton.Config.html`）。

### 9.3 怎么选“合理默认值”：先可用，再交给 autotune

这篇文章不以性能为主，但为了让你建立“工程上可操作”的直觉，这里给一个很稳的策略：

- **先用教程里的常见默认**（例如 `num_warps=4/8`、`num_stages=2/3` 这种范围）
- **当 kernel 已经正确**、且你发现性能/吞吐确实重要，再用 autotune 让机器帮你选（第 10 章）

> **关键点**：别在 kernel 还不稳定时就把问题归因到 `num_warps/num_stages`。先用解释器与小 shape 把索引/mask/地址确认对（第 11 章的调试方法）。

### 9.4 你选错了会发生什么：常见“症状—原因”映射

- **症状：`num_warps` 越大越慢**

- **症状：改 `num_stages` 没变化**

- **症状：第一次运行很慢**

### 9.5 本章小结

- `num_warps`：控制每个 kernel instance 内部的协作规模（warps/threads），影响并行度与资源占用
- `num_stages`：控制循环 software-pipelining 的深度，影响 load/compute 的重叠
- 策略：先用保守默认让 kernel 稳定跑对；需要时再交给 autotune 系统化搜索

- 文档：`https://triton-lang.org/main/python-api/generated/triton.Config.html`（`num_warps`/`num_stages` 的定义与说明）

### 10. Autotune / Heuristics：把“选参数”系统化

### 本章你会得到什么

- **你将理解**：为什么 autotune 会让“第一次运行很慢”，以及它具体在做什么（跑哪些配置、什么时候重新跑）。
- **你将能做**：为你的 kernel 选择合适的 `key`、避免 autotune 带来的副作用，并在“调参没生效/结果被重复更新”时快速定位原因。

Triton 的典型风格是：把性能敏感参数（BLOCK 大小、warps、stages）放在 meta 参数里，然后把“选参数”这件事系统化：

- `@triton.autotune(configs=[...], key=[...])`：枚举多个配置，按 key（通常是输入 shape）缓存最优配置
- `@triton.heuristics({...})`：用规则在编译前决定一些 meta 参数

即使你不追求性能对比，也建议理解 autotune 的“机制”，因为它会影响：

- 编译次数（配置越多，首次运行可能越慢）
- 缓存 key 的粒度（key 选得不对会导致复用失败或误复用）

### 10.1 `@triton.autotune`：把“试配置”变成可复现流程

`triton.autotune(configs, key, ...)` 的定义非常直白（`https://triton-lang.org/main/python-api/generated/triton.autotune.html`）：

- **configs**：`triton.Config` 的列表（每个 config 包含 `kwargs` 的 meta 参数，以及 `num_warps/num_stages` 等编译选项）
- **key**：一组“参数名”，当这些参数的值变化时，会触发对 configs 的重新评估

> **结论**：autotune 的核心就是——“同一个 kernel，多套 meta 配置；用 key 决定什么时候需要重新找最优配置”。

### 10.2 为什么 autotune 会慢：每个配置都要编译/运行/测量

文档明确写到：当所有配置被评估时，kernel 会运行多次（`https://triton-lang.org/main/python-api/generated/triton.autotune.html`）。

这解释了你在第 9 章提到的现象：

- **“第一次运行很慢”**：可能不是你代码慢，而是 autotune 正在跑一轮“编译 + benchmark 多配置”

### 10.3 key 怎么选：选“会改变最优配置”的那几个输入特征

一个实用原则是：

- key 只放那些**一变就可能换最优配置**的输入特征（最典型是尺寸：`M/N/K`、`n_elements` 等）
- 不要把“变化很频繁但对性能影响很小”的参数也塞进 key，否则会导致频繁重新 autotune

> **陷阱**：key 选太少会“错误复用”（用上一次的最优配置硬套到另一种输入）；key 选太多会“频繁重新评估”（每次都像第一次一样慢）。

### 10.4 autotune 的副作用：你的 kernel 会被执行多次

`@triton.autotune` 文档专门提醒了一个“正确性层面”的副作用：

- 当评估所有 configs 时，kernel 会运行多次
- 因此“kernel 更新的任何值”都会被更新多次

并给了标准解决方案：`reset_to_zero`（在每个配置跑之前把指定 tensor 置零），以及 `restore_value`（评估后恢复）（同样见 `https://triton-lang.org/main/python-api/generated/triton.autotune.html`）。

> **结论**：autotune 默认假设你的 kernel 是“纯函数式输出”（每次写同一个输出没副作用）。如果你的 kernel 有累加/原子/带状态写回，就必须显式处理这个问题。

### 10.5 让 autotune 变得“可观察”：打印最佳配置与耗时

`@triton.autotune` 文档说明：当环境变量 `TRITON_PRINT_AUTOTUNING=1` 时，会在每个 kernel autotuning 完成后打印包括“耗时 + 最佳配置”的信息（`https://triton-lang.org/main/python-api/generated/triton.autotune.html`）。

你也可以在 Triton 仓库 README 里看到同一个开关（`triton/README.md`）：

- `TRITON_PRINT_AUTOTUNING=1`：打印最佳配置与总 autotune 时间

> **关键点**：当你怀疑“是不是根本没 autotune / 或者 key 没触发重新评估”，先把这个开关打开，你会更快得到答案。

### 10.6 `@triton.heuristics`：当你不想（或不能）跑 autotune

`triton.heuristics(values={...})` 用来“计算某些 meta 参数的值”（`https://triton-lang.org/main/python-api/generated/triton.heuristics.html`）：

- 你提供一个字典：`meta_name -> callable(args) -> value`
- callable 会基于运行时参数（args）算出 meta 参数（constexpr）值

它适合：

- autotune 太贵（配置太多、首次延迟不可接受）
- 你有清晰的规则（比如 `BLOCK_SIZE = next_power_of_2(n)` 这种）

> **结论**：heuristics 的目标不是“找到最优”，而是“用规则快速给一个够好的值”，并避免 autotune 的多次运行与测量成本。

### 10.7 本章小结

- autotune：**枚举 configs + 用 key 决定何时重跑**；代价是首次会运行多次并做测量
- key：只放“会改变最优配置”的输入特征，避免“频繁重跑”和“错误复用”
- 副作用：kernel 会被执行多次；需要用 `reset_to_zero/restore_value` 等机制避免重复更新导致错误
- heuristics：用规则计算 meta 参数，适用于“autotune 太贵或不适用”的场景

- 文档：`https://triton-lang.org/main/python-api/generated/triton.autotune.html`（`configs/key`、多次运行、副作用与 `reset_to_zero`、`TRITON_PRINT_AUTOTUNING`）
- 文档：`https://triton-lang.org/main/python-api/generated/triton.heuristics.html`（heuristics 的定义与用法）
- 文档：`triton/README.md`（`TRITON_PRINT_AUTOTUNING` 等调试/观测开关）

### 11. 调试与理解：让 kernel 变得“可解释”

### 本章你会得到什么

- **你将理解**：Triton 的调试工具分别适合解决哪类问题（逻辑错误、越界、数据竞争、编译阶段问题）。
- **你将能做**：按一个固定流程把“看起来很玄学的问题”快速收敛到：索引/地址/边界/编译缓存/后端生成中的某一类。

当你写 kernel 出 bug（越界、结果错、形状不对）时，最有效的不是“盲调参数”，而是让它可观察。

### 11.1 先把问题分型：你到底在排查什么？

- **逻辑/索引错误（结果不对）**：优先用 interpreter + 小 shape + 打印中间值
- **越界/非法访存（崩溃或随机错）**：优先检查 `mask`，然后用 sanitizer/断言
- **编译/变换阶段问题（dump/重编译不生效）**：优先处理缓存与 dump 开关

> **关键点**：不要一上来就调 `num_warps/num_stages` 或改一堆代码。先用“可观测”手段定位问题类型。

### 11.2 Interpreter：把并行变成顺序，方便你看清每一步

Triton 的调试文档把 interpreter 描述为一种“直接且有帮助”的工具：它会让 kernel 绕过编译，在 CPU 上用 numpy 等价实现来模拟执行（`triton/docs/programming-guide/chapter-3/debugging.rst`）。

- 开启方式：`TRITON_INTERPRET=1`
- 执行特征：**按 program instance 顺序逐个执行，操作逐条执行**（文档原文强调了 sequential / one at a time）

文档给了三种典型用法：

- 直接 `print(tensor)` 或 `print(tensor.handle.data[idx])` 看中间值
- 用 `pdb` 单步调试：`TRITON_INTERPRET=1 pdb main.py`
- 在 kernel 内 `pdb.set_trace()` 打断点（同文档示例）

> **结论**：interpreter 最适合排查“索引/地址/mask 逻辑是否如你所想”，因为它把并行的不确定性移除掉了。

### 11.3 Debugging ops：编译期 vs 运行期

调试文档提到 Triton 有四个调试算子（`triton/docs/programming-guide/chapter-3/debugging.rst`）：

- **编译期**：`static_print`、`static_assert`
- **运行期**：`device_print`、`device_assert`

并且：

- `device_assert` 只在 `TRITON_DEBUG=1` 时执行
- 其他调试算子不依赖 `TRITON_DEBUG`（文档原文）

> **关键点**：当你需要确认“编译期常量、分支是否展开、某个 shape/constexpr 是否如预期”，用 `static_*`；当你要确认运行时数据，才用 `device_*`。

### 11.4 后端工具：把“越界/数据竞争”变成明确报错

调试文档还列了第三方工具建议（`triton/docs/programming-guide/chapter-3/debugging.rst`）：

- NVIDIA：`compute-sanitizer` 用于检查 data race 与内存访问问题
- AMD：ROCm 侧的 AddressSanitizer（文档给了链接）
- 可视化：`triton-viz`（文档给链接）

> **注意**：这类工具适合解决“并发导致的非确定性问题”或“看起来像随机的非法访存”。逻辑错误还是先回到 interpreter。

### 11.5 让编译过程可观察：IR dump / timing / 强制编译 / 清 cache

当你怀疑问题来自“编译/变换阶段”，或者你觉得“改了代码却没生效”，Triton 的 README 提供了一整套开关（`triton/README.md` 的 Tips for hacking）：

- **dump IR**：`MLIR_ENABLE_DUMP=1`、`LLVM_IR_ENABLE_DUMP=1`、`TRITON_KERNEL_DUMP=1` + `TRITON_DUMP_DIR=...`
- **强制重编译**：`TRITON_ALWAYS_COMPILE=1`
- **缓存干扰**：dump 不生效时可清理 `~/.triton/cache/*`（README 里明确提醒）
- **看 autotune**：`TRITON_PRINT_AUTOTUNING=1`（第 10 章提到过）

> **结论**：学习/调试阶段，把这些开关当作“观察窗口”。你不是要背它们，而是要在需要时知道“该打开哪一个”。

### 11.6 一条可执行的调试流程（建议照着做）

- **步骤 1**：缩小输入（小 shape、尾块 case，例如 `N=17`）
- **步骤 2**：先保证边界安全（对称的 `tl.load`/`tl.store` mask，必要时加 `other`）
- **步骤 3**：开 interpreter（`TRITON_INTERPRET=1`），确认索引/地址/中间值
- **步骤 4**：如果是并发相关/非法访存，换 sanitizer 或 `device_assert`
- **步骤 5**：如果怀疑编译阶段，开 dump/强制编译，并清 cache 排除干扰

### 11.7 本章小结

- interpreter：排逻辑（索引/地址/mask），最稳最快
- 调试算子：区分编译期 `static_*` 与运行期 `device_*`
- 后端工具：排 data race/非法访存
- README 的环境变量：排“编译阶段/缓存/不可观测”

### 12. 写 Triton kernel 的检查清单（正确性优先）

- **块划分**：`grid` 是否覆盖所有元素？`triton.cdiv` 用对了吗？
- **索引**：`pid` 的轴含义是否一致？是否把 1D/2D 坐标正确映射到线性地址？
- **layout**：如果不是 contiguous，你有没有传 stride？地址计算是否使用 stride？
- **mask**：

- **dtype**：是否发生了不想要的类型提升/截断？（例如用 `to(tl.float32)` 做中间累加）
- **可重复性**：如果用了原子操作/并行归约，是否允许非确定性？（不追求性能也要意识到这点）

### 12.1 新手高频坑位（看到就该警惕）

- **把 `tl.tensor` 当 Python 标量用**：例如在 kernel 里写 `if cols == 0:`（`cols` 是向量，不是标量）
- **mask 形状不对**：`mask` 要和被 load/store 的张量形状一致（或可广播到一致），否则会得到“看起来能跑但结果错”
- **stride 单位混乱**：把 stride 当 byte 还是 element？（实践中：按 PyTorch 的 element-stride 传入，并在 kernel 里按“元素步长”做指针算术）
- **忘了最后一个 tile 的边界**：尤其是 2D/3D 时，行列两个维度都要 mask

### 附录：最小可运行例子

下面给两个“通用且短”的例子：一个向量加法、一个按行 reduce（都能帮助你练索引/访存/mask）。

### A. 向量加法（1D grid）

```text
import torch
import triton
import triton.language as tl

@triton.jit
def add_bias_kernel(x_ptr, y_ptr, bias, N: tl.constexpr, BLOCK: tl.constexpr):
    pid = tl.program_id(0)
    offs = pid * BLOCK + tl.arange(0, BLOCK)
    mask = offs < N
    x = tl.load(x_ptr + offs, mask=mask, other=0.0)
    y = x + bias
    tl.store(y_ptr + offs, y, mask=mask)

def add_bias(x: torch.Tensor, bias: float, block: int = 1024):
    assert x.is_cuda
    y = torch.empty_like(x)
    grid = (triton.cdiv(x.numel(), block),)
    add_bias_kernel[grid](x, y, bias, N=x.numel(), BLOCK=block)
    return y
```

你应该重点看懂：`pid/offs/mask` 的关系，以及为什么 `other=0.0` 是安全的。

### B. 按行求和（2D grid 的雏形）

```text
import torch
import triton
import triton.language as tl

@triton.jit
def row_sum_kernel(x_ptr, y_ptr, stride_xm, stride_xn, M: tl.constexpr, N: tl.constexpr, BLOCK_N: tl.constexpr):
    pid_m = tl.program_id(0)  # 每个 program instance 处理一行（或一块行）
    cols = tl.arange(0, BLOCK_N)
    offs = pid_m * stride_xm + cols * stride_xn
    mask = (pid_m < M) & (cols < N)
    x = tl.load(x_ptr + offs, mask=mask, other=0.0).to(tl.float32)
    s = tl.sum(x, axis=0)
    tl.store(y_ptr + pid_m, s, mask=pid_m < M)

def row_sum(x: torch.Tensor, block_n: int = 1024):
    assert x.is_cuda and x.ndim == 2
    M, N = x.shape
    y = torch.empty((M,), device=x.device, dtype=torch.float32)
    grid = (M,)
    row_sum_kernel[grid](x, y, x.stride(0), x.stride(1), M=M, N=N, BLOCK_N=block_n)
    return y
```

这个例子不是“最优写法”，但它能让你练到：

- stride 如何参与地址计算；
- `cols < N` 的尾块 mask；
- 为什么 reduce 的写回要小心：这里**只对一个 BLOCK 的列做求和**；如果 `N > BLOCK_N`，你需要在 N 维上分块循环累加（可用 `tl.static_range` 做编译期展开），或者用多个 program instance 分担并用原子/分层归约合并。
