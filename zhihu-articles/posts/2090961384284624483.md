2026 年 10 月芯片生态编译器基础设施 2026 年 9 月 30 日，DeepSeek 开源了面向华为昇腾 950 平台的六个基础设施组件。本文从 TileLang 编译器的技术架构出发，厘清 CUDA、Ascend C、TileLang、Compiler、Backend 五个核心概念的边界，并分析这一事件对 AI 芯片生态的结构性影响。

### 一、事件概述

DeepSeek 此次开源的组件与其面向 NVIDIA 平台的开源组件一一对应[1]：

| 组件 | 类型 | NVIDIA 对应物 |
| --- | --- | --- |
| TileLang（Ascend 版） | DSL + Backend | TileLang（CUDA 版） |
| DeepGEMM-Ascend | 算子库（TileLang 实现） | DeepGEMM |
| DeepEP-Ascend | 通信库（TileLang 实现） | DeepEP |
| TileKernels（昇腾版） | 算子库（TileLang 实现） | TileKernels |
| FlashMLA（昇腾版） | 算子库（TileLang 实现） | FlashMLA |
| DeepSelect（昇腾版） | 算子库（TileLang 实现） | DeepSelect |

其中，TileLang 是由北京大学、帝国理工学院、微软研究院联合开源的领域专用语言（DSL），论文发表于 ICLR 2026 Oral[2]。其余五个组件均为用 TileLang 编写的算子实现。

DeepSeek 官方声明，其训练中使用的全部 TileLang 算子已在昇腾 950 上达到高性能实现，计算与通信性能”接近硬件上限”[1]。与此同时，DeepSeek 与华为联合推进了基于 128 卡昇腾 950 的超节点方案[3]。

### 二、五个核心概念的边界

理解这一事件的前提，是准确区分以下五个常被混用的概念。它们处于不同的抽象层级，承担不同的技术职责。

### 2.1 CUDA C++ / Ascend C：硬件原生编程接口

**CUDA C++**是 NVIDIA GPU 的原生编程接口；**Ascend C**是华为昇腾 NPU 的原生编程接口。二者均直接面向硬件，具有以下特征：

- 直接操作硬件资源：线程、寄存器、共享内存（或昇腾的 Unified Buffer）、异步 DMA 引擎
- 与硬件架构深度绑定：CUDA 面向 SIMT 架构；Ascend C 面向 Cube/Vector 双核架构
- 代码不可移植：为 NVIDIA 编写的 CUDA 代码无法在昇腾上运行
- 性能上限：手写优化的 CUDA/Ascend C kernel 是各平台的性能天花板

**核心认知：**CUDA C++ 和 Ascend C 不是 TileLang 的”替代者”或”前任”，而是 TileLang 编译器的**输出产物之一**。TileLang 编译器根据目标设备，生成对应的 CUDA C 或 Ascend C 代码，再交由厂商工具链（NVCC 或 CANN 编译器）编译为最终二进制。

### 2.2 TileLang：基于 TVM/TIR 的领域专用语言

TileLang（论文标题：”TileLang: A Composable Tiled Programming Model for AI Systems”，arXiv:2504.17577）是一种 Python 嵌入式 DSL，其核心设计原则是[2]：

> “TileLang decouples scheduling space (thread binding, layout, tensorize and pipeline) from dataflow, and encapsulated them as a set of customization annotations and primitives.”

— Wang et al., ICLR 2026

具体而言，TileLang 建立在 Apache TVM 的基础设施之上，使用 TVM 的 TensorIR（TIR）作为中间表示（IR）[4]。开发者用 Python 语法描述 tile 级的计算 dataflow，调度决策（线程绑定、内存布局、张量化、流水线）通过显式原语控制，而非直接操作硬件寄存器。

关键原语包括：

- `T.Parallel`：线程绑定
- `T.copy`：tile 级数据搬运（Global ↔ Shared ↔ Local）
- `T.gemm`：矩阵乘张量化
- `T.Pipeline`：异步流水线

论文中的实验数据显示，FlashAttention 的 TileLang 实现仅需约 80 行 Python 代码，性能达到手写 CUDA 实现的 95% 以上[2]。

### 2.3 Compiler：多阶段编译管线

TileLang 的编译器不是一个单一程序，而是一个多阶段管线（pipeline）。根据 TileLang 源码和文档[[5][6]]，其内部结构如下：

```text
Python DSL (T.prim_func)
    ↓ (AST 解析 + Layout 内联)
TIRX Multi-Backend Dialect IR
    ↓
┌─────────────────┬─────────────────┐
│ Tile Scheduler  │ Layout & Swizzle│
│ (Pipeline/Auto-│ (TMA Lowering/  │
│  Sync)          │  Bank Conflict) │
└────────┬────────┴────────┬────────┘
         ↓                 ↓
    IR Lower Trace & Pass Optimization
         ↓
Backend CodeGen Dispatch Registry
    ├── CUDA (SM75-SM120)
    ├── ROCm (CDNA3/CDNA4)
    ├── Metal (M5)
    ├── Ascend (950 SIMD/SIMT)
    └── LLVM (x86/ARM CPU)
```

其中，**TIRX**（Tensor IR Extended）是 TileLang 在 TVM TIR 之上扩展的多后端方言 IR，用于承载跨硬件的通用表示[4]。

### 2.4 Backend：编译器内部的模块化插件

在 TileLang 的架构中，**Backend**是编译器内部的一个模块化组件，负责将 TIRX IR lower 到特定硬件的代码。TileLang 从 v0.1.12 起引入了**Backend Registry**架构，host 和 device 的 CodeGen 均通过注册表分发[7]。

截至 2026 年 9 月 30 日，TileLang 支持的 backend 如下[8]：

| Backend | Target | 硬件 | 支持级别 |
| --- | --- | --- | --- |
| NVIDIA CUDA | cuda | SM70 ~ SM120 | Primary |
| AMD ROCm/HIP | hip | CDNA / RDNA | Supported |
| Huawei Ascend 950 | ascend | Ascend 950 NPU | Supported（2026-09-30 加入） |
| Apple Metal | metal | Apple Silicon | Supported |
| LLVM CPU | llvm | Host CPU | Experimental |
| WebGPU | webgpu | WebGPU runtimes | Experimental |

新增 backend 不需要重写整个编译器，只需实现该 backend 的 Language Dialect 扩展、PassPipeline 和 CodeGen 模块，并注册到 Backend Registry 中。

### 2.5 cuBLAS / CANN 算子库：与 TileLang 并行的独立路线

**cuBLAS**、**cuDNN**、**CANN 算子库**是芯片厂商用手写 CUDA C / Ascend C 打磨的**闭源预编译库**。它们与 TileLang 的关系不是上下级，而是**框架层以下的两条并行算子供给路线**：

| 特征 | 厂商闭源算子库 | TileLang 开源算子语料 |
| --- | --- | --- |
| 源码可见性 | 无（二进制 .so） | TileLang Python 源码 |
| 执行路径 | 框架直接调用，不经过 TileLang | 经 TileLang 编译器 → CodeGen → 执行 |
| 性能 | 最优（手写优化） | 接近最优（通常 90-99%） |
| 覆盖范围 | 有限（头部常见 case） | 理论上无限（任何可表达算子） |
| 维护主体 | 芯片厂商 | 社区 + 模型厂商 |

PyTorch 的实际调度策略是**先查询闭源库，再 fallback 到 TileLang**：调用`torch.matmul`时，若 cuBLAS 存在优化实现则直接调用；若遇到自定义融合算子不在库中，则通过`torch.compile`触发 TileLang/Triton 现场编译。

### 三、概念关系的完整图景：从框架层到硬件的两条路线

两条路线共享同一个起点（PyTorch ATen 算子分发层），但执行路径完全不同：路线 A 是**运行时直接加载预编译二进制**，路线 B 是**编译时经 TileLang 管线现场生成 kernel**。以下分层次展开。

### 3.1 统一起点：PyTorch ATen 算子分发层

当模型执行到某个算子（如`aten::matmul`或自定义融合算子）时，PyTorch 的 ATen 分发器（Dispatcher）会依次查询以下注册表：

1.**Native 实现**：是否有针对该设备（CUDA / NPU）的原生实现

2.**Vendor Library 注册表**：cuBLAS / CANN 等是否注册了该算子的优化实现（路线 A）

3.**torch.compile 捕获**：若用户启用了`torch.compile`，算子落入 FX Graph，进入 inductor 的编译路径（路线 B）

路线 A 和路线 B 的分叉点就在这里：前者走**已编译的 C++ 库调用**，后者走**DSL → IR → CodeGen → 编译 → 执行**的完整管线。

### 3.2 路线 A：Vendor Library Path（运行时直接调用）

路线 A 不涉及 TileLang。PyTorch 通过`torch.ops`或 ATen 内部逻辑直接调用厂商提供的动态链接库：

```text
# 伪代码示意 ATen 内部逻辑
if (has_cublas_gemm(shape, dtype)):
    return cublasGemmEx(...)          # 直接调用 cuBLAS
elif (has_cann_gemm(shape, dtype)):
    return aclblasGemmEx(...)         # 直接调用 CANN
else:
    fallback_to_torch_compile(...)    # 转入路线 B
```

cuBLAS、cuDNN、CANN 算子库均是以手写 CUDA C / Ascend C 编译而成的二进制 .so 文件。框架加载后通过 dlsym 或静态链接直接调用其符号，**全程不经过 TileLang 编译器**。这是性能最优的路径，但覆盖范围受限于厂商人力——CANN 当前约 1500+ 算子，而社区长尾需求远超此数。

### 3.3 路线 B：TileLang JIT Path（编译时现场生成）

路线 B 是 TileLang 的核心战场。当 ATen 分发器决定走`torch.compile`路径时，inductor 会调用 TileLang（或 Triton）将 Python DSL 编译为设备可执行代码。以下以 TileLang 源码为例，逐层展开其编译管线。

### 3.3.1 编译入口：tilelang.lower()

TileLang 的编译入口是`tilelang.lower()`，位于`tilelang/engine/lower.py`[11]。其核心逻辑如下（简化自实际源码）：

```text
# tilelang/engine/lower.py
def lower(func_or_mod, target="cuda", target_host="llvm", ...):
    # Step 1: 规范化 target
    target = determine_target(target)  # 解析 target string → TVM Target 对象

    # Step 2: 语义检查
    PreLowerSemanticCheck(mod)

    # Step 3: IR 降低与合法化
    mod = LowerAndLegalize(mod, target)

    # Step 4: 针对目标设备优化
    mod = OptimizeForTarget(mod, target)

    # Step 5: 分离 host 与 device 代码
    host_mod = Filter(_is_host_call)(mod)
    device_mod = Filter(_is_device_call)(mod)

    # Step 6: device 代码生成（关键：backend dispatch 发生在这里）
    codegen_mod = device_codegen(device_mod, target)

    # Step 7: host 代码生成
    host_mod = host_codegen(host_mod, target_host)
    host_mod.import_module(codegen_mod)

    return CompiledArtifact(host_mod, device_mod, ...)
```

注意 Step 3 和 Step 4 中的`LowerAndLegalize`与`OptimizeForTarget`：前者将 TileLang 的 DSL 语法（如`T.copy`、`T.gemm`）展开为 TIRX（Tensor IR Extended）表示；后者执行后端特定的优化 pass，如内存布局推断、线程绑定、bank conflict 规避等。

### 3.3.2 Backend Registry：target → codegen 的分发机制

TileLang 从 v0.1.12 起引入了**Backend Registry**架构[7]。device codegen 和 host codegen 不再通过硬编码的 if-else 分支判断 target，而是通过注册表动态分发。其核心位于`tilelang/<backend>/backend.py`。

以 CUDA backend 和 Ascend backend 为例，其目录结构如下：

```text
tilelang/
├── cuda/
│   ├── backend.py          # CUDA Backend Registry 注册
│   ├── pipeline.py         # CUDA-specific pass pipeline
│   └── language/
│       └── __init__.py     # CUDA 方言扩展（如 TMA、WGMMA 原语）
├── ascend/
│   ├── backend.py          # Ascend Backend Registry 注册
│   ├── pipeline.py         # Ascend-specific pass pipeline
│   ├── target.py           # Ascend target 规范化（target_is_ascend, normalize_ascend_target）
│   └── language/
│       └── __init__.py     # Ascend 方言扩展（如 Cube/Vector 双核原语）
└── backend/
    └── target.py           # determine_target()：统一 target 解析入口
```

在`tilelang/backend/target.py`中，`determine_target()`将用户传入的字符串或字典解析为 TVM 的`Target`对象[8]：

```text
# tilelang/backend/target.py
from tilelang.backend.target import determine_target

# 解析为 CUDA Target
target_cuda = determine_target({"kind": "cuda", "arch": "sm_90"}, return_object=True)
# → Target("cuda", host="llvm", arch="sm_90")

# 解析为 Ascend Target
target_ascend = determine_target("ascend", return_object=True)
# → Target("ascend", host="llvm")
```

解析后的`Target`对象携带`target.kind.name`属性（值为`"cuda"`或`"ascend"`），编译器据此通过 Backend Registry 路由到对应的 codegen 实现。host codegen 的分发逻辑在`tilelang/engine/lower.py`中可见[11]：

```text
# tilelang/engine/lower.py (host_codegen 简化片段)
def host_codegen(host_mod, target_host):
    host_mod = BindTarget(target_host)(host_mod)
    host_mod = LowerTVMBuiltin()(host_mod)
    host_mod = LowerCustomDatatypes()(host_mod)
    host_mod = LowerIntrin()(host_mod)

    # Backend Registry 分发：根据 target_host.kind.name 选择构建函数
    if target_host.kind.name == "llvm":
        host_mod = tvm.ffi.get_global_func("target.build.llvm")(host_mod, target_host)
    elif target_host.kind.name == "c":
        host_mod = tvm.ffi.get_global_func("target.build.tilelang_c")(host_mod, target_host)
    else:
        raise ValueError(f"Target host {target_host.kind.name} is not supported")
    return host_mod
```

device codegen 的分发机制与此类似，但通过`target.build.tilelang_cuda`或`target.build.tilelang_ascend`等全局函数调用[12]。Backend Registry 将这些全局函数注册到 TVM 的 FFI 系统中，实现插件式扩展。

### 3.3.3 从 TIRX 到硬件代码：IR Lowering 的五阶段管线

TileLang 论文中描述的编译流程可归纳为五个阶段[2]：

1.**Parse**：Python AST 解析为 TileLang AST，识别`@T.prim_func`装饰的 kernel

2.**AST → TIRX IR**：TileLang AST 转换为 TVM TIRX（Tensor IR Extended）表示，保留 tile 和 layout 语义

3.**Tile Scheduler + Layout Inference**：- 自动推断 tile 配置（tile size、memory scope 分配）

- 线程绑定（thread binding）通过 top-down 类型推断建立
- 内存布局函数推断（swizzle、padding 以规避 bank conflict）
- 流水线推断（异步 copy stage、mbarrier 序列插入等）

4.**Pass Optimization**：循环融合、尾处理、常量传播、MMA lowering 等

5.**Backend CodeGen**：通过 Backend Registry 分发到具体后端，生成 CUDA C++ 或 Ascend C 源码

IR Lower Trace 工具可完整观察上述管线[13]。设置环境变量`TL_LOWER_TRACE=html`后，编译器会在`TL_LOWER_TRACE_DIR`下生成如下目录结构：

```text
TL_LOWER_TRACE_DIR/
└── my_script/
    ├── report.html              # 可视化 diff 报告
    ├── codegen.cpp              # 最终生成的 device 代码（可编辑后重新注入编译）
    └── .run_records/
        └── run_20261007_120000/
            ├── pipeline_c/      # Phase 1: C 语言层面的 lowering
            │   ├── 00_BindTarget_before.tir
            │   ├── 00_BindTarget_after.tir
            │   └── ...
            ├── phase2_optimize/ # Phase 2: 目标设备优化
            │   └── ...
            └── codegen/         # CodeGen 阶段
                ├── 42_codegen_before.tir
                └── 42_codegen_after.cpp
```

### 3.4 实例：同一份 TileLang 源码，经不同 target 编译

以下是一个简化的 FlashAttention tile 计算示例，展示同一份源码如何经不同 target 生成不同硬件代码（基于 TileLang 官方示例风格）[5]：

```text
import tilelang as tl
import tilelang.language as T

@T.prim_func
def flash_attention_tile(
    Q: T.Buffer((B, H, N, D), "float16"),
    K: T.Buffer((B, H, N, D), "float16"),
    V: T.Buffer((B, H, N, D), "float16"),
    O: T.Buffer((B, H, N, D), "float16"),
):
    with T.Kernel(B * H, threads=128) as bx:
        # 分配 shared memory / UB
        q_tile = T.alloc_fragment((64, D), "float16", scope="shared")
        k_tile = T.alloc_fragment((64, D), "float16", scope="shared")
        v_tile = T.alloc_fragment((64, D), "float16", scope="shared")

        # Tile-level copy：自动推断线程绑定和向量化
        T.copy(Q[bx, :, :], q_tile)

        # Tile-level GEMM：自动匹配硬件指令（WGMMA / Cube Core / MFMA）
        acc = T.alloc_fragment((64, 64), "float32", scope="local")
        T.gemm(q_tile, k_tile, acc, trans_B=True)

        # Softmax 规约
        m = T.max(acc, axis=1)
        acc_exp = T.exp(acc - m)
        l = T.sum(acc_exp, axis=1)

        # 输出写回
        T.copy(acc_exp / l, O[bx, :, :])

# --- 编译到 NVIDIA GPU ---
target_cuda = {"kind": "cuda", "arch": "sm_90"}
kernel_cuda = tl.compile(flash_attention_tile, target=target_cuda)
# → 生成 CUDA C++，调用 WGMMA (SM90) 或 TMA 异步拷贝

# --- 编译到昇腾 950 NPU ---
target_ascend = {"kind": "ascend"}
kernel_ascend = tl.compile(flash_attention_tile, target=target_ascend)
# → 生成 Ascend C，调用 Cube Core 矩阵乘 + Vector Core 规约
```

关键观察：

- `T.copy`、`T.gemm`等高级原语在 CUDA backend 下展开为`cp.async`+`wgmma.mma_async`序列；在 Ascend backend 下展开为`DataCopy`+`CubeCore`指令序列
- `scope="shared"`在 CUDA 下映射到`__shared__`内存；在 Ascend 下映射到`Unified Buffer (UB)`
- 线程数`threads=128`在 CUDA 下映射为 128 个 SIMT 线程；在 Ascend 下经 scheduler 重新映射为 Vector Core 的 SIMD lane 配置

这即是 DeepSeek 所说的”一一对应”：同一份`flash_attention_tile`函数体，不修改任何源码，仅更换`target`参数，即可生成两个平台的可执行 kernel。

### 3.5 两条路线的关系：互补，非替代

| 维度 | 路线 A：Vendor Library | 路线 B：TileLang JIT |
| --- | --- | --- |
| 触发时机 | 运行时（Runtime） | 编译时（Compile-time），首次执行或 cache miss 时 |
| 代码形态 | 预编译二进制（.so） | TileLang Python 源码（文本） |
| 是否经过 TileLang | 否，框架直接 dlsym 调用 | 是，完整 lower → codegen → compile 管线 |
| 性能 | 最优（手写优化十年） | 接近最优（通常 90-99%， hardest case 可能更低） |
| 覆盖范围 | 有限（头部通用 case） | 理论上无限（任何可表达为 TileLang 的算子） |
| 维护主体 | 芯片厂商（NVIDIA / 华为） | 社区 + 模型厂商（DeepSeek 等） |
| 典型代表 | cuBLAS, cuDNN, CANN | TileKernels, FlashMLA, DeepGEMM |

**核心结论：**PyTorch 的调度策略是”先 A 后 B”——ATen 先查询 vendor 库是否存在优化实现，存在则直接调用（路线 A）；不存在或算子为自定义融合模式，则 fallback 到`torch.compile`，经 TileLang 现场编译生成（路线 B）。TileLang 不取代 cuBLAS 或 CANN，而是在厂商库覆盖不到的**长尾地带**，提供了一条源码可跨硬件复用的新路线。DeepSeek 开源的六个组件全部落在路线 B。

### 四、梁文峰的三点论述：CUDA 护城河的瓦解

在 2026 年初的一次内部会议中，梁文峰对国产芯片替代的历史性机遇做了系统阐述[9]。其论述与 TileLang 的技术路线高度吻合，可以从三个层面理解：

### 4.1 AI 辅助编程降低了生态构建门槛

> “现在有了 AI，我要建立起这个生态比以前容易很多了，因为 AI 可以写代码。我可以用 AI 来构建这个生态，就可以把跟英伟达一模一样的生态全部都写一遍。”

— 梁文峰，2026

TileLang 的 Pythonic 语法降低了手写 kernel 的门槛，而 AI 辅助编程进一步加速了算子库的构建过程。DeepSeek 能够在短时间内完成昇腾 950 的完整算子适配，与此密切相关。

### 4.2 TileLang 等高级语言提供了跨硬件抽象

> “我们家出了一个技术，叫 TileLang，是一种高级语言。用这个高级语言来写 CUDA 的算子，可以很快地把英伟达的整套生态全部都写一遍……这个技术路线看起来是没有什么障碍的。”

— 梁文峰，2026

这正是 TileLang 论文的核心贡献：通过将 dataflow 与 scheduling space 解耦，TileLang 提供了一层与硬件无关的算子描述语言。同一套算子源码，只需更换 target backend 即可适配不同硬件，而无需用 CUDA C 和 Ascend C 分别重写。

### 4.3 计算卡市场超越游戏卡，专用芯片不再绑定 CUDA

> “CUDA 是兼容游戏卡的。以前因为 AI 计算是一个很小的领域，比游戏卡的市场要小，所以这样是合理的。但是现在计算卡的市场已经比游戏卡更大了，就没有理由这两个还需要耦合起来。”

— 梁文峰，2026

CUDA 的设计继承了游戏 GPU 的遗产（SIMT 线程模型、显存层次结构等），而现代 AI 加速器（包括 NVIDIA 的 Blackwell 和华为的昇腾 950）正在向更专用的架构演进。在这种背景下，专用芯片的设计本身就考虑了如何建立独立于 CUDA 的软件生态——TileLang 恰好充当了这一层跨硬件的抽象接口。

### 五、对各方参与者的结构性影响

### 5.1 芯片厂商：从”写算子”到”写 Backend”

旧范式下，芯片厂商需要维护庞大的算子适配团队，逐算子追赶框架和模型的新需求。新范式下，核心工作收敛为：

1. 实现高质量的 TileLang Backend（IR lowering、指令调度、内存映射）
2. 将 Backend 推进上游（合入 tile-ai/tilelang 主仓库）
3. 维护厂商闭源库（cuBLAS/CANN）以覆盖头部通用 case

Backend 一旦进入上游，社区和模型厂商写的每一个 TileLang 算子都自动在该硬件上可运行。边际成本从”无限增长的适配劳动”变为”一次性基础设施投入 + 社区乘数摊销”。

但这也带来新的竞争维度：**上游治理权**。如果 Backend 无法合入上游，fork 的维护成本将吞噬所有收益。寒武纪加入 PyTorch 基金会理事会、昇腾运营 Ascend for PyTorch 社区（外部贡献占比过半）[10]，本质上都是在争夺这张”自动获得社区语料”的门票。

### 5.2 模型厂商：算子资产的跨硬件保值

在 CUDA C / Ascend C 时代，模型厂商为 NVIDIA 写的 kernel 是平台锁定资产——换到昇腾就需从零重写。Cube/Vector 双核、UB 内存、异步 DMA 等底层差异决定了这不是翻译，而是重构。

TileLang 范式下，同一份算子源码：

- 用`target="cuda"`编译，生成 CUDA kernel 在 NVIDIA GPU 上执行
- 用`target="ascend"`编译，生成 Ascend kernel 在昇腾 NPU 上执行
- 未来新增 backend 后，同一份代码可扩展至更多平台

DeepSeek 将资产写在 TileLang 层，本质上是做**算子资产的跨硬件保值**。开源则是将”私有维护成本”转化为”社区摊销收益”——同时释放”模型在哪都能跑”的市场信号。

### 5.3 独立开发者：公共语料层的贡献激励

TileLang 源码是硬件无关的公共语料。开发者为 TileLang 生态贡献算子，逻辑与为 CUDA 生态贡献开源 kernel 同构，但中立性更强：今天写昇腾能跑，明天寒武纪 backend 成熟，同一份代码自动多一个平台可用。

当然，”硬件绑定的调优劳动”（per-backend 的 schedule 覆盖）仍然存在，但这部分仅限于配置层，而非源码重写层。DeepSeek 官方表示已为昇腾 950 写了针对性的 schedule 覆盖，包括 Cube/Vector 核的自动分离、DMA 异步流水等。

### 六、局限与边界

- **TileLang 不取代 cuBLAS/CANN。**厂商闭源库在通用 GEMM、Conv 等头部 case 上仍是性能天花板。TileLang 覆盖的是”长尾自定义算子”——新模型结构、新融合模式、cuBLAS 不支持的变体 shape。
- **hardest kernel 仍需手写。**当 TileLang 的调度空间无法表达某些特殊优化（如极致的 warp specialization、特定的内存 bank conflict 规避）时，仍需退回手写 CUDA C / Ascend C。
- **“接近硬件上限”是官方口径。**真实竞争力还需考虑整机功耗、互联稳定性、128 卡超节点的实际利用率、产能和良率决定的 TCO。 -**非 AI 负载适用性有限。**Tile 抽象擅长规则张量并行，但对 FP64 科学计算、不规则 gather/scatter、图遍历等负载收益有限。CUDA 在 HPC 领域二十年的库积累不会因 DSL 出现而重写。
- **生态碎片化风险。**如果各厂商维护独立的 backend fork，反而削弱标准化。DeepSeek 的”一一对应”策略——严格保持 NVIDIA 版和昇腾版接口一致——是在主动收敛接口、降低开发者心智成本。

### 七、结语

DeepSeek 开源 TileLang@Ascend 组件的本质，是在 AI 芯片软件栈中增加了一个**跨硬件的算子描述层**。

底层事实没有改变：NVIDIA 的 PTX/SASS 和昇腾的 PTO ISA 仍然互不相通，cuBLAS 和 CANN 仍然是各自平台的性能天花板。改变的是**算子资产的归属权**——从”用 CUDA C 写就绑死 NVIDIA，用 Ascend C 写就绑死昇腾”，变成了”用 TileLang 写，换 target 即可编译到不同硬件”。

对芯片厂商，竞争规则从”有多少个兼容 CUDA 的 API”变成了”backend 有没有进入上游、能不能吃到社区语料”。对模型厂商，算子资产从”一次性消耗品”变成了”可复用的基础设施”。对整个生态，”国产 AI 芯片能不能跑前沿模型”第一次从立场争论变成了可下载、可复现、可 benchmark 的工程命题。

正如梁文峰所言：”未来一年之内，我们能够看到有一个事情被验证：国产芯片的生态完全没有问题。”[9]这次开源，是用代码而不仅是宣言，来验证这一判断。
