## 1、 **引言**

## 1.1 目的与范围

本规范旨在定义和阐述 **“上下文工程”（Context Engineering）** 的核心概念、构成要素、设计原则和实施流程。其主要目的是为产品经理、AI工程师和开发人员提供一套系统化的方法论，用于设计、构建和优化基于大型语言模型（LLM）的应用程序，确保其具备更高的可靠性、可扩展性和性能。

本规范适用于所有需要与LLM进行复杂交互的应用场景，特别是涉及多轮对话、外部知识检索、工具调用和个性化服务的智能体（Agent）类产品。

## 1.2. 目标读者

**v** **产品经理** ： 理解如何设计功能更强大、体验更连贯的AI产品。

**v** **AI工程师/算法工程师** ： 学习如何构建高效、稳定的LLM调用系统。

**v** **软件开发工程师** ： 了解如何将LLM集成到现有业务系统和工作流中。

## 1.3. 从“提示工程”到“上下文工程”的演进

传统的 **提示工程（Prompt Engineering）** 专注于优化单一、静态的文本指令，以期在单次交互中获得最佳结果。这是一种“手工艺式”的优化，在处理需要多轮对话、外部知识和工具调用的复杂任务时，其局限性日益凸显。

**上下文工程（Context Engineering）** 是其必然的演进。它不再局限于一个静态的提示，而是将其视为一门设计和构建动态系统的科学。该系统负责在LLM执行任务的每一步，动态地、智能地组合所有必要信息，填充其“上下文窗口”（Context Window）。这标志着LLM应用开发从“提示的艺术”迈向了“系统的科学”。

正如 Andrej Karpathy 所说，大语言模型（LLM）就像一种新型操作系统。LLM 是“CPU”，而它的上下文窗口就像“RAM”，是模型的工作记忆。正如 RAM 容量有限，上下文窗口也只能容纳有限的信息。就像操作系统需要精心管理 CPU 的 RAM 一样，“上下文工程”扮演类似角色。Karpathy 总结得很好：

*核心观点 (引用自 Andrej Karpathy): “在每一个工业级的LLM应用中，上下文工程都是一门精巧的艺术和科学，旨在用恰到好处的信息填充上下文窗口以完成下一步任务。”*

*[Context engineering is the] ”…delicate art and science of filling the context window with just the right information for the next step.”*

**根本原因** ：模型能力稳步提升，又不够强大到不需要工程协助解决不足的情况下的一种情况？现阶段必须，未来也有可能动态变化的一种现象。

## 2、 **核心概念：什么是上下文工程？**

## 2.1. 定义

上下文工程（Context Engineering） 是指设计、构建并优化一个动态系统，该系统能够在正确的时间，以正确的格式，向大型语言模型提供正确的信息和工具，从而使其高效、可靠地完成指定任务。

![](https://pic4.zhimg.com/v2-4570db4dcdec65bbc09433ea08ee9313_1440w.jpg)

## 2.2. 核心特征

**v** **是一个系统，而非一个字符串** ： 上下文是运行在LLM调用之前的软件系统的输出，而非一个简单的静态模板。

**v** **动态性：** 上下文是根据当前任务即时生成的。对于一个请求，它可能包含日历数据；对于另一个请求，则可能包含邮件内容或数据库查询结果。

**v** **信息与能力的集合：** 它不仅提供知识（通过检索增强生成RAG等），还提供能力（通过工具定义）。

**v** **效率与性能导向：** 精心设计的上下文能用最少的Token（成本）实现最佳的模型性能（效果），避免因信息过多或无关导致性能下降。

## 2.3 同提示词工程对比总结

| 特征 | 提示工程 (Prompt Engineering) | 上下文工程 (Context Engineering) |
| --- | --- | --- |
| 主要目标 | 从模型中“引”出一段特定响应 | 构建一个可靠、可扩展、有状态的完整应用 |
| 核心活动 | 手工雕琢静态文本字符串 | 设计动态拼装上下文的系统 |
| 隐喻比喻 | 像念咒语或下达一次性指令 | 像调用通用函数的 API、像剧本编排，也像操作系统管理 RAM |
| 覆盖范围 | 最终发给模型的那一条指令 | 整条流水线：指令、状态、检索数据、工具链与输出格式 |
| 交互性质 | 主要是单轮、无状态的问答 | 天然多轮、有状态且持续演进 |
| 关键技能 | 创意写作 + 深度理解模型特性 | 系统设计 + 信息检索 + 数据工程 + 持续评估 |

## 3、 **上下文的核心构成要素**

一个完整的上下文窗口由多种信息组件构成，这些组件共同为LLM执行任务提供必要的环境。我们将这些组件归纳为以下五大类：

![](https://picx.zhimg.com/v2-4da5801acb199407360add6b364879cb_r.jpg)

**但必须注意，这5类指令主要指类型，在实际拼接时，可能会有交叉，比如工具定义常单独拼接，工具实际响应则和记忆模块一起拼接，作为记忆的一部分，格式化/结构化上下文有时可能作为作为指令上下文约束的一部分，而指令上下文中，系统指令一般单独拼接，用户输入则可能和记忆模块一起拼接！！**

## 3.1. 指令性上下文

### 3.1.1 概述

指导LLM行为的核心框架，是其行动的“宪法”。

**v** **系统提示 (System Prompt):** 设定AI的角色、高级目标、行为准则、沟通风格和核心约束。

**v** **用户输入/查询 (User Input/Query):** 用户当前提出的直接问题或命令，是任务的直接触发点。

**v** **少样本示例 (Few-shot Examples):** 提供具体的“输入-输出”范例，以非指令的方式引导模型遵循特定的格式或推理模式。

### 3.1.2 说明

系统提示作为全局性指令，一般可以单独作为一个模块，而其他组件组合后，拼接形成用户上下文，如：

[

{“role”: “system”, “content”: “系统指令说明”},

{“role”: “user”, “content”: “context engineering其它组件拼接组合”}

]

## 3.2. 时序/状态上下文

### 3.2.1 概述

使AI能够跨越多轮交互保持连贯性和记忆。

**v** **短期记忆 (Short-term Memory / Chat History):** 记录当前对话的直接历史，用于理解指代关系和对话逻辑。通常有容量限制。

**v** **长期记忆 (Long-term Memory):** 跨会话持久化存储关键信息，如用户偏好、历史摘要等。通常通过外部数据库（如向量数据库）实现，使AI具备“记性”和个性化能力。

**v** **全局状态/暂存区 (Global State / Scratchpad):** AI在执行多步骤任务时的“草稿纸”，用于记录中间思考、计划或计算结果，避免污染主对话历史。

### 3.2.2 说明

**要点1** ：记忆模块对于提供个性化智能体能力至关重要，针对个体长期服务的记录可考虑用单独的数据库存入，用户使用时通过工具调用获取对应记忆，拼接到上下文中对应部位，引导大模型提供个性化服务；

**要点2** ：记忆可分为不同类型，针对短期记忆中新增部分，涉及用户画像部分的内容，可考虑通过压缩总结，汇入长期记忆中；

## 3.3. 外部知识上下文

连接LLM与外部世界，为其提供事实依据，减少“幻觉”。

**v** **检索到的信息 (Retrieved Information - RAG):** 通过从外部知识库（如公司文档、数据库、API、网页）动态检索与当前任务最相关的信息，并注入到上下文中。

## 3.4. 工具驱动上下文

赋予AI与外部世界交互并执行操作的能力。

**v** **工具定义/模式 (Tool Definitions/Schemas):** 向LLM清晰描述可用工具的名称、功能、输入参数和预期输出格式。

**v** **工具响应 (Responses from Tools):** 工具执行后返回的结果（如API的JSON响应、数据库查询结果），这些结果被反馈到上下文中，作为LLM下一步推理的依据。

## 3.5. 格式化/结构化上下文

### 3.5.1 概述

约束LLM的输入输出格式，以提高可靠性和机器可读性。

**v** **结构化输出模式 (Structured Output Schemas):** 定义LLM响应必须遵循的特定格式，如强制其输出一个符合特定JSON Schema的对象。

**v** **作为输入的结构化数据 (Structured Data as Input):** 以紧凑、结构化的格式（如JSON、XML）向模型提供信息，比非结构化文本更高效、更易解析。

## 4、 **上下文工程的设计和管理**

## 4.1 上下文工程的设计参考原则

### 4.1.1 原则一：明确性与精确性

指令必须是无歧义的、具体的。避免使用模糊的词汇。例如，不说“处理退货”，而说“根据订单号ORD-XXXX，验证其是否在30天退货期内，并为符合条件的商品启动退货流程”。

### 4.1.2 原则二：相关性与简洁性

只提供完成当前任务所必需的信息。过多的、无关的信息会增加Token成本，并可能干扰模型的注意力，导致性能下降（“Lost in the Middle”现象）。应积极采用上下文压缩、摘要和剪枝技术。

### 4.1.3 原则三：动态性与适应性

上下文应根据任务的每一步动态构建。一个好的系统能够判断何时需要检索知识，何时需要调用工具，何时需要回顾历史对话，并智能地组合它们。

### 4.1.4 原则四：结构化与可靠性

尽可能使用结构化格式（如JSON、XML、Markdown）来传递数据和约束输出。这不仅能节约Token，还能确保输出的格式稳定，便于后续的程序化处理，降低解析错误率。

### 4.1.5 原则五：模块化与关注点分离

将不同类型的上下文视为独立的“块”（Blocks），如角色块（Persona Block）、记忆块（Memory Block）、知识块（Knowledge Block）。这种模块化设计使得上下文的管理、更新和调试更加清晰和高效。

## 4.2 上下文工管理原则

然而，随着任务和对话的持续进行，导致上下文窗口迅速膨胀。这会带来诸多问题：超出上下文窗口限制、增加成本/延迟、降低系统整体性能。Drew Breunig 详细列举了长上下文可能导致的具体问题：

**v** **上下文污染（Context Poisoning）** ：幻觉信息进入上下文；

**v** **上下文干扰（Context Distraction）** ：上下文信息过多，干扰模型训练；

**v** **上下文混淆（Context Confusion）** ：无关上下文影响回答；

**v** **上下文冲突（Context Clash）** ：上下文内部信息相互矛盾。

为减轻过载的上下文对模型性能的干扰，现有常见上下文方法归为四类：

**写入（Write）、选择（Select）、压缩（Compress）和隔离（Isolate）**

### 4.2.1 写入上下文

将内容繁多的各类上下文保存到数据库或文件内，以便系统需要时写入和读取。

![](https://pic4.zhimg.com/v2-86752f534305f66e2df7e77a64757051_1440w.jpg)

### 4.2.2 选择上下文

选择上下文是指将相关信息【记忆、工具、外部知识等】拉入上下文窗口，以帮助智能体完成任务。可借助检索工具，只检索必要信息融入上下文，避免上下文长度过载。本部分是重要工程课题，对最终效果影响较大。

### 4.2.3 压缩上下文

压缩上下文是指仅保留完成任务所需的最少 token。同选择上下文类似，力图避免干扰信息过载，影响模型效果，常见方法包括上下文摘要和上下文修剪等。

### 4.2.4 隔离上下文

隔离上下文是指将上下文拆分，分配给多个子智能体，子智能体并行运行，拥有各自独立的上下文窗口，同时探索问题的不同方面。是更高阶的工程优化策略。

## **5、综合案例解析：AI客服助手**

本章节将使用您提供的详尽案例，并标注其如何对应上文定义的上下文组件。

## 5.1 场景描述

用户Alice的笔记本电脑无法开机，希望联系“量子科技商城”的客服进行退货。

## 5.2 上下文构建详解

最终发送给LLM的完整上下文结构如下：

```

**<!-- 1. 指令性上下文: 定义AI的角色、目标和行为准则 -->**

[系统提示]

# 角色与身份

你是"量子客服助手"，专业的电商客服AI助理...

... (此处省略详细内容)

[结束系统提示]

**<!-- 2. 时序/状态上下文 (长期记忆部分): 关于当前用户的持久化信息 -->**

[长期记忆]

{

"用户档案": {

"用户ID": "alice_001",

"姓名": "Alice",

...

},

...

}

[结束长期记忆]

**<!-- 3. 外部知识上下文 (RAG): 在对话早期检索到的相关知识 -->**

[检索知识库]

{

"知识内容": [

{

"主题": "电子产品退货政策",

...

},

...

]

}

**分析：**

1 & 6 组成了完整的指令性上下文，告诉AI它是什么，以及它现在需要做什么。

2 & 5 构成了完整的时序/状态上下文。长期记忆提供了用户背景，对话历史提供了即时语境和工具执行的历史。

3 是外部知识上下文，通过RAG检索，为AI决策提供了政策依据。

4 是工具驱动上下文，让AI知道自己可以调用哪些API来执行实际操作。

## 5.3 案例流程

**指令性上下文：**

系统指令和用户指令分离

**工具驱动上下文：**

Baseline version: 少量工具列表固化至系统指令中，传统function calling策略

Improved version: LLM动态从工具库中召回工具列表，更新到工具调用组件内，并进行选择调用

**外部知识上下文：**

Baseline version: 传统RAG路线，检索内容固定存入

Improved version: LLM自主决定当前是否执行检索及设定检索内容

**时序/状态上下文：**

Baseline version: 长期记忆为固定用户画像，短期记忆为近几轮对话，无记忆更新

Improved version: LLM自主决定记忆上下文更新，实时从数据库（如mem0）获取内容更新上下文，自主决定短期记忆何时更新至长期记忆

**格式/结构化上下文：**

主要为指导原则，用清晰的标识符将不同上下文组件进行区分，同时每个组件内的子组件进行划分，xml tag诗歌很好的选择

关于输出约束，可清晰指导大模型输出样式，根据实际情况放入系统指令或用户指令中均可。

## 6.2 术语表

**LLM (Large Language Model):** 大型语言模型，如GPT系列、Gemini、Llama等。

**Context Window:** LLM单次处理中能够接收的最大Token数量。

**RAG (Retrieval-Augmented Generation):** 检索增强生成。一种通过从外部知识库检索信息来增强LLM生成内容的技术。

**Agent (智能体):** 一个具备感知、思考、决策和行动能力的AI系统，通常通过上下文工程实现。

**Token:** LLM处理文本的基本单位，可以是一个词、一个字符或一个子词。

**Few-shot Learning:** 通过在提示中提供少量示例来引导模型学习任务模式。

**JSON Schema:** 一种用于定义JSON数据结构的规范。
