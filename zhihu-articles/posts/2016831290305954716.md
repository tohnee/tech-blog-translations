### 1. 引言：一次迁移引发的性能悬崖

### 1.1 问题场景

在前面的系列文章中，我们从 Ray Core 的 Actor 模型、GCS 全局状态、Object Store 共享内存，一路剖析到 Ray Data 的查询优化器、流式执行引擎、背压机制，再到 Ray Train 的分布式训练编排。理论上，这套架构应该让分布式训练变得”开箱即用”。

但真实世界总是比设计文档复杂。一个常见的迁移场景是：

```text
# 迁移前：原生 PyTorch + DeepSpeed
# 训练时间：20-30 min，GPU 利用率 > 90%
torchrun --nproc_per_node=4 train.py

# 迁移后：Ray + PyTorch + DeepSpeed
# 训练时间：30-40 min，GPU 利用率波动剧烈
trainer = TorchTrainer(train_func, scaling_config=ScalingConfig(num_workers=4, use_gpu=True))
trainer.fit()
```

**33%-50% 的性能回归**，足以让任何工程团队质疑迁移的合理性。

### 1.2 为什么需要这篇文章

性能回归的根因并非 Ray 框架本身的缺陷，而是**分布式执行模型与原生单进程模型之间的结构性差异**。理解这些差异，是在享受 Ray 的弹性调度、容错恢复、统一 Data/Train/Serve 生态等红利的同时，不丢失训练性能的关键。

### 1.3 全景开销分析

| # | 开销来源 | 影响程度 | 修复难度 |
| --- | --- | --- | --- |
| 1 | GPU 资源竞争（数据预处理 vs 训练） | 高 | 中 |
| 2 | Ray Data 摄入管线多阶段开销 | 高 | 中 |
| 3 | Worker 启动与进程组初始化 | 中 | 低 |
| 4 | Object Store 序列化/反序列化 | 中 | 中 |
| 5 | 数据格式转换冗余 | 低-中 | 低 |
| 6 | Checkpoint I/O 开销 | 低 | 低 |

接下来我们逐一深入源码，拆解每一个开销来源。

### 2. 架构对比：原生 PyTorch vs Ray 的执行路径差异

### 2.1 原生 PyTorch+DeepSpeed 的执行路径

```text
┌──────────────────────────────────────────────────┐
│              单进程（GPU 独占）                      │
│                                                    │
│  DataLoader(pin_memory=True, num_workers=4)        │
│       ↓ 共享内存 / pin memory DMA                   │
│  GPU 训练 (DeepSpeed Engine)                        │
│       ↓ NCCL AllReduce（进程间直连）                  │
│  Checkpoint → 本地磁盘                               │
│                                                    │
│  特点：                                             │
│  ✓ 进程独占 GPU，零竞争                              │
│  ✓ DataLoader 在同一进程内，零序列化                   │
│  ✓ NCCL 通过 torch.distributed 直接初始化             │
│  ✓ 数据路径：磁盘 → 共享内存 → pin_memory → GPU       │
└──────────────────────────────────────────────────┘
```

### 2.2 Ray+PyTorch+DeepSpeed 的执行路径

```text
┌────────────────────────────────────────────────────────────┐
│                    Ray 分布式环境                              │
│                                                              │
│  ┌──────────────┐    ┌──────────────────────────────────┐   │
│  │ Ray Data      │    │ Ray Train Workers (4 × Actor)    │   │
│  │ Actors        │    │                                  │   │
│  │ ┌──────────┐  │    │ ┌────────────┐ ┌────────────┐   │   │
│  │ │ Read     │──┼────┼→│ Worker 0   │ │ Worker 1   │   │   │
│  │ │ (S3/磁盘) │  │    │ │ DeepSpeed  │ │ DeepSpeed  │   │   │
│  │ └──────────┘  │    │ │ Engine     │ │ Engine     │   │   │
│  │ ┌──────────┐  │    │ └────────────┘ └────────────┘   │   │
│  │ │ Preproc  │  │    │ ┌────────────┐ ┌────────────┐   │   │
│  │ │ (GPU?)   │  │    │ │ Worker 2   │ │ Worker 3   │   │   │
│  │ └──────────┘  │    │ │ DeepSpeed  │ │ DeepSpeed  │   │   │
│  └──────────────┘    │ │ Engine     │ │ Engine     │   │   │
│         ↑             │ └────────────┘ └────────────┘   │   │
│    Object Store       │                                  │   │
│    (Arrow格式)         │   ← streaming_split →            │   │
│         ↓             │   ← NCCL via env:// →            │   │
│    SplitCoordinator   │   ← Checkpoint → S3/磁盘 →       │   │
│    (协调器 Actor)      └──────────────────────────────────┘   │
└────────────────────────────────────────────────────────────┘
```

### 2.3 关键差异对照表

| 维度 | 原生 PyTorch | Ray + PyTorch | 开销差异 |
| --- | --- | --- | --- |
| 进程启动 | torch.mp.spawn (~0.5s) | Ray Actor 调度 (~3-8s) | +2.5-7.5s |
| NCCL 初始化 | 直接 init_process_group (~1-2s) | 通过 Ray env:// (~2-5s) | +1-3s |
| 数据就绪 | 共享内存，即时可用 | streaming_split + 协调器 (~2-5s) | +2-5s |
| 数据传输 | 进程内零拷贝 | Object Store → ray.get() → 反序列化 | +ms级每batch |
| GPU 访问 | 独占，零竞争 | 可能与 Data Actors 共享 | 关键瓶颈 |
| 数据管线 | DataLoader 2 阶段 | BatchIterator 6 阶段 | +管线延迟 |

**核心洞察**：原生 PyTorch 的优势在于**一切都在同一进程地址空间内**——数据加载、预处理、训练共享同一块 GPU 显存，无需跨进程通信。Ray 的分布式架构引入了进程间隔离（更安全、更弹性），但代价是每一层交互都增加了序列化、调度、网络传输的开销。

### 3. 六大根因深度剖析

### 3.1 根因一：GPU 资源竞争（最可能的首要瓶颈）

### 3.1.1 竞争的本质

当数据预处理需要 GPU（如图像解码、Tokenization 加速、特征工程），Ray Data 的 Actor 和 Ray Train 的 Worker **争夺同一个 GPU 资源池**。

```text
# ❌ 典型的资源竞争配置
train_ds = ray.data.read_parquet("s3://data/train/")
train_ds = train_ds.map_batches(gpu_preprocess, num_gpus=1)  # ← 需要 GPU

trainer = TorchTrainer(
    train_func,
    scaling_config=ScalingConfig(num_workers=4, use_gpu=True),  # ← 4 GPU
    datasets={"train": train_ds},
)
# 问题：4 张 GPU 全部被 Train Worker 预留，Data Actor 拿不到 GPU！
```

### 3.1.2 源码级分析：资源排斥机制

Ray Train 通过 `DataConfig.configure()` 中的 `exclude_resources` 机制，将训练 Worker 占用的 GPU 排除出 Ray Data 的可用资源池：

```text
# 源码路径：python/ray/train/_internal/data_config.py L126-135

def configure(self, datasets, world_size, worker_handles, worker_node_ids, **kwargs):
    from ray.data._internal.execution.interfaces.execution_options import (
        ExecutionResources,
    )
    # ...
    for name, ds in datasets.items():
        execution_options = self._get_execution_options(name)

        if execution_options.is_resource_limits_default():
            # 关键逻辑：将训练预留的 CPU/GPU 加入排除列表
            execution_options.exclude_resources = (
                execution_options.exclude_resources.add(
                    ExecutionResources(
                        cpu=self._num_train_cpus,   # 训练占用的 CPU
                        gpu=self._num_train_gpus    # 训练占用的 GPU
                    )
                )
            )
```

**这意味着**：如果集群有 4 张 GPU，4 个 Train Worker 各占 1 张，那么 Ray Data 的 `exclude_resources` 会排除全部 4 张 GPU。此时如果 `map_batches(fn, num_gpus=1)`，Data Actor **将无法获得 GPU 资源**，任务会排队等待（饥饿），或者降级到 CPU 执行。

### 3.1.3 为什么原生 PyTorch 没有这个问题

```text
# 原生 PyTorch：单进程独占模式
def train_worker(rank, world_size):
    torch.cuda.set_device(rank)  # 独占 GPU[rank]
    
    # DataLoader 在同一进程内，共享 GPU[rank]
    # 预处理和训练串行执行，不存在并发竞争
    dataloader = DataLoader(dataset, num_workers=4, pin_memory=True)
    
    for batch in dataloader:
        batch = batch.cuda()  # 同一块 GPU，零竞争
        model(batch)
```

**对比**：原生 PyTorch 中，数据预处理的 GPU 操作和训练的 GPU 操作在同一进程内**时间分片**执行（串行），而非**空间分片**（并行竞争）。Ray 的 Actor 模型强制将二者拆分到不同进程，引入了资源竞争。

### 3.2 根因二：Ray Data 摄入管线多阶段开销

### 3.2.1 六阶段管线架构

Ray Data 使用一个**六阶段异步管线**向训练 Worker 交付 Batch 数据。这个管线的设计初衷是支持 TB 级数据的分布式流式处理，但对于中小规模数据集，管线本身的开销可能**超过实际数据加载时间**。

```text
# 源码路径：python/ray/data/_internal/block_batching/iter_batches.py L31-65

class BatchIterator:
    """
    管线阶段：
    
    [用户线程] 训练 Batch 0
    - [Fetch线程] Batch 1 终态化 + 移入输出队列
            - [Worker线程1] Batch 2 格式化 + Collate
            - [Worker线程2] Batch 3 格式化 + Collate
            - [Raylet] Batches 4+5 预取到本地 Object Store
    
    实际步骤：
    1. 触发 Ray 本地预取（prefetch_batches 个 Block 的 ObjectRef）
    2. 解析引用（调用 ray.get()）
    3. Batch 切分/拼接，可选 shuffle
    4. 线程池格式化（默认 4 个线程）：Arrow → Pandas/NumPy/Torch
    5. 终态化（如 GPU 传输）
    6. 按序输出
    """
```

### 3.2.2 管线开销量化

| 阶段 | 原生 DataLoader | Ray Data BatchIterator | 差异原因 |
| --- | --- | --- | --- |
| 预取 | num_workers 进程并行读取 | prefetch_batches 个 Block 的 ObjectRef 解析 | IPC vs Actor 调度 |
| 序列化 | 共享内存，零序列化 | Arrow → Plasma → ray.get() → 反序列化 | 跨进程隔离的代价 |
| 格式转换 | pin_memory + DMA | Arrow → NumPy → Torch (多次拷贝) | 数据表示不一致 |
| Shuffle | Sampler 索引级 shuffle | shuffle_buffer_min_size Block 级 shuffle | 粒度不同 |
| 冷启动 | ~0.1s | ~2-5s (iter_time_to_first_batch_s) | 协调器初始化 |

### 3.2.3 冷启动惩罚的根源

Ray Data 的 `streaming_split()` 需要一个 `SplitCoordinator` 协调器 Actor 来管理多个 Worker 的数据分配：

```text
# 源码路径：python/ray/data/_internal/iterator/stream_split_iterator.py L34-54

@staticmethod
def create(base_dataset, n, locality_hints):
    # 创建协调器 Actor（需要 Actor 调度 + 初始化）
    coord_actor = SplitCoordinator.options(
        max_concurrency=n + 1,  # n 个消费者 + 1 个 shutdown 线程
        scheduling_strategy=NodeAffinitySchedulingStrategy(
            ray.get_runtime_context().get_node_id(), soft=False
        ),
    ).remote(base_dataset, n, locality_hints)
    
    return [StreamSplitDataIterator(base_dataset, coord_actor, i, n)
            for i in range(n)]
```

**每个 epoch 的首次迭代**都需要通过协调器同步所有 Worker（隐式屏障），这引入了额外的 RPC 延迟：

```text
# 源码路径：stream_split_iterator.py L72-106

def gen_blocks() -> Iterator[RefBundle]:
    # 阻塞等待：所有 Worker 必须同时到达屏障
    cur_epoch = ray.get(
        self._coord_actor.start_epoch.remote(self._output_split_idx)
    )
    # 首次 get：0 字节预取
    future = self._coord_actor.get.remote(cur_epoch, self._output_split_idx, 0)
    while True:
        block_ref_and_md = ray.get(future)
        if not block_ref_and_md:
            break
        # 流水线预取：在消费当前 Block 时，提前请求下一个
        future = self._coord_actor.get.remote(...)
        yield RefBundle(...)
```

**关键指标**：`iter_time_to_first_batch_s` 应 < 2s。如果显著超过，说明协调器初始化或首次 Block 读取存在瓶颈。

### 3.3 根因三：Worker 启动与进程组初始化

| 阶段 | 原生 PyTorch | Ray Train | 差异 |
| --- | --- | --- | --- |
| 进程创建 | torch.mp.spawn ~0.5s | Ray Actor 调度 ~3-8s | Actor 需要经过 GCS 注册、资源分配、进程 fork |
| NCCL 初始化 | 直接 init_process_group ~1-2s | 通过 Ray env:// 中转 ~2-5s | 需要先建立 Ray Worker 间的通信通道 |
| 数据就绪 | 共享内存立即可用 | streaming_split + 协调器 ~2-5s | 需要初始化协调器 Actor、建立 Block 分发管线 |
| 启动总计 | ~2-4s | ~7-18s | +5-14s |

Ray Train Worker 的启动过程涉及完整的 Actor 生命周期：

```text
# 源码路径：python/ray/train/torch/config.py L41-62

@dataclass
class TorchConfig(BackendConfig):
    backend: Optional[str] = None  # 默认 GPU 用 nccl, CPU 用 gloo
    init_method: str = "env"       # 通过环境变量初始化
    timeout_s: int = 1800          # 进程组操作超时 30 分钟

# 源码路径：python/ray/train/v2/torch/torch_trainer.py L188-207

def __init__(self, ...):
    torch_config = torch_config or TorchConfig()
    if not torch_config.backend:
        is_gpu_training = scaling_config and scaling_config.use_gpu
        torch_config.backend = "nccl" if is_gpu_training else "gloo"
    # ↑ GPU 训练自动选择 NCCL，但通过 Ray 的 env:// 中转
    #   比原生 torch.distributed 多一层间接
```

**影响评估**：对于 20-30 分钟的训练任务，7-18s 的启动开销占 ~1-1.5%，看似不大。但如果训练过程中有**每 epoch 重新初始化**的逻辑（如某些调参框架），启动开销会线性累积。

### 3.4 根因四：Object Store 序列化/反序列化

Ray Data 将中间 Block 存储在 **Object Store**（Arrow 格式的 Plasma 对象）中。训练 Worker 通过 `ray.get()` 获取 Block，涉及完整的序列化→IPC/网络传输→反序列化链路：

```text
数据流：
磁盘/S3 → [Read Actor] → Arrow Table → Plasma (Object Store)
                                              ↓ ray.get()
                                      [Train Worker] → 反序列化
                                              ↓
                                      Arrow → NumPy → Torch Tensor
                                              ↓
                                      .cuda() → GPU 显存
```

**对比原生 PyTorch**：

```text
数据流：
磁盘 → [DataLoader Worker] → 共享内存 (pin_memory)
                                    ↓ DMA
                              GPU 显存
```

原生路径只有 **2 次数据拷贝**（磁盘→内存, 内存→GPU），Ray 路径至少 **4 次**（磁盘→Arrow, Arrow→Plasma, Plasma→Python, Python→GPU）。

### 3.5 根因五：数据格式转换冗余

```text
# ❌ 常见的双重转换陷阱
ds = ds.map_batches(fn, batch_format="numpy")  # Arrow → NumPy
# 然后在训练循环中
for batch in ds.iter_torch_batches(batch_size=32):  # NumPy → Torch
    # Arrow → NumPy → Torch（两次转换，两次拷贝）
    pass

# ✅ 保持 Arrow 格式到最后一步
ds = ds.map_batches(fn, batch_format="pyarrow")  # 保持 Arrow
for batch in ds.iter_torch_batches(batch_size=32):  # Arrow → Torch（一次转换）
    pass
```

`iter_batches.py` 中的格式化阶段使用线程池进行数据转换：

```text
# 源码路径：iter_batches.py L26-28
DEFAULT_FORMAT_THREADPOOL_NUM_WORKERS = env_integer(
    "RAY_DATA_MAX_FORMAT_THREADPOOL_NUM_WORKERS", 4
)
# 默认 4 个线程执行格式转换
```

### 3.6 根因六：Checkpoint I/O 开销

DeepSpeed 的 Checkpoint 包含：优化器状态（ZeRO 分片）、模型参数（可能分片）、学习率调度器状态。通过 Ray Train 保存时，涉及跨 Worker 的分布式检查点写入：

```text
# 源码路径：python/ray/train/examples/deepspeed/deepspeed_torch_trainer.py L112-122

with TemporaryDirectory() as tmpdir:
    # 每个 Worker 保存自己的 checkpoint shard
    model.save_checkpoint(tmpdir)
    
    # 等待所有 Worker 完成（分布式屏障）
    torch.distributed.barrier()
    
    # 通过 Ray Train 上报 checkpoint（可能涉及 S3 上传）
    ray.train.report(
        metrics=eval_metric,
        checkpoint=Checkpoint.from_directory(tmpdir)
    )
```

**开销来源**：

- `model.save_checkpoint()` → 本地磁盘 I/O
- `torch.distributed.barrier()` → Worker 间同步等待
- `Checkpoint.from_directory()` → 目录打包 + 可能的 S3 上传

对于 ZeRO Stage 3，每个 Worker 只持有模型参数的 1/N，checkpoint 写入量相对较小。但 Stage 1⁄2 的优化器状态可能很大（与模型参数同等规模）。

**预取参数选择指南**：

| prefetch_batches | 适用场景 | 内存开销 |
| --- | --- | --- |
| 1（默认） | CPU 训练、小 batch | 低 |
| 2-4 | GPU 训练、中等 batch | 中 |
| 4-8 | 大规模 GPU 训练、数据密集模型 | 高 |

### 6. Phase 1：数据管线重构——解耦 GPU 预处理与训练

### 6.1 两阶段执行模式（推荐方案）

这是**影响最大的优化**。核心思想：将 GPU 预处理和 GPU 训练拆分为两个独立的 Ray 任务，彻底消除资源竞争。

```text

# === 阶段二：训练（全部 GPU 专注训练） ===
```

**收益**：训练阶段获得 100% GPU 分配，零竞争。预处理的一次性开销被摊销到多次训练迭代中。

### 6.2 原生 DataLoader 旁路方案

当数据集能够完全放入内存，且不需要 Ray Data 的分布式流式处理能力时，直接使用原生 PyTorch DataLoader 是**开销最低**的方案：

```text
def train_func(config):
    from torch.utils.data import DataLoader, TensorDataset
    from torch.utils.data.distributed import DistributedSampler
    
    # 直接从共享文件系统加载（绕过 Ray Data 管线）
    data = torch.load("/shared/preprocessed_train.pt")
    dataset = TensorDataset(data["inputs"], data["labels"])
    
    # 使用原生 DistributedSampler 进行数据分片
    sampler = DistributedSampler(
        dataset,
        num_replicas=ray.train.get_context().get_world_size(),
        rank=ray.train.get_context().get_world_rank(),
    )
    dataloader = DataLoader(
        dataset,
        batch_size=config["batch_size"],
        sampler=sampler,
        num_workers=4,          # DataLoader 子进程数
        pin_memory=True,        # 启用锁页内存，加速 CPU→GPU 传输
        persistent_workers=True, # 避免每 epoch 重建子进程
    )
    
    # DeepSpeed 初始化
    model, optimizer, _, scheduler = deepspeed.initialize(
        model=model, config=ds_config,
    )
    
    for epoch in range(config["num_epochs"]):
        sampler.set_epoch(epoch)  # 确保每 epoch shuffle 不同
        for batch in dataloader:
            batch = {k: v.cuda() for k, v in batch.items()}
            outputs = model(**batch)
            model.backward(outputs.loss)
            model.step()
```

| 数据在分布式存储（S3/GCS） | ✅ | ❌ |
| 需要流式 Shuffle | ✅ | ❌ |
| 数据完全放入内存 | ❌ | ✅ |
| GPU 预处理（已解耦） | 阶段一用 | ✅ 阶段二用 |
| 简单表格数据 | 均可 | ✅ 更轻量 |

### 7.1 自定义 DataConfig：GPU 感知资源限制

```text

from ray.train import DataConfig
from ray.data import ExecutionOptions

class GPUAwareDataConfig(DataConfig):
    """自定义 DataConfig：为 Ray Data 设置 Object Store 内存上限，
    防止数据管线占用过多内存影响训练。"""

    def __init__(self, **kwargs):
        exec_opts = ExecutionOptions(
            verbose_progress=False,
            resource_limits=ExecutionOptions.ResourceLimits(
                object_store_memory=2 * 1024**3,  # 限制 Ray Data 最多用 2GB Object Store
            ),
        )
        super().__init__(execution_options=exec_opts, **kwargs)
```

**为什么需要限制 Object Store**：DeepSpeed 的 ZeRO 优化器会在 GPU 显存和 CPU 内存之间移动参数/梯度/优化器状态。如果 Ray Data 的 Object Store 占用了大量 CPU 内存，可能触发 ZeRO offload 的 OOM。

### 7.2 DeepSpeed 专项调优

**ZeRO 阶段选型决策**：


### 7.3 利用流式管线重叠计算与通信

```text
def train_func(config):
    train_ds = ray.train.get_dataset_shard("train")

    for epoch in range(config["num_epochs"]):
        # iter_torch_batches 是惰性的——batch 在 GPU 训练时异步预取
        batch_iter = train_ds.iter_torch_batches(
            batch_size=config["batch_size"],
            prefetch_batches=8,  # 激进预取，确保 GPU 不空闲
            pin_memory=True,
        )

        for step, batch in enumerate(batch_iter):
            # ↓ 当 GPU 处理当前 batch 时，后台线程已经在预取下一批
            batch = {k: v.to(device) for k, v in batch.items()}
            outputs = model(**batch)
            model.backward(outputs.loss)
            model.step()
```

**流水线时序图**：

```text
时间 →  t0    t1    t2    t3    t4    t5
GPU:   [Train B0]  [Train B1]  [Train B2]  [Train B3]
Fetch:      [Fetch B1]  [Fetch B2]  [Fetch B3]  [Fetch B4]
Format:         [Fmt B2]  [Fmt B3]  [Fmt B4]  [Fmt B5]
Prefetch:           [Pre B3+B4]  [Pre B5+B6]  [Pre B7+B8]

当 prefetch_batches=2 时，任意时刻有 3 个 batch 在飞行中：
- 1 个在 GPU 上训练
- 1 个在 CPU 上格式化/collate
- 1 个在 Object Store 中预取
```

```text
 │    ├── 是 → 解耦预处理（Phase 1.1）
 │    │         先物化到存储，再训练
 │    └── 否 → CPU 预处理 map_batches(num_cpus=N)
 │
 ├── 训练数据是否放得进内存？
 │    ├── 是 → 考虑原生 DataLoader（Phase 1.2）
 │    │         开销最低，API 最熟悉
 │    └── 否 → Ray Data 流式 + 调优预取（Phase 0.2）
 │
 ├── 训练时长是否 < 1 小时？
 │    ├── 是 → 启动开销占比高
 │    │         最小化 Ray Data 管线复杂度
 │    │         优先物化（Phase 1.3）
 │    └── 否 → 启动成本被摊销
 │             聚焦稳态吞吐优化
 │
 └── 是否使用 ZeRO Stage 3？
      ├── 是 → 通信开销最大
      │         确保 NCCL 不与 Ray Data 争带宽
      │         考虑降到 Stage 2（如果模型放得下）
      └── 否 → 标准优化流程
```

### 10. 总结与思考

### 10.1 优化效果预估

| 优化手段 | 预期加速比 | 适用条件 |
| --- | --- | --- |
| 修复 GPU 竞争（Phase 0.1） | +20-40% | 预处理依赖 GPU |
| 调优预取参数（Phase 0.2） | +5-15% | 通用 |
| 解耦 GPU 预处理（Phase 1.1） | +15-30% | 预处理依赖 GPU |
| 原生 DataLoader（Phase 1.2） | +10-25% | 数据放得进内存 |
| 内存物化（Phase 1.3） | +10-20% | 中等数据量 |
| 组合优化 | 匹配或超越原生性能 | — |

### 10.2 核心认知

**迁移性能回归的根因，不是 Ray 框架本身的缺陷，而是分布式执行模型与单进程模型之间的结构性差异。** 理解了这一点，调优方向就非常清晰：

1. **消除不必要的分布式开销**：如果数据不需要分布式流处理，就不要经过 Ray Data 管线
2. **隔离资源竞争**：预处理和训练在时间维度上串行（而非空间维度并行竞争）
3. **最大化管线重叠**：利用 `prefetch_batches` 让数据准备和 GPU 计算并行
4. **选择正确的 ZeRO 阶段**：通信开销与内存节省的权衡

### 10.3 与系列文章的衔接

本文所分析的性能问题，实际上与前几篇文章中讨论的主题紧密关联：

- **Ray Data 流式执行引擎**（第 22 篇）中分析的 `StreamingExecutor` 和 `ReservationOpResourceAllocator`，正是本文根因 2（管线开销）的底层实现
- **CBO 技术方案**（第 23 篇）中设计的代价模型和选择率估算，未来可以自动推导最优的 `prefetch_batches` 和 `reservation_ratio`，而非依赖人工调参
- **Object Store 与 Block 生命周期**的分析，解释了根因 4（序列化开销）的底层机制

> 经过合理优化，Ray+PyTorch+DeepSpeed 应当能在 **原生性能的 5% 以内**，同时获得分布式调度、弹性伸缩、故障恢复、统一 Data/Train/Serve 管线等额外收益。关键在于理解——哪些分布式开销是不可避免的（如 Actor 调度），哪些是可以消除的（如 GPU 资源竞争），哪些是可以隐藏的（如管线预取）。
