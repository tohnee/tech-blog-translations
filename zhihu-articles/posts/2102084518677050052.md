# Kubernetes Operator 入门：让集群学会"自己照顾自己"

> 写给被重复运维工作折磨的你：如果 Deployment 解决不了你的中间件，也许你需要的不是更多的脚本，而是一个 Operator。

![](https://picx.zhimg.com/v2-b4c7718fcbdbe59dae984c380be1e3bf_1440w.jpg)

---

## 一、从一个真实的场景说起

假设你要在 K8s 上维护一套 MySQL 主从集群。用原生资源你会发现：

- Deployment 只管"副本数"，不管"主从关系"；
- 主库挂了，谁来做故障切换？K8s 不知道；
- 扩容一个从库，要手动改配置、建 PVC、改 Service，一套动作下来十几个命令。

把这些经验写成一个循环脚本：**观察现状 → 对比期望 → 执行动作 → 记录结果**，再把它打包成一个常驻 Pod，让它 7×24 小时盯着你自定义的"MySQLCluster"对象——这就是 Operator。

一句话定义：**Operator = CRD（自定义资源）+ 自定义控制器，用 K8s 的方式管理有状态、有专业知识要求的软件。**

这个模式源自 CoreOS 在 2016 年的开源实践（etcd Operator），如今已成为 Prometheus、PostgreSQL、Kafka 等众多中间件在 K8s 上的标准交付形态。

---

## 二、核心概念：CRD 与 Controller 各管一半

![](https://pica.zhimg.com/v2-7ea96fb0077da4f6ac29d6c402e1743a_1440w.jpg)

### 1. CRD：教 kubectl 认识新对象

CRD 本身只是"类型定义"，相当于给 API Server 扩展了一种新的资源类型：

```text
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  # 命名必须是 <plural>.<group>
  name: mysqlclusters.db.example.com
spec:
  group: db.example.com
  scope: Namespaced
  names:
    kind: MySQLCluster
    listKind: MySQLClusterList
    plural: mysqlclusters
    singular: mysqlcluster
    shortNames:
      - myc
  versions:
    - name: v1
      served: true
      storage: true
      subresources:
        status: {}
      additionalPrinterColumns:
        - name: Replicas
          type: integer
          jsonPath: .spec.replicas
        - name: Ready
          type: integer
          jsonPath: .status.readyReplicas
      # apiextensions.k8s.io/v1 起，openAPIV3Schema 是必填项，
      # 且必须是 structural schema：每个字段都要有明确的 type
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              required:
                - replicas
                - version
                - storage
              properties:
                replicas:
                  type: integer
                  minimum: 1
                  maximum: 9
                  default: 3
                version:
                  type: string
                  pattern: '^8\.0\.[0-9]+$'
                  description: MySQL 8.0.x 版本号
                storage:
                  type: string
                  pattern: '^[0-9]+(Mi|Gi|Ti)$'
                  description: 每个实例的数据盘大小
            status:
              type: object
              properties:
                readyReplicas:
                  type: integer
                conditions:
                  type: array
                  items:
                    type: object
                    required:
                      - type
                      - status
                    properties:
                      type:
                        type: string
                      status:
                        type: string
                      reason:
                        type: string
                      message:
                        type: string
                      lastTransitionTime:
                        type: string
                        format: date-time

```

这里有两个细节值得注意：

- `openAPIV3Schema`**不能省**。自 Kubernetes 1.22 起 `apiextensions.k8s.io/v1beta1` 已不再提供，v1 版本要求每个字段都有明确类型（structural schema），否则 API Server 直接拒绝创建 CRD。
- `subresources.status: {}` 让 `.status` 拥有独立的更新端点，避免控制器回写状态时把用户改的 `spec` 覆盖掉。
- `default: 3` 需要 API Server 的 `CustomResourceDefaulting` 特性（1.17 GA，现已是默认行为）。

装上之后，等 CRD 的 `Established` 条件变为 `True`（通常几秒），`kubectl get myc` 就能用了：

```text
kubectl get crd mysqlclusters.db.example.com \
  -o jsonpath='{.status.conditions[?(@.type=="Established")].status}'
# 输出 True 即表示可用

```

但此时它只是一个"类型"，还没有任何行为——行为要靠 Controller 来给。

### 2. CR：你写的那份"需求单"

```text
apiVersion: db.example.com/v1
kind: MySQLCluster
metadata:
  name: order-db
spec:
  replicas: 3
  version: "8.0.36"
  storage: 50Gi

```

用户只声明"要什么"，不关心"怎么做到"——这正是 K8s 声明式 API 的精髓。schema 里的 `pattern`、`minimum`、`required` 会在提交时由 API Server 直接校验，写错字段立刻报错，而不是等到控制器运行时才炸。

> 💡 想快速验证这两个文件是否可用，不需要真的装集群：`kubectl apply --dry-run=server -f crd.yaml` 会请求 API Server 做完整的服务端校验（需要能连上集群）。离线时可先用 `kubectl apply --dry-run=client -f crd.yaml` 做语法检查。

### 3. Controller：把需求变成现实的那段 Go 代码

真正干活的是控制器。基于 controller-runtime 的典型实现，它由三层协作完成：

| 层 | 位置 | 职责 |
| --- | --- | --- |
| Manager / Builder | internal/controller/*_controller.go 的 SetupWithManager | 向 Manager 注册控制器，声明"我要 Watch 哪些资源" |
| Informer（Cache） | controller-runtime 内置，由 Manager 统一管理 | List/Watch API Server，把对象放进本地缓存，变化时投递事件 |
| Reconciler | Reconcile() 方法 | 从缓存读对象、对比期望与实际、按需创建/更新子资源 |

> 注意：Builder 不是去操作资源的执行者，它只负责"接线"。真正生成 StatefulSet、Service、PVC 的代码是你写在 `Reconcile()` 里的。

## 三、Reconcile：整个模式的心脏

![](https://pic4.zhimg.com/v2-fee51609b69e585ea790b73eb8d11f8b_1440w.jpg)

控制器不断重复同一个循环：

1. **收到事件**——CR 变了，或关联资源变了，或到了重同步时间；
2. **读 CR**——拿到期望（Spec）与上次记录的现状（Status）；
3. **校验**——字段合法吗？版本支持吗？
4. **读子资源**——Deployment/Service 已经存在吗？
5. **逐项对比**——副本数、镜像、配置、存储和期望一致吗？
6. **生成变更**——缺就建，旧就改，多就删；
7. **回写 Status**——把进度记录回 `.status`，供下一轮和用户查看。

没有差异就直接返回；有差异处理完之后通过 `RequeueAfter` 约定下次再看。

> ⚠️ **写 Reconcile 的铁律：幂等。** 同一个 CR 被触发 10 次，结果必须和触发 1 次完全一样。因为事件可能丢失、可能重复、可能乱序，你不能假设"每一步只发生一次"。实践中就是：每一步先查再建，全部通过"获取实际对象 → 对比 → 按需更新"的套路来写。

下面是一段可直接编译运行的最小实现（kubebuilder v4 脚手架生成后的 `Reconcile()` 填充版），演示了上面这套套路：

```text
func (r *MySQLClusterReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
	log := logf.FromContext(ctx) // 需 import logf "sigs.k8s.io/controller-runtime/pkg/log"

	// 1. 读 CR：不存在通常说明已被删除，直接返回即可
	cluster := &dbv1.MySQLCluster{}
	if err := r.Get(ctx, req.NamespacedName, cluster); err != nil {
		if apierrors.IsNotFound(err) {
			return ctrl.Result{}, nil
		}
		return ctrl.Result{}, err
	}

	// 2. 计算期望的子资源（注意：这里只算，不提交）
	desired, err := r.buildStatefulSet(cluster) // 返回 error 便于后续扩展校验逻辑
	if err != nil {
		return ctrl.Result{}, err
	}

	// 3. 先查实际对象
	found := &appsv1.StatefulSet{}
	err = r.Get(ctx, types.NamespacedName{
		Namespace: desired.Namespace,
		Name:      desired.Name,
	}, found)

	switch {
	case apierrors.IsNotFound(err):
		// 4a. 不存在 -> 创建
		log.Info("creating StatefulSet", "name", desired.Name)
		if err = r.Create(ctx, desired); err != nil {
			return ctrl.Result{}, err
		}
	case err != nil:
		return ctrl.Result{}, err
	default:
		// 4b. 已存在 -> 只更新与期望不一致的部分
		if !equalIgnoringRuntimeFields(found, desired) {
			log.Info("updating StatefulSet", "name", desired.Name)
			// 保留 resourceVersion 才能通过乐观锁校验
			desired.ResourceVersion = found.ResourceVersion
			if err = r.Update(ctx, desired); err != nil {
				// 冲突说明有人并发改了，交给下一轮重试，不要在这里死循环
				if apierrors.IsConflict(err) {
					return ctrl.Result{Requeue: true}, nil
				}
				return ctrl.Result{}, err
			}
		}
	}

	// 5. 回写 Status（使用 Status().Update，不影响 spec）
	if found.Status.ReadyReplicas != cluster.Status.ReadyReplicas {
		cluster.Status.ReadyReplicas = found.Status.ReadyReplicas
		meta.SetStatusCondition(&cluster.Status.Conditions, metav1.Condition{
			Type:               "Ready",
			Status:             conditionStatus(found.Status.ReadyReplicas, cluster.Spec.Replicas),
			Reason:             "Reconciled",
			ObservedGeneration: cluster.Generation,
		})
		if err = r.Status().Update(ctx, cluster); err != nil {
			return ctrl.Result{}, err
		}
	}

	// 6. 未就绪就主动回来再看一眼；就绪则只靠事件驱动
	if found.Status.ReadyReplicas < cluster.Spec.Replicas {
		return ctrl.Result{RequeueAfter: 15 * time.Second}, nil
	}
	return ctrl.Result{}, nil
}

// buildStatefulSet 只负责"拼出期望的样子"，任何名字、标签、OwnerReference 都在这里定好
func (r *MySQLClusterReconciler) buildStatefulSet(c *dbv1.MySQLCluster) (*appsv1.StatefulSet, error) {
	name := c.Name + "-mysql"
	labels := map[string]string{"app": name, "managed-by": "mysql-operator"}
	replicas := c.Spec.Replicas

	return &appsv1.StatefulSet{
		ObjectMeta: metav1.ObjectMeta{
			Name:      name,
			Namespace: c.Namespace,
			Labels:    labels,
			// 关键：CR 被删时级联删除子资源，避免孤儿对象
			OwnerReferences: []metav1.OwnerReference{
				*metav1.NewControllerRef(c, dbv1.GroupVersion.WithKind("MySQLCluster")),
			},
		},
		Spec: appsv1.StatefulSetSpec{
			Replicas:    &replicas,
			ServiceName: name,
			Selector:    &metav1.LabelSelector{MatchLabels: map[string]string{"app": name}},
			Template: corev1.PodTemplateSpec{
				ObjectMeta: metav1.ObjectMeta{Labels: labels},
				Spec: corev1.PodSpec{
					Containers: []corev1.Container{{
						Name:  "mysql",
						Image: "mysql:" + c.Spec.Version,
						Env: []corev1.EnvVar{{
							Name:  "MYSQL_ROOT_PASSWORD",
							Value: "change-me", // 生产环境务必从 Secret 注入
						}},
						Ports: []corev1.ContainerPort{{Name: "mysql", ContainerPort: 3306}},
					}},
				},
			},
			VolumeClaimTemplates: []corev1.PersistentVolumeClaim{{
				ObjectMeta: metav1.ObjectMeta{Name: "data"},
				Spec: corev1.PersistentVolumeClaimSpec{
					AccessModes: []corev1.PersistentVolumeAccessMode{corev1.ReadWriteOnce},
					Resources: corev1.VolumeResourceRequirements{
						Requests: corev1.ResourceList{
							corev1.ResourceStorage: resource.MustParse(c.Spec.Storage),
						},
					},
				},
			}},
		},
	}, nil
}

// equalIgnoringRuntimeFields 只比较好"业务字段"，忽略 API Server 自动填充的内容
// 实际项目里建议用 apiequality.Semantic.DeepEqual 加 cmp.Diff 精确定位差异
func equalIgnoringRuntimeFields(found, desired *appsv1.StatefulSet) bool {
	if *found.Spec.Replicas != *desired.Spec.Replicas {
		return false
	}
	if len(found.Spec.Template.Spec.Containers) == 0 ||
		len(desired.Spec.Template.Spec.Containers) == 0 {
		return false
	}
	return found.Spec.Template.Spec.Containers[0].Image ==
		desired.Spec.Template.Spec.Containers[0].Image
}

// conditionStatus 把"就绪数 vs 期望数"翻译成标准 Condition 状态
func conditionStatus(ready, want int32) metav1.ConditionStatus {
	if ready >= want {
		return metav1.ConditionTrue
	}
	return metav1.ConditionFalse
}

```

几个容易踩的点，这段代码里都已经处理：

- `desired.ResourceVersion = found.ResourceVersion`——不带上它，`Update` 会被乐观锁拒绝；
- `IsConflict` 时返回 `Requeue: true` 而不是 `err`，避免把"正常的并发冲突"记成错误日志；
- 子资源一律通过 `metav1.NewControllerRef` 设置 OwnerReference，否则删掉 CR 后会残留一堆孤儿 StatefulSet。

> ✅ 上述代码已在 `k8s.io/api v0.29.3` + `controller-runtime v0.17.2` + Go 1.21 环境下实际编译（`go build` / `go vet` 均通过），并用 fake client 跑过测试：首次创建成功、二次调用不产生多余更新（幂等）、修改 `replicas` 能正确同步到 StatefulSet、CR 删除后安全返回。注意 `VolumeResourceRequirements` 是 1.29 引入的类型，若你用的是更早版本（如 1.27），请换回 `corev1.ResourceRequirements`。

## 四、Operator vs Helm vs 脚本：到底该用谁？

| 维度 | Helm / YAML | Shell / Python 脚本 | Operator |
| --- | --- | --- | --- |
| 适合对象 | 部署形态稳定的应用 | 一次性任务、批量操作 | 有状态、需要持续照顾的中间件 |
| 生命周期管理 | 只管安装/升级，运行期不介入 | 靠人盯 | 全生命周期持续调谐 |
| 故障自愈 | ❌ 不介入运行期 | 需自行实现 | ✅ 持续对齐期望状态 |
| 专业知识沉淀 | 在 values 与注释里 | 在人的脑子里 | 在代码里，可复用 |
| 开发成本 | 低 | 低 | 较高 |

需要说明的是：**Helm 和 Operator 不是替代关系**。Helm 负责"把一堆资源打包部署"，Operator 负责"部署之后持续管理"，官方文档也明确二者互补——典型的用法是用 Helm Chart 安装 Operator 本身，再用 CR 声明业务实例。

**判断标准很简单**：部署完就不想再管的东西，用 Helm；需要持续"照顾"（扩缩容、故障切换、备份、版本升级联动）的东西，才值得写 Operator。

## 五、上手路径：四步跑通第一个 Operator

以下命令与版本依据 kubebuilder 官方 Quick Start（当前要求 **Go v1.24.6+**、kubebuilder v4 脚手架），按顺序执行即可。

**第 0 步：准备环境**

```text
# Go 1.24.6+、Docker 17.03+、kubectl 1.11.3+，以及一个可用的集群（推荐 kind）
kind create cluster --name operator-lab

# 安装 kubebuilder（装到 PATH 里才能全局调用）
curl -L -o kubebuilder "https://go.kubebuilder.io/dl/latest/$(go env GOOS)/$(go env GOARCH)"
chmod +x kubebuilder && sudo mv kubebuilder /usr/local/bin/
kubebuilder version   # 确认可用

```

**第 1 步：初始化项目**

```text
mkdir -p ~/projects/mysql-operator && cd ~/projects/mysql-operator
# 注意：--repo 必须显式给出，否则在非 GOPATH 目录下会报错
kubebuilder init --domain example.com --repo example.com/mysql-operator

```

生成的目录结构如下（v4 脚手架的关键位置）：

```text
mysql-operator/
├── cmd/main.go                        # 入口，注册 Manager 与 Reconciler
├── api/v1/mysqlcluster_types.go       # 在这里写 Spec / Status 结构体
├── internal/controller/
│   └── mysqlcluster_controller.go     # 在这里写 Reconcile 逻辑
├── config/                            # CRD、RBAC、Deployment 等清单
│   └── samples/                       # 示例 CR
├── go.mod
└── Makefile

```

**第 2 步：生成 API 与控制器骨架**

```text
kubebuilder create api --group db --version v1 --kind MySQLCluster
# 交互式提示两件事，都选 y：
#   Create Resource [y/n]   -> 生成 api/v1/mysqlcluster_types.go（CRD 类型）
#   Create Controller [y/n] -> 生成 internal/controller/mysqlcluster_controller.go

```

接着编辑 `api/v1/mysqlcluster_types.go`，把 `Spec` 填成 CRD 里声明过的三个字段；再执行：

```text
make generate    # 生成 DeepCopy 等代码
make manifests   # 依据结构体生成 CRD YAML、RBAC

```

> `make manifests` 会把结构体里的 `+kubebuilder:validation:*` 标记转成 OpenAPI schema。也就是说：**手写 CRD 的 schema 只需要理解原理，实际开发中由标注自动生成。**

**第 3 步：本地调试**

```text
make install    # 先把 CRD 装进集群（不装的话控制器 Watch 不到任何对象）
make run        # 在宿主机前台运行控制器，直连当前 kubeconfig 指向的集群

```

另开一个终端提交 CR：

```text
kubectl apply -k config/samples/
kubectl get myc -w      # 用 shortNames 观察状态变化

```

`make run` 的好处是支持断点调试；缺点是进程不在集群内，权限就是你的 kubeconfig 权限。

**第 4 步：构建镜像并部署**

```text
# IMG 必须指定，否则 Makefile 会用到默认值
export IMG=<你的镜像仓库>/mysql-operator:v0.1.0
make docker-build docker-push IMG=$IMG

# kind 集群可直接本地加载，省掉推仓库
# kind load docker-image $IMG --name operator-lab

make deploy IMG=$IMG
kubectl get pods -n mysql-operator-system

```

删除时按相反顺序执行 `make undeploy`、`make uninstall`（后者会删掉 CRD，连带所有 CR，慎用）。

建议第一个练手项目选一个你最熟悉的中间件，从只实现"部署 + 扩缩容"两个能力开始，不要一上来就做故障切换。

## 六、生产环境的五个坑

1. **Reconcile 里做阻塞操作**——慢查询、外部 API 调用会拖垮整个工作队列，耗时操作要异步化并记录进度；
2. **忽略 ownerReference**——子资源必须设置 Owner，否则 CR 删除后残留一堆孤儿资源；
3. **Status 乱写**——Status 是给别人看的契约，建议用 `conditions` 标准结构，别只塞一个字符串；
4. **不做并发保护**——更新对象时要带上 `resourceVersion` 做乐观锁，遇到 `IsConflict` 要重试而不是直接报错；
5. **忘记 Status 子资源**——CRD 不声明 `subresources.status` 时，控制器回写状态可能覆盖用户修改的 `spec`。
