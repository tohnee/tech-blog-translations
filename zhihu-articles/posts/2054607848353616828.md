你是否曾遇到这种问题，256 张 H100 上跑着 70B 的 Llama，iter 5000，突然 OOM。但看了眼 `nvidia-smi`——每张卡明明还有 12 GB 显存空着。PyTorch 报错说想申请一块 2 GB 的连续显存，失败了。

GPU 显存从来不是“还剩多少空间”的问题，而是“这些空间长什么样”的问题。剩下 12GB 是一堆碎片，不是一块能用的地皮。

## 1. Allocator 显存碎片的真相

`CUDACachingAllocator `的工作方式很像内存管理的老故事：你分配、释放、再分配、再释放。每次释放的 block 会被丢进 free list，下次分配时 allocator 会试图复用。但问题是，长期运行后，不同大小的 block 被反复切分，free list 里的块越来越小、越来越散。

训练跑到 iter 5000 才崩，不是因为模型突然变胖了。iter 1 和 iter 5000 的 op trace 在形状和顺序上几乎一模一样, tensor shape 固定, 调用顺序固定, stream 关系也固定 (严格说 dropout mask、AC 重算路径里的随机数 op 是”相同 op、不同结果”, 但 allocator 看到的 size/lifetime 序列是一致的)。但 PyTorch 的 allocator 不”认识”这个模式。它每次还是老老实实走一遍：找 free list、切 block、返回指针。几万次迭代后，地址空间被切得稀碎，明明总量够，就是凑不出一块 2GB 连续的空闲段。

这其实是通用 allocator 的设计代价。它要保证“什么模型都能跑”，所以它不能假设你的训练循环是重复的。但这个代价在稳定训练场景下尤其存在问题的——我们明确知道下一轮要分配什么、多大、什么时候释放，allocator 却装不知道。

PyTorch 的 CUDA OOM 报错里通常会同时出现几类数字: allocated、reserved、free、以及本次申请的 size。 但 allocator 真正要找的是一块满足约束的 block: size 要够, stream 语义要安全, 必要时还要能 split 或 merge。而不仅仅是 `nvidia-smi` 或 free 字段对应显存需求。

我们可以把默认 allocator 简化成三层账本:

```text
CUDA driver:     真实显存段, cudaMalloc/cudaFree 负责向 driver 申请或归还
PyTorch segment: PyTorch 从 driver 拿到的大段显存, reserved 在这里增长
Allocator block: segment 内部被 split/merge 出来的小块, allocated/free 在这里变化
```

所以“还有 12 GB free”只能说明总账没满, 不能说明 free list 里有一块连续 2 GB 的可用 block。训练前几千步没问题, 后面突然 OOM, 典型原因就是大块不断被 split, 小块释放后又无法和相邻块合并, 最后形成“总量足够、连续块不足”的状态。

这也是 `PYTORCH_ALLOC_CONF=max_split_size_mb` 和 `expandable_segments` 经常能缓解问题、却不总能根治问题的原因: 前者减少大块被切碎的概率, 后者让大段分配可以随需求增长, 减少 batch size 轻微变化时产生的 unusable slivers; 但它们都没有真正拿到完整 iter 的生命周期信息。CUDA backend 的主名是 `PYTORCH_CUDA_ALLOC_CONF`, 跨 backend (CUDA / HIP / XPU) 的统一别名是 `PYTORCH_ALLOC_CONF`, 两者读同一组 kv, 可以互换。

## 2. Iter 5001 和 Iter 1 一样, allocator 却不知道?

下面我们先来看一个例子：

PyTorch 自带的 `torch.cuda.memory._record_memory_history()` 能把所有 allocator 事件录下来, `_snapshot()` 能在某个时刻拍快照。把它套在一个标准训练循环外面:

```text
import torch
torch.cuda.memory._record_memory_history(max_entries=100_000)

for step, batch in enumerate(loader):
    loss = model(batch).loss
    loss.backward()
    optimizer.step()
    optimizer.zero_grad()

    if step in {1, 100, 1000, 5000}:
        torch.cuda.memory._dump_snapshot(f"snap_{step}.pickle")
```

把 dump 出来的 pickle 拖进 `pytorch.org/memory_viz`，你会看到：

- iter 1：used block 之间夹着大块整齐的灰色 free 区，顶部有充足的连续空间
- iter 5000：used 条带之间塞满细碎灰色缝隙，就像瑞士奶酪——总空余面积很大，但每一口都太小

memory_viz 的 timeline 视图上，每个彩色条带是一块仍在使用的显存 block，颜色对应分配调用栈。健康的训练循环里，条带密集但排列整齐，顶部留出大片灰色；碎片化的 trace 里，灰色 free 块被切割成几十 MB 甚至几 MB 的小段，每一段都撑不起下一次大 tensor 分配。

### 2.1 为什么 allocator 不”记住”？

为什么 allocator 不能”记住” iter 1 学到的东西?

答案在 `c10/cuda/CUDACachingAllocator.cpp` 的核心数据结构里。`CUDACachingAllocator` 会把从 CUDA driver 申请到的大段显存切成 block, 再用按 size/stream 等条件组织的 free block 集合做复用。旧版本和不同 backend 的细节会变, 但 native allocator 的核心思路可以简化成: rounded size、查找可复用 block、必要时 split、释放时尝试 merge。一次 alloc 的逻辑大致是:

```text
alloc(size, stream):
  size_rounded = round_up(size, 512)           # 对齐到 512 字节
  block        = find_reusable_block(size_rounded, stream)  # best-fit 搜索
  if block is None:
    block = alloc_new_segment(size_rounded)    # 调用 cudaMalloc 取新显存
  if block.size - size > 512:
    rest = split(block, size)                  # 切下剩余部分放回 free list
    free_list.insert(rest)
  return block

free(ptr):
  把 block 标记为空闲
  如果左右邻居都空闲，merge 成大块
```

free 的时候做反向操作: 块还回 `BlockPool`, 如果左右邻居都空闲就 `try_merge_blocks` 合并。这个 “split + merge” 设计的本意是”在不知道未来 size 分布的情况下尽量保持可用性”, 但代价是: 当 free list 因为各种历史原因被切得很碎之后, 一次大请求即使总剩余 > 请求量, 也会触发 `cudaMalloc` 拿新段。

> `find_reusable_block` 在 CUDACachingAllocator 里不是遍历全 list 找全局最优, 而是在按 `(stream, size)` 索引的 `BlockPool` 上做 `lower_bound`——取”第一个 size ≥ 请求量”的 block, 复杂度 O(log n), 语义更接近 smallest-fit 而不是 best-fit。对齐策略也不是统一 512 B: 小块按 512 B、大块按 2 MB, 还支持 `roundup_power2_divisions` 把请求 size 进一步向 2 的幂对齐。

这个设计本意是好的：”我不知道你下次要多大，所以我尽量保留各种 size 的 free 块，并尝试合并相邻块”。但它有两个致命假设：

- 历史 size 分布能预测未来——训练循环里 tensor size 确实不变，但分配顺序在 iter 之间虽然一致，allocator 没拿到”这个 block 下个 iter 还会被同 size 复用”的提示，只能按地址就近合并，而地址本身在漂移
- split + merge 可以无限维持秩序——实际上每次 split 都会在 free list 里留下一个边缘碎片，merge 只能合并物理相邻的块。但同一个 call site 分配的 tensor，每次可能落到不同的地址段，相邻关系不断变化，merge 效率越来越低

用图说话：

```text
iter 100  (free list 比较干净):
[========free 2GB========][used][===free 1GB===][used]

iter 5000 (碎片化):
[free 64MB][used][free 32MB][used][free 80MB][used][free 16MB] ...
```

每个 free 块都小于下一次要分配的 2GB tensor，总剩余加起来可能有 12GB，但 find_reusable_block 遍历 free list 找不到够大的块，只能调 cudaMalloc 去 driver 端申请新显存。此时 driver 一看：进程已经占用了大部分显存，剩下的连续空闲区域确实没有 2GB，直接返回 OOM。

两个常用”治标”参数:

| 参数 | 作用 | 为什么治标 |
| --- | --- | --- |
| PYTORCH_ALLOC_CONF=max_split_size_mb:N | native allocator 不再 split 大于 N MB 的 block | 减少大块被切碎的概率, 但对长期碎片化只是延缓; 官方文档也建议只在 OOM 且 inactive split blocks 很多时作为 last resort 调 |
| PYTORCH_ALLOC_CONF=expandable_segments:True | 让大分配段后续可扩展, 典型目标是 batch size 轻微变化导致的 slivers | 能减少某类 unusable free slices, 但 free 时机仍由 allocator 决定, 完整 lifetime 信息还是丢失 |

`expandable_segments` 实际上已经在朝“更稳定的大段布局”方向演化了: 它让 allocator 尽量维护可增长的大 segment, 避免许多相近 size 的大分配彼此留下尾部碎片。但它还差关键一步: **它不知道整个 iter 的生命周期, 所以只能 reactive 地扩展和复用, 没法主动给每个 op 预排地址。**

可以说，**通用 allocator 在每个 iter 都像第一次见到这个程序, 因为 API 接口只承诺 `alloc(size) -> ptr`, 调用方没办法告诉它“这个 ptr 我下一个 iter 还要在同一个 size、同一个 stream 上申请”。**

如果 allocator 真的知道未来的情况, 它会退化成一张静态 offset 表: 给定 op id, O(1) 拿到地址, 不需要反复 split/merge, 也不会把同一段生命周期稳定的内存切成碎片。理想情况下, `cudaMalloc` 只在程序启动或 shape 切换时发生, 后续 iter 复用同一套地址布局。这种效果在固定的业务场景上更符合直观的预期。

针对这个问题，我们怎么做优化呢，我们梳理了几个思路：

## 3. 可预测静态调度显存复用：静态 Buffer

先复盘分布式训练策略的演化：

- FSDP1 (FullyShardedDataParallel, 2022) 的逻辑是：每一层 wrap 成一个 unit，forward 时 all_gather 把分片参数凑齐，计算，然后 reshard（把非本 rank 的部分释放），backward 时再来一遍。问题在于：

```text
每层 all_gather 申请一块"layer-sized"的临时 buffer，计算完释放，下一层再分配——allocator 看见的是一串"创建-销毁"事件

预取（提前 all_gather 下一层）必须用户自己管，容易和计算流抢内存

同构 Transformer 的许多层 buffer size 一致或高度接近，具备显式复用的条件，但默认 allocator 不知道这种模型结构先验
```

- FSDP2 / per-parameter sharding 把表达粒度从 layer flatten buffer 推向更细的 parameter/DTensor 语义。粒度细带来的好处是：MoE 中不同 expert 可以独立分片、参数分组更灵活、和 torch.compile/编译器路径更容易协同。但小参数会被集合通信启动开销拖累——每个集合通信的启动开销在μs 量级，一个 RMSNorm 才几 KB，payload 可能根本跑不出 NCCL 的最高带宽。因此真实系统通常还要依赖 bucketing/重排把多个小参数合成更大的通信单元。

而这种策略的问题就在于，小参数合并重排和重复申请释放，其实在同构 Transformer 场景上其实不是最优的，就有可能导致 OOM 的问题。

一个直接静态 buffer 的思路是：既然同构 Transformer 每一层的分片参数 shape 完全一致，那就常驻两块 layer-sized buffer，叫它们 A 和 B。

```text
compute stream         NCCL stream
iter t, layer 0:  compute(A)  <----  all_gather → A   (preloaded)
                                     all_gather → B  (prefetch layer 1)

iter t, layer 1:  compute(B)         all_gather → A  (prefetch layer 2)

iter t, layer 2:  compute(A)         all_gather → B  (prefetch layer 3)
                  ...
偶数层落 A, 奇数层落 B, fwd/bwd 复用同一对 buffer。
```

这件事的关键不是”双 buffer 提速”, 而是 **把 buffer 的生命周期从 allocator 手里夺过来, 自己作为一个 mini-allocator 管两块固定地址**。这个 ownership 转移有几个直接收益:

1. `cudaMalloc` 次数从”每层一次”降到”启动时两次, 之后零次”
2. NCCL stream 写哪一块 buffer、何时切换 ownership, 完全由训练逻辑控制, prefetch 不再和 compute 抢
3. **地址是固定的** —— 这才是 CUDA Graphs 能落地的前提

> 这类方案的端到端收益不能脱离训练栈和集群环境引用。它减少的是 layer-sized 临时 buffer 的重复分配、NCCL/compute ownership 争用和 CUDA Graphs capture 的地址不稳定性; 最终能换来多少 throughput, 取决于模型大小、层数、bucket 策略、通信拓扑、activation checkpoint 和 kernel/communication overlap。更稳妥的说法是: 模型越大、单层 buffer 越大、训练循环越稳定, 静态 buffer 布局的 ROI 通常越高; 具体百分比必须在自己的训练栈上测。

**硬要求**: 要让 A/B 两块 buffer 通用复用, 被复用的 layer sharded 参数 shape 必须一致或能被同一组 bucket 容纳。MoE、异构层、动态专家路由、不同 FFN dim 的层, 通常需要 fallback 到 per-layer/per-bucket 分配, 也就会损失这类静态布局的核心优势。

### 3.1 静态 Buffer + CUDA Graphs

静态 buffer 把地址锁定之后，真正的杠杆才出现——CUDA Graphs。静态 buffer 解决”每次 alloc 落到同一个地址”的问题, CUDA Graphs 解决”每次 launch 都要走 CPU 一遍”的问题, 两个机制天然配对。

一段被捕获成 graph 的 kernel 序列，在重放时跳过所有 CPU 端的启动开销（kernel 提交、参数编组、stream 管理），直接把整段 device-side 工作单元批量提交。一个典型 iter 里的 kernel launch 可能上千次，每次 CPU 侧几μs 到几十μs，累积下来在 small-shape 场景非常显眼。

但 CUDA Graphs 有一条铁律, 现在第一次完整说清楚: **capture 时记录下来的是每个 kernel 看见的具体指针, replay 时这些指针必须依旧有效且仍然属于 graph 期待的那段内存**。

换言之, 整张 graph 锁定的不是张量逻辑, 而是物理地址。这意味着每次 iter 都要把 sharded 参数 all_gather 到 **同一个地址**; 也意味着输入 tensor 必须放在 graph 自己持有的”占位”内存里, 数据按 iter 通过 in-place copy 灌进去, 而不是每个 iter 用一个新的 `torch.from_numpy(...)` 喂进去。

如果 sharded 参数或输入 tensor 每轮都由普通 allocator 重新决定地址, 就很难直接 replay 同一张 graph; 工程上常见做法是使用静态输入占位、固定通信 buffer, 或用 `torch.cuda.MemPool` 隔离 graph 相关分配 (见 §8)。 静态的 A/B buffer 地址从程序启动后保持稳定, 因而更容易和 capture 配合。

```text
# 伪代码: 静态 buffer 与 cudagraph capture 的协同
buf_a = torch.empty(layer_sharded_size, device='cuda')
buf_b = torch.empty(layer_sharded_size, device='cuda')

# 关键: 给输入也准备静态占位 tensor, 后续每个 iter 往里 copy_
static_inputs = {k: torch.empty_like(v) for k, v in batch.items()}

# warmup: 跑几个 iter, 让 NCCL/allocator 状态稳定
for _ in range(3):
    for k in static_inputs:
        static_inputs[k].copy_(batch[k])
    train_step(model, static_inputs)

g = torch.cuda.CUDAGraph()
with torch.cuda.graph(g):
    # capture 时记录的就是 static_inputs / buf_a / buf_b 这几个地址
    train_step(model, static_inputs)

# 实际训练: replay 一次顶过去一整个 iter
for batch in loader:
    for k in static_inputs:
        static_inputs[k].copy_(batch[k])   # 数据进 graph 的占位 buffer
    g.replay()
```

`torch.cuda.make_graphed_callables` 是 PyTorch 提供的更“用户态友好”的入口, 可以把函数或 `nn.Module` 包装成 graphed callable。它会做 warmup, forward 和 backward 都会以 CUDA graph 的形式运行; 但调用时参数顺序/格式必须和 `sample_args` 一致, Module 也不能在 capture 后再增删参数或 buffer。理解上面这段裸 capture 的地址约束, 是出问题时能 debug 下去的前提。

什么时候 capture 会失败?

- 动态 shape (变长 seq、动态 batch): capture 一次只能锁一个 shape, 多 shape 要么多 graph、要么放弃
- MoE 路由: 每个 iter 激活的 expert 集合不同, 通信拓扑变, 没法用一张 graph
- 控制流分歧: `if loss.isnan():` 这类 host-side 判断 capture 会跳过

把这条主线拉直：CUDA Graphs 把”可预测性”编码到 CUDA runtime 层面，静态 buffer 把”可预测性”编码到 buffer 布局层面，两者天然耦合。 静态调度的理想形态，是热路径上的 allocator call 尽可能接近零。

## 4. 不可预测静态显存调度复用：PagedAttention

但是某些真实的场景中存在不可预测 workload，那应该如何优化呢？

比如推理场景里的 KV cache 是不可预测的，我们来看看这个场景如何优化。

**vLLM 的处境**: 一个推理服务面对的真实情况是,

- request 长度方差极大: 一条短 prompt 可能 64 tokens, 一条长文档可能 32K
- continuous batching: 不是按 batch 凑齐才提交, 而是有 request 就插进当前 batch, 跑完一条立即出 batch, 任意时刻活跃 request 数都在变
- prefix caching: 多个 request 共享同一个 system prompt 时, KV cache 可以共享前缀
- speculative decoding: 推测分支可能被 reject, KV 要回滚

如果用”训练那一套”提前预分配[max_batch, max_seq_len, n_layers, n_heads, head_dim]的 KV cache，问题立刻就暴露了：

- 一条 64-token 的请求占用 32K-token 的位置，90% 是浪费
- prefix 没办法跨请求共享
- 实际生产环境里显存浪费经常超过 60%（PagedAttention 论文实测数据）

这不是显存总量不够，而是预分配策略和实际使用模式严重错配。剩余显存被切成几块大”预留区”，每块都有大量闲置空间，但每块都不够塞进一个新的大请求——和本文开篇训练场景里 free list 碎成 16MB 小块、凑不出 2GB 连续块的底层逻辑完全一样。

### 4.1 分页如何绕过这个问题

PagedAttention 把 KV cache 切成固定大小的 page（vLLM 早期默认 block_size=16 tokens, 新版本支持多档可选），每个请求只持有自己实际用到的 page，按需申请。

```text
请求 A（64 tokens）:   [page 1][page 2][page 3][page 4]
请求 B（32768 tokens）: [page 5][page 6]...[page 2053]
请求 C（128 tokens，共享 system prompt）: [page 1][page 2][page 8][page 9]
                           ↑
                    和请求 A 共用 page 1-2（system prompt 部分）
```

三件事同时发生：

消除内部碎片：短请求只占 4 个 page，不再为 max_seq_len 买单。碎片从”预留但未使用”变成”物理上就不分配”

物理不连续不再是障碍：请求 C 的 logical page 1、2、8、9 在物理上可以是任意位置，通过 block table 做一层映射。推理场景里 attention kernel 只关心 KV 值本身，物理是否连续不关键

共享成为可能：system prompt 的 page 被多个请求引用，物理上只存一份

间接寻址的开销（每次 attention 查 block table）换来的是碎片率从 50%+降到个位数。在请求长度极度不规则的推理场景里，这笔交易是划算的。

### 4.2 PagedAttention 是否可以应用到训练呢

训练里 KV activation 的生命周期只覆盖一次 forward + 对应的 backward。FlashAttention 的 backward 仍需要保存完整的 Q / K / V / O, 加一个 per-token 的 logsumexp 向量 L; 它省的是 `N × N` 的 attention 概率矩阵——不去物化那张大表, 而不是不保存 K / V。即便如此, K / V 的占用仍然在 MB 量级而非 KB 量级。

这和推理的”请求持续几秒到几十秒, KV cache 全程驻存”在 lifetime 上不是一个量级: 训练里每段 K / V 的存活窗口只是一次 fwd + 对应 bwd, 边界已知, 不需要在线分页。这是训练侧不引入 PagedAttention 的真正原因, 而不是”K / V 不需要保存”。

训练里的变长序列, 一般使用 Sequence Packing, 用的是 packing + cu_seqlens, Flash Attention 的 `flash_attn_varlen_func` 直接用 cu_seqlens 控制计算范围, kernel 层面不碰 padding token。这是计算优化——砍掉 padding token 上的无效 FLOPs。

虽然训练侧无法复用推理的显存优化思路, 但可以借鉴类似的思想, 那就是 prefix 共享。

### 4.3 SFT prefix 共享优化

训练里的 prefix 共享和推理里的 prefix caching 是两回事。推理里是运行时动态发现共享，训练里是编译期静态安排共享。前者需要 page table 做在线映射，后者只需要在数据预处理阶段把共享关系编码进 batch。

这里实现一般有两种粒度的方案：

- Token-level 共享

这种实现的做法是，把共享的 system prompt 只存一次，拼在每条样本前面，用 attention mask 控制可见范围。

假设 system prompt 是”S”（10 tokens），三条样本分别是 A、B、C（各 100 tokens）。普通做法是每条样本都存一份 S：

```text
样本 1: [S][A][PAD][PAD]...  (每条都带 S)
样本 2: [S][B][PAD][PAD]...
样本 3: [S][C][PAD][PAD]...
```

S 被重复存了 3 次，显存浪费 30 tokens × hidden_dim × n_layers。

即使我们做 Sequence Packing, S 确实被复制了三次，物理上占了三份位置。真正的共享怎么做？ 更进一步的做法是把 S 单独放在序列最前面，和 Sequence Packing 原理一样，我们只需要控制 mask 就行。

```text
packed sequence: [S][A][B][C]
attention_mask:  A 的 token 能看到 S + A 自己
                 B 的 token 能看到 S + B 自己（看不到 A）
                 C 的 token 能看到 S + C 自己（看不到 A/B）
```

但这样 position_ids 处理起来比较麻烦——A / B / C 各自从 0 开始计数还是接在 S 后面? 如果从 0 开始, RoPE 的位置编码就和 S 的长度解耦了, 需要 custom attention mask 来重置位置。所以这个优化仅在 prefix 占比高的场景下值得做, 且实现门槛不低。

需要说明的是，Token-level packing 省的是显存里 token 的重复存储，但 prefix 的 forward 计算还是被算了 N 次（对应到 packed 后 N 段 attention）

- Compute-level 共享

prefix forward 只跑一次，后续样本在 attention 里直接拿这份 KV。省的是 prefix 那段的算力。

在 transformer 链路里只有 attention 这一步有”跨位置”的依赖——其他所有算子（embedding、LayerNorm、Q/K/V projection、MLP）都是逐位置的。所以”prefix 在所有样本里完全一样”

所以其优化做法可以实现自定义attention mask，需要自定义融合计算。

几个需要关心的细节：

- RoPE position：suffix 的 position_ids 要从 L_p 开始，不是从 0。否则相位对不上。
- Backward：N 条样本的梯度自动累加回 prefix 的同一组 leaf，等价于”N 条独立样本梯度求和”。loss 用 mean 还是 sum 要和 baseline 对齐，否则 prefix 那段的 effective LR 会偏 N 倍。
- Activation：prefix 的中间激活要活到 backward。配 gradient checkpointing 最划算——prefix 只重算一次而不是 N 次。

## 5. Activation Checkpoint 的 recompute buffer

Activation checkpoint 是大模型训练的标配 —— 把中间 activation drop 掉, bwd 时重跑 fwd 重新算。当前 PyTorch 推荐用 `torch.utils.checkpoint.checkpoint(fn, *args, use_reentrant=False)`, 内部走的是 `_checkpoint_without_reentrant_generator` (源码里这是 generator 形式, 没有 `_checkpoint_without_reentrant` 这个名字), 通过 `saved_tensors_hooks` 机制接管”哪些 tensor 不存”。

```text
# torch.utils.checkpoint 的简化逻辑
def checkpoint(fn, *args):
    storage = {}
    def pack(tensor):
        return store_idx(storage, tensor)  # fwd: 替换为 idx 标记
    def unpack(idx):
        # bwd 时如果发现需要这个 tensor, 重跑 fn 重新生成
        if idx not in storage_recomputed:
            recompute(fn, *args, storage=storage_recomputed)
        return storage_recomputed[idx]

    with torch.autograd.graph.saved_tensors_hooks(pack, unpack):
        return fn(*args)
```

关键观察: **recompute 出来的中间 tensor, 在 size、dtype、stream 三个维度上和原始 fwd 完全一致** —— 因为它就是把同一段代码再跑一遍。这是另一段”未来已知”的窗口, 但默认实现把它交给 allocator 处理: 每次 unpack 触发 recompute, 内部所有 alloc 走通用 allocator。

这块的优化空间是 **为每个 checkpoint segment 预留一块 recompute scratch buffer**, bwd 时直接 in-place 写。和 selective checkpoint (FlashAttention 之后主流的”只保留 attention 输出, drop 中间的 softmax、attention score”) 配合特别合适 —— 因为被 drop 的 tensor 类型很稳定, scratch buffer 的 size 容易预先算出来。

代码大致是:

```python3
class ScratchCheckpoint(torch.autograd.Function):
    @staticmethod
    def forward(ctx, fn, scratch_buf, *args):
        ctx.fn = fn
        ctx.scratch = scratch_buf       # 复用一块预分配 buffer
        ctx.save_for_backward(*args)
        with torch.no_grad():
            return fn(*args)

    @staticmethod
    def backward(ctx, *grad_outputs):
        args = ctx.saved_tensors
        # 关键: recompute 时所有中间 tensor 落在 scratch 上, 不走 allocator
        with use_static_buffer(ctx.scratch):
            with torch.enable_grad():
                args_with_grad = [a.detach().requires_grad_() for a in args]
                out = ctx.fn(*args_with_grad)
                grads = torch.autograd.grad(out, args_with_grad, grad_outputs)
        return (None, None) + grads
```

`use_static_buffer` 这个 ContextManager 不是 PyTorch 现成 API, 需要 hook 到 allocator 层。如果更偏 torch API, 可以使用 `torch.cuda.MemPool` + `torch.cuda.use_mem_pool(pool)`: 它可以把一段代码的分配隔离到指定 pool, 同时仍保留大部分 CUDACachingAllocator 的缓存行为。pool 的内存不是退出 context 就立刻全部归还系统, 而是在 tensor 引用释放、pool 生命周期结束后再回收。

> 这种 scratch buffer 的设计思路, **把一段已知生命周期的内存从全局 allocator 隔离出来, 用更简单的本地策略 (静态偏移或 ring buffer) 管。**

## 6. 什么时候静态调度显存复用划算

不可预测 (推理用户请求) 和难以预测 (训练里随机 batch order、动态 dropout) 是两件事, 后者只是没人去 staticize。下面这张矩阵默认讨论的是后者 —— **训练 workload 的”难以预测”程度有多高**, 横轴 workload 可预测度, 纵轴 kernel 占比 (kernel 占 iter 时间越多, allocator 的 μs 级开销相对越显眼; 反之 IO 主导的训练 allocator 影响就小):

|  | workload 低可预测度<br>(MoE / 动态 shape / research) | workload 中可预测度<br>(SFT / 长尾推荐 / 混合精度切换) | workload 高可预测度<br>(同构 Transformer 预训练 / 推荐 dense 段) |
| --- | --- | --- | --- |
| kernel 占比高<br>(纯 GPU bound) | 默认 allocator + expandable_segments | torch.cuda.MemPool / CUDAPluggableAllocator 半静态 | 静态 buffer + CUDA Graphs —— Llama 70B 预训练、Megatron-LM flat-buffer |
| kernel 占比中<br>(部分 IO / 通信 bound) | 默认 allocator | expandable_segments + 按 group bucketing | 静态 layer buffer (不 capture graph 也值得) |
| kernel 占比低<br>(IO bound / 小 batch debug) | 默认就好 | 默认就好 —— 优化 allocator 收益被 IO 等掩盖 | 默认就好 |

## 7. 小结

静态调度的本质不是简单地“让程序更快”, 而是 **把 workload 的先验知识从程序员脑子里搬到运行时**。只有运行时知道 shape、lifetime、stream 和参数分组的稳定性, allocator 才能从“通用 best-fit”退化成“按计划复用”。
