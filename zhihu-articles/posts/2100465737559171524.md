> 论文：Only Accepted Tokens Count: An Energy Accounting of Speculative Decoding Under Latency Targets

> 作者：Bole Ma、Ayesha Afzal、Jan Eitzinger、Harald Koestler、Gerhard Wellein（Erlangen 国家高性能计算中心，FAU）

> arXiv:2610.40287v1，2026-10-29

数据中心现在越来越像一座受电力配额约束的工厂：能服务多少 token，取决于每兆瓦能换回多少 token。于是「每 token 多少焦耳」（energy per token，EPOT）从一个边角指标变成了采购与调度的一等公民。与此同时，用户侧的延迟目标并没有放松——首 token 时间（TTFT）和 token 间隔（TBT，也叫 TPOT）仍然是硬约束。

这篇来自 Erlangen 国家高性能计算中心的论文，做了一件此前没人系统做过的事：**在真实生产栈（SGLang + CUDA graphs）上，把投机解码的能耗账本从头算了一遍**。它的结论有点反直觉——投机解码省不省电，几乎完全取决于「每次验证能被接受几个 token」，而这个数又随 batch、模型、GPU、甚至服务文本的语言而变。同一套 drafter 配置，在 H100 上省 40%，搬到带宽更高的 H200 上可能就变成亏。

## 一、先算清楚 decode 的钱花在哪

自回归 decode 每生成一个 token，就要把模型全部权重从显存读一遍。算术单元几乎全程在等内存：论文引用 GH200 的实测数据，从 HBM 读一个字节约 93 pJ，而一次 16 位 tensor core 运算约 0.5 pJ，差了近两个数量级。

用 roofline 的语言说，H100 的「平衡点」（算术强度达到峰值算力所需的每字节运算数）约 316 op/byte，H200 约 163 op/byte；而单流 decode 一步只有大约 10 op/byte（这个数已经把 tensor core 的 padding 浪费算进去了）。也就是说，**decode 离算力墙还有一个数量级**，能耗和时间都跟着字节走。

这解释了两件事：为什么 batching 能省电（一次权重读取摊给多个请求），也为什么投机解码能提速（一次权重读取产出多个 token）。

## 二、batching 与投机解码是两把不同的杠杆

batching 摊薄权重读取，但对单个用户没有任何加速。论文实测：在 dense 模型上，从 batch 1 到 batch 32，单用户的 token 间隔反而增长 9% 到 34%；在 MoE 模型上增长 2.5 到 4.0 倍，因为每个新增请求都会把自己的专家权重加进这次读取。**batch 越大，单个用户越慢**——这就是延迟目标与吞吐目标的结构性冲突。

当延迟目标足够紧时，任何 batch 都救不了。论文里，25 ms/token 的目标下最大的 dense 模型 gemma-4-31B-it 在所有跑过的 batch 上都不达标；10 ms/token 的目标下 11 个模型里有 4 个不达标。投机解码是唯一还能动的杠杆：单流平均 token 间隔缩短 1.3 到 4.3 倍，上述所有模型都被拉回目标线内。

代价是能量。而这里有一个容易被忽略的细节：**引擎默认的验证是「不 ragged」的**——不管某个请求的 drafter 提议了几个 token、接受了几个，验证阶段都按固定数量跑满。所以被拒绝的 token 不但白 draft，还白占了一份验证算力。真正决定能耗的是「每次验证接受几个 token」（accepted tokens per verification），而不是常被引用的「接受率」。

## 三、实验怎么做的

实验覆盖 11 个模型、4 类注意力结构、5 种 drafter：

注意力结构：plain GQA（Qwen3-4B/8B/14B、Qwen3-Coder-30B-A3B）、GQA + 滑动窗口（gemma-4-12B/26B-A4B/31B）、MLA（GLM-4.7-Flash、JoyAI-LLM-Flash）、以及交错 Gated DeltaNet 与门控注意力的状态空间混合架构（Qwen3.6-27B、Qwen3.6-35B-A3B）。其中 5 个是 MoE。

drafter：免训练的 n-gram 查表、MTP 头（含 gemma 的 assistant）、EAGLE3、块式 drafter DFlash 与 DSpark。块式 drafter 一次前向出一整块（16 token 或 7 token），头式 drafter 一次一个 token、串行多趟。

硬件：单卡 H100 SXM5（94 GB HBM2e、700 W 上限，实测 2.28 TB/s、719 TFLOP/s BF16）；三个模型放不下或大 batch 放不下时换 H200（141 GB HBM3e、4.44 TB/s、722 TFLOP/s）。

方法：SGLang 0.5.12+、CUDA 13.2、BF16 权重与 KV、greedy 解码、每请求生成 512 token、每格至少 3 个 seed；能耗取 GPU 板载累积计数器（NVML），10 Hz 采样，取生成前后两次读数之差。

对照：**每个投机配置都配一个同模型、同 batch、同 prompt 池、同生成长度的非投机基线**，省电比例是「相对这个配对基线」的下降幅度。这挡住了「拿不同服务配置的差异冒充算法收益」这类最常见的错误。

一个方法论上的关键决定：所有数字都在 **CUDA graph capture 打开**的状态下报告。原因是生产引擎本来就开 capture，而 capture 对基线（launch-bound 最严重）的帮助大于对投机运行（每 launch 已经带了很多 token 的工作量）的帮助。若关掉 capture 测，等于把投机从没消除过的 launch 开销算成它的功劳。

## 四、结果一：单流能省一半，但随 batch 迅速衰减

单流（batch=1）时，每个模型总能找到一种省电的方案，各模型最大节省的中位数是 decode 能量的 54%。最亮的是 gemma-4-31B-it 用 DFlash：EPOT 从 12.65 J/token 降到 2.91 J/token，省 77%；gemma-4-12B-it 省 75%；Qwen3-8B 用 DSpark 省 60%。唯一的反例是 n-gram 在 MoE 上——它接受的 token 太少，付不起每个额外验证 token 读进来的专家权重。

随 batch 增大，节省单调衰减（图 2）：batching 已经把权重读取摊薄了，drafter 能「再分一次」的空间随之变小。到 batch 64，各模型最大节省仍有 15% 到 52%，但**不是所有方案都还省电**：n-gram 在除 Qwen3-Coder 外的所有模型上都是净亏损；DFlash-16 在 Qwen3-4B/8B 上亏；EAGLE3 与 DFlash-7 在 Qwen3-14B 上亏。这与 Fernandez 等人此前在两个 dense GQA 模型上观察到的符号翻转一致。

## 五、结果二：能耗花在验证上，不在 draft 上

论文用了一个很干净的拆法来分离 draft 与 verify 的能量：保持验证的 token 数与形状不变，把第一步之后的 drafter 前向全部跳过，用第一步的 draft 反复验证。两次运行的差值就是 draft 的能量。

结论很一致：**在 dense 模型上，验证吃掉 decode 能量的大头**。没有任何 drafter 超过 45%，块式 drafter 最多 23%；即使把块式 drafter 的成本砍半，decode 能量最多降 12%。EAGLE3 在 Qwen3 系列上占比最大（43% 到 45%），因为它每 draft 一次要串行跑 7 趟小前向；assistant 只占 8%，但它的接受长度也短。

这条结论直接改写优化优先级：想让投机解码更省电，先看验证侧的形状（验证多少 token、batch 多大），而不是先想着把 drafter 做小。在 MoE 上这个拆法失效——每个被验证的 token 会路由到自己的专家，把 draft 换成随机 token，验证能耗最多变化 52%，说明成本取决于「验证了哪些 token」而不只是「验证了几个」。

![figure05](https://pic4.zhimg.com/v2-1264da53f896c921a2ffb2173ccef45d_1440w.jpg)

图 3：左：能耗节省与每次验证被接受 token 数的关系（按 batch 着色），同一个 batch 下接受越多越省；右：B=1 与 B=64 时 decode 能量在 draft 与 verify 之间的切分，验证始终占大头。

同一个 batch 内，接受 token 数确实能预测能耗排序：332 对同模型方案里 287 对成立；不成立的 45 对中有 44 对是「接受更多、但验证的 token 也更多」的组合（通常是块式对头式）。所以正确的最小指标是**二元组**：每次验证接受的 token 数，加上每次验证实际验证的 token 数。

## 六、结果三：越过平衡点，节省就变成亏损

投机解码的教科书解释是「把工作点往 roofline 右侧推」。论文用硬件计数器实测了算术强度（分子是实际执行的运算量，含 tensor core padding；分母是整个 decode 步的内存流量），得到两个反直觉的结论。

第一，**只增加验证 token 数，几乎推不动工作点**。单流下每种方案都只在基线附近几个百分点内。真正把工作点推上去的是 batch 与验证 token 数的组合。

第二，**越过平衡点不是收益，而是收益结束的地方**。在 Qwen3-4B 上（260 token 上下文），DFlash-16 在 batch 32 达到 H100 的平衡点、batch 16 达到 H200 的平衡点；DSpark-7 验证的 token 不到一半，在 H100 上到 batch 64 都还在平衡点下方，但在 H200 上从 batch 32 就越过去了。而在越过平衡点后的**一个 batch 倍增之内，节省就翻成负数**：DFlash-16 在 H100 上于 batch 16 到 32 之间翻正，在 H200 上于 batch 16 翻正。原因很朴素——DFlash-16 每次验证 16 个 token，其中被接受的不到 3 个，一旦权重读取不再能掩盖这些算术时间，被拒绝的 13 个 token 的算术就成了纯开销。

![figure06](https://pica.zhimg.com/v2-ea7add174faf6890bd61498582a137f2_1440w.jpg)

图 4：Qwen3-4B decode 步的算术强度随 batch 变化（上），与同一批 drafter 在两个 GPU 上的能耗节省（下）；填充色表示该 batch 已越过对应 GPU 的平衡点。

工程含义很直接：**在 H100 上调好的 draft 长度，搬到 H200 上不成立**。H200 每单位算力的带宽更高，平衡点更低，同样的 draft 长度会更早把验证推进 compute-bound 区间，节省更早消失。论文里 DSpark-7 就是活例：H100 上 batch 64 仍然省电，H200 上同一配置已经在亏。

## 七、结果四：训练方式决定鲁棒性，比「谁训的」更重要

投机解码的收益高度依赖被服务的文本。论文在五个池子上重复了完整扫描：

**对话比代码难预测**，对每一个 drafter 都成立，连免训练的 n-gram 也一样。掉多少跟训练方式强相关：与模型联合训练的 MTP 头掉得最少（GLM-4.7-Flash 的头在两个池子上节省完全相同）；post-hoc 训练的 drafter 掉得多；越专用的掉得越狠——为 Qwen3-Coder 训练的 DFlash 在代码上每次验证接受 5.9 个 token，在对话上只有 2.0 到 3.0 个，batch 64 时代码上省 51%、对话上直接亏钱。

在 batch 64 上，各模型的最大节省在对话上比代码上中位数低 11 个百分点。

**长文档**上答案大量抄 prompt，n-gram 在 gemma 上的接受长度反而高于代码——这印证了 Spec-Bench 关于 lookup drafting 的观察。

语言维度更锋利。论文选了罗曼什语（Romansh，低资源语言，没有任何模型把它列进支持语言，也没有任何 post-hoc drafter 的训练集包含它）：

![figure03](https://picx.zhimg.com/v2-346ff642cff7cceb46fc4ded7e36b951_1440w.jpg)

图 5：罗曼什语相对英语的接受长度比，与 batch=1 时的能耗节省；颜色区分 drafter 的训练方式（联合训练 / 厂商 post-hoc / 第三方 post-hoc / 免训练）。

在三个「同一个模型上同时有多种来源 drafter」的例子里，结果跟着**训练时机**走，而不是跟着「块式还是头式」「谁训的」走：GLM-4.7-Flash 与 Qwen3.6-35B-A3B 上，联合训练的 MTP 头保留了英文接受长度的 81% 到 84%，post-hoc drafter 只剩 70%。gemma-4-12B-it 上，Google 自己训的 assistant 只保留 66% 到 69%，和第三方 DFlash 一样——它是 post-hoc 的，表现就按 post-hoc 算。

## 八、结果五：投机能替代多少 batching

一个常被问的问题是「既然投机解码省电，那还要不要加 batch」。论文把两者放在同一张图上：

投机运行服务 1 个请求，其 EPOT 相当于基线服务 2 到 8 个请求（视模型而定）。

反过来，投机运行服务 32 个请求时，基线在任何模型上都需要至少 64 个请求才追平；11 个模型里有 5 个，即使基线开到 64（论文的上限），EPOT 仍高于投机 32 的配置。

但两者的适用场景几乎正交。在 dense 模型上，batch 增大时基线轨迹近乎垂直下落（EPOT 降一个数量级），单用户速度基本不变；投机解码把轨迹向右推（单用户速度提高 1.3 到 4.3 倍），能量收益随 batch 衰减。

![figure04](https://picx.zhimg.com/v2-47d244599dbe33315f8b9879a22f0fa7_1440w.jpg)

图 6：每 token 能耗 vs 单用户吞吐，每条轨迹从 batch=1（空心标记）走到 batch=64 或引擎能撑住的最大 batch。

论文还给了一个否定的结果：**DVFS 的腾挪空间很小**。在 H200 上把 SM 时钟锁到 1500 MHz，无投机时能省 4% 到 11% 的能量（代价是 3% 到 7% 吞吐）；但一旦开了投机（DSpark-7 或 DFlash-16，batch 16 以上），GPU 本来就在 1450 到 1700 MHz 之间跑，同样的时钟锁几乎不省能量。想把延迟目标保住又靠降频省电，这条路在投机解码打开后基本被堵死。

## 九、工程建议：怎么选 drafter、draft 多长、什么时候别用

**选 drafter 要看 batch。** 单流时块式 drafter 在 9 个有块式 drafter 的模型里领先 7 个（关掉 capture 时 9 个全领先），因为它每次验证接受的 token 最多。但在同时有两种 drafter 的 5 个模型上，**大 batch 时全部是头式 drafter 更省**：块式一次验证 16 个 token，头式只验证 4 到 6 个，batch 一大，多验证的那 10 来个 token 的算术成本就超过了多接受几个 token 的收益。

**draft 长度宁可短。** 在 gemma-4-31B-it 上把 n-gram 的 draft 数从 1 扫到 32：单流时 draft 越多越省，但从 batch 4 起 4 个 token 最省，到 serving batch 时**任何** draft 数都亏，32 最亏。两个 MoE 模型更极端，单流下任何 draft 数都亏。**over-drafting 才是主要失败模式**，在单流 dense 上调出来的 draft 长度，加 batch 时必须往下砍。

**注意回滚缓冲。** 在状态空间混合架构上，回滚一个被拒的 draft 不是丢 KV 条目那么简单：循环状态已经把被拒 token 吸收进去了，引擎必须为每个请求的每个 draft token 保存一份状态副本。在 Qwen3.6-27B 上，batch 16 时这份缓冲约为 drafter 权重的 10 倍，DFlash-16 直接起不来（不是慢，是 OOM 失败），而只验证 4 个 token 的 MTP 头能把 Qwen3.6-35B-A3B 撑到 batch 64。**在循环架构上部署投机解码，要为 draft 数乘 batch 预留内存，而不只是为 drafter 权重。**

**CUDA graph 必须打开测。** 关闭 capture 时，MoE 模型上投机的「节省」会被高估 19 到 39 个百分点（dense 模型不到 10 个点），而且会改变结论：在 Qwen3.6-35B-A3B 和 gemma-4-26B-A4B-it 上，关 capture 时块式 DFlash 最省，开 capture 后变成 MTP 头最省；n-gram 在关 capture 时每个模型都省电，开 capture 后在每个 MoE 上都亏。

## 十、测量陷阱：每一个都能让结论反转而不留痕迹

论文专门列了一节「测量陷阱」，值得所有做推理 benchmark 的人当清单用。它们的共同形态是：运行成功、结果文件格式正确、数字看起来合理，但配置已经不是你以为的那个。

**请求的 batch 与实际跑的 batch 不是一回事。** 引擎自己解析并发度，结果文件把两者写在不同字段里。

**batch 超过 prompt 池大小时，重复的 prompt 共享前缀缓存**，测到的是前缀复用而不是 batching。

**没套 chat template**：对指令微调模型直接喂原始 prompt，n-gram 在 gemma 上的节省会被高报最多 117 个百分点，JoyAI-LLM-Flash 的 MTP 头会被低报 12 个百分点。

**profiler 窗口在请求还在进入时打开**，把 prefill 算进了 decode。

**phase marker 记的是 host 进入阶段的时间，不是 GPU 执行的时间**，会把验证的 GPU 时间记到 draft 头上。

**结果写入器按已有表头逐列匹配**，表头没有的列（往往正是「这行是在什么条件下测的」）会被静默丢掉。

**结果行没写 GPU 型号**，H100 与 H200 的数据混在一起；同一个请求 batch 在一张卡上跑满、在另一张卡上跑不满。

**不尊重 EOS**：生成越过答案末尾后会重复文本，而重复文本对 drafter 极好预测，接受长度虚高。论文的代码 prompt 中位答案超过 700 token，所以 512 token 的生成始终落在答案内部。

## 十一、批判性评估

这篇论文的强项是方法论：配对基线、capture 开关的对照实验、per-seed 配对的节省统计、以及把「draft / verify」真正拆开的构造。它给出的不是「投机解码省 X%」这种单点结论，而是一张「在什么条件下省、为什么省、什么时候反过来亏」的地图。

局限也清楚：

roofline 部分只覆盖 Qwen3-4B 一个模型，其他模型的平衡点结论是外推。

batch 上限 64（受 prompt 池限制），真实在线服务常见的目标并发可能更高；长上下文下 KV cache 会让大 batch 仍处于内存受限，论文自己也指出此时投机的加速可能随 batch 增长（MagicDec 的结论），与本文的短上下文结论方向相反。

延迟指标是整段生成的平均 TBT，没有 p99；而线上 SLO 通常看尾延迟。

能耗计数器只覆盖 GPU 板卡，不含 host、内存、网络与制冷——这对 n-gram（匹配跑在 host 上）是有利的偏差。

只测了 SGLang 一个引擎，vLLM 的调度与 kernel 选择不同，绝对值不能直接搬。

MoE 上没能给出 draft / verify 的能量拆分，因为验证成本依赖「验证了哪些 token」。

但即便有这些限制，它给工程实践的三条结论是稳的：**延迟受限的服务用投机解码是为了延迟，不是为了电；能耗受限的服务应该先加 batch，再看 drafter 还能不能省；而任何 draft 长度与 drafter 选择，都必须绑定「GPU 型号 + batch + 服务文本」这三件事重新测一遍。**
