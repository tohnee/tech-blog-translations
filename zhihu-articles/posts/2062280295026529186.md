## 1. 什么是 InfiniBand？

InfiniBand（简称 IB）是一种高性能、低延迟的互连技术，最初由 InfiniBand Trade Association（IBTA）于 1999 年提出，现已成为 NVIDIA（通过收购 Mellanox）主导的高性能计算（HPC）和 AI 数据中心网络标准。它专为大规模并行计算、存储网络和 AI 训练集群设计，提供远超传统以太网的吞吐量和确定性延迟。

![](https://pic1.zhimg.com/v2-2177a65ebb40ead3bca6065265c9fe10_r.jpg)

> 另外，我撰写的**大模型相关的博客及配套代码**均整理放置在Github：[llm-action](https://github.com/liguodongiot/llm-action/tree/main)，有需要的朋友自取。<br>

**核心优势**：

| 特性 | InfiniBand | 传统以太网 |
| --- | --- | --- |
| 延迟 | 亚微秒级（~600ns） | 微秒级（~10μs+） |
| 流控 | 基于信用的无损流控（原生） | 需 PFC/ECN 配置 |
| CPU 卸载 | 硬件 RDMA + 内核旁路 | 软件 TCP/IP 协议栈 |
| 路由 | LID 预计算，集中式 SM | MAC/IP 分布式学习 |
| 管理 | Subnet Manager 集中配置 | 逐交换机或控制器管理 |
| 适用场景 | HPC、AI 训练、高性能存储 | 通用云计算、混合负载 |

## 2. InfiniBand 技术原理

### 2.1 OSI 分层模型映射

InfiniBand 采用四层协议栈，与 OSI 模型对应关系如下：

```text
┌─────────────────────────────────────────────────────────────┐
│  传输层 (Transport Layer)                                     │
│  ├─ RC (Reliable Connection)      可靠连接，类似 TCP           │
│  ├─ UC (Unreliable Connection)   不可靠连接                  │
│  ├─ UD (Unreliable Datagram)      不可靠数据报，类似 UDP       │
│  ├─ RDMA 操作 (Write/Read/Atomic) 远程直接内存访问             │
│  └─ 内核旁路 (Kernel Bypass) + 零拷贝 (Zero Copy)            │
├─────────────────────────────────────────────────────────────┤
│  网络层 (Network Layer)                                       │
│  ├─ Subnet Manager (SM)           子网管理器，集中式控制       │
│  ├─ LID (16-bit) / GID (128-bit)  本地/全局标识符              │
│  ├─ GRH (Global Route Header)      全局路由头                  │
│  ├─ PKey (Partition Key)           分区隔离                   │
│  └─ SMA (Subnet Manager Agent)     设备内嵌管理代理            │
├─────────────────────────────────────────────────────────────┤
│  链路层 (Link Layer)                                          │
│  ├─ 基于信用的流控 (Credit-Based Flow Control)                 │
│  ├─ LRH (Local Route Header)       本地路由头                  │
│  ├─ 虚拟通道 (Virtual Lanes, VL)   QoS 服务质量                │
│  ├─ 链路级重传 (Go-Back-N / Selective)                       │
│  └─ CRC 校验                      端到端数据完整性             │
├─────────────────────────────────────────────────────────────┤
│  物理层 (Physical Layer)                                      │
│  ├─ HCA (Host Channel Adapter)     主机通道适配器 (网卡)       │
│  ├─ 交换机 (Quantum-2 / Quantum-X800)                        │
│  ├─ 线缆 (DAC / AOC / 光模块)                                  │
│  ├─ 速率: NDR 400G / XDR 800G / GDR 1.6T                     │
│  └─ 编码: PAM4 / NRZ                                           │
└─────────────────────────────────────────────────────────────┘

```

### 2.2 RDMA（远程直接内存访问）

RDMA 是 InfiniBand 的核心技术，允许一台主机直接读写另一台主机的内存，无需操作系统内核介入。

**RDMA 三种操作模式：**

| 操作 | 说明 | 应用场景 |
| --- | --- | --- |
| RDMA Write | 发送方将数据直接写入接收方内存 | 大规模数据广播 |
| RDMA Read | 发送方直接从接收方内存读取数据 | 分布式参数服务器 |
| RDMA Atomic | 原子操作（Compare-and-Swap / Fetch-and-Add） | 分布式锁、计数器 |

**RDMA 的优势：**

- **零拷贝**：数据直接从网卡 DMA 到用户空间内存，无需经过内核缓冲区
- **内核旁路**：应用程序通过 Verbs API 直接与网卡交互，绕过系统调用开销
- **CPU 卸载**：网络协议处理完全由网卡硬件完成，释放 CPU 用于计算

### 2.3 基于信用的无损流控（Credit-Based Flow Control）

InfiniBand 的链路层采用**基于信用的流控机制**，确保网络不会出现丢包：

1. 接收端维护一个**信用计数器**（Credits），表示当前可接收的数据量
2. 发送端只有在拥有足够信用时才能发送数据
3. 接收端处理完数据后，通过 ACK 返回新的信用
4. 交换机内部同样维护信用，实现端到端无损传输

这与以太网的 PFC（Priority Flow Control）形成鲜明对比——后者是"尽力而为"基础上的补救措施，而 InfiniBand 的流控是架构原生设计。

### 2.4 Subnet Manager（子网管理器）

SM 是 InfiniBand 网络的大脑，负责：

- **拓扑发现**：通过 SMA 扫描全网设备
- **LID 分配**：为每个端口分配 16 位本地标识符
- **路由计算**：基于拓扑预计算最优路径（Fat-Tree、Dragonfly+ 等）
- **分区配置**：通过 PKey 实现网络隔离
- **QoS 设置**：配置虚拟通道和服务等级
- **故障检测与重收敛**：链路故障时快速重新计算路由

> ⚠️ **重要**：SM 是单点故障源，生产环境必须部署主备 SM 实现高可用。<br>

## 3. InfiniBand 架构详解

### 3.1 核心组件

InfiniBand 是一种基于通道的结构，组成单元主要分为四类：

- HCA（Host Channel Adapter，主机通道适配器）
- InfiniBand link（连接通道，可以是电缆或光纤，也可以是板上链路）
- InfiniBand交换机和路由器（组网用的）
- TCA（Target Channel Adapter，目标通道适配器）

![](https://pica.zhimg.com/v2-255b97c6e8fa4b3c6364f36722beb3d8_1440w.jpg)

### 3.2 HCA（Host Channel Adapter）— 主机通道适配器

HCA 是 InfiniBand 的网卡，当前主流产品：

| 型号 | 速率 | 代际 | 端口 | 适用场景 |
| --- | --- | --- | --- | --- |
| ConnectX-6 | 200G | HDR | 1/2 | 上一代 HPC |
| ConnectX-7 | 400G | NDR | 1/2 | H100/H200 GPU 集群 |
| ConnectX-8 | 800G | XDR | 1/2 | 前沿 AI 训练集群 |

HCA 支持 VPI（Virtual Protocol Interconnect）技术，可在 InfiniBand 和以太网模式间切换。

### 3.3 交换机

| 型号 | 端口数 | 速率 | 总吞吐 | 定位 |
| --- | --- | --- | --- | --- |
| Quantum-2 | 64 | NDR 400G | 51.2 Tbps | 主流 AI 集群 |
| Quantum-X800 | 144 | XDR 800G | 115.2 Tbps | 前沿 AI 集群 |

![](https://picx.zhimg.com/v2-ed09d5b33738a2f1f10378943996d949_r.jpg)

### 3.4 线缆与光模块

| 类型 | 距离 | 功耗 | 适用场景 |
| --- | --- | --- | --- |
| DAC（无源铜缆） | <3m | 极低 | 机架内连接 |
| ACC（有源铜缆） | <7m | 低 | 机架间短距 |
| AOC（有源光缆） | <100m | 中 | 数据中心内部 |
| 光模块（OSFP） | <2km | 高（20-30W@800G） | 跨机房 |

> 注意：XDR 800G 光模块功耗可达 20-30W，一个满载 144 端口的 Quantum-X800 交换机仅光模块热耗就超过 2000W，散热设计必须充分考虑。<br>

![](https://pic4.zhimg.com/v2-994f2c458b5bd0fbc10f703acdf37cc5_r.jpg)

## 4. 组网拓扑

### 4.1 Fat-Tree（胖树）拓扑

最常用的 InfiniBand 拓扑，特点：

- 任意两个节点间存在多条等长路径
- 无阻塞（Non-blocking）或近似无阻塞
- 易于扩展，适合大规模集群

![](https://pic2.zhimg.com/v2-cc26425cdcfabf6ee4ac8d12caefe101_1440w.jpg)

**典型三层结构：**

- **Core 层**：核心交换机，负责跨 Pod 通信
- **Spine 层**：汇聚交换机，连接 Core 和 Leaf
- **Leaf 层**：接入交换机，直接连接服务器

### 4.2 Rail-Optimized 拓扑

专为 AI 训练优化的拓扑，NVIDIA DGX SuperPOD 采用：

- 同一 Rail（轨道）上的 GPU 通过 Leaf 交换机直连
- 跨 Rail 通信通过 Spine/Core 层
- 最小化 All-to-All 通信的跳数

## 7. 性能调优建议

1. **CPU 亲和性**：将 RDMA 应用绑定到与 HCA 同一 NUMA 节点的 CPU
2. **巨页内存**：启用 HugePages 减少 TLB miss
3. **中断聚合**：调整 HCA 中断合并参数，减少 CPU 中断开销
4. **QoS 配置**：为不同业务流分配独立 Virtual Lane
5. **拓扑优化**：采用 Rail-Optimized 拓扑减少 AllReduce 通信跳数

## 8. NCCL 中使用 InfiniBand 与 SHARP

### 8.1 NCCL 与 InfiniBand 的集成架构

NCCL（NVIDIA Collective Communications Library）是分布式 GPU 训练的核心通信库，负责在多个 GPU 间执行 AllReduce、AllGather、Broadcast 等集合通信操作。当训练规模跨越单节点时，NCCL 通过 InfiniBand 实现跨节点高速互联。

**NCCL 的传输层架构：**

```text
┌─────────────────────────────────────────────────────────────┐
│  PyTorch / TensorFlow / JAX                                 │
│  └─ torch.distributed / Horovod / Megatron-LM               │
├─────────────────────────────────────────────────────────────┤
│  NCCL API (ncclAllReduce, ncclBroadcast, ...)               │
├─────────────────────────────────────────────────────────────┤
│  NCCL 内部传输层                                              │
│  ├─ NVLink Transport      ← 节点内 GPU 互联                  │
│  ├─ P2P Transport         ← 节点内 PCIe 直连                 │
│  ├─ NET/IB Transport      ← 跨节点 InfiniBand (IB Verbs)     │
│  │   └─ IB Verbs (libibverbs) → RDMA QP (Queue Pair)        │
│  │   └─ GPUDirect RDMA    ← GPU 内存 ↔ HCA 零拷贝           │
│  └─ NET/Socket Transport  ← 回退 TCP/IP (性能差)             │
├─────────────────────────────────────────────────────────────┤
│  HCA (ConnectX-7/8) → InfiniBand Fabric → Remote HCA        │
└─────────────────────────────────────────────────────────────┘

```

NCCL 在初始化阶段会自动探测拓扑：查询 PCIe 总线发现 GPU 位置、NVLink 连接关系、NIC 与 PCIe Switch 的亲和性，构建内部图结构，然后选择最优通信路径。

### 8.2 GPUDirect RDMA：零拷贝跨节点通信

GPUDirect RDMA 是 NCCL 在 InfiniBand 上实现高性能的关键技术，它允许 HCA 直接读写 GPU 显存，无需经过 CPU 内存中转。

**启用条件：**

1. HCA 支持 GPUDirect（ConnectX-5 及以上）
2. 加载 `nvidia_peermem` 或 `nvidia_p2p` 内核模块
3. GPU 与 HCA 位于同一 PCIe Switch 下（最佳）或同一 NUMA 节点

**验证 GPUDirect 是否生效：**

```text
# 检查 nvidia_peermem 模块
lsmod | grep nvidia_peermem

# NCCL 日志中查看 GDR 状态
NCCL_DEBUG=INFO NCCL_NET_GDR_LEVEL=5 python train.py 2>&1 | grep GDR
# 应出现: "NET/IB : GPU Direct RDMA enabled"

```

**关键环境变量：**

| 变量 | 默认值 | 推荐值 | 说明 |
| --- | --- | --- | --- |
| NCCL_NET_GDR_LEVEL | 2 | 5 | GDR 启用深度，5 表示所有跨节点通信都使用 GDR |
| NCCL_IB_GID_INDEX | 0 | 3 | RoCEv2 需要设为 3，InfiniBand 通常保持默认 |
| NCCL_IB_HCA | 全部 | mlx5_0,mlx5_1 | 指定使用的 HCA 端口，避免非 IB 设备干扰 |
| NCCL_IB_PCI_RELAXED_ORDERING | auto | 1 | 启用 PCIe Relaxed Ordering（PCIe宽松排序）功能，可提升 6 倍以上性能 |

NCCL_IB_PCI_RELAXED_ORDERING 是一个针对虚拟化环境中InfiniBand网络的性能优化开关。默认情况下，NCCL_IB_PCI_RELAXED_ORDERING 使用严格排序（Strict Ordering）。在严格排序下，PCIe总线上的数据包必须严格按照发送顺序到达目的地。这虽然确保了数据一致性，但在某些场景下可能造成不必要的等待，降低总线利用率。而宽松排序则允许数据包在一定程度上“超车”，不受严格顺序束缚。这能提高PCIe总线的利用率，减少数据重传，从而提升网络通信性能。此功能要求使用 Mellanox ConnectX-5 或更新型号的网卡。

这项优化在虚拟化环境（如公有云VM）中效果尤其明显。

- 虚拟机中的I/O路径更长，涉及更多地址转换步骤（如PCIe的ATS，即地址转换服务）。
- 这些额外的步骤会使严格的排序更容易成为性能瓶颈。开启宽松排序可以缓解此瓶颈，带来可观的性能提升。

因此，在Azure、DGX Cloud等云环境的A100 GPU集群上，官方推荐配置中常会包含此设置。在 Azure HPC 等环境中可带来超过 6 倍的 AllReduce 性能提升（从 25GB/s 提升到 188GB/s）。

由于在物理机（裸金属）环境，I/O路径更直接，排序开销本身较小，开启此功能通常没有明显性能提升。有时，官方甚至会建议在某些物理机环境下将其设为 0 来避免潜在问题。

### 8.3 SHARP：网内聚合与规约（In-Network Reduction）

具体请看之前的文章：[NVIDIA SHARP 技术解析：通过网络内计算提升分布式通信性能](https://zhuanlan.zhihu.com/p/2060851766304970672)

### 8.3.1 为什么需要 SHARP？

在标准 Ring 或 Tree AllReduce 中，每个 GPU 需要：

1. **ReduceScatter 阶段**：将梯度分块发送给邻居，逐轮累加，耗时 O(N) 轮
2. **AllGather 阶段**：将聚合结果广播给所有 GPU，再耗时 O(N) 轮

当集群规模扩大到 64+ 节点时，通信轮次成为瓶颈。SHARP（Scalable Hierarchical Aggregation and Reduction Protocol）将 Reduce 计算卸载到 InfiniBand 交换机硬件中执行。

![](https://pica.zhimg.com/v2-056212359f87f4fca44e1073b0945046_r.jpg)

### 8.3.2 SHARP 工作原理

SHARP 的核心思想是：**让交换机代替 GPU 完成梯度聚合**。

```text
传统 AllReduce (Ring):
  GPU0 → GPU1 → GPU2 → GPU3 → ... → 回到 GPU0
  每轮传递 + 本地 Reduce，共 2(N-1) 轮

SHARP AllReduce:
  GPU0 ──┐
  GPU1 ──┼→ [SHARP Switch] ──→ 聚合结果 A+B+C+D ──→ 所有 GPU
  GPU2 ──┤         ↑
  GPU3 ──┘    交换机内硬件 Reduce
  仅需 2 轮（发送 + 广播），通信量近乎减半

```

**SHARP Tree 逻辑结构：**

- 基于物理 Fat-Tree 拓扑构建逻辑 SHARP Tree
- 一个交换机最多可参与 64 个 SHARP Tree
- 每个 SHARP Tree 可建立大量 Group（基于现有 Host 的子集）
- 支持数百个集合通信 API 并发执行

### 8.3.3 SHARP 版本演进

| 版本 | 交换机要求 | 新特性 |
| --- | --- | --- |
| SHARP v1 | EDR/HDR | 基础 AllReduce 卸载 |
| SHARP v2 | Quantum-2 (NDR) | 更大聚合树、多租户隔离 |
| SHARP v3 | Quantum-X800 (XDR) | FP8/FP16 低精度支持、更大聚合树、增强多租户隔离 |

SHARP v3 随 Quantum-X800 Q3400 交换机发布，针对 B200/B300 时代的 FP8 训练做了专门优化。

### 8.4 SHARP 配置与启用

### 8.4.1 硬件与软件前提

- **交换机**：NVIDIA Quantum-2 (NDR) 或 Quantum-X800 (XDR)
- **HCA**：ConnectX-7 (NDR) 或 ConnectX-8 (XDR)
- **驱动**：MLNX_OFED 5.4+ 或最新 LTS
- **NCCL**：2.19+（支持 `CollNet` 算法）
- **插件**：`nccl-rdma-sharp-plugins`（NVIDIA 官方插件）

按照前文教程安装了 MLNX_OFED ，SHARP 所需的底层库（libsharp、sharpd 守护进程）已经包含在内，无需单独安装。具体参考：[https://networking-docs.nvidia.com/mlnxenswum/23104091lts/legal-notices-and-3rd-party-licenses](https://networking-docs.nvidia.com/mlnxenswum/23104091lts/legal-notices-and-3rd-party-licenses)

在聚合管理器节点启动sharp_am。

```text
# 查看日志

```

其中，sharp_am.cfg 配置如下所示：

```text
# /etc/sharp/sharp_am.cfg
# SHARP Aggregation Manager 配置文件

# SM 相关配置
sm_guid 0x0002c90300abcdef  # 主 SM GUID
sm_priority 15              # SM 优先级

# 拓扑与路由

sharp_tree_type sat          # 默认使用 SAT（流式聚合）

# 资源限制

max_groups_per_tree 64       # 每棵树最大组数
max_qps_per_group 1          # 每组 QP 数

# 日志与调试
log_level INFO
log_file /var/log/sharp/sharp_am.log

```

SHARP 使用 UD（Unreliable Datagram）多播进行结果分发，需确保 IPoIB 多播正常：

```text

#           BOOTPROTO=none
```

### 8.5 NCCL + IB 的完整调优清单

### 8.5.1 算法选择

| 场景 | 推荐 NCCL_ALGO | 说明 |
| --- | --- | --- |
| ≤32 GPUs 单集群 | Ring | 带宽最优，链路负载均衡 |
| >32 GPUs 或跨机架 | Tree | 延迟更优，根节点链路负载高 |
| SHARP 交换机可用 | CollNet | 网内聚合，通信量减半 |
| NVLink + IB 混合 | NVLS | Hopper+ GPU 的 NVLink SHARP |

### 8.5.2 协议选择

| 场景 | 推荐 NCCL_PROTO | 说明 |
| --- | --- | --- |
| InfiniBand 跨节点 | Simple | 高带宽场景开销最低 |
| NVLink 节点内 | LL128 | 128 字节低延迟变体 |
| 小消息 (<1KB) | LL | Low Latency 协议 |

```text

module load mpi/hpcx
```

### 8.6 常见问题排查

| 问题 | 诊断 | 解决方案 |
| --- | --- | --- |
| SHARP 未生效 | NCCL_DEBUG 无 CollNet 字样 | 检查交换机固件是否支持 SHARP；确认 NCCL_COLLNET_ENABLE=1 |
| GDR 未启用 | 日志中 GPU Direct RDMA disabled | 加载 nvidia_peermem；检查 PCIe 拓扑 |
| IB 连接失败 | ibstat 显示 Port Down | 检查物理连接；确认 SM 运行；验证子网配置 |
| 性能不达预期 | all_reduce_perf 带宽低 | 启用 NCCL_IB_PCI_RELAXED_ORDERING=1；检查 NUMA 绑定 |
| SHARP 初始化失败 | sharp_coll_init 报错 | 确认 HPC-X 或 sharp 插件版本匹配；检查交换机 SHARP 许可 |

## 10. 总结

NVIDIA InfiniBand 凭借其原生无损传输、硬件 RDMA 和集中式子网管理，成为 AI 训练和高性能计算的事实标准。从 NDR 400G 到即将推出的 GDR 1.6T，InfiniBand 持续推动着数据中心网络性能的边界。对于需要极致网络性能的集群，InfiniBand 仍然是无可替代的选择。尽管以太网通过 RoCEv2 不断追赶，但在延迟确定性和部署简便性上，InfiniBand 的架构优势依然明显。

而InfiniBand 与 NCCL 的结合是当代大规模 AI 训练的基石。通过 GPUDirect RDMA 实现零拷贝跨节点通信，再通过 SHARP 将集合通信的 Reduce 计算卸载到交换机硬件，NCCL 能够在数千 GPU 规模下仍保持接近线性的扩展效率。
