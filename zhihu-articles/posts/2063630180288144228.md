## **一、RAG 是什么：从一个真实的尴尬开始**

场景一：你在用 AI 助手处理公司业务，问它"我们的新产品 SKU-2026-A 的退换货政策是什么"，它给了你一个听起来很专业、实际上是凭空捏造的答案。

场景二：你问它昨天发生的事，它说"我的训练数据截止到……"，然后礼貌地拒绝你。

场景三：你问它一篇根本不存在的论文，它给你编出了完整的标题、作者、摘要，甚至 DOI 号——全是假的，但语气笃定。

这三个场景背后是同一个根本问题：大模型是静态的参数记忆，它所有的"知识"都封印在训练时的权重里，对三类信息天生无能为力：

| 缺陷类型 | 具体表现 | 典型危害 |
| --- | --- | --- |
| 知识有截止日 | 训练后发生的事一概不知 | 答案过时，给出错误决策依据 |
| 私有数据盲区 | 从未见过你公司的内部文件 | 无法支撑企业知识问答 |
| 幻觉式编造 | 不知道却假装知道，一本正经说假话 | 在医疗/法律/金融场景是致命风险 |

RAG（Retrieval-Augmented Generation，检索增强生成） 就是为了直接解决这三个问题而生的。它的核心逻辑只有一句话：

> 在模型回答之前，先去知识库里找出相关资料，把资料和问题一起喂给模型，让模型"有据可答"而非"凭空作答"。

**一个新的比方：AI 医生的诊断模式**

把大模型想象成一位医学院毕业的医生。他读了医学院里所有的教材（预训练数据），记忆力惊人，理解能力极强。但他毕业以后就没有再看过任何文献，也从来没见过你这家医院的患者档案。

现在你让他给一个复杂病人看诊：

- 纯 LLM 模式：只靠记忆，给出一个基于多年前知识的判断。可能大方向对，但细节可能已经被新指南推翻，也不了解病人的个人病史。
- RAG 模式：先调取病人的历史病历、最新检查报告、最新临床指南，再结合自己的医学知识综合判断。有据可查，也可以被质疑和核实。

RAG 把模型从"只靠记忆"升级为"记忆 + 即时查阅"——这也是为什么它成为企业 AI 落地的标配方案。

```text
📷 图片提示词 1手绘涂鸦风格信息图，横版 16:9，浅米色/奶油黄背景（#F5F0E8）。左侧：一个带锁图标的大脑，标注"静态记忆——仅靠训练知识"，周围散布问号和 ❌ 标签，分别写"知识过期"、"私有数据缺失"、"幻觉编造"。右侧：同一个大脑，通过箭头连接一本翻开的书/文件夹，标注"RAG——先检索再回答"，旁边 ✅ 标签写"实时知识"、"私有文档"、"可追溯验证"。中间用一个粗大的 ➜ 箭头分隔，文字写"RAG 改变了工作流"。整体像技术科普插画，钢笔勾线加淡彩填色，标注文字均为手写体风格。
```

> ⚠️ RAG 的能力边界 
>  RAG 解决的是"模型缺特定知识"的问题。它改变不了模型自身的推理深度（模型本来就逻辑弱，给再多资料也白搭）、改变不了输出风格（那是微调的活），也无法保证 100% 准确——检索到错误文档、模型曲解文档，幻觉照样发生。准确定位：一种让模型基于真实、可更新知识回答的工程方案。

## **二、整体运转机制：两条流水线**

很多人以为 RAG 就是"检索 + 生成"，实际上它由两条各自独立的流水线构成，分工和时序完全不同。

**流水线一：离线索引（建库 · 慢慢做）**

这一步相当于"备考前整理资料"——把你所有的文档整理成可以被快速检索的格式。只要知识库不变，这步不需要重复执行。

```text
文档加载 → 文档切割 → 向量化(Embedding) → 存入向量数据库
```

文档加载：支持 PDF、Word、PPT、HTML、Markdown、数据库等各种格式，统一转成纯文本。这步最麻烦的是带表格、图片、多栏排版的 PDF——解析质量直接影响下游一切。

文档切割（Chunking）：这是最容易被低估的关键步骤，后面单独展开讲。

向量化：用 Embedding 模型把每段文字转成一个高维数值向量。向量的作用是把语义编码成几何距离——语义相近的两段话，在向量空间中的距离也近。比如"发烧头疼"和"体温升高、头部疼痛"在向量空间里挨在一起；和"Python 闭包原理"则离得很远。

存入向量数据库：建好支持毫秒级相似度检索的专用索引。

**流水线二：在线查询（答题 · 要快）**

用户每次提问都触发这条流水线：

```text
问题向量化 → 相似度检索 Top-K → 构造增强 Prompt → LLM 生成回答
```

问题向量化：用与索引阶段完全相同的 Embedding 模型把用户问题也转成向量（模型一致性至关重要）。

相似度检索：在向量数据库中找出与问题向量距离最近的 Top-K 个文档块。

构造增强 Prompt：把检索到的资料拼进提示词，格式大致如下：

```text
你是一个专业助手。请严格基于以下参考资料回答用户问题。
如果资料中没有相关信息，请如实说明，不要编造。
​
=== 参考资料 ===
[资料1] 公司年假政策：全职员工入职满一年享有10天带薪年假，
        可拆分使用，最少半天。
[资料2] 年假结转规定：当年未用完年假可结转至下年，上限5天。
[资料3] 特殊假期说明：试用期员工不计入年假资格。
​
=== 用户问题 ===
公司的年假怎么用？可以攒着用吗？
```

LLM 生成回答：模型基于真实资料作答，而非凭参数记忆发挥。

```text
📷 图片提示词 2手绘涂鸦风格信息图，横版 16:9，奶油白背景。画面分上下两条泳道。上方泳道标注"离线索引阶段（建知识库）"，用靛蓝色高亮：4 个方框依次用箭头串联——📄「加载文档（PDF/Word/HTML…）」→ ✂️「文档切割」→ 🔢「Embedding 向量化」→ 🗄️「存入向量数据库」。下方泳道标注"在线查询阶段（答题）"，用珊瑚红色高亮：4 个方框——❓「用户提问」→ 🔢「问题向量化」→ 🔍「相似度检索 Top-K」→ 💬「LLM 生成回答」。两条泳道之间用一个双向箭头 ↕ 连接，注释"必须使用同一个 Embedding 模型"。手写体标注，涂鸦技术插画风格。
```

> 这套最基础的"加载→切割→向量化→入库 | 提问→检索→增强→生成"流程叫做 Naive RAG（朴素 RAG）。 它是起点，也是所有高级技术的基础。

## **三、微调 vs RAG：到底怎么选**

"我想让模型更懂我的业务，是微调好还是 RAG 好？"这是企业落地时最常见的决策困惑。

**先理解两者的本质差异**

微调（Fine-tuning）：用你自己的业务数据继续训练模型，把知识和能力"烧进"模型的参数权重里。代价是一次性的训练成本（计算、时间、标注），但之后推理不需要额外检索，反应更快。

RAG：知识存放在外部数据库，模型本身不变，每次回答前去检索。知识更新只需改数据库，不用重训模型；但每次推理都有检索开销，prompt 也更长。

用一个生活比方：

- 微调像是参加了一个专项培训，结束后知识内化到脑子里，不需要查书就能答。但培训一旦结束，新知识就没进去了；下次更新要重新培训，代价不小。
- RAG 像是配了一个随身资料库，随时翻查。资料库可以随时更新、可以无限扩充，出错了还能直接找到是哪份资料出了问题。

**选型决策矩阵**

| 维度 | 微调 | RAG |
| --- | --- | --- |
| 知识更新频率 | 低频（月/年级别更新可接受） | 高频（每天甚至实时更新） |
| 知识可追溯性 | 弱（模型记忆，来源不透明） | 强（每条回答可追溯到原始文档） |
| 输出风格/格式 | 强项 ：能深度学习特定文风 | 较弱：风格取决于底座模型 |
| 私有数据体量 | 中等（太大难以全量微调） | 任意大（只要能存进知识库） |
| 初始成本 | 高（GPU 时间 + 数据标注） | 低（主要是 Embedding 建库） |
| 推理开销 | 低（无额外检索步骤） | 中（每次需检索 + 更长 prompt） |
| 幻觉风险 | 较高（模型可能记错或混淆） | 较低（有实际文档做约束） |

**实战结论**

大多数场景，优先 RAG。特别是：

- 回答必须严格引用特定文档（法律条款、产品手册、合同条款）
- 知识库频繁更新
- 需要回答有出处、可核验
- 私有数据体量大，全量微调成本不现实

这几类更适合微调：

- 需要特定输出风格（客服话术、特定行文格式）
- 需要模型学会某种"能力"而非"知识"（某种特殊编程框架的语法习惯）
- 数据量精炼且不常变，对推理延迟有极致要求

> 生产实践里最成熟的方案：微调 + RAG 组合。 先微调让模型适应你的领域和文风（学会行业术语、固定回答格式），再用 RAG 提供实时准确的知识。就像先送员工去岗前培训，再给他配一套随时可查的内部知识库。

## **四、文档切割：被严重低估的质量瓶颈**

在 RAG 系统里，有一步操作看起来最不起眼，实际上对最终质量影响最大——文档切割（Chunking）。

**为什么要切，切多大**

即使现代模型的上下文窗口已经达到了百万 token 级别，也不意味着可以把整个知识库一股脑塞进去，原因有三：

1. **1. 成本：API 按 token 计费，每次查询都塞几十万 token，账单会爆炸。**
2. **2. Lost-in-the-Middle（注意力走神）：研究发现，当上下文特别长时，模型对开头和结尾记得牢，中间部分经常被忽略。塞得多 ≠ 用得上。**
3. **3. 检索精度：你需要的是最相关的那一小段，而不是整本手册——精准检索出相关片段永远优于丢一堆上下文让模型自己找。**

切割是个两难困境：

- 切太小：每块语义信息太少，"公司全职员工入职满一年后享有"——后半句没了，完全无法理解。
- 切太大：检索时命中了 2000 字的块，但实际相关的只有其中 3 行，大量噪音拉低质量。

最佳实践：256–512 tokens 是最常用的起点，配合 10%–20% 的重叠区（Overlap）防止边界处信息割裂。

**五种切割策略（从简到精）**

**① 固定大小切割**

最朴素的方式：每 N 个字符/token 切一刀，不管内容。简单可预测，缺点是完全无视语义边界，可能截断一句话的中间。配合 Overlap 可以缓解但不能根治。仅适合快速原型验证。

**② 递归字符切割（生产首选）**

目前最广泛使用的方法，LangChain `RecursiveCharacterTextSplitter` 的核心逻辑。

核心思路：维护一个分隔符优先级列表，从最粗粒度到最细粒度依次尝试：

```text
优先级: ["/n/n", "/n", "。", "！", "？", "；", "，", " "]
```

先按段落（双换行）切，如果块还是太大，再按单换行切，还太大再按句号……直到块大小达标为止。保证了在合理范围内尽量切在自然边界。

起步配置： `chunk_size=512, chunk_overlap=64` ，覆盖大多数通用文档场景。

**③ 基于文档结构切割**

利用文档自身格式：Markdown 按 `#` 层级标题切、代码文件按函数/类定义切、HTML 按标签结构切、表格按行切。

好处是切出来的块天然语义完整；前提是文档格式规范。乱糟糟的扫描版 PDF 这招没用。

**④ 语义切割**

真正按内容而非规则来切。思路：

1. **1. 先按句子初步切分**
2. **2. 计算相邻句子的向量余弦相似度**
3. **3. 相似度高的句子归一块，相似度突然下降的地方就是话题转折点，在此切割**

比如一篇技术文档，前半部分讲"TCP 三次握手的原理"，后半部分讲"UDP 的无连接特性"——语义切割能精准识别这个话题边界，在中间切一刀，而固定大小切割可能把两个话题混在一块。

代价是对每个句子都要做 Embedding，计算成本是其他方法的几倍。

**⑤ 父子块策略（进阶实战常用）**

兼顾精准检索与完整上下文的聪明做法：

- 存储：将文档分成大块（父块，512–1024 tokens）和小块（子块，64–128 tokens），在数据库里建立父子索引关系
- 检索：用小块检索（小块语义更聚焦，命中更精准）
- 返回：找到小块后，返回其对应的父块给 LLM（父块上下文完整，信息更充分）

效果：精准检索 + 上下文完整，两头都要。

```text
📷 图片提示词 3手绘涂鸦风格信息图，横版 16:9，浅米色背景。标题："文档切割策略——从简单到精准"。画面展示 5 行横向对比，每行代表一种策略：第 1 行"固定大小切割"——一条长文字横条被等距剪断，部分块旁有 ✂️ 和 ⚠️ 标注"句子被截断"；第 2 行"递归字符切割"——同样横条但切割点落在段落/句子边界，旁边打 ✅；第 3 行"结构切割"——展示 Markdown 标题（# ## ###）作为自然切割点；第 4 行"语义切割"——文字上方画一条余弦相似度曲线，曲线突然下降处打一个切割标记；第 5 行"父子块策略"——小块用 🔍 标注"检索用小块"，小块通过箭头连接更大的父块，父块用 📖 标注"返回给模型"。从上到下颜色渐变，蓝色→绿色表示从简单到高级。钢笔素描风，手写标注。
```

> 

- 项目起步：直接用递归字符切割， `chunk_size=512, overlap=64`

## **五、Embedding 模型：四代演进与现状**

Embedding 就是"把文字变成数字坐标"的技术。语义接近的文字，坐标在高维空间中也挨得近——这是向量检索能工作的数学基础。理解 Embedding 的演进史，才能理解为什么现在要用新一代模型而不是随便选一个。

### **第一代：静态词向量（2013）**

代表：Word2Vec（Google，2013）、GloVe、FastText

核心假说：上下文相似的词，语义也相似。Word2Vec 训练时让模型"用上下文猜中间词"（CBOW）或"用一个词猜上下文"（Skip-Gram），训练完每个词得到一个固定向量。

经典示例： `国王 − 男人 + 女人 ≈ 女王` （向量的代数运算居然有语义意义）

致命缺陷：一个词只有一个固定向量，无法处理多义词。"苹果"在"吃了个苹果"和"苹果公司发布新品

- OpenAI text-embedding-3：自 2024 年 1 月起未更新，在新榜单上已落后于 Qwen3、Gemini、Voyage 等，"用 OpenAI Embedding 就行"这个思路在 2026 年已经过时。

## **六、向量数据库：选型实战指南**

Embedding 生成的向量往哪里存？如何从百万千万个向量里毫秒级找出最近邻？这就是向量数据库要解决的工程问题。

**为什么需要专门的向量数据库**

假设知识库有 100 万个文档块，每块是 1536 维向量。用户提问时，如果暴力枚举每个向量做相似度计算，需要进行 100 万次浮点运算——在毫秒级响应要求下完全不可行。

向量数据库通过预建索引解决这个问题，用"提前算好的结构"换取查询时的速度，本质上是用空间换时间的近似最近邻搜索（ANN）。

**三种核心索引技术**

HNSW（层级可导航小世界图）——用得最广

把所有向量组织成多层图结构，每层都是一个"小世界"导航网络。查询时从最顶层（稀疏连接，粗粒度定位）开始，层层向下收窄，到底层（密集连接，精细搜索）时范围已经极小。

类比：在一栋陌生大楼里找人。楼外看整栋楼定位楼层，进电梯定位到某层，再沿走廊找到具体房间——而不是一个房间一个房间挨个敲门。速度快、召回率高，是绝大多数向量库的默认索引。

IVF（倒排文件索引）——大规模高效

先把所有向量聚类成 N 个"桶"（Voronoi 分区），查询时只搜索最可能的几个桶。类比快递分拣：先按省份分，找上海的包裹只翻"华东区"，不用翻全国。内存效率高，适合超大规模（亿级以上），但只搜部分桶会损失一点召回。

PQ（乘积量化）——压缩存储

把每个向量压缩存储：切分成子向量、每段用有限个"码本"近似表示。像把高清照片压成缩略图，关键特征保留但体积缩小几十倍。常与 IVF 组合（IVF-PQ），在超大规模场景大幅降低内存占用。

**主流向量数据库横评**

| 产品 | 定位 | 最适合谁 |
| --- | --- | --- |
| Milvus | 开源标杆，支持十亿级向量；索引丰富，支持 GPU 加速，GitHub 4 万+ ⭐ | 企业级超大规模；运维有一定门槛 |
| Qdrant | Rust 编写，单机性能极强；混合检索和过滤功能丰富 | 对性能极致要求 + 想自建 + 不想引入 K8s |
| Weaviate | 原生混合检索（向量 + BM25），内置 Embedding 集成 | 混合检索 RAG；中小规模快速上线 |
| Pinecone | 全托管 SaaS，零运维，自动扩缩容 | 不想管基础设施；合规敏感场景慎用 |
| Chroma | 极轻量，pip install 即用，API 极简 | 原型验证、教学、个人项目 |
| pgvector | PostgreSQL 扩展，SQL 原生支持向量 | 已有 PG 基础设施；中小规模；运维成本近零 |

> 一个务实趋势：如果你的项目已经在用 PostgreSQL 或 Elasticsearch，pgvector / ES 向量搜索是最省事的起点——不引入新组件，性能比不上专用库，但中小规模完全够用。等规模上来再考虑迁移也不迟。

选型快速决策：

- 快速 POC → Chroma，别把精力浪费在基础设施上
- 生产级 + 私有化 + 性能优先 → Qdrant 或 Milvus（Milvus 更大规模）
- 混合检索需求 → Weaviate 开箱即用
- 已有 PG/ES 栈 → 先用 pgvector / ES 向量扩展

## **七、多路召回与 RRF 融合**

**为什么单一向量检索不够**

向量检索是语义层面的近邻搜索，擅长理解意图但有两个弱点：

弱点一：精确关键词匹配 用户搜"iPhone 15 Pro Max 256GB 深空黑"，向量检索可能把"iPhone 14 Pro Max 512GB 银色"也召回来——因为两者语义太相近了，但用户明确要找的是另一个 SKU。

弱点二：专有标识符 内部产品编号"PRD-2026-089"、合同编号"CONTRACT-BJ-2024-0312"——这类编号根本没有语义，向量相似度搜索对它们无效。

解决方案：不要只走一条路，同时走多条路，最后合并结果。

**三路召回架构**

```text
用户问题
   ├── 第一路：向量检索（Dense）    → 语义相似匹配，擅长意图理解
   ├── 第二路：关键词检索（BM25）   → 精确匹配专有名词/编号/术语
   └── 第三路：知识图谱（可选）     → 实体关系推理（"A的CEO是谁"）
              ↓
          结果融合（RRF）
              ↓
       （可选）Re-rank 精排
              ↓
         最终 Top-N → LLM
```

BM25 是经典全文检索的核心算法（Elasticsearch、Lucene 背后都是它），按词频（TF）和逆文档频率（IDF）计算相关性——出现越多、越罕见的词得分越高。它不理解语义，但对精确关键词命中无敌。

**RRF：把不同量纲的分数公平合并**

向量检索的余弦相似度和 BM25 的 BM25 分数没有可比性（量纲完全不同）。RRF（Reciprocal Rank Fusion，倒数排名融合）的聪明之处在于：不看绝对分数，只看名次。

对每个文档 `d` ，在各路检索结果中的排名分别是 `rank_1, rank_2, ...` ，RRF 综合得分为：

```text
RRF(d) = Σ  1 / (k + rank_i(d))
          i

其中 k 是平滑常数（工程上常取 60），防止排名第 1 的得分过于夸张

规律：
- 排名越靠前 → 分母越小 → 得分越高
- 被越多路同时命中 → 累加项越多 → 综合分越高
```

举例：文档 A 在向量检索里排第 2、BM25 里排第 5：

```text
RRF(A) = 1/(60+2) + 1/(60+5) = 0.01613 + 0.01538 ≈ 0.0315
```

文档 B 只在向量检索里排第 1：

```text
RRF(B) = 1/(60+1) ≈ 0.0164
```

A 的 RRF 分数更高，因为它被两路都认可——共识高于单路第一，这个逻辑非常符合直觉。

## **八、Re-rank：用精排弥补召回的先天缺陷**

多路召回给了我们 50–100 个候选文档块，但这 50 个的排序是最优的吗？不一定。这就是重排序（Re-rank）要补的关键洞。

**Bi-Encoder 的先天硬伤**

前面所有检索（无论向量还是 BM25）都属于"两段分开处理"的模式——查询和文档各自编码成向量，再算相似度。这就是 Bi-Encoder（双编码器）的工作方式。

问题出在"各自"两个字：

文档的向量是在索引阶段预先算好的，那个时候模型根本不知道用户将来会问什么。结果就是每篇文档的向量是一个"通用、平均"的语义表示——就像图书馆员给每本书写了一段通用简介，但这个简介并没有针对你具体的问题来写。

硬伤一：信息压缩损失——几百字压成一串数字，某些细微但关键的信息可能丢失。 硬伤二：不感知查询意图——同一文档，不管你问的是事实、比较还是操作步骤，它的向量都一模一样。

**Cross-Encoder：面对面精确匹配**

Re-rank 用的是 Cross-Encoder（交叉编码器），区别在于把查询和文档拼在一起送进模型：

```text
输入：[CLS] 用户的问题 [SEP] 检索到的文档内容 [SEP]
```

整段拼接过 Transformer，自注意力让问题里的每个词都和文档里的每个词交互，输出一个精确的相关性分数。

类比：

- Bi-Encoder 像招聘投简历：HR 一眼扫简历，快速筛出 50 个候选人
- Cross-Encoder 像面试：面试官针对候选人的具体经历逐条追问，精确判断合适程度

显然面试更准，但也更慢。

**为什么不直接全用 Cross-Encoder**

因为太慢了。Bi-Encoder 快是因为文档向量早就算好了；Cross-Encoder 要把查询和每一篇候选文档拼起来跑一次完整的 Transformer 推理。如果知识库有 1000 万篇文档，就需要 1000 万次推理——完全无法接受。

实际工程方案：两阶段流水线

```text
Bi-Encoder 粗筛（快）
从全量中召回 Top-50~100，目标：不漏，宁多勿少
        ↓
Cross-Encoder 精排（准）
仅对 50~100 个候选做精细重排，慢一点也可以接受
        ↓
最终 Top-5~10 → LLM
```

**主流 Re-rank 模型**

| 模型 | 特点 | 适用场景 |
| --- | --- | --- |
| BGE-Reranker-v2-m3 （智源） | 开源标杆，中文表现优异，可本地部署 | 国内生产首选，有 GPU 资源 |
| Cohere Rerank | 商业 SaaS API，几行代码接入 | 不想管模型，追求省心 |
| ms-marco-MiniLM （微软） | 轻量，推理快 | 资源有限/低延迟要求 |
| Jina Reranker v2 | 多语言支持好 | 多语种混合内容 |

> 实战建议：先用 Bi-Encoder 召回 50–100 个候选，Re-rank 精排到 Top-5~10，是目前性价比最高的标准配置。简单事实查询 Re-rank 提升有限，可以设条件触发（初排第一名分数超过阈值就跳过重排）；复杂多意图查询则建议始终开启。

## **九、效果量化：怎么知道 RAG 到底好不好**

"凭感觉优化"是 RAG 工程里最常见的陷阱。没有量化的基线，你不知道这次改动是进步还是退步，优化就变成了玄学。

**为什么比评估普通 LLM 更复杂**

RAG 系统有两个部件：检索器（找资料）和生成器（写答案）。

如果最终答案质量差，需要分清是检索的问题还是生成的问题：

```text
最终答案差
    ├── 检索出了错误/不相关的文档？ → 检索问题
    └── 文档对但模型理解错了/曲解了？ → 生成问题
```

类比：餐厅菜品差评，需要分清是食材采购出了问题，还是厨师烹饪出了问题——两类问题的解法截然不同。

**第一层：检索质量指标**

| 指标 | 含义 | 怎么算 | 关注什么 |
| --- | --- | --- | --- |
| Recall@K | 找全了没？ | Top-K 里相关文档占所有相关文档的比例 | 遗漏率，宁多勿漏 |
| Precision@K | 找准了没？ | Top-K 里有多少是真正相关的 | 噪声率，避免乱凑 |
| NDCG@K | 排对了没？ | 高度相关的是否排在前面 | 综合排序质量 |
| MRR | 第一个相关结果排第几 | 各查询首个相关结果倒数排名的均值 | 快速找到答案 |

**第二层：生成质量指标**

| 指标 | 含义 | 重要性 |
| --- | --- | --- |
| Faithfulness（忠实度） | 答案是否忠实于检索文档，有无编造 | ⭐⭐⭐⭐⭐ 最重要 |
| Answer Relevance（答案相关性） | 答案有没有真正回答问题，是否跑题 | ⭐⭐⭐⭐ |
| Context Relevance（上下文相关性） | 检索到的文档和问题相不相关 | ⭐⭐⭐⭐ |
| Context Recall | 必要信息是否都被检索到了 | ⭐⭐⭐ |

Faithfulness 是生成质量的核心指标。RAGAS 的计算方式：把回答拆成独立陈述，逐条验证是否在检索文档中有据可查。10 条陈述中 8 条有支撑 → Faithfulness = 0.8。

**主流评估框架**

RAGAS（最流行）：无需人工标注答案，用更强的 LLM 当"裁判"自动打分。准备包含 `question` 、 `contexts` 、 `answer` （可选 `ground_truth` ）的数据集，调用 `evaluate()` 一键输出所有指标。

```text
from ragas import evaluate
from ragas.metrics import faithfulness, answer_relevancy, context_recall

results = evaluate(
    dataset=your_dataset,
    metrics=[faithfulness, answer_relevancy, context_recall]
)
print(results)
```

同类工具：

- DeepEval：把评估融进单元测试，适合 CI/CD 集成的工程团队
- TruLens：深度诊断，适合需要详细溯源分析的场景
- ARES：用 LLM 自动生成合成评估数据，解决人工标注成本问题

**RAG 为何是最有效的降幻觉手段**

核心就是把"闭卷"变"开卷"：纯 LLM 靠模糊的参数记忆，RAG 提供了真实可验证的参考文档。具体作用：

- 注入真实知识：大幅减少凭空编造
- 可追溯性：出了错能定位到具体哪份文档出问题
- 注意力偏向：模型倾向于引用 Prompt 里明确给出的信息

但 RAG 不是银弹：检索到错文档、模型曲解文档、越界推断——幻觉照样发生。

**组合防线（五层防御）**

```text
Layer 1: Prompt 约束（零成本，立即生效）
    → "仅基于以下资料回答，没有相关信息请说'无法回答'"
    → 要求标注来源、鼓励承认不确定性

Layer 2: RAG 检索（核心机制）
    → 混合检索 + Re-rank 提高检索文档质量

Layer 3: 输出验证（事后检查）
    → LLM-as-Judge：另一个模型交叉验证
    → 规则引擎：校验数字/日期/金额等关键字段
    → 多次采样：多个回答说法不一致 → 可疑，触发人工审核

Layer 4: 领域微调（专业场景）
    → 用高质量"问题-正确答案"对做 SFT
    → RLHF 阶段奖励"坦承不知道"而非"回答得好听"
    → 成本高，在前三层不足时再考虑

Layer 5: 不确定性量化（UQ）
    → 基于 logprobs 计算 token 级置信度
    → 基于多次采样一致性计算置信区间
    → 置信度低 → 触发人工审核 / 拒绝回答 / 降低措辞确定性
```

## **十一、RAG 演进全景：从朴素到智能体**

前面讲的是 RAG 的基础组件。但 RAG 技术本身也在快速演进——理解它的演进图谱，才能在合适的场景选合适的方案。

**三代 RAG 架构**

**Naive RAG（朴素 RAG）——第一代**

流程：加载 → 切割 → Embedding → 向量库 | 提问 → 检索 → 增强 Prompt → 生成

优点：简单、可预测、调试容易

局限：

- 单路向量检索，精确匹配差
- 没有查询优化（用户问法直接影响召回质量）
- 没有重排序
- 对多跳推理（需要整合多篇文档信息）无能为力

适用：快速验证、小规模知识库（< 10万文档）、问题简单直接

**Advanced RAG（高级 RAG）——第二代**

在朴素 RAG 的三个阶段分别增强：

检索前（Pre-retrieval）：

- 查询改写：用 LLM 把用户问题重写成更利于检索的形式。"你们公司加班多吗" → 分解为"加班制度"、"加班时长规定"、"加班补贴政策"三个子查询并行检索，合并结果
- HyDE（假设文档嵌入）：先让 LLM 基于问题生成一个"假设性答案"，用这个假设答案的向量去检索——因为假设答案在表述风格上更接近真实答案，命中率更高
- 多查询扩展：生成多个不同角度的子问题，分别检索后 RRF 融合

检索中（Retrieval）：

- 混合检索（Dense + BM25）+ RRF
- 元数据过滤（时间范围、来源、分类）

检索后（Post-retrieval）：

- Cross-Encoder 重排序
- 上下文压缩（去掉检索文档中与问题无关的部分，降低 LLM 的噪声干扰）
- 强制引用标注

适用：大多数企业 RAG 场景，是当前生产部署的主流方案

### **Agentic RAG（智能体 RAG）——第三代**

前两代 RAG 都是一次性的固定流水线：问题进来，走完流程，答案出去。

Agentic RAG 不同——它让 LLM 作为决策主体，自主决定：

- 是否需要检索？（简单数学题不需要）
- 检索到的文档够用吗？不够 → 重新检索
- 这个问题需要拆解成子问题分别处理吗？
- 需要调用哪些工具（代码执行、网络搜索、数据库查询）？

典型框架：

- ReAct（推理 + 行动）：Thought → Action → Observation → Thought … 循环直到问题解决
- Self-RAG：训练模型自己判断何时需要检索、检索结果是否相关、生成是否有依据
- CRAG（Corrective RAG）：自带纠错机制，检索质量差时自动触发网络搜索补充

适用：需要多步推理的复杂问题、需要整合多个数据源、问题类型多样需要动态路由

### **GraphRAG——关系推理专用**

传统 RAG 把文档切成独立的块，块与块之间没有连接关系。对于需要整合多篇文档信息的问题效果差。

GraphRAG 的思路：先从文档中抽取实体和关系，构建知识图谱，再基于图的遍历做检索。

```text
文档集 → 实体抽取（人、地点、组织、概念） 
       → 关系抽取（A 创立了 B、C 属于 D） 
       → 构建知识图谱
       → 图检索（BFS/社区汇总/关系路径）
       → 答案生成
```

擅长：

- 多跳推理（"A 公司的 CEO 之前在哪家公司任职"）
- 关系交叉查询（"同时出现在项目 X 和项目 Y 中的人员有哪些"）
- 全局理解（"这批合同的主要风险点有哪些"）

代价：索引成本高（需要大量 LLM 调用抽取实体关系）。微软 2025 年推出的 LazyGraphRAG 将索引成本降低到完整 GraphRAG 的 0.1%，大幅降低了使用门槛。

LightRAG：开源 GraphRAG 轻量实现，支持增量更新（新文档不需要重建全图），是当前国内生产中最常用的 GraphRAG 方案之一。

### **RAG vs 其他方案全景对比**

| 方案 | 核心优势 | 关键局限 | 最适合场景 |
| --- | --- | --- | --- |
| RAG | 实时知识、可追溯、私有数据 | 检索失败会直接影响答案质量 | 动态/私有知识库问答 |
| 微调 | 深度领域适应、风格定制 | 知识更新成本高、无可追溯性 | 固定风格/能力增强 |
| 超长上下文 | 单文档深度分析简单直接 | 成本高、Lost-in-the-Middle 问题 | 单个长文档分析 |
| Text-to-SQL | 精确查询结构化数据 | 需要 schema 建模，非结构化数据无效 | 数据库查询问答 |
| GraphRAG | 关系推理、多跳问答 | 构建成本高 | 知识密集型关系推理 |
| Agentic RAG | 复杂多步骤任务 | 延迟高、不可预测性强 | 复杂决策支持 |

## **十题速查**

| 题目 | 核心答案 |
| --- | --- |
| RAG 是什么 | 检索增强生成：先找资料再作答，解决知识过期/私有/幻觉三大痛点 |
| 整体流程 | 离线：加载→切割→Embedding→入库；在线：提问→检索→增强 Prompt→生成 |
| 微调 vs RAG | 微调内化知识/风格，RAG 外挂实时知识库，互补而非替代 |
| 切割策略 | 优先递归字符切割（512 tokens, 10%重叠）；结构化文档改用结构切割 |
| Re-rank 原理 | Bi-Encoder 粗筛速度快但精度低；Cross-Encoder 精排准但慢，两阶段配合 |
| Embedding 现状 | Qwen3-Embedding-8B 领跑开源多语言 MTEB；多模态入局（Cohere v4、Gemini 2） |
| 向量库选型 | 原型用 Chroma；生产用 Qdrant/Weaviate/Milvus；已有 PG 先试 pgvector |
| 多路召回 | 向量（语义）+ BM25（精确）+ RRF 融合，混合检索已成标准方案 |
| 效果量化 | 检索看 Recall/Precision/NDCG；生成看 Faithfulness（最重要）/Relevance；工具用 RAGAS |
| 降幻觉 | RAG 是核心手段但非银弹；需 Prompt 约束 + 输出验证 + 微调 + UQ 组合防线 |
