本文是上次推理优化记录的续篇。

## 任务背景

- 任务：将一个混合架构模型（GDN 49层 + FullAttn 7层 & MoE , 30A2B）在昇腾910B（4*64GiB HBM）上跑起来，并尽可能提高推理速度<br>
- 推理引擎：
- 上次把GDN Prefill阶段的算子换成 AscendC fused ops之后，经过vllm bench测量确实验证了Prefill阶段的speedup，对TTFT和总throughput都有较大提升。**然而Decode仍然很慢，单并发下TPOT为54ms左右**（由于线性注意力特性，此TPOT在1k到256k的上下文均成立）

## 优化过程

### **1. 调整cudaGraph模式**

不同图编译模式实际上对模型推理速度影响甚大。下面简单介绍一下，详细可见文末链接。

| Mode | 实际行为 | 主要取舍 |
| --- | --- | --- |
| NONE | 完全 eager，不捕图 | 适合排障 |
| PIECEWISE | 将前向拆成多个片段；不兼容图的 Attention 等保持 eager，其余片段 capture/replay | 兼容性最好，但捕获图数量会随层数增加，最容易遇到 stream/resource 压力 |
| FULL | 对非 uniform batch 捕获整图；uniform decode 可复用同 batch size 的整图 | 需要 Attention 后端支持整图及运行时参数更新 |
| FULL_DECODE_ONLY | 仅对 uniform decode 捕获整图；prefill / mixed batch 不走 cudagraph | 比 FULL_AND_PIECEWISE 更省图内存和启动捕获成本，P/D 分离或 decode 主导场景常合适 |
| FULL_AND_PIECEWISE | uniform decode 用 full graph；prefill / mixed batch 用 piecewise graph | 通常性能最强，但图内存最多、capture 最慢 |

我查看之前的模型serve日志，发现执行的是 PIECEWISE 模式

![](https://pic4.zhimg.com/v2-f0f89d42306cb7e2ebc67f2c94b85815_r.jpg)

之前看traceview的时候我也注意到Decode的时候只有MoE层是Graph模式的，Attention和GDN都是eager模式，也符合PIECEWISE模式的特征。

Decode由于输入shape固定，很适合用Graph模式来进行decode的加速，减少细小算子的kernel launch overhead.

于是将PIECEWISE模式切换成FULL_DECODE_ONLY模式再次推理，在vllm serve时显式传递 `compilation-config` 参数即可。

![](https://pic4.zhimg.com/v2-7c258c2d139db130750de31cb2db305b_r.jpg)

> 此处要capture 51个图是因为默认捕捉51个不同长度的bucket，规则详见：[capture_size_and_bucketing](https://docs.vllm.ai/projects/ascend/en/latest/developer_guide/Design_Documents/ACL_Graph.html?#capture-sizes-and-bucketing)。

结果如下：

- Hybrid Model TPOT p50: 54ms->21ms
- Softmax Model TPOR p50: 37ms->14ms (when ContextLength < 32k)<br>

![](https://pic4.zhimg.com/v2-cfd34a794151c5169cd0db781c5f442b_r.jpg)

这里存在一个问题，为什么在未定义图编译模式的情况下采用了PIECEWISE呢？

① vllm 默认 optimization_level=O2

vllm/config/vllm.py:336:

```python
optimization_level: OptimizationLevel = OptimizationLevel.O2
```

② O2 的默认表给 cudagraph_mode = FULL_AND_PIECEWISE

vllm/config/vllm.py:228(OPTIMIZATION_LEVEL_02 内）:

```python
"cudagraph_mode": CUDAGraphMode.FULL_AND_PIECEWISE,
```

即 vllm 上游本意默认是「decode FULL + prefill PIECEWISE」。

③ vllm-ascend 平台钩子把 FULL_AND_PIECEWISE 强行降成 PIECEWISE

vllm_ascend/platform.py:378-380:

```python
# TODO: Full graph is fully supported later, and the default value will be set to full graph.
if compilation_config.cudagraph_mode == CUDAGraphMode.FULL_AND_PIECEWISE:
   compilation_config.cudagraph_mode = CUDAGraphMode.PIECEWISE
```

原来是这个版本还不支持。。

可正常解题

优化在算子层面与端到端层面都有正面效果，验证通过。下一步看具体是怎么做的。

**原理**

- GDN在进行RNN式更新前需要在序列维度做一次短卷积conv1d。conv1d 的 query_start_loc / cache_indices / num_accepted 这些metadata, 本来在 vLLM 里就已是设备张量(attention 后端直接消费）。<br>

```python
self.non_spec_query_start_loc: torch.Tensor = torch.empty(
	(self.decode_cudagraph_max_bs + 1,),
	dtype=torch.int32,
	device=device,
)
```

- 但这个`causal_conv1d_update` op 的接口是 host int[] + ValueDepend——tiler 在定型时要读这些 host 值。
- 于是旧流程每次调用这个op都要把这些位于设备侧的值做 `.tolist()` （拉回 CPU） → 转成 host 元组 → 经graph_task_update_begin/end 逐层登记回捕获图的节点参数 → 之后 graph replay 才真正执行计算。（`vllm-ascend/vllm_ascend/compilation/acl_graph.py`中行为）<br>

```python
def to_int64_tuple(tensor: torch.Tensor) -> tuple[int, ...]:
	tensor = tensor.to(torch.int64)
	if tensor.dim() == 0:
		return (tensor.item(),)
	return tuple(tensor.tolist())
```

无论是 `.item()`还是`.tolist()`都会触发D2H同步（DeviceToHost），因为Host侧必须立刻知道当前这个tensor的值，而D2H同步就会导致Python主线程阻塞，造成时间浪费。

- 知道了原因，就可以确定最终方案：**把 metadata 从 host 参数改成设备张量图输入**。<br>

- 为什么这几个参数**能够**作为设备张量被op读取？

直接引用AI的回答：

> 一句话原理：host 发射 kernel 时，发射包里装的是「指针 + host」。这四个参数是「值」，host不需要看它们，只需要把装着它们的显存地址交出去。<br>为什么这四个可以<br>每次 launch kernel时, host 往 device 送的东西分两类：<br>张量指针（x、weight、conv_state、query_start_loc、cache_indices 等）<br><br>Host不需要具体值。只需要地址；capture 时地址确定，replay 时继续使用该地址<br><br>host 的拍板决策（grid 核数、workspace 大小、选择哪个 kernel、shape/stride 等）<br><br>Host必须要知道具体值。这些信息需要在 kernel 发射时填入 launch 参数。<br><br>看这四个参数实际干什么：<br><br>query_start_loc:kernel 里读「第 i 个序列从哪开始/到哪结束」→<br>逐序列的窗口计算，kernel 自己读自己算<br>cache_indices:kernel 里读「第 i 个请求对应 conv_state 的哪一行」→ 逐序列的<br>gather/scatter 地址,kernel 自己读自己跳<br>num_accepted_tokens:spec decode 里读「这个请求采纳了几个 token」→<br>逐序列步进，kernel 自己读<br>initial_state_mode:逐序列「要不要用初始状态」→ kernel 运行时分支<br>共同特征：它们只影响 kernel 执行时「读哪、算哪、跳过哪」，全部是可以推迟到设备上做的逐序列决策。 host 侧不需要用这些值决定任何事——grid 不按它们变、workspace 不按它们变、shape 不按它们变。<br>改造做的正是把这个事实显式化：<br><br>ValueDepend 删掉 → 声明「编译期 host 不看这些值」<br>tiler 里 qslData 读取删掉 → 定型只按 shape 不按值<br>kernel 加 ReadQueryStartLocValue() 等 → 值的消费点从 host 搬到 device(HBM读）<br>外加一个边界条件：shape 必须固定（地址固定、大小固定），值随便变。请求数变化用 padding + PAD_SLOT_ID no-op 吸收——「形状冻住，内容任换」。<br>什么样的不行<br>凡 host 发射前必须拿值来拍板的，都不行：<br><br>决定 grid 的值——「按实际请求数分核」。发几个核要填进发射包，host必须先知道请求数。<br>决定 workspace 大小的值——buffer 是 host 先分配再发射的。大小依赖运行时值 → host 必须知道。<br>决定 shape/布局的值——shape 变了 = 图输入槽位对不上，capture 直接失效。内容可变、形状不可变。<br>决定「跑哪个 kernel 二进制」的值——host 要按值选分支 kernel；这必须在发射前知道。<br>注意区分：kernel 内部按值分支（if has_init_state ...）没关系，那是 device上跑的时候自己判断的；破坏的是「这个值让 host 换一条 launch 路径」。

## 小结

本文介绍了两次推理优化，一次是调整图编译模式，一次是调整kernel launch参数从而减小host-side overhead,在减小TPOT方面取得了较好的效果。

此外，个人认为推理优化之类的Infra其实很适合agent去做。因为本质上就是工程问题，大多数问题的根源都在源代码里面，对于AI来说问题搜索空间很小，而且一次modify也很容易验证效果，可以快速迭代。
