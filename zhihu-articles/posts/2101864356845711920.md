### 写在前面

近期有这几件事，可以作为导入：

- **高通**：新一代骁龙声称是 *totally designed for agents*，NPU 共享内存扩容 **50%**；
- **苹果**：A20 Pro 内存带宽提升 **50%**；
- **面壁**：MiniCPM-V4.7-35B-A3B，在 iPhone Duo 上用 **3GB 内存**跑到 **30+ tps**；
- **Arm** 10 月底发了一篇 agentic AI 从云走到端的长文，核心观点是：

> Agentic AI will require the whole system – software and hardware together – to be rethought from the ground up.

总而言之，大家都想解决同一件事：**如何在资源受限（算力、内存容量和带宽、功耗、散热、体积）的环境里，让端侧 AI 满足真实业务需求，并且长稳运行。**

这是一个在不可能三角中寻找平衡的故事： **运行资源受限 × 达成效果优异 × 系统长稳可靠**

难点在于，端侧资源虽然受限，**整个 AI 软件栈却一层没少**。（分布式部分暂时除外——当前不论是芯、模还是应用，更多都 focus 在单机；但端端互联的算力小集群，我预测也会是接下来的重点。）

### 云侧有余量，端侧处处是短板

云侧大厂还在不停地买算力，可 SemiAnalysis 分析数据中心电力账单时发现，**通用云负载的利用率一般也就 50%～60%**。（这是一个很好的方法：通过电力消耗反推实际负载，包括 CPU、通信、GPU、XPU 等。）这有点反直觉，but it’s true.

云侧资源在某种程度上是有余量的。因为有利用率盈余，下面每一项优化在云侧都能带来很大的性能提升：

- **模型**：量化、MoE、投机推理
- **Infra**：batch、KV、PD 分离、prefix match
- **Agent**：上下文工程、记忆系统、沙箱、agent swarm

但到了端侧，模型 + Agent + 业务一旦运行，**系统负载非常容易打满**——不是内存，就是算力，亦或带宽。由于短板的存在，单点优化对系统性能的提升都很有限，**硬件中的每一项都可能成为 bottleneck**。

### 为什么非要做端侧？

有同学可能会想：既然有这么多问题，为什么非得执着于把 AI 放在端侧跑？手机设计之初也没考虑要跑模型，有啥问题是接入云侧 API 解决不了的？

从技术上来说，**没有**。

但反过来说，假设端侧的模型服务给业务提供一个 HTTP 接口，效果也是一样的。用户根本不关心这个 token 来自端侧还是云侧，**他只关心自己的需求到底有没有被解决。**

那既然都可以，为什么还要做端侧？简单写几点，以后有机会在别的问题里展开：

**1. 愿景**

AI 走进生活，就会进入物理世界。最丝滑的方式是让 AI 在现场自闭环——感知、决策、执行都在本地设备上完成：**低延迟、长驻留、高隐私**。

中心化算力在我看来是阶段性结果，而非终局。云侧与端侧并非二元对立，而是互相补齐场景，共同让 AI 走向商业落地——**得端云两条腿一起走路**。

**2. 场景**

端侧需求是真的：

- **数据高隐私**：政务、医疗、金融、公安；
- **网络可靠性不足**：地库、隧道、隔离的产线内网；
- **响应要即时**：语音、设备控制；
- **成本要可控**：现在 AI 应用的规模化与云侧 API 订阅之间存在 paradox，常出现用户越多亏损越大（比如 Character.AI、Manus），到最后为了控制成本，反过来去控制用户增长，这种反直觉的事情。

所以接下来会发生的事情是：**业务会重新布局，跟随本质逻辑自发寻找自己在端侧和云侧的位置。**

**3. 实景**

端侧硬件能力冗余持续抬升，算力基础已经具备，自然会有场景承接。**端侧 AI 只是算力溢出的天然出口之一。**

---

回到正题。端侧 AI Infra，我认为很重要的一个思想是：

**系统性协同：Model、Infra、Agent、SoC 不应该割裂地各自发展，各层级都要放在一起做系统设计。**

下文分三块：

1. **现状**：端侧商业化的需求和 gap；
2. **问题**：端侧到底卡在哪；
3. **构想**：一是系统协同的设计哲学，二是评测和自进化的底座。

### 一、商业化需求和现状之间的 gap

先看端侧的生意运行在哪。硬件底座大致可分四档：

| 档位 | 典型设备 | 特点 |
| --- | --- | --- |
| 便携式 | 手机、眼镜、AI 吊坠、耳机 | 离人最近，数据最私密，电池最小 |
| 板级 | 工控机、嵌入式板卡、机器人 | 网络常隔离，7×24 运行，散热条件差 |
| AIPC | 笔记本、桌面机、车机、AI BOX | 本地跑 coding agent 正成趋势 |
| 边缘服务器 | 不带超节点互联的单机 | 政务、金融、医疗是主力买家 |

**便携式**：手机、眼镜、AI 吊坠、耳机，离人最近，数据最私密，电池最小。比如豆包、阶跃的 AI 手机，Meta 的 AI 眼镜等。

**板级**：工控机、嵌入式板卡、机器人。产线、园区、电力现场，网络常常是隔离的，设备要 7×24 跑在没有像样散热的地方。

**AIPC**：桌面式、便携式，也包括车机。

- 笔记本（高性能的叫 AIPC，本质没区别）上本地跑 coding agent 正在成为趋势；
- 车机非常典型：地库和隧道没网，语音要即时，舱内摄像头的数据不能随便上云；
- AI BOX 算力盒子：没有显示器的裸微型服务器，类似自己装显卡配机箱但啥外设都不装，或者早几年都没什么人买的 Mac mini。。。

**边缘服务器**：翻译一下，就是云侧除超节点之外（不附带 NVLink、UB 等互联总线）的单机。政务、金融、医疗（包括但不限于）是主力买家。按赛迪的数据，**今年上半年国内 AI 一体机市场 53.8 亿元，同比增长 24.5%**。

虽然硬件档位分好了，但在客户现场，经常会遇到一个问题：端侧的业务场景，需要多大的模型？搭配什么样的智能体？能解决什么问题、完成什么任务？成本是多少？预计并发有多少？

**没有概念。现在太缺数据了——真实端侧商业化的数据。**

而模型发布的 benchmark 和客户现场的语言又是脱节的。没有人能对着 benchmark 上的 intelligence score 给出一个精准的答案。大家太习惯直接从 ranking board 上找最好的用，nobody cares 这个模型的效果到底好在哪，全靠“体感”——我“感觉”模型降智了。

对于商业落地来说，没有人喜欢 buy in“体感”，大家只 buy in “yes” or “no”。

端侧需求是真的，但从玩具到生产，有距离。

距离有多远，不好说。反正在“体感”上，有些近，有些远。

### 二、端侧 Infra 的问题

有新问题，也有云侧的老问题，简单聊聊。

### 新问题：硬件种类太多了

- **三种协同形态**：云重端轻、云轻端重、纯端；
- **三种推理形态**：单机、同构多机、异构多机；
- **四档设备级别**：便携、板级、AIPC、边缘服务器。

层层组合下来，才是端侧 Agent 真实的运行底座。

举个例子：不同硬件能支撑的模型规模（100B → 1B）差距很大，而模型的智能水平又会反过来影响 Agent runtime core 的设计。**我们不可能为每个格子单独写一套新的 harness**，这不优雅，也不现实。

### 老问题 1：调度

我在 M5 MacBook Pro（10 核）上用 Claude Code 跑复杂任务，**CPU 平均负载只有 0.5%**。这对功耗是好事，但拉出 profiling 一看就很灾难：pipeline 里都是空闲气泡——harness 和推理引擎在同一台机器上运行，却各做各的。

Georgia Tech 和 Intel 去年 11 月的 profiling 显示：SWE-Agent 的**工具执行占端到端时延的 43.8%–78.7%**，这段时间 device（加速单元部分）基本在空等。按 Amdahl 定律算，**加速器快一倍，端到端只能快 1.12–1.39 倍**。

### 老问题 2：内存

算一笔账：一个 2B dense 模型，BF16 拉满原生 128K 上下文：

- KV Cache 约 **5.6GB**；
- BF16 权重约 **4.7GB**；
- 合计：一个没有优化的 2B 模型要 **约 10GB 运行内存**。

现在本地推理对便携式机型的压力还是很大。

另外，现在端侧很多在做存算一体，但 SRAM 上的烧录参数终究有限（MB 级别）；运行内存用的是 DDR5+，**平均带宽在 300GB/s 以下（2026）**，数据传输压力很大。CPU、GPU、NPU 以及各种外设共用一个 DDR 带宽，而 decode 又最吃带宽。

所以端侧真正的分层是**纵向**的：片上 SRAM → LPDDR → Flash，最后落到驻留问题上，内存紧缺很严重。

### 老问题 3：通信

端间互联还在起步：

- **DGX Spark**：单台 273GB/s 内存带宽，两台 200GbE 直连折合约 25GB/s；
- **macOS 26.2** 起支持 RDMA over Thunderbolt 5，实测 50–60Gbps，但没有交换机，只能两两直连；
- **prima.cpp** 在 4 台走 Wi-Fi 的家用设备上把 70B 跑到 674ms/token。

这些基本都是几乎不可用的状态。

很多时候出于成本控制，单台设备无法保障业务，上一体机预算又不够。小集群的 AI BOX 多机互联方案粗看很 sexy，但现实是落地的硬件底座完全没打好，**以软补硬无异于无米之炊**。

**需要软、硬、芯系统协同。**

### 三、端侧的系统协同哲学

### 3.1 从语义协同走向系统深度协同

**先说问题：Agent 和底层 AI 软件栈之间没有语义上的协同。**

现在，Agent 的自然语言最多传到推理框架这一层，再往下就被切成一个个 block id。上层完整的任务意图，对底层来说是黑盒。

结果就是，资源放哪、留哪、谁来抢占，harness 和设备走的都是最传统的 LRU。经典的东西确实好用，但问题在于信息是割裂的：**harness 懂语义，但不懂资源；设备懂资源，但不懂语义。**两边各自优化，谁也看不到全局。

**潜在解法：打通业务的任务语义和底层的推理 runtime，让信息双向流动。**

- **Agent 向下声明**：需要哪些模型；每块上下文要保留多久；这块上下文丢了，重算代价有多大；时延目标是多少。
- **OS 向上暴露**：当前的内存、带宽和热余量；KV Cache 存在哪一级存储单元；device 能不能被抢占。

光有双向通道还不够，还要**形成闭环**。比较合理的做法是参考 Android 的 **ADPF**（Android Dynamic Performance Framework）：先声明目标，再给出数据和调度逻辑，执行完汇报结果，下一轮据此调整。

还有一点值得强调：**Agent 首先要调度的是它自己的任务**，毕竟 Agent 最初的本质就是 context 编排。Agent、Infra 和设备应该把各自的信息聚合起来，一起分析，快速决策。至于这套逻辑具体放在哪一层实现，其实不重要——说到底只是代码运行在哪里的问题，**重要的是跑出来的效果**。

这能带来什么价值？至少有四点：

1. **缓存策略：从盲目的 LRU 变成任务感知的智能驻留。** 系统知道一段上下文后面还会不会复用、重算成本有多高，就可以把高代价、高频访问的 KV 优先留在片上高速存储，避免反复刷写和重复 Prefill，大幅减少 token 搬运开销。
2. **阻塞时主动让出资源。** 遇到工具调用、联网、读外设这类长时间等待，调度层能识别出这是 Agent 主动停下来了，于是把 NPU/GPU 让给其他推理任务，而不是让硬件空转。
3. **差异化的 QoS 保障。** 按 Agent 声明的时延目标分配资源：交互主链路优先抢占，必要时降低批处理规模。这样能在端侧的功耗墙和热墙之内，稳住 TTFT、并发量这些核心指标。
4. **故障处理和降级跨层协同。** 内存吃紧或温度触限时，底层不再粗暴地杀进程，而是参考上下文的重算成本，优先丢掉恢复代价最低的分支，保住主会话。降级对用户来说几乎无感。

业界已经有不少尝试：

- 去年 10 月的 **EdgeAgent** 论文，把 Agent 的状态直接交给 M4 芯片上的调度层，工具调用卡住时就主动让出资源。在工具时延较长的场景下，**整体速度快了 1.77 倍**。
- **Georgia Tech × Intel** 之前的论文，在 profiling 之后又做了 CPU、GPU 协同的批处理和调度，**P50 时延分别快了 2.1 倍和 1.41 倍**。

我们智能体团队在这个方向上做了进一步的系统抽象，后面有机会再和大家详细分享。

### 3.2 用业务负载反哺软件、硬件和芯片的协同设计

思路是：**真实的业务负载先反哺 Agent 和 Infra，最终为模型和芯片设计提供新的方向。**

其实模型侧和芯片侧已经在朝同一个方向走了：

- **模型侧**：我们的 MiniCPM-V 4.7 能在手机上只用 3GB 内存运行。靠的是只保留少数几层全注意力来压缩 KV，再用 LES 专家预取、分层量化和投机解码，把数据搬运的开销藏起来。
- **芯片侧**：NV，高通，intel，AMD，苹果...都在扩大 NPU 共享内存，目的也是把 KV 尽量留在片上。

两边的共同点是**提前一步看**：预判接下来要用什么，提前准备好，把搬运和计算的等待藏起来。

Agent 侧也该做同样的事。比如在工具运行的那几秒里，先把下一步一定会用到的前缀 prefill 好，把要用的模型提前换进内存。

要做到这一点，Agent 单方面努力是不够的，需要和芯片厂商、Infra 生态保持密切交流，**把负载特征变成设计输入**。

### 3.3 端侧超节点

这一点真实业务输入还比较少，先简单聊聊。

思路可以借鉴云侧的超节点。云上的做法是通过高带宽、低时延的互联，把多卡/多机在算力、访存、传输拓扑上都做成逻辑统一的大节点，让算力和显存可以池化、统一调度。

放到端侧，我们是否也可以考虑**小算力超节点**？用户身边其实已经有不少算力设备：手机、PC、平板、车机、家庭边缘盒子等。单个设备的算力和内存都有限，但如果能通过低时延互联把它们组织起来——

**纸面参数比一体机漂亮，实际推理效果接近或超越一体机，价格还有优势，想象空间就非常大了。**

- **算力和内存池化**：单设备跑不动的模型或长上下文，可以跨设备拆分承载；
- **按设备特点分工**：算力强、散热好的设备承担 Prefill 这类计算密集的部分，手机这类交互终端专注 Decode 和响应；
- **KV 和任务状态跨设备迁移**：用户切换设备时，任务可以接着跑，不用从头再来；
- **隐私留在本地**：数据只在用户自己的设备之间流转，不出可信域。

当然，挑战也很明显：端侧互联的带宽和时延远不如云上，设备可能随时离线，功耗和发热各不相同，跨厂商还有生态壁垒。这些都需要和 3.1、3.2 里提到的语义协同、软硬协同结合起来考虑。

比如，可以先联合生态伙伴从**同构小集群**做一些技术探索。

现在技术和商务都跑得很快，我们团队也一直看到一些新的东西，后续有机会再和大家分享。

### 四、端侧的系统评测

### 有了思路，还缺数据闭环

上一章都是思路。但思路对不对、收益有多大，单看 AI 软件栈某一层的数字是回答不了的。就像现在大家看模型刷榜，已经有点脱敏了：**榜单分数涨了，不代表用起来更好。**

AI 要商业落地，就得讲**产品语言、商业语言**。客户真正关心的是：

- 每个成功任务的端到端时延是多少？
- 任务完成的质量怎么样？
- 并发能做到多少？
- 结果稳不稳定？运行噪音大不大？

这些指标，很难脱离真实业务场景做预估。

所以评测必须按完整系统来做：**模型 × 智能体 × 硬件 × 场景**

每次运行都要尽可能记录全栈信息（包括但不限于）：

| 维度 | 指标 |
| --- | --- |
| 效果 | 任务成功率、完成质量 |
| 时延 | TTFT、TPOT、E2E 耗时 |
| 资源 | token 消耗、上下文峰值、内存占用 |
| 物理约束 | 功耗、温度 |

### 再聊聊端侧和自进化

最近 RSI（Recursive Self-Improvement）很火，这里顺着系统评测，聊聊端侧和自进化的关系。

**先说结论：端侧特别适合走自进化这条路。**

原因有两个：

1. **端侧要靠系统协同**，而模型、智能体、硬件、场景的组合太多了，靠人针对每个场景去特化调优，不现实。
2. **端侧天然具备自进化需要的条件。** 数据在本地，硬件配置固定，业务长期稳定，优化目标也明确。再加上系统评测底座，效果、时延、功耗每次变了多少都能量化——**反馈信号都可度量**。

目前规划能自进化的东西，从浅到深：

| 层级 | 代表工作 | 效果 |
| --- | --- | --- |
| System Prompt | GEPA：用自然语言反思来进化 prompt | 比 GRPO 强化学习平均高 6 个点，rollout 最多少 35 倍 |
| Skills / Plugins | ACE：把上下文当成不断演进的 playbook | Agent 任务平均提升 10.6% |
| Harness | Darwin Gödel Machine（DGM）：让 coding agent 改自己的代码 | SWE-bench 从 20% 爬到 50% |
| Infra | 面壁 ForgeKernel | 10 月底同时登顶昇腾 CANNBench 950DT、950PR、A3 三张硬件榜，相对基准加速 1.5–1.9 倍 |
| 模型参数 | AutoSFT（面壁协同清华）：一组 Agent 自己改 SFT 数据，每轮从基座重新训练 | +6.5 IFEval；合成再 +3.4 IFEval / +2.9 IFBench；代码域 +3.7 MBPP+ |

补充一点：ForgeKernel 从英伟达迁到昇腾，只是把 profiler 从 NCU 换成了 msprof。

**从 system prompt 到模型参数，越往下改，代价越大，风险越高，对系统评测的要求也越高。** prompt 改坏了随时能回滚；kernel 或模型参数改坏了，影响的是整个系统的正确性和稳定性。

但不管改哪一层，最终目标都是同一件事： **在效果、效率、成本这个不可能三角里，为客户找到现阶段最优的落地点。**
