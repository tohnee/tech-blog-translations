学习之后自问自答一下, 标题夸大了, 其实就是分享Dynamo在fault-tolerance问题的解决方案, 看Dynamo如何拆解这个问题

首先, 对于大规模的推理服务系统, 容错机制是必要的, 一台推理 worker 退出，带来的问题远不止“少了一台机器”。已经输出一半的回答还在等待后续 token，原本发往故障实例的新请求需要改道，剩余 worker 承受的压力随之上升。如果服务采用 Prefill/Decode 分离，另一台机器还可能正在读取故障一侧准备好的 KV 数据。

这些工作的结束时间并不相同。把新流量切走，可以恢复一部分服务可用性；把替代 worker 拉起来，可以补回容量；让原来的客户端继续收到完整回答，则需要单独的请求恢复机制。大规模推理系统的容错，必须同时处理这几个层次。

Dynamo 的设计可以沿两条主线理解：**Request fault tolerance 维护一次请求的执行与结果，Worker fault tolerance 维护可服务实例的生命周期与容量。**两者通过路由、请求上下文和资源管理协同。本文从这些组件的职责出发，解释故障检测、失效隔离、请求迁移、过载保护、取消和优雅退出如何组成一个完整系统。

## 一、先找到状态的主人，才能理解谁负责恢复

**Dynamo 把请求状态、路由视图和引擎执行状态放在不同的组件中，容错责任也沿这些边界划分。**

Frontend 接收 HTTP 请求，维持客户端的流式响应，并组织prefill、迁移和后续推理流水线。Router 根据模型、角色、拓扑、负载等条件选择执行目标。Worker 将请求交给 vLLM、SGLang、TensorRT-LLM 等具体引擎。Distributed Runtime 则提供组件之间的通信、请求上下文与服务发现能力。

这里的 Router 是一种逻辑职责，具体部署可以让它与 Frontend 位于同一进程。理解机制时，应先看状态由谁维护，再看组件最终部署在哪台机器上。

一次生成至少涉及三类状态：

| 状态 | 主要持有者 | 故障时需要解决的问题 |
| --- | --- | --- |
| 逻辑请求与已观察到的生成进度 | Frontend 的请求处理流水线 | 原请求是否仍有效，能否建立下一次执行尝试 |
| 成员、可路由目标与负载视图 | Discovery 消费者、Runtime client、Router | 哪些目标现在可以参与选择 |
| 模型、KV cache 与底层执行状态 | Worker 与推理引擎 | 怎样停止失效执行、保留必要资源、恢复执行能力 |

这三类状态解释了两个容易混淆的现象。

第一，worker 已经从路由候选中移除，原来的响应流还需要自己的终态。成员移除怎样影响在途通信，取决于响应平面：TCP 路径允许已建立的响应流继续排空，QUIC 路径还会取消活动流。后续选择与既有执行需要分别处理。

第二，替代 worker 已经启动，也未必能接回旧请求。模型加载与成员注册解决执行能力和可发现性；请求续接还需要 Frontend 保存的上下文，以及允许重试的错误和请求条件。

在 P/D 分离部署中，Prefill 负责处理输入上下文，Decode 负责持续生成，二者通过 KV cache（注意力计算的键值缓存）的传输连接。一次请求因而可能同时依赖多个 worker，控制流程的终止还需要照顾跨进程的数据依赖。后面的取消与关闭机制，正是在处理这类生命周期交错。

## 二、发现故障：成员还在线，引擎也可能已经无法工作

**Dynamo 使用多个observer检测不同层次的问题，而不是把所有故障压缩成一个全局 healthy 标志。** 一种检查能够证明的范围，取决于它实际经过了哪些组件。

| Observer | 观察的对象 | 这条信号适合支持什么决策 |
| --- | --- | --- |
| Engine monitor | 引擎原生健康接口、引擎死亡或致命错误 | 结束失效引擎和 worker 生命周期 |
| Runtime 本地 canary | 本地已注册 endpoint 的执行响应 | 更新本地 endpoint 的健康状态 |
| HTTP health 与 readiness | 组件生命周期、依赖或模型就绪状态 | 供探针与部署系统判断接流或重启动作 |
| 实际请求 | 建连、派发与响应流的错误或超时 | 结束当前尝试，并决定隔离或请求恢复 |
| 服务发现后端 | 注册、租约与 Kubernetes 就绪信息 | 更新可发现成员集合 |

### 引擎检测处理的是“包装进程活着，引擎失效”

Worker 的服务进程与真正执行推理的引擎，不一定共享同一种存活状态。例如引擎子进程已经停止推进，外层进程仍可能维持网络连接和注册续租。单靠发现记录，就会把这类实例继续留在服务中。

集成式 vLLM worker 使用 engine monitor 调用原生健康检查；引擎死亡或检查超时后，monitor 尝试关闭引擎、发起 Runtime shutdown，并最终退出进程。TensorRT-LLM 在引擎提供相应健康能力时也有监控路径，还通过独立 watchdog 处理已经记录的致命错误。

这一步把引擎内部故障转成外部能够处理的生命周期变化。进程管理器或 Kubernetes 随后可以负责重启。Monitor 的职责在于识别和结束失效执行，请求迁移与容量重建分别由其他组件完成。SGLang、Sidecar 等路径需要按照各自的集成方式理解，不能套用一套统一的 monitor 实现。

### 本地 canary 与真实请求补足不同盲区

本地 canary 启用后，会在 endpoint 缺少正常活动时发起小规模执行检查。正常响应活动会推迟检查，减少额外开销；空闲一段时间后，再确认执行路径还能产生有效响应。

它通过进程内 registry 调用 endpoint，并不重走 Frontend 到 worker 的远端网络路径。因此，本地 canary 成功与某个 Frontend 能否访问这个 worker，是两个观察结果。类似地，HTTP 状态接口表达的是该组件定义的状态：Frontend 的接流状态、Runtime 的依赖状态、模型的最低就绪条件，各有自己的含义。

真正的请求还要面对检查间隔之间出现的故障，以及只影响单条网络路径的问题。请求路径因此需要自己的错误传播和等待边界。适用路径配置后端响应无活动超时后，会限制等待下一次响应的时间；整条请求的 deadline 则限制总预算。这两种时间边界需要分别设置和理解。

这些信号通常并行到达。某个 Frontend 可能先遇到断连，稍后发现系统才移除成员；另一次故障则可能先触发 worker 主动退出。架构必须允许观察者按已经得到的信息采取行动。

## 三、失效隔离：用长期成员信息和局部反馈共同修正选择

**Dynamo 把“这个实例属于服务”与“这次选择应不应该使用它”分开处理。** 前者依赖服务发现，后者还消费请求故障、路由约束和负载信息。

下文的 Runtime client 是服务进程内部调用下游 endpoint（服务入口）的对象。它维护自己的成员与选路视图，使用它的组件可能是 Frontend，也可能是其他服务。

### 服务发现负责成员信息的收敛

在 etcd 模式中，worker 注册的 endpoint 记录附着 Runtime 租约，调用方 watch 这些记录来维护成员视图。正常退出可以主动注销，进程突然消失则依靠租约失效清除记录。

租约反映的是 Runtime 能否继续维持注册。它不能直接回答引擎是否还能生成 token，也不能让所有调用方在故障发生的同一时刻获得相同视图。主动注销、剩余租期与 watch 传播都会影响更新到达时间。

Kubernetes discovery 走另一条信息链：发现组件把 worker metadata 与 Pod 或容器的就绪状态结合，再向消费者提供成员变化。Metadata 还需要匹配所属 Pod 的 UID，避免同名 Pod 重建后，旧记录替新实例取得成员资格。

在 Kubernetes discovery 中，从健康检查到路由变化，中间存在明确的消费者关系：检查影响 Kubernetes 状态，发现组件消费状态，client 再更新本地成员视图。Etcd 模式则沿租约与注册记录更新，readiness 变化不会自动删除租约记录。某个健康接口变红，需要经过实际部署采用的信息链，才能影响后续路由。

### 局部抑制缩短等待，请求内排除约束恢复尝试

成员信息传播期间，已经遇到错误的调用方可以先减少无效派发。Dynamo 为此提供不同作用域的排除机制：

| 机制 | 状态归属 | 作用 |
| --- | --- | --- |
| Runtime client 的临时 inhibition | 该 client 及共享状态的 clones | 在适用选路路径上暂时回避刚出现目标或传输故障的实例 |
| 请求内失败目标集合 | 一条请求的迁移状态 | 在消费该状态的 KV 路由路径中排除这条请求已经失败的目标 |
| Discovery 成员移除 | 各个已经收到更新的成员视图 | 从服务成员层面停止后续选择 |

Runtime client 的局部抑制可以先于成员删除发生。它与 discovery 周期性对齐，发现更新也能触发对齐；配置中的对齐周期，并不等于每次失败之后都有一段精确的固定封禁时间。

请求内失败集合则维护另一种约束：即使短期成员视图仍包含原目标，同一请求的恢复尝试也可以记住此前的失败。这份状态需要路由路径实际消费，不能直接推广到所有 RR、random 或显式目标派发接口。

这套设计允许两个 Frontend 暂时对同一个 worker 作出不同判断：一个已经遇到连接错误，另一个仍可正常访问。局部故障反馈先保护已受影响的调用方，成员变化随后帮助更多消费者收敛。系统由此获得较快的响应，同时保留了网络故障具有局部性的事实。

## 四、请求迁移：保持外层请求，替换内部执行尝试

**Request migration 把一次逻辑请求组织成多个有界的执行尝试。** 外层客户端继续读取原来的响应，Frontend 在条件允许时替换下游执行。

### 迁移层为什么放在 Frontend 的推理流水线中

在本文基线的普通文本路径中，`Migration` 算子接在请求预处理之后、token Backend 与后续路由之前。请求沿流水线下行，响应沿相反方向返回。这个位置让迁移层既能拿到预处理后的请求，也能观察返回的生成 token。

这里的 token Backend 处理 token 与输出解码等逻辑。它与 GPU 上的推理引擎属于不同层次。

`Migration` 为请求创建 `RetryManager`，由它持有用于续接的请求、当前下游流、剩余尝试预算与相关迁移状态。客户端响应流的生命周期可以长于某一次 worker 执行，这正是中途更换执行目标的基础。

### 保存生成前缀，降低跨 worker 恢复的状态要求

假设输入上下文为 P，允许最多生成 80 个 token。迁移层已经观察到 30 个生成 token，记为 G，此时当前 worker 失效。

下一次尝试可以使用 P + G 作为上下文，并把剩余生成上限调整为 50。替代 worker 重新处理这段上下文，再生成后续内容。这个计数只包含迁移层(frontend)实际收到的 token；故障 worker 已经计算、尚未传回的结果不在其中。

这样的状态选择降低了对引擎执行现场的依赖。迁移层保留较轻的 token 上下文，替代 worker 通常通过重新 prefill 恢复继续生成所需的状态。代价是重复计算，以及两段输出之间可能出现停顿。

前缀重放还影响输出解释：替代 worker 把 G 当作输入，但用户仍应把 G 理解为同一次回答已经生成的部分。Frontend 因而需要调整 usage，并维护 token 进度与可见文字之间的关系。对于隐藏 stop 序列等解码缓冲，当前实现通过 checkpoint 在同一 Frontend 中重建输出解码状态。

这份 checkpoint 没有把完整引擎现场搬到新 worker。生成惩罚、thinking budget、约束解码状态等仍有各自的恢复边界，后续采样轨迹也可能变化。当前实现禁用 guided decoding、`n > 1` 等形态的迁移，体现的正是一个基本约束：只有保留下来的状态足以表达下一次执行，恢复尝试才有意义。

### 重试资格、预算与目标选择共同约束恢复

迁移按内部错误语义判断。连接失败、异常断流、引擎关闭或单个 worker 过载，可以进入资格检查；取消、总 deadline 到期和整个可用池耗尽，则要求结束恢复。

初始建流失败与中途流错误共享请求级重试预算，建立替代流失败也会消耗机会。请求显式 pin、阶段约束和路由资格还会进一步限制可选目标。该版本默认迁移预算为 0，需要显式启用。

这些约束保护了剩余容量。一个 worker 失效后，很多请求可能同时重放；无限重试会把恢复开销转移到幸存实例上。迁移因此必须与准入控制配合。

还有一个状态所有权边界：迁移上下文保存在 Frontend。另一个 Frontend 能接收新请求，并不意味着它能接回原 Frontend 丢失的 TCP/SSE 连接与请求进度。

### 五、过载保护：恢复流量也必须付出真实容量

**Dynamo 用路由层的负载判断和 worker 侧的准入记账共同限制工作进入。** 两层配合，才能处理遥测滞后、并发选择和故障后的流量集中。

### Router 判断“适不适合”，Backend gate 决定“现在能不能进”

Router 根据活跃 prefill token、decode KV 压力等信息标记 busy 目标，在选择阶段避开暂时不适合增加工作的容量。采用数据并行的 worker 还要区分各个副本，即 DP rank：一个 rank 已满，其他 rank 仍可能接收工作。

负载信息有传播延迟。多个 Frontend 可能根据相近的旧视图，同时选择同一个 worker。Backend admission gate 因而在更靠近执行的位置保留真实额度，充当进入引擎前的最后一道容量约束。

这套 gate 由 worker 的相关 backend endpoints 共享，并按 DP rank 管理限制；已声明 rank 的请求还要同时满足 worker 的汇总额度约束。它同时跟踪两种引擎额度：

| 额度 | 占用到什么时候 | 保护什么 |
| --- | --- | --- |
| Engine request | 响应流完成或被释放 | 已准入且响应流仍存活的请求数量 |
| Engine waiting | 首个真实生成 token，或请求完成 | 已准入、尚未产出首 token 的工作数量 |

两种额度需要同时取得。首个 token 只归还 waiting 额度，已经开始 decode 的请求仍占用总请求额度。控制消息和 bootstrap metadata 不能提前释放 waiting 额度。

这种拆分让系统可以分别约束执行中的工作和等待首输出的压力。首输出之前的工作可能包含排队、prefill 等成本，把它与持续 decode 的请求只记成一个计数，会丢失重要的容量信息。

### 队列吸收短期波动，也要防止压力无限积累

暂时拿不到引擎额度的请求，可以进入 backend 的有界队列。当前实现按 rank 保持 FIFO，再从可执行的队首中选择较早到达者，减少某个满 rank 阻挡其他 rank 工作的情况。

Router 也有自己的 policy queue，用于派发之前的等待。它与 backend 队列维护不同的状态、容量和到期规则；有界队列长度本身也不能保证等待时间有界。请求总时间仍需要自己的 deadline 约束。

队列耗尽时，明确拒绝可以阻止负载继续放大。Frontend 的相关过载路径默认返回 529；其他接口可能采用不同状态码。恢复逻辑需要继续识别错误范围：单 rank 满、整个 worker 满与整个候选池满，分别允许不同的后续选择。

Busy worker 通常还在完成已接收工作。系统因此把容量拒绝与故障成员移除分开：负载下降后，原实例可以继续接单；删除成员和重启容器会付出额外的恢复成本。

### 六、请求取消：让控制意图走到引擎，也让资源活到安全时刻

**取消既要结束无用计算，也要维护仍被其他阶段使用的数据。** 在流式生成和 P/D 分离系统中，“客户端已经离开”与“所有资源可以立刻释放”之间存在必要的协调。

### 请求上下文连接不同层的取消动作

Dynamo 通过请求上下文把一次工作在流水线中的身份和控制状态关联起来。`AsyncEngineContext` 提供请求标识、状态查询、异步等待，以及 stop、kill 等控制接口；正常关联的父子上下文还可以把取消意图传递到下游工作。

这组接口让各层不必各自发明一套“这条请求还要不要继续”的协议。Frontend 观察客户端断开后可以更新上下文；Runtime 将相应控制传向下游；backend 观察状态，再调用具体引擎的 abort 或清理逻辑。

上下文控制仍然需要执行方配合。即使接口叫 kill，它也不能直接替自定义 backend 终止底层 GPU kernel。适配层必须消费信号，并把它转换成引擎支持的动作。TCP 路径还可以通过连接断开感知上游消失；其他传输需要各自的取消机制。

因此，取消有三个不同完成点：意图已经传播，引擎工作已经停止，相关额度和 KV 资源已经回收。系统需要按实际资源生命周期处理这些阶段。

### P/D 分离把“计算结束”与“数据可以释放”分开

Prefill 产生 KV 后，Decode 可能还在建立传输或读取远端数据。此时立刻终止 Prefill 并释放其内存，会破坏另一侧仍然依赖的数据。

为处理这类依赖，Dynamo 的远端 prefill 路径会为工作建立独立的取消控制器，同时保留请求身份。这样，客户端取消可以改变逻辑请求的控制状态，而必要的 prefill 工作仍能按 KV 传输生命周期收尾。请求 ID 相同，控制器和资源存活时间仍可以不同。

在需要延后 abort 的分离式 decode 路径中，适配层要等待相应的安全输出边界。把统一请求接口连接到引擎的公共适配层（Common adapter），使用首个真实生成 token 作为允许 abort 的边界，bootstrap metadata 不满足这个条件。其他集成路径也按各自的引擎行为协调清理。

已经准备好暂存 KV（staged KV）、但 decode 接入尚未结束时，清理本身还可能需要完成必要的选路与派发。在本版本中，这类 Router 清理选路、记录与派发共用 120 秒预算；它约束的是这些路由动作，整个取消过程和远端资源回收各有自己的生命周期。预算耗尽后，本地可以结束等待，远端资源仍按自己的到期机制收尾。

这个设计同时保护两个目标：用户不再需要的生成应停止，而仍被跨节点操作使用的数据应保持有效。过早释放可能破坏正确性，无限保留则会占住后续请求需要的容量。

取消也因此与过载保护直接相连。Backend 队列中的请求取消，应释放队列空间；进入引擎的请求结束或流被释放，应归还 admission 额度。额度记账完成与远端 GPU 工作结束仍需各自协调，才能把容量真正交还给系统。

### 七、优雅退出：利用提前知道的信息，协调一次有界撤离

**缩容、滚动升级和维护为系统提供了提前协调的机会。** Graceful shutdown 利用这段窗口，把新流量撤离、在途请求结束和资源清理组织成有界流程。

Worker 的公共思路可以分成几个阶段：

1. 接收退出信号，撤销 endpoint 的发现资格并进入关闭过程。
2. 留出状态传播窗口，让其他调用方更新成员视图。
3. 按具体角色与后端协调在途执行、KV 传输和资源清理。
4. 在退出预算内关闭 Runtime 和进程，期限耗尽时执行强制收尾。

发现注销与关闭监听器是不同操作。传播窗口内，持有旧候选或已有连接的调用方仍可能送来工作；一段固定等待也无法保证所有长请求都完成。关闭机制必须为这些迟到请求和未完成工作保留明确结果。

### 不同组件排空的是不同对象

| 组件路径 | 关闭时需要协调的重点 |
| --- | --- |
| 集成式 Python worker | 注销、grace window、实际接入的 drain 或生命周期回调、引擎与 Runtime 收尾 |
| 公共 Worker 生命周期实现（Common Worker）/ Rust Sidecar | 尤其关注 prefill 在释放内存之前仍需维持的 KV 传输；具体引擎能力决定能否观测静止 |
| Frontend | 拒绝新的推理请求，等待已接收请求的完整响应体，并在预算内结束连接 |

Python 公共关闭流程允许不同 backend 接入不同回调。Common Worker 则有自己的 prefill 排空与外层退出期限。Sidecar 把 Runtime adapter 与原生引擎分开部署，还需要协调二者的退出顺序。这些实现共享目标，但排空对象和可观察能力各不相同。

以 Common Worker 的 prefill 路径为例，撤出发现与 grace window 之后，驱动在预算内等待传输静止。引擎若未提供可确认静止的实现，就采用保守的有界等待，再继续收尾；外层退出期限仍可强制结束进程。这里把“已经观测到静止”与“等待预算用尽”作为两种结果，避免仅凭时间流逝推断所有 KV 依赖都已消失。

Frontend 的在途计数同样需要尊重流式响应：响应头已经发出，生成工作仍可能持续很久。因此，排空许可要随响应体存活，直到流结束或被释放。进入 draining 后，新推理请求收到拒绝，原请求则获得在剩余预算内完成的机会。

### 时间预算把局部等待约束成整体退出

一次退出可能同时受传播窗口、drain timeout、引擎 cleanup、Runtime shutdown 与 Pod termination grace period 约束。某个内部阶段允许等待很久，实际执行仍受较短的外层期限限制。

有界退出为系统保留了终点。慢客户端、挂起传输或失效引擎都可能阻止正常完成，部署系统不能永远等下去。期限耗尽时，一部分请求仍可能中断。当下游执行失败而 Frontend 仍存活时，请求层可以依据迁移资格和剩余预算继续处理这些错误；Frontend 自身退出则需要在 HTTP 排空预算内收尾原连接。

突然宕机没有这段提前协调窗口。优雅退出降低计划变更对服务的冲击，请求迁移处理允许恢复的执行失败，两种机制覆盖不同的时间条件。

### 八、恢复容量：把健康的执行能力重新接回服务

**请求层能够替换执行尝试，依赖池中仍有合格容量；容量本身则需要 worker 生命周期和部署系统来恢复。**

Engine monitor 可以让失效 worker 退出，进程管理器、kubelet 或控制器负责相应层次的重启与重建。重新启动后，执行引擎、模型、endpoint、就绪状态与成员传播需要分别满足服务条件；具体顺序取决于集成方式，不能仅凭进程出现就认定容量已经恢复。

重建单位取决于故障域。单个服务进程、单卡引擎、P/D 角色，以及跨节点组成的多 rank 引擎，具有不同的依赖边界。多节点引擎的某个 rank 重启后，其他 rank 未必能沿用旧的通信与执行状态；需要按部署采用的 worker group 和组重启策略协调恢复。

这里可以区分三个恢复结果：

- **请求恢复**：原来的逻辑请求继续执行，并得到最终结果。
- **服务恢复**：系统重新能够接收并完成新请求。
- **容量恢复**：执行池重新获得预期的并发和吞吐能力。

幸存 worker 可以先恢复新请求的服务，替代实例随后补足容量；符合条件的原请求则可能在这个过程中迁移完成。权重加载、调度、重新 prefill 和数据传输都会影响耗时，因此一个检测间隔或某次成功建流，无法单独代表端到端恢复速度。

把各层重新放到一起，可以看到不同事件由哪些机制协作处理：

| 事件 | 请求侧的主要动作 | Worker 与容量侧的主要动作 |
| --- | --- | --- |
| 执行中的 worker 失效 | 传播尝试错误，按资格和预算重放续接 | 局部隔离、成员收敛、退出与重建 |
| 部分调用方访问失败 | 处理该调用路径的错误，在允许时替换尝试 | 按观察范围回避目标，等待发现与网络状态更新 |
| 存活实例暂时过载 | 排队、拒绝，或在容量语义允许时选择其他目标 | 保留成员身份，完成已有工作后归还容量 |
| 客户端断开 | 传播取消，协调引擎停止和请求清理 | 维护必要的跨阶段资源寿命，回收可复用额度 |
| 计划退出 | 结束或在允许时恢复受影响请求 | 撤销发现、排空、清理，并按部署目标调整实例 |

Dynamo 的容错能力，建立在这些状态所有权和协作边界上：Frontend 保存能够重放的请求进度，Runtime 与发现机制维护可用目标的视图，worker 管理引擎执行与资源寿命，部署系统负责重建执行能力。请求取消、重试预算、准入额度和退出期限，又共同限制恢复过程能消耗多少额外工作。

这种设计面对的是持续变化的局部事实：某条流已经失败，某个实例仍在传输 KV，另一个调用方尚未收到成员更新，剩余 worker 的容量也在变化。各组件在自己的职责范围内作出有界决策，系统才有机会同时维持请求正确性、流量可控性和可服务容量。
