## 引言

本文围绕三个问题展开：

1. GPU 运行里的 latency hiding 是什么？
2. Warp occupancy 是什么，受哪些资源限制？
3. 如果想提高 occupancy，一般有哪些手段？

个人理解，可以先把 **“已经驻留在 SM 上”** 和 **“当前可以发射指令”** 区分开，再看调度器如何利用这些 warp 覆盖等待时间。这样，延迟隐藏和 occupancy 就能连起来理解了。

## GPU Latency hiding

GPU 执行指令时也会遇到等待。例如，从全局内存加载的数据尚未返回，或者下一条计算指令依赖前一条指令的结果。

如果一个 warp 只能一直等到数据准备好，执行单元就可能空闲。GPU 的做法是：**当一个 warp 暂时不能继续发射指令时，warp scheduler 可以选择其他 ready warp 的指令，让执行单元继续工作。**

举个例子：

```text
Warp A：发射加载指令 → 等待数据返回 ─────────→ 继续计算
Warp B：                   发射独立的计算指令
Warp C：                            发射独立的计算指令
```

A 的访存等待仍然存在，但等待期间执行了 B、C 的有用工作，这就是 latency hiding（延迟隐藏）。如果其他 warp 也都在等待，调度器没有可发射的指令，执行单元仍然可能空闲。

### 为什么GPU切换warp很快？

CPU 的操作系统线程切换，通常需要保存和恢复线程上下文。而 GPU 中这些 warp 已经驻留在 SM 上，寄存器状态等执行上下文也已经保留在硬件中。

Scheduler 从 A 改选 B，通常不需要像操作系统切线程一样，保存、恢复整套上下文。因此，GPU 可以频繁选择不同 warp 的指令来覆盖等待。

> 经常说的“零开销切换”，强调的是驻留 warp 之间无需进行软件上下文切换。指令发射仍然受调度器、流水线和依赖条件限制。

理解这一点很关键：**A 等待时仍然驻留在 SM 上，并且继续占用已分配的资源；scheduler 只是改选 B 的指令。**

## Warp的驻留与调度

一次 kernel launch 会启动一个 grid，grid 中包含多个 block。常规 CUDA block 被分配到 SM 后，其中的线程按每 32 个线程组成一个 warp，最后不足 32 个线程也会占用一个 warp。

一个 SM 可以同时驻留多个 block，但数量受寄存器、shared memory 以及硬件上限约束。暂时没有足够资源的 block，需要等待后续调度。

Block 的驻留需要先分配资源，warp 的指令调度则是在驻留之后反复发生的过程。**驻留多少 warp，与当前发射多少 warp 的指令，是两个不同的问题。**

### Active、Eligible和Issued有什么区别？

| 概念 | 含义 |
| --- | --- |
| Unused | 所属 block 尚未获得 SM 资源，warp 还没有进入该 SM 的调度集合 |
| Active / Resident | warp 已驻留在 SM 上，尚未执行结束 |
| Stalled / Not eligible | warp 已驻留，但下一条指令当前不能发射 |
| Eligible / Ready | 下一条指令满足发射条件，可以被 scheduler 选择 |
| Selected / Issued | scheduler 选中了该 warp，并发射其指令 |
| Completed | warp 执行结束；所属 block 完成后释放相应的驻留资源 |

可以用下面的关系来理解某个调度时刻：

```text
Active / Resident：所有驻留 warp
├─ Not eligible：当前不能发射
└─ Eligible：当前可以发射
   ├─ Selected：当前被选中发射
   └─ Not selected：可以发射，但当前未被选中
```

**Active warp 不等于正在执行计算的 warp。** 正在等待访存结果、指令依赖或者同步的 warp，也属于 active warp。

同样，eligible warp 也不一定立即发射。一个 scheduler 的发射能力有限，其他 ready warp 需要等待后续选择。

### Warp为什么会Stalled？

| 原因 | 直观理解 | 可以关注的方向 |
| --- | --- | --- |
| Instruction fetch | 下一条指令尚未准备好 | 指令缓存、代码规模与控制流 |
| Memory dependency | 后续指令等待访存结果 | 访存模式、数据复用、预取和独立工作 |
| Execution dependency | 后续指令等待前面的计算结果 | 依赖链长度、独立指令数量 |
| Pipeline / Resource busy | 目标流水线或相关资源暂时不能接收请求 | 指令组合、执行单元吞吐、请求压力 |
| Synchronization barrier | 等待其他线程到达同步点 | 同步次数、线程工作量是否均衡 |

这里是概念分类，Nsight Compute 中的具体 stall 指标名称需要结合工具版本和硬件查看。出现 stall 也不一定说明 kernel 性能差：如果 scheduler 仍能持续发射其他 warp 的指令，等待可能已经被有效覆盖。

## Warp slot

Warp slot 可以理解为硬件管理一个驻留 warp 所需的位置。Slot 数量限制了可管理的驻留 warp 数，**slot 被占用不代表这个 warp 正在使用计算单元。**

以 A100（compute capability 8.0）为例，一个 SM 最多驻留 64 个 warp。它有四个 warp scheduler，按其 SM 分区组织，可理解为每个 scheduler 最多管理 16 个驻留 warp。这个数字描述的是驻留容量，不能理解成每个周期同时发射 64 个 warp 的指令。

不同架构甚至同代不同型号的上限也可能不同。例如，Ampere 的 compute capability 8.6 设备，每个 SM 的最大驻留 warp 数是 48。具体上限应查目标设备。

### Warp Occupancy

Occupancy 通常翻译为占用率，描述一个 SM 的驻留 warp 数占硬件最大驻留 warp 数的比例：

```text
Occupancy = SM 上的 active warp 数 / SM 最大支持的 active warp 数
```

例如，A100 的一个 SM 最多支持 64 个 warp。如果某个 kernel 的资源配置最多允许它驻留 32 个 warp，那么理论 occupancy 为 32 / 64 = 50%。

注意，分母是硬件支持的最大驻留 warp 数，不能用 CUDA Core 数量除以 32 来推算。CUDA Core 的执行能力和 warp 的驻留容量描述的是不同的硬件资源。

另外，还需要区分：

- **Theoretical occupancy（理论占用率）**：根据 kernel 的资源需求、launch 配置和设备上限，推算能达到的驻留比例。
- **Achieved occupancy（实际占用率）**：执行期间测得的平均驻留比例，还会受到工作量不足、block 执行时间不均衡、尾部阶段等因素影响。

### 哪些资源会限制Occupancy？

对于普通固定资源配置的 kernel，可以先用下面的关系理解：

```text
每个 SM 的最大驻留 block 数 = min(
    寄存器容量允许的 block 数,
    shared memory 容量允许的 block 数,
    线程数 / warp 数上限允许的 block 数,
    硬件最大驻留 block 数
)

每个 block 的 warp 数 = ceil(block 中的线程数 / 32)
```

真实硬件还有资源分配粒度和分区约束，因此手算主要用于理解，精确结果应结合 occupancy 工具。

**1. 寄存器**

每个线程通常需要寄存器保存私有变量和中间结果，SM 的寄存器总量有限。每线程用得越多，一个 block 的寄存器需求就可能越大，可同时驻留的 block 数也可能减少。

例如，假设一个 SM 有 65,536 个 32-bit 寄存器，每个 block 有 256 个线程，每线程使用 64 个寄存器：

```text
每个 block 的寄存器需求 ≈ 256 × 64 = 16,384
寄存器允许的 block 数 ≈ 65,536 / 16,384 = 4
4 个 block × 每 block 8 个 warp = 32 个 warp
```

在最大支持 64 个 warp 的 SM 上，只考虑这一项限制，occupancy 上限就是 50%。这里忽略了分配粒度，其他资源还可能进一步限制驻留数量。

**2. Shared memory**

Shared memory 通常按 block 分配。Tile 越大、缓冲区越多或者流水线 stage 越多，每个 block 的 shared memory 需求就可能越大，SM 能同时容纳的 block 数随之减少。

例如，假设可分配的 shared memory 为 128 KiB，每个 block 使用 48 KiB，那么单看这一项最多容纳 2 个 block。这是说明资源约束的假设例子，具体容量要以目标设备及配置为准。

**3. Block size与硬件上限**

Block size 决定每个 block 有多少线程和 warp，也会影响寄存器总需求。Block 太大，可能只剩少量 block 能驻留；block 太小，则可能先碰到最大驻留 block 数上限，warp 数却还没有填满。

所以，block size 和 occupancy 之间并不是简单的单调关系。一般可以优先尝试 32 的整数倍，但最终仍要结合算子的任务划分和测量结果。

### 提高Occupancy与性能调优

如果想把Occupancy打满，有哪些手段？

先判断限制来自哪里，再调整对应资源：

| 限制来源 | 可以尝试的调整 | 需要同时观察的代价 |
| --- | --- | --- |
| 寄存器 | 减少同时存活的中间变量，调整展开程度、每线程任务量或 register tile | 可能增加重复计算、指令数量或寄存器 spill |
| Shared memory | 缩小 tile、减少缓冲区或流水线 stage、改善存储复用 | 可能减少数据复用和访存计算重叠 |
| 线程 / warp 数上限 | 调整 block size，改变任务划分 | 可能改变同步成本、访存模式和每 block 资源需求 |
| 最大驻留 block 数 | 在任务允许时增大 block，让每个 block 包含更多 warp | 其他驻留资源可能成为新限制 |
| Grid 工作量不足 | 提供更多可独立执行的 block，调整任务切分 | 切分过细可能增加归约或重复加载成本 |

最后一项主要影响实际设备利用情况：即使资源配置允许很高的理论 occupancy，如果 grid 太小，没有足够的 block 分给各个 SM，实际执行也无法充分利用设备。

### 为什么Occupancy越高，不一定越快？

Occupancy 提供的是更多可供调度的驻留 warp，但真正能覆盖等待的，是其中可发射的指令。

**第一，active 多，不代表 eligible 多。** 如果很多 warp 都在等待同一类访存或同步，驻留数量再多，也可能缺少 ready work。

**第二，提高 occupancy 可能牺牲每个 warp 的效率。** 例如，为了减少 shared memory 缩小 GEMM tile，虽然能驻留更多 block，却可能降低数据复用，增加全局内存流量。减少流水线 stage，也可能削弱搬运与计算的重叠。

**第三，强行压低寄存器用量可能引入 spill。** 常见情况下，部分值会转入 local memory，增加额外访存；具体行为还取决于编译器和配置。因此不能只看寄存器数量下降，还要检查生成代码和执行耗时。

**第四，较低 occupancy 也可能已经足够。** 如果每个 warp 内有足够多的独立指令，或者执行单元、内存带宽已经充分利用，继续增加 warp 未必带来收益。

> 调优时需要找到足够隐藏延迟的并行度，并兼顾数据复用和每个 warp 的执行效率。最终判断依据是 kernel 耗时与吞吐量。

### 实际排查时怎么看？

可以沿着下面的顺序理解 profiling 结果：

```text
Active warp 少
→ 看寄存器、shared memory、block size 与 grid 工作量

Active warp 多，但 Eligible warp 少，发射经常空闲
→ 看访存依赖、计算依赖、同步与资源阻塞

Eligible warp 足够，指令持续发射
→ 看具体执行单元和内存系统的吞吐瓶颈
```

使用 Nsight Compute 时，可以结合 Occupancy、Scheduler Statistics、Warp State Statistics，以及计算和内存分析来判断。
