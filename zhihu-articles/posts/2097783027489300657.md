### 0. 定义与大纲

> **“Context engineering is the delicate art and science of filling the context window with just the right information for the next step.”** —— Andrej Karpathy 
>  **上下文工程：用恰如其分的信息填满上下文窗口的精妙艺术与科学——为下一步服务。**

大纲：① 动机（上下文腐烂 Context Rot、token 成本、提示缓存 Prompt Caching）；② 作为架构思维的上下文工程；③ 技术：写上下文（Write）、选上下文（Select）、压缩上下文（Compress）、隔离上下文（Isolate）。

---

### 1. 动机

### 1.1 上下文窗口很快会被填满

当前模型上下文窗口 **128k～1M token** （128k token ≈ 200 页文本）——但 **反复的工具调用与长任务会迅速填满它** 。

### 1.2 上下文腐烂（Context Rot）

> **Context Rot：随着输入上下文变长，LLM 的准确性与可靠性退化。**

![](https://pic3.zhimg.com/v2-261ca3ac360d408d4f9a048871c5604e_r.jpg)

*图 1　Context Rot 实验（ [http://research.trychroma.com/context-rot](http://research.trychroma.com/context-rot) ）：输入越长性能越差——长上下文≠可靠利用长上下文。*

> **【补充知识】** “大海捞针”（NIAH）测试是检验长上下文利用的经典实验：把一句关键事实埋进长文档的某个位置，看模型能否检索出来。Chroma 的实验进一步表明：即使模型声称有 1M 窗口， **把无关材料堆进去会稀释注意力** （distraction effect），且模型对 **中部信息** 的利用差于首尾（lost in the middle，Liu et al., 2023, TACL）。这与第 3 讲 ICL 的顺序敏感性是同一现象的不同表现。

### 1.3 token 成本：智能体又贵又慢

![](https://pic4.zhimg.com/v2-bf078e0b7b9657f71804f438daf9bfa3_r.jpg)

*图 2　智能体成本实测（该组 WWW 2026 论文）： **接口选型直接决定成本** ——HTML 界面每任务 24 万 token，RAG/NLWeb 只需 ~5-7 万 token，且 RAG 的 CR/F1 还最高。*

### 1.4 提示缓存（Prompt Caching）

![](https://pic4.zhimg.com/v2-b0ae6a442bfc2a56afd6b9fa60e8efa7_r.jpg)

*图 3　Prompt Caching：缓存处理过的提示前缀的 Transformer 状态（keys & values），相同前缀的后续请求直接加载、不重算。*

要点：

- 存储处理过的 **前缀** 的 KV 状态；第二请求同前缀则加载、不重算 → **省算力** ；
- **但 10 万 token 的 KV 要占数 GB 内存** ——存在 GPU 显存或同机存储；
- 后续请求按 **前缀** 路由到 **同一台机器** （这是缓存命中与运维复杂度的来源）。

![](https://picx.zhimg.com/v2-fc6839534a679a2f4e78992632609761_r.jpg)

*图 4　缓存 token 的折扣（cached input 通常为原价 10%–25%）。*

![](https://pic2.zhimg.com/v2-0183be51b037b21723f55fc82314546f_r.jpg)

*图 5　TTFT（time to first token）vs prompt token 数：命中缓存后首 token 时延大幅下降且几乎不随上下文增长（OpenAI cookbook 实测）。*

**对上下文工程的直接启示** ：

- **把稳定内容块放前面** （stable prefix：system prompt、工具定义、长文档）；
- 动态内容放后面（dynamic suffix：用户输入、检索块、会话状态）；
- **避免缓存未命中与更新** ——它们很贵！

### 2. 上下文工程作为架构思维

- **按”内容块（content blocks）”思考** ；
- 问自己： **哪些块与 LLM 当前这一步相关** ？这些块的 **最佳顺序** 是什么（既要答得好，又要避免缓存失效）？

![](https://pic4.zhimg.com/v2-8d10e6d5df89dc59ad43decd84f2cdb7_r.jpg)

*图 6　Prompt vs. Context Engineering（Anthropic）：提示工程面向 **单次查询** ；上下文工程面向 **智能体多轮轨迹** ——核心动作是”策展（Curation）”。*

![](https://pic1.zhimg.com/v2-5bb11c900340a11c8d1094fca69e9bce_r.jpg)

*图 7　真实智能体的上下文账本：一半以上被 **消息历史** 占用——这正是压缩技术要处理的对象。*

> **【补充知识】** 这张 `/context` 面板是理解上下文工程的最佳实物教材：① 消息历史（52.6%）是最大头——长轨迹agent的上下文基本被历史淹没；② 系统工具 + MCP 工具定义（~17k）是固定成本—— **每挂一个 MCP server 都在收”上下文税”** （呼应第 4 讲的工具检索）；③ Claude Code 的 autocompact buffer（16.5%）是 **为压缩预留的空间** ——到阈值就自动摘要，与 3.3 节的 Context Summarization 对应。

### 3. 四大技术

四大技术及其定位（ [http://rlancemartin.github.io/2025/06/23/context_engineering/](http://rlancemartin.github.io/2025/06/23/context_engineering/) ；LangChain 博客）：

| 技术 | 做什么 |
| --- | --- |
| 写上下文（Write） | 把可能之后有用的信息显式写到上下文窗口之外（文件、记忆）支持智能体完成任务 |
| 选上下文（Select） | 按需把相关信息拉进上下文窗口，帮助完成任务并保持上下文聚焦 |
| 压缩上下文（Compress） | 只保留任务所需部分，给臃肿的上下文瘦身 |
| 隔离上下文（Isolate） | 把上下文拆分（如分给子智能体），或隔离大上下文，只为特定（子）任务提供相关上下文 |

**实现路径** ：这些技术由 **系统提示中的指令** （解释有哪些功能/工具、该怎么用）与 **agent harness 的功能** （文件/键值存储、检索信息/工具描述/示例、调 LLM 压缩历史、管理多智能体通信）组合实现。

### 3.1 写上下文（Write Context）

**思想** ：把之后可能相关的信息存到上下文窗口 **之外** ——只保留与下一次 LLM 调用相关的信息；帮助 LLM 聚焦当前任务；支持按需检索。典型场景：记住以往解决问题的经验、存中间结果（RAG 场景下写了一半的论文）。

**常见机制** ：

- **记忆（Memory）** ：

- **草稿本（Scratchpad）** ：

![](https://picx.zhimg.com/v2-83e8e3a3652d559428e3836f14105c2d_r.jpg)

*图 8　Scratchpad 概念与实现（LangChain 的 `write_todos` 中间件即典型实现：复杂目标先拆 todo、随做随划掉、可随时修订）。*

**长期记忆** ：把持久性扩展到单个任务/会话之外——智能体可保留偏好、有用的历史交互等；ChatGPT、Claude、Cursor 等工具已广泛采用；通过存文件或向量库实现； **LLM 可自动创建和更新记忆** （如每轮反思后自省、从历史反馈周期性综合）。

![](https://pic3.zhimg.com/v2-8162a05d9753b0df3a6d99f8158ab5e4_r.jpg)

*图 9　LangChain 长期记忆的系统提示写法：记忆写入规则（何时写/何时不写）直接决定记忆质量。*

> **【补充知识】** 记忆系统设计的核心难题是” **写什么** “（retrieval & write policy）：全量存 → 检索噪声大；只存显式指令 → 记忆稀疏。业界趋势是把记忆分层（情景记忆 episodic / 语义记忆 semantic / 程序性记忆 procedural），并用 LLM 在每轮结束自动提炼”本次对话值得记的事实”。安全上要注意： **记忆是新的攻击面** ——恶意内容可能被写入记忆并在后续会话被”激活”（记忆投毒）。

### 3.2 选上下文（Select Context）

按需把信息拉进上下文窗口，支持智能体表现——允许 **细粒度控制每步 LLM 看到什么** ；可提升专注度、工具使用与任务表现； **需要仔细过滤** 以避免无关内容或工具。五种机制：

1. **草稿本检索** （Scratchpad retrieval）
2. **记忆检索** （Memory retrieval）
3. **通过 Skills/RAG 做工具搜索** （Tool Search）
4. **通过 Skills/RAG 做知识检索** （Knowledge Retrieval）
5. **上下文学习的示例选择** （Demonstration Selection，见第 3 讲）

**智能体技能（Agent Skills）** ： **技能 = 指令、脚本与资源的文件夹** ，智能体可发现并使用它们以更准确高效地做事；提供 **程序性知识** 与公司/团队/用户专属上下文——相当于”操作指南（how-to guides）”。

![](https://pic2.zhimg.com/v2-4ab32f71d164ea4e89c5c21ff7ecf9d3_r.jpg)

*图 10　Skills 的渐进式披露（progressive disclosure）：每个 skill 定义 **触发器** 决定何时加载；元数据常驻、指令触发时加载、资源/代码用到时才加载。*

![](https://pic3.zhimg.com/v2-8f4bd3fb47ec3ba859df5efe9f1d7084_r.jpg)

*图 11　技能生态示例（Anthropic/OpenAI skills 仓库、clawhub.ai）。*

**技能设计准则** ：① 核心技能保持简洁、细节放进被引用文件；② 描述带关键词与清晰触发条件；③ **渐进式披露** （元数据始终可见 → 触发时加载指令 → 需要时才加载资源/代码）；④ 把复杂任务组织成显式工作流/检查清单；⑤ 加反馈循环与验证步骤。

**工具搜索（Tool Search）** ：给智能体** upfront 塞全部工具定义**——上千工具时不可扩展，且无关上下文伤性能。常见解法：通过 **skills** 或 **单个元工具（meta tool）做工具发现** 。 **Anthropic 报告上下文占用减少 90%** ，同时可扩展到上千工具。

两种模式：

- **检索式工具搜索** ：把工具描述嵌入稠密向量空间，语义搜索取最匹配的工具（Anthropic cookbook 示例）；
- **选择器式工具搜索** ：用 **次级 LLM** 从工具库中选相关工具（LangChain DeepAgent 提供）。

![](https://pic1.zhimg.com/v2-28862ed0f2edc31255c8ab479a0994c2_r.jpg)

*图 12　Tool Search 的 DeepAgent 实现：selector 中间件”幕后”换工具，主智能体无感。*

### 3.3 压缩上下文（Compress Context）

**目的** ：从上下文削减 token——只保留相关信息、 **避免大海捞针问题** ；应对长交互历史与重型工具调用；降低窗口占用、时延与成本。 **挑战：保住重要细节** 。两种机制：

**① 上下文修剪（Context Trimming）** ：删除/裁剪而非重写；常基于规则或启发式（丢最老消息、丢冗长工具结果的一部分）；比 LLM 摘要简单便宜。

- **问题 1** ：规则设计不好可能误删相关内容；
- **问题 2** ： **修剪可能使提示缓存失效** ——修剪后的调用可能贵 10 倍！设计决策： **裁还是不裁？缓存什么？**

![](https://pic4.zhimg.com/v2-865857b8fc8405936cd1b36cc379347d_r.jpg)

*图 13　上下文修剪实现：按长度阈值触发、保留最近 N 次工具调用。*

**② 上下文摘要（Context Summarization）** ：用（另一个）LLM 把长交互历史摘要成短表示。策略： **递归摘要** （反复摘要内容块、再摘要摘要）与 **层级摘要** （先小单元、再合并成保留原结构的高层摘要）。

![](https://picx.zhimg.com/v2-6a1bf2bc737399e12e7400938fcc005f_r.jpg)

*图 14　上下文摘要实现：不改系统提示；摘要提示本身是一份”上下文抽取检查清单”。*

> **【补充知识】** 修剪与摘要的选择本质是” **确定性 vs 语义保真** “的权衡：修剪便宜、确定、可复现，但丢信息；摘要保语义但引入 LLM 调用成本与新的不确定性（摘要本身可能失真或幻觉）。生产上常见组合： **保留全部近期消息 + 对中段历史滚动摘要 + 关键事实落长期记忆** （即 Claude Code 的 autocompact 思路）。另注意 3.3 的缓存陷阱： **任何改动历史中段的行为都会使后续缓存全部失效** ，所以”追加式摘要”（只在末尾追加、不改写前文）比”就地改写”更友好。

### 3.4 隔离上下文（Isolate Context）

把上下文拆成独立部分——降低单窗口过载；让不同子任务用不同指令与工具；通过保持上下文窄而相关来提升模型专注度； **需要协调以保持各隔离上下文对齐** 。三种机制：

**① 多/子智能体（Multi-/Sub-Agents）** ：把工作分给多个各有独立上下文窗口的子智能体；每个有自己的任务、工具与指令；可探索问题不同侧面；复杂任务上 **可超过单智能体** 。挑战：token 用量高、协调开销、需要仔细规划。

![](https://pica.zhimg.com/v2-9c1eecabcfd6532a9047c479cd8dd1c4_r.jpg)

*图 15　子智能体委派工具的设计：连”何时不要用”都写进系统提示——这是”写上下文”技术在起作用。*

**② 执行环境（Execution Environments）** ：把部分工具调用移出 LLM 上下文窗口、放进执行环境（如编码智能体的 Python 解释器）；工具调用在沙箱运行、 **只有选定的结果返回模型** ；适合隔离文件、图像、中间输出等重型 token 对象。

**③ 结构化运行时状态（Structured Runtime State）** ：把信息存在运行时 state 对象而非直接放上下文窗口；state 可按 schema 组织（消息、计划、结果等带类型的字段）； **每步只暴露选中的字段** ；支持对模型可访问内容的细粒度控制。

---

### 4. 小结

- 长轨迹 + 工具定义/调用及其结果会 **迅速填满上下文窗口** → **context rot 致准确率损失** + 高成本高时延；
- 上下文工程 = **在正确的时机、以正确的顺序，给 LLM 正确的信息** ：
- 做得好的上下文工程提升 LLM 智能体的 **质量、效率与可扩展性** 。
