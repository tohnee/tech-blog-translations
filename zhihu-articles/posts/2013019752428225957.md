> 这不是一篇”10 个常见坑”的泛泛之谈。每一个坑都来自 SpinMuse 的实际开发过程——有些让服务挂掉，有些让用户困惑，有些让 AI 变蠢。我们不仅踩了，还找到了根因并给出了生产级的解决方案。

---

### 一、Agent 智能层：让 AI 变聪明比想象中难

### 坑 1：给 LLM 太多工具，它就选错

**现象**：用户说”测试一下 recomserver 的服务状态”，AI 没有直接调用 `mlops_test_service`，而是先初始化沙箱、拉取代码、写测试脚本，绕了一大圈。

**根因**：当 LLM 面前有 22 个工具时，它会”过度思考”。`sandbox_init` 和 `mlops_test_service` 对它来说都像是合理选择，它倾向于选择”更安全”的复杂路径。

**解法：意图分类 + 工具精准筛选**

我们在 Agent Loop 前增加了一层**需求分发专员**。每条用户消息先经过关键词匹配 + 历史上下文感知，分类为 5 种意图（ops_task / readonly / coding / complex / general），每种意图只暴露最相关的 3-6 个工具。

关键创新：**历史上下文延续**。如果前几轮一直在聊”测试服务”，用户突然说”换个参数再试”——虽然当前消息不含任何服务关键词，系统也能识别为 ops 延续，继续只暴露运维工具。

**效果**：工具选择准确率从约 70% 提升到 95%+。”测试服务”不再触发沙箱初始化。

---

### 坑 2：LLM 执行完工具后”失忆”

**现象**：AI 成功读取了代码文件，但后续回复完全不提代码内容，只说”我已经读取了文件”。或者执行完服务测试后，不总结结果，直接说”已完成”。

**根因**：工具返回的原始结果太大（一个代码文件可能 50KB），塞进上下文后超出模型的有效注意力窗口，模型”看到了但没理解”。反过来，简单截断又丢掉关键信息。

**解法：智能工具结果压缩 + 验证合同**

我们按工具类型定制压缩策略：代码读取保留头 70% + 尾 30%（上限 12KB），保留 import 和类定义；命令执行保留 exit_code + 完整 stderr + stdout 头尾；文件浏览只保留前 25 条 + 总数统计。

更关键的是”验证合同”——每次工具执行后，自动注入一条后续行为指令。例如 `mlops_read_code` 成功后注入”请用中文总结代码结构和关键逻辑，不要重复读取”。这相当于给 LLM 一个明确的”下一步该做什么”的指引。

**效果**：工具调用后的有效输出率从不到 50% 提升到 90%+。

### 坑 3：不同 LLM 供应商的”兼容性地雷”

**现象**：用硅基流动的 DeepSeek 模型时，请求直接报 400 错误：”System message must be at the beginning”。换用智谱 GLM 时没问题。

**根因**：SpinMuse 的 Agent 系统会在对话中间插入 system 消息（记忆注入、验证合同、行为指导等）。这在 OpenAI 和智谱 API 上没问题，但硅基流动严格要求 system 消息只能有一个且必须在 index 0。

**解法：Provider 层消息清洗**

在每次 API 调用前，自动执行 `_sanitize_messages()`：将开头连续的多个 system 消息合并为一个；将中间出现的 system 消息转为 user 角色。上层代码可以自由插入 system 提示，不需要关心底层供应商的限制。

**教训**：OpenAI 兼容协议≠真正兼容。每个供应商都有自己的”潜规则”，必须在 Provider 层做统一适配。

---

### 坑 4：Agent 在工具调用后返回空内容

**现象**：AI 调了工具、拿到了结果，但最终给用户的回复是空白的。后端日志显示 “LLM returned empty content after tool calls”。

**根因**：部分模型在处理完 tool_call 后，认为”任务已完成”而不再生成文字回复。特别是当工具结果已经很完整时（如服务测试返回了详细 JSON），模型觉得”没什么好补充的”。

**解法：空内容检测 + 摘要重调**

在 Agent Loop 中增加空内容检测：如果 LLM 在工具调用后返回空白，自动追加一条”请用中文总结以上工具执行结果”的提示，重新调用一次 LLM 生成摘要。最多尝试 2 次。

---

### 坑 5：上下文膨胀让 AI “变蠢”

**现象**：对话到第 10 轮之后，AI 的回复质量明显下降——开始重复之前说过的话，或者给出与上下文矛盾的建议。

**根因**：不是 token 超限的问题（远没到上限），而是**信噪比下降**。当上下文中混杂了 10 轮对话 + 3 次工具结果 + 记忆注入 + 系统提示，模型的注意力被稀释。

**解法：做减法的上下文管理**

这是 SpinMuse 最核心的设计哲学之一：

- **记忆按场景过滤**：mlops 对话不注入 consulting 相关的历史记忆
- **工具结果即用即弃**：Agent Loop 每轮迭代后，压缩前轮工具结果
- **历史对话清洁**：跳过空消息、截断过长的 assistant 回复、对齐消息角色
- **Feature tag 行为约束**：4 种 MLOps 子模式各有独立的行为指令集，不会互相干扰

反直觉的结论：给 AI 更少但更精准的信息，比给更多信息效果好。

### 二、MLOps 服务管理：生产环境容不得半点马虎

### 坑 6：Kill 掉服务后状态不更新

**现象**：手动用 `kill` 命令终止了一个 gunicorn 服务，但页面上的状态仍然显示”运行中”。刷新页面也不变。

**根因**：启动脚本使用了管道 `exec gunicorn ... | while read ... done`。管道导致 `exec` 无法真正替换 bash 进程，存储在数据库中的 PID 是 bash 管道宿主进程的 PID，不是 gunicorn 的真实 PID。用户 kill 的是 gunicorn，但 bash 包装进程还活着，`os.kill(pid, 0)` 仍然返回”存在”。

**解法：双重检测 + 脚本修复**

- 修复启动脚本：去掉管道，改用 `> log 2>&1` 直接重定向，让 `exec gunicorn` 真正替换 bash 进程
- `get_service_status()` 增加端口检查：PID 存在 **且** 端口被监听才算”运行中”
- 检测到 stopped 时同步清除数据库中的 PID 字段，避免残留 PID 持续误判

**教训**：在 Unix 进程管理中，`exec` 与管道的组合行为是反直觉的。存储的 PID 不一定是你以为的那个进程。

---

### 坑 7：三个 API 端点重复检查 PID，性能浪费

**现象**：后端日志中 `/mlops/api/services/global-status` 每 15 秒触发一次，`/api/services/health` 每 30 秒触发一次，`/api/projects/{id}/services` 每次用户操作都调用。三个端点都在做 `os.kill(pid, 0)` 检查。

**解法：单一真相源**

只保留 `/api/services/health` 做 PID+端口双检查并更新数据库。`global-status` 和 `loadServiceConfigs` 改为只读数据库，不再做系统调用。轮询频率统一为 30 秒。

当 health 检测到状态变化时，通过前端联动自动刷新 serviceConfigs 列表和项目健康摘要。

---

### 坑 8：健康标签不同步——”3⁄3 运行中”的谎言

**现象**：SERVICE 列表已经正确显示某个服务为”已停止”，但旁边的 “3⁄3 运行中” 小标签仍然是绿色的。

**根因**：全局健康条 `healthSummary`、项目列表小绿点 `projects[].health`、SERVICE 旁边的标签 `activeProject.health` 来自不同的 API，更新时机不一致。`_pollHealth()` 更新了全局数据，但没有同步 `activeProject.health`。

**解法：单次轮询驱动全面同步**

每次 `_pollHealth()` 返回数据后，直接从响应中提取各项目的健康计数，立即同步到 `activeProject.health.prod` 和 `projects` 列表的 `health` 字段。不依赖额外的 API 调用，一次轮询驱动所有 UI 元素同步更新。

**教训**：前端多个 Alpine.js 组件引用同一份数据时，更新一处不等于更新所有引用。必须在数据源头做统一分发。

---

### 坑 9：服务启动时用户看到”空白等待期”

**现象**：点击”确认启动”后，弹窗立即消失，但过了好几秒才出现”启动成功”的提示。中间用户不知道系统在干什么。

**根因**：确认按钮的处理流程是——关闭弹窗 → 显示 toast → await API → 显示结果 toast。Toast 有 2.5 秒自动消失，但 API 可能耗时 5-10 秒，中间出现了”真空期”。

**解法：弹窗保持打开 + 逐服务进度面板**

- 弹窗在 API 完成前保持打开，按钮变为”执行中…“并禁用
- 弹窗内显示实时进度面板：百分比进度条 + 逐服务状态列表
- 批量重启时，前端逐个调用单服务启动 API，每完成一个更新进度
- 每个服务有 4 种状态图标：○ 待启动 → ◎ 正在启动 → ✓ 成功 → ✗ 失败
- 全部完成后短暂展示结果，再关闭弹窗并弹出汇总 toast

**效果**：用户全程可见进度，不再有”空白等待期”。

---

### 坑 10：服务版本选择”形同虚设”

**现象**：在启动弹窗中选择了”其他版本”并选定 v0.3，但服务实际启动的还是当前版本 v0.1。

**根因**：版本选择下拉框的 `selectedVersion` 初始值被设为当前版本，且选择下拉框时没有自动切换 `verMode` 为 `'other'`。结果 `_svcLaunchVersion()` 函数始终读取的是 `current` 模式对应的版本。

**解法**：初始化 `selectedVersion` 为空字符串；下拉框增加 `@change` 事件自动切换 `verMode`；增加一个 disabled 占位选项 “选择版本…“，明确告诉用户需要做出选择。

**教训**：表单的默认值和联动逻辑必须从用户操作路径的角度去验证，而不是从代码逻辑的角度。

### 三、日志与监控：看起来简单，做对很难

### 坑 11：业务监控日志不断重复增长

**现象**：业务监控面板中的错误日志条目不断增多，即使没有任何请求发往服务。所有条目的时间戳都相同，明显是历史重复。

**根因**：两个层面的问题叠加——

第一层：LogWatcher 启动时，所有文件的 offset 从 0 开始，会把日志文件的全部历史内容当作”新内容”读入内存。

第二层：前端使用 EventSource 做 SSE 实时推送。EventSource 断线后自动重连，而每次连接（包括重连），服务端的 `subscribe()` 方法都会发送最近 20 条历史记录作为 catch-up。前端将这些条目追加到 `monitorLines`，不做去重。结果：每 30 秒心跳超时重连一次，每次追加 20 条 → 日志无限膨胀。

**解法**：

- LogWatcher 启动前先扫描所有日志文件，将 offset 初始化为当前文件大小（只监控启动后的新内容）
- 每条日志分配递增 ID，SSE 响应中发送 `id:` 字段
- `subscribe()` 接受 `last_event_id` 参数，重连时跳过已发送的条目
- 前端每次打开 Monitor tab 时清空旧数据，从干净状态开始

---

### 坑 12：服务日志无限追加，重启后看到的全是旧日志

**现象**：重启服务后查看”服务日志”，看到的是上一次甚至上上次启动的日志内容，新的启动信息淹没在大量旧日志中。

**根因**：启动脚本使用 `>>` (append) 模式写入日志文件。每次重启都追加到同一个文件末尾。

**解法**：启动脚本中，在 `exec gunicorn` 之前先用 `: > file` 清空 run_log、access_log 和 error_log，stdout 改用 `>` (覆盖) 模式。每个服务有独立的日志文件（如 `run_recomserver_8903.log`），同批次启动的多个服务互不影响。LogWatcher 的文件截断检测机制（`size < prev_offset → reset`）自动适配这一变化。

### 坑 13：侧边栏错误计数与页面不同步

**现象**：在 MLOps 页面点击”清除全部”清空业务错误后，页面上的计数变为 0，但侧边栏”模型运维”旁边的错误徽标还显示原来的数字。

**根因**：侧边栏的 `sidebarMLOps()` 和主页面的 Alpine 组件是两个独立的 Alpine 实例，没有通信机制。清除操作只更新了页面内的 `globalErrors`，侧边栏组件完全不知情。

**解法**：通过 `window.dispatchEvent(CustomEvent)` 实现跨组件通信。页面清除错误时派发 `spinmuse:err-update` 事件；侧边栏监听该事件并立即同步 `errCount`。同时，侧边栏自身的轮询也读取 `sessionStorage` 中的清除时间戳，避免下次轮询后数字”回弹”。

### 四、数据库与架构：小选择大影响

### 坑 14：SQLite 写锁导致历史对话加载卡顿

**现象**：AI 助手的历史对话列表经常显示为空，需要连续刷新好几次才能加载出来。

**根因**：所有用户的对话记录、AI 调用日志、知识条目、记忆都写在同一个 SQLite 数据库中。AI 对话场景的写入非常密集（每次对话涉及消息保存、token 统计、记忆合并等多次写操作），频繁触发 SQLite 的写锁，阻塞了其他用户的读操作。

**解法：双数据库架构**

系统元数据（用户、项目、策略、实验、配置）共享一个主库；上下文数据（对话、日志、知识、记忆）每个用户一个独立 SQLite 库。用户注册时自动创建专属数据库。通过 `UserDBManager` + Peewee 的 `DatabaseProxy` + LRU 缓存实现请求级别的动态数据库绑定。

**效果**：用户 A 的密集对话不再阻塞用户 B 的知识检索。

### 坑 15：编辑器选型的三次失败

**现象**：

- V1 CodeMirror 5：多文件切换时 `swapDoc` 频繁报错 `Cannot read properties of undefined (reading 'map')`，编辑后页面挂死
- V2 Monaco Editor：2.5MB 的体积导致页面加载极慢，在某些网络环境下白屏

**解法：最终选定 Ace Editor**

300KB 体积，CDN 单文件加载。`EditSession` 机制天然支持多文件切换——每个文件一个独立 session，切换只需 `editor.setSession(session)`，原子操作，不存在 CodeMirror 的 swapDoc 状态冲突。

**教训**：前端库的选型，”功能丰富”不等于”适合你的场景”。代码编辑器这种重型组件，稳定性和体积比功能更重要。

### 五、总结：15 个坑的分类与教训密度

| 类别 | 坑 | 核心教训 |
| --- | --- | --- |
| Agent 智能 | 工具选错 | 工具集越小越精准，意图分类是前置关键 |
|  | 执行后失忆 | 工具结果要压缩 + 验证合同引导下一步 |
|  | 供应商兼容 | OpenAI 兼容≠真兼容，Provider 层必须做消息清洗 |
|  | 空内容回复 | 必须有兜底：检测空回复 → 主动要求摘要 |
|  | 上下文膨胀 | 做减法而非加法，信噪比比信息量更重要 |
| 服务管理 | PID 误判 | exec + 管道 ≠ 真正替换进程，需 PID + 端口双检测 |
|  | 重复检查 | 单一真相源原则，只让一个端点负责状态更新 |
|  | 标签不同步 | 数据驱动 UI 时，必须在源头做统一分发 |
|  | 空白等待 | 异步操作必须有全程可见的进度反馈 |
|  | 版本失效 | 表单联动从用户操作路径验证，而非代码逻辑 |
| 日志监控 | 日志重复 | SSE 重连必须有 event ID 去重 + 启动时跳过历史 |
|  | 日志堆积 | 服务重启 = 日志重置，不是无限追加 |
|  | 跨组件不同步 | 独立 Alpine 组件间用 CustomEvent 通信 |
| 架构 | SQLite 写锁 | 多用户场景下按用户拆库，消除锁竞争 |
|  | 编辑器崩溃 | 稳定性 > 功能丰富度，选最简单够用的 |

### 六、一条贯穿始终的原则

回顾这 15 个坑，能提炼出一条最核心的原则：

> **精准优于丰富。**

给 AI 3 个工具而非 22 个。给日志一个 offset 起点而非从头读。给用户一个进度条而非一个转圈。给 SQLite 一个独立库而非共享锁。

每一次”做减法”的决策，都带来了更好的结果。这不是懒惰，这是工程判断力。

Agent 开发的真正难点，不在于让 AI 能做更多事，而在于**让它在正确的时间做正确的事**——而这取决于你给它的上下文有多精准。
