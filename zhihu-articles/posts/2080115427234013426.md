> 对于 Java 开发者来说，Kubernetes 不仅是容器编排工具，更是一套需要深度理解的分布式控制系统。从容器底座到集群架构，从资源调度到高可用设计，掌握这些核心机制才能避免‘会用’与‘用好’之间的分水岭。

## 1. 先建立总认知：Kubernetes 本质上是“分布式状态控制系统”

Kubernetes 不是“更高级的 Docker”，也不是单纯的容器启动器。它更接近一个持续运行的分布式控制系统：我们声明期望状态，例如“订单服务应该有 6 个副本、每个副本需要 1Gi 内存、只接收健康流量”；控制器持续观察实际状态并把它拉回期望状态。

如果用 Java 类比：spec 像不可变的目标配置，status 像运行时状态；Controller 类似不断执行的 reconciliation loop；API Server 类似统一的领域 API；etcd 类似强一致的状态存储；Scheduler 类似资源分配器；kubelet 类似每台机器上的执行代理。

最重要的公式是：

期望状态（Desired State） -> API -> 控制循环 -> 实际状态（Actual State） -> 再观察 -> 再收敛

只要理解“声明式 + 控制循环”，Deployment、StatefulSet、HPA、Operator、GitOps 都会变成同一种模式的不同应用。

## 2. Kubernetes 之前必须懂的容器底座：OCI、Namespace、cgroup、CRI

容器并不是轻量虚拟机。Linux 容器的核心是“同一个内核上的进程隔离与资源约束”。Namespace 负责隔离 PID、网络、挂载点、主机名等视图；cgroup 负责 CPU、内存、IO 等资源统计与限制；镜像按照 OCI 规范组织为多层只读文件系统和元数据。

Kubernetes 自己不直接运行容器，而是通过 CRI（Container Runtime Interface）调用容器运行时，例如 containerd 或 CRI-O。kubelet 面向 CRI，运行时再负责真正创建容器、配置 cgroup 和挂载文件系统。

Java 开发者要特别注意：容器限制最终会映射为 Linux cgroup。JVM 看到的 CPU 数量、可用内存、GC 并行度、ForkJoinPool 并行度，都可能受到 cgroup 限制影响。现代 JDK 已具备较好的容器感知，但生产仍应明确设置资源与 JVM 策略，而不是依赖“自动猜得刚好”。

## 3. 集群架构：Control Plane 与 Worker Node

![](https://pic3.zhimg.com/v2-8e01a61fc2016ceef6289cb084a64370_r.jpg)

控制平面负责“决定应该发生什么”，工作节点负责“真正运行工作负载”。一个标准集群通常包含以下组件：

| 组件 | 位置 | 作用 | Java 类比 |
| --- | --- | --- | --- |
| kube-apiserver | Control<br> Plane | 所有<br> API 的统一入口 | REST/API<br> Gateway + 领域服务入口 |
| etcd | Control<br> Plane | 保存集群权威状态 | 强一致<br> KV 数据库 |
| kube-scheduler | Control<br> Plane | 为未绑定节点的<br> Pod 选择 Node | 资源调度器 |
| kube-controller-manager | Control<br> Plane | 运行大量控制器 | 后台<br> reconciliation workers |
| kubelet | 每个<br> Node | 保证<br> Pod/容器按声明运行 | 本机<br> Agent |
| kube-proxy 或等价数据面 | 每个<br> Node/网络层 | 实现<br> Service 流量转发 | 四层服务代理 |
| Container Runtime | 每个<br> Node | 运行容器 | 进程执行引擎 |
| CoreDNS | Add-on | 集群<br> DNS 服务发现 | 内部<br> DNS/注册发现 |

控制平面可以高可用部署；生产环境通常不把业务 Pod 和控制平面混在同一组节点上。

## 4. kube-apiserver：所有动作的“唯一正门”

无论是 kubectl apply、Controller、Scheduler、kubelet，还是 Java Kubernetes Client，本质上都在与 kube-apiserver 通信。典型写请求路径是：

客户端 -> 认证 Authentication -> 授权 Authorization -> Admission -> 校验/默认值 -> 持久化 etcd -> Watch 通知控制器

API Server 的价值不只是 HTTP 接口，它还负责版本化 API、鉴权、准入、对象校验、乐观并发、Watch、审计和聚合 API 等。

生产排障时，如果大量组件同时异常，要先判断是不是 API Server/etcd 层故障，因为上层几乎所有控制循环都依赖它。

## 5. etcd：Kubernetes 的“权威状态库”，不是业务数据库

etcd 保存 Kubernetes 对象的权威状态。控制平面高可用不等于 etcd 可以随便丢；如果 etcd 数据不可恢复，集群对象定义、Secret、Lease 等关键状态都会受到影响。

生产原则：

**1.**定期做 etcd snapshot，并真实演练恢复。

**2.**关注磁盘延迟、空间、碎片、leader 变化和 quorum。

**3.**对 Secret 等敏感数据启用静态加密（Encryption at Rest/KMS），因为 Base64 不是加密。

**4.**不要把 CRD 当成业务海量数据存储；Kubernetes API 适合控制状态，不适合订单、日志、指标等业务数据。

## 6. Scheduler：它只负责“选择 Node”，不负责启动容器

Scheduler 只处理尚未绑定 Node 的 Pod。核心过程可以理解为两阶段：Filter 过滤不满足条件的 Node，Score 对剩余 Node 打分，然后完成绑定。

它会综合 requests、nodeSelector、Node Affinity、Pod Affinity/Anti-Affinity、Topology Spread、taints/tolerations、Priority、Volume 拓扑、设备资源等条件。

Java 开发者经常误判：Pod 一直 Pending 不一定是镜像或应用问题；如果事件显示 0/10 nodes are available，这通常是调度问题，应先看 kubectl describe pod 的 Events。

## 7. Controller Manager：真正体现 Kubernetes 灵魂的控制循环

Controller 不断比较“期望状态”和“实际状态”。例如 Deployment Controller 发现期望 6 个副本而只有 5 个，会驱动 ReplicaSet 创建新的 Pod；Node Controller 发现节点异常，会更新 Node 状态并影响 Pod 处理。

Operator 的本质也一样：CRD 定义新的期望状态，自定义 Controller 把领域知识编码成 reconcile 逻辑。

Java 视角可以把 Controller 想成幂等的事件驱动状态机：同一个 reconcile 被重复调用应该仍然得到正确结果，而不是假设“这个事件只会来一次”。

## 8. kubelet：每台节点上的执行者

kubelet 观察分配到本节点的 PodSpec，然后通过 CRI 驱动运行时创建/停止容器，挂载卷，执行探针，上报 Pod/Node 状态和指标。

Pod 已经被 scheduler 绑定到某个 Node，但容器迟迟起不来时，重点就从 scheduler 转到 kubelet、runtime、镜像、Volume、CNI 和应用启动过程。

kubectl describe pod 中诸如 FailedMount、ErrImagePull、CreateContainerConfigError、probe failed，都是 kubelet 执行阶段的重要线索。

## 9. 一次记住 CRI、CNI、CSI：运行、网络、存储三大插件接口

| 接口 | 管什么 | 常见实现 |
| --- | --- | --- |
| CRI | 容器生命周期与镜像 | containerd、CRI-O |
| CNI | Pod<br> 网络、路由、NetworkPolicy | Cilium、Calico、Antrea<br> 等 |
| CSI | 持久卷<br> attach/mount/snapshot 等 | 云盘、Ceph、NFS<br> 等 CSI Driver |

这三个缩写分别回答：容器怎么跑、Pod 怎么联网、持久盘怎么挂。

## 10. Kubernetes 对象模型：apiVersion、kind、metadata、spec、status

一个对象通常包含：

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
 name: order-service
 namespace: prod
 labels:
 app: order-service
spec:
 replicas: 3
 template: {}
status: {}
 
 
```

metadata 是身份与组织信息；spec 是用户期望；status 是控制器汇报的当前状态。不要手工维护 status，也不要把运行时结果塞进 spec。

Kubernetes 的 API Group/Version 体现了 API 演进。升级集群时，必须检查废弃 API，而不是只看节点能否升级。

## 11. 声明式管理、Watch、resourceVersion 与 Server-Side Apply

声明式管理的核心不是“YAML 文件”，而是“提交最终期望状态”。Controller 可以通过 List + Watch 高效追踪变化；对象的 resourceVersion 用于表示存储版本和并发语义。

多人/多控制器共同管理对象字段时，应理解 Server-Side Apply 的字段所有权：不同 field manager 对不同字段负责，可以检测冲突。GitOps、HPA、Operator、平台控制器共同修改对象时，这一点非常重要。

不要把 kubectl edit 当成长期生产变更方式；真正可审计的配置应进入版本控制和流水线。

## 12. Namespace、Label、Selector、Annotation：K8s 组织资源的四件套

Namespace 提供逻辑隔离边界，但不是天然的强安全边界；Label 是可查询、可选择的键值；Selector 用于 Service、Deployment、NetworkPolicy 等对象关联；Annotation 存放不用于选择的元数据。

推荐使用稳定标签，例如：

```java
labels:
 app.Kubernetes.io/name: order-service
 app.Kubernetes.io/instance: order-service-prod
 app.Kubernetes.io/version: 「2026.09.06」
 app.Kubernetes.io/component: api
 app.Kubernetes.io/part-of: trade-platform
 
 
```

很多生产事故来自 selector 配错：Service 选不到 Pod、Deployment selector 与 template labels 不一致、NetworkPolicy 误选对象。

## 13. ownerReferences、Finalizer、Garbage Collection：对象为什么“删不掉”

OwnerReference 表示对象间的归属关系，垃圾回收器可做级联删除。Finalizer 则是一种删除前的清理协议：对象收到删除后会进入带 deletionTimestamp 的终止状态，只有相关控制器移除 finalizer 后才真正删除。

所以资源长期 Terminating 时，不要第一反应就是强删；先检查 finalizers、Webhook、CSI、Namespace controller 等清理链路是否卡住。

## 14. Pod：Kubernetes 最小调度单元，不是单个容器

Pod 是一组共享网络命名空间和卷的容器。一个 Pod 内的容器通常共享同一个 IP，可以通过 localhost 通信。

Pod 应被视为可替换、短命的实例。不要把“某个 Pod 名称”当成永久服务器。业务稳定身份应该来自 Service、StatefulSet 身份、持久存储或外部系统。

绝大多数 Java Web 服务：一个主业务容器 + 必要的 sidecar/init container；不要为了“省 YAML”把多个无关服务塞到同一个 Pod。

## 15. Pod 生命周期：Phase、Condition、Container State 要分开看

Pod 常见 Phase：Pending、Running、Succeeded、Failed。但排障更应该看 Conditions、各 Container 的 state / lastState、restartCount 与 Events。

CrashLoopBackOff 不是 Pod Phase，而是容器反复启动失败后 kubelet 的退避状态。OOMKilled 常见于内存越过 cgroup limit。ImagePullBackOff 是镜像拉取失败后的退避。

restartPolicy 有 Always、OnFailure、Never；Deployment 中一般使用默认 Always。

## 16. Init Container、Sidecar、Ephemeral Container 各自解决什么问题

Init Container 在业务容器前执行，适合初始化文件、等待依赖、迁移轻量配置，但不适合做长时间阻塞的“万能等待脚本”。

Sidecar 与主容器协作，例如代理、日志/安全代理。Sidecar 会增加资源、升级和终止顺序复杂度，只有在职责确实需要共生命周期时使用。

Ephemeral Container 主要用于排障：当业务镜像极简、没有 shell 或诊断工具时，可以临时加入调试容器，而不是把 curl、tcpdump、jstack 永久塞进生产镜像。

## 17. Java 服务最关键的退出链路：SIGTERM、Readiness、preStop、terminationGracePeriodSeconds

Kubernetes 删除 Pod 时会进入优雅终止。Java 服务要做到：停止接收新请求、等待在途请求、停止消费者拉取、提交必要状态，然后在 grace period 内退出。

推荐思路：

**1.**Pod 进入终止流程后尽快让 readiness 变为失败或由框架进入拒绝新流量状态。

**2.**应用收到 SIGTERM 后执行 Spring Boot graceful shutdown。

**3.**`preStop` 只用于确实需要的外部协调，不要无脑 `sleep 30`。

**4.**`terminationGracePeriodSeconds` 必须大于应用真实最大收尾时间。

**5.**消费 MQ 的 Java 服务要让 listener container 停止拉新消息，并给正在处理的消息足够时间。

Spring Boot 可使用 graceful shutdown，并将容器停止时间与 Kubernetes grace period 对齐。

## 18. Startup、Readiness、Liveness：三种探针不能混用

| 探针 | 回答的问题 | 失败结果 | Java 场景 |
| --- | --- | --- | --- |
| startupProbe | 应用是否完成启动 | 未成功前抑制其他探针 | JVM<br> 冷启动、类加载、缓存预热 |
| readinessProbe | 是否可以接收流量 | 从<br> Service 后端移除 | DB/下游严重故障、应用正在排水 |
| livenessProbe | 进程是否需要重启 | kubelet<br> 重启容器 | 死锁、内部无法自恢复 |

最危险的错误是把“下游数据库暂时不可用”直接做成 liveness 失败，结果所有 Pod 同时重启，形成级联故障。

对 Java 服务，startupProbe 能防止长启动阶段被 liveness 误杀；readiness 应代表“现在能否正确服务”；liveness 应只代表“重启我有价值”。

## 19. requests 与 limits：调度、资源保障和 OOM/Throttle 的根本

requests 主要参与调度和资源权重；limits 表示上限。CPU limit 超限通常导致 throttling，而不是杀掉容器；Memory limit 超限可能触发 OOM kill。

CPU 单位 1000m = 1 CPU。内存要明确使用 Mi / Gi，避免把 400m 写成内存单位这种低级错误。

一个 Java Pod 若配置：

```yaml
resources:
 requests:
 cpu: 500m
 memory: 768Mi
 limits:
 cpu: 「2」
 memory: 1536Mi
 
 
```

scheduler 至少按 500m/768Mi 找可容纳节点；运行时最多受 2 CPU 和 1536Mi 内存上限约束。

## 20. QoS：Guaranteed、Burstable、BestEffort 与节点压力下的生存顺序

Kubernetes 根据 requests/limits 给 Pod 分配 QoS：Guaranteed、Burstable、BestEffort。节点资源紧张时，BestEffort 通常最先被驱逐，其次 Burstable，Guaranteed 最后。

对于关键 Java 服务，不要无 requests/limits 裸奔。最常见实践不是追求所有 Pod Guaranteed，而是先建立真实 requests，再根据压测与峰值设合理 limit。

## 21. Java/JVM 容器资源调优：内存 limit 不能等于 `-Xmx`

JVM 进程内存不仅有 Java Heap，还包括 Metaspace、线程栈、Code Cache、Direct Buffer、JNI/native、GC 结构、mmap 等。若 Pod limit=1Gi 而 -Xmx1g，几乎必然没有给 native memory 留空间。

稳妥做法是基于容器内存百分比或压测结果留出 headroom，例如 heap 只占 limit 的 50%~75%，具体比例取决于 Netty/direct buffer、线程数、类数量和 GC。

Java 常见排障信号：

**1.**容器 `OOMKilled`：是 cgroup 级 OOM，不一定有 Java `OutOfMemoryError` 日志。

**2.**Java OOM 但容器没死：可能是 heap/metaspace 自身达到 JVM 上限。

**3.**CPU limit 过紧：GC、JIT、ForkJoinPool、线程池都会被 throttle，P99 延迟恶化。

**4.**HPA 基于 CPU 时，requests 过大/过小会直接影响 utilization 百分比计算。

## 22. ephemeral-storage、emptyDir、日志：磁盘也会让 Pod 被驱逐

本地临时存储包括容器 writable layer、Pod 日志、emptyDir 等。磁盘压力会触发 Node Pressure Eviction。

emptyDir 与 Pod 生命周期绑定，适合临时缓存、容器间共享文件；emptyDir.medium: Memory 使用 tmpfs，本质会消耗内存，不能当成“免费高速盘”。

hostPath 强耦合节点文件系统，生产业务慎用；它常用于 DaemonSet 类型的节点级 Agent，而不是普通应用持久化。

## 23. Deployment 与 ReplicaSet：无状态 Java 服务的默认选择

Deployment 管理 ReplicaSet，ReplicaSet 再管理 Pod。Deployment 负责滚动更新、回滚、扩缩容和历史版本。

RollingUpdate 两个关键参数：maxUnavailable 控制最多不可用多少，maxSurge 控制最多额外创建多少。默认通常是 25%/25%，关键业务应结合容量和 SLO 明确设定。

发布成功不等于新容器“进程启动了”，而是需要 readiness、minReadySeconds、progressDeadlineSeconds 等共同定义真正可用。

## 24. StatefulSet：稳定身份 + 稳定存储 + 有序语义

StatefulSet 适合需要稳定网络身份、稳定持久卷、有序启动/缩容的工作负载。Pod 名通常是 name-0、name-1，每个副本可拥有独立 PVC。

典型场景：数据库、ZooKeeper、Kafka 某些部署模式、需要成员身份的分布式系统。普通 Spring Boot 无状态 API 不要为了“固定 Pod 名”使用 StatefulSet。

StatefulSet 常与 Headless Service 配合，让客户端可以解析到各个 Pod 的稳定 DNS。

## 25. DaemonSet：每个节点一个 Pod

DaemonSet 适合节点级基础设施：日志采集、网络 Agent、监控 Agent、存储插件、节点安全组件等。

不要用 DaemonSet 部署普通 Java Web 服务，因为它的目标不是“需要 N 个副本”，而是“匹配的每个节点上运行一个”。

## 26. Job 与 CronJob：一次性任务和定时任务

Job 保证任务完成，CronJob 按计划创建 Job。适合批处理、数据修复、离线任务、数据库维护等。

要理解 completions、parallelism、backoffLimit、TTL、CronJob concurrencyPolicy、startingDeadlineSeconds。

Java 批任务必须保证幂等，不能假设 Job 永远只执行一次。失败重试、节点故障、控制器恢复都可能让任务再次执行或重新创建 Pod。

## 27. Service：稳定虚拟入口，解耦 Pod IP 的变化

Pod IP 会变，Service 提供稳定的虚拟 IP/DNS，并通过 EndpointSlice 追踪后端 Pod。

| Service 类型 | 用途 |
| --- | --- |
| ClusterIP | 集群内部访问，默认类型 |
| NodePort | 每个<br> Node 暴露端口，常作为其他入口机制的基础 |
| LoadBalancer | 由云/基础设施提供外部负载均衡 |
| ExternalName | DNS<br> CNAME 指向外部名称，不做代理 |
| Headless | `clusterIP:<br> None`，直接通过 DNS 暴露后端端点 |

Service 通过 selector 匹配 Pod labels。排障 Service 的第一步之一是看 EndpointSlice 是否真的包含 Ready Pod，而不是只看 Service 对象存在。

## 28. DNS 与服务发现：Java 连接池最容易踩的“看不见的坑”

通常同 Namespace 可以用 [HTTP://inventory:8080](HTTP://inventory:8080)，跨 Namespace 可用 inventory.prod.svc.cluster.local 一类 FQDN。

Java 客户端要意识到 DNS 结果可能变化，而长生命周期连接池可能持续复用旧连接。对于滚动发布、Headless Service、数据库驱动、gRPC 长连接，要明确客户端的 DNS 重解析、连接寿命和负载均衡策略。

CoreDNS 是常见集群 DNS；大规模集群还可能使用 NodeLocal DNSCache 降低 DNS 压力与延迟。

## 29. Ingress 与 Gateway API：2026 年应优先理解 Gateway API

Ingress 仍然稳定且不会立刻消失，但其 API 已冻结；Kubernetes 官方推荐新能力优先采用 Gateway API。

Gateway API 把职责拆成 GatewayClass、Gateway、HTTPRoute、GRPCRoute 等资源，更适合多团队、协议感知、权重路由、基础设施与应用职责分离。

注意：Gateway API 是附加 API/CRD 体系，需要安装对应实现，不是“写了 Gateway YAML 就自动有网关”。

## 30. Kubernetes 网络模型与 CNI：Pod 为什么能跨节点互通

Kubernetes 的理想网络模型是每个 Pod 有自己的 IP，Pod 间可以直接通信，不要求应用自己做端口映射。真正的数据面由 CNI 实现。

一个典型外部请求路径可以理解为：

![](https://pica.zhimg.com/v2-9a286fdfc231b2d665cc19bf74498c0e_r.jpg)

实际实现可能基于 iptables、nftables、eBPF、云网络等。不要把 kube-proxy 等同于“所有集群网络”；有些 CNI 会替代 Service 数据面实现。

## 31. NetworkPolicy：Kubernetes 里的 L3/L4 微隔离

NetworkPolicy 通过 Pod/Namespace selector 和 IPBlock 控制 ingress/egress。前提是 CNI 真正支持并执行它；只有 API 对象而网络插件不实现时，策略不会生效。

推荐生产模式：

**1.**先做 namespace 级 default deny。

**2.**明确放行 DNS。

**3.**再逐项放行业务所需入口和出口。

**4.**分清 ingress 与 egress 是独立维度。

**5.**策略是允许规则的并集，不是按文件顺序“先拒后放”。

Java 微服务如果使用大量动态下游，应先梳理依赖图，否则一次性 default-deny 很容易把 DNS、监控、证书、MQ、数据库一起切断。

## 32. 持久化存储：PV、PVC、StorageClass、CSI 一次串起来

PVC 是“应用对存储的请求”，PV 是“实际可用存储资源”，StorageClass 描述动态供给策略，CSI Driver 负责对接真实存储系统。

生命周期可以理解为：

Pod -> PVC -> StorageClass/Provisioner -> PV -> CSI -> 真实磁盘/文件存储

关注 accessModes（RWO/RWX/ROX/ReadWriteOncePod）、容量扩展、reclaimPolicy、VolumeBindingMode、拓扑、快照与备份。

数据库放进 Kubernetes 并不自动获得数据安全。K8s 能管理卷的挂载与生命周期，但备份、恢复、复制、RPO/RTO 仍然是数据库系统和运维架构问题。

## 33. ConfigMap、Secret、Projected Volume、Downward API

ConfigMap 放非敏感配置；Secret 放敏感数据，但默认 Base64 只是编码。Secret 应结合 etcd 静态加密、最小 RBAC、外部 Secret 管理/KMS 等一起使用。

配置注入方式包括环境变量和 Volume 文件。环境变量通常只在进程启动时读取；Volume 挂载的 ConfigMap/Secret 可以被 kubelet 更新，但应用是否动态重载取决于自身实现。

ConfigMap/Secret 单对象不适合巨大数据；生产可以使用 immutable 版本化配置并通过滚动发布更新。

Downward API 可把 Pod 名、Namespace、labels、resource 信息等注入容器，便于日志和遥测打标签。

## 34. 调度约束：nodeSelector、Node Affinity、Pod Affinity、Topology Spread

nodeSelector 最简单；Node Affinity 支持硬约束/软偏好；Pod Affinity/Anti-Affinity 根据其他 Pod 分布做约束；Topology Spread 用 topologyKey 控制副本跨节点/可用区均匀分布。

高可用 Java 服务常见目标：同一服务副本不要全落在一台 Node，也不要全落在一个 Zone。Topology Spread 往往比复杂 anti-affinity 更直观。

不要无限叠加硬约束；约束越多，越容易出现“集群明明有资源但 Pod Pending”。

## 35. Taint 与 Toleration：节点排斥机制

Taint 放在 Node 上，Toleration 放在 Pod 上。效果包括 NoSchedule、PreferNoSchedule、NoExecute。

典型用途：GPU 节点只给 AI 工作负载；数据库专用节点；系统组件专用节点；节点异常时基于 taint 驱逐。

注意 Toleration 只代表“允许上这个节点”，不代表“一定调度到这个节点”；如果要吸引到目标节点，通常还需要 affinity/selector。

## 36. Priority、Preemption、PDB 与 Eviction：高可用不是“replicas: 3”就结束

PriorityClass 决定资源紧张时谁更重要，高优先级 Pod 可能通过 preemption 让低优先级 Pod 腾位置。

PDB 约束“自愿性干扰”同时最多影响多少副本，例如节点 drain；它不保护所有故障，也不会阻止直接删除 Deployment/Pod，更不能替代多副本和多故障域分布。

Node Pressure Eviction 是 kubelet 为了自保主动驱逐 Pod；硬阈值时甚至不会尊重你想象中的完整应用 graceful period。因此 requests、QoS、磁盘和内存管理仍是根本。

## 37. HPA：水平扩缩容的算法、前提和 Java 启动尖峰

HPA 不是“CPU 高了就加 Pod”这么简单。核心近似公式：

desiredReplicas = ceil(currentReplicas * currentMetric / desiredMetric)

资源利用率基于 requests 计算，所以 requests 配错会让 HPA 判断失真。HPA 可使用 resource/custom/external metrics，并有 scaleUp/scaleDown behavior、stabilization window、tolerance 等参数。

Java 应用启动时常有 JIT、类加载、连接池和缓存预热 CPU 尖峰。应使用 startupProbe/readiness 与 HPA 初始化窗口，避免把启动尖峰误判为持续业务压力。

Kubernetes 1.37 中，基于 object/external metrics 的 HPA scale-to-zero 进入 Beta 并默认启用；CPU/内存指标不能从 0 副本唤起，因为没有运行中的 Pod 可采样。

## 38. VPA、Node Autoscaling、KEDA/事件驱动：扩缩容是三层问题

HPA 改副本数；VPA 关注 Pod requests/limits 建议或调整；Node Autoscaling 在 Pod 因资源不足无法调度时增加/减少节点。它们解决不同层级问题。

生产设计要避免控制器互相打架，例如 HPA 基于 CPU utilization、VPA 又频繁修改 CPU request，会改变 HPA 分母。

队列消费型 Java 服务更适合基于 backlog、lag、队列长度等外部指标扩容，而不是只看 CPU。KEDA 等生态工具经常用于事件驱动扩缩容，但它不是 Kubernetes 核心 API。

## 39. ResourceQuota 与 LimitRange：多团队共享集群的资源治理

ResourceQuota 限制 namespace 总 CPU、内存、存储、对象数量等；LimitRange 约束单个 Pod/Container/PVC 的最大最小值并可注入默认 requests/limits。

只创建 Namespace 不等于实现多租户。真正的多租户通常还要组合 RBAC、NetworkPolicy、Pod Security、Quota、LimitRange、独立 ServiceAccount、审计和成本标签。

## 40. 安全总模型：Authentication -> Authorization -> Admission

Authentication 解决“你是谁”，Authorization 解决“你能做什么”，Admission 解决“即使你有权限，这个对象是否符合平台规则”。

Kubernetes 不把所有人类用户做成 API 内置 User 对象；企业常通过 OIDC/IAM 等外部身份接入。工作负载身份常用 ServiceAccount。

## 41. RBAC 与 ServiceAccount：Java Pod 不应该默认拥有集群权限

RBAC 四个核心对象：Role、ClusterRole、RoleBinding、ClusterRoleBinding。Role 是 namespace 级权限；ClusterRole 可定义集群级资源权限，也可被 RoleBinding 绑定到单一 namespace。

每个 Pod 会关联 ServiceAccount；如果应用不需要访问 Kubernetes API，可以设置：

automountServiceAccountToken: false<br> <br>

如果 Java Operator 需要 Watch CRD，应只授予它需要的 verbs/resources/namespaces，遵循最小权限，不要直接 cluster-admin。

## 42. Pod Security、SecurityContext 与供应链安全

Pod Security Admission 可以按 namespace 执行 privileged、baseline、restricted 三类标准。应用侧常见安全配置：非 root、只读根文件系统、drop capabilities、禁止 privilege escalation、seccomp、合适的 fsGroup。

镜像侧：使用最小基础镜像、固定 digest 或可追踪 tag、镜像扫描、SBOM、签名/验证、避免把 Secret 打进镜像层。

Java 镜像不要为了排障永久保留完整 JDK + shell + 包管理器；生产可使用 JRE/runtime image，必要时通过 ephemeral container 或专用诊断镜像排障。

## 43. Admission 与策略：Webhook、ValidatingAdmissionPolicy、CEL

Admission 在认证和授权之后、对象持久化之前执行。Mutating Admission 可以修改对象，Validating Admission 可以拒绝不符合规则的对象。

ValidatingAdmissionPolicy 使用 CEL 做进程内声明式校验，适合“必须有 owner label”“禁止 latest tag”“生产 namespace 必须设置 requests”等规则，减少外部 Webhook 的可用性依赖。

Webhook 是控制平面关键路径依赖，必须设置合理 timeout、failurePolicy、HA 和监控，避免一个失效 Webhook 让整个集群创建/更新资源都卡住。

## 44. 可观测性：Metrics、Logs、Traces、Events 四种信号要一起看

Kubernetes 自身和应用都需要可观测性。Java 服务至少应有：

**1.**Metrics：CPU、内存、GC、线程池、连接池、HTTP/RPC、队列 lag、业务指标。

**2.**Logs：结构化日志，包含 traceId、pod、namespace、version 等字段。

**3.**Traces：跨 Service、MQ、DB 的调用链。

**4.**Events：Kubernetes 调度、镜像、挂载、探针等生命周期事件。

kubectl top 依赖资源指标链路；HPA 的资源指标通常来自 Metrics Server。Prometheus/OpenTelemetry 是常见生态，但 Kubernetes 不强制单一观测栈。

## 45. 一套高命中率的 Pod 排障顺序

面对“服务不可用”，建议固定顺序：

**1.**`kubectl get pod -o wide`：状态、重启次数、Node、IP。

**2.**`kubectl describe pod`：Events、调度、挂载、探针、镜像。

**3.**`kubectl logs --previous`：上一次崩溃日志。

**4.**看 Container `lastState`：ExitCode、Reason、OOMKilled。

**5.**看 requests/limits、Node pressure、QoS。

**6.**看 Service/EndpointSlice 是否包含该 Pod。

**7.**DNS 测试、NetworkPolicy、CNI。

**8.**Java 进程层：线程、GC、heap/native memory、连接池、下游超时。

排障时不要只盯 kubectl logs。很多错误发生在容器启动前，应用根本没有机会输出日志。

## 46. 网络排障：从 DNS 到 EndpointSlice，再到 Pod 端口

当 A 调 B 不通时按层排：

DNS 名称 -> Service ClusterIP -> EndpointSlice -> Pod IP -> Container Port -> 应用监听地址

常见错误：Service selector 不匹配；Pod readiness=false 被移出端点；Java 只监听 127.0.0.1；targetPort 写错；NetworkPolicy 拒绝；DNS 被 egress default-deny；Gateway backendRef 指错 namespace/service/port。

不要一上来 tcpdump。先用对象关系确定流量本来应该走到哪里，再进入数据面抓包。

## 47. 存储排障：Pending PVC、FailedMount、Multi-Attach 怎么定位

先看 PVC/PV 是否 Bound，再看 StorageClass、CSI Controller/Node 插件、VolumeAttachment、Node 拓扑和 Events。

常见问题：没有默认 StorageClass；accessMode 与存储能力不匹配；RWO 卷还挂在旧节点导致 Multi-Attach；Zone 不匹配；CSI driver 异常；扩容后文件系统 resize 未完成。

对数据库，不要用“删 Pod 试试”代替理解挂载和恢复过程。

## 48. Helm、Kustomize 与 GitOps：配置管理不是把 YAML 复制 20 份

Helm 适合模板化和打包 Chart；Kustomize 适合 base + overlay 的声明式 patch；两者都可以进入 GitOps 流程。

生产核心不是选哪个工具，而是做到：

**1.**单一可信源进入 Git。

**2.**环境差异最小化。

**3.**Secret 不明文进仓库。

**4.**变更可审计、可 diff、可回滚。

**5.**不允许平台控制器/HPA 与手工 apply 长期争夺同一字段。

GitOps 工具本质也是控制器：Git 里的期望状态与集群实际状态持续对账。

## 49. CRD、Operator 与 Java：从“使用 Kubernetes”进阶到“扩展 Kubernetes”

CRD 为 Kubernetes 增加新的资源类型；Custom Controller/Operator 把领域知识写成 reconcile 逻辑。例如定义：

```yaml
apiVersion: platform.example.com/v1
kind: JavaService
metadata:
 name: order-service
spec:
 image: registry/order:2026.09.06
 replicas: 3
 jvm:
 maxRamPercentage: 65
 exposure:
 gateway: internal
 
 
```

Operator 可以把它翻译为 Deployment、Service、HPA、PDB、NetworkPolicy 等一组资源。

Java 开发 Operator 时常用 Fabric8 Kubernetes Client、官方 Java Client 或相应 Operator Framework。必须掌握 Watch、Informer/缓存、幂等 reconcile、status conditions、finalizer、leader election、重试退避、429/Retry-After、RBAC 最小权限。

不要把 Operator 写成“收到事件就执行一次脚本”。事件可能丢、重复或乱序；真正可靠的是根据当前状态重新计算应该做什么。

## 51. Kubernetes 1.37 需要特别知道的变化

截至 2026-09-06，最新稳定小版本基线是 1.37.0。1.37 的几个值得 Java/平台开发者关注的点：

**1.**HPA 基于 object/external metrics 的 scale-to-zero 进入 Beta，默认启用。

**2.**HPA 可配置 tolerance 在 1.37 达到 Stable，可分别控制扩容/缩容对小幅指标变化的敏感度。

**3.**`[http://metrics.k8s.io](http://metrics.k8s.io)` API 本身在 1.37 达到 Stable；但当前 HPA 的资源指标路径仍要注意版本兼容，官方文档指出 HPA 仍使用 `[http://metrics.k8s.io/v1beta1](http://metrics.k8s.io/v1beta1)`。

**4.**KYAML 在 1.37 达到 Stable，可通过 `kubectl get -o kyaml` 输出更明确的 YAML 子集表现形式，但现有 YAML 不需要迁移。

**5.**Pod certificates 与 ClusterTrustBundles 达到 Stable，为工作负载 X.509 身份和信任分发提供更原生的能力。

**6.**Memory QoS 基于 cgroups v2 的支持进入 Beta；cgroup v1 正在退出历史舞台。

**7.**Gang scheduling / workload-aware preemption 等能力继续演进，面向 AI/HPC 多 Pod 协同调度。

**8.**kube-proxy 的 IPVS 模式已进入废弃路线，长期需要关注 nftables/其他数据面方向和具体发行版实现。

**9.**kube-dns 继续退出历史舞台，CoreDNS 是标准选择。

不要因为“新版本有功能”就立刻生产开启 Alpha。先看 Feature State、feature gate、运行时/CNI/CSI 兼容矩阵和发行版支持策略。

## 52. 升级与版本偏差：生产集群最不能“直接跨版本试试”

当前 Kubernetes 维护最近三个 minor release。升级时要遵守 version skew：kubelet 不能比 kube-apiserver 新；现代版本通常允许 kubelet 最多落后三个 minor；kubectl 通常支持在 kube-apiserver 前后一个 minor 范围内。

生产升级步骤应包含：

**1.**查 API deprecation / removed APIs。

**2.**查 CNI、CSI、Ingress/Gateway、Metrics、Operator、Admission Webhook 兼容矩阵。

**3.**备份 etcd 和关键配置。

**4.**先控制平面，再逐节点 drain/升级 kubelet。

**5.**验证 PDB、节点容量、扩容能力和回滚方案。

**6.**不跳过 minor version 做控制平面升级。

## 53. 高可用集群：多副本只是起点

真正高可用要同时覆盖：Control Plane HA、etcd quorum、多个故障域、业务 Pod 拓扑分散、PDB、负载均衡、DNS、存储复制、备份恢复、外部依赖高可用。

一个 3 副本 Deployment 如果三个 Pod 都在同一 Node 或同一可用区，不能算真正的高可用。

应用层还要做超时、重试、熔断、限流、幂等和负载削峰；Kubernetes 只能调度和恢复进程，不能自动修复错误的分布式系统语义。

## 54. 常见反模式：会用 K8s 和用好 K8s 的分水岭

**1.**所有服务都 `requests`/`limits` 为空。

**2.**`liveness` 依赖所有下游，导致下游故障时全体重启。

**3.**`-Xmx` 等于 memory limit。

**4.**Service selector 与 Pod label 随意改。

**5.**把 Pod IP、Pod 名当稳定地址。

**6.**用 `latest` tag 且无法追踪版本。

**7.**Secret 明文进入 Git 或镜像。

**8.**每个 Java 服务都申请 cluster-admin。

**9.**把 `kubectl edit` 当正式发布流程。

**10.**PDB 配得过严导致节点永远 drain 不掉。

**11.**HPA 与 Deployment manifest 长期同时争夺 `spec.replicas`。

**12.**把 StatefulSet 当“更稳定的 Deployment”。

**13.**用 hostPath 给业务做持久化。

**14.**default-deny NetworkPolicy 后忘记放行 DNS。

**15.**把 CRD 当数据库存业务海量记录。

## 56. 最后的专家级心智模型：只记住这 12 句话也能快速定位大多数问题

**1.**Kubernetes 管的是“期望状态”，不是一次性命令。

**2.**所有控制平面动作最终都绕不开 kube-apiserver。

**3.**Pod 是调度单元，容器是执行单元。

**4.**Deployment 负责无状态副本，StatefulSet 负责身份/存储语义。

**5.**Service 提供稳定入口，EndpointSlice 才是真正后端集合。

**6.**Scheduler 看 requests 和约束；kubelet 才负责把容器跑起来。

**7.**CPU 超限多表现为 throttle，内存超限可能直接 OOMKill。

**8.**Readiness 控流量，Liveness 决定重启，Startup 保护慢启动。

**9.**NetworkPolicy 只有在 CNI 实现它时才真正生效。

**10.**PVC 只是存储请求，真正挂载还要走 StorageClass/CSI/Node。

**11.**RBAC 决定能不能做，Admission 决定即使能做是否允许这样做。

**12.**排障永远从对象状态和 Events 开始，再逐层进入网络、存储、节点和 JVM。

当我们能把“一个用户请求为什么最终落到某个 Java Pod”与“这个 Pod 为什么能被创建、调度、联网、挂盘、扩容、退出和恢复”完整讲通时，Kubernetes 就不再是一堆 YAML，而是一套可以推理的分布式控制系统。
