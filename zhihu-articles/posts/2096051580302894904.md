# CodeX 实用技巧（二）：提示词工程进阶，把任务描述成可验收的规格

## 一、为什么提示词决定成败

CodeX 的输出质量，高度依赖于它"看到"了什么，以及你如何描述"要做什么"。普通提示词往往过于笼统，例如"帮我优化这个函数"。而高级用法是把任务写成带验收标准的规格说明。

## 二、五要素提示词模板

一个标准的工程指令应包含五个要素：

1. **背景**：说明项目运行环境、技术栈

2. **目标**：说清具体改动指标和预期效果

3. **范围**：圈定可修改的文件和模块

4. **约束**：明确"不要做什么"——如不能引入第三方依赖、不能破坏 API 签名

5. **验收**：给出可执行的验证命令或预期结果

## 三、对比案例

**初级写法**：

"请帮我重构 user_service.py，让代码更好。"

**高级写法**：

"任务：重构 user_service.py 的注册逻辑，追求可维护性而非极致性能。

背景：当前 register 函数约 130 行，混合了参数校验、数据库写入、邮件发送三种职责。

目标：将以上三种职责拆分为独立函数；公共校验逻辑抽取到 validators 模块；保持对外函数签名不变。

约束：保持 Python 3.11 语法；不要引入新的第三方依赖；不要修改数据库表结构。

验证：运行 python -m pytest tests/test_user_service.py 应全部通过；重构后 register 函数体不超过 20 行。"

## 四、关键要点

- **明确写出"不要做什么"与"如何验收"**，比反复强调"做好一点"更有效

- CodeX 对否定约束和可执行验证命令的遵从度明显更高

- 不需要告诉它第一步打开哪个文件、第二步修改哪个方法，只需要把目标和边界讲清楚，具体怎么实现让它自己判断

## 五、任务边界与 Goal Mode

很多人在使用 CodeX 时提示词写得过于宽泛，比如"写一个登录功能"。这种提示的问题在于 CodeX 不知道你的技术栈、项目结构、安全要求和代码风格，它只能给出一个最通用的、可能并不适合你当前项目的方案。

在提示中明确任务边界，不仅仅是写更详细的注释，而是把任务定义成可验收的规格，让 CodeX 从"能用"跨越到"好用"。

**总结**：提示词工程是 CodeX 使用中最核心的技能。把任务描述成可验收的规格，让 CodeX 真正

理解你的意图，才能从"更聪明的代码提示工具"变成"真正理解你工作流的智能伙伴"。
