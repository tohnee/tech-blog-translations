做 MoE 推理的人都有一个共同体验：**大 batch 时你在算带宽，小 batch 时你在等同步。**

NVIDIA 这篇预印本（13 位作者，全部来自 NVIDIA）盯的就是后者。它把专家并行（Expert Parallelism，EP）里的 dispatch / combine 两次 all-to-all 改成**单边通信（one-sided）**：源 rank 直接把 token 写进目标 GPU 的对称内存里，不先交换任何元数据，MoE 的 grouped GEMM 就地读。配套两套同步协议：FENCE 面向大吞吐，SENTINEL 面向低延迟。

效果：Blackwell 上 dispatch+combine 比 DeepEP 快 1.2–3.0 倍，MoE 层比 DeepEP+DeepGEMM 快最多 2.4 倍；在 128 token/rank 以内甚至快过 DeepGEMM 融合版 MegaMoE。代码已进 FlashInfer，并接入 vLLM / SGLang / TensorRT-LLM。

## 一、问题：decode 阶段，all-to-all 的时间去哪了

EP 部署下，attention 走数据并行（每个 rank 服务自己的请求），MoE 层把专家切到 P 张卡上。于是每个 MoE 层都有两次 all-to-all：

- **dispatch**：把 token 送到持有它命中专家的那些 rank；
- **combine**：把专家输出送回 token 的原 rank 并按路由权重求和。

关键在于推理和训练的 token 量级完全不同。论文给了一个具体例子：DeepSeek 的 DeepInfer 在 DeepSeek-V4.1-Flash 上按每用户约 250 token/s 解码、每 rank 服务 64 个请求，每个请求带 3 个 draft token，于是一个 decode step 每 rank 只有 256 个 token。

这时候，token 本身的数据量小到可以忽略——在理论 NVLink 带宽下不到 1 微秒。但实测 dispatch+combine 往返是**几十微秒**。也就是说，时间几乎全花在**不随 token 数增长的固定开销**上：生产者与消费者跨 GPU 的同步、把数据先写进中间缓冲区再多走一遍搬运的额外 pass。

NCCL 和 DeepEP 的常见做法都是「先写中间 buffer，接收方再 copy / regroup 成下一个 kernel 需要的布局」。大 batch 时这一趟多余的数据搬运吃掉显存带宽；小 batch 时它变成纯粹的延迟。

## 二、关键观察：路由是本地已知的，所以不需要元数据

论文的出发点只有一句话：**一个 token 该发到哪几个 rank，只由本 rank 的路由结果决定。**

既然源 rank 自己就知道目的地，就没有必要先发一轮「我要给你发多少个 token、命中哪些专家 id」的元数据，也没有必要让接收方按元数据重新计算偏移。可以直接写。

单边通信能成立的前提是 NVLink 域内的**对称内存（symmetric memory）**：通过 CUDA VMM，每个 rank 分配物理内存、导出 handle、把对端的内存映射进自己的地址空间，之后 kernel 用普通的 load/store/atomic 就能访问对端显存。Blackwell 上 18 条第五代 NVLink、每条 100 GB/s，单向 900 GB/s、双向 1.8 TB/s；一个 HGX B300 板内 8 卡全互联，GB200/GB300 NVL72 机柜构成一个 72 卡的 NVLink 域。出域之后每卡只有一个 ConnectX-8（800 Gb/s，约 100 GB/s 单向），差一个数量级——这条边界后面会成为本文最重要的限制。

## 三、rank-major 布局：省一次搬运，还省一半字节

如果多个源 rank 同时往同一个目标 rank 写，槽位怎么分？两种笨办法：远端计数器做 atomic（每次都要跨卡原子操作），或者预先按所有源 rank 的计数算好偏移（又回到元数据交换）。

论文的做法是把 workspace 按源 rank 分区：**目标 rank 的 dispatch workspace 里，每个源 rank 有一块自己的区域，只有它能写**，用本地计数器 atomicAdd 取下一个槽位，槽位在区域内是稠密前缀。这个布局叫 **rank-major**。

每个区域有 Ĉ 个槽位（Ĉ 是全组每 rank 的最大 token 数，DP attention 每步本来就共享 batch size 信息，所以每个 rank 都知道）。一个 token 对每个目标 rank 只占**一个**槽位，槽位里放它的全部 k 个专家 id 和路由权重——不管它选中了该 rank 上的几个专家。

这一步带来两个直接收益：

- **去重**。每个 token 最多发 min(k, P) 次，而不是 k 次。k=16、8 卡时，无论路由怎么选，字节数最多只有原来的一半。
- **workspace 更小**。dispatch 和 combine 的 workspace 各只有 P×Ĉ 个槽位；expert-major 的 buffer 要给「每个本地专家都可能收到每个 token」留空间，DeepEP V1 的低延迟 kernel 需要 Eℓ 倍的槽位，DeepEP V2.5 也要 min(k, Eℓ) 倍。

论文给了一组具体占用：DeepSeek-V4.1-Flash（hidden 5120、384 专家、top-6、expert intermediate 2304）在 8 卡、每 rank 最多 4096 token 时，dispatch workspace 是 160 MiB（8×4096 槽 × 5120 字节 MXFP8），combine workspace 320 MiB（BF16）；而 DeepEP V2.5 + DeepGEMM 需要 242 MiB 通信 buffer，外加大约 1020 MiB 的 expert-major GEMM 输入——是前者 160 MiB 的约 6 倍（多出来的是对齐 padding）。这些 buffer 都随 EP 规模线性增长，EP 越大越吃紧。

## 四、MoE 计算怎么「就地读」

token 留在 dispatch workspace 的原槽位不动，所谓的「按专家分组」退化成一串**槽位索引**：

- **indexing kernel**：挑出本地专家的 id，跳过无效槽位，为每个专家建立槽位索引列表，同时建立反向映射（槽位 → 该 token 的 FC2 输出行），供 finalize 用；
- **FC1**：按索引直接从 dispatch workspace gather 输入。FlashInfer 的 Prims-TS grouped GEMM 用 TMA `gather4` 指令，一条指令取 4 个不连续槽位的 128 字节切片，且**永远不会读空槽**；
- **FC2**：按专家分组顺序读 FC1 的输出；
- **finalize**：按反向映射把每个 token 的各专家输出取回，乘路由权重、求和，写进 combine workspace 的同一槽位；
- **combine**：源 rank 按 dispatch 时记下的（目标 rank, 槽位）把部分和拉回来相加——同样不需要任何元数据。

## 五、两套同步协议：FENCE 与 SENTINEL

单边写没有顺序保证：远端 store 不等待对端，可能乱序到达；GPU 内存是弱序的。所以要两处同步：dispatch 结束前（目标 rank 必须确认所有源 rank 都写完了）和 combine 开始前（源 rank 必须确认所有目标 rank 都算完了）。

**FENCE（面向吞吐）**：每个 thread block 负责一个 token 的 dispatch 和 combine。block 用 atomicAdd 在每个目标 rank 的区域里取槽位；全部发完后，最后一个完成的 block 代表整个 rank 写 slot counts，执行一次 `fence.release.sys`，然后给每个 peer 写 flag，并自旋等所有 peer 的 flag。随后一个小 kernel 把「计数之后」的槽位专家 id 标成 −1，让它们不参与计算。combine 同理，只是由第一个 block 写 flag，所有 block 自旋 + `fence.acquire.sys` 后再拉数据。

代价是串行链：原子计数 → 系统级 fence → 发布/等待 flag，每个 decode step 一次。GB200 上一次内存屏障就是微秒级，这条链在小 batch 时非常显眼。

**SENTINEL（面向延迟）**：让数据自己当旗标。落地槽位每个 32 位字预先写入哨兵值（sentinel，BF16 payload 用 0xFFFFFFFF，即两个 NaN；生产者遇到这个值就改写成 0x7FFF 两个 NaN 来规避冲突）。目标 rank 轮询这些字——因为对齐的 32 位字是**整体到达**的，一个槽位的所有字都不等于哨兵值，就说明槽位完整，不需要 fence。

问题来了：路由决定哪些槽位会有 token，而接收方必须区分「还在路上的槽位」和「永远不会被写的槽位」。解法是让「源 rank s 的第 i 个 token 永远落在 s 区域的第 i 个槽位」，并且每个源 rank 给**每个** rank 都写专家 id（没有 token 就写 −1，专家 id 槽用另一个哨兵 0x88888888）。这样专家 id 槽一定会到，它本身告诉接收方「payload 会不会跟来」。

combine 也改成 push：目标 rank 算完就把部分结果直接写回源 rank 的 combine 槽，token 的 block 轮询并累加。

![](https://pic2.zhimg.com/v2-15513bc403de38d69346a96d1d6d4431_1440w.jpg)

图 4：左边是 FENCE 的「稠密前缀 + 计数」布局，右边是 SENTINEL 的「按 token 序号固定槽位 + 哨兵」布局；下方是两种协议到 MoE 开始的临界路径对比。SENTINEL 砍掉的是「等待之外的准备工作」，等待本身砍不掉。

## 六、实测：小 batch 赢在固定开销，大 batch 输在不能重叠

测试平台是 8 张 NVLink 互联的 B300（CUDA 13.5），大 EP 实验在 GB200 NVL72 上做；被测模型是 DeepSeek-V4.1-Flash 和 Kimi-K3（896 专家、top-16）的路由专家层，token 数从 1 到 4096/rank。计时方式是 10 次 warm-up + 100 次计时迭代放在同一个 CUDA graph 里背靠背跑、每次前刷 L2；all-to-all 输出与参考实现按位一致，MoE 层相对 L2 误差不超过 5.7×10⁻³。

**all-to-all 单看**：1 token/rank 时，DeepSeek-V4.1-Flash 的往返 SENTINEL 17.4 µs、FENCE 27.6 µs、DeepEP 47.9 µs；4096 token 时 FENCE 达到单向 900 GB/s 的 68–71%。总体比 DeepEP 快 1.75–3.00 倍（≤128 token/rank）和 1.17–1.63 倍（≥256 token/rank）。

| 16 | 20.6 | 29.6 | 48.5 |
| 64 | 27.0 | 32.8 | 53.6 |

交叉点在 256 token/rank：再往下 SENTINEL 更快，再往上 FENCE 更快。论文用 IKET 在 kernel 内打点解释了原因——1 token 时两种协议等 peer 的时间差不多，SENTINEL 省掉的是「等待之外的工作」（FENCE 的串行链和额外 kernel，dispatch 耗时直接减半；combine 变成谁算完谁 push）。batch 变大后传输本身占主导，而 SENTINEL 的每槽位开销（每个收到的槽位都要检查、copy-out、重置，且 combine 的 block 数超过 GPU 同时能跑的数量）把省下的又还回去了。

**整个 MoE 层**：比 DeepEP+DeepGEMM 快最多 2.4 倍（Kimi-K3 1 token：42.1 µs vs 99.7 µs）。对融合版 MegaMoE，128 token/rank 以内本文更快（论文称最高 30%），256 token 起 MegaMoE 领先，4096 时领先 35%——因为 MegaMoE 是把 dispatch、两个 grouped GEMM、combine 融进一个 persistent kernel，NVLink 传输可以在 Tensor Core 计算期间进行，而分离的 kernel 做不到。

**倾斜路由**：上面的实验用的是完美路由（每个 token 的 k 个选择均匀铺到连续 rank 上）。论文另外用 Zipf 路由测了一组：1024 token/rank、α=1.25 时，最忙 rank 的 token–专家对是均衡情况的 1.91 倍，grouped GEMM 慢 50–70%，而通信只按「收到的 token 数」增长（一个 token 对一个目标 rank 只发一次）。此时最忙 rank 的 dispatch/combine 是 160/135 µs，DeepEP 是 267/400 µs；层延迟 619 µs，DeepEP+DeepGEMM 696 µs，但 MegaMoE 只要 411 µs——倾斜路由下融合方案的优势更明显。

**大 EP 扩展**：在 NVL72 上从 8 卡扩到 64 卡（固定 token/rank）。1 token/rank 时 SENTINEL 往返稳定在 16.6–17.8 µs（没有 per-peer 握手），FENCE 从 43.0 涨到 47.6 µs（每个 peer 一个 flag）。层延迟在 128 token/rank、64 卡时 102.6 µs，8 卡时 181.7 µs——因为每卡只持有 6 个专家而不是 48 个，权重要读的少了。

## 七、批判性评估：三个必须先说清的前提

这篇论文工程完成度很高（有开源实现、进了三个主流框架、实验覆盖两种模型族和 8/64 卡两档），但它的结论有明确适用边界，读的时候要注意：

**1. 它只在「一个 NVLink 域内」成立。** 两套协议都依赖直接 load/store 对端内存，以及「对齐的 32 位字整体到达」这个保证——RDMA 两者都不提供（RDMA Write 内部的落盘顺序未定义，必须等完成通知）。所以跨节点、跨机柜的 EP 用不了，这是硬限制，作者自己在 Discussion 里写得很清楚。GDN/大规模跨域部署要另想办法。

**2. workspace 随 EP 规模线性增长。** rank-major 是「每个源 rank 一块区域」，P 越大总量越大。8 卡 4096 token 时已经是 160+320 MiB；EP 到 64 卡时虽然仍是每 rank 同样的区域数，但整组占用的显存总量翻倍。论文把它列为 limitation，没有给 64 卡下的显存数字。

**3. 大批量仍输给融合方案。** 这是架构性差距，不是实现细节：分离的 kernel 无法把 NVLink 传输藏进 Tensor Core 计算里。作者把「把单边设计搬进 fused operator」列为未来工作——也就是说，本文当前形态最适合的是 **decode 小 batch**，而不是 prefill 或大 batch 推理。如果你的线上负载是长 prompt 预填充为主，MegaMoE 那一类融合 kernel 更合适。

另外几点值得记录：

- 主实验是**完美路由**（均匀、连续 rank），只有 Table 5 做了 Zipf，且 α 最大 1.25、最忙 rank 负载 1.9 倍。真实部署的热门专家集中度可能更高，此时 grouped GEMM 的瓶颈会盖过通信收益，本文的通信优势仍在但层收益会被压缩。
- 加速比全部是相对 DeepEP / DeepGEMM 的数字，没有绝对带宽效率之外的跨平台对照；baseline 的 payload 位宽细节（本文 dispatch 走 MXFP8）论文没展开，读者不宜把 1.2–3.0 倍直接外推到「同精度、同布局」的其它实现。
- 反例价值：作者明确写了 MegaMoE 的强项是 overlap、弱点是「元数据先行 + 与 GEMM tile 强耦合（换精度或换 GEMM 就要重写）」。这其实是分离式设计换来的可组合性——本文的模块化接口（FlashInfer `MoEEpCommunication`）能同时支持 BF16/FP8/MXFP8/NVFP4，也是它被三个框架接入的原因。
- 可复现性：all-to-all 输出按位一致、层误差 5.7×10⁻³ 都报了；IKET 打点使往返最多变化 6%，属于可信范围。

## 八、对工程实践的启示

- **先算固定开销占比，再决定要不要换通信库。** 判据很简单：把每步 token 数除以理论传输时间，如果这个时间远小于实测往返（本文 1 token 是 <1 µs vs 17–48 µs），那么优化重点在同步而不是带宽。反过来，当每 rank token 数过千，带宽利用率（本文 FENCE 到 68–71%）才是主指标。
- **小 batch 用「数据即旗标」，大 batch 用「计数 + fence + flag」。** 这不是实现偏好，而是两条代价曲线的交叉：哨兵方案每槽位都要 copy-out 和 reset，batch 一大就不划算；fence 方案的串行链在小 batch 时无法隐藏。自己做通信库时，按 token/rank 在 256 附近切换是合理的默认值。
- **布局比带宽更值得改。** rank-major 的两个收益（去重后最多省一半字节、workspace 小 6 倍）都是「不改硬件就能拿」的，而且对显存紧张的 PD 分离部署尤其重要。
- **接口解耦能换来生态。** 本文把通信做成与量化格式无关、与 MoE 计算后端解耦的模块，代价是大 batch 下少了融合优化，收益是被 vLLM/SGLang/TensorRT-LLM 直接吸收。工程上这是个明确的取舍，不是缺陷。

一句话总结：**MoE 推理的 all-to-all，在小 batch 区间是一个同步问题，不是一个带宽问题。** 这篇论文把「不交换元数据、直接把 token 推到消费它的地方、让数据自己报告到达」这三件事做干净了，并且诚实地标出了它失效的地方——出 NVLink 域，或者 batch 大到需要靠融合来藏通信。
