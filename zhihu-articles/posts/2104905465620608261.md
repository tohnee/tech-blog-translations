## 0x00 教程内容

2026 年 11 月 10 日，Google 开放 Gemini 4 Carbon，并在 Antigravity 里预览 `/swarm`；同一天 Cursor 把 Projects 升级成多人协作。两条消息被写成同一个故事：一条提示词拉起一队智能体。**把六家官方文档并排放，结论反过来：多智能体不是新东西，各厂商补的是编排权、成本分层、验证闭环这三层，而且四种可用状态并不一致。**

## 0x02 第一层，编排权归谁

真正的分水岭不是“能不能起多个 agent”，而是**下一步由谁决定**。Swarm 只有 handoff，交给模型自己转交 [S5]。Claude Code 的 dynamic workflows 把计划搬进代码：脚本持有循环、分支与中间结果，模型上下文里只留最终答案，规模定位是单次运行数十到数百个 agent，脚本可读、可保存、可重跑 [S3]。OpenAI Agents SDK 把编排分成 “Orchestrating via LLM” 与 “Orchestrating via code”，原文写明后者在速度、成本与性能上 “makes tasks more deterministic and predictable” [S6]。LangGraph 则从另一侧解决同一件事：checkpointer 把 thread 状态存成快照，用于人工介入、时间旅行与故障恢复；内存型 saver 重启即丢，生产要用 PostgresSaver 或 SqliteSaver [S9]。

**编排权迁移带来的直接结果，是中断可续、重跑一致与中间结果不占主上下文。** 这类约束跟模型能力无关，属于工程层 [S3][S9]。

## 0x03 第二层，成本怎么分层

Google 这次把角色分工和定价写进了同一份公告：Carbon 被分给架构设计、协调、审计这类最吃推理的角色，更快更轻的模型在并行隔离工作区里执行，对抗验证器测每次改动 [S1]。同一份公告又写明 Argon 仍是“绝大多数软件工程与知识工作”的理想选择，并承认 Carbon 会消耗更多 token 去跑扩展验证循环 [S1]。首发价每百万输入 2 美元、输出 10 美元，官方脚注写明优惠期 2026-11-30 到期，之后为 4 美元与 20 美元，且仅适用于公开访问的 Carbon [S1]。**4÷2 = 2、20÷10 = 2，是单价翻倍，不是“涨价两倍”**，这两个口径常被混着写。

| 产品 | 成本口径 | 官方文档写的代价 |
| --- | --- | --- |
| /swarm + Carbon | 贵模型只做架构/协调/审计，快模型并行 | Carbon 比 Argon 消耗更多 token 跑验证循环 [S1] |
| Claude Code agent teams | 每个队友是独立 Claude 实例 | “use significantly more tokens than a single session” [S4] |
| Cursor Agents Window | 云端并行 agent，可按任务切本地/云 | 文档未给统一成本数字 [S8] |
| GitHub Copilot | 多个 agent session 与入口扩张 | 周更新未给单价 [S10] |

还有一层容易踩坑的是**可用状态，不是能力**：`/swarm` 是 preview [S2]，Cursor Projects 多人协作是 beta [S7]，Cursor 3 的 Agents Window 早在 2026-04-02 就 GA [S8]，Claude Code agent teams 是 experimental、默认关闭、还要求交互会话 [S4]。agent teams 的文档自己列了不适用的场景：顺序依赖、同文件编辑 [S4]。

## 0x04 第三层，改完谁验

Antigravity 侧的写法是：coordinator 在隔离的 git worktree 里起并行 worker，让改动不互相覆盖，再由对抗验证器跑测试、挑战 diff；所有 agent 在一个 append-only 的共享留言板上协作 [S2]。Claude Code 的 dynamic workflows 写得更早：独立 agent 在结论上报前互审，内置 `/deep-research` 会把没通过交叉核对的说法过滤掉 [S3]。Cursor 走的是团队路线，共享任务看板加上跨队友的智能体通信，协调智能体提前发现两个人的工作重叠并同步，避免后面的重构与合并冲突 [S7]。

**验证闭环仍不是默认答案。** Claude Code 文档明确警告“两个队友编辑同一个文件会互相覆盖”，建议按文件划分所有权 [S4]；Antigravity 用隔离 worktree 从机制上绕开同类冲突，该博客同时写明这是五周内部试用 [S2]。**厂商把“跑测试、挑战 diff”写进产品，是产品化补齐**。

## 0x05 按场景分档

| 场景 | 优先看哪层 | 可核的官方文档依据 |
| --- | --- | --- |
| 长任务要可重跑、可审计 | 编排权归代码 | 脚本持有循环与中间结果、可重跑 [S3]；code-driven 更确定 [S6]；checkpointer 可恢复 [S9] |
| 崩了要续、要人工卡点 | 持久化 | checkpointer / human-in-the-loop / 生产用持久 saver [S9] |
| 改动要过独立复核 | 验证闭环 | 独立 agent 对抗互审 [S3]；隔离 worktree + 对抗验证器 [S2] |
| 团队多人并行、怕改撞车 | 协作与隔离 | 共享任务看板与 agent 间通信 [S7]；按文件划分所有权 [S4] |
| 已经 GA、今天就要用 | 入口成熟度 | Cursor 3 Agents Window 2026-04-02 GA [S8]；其余标 preview / beta / experimental [S2][S7][S4] |

验收别靠感觉，三条可核的步骤就够：同一任务按同样输入重跑两次，比对产物是否一致；故意在产物里注入一处事实错误，看独立校验能否拦下；让两个执行角色改同一个文件，看有没有机制报冲突。**先把这三条稳定跑通，再考虑换模型或扩大规模。**

## 0x06 把三层落到自己那套流程上

我最近拿 Orca 在搭一套多智能体协作流程，想做到的是一句话丢进需求，出来能提交、能进评审的改动。角色按三层摆，**强模型只跑四处决策**：拆需求、设计拆分、验收判定、PR 评审；开发、集成、提交交给免费模型。每个开发角色一个独立 worktree，文件范围在设计阶段就切到两两不重叠；下一环只读上一环留下的产物，不看它的推理过程。

我 11 月 11 日的方案记录里有一轮隔离仓库验证：开发、测试、评审、提交四个任务走完，模型配置恢复。也是那次记录里，**最后一次完成通知没送达**、状态未读，主控停在那里，补一次唤醒才收尾。按当时那版 Orca 的本机观察，它没有原生的自定义角色对象，也没有合并、建 PR 命令，角色只能靠全局规则、模型映射、启动参数三层拼出来。

| 三层 | 要定死的门禁点 |
| --- | --- |
| 编排权 | 完成通知不能当状态，送达要单独确认 |
| 成本分层 | 强模型收敛到四处决策，省的是决策次数 |
| 验证闭环 | 通知送达不等于验收通过，产物和准出条件要另查 |

按方案记录，这套流程只在隔离仓库验证过一轮机制，完整版本机还在实施，没上真项目。**难的不是能不能起一队 agent，是把“验过”做成默认门禁**：不定义清楚什么算真的做完，一条漏投的通知就能让整轮停在半路。

## 0xFF 总结

1. 多智能体能力不是新东西，2024 年的实验项目、Claude Code 的对抗互审、Cursor 9 月的 Projects 都能作证。
2. 变的是三层工程约束：编排权从模型移到代码、成本按角色分层、验证闭环被写进产品；四家的可用状态从 preview 到 GA 并不齐。
3. 按场景选，别按榜单选；自己搭时先把完成通知、验收证据与回环轮次上限定死，再上真项目。
