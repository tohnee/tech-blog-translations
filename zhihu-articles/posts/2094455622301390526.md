## vLLM 的 KV Cache 全景：类型、LMCache 优势与多实例共享实现

### 结论先行

1. vLLM 里 KV 的传输与共享统一由 **KV Connector**（`KVConnectorFactory` 注册，15 个）实现。
2. 跨实例共享 KV 的能力由 KV Connector 提供，LMCache 是其中**第三方实现**的共享型 connector，其余多为 vLLM 内建。
3. LMCache 的核心优势是**成熟易用**：独立 server + 前缀命中 + 分层存储，一条命令即可让多实例共享 KV。
4. LMCache 多实例共享通过 `LMCacheMPConnector` 实现：每个 vLLM 实例按 `role` 建立 scheduler/worker adapter，连接到同一个 LMCache server 读写同一份 KV 缓存。

### 二、LMCache 与其它方案的优势对比

### 2.1 共享范式对比（只看 KV 共享）

| 维度 | LMCache | 原生 NIXL | 原生 Mooncake / MooncakeStore |
| --- | --- | --- | --- |
| 代码位置 | 第三方包，vLLM 只放薄壳适配 | vLLM 内建 | vLLM 内建 |
| 共享范式 | 独立 lmcache server，多实例读写同一缓存 | P/D 分离，GPU 间点对点直传 | 分布式 KV store / 池 + 元数据 |
| 是否落缓存 | 是（L1 CPU / L2 磁盘 / 远程） | 否（传完即用，不持久） | 是（store 持久） |
| prefix cache 关系 | 按前缀命中复用 | 与本地 prefix cache 协作裁剪 | 强制依赖 prefix-cacheable group |
| 额外依赖 | pip install lmcache + server | pip install nixl 传输库 | pip install mooncake |
| 部署复杂度 | 低（起个 server 即可） | 中（需 P/D 拓扑） | 中（需 store 集群） |

### 2.2 LMCache 的四大优势

1. **部署最轻**：一条 `lmcache server --port 5555 --l1-size-gb 20` 起服务，所有 vLLM 实例 `--kv-offloading-backend lmcache` 连上即可，不要求 P/D 分离架构，普通多副本也能共享。
2. **成熟的缓存语义**：自带分层存储（L1 CPU / L2 磁盘 / 远程后端）、淘汰策略、前缀管理，开箱即用；而 NIXL 只是「直传管道」，Mooncake 要自己管 store 和元数据。
3. **版本解耦**：`use_native` 开关能切「vLLM 内置实现」或「lmcache 包最新实现」（见 [lmcache_connector.py](https://github.com/vllm-project/vllm/blob/03091e28b8ba956634c153beab0e52decafdef31/vllm/distributed/kv_transfer/kv_connector/v1/lmcache_connector.py#L88-L106)），升级缓存能力不依赖 vLLM 发版。
4. **生态成熟**：文档、社区、后端支持（磁盘/Redis/S3 等）比 vLLM 内建共享 connector 更丰富。

### 2.3 原生方案的优势（反过来说）

- **零第三方耦合**：代码就在 vLLM 里，版本天然兼容。
- **低延迟直传**：NIXL 走 NVLink/InfiniBand 点对点，P/D 分离场景比「经 server 中转」延迟更低、带宽更高。
- **专用优化**：Mooncake 有专门的元数据/分片管理，适合超大规模 KV 池。

### 2.4 选型建议

| 需求 | 推荐 |
| --- | --- |
| 快速、低运维的多实例缓存复用 | LMCache |
| 极致低延迟的 prefill/decode 解耦 | NIXL |
| 超大规模分布式 KV 池 | MooncakeStoreConnector |

### 三、LMCache 如何实现多实例共享

LMCache 通过 **`LMCacheMPConnector`**（多进程模式）实现多实例共享，核心思路：**多个 vLLM 实例都作为客户端，连接到同一个 LMCache server，读写同一份 KV 缓存。**

### 3.1 架构模型

```text
flowchart TB
    server["LMCache Server<br/>(共享 KV 缓存池: L1/L2/远程)"]

    subgraph A["vLLM 实例 A"]
        sa["scheduler / worker"]
    end
    subgraph B["vLLM 实例 B"]
        sb["scheduler / worker"]
    end
    subgraph C["vLLM 实例 C"]
        sc["scheduler / worker"]
    end

    server <-->|读 / 写 KV| A
    server <-->|读 / 写 KV| B
    server <-->|读 / 写 KV| C
```

任一实例算出 KV 存入 server，其他实例命中相同 prefix 时直接加载，跳过重复 prefill。

### 3.2 关键实现代码

**① 连接参数从 extra_config 读取，按 role 建立对应 adapter**

见 [lmcache_mp_connector.py](https://github.com/vllm-project/vllm/blob/03091e28b8ba956634c153beab0e52decafdef31/vllm/distributed/kv_transfer/kv_connector/v1/lmcache_mp_connector.py#L472-L518)：

```python
def __init__(self, vllm_config, role, kv_cache_config):
    super().__init__(vllm_config, role, kv_cache_config)
    assert vllm_config.kv_transfer_config is not None

    # 从 extra_config 读取 LMCache server 连接信息
    server_host = vllm_config.kv_transfer_config.get_from_extra_config(
        "lmcache.mp.host", "tcp://localhost")
    server_port = vllm_config.kv_transfer_config.get_from_extra_config(
        "lmcache.mp.port", 5555)
    mq_timeout = float(vllm_config.kv_transfer_config.get_from_extra_config(
        "lmcache.mp.mq_timeout", 300.0))
    heartbeat_interval = float(vllm_config.kv_transfer_config.get_from_extra_config(
        "lmcache.mp.heartbeat_interval", 10.0))

    server_url = f"{server_host}:{server_port}"
    zmq_context = zmq.Context.instance()

    # 根据角色建立不同的 adapter，二者都连向同一个 server
    if self.role == KVConnectorRole.SCHEDULER:
        self.scheduler_adapter = create_scheduler_adapter(
            server_url, zmq_context, vllm_config, mq_timeout, heartbeat_interval)
        self.request_trackers = {}
    elif self.role == KVConnectorRole.WORKER:
        self.worker_adapter = create_worker_adapter(
            server_url, zmq_context, vllm_config, mq_timeout, heartbeat_interval)
    else:
        raise ValueError(f"Unknown KVConnectorRole: {self.role}")
```

**② 强制关闭 hybrid KV cache manager**

见 [lmcache_mp_connector.py](https://github.com/vllm-project/vllm/blob/03091e28b8ba956634c153beab0e52decafdef31/vllm/distributed/kv_transfer/kv_connector/v1/lmcache_mp_connector.py#L70-L83)：

见 [lmcache_mp_connector.py](https://github.com/vllm-project/vllm/blob/03091e28b8ba956634c153beab0e52decafdef31/vllm/distributed/kv_transfer/kv_connector/v1/lmcache_mp_connector.py#L1191-L1217)：

### 3.3 使用方式

```bash
# 1. 起一个共享的 LMCache server
lmcache server --host localhost --port 5555 --l1-size-gb 20 &

# 2. 每个 vLLM 实例都指向这个 server
vllm serve <model> \
    --kv-offloading-backend lmcache \
    --kv-offloading-size 20 \
    --disable-hybrid-kv-cache-manager
```

多个实例连同一个 server 后，任一实例算出的 KV 缓存写入 server，其他实例遇到相同前缀即可命中复用。

### 3.4 与进程内模式的区别

| 模式 | Connector | 存储位置 | 是否跨实例 |
| --- | --- | --- | --- |
| 进程内 | LMCacheConnectorV1 | 本实例进程内的 LMCache 引擎 | 否 |
| 多进程 | LMCacheMPConnector | 独立 lmcache server | 是 |

### 3.5 前缀命中如何实现

前缀命中分三层，核心是「按 block 哈希去重 + 匹配最长可复用前缀」。

**第一层：vLLM 侧生成 block hash**

vLLM v1 给每个 KV block 算一个哈希（`block_hashes`），作为「这段 prompt 的 KV 指纹」——相同 prompt 前缀 → 相同 block hash，这是所有 prefix cache（含 LMCache、MooncakeStore）的共同基础。请求对象带 `all_token_ids`（完整 prompt token）和 `cache_salt`（见 [request.py](https://github.com/vllm-project/vllm/blob/03091e28b8ba956634c153beab0e52decafdef31/vllm/v1/request.py#L185-L220)），`cache_salt` 用于隔离不同缓存命名空间（不同模型/配置不互相命中）。

**第二层：LMCache 侧做最长前缀匹配**

核心入口 `get_num_new_matched_tokens`（见 [lmcache_mp_connector.py](https://github.com/vllm-project/vllm/blob/03091e28b8ba956634c153beab0e52decafdef31/vllm/distributed/kv_transfer/kv_connector/v1/lmcache_mp_connector.py#L724-L792)）：

```python
def get_num_new_matched_tokens(self, request, num_computed_tokens):
    tracker = self._get_or_create_request_tracker(request)

    # 1. 用「完整 token 序列 + cache_salt」向 LMCache server 查询
    self.scheduler_adapter.maybe_submit_lookup_request(
        request.request_id,
        token_ids=list(request.all_token_ids),   # 完整 prompt token
        cache_salt=tracker.cache_salt,           # 命名空间隔离
    )

    # 2. 取查询结果
    ret = self.scheduler_adapter.check_lookup_result(request.request_id)
    if ret is None:
        return None, True    # server 还没算完，让 scheduler 稍后再问

    # 3. ret = server 侧已缓存的 token 数（按 chunk 对齐）
    num_vllm_blocks    = num_computed_tokens // self.vllm_block_size
    num_lmcache_blocks = ret // self.vllm_block_size
    tracker.increase_num_stored_blocks(num_lmcache_blocks)

    # 4. 需要从 server 加载的 = 缓存命中数 - 本地已算数
    need_to_load = max(0, ret - num_computed_tokens)
    return need_to_load, need_to_load > 0
```

关键点：`need_to_load = max(0, ret - num_computed_tokens)` —— **server 命中的 token 数减去本地已经算过的，就是真正要加载的部分**，从而跳过重复 prefill。

**第三层：匹配粒度按 chunk 对齐**

LMCache 存 KV 的单位是 **chunk**（N 个 block 一组），命中数必须按 chunk 边界对齐（见 [lmcache_mp_connector.py](https://github.com/vllm-project/vllm/blob/03091e28b8ba956634c153beab0e52decafdef31/vllm/distributed/kv_transfer/kv_connector/v1/lmcache_mp_connector.py#L774-L777)）：

```python
assert ret % (self.scheduler_adapter.num_blocks_per_chunk() * self.vllm_block_size) == 0
```

即前缀命中长度被**向下取整到最近的 chunk 边界**——宁可少加载一个不完整 chunk，也不加载半个 chunk。

**双命中合并（vLLM APC + LMCache 不重复计）**

若请求同时被 vLLM 本地 prefix cache（APC）和 LMCache 命中，两者都是「同一段前缀的 KV」，不能简单相加，否则重复计数。代码用 `max` 取两者较大者（见 [lmcache_mp_connector.py](https://github.com/vllm-project/vllm/blob/03091e28b8ba956634c153beab0e52decafdef31/vllm/distributed/kv_transfer/kv_connector/v1/lmcache_mp_connector.py#L314-L333)）：

```python
computed_blocks = tracker.num_scheduled_tokens // vllm_block_size + max(
    tracker.num_vllm_hit_blocks,     # vLLM 本地命中
    tracker.num_lmcache_hit_blocks,  # LMCache 命中
)
```

**小结**：前缀命中 = 用完整 prompt token（+ `cache_salt` 命名空间）向 LMCache server 查询最长可复用前缀长度，命中长度按 chunk 对齐取整，减去本地已计算的 token 数，得到真正需要加载的量；vLLM 本地 prefix cache 与 LMCache 命中取 `max` 合并避免重复计数。

### 四、LMCacheConnectorV1 与 LMCacheMPConnector 代码详解

LMCache 在 vLLM 里有两个 connector，代码形态差异很大：`LMCacheConnectorV1` 是**薄壳委派**，几乎没有业务逻辑；`LMCacheMPConnector` 是**完整实现**，直接通过 ZMQ 连接独立 server。

### 4.1 LMCacheConnectorV1（进程内模式，薄壳适配器）

这个类本身几乎不承载业务逻辑，它把 vLLM 的 `KVConnectorBase_V1` 接口调用全部转发给真正的引擎 `self._lmcache_engine`。

### 4.1.1 构造：`use_native` 二选一决定引擎

见 [lmcache_connector.py](https://github.com/vllm-project/vllm/blob/03091e28b8ba956634c153beab0e52decafdef31/vllm/distributed/kv_transfer/kv_connector/v1/lmcache_connector.py#L78-L108)：

```python
use_native = vllm_config.kv_transfer_config.get_from_extra_config("use_native", False)
if use_native:
    from vllm.distributed.kv_transfer.kv_connector.v1 import lmcache_integration
    cls = lmcache_integration.vllm_v1_adapter.LMCacheConnectorV1Impl   # vLLM 内置
else:
    from lmcache.integration.vllm.vllm_v1_adapter import (
        LMCacheConnectorV1Impl as LMCacheConnectorLatestImpl)
    cls = LMCacheConnectorLatestImpl                                    # lmcache 包最新版

self._lmcache_engine = cls(vllm_config, role, self)   # 引擎拿到 role 和 self(壳) 引用
```

**关键点**：引擎构造函数收到的第三个参数是 `self`（这个壳本身），因此引擎需要反向调用 vLLM 接口时会通过这个壳回调，形成「vLLM 壳 ↔ LMCache 引擎」的双向引用。

### 4.1.2 委派模式：所有方法一行转发

worker/scheduler 侧的 `start_load_kv` / `save_kv_layer` / `wait_for_layer_load` / `build_connector_meta` / `request_finished` 等全部一行转发给引擎（见 [lmcache_connector.py](https://github.com/vllm-project/vllm/blob/03091e28b8ba956634c153beab0e52decafdef31/vllm/distributed/kv_transfer/kv_connector/v1/lmcache_connector.py#L161-L305)）。

其中 `get_num_new_matched_tokens` 有个**重要差异**——把引擎返回的布尔值强制改成 `False`：

```python
return self._lmcache_engine.get_num_new_matched_tokens(request, num_computed_tokens), False
```

含义：进程内模式**不做异步加载**，命中多少 token 都同步返回，scheduler 不会「稍后再问」。这是进程内模式（同进程直接内存拷贝）和多进程模式（跨进程异步传输）的本质区别。

### 4.1.3 两个独有的非委派方法

- `requires_piecewise_for_cudagraph`（[L69-L76](https://github.com/vllm-project/vllm/blob/03091e28b8ba956634c153beab0e52decafdef31/vllm/distributed/kv_transfer/kv_connector/v1/lmcache_connector.py#L69-L76)）：启用 `use_layerwise` 时要求 CUDA graph 用 PIECEWISE 模式，因为 `wait_for_layer_load`/`save_kv_layer` 里有真实异步同步，无法被 CUDA graph 捕获。
- KV events 聚合（`get_kv_connector_kv_cache_events` / `update_connector_output` / `take_events`，[L239-L357](https://github.com/vllm-project/vllm/blob/03091e28b8ba956634c153beab0e52decafdef31/vllm/distributed/kv_transfer/kv_connector/v1/lmcache_connector.py#L239-L357)）：把引擎产生的 `BlockStored` 事件包装成 `LMCacheKVEvents`，用 `KVEventAggregator` 做多 worker 聚合，喂给 vLLM 的 KV 事件系统。

### 4.2 LMCacheMPConnector（多进程模式，完整实现）

这是真正有完整逻辑的 connector，不委派给外部引擎，直接通过 **ZMQ 消息队列** 和独立 `lmcache server` 通信。

### 4.2.1 整体架构：scheduler/worker 双角色 + 独立 server

见 [lmcache_mp_connector.py](https://github.com/vllm-project/vllm/blob/03091e28b8ba956634c153beab0e52decafdef31/vllm/distributed/kv_transfer/kv_connector/v1/lmcache_mp_connector.py#L472-L520)：

```python
if self.role == KVConnectorRole.SCHEDULER:
    self.scheduler_adapter = create_scheduler_adapter(...)   # lookup/加锁/元数据
elif self.role == KVConnectorRole.WORKER:
    self.worker_adapter = create_worker_adapter(...)         # 真正的 KV 存取
```

scheduler 侧维护 `request_trackers`（每请求一个状态机），worker 侧持有 `worker_adapter` 做实际数据传输，两侧通过 vLLM 的 scheduler↔worker 通道传递 `LMCacheMPConnectorMetadata`。

### 4.2.2 三个基础模块

- `reformat_block_ids`（[L70-L83](https://github.com/vllm-project/vllm/blob/03091e28b8ba956634c153beab0e52decafdef31/vllm/distributed/kv_transfer/kv_connector/v1/lmcache_mp_connector.py#L70-L83)）：强制禁用 hybrid KV cache manager，因为 LMCache 只支持单层 KV cache，多层 block_ids 直接抛错。
- `extract_world_size_and_kv_rank`（[L86-L105](https://github.com/vllm-project/vllm/blob/03091e28b8ba956634c153beab0e52decafdef31/vllm/distributed/kv_transfer/kv_connector/v1/lmcache_mp_connector.py#L86-L105)）：MLA 模型特判——TP 不改变 MLA 的 KV cache，用 `rank // tp_size` 剔除 TP 对 rank/world_size 的影响。
- `ParallelStrategy`（在 adapter 工厂函数中构造）：把 `mla_enabled`、world_size、kv_rank、TP、PP 打包传给 LMCache adapter，让 server 知道 KV 如何跨并行维度分布。

### 4.2.3 状态机：LMCacheMPRequestTracker

见 [lmcache_mp_connector.py](https://github.com/vllm-project/vllm/blob/03091e28b8ba956634c153beab0e52decafdef31/vllm/distributed/kv_transfer/kv_connector/v1/lmcache_mp_connector.py#L174-L227)，请求生命周期：

```text
PREFETCHING ──update_state_after_alloc──▶ WAITING_FOR_LOAD ──process_loading_requests──▶ READY
```

Tracker 关键字段：

| 字段 | 含义 |
| --- | --- |
| all_token_ids | 完整 prompt token（只读） |
| block_hashes | 每个 block 的哈希（只读） |
| allocated_block_ids | 已分配的 block id（动态增长） |
| num_scheduled_tokens | 已调度 token 数（避免存半满 block） |
| num_stored_blocks | 已存入 LMCache 的 block 数 |
| num_vllm_hit_blocks | vLLM 本地 prefix cache 命中块数 |
| num_lmcache_hit_blocks | LMCache 命中块数 |
| state | 状态机当前状态 |

### 4.2.4 双命中合并逻辑（最精妙的部分）

见 [lmcache_mp_connector.py](https://github.com/vllm-project/vllm/blob/03091e28b8ba956634c153beab0e52decafdef31/vllm/distributed/kv_transfer/kv_connector/v1/lmcache_mp_connector.py#L314-L333) 的 `GetStoreMetadata`：

```python
computed_blocks = tracker.num_scheduled_tokens // vllm_block_size + max(
    tracker.num_vllm_hit_blocks,     # vLLM 本地命中
    tracker.num_lmcache_hit_blocks,  # LMCache 命中
)
```

源码注释解释了为何用 `max` 而非 `sum`：

- 两者都是「同一段前缀的 KV 已可用」，**不能相加**（会重复计重叠前缀）。
- `num_lmcache_hit_blocks` 已算进 `num_stored_blocks`（lookup 时设置），必须包含以保证上界一致，且不会重复存。
- LMCache 按 chunk 存，`num_lmcache_hit_blocks` 会被**向下取整**到 chunk 边界；若 vLLM APC 命中更多（如 APC=44 块、LMCache 对齐后=32 块），只用 lmcache 值会把上界设低导致**漏存** APC 命中的 12 块。用 `max` 取较大值保证上界正确。

### 4.2.5 retrieve 时的 APC 重叠保护

见 [lmcache_mp_connector.py](https://github.com/vllm-project/vllm/blob/03091e28b8ba956634c153beab0e52decafdef31/vllm/distributed/kv_transfer/kv_connector/v1/lmcache_mp_connector.py#L407-L420)：

```python
apc_overlap_blocks = tracker.num_vllm_hit_blocks - start
skip_first_n_tokens = apc_overlap_blocks * vllm_block_size
```

原因：retrieve 在 LMCache 的 CUDA stream 上写，而并发的其他请求可能在 vLLM stream 上读这些 APC 共享块。为避免**跨 stream 数据竞争**，server 必须跳过写这些与 APC 重叠的位置。

### 4.2.6 模块加载回退：_resolve_lmcache_mp_connector

见 [lmcache_mp_connector.py](https://github.com/vllm-project/vllm/blob/03091e28b8ba956634c153beab0e52decafdef31/vllm/distributed/kv_transfer/kv_connector/v1/lmcache_mp_connector.py#L1191-L1217)，在模块加载时执行一次：优先用 lmcache 包外部实现，失败回退到 vLLM 内置，`LMCACHE_USE_UPSTREAM_MP` 环境变量可强制用内置。这样用户只配 `kv_connector: "LMCacheMPConnector"` 即可，无需手配 `kv_connector_module_path`。

### 4.3 两者对比总结

| 维度 | LMCacheConnectorV1 | LMCacheMPConnector |
| --- | --- | --- |
| 模式 | 进程内 | 多进程（独立 server） |
| 代码形态 | 薄壳委派 | 完整实现 |
| 引擎位置 | lmcache 包 / vLLM 内置（use_native 切换） | 直接连 lmcache server（ZMQ） |
| 通信 | 同进程直接调用 | scheduler/worker 传 metadata + ZMQ 连 server |
| 异步加载 | 否（强制返回 False） | 是（None, True 触发重试） |
| 状态机 | 无（引擎内部管理） | 有（PREFETCHING→WAITING_FOR_LOAD→READY） |
| 多实例共享 | 否 | 是 |

**核心结论**：`LMCacheConnectorV1` 把 LMCache 当本地缓存库用，`LMCacheMPConnector` 把 KV 缓存集中到独立 server 让多实例共享。后者代码复杂得多，因为它要自己处理跨进程 lookup、加锁、chunk 对齐、异步加载、双命中合并、APC 竞争保护等一系列分布式缓存问题。

### 4.4.1 LMCacheConnectorV1（lmcache_connector.py，共 358 行）

### 4.4.2 LMCacheMPConnector（lmcache_mp_connector.py，共 1217 行）

**模块级三处关键设计**：

1. **顶部 import 的 try/except（[L26-L50](https://github.com/vllm-project/vllm/blob/03091e28b8ba956634c153beab0e52decafdef31/vllm/distributed/kv_transfer/kv_connector/v1/lmcache_mp_connector.py#L26-L50)）**：优先从 lmcache 包导入 `LMCacheMPSchedulerAdapter`/`LMCacheMPWorkerAdapter`/`LoadStoreOp`/`ParallelStrategy`；若 lmcache 包版本旧则回退到 vLLM 内置 `lmcache_integration`。还处理了 `RequestAllocationRecord` 的改名兼容（旧版叫 `BlockAllocationRecord`）。
2. **`reformat_block_ids`（[L70-L83](https://github.com/vllm-project/vllm/blob/03091e28b8ba956634c153beab0e52decafdef31/vllm/distributed/kv_transfer/kv_connector/v1/lmcache_mp_connector.py#L70-L83)）**：vLLM 的 `KVCacheBlocks.get_block_ids()` 返回 `tuple[list[int], ...]`——外层 tuple 对应多层 KV cache（hybrid），内层 list 是单层 block id。LMCache 只支持单层，所以 `None`→空列表、长度>1→抛错强制 `--disable-hybrid-kv-cache-manager`、否则取 `block_ids[0]`。
3. **`extract_world_size_and_kv_rank`（[L86-L105](https://github.com/vllm-project/vllm/blob/03091e28b8ba956634c153beab0e52decafdef31/vllm/distributed/kv_transfer/kv_connector/v1/lmcache_mp_connector.py#L86-L105)）**：MLA 模型（DeepSeek 系列）的 KV cache 只按非 TP 维度切分，TP 不复制 KV。所以要「剔除 TP 影响」：`rank // tp_size`。注释还解释了 vLLM 并行组构建顺序（先 TP 后 PP），所以 `rank // tp_size` 能正确映射到不含 TP 的逻辑 KV rank。

**`LMCacheMPRequestTracker`（[L185-L285](https://github.com/vllm-project/vllm/blob/03091e28b8ba956634c153beab0e52decafdef31/vllm/distributed/kv_transfer/kv_connector/v1/lmcache_mp_connector.py#L185-L285)）**：每请求一个 tracker，是状态机载体。关键判断方法：

- `needs_retrieve()`：`num_lmcache_hit_blocks > num_vllm_hit_blocks and state != READY`，即「LMCache 命中比 vLLM 本地命中多，且还没加载完」才需要 retrieve。
- `is_ready_for_retrieving()`：`state == WAITING_FOR_LOAD and needs_retrieve()`。

两者组合决定「何时真正从 server 拉 KV」。

**`LMCacheMPRequestMetadata`（[L288-L431](https://github.com/vllm-project/vllm/blob/03091e28b8ba956634c153beab0e52decafdef31/vllm/distributed/kv_transfer/kv_connector/v1/lmcache_mp_connector.py#L288-L431)）**：跨 scheduler/worker 传递的操作描述，只有两个静态工厂方法，是核心逻辑所在。

- **`GetStoreMetadata`**（存 KV）：<br>

1. `computed_blocks = num_scheduled_tokens // vllm_block_size + max(vllm_hit, lmcache_hit)` —— 有效已就绪块上界。
2. `min_available_blocks = min(len(block_hashes), len(allocated_block_ids), computed_blocks)` —— 取三个下界最小值避免越界。
3. `num_staging_blocks = min_available_blocks - num_stored_blocks` —— 减去已存的得「本轮待存」。
4. `num_chunks = num_staging_blocks // blocks_in_chunk` —— **向下取整到 chunk 边界**，不足一个 chunk 不存（LMCache 以 chunk 为存取单位）。
5. 若 `num_chunks >= 1`，构造 `LoadStoreOp` 方向 `STORE`，`num_stored_blocks` 前移 `end - start`。

- **`GetRetrieveMetadata`**（取 KV）：<br>

1. 先判 `is_ready_for_retrieving()`，否则返回 `None`。
2. `start = num_vllm_hit_blocks // blocks_in_chunk * blocks_in_chunk` —— 从 vLLM 命中块的 chunk 对齐边界开始（已算部分不用再取）。
3. `end = num_lmcache_hit_blocks` —— 取到 LMCache 命中块为止。
4. `assert end % blocks_in_chunk == 0` —— 保证 end 在 chunk 边界。
5. 计算 `skip_first_n_tokens`（APC 重叠保护）。
6. 构造 `LoadStoreOp` 方向 `RETRIEVE`，带 `skip_first_n_tokens`。

**`LMCacheMPConnectorUpstream`（[L461-L1214](https://github.com/vllm-project/vllm/blob/03091e28b8ba956634c153beab0e52decafdef31/vllm/distributed/kv_transfer/kv_connector/v1/lmcache_mp_connector.py#L461-L1214)）**，主体类，方法分 worker / scheduler 两侧：

Worker 侧：

- `start_load_kv`（[L555-L592](https://github.com/vllm-project/vllm/blob/03091e28b8ba956634c153beab0e52decafdef31/vllm/distributed/kv_transfer/kv_connector/v1/lmcache_mp_connector.py#L555-L592)）：从 metadata 筛 `RETRIEVE` 请求，用 `torch.cuda.Event(interprocess=True)` 记录跨进程事件，再 `batched_submit_retrieve_requests` 批量提交。event 让 server 在正确时机开始异步拷贝。
- `wait_for_layer_load`（[L594-L605](https://github.com/vllm-project/vllm/blob/03091e28b8ba956634c153beab0e52decafdef31/vllm/distributed/kv_transfer/kv_connector/v1/lmcache_mp_connector.py#L594-L605)）：空实现——MP 模式不做逐层流水线，一次性批量加载。
- `save_kv_layer`（[L607-L626](https://github.com/vllm-project/vllm/blob/03091e28b8ba956634c153beab0e52decafdef31/vllm/distributed/kv_transfer/kv_connector/v1/lmcache_mp_connector.py#L607-L626)）：空实现——MP 模式的存不在 attention 层逐层做，集中在 `wait_for_save` 批量做。

Scheduler 侧：

### 4.5 完整数据流串联

```text
scheduler 侧                          worker 侧
─────────────                         ─────────────
get_num_new_matched_tokens            start_load_kv
  └─ maybe_submit_lookup_request        └─ 筛 RETRIEVE 元数据
     (向 server 查前缀)                   └─ batched_submit_retrieve_requests
update_state_after_alloc                    (ZMQ → server 异步拉 KV)
  └─ PREFETCHING→WAITING_FOR_LOAD      wait_for_save
build_connector_meta                     └─ 筛 STORE 元数据
  ├─ _process_retrieve_requests           └─ batched_submit_store_requests
  │    └─ WAITING_FOR_LOAD→READY             (ZMQ → server 异步存 KV)
  ├─ _process_new_requests
  └─ _process_cached_requests
```

核心分工：**scheduler 侧负责「决策」**（查前缀、算命中、定状态、生成元数据），**worker 侧负责「执行」**（真正通过 ZMQ 从 server 拉/存 KV）。两者通过 `LMCacheMPConnectorMetadata` 传递操作指令。

### 五、总结

- vLLM 的 KV 传输与共享统一由 **KV Connector（15 个）** 实现，跨实例共享型 connector 共 11 个。
- LMCache 是第三方共享型 connector，核心优势是**成熟易用**：独立 server、前缀命中、分层存储、生态完善，部署最轻。
- LMCache 提供两种 connector：`LMCacheConnectorV1`（进程内，薄壳委派）和 `LMCacheMPConnector`（多进程，完整实现）。
- 多实例共享由 `LMCacheMPConnector` 实现：所有实例作为客户端连接同一个 LMCache server，按 `role` 建立 scheduler/worker adapter 读写同一份 KV 缓存，通过前缀命中跳过重复 prefill。
