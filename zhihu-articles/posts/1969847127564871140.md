> 本文似乎是重新推了一遍 ChunkFlow 论文中的 ChunkSchedulingAlgorithm...

在开发 rl 框架的过程中，我发现序列并行变成了提升整体实验效率的一个卡点。

在 [slime v0.1.0: 重新定义高性能 RL 训练框架](https://zhuanlan.zhihu.com/p/1945237948166547268) 中我提到，我们应该按 RL 中推理部分的最佳工况来给实验分配 gpu，例如如果 64 张卡推理就可以满足当前任务的 kv cache 需求，那么把 256 卡分为 4 个并行的实验，而不是直接跑一个实验，是收益更大的。为此，fsdp/zero3、cpu adam 等在 pretrain 场景下比较受嫌弃的省显存技术变得重要了起来。

但是从这个角度来说，我们没有一个很好的用更少的卡训练更长序列的方法：在 agent 的大背景下，rollout 部分会很容易生成一个 1M 长度的序列，如果一个 dp 组只能跑 8k token，那么训练就会按 128 的倍数往上加。而且在 rl 场景中我们其实很难预测一个 sample 的最终长度，似乎只能盲目地给一个上限（如 64k），希望不要产生太多被截断的样本，同时为了避免训练 oom 而尽量开大 cp。

更直接地说，很多人能搞来 8 卡跑个 4B 模型，能用这 8 卡给 4B 模型推理出 1M 的序列，但是这 8 卡训不动这 1M 的序列。

那么我们有没有可能通过牺牲一些训练时间，用更少的卡训更长的序列呢？

注意到推理框架是可以在很少的资源下推很长很长的序列的，这是因为推理部分有 kv cache，从而可以通过 chunked prefill 的方式来减少单次的计算量。而一般我们认为在训练过程中，kv cache 操作会让梯度中断，从而无法直接使用这个技巧。

但是观察到：

- 前向计算的时候，前面的序列的激活值不依赖后面序列的激活值 => 我们可以从前向后算
- 反向计算的时候，后面序列的梯度不依赖前面序列的梯度 => 我们可以从后向前算

所以如果我们愿意牺牲一次前向计算，似乎是可以实现训练中的 kv cache 的。

考虑如下的一种情况，我们将输入的 sequence 拼为 n 个 chunk，首先进行一次**从前向后**的正向计算，并保存每一段的 kv cache：

```python
# init a dict for storing kv cache
model.kv_cache: dict[int, torch.Tensor] = {}
with torch.no_grad():
    for i in range(num_chunks):
        model(input_ids[i * chunk_size : (i + 1) * chunk_size])
```

其中 attention 部分采用分段计算，大致为：

```python
def attn_forward(self, q_i, kv_i):
    # move to cpu to save memory
    self.kv_cache[i] = kv_i.detach().cpu()
    out_i, lse_i = flash_attn_forward(q_i, kv_i, causal=True)
    for j in range(i):
        out_j, lse_j = flash_attn_forward(
            q_i, self.kv_cache[j].gpu(), causal=False,
        )
        out_i, lse_i = update_out_and_lse(out_i, lse_i, out_j, lse_j)
    return out_i, lse_i
```

即，分段计算并存储 kv cache，并利用前面 chunk 的 kv cache 来计算后面的 attention。这里 `update_out_and_lse` 的方式参见：[ring attention + flash attention：超长上下文之路](https://zhuanlan.zhihu.com/p/683714620)。

并在实际训练的时候，**从后向前**进行训练：

```python
# init a dict for storing the gradient of kv cache
model.dkv_cache: dict[int, torch.Tensor] = {}
for i in reverse(range(num_chunks)):
    out_i = model(input_ids[i * chunk_size : (i + 1) * chunk_size])
    loss = loss_func(out_i, label[i * chunk_size : (i + 1) * chunk_size])
    loss.backward()
```

其中 attention 部分的前向部分如上，反向部分大致为：

```python
def attn_backward(self, d_out_i, q_i, kv_i, lse_i):
    d_q_i, d_kv = flash_attn_backward(d_out_i, q_i, kv_i, lse_i, causal=True)
    d_kv_i = (
        d_kv + self.d_kv_cache[i].gpu()
        if i in self.d_kv_cache else d_kv
    )
    for j in range(i):
        d_q, d_kv = flash_attn_backward(
            d_out_i, q_i, self.kv_cache[i].gpu(), lse_i, causal=False,
        )
        d_q_i += d_q
        self.d_kv_cache[j] = (
            d_kv + self.d_kv_cache[j].gpu()
            if j in self.d_kv_cache else d_kv
        ).cpu()
    return d_q_i, d_kv_i
```

似乎我们就完成了在单卡上分 chunk 计算长序列。同时因为我们在训练中可以将 kv cache offload 至 cpu，所以并不会出现 O(seq_len) 的激活峰值。

那么进一步，我们能不能将这个方案和多机的序列并行结合呢？

如果假设我们的序列并行维度为 k（为了表述简单，我们称为 k 张卡），并将序列分解为 kn 个 chunk，似乎只需要把这 kn 个 chunk 划分为 (0, 1, ..., k -1), (k, k + 1, ..., 2k - 1), ... ((n-1)k, (n-1)k + 1, ..., nk - 1) 这 n 段，并让这 k 张卡使用 ring attn 或者 ulysses 等方案同时计算其中的一段，就可以复现上述的训练流程了。如果使用 ring attn 进行段内的计算，可以考虑使用 zigzag 等方案均衡计算量。
