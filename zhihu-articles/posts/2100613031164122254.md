之前有不少同学问我，想自己从零做一个 Agentic RL 项目，该怎么找论文？好不容易找到一个有意思的项目，结果没有显卡，训练环境配不起来，论文不提供数据，不知道怎么改进项目。<br>这次我就以一个多模态 Agent rl 论文作为项目来抛砖引玉一下吧，大家可以在此基础上尝试复现，然后魔改，也可以自己找项目自己包装一下。<br>**代码与复现资源**

<br>一、找项目<br>现在有 AI 帮忙，想找个高质量的项目论文其实很简单。<br>比如我想做一个多模态 Agentic RL 的项目，直接让 gpt(最好国外的 ai，方便搜 arxiv 和 GitHub)搜索最近几个月出的多模态 agentic RL 相关论文，要求有可复现的代码和数据。然后自己挑选感兴趣的任务类型就可以尝试复现了。<br>我这次选的论文是腾讯混元联合港中文、港大和 UCLA 今年 5 月挂载 Arxiv 上的 OpenSearch-VL，选它主要是因为其任务简单直观好理解，而且论文开源了模型、训练数据和代码，非常方便复现。<br>论文地址：[HTTPS://arxiv.org/abs/2605.05185](HTTPS://arxiv.org/abs/2605.05185) 。<br>论文主要研究如何通过 SFT 和 Agentic RL，让模型自主使用图像裁剪、OCR、以图搜图、文字搜索等工具，完成需要视觉理解、外部信息检索和多步推理的复杂问答任务。<br>

它的任务挺有意思的。比如给模型一张桥的照片，问它是哪一年通车的。<br>模型光看图片肯定不一定知道答案，它可能需要先裁剪图片找路牌，用 OCR 识别文字，再通过以图搜图确定这座桥的名字，最后用文字搜索确认通车时间。<br>整个过程需要模型自己决定什么时候看图、什么时候搜索、搜索完要不要继续核验。<br>

<br>二、没有 GPU，训练怎么搞？<br>之前想要复现论文，要么自己租 GPU 服务器，要么用公司或者课题组的算力。虽然也能用，但经常会遇到各种问题，比如 CUDA 和驱动版本对不上、环境依赖下不来、网络不通，有时候还要和别人抢卡。更麻烦的是，除了模型训练，还得自己维护一套推理服务和 Trainer 框架，可能论文还没正式开始复现，就先花了好几天折腾环境。<br>在@不要葱姜蒜大佬的介绍下，我这次尝试使用 PyTRIO [HTTPS://pytrio.com/home](HTTPS://pytrio.com/home)<br>简单介绍一下，PyTRIO 是一个提供远程模型训练和推理能力的平台。它把训练过程中需要 GPU 的部分封装成了 API，比如模型的前向传播、反向传播、优化器更新、LoRA 权重保存以及模型采样等。我们只需要通过 Python SDK 调用这些接口，就能完成模型训练。<br>我感觉比较方便的一点是，数据处理、Reward、Loss 和训练循环这些都可以自己用 Python 来写，底层的 GPU 计算交给 PyTRIO**。** <br>我这次就是在 Mac 上写代码，CPU 服务器负责数据处理和工具调用，Qwen3.5-4B 的 SFT 和 RL 训练都通过 PyTRIO 完成。整个过程中没有自己部署 GPU 训练服务，也不用操心显卡调度和显存资源。<br>当然，Agent 的工具环境、数据清洗和评测这些工作还是要自己做的。不过至少省掉了不少训练基础设施上的麻烦，可以把更多精力放在任务、数据和算法本身。<br>另外 PyTRIO 还有一个[官方 Skill](https://github.com/SwanHubX/pytrio-skill)，我直接装给了 Codex，让它参考 SDK 文档帮我适配训练代码、检查报错和分析日志。<br>这个任务 还有个麻烦的地方：需要外部的搜索工具。但好在多数的服务都有免费额度，dpsk 的 search 也很便宜。<br>这次文字搜索和网页抓取用了 DeepSeek，图搜用豆包 Global，OCR 用 PaddleOCR，裁剪和图像增强这些放在 CPU 端执行。工具结果经过 27b 模型摘要处理后，再交给模型继续决策。<br>具体的外部服务选型如下：<br>

| 工具能力 | 本次使用 | 额度和费用 |
| --- | --- | --- |
| 文字搜索 | DeepSeek Search | 成功且结果非空的请求，5元／千次 |
| 网页抓取 | DeepSeek Fetch | 成功且结果非空的请求，5元／千次，和搜索分别计次 |
| 以图搜图 | 豆包 Global visual | 每账号每月500次共享免费调用 |
| OCR／版面解析 | PaddleOCR-VL-1.6 | 官方 API 提供免费额度，按账号实际配额使用 |
| 裁剪、锐化、透视校正、超分辨率 | CPU 图像处理，超分使用 EDSR | 本地执行 |

<br>三、SFT 冷启动<br>数据直接用了 OpenSearch-VL 公开的 SFT 轨迹。官方提供了 36K 条轨迹数据。<br>我从中选了 2,048 条，主要考虑任务分布、工具覆盖和交互轮次，同时检查图片是否有效、轨迹能不能正常结束、有没有超过长度限制，以及和测试集是否存在重叠。<br>2048 条里大概 60% 是检索类任务，30% 涉及裁剪或 OCR，还有 10% 涉及图像增强。<br>SFT 用的是多轮完整轨迹，图片、用户问题和工具返回作为上下文，只对 Assistant 生成的内容计算 Loss。<br>SFT 训练参数如下：

| 参数 | 配置 |
| --- | --- |
| 基础模型 | Qwen3.5-4B |
| 微调方式 | LoRA |
| LoRA rank | 32 |
| 训练数据 | 2,048 条多轮轨迹 |
| 学习率 | 2.00E-05 |
| Batch size | 4 |
| Epoch | 1 |
| 参数更新次数 | 512 |
| 全程耗时 | 54 分 19 秒 |

<br>用真实日志生成的曲线如下。左侧是每批 Loss 和 32 步加权均值，右侧是同一个训练样本在不同 checkpoint 上的 NLL。固定训练样本上的 NLL 从 0.5676 降到了 0.4154，至少说明模型确实在学习这份教材。至于实际 Agent 能力有没有提升，还得跑评测。<br>

<br>四、RL<br>SFT 跑完之后，我先用当前模型对候选任务做了一轮 Probe Rollout。每道题采样 4 次，检查任务完成情况、Reward 分布和工具调用，最后整理出 100 道训练题和 16 道开发验证题。<br>训练题里，50 道四次全对，31 道有对有错，19 道四次全错。这次保留了不同难度的任务。答案相同的轨迹，在搜索质量和格式上仍可能有差异；如果同组的总 Reward 完全相同，就没有组内相对优势信号。<br>Reward 设计参考论文：<br>`reward = format × (0.8 × accuracy + 0.2 × query_quality)`<br>其中，accuracy 判断答案是否正确，query_quality 评价搜索质量，format 检查轨迹格式。<br>算法采用论文的 **Multi-Turn Search Fatal-Aware** 训练思路。多轮搜索中，模型可能连续调用错误的工具参数，之后一直在无效交互里打转。如果直接把整条失败轨迹一起惩罚，前面有效的搜索和观察也会受到影响。<br>

![](https://pica.zhimg.com/v2-a16a4515d92594b7c337ad1de53e0b9c_r.jpg)
*图4：多轮搜索致命错误感知的 RL 训练流程*

<br>一次搜索任务可能经过好几轮交互：模型先生成搜索词，搜索服务返回网页内容，模型读完以后再裁剪图片、继续检索，最后回答。整条上下文里混着问题、图片、模型输出和工具结果，计算训练损失时需要区分它们。<br>我们的实现把每轮生成拆成一个训练单元。输入保留这一轮之前的完整图文上下文，只对当前轮模型实际生成的 token 计算 PPO 损失。模型生成的思考、工具调用参数和最终答案都参与训练；用户问题、工具返回、图片和程序补入的分隔符作为上下文。<br>

| 一条轨迹中的内容 | 是否直接计算策略损失 |
| --- | --- |
| 用户问题、原始图片 | 否 |
| Assistant 的思考和工具调用 | 是 |
| 搜索结果、OCR文字、工具返回图片 | 否 |
| Assistant 的最终回答 | 是 |
| Fatal-Aware 判定的错误后缀 | 屏蔽 |

<br>比如模型生成了一次错误的搜索调用，搜索服务随后返回错误信息。训练需要调整的是模型生成这个调用的概率；错误信息仍然留在上下文中，供模型判断下一步。<br>采样时，我们直接保存服务返回的 token ID 和 logprob。下一轮在原有 token 后追加工具结果，避免把之前的回答重新编码后改变序列。更新前，再用尚未更新的 Actor 重算这些生成 token 的旧策略 logprob，作为 PPO 概率比的基准。<br>因此，372 条有效 Rollout 最后拆成了 1,598 个训练 Datum。一条多轮轨迹会产生多个训练单元，每个单元只负责其中一轮的生成内容，前面的 Assistant 输出不会因为再次出现在上下文里而被重复计算损失。<br>RL 训练的配置如下：

| 参数 | 配置 |
| --- | --- |
| 初始模型 | SFT 后的 Qwen3.5-4B |
| 微调方式 | LoRA，rank=32 |
| 训练题数 | 100道 |
| 开发验证集 | 16道 |
| 每题采样数 | 4条 Rollout |
| 每批任务数 | 4道 |
| 学习率 | 1.00E-06 |
| 上下文长度 | 32k |
| 采样 temperature | 0.7 |
| 最大交互轮数 | 50轮 |
| 训练轮数 | 1轮 |
| 参数更新次数 | 25次 |

<br>五、结果怎么样？<br>这次我从论文覆盖的七类公开 Benchmark 中选了 99 道题，包含 SimpleVQA、InfoSeek、VDR、FVQA、MMSearch、LiveVQA 和 BrowseComp-VL。<br>Base、SFT、RL 都在同一批题上评测，使用相同的生成设置和 Judge 提示词。每题只采样一次，temperature=0，最多 50 轮，主上下文窗口 64k。<br>Judge 使用 GLM-5.3-Flash，根据回答与参考答案的匹配情况判分。<br>结果如下：

| 同一批 99 道题 | Base | SFT | RL |
| --- | --- | --- | --- |
| 答对题数 | 53 | 50 | 49 |
| 正常结束并作答 | 82 | 97 | 97 |
| 工具调用次数 | 693 | 376 | 380 |
| 输出 Token | 430,635 | 98,033 | 98,766 |

![](https://pic2.zhimg.com/v2-32901dc37c33a13b41650c9d05151c49_r.jpg)
*图 5：Base、SFT、RL 在 99 道 benchmark 题上的评测结果*

<br>这个结果我觉得还挺有意思的。<br>先看 SFT，正常结束并作答的任务从 82 道增加到 97 道，工具调用减少了 45.7%，主模型输出 Token 减少了 77.2%。<br>Base 有些任务会反复搜索、一直思考，到最后也没有给出有效答案。SFT 之后这种现象少了很多，模型更容易把流程正常走完。<br>**但准确率从 53/99 降到了 50/99。**<br>逐题对比，有 8 道题从错变对，同时有 11 道从对变错。<br>比如有道题让模型比较四张图片的对比度，Base 选对了第 1 张，SFT 却选成了第 4 张，RL 之后还是第 4 张。<br>也就是说，模型确实学会了更简洁地使用工具、更及时地结束任务，但视觉判断能力并没有同步提升。<br>再看 RL，准确率又从 50/99 变成了 49/99，工具调用和 Token 消耗基本没什么变化。<br>不过格式方面有一点改善，平均步骤格式合规率从 75.8% 提高到了 80.2%，但参数错误次数也从 11 次增加到了 15 次。<br>我又看了留出的 16 道开发验证题，每题采样 4 次，共 64 条回答。<br>这一组 SFT 答对 38/64，RL 是 36/64。平均格式奖励从 0.541 涨到了 0.669，可比较的 63 条回答中，平均组合 Reward 从 0.353 涨到了 0.419。<br>**这就出现了一个很典型的问题：Reward 涨了，准确率却没涨。**<br>从目前的结果看，模型可能更多地学会了满足格式要求，答案本身没有因此变得更准确。<br>当然，只训练了 93 道有效任务、25 次更新，评测集太小了，这些现象还不足以证明 RL 对能力产生了稳定的负面影响。<br>六、具体轨迹对比<br>Agent 项目只看成功率还不够，具体还得分析轨迹，看看每一步做对了什么，做错了什么。<br>比如 eval-0101 这道题，要求识别图片里一辆马车由哪个组织提供马匹，以及背景砖楼里的商店叫什么。<br>SFT 没有正确识别供马组织，RL 则回答出了参考答案中的 Stevenson & Sons Funeral Homes 和 Star Printing & Office Supply。<br>看 RL 的轨迹，它先裁剪图片、进行超分处理，再使用图搜和文字检索寻找线索。整个过程能看到模型在尝试通过工具逐步确认答案。

![](https://pic4.zhimg.com/v2-9b675b750ae3cb7f38193a0d7d0c6cbd_r.jpg)
*图 6：eval-0101 题目 SFT 与 RL 的轨迹对比*

<br>但也有反例。<br>另一道关于 Titans 论文的题，SFT 原本已经回答正确了，RL 却反复检索了整整 50 轮，最后连有效答案都没给出来。<br>后面如果要继续做，至少得增加评测题量、多次采样，最好再对这些评分有争议的题目做人工核验。<br>七、花了多少钱？这次有什么感受？<br>说一下整个实验下来的花费吧，一共 416.13，这个任务还是比较烧钱的，因为需要有两个模型部署推理，需要一个 27b 的模型做网页的摘要。<br>

<br>这次用 PyTRIO，我比较喜欢的就是可以直接用 Python 和远程训练接口开始实验，不需要为了一个 4B 小模型自己准备一整套 GPU 训练服务。<br>配合官方 Skill，Agent 也能帮忙处理不少繁琐的工程工作，比如适配 SDK、修改脚本、检查日志和整理结果。当然，数据和训练逻辑还是得自己检查，尤其是多模态轨迹的 Mask、Reward 和评测设置，AI 写出来也不代表就一定正确。<br>如果是刚开始接触 Agentic RL，又没有本地训练显卡的同学，我感觉这种方式挺适合拿来做第一次小规模实验。可以先找一个数据和工具环境相对完整的项目，缩小训练规模，真正把 SFT、Rollout、Reward 和评测都跑一遍，再考虑扩大实验。
