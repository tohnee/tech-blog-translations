Rubrics RM本身是一个specific的LLM as Judge。

- 在使用上，Rubrics基本上是 query dependent，**对于每个问题的话我们会有一个 checklist，注意一般不是比较high level的rubrics，rubrics一般都会比较具体到特定问题**，然后 LLM as judge 的话会在 given 一个 prompt、given checklist 对一个 response 逐一的去 检查checklist，然后去做一个打分，hit or not，简单的用法就是多个binary结果的组合，这个是它的一个基本使用方法。
- 为啥要用Rubrics RM？一般给分的方向稳定，对RLHF这种长程的优化的direction是更友好的
- 设计RubricRM的一般经验，数量上看任务分布，简单的任务一般就10条以内，难的任务可能会到几十条，并且绝大多数rubrics会遵循原子化、具体化、**客观rubrics占比为主**的设计方式。RubricsRM一般会选择IF能力比较强的model作为judge。**Rubric正向为主、扣分占一部分、严重违背置0。**所以check rubrics的质量的一个方面也会考虑fix policy和judge，看一下一样的内容多次judge的方差大小，一般客观rubrics的judge的方差会小一些。

Rubric RM的hacking也比较有意思，不过和Policy Model Size和能力都有关系，下面是摘选自AdvancedIF的一个描述。忽然就想起来很久之前在RLVR那边踩过的一个坑，就是math 的verifier直接把整个response的\boxed都提取出来，只要有一个hit了就给分，这样子带来的问题就是模型会疯狂枚举答案试图去cover label🤣。这边的话，也可能模型会疯狂输出各种东西试图更好的cover rubrics。

参考代码：

```python3
import torch

def opd_loss(
    logits_student: torch.Tensor, # (B, L, V) 
    logits_teacher: torch.Tensor, # (B, L, V)
    mask: torch.Tensor = None, # (B, L)
):
    # B, L, V = logits_student.shape
    # loss = -\mean_{B,L} \sum_{V} p_{i,t,v} (log p_{i,t,v}-logpT_{i,t,v})
    prob_student = torch.softmax(logits_student, dim=-1)
    prob_teacher = torch.softmax(logits_teacher, dim=-1)
    log_prob_student = torch.log(prob_student)
    log_prob_teacher = torch.log(prob_teacher) 

    token_kl = torch.sum(prob_student * (log_prob_student - log_prob_teacher.detach()), dim=-1)

    if mask:
        return token_kl.mean() 

    mask = mask.to(token_kl.dtype)

    # 不能直接 mean，否则 padding token 也会进入分母
    return (token_kl * mask).sum() / mask.sum().clamp_min(1.0)

if __name__ == '__main__':
    B,L,V = 2, 15, 50
    ls = torch.randn(B, L, V, requires_grad=True)
    lt = torch.randn(B, L, V)

    loss = opd_loss(ls, lt)

    print(loss)

```

OPD 可以参考 **On-Policy Delta Distillation（OPD²）**。这篇论文的核心思想是：相比直接让 Student 模仿 post-trained Teacher 的完整输出分布，不如进一步引入 Teacher 在 post-training 之前的 Base Model，用二者的概率差异提取 post-training 真正带来的能力增量。

对于 Student 在状态 $s_t=(x,y_{<t})$ 下采样出的 token $y_t$，OPD² 定义 Delta reward：

$$ R_t^{\Delta} = \log \pi_T(y_t\mid s_t) - \log \pi_{T_{\text{base}}}(y_t\mid s_t). $$

如果 Teacher 完成 post-training 后，相比 Base Model 更“喜欢”这个 token，即

$$ \pi_T(y_t\mid s_t) > \pi_{T_{\text{base}}}(y_t\mid s_t), $$

那么 $R_t^\Delta>0$，Student 会提高该 token 的生成概率；反之则会抑制该 token。直观地说，这个 Delta signal 试图过滤掉 Teacher 在预训练阶段就已经具备的语言建模偏好，只蒸馏 post-training 所产生的行为变化，例如更可靠的推理步骤、逻辑连接和答案组织方式。

论文并没有直接使用 $R_t^\Delta$，而是先进行中心化：

$$ A_t^\Delta = R_t^\Delta - \mathbb{E}_{a\sim\pi_\theta(\cdot\mid s_t)} \left[R^\Delta(a,s_t)\right]. $$

因此，真正决定更新方向的不是某个 token 的绝对 Delta reward，而是它相对于 Student 当前策略平均水平的优势。论文还使用普通 OPD 的 teacher-student advantage 作为门控：只有 Delta signal 与普通 OPD signal 方向一致时才更新，

$$ A_t^{D^2} = \begin{cases} A_t^\Delta, & A_t^\Delta A_t^{\mathrm{OPD}}>0,\\ 0, & \text{otherwise}. \end{cases} $$

这一步很重要，因为单独最大化 Delta reward 会不断把概率推向 Delta 最大的 token，而不保证 Student 最终收敛到 Teacher。通过中心化和方向一致性门控，OPD² 在突出 post-training 能力增量的同时，避免 Student 被过度优化到偏离 Teacher 的位置。

以及MOPD上工业界模型合版比如coding有些时候会做伪多轮的off-policy的Distill，先把Teacher的轨迹在每一个token和词表上的logprob存储下来做细粒度，之后做更细粒度的SFT【模型合版每次时间都很紧张🤣，再加之有些domain做OPD很容易训崩】。
