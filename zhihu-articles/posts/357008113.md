## 1. 实际机器学习研发流程中复杂性

和一般的研发流程比较起来，机器学习的模型研发流程算是一个很特殊的物种。

它没有办法仅仅由代码逻辑定义。训练样本集，标注样本方法，数据集处理方式相关，训练时的超参数和停止条件等等，和它都有关联。

为了管理软件的生命周期，促进研发团队之间的高效协同，各类**DevOps**工具已经如雨后春笋一般冒了出来。而对于机器学习算法从业者来说，虽然也出现了类似的**MLOps**的概念，但相关的生态和工具链还远没有达到成熟的程度。

维基百科中关于MLOps的定义：

> MLOps是ModelOps的子集，是数据科学家和操作专业人员之间进行协作和交流的一种做法，可帮助管理生产机器学习生命周期。与DevOps或DataOps方法相似，MLOps旨在提高自动化程度并提高生产ML的质量，同时还关注业务和法规要求。

![](https://pica.zhimg.com/v2-ab01ce380c68641ee08c162833926824_r.jpg)
*来自nvidia blogs*

由于算法模型的生产和应用场景千差万别，很多开源的平台很难被推广应用。据小范围不完全统计，很多大厂都在这方面造了自己的轮子，但是仍然很难满足工程师的需求，经常听到抱怨的声音。

而小厂则很容易在这方面疏于管理。于是乎，在经历了多轮业务洗礼之后，往往会出现满目疮痍的景象：

- 线上某个神奇的支撑大量业务的模型不慎被删，但负责的算法工程师已经离职
- 线下没有保存模型版本库，线上用的哪个版本的模型已经无从知晓
- 接手的工程师好不容易从代码库中翻出模型的训练代码，但是找不到训练数据集
- 标注的小伙伴费了半天劲，才从聊天记录，发掘出标注样本位置
- 但是我们的训练超参是什么，数据的切分标准是怎样的，数据是如何评估上线的，和这个模型兼容的推理代码是怎样的，新模型的性能如何……
- 这位新接手的算法工程师，看起来手忙脚乱、满头大汗。Leader一定在担心，这个人我还能不能留得住……

## 2. 来自算法工程师的朴素需求

在调研诸多可用的轮子之前，我习惯先把需求和目标写下来。从一个算法工程师视角，我觉得最朴素的需求是这样子的：

| 需求 | 说明 |
| --- | --- |
| 代码版本库 | 比如git，能够管理训练、推理、测试评估、数据加工等相关代码 |
| 实验管理 | 记录每次实验的超参数、指标，最好能有可视化的界面进行比较选择 |
| 模型版本库 | 记录可发布的模型版本快照。版本只增不减，采用md5等手段保证数据文件的完整性。最好能有冗余备份提供安全性。 |
| 数据集版本库 | 与模型对应的数据集也能够版本化管理起来，拆分为训练、验证和测试集等。 |
| 模型元数据库 | 用于把实验数据、数据集、模型文件关联起来，记录各种描述性的元数据。我觉得如下信息是比较重要的：日期时间、模型名称、模型用途、版本号、模型文件名列表、代码库依赖、主要改进说明、训练数据流程指标、测试数据流程指标等。 |
| 模型部署 | 具备方便获取不同版本模型的能力。具备方便部署到不同环境的能力。 |
| 模型服务 | 如果能够集成主流平台的模型服务能力更佳 |

带着这样的需求，花了一点时间，快速调研了三款出镜率较高的MLOps平台，分别是DVC、MLflow和Valohai。

## 3. DVC，Data Version Control

[Data Version Control · DVC](https://dvc.org/)

开发者为iterative.ai，成立于2017年。开源免费，有企业服务。

从数据版本化管理概念切入，提供ML全方位的支持。DVC设计的主要模块和功能如下：

| 模块 | 功能 |
| --- | --- |
| Data Versioning | 提供大数据文件、数据集和机器学习模型的版本管理能力。数据会被单独存储，类似git for data。 |
| Data Access | 提供了项目之外访问DVC管理的数据工件的能力，比如下载某个版本的模型文件并部署。 |
| Data Pipelines | 定义了模型和其它数据工件加工生成的流水线，类似传统意义上的Makefile。 |
| Metrics, parameters, and plots | 流水线上各环节记录的信息 |
| Experiments | 一个可视化的浏览比较工具 |

![](https://pic4.zhimg.com/v2-1c26e496b84e241f2911fd71f82e84f1_1440w.png)
*DVC对接本地存储和云存储的能力*

![](https://picx.zhimg.com/v2-4a4b24784c7f34193e703dcfff79e2b5_1440w.png)
*DVC实验对比的控制台界面*

初印象：

1. 与git类系统深度整合，命令也非常类似，看起来学习上手成本低
2. 对于大数据文件存储的支持方案丰富，从云存储到私有的大数据存储，应有尽有，包括Google Drive, Amazon S3, Azure Blob Storage, Google Cloud Storage, Aliyun OSS, SSH, HDFS, and HTTP等
3. 多种编程语言和深度学习框架支持，如Python, R, Julia, Scala Spark, custom binary, Notebooks, flatfiles/TensorFlow, PyTorch

## 4. mlflow

[https://mlflow.org/](https://mlflow.org/)

MLflow是由知名大数据公司Databrick推出的开源机器学习平台，也是提供从数据准备到模型训练到最终部署的全流程解决方案。拥有较成熟的社区和较大的客户群。

MLflow的核心设计理念包括如下4个模块：

| 模块 | 功能 |
| --- | --- |
| Tracking | 记录实验参数和比较结果的API，并提供了可视化的UI界面 |
| Projects | 提供了一种标准目录格式，包括一个描述文件，把机器学习代码打包成可复用，可重现，可分享的项目 |
| Models | 提供通用的模型文件管理和部署能力，支持多种框架和多种平台的部署 |
| Model Registry | 提供模型全生命周期管理和协作中心，包括版本管理，环境迁移等等 |

![](https://pic3.zhimg.com/v2-82a0d16629137f5d3eab95086cddc334_1440w.png)
*实验参数结果对比的web界面*

初印象：

1. mlflow的设计理念是减少对现有系统的侵入，承认现实世界的复杂性，自动对不同的库进行适配，因此改动相对较少
2. 它提供REST风格的接口以及CLI命令行，因此理论上可以和任何编程语言或者机器学习库对接
3. 可以将不同流派的模型保存成一种通用的格式，并基于此提供了模型存储和服务能力
4. 可以看出，它从Databricks带来的大数据和分布式的基因

## 5. Valohai

[Train, Evaluate, Deploy, Repeat.](http://valohai.com)

公司总部位于芬兰，提供商业化的MLOps解决方案，提供PRO/Enterprise两套可定制的解决方案。Train, Evaluate, Deploy, Repeat. Valohai is the only **MLOps platform** that automates everything from data extraction to model deployment.

Valohai的核心概念是把机器学习流程抽象成为pipelines。它有一句口号叫做，铁打的pipelines，流水的models。

初印象：

1. 产品整体看起来成熟度较高，文档也相对丰富。
2. 它宣称是可以提供预测类模型全生命周期的管理，包括：数据转换、数据增强、数据匿名化、数据合成、数据管理、迭代开发、训练、超参优化、模型管理、模型分析、模型可解释性、仿真、批量推理、模型服务、在线实验。是个大全家桶。
3. 核心概念是pipeline，它定义了整个机器学习流程。而pipeline的核心配置文件叫valohai.yaml，它是驱动项目的核心，定义了流水线的每个步骤和衔接方式。

## 6. 不是结语

整体上来看，三个MLOps平台产品的成熟度比我想象得要好。虽然不同平台定义了自己的模块概念，但是**基本上都可以完成调研之前所列出的需求**。很多概念非常相似，大同小异。

当然，优秀的MLOps平台还有很多。即便是这三款也只是蜻蜓点水看了一下主要文档，真正用起来可能还会有一些坑和更多的细节感受。留待后续补课吧。
