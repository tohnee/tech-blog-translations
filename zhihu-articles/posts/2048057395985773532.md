### 一、什么是上下文（Context）

很多人将 **上下文（Context）** 理解为用户输入给大语言模型（LLM）的提示词（Prompt），但实际上 **提示词只是上下文的一部分** 。

### 1.1 正式定义

> **上下文（Context）是指模型在一次推理（Inference）时能够看到的全部 Token 集合。**

模型只能基于这些 Token 进行预测，因此模型所能“知道”的信息，全部来源于上下文。

**什么是 Token？** 
 Token 是文本的最小处理单元。例如“你好，世界”可能被切分为 [“你”,“好”,“，”,“世界”] 四个 Token。模型一次能处理的最大 Token 数称为 **上下文窗口** 。

### 1.2 上下文的组成

在实际应用中，一个 Agent 的上下文通常由四部分组成：

```text
Context
├── System Prompt（系统提示词）
├── User Prompt（用户输入）
├── Memory（记忆）
└── Tool Results（工具调用结果）
```

**示例** ： 
 假设系统提示词为“你是一名专业Java开发工程师”，记忆模块记录了“用户擅长C++，最近正在学习Spring Boot”，用户输入“帮我写一个REST API”，同时工具调用返回了数据库 Schema `User(id,name,age,email)` 。

真正送入模型推理的内容实际上是：

```text
System Prompt
+
Memory
+
Tool Result
+
User Prompt
```

而不是只有最后一句用户输入。因此，对于 Agent 来说， **上下文远远大于 Prompt** ，它代表了模型当前拥有的全部知识。

---

### 二、为什么上下文如此重要？

LLM 本质上采用 Transformer 架构，其核心是 **Self-Attention（自注意力机制）** 。理论上，每一个 Token 都可以关注上下文中的所有 Token。但是随着上下文长度不断增加，会出现几个问题。

### 2.1 注意力分散（Attention Dilution）

**直观理解** ： 
 假设上下文只有 100 个 Token，模型可以很容易找到“用户喜欢 Python”这句话。但如果上下文变成 50000 个 Token，模型需要在大海捞针般的信息中定位这一句话，注意力容易分散。

**结论** ：虽然模型理论支持长上下文，但实际利用效率会下降。

### 2.2 上下文腐蚀（Context Rot）

近年来大量研究发现： **当上下文长度持续增长时，模型准确回忆早期信息的能力会下降** 。

**示例** ：

```text
开头：密码是 apple123
......（中间5万Token）
...... 
最后：密码是什么？
```

模型可能回答错误。这种现象被称为 **Context Rot** ，即信息虽然仍存在于上下文中，但模型已经无法稳定利用。

因此：

> **更多的上下文 ≠ 更好的效果。** 
>  大量低价值信息甚至可能降低模型性能。

### 2.3 计算成本增加

Transformer 的 Self-Attention 计算复杂度约为 **O(n²)** ，其中 n 为 Token 数量。如果 Token 数量翻倍（10000 → 20000），计算量约增加 **四倍** 。因此：

- 推理速度下降
- 成本增加
- 延迟变高

对于商业 Agent 来说，上下文长度直接决定推理成本。

### 三、什么是上下文工程（Context Engineering）

**上下文工程** 是近年来 Agent 领域提出的重要概念。它关注的问题是：

> **如何在有限的上下文窗口内，组织最有价值的信息，使模型获得最稳定、最优秀的推理效果。**

换句话说，上下文工程研究的是：

- 什么信息应该进入上下文？
- 什么信息应该被删除？
- 什么信息应该压缩？
- 什么信息应该延迟加载？
- 如何组织上下文结构，使模型更容易理解？

它不仅包括 Prompt，还包括：

- System Prompt
- Memory
- Tool Description
- Tool Result
- Retrieval（RAG）
- Planning
- Scratchpad（思维草稿）
- Environment State（环境状态）

因此：

> **上下文工程可以看作 Prompt Engineering 的升级版。**

### 3.1 与提示词工程（Prompt Engineering）的区别

| Prompt Engineering | Context Engineering |
| --- | --- |
| 关注提示词如何编写 | 关注整个上下文如何组织 |
| 重点优化用户输入 | 优化整个推理环境 |
| 面向单次调用 | 面向长期 Agent |
| 内容主要是 Prompt | 包括 Prompt、Memory、Tool、RAG 等 |
| 偏技巧 | 偏系统工程 |

可以认为：

```text
Context Engineering
    └── Prompt Engineering
```

提示词工程只是上下文工程中的一个组成部分。

### 四、如何实现上下文工程

### 核心目标

上下文工程的核心目标可以总结为一句话：

> **在有限的上下文窗口内，实现尽可能高的信息密度（Information Density）。**

所谓信息密度，就是：

- 保留更多有效信息；
- 删除冗余信息；
- 减少无关噪声；
- 让模型能够快速定位关键内容。

实践中，用户输入和长期记忆通常无法随意修改，因此优化重点主要集中在：

- System Prompt
- Tool
- Example
- Retrieval（检索）
- Memory Injection（记忆注入）

下面分别介绍。

### 4.1 系统提示词（System Prompt）

系统提示词决定了 Agent 的身份、目标和行为边界。

### （1）职责单一

不要让一个 Prompt 同时承担多个复杂职责。

**反例** ：

```text
你是程序员，同时也是律师，同时也是心理咨询师，同时还是数学老师。
```

模型容易产生角色混淆。

**正例** ：

```text
你是一名后端开发助手。
职责：
- 编写代码
- 分析Bug
- 输出Markdown
```

角色越聚焦，模型表现通常越稳定。

### （2）语义清晰

避免模糊描述。

**反例** ：

```text
尽量回答好一点。
```

**正例** ：

```text
优先保证正确性，其次保证代码可维护性，最后考虑性能优化。
```

明确的约束比模糊要求效果更好。

### （3）避免复杂 if-else

**反例** ：

```text
如果A输出1，
否则如果B输出2，
否则如果C输出3，
否则如果D输出4……
```

当规则越来越多时：难维护、模型容易遗漏条件、新旧规则可能冲突。

**正例** ：采用声明式描述

```text
原则：
1. 优先安全。
2. 优先准确。
3. 信息不足时主动提问。
```

这种方式更符合 LLM 的推理特点。

### （4）结构化组织 Prompt

推荐采用 Markdown 或 XML 分区。

**示例** ：

```text
# Role
你是一名数据库专家。

# Goal
分析SQL性能。

# Constraint
不能修改业务逻辑。

# Output
Markdown格式输出。
```

结构化 Prompt：更容易维护、更容易扩展、模型理解效果通常更好。

### 4.2 工具（Tool）

Tool 是 Agent 与现实世界交互的重要桥梁。模型本身无法访问数据库、网络或本地文件，必须借助工具。

```text
LLM → Search Tool
LLM → Python Tool
LLM → Database Tool
```

工具设计直接影响 Agent 的能力上限。

### （1）工具职责单一

**反例** ：

```text
search_and_download_and_parse_and_summary()
```

**正例** ：拆分为

```text
search()
download()
parse()
summary()
```

粒度更小：更容易组合、更容易调试、更方便模型规划调用流程。

### （2）工具描述准确

工具描述实际上也是 Prompt。模型主要依赖工具描述来决定是否调用工具。

**反例** ：

```text
搜索一下。
```

**正例** ：

```text
search(query) : 根据关键词搜索互联网信息，返回最相关网页列表。
```

效果更稳定。

### （3）工具返回结果应精简

**反例** ：返回 HTML 源码 300KB。

**正例** ：返回结构化摘要

```text
标题：
正文摘要：
发布时间：
来源：
```

工具结果越干净，上下文利用率越高。

### 4.3 示例（Few-shot Example）

Few-shot Learning 是提升模型稳定性的经典方法。相比大量规则， **优秀的示例往往比复杂规则更有效** 。

**示例** ：

```text
输入：你好
输出：您好，请问有什么可以帮助您？

输入：写代码
输出：先分析需求，再给代码。
```

模型会自动学习这种模式。

### 示例设计原则

不要罗列所有边界条件（情况1…情况500），这样上下文会迅速膨胀。

推荐选择：

- 最典型
- 最容易混淆
- 覆盖面最广

的少量示例。用最少的示例表达期望行为。

### 五、上下文策略

### 5.1 及时上下文（Just-In-Time Context，JIT Context）

传统方式是一次性将所有内容塞入上下文，导致两个主要问题：

- Token 浪费；
- 大量无关信息干扰推理。

现代 Agent 越来越采用 **Just-In-Time Context** ，即 **上下文按需加载** 。

**示例** ：Agent 收到任务“修复项目登录Bug”。不是立即加载整个项目，而是：

```text
目录
  ↓
login/
  ↓
login_service.py
  ↓
authenticate()
  ↓
需要时继续展开
```

Agent 逐层探索，自主决定下一步需要哪些信息。

### 渐进式披露（Progressive Disclosure）

JIT Context 的重要思想是 **Progressive Disclosure（渐进式披露）** 。每一步交互都会生成新的上下文，并指导下一步决策。例如：

```text
项目目录
  ↓
发现 auth/
  ↓
发现 login.cpp
  ↓
发现 Login()
  ↓
发现 TokenManager
```

Agent 像人阅读代码一样逐层深入，而不是一次加载整个仓库。这样可以始终保持当前工作记忆中只有最必要的信息。

### 5.2 混合策略（Hybrid Context）

实际工程中，很少完全依赖 JIT，通常采用 **混合策略** ：

```text
高价值信息        → 直接加载
普通信息          → 引用（如路径）
需要时再动态展开
```

**示例** ：

- System Prompt → 直接加载
- 当前任务 → 直接加载
- 最近记忆 → 直接加载
- 数据库 Schema → 直接加载
- 整个代码仓库 → 不加载，只引用 README 和文件路径，需要时再读取

这是目前 Cursor、Claude Code、OpenCode 等代码 Agent 普遍采用的策略。

### 六、长时程任务中的上下文工程

对于需要几十轮甚至数百轮循环的 Agent，单纯依赖上下文窗口是不够的。原因：

- 上下文长度有限；
- Token 成本越来越高；
- 模型容易遗忘早期目标；
- 历史对话不断污染当前推理。

因此，需要工程化手段维护长期一致性。目前主流方案包括： **压缩整合、结构化笔记、子代理框架** 。

### 6.1 压缩整合（Compression）

压缩并不是简单摘要，而是在 **保留关键信息的前提下删除冗余内容** 。

**示例** ：原始对话

```text
用户：我要开发招聘系统。
Agent：好的。
用户：支持Excel导出。
Agent：好的。
用户：支持定时抓取。
Agent：好的。
……
```

经过压缩：

```text
当前需求：
- 招聘抓取
- 定时调度
- Excel导出
- 支持规则扩展
```

原来数千 Token 可以压缩到几十 Token。

**优秀的压缩应保留** ：

- 已完成任务
- 未完成任务
- 当前目标
- 关键约束
- 已确定决策

**应删除** ：

- 客套话
- 重复讨论
- 已失效内容
- 无关推理过程

压缩通常会在 Agent 循环过程中定期执行，以防上下文无限增长。

### 6.2 结构化笔记（Structured Notes）

相比自然语言摘要，现代 Agent 更倾向维护 **结构化状态** 。

**示例** （YAML 格式）：

```text
Task:
  - 完成数据库设计
  - 等待接口开发

Decision:
  - 使用PostgreSQL
  - ORM选择SQLAlchemy

Risk:
  - 登录模块待验证

Todo:
  - 编写用户管理接口
```

**优点** ：

- 信息清晰
- 易于增删改
- 方便模型快速检索
- 可长期持久化存储

很多 Agent 框架都会维护类似的 **Scratchpad（工作笔记）** 或 **State（状态）** ，作为循环推理的重要依据。

### 6.3 子代理框架（Sub-Agent Framework）

当任务复杂度较高时，将所有工作交给一个 Agent 往往效果不佳。更合理的方法是：

> **拆分任务，由多个专业 Agent 协同完成。**

**示例** ：开发一个完整的软件项目

```text
主Agent（Project Manager）
│
├── Planner Agent      → 制定计划
├── Code Agent         → 编写代码
├── Test Agent         → 生成测试
├── Review Agent       → 代码审查
└── Documentation Agent → 编写文档
```

每个子 Agent 只维护自身相关的上下文，不需要加载整个项目的全部信息。

**优势** ：

- 单个 Agent 的上下文更短，推理质量更高
- 不同任务之间相互隔离，减少干扰
- 可以并行执行，提高整体效率
- 更容易扩展和维护

当前许多先进的多 Agent 系统都会采用这种架构，通过上下文隔离和任务分解来突破单个模型上下文窗口的限制。
