**前言**

第一篇我们讲了 vLLM 的整体架构，提到了 PagedAttention 是其核心特性之一。本文深入解析 PagedAttention 的设计原理、解决的问题，以及 vLLM 中的实现细节。

**阅读建议**：本文涉及较多 CUDA 编程概念，但不熟悉 GPU kernel 的读者也可以从概念层面理解 PagedAttention 的核心思想。

---

### 1. 背景：传统 KV Cache 的内存困境

### 1.1 LLM 推理的两个阶段

LLM 推理分为两个阶段：

- **Prefill 阶段**：处理输入 prompt，生成第一个 token，同时将 KV Cache 写入显存
- **Decode 阶段**：逐 token 生成，每次只处理一个新 token，需要读取历史 KV Cache

![](https://picx.zhimg.com/v2-81e753c7d0be01189826016cd9d035ff_r.jpg)

### 1.2 KV Cache 的内存问题

在 Decode 阶段，每次推理都需要读取**全部历史** KV Cache。假设：

- 模型：LLaMA 70B（80 层，KV head 数 8，head 维度 128）
- 上下文长度 4096
- 精度 FP16（2 字节/元素）

KV Cache 总大小约为：

```text
80 层 × 8 KV heads × 128 head_dim × 4096 tokens × 2 字节
  ≈ 6.4 GB
```

加上 activation、模型权重、中间计算结果，显存消耗轻松达到数十 GB。这已经超过了很多 GPU 的显存容量。更大的问题是：**显存碎片化**。

### 1.3 传统方案的缺陷

传统框架采用**连续内存分配**策略：

```text
# 伪代码：传统方式
max_seq_len = 4096
kv_cache = torch.zeros(max_seq_len, num_heads, head_size)  # 预先分配整块
```

问题：

1. **内部碎片**：实际生成长度往往远小于 max_seq_len，大部分显存浪费
2. **外部碎片**：不同请求长度不同，释放后难以复用
3. **无法动态扩展**：无法利用显存中零散的空闲块

这就像给每个人分配一套固定大小的房子——房子不是住满的，浪费严重，而且有的人需要 3 间、有的人需要 10 间，固定分配必然导致大量空置。

---

### 2. 核心思想：借鉴操作系统的分页管理

### 2.1 OS 虚拟内存的启示

操作系统在处理物理内存时，采用了**分页（Paging）**策略：

- 虚拟地址连续，但映射到物理内存的任意位置
- 按固定大小（通常 4KB）分页，按需分配
- 通过页表维护映射关系，灵活高效

vLLM 的 PagedAttention 借鉴了这一思想，将 KV Cache 也分块管理。

![](https://picx.zhimg.com/v2-912d0d01bb9d803fbe55966bfa7e6537_r.jpg)

### 2.2 PagedAttention 的核心设计

PagedAttention 将 KV Cache 按固定大小（通常 16 个 token 为一块）分块存储，通过一个**块表（Block Table）**维护逻辑序列到物理块的映射。

![](https://pic2.zhimg.com/v2-446479421f4ef6e41000646085f594a3_r.jpg)

逻辑上序列是连续的，但物理上块可以分散存储、按需分配。

### 3. PagedAttention 的实现细节

### 3.1 块表的结构

在 vLLM v1 中，`MultiGroupBlockTable` 是对外暴露的核心接口（来源：`vllm/v1/worker/block_table.py`）。

### 为什么有多个 BlockTable？

BlockTable 的数量由 **`kv_cache_groups`** 的长度决定——每个 KV cache group 对应一个 BlockTable。

而 `kv_cache_groups` 是按**注意力机制类型**划分的：

```text
For models with only one type of attention, there is only one group that
contains all layers.
For models with multiple types of attention, there will be multiple groups.
```

也就是说：

- **标准 Multi-Head Attention 层** → 1 个 group
- **Mamba 层**（状态空间模型）→ 单独 1 个 group
- **MLA 层**（DeepSeek 的低秩注意力）→ 单独 1 个 group

不同注意力机制的 KV Cache 数据布局完全不同（Mamba 是状态空间形式、MLA 是低秩压缩），必须分开管理，所以要各自独立的 BlockTable。

对于大多数 LLaMA 模型，只有 1 个 group（全部标准 Attention 层），所以只有 1 个 BlockTable。

### MultiGroupBlockTable 的三个配置参数

```text
class MultiGroupBlockTable:
    def __init__(
        self,
        max_num_reqs: int,
        max_model_len: int,
        max_num_batched_tokens: int,
        pin_memory: bool,
        device: torch.device,
        block_sizes: list[int],         # 每个 group 的 KV block 分配粒度
        kernel_block_sizes: list[int],  # 每个 group 的 kernel 计算粒度
        max_num_blocks: list[int] | None = None,
        cp_kv_cache_interleave_size: int = 1,
    ) -> None:
```

三个列表**按位置一一对应**，每组参数共同描述一个 KV cache group：

| 参数 | 含义 | 举例 |
| --- | --- | --- |
| block_sizes[i] | 第 i 个 group 的 KV block 分配粒度（每块存多少 token） | 32 → 每块存 32 个 token |
| kernel_block_sizes[i] | 第 i 个 group 的 kernel 计算粒度 | 16 → kernel 以 16 token 为单位计算 |
| max_num_blocks[i] | 第 i 个 group 每个请求最多能用的块数 | 由 max_model_len / block_size 决定，例如 max_model_len=4096, block_size=32 → max_num_blocks=128；多 group 时各 group 独立计算 |

**完整配置示例**：

```text
# 一个同时含标准 Attention 和 MLA 的模型：
block_sizes        = [32, 16]       # group0 每块 32 tokens, group1 每块 16 tokens
kernel_block_sizes = [16, 16]       # 两组 kernel 计算粒度都是 16
max_num_blocks     = [128, 256]     # group0 最多 128 块, group1 最多 256 块

# 普通 LLaMA（单一 Attention 类型）：
block_sizes        = [32]
kernel_block_sizes = [32]            # 与分配粒度相同，无 hybrid
max_num_blocks     = [128]
```

**为什么 `kernel_block_size` 可能不等于 `block_size`？**<br>当两者不等时启用 hybrid 模式：`blocks_per_kv_block = block_size / kernel_block_size`。例如分配粒度 32 tokens/KV block，kernel 计算粒度 16 tokens/block，则每个 KV block 物理上对应 2 个 kernel block。

**hybrid 模式下的物理寻址（多跳）**：

普通模式下：`block_id * block_size + offset` 即可一步定位物理地址。

hybrid 模式下需要多跳：

```text
KV block_id = block_table[req][i]           # 逻辑块映射到的 KV block 号
kernel_block_id = KV_block_id * blocks_per_kv_block + kernel_block_index
物理地址 = kernel_block_id * kernel_block_size + offset
```

也就是说，hybrid 模式下物理地址映射要多经过一层 kernel block 索引计算，BlockTable 内部通过 `map_to_kernel_blocks()` 方法完成这一转换，对外暴露的逻辑仍然是统一的。

### BlockTable 核心数据结构

```text
class BlockTable:
    def __init__(
        self,
        block_size: int,
        max_num_reqs: int,
        max_num_blocks_per_req: int,
        max_num_batched_tokens: int,
        pin_memory: bool,
        device: torch.device,
        kernel_block_size: int,
        cp_kv_cache_interleave_size: int,
    ):
        self.block_table: torch.Tensor    # [max_num_reqs, max_num_blocks_per_req]
        self.slot_mapping: torch.Tensor   # [max_num_batched_tokens]
        self.num_blocks_per_row           # [max_num_reqs]
        self.use_hybrid_blocks             # 是否启用混合块大小
```

**`block_table[req][i]`** = 请求 req 的第 i 个**逻辑块**指向的**物理块号**（请求本地逻辑编号，从 0 开始）：

```text
block_table[0] = [7, 3, 12, 0, 0, 0, 0, 0]   # 请求0的逻辑块0→物理块7，逻辑块1→物理块3，...
block_table[1] = [15, 6, 0, 0, 0, 0, 0, 0]    # 请求1的逻辑块0→物理块15，逻辑块1→物理块6，...
```

每个请求的**逻辑块号都是从 0 开始的**，是请求本地的，不和其他请求冲突。**物理块号才是全局唯一的**。

**`slot_mapping[t]`** = 当前 batch 内第 t 个 token 的**物理槽位号**（形状固定，内容每次调度重新计算）：

```text
假设 batch 里请求0（80 tokens）+ 请求1（32 tokens），共 112 个 token：

slot_mapping[0]   = 7 * 16 + 0  = 112   # 请求0的 token0 在物理槽 112
slot_mapping[15]  = 7 * 16 + 15 = 127   # 请求0的 token15 在物理槽 127
slot_mapping[16]  = 3 * 16 + 0  = 48    # 请求0的 token16 在物理槽 48
slot_mapping[79]  = 3 * 16 + 15 = 63    # 请求0的 token31 在物理槽 63
slot_mapping[80]  = 15 * 16 + 0 = 240   # 请求1的 token0 在物理槽 240
```

`slot_mapping` 的**下标 t 是 batch 内的 token 位置**（不是请求内的 token ID），**值是物理槽位号**，不是块号。

### block_table 和 slot_mapping 各司其职

| 变量 | 职责 | 谁用 |
| --- | --- | --- |
| block_table[req][i] | 请求↔物理块的所有权映射，负责分配和释放 | BlockPool 管理系统 |
| slot_mapping[t] | 当前 batch 内 token→槽位的临时寻址输入 | Attention Kernel |

**为什么两者缺一不可？**

`slot_mapping` 只告诉 kernel”这个 token 在槽 112”，但它不知道”槽 112 属于哪个物理块、属于哪个请求”。执行完后，**如果没有 block_table，根本不知道该把哪些物理块还回空闲队列**。

所以：

- `block_table` 负责**资源管理**（请求生命周期内稳定）
- `slot_mapping` 负责**kernel 寻址**（每次调度重新计算）

### 从物理块号到显存地址

KV Cache 在 GPU 上是一块预先分配好的连续显存：

```text
key_cache = torch.empty(
    [num_blocks, num_kv_heads, head_size // x, block_size, x],
    dtype=torch.float16, device="cuda"
)
```

物理块号 `b` 就是这块内存的**数组索引**，`key_cache[b]` 就是物理块 b 的全部数据。

kernel 计算绝对地址：

```text
base_ptr = key_cache.data_ptr()   # 块0的起始地址
slot = block_id * block_size + offset_in_block
address = base_ptr + slot * element_size  # FP16 → 2字节
```

所以 `block_table[req][i] = 7` 的含义是：**请求 req 的逻辑块 i，对应 key_cache 的第 7 个切片（块7）**。

### 3.2 KV Cache 的读写

写入 KV Cache 时，通过 `slot_mapping` 确定物理位置：

```text
# 来源：vllm/v1/attention/ops/paged_attn.py
@staticmethod
def write_to_paged_cache(
    key, value,
    key_cache, value_cache,
    slot_mapping,
    ...
):
    ops.reshape_and_cache(
        key, value,
        key_cache, value_cache,
        slot_mapping.flatten(),  # 物理槽位映射
        ...
    )
```

读取时，通过 `block_table` 查找物理块，再通过 `slot_mapping` 定位具体 token：

```text
# 来源：vllm/v1/attention/ops/chunked_prefill_paged_decode.py
# 其核心计算由 Triton 实现的 kernel_paged_attention_2d 完成
# Grid：(num_seqs, num_kv_heads)，BLOCK_SIZE 动态（16/32，非固定 128）
```

### 3.3 内存布局的优化

KV Cache 在显存中按块存储，每个块内 KV 分开：

```text
key_cache shape:  [num_blocks, num_kv_heads, head_size//x, block_size, x]
value_cache shape: [num_blocks, num_kv_heads, head_size, block_size]
```

这样做有两个好处：

1. **x 维度拆分**（key_cache）：配合向量化访存，一次读取 x 个元素，提升带宽利用率
2. **KV 分离**：Attention 计算时按需访问，不必同时读取完整的 K 和 V

### 4. BlockPool 与块分配（v1 架构）

### 4.1 BlockPool：全局块管理器

vLLM v1 引入了 `BlockPool`（来源：`vllm/v1/core/block_pool.py`）来统一管理所有 KV Cache 块：

```text
class BlockPool:
    def __init__(self, ...):
        self.free_block_queue: FreeKVCacheBlockQueue           # 空闲块队列（O(1) 分配/释放）
        self.cached_block_hash_to_block: BlockHashToBlockMap  # 哈希→块映射（用于前缀缓存）
        self.blocks: list[KVCacheBlock]                       # 所有块的列表
```

![](https://pic2.zhimg.com/v2-48f834ea4d6a0f6806c088cdd65f3169_r.jpg)

空闲块通过队列管理，分配时 O(1) 取用，释放时 O(1) 归还。

### 4.2 前缀缓存与引用计数

v1 架构支持**前缀缓存**：如果不同请求有相同前缀，它们的 KV Cache 块可以共享，只分配一次。通过 `BlockHashToBlockMap` 维护块哈希到物理块的映射。

引用计数机制确保块在被所有使用者释放前不会被回收：

```text
def touch(self, blocks: Sequence[KVCacheBlock]) -> None:
    """增加块的引用计数，标记该块正在被使用"""
    for block in blocks:
        block.ref_count += 1
```

当请求结束时，调用方减少引用计数，计数归零时块回到空闲队列。

### 5. PagedAttention Kernel 执行流程

### 5.1 Triton Kernel 执行流程

Attention 的核心计算在 Kernel 中完成。v1 的 decode attention 由 Triton 实现的 `kernel_paged_attention_2d` 驱动，通过 `_custom_ops` 桥接到 CUDA。

以 `kernel_paged_attention_2d` Triton kernel 为例，每个实例的执行步骤如下：

| 步骤 | 操作 | 说明 |
| --- | --- | --- |
| 1 | 查块表 | 通过 block_tables 找到当前 token 所在物理 KV block |
| 2 | 定位槽位 | 通过 slot_mapping 精确定位 block 内槽位 |
| 3 | 读取 Key | 分块读取 key_cache，计算 QK^T |
| 4 | Softmax | 两阶段在线 softmax（warp reduction → 归约） |
| 5 | 乘加 | 与 value 相乘并累加到 output |

### 5.2 分块 softmax 的实现

Attention 的 softmax 需要遍历所有 token 才能归一化，但分块后物理块分散在不同显存位置。vLLM 采用了**两阶段 softmax**：

```text
第一阶段（并行）：
- 每个 thread block 计算本地 max 和 exp sum
- warp 级别 reduction，得到整个序列的 max 和 sum

第二阶段（归约）：
- 用全局 max 和 sum 归一化所有 exp 值
- 与 value 相乘并累加
```

这保证了在分块存储的情况下，Attention 计算仍然是正确的。

### 6. v0 与 v1 架构对比

| 特性 | v0 | v1 |
| --- | --- | --- |
| KV Cache 管理 | BlockSpaceManager | BlockPool + MultiGroupBlockTable |
| 前缀缓存 | 支持 | 支持（引用计数机制增强） |
| Chunked Prefill | 不支持 | 支持 |
| Attention Kernel | CUDA C++ | Triton Kernel（via _custom_ops） |
| Block 分配 | 按需分配 | FreeKVCacheBlockQueue O(1) |
| Hybrid Block 大小 | 不支持 | 支持（kernel_block_size ≠ block_size） |

### 7. 性能收益

来自 PagedAttention 论文（SOSP 2023）的关键数据：

| 指标 | 传统方案 | PagedAttention | 提升 |
| --- | --- | --- | --- |
| 显存利用率 | ~20-30% | ~60-80% | 2-4x |
| 吞吐量（Same Latency） | 1x | 2.3x-4x | 2-4x |
| 支持序列数（16384 tokens） | 4 | 58 | 14.5x |

更重要的是，PagedAttention 使得**超长上下文**成为可能——在相同显存下，支持的并发序列数和最大长度都大幅提升。

---

### 8. 总结

PagedAttention 的核心贡献是**将操作系统内存管理的思想引入 LLM 推理**：

1. **分块存储**：KV Cache 不再连续分配，而是按固定大小分块，物理上分散存储
2. **块表映射**：通过逻辑→物理映射，attention kernel 仍然可以透明地”看到”完整的序列
3. **按需分配**：根据实际生成长度分配显存，避免预先分配的浪费
4. **碎片复用**：释放的块进入空闲队列，可立即被后续请求复用

这套设计在几乎没有额外计算开销的情况下，大幅提升了显存利用率和系统吞吐量。
