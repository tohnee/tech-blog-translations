如果我们做过 GPU kernel 开发，大概率见过这样的编译流程：写完 CUDA/Triton 代码，经过一系列 IR 变换，最后总要落到 LLVM IR，再由 NVPTX 后端生成 PTX，最后 ptxas 装配成 cubin。AMD 那边也差不多，LLVM AMDGPU 后端生成 amdgcn，再链接成 hsaco。

但如果我们接触过 NPU 或 TPU 的编译链，会发现情况完全不同。以华为昇腾为例，Triton-Ascend 的主链路是这样的：TTIR 经过一串 Adapter pass，直接进厂商编译器（bishengir-compile），产出设备二进制，运行时注册执行。整条链路里根本没有 LLVM IR，也没有 llc，更没有 ptxas。

这不是某个团队选择不用 LLVM 的问题，而是两类硬件的执行模型和资源约束从根本上就不一样，导致编译器要干的活、要解决的问题、要产出的东西都不同。

先来看两条典型的编译链长什么样。

## GPU 编译链（以 Triton + CUDA 为例）

```text
Python Kernel
    ↓
Triton AST → TTIR（Triton IR）
    ↓
TTIR 优化（combine, reorder_broadcast, CSE, LICM, loop_unroll）
    ↓
TritonGPU 方言（映射线程块/warp、共享内存布局、向量化策略）
    ↓
NVVM 方言（注入 NVIDIA 特有语义：maxnreg, reqntid, cluster, tensor core intrinsic）
    ↓
LLVM dialect → 导出 LLVM IR
    ↓
LLVM NVPTX 后端 → PTX
    ↓
ptxas（寄存器分配、指令调度、优化）→ cubin
    ↓
驱动加载执行
```

这条链的后半段，从 LLVM IR 到 cubin，是 GPU 编译的最后一公里。ptxas 在这一步干的活非常重，包括真正的寄存器分配、指令级调度、目标代码优化，最后产出可以被驱动加载的二进制对象。

AMD 那边结构类似，只是把 NVVM 换成 ROCDL，把 ptxas 换成 LLVM AMDGPU 后端 + ROCm 工具链，产物从 cubin 变成 hsaco。

## NPU 编译链（以 Triton-Ascend 为例）

```text
Python Kernel
    ↓
Triton AST → TTIR
    ↓
TTIR 优化（同样的 combine, CSE, LICM 等）
    ↓
Triton-Adapter 串：
    --discrete-mask-access-conversion（掩码访存离散化）
    --triton-to-annotation（标注与属性注入）
    --triton-to-unstructure（不规则访存结构化）
    --triton-to-hivm（同步/屏障/管道语义映射）
    --bubble-up-operation（算子上浮）
    --triton-to-linalg（数据通路抽象）
    ↓
厂商编译器（bishengir-compile / npuc）
    ↓
设备二进制 / 命令流
    ↓
运行时注册（rtDevBinaryRegister / rtFunctionRegister）执行
```

注意看这条链的后半段。从 Adapter 产出的 MLIR 直接进厂商编译器，主链路不导出 LLVM IR、不调用 llc、不走通用目标后端。产物也不是 cubin/hsaco 那种通用可链接的对象文件，而是命令流加设备二进制，由运行时直接注册加载。

这里有个容易混淆的点：Triton-Ascend 的 NPU Adapter 不包含 `--triton-to-llvm`。NPU 主链不导出 LLVM IR、不调用 `llc`。只有 CPU 对照链才会使用 `mlir-translate --mlir-to-llvmir` 与 `llc`。此外，部分特定领域优化（如 HFusion）由厂商编译器开关 `--enable-hfusion-compile=true` 控制，而不属于开源 Adapter pass 的一部分。

## 两条链的关键差异

把两条链放在一起看，差异就很明显了：

| 维度 | GPU（CUDA/ROCm） | NPU（Ascend） |
| --- | --- | --- |
| 最后一公里的入口 | LLVM IR | MLIR（Linalg/HIVM/HFusion） |
| 最后一公里干什么 | 寄存器分配、目标指令选择、指令级调度 | UB 规划、多缓冲、DMA-Compute 流水、屏障图、核变体选择 |
| 最后一公里谁干 | LLVM NVPTX/AMDGPU + ptxas | 厂商编译器（bishengir-compile） |
| 产物形态 | cubin/hsaco（可链接对象，符号表/行号/调试信息） | 命令流/设备二进制（运行时直接注册） |
| 运行时接口 | 驱动加载 cubin，按 ABI 设置参数 | rtDevBinaryRegister + rtFunctionRegister |

## 这意味着什么

GPU 编译链对 LLVM 的依赖是刚性的。LLVM 的 NVPTX/AMDGPU 后端解决的是把 SSA 形式的中间表示落成目标机器指令这件事，包括：

- 把虚拟寄存器映射到物理寄存器（寄存器分配）
- 把中立的 IR 操作映射到 PTX/amdgcn 的具体指令（指令选择）
- 按照目标机器的延迟/吞吐模型重排指令（指令调度）
- 生成带符号表、调试信息的可链接目标文件（对象生态）

这些能力对 GPU 而言缺一不可。少了寄存器分配，kernel 跑不起来；少了指令选择，tensor core 用不上；少了调度，访存延迟藏不住；少了对象生态，调试和性能分析没法做。

NPU 那边不是不需要解决这些问题，而是问题的形态变了。寄存器分配对 NPU 吞吐的影响远没有 GPU 那么大，性能瓶颈在 UB 容量和 DMA 带宽。目标指令选择变成了选哪个核变体、配什么参数，不是从通用指令集里挑指令。调度问题在 MLIR 层就以多缓冲深度、流水阶段、屏障插入的形式解决了，不需要到目标机器码层面再做指令级重排。产物也不需要是可链接对象，命令流由运行时直接消费。

所以问题不是 NPU 团队为什么不用 LLVM，而是 LLVM 擅长解决的那类问题，在 NPU 编译链里要么不存在，要么被前移到更高的抽象层解决了，要么被厂商编译器用完全不同的方式处理了。

接下来我们从硬件层面看看，GPU 和 NPU 的执行模型到底有什么不同，导致编译职责出现这样的分化。

## GPU 和 NPU 的硬件执行模型

要理解编译链的差异，得先搞清楚这两类芯片到底是怎么跑计算的。不是泛泛地说 GPU 并行度高或者 NPU 是专用加速器，而是要看它们的执行单元怎么组织、数据怎么流动、延迟怎么隐藏、资源约束在哪里。

## GPU：指令流驱动的 SIMT 机器

GPU 的基本执行单位是线程。但 GPU 不是一个线程一个线程地跑，而是把 32 个线程（NVIDIA）或 64 个线程（AMD）打包成一个 warp（或 wavefront），让它们锁步执行同一条指令。这就是 SIMT（Single Instruction Multiple Thread）模型。

一个 SM（Streaming Multiprocessor，NVIDIA 的叫法）或 Compute Unit（AMD 的叫法）上可以同时驻留多个 warp。硬件调度器在这些 warp 之间快速切换：当一个 warp 在等数据（比如从显存读数据，延迟几百个周期），调度器立刻切到另一个 warp 继续执行。这是 GPU 隐藏延迟的核心机制。

来看 GPU 内部的资源组织：

```text
SM / Compute Unit
├── 寄存器文件（Register File）
│   └── 容量固定，所有驻留 warp 共享这个池子
├── 共享内存（Shared Memory / LDS）
│   └── 程序员可控的片上存储，容量有限
├── L1 缓存
├── 调度器
│   └── 管理多个 warp 的切换
├── ALU / FPU
├── Tensor Core / Matrix Unit
│   └── 专用矩阵乘累加单元
├── Load/Store Unit
└── 特殊功能单元（SFU）
```

几个关键约束要注意：

**寄存器压力决定并发度**。SM 的寄存器文件是固定大小的，比如 65536 个 32 位寄存器。如果我们的 kernel 每个线程用 64 个寄存器，一个 warp（32 线程）就用掉 2048 个寄存器，整个 SM 最多驻留 32 个 warp。如果每线程用 128 个寄存器，最多只能驻留 16 个 warp。驻留的 warp 越少，调度器能切换的余地就越小，延迟就越难藏住。

这个能驻留多少 warp 跟理论上限的比值叫 occupancy。occupancy 低不一定性能差（有时候寄存器多了计算更快），但它是 GPU 性能调优绑不开的参数。

**共享内存也是约束**。共享内存和寄存器一样，是多个线程块竞争的资源。用多了，能驻留的线程块就少了。而且共享内存有 bank 结构，访问不当会产生 bank conflict，拖慢访存。

**指令流是显式的**。GPU 执行的是一条一条的机器指令：load、store、算术运算、tensor core 指令、屏障、分支。编译器要把高层代码翻译成这些指令序列，每条指令的延迟、吞吐、依赖关系都影响最终性能。

**专用单元需要专用指令**。Tensor Core 做矩阵乘需要 mma 指令，异步数据搬运需要 cp.async 或 TMA 指令，跨 warp 同步需要 mbarrier 指令。这些指令在不同代 GPU 上形态不同（Volta/Ampere/Hopper 的 mma 就不一样），编译器得根据目标架构选对指令，参数也得合法。

用一个简化的视角来看 GPU 怎么跑一个 GEMM kernel：

```text
for each tile:
    1. 发射异步 load 指令，从 HBM 搬数据到共享内存
    2. 插入屏障，等数据就位
    3. 从共享内存 load 到寄存器
    4. 执行 tensor core mma 指令，累加到寄存器
    5. 循环直到 K 维走完
    6. 把寄存器里的结果写回 HBM
```

这个过程里，每一步都是具体的机器指令。寄存器用多少、共享内存怎么排布、load 和 compute 怎么交错、屏障插在哪里，都直接影响性能。编译器的活儿就是把高层的矩阵乘翻译成这样的指令序列，还得保证寄存器不溢出、共享内存不冲突、指令调度能藏住延迟。

## NPU：命令流驱动的数据流机器

NPU 的执行模型跟 GPU 完全不同。以华为昇腾为例，它的核心组件是这样的：

```text
NPU 核心
├── Cube Unit（矩阵运算单元）
│   └── 专做矩阵乘、卷积等
├── Vector Unit（向量运算单元）
│   └── 做向量运算、激活函数、归约等
├── Scalar Unit（标量控制单元）
│   └── 控制流、地址计算
├── DMA 引擎
│   └── 负责 GM（全局内存）和 UB 之间的数据搬运
├── UB（Unified Buffer）
│   └── 片上高速缓存，所有计算单元共享
└── 事件/屏障机制
    └── 跨引擎同步
```

几个关键差异：

**上层编程不以每线程为抽象**。与 GPU 的每线程加 warp 编程模型不同，NPU 用命令流描述任务：先搬这块数据到 UB，然后用 Cube 算矩阵乘，结果写回 UB，再用 Vector 做激活，最后搬回 GM。硬件按命令流与屏障时序推进，不存在 GPU 式的 warp 切换。

**数据搬运是显式的**。GPU 的 load/store 指令背后有复杂的缓存层次（L1/L2/HBM），程序员写 `a[i]` 就行，缓存命中不命中是硬件管的。NPU 不一样，数据必须显式地从 GM 搬到 UB 才能参与计算，计算完必须显式搬回 GM。这个搬运由 DMA 引擎执行，跟计算单元是分开的。

**延迟隐藏靠流水和多缓冲**。GPU 靠 warp 切换藏延迟，NPU 靠的是 Load、Compute、Store 三个阶段的重叠。具体来说，把 UB 切成多段（双缓冲或多缓冲），当 Cube 在算第 i 块数据的时候，DMA 同时在加载第 i+1 块数据，还在写回第 i-1 块的结果。三个阶段并行推进，流水起来。

**UB 容量是硬约束**。UB 就那么大（比如几百 KB），工作集必须塞进去。如果一个 tile 太大，UB 装不下，要么切小，要么溢出到 GM（性能会很差）。多缓冲还要额外占空间，双缓冲意味着同样的数据要留两份的位置。所以 tile 大小怎么选、多缓冲几段、UB 怎么切，是 NPU 编译的核心问题。

**同步靠屏障和事件**。DMA 搬完数据要通知 Compute 可以算了，Compute 算完要通知 DMA 可以写回了。这个同步通过事件/屏障机制实现。屏障设少了，数据没就位就开算，结果错误；屏障设多了，流水断了，性能下降。编译器要算出最小够用的屏障集合。

用同样简化的视角看 NPU 怎么跑一个 GEMM：

```text
初始化：把 UB 切成 buffer_0 和 buffer_1（双缓冲）

预加载：DMA 把第 0 块 A、B 搬到 buffer_0

for i in range(num_tiles):
    # 三个阶段并行
    Stage 1 (DMA): 加载第 i+1 块到 buffer_(i+1)%2
    Stage 2 (Cube): 用 buffer_i%2 的数据算矩阵乘
    Stage 3 (DMA): 把第 i-1 块结果从 buffer_(i-1)%2 写回 GM
    
    # 屏障同步
    等 Stage 1 完成，才能开始下一轮的 Stage 2
    等 Stage 2 完成，才能开始下一轮的 Stage 3

收尾：写回最后一块结果
```

这里面没有每线程用多少寄存器的概念，也没有指令怎么排序的问题。核心是：tile 切多大、双缓冲还是三缓冲、DMA 的步幅和对齐对不对、屏障插在哪里保证时序。

## 两类硬件的对照

| 维度 | GPU | NPU |
| --- | --- | --- |
| 执行模型 | SIMT 指令流，warp 锁步执行 | 命令流驱动，阶段式流水 |
| 基本并行单位 | warp（32/64 线程） | 无线程概念，按 tile/block 组织 |
| 数据搬运 | load/store 指令 + 缓存层次 | 显式 DMA，GM ↔ UB |
| 片上存储 | 寄存器文件 + 共享内存 | UB（Unified Buffer） |
| 延迟隐藏 | warp 切换 + 指令级调度 | DMA-Compute 流水 + 多缓冲 |
| 核心资源约束 | 寄存器/共享内存配额 → occupancy | UB 容量/带宽 → tile 大小和缓冲深度 |
| 同步机制 | 屏障指令（__syncthreads, mbarrier） | 事件/屏障图（跨 DMA/Compute 引擎） |
| 专用单元 | Tensor Core / Matrix Core | Cube Unit / Vector Unit |
| 专用单元调用方式 | 特定指令（mma, mfma） | 核变体选择 + 参数配置 |

## 性能瓶颈在不同的地方

GPU 的性能瓶颈经常在这几个地方：

1. **寄存器溢出**。寄存器不够用，编译器把数据溢出到 local memory（其实在 HBM 上），访存延迟从几个周期变成几百个周期。
2. **occupancy 太低**。寄存器或共享内存用太多，驻留 warp 太少，延迟藏不住。
3. **shared memory bank conflict**。多个线程同时访问同一个 bank，串行化。
4. **指令调度不好**。计算指令和访存指令没有交错好，发射端口空着。

NPU 的性能瓶颈在另外一些地方：

1. **UB 装不下**。tile 切太大或者多缓冲太深，UB 溢出，只能回退到更小的 tile 或更浅的流水。
2. **DMA 和 Compute 没流水起来**。屏障太多或位置不对，流水断了，硬件空转。
3. **DMA 步幅/对齐不对**。非对齐访问或奇怪的步幅导致 DMA 效率低。
4. **核变体选错了**。比如该用 Cube 的用了 Vector，或者 im2col 和 direct 选错了。

这就是为什么 GPU 编译器要花大力气做寄存器分配和指令调度，而 NPU 编译器要花大力气做 UB 规划和流水编排。两类硬件的性能敏感点不一样，编译器干的活也就不一样。

接下来看看，这些硬件差异怎么体现在编译器的具体职责上。

## 编译器的职责跟着硬件走

硬件执行模型不同，编译器要解决的问题也就不同。这不是选择的问题，是必须的问题。GPU 编译器必须解决寄存器分配，因为寄存器用多少直接决定能跑多少 warp；NPU 编译器必须解决 UB 规划，因为 UB 装不下整个计算就跑不起来。

来看看两边的编译器各自要干什么活。

## GPU 编译器的四大职责（以 ptxas 为核心）

### 1. 寄存器分配

这是 GPU 编译最后一公里的核心问题之一。

高层 IR（包括 LLVM IR）用的是 SSA（Static Single Assignment）形式，变量是虚拟寄存器，想用多少用多少。但真实的 GPU 寄存器文件是有限的，必须把这些虚拟寄存器映射到物理寄存器上。如果映射不过来，就得把一部分数据溢出到 local memory。

溢出的代价很大。Local memory 在物理上是全局内存的一部分，访问延迟是寄存器的几百倍。一个本来很快的 kernel，如果寄存器溢出严重，性能可能掉一个数量级。

所以 GPU 编译链对寄存器分配非常重视。Triton 在生成 NVVM IR 的时候，会把用户设置的 `maxnreg`（最大寄存器数）传递下去，让后端知道寄存器预算是多少。

让我们看看 Triton 是如何通过代码将这个意图传递给 LLVM 的。在 `lib/Conversion/TritonGPUToLLVM/FuncOpToLLVM.cpp` 中，我们可以看到它显式地提取了 `maxnreg` 属性并“注入”到了 NVVM 函数上：

```text
if (Attribute maxnregAttr = funcOp.getParentOp()->getAttr(
        triton::gpu::AttrMaxRegistersName)) {
  newFuncOp->setAttr(NVVM::NVVMDialect::getMaxnregAttrName(), maxnregAttr);
}
```

这段代码把模块级的 `ttg.maxnreg` 属性传递到 NVVM 函数上，变成 `nvvm.maxnreg` 属性。最终这个属性会影响 ptxas 的寄存器分配策略。

更有意思的是 `AllocateWarpGroups` 中为 ptxas 设定初始寄存器预算（`lib/Conversion/TritonGPUToLLVM/AllocateWarpGroups.cpp`）：

```text
// Set the initial max number of registers. This is needed for PTXAS to cooperate.
mod->setAttr(AttrMaxRegistersName, 
             Builder(op.getContext()).getI32IntegerAttr(maxnreg));
```

needed for PTXAS to cooperate，说得很直白：这个值是给 ptxas 看的，让它配合做寄存器分配。Triton 前端只能设一个意图，真正干活的是 ptxas。

ptxas 做寄存器分配的时候，会考虑：

- 用户设置的 maxnreg 上限
- kernel 的实际寄存器需求
- 目标 GPU 的寄存器文件大小
- 溢出的代价

如果寄存器需求超过上限，ptxas 会选择溢出一部分到 local memory。如果我们跑 ptxas 的时候加上 `-v` 选项，它会告诉我们这个 kernel 用了多少寄存器、溢出了多少字节。

### 2. 目标指令选择和合法化

GPU 每一代都有新指令、新能力。Volta 的 tensor core 用 `mma.sync`，Ampere 改进了，Hopper 又加了 `wgmma`。异步数据搬运从 `cp.async` 到 TMA。屏障从简单的 `bar.sync` 到复杂的 `mbarrier`。

编译器要根据目标架构选对指令，还要保证参数合法。比如 tensor core 指令对矩阵形状有要求（16x16x16 之类的），地址对齐有要求，数据类型有要求。用错了，要么编译报错，要么运行时崩溃，要么结果不对。

这个过程叫指令选择和合法化。在 Triton 里，这部分工作分成两层：

第一层是 TritonGPU 到 NVVM 的转换。这一步把 Triton 的高层操作（比如 `tt.dot`）转成 NVVM 方言的操作，注入目标特定的语义。

第二层是 NVVM 到 LLVM IR 的转换，再到 NVPTX 后端。LLVM 的 NVPTX 后端知道每个 PTX 指令的语义、约束、延迟，会做最终的指令选择。

Triton 会把这些无法对应的操作封装成 **内联汇编（Inline Assembly）** 节点。在 MLIR 层面，这是通过 `LLVM::InlineAsmOp` 实现的，它允许编译器直接携带目标机器的汇编文本。

比如 `mbarrier.init` 这个指令，就是通过构建包含具体 PTX指令文本的内联汇编来实现的：

```text
// TritonNVIDIAGPUToLLVM/BarrierOpToLLVM.cpp
const std::string ptx = "@$0 mbarrier.init.shared::cta.b64 [$1], $2;";
// ... 创建内联汇编 Op ...
```

这段代码直接把 PTX 汇编文本嵌进去了。为什么要这样？因为 `mbarrier` 是 Hopper 架构引入的新特性，MLIR 的标准方言表达不了，只能直接写目标汇编。

### 3. 指令级调度

GPU 的执行单元有多个发射端口，可以同时发射不同类型的指令（比如一条算术指令和一条访存指令）。指令之间有依赖关系和延迟约束。编译器要把指令排好序，尽量让发射端口不空着，让访存的延迟被计算指令盖住。

这是经典的指令调度问题，涉及到：

- 依赖图分析（哪些指令必须等哪些指令完成）
- 延迟建模（每条指令要多少周期）
- 资源建模（发射端口、执行单元的限制）
- 调度算法（列表调度、软件流水等）

在 Triton 的 GPU 后端里，ptxas 和 LLVM AMDGPU 后端承担了大部分指令调度的工作。Triton 层面做的是更高层的调度，比如循环的软件流水（pipeline）、访存和计算的交错（scheduling）。

看 `third_party/nvidia/backend/compiler.py` 里的 pass 列表：

```text
# backend/compiler.py
passes.ttgpuir.add_fuse_nested_loops(pm)
passes.ttir.add_triton_licm(pm)
passes.common.add_cse(pm)
passes.ttgpuir.add_assign_latencies(pm)  # 延迟标注
passes.ttgpuir.add_schedule_loops(pm)    # 循环调度
passes.ttgpuir.add_pipeline(pm, opt.num_stages)  # 软件流水
```

这些 pass 在 MLIR 层面做了一些调度准备工作，但真正的指令级调度还是在后端。ptxas 有自己的调度器，会根据目标 GPU 的微架构模型重排指令。我们可以用 `--opt-level` 控制 ptxas 的优化级别，`--opt-level 0` 会关掉大部分优化包括调度；或通过 `PTXAS_OPTIONS` 传入等价参数。

### 4. 对象和调试生态

编译器最终要产出可执行的二进制。对 GPU 来说，这是 cubin（NVIDIA）或 hsaco（AMD）。这些不只是机器码，还包含：

- 符号表（函数名、入口地址）
- 调试信息（源代码行号映射、变量信息）
- 元数据（寄存器使用量、共享内存大小、线程块配置）

有了这些信息，nsight、rocprof 这些工具才能做性能分析和调试，才能告诉我们第 42 行代码执行了多少次，花了多少时间。

Triton 会把调试信息传递到后端。可见 LLVM debug info 的生成与注入（参见 `lib/Target/LLVMIR/LLVMDIScope.cpp`），最终由后端嵌入到对象文件中。

这些 debug info 最终会被 ptxas 处理，嵌入到 cubin 里。我们跑 kernel 的时候如果崩溃了，调试器能告诉我们崩在源代码的哪一行。

## NPU 编译器的四大职责（以 UB 和流水为核心）

NPU 编译器要解决的问题完全不同。来看 Triton-Ascend 的编译链。

### 1. UB 规划和多缓冲

UB 是 NPU 的片上存储，所有计算都要经过它。编译器要回答几个问题：

- tile 切多大？太大 UB 装不下，太小计算效率低。
- 多缓冲几段？双缓冲能让 Load 和 Compute 重叠，三缓冲能进一步提高流水效率，但 UB 占用也更多。
- 数据怎么排布？不同的排布方式影响 DMA 效率和计算效率。

在 `triton-ascend/ascend/backend/compiler.py` 里可以看到相关选项：

```text
# 片段
if metadata.multibuffer:
    _compile_option_list.append("--enable-auto-multi-buffer=true")

（注：Triton-Ascend 未提供打印 UB 占用的通用开关；UB 占用与多缓冲配置通常通过编译选项与 profiler 配合观测。）

### 2. DMA-Compute 流水编排

DMA 搬数据和计算单元算数据是分开的硬件，可以并行工作。但并行需要正确的编排：

- DMA 什么时候开始搬第 i+1 块数据？
- Compute 什么时候可以开始算第 i 块数据？
- 回写 DMA 什么时候可以写第 i-1 块的结果？

这些时序关系要通过屏障/事件来保证。编译器有几种策略：

```python
# 片段
if opt.enable_hivm_auto_cv_balance is not None:
    _compile_option_list.append(
        f"--enable-hivm-auto-cv-balance={str(opt.enable_hivm_auto_cv_balance).lower()}")

if opt.enable_hivm_graph_sync_solver is not None:
    _compile_option_list.append(
        f"--enable-hivm-graph-sync-solver={str(opt.enable_hivm_graph_sync_solver).lower()}")
```

`--enable-hivm-auto-cv-balance` 让编译器自动平衡 Compute 和 Vector 的负载。

还有一系列屏障相关的选项：

```text
if opt.enable_hivm_unit_flag_sync is not None:
    _compile_option_list.append(...)
if opt.enable_hivm_inject_barrier_all_sync is not None:
    _compile_option_list.append(...)
```

这些选项控制屏障注入的粒度和策略。屏障太少会导致数据竞争（结果错误），屏障太多会打断流水（性能下降）。编译器要找到那个平衡点。

### 3. 核变体和引擎选择

NPU 有多种计算单元：Cube Unit 擅长矩阵乘，Vector Unit 擅长向量运算。同一个算子可能有多种实现：卷积可以用 direct、im2col、Winograd；GEMM 可以用不同的 tile 策略。

编译器要根据输入形状、数据类型、UB 预算选择合适的实现。

在 Triton-Adapter 里，mix_mode 就是用来标记核类型的：

```text
# TritonToLinalgPass.cpp
kernelMixMode = existDot ? "mix" : "aiv";
funcFunc->setAttr(kernelMixModeName, builder.getStringAttr(kernelMixMode));
```

如果 kernel 里有 `tt.dot`（矩阵乘），就标记为 `mix` 模式，意味着要用 Cube Unit；否则标记为 `aiv`（All In Vector），只用 Vector Unit。

这个标记会传递到运行时，影响二进制的加载方式（`backend/npu_utils.cpp`）：

```text
if (kernel_mode == "aiv") {
    devbin.magic = RT_DEV_BINARY_MAGIC_ELF_AIVEC;
} else {
    devbin.magic = RT_DEV_BINARY_MAGIC_ELF;
}
```

不同的 magic 告诉运行时用不同的方式加载和执行这个 kernel。

tile 策略也可以调整：

```text
# 片段
if opt.tile_mix_vector_loop is not None:
    _compile_option_list.append(f"--tile-mix-vector-loop={opt.tile_mix_vector_loop}")
if opt.tile_mix_cube_loop is not None:
    _compile_option_list.append(f"--tile-mix-cube-loop={opt.tile_mix_cube_loop}")
```

这些选项控制 Vector 回路和 Cube 回路的 tile 大小。

### 4. 结构化不规则访存

GPU 可以比较自由地访问内存，缓存会处理大部分复杂性。NPU 的 DMA 对访存模式有更强的约束：步幅要规整、地址要对齐、形状要适合硬件。

如果用户写了不规则的访存（比如带 mask 的 load、间接索引、非连续切片），编译器要把它转换成 DMA 能处理的形式。

Triton-Adapter 里有一系列 pass 做这个事情：

```text
# 片段
cmd = [
    self.get_triton_adapter_opt(),
    "--discrete-mask-access-conversion",  # 掩码访存离散化
    "--triton-to-annotation",
    "--triton-to-unstructure",            # 不规则访存结构化
    "--triton-to-hivm",
    "--bubble-up-operation",              # 算子上浮
    "--triton-to-linalg",
]
```

`--discrete-mask-access-conversion` 处理带 mask 的访存。如果 mask 是连续的，可以转成对齐的 DMA；如果 mask 不连续（离散），Pass 会将其标记为 `discrete`，指导后端采用非向量化的安全处理方式，避免非法内存访问。

`--triton-to-unstructure` 类似地处理不规则的张量切片。它会将这些操作显式化为 `extract_slice` 并打上 `discrete` 标注，防止编译器生成错误的 DMA 搬运指令。

`--bubble-up-operation` 则负责将计算算子（如浮点运算）向上浮动（Bubble Up），使其尽可能靠近数据加载操作。这样做为后续的指令流优化创造了空间，使得计算和访存更容易重叠。

这些 pass 的目标是把用户写的自由形式的 kernel 转换成后端能高效处理的结构化形式。

## 两类编译器的职责对照

| 职责 | GPU 编译器 | NPU 编译器 |
| --- | --- | --- |
| 核心资源管理 | 寄存器分配（决定 occupancy） | UB 规划（决定 tile 大小和多缓冲深度） |
| 延迟隐藏 | 指令级调度（填满发射端口） | DMA-Compute 流水编排（阶段重叠） |
| 目标特性适配 | 指令选择和合法化（mma/TMA/mbarrier） | 核变体选择（Cube/Vector, direct/im2col） |
| 访存优化 | 共享内存布局、coalescing | DMA 步幅/对齐、访存结构化 |
| 同步 | 屏障指令（syncthreads, mbarrier） | 屏障图求解（跨 DMA/Compute 引擎） |
| 产物 | cubin/hsaco（可链接对象） | 命令流/设备二进制（运行时注册） |

这就是编译器的活儿跟着硬件走。GPU 硬件的性能敏感点在寄存器和指令级并行，编译器就得花大力气做寄存器分配和指令调度。NPU 硬件的性能敏感点在 UB 和数据流水，编译器就得花大力气做 UB 规划和流水编排。

接下来看看，LLVM 在 GPU 编译链里具体干了什么活，为什么 GPU 离不开它。

## LLVM 在 GPU 编译链里干了什么

前面讲了 GPU 编译器要解决寄存器分配、指令选择、指令调度、对象生态这四件事。这一节来看看 LLVM 具体是怎么干这些活的，以及为什么 GPU 编译链几乎绑定在 LLVM 上。

## LLVM 的角色定位

先把 LLVM 在 GPU 编译链里的位置搞清楚。

LLVM 不是一个单一的工具，而是一套编译基础设施。对 GPU 编译来说，关键组件有：

- **LLVM IR**：一种低层但与目标无关的中间表示，SSA 形式，类型化，带显式控制流。
- **LLVM NVPTX 后端**：把 LLVM IR 翻译成 NVIDIA 的 PTX 汇编。
- **LLVM AMDGPU 后端**：把 LLVM IR 翻译成 AMD 的 amdgcn 汇编。
- **LLVM 优化 pass**：一系列通用的优化（死代码消除、常量折叠、循环优化等）。

在 Triton 的编译链里，LLVM 的位置是这样的：

```text
TritonGPU IR (MLIR)
    ↓
NVVM/ROCDL 方言 (MLIR，带目标特定语义)
    ↓
LLVM dialect (MLIR)
    ↓
导出为 LLVM IR (mlir-translate)
    ↓
LLVM 优化 (opt -O3)
    ↓
LLVM NVPTX/AMDGPU 后端 (llc)
    ↓
PTX / amdgcn 汇编
```

对 NVIDIA，PTX 汇编还要再经过 ptxas 变成最终的 cubin。ptxas 是 NVIDIA 自己的工具，不属于 LLVM，但它做的事情和 LLVM 后端类似：寄存器分配、指令调度、目标代码生成。

来看 Triton 里这些依赖是怎么链接的（`lib/Target/LLVMIR/CMakeLists.txt`）：

```text
target_link_libraries(TritonLLVMIR
  PRIVATE
  MLIRNVVMToLLVM
  MLIRLLVMToLLVMIRTranslation
  MLIRNVVMToLLVMIRTranslation
  MLIRROCDLToLLVMIRTranslation
  MLIRTargetLLVMIRExport
  ...
)
```

这些库提供了从 MLIR（NVVM/ROCDL 方言）到 LLVM IR 的翻译能力。

在顶层 `CMakeLists.txt` 里：

```text
target_link_libraries(triton PRIVATE
  LLVMNVPTXCodeGen
  LLVMAMDGPUCodeGen
  ...
)
```

这两个库是 LLVM 的 NVPTX 和 AMDGPU 后端，提供了从 LLVM IR 到目标汇编的代码生成能力。

## LLVM 怎么做寄存器分配

寄存器分配是把 LLVM IR 里的虚拟寄存器映射到物理寄存器的过程。这个过程要考虑：

- 物理寄存器的数量和类型（通用寄存器、浮点寄存器、特殊寄存器）
- 变量的活跃区间（一个变量从定义到最后一次使用的范围）
- 寄存器的调用约定（哪些寄存器是 caller-save，哪些是 callee-save）
- 溢出策略（寄存器不够用时怎么办）

LLVM 有复杂的寄存器分配算法（如 Greedy, PBQP 等）。其基本流程大致是：

1. 构建干扰图（哪些变量的活跃区间重叠）
2. 给变量排优先级（使用频率高的、活跃区间长的优先）
3. 按优先级给变量分配物理寄存器
4. **如果分配失败**（没有可用的物理寄存器），把变量溢出到栈上

对 GPU 来说，栈其实是 local memory，访问延迟比寄存器高两个数量级。所以 GPU 编译非常在意溢出量。

Triton 层面能做的是告诉后端我希望最多用多少寄存器。这个信息通过属性传递：

```text
// lib/Conversion/TritonGPUToLLVM/FuncOpToLLVM.cpp
if (Attribute maxnregAttr = funcOp.getParentOp()->getAttr(
        triton::gpu::AttrMaxRegistersName)) {
  newFuncOp->setAttr(NVVM::NVVMDialect::getMaxnregAttrName(), maxnregAttr);
}
```

这个 `nvvm.maxnreg` 属性会被翻译成 PTX 的 `.maxnreg` 指令：

```text
.entry my_kernel(...) .maxnreg 64 {
    // kernel 代码
}
```

ptxas 看到这个指令后，会把寄存器分配的上限设为 64。如果 kernel 实际需要更多寄存器，ptxas 会选择溢出。

我们可以用 `PTXAS_OPTIONS` 环境变量传递参数给 ptxas，比如 `-v` 会让它输出寄存器使用信息（参见 Triton 文档）：

```text
ptxas info    : Compiling entry function 'my_kernel'
ptxas info    : Used 48 registers, 8192 bytes smem, 364 bytes cmem[0]
```

这告诉我们 kernel 用了 48 个寄存器、8192 字节共享内存。如果这里显示 “spill stores” 或 “spill loads”，说明有寄存器溢出。

对于新架构（Hopper/Blackwell），还有 Tensor Memory（TMEM）这个新的存储层次。TMEM 的访问指令（`tcgen05.ld`/`tcgen05.st`）也受寄存器数量的约束：

```text
// lib/Dialect/TritonNvidiaGPU/IR/TensorMemoryUtils.cpp
// PTXAS validates the register usage of `tcgen05.ld` and `tcgen05.st` ...
if (auto maxnregAttr = mod->getAttrOfType<IntegerAttr>(AttrMaxRegistersName))
    maxnreg = std::min<int>(maxnreg, maxnregAttr.getInt());
```

这段注释说得很清楚：ptxas 会验证 TMEM 指令的寄存器使用，编译器必须和 ptxas 配合。

## LLVM 怎么做指令选择

指令选择是把 LLVM IR 的操作映射到目标机器指令的过程。LLVM IR 是通用的，一条 `add` 指令可以加整数也可以加浮点数，可以是 32 位也可以是 64 位。但目标机器的指令是具体的，加 32 位整数和加 32 位浮点数是不同的指令。

LLVM 的指令选择器要做的事：

- 把 LLVM IR 操作匹配到目标指令模式
- 处理操作数类型转换（需要时插入类型提升/截断）
- 处理地址空间（GPU 有多个地址空间：global、shared、local、constant）
- 处理目标特定的约束（对齐、合法的立即数范围等）

对 GPU 特别重要的是专用单元的指令选择。Tensor Core 的矩阵乘需要 mma 指令，不同代 GPU 的 mma 形态不同：

```text
Volta:   mma.sync.aligned.m8n8k4.row.col.f32.f16.f16.f32
Ampere:  mma.sync.aligned.m16n8k16.row.col.f32.f16.f16.f32
Hopper:  wgmma.mma_async.sync.aligned.m64n64k16.f32.f16.f16
```

Triton 在 TritonGPU 到 NVVM 的转换里选择对应的指令模式（参见 `DotOpToLLVM/MMAv2.cpp`）。

有些指令 LLVM 的 NVPTX 后端直接支持，有些需要用 NVVM intrinsic，还有些需要内联 PTX。

NVVM intrinsic 是 LLVM 为 NVIDIA GPU 定义的特殊函数，会被 NVPTX 后端翻译成对应的 PTX 指令。比如：

```text
%result = call i32 @llvm.nvvm.read.ptx.sreg.tid.x()
; 被翻译成
mov.u32 %r1, %tid.x;
```

内联 PTX 是更底层的逃生舱口，当 NVVM intrinsic 表达不了的时候用。比如 mbarrier 系列指令在 Hopper 上有很多新形态，用内联 PTX 更直接：

```text
// TritonNVIDIAGPUToLLVM/BarrierOpToLLVM.cpp
const std::string ptx = "@<!--MATH_PH_1-->1], $2;";
```

这里直接把 PTX 汇编嵌进去了，`@$0` 是 predicate，`[$1]` 是地址，`$2` 是操作数。

LLVM 后端也要做合法化。有些 LLVM IR 操作在目标机器上不直接支持，需要展开成多条指令或者用库函数。比如 64 位整数除法在一些 GPU 上没有硬件指令，就得用软件实现。

## LLVM 怎么做指令调度

指令调度是在保证正确性的前提下重排指令，提高执行效率。LLVM 有几个调度 pass：

- **Pre-RA scheduling**：在寄存器分配之前做的调度，目标是减小活跃区间，降低寄存器压力
- **Post-RA scheduling**：在寄存器分配之后做的调度，目标是隐藏延迟，提高吞吐

调度器需要两类信息：

**依赖信息**：哪些指令之间有数据依赖（RAW：读后写）、反依赖（WAR：写后读）、输出依赖（WAW：写后写）。有依赖的指令不能随意交换顺序。

**延迟信息**：每条指令执行需要多少周期，结果什么时候可用。这些信息来自目标描述文件（TableGen 格式），描述了目标机器的微架构。

LLVM 的调度器通常采用**列表调度（list scheduling）**策略。它会构建指令依赖图，计算关键路径，并在保证依赖关系的前提下，优先发射那些能掩盖后续指令延迟的操作（如提前发射访存指令）。

这个过程需要精确的目标机器模型：

但 LLVM 后端的调度能力是有限的。它基于静态分析，不知道运行时的实际行为（比如 cache 命中率）。而且 LLVM 生成的是 PTX，不是最终的机器码，ptxas 还会再做一轮调度。

Triton 在更高层做了一些调度相关的优化：

```text
# backend/compiler.py
passes.ttgpuir.add_assign_latencies(pm)  # 给操作标注延迟
passes.ttgpuir.add_schedule_loops(pm)    # 循环内的调度
```

`add_assign_latencies` 给 IR 里的操作标注预估延迟，`add_schedule_loops` 基于这些信息做循环内的指令编排。这是在 MLIR 层面做的，比 LLVM 层面更高，能看到更多上下文信息。

ptxas 做的调度更激进。它知道目标 GPU 的精确微架构模型，包括：

- 发射端口数量和类型（INT、FP32、FP64、TENSOR、LD/ST）
- 每个端口的吞吐（每周期能发射几条指令）
- 指令的延迟和占用的端口
- 记分牌机制（GPU 跟踪指令依赖的硬件机制）

我们可以用 `--opt-level` 控制 ptxas 的优化级别，或通过 `PTXAS_OPTIONS` 直接传入：

```text
# Triton 实际调用示例
disable_opt = ['--opt-level', '0'] if knobs.nvidia.disable_ptxas_opt else []
ptx_extra_options = opt.ptx_options.split(" ") if opt.ptx_options else []
ptxas_cmd = [ptxas, *debug_info, *fmad, '-v', *disable_opt, *ptx_extra_options, f'--gpu-name={arch}', fsrc.name, '-o', fbin]
```

其中，`DISABLE_PTXAS_OPT=1` 可关闭大部分优化（等价于 `--opt-level 0`），`PTXAS_OPTIONS` 可携带 `--opt-level` 等更多选项。

## LLVM 怎么生成对象文件

编译的最后一步是生成可执行的二进制。对 NVIDIA 来说，这分两步：

1. LLVM NVPTX 后端生成 PTX 汇编
2. ptxas 把 PTX 装配成 cubin

在 Triton 里（`backend/compiler.py`）：

```text
# 翻译产生 PTX
ptx = llvm.translate_to_asm(llvm_mod, "nvptx64-nvidia-cuda", ...)

ptxas_cmd = [
    ptxas_path,
    "--gpu-name=sm_" + str(capability),
    "-v",
    "--regAllocOptLevel=2",
    "-o", cubin_path,
    ptx_path
]
```

PTX 是 NVIDIA 定义的虚拟指令集，可以跨 GPU 代际。cubin 是最终的机器码，只能在特定架构上运行。ptxas 做的事情包括：

- 把 PTX 指令翻译成 SASS（真正的机器码）
- 寄存器分配（PTX 用虚拟寄存器，SASS 用物理寄存器）
- 指令调度
- 生成 ELF 格式的 cubin，包含代码段、元数据、调试信息

cubin 里的元数据很重要：

```text
.nv.info:
    kernel: my_kernel
    regs: 48
    smem: 8192
    bar: 1
```

运行时靠这些信息配置 kernel 启动参数。

AMD 那边不用 ptxas，LLVM AMDGPU 后端直接生成 amdgcn 汇编，再装配并用 lld（或等价工具）链接成 hsaco。Triton AMD 后端的对应实现如下（`amd/backend/compiler.py`）：

```text
# amd/backend/compiler.py

def make_llir(...):
    # MLIR LLVM dialect → LLVM IR（LLVM），并附加 AMDGPU 目标三元组/数据布局
    llvm_mod = llvm.to_module(mod, context)
    amd.attach_target_triple(llvm_mod)
    llvm.attach_datalayout(llvm_mod, amd.TARGET_TRIPLE, options.arch, target_features)
    ...

@staticmethod
def make_amdgcn(src, metadata, options):
    amdgcn = llvm.translate_to_asm(src, amd.TARGET_TRIPLE, options.arch, features, flags, options.enable_fp_fusion, False)
    return amdgcn

@staticmethod
def make_hsaco(src, metadata, options):
    hsaco = amd.assemble_amdgcn(src, options.arch, target_features)
    amd.link_hsaco(tmp_in.name, tmp_out.name)
    return ret

def add_stages(self, stages, options, language):
    stages["llir"] = lambda src, metadata: self.make_llir(src, metadata, options)
    stages["amdgcn"] = lambda src, metadata: self.make_amdgcn(src, metadata, options)
    stages["hsaco"] = lambda src, metadata: self.make_hsaco(src, metadata, options)
```

此外，AMDGPU 路径还通过函数属性向后端提供 occupancy/调度提示（`amd/backend/compiler.py`）：

```text
# 设置 kernel 属性（amdgpu-flat-work-group-size / waves-per-eu / sched-strategy 等）
fns = [fn for fn in llvm_mod.get_functions() if not fn.is_declaration()]
fns[0].set_calling_conv(amd.CALLING_CONV_AMDGPU_KERNEL)
fns[0].add_fn_attr("amdgpu-flat-work-group-size", f"1,{options.num_warps*options.warp_size}")
if "memory-bound-attention" in options.schedule_hint.split(','):
    fns[0].add_fn_attr("amdgpu-sched-strategy", "iterative-ilp")
fns[0].add_fn_attr("uniform-work-group-size", "true")
fns[0].add_fn_attr("amdgpu-waves-per-eu", f"{options.waves_per_eu}, {options.waves_per_eu}")
```

调试信息的生成也走 LLVM 的基础设施。Triton 在 MLIR 层面构建调试信息，导出到 LLVM IR 后带上 debug metadata，最终生成的 cubin/hsaco 里就有行号映射和变量信息：

```text
// lib/Target/LLVMIR/LLVMDIScope.cpp
auto funcDI = builder.createFunction(
    compileUnitAttr,
    funcOp.getName(),    // 函数名
    linkageName,
    fileDI,              // 源文件
    lineNo,              // 行号
    ...
);
```

有了这些信息，nsight compute 可以把性能数据关联到源代码行，告诉我们第 42 行访存效率低或第 56 行 bank conflict。

## 为什么 GPU 离不开 LLVM（或等价物）

总结一下，LLVM（加上 ptxas）在 GPU 编译链里做的事情：

| 能力 | 说明 | 为什么 GPU 需要 |
| --- | --- | --- |
| 寄存器分配 | 把虚拟寄存器映射到物理寄存器 | 寄存器用量直接决定 occupancy，溢出代价极高 |
| 指令选择 | 把 IR 操作映射到目标指令 | Tensor Core、TMA、mbarrier 等需要特定指令，不同架构形态不同 |
| 指令调度 | 重排指令隐藏延迟 | 访存延迟几百周期，必须用计算指令盖住 |
| 对象生成 | 生成可加载的二进制 | cubin/hsaco 要符合驱动的加载格式，要带元数据和调试信息 |

这些能力缺一不可。如果我们想自己写一个 GPU 编译器，不走 LLVM，我们得自己实现：

- 一个寄存器分配器，支持 GPU 的物理寄存器约束
- 一个指令选择器，覆盖 PTX/amdgcn 的所有指令
- 一个指令调度器，理解 GPU 的微架构
- 一个目标代码生成器，生成正确的 cubin/hsaco

这是巨大的工程量，而且要跟着 GPU 代际更新维护。LLVM 社区和 NVIDIA/AMD 已经做了这些工作，用 LLVM 是最务实的选择。

Vulkan/SPIR-V 路径是个例外。走 SPIR-V 可以不用 LLVM，但最后一公里的工作并没有消失，只是转移到了 GPU 驱动里。驱动有自己的编译器后端，做寄存器分配、指令选择、调度这些事。用户看不到，但活儿还是得有人干。

接下来看 NPU 那边。LLVM 做的这些事情，为什么在 NPU 编译链里不需要（或者说，以完全不同的形式存在）。

## NPU 为什么不需要 LLVM 这一步

前面讲了 LLVM 在 GPU 编译链里干的四件事：寄存器分配、指令选择、指令调度、对象生成。这一节来看看，这四件事在 NPU 编译链里是怎么回事。

结论先放这里：不是 NPU 不需要解决这些问题，而是问题的形态变了，解决方式也变了。用三个词概括：**缺席**、**替代**、**前移**。

## 缺席：通用寄存器分配和可链接对象

### 寄存器分配为什么可以缺席

GPU 编译器对寄存器分配如此重视，是因为寄存器用量直接决定 occupancy，occupancy 直接影响延迟隐藏能力。寄存器溢出的代价是访问 local memory，延迟从几个周期变成几百个周期。

NPU 的情况完全不同。

NPU 的计算单元（Cube Unit、Vector Unit）内部确实有寄存器，但这些寄存器对编译器来说是不可见的，或者说只在很有限的范围内可控。NPU 的编程模型不是给每个线程分配寄存器，而是告诉硬件搬什么数据、做什么计算。

更重要的是，NPU 的性能瓶颈不在寄存器。回顾一下 NPU 的执行模型：

```text
GM (全局内存)
    ↓ DMA
UB (Unified Buffer, 片上缓存)
    ↓
Cube / Vector Unit (计算)
    ↓
UB
    ↓ DMA
GM
```

性能瓶颈在哪里？

1. **UB 容量**：工作集必须塞进 UB，UB 装不下就得切更小的 tile，tile 太小计算效率低。
2. **DMA 带宽**：数据搬运的速度限制了计算的吞吐。
3. **流水效率**：DMA 和 Compute 能不能重叠起来，流水有没有气泡。

计算单元内部的寄存器使用对整体吞吐的影响是边际性的。一个 GEMM kernel，如果 UB 规划得好、流水编排得好，吞吐主要取决于数据能多快喂给计算单元，而不是计算单元内部寄存器怎么分配。

所以 NPU 编译链的主链上，没有一个独立的通用寄存器分配 pass。核内部的寄存器管理要么由硬件自动处理，要么由厂商编译器在封闭环境里解决，不暴露给上层。

在 Triton-Ascend 的编译链里，我们找不到任何 `regalloc` 相关的逻辑。对比 Triton GPU 后端：

```text
# GPU: triton/lib/Conversion/TritonGPUToLLVM/AllocateWarpGroups.cpp
# "Set the initial max number of registers. This is needed for PTXAS to cooperate."

# NPU: triton-ascend/ascend/backend/compiler.py
# 没有任何寄存器分配相关的代码
```

### 可链接对象为什么可以缺席

GPU 编译产出 cubin/hsaco，这些是标准的 ELF 格式对象文件，包含：

- 代码段（机器码）
- 符号表（函数名、入口地址）
- 重定位信息（如果有外部依赖）
- 调试信息（行号、变量）
- 元数据（寄存器使用量、共享内存大小）

为什么要这么复杂？因为 GPU kernel 要和 host 代码链接，要被驱动加载，要能被调试器分析，要能被性能工具剖析。通用的对象格式让这些工具链能协同工作。

NPU 不需要这些。

NPU 的产物是命令流或设备二进制，直接被运行时消费。不需要和其他对象链接，不需要符号解析，不需要重定位。运行时拿到二进制后，调用厂商 API 注册，然后执行。

看 Triton-Ascend 的产物处理：

```text
# 片段
return Path(bin_path).read_bytes()
```

就是读一个文件的字节，返回给上层。没有符号表解析，没有段提取，没有重定位处理。

运行时注册的代码（片段：06-code/triton-ascend/ascend/backend/npu_utils.cpp）：

```text
rtDevBinary_t devbin;
devbin.data = kernel;
devbin.length = length;
if (kernel_mode == "aiv") {
    devbin.magic = RT_DEV_BINARY_MAGIC_ELF_AIVEC;
} else {
    devbin.magic = RT_DEV_BINARY_MAGIC_ELF;
}

rtDevBinaryRegister(&devbin, &devbinHandle);
rtFunctionRegister(devbinHandle, func_stub_handle, stubName.c_str(), ...);
```

`rtDevBinaryRegister` 把二进制注册到运行时，`rtFunctionRegister` 注册函数入口。magic 字段告诉运行时这是什么类型的 kernel（纯 Vector 还是 Vector+Cube 混合）。

这个接口和 cubin/hsaco 的加载方式完全不同。GPU 那边是：

```text
// CUDA
cuModuleLoadData(&module, cubin_data);
cuModuleGetFunction(&function, module, "my_kernel");
```

CUDA 驱动会解析 cubin 的 ELF 结构，提取代码段，解析符号表，设置各种元数据。NPU 这边就简单得多，运行时直接消费二进制数据。

调试和性能分析怎么办？NPU 用的是不同的方法：

- 性能分析靠流水时间线（哪个阶段花了多少时间）
- 资源分析靠 UB 占用报告
- 正确性调试靠数据比对和边界检查

不是通过在二进制里嵌入调试信息，而是通过运行时的 profiling 接口和日志。

## 替代：目标指令选择变成核变体选择

GPU 的指令选择是把 IR 操作映射到具体的机器指令：add 用哪条指令，load 用哪条指令，矩阵乘用哪个 mma 变体。指令集是细粒度的，每条指令做一件小事。

NPU 的指令粒度完全不同。

NPU 编程不是写一条一条指令，而是选择核变体和配置参数。比如做矩阵乘：

- 用 Cube Unit 还是 Vector Unit？
- 用 direct 算法还是 im2col？
- tile 大小是多少？
- 输入输出的数据排布是什么？

这些选择比指令选择高一个抽象层次。不是从 100 条指令里选哪一条，而是从几种实现策略里选哪一种。

在 Triton-Adapter 里，核类型的选择是这样做的：

```text
// 片段（TritonToLinalgPass.cpp）
kernelMixMode = existDot ? "mix" : "aiv";
funcFunc->setAttr(kernelMixModeName, builder.getStringAttr(kernelMixMode));
```

如果 kernel 里有 `tt.dot`（矩阵乘操作），就标记为 `mix` 模式，意味着要用 Cube Unit；如果只有向量操作，就标记为 `aiv`（All In Vector），只用 Vector Unit。

这个标记传递到厂商编译器，影响代码生成策略：

```text
# 片段
if npu_compiler_path.endswith("bishengir-compile"):
    _compile_option_list += [
        "--enable-hfusion-compile=true",
        "--enable-triton-kernel-compile=true"
    ]
```

tile 策略也是通过选项配置的：

```text
# 片段
if opt.tile_mix_vector_loop is not None:
    _compile_option_list.append(f"--tile-mix-vector-loop={opt.tile_mix_vector_loop}")
if opt.tile_mix_cube_loop is not None:
    _compile_option_list.append(f"--tile-mix-cube-loop={opt.tile_mix_cube_loop}")
```

`--tile-mix-vector-loop` 控制 Vector 回路的 tile 大小，`--tile-mix-cube-loop` 控制 Cube 回路的 tile 大小。

这和 GPU 的指令选择有本质区别：

| GPU 指令选择 | NPU 核变体选择 |
| --- | --- |
| 从指令集里选具体指令 | 从实现策略里选核变体 |
| 粒度是单条指令 | 粒度是整个算子或算子子图 |
| 约束是指令合法性（操作数类型、对齐等） | 约束是资源适配性（UB 够不够、数据排布对不对） |
| 由 LLVM 后端完成 | 由厂商编译器完成 |

厂商编译器内部可能也有指令选择的过程，但那是在更低的抽象层，对上层不可见。上层只需要告诉它我要做矩阵乘，输入是这个形状，用这种 tile 策略，具体怎么生成硬件指令是厂商编译器的事。

命令流生成是另一个差异点。GPU 产出的是一条条机器指令，CPU 那边 launch kernel，GPU 按指令序列执行。NPU 产出的是命令流，包含：

- DMA 命令（从哪里搬到哪里，多大，什么步幅）
- 计算命令（调用哪个核，什么参数）
- 同步命令（等待哪个事件，发送哪个信号）

这些命令的粒度比机器指令大得多，每条命令可能对应硬件上的一整个动作。

## 前移：指令级调度变成流水编排

GPU 的指令调度是在机器指令层面做的：把这条 load 提前，让后面的 compute 不用等；把这两条独立的 add 并行发射。调度器要理解每条指令的延迟、依赖、资源占用。

NPU 不在指令级别做调度，而是在阶段级别做流水编排。

回顾 NPU 的执行模型：

```text
Stage 1 (Load):    DMA 把数据从 GM 搬到 UB
Stage 2 (Compute): 计算单元处理 UB 里的数据
Stage 3 (Store):   DMA 把结果从 UB 搬回 GM
```

三个阶段可以流水起来：当 Compute 在处理第 i 块数据时，Load 在搬第 i+1 块，Store 在写第 i-1 块的结果。这是宏观的流水，不是指令级的。

实现流水需要：

1. **多缓冲**：UB 要分成多段，让不同阶段操作不同的段
2. **屏障同步**：Load 完成后通知 Compute 可以开始，Compute 完成后通知 Store 可以开始
3. **正确的时序**：屏障不能太早（数据没就位就开算），也不能太晚（流水断了白等）

这些决策在编译时就要做好，不是运行时动态调度。

在 Triton-Ascend 里，流水相关的选项很多：

```text
# 片段
# 计算-访存均衡
if opt.enable_hivm_auto_cv_balance is not None:
    _compile_option_list.append(
        f"--enable-hivm-auto-cv-balance={str(opt.enable_hivm_auto_cv_balance).lower()}")

# 图级同步求解
if opt.enable_hivm_graph_sync_solver is not None:
    _compile_option_list.append(
        f"--enable-hivm-graph-sync-solver={str(opt.enable_hivm_graph_sync_solver).lower()}")
```

`--enable-hivm-auto-cv-balance` 让编译器自动平衡 Compute 和 Vector 的工作量，避免一方空等另一方。

`--enable-hivm-graph-sync-solver` 启用图级别的同步求解。什么意思？kernel 里有多个操作，形成一个数据流图。每个操作可能涉及 DMA、Cube、Vector 不同的硬件单元。编译器要分析这个图，找出最小的屏障集合，保证正确性的同时最大化流水。

屏障相关的选项更细：

```text
# 片段
# 单元级屏障
if opt.enable_hivm_unit_flag_sync is not None:
    _compile_option_list.append(...)

# 全局屏障注入
if opt.enable_hivm_inject_barrier_all_sync is not None:
    _compile_option_list.append(...)

# block 级屏障
if opt.enable_hivm_inject_block_all_sync is not None:
    _compile_option_list.append(...)

# 禁用自动屏障
if opt.disable_auto_inject_block_sync is not None:
    _compile_option_list.append(...)
```

这些选项控制屏障注入的粒度和策略。不同的 kernel、不同的硬件版本，最优的屏障策略可能不同。

Adapter 层也做了大量的前移工作。比如 HIVM pass 把 Triton 的同步语义转换成 HIVM 方言（`TritonToHIVM/TritonToHIVM.cpp`）：

```text
rewriter.create<hivm::SyncBlockSetOp>(
    loc, coreAttr, prodPipe, consPipe, rewriter.getIndexAttr(id));
rewriter.create<hivm::SyncBlockWaitOp>(
    loc, coreAttr, prodPipe, consPipe, rewriter.getIndexAttr(id));
```

`SyncBlockSetOp` 发送同步信号，`SyncBlockWaitOp` 等待同步信号。`prodPipe` 和 `consPipe` 指定生产者和消费者是哪个管道（MTE 是访存管道，FIX 是计算管道）。`coreAttr` 指定核类型（VECTOR 或 CUBE）。

这些信息在 MLIR 层面就显式表达出来了，不是等到厂商后端再去推断。后端拿到这些信息后，可以更高效地生成命令流。

多缓冲的控制也是前移的：

```text
# 片段
if metadata.multibuffer:
    _compile_option_list.append("--enable-auto-multi-buffer=true")
```

`metadata.multibuffer` 是上层（可能来自 autotune）决定的，传给厂商编译器让它生成多缓冲的代码。

把这个和 GPU 的指令调度对比：

| GPU 指令调度 | NPU 流水编排 |
| --- | --- |
| 粒度是单条指令 | 粒度是阶段（Load/Compute/Store） |
| 目标是填满发射端口、隐藏单条指令延迟 | 目标是让多个阶段重叠、隐藏 DMA 延迟 |
| 基于指令依赖图和延迟模型 | 基于数据流图和屏障约束 |
| 由 LLVM 后端 / ptxas 完成 | 由 MLIR pass + 厂商编译器完成 |
| 运行时硬件也参与动态调度（warp 切换） | 运行时按命令流顺序执行，调度完全静态 |

## 为什么说前移而不是不需要

有个常见的误解：NPU 编译比 GPU 简单，因为不需要做那些复杂的后端优化。

这是错的。

NPU 编译不是更简单，是优化的位置不同。GPU 把很多优化放在后端（LLVM + ptxas），是因为那些优化需要目标机器的精确信息（寄存器数量、指令延迟、发射端口）。NPU 把优化前移到 MLIR 层，是因为 NPU 的性能关键在数据流级别，在 MLIR 层能看到完整的数据流图，做全局优化。

举个例子：多缓冲深度的选择。

GPU 不太需要在编译器里决定用几重缓冲，因为 GPU 靠 warp 切换藏延迟，寄存器和共享内存的分配由后端处理。

NPU 必须在编译时决定多缓冲深度。双缓冲意味着 UB 里同时存两份数据，三缓冲存三份。深度越深流水越满，但 UB 占用也越多。这个决策需要知道：

- kernel 的数据流结构（哪些数据要缓冲）
- UB 的总容量
- 每个 tile 的大小
- DMA 和 Compute 的相对速度

这些信息在 MLIR 层都有，在目标后端反而看不清楚（因为已经降级到更低的抽象）。所以优化要前移。

Triton-Ascend 的 Adapter pass 串就是在做这个前移：

```text
# 片段
cmd = [
    "--discrete-mask-access-conversion",  # 处理不规则访存
    "--triton-to-unstructure",            # 结构化
    "--bubble-up-operation",              # 算子上浮
    "--triton-to-hivm",                   # 同步语义
    "--triton-to-hfusion",                # 融合语义
    "--triton-to-linalg",                 # 数据通路
]
```

每个 pass 都在为后端准备信息：

- `discrete-mask-access-conversion`：告诉后端哪些访存是离散的，需要特殊处理
- `triton-to-unstructure`：把不规则访存转成结构化形式，方便后端生成 DMA 命令
- `bubble-up-operation`：把算子上移，靠近访存，增大融合空间
- `triton-to-hivm`：显式表达同步语义，让后端知道屏障怎么插
- `triton-to-hfusion`：标记可融合的算子，让后端做算子融合
- `triton-to-linalg`：统一数据通路抽象，方便后端 bufferize

这些工作在 GPU 编译链里不需要做（或者在更早的阶段做），因为 GPU 后端自己能处理。NPU 编译链必须在 MLIR 层把这些信息准备好，厂商编译器才能生成高效的命令流。

## 小结：缺席、替代、前移

把 LLVM 的四个核心能力和 NPU 编译链对照：

| LLVM 能力 | 在 NPU 编译链的状态 | 说明 |
| --- | --- | --- |
| 寄存器分配 | 缺席 | NPU 性能瓶颈不在寄存器，核内部寄存器管理由硬件/厂商后端封装 |
| 目标指令选择 | 替代 | 变成核变体选择 + 命令流生成，粒度更粗，抽象更高 |
| 指令级调度 | 前移 | 变成 DMA-Compute 流水编排，在 MLIR 层完成 |
| 对象生成 | 缺席 | 产物是命令流/设备二进制，由运行时直接消费，不需要通用对象格式 |

这就是为什么 NPU 编译链的主路径上没有 LLVM：不是因为 NPU 简单到不需要优化，而是因为 NPU 的优化问题形态不同，LLVM 擅长解决的问题在 NPU 上要么不存在（缺席），要么以完全不同的方式解决（替代），要么在更高的抽象层解决（前移）。

## 总结：编译链跟着硬件走

回到开头的问题：为什么 GPU 编译链要过 LLVM，而 NPU 不需要？

答案不是某个团队的技术选型，而是硬件执行模型的必然结果。

## 核心结论

GPU 是指令流驱动的 SIMT 机器。每个线程执行一条条机器指令，warp 锁步，靠 warp 切换藏延迟。性能瓶颈在寄存器（决定 occupancy）、目标指令（tensor core/TMA 得用对）、指令调度（填满发射端口）。这些问题的解法是：把高层 IR 精确落成目标机器指令，在寄存器分配、指令选择、指令调度上做到位。LLVM 正好擅长这些，所以 GPU 编译链几乎都落到 LLVM 上。

NPU 是命令流驱动的数据流机器。没有线程的概念，执行单位是搬数据、算、写回的阶段。靠 DMA 和 Compute 的流水重叠藏延迟，靠多缓冲让流水跑起来。性能瓶颈在 UB 容量（工作集得塞进去）、流水编排（阶段得重叠起来）、屏障（同步得够但不能过）、核变体（选对实现策略）。这些问题在 MLIR 层就得解决，等到目标后端就太晚了。所以 NPU 编译链的优化前移到 MLIR，产物是命令流而不是机器指令序列，不需要过 LLVM。

用一张表总结：

| 维度 | GPU | NPU |
| --- | --- | --- |
| 执行模型 | SIMT 指令流，warp 锁步 | 命令流驱动，阶段式流水 |
| 延迟隐藏 | warp 切换 + 指令级调度 | DMA-Compute 流水 + 多缓冲 |
| 核心资源 | 寄存器、共享内存 | UB（Unified Buffer） |
| 性能关键 | 寄存器分配、指令选择、指令调度 | UB 规划、流水编排、屏障求解 |
| 优化位置 | 后端（LLVM + ptxas） | 前端（MLIR + 厂商编译器） |
| 产物形态 | 机器指令序列（cubin/hsaco） | 命令流（设备二进制） |
| 运行时接口 | 驱动加载对象文件 | 运行时注册二进制 |

## LLVM 的四个能力在 NPU 上的状态

把 LLVM 做的事情逐个对照：

**寄存器分配**：在 NPU 上**缺席**。NPU 的性能瓶颈不在核内部的寄存器，而在 UB 和 DMA 带宽。核内部的寄存器管理由硬件或厂商后端封装，不暴露给上层编译器。

**目标指令选择**：在 NPU 上被**替代**。GPU 是从指令集里选具体指令，粒度是单条指令。NPU 是从实现策略里选核变体，粒度是整个算子。不是选哪条 load 指令，而是用 Cube 还是 Vector，用 direct 还是 im2col。

**指令级调度**：在 NPU 上被**前移**。GPU 在机器指令层面重排指令，藏住访存延迟。NPU 在 MLIR 层面编排 Load/Compute/Store 三个阶段的流水，靠多缓冲和屏障实现重叠。调度的粒度从指令变成了阶段。

**对象生成**：在 NPU 上**缺席**。GPU 产出符合 ELF 格式的 cubin/hsaco，带符号表、调试信息、元数据，可以被通用工具链处理。NPU 产出命令流或设备二进制，由运行时直接消费，不需要通用对象格式。

## 两条编译链的完整对照

### GPU 编译链（以 Triton + CUDA 为例）

```text
Python Kernel
    ↓
Triton AST → TTIR
    ↓ [高层优化：combine, CSE, LICM, loop_unroll]
TTIR
    ↓ [GPU 映射：线程块、warp、共享内存、向量化]
TritonGPU IR
    ↓ [目标语义注入：maxnreg, reqntid, tensor core intrinsic]
NVVM 方言
    ↓ [桥接到 LLVM]
LLVM dialect → LLVM IR
    ↓ [LLVM 优化：O3]
LLVM IR
    ↓ [目标代码生成]
PTX
    ↓ [ptxas：寄存器分配、指令调度、装配]
cubin
    ↓ [驱动加载]
执行
```

关键点：

- 后半段（LLVM IR → cubin）是最后一公里
- ptxas 做真正的寄存器分配和指令调度
- 产物是可链接的对象文件

### NPU 编译链（以 Triton-Ascend 为例）

```text
Python Kernel
    ↓
Triton AST → TTIR
    ↓ [高层优化：combine, CSE, LICM, loop_unroll]
TTIR
    ↓ [Adapter：结构化、标注、同步语义、方言转换]
    --discrete-mask-access-conversion
    --triton-to-annotation
    --triton-to-unstructure
    --triton-to-hivm
    --bubble-up-operation
    --triton-to-linalg
    ↓
MLIR（Linalg/HIVM）
    ↓ [厂商编译器：UB 规划、流水生成、屏障求解、核变体选择]
bishengir-compile / npuc
    ↓
设备二进制 / 命令流
    ↓ [运行时注册]
rtDevBinaryRegister + rtFunctionRegister
    ↓
执行
```

关键点：

- 最后一公里在 Adapter + 厂商编译器
- 没有 LLVM IR，没有 llc，没有 ptxas
- 产物是命令流，由运行时直接消费

## 最后

GPU 和 NPU 编译链的差异，本质上是硬件执行模型差异在编译器层面的投影。

GPU 是通用指令流机器，性能关键在微观的寄存器和指令级并行，需要后端做精细的资源分配和调度，LLVM 正好擅长这个。

NPU 是专用数据流机器，性能关键在宏观的 UB 规划和阶段式流水，需要在高层 IR 做全局的数据流编排，这是 LLVM 不擅长也不该做的。

不是 NPU 不需要优化，而是 NPU 的优化问题形态不同，需要在不同的位置用不同的方法解决。

理解了这一点，GPU 和 NPU 的编译链设计就不再神秘：跟着硬件走，把优化放在正确的位置，用正确的方法解决正确的问题。
