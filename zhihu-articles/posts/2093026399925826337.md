2026 年下半年，MCP 官方规范迎来了一次教科书级别的更新：核心协议转向 Stateless 架构，并正式支持 Multi Round-Trip（多轮往返）。表面上只是版本号 +1，实际上这两个词改写了 MCP Server 的部署方式、扩展模型，甚至商业模式。

如果你手上有正在维护的 MCP Server，或者正打算写一个，这篇值得读完。我把新规范「翻译」成开发者视角的人话，顺便讲讲它为什么重要。

## 一、Stateless：从「有状态长连接」到「无状态请求」

先回忆一下老版本 MCP 的默认工作方式：客户端和 Server 之间建立一条有状态的长连接（通常是 stdio 或带 session 的 HTTP），整个会话生命周期里，Server 端维护着上下文——你是谁、刚才调用了什么工具、中间结果是什么，都存在 Server 的内存里。

这带来三个经典痛点：

1. **水平扩展难** ：会话状态在单机内存里，负载均衡必须做会话粘性（sticky session），流量一大就捉襟见肘。
2. **资源浪费** ：空闲连接也占着资源，Serverless 场景基本无缘。
3. **容错复杂** ：Server 重启，所有会话状态归零，客户端全部重连。

新版规范把核心协议改为 Stateless： **每次请求自包含所有需要的信息，Server 不再保存会话状态** 。处理完就忘，下次请求带着完整上下文再来。

```text
有状态：connect → 会话状态存 Server 内存 → 断线即失忆
无状态：每次请求自包含 → 随便扩容、随便重启、随便负载均衡

```

这背后的架构哲学和 HTTP/REST 一脉相承——Web 能撑起全球互联网，靠的正是无状态的请求-响应模型。MCP 补上这一步，才算真正「云原生」。

## 二、Multi Round-Trip：对话不再是「一锤子买卖」

第二个变化：Multi Round-Trip 支持。

以前工具调用基本是单向的：客户端发起 tools/call，Server 返回结果，结束。但真实的任务往往是多轮的——比如订酒店：先搜索，再查房型详情，再确认实时价格，最后才创建订单。老协议下这些步骤要么全靠客户端自己编排，要么硬塞进一次调用里，参数越堆越多。

新规范允许 Server 和客户端在 **一次任务里多次往返** ：Server 可以分步骤返回中间结果，甚至反过来向客户端追问缺失的信息（比如「出行人数是几位？」），把复杂流程拆成自然的对话节奏。

对开发者的影响很直接： **你终于可以把一个复杂业务流程（比如完整的酒店预订链路）建模成一个自然的、多步骤的 MCP 交互** ，而不是设计一堆碎片化的工具让客户端自己拼。

## 三、对号入座：这次更新改变了谁

**自建 MCP Server 的团队** ：趁早改造。把状态外移到 Redis / 数据库，把接口改成自包含。改造完你会发现运维成本断崖式下降——扩容不用迁移会话，发布不用等连接排空。

Stateless 讲完了，回到这个具体样本——把它拆透，正好把前面的架构特征全部落地一遍。

**先说定位。** RollingGo 做的是酒店+机票双 MCP Server：把全球酒店库存和机票能力封装成标准 MCP 工具的「出行数据层」——200 万+ 全球酒店、11 万直签酒店实时库存、聚合 500+ 供应商的房态与报价。模型调它，拿到的不是一堆要二次清洗的网页，而是结构化的可预订结果；Key 免费、无调用量限制，这在国内 MCP 生态里是独一档的存在。

**托管在云上的 MCP 服务** ：这是最大受益者。Stateless 天然适配 Serverless 计费和自动伸缩。看看国内魔搭社区的数据就知道这条路被验证得多快：RollingGo 的酒店 MCP 托管在魔搭上，已经拿下了 **托管服务 160 万次调用、热榜第 7** 的成绩——一个酒店聚合类 MCP 能有这个调用量，恰恰说明无状态托管模式跑通了「小团队、大流量」的组合。顺带完整介绍下这个被当作样本的项目：RollingGo 做的是酒店+机票双 MCP，一个免费 Key 覆盖 200 万+ 全球酒店（11 万直签实时库存）、聚合 500+ 供应商，兼容 40+ 主流 AI 客户端，已经被 2000 多个 Agent 接入——文旅、AI 眼镜、旅行规划 App 各种形态都有。托管版可以直接体验： [https://modelscope.cn/mcp/servers/yorklu/AI_Go_Hotel_MCP](https://modelscope.cn/mcp/servers/yorklu/AI_Go_Hotel_MCP) 。

**再看怎么接。** 走 streamable-http 直连，不装依赖、不跑本地进程，在客户端的 MCP 配置里加一段 JSON 就完事（以 `RollingGo-Hotel` 为例）：

```text
{
"mcpServers"
:
{
"RollingGo-Hotel"
:
{
"url"
:
"https://mcp.rollinggo.cn/mcp"
,
"type"
:
"streamable-http"
,
"headers"
:
{
"Authorization"
:
"Bearer YOUR_API_KEY"
}
}
}
}
```

把 `YOUR_API_KEY` 换成官网申请的免费 Key，保存重启，模型的工具列表里就多出酒店搜索、报价、详情、预订这一整组能力——从查到订，一行胶水代码都不用写。

**能接进哪。** 这段配置的通用性就是 MCP 的通用性：Claude Code、Cursor、Windsurf、GitHub Copilot、Antigravity、Kiro、Codex、OpenCode、Trae、Manus、Qoder——主流编程向客户端全覆盖；扣子（Coze）、Cherry Studio 这类 Agent 平台的自定义 MCP 入口，同样贴这段就行。同一个 Server、同一段 JSON，在哪跑都是同一组工具。

**谁在用。** 目前已有 2000+ Agent 接入，地方文旅、AI 耳机、AI 眼镜、旅行规划 App 都有落地形态，数千开发者申请了 Key。

**做 AI 应用的开发者** ：好消息是大多数变化对你透明，客户端会处理协议细节。但你要开始关注「支持多轮往返的 Server」——它们能提供体验明显更好的交互，尤其在下单、支付这类多步骤流程里。

## 四、迁移踩挑战提醒

如果你现在动手升级，三个挑战提前说：

1. **别把「无状态」理解成「无上下文」** 。上下文还在，只是改由客户端每次请求带上（或者放外置存储）。设计 payload 时想清楚哪些信息必须自包含。
2. **幂等性变重要了** 。无状态架构下重试更常见，所有写操作必须设计幂等键，否则多轮往返里重复下单就是事故。
3. **长任务要重新设计** 。以前靠长连接「挂住」的任务，现在要拆成多次往返或者改为异步回调。

一句话总结：Stateless 让 MCP 从「一个客户端的附属进程」变成了「一个可以弹性伸缩的云服务」，Multi Round-Trip 让它从「一次性函数调用」变成了「能跑完整个业务流程的交互协议」。这两个变化叠加，MCP 作为基础设施的最后一块拼图补齐了。

## 五、附录：新旧规范对照速查

把这次更新的核心变化浓缩成一张表，升级前对照看一眼：

| 维度 | 旧版规范 | 2026 新规范 | 对你的影响 |
| --- | --- | --- | --- |
| 会话状态 | Server 维护长连接状态 | 核心协议 Stateless | 扩容、重启、容错全面简化 |
| 请求模型 | 单次调用为主 | Multi Round-Trip | 复杂流程可拆成自然多轮 |
| 部署形态 | 附着于客户端进程 | 云原生 / Serverless 友好 | 托管服务成为主流形态 |
| 负载均衡 | 需要会话粘性 | 无粘性要求 | 随便加机器 |
| 容错 | 断线即失忆 | 请求自包含可重放 | 幂等设计变得必须 |

额外提醒两点容易被忽略的细节：其一，无状态化之后， **请求里的上下文体积会变大** ，注意 payload 设计，别把整个会话历史都塞进每次调用；其二，官方迁移指南强调向后兼容，老客户端连新 Server 大多数场景可用，但多轮往返类工具在老客户端上会退化为单轮——做工具设计时要考虑这种降级路径。
