随着开源基础模型在通用能力上日趋成熟，工程实践的关注点正从"是否需要微调"转向"应当采用何种微调策略"。

SFT（Supervised Fine-Tuning，监督微调）作为大模型训练流程中的标准环节，已被广泛采用。然而，在真实业务场景中，仅依赖 SFT 难以满足生产环境的全部要求。

本文系统梳理 SFT 之后仍需进一步微调的原因、当前主流的微调方法体系，以及典型应用场景，为工程实践提供参考。

### **一、SFT 与微调的概念澄清**

在工程语境中，"微调"（Fine-Tuning）是一个总称，SFT 仅是其中最基础的一种实现方式。完整的微调技术体系至少包含以下方法：

```text
微调（Fine-Tuning）
├── SFT（Supervised Fine-Tuning）— 指令对齐
├── LoRA / QLoRA — 参数高效微调
├── Prefix Tuning / Prompt Tuning — 输入侧适配
├── RLHF — 基于人类反馈的强化学习对齐
└── DPO / ORPO — 直接偏好优化
```

因此，问题的核心不在于"是否需要进一步微调"，而在于 **根据具体业务约束（数据规模、算力资源、效果目标）选择最适配的微调方案** 。

### **二、为什么 SFT 之后仍需继续微调？**

SFT 主要解决"模型对人类指令的响应能力"问题，但在以下四个维度上存在明显局限。

**1. 领域知识深度不足**

通用基础模型的预训练语料中，医疗、法律、金融等垂直领域的内容占比通常不足 5%。即便经过 SFT，模型在专业术语理解、领域推理链构建等方面仍与领域专家存在显著差距。

**领域微调的目标：构建具备深度专业能力的垂直模型。**

**2. 输出风格与个性化需求不匹配**

SFT 训练后的模型输出通常呈现"通用助手"风格——表达规范、态度中立、措辞保守。在需要特定特征（如企业品牌、个人风格）的场景中，需要通过风格微调实现差异化表达。

**3. 特定任务能力上限受限**

SFT 能让模型"理解任务"，但对特定任务（如合同审查、表格抽取、代码评审）的准确率提升存在上限。任务专项微调可将该上限从 70% 提升至 90% 以上。

**4. 幻觉问题未根本解决**

SFT 仅优化"指令-回答"的映射关系，并未直接约束模型的"认知边界"。要实现"知之为知之"的对齐效果，需要引入 RLHF 或 DPO 等对齐微调方法。

> **"SFT 解决的是'能不能用'，后续微调解决的是'用得多好'。"**

### **三、六种主流微调方法**

### **① 全参数微调（Full Fine-Tuning, FFT）**

对模型全部参数进行更新。

- **优点** ：效果上限最高
- **缺点** ：计算与存储成本极高，训练需数十张 A100/H100 级 GPU
- **典型场景** ：头部厂商的旗舰模型迭代

### **② LoRA（Low-Rank Adaptation）**

在 Transformer 层的权重矩阵上引入低秩分解矩阵，仅训练新增的少量参数（通常 0.1%–1%），原始参数保持冻结。

- **优点** ：显存需求降低约一个数量级
- **缺点** ：效果通常略逊于全参数微调
- **典型场景** ：中小团队、垂直领域适配

### **③ QLoRA**

在 LoRA 基础上引入 4-bit 量化技术，进一步降低显存占用。

- **优点** ：单卡（24GB 显存）即可微调 65B 参数级模型
- **缺点** ：存在轻微的精度损失
- **典型场景** ：算力受限的个人开发者

### **④ Prefix Tuning / Prompt Tuning**

不修改模型参数，仅在输入序列前添加可学习的"软提示"向量。

- **优点** ：参数量极小（0.001% 量级），推理时可忽略不计
- **缺点** ：表达能力存在上限
- **典型场景** ：轻量任务适配、批量场景的快速迭代

### **⑤ RLHF（Reinforcement Learning from Human Feedback）**

通过人类对模型输出的偏好标注训练奖励模型，再以 PPO 等强化学习算法优化语言模型。

- **优点** ：对齐人类偏好的效果最优
- **缺点** ：流程复杂，需大量人工标注与算力投入
- **典型场景** ：ChatGPT、Claude 等 C 端对话产品

### **⑥ DPO（Direct Preference Optimization）**

跳过奖励模型训练阶段，直接利用偏好数据对语言模型进行优化。

- **优点** ：实现简单，训练稳定性高，效果接近 RLHF
- **缺点** ：方法仍在快速演进
- **典型场景** ：希望实现偏好对齐但资源受限的团队

### **四、方法对比**

| 方法 | 可训练参数比例 | 显存需求 | 效果上限 | 工程成本 | 典型应用 |
| --- | --- | --- | --- | --- | --- |
| 全参数微调 | 100% | 极高 | 最高 | 极高 | 旗舰模型 |
| LoRA | 0.1%–1% | 中等 | 高 | 较低 | 垂直领域 |
| QLoRA | 0.1%–1% | 较低 | 高 | 低 | 个人开发者 |
| Prefix Tuning | 0.01% | 极低 | 中 | 极低 | 轻量任务 |
| RLHF | 100% | 极高 | 最高 | 极高 | C 端对齐 |
| DPO | 100% | 高 | 高 | 中 | 偏好对齐 |

### **五、典型应用场景**

**1. 行业垂直化**

针对医疗、法律、金融、政务等高门槛领域，通过领域 SFT + LoRA 构建具备专业资质的垂直模型。典型应用包括辅助诊断、合同审查、研报分析等。

**2. 风格与个性化对齐**

通过风格 SFT 与 DPO，使模型输出符合特定品牌、个人或角色的语言风格与价值取向。典型应用包括数字分身、IP 角色、定制化客服。

**3. Agent 能力构建**

通过 SFT 训练工具调用与任务规划能力，结合 RLHF 强化复杂任务的执行稳定性，支撑 Agent 类应用。

**4. 多模态能力扩展**

在语言模型基础上，通过多模态 SFT 引入视觉、语音、视频理解能力，实现跨模态任务处理。

**5. 推理能力增强**

通过 Chain-of-Thought 微调与 RLHF 训练，提升模型在数学、代码、逻辑推理等高难度任务上的表现。

### **六、微调方案选型框架**

在实际工程中，微调方案的选择应基于以下三个核心约束：

**约束 1：预算规模**

- 充足：可考虑全参数微调或 RLHF
- 中等：推荐 LoRA
- 有限：建议 QLoRA 或 DPO

**约束 2：算力资源**

- 数十张 A100/H100：全参数微调
- 数张 A100：LoRA
- 单卡消费级 GPU：QLoRA
- 无本地算力：建议直接调用 API 能力

**约束 3：业务目标**

- 领域专业性：行业 SFT
- 偏好对齐：RLHF / DPO
- 快速实验验证：Prefix Tuning

> **"微调方案的选择，本质是在效果、成本、稳定性之间寻找平衡点。"**

### **总结**

随着基础模型能力趋同，工程能力的差异将更多体现在 **对模型的二次开发与场景适配** 上。

SFT 是这一过程的起点，而非终点。 **系统掌握 LoRA、QLoRA、RLHF、DPO 等微调方法，是构建可落地大模型应用的关键能力** 。
