> 一句话概括：这篇论文报告了一个反直觉的生产事故——给 vLLM 引擎接上「共享远端 KV 缓存」（LMCache + Valkey）之后，中位 TTFT 毫无变化，但 16k 长 prompt 的 p99 从 3.96 s 飙到 17.3 s。作者用一个两项成本模型解释了原因：远端命中的收益取决于「缓存层交付带宽能否跑赢本机 prefill 速率」，在 8×B300 上这条生死线是 2.53 GB/s；同时存在一个「每命中固定成本」T₀≈0.33 s，导致约 17k token 以下的 prompt 无论带宽多高都不如重算。据此他们把 MLA 的 KV 存储按上下文并行 rank 分片、把远端层按 rank 切成一 rank 一实例（带宽 1.71→10.76 GB/s，6.3×）、补上异步加载并修掉三个客户端 bug，hit-heavy 流的 p99 从 83.32 s 降到 0.67 s（124×）。

## 一、背景：远端 KV 层看起来很美

长 prompt 场景下 prefill 决定 TTFT（time-to-first-token，首 token 延迟）——读一个 20 万 token 的 prompt 即使在新一代加速器上也要好几秒。于是服务系统普遍会缓存历史 prompt 的注意力 KV cache（键值缓存），新请求若共享前缀就直接复用。

一个常见布局是两层：

- **L1（快层）**：每个引擎自己的主机内存；
- **L2（远端层）**：一个所有引擎都能读、且能扛住重启的共享存储。

远端层的诱惑在于：缓存容量与引擎数量解耦，一个引擎算过的 KV 别的引擎也能用。**但它背后有一个隐含假设：加载 KV 一定比重新计算便宜。这篇论文报告的，正是这个假设在生产环境里失效的过程。**

**部署形态。** 论文服务的是 GLM-5.3——一个采用 DeepSeek 式 MLA（Multi-head Latent Attention，多头潜在注意力）的大型 MoE 模型，以 FP8 精度跑在 8 卡 B300 节点上。prefill 与 decode 分离部署：每个 prefill 节点跑一个 vLLM 引擎，prefill 内部按序列切分做上下文并行（PCP8，八卡），各 rank 用集合通信交换 KV、锁步前进。LMCache 把 KV 按 256 token 一块存在主机内存（L1）里，并可选地存进 Valkey 远端存储（L2）。

![](https://pica.zhimg.com/v2-b6dfedfd7b2b89df4de95c90c3580260_1440w.jpg)

图 1：最终系统总览——一个 8×B300 的 prefill 引擎（PCP8 + EP8，各 rank 锁步），每张卡（rank r）拥有自己的 L1 与一份共享的 Valkey 实例 v_r；chunk c 由 rank(c mod 8) 独占负责存、查、取。原始设计把所有 chunk 都从 rank 0 写进单个 Valkey 实例。

## 二、现场：一次「反向优化」

把一个面向企业 SLA 的负载（prompt 长度 9k–200k token）开启 L2 之后，结果是这样的：

| 指标 | 仅 L1 | 开启 L2 |
| --- | --- | --- |
| 16k 中位 TTFT | 不变 | 不变 |
| 16k p99 | 3.96 s | 17.3 s |
| 32k p99 | 6.06 s | 25.0 s |

中位没动，尾巴炸了。于是这次上线被回滚回 L1-only。

作者没有停在「网络慢」这种一句话诊断上，而是重建了生产引擎的原始请求流（从路由日志 + 压测客户端数据库里还原出 SLA 负载 16k 档下该引擎收到的 683 条请求及其原始 prompt 与发送时间），在一台空闲的 8×B300 节点上用与生产完全一致的镜像与配置（vLLM 0.31.0、LMCache 0.5.5、FlashInfer 0.7.0、NCCL 2.30、CUDA 13.0）回放，并用 Nsight Systems + py-spy 剖析，得到三个根因。

## 三、三个根因

### 3.1 命中竟然比未命中还慢

一条 16k token 的 prompt，**重新计算只要 0.31 s，从 L2 加载却要 0.88 s**。这台 B300 节点的 prefill 速率约 52.2k token/s，而 L2 通路交付的带宽远远跟不上这个速率。换句话说：不是网络「慢」，是 GPU 太快——缓存层没能跑赢重算。

### 3.2 同步加载把引擎变成了过载队列

更糟的是加载方式。同步加载意味着一次加载发生在引擎 step 内部，而 PCP 下这会**卡住全部 8 个 rank**（锁步）。于是引擎的行为退化成一个单服务器排队系统，每次命中的服务时间至少是 ns/B。设到达率 λ、每 token 的 KV 字节数 s、带宽 B，则利用率 ρ = λns/B。

在 hit-heavy 回放里 λ = 1.21 请求/s，中位 prompt 的 KV 量约 0.79 GB；单实例实测只撑到 0.78–0.89 GB/s（服务端计数），于是 **ρ ≈ 1.13 > 1**：队列没有稳态，只要命中持续到达它就一直在涨。实测中位延迟在前三分之一从 3.52 s 涨到 52.30 s，引擎里一度同时有 59 条请求，而 **GPU 利用率只有 7%**。

### 3.3 三个客户端 bug 放大了最坏情况

带宽解释了稳定的成本，而三个 bug 解释了最离谱的离群点，它们都会让 GPU 时间线「空掉」：

- **丢完成（lost completion）**：原生客户端的同步方法先提交请求、再注册接收结果的 future，而完成事件在事件循环线程上被消费——两步之间到达的完成会被丢弃，调用方永久阻塞。分片把暴露面乘以 W（每次查询都发给所有 rank），且一次丢失是永久性的：之后每次调度查询都要等满 3 s 超时。生产引擎的日志精确记录了这个现象（某时刻起每路由一次请求就记一次超时，一分钟 16/16），py-spy 显示所有查询线程都阻塞在没有未完成的 `fut.result()` 上。
- **缺失 key 的 GET 永不返回**：RESP 协议里缺值编码为 5 字节的空 bulk string（形如「美元符号 + 负一」）。原生连接器按「一个 chunk 的固定 11 字节头」去读，遇到缺 key 就读不满、连接永久损坏。LRU 淘汰下 chunk 可能正好在 EXISTS 与 GET 之间消失，于是同步加载会卡住全部 rank 长达 10 s。
- **异步 GET 用错了 key**：异步 GET 没有把 key 改写成异步查询所用的 worker-0 名字，导致非 0 rank 找到自己的 chunk 后又去请求不存在的 key。

## 四、成本模型：一条 2.53 GB/s 的生死线

论文的核心洞察浓缩成一个两项模型。设 n 为从缓存命中的 token 数，s 为每 token 的 KV 字节数，R 为引擎 prefill 速率（token/s），B 为缓存层给单个 prompt 的带宽，则

- 重算：T_recompute = n / R
- 加载：T_load = T₀ + n·s / B

其中 T₀ 是「一次命中无论如何都要付、且不随带宽缩小」的固定开销：调度、查询往返、对少数未缓存尾 token 的一次前向、以及每 chunk 的元数据交换与广播。

**盈亏平衡带宽。** 忽略 T₀，命中要划算当且仅当 B > B* = s·R。prompt 长度被约掉了——**阈值只取决于模型的 KV 体积和硬件的 prefill 速度**。对 GLM-5.3 FP8 + B300：s = 48.4 KB/token，R = 52.2k token/s，于是

B* = s·R ≈ **2.53 GB/s**。

而单个 Valkey 实例服务 8 个 PCP rank 时最好只交付 1.71 GB/s（见下节），低于 B*——**每一次 L2 命中都比重算更慢**。

**固定成本。** 当 T₀ > 0，命中要划算需要 n/R > T₀ + ns/B，即至少 n > R·T₀。论文用单点（最快的 8 实例配置，B = 10.76 GB/s）拟合出 T₀ ≈ 0.33 s，由此推得阈值 R·T₀ ≈ 17k token：**在这套硬件与实现上，16k 的 prompt 用 L2 不可能改善中位延迟，只有更长的 prompt 才有收益。** 模型对 16k 命中的预测 0.79 s 也接近实测的 0.83–0.88 s（且这几个点没有用于拟合）。

模型给出的两个杠杆很清楚：**给每个 prompt 交付更多带宽**，以及**在加载慢的时候让引擎继续跑**。

## 五、四个改动

### 5.1 把 MLA KV 存储跨 PCP rank 分片

**rank-0 瓶颈。** 在张量并行下「只从 rank 0 存 MLA KV」是合理的（每个 rank 持有相同的 latent）。但 PCP 下不同：AllGather 之后虽然 latent 也是复制的，可 rank 0 要在 step 内把整段 prompt 的 KV 拷到主机内存，其余 7 个 rank 在下一个集合通信点等它。一次约 20 万 token 双 prompt 的 Nsight 追踪里，rank 0 向主机内存写了 19.1 GB、忙碌度 82%，而其他 rank 98% 忙——每个 rank 在 9.5 s 窗口里累积了约 1.55 s 的 AllGather 等待。

**所有权。** AllGather 之后每个 rank 都握有整段 prompt 的 KV，因此任何 rank 都能存任何 chunk。定义第 c 个 chunk（起始 token 256c）由 rank o(c) = c mod W 拥有；每个 rank 只存/查/取自己的 chunk，L1 也切成 1/W 份，总内存不变。

**查询。** vLLM 调度器本来就把每次查询发给每个 rank 的 lookup server 并取最小值。Proposition 1 证明：在此分片下，各 rank 返回「自己第一个缺失的自有 chunk 起点」的最小值，恰好等于**最长全命中前缀**——即现有的最小值查询无需任何新消息就自动正确。论文还对小规模做了穷举验证（≤10 chunk × W∈{2,3,4,8}，以及最多 800 chunk 的随机 prompt）。

**加载。** 关键是不能让任何 rank 跳过集合通信，否则整个 step 挂死。于是所有 rank 都跑同一套流程（Algorithm 1）：各自取并暂存自有 chunk → 每个 rank 发一条小消息（chunk 列表指纹 + 首个失败 + 元数据）→ 用 W 条消息算出**各 rank 一致**的公共前缀 → 按前缀逐 chunk 从属主广播。本地失败（淘汰、GET 失败、引擎不健康、暂存错误）只通过交换上报，变成「一致地更短的前缀」；输入不一致时指纹不同，公共前缀退化为 0。

### 5.2 按 rank 切分远端层

要提高 B 就得有更多服务线程，也就意味着更多 Valkey 实例。分散 key 通常需要集群协议或客户端一致性哈希——但分片存储已经天然提供了静态分区：rank r 只碰 c mod W = r 的 chunk，且每个引擎的 rank r 拥有相同的 chunk 索引。于是**实例 r 只放 rank r 的 chunk**，无需路由逻辑、实例间零流量、跨引擎复用不丢。客户端改动就一处：远端 URL 里的 `{rank}` 替换成 worker 的 rank（如 `resp://valkey-{rank}:6379`）。

效果（图 3）：单实例从 1 个客户端加到 8 个只提升 13%（都在同一服务线程上排队，一个 rank 的批要 440 ms）；而一 rank 一实例后，聚合带宽升到 **10.76 GB/s（6.3×）**，一个 rank 的批只要 70 ms。

![](https://picx.zhimg.com/v2-653814292a2216f89e035190d4221899_1440w.jpg)

图 3：聚合 GET 带宽（LMCache 原生 RESP 客户端，12.4 MB chunk）——单实例加客户端几乎不涨（1.51→1.71 GB/s），一 rank 一实例达 10.76 GB/s。

### 5.3 分片存储的异步加载

当带宽足够时 ρ ≪ 1，同步加载也跟得上；但异步加载真正的价值是**消除失败模式**：一次慢加载只拖慢它自己的请求，引擎继续服务别人。LMCache 的异步路径原本假设 rank 0 做全部查询，论文把它扩展到分片模式且不新增协议消息：每个 rank 只预取自有 chunk，并给存储层传一个自定义的累积长度向量（第 k 项 = 它第 k 个自有 chunk 的起始 token），于是存储层「连续命中」的答复恰好就是命题里的 aᵣ（以 token 计），调度器取最小值得到与同步路径相同的前缀。论文用 3000 组随机存在性模式做了等价性属性测试，并修掉一个边界：完全没有命中的 rank 原本报 0 token，在分片下是错的（rank 1 首个自有 chunk 缺失时正确答案是 256 token，因为 chunk 0 属于 rank 0）。

### 5.4 三个 bug 各自的修法

- 丢完成：用一把锁覆盖「提交 + 注册 future」与 drain 两个动作；
- 缺 key 的 GET：把头部解析改成读到 CRLF 为止，把这种空 bulk string 当作「该 key 未命中、回复已完整消费」，并让 Python 层释放未填充缓冲而不是当成 KV 返回（实测：删掉一个 key 的 4-chunk GET 现在 69 ms 返回 `[T,T,F,T]`，连接还能在 40 ms 内服务下一次 GET；此前 12 s 都没有完成）；
- 异步 GET：修正 key 改写为 worker-0 名字。

**hit-heavy 流（450 条 16k 请求，L2 预热、L1 清空）。**

| --- | --- | --- | --- | --- | --- |
| H1b 单实例·同步 | 9.70 | 61.17 | 83.32 | 98.5% | 7% |
| H2b 单实例·异步(rank-0) | 3.20 | 3.70 | 3.82 | 50.6% | 28% |

**与重算的剩余差距。** 中位上 H5b 比直接重算慢 0.09 s。其中传输只占 0.074 s（10.76 GB/s 下），其余是 T₀——花在引擎里（调度、未缓存尾部的 forward、每 chunk 的交换与广播），而不是花在 Valkey 上。即使带宽无限大，一次 16k 命中也要约 0.33 s，略高于重算；所以在快 GPU 上，除非 T₀ 变小，它在**中位延迟**上赢不了。但它的**尾部**更好（p99 0.67 s 对 1.28 s），而且命中不消耗 GPU 算力。

**正确性。** 逐位比对不可用（引擎非确定性，两次冷跑同一 prompt 都会给出不同文本）。论文用 6 个 12.8k–166.7k token 的「大海捞针」prompt 做语义测试（冷跑 / L1 异步预取 / 重启后从 L2 加载 / 再冷跑作对照，各用贪心解码），代码在 24/24 个答复里都被找到；缓存答复与冷答复的差异不超过两次冷跑彼此的差异。同步分片存储在 GPU 缓存淘汰后通过 3/3 针，并发突发 36/36，30 分钟 soak 1549 条请求零错误。

## 七、对工程实践的启示

- **拿缓存层和「本机的 prefill 速率」比，而不是和网络延迟比。** B* = s·R 会随加速器一代代提高——GPU 越快，缓存层要跑赢它所必须交付的带宽就越高。在 B300 上这是每 prompt 2.53 GB/s，通用 KV 服务器必须像本文的 rank 分区那样随引擎并行度扩展，或者转向 RDMA 传输。
- **缩短固定成本 T₀。** 0.33 s 意味着这套实现下约 17k token 以下的远端命中在任何带宽下都不划算。论文指出自然的下一步：把每个属主的 chunk 批成一次 AllGather 式集合通信、把交换与取数重叠，以及做一个「按模型预测的加载时间 vs n/R 逐请求比较」的「加载或重算」策略。
- **锁步会放大一切。** PCP 下任何单 rank 的停顿（一个 rank 包办所有存储、一次慢 GET、一次丢完成）都会卡住所有 rank。面向上下文并行的引擎设计应保持各 rank 工作对称，并把任何可能无界阻塞的操作赶出 step。
- **静态分区让 scale-out 免费。** rank 分区能成立，是因为分片存储把所有权固定在 chunk 索引上——任何确定性、rank 本地的放置都具备这个性质。

## 八、局限（作者自述，值得留意）

- **单次运行**：每个条件只跑一次。大效应（p99 的 124×、6.3× 带宽、不稳定队列）远超运行间波动，但 10% 以内的差异（如 H3 对 H4）未确立。
- **仅 prefill、仅单引擎**：回放省略了到 decode 的 KV 交接，且只用了一个引擎作为唯一的 Valkey 客户端；多引擎争用是估计而非实测。
- **单一 prompt 长度桶**：延迟结果针对 14.7k–17.9k token；T₀ 仅由单点拟合，它推出的长度阈值是一个尚未直接测量的预测。
- **端到端对比非同口径**：部署对比里除了缓存层，并行度与 prefill/decode 布局也不同，论文明确把它当作「部署背景」而非上述技术的消融。
