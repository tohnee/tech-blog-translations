## 引子：当数据工程师遇上多模态

做数据的朋友，最近两年应该都有一个共同的感受-你的数据 Pipeline 里，"正经"的结构化数据占比越来越少了。取而代之的是图片、音频、视频、PDF 文档、向量 Embedding...这些东西每一个都比传统的行列数据大几个数量级，处理逻辑也完全不同。

用 Spark 跑个图片分类？executor 内存炸了。用 Pandas 处理百万级 Embedding？单机扛不住。用 Ray Data 搭 Pipeline？一堆参数要手动调，稍不注意就 OOM。

这不是某个工具的锅，而是整个数据工程的技术栈，正在经历一次范式转移—从"以表格为中心"走向"以多模态为中心"。

本文要介绍的 Daft + Ray + Lance 组合，正是这个新范式下一套值得关注的技术栈。它不是一个 all-in-one 的平台，而是三个独立的开源项目，各自解决一层问题，组合起来形成了一条从存储、计算到调度的完整链路。

下面逐一拆解。

## 一、Daft：不是又一个 DataFrame，而是多模态数据引擎

### 1.1 Daft 是什么

Daft 是由 Eventual 公司开源的高性能数据引擎，底层用 Rust 实现，对外提供 Python DataFrame API。它的核心定位不是替代 Pandas 或 PySpark，而是专门为 AI 和多模态工作负载设计的分布式数据引擎。

官方 GitHub 上的定位很直接：High-Performance Data Engine for AI and Multimodal Workloads。

### 1.2 为什么不是 Spark / Pandas / Polars

先说结论：工具没有绝对的好坏，关键看你的数据长什么样。 如果你的数据是百亿行的结构化表，Spark 依然是最稳的选择。如果你的数据在单机内存放得下，Polars 的性能让人印象深刻。但如果你的"行"里面包含的是一张 5MB 的图片、一个 30 秒的音频片段、或者一个 768 维的 Embedding 向量——事情就不一样了。 传统引擎面对多模态数据的核心痛点有三个：

内存管理问题。 一张 JPEG 图片在磁盘上可能只有几百 KB，解码为 RGB Tensor 后膨胀到 20 倍以上。Spark 的执行模型是先把整个 partition 的数据全部物化到内存，再送入下游算子——这意味着 10 万张图片的 partition，解码后会直接把 executor 撑爆。

资源编排问题。 多模态 Pipeline 天然需要 CPU（数据预处理）和 GPU（模型推理）协同工作，而且还有大量网络 I/O（从对象存储下载数据）。Spark 的任务模型假设一个 task 对应一个 core，没有原生的 GPU 编排能力。想在 Spark 上跑 GPU 推理，配置起来是一场噩梦。

API 表达力问题。 多模态处理中大量的自定义逻辑需要通过 UDF 实现，但 Spark 的 Pandas UDF 无法为不同的 UDF 指定不同的资源需求和 batch size——只有一个全局配置 `spark.sql.execution.arrow.maxRecordsPerBatch` ，这对复杂 Pipeline 来说远远不够。

### 1.3 Daft 的技术架构

Daft 的执行引擎叫 Swordfish，是一个流式、推送（push-based）的执行模型。数据以小批次（morsel）的形式在 Pipeline 中流动，上游产出一批就立即推给下游，不需要等整个 partition 处理完毕。

几个关键设计决策：

自适应反压（Backpressure）。 如果下游 GPU 推理成为瓶颈，上游的下载和解码会自动降速，从而控制内存使用量。这不需要用户手动配置，引擎自己会根据运行时状态动态调节 batch 大小。

单 Worker 全机控制。 Daft 的每个 Worker 进程控制整台机器的全部资源（CPU + GPU + 网络），这样它可以在单个 Worker 内完成 I/O → CPU 预处理 → GPU 推理的完整流水线，避免了跨进程数据拷贝和序列化开销。

原生多模态类型系统。 Daft 的 DataType 系统内置了 Image、Tensor、Embedding 等类型，以及对应的表达式操作-比如 `col("image_url").url.download().image.decode(mode=ImageMode.RGB)` ，可以直接在 DataFrame API 中完成图片下载和解码，不需要写额外的 UDF。

## 二、Ray：分布式计算的"操作系统"

### 2.1 Ray 在这套技术栈中的角色

Ray 是 UC Berkeley RISELab 开源的通用分布式计算框架（现由 Anyscale 维护）。在 Daft + Ray + Lance 这套栈中，Ray 的角色是分布式调度后端——它不直接处理数据逻辑，而是负责把 Daft 的 Worker 调度到集群的多台机器上。 Daft 有两种运行模式：

```text
# 本地模式 - 单机执行
import daft
df = daft.read_parquet("s3://my-bucket/data/")
df.show()

# Ray 模式 - 分布式执行
import daft
daft.context.set_runner_ray()
df = daft.read_parquet("s3://my-bucket/data/")
df.show()

```

从单机切换到分布式，只需要一行 `daft.context.set_runner_ray()` 。在 Ray 模式下，Daft 的 Swordfish Worker 会被调度为 Ray Actor，每个 Actor 独占一台机器的资源，底层的流式执行模型保持不变。

### 2.2 为什么选 Ray 而不是自建调度

这是一个务实的工程决策。分布式调度是一个独立的、极其复杂的问题域——容错、资源管理、任务依赖、数据亲和性……自己造轮子的成本极高。Ray 在这个领域已经打磨多年，被 OpenAI、Uber、蚂蚁集团等公司大规模使用。

- Ray 带来的核心价值包括： 异构资源调度：可以声明 task 或 actor 需要多少 CPU、GPU、内存，Ray 会自动做 placement
- 弹性伸缩：与 AWS、GCP、K8s 的 autoscaler 集成，根据负载动态增减节点
- Actor 模型：有状态的计算单元，适合需要加载模型权重的推理场景 生态丰富：Ray Train、Ray Serve、Ray Tune 等子项目覆盖了 ML 全生命周期.

### 2.3 Daft 新动向：Flotilla 引擎

值得关注的是，Daft 在 2025 年推出了名为 Flotilla 的全新分布式引擎（在 v1.5 中发布）。Flotilla 是 Daft 自研的分布式调度层，目标是在保留 Ray 兼容性的同时，提供更轻量、更可控的分布式执行。

这意味着未来 Daft 的分布式执行不再强依赖 Ray——但 Ray 仍然是一个重要的、完全支持的后端。对于已经有 Ray 集群的团队来说，直接使用 Ray 模式仍然是最低成本的选择。

## 三、Lance：为 AI 重新设计的存储格式

### 3.1 一个文件格式凭什么值得单独讨论

在传统数据工程中，文件格式的讨论基本就是 Parquet vs ORC，偶尔加个 Avro。大家关心的是压缩比、列裁剪、谓词下推这些经典话题。但到了多模态和 AI 场景，Parquet 的局限性开始显现。 Lance 是 LanceDB 团队开源的列式存储格式，它同时覆盖了文件格式、表格式和 Catalog Spec 三个层次——这一点和 Iceberg（只管表格式 + Catalog Spec，文件格式依赖 Parquet）有本质区别。

### 3.2 Lance vs Parquet：关键差异

几个关键点展开说：

- 向量索引。 在 RAG、语义搜索等场景中，Embedding 向量的近邻检索是核心需求。如果数据存在 Parquet 里，你需要额外维护一个向量数据库（Milvus、Pinecone 等）来做检索。Lance 格式原生支持 ANN（近似最近邻）索引，向量和元数据存储在同一个地方，查询时不需要跨系统关联。Lance 已经被验证可以索引数十亿向量，在对象存储上支持超过 10,000 QPS、延迟低于 50ms 的向量检索。
- 零拷贝 Schema 演进。 这是 Lance 在实际生产中最实用的特性之一。假设你有一个 100GB 的数据集，现在需要添加一列 1GB 的 Embedding 数据。在 Iceberg/Parquet 方案下，backfill 新列需要重写整个表——也就是写入 101GB。在 Lance 中，由于其 fragment 设计允许每个 fragment 独立添加列文件，添加新列只需要写入 1GB 的增量数据，不触碰已有数据。数据规模越大，这个优势越明显。Netflix 在构建其多媒体数据湖时就注意到了这一点，并选择了 LanceDB 来管理 AI 和多模态工作负载。

#### 3.3 Lance 的定位：不是替代 Iceberg，而是互补

需要明确的是，Lance 并不是要取代 Iceberg 和 Parquet。用 LanceDB 团队自己的话说：

> Analytical workloads, we would still expect that to be stored in Iceberg, but with Lance we would expect the use cases and data sets where it's AI heavy: search, training and AI inference would be in Lance.

一种正在形成的架构范式是双格式策略：

- Iceberg/Parquet -> BI 和分析型工作负载（SQL 查询、报表、数据仓库）
- Lance -> AI 和多模态工作负载（向量检索、模型训练、特征工程） 两者共享底层对象存储（S3/GCS/HDFS），通过统一的 Catalog 层（Glue、Unity、Polaris 等）做管理。这种分而治之的思路比"用一种格式打天下"更务实。

## 四、三剑合璧：端到端架构实战

### 4.1 整体架构

将三个组件组合起来，形成的是一个三层架构：

┌─────────────────────────────┐

Daft DataFrame API   │ ← 用户交互层（Python） ├─────────────────────────────┤

Swordfish / Flotilla   │ ← 执行引擎（Rust） ├─────────────────────────────┤

Ray Cluster         │ ← 分布式调度层 ├─────────────────────────────┤

Lance Format (on S3/GCS) │ ← 存储层 └─────────────────────────────┘

数据在 Lance 格式中存储于对象存储，Daft 通过原生的 Lance 连接器读写数据，Swordfish引擎负责执行查询计划，Ray负责将Worker 分发到集群多台机器上。

### 4.2 典型 Pipeline 示例

以一个实际场景为例：对百万级图文数据集做质量过滤 + Embedding 生成 + 写回存储。

```text
import daft
from daft import col

# 1. 切换到 Ray 分布式模式
daft.context.set_runner_ray()

# 2. 从 Lance 数据集读取数据
df = daft.read_lance("s3://my-bucket/multimodal-dataset/")

# 3. 基础过滤：只保留有效记录
df = df.where(
  (col("image_url").is_not_null()) &
  (col("caption").str.length() > 10)
)

# 4. 下载图片并解码
df = df.with_column(
  "image",
  col("image_url").url.download().image.decode(mode=daft.ImageMode.RGB)
)

# 5. 图片质量过滤（分辨率大于 224x224）
df = df.where(
  (col("image").image.width() >= 224) &
  (col("image").image.height() >= 224)
)

# 6. 调用模型生成 Embedding（通过 UDF）
@daft.udf(return_dtype=daft.DataType.tensor(daft.DataType.float32()))
class EmbeddingModel:
  def __init__(self):
    from sentence_transformers import SentenceTransformer
    self.model = SentenceTransformer("all-MiniLM-L6-v2")

  def __call__(self, texts):
    returnself.model.encode(texts.to_pylist())

df = df.with_column("embedding", EmbeddingModel(col("caption")))

# 7. 选择需要的列，写回 Lance
df = df.select("image_url","caption","embedding")
df.write_lance("s3://my-bucket/curated-dataset/")

```

这段代码看起来和普通的 DataFrame 操作没什么区别，但背后发生的事情完全不同：

- `url.download()` 是异步 I/O，不阻塞 CPU
- `image.decode()` 是 Rust 实现的高性能解码
- UDF 用 class 定义，模型权重只加载一次，之后在同一个 Worker 上复用
- 整个 Pipeline 是流式执行的，不会把百万张图片全部加载到内存

Lance格式的写入支持增量append,不需要覆盖已有数据。

### 4.3 适用场景

这套技术栈最适合以下场景：

- 场景一：多模态数据集 Curation。 从原始爬取的数据中，做图片去重、质量过滤、标注校验、格式统一。这是训练多模态大模型前的核心环节。
- 场景二：大规模 Embedding 计算与管理。 对文档、图片、音频批量计算 Embedding，存储在 Lance 中，利用其原生向量索引做检索。免去了维护独立向量数据库的运维成本。
- 场景三：特征工程。 在已有数据集上增量添加新特征列（比如新的模型推理结果），利用 Lance 的零拷贝 Schema 演进避免全量 rewrite。
- 场景四：ML 训练数据管道。 Lance 与 PyTorch DataLoader 的集成可以利用其高效的随机访问能力，配合分布式缓存实现超过 500 万 IOPS 的训练数据读取。

## 六、落地建议与注意事项

聊完了技术亮点，也要客观说说目前的局限，帮你做出更靠谱的技术选型。

### 6.1 Daft 还很年轻

Daft 目前的生产案例主要集中在 AI/ML 领域的头部公司和团队。相比 Spark 十多年的积累，Daft 的社区规模、文档完善度、第三方集成数量都还有差距。如果你的核心工作负载仍然是传统的 SQL 分析和 ETL，目前切换到 Daft 的必要性不大。

### 6.2 Ray 集群的运维成本

Ray 集群的部署和运维不是零成本的事。对于小团队或者数据量不大的场景，直接用 Daft 的本地模式（单机 Swordfish 引擎）可能就够了——不需要 Ray 也能获得不错的性能。只有当数据量确实需要多机并行时，才有必要引入 Ray。

### 6.3 Lance 的生态覆盖

Lance 格式目前的计算引擎集成主要集中在 Daft、Spark（通过 lance-spark）和 Ray（通过 lance-ray）。主流的 OLAP 引擎（Trino、StarRocks、Flink 等）对 Lance 的支持还在早期阶段。如果你的数据需要同时服务 BI 和 AI 两类需求，目前更务实的方案是 Iceberg + Lance 双格式并行。

### 6.4 建议的入门路径

1. 先在单机上体验 Daft： `pip install daft` ，用你自己的多模态数据跑几个Pipeline，感受一下和Spark/Pandas的差异
2. 尝试 Lance 格式：把一些数据从 Parquet 转成 Lance，对比随机访问和写入性能
3. 数据量大了再引入 Ray：一行代码切换到分布式模式
4. 生产上渐进式采用：不需要一步到位替换整个技术栈，可以先在 AI/ML Pipeline 中局部引入

## 七、总结

回到文章开头的问题：多模态 AI 时代，数据工程需要什么样的技术栈？

Daft 提供了一个专为多模态设计的高性能计算引擎，流式执行+自适应反压让你不用再和OOM搏斗。Ray在需要时提供分布式调度能力，从单机无缝扩展到集群。Lance在存储层重新定义了AI数据的组织方式，随机访问、向量索引、零拷贝演进——都是为 ML/AI 工作负载量身打造的能力。 这三个项目各自开源、各自独立、各自演进，但组合在一起恰好覆盖了多模态数据工程的核心需求。

技术选型从来不是"选最新的"，而是"选最适合的"。如果你的 Pipeline 里开始出现图片、音频、视频、Embedding-这套技术栈值得你花时间认真研究一下。
