2023 年 12 月 12 日，UC Berkeley、Stanford 等机构的 Lianmin Zheng、Liangsheng Yin、Ying Sheng 等研究者公开了一篇论文：

**SGLang: Efficient Execution of Structured Language Model Programs。**

这篇论文后来发表于 NeurIPS 2024。

它提出了一个叫 SGLang 的系统。

但如果回到论文最初的问题，会发现一个很有意思的现象。

**SGLang 最开始并不是为了重新发明一个 vLLM。**

它甚至不是单纯从 GPU Kernel 或 KV Cache 内存管理出发。

它真正想解决的是：

**为什么大语言模型已经能够执行越来越复杂的任务，但我们仍然需要用大量笨拙的 Python 字符串拼接和 API 调用来组织它们？**

例如，假设我们想让一个 LLM 完成下面的任务：

阅读一篇文章。

从三个不同角度分别评价文章。

将三份评价合并。

最后生成符合 JSON Schema 的结果。

最直接的实现可能是：

```python
summary = llm(prompt_1)

clarity = llm(prompt_2 + summary)
originality = llm(prompt_3 + summary)
correctness = llm(prompt_4 + summary)

final = llm(
    prompt_5
    + clarity
    + originality
    + correctness
)

result = json.loads(final)
```

这段代码看起来不复杂。

但仔细考虑，就会发现很多问题。

三个评价任务其实可以并行执行。

它们还共享很长的一段原始文章。

如果每次调用都重新执行 Prefill，就会反复计算同一段输入。

如果最终 JSON 格式错误，还需要重新生成或者修复。

如果需要从几个固定选项中选择一个结果，直接生成自由文本再解析，也会引入不必要的不确定性。

到了 2023 年，研究者已经拥有：

ReAct。

Tree of Thoughts。

Self-Consistency。

Generative Agents。

以及各种复杂的 Prompting Workflow。

但这些系统通常将 LLM 当成一个反复调用的黑盒函数：

```python
output = llm(prompt)
```

每次调用相对独立。

而底层推理系统只看到：

又来了一条 Prompt。

它并不知道：

这几条 Prompt 其实属于同一个程序。

它们共享大量历史。

后面的任务依赖前面的结果。

其中一些分支可以并行。

还有一些输出必须满足特定语法。

于是 SGLang 提出了一个新的抽象：

**Language Model Program，语言模型程序。**

并且试图同时解决两个问题。

第一：

怎样让人类更容易编写这种程序？

第二：

怎样让推理系统利用程序内部的共享结构，减少冗余计算？

所以 SGLang 最初包含两个部分：

**SGLang Frontend Language。**

以及：

**SGLang Runtime，简称 SRT。**

前者负责描述生成逻辑。

后者负责高效执行。

在原始论文的测试中，SGLang 在相关 LM Program 工作负载上，取得最高约 6.4 倍吞吐提升，并将部分任务的延迟降低至原来的约 1⁄3.7。

但到了 2026 年，如果打开 SGLang 的 GitHub 仓库，会发现项目的中心已经发生了巨大变化。

今天的 SGLang 已经支持：

Continuous Batching。

RadixAttention。

Prefix Caching。

Tensor Parallelism。

Expert Parallelism。

Prefill–Decode Disaggregation。

Speculative Decoding。

CUDA Graph。

多模态生成。

分布式 KV Cache。

以及强化学习 Rollout。

2026 年 9 月 23 日，SGLang 又发布了 Unified Radix Cache。

它尝试用一套统一的缓存结构，同时管理：

Full Attention。

Sliding Window Attention。

Mamba 类递归状态。

以及 GPU、CPU、外部存储中的多级缓存。

同年 10 月，SGLang 甚至已经与 Miles 共同为前沿 MoE 模型提供 Day-0 推理和强化学习支持。

这就产生了两个值得研究的问题。

**第一，为什么一个从 Prompt 编程出发的系统，最终成为了与 vLLM 正面竞争的高性能推理引擎？**

**第二，为什么 RadixAttention 这种看起来只是管理字符串前缀的技术，最终能够延伸到百万 Token Agent、混合注意力模型和分布式 KV Cache？**

要理解这段历史，我们需要回到 2023 年之前。

---

### 一、2022—2023 年：大模型为什么开始需要一门“编程语言”？

### 1. 最早的大模型调用其实非常简单

假设我们拥有一个文本生成模型。

最朴素的使用方式是：

```python
prompt = "请解释什么是强化学习"

response = model.generate(prompt)
```

输入一段文本。

得到一段文本。

如果任务只是：

聊天。

摘要。

翻译。

一次性问答。

这套接口通常足够。

但当研究者开始让 LLM 执行复杂任务时，问题逐渐出现。

例如 ReAct：

```text
Thought
    ↓
Action
    ↓
Observation
    ↓
Thought
    ↓
Action
    ↓
Observation
```

模型需要与外部环境多次交互。

每一步都可能依赖前一步的结果。

再例如 Self-Consistency：

```text
同一个问题
     │
     ├── Sample 1
     ├── Sample 2
     ├── Sample 3
     └── Sample 4
            │
            ▼
       Aggregate
```

这里又出现并行分支。

再例如 Tree of Thoughts：

```text
初始问题
    │
    ├── 思路 A
    │    ├── A1
    │    └── A2
    │
    └── 思路 B
         ├── B1
         └── B2
```

模型不仅需要生成文本。

还需要管理：

分支。

同步。

变量。

条件判断。

循环。

以及多个生成结果之间的依赖关系。

这已经越来越像程序执行。

### 2. 为什么不能一直手工拼 Prompt？

当然可以。

例如：

```python
history = ""

history += "Question: " + question

answer_1 = llm(history + "\nTry solution A:")
answer_2 = llm(history + "\nTry solution B:")

history += answer_1
history += answer_2

final = llm(history + "\nSummarize:")
```

但随着复杂度提高，会出现很多问题。

首先是状态管理。

`history` 到底包含哪些内容？

哪些属于 System？

哪些属于 User？

哪些属于 Assistant？

哪些属于工具结果？

其次是并行执行。

如果 A、B 两条分支互相独立，我们希望它们同时运行。

但普通同步函数调用会阻塞。

再次是结构化输出。

例如希望模型生成：

```json
{
  "score": 8,
  "reason": "..."
}
```

如果模型输出：

```text
The score is eight.
```

那么程序可能无法解析。

最后是计算复用。

如果 A 和 B 使用相同的 10000 Token Prefix，底层推理系统会不会重新计算两遍？

对于越来越复杂的 Agent Workflow，这些问题会反复出现。

### 3. LMQL 和 Guidance 已经在尝试解决这个问题

SGLang 并不是第一个提出：

Prompting is Programming。

这一思想的系统。

2023 年，LMQL 提出了一种用于语言模型交互的查询语言。

它允许开发者描述：

生成变量。

逻辑约束。

输出条件。

以及模型调用。

同一时期，Microsoft Guidance 也开始通过模板和 Python 风格的接口，让开发者控制语言模型生成过程。

例如：

固定文本。

生成变量。

条件分支。

正则表达式约束。

这些都是 SGLang 的重要前驱。

### 4. SGLang 的不同之处是什么？

SGLang 的关键选择是：

**不只设计一套更方便的 Prompt API，还要共同设计执行它的推理 Runtime。**

因为：

如果前端知道多个请求共享 Prefix。

但后端不知道。

那么前端只能表达这种共享关系，却无法直接利用它节省 GPU 计算。

如果前端知道某个 JSON 片段是固定的。

但后端只提供普通逐 Token Sampling。

那么生成固定片段时仍然可能产生多次不必要的 Decode。

所以原始论文提出：

```text
Frontend Language
        │
        │ Generation / Branch / Control Flow
        ▼
SGLang Runtime
        │
        ├── RadixAttention
        ├── Compressed FSM
        └── Efficient Scheduling
        │
        ▼
      GPU
```

这就是 Frontend–Runtime Co-Design。

前端语言和后端执行器共同设计。

### 二、2023 年：SGLang Frontend 到底是一门怎样的语言？

### 5. SGLang 并不是重新发明 Python

SGLang 最初采用：

**Python-Embedded Domain-Specific Language。**

中文叫：

嵌入 Python 的领域专用语言。

DSL：

Domain-Specific Language。

例如 SQL 是一种用于数据库查询的 DSL。

而 SGLang 的 DSL 专门用于：

组织 LLM Generation。

它直接利用 Python 的：

函数。

循环。

条件判断。

变量。

并发控制。

同时添加少量专门的 LLM 原语。

### 6. 一个最简单的 SGLang 程序

```python
import sglang as sgl

@sgl.function
def answer_question(s, question):
    s += sgl.user(question)
    s += sgl.assistant(
        sgl.gen("answer", max_tokens=256)
    )
```

这里最重要的是：

```python
@sgl.function
```

它将普通 Python 函数包装成 SGLang Program。

而：

```python
s
```

不是普通字符串。

它是：

**Prompt State。**

可以理解为一个不断增长、能够包含生成操作和角色信息的状态对象。

### 7. `s +=` 是什么？

例如：

```python
s += "Question: "
```

表示：

向当前 Prompt State 添加内容。

再执行：

```python
s += question
```

Prompt 就变成：

```text
Question: 什么是 PPO？
```

注意：

这不一定意味着每次 `s +=` 都立即向 GPU 提交一次模型请求。

SGLang Frontend 会管理这些操作，再由执行器按照依赖关系组织实际调用。

### 8. `sgl.gen()` 是什么？

例如：

```python
s += sgl.gen("answer", max_tokens=256)
```

表示：

从当前 Prompt 开始，让模型生成文本。

并将生成结果保存在变量：

```python
s["answer"]
```

中。

这样就不需要手工执行：

```python
response = call_api(...)
```

再自己拼接返回内容。

### 9. `sgl.select()` 又是什么？

假设希望模型选择：

```text
Positive

Negative
```

可以使用：

```python
s += sgl.select(
    "sentiment",
    choices=["Positive", "Negative"]
)
```

它不是要求模型随意生成一句话，再从文本中查找关键词。

而是通过候选评分等机制，从指定选项中选择。

这样可以减少自由文本输出带来的解析问题。

### 10. `fork()` 和 `join()` 为什么重要？

假设我们需要从三个角度分析一段文字。

可以创建三个分支。

下面是根据原始 SGLang Frontend API 改写的示意：

```python
@sgl.function
def evaluate_text(s, text):
    s += "Evaluate the following text:\n"
    s += text

    forks = s.fork(3)

    dimensions = [
        "Clarity",
        "Originality",
        "Correctness",
    ]

    for f, dimension in zip(forks, dimensions):
        f += f"\nEvaluate {dimension}:\n"
        f += sgl.gen(
            "judgment",
            max_tokens=128
        )

    forks.join()

    for dimension, f in zip(dimensions, forks):
        s += f"\n{dimension}: "
        s += f["judgment"]

    s += "\nFinal summary:\n"
    s += sgl.gen("summary", max_tokens=256)
```

逻辑是：

```text
原始 Prompt
      │
      ▼
     Fork
      │
  ┌───┼───┐
  ▼   ▼   ▼
 A    B   C
  │   │   │
  └───┼───┘
      ▼
     Join
      │
      ▼
  Final Summary
```

这里的核心不是简单的 Python 并行。

而是：

**不同分支具有共同的 Prompt Prefix。**

因此，后端可以利用这一结构，复用共同 Prefix 的 KV Cache。

这就引出了 SGLang 最重要的早期创新：

RadixAttention。

### 三、2023 年：为什么 SGLang 认为传统推理系统浪费了大量重复计算？

### 11. 一个非常简单的例子

假设我们要评估三篇文章。

使用相同的 System Prompt：

```text
You are an expert scientific reviewer.
```

然后输入：

```text
Article A
Article B
Article C
```

传统方式：

```text
Request A：
System Prompt + Article A

Request B：
System Prompt + Article B

Request C：
System Prompt + Article C
```

如果三次调用独立执行，就可能重复计算相同 System Prompt。

### 12. 但真实 LM Program 中的共享更加复杂

例如一个多轮 Agent：

```text
System Prompt
      │
      ▼
User Task
      │
      ▼
Assistant Thought
      │
      ├── Tool Call A
      │      │
      │      ▼
      │   Result A
      │
      └── Tool Call B
             │
             ▼
          Result B
```

这里不只是所有 Request 共享最初的 System Prompt。

不同分支还可能共享：

System Prompt。

User Task。

此前的 Assistant Thought。

甚至更长的历史。

所以需要管理的是：

**动态变化的共享 Prefix Tree。**

### 13. 为什么普通 Dictionary 不够自然？

最简单的缓存方案可以是：

```python
cache[prompt] = kv_cache
```

即：

使用完整 Prompt 作为 Key。

但假设两个 Prompt：

```text
A B C D
```

和：

```text
A B E F
```

它们虽然不完全相同，却共享：

```text
A B
```

如果只使用完整字符串匹配，那么：

```text
A B C D != A B E F
```

系统就无法直接发现：

它们有一段可以复用的共同前缀。

我们真正需要的是：

**Longest Common Prefix。**

最长公共前缀。

### 四、Radix Tree 为什么适合管理 LLM 的共享 Prefix？

### 14. 先理解 Trie

Trie：

前缀树。

假设有三条 Token 序列：

```text
A B C

A B D

A E F
```

普通 Trie 可以表示为：

```text
Root
          │
          A
        /   \
       B     E
      / \     \
     C   D     F
```

每条边通常对应一个 Token。

因此，共同的前缀自然被合并到相同节点。

例如：

```text
A B C
```

与：

```text
A B D
```

共享：

```text
A B
```

这使前缀匹配非常方便。

### 15. Radix Tree 又是什么？

Radix Tree：

基数树。

也叫：

Compressed Trie。

它允许把没有分叉的连续路径压缩成一条边。

例如：

普通 Trie：

```text
Root
  │
  A
  │
  B
  │
  C
  │
  D
```

Radix Tree：

```text
Root
  │
[A B C D]
```

边的标签可以是一段 Token 序列。

因此节点数量更少。

遍历和管理开销也更低。

### 16. 为什么这特别适合 LLM Prompt？

因为 LLM 的 Prompt 经常包含很长的连续共享部分。

例如：

```text
System Prompt：2000 Token

Few-shot Examples：5000 Token

User Question：100 Token
```

大量请求共享前面：

7000 Token。

如果使用每 Token 一个节点的 Trie，管理结构可能很庞大。

而使用 Radix Tree，可以把长的无分叉前缀压成少量边。

例如：

```text
Root
  │
[System Prompt + Few-shot]
       │
    ┌──┴──┐
    ▼     ▼
Question A
Question B
```

这里的每个节点或边，可以关联对应的 KV Cache。

### 17. RadixAttention 到底是什么？

原始论文的定义可以概括为：

**利用 Radix Tree 管理 Token Prefix 与对应 KV Cache 的映射，并支持自动匹配、插入、共享和逐出。**

例如：

```text
Token Prefix
      │
      ▼
Radix Tree
      │
      ▼
KV Cache Indices
      │
      ▼
Physical KV Memory
```

注意：

RadixAttention 不是一个新的 Attention 数学公式。

它不把：

$$ \operatorname{softmax} \left( \frac{QK^\top}{\sqrt d} \right)V $$

替换成另一种 Attention。

它真正改变的是：

**历史 KV Cache 如何被管理和复用。**

### 五、RadixAttention 的 Insert 和 Split 究竟怎样执行？

### 18. 假设缓存最初为空

系统收到第一条请求：

```text
A B C D
```

执行 Prefill 后，得到对应的 KV Cache。

Radix Tree：

```text
Root
  │
[A B C D]
```

### 19. 第二条请求到来

```text
A B E F
```

系统从 Root 开始比较。

发现：

```text
A B
```

相同。

但：

```text
C != E
```

因此，需要将原来的边拆分。

拆分以后：

```text
Root
        │
      [A B]
      /   \
   [C D] [E F]
```

这样两条请求就能够共享：

```text
A B
```

对应的 KV Cache。

### 20. 为什么 Split 不需要重新执行模型？

因为：

已经缓存的：

```text
A B
```

对应 KV 并没有改变。

系统只是调整索引结构和引用关系。

后续新请求只需要对未命中的后缀进行计算。

例如：

```text
A B E F
```

如果：

```text
A B
```

命中缓存。

就只需要 Prefill：

```text
E F
```

相应的 Attention 仍然能够访问已经缓存的 A、B。

### 21. 第三条请求为什么还能进一步复用？

假设新的 Prompt 是：

```text
A B C G
```

当前缓存树：

```text
Root
        │
      [A B]
      /   \
   [C D] [E F]
```

系统发现：

```text
A B C
```

是已有路径：

```text
A B C D
```

的 Prefix。

于是再次拆分：

```text
Root
        │
      [A B]
      /   \
     C    [E F]
    / \
   D   G
```

这就是动态前缀树。

它不需要在最初就知道所有请求的分支结构。

而是随着请求到来：

匹配。

分裂。

插入。

逐渐形成共享的 Prefix Tree。

### 六、为什么缓存不能只保存当前正在运行的请求？

### 22. 一次请求结束以后，KV Cache 还有价值吗？

假设：

```text
Request A：
System + History + Question A
```

执行完成。

如果系统立即释放全部 KV Cache，那么下一轮：

```text
Request B：
System + History + Question A + Answer A + Question B
```

就需要重新计算大量历史。

但实际上：

这两次请求共享很长的 Prefix。

因此，SGLang 选择：

**即使 Request 完成，也可以继续保留其 KV Cache。**

只要显存还允许。

这样，KV Cache 就不再只是某条活跃请求的内部状态。

它成为：

**跨 Request 的共享缓存资源。**

### 23. 那显存不够怎么办？

SGLang 使用：

LRU Eviction。

即最近最少使用策略。

但这里并不是简单删除整条旧请求。

因为 Radix Tree 中的公共前缀，可能被很多 Request 共享。

例如：

```text
Root
          │
      [System]
       /    \
      A      B
      │      │
     A1     B1
```

如果：

```text
A1
```

很久没有被使用。

但：

```text
System
```

仍然被其他请求引用。

那么系统应该优先回收：

```text
A1
```

对应的独有部分。

而不是删除整段 System Prefix。

因此，RadixAttention 的逐出策略会从可回收的 Leaf 开始。

### 24. Reference Count 为什么重要？

假设：

```text
System Prefix
```

正在被三个 Request 使用。

则对应缓存节点存在：

```text
ref_count = 3
```

这些 KV 不能在请求仍然需要时被回收。

当请求结束：

```text
ref_count
```

下降。

当没有活跃请求使用时，节点才可能成为可回收缓存。

但是否立即删除，还取决于缓存容量和 LRU 策略。

### 25. 为什么 RadixAttention 不需要独立的固定大小缓存池？

原始论文的一项重要设计是：

缓存与当前运行请求，共享同一套 KV 内存池。

当有空闲容量：

可以保留完成请求的 KV。

当新请求需要显存：

可以逐出不再被活跃请求使用的旧缓存。

因此：

```text
更多缓存
    ↔
更多并发请求
```

二者动态竞争显存。

如果当前存在大量运行请求，系统可以逐出旧缓存，为更大的 Batch 让出空间。

这比固定划分：

```text
50% 显存专门做 Cache

50% 显存专门运行请求
```

具有更好的资源灵活性。

### 七、RadixAttention 与 vLLM 的 PagedAttention 究竟是什么关系？

### 26. 它们解决的问题并不完全相同

2023 年的 vLLM PagedAttention，重点在于：

**将逻辑 KV Block 映射到非连续的物理 KV Block。**

例如：

```text
Logical Block 0 → Physical Block 7
Logical Block 1 → Physical Block 3
Logical Block 2 → Physical Block 12
```

这主要解决：

KV Cache 动态增长。

显存碎片。

按需分配。

物理缓存共享。

而 SGLang 的 RadixAttention，更突出：

**不同 Request 的 Token Prefix 具有怎样的共享关系？**

例如：

```text
Request A：
A B C D

Request B：
A B E F
```

Radix Tree 能够高效找到共享的：

```text
A B
```

然后复用对应 KV。

### 27. 为什么 SGLang 也需要 Paged KV？

因为：

找到可以复用的 Prefix，不等于解决了物理显存存储问题。

Radix Tree 可以告诉我们：

逻辑 Token A、B 对应哪些缓存。

但实际 KV 仍然需要存放在 GPU 中。

因此 SGLang 也采用分页式、非连续的 KV 存储布局。

在 2023 年的原始实现中，论文描述了 Token 粒度的 Page。

后续实现又支持不同的 Page Size。

例如 2026 年的部分部署使用：

```text
--page-size 64
```

所以：

**RadixAttention 与 PagedAttention 在工程上可以共同存在。**

一个负责共享前缀的逻辑组织。

另一个负责 KV 的物理分配与访问。

### 28. 那今天的 vLLM 也支持 Prefix Caching 吗？

支持。

经过后续发展，vLLM 也提供 Automatic Prefix Caching。

因此，不能把 2023 年论文中的对比，直接当成 2026 年两个系统的全部功能差异。

真正的历史区别是：

vLLM 从高效 KV 物理内存管理出发。

SGLang 从多调用程序的 Prefix Sharing 出发。

但两者后来不断吸收相似的工程技术。

到 2026 年，它们在：

Continuous Batching。

Paged KV。

Prefix Caching。

Speculative Decoding。

PD Disaggregation。

分布式 MoE。

等方面已经有大量功能重叠。

### 八、RadixAttention 为什么还需要 Cache-Aware Scheduling？

### 29. 假设 GPU 同时收到四条请求

```text
Request A：
Prefix X + Question A

Request B：
Prefix Y + Question B

Request C：
Prefix X + Question C

Request D：
Prefix Y + Question D
```

其中：

A、C 共享 Prefix X。

B、D 共享 Prefix Y。

如果缓存容量足够，调度顺序影响可能不大。

但如果显存非常有限：

系统可能执行 A。

保存 Prefix X。

然后执行 B。

为了腾出显存，逐出 X。

接着执行 C。

发现 X 已经被逐出。

于是又重新计算。

这显然浪费。

### 30. 为什么不让共享 Prefix 的请求尽量靠近执行？

例如：

```text
A → C → B → D
```

这样：

A 执行后，C 可以复用 X。

B 执行后，D 可以复用 Y。

这就是：

**Cache-Aware Scheduling。**

SGLang 原始论文研究了利用 Radix Tree 的 Prefix 结构，改善请求调度。

其中包括根据共享 Prefix 的情况，优先安排具有较高缓存复用潜力的请求。

### 31. 但为什么不永远优先选择最长 Prefix Match？

因为调度还需要考虑：

请求等待时间。

显存。

当前运行 Batch。

Prefill Cost。

Decode Latency。

以及公平性。

如果始终优先执行最容易命中缓存的请求，某些缺少共享 Prefix 的请求可能等待很久。

因此，调度的目标并不只是：

Cache Hit Rate 最大。

还要兼顾：

吞吐。

延迟。

以及请求等待。

这也是后来 SGLang 将 Cache-Aware Routing 和 Scheduling 分别研究的原因。

### 九、2023 年：Compressed FSM 为什么是 SGLang 的第二项重要创新？

### 32. 为什么结构化输出会浪费 Decode？

假设我们要求模型生成：

```json
{
  "name": "Alice",
  "age": 20
}
```

如果使用 JSON Schema，可以明确规定：

必须包含：

```text
name

age
```

两个字段。

字段名和部分标点是固定的。

例如：

```text
{"name":"
```

这些字符串的内容已经由语法规则确定。

但是普通自回归生成仍然可能：

一个 Token。

一个 Token。

地生成它们。

### 33. 有限状态机怎样约束输出？

FSM：

Finite State Machine。

有限状态机。

可以把结构化生成过程表示成状态转移。

例如：

```text
START
  │
  ▼
{
  │
  ▼
"name"
  │
  ▼
:
  │
  ▼
"
  │
  ▼
STRING_CONTENT
```

如果某个状态只允许一个后继 Token，那么：

这一位置其实没有真正的选择问题。

模型不需要通过概率分布决定：

到底输出哪个 Token。

因为只有一个合法候选。

### 34. 为什么普通 Grammar-Constrained Decoding 仍然可能慢？

一种简单实现是：

模型 Forward。

得到 Logits。

根据 FSM 当前状态，把非法 Token 的 Logit 设为负无穷。

然后采样合法 Token。

更新 FSM State。

下一轮继续。

例如：

```text
Model Forward
     ↓
Grammar Mask
     ↓
Token 1
     ↓
Model Forward
     ↓
Grammar Mask
     ↓
Token 2
```

即使某些 Token 完全由 Grammar 决定，系统仍然执行多轮模型计算。

### 35. Compressed FSM 改变了什么？

SGLang 观察到：

如果一段状态转换是完全确定的，那么它可以被压缩。

例如：

```text
State A
   │
   ▼
Token 1
   │
   ▼
Token 2
   │
   ▼
Token 3
   │
   ▼
State B
```

可以抽象为：

```text
State A
   │
   ▼
[Token 1, Token 2, Token 3]
   │
   ▼
State B
```

然后一次向模型输入这段已知 Token。

让 Transformer 并行计算必要的状态。

这实际上利用了与 Blockwise Decoding 类似的基本性质：

**已经确定的 Token，可以批量输入并计算。**

因此，原本需要多个逐 Token Decode Step 的固定片段，有机会在一次模型执行中处理。

### 36. 为什么这不只是把 JSON 字符串直接拼到输出上？

因为：

模型后续的 Attention 仍然需要这些固定 Token 对应的内部状态。

即使不需要模型自己决定：

`{`

或者：

`"name"`

是否应该出现。

这些 Token 仍然是后续生成的 Context。

因此，系统需要正确更新：

Token History。

Positions。

KV Cache。

以及 Grammar State。

不能只在最后的文本结果中拼接几个字符，却不让模型感知这些 Token。

### 37. 后来为什么又引入 XGrammar？

2024 年 12 月，SGLang v0.4 将 XGrammar 作为结构化输出的重要优化。

它通过更高效的 Grammar 编译、Token Mask 等机制，提高 JSON、Regex 和其他约束生成的性能。

官方在指定结构化输出 Benchmark 中报告最高约 10 倍加速。

这里与原始 Compressed FSM 的目标一致：

减少结构化生成中的无效开销。

但具体优化技术已经进一步扩展。

到现代 Thinking Model，SGLang 还需要处理：

自由推理区间。

结构化最终回答。

工具调用 Grammar。

以及不同模型的特殊 Token 边界。

例如：

```text
<think>
...
</think>
```

中的内容可能允许自由生成。

而后面的 JSON 输出则需要受到 Schema 约束。

这已经比 2023 年最初的 Regex Generation 复杂得多。

### 十、为什么 SGLang 原始论文还研究 API Speculative Execution？

### 38. 如果模型只提供远程 API，RadixAttention 就无法直接控制

SGLang 最初既支持：

本地开放权重模型。

也支持：

通过 API 调用的闭源模型。

例如 GPT-4。

对于闭源 API：

我们无法直接管理 Target Model 的 KV Cache。

也无法修改内部 Attention Kernel。

那么还能怎样优化 LM Program？

### 39. 原始论文提出了 API Speculative Execution

考虑一个多步生成程序：

```text
Name:
让模型生成名字。

Job:
让模型生成职业。
```

如果严格按程序步骤执行：

第一轮 API：

```text
Name:
```

生成：

```text
Alice
```

第二轮 API：

```text
Name: Alice
Job:
```

生成：

```text
Engineer
```

这里出现两次远程请求。

而第二次又重新发送了前面的 Context。

### 40. 为什么可以提前生成后续内容？

如果我们知道下一步 Prompt 的大致结构，可以在第一轮请求时，让模型继续生成额外内容。

例如：

```text
Name: Alice
Job: Engineer
```

然后前端尝试识别：

哪些额外输出可以复用于下一步程序调用。

如果猜测正确，就可能减少一次 API 请求。

同时节省：

网络往返延迟。

重复输入 Token 成本。

### 41. 这和经典 Speculative Decoding 有什么区别？

经典 Speculative Decoding：

```text
小模型预测 Token
      ↓
大模型验证 Token
      ↓
接受 / 残差校正
```

它可以在正确实现下保持 Target Sampling Distribution。

但 SGLang 原始论文的 API Speculative Execution：

主要是利用程序未来可能执行的结构，提前生成并尝试复用后续输出。

它不是同一个数学算法。

因此，不能把两者都翻译成“投机”，就认为它们具有相同的 Lossless 保证。

原始 SGLang 更关注：

**程序执行路径上的提前计算与结果复用。**

### 十二、Zero-Overhead Batch Scheduler 为什么出现？

### 47. GPU 推理为什么还会被 CPU 拖慢？

假设一次 Decode 包含：

```text
CPU：
构造 Batch。

CPU：
分配 KV Cache。

CPU：
准备 Positions。

CPU：
构造 Attention Metadata。

GPU：
执行 Forward。
```

GPU 计算完成以后：

```text
CPU：
读取输出。

CPU：
更新 Request 状态。

CPU：
准备下一轮。
```

这会形成一种串行流程：

```text
CPU Prepare 1
      ↓
GPU Forward 1
      ↓
CPU Prepare 2
      ↓
GPU Forward 2
```

如果 GPU Forward 很快，而 CPU 准备较慢，就可能出现：

GPU 等待 CPU。

### 48. 为什么不让 CPU 提前准备下一轮？

这就是 Overlap Scheduling。

理想流程：

```text
时间 ─────────────────────▶

CPU：
[Prepare 1][Prepare 2][Prepare 3]

GPU：
           [Forward 1][Forward 2][Forward 3]
```

CPU 在 GPU 执行当前 Batch 时，准备下一 Batch。

让两个阶段重叠。

这不是 SGLang 第一次提出 CPU-GPU Overlap 的思想。

2024 年的 NanoFlow 等研究已经讨论过相关机制。

SGLang v0.4 的贡献在于：

将它集成到自己的实际调度器中。

并处理 KV Cache、采样结果与下一轮调度之间的依赖。

### 49. 但是下一轮 Token 还不知道，CPU 怎么提前准备？

这就涉及 Future Token。

假设：

```text
Batch A 正在 GPU 上执行。
```

CPU 想提前准备 Batch B。

但 Batch A 的新 Token 尚未返回。

那么 CPU 不可能知道所有真实 Token ID。

一种方法是：

先建立占位符或未来结果引用。

将可以提前确定的元数据准备好。

等 GPU 结果可用时，再补上真正依赖采样结果的数据。

例如：

```text
CPU：
提前决定 Request 顺序。

CPU：
准备部分 Batch Metadata。

GPU：
完成当前 Token Sampling。

CPU/GPU：
补全必要依赖。

GPU：
执行下一轮。
```

SGLang 通过 CUDA Event、同步规则和相关缓冲结构实现这一流程。

### 50. 为什么这件事没有想象中简单？

因为多个阶段可能操作同一批状态。

例如：

当前 GPU Forward 还没有完成。

CPU 却已经修改某个 Request 的 Token History。

或者某个 Logits Processor 需要读取最新状态。

如果同步设计不正确，就可能发生：

Race Condition。

即竞争条件。

2025 年的 SGLang Issue #8056，就报告过 Overlap Mode 下自定义 Logits Processor 产生竞态问题。

开发者通过关闭 Overlap Scheduler 绕过该问题。

这说明：

Overlap Scheduling 的主要挑战，不只是把 CPU 和 GPU 同时运行。

而是要保证两边读写状态的时序正确。

### 51. 为什么叫 Zero-Overhead，而不是真的没有开销？

这个名称表达的是：

尽量将 CPU 调度开销隐藏在 GPU 计算期间。

当 CPU 工作完全被 GPU Forward 覆盖时：

从 GPU 时间线看，调度造成的额外空闲可能接近零。

但 CPU 仍然在执行调度。

Cache Matching 仍然需要时间。

数据结构仍然需要更新。

因此，Zero-Overhead 的实质是：

**Overlap and Hide。**

重叠与隐藏。

而不是这些工作在物理上完全消失。

### 十三、2024 年：为什么 SGLang 的 Cache-Aware Router 需要用 Rust？

### 52. 单机缓存命中高，不代表多机系统命中高

假设我们有四个 SGLang Server。

```text
Server A

Server B

Server C

Server D
```

每个 Server 都有自己的 Radix Tree。

自己的 GPU KV Cache。

现在一个用户的第一轮请求进入：

```text
Server A
```

其历史 KV 保存在 A。

但第二轮请求被 Round-Robin 分配到：

```text
Server B
```

那么：

B 可能完全没有这段缓存。

于是重新 Prefill。

即使 A 还保存着完整历史，也无法直接复用。

### 53. 为什么 Round-Robin 不够？

Round-Robin：

轮询。

例如：

```text
Request 1 → A

Request 2 → B

Request 3 → C

Request 4 → D

Request 5 → A
```

它通常能够简单地分散请求数量。

但完全没有考虑：

请求与哪个 Server 已缓存的 Prefix 更相似。

这会降低缓存局部性。

### 54. Cache-Aware Routing 怎么做？

Router 估计：

每个 Server 对当前请求的 Prefix Cache Hit。

例如：

```text
Request Q：

Server A：
命中 8000 Token。

Server B：
命中 1000 Token。

Server C：
命中 0 Token。

Server D：
命中 3000 Token。
```

如果负载允许，就优先选择：

```text
Server A
```

这样可以节省更多 Prefill。

### 55. 为什么不能永远选择命中最多的 Server？

因为：

A 可能已经非常拥挤。

B 虽然缓存命中低，但 GPU 空闲。

如果全部请求都集中到 A，队列等待时间就可能超过 Prefill 节省的时间。

因此，Router 需要在：

Cache Locality。

和：

Load Balancing。

之间做权衡。

2024 年的 SGLang Cache-Aware Router 同时考虑这两方面。

### 56. Router 怎样知道每个 Server 缓存了什么？

一种方案是：

每个 Worker 不断向 Router 同步完整 Radix Tree。

但这样会增加通信开销。

SGLang 选择了更加轻量的方式：

Router 维护一棵近似的 Radix Tree。

根据请求路由和运行信息，估计不同 Worker 可能缓存的 Prefix。

这避免了频繁的完整缓存同步。

### 57. 为什么使用 Rust？

因为 Router 是一个独立的高并发服务。

它需要快速处理：

大量 HTTP 请求。

Cache Matching。

负载选择。

Worker 状态。

连接管理。

Rust 提供：

较低运行时开销。

安全的内存管理。

高性能并发执行能力。

因此，SGLang 采用 Rust 实现这一 Routing 组件。

2024 年官方在共享长 Prefix 的指定 Benchmark 中报告：

吞吐从：

```text
82665 tokens/s
```

提高到：

```text
158596 tokens/s
```

Cache Hit Rate 从：

```text
20%
```

提高到：

```text
75%
```

这说明：

对于多轮 Agent 和共享 Prefix 工作负载，Router 自身已经成为推理性能的重要部分。

后来，这一路线又逐渐发展成：

**SGLang Model Gateway，简称 SMG。**

### 十四、2024—2025 年：为什么 DeepSeek 让 SGLang 开始研究更加复杂的 GPU 并行？

### 58. 原来的 Tensor Parallel 为什么不够？

普通 Tensor Parallel：

将一个大型矩阵计算分到多个 GPU。

例如：

```text
GPU 0：
计算矩阵的一部分。

GPU 1：
计算另一部分。

GPU 2：
计算另一部分。

GPU 3：
计算另一部分。
```

最后通过通信组合结果。

这对于 Dense Transformer 很自然。

但 DeepSeek-V3 使用：

**Mixture of Experts，MoE。**

还有：

**Multi-head Latent Attention，MLA。**

它们提出了不同的系统需求。

### 59. 为什么 MLA 会改变 Attention 的并行方式？

DeepSeek MLA 将历史 KV 压缩为更加紧凑的潜在表示。

与普通 MHA 保存大量独立 KV Head 不同，MLA 的缓存和计算结构具有特殊的共享性质。

如果机械地进行高维 Tensor Parallel，可能出现：

同一份压缩 KV 被多个 GPU 重复保存。

这会浪费显存。

因此，SGLang 开始采用：

**Data Parallelism Attention，DP Attention。**

核心思想是：

不同 DP Rank 处理不同 Request 的 Attention。

而不是让多个 Rank 对同一条 Request 的某些 KV 进行重复存储和计算。

### 60. 为什么 MoE 又需要 Expert Parallelism？

假设一个 MoE 模型拥有：

256 个 Expert。

每个 Token 只激活其中一部分。

如果每张 GPU 都保存全部 Expert，显存成本可能极高。

因此，可以将 Expert 分散到不同 GPU。

例如：

```text
GPU 0：
Expert 0～31。

GPU 1：
Expert 32～63。

GPU 2：
Expert 64～95。
```

具体布局取决于 Expert 数量和并行度。

当某个 Token 需要 Expert 50 时，就必须将该 Token 的中间表示发送到保存 Expert 50 的 GPU。

这涉及：

All-to-All Communication。

与普通 Dense Tensor Parallel 的通信形态不同。

### 61. DeepEP 为什么重要？

DeepSeek 开源的 DeepEP 专门优化 MoE Expert Parallel 的通信。

它需要处理：

不同 Token 被路由到不同 Expert。

不同 GPU 之间的 Token Dispatch。

Expert 计算后的结果回传。

而且：

Prefill。

与：

Decode。

具有不同的通信和计算特征。

SGLang 因此需要将：

Attention Parallelism。

Expert Parallelism。

以及推理阶段的资源划分。

协调起来。

### 62. 2025 年 5 月：96 张 H100 的 DeepSeek Serving

2025 年 5 月 5 日，SGLang 团队发布：

*Deploying DeepSeek with PD Disaggregation and Large-Scale Expert Parallelism on 96 H100 GPUs*。

他们使用：

12 台机器。

每台 8 张 H100。

总共：

96 张 H100。

构建 DeepSeek 的大规模推理服务。

其中包含：

PD Disaggregation。

Large-Scale EP。

DeepEP。

DeepGEMM。

Expert Parallelism Load Balancer。

以及 Two-Batch Overlap。

官方报告，在相应 2000 Token 输入设置下，每节点达到约：

```text
52.3K input tokens/s
```

和：

```text
22.3K output tokens/s
```

这里的关键不只是绝对吞吐数字。

而是：

**SGLang 开始把不同计算阶段和不同模型层的并行方式，分别优化。**

### 63. 为什么还要 Prefill–Decode Disaggregation？

因为 Prefill 与 Decode 的资源需求不同。

Prefill：

一次处理大量 Token。

计算量较大。

Decode：

每轮生成少量 Token。

容易受到权重带宽、通信和 KV 访问影响。

如果两个阶段混合执行，可能相互干扰。

所以可以：

```text
Prefill GPU Pool
        │
        │ Transfer KV
        ▼
Decode GPU Pool
```

分别优化。

在 DeepSeek MoE 中，这种分离还能够让不同阶段采用更加合适的 DeepEP 通信模式。

因此，PD 分离不仅是为了避免长 Prefill 打断 Decode。

它还允许整个分布式并行配置更加适合当前阶段。

实际多 GPU、多节点部署还会增加相应的 Worker、通信组和调度组件。

### 65. TokenizerManager 做什么？

主要负责：

接收用户请求。

将文本转换为 Token IDs。

管理请求身份。

记录请求状态。

把请求发送给 Scheduler。

```text

```

经过 Tokenizer：

```python

```

然后构造内部请求对象。

其中包含：

```text
Request ID

Input IDs

Sampling Parameters

Stream Flag
```

再交给 Scheduler。

### 66. 为什么单独设置 DetokenizerManager？

因为模型真正输出的是：

Token IDs。

例如：

```text

```

用户希望看到的却是：

```text
你好，我可以帮助你。
```

所以需要将 Token IDs 转换成文本。

而且在 Streaming 场景中，不能简单逐 Token Decode。

因为某些 Token 可能只对应一个 UTF-8 字符的一部分。

如果直接独立 Decode，就可能出现乱码或替换字符。

因此，DetokenizerManager 会维护增量解码状态。

将生成 Token 正确转换成连续文本。

### 67. Scheduler 做什么？

它维护：

Waiting Queue。

Running Batch。

以及 KV Cache 状态。

决定：

哪些请求进入 Prefill。

哪些请求继续 Decode。

当前是否有足够 KV 空间。

是否需要回收旧缓存。

是否应该暂停某些请求。

本轮如何组织 Batch。

### 68. ModelRunner 做什么？

ModelRunner 真正负责：

准备 GPU 输入。

构造 Attention Metadata。

加载和执行模型。

调用 Attention Backend。

执行 Sampling。

例如：

```text
Input IDs
     ↓
Positions
     ↓
Attention Metadata
     ↓
Transformer Forward
     ↓
Logits
     ↓
Sampler
     ↓
Next Token
```

这里 Scheduler 和 ModelRunner 的职责不同。

Scheduler 负责：

决定本轮做什么。

ModelRunner 负责：

把调度结果真正变成 GPU 计算。

### 69. 为什么使用 ZMQ？

ZMQ：

ZeroMQ。

是一种高性能消息通信库。

SGLang 使用它组织不同进程之间的消息传递。

例如：

```text
TokenizerManager
       │
       ▼
Scheduler
```

以及：

```text
Scheduler
       │
       ▼
DetokenizerManager
```

这样：

网络请求处理。

GPU 任务调度。

文本增量解码。

可以相对独立地执行。

减少单个 Python 进程内部的执行竞争。

### 十七、2025 年：为什么 SGLang 又要把缓存扩展到 CPU 和外部存储？

### 78. GPU KV Cache 终究有容量限制

假设 Agent 已经积累：

100K Token 历史。

当前请求结束以后，SGLang 可以把对应 KV 留在 GPU Cache。

但如果同时存在很多其他用户：

GPU 显存就可能不够。

于是旧 KV 被回收。

当 Agent 下一轮重新提交完整历史时：

系统不得不重新 Prefill。

这就有些浪费。

因为：

这些 KV 曾经计算过。

只是没有足够 GPU 显存继续保存。

### 79. HiCache 的思想

SGLang 后来提出：

**HiCache。**

Hierarchical KV Cache。

分层 KV 缓存。

它借鉴 CPU Cache Hierarchy 的思想，将 KV 存放在不同存储层次。

例如：

```text
L1：
GPU HBM
    │
    ▼
L2：
CPU Host Memory
    │
    ▼
L3：
External / Distributed Storage
```

GPU HBM：

最快。

但容量较小。

CPU Memory：

容量更大。

但访问延迟更高。

外部存储：

可能拥有更大容量。

但网络或磁盘访问成本更高。

### 80. 为什么不是简单把所有 KV 都放 CPU？

因为：

读取 CPU 中的 KV，仍然需要传输到 GPU 或通过对应机制供 Attention 使用。

如果传输成本太高，可能还不如重新计算。

因此，缓存系统需要判断：

直接复用 GPU KV。

从 CPU 读取。

从外部存储读取。

还是重新 Prefill。

这些选择依赖：

Prefix 长度。

存储层级。

传输带宽。

当前 GPU 负载。

以及未来复用概率。

### 81. 为什么还需要 Write-Back Policy？

例如：

一个新的 KV Block 刚刚在 GPU 上产生。

是否应该立即复制到 CPU？

如果每次都复制：

缓存覆盖面更大。

但数据传输开销也更高。

如果只在需要逐出时复制：

可以减少无效写入。

但又可能在内存紧张时形成额外延迟。

因此，HiCache 支持不同的 Write Policy。

例如：

Write-Through。

Write-Back。

以及选择性写入。

这已经与传统多级缓存系统非常相似。

### 十八、2026 年 9 月：为什么 SGLang 又要重构 RadixAttention 本身？

### 82. 2023 年的 RadixAttention 默认了什么？

在最初的典型 Transformer 模型中：

不同 Attention 层主要使用 Full Attention。

因此，如果一个 Prefix 的 KV 已经保存下来，就可以在对应条件下直接复用。

但 2026 年的前沿模型架构发生了变化。

例如：

Full Attention。

Sliding Window Attention。

Gated Delta Attention。

Mamba 类递归状态。

可能同时存在于一个模型内部。

### 83. 为什么 Sliding Window Attention 的缓存规则不同？

假设：

Sliding Window Size：

$$ W=4 $$

当前处理到：

$$ t=10 $$

那么某些层可能只需要：

```text
Token 7

Token 8

Token 9

Token 10
```

对应的历史状态。

更早的 Token KV 不再直接参与这个位置的 Attention。

因此，对于 SWA：

缓存不一定需要保存完整历史。

它更加关注当前有效窗口。

### 84. 为什么 Mamba 又不一样？

Mamba 类模型使用递归状态。

可以抽象为：

$$ s_t=f(s_{t-1},x_t) $$

因此：

要从位置 $t$ 继续执行，需要的是位置 $t$ 对应的正确递归状态。

而不是简单获得该位置之前的全部 Full Attention KV。

假设模型当前缓存了：

```text
Prefix A B C D
```

对应的某个 Mamba State。

如果要从相同 Prefix 继续生成，可以复用该状态。

但如果 Prefix 不同，或者状态边界不一致，就不能直接复用。

### 85. 为什么原来的 Radix Tree 不够？

因为原来的共享逻辑主要围绕：

Token Prefix。

与：

Full Attention KV。

建立映射。

但 Hybrid Model 需要同时回答：

Full Attention KV 是否完整？

SWA 需要的最近窗口是否存在？

Mamba 的正确 State Checkpoint 是否存在？

如果不同组件需要不同的缓存结构，就很容易产生大量特殊实现。

例如：

```text
Full Attention Cache

Full + SWA Cache

Full + Mamba Cache

Full + SWA + Mamba Cache
```

随着架构组合增多，维护成本就会迅速提高。

### 86. Unified Radix Cache 怎样解决？

2026 年 9 月 23 日，SGLang 发布：

*Unified Radix Cache in SGLang: One Tree for Hybrid Model Prefix Caching*。

它提出：

**一棵共享 Prefix Tree，加上多个可插拔的缓存组件。**

例如：

```text
Unified Radix Tree
                       │
              Shared Prefix Identity
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
       FULL KV      SWA Window   Mamba State
```

每个 Radix Node 可以拥有不同组件对应的 Slot。

例如：

Full Attention 保存完整相关 KV Page。

SWA 保存有效窗口。

Mamba 保存边界对应的递归状态 Checkpoint。

### 87. 什么叫 Safe Reuse Boundary？

假设某个请求匹配到长度为：

$$ T $$

的 Token Prefix。

但不同模型组件的缓存情况不同。

例如：

Full Attention：

可安全复用到 Token 1000。

SWA：

可安全复用到 Token 800。

Mamba：

只保存了 Token 768 位置的有效状态。

那么系统不能直接从 Token 1000 继续。

因为 Mamba 和 SWA 的必要状态可能不存在。

必须选择一个所有组件都能正确恢复的边界。

即：

**Safe Reuse Boundary。**

在简单的连续可用前缀情形下，可以直观理解为取所有必要组件共同支持的最深边界。

但对于真实实现中的窗口、Checkpoint 和被逐出的状态，还必须由组件分别验证候选边界的可用性。

### 88. 为什么这次重构很重要？

因为 Radix Tree 不再只是：

Full Attention KV 的索引。

它开始成为：

**多种模型状态共享的统一身份系统。**

同一个 Prefix，可以关联：

Full KV。

SWA 状态。

Mamba 状态。

以及不同存储层次的缓存位置。

从 2023 年到 2026 年，RadixAttention 的核心思想依然是：

识别共享 Prefix。

复用已经计算的历史。

但它管理的状态类型已经发生了很大变化。

### 十九、2026 年的 Unified Radix Cache 实际改善了多少性能？

### 89. DeepSeek-V4-Flash 的多轮实验

SGLang 团队使用：

4 张 H200。

TP4。

48 个并发客户端。

每个客户端进行 60 轮交互。

每轮约：

4096 个新增输入 Token。

以及：

16 个输出 Token。

比较三种缓存布局。

第一种：

只使用 GPU L1 Cache。

第二种：

GPU + CPU L2。

第三种：

GPU + CPU + Mooncake L3。

### 90. 实验结果

| 缓存层级 | Effective Input Throughput |
| --- | --- |
| L1 | 9.4K tokens/s |
| L1 + L2 | 14.3K tokens/s |
| L1 + L2 + L3 | 145.5K tokens/s |

在 L3 设置下，后续轮次的 Prefix Cache Hit Rate 接近：

$$ 98\% $$

这个结果非常显著。

但这里的：

Effective Input Throughput。

不是 GPU 实际重新执行了多少 Input Token 的 Forward。

它计算的是：

完整逻辑 Prompt Token 数量。

除以：

实际执行时间。

因此，如果大量 Prefix 被缓存命中，系统不需要重新计算这些 Token，就能够报告很高的 Effective Input Throughput。

这正是缓存复用的价值。

### 91. 为什么这对长程 Agent 特别有意义？

假设一个 Agent 运行：

100 轮。

每一轮都携带此前历史。

那么完整 Prompt 长度可能不断增长：

```text
Round 1：
4K

Round 2：
8K

Round 3：
12K

...

Round 100：
400K
```

如果每轮都重新 Prefill 全部历史，累计计算成本会非常高。

而如果系统能够保留和复用大部分历史状态：

真正需要重新计算的，主要是每轮新增部分。

因此：

**长程 Agent 的核心推理成本，越来越取决于历史状态能否跨轮保留，而不只是单次 Forward 有多快。**

### 二十、2026 年：Breakable CUDA Graph 为什么又成为 SGLang 的重要创新？

### 92. 为什么 CUDA Graph 可以加速推理？

普通 PyTorch Eager Execution 可能需要 CPU 多次启动 GPU Kernel。

例如：

```text
CPU Launch：
RMSNorm

CPU Launch：
QKV Projection

CPU Launch：
RoPE

CPU Launch：
Attention

CPU Launch：
MLP
```

即使每个 Kernel 本身执行得很快，也需要 CPU 不断提交任务。

CUDA Graph 可以提前记录一组 GPU 操作。

后面直接 Replay。

例如：

```text
Capture Once
      ↓
Replay Graph
      ↓
GPU 执行多个 Kernel
```

从而减少 CPU Launch Overhead。

### 93. 但为什么不能把所有操作都直接放进 CUDA Graph？

因为真实模型中存在：

动态 Shape。

运行时控制流。

某些不支持 Graph Capture 的算子。

依赖外部信息的操作。

以及特殊的内存管理路径。

如果某个操作无法被 Capture，就可能阻断整个连续的 Graph。

### 94. Breakable CUDA Graph 的思想

2026 年 8 月 27 日，SGLang 发布：

*Breakable CUDA Graph in SGLang: 5× Faster Graph Builds, 1.93× Faster Prefill*。

它将执行过程拆成：

```text
CUDA Graph Segment A
        │
        ▼
Eager Operation
        │
        ▼
CUDA Graph Segment B
```

这样：

能够 Capture 的部分继续使用 CUDA Graph。

无法 Capture 的部分保留 Eager Execution。

### 95. 为什么不直接依靠 torch.compile？

一种方案是：

使用 `torch.compile` 追踪完整计算图。

然后在特定位置拆分。

但对于复杂大模型：

Graph Tracing。

Compilation。

以及自定义 Kernel 的适配。

可能非常昂贵。

SGLang 的 Breakable CUDA Graph 允许在 Capture 过程中直接设置断点。

不需要让 Compiler 完整理解整条 Forward。

### 96. 它究竟节省了什么？

官方报告：

在相关 Prefill Graph Build 实验中，Breakable CUDA Graph 的构建速度比 `torch.compile` Piecewise 方案快约 3.8～5.2 倍。

在部分 Prefill Benchmark 中，完整 Capture 可达到约 1.93 倍的 Eager 性能。

Breakable CUDA Graph 自身也显著加速了 Prefill。

这里的核心变化是：

**让高效 GPU 执行不再完全依赖复杂的整图编译。**

这也是为什么 SGLang 不仅在 KV Cache 和 Scheduler 上创新，还持续研究 CUDA Graph 和 Kernel Execution。

### 二十一、2026 年：SGLang 为什么又扩展到 Diffusion 和 Omni？

### 97. 文本自回归并不是全部生成任务

早期 SGLang 主要面向：

Autoregressive Text Generation。

即：

```text
Token 1
   ↓
Token 2
   ↓
Token 3
```

但现代生成模型还包括：

Text-to-Image。

Text-to-Video。

Audio Generation。

Speech-to-Speech。

Omni-Modal Model。

其中某些模型采用：

Diffusion。

或者多阶段生成结构。

例如：

```text
Text Encoder
      ↓
Semantic Representation
      ↓
Audio Token Generator
      ↓
Vocoder
      ↓
Waveform
```

这已经不适合直接套用普通文本 Decode Loop。

### 98. SGLang Omni 怎样重新划分执行结构？

SGLang Omni 使用多阶段 Pipeline Runtime。

逻辑上可以表示为：

```text
HTTP API
    │
    ▼
Client
    │
    ▼
Coordinator
    │
    ▼
Stage 1
    │
    ▼
Stage 2
    │
    ▼
Stage 3
    │
    ▼
Output
```

每个 Stage 可以拥有：

自己的 Scheduler。

自己的 Model Runner。

自己的 Device Placement。

以及阶段间数据传输逻辑。

例如：

Audio Model 可能需要多个阶段协作。

Image/Video Model 可能需要扩散步骤调度。

这与普通文本 Serving 中的：

```text
TokenizerManager
      ↓
Scheduler
      ↓
ModelRunner
```

有明显区别。

### 99. 为什么它仍然属于 SGLang 的技术路线？

因为核心问题没有变：

**怎样将复杂生成任务组织成可以高效执行的计算流程？**

早期 SGLang 使用：

Frontend Language。

表示多次 LLM 调用之间的程序结构。

后来 SGLang Runtime 优化：

KV Cache。

Scheduler。

GPU Kernel。

现在 Omni 又进一步将生成任务拆成：

多个执行阶段。

因此，SGLang 最初的 LM Program 思想，并没有完全消失。

它在新的多模态系统中，以更加底层的 Pipeline Orchestration 形式重新出现。

### 二十二、2026 年：为什么 SGLang 与 Miles 开始共同发展 Agentic RL？

### 100. RL Rollout 与普通 Serving 有什么区别？

普通 Serving：

```text
User Prompt
     ↓
Model Generate
     ↓
Return Output
```

而 Agentic RL：

```text
RL Trainer
    │
    ▼
Rollout Server
    │
    ▼
AgentLoop
    │
    ├── LLM Generate
    ├── Tool Call
    ├── Observation
    └── LLM Generate
    │
    ▼
Trajectory
    │
    ▼
Reward
    │
    ▼
Policy Update
```

这里的推理引擎不仅需要快。

还需要支持：

多轮请求。

权重更新。

较高并发。

复杂 Tool Call Format。

长上下文缓存。

以及训练与推理概率分布的一致性。

### 101. 为什么训练权重同步如此重要？

假设：

Rollout Server 当前加载：

$$ \theta_t $$

Trainer 更新得到：

$$ \theta_{t+1} $$

下一轮采样如果继续使用：

$$ \theta_t $$

就可能产生 Policy Staleness。

因此需要将新的模型权重同步到 Rollout Engine。

如果模型是大规模 MoE：

还需要考虑：

模型并行布局。

Expert 分布。

训练权重格式。

推理权重格式。

以及传输开销。

这已经不是简单的：

```python
model.load_state_dict(...)
```

可以概括的问题。

### 102. 为什么 SGLang 会与 Miles 结合？

Miles 是围绕大规模 RL Post-Training 发展的训练系统。

而 SGLang 擅长：

高效生成 Rollout。

Serving。

复杂模型推理。

因此两者的结合具有很自然的职责分工。

例如：

```text
Miles：
RL Algorithm
Training
Reward
Weight Update

SGLang：
Inference
Rollout
Serving
Sampling
KV Cache
```

但真正困难的部分是：

它们必须在实际系统中正确协调。

### 103. 2026 年 10 月 14 日的 Step 5 Preview 实验

SGLang 和 Miles 团队发布：

*Step 5 Preview: Day-0 Inference and RL Support with SGLang and Miles*。

它不仅展示模型的推理性能。

还报告了：

一个 79-Step 的 GRPO 训练实验。

训练数据：

DAPO-Math-17K。

每 Step：

256 个 Sample。

Response Cap：

2048 Token。

实验中的五步移动平均 Reward 从约：

$$ 0.44 $$

上升至：

$$ 0.75 $$

同时记录：

Trainer 与 Rollout 侧的概率差异。

以及 Token-Level KL。

这说明：

SGLang 正在被放进完整的 RL Training Loop 中测试。

而不再只是独立的模型推理服务。

### 104. 这里最重要的技术问题是什么？

**推理引擎实际生成的 Token，究竟来自什么概率分布？**

如果 Rollout 端使用：

不同的数值精度。

不同的 MoE Routing。

不同的 Sampling Kernel。

或者不同的工具调用格式处理方式。

那么训练端重新计算：

$$ \log\pi_\theta(a_t\mid s_t) $$

时，可能获得不同结果。

这就是：

Train–Inference Mismatch。

因此，SGLang 与 Miles 的协作，也开始关注：

Rollout Probability。

Trainer Probability。

Policy Synchronization。

以及 RL 的数值稳定性。

这与 2026 年 vLLM 开始研究训练—推理一致性，属于同一个更大的系统趋势。

### 二十三、SGLang 与 vLLM 到底谁更好？历史差异比简单跑分更重要

### 105. 两者最初研究的问题不同

vLLM：

从大模型 Serving 的 KV Cache 内存管理出发。

最重要的早期贡献是：

PagedAttention。

SGLang：

从复杂 LM Program 的执行效率出发。

最重要的早期贡献包括：

Frontend Language。

RadixAttention。

Compressed FSM。

以及程序结构与 Runtime 的协同优化。

### 106. 但到 2026 年，两者功能高度重叠

| 维度 | vLLM | SGLang |
| --- | --- | --- |
| 原始研究出发点 | 高效 KV 内存管理 | 高效 LM Program 执行 |
| 代表性早期创新 | PagedAttention | RadixAttention |
| Continuous Batching | 支持 | 支持 |
| Prefix Caching | 支持 | 支持 |
| Paged KV | 支持 | 支持 |
| Speculative Decoding | 支持 | 支持 |
| Structured Output | 支持 | 支持 |
| Tensor/Expert Parallelism | 支持 | 支持 |
| Prefill–Decode 分离 | 支持 | 支持 |
| 分层 KV Cache | 支持相关方案 | HiCache |
| Agentic RL | veRL 等集成 | Miles、veRL 等集成 |
| 多模态 | 广泛支持 | SGLang Omni / Diffusion |

这意味着：

不能因为 SGLang 发明了 RadixAttention，就认为 vLLM 不懂 Prefix Caching。

也不能因为 vLLM 发明了 PagedAttention，就认为 SGLang 没有高效的分页 KV 内存管理。

两者后来不断吸收相似的工程技术。

### 107. 为什么一些任务中 SGLang 可能更快？

例如：

大量请求共享长 Prefix。

复杂结构化输出。

某些特定 MoE 模型拥有专门优化的 SGLang Kernel。

某些硬件平台上的推理后端实现更成熟。

这些情况下，SGLang 可能获得明显优势。

### 108. 为什么另一些任务中 vLLM 可能更快？

例如：

特定模型已经拥有高度优化的 vLLM Backend。

某种硬件架构对应的 Model Runner 更高效。

特定 Batch Size、Prefill/Decode 比例或 Speculative Decoding 设置更加适合 vLLM。

这些情况下，vLLM 也可能取得更好的性能。

所以真正需要比较的不是：

```text
SGLang Benchmark Maximum Speedup

VS

vLLM Benchmark Maximum Speedup
```

而是相同模型、硬件和请求分布下的：

TTFT。

TPOT。

Overall Throughput。

Goodput。

GPU Memory。

KV Cache Hit Rate。

以及实际成本。

### 二十四、怎样在本地真正运行 SGLang？

### 109. 启动一个模型服务

例如：

```bash
python -m sglang.launch_server \
  --model-path Qwen/Qwen3-0.6B \
  --host 127.0.0.1 \
  --port 30000
```

这会启动 SGLang Server。

模型会被加载到可用计算设备。

后续可以通过 HTTP 请求模型推理。

现代版本也支持：

```bash
sglang serve \
  --model-path Qwen/Qwen3-0.6B \
  --port 30000
```

### 110. 使用 OpenAI-Compatible API

```python
from openai import OpenAI

client = OpenAI(
    base_url="http://127.0.0.1:30000/v1",
    api_key="EMPTY",
)

response = client.chat.completions.create(
    model="Qwen/Qwen3-0.6B",
    messages=[
        {
            "role": "user",
            "content": "什么是 PPO？",
        }
    ],
    max_tokens=256,
)

print(response.choices[0].message.content)
```

这与调用远程 OpenAI-Compatible Server 的体验类似。

但真正执行模型的是本地 SGLang。

### 111. 使用 SGLang Frontend Language

也可以使用：

```python
import sglang as sgl

sgl.set_default_backend(
    sgl.RuntimeEndpoint(
        "http://127.0.0.1:30000"
    )
)

@sgl.function
def explain(s, question):
    s += sgl.user(question)
    s += sgl.assistant(
        sgl.gen("answer", max_tokens=256)
    )

state = explain.run(
    question="什么是策略梯度？"
)

print(state["answer"])
```

这里能够清楚看到 SGLang 的两种使用方式。

第一种：

作为普通 Serving Engine。

第二种：

作为 LM Program Runtime。

这也是理解 SGLang 历史身份最重要的一点。

### 二十六、结语：SGLang 的技术史，为什么最终回到了它最初的 LM Program 思想？

回头看这段历史，会发现 SGLang 的发展其实存在一条很有意思的循环。

2023 年，研究者提出 SGLang 时，最关心的问题是：

语言模型不应该只是一个孤立的文本生成函数。

因为真实应用越来越复杂。

一个任务可能包含：

多次生成。

条件分支。

并行调用。

结构化输出。

以及大量共享历史。

所以，研究者提出：

**Language Model Program。**

希望将这些复杂工作流描述成一套更加明确的程序。

而且，他们并不满足于只提供漂亮的 Python API。

还希望让底层 Runtime 理解程序结构，并据此复用计算。

于是：

RadixAttention 出现了。

它把不同请求的 Token Prefix 组织成 Radix Tree。

让多个分支共享已经计算过的 KV Cache。

Compressed FSM 则利用结构化输出的确定性，减少不必要的 Token-Level Decode。

API Speculative Execution 又尝试利用程序已知的后续结构，提前计算未来可能需要的结果。

这三项技术都体现了 SGLang 最初的设计思想：

**如果系统知道生成任务之间的结构关系，就不应该把每次 LLM 调用都当成完全独立的黑盒操作。**

但到了 2024 年，SGLang 发现，即使用户完全不使用它的 Frontend Language，Runtime 本身也已经具有很大的工程价值。

于是项目开始更加专注于：

Serving。

Batch Scheduler。

KV Cache。

GPU Kernel。

以及模型并行执行。

2024 年 12 月的 v0.4，进一步将 Overlap Scheduler、Cache-Aware Router、DP Attention 和 XGrammar 推向成熟。

2025 年，DeepSeek-V3 和 DeepSeek-R1 的出现，又迫使 SGLang 进入大规模 MoE 推理。

它开始研究：

Prefill–Decode Disaggregation。

Expert Parallelism。

DeepEP Communication。

DeepGEMM。

MoE Load Balancing。

以及更复杂的分布式执行。

这一时期，SGLang 看起来越来越像一个完整的 GPU 推理系统。

它最初的 LM Program Frontend，似乎反而不再是项目最显眼的部分。

但到了 2026 年，长程 Agent 和 Hybrid Model 又把一个古老的问题重新带到了台前。

**不同生成请求之间，究竟共享了哪些历史？**

对于普通聊天，这个问题可能只是：

能否复用 System Prompt？

但对于长程 Coding Agent：

一次任务可能持续几十分钟。

经历几百次工具调用。

维护数十万 Token 的工作历史。

每次重新调用模型时，又需要重新提供大量相同的上下文。

如果这些历史 KV 不断丢失，那么即使 GPU 的单次 Forward 已经非常快，整个 Agent 仍然会反复支付昂贵的 Prefill 成本。

于是，RadixAttention 重新成为系统的核心。

但这一次，它管理的不再只是传统 Full Attention 的 KV。

而是：

Full Attention KV。

Sliding Window State。

Mamba Checkpoint。

GPU Cache。

CPU Cache。

外部分布式 KV Pool。

以及跨轮的 Session State。

因此，2026 年的 Unified Radix Cache，实际上是 2023 年 RadixAttention 思想的一次重要扩展。

而 SGLang Omni 的多阶段 Pipeline，也在另一个维度重新研究：

怎样让复杂生成任务的不同阶段能够被高效调度和执行？

与此同时，Miles 与 SGLang 的结合，又让推理系统进入 Agentic RL 训练闭环。

这意味着：

SGLang 不仅需要完成生成。

还要支持模型权重更新后的 Rollout。

支持多轮工具调用。

支持训练与推理的概率一致性检查。

并且尽量复用长程交互中已经计算过的历史状态。

所以，SGLang 的技术史并不是：

一个 Prompt DSL 被 GPU Serving Engine 取代的故事。

它更像：

**最初为复杂 LM Program 设计的执行思想，在大规模模型、混合架构和长程 Agent 时代，逐渐演化为更加底层的推理系统能力。**

如果一定要将这段历史压缩成一句话，我认为应该是：

**vLLM 最初让大模型能够更高效地保存和访问 KV Cache，而 SGLang 最初进一步追问：既然不同的语言模型调用本来就共享大量计算历史，为什么推理系统不能直接理解并利用这种程序结构？**

从 2023 年的 RadixAttention，到 2026 年的 Unified Radix Cache，SGLang 一直在研究这个问题。

只是共享的对象，已经从简单的 Token Prefix，逐渐扩展到整个长程智能体的多种内部计算状态。

因此，未来 SGLang 真正值得关注的方向，可能并不是某一个新模型又取得了多少 Tokens/Second。

而是：

当越来越多 AI 系统开始自主执行长程任务时，推理基础设施能否将模型反复经历的历史，转化成可以跨轮、跨 GPU、跨节点不断复用的计算资源？

过去，我们总把一次 LLM 调用视为：

输入 Prompt。

计算 Forward。

输出 Response。

但到了 Agent 时代，一次模型调用往往只是整个任务生命周期中的一小段。

真正昂贵的不是这一小段生成本身。

而是模型在数百次调用中，不断重新理解那些它已经处理过的历史。

**SGLang 最初希望让推理系统理解 LM Program，而它今天正在尝试让推理系统理解一个长程智能体的计算历史。**

这也许才是 RadixAttention 从一项缓存优化，逐渐成长为现代 Agentic Serving 核心基础设施的真正原因。
