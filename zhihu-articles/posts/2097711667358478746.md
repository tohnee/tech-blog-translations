有意思，[DeepSeek 前几天刚开源了专门跑自家模型的 DeepInfer](https://www.zhihu.com/question/2095922064804636469/answer/2095936165174166124)，然后这次 vLLM 现在就说[自己跑 DeepSeek V4.1 Flash 的性能也已经差不多了](https://vllm.ai/blog/2026-10-23-deepseek-v41-flash-pd-wide-ep)。

vLLM 拿 DeepInfer 官方曲线做的对照，在 131K 上下文、Batch 8–256 的 Decode 测试里面，**两者吞吐差距能缩到 6% 以内，**要知道 DeepInfer 原本就是从 vLLM 起步，再针对 DeepSeek 的模型做了很多专项优化，现在 vLLM 又把 DeepSeek 开放的 Kernel 接回来，这大概就是开源的魅力了吧？。

![](https://picx.zhimg.com/v2-6022e6aecf32944a7a2f30c8b85582bf_r.jpg)

> **比如这里给出的是，64 张 GB300 组成一套服务，平均折算每张 GPU 每秒处理 95.4 万 Token，比之前的单节点方案高了 7.9 倍**。

比如用户已经聊了 128K 的历史，而且这部分命中了前缀缓存，现在又发来 32K 新内容，正常服务器需要要处理输入，也就是 Prefill，然后才是一个 Token 接着一个 Token 往外生成去 Decode。

**vLLM 让两组 GPU 分头负责，前面算完就把 KV Cache 交给后面，而 V4.1 Flash 本身又把 KV Cache 压得很小，这样同一张卡可以同时照顾更多长会话**。

这里比较有意思的是，**处理输入的时候，GPU 反而不适合绑得太多，**因为 Agent 的请求长度差异很大，有的只增加几百 Token，有的一次进来几万 Token，如果四张卡绑成一组，碰上长输入就容易互相等待，所以 vLLM 发现两卡一组反而更合适。

**除此之外，它还把一些没必要重复做的计算省掉，比如第 20 层还是写入所有新 KV，但后续只对最后 128 个 Token 继续计算，这一组 Prefill 优化在 32K 新输入下带来了 42.5% 的吞吐提升**。

然后到了 Decode 情况就反过来了，因为 V4.1 Flash 每次生成主要花时间在读取 MoE 专家权重，这时候把专家摊到更多 GPU 上，大家各读一小部分，速度就上来了。

**vLLM 把这叫 Wide-EP，不过专家也有冷热之分，不能让一张卡天天处理热门专家，其他卡没活干，所以还要靠 EPLB 动态挪动专家的位置**，甚至连负责提前猜 Token 的 DSpark 小模型也要一起照顾，最终在 32 卡的一组测试里，**专家负载均衡让 Decode 吞吐提高了 25%**。

![](https://pic2.zhimg.com/v2-db7d9c29476cbd973f0be882ce7dc273_r.jpg)

结果 GPU 越跑越快之后，vLLM 又遇到一个更有意思的问题：

> **32 卡的 GPU 计算明明比 16 卡快，整轮 Decode 却反而更慢了**。

然后问题就来到了 CPU ，原因是 CPU 在拖后腿，比如生成线程还在同步等待 KV 传输、几十张卡之间反复同步，或者突然有一大批请求一起进来，都会让 GPU 停下来干等。

所以 vLLM 团队又把 KV 传输挪出生成主循环，减少同步，同时限制一次接入的请求数量，这样 GPU 省下来的时间这才真正变成了吞吐。

最后再看和 DeepInfer 的对比就挺清楚了：**DeepInfer 重点把 DeepSeek 自家模型的底层计算做好，而 vLLM 是在接近这个计算性能的同时，把 Prefill/Decode 分离、KV 传输和整机柜的请求调度接了起来。**
