给大模型发去一份长文档，第一次等了很久才开始出字。接着追问一句，明显快了。于是我们打开前缀缓存、增加缓存容量，再接上共享存储，希望把这种加速保留下来。

但上线后，可能看到另一种情况：监控里的缓存命中率已经超过 90%，用户仍然抱怨响应慢；Host 内存给得更多了，首字延迟却没怎么改善；明明使用了 Mooncake，请求换到另一台机器后还是重新计算。

这些现象并不矛盾。**缓存命中表示有一部分计算结果可以复用。它没有回答结果在哪里、多久能送到 GPU，以及请求还需要等什么。**

我们跟着一段多轮对话，看看这几个问题是怎样连在一起的。下文以 SGLang HiCache 的常规 GPU 推理路径和 Mooncake Store 为例，讨论可复用的前缀 KV；文中的请求长度、时间和带宽数字均为教学假设，不是线上实测。

**先说清楚，KV Cache 缓存了什么。**

假设你上传了一份文档，然后问：“请概括这份文档。”模型会先处理输入，这个阶段通常叫 Prefill；随后逐步生成回答，也就是 Decode。

在常见的自回归 Transformer 中，Attention 会为已经处理过的 token 生成 Key 和 Value。后面的 token 需要参考前面的内容，保存这些中间结果，就能避免每生成一个新 token 都把整段历史重新算一遍。

这就是 KV Cache 的基础作用。在此之上，前缀缓存又做了一件事：一次请求结束后，保留能够复用的 KV，让后续请求也有机会受益。两者有关联，但“生成过程中需要 KV”不等于“请求结束后一定继续保留可复用前缀”。

如果第二次请求仍然包含同一份文档，只是在末尾增加一句“其中最大的风险是什么”，那么公共前缀的 KV 就可能被复用。它并没有保存第二个问题的答案；模型仍需要处理新增内容，并生成新的回答。

这里的“相同”也比人眼看到的相似更严格。普通前缀缓存依赖兼容的模型状态与实际 token 前缀；聊天模板、系统提示词或前面某段内容改变，都可能缩短可复用的范围。同一段文字放在不同的前文之后，其 KV 通常也不同，不能随意抽出来拼接。

可以先把请求想成这样：

```text
第一次：[系统提示词 | 长文档 | 问题 A]
第二次：[系统提示词 | 长文档 | 问题 B]
         └──可能复用的公共前缀──┘
```

真实多轮对话还会带上此前的问答。上图只保留理解前缀复用所需的部分。

**第二次很快，是因为结果还在手边。**

假设这段公共前缀的 KV 仍在同一个推理实例的 GPU 显存里。后续请求找到它，就可以复用相应位置上的 KV，不必先从主机内存或外部存储搬回来。

这是最容易理解的命中，也是我们通常对“命中缓存”的直觉：东西已经准备好了，马上就能用。

但显存还要放模型权重、正在运行的请求的 KV，以及算子工作空间等数据。服务不断接收新请求，曾经有用的前缀不可能永远留在 GPU 上。

如果为了接纳当前请求，需要释放某段前缀占用的显存，我们有两个选择：以后遇到它时重新计算，或者先把它保存在容量更大的地方。分层 KV Cache 就是在这两种成本之间做选择。

在 HiCache 的命名中，GPU 显存是 L1，推理实例自己的 Host 内存是 L2，外部存储后端是 L3。这里的层级由推理系统管理，与 CPU 芯片里自动工作的 L1、L2、L3 硬件缓存不是一套机制。[HiCache 设计说明](https://docs.sglang.io/docs/advanced_features/hicache_design)

*图 1：A、B 各有自己的 L1 和 L2。通过兼容配置连接同一个共享 L3，才有机会复用对方写入的 KV。图中箭头表示逻辑数据路径，省略多 rank、分页和异步流水。*

**隔一会儿再来，命中的可能已经是内存。**

假设这段前缀已在 L2 留下可用副本，L1 对应空间随后被释放。第三次请求到来时，引擎仍然能找到它，因此仍然可以报告缓存命中。

区别在于，GPU 计算前，需要把所需 KV 从 Host 内存恢复到显存。这个过程通常叫 load-back。它节省了重算前缀的工作，却增加了数据搬运。

这和查资料很像：书放在桌上，伸手就能翻；书放在隔壁书架上，也算“已有资料”，但要先取回来。这个类比只帮助理解位置的差别；实际系统还可以分页传输、分层加载，让搬运与计算重叠，不一定等整段数据全部到齐再开始工作。

所以 **L2 命中不代表一次完整的额外搬运时间都会暴露在请求延迟里，也不代表搬运完全没有代价**。关键是有多少搬运留在了请求必须等待的路径上。

缓存还可以同时有多个副本。L1 和 L2 同时保存一段 KV 很正常；“L1 淘汰”只说明 GPU 这一层释放了相应空间，不能据此断言所有层的数据都被删除了。

**换一台机器，还能找到之前的 KV 吗？**

现在第四次请求被分配给了实例 B。之前处理文档的是实例 A，KV 保存在 A 的 Host 内存里。

给 A 增加更多 L2，并不会自动让 B 能读取 A 的 L2。即使两个实例部署在同一台物理机器上，各自管理的 Host 缓存也不能直接当成一个共享缓存池。

要实现跨实例复用，一种办法是把 KV 写入共享的 L3，让 B 按相容的 key、命名空间和存储格式找到它。SGLang 可以把 Mooncake Store 作为这样的后端。**L3 表示外部存储接口这一层；是否真的跨机器共享，取决于后端及其配置。** 例如，一个指向节点本地目录的文件后端，并不会因为叫 L3 就变成集群共享存储。[HiCache 配置与共享范围](https://github.com/sgl-project/sglang/blob/37ae292e6f84cb8ec9503892d6cf74f9c8b2bfaf/docs/docs/advanced_features/hicache_best_practices.mdx#L9-L11)

有了可复用的 L3 数据，在本文讨论的常规 HiCache 路径中，B 会把需要的部分预取到本地 L2，再加载到 GPU 使用。这样避免了重算，但读取外部存储、经过网络以及 Host 到 GPU 的搬运，都可能占用时间和带宽。

如果 Mooncake Store 启用了 SSD offload，而且对象只剩磁盘副本，读取路径还会多出磁盘 I/O。对接入它的 SGLang 来说，后端仍然是 Mooncake；SSD 是 Store 内部的存储层次，不能直接写成“HiCache 固定有一个 L4”。[Mooncake SSD offload 设计](https://github.com/kvcache-ai/Mooncake/blob/b140c1a904d53d24ed211d01ce9a87fc161cb432/docs/source/design/store/ssd-offload.md)

![](https://pic1.zhimg.com/v2-38cb3774ff59a60e26b3ec244ece077e_r.jpg)

这里还有一个容易误解的现象：某段 KV 先从 L3 拉回，下一次访问直接在 L2 命中。第二次的命中来源可以记为 Host，而不是 Storage。**当前这次从哪一层取到，与数据最初从哪里来，是两种统计问题。**

**“用了 Mooncake”还不能说明缓存已经共享。**

Mooncake 里有两个与本文直接相关的组件。

Transfer Engine 提供数据传输能力。Store 则在传输能力之上管理可复用的缓存对象，提供查询、读写、空间管理和驱逐等功能。Store 的 Master 主要管理元数据和资源；KV 数据在客户端或存储节点之间流动，并不要求先经过 Master 再转发。[Transfer Engine 设计](https://github.com/kvcache-ai/Mooncake/blob/b140c1a904d53d24ed211d01ce9a87fc161cb432/docs/source/design/transfer-engine/index.md) · [Store 设计](https://github.com/kvcache-ai/Mooncake/blob/b140c1a904d53d24ed211d01ce9a87fc161cb432/docs/source/design/store/mooncake-store.md)

在 Prefill/Decode 分离部署中，Prefill 算出的 KV 要交给 Decode，Transfer Engine 可以承担这段传输；HiCache 的 L3 则负责把缓存保留下来，供之后的请求复用。这是两条目的不同的数据路径：

```text
这一次请求的交接：Prefill ──KV 传输──→ Decode
跨请求的缓存复用：实例本地缓存 ←──→ 共享 Store
```

因此，配置 P/D 传输使用 Mooncake，并不能单独证明 HiCache 已经启用了 Mooncake Store。判断时要看相应的存储后端配置及真实读写行为，而不是只看命令里是否出现了 `mooncake`。[SGLang P/D 说明](https://github.com/sgl-project/sglang/blob/37ae292e6f84cb8ec9503892d6cf74f9c8b2bfaf/docs/docs/advanced_features/pd_disaggregation.mdx)

**命中值不值得，要比较取回与重算的代价。**

先把排队等其他因素固定，只比较同一段前缀的两条处理路径：

```text
复用路径：查找 + 等待/搬运 + 剩余计算
重算路径：前缀重算 + 剩余计算
```

这是帮助判断的成本模型，不是逐项相加就一定等于真实延迟的公式。实际执行会发生重叠，而且复用与重算也可能改变 batch 形态。

用一个极简的教学例子：假设本次需要恢复的 KV 共 8 GB，实际有效传输带宽是 20 GB/s，只算数据经过这段链路的时间，就是 0.4 秒。若带宽竞争让有效带宽降到 4 GB/s，同一批数据就需要约 2 秒。

再假设，这段前缀在当前计算条件下重算需要 1 秒。如果其他开销相同、搬运也没有被计算掩盖，那么前一种情况下复用有优势，后一种情况下等待恢复反而可能更慢。

这个例子没有给任何硬件排名。8 GB 是显式假设，不能直接从“多少个 token”套出来；模型结构、KV 精度、并行切分和数据布局都会影响真实字节数。网卡标称带宽也不能直接当作应用的有效带宽。

这也解释了为什么系统需要预取策略：等更多数据回来，可能减少重算；尽早停止等待，可能让请求更早执行。SGLang 提供 `best_effort`、`wait_complete` 和 `timeout` 等策略，分别表达尽力预取、等待完成和受超时约束的等待。选哪一个，应当看端到端延迟与负载，而不只是命中率。[预取策略配置](https://github.com/sgl-project/sglang/blob/37ae292e6f84cb8ec9503892d6cf74f9c8b2bfaf/docs/docs/advanced_features/hicache_best_practices.mdx#L66-L74)

共享系统还多一层取舍：重算会消耗 GPU，恢复会消耗存储和互连资源。单条请求最快的选择，未必让整批请求都最快。因此最终要在目标并发下验证。

**90% 命中率，为什么仍然可能等很久？**

首先要问，这个 90% 的分母是什么。

如果它是按输入 token 统计的前缀命中率，那么一个 10 万 token 的请求命中 9 万，仍然留下 1 万个 token 要处理。新增部分的 Attention 还需要访问此前的上下文。省去了大量前缀计算，并不意味着剩余计算量、访存量和时间都严格缩小为原来的 10%。

整个服务的 90%，也不意味着每个请求都命中 90%。长请求在按 token 加权的指标里占比很大；高命中的流量完全可能掩盖另一批低命中请求的长尾。

更关键的是，命中率描述的是复用情况，用户感受到的是从发出请求到收到第一个 token 的时间，也就是 TTFT。它还受到接入处理、排队、KV 准备、剩余 Prefill、P/D 交接和首 token 返回等环节影响。不同实现可以让其中部分过程重叠，不能把每个监控阶段的时长机械相加。

看下面两组教学数字。为了展示关系，图中把时间抽象成互不重叠的两段，“其他等待与处理”包含此次缓存优化没有改善的部分：

![](https://pic1.zhimg.com/v2-38cb3774ff59a60e26b3ec244ece077e_r.jpg)
*图 3：两组情况下，与缓存相关的准备和计算都从 2.0 秒降到 0.6 秒。其他部分只有 0.5 秒时，总时间下降 56%；其他部分长达 10 秒时，总时间只下降约 11.7%。全部数值均为教学假设。*

后一种情况下，缓存优化依然节省了计算，只是请求的大部分时间仍然花在别处。若同时增加了外部缓存读取等待，端到端收益还可能进一步缩小。

P/D 分离时尤其要注意：Prefill 缓存命中，也不代表 Decode 已经有足够的 KV 空间、请求已经获准执行，或者交接已经完成。某一层表现很好，不能保证整条请求路径都畅通。

**把 Host 缓存继续增大，会发生什么？**

扩大 L2 首先改变的是“能保留多少前缀”。它不直接缩短单次搬运，也不会让以前从未出现过的输入突然命中。

如果用户经常隔几分钟继续同一段对话，而旧前缀恰好在这段间隔内被淘汰，增加容量就可能保住有价值的数据。反过来，如果大多数输入都是一次性的，或者热点前缀本来就能放下，继续扩大缓存未必明显改善延迟。

因此，容量需要和复用间隔一起看。同样大小的缓存，对每秒反复访问的公共提示词、隔半小时恢复的会话、只读一次的文档，价值完全不同。

`--hicache-ratio` 用来按设备 KV 池的规模配置 Host KV 池。它不是“使用整机内存的百分比”，也不是“把显卡全部显存乘一个倍数”。显式设置的 `--hicache-size` 则可以覆盖 ratio。估算整机消耗时，还要结合每个 rank 的分配、KV 布局、分片或去重方式，检查启动日志里的实际字节数。[容量参数定义](https://docs.sglang.io/docs/advanced_features/hicache_design#related-parameters)

为了缓存占满 Host 内存，也可能挤压其他进程、数据缓冲和系统余量。一次有效的扩容，应当观察到值得保留的前缀留得更久、实际复用增加，并在目标负载下改善延迟、吞吐或成本。

**缓存放对了地方，请求还要送到合适的位置。**

前面假设请求回到了拥有缓存的实例。实际多副本服务还要做路由选择。

如果 A 已经保存了某段前缀，B 没有，把请求送到 A 可能节省准备时间。但若 A 已经排了很长的队，空闲的 B 即使重算也可能更早完成。

这是一种带条件的选择：缓存位置提供了复用机会，负载决定了这次机会是否值得等待。

SMG 的缓存感知路由中，有根据历史路由推测缓存位置的近似路径，也有根据引擎 KV 事件维护索引的路径。前者知道“请求过去发给了谁”，后者进一步接收缓存块存入、移除等信息。即便如此，事件索引也不应被直接当成一次请求的完整耗时预测。[SMG KV-events 路由说明](https://lightseek.org/smg/getting-started/kv-events-cache-aware-routing)

共享 L3 扩大了可复用的范围，本地命中仍然可能省去外部读取。因此，缓存容量、数据位置与请求调度需要放在一起考虑。

**要判断缓存是否有效，可以沿着一条证据链往下看。**

先确认业务结果：同样的模型、输入输出分布、并发和缓存初始状态下，TTFT 的 P50、P95、P99 有没有变化，吞吐和失败率有没有变化。对照应使用完整运行结果，并明确区分冷启动与稳定运行阶段。

再确认这次请求究竟从哪里复用了 KV。一个总命中率不够，需要区分 device、host 和 storage；如果只有总命中率增加，却不知道来源，就难以解释新增的取回成本。

接着检查搬运和容量。读回、回写的 token 或字节计数描述一段时间内发生了多少流动，缓存占用描述此刻存了多少数据。累计读回很多，并不能证明现在仍留着很多。对于累计计数，应查看相同时间窗内的增量或速率，而不是直接比较启动以来的总数。

最后，把这些变化与排队和实际计算时间对上：重算减少了吗，搬运等待增加了吗，请求是否仍然堵在其他阶段？

这里很值得看一眼指标定义。例如，在本文核对的 SGLang 版本中：

| 指标 | 它回答的问题 | 容易产生的误读 |
| --- | --- | --- |
| sglang:prefill_effective_tokens_total | 本窗口的有效 token 分别来自 device、host、storage 命中还是未命中部分 | 把某一个标签的计数直接当成命中率 |
| sglang:load_back_tokens_total | 有多少 token 从本地 Host 恢复到 GPU | 当成 L3 读取量，或把重复报告的 TP rank 直接相加 |
| sglang:evicted_tokens_total | GPU 因驱逐释放了多少 KV token 槽位 | 认为这些数据一定写回了 Host，或认为 L3 删除了同样多的数据 |

第一项指标尤其容易看错：这个版本的 `input` 标签表示未命中的计算部分，并不是所有输入的总量。窗口命中率的分子是三种命中模式的增量之和，分母则是四种模式的增量之和；比较时还要保持 worker 和 rank 的统计范围一致。[有效 token 指标定义](https://github.com/sgl-project/sglang/blob/37ae292e6f84cb8ec9503892d6cf74f9c8b2bfaf/python/sglang/srt/observability/metrics_collector.py#L1008-L1021)

当前源码对 `evicted_tokens_total` 的定义明确包含“备份到 Host”和“直接丢弃”等不同结果。因此，要判断回写量，需要结合对应的 backup 指标；只看到 eviction 增长，不足以确定数据去了哪里。旧版本或看板重命名后的指标，也应按对应实现确认语义。[驱逐与加载指标定义](https://github.com/sgl-project/sglang/blob/37ae292e6f84cb8ec9503892d6cf74f9c8b2bfaf/python/sglang/srt/observability/metrics_collector.py#L2457-L2501)

**下一次看到高命中率却仍然很慢，可以先问三个问题。**

命中的 KV 在哪里？它什么时候能被 GPU 使用？拿到它之后，请求还在等什么？

这三个问题会把注意力从一个百分比，带回一条真实的数据与请求路径。某些场景需要更大的缓存，某些场景需要更快的搬运，另一些场景则需要处理排队、准入或路由。只有知道时间花在哪里，才能判断下一份资源该加在哪里。

缓存最有价值的结果，是让本来要等待的请求更早完成，或让同样的资源承担更多工作。命中率帮助我们观察这个过程，端到端表现才告诉我们目标是否达成。

*实现依据：在线文档核对日期为 2026 年 10 月 9 日。本文聚焦常规前缀复用与分层存储，不把所有特殊 attention、直连后端或压缩缓存路径视作完全相同的实现。*
