## 简介

> Orca: A Distributed Serving System for Transformer-Based Generative Models<br> OSDI 2022

Orca 提出的 Continue Batching（Selective Batching）是主流推理服务的基础，它是一种动态构建 Batch 的技术。例如 vLLM 可以视为是 Conitinue Batching + Page Attention 的有机结合。

在 解码器Transformer 类模型推理系统中， 提高系统吞吐效率是推理服务的核心目标。解码器生成过程包含 Prefill 和 Decoding 两个阶段，相较单个请求 Decoding， Batching Decoding可以提升计算并行性从而提升生成效率。如果不考虑显存限制，可以粗暴的认为 Batching 越高，解码效率（吞吐）越高。

Batching Decoding 的问题在于：批内其中一个请求生成时间过长，将导致批内其他已完成解码的请求产生空闲。一个直觉的思想是"先结束先出，对于已解码结束的请求在批内剔除，在批内空位填上新的请求，这便是 Conitnue Batching 技术。下图(右) S5 在 S3 结束后填充至 batching 内计算。

![](https://pic3.zhimg.com/v2-c6cd1fdb72d40fde90e4faa5e2f0fa82_r.jpg)

## Continue Batching 算法

Conitnue Batching 可以看作是一个不间断的计算处理引擎

### 主算法流程

Continue Batching 算法可以抽象成两个进程:

1. 请求管理器(RequestManager)：在服务器中接受用户请求，并挑选请求发送到推理引擎 ，当推理引擎所处理的请求数量达到上限，请求将阻塞。
2. 推理引擎(InferenceEngine)：不间断循环执行a. 监听等待队列 b. 不间断执行 Generate 计算操作(无数据时 skip, 不调用计算内核 )

下图(左) 必须要整批数据生成结束，才计算下一批次数据；下图(右) 当 Req3 结束, Req5 就参与到批计算中。

![](https://pica.zhimg.com/v2-1a26100764ab27b07a53cacdf156f148_r.jpg)

在推理引擎执行 Generate 前，可以灵活组织好 Batch 数据。 在 LLM 推理时需要存储 KV-Cache, 可以在每个 Request 对象中存储一个 KV Cache 对象。下图 step2 中 req1,2,4 可以复用 KV Cache 进行 Decoding, req5 则进行 Prefill。

![](https://picx.zhimg.com/v2-c5703721f035e6534f0d5d3a483d5965_r.jpg)

此方式的处理过程在于需要频繁的申请和释放用于 KV-Cache 存储空间。改进可以申请一块大的显存，预留可处理的最大 batch_size 和 len_size，自主管理 Cache 的增删。

![](https://pic1.zhimg.com/v2-d601d8aa357e820325287135d7669c60_r.jpg)

### 处理请求逻辑

Requests 将请求填入到等待队列，在 KV-Cache 上可以做 request id 到 in-batch 内的 slot-id 相互映射。当 KV-Cache中有空槽(slot)时，从等待队列选择一个请求变更为运行状态。在无等待请求时，即使 in-batch 未打满，也可以执行模型的 forward 计算。下图(中)先到先处理策略。

![](https://pic3.zhimg.com/v2-bffd28cad5fd8148ea47a82bf39d70cc_r.jpg)

更加复杂的请求调度策略，则可以定义优先级派发；或者在处理离线数据集，根据 prompt 长度特定组合或选择 batch, 使得 in-batch 内尽可能减少 padding, 提高计算有效性，如上图(右)所示。

### 主算法流程

1. `Request` 存放一条用户 prompt 输入，包含其一状态：挂起、运行和完成
2. `RequestManager` 存放关于 Request 对象的等待队列和运行队列；生成 token 后有接口更新 request 的状态，例如请求生成 `<EOS>` 将`运行`状态改变为`完成`; 此后等待队列选出一个新请求传输到运行队列。
3. `KVCacheManager` 申请一块大的显存， KV-Cache上具有坑位 Slot-ID 的管理数据结构。运算过程产生的 KV 需要填入到 request id->slot_id 上的 KV-Cache 显存上。
4. `ContinueBatchingEngine`计算步内顺序运行 Prefill 和 Decoding。 笔者编排先 Decoding 再 Prefill，仅是为了方便实现。

下图中展示了带 KV Cache 管理的计算流程。

```python
class ContinueBatchingEngine:
    def __init__(self, model, config):
        self.kv_cache_manager = KVCacheManager(config)
        self.model = ModelWrapper(model, self.kv_cache_manager)
        self.request_manager = RequestManager(config.max_batch_size,)
        
    def add_request(self, prompt: List[int], max_seq_len) -> int:
        return self.request_manager.add_request(prompt, max_seq_len)
    
    def step(self):
        # 阶段 Decoding（已有请求）
        if has_active_requests():
            active_slots, request_ids = get_active_slots_info()
            # 获取最新 token
            input_tokens = get_input_ids(self.request_manager, request_ids)
            decoding_logits = self.model.decode(input_tokens,
                                                active_slots,)
            # update_kvcache() 在 decode 程序内部
            
            next_tokens = generate_next_tokens(decoding_logits)
            # 更新状态
            for i, request_id in enumerate(request_ids):
               # 更新 request 状态
                update_request(request_id, next_tokens[i])
                update_slots(request_id) # 如果结束, 释放 slot
                
        # 阶段 Prefill（新请求）
        if has_available_slots():
            pending_requests = get_pending_requests()
            if pending_requests:
                prefill_logits = self.model.prefill(pending_requests)
                prefill_tokens = generate_next_tokens(prefill_logits)
                # 更新请求状态
                for i, (request_id, _) in enumerate(pending_requests):
                    update_request(request_id, prefill_tokens[i].item())
```

## 面向推理服务的 KV Cache

Continue Batching 的核心实现是 KV Cache。其 KV Cache 量与显存、预设的请求 batch_size 和 seq_len。

### 初始化

根据配置申请 2 个 （KV各1个） 5 维 tensor：

1. num_layers：注意力层数
2. batch_size: 处理量
3. seq_len: 上下文长度
4. num_heads：注意力头数
5. head_dim：头维度

```python
class KVCacheManager:
    def __init__(self, config):
        self.k_cache = torch.zeros(config.num_layers, config.max_batch_size, 
                                   config.max_seq_len, config.num_heads, config.head_dim)
        self.v_cache = torch.zeros(config.num_layers, config.max_batch_size, 
                                   config.max_seq_len, config.num_heads, config.head_dim)
        
        self.sequence_lengths = torch.zeros(config.max_batch_size, dtype=torch.long)
        self.request_to_slot = {}  # request_id -> slot_index
        self.slot_to_request = {}  # slot_index -> request_id
        self.free_slots = set(range(config.max_batch_size))
```

另外以下对象成员负责请求与 in-batch 坑位之间的映射

1. Req_to_Slot，Slot_to_Req：前者可以用于查询 KV-Cache、后者可以查询 req 的现有 token_id 序列；
2. free_slot：可用坑位 slot-id 集合，可用于判断是否可以加入新的处理请求

### Cache 更新

Cache 的更新分为 Prefill 和 Decoding, 统一以 Right Padding 作为模型输入进行 Forward 计算。下图 (step4a) 中, 看似同时做了PD，实际上是将 Req1,2,4 做 Decoding（in-batch 3条数据）, Req 5 做 prefill。

![](https://pic4.zhimg.com/v2-9bc8a44c3d99e95a882ca66ecab04323_r.jpg)

1. Prefill 更新：前向计算的数据映射回原 slot 上左侧填充, 如上图 step1 和 step4a
2. Decoding 更新：前向计算时应当在当前长度后一个位置进行填充，如上图 step2, step3a, step4a

在实现上， Prefill 是序列填充 `:seq_len`, Decoding 是单点填充 `cur_len`

```python
def update_slots(self, slot_ids, new_kv_cache):
    # print('update_slots', slot_ids)
    for i, layer_kv_cache in enumerate(new_kv_cache):
        bsz, seq_len, num_heads, head_dim = layer_kv_cache[0].shape
        if seq_len == 1: # decoding mode
            # 每个序列 context 长度不同
            cur_len = self.sequence_lengths[slot_ids]
            self.k_cache[i, slot_ids, cur_len, :, :]  = layer_kv_cache[0][:,0,:,:]
            self.v_cache[i, slot_ids, cur_len, :, :]  = layer_kv_cache[1][:,0,:,:]
        else: # Prefill mode
            self.k_cache[i, slot_ids, :seq_len, :, :]  = layer_kv_cache[0]
            self.v_cache[i, slot_ids, :seq_len, :, :]  = layer_kv_cache[1]
```

在Batch Decoding 时 context 的 position_id 具有连续性要求，通常采用 Left Padding。分析本文定义 Right Padding 分析是否合理？结论是合理的，以下为两种新增 cache 的方式，第二种较合理

1. 左图在已申请的 **KV Cache 尾部**添加新的 KV，推 next token 时，context 的 p1、p2和p9 位置不连续
2. 右图3个请求中，在各自的 **context 尾部** 填入新的 KV, 推 next token 时，p1、p2和p3 位置连续。

![](https://pic2.zhimg.com/v2-476393eeb535d83fe8b3414859ab00bf_r.jpg)

### Cache 删除

当 Inference 时, 检测到特定 request 完成，则根据 request_to_slot 表将 Cache 数据置为 0 ( 而非释放 ), 此时将此 slot-id 填入到 free_slot 上。

```python
    def free_slot(self, request_id: int):
        """释放请求占用的槽位"""
        if request_id in self.request_to_slot:
            slot_id = self.request_to_slot[request_id]
            del self.request_to_slot[request_id]
            del self.slot_to_request[slot_id]
            # 释放槽位
            self.free_slots.add(slot_id)
            # 清空该槽位的缓存
            self.k_cache[:, slot_id, :, :, :] = 0
            self.v_cache[:, slot_id, :, :, :] = 0
```

### KV-Cache 管理分析

这里所讨论的 KV-Cache 管理的动态性体现于 Batch 可以组合，其静态性体现于 Batch 和 Seq_len 是系统固定的

1. 当 context 普遍较短时，下图(中) 设置处理低效
2. 当 context 长度不均衡时，下图(右) 则难以处理 long-context 样本

![](https://pic3.zhimg.com/v2-4dde52b89ca889bce3a75e66f2b0b276_r.jpg)

固定的Cache管理弊端在于：

1. 从存储角度看，其不可避免的产生内部碎片, 预设 Seq_Len 越长，系统产生越多碎片；
2. Context 处理长度受限，当前 KV Cache 管理器不支持跨坑位存储
3. 批处理并行度受 Seq_len 影响大
4. 组合 batch 产生额外的访存耗时（将在手撕 Inference (2) 中进一步分析）

上述分析的弊端，在 vLLM 中有极大的改善。

### ContinueBatchingEngine

在Continue Batching中，需要传入模型，此时会分配好 KVCache 和 请求管理器。在 step 任务中执行：（1） 整理输入 batch 或 kv cache；（2）执行 prefill / decoding 得到 logits 并解码（3）将解码结果填入请求更新状态，并更新 KV Cache

```python
class ContinueBatchingEngine:
    """连续批处理主引擎"""
    
    def __init__(self, model, config):
        self.kv_cache_manager = KVCacheManager(config)
        self.model_wrapper = ModelWrapper(model, self.kv_cache_manager)
        self.request_manager = RequestManager(config.max_batch_size,)
    
    def add_request(self, prompt: List[int], max_seq_len) -> int:
        """添加新请求"""
        return self.request_manager.add_request(prompt, max_seq_len)
    
    def step(self):
        # 阶段2: 处理解码（已有请求）
        if self.kv_cache_manager.has_active_requests():
            active_slots, request_ids = self.kv_cache_manager.get_active_slots_info()

            # 准备输入token (上一个步骤生成的token)
            input_tokens = torch.tensor([
                self.request_manager.requests[req_id].generated_tokens[-1]
                for req_id in request_ids
            ], dtype=torch.long)

            current_length = torch.tensor([
                self.request_manager.requests[req_id].current_length
                for req_id in request_ids
            ], dtype=torch.long)

            input_tokens = input_tokens.unsqueeze(dim = 1)
            
            # 解码
            decoding_logits = self.model_wrapper.decode_next_tokens(input_tokens, active_slots, current_length)
            next_tokens = self.model_wrapper.generate_next_tokens(decoding_logits)
            
            # 更新状态
            self.kv_cache_manager.update_after_step(next_tokens)
            for i, request_id in enumerate(request_ids):
                self.request_manager.update_request(request_id, next_tokens[i].item())
                
                # 如果请求完成，释放槽位
                if self.request_manager.requests[request_id].is_finished():
                    self.kv_cache_manager.free_slot(request_id)
                    
        # 阶段1: 处理预填充（新请求）
        if self.kv_cache_manager.has_available_slots():
            pending_requests = self.request_manager.get_pending_requests(
                self.kv_cache_manager.get_available_slots()
            )
            if pending_requests:
                prefill_logits = self.model_wrapper.prefill_requests(pending_requests)
                prefill_tokens = self.model_wrapper.generate_next_tokens(prefill_logits)
                
                # 更新请求状态
                for i, (request_id, _) in enumerate(pending_requests):
                    self.request_manager.update_request(request_id, prefill_tokens[i].item())
```

## 改进优化

### PageAttention：更灵活的 KV-Cache 管理

vLLM 借鉴操作系统中的分页存储机制，将 KV-Cache 划分为块进行管理，从而更灵活地适应不同序列长度，并显著提高管理效率。在计算过程中，一个查询（Q）可以与多个键值（KV）子块分别进行块注意力（block-attention）计算，最后再聚合结果。

### DistServe：解耦 Prefill 与 Decoding

Prefill 和 Decoding 阶段具有不同的计算特性，DistServe 将其分别调度到不同的服务节点进行专项处理。例如，Prefill 节点完成上下文计算后，将生成的 KV-Cache 传输至 Decoding 节点（尽管会引入通信开销），两者可根据任务需求独立设定计算规模，如 Decoding 节点可运行更大的批处理大小（Batch Size）。

在大型推理服务系统中，Prefill 与 Decoding 的分离是提升吞吐量的关键，但也带来了更复杂的系统设计挑战，例如 DeepSeek-V3 推理基础设施中就实现了此类架构。

### ChunkPrefill：合并 Prefill 与 Decoding

尽管前文实现中将 Prefill 与 Decoding 视为独立阶段，但 Decoding 阶段仅处理单个请求，每层注意力需频繁加载权重并读取 KV Cache，导致较高的内存访问开销。ChunkPrefill 提出将 Decoding 阶段待生成的下一个 token 填入 Prefill 上下文中，“搭便车”完成其投影变换，仅保留注意力计算逻辑不变，从而减少访存次数，提升整体效率。

## 总结

1. 本文系统分析了批解码（Batch Decoding）存在的效率问题，指出了推理服务在实际部署中面临的若干挑战：请求到达随机、Prompt 长度不一，以及批处理大小受显存限制等。在此基础上，进一步明确了推理服务的核心优化目标——提升解码阶段的吞吐量。
2. 本文手撕了带 Continue Batching 的推理服务 demo，实现了对 KV-Cache 的管理，一定程度隔离了 attention 计算任务。本代码具有一定扩展性，为后续优化奠定基础（例如优化 KV-Cache 管理、引入请求调度与整理机制等）
3. 推理服务可以针对 Cache管理(vLLM) 和计算特性（PD分离/ChunkPrefill）进行深度优化；在面向集群的分布式推理场景中，则需统筹存储、通信和计算资源，以实现任务的高效部署与资源利用。。本专题将系统更新：手撕vLLM、手撕 ChunkPrefill 和 手撕 PD 分离等。
