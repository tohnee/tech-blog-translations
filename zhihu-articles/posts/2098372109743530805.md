Cloudflare 最近公开了一个挺严重的 AI 推理事故：**它在 Workers AI 上提供的 GLM-5.3，有些请求居然会收到其他客户此前发给模型的内容**。

问题从 8 月 27 日上线就一直存在，直到 9 月 9 日才修好，**Cloudflare 最终确认有 155 次响应受到影响，而且这些请求的输入都超过了 681,280 Token**。

![](https://pic2.zhimg.com/v2-ff32dfe91c601f552445e3db66f44683_r.jpg)

这个问题可能还要回溯到之前我们聊过的 [《Cloudflare 如何优化部署 Kimi 和 GLM ，实现同性能下的加速和降本》](https://zhuanlan.zhihu.com/p/2068351519687184385) ，但是 Cloudflare 就说：

> 最近针对 Kimi 和 GLM 做了一次优化，在不改模型能力的前提，通过推理系统工程优化，让同一批 GPU 可以同时容纳更多请求，而且在降低单位 Token 成本的同时，还处理了避免多租户共享 KV Cache 时出现串数据的问题。

看到没有，但是说的就是，「在降低单位 Token 成本的同时，还处理了避免多租户共享 KV Cache 时出现串数据的问题」，然后后来发现数据串了。

之前 Cloudflare 为了提高吞吐量，把推理拆成了两组 GPU：

- **Prefill 负责先读完整个 Prompt、算出 KV Cache**
- **Decode 接过这些缓存，再一个 Token 一个 Token 地生成回答**

这两组 GPU 之间通过 Mooncake 和 RDMA 直接传输 KV Cache，可以省掉很多不必要的数据搬运，然后与此同时，KV Cache 显存被切成很多可以重复使用的页，请求结束就归还，下一位用户拿到这些页时再覆盖旧数据，**而且为了性能，页面不会每次都提前清零**。

问题就出在这里，Cloudflare 给 GLM-5.3 配置的上下文窗口是 1,048,576 Token，但是 Prefill GPU 在加载模型权重、分配其他显存之后，真正可用的 KV Cache 池只能装 681,280 Token。

> 这里的这两个数是分别决定的，模型说自己支持 100 万 Token，不代表当前这台推理服务器真的给它留够了缓存空间。

**更有意思的是，Cloudflare 上线前就知道这两个数字对不上，当时他们觉得 SGLang 应该能妥善处理**？？？？

什么魔鬼笑话，他们觉得 SGLang 放不下就会正常报错，或者通过其他方式处理，但是测试时超长请求确实收到了 HTTP 200，也没看到流式响应中的错误，他们就误以为这套服务把长 Prompt 正常处理完了！！！！

> **后来才发现，测试基本验证了状态码和速度，根本没认真检查回答内容到底是不是基于用户自己的 Prompt 生成的。**

那为什么本该报错的请求，反而读到了别人的缓存？其实就是图片里所示的，上半部分是正常流程，下半部分是出问题的流程：

![](https://pica.zhimg.com/v2-249a9d71c25ab1907acaa87101960e3e_r.jpg)

正常情况下，一个请求需要 8 页 KV Cache，Prefill 算完以后把 8 页都传给 Decode，Decode 读取的自然都是当前请求的数据。

可是如果 Prompt 超过了 Prefill 的容量，SGLang 调度器其实已经决定拒绝它，同时把原来的长 Prompt 临时替换成 **1 个 Token 的占位内容**，本来是想让这个请求走完内部清理流程，再把错误返回给客户端。

但在 Prefill 和 Decode 分离部署的模式下，负责接收请求的两个队列都只检查了 `req.finished()`，没有正确识别“这个请求已经被标记为拒绝”。

然后因为错误暂时存在 `to_finish` 里，而 `finished_reason` 还没设置，`req.finished()` 依然是 `False`，于是它一路被当成正常请求放行。

接着就离谱了：

- Decode 一开始已经按照原始 Prompt 长度预留了 8 页，Prefill 居然只给这个占位 Token 算出 1 页，然后告诉 Decode“传输完成”
- **Decode 以为 8 页都准备好了，开始生成时照样读取 P0 到 P7，实际上只有 P0 是这次写入的，剩下 P1 到 P7 还留着其他请求的数据。**

> 所以图里下半部分才会出现 1 页绿色、7 页橙色斜线的情况。

比如用户 A 刚让模型分析一份内部代码，随后用户 B 发来一个特别长的 Prompt，刚好触发这条错误路径，这时候用户 B 不需要知道 A 的内容，模型生成时反而可能受到 A 留在 KV Cache 中的计算状态影响，甚至把 A 的代码片段答出来。

**所以这说不准是 SGLang 的锅大一点，但是 Cloudflare 的问题大一点····**

在发现问题之后，Cloudflare 直接调整了配置，给 KV Cache 腾空间，让 Prefill 缓存池能容纳大概 **204 万 Token**，这样合法输入就不会因为池子太小走到这条拒绝路径。

然后同时改 SGLang，**请求只要已经被标记为拒绝，就应该在 Prefill/Decode 的入队阶段直接结束并返回错误，不能先占显存、传一点缓存，再让 Decode 猜它是不是成功了**。

> 相关修复先后进入 [#36988](https://github.com/sgl-project/sglang/pull/36988) 和 [#38935](https://github.com/sgl-project/sglang/pull/38935)，Cloudflare 和 SGLang 都建议分离式部署升级到包含后续加固的 v0.5.22 或更新版本。
