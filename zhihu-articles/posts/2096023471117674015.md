### 运行环境

虽然前言提到，本文是从全局视角出发的，但受制于推理框架版本的快速迭代，此处特注明运行环境及软件版本，以作为参考：

- CPU 核心数: 192
- OS: Ubuntu 22.04.5 LTS (aarch64)
- RAM: 1T
- NPU: 910B4 32G NPU * 8
- Python: 3.12.13
- CANN: 9.1.0
- vLLM: 0.30.0
- vLLM-Ascend Docker 容器版本: nightly-main(git sha: 8194eceae)
- LLM: Qwen3.8-27B-w8a8

下文将会提到为什么不选 SGLang 而是 vLLM-Ascend，前者在高并发多用户场景下存在显著劣势。

可以看到，由于 NPU 内只有 32G 显存，笔者在做 PD 分离及各项优化的时候是有妥协的，在下文的各个优化章节中会对 64G 卡的情况也补充优化思路。

同时，模型的选择也不是绝对的，此处选择 Qwen3.8-27B 原因为截至编写该文时，它为能在此环境下部署的模型中能保持智力与速度平衡的选择。DeepSeek-V4-Flash-w4a8 也能勉强部署，但其速度和并发性能明显低于可用标准。

### 技术选型

在 Ascend 环境下的推理框架选择，主流的有 vLLM-Ascend、SGLang 和 MindScore，其中 MindScore 的迭代速度较慢，无法满足使用前沿先进模型的需求；而 SGLang 虽然在短请求、低并发情况下在单请求内表现出更快的 Prefill 和 Decode 速度，却在并发数提高、前缀输入变长的情况下出现了不可忽略的性能损耗。

除此之外，SGLang 虽然是原生支持 Ascend，但对平台内的适配迭代速度并没有 vLLM-Ascend 快，同时还出现了 MTP 在长前缀下性能开销的恶性问题；相比之下，vLLM-Ascend 属于 Ascend 官方支持，且拥有广泛的用户群体，在各种问题的反馈和修复上都比较及时。因此哪怕 SGLang Day-0 适配模型速度明显更快，为保持服务的稳定性和可用性，仍然选择了 vLLM-Ascend 作为推理引擎。

> 当然，上文并不是对 vLLM-Ascend 稳定性的承诺。即使是笔者在实际使用的过程中也遇到了一些在配置和运行时的兼容性问题，因此不得不向官方提交 PR，并将未及时合并的 PR 放入自己的 fork 仓库内的部署分支作为生产环境的推理引擎。

### 部署模型服务

出于可维护性和隔离性的考虑，强烈建议所有尝试部署服务的读者使用 Docker 管理服务环境。即使在 Conda 环境下，也会涉及大量环境配置问题的调试，且拉起、关闭、重启服务相比 Docker 容器复杂度极高，会消耗大量时间在调试环境上。哪怕有高度定制化/算子级调优的需求，也只建议在容器内替换 vLLM-Ascend 到 fork 的仓库。

此部分内容在 [官方文档](https://docs.vllm.ai/projects/ascend/zh-cn/latest/getting_started/installation.html) 中已有详细的教程，以官方教程为准，此处只补充一些启动容器后可能出现的报错应对。

### 显存不足（Out Of Memory）

推理服务的显存占用受到以下配置影响：

- 模型权重大小（如果量化需要 `--quantization ascend`）
- 最大序列数（同时可处理请求数最大值，`--max-num-seqs`）
- 模型上下文最大值（最长能处理的 Token 数，`--max-model-len`）
- KV Cache 量化方式（有运行时精度损失，`--kv-cache-dtype`）
- 分配给 KV 的显存比例（除了固定占用以外，启动时直接分配的显存比例，`--gpu-memory-utilization`）
- Chunked Prefill Token 数（如果开启分块预填充，`--max-num-batched-tokens`）
- 张量并行数（将一个模型权重分到几张卡上，`--tensor-parallel-size`）
- 数据并行数（一共有几个模型权重相互独立计算，`--data-parallel-size`）
- 推理解码方式及草稿模型权重大小（如果开启推测解码，`--speculative-config`）

除此之外，其他配置也会对显存占用产生较小影响，但对上述配置进行调整已能满足绝大多数场景。

由于 vLLM 在启动阶段就会静态计算显存需求量，因此上述配置会在启动阶段立即终止，调整的速度是比较快的。

### 配置参数调优

跑起来的服务只能算作是性能基线，需要进一步根据服务器特性微调，才能在对应的业务场景下得到较优秀的性能。此段从易到难优先介绍无需 profiling 的调优经验。

为方便理解下文提到的优化，首先先明确一个概念：输入速度受制于算力和空等，输出速度受制于通信（节点内带宽与节点间通信）速度与草稿模型命中率。但这也不是绝对的，会根据模型的架构而产生额外的影响，如混合专家（MoE）模型相比稠密（Dense）模型，前者对通信要求更高，后者对算力要求更高。

### 模型权重量化

在一般的模型推理服务中，模型的权重占据了较多显存，可以通过量化减少占用，但同时因精度损失也会对模型的“智力”产生损伤。

vLLM-Ascend 仅支持 WA 量化，即权重与激活值分别以不同精度量化，最常用、保持权重大小与精度平衡的量化为 W8A8，一般可以在 ModelScope 上找到 [官方](https://www.modelscope.cn/organization/Eco-Tech) 的量化权重。除此之外还有 W8A16、W4A16、W4A8 等多种方式，数字越大模型权重越大，数字越小模型精度越低。

受制于算力，一般来说不选择 BF16 原始权重，而是使用 W8A8 量化。使用量化模型需要在启动脚本添加 `--quantization ascend` 选项。

它会影响的范围包括：

- 单序列内的输入速度：低精度的模型在运算阶段明显加速（需要卡内有明确支持）
- 单序列内的输出速度：更小的模型权重加速了模型读取，直接降低了 TPOT（输出时间）
- 加载阶段的启动速度：减少了从磁盘加载模型权重所需的时间
- 模型权重的显存占用：降低模型精度能大幅减少模型权重占用，将更多显存留给并行处理请求与前缀缓存

如果未能找到量化的模型，也可通过 [msmodelslim](https://gitcode.com/Ascend/msmodelslim) 量化模型权重。官方最佳实践对主流模型保持支持。

注意：量化过程中，如果模型包含 MTP 所需的草稿头，需要对其保持全精度，以避免草稿模型接受长度骤降的问题。

特别地，经测试，稀疏模型的自动量化精度损失远高于稠密模型。对 Qwen3.8-27B 及其社区微调模型量化，相比 Qwen3.6-35B-A3B 能够保持更好的精度。

### 模型上下文

由 `--max-model-len` 决定，根据实际需要进行控制，不建议在所有场景下均保持默认最大上下文。

服务的输出速度会随着请求内上下文增长而显著下降。作为示例，未调优时短输入时 70token/s 可在 200K 输入时降低到 20 token/s。

在 SGLang 内，存在 MTP 对长上下文输出速度急剧衰减的问题，该问题已在 vLLM-Ascend 中得到修复，但 SGLang 社区仍有类似的反馈。

### 最大序列数

由 `--max-num-seqs` 决定，只决定可进入等待的请求数，而非 **同时处理请求数** 大小，后者受 KV 分配显存大小影响。即：可以同时等待多个请求，但输入处理速度有限，因此不一定同时处理全部请求，未被处理的请求表现为请求长等待，TTFT（首字延迟）提高。

服务的总吞吐量并不是随着并发数线性提升的，而是会有相当程度的衰减。在高并发场景下，不仅平均的请求内输入输出速度会显著降低，多请求之间还会发生资源竞争而导致阻塞、卡顿等情况。建议根据服务器承载量和实际需求量决定，建议保持在 4 到 32 之间。

### 张量并行

由 `--tensor-parallel-size` 决定。张量并行（TP）数决定了模型权重被切分到几张卡上，可以减少显存占用、增加可利用的显存和卡数。

然而，TP 也涉及到多卡间并行通信的额外开销，如 AllGather 算子、AllReduce 操作产生的额外延迟和通信开销。TP 通信开销是较为显著的，在算力、显存足够的情况下，减少 TP 数可以提高推理速度。

对一般情况下，能够利用上全部卡用于 KV 缓存等多用处是比更快的速度要更重要的，因此 TP 在调整其他参数至最佳前不应纳入优化考虑。如果真有较大的显存剩余，能够容纳多个模型运行的，一般考虑下文的数据并行和 PD 分离特性。

### 数据并行

由 `--dp-parallel-size` 决定。数据并行（DP）数决定了在服务内存在几个独立的模型实例，并行数与总吞吐量呈线性关系。

DP 的扩展性较好，可以在需求增加时通过扩大显存直接拉高总吞吐量。由于笔者本文主要介绍在显存受限环境下的性能调优，故该方案并不属于主要介绍的内容。

### 分块预填充

由 `--max-num-batched-tokens` 决定，特性本身已默认开启。将长输入切分为大小一致的块进行处理，可以更高效利用算力，但绝非越长越好，一般来说定在 1024-32768 最佳。良好的分块大小可以产生 10% 到 20% 的输出总吞吐量提升。但过大的分块反而会导致处理速度下降，并拉高一般情况下的 ITL（字间延迟）。

除了影响处理速度，块大小还会影响启动阶段 vLLM 的静态显存检查，在超过显存可用范围时会导致 OOM 报错。

### 前缀缓存

由 `--enable-prefix-caching` 决定。可以选择关闭，在开启时会额外使用空余显存来保存最新请求的前缀，并在下次命中时直接复用，避免全量重算输入。对于绝大多数需要多轮长对话的场景，前缀缓存是必要的配置，以减少重复算力开销，优化请求处理性能。

但它也不能保证每次的完全命中，输入块只有能填满一个缓存块大小的部分会被缓存，末尾不足一个缓存块的会被丢弃并在下次重算。这部分由 `--block-size` 影响，并在混合注意力模型之中配合 `--prefix-cache-retention-interval` 按间隔保存 KV Cache。

然而前缀缓存实际上还有各种问题，有下列多种方式分级解决：

- AscendStoreConnector KV 缓存池：将显存收集起来集中复用，提高分配缓存的利用率，直接提高了缓存命中率
- CPUOffloadingConnector：将 KV Cache 卸载到内存中，直接扩大了能保存的缓存大小
- PreemptOffloadConnector：用于 PD 分离中，将不够处理请求时被抢占丢弃的 KV Cache 卸载到 CPU，避免抢占恢复时的二次重算
- LMCache 分级卸载：可以将不常用 KV Cache 卸载到内存甚至磁盘中，进一步扩大 KV Cache 可保留范围

KV Connector 是可以叠加使用的，需要用到 `MultiConnector`。在笔者使用时该特性有注册名与调用名不同的问题，现已[被笔者修复](https://github.com/vllm-project/vllm-ascend/pull/16930) 而重新处于可用状态。

AscendStoreConnector 支持 Mooncake、Memcache 等多后端，其中 Mooncake 后端强制依赖 RDMA，在单节点无 RDMA 的环境下可以用 Memcache 后端代替。

### 图模式

由 `--compilation-config` 决定。配置了推理过程中的图模式，常见的包括全图模式（FULL）、分段图模式（PIECEWISE）、仅 Decode（FULL_DECODE_ONLY）等。

其中分段图和仅 Decode 较常用，且部分特性指定了特定的图模式。该配置在启动时即生效，会明显增加启动时间，但对推理速度有明显增益。可通过配置模型编译缓存等方式优化启动时间。

### 推测解码

由 `--speculative-config` 决定。其原理是使用模型特化微调过的小草稿模型预测大模型的输出，并让大模型只负责验证而无需走完整输出路径，只在预测错误时重走全量路径。因此草稿模型预测 Token 的接受率（接受长度）直接影响了输出速度，甚至在较低接受率下模型输出速度会显著慢于不启用该参数时。

目前常用的推测解码包括以下几种方案：

- MTP：需要加载额外的草稿头，一般由模型自带，主流的是串行预测，接受率随长度增加衰减较小
- DFlash：使用独立的块扩散模型，并行生成多个候选 Token，但块内预测独立，导致接受率随长度增加迅速衰减
- DSpark：保留DFlash并行主干，并增加轻量级顺序模块改进了接受率问题

上述方法中，MTP 一般在模型中集成，而 DFlash 和 DSpark 则需要额外加载草稿模型，因此 MTP 的额外显存占用相对后两者较少。DFlash 和 DSpark 的并行特性使得在同等预测率下理论速度快于 MTP。在实际测试中，其接受长度相对 MTP 更短，且由于计算和读取上的额外开销，速度反而更慢。因此目前只建议使用 MTP 作为加速手段。

此外，还有 DFlash2 这样的最新方案。虽然官方文档写已经支持，但在服务器上实测还是会生成无意义 Token，没法正常使用，且未有性能提升。后续可以跟进官方的支持，但目前看来配置简单程度和优化效果来看都是不如 MTP 的。

### PD 分离

前面提到，当输入负载高时，会出现正在输出的请求降速或被中断的情况；且 P(Prefill) 节点和 D(Decode) 节点的性能瓶颈有所不同：P 节点需要处理输入的所有内容，在 Transformer 架构下，大量层需要进行大矩阵运算，因此产生了算力瓶颈；D 节点每次只需自回归生成 1 个 Token，且输出有前向依赖性只能串行，处理起来传输成本相对计算量更大，因此产生了带宽瓶颈，而在多节点（跨服务器）部署模型时，节点间的通信同样是瓶颈之一。

PD 分离在 P 和 D 瓶颈完全不同的情况下，将二者分离为不同的服务，可以更高效利用硬件，使彼此之间的资源抢占问题更少，在高压请求下对 TTFT 和 ITL 都有着明显的优化作用，可以有效提高总吞吐量。PD 分离的收益根据硬件的不同有所出入，实际情况下可能要对 TTFT、TPOT 和 ITL 都进行全面测试才能得出最佳方案，但在笔者的环境下 PD 分离的使用体验有明显改善。

常用的 PD 分离需要借助外部框架在节点间进行 KV 传输，常用的框架为 Mooncake，已经在官方的 Docker 容器中包含。

根据 P 和 D 需求性质的不同，可以为两侧节点配置不同的数量、显存、配置等，但笔者的配置并没有必要做 1P1D 以上的调整，因为每个节点都需要保留一份独立的模型权重占据显存。

此外，在显存耗尽时，服务会发生抢占：将部分请求丢弃腾出空间用于计算当前请求，后续空闲时再进行重计算。在单服务内，重计算的耗时极小，但在 PD 分离时却涉及到 KV 传输的开销。因此对于 PD 分离场景，可以通过 PreemptOffloadConnector 缓解该问题。它将被抢占 KV 卸载到内存，再在空闲时恢复到显存，优化了重计算时间，同时也缓解了高压下显存耗尽导致的 KV 重算卡顿。
