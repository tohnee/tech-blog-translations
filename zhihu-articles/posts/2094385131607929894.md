CP（Model Context Protocol）正在成为 AI Agent 接工具的事实标准。Claude、VS Code、Cursor、各大厂都在支持它。官方 SDK 名单有十种语言：TypeScript、Python、C#、Go、Rust、Ruby、Java、Swift、PHP、Kotlin。

**没有 C++。**

而 C++ 恰好是数据基础设施聚集的地方——数据库、游戏引擎、嵌入式、交易系统、HPC。这些系统要接入 Agent 生态，目前只有两条路：绑一个非 C++ 的 SDK，或者自己手写协议。

我们选择了第二条，然后把它做成了开源 SDK： **[mcp-cpp](https://github.com/zhoutk/mcp-cpp)** ，C++17，目标规范 **2026-07-28** ，不要求异步运行时，也不依赖 OpenSSL——SHA-256/HMAC、CSPRNG 全部树内实现。依赖只有一个内联的 JSON 头文件 + 可选的 cpp-httplib。 `find_package(mcp CONFIG)` 就能进你的构建。

这篇文章讲三件事：它实现了什么、官方一致性测试抓出了我们哪 5 个真 bug、以及我们在测试套件的 mock 里发现的一个 bug。

### 2026-07-28 版的协议和 2025 完全不是一个东西

当前版做了几个大改动： **没有 initialize 握手、没有会话 id** ；每个请求在 `params._meta` 里自带协议版本和客户端能力；服务器通过 `server/discover` 自报家门；最关键的一条—— **服务器永远不主动发请求** 。服务器需要补充信息时，返回一个 `input_required` 结果，客户端收集好输入后重试同一个请求（MRTR 模式）。实时推送走 `subscriptions/listen` 。

mcp-cpp 全部实现了：

- **服务端** ： `Builder` 注册工具/资源/提示词（含 RFC 6570 URI 模板）、能力门控、MRTR（带 **`requestState` 签名编解码** ：HMAC-SHA256、绑定上下文、TTL——SHA-256 全部树内自研实现，零加密库依赖）、进度通知、取消、CacheableResult 缓存提示。
- **客户端** ：阻塞式、值语义；MRTR 自动履行（ `callToolWithInput` ）；完整的 **OAuth 2.1 客户端** ——受保护资源元数据发现（RFC 9728）、授权服务器元数据（RFC 8414 + OIDC 双拼写）、动态注册（RFC 7591）、CIMD 客户端元数据文档（SEP-991）、PKCE（S256，随机数来自 CSPRNG）、RFC 8707 resource、RFC 9207 iss 校验、scope 升级、SEP-2352 授权服务器迁移。
- **传输** ：stdio + Streamable HTTP 双侧——镜像头校验（ `MCP-Protocol-Version` / `Mcp-Method` / `Mcp-Name` / `Mcp-Param-*` ，不符 `-32020` ）、SSE、旧版 GET 监听流、按 `retry:` 字段退避的 `Last-Event-ID` 重连。
- **校验** ：JSON Schema 2020-12 校验器（仅本地 `$ref` 、带资源上限），每次调用强制 `inputSchema` / `outputSchema` 。

15 行写一个完整服务端：

```cpp
#include <mcp/mcp.hpp>
#include <string>

int main() {
  mcp::server::Builder b;
  b.name("my-server").version("1.0");
  b.tool(mcp::Json(R"({"name":"add","description":"adds two integers",
    "inputSchema":{"type":"object","properties":{"a":{"type":"integer"},
      "b":{"type":"integer"}},"required":["a","b"]}})"),
    [](mcp::server::Ctx& c) -> mcp::McpResult<mcp::Json> {
      const mcp::Json args = mcp::member(c.params, "arguments");
      const int64_t sum = mcp::member(args, "a").toInt64() +
                          mcp::member(args, "b").toInt64();
      mcp::Json out(R"({})");
      out.add("sum", mcp::Json(sum));
      return mcp::Ok(mcp::server::structuredResult(out,
          "sum = " + std::to_string(sum)));
    });
  mcp::StdioTransport t;
  return b.build()->run(t).has_value() ? 0 : 1;
}

```

### 成绩单：用官方一致性测试跑分，不是自说自话

我们用官方 SDK 同款的 [modelcontextprotocol/conformance](https://github.com/modelcontextprotocol/conformance) （v0.2.0-alpha.12）跑了 **两个规范版本 × 服务端 + 客户端** 四个象限：

| 角色 | 2026-07-28 | 2025-11-25 |
| --- | --- | --- |
| 服务端 | 42⁄42 检查项 · 20⁄20 场景（100%） | 26/30（原因见下） |
| 客户端 | 32⁄32 场景 · 399⁄399 检查项（100%），含全部 25 个 auth/*（OAuth 2.1 + CIMD） | 17/18（原因见下） |

每一个没过的项都在 [expected-failures.yaml](https://github.com/zhoutk/mcp-cpp/blob/master/conformance/expected-failures.yaml) 里写明了理由：

- 2025 服务端那 4 个失败（sampling/elicitation 的 `tools-call-*` 场景）全部要求 **服务器在调用中途向客户端发请求** ——这正是 2026-07-28 **用 MRTR 取代的机制** 。为一个 2025-only 场景去实现一个已被废弃的机制，是明确的不做清单。
- 2025 客户端那 1 个失败，是测试套件自己的 mock 的问题，下一节详说。

### 官方套件抓出的 5 个真 bug（诚实的部分）

跑官方 harness 的头几天，它就在我们的实现里抓出了 5 个真实缺陷。每个都在提交历史里带着规范条款号：

1. **HTTP 上传输在请求期间产生的通知被静默丢弃** ——响应 sink 只保留了最后一行。等于 Streamable HTTP 上根本没有进度和日志。修复：多于一条消息时按 SSE 流式回传。
2. **给 legacy 响应注入了 `resultType`** ——2025 的 schema **拒绝未知字段** 。一条符合 2026 的响应就是违反 2025 的。
3. **JSON-RPC 2.0 允许错误响应带 `"id": null`** ——2025 时代对端真的会发。我们的严格解析器直接拒绝，客户端一直挂到读超时都不报错。
4. **`initialize` 返回的 `Mcp-Session-Id` 和下一个请求发生了竞态** ——有状态的 2025 服务器回了 `400 Invalid or missing session ID` 。修复：等会话 id 落袋再放行响应消息。
5. **空字符串是合法的镜像头值** —— `Mcp-Param-X:` 必须 **发送** 而不是删除。我们 `setHeader(name, "")` 的”空即删”语义是错的， `http-custom-headers` 场景（18 项检查）当场证明。

还有一个是在 **他们的 mock** 里发现的： `elicitation-sep1034-client-defaults` 场景的 mock 从不真正下发服务端→客户端的 elicitation——GET 流上只回 keepalive，工具调用永远等不完。我们没有两手一摊：把 **官方 rust-sdk 的参考客户端** 在同一环境构建出来跑同一个场景—— **同样失败** （0/5，且以 `0xC0000005` 崩溃）。这是 mock 的缺陷，不是 SDK 的缺陷。我们已向上游提交 issue，并在基线文件里附上这个证据，直到它修复。

### 几个设计取舍（C++ 味儿的）

- **用 C++17，不用 20/23。** 受众是存量的 C++ 基础设施，GCC 9 / MSVC v142 满地都是。检测到 `std::expected` 时自动别名到标准库，现代编译器拿好处，构建矩阵不分裂。
- **值语义 + 协议层零异常。** `McpResult<T>` 、 `[[nodiscard]]` ，从传输到 handler 不抛异常。
- **加密零依赖。** HMAC-SHA256 和 CSPRNG（PKCE verifier、OAuth state）全部树内实现——Windows 用 RtlGenRandom，POSIX 用 /dev/urandom。
- **单线程无状态派发。** 一条连接一个服务器一把锁都不上（订阅扇出除外）。对数据库类 MCP 服务器这是正确形状：慢的是 handler，不是循环。
- **文档双语默认** ：英文为主，每份都有完整中文兄弟文件。

### 谁在用

这个 SDK 是 [zorm-mcp](https://github.com/zhoutk/zorm-mcp) 的协议层——一个把 **13 个结构化数据库工具 × 5 种后端** （sqlite3/jsonfile/mysql/postgres/dm8）通过一套无方言工具面暴露出去的 MCP 服务器——以及它底下的 ORM [zorm](https://github.com/zhoutk/zorm) 。真实用户、五种后端、一个 issue 跟踪区。
