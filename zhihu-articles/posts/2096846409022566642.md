大模型 serving 的扩容通常有两种办法：买更多 GPU，或者把已经买来的 GPU 用得更满。这篇论文从后者切入，先给了一个刺眼的数字：**350 个企业用户、6000 次小时级测量，GPU 计算利用率平均只有 17.6%，94% 的用户平均低于 50%**。

投机解码（speculative decoding）本来就是个"两个模型一起干活"的场景：小 draft 模型猜若干个 token，大 target 模型一次前向验证。但现有系统只把这层关系当成调度/放置问题——两个模型各自编译、各自优化，然后排队执行。UCSD、MIT、UT Austin 的合作者（Ghobadi、Rossbach、Esmaeilzadeh 组）提出的 **Conjugate Compilation** 换了个问法：如果不改任何一个模型的数学，只把它们的**联合执行**当成编译对象，能不能把闲置容量捞回来？

答案是能，而且幅度不小：在 B300 与 RTX 5090 上，六个单卡投机解码配置的平均每轮加速 **1.37×**，加上交织 kernel 后 **1.45×**，最好一例 **1.59×**；GPU 利用率在 RTX 5090 上从 50.4% 提到 73.2%。

![](https://pic3.zhimg.com/v2-45bdf742c0bcdfecd0f11afe7fece6f0_1440w.jpg)

图 1：企业用户的小时级 GPU 计算利用率（2026 年 5–8 月，350 个用户共 6000 次测量）。黑线是全体用户的小时均值，全数据集平均 17.6%，94% 的用户平均低于 50%。

## 一、先把时间账摊开：串行不是依赖，只是习惯

单卡上常规的投机解码执行是这样的：γ 个 draft step 全部跑完，target 才开始验证。若单个 draft step 耗时 T_D、target 验证耗时 T_V，一轮就是：

$T_{\text{conventional}} = \gamma T_D + T_V$

关键在于：**这个先后顺序反映的是同一个 batch 内的真依赖，而依赖不跨 batch**。target 在验证第 b 批的草稿时，draft 完全可以去准备第 b+1 批的草稿。论文用一个"保依赖的多流共调度器"把这段并发显式暴露出来：

- 把两个模型切成有序的**段**，粒度可以从整层一直细到 attention/MLP 的一半、再到单个 projection；
- target 段和 draft 段分别提交到两条 CUDA stream，流内保序，跨流只在真正需要协调的地方插 CUDA event；
- 把整个共调度轮次**捕获成一张 CUDA graph** 一次性重放，避免 host 端 launch 开销破坏重叠。

![](https://pic4.zhimg.com/v2-b08d50b2643f72d1cae9643b6d952719_1440w.jpg)

图 2：三种执行方式的时间线。(a) 常规单卡执行：draft 的 γ 步全部完成后 target 才开始验证，31.3 ms；(b) 共调度后两模型的段在时间轴上重叠，22.0 ms；(c) 再把部分操作组合并成交织 kernel，19.7 ms，相对常规 1.59×。

只做共调度（不动任何 kernel）就已经把 31.3 ms 压到 22.0 ms。这一步的收益来自"填空"：target 在等权重、等数据时留下的 SM 空档，被 draft 的段填上了。

## 二、编译器的边界往外挪一格

共调度只是运行时的排班。论文真正的贡献是把 draft 和 target 的**编译决策**放到同一个优化问题里。

一个联合优化方案 θ 包含四件事：

- **跨模型操作组**（conjugated operation groups）：从两个模型里挑出 K 个共享同一 kernel 家族（GEMM、RMSNorm、残差加、softmax）的独立操作，绑成一组；
- **交织比例**：组内每个成员分到多少工作，按算术量占比 πk = Fk / ΣFr 决定，不额外搜索；
- **kernel 配置**：每个（无论是否交织的）kernel 的 TVM schedule 参数；
- **调度安排**：这组操作在两条流上的会合点（joint node），要求映射 i → j 单射且沿两条执行链严格递增，避免成环。

第 1、2 条落到实现上就是**交织 kernel**：把一个 GEMM 拆成输出 tile × 归约片的单元，用一张 descriptor table 记录每个单元属于哪个成员、tile 坐标、归约片、操作数地址，然后把两个模型的单元塞进同一次 launch。每个单元仍然只读自己那份数据、只累加自己的结果，**数学上完全等价**——它改变的是"这些工作如何填满 GPU"，不是"算的是什么"。

![](https://pic3.zhimg.com/v2-5b2003aeb1780cd95aa640b1b6ffc392_1440w.jpg)

图 3：Conjugate Compilation 作为自改进的 agentic 循环。MCTS 选一个已探索的方案，LLM agent 提出结构化修改（add / merge / split / remove），编译器做合法性与数值校验并构建、调优 kernel，GPU 测完整轮次延迟，奖励回传搜索树，kernel 级判定与编译器反馈进入 LLM 的上下文。

这里有个容易被忽略的论点，也是我认为全文最"反直觉但正确"的地方：**这个优化目标不可分解**。设单个操作的独立延迟是 τ(o)，交织组的延迟是 τ(g)，那么

$T_{\text{round}}(\theta) \neq T_{\text{round}}(\varnothing) - \sum_{g} \sum_{o_k \in g} \left(\tau(o_k) - \tau(g)\right)$

原因很实在：共享执行本来就已经隐藏了一部分操作的延迟；而一个决定会改变别处的资源争用、重叠机会和同步点。**一个在孤立测试里更快的交织组，完全可能让整轮更慢。** 所以作者坚持所有候选方案都必须用"完整共调度轮次的实测延迟"来评分，而不是 kernel 级收益相加。

## 三、搜索：LLM 提方案，MCTS 决定改哪个，GPU 当裁判

联合优化空间是组合爆炸的，而且每个点的价值只有编译+实测之后才知道。系统因此做成三层闭环：

- **MCTS 选点**：每个节点是一个完整可执行方案，根节点是空方案（只共调度、不共编译）；选择的 UCB 公式带 progressive widening，控制新分支的引入速度；
- **LLM 改方案**：agent 不直接写 GPU kernel，只在方案抽象上做四种编辑（add / merge / split / remove），并指定作用于哪些层、哪些 draft step。它的输入不只是当前方案，还包括祖先方案、它们的实测延迟、kernel 级判定、编译器反馈、合法放置选项，以及若干代表性 draft–target 段在"分开跑 / 并发跑 / 常规跑"下的测量值；
- **两级验收**：新组先过 kernel-gain 门 v(g) = Στ(ok) / τ̂(g) 大于 1 + max(δ, z·s)（含最小增益余量与配对计时标准误），再过整轮数值校验——每个 draft step 的相对误差要在 1e-2 内，argmax 只允许在参考 logits 本身接近平手时不同。

最终报告前还有一道更严的关：候选方案与共调度锚点在 ABBA 块里成对重测，95% 置信区间必须排除 0，并且做 leave-one-out 剪枝——任何一段 joint node 若单独移除后收益没有超过噪声阈值，就删掉。

## 四、实测：1.37×–1.59×，以及"利用率越高收益越小"的规律

B300 上跑了四对模型（Llama-3.1-8B/3.2-1B、Qwen3-14B/0.6B、Qwen3-32B/4B、Llama-3.1-70B/8B），batch 8、输入 1024 token、FP16、γ 不超过 6：

![](https://pic1.zhimg.com/v2-9f7b6e82a6792170edf231e4e8f7fa88_1440w.jpg)

图 4：B300 上相对常规执行的吞吐（左轴）与 GPU 利用率（右轴）。四对模型上共编译平均 1.38×，加交织 kernel 后 1.47×，最高 1.59×；Llama 对的利用率从 11.6% 提到 18.7%。

- **B300 平均**：共编译 1.38×，加交织 kernel 1.47×，四对模型里每一对都是交织版最快；
- **最好的例子**：Llama-3.1-8B / Llama-3.2-1B，1.59×，利用率 11.6% → 18.7%（+61%），吞吐提升 59%；
- **交织 kernel 的单独贡献**：B300 上平均再多 7%，RTX 5090 上只有 4.1% / 3.3%——因为 5090 的基线利用率本来就高（50.4% / 46.2%），可填的空隙少。

一个 kernel 级的例子能解释这 7% 从哪来：Llama 对的两个 down projection 单独跑合计 17.9 TFLOP/s，交织后 46.5 TFLOP/s，**2.6×**，而且工作点从"远离屋顶"挪到了贴着 HBM 8 TB/s 带宽屋顶的位置——两个 memory-bound 的小 GEMM 合成一个大 GEMM，有效带宽利用率才上得去。

![](https://pic4.zhimg.com/v2-f2579a3fdbbd695090045173b7af6aa1_1440w.jpg)

图 5：Llama down-projection kernel 在 B300 上的 roofline。交织后的 kernel（右）比两个单独 kernel（左）更贴近带宽屋顶，达到 2.60× 的 kernel 级提升。

**敏感性**这一组实验信息量很大：

![](https://pic2.zhimg.com/v2-84410d84c0faa5a917069bfabe3c8869_1440w.jpg)

图 6：换到 RTX 5090。两对模型的加速为 1.38× / 1.41×，平均 1.40×；利用率从 50.4% / 46.2% 提到 73.2% / 67.9%。

![](https://pica.zhimg.com/v2-3dede8074f81a326c174661cc5d3300a_1440w.jpg)

图 7：batch 敏感性（Llama-3.1-70B / 8B）。batch 8 时 1.27× / 1.34×，batch 16 时降到 1.20× / 1.22×——每个模型自身的活越多，共编译能填的空越少。

![](https://pica.zhimg.com/v2-88b6590271f1452c3883f9fe3f78b83a_1440w.jpg)

图 8：draft 长度敏感性（Qwen3-14B / 0.6B）。γ=4 时 1.45× / 1.55×，γ=6 时降到 1.32× / 1.37×。接受率 0.73 下，γ=4 的 852 tok/s 反而高于 γ=6 的 713 tok/s。

规律很清楚：**当每个模型自己提供的并行度越低（batch 小、γ 小、模型小、单卡），共编译的相对收益越大**。这与"填满闲置容量"的解释一致，也意味着这套方法的适用面是"低利用率区间"——正好是论文开头那 17.6% 的绝大多数场景。

## 五、和既有工作的位置关系

- 并行投机解码系统（PEARL、MineDraft、SwiftSpec、FASER）把 draft–target 并行当成**运行时**的调度、放置、资源分配问题，多数还把两个模型分到不同 GPU 上；它们在编译之后动手，不改变"两个模型怎么被编译"。
- GPU 共享/多租户编译（Orion、VELTAIR、ConCo 等）决定"哪些已编译好的计算可以并发"，或用分析模型给单 kernel 定资源预算；它们不针对投机解码，也不用执行反馈驱动编译决策。
- LLM 驱动的 kernel 优化（KernelBench、STARK、LLM Compiler 系列）优化的是单个 kernel 或程序；本文把 agentic 优化扩展到**跨模型的联合方案**。

所以它的定位可以概括成一句话：**把"多模型共存"从运行时问题提升为编译问题**，并用实测的联合执行作为唯一可信的评分函数。

## 六、批判性评估

几个必须指出的限制：

- **利用率数据的来源需要打折看**：17.6% 来自 Systalyze 的 Utilyze 工具，而 Systalyze 是论文作者之一的关联公司（署名单位里就有）。这是"企业用户 GPU 的利用率"，不等于推理集群的利用率——推理服务的 GPU 通常比训练/实验集群满得多。所以"大量闲置容量"这个前提对推理集群的适用性要弱一些。
- **搜索成本完全没有报告**。整个流程依赖 gpt-5.6-luna 反复提方案、TVM 编译、GPU 实测；论文给了每个配置重复 50 次取中位数，但没给"找到一个可用方案要编译/实测多少轮、花多少 wall-clock 和多少 token"。如果搜索要几小时，那 1.37× 的收益对快速迭代的 serving 团队就不一定是净赚。这是我认为最需要补的数据。
- **实验面窄**：只做单卡、batch 8、序列 1024、FP16；没有多卡 TP/EP、没有多租户并发、没有 FP8/FP4。跨模型交织在量化格式不同（draft BF16、target FP8）时能不能成立，论文没回答。
- **"吞吐"的口径**：1.47× 是 target-model verification throughput，不是端到端请求吞吐。端到端只有 γ 敏感性那一处给了绝对数字（852 vs 713 tok/s），其余都是相对值。
- **数值等价性**：校验阈值是相对误差 1e-2、argmax 允许近似平手不同。对生成质量够用，但会轻微改变投机解码的接受率统计——论文没有报告接受率是否发生变化，而这会直接影响端到端加速比。
- **可复现性**：论文没有给出代码/artifact 链接（正文与附录都没有），实现依赖 TVM v0.25 与内部 agent 框架，第三方无法复核 1.37× 这个数字。

## 七、对做 serving 的团队意味着什么

- **先做共调度，别急着改 kernel**。把两个模型切段、放两条流、用 CUDA graph 捕获整轮，这一步在所有配置里贡献了大部分收益（B300 上 1.38× 中的绝大部分，交织只再加 7%），工程量却小得多，也不改变任何数值行为。
- **收益与基线利用率强相关**。基线 11.6% 时能拿 59%，基线 50% 时只有 38%–41%，基线更高时会更少。上线前先量自己集群的 SM 利用率，别把论文的 1.59× 当成普遍值。
- **"kernel 级更快 ≠ 端到端更快"应该成为团队的默认假设**。这篇论文用式 (7) 和整套"整轮实测"的流程，把这个直觉变成了工程纪律。
- **交织 kernel 的机会在 memory-bound 的小 GEMM 上**。down projection 从 17.9 到 46.5 TFLOP/s 的例子说明：把两个小 GEMM 合成一次 launch，收益来自有效带宽而不是算力，这类形状在 decode 阶段到处都是。

一句话总结：**投机解码的两个模型本来就共享一个 GPU，本文只是让编译器承认这个事实**——而这件"承认"带来的收益，比大多数单 kernel 优化都大。
