==================================================

2026 年 7 月，TensorRT-LLM 做了一个看起来最不像 TensorRT-LLM 的决定：

**删除 TensorRT backend。**

6 月 30 日发布的 `v1.3.0rc20` 明确宣布，这是最后一个支持 TensorRT backend 的 RC 版本；7 月 22 日发布的 `v1.3.0rc22` 又进一步删除了旧 TensorRT backend 的 C++ 模块。当前主线迁移文档则直接写明：PyTorch 已经成为 TensorRT-LLM 唯一的执行后端，`trtllm-build`、`trtllm-refit`、逐模型 checkpoint 转换脚本以及对 TensorRT Python 包的依赖都被移除，Hugging Face checkpoint 可以直接加载。([GitHub](https://github.com/NVIDIA/TensorRT-LLM/releases))

截至 2026 年 7 月 25 日，TensorRT-LLM 最新稳定版仍是 4 月 20 日发布的 `v1.2.1`，最新预发布版本则是 `v1.3.0rc22`。因此，生产用户现在看到的是一个明显的过渡状态：稳定版还保留旧体系，而 1.3 主线已经完成了架构换轨。([GitHub](https://github.com/NVIDIA/TensorRT-LLM/releases?page=2))

这不是简单地“多支持了一个 PyTorch 后端”。

更准确地说，这是 TensorRT-LLM 在重新回答一个根本问题：

> 大模型推理的性能，究竟应该主要来自一个提前构建好的静态 TensorRT Engine，还是来自“PyTorch 模型表达 + 专用算子 + CUDA Graph + 动态推理运行时”的组合？

NVIDIA 现在显然选择了后者。

---

### 一、这条路线并不是突然发生的

回头看过去一年多的动作，可以发现 TensorRT-LLM 的转向非常有连续性。

在 `v1.0.0rc0` 中，PyTorch LLM 就已经被提升为默认后端。2025 年 8 月的架构路线图又明确提出，要解除 PyTorch backend 对 TensorRT framework 的硬依赖，并以 TorchSampler 为基础，把原来 C++ Sampler 的性能能力逐步迁移过来。也就是说，NVIDIA 当时已经不再把 PyTorch backend 看成兼容性补丁，而是在把它建设成新的主架构。([GitHub](https://github.com/NVIDIA/TensorRT-LLM/discussions/5478))

随后几个月的节奏更加清晰：

- 2026 年 2 月，NVIDIA 推出 AutoDeploy Beta，希望通过 `torch.export` 和图变换，自动给 PyTorch 模型插入 KV Cache、模型切分、量化和算子融合。
- 4 月的 `v1.3.0rc11` 开始在旧 TensorRT backend 入口上增加弃用警告，同时弃用旧的 TRTLLMSampler。
- 6 月的 `v1.3.0rc20` 宣布这是最后一个支持 TensorRT backend 的版本。
- 7 月的 `v1.3.0rc21` 宣布 AutoDeploy 进入弃用流程，转向基于 Agent 的模型适配。
- `v1.3.0rc22` 正式删除遗留 TensorRT backend 的 C++ 模块。([NVIDIA Developer](https://developer.nvidia.com/blog/automating-inference-optimizations-with-nvidia-tensorrt-llm-autodeploy/))

所以，TensorRT-LLM 最近的动作不能分开看。

**PyTorch 成为默认后端、移除 TensorRT Engine、弃用 AutoDeploy、建设建模 Agent、开放 FlashInfer 内核、加强 PyExecutor 和 KV Cache Manager，本质上是同一场架构重组。**

### 二、被删除的 TensorRT backend，到底是什么？

过去 TensorRT-LLM 的典型工作流是：

```text
Hugging Face / NeMo Checkpoint
          ↓
Checkpoint 转换
          ↓
TensorRT-LLM Model Definition
          ↓
trtllm-build
          ↓
序列化 TensorRT Engine
          ↓
C++ Executor 执行
```

用户需要先把模型权重转换成 TensorRT-LLM 能理解的格式，再根据 TP、PP、最大 Batch、最大输入长度、最大输出长度、量化方式等参数构建 Engine。

它的优点很明显：可以在离线构建阶段完成图优化、算子选择、常量折叠、插件配置和内存规划，最终得到一个相对稳定、可重复执行的 Engine。

但问题也同样明显：

模型架构每变化一次，TensorRT-LLM 基本都要重新实现一套模型定义、权重转换和 plugin 对接；部署参数变化后，往往还要重新构建 Engine；面对动态 Batch、Chunked Prefill、推测解码、MoE、混合 Attention、多模态和复杂 KV Cache 状态时，静态 Engine 的管理成本越来越高。

新的工作流则变成：

```text
Hugging Face Checkpoint
          ↓
TensorRT-LLM 原生 PyTorch Model
          ↓
PyTorchModelEngine
          ↓
PyExecutor
          ↓
专用 Attention / MoE / GEMM / Communication Kernel
          ↓
可选 torch.compile + Piecewise CUDA Graph
```

官方迁移文档明确表示，新的路径不再需要独立的 checkpoint 转换和 Engine Build 步骤，`LLM(model="<hf_model>")` 或 `trtllm-serve <hf_model>` 就可以直接加载模型。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-LLM/legacy/tensorrt-backend-removal.html))

这意味着 TensorRT-LLM 的主要部署产物，也从“提前生成的 TensorRT Engine”，变成了“checkpoint、运行时配置、专用内核以及运行期间生成的 CUDA Graph、autotuning cache 和 JIT cache”。

但这里必须强调一点：

> PyTorch backend 不等于直接运行 Hugging Face 的 `transformers.generate()`，更不等于所有算子都回到了普通 PyTorch eager。

TensorRT-LLM 只是把**模型表达和运行时控制**迁到了 PyTorch，真正的高性能计算仍然依赖大量 NVIDIA 专用实现。

### 三、PyTorch backend 的本质：PyTorch 是控制面，专用内核是数据面

现在的 TensorRT-LLM 大致可以分成五层：

```text
┌──────────────────────────────────────────────┐
│ OpenAI API / LLM API / trtllm-serve          │
├──────────────────────────────────────────────┤
│ PyExecutor                                   │
│ Scheduler / KVCacheManager / Sampler         │
├──────────────────────────────────────────────┤
│ TensorRT-LLM Native PyTorch Model            │
│ AttentionMetadata / ModelConfig / Modules    │
├──────────────────────────────────────────────┤
│ torch.compile Custom Backend                 │
│ Piecewise CUDA Graph / Graph Rewrite         │
├──────────────────────────────────────────────┤
│ TRT-LLM Gen / FlashInfer / CUTLASS / CuTe DSL│
│ Triton / Custom CUDA / NCCL / NIXL           │
└──────────────────────────────────────────────┘
```

### 1. 模型定义层改成了原生 PyTorch

新增模型时，开发者可以从 Hugging Face 的 modeling 代码出发，复用 Hugging Face 的 config，但仍然需要把 Attention、DecoderLayer、MoE 等关键模块改写成 TensorRT-LLM 的 PyTorch 模块。

例如模型的 `forward` 不再只是接收普通的 `input_ids` 和 `position_ids`，还需要接收 TensorRT-LLM 运行时生成的 `AttentionMetadata`。Attention 模块也会被替换成 `tensorrt_llm._torch.modules.attention.Attention`，从而接入 Paged KV Cache、Packed Token、不同 Attention Backend 和 CUDA Graph。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-LLM/models/adding-new-model.html))

因此，这是一种“PyTorch 原生但推理系统感知”的模型定义，而不是直接拿 Hugging Face 模型原样执行。

### 2. PyExecutor 负责动态服务调度

`LLM` API 内部会在每个 rank 上创建 PyExecutor。PyExecutor 持续运行一个请求循环，负责：

- 拉取新请求；
- 选择当前 step 执行哪些请求；
- 分配和释放 KV Cache；
- 调用 ModelEngine 完成一次 forward；
- 执行采样；
- 更新请求状态并返回结果。

其核心组件包括 Scheduler、KVCacheManager、ModelEngine 和 Sampler。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-LLM/developer-guide/overview.html))

这也是 PyTorch backend 与普通 PyTorch 推理最大的区别之一。

普通 PyTorch 模型主要解决“给定 Tensor 如何做一次 forward”；TensorRT-LLM 的 PyExecutor 解决的是“服务中几百个生命周期不同的请求，如何在每一步组合成一个高效 Batch，并正确管理 KV Cache、推测 token、暂停请求和完成请求”。

### 3. 重算子仍然是 Custom Op

在 Attention、MoE、MTP、量化 GEMM 等热路径上，TensorRT-LLM 并没有寄希望于通用 PyTorch 算子自动得到最优性能。

相反，它大量使用 TRT-LLM Gen、FlashInfer、CUTLASS、CuTe DSL、Triton 和自定义 CUDA Kernel。2026 年的稳定版已经加入或强化 FlashInfer Sampling、TRT-LLM Gen Kernel、CuTe DSL MoE、DeepEP CUDA Graph、EPLB 和多种低精度路径。([GitHub](https://github.com/NVIDIA/TensorRT-LLM/releases?page=2))

TensorRT-LLM 文档还明确提到，对于 DeepSeek、Qwen、Llama 等重点模型，Attention、MoE routed expert 和 MTP 等大模块会被包装成较大的 PyTorch Custom Op。

这样做有两个作用：

第一，Custom Op 对 `torch.compile` 来说是一个黑盒，可以绕过复杂的动态控制流、数据相关循环和 Graph Break。

第二，真正决定性能的代码仍然由 NVIDIA 手写和调优，而不是完全交给 TorchInductor 自动生成。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-LLM/features/torch_compile_and_piecewise_cuda_graph.html))

换句话说：

> PyTorch 负责描述模型和组织执行，CUDA、CUTLASS、CuTe DSL 和 FlashInfer 负责把 GPU 跑满。

### 四、TensorRT-LLM 使用了 torch.compile，但不是大家通常理解的 Inductor 路线

看到 PyTorch backend，很多人会自然联想到：

```text
model = torch.compile(model)
```

然后让 TorchDynamo、AOTAutograd 和 TorchInductor 自动完成图捕获和 Kernel 生成。

但 TensorRT-LLM 的做法并不完全是这样。

它在 `torch.compile` 后面实现了自己的 custom backend。这个 backend 会在 Torch FX IR 和 ATen IR 上进行一系列专门针对推理的优化，例如：

- AllReduce、Residual 和 RMSNorm 融合；
- AllReduce 与 FP8、FP4 量化融合；
- User Buffer 接入；
- 去除不必要的 mutation copy；
- 自动多 Stream 调度；
- Piecewise CUDA Graph 分区。

官方文档甚至明确指出，这条路径依赖 Custom Op，并不使用常规的 Inductor Codegen 来完成整个模型。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-LLM/features/torch_compile_and_piecewise_cuda_graph.html))

所以更准确的理解是：

> TensorRT-LLM 把 `torch.compile` 当成图捕获、图分析、模式匹配和执行分区的基础设施，而不是把所有高性能 Kernel 的生成权交给 TorchInductor。

这其实很符合大模型推理的现实。

RMSNorm、逐元素算子、简单通信后处理可以通过图模式进行垂直融合；但 FlashAttention、MLA、MoE、MTP、低精度 GEMM 等复杂模块，通常仍然需要架构特化的手写 Kernel 和大量 heuristic。

### 五、Piecewise CUDA Graph：静态图与动态执行不再二选一

PyTorch backend 面临的一个现实问题是 CPU Launch Overhead。

Decode 阶段单步计算量小、Kernel 数量多。如果每个 token 都通过 Python 和 CUDA Driver 逐个下发 Kernel，CPU 侧开销很容易成为瓶颈。

TensorRT-LLM 的解决方式不是重新回到“整个模型生成一个静态 TensorRT Engine”，而是使用两种 CUDA Graph：

- Generation-only CUDA Graph 处理纯 Decode step；
- Piecewise CUDA Graph 处理 Prefill 或 Prefill 与 Decode 混合的 step。

Piecewise CUDA Graph 的核心思想是：

> 不能捕获的区域继续 eager 执行，能捕获的区域切成若干段 CUDA Graph。

当前设计主要把 Attention 视为不可捕获区域，让 Attention 在 eager/custom-op 模式下运行；Attention 前后的可捕获区域则分别记录成 CUDA Graph，并在运行时根据 token 数量选择对应的 Graph。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-LLM/features/torch_compile_and_piecewise_cuda_graph.html))

这很重要，因为它说明 NVIDIA 已经不再追求“一定要把完整模型塞进一个静态图”。

对于现代推理系统来说，Attention 的 Batch 组成、KV Block Table、上下文长度、稀疏索引和 Cache 状态都可能动态变化。与其为了构建完整静态图增加大量限制，不如承认动态区域存在，只捕获真正稳定的部分。

TensorRT-LLM 的新优化哲学因此可以概括为：

> **能静态的静态，必须动态的动态，最重的部分交给 Custom Op。**

### 六、为什么 NVIDIA 要在现在完成这次换轨？

### 原因一：模型更新速度已经超过了静态 Engine 工作流的承受能力

过去主流模型基本都是结构相似的 Dense Transformer。支持一个新模型，往往只是修改 QKV 布局、RoPE、Norm 和 MLP。

但现在的新模型已经越来越像独立的推理系统：

- DeepSeek 系列有 MLA、MoE、MTP、Attention DP 和复杂 EP；
- Hybrid Model 同时包含 Attention、Mamba、Linear Attention；
- 多模态模型包含 Vision Encoder、Cross Attention 和动态输入；
- 推测解码需要同时管理 Target、Draft 和多个 Cache；
- 稀疏 Attention 还需要额外保存 Index、Label 或压缩状态。

TensorRT-LLM 最新的 DeepSeek-V4 实现就是一个很典型的例子。它不是简单注册一个模型类，而是实现了专门的 `DeepseekV4ForCausalLM`、Sparse Attention Backend 和 `DeepseekV4CacheManager`，用来管理 Sliding Window Cache、压缩 Cache、Compressor 中间状态和 Indexer Cache。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-LLM/blogs/tech_blog/blog26_DeepSeek_V4_on_NVIDIA_Blackwell_Model_Specific_and_Agentic_Workload_Optimizations_in_TensorRT-LLM.html))

面对这类模型，提前把一切固化成一个通用静态 Engine，适配成本会越来越高。

PyTorch 模型代码则更适合表达复杂状态、条件分支和模型特有逻辑。

### 原因二：服务运行时比模型计算图本身更重要了

现在决定推理效率的已经不只是单次 forward，还有：

- In-Flight Batching；
- Paged KV Cache；
- Prefix Cache；
- Chunked Prefill；
- Overlap Scheduler；
- Speculative Decoding；
- Context/Generation 分离；
- KV Cache 传输；
- 请求暂停、恢复和驱逐；
- 多租户 LoRA；
- Agent 多轮请求中的 KV 复用。

这些机制高度依赖请求的实时状态，不可能完全由一个提前构建好的静态 Engine 决定。

TensorRT-LLM 当前的架构已经把 Scheduler、KVCacheManager、ModelEngine 和 Sampler 都提升为一等组件；Q3 路线图还计划默认启用 KV Cache Manager V2 和 KV Cache Transceiver V2。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-LLM/torch/arch_overview.html))

这说明 NVIDIA 正在把产品重心从“模型编译器”移向“推理运行时”。

### 原因三：必须缩短模型从发布到上线的时间

vLLM 和 SGLang 的一个重要优势，就是新模型通常可以快速从 Hugging Face 实现迁移过来。

TensorRT-LLM 过去需要重新实现模型、转换权重、实现 Plugin、构建和验证 Engine，很容易错过新模型发布后的第一波部署需求。

PyTorch backend 允许开发者复用 Hugging Face config 和 modeling 代码，并直接加载 Hugging Face checkpoint。虽然重点模型仍然需要针对 Attention、MoE 和 Cache 做专门适配，但整体开发路径已经更接近 PyTorch 社区。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-LLM/models/adding-new-model.html))

### 七、最值得玩味的动作：AutoDeploy 五个月内从 Beta 走向弃用

2026 年 2 月，NVIDIA 对 AutoDeploy 寄予了很高期待。

AutoDeploy 的设计是：

```text
原始 Hugging Face / PyTorch Model
                ↓
            torch.export
                ↓
         Torch / ATen Graph
                ↓
插入 KV Cache、模型切分、量化、算子融合
                ↓
        TensorRT-LLM PyTorch Runtime
```

它希望让一个普通 PyTorch 模型无需人工重写，就能自动获得 KV Cache、Multi-GPU Sharding、量化、Attention Fusion 和 CUDA Graph，并快速形成 Day-0 可运行版本。([NVIDIA Developer](https://developer.nvidia.com/blog/automating-inference-optimizations-with-nvidia-tensorrt-llm-autodeploy/))

但在 7 月 15 日发布的 `v1.3.0rc21` 中，NVIDIA 宣布 AutoDeploy backend 正在被弃用，同时表示将采用“agentic approaches”缩短 PyTorch backend 的模型适配时间，并称这一方法已经帮助 MiniMax M3 在模型发布后一周内获得功能支持。Q3 路线图里也出现了 Modeling Agent、Kernel Agent、CI Agent 和自动性能优化 Agent。([GitHub](https://github.com/NVIDIA/TensorRT-LLM/releases))

NVIDIA 并没有公开给出弃用 AutoDeploy 的完整技术原因。下面是我的判断。

### 通用图变换适合做 Baseline，但很难完成生产级语义适配

自动编译器可以识别 Linear、Attention、Norm 和 GEMM，但未必理解：

- 某个状态应该保存多久；
- 某段 Cache 是否可以 Prefix Reuse；
- 某个压缩状态应该如何跨 Chunked Prefill 延续；
- Draft 和 Target 应该共享还是独立管理 KV；
- 某个 MoE 路由如何与 EPLB、EP 和 All-to-All 组合；
- 某个动态循环是否允许被 CUDA Graph 捕获；
- 不同硬件上应该选择哪一种 Attention 或 MoE Backend。

DeepSeek-V4 的专用 Cache Manager 就说明，生产级模型支持经常需要理解模型语义，而不仅仅是变换算子图。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-LLM/blogs/tech_blog/blog26_DeepSeek_V4_on_NVIDIA_Blackwell_Model_Specific_and_Agentic_Workload_Optimizations_in_TensorRT-LLM.html))

因此，NVIDIA 现在似乎正在从：

> “用一个通用编译器自动转换任意模型”

转向：

> “让 Agent 自动生成和维护一份 TensorRT-LLM 原生 PyTorch 模型实现，再接入成熟的 Kernel 和 Runtime”。

后者仍然是自动化，但自动化的对象从“运行时 Graph”变成了“模型适配代码”。

这是一个非常值得关注的方向变化。

### 八、PyTorch backend 之外，TensorRT-LLM 最近还在做什么？

把近期 Release 和 Q3 Roadmap 放在一起，可以看到四条非常明确的主线。

### 1. 统一运行时组件

TensorRT-LLM 正在推动 KV Cache Manager V2、KV Cache Transceiver V2，并准备合并 TorchSampler、TRTLLMSampler 和 speculative decoding sampler。

这意味着过去 C++ 与 Python 两套实现并存的组件，会逐渐统一到以 Python 为接口、以专用 Kernel 为性能基础的体系。([GitHub](https://github.com/NVIDIA/TensorRT-LLM/issues/15044))

### 2. 从单机推理转向分布式服务系统

`v1.2.0` 已经加入动态服务发现、请求取消、NIXL-LibFabric、Mooncake Cache Transceiver、Helix Parallelism 和 Ray Orchestrator；`v1.3.0rc22` 又加入了 Disaggregated Coordinator 和多进程 Orchestrator Fleet。([GitHub](https://github.com/NVIDIA/TensorRT-LLM/releases?page=2))

TensorRT-LLM 的 P/D 分离也不再只是一个 Demo。当前架构已经把 KV Cache 交换从 KV Cache Manager 和底层通信库中解耦，支持 UCX、NIXL、MPI、RDMA 和 NVLink，并在此基础上建设动态扩缩容。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-LLM/features/disagg-serving.html))

### 3. 把推测解码和 Agent 工作负载提升为核心能力

Q3 路线图明确列出了 DFlash、动态 Draft Length、Eagle 单模型配置简化、Helix 与 Speculative Decoding 组合等能力。最新 RC 也加入了 Laguna DFlash Drafter 和 DeepSeek DSpark Drafter。([GitHub](https://github.com/NVIDIA/TensorRT-LLM/issues/15044))

与此同时，TensorRT-LLM 对 Agent 的优化边界已经从单次模型 forward 扩展到路由、KV Cache 复用、Host 开销、调度、编排和控制面。DeepSeek-V4 的最新优化文章已经直接把“Agentic Workload Optimization”作为独立部分讨论。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-LLM/blogs/tech_blog/blog26_DeepSeek_V4_on_NVIDIA_Blackwell_Model_Specific_and_Agentic_Workload_Optimizations_in_TensorRT-LLM.html))

### 4. 从 LLM Engine 扩展成生成式 AI Runtime

Q3 路线图中已经出现：

- `LLM.encode()`；
- Embedding Endpoint；
- Scoring API；
- 在线 Profiling Endpoint；
- Visual Generation；
- GPU Memory Service；
- ModelExpress P2P Weight Transfer。

最新版本也在持续增加图像、视频和多模态生成能力。([GitHub](https://github.com/NVIDIA/TensorRT-LLM/issues/15044))

所以未来的 TensorRT-LLM，可能已经不适合再被简单理解成“一个 LLM Engine Builder”。

它正在变成 NVIDIA GPU 上的**生成式 AI 推理运行时和参考实现**。

---

### 九、这对 vLLM、SGLang 和整个推理生态意味着什么？

过去 TensorRT-LLM 与 vLLM、SGLang 的差异非常明显：

- TensorRT-LLM 更偏静态 Engine、Kernel 极致优化和 NVIDIA 硬件特化；
- vLLM、SGLang 更偏 PyTorch 原生、动态调度和模型快速适配。

随着 TensorRT backend 被删除，这个边界正在迅速变模糊。

TensorRT-LLM 现在同样采用：

- PyTorch 模型定义；
- 动态 Scheduler；
- Paged KV Cache；
- Python Runtime；
- CUDA Graph；
- 多种可切换 Attention 和 MoE Backend；
- 分布式 KV Cache 传输；
- OpenAI 兼容服务接口。

因此，未来三者竞争的重点不再只是“谁的 Kernel 更快”，而会集中在：

- 新模型适配速度；
- Feature Combination 的稳定性；
- KV Cache 和请求调度能力；
- 推测解码；
- P/D 分离；
- 多节点扩缩容；
- 启动和加载速度；
- 配置复杂度；
- 性能调优体验。

更有意思的是，NVIDIA 还在通过 FlashInfer 主动把 TensorRT-LLM 中的高性能 Kernel 提供给 vLLM、SGLang 和其他推理框架。NVIDIA 官方明确表示，正在把包括 TensorRT-LLM Kernel 在内的高性能推理算子发布到 FlashInfer，并以 Attention、GEMM、Communication 和 Sampling 四类接口供其他 Serving Engine 接入。([NVIDIA Developer](https://developer.nvidia.com/blog/run-high-performance-llm-inference-kernels-from-nvidia-using-flashinfer/))

这背后的战略并不难理解：

> NVIDIA 不一定要求所有用户都使用 TensorRT-LLM，但希望无论用户选择 TensorRT-LLM、vLLM 还是 SGLang，底层最终都使用 NVIDIA 最优化的 Kernel。

TensorRT-LLM 是完整运行时，FlashInfer 则可能成为跨框架的 Kernel 分发层。

从这个角度看，NVIDIA 的护城河正在从“一个封闭的 TensorRT Engine”，迁移到：

1. GPU 架构与 Kernel 联合设计；
2. Attention、MoE、低精度和通信算子；
3. KV Cache 与调度运行时；
4. 多机互联和 P/D 分离；
5. 新模型上线和自动优化能力。

### 十、PyTorch backend 仍然有明显风险

### 风险一：`torch.compile` 还没有达到“开了就更快”的程度

最新的 `v1.3.0rc22` 仍然把 PyTorch Compilation Backend Crash 列为已知问题。

部分 DeepSeek、Llama、FP8、NVFP4 和 FlashInfer 多卡配置在 `torch_compile=True` 时会出现 KeyError、Accuracy Failure 或 CUDA 错误，官方给出的临时解决方式就是关闭 `torch.compile`。([GitHub](https://github.com/NVIDIA/TensorRT-LLM/releases))

当前文档也表示，torch.compile 暂不支持 Multi-ModelEngine 配置，双模型 Eagle3、双模型 MTP 和部分多模态场景存在限制。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-LLM/features/torch_compile_and_piecewise_cuda_graph.html))

所以工程上不能简单认为：

```text
PyTorch backend + torch.compile = 最优性能
```

真实情况往往是：

```text
模型 × GPU × 精度 × 并行策略 × Attention Backend
× MoE Backend × CUDA Graph × Overlap Scheduler
```

共同决定最终结果。

### 风险二：离线 Build 成本并没有完全消失，只是转移了

不再执行 `trtllm-build`，确实降低了部署门槛。

但运行时仍然可能需要：

- 加载和重新布局权重；
- JIT 编译 Kernel；
- 执行 Kernel Autotuning；
- Warmup；
- 捕获多组 CUDA Graph；
- 为不同 Token 数准备 Piecewise CUDA Graph；
- 分配 KV Cache Pool；
- 初始化通信和并行环境。

也就是说，过去集中在离线 Engine Build 阶段的部分成本，被转移到了服务初始化、Warmup 和运行时 Cache 管理阶段。

这会提高灵活性，但也会给冷启动时间、版本一致性和部署复现带来新的要求。

### 风险三：后端选择仍然复杂

TensorRT-LLM 目前拥有多种 Attention、MoE、GEMM 和 Communication Backend。2025 年的架构路线图甚至提到 MoE 模块已经有七种不同后端，而 Q3 2026 路线图仍然把“简化 MoE Backend 配置”和“静态配置校验”列为重点。([GitHub](https://github.com/NVIDIA/TensorRT-LLM/discussions/7834))

PyTorch 让模型代码更灵活，却不一定自动让整个系统更简单。

真正困难的部分，已经从“如何 Build Engine”，转变成了“如何为当前模型和硬件选择正确的 Kernel、Graph、Parallelism 和 Runtime 组合”。

---

### 十一、对使用 TensorRT-LLM 的工程团队有什么建议？

### 第一，新项目不要再围绕 TensorRT Engine Build 设计

新的项目应当直接采用：

```text
Hugging Face Checkpoint
        +
TensorRT-LLM PyTorch Model
        +
LLM API / trtllm-serve
```

不要再为 `convert_checkpoint.py`、`trtllm-build` 和 Engine Artifact 建设新的发布体系，因为主线已经明确移除了这些入口。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-LLM/legacy/tensorrt-backend-removal.html))

### 第二，旧项目需要区分“短期稳定”和“长期演进”

仍然严重依赖旧 TensorRT Engine 的生产项目，可以短期固定在 `v1.2.1` 或仍然包含旧 backend 的版本上，但必须开始评估迁移。

需要重点检查的不是 API 能不能跑通，而是：

- 量化 checkpoint 能否直接加载；
- 旧 Plugin 对应的新 Kernel Backend；
- CUDA Graph 覆盖率；
- KV Cache 占用；
- Prefix Cache 命中率；
- Speculative Decoding；
- 多卡和多节点稳定性；
- 冷启动与 Warmup 时间。

### 第三，不要只测试一个“PyTorch backend 性能数字”

至少应该分别测试：

1. Eager + Custom Op；
2. Generation CUDA Graph；
3. `torch.compile`；
4. `torch.compile + Piecewise CUDA Graph`；
5. 不同 Attention Backend；
6. 不同 MoE Backend；
7. Aggregated 与 Disaggregated Serving；
8. 开关 Overlap Scheduler；
9. 开关 KV Cache Reuse；
10. 开关 Speculative Decoding。

同时记录 TTFT、TPOT、Output Throughput、Tokens/s/GPU、GPU Memory、CPU 占用、Warmup 时间和长时间稳定性。

“PyTorch backend 快不快”本身不是一个完整问题。

必须进一步问：

> 在哪个模型、哪种精度、哪种并行配置、哪种 Kernel Backend、哪种请求分布下快不快？

### 第四，`torch.compile=True` 不应成为未经验证的默认项

最新 RC 仍然存在多卡编译问题，因此生产配置应当按模型建立白名单。

对于重点模型，可以使用 `torch.compile` 和 Piecewise CUDA Graph；对于不稳定模型，则保留 Eager Custom Op 和 Generation-only CUDA Graph 路径。([GitHub](https://github.com/NVIDIA/TensorRT-LLM/releases))

### 十二、对其他推理框架和芯片后端的启示

TensorRT-LLM 的变化也验证了一种越来越清晰的推理框架架构：

```text
PyTorch 原生模型表达
        ↓
少量高性能 Custom Op 岛
        ↓
可静态区域进行图编译和 Graph Capture
        ↓
独立的 Scheduler、KV Cache Manager 和 Executor
```

这比“全 PyTorch eager”和“整个模型一次性静态编译”都更现实。

对于其他芯片后端，值得参考的是同时建立四层能力：

1. **模型层**：让新模型能以接近 Hugging Face 的 PyTorch 代码快速接入；
2. **算子层**：FA、GMM、MoE、量化、通信仍然由高性能专用算子承载；
3. **图执行层**：允许动态区域与静态图区域共存，而不是强迫整个模型全部成图；
4. **运行时层**：Scheduler、KV Cache、Prefix Reuse、P/D 分离和推测解码成为独立系统组件。

尤其是 AutoDeploy 从通用图变换转向建模 Agent，也说明单靠一个“万能图编译器”很难解决不断变化的新模型。

未来更实际的自动化路径，可能是由 Agent 根据参考模型自动生成：

- 芯片后端模型代码；
- 权重映射；
- Attention Metadata；
- KV Cache 定义；
- 算子替换；
- 并行切分；
- Accuracy 和 Performance CI。

---

### 结语：TensorRT-LLM 没有放弃 TensorRT 的思想，而是拆掉了 TensorRT Engine 的边界

TensorRT-LLM 删除 TensorRT backend，看起来像是在“去 TensorRT 化”。

但它真正放弃的，并不是硬件特化、Kernel Fusion、低精度计算和静态执行优化，而是：

> 把整个大模型提前固化成一个单一 TensorRT Engine，作为所有推理优化的唯一载体。

新的架构把不同职责重新分配了：

- 模型表达留在 PyTorch；
- 请求调度交给 PyExecutor；
- KV Cache 交给独立的 Cache Manager；
- Attention 和 MoE 交给专用 Custom Op；
- 融合和分区交给自定义 `torch.compile` backend；
- 稳定区域交给 CUDA Graph；
- 多节点扩展交给 NCCL、NIXL、Ray 和 Dynamo；
- 新模型适配则开始交给建模 Agent。

因此，TensorRT-LLM 最近最大的变化，不是“支持了 PyTorch”。

而是 NVIDIA 正在把 TensorRT-LLM 从一个**静态大模型 Engine Builder**，改造成一个以 PyTorch 为模型语言、以专用 Kernel 为性能基础、以动态调度和 KV Cache 为核心的**生成式 AI 推理操作系统**。

未来最强的推理框架，可能不再是那个能够把完整模型编译成最漂亮静态图的框架。

而是那个能够在**模型更新速度、服务动态性和硬件性能极限**之间，持续找到正确分层方式的系统。
