## llama.cpp 怎么更新到最新版：国内镜像下载 + 版本选择避坑（AMD/核显 multi-build 实战 2026 版）

> 我本地用 AMD 核显（Radeon 8060S，Strix Halo APU，gfx1151）跑大模型，llama.cpp 是底层推理引擎。官方几乎**每周**发新版（上游滚动 nightly 截至 2026-09-09 实测已到 b10868；发布时以 releases 页最新 build 为准），更新能拿到性能提升、新量化格式支持、一大堆 bug 修复。但每次想更新，都卡在第一步：GitHub release 下载动辄超时。<br> 本文给你一套我**实测可用**的更新流程：确认版本 → 选对构建 → 国内镜像加速下载 → 校验完整性 → 备份+覆盖。重点在三个最容易翻车的地方：① **选错构建版本**（CUDA / HIP / CPU / Vulkan / ROCmFP4 五花八门）直接导致跑不起来，而 APU 用户还多了”ROCm 还是 Vulkan”的二阶坑；② 国内直连 GitHub 慢，得用镜像代理兜底；③ Windows 下解压被进程锁文件导致**静默部分失败**，版本号没变却以为更新成功。<br> ⚠️ 本文初版（2026-07）是”单 Vulkan 构建”视角，核心建议是”AMD 核显闭眼选 Vulkan”——**那一条对你这块 Strix Halo APU 现在已不成立**，本文 2026-09 大改重写了构建选择章节，请直接看第二节。

---

### 一、为什么要经常更新 llama.cpp

很多人装完 llama.cpp 就再也没动过。但这是个**更新极频繁**的项目，保持新版通常能白嫖到：

- **推理性能提升**：GGML 后端每个月都有 kernel 优化，同样的显卡能多跑几个 token/s（Strix Halo 上 Vulkan 还有专门的 batched inference 调优 #27909，批量 n≥5 / 投机解码 n4+ 时显著）；
- **新量化格式**：IQ 系列、ROCmFP4（STRIX/FAST/LEAN）、更省显存的混合量化，老版本根本加载不了新 GGUF；
- **模型支持**：新出的 Qwen3.8-Flash-Next、DeepSeek-V4、Ling-3.0 这类模型，常有架构或模板依赖，旧版跑起来会出怪问题；
- **bug 修复**：`</chat>` 截断、长上下文崩溃、Vulkan 内存泄漏……很多都是新版修的。

结论先行：**与其等出问题再救，不如每月花 5 分钟跟一次新版。**

### 二、第一步就翻车：选对构建版本（本节 2026-09 重写）

这是 90% 的人更新的第一道坎。llama.cpp 的 release 资产有**一大排**，名字长得像，下错一个就白忙活。而且随着 ROCmFP4、qwen4exp-MTP 等新能力的出现，**同一个硬件上现在往往要并存多个构建**，各自干不同的活。

### 2.1 构建速查表

| 构建 | 来源仓库 | 适用硬件 / 用途 | 我的建议 |
| --- | --- | --- | --- |
| bin-win-vulkan-x64 | ggml-org/llama.cpp | AMD / Intel 集显、核显（APU）通用兜底，兼容性最广 | ✅ 通用首选；也是跑分对照基准 |
| windows-rocm-gfx1151-x64 | lemonade-sdk/llamacpp-rocm | Strix Halo / Radeon 8000 系列 APU（gfx1151）特调主力 | ✅ APU 用户主力；自带 ROCm 运行时，免装系统 ROCm |
| bin-win-hip-radeon-x64 | kingjones30/ROCmFPX | ROCmFP4 张量专用（STRIX/FAST/LEAN 等量化，普通构建加载不了） | ROCmFP4 模型必用；含 gfx1151 内核，APU 也能跑 |
| app-*-windows-x64-rocm-gfx1151 / *-vulkan | unslothai/llama.cpp | qwen4exp MTP（draft-mtp）专用，上游暂未合入 | qwen4exp 草稿加速必用 |
| bin-win-cuda-12.4 / 13.3-x64 | ggml-org/llama.cpp | NVIDIA 独立显卡 | N 卡专用，别给 A 卡下 |
| bin-win-cpu-x64 | ggml-org/llama.cpp | 纯 CPU 兜底 | 没显卡时用，无 GPU 加速，慢 |
| 上游 bin-win-hip-radeon-x64 | ggml-org/llama.cpp | 离散 Radeon 独显 | ⚠️ 面向独显，APU 兼容性差，核显别下（见 2.3） |
| bin-ubuntu-* 等 | Linux 专用 | — | Windows 用户别碰 |

### 2.2 Strix Halo / Radeon 8000 APU（gfx1151）专属建议

> 原版”AMD 核显闭眼选 Vulkan”对**老 AMD 卡 / 不确定硬件**仍成立，但对 **Strix Halo 这种新 APU 不成立**——这是我踩了半年坑后的修正。

我这块 Radeon 8060S 是 Strix Halo APU，实测结论是**多构建并存**，不能只装一个：

1. **普通量化模型（Q4_K_M 之类）的主力用 `lemonade-sdk/llamacpp-rocm` 的 `gfx1151` 构建**。它是专为这块 APU 调好的 ROCm 版，自带 ROCm 运行时（amdhip64_7.dll / ggml-hip.dll / hipblas.dll），**免装系统 ROCm**；在我机器上 Vulkan 的 prefill 仅约 27 t/s，而 ROCm 约 1321 t/s（差近 50 倍），且 ROCm 对 MoE 长上下文更稳，所以生产跑 ROCm、Vulkan 只留作跑分对照。
2. **ROCmFP4 量化模型（STRIX/FAST/LEAN 张量）必须走 `kingjones30/ROCmFPX`**。lemonade、unsloth、上游 Vulkan 全都不认 ROCmFP4 张量类型——二进制里扫不到 `ROCmFP4`/`Q4_0_ROCMFP` 引用。这类模型在 ROCm 构建上直接 `unknown tensor type` 起不来。
3. **上游 Vulkan 构建保留做跑分对照**（不服务任何生产端口）。真要深挖普通量化负载的吞吐，可以按双后端 A/B 在 Vulkan 上测；但日常别让它占生产端口。
4. **qwen4exp 的 MTP 草稿（draft-mtp）目前只有 `unslothai/llama.cpp` 确认可用**（其 release 明确写 “MTP for Qwen3.8-Flash-Next”）。上游 lemonade 二进制里能扫到 `draft-mtp` 字样，但那是通用 MTP 选项，**qwen4exp 专用 NextN 头能否接受未经验证**——主模到位后必须实测。

一句话：**APU 用户先想清楚”我要跑哪种张量”，再选构建，而不是无脑 Vulkan。**

### 2.3 HIP vs ROCm：一个最容易被坑的命名陷阱

两种 `hip-radeon` 不是一回事，下错直接跑不起来：

- **上游 `ggml-org` 的 `bin-win-hip-radeon-x64`**：面向**离散 Radeon 独显**，APU（核显）不一定能跑，Strix Halo 上兼容性差——**别给核显下**。
- **`kingjones30/ROCmFPX` 的 `bin-win-hip-radeon-x64`**：虽然名字一样，但它**包含 gfx1151 内核**、且驱动 26.7.1 实测兼容，是 ROCmFP4 模型在 APU 上能跑的唯一构建。**这是例外，不是上游那个**。

区分口诀：**看仓库不看文件名**——要 ROCmFP4 就去 `kingjones30/ROCmFPX`，要通用 ROCm 去 `lemonade-sdk/llamacpp-rocm`（asset 名带 `gfx1151`），别拿上游 `hip-radeon` 往 APU 上塞。

### 2.4 ⚠️ 四套 build 号互相独立，数字大 ≠ 更新 ≠ 更好

不同来源各自编号，**禁止跨线比大小**：

| 构建线 | 编号格式 | 当前基线（2026-09） | 说明 |
| --- | --- | --- | --- |
| 上游 Vulkan | b10xxx | b10868 | 滚动 nightly |
| lemonade ROCm（gfx1151） | b13xxx | b1325 | 通用主力，编号体系独立 |
| ROCmFPX（ROCmFP4） | b2xx | b271 | 只跑 ROCmFP4 张量 |
| unsloth ROCm/Vulkan | b10xxx-mix-<commit> | b10798 | 资产名是 app- 前缀不是 llama- |

例：unsloth b10798 数字小于上游 b10868，但功能上多了 qwen4exp MTP，两者用途完全不同。**查版本时分别去各自仓库的 releases 页，别拿一个数字大小判断谁新。**

### 三、确认最新版本

版本号直接拼进文件名，所以你只要拿到那个 `bXXXXX` 数字，后面的包名就能自己拼出来。

**上游 Vulkan（ggml-org）**：打开 [releases 页面](https://github.com/ggml-org/llama.cpp/releases)，最新滚动 nightly 形如 `b10868`，对应的 Windows 资产名就是：

```text
llama-b10868-bin-win-vulkan-x64.zip
```

> ⚠️ 注意：`/releases/latest` 会重定向到**稳定版 tag**（现在 v0.4.0，其 nightly 号反而比真正的滚动 nightly 低）。**真正的滚动 nightly 在 releases 列表里的预发布条目**，点进列表第一条（如 `b10868`）拿资产名最准。

**其他构建线各自查各自的 releases 页**：

- lemonade ROCm：`lemonade-sdk/llamacpp-rocm` → 资产 `llama-b<BUILD>-windows-rocm-gfx1151-x64.zip`
- ROCmFPX：`kingjones30/ROCmFPX` → 资产 `llama-b<BUILD>-bin-win-hip-radeon-x64.zip`（顺带下 `archs.txt` 确认模型架构支持）
- unsloth：`unslothai/llama.cpp` → 资产 `app-b<BUILD>-mix-<commit>-windows-x64-rocm-gfx1151.zip`（**注意是 `app-` 前缀，别拼成 `llama-` 否则 404**）

> ⚠️ 各第三方构建的资产名会随仓库调整，**发布前请以各自 releases 页实际文件名核对**，下文示例仅反映 2026-09 现状。<br> 小提示：用浏览器/GitHub 页面能确认版本和资产名，但**二进制本体得下载**——网页预览不了 zip 里的 exe。

### 四、国内下载：镜像代理加速（核心技巧）

**痛点**：国内直连 GitHub 下载 release 经常超时、速度个位数 KB/s，GitHub 官方 CDN 在国内的连通性一言难尽。

**解法**：用「GitHub 前缀代理」镜像节点。原理很简单——把完整 GitHub 下载 URL 拼在某个国内可达节点的域名后面：

```text
https://<镜像节点>/https://github.com/ggml-org/llama.cpp/releases/download/b10868/llama-b10868-bin-win-vulkan-x64.zip
```

**实测可用的两个节点**（2026-09-09 亲测均返回 `206` 真文件流；此前 08-30⁄31 曾短暂抽风，现已恢复）：

| 节点 | 角色 | 说明 |
| --- | --- | --- |
| github.tbap.top | 主用 | 速度较快，~35MB 约半分钟~1 分钟 |
| gh.dpik.top | 备用 | 主节点抽风时切换；大包（ROCm 94MB / ROCmFPX 400MB）更稳 |

**下载前先探一下节点活不活**（range GET 看是否返回 `206`）：

```bash
URL_PATH="https://github.com/ggml-org/llama.cpp/releases/download/b10868/llama-b10868-bin-win-vulkan-x64.zip"
for m in "https://github.tbap.top/" "https://gh.dpik.top/"; do
  curl -s -o /dev/null -w "$m -> %{http_code} ct=%{content_type}\n" --max-time 25 -r 0-1023 \
    -A "Mozilla/5.0 (Windows NT 10.0; Win64; x64)" "${m}${URL_PATH}"
done
```

返回 `206` + `application/octet-stream` 就可以放心下。带 browser UA（部分节点会拦空 UA）：

```bash
mkdir -p "D:/软件"
cd "D:/软件"
curl -L --fail --retry 3 --retry-delay 2 -C - \
  -A "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36" \
  --max-time 600 \
  "https://github.tbap.top/${URL_PATH}" -o "llama-b10868-bin-win-vulkan-x64.zip"
```

`-C -` 支持断点续传，网络抖断重跑会接着下，不用从头来。ROCmFPX 那种 400MB 大包在镜像上常被单连接限速，**直接后台跑并显式续传**，别在前台死等。

⚠️ **安全提醒（重要）**：这些镜像都是社区公共代理，**没有 SLA、随时可能失效**，更关键的是——第三方节点理论上能篡改你下载的内容。所以**下载后务必做下一步的完整性校验**，别跳过。只从你验证过返回 `206` + `application/octet-stream` 的节点下，且校验通过再解压。

### 五、校验完整性（别跳过）

下载完先验证 zip 没损坏、且包含该有的文件。Python 一行搞定（读内部不落盘，不算”解压”）：

```bash
python -c "import zipfile; z=zipfile.ZipFile(r'D:/软件/llama-b10868-bin-win-vulkan-x64.zip'); bad=z.testzip(); print('corrupt:',bad) if bad else print('ZIP OK', len(z.namelist()),'entries')"
```

确认两点：

1. 输出 `ZIP OK`（无损坏）；
2. 里面**必须**有 `ggml-vulkan.dll`、`llama-server.exe`、`llama-cli.exe`、`llama-quantize.exe`、`llama-bench.exe` 这几个关键文件。

> ⚠️ **Vulkan 包体量偏小（约 35 MB / 34 MiB）**，镜像一抽风就下成更小的残包，`testzip` 会直接报损坏——所以 Vulkan 包**必跑 testzip**，残包一律重下。ROCm 包（94MB）/ ROCmFPX（400MB）同理，下载后都过一遍。

**ROCm / ROCmFPX 构建**还要额外确认含 ROCm 运行时 dll：

```bash
python -c "import zipfile; z=zipfile.ZipFile(r'D:/软件/llama-b<BUILD>-windows-rocm-gfx1151-x64.zip'); [print(' ',n) for n in z.namelist() if n.endswith('.exe') or 'hip' in n.lower() or n.endswith('.dll')]"
```

确认有 `llama-server.exe` 及 `amdhip64_7.dll` / `ggml-hip.dll` / `hipblas.dll` 等。

解压**前**先确认一版当前 build 号（用 Windows 风格路径 `D:/软件/...`，别用 `/d/软件/...`，原生 exe 会找不到文件）：

```bash
"D:/软件/llama-cpp-vulkan/llama-server.exe" --version
```

输出形如 `version: 0.4.0-dev (build 10868, commit 304665fe7)`，记下来，解压后要对得上。

### 六、备份旧版 + 解压覆盖

llama.cpp 的安装目录一般就是一堆 exe + dll，没有用户脚本混在里面，直接覆盖副作用很小。但**稳妥起见先留回退点**，万一新版翻车能秒回退。

**备份策略（单 zip 法）**：安装目录内不再留 `_backup_*` 子目录，**唯一备份是 `D:/软件/llama-b<最新BUILD>-*.zip`**（始终保留最新一个，外加一个上一版作一步回滚）。回退 = 用旧 BUILD 的 zip 重新解压。不同构建线各自目录独立并存，互不干扰：

```text
D:/软件/llama-cpp-vulkan/      ← 上游 Vulkan（本文示例）
D:/软件/llama-cpp-rocm/        ← lemonade gfx1151 ROCm 主力
D:/软件/llama-cpp-rocmfpx/     ← ROCmFP4 专用
D:/软件/llama-cpp-unsloth-rocm/  ← qwen4exp MTP
```

解压覆盖（先确认无进程占用该目录）：

```bash
python -c "
import zipfile,os
inst=r'D:/软件/llama-cpp-vulkan'
try:
    with zipfile.ZipFile(r'D:/软件/llama-b10868-bin-win-vulkan-x64.zip') as z:
        z.extractall(inst)
except PermissionError as e:
    raise SystemExit('EXTRACT_BLOCKED_BY_LOCK: '+str(e)+' —— 关闭占用进程后重试')
print('extracted new build to',inst)
"
```

- **回退**：把上一版 BUILD 的 zip 重新 `extractall` 到对应目录即可；不长期保留多个旧 zip。
- 你自己的启动脚本、模型配置如果放在别的目录（通常都这么放），覆盖安装目录零影响。

### ⚠️ 致命坑：Windows 文件占用致解压静默部分失败

本机若有 `llama-server.exe` / `ollama` 进程在跑，Windows 会**锁住 `llama-server.exe` 及部分 dll**，`extractall` 对个别文件写不进却**不会整体报错**——结果是：备份”成功”、覆盖”失败”、**版本号没变却走到 DONE**。这是最容易让人误以为更新成功、实则原地踏步的坑。

正确做法（缺一不可）：

1. **解压前先关占用进程**：生产端口（如 8080–8084）正跑的 llama-server 会锁 ROCm 目录，先停掉再解压；
2. `extractall` **必须捕获 `PermissionError` 显式报错**（上面的脚本已做），禁止静默继续；
3. **解压后必须断言版本号真的变了**——这是兜底的最后一道闸：

```bash
"D:/软件/llama-cpp-vulkan/llama-server.exe" --version   # 必须是新 build 号
"D:/软件/llama-cpp-vulkan/llama-server.exe" --list-devices  # 必须看到你的 GPU
```

若 `--version` 仍是旧号，说明覆盖没生效（多为文件占用），回到上一步重新解压，**切勿当作完成**。`--list-devices` 还应能看到 `Vulkan0: AMD Radeon(TM) 8060S Graphics` 之类——若只剩 CPU，说明 ROCm 运行时与驱动不兼容。

### 七、避坑清单（建议收藏）

| 坑 | 后果 | 正确做法 |
| --- | --- | --- |
| 下错构建版本 | CUDA/HIP/CPU 直接跑不起来 | AMD/核显通用选 vulkan；Strix Halo APU 主力选 lemonade gfx1151 ROCm；ROCmFP4 选 ROCmFPX |
| 四套 build 号独立 | 拿数字大小判断”谁新”误判 | 各查各仓库；数字大 ≠ 更新 ≠ 更好 |
| 上游 hip-radeon 往 APU 上塞 | APU 起不来 | 看仓库：kingjones30/ROCmFPX 的 hip-radeon 含 gfx1151 内核才给 APU 用 |
| ROCmFP4 张量走错构建 | unknown tensor type | 只有 ROCmFPX 认；lemonade/Vulkan/unsloth 全不行 |
| unsloth 资产名 app- 前缀 | 拼 llama- 直接 404 | 用 app-b<BUILD>-mix-<commit>-windows-x64-rocm-gfx1151.zip |
| 常见 ghproxy 节点失效 | [http://ghproxy.com/.net/.cc](http://ghproxy.com/.net/.cc)、kgithub、moeyy、[http://ghproxy.homeboyc.cn](http://ghproxy.homeboyc.cn) 等多数已失效/不稳定 | 用 github.tbap.top / gh.dpik.top（发布时以实测可达为准） |
| 镜像节点无 SLA | 今天能用明天 404 | 主备两个都探一下，全挂就换思路（或交本机迅雷多线程下） |
| Vulkan 包被截断在 ~34MB | 残包 testzip 报错 | Vulkan 包必跑 testzip，残包重下 |
| 下载后不校验 | 可能拿到损坏/被篡改文件 | zipfile.testzip() 必跑 |
| Windows 文件占用致静默部分失败 | 版本号没变却以为更新成功 | 解压前停 llama-server/ollama；解压后断言 --version 真变 |
| 中文路径用 /d/软件/... | 原生 exe 报找不到文件 | 用 Windows 风格 D:/软件/... |

### 写在最后

更新 llama.cpp 这事，拆开看每一步都不难，但组合在一起最容易在「选错版本」「下载卡死」「解压被锁没生效」这三步翻车。如果只让我留三条：

1. **选对版本 > 下载方式 > 校验**——版本选错，后面全白搭；而 APU 用户还得先想清”跑哪种张量”再选构建，别无脑 Vulkan；
2. **国内下载认准镜像代理 + 必做完整性校验**，社区节点没有兜底，安全自己负责；
3. **先留回退 zip 再覆盖，且解压后必须断言 `--version` 真变**——一个被进程锁住的文件就能让”更新”原地踏步。

我现在的本地是**多构建并存**：上游 Vulkan b10868（跑分对照）+ lemonade gfx1151 ROCm b1325（普通量化主力）+ ROCmFPX b271（ROCmFP4 专用）+ unsloth b10798（qwen4exp MTP），Radeon 8060S 核显跑 Qwen3.8 / Ornith 35B MoE / Ling 稳得很。如果你也在本地用 llama.cpp，特别是 AMD 核显党，希望这篇能帮你 5 分钟跟一版，少熬几个深夜。
