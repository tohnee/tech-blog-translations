> **一句话版**：端侧需要的是一个 `batch=1, model_set>1` 的 vLLM——和云端 `batch>1, model_set=1` 正好轴是反的。<br> *作者：王多鱼-加油 | 专栏：HPC-端侧 · sysML* *立论文章 · 配套开源项目进行中*

### 零、先把结论摆在桌面上

过去半年，我在一台 Jetson Orin AGX 上围绕一个 3B 参数的具身 VLA——Wall-X——把能上的现代推理栈挨个走了一遍：

- **主线**：手写 CUDA + CUTLASS，自己把 MoE permute、M-RoPE、FlashAttention 端侧变体一个个推到 sm87 稳跑；
- **旁线 1**：TRT-LLM plugin，~1000 行 C++ 才把 Wall-X 的非标算子塞进去；
- **旁线 2**：TVM Relax 自管 pass，能跨编译器取回控制权，代价是端侧后端的坑要自己踩；
- **旁线 3**：torch.compile + Triton，day-1 跑通，却顶不到产线性能。

四条路线，每一条都亲手撞过一次壁。

**这件事做完，一个判断已经绕不过去：端侧 AI Infra 现在这个位置，大致对应云端 2022~2023 年那个节点——差 3 年。但差的不是硬件、不是算子、也不是编译器。**

Orin 上 Triton / FlashAttention 2 / TRT-LLM / TVM Relax / CUTLASS / FlashInfer，这些云端 LLM 推理主流栈，我一个个都装过、跑过、在 Wall-X 和 Qwen 上打过 benchmark。**没有一个是装不上或跑不通的**——问题从来不是「端侧缺工具」，而是「每条路线走到底都要再来一轮重写」。作为硬件底座，Orin + CUDA / TensorRT 生态的**编译器层和算子层已经基本齐活**。

那 3 年差距差在哪？差在这四件事：

- **具身 VLA 这一侧还停在 PyTorch + Transformers demo 阶段**——Wall-X、π0、OpenVLA、Diffusion Policy、ACT、Octo 几乎无一例外；
- **模型结构以月为单位迭代**——MoE、Flow Matching、dual-track attention、M-RoPE、各种 action head，每家一套；
- **云端 vLLM 是把「PyTorch demo → 生产级推理」这条沟填上的关键，但它的设计假设全绑在 batch=N / continuous batching / 吞吐优先上——和端侧机器人场景几乎条条相反**；
- **真正缺的是一个「batch=1、model_set>1（多模型共栖）、低延迟、能吃非标准输出」的端侧版 vLLM**——和云端 vLLM 的 `batch>1, model_set=1` 正交相反。

**3 年的差距，就差在这一层 runtime 上。这一层现在是空的。**

本文接下来讲清楚四件事：Orin 上其实什么都能装；为什么还是缺这一层；这一层应该长什么样；以及**三层栈 × 应用层三轨**的架构为什么是解法。

### 一、我在 Orin 上实测过的云端工具链清单

过去半年我在一台 Jetson Orin AGX 64GB 上，把云端 LLM 推理生态的主力工具都装了、跑了、打过 benchmark。这是本文所有判断的证据基座。

| 工具 | Orin 上的状态 | 实测结论 |
| --- | --- | --- |
| Triton（OpenAI Triton） | 可编可跑 | 端侧自定义 kernel 可写，作为 Track 1 研发轨的主力语言可行 |
| FlashAttention 2 | Wall-X 视觉分支已用 | 源码编译通过，Ampere+ 官方支持 sm87 |
| FlashInfer | flashinfer-python 0.6.9 能装能 import，show-config 正确识别 sm87 | pip install 会拉 torch 2.11 + CUDA 13.x 撞主栈，必须 --no-deps 隔离安装 |
| TensorRT-LLM | Jetson 分支 v0.12.0-jetson 可用 | 在此基础上手写了约 1000 行 plugin（MoE permute/unpermute、M-RoPE、Action Head、HuggingFace → TRT 权重 remap） |
| TensorRT | 原生可用（Orin 出厂即带） | SigLIP ViT 做成独立 engine，与 LLM backbone 异构协作 |
| TVM Relax | 后端可跑（sm87 / Ampere-mobile） | 可作为 TRT-LLM 失控时的 fallback 编译路径；与 TRT engine 子图互操作已验证 |
| CUTLASS | 模板库可用 | 写 plugin 时作为 GEMM / fused kernel 模板，减少从零写 CUDA |
| llama.cpp（CUDA backend） | 可编可跑 | 中小模型 baseline 参照；Q4_K_M / Q8_0 生态齐全 |

**一句话**：**Orin 作为硬件底座 + CUDA / TensorRT 生态，云端推理栈的编译器层和算子层在端侧已经基本齐活**。”端侧什么都没有”这个印象不准确。

麻烦在别的地方。

### 二、但具身 VLA 还停在 PyTorch demo 阶段

我系统性分析过目前主流的具身开源项目：Wall-X、OpenVLA、openpi、Diffusion Policy、ACT、Octo、LeRobot。几乎**无一例外**：

- **主干都是 PyTorch + Transformers + HuggingFace**
- **推理入口很多还是 `model.generate()` 或手写 Python for 循环 + ODE 积分**
- **动作输出不是标准 AR decode**（Flow Matching / Diffusion / ODE / 多头 action chunk）
- **控制流复杂**（多模态输入、proprioception scatter、多头输出、动态 dof mask）
- **部署代码往往不开源，即使开源也是 demo 级 Python 脚本**

以 Wall-X 为例，推理入口 `infer_robochallenge.py` 本质上是一个研究脚本 —— `predict_action_rtc()` + `_construct_input()` 做输入装配，attention 后端在运行时被显式改写，模型加载通过 `from_pretrained()` + 二次注入配置再挂 action 能力。扒完源码的结论很清晰：**主干仍是标准 PyTorch + Transformers，自定义算子只集中在 MoE / M-RoPE / 视觉 window/index 三处**。

这不是贬低 —— 研究阶段这样写是合理的。但**它和「生产级端侧推理」之间隔着完整的一段路**：

- 编译（PyTorch ckpt → 某个 runtime 可执行的东西）
- 量化（GPTQ / AWQ / SmoothQuant 端侧适配）
- 调度（多模型共栖、带宽感知、多进程编排）
- 服务化（ROS2 / gRPC 接入、zero-copy）
- 可观测性（trace / profiling / drop-rate / latency 分布）

**这一段路云端通过 vLLM / SGLang / TRT-LLM Server 填上了；端侧目前空着。**

> 详见：《别一上来就谈 CUDA：Wall-X 推理优化前，先搞清楚它到底是什么模型》、《从 infer_robochallenge.py 开始：Wall-X 的推理入口、数据加载和模型加载》、《具身开源项目横向对比表》

### 三、为什么云端 vLLM 端侧用不了

vLLM 是把”PyTorch demo → 生产级 LLM 推理”这条沟填平的关键。但它的每一条核心设计假设都绑在**云端场景**上 —— 端侧几乎条条相反：

| vLLM 假设 | 端侧机器人实际情况 |
| --- | --- |
| batch size 通常 > 1，要 continuous batching | 机器人单体部署，batch = 1 是常态 |
| 多请求吞吐最大化 | 单请求延迟最小化（决定动作 chunk 能不能接住） |
| PagedAttention 跨请求共享 KV cache | 单会话，paged 的工程复杂度几乎白给 |
| 模型是标准 decoder-only AR | Flow Matching / Diffusion / ODE / 多头动作输出 |
| 独占 GPU | Orin 上同时跑 ViT + LLM + Action Head + 语音 + 运动策略 |
| 服务端部署，起停成本低 | 机器人冷启动要秒级 ready |
| 内存和带宽充足 | LPDDR5 总共 204.8 GB/s，3B 模型单步搬 3.28 GB 就能打满 |
| Speculative decoding 靠多候选并行 | batch=1 场景并行度本来就低，收益很弱 |

**每一条都是相反的**。所以即使 vLLM 在 aarch64 上能编出来（目前官方没有 aarch64 wheel，要用 dustynv/vllm 社区镜像），在机器人部署场景里也是 90% 核心功能用不上、真正需求没被覆盖。

**结论**：**端侧需要一个和 vLLM 目标不同、但功能对标的 runtime —— `batch=1, model_set>1`、低延迟、能吃非 AR 输出、把 PyTorch demo 拉到生产级**。这个东西现在不存在。

> **轴对比**：vLLM 优化的是「一个模型，多请求」（`batch>1, model_set=1`）；端侧机器人需要的是「多个模型，每个单请求」（`batch=1, model_set>1`）。PagedAttention、continuous batching、跨请求 KV 共享都是前者的直接推论，把轴一翻，整个调度器就得反过来。

这是整篇文章的立论句：**端侧不缺编译器，缺的是一个 `batch=1, model_set>1` 版的 vLLM**。

### 四、具身 VLA 让这个缺口无法再拖

如果端侧只是跑分类检测，这个缺口可以再拖几年。但 2024 年起具身智能把事情推到了临界点：

1. **模型参数量跃升**：VLA 从 0.1B → 1B → 3B → 7B，一年一个数量级
2. **结构非标**：M-RoPE、dual-track attention、MoE expert、Flow Matching action head，每家一套
3. **多模型共存**：一台 Orin 同时跑 VLA（2Hz）+ 语音 ASR/TTS（实时）+ 运动策略（100Hz+）
4. **硬实时约束**：运动控制 10ms 级 deadline，一次 GC / page fault 就是摔倒
5. **迭代速度**：研究院每月新架构，产线要稳定交付

这五件事合在一起砸到 Orin 上，原来「每家公司自己用 Python + PyTorch 捞一遍」的方式直接顶不住。**具身 VLA 就是把「端侧缺一层 `batch=1, model_set>1` vLLM」这个问题从「可以拖」变成「必须现在解」的 forcing function**。

### 五、来自 Orin 的四条实战证据

上面这套判断不是白板推演，而是过去半年在 Jetson Orin AGX 上做了一堆实测之后收敛出来的。这里列出四条**反直觉、只有动手跑过才会看到**的证据。

### 证据 1：Wall-X 不是「深度自定义 CUDA」项目

拿来做端到端验证的模型是 Wall-X（Qwen2.5-VL 基座 + MoE expert0/expert1 + Flow Matching Action Head）。直觉上一个具身 VLA 会有一大堆自定义 CUDA 算子，源码级别扒完的结论是：

- 自定义算子只集中在三处：MoE permute/unpermute、M-RoPE、视觉 window/index
- 主干仍是标准 PyTorch + Transformers：文本走 SDPA，视觉走 FlashAttention 2
- 动作生成走 Flow Matching + ODE 积分，不是 AR decode

**推论**：不需要把 Wall-X 整体重写成自定义 runtime，但**必须接管 Action Head 这条非标准推理链路**。这正是 Track 1 研发轨要解决的 —— 让新架构的”非标部分”能被 Triton / FlashInfer 随手接住。

### 证据 2：TRT-LLM vs llama.cpp，框架差异 < 精度差异

在 Orin 64GB 上跑了 Qwen2.5-1.5B / 7B 全精度矩阵对比：

- Orin LPDDR5 总带宽 204.8 GB/s，1.5B 单跑 82 tok/s，3B 单跑 39 tok/s —— **内存带宽是绝对瓶颈**
- **框架差异 < 量化精度差异**：同一模型换 Q4_K_M → FP16 的落差，远大于换 llama.cpp → TRT-LLM
- **3~5B 交叉点**：小于这个规模 llama.cpp 足够用；大于之后 TRT-LLM 才真正拉开差距

**推论**：端侧选型逻辑是「**先选量化精度，再选框架**」，与云端「先服务化再调量化」的次序相反。

> 详见：《AGX Orin 端侧 LLM 推理引擎实测：TensorRT-LLM vs llama.cpp》

### 证据 3：多模型共栖不是「带宽 1:1 平分」

最反直觉的一次实测。把 Qwen 1.5B Q4_K_M（语音）+ 3B Q8_0（VLA）扔在同一台 Orin 上共跑：

| 组别 | 配置 | 结果 |
| --- | --- | --- |
| G2 | 3B 单跑 | 39.27 tok/s |
| G4 | 3B + 3B 同跑 | 总吞吐 34.58 tok/s（只掉 12%），但单进程腰斩到 17 tok/s，TTFT 涨 4 倍到 7.4 秒 |
| — | GPU 利用率 | 99%@1298MHz，RAM 仅 9.6 / 62.8 GB |

**真正机制**：3B 单步搬 3.28 GB 权重，1.5B 单步搬 980 MB —— 3B 抢走 **3.35 倍**的带宽时间片。系统总吞吐只掉 12%，但**单进程 TTFT 被显著劣化**。

**推论**：端侧多模型调度需要一个**带宽感知**的调度器 —— 按”单步 DRAM 搬运量”分配时间片。这是 vLLM continuous batching 哲学搬不过来的地方，也是 batch=1 版 vLLM 必须内建的能力。

> 详见：《AGX Orin 端侧多模型共栖推理实测：语音模型 + VLA 模型同时跑会发生什么》

### 证据 4：FlashInfer「官方支持 sm87」≠「能装进主栈」

FlashInfer 是云端 attention 库的事实标准。装进 Wall-X 的 venv（PyTorch 2.5 / CUDA 12.6）：

- `pip install flashinfer-python` 直接拉 torch 2.11 + CUDA 13.x —— 与主栈不兼容
- 必须 `--no-deps` 隔离安装到 `/tmp`，再小心剔除被覆盖的 numpy 2.x
- 装完能 `import`，`show-config` 能认出 sm87 —— 但这只是”隔离试用”

**推论**：**端侧的开源生态是”能编过，但整合成本极高”**。这不是技术问题，是云端开源社区默认 x86_64 + 最新 CUDA 的惯性。要让端侧真正用上 FlashInfer / CUTLASS，必须有人做系统性的”端侧 backport + 依赖解耦” —— 这正是端侧开源项目要承担的基础设施义务。

> 详见：《FlashInfer on Orin：实测记录》

### 四条证据汇总

| 证据 | 证明了什么 | 对解法的影响 |
| --- | --- | --- |
| 1 · Wall-X 主干是标准的 | 不需要整体重写，但必须接管非标链路 | Track 1 研发轨 |
| 2 · 精度 > 框架 | 量化是第一优先级 | 编译器层必须自带量化 pass |
| 3 · 带宽按单步搬运加权 | 云端调度器搬过来不能用 | batch=1 runtime 要带宽感知 |
| 4 · FlashInfer 整合代价 | 开源生态默认不端侧友好 | 需要端侧 backport |

### 六、回到 Wall-X 的部署拓扑

回到开头的 Wall-X 案例。为了让它在 Orin 上跑起来，最终部署拓扑是：

```text
┌──────────────────────────────────────────┐
           │       Jetson Orin AGX (30W / 64GB)       │
           │                                          │
  Camera → │  ┌──────────┐  ┌─────────────────────┐  │
    x3     │  │ SigLIP   │  │ Qwen2.5-VL backbone │  │
           │  │ ViT      │→ │ + MoE (expert0/1)   │ → Flow Matching
           │  │ pure TRT │  │ TRT-LLM + 手写算子  │   Action Head
           │  └──────────┘  │ (~1000 行 C++)      │   (ODE 积分)
           │                └─────────────────────┘  │
           │       ↑                    ↑            │
           │   Python glue (2Hz, 10~20ms 开销)       │
           └──────────────────────────────────────────┘
```

**算子分布**：

- **A 类 ~70%**：TRT-LLM 原生（matmul / LayerNorm / softmax / silu / standard attention）
- **B 类**：workaround（M-RoPE 拆成标准 RoPE + transpose、GQA 特殊 shape、masked_scatter 改 where）
- **C 类 ~1000 行**：手写 plugin（MoE permute/unpermute、M-RoPE 融合、Action Head、权重 remap）
- **D 类**：完全跳出 TRT-LLM（SigLIP ViT 独立 TRT engine；Flow Matching ODE 积分在 Python 调度层）

**Wall-clock 分布**：ViT + LLM 的 C++/CUDA 占 ~85%，Python glue 共 ~10~20ms。

**关键观察**：

1. TRT-LLM 黑盒跑得快，但新架构来一遍要重写 C 类算子，每次 ~1000 行成本
2. Python 不是瓶颈，2Hz VLA 不需要 C++ 化（但 100Hz+ 运动策略必须）——单次前向预算 500ms，Python glue 占比 ~2~4%，反而给 `ModelSet` 调度器留出了充足的时间窗去穿插 ASR 与运动策略，**异构速率共栖的核心矛盾不在语言，而在调度**
3. 真正要投入的不是”重写”，而是**让下次重写的成本 → 0**
4. Flow Matching / Diffusion 这类非 AR 输出注定跳出 TRT-LLM 抽象，而下一代 VLA（GR00T / π0 / Octo 变种）几乎都在 AR decode 之外做事 —— **自定义 runtime 不是选项**

### 七、解法：三层栈 × 应用层三轨

基于「Orin 编译器 / 算子层已齐、缺的是 `batch=1, model_set>1` runtime」的判断，架构收敛成这张图：

```text
┌──────────────────────────────────────────────┐
│ 应用层：三轨并行（研发轨 / 生产轨 / 算子轨） │
├──────────────────────────────────────────────┤
│ 编译器层：TVM Relax / torch.compile / TRT-LLM│
├──────────────────────────────────────────────┤
│ 算子层：Triton / CUTLASS / FlashInfer        │
├──────────────────────────────────────────────┤
│ 硬件层：Jetson Orin（CUDA / TensorRT 底座）  │
└──────────────────────────────────────────────┘
```

四层的关系是**自下而上已有、自上而下需要补**：

### 7.1 硬件层：Jetson Orin（已经有了）

CUDA / TensorRT 原生可用，sm87 Ampere-mobile，64GB LPDDR5 统一内存 204.8 GB/s。硬件底座不再是瓶颈。Jetson Thor（Blackwell 架构，带宽与算力较 Orin 再翻一倍）在 2025 年已经进入市场——我手头暂时没有 Thor 实机，不做实测背书，但从架构延续性看（同样 aarch64 + 统一内存 + 官方 CUDA / TensorRT 栈），本文讨论的 `batch=1, model_set>1` runtime 在设计层面应当能直接平移，只有 kernel 需要按新 SM 重调 auto-tune。换句话说：**下兼容 Orin，上兼容 Thor**。

### 7.2 算子层：Triton / CUTLASS / FlashInfer（能用但要 backport）

这三个库在 Orin 上都能跑，但都有”不端侧友好”的整合代价：

- **Triton** 作为研发轨的 kernel 语言，成熟度足够
- **CUTLASS** 作为生产轨写 plugin 时的 GEMM 模板，可用
- **FlashInfer** 要 `--no-deps` 隔离安装，需要端侧友好的 fork 或者 backport

算子层的核心任务是沉淀 **5 个可复用 fusion**（RMSNorm+QKV、FlashAttention 端侧变体、SwiGLU、MoE gate、M-RoPE），Triton + CUTLASS 双实现共享一套 numerical test。

### 7.3 编译器层：TVM Relax / torch.compile / TRT-LLM（三栈并存、可互切）

三个编译器栈在 Orin 上都跑通了，各自有强项：

| 编译器栈 | 强项 | 弱点 |
| --- | --- | --- |
| torch.compile + Inductor | 新模型 day-1 跑通；Python 友好 | 性能上限 ~70% TRT-LLM；产线部署格式不够稳 |
| TensorRT-LLM | 冻结模型极限性能；Jetson 分支成熟 | 黑盒；新算子要自己写 plugin；版本碎片 |
| TVM Relax | 自己能改 pass；可跨硬件迁移；量化 pass 可深度定制 | 端侧后端需要持续维护；生态比前两个小 |

**关键设计原则**：**三栈必须可互切**。今天 TRT-LLM 不支持新算子，能无缝退回 TVM Relax + Triton 接一条通路，而不是等半年官方 release。TVM Relax ↔ TensorRT 子图互操作已经验证可跑（TRT 擅长的子图交给 TRT，其他交给 Relax）。

### 7.4 应用层：三轨并行

| 轨道 | 技术栈组合 | 定位 | 性能目标 |
| --- | --- | --- | --- |
| Track 1 · 研发轨 | torch.compile + Triton + FlashInfer | 新架构 day-1 跑通，24~72 小时验证 | ≥70% 生产轨性能 |
| Track 2 · 生产轨 | TensorRT-LLM + CUTLASS fusion | 冻结模型极限优化 | 相对原始 +20~40% |
| Track 3 · 算子轨 | 5 个可复用 fusion（Triton + CUTLASS 双实现） | 跨模型复利资产 | 被 Track 1⁄2 共同调用 |

三轨并行而不是串行替代：

- 研究院出新模型 → Track 1 先跑通
- 产线准备上线 → Track 2 榨性能
- 同一个优化反复出现 → Track 3 沉淀成库

**Track 3 是护城河**：每上线一个新架构，5 个 fusion 就被复用一次，积累呈复利。

### 7.5 三轨汇合点：端侧 `batch=1, model_set>1` runtime

三轨在应用层向下汇合到**同一个 `batch=1, model_set>1` runtime**（暂称 edge-infer）。核心抽象是 **`ModelSet`**——一个容器，持有 N 个已编译好的模型 artifact，共享内存、共享调度器：

- **核心抽象 `ModelSet`**：一台 Orin 上 VLA + ASR + TTS + 运动策略都是 `ModelSet` 里的成员，而不是各自起一个独立 engine
- **加载入口**：PyTorch ckpt / HuggingFace → 通过三个编译器栈之一产出可执行 artifact，统一注册进 `ModelSet`
- **调度核心**：带宽感知的跨模型调度器——调度单元是「某个模型的一次前向」，按单步 DRAM 搬运量分时间片，而不是按 batch 数量或 token 数
- **输出灵活**：AR decode / Flow Matching / Diffusion / ODE 积分 / 多头 action chunk 都是「某个模型的一次前向」的类型参数
- **低延迟**：每个模型 batch=1 单请求路径，目标 50ms 端到端
- **backend 可复用**：attention 层（FA / FlashInfer / Triton）可以直接借 vLLM 的 backend 抽象——要重写的只是调度器和内存管理器
- **服务化**：ROS2 / gRPC / zero-copy buffer 接入
- **可观测**：trace / profiling / latency 分布 / drop-rate 开箱即用

这就是”端侧 vLLM”的具体形态 —— 不是 vLLM 的 aarch64 移植，是在端侧负载下对”PyTorch demo → 生产级推理”这条沟的重新设计。

### 八、为什么是现在

三个信号叠加：

1. **需求侧起量**：具身机器人 2025~2027 是量产窗口，每家都在 Orin / Thor / 国产 SoC 上卡同样的问题
2. **技术侧已就绪**：Triton / FlashAttention / TRT-LLM / TVM / CUTLASS / FlashInfer 在 Orin 上都跑通了，搬到端侧不是从零造轮子，是**整合 + 端侧特化**
3. **生态侧真空**：GitHub 上搜 `Jetson + VLA + inference`，能打的开源项目是零。不是没人做，是大家都闷在各自公司里自己写，没有对外输出

**端侧 AI Infra 现在需要的不是更聪明的人，是肯把这层 runtime 造一遍并开源出来的人。** 窗口期大概 18~24 个月，之后要么被大厂做闭源 SDK，要么出现一个”端侧版 vLLM”统一生态。

### 九、我接下来打算做的事

先把范围说清楚：1.0 还没到发版状态，这一节不是开源发布公告，而是一份路线图——我手上正在推进的方向，**不是再做一个 VLA 项目**（VLA 开源项目已经够多，我也不缺落地场景），而是**端侧 batch=1 推理 runtime + 三层栈适配代码**。核心部分做到能复用的程度、且合规允许，会逐步开源。

### 9.1 核心产品：edge-infer（暂名）

一个 `batch=1, model_set>1` 为一等公民的端侧 runtime，具体包括：

- **编译适配**：TVM Relax / torch.compile / TRT-LLM 三个 frontend 都能进，产出统一的 engine bundle
- **算子层**：5 个端侧可复用 fusion（Triton + CUTLASS 双实现）
- **调度核心**：带宽感知多模型调度，按单步 DRAM 搬运量分时间片
- **非 AR 输出支持**：Flow Matching / Diffusion / ODE 积分在 runtime 原生支持
- **ROS2 接入**：zero-copy shared memory，与机器狗 / 机械臂主控自然集成

### 9.2 配套资产

- **Embodied Inference Benchmark**：聚焦具身场景的端侧 LLM / VLA 推理榜单，首发覆盖 Jetson Orin 一家，对齐 MLPerf 命名规范；手机 NPU / 车载 SoC 等其他端侧硬件视开源推进节奏逐步纳入
- **5 个 reference fusion kernel**：端侧友好实现，带 numerical test
- **Case study 白皮书**：3B VLA（Wall-X）在 Orin 上从”跑通”到”跑到极限”的完整路径

### 9.3 明确不做

- ❌ 不做新的 VLA 模型（市场已饱和）
- ❌ 不做 Triton Inference Server 的复刻（厂商已做完）
- ❌ 不做 TensorRT-LLM 的替代品（打不过 NVIDIA，也没必要）
- ❌ 不做 vLLM 的 aarch64 移植（设计假设不匹配，白做）

**定位一句话**：给具身时代的端侧工程师，把从 PyTorch ckpt 到 Orin 上跑起来的「`batch=1, model_set>1` 端侧 runtime」这条路打通；开源与否以合规和成熟度为前提，不赶着抢发。

---

### 十、写在最后

云端用了 5 年，把「PyTorch demo → 生产级 LLM 推理」这条沟填平——中间站着 vLLM / SGLang 这一层。端侧 2026 年这一层还是空的，**而且 vLLM 原样搬过来 90% 的设计假设都用不上**：它的轴是 `batch>1, model_set=1`，端侧机器人要的是 `batch=1, model_set>1`，正好相反。

这不是「等社区慢慢补」能解决的事。具身模型在月度迭代、多模型必须共栖、硬实时不能妥协——每家公司用一套 Python 脚本各自捞一遍，是在给未来攒工程债。**这是基础设施问题，不是算法问题。**

所以过去半年把四条路线都撞了一遍之后，我想清楚了：**端侧差云端的 3 年，不是差时间、不是差人、也不是差硬件——差的就是这一层 `batch=1, model_set>1` 的 runtime。把它造出来并开源，是这个窗口期里最值得做的一件事。**

如果你也在 Orin 上写过那 1000 行 plugin、调过那些 CUDA kernel、等过 TRT-LLM 那些 issue 被 close——欢迎一起把这一层 runtime 补上。

本文观点来自过去半年在 Jetson Orin AGX 上部署 Wall-X VLA（Qwen2.5-VL + MoE + Flow Matching Action Head）的实战经验。核心工作沿**多条并行路线**展开，每条都跑到了能稳定出动作的程度：

- **旁线 · TVM Relax 自管 pass**：当 TRT-LLM 无法覆盖新算子时的退路，与 TensorRT 子图互操作已打通
- **旁线 · torch.compile + Triton**：day-1 快速验证新架构，作为研发轨的前沿阵地
- **异构协作**：把 SigLIP ViT 做成独立 TensorRT engine，与 LLM backbone 分工
