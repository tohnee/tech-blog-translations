> --gpu-memory-utilization

vLLM 会在启动时预先分配可用显存,用于加载模型权重和 KV Cache，剩下显存用于框架本身的上下文运行和其他系统开销（比如**图捕获**时的显存需求）

建议范围0.7～0.9。太低会导致kv cache空间不足；太高时，底层CANN 框架、HCCL在运行时向NPU动态申请显存来存放中间计算结果的空间不足，进而导致 NPU 显存OOM，或者被迫向主机内存发生疯狂的换页交互，CPU和NPU(或GPU)之间通信走的是PCIe，这无疑会带来通信瓶颈。

> --max-num-seqs

服务允许同时处理的**最大**并发请求数。比如该参数设置为32，那现实并发度如果是128的话，大量请求会阻塞。但是其并不保证 32条都能同时执行有效计算，它还会受到 token budget、KV Cache 和显存的共同限制。

> --max-model-len

设定模型支持的最大上下文长度（Prompt + 预测的 Token 总和）。

> --max-num-batched-tokens

在一次调度步骤中，批处理的 Token 总数上限。防止由于单个极长 Prompt 或过多 Prompt 一次性输入导致 OOM。

> --enable-chunked-prefill

启用分块预填充。当收到长 Prompt 时，不会一次性计算所有 Token（这会阻塞其他正在进行 Decode 生成的请求），而是将其切分成多个较小的 Chunk 交替计算。这能显著优化首字延迟（TTFT）和整体调度的平滑度。

**以上三个参数重点说下**

max-model-len和max-num-batched-tokens有着本质的不同。前者的主体是模型，**太短会削弱模型的长文本能力**。如果max-model-len比输入还短，服务会直接拒绝该请求；如果max-model-len比输入+输出短，可能会导致模型输出不完整。后者的主体是调度引擎，**太短会让通信与计算太碎，增加CPU调度开销**，太长会导致OOM。

在没有启用--enable-chunked-prefill的前提下（现在最新的vllm版本是默认启动chunked-prefill），vLLM推理引擎会默认把max-num-batched-tokens 调整到大于等于 max-model-len。（这是在max-num-batched-tokens参数没有显示设置时。如果该参数显示设置了，并且启用了chunked-prefill，还小于max-model-len，推理服务会启动失败。 ）

这三个参数需要根据真实业务场景灵活调整。

> --block-size

PagedAttention 机制中的 KV Cache 块大小。一般默认是16。较大的块在某些特定硬件（如 NPU）上能获得更好的内存连续性和访存性能。

> --no-enable-prefix-caching

明确**禁用**前缀缓存（Automatic Prefix Caching, APC）。前缀缓存通常用于复用相同的 System Prompt

> --speculative-config

{\"method\": \"dspark\", \"num_speculative_tokens\": 5}

配置投机采样。

> --compilation-config

{\"cudagraph_mode\": \"FULL_DECODE_ONLY\", \"cudagraph_capture_sizes\": [6,12,18,24,30,36,42,48,54,60,66,72,78,84,90,96,102,108,114,120,126,132,138,144,150,156,162,168,174,180,186,192]}

配置计算图编译。

> --kv-transfer-config

KV 缓存传输配置，常用于分离式部署架构。

> --host "0.0.0.0"

绑定服务的主机 IP 地址。`0.0.0.0` 表示监听本机上的所有网络接口，使得外部网络可以通过 IP 访问该推理服务。

> --enable-expert-parallel

启用专家并行（Expert Parallelism）。通常用于部署 MoE（混合专家）架构模型，将不同的专家网络分布到不同的计算设备上，以优化显存和计算效率。

> --compilation-config

序列并行配置，比如可以这么写'{"pass_config": {"enable_sp": true, "sp_min_token_num": 8192}}' 即开启序列并行，最小序列并行长度为8192，避免过小的序列也并行带来额外通信开销。
