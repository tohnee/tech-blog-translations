## 引言

如果只看 ZeRO 论文，我们很容易得到下面这样的认识：

- ZeRO-1：切分 Optimizer States；
- ZeRO-2：进一步切分 Gradients；
- ZeRO-3：进一步切分 Parameters；
- 理想情况下，每张 GPU 只需要长期保存全量状态的 (1/N)。

这些结论当然没有问题，但真正打开 DeepSpeed 源码后会发现：**“把参数切成 (N) 份”只是算法起点，如何让切分后的模型仍然像普通 PyTorch 模型一样运行，才是 ZeRO-3 最复杂的地方。**

例如，一次普通的 `Linear.forward()` 背后至少要回答下面这些问题：

1. 一个普通的 `torch.nn.Parameter` 是怎样被 DeepSpeed 接管的？
2. 参数什么时候被切分，哪个 rank 负责哪一段？
3. forward 开始前，Runtime 怎么知道当前 Layer 即将使用哪些参数？
4. 参数什么时候发起 AllGather？
5. AllGather 完成前，Compute Stream 怎么保证不会提前读取参数？
6. backward 中的梯度什么时候算 ready？
7. DeepSpeed 怎样自动触发 ReduceScatter？
8. 为什么不能为每个 Parameter 单独调用一次 NCCL？
9. 参数用完后应该立即释放，还是暂时保留在 GPU 上？
10. `overlap_comm=true` 到底在源码里做了什么？

本文是一篇面向工程实现的源码导读。全文会围绕**一个参数的完整生命周期**展开：

```text
Parameter 初始化
      ↓
DeepSpeed 接管 Parameter
      ↓
Parameter Partition
      ↓
Forward Pre-hook
      ↓
Parameter Fetch / AllGather
      ↓
Parameter AVAILABLE
      ↓
CUDA Compute
      ↓
Release / Re-partition
      ↓
Backward
      ↓
Gradient Hook
      ↓
ReduceScatter
      ↓
Local Gradient Shard
      ↓
Local Optimizer Step
```

从系统视角看，这条链路连接了 PyTorch Module、Autograd、DeepSpeed Runtime、CUDA Stream、NCCL Collective，以及 GPU、NVLink、PCIe 和 RDMA 等底层硬件。

## 1. ZeRO-3 的“自动”究竟自动在哪里？

使用 DeepSpeed 时，用户代码通常仍然非常接近普通 PyTorch：

```python
outputs = model(inputs)
loss = criterion(outputs, labels)

engine.backward(loss)
engine.step()
```

用户并不会手动写 `dist.all_gather()` 或 `dist.reduce_scatter()`，但在 ZeRO-3 下，一次训练过程却会自动完成：

```text
Parameter AllGather
        ↓
Forward Compute
        ↓
Backward Compute
        ↓
Gradient ReduceScatter
        ↓
Optimizer Update
```

这里的“自动”并不是由某一个模块独立完成的，而是下面几种机制共同作用的结果：

```text
Parameter Interception
        +
Module Forward / Backward Hooks
        +
Autograd Gradient Hooks
        +
Parameter Coordinator
        +
Collective Communication
```

可以把它理解为：

> DeepSpeed 在 PyTorch 原有的执行流程旁边，插入了一套“参数生命周期 Runtime”。

这是阅读 ZeRO-3 源码时最重要的视角。ZeRO-3 并不只是静态地切分 Tensor，而是在训练过程中持续决定参数什么时候存在、存在于哪里，以及什么时候可以被释放。

## 2. DeepSpeed 如何接管 `torch.nn.Parameter`？

ZeRO-3 的核心源码之一位于：

```text
deepspeed/runtime/zero/partition_parameters.py
```

这里最值得关注的不是某一个 NCCL API，而是 DeepSpeed 如何改变 Parameter 的语义。

在普通 PyTorch 中，我们通常认为：

```python
weight = torch.nn.Parameter(...)
```

其中 `weight.data` 就是模型真正使用的完整参数。但进入 ZeRO-3 后，一个 Parameter 在逻辑上更接近下面这个分布式对象：

```text
torch.nn.Parameter
│
├── 原始 PyTorch 属性
├── ds_id
├── ds_status
├── ds_shape
├── ds_numel
├── ds_tensor
│
├── partition()
├── all_gather()
└── all_gather_coalesced()
```

DeepSpeed 并没有要求用户把 `nn.Linear` 改写成某种 `DistributedLinear`。上层仍然使用原生 PyTorch Module，但底层 Parameter 已经附带了 ZeRO Runtime 所需的元数据、状态和操作。

这是一种很典型的系统设计：

> **保持上层编程接口不变，在底层替换对象的存储与生命周期语义。**

类似思想也能在 PyTorch FSDP、DTensor 和 Megatron Distributed Optimizer 等系统中看到。

### 2.1 `ds_id`：为什么分布式参数需要唯一编号？

ZeRO 管理的 Parameter 会带有类似 `ds_id` 的分布式标识。它的作用不只是方便 Debug，更重要的是维护 Collective 的一致顺序。

分布式通信有一个非常重要的前提：**所有 rank 必须以一致的顺序参与同一组 Collective。**

假设 rank 0 认为参数顺序是：

```text
[A, B, C]
```

而 rank 1 认为参数顺序是：

```text
[B, A, C]
```

即使这些 Tensor 的形状恰好相同，也可能出现非常隐蔽的数据错位。DeepSpeed 因此会在参数聚合路径中维护一致的参数顺序，源码中可以看到基于 `ds_id` 的排序和管理逻辑。

从工程角度看，这反映出一个很容易被忽略的问题：

> 分布式系统的 Correctness 不只是“调用了相同 API”，还要求所有 rank 对 Collective Sequence 有完全一致的理解。

### 2.2 Parameter 不是一个 Tensor，而是一个状态机

理解 ZeRO-3 的一个关键突破，是不要再把 Parameter 简单地看成“一个 Tensor”。更准确地说，它是一个**有状态的分布式对象**。

DeepSpeed 中存在类似 `ZeroParamStatus` 的状态，用来描述一个 Parameter 当前是否已经 Materialize。可以将它抽象为：

```text
AllGather
NOT_AVAILABLE ────────────→ INFLIGHT
                                  │
                                  │ Communication Complete
                                  ↓
                              AVAILABLE
                                  │
                                  │ Partition / Release
                                  ↓
                            NOT_AVAILABLE
```

- `NOT_AVAILABLE`：当前 rank 上只有自己的 Shard，没有可直接供 Module 使用的完整参数。
- `INFLIGHT`：参数正在异步获取，例如 NCCL AllGather 已经提交，但通信尚未完成。
- `AVAILABLE`：完整参数已经 Materialize，可以安全参与当前 Module 的计算。

这个状态机解决的是异步 Runtime 中的 Correctness 问题：

```text
Communication Stream:
AllGather(W)
████████████

Compute Stream:
          GEMM(W)
          █████████████
```

如果没有 `INFLIGHT`、`AVAILABLE` 等状态及其对应的依赖管理，Compute Stream 就可能在参数准备完成前提前访问它。

因此，`ds_status` 并不只是一个方便打印的状态变量，而是 ZeRO Parameter Runtime 的核心同步语义之一。

## 3. 参数如何完成确定性切分？

假设一个参数为：

```text
W = [w0 w1 w2 w3 w4 w5 w6 w7]
```

Data Parallel World Size 为 4，最简单的逻辑切分结果是：

```text
rank 0 → [w0 w1]
rank 1 → [w2 w3]
rank 2 → [w4 w5]
rank 3 → [w6 w7]
```

实际工程中还要继续处理：

- Tensor 对齐与 Padding；
- DType 与 Process Group；
- Parameter Group；
- CPU / NVMe Offload；
- Contiguous Buffer；
- Quantized Communication。

这也是 `partition_parameters.py` 的实现远比论文中一句 “partition parameters across data parallel ranks” 复杂的原因。

ZeRO 的一个重要原则是：**参数的 Ownership 在初始化后是确定的。**

并不是每次 forward 都由某个中心 rank 动态决定参数如何分配，而是所有 rank 根据下面这些信息独立计算出自己负责的 Shard：

```text
World Size
Rank
Parameter Ordering
Partition Size
Process Group
```

这种 Deterministic Partition 不需要额外的中心调度，同时也能保证每个 rank 对参数归属形成一致理解。

## 4. Forward：真正实现自动 AllGather 的是 Hook

接下来进入最关键的问题：

> DeepSpeed 怎么知道“某个 Layer 马上要使用自己的参数了”？

答案是 **PyTorch Module Hook**。

相关核心文件包括：

```text
deepspeed/runtime/zero/parameter_offload.py
deepspeed/runtime/zero/partitioned_param_coordinator.py
```

从调用链看，可以抽象为：

```text
Module.__call__()
      ↓
forward_pre_hook
      ↓
DeepSpeed Pre-forward Hook
      ↓
pre_sub_module_forward_function()
      ↓
param_coordinator.fetch_sub_module()
      ↓
AllGather Required Parameters
      ↓
Module.forward()
```

也就是说，在真正进入 `Linear.forward()` 之前，DeepSpeed 已经获得了一次检查机会：

```text
这个 Module 需要哪些 Parameter？
这些 Parameter 当前 AVAILABLE 吗？
如果不可用，是否需要发起 AllGather？
```

用户虽然只写了：

```python
x = self.fc1(x)
```

但 Runtime 实际执行的逻辑更接近下面的伪代码：

```python
def before_forward(module):
    params = params_needed_by(module)

    for param in params:
        if param.status == NOT_AVAILABLE:
            fetch(param)

    wait_until_ready(params)

module.forward(...)
```

这就是 ZeRO-3 对上层透明的关键之一。

### 4.1 一个 Linear Forward 到底发生了什么？

考虑下面这个简单模型：

```python
class Net(nn.Module):
    def __init__(self):
        super().__init__()
        self.fc1 = nn.Linear(4096, 4096)
        self.fc2 = nn.Linear(4096, 4096)

    def forward(self, x):
        x = self.fc1(x)
        return self.fc2(x)
```

假设 `fc1.weight` 当前处于 `NOT_AVAILABLE` 状态，每张 GPU 只持有自己的 Shard。当执行 `self.fc1(x)` 时，大致会经历：

```text
PyTorch Module.__call__
        ↓
forward_pre_hook(fc1)
        ↓
DeepSpeed pre_sub_module_forward_function
        ↓
PartitionedParameterCoordinator.fetch_sub_module(fc1)
        ↓
检查 fc1.weight / bias 状态
        ↓
发起 AllGather
        ↓
NOT_AVAILABLE → INFLIGHT
        ↓
NCCL Communication
        ↓
INFLIGHT → AVAILABLE
        ↓
fc1.forward()
        ↓
GEMM
```

如果 forward 结束后 Runtime 判断该参数近期不会再被使用，它还会继续执行：

```text
AVAILABLE
   ↓
Release / Partition
   ↓
NOT_AVAILABLE
```

所以，ZeRO-3 并不是“GPU 在任何时刻都只有 $1/N$ 参数”。更准确的说法是：

> **静态、持久的参数存储是 Sharded 的，计算所需参数会在使用前按需临时 Materialize。**

这也是 ZeRO-3 可以继续使用普通 GEMM Kernel 的原因。矩阵乘法 Kernel 并不知道模型启用了 ZeRO，它看到的仍然是一个完整、可访问的 `weight`。分布式复杂性被 Runtime 隐藏在了计算之前。

## 5. `PartitionedParameterCoordinator`：ZeRO-3 Runtime 的大脑

如果只把 ZeRO-3 理解为“forward 前执行 AllGather”，仍然会低估它的工程复杂度。Runtime 真正需要决定的是：

```text
Gather 哪些参数？
什么时候 Gather？
一次 Gather 多少？
什么时候释放？
能否提前 Prefetch 下一层参数？
参数很快还会再用，是否应该暂时保留？
当前 GPU 已经有多少 Live Parameters？
```

`partitioned_param_coordinator.py` 负责了大量这类 Runtime 决策，可以将其抽象为：

```text
Module Execution
                      ↓
        ┌────────────────────────┐
        │ Parameter Coordinator  │
        └───────────┬────────────┘
                    │
          ┌─────────┼─────────┐
          ↓         ↓         ↓
        Fetch    Prefetch   Release
          ↓         ↓         ↓
      AllGather  AllGather  Partition
```

因此，我更倾向于把它称为 **ZeRO-3 Parameter Scheduler**，而不是简单的“参数通信模块”。

### 5.1 Forward 结束后，为什么不能立即释放参数？

一个参数刚用完时，最直接的策略似乎是：

```text
用完 → 立即 Partition → 释放完整参数
```

但如果它很快又会被使用，就会出现：

```text
Release
   ↓
经过几个 Op
   ↓
重新 AllGather
```

这反而引入了额外通信。因此 Runtime 需要考虑 Parameter 的 Reuse Distance：

- Reuse Distance 很短：继续保留 `AVAILABLE` 可能更划算；
- Reuse Distance 很远：Release / Partition 更有利于降低显存占用。

Stage 3 中出现的 `max_reuse_distance`、`max_live_parameters` 和 `param_persistence_threshold` 等参数，本质上就是对这类调度策略的暴露。

### 5.2 把 ZeRO-3 看成一个分布式参数 Cache

到这里可以得到一个比“参数切分”更接近源码的理解：

> ZeRO-3 很像一个 Distributed Parameter Cache。

```text
GPU Memory
              ┌────────────────┐
              │ Param A FULL   │
              │ Param B FULL   │
              │ Param C Shard  │
              └────────────────┘
                    ↑
        Fetch / Keep / Release
                    ↑
            Parameter Coordinator
```

如果启用了 CPU 或 NVMe Offload，这种层次会更加明显：

```text
NVMe
  ↕
CPU Memory
  ↕
GPU Local Shard
  ↕
Temporary Full Parameter
  ↓
CUDA Kernel
```

于是一个参数拥有了类似缓存对象的生命周期：

```text
Fetch → Prefetch → Materialize → Use → Keep / Evict → Offload
```

这已经远远超出了“把 Tensor 平均切成 $N$ 份”。

### 5.3 ZeRO-3 与操作系统虚拟内存的类比

我认为操作系统虚拟内存是一个很有帮助的类比：

| 操作系统 | ZeRO-3 |
| --- | --- |
| Virtual Address Space | Logical Full Model |
| Physical RAM | GPU Memory |
| Page | Parameter / Parameter Shard |
| Page-in | Parameter Fetch / AllGather |
| Eviction | Release / Re-partition |
| Prefetch | Parameter Prefetch |
| Working Set | Live Parameters |
| Page State | ds_status |
| Memory Manager | Parameter Coordinator |
| Disk | CPU / NVMe Offload |

两者当然不是完全等价的系统，但这个类比揭示了 ZeRO-3 的本质：

> ZeRO-3 实际上在做一种 **Parameter Virtualization**。

从用户角度看，`model.parameters()` 仍然代表一个完整模型；从物理存储角度看，每个 rank 只长期保存部分 Parameter。Runtime 负责在正确的时间，把逻辑上的完整 Parameter 映射到当前计算设备。

## 6. 为什么需要 Flatten、Bucket 和 Coalescing？

现代 Transformer 可能包含成千上万个 Parameter。如果简单实现为：

```python
for param in parameters:
    all_gather(param)
```

就会产生大量细碎的 NCCL 调用：

```text
Parameter 0 → NCCL Call
Parameter 1 → NCCL Call
Parameter 2 → NCCL Call
Parameter 3 → NCCL Call
...
```

NCCL Collective 并不是“零开销函数调用”。每次通信都涉及 Launch、Communicator、Stream、Topology、Synchronization 和 Protocol Latency。尤其对于小 Tensor，单次通信很难充分利用链路带宽。

因此 DeepSpeed 会进行 Flatten、Bucket 和 Coalescing：

```text
P0 ─┐
P1 ─┤
P2 ─┼──→ Contiguous Communication Buffer
P3 ─┤
P4 ─┘
                  ↓
              AllGather
```

源码中可以看到 `all_gather_coalesced()`、`reduce_scatter_coalesced()`，以及 `_flatten_dense_tensors`、`_unflatten_dense_tensors` 等相关接口。

### 6.1 Flatten 的价值

Flatten 主要解决三个问题：

1. **降低碎片化 Tensor 的管理开销。** 大量独立 Tensor 会带来 Allocation、Metadata、Communication 和 Optimizer Update 开销。
2. **让 Collective 面向更大的连续 Buffer。** 通信系统通常更擅长处理大块连续内存，而不是大量离散小 Tensor。
3. **方便维护状态映射。** 可以分别构造 FP16 Flat Partition、FP32 Master Partition、Gradient Partition 和 Optimizer States，再维护它们之间的对应关系。

这也是大模型训练框架中非常常见的工程技巧。

### 6.2 Bucket Size 为什么是性能参数？

Stage 3 初始化参数中可以看到：

```text
reduce_bucket_size
prefetch_bucket_size
```

Bucket 太小时：

- 通信可以更早启动，更容易形成 Overlap；
- 但 Collective 次数增加，Launch Overhead 上升，小消息的网络效率也更低。

Bucket 太大时：

- 单次消息更大，更容易获得较高链路吞吐；
- 但必须等待 Bucket 填满，通信启动更晚；
- 临时 Buffer 更大，显存峰值也会增加。

所以：

> Bucket Size 本质上是在 Latency、Bandwidth、Memory Footprint 和 Overlap 之间做权衡。

这类问题往往不会在算法论文中展开，却是工程实现必须处理的核心问题。

## 7. Backward：梯度如何自动完成 ReduceScatter？

Forward 的自动化主要来自 Module Hook；Backward 更有意思，因为梯度生成由 PyTorch Autograd Engine 驱动。

DeepSpeed Stage 3 中存在明确的 Gradient Hook 注册逻辑，例如：

```text
create_reduce_and_remove_grad_hooks()
```

其目标可以概括为：**当某个 Parameter 的 Gradient 被 Autograd 计算出来时，立即通知 ZeRO Runtime。**

```text
Autograd Engine
      ↓
Parameter Gradient Ready
      ↓
Gradient Hook
      ↓
Gradient Bucket
      ↓
ReduceScatter
      ↓
Local Gradient Shard
```

用户不需要遍历所有参数判断 `p.grad` 是否 Ready。PyTorch Autograd 已经提供了“梯度就绪”这个事件，DeepSpeed 只需要把自己的分布式逻辑挂接到该事件上。

### 7.1 为什么 DDP 常用 AllReduce，而 ZeRO 使用 ReduceScatter？

普通 DDP 的目标是让每张 GPU 最终都拥有完整梯度：

```text
rank 0 → Full Reduced Gradient
rank 1 → Full Reduced Gradient
rank 2 → Full Reduced Gradient
rank 3 → Full Reduced Gradient
```

但 ZeRO-2 和 ZeRO-3 本身就不希望每个 rank 长期保留完整 Gradient，因此更合理的是：

```text
ReduceScatter

rank 0 grad ─┐                     rank 0 → Gradient Shard 0
rank 1 grad ─┼── Reduce+Scatter → rank 1 → Gradient Shard 1
rank 2 grad ─┼──────────────────→ rank 2 → Gradient Shard 2
rank 3 grad ─┘                     rank 3 → Gradient Shard 3
```

也就是说，ReduceScatter 将 Reduce 和 Scatter 两个逻辑合并。`stage3.py` 中使用的 `reduce_scatter_coalesced()`，就是 ZeRO Gradient Partition 在 Collective 层的直接映射。

### 7.2 为什么每个 rank 可以独立执行 Optimizer Step？

ReduceScatter 结束后，每个 rank 拥有自己的 Gradient Shard；同时，ZeRO 已经让每张卡持有对应的 Parameter Shard 和 Optimizer State Shard。

以 Adam 为例：

```text
rank 0:
    Parameter Shard 0
    Gradient Shard 0
    m Shard 0
    v Shard 0

rank 1:
    Parameter Shard 1
    Gradient Shard 1
    m Shard 1
    v Shard 1
```

因此 Optimizer Step 可以局部完成：

```text
Local Optimizer States
        +
Local Gradient
        ↓
Update Local Parameter Shard
```

不需要先恢复完整模型再更新，这也是 ZeRO 能显著降低 Optimizer Memory 的根本原因之一。

## 8. `overlap_comm=true` 到底做了什么？

DeepSpeed Stage 3 初始化中有一个很值得关注的设计：

```text
reduce_and_partition_stream
```

源码附近也有明确注释：

```text
streams used for overlapping computation with communication
```

如果通信和计算完全串行，Timeline 更接近：

```text
Communication
████████

        Compute
        █████████████
```

开启 Overlap 后，可以尝试形成：

```text
Compute Stream

Layer 0 GEMM
████████████████

                Layer 1 GEMM
                ████████████████

Communication Stream

        AllGather Layer 1
        ███████████

                         AllGather Layer 2
                         ███████████
```

理想情况下，总耗时更接近：

```text
max(Compute, Communication)
```

而不是简单的 `Compute + Communication`。

但是否真的能形成有效 Overlap，还取决于：

- GPU 是否有足够的并行资源；
- NCCL Kernel 是否与计算 Kernel 竞争 SM；
- PCIe、NVLink 或 NIC 带宽；
- Prefetch 是否足够早；
- Bucket 大小是否合适；
- CUDA Dependency 是否正确。

### 8.1 两个 CUDA Stream 并不代表天然异步安全

假设 Communication Stream 正在执行AllGather(W1)，而 Compute Stream 准备执行 `GEMM(W1)`。如果 Runtime 不维护依赖，Compute Stream 可能在参数 Gather 完成前就开始读取。

因此必须建立 Producer-Consumer Dependency：

```text
Comm Stream              Compute Stream

AllGather(W1)
██████████
        │
        └──── Event ─────→ Wait
                           ↓
                           GEMM(W1)
                           ███████████
```

所以 Overlap 的真正实现不是“创建两个 Stream”，而是：

> **创建多个 Stream，并精确管理跨 Stream 的数据依赖。**

### 8.2 Prefetch 为什么重要？

最朴素的 ZeRO-3 实现可能是：

```text
AllGather W0 → Wait → Compute L0
AllGather W1 → Wait → Compute L1
```

对应 Timeline：

```text
AG W0   GEMM0     AG W1    GEMM1
████    ███████   ████     ███████
```

GPU 中间存在明显 Bubble。更好的策略是在 Layer 0 计算期间，提前 Fetch Layer 1 的参数：

```text
AG W0
  ↓
GEMM0
██████████████
      ↘
       AG W1
       ███████
             ↓
             GEMM1
```

这样 Layer 1 开始时，`W1` 已经 `AVAILABLE`，或者至少接近完成。这就是 Prefetch。

Stage 3 直接暴露 `prefetch_bucket_size`，正是因为预取量会同时影响 Overlap、Memory Pressure 和 Network Efficiency。

### 8.3 为什么不能无限提前 Prefetch？

如果一次性 Gather 后续所有参数，就会重新接近完整模型的显存占用，直接破坏 ZeRO-3 的目标。

因此 Runtime 必须限制当前 Live Parameters，这也是 `max_live_parameters` 等参数存在的直观原因。

Parameter Coordinator 实际上一直在两个目标之间权衡：

```text
尽可能提前通信
        vs
尽可能降低显存峰值
```

这已经是一个典型的资源调度问题。

## 9. ZeRO-3 Runtime 本质上维护了一个异步执行 DAG

如果只看 Python 代码：

```python
x = layer0(x)
x = layer1(x)
x = layer2(x)
```

执行过程似乎完全串行。但 ZeRO Runtime 实际面对的是：

```text
AG(W0)
   ↓
Compute(L0)
   ├────────────→ Release(W0)
   │
   └────────────→ AG(W1)
                       ↓
                  Compute(L1)
                       ├────→ Release(W1)
                       └────→ AG(W2)
```

Backward 又会形成另一条链路：

```text
Compute Grad L2
      ↓
Gradient Ready
      ↓
ReduceScatter G2
        ↘
          Overlap with Compute Grad L1
```

所以 ZeRO-3 真正执行的是：

> **Compute、Communication 和 Memory Lifecycle 共同构成的异步 DAG。**

这也是理解 DeepSpeed 性能问题的核心视角。

## 10. 如何把源码映射到 Nsys Timeline？

理解前面的 Runtime 后，再看 Nsight Systems Timeline，关注点会完全不同。

假设看到：

```text
CUDA Stream 7:
ncclAllGather
██████████

CUDA Stream 0:
          GEMM
          ███████████████

CUDA Stream 7:
                ncclAllGather
                █████████
```

以前可能只能得出“这里 NCCL 很多”。现在则可以继续追问：

1. 这个 AllGather 对应哪个 Module？
2. 它是当前层的 Parameter Fetch，还是下一层的 Prefetch？
3. 为什么在这个时间点启动？
4. Parameter Coordinator 为什么没有更早 Fetch？
5. Bucket 是否过大，导致通信启动变晚？
6. 通信本身是否没有跑满链路带宽？
7. 当前 GEMM 是否足够长，能够覆盖通信？

这时 Nsys 分析才真正进入 Runtime 层。

### 10.1 常见 Bubble 应该怎样定位？

例如下面这段 Timeline：

```text
Comm:
AllGather W
████████████

Compute:
            GEMM
            ███████████
```

计算必须等待 Parameter Ready，说明这段通信已经暴露在关键路径上。可能原因包括：

1. Prefetch 太晚；
2. 上一层 Compute 太短，无法覆盖通信；
3. Bucket 设置不合适；
4. 跨节点 AllGather 延迟过高；
5. PCIe、NVLink 或 NIC 带宽不足；
6. CPU Runtime 没有及时提交 NCCL；
7. CUDA Stream Synchronization 过多。

更合理的分析顺序是：

```text
先判断 Bubble 在等待什么
        ↓
是否属于 Parameter Dependency？
        ↓
为什么 Parameter 没有 Ready？
        ↓
是通信启动太晚，还是通信执行太慢？
```

这比只看一个 `GPU Util = 70%` 有意义得多。

## 总结

在 DeepSpeed ZeRO-3 中，一个 iteration 的核心通信过程可以概括为：

forward 阶段按需通过 AllGather 恢复当前计算所需的完整参数，backward 阶段在计算梯度的同时通过 ReduceScatter 将梯度归约并切分到各个 rank，optimizer step 则主要使用本地持有的 parameter shard、gradient shard 和 optimizer state shard 完成本地更新，因此参数更新本身通常不需要重新聚合完整模型。

不过，实际执行比“forward 用 AllGather、backward 用 ReduceScatter、step 无通信”更复杂：ZeRO-3 在 forward 结束后可能释放完整参数，因此 backward 在计算 `dX` 等需要权重的梯度时，可能再次对相关参数执行 AllGather；为了隐藏这部分通信，Runtime 会在当前层计算时提前 prefetch 后续即将使用的参数，使参数传输与计算尽可能重叠。

对于梯度通信，DeepSpeed 并不是某个参数的梯度一 ready 就立即单独发起 ReduceScatter，而是利用 Autograd hook 将已经 ready 的梯度加入通信 bucket，当 bucket 达到触发条件后再发起 ReduceScatter，并用后续层的 backward compute 掩盖前一批梯度通信。

这里 bucket size 存在典型权衡：bucket 太大虽然有利于提高 NCCL 带宽利用率，但会导致通信启动过晚、尾部通信暴露增加；bucket 太小则能更早开始通信，却会增加 collective 次数和小消息开销。

因此，ZeRO-3 的性能优化本质上是在同时解决两类 communication hiding 问题：一类是通过 parameter prefetch 隐藏 forward/backward 所需参数的 AllGather，另一类是通过梯度 bucket 和异步 ReduceScatter 隐藏 backward 中的梯度同步。

实际分析 Nsys timeline 时，应重点关注三类暴露通信：forward 等待参数 AllGather、backward 等待参数 AllGather，以及 backward 最后一个 ReduceScatter bucket 因后续已无计算可覆盖而形成的 communication tail。需要注意的是，虽然 optimizer update 本身通常是本地操作，但 `step()` 的高层实现中仍可能包含 gradient norm、overflow 检测或 loss scaling 等辅助性跨 rank 通信，因此更严谨的说法是：ZeRO-3 的 optimizer 参数更新是 shard-local 的，而不是整个 `step()` 绝对没有通信。
