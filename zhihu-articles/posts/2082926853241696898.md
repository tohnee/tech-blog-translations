## 1. sglang/vllm项目介绍

在开源推理引擎中，vLLM和SGLang是两个最受关注的项目，这两个项目已成为全球首选的推理解决方案，谷歌、Meta、Microsoft、字节跳动、阿里巴巴、腾讯等公司的工程师积极参与。

![](https://pic1.zhimg.com/v2-c283d87b0b5738bb187dfe9428a2a2b8_r.jpg)

**共同背景：**两个项目均来自**美国加州大学伯克利分校**。<br>**开源时间：**vLLM 率先于 **2023 年 6 月**发布开源版本；SGLang 大约在六个月后问世。

### 1.1 vLLM 的起源

<br>*论文：Efficient Memory Management for Large Language Model Serving with PagedAttention*

- 追溯到 2023 年发表的一篇以 PagedAttention 算法为核心的论文《基于 PagedAttention 的大型语言模型服务的高效内存管理》。
- 它借鉴了操作系统中的分页和缓存管理思想，实现了细粒度的内存管理，并通过**PagedAttention**机制为高吞吐量请求处理奠定了基础。
- vLLM 还吸收并改进了多项行业技术，例如在论文《Orca：基于 Transformer 的生成模型的分布式服务系统》中首次提出的**Continuous Batching。**
- 项目地址：[vLLM GitHub 仓库](https://github.com/vllm-project/vllm)

### 1.2 SGLang 的起源：

*论文：SGLang: Efficient Execution of Structured Language Model Programs*

- 源自论文《SGLang：结构化语言模型程序的高效执行》，它以**RadixAttention**为核心，它使用基数树 (radix tree) 数据结构实现自动、细粒度的 KV 缓存复用。同时，采用高度优化的后端运行时和高效的 CPU 调度设计，开辟了新的领域。这使得它在多轮对话、RAG 流水线以及任何具有共享前缀的工作负载中速度异常出色。
- RadixAttention 并没有抛弃 PagedAttention，而是对其进行了扩展：它尽可能地保留提示符和生成键值缓存，并尝试在请求之间重用键值缓存；当前缀匹配时，它会减少预填充计算。

| 项目 | 论文 | 核心算法 | 思想来源 |
| --- | --- | --- | --- |
| vLLM（2023.6 开源） | Efficient Memory Management for LLM Serving with PagedAttention | PagedAttention | 借鉴 OS 的分页与虚拟内存管理，实现细粒度 KV Cache 管理；并吸收 Orca 首次提出的 Continuous Batching |
| SGLang（2024.1 首个版本，晚约 6 个月） | SGLang: Efficient Execution of Structured Language Model Programs | RadixAttention | 用基数树（radix tree）实现自动、细粒度的 KV Cache 跨请求复用；不是抛弃 PagedAttention，而是扩展它——前缀匹配命中时减少 prefill 计算 |

- 这个"扩展而非颠覆"的关系很关键：**RadixAttention 保留 paged KV cache 的内存管理底座，在其上加了跨请求前缀复用层，因此在多轮对话、RAG、共享前缀负载中优势较大。**

**vLLM 的优势：**拥有规模更大的开发者社区、更多 GitHub Star 和更丰富的教程指南；兼容性广泛，覆盖大量模型架构与硬件后端；并已在 Amazon、Roblox、Stripe、Meta 等大规模场景中接受验证。<br>此外，vLLM 拥有成熟的 Kubernetes 生态，其官方 Production Stack 与 llm-d 项目由 Red Hat、Google Cloud、IBM、NVIDIA 等共同推动。**与 SGLang 相比，主要差异体现在：**

- **吞吐量稍慢** — 在具有共享前缀工作负载的批量基准测试中，比 SGLang 慢约 29%
- **前缀缓存效率较低** — PagedAttention 缺乏 SGLang 那种基于自动基数树的前缀复用

## **2. sglang/vllm相互借鉴史**

- vLLM 与 SGLang 面对的问题域完全相同——大模型推理的**内存管理、动态调度**、超长上下文与 KV Cache 膨胀——因此基础能力高度趋同且相互借鉴：**Continuous Batching、PagedAttention、Chunked Prefill、Speculative Decoding、PD 分离、CUDA Graphs**，以及 FlashInfer / FlashAttention / DeepGEMM 算子生态，双方均已覆盖。

| 方向 | 技术/思想 | 关键证据 | 结论 |
| --- | --- | --- | --- |
| vLLM → SGLang | 模型层整体移植（PagedAttention + 模型实现 + RMSNorm/SiLU 等基础层） | SGLang 官方移植指南：除 Attention 替换为 RadixAttention 外"几乎完全相同"；早期代码直接 import vllm 内部函数（Issue #391） | SGLang 早期模型执行栈建立在 vLLM 之上；基础算子为生态惯例，不归 vLLM 原创 |
| vLLM → SGLang | Fused MoE Triton kernel | SGLang README 明言 "Adapted from vllm's benchmark_moe.py"；官方博客 "using vLLM as reference and baseline" | kernel 级直接移植 + 再调优 |
| vLLM → SGLang | Piecewise CUDA Graph（torch.compile 切片编译） | vLLM V1（2025.1）首发并默认启用；SGLang PCG（2026）架构同构（FX 切图 + split op + 子图替换） | 编译期切图路线由 vLLM 定义，SGLang 跟进 |

| SGLang → vLLM | Breakable CUDA Graph | vLLM RFC #42770 原话 "adopt the 'breakable CUDA graph' approach from SGL"，原型 #42304（灵感来自 sglang#19102） | vLLM 官方明言的反向借鉴 |
| SGLang → vLLM | Weight Offloading v2（异步权重预取） | vLLM 官方博客（2026.2）原话 "inspired by the offloading approach in SGLang prefill" | vLLM 官方明言受 SGLang 启发 |
| SGLang → vLLM | xgrammar 结构化输出 | 官方集成记录：SGLang 2024.11 → vLLM 2024.12 → TRT-LLM 2025.1 | SGLang 领先一个月，承接其 compressed FSM 基因 |

| SGLang → vLLM | TBO → DBO（双批次重叠） | DynaFlow 论文记载 SGLang TBO 实现耗时 2 个月、1.3K 行代码；vLLM DBO 后至并泛化为 XBO（#30105） | SGLang 工程首发，vLLM 跟进 |
| SGLang → vLLM | Overlap / 零开销调度 | WukLab 研究（2024.9，vLLM 调度开销 >50%）→ SGLang v0.4 零开销调度器（2024.12）→ vLLM V1 重构（2025.1） | 时间线与动机明确；无 vLLM 官方明言，不能将整个 V1 Scheduler 归因于 SGLang |
| SGLang → vLLM | PD 分离工程实现 | sglang工程实现更早，vllm后续跟进 | 工程节奏 SGLang 更早成熟，但"借鉴"证据弱 |
| ➡️ 共同上游 | Continuous Batching | vLLM 率先工程化推广，SGLang 从第一天起作为标配继承 | 非互相借鉴 |
| ➡️ 共同上游 | EPLB / DeepEP / DeepGEMM / MLA 部署方案 | 双方均快速集成（SGLang 普遍更快） | 非互相借鉴 |
| ➡️ 共同上游 | FlashInfer / FlashAttention / LightLLM kernel | 双方默认注意力后端均基于之；LightLLM README 列出两家均使用其 kernel | 非互相借鉴 |
| ➡️ 共同上游 | Mooncake Transfer Engine | 双方均已接入（SGLang 2025.3/9，vLLM 2025.12） | 非互相借鉴，但接入节奏反映两框架差异 |

**之前的核心问题：**

- Static Batching传统调度带来的**严重内部碎片和显存利用率不足**的问题

![](https://picx.zhimg.com/v2-7fac35b89cc6b5b2fd5cdc0d327f70b5_r.jpg)

解决方案：

- **continue batching + paged_attention**：vllm和sgalng都引入了动态调度方案解决

![](https://pic1.zhimg.com/v2-c5148ecb559f35b945ab7e190faac90e_r.jpg)

![](https://picx.zhimg.com/v2-898e9b3b311fbe794417dbdbf3f207cb_r.jpg)

**现在的核心问题：**

- Agent 时代面临的**超长上下文 + kv cache处理问题**

![](https://pica.zhimg.com/v2-dc340e75a967456aac3a1053919e62de_r.jpg)

报告开篇即给出问题陈述：**超长 agent 应用**的快速扩张使**超长上下文处理成为日益重要的模型负载**，而支撑这类负载不仅需要高效的长序列处理，还需要**大规模 KV cache 的持久化存储、复用与传输**。<br>

- 传统对话场景下，上下文短、turn 间复用少，KV cache 是”用完即弃”的临时状态；
- 而 agentic 工作流中，频繁的 tool call 产生大量 prefill 请求，上下文在数十轮工具交互中单调增长，同一前缀的 KV cache 需要跨分钟甚至跨小时存活并被反复命中。
- **KV cache** 由此从”计算副产物”升格为”**需要被管理的基础设施资产**”，报告称之为模型部署的 foundational capability。

这一转变把压力同时施加到三个资源维度上。<br>

- 其一是**计算**：agent 的负载天然 input-heavy——每轮交互要重新摄入大量新上下文（工具返回、文件内容、页面快照），KV cache miss 时的 prefill 计算成为主要开销。
- 其二是**存储**：运行时 KV cache 常驻 HBM，受显存容量约束；为前缀复用而持久化的 persistent KV cache 则受 SSD 与 host 内存容量约束。
- 其三是**通信**：cache 的迁移与加载受 I/O 与互联带宽限制。

### 3.2 sglang和vllm对kv cache的抽象处理<br>

kv cache很重要，两个问题：

- kv cache在推理系统中的本质是什么？
- **SGLang 和 vLLM 分别选择了什么作为 KV Cache 的一等抽象?**

**kv cache在推理系统中的本质是什么？**

```text
户请求
   │
   ▼
Token Prefix
   │
   ▼
已经计算过的 KV
   │
   ├── 能不能识别？
   ├── 能不能复用？
   ├── 能不能长期保存？
   ├── 应该什么时候淘汰？
   ├── 谁可以继续使用？
   ├── 放 GPU / CPU / L3 哪一层？
   └── 下一个请求应该不应该路由过来？
```

**SGLang 和 vLLM 分别选择了什么作为 KV Cache 的一等抽象?**

- SGLang 的 KV Cache一等抽象：**Prefix Node + Radix 前缀树拓扑（topology-centric）**；
- vLLM 的 KV Cache一等抽象： **KV Block（block-centric）**。
- 一等抽象：意味着缓存子系统的全部核心能力——**会话session、驱逐eviction、调度schedule、分层驻留Hierarchy**——都围绕**这个核心对象建模**，而不是外挂的附加功能。

![](https://pic2.zhimg.com/v2-8493a865d107601ba2cc1443f6d8a319_r.jpg)

**SGLang 与 vLLM 的 KV Cache 差异，本质在于一等抽象的选择：**

- SGLang **以 Prefix Node + Radix 前缀拓扑**为一等实体：<br>
- **vLLM 以 content-addressed KV Block 为一等实体**：<br>

这一选择决定了两者能力演化的形态:

| 问题 | Prefix-Topology-Centric (SGLang) | Block-Identity-Centric (vLLM) |
| --- | --- | --- |
| 一等对象 | Radix Node / Prefix | KV Block（由 content hash 标识） |
| 共享如何表示 | 树上的公共路径 | 相同 hash 指向同一 physical block |
| 生命周期挂在哪 | Node（lock / session / priority / residency） | Block（refcount）+ 外部 policy/event |
| 调度如何感知 cache | 直接使用 prefix hit length（LPM 等） | 使用已命中的 computed blocks |
| 分层与分布式 | 拓扑 + 节点 residency（HiCache） | BlockPool + KVConnector + events |
| 典型衍生能力 | Session Radix、LPM、Priority Eviction、Unified Tree、HiCache | BlockPool、Partial Block、Hybrid Coordinator、Connector、Block Events |

- SGLang 的 Session Radix Cache、LPM 调度、Priority Eviction、Unified Radix Tree 与 HiCache 均为同一拓扑上的维度投影，天然形成语义闭环
- vLLM 会自然长出 BlockPool、Partial Block、HybridKVCoordinator、KVConnector、Block Events小结：主对比表

### **3.3 kv cache抽象小结**

<br>从第一性原理出发，详细比较sglang/vllm kv cache抽象：<br>

- **第一个问题：kv cache核心抽象对象：**<br>
- **第二个问题：多请求共享前缀表达，cache之间的关系**<br>
- **第三个问题：KV cache生命周期，谁正在使用（lock/recount）? 谁希望留下（priority）?属于哪个session或者存储在哪里？什么时候淘汰（eviction）? 请求结束怎么办？（retract）**：<br>
- **第四个问题：schedule怎么执行前缀匹配操作？**<br>
- **第五个问题：Cache 不够 GPU 放怎么办？Cache Hierarchy多级存储怎么处理？**<br>
- **第六个问题：Hybrid (混合注意力)怎么处理？Full Attention + mamba + SWA等混合注意力**<br>
- **第七个问题: Agent场景下的KVcache问题怎么处理？**<br>

| 核心维度 | 第一性问题 | SGLang | vLLM | 核心差异 | 判断 |
| --- | --- | --- | --- | --- | --- |
| Cache Identity | 一段 KV 到底由什么定义？ | Prefix / Radix Node；以 prefix 为一等实体 | Content-addressed KV Block；以 block 为一等实体 | SGLang 以 prefix 为一等实体，vLLM 以 block 为一等实体 | 根本差异 |
| Cache Topology | 多个请求之间共享关系如何表达？ | 显式 Radix Tree；prefix topology 被显式物化 | Block Hash + Parent Hash Chain；通过 content-addressed block identity 表达 | SGLang 显式物化 prefix topology；vLLM 物化 block identity | 根本差异 |
| Cache Lifecycle | KV 什么时候保留、锁定、淘汰？ | Node-centric lifecycle：lock / session / priority / eviction | Block-centric lifecycle：refcount / block eviction / events | SGLang 多种生命周期语义围绕同一 Radix node；vLLM 以 block 为核心操作对象 | SGLang 核心优势 |
| Execution Locality | 如何让调度器利用已有 KV？ | Radix match → LPM / locality scheduling；match_prefix() 直接提供 prefix hit length | computed blocks → scheduler；暂无同等成熟 LPM policy | SGLang 可直接将 prefix locality 转换成调度策略 | SGLang 当前明显领先 |
| Hybrid (混合注意力)+ Hierarchy（分层存储） | GPU/CPU/L3 如何组织？ | Unified Radix Tree + TreeComponent + HiCache；Radix topology + residency + HiCache | KV Groups + HybridCoordinator + KVConnector；Block + KVConnector + remote KV | SGLang 在 topology 层统一；vLLM 在 manager/connector 层模块化 | SGLang topology 优势 |
| Distributed / Agent Orchestration（Session / Agent） | session、router、PD、agent 如何管理 KV？ | Radix/session/event/HiCache 组合；Session → Radix Node → KV → eviction / HiCache | Block event/session/connector/control plane 组合；Session metadata → Block/Event → orchestration | SGLang session 生命周期与 prefix topology 耦合更紧；vLLM 更依赖 block metadata、events 与 connector/control plane | SGLang 当前领先 |
| 共同基础能力 | 这些基础能力是否仍能区分两者？ | Prefix cache、partial cache、hybrid、Mamba、SWA、events、remote KV、preemption | 同样具备 | 双方均具备，已不是有效的独占差异 | 双方趋同 |

<br>总结：

- SGLang 的 Engine 内部将 Prefix Topology 显式物化为 Radix Tree，使 Prefix Node 成为 KV 共享、匹配、锁定、Session Reference、Eviction 和部分 Residency 管理共同围绕的生命周期实体；Router 进一步维护 Prefix Locality 的近似视图进行 placement。
- vLLM 则将 Content-addressed KV Block 及其 Parent-hash Lineage 作为 Engine 内的核心 Cache Identity，通过 BlockPool、KV Groups、KV Events 和 KVConnector 向外暴露状态，使 Router / Orchestrator 在 Engine 之外构建 Prefix、Session、Retention 和 Distributed KV 的控制视图。
- 真正的架构差异不是”谁有没有 Prefix Cache”，也不是”谁能支持 Agent”，而是 Prefix Topology 这棵树物化在哪一层：SGLang 住在 Engine 内，直接向 Scheduling / Lifecycle / Routing 供语义；vLLM 住在 Engine 外，由 Event / Connector / Control Plane 组合重建

### 3.4 sglang和vllm 能力对比总结

### <br> 3.4.1 kv cache抽象与数据结构

**SGLang 的核心对象是 Prefix Node，vLLM 的核心对象是 KV Block。**<br>**[sglang]adix_cache.py：**

- **TreeNode**：每个节点持有 children（字典）、parent、key（token id 序列）、value（KV 池索引）、lock_ref（引用计数）、last_access_time。节点本身就是”一个前缀及其 KV 位置”的完整描述。
- **match_prefix**：沿树下降做最长前缀匹配，返回命中长度与最后一个命中节点。共享-分叉关系直接编码在树的拓扑里。
- **_split_node**：当新请求在节点中途分叉时，把节点一分为二——父段留下继续被共享，子段成为分叉。**分裂操作就是”共享-分叉关系”的原生表达**，无需任何额外元数据。
- **RadixCache.evict**：驱逐沿树的叶子进行，lock_ref > 0 的节点（正在被运行中的请求使用）受保护；可选 evictable_size_ / protected_size_ 记账，并由 EvictionStrategy 策略类决定受害者。
- 总结：SGLang 的缓存不是一个容器，而是一棵**可查询、可分裂、可引用计数、可分层扩展的前缀拓扑**。

**【vllm】vllm/vllm/v1/core/：**

- **kv_cache_utils.py**：hash_block_tokens 用链式哈希
- 为每个 block 生成内容指纹。哈希值编码了”这个块的全部祖先”，但**不保存任何显式拓扑**——没有父指针、没有子表。
- **kv_cache_manager.py / get_computed_blocks**：命中判断 = **在 BlockPool 的哈希表里逐块查找**。代码注释明确写着：*“Since incomplete blocks are not eligible for sharing, num_computed_tokens is always a multiple of block_size”*——**不满一个 block 的前缀尾部不参与共享**。
- **block_pool.py**：BlockPool 管理固定大小 block 的分配/回收；新版本已引入 hash_block_size 与 cache_partial_block 参数。
- **kv_cache_coordinator.py + single_type_kv_cache_manager.py**：对混合架构（FullAttention / SlidingWindow / Mamba）分别由专用 manager 管理各自的块池，由 coordinator 协调。
- 小结：vLLM 的缓存是一个**以 block 为单位、以内容为键、以池为生命周期**的分配器；前缀之间”是否共享”**由哈希相等性隐式判定**，“在哪里分叉”这个问题在数据结构中**不可查询**。

<br><br>**Cache Topology：共享关系如何表达？**<br>**原理：** 多个请求共享长前缀时，共享关系是树边，还是 hash 父子？

| 能力 | SGLang | vLLM |
| --- | --- | --- |
| 拓扑 | parent/child、split、subtree 显式 | block hash + parent_block_hash 谱系 |
| 匹配 | match_prefix() 树遍历 → 最长前缀 | hash 查找 + cached block 匹配 |
| 细粒度 / partial | node split | partial block / partial hash |
| CLI | 默认 Radix；--disable-radix-cache | --enable-prefix-caching；--block-size |

### <br>**3.4.2 Cache Lifecycle 多种驱逐策略**

<br>【sglang】radix_cache.py:

- SGLang CLI 支持多种驱逐策略：**--radix-eviction-policy {lru, lfu, slru, priority}**<br>

vLLM 块池按哈希组织，块与块之间无显式共享结构，**传统上只有近似 LRU 的释放序**（V1 APC 释放即回收）。<br>

| 能力 | SGLang | vLLM | 相对优势（表述要稳） |
| --- | --- | --- | --- |
| 驱逐对象 | Radix node / 路径 | Block + free queue | SGLang 驱逐语义贴拓扑 |
| 策略 CLI | --radix-eviction-policy {lru,lfu,slru,priority} | cache manager 内部为主 | SGLang prefix 级 priority 更直接 |
| 共享保护 | lock_ref 护路径 | block refcount / 使用中占用 | 都有；对象不同 |
| Session | --enable-session-radix-cache + session_id + /close_session（soft，非 pin） | session 元数据 / events；Retention RFC/实现演进 | SGLang 已进 Engine 缓存生命周期 |
| 抢占/回收 | 请求私有 KV 可收；共享前缀可留 | preemption + recompute | 拓扑上「共享 vs 私有」更清晰 |

### <br>3.4.3 Execution Locality：调度是否「看见」缓存拓扑？

<br>Prefix Cache 只解决「算的时候能不能复用」。若调度仍是纯 **FCFS（先来先服务）**，可能出现：

- 队列里有一条与当前 GPU 上热前缀 **高度重合** 的请求排在后面；
- 先跑一条 **几乎无共享前缀** 的请求，把热前缀挤冷或打乱局部性。

**Execution Locality** 问的是：**调度器会不会利用「和缓存拓扑的亲和」来排谁先上**。

- SGLang --schedule-policy lpm（longest-prefix-match） 把”与前缀缓存亲和”的请求排前，提高命中率；默认 fcfs；

| 能力 | SGLang | vLLM |
| --- | --- | --- |
| 信号来源 | match_prefix → hit length、组件可用性 | scheduler 可见 cached/computed blocks |
| LPM | --schedule-policy lpm | 无同等成熟的「最长前缀优先」核心策略 CLI |
| 子树局部性 | --schedule-policy dfs-weight | 无完全对应的 Radix-subtree 策略 |
| 与优先级组合 | --enable-priority-scheduling 等 | 有 request priority，与 cache-affinity 组合方式不同 |

- SGLang 把 cache locality 做成一等调度策略（LPM / DFS-weight）；
- vLLM 强在通用调度与 block 状态，不支持上述策略。

## 4. sglang/vllm kv cache不同抽象下演化的能力

### <br>4.1 **SGLang 侧（Prefix-Topology-Centric 下自然长出的能力）**

<br>**Session Radix（Session-aware Radix Cache）**

- **核心问题：**多轮对话 / Agent 场景里，某段前缀可能暂时没人访问，但仍属于一个还活着的会话。纯 LRU 会按「最近是否被用」淘汰，容易把暂停中的会话前缀清掉，导致下一轮全量重算。
- **核心概念**<br>

**LPM（Longest Prefix Match 调度）**

- **核心问题：**等待队列里有的请求已有很长缓存前缀、有的几乎没有。若只按到达顺序（FCFS）调度，可能先跑「冷」请求，浪费本可立刻省掉的 prefill。
- **核心概念：**<br>

**Priority Eviction（优先级驱逐）**

- **核心问题：**不同前缀价值不同：系统提示、长期会话前缀应比一次性查询更难被淘汰。仅靠 LRU/LFU 无法表达「业务优先级」。
- **核心概念**<br>

**Unified Tree（Unified Radix Tree / Unified Radix Cache）**

- **核心问题：**混合模型同时有 FULL 注意力、滑动窗口（SWA）、Mamba/SSM 等，若各用一套 cache 树，会重复实现匹配、加锁、驱逐，且前缀身份不统一。
- **核心概念**<br>

**HiCache（Hierarchical Cache）**

- **核心问题：**GPU 显存有限，命中率受容量限制；需要把冷前缀放到 Host 甚至外部存储，并在需要时拉回，且最好仍挂在同一套前缀语义上。
- **核心概念**<br>

### <br><br>4.2 **vLLM 侧（Block-Identity-Centric 下自然长出的能力）**<br>

**BlockPool**

- **核心问题：**以固定（或可配置）大小的 KV **block** 为资源单位时，需要统一的分配、回收、引用计数和空闲管理，类似操作系统的页框池。
- **核心概念**<br>

**Partial Block（部分块 / 细粒度前缀命中）**

- **核心问题：**若只能「整 block 命中」，共享长度不是 block 整数倍时，尾部要对齐或重算，细粒度前缀复用受限。
- **核心概念**<br>

**Hybrid Coordinator（HybridKVCoordinator / KV groups）**

- **核心问题：**同一模型中 FULL、SWA、Mamba 等对「缓存什么、按什么粒度复用」规则不同，需要协调多套 KV 状态，又避免完全碎片化的重复逻辑。
- **核心概念**<br>

**Connector（KVConnector）**

- **核心问题：**KV 需要在 GPU、CPU、远程存储或 PD 分离的实例之间移动；需要与引擎解耦的「搬运与对接」层。
- **核心概念**<br>

**Block Events**

- **核心问题：**Router、控制面、外部编排需要知道「哪些 KV 被缓存了 / 被删了」，以便做亲和路由、容量规划或 session 编排，而不必侵入引擎内部结构。
- **核心概念**<br>

## <br><br>5. SGLang UnifiedRadixTree vs vLLM HybridKVCacheCoordinator架构对比图

<br>**核心问题：**当 KV Cache 不再只是单一 Full Attention 的 KV，而是包含 Full / SWA / Mamba 等多种异构 State 时，系统应该用什么作为一等抽象来组织kv cache缓存？<br>不同 Attention 类型需要的 State 不同：<br>

| Attention 类型 | 需要的 State | 复用边界 |
| --- | --- | --- |
| Full Attention | 全量 KV | 完整前缀 |
| SWA（Sliding Window Attention） | 窗口 KV | 最近窗口 |
| Mamba / SSM | SSM State | 特定状态点 |

<br> **内存分配需求（allocation needs）**

- Full Attention（全注意力）: 每一层需要为序列里全部 token保留 KV 存储槽位。 长上下文场景，序列越长，占用 KV 空间线性增长；只要 token 存在，对应的 KV 就必须保留。
- Sliding Window Attention（滑动窗口 SWA）: 只保留最近 `sliding_window_size` 个 token的 KV；更早的 token 对应的 KV 可以丢弃 / 失效。 序列变长时，旧 KV 会被淘汰，不需要无限分配存储空间。
- Mamba/SSM ：它根本不是 KV，是状态向量，内存模型、写时复制规则和 Attention 完全不同。

**前缀缓存命中规则（prefix-cache rules）**

- Full Attention：前缀缓存命中的条件：前缀里所有 token 的 KV 都完整存在。只要前缀任意位置 KV 丢失，整条前缀失效。
- Sliding Window Attention：前缀命中条件不一样。只要求窗口内最后 N 个 token 的 KV 有效；窗口外更早的 tokenKV 即使被丢弃，依然可以命中前缀。

核心矛盾：同一条 token 序列，对 Full 和 SWA 来说，「哪些 KV 算有效、能不能命中前缀」的判定标准完全不一样。<br>举个例子：窗口大小 = 1024；序列长度 2048

- Full：想要复用前 2048 前缀，全部 2048 个 token 的 KV 必须都在
- SWA：想要复用前缀，只需要最后 1024 个 tokenKV 存在；前面 0~1023 的 KV 可以丢掉

### 5.1 SGLang UnifiedRadixTree: 一棵树挂多种 State（Topology-Centric）<br>

- [https://mp.weixin.qq.com/s/MgRzOhCdzxPTboAs8m6-iw](https://mp.weixin.qq.com/s/MgRzOhCdzxPTboAs8m6-iw)
- [https://www.lmsys.org/blog/2026-08-11-unified-radix-cache](https://www.lmsys.org/blog/2026-08-11-unified-radix-cache)

UnifiedRadixTree, 是SGLang 2026 年 8 月刚完成的一次大规模重构的直接产物，

- [https://github.com/sgl-project/sglang/issues/20415](https://github.com/sgl-project/sglang/issues/20415)
- 核心思想：**同一条 Prefix tree nodeTopology 上挂载多种 State 作为不同的 TreeComponent。**<br>
- 匹配过程不是简单的哈希查找，而是 Radix Tree Traversal：**沿树找到最长公共前缀，同时对每个 TreeComponent 做组件校验**
- 匹配结果不是单一长度，而是“**最长公共前缀 + 所有组件一致的有效边界**”。

TreeComponent 的三种 State，物理形态完全不同<br>

| 组件 | 物理形态 | 复用语义 |
| --- | --- | --- |
| Full Component | 全量 K/V 张量，随序列长度线性增长 | 前缀命中 = 所有 token 的 KV 都在 |
| SWA Component | 只保留最近 window 的 K/V | 命中只需要最近 window 完整；window 外自动释放 |
| Mamba Component | SSM state（固定大小）+ 卷积 state | 每条序列路径独占一份 state，分支时必须 copy-on-write |

<br>SGLang 选择了"**Prefix tree nodeTopology**为唯一真值"。 <br>

- 前缀结构（树）是唯一的一等状态，Full/SWA/Mamba 的差异被封装为"同一节点上的不同组件视图"。
- 收益：匹配、调度、session、分层、驱逐全部围绕同一结构，跨组件一致性是结构自带的，不需要事后协商。
- 代价：树必须理解每种组件的特殊性（SWA 的窗口对齐、Mamba 的 COW 和 per-path 状态数上限），树本身的复杂度随组件种类增长

## 6. Agent 场景下的 KV Cache<br>

Agent 场景：

- 一个带有持久状态的、可能多次暂停和恢复的、可能分叉的 LLM 交互序列。
- 核心特征：KV Cache 不再是“请求结束即释放”的临时资源，而是需要**跨阶段保留、复用、分层、分支管理**的会话状态，变成了**跨请求、跨时间、跨 Worker 的长期状态。**
- **而 SGLang 和 vLLM 对”这个状态长什么样、住在哪一层”给出了两种根本不同的回答。**

**一个 Agent Session 可能：**

- 执行多个 Turn；
- 调用外部工具并等待数秒甚至数分钟；
- 暂停后继续执行；
- 从同一个历史状态产生多个 Branch；
- 在不同 Worker 之间迁移；
- 将部分状态从 GPU 放到 Host；
- 甚至把状态放到远端 KV Store。

```text
Agent Session
  ├── Turn 1        → 产生 KV
  ├── Tool Call     → 停顿 5s / 30s / 5min
  ├── Turn 2        → 希望复用 KV
  ├── Branch A/B    → 共享历史 + 独立 delta
  └── Resume        → 恢复状态
```

**概念解释：**<br>

- **Turn（一轮交互）：**是 Agent 的一次完整“输入 → 模型生成 → 输出”循环。
- **Tool Call（工具调用与停顿）：**是 Agent 决定调用外部工具的动作。模型生成一个结构化的工具调用请求后，会话暂停，等待工具返回结果。**需停顿，但是不产生kv cache**
- **Branch（分支）：**Branch 指 Agent 从某个共同历史点分叉出多条可能的路径，Branch A 和 Branch B 共享前缀 ，但各自有独立的后续 KV（delta A / delta B）
- **Resume（恢复会话）：**Agent Session 在暂停后重新恢复执行

vLLM 社区对失效模式的量化描述非常精确：[https://github.com/vllm-project/vllm/issues/37003](https://github.com/vllm-project/vllm/issues/37003)<br>

- 一个典型 Agent turn 中超过 90% 的 token 是对上一 turn 前缀的逐字复用（prefix cache 命中），但40–60% 的会话时间处于工具调用的暂停态，此时这些 KV 处于 unreferenced 状态，并发负载下会被其他 agent 的 LRU 驱逐；会话恢复时全量重算一个可增长到 70K–200K token 的上下文

**由此产生四个 KV Cache 系统必须回答的问题：**<br>

| 问题 | 语义 | 对 Cache 系统的要求 |
| --- | --- | --- |
| ① KV 应该在哪个 Worker？ | Session 亲和性与 prefix 感知路由， 相同的session放在同一worker内 | Cache 状态必须可被 Router 感知 |
| ② Session 停顿时怎么办？ | 跨 turn 的 KV 保留与分层卸载 | KV 生命周期必须支持 session 级引用 |
| ③ Agent Branch 怎么办？ | 共享 prefix + 独立 delta 的树形复用 | Cache 拓扑必须支持分支 |
| ④ 能否主动告诉 Cache “保留这个”？ | Passive Cache → Programmable Cache | Cache 系统必须暴露控制接口 |

<br>**问题1： KV 应该在哪个 Worker？**<br>

- **核心问题：**Agent 场景问的是”**这个 Session 的 KV 在哪里**”。路由错 Worker = 全量重新 prefill。所以本质是 *Where is the state?*
- **sglang解决方案**：[https://lmsysorg.mintlify.app/docs/advanced_features/session_radix_cache](https://lmsysorg.mintlify.app/docs/advanced_features/session_radix_cache)<br>

```text
               SGLang
        ┌─────────┴─────────┐
        ▼                   ▼
  Engine/Worker          Router
        │                   │
UnifiedRadixTree    Approximate RadixTree
 （真实 KV 拓扑）     （locality 估计模型）
```

- **Worker 内**：UnifiedRadixTree 是真实 KV 拓扑（v0.5.19 起全模型默认，#35081）。
- **Router 侧**：cache_aware 策略为**每个 worker 维护一棵基于请求历史的近似 radix tree，据此预测各 Worker 的 prefix 命中率并选择目标，按前缀匹配度路由；负载严重不均衡时可退回最短队列等策略。**
- Router 的近似树 ≠ Worker 内的真实树。**SGLang 的特点不是”Router 直接读真实树”，而是 prefix locality 被显式建模为 routing policy 的输入。**
- **vllm解决方案：[https://docs.nvidia.com/dynamo/v-0-9-0/components/backends/v-llm](https://docs.nvidia.com/dynamo/v-0-9-0/components/backends/v-llm)**<br>

```text
tokens → block hash → KVCacheBlock → BlockPool
                │
           KV Events (BlockStored / Removed, parent_block_hash, …)
                │
     External Router / KvIndexer / Prefix·Session Index
                │
              Routing
```

- vLLM Engine 只承诺暴露Block**级事实流**；prefix/session 视图由外部系统构造。且这已是生产现实：
- **NVIDIA Dynamo**：KV Router 消费 vLLM 的 KV events，其 KvIndexer **内部就是一棵 RadixTree**；
- **llm-d**：KVEvents → KV-Block Index → Prefix Index 的两层架构。

<br><br>**问题2： Session 停顿怎么办？**<br>

- **核心问题：**Tool 调用 5 分钟，KV 悬置：一直占 HBM 是浪费；直接驱逐则 Resume 时全量重算；多 Agent 并发下，朴素 LRU 会**优先牺牲暂停中的 session**（它最久未被访问）。真正的问题是：**Paused Session 的 KV 是否仍具有未来价值？**
- **sglang解决方案**：--enable-session-radix-cache<br>

```text
Session → Session Reference → Radix 节点优先级
         → Eviction：unreferenced 先，referenced 后
         → Residency：GPU / Host / L3
```

- Session-aware radix cache（**#27058**，v0.5.17 发布 #29173 配套）：session 可对 prefix 持有 **Session Reference**，语义是”当前无请求执行，但未来可能恢复”——介于 Normal Request Lock（正在用，不可回收）与 Unreferenced（最先驱逐）之间的**软保护**。
- **必须强调**：soft protection ≠ permanent pin。内存极端不足时：Unreferenced → 先驱逐；Referenced → 必要时后驱逐。
- 叠加**HiCache**（--enable-hierarchical-cache，后端 {file, mooncake, hf3fs, nixl, aibrix, eic…}）形成 **Session → Prefix Reference → Eviction Priority → Residency（GPU/Host/L3）** 的完整链条

**核心问题：**

- 传统 cache 只知道”最近用过没有”，不知道这个 prefix 是：长期 Agent session？马上要 resume？高价值 system prompt？即将 branch 的状态？应该下沉 L3 的状态？
