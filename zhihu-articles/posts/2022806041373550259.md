做 LLM Serving，绕不开"调度"二字。但如果把 2022 年到 2025 年这几篇关键论文摊开来看，会发现一条极其清晰的演化主线：**调度粒度在不断变细，而每一次变细，都是在回答上一代方案留下的那个"但是"**。

沿着 ORCA → SARATHI → DiT-Serve → Layered Prefill 这条脉络，重新走一遍这条路。不是论文摘要的堆砌，而是试图把每篇论文放回它诞生的那个具体问题场景里，看看它到底解决了什么，又留下了什么。

### 一、ORCA：打碎 batch 的边界

**论文：** *ORCA: A Distributed Serving System for Transformer-Based Generative Models* (OSDI 2022)

在 ORCA 之前，LLM 推理服务的调度方式和你在食堂排队没什么区别——一批人凑齐了一起进去，等所有人都吃完了，下一批再进。这就是所谓的 **request-level scheduling**：一个 batch 里的所有请求，必须等最长的那个生成完毕，整个 batch 才能释放。

这带来一个直觉上就很荒谬的问题：如果一个 batch 里有一个请求只需要生成 10 个 token，另一个要生成 500 个，那前者生成完之后只能干等着，GPU 上属于它的那份算力白白空转。

ORCA 的核心洞察其实非常朴素——自回归生成本身就是迭代式的，**每生成一个 token 就是一次完整的前向传播**。既然如此，为什么不把调度的决策点从"整个 batch 结束"下移到"每个 iteration 结束"？

这就是 **iteration-level scheduling** 的本质。具体来说：

每一次 iteration（即每一次 forward pass 生成一个 token）结束后，调度器可以做两件事：把已经生成完毕的请求立刻移出 batch，同时把等待队列里的新请求插入 batch。不需要等任何人，走得快的先走，来得新的直接加入。

为了实现这一点，ORCA 引入了一个关键机制叫 **selective batching**。问题在于：不同请求的输入序列长度不同，在 attention 计算时它们的 KV cache 形状各异，没法简单地 stack 成一个张量做矩阵乘。Selective batching 的做法是，对于非 attention 算子（比如 FFN、LayerNorm），所有请求的 token 拼在一起做一次大的 batched 计算；对于 attention 算子，则拆开来分别计算各自的 attention，再拼回去。

![](https://pica.zhimg.com/v2-881a7c1281f135c85cfbed0171ec6c2e_r.jpg)

这个设计后来被 vLLM 等系统发扬光大，变成了大家耳熟能详的 **continuous batching**（也叫 dynamic batching）。本质上是同一件事：把调度粒度从 request 级别细化到 iteration 级别。

ORCA 的影响是深远的——它定义了 LLM serving 的基本范式。在此之后，几乎所有主流推理框架（vLLM、TensorRT-LLM、SGLang）都采用了 continuous batching 作为默认调度策略。

**但是——**

ORCA 有一个它没有解决的问题，或者说在当时还不算严重的问题：**prefill 阶段的阻塞**。

当一个新请求加入 batch 时，它需要先完成 prefill（处理整个输入 prompt），这是一次计算量很大的前向传播——prompt 可能有几千甚至几万个 token。在 prefill 期间，这个请求会独占大量的 GPU 计算资源，导致同一 iteration 内其他正在 decode 的请求被拖慢。更糟的是，decode 请求的每一次 iteration 只处理一个 token，本身耗时很短，但如果和一个大 prefill 挤在同一个 iteration 里，就要等 prefill 做完才能拿到结果。

对 decode 请求来说，这种被迫等待直接体现为 **Time-Between-Token (TBT)** 的抖动——用户看到的就是输出卡了一下。当 prompt 越来越长（long-context 场景），这个问题就从"偶尔卡一下"变成了"经常性的卡顿"。

### 二、SARATHI：把 Prefill 切碎

**论文：** *Taming Throughput-Latency Tradeoff in LLM Inference with Sarathi-Serve* (OSDI 2024)，前身为 arXiv preprint *SARATHI: Efficient LLM Inference by Piggybacking Decodes with Chunked Prefills* (2023)

SARATHI 盯住的就是 ORCA 留下的这个"但是"。

它的核心想法非常直接：既然一个完整的 prefill 太大了会阻塞 decode，那就 **把 prefill 切成小块**，每个 iteration 只做一小块 prefill，剩下的算力用来给 decode 请求跑 token。

这就是 **chunked prefill** 的含义。假设一个新请求的 prompt 有 4096 个 token，chunk size 设为 512，那么这个 prefill 会被拆成 8 个 chunk，分散到 8 个 iteration 中完成。每个 iteration 里，GPU 同时处理一个 512-token 的 prefill chunk 和若干 decode 请求的单 token 生成。

SARATHI 把后者形象地称为 **decode piggybacking**——decode 请求"搭便车"在 prefill chunk 上。

![](https://pic2.zhimg.com/v2-8e57d6cab9298bce5904ed6afdcb6989_r.jpg)

从资源利用的角度看，这个设计解决了两个问题：

第一，**消除了 prefill 对 decode 的阻塞**。因为每个 iteration 的 prefill 工作量被限定为一个 chunk（比如 512 tokens），不管原始 prompt 多长，单次 iteration 的延迟都被 bound 住了。decode 请求的 TBT 不再受 prompt 长度的影响，抖动被大幅抑制。

第二，**提高了 GPU 利用率**。在 ORCA 的方案中，如果一个 iteration 只有 decode 请求，那每个请求只处理一个 token，GPU 的计算单元严重吃不饱（decode 是 memory-bound 的）。Chunked prefill 通过在 decode iteration 中塞入一些 prefill tokens，把这些本来浪费的算力利用起来了。从 roofline model 的角度看，prefill chunk 是 compute-bound 的，decode 是 memory-bound 的，两者混合执行可以同时打满计算单元和内存带宽。

在实现层面，SARATHI 的调度器在每个 iteration 开始前做一次调度决策：从 prefill 队列中取出一个 chunk（或多个短请求的 chunk），与当前所有活跃的 decode 请求组合成一个混合 batch，送入模型执行。调度策略要确保混合 batch 的总计算量不超过延迟预算。

SARATHI 的效果是显著的：在保持 decode 延迟基本不变的前提下，端到端吞吐量可以提升接近 2 倍（原始论文报告最高约 1.91 倍），decode 阶段的吞吐提升更为显著。后续的 Sarathi-Serve 版本将这一方案与 continuous batching 进一步结合，成为了当时最先进的 LLM serving 方案之一。

如果说 ORCA 把调度粒度从 request 级别推进到了 iteration 级别，那 SARATHI 则在 iteration 内部引入了 **chunk 级别的调度**——把 prefill 在 token 维度上切分，与 decode 交错执行。

**但是——**

Chunked prefill 有一个代价，在稠密模型上不算显眼，但在 MoE 模型上会变得尖锐：**每个 chunk 都要完整地穿过模型的所有层**。

一个 4096-token 的 prompt 被切成 8 个 chunk，每个 chunk 都要从第 1 层到最后一层做一次完整的前向传播。也就是说，每一层的权重被加载了 8 次，而不是 1 次。对于稠密模型，层的权重总量是固定的，多加载几次的开销相比于计算本身占比不大。但对于 MoE 模型，每层有几十甚至上百个 expert，每次前向传播只激活其中一部分（比如 top-8）。小 chunk 的问题在于：它激活的 expert 覆盖面很广（token 少但分散），每个 expert 被激活后只处理极少的 token，导致 expert 权重加载的代价远大于实际计算。论文将这个现象称为 **sparsity erosion（稀疏性侵蚀）**。

更进一步说，chunked prefill 的本质是在 **token 维度** 做切分。这个维度并不是唯一的选择——模型还有一个维度可以切：**层（layer）维度**。

这个思路，就是 Layered Prefill 的起点。但在讲它之前，让我们先做一个有趣的 detour。

### 三、DiT-Serve：当调度思想跨越模态边界

**论文：** *DiT-Serve: An Efficient Serving Engine for Diffusion Transformers* (Berkeley EECS-2025-46)

如果你只关注 LLM serving，可能会错过这篇论文。但它做的事情非常值得关注：把 ORCA 的 iteration-level scheduling 思想，迁移到了 **扩散模型（Diffusion Model）** 的推理服务上。

我之所以把它放在这条脉络里，不是因为它在技术上直接推进了 LLM 调度的粒度演化，而是因为它回答了一个更元层面的问题——**ORCA 的调度范式有多大的泛化能力？**

先快速回顾一下 Diffusion Transformer（DiT）的推理过程。和 LLM 的自回归生成不同，DiT 生成图片或视频的方式是：从一个随机噪声出发，经过 T 步去噪（denoising step），每一步都是一次完整的前向传播，逐步"提纯"成最终的图像。T 通常在 20-100 之间。

在 DiT-Serve 之前，DiT 的 serving 方式和 ORCA 之前的 LLM serving 一样原始：凑齐一个 batch，所有请求一起跑完所有去噪步骤，然后下一批。问题也一模一样——不同请求的去噪步数不同（有的要 20 步，有的要 50 步），短请求做完了只能干等长请求。更糟的是，不同请求的分辨率和视频长度还不一样，导致序列长度（patch 数量）各异，batch 时需要 pad 到最长的那个，算力又浪费了一大块。

DiT-Serve 的解法非常自然——**step-level batching**，直接类比 ORCA 的 iteration-level scheduling：

| 概念 | ORCA（LLM） | DiT-Serve（Diffusion） |
| --- | --- | --- |
| 调度粒度 | 每个 decode iteration | 每个 denoising step |
| 原子单元 | 一次前向传播生成一个 token | 一次前向传播完成一步去噪 |
| 核心问题 | 序列长度不同，短请求等长请求 | 去噪步数不同，短请求等长请求 |
| 中间状态 | KV cache（大，管理复杂） | latent tensor（小，迁移方便） |
| 新请求加入 | 任意 decode iteration 可加入 | 任意 denoising step 可加入 |

![](https://pica.zhimg.com/v2-a595b17e8b02e00a85e72eda3fc4e928_r.jpg)

每一步去噪结束后，调度器可以把已完成的请求移出，把新请求加入，甚至可以做抢占（preemption）——把某个请求的当前 latent tensor 卸载到 CPU 内存，腾出 GPU 给更高优先级的请求。因为 DiT 没有 KV cache（中间状态只有一个 latent tensor，比 KV cache 小得多），抢占的代价非常低。

DiT-Serve 还引入了 **Brick Attention** 来解决空间维度的异构性。传统的 Ring Attention 要求所有 GPU 处理相同长度的序列，不同分辨率的请求会被 pad 到最长的那个。Brick Attention 用 best-fit bin-packing 算法把不同大小的请求分配到不同数量的 GPU 上（1、2、4 或 8 个），高分辨率请求占更多 GPU，低分辨率请求占更少，多个 ring attention 实例并行运行。

调度策略上，DiT-Serve 使用 **最短作业优先（SJF）**，根据请求的剩余计算量（不仅是剩余步数，还要乘以每步的计算量，因为分辨率不同每步代价不同）来排优先级。因为去噪步数是提前已知的，这个估算是精确的——不像 LLM 里你事先不知道一个请求会生成多少 token。

实验结果上，DiT-Serve 在 Open-Sora、Mochi、CogVideoX 等模型上取得了 **2-3 倍的吞吐提升** 和显著的延迟降低。

回到我们的主线。DiT-Serve 的价值在于：它证明了 ORCA 所开创的 iteration-level scheduling 范式 **不是 LLM 特有的**，而是一种可以泛化到任何迭代式生成过程的调度思想。LLM 的自回归生成是迭代式的（每次生成一个 token），扩散模型的去噪也是迭代式的（每次做一步去噪），调度策略可以在"迭代"这个自然边界上做决策，而不需要等到整个任务完成。

同时，DiT 和 LLM 的一个关键区别也很有启发性：DiT 没有 prefill/decode 的不对称性。每一步去噪的计算量基本相同（对于固定分辨率），不存在"第一步特别重"的问题。这意味着 SARATHI 要解决的那个问题——prefill 阻塞 decode——在 DiT 的世界里天然不存在。去噪步骤本身就是一个天然的、均匀的调度 chunk。

但在 LLM 的世界里，prefill/decode 的不对称性是无法回避的现实。SARATHI 用 chunked prefill 在 token 维度切分来缓解它，而 Layered Prefill 则找到了一个全新的切分维度。

### 四、Layered Prefill：换一个维度切下去

**论文：** *From Tokens to Layers: Redefining Stall-Free Scheduling for LLM Serving with Layered Prefill* (arXiv 2510.08055, 2025)

如果说前面三篇论文沿着同一个维度不断变细——从 request 到 iteration 到 chunk——那 Layered Prefill 做的事情更有意思：**它换了一个维度**。

之前的方案都是在 token 维度上做文章：ORCA 在 token 生成的 iteration 边界上调度，SARATHI 把 prompt 的 token 序列切成 chunk。Layered Prefill 说：不切 token，切 layer。

具体来说，它把 Transformer 模型的所有层分成 G 个 **layer group**，G 的大小根据 prompt 长度动态计算：

```text
G(L) = max(1, ceil(L / 512))
```

一个 8192-token 的 prompt 会让模型被分成 16 个 layer group。然后，调度规则极其优雅：

**每个 iteration 中，恰好有一个 layer group 同时执行 prefill 和 decode，其他所有 layer group 只执行 decode。**

![](https://pic1.zhimg.com/v2-5d82a0e0cd3996897a5beaef886f5442_r.jpg)

用一个 G=4 的例子来看：

| Iteration | Group 1 | Group 2 | Group 3 | Group 4 |
| --- | --- | --- | --- | --- |
| 1 | prefill + decode | decode | decode | decode |
| 2 | decode | prefill + decode | decode | decode |
| 3 | decode | decode | prefill + decode | decode |
| 4 | decode | decode | decode | prefill + decode |

Prefill 像一道波浪一样，每个 iteration 向下推进一个 layer group。4 个 iteration 之后，这个请求的 prefill 就在所有层上做完了，它无缝地变成一个纯 decode 请求加入后续 batch。

这个设计最妙的地方在于：**decode 从来没有被阻塞过**。每一个 iteration，所有 layer group 都在为 decode 请求推进计算。prefill 的额外计算量被均匀分摊到 G 个 iteration 中，每个 iteration 只承受一个 layer group 的 prefill 负载。

与 chunked prefill 的关键区别：

在 SARATHI 的方案中，一个 4096-token 的 prompt 被切成 8 个 512-token 的 chunk。每个 chunk 都要从第 1 层走到最后一层，意味着模型的每一层权重被加载了 8 次。在 Layered Prefill 中，每一层只处理一次完整的 4096-token prompt（在它被指定为"prefill + decode"的那个 iteration 中），权重加载次数和不做 chunking 时一样——只有 1 次。

**token 维度切分 vs 层维度切分**，这是两种正交的方案。前者切 prompt 保全层，后者保全 prompt 切层。

在稠密模型上，这两种方案的差异不是特别大——层权重加载的开销相比计算本身占比有限。但在 MoE 模型上，差异是戏剧性的。

MoE 模型每层有几十上百个 expert，每次前向传播只激活一部分。SARATHI 的小 chunk（比如 512 tokens）导致每个 chunk 激活的 expert 覆盖面很广但每个 expert 只处理极少 token，expert 权重加载的开销远大于实际计算——这就是 sparsity erosion。Layered Prefill 让每个 layer group 一次性看到完整的 prompt，token 数量足够多，每个被激活的 expert 都能处理大量 token，充分摊薄了权重加载的代价。

实验数据非常有说服力。在 Qwen3-30B-A3B（128 experts，top-8）和 GPT-OSS-20B（32 experts，top-4）两个 MoE 模型上，对比 vLLM + SARATHI 式 chunked prefill（chunk size 512）的基线：

TTFT（首 token 延迟）降低最多 70%（arXiv 数据集上从 2.80s 降到 1.24s），端到端延迟降低最多 41%，SLO 限制下的吞吐提升最多 29%，HBM/NVLink 流量减少最多 39%，每 token 能耗降低最多 22%。

### 五、回看全局：调度粒度的演化地图

把四篇论文放在一起，一条演化线清晰可见：

| 维度 | ORCA (2022) | SARATHI (2024) | DiT-Serve (2025) | Layered Prefill (2025) |
| --- | --- | --- | --- | --- |
| 调度粒度 | request → iteration | iteration 内 chunk-level | denoising step（跨模态迁移） | iteration 内 layer-level |
| 切分维度 | 请求边界 | token 序列 | 去噪步骤边界 | 模型深度 |
| 解决的问题 | batch 内短请求等待长请求 | prefill 阻塞 decode | 异构请求阻塞（步数、分辨率） | chunked prefill 的冗余权重加载 |
| 留下的问题 | prefill 阻塞 decode | 冗余层遍历；MoE sparsity erosion | — | 调度开销与模型深度耦合 |

不管是 ORCA、SARATHI 还是 Layered Prefill，做的事情本质上都一样：把一个大块的、独占式的计算任务拆成小块，在小块的边界上做"换人"的决策。操作系统教科书里的时间片轮转、进程抢占，和这里的 iteration-level scheduling、chunked prefill，在抽象层面上是同一件事。区别只在于"时间片"的定义：是一个 request、一个 iteration、一个 token chunk、还是一个 layer group。

每一步都不是凭空的发明，而是对上一步方案的某个具体局限性的精确回应。ORCA 打碎了 batch 的边界，但 prefill 仍然是一整块；SARATHI 把 prefill 切成 chunk，但 chunk 要反复穿过所有层；Layered Prefill 换了一个维度来切，让每层只看一次完整 prompt。DiT-Serve 则从侧面验证了这套调度思想的跨模态泛化能力。

调度粒度的极限在哪里？可能直到它的控制面开销超过了它带来的收益，这条线才会停下来。
