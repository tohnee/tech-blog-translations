大模型能写文章、改代码，但你让它查一下公司数据库里的订单，或者把查询结果存到本地文件，它光靠聊天是做不到的。得有程序替它连数据库、读写文件，再把结果交回来。

接一个工具还好，接得多了就容易麻烦：这个应用有自己的接法，那个应用又有另一套。同一个查订单的功能，换个助手，可能又得适配一遍。

MCP 想解决的，就是这类重复接工具的问题。

### 可以把 MCP 理解成工具接口里的 USB

MCP 的全称是 **Model Context Protocol，模型上下文协议**，最初由 Anthropic 提出并开源。

它不是某个智能体框架，也不是一个装上就能包办所有事情的工具，而是一套开放的通信协议。它约定了应用和外部服务该怎么互相介绍能力、传递请求、返回结果。

拿 USB 打个比方：鼠标、键盘、移动硬盘做的事情完全不同，但只要接口兼容，电脑就能按统一的方式接入它们。MCP 在智能体应用和外部工具之间，起的就是类似的作用。

把这个比喻换成文字结构，大致是这样：

```text
智能体应用（Claude Desktop、Cursor、Cline 等）
    ↕ 应用内的 MCP Client
统一的 MCP 协议
    ↕ MCP Server
具体能力：查数据库、读写文件、访问远程服务
```

比如，公司已经有一个查询订单的接口。以前，你可能要分别给客服助手、运营助手写接入代码。用了 MCP，就可以把查询订单的能力包装成一个 MCP Server，再让这些支持 MCP 的应用连接它。

订单到底存在哪张表、接口怎么调用，由 Server 这一侧处理。应用通过统一协议获取工具说明，再按说明调用，不用每换一个助手就重写一遍订单查询逻辑。

从两边来看，能接上的东西不只一种：

| 应用这一侧 | 连接方式 | 数据和工具这一侧 |
| --- | --- | --- |
| Claude Desktop 等聊天应用 | 通过内置的 MCP Client 连接对应的 MCP Server | PostgreSQL、SQLite、本地文件等 |
| Cursor、Cline 等编程助手 | 通过内置的 MCP Client 连接对应的 MCP Server | Git、错误监控、代码相关工具等 |
| 自己开发的智能体应用 | 集成 MCP Client，连接对应的 MCP Server | 邮件、日历、地图、公司内部接口等 |

表格只是按常见用途举例，不是说某类应用只能接某类工具。重点是两边都按同一套约定来，接入代码就更容易复用。

当然，“即插即用”不等于完全不用配置。Server 怎么启动、连哪个地址、账号有没有权限，这些仍然要处理。社区里已经有不少现成的 MCP Server，可以少写一些代码，但工具能不能用、好不好用，还得看它的实现和你的使用场景。

### 已经有 Function Call 了，为什么还要 MCP？

这两个名字经常放在一起说，但它们管的不是同一件事。

**Function Call 解决的是：怎么让模型告诉程序，该调用哪个工具、传什么参数。**

比如你告诉模型，有一个 `get_weather` 工具可以查天气。用户问“杭州今天什么天气”，模型就可以返回一条结构化指令：调用 `get_weather`，参数是杭州。

但模型给出指令以后，谁去调用天气接口？接口需要什么鉴权？结果怎么整理？这些不是 Function Call 本身替你做的，得由应用或框架来处理。

如果每个项目都单独写这套代码，工具一多，就会出现重复适配的问题：

- 工具名称、参数和用途，要在应用里维护。
- 收到模型的调用指令后，要找到对应的实现并执行。
- 换一个应用，可能又得接一遍。
- 工具接口发生变化，接了它的几个应用可能都要跟着改。

这不是说 Function Call 天生就得把代码“写死”。你也可以抽公共模块、封装服务。只是它本身不规定不同应用之间该怎么共享和接入这些工具。

**MCP 解决的则是：应用怎么用统一的方式发现和调用外部能力。**

工具说明和具体实现放在 MCP Server 这一侧，应用通过 MCP Client 与它通信。这样，一个 Server 就能供多个兼容的应用使用。

### Host、Client、Server，分别干什么？

这三个词不用想得太复杂：

- **Host（宿主应用）**：就是用户正在使用的应用，比如 Claude Desktop，或带有智能体能力的编辑器。它负责组织对话、调用模型，以及管理工具使用和授权流程。
- **Client（客户端）**：在 Host 内部，负责和某个 MCP Server 建立连接、协商能力、收发消息。
- **Server（服务端）**：把文件、数据库或其他系统的能力，按 MCP 的约定提供出来，并处理相应请求。

一个应用接多个 Server 时，可以这样理解：

```text
Host：用户正在使用的智能体应用
├── MCP Client A ↔ 文件 MCP Server ↔ 本地文件
├── MCP Client B ↔ 数据库 MCP Server ↔ 数据库
└── MCP Client C ↔ 远程服务 MCP Server ↔ 外部 API
```

每个 Client 维护与对应 Server 的连接。Server 可以在本机运行，也可以部署在远程，不是名字里带了 Server 就一定要放到云上。

Client 和 Server 之间的消息基于 **JSON-RPC 2.0**，也就是用约定好的 JSON 消息表达请求、响应和通知。模型 API 的调用则是另一段通信，不要把这两段混为一谈。

所以，MCP 并没有取代 Function Call。常见做法是：应用通过 MCP 拿到工具说明，转换成模型 API 支持的工具定义；模型返回调用指令后，应用再通过 MCP 去执行。

### 一次 MCP 工具调用，是怎么跑起来的？

假设你对助手说：

> 帮我查一下杭州现在的天气，再把结果保存到本地的天气记录文件里。

助手已经接好了天气和文件两个 MCP Server，也有相应的访问权限。整个过程可以分成下面几步。

### 第一步：先问清楚，有哪些工具能用

应用通过 MCP Client 和 Server 完成初始化，确认协议版本和双方支持的能力，然后获取工具列表。

在工具调用这个场景里，可以通过 `tools/list` 获取工具说明，包括工具叫什么、能做什么、参数怎么填。比如天气工具需要城市，文件工具需要文件路径和写入内容。

这些说明是标准化的数据，不是给用户看的使用手册，而是供程序读取、再整理给模型的工具定义。

### 第二步：把问题和工具说明交给模型

应用把用户的问题、相关对话上下文，以及当前任务可用的工具说明发给模型。

模型发现，保存天气之前得先查到天气，于是给出第一条指令：调用天气工具，城市填杭州。

这里模型只是做了决定，还没有真的连上天气服务。

### 第三步：应用执行调用，把结果送回来

应用收到指令后，按权限和确认规则检查这次调用，再由对应的 MCP Client 通过 `tools/call` 请求天气 Server 执行。

Server 查询天气服务，把结果返回给应用。应用再把这个结果交给模型，模型才知道下一步要写入什么内容。

接下来，模型给出文件写入指令。应用按同样的方式调用文件 Server，拿到保存成功或失败的结果。

查天气和写文件有先后依赖，不能还没查到天气，就先编一份内容写进去。涉及写文件、改数据这样的操作，也不能因为模型提议了就跳过必要的授权。

### 第四步：根据实际结果回复用户

两次调用结束后，应用把工具结果和必要的对话上下文交给模型，由模型组织最后的回复。

整个过程用文字串起来就是：

```text
准备：应用 ↔ MCP Server，初始化并获取工具说明

用户 → 应用：查询杭州天气，并保存到文件
应用 → 模型：用户问题 + 可用工具说明
模型 → 应用：调用天气工具，城市为杭州
应用 → 天气 MCP Server：检查权限后，发起工具调用
天气 MCP Server → 应用：返回天气结果
应用 → 模型：补充天气查询结果
模型 → 应用：调用文件工具，写入查到的天气
应用 → 文件 MCP Server：检查权限后，发起写入调用
文件 MCP Server → 应用：返回写入结果
应用 → 模型：补充文件写入结果
模型 → 应用 → 用户：说明天气情况和保存结果
```

如果写入失败，就应该告诉用户失败原因，而不是直接说“已经保存”。实际任务也不一定只走一轮，模型可能需要根据工具结果继续调用，或者向用户追问缺少的信息。

这里 MCP 主要参与的是工具发现和工具执行。至于模型怎么规划、对话历史怎么整理，仍然是模型和应用这一侧的事情。

### 别弄反了：模型做决定，程序去执行

“大模型调用工具”这个说法很方便，但容易让人以为模型自己打开了数据库连接，或者自己发起了 HTTP 请求。

实际上，在上面这种工具调用流程里，分工是这样的：

| 角色 | 负责什么 |
| --- | --- |
| 大模型 | 根据问题和工具说明，决定调用哪个工具、传什么参数；拿到结果后继续判断或生成回复 |
| 智能体应用 | 整理上下文、处理授权、解析调用指令，通过客户端发起调用，再把结果交回模型 |
| MCP Server | 处理工具请求，执行具体逻辑或访问背后的系统，把执行结果返回给应用 |

看一个具体的请求就更容易明白了。下面沿用通义千问的兼容接口，使用 `tools` 字段，把用户问题和天气工具的说明一起传给模型。

请求地址：`POST https://dashscope.aliyuncs.com/compatible-mode/v1/chat/completions`

下面是请求体；实际调用还需要在请求头中配置你自己的 API Key，并确认账号有该模型的调用权限。

```json
{
  "model": "qwen-plus",
  "messages": [
    {
      "role": "user",
      "content": "帮我查一下杭州现在的天气"
    }
  ],
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "get_weather",
        "description": "查询指定城市的实时天气",
        "parameters": {
          "type": "object",
          "properties": {
            "city": {
              "type": "string",
              "description": "城市名称，例如杭州"
            }
          },
          "required": ["city"]
        }
      }
    }
  ]
}
```

模型并没有收到天气接口的实现代码。它只看到了工具名称、用途，以及用 JSON Schema 描述的参数格式。

它可能返回这样的调用指令。这里只展示响应中的 `message` 部分，调用 ID 仅作示意：

```json
{
  "role": "assistant",
  "content": null,
  "tool_calls": [
    {
      "id": "call_weather_001",
      "type": "function",
      "function": {
        "name": "get_weather",
        "arguments": "{\"city\":\"杭州\"}"
      }
    }
  ]
}
```

注意，这里面没有“晴天”“多少度”，只有工具名和参数。`arguments` 在这个接口里还是一个 JSON 字符串，应用需要解析、校验后再使用。

如果工具是应用自己接的，应用就去执行对应的函数或服务调用；如果工具来自 MCP Server，应用就通过 MCP Client 发起调用。无论走哪条路，都得拿到真实结果，再交给模型生成天气回复。

回头看，MCP 并不是让模型多学会了一项查数据库或读文件的本领。它做的是把工具接入这件事统一起来：工具提供方按标准提供能力，应用按标准连接和调用。模型负责判断该用什么，程序负责把事情真正做完。换一个兼容的应用时，同一套工具也能继续用，不必再从头接一遍。
