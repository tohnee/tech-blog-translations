PyTorch 中能正常推理，不代表模型已经适合上线。生产环境还要关注启动时间、显存、吞吐、延迟、并发和硬件兼容性。常见交付链路是：**固定推理行为，导出 ONNX，校验计算图与数值**，再**针对目标 GPU 构建 TensorRT Engine**，最后接入服务并做性能、精度和稳定性验收。*专辑：*[互联网-部署优化相关技术 - 知乎](https://www.zhihu.com/column/c_2075159379821834570)

## **一、先搞懂 ONNX、ONNX Runtime 和 TensorRT 分别负责什么**

（1）ONNX 是开放的模型交换格式，**用标准计算图描述网络结构、权重、输入输出和部分形状信息**；它解决的是“**模型如何被不同工具理解**”，不是加速器。（2）ONNX Runtime 是推理运行时，支持 CPU、CUDA、TensorRT 等 Execution Provider**，适合做导出后的第一层验证**。（3）TensorRT 是 NVIDIA 的 GPU 推理优化器和运行时，**会结合目标显卡、精度、输入形状和工作空间，优化图并编译出 Engine**。

## **二、从训练模型到可运行 Engine 的完整流程**

**1. 固定推理行为并导出。** 导出前调用 `model.eval()`，明确颜色通道、缩放、归一化、NCHW/NHWC 和 padding。保存固定样本的 PyTorch 输出，作为各阶段基准。示例：

```python
model.eval()
dummy = torch.randn(1, 3, 640, 640, device="cuda")
torch.onnx.export(
    model, dummy, "model.onnx",
    input_names=["images"], output_names=["output"],
    opset_version=17,
    dynamic_axes={"images": {0: "batch"}, "output": {0: "batch"}},
)
```

导出后查看输入输出名称、数据类型和维度，运行 `onnx.checker.check_model`**，再用 ONNX Runtime 跑基准样本**。对比时要使用完全一致的预处理、随机种子和后处理，否则误差结论没有意义。比较输出张量的最大绝对误差、平均误差和相对误差，不要只看最终标签。检测模型还要核对坐标格式、置信度、类别索引和 NMS；图内外后处理不能重复执行。根据 FP32、FP16 或 INT8 设置阈值，并在必要时逐层定位首个偏差节点。

**2. 构建 TensorRT Engine。** `trtexec` 可快速验证：

```bash
trtexec --onnx=model.onnx --saveEngine=model_fp16.engine \
  --fp16 --minShapes=images:1x3x640x640 \
  --optShapes=images:4x3x640x640 \
  --maxShapes=images:8x3x640x640
```

三个 Shape 构成动态输入的 Optimization Profile，`optShapes` 应接近真实流量。FP16 通常可降低显存、提高吞吐，但要复核精度；INT8 需要覆盖真实光照、尺寸、类别和边界情况的校准数据。**遇到不支持的算子，先确认 opset 和 TensorRT 版本，再考虑改写、替换或插件；训练损失、随机增强和反向传播节点应在导出前移除**。

**4. 接入应用。** 基本链路是创建 Runtime，反序列化 Engine，创建 Execution Context，分配输入输出显存并提交异步推理。生产服务应复用 Context、缓冲区和 CUDA Stream，避免每个请求重复分配；多线程不要无保护地共享同一 Context，应使用独立 Context 或队列。请求链路要明确批处理、超时、取消和异常释放策略；输入尺寸变化时先设置正确的 binding shape，再分配或复用对应缓冲区。服务启动阶段可提前加载 Engine、创建 Context 并做一次预热，避免首个用户请求承担初始化成本。

## **三、性能、精度与线上稳定性该怎么验证**

验收至少覆盖正确性、延迟、吞吐和资源占用。延迟看 P50、P95、P99，并拆分预处理、Host 到 Device、GPU 推理、Device 到 Host 和后处理；吞吐记录 batch、并发、输入形状和预热次数。第一次推理可能包含 CUDA 初始化、内存申请和算法选择，压测应先预热并统计稳定区间。尺寸变化过大时，限制尺寸集合或为常用尺寸分别构建 Engine。

![](https://pic4.zhimg.com/v2-e8af06c3177b136523e7c31037dbb49d_r.jpg)

精度要按任务验证：分类看准确率和混淆矩阵，检测看 mAP 与召回率，分割看 IoU，生成式模型结合任务指标和人工抽检。FP16 通常可控；INT8 收益更大，但校准不匹配可能伤害少数类别。显存还包括权重、工作空间、激活、缓冲区和 CUDA 上下文，应预分配缓冲池、限制并发并监控峰值。排查延迟异常时，先确认是否完成预热，再分别观察 CPU、GPU、拷贝和后处理耗时；排查精度异常时，先固定一条输入，依次比较 PyTorch、ONNX Runtime 和 TensorRT 的输出。若只有部分请求失败，还要检查动态 Profile 是否覆盖实际尺寸、输入是否越界，以及不同线程是否错误复用上下文。上线检查清单至少包括：目标 GPU 能否反序列化 Engine，驱动和 CUDA 是否匹配，插件是否已注册，服务重启后是否能自动恢复，以及满负载时是否有超时和降级策略。

![](https://pic1.zhimg.com/v2-eeea82043965e34f2dfba1e1381f3816_r.jpg)

发布时把模型、Engine、预处理配置、后处理代码和校准数据作为同一版本，记录提交号、opset、硬件、环境和构建日志。上线前做离线回归、压测和灰度，上线后监控错误率、延迟分位数、吞吐、显存、GPU 利用率和业务指标，并保留上一版 Engine 以便回滚。回归样本应包含正常输入、空结果、极端尺寸、异常编码和边界类别；压测还要覆盖冷启动、持续高并发和显存接近上限的场景。这样才能区分模型问题、资源瓶颈与服务编排问题。

![](https://pica.zhimg.com/v2-3d43949e3db76b4e0d6213e07faad710_r.jpg)

总之，ONNX 负责交换，ONNX Runtime 负责验证，TensorRT 负责面向 NVIDIA GPU 优化和构建。可靠部署的关键不是简单转换 `.pt` 到 `.engine`，而是先保证输入与数值一致，再针对真实硬件和流量优化，最后用监控与版本管理保障上线。
