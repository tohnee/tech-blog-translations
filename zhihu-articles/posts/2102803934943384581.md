本文从两个维度理解 GPU RDMA：GDR（GPUDirect RDMA，历史文章有介绍）决定 NIC 是否直接读写 GPU 显存；CPU Proxy、GDAKI、IBGDA 决定通信请求如何发起和推进（GPU 或 CPU）。开启 GDR 不等于由 GPU 发起通信。

无论使用哪种路径，通信过程中都必须分别确认：源数据已经准备好、远端数据可读、接收方已完成消费。三者决定何时可以发送、读取和覆盖通信缓冲区。

### 1. CPU Proxy

CPU 创建保护域 PD、注册内存区域 MR、创建完成队列 CQ 和可靠连接 RC QP，通过控制通道（可使用 TCP 连接）交换连接信息、地址与 rkey，再用 `ibv_modify_qp()` 迁移 QP 状态：INIT → RTR → RTS。随后用 `ibv_post_send()` 投递数据，用 `ibv_poll_cq()` 获取完成。

GDR 关闭时，NIC 读写 host 锁页内存；GPU 与 host 之间可以通过 D2H/H2D 拷贝，也可以由 kernel 直接访问映射的主机缓冲（load/store）。本文所述 NCCL 非 GDR 路径采用后者。开启 GDR 后，NIC 可以直接读写 GPU MR，但投递和完成处理仍由 CPU 负责。[主机缓冲映射](https://github.com/NVIDIA/nccl/blob/7b83616df3ae082a1f32bb74c27458bfe8153a13/src/transport/net.cc#L1121)

GDR 开启时，GPU 显存可通过 nvidia-peermem 配合 `ibv_reg_mr()` 注册，也可由 CUDA 导出 DMA-BUF，再用 `ibv_reg_dmabuf_mr()` 注册。两者注册路径不同，但不改变 RDMA 操作，地址管理和映射细节由底层处理。注意，内存释放后，即使重新分配得到相同地址，也不能沿用旧注册。[注册与复用](https://docs.nvidia.com/cuda/gpudirect-rdma/)

### Write、通知与队列回收

普通 RDMA Write 按远端地址和 rkey 写入，不产生远端接收 CQE。`RDMA_WRITE_WITH_IMM` 额外消耗一个 Receive WQE，并生成一个 `IBV_WC_RECV_RDMA_WITH_IMM` 类型的 CQE，携带 32 位 IMM data。数据直接写入远端 MR，而不是 Receive SGE，因此接收端可用 `ibv_post_recv()` 预投递 zero-SGE WQE，获取 IMM data。

RC 的 SEND、WRITE_WITH_IMM 到达时，若没有可用 Receive WQE，会触发 RNR（Receive Not Ready，接收方未就绪）重试。及时补齐可继续，有限次重试耗尽则失败。普通 Write、Read、Atomic 不消耗这类 Receive WQE。

通知可与数据合并，也可拆为同 QP 的普通 Write + 零字节 Write-With-Immediate。QP 设置 `sq_sig_all=0` 时（NCCL 如此设置），可只给尾部的 WR 设置 `IBV_SEND_SIGNALED`，减少本地 CQE。

Unsignaled 请求仍占用该 QP 的发送队列，只是成功时不再单独生成 CQE。轮询后续 signaled WR 的成功完成，可回收同 QP 此前已完成请求的槽位。必须在 SQ 填满前安排 signaled WR 并轮询 CQ，避免队列耗尽或错误覆盖尚未回收的 WQE。[NCCL 的 SQ 回收说明](https://github.com/NVIDIA/nccl/blob/7b83616df3ae082a1f32bb74c27458bfe8153a13/src/transport/net_ib/p2p.cc#L413)

NCCL 开启 AR（Adaptive Routing，自适应路由）且数据较大时，采用若干 bulk write + 最后零字节 Write-With-Immediate 的拆分方式，利用 AR 的能力。如果收发双方支持并启用 OOO RQ（Out-of-order Receive Queue，乱序接收队列），则 WRITE_WITH_IMM 不需要因为 AR 被强制拆分为 Write + 零字节 Write-With-Immediate。OOO RQ 允许接收 WQ 乱序消费。[发送分支](https://github.com/NVIDIA/nccl/blob/7b83616df3ae082a1f32bb74c27458bfe8153a13/src/transport/net_ib/p2p.cc#L143) · [OOO RQ 定义](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/env.html#nccl-ib-ooo-rq)

### CTS：接收完成不等于允许覆盖

MR 提供访问权限，不管理缓冲区的使用权。NCCL 接收方通过 RDMA Write 向发送方 FIFO 发布 CTS（Clear To Send），携带地址、长度、rkey、tag 和递增序号；发送方匹配后才写数据。序号用于区分循环 FIFO 中的新旧授权。[CTS 发布](https://github.com/NVIDIA/nccl/blob/7b83616df3ae082a1f32bb74c27458bfe8153a13/src/transport/net_ib/p2p.cc#L391)

SPSC 队列中，生产者推进 tail，消费者推进 head，head 与 tail 之间是待消费数据。在 NCCL SIMPLE 环形缓冲路径中，proxy 等待网络完成并建立 GPU 可见性后推进 tail；GPU 消费后推进 head，归还槽位 credit，才允许再次覆盖。空闲槽位可提前发布 CTS，形成流水线。[槽位回收](https://github.com/NVIDIA/nccl/blob/7b83616df3ae082a1f32bb74c27458bfe8153a13/src/transport/net.cc#L1554)

### 接收 GPU 何时可以读

CPU 收到接收 CQE，不等于正在运行的 GPU kernel 已能读到新数据。接收端需要通过适用的 flush 或同步机制建立 GPU 可见性。[GPU 内存序](https://docs.nvidia.com/cuda/gpudirect-rdma/#synchronization-and-memory-ordering)

- **GDR 关闭：**显式拷贝路径先等网络接收成功，再执行 H2D，并用同 stream 排序或跨 stream 事件保证消费 kernel 在拷贝完成后执行；直接访问主机暂存缓冲时，则由 proxy 发布就绪进度，GPU 等待后消费。
- **GDR 开启：**NCCL NET/IB 的 Read flush 路径通过接收端本地回环 QP，从接收 GPU buffer 读回 1 字节；等 Read 的 CQE 后再通知 GPU 消费。重要的是 Read 的完成，而非读回的值。Read flush 是否必要取决于平台和已有同步机制。[Read flush](https://github.com/NVIDIA/nccl/blob/7b83616df3ae082a1f32bb74c27458bfe8153a13/src/transport/net_ib/p2p.cc#L569)

### 2. NCCL GDAKI

CPU 准备 context、window 和 QP；GPU 调用 GIN `put()`，带 signal 的传输在 GDAKI 后端通过 DOCA 的 `doca_gpu_dev_verbs_put_signal()` 生成 Write + Atomic。采用 GPU doorbell 时，GPU 写 WQE、敲门铃并轮询 CQ，这条路径会占用 SM，并非 zero-SM。

针对双口 LAG 的 queue_affinity，NCCL GDAKI 的修复改为按 peer 连续连接各 context 的主 QP，避免穿插打断轮转，使同一 peer 的主 QP 更均匀地分配到两个本地 TX 端口。[QP 连接顺序修复](https://github.com/NVIDIA/nccl/commit/a93cc0)

### 生产、投递与线程协作

- 数据由前一个 kernel 生成：生产和发送放在同一 stream；跨 stream 时用 event 建立依赖。
- 数据由同一 kernel 的多个线程生成：先执行覆盖所有生产者的线程同步，再发起发送。

Release fence 配合平台和接口要求，保证写入按要求对 NIC 可见，包括数据先于 NIC 读取、WQE 先于门铃通知。NCCL/DOCA 的投递接口处理发布顺序。

本文所述 NCCL 实现中，`put(..., ncclCoopWarp())` 会先同步 warp，配合接口要求的 release fence 发布数据，再由 lane 0 生成 WQE、提交请求，返回前再次同步。单线程发起则使用 `ncclCoopThread()`。[put 入口](https://github.com/NVIDIA/nccl/blob/7b83616df3ae082a1f32bb74c27458bfe8153a13/src/include/nccl_device/impl/gin__funcs.h#L550)

### MR 排序与通知

Relaxed ordering 允许 NIC 放宽写入目标 MR 的顺序。对 relaxed MR，不能只靠“先 Write 数据，再普通 Write flag”通知数据就绪：缺少额外的顺序保证时，接收方可能先看到 flag，而数据尚未齐全。[MR 排序](https://man7.org/linux/man-pages/man3/ibv_reg_mr.3.html)

使用 GIN 的 signal 通知机制时，让 `put()` 携带 signal：GDAKI 在同一 QP 上先 Write 数据，再用 Atomic 更新 signal。接收方以 acquire 语义等到本轮信号后，再读取该信号覆盖的数据。[signal 语义](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/api/device_gin.html#devapi-signals)

注册 window 时，关键看 signal 放在哪里：NCCL 将 signal 单独分配并以 strict ordering 注册；数据 window 可按配置使用 relaxed ordering。[内部 signal 注册](https://github.com/NVIDIA/nccl/blob/7b83616df3ae082a1f32bb74c27458bfe8153a13/src/transport/net_ib/gdaki/gin_host_gdaki.cc#L701)

Strict ordering 只是约束 MR 的写入排序；发送前仍需要完成数据生产同步，接收端仍需要等待 signal，不同 QP 之间仍需要单独建立顺序。

### 本地复用与远端就绪

`put()` 返回或拿到 DOCA ticket 不保证操作已完成，不能据此复用源缓冲或读取远端数据。随后要区分：

- **源缓冲可复用：**`gin.flush()` 保证当前 context 内参与线程此前 put 的源数据已被消费，不承诺远端数据已就绪。它不同于 proxy 的接收端 Read flush。
- **接收端可读：**用 acquire 语义的 `waitSignal()` 等到本轮信号，再读取其覆盖的数据。

`ncclGin_WeakSignalInc` 只覆盖捆绑的本次 put；`ncclGin_StrongSignalInc` 还覆盖同 context、同 peer 此前的 put。需要一次通知确认多次传输时使用 strong。[GIN 完成语义](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/api/device_gin.html)

### 3. NVSHMEM IBGDA 与 DeepEP

NVSHMEM 管理 bootstrap（控制通道）、对称 heap 和 MR/QP。一般应用可在 GPU 调用 `nvshmem_putmem_signal_nbi()` 发起带通知的非阻塞传输；发送端用 `nvshmem_quiet()` 确认此前通信完成，接收端等待 signal 后消费。

DeepEP legacy 为精简数据路径，直接利用 NVSHMEM 的资源，由 warp 协作填写 mlx5 WQE、更新 DBREC 并敲 GPU 门铃。[NVSHMEM 设备入口](https://github.com/NVIDIA/nvshmem/blob/919760f413fb834e76382d129ba9c3314ce722be/src/include/device/nvshmem_defines.h#L312)

对称内存：IBGDA 用“对端 heap 基地址 + 本地偏移”定位目标地址并查找 key。连续分配不等于一个 MR；源或目标跨注册边界时，需要拆成多个 WQE。

### Normal 与 low-latency 的跨机通知协议

DeepEP 的 normal 模式通过 tail/head 管理环形缓冲区。发送方按批次 Write token，再在同一 QP 上用 Atomic 推进远端 tail，表示有新的可消费数据入队。接收方以 acquire 语义观察 tail 后读取、转发数据。

汇总槽位消费进度后，接收方再通过反向 Atomic 更新发送方显存中的 head。发送方本地轮询 head，确认对方槽位可复用，就无须主动通过 RDMA Read 查询。

Tail 表示数据就绪，head 表示空间归还。数据可读和槽位可复用是两个状态。[数据与 tail 提交、消费进度回传](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaac82068020353dce2c302e38153c0bfaa/csrc/kernels/legacy/internode.cu#L1036)

Low-latency 模式的 dispatch 通过最后的 token count 通知就绪。各发送 warp 先将发往同一 rank、同一 expert 的 token write 提交到对应 QP，再通过本地 finish counter 的 release/acquire 汇总提交进度。

负责通知的线程确认这些 Write 均已提交后，在同一 QP 尾部追加 Atomic，更新对端 `rdma_recv_count`。本地 finish counter 只确认提交进度，数据先于通知的保证来自这一实现中同一 QP 上 Write → Atomic 的排序。

接收方以 acquire 语义等到 recv_count 非零，再读取这一批 token。Count 使用 `-(N+1)` 编码，因此 N=0 时也能通知本轮已完成。[发送与 count 提交](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaac82068020353dce2c302e38153c0bfaa/csrc/kernels/legacy/internode_ll.cu#L254) · [接收等待](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaac82068020353dce2c302e38153c0bfaa/csrc/kernels/legacy/internode_ll.cu#L387)

Low-latency 的 combine 使用完成 flag：相关 token write 提交后，在同一 QP 追加 Atomic 更新远端 flag，接收方以 acquire 语义等待 flag 后再读取数据。[combine 通知](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaac82068020353dce2c302e38153c0bfaa/csrc/kernels/legacy/internode_ll.cu#L915)

### qp_depth 是正确性约束

SQ 是环形队列，预留序号不等于已有空位。NVSHMEM 常规路径会检查空位；DeepEP 精简路径省略逐次检查，要求队列深度覆盖最大在途 WQE。Legacy low-latency dispatch/combine 检查：

```text
qp_depth >= (num_max_dispatch_tokens_per_rank + 1) * 2
```

容量预算要包括数据分片、Atomic 通知和允许同时在途的轮次，上述检查中的 `* 2` 与 DeepEP 双 buffer 设计一致。[容量约束](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaac82068020353dce2c302e38153c0bfaa/deep_ep/buffers/legacy.py#L609)

DeepEP 内部的 `nvshmemi_ibgda_quiet(dst_pe, qp_id)` 等待指定 QP 此前已提交 WQE 的完成，不覆盖其他 QP。其核心是 GPU 轮询本地发送 CQ，直到完成进度达到调用时记录的提交位置。[QP 完成与并发约束](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaac82068020353dce2c302e38153c0bfaa/csrc/kernels/legacy/ibgda_device.cuh#L462)

### 4. 多 QP 与 barrier

Barrier 必须说明：哪些参与者到达，以及此前哪些操作已经完成。

数据从 QP 1 发出，随后在 QP 0 发 barrier 信号，接收端仍可能先看到信号。多 QP 分片必须确认所有相关 QP 上的数据完成。

混用 NVLink 写入与 RDMA 时，两条路径都需建立可见性；仅等待网卡完成不够。Barrier 信号还须区分轮次，例如每个参与者维护单调计数器，等待本轮目标值。重置信号不能与远端更新并发，否则可能丢通知。
