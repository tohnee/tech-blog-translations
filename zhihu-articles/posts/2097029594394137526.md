## 引子

自回归 decode 有个尴尬的结构性浪费：每生成一个 token，都要把**整个模型的权重从 HBM 完整读一遍**——一个 70B 的 FP16 模型，每 token 要搬 140 GB 权重，而真正用来”算这一个 token”的算力连零头都不到，GPU 的 Tensor Core 大部分时间在等内存。既然算力大量空着，能不能顺手多干点活？投机解码的答案很直觉：**让一个小模型先猜几个 token，大模型用一次前向把猜测全部验完——猜对的直接收下，猜错的当没发生过，输出分布还严格不变**。

### 一、是什么

**投机解码（Speculative Decoding）**：一个”草稿 + 验证”的两段式解码加速方法。

1. **草稿（draft）**：一个远小于目标模型的小模型（draft model），基于当前上下文自回归地一口气猜 γ 个候选 token；
2. **验证（verify）**：目标模型（target）跑**一次**前向，并行算出这 γ+1 个位置各自的概率分布；
3. **裁决**：用改造过的拒绝采样从左到右决定接受哪些草稿 token——接受最长的一致前缀，在第一个不一致的位置用目标模型的分布重新采一个补上，一轮结束。

- **位置**：解码加速层。不改模型权重、不改输出质量，属于推理系统的调度/解码策略，和权重量化、KV Cache 量化、PD 分离都**正交可叠加**。
- **一句话**：把”串行等权重”的时间换成”并行验多个”，用便宜模型的猜测去填目标模型空闲的算力。
- **两个起点论文**（几乎同时、独立提出）：Leviathan et al.，*Fast Inference from Transformers via Speculative Decoding*，arXiv:2211.17192（ICML 2023）；Chen et al.，*Accelerating Large Language Model Decoding with Speculative Sampling*，arXiv:2302.01318（DeepMind）。
- **关键指标**：**接受率（acceptance rate）**——草稿 token 被目标模型接受的比例，直接决定加速比。

### 二、为什么（动机 → 量化因果链）

### 2.1 decode 慢在搬权重，不在算

单步 decode 是典型的 **memory-bound**：每步只算 1 个 token，但要把全部权重读一遍。

- 70B FP16 模型：每 token 读约 140 GB 权重，H100（~3.35 TB/s）下一步就要 ~40 ms，几乎全耗在 HBM→计算单元的数据搬运上，算力单元大量闲置；
- Qwen3-8B FP16：每 token 读约 16 GB，同样是一步一次的”全权重搬运”，算术强度极低。

这是量化、投机解码等一众解码优化的共同出发点：**decode 的瓶颈是带宽，不是算力**。

### 2.2 关键洞察：验证几乎是免费的

一次前向多算几个位置，边际成本极小：算 `γ+1` 个 token 和算 1 个 token，都要把同样一份权重读一遍——**权重读一次，就能顺带把多个位置的分布都算出来**。多出的那点计算，填的正是原本闲置的算力。

于是”猜测—验证”循环成立：小模型猜 γ 个的成本低（它权重小、读得快），大模型一次前向全验的成本 ≈ 原来一步的成本。**只要猜得准，每一步都在赚**。

### 2.3 收益有多大：接受率说了算

每轮循环的产出是 `1 + 平均接受长度`（至少产出 1 个——验证位置本身就会采出 1 个 token）。加速比大致正比于这个数，除以草稿成本与验证成本之和。论文口径（**随模型、负载、硬件而异，不是固定值**）：

- Leviathan et al.：T5-XXL 上较标准实现 **2–3×**，输出完全一致；
- Chen et al.：Chinchilla 70B 上 **2–2.5×**。

工程上常见的经验区间也是 **1.5–3×**，草稿质量高、内容可预测性强的场景（代码、摘要、RAG）更高。2025–2026 的方法代差把这个区间整体上移：EAGLE-3（arXiv:2503.01840）论文口径最高 **6.5×**；DeepSeek-V3 把 MTP 模块作为生产草稿器，论文口径 **1.8× TPS**（接受率 85–90%）。数字随方法代差快速上移，但都附带各自的适用条件——尤其是测量时的并发档位（见 2.5 与 3.2 的最新数据）。

### 2.4 为什么说它”无损”

这是投机解码区别于量化/剪枝的分水岭。验证环节用的是**修正的拒绝采样**：草稿 token 在目标模型下的概率不低于草稿模型给出的概率时必然接受；否则按两者比例概率拒绝，并在拒绝点从”残差分布”（目标分布减草稿分布后的归一化）里重采一个。数学上可证：**整个过程的输出分布与目标模型单独逐 token 采样逐位等价**——任何温度下都不掉点。代价仅仅是工程上要维护草稿模型。

### 2.5 边界：不是所有场景都赚

- **接受率是命门**：草稿和目标越对齐接受率越高；高 temperature、强创意性、高熵内容的接受率低，收益缩水；
- **大 batch 下失效**：高并发时 GPU 算力本就被大量请求占满，”免费”的闲置算力变少，验证的额外计算反而可能拖慢整体吞吐——所以投机解码的主场是**低 batch、延迟敏感的交互式场景**。2026 年的公开实测把这堵墙量化得很直白：DSpark、DFlash2 在并发 1 下分别有 2.57× / 2.80× 的加速，到 512 并发时反而跌到 vanilla 的 0.67× / 0.78×——**为低并发调优的草稿器，在满载服务器上是净负担**。这也是最新一代方法把”验证长度”从固定参数改成运行时自适应变量的直接原因；
- **草稿自身有成本**：草稿模型再小也要跑、也要占显存，猜得太慢或太不准都会侵蚀收益。

### 三、怎么办

### 3.1 草稿从哪来：四代做法

| 做法 | 代表 | 草稿怎么来 | 特点 |
| --- | --- | --- | --- |
| 独立小模型 | 原始投机解码 | 同词表的小号模型（或同架构小版本） | 直接可用，但要维护第二个模型，占显存、占调度槽 |
| 自投机（挂头） | Medusa（arXiv:2401.10774）、EAGLE-1/2/3（arXiv:2401.15077 / 2406.16858 / 2503.01840） | 在目标模型上加轻量预测头，复用目标模型已算出的隐状态 | 无需第二个模型；Medusa 多解码头 + 树注意力验证；EAGLE 在特征级（倒数第二层特征）自回归草拟，比 token 级信息更足 |
| 并行块草稿 | DFlash / DFlash2（arXiv:2602.06036）、P-EAGLE（arXiv:2602.01469）、DSpark（arXiv:2607.05147） | 一次前向并行生成整个 draft block：DFlash 走块扩散 + KV Injection；P-EAGLE 把验证模型 hidden states 同时映射到多个未来位置；DSpark 在 DFlash 主干上叠加顺序修正与置信度估计 | 草稿延迟与猜测长度解耦；但块内 token 依赖弱，接受长度通常低于自回归草稿——DSpark 的顺序修正头专门补这个 |
| 原生化 MTP | DeepSeek-V3 的 MTP 模块（arXiv:2412.19437） | 预训练期加入 MTP 目标，推理时用附带的单层模块做草稿 | 草稿与目标同源、无独立显存；但绑定权重版本，不随引擎热更新 |
| 零成本草稿 | n-gram / prompt lookup | 直接拿输入文本里的 n-gram 当草稿 | 不训任何模型；输出复述输入时（摘要、代码、RAG）近乎免费，与输入无关时无效 |

演进主线：**从”外挂一个小模型”到”贴着目标模型长出头”、到”一次并行出一整块”、再到”预训练时就焊进去”**——每一步都在降草稿的成本、提高与目标的对齐度；而 2026 年的最新战场已经换了维度：从”把草稿做准”转向”让验证长度跟着负载走”（见 3.2）。

### 3.2 最新进展（2025—2026）：原生化、并行化与负载自适应

**MTP 原生化**。源头是 Meta 的 MTP 训练目标（Gloeckle et al.，arXiv:2404.19737）：预训练时用多个额外输出头一次预测未来 n 个 token，推理时这些头直接当草稿器用——论文口径 4-token 预测推理快至 3×，且**大 batch 下依然有效**。DeepSeek-V3（arXiv:2412.19437）把单层 MTP 模块作为生产草稿器：第 2 个 token 的接受率 85–90%，TPS 提升 1.8×。意义在于草稿器从”推理时外挂”变成”预训练时内建”，接受率与成本的权衡被前移到训练期解决。

**并行块草稿**。DFlash（arXiv:2602.06036，UCSD Z Lab，2026-02）用块扩散模型一次前向并行生成整个 draft block，并用 KV Injection 把目标模型的隐特征注入草稿模型提精度——论文口径 5–6× 无损加速（DDTree 优化后 HumanEval 最高 8.22×），已接入 vLLM / SGLang / MLX。相比 EAGLE-3 的逐步自回归草稿，并行出块把草稿延迟与猜测长度解耦，但块内 token 间依赖弱（长草稿尾部接受率衰减）。DSpark 论文的横向口径很说明问题：在 Qwen3-4B/8B/14B 上，并行草稿（DFlash）的平均接受长度比自回归草稿（EAGLE-3）低 16–18%——**并行省了延迟，丢了接受率**。

**DSpark（DeepSeek × 北京大学，arXiv:2607.05147，2026-06 开源）**。两个设计直接回应上述矛盾：

- **半自回归生成**：并行骨干一次出一块的 logits，再挂一个轻量顺序头（Markov 头或 RNN 头）逐 token 注入前缀依赖，缓解”接受率随草稿长度衰减”——两层 DSpark 的接受长度超过五层并行模型（DFlash）；
- **置信度调度验证**：硬件感知的 prefix scheduler 按实时并发和 token 存活概率动态决定验证长度——GPU 空闲多验几个，峰值只验高置信前缀。这把”验证预算”从模型属性变成了调度变量，正是对 2.5 那堵墙的直接回应。

生产口径（DeepSeek-V4 线上，对比 MTP-1 基线，**均为特定 SLA 下的口径，不是普遍值**）：同吞吐下单用户生成速度 V4-Flash **+60–85%**、V4-Pro **+57–78%**；严格 SLA 下总吞吐 V4-Flash +51%（80 token/s/user）→ +661%（120 token/s/user），V4-Pro +52%（35）→ +406%（50）——后面这组”翻数倍”要理解为 MTP-1 在该 SLA 下已接近承载边界、DSpark 把原本达不到的区间打开了，而非常规场景普遍 6 倍。离线口径：Qwen3-4B/8B/14B 上较 EAGLE-3 接受长度 +26.7–30.9%、较 DFlash +16.3–18.4%。

**落地速度也是竞争力的一部分**。DSpark 是并行草稿家族里开源生态支持最顺的：vLLM 在 Kimi K3 发布时即 day-0 支持（2026-07），`--speculative-config` 里 `"method": "dspark"` 一行启用；草稿模型按 HuggingFace 兼容格式打包、vLLM 直接加载，Kimi K3 的 DSpark 草稿器单流实测 118→370 tok/s（SPEED Bench 口径，3.14×），其草稿按 MLA 原生布局与目标共享 KV 结构，便于接前缀缓存与 PD 分离等高级 KV 管理。

**EAGLE-4（2026-10 发布，附论文与代码）**。核心主张是”一个训练好的 drafter 通吃所有 batch”：eagle-harness 在运行时实测草稿与验证的真实成本，按当前 batch 和负载现场决定猜测树形（滑窗 draft 层、低秩候选头、append-only 草稿缓存）。论文口径（27B 级目标模型、4×B300）：单请求 863.8 vs 240.5 token/s（**3.59×**）；512 并发 28,340 vs 21,203 token/s（**1.34×**）——是目前公开数据里唯一在”单请求”和”满载”两个区间都对 vanilla 有正收益的方法。

**生产落地：DeepInfer（DeepSeek，2026-10 开源）**。DeepSeek 开源的内部推理框架（支撑 V4.1 Flash 大规模服务），把上面这些能力工程化：DSpark 式动态验证长度（较固定验 5 个 token 吞吐 +6%）、SWABoundedReplay（只回放最近 128 个 token 恢复滑窗缓存，输入阶段计算近乎减半）、PD 分离 + KV 复用。披露口径：单集群 155 万亿 token/天、平均约 0.4 s 出首 token、生成 230 token/s、单卡时收约 38 美元。

### 3.3 怎么选

- **有现成的同词表小模型**、显存吃得下：直接用独立草稿模型，最省事；
- **追求上限、能接受一次轻量训练**：EAGLE 系（特征级草稿，接受率与加速比通常最好，EAGLE-3 论文口径最高 6.5×）；
- **想最快落地、训练预算极小**：Medusa（几个小时单卡可训完，论文口径 2.2–3.6×）；
- **想用并行草稿又不想自己训**：vLLM Speculators 生态已放出多款预训练草稿模型（P-EAGLE / DFlash / DSpark），HuggingFace 格式直接加载，一行 `--speculative-config` 启用；
- **场景是摘要/代码/RAG、输出大量复述输入**：先试 n-gram，几乎零成本，常有不俗收益；
- **模型自带 MTP 模块**（如 DeepSeek-V3 系）：直接用原生 MTP 做草稿器，同源无损、无独立显存；
- **高并发生产服务**：优先选验证长度可随负载自适应的方法（DSpark 的置信度调度、EAGLE-4 的运行时树形），别用固定 γ——2.5 的实测已经证明固定参数在满载时可能反噬；
- **通用经验**：低 batch、延迟优先的交互服务优先上；高并发吞吐场景谨慎评估，且加速比数字必须连同测量时的并发档位一起看。

### 3.4 落地

- **框架支持**：vLLM 覆盖最全——独立草稿模型 / EAGLE 系 / Medusa / n-gram / MTP 之外，并行草稿三件套（P-EAGLE、DFlash、DSpark）已完整开源可用，草稿模型按 HuggingFace 兼容格式分发，`--speculative-config` 指定 `method` 即可加载；TensorRT-LLM（Medusa 等原生支持）、SGLang（DFlash、与 PD 分离联动）均有投机解码能力，不同版本成熟度以各自文档为准；EAGLE-4 发布即附带三个推理引擎插件；
- **训练侧**：DSpark/DFlash 类并行草稿器需要针对目标模型训练，这条路径已经工具化：vLLM 的 Speculators 库（[http://github.com/vllm-project/speculators](http://github.com/vllm-project/speculators)）统一了训练—打包—部署流程，训练侧用 TorchSpec 保证草稿推理与训练数值一致，产出的草稿模型 HuggingFace 兼容、vLLM 直接加载；HF 上的 Speculators Collection 已有多款预训练草稿模型（Qwen3-8B-P-EAGLE、Qwen3-30B-A3B-DFlash、gemma-4-31B-it-DSpark）可直接起步；DSpark 官方亦开源了训练评测代码库 DeepSpec（MIT）；
- **启用长这样（vLLM，示意，参数名与取值以官方文档为准）**：

```bash
vllm serve <target-model> \
  --speculative-config '{"model": "RedHatAI/gemma-4-31B-it-speculator.dspark",
                          "method": "dspark",
                          "num_speculative_tokens": 7}'
```

- **调什么**：草稿长度 γ 要对着实测接受率调——猜得长但接受率低，浪费的是验证算力；用了负载自适应方法后，这个参数部分交给调度器；
- **叠加关系**：与 KV Cache 量化、权重量化（W4A16/FP8）正交，可同时开；与 PD 分离也兼容（草稿发生在 decode 侧）。
