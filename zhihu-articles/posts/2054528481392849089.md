## 昇腾 A5 超节点底层设计逻辑评注

> 写作缘起：本文为对 2026-05-22 KADC2026 廖恒（华为公司 Fellow、半导体首席科学家）演讲《昇腾超节点底层设计逻辑和最佳实践》的研究性评注。原讲面向硬件与系统工程社区，从四项指标出发，逐次解释 A5 代次超节点的 Scale-Up/Scale-Out 双网设计、MoE Dispatch 的通信约束、内存语义与消息语义之辨、Agentic AI 对 KV cache 的拓扑冲击、UB 灵衢的弹性扩展机制与软件栈薄化方向。本文按演讲的论证主轴重排。

### 引言

昇腾 950 系列自 A3 代次起进入超节点形态，A5 代次”正进入大规模部署起点”（演讲原话），目前实际部署的是 1.6 万卡 Scale-Up + Scale-Out 混合系统，单超节点理论上限为 8192 卡。廖恒在演讲中提出一套围绕「四项指标 + 双层网络 + 内存语义」的设计逻辑，并将其映射到 MoE 推理、Agentic AI、KV cache 池化、CPU/存储弹性扩展等具体业务形态。

该演讲在工业界既有的「Scale-Up vs Scale-Out」「内存语义 vs 消息语义」「计算-通信流水」等讨论上，给出了三项与众不同的判断：

1. 国产单芯片规格的劣势在系统层由超节点尺寸弥补，互联能力直接决定超节点构建质量，是系统性能的一阶决定项；
2. Scale-Up 与 Scale-Out 网络在物理端口与交换路径上**必须彻底隔离**，抖动是一阶问题而非二阶问题；
3. 内存语义（LOAD/STORE）与消息语义（DMA/RDMA）的差异不仅在带宽，更在 IOPS 与软件路径开销，细粒度通信下两者性能数量级不同。

本文按演讲主干分十节展开论证与评注，最后一节归纳「已确证」「待验证」与「演讲未触及」三类判断，并附参考文献。

### 1. 四项指标的场景相关排序

### 1.1 演讲核心论断

AI 加速芯片的关键性能维度不止「算力」一项。算力之外，「HBM 带宽」「内存容量」「IO 互联带宽」三项与算力同等重要，且不同应用场景下四项指标的最佳比例显著不同。

### 1.2 演讲给出的场景-指标排序

| 场景 | 第一位 | 第二位 | 第三位 | 第四位 |
| --- | --- | --- | --- | --- |
| 训练 / 预训练 / 推理 prefill | 算力 | 内存容量 | 内存带宽 | IO 带宽 |
| 推理 decode | 内存带宽 | 内存容量 | 算力 | IO 带宽 |

decode 阶段算力降至第三位的原因在 LLM 推理工程内部已成共识：自回归生成每步需读取完整 KV cache，DRAM/HBM 带宽消耗远超矩阵乘法的算力消耗，TPOT (time per output token) 由 HBM 带宽下限决定。该结论可在 vLLM、SGLang、TensorRT-LLM 等推理引擎的 roofline 分析中复现。

### 1.3 体现在产品上的差异化

演讲中列出 A5 代次的 PR 与 DT 两种规格，明确二者 HBM 带宽与算力的比值 **265 vs 120** 用以区分使用场景：高 BW/FLOPS 比的 PR 偏向 decode-heavy 推理，低 BW/FLOPS 比的 DT 偏向训练与 prefill。

### 1.4 评注

四项指标的引入是合理的，但「场景四档」排序在算法侧并不完全静态。三项最近的演化使得该排序需要附加修订条款：

- **Speculative decoding** 把 decode 阶段的 token-per-step 从 1 提升到 4~8，逐渐把 decode 推回 compute-bound 区间；
- **MoE inference** 中 expert FFN 由于稀疏激活，单 token 实际算力远低于稠密模型，更进一步压低算力优先级；
- **长上下文 prefill** 实质是 decode 化的 prefill，对 KV cache 写入带宽与 attention compute 同时敏感，属于第五种「混合」场景。

### 2. 超节点域大小：延迟与覆盖的权衡

### 2.1 演讲核心论断

Scale-Up 域的物理大小不是越大越好。网络信号传播速度约 5 ns/m，每经一跳交换机引入额外接收-重发-转发延迟。Scale-Up 域大小本质是「延迟与覆盖范围」的权衡，并应优先按业务在极高带宽域所需的节点数量来选定。

### 2.2 演讲给出的物理参数与对应规模

| 项目 | A5 代次参数 |
| --- | --- |
| 单芯片单向 Scale-Up 带宽 | 3.2 TB/s |
| 单层交换最大节点数（NPO） | 512 |
| 两层 Scale-Up 最大节点数 | 8192 |
| Scale-Out 单接口带宽 | 400G / 800G |
| 两层 Scale-Out 最大节点数 | 16000 |
| 板内 8P full mesh 跳数 | 0 |
| 512 节点内跳数上限 | 1 |
| 8192 节点内跳数上限 | 2 |

### 2.3 跳数与可接受度的经验规则

演讲明确提出一条工程规则：

| 跳数 | 评价 |
| --- | --- |
| 0 | 最佳 |
| 1 | 不错 |
| 2 | 难受 |
| 3 | 不可接受 |

该规则尚未在公开演讲中给出严格的延迟数值与失败业务案例支撑。其工程含义是：在 EP 通信发起次数与节点规模 n 呈平方关系的负载下，跳数每增加一级，端到端 P99/P999 延迟方差随之放大，TPOT 的可控性恶化。

### 2.4 评注

按业务通信模式选择 Scale-Up 域大小是正确方向。演讲明示当前 MoE 推理（举例 DeepSeek V4 Pro）可以由 128/256/512 卡的单层 Scale-Up 覆盖。但有两项变量会改变该结论：

- **更大 expert 数的 MoE**（演讲提到 V4 Pro 之后路线）可能需要 EP 域进一步扩大，迫使 Scale-Up 转入两层；
- **训练侧 ZeRO-3 / FSDP** 的 all-gather 流量在大模型尺寸下也会沿 Scale-Up 域聚集，与 EP 流量竞争同一物理网络。

### 2.5 一手部署事实

演讲压轴明确给出当前实际部署的 1.6 万卡混合系统参数：**Scale-Up 选择 128 卡规模，配合两层 UB 交换网络构成 Scale-Out 16000 卡覆盖范围**。该选择与上文”对延迟极敏感的负载放在单层交换范围内”的工程主张一致：在 8000~8192 卡两层 Scale-Up 与 128 卡单层 Scale-Up 之间，工程实际落点偏向后者，单层单跳的延迟可控性在 1 毫秒 TPOT 目标下优先于覆盖范围。

### 3. MoE Dispatch 的 O(n²) 消息复杂度

### 3.1 演讲核心论断

MoE 模型每层包含一次 dispatch（attention worker 按 top-K 路由把 token 多播到 expert）与一次 combine（expert 结果回送）。Dispatch 在超节点内呈类 All-to-All 的多对多通信，**单包粒度仅 7~14 KB，通信发起次数与 EP worker 数 n 呈平方关系 O(n²)**。这种”细粒度、低延迟、高带宽、平方扩展”的通信模式给 SU 设计带来主要压力。

### 3.2 复杂度的来源

| 元素 | 含义（演讲依据） |
| --- | --- |
| n | EP 域内 worker 数 |
| K | 每 token 选中的 expert 数（演讲未给具体值，业界 MoE 实现常见个位数） |
| 单次 dispatch 总消息数 | O(n²)，每对 (src, dst) 均可能有消息 |
| 单条消息大小 | 演讲明示 7~14 KB，由 token hidden dim × dtype 决定 |

n 较大时，平方复杂度的细粒度并发挤压交换机 buffer 与 NIC PPS 能力，基于 ECN 的反馈算法在 micro-burst 下频繁触发降速，进一步抬高尾延迟。

### 3.3 演讲给出的工程后果

- TPOT 目标在 Agent 时代被推向 10 ms → 5 ms → 1 ms 以下的量级；
- 单用户每小时模型调用频次较对话式 AI 提升 50~100 倍，可达 100 次以上；
- 单次 Agent 指令可能触发数百次模型调用，TPOT 直接换算为用户等待时间。

### 3.4 评注

把 dispatch 标记为 O(n²) 是准确的工程刻画，但有一处需要补充：实际 MoE 部署中 EP_size 通常不随集群规模线性扩展。例如 DeepSeek-V3 的 EP_size = 64，无论部署在 1024 卡还是 8192 卡集群中，dispatch 的真实消息复杂度都是 O(64²) = 4096，而非随集群线性平方。换言之，O(n²) 的”n”指的是 EP 维度而非超节点维度，演讲在引导工程师正确直觉，但术语精度上需要明确”n = EP_size”而非”n = 超节点 NPU 数”。

### 4. 内存语义与消息语义的辨析：被忽略的 IOPS 维度

### 4.1 演讲核心论断

LOAD/STORE（内存语义）与 DMA/RDMA（消息语义）即使跑在同一物理网络、理论带宽相同，实际性能差异巨大。差异主要不在带宽而在两项被工业界长期低估的指标：**IOPS**（每秒可发起的通信请求次数）与**软件路径开销**（处理器发起一次通信消耗的指令数）。

### 4.2 三项关键指标的量纲对比

演讲给出的核心数据如下：

| 指标 | 超高性能 RDMA NIC | NVMe SSD | A5 LOAD/STORE | A5 DMA |
| --- | --- | --- | --- | --- |
| IOPS (次/秒) | 数千万 | 百万级 | 4 亿 | 1 亿（顶配） |
| 发起单次通信指令数 | — | — | 1（单周期） | ~2000 |

DMA 发起开销的约 2000 条指令拆分为：填充 64 字节描述符、写入提交队列、处理完成消息（completion）三部分。LOAD/STORE 由处理器一条指令单周期发出，无描述符、无队列、无 completion 后处理。两者的软件延迟差距由此呈数量级差异。

### 4.3 与通信粒度的耦合

IOPS 的优势在大粒度通信下被淹没，在细粒度通信下被放大。粒度边界来自带宽除以单次数据量。下表以 100 GB/s 单链路带宽为示意基准，演讲给出的 MoE dispatch 单包尺寸（7~14 KB）与 Flash 类模型单包尺寸（4 KB）落入 10⁷ 量级以上的 IOPS 需求区间：

| 单次数据量 | 维持 100 GB/s 带宽所需 IOPS（示意） |
| --- | --- |
| 1 MB | 10 万 |
| 64 KB | 1.6 百万 |
| 7 KB（MoE dispatch 单包） | 14 百万 |
| 4 KB（Flash MoE） | 25 百万 |

细粒度通信的 IOPS 需求超出现役 RDMA NIC 数千万级的能力上限，演讲据此判定该类通信必须以内存语义承担。

### 4.4 评注

把 IOPS 与软件指令数引入 AI 通信讨论是这次演讲最有工程价值的一处校正。RDMA 文献几十年来以”带宽 + RTT”两维度刻画网络，IOPS 仅在存储领域被严肃对待。MoE/Agent 时代的细粒度通信第一次把 IOPS 推到与带宽同等的位置。

但内存语义并非无代价。LOAD/STORE 会阻塞处理器流水线（必须等远端响应），而 DMA 提交后可异步释放处理器。演讲给出的最终建议是分场景使用：单次数据量越小越倾向 LOAD/STORE；颗粒度较大时使用 DMA 以避免阻塞 NPU；中间区间由 batch size 与延迟要求权衡。演讲未给两者的具体粒度切换阈值。

### 5. SU 与 SO 网络的物理隔离：抖动作为一阶问题

### 5.1 演讲核心论断

Scale-Up 网络与 Scale-Out 网络在 A5 上做了”**物理端口与交换路径的彻底隔离**“，即使地址层面可联通也不复用同一物理网络。理由是抖动对业务性能的影响巨大，而抖动的根本来源是不同业务流路径重叠导致的瞬态拥塞。

### 5.2 隔离的具体内容

| 维度 | A5 处理方式 |
| --- | --- |
| 物理端口 | SU/SO 端口分离 |
| 交换路径 | SU/SO 交换芯片分离 |
| 多路径策略 | SU 网络在极低延迟场景回退到单路径，放弃 ECMP 与硬件自适应路由 |
| 流量类型 | SU 承担 EP dispatch/combine；SO 承担 prefill / KV cache / PP / DP |

### 5.3 抖动的物理来源

抖动的本质是消息延迟概率分布的方差。方差的主导成因有三：

1. 不同业务流路径重叠产生瞬态拥塞（演讲明示）；
2. 多路径 ECMP 在小消息下因不相干数据包路径冲突放大方差（演讲明示）；
3. 交换机 buffer 在 micro-burst 下进入 PFC/ECN 反馈环（学界共识）。

A5 用物理隔离消除第一项、用回退单路径消除第二项、用 UB CTP 的链路级重传应对第三项。

### 5.4 评注

「抖动是一阶问题」这一判断在 AI 训练与推理系统中已有共识，但**为消除抖动而牺牲多路径 ECMP** 是较激进的工程决定。多路径的物理价值在于失效弹性与吞吐弹性，单路径回退意味着 A5 在「极低延迟」场景下放弃这两项弹性，依赖 UB CTP 的快速重传与上层 IO retry 承担可靠性保障。

该选择隐含一项前提：SU 网络的链路与交换芯片 MTBF 足够高，且 IO retry 的成本可接受。该前提在 SU 域规模上限（8192 卡）下是否仍成立，是 A5 大规模运行后值得长期观察的可靠性指标。

反证：若多路径在所有场景下均优，A5 不会保留单路径回退选项。同一硬件保留两条路径意味着工程界尚未对”小消息低延迟下的最优路径策略”形成统一答案。

### 6. Agentic AI 重塑 KV Cache 拓扑

### 6.1 演讲核心论断

Agentic AI 把 KV cache 的工程拓扑从 DRAM 池化推向 SSD 直连。原因是演讲明示的两项业务参数量级跃迁：

| 参数 | Chatbot 时代 | Agent 时代 |
| --- | --- | --- |
| 单用户每小时模型调用次数 | 对话式 AI 量级 | 100+ 次（提升 50~100 倍） |
| 序列长度 | 4 K | 接近 1 M（提升约 250 倍） |
| KV cache 命中率 | — | 95% 以上（演讲明示） |
| 单会话 KV cache 容量 | — | 与序列长度同阶放大约 250 倍 |

命中率上升的工程含义是 prefill 阶段重算成本下降，但保留下来的 KV cache 必须长期驻留以保证下一轮命中；叠加序列长度跃迁，**KV cache 总容量**与单次驻留时间同步放大，DRAM 池化方案在成本与容量上无法承载，迫使存储介质下沉到 SSD。

### 6.2 传统路径的瓶颈

演讲给出的传统分布式 KV cache 数据路径需依次经过存储服务器 CPU、DDR、网卡，再到 AI 服务器网卡、DDR，最后拷入 NPU 的 HBM。每一段均引入额外延迟与带宽损失，多 NPU 同时取回 KV cache 时存储侧网卡成为收敛点。

### 6.3 A5 的 SSU 方案

SSU（UB-attached SSD）以 UB 端口直挂 Scale-Out 网络，跳过存储机头、文件系统、网卡中转。NPU 经 UB 读写 SSU，数据直传 HBM。

| 维度 | 传统分布式 KV cache | SSU 直挂方案 |
| --- | --- | --- |
| 数据路径 | 存储 CPU/DDR/NIC + AI 服务器 NIC/DDR 多重中转 | NPU 经 UB 直读 SSU |
| 单 NPU 可用带宽 | 受网卡收敛限制 | 受 SSD/UB 限制（演讲：至少提升一个数量级） |
| 文件系统介入 | 是 | 否 |
| 介质 retention | 多年量级 | 1~2 小时量级 |
| SSD 寿命换取项 | 长 retention | 短 retention 换显著寿命提升 |

### 6.4 评注

KV cache 介质下沉 SSD 的方向并非 A5 独有，业界已有多条路径将 NVMe 与 GPU/加速器直连以承担 KV cache 持久化。但 **SSU 直挂 UB** 在工程上有两项独特之处：

1. **绕过文件系统**：演讲明确说”去掉存储机头和文件系统”，意味着 SSU 直接呈现块或区域语义给 NPU，路径短但需 NPU 侧承担一致性与索引管理；
2. **短 retention 换 SSD 寿命**：将 SSD 物理特性（write amplification 与 P/E cycle）暴露给系统设计，是对 Agent 时代 KV cache 1~2 小时寿命这一业务特征的针对性优化。

但有两项假设需要长期检验：

- **95% 命中率是否可持续**：演讲列举的高命中率场景来自 AI 辅助编程类 Agent（演讲明示举例 Cursor、Claude Code），其 KV cache 重用模式与对话式 AI 显著不同。其他 Agent 类型（搜索 Agent、工具 Agent、多模态 Agent）的命中率分布尚无公开数据；
- **去文件系统的运维代价**：分布式存储的文件系统抽象同时承担命名空间、配额、快照、故障迁移等功能，SSU 方案需要在 NPU 侧或上层调度器重建这些机制，否则规模化运维风险显著。

反证：若 SSU 在所有场景下完胜分布式 KV cache，演讲不会保留”用 SO 网络连接 SSU 节点”而非”用 SU 网络紧耦合 SSU”的设计。SSU 接入 SO 而非 SU 恰恰说明 SSU 的延迟需求不是极致紧耦合级别，分布式 KV cache 与 SSU 是不同业务的不同最优解。

### 7. UB 灵衢的弹性扩展：Scale-Out 承担 90% 扩容诉求

### 7.1 演讲核心论断

硬件整机一旦量产，资源配比就不能随便改，但 AI 业务持续演化对 CPU / DDR / SSU 比例提出多变要求。UB 灵衢总线通过对所有节点（NPU、CPU、SSU）暴露统一的 Scale-Up 与 Scale-Out 双层接入能力，提供物理层的弹性扩展机制。

### 7.2 扩展位置的两档选择

| 接入位置 | 带宽 | 延迟 | 经济性 | 扩容范围 |
| --- | --- | --- | --- | --- |
| Scale-Up 域 | 3.2 TB/s | 极低 | 昂贵 | 受 SU 域大小约束 |
| Scale-Out 域 | 400G / 800G | 中等 | 经济 | 大 |

### 7.3 演讲的工程判断

演讲明示：”**到目前为止几乎没看到非连到 Scale-Up 域不可的扩容诉求，90% 以上的情况在 Scale-Out 里就足够**“。其论证逻辑是：AI 系统绝大多数软件与业务系统天然存在模块化与分层解耦，CPU 与 NPU 之间是相对松耦合的；只有延迟要求极低且带宽要求达 3.2 T 级别才需要进入 Scale-Up 域。

### 7.4 评注

「90% 走 SO」是一个未公开统计基础的工程经验值，但其推论结构是健康的：紧耦合资源的稀缺性应当被显式定价，扩容时倾向经济型 SO 通道有利于系统经济性。这与 NVIDIA Grace Hopper 把 CPU-GPU 紧耦合至 NVLink-C2C、其他 CPU 经 PCIe 接入的设计哲学相一致——紧耦合资源面向延迟敏感型负载保留，普适资源使用经济型互联。

但有两类业务可能挑战该判断：

- **CPU 卸载式 attention**：将部分 KV cache 或 attention 计算放到 host 侧执行，需要 CPU 与 NPU 之间高带宽低延迟数据流动，可能进入 SU 需求；
- **GraphRAG / 向量数据库**：CPU 内存中数十亿条 embedding 与 NPU 高频交互，带宽与延迟均较敏感。

反证：90% 的统计来自 2026 年时点的业务画像。Agent 时代每 6 个月有新的负载形态涌现，该比例需要随业务演化持续校准。

### 8. UB 工作模式的选择：TP、CTP 与 URMA DMA

### 8.1 演讲核心论断

UB 总线提供多种工作模式，演讲针对 Dispatch-Combine 给出明确的选择规则：

| 模式 | 全称 | 适用场景 | 关键特性 |
| --- | --- | --- | --- |
| UB TP | Transport Protocol（可靠传输） | SO 网络 | 链路级 + 端到端可靠性双重保障 |
| UB CTP | Compact Transport（轻量级传输） | SU 网络 | 仅链路级重传；端到端故障 IO retry；无保序 |
| UB URMA DMA | One-sided remote memory access | 大块数据 | 异步、不阻塞 NPU |
| UB LOAD/STORE | 内存语义 | 细粒度、低延迟 | 同步、低软件开销 |

### 8.2 选择规则

| 通信模式 | 推荐 UB 模式 | 原因（演讲依据） |
| --- | --- | --- |
| Dispatch-Combine（小 batch 低延迟） | LOAD/STORE | 单包仅 7~14 KB，IOPS 需求极高 |
| Dispatch-Combine（大 batch 高 BW） | URMA DMA | 异步释放 NPU |
| Dispatch-Combine | 不适合 CTP | CTP 无保序，跨 MTU send/receive 难按序拼接 |
| Dispatch-Combine | 不适合 TP | 端到端可靠性保障开销过大 |

KV cache 跨节点搬运与 EP allreduce/allgather 等大块通信路径的具体模式选择，演讲未明确，本文不再外推。

### 8.3 评注

UB CTP 的「**无保序 + 链路级重传 + 整 IO retry**」三件套是工程上有意义的折中。无保序避免了 reorder buffer 与重组逻辑，链路级重传避免了端到端重传的协议开销，整 IO retry 把可靠性责任推到上层算法。该折中假设 SU 网络故障概率极低（演讲明示），上层 IO retry 成本可接受。

该假设在万卡量级 A5 部署下的实测故障概率与 retry 成本，是判断 UB CTP 工程合理性的核心数据，但演讲未给出量化结果。

### 9. 软件栈的厚薄两面性与 1 ms TPOT 目标

### 9.1 演讲核心论断

软件兼容性与执行效率呈反比关系。兼容性越好的软件栈引入越多适配层，单次推理的软件开销随之放大。在 1 ms 量级的极致推理系统中，传统厚重软件栈无法承担。

### 9.2 演讲给出的核心论据

演讲明示：在 1 毫秒级推理系统中，传统厚重软件栈”光是这个开销就不可能达到一到两个数量级的推理延迟下降”。该论断仅约束软件开销与 TPOT 之间的数量级关系，未给单次推理软件开销的具体微秒数。

| 指标 | 厚软件栈 | 薄软件栈目标 |
| --- | --- | --- |
| 单次推理软件开销 | 决定厚重软件栈不可承担 1 ms TPOT 的量级 | 数量级压缩 |
| TPOT 下限 | 数十 ms 级别（业界常见） | 1 ms 以下（演讲明示） |
| 调用频次（每用户/小时） | 对话式 AI 量级 | 100+ 次（演讲明示） |

### 9.3 演讲给出的演进方向

| 方向 | 内容 |
| --- | --- |
| 补短板 | CANN 层次努力补齐与行业生态的差距 |
| 探新路径 | 简化软件，化简过去仰仗的多层抽象 |
| 共存状态 | 厚生态与薄高性能在同一系统并行演进 |

### 9.4 评注

「软件越厚效率越低」是工程界长期共识，但 1 ms TPOT 是否要求软件栈薄化至**单一垂直整合**，是 A5 代次最具争议的工程判断之一。竞争性观点有三：

1. **生态厚度优先**：保留主流框架与生态层次，通过 fused kernel、图捕获、AOT 编译等手段把热路径压薄；
2. **Tile-level DSL 路线**：在中间层引入面向硬件的瓦片级 DSL，框架仍然厚但 kernel 直接编译到硬件；
3. **A5 演讲指向的路线**：将 device-initiated UB 内存语义原语（LOAD/STORE 等）下沉至 kernel 内指令级别，取代部分图层集合通信。

三条路线指向同一个目标——通信粒度下降、控制流下沉到 device，但对软件生态的兼容性策略不同。A5 路线是三者中较激进的一档，其成败取决于 CANN 与昇腾上的 kernel DSL 生态对外部模型代码的覆盖度。

反证：若薄软件栈在所有场景下均优，A5 不会同时强调”补 CANN 短板”与”简化软件”。同时推进两个方向意味着两类业务（兼容性优先 vs 性能优先）将长期共存于昇腾生态。

### 10. 已确证、待验证与演讲未触及

### 10.1 三类判断的分层

| 类别 | 判断 |
| --- | --- |
| 已确证 | 四项指标场景相关；MoE Dispatch 是 EP 域内 O(EP²) 细粒度通信；LOAD/STORE 与 DMA 在 IOPS 与软件路径开销上存在数量级差异；网络抖动是 AI 业务一阶问题；KV cache 总容量随 Agent 时代序列长度同步放大 |
| 待验证 | 「跳数 0/1/2/3 不可接受」的具体延迟边界；SU 单路径回退在 8192 卡量级的故障弹性；Agentic KV cache 95% 命中率的可持续性；90% 扩容走 SO 在新业务下的稳定性；UB CTP 整 IO retry 的工程代价 |
| 演讲未触及 | 光电路交换在大型 Scale-Out 中的潜力；网内计算（SHARP 类）在 EP allreduce 中的作用；CXL.mem 与 UB.mem 在协议层的差异化定位；MoE expert parallelism 与 sequence parallelism 在 A5 上的混合编排 |

### 10.2 演讲的工程方法论

抛开具体技术判断，该演讲展示了一套清晰的工程方法论：

1. **指标先于产品**：用四项指标 + 场景排序作为讨论起点，避免陷入”算力数字大小”之争；
2. **物理约束优先**：用光速、跳数延迟、IOPS 等物理量约束设计选择，避免软件目标脱离硬件可能；
3. **场景驱动配比**：每一处设计取舍都映射到具体业务（MoE Dispatch、Agentic KV cache、扩容场景），避免空对空；
4. **保留备选路径**：对每一项主张都保留备选项（SU 内单路径回退、DMA 与 LOAD/STORE 并存、SO 与 SU 同时挂 SSU），承认工程不是单选题。

### 10.3 评注的元判断

演讲的核心元判断是：**国产 AI 加速器的竞争力不在单芯片规格，而在超节点尺寸 × 单芯片规格的乘积**。这一判断把竞争焦点从「制程与算力」转向「互联与系统」，与海外厂商近年来强调 scale-up 互联（NVLink、NVLink-C2C 等）以承载大模型并行的整体方向呈现相似指向，但论证路径截然不同：NVIDIA 沿 NVLink 路径加深紧耦合，华为沿 UB 灵衢路径同时铺开 SU 与 SO 双层网络。

两条路径的长期收敛点尚不可见。但可以确定的是，单芯片军备竞赛在 AI 时代已不是最重要的轴线——这是演讲在 KADC2026 这个时间点最有公共价值的判断。

---

### 11. 结论

A5 代次超节点设计逻辑的核心是「**四项指标场景化 + 双层网络物理隔离 + 内存语义补足消息语义 + 业务驱动弹性扩展**」四条主线。每一条都映射到具体的工程证据与业务场景，每一条都保留备选路径。演讲展现的是一套以物理约束为底、以业务画像为面、以工程取舍为骨的体系结构方法论。

国产 AI 加速器在单芯片规格上的相对劣势，被 Scale-Up 单超节点 8192 卡上限 + Scale-Out 16000 卡覆盖范围的双层网络在系统层吸收（当前实际部署 1.6 万卡混合系统，单层 Scale-Up 选用 128 卡规模）。互联能力替代算力规格，成为系统性能的一阶决定项。这一判断是否能够在生产环境长期成立，取决于 UB CTP 在大规模下的可靠性、SSU 方案在多类 Agent 业务下的命中率、以及 CANN 与昇腾 kernel DSL 生态对外部模型代码的覆盖度。三项前提至少在 2026 年时点尚未给出公开量化结果，构成 A5 代次进入大规模部署后最值得长期跟踪的工程指标。
