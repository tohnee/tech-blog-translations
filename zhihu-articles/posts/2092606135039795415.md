最近在系统学习大模型推理优化，这一篇记录 PagedAttention 的核心原理，主要参考 DefTruth 的技术文章、vLLM 原论文以及官方文档。

之前已经了解了 Transformer 的 Prefill、Decode 和 KV Cache。这次重点搞懂：为什么 KV Cache 要分页？Block Table 如何映射？调度器如何管理 KV Block？

## 一、为什么需要 PagedAttention？

首先，回顾 KV Cache 的作用。

在自回归推理过程中，模型每次生成新 Token，都需要利用历史 Token 对应的 Key 和 Value 计算 Attention。

如果每生成一个 Token 都重新计算历史 K、V，会产生大量重复计算，因此推理引擎会把历史 K、V 缓存在显存中。

问题在于：**KV Cache 会随着序列长度增长，而且不同请求的长度往往无法提前确定。**

对于一个普通 Transformer 模型，其 KV Cache 显存占用可以近似表示为：

[<br>M_{KV}=2\times L\times S\times H_{KV}\times D\times b<br>]

其中：

- (L)：Transformer 层数
- (S)：序列长度
- (H_{KV})：KV Head 数量
- (D)：每个 Head 的维度
- (b)：每个元素的字节数（FP16 通常为 2）
- 乘 2：同时保存 K 和 V

假设一个模型有 32 层、8 个 KV Heads、Head Dimension 为 128，使用 FP16 精度。

当序列长度为 8192 时，单个请求的 KV Cache 就需要约 **1 GiB 显存**。

当并发请求不断增加时，KV Cache 会成为限制推理系统吞吐量的重要因素。

### 传统连续显存分配有什么问题？

假设系统最多允许生成 2048 个 Token，为了保证一个请求能够正常执行，传统方案可能提前预留很大的连续 KV Cache 空间。

但实际上，这个请求也许只生成了 100 个 Token 就结束了。

由此出现三类浪费：

1. **预留浪费（Reserved Memory）**：为未来可能生成、但尚未生成的 Token 提前预留显存。
2. **内部碎片（Internal Fragmentation）**：分配空间的实际使用量小于容量，产生无法有效利用的空余部分。
3. **外部碎片（External Fragmentation）**：不同请求频繁申请和释放连续显存，形成分散的空闲区域，难以满足较大的连续分配需求。

问题的本质不只是 KV Cache 占用大，而是 **动态增长的 KV Cache 很难通过连续显存分配实现高效管理。**

## 二、PagedAttention 的核心思想：借鉴操作系统分页

PagedAttention 最巧妙的设计，就是借鉴操作系统中的虚拟内存分页机制。

操作系统会把虚拟地址空间划分为固定大小的 Page，再通过页表映射到实际物理内存。

PagedAttention 采用类似思想：

**把一条逻辑上连续的 KV Cache 序列切分成固定大小的 KV Block，再通过 Block Table 映射到不连续的物理显存。**

需要区分三个概念：

| 概念 | 作用 |
| --- | --- |
| Logical Block | 请求视角下，按照 Token 顺序组织的逻辑块 |
| Physical Block | GPU 显存中真正存储 K、V 数据的物理块 |
| Block Table | 维护逻辑块到物理块的映射关系 |

假设 Block Size = 4，即每个 KV Block 可以存储 4 个 Token 的 KV 数据。

一个请求已经拥有 10 个 Token：

- Logical Block 0：Token 0～3
- Logical Block 1：Token 4～7
- Logical Block 2：Token 8～9

系统只需要为它分配 3 个 Physical Blocks。

其中最后一个 Block 仅填充了 2 个位置，还空余 2 个位置。

**关键是：这三个 Physical Blocks 不需要在物理显存中连续。**

### Block Table 如何映射？

假设 Block Table 为：

| Logical Block | Physical Block |
| --- | --- |
| 0 | 7 |
| 1 | 2 |
| 2 | 9 |

这代表一个请求逻辑上的三个连续 Block，实际上存放在 GPU 的 Physical Block 7、2、9 中。

如果现在需要访问 Token 9：

逻辑块编号：

[<br>9 // 4 = 2<br>]

块内偏移：

[<br>9 \bmod 4 = 1<br>]

通过 Block Table：

[<br>LogicalBlock[2]\rightarrow PhysicalBlock[9]<br>]

所以 Token 9 对应的数据位于 Physical Block 9 的块内偏移 1 处。

这样，推理引擎无需要求整条序列在 GPU 显存中连续存储。

### 为什么可以减少显存碎片？

因为 KV Cache 不再需要提前申请一大片连续空间，而是可以随着序列增长按需分配。

对于普通的固定大小 Block 管理方式，一个序列最后最多只会出现 (B-1) 个未使用的 Token Slot，其中 (B) 为 Block Size。

例如 B=4，序列长度为 10，就只浪费 2 个 Slot。

外部碎片也大幅减少，因为任意可用 Physical Block 都可以分配给请求使用。

但需要注意：PagedAttention 并不意味着显存完全没有浪费。最后一个 Block 仍可能产生内部碎片，Block Table 和管理结构也有额外开销。

## 三、PagedAttention 如何完成 Attention 计算？

这个问题也很重要。

传统 Attention 可以直接读取逻辑上连续排列的 K、V 数据。

但 PagedAttention 的 KV Cache 分散在不同 Physical Blocks 中，因此 Attention Kernel 需要根据 Block Table 找到对应的数据位置。

大致流程是：

1. 根据当前请求找到对应的 Block Table。
2. 获取需要访问的 Physical Block ID。
3. 根据物理地址和块内偏移读取 K、V。
4. 计算 Query 与历史 Keys 的相似度。
5. 完成 Softmax 和对 Values 的加权求和。

这里需要强调：

**PagedAttention 改变的是 KV Cache 的物理存储布局和访问方式，而不是标准 Attention 的数学定义。**

在原论文的实现中，它仍然可以计算精确 Attention，并没有因为分页而主动丢弃历史 Token。

当然，增加 Block Table 查找和非连续内存访问并不是零成本，Kernel 需要专门优化访存与线程组织。

这也是为什么 PagedAttention 不仅涉及内存管理，还涉及 CUDA Kernel 设计。

## 四、vLLM 调度器如何管理 KV Block？

PagedAttention 提供分页访问能力，但具体什么时候申请、释放和共享 Block，还需要 KV Cache Manager 与 Scheduler 协同完成。

### 1. Prefill 阶段：申请所需 Block

假设用户输入的 Prompt 有 100 个 Token，Block Size=16。

系统需要：

[<br>\lceil100/16\rceil=7<br>]

也就是 7 个 KV Blocks。

在完成相应 Prefill 计算后，Prompt 的 KV Cache 会被保存到这些物理块中。

实际系统还可能结合 Chunked Prefill、Prefix Cache 命中情况进行分配，并非所有实现都要求一次处理完整 Prompt。

### 2. Decode 阶段：KV Cache 动态增长

随着 Decode 继续进行，新产生的 Token 需要保存对应 KV。

如果当前最后一个 KV Block 还有空间，就继续写入当前 Block。

如果空间不足，就申请一个新的 Physical Block，并更新 Block Table。

因此，KV Cache 的物理空间可以随着推理逐渐增长，无需预留整个最大生成长度。

### 3. 请求完成：释放 Block

请求结束后，系统会解除该请求对 KV Blocks 的占用。

如果 Block 没有其他请求引用，它可以重新变成可分配资源。

但如果开启 Prefix Caching，系统也可能保留部分已经计算好的 KV 内容，等待未来请求复用，而不是立刻清除缓存数据。

### 4. 显存不足：请求抢占与恢复

当 GPU 中没有足够的 KV Blocks 时，调度器可能无法继续接纳或者执行所有请求。

这时可能需要进行请求抢占（Preemption）。

原论文讨论了两种恢复方式：

- **Swap**：将部分请求的 KV Cache 换出到 CPU 内存，之后再恢复。
- **Recompute**：放弃部分已有 KV Cache，等请求恢复执行时重新计算。

这两种方式存在不同成本：Swap 需要数据传输，Recompute 需要重复计算。

不同版本 vLLM 的抢占与缓存实现会有所变化，不能把原论文机制直接当成所有最新版本的运行逻辑。

## 五、PagedAttention 如何实现 KV Cache 共享？

这是我认为 PagedAttention 非常重要的另一个价值。

假设有两个请求：

- Request A：相同系统提示词 + 问题 A
- Request B：相同系统提示词 + 问题 B

如果前面存在完全相同、可复用的 Token 前缀，并且缓存条件一致，那么这部分 KV Cache 没必要重复计算和存储。

传统方式可能为两个请求分别保存相同的 KV。

PagedAttention 允许两个请求的 Logical Blocks 指向同一个 Physical Block。

**一份物理 KV 数据可以被多个请求引用。**

### 引用计数（Reference Count）

系统通过引用计数等信息追踪 Physical Block 的使用情况。

例如 Physical Block 5 同时被两个请求引用：

[<br>refcount(Block5)=2<br>]

如果 Request A 结束，引用计数下降为 1。

此时 Request B 还在使用该数据，所以 Block 5 不能被随意覆盖。

这和操作系统中共享内存页的管理思路非常类似。

### 写时复制（Copy-on-Write）

如果两个请求共享同一个 Block，但其中一个请求需要修改这个共享 Block，就不能直接覆盖原数据。

否则会影响另一个请求。

解决方法是 Copy-on-Write（COW）：

1. 检查 Block 是否被多个请求共享。
2. 如果需要修改共享数据，则为当前请求申请新的 Physical Block。
3. 将必要的旧数据复制过去。
4. 当前请求修改自己的 Block，另一个请求继续使用旧 Block。

通过这种方式，可以在保证数据正确性的前提下减少重复存储。

这一思想可以用于 Parallel Sampling、Beam Search 等具有共享前缀的场景。

另外，现代 vLLM 的 Automatic Prefix Caching 通常会利用包含历史前缀信息的 Block Hash 查找可复用的 KV Block，因此判断共享不能只比较某个 Block 内部的 Token 是否相同。

## 六、Block Size 为什么不能越小越好？

最初我觉得，Block Size 越小，最后一个 Block 的空间浪费就越少，应该是更好的选择。

但是 Block Size 其实涉及性能权衡。

**Block Size 太小：**

- Block 数量增多，映射和管理成本增加。
- GPU Kernel 可能需要处理更多小块访问。
- 访存效率和线程利用率可能受到影响。

**Block Size 太大：**

- 最后一个 Block 的内部碎片增多。
- 对较短的序列可能造成明显浪费。
- 共享与分配的粒度变粗，降低灵活性。

所以 Block Size 的选择需要综合考虑显存利用率、Attention Kernel 的访存效率与运行时管理开销。

原论文研究了不同 Block Size 对性能的影响，不能简单认为块越小越好。

## 七、PagedAttention 与 FlashAttention 有什么区别？

这两个概念非常容易混淆，但它们优化的问题并不相同。

| 技术 | 主要解决的问题 |
| --- | --- |
| FlashAttention | 减少 Attention 计算过程中的不必要 HBM 数据读写，改善 IO 效率 |
| PagedAttention | 改善 KV Cache 的存储管理、动态分配和共享 |

FlashAttention 侧重 Attention Kernel 的计算和访存效率。

PagedAttention 侧重 KV Cache 的内存布局与管理，同时需要对应的高效 Attention Kernel。

它们不是互斥的优化思路，实际推理系统可以结合分块计算与分页 KV Cache 管理。

另外，也不能把减少显存浪费直接理解成减少 Attention 计算量。

**PagedAttention 的主要吞吐收益来自更高效的显存利用和更强的并发服务能力。**

原论文报告，在对应实验设置中，vLLM 相比当时的代表性基线系统实现了约 2～4 倍吞吐提升，且保持相近延迟。这是特定模型、硬件和工作负载下的实验结果，并不意味着任何部署都能稳定提升 2～4 倍。

## 八、最后总结：我真正学到了什么？

这一轮学习下来，我觉得需要建立以下几个认识：

1. KV Cache 的核心困难不仅是容量大，更在于请求长度不确定、动态增长和并发竞争。
2. PagedAttention 借鉴了操作系统分页思想，通过 Block Table 把逻辑顺序与物理显存位置解耦。
3. Physical Blocks 不需要连续，从而支持 KV Cache 按需分配，减少碎片与预留浪费。
4. 多个请求可以共享相同前缀的 KV Blocks，引用计数和写时复制保证数据管理正确。
5. Scheduler 和 KV Cache Manager 需要共同解决 Block 分配、回收、缓存复用与显存不足时的抢占问题。
6. PagedAttention 是一项系统级优化：显存管理、请求调度和 GPU Attention Kernel 之间需要协同。

**一句话总结：PagedAttention 把操作系统的分页内存管理思想应用到 LLM KV Cache，使推理系统不再依赖大块连续显存分配，从而支持更灵活的缓存管理、更高的内存利用率和更好的并发吞吐。**
