## 为什么需要推理引擎

这样的方式也可以推理？

```text
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM

model_name = "Qwen/Qwen2.5-0.5B-Instruct"

tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(
    model_name,
    torch_dtype="auto",
    device_map="auto",
)

prompt = "请简单介绍一下 Transformer。"
inputs = tokenizer(prompt, return_tensors="pt").to(model.device)

model.eval()
with torch.inference_mode():
    output_ids = model.generate(
        **inputs,
        max_new_tokens=100,
        do_sample=False,
        use_cache=True,
    )

# generate 返回“输入 token + 新生成 token”，这里只截取新生成部分
new_token_ids = output_ids[:, inputs["input_ids"].shape[1]:]
response = tokenizer.batch_decode(
    new_token_ids,
    skip_special_tokens=True,
)[0]

print(response)
```

但这种方式会面临如下问题：

1. 如何处理来自不同用户的高并发请求？
2. 资源利用率如何维持较高水平，最大化吞吐？
3. 如何在高并发，长序列场景下推理时避免 GPU OOM？

## vLLM Framework

为了解决通用深度学习框架中存在的不足，vLLM设计了几个关键模块：

1. API server + Scheduler，用于解决多请求之间的调度协同问题；
2. KV cache manager，系统地管理 KV cache 内存资源。
3. Model runner，完成模型的计算，涉及分布式计算。

![](https://pic4.zhimg.com/v2-fd8c4d91940fedd2bec68116fc4b05b9_r.jpg)

这里面除了 Model runner 的框都是 cpu 任务，且每个cpu 框的 cpu 需求量都不完全相同。如果每一个框之间都是串行阻塞执行，那在执行 model runner 这个非常耗时的操作时，cpu需要等待较长时间，cpu资源就被浪费了。实际上这个框图会被设计为几个异步的程序执行，进程与进程之间通过一种高性能的进程间通信（IPC）消息库 **ZeroMQ** 来消息传递。

![](https://pic2.zhimg.com/v2-e5f07d8f4178ff7059b37b1047b98ca7_r.jpg)

当我们想要在多个计算节点上跑分布式计算时，我们并不需要给每个节点都分配一个 request handler，但是每个计算节点都需要有 Engine Core / Model Executor，因此 vLLM 又抽象出了一个用来给各个节点上的 engine core 分配计算任务的模块 engine_core (client)，(client) 指它负责分发任务给其他的 engine_core。

因此除了 Node 0 会额外跑纯cpu模块 AsyncLLM，其他的计算节点都只运行 engine core (就是需要你跑的 vllm/entrypoints/cli/serve.py)

![](https://pic4.zhimg.com/v2-3c155882ed4eed58822dd78712e591f3_r.jpg)

一个请求的生命周期：当你执行这个命令时，

![](https://picx.zhimg.com/v2-986404f292b19566f6feb207316bd5cf_r.jpg)

如前所述，它会经历这些过程：

1. API server响应请求，对请求的信息进行初步处理；
2. 进行请求的前置处理，包括对prompt进行token转换获得token id；
3. engine core client将请求发送给合适engine core，engine core完成自回归运算；
4. 进行后置处理，包括token转文本的过程；
5. 返回请求结果给用户。

下面我们一个个拆解这些模块：

## EngineCore Framework

AsyncLLM与engine core运行在不同的进程中，两者通过队列(queue)交互。

每个 EngineCore 都会维护一个输入输出队列，scheduler 不断从输入队列拿 input_processor 处理后的 token，将需求分配给 executor，再下发给每个 worker (一般是一张GPU)，完成计算后将输出放入输出队列，output_processor不断访问这个队列拿走输出返回给用户。

![](https://pic1.zhimg.com/v2-95936560c6d58f8c4f7b21909a1ed19e_r.jpg)

因此 Engine Core 内部需要 3 个协同的线程来处理三件事情：

1. 输入处理线程(process input)：主要负责接收engine core client传递过来的数据，并将请求放入队列；这里面 _handle_client_request 里的 add_request 和 abort_request都比较好理解，start_dp_wave和execute_dummy_batch的主要作用是在当前的 dp_replica 在本次 step 不需要工作时，保持苏醒，可以执行 alltoall操作而不会卡死整个通信。
2. 输出处理线程(process output)：将数据通过zmq通信返回给engine core client；
3. 处理[循环线程](https://zhida.zhihu.com/search?content_id=267799058&content_type=Article&match_order=1&q=%E5%BE%AA%E7%8E%AF%E7%BA%BF%E7%A8%8B&zhida_source=entity)(run busy loop)：持续地从输入队列拿取请求，按照vLLM config里的参数构造数据，并执行 _process_engine_step，包含 scheduler.schedule() 以及 execute_model(scheduler_output)

![](https://pic1.zhimg.com/v2-700e518d261e4ddb2cec446208f8a222_r.jpg)

scheduler和model runner是 vllm 非常核心的模块，包含了较多关键的优化技巧，接下来一一深入研究：

## Scheduler: Continuous Batching + Chunked Prefill

scheduler模块主要职责是：根据系统资源（GPU，VRAM...）和当前在执行请求的情况，高效地组织每次推理需要计算的数据。

分析scheduler的执行逻辑前，先回顾下LLM推理过程的一般特点：

- LLM前向推理分为两种模式，prefill和decode，他们的计算、访存的资源消耗量不同：

```text
Prefill:
Q: [B, H, L, D]
K: [B, H, L, D]
Attention: [B, H, L, L]       

Decode:
Q: [B, H, 1, D]
K: [B, H, L+1, D]
Attention: [B, H, 1, L+1]
```

- 因此他们需要被引擎以两种方式调度和分配资源：

![](https://picx.zhimg.com/v2-51270a5879666ee23e733dd15215a215_r.jpg)

例如下两条prompt输入时，会需要先对两条序列进行 prefill forward 使得 prompt 变成蓝色的 （获得 kv cache），下一步再decode，但是这种最原始的 batch generation 在一条序列生成结束时，浪费算力。

比如下图中的 who ate the pie? <eos>，当它提前生成 <eos> 并结束时，为保持 batch 张量形状一致，它仍会占据一个 batch 槽位，并在后续解码步骤中反复处理无意义的 <eos> 或 padding token，直到最长序列生成完毕。因此，短序列已完成后的计算不会产生效输出，却仍消耗 GPU 算力、显存带宽和 KV cache 空间；batch 内序列长度差异越大，这种资源浪费越严重。

![](https://pic3.zhimg.com/v2-e67ecfab8c22a82c30bf985963cf4d78_r.jpg)

一种简单的想法是，一条序列结束后，就加一条新的prompt进来

![](https://pica.zhimg.com/v2-16efe6ddfe0b37565ad8958bf4c5dec2_r.jpg)

但是新的prompt需要被prefill，为了保持注意力矩阵在 seq_len 维度是对齐的，这会导致我们不得不为其他已经有kv cache，只需要一维注意力的decode的序列前面加上很多padding，又浪费了很多算力。

一种更聪明的方式是把他们拼成一条序列，去掉 num_seq 这个维度，但是通过控制 attention mask 的方式使得 attention 的计算是合理的，每个序列只注意到其序列内部的token，即 Ragged Batching （破烂不堪地batch）

![](https://pic3.zhimg.com/v2-bf9bd2ec8787266743dcf45fe8c33bfc_r.jpg)

嘶但是这种方式看起来需要申请一个非常大的attention mask？并且很多空白的地方都被浪费了

实际上，上图中的空白的区域，现代的flash attention kernel会聪明地根据输入的cur_seq_len=[0, 5, 12]不计算它们，而是在一个Attention kernel内计算这样的多个分块注意力（因为FlashAttention本身也是基于矩阵块实现的）

```text
Attention(Q[0:5], K[0:5], V[0:5])
Attention(Q[5:12], K[5:12], V[5:12])
```

![](https://pic1.zhimg.com/v2-5892fb247cee654f9fa098d86749d9c2_r.jpg)

因此本质上，我们在 Attention Kernel 内运算时，num_seq 这一张量维度就消失了，真正限制注意力计算的是一个batch内有多少token（很像verl里的`ppo_max_token_len_per_gpu` ）。

**Continuous Batching**: 如果显存限制下，最大的token数是m，continous batching实际上就是一种聪明的dynamic batching方式：

每一次attention计算，我们首先把所有decode的请求加到batch，然后把 chunked prefill 的prompt加到batch中，填满显存。当某条序列生成 `<eos>` 提前结束时，系统会立即释放它占用的 batch 槽位，并从等待队列中加入新的请求，而不必等到当前 batch 中最长的序列完成。新请求先执行 prefill、建立 KV cache，随后与其他未完成序列共同进行逐 token 解码。

这样，batch 的成员可以持续“流入”和“流出”（也就是continuous)，GPU 始终处理有效请求，避免对已结束序列反复计算 `<eos>` 或 padding token，从而提高 GPU 利用率、系吞吐量，并降低请求的排队延迟。

![](https://picx.zhimg.com/v2-618b620e3d0a7efa36c0c860b9039d07_r.jpg)

**Chunked prefill:** 而这里 prefill 任务会被以一种分块的方式加入一次attention计算中，因为长序列直接全部prefill显然会爆显存，并且 prefill 的时长总是会比 decode 要长很多，这样做也可以增加整个计算的吞吐，最大化地填满显存

![](https://pic4.zhimg.com/v2-e8577c5a7f3c1858e8f5d96b0d82d579_r.jpg)

## KV Cache Manager / Page Attention

Page Attention是vLLM最原始的论文中提出的管理 KV Cache的方法，vLLM 使用类似于操作系统中分页管理虚拟内存的方式来管理，首先回顾一下操作系统中的分页管理机制：

![](https://pic4.zhimg.com/v2-bda52a1455622c744bf8bc876be76d43_r.jpg)

我们可以将进程1、进程2想成是两本书。进程需要的文件分布在书的不同page上。我们希望想读哪一页，就加载哪一页，而不是一下把两本书都加载进来。

如果我们希望读进程1和进程2的page1，我们就将其加载到物理内存上。虚拟内存会帮我们做好映射，把来自不同进程的这两页分别加载到物理内存对应位置。其核心思想就是：

- 将物理内存划分为**固定大小的块**，我们称每一块为**页**（page）。从物理内存中模拟出来的虚拟内存也按相同的方式做划分
- 对于**1个进程**，我们不需要静态加载它的全部代码、数据等内容。我们想用哪部分，或者它当前跑到哪部分，我们就动态加载这部分到虚拟内存上，然后由虚拟内存帮我们做物理内存的映射。
- 对于1个进程，虽然它在物理内存上的存储不连续（可能分布在不同的page中），但它在自己的虚拟内存上是连续的。通过模拟连续内存的方式，既解决了物理内存上的碎片问题，也方便了进程的开发和运行。

现在我们类比到 LLM 推理和显存的关系上：

- **请求**（request）可理解为操作系统中的一个进程
- **逻辑内存**（logical KV blocks）可理解为操作系统中的虚拟内存，每个KV Cache block类比于虚拟内存中的一个page。每个block的大小是固定的，在vLLM中默认大小为16，即可装16个token的K/V值
- **块表**（block table）可理解为操作系统中的虚拟内存到物理内存的映射表
- **物理内存**（physical KV blocks）可理解为操作系统中的物理内存，实际存放在gpu显存上

![](https://picx.zhimg.com/v2-a311be5ce01b0469b5036b527809ce0f_r.jpg)

这样我们对于大模型这种生成长度不能事先确定的需求，可以动态地分配内存，而无需提前申请一个大内存导致内存碎片化和浪费。

更新的 vLLM 也结合了 SGlang 中的前缀树思想，对于 agent 场景这种多个请求容易共享前缀的任务，以前缀树的方式来管理 KVCache Block，减少存储相同的 prompt 的 KVCache Block 来减少内存开销：

如下图，在步骤（1）中，Radix 树最初为空。

在步骤（2）中，服务器处理用户发来的消息“Hello”，并生成“Hi”。系统提示词“You are a helpful assistant”（这里作为Agent系统中的system prompt示例）、用户消息“Hello!”以及模型回复“Hi!”被合并为树中的一条边，并连接到一个新节点。

在步骤（3）中，一个新的提示词到达。服务器在Radix 树中找到该提示词的公共前缀，也就是对话的第一轮，并复用该前缀对应的 KV Cache。随后，新一轮对话作为一个新节点追加到树中。

在步骤（4）中，一个新的聊天会话开始。步骤（3）中的节点 `b` 被拆分为两个节点，从而使两个聊天会话能够共享同一段系统提示词。

在步骤（5）中，第二个聊天会话继续进行。但是由于显存容量限制，必须淘汰步骤（4）中的节点 `c`。随后，新一轮对话被追加到步骤（4）的节点 `d` 之后。

## Model Runner

[模型执行器](https://zhida.zhihu.com/search?content_id=267799058&content_type=Article&match_order=1&q=%E6%A8%A1%E5%9E%8B%E6%89%A7%E8%A1%8C%E5%99%A8&zhida_source=entity)(model runner)主要负责计算调度器发送过来的批请求，并返回执行结果。

从上面engine core的架构可知，executor可以有多个worker模块，每个worker都会有自己的model runner。model runner的逻辑主要是模型运算、以及物理层的kv cache分配与管理。

![](https://picx.zhimg.com/v2-8c4536e5556fa3f7e819ca8476b02bdf_r.jpg)

执行的基本步骤：

1. 根据映射表(block table)信息为每个待执行请求分配kv blocks；
2. 将请求组成序列batch，基于 kv blocks 完成 transformer 的 MoE + Attention 前向推理过程

**Attention Backend**

这里根据硬件和模型的不同可以使用特定的 AttentionBackend

![](https://pic2.zhimg.com/v2-c02c52a07343ddd1f9830497acd429f7_r.jpg)

并且实际上每个 GPU 上跑的都是被切分的 Attention 和 MoE

![](https://pic3.zhimg.com/v2-200bb5430714928533c80a81fa217918_r.jpg)

TP，DP，SP 和 EP 都值得钻研，回答最后到一个GPU上的张量形状究竟是怎么被算出来的，怎么才能有一个principled的方法，保证绝对不oom，这个就之后讲吧~
