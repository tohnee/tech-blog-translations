DeepSeek 开源 DeepInfer 后，我沿着缓存、YoCo 和 DSpark 的调用链写了几篇源码笔记。看这类代码，有些问题对着公式就能推，有些却很难只靠阅读确认。比如一轮草稿验证结束，输出列表只多了两个 Token，模型内部可能已经写进去四个位置。剩下那两个位置怎么办，下一轮还会不会读到？

这个问题让我想做一个小实现，把模型尺寸压下来，把多卡、通信和 kernel 优化先拿掉，保留一条会持续修改状态的请求链。这样我可以在每次写 KV 的地方停下来，看它写了什么，再拿最普通的逐 Token 解码作对照。

于是我从昨晚熬夜爆肝一整夜做好了。项目叫 [Core-DeepInfer](https://github.com/he-yufeng/core-deepinfer)，用 NumPy 写的，CPU 就能跑。欢迎先来点个 Star和 Fork，这对我很重要：

[Core-DeepInfer](https://github.com/he-yufeng/core-deepinfer)

里面的模型参数是随机的，attention 和前馈网络都真算，但它不会聊天。默认演示有一条请求会连续输出八个 `17`：

```text
request-1: length, tokens=[17, 17, 17, 17, 17, 17, 17, 17]
```

这串数字没什么可欣赏的。值得看的是，在它生成这些数字的过程中，缓存曾经失效，草稿曾经被拒绝，请求也会被重新放回队列。经过这些绕路，最后留下的 KV 和直接算出来的 KV 是否一致，才是我想检查的东西。

我没有从 DeepInfer 里删出一个小版本，也没有接 DeepSeek 权重。模型结构做了简化，主要保留共享来源 K/V 和局部窗口状态，方便单独观察原版里相关设计的行为。下面的数字都来自这个小实现。

## 把窗口缩到两个位置，回滚就藏不住了

先不考虑吞吐，只看一个请求。

假设输入已经算了四个 Token，绝对位置是 `0、1、2、3`。局部注意力只保留最近两个位置，所以此时两个缓存槽里放的是位置 `2` 和 `3`，下一次应该写位置 `4`。

草稿模型接着提出了四个 Token：`[6, 23, 6, 7]`。目标模型同意第一个 `6`，但在第二个位置选了 `22`。这一轮最终应该交付 `[6, 22]`。

看输出很简单。看看缓存发生了什么。

| 时刻 | 槽位0保存的位置 | 槽位1保存的位置 | 下一写入位置 |
| --- | --- | --- | --- |
| 验证前 | 2 | 3 | 4 |
| 写入草稿6 | 4 | 3 | 5 |
| 写入草稿23 | 4 | 5 | 6 |
| 写入后面的草稿6 | 6 | 5 | 7 |
| 写入最后的草稿7 | 6 | 7 | 8 |

环形缓冲区反复用了那两个槽。等验证结束，位置 `2、3` 的 K/V 早就被覆盖，连接受的那个 `6` 写在位置 `4` 的 K/V 也被覆盖了。

如果这时只是把输出列表截短，再把 `next_position` 减回去，旧数据不会跟着回来。

![](https://pica.zhimg.com/v2-e81b8a1b3481f111ef29b2e6f979f2c8_r.jpg)

我的处理是回到“已经接受第一个6”的检查点。这个时刻的槽位标签是 `[4, 3]`，下一写入位置是 `5`。随后把目标选出的 `22` 算进去，得到 `[4, 5]`，下一写入位置变成 `6`。

这里还容易漏掉一个细节：草稿 `23` 和替代 Token `22` 都曾经占据位置 `5`。只检查位置标签，两个分支看起来完全一样。可它们的 K/V 数值不同，下一次 attention 读到哪一份，后续结果就可能不同。

这段实验可以直接运行：

```python
import numpy as np
from core_deepinfer import TinyModel
from core_deepinfer.demo import state_error
from core_deepinfer.runtime import Runner
from core_deepinfer.speculative import generate

model = TinyModel(seed=7, width=8, depth=2, window=2)
prompt = [1, 2, 3, 4]
baseline = generate(model, prompt, max_tokens=5)
drafts = [baseline.tokens[0], (baseline.tokens[1] + 1) % model.vocab_size, 6, 7]
runner = Runner(model, model.prefill(prompt))
result = runner.verify(drafts, max_tokens=5)
expected = model.prefill([*prompt, *result.tokens])

assert runner.tokens == expected.state.tokens
error = state_error(runner.state, expected.state)
assert error < 1e-10
assert np.allclose(runner.logits, expected.logits[-1], atol=1e-10, rtol=0)
print(result)
print("KV max error:", error)
```

这组参数下，返回的是：

```text
Verified(tokens=(6, 22), accepted=1, verified=4, discarded=3)
KV max error: 8.881784197001252e-16
```

注意这里的 `verified=4`。我故意让目标模型在这一轮写入全部四个草稿，检查拒绝之后能不能恢复。原版引擎如何把验证打成并行计算，是另一个实现问题；这个 NumPy 版本按顺序执行 forward，不拿它测投机解码加速。

光对 Token 还不够，所以例子又比较了全局来源、逐层局部 K/V 和下一 Token 的 logits。同一个 argmax 可能来自两份不同的 logits，只看生成结果，状态错误有时能藏很久。

我还在独立 Runner 上做了一个故意错误的恢复：Encoder 和 logits 恢复了，两个 ring 只退游标，不恢复数组和标签。读取旧位置 `2` 时直接报 `KeyError`，槽里还标着 `6`。这比“理论上可能有问题”直观得多。

不过，看到这个反例以后，也不能得出“生产引擎每次回滚都得复制 KV”。我这里把容量压到两个位置，就是为了让覆盖立刻发生。实际系统可以多留一段空间，只要可能回退到的数据还没被覆盖，就有别的恢复办法。

DeepInfer 的 [get_inference_swa_block_size](https://github.com/deepseek-ai/DeepInfer/blob/8b16149741a4935e1dec8cea27853f273b374c5b/deepinfer/worker/cache_engine.py#L88-L110) 就把推理时的 SWA 容量写成了 `window_size + DEEPINFER_MAX_BACKTRACKING_TOKENS`。正常注意力窗口之外，还要为回退留位置。存储视角又会叠加额外的留存范围，和运行时容量分开计算。

这样再看原版里那些比窗口多出来的 Token，就不只是一个需要照抄的常数了。你得知道它们在保护哪段数据；改窗口、草稿长度或者缓存落盘边界时，也得一起检查这段数据还能不能留住。

小实现用了最省脑子的办法：复制快照。检查点会保存 Encoder 历史、共享来源 K/V、两个局部 ring 的内容和标签，以及 logits。恢复时把它们放回同一个前缀边界。代价也明显，历史越长，复制越贵。如果下一步要换成 undo log，至少已经有一个笨但清楚的版本可以对照。

## 同样命中四个 Token，为什么有的请求还要重算

回滚解决以后，缓存恢复也好理解一些了：你拿回来的究竟是哪一份状态？

这个模型前面有一个全局因果 Encoder，输出投影成共享的来源 K/V；后面是多层 consumer，每层保留自己的局部窗口，同时读取共享来源。新增一个 Token 时，这两部分都会更新。Encoder 和 consumer 是模型结构里的划分，不能把它们直接叫作 prefill 和 decode 两个阶段。

因此，一段前缀可能只剩下 Encoder 的结果，也可能连局部窗口、下一 Token 的 logits 都还在。两者都能说“前四个 Token 命中了”，接下来要做的工作却不同。

默认演示用了三层 consumer，恢复一个四位置前缀时，实际记录如下：

| 找回来的状态 | Encoder新增query行 | consumer新增query行 |
| --- | --- | --- |
| 完整状态，hot | 0 | 0 |
| 只有Encoder前缀，warm | 0 | 12 |
| 都没有，cold | 4 | 12 |

warm 路径的 `12` 是四个位置乘三层。全局来源已经有了，但逐层局部状态丢了，仍要从来源重放。hot 路径把这些状态一起拿回来，可以直接接着生成。

![](https://pica.zhimg.com/v2-67075550f6e14622e5ea0ed47cbe6698_r.jpg)

这也是我觉得只报缓存命中率不够的原因。同样的输入长度、同样的命中长度，如果一个命中了完整状态，一个只命中了来源，它们剩下的计算量就不在同一个起点上。

缓存键也得表达这种区别。我的实现会区分参数、布局、精确 Token 前缀、边界和恢复模式。最直接的反例是改掉模型的输出投影：prompt 一个字没变，原来的 logits 却已经失效。只按 prompt 找缓存，就可能继续用旧分布生成。

这里我每次用参数身份时都重新计算内容哈希，图的是小模型上容易查错。生产服务通常可以依靠严格的模型版本管理，但“同一个版本号对应不可变权重”得是系统真的能保证的事。给一个可变对象挂个固定名字，不能让旧状态自动变得有效。

图里的行数也只回答模型新算了多少行。hot 路径还要读取、复制和校验状态，参数指纹也有开销。是否值得缓存，最后要把这些成本和重算放到一起看，不能见到两个零就当作免费。

## YoCo那部分，最容易把两个问题混在一起

只有 Encoder 前缀、局部状态丢失时，需要补回后面的计算。DeepInfer 的有限回放，就是我在这里最想单独观察的一部分。

先想一个多层滑动窗口模型。最后一层某个位置的状态，依赖上一层附近的位置；这些位置又依赖更前一层的附近位置。每层只看一个小窗口，不代表恢复末尾状态时，只算最后一个窗口就能精确还原。依赖会沿层数往前展开。

如果规定恢复时只看最后一小段，并且把这一小段以外的局部依赖切掉，计算范围可以缩小，但恢复出的已经是另一张依赖图。这样做能不能用于原模型，需要质量回归。我这个随机模型没有能力回答 DeepSeek 的任务质量问题。

它能回答一个更局部的问题：决定采用这张截断图以后，代码有没有真的少算。

在32个位置、保留末尾8个的算例里，`mask` 和 `compact` 两条路径都采用相同的局部可见范围。`mask` 仍让全部32行经过三层 consumer，只是在局部注意力里屏蔽相应位置；`compact` 在进入 consumer 前把 query 裁到8行。于是计数从 `32 × 3 = 96` 变成 `8 × 3 = 24`。

被裁掉的行不会再经过后面那些投影和前馈计算，这才是裁行带来的实际变化。只改 mask，虽然限制了“看哪里”，却不一定去掉了“算哪些行”。

但来源没有一起裁掉。consumer 的 cross attention 仍然读取32个位置的共享来源；这个来源来自全局因果 Encoder。若顺手把它也截成8个位置，模型保留的历史信息就又变了。

原版也把这两个东西分开处理。可以对着 [decoder_layer.py 的边界逻辑](https://github.com/deepseek-ai/DeepInfer/blob/8b16149741a4935e1dec8cea27853f273b374c5b/deepinfer/model_executor/models/decoder_layer.py#L134-L152) 看：裁 consumer 侧 hidden states、residual 的行，不等于把供后续读取的全局来源一起截短。

![](https://pic3.zhimg.com/v2-b926296a86cc18724b88add59ba5f4bc_r.jpg)

这个实验里，mask 与 compact 在保留位置上的最大 logits 误差约 `2.55e-15`，但有界结果相对 exact 的误差约 `2.05`。这两组数可以同时成立。前一组说明裁行实现没有额外改坏已经选定的截断图，后一组说明截断图本来就不等于原来的精确计算。

所以我会分别保留这两种对照。要是只留下“两个优化版本相等”的测试，就可能把共同引入的近似当成没有近似。至于96变24，它说的是这里的 consumer 行数；Encoder、完整来源和其他工作都还在，离整条推理快四倍差得远。

### 草稿猜了四个，目标不一定该验四个

前面的回滚实验故意把四个草稿全部交给目标。接到多请求调度上，就要再问一句：这些位置值得验吗？

如果两条请求总共只有四个有效位置，一种分配是 `[3, 1]`。每个请求先留一个主位置，用来保证推进；余下两个位置给第一条请求验证草稿。这里的3并不代表三个草稿。

假设新一轮信息显示，第二条请求的草稿更可能被接受，那么同样四个位置可以改分成 `[1, 3]`。前一条少验，后一条多验。总量没变，工作却挪到了另一条请求上。

DeepInfer 的相关路径还涉及信息时序：CPU 选总预算时，较新的置信度可能还没准备好，于是先用旧信息定总量，再根据新信息修正逐请求长度。追这段代码时，如果忽略“这份信息是哪一轮的”，很容易把两次决策看成重复计算。我在小实现里把它们写成前后两次函数调用，方便观察分配怎样变化；原版的 CPU/GPU 重叠没有照搬过来。

预算算完，还得有人执行它。引擎把每条请求分到的长度减一，按这个数量截取草稿，再交给 `Runner.verify`。在本项目里，改变这个长度会改变实际进入目标 forward 的草稿数。

还要处理另一份容易被忘记的状态：草稿模型自己已经向前走了。即便目标只验证其中一部分，草稿模型也可能已经生成了更长的后缀。目标拒绝以后，draft 同样得回到接受边界，再吃入目标给出的替代 Token。否则这一轮输出是对的，下一轮却从错误的草稿前缀开始。

这两处在 [Engine 的提交路径](https://github.com/he-yufeng/core-deepinfer/blob/c541f77799bda3796467cf14e4d14270d11fc8e7/core_deepinfer/engine.py#L348-L364) 里挨得很近：先按预算验证目标，再恢复和追齐 draft，最后把 Token 加到请求结果中。

我这里使用草稿模型对自己选中 Token 的概率，成本曲线也是手工给的。DSpark 的训练置信度和硬件计时要复杂得多。这部分实验只用来检查预算是否控制了执行、执行后双方状态是否还对得上，拿它选最快的 GPU 配置没有意义。

### 最后还是要回到一条完整请求

单独写一个验证函数，可以把很多麻烦留给调用方。等它要连续处理请求，之前省掉的事情又会回来。

比如一条请求已经提交了本轮结果，处理下一条时来了中断。整轮退回去，会把前一条已经提交的结果也算一遍；什么都不退，又可能留下后一条写了一半的状态。我在引擎里单独记录了请求的检查点和提交状态，让中断清理只撤销尚未提交的分支，再把没结束的请求放回队列。清理完成后仍然把中断抛出去。

错误处理也类似。一条请求失败，不应该让同一批里的健康请求失去结果；这批错误报告过以后，也不该让下一次 `run()` 继续替上一批报错。这些看起来不如注意力算子显眼，但只要想复用同一个引擎实例，就绕不过去。

我没有继续往这个项目里塞服务端、权重下载器和硬件后端。先让这条小请求链经得起改动比较有用：少验几个草稿、换一个队列顺序、让短期状态过期，再检查输出和已提交状态。哪一步对不上，就能退回普通逐步解码，查到第一个不同的位置。

可以直接从默认演示开始：

```bash
python -m pip install core-deepinfer
core-deepinfer demo --trace
```

![](https://picx.zhimg.com/v2-7c0fd493d88878ab8f6f78fb0bdfd3a9_r.jpg)

trace 里能看到请求什么时候入队、从哪种缓存恢复、分到多少位置，以及这一轮验证后提交了什么。演示通过注入时钟推进到0、3、200秒，让短状态和长前缀依次失效，不需要真的等几分钟。

读代码可以从 `runtime.py` 的 `verify` 开始，然后去 `engine.py` 看预算和提交。模型本身在 `model.py`，想知道某个位置为什么还能看到更早的内容，就顺着 `source`、`shared_keys` 和 `shared_values` 往回找。我把对应原版的位置和小实现的差异也写进了导读，方便两边对着看。
