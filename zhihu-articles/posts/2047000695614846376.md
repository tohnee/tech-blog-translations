### 1. 投机解码

投机解码（Speculative Decoding）是目前大语言模型（LLM）推理加速领域最核心的技术之一。它的核心目标是：在不牺牲模型生成质量（保证数学上无损）的前提下，极大地提升大模型的文本生成速度。

传统的自回归生成就像“老太太敲键盘”，无论大模型多聪明，每蹦出一个字都必须把几百亿参数在显存里完整搬运一次，导致速度极慢。而投机解码通过“两段式”的设计打破了这一瓶颈。

### 1.1 投机解码的核心架构

投机解码将推理任务分工给两个不同的角色：

- **草稿器**（Drafter / Draft Model）：通常是一个体积很小、速度极快的模型（例如 $1B$ 或更小），或者是一个简单的无参数算法（如你刚才看到的 N-Gram 匹配）。它的任务是“盲猜”接下来的几个 Token。
- **验证器**（Validator / Target Model）：就是你想真正使用的大模型（例如 $70B$ 的 Llama-3）。它的任务是“批改作业”，并行验证小模型的猜测是否正确。

### 1.2 核心工作流程（以投机 4 个 Token 为例）

**步骤一：小模型盲猜（Drafting）**

小模型一口气连续自回归生成 4 个 Token。因为小模型极小，这个过程花费的时间微乎其微。

草稿：["人工智能", "将", "改变", "未来"]

**步骤二：大模型并行验证（Verification）**

大模型把现有的历史文本连同这 4 个草稿 Token 一起拼接起来，一次性输入给大模型。通过 Transformer 的因果掩码（Causal Mask）特性，大模型在单个前向传播（Forward Pass）中，能同时算出这 4 个位置上大模型自己最想生成的 Token。

**步骤三：结果比对与裁剪（Acceptance & Correction）**

算法从左到右比对小模型的草稿和大模型的预测结果：

- 如果前 3 个 Token 大模型都认可了，第 4 个 Token ["未来"] 大模型觉得不对（大模型更想输出 ["世界"]）。
- 那么系统会**接受前 3 个 Token**，并顺手把第 4 个位置修正为大模型的答案 ["世界"]。

神奇的结果：在这一轮中，大模型只运行了一次，但最终却直接输出了 4 个 Token。原本大模型需要串行跑 4 次的开销，现在被压缩到了 1 次。

### 1.3 为什么投机解码能带来实质加速？

这涉及到大模型推理的底层物理瓶颈——**内存带宽限制（Memory Bound）**。

在单 Token 生成阶段，计算算力不是瓶颈，最耗时的是**从显存中读取庞大的模型参数**（搬运权重）。

- **普通生成**：生成 4 个 Token，大模型要从显存读取 4 次完整权重。
- **投机解码**：大模型读取 1 次完整权重，顺便把小模型送来的 4 个草稿全部算完。虽然计算量变大了一点，但搬运权重的次数减少了，而 GPU 刚好可以利用闲置的算力把这些多出来的计算并行做完。

### 1.4 常见的草稿器（Drafter）流派

根据如何产生“草稿”，投机解码演化出了几种主流的设计路线：

| 流派 | 设计原理 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 小模型投机 (Vanilla) | 专门训练一个同词表的小模型（如 7B 预测 70B） | 泛化能力强，各种场景都能猜中一些 | 需要额外维护一个小模型，占用额外显存 |
| N-Gram 投机 | 直接在 Prompt 和已生成历史中找重复的 Token 模式 | 零额外显存，零训练成本，CPU 匹配 | 只在代码、结构化文本等重复率高的场景有效 |
| Medusa / EAGLE | 在大模型顶层挂几个并行的预测头（Heads） | 不需要独立小模型，准确率极高 | 需要对大模型进行微调，增加了主模型的体积。 |

## 2. 大模型并行验证

在投机解码（Speculative Decoding）中，并行验证（Parallel Verification）是大模型能够实现加速的“魔术所在”。

传统的自回归生成是串行的：生成 $K$ 个 Token 需要让大模型前向传播（Forward Pass）$K$ 次。

而并行验证的核心设计是：利用 Transformer 的因果掩码（Causal Mask）特性，让大模型在单次前向传播中，同时计算并验证这 $K$ 个投机 Token 的概率分布。

以下是并行验证的具体设计和底层工作原理：

### 2.1 核心底层：因果掩码（Causal Mask）的妙用

在 Transformer 的 Decoder 中，自回归模型通过注意力掩码（Attention Mask）来确保当前位置只能看到它之前的 Token，而不能看到未来的 Token。

当草稿器（如 N-Gram 或小模型）一次性给出了 $K$ 个投机 Token（假设 $K=3$）时，验证器（大模型）并不会傻傻地一个一个去读，而是把它们拼接成一个连续的序列，一次性输入给大模型。此时，大模型的输入序列变成了：

$\text{Input} = [\text{已有历史}, \text{投机 Token}_1, \text{投机 Token}_2, \text{投机 Token}_3] \\$

通过巧妙地设计 Causal Mask，大模型在计算时：

- 计算 $\text{投机 Token}_1$ 位置的输出时，只能看到 $\text{已有历史}$；
- 计算 $\text{投机 Token}_2$ 位置的输出时，能看到 $\text{已有历史} + \text{投机 Token}_1$；
- 计算 $\text{投机 Token}_3$ 位置的输出时，能看到 $\text{已有历史} + \text{投机 Token}_1 + \text{投机 Token}_2$。

这就意味着，大模型在单次矩阵生长的计算中，实际上同时得出了这三个位置的预测概率分布（Logits）。

### 2.2 具体的验证算法

大模型跑完单次前向传播后，会输出每个投机位置的真实概率分布。接下来，验证系统会采用贪婪采样验证或核采样（Nucleus/Probabilistic）验证。

以最直观的贪婪采样（Greedy Decoding）为例，验证过程如下：

**假设场景：**

- 投机器给出的草稿是：["很", "高兴", "见到"]
- 大模型并行计算后，这三个位置上概率最高（Top-1）的 Token 分别是： <br>

**验证比对（从左到右）：**

1. 验证第 1 个：草稿是 "很"，大模型认为应该是 "很"。[接受]
2. 验证第 2 个：草稿是 "高兴"，大模型认为应该是 "高兴"。[接受]
3. 验证第 3 个：草稿是 "见到"，大模型认为应该是 "认识"。[拒绝]

**最终结果：**

一旦发现错误，后续的投机全部失效。系统会执行以下操作：

- 保留通过验证的 Token：["很", "高兴"]。
- 修正错误的位置：直接采用大模型在位置 3 算出的正确答案 "认识"。
- 本轮前向传播结束，最终实际生成了 3 个 Token（"很"、 "高兴"``、"认识"），但只花了单次大模型的计算时间。

*注意（Probabilistic Sampling）：如果开启了随机采样（Temperature > 0），验证会使用一种基于拒绝采样（Rejection Sampling）的数学公式。如果大模型在该位置采样出草稿 Token 的概率低于某个阈值，会按概率决定是否拒绝，并用差值分布重新生成，以保证生成的文本分布与直接使用大模型完全一致，做到无损加速。*

### 2.3 为什么单次并行验证比串行快？

你可能会问：大模型一次性算 4 个 Token 的输入，计算量不是变大吗？为什么反而变快了？

这就涉及大模型推理的瓶颈——内存带宽限制（Memory Bound）：

- 在 Decode 阶段（串行生成），大模型每生成一个 Token，都要把几百亿参数的权重从显存（HBM）加载到 GPU 核心（SRAM）一次。此时 GPU 算力严重闲置，时间都浪费在“搬运权重”上了。
- 在 并行验证 时，大模型只需要加载一次参数，就能顺便把这 $K$ 个 Token 的计算全部做完。对 GPU 来说，算 1 个 Token 和算 4 个 Token 消耗的搬运权重时间几乎是一样的。

通过这种方式，并行验证成功用闲置的 GPU 算力换取了推理时感的巨大提升。

## 3. N-Gram 投机解码

在 vLLM 等大模型推理框架中，N-Gram 投机解码（N-Gram Speculative Decoding） 是一种不需要额外训练小模型（Draft Model），而是利用 prompt 和已生成文本中的历史重复模式来进行加速的投机解码技术。

其核心设计思想是：“人类说话和写代码往往会重复自己。” 比如在代码中常常连续出现 if **name** == '**main**':，在文本中常出现特定的短语。它的具体设计和工作流程可以分为以下几个关键步骤：

### 3.1 核心设计原理

N-Gram 投机解码用一个简单的 N-Gram 匹配算法替代了传统投机解码中的草稿模型（Draft Model）。

- 草稿器（Drafter）：一个基于 CPU 或轻量级维护的固定窗口历史 Token 查找表（类似于一个 Sliding Window 缓存）。
- 验证器（Validator）：原本的大语言模型（Target Model）。

通过直接在已有 Token 历史中匹配“前缀”，来预测接下来的几个 Token，从而省去了运行草稿小模型的计算开销和显存占用。

### 3.2 详细工作

流程假设大模型当前已经生成了一长串 Token 历史，现在需要预测下一个位置。N-Gram 投机解码会执行以下操作：

**步骤一：查找当前匹配前缀（Context Window Matching）**

算法会提取当前序列最后 $N-1$ 个 Token 作为“检索词”（即 Lookback 窗口）。

举个例子：假设当前文本最后 3 个 Token 是 ["if", "args", "."]（此时 $N=4$）。

**步骤二：在历史文本中搜索（Slide & Match）**

算法会在之前已经生成的整个文本（包括 Prompt 和已经生成的回复）中，从前向后搜索同样出现了 ["if", "args", "."] 的地方。

**步骤三：提取投机候选 Token（Draft Generation）**

如果在历史中找到了匹配的片段，算法会顺着这个匹配点，直接抄袭后面的 $K$ 个 Token，作为“投机 Token”（Speculative Tokens）。

延续例子：发现在第 100 个 Token 处也出现过 ["if", "args", "."]，且它后面紧跟着的是 ["method", "==", '"ngram"']。那么算法直接把 ["method", "==", '"ngram"'] 拿过来，作为草稿投机给大模型。

**步骤四：大模型并行验证（Parallel Verification）**

大模型（Target Model）接收到当前的输入以及投机给它的 $K$ 个 Token，在单个推理步（Single Forward Pass）中并行计算这几个位置的概率分布，并与投机 Token 进行比对：

- **接受（Accept）**：如果大模型判定投机的 Token 符合采样概率，则直接通过。一个 Token 的计算时间直接拉出了 $K$ 个 Token。
- **拒绝（Reject）**：如果在某一个位置大模型认为投机错了，则在此处截断，保留前面对的，重新生成错的位置。

### 3.3 关键配置参数

以 vLLM 为例，N-Gram 的配置包含以下三个核心参数：

- **num_speculative_tokens ($K$)** ：每次大模型前向传播时，最多投机预测多少个 Token（即草稿的长度）。
- **prompt_lookup_max** ：在历史记录中进行 N-Gram 匹配时，N 值的最大值（即最长匹配多长的历史前缀）。
- **prompt_lookup_min** ：N 值的最小值。如果历史中连这么短的前缀都匹配不上，说明没有重复模式，就会放弃投机，退回到普通的单 Token 解码。

### 3.4 N-Gram 投机解码的优缺点

**优点**

- 零显存与计算开销：不需要像 Medusa 或 EAGLE 那样多加载一个几 GB 的小模型，也不需要额外的显存来存草稿模型权重，纯粹是 CPU/内存级别的字符串/Token 匹配。
- 在特定场景下加速极高：在代码生成（Code Generation）、结构化输出（JSON/XML Parsing）以及长文本检索生成（RAG）中表现极为优异，因为这些场景下文本重复率极有规律。

**缺点**

- 泛化能力弱：如果生成的文本极具创意、完全不重复（例如写小说），N-Gram 找不到匹配项，投机成功率（Acceptance Rate）会跌到接近 0，此时因为增加了匹配算法的开销，反而会导致微小的性能下降。
