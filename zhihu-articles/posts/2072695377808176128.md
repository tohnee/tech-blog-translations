本章讲**投机解码**——把“每步 1 个 token”变成“每步平均 >1 个 token”；**量化**——把权重与 KV 的字节数压下来（decode 是访存瓶颈，字节数直接决定吞吐）——见第 9 章。两者独立正交，都直接作用于 decode 吞吐。

## 8.1 投机解码原理

### 8.1.1 动机

decode 的瓶颈是“读一遍权重只换回 1 个 token”（第 1 章 1.3.2）。如果能**一次 forward 产出多个 token**，权重的读一遍就被多个 token 摊薄。但自回归是串行的：第 $t+1$ 个 token 依赖第 $t$ 个的采样结果。

**投机解码（speculative decoding）**的思路：

1. 用一个**便宜的 draft 模型**（小模型/浅层头/规则）快速自回归生成 $K$ 个草稿 token（draft tokens）；
2. 目标模型**一次 forward 并行验证**这 $K+1$ 个位置（第 $t$ 个真实 token + $K$ 个 draft）；
3. 用 rejection sampling 决定接受前缀长度 $r$——本步产出 $r+1$ 个 token，**输出分布与目标模型完全一致（lossless）**。

术语澄清（避免与直觉冲突）：本步产出的第 $r+1$ 个 token 有**两种来源**——若 $r = K$（全部接受），它是从目标分布额外采的 **bonus token**；若 $r < K$（部分拒绝），它是从修正分布（8.1.2）重采的 **recovered token**。两者在结算时都计入“本步产出”，但只有前者叫 bonus。

### 8.1.2 Rejection Sampling 的数学

设目标模型分布 $p(x)$（目标模型**实际用于采样**的分布——target logits 经 penalties/top_k/top_p 等约束后再 softmax，见 8.2.3 ②），draft 模型分布 $q(x)$（draft 采样时的分布）。验证第 $i$ 个 draft token $x_i$：

- 采样 $u \sim U(0,1)$；
- 若 $u \le \min(1, \frac{p(x_i)}{q(x_i)})$（当 $q(x_i) > 0$；因 $u \le 1$，与直接写 $u \le p(x_i)/q(x_i)$ 等价）：**接受** $x_i$，继续验证下一个；
- 否则**拒绝**：从修正分布 $p(x) - q(x)$ 的正部归一化后重新采样：

$$ x' \sim \frac{\max(p(x) - q(x), 0)}{\sum_y \max(p(y) - q(y), 0)} $$

关键性质（概率论中的 standard result）：**这个流程采样出的分布恰好就是 $p$**。验证：对任意 token $x$，输出 $x$ 的总概率 = “接受 $x$（被 draft 采到且通过检验）” + “拒绝后从修正分布采到 $x$”：

$$ P(\text{out}=x) = q(x)\min\!\Big(1,\frac{p(x)}{q(x)}\Big) + \max(p(x)-q(x),0) $$

其中第二项的推导：先以概率 $P(\text{reject})$ 进入拒绝分支，再从修正分布采到 $x$，条件概率为 $\frac{\max(p(x)-q(x),0)}{Z}$；而 $Z = P(\text{reject})$（见下式），两项相乘后消去，正是 $\max(p(x)-q(x),0)$。

分两种情形核对：$p \ge q$ 时第一项 $= q$、第二项 $= p-q$，合计 $p$；$p < q$ 时第一项 $= p$、第二项 $= 0$，合计 $p$。又拒绝概率 $P(\text{reject}) = 1 - \sum_y q(y)\min(1,\frac{p(y)}{q(y)}) = \sum_y \max(p(y)-q(y),0)$——正是修正分布的归一化常数 $Z$（也对应 8.1.1 里 recovered token 的分布总量）。因此投机解码**不改变输出分布**，只改变每步产出的 token 数（期望接受长度 $\mathbb{E}[r]$）。

greedy 模式退化得更简单：draft token == 目标模型 argmax 则接受，否则拒绝；全接受才追加 bonus。

### 8.1.3 收益公式

每步实际产出 $\mathbb{E}[r] + 1$ 个 token，代价是“draft 的 $K$ 步自回归 + 目标模型一次 $K+1$ token 的 forward”（EAGLE 的第一个 draft 直接吃目标模型隐状态、不额外自回归，见 8.3）。当 draft 便宜且准确率高（$\mathbb{E}[r]$ 接近 $K$）时，加速比显著。**draft 与目标越像，接受率越高**——所以主流方案（EAGLE）让 draft 直接用目标模型的隐状态。

接受长度的期望（i.i.d. 假设下）：单个位置的接受概率是 $P(\text{accept}) = \sum_x q(x)\min(1, p(x)/q(x)) = \sum_x \min(p(x), q(x))$。定义 total variation 距离 $\text{TV}(p,q) = \tfrac12\sum_x |p(x)-q(x)|$，则 $\sum_x \min(p,q) = 1 - \text{TV}$（由 $\min(p,q)=\tfrac12(p+q-|p-q|)$ 两边求和），故 $P(\text{accept}) = 1-\text{TV}$。于是 $\mathbb{E}[r]$ 是**几何级数**而非线性乘积：对取非负整数值的 $r$，期望等于生存概率之和 $\mathbb{E}[r]=\sum_{j\ge1}P(r\ge j)$——$r\ge j$ 意味着前 $j$ 个 draft 全部通过，其概率为 $(1-\text{TV})^j$，故 $\mathbb{E}[r] = \sum_{j=1}^{K} (1-\text{TV})^j$（在首次拒绝处停止）。例如 $K=5,\ \text{TV}=0.2$ 时 $\mathbb{E}[r] \approx 2.69$，而 $K(1-\text{TV})=4$ 是高估约 50%；近似 $K(1-\text{TV})$ 只在 $K\cdot\text{TV} \ll 1$ 时成立。**接受率与 draft 分布和目标分布的重叠度直接挂钩**，这也解释了“为什么 draft 要与目标共享隐状态”。

这里的算例把 draft 各位置当作 i.i.d.（接受概率处处相等）；真实 EAGLE 是条件分布的链——每个位置都在“已知已接受前缀”的条件分布下生成，接受概率逐位置不同，上式只是同分布假设下的直觉与量级估计。

## 8.2 vLLM 的投机解码实现

### 8.2.1 调度侧：lookahead 与占位

第 5 章已铺垫三个机制，这里连起来：

```text
调度器：
- num_lookahead_tokens（EAGLE/draft model 时 = num_spec_tokens；DFlash 例外 = num_spec_tokens+1）
  → allocate_slots 预留的槽覆盖“真实 token + lookahead”两部分（num_lookahead_tokens 在
    vllm/v1/core/sched/scheduler.py:245-271 定义、:577-583 传给 kv_cache_manager），与 8.2.4 的死槽语义呼应
- 新 decode 请求 pad 成 1 + num_spec_tokens 个 token（-1 占位），保持 CUDA Graph uniform batch
- scheduled_spec_decode_tokens[req] = request.spec_token_ids（上步 draft，vllm/v1/core/sched/scheduler.py:641-657）
```

`-1` 占位的生命周期（时机 | 写入位置 | 代码）：

| 时机 | 写入位置 | 代码 |
| --- | --- | --- |
| 构造时 | Request.spec_token_ids 初始化为 [] | vllm/v1/request.py:173 |
| async 每步 | 把 [-1]*num_spec_tokens 赋给解码请求的 spec_token_ids（实际值后续在 worker 侧写） | vllm/v1/core/sched/async_scheduler.py:16, 23-25, 44 |
| sync 新解码请求 | -1 占位直接写入 scheduled_spec_decode_tokens | vllm/v1/core/sched/scheduler.py:1077-1080 |
| 调度时 | 按配额截断：spec_token_ids[:num_scheduled_spec_tokens]（这里只截断不补足） | vllm/v1/core/sched/scheduler.py:649-653 |
| 结构化输出 | update_draft_token_ids_in_output 先截断到调度数、grammar 校验剔除非法 draft、再 -1 补足 | vllm/v1/core/sched/scheduler.py:2180-2215（校验 :2203-2206、补 -1 :2207-2211） |
| worker 侧 | -1 与 draft 一起写进预分配行 | vllm/v1/worker/gpu/input_batch.py:326-383（写入 :373-382） |

**-1 的下游语义**：`-1` 作为 draft 进 rejection kernel 后必被拒——源码注释明确写 “padded draft token ids that should be rejected”（vllm/v1/sample/rejection_sampler.py:751-752 与 :809-811），被拒位置按正常目标采样产出 recovered token。所以新 decode 请求 pad 成 `1+K` 的实际效果是“首步无 draft、照常产出 1 个 token”，只是把 CUDA Graph 的 batch 形状占住。

### 8.2.2 执行侧：一次 forward 验证全部 draft

运行器把“采样 token + draft tokens”拼进 input_ids（`_combine_sampled_and_draft_tokens_kernel`，`vllm/v1/worker/gpu/input_batch.py:326` 定义、:410 启动），**draft 与真实 token 一起过模型、一起写 KV**（slot_mapping 为 draft 预留的槽）。采样位置由 `_calc_spec_decode_metadata`（vllm/v1/worker/gpu_model_runner.py:2859）算好：

```text
logits_indices:       每请求 K+1 个采样位置（K 个 draft 位置 + 1 个 bonus 位置）
target_logits_indices: 前 K 个（验证用）
bonus_logits_indices:  最后 1 个
```

**最小算例（单请求 K=2）**：行内序列是 `[t, d1, d2]`，t 为最后采样的真实 token（位置 0）。则 `logits_indices = [0,1,2]`（行内最后 3 个位置）、`target_logits_indices = [0,1]`、`bonus_logits_indices = [2]`。关键语义：**位置 $i$ 的 logits 预测的是行内第 $i+1$ 个 token**（自回归因果），因此验证关系是“用前一位的 logits 验当前位的 token”——draft $d_1$（位置 1）由位置 0（真实 token t）的 logits 验证，$d_2$（位置 2）由位置 1 的 logits 验证，bonus 从位置 2 的 logits 采样。所以 `target_logits_indices` 里的“K 个位置”指**采样位置**（t 之后的 K 个 logits 位），对应行内下标分别是 $1,2,\dots,K$——验证时把 logits 与 draft 错开一位，draft $d_i$ 的验证者是位置 $i-1$ 的 logits。多请求时各行的 `target`/`bonus` 按每行完整 token 数的累计偏移平铺开（decode 行即 $1+\text{draft\_len}$；混有 prefill 行时偏移更大），同一行内的相邻关系不变（计算见 `_calc_spec_decode_metadata`，vllm/v1/worker/gpu_model_runner.py:2859）。

### 8.2.3 验证：RejectionSampler

`vllm/v1/sample/rejection_sampler.py:92` 的 forward：

```text
① bonus 采样：先按正常采样器（带 top_p/top_k）从 bonus logits 采 1 个 bonus token
② target_logits → apply_logits_processors（penalties 等）→ apply_sampling_constraints
③ 逐位置验证：
   random 路径（kernel :774）:  accepted = draft_prob>0 and target_prob/draft_prob >= u
   greedy 路径（kernel :715）:  accepted = draft_id == target_argmax
   输出 buffer 初始化为 -1（PLACEHOLDER，:428-433）
   random 路径：被拒位置写入 recovered token（Gumbel：score = max(p-q,0) * inv_q 的 argmax）
   greedy 路径：被拒位置写入 target_argmax
   首次拒绝之后的位置不再写入，保持 -1 占位
   parse_output 按 -1 过滤出有效 token（:273）
```

输出行的填充规则由此确定：buffer 是 `(batch_size, max_spec_len+1)` 的行，`r` 个被接受的 draft 占前 `r` 格，第 `r+1` 格在 `r=K` 时写 bonus、`r<K` 时写 recovered，其余全为 `-1`。例（K=3）：接受 1 个 → `[d1, recovered, -1, -1]`；全接受 → `[d1, d2, d3, bonus]`。`parse_output` 丢掉 `-1` 后本步恰好产出 `r+1` 个 token——这就是 8.2.4 里 `num_accepted` 公式的来历（`num_sampled` 默认 1 时即 `len(generated) - 1`）。

draft 概率从哪来：draft 模型采样时缓存（`_last_draft_probs`）；n-gram draft 无概率——随机路径下 kernel 把 `draft_prob` 置为 1（vllm/v1/sample/rejection_sampler.py:817），即按 `p(x_i)` 接受（等价 $\min(1,p(x_i))$）。被拒后的重采样（vllm/v1/sample/rejection_sampler.py:913-918）与 8.1.2 的修正分布精确一致：n-gram 的 draft 分布退化为 $q=\delta_d$（只有 draft token $d$ 有概率 1），代入修正分布 $\frac{\max(p-q,0)}{Z}$ 恰为“$p$ 排除 $d$ 再归一化”，接受条件 $u\le p(d)$ 也正是 $\min(1,p(d)/q(d))$——kernel 只是把 $q$ 排除项的 prob 置 0 后做 Gumbel argmax，不物化 $q$。

### 8.2.4 结算侧：回滚语义

`update_from_output`（vllm/v1/core/sched/scheduler.py:1767-1785）：

```text
num_accepted = max(len(generated) - num_sampled, 0)   # num_sampled = num_sampled_tokens_per_step（默认 1）
num_rejected = num_draft_tokens - num_accepted
request.num_computed_tokens -= num_rejected
request.num_output_placeholders -= num_rejected
```

**KV cache 只做逻辑回滚，不做物理回滚**：被拒 draft 写入的槽变成“死槽”——后续 attention 的 `seq_lens` 不再覆盖它们，永远不会被读到（第 4 章的乐观 seq_lens 与此配合）。新 token 的写入覆盖或另分配新槽。**回滚的代价为零**，这是分页 + 逻辑 seq_lens 设计的一个隐藏红利。

**死槽会污染前缀缓存吗？**不会。哈希的入口只有**装满的块**：`cache_blocks` 里 `num_full_blocks = num_tokens // block_size`，只有这些块会被哈希入表（vllm/v1/core/single_type_kv_cache_manager.py:445-477；“We only hash full blocks”，vllm/v1/core/kv_cache_utils.py:685-726）——死槽只可能出现在未满的尾块里，未满块永不入表，而块一旦写满，块内所有槽位都已被有效 KV 覆盖。`request.free()` 只退块、不做哈希（vllm/v1/core/block_pool.py:719-742）。再配合 `allocate_slots` 里对 `cache_blocks` 入参的上限（`num_tokens_to_cache = min(total_computed + num_new, request.num_tokens)`，不含未验证的 draft，vllm/v1/core/kv_cache_manager.py:554-563），被拒 draft 的槽既不会以“脏前缀”入表，后续请求命中读到的一律是有效数据。

### 8.2.5 一张时序图（EAGLE 为例）

```text
step N（调度）:
  请求 r 有 1 个真实 token + K 个 draft（来自上步的 spec_token_ids）
  draft 拷入 scheduled_spec_decode_tokens 后立即清空 request.spec_token_ids（scheduler.py:657）
  allocate_slots 预留 (1+K) 槽
step N（执行）:
  目标模型 forward(1+K tokens) → logits
  RejectionSampler：接受 r 个 draft + bonus → 输出 r+1 个 token
  EAGLE draft 模型（用目标模型隐状态 + 移位输入）自回归生成下一轮 K 个 draft
step N（结算）:
  update_from_output: 接受 r 个 → 回滚 K-r 个（num_computed_tokens 减少）
  update_draft_token_ids 把新 draft 回填 request.spec_token_ids（scheduler.py:2158-2178，
  结构化输出先过 grammar 校验），下轮复用
```

## 8.3 Draft 模型的三种形态

本指南用“draft 从哪来”把 proposer 分成三族；验证侧只关心 draft 的分布 $q$（8.1.2 的 rejection 数学），不关心它怎么来的——三族差异只在 $q$ 的质量与生成代价：

- **模型型·链式**：draft 是带注意力的小模型（或目标模型的原生浅层模块），逐 token 自回归 $K-1$ 次（vllm/v1/spec_decode/llm_base_proposer.py:685 的循环）——独立小模型、EAGLE、Eagle3、MTP、Step3.5、Gemma4；
- **模型型·一次 forward**：一次 forward 产出全部 K 个 draft，无链式循环——Medusa、DFlash、PARD；
- **规则型**：零额外模型，draft 从文本结构里找——n-gram、Suffix decoding。

vLLM V1 的 `vllm/v1/spec_decode/` 下 `EagleProposer`（eagle.py:10）、`DraftModelProposer`（draft_model.py:19）、`MedusaProposer`（medusa.py:18）、`DFlashProposer`（dflash.py:23）、`SuffixDecodingProposer`（suffix_decoding.py:9）、`Gemma4Proposer`（gemma4.py:32）、`Step3p5MTPProposer`（step3p5.py:24）等全数归入上述三族，共享 8.2 的 lookahead + rejection 验证框架，差异只在“draft 怎么生成”。全景表：

| 方法 | 族 | 额外模型 | draft 节奏 | 论文/来源 |
| --- | --- | --- | --- | --- |
| 独立小模型（DraftModelProposer） | 模型型·链式 | 需要（独立 checkpoint，要求 TP 一致） | 逐 token | arXiv 2302.01318 |
| EAGLE | 模型型·链式 | 需要（浅层副本 + fc） | 逐 token | arXiv 2401.15077 |
| Eagle3 | 模型型·链式 | 需要 | 逐 token | EAGLE-3 |
| MTP | 模型型·链式 | 不需要（目标模型原生） | 逐 token | DeepSeek-V3 起 |
| Step3.5 | 模型型·链式 | 不需要 | 逐 token | — |
| Gemma4 | 模型型·链式 | 不需要 | 逐 token | — |
| Medusa | 模型型·一次 forward | 需要（K 个浅层头） | 一次 | arXiv 2401.10774 |
| DFlash | 模型型·一次 forward | 不需要（复用目标尾层） | 一次 | — |
| PARD（parallel_drafting） | 模型型·一次 forward | 配合 EAGLE/独立小模型 | 一次 | arXiv 2504.18583 |
| n-gram | 规则型 | 无 | — | prompt lookup decoding |
| Suffix decoding | 规则型 | 无 | — | arXiv 2411.04975 |

数字口径统一说明：`num_speculative_tokens` 在链式族里是**链长**（draft 总数 K），在 Medusa 里是**头数**，在 Suffix 里是**上限**（每次实际数可变）。

### 8.3.1 模型型·链式：逐 token 自回归（隐状态条件化）

链式族的共同点：第 $i$ 个 draft 依赖第 $i-1$ 个的输出，循环 forward $K-1$ 次（vllm/v1/spec_decode/llm_base_proposer.py:685）。族内分两条路线：独立小模型只吃 token id，自回归性质从零建模；其余成员（EAGLE 家族）在此基础上加**隐状态条件化**——draft 输入 =（当前 token 的 emb ∥ 目标模型刚算出的隐状态），等价于“已知全部历史 + 当前 token”的条件生成，这就是 8.1.3 里“draft 与目标共享隐状态”的落地。链式与 8.3.2 的并行 draft 相对；树形 draft（beam 树一次 forward 算所有分支）vLLM V1 不支持。

### EAGLE（链式基线）

链式族的机制主轴以 EAGLE 为例展开，8.2.5 的时序图就是它的全链路：

**EAGLE 的结构**（`vllm/model_executor/models/llama_eagle.py`）：目标模型尾部浅层 decoder 层副本 + 一个融合层 `fc`。EAGLE 的 decoder 层第一个实例 `input_layernorm` 被替换为 `nn.Identity()`（llama_eagle.py:42-44，即跳过第一层 norm）；`fc` 是 `ReplicatedLinear`，输入维度是 `hidden_size * 2`（llama_eagle.py:95-103）：

```text
draft 输入 = fc([embed_tokens(移位后的 input_ids) ; 目标模型最后隐层的输出 hidden_states])   # 拼接发生在调用点 llama_eagle.py:115 的 torch.cat，作为 fc 的输入传入，fc 本身不拼接
→ 浅层 decoder 层（第一层的 input_layernorm 为 Identity）
→ 取 logits 的 argmax → 下一个 draft token
```

- 输入左移一位 + 用上一步的 hidden states，是 EAGLE 的核心 trick：draft 每一步都“知道”目标模型刚算什么。具体机制（`set_inputs_first_pass`，vllm/v1/spec_decode/llm_base_proposer.py:824，左移逻辑 :849-854）：目标模型刚算完位置 $[s, s+K]$（真实 token + draft），draft 的输入序列 = `target_token_ids[1:]`（整体左移一位）再补上本步新采样的 token，与目标模型的隐状态拼接——于是 draft 的第一层前向等价于“已知全部历史 + 当前 token”的条件生成。逐位看：draft 输入第 $i$ 位 =（emb(目标第 $i+1$ 位 token) ∥ 目标第 $i$ 位 hidden $h_i$），模型每位预测的是“该 token 的后继”；最后一位（本轮新采样的 token）的预测就是下一轮的第一个 draft。源码注释自带的例子（:849-854）：`[a1, b1, b2, c1, c2, c3]` 左移一位后变为 `[b1, b2, c1, c2, c3, c3]`，再把各请求的采样位替换为新 token，如 `[a2, b2, b3, c2, c3, c4]`。
- **EAGLE 是链式不是树**：vLLM 的 EAGLE 逐 token 自回归 $K-1$ 次（chain，无树形分叉；树形实现仍是 TODO，vllm/v1/spec_decode/llm_base_proposer.py:1636-1637 的 FIXME 注释）。
- 权重共享：EAGLE checkpoint 没有自己的 embed/lm_head 时直接复用目标模型的（`_maybe_share_embeddings`，vllm/v1/spec_decode/llm_base_proposer.py:1425）。
- draft 层有自己的 KV cache group（第 4 章 4.7），每步用 `eagle_step_update_slot_mapping_and_metadata` kernel（`vllm/v1/spec_decode/utils.py:88`）推进 draft 的 position 与槽位。

### Eagle3

Eagle3 与 EAGLE 走同一个 `EagleProposer`，差异只在融合层 `fc` 的输入：EAGLE 只拼最后一层隐状态，Eagle3 拼**多个指定层**的辅助隐状态——`eagle_aux_hidden_state_layer_ids` 指定层号，`fc_input_size = target_hidden_size × num_aux_hidden_states`（llama_eagle3.py:181-187），并可选在拼接后归一化（`norm_before_fc` 对整个输入一个 RMSNorm :189-195，`fc_norm` 每段各一个 :198-206）。执行侧 `combine_hidden_states` 合并多个 aux 隐状态（llama_eagle3.py:359-365；vllm/v1/spec_decode/llm_base_proposer.py:529-545 对 eagle3 走这条路径）。与 EAGLE 相同：链式不是树；可选 `parallel_drafting`（llama_eagle3.py:309，见 8.3.2）。

### MTP

MTP（Multi-Token Prediction）把“预测后继 token 的浅层头”做成目标模型的**原生训练模块**：draft 权重就在目标 checkpoint 里，不需要独立小模型（vllm/config/speculative.py:718-727 对 mtp 直接复用目标模型权重）。结构（deepseek_mtp.py）：每层 `eh_proj` 把 [emb(当前位置 token) ∥ 上一步 draft 步的 hidden] 拼接投影（:114-120），过一层 decoder layer 后 `SharedHead`（RMSNorm + lm_head，:47-63）输出本步 logits、hidden 递给下一步（:134）——拼接方式与 EAGLE 同构，区别在归属：EAGLE 是外挂 checkpoint，MTP 是目标模型的扩展层。执行路径也与 EAGLE 一致：`use_eagle` 对 mtp 返回 True（vllm/config/speculative.py:1433-1437），走 `EagleProposer`。数字口径：`num_speculative_tokens` 是链长；同一 MTP 层重复 forward 超过一次会告警（vllm/config/speculative.py:922-931，接受率下降）。

### Step3.5

Step3.5 的 MTP（method `step3p5_mtp`）是“多层版”：`num_mtp_layers` 个 MTP 层，每步按 `spec_step_idx % num_mtp_layers` 轮换（step3p5_mtp.py:129），每层自带 `shared_head`（:143-147）。轮换使 `num_speculative_tokens > 1` 不再触发 MTP 的复用告警（vllm/config/speculative.py:924-927 排除 step3p5_mtp 与 inkling_mtp）。proposer 继承 `EagleProposer`（step3p5.py:24），并扩展**多 KV cache group**：每个 group 独立的 block table 与 slot mapping（step3p5.py:34-77）。

### Gemma4

Gemma 4 的 assistant draft（method `mtp`）仍是链式，但把“浅层模型”换成极轻的 **Q-only 层**：draft 层只有 Q 投影，K/V 直接读**目标模型的 KV cache**（gemma4_mtp.py:148-259，attention 的 K/V 用占位张量 :248-257），每个 draft 层经 `kv_sharing_target_layer_name` 绑定到目标模型的同类型层（sliding/full 分别绑定，gemma4.py:304-364）。配套机制：`constant_draft_positions=True`——所有 draft 步在同一个 position 上预测（gemma4.py:48），无需逐步推进位置；`pre_projection`/`post_projection` 在目标 backbone 维度与 draft 小维度之间桥接（gemma4_mtp.py:379-395）；共享目标模型 embed（gemma4.py:169-190）；可选 centroids 稀疏 logits（gemma4.py:116）。与 EAGLE 的差异：EAGLE 有自己的浅层 decoder 与独立 KV group（第 4 章 4.7），Gemma4 复用目标 KV、无 K/V 投影，draft 前向更轻。

### 8.3.2 模型型·一次 forward：并行族

并行 draft 一次 forward 产出全部 K 个，没有链式的 K-1 次循环。两条实现路线：**无 attention**——draft 只是隐状态的浅层变换（Medusa），不写自己的 KV；**有 attention**——draft 位置之间要么非因果互见（DFlash），要么输入填 mask 占位 token（PARD）。注意 **lookahead 是给 draft 自己的 KV 预留的槽**（8.2.1 里 allocate_slots 的预留语义）：无 attention 就没有 KV，自然不需要 lookahead（Medusa 为 0）；有 attention 才按 K 预留。

### Medusa

Medusa 的思路：目标模型后挂 K 个浅层“头”，第 $i$ 个头预测未来第 $i+1$ 个 token（头 0 即常规下一个 token），一次 forward 全部产出。输入输出：`MedusaProposer.propose` 只吃 `target_hidden_states`（medusa.py:40-58，`slot_mappings` 标了 unused :46-47），模型 forward 一次返回 $(batch, K)$ 的 draft 矩阵——没有“第 2 个 draft 依赖第 1 个”的链式依赖。头的结构（model_executor/models/medusa.py）：每个头 = `ResidualBlock`（SiLU + 残差 MLP，:19-38）+ 独立 `ParallelLMHead`（:81-90；`original_lm_head` 则所有头共享一个 lm_head，:73-79）；`token_map`/`truncated_vocab_size` 可把 draft 词表截断到高频词（:97-103、123-135）。

与 EAGLE 的异同：都用目标隐状态（隐状态条件化），但 EAGLE 链式 $K-1$ 次 forward、有 attention、写自己的 KV；Medusa 一次 forward、无 attention、无 KV——`num_lookahead_tokens = 0`（vllm/v1/core/sched/scheduler.py:257-271 只有 eagle/draft_model/dflash/dspark 设置 lookahead）。代价是每头独立预测、缺少“已知已接受前缀”的条件化（对比 8.1.3 的链式条件分布），接受率低一档，但 draft 前向几乎免费。数字口径：`num_heads == num_speculative_tokens`（transformers_utils/configs/medusa.py:62-67），即 `num_speculative_tokens` 是**头数**。论文的树形 draft（每头 topk 多候选 + `max_paths` 组合成 beam 树）vLLM 未实现，实际是“K 个深度 1 的平行猜测”（每头只取 argmax）。论文 arXiv 2401.10774。

### DFlash

DFlash（Qwen3.5 家族的方案）是“一次 forward + 有 attention”：draft 模型**复用目标模型尾部层**（`start_layer_id = target_layer_num`，qwen3_dflash.py:664-678），把目标隐状态直接算成 K/V 写进 KV cache（`precompute_and_store_context_kv`，dflash.py:280-284），query 侧是 $1 + K$ 个位置——真实采样 token + K 个 draft（in-fill 式，dflash.py:119）。draft 位置之间用**非因果注意力**互相可见（`dflash_causal`，dflash.py:77-81；qwen3_dflash.py:58-64 只有 sliding-window 层保持因果），一次 forward 即可并行产出全部 K。输入构造在 `set_inputs_first_pass`（override，dflash.py:105）里由 `copy_and_expand_dflash_inputs_kernel` 完成（:144-171）。

与 EAGLE 的异同：都用目标隐状态、都有 attention；但 EAGLE 链式（每步推进 position、独立 KV group），DFlash 一次 forward（query 间非因果互见）。数字口径：query 数 = $K+1$，`num_lookahead_tokens = num_spec_tokens + 1`（vllm/v1/core/sched/scheduler.py:262-266，注释写明 in-fill）。

### PARD（`parallel_drafting`）

PARD（Parallel Draft Models）是机制层的并行开关，作用于 EAGLE 或独立小模型之上：`parallel_drafting=True` 时 draft 输入**不左移**，未采样位置填 **mask 占位 token**，一次 forward 并行产出全部 K（vllm/v1/spec_decode/llm_base_proposer.py:112-119 定义开关，:622-630 跳过链式循环）。mask token 由配置提供（`pard_token`/`ptd_token_id`/`dflash_config.mask_token_id`，vllm/v1/spec_decode/llm_base_proposer.py:350-363），被 mask 位置的隐状态被擦除（:928-938），防止并行位置的注意力“偷看”未来的真实 token。mask 占位 token 与 8.2.1 的 `-1` 占位语义不同：`-1` 是调度层给“尚未生成 draft”的槽位占位（进 rejection 必被拒）；mask token 是 draft 输入序列里的真实 token，作用是让并行 forward 的未采样位置不泄露信息。官方文档注明 `parallel_drafting` 只兼容 EAGLE 和独立小模型（docs/features/speculative_decoding/README.md:86）；dflash/dspark 强制开启（vllm/config/speculative.py:999-1000）。与 Medusa 的差异：PARD 保留完整 attention、写自己的 KV（需要 lookahead 槽），Medusa 无 attention。

### 8.3.3 规则型：零模型

规则型不训练任何参数，draft 从文本结构里找；无概率的 draft 在 8.2.3 由 kernel 把 `draft_prob` 置 1 处理。

### n-gram

n-gram 从已生成的文本（prompt + 输出）里找与当前后缀匹配的重复片段，直接续写为 draft，零额外模型。`prompt_lookup_min`/`prompt_lookup_max` 定义匹配的 n 的范围（ngram_proposer.py:18-25）；GPU 版 `NgramProposerGPU` 把查找搬到 GPU（ngram_proposer_gpu.py:217）。

### Suffix decoding

Suffix decoding 用 **ArcticInference** 官方实现的后缀树（suffix_decoding.py:9）：每个请求维护一棵后缀树，从最近 `max_tree_depth` 个 token 中找最长匹配后缀，**动态决定本次深度**——`num_speculative_tokens` 只是上限（`max_spec_tokens` 取 num_spec 与剩余长度的较小者，suffix_decoding.py:84-86），每次实际 draft 数可不同。可配 `suffix_decoding_max_tree_depth`/`max_spec_factor`/`min_token_prob`（:20-22）。与 n-gram 的差异：n-gram 只在已生成文本里找精确重复、无概率、无深度概念；suffix 树能匹配之前生成的内容、带频次估计（`min_token_prob`）、深度自适应。论文 arXiv 2411.04975。

### 8.3.4 其他形态

- **MLP speculator**（mlp_speculator.py:60）：轻量 MLP 逐层预测未来 token，V1 已禁用（vllm/model_executor/models/registry.py:667-668 注释）。
- **Dynamic speculative decoding**：scheduler 按当前 batch 大小从预置表查最优 K（vllm/v1/core/sched/scheduler.py:1194-1198；docs/features/speculative_decoding/dynamic_speculative_decoding.md）。
- **Custom proposer**：用户自定义 proposer 类（custom_class_proposer.py:12）。
- **Hidden state extraction**（extract_hidden_states.py:29）：不投机，只导出目标模型中间隐状态供外部使用。
- **DSpark**：DeepSeek 的块式并行 draft，scheduler/config 已接入（vllm/v1/core/sched/scheduler.py:267-271），文档较少。
