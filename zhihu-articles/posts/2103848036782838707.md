## 一、先看失败现场：向量检索在多跳题上是"物理上限"，不是调参问题

一个典型问题：

> 「收购了 B 公司的企业，它的 CTO 后来加入了哪个项目？」

三段证据散在三个文档里：

- 文档 1：A 公司全资收购 B 公司
- 文档 2：张三被任命为 A 公司 CTO
- 文档 3：张三离职，加入盘古大模型项目

答案在文档 3，但文档 3 里没有「收购」「B 公司」「CTO」任何一个词。它和问题之间唯一的桥是「张三」，而「张三」根本没出现在问题里。

把 query 编码成一个向量去找邻近段落，文档 1、2 近，文档 3 远。把 top-k 从 10 调到 50 也许能捞到，但那是靠扩大召回面积，噪声一起进来，而 reader 只有 10 个位置。**没有任何一个 query 向量能同时靠近三段互不共享词汇的文本**——这是表达能力问题，不是参数问题。

下面这段无第三方依赖的代码可以直接复现这个"只看脸"的失败：

```text
# python3 直接运行，无第三方依赖
DOCS = {
    "doc1": "A 公司全资收购 B 公司",
    "doc2": "张三被任命为 A 公司 CTO",
    "doc3": "张三离职，加入盘古大模型项目",
}

def naive_score(q, d):          # 最朴素的词面相似度，代表「只看脸」
    return sum(1 for t in q.split() if t in d)

q = "收购 B 公司 的企业 它的 CTO 后来 去了 哪个 项目"
ranked = sorted(DOCS.items(), key=lambda kv: -naive_score(q, kv[1]))
for name, text in ranked:
    print(f"{naive_score(q, text):>2}  {name}  {text}")

#  3  doc1  A 公司全资收购 B 公司
#  2  doc2  张三被任命为 A 公司 CTO
#  1  doc3  张三离职，加入盘古大模型项目   ← 唯一的答案，排最后

```

换成语义向量也一样。换成更大的 embedding 模型呢？论文给了负面答案：在 MuSiQue 上，bge-large-en-v1.5 只有 56.32，7B 级的 NV-Embed-v2 是 68.84、GritLM-7B 是 66.22，离 SAG 的 80.36 仍有十几到二十几个点。**换更大的 embedding 模型补不上多跳这个缺口。**

### 图 RAG 补上了边，但成本压在入库那一刻

知识图谱把文档拆成 `(头实体, 关系, 尾实体)`，多跳变成图上走路。代价有三个：

| 成本 | 具体形态 | 论文 v2 量到的数 |
| --- | --- | --- |
| 构建成本 | 通读全语料、逐段调 LLM 抽取、社区聚类与摘要 | GraphRAG 在 11,656 chunk 上耗 10.15 h / 125.12 M token；LightRAG 25.94 h / 103 M token |
| 语义碎片 | 一句「以 35 亿元全资收购」拆成多条三元组，事实边界消失 | 换回原子三元组索引，Recall@5 掉 2.75 |
| 增量困难 | 新文档可能改变社区划分与摘要，严重时要重跑 | 论文将 incremental updates 列为固有问题 |

最刺眼的是图其实是碎的：在同一批 MuSiQue 语料上，GraphRAG 的实体图有 **66,472 个连通分量、51.1% 实体是孤立节点**；SAG 的关联结构只有 400 个分量、1 个孤立节点。你以为在做多跳推理，大部分时候还在做单点匹配，只是多付了建图的钱。

### 真正的分歧点：图什么时候建

- 向量 RAG：**不建图**，所以没有可走的边
- 图 RAG：**入库时建全图**，所以边很贵且容易碎
- SAG：**查询时临时建局部图**，只给这一次查询用

SAG 把"关系"从存储问题变成计算问题：只维护一堆关联行，等查询来了现拼。新增文档只是 `INSERT` 若干行，不动任何全局结构——这是它敢说"增量友好"的全部底气；反面是每次查询都要重新走一遍路。

## 二、SAG 是什么：把关系从图数据库搬回一张 SQL 表

**SAG（SQL-Retrieval Augmented Generation，arXiv 2606.15971，Zleap AI）** 的做法：

1. 离线：每个文本块调 1 次结构化输出 LLM，产出**恰好一个语义完整的 event** 和一组**带类型的 entity**
2. 只把 `(event_id, entity_id)` 关联行写进数据库，不物化任何全局图
3. 在线：`SQL JOIN` 沿共享实体向外扩一层，把相关事件拼成一条只属于这次查询的局部超边
4. 最后**只把原始 chunk** 交给 reader 生成答案

论文的立论是这句：`the connections available during retrieval are determined before the query arrives`——检索时可用的连接，在查询到来之前就被定死了。SAG 想让连接在查询发生时再激活。

### 三种组织方式的差别不在检索算法，而在"数据准入时被组织成什么样"

|  | 向量 RAG | 图 RAG（三元组） | SAG（event-entity） |
| --- | --- | --- | --- |
| 记住的东西 | 坐标 | 边（入库时固定） | 多对多关联行 |
| 段落之间 | 没有可走的路 | 有路，但要提前修 | 查询时才走出来 |
| 增量更新 | 加向量即可 | 可能重算全图 | INSERT 若干行 |
| 代价 | 多跳必断链 | 10.15 h 建图 | 每次查询重走 + 18.67 s |

### 索引层三条硬规则

| 规则 | 它保证了什么 |
| --- | --- |
| 1 chunk → 恰好 1 event | event 与原文一一对应，检索到的事件永远能映射回确定 chunk，不会"拼出原文里没有的事实" |
| 1 event → 一组带类型实体 | 实体是 join key，没有实体的 event 是孤岛 |
| 实体类型封闭为 11 类 | 同一类实体不会出现十种叫法，join 时能对上 |

![](https://pica.zhimg.com/v2-a8c4a13c8e06e7069d508fa1daaadf32_1440w.jpg)

> 图 2：只写 `(event, entity)` 关联行，潜在超边不落库；工程上限由实体抽取质量决定，不由检索算法决定。

11 类实体是：`time, location, person, organization, group, subject, work, product, action, metric, tags`。注意「收购」「离职」「任命」这类**动作被当成实体而不是关系谓词**——这让"哪些事件涉及收购"变成一次实体匹配，比谓词推理稳定得多。网上流传的「9 类」是误传，把 `group/subject/work/tags` 并进了 topic 与 label。

这五行合起来就是该事件的**潜在超边**——它此刻并不存在，只是五条记录；等查询需要"张三 + A 公司 + 离职"的事件集合时，SQL 才把它们拼成一条边。

### 为什么不用三元组

`(A 公司, 收购, B 公司)` 看着干净，但拆的过程会丢掉三样东西：**量词与条件**（35 亿元、全资）、**同源性**（同一件事的三个事实散了）、**谓词抽取的稳定性**（开放集合，同一意思能抽十种关系名）。SAG 选择不拆，整句作为事件文本保留，实体只做索引键。

这个选择值多少钱？消融给的答案是 **2.75 个点**（换成原子三元组索引，R@5 从 80.36 → 77.61）。记住这个数，第五节会拿它做对照。

### 工程上真正会翻车的三处

1. **关键桥接实体被漏抽**：如果模型认为「张三」只是主语、没抽成实体，整条链当场断掉，调参救不了
2. **同名不同人**：人事文档和供应商合同里的「张三」是两个人，只按名字 join 会拼出一条"听起来合理但完全错误"的链——破坏性远大于漏召回
3. **长文档实体归一**：「A 公司」「A集团」「该公司」「甲方」指同一对象。11 类清单只解决类型归一，**名称归一得自己补**（字符串规范化 + 别名表）

一个立刻能做的检查：抽 100 个 event，人工看"答对了的那批题"依赖的桥接实体在不在库里、名称是否唯一。这比调任何检索参数都更有效。

> 补充一个论文留白：全文没有报告 chunk size、切分策略和 embedding 维度。复现时这部分要自己定，而它直接决定 event 质量。太大（2000 字）会逼模型写"综合事件"、实体集膨胀；太小（一句）会让「他于次年离职」无法解析。常见折中是按段落/标题切、**300–600 token** 并保留结构边界。抽取 prompt 要同时喂三样东西：当前 chunk 正文、**前一个 chunk 的上下文**（用来还原跨块指代）、11 类封闭清单。

## 三、查询层：18 秒里，SQL JOIN 只占几毫秒

### 五步链路

1. **抽 query 实体**：不是把整句做向量，先抽出 1–3 个实体（本例是 B 公司、CTO），让"问题里的名词"变成可 join 的键
2. **双路召回**：结构路径用实体命中事件（`τ_ent = 0.9`，严），语义路径用事件向量直接检索（`τ_evt = 0.4`，松），两路取并集
3. **合并 + 前进一层**：候选集沿共享实体再走一格（`L=1`）
4. **终选**：把 `K_cand = 100` 个候选事件一起交给大模型，在一个上下文里**联合比较**，选出 `K_event = 5` 条
5. **补位**：语义路径把剩余名额填到 `K_out = 10` 段 chunk，交给 reader

| 参数 | 默认值 | 含义 |
| --- | --- | --- |
| L | 1 | 扩展深度（event → entity → event 迭代几轮） |
| K_seed / frontier | 50 / 50 | 种子事件数 / 每轮前沿预算 |
| K_cand | 100 | 进入大模型终选的候选事件数 |
| K_event | 5 | 结构路径最终选中几个事件 |
| K_out | 10 | 返回给 reader 的 chunk 总数 |
| K_pool | 500 | 有界激活模式下先召回的 chunk 数 |
| τ_ent / τ_evt | 0.9 / 0.4 | 实体扩展 / 事件直检的相似度阈值 |

> 图 3：JOIN 只占几毫秒，瓶颈是「100 条候选整批比较」；红色那步贡献了单项最大跌幅 −13.25（论文 v2 Table 8）。

### 两跳 SQL 长什么样

```text
-- PostgreSQL 语法，语义按论文命题构造，字段名自拟，非官方实现
WITH q_ent AS (SELECT unnest(ARRAY['B 公司', 'CTO']) AS name),
-- 第 0 跳：query 实体 → 种子事件（结构路径）
seed AS (
    SELECT ee.event_id, COUNT(*) AS hits
    FROM event_entity ee
    JOIN q_ent q ON q.name = ee.entity_name
    GROUP BY ee.event_id
    ORDER BY hits DESC
    LIMIT 50                      -- K_seed = 50
),
-- 第 1 跳：反向展开种子事件的实体，再 join 回事件（= 二部图上走两格）
hop1 AS (
    SELECT DISTINCT ee2.event_id
    FROM event_entity ee1
    JOIN event_entity ee2 ON ee2.entity_name = ee1.entity_name
    WHERE ee1.event_id IN (SELECT event_id FROM seed)
      AND ee2.event_id NOT IN (SELECT event_id FROM seed)
    LIMIT 50                      -- frontier budget = 50
),
cand AS (
    SELECT event_id FROM seed
    UNION
    SELECT event_id FROM hop1
    LIMIT 100                     -- K_cand = 100
)
SELECT e.event_id, e.text, e.chunk_id
FROM event e JOIN cand c USING (event_id);

```

这段 SQL 里**没有权重、没有迭代、没有收敛判断**。"多跳"就是多写一个 CTE。这也是它相对 Personalized PageRank 式扩展最大的工程优势：查询计划确定，能进数据库执行计划器、能加索引、能并行；而且路径不打折——PPR 多走一跳要乘一次转移概率，四跳后信号已经很弱，SAG 走两格就是走两格。

论文把它写成命题：数据是二部结构（事件侧、实体侧），**一次 join 等价于在二部图上走一格**，L 层扩展覆盖二部距离 ≤ 2L 的事件。

### 两个旋钮都已经饱和

| 扩展深度 L | 0 | 1（默认） | 2 | 3 | 4 |
| --- | --- | --- | --- | --- | --- |
| Recall@5 | 69.41 | 80.36 | 80.47 | 80.40 | 80.71 |

0→1 拿 **10.95** 个点，1→4 一共只拿 0.35。第一层已经把共享实体能提供的信息榨干了，再走连上的都是"碰巧提到张三"的噪声。

`K_event` 同理：0→56.23、2→73.52、4→79.80、**5→80.36**、6→79.93、10→79.80。5 是饱和点且不单调——结构路径选得多，留给语义路径补位的名额就少，而语义路径在"字面相似但无实体连接"的题上是唯一救命稻草。

还有一条很值得抄的工程经验：**有界激活**。`K_pool = 500` 时 R@5 是 79.57，全池（11,656）是 80.36——只激活不到 5% 的语料，保留约 99% 的效果。先窄后精，别让结构化操作跑在全量数据上。

### 终选才是重头，也是 18 秒的主要去处

拿到 100 个候选后，SAG 不按分数截断，而是让大模型**在一个上下文里联合比较**选出 5 条。把它换成逐点打分的 Qwen3-Reranker-8B，R@5 从 80.36 掉到 **67.11（−13.25）**，比"完全不扩展"（−10.95）掉得还多。

原因很直接：逐点 reranker 判断的是 `(query, 单条候选)` 相关性，而多跳题需要判断的是"这 5 条**合起来**够不够回答"。单条都不够相关、组合起来才够——这个信号只存在于联合上下文里。

论文只给了总账：检索 18.67 s + 问答 6.36 s = 端到端 **25.03 s**（HippoRAG 2 是 0.66 + 8.50 = 9.16 s）。JOIN 不是瓶颈，**大模型在 100 条候选上做联合比较**才是。一个可验证的推论：把 `K_cand` 降到 50，端到端只从 25.03 降到 22.68 s，说明固定开销（query 实体抽取、池化召回）本身就占了不少。

## 四、实验数据怎么读：80.36% 是真的，那 12 个「–」也是真的

### 主表（论文 v2 Table 4）

| 数据集 | 语料段落 | SAG R@2 | SAG R@5 | 最强基线（方法 / R@5） | 领先 |
| --- | --- | --- | --- | --- | --- |
| HotpotQA | 9,811 | 91.55 | 96.50 | NV-Embed-v2 / 95.25 | +1.25 |
| 2WikiMultiHopQA | 6,119 | 83.93 | 93.34 | HippoRAG 2 / 90.35 | +2.99 |
| MuSiQue | 11,656 | 63.62 | 80.36 | NV-Embed-v2 / 68.84 | +11.52 |

三点必须注意：

- **"最强基线"不是同一个方法**：HotpotQA / MuSiQue 上是 7B 级向量模型 NV-Embed-v2，2Wiki 上才是同为图检索的 HippoRAG 2。若只跟 HippoRAG 2 比，三个数据集是 +2.15 / +2.99 / +15.23，引用时要说清跟谁比。
- **领先幅度随难度单调放大**（+1.25 → +2.99 → +11.52），这个趋势比单个数字更有说服力：增益确实来自"多跳"这个能力维度，不是通用召回能力的普遍提升。反过来看更要紧：在最简单的 HotpotQA 上只领先 1.25 个点，而 1,000 题的 95% 置信区间约 ±2.5 个点——**统计上不显著**。业务以单跳/双跳为主时，投入这套工程成本换不回可测量收益。
- **规模是 11,656 段**：三个数据集都是抽 1,000 题、用这些题涉及的段落建小语料池，而 HotpotQA 全库约 523 万段，差 500 倍。"亿级数据、秒级延迟"是产品声明，来自另一套系统和另一批数据，**不能互相引用**。

### 三个口径陷阱

**① any-hit 会高估。** 论文的 Recall@K 定义是"top-K 里至少有任意一段支持证据就算命中"。一道题有 3 段证据、只召回 1 段，在 any-hit 下就是满分 100%，而多跳问答必须 3 段都拿到。论文 §4.3 自己承认这 `tends to overstate performance under strict multi-hop evaluation`。同一份结果三种口径能差出很多：

```text
# python3 直接运行
gold = {0, 5, 9}                                  # 一道题的 3 段标准证据
topk = [3, 5, 7, 9, 11, 12, 14, 15, 18, 20]     # 检索返回的 top-10

any_hit = len(gold & set(topk)) > 0              # 论文口径
all_hit = gold.issubset(set(topk))               # 严格口径
passage_recall = len(gold & set(topk)) / len(gold)
print(f"any-hit={any_hit}  all-hit={all_hit}  passage_recall={passage_recall:.2f}")
# any-hit=True  all-hit=False  passage_recall=0.67

```

所有方法用同一口径，横向比较仍有效；但别把 80.36% 读成"80% 的题都能答对"——端到端 EM 在 MuSiQue 上只有 **50.20**，低了整整 30 个点。

**② 12 个「–」意味着有些对比根本不存在。** 主检索表里 GraphRAG、LightRAG、HyperGraphRAG、HyperRAG 四行 × 三个数据集全是空缺，因为这些方法返回的是生成答案而不是排序段落，段落级 Recall 无从计算。所以"SAG 在检索指标上打败 GraphRAG"没有数据支撑。真正可比的是 EM/F1 表：

| 方法 | MuSiQue F1 | 2Wiki F1 | HotpotQA F1 | 平均 F1 |
| --- | --- | --- | --- | --- |
| BM25 | 35.19 | 56.26 | 64.64 | 52.03 |
| GraphRAG | 54.14 | 72.08 | 76.29 | 67.50 |
| HippoRAG 2 | 47.49 | 74.34 | 77.24 | 66.36 |
| SAG | 61.15 | 78.06 | 79.66 | 72.96 |

端到端差距从"十几个点"缩到"几个点"，是检索增强系统的常态：召回提升会被 reader 的容错和"多给的噪声"吃掉一部分。而且 F1 是端到端结论，混合了检索质量、上下文长度、reader 行为三件事，**不能单独归因给检索层**。

## 五、消融：到底是谁在承重

以默认配置为基线，每次只改一处，MuSiQue Recall@5：

| 改动 | Recall@5 | 相对基线 | 它实际在测什么 |
| --- | --- | --- | --- |
| 默认 SAG | 80.36 | — | 基线 |
| 换成原子三元组索引 | 77.61 | −2.75 | event 这个数据模型值多少 |
| 关闭实体扩展（L=0） | 69.41 | −10.95 | 多跳走这一步值多少 |
| 终选换成 Qwen3-Reranker-8B | 67.11 | −13.25 | "整批联合比较"值多少 |
| 只用语义路径（K_event=0） | 56.23 | −24.13 | 结构路径整体值多少 |

![](https://pic4.zhimg.com/v2-445f4bf1922421d2941a3d567dd5aba9_1440w.jpg)

> 图 4：四个变体的 Recall@5 对照基线 80.36。数据模型只值 2.75 分，「让大模型整批比较」值 13.25 分。

结论有点反直觉：**掉得最狠的不是"事件超边"这个招牌设计，而是"让大模型整批比较候选"这个通用技巧**。SAG 全文反复强调 event 保留语义完整性、三元组会碎片化，这个论点直觉上成立，实测却只值 2.75 个点——它解决的是"事实边界"的正确性问题，不是"召回率"的性能问题。

如果只从这篇论文里拿走一条工程结论，就是：**多跳检索的最后一步不要用逐点打分，要让模型看整批。**

有个真实的复现踩坑很典型：有人把终选的 Qwen3.6-Flash 换成本地 bge-reranker-v2-m3（延迟低、成本几乎为零），其余不动，R@5 从 80 掉到 62 附近。先怀疑 join 写错（dump 100 条候选逐条比对，排除），再怀疑实体抽取质量（抽 50 个 event 人工核对，覆盖率 90%+，排除），最后换成"把 100 条塞进一个 prompt 让模型排序"，同样用本地小模型，分数回到 76 左右。**不是模型不行，是"逐点打分"这个范式不行**——13 个点的损失大到足以让人误判"论文是假的"。

### 四项掉点不能相加

```text
base = 80.36
variants = {"换成原子三元组": 77.61, "关闭扩展(L=0)": 69.41,
            "终选换 reranker": 67.11, "只用语义路径": 56.23}
total = sum(v - base for v in variants.values())
worst = min(variants.values()) - base
print(f"四项掉点之和: {total:+.2f}")
print(f"最差变体实际掉点: {worst:+.2f}")
print(f"重叠部分: {total - worst:.2f}")
# 四项掉点之和: -51.08
# 最差变体实际掉点: -24.13
# 重叠部分: -26.95（约 27 个点被重复扣分）

```

重叠的 27 个点基本是同一批"真正的多跳题"：它们的失败同时触发多个部件的短板。反过来也说明 SAG 的提升集中在少数难题上，与"领先幅度随难度放大"一致。

## 六、工程账与复现

### 先把账摊开（论文 v2 Table 8，同机同 reader 模型）

| 方法 | F1 | 离线索引 | 离线 token | 检索 s/query | 端到端 s/query | token/query |
| --- | --- | --- | --- | --- | --- | --- |
| RAG (BGE) | 42.80 | 0 h | 0 | 0.10 | 1.85 | 1,727 |
| HippoRAG 2 | 47.49 | 2.30 h | 15.93 M | 0.66 | 9.16 | 4,788 |
| GraphRAG | 54.14 | 10.15 h | 125.12 M | 0.23 | 12.79 | 11,438 |
| SAG | 61.15 | 4.57 h | 28.26 M | 18.67 | 25.03 | 11,536 |

四行结论：

1. **索引成本处在中间**：4.57 h / 28.26 M token，比 GraphRAG 省 55% 时间、77% token，但比 HippoRAG 2 贵一倍（每个 chunk 都要调一次结构化输出）
2. **在线检索是明显短板**：18.67 s vs 0.66 s，差 **28 倍**，直接排除绝大多数在线场景
3. **没有因为"结构化"而更省上下文**：11,536 token/query 与 GraphRAG 的 11,438 同一量级，因为把 100 条候选塞给大模型本身就贵
4. **问答环节反而最快**（6.36 s，GraphRAG 12.56 s），可能是证据更聚焦、生成更短，但这点优势被检索的 18 秒吃干净了

换算成容量规划（可直接改参数跑）：

```text
RETRIEVAL_S, QA_S = 18.67, 6.36          # MuSiQue, K_cand=100
TOTAL_S = RETRIEVAL_S + QA_S
peak_qps = 0.2                           # 峰值每秒查询数（示例：内部知识库）
concurrency = peak_qps * TOTAL_S
tokens_per_q = 11_536
daily_q = int(peak_qps * 3600 * 8)      # 按每天 8 小时高峰算
print(f"单条端到端: {TOTAL_S:.2f} s")
print(f"需要并发槽位: {concurrency:.2f} → 取整 {int(-(-concurrency // 1))}")
print(f"高峰日请求量: {daily_q:,} 条")
print(f"高峰日 token: {daily_q * tokens_per_q / 1e6:.1f} M")
# 单条端到端: 25.03 s / 并发槽位 6 / 高峰日 5,760 条 / 66.4 M token

```

0.2 QPS 的小系统，日 token 就是 6,600 万。任何想在生产用它的团队，第一件事都该是把 `K_cand` 降到 50 试试（省一半 token，只掉 1 个点：79.35）。

### 复现

```text
git clone https://github.com/Zleap-AI/SAG-Benchmark.git
cd SAG-Benchmark/sag
uv sync --frozen
test -f .env || cp .env.example .env     # 填 LLM / Embedding 端点
source .venv/bin/activate

```

四个前提：

- 环境：Python 3.11+、uv、Docker Compose，以及可用的 LLM 与 Embedding 服务端点
- **Rerank 端点只在跑 “final selection 消融” 时才需要**，主实验不需要它，别被 `.env.example` 里的字段误导
- CLI 支持复现 SAG、BM25、bge-large-en-v1.5 三条基线，另有 atomic 上传/检索用于三元组消融；**没有 GraphRAG / LightRAG 的复现代码**，那几行数字是论文作者自己跑的
- 仓库里有两套实现：`sag/`（原实现，MySQL/ES 语义）与 `sag2/`（SQLite 版）。目录、配置、索引都不同，**不要混用 `.env`**

一个现实预期：光把三个数据集的 LLM 抽取跑完，按 28.26 M token 量级，用商用 API 也要几百到上千元人民币。建议先在 MuSiQue 的 200 题子集上跑通链路再决定要不要全量。

## 七、该不该上：选型判据与落地顺序

**一句话判据：如果一道题的正确回答必须组合两段以上互不共享词汇的文本，SAG 类方案才有意义；否则你付的是延迟和 token，换回来的是噪声。**

| 你的场景 | 建议 |
| --- | --- |
| 延迟要求 < 1 s（在线客服、搜索框） | 别用，单条检索就要 15.9–18.7 s |
| 以单跳 / 定义查找 / FAQ 为主 | 向量 + rerank 足够，18 秒换不来收益 |
| 多跳、可离线或异步（跨文档推理、尽调、审计） | 值得上，+15.23 个点就在这里 |
| 语料持续增长、要求增量友好 | 看关联表方案或 SAG2，追加文档只 INSERT |

![](https://pic3.zhimg.com/v2-26db36934e69702dcf703a23e7b0bed6_1440w.jpg)

> 图 5：四类场景的选型判据与落地顺序，统一判据是「正确回答是否必须组合两段以上互不共享词汇的文本」。

如果确定要上，落地顺序建议：

1. **先只抄「实体扩展 + 单层 join」**——这部分值 10.95 个点，且不依赖它的 event 数据模型
2. **终选一定要用整批联合比较**，别用逐点 reranker（这里差 13.25）
3. `K_pool` 控制在全库 5% 以内，`K_cand` 从 50 起调
4. 实在受不了延迟，走 SAG2 的路线：去掉 embedding 与 LLM 抽取，接受四跳题的损失

## 八、版本演进：半年后作者自己换了条路

引用这篇论文必须标注版本。v1 → v2 改动不小：

| 项目 | v1 | v2 |
| --- | --- | --- |
| 2WikiMultiHopQA R@5 | 88.00 | 93.34 |
| 摘要核心声明 | “9 项 Recall 指标中 8 项最优” | 该句已不再出现 |
| 摘要部署声明 | “亿级数据、秒级延迟” | 改为更保守的表述 |
| 消融细节 | 部分数字后被替换 | 重跑了 Qwen3-Reranker-8B 等 |

二手文章里流传的「R@2 平均提升 11.16 个百分点」是 v1 口径，按 v2 表格复算是 **11.56**（MuSiQue +14.10、2Wiki +7.38、HotpotQA +13.20）。两种读法都成立：正面看是作者在补证据、修口径；谨慎看是——如果一个数字两个月内从 88.00 变成 93.34，引用时不标版本就会出错。

更值得玩味的是仓库里后来多了一套 `sag2/`（对应 arXiv 2610.22588），做的事几乎是 SAG 的反面：

| 维度 | SAG | SAG2 |
| --- | --- | --- |
| 索引期模型调用 | 每 chunk 1 次 | 0 次 |
| 检索底座 | 向量 + SQL JOIN | SQLite + BM25，无 embedding |
| 关系表示 | event + 实体关联行 | event 共现（JEV） |
| 报告成绩 | MuSiQue R@5 80.36 | MuSiQue R@10 86.62 |

**注意别把 86.62 和 80.36 直接相减**，不是同一把尺子；正确比较对象是 SAG 的 R@10 = 83.37，SAG2 高 3.25 个点。代价是论文自己承认的：四跳题 AE@10 只有 28.31%。

这条演进线本身就是最好的注脚：当"用 LLM 换召回"的成本无法被生产环境接受时，作者选择降低 LLM 依赖，而不是继续堆效果。你在做选型时，大概率会走到同一个岔路口。

### 五条核查清单

下次看到关于 SAG 的爆款文章，用这五条对一遍：

1. 「Recall@2 平均提升 11.16 个百分点」→ v1 口径，v2 复算 11.56
2. 「亿级数据、秒级延迟」→ 产品声明；论文实验是 11,656 段、18.67 s/query
3. 「打败了 GraphRAG 的召回」→ 检索表里 GraphRAG 那行是「–」，可比的是端到端 F1（61.15 vs 54.14）
4. 「11 类实体」→ 对；「9 类」是把 group/subject/work/tags 并进了 topic 与 label
5. 「消融证明超边是关键」→ 恰恰相反，换三元组只掉 2.75，掉最多的是终选换 reranker（−13.25）

## 九、总结

SAG 的价值不在于它把关系存成了 SQL 表，而在于它证明了**「查询时现场建关系」这条路走得通，以及走通它要付多少钱**。

三句话收尾：

- **数据结构上**：把"关系"从入库时写死的全局图，变成查询时按需拼装的关联行，换来真正的增量友好
- **效果归因上**：真正承重的不是 event 数据模型（2.75），而是「沿共享实体走一格」（10.95）和「让大模型整批比较候选」（13.25）——与其说是图 RAG 的胜利，不如说是上下文工程的胜利
- **工程决策上**：25 秒端到端、11,536 token/query，把它锁死在离线 / 异步的多跳场景；在线场景先抄它的两个关键动作就够了
