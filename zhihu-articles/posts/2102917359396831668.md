上一篇把现代架构的开销拆成三本账。这一篇讲第一本，也是过去五年最成功的一次改动：MoE。

它的动机很单纯：**让模型多存参数，但每个 token 只算一部分。**

结果是 V4.1-Flash 用 552B 的总容量，每 token 只激活 16B，激活率不到 3%。这一篇拆它怎么做到的，以及为此付了什么代价。

### 1. 先把参数账算清楚

Llama 3 8B 里，FFN 是绝对大头。一层 FFN 是三个 4096×14336 的矩阵，约 1.76 亿参数；attention 的 Q、K、V、O 四个投影加起来才 4200 万。32 层里，FFN 占约 5.6B，attention 占约 1.3B。

这个比例不是 Llama 特有的。标准 Transformer 的 FFN 扩展比通常是 4 倍，所以 FFN 参数一般是 attention 的 3 到 4 倍。想让模型记住更多事实、更多模式，最直接的办法就是加宽 FFN。

但每加宽一分，每个 token 的计算量就涨一分。参数和算力被同一根轴绑着。

### 2. 基本结构：稀疏激活

![](https://pic1.zhimg.com/v2-8c8fb0270e2448dc38e95fb139a46b54_r.jpg)

*MoE 的稀疏激活路径：router 选 6 个，共享专家常在线。*

MoE 换了一个问法：能不能只让每个 token 走一小部分 FFN？

DeepSeek-V4.1-Flash 每层有 1 个共享专家和 384 个路由专家。每个专家的中间维是 2304，三个矩阵下来约 3540 万参数。一层 384 个路由专家合计约 136 亿参数。

每个 token 只选 6 个路由专家，加上那个一直在线的共享专家，一共碰 7 个，约 2.5 亿参数。40 层叠起来，专家部分总共约 544B，但每个 token 只激活约 10B。加上 attention 和嵌入，就是官方说的 decode 16B。

总参数 552B，激活率不到 3%。

### 2.1 两个设计

第一，专家做得小而多。Llama 的 FFN 是 14336 维，一个大专家；DeepSeek 把它拆成 384 个 2304 维的小专家。6 个专家从 384 个里选，组合数约 4 万亿。

组合多了，模型可以用不同的专家组合处理不同的模式，这比「8 选 2」的分工空间大得多。小专家的另一个好处是负载更细：384 个桶分摊 token，比 8 个桶更容易平衡。

第二，共享专家一直在线。路由专家负责细分模式，共享专家负责所有 token 都要用的通用变换。这样路由专家不用重复学通用部分，容量可以用在刀刃上。

这个「共享 + 路由」的结构来自 DeepSeekMoE，现在已经被多数开源模型采用。

### 2.2 路由是怎么做的

路由本身是一个小网络：每个 token 的 hidden state 过一个线性层，算出 384 个分数，取 top-6。

V4.1 用的是 `sqrtsoftplus` 作为打分函数（config 里的 `scoring_func`），而不是常见的 softmax。这个选择配合 `routed_scaling_factor = 1.5`，控制被选中专家的输出尺度。

这类细节论文正文没有展开，但从配置能看出一个取向：**MoE 的稳定性和打分函数的形状关系很大。** softmax 会把分数压进一个概率单纯形，sqrtsoftplus 没有这个约束，top-k 的选择更自由，但输出需要额外缩放。

### 2.3 负载均衡：不加辅助损失的做法

MoE 最怕的是路由塌陷：router 把大部分 token 都送给少数几个专家，其他专家就是死权重，GPU 也会一边忙死一边闲着。

传统做法是加一个辅助损失，惩罚不均衡。但辅助损失会和主目标打架，权重调不好就掉点。

DeepSeek 用的是 aux-loss-free 的偏置调整：每个专家有一个修正偏置，训练中根据负载慢慢调，不往主损失里加辅助损失。配置里对应 `topk_method = noaux_tc`。

具体机制是：偏置只影响「选谁」，不影响「权重多少」。每步训练后，偏置按专家的实际负载更新——负载高的降一点，负载低的高一点。

保留一个极小的序列级平衡损失（权重 0.0001），只用来防止单条序列内部出现极端失衡。

这个设计的好处是把均衡从「优化目标」降级成「选路修正」，不会污染梯度。

### 3. 代价：通信和显存

MoE 不是白拿的。它把成本从「每个 token 的计算」搬到了两个地方。

### 3.1 all-to-all：MoE 最贵的那一笔

![](https://pic1.zhimg.com/v2-b49be0101f3420ad8e42a40322db2de8_r.jpg)
*all-to-all：token 要过卡。*

先问一个问题：专家为什么要分散在多张卡上？

因为放不下。每层 384 个专家，每个 3,540 万参数，一层就是 136 亿。40 层叠起来 544B。一张 H800 只有 80 GB，塞不进。

所以第 1-96 号专家放 GPU 0，第 97-192 号放 GPU 1，依此类推。这是**专家并行（EP）**。

问题来了：GPU 0 上的 token，router 算出它该去第 200 号专家，而 200 号在 GPU 2 上。

token 必须过卡。

### 它和普通通信的区别

平时我们说的通信（比如数据并行的 All-Reduce）是「大家把数加起来，每张卡得到同样的结果」。all-to-all 不是这样。

**all-to-all 是每张卡向每张卡各发一份不同的数据。**

打个比方，四张卡各持 8 个 token：

```text
发之前：GPU0 有 token 0-7，GPU1 有 token 8-15，GPU2 有 16-23，GPU3 有 24-31
发之后：GPU0 有去专家1/2/3的，GPU1 有去专家0/2/3的……
```

每个 GPU 都把一部分 token 送出去，同时收进一部分。**所有卡的 token 总数不变，但归属全变了。**

这就是为什么它叫 all-to-all：不是「一传多」也不是「多传一」，而是「每张卡都向每张卡发」。

### Dispatch 和 Combine，两次

MoE 一层要走两遍 all-to-all：

|  | 方向 | 传什么 | 量 |
| --- | --- | --- | --- |
| Dispatch | token → 专家所在卡 | 被选中的 token 的 hidden state | token 数 × 被选专家数 |
| Combine | 专家所在卡 → token 原卡 | 专家算完的输出 | 同上 |

Dispatch 之前还要做一次**重排**：把同一目标专家的 token 打包在一起，否则 NIC 会发一堆小包，带宽利用率极低。这个重排叫 permutation，也是要花时间的。

所以一层 MoE 的真实开销是：**permutation + dispatch(all-to-all) + 专家计算 + combine(all-to-all) + 反重排**。

### 为什么 decode 特别痛

![](https://pic4.zhimg.com/v2-3951dd26298a6dd391d04efe1e950f9d_r.jpg)
*为什么 decode 特别痛。*

Prefill 时一次要处理几十万 token，一次 all-to-all 摊到每个 token 上很便宜。

decode 时每步只处理 batch 里的那些 token（比如 60 个序列各 1 个），但**这一步的 all-to-all 一次都不能少**。通信量小，但延迟固定。

这就是为什么 decode 的延迟里，all-to-all 占比很高。也是为什么第十一篇里，decode 要用 Wide-EP：EP 越大，专家分得越散，每个专家上的 token 越少，MoE 的访存压力越小——但代价是 **all-to-all 的跨卡范围更大**。

这是一个明确的取舍：**EP 加大，访存压力下降，通信范围上升。** 找平衡点是推理系统的核心工作之一。

### V4.1 怎么压这笔成本

![](https://pic2.zhimg.com/v2-122333b650d3b6eccd86ee496529e407_r.jpg)
*EP 加大，两头反向。*

论文没展开细节，但从部署文档和 kernel 名字能看出方向：

- **Mega-MoE 融合 kernel**：把 Gate、permutation、dispatch、专家计算、combine 尽量融进少数几个 kernel，减少 kernel launch 和中间结果的显存往返
- **DeepEP**：专门为 MoE 写的通信库
- **分层通信**：机内走 NVLink，机间走 RDMA，按拓扑选路由

物理成本消不掉。光速和带宽摆在那里。能做的只是**让数据少搬一次、让搬的时候别等**。

### 一个容易忽略的点

all-to-all 的通信量不取决于专家总数，取决于**每个 token 被选中的专家数**（V4.1 是 6）。

384 个专家不会让通信量变成 384 倍。但反过来，如果把 top-k 从 6 提到 8，通信量直接涨 1/3。

**这就是为什么 MoE 论文里 top-k 通常很小。** 它同时控制算力和通信。

### 3.2 显存必须够大

552B 参数按 FP8 存要 552 GB。一张 H800 是 80 GB，这意味着至少要 8 张卡才能装下权重，实际部署要考虑冗余和 KV cache，卡数更多。

这就是为什么 MoE 的胜利本质上是「用显存和通信换算力」的交易。过去几年 HBM 容量和互联带宽的增长，刚好让这笔交易划算。

### 4. 为什么它成了默认选项

2023 年的 Mixtral 8x7B 让开源社区第一次大规模用上 MoE。2024 年 DeepSeek-V2 用 236B 总参数、21B 激活，把成本差摆到台面上。之后 V3、Qwen3、Kimi K2、GLM-4.5/5、MiniMax 基本都走这条路。到了 2026 年，不开 MoE 的前沿模型已经很少。

原因不复杂。固定算力预算下，MoE 能买到更多参数；固定显存预算下，MoE 能买到更多知识。推理时每个 token 只过少数专家，延迟接近同激活量的 dense 模型。

但有个前提：**负载要够大**。如果每天只有几百个请求，多卡 MoE 的固定成本摊不平；只有服务规模足够大，稀疏激活的算力节省才能盖过多卡部署的开销。这也是为什么 MoE 最先在云厂商和头部模型公司普及。

### 5. MoE 买到了什么，没买到什么

![](https://picx.zhimg.com/v2-62c6fd770ec270228cb86715a3d1d8a9_r.jpg)
*MoE 买到了什么，代价是什么。*

买到了两件事：参数容量，和每 token 的激活算力。

没买到的是：KV cache 的压缩、attention 计算的减少，以及知识存放方式的改变。

最后一点值得强调，因为下一篇要讲 Engram。MoE 让参数变多、激活变少，但知识仍然存在**矩阵里**——只是分了 384 个房间，token 按需进几间。它没有改变「知识要靠矩阵乘取出来」这件事。

Engram 走的是另一条路：把知识存进**表里**，用哈希地址直接查，不经过矩阵乘。这是两个不同的方向，下一篇展开。

### 6. 小结

MoE 用 384 个小专家加 1 个共享专家，让 552B 的总容量只激活 16B。

它的两个关键设计是「专家小而多」和「共享专家常在线」，两个关键工程是 aux-loss-free 的负载均衡和跨卡通信优化。

代价是 all-to-all 通信和庞大的显存占用，所以它的经济性依赖服务规模。

它解决了参数账，但没解决上下文账和深度账，也没改变知识的存放方式。
