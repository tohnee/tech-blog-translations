sglang 的 cache 部分主要分为两部分——容量（kv cache）与复用（radix cache）。

## 容量管理

我们先从容量开始讲起。传统的 attention 计算通过存下之前计算的 kv 用空间换时间，省去了重算的过程。在每一层 decode 都需要维护一个 **kv cache pool**。这个 cache pool 的存在形式如下：

```text
k_buffer[num_slots, k_head, k_dim]
v_buffer[num_slots, v_head, v_dim]
```

把后两个维度展平，就得到直观的理解：<u>buffer = 槽位数量 × 一个 token 在该层的数据维度。</u>

物理池就是这样一个简单的构造，上次的逻辑部分的数据结构是 **ReqToTokenPool**：

```text
ReqToTokenPool[max_reqs][max_tokens] = slot_id
```

这是一个二维表，我们通过 req_id、token_id 可以得到一个 slot_id，通过这个 slot_id 就可以在 buffer 里找到这个 token 对应的 cache（buffer[slot_id]）。

对 buffer 的申请和释放都由 **Allocator**负责，Allocator 维护了一个 free_slots 的列表：

```text
free_slots = [0,1,2, ..., slot_num - 1]
```

有人申请的时候就把里面的值扣出去，有人释放了就加回来。

整个的容量管理部分主要就由这三部分构成：**物理槽位（buffer）**、**分配器（Allocator）**、**申请记录（ReqToTokenPool）**。它之间通过 slot_id 联系在一起。

## 复用管理

复用管理由 radix cache 负责，radix cache 记录了 tokens -> slots 的映射。它是一个前缀树的结构，一个请求从前缀树往后走，能够每个 token 都一致就是 prefix 命中。命中的 token 就不用计算了，直接拿着它的 slots 存到 ReqToTokenPool 就行了。

若未命中，则在未命中出分出一条新的枝，记录自己的路径。

当我们开启了 radix cache 之后，回收 slots 的判断都由 radix 负责。具体来说每当一个请求沿着一条枝干匹配过的时候就给这个枝干的计数器 +1；请求结束则他走过的枝干计数器 -1；计数为 0 的枝干就是可回收的枝干，当 cache 空间不够时就可以回收它们。当然，觉得谁可以释放的是 radix cache，真正动手的还是 allocator。

当把能够回收的 cache 都回收了，allocator 里面也没有剩余空间，就会 retract 某个请求，把这个请求过去做的计算作废，等有空间了再重新算。当然也不见得一定要扔掉这个 cache，存到主机内存之后再读也是一种方法。

顺带说一下，radix cache 的写入时机有三类：chunked prefill 的每个 chunk、prefill 结束后写入、一个 request 结束后把 decode 产生的 cache 写入。

## slots -> pages

刚刚我们讲的管理维度是 slot，但是现实场景中经常使用的是 page 进行管理。一个 page 里面有若干 slot，这里我们就假设是 64 好了。真正因此改变的是 allocator 部分，他里面维护的空间表从 free_slots 变成了 free_pages。

```text
free_pages = [1, 2, 3, ...]  # 页 0 留作 padding
slot_id = page_id * page_size + offset
```

普通逐 token decode 时，上层先从请求映射取出 `last_loc`，再把它和序列长度交给分页 Allocator。尾页未满，就返回 `last_loc+1`；跨过页边界，才从空闲列表取新页。

引入 page 后，radix cache 仍然记录 token 序列及其对应的 slot，但插入和前缀匹配都按完整 page 对齐，能够复用的前缀长度必须是 page_size 的整数倍。

例如 page_size = 64，一个新的请求包含 127 个 token，且树中已经缓存了与它相同的前缀，那么最多可以复用前 64 个 token 的 KV；剩余 63 个 token 不构成完整 page，需要在本次 prefill 中重新计算。即使已有缓存与这 127 个 token 全部一致，也不能通过普通 radix 前缀匹配复用后面这 63 个 token。

再提醒一下，我们现在的 FlashAttention 在计算的时候会用到一个叫做 page table 的数据结构，这个 page table 不是 sglang cache 管理机制的一部分，它只是缓存的一个视图，在每次 step 的时候更新。
