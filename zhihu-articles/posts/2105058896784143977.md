> **导读**：当前大模型在众多任务的处理中都可以表现的比较专业全面，但是被问到关于私有或专有数据源的信息，大模型可能会一本正经的胡说八道，也就是大模型出现了幻觉。所以大模型在处理某些特定任务时可能还需要进行更多的定制化工作。不同的任务具有不同的数据特点和需求，大模型往往需要进行针对性的调整和优化才能取得最佳性能。然而，这种定制化工作通常需要大量的时间和资源投入，增加了模型应用的难度和成本。因此RAG检索生成增强就应运而生了。

## 1、基本概念

**检索增强生成（Retrieval-Augmented Generation, RAG）** 是将大语言模型（LLM）与外部知识库结合的技术框架。其核心流程分为三步：

- **检索（Retrieval）：根据用户问题从知识库中查找相关文档片段。**
- **增强（Augmentation）：将检索结果拼接到用户问题中，形成增强提示词。**
- **生成（Generation）：LLM 基于增强后的提示生成最终回复。**

**RAG 的核心思想：在生成回答之前，先从外部知识源检索与问题相关的内容，把它注入大模型的上下文，让模型基于检索到的证据作答，而不是只凭训练时“记住”的参数知识。**

**RAG 把“记住知识”和“组织语言”这两件事解耦：知识放在外部，模型只负责在给定证据的条件下生成回答。更新知识只需要更新文档库，不需要动模型。**<br>

**检索质量决定了生成质量的上限。**

## 2、实现步骤

把上面的原理落地，一个最小可用的 RAG 系统可以概括为五步。

**第一步：加载与解析文档。** 把 PDF、文本文件或网页转成可处理的文本。如果是扫描件，先做 OCR。

**第二步：文本分块。** 使用递归分块器按段落、句子边界切分，设置合理的 `chunk_size` 和 `chunk_overlap`。`chunk_overlap` 过低会导致跨块语义被切断，过高则会引入大量重复内容。

**第三步：嵌入并写入向量库。** 用嵌入模型把每个块变成向量，连同原文和元数据存入向量数据库。开发和演示阶段常用 Chroma 这类轻量库，生产环境可以考虑 Milvus 等方案。

**第四步：检索与重排序。** 用户问题经同一嵌入模型向量化后，从向量库召回 Top-K 候选。条件允许时，加一层 Cross-Encoder Rerank 对候选重新打分排序。

**第五步：拼装 Prompt 并生成。** 把精排后的片段作为上下文放入提示词，要求模型“只依据以下资料回答；资料不足时明确说明”。最后返回答案，并附上引用来源，方便溯源。

## 3、python实现

下面用 LangChain 搭建一个最小可运行的文档问答系统。它覆盖了加载、分块、嵌入、向量库存储和检索问答的完整链路。

```python3
# pip install langchain langchain-openai langchain-community langchain-chroma

from langchain_community.document_loaders import TextLoader
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_openai import OpenAIEmbeddings, ChatOpenAI
from langchain_chroma import Chroma
from langchain.chains import RetrievalQA

# ========== 1. 加载本地文档 ==========
loader = TextLoader("./business.txt", encoding="utf-8")
docs = loader.load()

# ========== 2. 文本分块 ==========
text_splitter = RecursiveCharacterTextSplitter(
    chunk_size=800,
    chunk_overlap=150,
)
splits = text_splitter.split_documents(docs)

print(f"原始文档数：{len(docs)}")
print(f"分块后片段数：{len(splits)}")

# ========== 3. 嵌入 + 写入向量库 ==========
embedding = OpenAIEmbeddings(api_key="your-api-key")
vectordb = Chroma.from_documents(
    documents=splits,
    embedding=embedding,
    persist_directory="./chroma_db",
)

# ========== 4. 构建检索问答链 ==========
llm = ChatOpenAI(
    model="gpt-4o-mini",
    api_key="your-api-key",
    temperature=0,
)

qa_chain = RetrievalQA.from_chain_type(
    llm=llm,
    retriever=vectordb.as_retriever(search_kwargs={"k": 4}),
    return_source_documents=True,
)

# ========== 5. 执行问答 ==========
result = qa_chain.invoke({"query": "本产品售后保修周期是多久？"})

print("答案：", result["result"])
print("\n参考来源：")
for doc in result["source_documents"]:
    print("-", doc.metadata.get("source", "unknown"))
```

chunk_size=800、`chunk_overlap=150` 控制分块粒度和边界重叠；`k=4` 是 Top-K 召回的数量；`return_source_documents=True` 让系统在返回答案的同时给出参考片段，方便验证答案是否“有据可依”。

运行后你可能遇到几个典型问题，它们恰好对应 RAG 工程中的常见坑：

- **答案混入无关信息**：`chunk_size` 可能过大，单块包含了多个主题，导致检索召回了语义相关但实际不回答问题的片段。适当降低 `chunk_size` 重新入库往往能改善。
- **关键信息回答不出**：`chunk_overlap` 可能过低，跨块的语义被切断，答案恰好落在边界上没有被任何一块完整包含。调大 overlap 可以缓解。
- **PDF 扫描件问答全部乱码**：文件本身是图片 PDF，没有可提取的文本层，必须先做 OCR 再把文本送入分块流程。

如果要加上 Rerank，可以在检索和生成之间插入一个 Cross-Encoder 重排序步骤，把召回数量放大到 20—50，再用重排模型选出最相关的几条送入上下文。这也是从“最小 Demo”走向“生产可用”时最常见的改造之一。

## 4、优缺点

**优点**

RAG 最直接的价值是**知识更新成本低**。改文档当天生效，不需要重新训练模型，相比微调在知识频繁变化的场景中灵活得多。其次，RAG 让答案**可溯源**：每条回答可以挂出检索到的原文片段和来源位置，这在客服、法务、企业内部问答等场景中非常关键。第三，RAG 在开放域问答等任务中可以**显著降低幻觉**，公开研究显示的抑制幅度大约在 30%—50%，因为模型被约束在检索到的证据上生成，而不是自由发挥。

**不足**

RAG 不是“接上向量库就完事”。检索本身就可能失败：用户表述和文档表述之间存在语义鸿沟，嵌入模型与领域不匹配、分块方式不合适，都会导致召回不到或排错序；即使召回到正确片段，如果它没有进入上下文，或者被无关内容稀释，生成质量依然会下降。
