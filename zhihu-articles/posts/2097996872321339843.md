## 一、大模型为什么会"幻觉"？

大模型有一个天生的毛病—— **幻觉（Hallucination）** ：它会非常自信地说出错误的答案。

为什么？

因为大模型的本质是"根据上文预测下一个最可能出现的词"。它脑子里的知识是训练时记住的，有两个先天缺陷：

1. **知识有截止日期** ：训练数据停在某个时间点，之后的事它不知道
2. **知识不精确** ：它记住的是"大概怎么说"，不是"准确数字是多少"

比如你问它"我们公司的报销流程是什么"，它根本不知道你公司是什么，但它会根据"报销流程一般有哪些步骤"编一个看起来很像的答案。

**怎么解决？**

- **思路一：微调模型** → 把你的资料灌进去，让模型记住（成本高、更新慢）
- **思路二：外挂知识库** → 回答前先去查资料，再根据资料回答（就是RAG）

## 二、RAG是什么？

RAG的全称是 **Retrieval-Augmented Generation** （检索增强生成）。

**先检索，再生成。**

```text
没有RAG：
用户提问 → 大模型凭记忆瞎编

有RAG：
用户提问 → 先从知识库找到相关资料 → 把资料+问题一起给大模型 → 大模型根据资料回答
```

就像开卷考试——你不用把所有书都背下来，考试的时候翻书找答案就行。

## 三、RAG完整流程拆解

一个生产级的RAG系统，完整流程是这样的：

```text
【离线阶段：建知识库】
原始文档 → 文档解析 → 切分Chunk → Embedding向量化 → 存入向量数据库

【在线阶段：回答问题】
用户提问 → 问题向量化 → 从向量库检索相关文档 → 重排序 → 组装Prompt → 大模型生成答案
```

下面逐环节讲。

### 3.1 第一步：文档解析

把各种格式的文档（PDF、Word、网页、Excel）变成纯文本。

**坑点：**

- 扫描版PDF是图片，需要OCR才能提取文字
- 表格如果解析不好，后面检索全错
- 复杂排版的文档（多栏、图文混排）解析容易乱

**常用工具：**

- 简单PDF：pdfplumber、PyPDF2
- 复杂排版：MinerU、Marker
- OCR：PaddleOCR

### 3.2 第二步：切分Chunk

长文档不可能整篇塞给大模型——上下文窗口有限，而且太长了模型抓不住重点。

所以要把文档切成一段一段的，就是Chunk。

**切分策略：**

| 策略 | 怎么做 | 适合 |
| --- | --- | --- |
| 固定长度切分 | 每500字切一段 | 简单文本，快速原型 |
| 递归切分 | 先按段落切，太长再按句子切 | 通用场景，推荐 |
| 按结构切分 | 按标题、章节切 | 文档类、合同类 |

**关键参数：**

- chunk_size：每段多大（一般300-800字）
- overlap：相邻段重叠多少字（一般50-100字，防止切断语义）

### 3.3 第三步：Embedding向量化

把文本变成一组数字（向量），计算机才能比较相似度。

```text
"今天天气很好" → [0.12, -0.34, 0.56, ..., 0.78] （768维向量）
```

语义相近的句子，向量距离也近。这样用户问问题的时候，就能找到语义最接近的文档片段。

**常用Embedding模型：**

- 开源首选：BGE-M3（中文效果好）
- 商用API：OpenAI text-embedding-3-small

### 3.4 第四步：存入向量数据库

把所有chunk的向量存起来，方便快速检索。

**常见选择：**

| 数据库 | 适合 |
| --- | --- |
| Chroma | 原型开发，轻量 |
| PGVector | 已有PostgreSQL，运维简单 |
| Milvus | 大规模生产环境 |
| Qdrant | 高性能生产环境 |

### 3.5 第五步：检索

用户提问来了，把问题也变成向量，去向量库里找最相似的Top K个chunk。

**这里有个坑：** 纯向量检索经常漏。为什么？因为用户可能用了很具体的关键词（比如产品型号、专业术语），纯向量匹配不一定能命中。

**解决方案：混合检索**

```text
向量检索（语义相似）+ BM25关键词检索（精确匹配）→ 合并结果
```

### 3.6 第六步：重排序（Reranker）

粗排召回的20条结果里，真正相关的可能只有3-5条。这时候用一个更强大的Cross-Encoder模型做精排，把最相关的排到前面。

```text
召回Top20 → Reranker打分 → 取Top5
```

**效果提升：** 加了Reranker，准确率通常能提升20%-30%。

### 3.7 第七步：生成答案

把用户问题 + 检索到的资料，一起组装成Prompt，发给大模型：

```text
请根据以下参考资料回答用户问题。如果资料中没有相关信息，请说"根据现有资料无法回答"，不要编造。

参考资料：
[检索到的chunk 1]
[检索到的chunk 2]
...

用户问题：[用户的问题]

请给出准确、简洁的回答，并标注信息来源。
```

## 四、RAG效果不好怎么调？

这是最常见的问题。按这个顺序逐层排查：

| 排查顺序 | 问题可能在哪 | 怎么调 |
| --- | --- | --- |
| 1 | 文档解析错了 | 检查提取出来的文本对不对 |
| 2 | Chunk切得不好 | 调chunk_size和overlap |
| 3 | Embedding模型不行 | 换更好的中文Embedding模型 |
| 4 | 召回没召回对 | 加BM25混合检索，调top_k |
| 5 | 召回了但排前面的不对 | 加Reranker |
| 6 | 上下文给了但生成不对 | 优化Prompt，加"只根据资料回答" |

**大部分RAG效果不好的问题，出在检索环节，不是生成环节。**

## 五、RAG vs 微调：怎么选？

很多人纠结什么时候用RAG，什么时候微调。一张表说清楚：

| 对比项 | RAG | 微调 |
| --- | --- | --- |
| 知识更新 | 改文档就行，实时 | 要重新训练，慢 |
| 成本 | 低，API调用费 | 高，训练成本 |
| 可解释性 | 强，能给出处 | 弱，黑盒 |
| 适合 | 知识问答、文档查询 | 风格定制、特定任务 |
| 幻觉控制 | 好，有依据 | 一般 |

大多数企业场景，RAG就够了。微调是当你需要模型学会一种特定风格或能力的时候才用。

## 六、五分钟上手RAG

想自己试试？用LangChain + Chroma，十几行代码就能跑起来：

```python
from langchain.document_loaders import TextLoader
from langchain.text_splitter import RecursiveCharacterTextSplitter
from langchain.embeddings import HuggingFaceBgeEmbeddings
from langchain.vectorstores import Chroma
from langchain.chains import RetrievalQA
from langchain.llms import Tongyi

# 1. 加载文档
loader = TextLoader("company_rules.txt")
documents = loader.load()

# 2. 切分
text_splitter = RecursiveCharacterTextSplitter(chunk_size=500, chunk_overlap=50)
chunks = text_splitter.split_documents(documents)

# 3. 向量化并存入数据库
embeddings = HuggingFaceBgeEmbeddings(model_name="BAAI/bge-small-zh-v1.5")
db = Chroma.from_documents(chunks, embeddings)

# 4. 构建问答链
qa = RetrievalQA.from_chain_type(
    llm=Tongyi(model_name="qwen-plus"),
    chain_type="stuff",
    retriever=db.as_retriever(search_kwargs={"k": 3})
)

# 5. 提问
print(qa.run("报销的流程是什么？"))
```

跑通这个最小demo，你就理解RAG的核心了。

RAG本质上就是"给大模型开卷考试"。它不是什么高深技术，而是一套工程方法——通过外挂知识库，让大模型能基于你的资料准确回答问题。
