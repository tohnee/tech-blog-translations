如果你在 2025 年 3 月打开任何一个技术社区，MCP 这三个字母几乎无处不在。教程、分析、大厂表态，“不追就落后”的紧迫感扑面而来。

但如果你只是听说过 MCP，却一直没搞明白它到底是个什么东西——这篇文章就是写给你的。

我会用最直白的语言，把 MCP 的原理、历史、能干什么全部拆开揉碎。读完之后，你不仅能跟任何人解释清楚 MCP 是什么，还能判断它跟你到底有没有关系。

## 一、MCP 是什么？

先说结论：MCP（Model Context Protocol，模型上下文协议）是一套开放标准，用来让 AI 应用和外部工具、数据源用同一种方式连接起来。

官方给出的类比非常精准：MCP 就是 AI 世界的 USB-C。

![](https://pica.zhimg.com/v2-dc2fc09f9808158ad8b7ae3023f8cf2c_r.jpg)

你想想 USB-C 之前的世界：打印机有打印口，鼠标有鼠标口，显示器有 VGA 口，每个设备都要配一根专用线。USB-C 出现之后，一根线走天下。MCP 做的事一模一样——在它出现之前，你想让 Claude 读本地文件，要写一套代码；想让 ChatGPT 查数据库，要写另一套代码；想让 Cursor 连公司内部 API，还得再写一套。

每个 AI 应用 × 每个数据源 = 一套定制集成代码。这就是 Anthropic 说的 N×M 集成问题。N 个 AI 应用，M 个数据源，如果每对组合都要单独写连接器，这个生态根本没法扩展。

MCP 的解法是：把连接方式标准化。理想情况下，N×M 变成 N+M——AI 应用只需要实现一次客户端能力，数据源只需要实现一次服务端能力，两边通过标准协议对话。

![](https://picx.zhimg.com/v2-f7e293e3414d5a50b675950a53b3f815_r.jpg)

## 1. MCP 的工作原理

**1.1 主机、客户端、服务器**

![](https://pic3.zhimg.com/v2-58c66e27e986ec2a7fda1b6d1aa61502_r.jpg)

MCP 的架构里有三个角色，名字很容易混淆，但用快递来类比就很好理解：

- Host（主机）——整个快递公司的总部。*它是你实际使用的 AI 应用，比如 Claude Desktop、Cursor、VS Code。总部不亲自送快递，但它负责调度、管理所有的快递员，决定哪个快递员去哪个片区。
- Client（客户端）——快递员。*每一个快递员只负责一个片区（一个 Server），它们由总部创建和管理。总部跟一个 Server 建立连接，就会创建（或者说“雇”）一个专属的快递员，这个快递员跟那个 Server 之间保持一对一的专属连接。
- Server（服务器）——片区里的驿站。*它提供具体的能力：读文件、查数据库、调 API、发邮件。驿站不关心是哪个快递员来取件，它只负责把包裹准备好。

![](https://pic4.zhimg.com/v2-b3a90342b7e9373501002c96ecaaf7f1_r.jpg)

所以整体流程是：你在 Host 里问“帮我看看本地项目里那个 config 文件写了什么”，Host 创建/复用一个 Client 去连接文件系统 Server，Client 把 Server 返回的文件内容拿回来，Host 把它交给大模型理解并回答你。

一个 Host 可以同时管理多个 Client，每个 Client 连接不同的 Server。VS Code 同时连接 Sentry Server 和本地文件系统 Server 时，就实例化了两个独立的 Client 对象，各自维护各自的连接。

这里有一个很容易被忽略但非常重要的设计原则：Server 看不到完整的对话历史。每个 Server 只收到自己需要的那部分上下文信息，完整的对话保留在 Host 手里。这就像快递员只知道要送什么包裹，不知道你昨天跟别人聊了什么——安全边界非常清晰。

![](https://pic4.zhimg.com/v2-4cf1c804f30802c95b89483f0dcd5483_r.jpg)

**1.2 案例解析**

![](https://pic3.zhimg.com/v2-cf3976c96d7ae3f3da361581a7de187e_r.jpg)

用一个具体的场景把三个角色串起来。

假设你在用 Claude Desktop 搭建一个“代码审查助手”，它需要做四件事：读取 GitHub 仓库代码、调用大模型审查、把结果写回本地文件、最后发一条 Slack 通知。

在 MCP 的世界里，你需要配置三个 Server：

- GitHub Server：负责从 GitHub API 拉取代码文件
- Filesystem Server：负责在本地目录读写审查结果
- Slack Server：负责向指定频道发送消息

当你说“帮我审查一下 xxx 仓库的 main 分支”，Host（Claude Desktop）会做以下事情：

- 1. 创建（或复用）一个 Client，让它去问 GitHub Server：“把 xxx 仓库 main 分支的文件列表给我”
- 2. 拿到文件内容后，Host 把内容交给大模型分析
- 3. 分析结果出来了，Host 再让 Filesystem Client 把结果写到本地文件
- 4. 最后让 Slack 客户端把总结发到频道里

整个过程中，GitHub Server 不知道大模型是怎么分析的，Slack Server 也不知道代码是从哪来的。每个 Server 只做自己那一件事，Host 负责编排全局。这就是 MCP关注点分离的威力。

## 2. 三个视角解读 MCP 的前世今生

- 同一个 MCP，站在不同的位置看，它的意义完全不同。

![](https://pic2.zhimg.com/v2-3f1aed1d61758f5e61909db6e7a58177_r.jpg)

**2.1 大模型视角：我终于有手了**

![](https://picx.zhimg.com/v2-46cdcf40fefb0cbf18f72d9885c2f05d_r.jpg)

大模型本身的定位是一个“知识渊博的顾问”。它知道很多事，但它没法帮你查数据库、没法帮你发邮件、没法帮你操作服务器。就像一个智商 200 但手被绑住的天才。

在 MCP 之前，大模型调用外部能力的标准方式是 Function Calling。Function Calling 解决的是“模型如何决策调用哪个工具”的问题——模型理解用户意图，判断该用哪个函数，生成调用参数。但 Function Calling 有硬编码的问题，每个 API 都要单独适配，同一个工具在 Claude、GPT、Qwen 上要分别写三套代码。

![](https://pic1.zhimg.com/v2-d95d68edac23001f23b54f43f626dd40_r.jpg)

MCP 解决的是另一个环节的问题：服务器如何发现和执行具体工具的标准。Function Calling 是大模型的“决策层”，MCP 是后端的“执行协议”，两者分属不同链路环节，并非替代关系。

从大模型的视角看，MCP 让它从一个“只会说”的顾问，变成一个有手有脚、能实际干活的 Agent。

**2.2 AI 应用视角：终于不用重复造轮子了**

![](https://pic2.zhimg.com/v2-8d079cd8f4b88b6b4bec6474ddaef779_r.jpg)

如果你是一个 AI 应用的开发者，MCP 出现之前，你可能经历过这样的噩梦：产品要接入 10 个业务系统、20 个接口，意味着你要写 200 个适配函数。更崩溃的是，每次对接一个新的大模型，这 200 个函数可能还要重写一遍。

MCP 把这个问题彻底翻转了。一个 MCP Server 写好之后，任何支持 MCP 的 AI 应用都能直接使用，无需二次开发。就像你开发了一个 USB-C 接口的鼠标，不管是 Mac、Windows 还是 Linux，插上就能用。

根据阿里云百炼平台的数据，MCP 可以将工具对接耗时从数天缩短至 5-10 分钟。

**2.3 技术设计视角：站在 LSP 的肩膀上**

MCP 的设计灵感来自 LSP（Language Server Protocol）。

![](https://pic2.zhimg.com/v2-b2f45c5dbd6e0474e46eda90ec48de35_r.jpg)

LSP 做的事情是让 VS Code 能和任何编程语言“对话”——不管你是 Python、Go 还是 Rust，只要你的语言服务实现了 LSP 协议，编辑器就能为你提供自动补全、跳转定义、错误诊断等功能。LSP 出现之前，每支持一种新语言，编辑器开发者都要写一套定制集成。

MCP 的设计者 David Soria Parra 和 Justin Spahr-Summers 就是从 LSP 得到了灵感：LSP 让编辑器与语言服务解耦，MCP 就让 AI 应用与工具/数据源解耦。核心思路完全一样——定义一个标准协议，让生态中的每个参与者只需要实现一次。

不过 MCP 比 LSP 走得更远。LSP 主要是反应式的（响应用户在编辑器里的操作），而 MCP 设计用于支持**自主的 AI 工作流——Agent 可以自己决定什么时候调用什么工具，不需要每一步都等人来触发。

在协议设计上，MCP 做了两个层面的清晰划分：

数据层：定义了基于 JSON-RPC 的通信语义，包括工具调用、资源读取、提示模板等核心能力。

传输层：定义了消息如何送达，本地进程用 STDIO，远程通信用 Streamable HTTP这种分层设计的好处是：上层逻辑不关心底层怎么传，换一种传输方式不用改协议语义。

![](https://pic3.zhimg.com/v2-0363b4888e6c2632959e75360fad3f40_r.jpg)

## 3. 为什么是历史选择了 MCP？

**3.1 MCP 的诞生**

![](https://pic4.zhimg.com/v2-a2e5449141c3c3f4fa674ce9e82743e5_r.jpg)

2024 年 11 月，Anthropic 开源了 MCP 协议，同时发布了 Claude Desktop 对 MCP 的支持。第一版协议定义了四个核心能力：Resources（让 AI 读取文件、数据库等数据）、Prompts（预定义的提示模板）、Tools（AI 可执行的函数）、Sampling（服务器发起的 LLM 调用）。

MCP 的诞生精准击中了当时 AI 应用开发最大的痛点：开发者不得不重复造轮子。每个 AI 应用都要自己搞一套插件系统，互相不兼容。Cursor 有 Cursor 的，Claude 有 Claude 的，OpenAI 有 OpenAI 的。你想让 AI 读一份 PDF，得另外写接口。

Anthropic 选择开源 MCP 而不是闭门造车，这一步棋非常关键。如果 MCP 是一个私有协议，它可能永远不会走出 Claude 的生态。但开源让它具备了成为行业标准的可能性。

**3.2 热度破圈**

MCP 真正破圈是在 2025 年春天。

2025 年 3 月，OpenAI 宣布支持 MCP。紧接着 4 月 Google 跟进，Microsoft 在 Win11 里做了原生集成。阿里云百炼、腾讯云、百度、高德，全部在推自己的 MCP 服务。

数据层面更能说明问题。根据 Anthropic 在 2025 年 12 月公布的数据：活跃的公共 MCP 服务器超过 10000 个，SDK 每月下载量超过 9700 万次，ChatGPT、Cursor、Gemini、Microsoft Copilot 和 VS Code 全部在一级客户端支持名单上。

2025 年 12 月，Anthropic 将 MCP 捐赠给 Linux 基金会下的 Agentic AI Foundation，与 Block、OpenAI 共同发起，Google、Microsoft、AWS、Cloudflare 等公司支持。这一步的意义在于“治理中立化”——降低了“绑定一家模型厂”的顾虑，让其他厂商更放心地投入。

到了 2026 年，MCP 的月度 SDK 下载量突破了 4 亿，Claude 应用商店里的 MCP 服务器超过 950 个。

当然，热度破圈也意味着争议。有开发者指出 MCP 在某些场景下引入的复杂度远大于它解决的问题，也有基准测试显示 MCP 的任务完成率不如 CLI 方案。这些质疑是真实的，但对新手来说，理解一个协议的价值，先看它解决了什么问题，再看它的局限性，比一上来就陷入争论要重要得多。

## 4. MCP：这东西能干什么？

![](https://pic4.zhimg.com/v2-853a663b183ef2e62ced1d09e45f479d_r.jpg)

**4.1 私有 Agent 场景的最佳拍档**

企业落地 AI Agent 最大的矛盾是什么？**数据不能出域，工具链却极其复杂**。

你可以把企业内部的 CRM 系统、运维脚本、本地文件系统全部封装成标准的 MCP Server，Agent 作为 Client 即插即用。不需要让数据流到外部，所有调用都发生在企业内网。

对于金融、医疗这类对数据隐私极度敏感的行业，MCP 提供了一种“内部 AI 能力标准化”的思路：推理层用云端大模型，执行层在本地容器或虚拟机中运行，通过 MCP 协议受控通信。既能用大模型的智能，又能保证数据不出域。

**4.2 个人 AI 助手搭建的最优选择**

如果你想搭一个自己的 AI 助手——能读你的本地文件、帮你管理日程、自动整理邮件、甚至帮你写周报——MCP 是目前门槛最低的方案。

你不需要写复杂的集成代码，只需要在配置文件里声明你要用哪些 MCP Server，剩下的交给 Host 去编排。就像搭乐高一样，选好积木块，拼起来就行。

**4.3 第三方“能力”有了新的变现方式**

MCP 催生了一个新的市场：MCP Server marketplace。

开发者可以把自己写的 MCP Server 发布到市场上，以免费或付费的方式提供给其他人使用。已经有平台支持在 5 分钟内把任意 API 转化为付费的 MCP 服务，调用次数直接计费。

这个模式的想象空间很大：你写了一个特别好用的“邮件智能分类”MCP Server，所有支持 MCP 的 AI 应用都能调用它，每次调用你都能获得收入。你不需要自己做一个 AI 产品，只需要做好一个能力模块。

4.4 让开发者创建 Agent 像搭积木一样简单

这是 MCP 对开发者最直接的价值。

以前做一个 Agent，你需要考虑：怎么对接大模型、怎么管理工具调用、怎么处理错误、怎么做鉴权。现在 MCP 把这些标准化了，开发者只需要关注业务逻辑本身。

想做一个“代码审查 Agent”？配置 GitHub Server + Filesystem Server + Slack Server，写主流程逻辑就行了。想做一个“客服 Agent”？配置 CRM Server + 知识库 Server + 工单 Server。每个 Server 都是一个独立的“积木块”，按需组合，随时替换。

## 5. 总结

回到最开始的问题：MCP 到底是什么？

它是一个协议，但更是一个生态的起点。

从技术上说，MCP 用 Host-Client-Server 的三层架构，把 AI 应用与外部工具的连接方式标准化了。Function Calling 解决了“模型怎么选工具”的问题，MCP 解决了“工具怎么被执行和被管理”的问题。

从历史上说，MCP 诞生于 AI 应用开发最混乱的时期——每个厂商都在搞自己的插件系统，开发者被迫重复造轮子。Anthropic 选择开源，加上后续的生态建设和治理中立化，让 MCP 从 Claude 的私有协议变成了行业标准。

从应用上说，MCP 让私有 Agent 部署变得安全可控，让个人 AI 助手搭建变得简单，让第三方能力有了新的变现路径，让开发者创建 Agent 像搭积木一样灵活。

当然，MCP 不是银弹。它有它的局限性和争议，后续章节我们会深入讨论。但如果你现在才开始了解 MCP，恭喜你——你赶上了 AI 应用开发范式转移的最佳时机。
