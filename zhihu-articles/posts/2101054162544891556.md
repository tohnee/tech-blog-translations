假设你在做一个客服助手，用户问：“帮我查一下订单 A20261103001 到哪了。”

这事靠模型自己猜肯定不行，得去订单系统里查。最直接的做法，是写一个查订单的方法，把方法说明和参数告诉模型，再由应用接住模型的工具调用请求，执行查询，把结果交回去。

一个助手、两三个工具，这么做没什么问题。可后来运营助手也要查订单，售后助手也要查订单，另一个团队还想用 Python 再做一套。查询逻辑明明已经有了，工具注册、参数转换、调用适配却又写了一遍。

麻烦往往不在工具能不能用，而在于：换个应用，为什么还得重新接？

MCP 想解决的就是这类重复劳动。它把工具实现和智能体应用分开，再约定好一套共同的通信规则，让不同应用能用相同的方式发现和调用这些工具。

这里先分清一件事：Function Call 并不要求你把工具硬编码在应用里，MCP 也不是来替代它的。Function Call 主要解决模型怎么表达“我要调用哪个工具、参数是什么”；MCP 则负责应用怎么连接外部能力、拿到工具说明，以及把调用发过去。两者可以配合使用。

下面就沿着一次查订单的过程，看看这套机制到底怎么运转。

### 一、为什么 MCP 要做成协议，而不是又一个框架？

假如订单团队给你一个 Java SDK，你的 Java 应用接起来很方便。但换成 Python 应用呢？总不能让所有团队为了查订单，都先换一遍技术栈。

当然，可以再提供 Python SDK，也可以把能力包装成普通 HTTP 接口。可接下来还有别的问题：工具清单去哪里拿？参数怎么描述？调用失败怎么返回？工具新增以后，客户端怎么知道？

这些约定如果每个团队都设计一套，接入方还是得逐个适配。

所以 MCP 没有要求大家使用同一个开发框架，而是规定：不管你用什么语言实现，双方都按照同一套规则交换消息。

这和浏览器访问网站有点像。浏览器不需要知道网站后端用了 Java、Go 还是 Python，只要双方遵守 HTTP 等约定，就能通信。

**MCP 本身是协议，SDK 和框架只是帮你实现协议的工具。**

它不只约定“怎么调用一个函数”，还包括连接初始化、能力协商、工具发现、资源读取、提示词获取等交互。对工具复用来说，关键是把这些原本各写各的接入规则统一起来。

### 二、工具是怎么从智能体里拆出来的？

MCP 把应用、连接组件和能力提供方分成了三个角色。

| 角色 | 可以怎么理解 | 主要负责什么 |
| --- | --- | --- |
| MCP Host | 用户正在使用的 AI 应用，比如客服助手、桌面助手或 IDE 插件 | 管理模型、对话上下文、权限，以及各个 Client |
| MCP Client | Host 里负责 MCP 通信的组件 | 连接某个 Server，协商能力，收发请求和通知 |
| MCP Server | 提供外部能力的程序或服务 | 暴露工具、资源和提示词，并处理对应请求 |

把它们的关系写成文字，就是下面这样：

```text
MCP Host：客服助手
├── MCP Client 1 ←→ MCP Server 1：订单查询服务
├── MCP Client 2 ←→ MCP Server 2：文件访问服务
└── MCP Client 3 ←→ MCP Server 3：数据库服务
```

一个 Host 可以管理多个 Client，每个 Client 分别维护与一个 Server 的连接。这里的“一对一”说的是 Client 与 Server 的连接关系，不是说一个 Server 只能服务一个应用。远程 Server 可以同时接待多个客户端。

拿查订单来说，订单团队把查询能力放在 MCP Server 里。客服助手只需要连接这个 Server，不必把查询实现搬进自己的工程。以后售后助手也要用，就再按 MCP 的规则接入。

Server 既可以是本机启动的一个进程，也可以是部署在远端的服务。“拆出去”说的是职责和接口解耦，不是非得另外买台机器。

这样一来，Host 关心的是“这个工具能干什么、怎么调用”，Server 关心的是“怎么把订单查出来”。至于 Server 内部查数据库还是调业务 API，Host 不需要跟着改。

### 三、只拆开还不够，双方得有共同的规矩

如果每个 Server 都有自己的消息格式，工具虽然拆出去了，接入成本却没降多少。

MCP 因此把通信约定分成了两层：

| 层次 | 解决的问题 | 主要内容 |
| --- | --- | --- |
| 数据层 | 发什么消息，消息是什么意思 | 基于 JSON-RPC 2.0 的请求、响应和通知，以及初始化、能力协商、工具等交互规则 |
| 传输层 | 消息从哪里走，怎么送到对方手里 | 本地进程的标准输入输出，或基于 HTTP 的通信方式 |

比如“调用查订单工具”这件事，不管走本地管道还是网络，消息里的方法名、工具名、参数结构都有统一约定。换的是传输方式，不是重新设计一套工具调用协议。

先看消息本身。

### 四、JSON-RPC：把调用写成双方都认识的 JSON

RPC 是 Remote Procedure Call，也就是远程过程调用。名字听起来有点绕，意思并不复杂：应用发出一个调用请求，由另一个程序执行，再把结果返回来。

JSON-RPC 则规定了这类请求、响应该怎么用 JSON 表达。MCP 使用的是 JSON-RPC 2.0。

比如，客户端要查订单，可以发送：

```json
{
  "jsonrpc": "2.0",
  "id": 3,
  "method": "tools/call",
  "params": {
    "name": "get_order_status",
    "arguments": {
      "order_id": "A20261103001"
    }
  }
}
```

这几个字段各管一件事：

- `jsonrpc`：声明消息遵循 JSON-RPC 2.0。
- `id`：这次请求的编号，收到响应时靠它对上号。
- `method`：要执行的协议方法，这里是 MCP 定义的 `tools/call`。
- `params.name`：具体要调用哪个工具，这里是 `get_order_status`。
- `params.arguments`：交给工具的业务参数。

注意，`tools/call` 和 `get_order_status` 不是一回事。前者是大家共用的协议方法，后者才是订单服务提供的工具名。

执行成功后，服务端返回：

```json
{
  "jsonrpc": "2.0",
  "id": 3,
  "result": {
    "content": [
      {
        "type": "text",
        "text": "订单 A20261103001 已发货，正在配送中，预计明天送达。"
      }
    ],
    "isError": false
  }
}
```

响应里的 `id` 和请求一致，实际结果放在 `result` 中。这里返回的是文本，MCP 的工具结果也可以包含其他受支持的内容类型。

如果客户端调用了服务端不支持的协议方法，可能收到这样的错误响应：

```json
{
  "jsonrpc": "2.0",
  "id": 4,
  "error": {
    "code": -32601,
    "message": "Method not found"
  }
}
```

`-32601` 表示协议方法不存在，别把它和“订单不存在”混为一谈。JSON-RPC 响应中，`result` 和 `error` 也不会同时出现。

还有一种情况：协议方法没问题，工具也找到了，但执行时订单系统超时了。这类工具执行错误通常通过工具结果表达：

```json
{
  "jsonrpc": "2.0",
  "id": 5,
  "result": {
    "content": [
      {
        "type": "text",
        "text": "订单系统暂时无法响应，请稍后重试。"
      }
    ],
    "isError": true
  }
}
```

也就是说，“这条协议请求处理不了”和“工具执行失败了”是两层不同的问题，客户端得分开处理。

除了请求和响应，还有**通知**。通知只有方法和必要参数，没有 `id`，接收方也不发送对应的 JSON-RPC 响应。后面会用它来表示“初始化完成”和“工具列表变了”。

顺便说一句，JSON-RPC 规定了消息格式，并不意味着 MCP 没有状态。初始化时谈好的协议版本、可用能力，以及某些传输方式下的会话信息，都需要双方管理。不能因为每条消息是独立的 JSON，就把整个 MCP 连接理解成完全无状态。

### 五、一次工具调用，实际要经过哪些步骤？

上面先看了调用消息的样子。但客户端刚连上 Server 时，还不知道对方支持什么，不能一上来就假定查订单工具一定存在。

正常流程是：先初始化，再发现工具，最后按需调用。

下面的示例使用 `2025-06-18` 协议版本来说明流程，它不是要求所有实现都固定使用这个版本。实际连接时，要以双方协商支持的版本为准。

### 1. 初始化：先确认双方能不能聊

客户端先发出 `initialize` 请求，告诉服务端自己支持的协议版本、能力和实现信息：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "initialize",
  "params": {
    "protocolVersion": "2025-06-18",
    "capabilities": {},
    "clientInfo": {
      "name": "customer-service-assistant",
      "version": "1.0.0"
    }
  }
}
```

这里的 `capabilities` 留空，表示示例客户端没有声明额外的可选能力，并不是随便填一个占位值。

服务端回应自己支持的版本和能力：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "protocolVersion": "2025-06-18",
    "capabilities": {
      "tools": {
        "listChanged": true
      }
    },
    "serverInfo": {
      "name": "order-service",
      "version": "1.0.0"
    }
  }
}
```

这份回应的意思是：“我支持这个协议版本，提供工具能力，而且工具列表变化时可以发通知。”

如果服务端返回的版本不在客户端支持范围内，就不该硬着头皮继续调用，而应断开连接或调整实现。

确认没问题后，客户端还要补一条通知：

```json
{
  "jsonrpc": "2.0",
  "method": "notifications/initialized"
}
```

到这里，初始化才算走完，可以开始正常的业务交互。

**初始化是确认协议和能力，不是获取工具清单。** “支持工具能力”和“具体有哪几个工具”是两件事，后者要接着问。

### 2. 发现工具：拿到工具的使用说明

客户端用 `tools/list` 获取工具列表：

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/list",
  "params": {}
}
```

服务端返回：

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "tools": [
      {
        "name": "get_order_status",
        "description": "根据订单号查询订单状态、配送进度和预计送达时间。",
        "inputSchema": {
          "type": "object",
          "properties": {
            "order_id": {
              "type": "string",
              "description": "要查询的订单号"
            }
          },
          "required": ["order_id"],
          "additionalProperties": false
        }
      }
    ]
  }
}
```

这就是工具的“说明书”：名字是什么、能做什么、需要哪些参数。`inputSchema` 用 JSON Schema 描述参数结构，客户端和模型都不必阅读工具源码。

工具列表也可能分页返回。如果结果中有 `nextCursor`，客户端需要带上游标继续请求，不能把第一页当成全部工具。

MCP Server 能提供的内容不只有工具，常见的三类能力是：

| 能力 | 主要用途 | 放到客服场景里 |
| --- | --- | --- |
| Tools，工具 | 执行操作或查询 | 根据订单号查配送进度 |
| Resources，资源 | 提供可读取的上下文数据 | 读取售后政策、产品手册 |
| Prompts，提示词 | 提供可复用的提示词模板 | 获取一套投诉处理的对话模板 |

Server 可以按需提供其中一类或多类，不必每种都实现。资源和提示词也有各自的协议方法，并不是都塞进 `tools/list` 里。

### 3. 调用工具：模型提出请求，应用负责执行

拿到工具说明后，Host 可以把相关说明交给模型。用户询问订单进度时，模型根据问题和工具描述，提出调用 `get_order_status`，并给出订单号。

接下来才由 Host 做权限检查、必要的用户确认，再通过 MCP Client 发送前面看到的 `tools/call` 请求。

Server 收到请求后，找到工具、校验参数、执行查询，然后按约定返回结果。Host 再把结果交给模型，让它组织成用户能看懂的回答，或者继续安排下一步操作。

把整条链路连起来看：

```text
用户问订单进度
  → Host 把问题和相关工具说明交给模型
  → 模型提出工具名和参数
  → Host 检查权限，必要时征求用户确认
  → MCP Client 发送 tools/call
  → MCP Server 调用订单系统
  → 查询结果经 MCP Client 返回 Host
  → 模型根据结果回答用户
```

模型并不是自己连上 Server、直接执行数据库操作，真正执行调用的是应用及其客户端组件。

统一协议省掉的是反复编写发现、通信和调用适配逻辑的工作，不是所有业务工作。订单权限怎么校验、超时后怎么办、是否允许退款，这些仍然需要应用和服务端认真处理。

### 4. 工具变了：通知客户端重新获取

假设订单服务后来新增了“查询物流轨迹”工具，客户端不必靠重启来碰运气。

如果服务端声明支持 `tools.listChanged`，工具列表变化时就可以发送：

```json
{
  "jsonrpc": "2.0",
  "method": "notifications/tools/list_changed"
}
```

这条通知只是在说“列表变了”，不包含完整的新清单。客户端收到后，再调用 `tools/list`，更新缓存和提供给模型的工具说明。

这样就不用把工具列表写死在应用里。不过，能不能及时更新，还取决于客户端有没有处理通知、连接是否正常，不能理解成协议会自动保证所有应用永远拿着最新清单。

### 六、消息有了，靠什么传过去？

到这里，“说什么、怎么说”已经清楚了。剩下的问题是，这些 JSON 消息到底走哪条路。

沿着 MCP 的演进来看，常见的有三种方式：本地的 stdio、旧版 HTTP + SSE，以及后来的 Streamable HTTP。下面仍按 `2025-06-18` 版本介绍，旧版 HTTP + SSE 用来帮助理解已有实现和升级过程。

### 1. stdio：本机两个进程，直接读写输入输出

如果助手和工具都在本机运行，可以不用绕一圈网络，直接通过进程的标准输入、标准输出通信。

通常由 Host 中的客户端组件启动 MCP Server 子进程。具体怎么创建进程取决于操作系统，不必理解成所有平台都调用 `fork`。

原来的通信示意图，可以写成下面几步：

1. **启动**：Client 启动 Server 子进程，并取得它的输入输出管道。
2. **发送消息**：Client 把 JSON-RPC 消息写入 Server 的 `stdin`。
3. **返回消息**：Server 处理请求，把响应写入自己的 `stdout`，由 Client 读取。
4. **记录日志**：Server 可以往 `stderr` 写日志，Client 按需收集或转发。
5. **结束使用**：Client 关闭输入流，等待 Server 退出；必要时再终止子进程。

```text
Client ── JSON-RPC 消息 ──→ Server 的 stdin
Client ←─ JSON-RPC 消息 ─── Server 的 stdout
Client ←─ 可选日志 ───────── Server 的 stderr
```

这里有个很容易踩的坑：`stdout` 是协议通道，别顺手往里面打印“服务启动成功”之类的普通日志。客户端可能把这行字当成 JSON 解析，连接就出问题了。

stdio 中的消息按换行分隔，一条消息应放在一行里。本文为了方便阅读，把 JSON 展开成了多行；实际通过 stdio 发送时要序列化成单行消息。

这种方式少了网络传输这一层，适合桌面助手、IDE 插件调用本地文件或本机工具。Server 的启动和清理通常由 Host 管理，但意外退出时是否清理干净，仍取决于实现，不能只靠“父进程没了，子进程肯定也没了”这个假设。

### 2. 旧版 HTTP + SSE：发消息和收消息分两条路

工具部署到远端以后，就需要网络通信。旧版 MCP 的一种标准做法，是把 HTTP POST 和 SSE 配合起来使用。

SSE，也就是 Server-Sent Events，允许服务端在客户端建立的 HTTP 响应流里持续发送事件。不过，这条流是服务端往客户端发，客户端不能反过来沿着同一条流提交工具调用。

所以旧方案把收、发分开了：

- **接收方向**：客户端打开一个 SSE 长连接，持续接收服务端消息。
- **发送方向**：客户端向另一个地址发 HTTP POST，把 JSON-RPC 消息交给服务端。

完整过程可以这样看，路径只是常见示例，不是必须使用的固定名字：

| 步骤 | 方向 | 发生的事情 |
| --- | --- | --- |
| 1 | Client → Server | 请求 GET /sse，建立 SSE 连接 |
| 2 | Server → Client | 在 SSE 流中发送 endpoint 事件，告知消息提交地址，例如 /messages |
| 3 | Client → Server | 向该地址发送 HTTP POST，提交 JSON-RPC 消息 |
| 4 | Server → Client | 在原来的 SSE 流中发送响应、通知等消息 |
| 5 | 双方继续交互 | 重复 POST 提交和 SSE 接收的过程 |
| 6 | Client | 使用结束后关闭 SSE 连接 |

它能工作，问题是客户端得同时照顾提交消息的请求和接收消息的长连接；代理超时、连接中断、服务端会话管理，也都得考虑。

SSE 本身有重连相关机制，但“连接重新建立”不等于“中断期间的工具结果一定能补回来”。旧版传输没有统一保证完整的会话恢复和消息重放，应用仍要处理这些问题。

### 3. Streamable HTTP：统一入口，按需返回普通结果或事件流

Streamable HTTP 对远程通信方式做了调整：客户端使用一个统一的 MCP 端点，例如 `/mcp`，不再依赖旧方案那种单独发布 SSE 地址和消息提交地址的结构。

客户端发消息时，向这个端点提交 HTTP POST。对于 JSON-RPC 请求，服务端可以按情况选择两种回应方式：

- **直接返回 JSON**：一次查询很快完成，就用 `application/json` 返回结果。
- **返回 SSE 流**：需要持续发送消息时，用 `text/event-stream` 返回事件流，最终在流中给出这次请求的响应。

所以它不是“把 SSE 彻底去掉了”，而是让流式通信按需要使用，不必所有交互都绑定在一条预先建立的 SSE 长连接上。

客户端发送 POST 时，需要在 `Accept` 中声明同时支持 `application/json` 和 `text/event-stream`。它还可以对同一个 `/mcp` 端点发起 GET，建立用于接收服务端消息的 SSE 流；服务端如果不提供这类独立的流，可以返回 `405 Method Not Allowed`。

**统一的是端点，不是把所有通信都塞进一条连接，也不是一条 POST 请求包办整个会话。** 客户端发出的每条 JSON-RPC 消息都需要新的 POST 请求，底层 HTTP 连接是否复用则是另一回事。

把初始化和后续交互的时序展开，就是下面这样：

| 阶段 | 客户端动作 | 服务端回应 |
| --- | --- | --- |
| 初始化 | 向 /mcp POST initialize | 返回初始化结果；如果使用会话管理，可以通过 Mcp-Session-Id 响应头分配会话 ID |
| 就绪通知 | POST notifications/initialized；若已分配会话 ID，则携带该 ID | 接受通知后返回 202 Accepted，不带 JSON-RPC 响应体 |
| 业务请求 | POST tools/list、tools/call 等请求 | 返回一个 JSON 结果，或者开启 SSE 流并在流中返回响应 |
| 客户端通知或响应 | 通过新的 POST 提交相应消息 | 接受后返回 202 Accepted，不带 JSON-RPC 响应体 |
| 独立接收服务端消息 | 按需对同一个 /mcp 发 GET | 返回 SSE 流；不支持时返回 405 |

按这个版本的 HTTP 规则，初始化之后的请求还要带上协商好的 `MCP-Protocol-Version` 请求头。若服务端分配了会话 ID，客户端也需要在后续请求中携带它。

这里有两个细节值得单独记一下。

第一，HTTP 层的 `202 Accepted` 只是说通知或响应已经被接收，并不是给 JSON-RPC 通知补了一份业务响应。通知依然没有对应的 JSON-RPC 响应消息。

第二，流式返回不等于必须依赖 HTTP/1.1 的分块传输编码。流式传输可以使用适合当前 HTTP 版本的机制，MCP 规定的是上层消息和交互规则，不是把实现限定死在某一种底层编码上。

那断线恢复呢？Streamable HTTP 为会话管理、事件 ID 和恢复读取提供了约定。支持消息保留和重放的服务端，可以给 SSE 事件设置 ID；客户端重连时，通过 `Last-Event-ID` 表明自己读到了哪里。

但这不是“带个 Session ID 就永远不会丢消息”。会话 ID 用来识别会话，事件 ID 用来标记接收位置；能否补发，还要看服务端是否实现了恢复、保存了哪些消息，以及相关会话是否仍然有效。

这套方式的好处主要是入口更统一、普通请求和流式请求都能处理，也方便接入现有 HTTP 基础设施。是否维护会话、是否保持独立接收流，可以根据实现和业务需要选择。部署时仍要注意网关的流式转发、缓冲和超时配置。

如果还要兼容旧版客户端，服务端可以同时保留旧的 SSE、POST 端点和新的 MCP 端点。这个兼容需要实现，不能假定换成 Streamable HTTP 后旧客户端就自然都能连上。

### 三种方式放在一起，怎么选？

| 传输方式 | 消息怎么走 | 主要特点 | 常见场景 | 需要留意什么 |
| --- | --- | --- | --- | --- |
| stdio | Client 写 Server 的 stdin，读取 stdout；日志走 stderr | 本地进程通信，不需要网络端点 | 桌面助手、IDE 插件、本机文件和工具访问 | 运行环境、进程清理，以及不要把日志写进 stdout |
| 旧版 HTTP + SSE | GET 建立 SSE 接收流，通过另一个端点 POST 发送消息 | 能远程通信，但发送和接收分开管理 | 对接仍使用旧传输的现有服务 | 长连接、会话关联、断线后的结果处理 |
| Streamable HTTP | 同一个 MCP 端点接收 POST，按需返回 JSON 或 SSE；也可通过 GET 接收事件流 | 统一端点，兼顾普通请求和流式交互 | 新建远程 MCP 服务，以及旧服务升级 | 协议版本、鉴权、可选会话、恢复能力和网关配置 |

本机工具通常先考虑 stdio；新建远程服务可以优先考虑双方都支持的 Streamable HTTP；对接已有系统时，先确认它支持的协议版本和传输方式，再决定怎么接。

不管选哪种，变化的是消息经过的通道。工具发现、调用、结果处理这些数据层约定，并不需要跟着另起一套。

### 七、回头看，MCP 到底省下了什么？

还是开头那个查订单的需求。没有共同约定时，客服助手接一次，售后助手接一次，换个框架可能又接一次。重复的往往不是查询逻辑，而是围绕工具写的那圈接入代码。

用了 MCP，订单团队可以专心维护一个提供查询能力的 Server。不同助手按照共同协议连接它，先协商能力，再获取工具说明，最后按需调用。

这里最重要的不是多了一个 `tools/call` 接口，而是几件事情终于有了共同的做法：

- 工具由独立的能力提供方维护，不必跟着每个智能体各写一份。
- 客户端能按统一规则发现工具、理解参数和处理结果。
- 本地进程和远程服务可以使用各自合适的传输方式。
- 工具列表发生变化时，有通知和重新发现的机制，不必只能依赖硬编码。

这不代表任何工具都能零成本接入任何应用。协议版本、客户端支持的能力、部署环境、鉴权和业务权限，仍然要对得上。

但至少，大家不用再从“你的接口长什么样，我重新写个适配器”开始。工具实现可以复用，应用也更容易组合不同服务的能力。

说到底，MCP 要做的就是把各个助手私有的工具接法，变成一套可以共同遵守的规则。工具团队把能力做好，智能体应用把模型、上下文和调用流程管好，双方通过协议配合，而不是在每个项目里重新绑在一起。

**总结**

通过深入剖析 MCP 的原理，我们看到它解决了传统 Function Call 的局限，将工具从智能体内部彻底解耦，并形成可复用、可组合的独立能力服务 。 MCP 并非一个框架，而是一种能力协商协议，其核心价值在于确立了工具发现、调用和通信的标准化语言（JSON-RPC 2.0）和传输机制（Stdio, Streamable HTTP）。正是这种彻底的标准化和解耦，使得工具无论用何种语言编写，都能被任何智能体应用无缝接入和动态调用 ，大家都可以根据自己的需要，按照统一标准创建各种 MCP 工具服务，避免了重复造轮子。 MCP 的出现，也标志着智能体正在从孤立的工作模式，转向即插即用的生态化协作模式。
