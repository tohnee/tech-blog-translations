> 原文：INC-MoE: Overlapping In-Network Collectives and Expert Computation for Expert-Parallel Mixture-of-Experts Inference<br>作者：John Stephan、Razvan Puscasu、Xu Yong、Ding Jiutao、Guan Zixuan（华为瑞士 / 华为北京）<br>arXiv:2610.36339v1，cs.DC，2026-10-26，19 页

MoE（混合专家）推理的算力账很好算：每个 token 只走 top-k 个专家，参数量上去了、计算量没上去。但一旦把专家切到多张卡、多个节点上，账就不一样了——每层都必须先把 token 送到「拥有它选中专家」的那张卡（dispatch），算完再把各卡的加权结果收回 token 的属主卡（combine）。这两步卡在每一层的关键路径上，而且跨节点带宽远低于节点内带宽时，它们能吃掉 MoE 层的大半延迟。

这篇论文的出发点很朴素：**dispatch 和 combine 在 vLLM 里本来就是两个标准集合通信**——一个 AllGather、一个 ReduceScatter。既然是标准集合通信，为什么不交给交换机做？更进一步，作者找到了一个很漂亮的观察：in-network 的 AllGather 是「收得多、发得少」，in-network 的 ReduceScatter 是「发得多、收得少」，两者**方向正好相反**。于是同时跑这两件事，正好把每条链路的两个方向都喂满，带宽受限的通信时间可以直接砍掉三分之一（4 卡）到 43%（8 卡）。

## 一、问题：MoE 一层的三段串行

在「数据并行 attention + 专家并行 FFN」这种最常见的部署形态里（vLLM 的默认 EP 路径），一个 MoE 层是这样执行的：

![](https://pica.zhimg.com/v2-c4a4e29becf9641aa971268ad5addec0_1440w.jpg)

图 2：vLLM 默认 EP 路径下一个 MoE 层的执行：AllGather → MoE 计算 kernel → ReduceScatter，三段严格串行

AllGather 把每个 rank 的 token 隐状态广播给所有 rank（这样每个 rank 都能算「自己负责的那些专家」对应的部分和），然后是专家计算（对齐/重排 + 两个 grouped GEMM 中间夹一个激活），最后 ReduceScatter 把各 rank 的部分和加起来、把属于自己 token 的行还回来。

两个低效点：

- **三段串行**。FFN 必须等整个 AllGather 完成才能开始，RS 必须等所有 token 的 FFN 都算完才能开始。通信时间全额暴露在关键路径上。
- **ring 集合通信本来就对称**。ring AllGather 和 ring ReduceScatter 各自都会用到两个方向，所以一个 collective 单独就能把链路喂饱——你把 AG 和 RS 重叠起来，总时间并不会缩短。

第 2 点很关键，它解释了为什么「微批重叠」「kernel 融合」这类工作只能把通信藏到计算后面，却不能减少通信本身。

顺带说一句，论文用的是 AllGather/ReduceScatter 而不是 all-to-all，这是有意的取舍：AG 把每个 token 发给所有 rank，不管它的专家在不在那儿。作者算过这笔冗余——E=64、k=8、N=4 时，某个 rank 一个专家都不沾的概率是 8.5%，也就是一个 token 平均需要 3 个远端 rank 中的 2.74 个，AG 只比「完全去重的 all-to-all」多传约 9%。用 9% 的冗余换一个**与路由无关的规则通信模式**，而这个规则性正是能卸载到交换机的前提。

## 二、第一层洞察：AG 收得多、RS 发得多，所以能同时跑

设 S 是整个 gather buffer 的字节数（即所有 rank 的 token 合起来），每个 rank 贡献 S/N。

- **ring AllGather**：每个 rank 发 (N−1)/N·S、收 (N−1)/N·S。两个方向都吃满。
- **in-network AllGather**：根节点把消息发给交换机，交换机多播给其余 N−1 个 rank。每个 rank 只**发** S/N（自己那一份，与 N 无关），但仍然要**收** (N−1)/N·S。
- **ring ReduceScatter**：同样是双向各 (N−1)/N·S。
- **in-network ReduceScatter**：每个 rank 要把自己那份部分和发给 N−1 个根，所以**发** (N−1)/N·S，但只**收** S/N（交换机已经帮它把 N−1 份减完了，根只做一次本地加法）。

于是发生了一件很有意思的事：单独看，in-network AG 和 in-network RS 的完成时间和 ring 版本**一模一样**——都是 (N−1)/N·S/BW，因为带宽受限时决定时间的是「更忙的那个方向」，而它们各自都有一个方向是满的。

![](https://pic4.zhimg.com/v2-deb4ad86f1baf747295252f825c15e43_1440w.jpg)

图 4：N=4 时 ring（需 N−1 个串行步，每步在端卡上做一次加法）与 in-network（单步：交换机多播 / 交换机归约）的 AG 与 RS 状态对照

但两者**并发**时，情况完全不同。AG 占的是接收方向，RS 占的是发送方向，同时跑起来每个方向恰好是：

$\frac{S}{N} + \frac{N-1}{N}S = S$

也就是双向各 S 字节，完成时间是 S/BW。而 ring 版本并发时，每个方向是 2(N−1)/N·S，一点没省。于是：

$t_{ring} = \frac{2(N-1)}{N}\cdot\frac{S}{BW},\qquad t_{INC} = \frac{S}{BW},\qquad 1-\frac{t_{INC}}{t_{ring}} = \frac{N-2}{2(N-1)}$

N=4 时 33.3%，N=8 时 42.9%，N 趋于无穷时趋近 50%。换成等效带宽的说法：并发的 in-network 集合通信最多能到并发 ring 集合通信的 2(N−1)/N 倍，N=4 就是 1.5 倍。

| 配置 | AG 发送 | AG 接收 | RS 发送 | RS 接收 | AG+RS 并发时间 |
| --- | --- | --- | --- | --- | --- |
| ring | (N−1)/N·S | (N−1)/N·S | (N−1)/N·S | (N−1)/N·S | 2(N−1)/N·S/BW |
| in-network | S/N | (N−1)/N·S | (N−1)/N·S | S/N | S/BW |

表 1：每个 rank 的流量（单位 S）与带宽受限时间。注意 in-network 的一行里，AG 的发送和 RS 的接收都很小，AG 的接收和 RS 的发送都很大——这正是「方向相反」的量化表达。

这个推导有个前提：N ≥ 3。N=2 时两个 in-network collective 各自已经是对称占用链路，改善为 0。也就是说这套方案只在**多节点 scale-out**（N 至少 4）时有意义，这也和论文的定位一致。

## 三、第二层洞察：只卸载不够，必须让 AG 和 RS 同时在飞

上面那个上界有一个讨厌的地方：在一个 MoE 层内部，AG 和 RS 是**严格依赖**的——RS 要等 FFN 输出，FFN 要等 AG 完成。光把两个 collective 卸载到交换机，它们还是串行的，一点收益都没有。

作者的解法是把一层的 token 切成若干个 **band**，然后把 AG、专家 FFN、RS 融合进**一个 persistent kernel**，用三类角色专用的 thread block 分别干这三件事：

![](https://pic2.zhimg.com/v2-5dfd8f27992f812d88fff3e82f3cefa7_1440w.jpg)

图 3：INC-MoE 总览：gather / compute / reduce 三类 thread block 按 band 流水，同时实现「通信-通信重叠」（AG 与 RS）和「通信-计算重叠」（AG/RS 与 FFN）

稳态下三层 band 同时在飞：gather block 在发第 j+1 个 band 的 AG，compute block 在算第 j 个 band 的 FFN，reduce block 在做第 j−1 个 band 的 RS。AG 占接收方向、RS 占发送方向，FFN 藏在两者后面。

几个工程细节决定了这套流水能不能真的跑起来：

- **band 边界必须逐位一致**。band j 取每个 rank 块的第 [jβ, min((j+1)β, Tmax)) 行，三类角色用同一套算术算边界。差一行，reduce 就会去发 compute 还没写的行，或者 compute 读到 gather 还没收到的行。
- **layout 用 padding 抹平不均衡**。各 rank 的 token 数不同，所以 gather/reduce buffer 统一按 N 个 Tmax 行（Tmax = 各 rank token 数的最大值）的块排布，rank r 的 token 占第 r 块的前 Tr 行。所有 rank 在层开始前就知道这些计数（vLLM 的 DP 元数据里有），不需要额外交换元数据。
- **完成信号用单调递增的计数器 + epoch**，不在操作之间清零。这样「上一次操作的迟到信号」和「这一次的重置」之间不会打架，因为 band 流水会连续发同类 collective。
- **跨 rank 同步只在一处**：每个 band 的 RS 之前做一次跨 rank barrier，每个 rank 只有一个 block 参与，然后通过本地 flag 广播给本卡其他 block。卡内则用 release/acquire 语义的 per-block 进度计数器，消费者只等它真正需要的那几个 block。这样避免「全 grid barrier 让最慢的 block 决定所有人节奏」。
- **空 band 也必须走完流程**。某个 band 在某些 rank 上可能是空的，或者某个本地专家一行都没分到——这些情况下 block 跳过计算，但**计数器与 barrier 必须照常推进**，否则各 rank 的到达次数不一致，流水直接死锁。
- **尾协助（tail assistance）**。最后一个 band 的 AG 完成后，AG 和 RS 的重叠就消失了，这段时间 RS 独自在关键路径上。于是发完最后一次 AG 的 gather block 去帮 reduce block 做最后几个 band 的本地归约。这个优化在 64K token/卡以上才明显，以下收益很小。

## 四、实现要点：消息语义、零拷贝、epilogue 融合

**消息语义，而不是内存语义。** 这一点值得单独说。很多 GPU 通信库（含 FlashMoE 一类工作）走的是「一个 rank 直接写对端显存」的内存语义；INC-MoE 走的是「端卡与交换机之间传消息」，交换机负责复制和归约 payload。好处有两个：交换机天然适合多播/归约；端卡完全不需要知道对端内存布局，只需要在消息里带 opcode、root、payload 在注册 buffer 里的字节范围、以及接收方该往哪个地址写完成信号。代价是多了一次「消息封装」的语义层。

**AG 用 rooted multicast，RS 用 rooted reduction。** AG 里每个 rank 都是自己那份数据的根：发一份给交换机，交换机多播给其余 N−1 个；每个 rank 只发一次，与 N 无关（ring 要转发 N−1 次）。RS 里每个 rank 是「自己 token 那个 shard」的根：其余 N−1 个 rank 分块把部分和送来，交换机凑齐一块就减一块、减完就转发（到达、归约、转发三级流水），根最后加一次自己的部分和。所以一个 rank 只收一个已经减好的 shard，而不是像 ring 那样收 N−1 个部分 shard、在卡上减 N−1 次。

**FFN 的 epilogue 直接写进 RS 的发送 buffer。** gate/up 两个投影用一个 GEMM 算（权重拼在一起），SwiGLU 在寄存器里对累加器做，只有激活后的中间结果落显存；down 投影的 epilogue 逐行乘路由权重 g(t,e)，直接累加进「该 token 在 RS 发送 buffer Z 里的那一行」。于是 FFN 和 RS 之间没有单独的加权、scatter、staging 步骤。

**输出零拷贝。** 根的本地归约把最终结果留在了 Z 里 rank 自己那块，INC-MoE 直接把这块以 tensor view 的形式交给 serving engine，不复制到另一个 output tensor。buffer 在引擎消费完之前不复用。

**vLLM 即插即用。** 替换的是「router 之后、专家计算之前」这一段；路由（专家选择与权重归一化）仍由引擎自己的函数做。模型维度、专家数、k、数据类型、EP 度都是运行时参数，任何「专家是 fp16/bf16 SwiGLU FFN」的 MoE 模型都能直接用。

![](https://pic2.zhimg.com/v2-df9ca171d9fd27a94747b19a925e1e59_1440w.jpg)

图 5：测试台：4 张卡各模拟一个节点（EP rank），第 5 张卡模拟 INC 交换机，通过一条 400 Gbps 链路共享给 4 个 rank，每 rank 有效 100 Gbps

## 五、实验：33% 的 TTFT 是怎么来的

测试台是 5 张加速卡：4 张当 EP rank（每张模拟一个节点，彼此不走节点内互连，全部走 RoCE 到一台以太网交换机），第 5 张专门模拟 INC 交换机。模型是 OLMoE-1B-7B（16 个 MoE 层，E=64，top-8，H=2048，专家中间维 1024，fp16），vLLM 配置 DP=4、EP=4、无 TP，只测 prefill，每卡 token 数从 24K 扫到 126K。

先看集合通信本身。并发发一对 AG+RS，测两者都完成的耗时，折算成等效带宽：

![](https://pic1.zhimg.com/v2-957fd48fa6f7e344a210f21ca20dc890_1440w.jpg)

图 6：并发 AG+RS 的等效带宽随 buffer 增大：ring 稳定在约 130 Gbps（上界 133 的 97.5%），in-network 163–172 Gbps（比 ring 高 25.6%–31.8%，达上界 200 的 82%–86%）

两个细节值得注意：ring 的曲线在所有消息尺寸上都平的，因为它本来就没有重叠空间；in-network 的曲线随消息变大而上翘——作者很老实地解释了原因：交换机是**用一张加速卡模拟**的，每条消息都有固定开销，RS 的 N 个 rooted reduction 还是串行服务的，小消息摊不薄这些开销。真正的交换机按线速处理，还能并行服务所有根，所以这条依赖应该会消失。

端到端 TTFT：

![](https://pic4.zhimg.com/v2-f1ec74a251d29377c5015461f348d83d_1440w.jpg)

图 1：OLMoE-1B-7B prefill 的 TTFT 随每卡 token 数变化，柱上百分比为相对 vLLM 默认 EP 路径的降幅（20.2%–33.1%）

具体数字：24K 时 TTFT 从 1.091 s 降到 0.871 s（−20.2%），126K 时从 5.623 s 降到 3.761 s（−33.1%）。换算成吞吐：

![](https://pic3.zhimg.com/v2-e378d58c27307d25b69edad9ad7801ce_1440w.jpg)

图 7：prefill 每卡吞吐（与图 1 同一批运行）：基线稳定在 22.5K–23.8K tokens/s，INC-MoE 为 28.2K–34.3K tokens/s（+25.3%–49.5%）

基线的吞吐几乎不随 prompt 变长而变化（22.5K–23.8K），说明它的开销随 token 数线性增长；INC-MoE 的吞吐反而随 prompt 变大而上升（28.2K → 34.3K），有两个原因叠加：band 变大后模拟交换机的固定开销摊薄了；band 数从 3 增到 10，fill/drain 阶段（AG 与 RS 不重叠的那两段）占比变小。

数值正确性方面：逐 token 对比每个 MoE 层的输出，16 层 × 4 rank 的 cosine 相似度都是 1.0。

## 六、批判性评估：这些数字之外还有什么

论文写得相当克制，但有几个点必须自己打折扣：

**1. 交换机是模拟的，而且是「一张卡」模拟的。** 这意味着端到端数字里含模拟器伪影，而且伪影方向不完全一致：固定开销让 in-network 吃亏（图 6 里 82%–86% 的上界达成率就是这个原因），但反过来，模拟器也没有真实交换机的排队、拥塞、多租户干扰。真实硬件上收益「应该更大」，这是作者的推断，没有人验证过。

**2. 基线只有 vLLM 默认路径。** 相关工作里点了 DeepEP、pplx-kernels（高吞吐 all-to-all）、Comet（细粒度计算-通信重叠）、FlashMoE（单 kernel 融合 + 单边传输），但实验里一个都没比。而这些恰恰是工业界真在用的对手。论文的定位是「交换机能做什么」，这个定位无可厚非，但读者不能把 33% 直接读成「比所有 EP 实现快 33%」。

**3. 只测了 prefill。** decode 阶段 FFN 的计算量小、通信占比更高，band pipeline 的 compute 段很可能填不满「AG 与 RS 同时在线」的时间窗——收益结构会变，可能更好（通信占比更高）也可能更差（compute 撑不住流水）。论文没有给 decode 的任何数字，这是一个明显的空白。

**4. AG/RS 的冗余随 N 增长。** 9% 这个数字是 E=64、k=8、N=4 算出来的。EP 度上到 8、16 甚至更高时，一个 rank 沾不到某个 token 任何专家的概率会下降（更多 rank 分摊专家），但「发给所有 rank」的绝对冗余仍然存在；更重要的是，AG 要求每个 rank 收到全部 (N−1)/N·S，这个接收量在 N 大时几乎等于全量，是实打实的。

**5. 依赖现网不具备的交换机能力。** 多播、线速归约、以及消息语义（opcode/root/字节范围/完成地址）这一整套接口。论文没有给交换机的面积、功耗、成本、可编程性评估，也没有讨论多租户/多任务下的隔离。这类「网络内计算」论文的共性短板。

**6. 层间没有流水。** 每个 MoE 层一个 persistent kernel launch，层与层之间 rs 的尾巴和下一层 AG 的头部不能重叠。对 16 层的模型，这个边界损失 × 16 不可忽略（论文没报 kernel launch 开销）。

**7. 没有开源。** 没有 artifact 链接，MSCCL++ 是公开的，但交换机侧服务和 band 流水 kernel 都要自己重写。

## 七、对做推理系统的人有什么用

即使你手上没有 INC 交换机，这篇论文里有两个东西是可以直接拿走的。

**第一，判断「重叠通信有没有用」的方法。** 不要笼统地问「这两个 collective 能不能重叠」，而要问「它们各自单独跑的时候，是否已经对称地占满了链路两个方向」。ring 算法是对称的，所以重叠无效；任何「收多发型 + 发多收型」的组合才有 2 倍空间。这个判据可以套到任何通信优化上，包括你在单机内做 NVLink 上的通信规划。

**第二，用规则性换可卸载性。** AG/RS 比 all-to-all 多传 9%，但换来与路由无关的固定模式——这是它能被交换机识别、复制、归约的根本原因。做系统设计时，「让通信模式变得可预测」往往比「让通信量少 9%」更值钱。

工程上的三个坑也很值得记：

- band 边界的算术必须所有角色、所有 rank 完全一致，差一行就是数据竞争或死锁；
- 空 band 必须走完整流程（计数器、barrier 一个不能少），这是所有流水线 kernel 的通病；
- 跨 rank 的同步点要尽量少、尽量粗（每 band 一次、每 rank 一个 block 参与），卡内用 per-block 计数器代替全 grid barrier。

什么情况下不该用这套方案：N=2（理论上就没有收益）；通信不是瓶颈（compute-bound 的大 batch prefill，比如单机 8 卡 NVLink）；以及没有 INC 交换机——那就退回到「微批重叠 + 融合 kernel」这条已经被 vLLM dual batch overlap、SGLang two-batch overlap 走通的路。
