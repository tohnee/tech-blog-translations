KV Cache是一个老生常谈的问题了，但似乎很多人并不明白什么时候该压缩kv cache，以及压缩到什么程度。这篇文章借几个月前的turboquant来谈一谈。

kv cache一直有一个显眼的问题：上下文越长、并发越高，占用的显存就越大。对标准 Decoder Transformer，一层 KV Cache 的大小近似为： $$ 2 \times \text{token 数} \times \text{KV head 数} \times \text{head dim} \times \text{元素字节数} $$

前面的 2 分别对应 Key 和 Value。模型层数和并发数再乘上去，最终显存占用很容易达到数十 GB。GQA 和 MQA 可以减少 KV head 数，但没有消除 KV Cache 随序列长度线性增长的问题。

我需要先说得是，TurboQuant 最合适的场景，不是单请求延迟优先的普通推理，而是 KV Cache 已经限制上下文长度或并发数的高负载服务。这类系统通常同时满足几个条件：

- 上下文很长，或者在线请求很多；
- GPU 显存放不下更多 KV Cache，请求开始排队；
- 必须保留全部历史 token，不能接受 token eviction；
- 可以牺牲一部分单 token 速度，换取更大的 KV 容量和更低的排队时间。

如果显存不是瓶颈，BF16 kv cache通常更合适。如果只需要大约 2 倍 KV 容量，FP8可能就够了。TurboQuant最适合的场景是 FP8 的 2 倍容量不够，需要用4bit压缩继续换取约 3.4 倍的显存容量，并且愿意承担额外的反量化开销和一定精度损失，这是 TurboQuant 的key point，它是一个显存容量方案，并不是加速方案。使得压缩后的请求可以更多地驻留在 GPU 上，但每个 token 的计算反而可能更慢。

TurboQuant 试图解决的就是这部分显存开销，它把原本以 FP16 或 BF16 保存的 K、V 压缩到 3～8 bit 左右，同时尽量保留 attention 所需的几何信息。同时，KV Cache 是运行时动态产生的，是动态量化，如果做长时间的离线校准去弄一个静态量化的scale的话，这是行不通的，精度直接gg；runtime的适合，新 token 产生后，K、V 必须立即完成量化和写入，后面用到的时候再拿出来反量化，这和我之前多次提到的kv为存储精度而不是计算精度相match。

本文主要不是讲TurboQuant量化算法，而是和大家分享一下它的实际应用场景和配置选择，这个我觉得比枯燥的数学公式推理有趣得多。另外，TurboQuant也遗留了很多工作并未做完，比如3bit kv和k3v4的稳定性，好了，发paper的机会又来了，我已经帮大家找到了科学研究问题了，剩下就看你们怎么解决了orz。。

### TurboQuant 的核心原理

略过，个人不喜欢量化的这些算法推导，感觉特别枯燥，感兴趣可以自己去看TurboQuant论文推导

### vLLM TurboQuant

当前 vLLM 针对TurboQuant的实现可以概括为：

- Key：Hadamard rotation + Lloyd-Max 标量量化，或者直接存 FP8；
- Value：按 token、按 KV head 动态计算 min/max，做 3-bit 或 4-bit 均匀量化；
- Decode：在 Triton/FlyDSL attention kernel 中边读取、边解包、边计算；
- Prefill：首段仍然用原始 FP16/BF16 K、V 跑 FlashAttention，同时把 KV 压缩写入 Cache。

并且有如下四种配置的量化以适配不同场景。激进程度依次增高。

### `turboquant_k8v4`

这个配置的 Key 直接保存为 FP8，Value 保存为 4 bit。

- K：FP8 E4M3 类格式；
- V：4-bit uniform；
- V 的 scale 和 zero：每个 token、每个 KV head 动态计算并以 FP16 保存；

以 head dimension 128 为例，每个压缩层中，每个 token/head 的 K+V 占 196 字节。原始 FP16 K+V 是 512 字节，对应约 2.61 倍的层内物理压缩，vLLM 的整模型实测容量约为 2.4 倍。

这是四个 TurboQuant preset 中精度风险最低的配置，但不是实际部署的首选。vLLM 的大模型评测显示，它相比原生 FP8 只多提供少量容量，却持续增加 latency、降低吞吐。若硬件支持 FP8 attention，应先测试 `--kv-cache-dtype fp8`，即kv保留为fp8

### `turboquant_4bit_nc`

Key 和 Value 都使用 4 bit，其中 Key 使用 Lloyd-Max，Value 使用动态均匀量化。后缀里面的`nc` 表示 norm correction，这里省略对这个的讲解。

head dimension 128 时，压缩层的物理 slot 为 134 字节，约为 FP16 KV 的 3.82 倍层内压缩，实测 KV 容量最高约为之前的 3.4 倍。

### `turboquant_k3v4_nc`

这个配置进一步把 Key 降到 3 bit，Value 仍保持 4 bit：

- K：3-bit Lloyd-Max + FP16 norm；
- V：4-bit uniform + FP16 scale/zero；

head dimension 128 时，压缩层内约为 4.34 倍。Key 精度下降，显然比 4bit_nc 更容易影响推理质量，整模型实际可用容量会因为非压缩层和布局开销而低于这个数字，虽然还是不低，这个需要实际针对模型测试通过后才能考虑采用。

### `turboquant_3bit_nc`

Key 和 Value 都保存为 3 bit，是压缩最激进的 preset：

- K：3-bit Lloyd-Max；
- V：3-bit uniform；

head dimension 128 时，压缩层内约为 5.02 倍。它是容量最激进的配置，但 vLLM 的长上下文和 reasoning 评测都显示出明显精度下降，同时解包成本也是四种 preset 中最高的，它不应作为默认配置。除非实际针对模型测试通过后才能考虑采用。

最后，`4bit`,`k3v4` 或 `3bit_nc` 描述的都是 KV Cache 的存储格式，并不是attention 使用 INT3×INT4 矩阵乘。这些低比特数据会在 attention kernel 中被反量化为 BF16/FP32 浮点数据，所以低比特kv cache带来的主要收益是减少 Cache 容量和 HBM 读取量，而不是使用 INT3/INT4 Tensor Core 提高算术吞吐。这一点和 FP8 KV Cache 不同，FP8 不仅压缩存储，还能使用硬件原生 FP8 attention，避免 TurboQuant 的复杂解包和浮点反量化成本。

### attention kernel 如何选择

常规 CUDA kernel对于以上四个量化方式而言，在VLLM里面都调用triton_turboquant_decode_attention，内部根据编译期参数dispatch到不同分支：

- `k8v4`：FP8 Key + V4；
- `4bit_nc`：MSE K4 + V4 + NC；
- `k3v4_nc`：MSE K3 + V4 + NC；
- `3bit_nc`：MSE K3 + V3 + NC。

第一阶段 kernel 完成：

1. 读取并解包 K；
2. 计算 attention score；
3. 读取并反量化 V；
4. 执行分块 online softmax 和 Value accumulation。

第二阶段再reduce不同 KV splits。

prefill 直接使用原始 K、V 调用 FlashAttention，同时把 KV 量化写入 Cache。对于较大的 continuation prefill，vLLM 还可能先把历史 KV 反量化，再调用 FlashAttention。因此 TurboQuant 最直接的收益出现在 Cache 容量和 decode 阶段。

### 适用哪些模型

从算法角度看，只要模型使用标准 dot-product attention，就可以考虑旋转量化 KV。从已经公开验证的范围看，比较适合：

- Decoder-only Transformer；
- 标准 MHA、GQA 和 MQA；
- Llama、Qwen、Mistral/MiniMax 一类使用标准 attention 的模型；
- 长上下文或大 batch serving；
- Key head dimension 为 64、128、256 等 2 的幂。

当前已明确不面向：

- Encoder 或 cross-attention；
- MLA/latent KV Cache；
- 依赖特殊 attention state 的非标准结构。

### 适用哪些硬件

vLLM 在 H100 上对 30B 和 70B 模型的系统评测显示，当前 TurboQuant kernel **没有**把带宽节省转化为更高的单 token 速度，反而：

- latency 相比 BF16 增加约 10%～68%；
- Qwen3-30B 的吞吐降至 BF16 的 73%～80%；
- Llama-3.3-70B 的吞吐降至 66%～75%；
- 量化越激进，packing 和反量化越复杂，吞吐通常越低。

**它的收益发生在显存饱和之后。Llama-3.3-70B 在 4 张 H100 上承受 burst 请求时，BF16 因 KV Cache 不足产生排队，P99 TTFT 上升到约 17 秒；TurboQuant 将其控制在 3.5 秒以内，不过 FP8 的结果更好，约为 1.3 秒。**

因此，TurboQuant 的性能价值应该表述为，牺牲 TPOT 和吞吐，换取更多可驻留请求，并在内存饱和时减少排队。它不是常规意义上的 decode 加速。（回忆一下为什么会有性能降低？）

### 实验结果应该怎么看

TurboQuant 论文在 Llama-3.1-8B-Instruct 上报告：

- Full Cache 的 LongBench 平均分为 50.06；
- TurboQuant 3.5 bit 同样为 50.06；
- TurboQuant 2.5 bit 为 49.44。

在 Ministral 模型上：

- Full Cache 为 49.89；
- TurboQuant 2.5 bit 为 49.62。

Needle-In-A-Haystack 实验中，TurboQuant 得分为 0.997，与 Full Precision 的 0.997 相同，并优于 SnapKV、PyramidKV 和 KIVI 等对照。

这些结果说明旋转量化在长上下文 KV Cache 上有潜力，原论文主要展示较小模型和有限任务上的结果。2026 年 5 月，vLLM 使用 v0.20.2 在 H100 上补充了一组更接近生产环境的评测，覆盖：

- Llama-3.3-70B；
- Qwen3-30B-A3B Instruct/Thinking；
- 200B+ 的 MiniMax-M2.7；
- Dense 和 MoE 模型；
- 最长 256K context；
- MRCR 长文本检索，以及 AIME25、GPQA、MATH500、LiveCodeBench reasoning。

这组结果给出了更清晰的精度分层，也启示了TurboQuant算法下，各精度类型该怎么选，如下

`k8v4` 和 FP8 在多数模型上都能恢复 BF16 的 98%～99% 以上准确率，**但 `k8v4` 的速度明显更慢，而整模型容量只从 FP8 的约 2 倍提高到约 2.4 倍。它很难成为比 FP8 更好的默认选项。**

`4bit_nc` 是**最实用**的 TurboQuant 配置。它在多数任务上损失约 1～4 个点，换取最高约 3.4 倍整模型 KV 容量。这个交换在显存紧张的服务或边缘部署中可能成立，但必须按目标任务验证。

`k3v4_nc` 和 `3bit_nc` 的风险明显更高。Qwen3-30B 在 128K～256K 长文本检索中，两者的 AUC 相比 BF16 出现约 30% 相对下降；在 AIME25 和 LiveCodeBench 等长输出 reasoning 任务上，准确率最高下降约 20 个点。误差会随上下文和生成长度积累，短 benchmark 上看似可用，不代表长任务安全。

vLLM 给出的参考 PPL 增幅是：

- `k8v4`：约 +1.17%；
- `4bit_nc`：约 +2.71%；
- `k3v4_nc`：约 +10.63%；
- `3bit_nc`：约 +20.59%。

这些结果能说明实际选型到底选哪一种

### 如何选择

我个人认为，如果准备在 vLLM 中使用 TurboQuant，可以按以下顺序测试：

1. 先建立 FP16/BF16 KV baseline，记录 PPL、LongBench、NIAH、吞吐、TTFT、TPOT 和最大并发；
2. 如果需要约 2 倍容量，先测试 `--kv-cache-dtype fp8`；
3. 只有 FP8 容量仍然不够时，再测试 `turboquant_4bit_nc`，观察 reasoning、长距离检索和 TPOT 是否可以接受；
4. `turboquant_k8v4` 通常没有足够优势替代 FP8，可以作为对照而不是首选；
5. 原则上避免两个 3 bit preset，除非容量压力极大，并且完整目标任务已经验证通过。

TurboQuant 最适合这样的系统：

- KV Cache 已经限制最大上下文或并发；
- 请求会因为 KV 显存不足而排队；
- 必须保留全部历史 token；

如果主要目标是减少 attention 计算量，可以考虑 token eviction、稀疏 attention 或架构级方案，因为TurboQuant 解决的是用在线、GPU 友好的方式减少 KV Cache 容量，让更多请求或更长上下文可以驻留在显存中。它不是对所有模型都无损的通用压缩算法，最终是否有效，要同时看四项指标：模型质量、TPOT、排队后的 TTFT，以及整机显存占用。
