### 一、引言

深度学习模型的规模正以指数级速度增长。从 2018 年 BERT 的 3.4 亿参数，到 2020 年 GPT-3 的 1750 亿参数，再到 2024 年 GPT-4（据传超过 1.8 万亿参数）以及各种开源大模型（Llama 3 405B、DeepSeek-V2 236B 等），模型参数量的激增对计算资源、存储带宽和通信效率提出了前所未有的挑战。

**训练加速**和**推理加速**已经成为大模型落地的核心问题：

- **训练阶段**：如何用有限的 GPU 资源在合理的时间内完成大模型训练？如何降低显存占用以避免 OOM（Out of Memory）？
- **推理阶段**：如何降低首 Token 延迟（Time to First Token, TTFT）？如何提高吞吐量（Throughput）？如何在单卡甚至 CPU 上运行百亿参数模型？

本文将从这两个维度出发，系统性地介绍当前工业界和学术界广泛采用的加速技术。

### 二、训练加速技术

### 2.1 数据并行（Data Parallel）

### 原理

数据并行（Data Parallel, DP）是最基本、最易理解的分布式训练策略。其核心思想是：

1. 将完整的模型复制到每张 GPU 上
2. 将每个 batch 的数据切分成多份，分别发送到不同 GPU
3. 每张 GPU 独立完成前向传播和反向传播，计算出本地梯度
4. 通过 AllReduce 操作同步所有 GPU 的梯度
5. 每张 GPU 用平均后的梯度更新本地模型参数

![](https://pica.zhimg.com/v2-d96551af3cc4a2d67b0ea68684ce3cd4_r.jpg)

### PyTorch 实现演进

**1. DataParallel (DP)** — 单机多卡，最早期的方案

```python
# PyTorch DataParallel 示例
import torch.nn as nn

model = nn.DataParallel(model)
output = model(input_data)
```

DP 的实现存在明显缺陷：

- 使用单进程多线程，受 Python GIL 限制
- 主卡（GPU 0）需要聚合所有梯度，负载不均衡
- 通信效率低

**2. DistributedDataParallel (DDP)** — 当前主流方案

```python
# PyTorch DDP 示例
import torch.distributed as dist
from torch.nn.parallel import DistributedDataParallel as DDP

dist.init_process_group(backend='nccl')
model = DDP(model, device_ids=[local_rank])
```

DDP 的优势：

- 多进程架构，每个 GPU 一个独立进程，不受 GIL 限制
- 使用 Ring-AllReduce 算法，通信效率 O(N) 且每个节点的通信负载均衡
- 梯度同步与反向传播重叠（overlap），进一步减少通信开销

**3. 通信算法：Ring-AllReduce**

Ring-AllReduce 是 DDP 底层的核心通信算法。假设有 N 个 GPU，每个 GPU 上的梯度被分成 N 份：

- **Reduce-Scatter 阶段**：经过 N-1 轮传递，每个 GPU 负责聚合一份完整的梯度
- **AllGather 阶段**：再经过 N-1 轮传递，每个 GPU 都获得聚合后的完整梯度

![](https://pic2.zhimg.com/v2-521e9ca77d69991c5d8462886cea1eb7_r.jpg)

通信量为 `2(N-1)/N × 数据量`，每个 GPU 的发送/接收量相同，避免了主从架构中的瓶颈。

### 局限性

数据并行的根本局限在于：**每张 GPU 必须能放下完整的模型**。当模型参数量超过单卡显存时（如 GPT-3 175B 需要约 350GB 显存仅存储参数），数据并行便无法直接使用。这就引出了模型并行。

> **参考论文**：

- Li et al., “PyTorch Distributed: Experiences on Accelerating Data Parallel Training”, VLDB 2020
- [PyTorch DDP 官方文档](https://pytorch.org/docs/stable/notes/ddp.html)

### 2.2 模型并行（Model Parallel）

模型并行的核心思想是将**模型本身切分到多张 GPU 上**，每张卡只负责模型的一部分。根据切分维度不同，主要分为张量并行和流水线并行。

### 2.2.1 张量并行（Tensor Parallelism）

张量并行将单个 Transformer 层内的参数矩阵切分到多张 GPU 上。

**以 Megatron-LM 为例**，对于一个 Transformer 层的 MLP 块和 Self-Attention 块：

![](https://pica.zhimg.com/v2-c0fb7495300fd5880cd2e57766c83b06_r.jpg)

**MLP 块切分**：

- 第一个全连接层 `Y = XA`：将权重矩阵 A 按列切分为 `A₁, A₂`，分别放在 GPU0 和 GPU1 上
- 激活函数 `Z = GeLU(Y)`：各卡独立计算
- 第二个全连接层 `W = ZB`：将权重矩阵 B 按行切分为 `B₁, B₂`

**Self-Attention 块切分**：

- 将 Q、K、V 的权重矩阵按列切分（按 attention head 维度）
- 每个 GPU 负责一部分 head 的计算
- 输出时通过 AllReduce 聚合

张量并行的通信量较大（每层都需要 AllReduce），适合在**同一节点内部的 GPU 之间**使用（NVLINK 高带宽）。

### 2.2.2 流水线并行（Pipeline Parallelism）

流水线并行将模型按**层**切分到不同 GPU 上：

- GPU 0 负责 Layer 1-8
- GPU 1 负责 Layer 9-16
- GPU 2 负责 Layer 17-24
- GPU 3 负责 Layer 25-32

![](https://pica.zhimg.com/v2-bf7d7cb2b3a1c12535f420e7b42f814c_r.jpg)

**关键挑战**：朴素流水线会导致大量 GPU 空闲时间（Bubble）。

**GPipe 方案**（Google, 2019）：

- 将 mini-batch 进一步切分为多个 micro-batch
- 前向传播：micro-batch 逐个通过流水线各阶段
- 反向传播：梯度按相反方向回流
- 流水线填充后，各 GPU 可同时工作
- Bubble 大小：`(K-1)/(M)`，其中 K 为 GPU 数量，M 为 micro-batch 数量

![](https://pic1.zhimg.com/v2-8e7338d698e936c509f732302993382e_r.jpg)

**1F1B（One-Forward-One-Backward）调度**（DeepSpeed/Megatron）：

![](https://pic3.zhimg.com/v2-fbd78bcbbfa8bca76ea0ec9ade2cd2c8_r.jpg)

- 在 warm-up 阶段连续发送若干 micro-batch 的前向计算
- 之后交替执行一个前向和一个反向
- 优点：显存占用更平稳，不需要保存所有 micro-batch 的中间激活
- Bubble 大小与 GPipe 相同

**Interleaved 1F1B**：

- 将每个 GPU 上分配多个模型片段（chunk），而非连续的一段层
- 进一步减少 Bubble，但通信量增加

### 2.2.3 3D 并行

在实际训练大模型时，通常将三种并行策略组合使用：

![](https://pic1.zhimg.com/v2-30a1d933952f1f0dfc90f6407566a308_r.jpg)

- **张量并行**：节点内部（NVLINK 高带宽）
- **流水线并行**：节点之间（网络连接）
- **数据并行**：跨节点组（最外层）

例如训练 GPT-3 175B 时，Megatron-LM 使用了 8 路张量并行 × 64 路流水线并行 × 若干数据并行。

> **参考论文**：

- Shoeybi et al., “Megatron-LM: Training Multi-Billion Parameter Language Models Using Model Parallelism”, 2019. [arXiv:1909.08053](https://arxiv.org/abs/1909.08053)
- Narayanan et al., “Efficient Large-Scale Language Model Training on GPU Clusters Using Megatron-LM”, SC 2021. [arXiv:2104.04473](https://arxiv.org/abs/2104.04473)
- Huang et al., “GPipe: Efficient Training of Giant Neural Networks using Pipeline Parallelism”, NeurIPS 2019. [arXiv:1811.06965](https://arxiv.org/abs/1811.06965)

### 2.3 混合精度训练（AMP）

### 原理

混合精度训练（Automatic Mixed Precision, AMP）在训练中同时使用 FP16（半精度浮点）和 FP32（单精度浮点）：

- **前向传播和反向传播**：使用 FP16，计算速度快、显存占用少
- **权重更新**：使用 FP32 Master Weights，保证精度
- **Loss Scaling**：放大 Loss 值，避免 FP16 下梯度下溢（underflow）

![](https://pic3.zhimg.com/v2-73fa7d0395f30afc930365b54c3d121c_r.jpg)

### 为什么需要 Loss Scaling？

FP16 的表示范围有限（最小正值约 6×10⁻⁸）。训练中很多梯度值非常小，在 FP16 下会变成 0（下溢），导致训练停滞。Loss Scaling 在反向传播前将 Loss 乘以一个大因子（如 2¹⁶），使得小梯度值能够映射到 FP16 的可表示范围，在更新前再缩放回来。

### PyTorch 实现

```python
from torch.cuda.amp import autocast, GradScaler

scaler = GradScaler()  # 默认动态调整 scale 因子

for data, label in dataloader:
    optimizer.zero_grad()
    
    with autocast():  # 前向传播自动使用 FP16
        output = model(data)
        loss = criterion(output, label)
    
    scaler.scale(loss).backward()   # 放大 loss 并反向传播
    scaler.step(optimizer)           # 更新权重
    scaler.update()                  # 动态调整 scale 因子
```

### 性能收益

- **计算吞吐**：Volta 及之后的 GPU（V100/A100/H100）的 Tensor Core 在 FP16 下吞吐可达 FP32 的 8 倍以上
- **显存节省**：FP16 的激活值和梯度占 FP32 一半的显存，大约可节省 30-40% 的显存
- **精度**：实践中，AMP 训练出的模型精度与纯 FP32 几乎无差异

### BF16：更好的选择？

NVIDIA A100 及之后的 GPU 支持 BF16（Brain Floating Point），与 FP16 相比：

- BF16 的指数位与 FP32 相同（8 位），表示范围更大，**不需要 Loss Scaling**
- BF16 的尾数位更少（7 位 vs 10 位），精度略低，但在深度学习中对最终模型精度影响极小

目前主流大模型训练（Llama、GPT-4 等）普遍采用 BF16 格式。

- Micikevicius et al., “Mixed Precision Training”, ICLR 2018. [arXiv:1710.03740](https://arxiv.org/abs/1710.03740)
- [NVIDIA Automatic Mixed Precision 文档](https://docs.nvidia.com/deeplearning/performance/mixed-precision-training/)
- Kalamkar et al., “A Study of BFLOAT16 for Deep Learning Training”, 2019. [arXiv:1905.12322](https://arxiv.org/abs/1905.12322)

### 2.4 梯度累积（Gradient Accumulation）

### 原理

梯度累积是一种**用时间换空间**的技巧，用于在显存不足以支持大 batch size 时模拟大 batch 训练：

1. 使用较小的 micro-batch size 连续执行多次前向+反向传播
2. 每次反向传播后不清零梯度，而是累积起来
3. 累积 N 次后，等价于使用 batch_size × N 的大 batch 进行一次训练
4. 然后执行一次优化器更新，并清零梯度

![](https://pic4.zhimg.com/v2-6a343ceece81535c9e3e48736d8beb6f_r.jpg)

```python
accumulation_steps = 4
optimizer.zero_grad()

for i, (data, label) in enumerate(dataloader):
    loss = model(data, label) / accumulation_steps  # 注意要除以累积步数
    loss.backward()
    
    if (i + 1) % accumulation_steps == 0:
        optimizer.step()
        optimizer.zero_grad()
```

### 注意事项

- **Batch Normalization**：梯度累积时 BN 层使用的是小 batch 的统计量，而非大 batch 的统计量，可能影响精度。建议使用 SyncBN（同步批归一化）或 Layer Normalization（Transformer 中常用）
- **等价性**：对于不包含 BN 等依赖 batch 统计量的层，梯度累积在数学上与使用大 batch 严格等价

- [HuggingFace - Gradient Accumulation 文档](https://huggingface.co/docs/transformers/v4.18.0/en/perf_train_gpu_one#gradient-accumulation)

### 2.5 梯度检查点/激活重计算

### 原理

反向传播需要用到前向传播的中间激活值来计算梯度。在大模型中，存储所有层的中间激活值（Activation）会占用大量显存——有时甚至超过模型参数本身。

**梯度检查点（Gradient Checkpointing / Activation Checkpointing）** 的思路是：**只保存部分层的激活值，其余的在反向传播时重新计算**。

![](https://pic2.zhimg.com/v2-1731dd89d3daa3bc94301d4ca679ce3b_r.jpg)

具体做法：

- 只在每 N 层保存一次激活值（checkpoint）
- 反向传播到非 checkpoint 层时，从最近的 checkpoint 开始重新执行前向计算，得到所需的激活值
- 重新计算后立即释放，不需要常驻显存

### 时间-空间权衡

- 显存节省：约 √(层数) 倍（理论最优），实践中可节省 40-70% 的激活显存
- 额外计算：需要重新计算部分前向传播，增加约 20-30% 的计算量
- **以计算换空间**的经典策略

### PyTorch 实现

```python
from torch.utils.checkpoint import checkpoint

# 对指定的模块/函数使用梯度检查点
output = checkpoint(self.attention_block, hidden_states, attention_mask)
```

### 2.6 DeepSpeed ZeRO

### 背景

微软 DeepSpeed 的核心贡献是 ZeRO（Zero Redundancy Optimizer）优化技术。传统数据并行中，每张 GPU 都保存完整的模型状态（参数、梯度、优化器状态），造成严重的显存冗余。ZeRO 通过**将模型状态分片到所有 GPU 上**来解决这个问题。

### ZeRO 的三个阶段

![](https://pic3.zhimg.com/v2-e9d6dd4acbc7e7efee9af7921ad287e4_r.jpg)

**显存占用分析**（以 7.5B 参数模型、Adam 优化器、FP16 为例）：

| 组件 | 大小 |
| --- | --- |
| 参数（FP16） | 7.5B × 2B = 15GB |
| 梯度（FP16） | 7.5B × 2B = 15GB |
| 优化器状态（Adam：FP32 参数 + FP32 动量 + FP32 方差） | 7.5B × 12B = 90GB |
| 合计 | 120GB |

其中优化器状态是最大的显存消耗者！

**ZeRO-1（优化器状态分片）**：

- 将优化器状态（如 Adam 的一阶矩 m 和二阶矩 v）分片到各 GPU
- 每个 GPU 只维护自己的分片，更新时也只更新本分片
- 显存节省：4 倍（从 120GB → 31.5GB）
- 通信量：与 DDP 相同

**ZeRO-2（优化器状态 + 梯度分片）**：

- 在 ZeRO-1 基础上，进一步将梯度分片
- 每张 GPU 的梯度通过 Reduce-Scatter 聚合到各自分片
- 显存节省：8 倍（从 120GB → 16.5GB）
- 通信量：与 DDP 相同

**ZeRO-3（优化器状态 + 梯度 + 参数分片）**：

- 将参数也分片到各 GPU
- 前向/反向传播时，按需从其他 GPU 收集所需参数分片（AllGather），用完即释放
- 显存节省：与 GPU 数量 N 呈线性关系（N 张 GPU 则节省约 N 倍）
- 通信量：比 DDP 增加 50%

### ZeRO-Offload 和 ZeRO-Infinity

**ZeRO-Offload**：将优化器状态和梯度卸载到 CPU 内存，进一步降低 GPU 显存需求。

**ZeRO-Infinity**：进一步支持将模型状态卸载到 NVMe SSD，使得在极少数 GPU 上也能训练超大模型。

### DeepSpeed 配置示例

```json
{
  "zero_optimization": {
    "stage": 2,
    "offload_optimizer": {
      "device": "cpu",
      "pin_memory": true
    },
    "allgather_partitions": true,
    "allgather_bucket_size": 5e8,
    "reduce_scatter": true,
    "reduce_bucket_size": 5e8,
    "overlap_comm": true,
    "contiguous_gradients": true
  }
}
# 使用 DeepSpeed 训练
import deepspeed

model_engine, optimizer, _, _ = deepspeed.initialize(
    model=model,
    model_parameters=model.parameters(),
    config_params='ds_config.json'
)

for batch in dataloader:
    loss = model_engine(batch)
    model_engine.backward(loss)
    model_engine.step()
```

- Rajbhandari et al., “ZeRO: Memory Optimizations Toward Training Trillion Parameter Models”, SC 2020. [arXiv:1910.02054](https://arxiv.org/abs/1910.02054)

### 2.7 FSDP（Fully Sharded Data Parallel）

### 原理

FSDP 是 PyTorch 官方对 DeepSpeed ZeRO-3 思路的等價实现。其核心机制：

- 将模型参数分片到所有 GPU 上
- 前向传播前：通过 AllGather 收集当前层所需的完整参数
- 前向传播后：立即释放非本分片的参数
- 反向传播前：再次 AllGather 收集参数
- 反向传播后：通过 Reduce-Scatter 将梯度聚合到各 GPU 的分片

![](https://pic1.zhimg.com/v2-7104827410ff954394ad37e8a7b47292_r.jpg)

### 与 DeepSpeed ZeRO-3 的对比

| 维度 | FSDP | DeepSpeed ZeRO-3 |
| --- | --- | --- |
| 维护方 | PyTorch 官方 | 微软 |
| 集成度 | 原生 PyTorch，API 一致性好 | 需要额外安装 |
| 性能 | 两者在 A100 上性能接近 | 更丰富的 offload 选项 |
| 生态 | torch.distributed 生态 | DeepSpeed 生态（含 Inference） |
| 使用复杂度 | 相对简单 | 配置项多，灵活度高 |

### FSDP 使用示例

```python
from torch.distributed.fsdp import (
    FullyShardedDataParallel as FSDP,
    MixedPrecision,
    ShardingStrategy,
)

# 配置混合精度
mixed_precision_policy = MixedPrecision(
    param_dtype=torch.bfloat16,
    reduce_dtype=torch.bfloat16,
    buffer_dtype=torch.bfloat16,
)

# 包装模型
model = FSDP(
    model,
    sharding_strategy=ShardingStrategy.FULL_SHARD,  # 对应 ZeRO-3
    mixed_precision=mixed_precision_policy,
    device_id=torch.cuda.current_device(),
)
```

> **参考论文**：

### 2.8 Flash Attention

### 动机

标准 Self-Attention 的计算和显存瓶颈：

- 给定序列长度 N、head 维度 d，注意力矩阵 `QK^T` 的大小为 O(N²)
- Softmax 需要完整的 O(N²) 矩阵才能计算
- 标准实现：在 HBM（高带宽显存）上分配完整的 O(N²) 注意力矩阵，读写开销极大

对于一个 8K 序列的 Attention 层，注意力矩阵约 64M 个元素，占 256MB（FP32），而经过 softmax + dropout 后仍需同样大小的矩阵。这成为长序列训练的瓶颈。

### Flash Attention 核心思路

Flash Attention 通过三个关键技术将 Attention 计算从 **IO-Bound** 变为 **Compute-Bound**：

1. **分块（Tiling）**：将 Q、K、V 切分成小块，逐块加载到 SRAM（片上共享内存）
2. **重计算**：不在 HBM 上保存完整的注意力矩阵，反向传播时重新计算
3. **Online Softmax**：增量计算 Softmax，不需要等待完整的注意力矩阵

![](https://pic3.zhimg.com/v2-56b396cb60f71e64de1a4e5751eb9d9e_r.jpg)

### 算法细节：Online Softmax

标准 Softmax：

```text
m = max(x)
s = sum(exp(x - m))
softmax(x) = exp(x - m) / s
```

Tiled Softmax（Online Softmax）：

```text
对每个块：
  m_new = max(m_old, m_block)
  s_new = s_old * exp(m_old - m_new) + s_block * exp(m_block - m_new)
  更新累积的 softmax 分子
```

这样就不需要一次加载整个 QK^T 矩阵。

### 性能

- **显存**：从 O(N²) 降至 O(N)（按块计算，无中间矩阵）
- **速度**：训练速度提升 2-4 倍（在长序列场景下更显著）
- **精度**：与标准 Attention 数学等价（数值上略有差异，但不影响最终模型质量）

### Flash Attention 版本演进

| 版本 | 改进 |
| --- | --- |
| Flash Attention 1 (2022) | Tiling + Online Softmax，支持 FP16/BF16 |
| Flash Attention 2 (2023) | 更好的并行策略，更少的非矩阵乘法操作，速度提升 2 倍 |
| Flash Attention 3 (2024) | 针对 H100 GPU 优化，支持 FP8，异步处理 |

### 使用

```python

# scaled_dot_product_attention 自动使用 Flash Attention（如果可用）

# 或通过 flash-attn 库显式调用

```

1. 自动处理设备 placement
2. 自动处理分布式训练的进程启动
3. 自动处理梯度同步、混合精度等细节
4. 通过配置文件切换不同的分布式后端

### 代码对比

**改造前**（单 GPU PyTorch）：

```python
model = MyModel()
optimizer = Adam(model.parameters())
dataloader = DataLoader(dataset, batch_size=32)

model.to('cuda')
for batch in dataloader:
    inputs, labels = batch
    inputs, labels = inputs.to('cuda'), labels.to('cuda')
    
    optimizer.zero_grad()
    outputs = model(inputs)
    loss = loss_fn(outputs, labels)
    loss.backward()
    optimizer.step()
```

**改造后**（Accelerate）：

```python
from accelerate import Accelerator

accelerator = Accelerator()

)

for batch in dataloader:
    optimizer.zero_grad()
    outputs = model(batch['inputs'])
    loss = loss_fn(outputs, batch['labels'])
    accelerator.backward(loss)
    optimizer.step()
```

### 三、推理加速技术

### 3.1 KV Cache

### 什么是 KV Cache

在自回归（Autoregressive）生成中，每个新 Token 的生成需要用到所有之前 Token 的 Key 和 Value。如果每次都重新计算所有 Token 的 K 和 V，会有大量的重复计算。

**KV Cache** 的核心思想：将已计算过的 Key 和 Value 缓存起来，生成新 Token 时只需计算当前 Token 的 K 和 V，然后与缓存的 K/V 拼接即可。

![](https://pica.zhimg.com/v2-815b25ed6e041766624add9e5389de10_r.jpg)

### KV Cache 的存储分析

对于一个 L 层的 Transformer，每个 Token 的 KV Cache 大小：

```text
KV Cache 大小 = 2 × L × H × d_head × 2 bytes (FP16)
```

以 Llama 2 70B 为例（L=80, H=64, d_head=128）：

- 每个 Token：2 × 80 × 64 × 128 × 2 = 2.5 MB
- 4096 Token 序列：2.5 MB × 4096 = **10 GB**

对于大批量、长序列的推理场景，KV Cache 是显存的首要瓶颈。

### KV Cache 优化方向

1. **Multi-Query Attention (MQA)**：所有 Query Head 共享一组 K/V，将 KV Cache 缩小为原来的 1/H 倍。PaLM 使用。
2. **Grouped-Query Attention (GQA)**：将 Query Head 分组，每组共享一组 K/V。Llama 2 70B 将 64 个 head 分为 8 组，KV Cache 缩小 8 倍。
3. **Multi-head Latent Attention (MLA)**：DeepSeek-V2/V3 提出，将 K 和 V 压缩到低维潜在空间（latent space），大幅减小 KV Cache。DeepSeek-V2 的 KV Cache 仅为 MHA 的约 1/7。

![](https://pic1.zhimg.com/v2-1c5f71a14d1879e56bcc87e4eccea522_r.jpg)

### 使用方式

```python
# HuggingFace Transformers 默认启用 KV Cache
from transformers import AutoModelForCausalLM

model = AutoModelForCausalLM.from_pretrained("meta-llama/Llama-2-7b-hf")
# use_cache=True 为默认值，自动使用 KV Cache
outputs = model(input_ids, use_cache=True)
past_key_values = outputs.past_key_values

# 下一个 token 推理时传入缓存
outputs = model(next_token_id, past_key_values=past_key_values, use_cache=True)
```

### 3.2 Continuous Batching（连续批处理）

### 问题：Static Batching 的浪费

传统的静态批处理（Static Batching）方式：

1. 将多个请求组装成一个 batch
2. 等 batch 中**所有**请求都生成完毕后，才开始处理下一批

这样的问题是：

- 不同请求的生成长度不同（有的生成 50 个 Token，有的生成 500 个）
- 短请求完成后必须等待长请求完成 → GPU 空闲
- 新请求必须等待当前 batch 整体完成 → 延迟增加

![](https://picx.zhimg.com/v2-7788c39338f40e2eeaacc685a754e80f_r.jpg)

### Continuous Batching 原理

Continuous Batching（也称 In-flight Batching / Iteration-level Scheduling）在**每个迭代**都可以调整 batch 的组成：

1. **动态插入**：当有新的请求到达时，在下一个迭代立即插入 batch
2. **动态退出**：当某个请求生成完毕（EOS），在下一个迭代立即从 batch 中移除
3. **逐 Token 调度**：以单个 Token 生成（一个 forward pass）为调度粒度

```text
Iteration 1: [请求A, 请求B, 请求C]     → 各生成1个Token
Iteration 2: [请求A, 请求B, 请求C, 请求D]  → 请求D新加入；请求C生成EOS
Iteration 3: [请求A, 请求B, 请求D]        → 请求C已移除
Iteration 4: [请求A, 请求B, 请求D, 请求E]  → 请求E新加入
...
```

### 优势

- **吞吐量提升**：GPU 利用率更高，通常是 Static Batching 的 2-10 倍
- **延迟降低**：新请求不需要等待当前 batch 完成，延迟显著降低
- **显存利用更优**：batch 大小动态调整，显存利用更灵活

### 实现

Continuous Batching 是 vLLM、TensorRT-LLM、TGI (Text Generation Inference) 等推理框架的核心特性。

```python
# vLLM 示例（Continuous Batching 内置）
from vllm import LLM, SamplingParams

llm = LLM(model="meta-llama/Llama-2-7b-hf")
sampling_params = SamplingParams(temperature=0.8, max_tokens=256)

# 所有请求会自动被 Continuous Batching 调度
outputs = llm.generate(prompts, sampling_params)
```

- [vLLM 官方文档 - Scheduling](https://docs.vllm.ai/en/latest/design/arch_overview.html)

### 3.3 量化技术（Quantization）

量化是推理加速中最常用的技术之一，通过降低参数精度来减少显存占用和加速计算。

### 3.3.1 基础概念

**量化**将高精度浮点数（FP32/FP16/BF16）映射到低精度整数（INT8/INT4/INT2）：

```text
量化：W_int = round(W_float / scale) + zero_point
反量化：W_float ≈ (W_int - zero_point) × scale
```

![](https://pic4.zhimg.com/v2-92a772e6308ae875165707584ca0bd5d_r.jpg)

### 3.3.2 训练后量化（Post-Training Quantization, PTQ）

**GPTQ**（Frantar et al., 2023）：

- **核心思路**：基于 Optimal Brain Surgeon（OBS）二阶信息，逐列量化权重矩阵
- **特点**：一次性量化，不需要重新训练；需要少量校准数据（128 个样本即可）
- **精度**：INT4 下精度损失极小（4-bit 下困惑度仅增加 0.1-0.5）
- **速度**：在支持 INT4 Tensor Core 的 GPU 上，理论加速 4 倍

GPTQ 的算法流程：

```text
对权重矩阵 W 的每一列：
  1. 量化该列：Ŵq = quantize(Wq)
  2. 计算量化误差：Δw = (Wq - Ŵq)
  3. 用 Hessian 矩阵的逆修正未量化列：W[:,q+1:] -= H^(-1)[q,:] × (Δw / [H^(-1)]_qq)
```

**AWQ**（Lin et al., 2024）：

- **核心观察**：不同权重通道的重要性不同——只有约 1% 的显著通道对精度影响大
- **方法**：通过分析激活值的分布，找到显著权重通道，对其应用 per-channel scaling 保护
- **优势**：比 GPTQ 快 1.5-2 倍，精度相当或更好
- **论文**：[AWQ: Activation-aware Weight Quantization for LLM Compression and Acceleration](https://arxiv.org/abs/2306.00978)

**GGUF/GGML**：

- llama.cpp 项目使用的格式
- 支持 2-8 bit 量化
- 针对 CPU 推理优化
- 多种量化类型：Q4_0, Q4_K_M, Q5_K_M, Q8_0 等

### 3.3.3 量化感知训练（Quantization-Aware Training, QAT）

在训练过程中模拟量化效果，让模型适应低精度表示：

- 前向传播使用模拟量化权重
- 反向传播使用 STE（Straight-Through Estimator）近似梯度
- 精度通常优于 PTQ，但需要完整训练流程

### 3.3.4 BitsAndBytes

HuggingFace 生态中广泛使用的量化库：

```python
from transformers import AutoModelForCausalLM, BitsAndBytesConfig

# INT4 量化加载
bnb_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_compute_dtype=torch.bfloat16,
    bnb_4bit_use_double_quant=True,  # 双重量化，进一步节省显存
    bnb_4bit_quant_type="nf4",        # NormalFloat4，信息最优的 4-bit 格式
)

model = AutoModelForCausalLM.from_pretrained(
    "meta-llama/Llama-2-70b-hf",
    quantization_config=bnb_config,
    device_map="auto",
)
```

**双重量化（Double Quantization）**：对量化的 scale 参数再次量化，进一步节省约 0.4 bit/参数的显存。

**NF4（NormalFloat4）**：基于正态分布设计的 4-bit 数据类型，信息论最优，比标准 INT4 更适合模型权重。

### 3.3.5 FP8 量化

NVIDIA H100 引入的 FP8 格式（E4M3 和 E5M2），在训练和推理中两端兼顾：

- Transformer Engine 自动管理 FP8 计算
- 精度损失极小，接近 BF16
- TensorRT-LLM 支持 FP8 推理

### 量化技术对比

| 方法 | 精度 | 显存节省 | 推理加速 | 使用场景 |
| --- | --- | --- | --- | --- |
| FP16 | 基准 | 基准 | 基准 | 训练/推理 |
| INT8 (SmoothQuant) | 极小损失 | 2× | ~2× | 推理 |
| INT4 (GPTQ/AWQ) | 轻微损失 | 4× | 2-4× | 推理 |
| GGUF Q4_K_M | 可接受 | ~4.5× | CPU推理 | 端侧推理 |
| FP8 | 极小损失 | 2× | ~2× | H100 推理/训练 |
| NF4 (BitsAndBytes) | 轻微损失 | 4× | 速度取决于硬件 | 推理/QLoRA |

### 3.4 投机解码（Speculative Decoding）

### 问题

自回归生成的本质是**串行**的：每个 Token 的生成需要前一个 Token 的信息。这导致：

- 无法利用 GPU 的并行计算能力
- 延迟受限于显存带宽（memory-bandwidth bound）

### 核心思路

用一个小而快的**草稿模型（Draft Model）** 快速生成多个候选 Token，然后让大模型一次验证所有候选 Token。

![](https://pic1.zhimg.com/v2-26117094dd5db64fda232ff9025d4436_r.jpg)

### 算法流程

```text
1. Draft 阶段：
   Draft Model 自回归生成 K 个候选 Token（如 K=5）
   由于 Draft Model 很小（如 50M 参数），生成速度极快

2. Verify 阶段：
   大模型一次性计算这 K+1 个位置的前向传播
   （当前 Token + K 个候选 Token）
   逐位置比对 Draft Model 和大模型的概率分布

3. Accept/Reject：
   对于每个候选 Token：
     if random() < min(1, P_target(token) / P_draft(token)):
       接受该 Token
     else:
       拒绝该 Token，用修正分布 P_reject 采样一个新 Token
       停止后续所有候选 Token 的验证
```

### 关键性质

- **无损**：最终输出的概率分布与纯大模型采样完全一致（数学等价）
- **加速比**：取决于 Draft Model 与大模型的一致性。实践中一般采用 Draft Model 的 30-50% 接受率，配合 K=5-8，可获得 2-3 倍加速
- **Draft Model 选择**：通常使用同系列的较小模型（如 Llama 7B 为 70B 做 Draft），或 n-gram 模型

### 变体

**Medusa**（Cai et al., 2024）：

- 不依赖单独的 Draft Model
- 在大模型顶部添加多个”Medusa Head”（额外的分类头）
- 每个 Head 同时预测不同位置（如 Head 1 预测 t+1，Head 2 预测 t+2）
- 然后大模型一次验证所有预测
- [论文链接](https://arxiv.org/abs/2401.10774)

**Eagle**（Li et al., 2024）：

- 使用特征级别的 Draft，而非 Token 级别
- 推理速度比 Medusa 更快
- [论文链接](https://arxiv.org/abs/2401.15071)

### 使用

```python
# vLLM 中的 Speculative Decoding
from vllm import LLM

llm = LLM(
    model="meta-llama/Llama-2-70b-hf",
    speculative_model="meta-llama/Llama-2-7b-hf",  # Draft Model
    num_speculative_tokens=5,  # K
)
```

### 3.5 Flash Decoding

### 背景

Flash Attention 很好地解决了长序列场景下 Attention 的显存和速度问题，但 Flash Attention 主要针对**训练场景**优化：在训练时，所有序列长度相同（padding 后），GPU 各线程块的工作负载均衡。

而在推理场景中，不同请求的序列长度可能差异很大（特别是结合 Continuous Batching 时）：

- 请求 A 的 KV Cache 有 4096 个 Token，当前生成 1 个新 Token
- 请求 B 的 KV Cache 有 128 个 Token，当前生成 1 个新 Token

Flash Attention 按 batch 维度并行时，负责请求 A 的线程块需要处理 4096 个 Token，而请求 B 只需处理 128 个，导致严重的**负载不均衡**。

### Flash Decoding 的解决方案

Flash Decoding 将推理阶段的 Attention 并行策略从**按 batch 维度并行**改为**按 KV 序列长度维度并行**：

1. 将长 KV 序列切分为多个 chunk
2. 不同线程块并行计算 query 与各个 chunk 的注意力
3. 使用 online softmax 合并各个 chunk 的结果
4. 最后输出

![](https://pic3.zhimg.com/v2-c63275f324916d88f8fac0b765387752_r.jpg)

### 效果

- 对于长序列推理（如 32K 上下文），解码速度提升可达 8 倍
- 与 Continuous Batching 完美配合，解决了 batch 中序列长度不一的负载均衡问题

> **参考论文**：

- [Flash-Decoding for long-context inference (PyTorch Blog)](https://pytorch.org/blog/flash-decoding/)
- Dao et al., FlashAttention-2 论文中也涉及了推理场景的讨论

### 3.6 PagedAttention 与 vLLM

### KV Cache 的显存碎片问题

在 Continuous Batching 场景下，KV Cache 的动态分配和释放会导致严重的显存碎片：

- 请求 A 需要 2GB KV Cache 空间
- 请求 B 需要 512MB KV Cache 空间
- 请求 A 完成后释放 2GB，但新请求 C 需要 1.5GB
- 如果显存已被碎化，可能无法分配连续的 2GB

更糟糕的是，我们通常需要**预先分配最大长度**的 KV Cache（over-provisioning），造成大量浪费。

### PagedAttention 原理

PagedAttention（来自 vLLM 项目）借鉴了操作系统的**虚拟内存和分页机制**，将 KV Cache 切分为固定大小的”页（Page/Block）”：

![](https://pic4.zhimg.com/v2-18c03875aea2cf35030b4a3d27a6a599_r.jpg)

核心特性：

1. **分块存储**：将每个请求的 KV Cache 切分为固定大小的 Block（如每块 16 个 Token）
2. **动态映射**：通过 Block Table 将逻辑 Block 映射到物理 Block
3. **按需分配**：只在实际写入时分配 Block，不需要预先分配最大长度
4. **内存共享**：不同请求可以共享同一个物理 Block（如并行采样、Beam Search 时共享 Prompt 的 KV Cache）

```text
Block Table (逻辑到物理映射):
请求 A: [物理块 0] → [物理块 3] → [物理块 7] → ...
请求 B: [物理块 1] → [物理块 5] → ...
请求 C: [物理块 0] → [物理块 3] → ... (共享 Prompt 部分)
```

### 显存利用率对比

| 方案 | 显存浪费来源 | 有效利用率 |
| --- | --- | --- |
| 静态预分配 | 最大长度预留 + 内部碎片 | ~20-40% |
| PagedAttention | 仅 Block 内部碎片（最后一个 Block） | ~96%+ |

### vLLM

vLLM 是基于 PagedAttention 构建的高性能 LLM 推理引擎：

```python
# vLLM 离线推理

    model="meta-llama/Llama-2-70b-hf",
    tensor_parallel_size=4,         # 张量并行
    max_num_seqs=256,               # 最大并发请求数
    max_model_len=4096,             # 最大序列长度
)

    temperature=0.8,
    top_p=0.95,
    max_tokens=512,
)

```

vLLM 支持的功能：

- PagedAttention（高效 KV Cache 管理）
- Continuous Batching

- FP8 / INT8 / AWQ / GPTQ 量化

### 3.7 TensorRT-LLM

### 是什么

TensorRT-LLM 是 NVIDIA 官方推出的 LLM 推理优化框架，将 TensorRT 的图优化技术与 LLM 特有的优化技术结合。

### 核心优化

**1. 图优化（Graph Optimization）**

- **层融合（Layer Fusion）**：将多个连续算子融合为一个 kernel，减少 kernel launch 开销和显存访问

- **常量折叠**：预计算编译时常量

**2. In-flight Batching（TensorRT-LLM 的 Continuous Batching）**

- 与 vLLM 的 Continuous Batching 类似
- 额外提供了 `max_num_tokens` 参数，直接从 Token 维度控制 batch 大小

**3. 优化的 Attention Kernel**

- Flash Attention 集成
- Flash Decoding 集成
- 针对不同 GPU 架构的手工优化 kernel

**4. FP8/INT8/INT4 量化支持**

- 权重 INT4 + 激活 INT8（Weight-Only + SmoothQuant）
- FP8：利用 H100 的 Transformer Engine
- INT4 AWQ/GPTQ

**5. Multi-Node 推理**

- 支持跨节点的 Tensor Parallelism + Pipeline Parallelism
- 支持张量并行的 NCCL 通信优化

### 使用

```python
# TensorRT-LLM Python API
from tensorrt_llm import LLM, SamplingParams

llm = LLM(
    model="meta-llama/Llama-2-70b-hf",
    # TensorRT-LLM 需要先将模型编译为 TRT Engine
)

sampling_params = SamplingParams(
    temperature=0.8,
    max_tokens=512,
)

outputs = llm.generate(prompts, sampling_params)
```

### 3.8 前缀缓存（Prefix Caching）

### 应用场景

很多 LLM 应用场景中存在**共享前缀**：

- **System Prompt 共享**：所有请求共享同一个 System Prompt（几百到几千 Token）
- **Few-shot Prompt**：多个请求共享 Few-shot 示例
- **RAG 中的检索上下文**：多个相关请求可能共享部分检索结果
- **对话历史**：多轮对话中的历史消息

如果每个请求都独立计算共享部分的 KV Cache，会造成大量的重复计算。

### 原理

Prefix Caching 将 Prompt 的 KV Cache 按 Token 序列（或 Block）哈希后存储：

![](https://picx.zhimg.com/v2-f853f1a2e8213e0eb3d4dc3cbbdd78cd_r.jpg)

1. 计算 Prompt 的 Hash（或 Trie 结构存储）
2. 遇到相同前缀时，直接复用缓存的 KV Cache
3. 只需计算差异部分

### 实现方式

**基于 Radix Tree 或 Trie 的缓存**：

```text
Root
├─ "你是一个" (KV Cache: Block[0])
│  ├─ "AI助手" (KV Cache: Block[1])
│  └─ "擅长编程的" (KV Cache: Block[1'])
└─ "请帮我" (KV Cache: Block[0'])
```

**基于 Hash 的 Block 级缓存**：

- 将 Prompt 按 Block（如 16 Token）切分
- 每个 Block 的 KV Cache 以 (prefix_hash, block_index) 为 Key 存储
- 新请求到达时，逐 Block 检查是否有缓存命中

### 效果

- 对于长 System Prompt 场景，TTFT（首 Token 延迟）可减少 50-90%
- 因为跳过整个 Prompt 的 Prefill 阶段

### 框架支持

- vLLM：Automatic Prefix Caching（APC），内置支持
- TensorRT-LLM：支持
- SGLang：RadixAttention，基于 Radix Tree 的前缀缓存

> **参考论文**：

- Zheng et al., “SGLang: Efficient Execution of Structured Language Model Programs”, 2023. [arXiv:2312.07104](https://arxiv.org/abs/2312.07104) — RadixAttention
- Gim et al., “Prompt Cache: Modular Attention Reuse for Low-Latency Inference”, 2023. [arXiv:2311.04934](https://arxiv.org/abs/2311.04934)

### 3.9 模型蒸馏与剪枝

### 3.9.1 知识蒸馏（Knowledge Distillation）

通过让小模型（Student）学习大模型（Teacher）的输出分布，在不显著降低精度的前提下缩小模型规模：

**Logit-level 蒸馏**：

- 使用 Teacher 输出的完整 logits 分布（soft labels）训练 Student
- Loss: `KL(P_teacher || P_student)`

**Feature-level 蒸馏**：

- 让 Student 的中间层特征逼近 Teacher 的中间层特征
- 逐层对齐 hidden states、attention maps 等

**大模型蒸馏的实践**：

- GPT-3.5 蒸馏 → GPT-4 mini 系列
- Llama 3 70B → Llama 3 8B（Meta 使用了蒸馏技术）
- DeepSeek-R1 蒸馏到 Llama/Qwen 系列小模型

### 3.9.2 结构化剪枝（Structured Pruning）

移除整个神经元、Attention Head 或 Layer，保持模型的规则结构，可直接在 GPU 上加速：

**LLM-Pruner**（Ma et al., 2023）：

- 基于梯度信息评估每个结构（head、neuron、layer）的重要性
- 移除不重要的结构单元
- 通过 LoRA 微调恢复精度

**SliceGPT**（Ashkboos et al., 2024）：

- 通过正交变换将权重矩阵投影到低秩空间
- 剪除低重要性的维度
- 速度提升 20-30%，仅损失 1-2% 精度

**ShortGPT**（Men et al., 2024）：

- 基于 BI（Block Influence）指标评估层的重要性
- 发现许多大模型存在大量冗余层
- 移除 25% 的层后，部分模型的性能下降可忽略

### 蒸馏与剪枝的对比

| 方法 | 原理 | 加速比 | 精度损失 | 代表工作 |
| --- | --- | --- | --- | --- |
| 知识蒸馏 | 迁移学习，让小模型模仿大模型 | 取决于目标大小 | 较小 | DistilBERT, MiniLLM |
| 非结构化剪枝 | 剪除单个权重 | 稀疏化，需稀疏硬件 | 较小 | SparseGPT, Wanda |
| 结构化剪枝 | 剪除整个结构单元 | 1.2-2× | 中等 | LLM-Pruner, SliceGPT |
