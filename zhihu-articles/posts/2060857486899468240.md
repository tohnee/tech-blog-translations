随着训练数据源越来越丰富，数据质量越来越高，通用大模型的知识储备、指令理解和推理输出能力已经达到了一个恐怖的水平，过去垂域任务中那种 基座大模型+SFT微调 的 基操不一定有必要了，甚至可能对大模型有害。个人认为当下需使用微调的场景仅限以下两种： （1）小众冷门的垂域任务，冷门的垂域知识数据或者数据中有很多冷门词汇，例如金融、物流、电商等工业/行业大模型微调 （2）输出格式、排版或者风格有非常严格要求，比如要求输出某种复杂格式的json、输出文字为鲁迅写作风格等等

在直接使用通用大模型可能产生幻觉的情况下，SFT微调仍然是有必要的，微调完成后一定要对比 通用大模型（注意是instruct版本）和微调后大模型的水平，确保微调这一操作是有效的

### 大模型微调背景

Moemuu/Muice-Dataset 沐雪数据集是一个非常著名的开源中文微调数据集，该数据集约定微调后的大模型将具备特定二次元角色“沐雪”人格和对话风格。Qwen3.5:0.8B是千问团队推出的一款短小精悍的多模态“大模型”，并且具备thinking或non-thinking两种模式，因此常被部署于客户端上使用。本次微调的目标就是基于Muice数据集来微调Qwen3.5:0.8B模型，下面是本文的模型微调计划：

| 微调方式 | 硬件/环境 | 基座模型 | 数据集 | 微调框架 |
| --- | --- | --- | --- | --- |
| 本地 LoRA 微调 | 6G 显存 | Qwen3.5:0.8B | Muice-Dataset | Transformers (Peft) |
| 本地 QLoRA 微调 | 6G 显存 | Qwen3.5:0.8B | Muice-Dataset | Unsloth (Transformers + Peft) |
| 云服务器全量微调 | AutoDL | Qwen3.5:0.8B | Muice-Dataset | LLaMA-Factory |

### 大模型微调训练

参考项目： [Eksi123/Qwen-SFT-Zn](https://gitee.com/Eksi/qwen-sft-zn)

本次大模型微调将采用LoRA微调，QLoRA微调以及全量微调三种微调方式，并分别计算比较基座模型+微调后的三个模型在测试集上的Perplexity、BLEU、ROUGE指标表现，其中Perplexity困惑度计算的是大模型在序列生成过程中平均要从多少个候选词中随机挑一个，如果Perplexity=10，那么需要从10个候选词中任意选择其一作为预测词，Perplexity越低说明模型的文本生成过程越有把握；BLEU和ROUGE分别计算的是参考文本和生成文本在n-gram上的precision和recall值，其中BLEU考虑的是生成文本中包含了多少个参考文本的n-gram词汇，而ROUGE考虑的是参考文本中有多少个n-gram词汇在生成文本中出现过。下面是本次大模型微调项目的整体框架：

- model_data ====>> 数据集处理(如果直接使用开源数据集，可跳过此步骤)
- model_train_eval ====>> 模型训练和评估
- model_inference ====>> 模型推理
- dataset  ====>> 模型训练测试数据集
- log ====>> 模型微调日志
- images ====>> 项目图片
- requirements.txt ====>> 三方依赖库
- README.md ====>> 项目说明

此处不展示完整的微调训练脚本，只强调大模型微调训练中的一些关键点：

（1） **加载超参数配置** ，超参数主要分为LoRA超参数、训练超参数和优化器超参数，其中最关键的是训练超参数 learning rate和LoRA超参数 秩r

（2） **加载基座模型model和tokenizer** ，需要注意的是model和tokenizer是一一对应的，不可混淆其他模型来使用

（3） **加载并处理数据集** ，数据集需要被划分为训练集和验证集（用于看验证集的损失变化），数据在输入模型经tokenizer转化为token ID

（4） **模型配置超参数** ，使用data_collator处理批次训练数据时，记得加上padding=True做序列填充，以及return_tensors=“pt”用于转化为torch处理的张量数据

（5） **模型训练与保存** ，加载模型时确保device=“cuda”，否则模型训练会调用cpu变得极慢。Trainer会自动将训练数据加载到模型对应的设备上

### 大模型推理生成

参考项目： [Eksi123/Qwen-SFT-Zn](https://gitee.com/Eksi/qwen-sft-zn)

微调训练完成后的大模型便可用于本地调用或部署（linux系统推荐使用vLLM推理框架）。将模型推理生成的逻辑封装为支持多轮对话的类，其核心在于存储多轮对话的历史并将历史对话信息作为作为下一轮对话的prompt补充，下面简单展示了多轮对话的实现方法：

```python3
# 定义聊条助手
class Chatbot:
    def __init__(self):
        self.conversation_history = [] # 存储对话历史，格式为 [{"role": "user/assistant", "content": "消息内容"}, ...]

    def chat(self, user_input, enable_thinking=False):
        # 用户输入及input记录
        self.conversation_history.append({"role": "user", "content": user_input})
        messages = self.conversation_history
        text = tokenizer.apply_chat_template(
            messages,
            tokenize=False, # 是否对输入文本进行分词，默认为False
            add_generation_prompt=True, # 是否在输入文本后添加生成提示符，默认为False
            enable_thinking=enable_thinking # 是否启用思考提示，默认为False
        )
        input_ids = tokenizer(text, return_tensors="pt").input_ids.to(model.device)

        # 生成大模型回复(流式输出)
        streamer = TextStreamer(tokenizer, skip_prompt=True, skip_special_tokens=True)
        with torch.inference_mode():
            outputs = model.generate(
                input_ids,
                max_new_tokens=5000, # 生成的最大token数量，超过这个数量会停止生成
                temperature=0.7, # 大模型生成的随机程度，值越大越随机，值越小越确定
                top_p=0.8, # nucleus采样的参数，值越小生成的文本越集中在高概率的词上，值越大生成的文本越分散
                do_sample=True, # 是否使用采样生成文本，默认为False（即贪心解码）
                repetition_penalty=1.2,  # 重复惩罚，值越大越不容易重复
                streamer=streamer # 流式输出生成的文本
            )
        output_ids = outputs[0][input_ids.shape[1]:]

        # 解码回复及output记录
        response = tokenizer.decode(output_ids, skip_special_tokens=True).strip("\n")
        self.conversation_history.append({"role": "assistant", "content": response})
        
        return response

chatbot = Chatbot()

if __name__ == "__main__":
    epoch = 1
    print("欢迎使用大模型对话，输入 'exit' 或 'quit' 来结束对话。")
    while True:
        print(f"---------------- 第 {epoch} 轮对话 ---------------")  # 流式输出完成后换行
        user_input = input("User: ")
        if user_input in ["exit", "quit", "再见","拜拜","ByeBye","byebye","结束","结束对话","结束聊天"]:
            print("当前对话结束")
            break
        else:
            print("Bot: ", end="")
            response = chatbot.chat(user_input)
            epoch += 1
```

进一步还可将模型推理生成的逻辑封装为一个支持多用户多轮对话的公共接口，实现方式为将不同用户的对话用session id加以区分：

```python3
# 多用户的对话管理
class ChatSession:
    def __init__(self):
        self.sessions = {} # {session_id: Chatbot实例}

    def get_or_create_session(self, session_id):
        """获取或创建用户会话"""
        if session_id not in self.sessions:
            self.sessions[session_id] = Chatbot()
        return self.sessions[session_id]
chat_sessions = ChatSession()
```

需注意的是此时所有的用户及对话数据是临时存储在内存当中，因此在实际项目中往往需要将所有对话及日志数据在线存储于文件或数据库中
