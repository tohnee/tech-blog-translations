很多人看到"DeepSeek 开源推理引擎"会以为服务端那一整套都能下载了。读完 README 我改变了这个判断：放出来的是内核，不是服务。

先说清楚放出来的是什么。DeepInfer 的自我定位是支撑 DeepSeek 大规模生产服务的高性能推理框架，这次开源的部分只提供离线推理，支持的模型也只有 DeepSeek-V4.1-Flash。一句话，能跑，但只跑一个模型、一种模式。

真正有信息量的是它列出的能力清单。算子层有 FlashMLA、DeepGEMM、DeepEP、TileKernels、DeepSelect 和自研的 TileLang kernel；并行层写的是 Attention DP 与 balanced CP，MoE 走 EP 加 EPLB；调度上做了异步批处理、batch-invariant 推理和确定性采样，还能按正则、JSON schema 或 EBNF 约束输出。

这些名字看着散，其实指向同一件事：推理服务的性能不在模型里，在算子、并行和调度怎么拼。模型权重谁都能下，能把同样的卡跑出多少吞吐，才是区分厂商的地方。

![](https://pic1.zhimg.com/v2-32110cbef9b44136f36c3eb73b40cd80_1440w.jpg)

挑几个名字展开说。FlashMLA 和 DeepGEMM 是把注意力与矩阵乘的算子按自家模型结构重写，DeepEP 管的是专家并行时的通信，EPLB 则在专家负载不均时做重新平衡。专家并行最容易出的问题是热门专家被压垮、冷门专家闲着，EPLB 就是为这件事准备的。

调度层里我最在意 DSpark。它用草稿 token 加置信度来决定验证哪些候选，本质上是把投机解码的成本挪到"验证"这一步，让解码阶段多出一点并行度。配合默认开启的异步调度，CPU 排批和卡上执行可以重叠起来。

还有两个工程细节容易被忽略。SWA 有界回放只重放窗口末尾的一段，减少解码前的预填充工作量；batch-invariant 则保证不同批次组合下模型输出一致，确定性采样在此基础上再固定种子。前者省算力，后者保可复现，做评测的人会懂后者有多重要。

结构化输出这一条，做 agent 的人会更有感觉。把生成约束到正则、JSON schema 或 EBNF 语法，等于在解码阶段就把格式错误挡掉，而不是事后重试。工具调用要稳定的参数、批处理要固定的字段，靠的都是这类约束。

确定性采样听起来像学术需求，其实是评测的地基。没有它，同一个 prompt 跑两遍结果不同，你根本分不清是模型变了还是采样随机。DeepInfer 把这两件事做成开关，说明它考虑的不只是吞吐，还有能不能被拿来做事后复现、能不能让评测结果站得住。

![](https://pic4.zhimg.com/v2-1435bf06d61b058f82ff82c65428aab9_1440w.jpg)

然后是我认为最值得盯的一段。README 把完整服务所需的组件列成了一份待补清单：KV cache 系统、VE/Prefill/Decode 分离、数据并行之间的负载均衡，这三样都标注在本次发布之外。README 在同一处也注明，大部分所需的引擎功能其实已经实现，剩下的是把它拼成完整服务的那一层。

**开源的是发动机，没给的是变速箱和传动轴。**

这三样恰好是自建服务最难的部分。KV cache 决定长上下文能不能扛住并发，PD 分离决定预填充和解码能不能各自扩容，负载均衡决定多机多卡是不是真的线性。缺了它们，你自己拼出来的东西大概能跑 demo，撑不住流量。

硬件那两行也值得单独看。支持列表写的是 NVIDIA SM100 GPU 和华为昇腾 950 NPU。把国产卡和英伟达这一代的数据中心 GPU 并列写进同一个开源框架，这不是随手一提，是把硬件路线摊在桌面上。

还有一个不对称的地方：batch-invariant 和确定性采样都标注只在 NVIDIA 上可用。同一份代码，两套硬件，能力并不对等。开源降低了接入门槛，但没有抹平硬件差距。

在我看来，自建推理真正难的不是把模型跑起来，是并发上来之后还能稳住。单条请求能出结果，和一百条同时进来还能稳住，中间隔着的就是 KV cache 的调度、预填充与解码的拆分、以及多机之间的流量分配。这三件事不是没有现成方案。README 的致谢里写得很清楚，DeepInfer 最初主要构建在 vLLM 之上，也借鉴了 SGLang 和 TensorRT-LLM。但现成方案给的是起点，流量曲线、预算和硬件组合是你自己的，参数还得自己调。

DeepInfer 把上游最难的部分做完了，把下游最脏的部分留给了使用者。这个分工合理不合理，取决于你是谁：有推理团队的，省下算子调优的时间；没有的，反而会低估上线的复杂度。

![](https://pic3.zhimg.com/v2-7b6c75d8873c04b63c29f70a93cf092c_r.jpg)

开源圈里总有人争论这算不算"真开源"。我的看法是：纠结名分没意义，看它把哪一段交给了社区。算子、并行、调度交出来了，社区可以针对自己的硬件调优；KV cache 和 PD 分离留着，说明完整服务的护城河还在厂商手里。

另一种解释也成立：把内核开源是一种招人方式和生态投资。愿意为某个模型重写算子的人，本来就少；把代码摊开，等于把这类人筛出来。至于服务端的拼装件，那是客户付费的部分，没必要送。

两种解释不矛盾。开源从来不是慈善，是把自己的长板变成别人的默认选项。看 DeepSeek 这次放出来的东西，长板在算子与调度，短板在完整服务的交付。

**开源的边界不在代码行数，在完整服务还差哪几块。**

还有一点值得记下来：这次开源只覆盖离线推理。离线意味着没有实时流量、没有多租户隔离、没有按请求计费的调度压力，它更接近"批处理"而不是"线上服务"。README 自己把边界写清楚了，读的人不该替它补全。

对想自建推理的人来说，这份代码的用法很具体：拿它当一份可读的算子与调度参考，对照自己的瓶颈去改，而不是指望它直接变成一套能上线的东西。真要上线，KV cache 那一层还得自己写，或者接现成的方案。

对做模型的人，它还有另一层含义：当推理框架开始开源，模型之间的差距会更快地被服务效率拉平。谁的引擎能把同样的硬件榨出更多吞吐，谁的单位成本就更低，这条规律在模型能力趋同之后会更明显。

**权重决定你能不能用，推理引擎决定你用得起不起。**

判断值不值得投入，我会问三个问题。你的模型是不是就在支持列表里，不在就别碰。你的硬件是 SM100 还是昇腾，决定你能用到哪些特性。你有没有人愿意接手 KV cache 和 PD 分离这两块，没有就先别自建。

如果后面 DeepSeek 把 KV cache 和 PD 分离也放出来，这个故事才真正完整。在那之前，把它当成一份高质量的内核参考，是我能给的最实在的建议。

你所在的团队，现在是自建推理还是直接用接口？如果自建过，最卡的是 KV cache 的调度还是预填充与解码的拆分？
