## 01｜引言：为什么负载均衡做完了，系统还是会失衡？

假设我们部署了一个 Prefill-Decode Disaggregation（PD 分离）的 LLM Serving 系统。（好难猜啊，就叫它MoonCake吧）

系统包含一个 Prefill Instance 和三个 Decode Instances。当请求完成 Prefill 后，Scheduler 根据当前各个 Decode Instance 的负载，为请求选择一个相对空闲的实例。看起来，这是一个非常自然的负载均衡策略。

但问题是：**请求刚进入 Decode 时的负载，并不代表它未来的负载。**

假设有三个请求：

- Request A：最终生成 200 Tokens
- Request B：最终生成 2,000 Tokens
- Request C：最终生成 20,000 Tokens

在请求刚开始执行时，我们并不知道它们最终会生成多少 Token。

即使初始时三个 Decode Instance 的 KV Cache 占用完全一致，随着生成过程推进，它们的工作量也可能迅速分化。

Request A 很快结束。

Request B 运行一段时间后结束。

Request C 则可能持续占用计算资源，并不断扩展自己的 KV Cache。

更重要的是，新的请求还在持续进入系统。这就可能导致某些 Decode Instance 不断积累长请求，而其他实例却已经释放了大量资源。

论文 Figure 3 展示了这种现象：无论采用 Round-Robin 还是基于当前负载的分配策略，不同 Decode Instance 的执行延迟仍然会随着时间推移出现明显分化。

![](https://picx.zhimg.com/v2-adc5b3746b081783e88c6e5c1d4bd82d_1440w.jpg)

这种失衡最终可能带来两个问题。

**第一，KV Cache OOM。**随着长请求不断生成 Token，KV Cache 的内存占用持续增长。如果某个实例承载了过多长请求，就可能超过可用显存容量。

**第二，TPOT SLO Violation。**当某个 Decode Instance 的工作集不断增大，其每次 Decode Iteration 的执行时间可能增加，导致该实例上的请求无法满足 Time Per Output Token（TPOT）要求。

传统的 Prefill-to-Decode Scheduling 只能决定请求最初被分配到哪里。一旦请求进入 Decode，调度决策通常就相对固定了。

STAR 的研究问题由此产生：**能不能在请求已经开始 Decode 之后，根据未来工作量重新分配请求？**

这篇论文给出的答案是：可以。但要做好这件事，至少需要解决两个问题：

1. 如何知道一个正在生成的请求还会继续生成多少 Token？
2. 如何判断迁移哪个请求、迁移到哪里，以及迁移带来的收益是否值得支付 KV Cache 传输成本？

STAR 分别针对这两个问题提出了 LLM-native Length Predictor 和 Decode-Phase Rescheduler。

## 02｜Motivation：为什么传统调度策略不够？

### 2.1 Round-Robin 只均衡了请求数量

假设三个 Decode Instances 的请求数量如下：

```text
Decode 0：3 Requests
Decode 1：3 Requests
Decode 2：3 Requests
```

从请求数量来看，它们完全均衡。

但如果进一步观察每个请求的剩余生成长度：

```text
Decode 0：100 + 200 + 300 Tokens

Decode 1：1000 + 2000 + 3000 Tokens

Decode 2：5000 + 8000 + 12000 Tokens
```

显然，三个实例未来需要承担的工作量完全不同。

Round-Robin 不会考虑这些差异。

### 2.2 Current-Load Balancing 只观察当前状态

另一种常见策略是根据当前 KV Cache 占用分配请求。

例如：

```text
Decode 0：10 GB
Decode 1：12 GB
Decode 2：8 GB
```

Scheduler 将新请求分配到 Decode 2。

这种策略相比 Round-Robin 更合理，因为它考虑了当前内存负载。

但问题依然存在。假设 Decode 2 上有多个长输出请求，它们未来可能继续生成数万个 Token。即使现在 Decode 2 的负载最低，也不代表它在未来仍然是最合适的选择。

所以，STAR 的核心观察是：**仅仅根据当前负载进行调度，无法解决由生成长度不确定性引起的长期负载失衡。**

### 2.3 为什么不能简单地预测一次输出长度？

实际上，之前已经有一些工作尝试预测 LLM 的输出长度。

论文主要讨论了两类方法。

第一类是 Prompt-based Prediction。例如，在用户输入前添加指令：

```text
Output the length you expect to generate on the first line.
```

让 LLM 先输出自己预计会生成的 Token 数量。这种方法的问题是需要修改原始 Prompt，可能影响模型的输出行为，而且还会引入额外生成开销。

第二类是 Auxiliary Model Prediction。例如使用 BERT 或 OPT-125M 等辅助模型，根据输入内容预测输出长度。这种方法不需要修改用户 Prompt，但存在另一个问题：辅助模型对复杂长文本和推理任务的理解能力，可能明显弱于真正负责生成的目标 LLM。

更重要的是，这些方法往往只在请求开始时预测一次。而随着 Decode 不断进行，模型实际生成的内容会提供越来越多的信息。例如，模型最初可能只知道用户要求解决一道复杂数学题。但生成了数千个 Token 后，它已经形成了较为明确的推理路径。此时，继续使用最初的长度预测显然不够合理。

STAR 因此提出：**与其在 Prefill 后预测一次完整输出长度，不如利用目标 LLM 的内部状态，在 Decode 过程中持续预测剩余生成长度。**

## 03｜STAR 系统架构：从一次性调度到动态重调度

论文 Figure 5 给出了 STAR 的整体架构。

![](https://pica.zhimg.com/v2-cfe06491ab00dc7c1aaf0f2ecdd19660_r.jpg)

它仍然建立在 PD 分离系统之上，并没有改变 Prefill 和 Decode 的基本执行方式。

STAR 主要增加了两个组件。

**Length Predictor**用于预测每个活跃请求还需要生成多少 Token。

**Migration Scheduler**根据当前负载和预测负载，决定是否将某个请求从一个 Decode Instance 迁移到另一个 Decode Instance。

整体流程如下：

```text
                Incoming Requests
                        │
                        ▼
                 Prefill Instance
                        │
                 Prefill Complete
                        │
                        ▼
                 Decode Scheduler
                        │
           ┌────────────┼────────────┐
           ▼            ▼            ▼
        Decode 0     Decode 1     Decode 2
           │            │            │
       Predictor    Predictor    Predictor
           │            │            │
           └────────────┼────────────┘
                        │
                 Status Tracker
                        │
                 Future Load
                        │
                Migration Scheduler
                        │
             Select Request / Target
                        │
                  KV Transfer
                        │
                 Resume Decode
```

每个 Decode Instance 周期性地更新请求的剩余长度预测，并将自身状态报告给 Scheduler。Scheduler 根据这些状态判断是否需要迁移。

因此，STAR 不再把 Prefill-to-Decode 的初始分配视为不可改变的决策。相反，它允许系统随着请求的实际生成过程不断修正之前的调度结果。

下面重点分析这两个组件。

## 04｜LLM-native Predictor：如何利用 Hidden State 预测剩余长度？

这是 STAR 的第一个核心技术点。

### 4.1 为什么使用目标 LLM 自己的 Hidden State？

对于一个 Decoder-only Transformer，模型在每次 Decode 时都会计算当前 Token 对应的 Hidden State。

这些 Hidden State 包含模型对当前上下文的内部表示。

STAR 的作者认为，与重新运行一个独立的辅助模型相比，直接利用目标 LLM 已经计算出来的 Hidden State，可以降低预测开销，同时保留更多与生成过程相关的信息。

论文比较了三个设计维度。

**第一，KV Cache 还是 Hidden State？**

作者选择 Hidden State。原因是 KV Cache 主要用于 Attention 中的 Key/Value 表示，而当前 Token 的 Hidden State 已经融合了上下文信息，更适合作为预测器的输入。

**第二，所有 Transformer Layers 还是最后一层？**

作者选择最后一层。如果使用所有层的 Hidden State，预测器的输入维度和数据处理成本都会增加。最后一层 Hidden State 已经经过前面各层的计算，因此作者认为它能够在信息量和开销之间取得较好的平衡。

**第三，所有 Token 还是最后一个 Token？**

作者选择最后一个 Token。如果收集所有 Token 的 Hidden State，输入规模将随着上下文长度增长。而最后一个 Token 的 Hidden State 在 Decode 过程中本来就会被计算出来，因此能够以固定维度作为预测器输入。

最终，STAR 使用：**Last Transformer Layer + Last Token Hidden State**作为剩余生成长度预测器的输入。

### 4.2 预测器具体是什么结构？

作者并没有设计一个新的 Transformer。而是采用了一个轻量级的四层 MLP。对于论文使用的 DeepSeek-R1-Distill-Qwen-7B，Hidden State 维度为 3584。

MLP 的维度变化如下：

```text
Last Token Hidden State
          │
       3584 dim
          │
      Linear + ReLU
          │
       2048 dim
          │
      Linear + ReLU
          │
        512 dim
          │
      Linear + ReLU
          │
         64 dim
          │
        Linear
          │
          ▼
 Predicted Remaining Tokens
```

数学表达式为： $\hat y=W_4\phi(W_3\phi(W_2\phi(W_1h)))$

其中：

- (h) 是最后一层、最后一个 Token 的 Hidden State；
- ( $\phi$ ) 是 ReLU 激活函数；
- ( $\hat y$ )是预测的剩余生成长度。

**STAR 并不是直接从 Hidden State 中读取一个已经存在的“剩余长度”字段。**Hidden State 本身并没有显式存储模型还要生成多少 Token。作者使用监督学习，让 MLP 学习 Hidden State 与剩余生成长度之间的统计关系。

### 4.3 训练数据如何构建？

作者使用 DeepSeek-R1-Distill-Qwen-7B 在 ShareGPT 请求上运行推理。

在生成过程中，每隔固定数量的 Token，记录一次：

```text
Hidden State h_t
Ground Truth Remaining Length y_t
```

例如：

```text
某请求最终输出：10,000 Tokens

生成到 2,000 Tokens：
Label = 8,000

生成到 5,000 Tokens：
Label = 5,000

生成到 8,000 Tokens：
Label = 2,000
```

最终构建约 100,000 条训练样本。论文采用 70% / 15% / 15% 的训练、验证和测试划分，并且按照 Request 而不是单条 Hidden State 样本进行划分。

这样可以避免同一个请求不同 Decode 时刻的样本同时进入训练集和测试集，造成数据泄漏。

### 4.4 预测效果怎么样？

论文 Table 1 给出了不同方法的对比。

![](https://pic3.zhimg.com/v2-29a67f51be5cf6c584eae1a0e39c6b42_r.jpg)

相较于 TetriInfer，STAR 将 MAE 降低约 49.42%。同时，预测器参数量从 125M 降低到 8.4M。

但这里有一个值得关注的问题：**平均误差 3,873 Tokens，真的足够准确吗？**如果一个请求只剩余 500 Tokens，预测误差达到数千 Token，显然可能导致错误的迁移决策。所以，STAR 并没有把这个预测器当作能够精确确定终止位置的模型。它的用途是提供相对可靠的未来负载信息，帮助 Scheduler 区分长请求和短请求。

### 4.5 为什么要持续预测？

论文 Figure 7 给出了一个非常关键的实验。

![](https://picx.zhimg.com/v2-5f26793951ce8fd58f294ddc41d497bd_r.jpg)

对于实际生成 30K～32K Tokens 的长请求：在只有输入 Prompt 时，STAR Predictor 的 MAE 达到 18,256 Tokens。而在已经生成 8,000 Tokens 后，MAE 降低到 2,929 Tokens。

这说明随着生成过程推进，模型内部状态能够提供更有价值的剩余长度预测信息。因此，STAR 会在 Decode 过程中周期性地重新预测。

这里存在一个重要权衡：预测越频繁，理论上越能及时修正误差，但预测本身也会消耗计算资源。

论文在 RTX 4090D 上测得，预测 10 个请求约需要 1.40 ms，而其测试配置下的一次 Decode Iteration 约为 18.23 ms。

如果每一步 Decode 都运行预测器，就会产生不可忽略的额外开销。最终，作者在实验中采用每 20 次 Decode Iteration 更新一次预测的策略。

## 05｜Decode Rescheduling：到底应该迁移哪个请求？

这是 STAR 的第二个核心技术点，也是整个系统真正产生调度收益的地方。

有了剩余长度预测，我们还需要解决迁移决策。

### 5.1 为什么不能直接迁移最长的请求？

假设：

```text
Decode A：负载较高
Decode B：负载较低
```

Decode A 上存在两个请求：

```text
Request 1：
当前 KV Cache = 20,000 Tokens
预计剩余 = 100 Tokens

Request 2：
当前 KV Cache = 5,000 Tokens
预计剩余 = 15,000 Tokens
```

如果只根据当前 KV Cache 大小选择迁移对象，可能会选择 Request 1。

但它只剩下 100 Tokens 就结束了。迁移它需要传输已经积累的 KV Cache，而未来能够减少的负载却非常有限。

相反，Request 2 当前的 KV Cache 更小，迁移成本可能更低，但预计还会持续运行很长时间。因此，Request 2 可能是更合理的迁移对象。

这个例子说明：**迁移收益取决于未来能够减少多少负载，而迁移成本主要与需要转移的已有执行状态有关。**

这两个因素必须同时考虑。

### 5.2 如何统一表示计算负载和内存负载？

论文 Figure 8 发现，在所测试的 Decode 配置下：每次 Decode Iteration 的执行时间与 Batch 中累计 Token 数量呈近似线性关系。

![](https://picx.zhimg.com/v2-6f9f71de17004648aed0e7312069f425_r.jpg)

KV Cache 内存占用同样与累计 Token 数量呈线性关系。

因此，作者使用 Token Load 作为统一的负载指标。

对于 Decode Instance (i)，其当前负载定义为： $N_i=\sum_{r\in B_i}N(r)$

其中 ( $B_i$ ) 是该实例上正在执行的请求集合，(N(r)) 是请求当前已经占用的 Token 数量。这里的 (N(r)) 应理解为请求当前累计的 Token 工作集规模，而不是简单的 Batch 中有多少条请求。

这种建模的优点是简单。

它不需要分别建立复杂的计算时间模型和 KV Cache 内存模型。

但这也隐含了一个假设：不同实例具有可比较的执行性能，且 Token Load 与执行时间之间的关系足够稳定。如果实例使用不同 GPU、不同 KV Cache 精度或不同 Attention Kernel，这种近似可能不再可靠。

### 5.3 STAR 的优化目标是什么？

作者首先定义当前实例负载的方差： $\sigma_0^2=\operatorname{Var}({N_i})$

方差越大，说明不同 Decode Instances 的负载越不均衡。但仅优化当前负载仍然不够。

因此，STAR 进一步考虑未来时间窗口内的预测负载： $\sigma_0^{2} + \sum_{t=1}^{\infty} \beta_t \operatorname{Var}({\hat N_i(t)})$

其中：

- $(\hat N_i(t)) $ 表示未来时刻 (t) 的预测 Token Load；
- $(\beta_t) $ 是对应时间的权重；
- $(\hat{\sigma}^{2}) $ 是结合当前与未来状态的加权负载方差。

实际在线算法使用有限预测窗口进行计算。

STAR 希望选择能够最大程度降低这一负载方差的迁移操作。需要注意，这并不是直接最小化所有请求的完成时间，也不是直接最大化 Goodput。作者使用负载方差作为优化代理指标，希望通过改善实例之间的负载均衡，间接改善 TPOT 和 SLO 达标情况。

### 5.4 三阶段迁移算法

论文 Figure 9 和 Algorithm 1 给出了 STAR 的调度过程。

![](https://picx.zhimg.com/v2-bc7943c2f56d03f7281596cbc69d584b_r.jpg)

![](https://pic2.zhimg.com/v2-986a6b36ab8a2373201d031ef04f71ef_r.jpg)

**Phase 1：Instance Classification**

首先根据当前和预测负载，将 Decode Instances 分为 Overloaded 和 Underloaded 两类。

只有存在负载差异时，才需要进一步考虑迁移。

**Phase 2：Candidate Enumeration**

对于每一组 Overloaded-Underloaded Instance Pair，枚举可能迁移的请求。但并不是所有请求都允许迁移。STAR 主要检查两个约束：

一是预计剩余生成长度是否足以摊销迁移开销。

二是目标实例在接收请求后，未来是否仍然具有足够的 KV Cache 内存容量，避免产生 OOM。

**Phase 3：Best-Feasible Selection**

对于满足条件的候选请求，模拟迁移之后的负载变化。计算迁移前后当前及预测负载方差的差异。最后选择能够带来最大方差下降的可行迁移操作。

整个过程可以概括为：

```text
收集 Decode Instance 状态
             │
             ▼
    识别负载过高/过低实例
             │
             ▼
       枚举迁移候选
             │
             ▼
      检查迁移成本与 OOM
             │
             ▼
       模拟未来负载变化
             │
             ▼
       选择最佳可行迁移
             │
             ▼
          KV Transfer
             │
             ▼
       在目标实例恢复 Decode
```

这是一种周期性的在线启发式调度算法，而不是对整个未来请求序列进行全局最优求解。

### 5.5 调度算法本身会不会太慢？

如果系统有大量 Decode Instances，直接枚举所有实例对、所有请求，并重新计算未来负载，Scheduler 的开销可能很大。

论文给出的朴素实现复杂度为： $O(n+|O|\cdot|U|\cdot R_{\max}^{2}\cdot H)$

其中：

- (n)：Decode Instance 数量；
- (|O|)、(|U|)：过载和低载实例数量；
- $(R_{\max})$ ：单实例最大活跃请求数；
- (H)：预测时间窗口。

为降低开销，STAR 将部分未来负载计算下沉到 Worker。每个 Worker 预先计算本地未来负载摘要。Scheduler 在评估某个迁移候选时，只需要增量更新源实例和目标实例的负载信息。

优化后的复杂度为： $O(n+|O|\cdot|U|\cdot R_{\max}\cdot H)$

论文报告，在 256 个实例的模拟规模下，相关调度计算仍能控制在 300 ms 以内，并且可以与 Decode 计算重叠。

不过，300 ms 的调度计算时间与单次 Decode Iteration 的毫秒级时间尺度并不相同。因此，这种设计更适合周期性、较粗粒度的跨实例负载调整，而不是每个 Token 都执行一次全局重调度。

## 06｜实验：预测和重调度分别带来了多少收益？

论文使用 DeepSeek-R1-Distill-Qwen-7B 和长输出工作负载进行评估，并比较基于 vLLM 的 PD 分离方案与 STAR 的不同配置。

### 6.1 Goodput 的改善

首先需要区分 Throughput 和 Goodput。

Throughput 衡量单位时间完成的请求数量。

Goodput 则进一步考虑请求是否满足设定的 SLO。

因此，一个系统即使能够处理很多请求，如果大量请求的 TPOT 超过 SLO，其 Goodput 仍然可能较低。

在论文的大规模集群实验中，某个负载设置下：

| 策略 | Goodput |
| --- | --- |
| vLLM 基线 | 0.102 req/s |
| STAR 不使用预测 | 0.142 req/s |
| STAR 使用预测 | 0.157 req/s |

可以看到：仅仅引入 Decode Rescheduling，就能够将 Goodput 从 0.102 提升到 0.142 req/s，增幅约为 39.2%。

在此基础上加入剩余长度预测，Goodput 进一步提高约 10.6%。

这组消融结果说明 STAR 的收益并不是全部来自 Length Predictor。**动态迁移本身已经能够改善负载失衡，而预测主要用于进一步优化迁移决策。**

### 6.2 P99 TPOT 的改善

论文还给出了 ShareGPT 工作负载下的一组结果。在 RPS=0.17 的设置中：

| 策略 | P99 TPOT |
| --- | --- |
| vLLM 基线 | 96.3 ms |
| STAR 不使用预测 | 28.3 ms |
| STAR 使用预测 | 24.3 ms |

这一结果说明，在负载倾斜比较严重的情况下，Decode Rescheduling 可以显著降低尾延迟。

但从这组数据同样能够观察到：相比完全不进行 Decode Rescheduling，引入迁移机制带来的改善更大。而 Length Prediction 是在已经具备迁移能力的基础上，进一步提升决策质量。因此，在评价 STAR 时，应当把这两部分贡献区分开来。

### 6.3 为什么不是预测越频繁越好？

论文 Table 4 比较了不同预测间隔。

![](https://pic3.zhimg.com/v2-a62a73f1718ae29ca303901f5a4021d4_r.jpg)

可以看到，每 20 次迭代预测一次反而取得了最好的整体效果。

原因在于：

预测太频繁，会引入额外计算开销，也可能触发不必要的迁移。

预测太稀疏，又会导致 Scheduler 使用过时的负载信息。

因此，预测间隔本身也是一个需要优化的系统参数。

### 6.4 预测精度真的需要非常高吗？

论文 Table 3 还研究了预测粒度的影响。

![](https://pic1.zhimg.com/v2-dd5bc0232e25744084768caca959eb14_r.jpg)

作者将剩余长度预测从连续数值转换为不同数量的长度区间。

结果显示，预测粒度越粗，整体性能通常越差。

但一个值得注意的现象是：使用 6 个长度区间，已经能够保留相当一部分预测收益。这意味着对于 Decode Rescheduling 而言，Scheduler 可能并不需要知道一个请求精确剩余 13,247 Tokens。

它可能更需要知道：这个请求是即将完成、还需要中等长度生成，还是仍然具有很长的剩余生命周期。

换句话说：**调度所需要的预测精度，不一定等于生成长度预测任务本身所追求的最小 MAE。**

这为后续设计更轻量的预测器提供了启发。

## 07｜Discussion：STAR 还有哪些值得商榷的问题？

前面介绍了 STAR 的主要设计和实验结果。

但从 LLM Serving 系统研究的角度，我认为这篇论文仍然存在几个值得进一步讨论的地方。

### 7.1 最大的收益可能来自迁移，而不完全来自预测

从论文的消融实验可以看到：在某些负载设置下，仅使用 Decode Rescheduling 就能够显著改善 Goodput 和 P99 TPOT。加入预测后，性能继续提升，但增量收益相对较小。这并不意味着预测没有价值。

相反，预测能够让 Scheduler 提前识别未来负载差异，避免部分不必要的迁移。

但这也引出一个问题：如果使用更简单的预测方法，例如基于已生成长度、历史请求统计或者长度分桶的估计，是否已经能够取得接近 STAR 的调度收益？

论文的预测粒度实验提供了一部分证据，但尚不足以完整回答这个问题。

我认为后续可以进一步比较：复杂 MLP Predictor 与轻量统计预测器在不同工作负载下的收益差异。尤其需要关注的是最终 Goodput，而不只是预测 MAE。

### 7.2 Token Load 不一定能够准确代表所有 Decode 负载

STAR 将累计 Token 数量作为统一的负载指标。

在论文测试的执行环境中，这种方法具有实验依据。

但对于现代 LLM Serving，Decode 负载还可能受到其他因素影响。

例如：

- 不同请求可能具有不同的 Attention Window；
- Prefix Caching 会改变部分 KV Cache 的实际存储方式；
- KV Cache 可能采用不同的量化精度；
- Speculative Decoding 会改变每次迭代处理和接受的 Token 数量；
- 不同 GPU 和不同 Kernel 的计算效率可能存在明显差异。

特别是对于 Sliding Window Attention，实际参与 Attention 的历史 KV 长度不一定随着完整上下文长度持续线性增长。

因此，单纯使用 Token Load 作为执行时间和内存占用的统一代理指标，可能无法准确适配所有模型架构。

如果希望将 STAR 扩展到更加异构的 Serving 环境，可能需要引入更加精细的性能模型。

### 7.3 KV Cache 迁移成本不能只看数据大小

STAR 通过迁移成本约束避免收益不足的迁移。

但实际迁移可能涉及：

源实例的 KV Cache 读取、网络传输、目标实例的显存分配、KV Cache 写入，以及请求执行状态的恢复。

这些过程还可能与正在运行的 Decode 请求争用网络、PCIe、显存带宽和计算资源。

因此，迁移成本不只是： $T_{\mathrm{migration}} \approx \frac{\text{KV Cache Size}}{\text{Network Bandwidth}}$

还可能包含额外的固定开销、同步开销和资源争用。

尤其在高负载环境下，网络的可用带宽可能明显低于标称带宽。

所以，STAR 的迁移策略如果部署到真实的大规模集群中，还需要考虑迁移操作对其他正在服务的请求造成的间接影响。

### 7.4 为什么不采用更加直接的 SLO-aware 调度目标？

STAR 的核心优化目标是降低 Decode Instances 之间的 Token Load Variance。

但用户真正关心的是请求的 TPOT、完成时间以及 SLO 是否满足要求。

这两者并不完全等价。

例如，某次迁移可能显著降低实例间的负载方差，却让目标实例中原本接近 SLO 阈值的请求出现延迟增加。

反过来，一次无法显著降低全局方差的迁移，也可能挽救某个即将违反 SLO 的关键请求。

因此，我认为后续可以考虑将负载均衡与 SLO Risk 结合。

例如，为每个请求估计未来的 SLO Violation Probability，再根据迁移操作能够减少的违约风险进行决策。

当然，这会引入更复杂的性能预测问题，调度成本也可能随之增加。

### 7.5 连续预测能否适应不同模型和不同采样策略？

STAR 的 Predictor 依赖目标 LLM 的 Hidden State。

这意味着它与具体模型之间存在一定耦合。

当模型发生变化时，例如从 DeepSeek-R1-Distill-Qwen-7B 切换到其他模型，Hidden State 的维度、分布以及与剩余生成长度之间的关系都可能改变。

此外，即使使用同一个模型，不同 Temperature、Top-p、最大输出长度或 Stop Condition，也可能改变最终生成长度的分布。

因此，预测器是否需要重新训练，以及跨模型、跨采样策略的泛化能力如何，是实际部署中需要重点关注的问题。

这里还有一个更深层的问题：

剩余生成长度本身并不是确定性的。

在非确定性采样条件下，相同的 Prompt 和相近的 Hidden State 也可能对应不同的最终输出长度。

因此，与其只输出一个点估计值，未来是否可以预测剩余长度的分布或置信区间？

例如： $P(L_{\mathrm{remain}}>L_{\mathrm{threshold}})$

这样的概率信息可能比单一预测值更适合用于判断迁移风险。

### 7.6 大规模调度的可扩展性仍需要真实系统验证

论文通过模拟实验验证了 STAR 在最多 256 个实例下的调度效果。

但模拟规模扩大，并不等于完整证明真实集群中的可扩展性。

真实系统还需要考虑状态上报延迟、Scheduler 的状态一致性、迁移失败恢复、网络拥塞以及多次迁移之间的相互影响。

特别是当 Scheduler 使用预测负载进行决策时，预测误差与状态更新延迟可能叠加。

例如，一个请求在 Scheduler 做出迁移决策时仍然预计剩余数千 Token，但在迁移真正开始之前已经接近结束。

这类状态陈旧问题可能导致无效迁移。

因此，如何设计低开销、低抖动且具有足够一致性的分布式调度控制平面，是 STAR 进一步工程化时的重要挑战。

### 7.7 Decode Rescheduling 与 Prefill-to-Decode Scheduling 的协同缺失

我认为 STAR 最值得进一步讨论的问题，并不是剩余生成长度预测器是否足够准确，而是其调度优化仍然主要局限于 Decode 阶段。

在 PD 分离架构中，请求的调度实际上包含两个相互关联的过程：

第一，在 Prefill 完成后，将新请求分配到某个 Decode Instance。

第二，在 Decode 执行过程中，根据实例负载变化，决定是否迁移已有请求。

STAR 重点解决了第二个问题。但这两个调度过程并不是相互独立的。

例如，Decode Rescheduler 可能已经根据未来负载预测，计划将一个长请求从 Decode 0 迁移到 Decode 1。

如果 Prefill-to-Decode Scheduler 没有获得这次迁移的决策信息，仍然依据当前负载为新请求选择 Decode Instance，那么新的请求分配就可能抵消原本的迁移收益。

反过来，如果 Decode Rescheduler 不知道上游已经规划了哪些新请求的分配，也可能在迁移完成后造成新的负载倾斜。

这说明，**单独优化 Decode 阶段的负载均衡，并不一定等价于优化整个 PD 分离系统的全局负载分布。**

更值得研究的方向，是将 STAR 已经获得的剩余生成长度预测、未来负载估计以及待执行迁移信息，进一步反馈给 Prefill-to-Decode Scheduler。

同时，让 Decode Rescheduler 感知上游已经做出的请求分配决策。

由此构建一个共享未来负载视图的联合调度框架：**Joint Prefill-to-Decode Scheduling and Decode-Phase Rescheduling。**

这样，系统就不再需要先通过初始调度分配请求，再依赖后续迁移被动修正负载失衡，而是能够在请求进入 Decode 之前，就尽可能避免未来的负载倾斜。

这可能比单纯继续降低 Length Prediction MAE 更具有系统层面的研究价值。

## 08｜总结：LLM Serving 调度不能只看现在

STAR 的核心贡献可以概括为两点。

第一，利用目标 LLM 自身的 Hidden State，通过轻量 MLP 持续预测请求的剩余生成长度。

第二，在 Decode 阶段引入动态迁移机制，综合当前和预测负载，选择能够改善实例间负载均衡的迁移操作。

它解决的不是单个 Kernel 的计算效率问题，而是更高层次的跨实例资源调度问题。

我认为这篇论文最值得关注的思想是：

**在长输出 LLM Serving 中，负载不是静态属性，而是随着生成过程不断变化的动态状态。**

传统 Scheduler 通常根据当前资源占用决定请求应该被放在哪里。

而 STAR 尝试让 Scheduler 不仅理解当前系统状态，还能够利用模型内部信息预测请求未来的执行需求。

这使调度从 Reactive Load Balancing 向 Predictive Load Balancing 迈进了一步。

不过，STAR 也留下了值得继续研究的问题：

预测需要多准确，才能真正改善调度？

迁移成本应该如何在动态资源竞争下建模？

负载方差是否是最合适的优化目标？

以及，能否将请求级未来负载预测与更加细粒度的 SLO-aware Scheduling 结合？

这些问题都值得继续探索。

对于 AI Infra 而言，STAR 提供的启发不仅是“Decode 请求可以迁移”，而是：

**模型推理过程中产生的内部信息，也可以成为系统调度决策的重要依据。**
