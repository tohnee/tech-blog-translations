## 1 如何使用物理显存

大模型推理计算过程中，通常采用KV cache策略来减少Attention模块的重复计算。不同的Attention范式，对应的KV cache存储格式存在差异：常见的MHA(Multi-Head Attention)模块会保存Key值和Value值；MLA(Multi-Head Latent Attention)模块保存K_pe值和C值(压缩的KV)；而线性注意力(Linear Attention)模块一般保存S(SSM)值和Conv值。

![](https://pic2.zhimg.com/v2-4e914b27d79dfbf0d91139ee795cc44b_r.jpg)
*MHA和MLA的KV cache对比*

为了降低讨论的复杂度，本文以MHA为例展开分析。MHA作为标准的Attention模块，其KV cache的大小与序列的长度正相关。在大模型中，序列由一连串的tokens构成，因此要掌握序列的显存占用情况，本质上就是了解tokens对显存的线性占用规律。

### **1.1 单个token需要多少显存？**

从LLM的输入数据结构组成可知，单个token的尺寸通常表示为[1, heads, heads_dim]，其中heads代表attention的头数，head_dim表示头维度，则单个token对应的数据量为：heads * heads_dim。此外，由于K和V均需存储一份数据，因此计算方式为：

one_token_data_size = 2 x heads * heads_dim * type_size

其中，type_size代表数据类型对应的字节大小，例如float32类型的大小为4 Byte，bfloat16类型的大小为2Byte。进一步而言，若要计算多个tokens的存储空间，只需在上述基础上再乘以tokens的数量即可。

![](https://picx.zhimg.com/v2-b50e4daabb375b4042630d0e13388061_r.jpg)

上述计算仅考虑了模型单层的情况，若模型各层采用相同的结构，只需在上述计算结果的系数前再乘以模型的层数即可。

![](https://pica.zhimg.com/v2-db063042b99c9380c49cc84c20b3016c_r.jpg)

在SGLang的显存使用逻辑中，存在一个关键变量：**page**。page作为tokens的管理单位，决定了显存使用的管控细粒度，其默认配置page_size=1。

值得注意的是，从直觉上看，较小的page_size会导致HBM数据离散，降低数据读写效率，进而影响整体运行速度。但实际测试发现，page_size=1几乎不会对attention算子在GPU中的计算效率产生影响，具体参考FIA报告[^2]。

![](https://pic2.zhimg.com/v2-7216b882f77f15f12442e2c6f9a4d0a1_r.jpg)

在单GPU上，MHA Attention的page大小、数量计算的代码如下：

```python
def get_mha_cache_per_page(head_dim, num_kv_heads,  num_layers, page_size=1, tp_size=1, dtype_size=2):
        """
        :param head_dim: dim大小
        :param num_kv_heads: 头数
        :param num_layers: 模型层数
        :param page_size: 页大小，默认1
        :param tp_size: 并行策略的TP大小， 默认1为没有TP切分
        :param dtype_size: 数据大小，torch.float32 4字节，torch.float16/torch.bfloat16: 2字节
        :return:
        """
        size = 2 * num_kv_heads * head_dim * num_layers * page_size / tp_size * dtype_size
        return size

def get_num_pages_for_kv_cache(available_memory, cache_per_page):
        num_pages = int(available_memory // cache_per_page)
        kv_size = num_pages * cache_per_page / (1024**3)
        print(f"Allocating {num_pages} pages for KV cache, K + V = {kv_size:.3f}GB")
        return num_pages

```

page大小的计算中涉及TP(Tensor Parallel)参数。这是因为在MHA中，当开启张量并行(tp > 1)后，KV cache会以分布式方式存储，因此需要在page的计算中纳入这一因素。(TP概念理解参考[LLM推理并行优化的必备知识](https://zhuanlan.zhihu.com/p/1937449564509545940))

### **1.2 物理显存如何排布？**

推理框架构建KV cache物理层时，遵循“仅申请一次”的原则，即在框架完成初始化后，从GPU中预先占用多块连续的物理内存。因此，尽管SGLang使用的是pytorch tensor作为KV cache的存储载体，但在框架层视角来看，KV cache申请的物理显存是连续的（vLLM框架d的情况类似[^3]）。

在KV cache的布局上，K值和V值既可以分开放置，也可以混合存储。在实际实现中，一般采用分开放置的方式。

![](https://pic3.zhimg.com/v2-28a9802424bd1e153349bd7201579f28_r.jpg)

由于申请的显存块连续，且块的大小一致。默认遵循以下规则：

1. 同一个token的K值和V值具有相同的索引位置；
2. 同一个token在不同层上的K值或V值，对应的索引也保持一致。

因此，在各层结构相同的情况下，**单个token只需一个地址索引即可定位到所有相关数据。**

### 1.3 单个请求的Attention计算

通过前面分析可知，显存是连续申请的，每个token都可以通过一个索引来定位其对应的数据，这个索引值被称为slot。

![](https://pic3.zhimg.com/v2-8809024a0596cbefac67e18edd22ff6c_r.jpg)
*连续的显存地址*

单个请求要完成Attention计算，还需解决核心问题：**如何管理每个请求对应的tokens数据？**在SGLang中，这一问题通过页表(page table)的方式解决，页表中记录了每个请求所对应tokens的slots数据。

下图列举了两个请求对应的索引页表示例，其中每个请求均分配有固定的slots：

![](https://picx.zhimg.com/v2-8f59236e421a65e6c41b07c4ff0cace5_r.jpg)

page table通过二维数组定义。

```python
def create_page_table(max_running_req, max_seq_len):
        page_table = torch.zeros((max_running_req, max_seq_len), dtype=torch.int32)
        return page_table
```

其中：max_running_req表示SGLang单次最多跑多少请求；max_seq_len表示单个请求最大的序列长度。

有了显存的物理地址和映射表，Attention在计算时就能正确读取到每个请求对应的KV cache显存数据。

## 2 理解关键的碎片问题

在了解物理显存应如何使用之后，我们分配一定数量的slots给Attention算子，计算就能够正常进行，但如何让slots使用效率更高？

首先来看一个问题：单个请求应该分配多少slots才合适？

一种简单且直观的解决方式是采用固定分配策略。如果slots设置得太小，由于推理生成长度是未知的，一旦超出固定值就需要重新分配地址；如果slots设置得太大，则会造成大量显存闲置。举个例子，如下所示，单个请求固定分配7个slots，请求0有3个slots空闲，请求1有4个slots空闲。

![](https://pic4.zhimg.com/v2-c7906a9061df76fd3bff9761a988329b_r.jpg)
*蓝色代表已使用的显存，灰色表示未使用的显存。*

再来分析存在前缀(prefix)复用的场景。在上述示例的基础上，若请求1（req_1）释放显存后，新接入一个请求2（req_2），且req_2可复用req_1前3个slots的值，则会生成显存碎片：[10,11, 12,13]。

![](https://pic4.zhimg.com/v2-3434ed252c21b3e5e3fe73b28084d253_r.jpg)

碎片问题是内存管理中常见的难题。其中一种消除碎片的方式是采用**细粒度分配**：在显存使用时，以单个slot为单位，为每个请求动态分配所需的slots。并且，当不同请求的前缀相同时，可以共享相同内容的物理存储空间。

举个例子，如下图所示，LLM在不同时刻接收到两个请求，请求的字符串首先会经过编码，得到对应的token ids。

![](https://pic2.zhimg.com/v2-2fbeff9ae23a4a81e97a3e4db686b941_r.jpg)

在处理KV cache时，若采用固定长度分配（下图方式1），则两个请求共占用14个slots（其中2个为预留）。由于这两个请求有4个tokens相同，若采用细粒度分配（下图方式2），则两个请求总共只需占用8个slots。

![](https://picx.zhimg.com/v2-728db5caf197f78c0ff58caa04f6245f_r.jpg)

通过上述分析，我们可以直观地看到细粒度分配的优势。

## 3 RadixTree数据结构的搭建

### 3.1 原理分析

在SGLang中，正是通过RadixTree（基数树）数据结构来实现这一细粒度分配的管理逻辑。RadixTree是一种高效的字符串存储结构，相较于标准前缀树(Trie/Prefix Tree)，它的节点数量更少。

当插入带有相同前缀的内容时RadixTree的插入操作会触发节点分裂(split) 机制。以下是两种数据结构执行新数据插入操作的示例：

![](https://pica.zhimg.com/v2-b9da5cd1d84a6de90d2998ff186d38c4_r.jpg)
*原有数据“kaiyuan”基础上插入“kaixin”*

RadixTree在执行节点删除操作时，若其父节点仅包含一个子节点，还会触发节点合并(merge)机制。

![](https://picx.zhimg.com/v2-3874e866e4d1477df1f5b3390eb2828f_r.jpg)

在SGLang的介绍论文[^4]中，给出了RadixAttention的示例（如下图），其管理逻辑与RadixTree保持一致。但它也有一些特殊之处：

1. 节点的删除/淘汰(evict)操作采用LRU(Least Recently Used，最近最少使用)策略；
2. 当节点正在被使用时，该节点不会被删除。

![](https://pic4.zhimg.com/v2-e512127556240efcca5f54b18c47e165_r.jpg)

为了实现RadixAttention的KV cache数据的管理，需要在节点内部定义以下基本参数：

- uuid：节点的唯一标识
- tokens：当前节点的数据（类似radix tree的字符串）
- slots：对应的tokens所在的物理空间位置

我们继续沿用前面的例子来进一步说明：如下图所示，两个请求的table信息依次存入了RadixTree中。

![](https://pic2.zhimg.com/v2-1cb800f45e7e07507654aa23ff4737b9_r.jpg)

为实现RadixAttention的数据淘汰逻辑，还要引入两个参数：

- timestamp：节点的操作时间。用于LRU策略。
- ref_count：节点被引用的次数。指该节点被其他请求作为前缀使用的次数

再结合RadixTree的其他基本参数来看，一个node包含的核心数据如下：

```python
children: Dict[int, RadixTreeNode] = {}
parent: RadixTreeNode | None = None
ref_count: int = 0
uuid = RadixTreeNode.counter
timestamp = tic or time.monotonic_ns()
tokens: torch.Tensor
slots: torch.Tensor
```

### 3.2 基本功能探索

在数据结构层面，我们在前面分析的基础上，新增用于查询和计数的参数；在数据操作层面，核心实现节点**数据匹配**与**节点分裂**功能（暂不考虑合并功能），同时实现RadixTree的增加、删除、查询功能。

**3.2.1 数据结构定义**

```python
class RadixTreeNode:
    counter: int = 0
    def __init__(self, tic: int | None = None) -> None:
        self.children: Dict[int, RadixTreeNode] = {}
        self._parent: RadixTreeNode | None = None
        self.ref_count: int = 0
        self.uuid = RadixTreeNode.counter
        RadixTreeNode.counter += 1
        self.timestamp = tic or time.monotonic_ns()
        self._token_ids: torch.Tensor
        self._slots: torch.Tensor
        self._length: int
```

**3.2.2 节点基本操作定义**

**匹配函数**：比较两个节点的token_ids是否相等。

```python
def find_first_diff_pos(tensor1: torch.Tensor, tensor2: torch.Tensor) -> int:
    """
    比较两个一维PyTorch tensor的值，返回第一个不同值的位置
    Returns:
        int: 第一个不同值的索引位置。如果完全相同返回-1
    """
    if tensor1.dim() != 1 or tensor2.dim() != 1:
        raise ValueError("两个tensor都必须是一维的")

    len1, len2 = len(tensor1), len(tensor2)

    # 遍历两个tensor直到较短的那个结束
    for i in range(min(len1, len2)):
        if tensor1[i] != tensor2[i]:
            return i

    return min(len1, len2)
```

**节点分裂函数**：将节点分裂成两个节点。其定义在node类的内部。

```python
    def _split_at(self, pos: int) -> RadixTreeNode:
        assert 0 < pos < self.length
        parent = self.parent

        new_node = RadixTreeNode(self.timestamp)
        new_node.set_ids_slots(self._token_ids[:pos], self._slots[:pos])
        new_node.set_parent(parent)
        new_node.ref_count = self.ref_count

        self.set_ids_slots(self._token_ids[pos:], self._slots[pos:])
        self.set_parent(new_node)
        return new_node
```

**节点比较函数**：用于比较两个节点的时间戳的大小。

```python
    def __lt__(self, other: RadixTreeNode) -> bool:
        return self.timestamp < other.timestamp
```

完整的RadixTreeNode定义参考[sglang_radix_attention.ipynb](https://github.com/CalvinXKY/InfraTech/blob/main/llm_infer/sglang_radix_attention.ipynb) 2.1。

**3.2.3 walk函数定义**

walk函数的作用是查找并匹配前缀：若存在相同前缀，则触发节点分裂操作，最终返回匹配到的前缀节点。

```python
def walk(input_ids: torch.Tensor) -> Tuple[RadixTreeNode, int]:
    """
    返回值 node：匹配到的前缀node。
        prefix_len: 匹配长度
    """
    node = root_node
    prefix_len = 0
    indice_len = len(input_ids)
    while prefix_len < indice_len:
        this_id = int(req_1_ids[prefix_len].item())
        if this_id not in node.children:
            return node, prefix_len

        node = node.children[this_id]
        match_len = node.get_match_len(input_ids[prefix_len:])
        prefix_len += match_len
   
        if match_len != node.length:
            node = node._split_at(match_len)
            return node, prefix_len
    return node, prefix_len
```

**3.2.4 引用计数与cache_handle**

当node被引用时，需将其引用计数加1；当某个请求不再引用该node时，需将引用计数减1。

```python
# 代码逻辑示例：
# 前缀node被引用了，增加父节点的引用计数。
node = cache_handle
while not node.is_root():
    node.ref_count += 1
    node = node.parent

# 请求被释放时，同时清除该请求产生的引用计数：
node = cache_handle
while not node.is_root():
    node.ref_count -= 1
    node = node.parent
```

代码中定义了一个cache_handle参数，其作用是记录每个请求所引用的node，该参数被纳入Request请求体的数据结构中。

**3.2.5 数据淘汰逻辑**

在新请求申请KV cache过程中，当空闲slots不足时，会从Radix Tree中释放空闲空间。释放的逻辑：

- 通过循环的方式逐步清理空闲的叶子节点，直至释放出所需的存储空间后停止；
- 空闲叶子节点的淘汰顺序，按照节点的最近使用时间从早到晚排序（即遵循 LRU 策略）。

```python
# 代码逻辑示例：
# 设定一个target需求：
target_size = 3

nodes = [root_node]
leave_nodes = []

while len(nodes) > 0:
    node = nodes.pop()
    if node.is_leaf():
        if node.ref_count == 0:
            leave_nodes.append(node)
    else:
        for child in node.children.values():
            nodes.append(child)

leave_nodes
heapq.heapify(leave_nodes)
evicted_indices = []
evicted_size = 0

# 删除空闲叶子结点，直到满足target_size
while evicted_size < target_size:
    assert (
        leave_nodes
    ), f"Cannot evict enough cache, need {target_size}, only {evicted_size} evicted"
    node = heapq.heappop(leave_nodes)
    assert node.ref_count == 0 and node.is_leaf() and not node.is_root()
    evicted_size += node.length
    evicted_indices.append(node.slots)
    parent = node.parent
    del parent.children[int(node._token_ids[0].item())]
    print_radix_tree(root_node)
    if parent.is_leaf() and parent.ref_count == 0:
        heapq.heappush(leave_nodes, parent)
```

代码中引入了heapq模块来对元素进行排序，由于堆结构的特性，堆顶元素始终为优先级最小的元素（即最近最少使用的节点），以此实现了LRU策略的逻辑。

new_node.set_parent(cache_handle) # 放入树中

## 4 KV cache管理实现

### 4.1 类定义

在第 3 节中，我们已完成RadixTree核心基础操作的实现；本节将聚焦具体函数的落地实现，并通过类的形式来封装承载所有相关功能。

**对外接口类CacheManager**：在数据层面，统计空闲物理slots数量；在功能层面，核心实现KV cache的申请、释放、引用计数处理功能；

CacheManager的关键函数：

- allocate：为请求申请slots，当空闲slots不足时，触发evict操作。
- match_req：为请求匹配前缀，并返回匹配的前缀长度、以及所在节点。
- lock/unlock：请求在使用/释放前缀时，需要操作对应节点的引用计数，该过程借助cache句柄来实现。
- free_and_cache_finished_req：当请求在计算结束后调用该函数，会将请求的数据插入RadixTree中，并释放对应前缀计数。

CacheManager的主要操作依赖RadixCacheManager。

**RadixCacheManager类**：在数据层面，核心维护一棵RadixTree，并统计该RadixTree中可被淘汰的数据量、已被保护的数据量（计量单位均为 slot 个数）；在函数层面，实现第3节中提及的查找、插入、删除核心操作。其中BaseCacheManager作为抽象基类，仅在该类中定义相关操作的接口规范。

**RadixCacheHandle数据类**：该类用于记录每个请求所使用的、来自RadixTree中前缀缓存的节点。在lock和unlock操作中，会通过CacheHandle对象对对应节点的引用计数执行加1或减1操作

![](https://picx.zhimg.com/v2-f21b15cf4709de9c99d27f92379d3145_r.jpg)
*UML类图*

RadixCacheManager的实现代码如下，其中部分函数的细节逻辑已在第3节中做过演示，因此本节不再展开赘述。

```python
class RadixCacheManager(BaseCacheManager):
    def __init__(self, device: torch.device):
        self.device = device
        self.empty_tensor = torch.empty(0, dtype=torch.int32, device=device)
        super().__init__()
        self.root_node = RadixTreeNode()
        self.root_node.ref_count = 1  # root is always protected
        self.evictable_size = 0
        self.protected_size = 0

    def lock_handle(self, handle: BaseCacheHandle, unlock: bool = False) -> None:
        if handle is None:
            return

        node = handle.node
        if unlock:
            while not node.is_root():
                node.ref_count -= 1
                assert node.ref_count >= 0
                if node.ref_count == 0:
                    self.evictable_size += node.length
                    self.protected_size -= node.length
                node = node.parent
        else:
            while not node.is_root():
                if node.ref_count == 0:
                    self.evictable_size -= node.length
                    self.protected_size += node.length
                node.ref_count += 1
                node = node.parent

    def match_prefix(self, input_ids: torch.Tensor) -> Tuple[RadixCacheHandle, torch.Tensor]:
        node, prefix_len = self._walk(input_ids)
        if prefix_len == 0:
            assert node.is_root() and node is self.root_node and prefix_len == 0
            return RadixCacheHandle(prefix_len, node), self.empty_tensor
        slots_list: List[torch.Tensor] = []
        matched_node = node
        while not node.is_root():
            slots_list.append(node.slots)
            node = node.parent
        slots_list.reverse()
        return RadixCacheHandle(prefix_len, matched_node), torch.cat(slots_list)

    def insert_prefix(self, input_ids: torch.Tensor, indices: torch.Tensor) -> int:
        node, prefix_len = self._walk(input_ids)
        assert prefix_len <= len(input_ids)
        if prefix_len < len(input_ids):
            new_node = RadixTreeNode()
            new_node.set_ids_slots(input_ids[prefix_len:], indices[prefix_len:].clone())
            new_node.set_parent(node)
            self.evictable_size += new_node.length
        return prefix_len

    def _walk(self, input_ids: torch.Tensor) -> Tuple[RadixTreeNode, int]:
        prefix_len = 0
        indice_len = len(input_ids)
        node = self.root_node
        tic = time.monotonic_ns()

        while prefix_len < indice_len:
            this_id = int(input_ids[prefix_len].item())
            if this_id not in node.children:
                return node, prefix_len

            node = node.children[this_id]

            # NOTE: at least 1 char is matched, so match_len >= 1
            match_len = node.get_match_len(input_ids[prefix_len:])
            prefix_len += match_len

            # need to split the node if not fully matched
            if match_len != node.length:
                node = node._split_at(match_len)
                return node, prefix_len

            # update timestamp for accessed node
            node.timestamp = tic

        return node, prefix_len

    def evict(self, size: int) -> torch.Tensor:
        if size == 0:
            return self.empty_tensor
        assert (
            size <= self.evictable_size
        ), f"Cannot evict {size}, only {self.evictable_size} is evictable"

        leave_nodes = self._collect_leave_nodes_for_evict()

        heapq.heapify(leave_nodes)
        evicted_indices: List[torch.Tensor] = []
        evicted_size = 0

        while evicted_size < size:
            assert (
                leave_nodes
            ), f"Cannot evict enough cache, need {size}, only {evicted_size} evicted"
            node = heapq.heappop(leave_nodes)
            assert node.ref_count == 0 and node.is_leaf() and not node.is_root()
            evicted_size += node.length
            evicted_indices.append(node.slots)
            self.evictable_size -= node.length
            parent = node.parent
            del parent.children[int(node._token_ids[0].item())]
            # NOTE: root is always protected, so won't be evicted
            if parent.is_leaf() and parent.ref_count == 0:
                heapq.heappush(leave_nodes, parent)

        return torch.cat(evicted_indices)

    def _collect_leave_nodes_for_evict(self) -> List[RadixTreeNode]:
        nodes: List[RadixTreeNode] = [self.root_node]
        leave_nodes: List[RadixTreeNode] = []

        while len(nodes) > 0:
            node = nodes.pop()
            if node.is_leaf():
                if node.ref_count == 0:
                    leave_nodes.append(node)
            else:
                for child in node.children.values():
                    nodes.append(child)

        return leave_nodes

    def reset(self) -> None:
        raise NotImplementedError("RadixManager.reset is not implemented")

    @property
    def size_info(self) -> SizeInfo:
        return SizeInfo(
            evictable_size=self.evictable_size,
            protected_size=self.protected_size,
        )
```

### 4.2 代码运行实践

实现CacheManager类后，我们可以将3.3节实践中零散的操作步骤完整串联起来。核心执行步骤如下：

- 定义KV cache的可用显存空间大小，并计算cache_per_page、num_pages的数值；
- 初始化page_table、 cache_manager；
- 创建请求0，为该请求申请显存空间，随后模拟请 0释放的操作；
- 创建请求1，先在 RadixTree 中匹配可复用的前缀缓存，再为请求1申请剩余所需空间；
- 模拟请求1释放过程；
