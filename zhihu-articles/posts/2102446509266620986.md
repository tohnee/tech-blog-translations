## 1. 从 KV Cache 张量到缓存管理系统

理解 `llama.cpp` 中的 KV Cache，首先要建立一个认识：**KV Cache 不只是一组用于保存 Key 和 Value 的张量，它还需要一套管理逻辑，负责记录缓存属于哪条序列、对应哪个逻辑位置、实际存放在哪个槽位，以及这些槽位何时可以复用。**

在 `llama.cpp` 中，`llama_kv_cache` 不仅管理各层 K/V 的存储张量，还要协调序列、缓存槽位、位置索引和多序列并发。可以先用下面几个概念建立整体认识：

| 概念 | 本质 | 主要解决的问题 |
| --- | --- | --- |
| Batch | 一次提交给模型处理的输入 Token/Embedding 集合 | 本轮有哪些输入需要一起处理？ |
| UBatch | Batch 拆分后的一次内部计算单元 | 如何控制单次计算规模，并组织实际计算？ |
| Sequence | 具有独立上下文和注意力历史的逻辑序列 | 当前 Token 属于哪条序列？它可以读取哪些历史 KV？ |
| Position | Token 在逻辑序列中的位置 | 当前 KV 在逻辑上下文中处于什么位置？ |
| Cell | KV Cache 中一个可分配的物理槽位 | 某个 Token 的 KV 被映射到哪个存储槽位？ |
| Stream | 一组 Sequence 共用的 KV Cache 分区/计算可见范围 | 哪些序列处于同一个 KV 缓存分区中？ |

这些概念并不处于同一个抽象层次：Batch 和 UBatch 主要描述**输入如何组织、计算如何切分**；Sequence 和 Position 描述**Token 的逻辑关系**；Cell 和 Stream 描述**KV Cache 如何组织和访问**。

可以用一句话概括：

> Batch/UBatch 组织计算，Sequence 描述逻辑归属，Position 描述逻辑顺序，Cell 描述物理槽位，Stream 描述缓存分区。

本文先从 Batch 和 UBatch 讲起，再逐步解释 Sequence、Cell、Position，最后通过 Unified KV Cache 的历史设计引出 Stream。

### 2. Batch 与 UBatch：如何组织一次推理计算

### 2.1 为什么需要 Batch？

先考虑一个多用户推理场景。假设模型同时服务三个用户：

```text
用户 A：当前输入 Token A5
用户 B：当前输入 Token B4
用户 C：当前输入 Token C3
```

每个用户都有自己的历史上下文。生成下一 Token 时，A 的 Query 需要读取 A 自己的历史 KV，B 的 Query 需要读取 B 的历史 KV，C 也一样。

最直观的方式是逐个处理：

```text
处理 A → 处理 B → 处理 C → ...
```

这种方式能够完成推理，但**在多请求并发时，GPU 可能需要频繁启动小规模计算**。尤其在自回归 Decode 阶段，每条序列每轮通常只新增少量 Token。如果每次只处理一条序列，计算规模可能偏小，难以充分利用 GPU 的并行计算能力。

**Batch 的核心思想，就是把多个序列在同一轮需要处理的输入 Token 放到一起提交，让模型能够以批量方式执行计算。**

例如：

```text
Batch
├── Sequence A：A5
├── Sequence B：B4
└── Sequence C：C3
```

模型可以将这些输入组织成一个批次执行。这样做通常有利于提高 GPU 利用率、摊薄部分调度和 Kernel 启动开销，并让矩阵运算具有更合适的规模。

需要注意：**Batch 不是“多个用户对话本身”，而是一次模型计算所接收的一组输入。** 一个 Batch 可以包含多条 Sequence 的 Token，也可以包含同一条 Sequence 的多个 Token。例如，在 Prompt 处理（Prefill）阶段，一个序列可能一次提交很多 Token；在 Decode 阶段，多个并发序列则可能各自贡献一个或少量 Token。

### 2.2 Batch 中的数据不只是 Token ID

在 `llama.cpp` 的批处理结构中，一个 Token 除了自身的 Token ID 或 Embedding，还需要携带与推理有关的信息，例如：

- 逻辑位置 `pos`；
- 所属的 Sequence ID 集合；
- 是否需要输出对应结果等标记。

这意味着 Batch 不只是简单的 Token 数组。它还表达了每个输入 Token 在逻辑上属于谁、位于什么位置，以及模型应该如何处理它。

例如：

```text
Token       Position       Sequence ID
--------------------------------------
A5          4              A
B4          3              B
C3          2              C
```

虽然它们位于同一个 Batch 中，但并不意味着它们属于同一条上下文，也不意味着它们可以互相读取对方的 KV Cache。Batch 解决的是“合并输入、批量执行”的问题；逻辑隔离仍然由 Sequence、Position 和 Attention Mask 等机制保证。

### 2.3 为什么还需要 UBatch？

Batch 越大，通常越有利于提高吞吐量，但单次计算规模也不能无限增大。过大的输入可能受到显存、工作区、后端实现能力或计算图规模等因素的限制。

因此，`llama.cpp` 会进一步把一个 Batch 拆分成若干个 UBatch（micro-batch）：

```text
Batch
├── UBatch 0
├── UBatch 1
└── UBatch 2
```

每个 UBatch 是内部一次处理和构建计算图的较小单元。它控制单次送入后续计算流程的数据规模。

可以用一个简单例子理解：

假设 Batch 总共有 1200 个 Token，而当前配置下希望每次最多处理 400 个 Token，那么内部就可能将其拆成三个 UBatch：

```text
Batch：1200 tokens

UBatch 0：Token 0   ~ Token 399
UBatch 1：Token 400 ~ Token 799
UBatch 2：Token 800 ~ Token 1199
```

这只是便于理解的示意。实际拆分并不一定是简单地按 Token 下标连续切片。`llama.cpp` 还要考虑不同 Token 对应的 Sequence 集合、序列长度是否相同、序列之间是否存在耦合，以及后续计算路径能否按序列组织等因素。

因此，UBatch 的目的不只是“GPU 放不下，所以切小一点”。它还承担了**调整计算规模、适配后端、组织序列集合和生成更合适计算单元**的职责。

### 2.4 Batch 与 UBatch 的区别

| 对比项 | Batch | UBatch |
| --- | --- | --- |
| 所处层次 | 输入批次 | 内部计算批次 |
| 主要作用 | 聚合本轮需要处理的输入 | 将输入拆成可执行的计算单元 |
| 数据规模 | 可以较大 | 通常受 n_ubatch 等参数约束 |
| 与 Sequence 的关系 | 可以包含多条 Sequence | 同样可以包含一条或多条 Sequence，具体取决于拆分方式 |
| 主要关注点 | 请求/Token 的批量组织 | 计算规模、序列组织和后端执行 |

从执行流程看，可以先将其理解为：

```text
用户请求 / 输入 Token
        │
        ▼
      Batch
        │
        ▼
  Batch 分配与拆分
        │
        ├── UBatch 0
        ├── UBatch 1
        └── UBatch 2
                │
                ▼
         构建并执行模型计算
```

后面介绍 KV Cache 时，需要记住：**Batch/UBatch 决定这一轮有哪些 Token 参与计算；Sequence 决定这些 Token 应该访问哪一段逻辑上下文。**

### 3. Sequence：逻辑上的 Token 序列

### 3.1 为什么需要 Sequence？

假设模型同时处理两条输入：

```text
Prompt A：A1 A2 A3 A4 A5
Prompt B：B1 B2 B3 B4
```

如果一次只处理一条序列，逻辑关系比较简单：

```text
Sequence A：A1 → A2 → A3 → A4 → A5
Sequence B：B1 → B2 → B3 → B4
```

每条序列都有自己的上下文历史。计算 A5 的 Attention 时，它应该读取 A1～A4 对应的历史 KV；计算 B4 时，则应该读取 B1～B3 的历史 KV。

现在，如果将多条序列放进同一个 Batch：

```text
Batch
├── Sequence A：A1 A2 A3 A4 A5
└── Sequence B：B1 B2 B3 B4
```

就必须让模型知道每个 Token 属于哪条逻辑序列。否则，模型无法正确区分不同用户或不同推理分支的历史上下文。

这就是 Sequence 的作用。

在 `llama.cpp` 中，`llama_seq_id` 用于标识一条逻辑序列。Batch 中的 Token 会携带 Sequence ID 信息。一个 Token 通常属于一条 Sequence，但数据结构允许一个 Token 关联多个 Sequence ID，这一点对于后续理解前缀共享非常重要。

### 3.2 Sequence 不等于 Batch，也不完全等于用户会话

这几个概念容易混淆：

| 概念 | 含义 |
| --- | --- |
| Batch | 一次提交给模型处理的输入集合 |
| UBatch | Batch 拆分后的一次内部计算单元 |
| Sequence | 具有独立逻辑上下文和注意力历史的序列 |
| Sequence ID | 标识 Sequence 的整数 ID |
| 用户会话 | 应用层的对话概念，通常映射到一条或多条推理序列 |

Sequence 是推理内存系统中的逻辑标识，并不天然等同于应用层的“一个用户”或“一个完整聊天会话”。例如，并行候选生成、分支推理或共享前缀等场景，都可能涉及多个 Sequence。

### 3.3 一个 Cell （下面会提到）为什么可能属于多个 Sequence？

这是 `llama.cpp` KV Cache 设计中非常重要的一点。

假设两个 Sequence 使用相同的公共 Prompt：

```text
                共同 Prompt
                  A1 A2 A3
                   /    \
                  /      \
          Sequence A    Sequence B
             A4 A5        B4 B5
```

A 和 B 在逻辑上是两条不同的序列，但它们的前缀 `A1 A2 A3` 完全相同。在模型参数、位置和相关推理条件一致的前提下，这段公共前缀产生的 KV 数据也相同。

如果为两个 Sequence 分别保存一份：

```text
Sequence A：[A1][A2][A3][A4][A5]
Sequence B：[A1][A2][A3][B4][B5]
```

那么前三个 Token 的 KV 就重复存储了。

Unified KV Cache 可以让多个 Sequence 共同引用公共前缀对应的物理 Cell：

```text
Cell 0：Position 0，Sequence {A, B}
Cell 1：Position 1，Sequence {A, B}
Cell 2：Position 2，Sequence {A, B}
Cell 3：Position 3，Sequence {A}
Cell 4：Position 3，Sequence {B}
```

这样，A 和 B 的前缀可以共用前三个 Cell，分叉之后再分别使用自己的 Cell。

这里要区分两个层面：

- **逻辑层面**：A 和 B 仍然是两条不同的 Sequence。
- **物理层面**：它们可以引用同一份公共前缀 KV 数据。

因此，Sequence 表示逻辑归属关系，而不是一条序列必须独占一整块物理 KV 内存。

### 4. Cell：KV Cache 中的物理槽位

### 4.1 Cell 究竟是什么？

先看一个简化的 KV Cache。假设模型有 32 层，每层都需要保存 K 和 V。当模型处理一个 Token 时，会在参与 KV Cache 的各层产生对应的 K、V。

因此，一个 Token 对应的 KV 可以抽象为：

$$ KV_t = \{K_t^{(0)},V_t^{(0)},K_t^{(1)},V_t^{(1)},\ldots,K_t^{(31)},V_t^{(31)}\} $$

假设缓存可以容纳 1024 个 Token 槽位，那么从逻辑上看，每一层的 K、V 都需要有对应的存储位置：

```text
Layer 0:
    K[0] K[1] K[2] ... K[1023]
    V[0] V[1] V[2] ... V[1023]

Layer 1:
    K[0] K[1] K[2] ... K[1023]
    V[0] V[1] V[2] ... V[1023]

...

Layer 31:
    K[0] K[1] K[2] ... K[1023]
    V[0] V[1] V[2] ... V[1023]
```

当某个 Token 的 KV 被分配到第 10 个槽位时，系统还必须知道：

- 这个槽位是否已经被占用？
- 它属于哪条 Sequence，或者被哪些 Sequence 共同引用？
- 它对应逻辑序列中的哪个 Position？
- 删除某条 Sequence 后，这个槽位是否还能被其他 Sequence 使用？
- 什么时候可以回收并重新分配？

K、V 张量中的数值本身无法回答这些管理问题。因此，KV Cache 还需要一套槽位元数据管理机制，这就是 Cell 的意义。

**Cell 可以理解为 KV Cache 中一个可分配的物理槽位。它记录的是槽位的管理信息，而不是直接保存 K、V 数值。**

真正的 K、V 数据保存在 `ggml_tensor` 所引用的后端缓冲区（Backend Buffer）中。Cell 索引会被用于确定相应张量中的读写位置。具体 Tensor 的形状、布局和偏移计算会受到模型结构、V Cache 是否转置、Attention Kernel 和后端实现等因素影响，因此不能把 Cell 简单理解成一段固定连续的 K/V 字节。

### 4.2 一个重要的源码细节：Cell 不一定是独立的 C++ 对象

从概念上讲，我们可以说“一个 Cell 管理一个 KV 槽位”。但在源码实现中，不应误以为每个槽位都对应一个独立的 `Cell` 类实例。

当前实现主要由 `llama_kv_cells` 管理一组并行数组：同一个下标 `i` 在不同数组中的数据，共同描述第 `i` 个 Cell 的元信息。例如：

```cpp
std::vector<llama_pos> pos;
std::vector<llama_kv_cell_ext> ext;
std::vector<llama_pos> shift;
std::vector<seq_set_t> seq;

```

也就是说，`pos[i]`、`ext[i]`、`shift[i]` 和 `seq[i]` 共同描述 Cell `i`。这种组织方式可以避免为每个槽位都单独分配一个复杂对象，并便于批量维护元数据。

### 4.3 Cell 管理哪些信息？

结合 `llama-kv-cells.h`，可以把主要数据归纳为下表。需要区分：前几项是按 Cell 下标存储的元数据，后几项则是为了快速检索而维护的管理索引。

| 数据 | 含义 | 主要作用 |
| --- | --- | --- |
| pos[i] | Cell i 对应的逻辑 Position；-1 表示空槽位 | 判断槽位是否被占用，并记录 Token 位置 |
| seq[i] | 一个 Bitset，记录哪些 Sequence 正在引用 Cell i | 管理序列归属和共享关系 |
| ext[i] | 扩展元数据，例如二维位置 x/y、特定场景下的 Token 信息 | 支持 M-RoPE 等位置或输入扩展场景 |
| shift[i] | 自上次重置以来累积的位置偏移 | 汇总位置调整，供后续位置更新流程使用 |
| used | 已使用 Cell 的索引集合 | 快速定位已占用槽位范围和使用状态 |
| seq_pos[s] | Sequence s 对应的 (Position, Cell Index) 有序集合 | 快速查询某条序列的最小、最大位置及邻近位置 |
| seq_bits[s] | 从 Sequence 维度组织的 Cell 位图 | 快速构造某条序列对应的 Cell 列表 |

其中最关键的是 `pos` 和 `seq`。

### `pos`：逻辑位置

例如：

```text
Cell 0：pos = 0
Cell 1：pos = 1
Cell 2：pos = 2
Cell 3：pos = 3
Cell 4：pos = -1
```

这里 `pos = -1` 表示该 Cell 为空。

需要特别注意：**Cell Index 和 Position 不是同一个概念。**

例如：

```text
Cell 0 → Position 100
Cell 1 → Position 101
Cell 2 → Position 102
Cell 3 → Position 103
```

也可能出现：

```text
Cell 0 → Position 103
Cell 1 → Position 100
Cell 2 → Position 101
Cell 3 → Position 102
```

原因是 KV Cache 的物理槽位可以被循环搜索、回收和复用，而 Token 的逻辑 Position 仍然由序列上下文决定。物理槽位的排列顺序不必与逻辑 Token 顺序一致。

因此：

$$ \boxed{\text{Cell Index} \neq \text{Token Position}} $$

可以将两者理解为：

```text
Position   ：逻辑地址，说明 Token 在序列中的位置
Cell Index ：物理槽位索引，说明 KV 数据映射到哪个缓存槽位
```

### `seq`：Sequence 归属关系

源码中使用 Bitset 记录 Cell 的 Sequence 集合，形式可以理解为：

```cpp
using seq_set_t = std::bitset<LLAMA_MAX_SEQ>;
std::vector<seq_set_t> seq;

```

例如：

```text
seq[0] = 00000011
seq[1] = 00000011
seq[2] = 00000011
seq[3] = 00000001
```

假设最低位代表 Sequence 0，第二位代表 Sequence 1，那么：

```text
Cell 0：属于 Sequence 0、Sequence 1
Cell 1：属于 Sequence 0、Sequence 1
Cell 2：属于 Sequence 0、Sequence 1
Cell 3：只属于 Sequence 0
```

因此，一个 Cell 可以同时被多个 Sequence 引用。这个集合也决定了哪些逻辑序列能够访问对应的缓存内容。

### 4.4 为什么还要维护 `seq_pos`？

源码中还有一个非常重要的结构：

```cpp
std::set<std::pair<llama_pos, uint32_t>> seq_pos[LLAMA_MAX_SEQ];

```

它为每条 Sequence 维护一组有序的 `(Position, Cell Index)`：

```text
Sequence 0：

(Position 0, Cell 10)
(Position 1, Cell 11)
(Position 2, Cell 12)
(Position 3, Cell 13)
```

有了这个有序集合，就可以较快地获得：

```cpp
seq_pos_min(seq_id);
seq_pos_max(seq_id);

```

也可以通过 `lower_bound()`、`upper_bound()` 等有序集合操作，定位某个 Position 附近的 Cell。

为什么需要额外维护它？

假设物理槽位的排列是：

```text
Cell 0 → Position 103
Cell 1 → Position 100
Cell 2 → Position 102
Cell 3 → Position 101
```

如果每次都扫描全部 Cell，才能找到某条 Sequence 的最小或最大 Position，检索成本就会随缓存规模增加。`seq_pos` 把“按逻辑位置查询”的需求单独组织成有序索引，避免每次都扫描整个物理槽位数组。

这里还有一个容易忽略的细节：`seq_pos` 使用的是 `(Position, Cell Index)`，而不是只使用 Position。因为同一条 Sequence 中可能出现多个 Cell 具有相同 Position，例如某些视觉模型的输入位置，或者缓存复用过程中暂时出现的重复位置。Cell Index 作为第二个排序字段，可以让这些记录同时存在。

### 4.5 为什么还要维护 `seq_bits`？

`seq_bits` 可以理解为 `seq` 的转置视图。

- `seq[i]`：从 Cell 出发，记录这个 Cell 属于哪些 Sequence。
- `seq_bits[s]`：从 Sequence 出发，记录这条 Sequence 使用了哪些 Cell。

这种双向组织不是为了保存两份不同的逻辑事实，而是为了让不同方向的查询更高效。

例如，Attention 构造 KV 行列表时，需要快速找出某个 Sequence 对应的 Cell。逐个扫描所有 Cell 并检查 `seq[i]` 会比较直接，但成本可能较高。`seq_bits[s]` 可以通过位运算快速筛选出属于指定 Sequence 的槽位，再结合 Position、滑动窗口等条件构造实际访问列表。

因此，`llama_kv_cells` 并不只是一个保存 `pos` 和 `seq` 的简单数组，而是包含了多种面向不同查询方向的索引结构。

### 4.6 Cell 的回收与复用

Cell 的另一个重要职责，是支持序列删除后的缓存回收。

例如：

```text
Cell 0：Position 0，Sequence {A, B}
Cell 1：Position 1，Sequence {A, B}
Cell 2：Position 2，Sequence {A}
Cell 3：Position 2，Sequence {B}
```

现在删除 Sequence B：

- Cell 0：移除 B 的引用，但 A 仍然使用，因此不能回收。
- Cell 1：移除 B 的引用，但 A 仍然使用，因此不能回收。
- Cell 3：没有其他 Sequence 使用，可以回收。
- Cell 2：原本就不属于 B，不受影响。

这类操作由 `seq_rm()` 等接口完成。删除某个 Sequence 时，系统会从 Cell 的归属集合中移除对应 ID；如果该 Cell 不再被任何 Sequence 引用，就可以清理元数据并将其重新纳入可分配槽位。

因此，Cell 的 Sequence Bitset 在一定程度上承担了类似引用计数的职责，但它并不是传统的整数引用计数：它记录的是**具体有哪些 Sequence 在引用这个 Cell**，而不只是一个引用数量。

### 5. Position：为什么不能用 Cell Index 代替？

前面已经介绍了：

- Sequence：逻辑序列；
- Cell：物理缓存槽位。

还需要一个独立的 Position，用来描述 Token 在逻辑序列中的位置。

假设 Sequence A 为：

```text
A1 A2 A3 A4 A5
```

它们的逻辑位置是：

```text
0  1  2  3  4
```

但由于环形分配、槽位回收与复用，物理存储位置可能是：

```text
Position 0 → Cell 10
Position 1 → Cell 11
Position 2 → Cell 12
Position 3 → Cell 0
Position 4 → Cell 1
```

Attention 需要依据逻辑位置和序列归属判断哪些历史 KV 可见，而不能把 Cell 的物理排列顺序当成 Token 的时间顺序。

Position 会参与因果关系、位置编码以及滑动窗口等逻辑。例如，当前 Token 在 Position 4 时，通常不能读取未来 Position 5 的 KV；如果模型采用滑动窗口 Attention，还要进一步排除超出窗口范围的历史位置。

### 5.1 多模态位置带来的额外情况

对于普通文本，可以直观地把 Position 理解为不断递增的 Token 下标。但在多模态模型中，位置关系不一定只有一维。

例如，一些使用 M-RoPE 的视觉输入会涉及二维空间位置。当前 `llama_kv_cell_ext` 中包含 `x`、`y` 等扩展信息，用于记录相关空间位置；此外，某些由 Embedding 输入产生的 Cell 还可能携带 Token 相关信息。

另外，同一条 Sequence 中也可能存在多个 Cell 使用相同的基础 Position。源码注释明确考虑了视觉模型重复位置以及缓存复用等情况。因此，`seq_pos` 用 `(Position, Cell Index)` 作为键，而不是假定 Position 在一条 Sequence 中永远唯一。

这也解释了为什么 Position 与 Cell Index 必须分开管理：Position 表达模型的逻辑位置语义，Cell Index 负责定位物理缓存槽位。

---

### 6. Unified KV Cache：为什么早期选择共享缓存池？

理解了 Batch、Sequence、Cell 和 Position，就可以进一步解释 KV Cache 的组织方式。

### 6.1 每条 Sequence 独占缓存会有什么问题？

假设系统同时服务四条 Sequence：

```text
Sequence A
Sequence B
Sequence C
Sequence D
```

假设为每条 Sequence 都单独分配 1000 个 Token 的缓存空间：

```text
Sequence A → KV Cache A（1000）
Sequence B → KV Cache B（1000）
Sequence C → KV Cache C（1000）
Sequence D → KV Cache D（1000）
```

总容量是 4000 个槽位。但实际使用情况可能是：

```text
Sequence A：使用 1000
Sequence B：使用  300
Sequence C：使用  500
Sequence D：使用  200

总使用量：2000
```

如果每条序列的容量被固定切分，那么 B、C、D 没有使用的空间可能无法直接交给 A 使用。A 需要继续增长时，可能出现 A 的分区已满、而其他分区仍然空闲的情况。

因此，一种更灵活的设计是：不提前将缓存容量固定切成每条序列独占的区域，而是让所有 Sequence 从同一个缓存池中动态申请 Cell。

这就是 Unified KV Cache 的基本思想。

### 6.2 Unified KV Cache 的组织方式

假设总共只有一个容量为 4000 个槽位的共享缓存池：

```text
Unified KV Cache
┌─────────────────────────┐
│ Cell 0   Cell 1   Cell 2   Cell 3 ...            │
│   A        B        C        A                   │
│ Cell 4   Cell 5   Cell 6   Cell 7 ...            │
│   D        B        A        C                   │
└─────────────────────────┘
```

不同 Sequence 的 Cell 可以交错分配：

```text
Cell 0 → Sequence A，Position 0
Cell 1 → Sequence B，Position 0
Cell 2 → Sequence C，Position 0
Cell 3 → Sequence A，Position 1
Cell 4 → Sequence D，Position 0
Cell 5 → Sequence B，Position 1
...
```

这里需要明确：**Unified 的“统一”，指的是物理 KV 缓存池统一，而不是逻辑上把所有 Token 合并成同一条 Sequence。** 每个 Cell 仍然记录自己的 Position 和 Sequence 归属。

### 6.3 Unified 的优势一：动态分配缓存空间

例如：

```text
KV Cache 总容量：4000

Sequence A：使用 2000
Sequence B：使用  500
Sequence C：使用  300
Sequence D：使用  200

总使用量：3000
剩余空间：1000
```

只要共享缓存池中还有空闲 Cell，A 就可以继续申请空间，不必受限于最初为 A 固定预留的某个小分区。

这也是共享缓存池的重要价值：**缓存容量按照实际使用情况动态分配，而不是平均分配给每条 Sequence。**

需要注意，`--ctx-size` 等参数的精确含义与具体运行模式、版本和配置有关。上面的 4000 个槽位用于解释 Unified 的共享池思想，不应直接推广成所有 llama.cpp 模式下每个参数的固定容量语义。

### 6.4 Unified 的优势二：公共前缀共享

假设有三条 Sequence：

```text
Sequence A：System Prompt + User A Prompt
Sequence B：System Prompt + User B Prompt
Sequence C：System Prompt + User C Prompt
```

它们具有相同的 System Prompt。只要公共前缀对应的 Token、位置以及相关推理条件一致，就可以只保留一份公共前缀 KV，让多条 Sequence 共同引用：

```text
                System Prompt
                     │
                     ▼
               共享 KV Cells
                /     |     \
               /      |      \
              A       B       C
```

Cell 使用 Sequence 集合记录哪些序列可以访问这些公共 KV。

因此，Unified KV Cache 并不是一个简单的“旧设计”或“错误设计”。它解决了两个重要问题：

1. 不同长度的 Sequence 可以从同一个池中动态申请缓存空间，提高空间利用率。
2. 多条 Sequence 可以共享相同的前缀 KV，减少重复计算和重复存储。

---

### 7. Unified KV Cache 的性能问题：Cross-Sequence Attention

### 7.1 逻辑隔离不等于计算隔离

Unified KV Cache 带来了空间利用率和前缀共享优势，但也带来了一个潜在的计算问题。

假设四条 Sequence 分别有 1000 个历史 Token：

```text
Sequence A：K_A，1000 个 Token
Sequence B：K_B，1000 个 Token
Sequence C：K_C，1000 个 Token
Sequence D：K_D，1000 个 Token
```

统一缓存视图中共有 4000 个 KV 位置：

$$ K_{all} = [K_A, K_B, K_C, K_D] $$

A 的 Query 在逻辑上只能关注 A 自己的历史 KV：

$$ Q_A K_A^T $$

但在某些早期统一缓存计算路径中，为了使用连续的共享 KV 视图，Attention 可能先构造更大的 Query-Key 关系：

$$ Q_A K_{all}^T $$

然后再通过 Attention Mask 把 B、C、D 对应的位置屏蔽：

$$ Q_A K_{all}^T + M $$

其中，对 A 不可见的位置，Mask 会加上负无穷或等效的屏蔽值，使其不会对最终 Softmax 和 Attention 输出产生贡献。

这里有一个关键区别：

- **逻辑上**：A 只允许关注 A 的历史 KV；
- **结果上**：Mask 保证 B、C、D 的信息不会混入 A 的最终 Attention 输出；
- **计算上**：如果 Attention Kernel 没有利用 Mask 跳过无效位置，那么对应的 QK 运算仍可能产生额外开销。

这就是 Cross-Sequence Attention 所讨论的问题：不同 Sequence 之间没有逻辑上的信息交互，但某些计算路径可能仍然做了不必要的跨序列计算。

### 7.2 这不代表所有版本、所有后端都会计算全部无效位置

需要避免一个过度概括：不能说所有 Unified KV Cache、所有 Backend、所有 Attention Kernel 都一定会对整个共享缓存执行完整的 QK 乘法。

实际开销取决于计算图如何构造 KV 视图、Attention Kernel 是否能够利用 Mask 或稀疏行信息，以及当前 UBatch 中的 Sequence 是否能够被拆分处理。

当前源码中已经能看到更细的 KV 行组织逻辑：在合适的条件下，可以按 UBatch 中的 Sequence 生成各自需要访问的 Cell 列表，而不是简单地让每个 Query 无差别面对整个缓存。若 UBatch 中的序列交错、耦合，无法拆成独立的序列切片，则实现仍可能退回到覆盖多个序列的统一切片。

因此，更严谨的表述是：**Unified 缓存组织存在跨序列 KV 视图和无效 Attention 计算的结构性风险；具体是否产生、产生多少额外运算，取决于当前版本的计算图和后端 Kernel 优化。**

---

### 8. Stream：把 KV Cache 拆分为多个缓存分区

### 8.1 Stream 为什么被引入？

上面已经介绍了 Unified KV Cache 的优势和潜在问题：所有 Sequence 共用一个缓存池，方便动态分配和共享公共前缀；但当多个 Sequence 相互独立、上下文都很长时，共享缓存视图可能导致不必要的跨序列 Attention 计算。

一个直接的优化方向是：让不同 Sequence 使用不同的 KV Cache Buffer，使某条序列在构造 Attention 时只面对自己所属分区中的 KV。

这就是 llama.cpp 引入 Stream 的主要动机之一。

2025 年 7 月，`ggerganov` 合入了 [llama.cpp PR #14363：llama: add high-throughput mode](https://github.com/ggml-org/llama.cpp/pull/14363)。该 PR 的目标是改善多序列 Decode 的性能，避免不必要的跨序列 Attention 计算。PR 描述中将 KV 缓存拆分为多个 Buffer，并在 Batch 进入 Attention 时按 Stream 组织；每个 Stream 拥有自己的 KV Cache Buffer，因此不会直接看到其他 Stream 的 KV。

### 8.2 Stream 是什么？

在这里，Stream 可以理解为 KV Cache 的一个物理管理分区，同时也是 Attention 组织 KV 可见范围时使用的一个分组概念。

要特别注意：**这里的 Stream 不是 CUDA Stream，也不是操作系统线程，更不是用户请求队列。** 它是 llama.cpp KV Cache 内部用于组织序列和缓存视图的概念。

PR #14363 引入这一设计时，主要提供两种组织方式：

1. **Unified / 单 Stream**：所有 Sequence 被映射到同一个 Stream，共享一个 KV Cache 分区。这对应原来的统一缓存池思路。
2. **Split / 多 Stream**：不同 Sequence 被映射到不同 Stream，各自使用独立的 KV Cache 分区。

在相应实现中，最初支持的主要是单 Stream，或者按 `n_seq_max` 为每个最大序列 ID 建立一个 Stream 的模式。当前源码中也可以看到类似的约束和 `seq_to_stream` 映射：当只有一个 Stream 时，Sequence ID 默认都映射到 Stream 0；当启用多个 Stream 时，序列 ID 会被映射到对应的 Stream。

因此，Stream 并不是 Sequence 的另一个名字。两者的区别是：

- Sequence 表示逻辑上的序列；
- Stream 表示这些 Sequence 使用哪一个 KV Cache 分区。

在单 Stream 模式下，多条 Sequence 可以处于同一个 Stream；在 Split 模式下，通常是一条 Sequence 对应一个 Stream。

### 8.3 Unified 与 Split 的组织方式

继续使用四条 Sequence 的例子。

**Unified：**

```text
llama_kv_cache
└── Stream 0
    ├── KV A ─── Seq A
    ├── KV B ─── Seq B
    ├── KV C ─── Seq C
    └── KV D ─── Seq D
```

四条 Sequence 都处于 Stream 0，共享同一个缓存分区。它们仍然通过 Cell 的 Sequence 元数据保持逻辑隔离。

**Split / Multi-stream：**

```text
llama_kv_cache
├── Stream 0
│   └── KV A ─── Seq A
├── Stream 1
│   └── KV B ─── Seq B
├── Stream 2
│   └── KV C ─── Seq C
└── Stream 3
    └── KV D ─── Seq D
```

这时每条 Sequence 被映射到自己的 Stream，缓存槽位和 KV 访问范围也随之分开。

在源码组织上，可以把它理解为：

- `seq_to_stream` 负责把 Sequence ID 映射到 Stream ID；
- `v_cells` 为不同 Stream 维护对应的 Cell 元数据集合；
- K/V Tensor 的存储布局也按 Stream 组织；
- 构建 Attention 时，根据当前 UBatch 中 Token 所属的 Sequence，找到对应 Stream 的 KV 数据。

### 8.4 Stream 如何减少跨序列 Attention？

在 Unified 模式下，若某条计算路径使用整个共享 KV 视图，A 的 Query 可能面对：

```text
Q_A × [K_A  K_B  K_C  K_D]
                  │
                  ▼
              Attention Mask
```

而在 Split 模式下，A 的 Query 被组织到 Stream A 中，只需要访问该 Stream 的 KV：

```text
Stream A：Q_A × K_A
Stream B：Q_B × K_B
Stream C：Q_C × K_C
Stream D：Q_D × K_D
```

这样就从缓存组织层面隔离了不同 Sequence 的 KV 可见范围，减少了跨序列 KV 计算的机会。

这里要强调，Stream 的作用不是让 GPU 把多个用户请求串行执行。多个 Stream 对应的数据仍然可以被组织进同一个 Batch/UBatch，并在模型计算中并行处理。Stream 改变的是 KV Cache 的组织和 Attention 使用的缓存范围，而不是简单地改变 CPU/GPU 的线程调度方式。

### 8.5 为什么不彻底废弃 Unified？

既然 Split 有机会减少跨序列 Attention，那么是不是应该完全取消 Unified？并不是。

Unified 有一个重要优势：多条 Sequence 可以直接共享同一个 Cell 中的公共前缀 KV。

例如：

```text
Sequence A：System Prompt + Prompt A
Sequence B：System Prompt + Prompt B
```

在 Unified 模式下，可以让两条 Sequence 共同引用 System Prompt 对应的 KV Cells：

```text
              System Prompt KV
                     │
               共享 KV Cells
                 /       \
                A         B
```

而在 Split 模式下，A 和 B 属于不同 Stream，不能直接把同一个 Stream 内的 Cell 当作另一个 Stream 的本地 Cell 使用。公共前缀通常需要在不同 Stream 中分别保存，或者通过额外的数据复制/迁移机制处理。

因此，两种模式体现的是不同的优化方向：

| 对比维度 | Unified / 单 Stream | Split / Multi-stream |
| --- | --- | --- |
| 缓存组织 | 多条 Sequence 共用一个缓存分区 | 不同 Sequence 使用独立缓存分区 |
| 主要目标 | 灵活分配缓存空间、共享前缀 KV | 减少独立 Sequence 之间的 KV 可见范围和无效计算 |
| Sequence 之间 | 可以共享 Cell | 不同 Stream 之间不直接共享同一个 Cell |
| 公共前缀 | 可以直接共享对应 KV | 通常需要在各 Stream 中分别保存，或额外复制 |
| 缓存容量 | 由共享池统一分配 | 各 Stream 分别管理可用槽位，容量和总内存取决于具体配置 |
| 更适合的情况 | 多条序列有较大的公共前缀，或序列长度差异较大 | 多条序列相对独立、上下文较长，跨序列计算开销明显 |

还要注意，Split 并不意味着把一个固定总容量的共享池简单切成几块。不同版本的具体分配方式、每个 Stream 的容量以及最终显存占用，需要结合对应版本的 `llama_kv_cache` 构造参数和 Tensor 分配代码判断，不能只凭示意图推导。

因此，Unified 和 Split 并不是简单的“新旧优劣”关系，而是对缓存空间利用、前缀复用和 Attention 计算效率进行不同权衡。

### 9. 把这些概念串起来：一次推理中 KV Cache 如何工作？

现在把前面的概念放回一次完整的推理流程中。

假设当前有三条 Sequence：A、B、C。它们各自提交一个新 Token，并需要读取自己的历史 KV。

```text
输入层：

Batch
├── Token A_new，Sequence A，Position pA
├── Token B_new，Sequence B，Position pB
└── Token C_new，Sequence C，Position pC
```

随后，Batch 分配器根据批次规模和序列关系，将输入拆成一个或多个 UBatch：

```text
Batch
   │
   ▼
llama_batch_allocr
   │
   ▼
UBatch
```

UBatch 中的 Sequence ID 告诉 KV Cache：每个输入 Token 属于哪条逻辑序列。KV Cache 再根据 Sequence ID 找到对应 Stream：

```text
Sequence A ──> Stream 0
Sequence B ──> Stream 1
Sequence C ──> Stream 2
```

接下来，KV Cache 为本轮输入寻找可用 Cell。可以将这一过程概括为：

```text
UBatch Token
    │
    ▼
Sequence ID + Position
    │
    ▼
seq_to_stream：确定所属 Stream
    │
    ▼
find_slot：为本轮 Token 寻找可写入的 Cell
    │
    ▼
slot_info：记录 Token 对应的 Stream / Cell 索引
    │
    ▼
计算 K、V，并写入相应的 KV Tensor
```

模型计算完成后，Attention 需要构造当前 Query 可以访问的历史 KV 范围。这个过程会结合：

- Sequence ID：判断 Cell 是否属于当前逻辑序列；
- Position：判断 Cell 是否满足因果位置、滑动窗口等约束；
- Stream：确定当前序列对应哪个缓存分区；
- Cell Index：定位实际 KV 存储位置。

最终，Attention 使用符合条件的历史 KV 完成计算。某条 Sequence 被删除或其缓存需要淘汰时，Cell 管理结构会移除对应的 Sequence 引用；当槽位不再被任何序列使用时，便可以回收并重新分配。

这条链路说明，KV Cache 管理并不是单纯的“把 K 和 V 写进显存”：它还必须维护输入 Token、逻辑序列、逻辑位置、物理槽位、缓存分区之间的映射关系。

### 10. 总结

理解 `llama.cpp` 的 KV Cache，最重要的是不要把逻辑序列、物理槽位和实际张量存储混为一谈。

| 概念 | 可以怎样理解 | 关键职责 |
| --- | --- | --- |
| Batch | 本轮输入的集合 | 聚合多条序列的输入，提高批量计算效率 |
| UBatch | Batch 的内部计算切片 | 控制单次计算规模，并适配序列组织和后端执行 |
| Sequence | 一条逻辑上下文 | 决定 Token 的逻辑归属和可访问的历史 KV |
| Position | 逻辑位置 | 决定 Token 在上下文中的位置关系 |
| Cell | 一个物理缓存槽位 | 记录槽位使用状态、位置和 Sequence 引用关系 |
| Stream | 一组 Sequence 共用的缓存分区 | 组织 KV 存储和 Attention 的缓存可见范围 |
| K/V Tensor | 真正保存 KV 数值的张量 | 存储模型各层计算得到的 Key 和 Value |

从演化角度看：

1. **Batch/UBatch** 解决的是多 Token 输入如何组织、如何拆分执行的问题。
2. **Sequence** 解决的是同一个 Batch 中存在多条上下文时，如何区分各自的逻辑历史。
3. **Position** 解决的是逻辑顺序问题，避免把物理存储顺序误当成 Token 顺序。
4. **Cell** 解决的是物理槽位管理问题，包括占用、归属、查询、回收和复用。
5. **Unified KV Cache** 让多条 Sequence 从共享池中动态申请 Cell，并支持公共前缀共享。
6. **Stream** 则进一步把缓存组织为多个分区，在多条独立 Sequence 并发时缩小 Attention 的 KV 可见范围，减少不必要的跨序列计算。

最终可以形成一个完整的心智模型：

> Batch/UBatch 决定“这一轮算哪些 Token”；Sequence 决定“Token 属于谁”；Position 决定“Token 在逻辑上下文中的位置”；Cell 决定“KV 放在哪里”；Stream 决定“这些 KV 属于哪个缓存分区，以及当前计算面对哪一部分缓存”。

当这几个概念能够区分开来，再去阅读 `llama_kv_cache`、`llama_kv_cells`、`llama_kv_cache_context`、`slot_info` 以及计算图中 KV 输入和 Attention Mask 的构造逻辑，就更容易把源码中的数据结构和一次真实推理过程对应起来。
