### **前言**

2026 年 10 月 22 日，两家顶级 AI 实验室OpenAI 和 Anthropic，几乎同时发布了各自关于生产级 Agent 工程实践的深度文章。

OpenAI 从“前线部署工程师”的第一视角出发，讲的是如何把 AI 能力真正落地到客户的复杂业务中；Anthropic 则聚焦企业 Agent 架构中最流行的“多智能体编排”模式，提出要把大部分子智能体折叠回主循环。

读完之后你会发现，它们指向的是同一个结论：**当下的企业 Agent 架构，普遍做复杂了。**

两大顶级AI巨头进行了一次罕见的交叉验证，这含金量不言而喻了。

---

### **两条路线**

### **OpenAI的部署鸿沟**

所谓“部署鸿沟”，是指：

> 模型能力的发展速度，已经超过了将其投入实际应用所需的系统和流程

说人话就是，你现在做harness的效率，可能已经赶不上模型进化的速度。

打个比方，业务方技术团队吭哧吭哧折腾了半天harness，终于达到业务需求了，结果发现又出新模型了。而对于新模型来说，之前的harness可能有点过时了，甚至会限制新模型的发挥。

这个问题催生了“前线部署工程师”（FDE）这个角色。他们的使命就是弥合这条鸿沟——深入客户业务一线，把当前模型能力迅速转变成可靠运行的系统。

OpenAI 的前线部署核心方法论：**从目标成果出发，为成功付诸必要的行动，再实现规模化。**

他们的典型路径是这样的：

**第一步，深入客户一线，先让 AI 产生实际价值。**

比如一个半导体客户的案例。前线部署工程师里有人几天前才加入 OpenAI，之前从未做过芯片设计。他们加入客户的验证团队，和工程师一起构建评估体系，测试 AI 能否生成有用的测试用例、能否正确诊断芯片故障。

3 到 6 个月内，十几个用例全部投入生产：AI 生成定向测试节省约 48% 的时间，内核优化带来 22% 的性能提升，几周的调试工作被压缩到了数小时。

**第二步，让成功可以复制。**

前线部署工程师用 Codex 重构应用，把原先的定制代码变成了基于通用 Codex 基础能力构建的**插件和技能**。结果每个项目移除了约 90% 的定制代码。

2026 年 8 月的一个用例中，首次部署花了两个月；把同样的解决方案推广到第二个团队，只用了一天。

**第三步，发现能力差距，推动模型进步。**

OpenAI 与一家电信客户合作扩展到语音服务时，用关键评估测了一下，模型当时的得分大约 60%——已经摸到了能力上限。函数调用和指令遵循还有明显短板。

于是前线部署工程师和客户一起搭建了测试平台，明确模型需要完成的任务；研究团队则针对性地改进模型，陆续推出快照版本让他们验证。六个月后，模型得分突破 90%，达到了生产环境要求。

### **Anthropic：多智能体陷阱**

Anthropic Applied AI 团队的视角则更聚焦在 Agent 架构本身。

他们观察到一个非常普遍的企业实践：每个业务团队都想构建自己的专业 Agent，然后由一个中央编排器把它们串起来。结果是：

- **子智能体泛滥**：每个团队都发自己的 Agent，企业里动不动几百个，没人管、没人维护、互相重叠
- **上下文丢失**：Agent 之间传递的是摘要而不是原始信息，每一次交接都是信息损耗
- **延迟翻倍**：一个客户做了对比测试，多智能体架构比单循环慢了大约 2 倍
- **提示词冲突**：每个团队往 System Prompt 里加一句话，规则互相打架
- **评估失真**：每个团队做自己那一小段的评估，没人对整体效果负责，领导看到的是一堆虚高的局部分数

Anthropic发现，当模型能力足够强时（从 Opus 4.5 开始，模型在单次循环里能管理的事情远超大多数团队的预期），用**渐进式上下文披露 + 工具搜索**的单循环设计，往往比多智能体架构效果更好。不仅质量更高，成本和延迟也更低。

什么是渐进式披露？

简单说就是：Agent 启动时只加载技能和工具的简要描述，只有在真正需要的时候，才把完整上下文加载进来。Claude Code 团队甚至把系统提示词精简了 80%。

砍掉的那些，都是可以通过渐进式披露动态加载的内容。

Anthropic 明确说，**子智能体只该在三种情况下保留**：

- 单个 Agent 循环因为上下文膨胀出现了可测量的性能下降
- 多个任务需要真正并行处理，而且各自有独立的上下文窗口可以在完成后丢弃
- 单个 Agent 在工具选择上确实有困难，或者系统提示词里有互相冲突的指令

除此之外，都应该往主循环里折叠。具体做法：

- **评估先行**：先建立一套端到端的任务完成度评估体系。评分标准不要看局部，要看最终任务有没有完成。在折叠之前和之后分别跑这套评估，用数据说话。
- **从高频联动开始合并**：如果生产流量里，有两个子智能体经常一前一后被调用（比如先查订单再查物流），这说明它们高度耦合，优先合并。
- **“子智能体作为工具”过渡**：不必一下子重写所有子智能体，让主循环把它们当成 MCP 工具来调用就好。
- **最后替换为 Skill + Tool**：把子智能体的系统提示词拆成 Skill（领域知识和流程步骤），把子智能体的 API 调用拆成 MCP Tool（数据读取和动作执行）。

### **殊途同归**

把两篇文章放在一起看，它们的底层逻辑惊人地一致。

**先复杂后简化，是不可避免的路径**

OpenAI 不会一开始就用通用框架。他们先让定制应用跑起来，拿到真实数据，再把有效的部分沉淀为通用组件。

Anthropic 也承认在企业里，现实往往需要先做复杂架构再逐步折叠。

**评估必须是端到端的，而不是局部的**

OpenAI 不会说“我的组件在基准测试里准确率 95%”，他们会说“芯片验证节省了 48% 的时间”、“Tax AI 处理量增加了 50%”。

Anthropic 也建议用端到端的任务完成度评估（task-completion eval）替代局部评估。

**模型能力在吃掉架构的工作**

Anthropic 提到，从 Opus 4.5 到 Opus 5.5 和 Fable 5.1，新模型越来越擅长在执行过程中自我叙述、自我检查。这意味着原来需要 harness 强制做的“计划-执行-验证”流程，现在模型自己就在做了。

OpenAI 这边，Codex 能力的提升，让他们能一次性砍掉项目里 90% 的定制代码。

**每一代新模型，都在让更多的工程架构变得冗余。**

Anthropic 特别强调：“让你的 Agent 架构尽量不绑定特定模型版本”。绑定得越死，迁移到下一代模型时越麻烦，因为那些精心设计的 harness 很可能反而阻碍了新模型发挥能力。

### **写在最后**

2026 年 10 月 22 日同一天，OpenAI 和 Anthropic 各自发布了文章。

OpenAI 的前线部署工程师正在让自己变得不再必需，因为 Codex 能力的提升让他们的很多定制工作变得多余。Anthropic 正在把多智能体折叠回主循环，因为新一代模型在单次循环里就能管理更多事情。

两个团队的终极目标惊人地相似：

> 让架构越来越简练，让模型承担越来越多的工作。

这可能就是当下生产级 Agent 工程的正确打开方式。

当模型能替你做的事越来越多，你的工程架构就应该越来越简单。
