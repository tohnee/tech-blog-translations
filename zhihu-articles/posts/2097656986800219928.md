这是这个系列的第 1 篇，也是第一阶段的导读。

接下来计划每天更新，按“模型与推理链路 → 离线理解与生成 → 推理优化 → 实时视频 → 多机集群”的顺序展开。每篇围绕一个具体问题，把相关论文、代码和实验连起来。第一周先弄清视觉 token、模型接口、时间编码和一次推理的计算过程，后面再深入缓存、并行与调度。

今天先沿着 Qwen2.5-VL 和 StreamingVLM 看一个问题：模型已经能理解一段视频，为什么让它一直看下去，还需要专门做研究？

看一段录好的比赛，我们可以先抽帧，再问模型“刚才发生了什么”。换成直播解说，下一秒画面马上要来，模型既要接着上一句说，又不能越看越慢。

先看视频怎样进入模型。

Qwen2.5-VL 会把画面转成视觉 token，再交给语言模型。空间上，视觉编码器以 14×14 的 patch 处理图像，随后合并相邻的四个 patch；视频还把相邻两帧组成一个时间单元。[1]

这些数字看起来是实现细节，却直接决定了推理成本。假设预处理后的每帧是 560×560，每秒采样两帧：一帧在空间上得到 40×40 个 patch，经过 2×2 合并后，对应 20×20 个位置；两帧组成一个时间单元，于是每秒约有 400 个视觉 token。这里忽略了特殊 token，也假设尺寸和帧数满足对齐要求。

如果长宽同时翻倍，视觉 token 数约变成四倍。提高分辨率的开销因此不只落在视觉编码器上，还会传到语言模型的输入处理和历史状态中。至于总耗时增加多少，仍要测，不能直接把 token 的倍数当成耗时的倍数。

视频还多了时间间隔的问题。相邻两张图，可能相隔半秒，也可能相隔五秒。Qwen2.5-VL 把时间位置与真实时间对齐，并用动态帧率训练，让模型有依据区分这些情况。[1]

不过，“这张画面发生在什么时候”还没有回答另一件事：新画面到来时，上一轮算过的东西怎么处理？

假设直播助手每秒回答一次，每次重新提交最近十六秒的视频。沿用前面的设置，一次窗口约有 6400 个视觉 token，其中真正新增的只有 400 个。如果每轮都从头处理，大部分输入都在重复计算。

这只是一个朴素调用方式的例子，不是在说 Qwen2.5-VL 不能接视频流，也不能据此宣称存在十六倍加速空间。实际重复多少，要看视觉特征、输入前缀和语言模型状态各自有没有复用。[2]

最自然的想法是把旧状态缓存起来。

视觉特征可以缓存，语言模型也可以通过 KV cache 保留历史注意力状态，让新增 token 读取已经算过的 key 和 value。可直播没有固定终点：一直保留，缓存会持续增长；定期全部清空，上下文又会断掉。

问题到这里就具体了：哪些状态值得留，应该留多久？

StreamingVLM 正是从 Qwen2.5-VL-7B-Instruct 微调而来，研究持续输入时的状态管理。它为不同内容设置不同的保留范围：开头的一部分 token 作为 attention sinks 保留，近期视觉状态用于理解连续动作，文本历史则覆盖更长时间。[3]

可以把它理解成：眼前的画面保留得更细，较早的事情更多通过已有文字延续。但文字不会无损保存被删除画面里的每一个细节。系统能够持续运行，并不意味着随时都能准确回忆任意久以前的画面。

只改缓存规则还不够。

如果训练时模型能依赖完整上下文，推理时却不断删除旧视觉信息，它能使用的证据就发生了变化。StreamingVLM 因而同时调整训练：使用带重叠的短视频片段，将视觉与文本交错组织，并限制带入的历史文本，使训练中的可见上下文近似持续推理的情况。它还处理了缓存滑动后的位置编号问题。[3][4]

这里值得留意的是，训练与推理的配合也是方案的一部分。不能把所有效果都归到“多留了一点 KV”，更不能假设给任意模型加上同一套淘汰规则，就会得到相同结果。

把两篇连起来，研究问题就从输入表示走到了持续状态：Qwen2.5-VL 帮我们理解画面怎样成为 token、空间和时间怎样进入模型；StreamingVLM 继续处理这些 token 不断到来之后，历史计算如何复用、模型如何在有限上下文下接着输出。

下一步的实验也可以沿这条线设计。用同一段视频、相同采样率和输出预算，对比重复窗口处理与状态复用，记录输入处理时间、KV 大小和事件到描述的延迟。同时检查跨窗口动作是否讲对、已经消失的对象是否被错误地继续描述。涉及不同权重和训练数据时，还需要相应消融，才能区分状态管理与模型能力的贡献。

这部分目前是论文阅读和实验设计，尚未进行个人复现。等单路直播中的重复计算和历史保留测清楚，再讨论多路并发与集群调度，我们才知道需要搬运什么状态，以及调度应该保护哪一段延迟。
