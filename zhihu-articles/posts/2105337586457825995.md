> 一句话：以后改接口会提前在版本号上打招呼。第一位数字不动，你原来写的代码就不用改。

2026 年 11 月 13 日，本地跑模型的圈子里刷了一条消息：**llama.cpp 和 ggml 同步发布 v1.0.0**。

评论区一半在庆祝，一半在懵：我服务跑得好好的，要跟着升吗？启动命令要重写吗？

先把心放回肚子里：**这次发的不是新功能，是一份「规矩」。** 而且对大多数自己跑 `llama-server` 的人来说，你那条启动命令基本一个字都不用改。

这篇 5 分钟能读完，回答三个问题：**1.0.0 到底立了什么规矩、你的启动命令要不要改、现在到底要不要升。** 急着改命令的，直接拉到第四、五节。

### 一、先认识这两个名字

- **llama.cpp**：负责把 GGUF 模型跑起来，你敲的 `llama-server`、`llama-cli` 就是它。
- **ggml**：它底下负责算数的张量库。

两层同一天一起定版，不是凑巧：上层要稳，下层也得稳。平时它藏在 Ollama、LM Studio 和大量本地应用的背后，这块地基一稳，整个本地 AI 生态都跟着受益。

### 顺带解开一个最容易绕晕的点：两套编号

- **`v1.0.0`**：正式版本标签，承载「兼容承诺」——包管理器、源码编译认它。
- **`b12359`**：第 12359 次构建，预编译二进制实际挂在这里。

官方 `v1.0.0` 那个 GitHub 发布页**本身不带安装包**，附件只有一个 `nightly-tag.txt`，里面写着 `b12359`；你下载到的二进制 `--version` 会报 `1.0.0-dev (build 12359, commit b1b770d)`。那个 `-dev` 不是「不算数」，是 nightly 构建的正常后缀。

**记一句就够：下载认 b 号，判断「会不会改坏」看 v 号——v 号回答「从这份起开始讲规矩」，b 号回答「我下到的是哪份文件」。**

---

### 二、版本号三档，这次真正的新东西

以前版本号就是流水号，升一次级像开盲盒：会不会编译不过、会不会加载就崩，全看运气。

从 1.0.0 起，官方把规则写死了：

- **`1.x → 2.0.0`（破坏接口：删函数、改名字、改结构）**：停下来读说明、改代码、排期迁移。
- **`1.0.0 → 1.1.0`（加新功能：新模型、新后端、新增参数）**：放心升，原来的用法照常。
- **`1.0.0 → 1.0.1`（修 bug，不动接口）**：最省心，正常合。

所以那句被传得最多的话是这么来的：

> **第一位没动，你原来写的代码就不用改。**

这也是「锁定 1.x」终于有了意义的原因——以前写 `>=1.0.0, <2.0.0` 是自我安慰，现在它是能挡住破坏性升级的闸门。

![](https://pic3.zhimg.com/v2-c94eae6383d462815c4732ffeae4e206_r.jpg)

### 两个别误读的地方

**1. 1.0 ≠ 接口冻结。** 恰恰相反：因为破坏性改动今后必须老老实实反映到版本号，维护者明说过，**以后主版本可能跳得比过去更勤**。稳下来的不是代码，是「变化必须提前挂牌」。

**2. 规矩管得比想象中窄。** 它保的是 `include/` 目录下的**公共 C API**。命令行参数、`llama-server` 的 HTTP 行为、Web UI 并不在这张表里。所以自建服务仍然该钉死具体版本、每次升级先试一遍，别看到「1.x」就无脑拉最新。

---

### 三、那 1.0.0 当天到底改了啥

一句话：**先把攒了三年半的旧账清干净，再立规矩。**

- `llama.h` 删掉 35 个废弃函数、`llama_set_warmup`
- 命令行删掉 `--defrag-thold`（短写 `-dt`）
- NextN 推测解码接口从 `llama-ext.h` 并进 `llama.h`，`clip.h` 并入 `mtmd`
- 动态库 soname 从 `libllama.so.0` 变成 `.so.1`
- ggml 同步清理废弃 API，RPC 协议升到 v9

看明白没：**「契约从今天生效」，但起点这一刀本身就是破坏性的。** 上面这些主要冲着写 C/C++、写语言绑定的开发者去；对敲命令跑服务的人，真正会疼的只有 `--defrag-thold` 那一条。

### 四、重点：你的启动命令要改吗

先给结论：下面这条，**五个参数全部保留，原样能跑**。

```bash
llama-server -m /models/qwen.gguf --host 0.0.0.0 --port 8080 -c 32768 -ngl 35
```

### 只有三种情况要动

**① 脚本里还带 `--defrag-thold` / `-dt` → 删掉**

老版本遇到它只是打一行弃用警告、照常启动；1.0 直接 `error: invalid argument` 退出。容器要是配了自动重启，就是「我什么都没改，服务却无限崩」。

更阴的是环境变量 `LLAMA_ARG_DEFRAG_THOLD`：**不报错、静默失效**。写在 docker-compose 里看起来一切正常，其实已经不起作用了。升级前搜一遍：

```bash
grep -rn 'defrag' /etc/systemd/system ./compose* 2>/dev/null
```

**② 服务挂在局域网、还开着工具 / MCP → 补一个密钥**

以前只警告，现在绑 `0.0.0.0` + 开工具 + 没设密钥，直接拒绝启动。三种解法：加 `--api-key`（推荐）、绑回 `127.0.0.1`、或显式加 `--allow-unauthenticated-tools`（只建议完全隔离的实验网）。

**③ 会读 NAS / 内网图片 → 放行**

加 `--media-allow-private-urls`。只在本机自己用、不开工具、不读内网图，这一项也不用加。

### 升级前后，直接复制

```bash
# 升级前（带旧参数，新版会崩）
llama-server -m /models/qwen.gguf --host 0.0.0.0 --port 8080 -c 32768 -ngl 35 --defrag-thold 0.1

# 升级后 · 本机自用、不开工具 → 只删旧参数
llama-server -m /models/qwen.gguf --host 0.0.0.0 --port 8080 -c 32768 -ngl 35

# 升级后 · 局域网 + 开工具/MCP → 多补一个密钥
llama-server -m /models/qwen.gguf --host 0.0.0.0 --port 8080 -c 32768 -ngl 35 --api-key 你的密钥
```

顺手能加、但**不必加**的：长对话显存吃紧可以试 `-ctk f8_e4m3 -ctv f8_e4m3`（KV 缓存相对 16 位约减半，建议先用自己的提示词对比一下回答质量）。另外如果你是从很久以前的 nightly 直接跳上来，记得显式写 `--port`——不同时期 nightly 的默认端口有差异（当前官方文档写的是 9931），显式指定就不受影响。

### 五、到底要不要升

自查只要一条命令：

```bash
llama-server --version
# 看 build 后面那个数字
# ≥ 12359 → 1.0 的内容已经全在，不用动
# < 12359 → 还在旧版，再看下面
```

**三句话决策：**

- **跑得好好的、只在本机自己用 → 别升。** 1.0 不提速，收益是「以后升级可预期」，对正在跑的服务没有即时好处。
- **服务挂在 NAS / 局域网、别的设备会来调 → 建议升**，顺手补了几个安全默认值；升之前把上面两处参数处理好。
- **想用新模型、长对话省显存、小显存跑大 MoE → 想升再升**，不急。

真要升，三条纪律：

1. **先在测试机试一遍**：能启动、带图正常、工具调用还能用，再动主力机。
2. **别用 `latest` 这种滚动标签**，钉完整 tag，例如 `server-cuda-v1.0.0-b12359-b1b770d`。
3. **留一个可回滚的旧镜像**；删容器前确认模型目录是 bind mount，别用匿名卷。

> 顺带一句：用 Ollama、LM Studio 这类封装工具的朋友，底层引擎由它们自己挑版本、自己适配，这次完全不用动手。

### 收口

**这次发的是「规矩」，不是「新功能」。**

版本号从流水号变成一句承诺：破坏接口升第一位，加功能升第二位，修 bug 升第三位。第一位不动，你的集成照常工作。

对你手上那条命令来说，最常见的场景浓缩成一句：**把 `--defrag-thold` 删掉，其余照跑**——挂局域网开工具、要读内网图的，按第四节的另外两种情况补参数。

三句话带走：

1. **看版本**：v 号是承诺，b 号是文件，下载认 b 号。
2. **改命令**：删掉 `--defrag-thold`，局域网开工具补 `--api-key`。
3. **定升级**：本机自用不急升，挂局域网的按第四、五节处理完再升。
