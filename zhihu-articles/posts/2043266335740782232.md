上周去了趟 MLSys，见到了许多代码极强的同学。

我发现，做 SYS 的人基本已经不看自己的代码，纯用 coding agent 了。

其中一个同学给我展示了他的工作流。

他打开手机，点开 Telegram，用豆包输入法发了一段语音。

豆包转成文字之后，发送给远端的 Claude Code。

Claude Code 就开始系统重构了。

我很惊讶，我说，“你难道不怕 AI 的代码写错吗？”

他笑了笑，说，“AI 的代码写得比我好多了。”

“那你又如何确定 AI 写的正是你所让他写的东西呢？”

他说，“我直接问他就好了，让 Coding Agent report 给我，他都干了些什么。”

我很诧异。

又问了会场许多人，几乎都是类似的回答，说“不管是系统重构还是写 kernel，LM 都已经做得很好了。”

听完这些话，我感到十分焦虑。

我深刻地理解，能否自动化自己的工作流，是决定程序员水平的至关重要的条件之一。

然而，除了极少数如前端的工作，我都不敢让 LM 自己写代码，而都要用 Cursor 肉眼看一看，才好放心。

当然也有例外。

譬如我见到一个搞 robotics 的哥们儿，他就不用 Claude Code 或者 Codex，而是只用 Cursor Agent。

据说曾两周烧了他老板一万五千刀。

回到公司，问身边 ML 人，也都还在肉眼读代码。

于是我便好奇起其中的缘故。

从常理出发，SYS 代码的难度远远高于 ML 代码。

为了追求极致优化，SYS 同学往往需要使用很底层的语言，如各种 DSL、CUDA，甚至于直接用 PTX 编程。

其 instruction set 的繁琐，以及对硬件计算机运行原理的要求都很高。

相比之下，我们大部分时候也就写写 PyTorch。

语言简洁且抽象，相对好编程，同时对性能追求也没那么高。

反正 torch.compile 能加速多少加多少，加不了就算了。

然而，对于 LLM 来说，这似乎不是决定难易程度的最重要因素。

更重要的是可验证性。

我们拿 kernel 优化来举例。

Kernel 优化还是相对好验证的。

对于任意一个 kernel，我们总可以生成一堆 test case，跑一跑，与未优化的代码如 PyTorch 实现对精度。

同时，kernel 质量的好坏也好衡量。

只需要跑一下，等几秒，拿到平均执行速度。

将此流程接入一个 auto research 的循环，大语言模型就可以自动优化了，完全不需要人类的参与。

相比之下，ML 炼丹可就难验证多了。

当你有一个 bug 时，如某个数值精度设置错了，或者加法乘法的计算换了顺序，你根本不会收到报错。

因为此代码在模型眼中是可执行的，你总不能把模型改成编译器。

你也不会很明显地发现问题。

它唯一的体现可能只是 loss curve 下降稍微慢了一点，或者 gradient norm 稍微大了一点。

甚至说，loss 都不一定更高啊。

毕竟炼丹作为纯玄学，犯了错反而涨点的事情，到处都是。

在这种情况，模型根本无从验证自己的行为，又如何自主进化呢？

以上只讨论了 test time。

对于后训练，可验证性的影响更甚。

自 o1 开始，推理模型的胜利已经告诉我们，凡可验证的任务都可以大规模跑强化学习。

模型公司如 OpenAI 或者 Anthropic，只需要搭一个环境沙盒，设置好所有验证的条件，就让模型跑着去吧。

模型可以尝试几百次几千次，只要有一次成功，它就可以增强这条轨迹的概率，更新自己的权重，于是越来越强。

近年来 coding agent 的进步足以说明这一点。

然而不可验证的项目，实在没有简单的规模化的办法。

于是今天的模型在对话写作等方面，反而可能比过去更差。

总之，ML 与 SYS 的差别，又是 Moravec's paradox 的体现之一。

SYS 难，反而更好被取代。

ML 容易，却可以多苟活一阵。

看来我要比你们晚失业六个月了！
