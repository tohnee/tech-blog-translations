## 推理两阶段：Prefill和Decode

1. 预填充（Prefill）阶段：**对完整的输入prompt进行一次性并行计算**，为每一个token生成并缓存键（Key）和值（Value）向量（即KV cache）。**这一步只需运行一次**，缓存内容将用于后续的生成步骤；
2. 解码（Decode）阶段：**模型以自回归方式逐步生成新 token**。每一轮仅需计算当前要生成的 token，并与此前缓存的 KV （包括用户查询和已经生成的token）进行注意力计算，从而避免对整个历史序列重复计算，显著降低了计算量。

### Prefill阶段

- Token 化：输入为批大小为batch_size的若干prompt，每个 prompt 被处理为长度为 seq_len 的 Token 序列。
- 嵌入层：这些Token序列会被映射为隐藏向量 X，其形状为 (batch_size, seq_len, hidden_dim)。
- **线性映射**：通过权重矩阵W_Q, W_K, W_V（形状为(hidden_dim，num_heads * head_dim)），分别计算得到Q, K, V，并重塑为(batch_size, num_heads, seq_len, head_dim)
- KV cache缓存：**计算得到的K 和 V 矩阵会被缓存下来**，供后续解码阶段使用。
- **注意力计算**
- 生成第一个token：在工程实践中，为减少一次显存读写和前向传播开销，通常会直接利用 prompt 最后一个位置的 hidden state来生成第一个token。

Prefill阶段是高度**并行**的，能够充分利用 GPU 的算力资源，因此属于 **compute-bound**（计算受限），瓶颈在于算力而非内存。

### Decode阶段

- 输入准备：使用prefill阶段已经计算并存储的KV cache，以及当前轮刚生成的 token（第一次decode时，是prefill阶段生成的第一个token）。
- 嵌入层：在第 t 步，将新生成的 token 转换为嵌入向量，计算得到Qt, Kt, Vt，并将Kt, Vt更新到KV cache中。
- **计算注意力**：基于Qt和现有的KV cache进行注意力计算，计算复杂度为O(seq_len)，相比prefill阶段大幅降低。
- 生成下一个token：将最后一层的注意力输出经过线性层和softmax，得到下一个token的概率分布，并根据解码策略（如greedy search、beam search）选出下一个token，作为下一次decode的输入。

Decode阶段是典型的**通信密集型**任务，主要受限于显存带宽。因为生成一条回复通常需要多次decode，每次都需要访问和更新KV cache。随着生成内容长度的增加，KV cache也会越来越大，对GPU内存带宽的压力也随之增大。

| 对比项 | Prefill 阶段 | Decode 阶段 |
| --- | --- | --- |
| 主要功能 | 一次性并行处理完整输入序列，计算并缓存 Key/Value，用于后续生成首个及所有后续 token | 每次只生成一个新 token，利用缓存的 Key/Value，生成新输出并持续更新缓存 |
| 计算类型 | 全序列自注意力计算，高度并行、计算密集型 | 增量式注意力计算，串行生成、通信密集型 |
| GPU 利用率 | 充分利用算力资源，能高度并行，效率高 | 并行度低，通常是小批量或单 token 操作，GPU 利用率较低 |
| 计算复杂度 | O(seq_len²) | O(seq_len) |
| KV Cache 管理 | 不依赖缓存，直接基于原始输入并行计算，构建并缓存所有 prompt 的 KV cache | 每步都查 KV cache，利用其计算注意力，并将新 token 的 K_t, V_t 持续追加到缓存中 |

**llm推理为什么需要kv cache，怎么计算kvcache大小，如何管理kvcache？**

KV cache是推理阶段最常用的缓存机制，用空间换时间。 通过使用KV cache，避免了对之前token的重复计算，加速模型推理速度。

KV cache的形状为 [batch_size, head_num, seq_len, head_dim]

Cache显存 = 2×层数×批大小×序列长×隐藏层维度×精度字节（第一个 2：是Key和Value两个缓存张量）

序列长度指需要缓存的长度，等于**Prompt 的长度加上已经生成的 Token 数量**

- 这种与序列长度成正比的显存增长，是制约大模型走向更长上下文的核心瓶颈之一。
- 传统推理系统通常采用**预分配**策略：请求开始时，就按最大可能生成的长度（如 2048 token）为每个请求分配一整块连续内存空间。这种方式带来显著的内存浪费，产生许多碎片
- 在 Parallel Sampling等复杂推理模式中，一个请求可能包含多个生成分支（如多个候选答案），这些分支共享相同的 prompt，因此理论上可以共享其 KV Cache。但传统系统将每个分支的 KV Cache 存放在独立的连续内存中，物理上无法实现共享，只能进行冗余复制，进而显著增加了内存开销。

因此催生了 PagedAttention，KV Cache 量化，滑动窗口注意力等一系列关键的推理优化技术。

需要注意：

- 模型有n层，例如7b的llama3有32层，所以k v cache的尺寸的第一个维度就是 第几层，然后才是后面的[batch_size,head,seq_len,hidden size]。
- 模型在prefill的时候生成整个prompt的k和v，到了decode的时候，对于每个层先加载第i个layer的k和v，然后拼接起来，随着decode越来越多，kv cache只是在seq_len维度上增大了，之前的内容都没有变。
- layer级别的kv cache transfer是比较好的方式，可以避免一次性传输整个kv cache，因为相比起gpu的高速传输，cpu的PCIE带宽会变成传输瓶颈。（PD分离）

## **vLLM**

VLLM 是一个用于LLM推理的高性能库，适用于需要快速响应和高吞吐量的大规模应用场景。

**解决了什么问题**

答：memory waste，vllm解决了下列三种memory waste：

1. 预留Token：传统推理会给每个request预留kv cache需要使用的memory，因为LLM本身无法确定这个请求会产生多少token，所以会按照固定的长度预留。
2. 内部碎片：系统通常也会以“块”为单位进行分配，而不是单个 token；一个sequence长度300 ，系统会分配 2 个块（共 512 个 token 的容量），第二个块中就有212 个 token 的位置wasted。
3. 外部碎片：每个请求使用的块大小不一样，memory在切割时会产生一些外部碎片，这些碎片可能不足以再分给一个新的请求。

![](https://pic4.zhimg.com/v2-87189b557a9312a942e6c0fb40753d33_r.jpg)
*PagedAttention 原文 Figure3：3种memory waste 图解*

### **解决方案**

vllm基于PagedAttention算法，通过“分页”机制，替代传统的“预先分配连续最大内存”策略，来减少内存碎片。

1. **解决预留Token：不再为Sequence预分配整个生命周期的内存**。系统维护一个全局的物理块池。Sequence只在需要时才申请新的物理块。
2. **解决内部碎片：将 KV Cache 存储在固定大小的块中**。一个Sequence的 KV Cache 可以分布在多个非连续的物理块中。最后一个块的未用空间就是内部碎片，但由于块大小固定且相对较小（如16个token），这种浪费被控制在了很低水平。
3. **解决外部碎片：由于Sequence可以使用非连续的物理块，系统只需维护一个全局的空闲物理块列表。**任何新请求都可以从列表中获得任意空闲块，而无需寻找连续空间。这从根本上消除了外部碎片。

注意：vllm是把waste控制在很低的水平，不是100% none waste，可以看这张图，对比了vllm和传统推理的waste水平：

## 核心组件

### 1-Paged Attention

在OS中，虚拟内存将程序的地址空间划分为固定大小的“页”（Page），这些页可以映射到物理内存中任意位置，实现**非连续分配**，从而有效解决了内存碎片和共享问题。<br>PagedAttention 将这一思路引入 KV Cache 的管理中，并带来了 3 项关键改进：

1. **KV Cache 被切分为固定大小的 block**：将每个序列的 KV Cache 切分为固定大小的 block（默认是 16 个 token），每个 block 存储若干个 token 的 Key 和 Value 向量。这种设计统一了内存分配粒度，使系统能够以更标准化的方式管理 KV Cache 的分配与回收，从而提升内存复用效率，并有效减少内存碎片。
2. **block 可以存放在非连续的物理内存中**：与传统的 Attention 不同，PagedAttention 不再要求这些 KV 向量在内存中连续排列，而是通过逻辑 block 与物理 block 的映射，实现非连续存储。映射关系由 block table 维护，它类似于操作系统中的页表，用于记录每个逻辑 block 对应的物理内存位置，确保模型在推理过程中可以正确读取所需的 KV Cache。
3. **支持灵活的分配与释放，以及共享机制**：PagedAttention 支持按需分配和回收 block，并允许多个序列共享 block。PagedAttention 使用了 copy-on-write（CoW）机制，允许多个生成样本共享大部分输入 prompt 的 KV Cache，只有当某个分支需要写入新 token 的 KV 数据时，系统才会将相关 block 复制到新的物理位置，从而在保证数据隔离的同时极大地节省显存资源，提升推理效率与吞吐量。

![](https://pic1.zhimg.com/v2-1cb426c248004030c0b434b3ec402ac6_r.jpg)

每个逻辑块仅在前一个块被填满后才会分配新的物理块，从而最大程度地减少内存浪费。<br>**在计算时我们操作的是逻辑块**，也就是说，这些 token 在形式上是连续排列的；与此同时，vLLM 会通过 block table 映射关系，在后台将逻辑块映射到实际的物理块，从而完成数据的读取与计算。<br>通过这种方式，每个请求仿佛都在一个连续且充足的内存空间中运行，尽管这些数据在物理内存中实际上是非连续存储的。（虚拟内存）

### 2-continuous batching

continuous batching可以实现数倍乃至数十倍的系统吞吐提升，被各大框架广泛使用。<br>他的提出主要解决三类问题：

- **对Early-finished Requests的处理：**一个batch中会有不同的请求，每个请求所生成的文本长度不一致，这就导致了在一个batch中，生成短文本的请求得等生成长文本的请求结束后整个才结束，造成了时间浪费。所以需要一个将**已生成结束的请求从batch中移除并提前返回结果**的机制，以此来降低服务响应时间。
- **对Late-joining Requests的处理：**同第一点，有提前走的，就有进来的，就需要一个将**新请求插入推理batch**的机制
- **多个请求合并到一次attention计算：**每个请求对应的QKV Tensor的Length维度各不相同，在批量计算Attention时，需要处理此问题。

## 高级特性

主要会聚焦于：

- 分块预填充(chunked prefill)
- 前缀缓存(Prefix caching)

上面两个特性聚焦于prefill阶段，会与continuous batching和kv cache深度结合。<br>下面的特性会聚焦在decoding阶段

- 引导编码(guided decoding)
- 推理编码(speculative decoding)
- PD分离(prefill/decoding分离)

### 1-chunked prefill

分块预填充是一种**处理长提示词的技术**，主要在prefill阶段将一个长请求进行分块处理，可以让其他prefill请求有机会插入执行。<br>

![](https://pic2.zhimg.com/v2-f9910ef2bccb0d9910ee98f03b5b38e1_r.jpg)

因为预填充（Prefill）的本质是对提示词的所有 token 执行一次完整前向传播，属于**计算密集型任务**（计算量随提示词长度线性增长）。当遇到超长提示词（如数百甚至数千 token）时：

- 单次预填充会占用 GPU 大量计算资源，且执行时间极长；
- 在此期间，引擎无法处理其他请求（尤其是短提示词请求），造成 “资源闲置” 与 “请求排队拥堵” 的双重问题；
- 短请求的等待时间（Latency）会急剧增加，破坏服务的响应性（如对话场景中用户等待过久）。<br><br>将prefill拆分成多个子块，并与其它请求的decode一起执行，这种方式能够有效地降低资源空泡，提升整体的资源利用率。<br>特性的实现：在推理框架中，主要改动点是调度器(Scheduler)的逻辑，保证多次分块的prefill请求能够衔接起来。<br>调度器的输出格式：{请求序号：tokens数量}<br>通过控制每个请求本轮需要计算的tokens数量，实现任意chunk大小的组合下发。

### 2-Prefix Caching

前缀缓存是一种避免重复计算多请求共享前缀token的技术<br>比如多个prompt在开头包含相同的“长前缀”时候，只需要在prefill阶段计算一次这个前缀的KV Cache，后续就无需重复执行前缀的prefill步骤<br>这里的 “长前缀” 定义为：**长度超过一个 KV 缓存块**（默认 16 个 token）的前缀。若前缀长度未对齐缓存块边界（即 `long_prefix_len % block_size != 0`），则未对齐的部分（余数 token）仍需重新计算，因为无法缓存不完整的 KV 块。<br>在实际场景中，多个请求共享长前缀的情况极为常见：

- 对话场景：所有请求均包含相同的 “系统提示”（如 “你是一个 AI 助手，需遵循安全准则回答”）；
- 批量处理场景：多个任务的输入包含相同的指令前缀（如 “总结以下文本：”）。

所以prefix的缓存极为重要。

vLLM 中前缀缓存的实现依赖 “**哈希匹配” 与 “KV 块关联”** 两大核心逻辑，具体分为以下步骤（以代码示例中两次 `generate` 调用为例）：<br>**步骤一：第一次generate，无缓存计算并存储前缀**

- 首先通过hash_request_token()计算前缀的哈希值。按KV 块的大小将long_prefix+prompt[0]的token ID列表拆分为多个完整块。对每个块，组合“前一个块的哈希值、当前块的 token ID、可选元数据” 生成唯一的hash；将每个块的hash值和token ID封装成BlockHash对象，存入哈希列表
- 通过find_longest_cache_hit()检查缓存命中。查询已经缓存哈希表，判断是否有匹配的。因为是第一次生成的结果，所以是返回空，如下图

![](https://pic2.zhimg.com/v2-6a371b08e98af3c58ecf16cd36a884e9_r.jpg)

- 通过之前提到的allocate_slots()为当前请求分块KV Cache块，并通过coordinator.cache_blocks()将BlockHash对象与分配的KV块ID绑定，记录到map映射中

![](https://pic3.zhimg.com/v2-563786c173c99c85d5eaa50ddd64ff6a_r.jpg)

- 执行prefill

**步骤二：第二次generate，有缓存，复用前缀的KV块**

- 对 `long_prefix + prompts[1]` 执行相同的 token 拆分与块哈希计算，得到与第一次生成相同的 “前缀块哈希列表”（因 `long_prefix` 相同）。
- 这时候调用find_longest_cache_hit()缓存命中匹配，就直接返回匹配的KV块ID列表
- 所以就不用对long_prefix再分配和计算KV，再看第一次请求是否完成（因为有continous batching和chunk prefill），如果完成，就重新标记“已占用”；如果还在运行第一次请求，就将块的引用计数+1，确保块不被释放。
- 仅prefill新的token，并复用前缀的KV块，进行前向传播

![](https://pic4.zhimg.com/v2-c44278fa55e5f61b814bebd4a83abef1_r.jpg)

### 3-Speculative Decoding 投机采样

vLLM 中的投机采样是一种强大的技术，通过同时利用小型和大型模型来加速token生成。

示例代码：

```text
from vllm import LLM, SamplingParams

prompts = [
    "Hello, my name is",
    "The president of the United States is",
]

sampling_params = SamplingParams(temperature=0.8, top_p=0.95)

speculative_config={
    "method": "ngram",
    "prompt_lookup_max": 5,
    "prompt_lookup_min": 3,
    "num_speculative_tokens": 3,
}

def main():
    llm = LLM(model="TinyLlama/TinyLlama-1.1B-Chat-v1.0", speculative_config=speculative_config)

    outputs = llm.generate(prompts, sampling_params)

if __name__ == "__main__":
    main()
```

**步骤一：初始化与模型加载**<br>创建一个候选模型**（drafter）**（这里是n-gram）和一个**拒绝采样器（rejection_sampler）**（其部分逻辑由 Triton 框架编写实现）。<br>加载候选模型权重 —— 对于 n-gram 而言，此步骤为**无操作（no-op）**<br>**步骤二：大模型prefill，用于奠定上下文基础**<br>例如一个prompt：Hello, my <br>对其进行完整前向传播，生成对应的KV Cache以及下一个token<br>**步骤三：n-gram生成并存储候选token**

- 通过`allocate_slots`函数根据 “候选 token 数量” 计算所需 KV 块数量，从`free_block_queue`（空闲块队列）中预留，避免后续前向传播时显存不足。

### 4-PD分离

接下来就是目前大模型推理中最重要的部分，PD分离<br>它是 vLLM 中一种**将 “预填充（Prefill）” 和 “解码（Decoding）” 两种任务从资源层面分离**的优化架构 —— 通过将 GPU 集群划分为 “预填充专用 GPU 组” 和 “解码专用 GPU 组”，让两类任务在独立资源上并行执行，避免相互争抢资源，最终提升整体系统的吞吐量与稳定性。

- 因为Prefill和decoding是用的同一套GPU，所以会出现资源争抢问题，当一批长提示词的预填充任务占用 GPU 计算单元时，解码任务会因 “等待计算资源” 导致延迟飙升；反之，大量解码任务占用显存带宽时，预填充任务会因 “带宽不足” 变慢，最终两类任务相互拖累。
- 耦合架构中，GPU 需同时适配 “计算密集” 和 “带宽密集” 两种负载，但单 GPU 的计算能力与带宽能力无法同时被充分利用 —— 例如，预填充时带宽闲置，解码时计算单元闲置。
- 实际服务中，解码任务往往需要更低延迟（如对话场景中用户等待下一个 token 的时间），而预填充任务可接受稍高延迟。但耦合架构中，高优先级的解码任务可能被低优先级的长提示词预填充任务阻塞。

所以PD分离可以尽可能的针对不同任务压榨GPU利用率的方法。<br>在实际应用中，一般会部署N个 vLLM prefill实例和M个 vLLM decoding实例，并根据实时请求的混合比例（如预填充请求与解码请求的数量占比）对它们进行自动扩缩容。其中，预填充实例会将生成的 KV 缓存写入**专用 KV 缓存服务**，而解码实例则从该服务中读取 KV 缓存，这样就可以将Prefll和decoding两个阶段分离开。<br>这个实例间KV缓存服务一般是使用SharedStorageConnector 或 LMCache实现，用于传递KV Cache。我们的示例代码使用SharedStorageConnector。

启动了2个vLLM实例，一个运行在GPU0，用于prefill，一个运行在GPU1，用于decoding。

```text
import os
import time
from multiprocessing import Event, Process
import multiprocessing as mp

from vllm import LLM, SamplingParams
from vllm.config import KVTransferConfig

prompts = [
    "Hello, my name is",
    "The president of the United States is",
]

def run_prefill(prefill_done):
  os.environ["CUDA_VISIBLE_DEVICES"] = "0"

  sampling_params = SamplingParams(temperature=0, top_p=0.95, max_tokens=1)

  ktc=KVTransferConfig(
      kv_connector="SharedStorageConnector",
      kv_role="kv_both",
      kv_connector_extra_config={"shared_storage_path": "local_storage"},
  )

  llm = LLM(model="TinyLlama/TinyLlama-1.1B-Chat-v1.0", kv_transfer_config=ktc)
  llm.generate(prompts, sampling_params)

  prefill_done.set()  # notify decode instance that KV cache is ready

  # To keep the prefill node running in case the decode node is not done;
  # otherwise, the script might exit prematurely, causing incomplete decoding.
  try:
      while True:
          time.sleep(1)
  except KeyboardInterrupt:
      print("Script stopped by user.")

def run_decode(prefill_done):
  os.environ["CUDA_VISIBLE_DEVICES"] = "1"

  sampling_params = SamplingParams(temperature=0, top_p=0.95)

  ktc=KVTransferConfig(
      kv_connector="SharedStorageConnector",
      kv_role="kv_both",
      kv_connector_extra_config={"shared_storage_path": "local_storage"},
  )

  llm = LLM(model="TinyLlama/TinyLlama-1.1B-Chat-v1.0", kv_transfer_config=ktc)

  prefill_done.wait()  # block waiting for KV cache from prefill instance

  # Internally it'll first fetch KV cache before starting the decoding loop
  outputs = llm.generate(prompts, sampling_params)

if __name__ == "__main__":
  prefill_done = Event()
  prefill_process = Process(target=run_prefill, args=(prefill_done,))
  decode_process = Process(target=run_decode, args=(prefill_done,))

  prefill_process.start()
  decode_process.start()

  decode_process.join()
  prefill_process.terminate()
```

**步骤一：connector实例化，在Engine构造阶段**<br>在Engine初始化的时候，connector会在两个时刻创建：

- 在Worker初始化过程中，worker负责实际的KV Cache读写操作
- Scheduler构造函数中，scheduler负责协调KV Cache的传输逻辑（如触发传输、记录缓存状态）

**步骤二：在调度阶段进行KV Cache查找**<br>当调度器从“等待队列（waiting queue）” 中处理prefill请求时（在完成本地prefix cache检查后），会调用connector的`get_num_new_matched_tokens`方法 —— 该方法会检查**外部 KV 缓存服务**中是否存在已缓存的 token。

- 对prefill请求：此处返回值始终为 0（预填充的作用是生成初始 KV，无需读取外部缓存）。
- 对decoding请求：若存在缓存命中（即预填充已生成对应 KV），则返回命中的 token 数量。

最终，该返回值会与本地缓存计数叠加，再调用`allocate_slots`（KV 缓存块分配函数）。

**步骤三：prefill的GPU组执行前向传播**

1. 对prompt执行完整prefill前向传播，生成提示词对应的 KV 缓存（键值对）；
2. prefill完成后，不执行任何decoding步骤，而是将 “请求元数据 + KV 缓存” 打包为 “prefill结果包”；
3. 通过connector，将 “prefill结果包” 传递到decoding的 GPU 组的 “KV 缓存接收缓冲区”；
4. prefill的 GPU 释放该请求的资源，立即接收下一个prefill请求（最大化计算单元利用率）。

**步骤四：decoding的 GPU 组接管并执行解码任务**

1. decoding 调度器将请求从 “KV 缓存接收缓冲区” 转移到 “decoding等待队列”；
2. 从decoding的 GPU 组中选取空闲 GPU，将传递来的 KV Cache加载到该 GPU 的显存中；
3. 执行传统的自回归解码步骤（每次生成 1 个 token，利用显存带宽优势），直至满足停止条件（如生成 EOS token）；
4. 解码完成后，将生成结果返回给用户，并释放该 GPU 的 KV Cache资源。

<br>**步骤五：动态负载均衡（运行时优化）**<br>Engine运行过程中，负载均衡器（Load Balancer）会实时监控两组 GPU 的资源利用率：

- 若prefill的 GPU 组长期满负荷（计算单元占用率 > 90%），且decoding的GPU 组有闲置资源，会临时将 1 个decoding的 GPU切换为prefill的GPU，补充计算能力；
- 同样的若decoding的 GPU 组长期满负荷（显存带宽占用率 > 90%），且prefill的 GPU 组有闲置资源，会临时将 1 个prefill的 GPU切换为decoding的 GPU，补充带宽能力；
- 资源切换仅需重新加载模型副本（无需重启引擎），实现动态适配负载变化。

P/D分离是 vLLM 针对 “大规模、高并发 LLM 推理服务” 设计的核心架构优化 —— 它通过 “任务与资源的精准匹配”，在有限硬件资源下实现了 “更高吞吐量” 与 “更稳延迟” 的双重目标。

### 5-Fast model execution with CUDA/HIP graph

在对Decoder架构的大型语言模型进行推理时，计算分为两个阶段：

1. **Prefill阶段**：处理输入的提示（prompt）。
2. **增量生成阶段**：逐个生成输出的token。

当batch size或者输入长度足够大时，prefill阶段会处理大量token，GPU的性能成为瓶颈，CPU的开销对性能影响不大。<br>而增量生成阶段，每次生成只处理一个token（序列长度为1），且batch size通常很小（甚至为1，比如交互式使用场景），这时CPU的速度可能成为限制因素，因此增量生成非常适合用**CUDA图**来优化。<br>CUDA图的一个限制是需要固定的输入形状（fixed shapes）。增量生成的序列长度固定为1，但**计算注意力时，涉及到所有已经生成的token，也就是序列长度会随着每步递增，这个长度对应存储在KV缓存（KV-cache）中**。<br>**vLLM**使用pagedAttention通过一层间接索引（level of indirection）管理KV缓存地址

- KV缓存的地址是“间接索引”的，base地址固定
- 变化的只是**block_tables**（一个记录token到cache页映射的小型索引表），可以通过**padding使其尺寸固定**
- 所有需要变化的部分都变成了“输入数据”，而非“Tensor形状”，这样就能安全录入CUDA图
- 更小的运行开销、更高的吞吐

通过torch.cuda.graph()上下文录制推理流程，之后复用replay接口调用CUDA图，省去了CPU到GPU多次调度和内核启动开销，极大提升了推理速度。

### 6-Optimized CUDA kernels, including integration with FlashAttention and FlashInfer

FlashAttention-2: Faster Attention with Better Parallelism and Work Partitioning：重点讨论了如何在序列维度（Sequence Length）上进行任务划分。

Flash Decoding 正是利用了论文中提到的“对序列维度进行切分并行”的思想，解决了 Decode 阶段 GPU 利用率低的问题。是 FlashAttention 团队针对 LLM 推理（Decode 阶段）专门推出的一种并行加速技术，核心思想是**把序列维度（KV Cache）切开，让多个 GPU 核心并行计算。**<br>[https://crfm.stanford.edu/2023/10/12/flashdecoding.html](https://crfm.stanford.edu/2023/10/12/flashdecoding.html)<br><br>具体步骤如下：

1. **切分（Split）：** 将漫长的 KV Cache 分成若干个较小的 **Blocks**（例如每块 128 或 256 个 Token）。
2. **并行计算（Parallel Compute）：**GPU 启动多个线程块，**同时**计算Q与每个KV块的局部 Attention 结果。<br>每个块会产出两个值：**局部加权和（P）** 和 **Log-Sum-Exp（L，用于归一化的中间值）**。
3. **归约（Reduction）：**最后增加一个极小的步骤，将所有块的局部结果进行合并。

- 利用 L 对各个块的 P 进行重新加权，得到最终的 Attention Output。
