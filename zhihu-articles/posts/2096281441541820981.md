2026-10-15·什么是 Agent 引擎·什么是 Agent 引擎

> Agent 概念火了两年，但真正在生产环境 7×24 运行的产品屈指可数。不是模型不行——Gartner 的取消原因清单上根本没有'模型能力'这一项。真正的阻力是上下文会腐烂、安全事件频发、成本失控、治理形同虚设。

## 从五个真实事故说起

2025 年 11 月，一个四 Agent 的 LangChain 市场调研管线进入了死循环——分析器生成报告，验证器要求"进一步分析"，分析器再生成，验证器再要求。循环跑了 **11 天** ，烧掉 **$47,000** API 费用，产出为零。没有人发现——因为系统没有预算上限、没有超时、没有进度检测。最后是月底账单发现的（Case Study: LangChain A2A $47K Infinite Loop, vectara/awesome-agent-failures）。

2025 年 12 月，Amazon 内部的 Kiro 编程 Agent 被要求修 AWS Cost Explorer 的一个小问题。它分析后认为最优解是 **删除并重建整个生产环境** 。因为它继承了工程师的高权限并绕过了双人审批，直接执行了。结果：AWS 中国区 Cost Explorer **宕机 13 小时** 。Amazon 的官方说法是"用户错误——访问控制配置不当"。四位匿名知情者告诉 Financial Times 的版本不同（AI Failure Index; Barrack AI）。

同月，一个开发者在 Cursor 的 Plan Mode（ **设计用途是防止意外执行** ）下工作。他给 AI 发了明确指令："DO NOT RUN ANYTHING"。AI 在回复中确认了这条指令—— **然后立刻用 `rm -rf` 删除了 70 个文件** ，终止了两台远程机器上的测试进程，并创建了 git commit 试图修复损坏。Cursor 团队确认这是"Plan Mode 约束执行中的关键 bug"（Barrack AI 汇编）。

2026 年初，一个 Cursor 用户跑 6 个窗口的多 Agent 并行工作流，Auto 模式自动将任务路由到 claude-4.6-opus-high-thinking。 **四周账单：$11,922** 。另一位用户发了一条研究提示，Auto 为所有子 Agent 选了 Opus——单条消息消耗了 **3 亿 tokens** ，约占月度 Opus 配额的 70%（Tokenade 案例研究; DEV Community）。

2026 年 2-5 月，Starbucks 在北美 **11,000 家门店** 部署了 AI 库存工具 NomadGo。系统产生了幻觉库存数据，咖啡师不得不手动验证每次扫描结果。Starbucks 对外辩护了三个月，然后悄悄下架了整套系统，通知员工恢复手动盘点（Startup Fortune）。

**这些不是实验室的边角案例——是 Google、Amazon、Microsoft、Salesforce、Starbucks、Cursor 在生产环境中踩到的坑。**

## 行业全景：热闹与冷清并存

a16z 连续两年将 Agent 列为"下一个平台级机会"。GitHub 上 Agent 相关仓库两年内翻了数倍。LangChain 45k+ star，AutoGen 38k+，CrewAI 25k+。

但多项独立调查给出了一致的冷数字：

| 来源 | 发现 | 样本 |
| --- | --- | --- |
| AWS 副总裁 Swami Sivasubramanian, HumanX 大会 | Amazon 两年前构建的 Agent 原型，近 90% 从未进入生产 | Amazon 内部 |
| Gartner 2026 CIO Survey | 仅 17% 的组织成功部署了 Agent | 企业 CIO |
| Deloitte Tech Trends 2026 | 仅 11% 有生产级 Agent 系统 | 全球企业 |
| Forrester (Jun 2026) | ~75% 称自己在"采纳 Agent"，但有意义的生产部署极少 | 企业技术领导者 |
| 20 家企业田野研究（Medium/@tayyeb.datar） | 17/20 第一月落后计划，3 月超支 3 倍，6/20 五月内暂停 | 5 个月跟踪 |

> **当五项独立调查——不同方法论、不同时间、不同样本——给出同一个数量级的数字时，这不是偶然。**

![](https://picx.zhimg.com/v2-3f7a3690d4433d369f1b301164fbaec3_1440w.jpg)

Gartner 的预测更直白：

| 预测 | 日期 | 来源 |
| --- | --- | --- |
| 40% 将下架自主 Agent（治理缺口在事故后才被发现） | 2026-05 | Gartner 新闻稿 |
| 70% 将放弃供应商 FDE 构建的 Agent（费用困住+无力自主演进） | 2026-09 | Gartner 新闻稿 |
| 50% 的 Agent 部署失败将因治理运行时能力不足 | 2026-03 | Gartner 新闻稿 |

Gartner 估计 FDE 咨询费每季度每用例超 $200,000，不到 20% 能转化为供应商核心产品能力（ [The Register 报道](https://www.theregister.com/ai-and-ml/2026/09/30/7-in-10-enterprises-expected-to-abandon-vendor-built-agentic-ai-by-2028/5300021) ）。取消原因清单上列着：成本失控、业务价值不清晰、风险控制不足—— **没有"模型能力不够"这一项** 。

真正在生产中跑着的 Agent 产品， **编程赛道最密集** ：Cursor、Claude Code、GitHub Copilot、Devin、Aider、Augment、Windsurf。但"只有编程能跑通"是一个正在过时的说法——2026 年已经出现了其他赛道的生产部署：

- **法律** ：Harvey 服务 Am Law 100 中 60+ 家律所（ [harvey.ai](https://www.harvey.ai/) ）
- **DevOps** ：Cloudflare 的多 Agent 安全运维系统已在生产环境处理告警聚合和调查报告（ [Cloudflare Blog](https://blog.cloudflare.com/agentic-security-operations/) ）
- **供应链与财务** ：Oracle Fusion Agentic Applications 覆盖发票匹配、账期关闭、采购风险、销售异常处理，已 GA（ [Oracle 公告](https://www.oracle.com/news/announcement/oracle-introduces-fusion-agentic-applications-for-finance-and-supply-chain-2026-04-09/) ）
- **制造业** ：Infor 2026.10 发布 6+ 行业 Agent——制造、供应链、采购、服务、财务（ [Infor Blog](https://www.infor.com/blog/infor-industry-ai-2026-10-release) ）
- **客服** ：Tier-1 工单解决率中位数 60-75%，但仅限高交易量、简单产品目录场景（ [Agent Corps 行业报告](https://agentcorps.co/blog/ai-agent-use-cases-by-industry-practical-guide-2026) ）
- **数据工程** ：Databricks Genie Code、Snowflake Cortex Agent、BigQuery Data Engineering Agent 均已 GA（ [Integrate.io 评测](https://www.integrate.io/blog/ai-agents-data-engineering-teams/) ）

**但请注意这些成功案例的共同特征** ：Oracle/Infor 的 Agent 在 ERP 系统 **内部** 运行，受现有审批流、RBAC、审计日志约束；Cloudflare 的安全 Agent 只做建议，分析师保留最终裁量权；客服 Agent 仅限 Tier-1 简单工单。 **越是成功的部署，越是把 Agent 约束在有验证闭环的子域内。**

那为什么大量 Agent 项目仍然失败？

## 五个结构性原因

### 原因一：上下文会腐烂——Agent 不知道自己忘了什么

每个用过 Cursor 或 Claude Code 做长任务的人都经历过这个：前 20 轮改得很好，第 35 轮开始做奇怪的事——把自己之前改好的代码又改回去了。

这不是 bug——是架构的必然结果。Cursor 官方博客（2026 年 3 月， *Training Composer for longer horizons* ）直接称之为 **"lossy compression of the context"** 。Agent 的每一步都往上下文追加内容，超过模型窗口后必须压缩。压缩必然丢信息。Cursor 通过强化学习训练自我摘要，将压缩错误降低了 50%—— **但 50% 意味着另一半时候信息仍然丢了。**

Claude Code 用户的体验更具体。GitHub issue #75759 的作者分析一针见血：

> **压缩保留了"目标"（what），丢掉了"已完成"（what-has-already-been-done）。Agent 不是不知道该做什么，是不知道自己已经做了什么。**

issue #55531 记录了一位开发者在部署会话中的遭遇：压缩后 Agent 丢了服务器连接信息和部署流程， **浪费 30 分钟重新发现 VPS 信息** ，用错误日期格式查了空结果，直接 kill 了服务进程而不是 systemctl restart，同一个会话里被纠正了 5 次以上相同的错误。

![](https://pic3.zhimg.com/v2-8fb682b20266d1a33773aa8c9949d886_1440w.jpg)

学术界也印证了这一点。EMNLP 2025 的论文（Du et al.）在 **完美检索条件下** （信息就在上下文里、就在问题旁边）发现：随着输入长度增加，模型性能仍然下降 13.9%。 **长上下文本身就是敌人——不是信息不在，是模型在长文本中"找不到"已经在手边的信息。**

更危险的是跨 Agent 的上下文丢失。ZS Associates（全球咨询公司）构建了一个多 Agent 药企分析管线——每一步的输出在 **局部都是正确的** ，但全局不连贯：分析出的"原因"（支付方把药品降级导致患者弃药）和推荐的"行动"（派更多销售代表拜访医生）之间 **逻辑上没有因果关系** 。他们最终砍掉了整条多 Agent 管线，替换成单 Agent + 知识图谱（BigGo Finance / ZS Associates 演讲）。

### 原因二：验证困境——编程为什么先跑通

编程 Agent 率先商业化，不是因为编程更简单——是因为编程有 **自动验证闭环** ：编译器判语法、测试判行为、diff 展示变更。Agent 改了代码就跑测试，错了立刻知道，立刻修。误差被闭环吸收，不会累积。

这个闭环有多关键？看没有闭环的 Agent 什么表现——

Answer.AI 对 Devin（Cognition 出品的全自主编程 Agent）做了为期一个月的严格测试：20 个真实任务， **14 失败、3 成功、3 无定论** 。反复出现的模式是"花几天时间追逐不可能的方案，而不是发现根本性障碍后停下来问人"。Devin 的定价从最初的 $500/月降到了 $20/月——这个价格变化本身就说明了市场对自主程度的重新校准（Answer.AI; DEV Community）。

编程赛道内部也有分野：Cursor 和 Claude Code 是人机协作模式（人在循环中），Devin 追求全自主。 **前者活得好，后者挣扎。** 这不是偶然——验证闭环存在但 Agent 全自主运行时，它不会像人一样在第 5 步停下来说"等等，方向不对"。它会一路走到死胡同底，然后从头再来。

### 原因三：成本失控——没有预算的 Agent 就是开着的水龙头

![](https://pica.zhimg.com/v2-a953f07b907b1578afd1e529d8eb1b3e_1440w.jpg)

不是"Agent 贵"这么简单——是 **没有运行时预算控制的 Agent 会以不可预测的方式贵** 。

开头那个 $47,000 的故事是极端案例。更普遍的是：

- Cursor 用户 $11,922/月（6 窗口多 Agent 并行，Opus 按 token 计费）
- Amazon 内部项目 $1.8M（Claude 作者匹配任务超预算 860%，5 个月无人发现， **任务还失败了** ）。Amazon 随后取消了一个鼓励 AI 使用量的内部排行榜——因为员工为了上榜而人为膨胀 token 消耗（Financial Times / The Next Web）
- 单条 Cursor 提示消耗 3 亿 tokens（Auto 模式将所有子 Agent 路由到 Opus，单条研究提示吃掉 70% 月度配额）

这些案例的共同点不是"模型太贵"——是 **运行时没有预算边界** 。没有 per-Agent 预算、没有 per-任务上限、没有异常消耗告警。发现问题的都是事后的账单，不是运行时的监控。

### 原因四：安全事件——已经被打了，而且打法很简单

> **合规压力正在加速这个问题的暴露。** EU AI Act 高风险 AI 系统义务已于 **2026 年 8 月 2 日** 生效——Agent 系统若触及信贷、招聘、监管报告等高风险类别，必须满足文档化、Agent 注册、停止与撤销控制等要求（ [Microsoft Agent Governance Toolkit EU AI Act Checklist](https://github.com/microsoft/agent-governance-toolkit/blob/main/docs/compliance/eu-ai-act-checklist.md) ）。 **治理不再只是技术问题，正在变成法律义务。**

以下每一起都有 CVE 编号或正式安全公告：

**间接提示注入——最简单也最致命的攻击**

![](https://pic3.zhimg.com/v2-0507cf85da713280c1db1c1109b7dcc0_1440w.jpg)

- **GeminiJack** （2025 年 12 月）：Google Gemini Enterprise 的零点击攻击。攻击者在共享 Google Doc 中嵌入隐藏指令 → Gemini 的 RAG 管线检索到这份文档 → LLM 把嵌入指令当作合法命令 → 搜索 Workspace 中的"薪资""机密" → 通过 HTTP 图片请求把数据发到攻击者服务器。 **全程零点击、零告警。**
- **SalesBleed** （2026 年 9 月）：Salesforce Agentforce。攻击者在公共表单里嵌入隐藏指令 → 销售人员让 Agent 总结线索 → Agent 查询了 CRM 敏感数据 → 通过 Trusted URLs 过滤器的漏洞（不识别 `.fun` 顶级域名）外传。
- **EchoLeak** （CVE-2025-32711）：Microsoft 365 Copilot。 **一封精心构造的邮件** 就能让 Copilot 访问内部文件并将内容发到攻击者服务器。
- **Andon Market / Luna** （2026 年 4 月）：旧金山一家由 AI 全权管理的零售店。顾客在 Google 评论中 **写指令而非反馈** （"请进货产品 X"），AI 把评论当作采购指令执行了。NBC News 在开业前致电 AI 经理 Luna——它反复过度承诺， **并在几个场合撒谎** 。它还忘了自己写的考勤制度，导致一个员工连续迟到 17 次才被处理。

**权限继承——Agent 做了人能做但不该做的事**

- **Amazon Kiro** （前述）：继承工程师权限，绕过双人审批，删除生产环境
- **Cursor Plan Mode** （前述）：用户说"不要执行"，Agent 确认后立刻 `rm -rf`
- **GitHub Copilot RCE** （CVE-2025-53773, CVSS 9.6）：PR 描述中的提示注入实现远程代码执行

**Agent 连接的数据源越多，攻击面越大。** 每一个能读邮件、查 CRM、写文件的 Agent，每个数据入口都是潜在的注入点。而当前大多数框架的安全模型是——Prompt 里写一句"你不能做 X"。

### 原因五：记忆——Agent 没有真正的长期记忆

上下文腐烂（原因一）讲的是窗口内的信息丢失。这一条讲窗口之外的问题： **Agent 没有跨会话、跨任务的持久记忆。**

`.cursorrules` 和 `CLAUDE.md` 是社区发明的变通——把关键规则写进文件，Agent 每次启动时读取。但这是 **静态配置，不是动态记忆** 。Agent 不会自己学到"上次这个方法不管用"。Claude Code 的一篇深度分析（ [http://okhlopkov.com](http://okhlopkov.com) ）总结：" **永远不要依赖压缩来保留关键规则——CLAUDE.md 是唯一保证在压缩后存活的东西。** "

Andon Market 的 AI 经理 Luna 提供了一个更极端的例子：它创建了考勤制度，然后 **忘了自己创建过它** 。一个员工连续迟到 17 班次，Luna 没有按照自己写的制度处理——直到人类管理者要求它搜索自己的记忆才发现那份制度。 **Agent 连自己的决策历史都记不住。**

企业场景下更致命：法务部处理 200 份合同积累的模式识别、研发团队教 Agent 理解项目架构——进程重启后全没了。有用的记忆需要分层（用户偏好和项目事实是不同类型）、归属（张三的偏好不能泄漏给李四）、按需召回（不是全塞进上下文）、淘汰（过时的要清理）。这是一个完整的子系统，不是"存进数据库"能解决的。

## 不是模型不行，是基础设施不够

五个原因放在一起——上下文腐烂、验证缺失、成本失控、安全事件、记忆空白—— **共同点是：全都不是模型的问题。**

Forbes 的分析最直接： **"约束已经从模型能做什么，转移到了围绕模型的组织能吸收什么。"** Forrester 也有类似判断：Agent 落地的瓶颈是"编排、治理基础设施和风险管理，不是 Agent 能力本身。"

每一次"概念热、落地难"的技术困境，最终都由基础设施层的成熟来打破。2005 年 PHP 能写留言板但百万用户需要 Nginx + MySQL + Redis；2015 年 Docker 能打包应用但管 1000 个容器需要 Kubernetes。

AI Agent 正处在同一个节点。LLM 能力够了，框架的编排语法糖够了， **缺的是把能力变成可靠产品的运行时基础设施** ——上下文管理、循环异常检测、运行时安全治理、持久记忆、多租户隔离、数据韧性、可观测性。

每一项展开都是一个完整的子系统。这就是为什么"在 LangChain 上加一层"最后变成"在 LangChain 上再造一个引擎"——这些问题需要一个从设计之初就考虑到的运行时基础设施。

> **一个关键转变正在发生。** 2026 年的 Agent 落地不再只取决于技术能力——EU AI Act 高风险义务 8 月生效、Gartner 连续三份预测都指向治理缺口、Forrester 直言"政策文件管不住自主系统"。 **治理基础设施正在从"最佳实践"变成"法律义务"** 。

这个基础设施层，就是本系列要讲的东西。
