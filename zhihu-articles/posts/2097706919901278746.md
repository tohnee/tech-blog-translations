从大模型到 AI 芯片系列 第一篇

聊到 AI 芯片，我们很容易先看算力、带宽和片上存储容量。这些指标当然重要，但配多少资源，得先看芯片要跑什么工作：负载长什么样，具体做哪些计算，瓶颈落在哪儿，又该怎么针对性地优化硬件架构。

同样是跑一个语言模型，处理一段输入和逐个生成 token，矩阵形状、数据复用和并行度也完全不是一回事。适合大矩阵的计算阵列，碰上小 batch 的逐 token 生成，未必还能保持同样的利用率。上下文一拉长，原先够用的缓存和带宽也可能变得紧张。

这也是我最近开始研究大模型的原因。做 NPU 架构设计和建模，最后总要把模型映射成芯片能高效执行的工作。

当然，我做这些不是要从芯片设计转去研究模型算法，而是想弄清楚自己设计的硬件到底要服务什么。服务对象不一样，瓶颈的位置也不一样：端侧单用户交互还是云端多请求并发，短对话还是长文档，同一个模型对延迟、吞吐和存储的要求都不同。所以在讨论阵列规模、片上存储和带宽之前，我想先从模型本身出发，看清一次推理到底算了什么、搬了哪些数据。

这个系列先写三篇模型相关的内容。这一篇搭建一个简化的 Dense Decoder，用真实语料跑一次短程训练，再把推理过程和工作负载对应起来；第二篇看 MoE 和 MLA 怎样改变计算与存储需求；第三篇再看具体的 Hybrid Attention 设计。先把模型的执行过程弄清楚，后面再回到硬件：计算阵列怎么组织，片上存储留给哪些数据，KV Cache 怎么访问，数据搬运和计算怎样重叠，矩阵单元与向量单元又该如何配合。以及经常出现的算子比如 Softmax、SiLU 等值不值得做专用加速，也要放到整个模型的执行过程中判断，看看它们究竟是不是瓶颈。

本文会介绍模型结构、短程训练和推理执行，工作负载分析以推理为主。文中的 FLOPs 和缓存容量按配置推导；第五节给出 GPU 推理实测，以及真实中文语料上的 300 步训练和验证损失曲线。训练实验用来观察模型怎样从文本里学习，不代表完整预训练或充分收敛，对齐和强化学习暂时不展开。

## 一 推理路径

语言模型拿到的不是直接编码成浮点数的文字，而是一串 token ID。Tokenizer 负责把文本映射成词表里的整数编号。一个 token 不一定是一个汉字，也不一定是一个完整的单词，怎么切取决于 tokenizer。

拿到 ID 以后，Embedding 从一张可学习的表里取出对应的向量。设 batch 为 B、输入长度为 S、隐藏维度为 H，Embedding 的输出形状就是 [B, S, H]。这些向量经过多层 Decoder Block，最后映射到词表大小 V，得到 [B, S, V] 的 logits。

Logits 是词表里每个候选 token 的未归一化分数。生成时一般只取最后一个位置的 logits，采样或者按别的策略选出一个 token，再把它接回序列。这里的“下一个”不是凭空并行出来的：普通自回归生成里，后一个 token 的输入取决于前一个 token 选了什么。本文不涉及推测解码这类会改变执行流程的方法。

![](https://picx.zhimg.com/v2-05e6230a44cd3ca0394f2d7cb4326ab3_r.jpg)
*图 1 从输入到自回归生成*

从硬件看，这条路径不是一种运算。Embedding 基本是按索引取向量；Decoder 里有大量矩阵乘法，也有归约和逐元素计算；输出投影要把隐藏向量映射到整个词表。就算先不谈芯片实现，光是这几类工作分清楚，也比用一个总 FLOPs 数描述模型有用得多。

下面这套教学配置是本文的算例。它方便拆开看，不代表某个商业模型，也不是 DeepSeek 的缩小复刻。

| 配置项 | 数值 |
| --- | --- |
| Decoder 层数 L | 6 |
| 隐藏维度 H | 768 |
| Query head 数 | 12 |
| 每个 head 的维度 d | 64 |
| FFN 中间维度 I | 2048 |
| 词表大小 V | 50257 |
| 当前最大序列长度 | 512 |

结构上采用 MHA、RoPE、Pre-RMSNorm 和 SwiGLU，输入 Embedding 与输出 LM Head 不共享权重。把线性层的 bias 和 RMSNorm 参数一起算进去，参数量约 1.197 亿。后面的解析算例默认 B=1；用 2 字节估存储，指的是 FP16/BF16 的元素大小，没有算上运行时完整的临时张量和框架开销。

## 二 Decoder Block

Decoder Block 可以先看成两个子层：Attention 让当前位置从可见的历史里取信息，FFN 对每个位置的隐藏向量再做一次变换。本文用 Pre-Norm，归一化放在各子层前面，输出再通过残差连接加回主干。

![](https://picx.zhimg.com/v2-e468e60bc97a647b4ee6940f91d1038b_r.jpg)
*图 2 一个 Pre-Norm Decoder Block*

### Attention 的输入输出

输入 X 先过三个线性投影，得到 Q、K、V。这里 Q/K/V 里的 V 是 Value，和前面表示词表大小的 V 不是一回事，看形状的时候别弄混。

普通 MHA 里，把 head 合并起来，三个投影的形状都是 [B, S, H]；拆开以后是 [B, n_h, S, d]，其中 H = n_h × d。只看单个 head，Attention 的主要计算是：[1]

Q 和 K 点乘得到匹配分数，因果 mask M 把未来位置排除掉，Softmax 再把可见位置的分数归一化。这里的“排除”通常是把对应 logits 置成负无穷，而不是在 Softmax 之后乘个零。归一化后的权重再乘 Value，得到每个 head 的输出；多头拼起来，过一遍输出投影，回到 [B, S, H]。

这几步对硬件的要求并不一样。Q/K/V 和输出投影是线性层；QK 和后面权重乘 Value 是矩阵乘法；Softmax 要做最大值归约、指数、求和归约和归一化。如果矩阵阵列算完以后，要长时间等着这些向量操作或归约，那光看阵列峰值算力，解释不了这个子层花的时间。

### RoPE

模型还得知道每个 token 在第几位。本文用 RoPE，按位置对 Q/K 的二维通道对做旋转，让注意力点积能表达相对位置关系；普通 RoPE 在这一步不旋转 Value。[2]

实现时要把两个约定对齐：哪些通道配成一对，对应的角度怎么排。如果用相邻通道配对，同一对通道必须用同一个角度。旋转以后向量长度不变，这个性质很适合单独验一遍。

这个检查和“带缓存和不带缓存的 logits 是否一致”不是一回事。两条路径要是用了同一个错误的旋转公式，也可能彼此对得上。所以除了代码对齐测试，还得独立核对算子的数学定义。

### RMSNorm 和残差连接

RMSNorm 沿隐藏维度算均方根，再缩放输入、乘上可学习的增益。它不用像 LayerNorm 那样先减均值。[3]

它的运算量一般比不上大矩阵乘法，但要沿 H 维做归约，还得让缩放系数对这一行数据可用。对 NPU 来说，这会牵涉归约路径、数据缓冲和精度安排，不只是逐元素乘法。

残差连接把子层输出加回输入。每一层改的都是同一条隐藏向量主干，不是把所有层的结果无限拼接起来。这也意味着实现时要安排好主干数据的生命周期，不能在子层输出回来之前就把它覆盖掉。

## 三 KV Cache

要是每生成一个 token 都把整个前缀重新送进模型，历史 token 的线性投影、FFN 和 Attention 都得重算一遍。KV Cache 就是为了省掉这部分历史重算。

它成立的前提是因果性。只要模型参数和输入前缀不变、推理过程是确定的，历史位置的隐藏状态就不依赖后面新加进来的 token，各层历史位置算出的 K/V 自然也不用重算。新的 query 直接读缓存就行。

注意缓存是按层存的。第 1 层和第 6 层看到的隐藏状态不一样，算出的 K/V 也不一样，不能整个模型共用一份。用了 RoPE 以后，历史 K 已经按各自位置旋转过，拼新 K 的时候不能再把旧 K 转一遍。

![](https://pica.zhimg.com/v2-e9a55e90964369584e3ed077be13ce4a_r.jpg)
*图 3 一次 Decode 中的缓存读写*

假设缓存里已经有 P 个位置，现在进来一个新 token。新 token 的位置是 P，要算出新的 Q/K/V，再把新的 K/V 写到对应位置。Attention 的 query 长度是 1，key/value 长度是 P+1。它照样要从可见历史里取信息， **缓存并没有让当前 query 对历史的 Attention 计算消失** 。

这也说清了一个常见的误解：KV Cache 省的是历史位置的重复前向，不是把每个新 token 的计算都变成常数。对完整历史做 Attention 时，读的缓存和 QK/PV 的工作量仍然随上下文长度增长。

教学代码里用 torch.cat 把新 K/V 拼到缓存后面，逻辑很直白。但这样通常要分配新张量、复制一遍历史内容，不等于硬件上“只追加一小段”。分析存储流量时，应该把这个软件实现的复制开销和模型本身需要的缓存访问分开看。生产实现还可能用预分配、分页或者别的缓存管理方式。

## 四 Prefill 和 Decode

一次普通的生成，通常先把 prompt 过一遍，这一步叫 Prefill。模型虽然有因果约束，但 prompt 的多个位置可以放进带 mask 的矩阵运算一起算，因为它们的输入 token 已经全都给出了。

Prefill 建好各层的 KV Cache，再用最后一个输入位置的 logits 选出第一个输出 token。之后的 Decode 把新生成的 token 送回模型，每次只算新增的位置，用更新后的历史状态预测下一个 token。

![](https://pic3.zhimg.com/v2-d7d92634ba931d8bc55289593fbd3094_r.jpg)
*图 4 Prefill 与 Decode 的矩阵形状*

所以，如果没有别的提前终止条件，生成 N 个新 token 一般是一次 Prefill 加 N−1 次后续 Decode 前向。最后一个输出 token 选出来以后，如果不需要它的后续 logits 或者更新后的缓存，就没必要再为它多做一次前向。

以线性投影为例，Prefill 里的 X 可以把 batch 和序列维合并成 [B×S, H]；Decode 里每个请求只有一个新增位置，合并后是 [B, H]。B 很小的时候，后者离一个大矩阵乘法差得很远。

这就是小 batch Decode 往往对带宽敏感的原因。但反过来说，也不能认定所有 Decode 都受带宽限制、所有 Prefill 都受算力限制。batch、上下文长度、权重能不能留在片上、算子融合和内存布局都会改变结果；长上下文 Prefill 里，Attention 的计算和数据访问也会明显增加。

放到服务系统里，还得把指标分开看：用户等第一个 token 的时间一般叫 TTFT，除了 Prefill，还可能算上排队、分词和调度；之后每个 token 的间隔反映交互流不流畅；吞吐则要同时说明并发量。只报一个 tokens/s，往往说明不了体验，也说明不了硬件利用得怎么样。

## 五 计算量、存储与实测

为了让讨论有个具体尺度，下面按 B=1、S=512、H=768、I=2048 算单个 Decoder Block 的主要矩阵 FLOPs。Decode 那一列 query 长度是 1，可见的 K/V 长度是 512。

本文把一次乘加算作 2 FLOPs，所以 [M,K] × [K,N] 的矩阵乘法约为 2MKN。这里只统计主要的矩阵乘法，bias、RMSNorm、RoPE、Softmax、SiLU、逐元素乘法、残差和采样都没算进去。

| 单个 Block 的主要矩阵运算 | Prefill FLOPs | 单步 Decode FLOPs |
| --- | --- | --- |
| Q/K/V 三组投影 | 1.812 GFLOPs | 3.539 MFLOPs |
| Attention 的 QK 与 PV | 0.805 GFLOPs | 1.573 MFLOPs |
| Attention 输出投影 | 0.604 GFLOPs | 1.180 MFLOPs |
| SwiGLU 三组投影 | 4.832 GFLOPs | 9.437 MFLOPs |
| 合计 | 8.053 GFLOPs | 15.729 MFLOPs |

Attention 这一项按显式的 dense 乘法计数，被因果 mask 挡住的位置也算进去了。如果 kernel 能跳过因果上三角，实际执行的 FLOPs 会不一样，所以这张表不能当成任意优化实现的实际运算量。

6 个 Block 的 Prefill 主要矩阵计算合计约 48.32 GFLOPs，还没算最后的 LM Head。这里面 FFN 投影的计算量比 QK 和 PV 加起来还大——Attention 更受关注，但不代表其他部分可以从芯片负载里略去。

输出投影也该单独拎出来看。当前 H=768、词表大小 50257，只给最后一个位置算 logits 大约要 77.19 MFLOPs；要是像教学版 forward() 那样给全部 512 个位置都算，就约 39.52 GFLOPs。训练一般需要每个位置的输出，普通生成的 Prefill 则可能只要最后一个位置。两条执行路径，账不一样。

单步 Decode 里，6 个 Block 加一个位置的 LM Head，主要矩阵运算约 171.57 MFLOPs。对这套词表偏大的小模型来说，LM Head 也不是可以随便忽略的收尾。

再看存储。按普通 MHA、每个元素 2 字节估算，512 个位置、各层的 KV Cache 一共 9 MiB；给一个新 token 追加各层 K/V，只要 18 KiB。前者是“已经存着的状态”，后者是“这次新写入的状态”，两笔账不能混着算。

权重也一样，容量和访问量要分开。输入 Embedding 一般按 ID 取行，不是每生成一个 token 就读一遍整张表。如果假设 Decoder 和 LM Head 的投影权重都长期留不到片上、每批 Decode 都得从外存各读一遍，这部分权重约 154.62 MiB。这是一个特定复用假设下的量级估算，不是带宽测量结果，更不能拿整个模型的参数字节数代替每步的访存量。

上面这些数值都能用仓库里的 [估算脚本](https://github.com/Ch1-n/llm-to-ai-chip/blob/main/tools/estimate_workload.py) 重新生成，详细假设记在 [估算数据](https://github.com/Ch1-n/llm-to-ai-chip/blob/main/data/llm-inference/estimates.json) 里。配置、统计范围和单位写清楚了，数字才值得拿出来讨论架构。

### GPU 实测

算完以后，我在一张 RTX 4090 D 24GB 上跑了同一套配置。环境是 PyTorch 2.7.0、CUDA Runtime 12.8，关掉 TF32。先检查 RoPE 的独立旋转性质、因果性和缓存路径，再跑性能测试。

下表是预热 3 次、重复 20 次之后，带 CUDA 同步的墙钟时间中位数。Prefill 输入长度 512；Decode 一次输入一个新位置，连同它算上可见的 KV 长度共 512，历史缓存的建立不计入这一步。推理时把模型权重直接转成对应精度，关掉 dropout，不开自动混合精度。

| 精度与 batch | Prefill 时间 | 单步 Decode 时间 |
| --- | --- | --- |
| FP32 B=1 | 40.65 ms | 34.42 ms |
| BF16 B=1 | 42.51 ms | 34.14 ms |
| FP16 B=1 | 41.19 ms | 34.37 ms |
| FP32 B=12 | 53.58 ms | 35.70 ms |
| BF16 B=12 | 45.37 ms | 39.79 ms |
| FP16 B=12 | 45.85 ms | 36.97 ms |

最值得注意的，是这张表和纯 FLOPs 的比例对不上。教学代码逐个 head 跑 Attention，显式算分数，用 torch.cat 扩缓存，Prefill 还要算所有位置的词表 logits；没用 SDPA、FlashAttention、torch.compile，也没用 CUDA Graph。算子形状变了以后，计算量掉了不少，单步时间却没跟着按比例掉。小算子调度、CPU 发起开销和内存分配都值得用 profiler 再查一查；光看这张表，还分不出各自占多少。

所以这组结果是 **当前教学执行路径的基线，不是 RTX 4090 D 跑这个模型的性能上限** ，也不能拿它判断 BF16 通常是否比 FP32 快。20 次测试仍有波动，原始数据里留了 P10/P90。以后要是合并多头、减少中间张量或者换 kernel，得在同一个数学定义下重新比。

正确性方面，完整模型在 FP32 下，最后一个位置的缓存与完整前向的 logits 最大绝对误差约 2.50e-6；BF16 和 FP16 分别约 0.0239 和 0.00366，本来就不能要求逐 bit 相同。这只是随机权重和测试输入下的数值检查，不代表低精度生成的质量。另外用 B=12、S=512，分别跑 FP32 和 BF16/FP16 AMP 的 3 步 AdamW 训练，loss 和梯度都是有限值；这只验证了前向、反向和更新链路能走通，不代表训练已经收敛。

这次推理基准直接调 forward()，没走原来的 generate()。后者还有多余的额外前向、到了上下文边界就停、过长 prompt 截断这些行为，需要单独整理，所以不能说完整生成接口已经验证无误。详细配置、显存数据和复现方式见 [CUDA 测试记录](https://github.com/Ch1-n/llm-to-ai-chip/blob/main/experiments/cuda-20261025.md) 。

### 中文语料上的短程训练

训练和前面的推理共用同一套模型结构，但执行过程不同。训练时，输入是一段连续的 token，标签是向后错开一个位置的同一段序列，模型要在每个位置预测下一个 token。把各位置的 logits 和标签计算交叉熵损失，再通过反向传播求出参数梯度，交给 AdamW 更新权重。这里没有复用推理阶段的 KV Cache，每个训练块都重新做完整前向；推理则固定权重，只计算输出并维护当前请求的历史状态。

前面的随机输入能检查执行链路，但说明不了模型能不能从文本里学到东西。我又从 [出门问问 Seq-Monkey 中文通用语料](https://github.com/mobvoi/seq-monkey-data) 的第三方镜像里流式取了一个有限子集，去掉规范化后完全相同的文档，再按文档哈希分训练集和验证集。最后得到 2,282 篇训练文档、114 篇验证文档，分别约 426 万和 20 万 token；分词和切块都在划分之后做，同一篇文档的片段没有被随机分到两边。

保持同样的模型配置，用 BF16 AMP、B=12、S=512 训练 300 步，实际处理 1,843,200 个训练 token。每 25 步在固定的 192 个验证块上评估一次，每次 98,304 个 token。曲线见下：灰线是每一步的训练 loss，蓝线是 10 步滑动均值，红点是实际测过的验证点；红点之间的连线只是方便阅读，不代表每一步都做了验证。

![](https://picx.zhimg.com/v2-1ae91b2822c83415a051104370b78545_r.jpg)
*图 5 Seq-Monkey 中文子集上的训练与验证损失*

验证 loss 从 11.00 降到 3.09，最后 25 步训练 loss 的均值是 3.07。跳过前 10 步之后，训练单步耗时中位数约 0.244 秒，大约 2.51 万 token/s；这个吞吐不含周期性验证和 checkpoint 保存。训练循环连同验证和保存一共约 107 秒，peak allocated 显存约 9.84 GiB。

两条曲线都在往下走，说明改善不只发生在当前这个训练 batch 上，但这还证明不了训练已经充分，也证明不了中文生成能力好。这里用的是 GPT-2 tokenizer，中文常常被拆成多个字节级 token，loss 下降里也包含对这些局部结构的学习；这些数值不能直接和用了别的 tokenizer 的模型比。数据只取了镜像里的一段，没做全库随机采样，也没做近似重复检测，更没有独立测试集。Train Loss 开着 dropout，Val Loss 关着，两条曲线之间那点差距不宜直接当成泛化差距。完整来源、学习率和日志见 [300 步训练记录](https://github.com/Ch1-n/llm-to-ai-chip/blob/main/experiments/seq-monkey-300.md) 。

## 六 上下文与并发

对普通的 MHA/GQA，先不管分页元数据、padding 和量化的附加信息，缓存容量可以写成：

最前面的 2 对应 K 和 V；L 是层数，B 是同时保存的序列数，T 是每条序列保存的长度，nKV 是 KV head 数，d 是每个 head 的维度，b 是每个元素的字节数。各请求长度不一样，就把 B×T 换成各请求缓存长度的总和。

MHA 里 KV head 数和 Query head 数相同。GQA 让一组 Query head 共享一份 K/V，省的是缓存的 head 维；MQA 可以看成只留一组 K/V 的特例。[5] 注意，这并不是说所有 Query head 的 Attention 计算也按同样比例减少。

为了看清容量随上下文怎么变，再取一个 **独立的假设配置** ：32 层、32 个 Query head、head dim 128、B=1、每个元素 2 字节。它和前面那个最大长度 512 的教学模型不是一回事，也不代表当前代码已经支持下面的长度。

| 保存的上下文长度 | MHA 的 KV Cache | 8 个 KV head 的 GQA |
| --- | --- | --- |
| 8192 | 4 GiB | 1 GiB |
| 16384 | 8 GiB | 2 GiB |
| 32768 | 16 GiB | 4 GiB |

![](https://pic1.zhimg.com/v2-8b1d1c22130849e3a92849e03378f59e_r.jpg)
*图 6 独立容量算例中的 KV Cache 增长*

这还只是一个请求的缓存。并发一上来，容量继续涨，Decode 读历史状态的方式也跟着变。所以长上下文和高并发不是给同一个模型换两个启动参数，它们改变的是存储和调度要面对的问题。

两类内存也要分开：KV Cache 是跟着序列留下的状态；显式实现里的 Attention score 则可能是 [B, n_h, S, S] 的临时张量，两者的生命周期和增长规律完全不同。

FlashAttention 靠分块和在线 Softmax 之类的办法，减少 HBM 和片上 SRAM 之间的中间数据往返，不用把完整的 score/probability 矩阵都写回外存。它算的仍然是精确的 dense Attention，不是没把整个矩阵落地就变成了稀疏 Attention；这里的“精确”也不要求不同浮点实现逐 bit 一致。[6]

所以看到某段 PyTorch 代码分了一块大张量，应该多问一句：这是模型必须留着的东西，还是当前执行方式产生的中间结果？芯片有时确实要提供这块容量，有时该靠融合和数据流设计，让这块外存分配根本不发生。

## 七 映射到 NPU

到这儿再看矩阵阵列、向量单元、SMEM 和 DMA，它们的分工就具体了。

矩阵阵列要面对的不只是“支持 GEMM”。Prefill 和小 batch Decode 的行数差得很远，阵列怎么切、数据怎么广播、怎么调度，都会影响利用率。权重和激活进片上的顺序、tile 大小、能复用几次，也得和实际的矩阵形状对上。

向量和归约路径要接 RMSNorm、Softmax、激活和逐元素运算。这些未必占多少 FLOPs，却常常夹在前后两个矩阵运算之间。流水能不能一直推下去，看的是它们的吞吐、归约延迟、缓冲组织和精度要求，而不是某个函数“支持”就行。

KV Cache 带来的是另一类状态访问。历史数据要读到 Attention 计算那一侧，新位置的数据要写进对应缓存，长期容量、分页映射和片上暂存是不同层次的问题。就算权重做了低比特量化，KV 状态和其他数据流量也不会自动按同样比例缩小；量化的 scale、反量化和累加精度还得单独安排。

从整体上看，可以先用一个很粗的下界检查数量级：

F 是工作量，P 是相应精度和运算类型下的计算吞吐上限，D 是在已声明的复用假设下必须搬的数据量，BW 是对应存储层级的带宽上限。两项的范围和单位必须一致。

这不是延迟预测公式。算子之间有依赖，通信未必能和计算完全重叠，实际吞吐一般也到不了峰值。尤其不能把峰值 TOPS、对不上的数值精度和随手估出来的外存流量拼在一起，就当成一个可信的模型执行时间。它更适合先用来判断“这个目标是不是明显不可能”，再靠执行图和时序模型往下细化。

具体到仿真，我会先固定模型版本、batch、prompt 长度、生成长度和精度，然后记下每个算子的 shape、执行顺序和数据生命周期，再一步步映射到 Engine 和存储通路。服务场景也要留着：单请求低延迟和批量高吞吐，调度上可能需要不同的取舍。

## 八 下一篇看 MoE 与 MLA

有了这套基线，接下来可以分别动 FFN 和 Attention，看看它们会把前面的计算和存储账本改成什么样。

第二篇先说 MoE 和 MLA。MoE 把不同 token 路由到不同专家，就不能再拿总参数量估每个 token 的计算量了；专家权重的容量、分发与聚合、负载不均、小矩阵利用率，都得重新分析。MLA 用潜在表示压缩历史状态，投影和矩阵吸收怎么安排，会影响 Decode 的计算路径。[7] 两者作用的位置不同，可以同时用，不是二选一。

第三篇再看具体的 Hybrid Attention，计划以 DeepSeek-V4 为对象，结构以固定版本的官方实现和配置为准。[8] 不同路径一旦用上窗口、压缩或稀疏选择，可访问的历史范围、保存方式和检索过程都可能变，不能直接套普通 MHA 的完整缓存公式。对芯片来说，除了看省下多少 Attention 计算，还要看多出来哪些压缩、索引、选择和数据搬运，以及这些工作好不好并行、会不会产生不规则访问。后两篇的实现和实验还没做，本文不给它们的性能结论。

比如说，在 PyTorch 里先把分数全算出来，再把没选中的位置 mask 掉，可以用来核对语义，但不代表硬件已经跳过了这些位置。模型层面说的稀疏、kernel 实际执行的工作量、芯片最后省下的时间，是三件不同的事，要分开验证。

先把一个普通 Decoder 的执行过程看明白，再顺着结构的变化往下走。这样回到芯片设计时，讨论的就不只是“加多少算力”，而是这部分资源能不能服务我们真正要跑的模型和场景。
