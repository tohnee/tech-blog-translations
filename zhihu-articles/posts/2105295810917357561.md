## 手搓 AI Agent 07：会规划 Plan-and-Execute——先拆步骤，再分步执行

第 6 篇让 Agent 有了记忆：短期压缩防止上下文溢出，长期存储跨会话都记得住。但还有一类任务，单靠「想一步做一步」的纯 ReAct 会吃力：任务本身有多个子目标，先后顺序有依赖，做着做着发现某条路走不通。比如「调研某主题，先算一个指标、再检索本地资料、最后汇总成一句话结论」——这种任务，如果让模型边想边做，容易中途迷失、漏掉环节、或者把已经做过的重复做。

这一篇引入**规划（Planning）**：把「规划」与「执行」分开。先用一个轻量规划器把任务拆成有序步骤，再让执行器一步一步做，做完汇总。这个模式叫 **Plan-and-Execute**。

---

### 00 引子：纯 ReAct 在什么情况下会乱

先明确 ReAct 循环（第 2 篇）的强项与弱项：

- **强项**：单轮意图清晰、需要即时调用工具时，反应快、路径直。
- **弱项**：任务一复杂（多子目标、有依赖、需中途纠偏），模型容易在一个循环里「既要又要」——一边想下一步、一边执行、一边总结，注意力被切碎，常常漏步骤或做重复劳动。

核心矛盾是：**思考的「前瞻性」与执行的「即时性」被混在同一圈里**。Plan-and-Execute 把两者拆开——先专门想清楚「要分几步、按什么顺序」，再专门去执行每一步。好处有两个：

1. **透明**：拆出来的步骤清单本身就是一份可检视的计划，人能提前看到 Agent 打算怎么干。
2. **可控**：某一步失败了，只需重规划那一步之后的部分，不必推倒整段推理。

---

### 01 概念：Plan-and-Execute 长什么样

一个典型的 Plan-and-Execute 跑起来是这样：

1. **规划（Plan）**：把任务变成一份有序步骤清单 `{ goal, steps: [...] }`。这一步通常是一次结构化输出（JSON），不是自由文本。
2. **执行（Execute）**：遍历每一步，每一步单独跑一遍 ReAct 子循环（该调工具就调工具），产出这一步的结果。
3. **合成（Synthesize）**：所有步骤跑完后，把各步结果汇总成面向总体目标的最终答复。
4. **（进阶）重规划（Replan）**：某一步在预算内没跑通，基于「已完成步骤 + 失败原因」重规划剩余步骤，再继续。

注意第 2 步的「执行」复用了第 2 篇就写好的 ReAct 循环——规划不推翻已有内核，只是把循环**包了一层调度**。这一点决定了本篇的改动量很小、且不会破坏之前的测试。

---

### 02 为什么用「结构化输出」而不是自然语言计划

规划器要产出一份机器能直接遍历的步骤清单。如果让模型用自然语言写计划（「首先……其次……」），解析起来很不可靠：编号可能缺失、措辞可能跑偏、还可能把计划塞进一段寒暄里。

更稳的做法是要求模型**只输出 JSON**，并配合 OpenAI / DeepSeek 都支持的 `response_format: { type: "json_object" }` 模式（下文简称 json_mode）双保险。但模型偶尔仍会在 JSON 前后多嘴，所以解析侧再补一层容错：在文本里抠出第一个 `{...}` 块再 `JSON.parse`。这样即便模型嘴瓢，也能拿到计划。

```ts
// src/llm/LLMClient.ts —— 仅在有 jsonMode 时附加 response_format
if (options.jsonMode) body.response_format = { type: "json_object" };

```

### 03 实现：Planner（规划器）

规划器只依赖 `LLMClient.chat`（非流式文本），不碰工具、不碰循环。它做两件事：首次规划、失败重规划。

`src/planning/Planner.ts`（节选）：

```ts
export class Planner {
  constructor(
    private readonly client: LLMClient,
    private readonly options: { jsonMode?: boolean } = {},
  ) {}

  async createPlan(task: string): Promise<Plan> {
    const messages: Message[] = [
      { role: "system", content: PLAN_SYSTEM },           // 要求只输出 JSON
      { role: "user", content: `任务：${task}\n\n请把它拆解成若干有序步骤。` },
    ];
    const raw = await this.client.chat(messages, {
      jsonMode: this.options.jsonMode,
      temperature: 0.3,                                   // 规划要稳，温度调低
    });
    return parsePlan(raw, "createPlan");
  }

  async revisePlan(
    goal: string,
    doneSteps: StepResult[],
    failedStep: string,
    reason: string,
  ): Promise<Plan> {
    // 把「已完成步骤 + 失败步骤 + 原因」喂给模型，让它规划剩余步骤
    const messages: Message[] = [/* … */];
    return parsePlan(await this.client.chat(messages, { jsonMode: this.options.jsonMode }), "revisePlan");
  }
}

```

`parsePlan` 是容错关键：

```ts
function parsePlan(raw: string, who: string): Plan {
  const text = raw.trim();
  let jsonStr = text;
  const start = text.indexOf("{");
  const end = text.lastIndexOf("}");
  if (start >= 0 && end > start) jsonStr = text.slice(start, end + 1); // 抠 {...} 块
  const data = JSON.parse(jsonStr);                                    // 失败则抛错
  const parsed = PlanSchema.safeParse(data);                            // Zod 校验结构
  if (!parsed.success) throw new Error(`Planner.${who}: 计划结构不符合预期 ${parsed.error.message}`);
  if (parsed.data.steps.length === 0) throw new Error(`Planner.${who}: 计划不能为空`);
  return parsed.data;
}

```

`PlanSchema` 用 Zod 定义：`{ goal: string, steps: string[] }`。Zod 在这里既是「结构校验」也是「文档」——模型该输出什么形状，一眼就能看明白。

### 04 实现：Agent.runPlan（把规划接进循环）

第 2 篇的 ReAct 循环原本直接挂在 `run()` 上。本篇先把它**抽成一个私有方法 `runLoop(messages, budget, currentUserInput)`**，让 `run()` 和 `runPlan()` 共用同一份循环逻辑。`runLoop` 的入参从「写死 `this.conversation`」改成「接收一个消息数组」，这样每一步执行都能用**独立**的消息数组，互不污染。

`runPlan` 的主干（节选）：

```ts
async runPlan(task: string): Promise<PlanRunResult> {
  if (!this.planner) throw new Error("Agent 未配置 planner，无法执行规划模式");
  const plan = await this.planner.createPlan(task);
  const stepResults: StepResult[] = [];
  let steps = [...plan.steps];
  let revisions = 0;
  let i = 0;

  while (i < steps.length) {
    const step = steps[i]!;
    // 每一步用独立消息数组跑 ReAct：前一步的对话不会泄漏进这一步
    const stepMessages: Message[] = [
      { role: "system", content: this.systemPrompt + STEP_GUIDANCE },
      { role: "user", content:
        `总体目标：${plan.goal}\n\n当前执行第 ${i + 1}/${steps.length} 步：${step}\n\n` +
        `请专注完成这一步，最后用一段话总结这一步的成果。` },
    ];
    const { answer, converged } = await this.runLoop(stepMessages, this.maxSteps, step);

    if (!converged && revisions < this.maxReplans) {
      // 这一步没跑通：先重规划剩余步骤，再把失败步记进结果便于追溯
      const revised = await this.planner.revisePlan(plan.goal, stepResults, step, answer);
      stepResults.push({ step, result: answer, done: false });
      steps = [...steps.slice(0, i), ...revised.steps];
      revisions++;
      continue;
    }
    stepResults.push({ step, result: answer, done: converged });
    i++;
  }

  // 终步合成：用中性系统提示把各步结果汇总成最终答复（避免诱导模型误发工具调用）
  const finalAnswer = await this.client.chat([/* 总体目标 + 各步结果 */]);
  return { plan, stepResults, revisions, answer: finalAnswer };
}

```

三个工程要点：

1. **步骤隔离**：每个 `stepMessages` 都是新数组，`runLoop` 只在它上面增删消息。做完一步，下一步重新从 `system + 这一步的任务` 起步，前一步的工具观察不会堆进下一步——这正是「分步」比「一锅炖」干净的地方。
2. **长期记忆 / 短期压缩仍在**：`runLoop` 内部照旧走 `buildContext`，所以每一步的上下文里依旧能注入相关记忆、依旧会在超阈值时被压缩。规划是「外层调度」，不剥夺内层能力。
3. **终步合成用中性提示**：合成阶段只做汇总，不该再让模型惦记工具，否则它会把 `remember` 之类的调用以文本形式漏进最终答复（实测 DeepSeek 在带工具说明的提示下会这么干）。换成中性提示后，最终答复干净。

---

### 05 失败重规划：执行偏离时的纠偏

纯 ReAct 一旦卡在某个工具调用上，只能干等预算耗尽。Plan-and-Execute 的纠偏更聪明：`runLoop` 返回 `converged` 标志（在预算内收敛为 `true`，撞上 `maxSteps` 为 `false`）。当某步 `converged === false` 且还有重规划额度（`maxReplans`，默认 1），就调用 `revisePlan`，把「已完成步骤 + 失败步骤 + 原因」交给规划器，让它重新规划**剩余**步骤，替换掉当前步及之后的部分，再回到循环继续。

这个设计的边界很清楚：重规划次数有上限，绝不会无限重来；额度用尽后，失败步会被如实标记为 `done: false` 但仍计入结果，合成阶段能看到「哪一步没跑通」。

`Agent` 构造函数新增两个可选参数：`planner` 与 `maxReplans`。不传 `planner` 时 `runPlan` 直接抛错提示，而 `run`（纯 ReAct）完全不受影响——所有旧测试继续有效。

### 08 坑与权衡

- **规划也会错**：规划器可能漏步骤、把一步拆得过碎、或拆出模型实际执行不了的步骤。生产里应在计划产出后做一次校验（步骤是否可执行、是否与可用工具匹配），再进入执行。
- **重规划的成本**：每次重规划都是一次额外 LLM 调用，且要把「已完成步骤」全文喂回去，token 不便宜。额度（`maxReplans`）要设小，避免泥潭。
- **步骤间状态传递靠文本**：本篇把「已完成步骤的产出」以文本塞进下一步的 user 消息。步骤一多，这段文本会膨胀，迟早要配第 6 篇的短期压缩——好在内层已经接好了。
- **不是所有任务都该规划**：一句话能解决的事，强行规划反而绕远。真实系统通常让模型先判断「这事要不要规划」，再决定走 `run` 还是 `runPlan`。这一点留作后续优化。
- **结构化解析要容错**：即便开了 json_mode，也要抠 `{...}` 兜底 + Zod 校验，否则一次嘴瓢就整段崩溃。

### 09 小结与下一步

本篇在 ReAct 循环之上叠加了 **Plan-and-Execute**：用 `Planner` 把任务拆成有序步骤（JSON 模式 + 容错解析），用 `runPlan` 让每一步独立跑一遍 ReAct 子循环（可调用工具），最后由中性提示做终步合成；某步在预算内没跑通时，有限次 `revisePlan` 重规划剩余步骤。规划器与执行器通过组合接入，`Agent` 内核循环零改动，`post-06` 的全部测试继续有效，并新增 8 例规划测试。

下一步（第 8 篇）要解决的是：**当单个 Agent 的能力或上下文不够时，怎么把它拆成多个各司其职的 Agent 协同完成**。也就是多 Agent 协作——规划负责「不乱」，协作负责「不孤」。
