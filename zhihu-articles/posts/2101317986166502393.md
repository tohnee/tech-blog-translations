## 写在前面

好久好久没更新了。要找客观原因的话能扯出一大堆，比如家庭和工作上的各种变故；但归根结底就是因为我失去了讲话的欲望。

自从写完那本推荐算法书之后，我基本就处于封笔状态，既不想写文章，也没什么兴致去拆解推荐领域的论文。一方面是以前写文章得罪过人，惹了些不大不小的麻烦——最夸张的时候，甚至有老师顾忌人情世故，不敢给我的书写推荐序。另一方面，当时对推荐算法确实产生了一种生理性的厌倦，觉得自己看穿了这行所有的套路，太阳底下再无新鲜事。

现在回看第二个原因，只能嘲笑自己当年真是 *Too young, too naive*。我的书问世之后，随着LLM杀入推荐领域，这行还是迎来了天翻地覆的变化。不过就连写出《历史的终结》那种“鸿篇巨制”的弗朗西斯·福山，最近不也改口认错了吗？如今这世界局势，哪有一点“历史终结”的意思，分明是“乱纪元”刚刚拉开序幕。连大师都会看走眼，我当年觉得“**推荐算法历史已经终结**”，虽然幼稚，倒也情有可原。

在闭嘴的这几年里，我也没闲着，一直在暗中观察和学习LLM的各种进展，并在一线亲自下场做实验，尝试复现那些大厂论文里吹得神乎其神的基于LLM的推荐算法。刚接触那会儿，隔着一层薄纱，我也曾有过惊叹和羡慕，觉得自己还没摸透，不敢乱说话。但经过这几年在泥潭里的摸爬滚打、踩坑复现，沉淀了足够多的亲身体会后，我那股“不吐不快”的冲动又压不住了。教员说过，“没有调查就没有发言权”。既然现在有了点实打实的调查和体感，我觉得自己终于可以再站出来跟各位同行唠唠嗑了。

在正式开喷之前，按江湖规矩，先给自己叠几层厚甲：

1. **一家之言，欢迎纠错**：本文纯属个人观点。年纪大了记忆力难免衰退，文中对部分论文细节的描述若有偏差，欢迎原作者私信指正，我一定老老实实修改。
2. **概念混用，领会精神**：文中会把 Transformer、Encoder-Decoder、Decoder-Only 等架构混为一谈，不再做学究式的严格区分。反正它们在底层算力逻辑和序列建模本质上没啥区别，大家领会精神即可。
3. **专戳泡沫，还原B面**：为什么要写这篇批判性的文章？因为市面上绝大多数推荐算法论文，都是**王婆卖瓜，自卖自夸**。各种离线指标和线上AB测试数字漂亮得让人眼馋，再加上顶着各大互联网大厂的光环，很容易让外人误以为找到了解决一切推荐难题的“银弹”。在推荐领域，我几乎没见过像 DeepSeek 那样敢在论文里自曝其短、把失败尝试写出来的团队。所以本文的目的，就是撕开这层滤镜，把论文里刻意隐去的“B面”和工程落地时的坑摆上台面，让大家对这些算法有个清醒、全面的认识。
4. **讲第一性原理，别拿AB实验数字压我**：本文的批评可能会冒犯到不少业内朋友。我先声明，我丝毫不怀疑你们论文里实验结果的真实性。我想质疑的是这些方法的**普适性**——它在你的特殊环境里跑通了，不代表就能放之四海而皆准。**无论是你们论文里正向的指标，还是我复现出来的负向结果，其实都不足以单独用来评判一个算法的优劣**。因此，我接下来的所有剖析，全部回归到**第一性原理**，从底层逻辑和理论根基上找瑕疵。**如果你非要拿着你那个场景下的AB实验数字来捍卫你的观点，那我直接投降认输——你说的都对，你的实验有效果，那就是你对，咱们就没必要往下聊了**。

## 推荐跌倒，LLM当锤：从“小甜甜”到“牛夫人”

很多年前，推荐算法界的一位大V曾写过一篇文章，把推荐算法奉为“**互联网工业皇冠上的明珠**”。谁能想到，短短几年光景，皇冠落地，推荐算法直接从皇座上摔了下来。以前资本和业务看咱们是“小甜甜”，现在再看，早已成了人老珠黄的“牛夫人”。

最直观的体现就是荷包和饭碗。几年前，“搜广推”工程师的薪资傲视整个互联网大厂；如今，咱们的薪水连大模型工程师的车尾灯都看不见了。更扎心的是，前阵子看到有人在鼓捣用 Agent 自动完成推荐算法的特征挖掘、写代码、上线、开AB实验乃至自我迭代。合着咱们不仅丢了皇冠，连手里的铁饭碗都快被大模型端走了。

说实话，当年“大模型”这个词刚冒出来时，我心里是很不服气的。论参数规模，咱们推荐模型才是祖宗级的“大模型”好吗！随便一个大厂都有上亿用户，哪怕一个 User ID 只用 32 维 Embedding 表示，Parameter Server（参数服务器）里的参数量也是百亿起步（虽然跟现在动辄万亿参数的 LLM 比是小巫见大巫，但在当年绝对有一战之力）。至于 Transformer 结构，咱们在做用户行为序列建模时也早就用烂了。可为什么短短几年下来，推荐算法连人家的背影都追不上了呢？

复盘下来，我觉得有三个底层原因：

**第一，社会价值与生产力属性的差异（虽然有点扎心）。** 从某种意义上讲，推荐算法对人类真实生产力的贡献确实乏善可陈。我以前有位前同事，曾在公开场合极其刻薄地把咱们这行总结为三个字——“黄赌毒”。虽然大家私下常自嘲这工作没啥社会意义，但骂得这么难听的，也是少见。仔细想想，咱们每天殚精竭虑优化的模型，核心目标不就是让普通人多剁手买一堆不需要的东西，或者刷各种 *Kill Time* 的短视频，在虚拟的多巴胺里沉沦吗？相比之下，现在的 LLM Agent 确实能帮人类写代码、做调研，实打实地提升生产力；而推荐算法除了帮资本家改善财报，对人类科技进步似乎没起太大推动作用。（不过话又说回来，咱们也不必过度自轻自贱。LLM提升效率的另一面是让大批打工人失业；而咱们至少还给普通人提供了廉价、片刻的欢愉。到底谁对人类社会的毁灭性更大？还真不好说，咱们拭目以待。）

**第二，各自为战的“诸侯割据” vs 拧成一股绳的“天下大同”。** 全世界的搜广推工程师不可谓不努力，但大家的力量根本无法拧成一股绳。推荐算法虽然底层数学原理相通，但一旦落到具体业务场景，数据分布和业务目标就千差万别。没有统一的度量衡，A厂电商场景下的重大突破，平移到B厂短视频场景可能直接水土不服。这也是为什么我读推荐论文时总带着十二万分的警惕——无数次头破血流的复现失败告诉我，外来的和尚经常水土不服。

而 LLM 恰恰相反。无论哪家大厂做模型，面对的都是共通的人类自然语言和逻辑推理规则。大家在同一个标准赛场上竞技，目标清晰、可量化、可对齐，甚至可以直接拿蒸馏别人的模型——能被直接蒸馏，就证明LLM的知识是普适的，是可以直接迁移的。全世界最聪明的大脑朝着同一个方向合力攻坚，自然能大力出奇迹；而推荐界永远在各自为战，拿什么去跟人家比？

**第三，普遍真理 vs 难测的人心。** 不是为了强行挽尊，其实咱们搜广推面临的业务场景，比自然语言复杂得多。LLM 之所以能跑通 Scaling Law，是因为它要学习的是一个客观存在的“普遍真理”。人类的语法规则、编程的编译逻辑、数学的推理范式，都存在明确、稳定的对错规则。只要你把参数堆上去、语料喂饱，这个客观存在的规律就一定能被拟合出来。

但推荐算法猜的是什么？是人心！人心深不可测，决定用户当下喜好的无数关键归因，根本不会显式地呈现在日志里。因为学习的对象根本不是一个稳态的普遍真理，所以我们注定无法复刻 LLM 那种统治级的表现。

我之所以铺垫这么多，是想点破一个事实：LLM 的巨大成功，绝不仅仅是因为它的模型结构或技术在数学上有多先进，更是因为它所处的问题域天然适配这套范式。 然而，现在推荐算法界却刮起了一股盲目的妖风——**手里拿着 LLM 这把金光闪闪的大锤，看推荐系统里哪里都像钉子，恨不得把传统推荐架构砸个稀巴烂，全盘照搬 LLM 的套路**。殊不知，这是两个底层逻辑截然不同的场景。盲目照搬，**就是邯郸学步，就是东施效颦**。

接下来，我就挨个盘点一下当前业内最流行的**四个“坏姿势”**，最后再聊一个我认为真正做到了结合自身特点进行扬弃的“好姿势”。

## 坏姿势一：强求 Scaling Law，却丢了“唯快不破”的看家本领

### 1. 推荐系统的 Scaling Law 是个伪命题

这波大模型浪潮的起点，源于业界发现了 Scaling Law：只要不断堆叠模型参数、投喂海量训练样本，模型能力就会顺着幂律曲线持续涌现。眼看隔壁吃肉，推荐界的同仁们自然也眼馋得紧，纷纷摩拳擦掌想要寻找推荐模型的 Scaling Law（**又是一个找银弹的故事**）。

但我要泼一盆冷水：**在推荐算法里寻找 Scaling Law，完完全全是个伪命题**。

原因我前面提过一嘴：NLP、代码生成和逻辑推理领域，存在着客观的“普遍真理”。说话不守语法别人就听不懂，写代码不守语法规则就过不了编译和 Test，算 $1+2$ 只要不等于 $3$ 就是错的。更重要的是，LLM处理任务所需的全部要素，几乎都包含在用户输入的 Prompt 和 Context Engineering 自动补充的上下文里了。这也是为什么现在各种 Agent Harness 框架越来越受重视——大家都意识到模型本身已经够聪明了，只要工程上能把上下文组织得清晰、完整，它就能给出正确答案。说白了，**一切皆在上下文中，谜底就在谜面上**。

可推荐系统面对的是什么鬼样子？我们要猜用户的兴趣，**而决定用户兴趣的绝大多数核心变量，在数据层面是完全不可见（Unobservable）的！** 一个用户平时高频复购某款商品，某天突然再也不买了，你的模型能从点击日志里猜到是因为他昨天被裁员了吗？一个用户平时酷爱刷恋爱甜宠视频，某天突然滑走不看了，你的模型能猜到是因为他刚刚失恋分手了吗？

这些场外要素的缺失，是推荐算法永远无法克服的内生缺陷。你告诉我，面对这种根本采集不到的缺失特征，你把模型参数从十亿堆到一万亿，拿再多的历史样本去死磕，它能把“用户失业/失恋”算出来吗？痴人说梦！

那么，在 LLM 出现之前，传统推荐系统是怎么弥补这种“先知能力”不足的呢？答案就一个字：**快**！ 天下武功，唯快不破。既然我猜不到你为什么突然不爱看甜宠视频了，那我就不猜原因，我靠极致的 **流式训练、Online Update**，在几分钟甚至几秒钟内敏锐捕捉到你最新的负反馈和兴趣漂移，瞬间调转船头给你推别的内容。**用“快速反应”去弥补“模型认知能力”的天然盲区，这才是传统推荐模型真正的看家法宝**。 令人痛心的是，在如今盲目追捧 Scaling Law 的狂热中，许多团队正在亲手扔掉这件法宝。

### 2. 得不偿失的“重”与“慢”

批判 Scaling Law 绝非单纯的学术清谈，因为这种执念已经在工业界引发了一系列走火入魔的技术选型。为了给模型塞进庞大的参数，工程师们在严苛的Latency约束下，不得不牺牲掉一些Online Update 的实时性，把大量核心计算挪到离线去做。在我看来，这完全是本末倒置、得不偿失。

- <br>**槽点 A：退化为“算力黑洞”的离线召回**。现在有些团队跟风在推荐模型里搞 Reasoning，把这当成一种 Inference-time Scaling技术。比如快手的 **OneReason** 模型，号称引入多步推理后性能卓越。但你去翻翻原始论文看它是怎么落地的？因为多步推理耗时太长，根本扛不住线上高并发的实时耗时要求，最后只能退而求其次，做成**离线召回**！ 有点常识的人都知道，离线召回是一种极其浪费算力的妥协方案。因为你根本不知道明天哪位大爷会打开 App，你只能开启“撒胡椒面”模式，在离线状态下把全量（或数亿高活）用户的推荐结果统统提前算好存起来。要是这位用户明天压根没来，算力直接打水漂；就算人家来了，他在前几秒刚刚产生了新的交互动作，或者把你离线算好的物料刚好看过了，你那套耗时耗力算出来的静态结果就作废了。<br>
- <br>**槽点 B：被严重误读的 Long History KV Cache**。<br>
- <br>**槽点 C：进退维谷的 Semantic ID（SID）死局** 。<br>

### 3. 唯一正确的姿势：蒸馏

那么，推荐系统里到底该怎么借力大模型参数规模的优势？我认为**唯一正确的姿势就是“模型蒸馏（Knowledge Distillation）”**。

你可以放心大胆地在离线搞一个参数极其庞大、结构极其复杂、专门吞吐超长用户历史的 Teacher Model。它不需要考虑线上延迟，怎么重怎么来；然后，通过蒸馏技术，把 Teacher 学到的深层表征和排序知识，实时或准实时地灌输给一个轻量级、结构精减的 Student Model。真正顶在线上抗并发、做分钟级 Online Update、对用户最新反馈做出闪电反应的，依然是那个敏捷的 Student Model。

在这条路线上，俄罗斯大厂 **Yandex 的 Sona 系统**就是个清醒且成功的工程典范，强烈建议各位同行去读读那篇论文，比跟风堆线上巨无霸模型务实多了。

## 坏姿势二：文本型 I/O + 微调通用 LLM，大材小用，适得其反

业内还有一条很火的路线：把推荐系统的输入输出全部改造成**纯自然语言文本（Text-based I/O）**，然后直接拿一个开源的通用大语言模型（如 LLaMA、Qwen）过来做微调（Fine-Tuning）。

支持者的逻辑听着很顺：通用 LLM 饱读诗书，拥有海量的跨领域世界知识和推理能力，简直就是个拿遍了全学科博士学位的“超级天才”。咱们请这位超级天才下凡，去商场里当个导购员（做推荐），那还不手到擒来、降维打击？

然而，这帮人忽略了一个最基本的工程常识：**沟通成本与信息密度**。

假设我们要向模型描述一个商品：“**10元的红色玩具小汽车**”。 在传统的结构化推荐模型里，这只需要极度紧凑的 3 个 Field：

1. 一个 `float` 浮点数表示价格：`10.0`；
2. 一个 `int` 枚举值表示颜色：`1`（代表红色）；
3. 一个无符号 `int` 表示 Item ID：对应“玩具小汽车”。

底层瞬间映射成稠密向量，干净利落。

可如果你非要照顾那位“全科博士”的阅读习惯，写成纯文本，它就得被切分成 `"10"`、`"元"`、`"的"`、`"红色"`、`"玩具"`、`"小汽车"` 等一长串 Token。信息表达效率低得令人发指！ 要知道，在线上环境里，让 LLM 每多吞吐一个 Token，燃烧的都是真金白银的 GPU 算力和电费。当你把用户的画像（Profile）、成百上千条历史交互记录（History）以及候选物品属性（Candidates）统统展开成小作文式的长文本 Prompt 时，那个序列长度和推理耗时，线上系统根本承受不起。**这就好比你请了位满腹经纶的老教授当商场导购，顾客本来指一下货架就能买单，现在非得用字正腔圆的学术论文腔调跟老教授寒暄半小时，他才明白顾客想买双袜子**——商场早关门倒闭了。

为了解决文本太啰嗦的问题，有些团队（比如阿里的 **RecGPT** 等工作）开始动脑筋：发明一套高度压缩、去冗余的“推荐专用精简文本格式”。比如把句子里的“的、地、得”、标点符号、语气助词统统砍掉，怎么短怎么拼。 结果呢？精简完之后，这串字符**压根就不像人话了**！ 这就陷入了一个荒诞的悖论：你之所以忍受高昂代价引入通用 LLM，看中的不就是它在海量人类自然语言上预训练出来的常识与理解力吗？而人类的自然语言本来就是充满了“的地得”、标点符号和语法冗余的。你现在塞给它一串洗剪吹之后的“加密电报”，通用 LLM 当场就懵圈了，它原本的通用语言能力根本发挥不出来！

同样的闹剧也发生在“**文本型 I/O + SID**”的缝合怪路线上。把自然语言文本和一串代表商品的 SID 编码拼在一起喂给通用大模型。对于通用 LLM 而言，那些人工造出来的 SID Token 就是彻头彻尾的“火星文”。

于是你会发现，凡是走这两条路线的论文，上来第一件事根本不是做推荐，而是必须先设计一套繁琐至极的Pre-training任务，逼着通用大模型先去“认字”，去重新学习这门“推荐专用黑话”或“SID 火星文”。在训练过程中还得战战兢兢、如履薄冰，生怕步子迈大了引发灾难性遗忘（Catastrophic Forgetting），把人家博士原有的通用知识给洗没了。

每次看到这种工作，我都觉得滑稽。**为了硬蹭通用大模型的热度，连“自然语言信息密度极低”这种天然缺陷都要全盘照收**，然后再花九牛二虎之力去削足适履、自找麻烦。这不是东施效颦是什么？

## 坏姿势三：照猫画虎自回归，妄想一次性吐出整个 Session

### 数据偏置+训练预测不一致

在推荐系统里，如何直接生成一整个 Session（比如用户一次下拉刷出的整屏 5~10 个物品列表）一直是个圣杯级的难题。 传统的工业级流水线大家都很熟：先用精排模型给每个候选物品单独打分，取 Top-N；但 Top-N 不能直接端给用户，因为排在前面的可能全是同质化内容，连着看会审美疲劳。所以精排后面还得接一层**重排（Re-ranking）**，主要是用各种启发式人工规则做多样性打散，最后才能向用户曝光。我完全承认，这种“精排+重排”的割裂架构不仅链路冗长，维护起来也很麻烦。

但传统方案有瑕疵，绝不意味着直接照搬 LLM 的自回归生成（Auto-regressive Generation）就是救世主！

看到 LLM 能像词语接龙一样，顺滑地一次性吐出一整篇逻辑严密的文章或大段代码，推荐界很多人又心动了：何不让推荐模型也用自回归的方式，连续多预测几步，一次性吐出由多个 Item 组成的完整 Session？ 在理想主义者眼里，这样做性价比极高：

1. **端到端干掉重排**：既然 LLM 擅长捕捉长序列内部的上下文关联，那它肯定能自动学会“好 Session”的内部多样性规律（比如相邻物品要互斥打散），从而一举把精排和重排合二为一；
2. **工程改造极简**：推理时无非就是把自回归解码多循环几步（词语接龙），底层架构和算子都不用大改。

听起来很美是吧？但我要毫不客气地指出：**目前绝大多数用自回归一次性生成整个 Session 的工作，其理论前提从根上就是错的，直接违背了机器学习最基本的原则！**

为什么？让我们回到训练数据的构造上。 由于 Transformer 的注意力机制对序列长度极其敏感，每多一个 Token 都是实打实的算力开销；而一个老用户的历史交互记录动辄跨越数年，哪怕只保留正向交互行为（Positive Items，如点击、点赞、完播、购买），序列长度就已经让工程团队喝一壶了。如果再把海量的负样本（比如曝光未点击的物料）全塞进去，序列长度直接爆炸，训练和线上推理根本跑不动。 因此，我可以非常肯定：在当下以及未来很长一段时间内，绝大多数序列推荐模型所喂入的 User History，全都是被人为筛选过的“纯正向交互序列（Positive-only Sequence）”。

这就意味着，模型在训练阶段所见到的历史上下文，并不是用户真实浏览轨迹的自然分布（真实轨迹里必然夹杂着大量滑走不看的负反馈），而是带了极强人工筛选偏置（Selection Bias）的温室花朵。

现在，请你推演一下线上推理（Inference）时的灾难现场：

1. **预测第 1 个物品（Next-1）**：模型读完用户过去纯正向的历史序列 `[Pos_1, Pos_2, ..., Pos_t]`（`Pos`代表Positive），预测出第 1 个推荐物品 `Pred_1`。到此为止，逻辑完全自洽，这也是传统的单步预测（Predict Single Next）范式。
2. **预测第 2 个物品（Next-2）**：为了继续做自回归词语接龙，你必须把刚刚新鲜出炉但**还没曝光给用户看**的 `Pred_1`，生硬拼接到 Postive-Only User History 的末尾，组成 `[Pos_1, ..., Pos_t, Pred_1]`，再喂回给 Transformer 去预测 `Pred_2`！

发现问题在哪了吗？ 你的模型在训练时，接在历史序列里的每一个位置，100% 都是经过用户真金白银确认过的 **Positive Item**！而在线上连续生成时，你把 `Pred_1` 拼进去的那一刻，**你其实在隐式地强行引入一个毫无根据的假设**——你假定用户一定会喜欢并点击 `Pred_1`！ 可实际上呢？`Pred_1` 连用户的面都还没见着，根本没有拿到真实反馈，它极大概率是个曝光未点击的负样本！当你把一个真假未知的预测值当成 100% 确定的正样本塞进上下文去预测 `Pred_2` 时，严重的 **Training-Inference Skew** 就已然发生了。接下来你再拿着质量存疑的 `Pred_2` 去接龙预测 `Pred_3`、`Pred_4`、`Pred_5`……这就是典型的**一步错、步步错，误差呈指数级累积放大**。建立在这种错误假设之上的 Session，根本就是毫无根基的沙中之塔。

有人可能会跳出来反驳：“*照你这么说，人家通用 LLM 写文章也是自回归接龙，怎么就没崩溃，偏偏到你推荐系统里就危言耸听了？*”

问出这话，恰恰说明没想明白自然语言与推荐序列的本质区别：

- **通用 LLM 的输入与输出是同分布的自然序列**。喂给 LLM 训练的语料是未加删减的自然语言，里面包含了大量毫无信息量的虚词、连词、“的地得”、“the”和标点符号。而我们也同样允许 LLM 在生成时吐出这些语法粘合剂式的“正确的废话”。因为输入和输出遵循的都是原汁原味的自然语言真实分布，没有任何人为的“正样本提纯”，所以人家自回归接龙稳如老狗。
- **推荐模型的输入与输出则是高度扭曲的人工序列**。为了省算力，输入端被我们人为过滤成了“纯正向序列”；而在输出端，因为屏幕上的每一个曝光坑位都贵如黄金，业务方恨不得模型吐出来的每一个 Item 全是爆款正样本，**绝不允许吐出“虽然符合浏览规律但用户不点击”的凑数废话**。在输入输出双重失真、且中间彻底缺失用户反馈闭环的前提下，强行模仿 LLM 搞多步自回归生成，在理论上就是完全破产的。

### 业务上不Make Sense

说到这儿，还真有一篇论文不得不提——老东家快手的 **OneRec**。 我第一次读 OneRec 时百思不得其解：它在训练阶段用来做 Teacher Forcing 的 Ground Truth，居然真的是一个未经筛选的、原汁原味的**真实完整 Session**！也就是说，那个 Session 里包含了大量曝光未点击（用户不喜欢）的坑位物料，OneRec 居然逼着大模型把这些负向坑位也一并模仿学出来！ 我当时心想：**这倒确实在形式上对齐了自回归所需的分布一致性，这样训练出来的模型推荐整个Session，理论上是站得住脚的**。

但转念一想，这在业务上不是疯了吗？推荐位寸土寸金，你为了迎合机器学习的分布一致性教条，故意训练模型在线上固定吐出几个“用户大概率不点”的垃圾物料去填坑？你去跟业务老板汇报说：“老板，为了保证自回归理论自洽，我让模型每刷一屏都精准预测并塞进去两个用户不想看的视频。”你猜你们部门本年度的绩效C是谁背？

而且再深扒一下就会发现，OneRec 的这种操作也不过是个掩耳盗铃的“歪打正着”：

1. **不伦不类的混搭**：它的输出端 Ground Truth 虽然用了完整真实 Session，但它输入端的 User History 依然是筛选过的 Positive Item 序列。前后根本没对齐，属于半吊子缝合。
2. **刻意回避争议**：对于“为什么逼模型去拟合真实 Session 里的负样本坑位”这一极其违背业务直觉的操作，原论文绝口不提，显然作者当时也未必想透了其中的悖论。
3. **续作打脸**：最精彩的证据在它的续集 **OneRec-v2** 里。你去翻看 OneRec-v2 的公式（10），它的最终 Loss 变成了仅仅由 3 个位置上的 SID Loss 相加！咱们前面讲过，1 个 Item 刚好用 3 个 SID 表示。Loss 只算 3 个 SID，意味着什么？意味着 OneRec-v2 已经悄悄放弃了初代吹上天的“一次性生成整个 Session”路线，灰溜溜地退回到了 **Predict Single Next** 的传统老路上了！这种自食其言，是不是宣告了“自回归生成整个 Session”这条路线的彻底破产？

## 坏姿势四：迷信 Reasoning，自嗨式加戏

当年ChatGPT刚问世时，其实我并没太当回事。毕竟早年我搞 NLP 那会儿，也用 LSTM 训过写古诗、讲笑话的玩具模型，觉得大模型无非是个更大号的文字接龙机罢了。直到后来以 o1、DeepSeek-R1 为代表的 **Reasoning模型**出现——在给出正式回答前，先用一段灰色的斜体小字给自己加一段好长的“内心独白（思维链）”，反复推演、自我纠错。那一刻我才真正意识到：“这一回，真的不一样了。”

看到大模型长出了看似具备真智能的“慢思考”能力，推荐算法界的同行们又坐不住了，一窝蜂地要把 Reasoning 搬进推荐模型里。对此，我的评价依然是：**邯郸学步，东施效颦**。

先从第一性原理想想：通用 LLM 为什么需要 Reasoning？ 因为你交给它的是复杂度极高、且**试错代价极其高昂**的重型任务！比如让它做深度行业调研写万字报告，或者重构一个复杂的软件工程代码库。整个生成过程要消耗数以万计的 Token 和漫长的时间，如果它不先在脑子里把逻辑框架盘清楚就莽撞动笔，一旦写歪了，时间和算力的沉没成本是灾难性的。所以，“三思而后行”对 LLM 来说是刚需。

可你低头看看咱们的推荐系统，这是个什么场景？ 无论是推一件衣服还是推一条短视频，推荐系统的试错代价低到几乎为零！ 推错了又怎样？用户大拇指在屏幕上轻轻一划就滑走了，人家根本不会因为你推错了一两条视频就愤而卸载 App。甚至很多时候，**“推错了被滑走”本身就是一个极其宝贵的实时负反馈信号，能帮系统快速完成对用户兴趣边界的探索（Exploration）**。 在一个任务颗粒度极小、试错成本极低的场景里，用户点开 App 就是为了刷个 15~30 秒的短视频图一乐，哪怕你让模型在后台推理 3 秒钟，都是对用户耐心的极大不尊重！ **扔掉“快速试错、实时反馈”的看家本领，去模仿人家笨重高冷的慢思考，纯属自己臆想出来的伪需求**。

### 1. 扒掉神秘底裤：隐式推理的本质是“课程学习”

话虽这么说，但我知道肯定有不少同学为了发顶会论文或者应付老板的 KPI，还是得硬着头皮往 Reasoning 这条死胡同里钻。既然拦不住，那我就帮大家彻底扒掉 Reasoning 那层“人工智能觉醒”的神秘底裤，还原它的本质，好让大家更快地上手交差。

推荐模型里的 Reasoning 分两条路线：

- **显式推理（Explicit Reasoning）**：跟通用 LLM 一模一样，先用人工或强模型构造出一段自然语言文本（例如：“因为该用户昨天买了猫粮，说明他养猫，所以今天应该给他推猫砂盆……”），强迫推荐模型在输出商品前先把这段小作文背出来。这条路线必须绑定我们前面痛批过的“文本型 I/O + 微调通用 LLM”，不仅慢得要死，而且笨重不堪，因此注定成不了主流。
- **隐式推理（Implicit Reasoning）**：这是目前工业界论文的主流玩法。常规模型读完 User History 后，直接解码吐出目标 Item；而隐式推理模型在读完历史特征后，不急着吐目标 Item，而是先在隐空间里多走 $K$ 步，自回归地先吐出 $K$ 个所谓的 **Think Tokens（思考隐向量）**，等这 $K$ 步走完，最后才吐出真正的推荐 Item。

很多外行看着“隐空间多步思考”觉得玄乎得不行，其实你把这层时髦的新词外衣扒掉，它的技术实质就是早已有之的**课程学习（Curriculum Learning）** 或多任务辅助监督！ 怎么训练这 $K$ 个 Think Tokens？总不能让它们在隐空间里毫无约束地乱飘吧？你必须人为给这中间的 $K$ 步设计明确的**监督信号（Supervision Signals）**，通过由浅入深的中间目标去辅助最终主目标的收敛。这就好比武术大师教徒弟绝世武功，不能上来就教大招，得先按部就班地制定扎马步、练拳架等一系列基本功考核——这套循序渐进的引导机制就是课程学习，只是赶上大模型风口，被包装成了“隐式推理”这个性感的新名词而已。

看穿了这一层，你就明白做隐式推理推荐论文的核心秘诀了：谁能为中间那 $K$ 个 Think Tokens 找到强有力、讲得通的监督信号，谁的工作就成功了 80%。比如：

1. **借用业务天然的级联漏斗信号**：在电商等漏斗极其清晰的场景里，如果终极目标是“成交（Purchase）”，那你就可以把前面的“点击（Click）”、“加购（Cart）”等中间环节的 Ground Truth 拿过来，分别作为第 $1$ 步到第 $K$ 步 Think Token 的监督信号。说白了，这跟咱们做了多年的多目标学习（Multi-task Learning）没有任何本质区别，纯粹是新瓶装旧酒，换个马甲蹭热度。
2. **暴力对齐最终 Ground Truth**：如果业务场景没有清晰的级联中间态，最简单粗暴的基线做法，就是拿最终的 Ground Truth 同时去监督中间的每一个 Think Token，强迫这 $K$ 步中的每一步输出都逐步向最终目标靠拢。

### 2. 唯一的正确姿势：只训练，不上线

既然看清了 Reasoning 的本质只是辅助模型收敛的“课程学习”，那么它在工业界落地的两条铁律也就呼之欲出了：

1. **绝不能把多步 Reasoning 搬到线上推理链路中去**。推荐之前，先给自己加一段“把大象装进冰箱需要几步”的哲学内心戏，那纯属劳民伤财；
2. **Reasoning 作为辅助任务，只在离线训练阶段发挥作用，目的只是为了更好地训练主任务，而不会亲自上阵**。还是用学武术打比方：徒弟平时在武馆里训练（Offline Training），可以老老实实按步骤扎马步、打木人桩；但一旦走上擂台跟人生死搏杀（Online Serving），当然是直接一招致命绝技轰出去！哪有对手拳头都砸到脸上了，你还在原地先把广播体操基本功演练一遍的道理？

这一点，腾讯的 《TGR: Advancing Industrial Recommendation from Generative-Paradigm Ranking toward Unified Generation and Reasoning》论文中说了一段大实话，深得我心：

> *"The property that makes reasoning amortizable is that this supervision improves accuracy **even when generation uses K=0, where the module never runs in the forward pass**. The gain lives in the LoRA adapters shaped by per-step supervision **rather than in multi-step computation at generation time**, so **the reasoning module is discarded after training** and the offline pipeline reduces to standard SID decoding... **placing the value of multi-step latent computation at training time rather than on the production generation path. The production Think model therefore generates reason tokens with K=0**."*<br>

翻译成人话就是：多步推理带来的收益，其实在训练阶段就已经沉淀到模型参数里了；哪怕在线上生成时把推理步数设为 **$K=0$（即压根不跑推理模块）**，精度依然能提升！因此，训练一结束，推理模块直接扔进垃圾桶，线上生产环境只跑 $K=0$ 的常规解码！ 看看，这才叫人间清醒。

同理，前面提过的快手 OneReason 论文里给出的第二种部署方案也还算靠谱：把离线耗时耗力训出来的重型推理模型当成 Teacher，通过知识蒸馏让轻量级的 Student 模型去模仿它的打分分布；**真正上线的只有 Student，线上绝不跑半步无意义的推理**。

## 好姿势：回归传统，只做 Cross-Attention

骂了这么多生搬硬套的“坏姿势”，最后咱们必须聊点正能量的“好姿势”。当推荐算法界被线上延迟和算力账单毒打了一轮之后，各大厂的一线团队冷静下来，结合推荐场景的真实物理约束，对 Transformer 架构进行了一次极其明智的“扬弃”。

通过研读多篇大厂核心论文（如快手的 OneRec、UniFormer，字节的 STCA、HyFormer，以及阿里的 EST 等），再结合我自己的实验体感，我发现业界在Ranking如何使用 Transformer 上，已经不约而同地达成了一个高度共识： **彻底放弃对长长的 User History 做全局 Self-Attention，转而只拿少量的 Candidate Item（候选物品）等信息作为 Query，去对 User History 进行反复、多层的 Cross-Attention！**

听着是不是特别耳熟？没错，这不是什么大模型时代的新发明，它骨子里其实就是阿里多年前提出的经典架构——DIN（Deep Interest Network）中 Target Attention 的多层升级版！ 我之所以对这个趋势高度赞赏，正是因为它没有盲目迷信通用 LLM 里统治一切的 Self-Attention，而是地回归了推荐系统的第一性原理。

为什么在推荐排序里，Cross-Attention 能够完胜 Self-Attention？核心原因有二：

1. **算力账单的物理倒逼**： 用户的历史行为序列动辄成千上万，Self-Attention 那 $O(L^2)$ 的平方级复杂度，在线上高并发环境下就是个算力无底洞，神仙也扛不住。而在 Cross-Attention 中，充当 Query 的信息（主要来自当前待打分的候选物品）数量极少，计算复杂度直接从二次方降维成线性级，完美契合线上严苛的实时性要求。
2. **推荐特征交叉的灵魂在于“千物千面”**： 我始终坚信一条铁律：在排序场景下，最有信息增益的特征交叉，绝不是用户历史行为内部的自嗨式互交（比如两年前买过的一双袜子和三年前点过的一首歌之间到底有什么注意力关系？），而是**当前候选物品（Candidate Item）与用户历史（User History）之间的定向碰撞**！ 只有拿着当前的候选物品当探针（Query），去浩瀚的历史记录里定向检索、提炼出与该物品高度相关的特定兴趣切面，才能让同一个用户的历史表征随着候选物品的不同而动态变化，真正实现用户表征的“**千物千面**”。

目前业界打磨出来的这套 **多层 Cross-Attention 标准范式**，流程非常清晰优雅：

1. **严控 Query 规模**：只挑选极其精简的核心信息作为初始 Query Tokens（最核心的就是 Candidate Item 特征；如果线上算力还有富余，可以适当塞入少量 User Profile 或极短的近期实时交互序列）。总之，死死卡住 Query Token 的总数 $Q$（$Q \ll L$），从源头上锁死计算规模。
2. **靶向提取历史（Cross-Attention）**：拿着这 $Q$ 个精悍的 Query Tokens，去和长度为 $L$ 的超长 User History 做 Cross-Attention，定向吸取历史精华，产出 $Q$ 个聚合结果。
3. **内部轻量交互（Token Mixing / Self-Attention）**：让产出的这 $Q$ 个结果在内部做一次深层交叉（比如跑一层小规模的 Self-Attention 或 Token Mixing）。因为 $Q$ 非常小，这步内部交互的算力开销几乎可以忽略不计。
4. **多层堆叠递进**：把内部交互后的 $Q$ 个向量作为下一层的新 Query Tokens，再次送入长历史序列中做 Cross-Attention。如此反复堆叠多层，像剥洋葱一样，一层比一层更深、更准地把**与当前候选物品最匹配的用户潜在兴趣**给榨取出来。

不盲从、不照搬，把最前沿的算子结构掰碎了，融进推荐系统“快”与“准”的传统血脉里——这才叫他山之石，可以攻玉。
