### 本章导读：为什么要从结构视角讲 DiT 加速？

在 ch8 里我们逐个拆解了 DiT 的结构家族——单流 DiT、双流 MM-DiT、视频 DiT、3D VAE。那些章节回答的是”**结构长什么样、为什么这么设计**“。本章要回答的是一个更工程化的问题：

> **给定一个特定结构的 DiT，训练和推理分别该用什么加速方案？为什么这个结构能这么加速、不能那么加速？**

这个问题在部署系列 ch10 里讲过通用答案——FP8 量化、torch.compile、TP/SP 切分、少步蒸馏。但那是”通用 DiT 加速”的视角。当你真正面对不同结构时，你会发现**结构本身的数学性质直接约束了加速选择**：

| 结构特征 | 对加速的约束 | 例子 |
| --- | --- | --- |
| MM-DiT 双流 attention（text/image 对称） | 双流可融合为单个 FA kernel，比 cross-attn 快 | Flux 训练时双流 attention 融合后 1.3× 加速 |
| AdaLN-Zero 的 timestep emb 每层都注入 | timestep emb 可在 batch 内预计算复用 | 同 batch 同 timestep → 6d GEMM 只算一次 |
| DiT 双向 attention（无 causal mask） | FA 完美适配，无 causal mask 拼接开销 | SD3 attention FA2 利用率 95%+ |
| 3D attention 的 O((T·H·W)²) | 必须分解成 spatial + temporal 才跑得动 | HunyuanVideo 13B 不分解 OOM |
| DiT 每步 latent 都变 | 无 KV Cache（推理核心约束） | Flux 50 步 = 50 次全 attention |
| 长视频前 chunk 的 KV 与后 chunk 部分相关 | causal attention + 跨 chunk KV 复用 | Sora 类长视频分钟级生成 |
| 视频去噪步数可蒸馏 | step distillation 是 DiT 独有 | LCM 把 50 步蒸成 4 步，12× 加速 |

这些约束不是”经验技巧”，而是结构数学性质决定的硬约束。本章的核心方法论一句话：

> **结构决定加速边界——DiT 的双向 attention 让 FA 完美适配，MM-DiT 的双流让 attention 可融合，3D attention 的 O((T·H·W)²) 强制分解，多步去噪让 step distillation 成为 DiT 独有优化，无 KV Cache 让 PagedAttention 那套显存管理全部失效。**

## 1 DiT 加速与 LLM 加速的根本差异

在进入五大分支之前，必须先把 DiT 加速和 LLM 加速的差异讲透——这不是点缀，而是整章的根基。如果你带着 LLM 加速的直觉来做 DiT 加速，会处处碰壁：PagedAttention / Continuous Batching / Prefix Caching / 投机解码在 DiT 上几乎全部不适用，但 step distillation / latent 预编码 / 3D attention 分解这些 DiT 独有优化 LLM 又用不上。

### 1.1 五大根本差异

| 维度 | LLM 加速 | DiT 加速 |
| --- | --- | --- |
| 生成范式 | 自回归（一次一个 token） | 迭代去噪（50 步逐步 refine 同一 latent） |
| KV Cache | 有，且是推理显存/延迟核心 | 无，每步 latent 都变，K/V 无法跨步缓存 |
| 训练瓶颈 | 通信均衡（TP/PP/DP/EP/CP 协同） | compute-bound + 数据吞吐（VAE/视频解码） |
| 推理瓶颈 | decode memory-bound（访存为主） | compute-bound（attention 序列固定且巨大） |
| 独有优化 | PagedAttention / 投机解码 / Prefix Cache | step distillation / latent 预编码 / 3D attention 分解 |
| 条件注入 | 无（输入即条件） | timestep + text，每层注入（AdaLN-Zero / cross-attn / 双流） |
| 三阶段 | 单一 Transformer | 文本编码器 + DiT + VAE（三阶段流水线） |
| 量化重点 | 权重 + KV Cache | 权重（DiT 主体）+ 激活（VAE 解码） |

### 1.2 为什么 DiT 无 KV Cache 但长视频又能复用

LLM 的 KV Cache 之所以成立，是因为自回归生成中**历史 token 的 K/V 不变**——第 t 步生成时，前 t-1 个 token 的 K/V 和第 t-1 步完全一样，可以直接复用。

DiT 完全不同。DiT 的输入是一个 latent（1024×1024 图像对应 128×128×4 latent，patchify p=2 后约 4K token），每一步去噪都要对这个 latent 做完整的 self-attention。但**每一步的 latent 都在变**（去噪过程在逐步修改 latent），所以第 t 步的 K/V 和第 t-1 步完全不同，无法缓存。

```text
LLM decode（KV Cache 可用）：
  step 1: latent = [tok_1]              → 算 K_1, V_1，缓存
  step 2: latent = [tok_1, tok_2]       → 只算 K_2, V_2，复用 K_1, V_1
  step 3: latent = [tok_1, tok_2, tok_3]→ 只算 K_3, V_3，复用 K_1..K_2

DiT 去噪（KV Cache 不可用）：
  step 1: latent = x_T      → 算全量 K, V（基于 x_T）
  step 2: latent = x_{T-1}  → 算全量 K, V（基于 x_{T-1}，与 step 1 完全不同）
  step 50: latent = x_0     → 算全量 K, V（基于 x_0）

长视频分块生成（部分 KV 复用）：
  chunk 1: latent = [z_1]                    → 算全量 K_1, V_1
  chunk 2: latent = [z_1_cond, z_2]          → z_1_cond 是 chunk 1 末帧（不变），
                                             → K_cond, V_cond 可复用 chunk 1 末帧 KV
                                             → 只算 z_2 部分的 K, V
```

这个差异的工程后果：**DiT 推理不能用 PagedAttention 那套显存管理**。LLM 的 PagedAttention 是为了管理”随序列增长、可跨请求共享”的 KV Cache；DiT 没有跨步 KV Cache，它的显存压力来自**单步前向的激活值**（4K token × 30 层 × hidden_dim 的中间激活），以及**多步迭代时的中间 latent 存储**。

但长视频是例外——分块生成时，**前一块的末尾几帧作为条件帧传入下一块**，这些条件帧的 KV 在两块间是不变的，可以复用。这是 1.4 / 1.5 的核心优化点。

### 1.3 为什么 DiT 是 compute-bound

LLM decode 之所以 memory-bound，是因为每步只生成 1 个 token，但要读取整个权重（70B 模型 140GB 权重），算术强度约 1-2 FLOP/byte。DiT 每步去噪处理的是**整个 latent**（4K-16K token），attention 的算术强度远高于 LLM decode：

```text
LLM decode 算术强度（Llama3-70B，单 token）：
  FLOPs ≈ 2 × N_params = 140 GFLOP
  访存 ≈ N_params × 2 bytes = 140 GB（BF16）
  算术强度 = 1 FLOP/byte  ← memory-bound（H100 拐点 74 FLOP/byte）

DiT 单步去噪（Flux 12B，1024×1024，latent 16K token）：
  FLOPs ≈ 6 × N_params × seq_len / hidden_dim ≈ 192 TFLOP
  访存 ≈ N_params × 2 bytes ≈ 24 GB（权重）
  算术强度 = 192 TFLOP / 24 GB ≈ 8000 FLOP/byte  ← compute-bound（拐点的 100+ 倍）
```

**关键洞察**：DiT 单步去噪的算术强度是 LLM decode 的 **8000 倍**。这意味着：

1. **量化对 DiT 延迟帮助巨大**：FP8 把 Hopper Tensor Core 算力翻倍（1979 vs 989 TFLOPS），compute-bound 时算力即瓶颈，FP8 直接 ~2× 加速。而 LLM decode 量化只省显存不省延迟（memory-bound 时算力不是瓶颈）。
2. **Batch 对 DiT 吞吐提升显著**：compute-bound 时增大 batch 不增加单步延迟（算力利用率已高），但成倍提升吞吐。LLM decode 的 batch 提升受限于显存带宽，边际收益递减。
3. **少步蒸馏是 DiT 独有优化**：LLM 的”步数”是 token 数，不能减少（除非投机解码）；DiT 的”步数”是去噪步数，可通过蒸馏从 50 步降到 4 步，直接 12× 加速。

### 1.4 DiT 三阶段流水线

DiT 生成不是单一模型，而是三阶段流水线。加速时三个阶段都要考虑：

![](https://pic2.zhimg.com/v2-51e3f958bc0d2118cf37bc15f459bd25_r.jpg)

**结构-加速协同关键**：文本编码器和 VAE 都是**一次性**的（推理时只跑一次），且**与 DiT 解耦**——它们可以离线预编码（训练）/ offload 到 CPU（推理），让 DiT 主体独占 GPU。这是 DiT 加速相对于 LLM 的一个独有优势：LLM 的 prefill 和 decode 是耦合的（同一个模型），DiT 的三阶段天然可分离。

## 2 图像 DiT 训练加速（Flux / SD3，结构-训练协同）

图像 DiT 是 DiT 最成熟的训练场景。SD3（2B/8B）和 Flux（12B）是 2024-2025 年的两个标志性图像 DiT：SD3 用 MM-DiT 把文本和图像放在对称的双流 attention 里；Flux 用更大的 12B 参数 + flow matching 把图像质量推到新高度。本节以 Flux 为主、SD3 为辅讲训练加速。

### 2.1 结构特点：MM-DiT 双流 attention + AdaLN-Zero + Flow Matching

回顾 ch8 的 1.2 节，MM-DiT 的核心结构是**双流 attention**——文本流和图像流在 Transformer 内部用对称的 self-attention 交互，而非传统 SD 的 cross-attention。一个 MM-DiT block 的结构如下：

![](https://pica.zhimg.com/v2-bbcea5ceb7afe185380613056ecbda48_r.jpg)

从训练加速的角度，这个结构有四个关键性质：

**性质 1：双流 attention 拼成一条序列做 self-attn，FA 完美适配。**

传统 cross-attention（如 PixArt-α）的 attention 是 `attn(Q=img, K=V=txt)`，FA 的输入是三条独立的序列，需要分别计算。MM-DiT 把 `[img; txt]` 拼成一条序列做 self-attn，FA 只需一次前向处理整条序列，**kernel launch 开销减半，且 FA 的双向 attention（无 causal mask）正是 DiT 默认形态**。

**性质 2：AdaLN-Zero 的 `Linear(d→6d)` 可在 batch 内预计算。**

每个 MM-DiT block 的 AdaLN-Zero 都需要一个 `d→6d` 的 GEMM 生成 `(γ1, β1, α1, γ2, β2, α2)`。这个 GEMM 的输入是 `c = t_emb + txt_pool_emb`，**在同 batch 同 timestep 的样本间完全相同**（如果 batch 用同一 timestep）。结构上，可以把 batch 内 timestep 分桶，相同桶的 `(γ, β, α)` 只算一次再广播。

**性质 3：文本编码器（T5-XXL）和 VAE 都冻结，可离线预编码。**

Flux 用 T5-XXL（4.7B）+ CLIP-L + CLIP-G 作文本编码器，三者共 ~5B 参数。训练时这三个模型**完全冻结**，所以可以把整个数据集的文本预编码成 embedding 存盘，训练时只读 embedding 不跑 T5。同理 VAE 也可预编码图像到 latent。这让训练时 GPU 只跑 DiT 主体，文本编码器和 VAE 完全不占训练算力。

**性质 4：Flow Matching 训练目标比 DDPM noise prediction 更结构友好。**

Flow Matching 的损失是 `MSE(v_pred, v_target)`，其中 `v_target = x_1 - x_0`（线性插值的速度），而 DDPM 是 `MSE(ε_pred, ε)`。两者结构上都是 MSE，但 Flow Matching 的 target 分布更集中（线性 vs 高斯），训练更稳定，可用更大学习率——这间接加速收敛（同等质量所需 step 数减少 20-30%）。

### 2.2 加速方案一：FlashAttention 2⁄3 适配双向 attention

DiT 的 attention 是**双向 full attention**（无 causal mask），这与 LLM 的 causal attention 形成对比。对 FA 来说这是**最理想**的输入形态——不需要 causal mask 的拼接与裁剪，整条序列一次计算。

**FA2 vs FA3 在 DiT 上的差异**：

| 维度 | FA2 (2023) | FA3 (2024, Hopper 专属) |
| --- | --- | --- |
| 硬件 | A100 / H100 | H100 专属（用 FP8 Tensor Core） |
| BF16 算力利用率 | ~70% | ~75% |
| FP8 支持 | 否 | 是（FP8 attention，2× 加速） |
| persistent kernel | 否 | 是（减少 launch 开销） |
| DiT 实测加速（H100 BF16） | baseline | 1.2× vs FA2 |
| DiT 实测加速（H100 FP8） | 不支持 | 2.0× vs FA2 BF16 |

```text
# FA3 在 Flux 训练中的接入（diffusers 内部已集成）
import torch
from flash_attn import flash_attn_func  # FA3

# MM-DiT 双流 attention 融合为单次 FA 调用
def mmdit_attention_fused(
    x_img, x_txt,    # [B, N_img, d] / [B, N_txt, d]
    W_Q, W_K, W_V, W_O,   # 双流共享或独立投影矩阵
    n_heads, head_dim,
):
    """双流 attention 融合：拼接 [img; txt] 一次 FA 计算"""
    B, N_img, d = x_img.shape
    N_txt = x_txt.shape[1]

    # 1. 双流各自投影
    Q_img = x_img @ W_Q  # [B, N_img, d]
    K_img = x_img @ W_K
    V_img = x_img @ W_V
    Q_txt = x_txt @ W_Q
    K_txt = x_txt @ W_K
    V_txt = x_txt @ W_V

    # 2. 拼接成一条序列（结构关键：双流融合）
    Q = torch.cat([Q_img, Q_txt], dim=1)  # [B, N_img+N_txt, d]
    K = torch.cat([K_img, K_txt], dim=1)
    V = torch.cat([V_img, V_txt], dim=1)

    # 3. reshape 为多头
    Q = Q.view(B, -1, n_heads, head_dim)
    K = K.view(B, -1, n_heads, head_dim)
    V = V.view(B, -1, n_heads, head_dim)

    # 4. FA3 一次前向处理整条序列（无 causal mask）
    out = flash_attn_func(Q, K, V, causal=False)  # [B, N, n_heads, head_dim]
    out = out.reshape(B, -1, d)

    # 5. 拆分回双流
    out_img = out[:, :N_img, :]
    out_txt = out[:, N_img:, :]
    return out_img @ W_O, out_txt @ W_O
```

**结构-加速协同**：MM-DiT 的双流 attention 在数学上等价于”拼接后做 self-attn 再拆分”，这与 FA 的”一次性处理整条序列”完美契合。相比之下，传统 cross-attention 需要两次 FA 调用（一次 img self-attn + 一次 img×txt cross-attn），FA 利用率低 30%。**这是 MM-DiT 相对 PixArt-α 的结构优势在训练加速上的直接体现**。

> **交叉引用**：FA2/FA3 的 kernel 原理（tiling / online softmax / persistent kernel）见 ch10 的 1.2 节与 CUDA 系列 flash attention 章节。本章只关注 DiT 结构如何让 FA 发挥最大效用。

### 2.3 加速方案二：latent 预编码 + 文本预编码

DiT 训练的三阶段中，文本编码器（T5-XXL）和 VAE 都是**冻结**的——它们不更新参数，只是把原始数据（文本/图像）转成 embedding/latent。这意味着可以**离线预编码**整个数据集，训练时只读已编码的 latent/embedding，不跑 T5/VAE。

![](https://picx.zhimg.com/v2-e0e59af06dd57e8c6d8fdc5d6e2b73d1_r.jpg)

**收益量化**：

| 配置 | 每 step 耗时 | 训练吞吐 | GPU 利用率 |
| --- | --- | --- | --- |
| 不预编码（T5+VAE 在线） | 1.0× baseline | 1.0× | DiT 60% / T5 30% / VAE 10% |
| latent 预编码（VAE 离线） | 0.7× | 1.4× | DiT 85% / T5 15% |
| latent + 文本预编码（推荐） | 0.45× | 2.2× | DiT 95%+ |

```text
# latent + 文本预编码脚本（一次性离线编码整个数据集）
import torch, webdataset as wds
from diffusers import FluxPipeline

# 1. 加载 VAE 和文本编码器（只用编码器部分）
pipe = FluxPipeline.from_pretrained("black-forest-labs/FLUX.1-dev", torch_dtype=torch.bfloat16)
vae = pipe.vae.to("cuda")           # 图像 → latent
text_encoder = pipe.text_encoder_2.to("cuda")  # T5-XXL
tokenizer = pipe.tokenizer_2

# 2. 离线编码图像
def encode_image(image_tensor):
    """图像 → latent，存盘"""
    with torch.no_grad():
        # image_tensor [B, 3, 1024, 1024] → latent [B, 16, 128, 128]
        latent = vae.encode(image_tensor).latent_dist.sample()
        # VAE 输出的 shift factor（Flux 特有）
        latent = (latent - vae.config.shift_factor) * vae.config.scaling_factor
    return latent  # 存为 .pt / .zarr

# 3. 离线编码文本
def encode_text(prompt_list):
    """文本 → T5 emb + pool emb"""
    with torch.no_grad():
        tokens = tokenizer(prompt_list, padding="max_length",
                          max_length=512, truncation=True, return_tensors="pt").to("cuda")
        emb = text_encoder(**tokens)[0]  # [B, 512, 4096]
    return emb

# 4. 流式处理整个数据集
dataset = wds.WebDataset("data/shards/img-{000000..001000}.tar")
for sample in dataset:
    img = load_image(sample["jpg"])  # [1, 3, 1024, 1024]
    prompt = sample["json"]["caption"]
    latent = encode_image(img)
    emb = encode_text([prompt])
    # 存盘（key = sample 的唯一 ID）
    torch.save(latent.cpu(), f"data/latents/{sample['__key__']}.pt")
    torch.save(emb.cpu(), f"data/embeddings/{sample['__key__']}.pt")
```

**结构-加速协同**：VAE 和 T5 之所以能预编码，是因为它们**结构上与 DiT 解耦**——VAE 不接收 timestep 输入，T5 不接收 timestep 输入，它们的输出只依赖图像/文本本身。这与 LLM 形成对比：LLM 的 prefill 和 decode 是同一个模型，无法把”前置计算”分离出来预编码。

### 2.4 加速方案三：bucket sampler 多分辨率训练

真实图像数据集的分辨率不统一（有 1024×1024、768×1344、1344×768 等多种比例），如果强制 resize 到同一分辨率会丢失信息。Flux 训练用 **bucket sampler**——把数据按分辨率分桶，每个桶内 batch 一起训练。

![](https://picx.zhimg.com/v2-7f881726b0e3834b9afb0e598ebe01ad_r.jpg)

**结构-加速协同**：bucket sampler 让每个 batch 内的 latent shape 一致，FA 可以一次调用处理整个 batch（不用 padding）。但跨 bucket 切换会让 token 数变化（1024×1024 → 4K token，768×1344 → 3.8K token），如果用 `torch.compile` 会触发重编译。**结构上的解法**：用 `dynamic=True` 编译，或对常见 bucket 预编译（生产推荐）。

```text
# bucket sampler 简化实现
import torch
from torch.utils.data import Sampler

class BucketSampler(Sampler):
    """按分辨率分桶采样，保证同 batch 同分辨率"""
    def __init__(self, dataset, bucket_specs, batch_size, shuffle=True):
        # bucket_specs = [(1024, 1024), (768, 1344), (1344, 768), ...]
        self.dataset = dataset
        self.bucket_specs = bucket_specs
        self.batch_size = batch_size
        self.shuffle = shuffle

        # 1. 把每个样本归到最近的 bucket
        self.buckets = {b: [] for b in bucket_specs}
        for idx, sample in enumerate(dataset):
            h, w = sample["height"], sample["width"]
            bucket = self._match_bucket(h, w)
            self.buckets[bucket].append(idx)

    def _match_bucket(self, h, w):
        """找最接近的 bucket"""
        best = None
        best_diff = float("inf")
        for (bh, bw) in self.bucket_specs:
            diff = abs(h - bh) + abs(w - bw)
            if diff < best_diff:
                best_diff = diff
                best = (bh, bw)
        return best

    def __iter__(self):
        # 2. 每 batch 从某个 bucket 抽 batch_size 个样本
        all_batches = []
        for bucket, indices in self.buckets.items():
            # 打乱桶内顺序
            if self.shuffle:
                indices = indices.copy()
                torch.manual_seed(0)
                torch.randperm(len(indices), out=torch.tensor(indices))
            # 切 batch
            for i in range(0, len(indices), self.batch_size):
                all_batches.append(indices[i:i + self.batch_size])

        # 3. 打乱 batch 顺序（不同 bucket 交替训练）
        if self.shuffle:
            import random
            random.shuffle(all_batches)

        for batch in all_batches:
            yield batch

    def __len__(self):
        return sum(
            (len(v) + self.batch_size - 1) // self.batch_size
            for v in self.buckets.values()
        )
```

### 2.5 加速方案四：torch.compile + BF16/FP8 混合精度

**torch.compile 在 DiT 训练上的收益**：DiT 的前向是纯 Transformer（attention + FFN + AdaLN-Zero），无 data-dependent control flow，**满足 `fullgraph=True` 编译条件**。compile 通过算子融合（RMSNorm + GEMM、SwiGLU 融合、AdaLN 的 6 路 scale/shift 融合）减少 kernel launch 和中间显存。

```text
# Flux 训练时 compile DiT 主体
import torch

model = FluxTransformer2DModel.from_pretrained(...).to("cuda")
model = torch.compile(model, mode="max-autotune", fullgraph=True)

# 优化器也要 compile 感知（FusedAdam）
optimizer = torch.optim.AdamW(model.parameters(), lr=1e-4, fused=True)
```

**BF16 vs FP8 混合精度训练**：

| 精度 | 权重 | 激活 | 梯度 | DiT 训练稳定性 | 算力 |
| --- | --- | --- | --- | --- | --- |
| FP32 | FP32 | FP32 | FP32 | ★★★★★ | 1× |
| BF16 | BF16 | BF16 | BF16 | ★★★★☆ | 2× |
| BF16 + FP8 attention | BF16 | FP8 (attn only) | BF16 | ★★★☆☆ | 3× |
| 全 FP8（实验性） | FP8 | FP8 | FP8 | ★★☆☆☆ | 4× |

DiT 训练**推荐 BF16**——稳定性高、算力翻倍、H100 原生支持。FP8 attention 在 H100 上可用 FA3 实现，但训练时激活分布波动大（不同 timestep 的 attention 激活范围差异大），需要 per-step scaling，工程复杂。**生产训练一般 BF16，FP8 留给推理**。

### 2.6 结构-训练协同：双流 attention 融合 + AdaLN-Zero 预计算

把前面四个加速方案串起来，得到 Flux 训练的”结构-加速协同”清单：

| 结构特点 | 加速方案 | 收益 |
| --- | --- | --- |
| MM-DiT 双流 attention（拼接后 self-attn） | FA3 一次调用处理整条序列 | 1.3× vs cross-attn + FA2 |
| AdaLN-Zero 的 d→6d GEMM | batch 内同 timestep 复用 + 预计算 | 5-8% 端到端 |
| 双向 attention（无 causal mask） | FA 完美适配，无 mask 拼接开销 | 利用率 95%+ |
| T5-XXL / VAE 冻结 | latent + 文本预编码 | 吞吐 2.2× |
| 多分辨率数据 | bucket sampler + dynamic compile | 不损失信息 |
| Flow Matching（target 集中） | 大学习率 + 少 step | 收敛快 20-30% |
| 纯 Transformer（无 control flow） | torch.compile(fullgraph=True) | 1.2× |

### 2.7 Flux 12B FSDP 训练配置

Flux 12B 在 8 卡 H100 上训练，**首选 FSDP 而非 TP**。这是结构-并行的协同决策：

- **TP 切 attention head**：Flux 的 `num_heads = 24`，TP=8 时每卡 3 head，可行但通信频繁（每层 2 次 all-reduce，30 层 = 60 次/step）
- **FSDP 切参数**：把 12B 参数切到 8 卡，每卡 1.5B 激活，前向/反向按需 all-gather 参数。通信量与 TP 相当，但实现简单（PyTorch 原生）

**为什么 Flux 选 FSDP 而不是 TP？** 三个理由：

1. **DiT attention 是双向 full attention**，不像 GQA 有 KV head 数限制 TP 上限——TP 与 FSDP 在 DiT 上都能切，FSDP 实现更简单；
2. **DiT 训练 batch_size 较小**（每卡 1-2 个 1024×1024 样本），TP 的算力利用率优势不明显，FSDP 的显存优势更直接；
3. **FSDP 不需要改模型代码**（TP 要重写 attention/FFN 的切分逻辑），对 diffusers 生态友好。

```text
# flux_fsdp_train.py
# Flux 12B 在 8 卡 H100 上 FSDP 训练
import torch
import torch.distributed as dist
from torch.distributed.fsdp import FullyShardedDataParallel as FSDP
from torch.distributed.fsdp import ShardingStrategy, MixedPrecision
from diffusers import FluxTransformer2DModel
from flash_attn import flash_attn_func

# 1. 初始化分布式
dist.init_process_group(backend="nccl")
rank = dist.get_rank()
torch.cuda.set_device(rank)

# 2. 加载 DiT 主体（每卡都加载完整权重，FSDP 会切分）
model = FluxTransformer2DModel.from_pretrained(
    "black-forest-labs/FLUX.1-dev",
    subfolder="transformer",
    torch_dtype=torch.bfloat16,
).to(f"cuda:{rank}")

# 3. FSDP 包装
mp_policy = MixedPrecision(
    param_dtype=torch.bfloat16,    # 参数 BF16
    reduce_dtype=torch.bfloat16,   # 梯度 reduce BF16
    buffer_dtype=torch.bfloat16,
)
model = FSDP(
    model,
    sharding_strategy=ShardingStrategy.FULL_SHARD,  # 完全切分
    mixed_precision=mp_policy,
    device_id=rank,
    use_orig_params=True,  # 兼容 optimizer state
)

# 4. compile（FSDP + compile 兼容，PyTorch 2.4+）
model = torch.compile(model, mode="max-autotune")

# 5. 优化器（fused AdamW）
optimizer = torch.optim.AdamW(model.parameters(), lr=1e-4, weight_decay=0.01, fused=True)

# 6. 训练循环（latent + 文本预编码版本）
from torch.utils.data import DataLoader
dataset = PrecomputedLatentDataset("data/latents", "data/embeddings")
sampler = BucketSampler(dataset,
    bucket_specs=[(1024, 1024), (768, 1344), (1344, 768), (896, 1152)],
    batch_size=1,  # 每卡 batch=1，8 卡全局 batch=8
)
loader = DataLoader(dataset, batch_sampler=sampler, num_workers=4)

model.train()
for step, batch in enumerate(loader):
    latent = batch["latent"].to(f"cuda:{rank}")         # [B, 16, 128, 128]
    txt_emb = batch["txt_emb"].to(f"cuda:{rank}")       # [B, 512, 4096]
    txt_pool = batch["txt_pool"].to(f"cuda:{rank}")     # [B, 4096]
    timestep = batch["timestep"].to(f"cuda:{rank}")     # [B]

    # Flow Matching 训练目标
    # 1. 采样 x_0 (latent) 和 x_1 (noise), t ~ U[0, 1]
    noise = torch.randn_like(latent)
    t = torch.rand(latent.shape[0], device=latent.device)
    # 2. 线性插值 x_t = (1-t)·x_0 + t·x_1
    x_t = (1 - t[:, None, None, None]) * latent + t[:, None, None, None] * noise
    # 3. target velocity v = x_1 - x_0 = noise - latent
    v_target = noise - latent
    # 4. DiT 预测速度
    v_pred = model(x_t, timestep=t * 1000, encoder_hidden_states=txt_emb,
                   pooled_projections=txt_pool).sample
    # 5. MSE loss
    loss = torch.nn.functional.mse_loss(v_pred, v_target)

    optimizer.zero_grad(set_to_none=True)
    loss.backward()
    torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
    optimizer.step()

    if rank == 0 and step % 10 == 0:
        print(f"step {step}, loss {loss.item():.4f}")
```

## 3 图像 DiT 推理加速（Flux / SD3，结构-推理协同）

图像 DiT 推理的核心瓶颈是**多步迭代**——Flux 标准推理 28-50 步去噪，每步是一次完整的 12B 参数 transformer 前向。本节聚焦”**结构如何决定推理加速方案**“。

### 3.1 结构特点：多步去噪，每步一次 DiT 前向

![](https://pic4.zhimg.com/v2-1d822b519946dc22032c5ccfec12643f_r.jpg)

从推理加速的角度，这个结构有四个关键性质：

**性质 1：每步 latent 都变 → 无 KV Cache。**

这是 DiT 推理与 LLM 推理最根本的差异。LLM decode 时历史 token 的 K/V 不变，可以缓存；DiT 每步的整个 latent 都在变（去噪过程在 refine），K/V 完全不同，无法跨步缓存。**这意味着 DiT 推理不能用 PagedAttention / Continuous Batching 那套**。

**性质 2：每步 timestep 都变 → timestep emb 每步重算。**

AdaLN-Zero 的输入 `c = t_emb + txt_pool_emb`，其中 `t_emb` 随 timestep 变化（每步不同）。所以每步的 `Linear(d→6d)` GEMM 都要重算，不能跨步复用。这与训练时（同 batch 同 timestep 可复用）不同。

**性质 3：每步文本 emb 相同 → 文本流可优化。**

MM-DiT 双流 attention 中，文本流的输入 `x_txt = txt_emb` 在所有去噪步中**完全相同**。这给了一个推理优化机会：文本流的 Q/K/V 投影结果在所有步中相同，可以**只算一次缓存复用**（部分模型的”双流分离”优化）。

**性质 4：compute-bound → 量化直接提算力。**

1.3 推导过，DiT 单步算术强度 ~8000 FLOP/byte，严重 compute-bound。FP8 把 H100 Tensor Core 算力翻倍（1979 vs 989 TFLOPS），单步延迟直接 ~2× 加速。

### 3.2 加速方案一：torch.compile 编译 DiT

DiT 前向是纯 Transformer，无 data-dependent control flow，**完美满足 `fullgraph=True`**。compile 的收益来自：

1. **算子融合**：RMSNorm + GEMM、SwiGLU 的 silu(gate) * up 融合、AdaLN 的 6 路 scale/shift 融合
2. **kernel launch 减少**：30 层 × 每层 ~10 个 kernel = 300 个 kernel/step，融合后降到 ~50 个
3. **中间显存减少**：融合后中间张量不落显存

```text
# Flux 推理 compile 配置
pipe.transformer = torch.compile(
    pipe.transformer,
    mode="max-autotune",  # 最激进优化，含 autotuning
    fullgraph=True,       # 整图编译
)
# 首次调用触发编译，约 30-60s 编译开销；后续调用快
```

**compile 的坑（DiT 专属）**：

| 问题 | 原因 | 解法 |
| --- | --- | --- |
| 首次编译 30-60s | max-autotune 触发 autotuning | 服务长驻时无所谓，短脚本用 default mode |
| 跨分辨率重编译 | token 数变化触发 dynamic shape | 用 dynamic=True 或预编译常见分辨率 |
| LoRA 切换重编译 | LoRA 改变了权重 shape | 用 fullgraph=False 或预编译常见 LoRA |
| CFG 改变重编译 | guidance_scale 变化 | CFG 蒸馏后无 CFG（见 3.4） |

### 3.3 加速方案二：FP8 量化（Hopper）

DiT 是 compute-bound，FP8 直接提算力（H100 FP8 Tensor Core 算力 1979 TFLOPS，BF16 的 2×）。**FP8 在 DiT 推理上的收益远大于 LLM 推理**——LLM decode 是 memory-bound，FP8 只省显存不省延迟；DiT 是 compute-bound，FP8 直接 ~2× 加速。

```text
FP8 在 DiT vs LLM 推理的收益对比：

LLM decode（memory-bound）：
  BF16: 140 GB 权重访存，140 GFLOP 计算 → 1 FLOP/byte
  FP8:  70 GB 权重访存，140 GFLOP 计算 → 2 FLOP/byte
  延迟: 受限于访存（70GB / 3TB/s = 23ms vs 140GB / 3TB/s = 47ms）
  收益: 延迟 2×（因为访存减半），但算力没用满

DiT 单步（compute-bound）：
  BF16: 24 GB 权重访存，192 TFLOP 计算 → 8000 FLOP/byte
  FP8:  12 GB 权重访存，192 TFLOP 计算 → 16000 FLOP/byte
  延迟: 受限于算力（192 TFLOP / 989 TFLOPS = 194ms BF16
                                 / 1979 TFLOPS = 97ms FP8）
  收益: 延迟 2×（因为算力翻倍），且算力被吃满
```

**FP8 格式选择**：DiT 推理用 **E4M3**（权重 + 激活）。E4M3 精度较高（~3.6 位有效），适合 DiT attention 激活范围集中的场景；E5M2 动态范围大但精度低，留给训练梯度用。

```text
# Flux FP8 推理配置
import torch
from diffusers import FluxPipeline

# 1. 加载 FP8 weight variant
pipe = FluxPipeline.from_pretrained(
    "black-forest-labs/FLUX.1-dev",
    torch_dtype=torch.bfloat16,   # 激活 BF16
    variant="fp8",                # 权重 FP8（E4M3）
)
pipe.to("cuda")

# 2. compile DiT
pipe.transformer = torch.compile(pipe.transformer, mode="max-autotune")

# 3. 生成
image = pipe(
    prompt="a photorealistic cat on a wooden table",
    num_inference_steps=28,
    guidance_scale=3.5,
    height=1024, width=1024,
).images[0]
```

### 3.4 加速方案三：CFG 优化

**CFG（Classifier-Free Guidance）** 是扩散模型的条件生成核心机制——同时前向”有条件”和”无条件”两个分支，用两者的差值放大条件信号：

```text
ε_cfg = ε_uncond + guidance_scale · (ε_cond - ε_uncond)
```

CFG 的结构代价：**每步要前向 2 次 DiT**（cond + uncond）。28 步去噪 = 56 次 DiT 前向，CFG 直接让推理慢 2×。

```text
CFG 推理（默认）：
  step 1: DiT(x, t, txt=∅)     → ε_uncond    ← 前向 1
          DiT(x, t, txt=prompt) → ε_cond      ← 前向 2
          ε_cfg = ε_uncond + s·(ε_cond - ε_uncond)
          x = sampler.step(ε_cfg, t, x)
  ...
  step 28: 同上
  总前向: 28 × 2 = 56 次

CFG 优化方案：
  1. CFG 蒸馏：训练时把 CFG 蒸进权重，推理无 CFG（前向减半）
  2. CFG 缩放：低 CFG（guidance_scale=1.0）时 cond/uncond 接近，可近似
  3. Batch 合并：cond/uncond 拼成一个 batch 一次前向（不省算力但省 launch）
  4. Inverted CFG：早期步用 CFG，晚期步（细节）不用 CFG
```

**结构-CFG 协同**：MM-DiT 的双流 attention 让 cond/uncond 可以**拼成 batch 一次前向**——双流的文本流分支分别为 prompt 和 ∅，图像流共享。这让 CFG 的 2× 算力代价不变，但 launch 开销减半（1 次 FA 调用 vs 2 次）。

```text
# CFG batch 合并（diffusers 内部已实现）
# cond/uncond 拼成 batch=2 一次前向
def forward_with_cfg(model, x, t, txt_cond, txt_uncond, guidance_scale):
    # 1. 拼接 cond/uncond
    x_batch = x.repeat(2, 1, 1, 1)  # [2, ...]
    txt_batch = torch.cat([txt_uncond, txt_cond], dim=0)  # [2, ...]

    # 2. 一次前向（batch=2）
    out = model(x_batch, t, txt_batch)  # [2, ...]

    # 3. CFG 计算
    out_uncond, out_cond = out.chunk(2)
    out_cfg = out_uncond + guidance_scale * (out_cond - out_uncond)
    return out_cfg
```

**CFG 蒸馏（最佳方案）**：把 CFG 直接蒸进模型权重，推理时 `guidance_scale=0`，只前向 1 次。Flux Schnell 就是 CFG 蒸馏版本（`guidance_scale=0`，4 步生成）。

### 3.5 加速方案四：step distillation（LCM / Schnell / Turbo）

**step distillation 是 DiT 独有的推理加速手段**——LLM 的”步数”是 token 数，不能减少；DiT 的”步数”是去噪步数，可通过蒸馏从 50 步降到 4 步，直接 12× 加速。

```text
step distillation 原理：

Teacher（50 步）：
  x_T → x_49 → x_48 → ... → x_1 → x_0
  （50 次 DiT 前向）

Student（4 步）：
  x_T → x_3 → x_2 → x_1 → x_0
  （4 次 DiT 前向，每步跨 12.5 个 teacher 步）

蒸馏 loss：
  L = MSE(ε_student(x_t, t), ε_teacher_trajectory(x_t, t))
  让 student 的"大步去噪"轨迹与 teacher 的"小步去噪"轨迹一致
```

**主流 step distillation 方法**：

| 方法 | 原理 | 步数 | 质量 | 代表 |
| --- | --- | --- | --- | --- |
| LCM (Latent Consistency) | 一致性蒸馏，让 student 在任意 t 都映射到 x_0 | 4-8 | ★★★★ | LCM-LoRA |
| SDXL Turbo | Adversarial + Diffusion 联合蒸馏 | 1-4 | ★★★★ | SDXL Turbo |
| Flux Schnell | Flow Matching + 蒸馏 | 4 | ★★★★ | Flux.1-schnell |
| SD3.5 Turbo | SD3 + 蒸馏 | 4 | ★★★★ | SD3.5-large-turbo |
| DMD2 (Distribution Matching Distillation) | 分布匹配蒸馏 | 1-4 | ★★★☆ | DMD2 |

**结构-step distillation 协同**：step distillation 之所以在 DiT 上可行而在 LLM 上不可行，根本原因是**DiT 的步数是迭代去噪步**（同 latent 反复 refine），而 **LLM 的步数是 token 数**（不同 token 序列展开）。DiT 的去噪轨迹是连续的（latent 在流形上滑动），可以被少步近似；LLM 的 token 序列是离散的，不能少步近似。

### 3.6 加速方案五：latent / VAE decode 优化

VAE Decoder 把 latent `[16, 128, 128]` 上采样回图像 `[3, 1024, 1024]`，是推理的最后一阶段。VAE 虽小（~0.1B），但输出大（3×1024×1024 = 3M pixel），且是卷积（不像 attention 容易加速）。

```text
# VAE tiling + fp8 优化
pipe.vae.enable_tiling()  # 分块解码，减显存
pipe.vae.to(torch.float8_e4m3fn)  # FP8（实验性，质量略降）
```

**结构-VAE 协同**：VAE 是**纯卷积**（无 attention），它的算术强度比 DiT 主体低（卷积的 FLOPs/byte 比例低于 attention），属于”轻度 memory-bound”。所以 VAE 量化的延迟收益不如 DiT 主体大，但 tiling 能减显存（高分辨率必须）。

### 3.7 结构-推理协同总表

| 结构特点 | 加速方案 | 收益 |
| --- | --- | --- |
| 多步去噪（28-50 步） | step distillation（4-8 步） | 5-12× |
| compute-bound | FP8 量化 | 2× |
| 纯 Transformer（无 control flow） | torch.compile(fullgraph=True) | 1.3× |
| CFG 双前向 | CFG 蒸馏 / batch 合并 | 2×（蒸馏）/ 1.1×（batch） |

| VAE 输出大 | VAE tiling + FP8 | 显存减半 |

## 4 视频 DiT 训练加速（HunyuanVideo / CogVideoX）

视频 DiT 是 DiT 训练最难的分支——3D attention 的 O((T·H·W)²) 复杂度让单卡显存爆炸，3D VAE 的视频数据吞吐让 IO 成为瓶颈。本节讲”**结构如何决定训练加速方案**“。

### 4.1 结构特点：3D attention + 3D VAE + temporal consistency

视频 DiT 把图像 DiT 的 2D latent 扩展到 3D：`[C, T, H, W]`。3D VAE 把视频 `[3, T_raw, H_raw, W_raw]` 压成 latent `[C, T_raw/f_t, H_raw/f_s, W_raw/f_s]`（HunyuanVideo 是 `[16, T/4, H/8, W/8]`）。

![](https://pic3.zhimg.com/v2-44d7c9c3e0ec608a1b0fb91a9c575b72_r.jpg)

从训练加速的角度，视频 DiT 有四个关键性质：

**性质 1：3D attention 的 O((T·H·W)²) 必须分解。**

完整 3D attention 的复杂度是 `O((T·H·W)²)`。HunyuanVideo 的 180K token 对应 attention 矩阵 180K×180K = 32B 元素，单层单头显存 128 GB——单卡 H100 80GB 装不下。**必须分解成 spatial + temporal attention**，把复杂度降到 `O(T·(H·W)² + (H·W)·T²)`。

**性质 2：3D VAE 压缩比决定 token 数。**

3D VAE 的压缩比 `(f_t, f_s, f_s)` 直接决定 latent 大小。HunyuanVideo 用 `(4, 8, 8)`，CogVideoX 用 `(8, 8, 8)`——CogVideoX 的时序压缩更激进（8× vs 4×），同长度视频 token 数少一半。**结构选择直接决定计算量**。

**性质 3：temporal attention 是优化重点（跨帧依赖）。**

分解后，spatial attention（每帧 H×W）和 temporal attention（每像素 T）的复杂度差距巨大：

```text
HunyuanVideo 5s 视频 (T=50, H=90, W=160 after VAE):
  spatial attention: T × (H·W)² = 50 × (90·160)² = 50 × 14400² ≈ 1.0e10
  temporal attention: (H·W) × T² = 14400 × 50² = 14400 × 2500 ≈ 3.6e7
  比例: spatial : temporal ≈ 280 : 1

  → spatial attention 占 99.6% 计算量，temporal 只占 0.4%
  → 但 temporal 是跨帧一致性的关键（不能省）
  → 优化重点: spatial 用 FA3，temporal 可独立优化（序列短）
```

**性质 4：3D VAE 离线预编码 + 视频数据吞吐是 IO 瓶颈。**

视频数据量大（5s 720p 视频 ~50MB），训练时如果在线解码（H.264 → tensor → VAE encode）会拖慢整个训练。**NVDEC 硬件解码 + WebDataset 流式读取 + VAE 离线预编码**是必须的组合。

### 4.2 加速方案一：3D attention 分解（spatial + temporal）

3D attention 分解的核心思想：**把 `O((T·H·W)²)` 的全 attention 拆成两次低维 attention**，分别处理空间维度和时间维度。

![](https://picx.zhimg.com/v2-9ec65e152aa8a391904d1725a4f8d3a1_r.jpg)

**结构-分解协同**：3D attention 分解本质上是把”全 3D 依赖”近似为”空间-时间可分离依赖”。这在数学上等价于假设”帧内空间结构和帧间时序变化可解耦”——对大多数自然视频成立，但对强时空耦合场景（如快速运动 + 复杂空间结构）会有质量损失。

```text
# 3D attention 分解实现（PyTorch + FA3）
import torch
from flash_attn import flash_attn_func

class Factorized3DAttention(torch.nn.Module):
    """spatial + temporal 分解的 3D attention"""
    def __init__(self, d_model, n_heads, head_dim):
        super().__init__()
        self.n_heads = n_heads
        self.head_dim = head_dim
        self.d_model = d_model

        # spatial attention 的 QKV（每帧内）
        self.W_Q_s = torch.nn.Linear(d_model, n_heads * head_dim)
        self.W_K_s = torch.nn.Linear(d_model, n_heads * head_dim)
        self.W_V_s = torch.nn.Linear(d_model, n_heads * head_dim)
        self.W_O_s = torch.nn.Linear(n_heads * head_dim, d_model)

        # temporal attention 的 QKV（每像素跨帧）
        self.W_Q_t = torch.nn.Linear(d_model, n_heads * head_dim)
        self.W_K_t = torch.nn.Linear(d_model, n_heads * head_dim)
        self.W_V_t = torch.nn.Linear(d_model, n_heads * head_dim)
        self.W_O_t = torch.nn.Linear(n_heads * head_dim, d_model)

    def forward(self, x):
        """x: [B, T, H, W, d] → [B, T, H, W, d]"""
        B, T, H, W, d = x.shape
        N_s = H * W  # spatial token 数

        # ============ Step 1: Spatial attention ============
        # reshape: [B, T, H, W, d] → [B*T, H*W, d]
        x_s = x.reshape(B * T, N_s, d)

        Q = self.W_Q_s(x_s).view(B * T, N_s, self.n_heads, self.head_dim)
        K = self.W_K_s(x_s).view(B * T, N_s, self.n_heads, self.head_dim)
        V = self.W_V_s(x_s).view(B * T, N_s, self.n_heads, self.head_dim)

        # FA3 处理每帧的 spatial attention（无 causal mask）
        out_s = flash_attn_func(Q, K, V, causal=False)  # [B*T, N_s, n_heads, head_dim]
        out_s = out_s.reshape(B * T, N_s, d)
        x_s = x_s + self.W_O_s(out_s)  # residual

        # reshape back: [B*T, H*W, d] → [B, T, H, W, d]
        x = x_s.reshape(B, T, H, W, d)

        # ============ Step 2: Temporal attention ============
        # reshape: [B, T, H, W, d] → [B*H*W, T, d]
        x_t = x.permute(0, 2, 3, 1, 4).reshape(B * N_s, T, d)

        Q = self.W_Q_t(x_t).view(B * N_s, T, self.n_heads, self.head_dim)
        K = self.W_K_t(x_t).view(B * N_s, T, self.n_heads, self.head_dim)
        V = self.W_V_t(x_t).view(B * N_s, T, self.n_heads, self.head_dim)

        # temporal attention，序列短（T~50），FA 也可用，或直接 torch attention
        out_t = flash_attn_func(Q, K, V, causal=False)  # [B*N_s, T, n_heads, head_dim]
        out_t = out_t.reshape(B * N_s, T, d)
        x_t = x_t + self.W_O_t(out_t)

        # reshape back: [B*H*W, T, d] → [B, T, H, W, d]
        x = x_t.reshape(B, H, W, T, d).permute(0, 3, 1, 2, 4).contiguous()
        return x
```

**复杂度对比**：

| 方案 | 复杂度 | 显存（单层） | HunyuanVideo 5s 实测 |
| --- | --- | --- | --- |
| 全 3D attention | O((T·H·W)²) | 128 GB | OOM |
| spatial + temporal 分解 | O(T·(H·W)² + (H·W)·T²) | 3 MB + 144 MB | 5 GB / 层 |
| 仅 spatial（无 temporal） | O(T·(H·W)²) | 3 MB | 4 GB / 层（质量降） |

### 4.3 加速方案二：时序 CP（Context Parallel）

3D attention 分解解决了**单卡显存**问题，但单卡算力仍然不够——5s 视频训练单步要几十秒。需要多卡并行，**时序 CP（Context Parallel）** 是视频 DiT 训练的首选并行方案。

**为什么视频 DiT 选 CP 而不是 TP/PP？** 三个理由：

1. **3D attention 分解后，spatial attention 是 per-frame 独立的**——把帧切到多卡，每卡算自己的帧，无需跨卡通信（除 temporal attention 外）；
2. **TP 切 attention head**：HunyuanVideo 的 `num_heads = 24`，TP=8 时每卡 3 head，但 attention 矩阵大（180K²），TP 通信频繁；
3. **PP 切层**：30 层切 PP=4，每 stage 7-8 层，但视频 DiT 的中间激活大（180K × d × 30 层），PP 的 activation buffer 显存爆炸。

**时序 CP 沿时间维度切分**：每卡负责一部分帧的 spatial attention，temporal attention 用 Ring / Ulysses 通信。

![](https://pic2.zhimg.com/v2-6e95ab623ccba0e181967b1c86d20ddf_r.jpg)

```text
# 时序 CP 实现（Ulysses 模式，伪代码）
import torch
import torch.distributed as dist

class TemporalCP(torch.nn.Module):
    """时序 CP：沿 T 切分，temporal attention 用 Ulysses all-to-all"""
    def __init__(self, cp_size, n_heads, head_dim):
        super().__init__()
        self.cp_size = cp_size
        self.rank = dist.get_rank()
        self.n_heads = n_heads
        self.head_dim = head_dim

    def forward(self, x, temporal_attn_fn):
        """x: [B, T, H, W, d] (完整 T) → [B, T, H, W, d]"""
        B, T, H, W, d = x.shape
        # 1. 沿 T 切分到各卡
        T_per_rank = T // self.cp_size
        x_local = x[:, self.rank * T_per_rank:(self.rank + 1) * T_per_rank]
        # x_local: [B, T/cp, H, W, d]

        # 2. spatial attention（每卡独立，无通信）
        # ... 略，见 4.2 的 spatial attention ...

        # 3. temporal attention 前先 all-to-all
        # reshape: [B, T/cp, H, W, d] → [B, T, H/cp, W/cp, d]
        # 通过 all-to-all 把 T 维聚合，把 H·W 维分散
        x_local = x_local.reshape(B * T_per_rank, H * W, d)
        # all-to-all: 每卡发 (B*T/cp, H*W/cp, d)，收 (B*T, H*W/cp, d)
        x_gathered = [torch.zeros_like(x_local[:, :H*W//self.cp_size])
                      for _ in range(self.cp_size)]
        dist.all_to_all(x_gathered,
                       [x_local[:, i*H*W//self.cp_size:(i+1)*H*W//self.cp_size]
                        for i in range(self.cp_size)])
        x_full_t = torch.cat(x_gathered, dim=0)  # [B*T, H*W/cp, d]

        # 4. 每卡对自己负责的 H*W/cp 像素做完整 T 的 temporal attn
        out_full_t = temporal_attn_fn(x_full_t)

        # 5. all-to-all 换回
        # ... 反向 all-to-all，恢复 [B, T/cp, H, W, d] ...
        return x  # [B, T, H, W, d]
```

### 4.4 加速方案三：FlashAttention + latent 预编码 + 视频数据吞吐

**FlashAttention 在视频 DiT 上的特殊性**：视频 DiT 的 spatial attention 序列长度是 `H·W`（HunyuanVideo ~14K），FA3 在这个长度上效率最高（短序列 FA3 的 persistent kernel 优势明显）。temporal attention 序列长度是 `T`（~50），FA 收益小，可直接用 PyTorch attention。

**3D VAE 离线预编码**：与图像 DiT 类似，3D VAE 也是冻结的，可离线预编码整个视频数据集。

```text
# 3D VAE 预编码（HunyuanVideo 风格）
import torch
from diffusers import AutoencoderKLHunyuanVideo

vae = AutoencoderKLHunyuanVideo.from_pretrained("...", torch_dtype=torch.bfloat16).to("cuda")

def encode_video(video_tensor):
    """video_tensor [B, C=3, T_raw, H_raw, W_raw] → latent [B, 16, T/4, H/8, W/8]"""
    with torch.no_grad():
        # 3D VAE 编码（时序 4× + 空间 8× 下采样）
        latent = vae.encode(video_tensor).latent_dist.sample()
    return latent  # 存盘
```

| 在线 H.264 解码 + VAE encode | CPU 软解 | 5 video/s | 原型 |

## 5 视频 DiT 推理加速（CogVideoX / HunyuanVideo）

视频 DiT 推理的核心瓶颈是**长视频显存**——5s 视频的 latent + 多步去噪的中间激活，单卡装不下。本节讲”**结构如何决定推理加速方案**“。

### 5.1 结构特点：多步去噪 + 长视频显存

视频 DiT 推理的数据流与图像类似（多步去噪），但每步处理的 latent 是 3D 的（`[C, T, H, W]`），显存压力远大于图像：

```text
视频 DiT 推理显存分解（CogVideoX-5B，5s 720p 视频，50 步）：
  DiT 权重:         10 GB（BF16）
  latent (50 步):   50 × [16, 13, 90, 160] × 2B ≈ 1 GB（如不优化）
  激活 (单步):       30 层 × 180K token × 3072 d × 2B ≈ 33 GB
  txt_emb:          0.1 GB
  VAE:              0.4 GB
  ─────────────────────────
  总计:              ~45 GB / 单步（峰值）
  50 步去噪显存:     如果不释放中间 latent，~50 GB
```

从推理加速的角度，视频 DiT 有四个关键性质：

**性质 1：长视频显存爆炸 → 必须分块生成。**

10s 以上视频的 latent 太大（180K × 2 token），单步激活显存爆炸。**分块生成**——把长视频切成 5s 一块，逐块去噪——是长视频推理的核心方案。

**性质 2：每步 latent 变 → 无 KV Cache，但跨块条件帧可复用。**

视频 DiT 每步的整个 latent 都在变，无法跨步缓存。但**分块生成时，前一块的末尾几帧作为条件帧传入下一块**，这些条件帧的 KV 在两块间不变，可以复用。

**性质 3：3D attention 分解在推理时同样适用。**

训练时的 spatial + temporal 分解，推理时可直接复用，且推理 batch=1 时分解的收益更明显（无法用 batch 摊销 attention 矩阵显存）。

**性质 4：temporal attention 是跨帧一致性的关键。**

推理时 spatial attention 处理每帧内的空间结构，temporal attention 处理跨帧的时序一致性。**如果省掉 temporal attention，视频会帧间闪烁**——这是视频 DiT 推理质量的底线。

### 5.2 加速方案一：分块生成（chunk）+ 跨块一致性

**分块生成的核心思想**：把长视频切成短块（如 5s/块），逐块去噪。块与块之间通过**条件帧**（前块的末尾几帧）传递信息，保证跨块一致性。

![](https://pica.zhimg.com/v2-bf895480d73a34fccec5d75398b3f550_r.jpg)

```text
# 视频分块生成实现
import torch

def generate_long_video(pipe, prompt, total_seconds=15, chunk_seconds=5, overlap_seconds=1):
    """长视频分块生成"""
    fps = 24
    total_frames = total_seconds * fps
    chunk_frames = chunk_seconds * fps
    overlap_frames = overlap_seconds * fps

    all_latents = []
    prev_cond_latent = None  # 前一块的条件帧

    for chunk_idx in range(0, total_seconds, chunk_seconds - overlap_seconds):
        if chunk_idx + chunk_seconds > total_seconds:
            break  # 最后一块

        # 1. 生成本块的初始噪声
        latent_shape = (1, 16, chunk_frames // 4, 90, 160)  # T/4 时序压缩
        noise = torch.randn(latent_shape, device="cuda")

        # 2. 注入条件帧（前一块的末尾 overlap_frames 帧）
        if prev_cond_latent is not None:
            # 把条件帧的 latent 填到本块开头
            cond_T = overlap_frames // 4  # 时序压缩后的条件帧数
            noise[:, :, :cond_T] = prev_cond_latent[:, :, -cond_T:]

        # 3. 去噪本块（50 步，条件帧不变，新生成帧逐步去噪）
        # 用 mask 标记哪些帧是条件帧（不变），哪些是生成帧（去噪）
        cond_mask = torch.zeros(latent_shape[2], device="cuda")
        if prev_cond_latent is not None:
            cond_mask[:cond_T] = 1.0  # 条件帧

        latent = pipe.denoise_chunk(
            noise, prompt=prompt,
            cond_mask=cond_mask,  # 条件帧不更新
            num_inference_steps=50,
        )

        # 4. 保存本块（去重叠部分）
        if prev_cond_latent is None:
            # 第一块，全保存
            all_latents.append(latent)
        else:
            # 后续块，去掉开头的重叠部分
            all_latents.append(latent[:, :, cond_T:])

        # 5. 更新条件帧（本块末尾 overlap_frames 帧）
        prev_cond_latent = latent

    # 6. 拼接所有块
    full_latent = torch.cat(all_latents, dim=2)

    # 7. VAE 解码为视频
    video = pipe.vae.decode(full_latent)
    return video
```

**结构-分块协同**：分块生成的本质是把”全视频 attention”近似为”块内 attention + 块间条件传递”。这在数学上等价于假设”远距离帧的依赖可通过中间帧间接传递”——对自然视频成立（一帧的内容主要由前一帧决定），但对强全局依赖场景（如长镜头运动）会有质量损失。

### 5.3 加速方案二：跨步 KV Cache 复用

虽然 DiT 每步 latent 都变（无跨步 KV Cache），但**分块生成时，条件帧的 KV 可跨步复用**。这是视频 DiT 推理的独有优化。

```text
跨步 KV Cache 复用（分块生成场景）：

Block 2 的 latent = [cond_frames (不变), generate_frames (变)]
  step 1: 算 cond + generate 的 K, V → 缓存 cond 部分
  step 2: latent 变了，但 cond 部分没变 → 复用 cond 的 K, V
          只算 generate 部分的新 K, V
  step 50: 同上

  收益: cond 部分的 K/V 计算从 50 次降到 1 次
       如果 cond 占块内 20%（1s/5s），节省 ~20% attention 计算
# 跨步 KV Cache 复用（条件帧的 K/V 缓存）
class ChunkedDiTWithKVCfg:
    """分块生成 + 条件帧 KV 跨步复用"""
    def __init__(self, dit_model):
        self.dit = dit_model
        self.cond_kv_cache = None  # [层, cond_frames, d]

    def forward_step(self, latent, timestep, txt_emb, cond_mask):
        """
        latent: [B, T, H, W, d]
        cond_mask: [T]，1 = 条件帧（不变），0 = 生成帧
        """
        cond_T = cond_mask.sum().item()
        gen_T = latent.shape[1] - cond_T

        if self.cond_kv_cache is None:
            # 第一步：计算全量 K, V，缓存条件帧部分
            full_out = self.dit(latent, timestep, txt_emb)
            # 提取条件帧的 K, V 缓存
            self.cond_kv_cache = self._extract_cond_kv(latent[:, :cond_T])
            return full_out
        else:
            # 后续步：条件帧复用 K/V，只算生成帧
            gen_latent = latent[:, cond_T:]  # [B, gen_T, H, W, d]
            gen_out = self.dit(gen_latent, timestep, txt_emb,
                              cond_kv=self.cond_kv_cache)  # 注入缓存
            # 拼接条件帧的输出（不变）和生成帧的输出
            cond_out = self.dit.decode_with_kv(latent[:, :cond_T],
                                                self.cond_kv_cache)
            return torch.cat([cond_out, gen_out], dim=1)

    def reset_cache(self):
        """每个新块开始时清空缓存"""
        self.cond_kv_cache = None
```

**结构-跨步 KV 协同**：跨步 KV 复用之所以在视频分块生成上可行，是因为**条件帧的 latent 在去噪过程中不变**（被 mask 固定）。这与 LLM 的 KV Cache（历史 token 不变）有相似的数学结构，但应用场景不同——LLM 是 token 级 KV 复用，视频分块是帧级 KV 复用。

### 5.4 加速方案三：step distillation（视频蒸馏）

图像 DiT 的 step distillation（LCM/Schnell）可直接迁移到视频，但视频蒸馏有额外挑战：

1. **视频质量评估更难**：FID 不够，需要 FVD（Fréchet Video Distance）、时序一致性指标
2. **训练成本高**：teacher 的 50 步视频前向已经慢，蒸馏的 student forward + teacher forward 更慢
3. **跨帧一致性敏感**：少步蒸馏容易让帧间闪烁加剧

```text
# 视频 step distillation（简化版 LCM 思路）
def video_lcm_distill_step(student, teacher, dataloader, optimizer):
    """一步 LCM 蒸馏"""
    for batch in dataloader:
        latent = batch["latent"]  # [B, C, T, H, W]
        txt_emb = batch["txt_emb"]

        # 1. teacher 多步去噪（生成 target 轨迹）
        with torch.no_grad():
            x_t = torch.randn_like(latent)  # 噪声起点
            teacher_trajectory = [x_t]
            for t in range(50, 0, -1):
                v_pred = teacher(x_t, t, txt_emb)
                x_t = x_t - v_pred * dt  # teacher 小步去噪
                teacher_trajectory.append(x_t)
            x_0_teacher = x_t  # teacher 的最终输出

        # 2. student 4 步去噪
        x_t = torch.randn_like(latent)
        for t in [4, 3, 2, 1]:  # student 大步
            v_pred = student(x_t, t, txt_emb)
            x_t = x_t - v_pred * dt * 12.5  # 大步

        # 3. 一致性 loss：student 的输出应与 teacher 一致
        loss = torch.nn.functional.mse_loss(x_t, x_0_teacher)

        optimizer.zero_grad()
        loss.backward()
        optimizer.step()
```

**视频蒸馏的代表**：

| 模型 | 原始步数 | 蒸馏后步数 | 加速比 | 质量（FVD） |
| --- | --- | --- | --- | --- |
| CogVideoX-5B | 50 | 8 | 6× | FVD +5% |
| HunyuanVideo | 50 | 10 | 5× | FVD +8% |
| Open-Sora 2.0 | 30 | 6 | 5× | FVD +10% |

## 6 长视频 DiT 优化（Sora 类分钟级视频）

分钟级视频（60s+）是 DiT 最前沿的优化方向。Sora 类长视频的 latent 巨大（60s 视频 latent 720K+ token），即使分块也面临显存与一致性的双重挑战。本节讲”**结构如何决定长视频优化方案**“。

### 6.1 结构特点：分钟级视频，latent 巨大

```text
长视频 latent 规模对比：
  图像 (1024×1024):         16K token
  短视频 (5s 720p):         180K token
  中视频 (15s 720p):        540K token
  长视频 (60s 720p):        2.2M token  ← Sora 类
  超长视频 (5min 720p):     11M token   ← 极限

长视频的显存挑战：
  单步 attention 激活: 2.2M token × 30 层 × 3072 d × 2B ≈ 400 GB / 单步
  → 单卡 H100 80GB 完全装不下
  → 即使分块（5s/块 = 180K token），12 块的中间 latent 也很大
```

从长视频优化的角度，视频 DiT 有三个关键性质：

**性质 1：latent 必须部分 offload 到 CPU。**

60s 视频即使分块，单卡也装不下所有块的中间 latent。**latent offload**——CPU 缓存历史块的 latent，GPU 只放当前块——是必须的。

**性质 2：长视频必须用 causal attention。**

完整 3D attention 在 2.2M token 上不可行（O((2.2M)²) 爆炸）。分块生成时，**前块的 KV 可以传给后块**（causal attention），让后块只 attend 前块的 KV 而不重算。这是 StreamingLLM 思想在视频生成上的迁移。

**性质 3：temporal attention 必须稀疏化。**

长视频的 temporal attention 序列长度 T 很大（60s / 4 = 900 latent 帧），O(T²) 仍然爆炸。**稀疏化**——只 attend 关键帧（如每秒 1 帧）——是必须的。

### 6.2 优化方案一：latent offload

**latent offload 的核心思想**：GPU 只放当前块的 latent + 模型权重，历史块的 latent 全部 offload 到 CPU 内存（CPU 内存比 GPU 大 10×，且便宜）。

![](https://pic2.zhimg.com/v2-335243c17f3da2f9a5222e5321b8545f_r.jpg)

```text
# latent offload 实现
import torch

class LatentOffloader:
    """长视频 latent offload 管理"""
    def __init__(self, gpu_device="cuda", cpu_device="cpu"):
        self.gpu = gpu_device
        self.cpu = cpu_device
        self.cpu_latent_cache = {}  # {block_idx: latent_on_cpu}

    def to_gpu(self, block_idx, latent):
        """把 latent 搬到 GPU"""
        return latent.to(self.gpu, non_blocking=True)

    def to_cpu(self, block_idx, latent):
        """把 latent 搬到 CPU 缓存"""
        self.cpu_latent_cache[block_idx] = latent.to(self.cpu, non_blocking=True)
        # 释放 GPU 显存
        torch.cuda.empty_cache()

    def get_history_kv(self, block_idx, n_cond_frames=3):
        """获取前块的 KV 作为条件（搬到 GPU）"""
        if block_idx == 0:
            return None
        prev_latent = self.cpu_latent_cache[block_idx - 1]
        # 只取末尾 n_cond_frames 帧的 KV
        cond_latent = prev_latent[:, :, -n_cond_frames:].to(self.gpu, non_blocking=True)
        return cond_latent

# 使用
offloader = LatentOffloader()
for block_idx in range(12):
    # 1. 从 CPU 加载本块 latent 到 GPU
    latent = offloader.to_gpu(block_idx, latent)
    # 2. 获取前块 KV
    cond_kv = offloader.get_history_kv(block_idx)
    # 3. 去噪（注入 cond_kv）
    latent = dit_denoise(latent, cond_kv=cond_kv)
    # 4. 本块 latent offload 回 CPU
    offloader.to_cpu(block_idx, latent)
```

**结构-latent offload 协同**：latent offload 之所以在长视频上可行，是因为**分块生成让块间计算解耦**——每块只需要前块的末几帧 KV，不需要全部历史 latent。这让 GPU 显存不随视频长度增长，只随单块大小增长。这与 LLM 的 KV Cache offload 形成对比——LLM 的 KV Cache 随序列增长（每生成一个 token 加一份 KV），offload 的开销随序列增长。

### 6.3 优化方案二：causal attention（前 chunk KV 给后 chunk）

**causal attention 的核心思想**：长视频生成时，后块的帧只 attend 前块的 KV（不 attend 未来块），形成因果链。前块的 KV 可以缓存复用，避免重算。

![](https://picx.zhimg.com/v2-36948e1b1701eb12184214c803835d65_r.jpg)

```text
# causal attention + 跨块 KV Cache
class CausalLongVideoAttention:
    """长视频 causal attention，跨块 KV 复用"""
    def __init__(self):
        self.history_kv = None  # 历史块的 KV，跨块累积

    def forward(self, x_current, block_idx):
        """
        x_current: [B, T_current, H, W, d] 当前块的 latent
        block_idx: 当前块索引
        """
        # 1. 计算当前块的 Q, K, V
        Q = self.W_Q(x_current)
        K = self.W_K(x_current)
        V = self.W_V(x_current)

        # 2. 拼接历史 KV（causal：当前块 attend 历史块 + 自己）
        if self.history_kv is not None:
            K_full = torch.cat([self.history_kv[0], K], dim=1)  # [B, T_hist+T_curr, d]
            V_full = torch.cat([self.history_kv[1], V], dim=1)
        else:
            K_full, V_full = K, V

        # 3. causal attention（当前块只 attend 历史块 + 自己，不 attend 未来）
        # 用 FA 的 causal=True，但只对当前块内 causal，历史块全 attend
        out = flash_attn_with_kv_cache(Q, K_full, V_full,
                                         causal_current=True)  # 自定义 op

        # 4. 更新历史 KV（当前块的 K, V 加入缓存）
        if self.history_kv is None:
            self.history_kv = (K, V)
        else:
            self.history_kv = (
                torch.cat([self.history_kv[0], K], dim=1),
                torch.cat([self.history_kv[1], V], dim=1),
            )

        return out

    def reset(self):
        """新视频生成时清空"""
        self.history_kv = None
```

**结构-causal attention 协同**：causal attention 之所以在长视频上可行，是因为**自然视频的时序因果性强**——后帧的内容主要由前帧决定（运动连续性），未来帧对当前帧的依赖弱。这与 LLM 的 causal attention 有相同的数学基础（autoregressive 假设），但应用在视频的帧维度而非 token 维度。

### 6.4 优化方案三：分块训练（渐进式扩展）

长视频 DiT 不能直接训练（显存不够），需要**渐进式扩展训练**——先训短视频（5s），再扩展到中视频（10s），最后到长视频（60s）。

```text
渐进式扩展训练（HunyuanVideo 风格）：

Stage 1: 5s 视频训练（基础时序建模）
  - 数据: 5s 视频片段（百万级）
  - batch: 8 卡 × batch=1
  - 训练 100K step
  - 学习率: 1e-4
  - 目标: 学会基础空间结构 + 短时序运动

Stage 2: 10s 视频微调（中时序扩展）
  - 数据: 10s 视频片段（十万级）
  - batch: 32 卡 × batch=1（需 CP=4）
  - 训练 50K step
  - 学习率: 5e-5（降一个数量级）
  - 目标: 学会中长度时序一致性

Stage 3: 60s 视频微调（长时序扩展）
  - 数据: 60s 视频片段（万级）

  - 训练 20K step
  - 学习率: 1e-5
  - 目标: 学会长时序因果链 + 跨块一致性
```

**结构-渐进训练协同**：渐进式扩展之所以有效，是因为 **3D attention 的时序建模能力可迁移**——5s 视频里学到的”短时序运动”在 60s 视频里仍然成立（运动规律不变），只需额外学习”长时序因果链”。这与 LLM 的 context length extension（从 4K 扩到 128K）思路一致，但 DiT 扩展的是时间维度而非 token 维度。

### 6.5 优化方案四：时序 CP + StreamingLLM 思想

长视频的 causal attention 会让 KV Cache 累积爆炸（块12 时 550 帧的 KV），需要**KV 压缩或稀疏化**。这里借鉴 LLM 长上下文领域的 **StreamingLLM** 思想：attention sink + sliding window。

![](https://pic1.zhimg.com/v2-d71d0022df5ebe2394f6ca4db0ca160a_r.jpg)

```text
# StreamingLLM 思想的视频 KV Cache 稀疏化
class SparseKVCache:
    """attention sink + sliding window + 稀疏采样"""
    def __init__(self, sink_size=2, window_size=20, sample_interval=5):
        self.sink_size = sink_size        # 每块保留首帧数（attention sink）
        self.window_size = window_size    # 滑动窗口大小
        self.sample_interval = sample_interval  # 远期块采样间隔

    def compress_history(self, history_kv, block_idx):
        """压缩历史块的 KV"""
        K_hist, V_hist = history_kv
        T = K_hist.shape[1]

        if block_idx <= 2:
            # 近期块全保留
            return K_hist, V_hist

        # 远期块：attention sink + 稀疏采样
        # 1. 保留首帧（sink）
        sink_K = K_hist[:, :self.sink_size]
        sink_V = V_hist[:, :self.sink_size]
        # 2. 保留末帧（最近窗口）
        window_K = K_hist[:, -self.window_size:]
        window_V = V_hist[:, -self.window_size:]
        # 3. 中间稀疏采样
        mid_K = K_hist[:, self.sink_size:-self.window_size:self.sample_interval]
        mid_V = V_hist[:, self.sink_size:-self.window_size:self.sample_interval]

        K_compressed = torch.cat([sink_K, mid_K, window_K], dim=1)
        V_compressed = torch.cat([sink_V, mid_V, window_V], dim=1)
        return K_compressed, V_compressed
```

### 6.6 结构-长视频协同：3D VAE 压缩 + temporal 稀疏化 + attention sink

| 结构特点 | 长视频优化方案 | 收益 |
| --- | --- | --- |
| latent 巨大（2.2M token） | latent offload 到 CPU | GPU 显存恒定 |
| 完整 3D attention O((2.2M)²) | causal attention + 跨块 KV 复用 | 计算可行 |
| KV Cache 累积爆炸 | StreamingLLM 思想（sink + window + 采样） | KV 5× 压缩 |
| temporal attention O(T²) | temporal 稀疏化（只 attend 关键帧） | O(T×K) |
| 长视频训练显存不够 | 渐进式扩展（5s → 10s → 60s） | 训练可行 |
| 3D VAE 时序压缩（T/4） | 直接降低 T | 4× token 减 |
| 块间一致性 | 条件帧传递 + 重叠 1s | 平滑过渡 |

```text
# Sora 类长视频（60s）推理：latent offload + causal + 稀疏化 + 8 步蒸馏
import torch
from diffusers import CogVideoXPipeline

pipe = CogVideoXPipeline.from_pretrained(
    "THUDM/CogVideoX-5b-distill",
    torch_dtype=torch.bfloat16,
    variant="fp8",
)
pipe.to("cuda")

# 1. compile + FP8
pipe.transformer = torch.compile(pipe.transformer, mode="max-autotune")
pipe.enable_model_cpu_offload()
pipe.vae.enable_tiling()

# 2. latent offload 管理
from long_video_utils import LatentOffloader, CausalLongVideoAttention, SparseKVCache

offloader = LatentOffloader()
causal_attn = CausalLongVideoAttention()
sparse_cache = SparseKVCache(sink_size=2, window_size=20, sample_interval=5)

# 3. 分块生成 60s 视频（12 块 5s，重叠 1s）
def generate_60s_video(pipe, prompt):
    total_blocks = 12
    chunk_frames = 5 * 24 // 4  # 30 latent 帧
    overlap_frames = 1 * 24 // 4  # 6 latent 帧

    all_latents = []
    for block_idx in range(total_blocks):
        # 1. 加载本块 latent 到 GPU
        latent = torch.randn(1, 16, chunk_frames, 90, 160, device="cuda")

        # 2. 获取前块 KV（causal + 稀疏化）
        if block_idx > 0:
            cond_kv = offloader.get_history_kv(block_idx, n_cond_frames=overlap_frames)
            cond_kv = sparse_cache.compress_history(cond_kv, block_idx)
        else:
            cond_kv = None

        # 3. 去噪本块（8 步蒸馏 + causal attention）
        latent = pipe.denoise_chunk(
            latent, prompt=prompt,
            cond_kv=cond_kv,           # 注入前块 KV
            causal_attn=True,           # causal attention
            num_inference_steps=8,
        )

        # 4. 更新 causal KV cache
        causal_attn.update_history(latent)

        # 5. latent offload 回 CPU
        offloader.to_cpu(block_idx, latent)
        all_latents.append(latent.to("cuda"))  # 最后拼接时再上 GPU

    # 6. 拼接 + VAE 解码
    full_latent = torch.cat(all_latents, dim=2)
    video = pipe.vae.decode(full_latent)
    return video

video = generate_60s_video(pipe, prompt="a cat exploring a garden over a minute")
```

## 7 重要结论与跨章总结

### 7.1 十大核心结论

经过五大分支的分析，我们提炼出以下核心结论：

**结论 1：DiT 的双向 attention 让 FA 完美适配，是结构-加速协同的基石。**

DiT 的 attention 无 causal mask（与 LLM 的 causal attention 形成对比），FA 的双向 full attention 正是 DiT 默认形态。这让 DiT 的 FA 利用率 95%+，而 LLM 的 causal attention 在 FA 里有 mask 拼接开销。**结构决定算子效率**——同样的 FA kernel，DiT 比 LLM 跑得更满。

**结论 2：MM-DiT 双流 attention 的”拼接后 self-attn”让 FA 一次调用处理整条序列。**

MM-DiT 把 `[img; txt]` 拼成一条序列做 self-attn，FA 只需一次前向。相比之下，传统 cross-attention（如 PixArt-α）需要两次 FA 调用。**这是 MM-DiT 相对 PixArt-α 的结构优势在训练加速上的直接体现**——结构选择决定了 FA 的调用次数。

**结论 3：3D attention 的 O((T·H·W)²) 必须分解，分解后 spatial 占 99% 计算。**

视频 DiT 的全 3D attention 在 180K token 上 OOM。分解成 spatial + temporal 后，复杂度从 O((T·H·W)²) 降到 O(T·(H·W)² + (H·W)·T²)，spatial attention 占 99.6% 计算量。**优化重点在 spatial（用 FA3 + CP），temporal 序列短可独立处理**。

**结论 4：DiT 无 KV Cache 是推理的根本约束，但长视频分块可部分复用。**

DiT 每步 latent 都变，无法跨步缓存 KV。这让 PagedAttention / Continuous Batching 那套 LLM 推理优化全部失效。但分块生成时，**条件帧的 KV 在去噪过程中不变，可跨步复用**——这是视频 DiT 推理的独有优化，LLM 没有对应物。

**结论 5：step distillation 是 DiT 独有的推理加速手段，LLM 无法对应。**

DiT 的”步数”是去噪步数（同 latent 反复 refine），可蒸馏从 50 步降到 4 步。LLM 的”步数”是 token 数（不同 token 展开），不能少步。**这是 DiT 与 LLM 在推理加速上的根本差异**——step distillation 让 DiT 推理有 12× 的”免费”加速空间。

**结论 6：DiT 是 compute-bound，FP8 量化直接提算力（2×）。**

DiT 单步算术强度 ~8000 FLOP/byte，严重 compute-bound。FP8 把 H100 Tensor Core 算力翻倍，单步延迟直接 2× 加速。而 LLM decode 是 memory-bound，FP8 只省显存不省延迟。**同样的 FP8 量化，在 DiT 和 LLM 上的收益完全不同**。

**结论 7：latent + 文本预编码是 DiT 训练的”免费午餐”。**

VAE 和 T5 与 DiT 解耦，可离线预编码。这让训练时 GPU 100% 给 DiT，吞吐 2.2× 提升。**这是 DiT 相对 LLM 的独有训练优势**——LLM 的 prefill 和 decode 是同一模型，无法把”前置计算”分离出来预编码。

**结论 8：视频 DiT 选 CP 而非 TP/PP，是结构-并行的协同决策。**

3D attention 分解后 spatial attention 是 per-frame 独立的，把帧切到多卡（CP）零通信。TP 切 attention head 通信频繁，PP 切层激活显存爆炸。**CP 与 3D 分解的结构协同让视频 DiT 训练 4× 加速**。

**结论 9：长视频 DiT 必须用 causal attention + latent offload + KV 稀疏化。**

60s 视频 latent 2.2M token，单卡装不下。causal attention 让前块 KV 给后块复用，latent offload 让 GPU 显存恒定，StreamingLLM 思想让 KV Cache 5× 压缩。**这三者是长视频 DiT 的”三件套”**，缺一不可。

**结论 10：结构决定加速边界，加速方案服从结构约束。**

这条结论是全章的核心：

- **双向 attention** → FA 完美适配（无 causal mask 拼接）
- **MM-DiT 双流** → attention 可融合为单个 FA kernel
- **3D attention O((T·H·W)²)** → 必须分解成 spatial + temporal
- **多步去噪** → step distillation 可减步（DiT 独有）
- **无 KV Cache** → 不能用 PagedAttention，但分块可部分复用
- **compute-bound** → FP8 直接提算力
- **三阶段解耦** → latent + 文本预编码（DiT 独有）
- **长视频因果性** → causal attention + 跨块 KV 复用

这些不是”经验技巧”，而是结构数学性质决定的硬约束。理解这些约束，才能为新结构设计最优加速方案。

| bucket sampler | 中 | 不丢信息 | 无 | 训练 |
| 3D attention 分解 | 中 | 3× | 小（可分离假设） | 视频训练 + 推理 |
| 时序 CP | 高 | 4×（CP=4） | 无 | 视频训练 |
| CFG 蒸馏 | 中 | 2× | 小 | 推理 |
| step distillation | 高 | 5-12× | 中（FID/FVD +5-10%） | 推理 |
| 分块生成 | 中 | 显存可行 | 小（条件帧传递） | 长视频推理 |
| latent offload | 中 | 显存可行 | 无（延迟略增） | 长视频推理 |
| causal attention | 高 | 计算可行 | 中（因果假设） | 长视频推理 |
| KV 稀疏化 | 高 | KV 5× 压缩 | 中（远帧信息丢失） | 长视频推理 |

**决策原则**：

1. **先上无质量代价的优化**：FA3 / compile / FP8 / 预编码 / bucket sampler
2. **再上小质量代价的优化**：3D 分解 / CFG 蒸馏 / 分块生成
3. **最后上中质量代价的优化**：step distillation / causal attention / KV 稀疏化
4. **质量优先场景**：跳过 step distillation，用 BF16 + 50 步
5. **延迟优先场景**：全开，Schnell 4 步 + FP8 + compile + TP=4

## 面试速答

**Q1：为什么 DiT 推理没有 KV Cache，但长视频分块生成又能复用 KV？**

A：DiT 每步去噪时整个 latent 都在变（去噪过程在 refine），所以每步的 K/V 完全不同，无法跨步缓存——这是”无 KV Cache”的含义。但分块生成时，前一块的末尾几帧作为条件帧传入下一块，这些条件帧的 latent 在去噪过程中被 mask 固定（不变），所以它们的 K/V 可以跨步复用。这是”帧级 KV 复用”，与 LLM 的”token 级 KV 复用”数学结构相似但应用场景不同。

**Q2：3D attention 为什么要分解成 spatial + temporal？分解后的优化重点在哪？**

A：全 3D attention 的复杂度是 O((T·H·W)²)，HunyuanVideo 5s 视频 180K token 对应 attention 矩阵 128GB/层，单卡装不下。分解成 spatial（每帧 H×W）+ temporal（每像素 T）后，复杂度降到 O(T·(H·W)² + (H·W)·T²)。分解后 spatial attention 占 99.6% 计算量，是优化重点（用 FA3 + CP），temporal attention 序列短（T~50）可独立处理。

**Q3：为什么 Flux 训练用 FSDP 而不是 TP？**

A：三个理由：(1) DiT attention 是双向 full attention，不像 GQA 有 KV head 数限制 TP 上限，FSDP 实现更简单；(2) DiT 训练 batch_size 较小，TP 的算力利用率优势不明显，FSDP 的显存优势更直接；(3) FSDP 不需要改模型代码（TP 要重写 attention/FFN 的切分逻辑），对 diffusers 生态友好。

**Q4：step distillation 为什么是 DiT 独有优化，LLM 不能用？**

A：DiT 的”步数”是去噪步数（同一个 latent 反复 refine），去噪轨迹是连续的（latent 在流形上滑动），可被少步近似——所以能从 50 步蒸成 4 步。LLM 的”步数”是 token 数（不同 token 序列展开），token 序列是离散的，不能少步近似。LLM 对应的”少步优化”是投机解码（token 级），与 DiT 的 step distillation（步数级）是不同的优化维度。

**Q5：FP8 在 DiT 推理和 LLM 推理上的收益为什么不同？**

A：DiT 是 compute-bound（算术强度 ~8000 FLOP/byte），FP8 把 H100 Tensor Core 算力翻倍（1979 vs 989 TFLOPS），单步延迟直接 2× 加速。LLM decode 是 memory-bound（算术强度 ~1 FLOP/byte），FP8 只减半权重访存（70GB → 35GB），延迟也减半但算力没用满——本质上 FP8 在 LLM decode 上是”省显存附带省延迟”，在 DiT 上是”直接提算力”。

**Q6：长视频 DiT 的”三件套”是什么？为什么缺一不可？**

A：causal attention + latent offload + KV 稀疏化。causal attention 让前块 KV 给后块复用（计算可行）；latent offload 让 GPU 显存恒定不随视频长度增长（显存可行）；KV 稀疏化（StreamingLLM 思想）让累积的 KV Cache 5× 压缩（KV 不爆）。缺 causal attention 则计算爆炸，缺 latent offload 则显存爆炸，缺 KV 稀疏化则 KV Cache 爆炸——三者分别解决计算、显存、KV 三个维度的爆炸问题。
