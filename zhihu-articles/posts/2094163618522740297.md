Q: vllm 在其他推理设置保持一致的情况下，开始speculative decoding相比于不开启，是否会更容易超过CUDA Graph的批大小上限导致进入eager模式?

A: 是的，在 CUDA Graph 上限固定、其他条件不变时，开启 speculative decoding 更容易因为有效 batch 变大而落入 eager 路径。

关键是 CUDA Graph 这里看的通常不是“请求数”，而是一次 forward 的 `num_tokens`：

- 不开启 speculative decoding：每个请求通常处理 1 个 query token<br>`num_tokens ≈ batch_size`
- 开启后，验证阶段每个请求通常处理 `1 + K` 个 token，其中 `K = num_speculative_tokens`<br>`num_tokens ≈ batch_size * (K + 1)`

例如：

```text
batch_size = 32
num_speculative_tokens = 4

不开启：32 tokens
开启后：32 * (4 + 1) = 160 tokens
```

如果最大的 CUDA Graph 只捕获到 128，那么不开启时可以命中 Graph，开启后就可能超过上限并进入 `CUDAGraphMode.NONE`，也就是 eager 执行。

不过当前 vLLM 实现会针对 speculative decoding 自动调整 Graph 配置：

- 默认最大 capture size 会按<br>`max_num_seqs * (num_speculative_tokens + 1) * 2`<br>计算，并受 `512` 和 `max_num_batched_tokens` 限制。
- 对 FULL decode Graph，capture sizes 会调整为 `num_speculative_tokens + 1` 的倍数。
- 配置初始化时还会检查最大 Graph 容量是否至少覆盖<br>`max_num_seqs * (num_speculative_tokens + 1)`。

所以实际表现要分两种情况：

1. 自动配置正常覆盖：vLLM 会扩大或重新对齐 CUDA Graph capture sizes，通常不会因为 speculative decoding 本身直接掉到 eager。
2. 显式设置的 Graph 上限不够，或者默认上限 512 不够：可能在启动时直接报配置错误；如果运行时 batch 超过实际 Graph 上限，dispatcher 会返回 `NONE`，该 batch 走 eager。

例如当前测试明确覆盖了这种约束：`max_num_seqs=8`、`num_speculative_tokens=3` 时，Graph 上限至少需要 `8 * 4 = 32`；上限只有 16 会失败。

还要注意两点：

- `num_speculative_tokens` 即使最终只接受了部分 draft tokens，静态 speculative decode 的 Graph shape 通常仍按 `1 + K` 设计，不能简单按平均接受长度估算。
- 如果是 PIECEWISE 模式，部分算子可能 eager，但不一定代表整个模型 forward 都进入 eager；只有 dispatcher 返回 `CUDAGraphMode.NONE` 才是该 batch 的完整 eager 路径。vLLM 官方 CUDA Graph 设计也把 speculative decode 定义为 query length 为 `1 + num_spec_tokens` 的 uniform decode batch。

因此，简化结论是：

> 固定 `max_cudagraph_capture_size` 时：是的，更容易超过上限。当前 vLLM 默认配置会尝试为 speculative decoding 扩容；如果扩容后仍无法覆盖，通常会在初始化时报错，运行时超限则回退到 eager。
