读 Linux GPU 驱动（DRM 子系统）的代码时，很多设计第一眼看上去很别扭：为什么 BO 要区分 VRAM 和 GTT 两种放置域？为什么 CPU 映射显存时要用写合并（Write-Combine WC），读回数据还要专门让 GPU 先拷一份到系统内存？为什么写进 GPU 页表的地址不能是 CPU 看到的物理地址？为什么每次提交都要带一个 fence，作业结束时还要刷缓存？

这些问题的答案都不在软件里，而在硬件里。本文不针对任何特定厂商，面向通用的 GPU 硬件模型，回答四个问题：

- GPU 在系统中处于什么位置，CPU 和 GPU 怎样访问对方的内存；
- GPU 怎样把虚拟地址翻译成真正的内存地址；
- 命令怎样从 CPU 交给 GPU，又怎样报告完成；
- CPU 和 GPU 的缓存为什么不一致，靠什么保持同步。

最后用一张表把这些硬件约束和 DRM 中对应的软件机制对上号。

### 一、GPU 在系统里的位置

GPU 在系统中的位置，决定了它用哪种内存，以及 CPU 怎样访问这些内存。下图以独立 GPU 为主体，同时画出了集成 GPU 的位置。

![](https://pic1.zhimg.com/v2-c3a2a5dbd90627198959100ee172c418_r.jpg)
*图 1 GPU 在系统中的位置与访存路径*

常见的 GPU 形态有三种：

- **独立 GPU**：作为 PCIe 设备插在主板上，自带显存（VRAM），也能访问系统内存。本地显存带宽很高，但 CPU 和 GPU 访问对方的内存都要穿越 PCIe。
- **集成 GPU**：与 CPU 在同一块芯片上，与 CPU 共享系统内存，部分平台还共享末级缓存，即统一内存架构（UMA）。固件可以在启动时预留一段内存（stolen memory）专供 GPU 使用。
- **嵌入式 SoC**：GPU 挂在片上总线上，共享系统内存。显示控制器和 GPU 往往是不同厂商的 IP，有些模块前面没有 IOMMU，只能访问物理连续的内存。

图中标出了四条访存路径，它们的差距非常大：

| 路径 | 发起方与目标 | 典型带宽 | 说明 |
| --- | --- | --- | --- |
| ① | CPU 访问 VRAM | 写入尚可，读取极慢 | 经显存 BAR 窗口 |
| ② | GPU 访问系统内存 | 数十 GB/s | 经 PCIe 与 IOMMU |
| ③ | GPU 访问 VRAM | 数百 GB/s 至数 TB/s | 不出 GPU，带宽最高、延迟最低 |
| ④ | 集成 GPU 访问系统内存 | 与 CPU 访存相当 | 经片上互连，可共享末级缓存 |

路径 ③ 与路径 ② 的带宽相差一个数量级以上。**对独立 GPU 来说，数据放在 VRAM 还是系统内存，对性能有决定性影响**，这正是驱动要花大力气管理 BO 放置与迁移的原因。

### 二、两边各有哪些部件

后文的流程会反复提到下面这些部件，先认个脸。

CPU 芯片一侧：

| 部件 | 作用 |
| --- | --- |
| CPU MMU 与 TLB | 按页表把虚拟地址翻译成物理地址，同时确定该页的内存类型（回写、写合并、非缓存） |
| L1/L2、末级缓存（LLC） | 缓存最近访问的数据；LLC 通常由所有 CPU 核共享，部分平台与集成 GPU 共享 |
| 一致性互连 | 连接 CPU 核、缓存、内存控制器与 IO 部件，按物理地址把请求路由到内存控制器或 PCIe，并维护 CPU 各缓存之间的一致性 |
| PCIe 根端口 | 把 CPU 发往设备的访问封装成 PCIe 事务层报文（TLP），并接收设备发来的 TLP |
| IOMMU | 把设备发出的 DMA 地址翻译成物理地址并检查权限；设备只能访问被显式映射的页面 |

独立 GPU 一侧：

| 部件 | 作用 |
| --- | --- |
| 寄存器 BAR | 把 GPU 的控制寄存器映射到 CPU 地址空间（MMIO） |
| 门铃 BAR | 每个命令队列对应一个门铃地址，CPU 写一下就通知 GPU 该队列有新命令 |
| 显存 BAR | CPU 访问 VRAM 的地址窗口 |
| 主机数据通路 | 承载 CPU 经显存 BAR 对 VRAM 的读写，部分厂商称为 HDP（Host Data Path）；带有写缓冲与读缓存，且不经过引擎侧的 GPU 缓存 |
| 命令处理器（CP） | 从命令队列取命令，分发给各执行引擎，完成后写回完成序号 |
| 执行引擎 | 图形与计算引擎执行着色器，复制引擎搬数据，视频引擎编解码，显示控制器扫描输出 |
| GPU 缓存 | 引擎内的 L1 与全局共享的 L2，与 CPU 缓存之间没有硬件维护的一致性 |
| GPU MMU 与 TLB | 把 GPU 虚拟地址翻译成 VRAM 地址或 DMA 地址，每个地址空间一套页表 |
| 中断控制器 | 把命令完成、缺页、错误等事件以中断形式通知 CPU |

### 三、CPU 访问显存：为什么写得动、读不动

CPU 不能直接寻址 GPU 的显存，只能通过显存 BAR 这个地址窗口间接访问。一次访问要经过的部件如下图所示。

![](https://pica.zhimg.com/v2-3dd38cb727432377f898092ef5bc4c60_r.jpg)
*图 2  CPU 经显存 BAR 访问 VRAM 的流程*

1. CPU 核执行访存指令，发出虚拟地址（①）。
2. CPU MMU 把它翻译成物理地址（②）。这个物理地址落在系统为显存 BAR 分配的窗口内，页表同时规定该页是写合并或非缓存类型，而不是普通内存的回写类型。
3. 写操作先进入写合并缓冲区，相邻的写入合并成较大的突发写再发出；读操作不经缓存，直接发出（③）。
4. 一致性互连解码物理地址，发现它属于 PCIe 设备的窗口，把请求转给 PCIe 根端口（④）。
5. 根端口把请求封装成存储器读或写 TLP（⑤），经 PCIe 链路传输（⑥）。写请求是 posted 事务，发出即可，不等应答；读请求是 non-posted 事务，必须等 GPU 返回完成报文。
6. GPU 的 PCIe 接口按地址范围认领请求（⑦），把 BAR 内偏移转换成显存地址（⑧），经主机数据通路（⑨）交给显存控制器访问 VRAM（⑩）。
7. 对读请求，数据装在完成报文里原路返回 CPU（⑪）。

这条路径带来四个硬约束，每一个都在驱动里留下了痕迹。

**读远慢于写。** 写合并让写操作可以连续发出、不必等待；读操作每次都要在 PCIe 上走一个来回，延迟以微秒计，还用不上 CPU 缓存。所以 CPU 应该尽量避免从 VRAM 读数据，确实要读时，更好的做法是让 GPU 先把数据复制到系统内存。

**窗口不够大。** 为了兼容 32 位地址空间，许多平台默认只给显存 BAR 分配 256 MB，远小于显存容量。PCIe 的 Resizable BAR 特性可以把窗口扩大到覆盖全部显存，但需要固件和操作系统共同支持。窗口盖不住全部显存时，VRAM 就分成了 CPU 可见和 CPU 不可见两部分，驱动放置 BO 时必须考虑这一点。

**写入可能被暂存。** 部分 GPU 在主机数据通路上设有缓冲，CPU 写的数据可能还停在缓冲里没到 VRAM。要让 GPU 引擎立即看到这些数据，得先刷新这个缓冲。

**主机访问绕过引擎侧缓存。** 引擎经 GPU 缓存（如 L2）访问 VRAM，主机请求则经主机数据通路直达显存控制器，两条路径之间没有硬件一致性。CPU 写完后，GPU 缓存里可能还是旧数据，需要失效；引擎写的结果可能还在 GPU 缓存里，需要先写回 VRAM，CPU 才能读到。如果 GPU 缓存设计在显存控制器之前、所有请求都经过它（显存侧缓存），这个问题就不存在，具体取决于架构。

### 四、GPU 访问系统内存：地址要翻译两次

GPU 访问系统内存时，地址要经过两级翻译：GPU MMU 把 GPU 虚拟地址翻译成 DMA 地址，IOMMU 再把 DMA 地址翻译成物理地址。

![](https://pic2.zhimg.com/v2-9f1bb8221b86a4de579fd0cf944dbf1f_r.jpg)
*图3  GPU 经 PCIe 访问系统内存的流程*

1. 执行引擎以 GPU 虚拟地址发出请求，GPU 缓存命中就直接返回。
2. 未命中时，GPU MMU 查 TLB，TLB 未命中就遍历 GPU 页表（页表通常放在 VRAM 里）。页表项无效时 GPU 触发缺页。
3. 页表项表明目标在系统内存，给出 DMA 地址，以及是否需要窥探 CPU 缓存。
4. PCIe 接口把请求封装成 TLP；页表项要求不窥探时，在 TLP 中设置 No Snoop 属性。
5. 请求经 PCIe 链路到达 CPU 芯片的根端口。
6. IOMMU 查 IOTLB，未命中就遍历 IO 页表。映射不存在或权限不符时，IOMMU 拦截访问并记录故障，访问不会到达内存。
7. IOMMU 输出物理地址。如果没有设置 No Snoop，一致性互连会查 CPU 缓存：缓存里有最新数据时，读请求拿到这份数据，写请求使 CPU 缓存中的副本失效。
8. 内存控制器访问 DDR，读到的数据装进完成报文返回 GPU，并填入 GPU 缓存。

这里有四个要点：

**DMA 地址不等于物理地址。** GPU 发出的是 DMA 地址（也叫总线地址）。有 IOMMU 时它由 IOMMU 翻译；没有或旁路 IOMMU 时，通常才与物理地址相同。**写进 GPU 页表的必须是 DMA 地址**，不能是 CPU 看到的物理地址，这也是驱动必须先调用 DMA 映射接口、再填页表的原因。

**物理页通常不连续。** 一块缓冲区在 GPU 虚拟地址空间里是连续的，背后的系统内存物理页往往是零散的。GPU 页表和 IOMMU 页表都按页建立映射，把零散的页拼成连续的地址范围。

**两级翻译有开销。** 每一级都可能因 TLB 未命中而遍历页表，IO 页表遍历本身还要访问系统内存。PCIe 的地址翻译服务（ATS）允许设备在本地缓存 IOMMU 的翻译结果，以减少这部分开销。

**窥探是一种取舍。** 窥探访问由一致性互连保证与 CPU 缓存一致，代价是延迟更高、占用互连带宽；非窥探访问更快，但 CPU 缓存中可能有还没写回内存的数据，GPU 会读到旧值。用非窥探访问时，CPU 一侧要以非缓存或写合并方式访问这些页，或者在 GPU 访问前显式刷新 CPU 缓存。

### 五、GPU 的页表、TLB 与缺页

### 从 GART 到多级页表

GPU 的地址翻译经历了两个阶段。

早期是 **GART**（Graphics Address Remapping Table，源于 AGP 时代）：一张全局共享的单级页表，把一段连续的 GPU 地址窗口映射到零散的系统内存页，让 GPU 能用上不连续的系统内存。

现代 GPU 则使用**与 CPU 类似的多级页表**，每个地址空间一套，用地址空间标识（如 VMID）区分，不同进程的 GPU 地址空间因此相互隔离。页表项除了地址，通常还包括有效位、读写与执行权限、目标位置（VRAM 或系统内存）、是否窥探、缓存策略，以及用于大页映射的页大小。

### TLB 失效：改完页表不等于生效

GPU MMU 同样用 TLB 缓存翻译结果，而且 GPU 内部可能有多级、多处 TLB。修改或撤销页表项后，必须使相关 TLB 项失效，并且**确认失效已经完成**，对应的物理页才能被回收或挪作他用，否则 GPU 可能经陈旧的 TLB 项访问到已经不属于它的内存。TLB 失效要通过寄存器或命令触发并等待硬件确认，开销不小。

### 缺页：从直接报错到可恢复

早期 GPU 遇到无效地址只能报错并终止相关上下文，所以命令要访问的所有内存都必须在执行前映射好，并在执行期间保持驻留。较新的 GPU 支持**可恢复缺页**（recoverable page fault）：访问无效地址时，硬件暂停相关执行单元，经中断把缺页地址报告给 CPU，软件建立映射后硬件重试。GPU 因此可以像 CPU 一样按需建立映射，但报告和重试都要经过中断与 PCIe，处理延迟远高于 CPU 缺页。

### 六、命令怎么交给 GPU：ring、门铃与 fence

### 两层接口：IB 与 ring

GPU 异步执行命令：CPU 把命令写进内存后通知 GPU，随即返回做别的事，GPU 稍后执行并报告完成。CPU 与命令处理器之间的接口分两层：

- **命令缓冲区（Indirect Buffer，IB）**：存放一项作业的具体命令，如绘制、计算分派、内存复制。
- **ring 缓冲区**：一段首尾相接的内存，存放命令处理器要依次处理的包。ring 里的包大多不含作业命令本身，而是指向 IB 的地址和长度，外加同步、缓存控制、完成通知等控制命令。写指针标记 CPU 写到哪里，读指针标记命令处理器读到哪里，两者之间就是已提交、待执行的包。

### 一次提交的完整过程

![](https://picx.zhimg.com/v2-076b5f597091c5757ad5f77caced673f_r.jpg)
*图 4 命令提交与完成：ring、门铃与 fence*

1. CPU 把作业命令写入 IB（①），然后发起提交（②）。
2. CPU 在 ring 的写指针处写两个包（③）：一个指向 IB，另一个是 fence 包。fence 包要求引擎在此前的命令全部完成、缓存写回之后，把一个递增的序号写到指定的 fence 内存，并触发中断。
3. CPU 更新写指针，通常就是写一下门铃（④）。
4. 命令处理器在读写指针之间依次取包（⑤），引擎按包中的地址读取 IB 并执行（⑥）。
5. 作业完成后，引擎把序号写入 fence 内存（⑦）并产生中断（⑧）。CPU 的中断处理程序读出这个序号，所有序号不大于它的作业都已完成。

同一 ring 上的包按顺序处理，fence 序号单调递增，**比较一下序号就知道任意一项作业是否完成**，不用逐项查询。Linux 中 `dma_fence` 的 context 与 seqno 设计，正是对这一硬件模型的抽象。

### 容量、挂起与固件调度

**ring 容量有限。** 写指针追上读指针时 ring 就满了，新的提交只能等命令处理器消化掉一部分包。

**作业可能挂起。** 着色器死循环、访问非法地址或硬件异常都可能让作业永远完不成，而硬件通常不会主动报告挂起，只能由软件在等待超时后判定，再复位相应引擎甚至整个 GPU。复位会丢失正在执行的作业及其上下文状态。

**固件调度。** 较新的 GPU 内置固件调度器，把大量软件队列复用到有限的硬件队列上，负责队列之间的抢占与切换。部分平台还允许应用直接写自己的队列和门铃，提交完全不经过内核。但 ring、门铃、fence 序号这套基本模型依然适用。

### 七、最容易踩坑的缓存一致性

### CPU 的三种内存类型

CPU 页表为每个页规定内存类型，决定 CPU 缓存怎样对待它：

| 内存类型 | 读 | 写 | 典型用途 |
| --- | --- | --- | --- |
| 回写（WB） | 经缓存 | 写入缓存，延后写回 | 普通系统内存 |
| 写合并（WC） | 不经缓存 | 在写合并缓冲区中合并后发出 | 显存 BAR、供 GPU 非窥探访问的系统内存 |
| 非缓存（UC） | 不经缓存 | 逐个直接发出 | 设备寄存器 |

同一物理页如果同时以不同类型映射，可能导致数据不一致。所以改变一个页的内存类型时，要先刷新它在 CPU 缓存中的数据，并使所有 CPU 上相关的 TLB 项失效，开销很大，不宜频繁进行。这也是驱动要维护写合并页池、尽量复用已经改好类型的页的原因。

### CPU 与 GPU 之间：谁来保证一致

一致性互连只管 CPU 一侧的缓存。CPU 与 GPU 之间的一致性要看访问方向：

| 场景 | 一致性如何保证 |
| --- | --- |
| GPU 窥探访问系统内存 | 一致性互连自动处理 CPU 缓存中的副本 |
| GPU 非窥探访问系统内存 | CPU 以写合并或非缓存方式访问，或在 GPU 访问前刷新 CPU 缓存 |
| CPU 经显存 BAR 访问 VRAM | 以写合并或非缓存方式映射；必要时刷新主机数据通路，并使 GPU 缓存失效或写回 |
| GPU 写入后供 CPU 或其他设备读取 | 必须把 GPU 缓存中的数据写回内存 |

后两种情况都依赖显式同步：GPU 的 L2 不会自动写回，CPU 也窥探不到 GPU 缓存。

### 同步在什么时候做

在缓存位于引擎一侧的架构中，GPU 完全感知不到 CPU 的访问：主机经显存 BAR 的读写不会窥探 GPU 缓存，也不会通知命令处理器；CPU 写系统内存也不会让 GPU 缓存里的副本失效。硬件里也没有部件持续追踪这些访问。因此**缓存同步只能由软件在已知的时间点显式触发**，通常选在作业边界：作业开始前和作业结束时。

同步动作本身由硬件完成，触发方式有三种：

- **命令流中的缓存控制包**：命令处理器执行到该包时，向各级缓存发出写回或失效请求，全部完成后再处理后续的包。典型用途是作业开始前使 GPU 缓存失效。
- **fence 包附带的缓存操作**：引擎完成此前全部命令后，先写回缓存，再写完成序号，保证序号可见时结果已经到达内存。
- **MMIO 寄存器**：CPU 写特定寄存器，直接触发刷新或失效，典型用途是刷新主机数据通路的写缓冲、使其读缓存失效。

GPU 内的缓存实例很多，每个计算单元都有自己的 L1。部分架构为此设有集中的缓存请求控制器，把一次写回或失效请求分发到所有实例，全部完成后统一应答。

![](https://pica.zhimg.com/v2-49a6807e6432a207d1795c16e011c600_r.jpg)
*图5  CPU 与 GPU 之间的缓存同步时序*

1. CPU 经显存 BAR 写入输入数据（①），然后刷新主机数据通路（②），让暂存的数据写进 VRAM。
2. CPU 写 ring 包并敲门铃（③）。命令处理器在作业开始时先使 GPU 缓存失效（④），避免引擎命中旧数据。
3. 引擎经 GPU 缓存读写数据（⑤），结果可能长时间留在缓存里。
4. 作业结束时，命令处理器写回 GPU 缓存中的脏数据（⑥），再写 fence 序号（⑦）并触发中断（⑧）。写回先于序号写入，所以 CPU 看到序号就能确认结果已经到达 VRAM。
5. 主机数据通路带读缓存时，CPU 读取前先使其失效（⑨），再经显存 BAR 读取结果（⑩）。

这一时序成立的前提是 **PCIe 的排序规则**：posted 写按发出顺序到达，所以输入数据不会落后于门铃写入；读请求的完成报文不能越过此前的 posted 写，所以 CPU 读回 GPU 的任一寄存器，就能确认此前的写入都已到达 GPU。不过数据是否已经写进 VRAM，仍取决于主机数据通路有没有刷新。

只有两种情况可以省掉这些显式同步：一是 GPU 缓存设计为显存侧缓存，主机访问和引擎访问都经过它；二是 CPU 与 GPU 之间采用硬件一致性互连，双方可以互相窥探缓存。

### 八、硬件约束与 DRM 软件机制的对应

把前面的硬件约束和 Linux DRM 中的软件机制放在一起看，很多设计就不再别扭了：

| 硬件约束 | DRM 中对应的软件机制 |
| --- | --- |
| VRAM 与系统内存带宽相差一个数量级 | TTM 的放置域（VRAM、GTT、SYSTEM）、BO 的放置与迁移、驱逐 |
| 显存 BAR 窗口有限，VRAM 分 CPU 可见与不可见 | BO 放置时区分可见显存，CPU 缺页时把 BO 迁入可见区域 |
| CPU 读 VRAM 极慢、映射需写合并 | TTM 的 caching 模式（cached、write-combined、uncached）与写合并页池 |
| GPU 页表里必须填 DMA 地址 | DMA 映射接口（dma_map_sgtable() 等）与 scatter-gather 表 |
| 每个地址空间一套 GPU 页表 | drm_gpuvm 管理 GPU 虚拟地址空间 |
| 改页表后必须 TLB 失效完成才能回收页 | 页表更新与 TLB 刷新以 fence 表示，释放前等待 |
| 可恢复缺页 | 基于 HMM 的 SVM，drm_gpusvm 与 drm_pagemap |
| ring、门铃、递增的 fence 序号 | dma_fence 的 context 与 seqno、dma_resv、drm_syncobj |
| ring 容量有限、作业可能挂起 | DRM 调度器的流控与超时检测（TDR） |
| CPU 与 GPU 缓存不一致 | 作业边界的缓存刷新、dma-buf 的 CPU 访问同步接口 |

用一句话概括 GPU 硬件模型：**独立 GPU 有一块又快又大、但 CPU 很难访问的显存；GPU 用自己的多级页表加上 IOMMU 访问内存；命令经 ring 和门铃异步提交，用递增的 fence 序号报告完成；而 GPU 感知不到 CPU 的访问，缓存只能在作业边界由软件显式同步。** DRM 子系统中关于内存管理、同步与调度的大部分设计，都是在回应这几条约束。
