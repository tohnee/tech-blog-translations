上周帮一个朋友 debug 推理服务，他用 70B 模型跑长上下文 agent，单卡 80G H100 直接 OOM 退出。一查显存占用：**KV cache 吃了 62GB，权重才占 14GB**。这种比例在长上下文时代已经成了常态。

这两年 KV cache 压缩从一个学术话题变成了工程必修课，论文一篇接一篇。我把目前能用、能落地的思路按四个方向梳理一下，附上我自己踩过的坑。

### 先搞清楚 KV cache 为什么这么贵

Transformer 每生成一个 token，注意力都要回看前面所有 token。如果不缓存，每步都要重算所有历史 K、V，复杂度 O(n²)。所以工程上必然缓存。

但**缓存的代价是显存随上下文线性增长**。一个粗略公式：

```text
KV cache size ≈ 2 × num_layers × num_heads × head_dim × seq_len × batch × dtype_bytes
```

代入 Llama 3 70B（80 层、64 头、128 dim、fp16）跑 32k 上下文 batch=4：

> 2 × 80 × 64 × 128 × 32000 × 4 × 2 ≈ **84 GB**

权重只要 140GB，KV cache 跑到 80G 一点也不夸张。**所有”压缩 KV cache”的论文，都在压上面那条公式里的某一项**。

### 路线一：架构级——MLA 直接把维度砍下来

DeepSeek-V2 的 [Multi-head Latent Attention (MLA)](https://arxiv.org/abs/2405.04434) 是目前架构级方案里最干净的一条。

思路很简单：传统 MHA 每个 head 都存独立的 K、V；MLA 把所有 head 的 KV 压成一个 **低秩 latent 向量**，需要用的时候再投影回去。

> DeepSeek-V2 论文给出的数字：**KV cache 减小 93.3%，最大吞吐量提升到 5.76 倍**。MoE 小模型里 KV cache 只要 14%，大模型里降到 4%。

我实测下来 MLA 几个关键点：

- **训练时就得用 MLA 架构**，不能在已训好的 MHA 模型上”贴一个 MLA 上去”——必须重训。所以这条路适合自家训模型的团队。
- 推理速度提升集中在 batch 大、长上下文的场景。短上下文低 batch 时 MLA 优势没那么明显，因为 KV cache 本来就没多大。
- 工程实现上有些坑：MLA 的 RoPE 处理和标准 MHA 不一样，要走”decoupled RoPE”。如果你拿开源代码改，先盯紧这块。

DeepSeek 这套做完，**直接把”长上下文 + 大 batch”的成本拉到能接受的区间**。这也是为什么这一年新出的国产开源模型，半数都在搬 MLA。

但 MLA 也不是免费午餐：低秩压缩本质上是把信息塞进更小的空间，**极端长上下文（百万 token 量级）下还是会有精度衰减**。我在内部测过 256k 上下文上 MLA 模型做 needle-in-haystack，召回率比 MHA 低 2–3 个点。所以 MLA 不是万金油，它解决的是「主流长度区间的成本问题」，不是「无限上下文」的银弹。

### 路线二：量化——能砍多少 bit 就砍多少

[Google Research 在 ICLR 2026 推的 TurboQuant](https://www.marktechpost.com/2026/04/29/top-10-kv-cache-compression-techniques-for-llm-inference-reducing-memory-overhead-across-eviction-quantization-and-low-rank-methods/) 把 KV cache 直接量化到 INT4 甚至 INT2。

核心做法是两阶段：先用 PolarQuant 对每个 K、V 向量做随机正交旋转（消除系统性偏差），再量化。比起直接量化，能在 INT4 上把精度损失压到 1% 以内。

实战建议（这条算是当下性价比最高的一条）：

- **先无脑试 INT8 量化**。绝大多数模型 INT8 KV cache 精度几乎无损，显存直接减半。
- 上 INT4 之前，**先在你自己的 eval 集上跑一遍**。少量任务（比如长文档 QA、code agent）对低比特量化很敏感，容易掉点。
- 别同时上权重 INT4 + KV cache INT4，**两个都极限压会叠加误差**。一般工程上是权重 INT8 + KV INT4，或者 W4A16 + KV INT8。

> 一句话：量化是工程师最该先动的开关。不改架构、不改算法，pip install 完调个参数就能上。

一个具体的踩坑：**别忘了 calibration 数据集要覆盖你的真实分布**。我之前直接用 wikitext 做 calibration，上线后发现代码生成场景质量下来一截，换成自己业务的 5k 条样本重做一次校准，差距立马补回来。这个动作 GPTQ、AWQ 之类的量化框架都支持，懒得自己做的话也有现成脚本。

### 路线三：eviction & 稀疏——边跑边丢

eviction 类方案的逻辑是：**不是所有 token 都值得长期存**。注意力分数低的 token 直接丢掉，腾出空间。代表工作有 H2O、StreamingLLM、SnapKV 等。

我做 agent 长链路时用过这套：

- StreamingLLM 那种”保留前几个 + 滑动窗口”的方式对纯生成任务 OK，但对需要回看历史的 agent 任务会丢信息。
- SnapKV 这类”按 attention 分数挑 token 保留”的更聪明，但有额外的 attention 计算开销，**短上下文反而变慢**。
- 实战阈值：上下文超过 16k 再考虑 eviction，更短就别折腾，量化已经够用。

最近还有一类思路是 **sparse attention as KV cache index**（[ArXiv 2605.06763](https://www.marktechpost.com/2026/04/29/top-10-kv-cache-compression-techniques-for-llm-inference-reducing-memory-overhead-across-eviction-quantization-and-low-rank-methods/)），把 KV cache 当成一个可检索的索引结构，每步只读相关的那一小段。这条路在 100k+ 超长上下文里特别用得上，但工程复杂度高，适合做基础设施的团队。

eviction 路线最大的暗坑是**不可逆**：丢掉的 token 后面要用就再也找不回来。所以做 agent 任务前，**先 profile 一下 attention 分数分布**，看看你的任务里 attention 到底是集中还是分散。集中型任务（每步只回看最近几条）适合上 eviction；分散型任务（要回看几十步前的工具调用结果）千万别用，掉点幅度会让你怀疑人生。

### 路线四：cache 复用——别让相同 prefix 重算

最后一条不是压缩，但效果惊人：**prefix caching**。

[LMCache](https://lmcache.ai/tech_report.pdf) 这种企业级方案把 KV cache 持久化到 CPU、SSD，跨请求复用。RAG 系统里 system prompt + 检索文档前缀经常是重复的，**复用一次能省 70%+ 的 prefill 计算**。

vLLM 0.6 之后原生支持 prefix caching，开启方式：

```text
LLM(model=..., enable_prefix_caching=True)
```

> 这条建议放第一位的优先级：所有做 RAG 或多轮对话的系统，**进 prod 之前先把 prefix caching 打开**，几乎零代码改动，TTFT 直接降一半。

### 怎么组合？给个能照抄的优先级

按”改造成本从低到高”排序，逐项试：

1. **打开 prefix caching**（vLLM/SGLang 都原生支持）——0 改动
2. **KV cache INT8 量化**——改启动参数
3. **权重 W4A16 + KV INT8**——重压模型一次
4. **加 eviction**（StreamingLLM 或 SnapKV）——只对 16k+ 上下文
5. **换成 MLA 架构**——重训成本，只在自训模型时考虑

> 我的经验：90% 的工程团队做到第 3 步就够了，再往下投入产出比会快速下降。能拿到一个 70% 显存削减 + 2x 吞吐已经能给业务讲清楚故事，不必为了 90% 极限优化牺牲三个月的迭代速度。
