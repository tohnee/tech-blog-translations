Triton 是一套用于编写高性能计算 Kernel 的编程语言和编译器。它提供接近 Python 的开发方式，让开发者以数据块为单位描述加载、计算和写回，再由编译器完成到目标机器代码的转换。对于想从框架调用走向算子实现的开发者，这种表达方式很有吸引力：既能直接控制计算过程，又不必从逐个线程的操作开始组织全部代码。[Triton 官方文档](https://triton-lang.org/main/index.html)

提到 Triton，通常想到的还是 GPU 编程。它的设计背景、官方教程以及常见优化案例，都与 GPU 上的深度学习计算紧密相关。矩阵乘法、归约和算子融合，是理解这套块级编程模型的典型入口；但教程里的任务划分和性能经验，也往往依赖 GPU 的执行方式与存储层次。[Triton 编程模型介绍](https://triton-lang.org/main/programming-guide/chapter-1/introduction.html)

那么，这套编程方式放到 RISC-V 上，会是什么样？SpacemiT 的 [spine-triton](https://github.com/spacemit-com/spine-triton) 已经提供了面向其平台的编译与执行支持，但从“能运行”走到“运行得高效”，仍需要把编程模型与具体硬件对应起来。

这里值得研究的是：**Triton 的块级表达落到 RISC-V 的向量计算、多核调度和存储资源上，最终会形成怎样的执行过程？** 同样是调整一个 BLOCK，可能同时改变单个任务的工作量和总任务数；同样是缓存一块数据，也要考虑复用收益能否抵消搬运成本。GPU 上熟悉的优化思路可以提供线索，具体选择则需要由目标平台上的测量来回答。

本次实验选择 SpacemiT K3，从 mv、mm 和 softmax 三个基础算子入手，比较 Triton 块级写法、SpacemiT 扩展与向量 eDSL 的实际表现。正文会结合代码、编译后的 IR 和性能图，观察任务粒度、数据布局与 TCM 使用方式如何影响完整调用的耗时，并与 PyTorch 8 线程原生实现进行对照。

下面先介绍 K3 的计算资源，再说明 SpacemiT Triton 如何表达和执行计算，随后进入三个算子的具体实验。

> 本次实验使用 `triton==3.6.0+spacemit.b0` 与 `torch==2.8.0+spacemit.0`，三个算子的输入输出均为 FP16。

### 1. 先认识 K3：算子最终跑在哪些核心上

SpacemiT K3 集成了 8 个 X100 通用计算核心和 8 个 A100 AI 计算核心。这里的 A100 是 SpacemiT 的核心名称。写算子时，可以先记住一个直接相关的差别：X100 支持 256-bit RVV，A100 支持 1024-bit RVV。两类核心的缓存配置和计算侧重点也有所不同。[官方硬件介绍](https://www.spacemit.com/community/document/info?lang=zh&nodepath=hardware%2Feco%2Fk3_com260%2Froot_overview.md)

| 硬件 | 本次实验关注什么 |
| --- | --- |
| X100 通用核心 | Python、框架和运行时等通用任务 |
| A100 AI 核心 | 较宽的向量计算能力，以及面向算子的计算资源 |
| 向量与矩阵计算指令 | mv 的乘加、softmax 的归约，以及 mm 的矩阵计算最终怎样执行 |
| 缓存与数据布局 | 同一批数据能否被复用，重排数据要付出多少成本 |

本次实验的运行记录也体现了这种分工：Python 主线程的 CPU affinity 为 0–7；Triton runtime 启动 8 个工作线程，分别绑定 CPU8–15，对应板卡上的 A100 核心。这个映射以实际运行记录为依据，换一套软件版本时，需要重新确认调度方式。

因此，优化要同时照顾两个层面：**一个核内部怎样处理向量，以及整个算子怎样拆成任务交给多个核。** 内层乘加写得紧凑，外层也得有足够的任务供工作线程执行。

后面的数据都来自 K3 Pico ITX 板卡。文章关注的是一次算子调用实际花了多少时间，以及代码里的哪项调整改变了这个结果。

### 2. SpacemiT Triton：从 Python 写法到 K3 执行

Triton 用接近 Python 的语法描述算子，再由编译器生成目标机器代码。`@triton.jit` 标记的函数会进入编译流程；它虽然写在 Python 文件里，内部仍需遵循 Triton 支持的语法和操作。

SpacemiT 的实现可以从开源项目 [spine-triton](https://github.com/spacemit-com/spine-triton) 入手。项目基于 triton-shared，增加了面向 SpacemiT 的编译与执行支持。本次实验使用对应的 `3.6.0+spacemit.b0` 构建，入口依然是熟悉的 `import triton`、`@triton.jit` 和 `triton.language`。

对本文涉及的算子，可以把执行过程画成下面这条路径：

```text
Python 准备张量、确定 launch grid
                 ↓
Triton kernel：描述每个 program 要做的计算
                 ↓
Triton / MLIR 编译流程 → LLVM IR → RISC-V 机器代码
                 ↓
SpacemiT runtime 调度任务，在 K3 上执行
```

这条路径里，编译器负责生成机器代码，runtime 负责组织一次 launch 中的任务。后面调整 BLOCK，既可能改变块内生成的计算，也可能改变任务数量，需要把两部分放在一起看。

代码中通过下面的方式显式选择后端：

```python
import triton
from triton.backends.spine_triton.driver import CPUDriver

triton.runtime.driver.set_active(CPUDriver())
```

### 3. 从块级编程开始：一个 program 负责一块数据

理解 Triton，可以先抓住 **program instance** 这个概念。一次 launch 能启动多个 program，它们执行同一份 kernel，通过 `program_id` 找到各自负责的数据块。这就是 SPMD：同一份程序，处理不同的数据。[Triton 编程模型介绍](https://triton-lang.org/main/programming-guide/chapter-1/introduction.html)

向量加法是个很直观的例子。下面每个 program 处理 BLOCK 个元素：

```python
import torch
import triton
import triton.language as tl
from triton.backends.spine_triton.driver import CPUDriver

triton.runtime.driver.set_active(CPUDriver())

@triton.jit
def block_add(A, B, C, N, BLOCK: tl.constexpr):
    pid = tl.program_id(0)
    offsets = pid * BLOCK + tl.arange(0, BLOCK)
    valid = offsets < N
    a = tl.load(A + offsets, mask=valid, other=0.0)
    b = tl.load(B + offsets, mask=valid, other=0.0)
    tl.store(C + offsets, a + b, mask=valid)

n = 257
a, b = torch.randn(n, dtype=torch.float16), torch.randn(n, dtype=torch.float16)
c = torch.empty_like(a)
block_add[(triton.cdiv(n, 128),)](a, b, c, n, BLOCK=128)
```

N=257、BLOCK=128 时，一共启动 3 个 program：

```text
program 0 → 元素   0～127
program 1 → 元素 128～255
program 2 → 元素 256；其余位置被 mask 掉
```

把代码和分块图对照起来，四个概念就容易区分了：

- **grid** 决定启动多少个 program。这里用向上取整，确保最后一个元素也有任务负责。
- **program_id** 是当前任务的编号，用来计算它处理的数据范围。
- **BLOCK** 是一个 program 处理的逻辑元素数。`tl.constexpr` 表示它在编译时已知，编译器可以据此构造块内计算。
- **mask** 保护最后一个不完整的数据块。加载时为无效位置给出填充值，存储时不写出界。

`tl.arange(0, BLOCK)` 生成块内的逻辑索引，`a + b` 描述这一组元素的相加。至于它们怎样拆成向量指令，后端会继续处理。块级编程的便利就在这里：先按数据块把计算写清楚，再交给编译器完成硬件映射。官方的[向量加法教程](https://triton-lang.org/main/getting-started/tutorials/01-vector-add.html)也从这个例子讲起。

**BLOCK=128 不代表需要一个装下 128 个元素的物理寄存器；grid=3 也不代表必须占用 3 个物理核。** 前者是代码里的数据分块，后者是任务数量。实际的指令划分和任务调度还要经过编译器与 runtime。

这个例子检查了长度 1、257 和 1024，以及输出末尾的保护区。先把简单算子的分块和边界处理走通，后面讨论归约、矩阵乘时，就能把注意力放在计算本身。

### 4. SpacemiT 扩展：块级矩阵操作与向量 eDSL

除了普通的 `tl.load`、`tl.sum`，SpacemiT 还提供了 `triton.language.extra.smt`。`smt.descriptor_load` 表达描述符加载，`smt.view` 表达子块和打包布局，`smt.dot` 处理打包后的矩阵乘；`smt.alloc` 则可以指定 `tcm` 等存储作用域。这些接口保留了按数据块表达计算的习惯，具体布局转换由编译器继续处理。

后面的 mm 会加入 `test_smt_mm` 作为对照，看看用 `smt.view`、`smt.dot` 描述布局和矩阵乘，能做到什么程度。softmax 也会组合普通 `tl` 运算与 `smt.alloc`，不把实现方式限定在向量接口上。

块级表达之外，算子作者有时还需要控制更具体的计算顺序：同一段输入向量如何复用到四行，累加器何时归约，矩阵数据怎样打包。这时就轮到向量 eDSL 了。

`smt_rvisa` 是 SpacemiT Triton 提供的嵌入式向量 DSL。它允许显式描述向量加载、乘加、归约、打包和循环。这些代码同样交给编译器处理，只是把更多计算安排交到了算子作者手里。

导入方式如下：

```python
import triton.language.extra.smt_rvisa as tle
from triton.language.extra.smt_rvisa import call as sr_call
```

两种表达方式可以配合使用。以 softmax 的一个对照版本为例：外层 program 选定一行，内层 raw kernel 负责这一行的向量计算。

```python
@triton.jit
def host_cached(X, Y, N):
    row = tl.program_id(0)
    sr_call(raw_cached, outputs=[], inputs=[X, Y, N, row])
```

`raw_cached` 由 `@tle.raw_kernel` 定义，接收输入指针、输出指针、行长和行号，再用 `row * N` 定位数据。外层负责划分任务，内层负责安排加载与计算，职责很清楚：

```text
Python launch：一共启动多少个 program
    ↓
@triton.jit：本 program 处理哪几行、哪一个 tile
    ↓
@tle.raw_kernel：这些数据怎样加载、计算、归约、写回
```

后面的代码会反复用到这些原语：

| 原语 | 可以先怎样理解 |
| --- | --- |
| vconfig | 配置逻辑向量宽度，以及尾块的有效范围 |
| vload / vstore | 一次读写一组向量元素 |
| sload / sstore | 读写单个标量 |
| vzero | 初始化向量累加器 |
| vmacc | 对向量做乘加 |
| vreduce_sum / vreduce_max | 把一组向量元素归约成一个标量 |
| vmadot | 表达矩阵计算 |
| vpack | 依输入类型做数据打包或寄存器布局重排 |

这里值得停一下，单独看看 `vconfig`。它描述的逻辑宽度，很容易被误当成单个物理寄存器能容纳的元素数。

在本次实验使用的版本中，`vconfig(-1, 1)` 按 1024-bit、FP16 的基准得到 64 个逻辑元素。等到使用 FP32 累加器时，仍可保持这 64 个元素的逻辑宽度，但需要更大的物理寄存器组。1024 bit ÷ 32 bit 是 32，因此不能把“逻辑上处理 64 个 FP32”说成“一个 LMUL=1 的寄存器装下 64 个 FP32”。

本次实验采集的 svector softmax 反汇编中就能看到 `e32, m2`，对应更大的寄存器组。类似地，`vmacc` 也不意味着最终一定是一条同名机器指令；本次实验的 mv 产物里能看到精度转换 `vfwcvt.f.f.v` 与乘加 `vfmacc.vv`。eDSL 负责表达计算，最终怎么落到机器上，还需要检查编译产物。

这就把前面的模型串起来了：**块级编程决定任务怎么分，向量 eDSL 进一步描述任务内部怎么计算。** 接下来的三个算子，会分别用到这些接口，也会用实测检验它们的效果。

### 5. 看性能图之前，先对齐比较口径

本次实验固定下面这些输入规模。mm 按 **M×N×K** 记，计算式为 `A[M,K] @ B[N,K].T`；mv 和 softmax 的两个数字表示矩阵行数与列数。

| 算子 | 本次实验的 shape |
| --- | --- |
| mm | 32×32×64、64×64×64、128×128×256、256×256×512、512×512×1024 |
| mv | 32×64、64×128、128×256、512×1024 |
| softmax | 32×64、64×128、128×256、512×1024 |

三个算子及其 PyTorch 原生对照统一使用 **FP16 输入与输出**。向量版 mv、mm 用 FP32 累加；softmax 在 kernel 内将 FP16 转为 FP32，完成 exp、归约和归一化后，再写回 FP16。因此，输入输出是半精度，中间计算的精度会按具体路径说明。

原生基线分别调用 `torch.mv`、`torch.mm`、`torch.softmax`，统一设置 **8 个 intra-op 线程**、1 个 inter-op 线程。`test_smt_mm` 原例还有 K 分段之间的精度差异，放到 mm 一节展开。

图中测量的是一次完整调用：从 Python 发起，到计算同步完成，包含任务派发。首次编译不计时，输出提前分配；输入打包、必要的输出布局转换、TCM 分配和搬运都计入时间。每项采集 5 轮、共 **50 个样本**，柱高为中位数，误差线为 p10–p90。输入重复使用，未主动清空缓存。

还有一个影响解读的前提：PyTorch 线程位于 X100 的 CPU 集合，Triton 使用 8 个 A100 工作线程。因此，这组原生对比反映的是当前软件栈下两条执行路径的调用差异，倍率同时包含硬件、运行时和实现方式的影响。PyTorch 设置为 8 线程，也不意味着每个算子都会充分用满 8 个核。

### 6. mv：先把每个任务的工作量安排好

先从矩阵向量乘开始：

```text
A: [M, K], FP16
x: [K], FP16
y = A @ x: [M], FP16
内部累加：FP32
```

相邻几行都要乘同一段 `x`，复用机会很明确。这里采用四行展开：输入向量加载一次，分别参与四行的乘加，等 K 循环结束后再归约。

```python
# acc0～acc3 预先初始化为 FP32 零向量。
for k in tle.range(0, Kfloor, vl):
    vx = tle.vload(x, k)
    a0 = tle.vload(A, row * K + k)
    a1 = tle.vload(A, (row + 1) * K + k)
    a2 = tle.vload(A, (row + 2) * K + k)
    a3 = tle.vload(A, (row + 3) * K + k)
    acc0 = tle.vmacc(acc0, a0, vx)
    acc1 = tle.vmacc(acc1, a1, vx)
    acc2 = tle.vmacc(acc2, a2, vx)
    acc3 = tle.vmacc(acc3, a3, vx)
tle.sstore(y, row, tle.cast(tle.vreduce_sum(acc0), tle.f16))
# 其余三行分别归约、转换为 FP16，再写回。
```

内层每次算四行，外层一个 program 则可以处理更多行。BLOCK 控制后者，当前整除输入对应 `grid=(M // BLOCK,)`。本次实验固定内层计算，扫描 BLOCK=4、16、min(64,M)、M；小矩阵中重合的配置只测一次。

![](https://pic1.zhimg.com/v2-531159fd0954e8092a5f4d6d512d8036_r.jpg)
*图 1：固定 BLOCK=min(64,M) 与 PyTorch 原生实现比较，不逐 shape 挑最快配置。纵轴为对数刻度，越低越快。*

小输入上，原生实现更占便宜。32×64 时，Triton 为 **125.97 μs**，PyTorch 8 线程为 **18.87 μs**；128×256 时，两者分别为 137.03、127.91 μs，差距已经缩小。到 512×1024，Triton 为 **127.66 μs**，PyTorch 为 **1811.05 μs**，前者约快 **14.19 倍**。

![](https://pic1.zhimg.com/v2-dbc9774add7a50bbbf90c52bac5187b6_r.jpg)
*图 2：上图改变每个 program 处理的行数；下图固定 BLOCK=16，只比较直接加载与 kernel 内打包。*

BLOCK 的影响也会随规模变化。128×256 上，BLOCK=16 的 109.97 μs 低于 BLOCK=64 的 137.03 μs；512×1024 上，从 BLOCK=4 改为 64，延迟由 **182.53 μs** 降到 **127.66 μs**，约 **1.43×**。但把全部 512 行交给一个 program，延迟又升到了 338.46 μs。把任务合并得更多，并不会一直更快。

这组现象可以从任务划分理解：块太小，任务切得碎；块太大，又可能只剩一两个 program，给多个工作线程的任务不够分。这是结合代码结构作出的解释，当前测量记录的是整次调用，并未通过硬件计数器拆分调度、访存和计算各自的耗时。

再看打包是否值得。同样固定 BLOCK=16，512×1024 的直接向量版为 **139.53 μs**，kernel 内打包版为 **348.62 μs**，后者耗时约为前者的 2.50 倍。

对这里的 mv，矩阵数据的复用机会有限，多搬一次数据未必能回本。因此，后文保留直接向量版作为 mv 的主线。TCM 更适合放到数据复用更充分的 mm，以及需要保存中间结果的 softmax 中继续考察。

### 6.1 打开 debug IR，确认四行展开和计算精度

性能变化已经看到了，再打开 IR，确认四行展开到底怎样落地。本次实验选取 **512×1024、BLOCK=64、FP16 输入输出**的直接向量版，查看同一次编译的 linalg 阶段与 LLVM 阶段。片段保留原始 SSA 名称，只调整换行并标记省略处，适合对照阅读，不是可独立编译的完整函数。

“linalg IR”在这里指编译流水线中的一个阶段，里面也会出现 `scf`、`arith`、`vector` 等操作。mv 已经显式描述了向量计算，所以这一层主要看循环、加载和乘加。

```text
%19:4 = scf.for %arg9 = %c0 to %9 step %c64 iter_args(%arg10 = %cst_0, %arg11 = %cst_0, %arg12 = %cst_0,
    %arg13 = %cst_0) -> (vector<64xf32>, vector<64xf32>, vector<64xf32>, vector<64xf32>) {
  %29 = vector.transfer_read %cast[%arg9], %cst {in_bounds = [true]} : memref<?xf16,
      #xsmt.memory_space<"global">>, vector<64xf16>
  %30 = arith.addi %12, %arg9 : index
  %31 = vector.transfer_read %cast_1[%30], %cst {in_bounds = [true]} : memref<?xf16,
      #xsmt.memory_space<"global">>, vector<64xf16>
  %32 = arith.addi %14, %arg9 : index
  %33 = vector.transfer_read %cast_1[%32], %cst {in_bounds = [true]} : memref<?xf16,
      #xsmt.memory_space<"global">>, vector<64xf16>
  %34 = arith.addi %16, %arg9 : index
  %35 = vector.transfer_read %cast_1[%34], %cst {in_bounds = [true]} : memref<?xf16,
      #xsmt.memory_space<"global">>, vector<64xf16>
  %36 = arith.addi %18, %arg9 : index
  %37 = vector.transfer_read %cast_1[%36], %cst {in_bounds = [true]} : memref<?xf16,
      #xsmt.memory_space<"global">>, vector<64xf16>
  %38 = arith.extf %31 : vector<64xf16> to vector<64xf32>
  %39 = arith.extf %29 : vector<64xf16> to vector<64xf32>
  %40 = math.fma %38, %39, %arg10 : vector<64xf32>
  %41 = arith.extf %33 : vector<64xf16> to vector<64xf32>
```

### 7. mm：把会重复使用的数据放进 TCM

到了矩阵乘，同一块输入往往要参与多个输出块的计算，数据搬进去之后有了更多复用机会。TCM（紧耦合存储器）正适合放在这里讨论：它提供程序可管理的局部暂存空间，而优化的关键是让搬运成本被后续计算摊薄。

### 7.1 从一个微块，扩展到完整的 M×N

这里以 **16×32 输出微块**组织计算，沿 M、N 两个方向分块。一个 program 负责 BM 行、32 列，内部依次算完 BM/16 个微块；BM 取 16、32、min(64,M)，用于比较不同的复用程度。

```text
program(pm, pn)
  ├─ 打包 B 的 32 行到 TCM，整个 program 内复用
  ├─ 取 A 的第 1 组 16 行，打包、计算一个 16×32 微块
  ├─ 取 A 的第 2 组 16 行，复用 B，计算下一个微块
  └─ ……直到处理完 BM 行
```

K 维按每 8 个元素分组，`vpack` 构造矩阵指令所需的布局。代码把 B 的打包放在外层，内层只替换 A：

```python
# n、k、bm 为编译期常量；pm、pn 来自外层 program_id。
tle.vconfig(-1, 1)
bp = tle.vpack(B, inner_tiles=(32, 8), stride=k,
               rows=32, offset=pn * 32 * k)
for mi in tle.range(0, bm // 16, 1):
    rowbase = pm * bm + mi * 16
    ap = tle.vpack(A, inner_tiles=(16, 8), stride=k,
                   rows=16, offset=rowbase * k)
    acc = tle.vzero(tle.f32, group=8)
    for kc in tle.range(0, k // 8, 1):
        a = tle.vload(ap, (0, kc), group=2)
        b = tle.vload(bp, (0, kc), group=4)
        acc = tle.vmadot(acc, a, b)
    # 随后重排累加器，按 FP16 写出当前微块。
```

在当前构建中，这些局部打包缓冲会落到线程局部 TCM。最大 shape 的 K=1024，A 的 16 行占 32 KiB，B 的 32 行占 64 KiB；对应 LLVM IR 中可以找到 `spine_thread_tcm_malloc(..., 98304)` 及配对释放。这个 program 使用的是 **96 KiB** 的局部缓冲。

这里的复用范围是**同一个 program**。跨 program 仍需重新打包 B，所以增大 BM 一方面增加了复用次数，另一方面也减少了 program 数量。和 mv 一样，复用与并行度需要一起考虑。

### 7.2 输出布局也属于成本

计算结束后，输出还要回到调用方需要的布局。当前 `smt_rvisa` 的二维 `vstore` 适合连续的 16×32 小块，这条实现先写出按 tile 排列的结果，再复制到普通行主序张量：

```python
# packed 的逻辑布局：[M/16, N/32, 16, 32]
# out 为调用方需要的连续 [M, N] 输出，已提前分配。
view = out.view(M // 16, 16, N // 32, 32).permute(0, 2, 1, 3)
view.copy_(packed.view(M // 16, N // 32, 16, 32))
```

这次复制计入所有向量 eDSL mm 的延迟。后面的 `smt.dot` 路径会在 kernel 内直接写回普通布局，因此没有这次 Python 侧复制。优化对照中的外部打包路径，则在每次调用时用 PyTorch 打包两侧输入，再计算、转换输出；它也没有提前准备好的权重。

### 7.3 用 `test_smt_mm` 看另一种写法

SpacemiT 已经提供了 `smt.dot`，矩阵乘也可以交给块级扩展来表达。本次实验加入源码中的 `test_smt_mm.py`，在同一块 K3 上比较这条路径。它的核心步骤更紧凑：

```python
# SPLIT_M 分支的核心；block pointer 已包含矩阵 shape、stride 和偏移。
b_desc = smt.descriptor_load(b_block_ptr, (0, 0))
b = smt.view(b_desc, (0, 0), (BLOCK_SIZE_K, BLOCK_SIZE_N), (8, 32))
for s in smt.parallel(0, sub_num):
    a_desc = smt.descriptor_load(a_block_ptr, (0, 0))
    a = smt.view(a_desc, (s * SUB_BLK_M, 0),
                 (SUB_BLK_M, BLOCK_SIZE_K), (16, 8))
    acc = smt.dot(a, b)
    c = smt.view(acc, (0, 0), (SUB_BLK_M, BLOCK_SIZE_N), (1, 1))
    tl.store(c_block_ptr, c.to(c_ptr.dtype.element_ty), boundary_check=(0, 1))
# c_block_ptr 的行偏移也随 s 更新，此处省略其构造。
```

`smt.view` 在这里会涉及打包或解包，可能产生实际搬运，不能按零成本操作理解。这些工作同样计入调用时间。它带来的便利是：解包之后，可以通过块指针直接写到普通矩阵输出，省去向量版在 Python 侧的布局复制。

下面三套参数使用同一个原始 `mm_kernel`，输出统一提前分配。“原例默认”保留的是 kernel 配置，不包含原包装函数中的输出分配：

| 路径 | program 输出块 | K 维与子块安排 |
| --- | --- | --- |
| 原例默认 SPLIT_K | 128×128 | K 每 256 个元素一段 |
| 调整后的 SPLIT_K | 16×32 | SUB_K=K，一次覆盖完整 K |
| SPLIT_M | 32×32 | 每个 M 子块 16 行，B 块在子块之间复用，覆盖完整 K |

看这几条曲线之前，需要先区分精度。原例默认路径把每个 K 段的 `smt.dot` 结果保存为 FP16，再累加到 FP16 中间结果。最大 shape 的独立检查中，最大绝对误差为 0.09090，有 41 个元素未满足 `atol=0.02、rtol=0.002`。因此，这条曲线单独采用原例的 `atol=0.1、rtol=0`，参考值仍为 FP64；它和另外两条路径的精度条件不同。

只把外层累加器换成 FP32，并不能补回每段 dot 已经发生的舍入。调整后的两条路径让一次 dot 覆盖完整 K，都通过了本次实验较严格的检查。这里改的是分块配置，仍使用原 kernel，编译器和运行库没有改动。

高层接口也会使用 TCM。最大 shape 的编译产物中，原例默认路径通过 `spine_thread_tcm_malloc` 分配 196608 字节，完整 K 路径与 SPLIT_M 均分配 100352 字节。局部存储可能由编译器生成，源码里有没有显式写 `smt.alloc`，并不足以判断实际是否使用了 TCM。

![](https://pic3.zhimg.com/v2-c5d856d5762df3c80c7a41376bf4b842_r.jpg)
*图 3：固定展示向量 TCM、BM=min(64,M)，以及 SMT SPLIT_M、BM=BN=32，两者对比 PyTorch 8 线程。输入输出均为 FP16，纵轴为对数刻度。*

在 32×32×64 上，向量 TCM 为 **227.78 μs**，SMT SPLIT_M 为 **238.55 μs**，PyTorch 为 **113.16 μs**，小矩阵仍由原生实现占优。到 64×64×64，三者分别为 247.65、248.48、394.91 μs，两条 Triton 路径开始更快。

最大一组 512×512×1024，向量 TCM 为 **1.197 ms**，SMT SPLIT_M 为 **1.178 ms**，PyTorch 为 **335.33 ms**，对应约 **280.1×、284.7×**。这个倍率很大，但结论要落在具体条件上：指定 PyTorch wheel 的原生 FP16 路径，与使用 A100 核心的 Triton 路径存在显著差距。它同时涉及 X100 与 A100、运行时和算子实现；本次实验没有与专门优化的 BLAS 比较，不能将其推广为一般 GEMM 性能或硬件峰值的差距。

*图 4：上图比较向量版的打包位置与 B 块复用；下图加入 test_smt_mm 三种配置。带星号的原例默认 SPLIT_K 使用单独标注的较宽误差阈值，不能直接视为同精度下的胜出。*

在 512×512×1024 上，外部打包为 **3.537 ms**，向量 TCM、BM=64 为 **1.197 ms**，整次调用约快 **2.95 倍**。沿着 TCM 路径继续看，BM=16、32、64 分别为 **1.980、1.459、1.197 ms**，增加 B 块复用确实带来了收益。不过，32×32×64 上，BM=16 为 224.63 μs，BM=32 为 227.78 μs，小矩阵没有呈现相同趋势。

`test_smt_mm` 的结果同样说明参数很关键。最大 shape 的默认 SPLIT_K 为 **730.58 μs**，但采用较宽的误差阈值；完整 K、16×32 为 **1723.08 μs**，SPLIT_M、32×32 为 **1177.86 μs**。同一个高层接口，也会因为分块、K 段之间的精度处理和数据复用方式不同，产生明显的性能差异。

在满足较严格误差检查的配置中，SMT SPLIT_M 已经接近手写向量 TCM。最大 shape 上，两者的 p10–p90 区间重叠，约 1.6% 的中位数差距不足以说明稳定胜出。这组结果给出的启发是：可以先用 `smt.view`、`smt.dot` 把计算与布局写清楚，再根据实际瓶颈决定哪些局部值得用向量 eDSL 细化。

几组对照改变的条件也要分清：外部打包改为 program 内 TCM 打包，改变了打包位置和实现；调整 BM，改变了复用次数与任务粒度；切到 `smt.dot`，还改变了输出写回方式。因此，上面的收益反映的是这些实现调整后的完整调用，不能合成一个“纯 TCM 带宽提升”的数字。

### 7.4 从两条 mm 路径的 IR 看打包、矩阵乘与 TCM

两条实现的延迟很接近，编译后的计算又有什么相同和不同？继续选取 **512×512×1024**，先看 BM=64、BN=32 的向量 TCM 版。linalg 阶段把打包和矩阵计算都保留了下来：

```text
%8 = tensor.empty() : tensor<1x128x32x8xf16>
%pack = linalg.pack %7 outer_dims_perm = [0, 1] inner_dims_pos = [0, 1] inner_tiles = [32, 8] into %8 :
    tensor<32x1024xf16> -> tensor<1x128x32x8xf16>
%collapsed = tensor.collapse_shape %pack [[0], [1], [2, 3]] : tensor<1x128x32x8xf16> into
    tensor<1x128x256xf16>
%9 = arith.muli %4, %c64 : index
%10 = tensor.empty() : tensor<1x128x16x8xf16>
scf.for %arg6 = %c0 to %c4 step %c1 {
  %11 = arith.muli %arg6, %c16 : index
  %12 = arith.addi %9, %11 : index
  %13 = arith.muli %12, %c1024 : index
  %reinterpret_cast_1 = memref.reinterpret_cast %arg0 to offset: [%13], sizes: [16, 1024], strides: [1024, 1]
      : memref<*xf16, #xsmt.memory_space<"global">> to memref<16x1024xf16, strided<[1024, 1], offset: ?>,
      #xsmt.memory_space<"global">>
  %14 = bufferization.to_tensor %reinterpret_cast_1 restrict : memref<16x1024xf16, strided<[1024, 1], offset:
      ?>, #xsmt.memory_space<"global">> to tensor<16x1024xf16>
  %pack_2 = linalg.pack %14 outer_dims_perm = [0, 1] inner_dims_pos = [0, 1] inner_tiles = [16, 8] into %10 :
      tensor<16x1024xf16> -> tensor<1x128x16x8xf16>
  %collapsed_3 = tensor.collapse_shape %pack_2 [[0], [1], [2, 3]] : tensor<1x128x16x8xf16> into
      tensor<1x128x128xf16>
  %15 = scf.for %arg7 = %c0 to %c128 step %c1 iter_args(%arg8 = %cst_0) -> (vector<8x64xf32>) {
    %24 = vector.transfer_read %collapsed_3[%c0, %arg7, %c0], %cst {in_bounds = [true]} :
        tensor<1x128x128xf16>, vector<128xf16>
    %25 = vector.shape_cast %24 : vector<128xf16> to vector<2x64xf16>
    %26 = vector.transfer_read %collapsed[%c0, %arg7, %c0], %cst {in_bounds = [true]} : tensor<1x128x256xf16>,
        vector<256xf16>
    %27 = vector.shape_cast %26 : vector<256xf16> to vector<4x64xf16>
    %28 = "vector_ext.cross_batch_matmul"(%25, %27, %arg8) {k = 8 : i64, m = 8 : i64, n = 8 : i64} :
        (vector<2x64xf16>, vector<4x64xf16>, vector<8x64xf32>) -> vector<8x64xf32>
    scf.yield %28 : vector<8x64xf32>
  }
  %16 = "vector_ext.group_interleave"(%15) {groupLen = 8 : i64} : (vector<8x64xf32>) -> vector<4x128xf32>
  %17 = "vector_ext.group_interleave"(%16) {groupLen = 16 : i64} : (vector<4x128xf32>) -> vector<2x256xf32>
  %18 = vector.shape_cast %17 : vector<2x256xf32> to vector<16x32xf32>
  %19 = arith.truncf %18 : vector<16x32xf32> to vector<16x32xf16>
  %20 = arith.divui %12, %c16 : index
  %21 = arith.muli %20, %c16 : index
  %22 = arith.addi %21, %5 : index
  %23 = arith.muli %22, %c512 : index
  %reinterpret_cast_4 = memref.reinterpret_cast %arg2 to offset: [%23], sizes: [16, 32], strides: [32, 1] :
      memref<*xf16, #xsmt.memory_space<"global">> to memref<16x32xf16, strided<[32, 1], offset: ?>,
      #xsmt.memory_space<"global">>
  vector.transfer_write %19, %reinterpret_cast_4[%c0, %c0] {in_bounds = [true, true]} : vector<16x32xf16>,

```

这段 IR 可以顺着循环边界读：B 先打包成 `1×128×32×8`，A 打包成 `1×128×16×8`，其中 128 来自 K/8。B 的 `%pack` 在处理四个 M 微块的循环之前，A 的 `%pack_2` 在循环内部，正好对应“打包一次 B、替换四次 A”。

内层的 `vector_ext.cross_batch_matmul` 接收 FP16 输入，累加结果为 `vector<8x64xf32>`。接下来的 `group_interleave` 和 `shape_cast` 才把中间布局重排成 `16×32` 微块，最后转为 FP16。这也说明，IR 中的向量形状需要结合前后操作看，不能直接当成最终张量布局。

LLVM IR 则能把 TCM 的分配、加载和矩阵乘加串起来：

```llvm

;...
```

先看地址：`98304` 对应 96 KiB 总空间，紧接着的 `getelementptr i8 ... 65536` 把 A 缓冲放在 B 的 64 KiB 缓冲之后。`vle` 从两块空间读取 FP16 数据，再提取矩阵计算需要的向量分组。

接着看类型：`llvm.riscv.smt.vfwmadot` 的两个乘数是 `half`，累加输入与返回值是 `float`；结束处还有配对的 TCM 释放。到这里，前面描述的存储和计算安排都有了编译产物的依据，至于这套安排省了多少时间，仍由性能对照回答。

换成 `test_smt_mm` 的 SPLIT_M，固定 BM=BN=32、SUB_M=16，linalg 阶段的结构更接近源码里的“打包、计算、解包”：


`linalg.mmt4d` 对四维分块表示执行矩阵乘，B 采用转置布局；这里的四维是矩阵 tile 的组织方式，不是额外增加了一个业务 batch 维度。[Linalg 的 mmt4d 说明](https://mlir.llvm.org/docs/Dialects/Linalg/#linalgmmt4d-linalgmmt4dop)

### 8. softmax：TCM 里存输入，还是存 exp

softmax 的稳定计算形式很熟悉：

```text
m = max(x)
e[i] = exp(x[i] - m)
y[i] = e[i] / sum(e)
```

算完一行的最大值后，exp 会在求和与归一化时用到。这里有两种直接的写法：重算版先求 max，再算 exp 并求和，最后重新算 exp、归一化；保存版则把第二遍的 exp 转成 FP16、写到输出缓冲区，第三遍读回并转为 FP32，再归一化。

前者多算一次 exp，后者多一次写回与读取，还多一次 FP16 中间舍入。本次实验同时检查两者的数值结果，再比较这笔取舍。

当前四个行长都能被 64 整除，性能代码按完整向量块处理。如果以后扩展到非整齐行长，max 阶段的尾部填充值要格外留意：全负输入下，补零可能让无效位置成为最大值，破坏数值稳定化。短行也应从有效元素初始化，避免满向量读取越界。本文的整除 shape 不覆盖这些边界。

### 8.1 在 `smt_rvisa` 中暂存一行输入

第一条 TCM 路径保留向量 eDSL，先把当前行搬进局部缓冲，再从中加载数据完成 max、exp-sum 和归一化：

```python
vl = tle.vconfig(-1, 1)
scratch = tle.alloc((1, n // 64, 1, 64), tle.f16)
tle.pack(X, (row, 0), scratch, (1, n // 64, 1, 64), n)

# 后续循环从 scratch 加载，再执行向量归约与计算。
x16 = tle.vload(scratch, (0, i // 64, 0, 0), dtype=tle.f16)
x = tle.cast(x16, tle.f32)
```

这里缓存的是**输入**，exp 仍要算两次。一个 program 分别处理 1、4、16 行，记作 BR=1、4、16；缓冲逐行复用，不必同时容纳 BR 行。N=1024、BR=4 的编译产物申请了 2304 字节 TCM，包括一行 2048 字节 FP16 数据和编译器临时空间。

这组对照分两步读：BR=1 与原始重算版比较，观察暂存输入的效果；再增加 BR，观察任务粒度变化。这样才能避免把减少 program 数量的收益也算到缓存上。

### 8.2 用块级表达，把 exp 放进 TCM

第二条路径回到块级表达：FP16 输入加载后转为 FP32，算出整行 exp，存进显式申请的 TCM 缓冲，再求和、归一化并转回 FP16。这里也比较 BR=1、4、16，缓冲在各行之间复用：

```python
import triton.language.extra.smt as smt

@triton.jit
def softmax_block_tcm_grouped(X, Y, N: tl.constexpr, BR: tl.constexpr):
    pid = tl.program_id(0)
    offsets = tl.arange(0, N)
    buf = smt.alloc([N], type=tl.float32, scope="tcm")
    for r in range(BR):
        row = pid * BR + r
        x = tl.load(X + row * N + offsets).to(tl.float32)
        e = tl.exp(x - tl.max(x, 0))
        tl.store(buf, e)
        cached = tl.load(buf)
        denominator = tl.sum(cached, 0)
        tl.store(Y + row * N + offsets, (cached / denominator).to(tl.float16))
```

这段代码的计算由普通 `tl` 运算完成，缓冲由 `smt.alloc` 申请，正好体现了两种接口的配合。它与前面的 `smt_rvisa` 向量 eDSL 是不同接口。N=1024 时，编译产物实际分配 10240 字节 TCM，包含显式 exp 缓冲和编译器临时空间。

不过，从向量版切到块级版，改变的不只是缓存位置。为了把条件对齐，这里加入了**相同块级表达、没有显式 TCM 缓存**的版本，直接用 `e / tl.sum(e, 0)` 写回，并在 BR=1、4、16 下逐一配对。

这个对照本身也有个有意思的细节：编译器为它申请了 6144 字节 TCM 临时空间。可见，源码没有显式缓存，并不等于执行时完全不使用 TCM。

### 8.3 把表达方式和任务粒度分开比较

另一条对照来自 `test_softmax_fragment.py` 的三遍扫描基线，经过 FP16 适配后使用 ROW_SIZE=4、COL_SIZE=64：输入输出为 FP16，加载后转 FP32，exp、分母累计和归一化在 FP32 下进行，写到输出里的 exp 仍为 FP16。它与整行块级版同时存在列分块循环、输出往返和 exp 实现上的差异，因此适合比较整体表达方式。

同文件的 `scope="fragment"` 路径此前使用 FP32 输入，在 `3.6.0+spacemit.b0` wheel 上编译失败，报错停在 `ConvertMemRefToSpeRT`，提示 fragment 内存空间未解析。因此图中只展示运行成功、完成 FP16 适配的三遍 baseline；fragment 保留为失败记录，也不作为 TCM 路径来解读。

![](https://picx.zhimg.com/v2-2dbc2cab5efbab9041fa49199f30754d_r.jpg)

512×1024 上，重算版为 **810.77 μs**，在输出保存 exp 为 **728.00 μs**。增加 TCM 输入缓存、保持 BR=1，延迟反而升到 **1160.21 μs**；改为 BR=16 后是 899.91 μs，仍慢于基础保存版。在这组输入上，暂存输入的收益没有抵消搬运和重复计算的成本。

把块级版本按相同 BR 排在一起，结论更清楚：

| 每个 program 的行数 | 无显式缓存 | 显式 TCM exp 缓存 |
| --- | --- | --- |
| BR=1 | 890.41 μs | 905.93 μs |
| BR=4 | 662.86 μs | 667.55 μs |
| BR=16 | 620.44 μs | 630.32 μs |

**相同任务粒度下，显式 TCM exp 缓存没有显示出额外收益。** 两侧从 BR=1 改为 BR=4⁄16 都变快了，这更支持调整任务粒度的作用，不能把显式缓存版自身的前后变化都归功于 TCM。两者的存储占用也不同：无显式缓存的 BR=4⁄16 实际分配 6144 字节 TCM，显式缓存版为 10240 字节。

三遍、64 列分块的 baseline 在最大 shape 上为 **2295.37 μs**，慢于整行块级表达。但这次变化同时涉及循环、访存和 exp 的计算方式，适合得出“当前整行写法更快”的结论，不能单独归功于某一种缓存机制。

![](https://pic2.zhimg.com/v2-2d54b2ac9d117fbcc79a597b51fe5a77_r.jpg)
*图 6：固定 BR=4，同时展示普通块级和 TCM exp 缓存，对比 PyTorch 8 线程。纵轴为对数刻度。*

与原生实现相比，小输入仍然吃亏：32×64 的 TCM、BR=4 为 **123.26 μs**，PyTorch 为 **43.31 μs**。到 128×256，两者分别为 168.16、243.07 μs；512×1024 时为 **667.55、3449.02 μs**，约 **5.17×**。最大 shape 的普通块级 BR=4 为 662.86 μs，约为 PyTorch 的 **5.20×**，与显式缓存版接近。

原生对比固定使用 BR=4，BR=16 等配置留在优化图中。对这里的 softmax，值得优先考虑的是整行表达和任务粒度；显式 TCM 缓存是否保留，则要与相同 BR 的版本比较后再决定。

这些结果都经过数值检查：参考值从同一份 FP16 输入转为 FP64 后计算，阈值为 `rtol=0.002、atol=0.00001`；另外覆盖输入整体平移 −1000、+1000 后转成 FP16 的情况，并检查行和与输出前后保护区。参考值必须来自量化后的实际输入，不能直接沿用原 FP32 随机数的结果。检查范围为非空、连续、有限 FP16 输入，未覆盖 NaN/Inf 的完整语义。

### 9. 总结

本次实验围绕 mv、mm 和 softmax，比较了块级编程、SpacemiT 扩展与向量 eDSL 在 K3 上的实际表现。三个算子的结果说明，性能并不取决于代码写得有多底层，而在于任务划分、数据复用和存储布局是否适合当前计算。

mv 展示了任务粒度的影响：一个 program 处理更多行，可以复用输入向量，但工作量继续增大并不一定更快。mm 中，TCM 分块相较外部缓冲版本降低了延迟，块级 SMT 写法也表现出竞争力；这些收益同时受到打包、输出布局和累加精度的影响。softmax 则给出了一个很直接的对照：整行表达和合适的行分组带来了收益，而在相同 BR 下，显式缓存 exp 没有比普通块级版本更快。

**TCM 能否带来收益，取决于数据复用节省的时间是否足以抵消搬运和布局转换的成本。** 显式使用 TCM 本身并不等于完成了优化；普通块级代码也可能由编译器分配 TCM。正文中的 IR 将这些实现细节与性能结果联系起来，也说明了为什么只看 Python 代码还不足以判断最终执行方式。

与 PyTorch 8 线程原生实现的对比中，较小输入仍受到调用开销的制约，较大输入则在本次测试的配置下体现出明显收益。这是两条实际执行路径的调用延迟对比，不能直接解释为同核指令效率的差距；mm 中采用不同累加方式的版本，也需要结合各自的误差结果理解。

这三个算子最终呈现的是同一个结论：在 K3 上使用 Triton，块级模型和向量 eDSL 各有适用之处。优化的价值，体现在满足数值要求后，包含必要搬运与布局转换的完整调用是否真正变快。
