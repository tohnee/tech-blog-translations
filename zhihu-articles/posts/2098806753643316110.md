vLLM 让同一张显卡多接 2 到 4 倍的请求，靠的是操作系统里的分页。

大模型推理服务（LLM serving，AI Infra 里负责把模型跑起来、对外提供服务的那一块）里常被提起的几项优化，大多能在 CPU 和操作系统的设计里找到原型。投机解码就是 CPU 的分支预测，FlashAttention 是缓存分块，连续批处理是操作系统的分时调度，PagedAttention 是虚拟内存加写时复制。

我在自己的 M4 Mac 上跑了几个小实验：同样逻辑的 C 代码，换个写法就能慢几十倍；同样 1600 万个数，存成链表比存成数组慢了近 400 倍。

## 先花一分钟：大模型推理在忙什么

大模型一次只生成一个 **token**（大致是一个词或半个词）。生成第 100 个 token 时，模型要“回头看”前 99 个。每个 token 在每一层都会算出两个向量，叫 **K** 和 **V**，回头看就是拿新 token 和这些 K、V 做注意力计算。旧 token 的 K、V 不会再变，算一次存起来就行，存下来的这份就是 **KV cache**。

一个请求分两个阶段。**prefill** 把用户的提示词一次性喂进去，几百上千个 token 一起算，GPU 的算力用得很满。之后是 **decode**，每一步只生成一个 token，却要把模型的全部权重从显存读一遍，算的东西很少。

KV cache 很占地方。Llama-3.1-8B 每个 token 的 KV cache 是 128KB，一个 2000 token 的对话就是 256MB，一张卡上同时跑几百个请求，显存先被它吃光。推理服务的优化，大部分是在想办法让 GPU 少等数据、让显存少浪费。CPU 和操作系统在这两件事上已经琢磨了几十年。

## 一、一颗 CPU 核心里有什么

一个 CPU 核心不是一条一条执行指令的，它更像一个后厨：前面有人接单、拆单，后面好几个厨师同时开火。

![](https://pic3.zhimg.com/v2-55077d997da448f93c4379f7cad19eaa_r.jpg)
*一个 CPU 核心的结构：前端负责取指、分支预测、译码和寄存器重命名；指令按顺序进入重排序缓冲区；调度器把数据到齐的指令发给多个 ALU、访存单元和 SIMD 单元乱序执行；结果写回重排序缓冲区后按顺序提交*

- **前端**负责接单：取指令、译码，再把指令里用到的寄存器换成内部编号（寄存器重命名，register renaming），消掉那些只是名字撞了、数据其实无关的假依赖。前端里还有个**分支预测器**，遇到 `if` 不等结果出来，先猜一条路往下取指令。
- **后端**负责炒菜。这里有几个 **ALU**（算术逻辑单元，做整数加减、比较、位运算），几个访存单元，几个 **SIMD** 单元（一条指令同时处理一排数，比如一次加 4 个 double）。调度器盯着所有指令，谁的数据先到齐就先发谁，不管它在程序里排第几，这叫**乱序执行**。
- 中间是**重排序缓冲区**（ROB，reorder buffer）。指令进来时按程序顺序排队，执行可以乱，提交（retire，把结果正式写回、让程序看得见）必须按顺序从队头来。

乱序执行最怕猜错，ROB 就是为这个准备的。后厨几个菜可以同时炒、谁先好谁先出锅，传菜口还是按点单顺序上菜；发现某一单点错了，这单之后还没端出去的菜全倒掉，客人根本不知道。CPU 也一样，分支猜错时，ROB 里排在分支后面的指令全部作废，程序看到的状态和老老实实按顺序执行时一模一样。

![](https://pic3.zhimg.com/v2-94db96895c855c1b569d392d48ff01c4_r.jpg)
*CPU 把大量晶体管花在控制逻辑和大缓存上，只有几个大核心；GPU 有成百上千个简单的计算单元，控制逻辑和缓存相对很少，靠切换线程组隐藏等待*

GPU 的设计思路正好反过来。CPU 把大量晶体管花在分支预测、乱序执行和大缓存上，为的是让一条指令流尽快跑完；GPU 堆了成百上千个简单的计算单元，控制逻辑很少。它的线程 32 个一组（叫 **warp**），一组线程一起执行同一条指令；这组在等内存，就换另一组上来算。

放到芯片上看：

![](https://pic2.zhimg.com/v2-63316e0e29ea7c3b48ee54a78f738521_r.jpg)
*芯片级结构示意：CPU 芯片上是几个大核、小核和共享缓存；H100 芯片上铺满上百个 SM，中间是共用的 L2，两侧是 HBM 显存；一个 SM 分成 4 份，每份有调度器、寄存器堆、FP32 单元和 Tensor Core*

GPU 芯片上铺满了 **SM**（streaming multiprocessor，GPU 里相当于“一个核心”的单位），H100 SXM 有 132 个。每个 SM 分成 4 份，每份有一个 warp 调度器、一块寄存器堆、32 个 FP32 单元和一个 **Tensor Core**。Tensor Core 专门做矩阵乘，一条指令算完一小块矩阵乘加。大模型的计算绝大部分是矩阵乘，主要就靠它。

换一组 warp 上场几乎不花时间。H100 每个 SM 有 64K 个 32 位寄存器，共 256KB，驻留在上面的所有 warp 的寄存器一直放在那里，换谁上场都不用保存、恢复任何东西。CPU 没有这么大的寄存器堆，只能靠缓存和乱序执行尽量少等。

矩阵乘法是成千上万个互不相关的乘加，适合 GPU 这种靠数量取胜的做法。代价是 GPU 很怕数据供不上。

## 二、流水线：CPU 其实同时在做好几件事

### 流水线和依赖链

洗衣服分洗、烘、叠三步。一件衣服走完三步再放下一件，三台机器总有两台闲着；第一件进烘干机时就把第二件塞进洗衣机，三台机器一起转，这就是流水线。

![](https://pic4.zhimg.com/v2-b972f7f0e42de0a866f7e5d2d9c08fe5_r.jpg)
*不用流水线时一条指令走完取指、译码、执行、写回四步，下一条才开始；用了流水线，每个时钟周期四个部件各忙一条指令，稳定后每个周期完成一条；遇到分支时前端按猜测已经取了好几条，猜错就全部作废*

现代 CPU 不止一条流水线，执行单元有好几个，一个时钟周期能同时发射好几条指令。前提是这些指令互不依赖。下一条要等上一条的结果，执行单元再多也只能干等。

数组求和最普通的写法就有这个问题：

```c
double s = 0;
for (int i = 0; i < N; i++)
    s += a[i];
```

每次加法都要等上一次的 `s`，一百万次加法排成一条长链，浮点加法单元一次只能干一件事。

换成四个累加器：

```c
double s0 = 0, s1 = 0, s2 = 0, s3 = 0;
for (int i = 0; i < N; i += 4) {
    s0 += a[i];
    s1 += a[i + 1];
    s2 += a[i + 2];
    s3 += a[i + 3];
}
double s = (s0 + s1) + (s2 + s3);
```

四条链互不相干，可以同时在流水线里跑。实测从 10.5ms 降到 3.6ms，快了将近 3 倍。

编译器不会自动帮你这么改，因为浮点加法不满足结合律，`(a+b)+c` 和 `a+(b+c)` 可能差在最后一位，换顺序就会改结果。整数没有这个顾虑：同样的单累加器写法换成整数，编译器自己就拆开了，还用上了 SIMD，跑出 1.4ms，比我手写的四累加器（2.0ms）还快。

### 分支预测：猜错一次，白干十几个周期

流水线越深，分支越麻烦。`if` 的条件还没算出来，后面十几条指令已经进了流水线，CPU 只能先猜一条路走下去，猜错了再全部作废，从正确的地址重来。

实验用一百万个 0 到 255 的随机数，只累加大于等于 128 的那些：

```c
for (int i = 0; i < N; i++) {
    if (p[i] >= 128) {
        s += p[i];
    }
}
```

同一个函数、同一组数，先排个序再跑：

| 数据 | 耗时 |
| --- | --- |
| 随机顺序 | 54.7 ms |
| 排好序 | 5.5 ms |

排序后快了 10 倍。随机数据下这个 `if` 一半成立一半不成立，预测器怎么猜都是五五开。排好序以后，前一半全不成立、后一半全成立，几乎次次猜中。

最初的版本两边一样快，看汇编才知道 clang 把 `if` 改成了“两边都算、再挑一个”的无分支写法，顺手还用上了 SIMD，跑出 1.0ms，比排好序的分支版本还快 5 倍。为了让分支真的存在，我只好在 `if` 里塞一句空的内联汇编。编译器这一手也正是对付分支预测失败的标准办法：数据没规律时，就别让 CPU 猜。GPU 上同样怕分支，一个 warp 里的线程走了不同的分支，两条路只能先后各执行一遍，这叫分支发散（warp divergence）。

### 投机解码：大模型版的推测执行

CPU 遇到分支时，先猜一条路执行下去，结果先放着不提交，等分支算出来再决定收下还是作废。这叫**推测执行**（speculative execution）。大模型推理里有个几乎一样的技术，叫**投机解码**（speculative decoding）。

![](https://pic4.zhimg.com/v2-4a2dc45dc8b774c0fc115f0e02a389c1_r.jpg)
*左边是 CPU：分支预测器先猜后面的指令，结果放在 ROB 里不提交，分支算出来后猜对的按顺序提交、猜错的清空；右边是投机解码：小模型连猜 4 个 token，大模型一次前向验证，通过的前缀全部接收，第一个没通过的位置由大模型重新出一个，后面的扔掉*

decode 每一步只生成一个 token，却要把整个大模型的权重读一遍，GPU 大部分时间在等显存。投机解码是这样做的：

1. 用一个小得多的草稿模型，便宜地连猜几个 token；
2. 大模型一次前向把这几个 token 一起验证。权重反正要读一遍，验 5 个和验 1 个花的时间差不多；
3. 从第一个开始，通过验证的那段前缀直接收下；第一个没通过的位置由大模型重新出一个 token，后面的全扔掉。

对应关系是：草稿模型是分支预测器，大模型验证是执行，按顺序收下通过的前缀是 ROB 按顺序提交，扔掉后面的是清空流水线。猜错的代价也一样，只是白算了一点，不会改变结果。这里的“不改变结果”分两种情况：每一步都选概率最高的词（贪心解码）时，输出和不猜时逐字相同；按概率随机采样时，验证那一步按概率决定收不收，保证的是输出的概率分布和不猜时一样，不是每次生成的字都一样。猜中的越多越划算，Google 和 DeepMind 2022、2023 年的两篇论文分别报告了 2 到 3 倍、2 到 2.5 倍的提速。

## 三、离计算单元越远，数据越贵

### 存储层级

计算单元很快，内存很慢。为了少等，硬件在两者之间放了好几层缓存，一层比一层大，也一层比一层慢。

![](https://picx.zhimg.com/v2-f71de99a00a8e4cb05c4b099adf5b001_r.jpg)
*存储层级：CPU 一侧从寄存器、L1、L2 到内存、SSD，延迟从不到 1 纳秒涨到几十微秒；GPU 一侧从寄存器和共享内存、HBM 显存、NVLink 到 PCIe 和 SSD，带宽一层比一层低*

GPU 一侧有几个名字要认识。**HBM** 是显卡上的显存，H100 每秒能读 3.35TB。**共享内存**（shared memory）是每个 SM 里的一小块片上 SRAM，比 HBM 快得多，每个 SM 只有两百多 KB。**NVLink** 连接卡与卡。**PCIe** 连接显卡和 CPU 内存，单向只有约 64GB/s，比 HBM 慢五十倍。

缓存之所以有用，是因为程序访问数据有规律，这叫**局部性**。时间局部性是说刚用过的数据很快还会再用，空间局部性是说用了一个地址，很快会用到它旁边的地址。所以缓存不是一个字节一个字节地搬，而是一次搬一整块，叫**缓存行**（cache line），常见的 x86 是 64 字节，我的 M4 是 128 字节。CPU 里还有**硬件预取器**，发现你在顺序读，就提前把后面的缓存行搬进来。

### 换个循环顺序，慢 50 倍

C 的二维数组在内存里一行接一行地存（行优先）。同样是把 4096×4096 的 `int` 数组加一遍：

```c
// 按行：外层 i，内层 j
for (int i = 0; i < R; i++)
    for (int j = 0; j < C; j++)
        s += m[i][j];

// 按列：外层 j，内层 i
for (int j = 0; j < C; j++)
    for (int i = 0; i < R; i++)
        s += m[i][j];
```

按行读 1.0ms，按列读 51ms，差了 50 倍。

![](https://pica.zhimg.com/v2-bec5c15f3578c2949cbde9866afe2be8_r.jpg)
*二维数组在内存里一行接一行存；按行读时地址一路往后，每条缓存行的数都用上；按列读时每次跳过一整行，搬进来的缓存行只用一个数*

按行读时地址一路往后，搬进来的每条缓存行 32 个数全都用上，预取器也猜得中。按列读每次跳过一整行（16KB），一条缓存行只用到一个数，等回头要用它旁边那个数时，这一行早被挤出缓存了。

这 50 倍里有一部分算 SIMD 的：按行读的循环被编译器向量化了，按列读的没法向量化。把向量化关掉再比，按行 4.3ms、按列 55ms，单是内存访问模式就差了 13 倍。

链表更极端。同样 1600 万个数，节点随机散在内存里的链表要 1664ms，数组顺序加一遍只要 2ms。数组这个数里有 SIMD 的功劳，关掉向量化是 4.3ms，链表照样慢了近 400 倍。缓存行用不满只是一部分原因，更要命的是下一个节点的地址要等这个节点读回来才知道（指针追逐，pointer chasing），乱序执行再厉害也没法提前发出下一次读取。数组的地址都算得出来，CPU 可以同时发出几十个读请求。

游戏引擎里的 **ECS**（实体-组件-系统）架构也是这个思路：把“所有怪物的位置”连续存成一列，而不是每个怪物一个对象、到处是指针。我写的 C# ECS 库 [EasyEcs](https://ecs.xgamedev.net/) 也是这样存组件的。

### 伪共享：没共享数据，也在抢

多线程还有一个更隐蔽的坑。四个线程各加各的计数器，互不相干，却慢得离谱：

```c
// 4 个计数器挨着放：共 32 字节
_Atomic long packed[4];

// 每个计数器独占一条缓存行
struct padded {
    _Atomic long v;
    char pad[128 - sizeof(long)];
};
```

| 计数器摆法 | 4 线程各加 2000 万次 |
| --- | --- |
| 挨着放 | 587 ms |
| 每个独占一条缓存行 | 37 ms |

两种写法差了 16 倍，代码里唯一的区别是那一行填充。

![](https://pic4.zhimg.com/v2-9077c4bed7cdb455c5158682eea72df5_r.jpg)
*两个核心分别只改变量 a 和 b，但 a、b 在同一条缓存行里，一致性协议让这一行在两个核心之间来回失效；每个变量补齐到一整条缓存行后互不打扰*

问题出在**缓存一致性协议**上。每个核心有自己的缓存，同一条缓存行可能在好几个核心里各有一份。为了不读到过期数据，硬件按一套规则办事（最常见的是 MESI 协议）：一个核心要写某条缓存行，得先让别的核心手里那份作废。

四个计数器挤在一条缓存行里，核心 1 写 `a`，核心 2 手里那份就作废了；核心 2 写 `b`，又得把这一行抢回来。变量明明不同，抢的却是同一行，这叫**伪共享**（false sharing）。

GPU 上这个问题换了个样子。一个 warp 的 32 个线程同时读内存，地址连续的话，硬件能把它们合并成几次大的读取（合并访存，coalescing）；地址散乱就只能拆成很多次小的。张量的维度最好凑成 64 的倍数，也是为了让访存和 Tensor Core 的分块对得齐。Karpathy 在 nanoGPT 里把 GPT-2 的词表从 50257 补到 50304（64 的倍数），代码注释写的就是为了效率，他自己发推说这一改快了约 25%。

## 四、少搬数据：分块、融合、少占字节

### 算力在等搬运

前面讲的是怎么搬得顺。有时候要搬的东西本身就太多，搬得再顺也赶不上算。

有个简单的指标可以衡量：每从内存搬一个字节，能做几次计算，叫算术强度（arithmetic intensity）。H100 每秒能做将近 1000 万亿次 16 位浮点运算，显存每秒能读 3.35 万亿字节，两者一除约等于 300。每搬一个字节做不到 300 次计算，算力就会闲着，瓶颈在显存带宽上。这套分析方法叫 Roofline 模型。

decode 远远达不到这个数。一批只有 1 个请求（batch = 1）时，每个权重（2 字节）只参与一次乘法和一次加法，算术强度约等于 1。Llama-3.1-8B 的权重有 16GB，读一遍要将近 5 毫秒，一个请求单独跑，每秒最多吐 200 个 token 左右，H100 的算力 99% 都闲着。下图纵轴的 TFLOPS 是每秒万亿次浮点运算：

![](https://pic1.zhimg.com/v2-517fc98c67fd9d1a4ac84e1712887b58_r.jpg)
*H100 的 Roofline：算术强度低于约 300 时卡在显存带宽，高于它时卡在算力；batch 为 1 的 decode 只能用到约 3 TFLOPS，batch 为 64 约 214 TFLOPS，prefill 能顶到算力上限*

办法是一次读出来的权重给很多请求用。64 个请求一起 decode，权重还是读一遍，算力却用上了 64 份，这就是批处理（batching）。第六、七节讲的显存管理和调度，很大程度上都是为了让一批里塞进更多请求。

### 分块：把要反复用的数据留在快的那一层

矩阵乘法 `C = A × B`，N = 1024，三层循环换个顺序：

| 循环顺序 | 耗时 |
| --- | --- |
| i-k-j（最内层顺序读 B 和 C 的一行） | 135 ms |
| i-j-k（教科书写法，最内层按列读 B） | 928 ms |
| j-k-i（最内层按列读 A 和 C） | 6800 ms |

最快和最慢差了 50 倍，道理和上一节的按行、按列读一样。

再往下就是**分块**（tiling）：把矩阵切成 64×64 的小块，一次只算一小块，让它在缓存里反复用完再换下一块。在 M4 上它只比 i-k-j 快了 15%，矩阵加大到 2048 也只快 17%。我猜是 M4 的缓存够大、预取器也聪明，i-k-j 本身已经很顺了，这点没有深究。真正的数学库会在分块之上再做寄存器分块、SIMD 和多线程，系统自带的 BLAS 算同样的矩阵只要 6ms，比我手写最快的版本还快将近 20 倍。

到了 GPU 上，分块的收益大得多。那边快的那一层实在太小：每个 SM 的共享内存只有两百多 KB，和几十 GB 的 HBM 差了五个数量级。

### FlashAttention：分块加融合

注意力计算的标准写法分三步：Q 乘 K 得到分数矩阵 S，对 S 做 softmax 得到 P，再拿 P 乘 V。S 和 P 都是 N×N 的（N 是序列长度），每一步都把结果整个写回 HBM，下一步再读出来。

![](https://pic2.zhimg.com/v2-5f367edc81d0411855ce0fab2a745847_r.jpg)
*普通注意力把 N×N 的中间结果 S 和 P 写回显存再读出来；FlashAttention 把 Q、K、V 切成小块，在 SRAM 里一气呵成地算完分数、softmax 和乘 V，只把输出写回显存*

FlashAttention 用的就是 CPU 矩阵乘分块的思路，外加一步**算子融合**。它把 Q、K、V 切成小块搬进 SRAM，算分数、softmax、乘 V 三步在 SRAM 里连着做完，只把最终输出写回显存，N×N 的矩阵从头到尾都不进 HBM。

麻烦在 softmax 上：它要先知道一整行的最大值和总和才能算，分块时一次只看得到一小段。FlashAttention 的办法叫在线 softmax，一边扫一边记着当前的最大值和总和，遇到更大的值，就把之前算好的部分按比例修正。论文报告 GPT-2 训练快了 3 倍。

融合在编译器课里叫**循环融合**（loop fusion）：两个循环合成一个，中间结果留在寄存器里，省掉一次写回内存、再读出来。GPU 上把几个算子合成一个 kernel（kernel 就是 GPU 上执行的一个函数），是一回事。

### 每个数少占几个字节

decode 既然卡在显存带宽上，也可以从另一头下手：让每个数小一点。

浮点数由三部分组成：符号、指数（决定范围）、尾数（决定精度）。FP32 占 4 字节；BF16 只占 2 字节，保留了 FP32 的指数位、砍掉大部分尾数，范围不变，精度降低。再往下还有 FP8、INT4。

权重从 BF16 降到 INT4，要从显存读的字节少了四分之三。decode 本来就卡在带宽上，省下的字节几乎直接变成速度，代价是一点精度。KV cache 也能这样量化，同样的显存就能放下更多 token、更多请求。

## 五、内存分配：碎片是怎么来的

### malloc 是怎么找到一块内存的

`malloc` 要在一大块堆内存里找一段空闲的给你，`free` 时再收回来。哪些地方是空的，常见的有三种记法，一种比一种复杂：

![](https://pic2.zhimg.com/v2-df04737e827a0f53d6ad8669e0a84f9d_r.jpg)
*三种空闲链表：隐式空闲链表靠每块头部记录的大小挨个往后跳，要连已分配的块一起扫；显式空闲链表只把空闲块用指针串起来；分离空闲链表按大小分成好几条链，要多大直接去对应的链上拿*

- **隐式空闲链表**：每块开头记着自己多大，从头一块一块往后跳，已分配的块也得跳过。实现简单，堆一大就慢。
- **显式空闲链表**：只把空闲块用指针串起来，分配时只看空闲块。
- **分离空闲链表**：按大小分成好几条链，16 字节一条、32 字节一条，要多大就去对应那条拿。现代的 `malloc` 基本都是它的变体。

栈分配就省事多了：函数调用时把栈顶指针往下挪一点，返回时挪回来，分配和释放都只是一条加减法指令，不用找，也不会碎。所以热路径上能放栈上的东西，尽量别往堆上放。

### 两种碎片

不管用哪种分配器，碎片都躲不开。一种是**内部碎片**：你要 20 字节，分配器给了一个 32 字节的块，多出来的 12 字节谁也用不了。另一种是**外部碎片**：空闲内存加起来很多，可都是零零碎碎的小段，没有一段大到能放下你要的那块。

### 早期推理系统的 KV cache 浪费

一个请求最后会生成多少 token，开始时并不知道。早期系统的做法是按最大长度（比如 2048）给每个请求预留一整段连续的显存。

![](https://picx.zhimg.com/v2-24b533108fa689bebca13f232ed197e7_r.jpg)
*早期推理系统按最大长度给每个请求预留一整段连续的 KV cache：已生成的部分之后，是以后会用的预留部分和永远用不到的内部碎片；请求之间还有塞不下新请求的外部碎片*

大部分请求只有几百个 token，最大长度却是几千，预留的空间大半永远用不上，这是内部碎片。还没生成的那部分现在空着，也不能借给别人。请求结束后留下的空洞大小不一，新请求不一定塞得进去，这是外部碎片。vLLM 论文测了当时的几个系统，KV cache 里真正存了 token 的只有 20% 到 38%。

我写了个小模拟：显存能放 20 万个 token，请求长度大多几百、最长 2048，比较三种分配方式：

| 分配方式 | 显存里真正存了 token 的比例 | 平均同时在跑的请求 |
| --- | --- | --- |
| 按最大长度预留 | 18% | 97 |
| 按实际长度连续分配（假设事先知道长度） | 50% | 236 |
| 分页（每块 16 个 token，用到才分配） | 98% | 543 |

就算事先知道每个请求多长、按实际长度分配，外部碎片加上“预留了还没用上”，照样吃掉一半显存。分页把利用率推到 98%，同时在跑的请求是按最大长度预留时的 5 倍多。

这只是模拟，它假设 GPU 一步能处理任意多个请求，没算计算量的上限，也没算抢占后重算的开销。真实系统里，vLLM 论文报告的吞吐提升是 2 到 4 倍。

GPU 显存的分配器也是这一套。PyTorch 的 CUDA（NVIDIA 的 GPU 编程平台）缓存分配器把 1MB 以下和以上的请求分到两个池，从缓存的块里挑能放下的最小那块（最佳适配，best-fit），大了就切开用，本质上就是分离空闲链表。碎片多了，就会出现“显存明明还剩不少，却报显存不足（OOM）”。它的 `expandable_segments` 选项从源码看是借 CUDA 的虚拟内存接口来缓解这个问题，也就是下一节要讲的东西。

## 六、虚拟内存：PagedAttention 的原型

### 页表、TLB 和页大小

操作系统让每个进程以为自己独占一整片连续的地址空间。实际上这片地址被切成固定大小的**页**（x86 常见 4KB，我的 M4 是 16KB），每一页可以映射到物理内存里的任意位置，记录这些映射的表叫**页表**。

![](https://pic1.zhimg.com/v2-c5db916d8aa443a615f64d12d200b340_r.jpg)
*左边是操作系统：虚拟页通过页表映射到散在各处的物理页，TLB 缓存最近查过的页表项；右边是 vLLM：逻辑块通过 block table 映射到散在各处的 KV 块，由注意力 kernel 自己查表*

所有页一样大，任何一个空闲的物理页都能用，所以分页没有外部碎片；一个进程最多浪费最后一页里没用完的部分。页表还可以先建好，等第一次真正访问某一页时再分配物理页，这叫**按需分配**（demand paging）。

每次访问内存都先查一遍页表就太慢了，所以 CPU 里有一个专门缓存页表项的小缓存，叫 **TLB**（translation lookaside buffer，地址转换后备缓冲）。查表的活由 **MMU**（内存管理单元）这块硬件来做，程序完全感觉不到。

TLB 能装的条目有限，数据散在太多页上就装不下，每次访问都得多查一次页表。我做了个实验：读同样多的缓存行，一组挤在一起，一组每行单独占一个 16KB 的页，用随机顺序的指针追逐量出每次访问的延迟：

| 缓存行数 | 挤在一起 | 每行一个页 |
| --- | --- | --- |
| 256 | 0.76 ns | 4.2 ns |
| 2048 | 5.2 ns | 7.4 ns |
| 4096 及以上 | 5.4~7.0 ns | 14~15 ns |

数据量一样，散在更多的页上就慢了将近 3 倍，多出来的时间花在地址转换上。数据库、虚拟机这类吃内存的程序喜欢开**大页**（huge page，x86 上是 2MB 或 1GB），就是因为页大了，同样多的 TLB 条目能覆盖更多内存。代价是内部碎片也变大，一个只用了几 KB 的大页照样占着 2MB。

### PagedAttention：把 KV cache 当成虚拟内存管

vLLM 的 PagedAttention 几乎是把上面这套原样搬了过来。每个请求的 KV cache 切成固定大小的**块**（block），默认每块 16 个 token，对应页。每个请求有一张 **block table**，记着第几个逻辑块放在哪个物理块，对应页表。物理块可以散在显存任何地方，请求生成满一块再要下一块，对应按需分配。

效果也和操作系统一样：没有外部碎片，内部碎片只出现在每个请求的最后一块，平均浪费不到半块。vLLM 官方博客说浪费不到 4%。

块大小的取舍和页大小一样。块越小，最后一块浪费得越少；块越大，查表次数越少，GPU 一次读到的连续数据也越多。vLLM 论文试过几种块大小，最后选了 16。

和操作系统不同的是，block table 没有硬件帮忙。CPU 的页表由 MMU 查，程序感觉不到；vLLM 的 block table 只是一个普通数组，注意力 kernel 得自己查下一块在哪，再去读。论文承认这让注意力 kernel 比不分页的版本慢了 20% 到 26%。好在省下来的显存能多塞很多请求进一批，整体吞吐还是高出好几倍。

微软的 vAttention 换了个思路：要的既然是虚拟内存，干脆直接用 GPU 自己的。它通过 CUDA 的虚拟内存接口，先给每个请求预留一大段连续的虚拟地址，用到哪里再映射物理显存。注意力 kernel 看到的是连续的 KV cache，不用改，也不用查表。论文报告吞吐比基于 PagedAttention 的 FlashAttention-2 和 FlashInfer kernel 最多高 23%。

### 写时复制：fork 和并行采样

MIT 6.S081 课程用的教学操作系统 xv6 里，`uvmcopy` 在 `fork` 时把父进程的内存整份拷贝给子进程。课程里有个实验，就是把它改成**写时复制**（copy-on-write）：fork 时父子进程共享同一批物理页，都标成只读，谁先要写，才把那一页复制一份。大多数子进程 fork 完马上 `exec` 换成别的程序，根本不会写，这一改省掉了大量拷贝。

![](https://pic1.zhimg.com/v2-d7614e001a0b12751a25adec286d35ae_r.jpg)
*同一个提示词采样出两个回答，提示词对应的物理块两个回答共用，引用计数为 2；回答 2 要往共享的块里写自己的 token 时，才复制出一个新块，两块的引用计数都变成 1*

vLLM 的并行采样（一个提示词同时生成好几个回答）和 beam search 用的是同一个机制。几个回答共享提示词那几块 KV cache，每个物理块带一个**引用计数**，记着有几个请求在用。某个回答要往共享的块里写自己的 token，才把这一块复制一份。引用计数归零，块才真正释放。

### 前缀缓存：内容相同的块只存一份

很多请求的开头是一样的，比如同一段系统提示词、同一份文档，它们的 KV cache 也一样，没必要每个请求各算一遍。

vLLM 的自动前缀缓存给每个块算一个哈希，输入是这一块的 token 加上前一块的哈希，相当于对从开头到这一块的全部内容做了哈希。新请求进来先按哈希找现成的块，找到就直接引用。Linux 内核有个功能叫 KSM（内核同页合并），把内容完全相同的物理页合并成一份，思路一样。

显存不够时，引用计数为 0 的块按 **LRU**（最近最少使用）淘汰，操作系统换出物理页也常用这个策略。SGLang 的 RadixAttention 把所有请求的 KV cache 组织成一棵基数树（radix tree），同样按 LRU 淘汰，论文报告吞吐最多高 6.4 倍。

### 换出还是重算

显存满了，又有新块要分配，就只能把某个请求踢出去。操作系统的做法是把页换出到磁盘（swap），用到时再换回来。vLLM 论文实现了两种：把这个请求的 KV cache 换出到 CPU 内存，或者直接扔掉，以后重新做一遍 prefill 算回来。哪种划算，要看 PCIe 有多慢、重算有多贵。新版 vLLM（V1）已经不做换出了，被抢占的请求一律重算。

同样叫“抢占”，CPU 进程和推理请求要搬走的东西差了几个数量级：

|  | CPU 进程切换 | GPU 整体抢占 | vLLM 抢占一个请求 |
| --- | --- | --- | --- |
| 要保存的状态 | 寄存器，几 KB | 寄存器堆和共享内存，几十 MB | KV cache，几百 MB 到几 GB |
| 什么时候切 | 随时（时钟中断） | 指令级，代价大 | 只在两步 decode 之间 |
| 怎么恢复 | 恢复寄存器 | 恢复寄存器堆 | 重算（V1）或换入 |

CPU 进程的上下文就是几 KB 的寄存器，存起来几微秒的事。一个大模型请求的上下文是它的整份 KV cache，所以 vLLM 从来不在 kernel 跑到一半时打断谁，只在两步 decode 之间重新决定这一轮带哪些请求。

### 内核态和用户态的开销

虚拟内存还把地址空间分成两半，内核空间和用户空间，用户程序碰不到内核那一半。程序要读写文件、收发网络数据，得通过**系统调用**进入内核态，切换一次的开销比一次普通函数调用大得多。

GPU 上有两处类似的开销。

- **启动 kernel 要经过驱动**。每启动一个 GPU kernel，CPU 都要走一遍驱动去提交，要几微秒。decode 一步要启动几百个小 kernel，加起来很可观。**CUDA Graphs** 把一串 kernel 录下来，之后整串一次提交，省掉每个 kernel 单独走驱动的开销，vLLM 默认也会用它。
- **从普通内存往显存拷数据要多拷一次**。GPU 用 DMA（直接内存访问，不经过 CPU，按物理地址直接读写内存）搬数据，那块内存必须一直待在物理内存里，不能被换出，也不能挪位置。普通的可分页内存做不到这一点，驱动只好先把数据拷到一块**锁页内存**（pinned memory）中转，再传给 GPU。所以要把 KV cache 卸载到 CPU 内存，通常也会用锁页内存。

加载模型权重也离不开虚拟内存。safetensors 和 llama.cpp 默认用 `mmap` 把权重文件映射进地址空间，借按需分页做到用到哪页才读哪页，几十 GB 的模型不用先整个读进内存。

## 七、调度：让 GPU 一直有活干

### 连续批处理

decode 要攒批才能用满算力。最早的做法是静态批处理：凑够一批一起跑，最长的那个请求生成完，整批才算结束。

![](https://pic1.zhimg.com/v2-5773451f2ce32e9574d7475a7195a93c_r.jpg)
*静态批处理时一批里短的请求做完后只能空等最长的那个，新请求要排到整批结束之后；连续批处理每生成一个 token 就重新组一次批，做完的立刻换上新请求，GPU 一直是满的*

一批里有一个请求要生成 2000 个 token，其他只要 50 个的也得陪着等。2022 年的 Orca 提出了**迭代级调度**：每生成一个 token（一次迭代）就重新组一次批，做完的立刻退出，新请求马上补上，现在一般叫**连续批处理**（continuous batching）。论文在 GPT-3 175B 上报告吞吐是 FasterTransformer 的 36.9 倍。

操作系统里对应的是分时调度。早期的批处理系统一个作业跑完才换下一个；分时系统把 CPU 时间切成时间片，每个时间片结束都重新决定下一个跑谁。decode 的一步，就相当于推理服务的一个时间片。

### 别让长任务霸占 GPU

衡量推理服务的两个核心指标是 **TTFT**（首 token 延迟，从发出请求到看见第一个字）和 **TPOT**（每个输出 token 的延迟，决定字往外蹦得多快）。

一个几万 token 的长提示词进来，它的 prefill 要算很久。一口气算完的话，同一批里正在 decode 的请求全得停下来等，TPOT 一下子变差。Sarathi-Serve 的做法叫 **chunked prefill**，把长 prefill 切成小段，每一步只做一段，和别的请求的 decode 拼在同一批里跑，和操作系统不让一个长任务霸占 CPU 是一个道理。

更进一步的做法是 **prefill/decode 分离**（PD 分离）。prefill 卡在算力上，decode 卡在带宽上，两种负载放在同一张卡上会互相干扰，索性分到不同的机器上，各按各的瓶颈优化。DistServe 论文报告，在同样的延迟要求下能多服务 7.4 倍的请求。

### 公平，以及 CPU 成了新瓶颈

调度还得管公平。Linux 用了十几年的 CFS 调度器，按谁用的 CPU 时间少就先让谁跑来保证公平，6.6 版内核换成了 EEVDF，思路相近。多租户的推理服务也有这个问题：一个用户拼命发长请求，不能把别人都挤掉。OSDI 2024 的 VTC 论文借了公平队列的思想，按每个用户已经消耗的 token 数来调度。

**阿姆达尔定律**说的是：只优化一部分，整体提速有上限，没优化的那部分迟早成为瓶颈。GPU kernel 越来越快，H100 上跑 Llama-8B 一步 decode 只要 5 毫秒左右，Python 写的调度、准备输入这些 CPU 开销就藏不住了。这是 vLLM 重写 V1 架构的动机之一：调度挪进独立的进程，每一步只更新输入里变了的部分；现在默认开启的异步调度，让 CPU 准备下一步的同时 GPU 执行这一步，用的还是流水线那一套。

| 流水线、计算和传输重叠 | 异步调度、CUDA Graphs |
| 局部性、缓存分块、循环融合 | FlashAttention、算子融合 |
| 合并访存、对齐 | 张量维度凑 64 的倍数 |
| 数据表示 | 权重量化、KV cache 量化 |
| 内部/外部碎片、空闲链表 | KV cache 预留浪费、PyTorch 显存分配器 |
| 分页、页表、按需分配 | PagedAttention、block table |
| 写时复制、引用计数 | 并行采样、beam search 共享 KV |
| 同页合并、LRU 置换 | 前缀缓存、RadixAttention |
| 换出 | KV cache 换出或重算 |
| 分时调度、抢占 | 连续批处理、chunked prefill |
| 公平调度 | 多租户公平调度（VTC） |
| 虚拟内存（真正用硬件） | vAttention |

实验里的数字：同样的逻辑，循环顺序能差 13 到 50 倍，分支猜不准差 10 倍，伪共享差 16 倍，链表和数组差近 400 倍，数据散在太多页上差 3 倍。

大模型推理面对的约束和几十年前一样：算得快、搬得慢，内存有限，请求长短不定。看到一个新的推理优化时，可以先找找它在操作系统或 CPU 里对应的是什么。
