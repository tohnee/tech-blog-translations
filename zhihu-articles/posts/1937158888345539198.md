剥除掉一切抽象，本质来说，RDMA：Remote Direct Memory Access

**DMA：**在本地复制内存的过程是通过CPU主导，将内存复制到CPU寄存器中，再复制到IO设备。CPU最主要的任务是计算而不是复制，这样的大量的数据复制占据了CPU，让他不能做自己该做的事情。后面提出了一种新的设备——DMA控制器，专门负责内存复制工作。CPU把内存复制的任务告诉DMA控制器，之后CPU就可以自己忙别的去了。

![](https://pic1.zhimg.com/v2-3ac11a80ebafbf40cd203911bc9a8276_r.jpg)

**RDMA（ Remote Direct Memory Access ）**意为远程直接地址访问，通过RDMA，本端节点可以“直接”访问远端节点的内存。所谓直接，指的是可以像访问本地内存一样，绕过传统以太网复杂的TCP/IP网络协议栈读写远端内存，而这个过程对端是不感知的，而且这个读写过程的大部分工作是由硬件（RDMA网卡）而不是软件完成的。

![](https://pic4.zhimg.com/v2-aa1592f365a8e6bf118ba157392f7371_r.jpg)

**RDMA的优势：**

1. 0拷贝：指的是不需要在用户空间和内核空间中来回复制数据。

由于Linux等操作系统将内存划分为**用户空间和内核空间**，在传统的Socket通信流程中CPU需要**多次把数据在内存中来回拷贝**。而通过RDMA技术，我们可以直接访问远端已经注册的内存区域。

2. 内核Bypass：指的是IO（数据）流程可以**绕过内核**，即**在用户层就可以把数据准备好并通知硬件准备发送和接收**。避免了系统调用和上下文切换的开销。

上图（原图[[1]](https://pc.nanog.org/static/published/meetings/NANOG76/1999/20190612_Cardona_Towards_Hyperscale_High_v1.pdf)）可以很好的解释“0拷贝”和“内核Bypass”的含义。上下两部分分别是基于Socket的和基于RDMA的一次收-发流程，左右分别为两个节点。可以明显的看到Socket流程中在软件中**多了一次拷贝动作**。

RDMA绕过了内核同时也减少了内存拷贝，数据可以直接在用户层和硬件间传递。

**RDMA有若干种实现**，（我认为）主要有两种：

1. InfiniBand 来自于以色列公司Mellanox，需要专属网卡和交换机，比较贵
2. RoCEv2，RDMA over Converged Ethernet，可以在已有的以太网设备上改造，性能比IB差一点

### 核心循环

client和server端的这部分代码是main中的核心循环，从这里入手可以获得对rdma双端的整体认知

```text
while (rdma_get_cm_event(ec, &event) == 0) {
    struct rdma_cm_event event_copy;

    memcpy(&event_copy, event, sizeof(*event));
    rdma_ack_cm_event(event);

    if (on_event(&event_copy))
      break;
  }
```

**功能**：从事件通道获取RDMA连接管理事件

- **阻塞特性**：如果没有事件，线程会阻塞等待
- **返回值**：成功返回0，失败返回非0（循环退出）
- **事件类型**：连接请求、连接建立、断开连接等

```text
int on_event(struct rdma_cm_event *event)
{
  int r = 0;

  if (event->event == RDMA_CM_EVENT_CONNECT_REQUEST)
    r = on_connect_request(event->id);
  else if (event->event == RDMA_CM_EVENT_ESTABLISHED)
    r = on_connection(event->id);
  else if (event->event == RDMA_CM_EVENT_DISCONNECTED)
    r = on_disconnect(event->id);
  else
    die("on_event: unknown event.");

  return r;
}
```

**Server端可能收到的事件**：

- `RDMA_CM_EVENT_CONNECT_REQUEST` - 客户端连接请求
- `RDMA_CM_EVENT_ESTABLISHED` - 连接建立成功
- `RDMA_CM_EVENT_DISCONNECTED` - 连接断开

```text
int on_event(struct rdma_cm_event *event)
{
  int r = 0;

  // client作为主动发起链接的一方，始终需要承担解析地址和router的任务
  if (event->event == RDMA_CM_EVENT_ADDR_RESOLVED)
    r = on_addr_resolved(event->id);
  else if (event->event == RDMA_CM_EVENT_ROUTE_RESOLVED)
    r = on_route_resolved(event->id);
  else if (event->event == RDMA_CM_EVENT_ESTABLISHED)
    r = on_connection(event->id);
  else if (event->event == RDMA_CM_EVENT_DISCONNECTED)
    r = on_disconnect(event->id);
  else
    die("on_event: unknown event.");

  return r;
}
```

**Client端可能收到的事件**：

- `RDMA_CM_EVENT_ADDR_RESOLVED` - 地址解析成功
- `RDMA_CM_EVENT_ROUTE_RESOLVED` - 路由解析成功
- `RDMA_CM_EVENT_ESTABLISHED` - 连接建立成功
- `RDMA_CM_EVENT_DISCONNECTED` - 连接断开

在收到不同的事件之后，会调用不同的函数比如on_addr_resolved on_route_resolved 等，进行不同的后处理

## 单边接口和双边接口的区别

即使我们知道了，所谓单边接口（write/read）指的是不需要对端cpu参与的通信，而双边接口是需要对端cpu提前准备好本次接收buffer在本地的dst地址。

那么具体它们在代码上有什么不同呢？

### opcode不同

直观的看，单边调用的是`wr.opcode = (s_mode == M_WRITE) ? IBV_WR_RDMA_WRITE : IBV_WR_RDMA_READ;` 而双边的opcode是不带rdma标识的：`wr.opcode = IBV_WR_SEND;`

### 是否需要事先交换rkey？

[6. RDMA之Memory Region](https://zhuanlan.zhihu.com/p/156975042)

> MR全称为Memory Region，指的是由RDMA软件层在内存中规划出的一片区域，用于存放收发的数据。IB协议中，用户在申请完用于存放数据的内存区域之后，都需要通过调用IB框架提供的API注册MR，才能让RDMA网卡访问这片内存区域。<br> <br> 而用户注册MR的动作会产生两把钥匙——lkey（Local Key）和 rkey（Remote Key），说是钥匙，它们的实体其实就是一串序列而已。它们将分别用于保障对于本端和远端内存区域的访问权限。<br>

在注册mr的时候都会产生一个lkey和一个rkey

lkey代表对local mem的访问权限

对于单边来说，只有lkey需要交换

```text
// send_message()中的SEND操作
sge.addr = (uintptr_t)conn->send_msg;     // 网卡需要从这个地址读取数据
sge.lkey = conn->send_mr->lkey;           // 验证网卡是否有权限读取这块内存
wr.opcode = IBV_WR_SEND;         // 双边操作

// post_receives()中的RECV操作
sge.addr = (uintptr_t)conn->recv_msg;     // 网卡需要向这个地址写入数据
sge.lkey = conn->recv_mr->lkey;           // 验证网卡是否有权限写入这块内存
TEST_NZ(ibv_post_recv(conn->qp, &wr, &bad_wr));
```

而对于双边来说

**Step 1 - 注册产生双key：**

```text
ibv_reg_mr() → 产生 {lkey, rkey}
// lkey: 本地访问权限
// rkey: 授权给远程的访问权限
```

**Step 2 - 发送rkey给对方：**

```text
send_mr() {
    // 发送包含rkey的完整MR信息
    memcpy(&conn->send_msg->data.mr, conn->rdma_remote_mr, sizeof(struct ibv_mr));
}
```

**Step 3 - 接收并使用对方的rkey：**

```text
// 接收对方的MR信息（包含对方的rkey）
memcpy(&conn->peer_mr, &conn->recv_msg->data.mr, sizeof(conn->peer_mr));

// 使用对方的rkey访问对方内存
wr.wr.rdma.rkey = conn->peer_mr.rkey;
```

### 是否需要提前post_recv？

什么是post_recv？

先看代码：

```text
// send-receive
void post_receives(struct connection *conn)
{
  struct ibv_recv_wr wr, *bad_wr = NULL;
  struct ibv_sge sge;

  wr.wr_id = (uintptr_t)conn;
  wr.next = NULL;
  wr.sg_list = &sge;
  wr.num_sge = 1;

  sge.addr = (uintptr_t)conn->recv_region;
  sge.length = BUFFER_SIZE;
  sge.lkey = conn->recv_mr->lkey;

  TEST_NZ(ibv_post_recv(conn->qp, &wr, &bad_wr));
}
```

post_receives指的是软件APP向硬件下发一条任务

我们先说WQE：

WQE可以认为是一种“任务说明”，这个工作请求是软件下发给硬件的，这份说明中包含了软件所希望硬件去做的任务以及有关这个任务的详细信息。比如，某一份任务是这样的：“我想把位于地址0x12345678的长度为10字节的数据发送给对面的节点”，硬件接到任务之后，就会通过DMA去内存中取数据，组装数据包，然后发送。

那什么是post？

WQ这个队列总是由软件向其中增加WQE（入队），硬件从中取出WQE，这就是软件给硬件“下发任务”的过程。为什么用队列而不是栈？因为进行“存”和“取“操作的分别是软件和硬件，并且需要保证用户的请求**按照顺序被处理**在RDMA技术中，所有的通信请求都要按照上图这种方式**告知硬件**，这种方式常被称为“Post”。

![](https://picx.zhimg.com/v2-0a066c043fb53bca0ec9c0324f66cd0d_r.jpg)

对于APP侧，wr wc

对于RDMA-engine：WQE、CQE

都是一个东西，只是不同阶段的名字不一样

[3. RDMA基本元素](https://zhuanlan.zhihu.com/p/141267386)

**那么这和鉴别单边双边接口有什么关系呢？**

从定义来说，单边接口就是接收方不需要提前使用cpu安排接收buffer应该存储的地址，往小了说是地址，往大了说就是不需要安排这次接受任务。自然也就是没有post receive

但是事实上，单边接口需要提供目的地址和rkey：

> 本端在准备阶段通过数据交互，获取了对端某一片可用的内存的**地址**和“**钥匙**”，相当于获得了这片远端内存的读写权限。拿到权限之后，本端就可以像访问自己的内存一样**直接对这一远端内存区域进行读写**，这也是RDMA——远程直接地址访问的内涵所在。<br> <br> WRITE/READ操作中的**目的地址和钥匙是如何获取的呢?**通常可以通过我们刚刚讲过的SEND-RECV操作来完成，因为拿到钥匙这个过程总归是要由远端内存的控制者——CPU允许的。虽然准备工作还比较复杂， 但是一旦完成准备工作，RDMA就可以发挥其优势，对大量数据进行读写。一旦远端的CPU把内存授权给本端使用，它便不再会参与数据收发的过程，这就解放了远端CPU，也降低了通信的时延。<br>

```text
// 发送方将自己的rdma_remote_mr（包含dst_addr和rkey）发送给对方
memcpy(&conn->send_msg->data.mr, conn->rdma_remote_mr, sizeof(struct ibv_mr));
// 接收方将recvmsg中的data.mr复制到peer_mr
memcpy(&conn->peer_mr, &conn->recv_msg->data.mr, sizeof(conn->peer_mr));
// 填写wr的时候，wr.rdma填写addr+rkey
wr.wr.rdma.remote_addr = (uintptr_t)conn->peer_mr.addr;       
wr.wr.rdma.rkey = conn->peer_mr.rkey;
```

## 内存生命周期

### **阶段一：内存分配和注册**

```text
// 1. CPU分配内存
conn->send_msg = malloc(sizeof(struct message));
conn->recv_msg = malloc(sizeof(struct message));
conn->rdma_local_region = malloc(RDMA_BUFFER_SIZE);
conn->rdma_remote_region = malloc(RDMA_BUFFER_SIZE);

// 2. 向RDMA子系统注册内存，产生访问权限
conn->send_mr = ibv_reg_mr(s_ctx->pd, conn->send_msg, size, IBV_ACCESS_LOCAL_WRITE);
conn->recv_mr = ibv_reg_mr(s_ctx->pd, conn->recv_msg, size, IBV_ACCESS_LOCAL_WRITE);
// 注册后产生：{lkey, rkey} 权限对
```

### **阶段二：双边消息传输流程**

**发送方（SEND）**：

```text
// 1. CPU准备发送数据
conn->send_msg->type = MSG_MR;
memcpy(&conn->send_msg->data.mr, conn->rdma_remote_mr, sizeof(struct ibv_mr));

// 2. 构造发送请求
sge.addr = (uintptr_t)conn->send_msg;    // 告诉网卡从哪里读数据
sge.lkey = conn->send_mr->lkey;          // 给网卡读取权限

// 3. 网卡执行
ibv_post_send() → 网卡从send_msg读取数据 → 通过网络发送
```

**接收方（RECV）**：

```text
// 1. CPU预先准备接收缓冲区
sge.addr = (uintptr_t)conn->recv_msg;    // 告诉网卡往哪里写数据
sge.lkey = conn->recv_mr->lkey;          // 给网卡写入权限

// 2. 网卡执行
ibv_post_recv() → 网卡从网络接收数据 → 写入recv_msg → 通知CPU
```

### **阶段三：单边数据传输流程**

**RDMA WRITE操作**：

```text
// 1. 本地内存访问（读取数据源）
sge.addr = (uintptr_t)conn->rdma_local_region;   // 网卡从这里读取要写入的数据
sge.lkey = conn->rdma_local_mr->lkey;            // 本地读取权限

// 2. 远程内存访问（写入目标）
wr.wr.rdma.remote_addr = (uintptr_t)conn->peer_mr.addr;  // 远程目标地址
wr.wr.rdma.rkey = conn->peer_mr.rkey;                    // 远程写入权限

// 3. 网卡执行
网卡从本地rdma_local_region读取数据 → 直接写入远程rdma_remote_region
```

### **推测的内存访问权限硬件验证机制**

**本地权限验证：**

```text
// 网卡内部验证逻辑（伪代码）
if (sge.lkey == registered_mr.lkey &&
    sge.addr >= registered_mr.addr &&
    sge.addr + sge.length <= registered_mr.addr + registered_mr.length) {
    // 权限验证通过，允许访问
    perform_memory_access();
} else {
    // 权限验证失败，拒绝访问
    return_error();
}
```

**远程权限验证：**

```text
// 远程网卡验证逻辑（伪代码）
if (wr.wr.rdma.rkey == remote_registered_mr.lkey &&
    remote_addr >= remote_registered_mr.addr &&
    remote_addr + length <= remote_registered_mr.addr + remote_registered_mr.length) {
    // 远程权限验证通过
    allow_remote_access();
}
```
