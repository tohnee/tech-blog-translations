## TL; DR[^1]

如果你在用 Rust 写 RDMA 代码，并且已经被这些事情折磨到开始怀疑人生：

- 在 `ibverbs-sys` / `rdma-core-sys` 上面手搓 FFI
- 为了 CQ / QP / MR 的所有权和生命周期，和 borrow checker 搏斗
- 为了链接一个小小的二进制，就得整个把 `rdma-core` 重编一遍

那么 **[sideway](https://github.com/RDMA-Rust/sideway)**会给你

- Rust 口味的现代 ibverbs 封装（`ibv_wr_*`、`ibv_start_poll`、CQ EX / QP EX）
- 一个基于 `dlopen` 的静态库，你不需要把 rdma-core 整个 vendor 进项目
- 一个「够用就行」的 `librdmacm` 封装

代码在这儿：[https://github.com/RDMA-Rust/sideway](https://github.com/RDMA-Rust/sideway)<br>文档在这儿：[https://docs.rs/sideway/latest/sideway/](https://docs.rs/sideway/latest/sideway/)

这篇文章主要讲：我们是怎么做的、做了哪些取舍、以及过程中踩了哪些坑

## 我们到底搞到了啥？

1. 一个 Rust 口味的 rdma-core 封装（实测可以打满 400 Gbps RNIC）
2. 两个已经合并到 rdma-core upstream 的 bug 修复
3. 一个给 C/C++ 程序员也能用的静态库，暴露 `libibverbs` / `librdmacm`（rdma-core-mummy）
4. 一堆 Rust + RDMA 的实战经验

## 现在这些封装到底哪儿不爽？

大多数 `libibverbs` / `librdmacm` 的 Rust 封装，更多关注「语言特性」：<br><br>比如 100% safe、async-first API 等等，而没那么关注「能不能真上生产」，它们非常适合探索学习，我们的实现也参考了很多，但当你想写一个跑得足够快的 RDMA 应用时，总会觉得哪里怪怪的

真开始写业务的时候，往往会变成：

- 最后还是要调用到 `ibverbs-sys`（或者别的 bindgen crate）
- 一边使用 C 类型，一边使用 Rust 类型

更麻烦的是：<br>很多 crate 默认你要把整个 rdma-core 项目编出来，再静态/动态链接进去；或者要求**编译机器**上已经安装好了 rdma-core。

这会引入一堆不必要的依赖和构建复杂度

我们想要的是这样的封装：

- 让 **control path** 在 Rust 里用起来符合人体工学
- 让 **data path** 尽量贴近原生 `ibverbs`，保证性能没问题
- 不需要每个项目都 vendor 一整套 rdma-core 进来

## sideway 跟其他 crate 比咋样？

我们完全没有打算取代谁——不同项目有不同的 trade-off。但如果你目标是**高性能、同步的 RDMA**，有些坑是很容易踩到的

| Crate | 需要构建 rdma-core | 封装了 librdmacm | 性能问题 |
| --- | --- | --- | --- |
| ibverbs | 是 | 否 | 1. 以固定大小 Poll CQ<br>2. 不支持 Batch Post Send<br>3. 无法指定 Send Flags |
| rrddmma | 可选 | 否 | 用户决定各类参数 |
| async-rdma | 否（但要求特定版本） | 是 | 1. 不支持 Batch Post Send<br>2. 无法指定 Send Flags |
| rdma | 否（但要求特定版本） | 否 | 用户决定各类参数 |
| rdma-rs | 是 | 是 | 1. 不支持 Batch Post Send<br>2. 无法指定 Send Flags |
| Sideway | 否 | 是 | 关注新的 ibverbs API (ibv_wr_*, CQ / QP Ex)<br>用户决定各类参数 |

## 设计：分层抽象

我们把 RDMA 的抽象拆成了几层来做：

![](https://pica.zhimg.com/v2-4bee81aa106c62f907fd907f29c58888_r.jpg)

### `rdma-mummy-sys` 最底层 rdma-core API 封装

第一层是一个「bindgen 生成 + 人肉修补」的 rdma-core 封装（实际链接的是 `rdma-core-mummy`，后面讲 `dlopen` 时会说）

它的角色是：

- 所有上层的基础
- 提供一个「尽可能接近 C API」的接口，给那些想直接操作 C API 的用户用

### `Sideway` Rust 风格的 rdma-core 封装

第二层是 sideway，本质上是一个「更现代、更 Rust 一点的 rdma-core 封装」，它会做这些事情：

- 把 C 宏和匿名枚举重新封装成 Rust 的 enum
- 用 builder pattern 把各种创建/配置 API 变得顺手
- 提供迭代器式的 CQ 轮询接口

这种 iterator 风格在一些项目里比 `ibv_poll_cq` 要快，而且能暴露更多信息，比如从 CQE 里直接拿硬件时间戳

我们**刻意没有**把所有东西都做成 safe：

- `ibv_reg_mr`、`ibv_post_send` / `ibv_wr_*` 相关封装依然是 `unsafe`
- 如果在这一层强行完全编码它们的安全性，要么：

我们的思路是：

- sideway 提供一个清晰、零开销的「现代 verbs 映射」
- 上层（比如 `trespass` 或你自己的库）再自己构建 safe 的内存池、连接抽象等

在用户体验上，我们还提供了 CQ / CQ Ex、QP / QP Ex 的统一接口。如果你写过 RDMA，那肯定知道 `ibv_post_send` 和 `ibv_poll_cq`，但未必用过 `ibv_wr_*` 和 `ibv_start_poll`，这些新 API 效率更高，也能拿到硬件时间戳。sideway 的目标是：

> 让你可以从「经典写法」平滑迁移到扩展 API，而不用大改代码结构

下面对比一下传统的 `ibv_post_send`、`ibv_wr_*` 和 sideway 的写法：

`ibv_post_send`

```c
struct ibv_send_wr wr;

struct ibv_sge sge = {
    .addr = local_addr,
    .length = 4096,
    .lkey = lkey,
};

wr.wr_id = 233;
wr.next = NULL;
wr.sg_list = &sge;
wr.num_sge = 1;
wr.opcode = IBV_WR_RDMA_WRITE;
wr.send_flags = IBV_SEND_SIGNALED;
wr.wr.rdma.remote_addr = remote_addr;
wr.wr.rdma.rkey = rkey;

// Before actual post, you could construct more WRs use `next` to chain them,
// which could increase performance
int ret = ibv_post_send(qp, &wr, NULL); 
```

`ibv_wr_*`

```c
ibv_wr_start(qp);

qp->wr_id = 233;
qp->wr_flags = IBV_SEND_SIGNALED;
ibv_wr_rdma_write(qp, rkey, remote_addr);

ibv_wr_set_sge(qp, lkey, local_addr, 4096);

// Before actual post, you could construct more WRs and then post them at once,
// which could increase performance
ibv_wr_complete(qp); 
```

再对比一下 `ibv_poll_cq` 和 `ibv_start_poll` 还有 sideway：

`ibv_poll_cq` 看起来很清爽，但不支持硬件时间戳；同时为了把 CQ 内容 copy 到 `ibv_wc`，还要多一点开销。

```c
struct ibv_wc wc;

while (ibv_poll_cq(cq, 1, &wc) > 0) {
    printf("wr_id: %lu, status: %u, opcode: %u\n", wc.wr_id, wc.status, wc.opcode);
} 
```

`ibv_start_poll`

```c
int ret = ibv_start_poll(cq, &attr);
// assume the first ret is not ENOENT
while (ret != ENOENT) {
    printf("wr_id: %lu, status: %u, opcode: %u\n", cq->wr_id, cq->status, ibv_wc_read_opcode(cq));
    ret = ibv_next_poll(cq);
}
ibv_end_poll(cq);
```

sideway

```rust
 match cq.start_poll() {
    Ok(mut poller) => {
        while let Some(wc) = poller.next() {
            println!("wr_id: {}, status: {}, opcode: {}", wc.wr_id(), wc.status(), wc.opcode())
        }
    }
    Err(_) => {
        continue;
    }
}

```

此外，我们还在 RDMA **控制路径**上狠狠加了一层可观测性：<br> 不再是「modify_qp 返回 `-EINVAL`，剩下全凭你猜」，而是尽量：

- 告诉你**哪一个属性**不合法
- 把内核的特定错误（比如 `ETIMEDOUT`）包装成有语义的 Rust 错误类型，方便监控和排查<br>
- 解析路由失败时，也会把 GID / sgid_index 打出来，配合 `show_gids` 一看就懂哪边地址搞错了，而不是只给你一个「Connection timed out」。

### `Trepass` 类 socket 通信库（WIP）

第三层是 `trespass`，一个类 socket 的 RDMA 通信库，你可以把它想象成：

- 和 UCX / `libfabric` 同一类型
- 但**刻意做得更简单、更聚焦**

它的目标是：

- 把 RDMA 使用中的细节都挡在后面，比如：
- 让用户可以**直接复用 socket 编程的经验**（不管是 C / C++ / Rust），上手成本降到最低

### RPC 框架?

最顶层——一套以 RDMA 为传输层的 RPC 框架——是我们**刻意暂时不碰**的

原因也很简单：不同应用差得太多了：

- 存储系统
- 重 RPC 的微服务
- 大模型推理服务

我们更希望先把下层这几块打磨好（rdma-mummy-sys / sideway / trespass），然后让别人基于这些砖块去造 RPC 大厦

### 那 async 呢？

你可能会问：

> 这是 Rust 啊，async 呢？

我们的看法是：

- RDMA 本身就是异步的
- 控制路径（创建 QP / 改状态 / 注册 MR）通常不是性能瓶颈
- 直接把 verbs「硬焊」到今天主流的 async runtime（尤其是 Tokio）上，其实挺别扭的

我们认为，对高性能 RDMA 来说，thread-per-core 式的 runtime 可能更靠谱，sideway 的设计也是朝这个方向留了空间：

- 每个核跑一个专用 RDMA worker 线程
- 和系统其他部分通过 channel 通信
- verbs 的使用尽量简单

未来我们也许会往这方面尝试，但 sideway 本身刻意保持为同步接口

## `dlopen` 的魔法

由于历史原因，`libibverbs` 以及某些 provider 用了一套比较烦人的「私有符号机制」：[https://github.com/linux-rdma/rdma-core/blob/master/Documentation/versioning.md](https://github.com/linux-rdma/rdma-core/blob/master/Documentation/versioning.md)

它的初衷是好的：

> 确保发布出去的二进制，运行时链接的 rdma-core 版本，和编译时的是同一个

现实结果就是：

> 你很难做一个「一个 binary 到处分发」的程序，就算你根本没用到那些 private symbol，也会被拖下水

为了解决这个问题，我们提供了一个静态库 **rdma-core-mummy**，它会：

- 在运行时用 `dlopen` 把 `libibverbs` 和 `librdmacm` 拉进来（DCN 里常用的基本就这俩）
- 应用程序只需要链接我们的静态库，而不需要直接链接整个 rdma-core

你可能会说：

> 那为啥不直接在 Rust 里用 `libloading` 呢？

因为我们也想让**C/C++ 开发者**也能享受这套 `dlopen` 带来的好处。所以干脆做成一个通用的静态库，大家都能用

## Lifetime，还是不用 lifetime，这是个问题

RDMA 的资源之间是有依赖拓扑的，参考 [如何在 Rust 中写 RDMA](https://zhuanlan.zhihu.com/p/524967763) 中的依赖图

直觉上，Rust 的生命周期系统看起来是非常自然的解法：

- 在类型系统里表达资源之间的依赖关系
- 在编译期就把错误用法卡掉

我们一开始也是这么干的（v0.4.0 之前的版本）

但当我们尝试把 CQ、QP、MR 等封装进一个 `WorkerContext`（C/C++ 里常见的用法）时，lifetime 很快变成了一场灾难：

- 类型变得又长又绕，读起来特别费劲
- 到处得用 `ouroboros` 之类的模式安抚 borrow checker
- 很多概念上「显然安全」的用法，编译器就是不干

当「安全」从帮你变成拦着你干正事的时候，我们觉得该踩刹车了。

于是我们选了一个更简单直接的模型：

> 大多数资源用 **`Arc`** 来管理。

- 用户不用再天天纠结 lifetime 如何标
- 资源之间的释放顺序依然是正确的
- 引用计数的开销不会出现在数据路径上（hot path 上还是写 WR / poll CQ）

在 stride 里这个变化很明显：

使用 `Arc` 前：[https://github.com/RDMA-Rust/stride/commit/c5a6a0c83973bd187f1f4ac57a07942d8d278e23](https://github.com/RDMA-Rust/stride/commit/c5a6a0c83973bd187f1f4ac57a07942d8d278e23)

```rust
pub struct WorkerContext<'a> {
    pub queue_pairs: Vec<GenericQueuePair<'a>>,
    pub send_completion_queue: Rc<RefCell<ExtendedCompletionQueue<'a>>>,
    pub recv_completion_queue: Option<Rc<RefCell<ExtendedCompletionQueue<'a>>>>,
    ...
}

```

使用 `Arc` 后：[https://github.com/RDMA-Rust/stride/commit/fd30aeb4b5b5fa27ee89d1877670058021d670e3](https://github.com/RDMA-Rust/stride/commit/fd30aeb4b5b5fa27ee89d1877670058021d670e3)

```rust
pub struct WorkerContext {
    pub queue_pairs: Vec<GenericQueuePair>,
    pub send_completion_queue: GenericCompletionQueue,
    pub recv_completion_queue: Option<GenericCompletionQueue>,
    ...
}

```

对比一下结构体就知道读起来舒服多了，也更接近真实系统里的 RDMA 资源管理方式

## Rust 的测试框架 & 给 upstream 打补丁

为了让 sideway 不至于能跑 demo，跑不了生产，我们用上了 Rust 自带的测试框架：

- 一部分单测可以在没有 RNIC 的环境下跑
- CI 里尽可能在 SoftRoCE 上跑 E2E

在这个过程中，我们顺带发现了 **rdma-core 里的两个 bug，并提了 PR 修复**

### SoftRoCE (RXE) CQ bug

我们在把 `ibv_rc_pingpong` 移植到 sideway 的时候，发现在 Mellanox NIC 上跑得好好的，一换 SoftRoCE 就开始抽风：我们不断从 CQ 里 poll 到 `wr_id == 0` 的 CQE

一开始我们还以为是自己实现问题，于是用 `bpftrace` 直接打到内核里看[^3]

用如下命令测试

```text
cargo run --example rc_pingpong_split -- -d rxe_0 -g 1 -n 1 &

cargo run --example rc_pingpong_split -- -d rxe_0 -g 1 127.0.0.1 -n 1
```

Bpftrace 输出

```text
$ sudo bpftrace ./rxe_qp_tracer.bt
Attaching 5 probes...
rxe_requester: valid: 0, state: 3
rxe_requester: max_wr: 1, max_sge: 8, index: 1
rxe_requester: return: -11
rxe_completer: valid: 0, state: 3
rxe_completer: max_wr: 1, max_sge: 8, index: 1
rxe_completer: return: -11
rxe_requester: valid: 1, state: 3
rxe_requester: max_wr: 1, max_sge: 8, index: 0
rxe_xmit_packet: return 0
rxe_requester: return: 0
...
rxe_completer: valid: 0, state: 6
rxe_completer: max_wr: 1, max_sge: 8, index: 1
rxe_completer: return: -11
^C
```

结果发现：

- `rxe_completer` 只跑了有限几轮
- 内核侧报告的 completion 数其实是对的

于是我们把火力转移到用户态 driver，经过一顿 debug + code review，终于定位到了原因，并提了修复：

[rxe: fix completion queue consumer index overrun #1512](https://github.com/linux-rdma/rdma-core/pull/1512)

也把端到端测试加到了 CI：[E2E rc_pingpong test](https://github.com/RDMA-Rust/sideway/blob/5311a8e5a4bfbfd3530c085040a19009cdf927d6/.cirrus.yml#L29)

### 设备探测问题

另一个 bug 是重启之后冒出来的：某个测试突然失败了，唯一的区别是：SoftRoCE 还没配置好。理论上机器上还有 Mellanox 的 VF，所以测试**应该**能跑。但 rdma-core 在 rdmacm 初始化逻辑上有点问题。

最后变成了这个 PR：[librdmacm: prevent NULL pointer access during device initialization](https://github.com/linux-rdma/rdma-core/pull/1547)

对应的单元测试：[rdmacm::communication_manager::tests::test_cm_id_reference_count](https://github.com/RDMA-Rust/sideway/blob/5311a8e5a4bfbfd3530c085040a19009cdf927d6/src/rdmacm/communication_manager.rs#L1013)

## 生产状态 & Roadmap
