> **摘要** ：手工试跑几个 prompt，往往还不足以判断 Agent 能否稳定上线。本文梳理测试用例、评分器、执行轨迹和评测运行四个基本构件，以及从线上发现问题到离线验证修复的五步闭环。

*本文编译自 Tenex 博客，原文作者 Jake Klaristenfeld。为便于中文读者阅读，编辑时调整了标题、段落顺序和部分表达，技术论证与原意保持一致。*

vibe coding（凭感觉写代码）可以很快让一个应用跑起来。可当 Agent 准备进入生产环境，几次手工测试能说明的，只是它在那几个输入上恰好成功了。

如果想进一步了解它能否稳定工作，就需要一套可以持续运行、反复比较的评测体系。

团队讨论评测时，很容易从 Langfuse、Braintrust、LangSmith 或 Arize 选哪个开始。这些工具负责记录轨迹、管理数据和运行评分器，但「 **Agent 需要完成什么，哪些表现算是做对了** 」，仍然取决于业务本身。

评测驱动开发（eval-driven development）围绕这个问题展开：先写清良好行为，再据此测试 Agent，根据结果反复调整。生产环境中出现的失败也会慢慢沉淀为回归测试，在以后的改动中继续发挥作用。

## 一、评测体系里的四个基本构件

可以先用一句话建立直觉： **评测，就是把评分器应用到执行轨迹上。**

### 1. 执行轨迹：一次运行的完整记录

假设客户问：「我的退款到哪里了？」Agent 先调用 `search_orders` ，再调用 `issue_refund` ，最后回复：「退款已发出，3～5 天到账。」输入、每次工具调用和最终回复加在一起，就是一条执行轨迹。

如果没有执行轨迹，故障究竟发生在哪一步，往往很难判断。因此，对尚未建立可观测性系统的团队来说，记录完整轨迹通常是比选评测平台更靠前的一步。

### 2. 评分器：对表现做出判断

评分器也叫 evaluator 或 scorer，指任何能够评定 Agent 表现的机制：可以是一段普通代码，也可以是由 LLM（大语言模型）担任的裁判。

### 3. 测试用例与评测数据集

测试用例也叫 dataset item、example 或 test case。它包含想要测试的输入，以及对「良好表现」的定义。多个用例组成评测数据集（dataset）。有些用例带有参考答案，有些则只指定要应用哪些评分器。

例如：订单 #4821 正在处理退款。客户输入「我的退款到哪里了？」，期望回复是「订单 #4821 的退款已经发出，预计 3～5 个工作日到账」。

### 4. 评测运行：把版本表现定格下来

评测运行也叫 experiment，指用某个特定版本的 prompt 或 Agent，跑完数据集中的每个用例。每个用例会产生一条轨迹，再接受评分。它像一张快照：「版本 X 在数据集 Z 上得到分数 Y。」

假设退款数据集有 40 个用例，v3 通过 36 个，v4 通过 39 个。团队不仅知道修改带来了改善，还能定位剩下那个失败用例。

## 二、一条轨迹，至少有四种评分方式

真实的评测体系通常会在同一条执行轨迹上同时运行多种评分器。

- **确定性检查。** 使用普通代码，不涉及模型。例如：Agent 是否只调用了一次 `issue_refund` ，而且订单 ID 与刚才查到的订单一致？这类检查便宜、快速、结果明确，有明确规则可写时，往往是很合适的起点。
- **参考答案评分器。** 把输出与用例中保存的参考答案比较。既可以精确匹配，也可以让 LLM 判断两种表达是否同义。生产流量不会自带正确答案，所以它更适合人工编写的离线用例。
- **Rubric 评分器（按明确的评分标准判断）。** 它可以检查风格、语气和诊断项，不依赖参考答案。例如：回复是否简洁？是否确认发生了什么？是否说明退款未按时到账时该怎么做？
- **轨迹评分器。** 它关心 Agent 采取了哪些步骤，不只看最终答案。如果 Agent 没查订单就发起退款，或连续调用了 12 次 `search_orders` ，一个漂亮的最终回复也无法消除执行路径里的风险。

轨迹评分器更慢、成本更高，本身也可能出错。LLM 裁判同样只是一段 prompt，可以先用几十条人工标注过的结果，测量它与人工判断的一致率。如果一致率偏低，问题通常还在评分标准本身；评分器改动后，这项检验也可以随之重跑。

## 三、在线发现问题，离线验证修复

在线评测和离线评测最根本的区别，是待评估的执行轨迹来自哪里。

在线评测能带回真实问题，但不适合直接反复尝试修复；离线评测适合安全试验，覆盖面又容易受限于团队已经想到的场景。两者放在一起，才能同时兼顾真实性和可控性。

连接两者的关键动作叫 **用例转化（promotion）** ：把生产环境中表现不佳的执行轨迹，转化为离线测试用例。

## 四、评测驱动开发的五步闭环

测试用例有两个入口。

- **主动式：** 开发某项行为之前，先把预期流程定义出来。例如：客户询问一笔待处理退款时，期望 Agent 查询订单、发起退款，并告知预计到账时间。
- **响应式：** 在线评分器或用户标记了一条不良轨迹，团队再把它转化为用例。例如：Agent 遇到退款查询时回答无法帮忙，这次输入便可以进入数据集，同时补上期望的处理方式。

无论从哪个入口开始，之后的循环都相同。

1. **写清测试用例和通过标准。** 用例包含输入和评分器。参考答案评分器需要一份答案；Rubric 评分器需要一组判定标准。
2. **在修改前运行用例。** 如果用例已经通过，这项行为可能原本正常，也可能是用例没测到预期内容。对生产轨迹转化而来的用例，这一步也能检查故障能否在离线环境重现。
3. **调整 Agent。** 可以修改 prompt、模型、指令、工具描述或 Skill（技能）定义。
4. **用同一用例复测。** 第 3、4 步可以重复多次，直到用例稳定通过。
5. **再跑完整评测数据集。** 这一步用来检查其他已有行为，看局部修复是否引入了回归问题。

### 先定义多少次通过才算通过

LLM 具有非确定性，同一输入这次可能通过，下次可能失败。因此，实际评测通常会让同一用例运行多次（记作 k），再事先设定通过门槛。

对「一次失败都不能接受」的高风险行为，比如把钱退到他人订单，可以采用 *all-of-k* （k 次运行必须全部通过）。k 次全部通过无法证明错误永不发生；任何一次失败，都足以证明风险真实存在。对允许一定波动的行为，可以使用 *n-of-k* （k 次中至少通过 n 次），例如 3 次中通过 2 次。

### 把生产故障转成测试用例

一条被标记的执行轨迹，可以从复制输入开始转成新用例，再补上对良好表现的定义。原来的输出已经暴露了故障，不适合直接当作参考答案；这里需要由人给出期望结果。

这些轨迹来自真实用户。进入团队共享的评测数据集前， **其中的个人信息、订单号等敏感数据需要先移除。**

不同系统可能要求 JSON、CSV 或图形界面输入。团队可以自建一个 Skill，把自然语言转成服务商要求的数据格式。例如：

1. 「创建一个测试用例：客户要求为一笔超过 90 天的订单退款。Agent 应该解释退款期限，并且不应调用 `issue_refund` 。」
2. 「根据生产轨迹 `{flagged_trace_id}` 创建测试用例。Agent 当时说无法提供帮助；正确行为应该是查询订单、发起退款，并告知预计到账时间。」

## 五、回归测试集如何积累长期价值

一次 prompt 修改可能修好当前用例，同时悄悄破坏其他行为。如果只重跑正在修复的那个用例，这些问题就不会暴露。

对有实质影响的改动，完整数据集可以放进 CI，并与上一次结果比较。随着时间推移，被转化的生产事故会成为长期保留的测试。数据集也因此逐渐记住 Agent 曾经出现过的失败方式，并在它们再次出现时把问题暴露出来。

把这些环节连起来，就得到一个闭环： **在线评测发现问题，用例转化保留问题，离线评测验证修复，完整数据集检查是否出现回归。**

## 六、评测体系起步时，三个容易被忽略的环节

第一个环节，是把「什么叫表现良好」写清楚。这往往是整套方法中最难的工作。预期行为一旦变成可测量的标准，一些原本被认为「当然没问题」的能力，可能会显示出不小的波动。

第二个环节，是创建测试用例的成本。如果把生产故障转成用例需要点开多个页面、手写 JSON，这一步就很容易被跳过。更顺手的流程可以是：一次点击转化轨迹，一个输入框描述预期行为。

第三个环节，是执行路径是否也在评分范围内。一个 Agent 可能用 30 个回合完成原本一次工具调用就能解决的任务，却仍然给出完美答案。只看输出的评分器不会标记这个问题；加入一项轨迹检查，则能让这类低效或高风险路径变得可见。

## 七、四个评测平台的术语对照

理解上面的四个构件后，不同平台之间就有了一套可对照的坐标。它们的具体能力和界面各有差异，但许多核心对象可以互相映射。

- **LangSmith：** 测试用例叫 *examples* ，评分器叫 *evaluators* ，评测运行叫 *experiments* 。在线 evaluator 可通过规则对生产轨迹评分，生产轨迹也可转入数据集。
- **Langfuse：** 测试用例叫 *dataset items* ，评分结果叫 *scores* ，完整的评测可记为 *experiment run* 。LLM-as-a-judge evaluator 可对实时轨迹评分，生产边缘用例也可补回数据集。
- **Braintrust：** 数据集中的测试记录叫 *records* ，评分器叫 *scorers* ，评测运行叫 *experiments* ，生产轨迹记录为 *logs* 。在线评分规则可按范围、过滤条件和抽样比例运行。
- **Arize AX：** 数据集中的测试用例叫 *examples* ，评分器叫 *evaluators* ，评测运行叫 *experiments* 。生产环境中的 span（调用片段）可加入数据集。

这些平台都以某种形式支持用例转化，让生产问题可以重新回到评测数据集。平台术语和界面变化很快，到正式选型时，再根据官方最新文档确认具体能力会更稳妥。

## 八、这套方法还有一个边界

上面的闭环有一个隐含前提：执行轨迹可以在离线环境中重现。简单 prompt 较容易满足这一点，会读写真实系统的 Agent 则要复杂得多。

外部状态会变化。退款轨迹运行时， `search_orders` 可能显示订单 #4821 正在处理退款；一周后用相同输入重跑，退款可能已经完成，Agent 也会走上另一条路径。

写操作还会产生真实后果。 `issue_refund` 会转移资金，离线评测需要验证 Agent 的退款能力，同时拦截真实写操作。如何重放外部状态，以及如何在离线环境中阻断写操作，是评测真实世界 Agent 时的下一层难题。

如果准备把这套方法带进现有系统，以下五个问题可以帮助判断闭环是否完整：

- 每项关键行为，能否用一句可检验的话说清怎样才算「做对」？
- 系统里是否留下了完整执行轨迹，而非只有最终输出？
- 评测中是否既有确定性检查，也有轨迹检查？
- 重要的生产故障，是否会在脱敏后转成长期保留的测试用例？
- 有实质影响的改动，是否会触发完整数据集，而非只测眼前的那一个用例？

当这些问题逐渐有了稳定答案，每次失败留下的内容，会从一条故障记录逐渐变成系统下一次更可靠的依据。
