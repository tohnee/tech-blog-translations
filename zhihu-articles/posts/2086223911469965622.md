### 2. 两条路线画像（先看结论）

> 一句话：

- **llama.cpp（Q4_K_M 单卡 + MTP）**：单流 **44.7 tok/s**、上下文 **262144（256k）**、思考/工具全通、**无跨卡开销**、部署简单。
- **vLLM（FP8 + TP2 + DFlash2）**：单流 **54 tok/s**、上下文 131072（128k）、思考/工具全通、双卡跨卡通信、部署复杂。

**选型一句话**：**要最大上下文 + 单卡简单拓扑 → llama.cpp；要更高单流（约 +20%）+ 高并发分片 → vLLM。** 上下文上 llama.cpp 是 vLLM 的 **2 倍**。

### 4. 速度对比（同口径）

> 口径统一：长输出 + `ignore_eos` 风格（vLLM 用 `ignore_eos=true`；llama.cpp 用长输出 600t）。

| 方案 | 单流 tok/s | 相对基准 |
| --- | --- | --- |
| llama.cpp 无投机（f16 KV） | 33.3 | 1.00 |
| llama.cpp MTP n-max2 | 44.7 | 1.34 |
| vLLM FP8 + DFlash2 | 54.0 | 1.62 |
| vLLM FP8 无投机 | 34.9 | 1.05 |

**解读**：

- llama.cpp 的 MTP 投机把单流从 33.3 → 44.7（**+34%**）。
- vLLM 的 DFlash2 把单流从 34.9 → 54.0（**+55%**）。
- vLLM+DFlash2 仍比 llama.cpp+MTP **高约 20%**，但注意：**vLLM 是双卡 TP2，llama.cpp 是单卡**。若把 llama.cpp 也铺到第二张卡（双实例 + nginx），聚合吞吐可超过 vLLM。

### 双卡聚合（llama.cpp）补充

| 场景 | 聚合 tok/s |
| --- | --- |
| 单卡单流 | 46–48 |
| 双卡并行（各 1 请求） | ~84 |
| 双卡 4 并发（每卡 2） | ~109 |

> vLLM 那套单流 54 用的是两卡 TP2；若要对比吞吐，可把 vLLM 无投机在并发下的吞吐（`SERVICE_USAGE`：FP8 无投机并发4 = 126.5 tok/s）拿出来看。

### 5. 上下文对比（关键差异）

|  | llama.cpp | vLLM |
| --- | --- | --- |
| 最大 ctx | 262144（=训练长度，无溢出） | 131072 |
| 380k+ | ❌ OOM | - |
| 为什么能做到 | Q4 量化（16.4GB）+ Qwen3-Next 混合注意力（仅 16 层 full-attn 有标准 KV，线性层不占）+ KV q8_0 压缩 | FP8（~31GB）更占显存，128k 封顶 |

> **llama.cpp 上下文 = vLLM 的 2 倍**。根源在于：llama.cpp 能用 Q4（4bit）省显存 → 给 KV cache 让出更多空间 → 塞下 256k。而 vLLM 要保功能得用 FP8（8bit），体积翻倍，只能 128k。

### 6. 功能对比（thinking / 工具 / 4bit）

### 6.1 thinking 与工具调用

| 项 | llama.cpp（Q4） | vLLM（FP8） | vLLM（NVFP4 4bit） |
| --- | --- | --- | --- |
| thinking | ✅ | ✅ | ❌ 损坏 |
| 工具调用 | ✅ 该调才调 | ✅ 该调才调 | ❌ 误触发 |

> **关键经验**：**4bit 在 llama.cpp 下不坏工具/思考**（Ollama 也印证）；坏掉的只是 **「vLLM + QUASAR-NVFP4」** 组合。所以：<br>

- llama.cpp 可以放心用 Q4（省显存 → 更大上下文）；
- vLLM 要保工具/思考得用 FP8（~31GB，占显存多 → 上下文小）。

### 6.2 几个容易混淆的点

| 说法 | 是否正确 | 解释 |
| --- | --- | --- |
| “4bit 一定坏功能” | ❌ 错 | llama.cpp 的 Q4 就是好的。坏的是「vLLM + NVFP4」组合，不是 4bit 本身 |
| “vLLM 一定比 llama.cpp 快” | ❌ 片面 | vLLM FP8+DFlash2 单流 54，llama.cpp MTP 单流 44.7，vLLM 快约 20% 但要双卡 TP2。单卡 vs 单卡的话，llama.cpp 甚至更快（无跨卡开销） |
| “NVFP4 速度最高就该用它” | ❌ 错 | NVFP4 单流 ~74 是快，但 thinking 和工具调用全坏，作为 agent 后端不可用。速度无意义 |
| “llama.cpp 上下文就是 2 倍” | ✅ 对 | 256k vs 128k，在 Q4 + 混合注意力 + KV q8_0 压缩组合下 |
| “部署越复杂性能越好” | ❌ 片面 | llama.cpp 单二进制部署最简单，性能并不差 |
| “vLLM 生态更好所以该用 vLLM” | ⚠️ 看需求 | vLLM 的 PagedAttention、continuous batching 对高并发确实更好。但单用户 agent 场景这些优势不明显 |

### 7. 架构与工程对比

| 维度 | llama.cpp | vLLM |
| --- | --- | --- |
| 依赖 | 单 glibc 2.35 兼容（好装） | 官方 wheel 需 glibc≥2.38，须源码重建 |
| 模型格式 | GGUF（社区/自转） | safetensors |
| 量化 | Q 系（Q4/Q6/Q8） | FP8 / NVFP4 |
| 4bit 的 thinking/工具 | ✅（GGUF Q4 正常） | ❌（NVFP4 坏）← 关键差异 |
| 多模态 | 支持 mmproj（需配） | 支持 |
| 投机解码 | draft-mtp / draft-dflash 等 | DFlash2 / MTP |
| 部署 | 单二进制 llama-server | 大 Python 栈（conda + wheel + 依赖） |
| systemd | 手动脚本（Type=simple 也可） | 已有 vllm-qwen38-fp8 |

### 8. 选型建议（按需求）

| 需求 | 推荐 |
| --- | --- |
| 单用户 / agent / 工具，要大上下文 | llama.cpp 单卡 Q4_MTP（256k，无跨卡） |
| 追求最高单流（~54） | vLLM FP8 + DFlash2（但 128k、需双卡） |
| 高并发 / 吞吐分片 | vLLM FP8 无投机（双卡 TP2），或用 llama.cpp 双实例 + nginx（新服务器） |
| 简化部署 / 低依赖 | llama.cpp |
| 纯对话、省显存 | 两者皆可；llama.cpp 更省 |

**本机最终推荐形态**：

> **llama.cpp 单卡黄金配置**跑最优（单用户 / 大上下文 / 简单）；**聚合吞吐**交给新服务器 nginx 分发到本机多实例。

---

### 9. 常见误解澄清

| 误解 | 真相 |
| --- | --- |
| “vLLM 一定比 llama.cpp 快” | 单流 vLLM 只快约 20%，且要双卡；llama.cpp 单卡就 44.7，双卡聚合可超 vLLM |
| “4bit 模型没救” | 4bit 在 llama.cpp 下是好的；坏的是 vLLM+NVFP4 组合 |
| “上下文越大越好” | 2 倍上下文（256k）适合长文档/长对话；若不需要大可无所谓 |
| “必须用 systemd” | 本机 llama.cpp 用手动脚本就够（只跑大模型一件事） |

---

### 10. 结论

1. **没有绝对赢家**，取决于你的首要指标：

- **要 256k 上下文 + 简单拓扑** → llama.cpp（Q4 单卡）。单流 44.7，双卡聚合可达 109。
- **要最高单流 54 + 能接受 128k + 双卡** → vLLM FP8 + DFlash2。

1. **工程上 llama.cpp 更省心**（单二进制、glibc 直接兼容、4bit 也不坏功能）；vLLM 强在高并发分片和生态。
2. **本项目最终**：单用户 agent 核心用 **llama.cpp 单卡**跑；聚合走新服务器 nginx；vLLM 方案作为高并发备选留档。
