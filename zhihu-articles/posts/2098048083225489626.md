## 训推一致>>

适配场景：DeepSeek V4.1 Flash，多模态原始包 → 纯文本 bf16，SGLang DPA + LoongSage R3 Agent RL，核心约束： **训推 logprob 万分位对齐、报错可复现、稳定不随机炸** ；

> 核心原则： **配置清洗前置、固化、版本锁死；不要靠框架自动容错；全链路两边（SGLang rollout + Megatron train）共用同一份清洗后的 config** 。 目标：消除 “随机失败、报错迷惑”—— 根源就是不同并行开关触发不同分支，多余配置条件性触发模块初始化。 
> 

## 一、流水线（顺序不能乱）

### Step1：先备份原始 config，绝不原地覆盖原始权重包

原始 HF 权重目录原样留存， **只拷贝一份 config.json 出来做清洗** ，权重文件不动。

> 最佳实践：清洗后的 config 单独放到独立 conf 目录（就是原文 repo 里 `conf/dsv41_flash_bf16` 的做法），和原始模型目录解耦；不同并行配置（TP8-DP2、TP8-DP4）单独放不同 config，不要共用。 
> 

### Step2：标准化清洗脚本（确定性清洗，人工手动删极易漏字段）

清洗逻辑固定，而不是人工改 json：

1. 读取原始 config
2. 删除顶层 `quantization_config` 整 key；
3. 取出 `text_config` ，把 text_config 内所有字段提升到顶层；
4. 删除 `vision_config` 、 `vision_tower` 等所有视觉相关 key；
5. 删除 `mtp_config` 、 `dspark_config` 、 `mtp` 、 `dspark` 相关全部字段；
6. 显式覆盖固定 dtype： `torch_dtype: "bfloat16"` ；
7. 显式关闭不需要的 flag： `use_mtp=false, use_dspark=false` ；
8. 补充 SGLang MLA/DPA 必须的缺失顶层参数（从原 text_config 继承： `mla_down_proj_dim, num_heads, n_groups` 等）；
9. 写新 config， **加版本注释，记录来源、清洗时间、目标并行组合** 。

> 重点：不要只删一部分；条件分支判断是 “if key exists → init module”，残留任意一个相关 key，在某些 TP/DPA/CudaGraph 组合下就会随机触发加载分支。 
> 

### Step3：校验阶段（非常关键，用来提前拦截迷惑报错）

清洗完不要直接上大集群跑 rollout，分两层校验：

1. **Dry-run 模型构造校验（单卡小测）** 只用 SGLang 加载这个清洗后的 config，不跑大 batch、不跑 DPA，只做 `sglang.LlamaForCausalLM.from_config(...)` ，看是否能成功构造模型、权重 key 一一匹配，打印权重 key diff： 1）不允许有 unexpected key（多余权重）；2）不允许 missing key（主干文本权重缺失）
2. **并行配置最小单元验证：TP=8，DP=1，EP=1** 先跑最简并行基线，确认能正常 prefill/decode，拿到稳定 logprob；基线通了，再打开 DPA、调高 EP。  很多随机报错是：单卡能加载，一开 DPA/EP/CUDA Graph，才触发冷门分支。 
 

### Step4：两边链路绑定同一份清洗后 config（R3 对齐的硬性要求）

- SGLang rollout（录 R3 路由、生成轨迹）
- Megatron 训练侧重前向、loss、R3 回放 **必须使用完全一模一样的清洗 config，包括所有 MLA、MoE、group、专家数量参数**

> 哪怕只是某个无关 flag 两边不一致，都可能计算图不一样，logprob 对不上。这不是加载报错，是静默的对齐失败，更难查。 
> 

### Step5：报错兜底排查（遇到迷惑报错时的诊断顺序）

按优先级排查，避免上来就怀疑权重损坏、网卡、TP 切分 bug：

1. 对比 SGLang 加载时读到的 config json 和 Megatron 的 config 是否 md5 一致；
2. 打印 `model_config` 里是否残留 vision /quantization/mtp /dspark key；
3. 关闭 cuda graph 重试：很多随机失败只在 cuda graph 开启时触发；
4. 降到 DP=1，关闭 DPA，判断是否是 DPA 路径引入的条件分支；
5. 打印权重 key 集合 diff，区分是 missing key（模块声明多了）还是 shape mismatch（维度配置不对）。

## 二、经验总结

### 📌 配置管理（最高优先级）

1. **禁止动态修改 config、禁止运行时 patch config** 不要在启动脚本里用 python 临时 pop 键；所有裁剪在离线脚本一次性做完，产出静态 json。运行时 patch 会在不同 rank、不同进程出现 patch 时机不一致，多卡下偶发随机失败。
2. **配置和并行规格强绑定，命名自解释** 示例命名： `dsv41_flash_tp8_dp2_ep16_bf16_no_mtp_no_vision.json` ； TP/DP/EP 一变，单独一份 config，不要一个 config 靠启动参数开关控制 mtp/vision。
3. 配置纳入版本控制（git），和训练脚本、sglang 启动脚本一起提交；每一次实验记录 config commit hash。
4. 原始模型只读，权限锁死，任何人不允许修改原始 HF 目录里的 config.json。

### 📌 SGLang 加载侧

1. 显式指定 `dtype=bfloat16` ，不要依赖自动推断；自动推断在原始包残留 quantization_config 时会跑偏。
2. 关闭自动量化探测：部分 SGLang 分支会自动识别 quantization_config 并尝试加载 fp8。
3. 开启 `skip_vision_encoder` 这类开关 **不能替代删除 vision_config** 。 开关只是跳过前向，但是 config 存在依然会触发子模块初始化，依然会在某些路径下找视觉权重，留下随机炸弹。  一句话： **不要用 flag 屏蔽，直接删掉配置项** 。
4. 循序渐进开启特性：先跑普通 TP，稳定后再开 DPA；DPA 稳定，再开 sticky routing；最后打开 R3 回放。不要一次性全量开启。

### 📌 RL R3 场景

1. 清洗脚本输出的 config，同时作为 SGLang 和 Megatron 的唯一真值源，做 md5 校验，启动时脚本校验两边 md5 相等，不等直接退出，禁止启动。
2. 禁止在 Megatron 训练侧单独再做一次 config 裁剪；两边共用同一份文件。
3. 记录日志时，把完整 config 打印到日志头部，便于复现 “为什么上次能跑这次炸了”。

### 📌 规避 “随机失败” 的工程手段

随机失败本质： **分支是条件触发，触发条件依赖 GPU 调度、cuda graph capture 顺序、rank 启动时序、batch shape** 。

- 实验固定：固定 GPU 型号、固定 SGLang commit、固定 Megatron commit、固定 cuda/cudnn 版本；版本漂移是第二大迷惑报错来源；
- cuda graph 作为风险开关：调通链路后，最后再打开 cuda graph 做性能优化；定位问题时优先关闭；
- 避免混合不同规格的节点；异构硬件下，不同 rank 的 kernel 路径差异更容易触发条件分支 bug。

## 三、避坑（做法看着省事，后面必踩坑）

❌ 人工手改 json，容易漏 key（比如只删 vision_config，忘记 mtp 子 key）

❌ 只在 SGLang 侧删，Megatron 侧还用原始多模态 config

❌ 保留 quantization_config，启动参数传 `--no-quant` 跳过量化

❌ 同一个 config，用来跑 TP8-DP2，又直接拿去跑 TP8-DP4，不做校验

❌ 不做 dry-run，直接上多机大集群提交任务，等几十分钟才加载失败，浪费机时

## 四、极简清洗脚本

```python
import json
from pathlib import Path

def clean_dsv41_multimodal_to_text(raw_cfg_path: Path, out_cfg_path: Path):
    with raw_cfg_path.open("r", encoding="utf-8") as f:
        cfg = json.load(f)
    # 取出文本配置，提升到顶层
    text_cfg = cfg.pop("text_config")
    cfg.update(text_cfg)

    # 删除全部不需要分支
    drop_keys = [
        "vision_config", "vision_tower",
        "quantization_config",
        "mtp_config", "mtp",
        "dspark_config", "dspark"
    ]
    for k in drop_keys:
        cfg.pop(k, None)

    # 强制锁定bf16
    cfg["torch_dtype"] = "bfloat16"
    cfg["use_mtp"] = False
    cfg["use_dspark"] = False

    with out_cfg_path.open("w", encoding="utf-8") as f:
        json.dump(cfg, f, indent=2)
    print(f"Clean config saved to {out_cfg_path}, md5: ...")

if __name__ == "__main__":
    clean_dsv41_multimodal_to_text(
        Path("original/config.json"),
        Path("dsv41_flash_tp8_dp2_ep16_bf16.json")
    )
```

## 总结

方案是 **离线确定性清洗 + 基线小步验证 + 全链路同一份 config + 版本锁定** ；

核心思想： **不依赖框架的容错、不依赖运行时开关去掩盖多余配置，从源头删掉所有可选分支的配置声明，消除条件式模块初始化，从而根除那种和 TP/DPA/CudaGraph 耦合、复现不稳定的迷惑报错** 。

## 一、术语

1. **Engram** ：V4.1 新增的条件记忆查表模块，超大固定 FP8 查表表，冻结，放 Host 内存； **训推两边都要有一份** ，极易被忽略。
2. **R3 / Routing Replay** ：MoE 专家路由回放；rollout 阶段记录每个 token 选了哪些专家，训练阶段强制复用这套路由，保证训推路径一致，避免路由随机漂移导致 logprob 对不上（Agent RL 对一致性要求极高）。
3. **DP Attention（DPA）** ：SGLang 针对 MLA 的并行方案；TP 切不动时，用 data 并行分摊 attention 计算，是 V4.1 推理的关键并行手段。
4. **共置部署（colocated）** ：同卡集群上， **SGLang rollout 推理进程 + Megatron 训练进程共用硬件** ，节省机器，但显存 / 主机内存资源互相争抢，是绝大多数 OOM 来源。
5. **sticky routing** ：同一条 agent 轨迹（多轮对话）的所有请求固定打到同一个计算副本，保证 KV Cache 不失效、不复算。

## 二、坑 + 根因 + 修复方案（按链路顺序）

### 1. 权重 & Config 转换：多模态→纯文本 bf16，无官方脚本

目标：统一 bf16、去掉多模态分支、适配 SGLang 加载 必须删掉 / 修改配置项：

- 删除 `quantization_config` ：否则 SGLang 加载报错
- 删除顶层 `vision_config` ，把 `text_config` 提升到顶层（V4.1 原生带多模态分支，RL 只用文本）
- 删除 mtp/dspark 配置（本次 RL 链路暂时不用）

> 坑点：社区只放出 day0 支持，但没有现成转换脚本，漏一项就随机加载失败，报错信息很迷惑。 
> 

### 2. SGLang 跨机部署并行拓扑约束（EP=16，TP 上限 = 8，DP=2）

- 单机 8 卡 load 权重 > 130G，再加 KV Cache，单机塞不下，选择两机 16 卡 EP=16；
- 硬约束： `linear_o_group_proj` 这个权重 **不能 TP 切分超过 8** → TP 最大只能 8；
- 不能开 PP（流水线并行）：PP 会破坏 routing replay，R3 失效，训推不一致；
- 剩余并行度只能走 DP Attention → 只能 DP=2。

> 这里是整个拓扑的硬性边界，不是随便调 TP/DP/PP。 
> 

### DP Attention 两个隐藏 SGLang Bug（作者已经提 PR 修复）

1. **健康检查请求直接 crash** 根因：开启 DPA 后，prefill token 总数 **必须是 attention tp size 的整数倍** ；探活健康包 token 长度不满足倍数约束，直接挂，看起来像启动失败，非常有迷惑性。
2. **关闭 cuda graph 时 decode 卡死** 根因：关闭 cuda graph 调试时，代码路径缺少 idle batch 处理，decode 循环无限等待，假死。

> 坑的放大效应：前面已经做了权重转换，出问题时人很容易怀疑权重损坏、网络问题，而不是 DPA 本身的 kernel bug。 
> 

### 3. KV Cache 反复重算：Router 感知粒度不够（sticky routing 下沉到 DP）

原始 LoongSage router 只做到「固定到某个 SGLang engine 实例」，但 DPA 下一个 engine 内部包含多个 DP 副本，请求会在 DP 之间负载均衡。 Agent 多轮轨迹场景：同一轮对话的不同请求跑到不同 DP → KV Cache 不在目标 DP，强制重算 KV，吞吐暴跌。 ✅ 解法：把 sticky routing 从 engine 级别下沉到 **DP 粒度** ，同一个 agent trajectory 永远发到同一个 DP 副本，保住 KV 复用。

### 4. Dummy 权重加速启动 → Engram 丢了（非常隐蔽）

加速思路：SGLang 启动指定 `load_format=dummy` ，跳过完整权重读取，由 Megatron 同步权重给 SGLang，大幅减少几十卡同时读共享存储的启动耗时。

- 雷：权重同步逻辑 **不传输 Engram** （Engram 是冻结独立查表表，不在常规权重同步流里面）；dummy 模式直接跳过 Engram 加载，模型永久丢失 Engram。
- 跨机额外雷：Engram host 内存布局默认 `shared` （单机内全局共享），跨节点不能共用，必须显式改成 `private/sharded` ，每个 rank 加载自己分片。 ✅ 临时修复：patch SGLang，dummy 模式下单独加载 Engram 分片。

### 5. 最大瓶颈：主机内存（不是 GPU 显存），R3+Engram+CPU 优化器三重暴击

原文实测：

- 每个 token R3 路由信息：960B；KV Cache 每个 token ~960B； **R3 的 host 内存开销≈KV Cache 显存开销 × 8** ； 例：每张卡给 KV 预留 20G → 主机要预留 160G 给 R3 routed expert 记录；KV 池开大 = 主机内存直接爆炸， **优先主机 OOM，而不是显存 OOM** 。
- 控制手段：显式限制 `max_total_tokens` ，收紧 KV cache 池上限，连带压制 R3 内存。
- 第二大头：CPU Optimizer（把 Adam 状态 offload 到 Host 省显存） 叠加 Engram（SGLang 一份 + Megatron 一份）+ R3，内存压力远大于 V4；原来跑 V4 的 6 机 H20（单机 2T 内存）直接 OOM。

✅ 最终方案：Megatron dev 分支 `chunked_optimizer_state_offload`

- 效果：主机内存峰值从 18N → 12N（N = 参数量），降低 1/3；
- 配套环境变量： `PYTORCH_ALLOC_CONF=pinned_max_cached_size:32`
- 原理：pinned 内存默认向上按 2 的幂对齐分配，会超额占用；这个配置砍掉多余的 pin 内存缓存，在内存边缘场景避免 “最后一根稻草” 式 OOM。

### 6. 混合精度 + chunked offload + fp32 lmhead → checkpoint 续训失败

根因：Megatron 优化器在这个组合下， **bf16 权重和 fp32 master 权重状态对不齐，checkpoint 加载校验失败** 。 ✅ 临时方案：monkey-patch 修复混合精度状态同步逻辑。

## 三、工程经验提炼（做同类 Agent MoE RL 最值得记住的几条）

1. Agentic RL 对 **训推 logprob 一致性要求是硬红线（本文做到万分位）** ，R3 路由回放、Engram、KV 复用、并行拓扑全部围绕这个目标；任何并行改动都不能破坏 R3。
2. 新一代 DeepSeek Flash 系列（带 Engram、mHC）不再只是 GPU 显存游戏， **Host 内存才是资源瓶颈** ，R3 的 8 倍放大效应很容易被忽略。
3. DP Attention（DPA）是 MLA 大模型推理扩容的重要手段，但它有独有的 prefill token 倍数约束、cuda graph 依赖，属于 SGLang 比较新的路径，bug 多、文档少。
4. dummy 权重预加载是多卡共享存储场景的刚需加速手段，但只要模型有独立冻结的外置记忆模块（Engram），一定要单独处理，不要默认跟着主权重同步。
5. 并行拓扑选型：V4.1 这个架构，TP 有硬上限，PP 基本不能在 R3 RL 场景使用，扩容只能靠 EP+DP Attention，选型空间很小。
