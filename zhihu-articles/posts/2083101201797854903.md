## 1. Device Buffer

写算子时，除了 kernel 本身，还要管理显存：输入输出、中间结果、workspace。手动 `cudaMalloc`/`cudaFree` 很容易泄漏或重复释放，C++ 用 RAII 解决这个问题：把资源获取放进构造函数、释放放进析构函数，让资源生命周期与对象绑定，离开作用域就一定释放。PyTorch 的 `Tensor`、Thrust 的 `device_vector`、CUTLASS 的 `DeviceAllocation` 底层都是这个思路，`DeviceBuffer` 是它的最简化的版本。

在 GPU 上还有两个额外问题。一是所有权：浅拷贝会让两个对象释放同一块显存，因此需要禁止拷贝、只允许移动，保证任何时刻只有一个对象负责释放。二是异步：kernel launch 只是把任务放进 GPU 的执行队列（stream）就立即返回，对象析构时 GPU 可能还在用这块显存。这个类本身不做同步，销毁前等相关任务执行完是调用方的责任；实际框架会记录显存与 stream 的关联，并用 caching allocator 代替每次 `cudaFree` 来处理这个问题。

```cpp
//device_buffer.h
#pragma once
#include <cuda_runtime.h>
#include <cstddef>
#include <stdexcept>
#include <utility>

inline void cuda_check(cudaError_t status) {
    if (status != cudaSuccess)
        throw std::runtime_error(cudaGetErrorString(status));
}

template<class T> class DeviceBuffer {
    T* ptr_ = nullptr;
    std::size_t count_ = 0;
public:
    explicit DeviceBuffer(std::size_t n) : count_(n) {
        if (n) cuda_check(cudaMalloc(
            // cudaMalloc 通过 void** 回填地址；T** 不能隐式转为 void**，需显式转换
            reinterpret_cast<void**>(&ptr_), n * sizeof(T))); 
    }

    // 析构函数，默认noexcept
    ~DeviceBuffer() noexcept { 
        if (ptr_) cudaFree(ptr_); 
    }
    
    // 禁止拷贝：浅拷贝会让两个对象持有同一指针，析构时重复释放
    DeviceBuffer(const DeviceBuffer&) = delete;             // 禁止 DeviceBuffer b = a;
    DeviceBuffer& operator=(const DeviceBuffer&) = delete;  // 禁止 b = a;

    // 移动构造：DeviceBuffer b = std::move(a);
    // b 是新对象，直接接管 a 的指针，并把 a 置空，保证只有 b 负责释放。
    // noexcept 是为了让 std::vector 等容器扩容时敢用移动，否则会退回拷贝（已禁止）导致编译失败。
    DeviceBuffer(DeviceBuffer&& other) noexcept
        : ptr_(std::exchange(other.ptr_, nullptr)),
          count_(std::exchange(other.count_, 0)) {}

    // 移动赋值：b = std::move(a);
    // b 已存在、可能持有旧显存，所以要先释放自己的，再接管 a 的并把 a 置空。
    // this != &other 防止 a = std::move(a) 时先把自己释放掉。
    DeviceBuffer& operator=(DeviceBuffer&& other) noexcept {
        if (this != &other) {
            if (ptr_) cudaFree(ptr_);
            ptr_   = std::exchange(other.ptr_, nullptr);
            count_ = std::exchange(other.count_, 0);
        }
        return *this;
    }

    T* data() const noexcept { return ptr_; }
    std::size_t size() const noexcept { return count_; }
};
 

```

## 2. 原子操作Atomic

有个头文件`gpu_ops.h`,定义了下面所有我们要用的function:

### 原题错误分析

```cpp
__global__ void broken(int* a, int* out, int* count, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) return;       // ① 边界写反：界内线程全部退出，越界线程反而继续执行
    a[i] = sinf(i);          // ② 类型不匹配：a 是 int*，sinf的结果(float)被截断成 0 或 ±1
    if (a[i] >= 0) {
        int loc = *count;
        *count += 1;         // ③ race condition：多个线程可能拿到同一个 loc
        out[loc] = n;        // ④ 写错值：应写元素本身 a[i]，而不是长度 n
    }
}

```

- ① 应为 `if (i >= n) return;`
- ② `a` 应为 `float*`，否则筛选条件失去意义
- ③ 应改用 `atomicAdd(count, 1)`
- ④ 应为 `out[loc] = a[i]`

### 填充：fill_kernel

```cpp
// grid-stride loop：一个线程处理多个元素，grid 大小与 n 解耦；
// 同一轮中 warp 内相邻线程访问相邻地址，访存仍然合并
__global__ void fill_kernel(float* a, int n) {
    int idx    = blockIdx.x * blockDim.x + threadIdx.x;
    int stride = gridDim.x * blockDim.x;
    for (int i = idx; i < n; i += stride)
        a[i] = sinf(float(i));
}

void fill_sin(float* a, int n, cudaStream_t stream) {
    if (n <= 0) return;                        // 空输入不启动 kernel
    int block = 256;
    int grid  = (n + block - 1) / block;
    fill_kernel<<<grid, block, 0, stream>>>(a, n);
    cuda_check(cudaGetLastError());            // 检查启动配置是否合法
}

```

### 筛选：atomic_kernel

```cpp
__global__ void atomic_kernel(const float* a, float* out,
                              int* count, int n) {
    int idx    = blockIdx.x * blockDim.x + threadIdx.x;
    int stride = gridDim.x * blockDim.x;
    for (int i = idx; i < n; i += stride) {
        if (a[i] >= 0.0f) {
            // atomicAdd 把「读旧值 + 加 1 + 写回」变成不可分割的一步，
            // 返回自增前的旧值，作为本线程独占的写入位置
            int loc = atomicAdd(count, 1);
            out[loc] = a[i];
        }
    }
}

void filter_atomic(const float* a, float* out, int* count,
                   int n, cudaStream_t stream) {
    // 清零必须在 n <= 0 的返回之前：空输入也要把 count 置 0
    cuda_check(cudaMemsetAsync(count, 0, sizeof(int), stream));
    if (n <= 0) return;
    int block = 256;
    int grid  = (n + block - 1) / block;
    atomic_kernel<<<grid, block, 0, stream>>>(a, out, count, n);
    cuda_check(cudaGetLastError());
}

```

- 输出顺序由线程抢到 `atomicAdd` 的先后决定，不保证与输入一致
- 清零、kernel 都提交到同一条 stream，靠流序保证清零先生效

## 3. 稳定筛选： scan + scatter

第 2 题里用 `atomicAdd` 来抢输出位置，虽然能保证每个元素都有地方放，但有个问题：**谁先抢到位置是不确定的**。

也就是说，最后输出的顺序可能会乱。比如输入里本来是先出现 A，再出现 B，但 GPU 线程执行顺序不固定，最后可能变成 B 在前、A 在后。

如果我们想让输出顺序和输入顺序一致，就不能让线程临时去“抢位置”，而是要提前把每个元素应该写到哪里算好。

思路其实很简单：

对每个元素先判断“要不要保留”。

- 保留：记成 `1`
- 丢掉：记成 `0`

这样就得到一个 `flags` 数组。

然后对 `flags` 做一次**排他前缀和**。

这个前缀和得到的值，正好表示：

> 当前元素前面一共有多少个元素会被保留下来。

所以这个数就可以直接当成当前元素在输出数组里的下标。

整个过程分三步：

1. **mark**：判断每个元素保不保留，得到 `flags`
2. **scan**：对 `flags` 做排他前缀和，得到 `offsets`
3. **scatter**：把保留的元素写到 `out[offsets[i]]`

例如输入：

`{-2, 0, 3, -1, 3}`

因为这里保留非负数，所以：

| i | 0 | 1 | 2 | 3 | 4 |
| --- | --- | --- | --- | --- | --- |
| a | -2 | 0 | 3 | -1 | 3 |
| flags | 0 | 1 | 1 | 0 | 1 |
| offsets | 0 | 0 | 1 | 2 | 2 |

看几个位置就很直观：

- `0` 前面没有保留元素，所以它写到 `out[0]`
- 第一个 `3` 前面有 1 个保留元素，所以写到 `out[1]`
- 最后一个 `3` 前面有 2 个保留元素，所以写到 `out[2]`

因此最后输出是：

`{0, 3, 3}`

总共有多少个元素，可以用：

```cpp
count = offsets[n - 1] + flags[n - 1];

```

来算。

为什么这里不需要原子操作？

因为每个真正要保留的元素都会得到不同的 `offset`，所以不会有两个线程写同一个位置。

有些被丢掉的元素可能和别人的 `offset` 一样，比如这里 `i=3` 和 `i=4` 的 offset 都是 2，但 `i=3` 不会写入，所以没有冲突。

### mark_kernel

```cpp
// 非负数标记为 1，负数标记为 0
__global__ void mark_kernel(const float* a, int* flags, int n) {
    int idx    = blockIdx.x * blockDim.x + threadIdx.x;
    int stride = blockDim.x * gridDim.x;

    for (int i = idx; i < n; i += stride)
        flags[i] = (a[i] >= 0.0f);
}

```

这个 kernel 做的事情非常简单：

每个线程负责检查一些元素，如果元素非负，就写 `1`，否则写 `0`。

### scatter_kernel

```cpp
__global__ void scatter_kernel(const float* a, float* out,
                               const int* flags,
                               const int* offsets,
                               int* count, int n) {
    int idx    = blockIdx.x * blockDim.x + threadIdx.x;
    int stride = blockDim.x * gridDim.x;

    for (int i = idx; i < n; i += stride) {
        if (flags[i])
            out[offsets[i]] = a[i];
    }

    if (idx == 0)
        *count = offsets[n - 1] + flags[n - 1];
}

```

这里也不复杂。

如果 `flags[i] == 1`，说明这个元素要保留，就把它写到提前算好的位置：

```cpp
out[offsets[i]] = a[i];

```

如果这个元素被丢掉，就什么都不做。

注意不能让所有元素都写，因为被丢掉的元素可能和后面的保留元素拥有同一个 offset，这样会把正确结果覆盖掉。

最后由 0 号线程计算总元素数量。

### filter_stable

```cpp
void filter_stable(const float* a, float* out, int* count,
                   int* flags, int* offsets, int n,
                   cudaStream_t stream) {
    if (n <= 0) {
        cuda_check(cudaMemsetAsync(count, 0, sizeof(int), stream));
        return;
    }

    int block = 256;
    int grid  = (n + block - 1) / block;

    // ① 先判断哪些元素要保留
    mark_kernel<<<grid, block, 0, stream>>>(a, flags, n);
    cuda_check(cudaGetLastError());

    // ② 计算每个保留元素最终应该放到哪里
    thrust::exclusive_scan(thrust::cuda::par.on(stream),
                           flags, flags + n, offsets);

    // ③ 按照算好的位置写入输出数组
    scatter_kernel<<<grid, block, 0, stream>>>
        (a, out, flags, offsets, count, n);
    cuda_check(cudaGetLastError());
}

```

这个函数整体就是：

先标记，接着算位置，最后写结果。

因为三个步骤都放在同一条 CUDA stream 里，所以 GPU 会按照：

`mark → scan → scatter`

这个顺序执行，不需要我们在中间手动同步。

这种方法相比 `atomicAdd` 会多做几次内存读写，所以开销会稍微大一些。

但好处也很明显：

- 输出顺序和输入顺序一致
- 不需要用原子操作抢位置
- 结果是稳定、确定的

可以把它理解成一句话：

> `atomicAdd` 是“大家现场抢座位”，而 `scan + scatter` 是“提前给每个人分好座位，然后直接坐过去”。

## 4. GEMM Kernel

GEMM 在第一篇笔记里介绍过，它是深度学习的核心算子。<br>为了高效利用 L1、L2 cache，HPC 里有 loop tiling 的概念,把大循环切成小块，让每块的工作集能装进快速存储，反复使用后再换下一块。写 GPU kernel 时同样用这个思路，只是快速存储换成了片上的共享内存。

先看维度：假如A 是 $M \times K$，B 是 $K \times N$。A 的第 row 行与 B 的第 col 列逐项相乘再求和，得到 $C[row][col]$，所以 $C = A \times B$ 是一个 $M \times N$ 的矩阵。这里 A 的列数必须等于 B 的行数，这个共同的维度 K 就是每次点乘的长度，也是后面要切分的方向。

每个 block 负责 C 的一个 16×16 输出块，每个线程负责其中一个元素 `C[row][col]`。沿 K 方向每轮取 A、B 各一个 16×16 小块放进共享内存，block 内 256 个线程共用，用完再换下一批，`sum` 跨轮累加。

### 为什么 tile 取 16

**线程数**：16×16 = 256，是 warp（32 线程）的整数倍，`256 / 32 = 8`个 warp，不会浪费。

**Occupancy**：SM 的驻留上限通常是 2048 个线程、16~32 个 block。

| tile | 线程/block | 装满 2048 需要 | 是否可行 |
| --- | --- | --- | --- |
| 8×8 | 64 | 2048 / 64 = 32 个 block | 需占满 block 名额，实际常因共享内存、调度槽位等每-block 开销先耗尽而达不到；架构限 16 个 block 时更只能跑到 1024 线程 |
| 16×16 | 256 | 2048 / 256 = 8 个 block | 线程装满，block 名额还富余 |
| 32×32 | 1024 | 2048 / 1024 = 2 个 block | 线程数已顶到 block 1024 的上限，调度余地极小 |

block 数本身是有限资源。block 越小，装满线程所需的 block 越多，越容易先撞上 block 数上限(16-32)；而且每个 block 都要单独分配共享内存、占用调度槽位与 barrier 资源，这些固定开销随 block 数线性增长，实际能驻留的数量往往达不到理论值。

**复用次数 = tile 边长**。内层循环是 `for (i = 0; i < 16; ++i)`，每个搬进共享内存的元素被用 16 次：

```text
一轮中，一个 block 从全局内存读   256 线程 × 2 = 512 个元素
                 从共享内存读     256 线程 × 32 = 8192 次
                 复用率           8192 / 512 = 16
```

全局访存量降到约 1/16。取 8 只能降到 1/8，取 32 可降到 1/32。

**共享内存占用**：共享内存是 SM 上的固定资源，每个驻留的 block 都要分走一份，占得越多能同时驻留的 block 就越少。

```text
16×16：As + Bs = 2 × (16 × 16 × 4 字节) = 2 KB / block
32×32：As + Bs = 2 × (32 × 32 × 4 字节) = 8 KB / block
```

tile 边长翻倍，占用翻 4 倍。

**尾部浪费**：grid 向上取整开，线程总数通常比矩阵大，多出来的线程照样要加载、同步、跑完累加循环，只是最后被边界判断挡住。以 M = 100 为例：

| tile | block 数 | 覆盖行数 | 浪费 |
| --- | --- | --- | --- |
| 16 | ⌈100/16⌉ = 7 | 112 | 12 |
| 32 | ⌈100/32⌉ = 4 | 128 | 28 |

tile 越大，边缘浪费的线程越多。

### grid 的计算

`(N - 1) / 16 + 1` 是向上取整的整数除法，等价于 `ceil(N / 16.0)`。

### **循环展开（Loop Unroll）**：

次数在编译期固定的循环，可以用 `#pragma unroll` 让编译器展开成顺序执行的多条指令。好处有两个：一是省掉循环计数和分支；二是数组下标都变成编译期常量，编译器才能把 `sum[4][4]` 这类小数组整个放进寄存器，否则会退回到 local memory（实际在显存里）。

### 代码

```cpp
__global__ void tiled_kernel(const float* A, const float* B,
                             float* C, int M, int N, int K) {
    __shared__ float As[16][16], Bs[16][16];
    int tx = threadIdx.x, ty = threadIdx.y;
    int row = blockIdx.y * 16 + ty;   // tx 对应列，保证 warp 内相邻线程访问相邻地址
    int col = blockIdx.x * 16 + tx;
    float sum = 0;                    // 每个线程私有，跨轮累加

    for (int base = 0; base < K; base += 16) {
        // 每个线程搬 A、B 各一个元素：As 存 A[row][base..base+15]，Bs 存 B[base..base+15][col]
        // 越界填 0，乘加时不影响结果，也不必改内层循环边界
        int aCol = base + tx;
        int bRow = base + ty;
        As[ty][tx] = (row < M && aCol < K) ? A[row * K + aCol] : 0.0f;
        Bs[ty][tx] = (bRow < K && col < N) ? B[bRow * N + col] : 0.0f;

        __syncthreads();              // 等所有线程搬完，才能读别人搬进来的数据

        #pragma unroll
        for (int i = 0; i < 16; ++i)  // 本轮 16 对乘加，接着上一轮的 sum 继续累加
            sum += As[ty][i] * Bs[i][tx];

        __syncthreads();              // 等所有线程用完，下一轮才能覆盖 As、Bs
    }

    // 越界线程不能提前 return，否则 __syncthreads() 会等不到它，只在写回时判断边界
    // K == 0 时循环不执行，sum 保持 0，C 被写成 0
    if (row < M && col < N)
        C[row * N + col] = sum;
}

void gemm_tiled(const float* A, const float* B, float* C,
                int M, int N, int K, cudaStream_t stream) {
    if (M == 0 || N == 0) return;     // C 无元素，不启动；K == 0 仍需启动以写零
    // 向上取整：x 方向覆盖 N 列，y 方向覆盖 M 行；多出的线程由 kernel 内的边界判断挡住
    dim3 grid((N - 1) / 16 + 1, (M - 1) / 16 + 1);
    tiled_kernel<<<grid, dim3(16, 16), 0, stream>>>(A, B, C, M, N, K);
    cuda_check(cudaGetLastError());
}

```

### 补充：thread tiling 版本

### 基础版的瓶颈在哪

前面的 tiled kernel 里，内层循环长这样：

```text
sum += As[ty][i] * Bs[i][tx];
```

跑 16 轮，每轮从共享内存读 2 个数、做 1 次乘加。**读 32 次，才算 16 次。**

共享内存虽然比显存快，但也不是免费的。读两个数的时间足够做十几次乘加，结果只做了一次,计算单元大部分时间在等数据。瓶颈从显存转移到了共享内存，并没有真正解决。

### 思路：让一个线程算多个输出

看 C 里相邻的四个元素：

```text
C[r0][c0] = Σ A[r0][k]·B[k][c0]
C[r0][c1] = Σ A[r0][k]·B[k][c1]
C[r1][c0] = Σ A[r1][k]·B[k][c0]
C[r1][c1] = Σ A[r1][k]·B[k][c1]
```

`A[r0][k]` 出现了两次，`B[k][c0]` 也出现了两次。基础版里这四个输出归四个不同的线程管，所以 `A[r0][k]` 被**两个线程各从共享内存读了一遍**,重复了。

如果让**一个线程**同时算这四个，`A[r0][k]` 只需读进寄存器一次，两次乘加都用它。

推广到 4×4：

```text
读 a[0..3] + b[0..3] = 8 个数
做 4×4 = 16 次乘加
```

读的量只涨了 4 倍（2→8），算的量涨了 16 倍（1→16）。**访存计算比改善 4 倍。**

复用从“显存 → 共享内存”又往下沉了一层，变成“共享内存 → 寄存器”。

### 配置怎么定

block 仍然是 16×16 = 256 线程，每个线程算 4×4 个输出，所以一个 block 覆盖的 C 子块是：

```text
BM = blockDim.y × TM = 16 × 4 = 64
BN = blockDim.x × TN = 16 × 4 = 64
```

K 方向每轮仍推进 16（`BK = 16`）。于是每轮要搬的 tile 变成 64×16 和 16×64，各 1024 个元素,256 个线程每人搬 4 个。

### 代价：三个新问题

**一、寄存器压力**。16 个累加值必须待在寄存器里，加上临时变量，一个线程约 40-50 个寄存器。SM 上能驻留的线程数随之下降。而且这些累加值只有在**所有循环完全展开**时才会被放进寄存器,下标必须是编译期常量，否则会被塞进 local memory（实际在显存里），性能直接崩。所以代码里每个循环都加了 `#pragma unroll`，这不是优化，是方案成立的前提。

**二、bank conflict**。共享内存被分成 32 个 bank（设计上如此），可以理解成 32 个并排的小仓库。二维数组在里面是按行摊平存放的，一个元素在第几个仓库，就看它摊平后的位置对 32 取余：

```text
下标 = 行 × 每行长度 + 列
bank = 下标 % 32
```

同一个 warp 里，如果几个线程要去**同一个仓库拿不同的东西**，就只能排队，一个一个来。tile 变大后，有两个地方会排队：

- **写 `As` 时**：tid 0~3 分别写 `As[0][0]`、`As[4][0]`、`As[8][0]`、`As[12][0]`，摊平后是 0、256、512、768。每行 64 个元素，正好是 32 的倍数，所以同一列的元素不管在哪一行，都落在同一个仓库。这 4 个全在 bank 0，要排 4 次队。
- **读 `Bs` 时**：每个线程读 4 个连续元素，tx 号线程从第 `tx × 4` 列开始。16 个线程一共要 64 个元素，但仓库只有 32 个，必然有两个线程挤进同一个仓库。比如 tx=0 从第 0 列开始，tx=8 从第 32 列开始，32 % 32 = 0，两人都要去 bank 0。

**三、并行度**。一个 block 覆盖 64×64，M=N=128 时只开出 4 个 block，而我的机器有 78 个 SM。这一点下面详细说。

### 两处冲突的解法不一样

**As 的冲突：把存放位置错开**

先回忆搬 A 时每个线程在干什么：`aRow` 是它负责 A 的第几行，`kk` 是这一轮 16 个 k 里的第几个。因为 `As` 是转置存的，元素最终放在 `As[kk][aRow]`，也就是 **`kk` 是行号，`aRow` 是列号**。

tid 0~3 的 `aRow` 都是 0，`kk` 分别是 0、4、8、12，所以都存在第 0 列的不同行上。每行 64 个元素是 32 的倍数，同一列不管在哪一行都在同一个 bank，4 个线程全挤进 bank 0。

但它们只要 4 个位置，32 个 bank 完全放得下，只是挤在了一起。办法是**按行号给列号加个偏移**，让不同行的同一列错开：

```text
实际存放的列 = aRow ^ SWZ(kk)
SWZ(kk) 取值：kk 在 0~3 → 0，4~7 → 8，8~11 → 16，12~15 → 24
```

| tid | kk | 原来存到 | bank | 加偏移后存到 | bank |
| --- | --- | --- | --- | --- | --- |
| 0 | 0 | As[0][0] | 0 | As[0][0] | 0 |
| 1 | 4 | As[4][0] | 0 | As[4][8] | 8 |
| 2 | 8 | As[8][0] | 0 | As[8][16] | 16 |
| 3 | 12 | As[12][0] | 0 | As[12][24] | 24 |

4 个线程分到 4 个不同 bank，冲突消失。取数据时用同一个公式算位置就能找回来，因为同一个数异或两次等于没变。这种按行号打乱列位置的做法，叫做 **swizzle**。

偏移选 8 的倍数，是为了不打乱连续的 4 个元素。后面从 `As` 取数据时要一次取 4 个连续的，8 的倍数二进制末两位是 0，异或只改高位：

```text
列 4,5,6,7  ^ 8  →  12,13,14,15   仍连续
列 4,5,6,7  ^ 1  →   5, 4, 7, 6   顺序乱了
```

另一种常见做法是 padding（每行多留一格，64 改 65），也能错开 bank，但第 1 行的起点变成第 65 个元素、字节地址 260，不是 16 的倍数，一次取 4 个就不行了。

**Bs 的冲突：分批读取**

这里加偏移没用：16 个线程每人读 4 个，一共要 64 个不同元素，bank 只有 32 个，怎么排都至少有两个线程抢同一个 bank。

办法是让每个线程**一次读 4 个 float**，CUDA 里用 `float4` 类型表示。共享内存一个周期最多给 32 个 bank × 4 字节 = 128 字节，而这样读一个 warp 要 512 字节，一次给不完，硬件会自动拆成 4 批，每批 8 个线程：

| 批次 | 线程 | 读的列 | 用到的 bank |
| --- | --- | --- | --- |
| 1 | tx 0~7 | 0~31 | 0~31，各一次 |
| 2 | tx 8~15 | 32~63 | 0~31，各一次 |

每批正好 32 个元素铺满 32 个 bank。原本会撞的 tx=0 和 tx=8 分在不同批次，不在同一时刻抢，也就不冲突了。

所以总的来说：一个一个读要 4 次、每次 2 路冲突，共 8 个周期；一次读 4 个只要 1 次、拆成 4 批，共 4 个周期。

### 代码

```cpp
#define BM 64   // 一个 block 负责 C 的 64 行 = blockDim.y(16) × TM(4)
#define BN 64   // 一个 block 负责 C 的 64 列 = blockDim.x(16) × TN(4)
#define BK 16   // K 方向每轮推进 16
#define TM 4    // 每个线程负责 4 行
#define TN 4    // 每个线程负责 4 列

// 逻辑位置 (kk, c) 实际存到物理位置 (kk, c ^ SWZ(kk))，SWZ 取值 {0,8,16,24}。
// 全是 8 的倍数，低 2 位恒为 0 —— 异或不打乱连续的 4 个元素，float4 仍可用。
#define SWZ(kk) ((((kk) >> 2) & 3) << 3)

__global__ void tiled4x4_kernel(const float* A, const float* B,
                                float* C, int M, int N, int K) {
    // As 转置存放（[k][row] 而非 [row][k]）：这样内层读 As[k][...] 的地址只跟 ty 有关，
    // 同 ty 的 16 个线程读同一地址 → 硬件广播，不算冲突。
    // __align__(16) 保证首地址 16 字节对齐，float4 访问的前提。
    __shared__ __align__(16) float As[BK][BM];
    __shared__ __align__(16) float Bs[BK][BN];

    int tx = threadIdx.x, ty = threadIdx.y;
    int tid     = ty * 16 + tx;          // 0..255，block 内的线性编号
    int rowBase = blockIdx.y * BM;       // 本 block 负责的 C 起始行
    int colBase = blockIdx.x * BN;       // 起始列

    // 16 个累加器。必须完全展开循环，下标才是编译期常量、才能放进寄存器；
    // 否则会被放到 local memory（实际在显存），性能崩掉。
    float sum[TM][TN];
    #pragma unroll
    for (int i = 0; i < TM; ++i)
        #pragma unroll
        for (int j = 0; j < TN; ++j) sum[i][j] = 0.0f;

    // 加载分工：tile 是 64×16 和 16×64，各 1024 个元素，256 线程每人搬 4 个。
    // 除数 = 每行需要几个线程：A 的 tile 有 64 行 → 256/64 = 4；B 的有 16 行 → 256/16 = 16。
    // 相邻 tid 读同一行的相邻位置，保证全局内存访问合并。
    int aRow = tid / 4,  aCol = (tid % 4) * 4;    // A：0..63 行，每人 4 列
    int bRow = tid / 16, bCol = (tid % 16) * 4;   // B：0..15 行，每人 4 列

    for (int base = 0; base < K; base += BK) {
        // 搬 A：转置 + swizzle。4 个元素写的是 As 的 4 个不同行，地址不连续，无法向量化。
        // 不加 swizzle 的话 tid=0,1,2,3 都写物理列 0，地址间隔 64 → 全落 bank 0 → 4 路冲突。
        #pragma unroll
        for (int i = 0; i < 4; ++i) {
            int kk = aCol + i;
            int r  = rowBase + aRow, c = base + kk;
            As[kk][aRow ^ SWZ(kk)] = (r < M && c < K) ? A[r * K + c] : 0.0f;
        }
        // 搬 B：先在寄存器里凑齐 4 个（逐个做边界检查），再一次 float4 写入。
        // bCol 是 4 的倍数 → 字节地址是 16 的倍数 → 对齐满足。
        // Bs 不转置也不 swizzle：写入本来就连续且铺满 bank，且行距保持 64 才能用 float4。
        {
            float4 t;
            int r = base + bRow;
            t.x = (r < K && colBase + bCol + 0 < N) ? B[r * N + colBase + bCol + 0] : 0.0f;
            t.y = (r < K && colBase + bCol + 1 < N) ? B[r * N + colBase + bCol + 1] : 0.0f;
            t.z = (r < K && colBase + bCol + 2 < N) ? B[r * N + colBase + bCol + 2] : 0.0f;
            t.w = (r < K && colBase + bCol + 3 < N) ? B[r * N + colBase + bCol + 3] : 0.0f;
            *reinterpret_cast<float4*>(&Bs[bRow][bCol]) = t;
        }
        __syncthreads();                 // 等所有人搬完

        #pragma unroll
        for (int k = 0; k < BK; ++k) {
            // 读 As：存的时候 swizzle 了，读的时候用同样的变换取回（异或是自己的逆运算）。
            // SWZ 不动低 2 位，所以这 4 个元素在物理上仍连续，可以一次 float4 读出。
            float4 av = *reinterpret_cast<const float4*>(&As[k][(ty * TM) ^ SWZ(k)]);
            // 读 Bs：用 float4 是为了消除 bank conflict —— 标量版里 tx=0(元素0) 和 tx=8(元素32)
            // 会撞 bank 0；float4 让 warp 请求 512 字节，超过 128 字节/周期的上限，
            // 硬件拆成 4 个 phase、每 phase 8 个线程，两者自然分到不同周期。
            float4 bv = *reinterpret_cast<const float4*>(&Bs[k][tx * TN]);
            float a[TM] = {av.x, av.y, av.z, av.w};
            float b[TN] = {bv.x, bv.y, bv.z, bv.w};

            // 外积：读 8 个数做 16 次乘加。a[i] 读进寄存器一次，参与该行 4 个输出的计算 ——
            // 这就是复用从共享内存下沉到寄存器的地方。
            #pragma unroll
            for (int i = 0; i < TM; ++i)
                #pragma unroll
                for (int j = 0; j < TN; ++j)
                    sum[i][j] += a[i] * b[j];
        }
        __syncthreads();                 // 等所有人用完，下一轮才能覆盖
    }

    // 16 个结果各自算出全局坐标后写回。边界判断只能放在这里：
    // 循环里有 __syncthreads()，越界线程若提前 return，其他线程会永远等不到它。
    #pragma unroll
    for (int i = 0; i < TM; ++i) {
        #pragma unroll
        for (int j = 0; j < TN; ++j) {
            int r = rowBase + ty * TM + i;
            int c = colBase + tx * TN + j;
            if (r < M && c < N) C[r * N + c] = sum[i][j];
        }
    }
}

```

### 实测

| M=N=K | naive | tiled | tiled4x4 | tiled/tiled4x4 |
| --- | --- | --- | --- | --- |
| 128 | 0.008992 | 0.007296 | 0.012128 | 0.602 |
| 256 | 0.019168 | 0.015104 | 0.019168 | 0.788 |
| 1024 | 0.688032 | 0.456768 | 0.181152 | 2.521 |

### 为什么小尺寸下更慢

一个 block 只能跑在一个 SM 上（block 内要共享 shared memory、要 `__syncthreads()`，跨 SM 做不到）。所以 block 数决定了能用上几个 SM：

```text
block 数 = ⌈M / BM⌉ × ⌈N / BN⌉
```

tiled4x4 的 BM/BN 是 tiled 的 4 倍，block 数就少 16 倍：

| M=N | tiled (BM=16) | tiled4x4 (BM=64) |
| --- | --- | --- |
| 128 | 64 个 | 4 个 |
| 256 | 256 个 | 16 个 |
| 1024 | 4096 个 | 256 个 |

我的机器有 78 个 SM，一个 block 只能跑在一个 SM 上，所以 block 数决定了能用上几个 SM。

**128 时：比的是能用上多少 SM**

tiled4x4 每个 block 负责 64×64，128×128 只切得出 2×2 = 4 个 block，只有 4 个 SM 在干活，74 个闲着。tiled 每个 block 负责 16×16，能切出 8×8 = 64 个，用上 64 个 SM。硬件用得多的一方自然快，tiled4x4 单个线程效率再高也补不回来。

**1024 时：两边 SM 都用满了，比的是干同样的活要搬多少数据**

tiled4x4 有 16×16 = 256 个 block，平均每个 SM 三四个，已经没有闲着的 SM。tiled 有 4096 个，但每个 SM 最多同时跑 8 个，多出来的只能排队，并不会更快。

硬件都用满之后，差距来自数据搬运量：

- **共享内存**：tiled 每做 1 次乘加要从共享内存读 2 个数；tiled4x4 读 8 个数能做 16 次乘加，平均只读 0.5 个。少 4 倍。
- **显存**：每个 block 要从显存加载自己用到的 A 的那几行、B 的那几列。tiled 的一个 block 用到 A 的 16 行、B 的 16 列；tiled4x4 用到 A 的 64 行、B 的 64 列。同一行 A 会被这一排上的每个 block 各加载一次：N = 1024 时，tiled 一排有 1024 / 16 = 64 个 block，要加载 64 次；tiled4x4 一排只有 1024 / 64 = 16 个，加载 16 次。B 的列同理，重复读取少 4 倍。

重复读取的数据少了，同样的计算就更快完成，所以 1024 时 tiled4x4 反超 2.5 倍。

**总结**：block 数不够填满 SM 时，拼的是并行度；填满之后，拼的是访存效率。tiled4x4 的 block 大，小尺寸下输在前者，大尺寸下赢在后者。

同一份代码在 128 下慢 40%、在 1024 下快 152%，说明 BM/BN/TM/TN 没有通用最优解：tile 大则单线程访存效率高但 block 少、SM 填不满，tile 小则并行度够但复用少，最优点取决于 M、N、K 和 SM 数量。

PS: 所以实际的库会同时保留多种配置：CUTLASS 把 tile 形状做成模板参数（如 `GemmShape<128, 128, 8>`），由使用者借助 cutlass_profiler 针对具体尺寸测速、按 GFLOP/s 排序后选定；cuBLAS 则在内部按问题尺寸和架构自动挑选，也可以通过 cuBLASLt 的 `cublasLtMatmulAlgoGetHeuristic` 拿到候选算法自行测速。这里的 `tiled` 和 `tiled4x4` 就相当于两种配置，要在所有尺寸上都快，就需要按 M、N、K 分发到合适的那个（这就是Kernel的魅力之一）。
