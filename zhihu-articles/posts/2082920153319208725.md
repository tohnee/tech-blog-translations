### 执行摘要

LLM 网关（也称 AI Gateway）作为大模型应用基础设施的核心组件，格局在 2026 年下半年发生了剧烈重组。传统市场分为三大阵营：以 LiteLLM、Bifrost、New-API 为代表的开源自托管阵营，以 OpenRouter、Portkey、Helicone 为代表的托管 + 开源混合阵营，以及以 Cloudflare AI Gateway、Kong、APISIX、Envoy AI Gateway 为代表的传统基础设施厂商延伸阵营。除此之外，本报告 6 月版完全遗漏、但截至 9 月星标总量已经 **超过传统网关之和** 的第四类，是 coding-agent 路由与 token 压缩代理：headroom（72.0k）、OmniRoute（65.9k）、CLIProxyAPI（51.7k）、sub2api（41.5k）、claude-code-router（37.2k）、9router（28.7k）。

与 6 月版相比，本期最重要的变化有四点。

第一， **独立网关中间层大面积整合** ：TensorZero 于 6 月 11 日归档仓库（公司关停），Pydantic AI Gateway 并入 Logfire，Helicone 被 Mintlify 收购，Portkey 被 Palo Alto Networks 收购，OpenRouter 于 8 月 19 日被 Stripe 宣布收购（外媒口径 > 70 亿美元）。这些事件共同说明，“一家公司只做一个独立网关”的商业叙事在 2026 年正在被两端挤压。

第二， **云原生与 Agent 网关确立为独立赛道** ：Envoy AI Gateway 于 6 月 23 日达到 v1.0 GA，是首个 CNCF 背书、生产稳定的开源 AI 网关；Higress、kgateway 补齐 AI 原生 K8s 位置；agentgateway、Plano 等专做 Agent 与 MCP 流量的治理。

第三， **性能叙事回归理性，缓存保真度成为新考点** ：第三方 llm-gateway-bench 实测每请求网关开销为 Bifrost 0.62 ms、Portkey 2.65 ms、LiteLLM 5.83 ms，与厂商“微秒级”宣称存在数量级差；同时“网关是否透传 prompt-cache 折扣”（fidelity，缓存保真度）成为账单上的隐性成本。

第四， **国内格局换代** ：New-API（仓库迁移至 QuantumNous/new-api）星标 48.1k 已反超 One-API 36.9k，后者基本停更；Higress、GPT-Load、sub2api、one-hub、metapi 等按细分场景补位。

### 一、LLM 网关的核心能力矩阵

一个成熟的 LLM 网关通常覆盖以下能力维度：

| 能力域 | 具体功能 |
| --- | --- |
| 统一接入 | 将不同提供商的 API 归一化为 OpenAI 兼容格式 |
| 智能路由 | 按成本 / 延迟 / 可用性自动选择模型，支持 fallback 和负载均衡 |
| 可观测性 | 请求日志、成本追踪、延迟监控、Token 用量统计 |
| 安全防护 | 内容审核、Prompt 注入检测、速率限制、API Key 管理 |
| 缓存加速 | 精确匹配缓存 + 语义缓存，减少重复调用 |
| 治理合规 | 预算控制、租户隔离、SOC2 / HIPAA 合规 |

与传统 API 网关的差异在于：LLM 网关需要处理 Token 级限流、双向内容过滤（Prompt / Response）、动态多模型路由、语义缓存、RAG 集成以及 Agent 工作流支持 [1]。

本期新增一个 6 月版未提及、但被反复验证的隐性维度：缓存保真度（fidelity）。第三方基准发现，请求经过网关后，厂商侧的 prompt-cache（提示词缓存）折扣经常静默失效，用户以为省了钱、实际并未享受。它直接抵消“网关省钱”这一核心卖点，选型时需专门核验 [4][17]。

### 二、开源 LLM 网关详细分析

本节覆盖 6 月版原有的 8 个开源网关（2.1 ~ 2.8），并在 2.9 ~ 2.12 补齐本期新增的三条主流线（K8s / CNCF 原生、Agent / MCP 治理、国内 AI 原生），最后用一个合并小节收纳其他值得关注的方案。

### 2.1 LiteLLM（BerriAI）

GitHub: 58.7k ⭐（6 月为 48.9k，半年 + 20%）| MIT（核心）+ 企业版双许可 | Python 最新版本: v1.100.1（2026-09-10）

定位: 最成熟的开源 LLM 网关，提供 SDK + Proxy Server 两种形态。

核心特性：支持 100+ 模型提供商，统一 OpenAI 格式接口；预算控制，按用户 / 项目 / Key 维度做额度管理；虚拟 Key 管理、自动重试与故障转移；与 Langfuse、Arize、Helicone 等观测工具集成。

优势：生态最完善，提供商覆盖面最广，Python 团队天然友好，社区活跃度最高 [2][3]。

局限：Python 运行时在高并发下仍会退化。第三方独立基准测得单请求网关开销约 5.83 ms，在三款主流自托管网关中最重，约为 Bifrost 的 10 倍 [17]；生产部署需额外配置 Redis + PostgreSQL；可观测性依赖第三方集成 [4][5]。

适用场景：原型验证、内部工具、中等流量的 Python 技术栈。

### 2.2 Bifrost（Maxim AI）

GitHub: 8.0k ⭐（6 月为 5.4k，半年 + 49%）| Apache 2.0 | Go 最新版本: v2.1.1（2026-09-09，已改为按模块发布：transports / plugins / ent 等）

定位: 高性能 LiteLLM 替代品，面向生产级高流量场景。

核心特性：厂商口径网关开销 < 100 μs @ 5k RPS、宣称比 LiteLLM 快约 50 倍；厂商口径支持 1000+ 模型；内置自适应负载均衡、语义缓存、按租户预算；原生可观测性（实时 UI、OpenTelemetry、Prometheus）；内置 MCP 网关支持。第三方独立基准实测网关开销约 0.62 ms，为三款自托管网关中最低，但仍高于厂商“微秒级”宣称 [17]。

优势：Go 语言架构在性能上显著优于 Python 方案，“治理、可观测性、可靠性不是附加功能而是内置能力” [4][6]。半年星标增速为开源头部网关中最快之一。

局限：支持的利基提供商数量不如 LiteLLM，社区规模相对较小；模块化发布（plugins / transports / ent）后版本语义趋复杂。

适用场景：高流量生产系统、对延迟敏感的场景、需要强治理能力的团队。

### 2.3 One-API（songquanpeng）

GitHub: 36.9k ⭐（6 月为 34.5k）| MIT | Go 最新版本: v0.6.10（2025-02-02，仓库最后推送 2026-01）

定位: 国内最早流行的开源 LLM API 管理与分发系统。

核心特性：统一接入 OpenAI、Azure、Anthropic Claude、Google Gemini、国内各大模型；模型映射 / 重定向；Token 额度管理、多租户支持；Docker 一键部署，轻量级。

优势：国内社区影响力大，Go 语言性能优秀，部署简单 [7][8]。

局限：维护活跃度实质性下降，正式版本一年多未更新；功能仍聚焦 API 分发，缺少语义缓存、高级路由等企业级能力；市场地位已被增强分支 New-API 反超（见 2.4）。

适用场景：个人 / 小团队统一管理多个 LLM API Key，将大模型能力封装为 OpenAI 格式对外提供服务。

### 2.4 New-API（QuantumNous/new-api，原 Calcium-Ion）

GitHub: 48.1k ⭐ | AGPL-3.0 | Go 最新版本: v1.0.0-rc.37（2026-09-11，发布节奏为每周多版） 备注: 仓库已迁移至 QuantumNous/new-api，旧路径 Calcium-Ion/new-api 通过 GitHub 重定向。

定位: One-API 的增强分支，本期已成为国内生态事实上的头部方案。

核心特性：在 One-API 基础上改进 UI 和性能；增加对 Midjourney 等图像模型的支持；更好的渠道管理、代理与 CNY 计费支持；已扩展为“unified AI model hub”，兼容 OpenAI / Claude / Gemini 通道，面向“国内模型 + 团队额度 + 计费面板”场景。

优势：星标（48.1k）已反超 One-API（36.9k），且处于高速迭代中，是 6 月到 9 月国内网关格局最显著的变化 [9][18]。

局限：与 One-API 面临类似的代理 / 性能问题；AGPL-3.0 对二次分发和商用有传染性约束；社区分化，长期维护方向仍需观察。

适用场景：需要 One-API 功能但要求更好 UI、更广模型覆盖与活跃维护的团队。

### 2.5 Portkey Gateway

GitHub: 13.0k ⭐（6 月为 11.9k）| MIT | TypeScript / Node.js 最新版本: v1.15.2（2026-01-12，仓库最后推送 2026-05-25）

定位: 全栈 LLMOps 平台的开源网关组件。2026 年 5 月 29 日，Portkey 被 Palo Alto Networks 收购，现为该安全平台的控制面 [19]。

核心特性：厂商口径路由至 1,600+ LLM、支持 45+ 提供商；内置 Guardrails（内容审核护栏）；SOC2 Type 2、ISO 27001、GDPR、HIPAA 合规；语义缓存、智能路由、负载均衡。第三方独立基准实测网关开销约 2.65 ms，且缓存保真度偏弱（fidelity 1/3）[17]。

优势：网关组件开源且轻量，企业级合规能力突出，被安全厂商收购后合规与护栏能力有望进一步加强 [3][5]。

局限：完整可观测性与治理功能需付费托管；被收购后开源路线图存在不确定性，需持续观察。

适用场景：需要合规认证的企业，或对内容安全有严格要求的场景。

### 2.6 Helicone AI Gateway

GitHub: 628 ⭐（ai-gateway 仓库，6 月约 593；主仓库 Helicone/helicone 6.2k ⭐）| GPL-3.0 | Rust 最新版本: 无正式 release 标签（ai-gateway 仓库最后推送 2025-11）

定位: 以可观测性为核心的轻量级开源网关。母公司 Helicone 于 2026 年 3 月被 Mintlify 收购，主仓库仍在提交，但 ai-gateway 子仓库进入低维护 / 维护模式 [19]。

核心特性：支持 100+ 模型，统一 OpenAI API；Rust 架构（厂商口径 P95 < 5 ms）；智能路由、速率限制、缓存；自动请求日志和成本追踪、故障转移。

优势：Rust 架构保证较低延迟；日志与成本追踪是每请求默认行为，无需额外配置 [5][10]。

局限：被收购后 roadmap 风险上升，网关子仓库更新停滞；评估与评分能力有限；云托管定价随请求量增长。

适用场景：对可观测性有强需求、可接受维护风险的个人与小团队。

### 2.7 TensorZero（已归档）

GitHub: 11.7k ⭐ | Apache 2.0 | Rust 最新版本: 2026.6.0（仓库已于 2026-06-11 归档，archived=true，转为只读）[19]

定位: 开源 LLMOps 平台，强调反馈循环驱动的模型优化。6 月版将其列为“范式级新星”，本期需重点提示：项目本体已停止维护，公司关停。

核心特性：统一网关、可观测性、评估、优化一体化；自适应 A/B 测试路由（基于反馈信号动态优化模型选择），创建“请求→反馈→优化”闭环。

优势：相比静态路由规则，TensorZero 率先把机器学习驱动的路由优化产品化，思路影响了一批后续方案 [11]。Apache-2.0 代码与 fork 仍可自取。

局限：不再接受新贡献与修复；生态集成不如 LiteLLM；不建议新项目直接采用，可参考其设计或选用活跃 fork。

适用场景：仅作架构参考；需要反馈驱动路由的活跃团队应评估其延续项目或自建。

### 2.8 Apache APISIX（AI Gateway 扩展）

GitHub: 17.1k ⭐（6 月为 16.7k）| Apache 2.0 | Lua / Go 最新版本: 3.18.0（2026-08-20）

定位: 云原生 API 网关的 AI 能力扩展。

核心特性：安全，Token 级速率限制、Prompt 注入防护；可观测性，用量追踪、日志集成；Prompt 工程，RAG 支持、动态上下文构建；可靠性，多 LLM 负载均衡、重试；与 APISIX 现有 ai-proxy / ai-proxy-multi 插件生态无缝集成。

优势：对已有 APISIX 部署的团队是零摩擦延伸；企业级 API 治理能力成熟；完全开源 [1][12]。

局限：AI 专属功能（语义缓存、高级 Guardrails）相比专用 LLM 网关仍有差距。

适用场景：已使用 APISIX 作为 API 网关，希望渐进式增加 AI 能力的团队。

### 2.9 Envoy AI Gateway（本期新增，CNCF 线代表）

GitHub: 2.1k ⭐ | Apache 2.0 | Go 最新版本: v1.1.0（2026-08-21），v1.0 GA 于 2026-06-23 发布

定位: CNCF 生态首个生产稳定的开源 AI 网关，构建在 Envoy Gateway 之上，由 Tetrate 与 Bloomberg 支持 [18][21]。

核心特性：Kubernetes Gateway API 原生，通过 InferencePool / AIGatewayRoute CRD 声明式路由；LLM 提供商统一接入、token 级限速、成本可观测；后端可指向自托管 vLLM 或云厂商 API；与 Envoy 插件生态（认证、限流、mTLS）天然集成。

优势：唯一由 CNCF 项目（Envoy Proxy / Envoy Gateway）背书、进入 v1.0 的开源 AI 网关，对已使用 Envoy Gateway 的团队是零摩擦延伸 [18][21]。

局限：星标数仍偏小（2.1k），生态集成不如 LiteLLM / Kong 成熟；需要 K8s 与 Gateway API 基础设施。

适用场景：企业级 K8s 原生部署、已有 Envoy / Istio 生态的团队。

### 2.10 agentgateway（本期新增，Agent / MCP 治理线代表）

GitHub: 4.8k ⭐ | Apache 2.0 | Rust 最新版本: 高频迭代，2026-09-14 仍在推送

定位: Linux Foundation 项目（非 CNCF），聚焦 Agent 与 MCP 流量的治理、鉴权与可观测，是该品类增长最快的代表 [18][22]。

核心特性：MCP（Model Context Protocol）治理与 A2A（Agent-to-Agent）通信；Identity-aware 访问策略；对 Agent→工具→模型的完整链路做统一鉴权与审计；单 Rust 二进制部署。

优势：在“模型路由”之外，把 Agent 与 MCP 流量视作一等公民；与 Hermes、LangGraph 等 agent 生态直接对接 [18][22]。

局限：品类新，标准仍在演化（MCP / A2A）；企业案例积累有限。

适用场景：正在建设 AI Agent 平台、需要治理工具调用与多 Agent 流量的团队。

### 2.11 Higress（阿里，本期新增，国内 AI 原生线代表）

GitHub: 9.4k ⭐ | Apache 2.0 | Go 最新版本: 活跃维护（2026-09-11 推送）

定位: 阿里开源的 AI 原生云原生网关，基于 Envoy / Istio，K8s / Ingress 生态友好 [18]。

核心特性：通义、DeepSeek 等国内模型一等公民支持；企业级治理、MCP 支持；提供 higress.ai 托管版；与阿里云 API Gateway 生态打通。

优势：国内企业级 K8s 场景的重要新选项，兼具 Envoy 生态与国内模型接入能力。

局限：文档双语但海外案例较少；在阿里云生态内使用最顺畅。

适用场景：国内企业、阿里云客户、K8s 原生团队。

### 三、Coding-agent 路由与 token 压缩代理（本期新增品类）

严格讲，这一类不完全是“LLM 网关”：headroom 是压缩代理、claude-code-router 与 OmniRoute 面向编码 CLI、sub2api 与 9router 做订阅池化。但截至 2026-09，它们星标总量已经超过本报告传统网关之和，且直接改变开发者选型行为。6 月版完全遗漏，本期补齐。

> ToS 风险说明（本报告 ⚠️ 标记的含义）：Claude Pro / Max、ChatGPT Plus、Gemini Advanced 等面向个人的编码订阅，其服务条款（Terms of Service，ToS）通常约定“仅限单人使用、不得作为 API 二次分发、不得用于服务化转售”。下列部分工具的技术本质是把订阅背后的 OAuth token 池化后，再暴露为 OpenAI 兼容 API 供多人 / 程序调用。技术上跑得通，但按提供商单方面认定的规则属于违约使用，后果包括账号封禁、订阅费不退、API Key 拉黑，甚至波及同支付卡 / 同 IP 下的其他账号。选型时“能不能用”和“敢不敢用”要分开看：自建生产系统、对外提供服务，不要押在 ⚠️ 项目上；纯粹个人折腾、随时可能被封也能接受，再考虑。品类中相对安全的方案是仅做端点转发、不池化订阅凭证的 claude-code-router（BYOK 路线）。

### 3.1 headroom（headroomlabs-ai/headroom）

GitHub: 72.0k ⭐ | Apache 2.0 | Python | 2026-09-13 推送

定位: token 压缩代理（compression proxy），不是路由器而是上下文瘦身工具。目标是在不改模型 / 提供商的前提下，通过压缩上下文体积直接压账单价钱。是本期增速最快、星标最高的“网关相关”方案，也是唯一无 ToS 风险的品类头部。

### 3.2 OmniRoute ⚠️（diegosouzapw/OmniRoute）

GitHub: 65.9k ⭐ | MIT | TypeScript | 2026-09-12 推送

定位: 跨 231+ 提供商的 coding-agent token 节省路由，依赖编码订阅池化。⚠️ 提供商 ToS 风险自担。

### 3.3 CLIProxyAPI ⚠️（router-for-me/CLIProxyAPI）

GitHub: 51.7k ⭐ | MIT | Go | 活跃维护

定位: 把 Claude Code、Codex 等编码 CLI 订阅封装为标准 API 端点，便于二次分发。⚠️ 与提供商 ToS 冲突风险显著。

### 3.4 sub2api ⚠️（Wei-Shaw/sub2api）

GitHub: 41.5k ⭐ | LGPL-3.0 | Go | 活跃维护

定位: 国内生态里“订阅账户池化到一个端点”的代表方案。⚠️ 同类 ToS 风险。

### 3.5 claude-code-router（musistudio/claude-code-router）

GitHub: 37.2k ⭐ | MIT | TypeScript | 2026-09-14 推送

定位: 把 Claude Code / 各类 Agent CLI 路由到任意提供商与模型。零封号记录，主打自带 Key 的合规路由（BYOK），被 awesome-ai-gateway 列为“cut Claude Code / Cursor bill without a ban”的推荐方案 [18]。

### 3.6 9router ⚠️（decolua/9router）

GitHub: 28.7k ⭐ | MIT | JavaScript

定位: BYOK 本地代理，订阅→便宜→免费三级 fallback。⚠️ 池化订阅部分同样存在 ToS 风险。

### 3.7 opencodex（lidge-jun/opencodex）

GitHub: 14.6k ⭐

定位: 把 Codex 的 Responses API 翻译到任意提供商，是 coding-agent 品类里的协议适配层。

### 四、托管 / 商业化 LLM 网关（含开源组件）

本节 4.1 ~ 4.4 是 6 月版原有方案，4.5 Vercel AI Gateway 与 4.6 云厂商自带网关为本期新增。

### 4.1 OpenRouter

非开源 | 管理化服务。2026 年 8 月 19 日，Stripe 宣布收购 OpenRouter（外媒口径 > 70 亿美元，官方未披露条款），双方承诺产品与 API 暂不变 [19][20]。

模型覆盖: 厂商口径 300 ~ 500+ 模型，独立清单统计活跃模型约 340 个（口径差异见来源）[5][18]。 定价: 按 Token 付费，无月费，平台收取约 5.5% 的充值手续费。

核心特性：单一 API Key 访问全部模型；自动故障转移；路由变体（按速度 / 成本优化）；预付费充值模式。

优势：模型覆盖最广的托管服务之一，零运维 [5]。

局限：无自托管；无内置可观测性、评估或追踪工具；无 BYOK（自带 Key）；被 Stripe 收购后定价与政策存在中期不确定性。

适用场景：零运维、最大模型覆盖，且能接受手续费与供应商锁定。

### 4.2 Cloudflare AI Gateway

非开源 | 边缘网络服务。 定价: 所有套餐可用，核心功能免费，按 Workers 用量计费；对自带 Key 场景 0% 加价。

核心特性：统一模型接口；边缘缓存（利用全球网络）；重试、速率限制、分析；与 Workers 深度集成。

优势：边缘网络实现极低延迟缓存；对已用 Cloudflare 的团队集成成本极低；自带 Key 不加价是本期对抗 OpenRouter 手续费的主要卖点 [4][13][18]。Cloudflare 也是唯一在所有套餐免费提供 SSO 的主流厂商 [18]。

局限：Cloudflare 生态锁定；支持的提供商有限。

适用场景：已使用 Cloudflare、追求 0 加价与边缘低延迟的团队。

### 4.3 Kong AI Gateway

GitHub: 44.1k ⭐（Kong 主仓库，6 月为 43.5k）| Apache 2.0（核心）| Lua / Go 最新版本: 3.9.3（2026-06-17） 定价: 企业计划按服务计费，约 105 美元 / 服务 / 月 + 用量费。

核心特性：60+ AI 功能插件（AI 可观测性、语义搜索等）；统一 LLM API；与 Kong 现有治理模型和安全策略一致；审计日志等能力多在企业 / 托管档（“SSO tax”）。

优势：对已有 Kong 部署的团队是自然延伸；企业级 API 治理成熟 [4][14]。

局限：部署较重；假设团队已熟悉 Kong 生态；审计 / SSO 等治理功能多为付费档。

适用场景：企业级 K8s + 审计合规场景，且已有 Kong 或计划引入统一 API 治理。

### 4.4 LLM Gateway（ [http://llmgateway.io](http://llmgateway.io) ）

开源 | AGPLv3（GitHub 标记为 “Other”）| TypeScript / Python GitHub: 1.63k ⭐（6 月约 1.3k）| 最新版本: v1.17.0（2026-09-14，迭代活跃）

核心特性：300+ 模型；BYOK（无加价）；Redis 缓存、故障转移、Guardrails。

优势：真正的开源且无 Token 加价，适合成本敏感场景 [3]。

局限：社区规模小，功能成熟度不及头部方案。

适用场景：成本敏感、希望自托管且自带 Key 的小团队。

### 4.5 Vercel AI Gateway（本期新增）

非开源 | 托管。

定位: Next.js / AI SDK 生态的默认选择，已 GA。

核心特性：0% 加价（自带 Key）、可选 ZDR（Zero Data Retention，零数据保留）、与 AI SDK 原生集成。

优势：对 AI SDK 用户零配置，自带 Key 不加价 [18]。

局限：SSO 等治理功能需要 300 美元 / 月的付费档（“SSO tax” 最明确的厂商）；模型覆盖与生态锁定于 Vercel。

适用场景：Next.js / AI SDK 团队、追求 0 加价托管。

“已在某一片云”的团队，主流云厂商的原生 AI 网关已经能给出可用答案：

共性优势：与已有 IAM、审计、成本中心、SLA 一体化，是最短的“合规过审 + 快速上线”路径。共性局限：跨云迁移成本高、模型选择受限于自家 catalog。

### 七、选型建议

按场景推荐：

- 快速原型 / 个人项目：LiteLLM 或 New-API。前者提供商覆盖最广、开箱即用；后者已取代 One-API 成为国内开发者首选，部署简单且维护活跃。
- 生产级高流量系统：Bifrost。Go 架构在高并发下最稳，第三方实测开销最低（0.62 ms），治理 / 可观测 / 可靠性内置。
- 企业合规场景：Portkey（合规体系完整，注意已被 Palo Alto 收购带来的路线图风险）或 Kong / Higress / kgateway / Envoy AI Gateway（企业 K8s + 审计）。
- 可观测性优先：Helicone（每请求自动日志 + 成本追踪），但需接受被收购后的维护风险；更稳妥可考虑 LiteLLM / Bifrost 内置可观测，或 MLflow AI Gateway（MLflow 生态）。
- K8s / 云原生原生治理：Envoy AI Gateway（首个 CNCF v1.0）、kgateway、Higress。
- 治理 AI Agent 与 MCP 流量：agentgateway，或已内置 MCP 的 Bifrost、Plano / Archgw。
- 削减 Claude Code / Cursor 成本：优先选 claude-code-router（BYOK 合规路线，零封号记录）；不想改模型只想压 token：headroom（无 ToS 风险）；池化订阅最激进的 OmniRoute / CLIProxyAPI / sub2api / 9router，需自担 ⚠️ ToS 风险。
- 已有 API 网关基础设施：Kong 或 APISIX，在现有网关叠加 AI 能力。
- 已在某一片云：优先选原生云厂商网关（AWS Bedrock / Azure APIM / Vertex + Apigee / Databricks / 腾讯云 / 火山引擎），合规过审最快。
- 零运维、最大模型覆盖：OpenRouter（单一 Key 覆盖数百模型），但需接受手续费、无自托管，以及被 Stripe 收购后的中期变化。
- 追求 0 加价托管：Cloudflare AI Gateway 或 Vercel AI Gateway（自带 Key 不加价）。
- 统一客户端 library（无需网络 hop）：aisuite（吴恩达）。
- 推理层 KV-cache 感知路由：NVIDIA Dynamo（数据中心自托管）。

### 八、行业趋势观察

- **整合是本期主旋律** ：独立网关中间层被两端挤压。云厂商在下方原生内置路由与花费上限，coding-agent 在上方长出更快增长的新一类网关；真正收缩的是“整家公司只做一个独立网关”的中间层。半年内：TensorZero 归档、Pydantic AI Gateway 并入 Logfire、Helicone 被 Mintlify 收购、Portkey 被 Palo Alto Networks 收购、OpenRouter 被 Stripe 宣布收购 [19]。
- **Coding-agent 路由与 token 压缩代理成最快增长品类** ：headroom、OmniRoute、CLIProxyAPI、sub2api、claude-code-router、9router 的合计星标已超过本报告所有传统 LLM 网关之和，是 6 月版完全遗漏的新战场。其中多数依赖池化编码订阅、带 ⚠️ ToS / 封号风险；品类内相对合规的两条路线是 BYOK 端点转发（claude-code-router）与上下文压缩（headroom）。
- **性能叙事回归理性** ：6 月版普遍引用厂商“微秒级”宣称，而第三方独立基准的可复现实测（Bifrost 0.62 ms、Portkey 2.65 ms、LiteLLM 5.83 ms）与营销数字差着一个数量级。选型应以能复现的基准为准，而非厂商话术 [17]。
- **缓存保真度成为新考点** ：prompt-cache 折扣经网关后常静默失效，是账单上最被低估的隐性成本 [4][17]。
- **CNCF 与云原生网关确立** ：Envoy AI Gateway v1.0 GA（首个 CNCF 背书）、kgateway（CNCF）、Higress 等 AI 原生网关成熟，K8s Gateway API 路线成为企业级重要方向 [18][21]。
- **Agent / MCP 网关独立成品类** ：agentgateway、Plano / Archgw、Bifrost MCP、AWS AgentCore Gateway、IBM DataPower Interact、MuleSoft Omni、NetFoundry、Lunar.dev 等聚焦 Agent 与 MCP 流量的治理与追踪，取代部分传统“模型路由”叙事 [18][22]。
- **ML 驱动路由式微** ：TensorZero 归档使“网关持续根据反馈优化模型选择”这一路线暂时失去最重要的实践者；RouteLLM、Not Diamond、Martian 等仍在探索，但社区热度已不如静态规则 + 成本路由。
- **国内格局换代** ：New-API（48.1k）星标反超 One-API（36.9k），后者停更；Higress、GPT-Load、sub2api、metapi（router of routers）补位企业 / 分发 / 池化场景 [9][18]。
- **零加价 vs 手续费成为托管分水岭** ：Vercel / Cloudflare 靠 0% 加价直接冲击 OpenRouter ~5.5% 手续费模式；OpenRouter 被 Stripe 收购后如何回应值得跟踪。

共识领域：所有主流网关都支持 OpenAI 兼容接口；路由、故障转移、速率限制是基础能力；可观测性（日志、成本、延迟）成为必选项；开源方案在功能上已能与商业方案匹敌；云厂商自带网关已经成为企业默认选项之一。

争议与不确定领域：最佳路由策略（静态规则 vs ML 驱动，后者随 TensorZero 归档而式微）；Python vs Go / Rust 的性能与生态权衡；自建 vs 托管的隐私 / 运维取舍；被收购网关（OpenRouter、Portkey、Helicone）的定价与路线图走向；语义缓存与缓存保真度缺乏统一基准；coding-agent 路由的 ToS 边界（⚠️ 项目是否被提供商封号，仍是动态博弈）。

进一步研究空间：各网关在真实 Agent 多步调用下的延迟累积与缓存保真度对比；语义缓存在不同领域（代码生成 vs 自然语言问答）的命中率差异；国内模型（DeepSeek、Qwen、GLM）在各网关的接入完善度；> 10k RPS 大规模生产下的稳定性基准；被收购事件（Stripe / Palo Alto / Mintlify）落地后的政策变化跟踪；以及编码订阅池化方案的封号事件统计与 ToS 边界演化。
