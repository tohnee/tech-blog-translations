## 背景

前几天写了一篇[从RDMA的测试结果说起 - 大包问题](https://zhuanlan.zhihu.com/p/2098690929876006027)，讲了我近期遇到的一个与RDMA测试相关的性能问题。今天就继续接着这个话题，说说与之相对的小包问题。

还是黏贴之前的那篇文章的测试方法

```bash
# Server
~# ib_write_bw \
    -d mlx5_0 \    # -d 指定RDMA的设备
    -s 1048576 \   # -s 指定message size
    -D 30 \       # -D 指定测试时常 
    --report_gbits # 报告格式

# Client
~# ib_write_bw \
    -d mlx5_0 \
    -s 1048576 \
    -D 30 \
    --report_gbits \
    192.168.1.10 # 指定Server IP
```

所谓的“小包问题”是指当 -s参数为64KB的时候（65536）的时候，有较小概率出现网络带宽下降的情况。

## 重新定义重现标准

起初，64KB的测试统计结果是这个样子的：长时间疲劳测试300+轮，大多数的带宽稳定在380Gbps附，相对非常稳定；少数几个样本记录了网卡带宽低于客户认定的验收标准的360Mbps（红线水位）。

![](https://picx.zhimg.com/v2-32075f60db5da221c72f035a4e568f87_r.jpg)

尽管是个大工程，不得已只能每一轮测试都采集PCM数据，发现PCM实际观察到的网络带宽（通过PCIe bandwidth计算）相对比较一致——±3%左右的范围，且远远高于红线带宽。

考虑到整个重现过程中为了降低重现成本，每一轮的ib_write_bw的测试时长被设置在了30秒，相对非常短的时间在受到噪声影响的情况下非常容易出现跑分尖刺。本以为适当延长测试时间——比如增加至2分钟会大大减少由于测试噪声导致的“尖刺”，但沟通下来考虑初期到这个case的重现成本高的惊人，我只得认定只有低于275Gbps的带宽（蓝线）才会被认为重现了性能下降的问题。说起来只是简单的调整了一下阈值，但实际上这个过程前后花费了接近一周时间，前后几次拉低了蓝线的水位也是不得已而为之。

换句话说，**对于某些牵扯到概率的单纯性能问题，不妨先从测量方法上入手看看是不是超预期的误差导致的。**

## PCM 数据分析

于是乎又是一顿昏天黑地的大规模重现，总算抓到了1组可以用来作为重现的样本。我又找到了一份同一机组上正常的数据，总计4份数据，good/bad * server/client 做了表格对齐。

### 从CPU视角看

RDMA（perftest）实测带宽113Gbps，相较正常值全程都在370Gbps以上，可以说是性能有了显著的下降。结合client端给到的数据是一致的；PCM相关的寄存器统计值也出现了从779Gbps -> 272Gbps的性能跌落，多方验证无误，出现明显的性能问题。PS：手搓水印，请忽略单位上的瑕疵。

metric_IO_bandwidth_disk_or_network_writes (MB/sec) 和 metric_IO_bandwidth_disk_or_network_reads (MB/sec) 两项指标下降比例并不一致，分别为40%和30%，IO的read下降更多。考虑到这个测试本身是个rdma write测试，对应的大头应该是IO read（这里被绕晕的同学先别着急，因为后面还有更晕的[狗头]）。Client端发起了RDMA write，对应的Server端就是数据从网卡写入内存；那从PCM或者从CPU的视角来看就是从PCIe bus上读取数据保存到DDR内存。——哲学上的从肯定到否定，再到否定之否定的异样美感！

按照惯例，看到了IO带宽异常之后想到的就是MMIO/L3 cache是不是健康。如果你看了上一篇大包问题的分析，你会发现随着数据包的减小，write cache miss有了显著的下降。经验告诉我们这个级别的IO write cach miss bandwidth意味着几乎所有的MMIO write——对应IO读都是命中L3 cache的，MMIO效率极高。与之对应的read cache miss bandwidth还是一如既往的等于IO wrtie，所有的通过网卡外发的数据都必须从内存读取，符合逻辑。总之，对于cache相关的指标，不论是从网络Tx还是Rx两个方向上看都没有任何异常，甚至可以说是非常健康。

MMIO和cache既然没什么大问题，压力大概率也不会出现在内存（特指DDR，DRAM内存）子系统上，不管是直接的内存读写带宽，还是从反应内存带宽压力的RPQ/WPQ上来看都找不到异常。甚至可以说BAD case远比GOOD case在整个从网卡到DRAM的通道上更加通畅、压力更小、更为健康。

### 从PCIe视角看

IO inbound read request per sec 和 write request per sec两个指标，顾名思义就是指PCIe设备每秒读/写的次数。两者下降了不少，从比例数上看又恰好和上面bandwidth的下降比例匹配。也就是说正是由于PCIe设备操作次数的减少导致了实际观测到的网络带宽（以IO带宽计算）有了同比例的下降。这些指标排除了由于测试过程中网络或/和PCIe协议层封装协议切换导致的问题。

IIO相对应的memory read/write 这一对指标实际上反映出测试的网卡本体的每秒读写带宽。由于测试环境中没有其他应用大量占用PCIe设备，在这里没有更多的作用，可以之际参考IO inbound的那一对。

IIO inbound ARB WON，实际上是用来体现io入口出现冲突之后发起裁决的次数，能得到的信息是GOOD case发起了更多的裁决而BAD case裁决次数较少。虽然只看比例BAD case 达到了GOOD case的70%+，但实际上GOOD case才是更恶劣的那个（因为GOOD case实际上已经接近饱和，不能提升更高了而已）。也就是说，至少BAD case不是因为通讯协议中的冲突导致了性能下降。

### 从uncore 视角上看

如果把整个PCIe到DRAM内存的通讯过程想象为一个队列，那对应的其实就是uncore部分的通讯流量。这个队列的吞吐能力-速度决定了PCIe的性能。

CHA tor insert IO 和 occupancy这一对指标分别针对IO设备向Uncore设备填入数据以及整体当前uncore中存在的未消化数据量。单掕着任何一个都没有太多意义，根据利特尔法则（litter's law）得到PCIe的read latency。

$Latency = \frac{Occupancy}{Insert}$

可见两个case在Uncore吞吐能力上并未出现明显差异。

### 小结一下

1. 明确了确实观察到了PCIe带宽下降的现象。
2. 从多个视角出发，对照GOOD case，BAD case的各个子系统均没有出现性能瓶颈。
3. 以读写操作次数/秒计，PCIe设备的操作频率出现显著下降是主要因素，目前无法通过指标得到解释。

简而言之，带宽下降的原因不是CPU测出现性能问题，而是网卡没有通过PCIe传递足够的数据到CPU。而这种显著的行为改变往往意味着软件层逻辑或者系统的某个配置被改变了。

## RDMA Credit消费分析

其实我非常讨厌credit这个名称，如果你单独接触PCIe、网络或者其他什么的高速通讯协议，你会觉得credit就是一个双方协商通讯额度，交换彼此队列长度的控制流信号。可一旦联系到这个case，“Credit”这个词就变得烂大街了—— UPI / Mesh / TOR / NIC / network / RDMA都有自己独立的一套毫不相干的credit系统，不削怎么玩？

这里只讨论RDMA协议的credit，除非有标注！

RDMA协议，特别是RDMA write的时候为了保证接受端有足够的资源，就必须要提前发送一个消息询问有没有足够的recive buffer，这个流控机制往往体现了主机的吞吐能力。

这里我抓了一份数据，表达的是出现问题的case由于系统没有足够的credit导致网络流控的等待纳秒时长。图中可见大量的请求都达到了us微秒级别，尖峰林立。虽说事实上这个状态在压力测试这种过饱和的场景下非常正常，没什么毛病～吗？

![](https://pic1.zhimg.com/v2-bfd0d13cf94543f31bbd4586fc86236a_r.jpg)

由于采样的数据特性，通过肉眼观察会完全会被尖刺迷惑，按照通常理论这个时候就应该讲积分了。考虑到近期的股市风云诡谲，要不就给圈子里炒股的朋友一点发挥余地，我就直接加个0.05%的指数平均，帮忙看看这盘子是涨还是跌😂

![](https://pica.zhimg.com/v2-8425e6527e852b77f27f9d146b1b9f4a_r.jpg)

测试开始后不久的某个时间节点之后，随着一波快速拉升之后数次震荡探底，盘面呈现出缓慢下滑的趋势。

credite的产生和消费理论上应该趋于平稳，在这个测试里首先不应该长期处于高位，其次不应该出现下滑趋势。长期高位意味着服务器资源紧张，无法提供足够的接收buff；假设网络状况没有大幅度的改变，那不应该看到由于credit逐渐充裕导致的这种耗时下降的趋势。

所以，是某种不为人知的机制导致了网卡层面上控制了网络流量不在提升才会出现credit逐渐宽裕。

## 结论

既然CPU的吞吐能力没有问题，credit导致的网络时延也在减少，那问题还是没解决，对于我来说就打算看看代码找找原因。结果上边的总结给到了网卡的供应商，一番调试之后认为是网卡本身的PFC（Priority Flow Control）机制在由于credit不足时会释放PFC Pause，但不知什么原因这次PFC pause有概率不会正常收回。这就字面意义上没我什么事儿了……
