> 靡不有始，鲜克有终 —— 《诗经》

存在的事物都有它自己的开始，可是哪些又能真正善终呢？

距离我上次更新专栏[深入了解 oneDNN计算图编译模块](https://www.zhihu.com/column/c_1492807621665501184)已经过去了2年了。从我去年离开这个项目之后，从Github上面公开的记录显示，oneDNN Graph Compiler这个AI计算图编译器项目已经一年多没有更新了。看来是到了为它盖棺定论的时刻了（有关此项目未来方向以Intel发布的消息为准）。我在2020年还是刚工作一年的小菜鸡，有幸成员这个项目最早的开发者之一，Tensor IR、Graph IR以及Pass、Runtime架构我都深度参与了最早的设计和后续开发。

当初在知乎上发表了一系列文章介绍了oneDNN Graph Compiler的各个方面，总共写了14篇，也得到了不少朋友的关注和谬赞，不胜感激。很可惜由于项目和个人的变动，这个专栏应该是不会再继续更新了。我不想让这个系统就这样“烂尾”，至少应该有一个总结和反思。这就是我写本文的初衷：希望至少我的这个专栏可以“鲜克有终”。

本文将先回顾一下Graph Compiler这个项目，然后是本人这几年参与开发AI编译器的一些经验教训和个人看法。

声明：本文只讨论纯技术方向，不评价任何特定公司的特定产品。

## **回顾Graph Compiler**

Graph Compiler是Intel oneDNN Graph下面的子项目。目的是将用户的AI计算图（例如Attention模块）“端到端”地编译到可执行代码，无需用户懂得硬件架构细节，也无需写底层C++代码。Graph Compiler自动完成算子展开、融合、代码生成等步骤。oneDNN Graph API则是Graph Compiler上层API，拥有PyTorch TensorFlow等框架的集成，使得用户可以将Torch等框架的代码编译到加速后的代码中。

有关这个项目的细节，我们发表过一篇论文：oneDNN Graph Compiler: A Hybrid Approach for High-Performance Deep Learning Compilation [CSDL | IEEE Computer Society](https://www.computer.org/csdl/proceedings-article/cgo/2024/10444871/1UUdPicbmOA) 。另外还有本专栏：[深入了解 oneDNN计算图编译模块](https://www.zhihu.com/column/c_1492807621665501184)。这里不再赘述。我想重点讨论的是这个项目和其他市面上的“Graph”Compiler（例如TVM、MLIR-based compilers、TorchInductor等等）的不同之处。

### **基于手写模板的算子展开**

TVM等编译器（至少在项目早期）会先将算子（例如matmul）彻底展开成循环，然后通过一些规则或者Tuner来schedule loop来生成更好性能的算子。而在Graph Compiler中，则是采用“人工”和“自动”相结合的办法来展开算子代码。对于计算密集型算子，例如matmul和conv，我们会手写一些被称之为“模板”的IR代码。这些手写代码结合了人工调优，手工优化了缓存、流水线等等方面。实际生成代码的时候，我们会从matmul等算子的shape、硬件信息等等，基于一定的规则，选择合适的“模板”（一个matmul可能有多个不同的模板实现，针对不同环境），填入模板后就得到了算子展开的IR了。

而对于简单的算子来说（例如add，relu），GraphCompiler会自动展开算子并且自动融合到前后的算子计算代码中。

### **自研编译器框架**

由于上游项目的要求，整个Graph Compiler项目几乎没有外部依赖。我在设计TensorIR的时候最初参考了TVM的实现。而IR Visitor、Pass等等都是我自行设计的。众所周知LLVM是众多AI编译器的底层。而对于Graph Compiler来说，LLVM这个依赖甚至都是可选的。如果不Link LLVM，Graph Compiler可以用自己的JIT Compiler生成高效的x86代码。

### **只面向纯CPU环境**

我可以很自豪地说，我们的Graph Compiler是x86上做得性能最好的端到端（Graph-to-kernel）AI编译器（也许没有之一？）。很可惜，这个项目自始至终只支持x86 CPU上运行。我曾经作为“探路先锋”做过两三次GPU的PoC，可惜都因故止步于实现简单Kernel为止。

### **其他**

由于做的是面向x86 CPU的AI编译，我们做了不少非常niche的优化。这里列举一二：

- 由于我们编译器保证内存分配一定是先进后出的，可以设计一个stack-based memory allocator。每次分配、释放只需要修改栈顶指针，效率非常高。同时，内存lifetime分析、in-place操作和内存合并等AI compiler标配我们也实现了。
- 基于任意底层线程池(OMP, Eigen, TBB)，我们封装了一个“managed thread pool”，意为由Graph Compiler自行管理的线程池。保证不同底层线程池得到的性能大体一致。最“骚”的操作是，在线程池Barrier等其他线程的时候，通常市面上的线程池会让线程等待，busy wait或者进内核态等待。我们的线程池则会利用这些被浪费的CPU时间去prefetch下一个matmul的weight（由于是图编译器，编译器有全局视野，可以知道这次barrier后面的计算是什么）。
- 通过分析图中哪些“小”算子可以并行执行（“小”算子指的是用不满CPU所有核心的算子，类似矩阵转置，quantization预处理等等），将这些算子合并放入同一个kernel并行计算用满所有计算资源
- 我们观察到CPU线程数量变得非常大之后，全局同步开销会非常大。我们将CPU线程进行分组，内层循环先进行组内同步，然后外层循环再进行全局同步。例如56线程，我们分组为4x14。矩阵乘法 MxK @ KxN，我们可以把M维度分配给4组线程，每组线程14线程通过splitK计算M_block x N的分块，并且只需要进行组内同步。
- 在CPU上支持数据类型量化：s8，u8，f16，bf16。需要CPU指令集的支持。

## **反思**

从这个项目当中我学到了什么呢？本节都是一些非常个人主观的看法。

### **服务器CPU搞大模型？**

特此说明，本文只讨论纯技术方向，不针对任何特定公司的特定产品。

Graph Compiler的主要目标硬件是服务器CPU。在我在项目的最后一年，大模型大热，项目也不可避免地试图去优化大模型上的workload。现在回过头来看，服务器CPU强行上大模型的意义是要打上大大的问号的。SPR这代开始，xeon CPU带上了TensorCore的类似物，也就是AMX。在算力上高端CPU和A100之类的当时顶级GPU至少可以站在一个数量级上了。最大的问题在于内存带宽。CPU至今没有普及HBM，而服务器GPU基本是HBM全覆盖了。我们知道大模型的“大”指的是模型本身和之前的AI模型提升了几个数量级。这就导致缓存不太可能装下模型大部分的weight。就算是只跑一次完整的前向inference，跑到最后一层transformer的时候，第一层的weight早就被踢出缓存了。至少对于CPU来说，内存带宽经常会成为跑大模型的主要瓶颈。

此外CPU设计哲学和GPU有诸多本质不同（例如CPU追求单核性能，GPU则生来众核），导致CPU对AI workload水土不服，在此按下不表。

### **拥抱新技术、拥抱开源**

有读者可能会问，为社么不使用TVM、MLIR等开源技术栈，而要自研一套完整的AI编译器技术栈呢？我也不懂，不要问我（笑）。

最近一年多以来，在技术栈切换到MLIR上之后，我惊叹毕竟MLIR出自Chris（LLVM之父）和Google之手，MLIR的IR的定义、各层抽象都十分老道。MLIR定义的Interface系统也让自以为熟悉C++的我感叹C++还可以这么写。它的基础设施也非常完备。虽然基于tablegen的ODS略显复杂，但是基于一套规则自动生成C++代码的定义IR方式在大部分情况下还是相当方便的。

刚开始学习MLIR的时候，我就觉得要是当初我参与设计的TensorIR GraphIR也这么搞（或者直接用MLIR）就好了。Graph Compiler的IR设计在MLIR面前犹如“腐草之荧光，如何比得上天空之皓月”了吧（笑）。

另外，Graph Compiler还自研了IR到底层x86指令的JIT编译器模块。当然我们也支持将Tensor IR lower到LLVM IR，通过LLVM完成JIT compile。这个项目花了不少人力来研发这个自研的JIT模块，其中包括了传统编译器常见的寄存器分配，基于SSA的各种优化等等。我也在这个子模块开发中出了一部分力。最终花了不少时间终于达到了接近LLVM的性能（相比之下，我开发Tensor IR的LLVM后端就用了一周时间）。要问自研x86 JIT compiler的优势在哪？我也只能说出“JIT编译速度比LLVM快”，“compiler本身大小比较小”之类云云了。为了这些而放弃LLVM 20年积累的各种优化，而去自研一套底层编译器，是否值得？只能说见仁见智吧。

最后我们的项目是开源项目，由于一些奇奇怪怪的原因，被要求支持最低到GCC 4.8.5的编译器版本。由于编译器版本被智子锁定在这个版本，C++也只能用C++11（笑）。C++14以及之后引入的好用的功能在项目里都没法使用。我重新造了一遍any variant optional ，引入到项目中来。其中any还是带Small Object Optimization的。optional则是按照我的口味加上了null folding:some(nullptr) == none。并且给optional加上了map flatmap 等链式操作。这倒是锻炼了我的C++能力，给我之后面试带来了不少自信就是了。项目中另外还有不少“重复轮子”，例如json等等（摊手）。

### **AI图编译器已死？**

不只是Graph Compiler，老牌AI编译器TVM看上去热度也在逐渐下降（大家可以猜猜陈天奇大佬去哪了）。有人可能会说Triton热度不是很高吗？这就要说明一下同样是AI编译器，Triton和TVM、Graph Compiler的不同了。

Triton更像是一个更方便的写cuda-like kernel的DSL，和cuda的不同是cuda是SIMT的，而Triton的抽象基本到Tile为止。但本质上来说Triton相比TVM这类“Graph”级别的AI编译器，更接近与cuda等底层编程语言，需要定义loop，定义细粒度的变量等等。而TVM、Graph Compiler的抽象级别更高。用户可以提供高层语义的算子，编译器自动完成算子展开到循环、算子融合等等操作。

问题在于，什么情况下用户需要AI编译器自动完成高层语义翻译？那就是模型迭代较快的年代。在AI编译器的上古时代，pytorch tensorflow等框架基本上只会对已知的模型结构进行pattern match，换上较快的实现。如果没有匹配到优化的实现，则是一个个单独算子执行。如果模型结构参差不齐，百花齐放，对于新出现的模型中的新结构人工就来不及第一时间实现优化的版本。这个时候如果使用了AI编译器，那么可以花费极少的精力，就能免费得到80%以上的硬件峰值性能。例如MobileNet的激活函数Hardswish就是一组Elementwise算子组成，基于计算图的AI编译器可以不费力气地优化这样新出现的结构。

而现在大模型时代，模型的核心Attention万变不离其宗，大多都是MHA的变种。模型收敛到Transformer系列之后，只需要人工手写kernel（通过cuda或者triton）即可。如果需要AI编译器自动优化某些新出现、但是尚未覆盖的结构，需要的精力通常都是要大于修改kernel代码的。这个时候再去开发端到端的AI编译器是否还值得呢？

另外编译器的优化pass本质上就是一组pattern match。还是需要人工“告诉”编译器遇到什么样的pattern，需要优化为什么样的等价代码。编译器的上限也就被输入的pattern集合所定义。很多时候编译器自动优化的代码是比不上人工精心设计的代码的。例如FlashAttention对Softmax的等价变换，很难通过一组简单的规则让编译器自动完成；到最后可能需要pattern match计算图中MHA，然后换成手写的FlashAttention了事。这样和PyTorch等框架干的事情没有啥区别了吧。

最后我想说一下，以上反思只是我作为AI编译器底层大头兵的个人看法。很多时候在环境当中身不由己，不管对于项目领导还是我这样的大头兵来说莫不如此，这就是社会人的无奈吧？
