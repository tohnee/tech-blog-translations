上一篇介绍了数据并行（**D**ata **P**arallelism，DP）框架 DeepSpeed 中的核心算法 ZeRO 和 ZeRO++。本篇将介绍另一种常见的并行计算方法：流水线并行（**P**ipeline **P**arallelism，PP）。

Pipeline Parallelism 对模型按照 Layer 进行分组，将连续的数个 Layer 分为一组（称为一个 Stage）。然后将不同的 Stage 分配到不同的计算设备上。这样每个 GPU 只计算网络中的一部分 Layer，所以也只需存储与之相关的信息（如模型参数、优化器状态、激活值等），可以大幅节约显存开销。本篇的主要内容包括：

- PART 1：使用一个简单、偏直觉的例子来说明 Pipeline Parallelism 的基本原理；
- PART 2：介绍 Google 提出的 GPipe，它是 Pipeline Parallelism 的经典方法，优点是简单易懂，缺点是各 GPU 会存在大量的空闲时间；
- PART 3：介绍 PipeDream，相比于 GPipe 在细节设计上更加极致，但也带来了许多新的问题。

### 1. 极简的 Pipeline Parallelism

我们使用一个简单的例子来说明 Pipeline Parallelism 的基本原理和它的一些特性。假设模型一共有 $L$ 层，GPU 数量为 $N$。为简单起见，再假设 $L$ 能被 $N$ 整除。这样就可以将模型的 $L$ 层均匀地划分为 $N$ 个 Stage $[S_1, S_2, \ldots, S_N]$，其中每个 Stage 包含 $L/N$ 层；每个 GPU 负责计算一个 Stage。在图 1.1 的示例中，模型的层数和 GPU 数量均为 4。模型被划分为 4 个 Stage，每个 Stage 刚好包含原网络中的某 1 层。

![](https://pica.zhimg.com/v2-15412bcfa6ec9bc8bab969d5c708ce66_r.jpg)
*图 1.1 极简 Pipeline Parallelism 示意图*

一种最朴素的流水线并行计算策略可以这样设计：在前向计算过程中，一个 Batch 数据首先由第一个 Stage $S_1$ 进行计算，计算完成后将输出传递给第二个 Stage $S_2$ 进行计算，依此类推，直到最后一个 Stage $S_N$ 计算完成，得到最终的输出结果，并计算出 Loss。

在反向计算过程中，梯度信息从最后一个 Stage $S_N$ 开始计算，并依次传递到前面的 Stage，直到第一个 Stage $S_1$ 完成梯度计算。当针对一个 Batch 的前向和反向计算都完成后，所有 GPU 使用优化器对模型参数进行更新，这个阶段称为 Pipeline Flush。Pipeline Flush 和 Data Parallelism 中的参数更新比较类似，都是统一执行，确保**参数一致性**。

> 这里的**参数一致性**是指所有模型的参数都是基于**相同 Batch 数据**计算得到的梯度进行更新的。<br> 这种方式下，每个 GPU 在前向和反向计算过程中都是串行执行，所以总的计算时间是所有 Stage 计算时间之和再额外加上 Pipeline Flush 的时间。

在图 1.1 中，Batch 由蓝色方框表示，图中一共有 4 个 GPU（Worker）。四个 GPU 依次进行前向计算，然后再从最后一个 GPU 开始依次进行反向计算（绿色框所示）。图中假设了反向传播过程的计算时间为前向计算的两倍。当所有计算完毕后，会使用优化器对模型参数进行整体更新（Pipeline Flush）。可以看出，这种简单的流水线并行方案会导致 GPU 出现大量空闲时间（这些空闲时间称为 Pipeline Bubble，如图中灰色区域所示）。流水线并行的研究主要关注：

- 如何减少 Pipeline Bubble，从而提高系统整体吞吐量；
- 降低每个 Worker 的显存开销，以确保能够扩展到更大的模型。

### 2. GPipe

GPipe 是 Google 在 2018 年提出的一种 Pipeline Parallelism 方法。它的设计主要源于这样一个现象：在 Pipeline Parallelism 中，GPU 出现大量空闲时间的主要原因是每个 GPU 需要等待前一个 GPU 计算完成后才能开始工作，并且每个 GPU 工作的时间和它处理的 Batch 大小密切相关。也就是说，如果一个 GPU 处理的 Batch 越大，那么它的计算时间就越长，后续的 GPU 也就需要等待更长的时间。

为了减少这种等待时间，一个简单的思路是把 Batch 进一步划分为多个更小的子 Batch（称为微批次，Micro-batch）。例如，假设原本的 Batch 大小为 64，我们将其划分为 4 个微批次，每个微批次大小为 16。对于第一个 Stage $S_1$ ，它首先处理第一个微批次，计算完成后立即将结果传递给第二个 Stage $S_2$，然后 Stage $S_1$ 马上开始处理第二个微批次。与此同时，第二个 Stage $S_2$ 则可以开始处理第一个微批次的计算任务。这个过程可以参考图 2.1。

![](https://pic4.zhimg.com/v2-91b51648fed840411261a641f3268ca9_r.jpg)
*图 2.1 GPipe 示意图*

图 2.1 中，假设一个 Batch 共包含 8 个样本，且将每一个样本当作一个 Micro-batch。与图1.1 的区别在于，每个 GPU 无需处理完整个 Batch 后才让下一个 GPU 工作，而是在处理完一个 Micro-batch 后，就将该 Micro-batch 送给下一个 GPU 进行处理。

下面分析一下 GPipe 的 Pipeline Bubble 占比。将每一个 Worker 的 Pipeline Bubble 记为 $t_{pb}$；记一个 Micro-batch 的数量为 $m$，GPU 数量为 $n$，并假设 $m \geq n$（保证不会出现绝对意义上的空闲）；单个 Micro-batch 的前向计算时间为 $t_f$，反向计算时间为 $t_b$。

首先来分析对于一个完整的 Batch，一次前向计算所需的耗时。在前向计算过程中，第一个 Worker 需要处理 $m$ 个 Micro-batch，每个 Micro-batch 的前向计算时间为 $t_f$，所以第一个 Worker 的前向计算总耗时为 $m \cdot t_f$。

接下来分析：当第一个 Worker 正在处理最后一个 Micro-batch 时，最后一个 Worker 当前正在处理第几个 Micro-batch？

由于每个 Worker 处理完一个 Micro-batch 后就会将 Micro-batch 传递给下一个 Worker，所以当第一个 Worker 处理第 $m$ 个 Micro-batch 时，最后一个 Worker 的前面有 $n-1$ 个 Worker 在同时工作。那么最后一个 Worker 正在处理第 $m - (n - 1)$ 个 Micro-batch。

因此，最后一个 Worker 还需要处理剩余的 $m - (m - (n - 1)) = n - 1$ 个 Micro-batch。每个 Micro-batch 的前向计算时间为 $t_f$，所以最后一个 Worker 还需要**额外的**前向计算时间为 $(n - 1) \cdot t_f$。

最后一个 Worker 所需的额外前向计算时间加上第一个 Worker 的前向计算时间，就是整个 Batch 的前向计算时间：

$ (2.1)\quad T_f = m \cdot t_f + (n - 1) \cdot t_f = (m + n - 1) \cdot t_f $

同理可得，整个 Batch 的反向计算时间为：

$ (2.2)\quad T_b = m \cdot t_b + (n - 1) \cdot t_b = (m + n - 1) \cdot t_b $

因此，整个 Batch 的总计算时间为：

$ (2.3)\quad T = T_f + T_b = (m + n - 1) \cdot (t_f + t_b) $

注意，上述的 $T$ 表示每个 Worker 参与完整的 Batch 计算所需的时间（包括前向计算、反向计算、等待时间）。而对于每个 Worker 来说，它真正参与计算的时间是：

$ (2.4)\quad T_{compute} = m \cdot (t_f + t_b) $

因此每个 Worker 的 Pipeline Bubble 时间为：

$ (2.5)\quad t_{pb} = T - T_{compute} = (m + n - 1) \cdot (t_f + t_b) - m \cdot (t_f + t_b) = (n - 1) \cdot (t_f + t_b) $

那么 Pipeline Bubble 的占比为：

$ (2.6)\quad \text{Bubble Ratio} = \frac{t_{pb}}{T} = \frac{(n - 1) \cdot (t_f + t_b)}{(m + n - 1) \cdot (t_f + t_b)} = \frac{n - 1}{m + n - 1} $

当 Worker 数量 $n$ 固定时，增加 Micro-batch 数量 $m$ 可以有效减少 Pipeline Bubble 的占比。在原论文中推荐的经验值是 $m \geq 4n$，此时 Pipeline Bubble 的占比小于 20%。此外，如果在训练阶段启用了 Gradient Checkpointing，因为每个 GPU 可以在空闲时重算前向计算的激活值，因此实际的 Pipeline Bubble 会更少（原论文称此种情况下可“忽略不计”）。

虽然我们可以通过将 Micro-batch 划分到最小来减少 Pipeline Bubble，但需要注意的是，让 GPU 执行一次 Batch_size=32 的计算和执行 32 次 Batch_size=1 的计算，二者的效率天差地别。所以在实际中需要综合考虑 Micro-batch_size 和 Pipeline Bubble 来进行权衡。

在 Pipeline Parallelism 中，不同 Worker 之间的通信只需要传输某一层的激活值（前向计算）和梯度（反向计算），所以通信开销相比于数据并行要小得多。

Pipeline Parallelism 要求每个 Stage 的计算时间尽可能相近，否则会出现某些 Stage 计算时间过长，导致其它 Stage 出现大量等待时间，从而影响整体的训练效率。在 CNN 主导的年代，因为 CNN 通常有下采样、上采样层，会导致不同层之间计算量差别较大。所以大多数 Pipeline Parallelism 框架都会有一个自动 Profiling 的功能，通过跑一些测试样例来估计每一层的计算时间，从而进行合理的 Stage 划分。在 LLM 时代，因为 Transformer 的每一层计算量相对均衡，所以可以直接将模型均匀划分为多个 Stage。

### 3. PipeDream

PipeDream 与 GPipe 都是 2018 年提出的 Pipeline Parallelism 方法。甚至在时间上，PipeDream 的时间还要更早一点。相比于 GPipe，PipeDream 在设计上更加极致，但也因此带来了许多新的问题。所以本文将它放在了 GPipe 之后进行介绍。

如果熟悉了图 2.1 中 GPipe 的工作原理，那么理解 PipeDream 的基本思路也不太困难。GPipe 的思路是把每个 Batch 的训练阶段分为三个阶段：首先执行所有 Micro-batch 的前向计算，然后执行所有 Micro-batch 的反向计算，最后统一更新模型参数。

而 PipeDream 的思路核心思路是“尽可能早地执行**反向计算**”。“尽可能早”的含义是，只要前提条件满足（即前序 Loss 或者梯度已经计算完成），就立刻执行反向计算。下面用图来分析 PipeDream 的具体做法和它能带来的好处。

![](https://pic1.zhimg.com/v2-99ca2deddb25e07c213bece6ffb4297e_r.jpg)
*图 3.1 PipeDream 示意图*

图 3.1 的示例中，每个蓝色的数字框表示一个独立的 Batch（注意和 GPipe 中的 Micro-batch 区别），这意味着每个 Batch 都会触发一次优化器更新，而在 GPipe 中是所有的 Micro-batch 共同触发一次优化器更新。

对于 Worker 1，当它处理完 Batch 1 的前向计算后，它将 Batch 1 的激活值传递给 Worker 2，然后立刻开始处理 Batch 2 的前向计算。这个过程与 GPipe 处理 Micro-batch 的方式类似。但是当 Worker 4 处理完 Batch 1 的前向计算后，它并不是立即处理 Batch 2 的前向计算，而是处理 Batch 1 的反向计算。这符合“尽早执行反向计算”的原则：Worker 4 包含输出层，因此可以直接得到 Batch 1 的 Loss，从而可以立刻进行 Batch 1 的反向计算。

同理，对于 Worker 3，当它收到 Worker 4 传递过来的 Batch 1 的梯度后，它立刻进行 Batch 1 的反向计算。在这种设定下，因为反向计算的优先级始终比前向计算高，所以就会出现图 3.1 中前向计算与反向计算穿插的情况。在图 3.1 中还有一个现象，随着训练的进行，每个机器的空闲时间越来越少，直到最后都处于高负荷状态。PipeDream 的这种模式称为 “1F1B”（1 Forward 1 Backward）。

就 Pipeline Bubble 占比而言，PipeDream 明显优于 GPipe，并且随着训练的进行，Pipeline Bubble 会越来越少。因此 PipeDream 看起来似乎是一个非常完美的方案。不过它有一个严重的“参数不匹配”问题。

### 3.1 参数不匹配问题

仔细观察图 3.1，对于 Worker 3 来说，当它完成 Batch 1 的反向计算后，它会立即更新自己部分的模型参数。但是当 Worker 3 执行 Batch 2 反向计算时，对于 Batch 2 来说，**它的前向计算和反向计算使用的模型参数并不相同**：

- Worker 3 对 Batch 2 在前向计算时使用的是初始模型参数；
- Worker 3 对 Batch 2 在反向计算时使用的是基于 Batch 1 更新后的模型参数。

更麻烦的是，不同 Worker 这种参数不匹配问题的程度还不太一样。比如对于 Worker 4，因为它恰好是一次前向、一次反向，所以它完全不存在该问题。而对于其它 Worker，该问题或多或少都持续存在。我们把这个问题称为“In-Stage Mismatch”，表示不匹配问题出现在单个 Worker 内部。

In-Stage Mismatch 的解决方案也很简单，对于存在参数不匹配问题的 Worker，在前向计算时为每个 Batch 记录下当时使用的参数快照，然后在反向计算时使用对应的参数快照即可。虽然简单，但是这会带来额外的显存开销，并且该开销随着同时存在的 Batch 数量增加而线性增长。因此 PipeDream 不太适用于 Stage 划分数量太大的场景。

除了 In-Stage Mismatch 问题，PipeDream 还存在 Cross-Stage Mismatch 问题。Cross-Stage Mismatch 问题是指：对于同一个 Batch，在不同 Worker 上的前向计算和反向计算使用的参数版本不一致。比如对于图 3.1 中的 Batch 2 来说：在 Worker 1、Worker 2、Worker 3 上的前向计算使用的是初始模型参数，而在 Worker 4 上的反向计算使用的是基于 Batch 1 更新后的模型参数。

解决 Cross-Stage Mismatch 的方案是为每个 Batch 在前向计算时记录一个参数版本号，并要求每个 Worker 在前向计算和反向计算时使用相同版本号的参数。详细推导每个 Worker 上的参数版本数量、版本管理策略非常繁琐，本文不详细介绍。这里只需要明白通过额外的模型参数副本，就能解决参数不匹配的问题（这在直觉上也非常容易理解）。

### 3.2 PipeDream-2BW

PipeDream-2BW（**D**ouble-**B**uffered **W**eight Updates）的主要改动是采用了 GPipe 中的 Micro-batch 方案。这个改动带来的好处其实不太直观。一种简单的理解方式是：

- 基于 Batch 的 PipeDream 中，前向计算与反向计算相互穿插在各个独立的 Batch 之间（如图 3.1）。因为每次反向传播都会触发参数更新，这意味着参数不匹配问题相当严重。
- 基于 Micro-batch 的 PipeDream-2BW 中，前向计算与反向计算**主要**穿插在同一个 Batch 的 Micro-batch 之间（如图 3.2）。而同一个 Batch 内部始终使用相同的模型参数版本，所以参数不匹配问题大大减轻。此时，参数不匹配问题主要出现在两个 Batch 的交界处（图 3.2 中的网格格子）。

![](https://pic2.zhimg.com/v2-885f55d491ec116df1f3b09c3056c40f_r.jpg)
*图 3.2 PipeDream-2BW 示意图*

我们使用图 3.2 来说明 PipeDream-2BW 导致的参数不匹配问题，以及解决方案。在图 3.2 中，假设一个 Batch 包含 4 个 Micro-batch，那么所有 Stage 的第一次参数更新发生在它们各自处理完 Micro-batch 4 的反向计算之后，图中使用了特殊颜色来标识。

我们重点关注编号为 7 的那一个 Micro-batch。虽然 Micro-batch 7 属于第二个 Batch，但它在 Stage 1 中的前向计算仍然使用的是初始模型参数 $\text{W}_1^{(0)}$（因为 Stage 1 还没有进行过参数更新），其中下标表示 Stage 编号；上标表示模型的参数版本号，参数版本号以触发参数更新的 Micro-batch 号作为编号。这意味着对于其它 Stage，即使当它们处理 Micro-batch 7 时已经有了更新后的参数 $\text{W}_i^{(4)}$（$i=2,3,4$），但它们在处理 Micro-batch 7 时仍然需要使用 $\text{W}_i^{(0)}$ 来进行前向计算，以保证不同 Stage 的模型参数版本号一致。那么在图 3.2 的示例中，Stage 2、Stage 3、Stage 4 都需要保存两个版本的模型参数：$\text{W}_i^{(0)}$ 和 $\text{W}_i^{(4)}$。只有当所有 Stage 处理完 Micro-batch 7 的反向计算后，大家的 $\text{W}_i^{(0)}$ 才会被释放掉。

PipeDream-2BW 有一个重要结论：上述的这种参数管理方法，每个 Stage 最多只会保存**两个版本**的模型参数。可以从 3.2 的图中来理解这个结论。最后一个前向计算会出现 Cross-Stage Mismatch 问题的 Micro-batch 编号是 7。触发下次一模型参数更新的 Micro-batch 编号是 8。按照 PipeDream 反向计算优先原则，Micro-batch 7 的反向计算一定会提前于 Micro-batch 8 之前完成。所以所有 Stage 在下一次参数更新前，就能释放掉之前旧版本的参数。

PipeDream-2BW 还有一个不太直观的地方是，它的参数更新规则有延迟：

$ (3.1)\quad \text{W}_i^{(t+1)} = \text{W}_i^{(t)} - \eta \cdot \nabla \text{W}_i^{(t-1)} $

而标准梯度下降中的方法是：

$ (3.2)\quad \text{W}_i^{(t+1)} = \text{W}_i^{(t)} - \eta \cdot \nabla \text{W}_i^{(t)} $

注意此处的上标 $t$ 表示参数更新的迭代次数。仍然以图 3.2 中的 Micro-batch 7 为例，Stage 1 在执行 Micro-batch 7 的反向计算时的参数状态为：

- Micro-batch 7 前向计算使用的参数为 $\text{W}_1^{(0)}$；
- Micro-batch 7 反向计算使用的参数为 $\text{W}_1^{(0)}$；
- 当前已经更新的参数为 $\text{W}_1^{(4)}$，用于下一个 Batch 中编号大于 7 的 Micro-batch 的前向计算。

如果采用式 (3.2) 中的标准更新规则，那么问题是：使用参数 $\text{W}_1^{(0)}$ 和 Micro-batch 7 计算得到的梯度去更新哪个参数？可选项只有 $\text{W}_1^{(0)}$ 和 $\text{W}_1^{(4)}$，但二者都不合适：

- $\text{W}_1^{(0)}$ 被更新为 $\text{W}_1^{(4)}$ 了，没有理由再使用它来获得一个新的版本；
- $\text{W}_1^{(4)}$ 在 Micro-batch 7 的整个计算中都没有被使用，用来更新它就更不合理。

所以在极度无奈的情况下，只能使用式（3.1）的更新规则。这个更新规则的核心逻辑是：当旧的参数所**参与的所有计算都完成后**，才使用它来更新当前模型参数。否则，有一部分的计算就会被浪费掉。

虽然 PipeDream-2BW 既有 PipeDream 的高吞吐量（极低的 Pipeline Bubble），又大大减少了每个 Stage 需要额外保存的模型参数版本数量，但它最大的缺点就是**不严谨的参数更新规则**。

实际上还有一种简单的改进 PipeDream 方法，就是采用 GPipe 的 Micro-batch 和 Pipeline Flush 方案，保留 PipeDream 的 1F1B。不过这种方案退化地非常接近 GPipe，没有太多优势。

### 4. 总结

本文介绍了两种经典的 Pipeline Parallelism 方法 GPipe 和 PipeDream。GPipe 通过将 Batch 划分为多个 Micro-batch 来减少 Pipeline Bubble，但仍然存在较多的 GPU 空闲时间。PipeDream 通过尽早执行反向计算来最大化 GPU 的利用率，但带来了参数不匹配。PipeDream-2BW 结合了 GPipe 的 Micro-batch 方案，减少了参数不匹配问题，但采用了不严谨的参数更新规则。虽然这些方法或多或少都有一些缺点，但在 LLM 发展早期，它们都是重要的并行化策略。
