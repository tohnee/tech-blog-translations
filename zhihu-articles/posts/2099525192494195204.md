> **话题标签**：`#上下文工程` `#大模型应用` `#RAG` `#提示词工程` `#企业AI` `#可靠性`<br><br> **摘要**：RAG 场景下，”模型答错了”几乎是必然事件。主流做法是在系统提示里加约束，要求模型”不确定时不要回答”。本文讨论一个不同的思路：不试图消灭错误，而是让错误可被识别、可被追溯、可被人低成本发现。在企业知识库场景里，这个思路比”提高准确率”更实用。

---

### 一、约束不是解法

系统提示里写”请仅依据检索到的内容回答用户问题”，这是标准做法。它有用，但不解决根本问题。

在我们的项目里，模型仍然会犯三类错：

| 错误类型 | 表现 | 发生率（改造前） |
| --- | --- | --- |
| 依据错 | 引用了正确文件但错误的条款 | 6.2% |
| 依据虚 | 引用了不存在的条款号或文件名 | 3.1% |
| 越界 | 检索内容不含答案，但模型自行补充了通用知识 | 2.4% |

**「依据虚」是最危险的一类。**

因为它看起来完全正常——答案格式规范、语气确定、还标注了来源。用户如果不去点开原文，根本发现不了。

我们第一版的系统提示是这样的：

```text
你是一个制度问答助手。请仅依据检索到的内容回答用户问题。
如果检索内容不足以回答，请明确说明"未找到相关规定"。
回答时需标注来源文件名与条款号。
```

看起来很完善。实测下来，”越界”从 2.4% 降到 1.1%，但”依据虚”几乎没变——**模型在编造条款号这件事上，提示词的约束力非常有限。**

原因是：模型在生成时并不”知道”自己引用的是不是真的存在。它只是在生成看起来符合模式的后续 token。约束写在提示词里，本质是”请求”它遵守，而不是”保证”它遵守。

**这两者的差别，比大多数提示词技巧都要大。**

---

### 二、换个思路：让结构强制执行，而不是靠提示词请求

第二版的做法是**改输出结构，而不是改措辞**。

核心动作：把”来源标注”从提示词里的一句请求，变成输出格式里的一个**必填结构**，并规定：来源字段为空或格式不合法时，整条回答作废。

```python
OUTPUT_SCHEMA = {
    "type": "object",
    "required": ["answer", "citations", "confidence"],
    "properties": {
        "answer": {"type": "string"},
        "citations": {
            "type": "array",
            "minItems": 1,                    # 至少一条，无例外
            "items": {
                "type": "object",
                "required": ["doc_id", "clause", "verbatim"],
                "properties": {
                    "doc_id": {"type": "string"},
                    "clause": {"type": "string", "pattern": r"^第[一二三四五六七八九十百]+条$"},
                    "verbatim": {"type": "string", "minLength": 10}
                }
            }
        },
        "confidence": {"type": "string", "enum": ["直接适用", "需人工确认", "未覆盖"]}
    }
}
```

三个设计点：

### 1. `citations` 的 `minItems: 1` 是硬约束

模型想”我不确定”的时候，不能只返回一句话，必须给出来源。给不出来，它会倾向于编一个。

而因为 `clause` 有正则约束 `^第[一二三四五六七八九十百]+条$`，”第十二条”能过，”第十二项”过不了——**格式约束把一部分编造挡在了外面。**

### 2. `verbatim` 要求逐字引用原文片段，不是让模型复述

**这是最关键的一条。**

复述是**生成**任务，模型会自然地”顺”下去——它会写出一段读起来很顺、但措辞已经偏移的内容。

逐字引用是**抽取**任务，必须从上下文中复制，一个字都不能改。

> **生成任务容易出错，抽取任务不容易出错。**<br>把工作从”生成”降维成”抽取”，是这里最省力的一个设计。

### 3. `confidence` 枚举三值，把判断权交回给人

“需人工确认”和”未覆盖”这两个值的存在，让模型有合法的”我不确定”出口。

**没有这个出口，模型只能硬答。**

### 三、加一道后置校验

结构约束之外，我们在输出后加了一次程序化校验：

```python
def validate_response(resp, index):
    """校验回答的每一条引用是否真实存在于知识库。"""
    errors = []
    
    if not resp.get("citations"):
        return ["missing_citations"]
    
    for c in resp["citations"]:
        # 1. 文档必须存在
        if c["doc_id"] not in index:
            errors.append(f"unknown_doc:{c['doc_id']}")
            continue
        
        # 2. 条款必须真实存在
        clause = index[c["doc_id"]].clauses.get(c["clause"])
        if clause is None:
            errors.append(f"unknown_clause:{c['doc_id']}/{c['clause']}")
            continue
        
        # 3. 引用片段必须逐字出现在该条款中
        if c["verbatim"] not in clause.text:
            errors.append(f"verbatim_mismatch:{c['doc_id']}/{c['clause']}")
    
    return errors
```

校验失败的处理**不是重试，而是显式降级**：

```python
errors = validate_response(resp, index)

if errors:
    return {
        "answer": "检索到相关内容，但引用校验未通过，需人工确认。",
        "citations": resp.get("citations", []),
        "confidence": "需人工确认",
        "validation_errors": errors,   # 错误详情进日志，不进用户界面
        "matched_chunks": top_k_chunks  # 附上原始检索结果，人可自行核对
    }
```

关键点：**不把有问题的答案藏起来，而是把它降级成”需人工确认”，同时附上原始检索结果让人能自己判断。**

### 四、效果

| 错误类型 | 改造前 | 改造后 | 说明 |
| --- | --- | --- | --- |
| 依据错（引用正确文件、错误条款） | 6.2% | 1.8% | 条款级切片 + 逐字引用双重作用 |
| 依据虚（引用不存在的内容） | 3.1% | 0% | 结构约束 + 后置校验，双重拦截 |
| 越界（自行补充通用知识） | 2.4% | 0.7% | confidence 枚举 + 空引用拦截 |

**“依据虚”降到 0 是最有价值的。**

因为这类错误在改造前是**不可发现**的——用户看不出来。现在哪怕有 0.7% 的越界残留，也会被明确标成”需人工确认”。

**“让错误可见”的实际含义**：错误率从 11.7% 降到 2.5% 是一回事；**更重要的是，剩下的 2.5% 用户能立刻识别**，而不是当成权威答案去执行。

### 五、为什么这个方向对 B 端特别重要

B 端和 C 端对 AI 的容错逻辑完全不同。

C 端场景里，一个错误的回答代价可能只是”用户不喜欢这次交互”。

**B 端场景里，一个看起来正确的错误制度条款，代价可能是有人按错误规定做了事。**

在工程建设领域尤其如此——制度条款被错误引用，后果可能是流程走错、审批违规、责任不清。

所以我形成了一个判断：

> **企业 AI 的目标函数不应该是”准确率最大化”，而应该是”错误可被发现的成本最小化”。**

这个转向带来几个具体变化：

- 不再追求”模型永不答错”（做不到），而是追求”错了立刻知道”
- 评测指标从”准确率”变成”**错误可识别率**“——一个能被人一眼看出错误的答案，危害远小于一个流畅但错误的答案
- 产品设计上加一个”用户报告”入口：用户点一下”这条引用不对”，直接进改进队列

### 六、一个反直觉的副作用：强制引用反而提升了答案质量

我们原本以为”强制引用”会限制模型发挥，让回答变啰嗦、变保守。

**实际观察下来相反。**

模型在必须给出逐字引用时，回答的准确率更高。

原因是这相当于给生成过程加了一道”自检”——模型在写”第十二条规定……”时，倾向于把注意力放到”第十二条说了什么”上，而不是”这个问题通常怎么答”。

**这个约束把任务从”生成答案”变成了”抽取并转述”，而抽取任务对模型的友好度远高于生成任务。**

这不是我的设计，是评测集跑出来的副产品。

但它给了我一个启发：**在企业场景里，”让模型更受限”往往比”让模型更自由”效果好。**

---

### 七、还没解决的问题

**校验依赖结构化索引。** 我们的知识库是条款级结构化的，能精确查到”第几条”。如果是不规则文档，校验粒度会退化到段落级或文档级，”依据虚”的拦截力度会下降。

**逐字引用的长度问题。** 太短的引用（如”同意”）验证通过但没有信息量，太长的引用会拖垮阅读。目前靠提示词控制长度，不够稳定。

**多跳引用的校验。** 当答案需要综合两条以上条款时，校验逻辑是”每条单独存在”，不能验证”这些条款组合起来是否成立”。

**下一步方向**：把校验从”存在性”扩展到”蕴含性”——不只是检查引用片段在不在原文里，而是检查”给定的原文片段是否真的蕴含了答案中的那个论断”。这需要一层轻量的语义校验，思路接近 NLI（自然语言推理）。

---

### 最后

这个项目最让我意外的一点，是**“让错误可见”这个设计本身，提升了答案质量**。

我们一开始的目标是”把错误率降下来”，做的是防御。做完之后才发现，真正的收益来自**把模型的注意力约束到正确的地方**——强制它去抽取，而不是让它去生成。

**防御性的约束，顺带变成了能力性的约束。**

这在企业 AI 里是个好消息：它意味着”更可靠”和”更聪明”不一定是取舍。
