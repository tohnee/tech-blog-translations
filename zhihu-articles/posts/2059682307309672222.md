如今不少超大规模语言模型采用了**混合专家模型（Mixture of Experts，MoE）**。它的核心并不复杂：

> 在扩大模型总参数容量的同时，只让每个 token 激活其中一小部分参数，从而控制单次计算成本。

在稠密 Transformer 中，每个 token 都会经过同一个前馈网络（FFN）。MoE 则将这个 FFN 替换为多个专家网络，并通过 Router 为每个 token 选择少量专家参与计算。

![](https://pic2.zhimg.com/v2-a408c9167d2080d027f17696663d13a1_r.jpg)

理想情况下，不同专家会在训练过程中逐渐形成不同的专长，例如部分专家更擅长处理代码、数学、特定语言或某些语义模式。不过，这种专门化通常是模型自发形成的，并不一定与人类定义的领域一一对应。

MoE 的概念最早可以追溯到 Jacobs 等人在 1991 年提出的混合专家模型。2017 年，Shazeer 等人将稀疏门控 MoE 扩展到大规模语言建模；随后，MoE 被引入 Transformer，并通过 Switch Transformer 等工作得到进一步发展。如今，它已经成为大模型扩展的重要技术路线之一（Brown et al., 2020；Grattafiori et al., 2024；DeepSeek-AI et al., 2024）。

## 最基础的 MoE 层

最简单的 MoE 层可以写成：

```text
def moe_layer(token, experts, router, k):
    # 为当前 token 计算所有专家的路由分数
    logits = router(token)

    # 选择分数最高的 k 个专家
    selected_logits, selected_indices = top_k(logits, k)

    # 计算被选中专家之间的混合权重
    weights = softmax(selected_logits)

    # 对专家输出进行加权求和
    output = 0
    for weight, expert_idx in zip(weights, selected_indices):
        output += weight * experts[expert_idx](token)

    return output
```

假设 token 的隐藏状态为： $$ x∈R^d $$ 模型中共有 $N$ 个路由专家。Router 通常是一个从隐藏维度 $d$ 到专家数量 $N$ 的线性映射： $$ z=xW^⊤,W∈R^{N×d} $$ 输出： $$ z∈R^N $$ 其中，第 $i$ 个元素 $z^i$ ​ 表示当前 token 对专家 $i$ 的路由分数。

模型随后选出得分最高的 $k$ 个专家，将 token 分别输入这些专家，并根据对应权重混合输出：

$$ y=\sum_{i∈S}{g_iE_{i}(x)} $$ 其中：

- $S$ 是当前 token 选中的专家集合；
- $E_{i}$ 是第 $i$ 个专家网络；
- $g_i$ 是对应的混合权重。

假设一个 MoE 层包含 256 个专家，但每个 token 只激活其中 8 个，那么模型可以拥有远大于单次实际计算量的总参数容量，这正是 MoE 的核心优势。

## MoE详细机制

![](https://pic4.zhimg.com/v2-c475b152a9d8b8382b58e8f253d03537_r.jpg)

从流程上看，MoE主要包括**路由**、**分数变换/归一化**、**选择专家**、**混合**等步骤，试图去解决2个根本问题：

- **专家利用率：**所有专家是否都真正得到了使用？
- **专家专门化：**不同专家是否学到了不同的能力，还是只是在相互模仿，从而造成参数冗余？

### 路由

**哈希路由**（Roller et al., 2021）是最直接的一种方式，不需要训练路由器，根据简单规则为token分配专家：ttoken_id mod N，N是专家数量。该方式专家利用率比较高，但是分配完全忽略上下文，会学习到大量重叠的表示，专家专门化程度低。

**学习式路由**最早由 Shazeer 等人于 2017 年提出，它采取了完全相反的思路：让模型自行学习，每个 token 应该由哪些专家处理。具体地，moe_layer中的router是一个可学习的线性层，会为每个专家输出一个logit，同时为了惩罚路由器的负载不均衡，还需要加入一个**辅助损失** 。学习式路由能够形成清晰、彼此分离的专家表示：每个专家都有自己擅长的领域，但存在一个问题：**路由器坍塌**（大多数token集中到一两个专家上）。目前工业界的主流选择都是学习式路由，比如**Qwen**、**DeepSeek**。

**Sinkhorn 路由**学习式路由通常从整体上约束负载均衡（添加负载均衡损失），Sinkhorn 完全取消辅助损失，改为对每一层分别施加正则化，从而直接抑制层内负载不均衡。具体地，分别在 **token 维度**、**专家维度**上归一化，再转换为专家混合权重。虽然 Sinkhorn 可以在所有层中达到接近哈希路由的负载均衡水平，同时保持接近学习式路由的性能，但更好的负载均衡不等于更好的学习效果。

```text
logits -= logsumexp(logits, dim=0, keepdim=True) # token维度
logits -= logsumexp(logits, dim=1, keepdim=True) # 专家维度
weights = exp(logits)
```

### 分数变换/归一化

在最基础的实现中，使用softmax对路由结果进行变换，显然可以使用不同策略进行变换。比如，DeepSeek V3没有对所有专家做softmax，而是独立计算每个专家的Sigmoid 匹配度，选择Top-k专家后只在选中专家间归一化。

假设3个专家的 logits 是：[4, 3, 0]，softmax后的结果是：[0.721, 0.265, 0.013]，第一个专家明显压制了第二个专家（**专家间竞赛，必须分出明显胜负**），而使用Sigmoid计算：[0.9820, 0.9526, 0.5000]，归一化后，top-2的结果约：[0.507,0.493]，更像“**分别判断每个专家是否适合当前token**”。

在DeepSeek V3中，还额外引入一个偏置 $b_i$ ，用于在Top-k选择时进行负载调控，权重计算时仍然只使用 $s_i$ 。专家偏置更像是一个调度修正量：它干预“把 token 分给谁”，但尽量不改变模型原本学习到的语义匹配权重。 $$ S=TopK(s_i​+b_i​,K) $$

### 专家选择

在上述MoE示例中，每次会选择top_k个专家结果，然而对于简单情况，Router分数比较稳定： $$ [0.90,0.05,0.03,0.02] $$ 第一个专家已经占据明显优势，其实top_k=1即可。但对于复杂情况，可能需要3个或者4个专家。**Top-p（Top-p 路由**或**动态专家选择）**不固定专家数量，而是根据 Router 的概率分布动态决定，首先将概率从高到低排列： $$ p(1)​≥p(2)​≥⋯≥p(N)​ $$ 寻找最小的 $m$ ，使得累计概率超过阈值 $P$ ： $$ m = \min \left\{ r : \sum_{j=1}^{r} p_{(j)} \ge P \right\} $$

- Router 越确定，概率分布越尖锐，激活的专家越少；
- Router 越不确定，概率分布越平坦，激活的专家越多。

无论采用 Top-k 还是 Top-p，解决的都是如何从**路由专家**中选择专家。但并非所有能力都需要被路由：语法、基础语义等通用模式往往会被大量 token 共同使用。如果这些知识完全由路由专家分别学习，不同专家就可能重复学习相似内容，造成参数冗余。

因此，一些现代 MoE 模型会同时设置**共享专家（Shared Experts）和路由专家（Routed Experts）**。对于每个 token，共享专家始终参与计算，负责承载通用知识；Router 则从路由专家中选择少数几个，负责处理更具差异化的模式。两部分输出最终相加：

![](https://pic3.zhimg.com/v2-823698b5aca2d1277fcd97df0867e074_r.jpg)

**共享专家**的主要作用，是减少通用知识在不同路由专家之间的重复，让路由专家拥有更多空间形成专门能力。它并不是直接的负载均衡机制，也不能替代辅助损失、专家偏置等路由调控方法。

以两个模型为例：

- **DeepSeek-V3**：每个 MoE 层包含 1 个共享专家和 256 个路由专家。每个 token 都会经过共享专家，同时从 256 个路由专家中激活 8 个，再将两部分输出相加。
- **Qwen2-57B-A14B**：每个 MoE 层包含 8 个共享专家和 64 个路由专家。每个 token 会使用共享专家，同时激活 8 个路由专家。

## 写在最后

MoE 的基本思路并不复杂：把一个 FFN 拆成多个专家，再让每个 token 只调用其中少数几个。但真正深入之后会发现，还是有非常多的技术细节。不同模型往往会围绕路由策略、分数变换、专家选择、负载均衡和系统效率等方面进行针对性设计。

本文只是对 MoE 架构和路由机制的一次初步梳理，很多细节还没有展开（比如在实际代码实现中，往往不会基于token维度遍历专家，而是基于专家维度批量处理token）。后续有机会，会继续探究更加深入的技术细节，并继续撰写相关文章。
