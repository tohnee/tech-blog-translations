## 核心结论

**固定同一个 Kernel Agent，换成一套适合 Agent 编辑、检查和扩展的编译环境，搜索效率、稳定性和最终性能都会明显改变。**

常见 Kernel Agent 直接修改 CUDA、PTX 或某种现成 DSL。编译器报错、正确性结果和延迟数字构成主要反馈。一次 Barrier 死锁、一次资源契约冲突、一次 Pipeline 性能停滞，最终都压缩成了错误日志或单个延迟值，Agent 很难把结果归因到具体调度决策。

CAKE 在 Agent 与 CUDA/PTX 之间加入一层 **CAKE IR**。这层 IR 直接表示 Warp 分工、内存层级、Pipeline、Barrier 和指令形式，同时保留足够的类型、资源和数据流信息，让编译器在生成代码前完成检查与性能分析。编译器随后把 CAKE IR 确定性地下降为 CUDA/PTX，再交给 NVIDIA 标准工具链生成 GPU 二进制。

论文中的“协同进化”包含两个时间尺度：

- **内层循环**：Agent 持续搜索更好的 Kernel 调度。
- **外层循环**：反复出现的能力缺口和失败模式被沉淀为新的 IR 原语、Verifier 规则、Lowering 支持和成本模型校准。

实验固定 GPT-5.6-sol 及其 Scaffold。这里的 Agent 负责提出和修改 Kernel，也参与编译器能力建设；持续演化的系统资产是 Kernel 集合与编译器 Harness。

## 方法全景

一次 Kernel 生成任务沿着下面的路径运行：

```text
数学规格、Shape、正确性 Oracle、目标 GPU
                    ↓
             Agent 编写 CAKE IR
                    ↓
       类型检查、Verifier、成本模型排序
                    ↓
             确定性生成 CUDA/PTX
                    ↓
          NVIDIA 工具链生成 GPU Binary
                    ↓
        数值验证、Benchmark、Profiler
                    ↓
       反馈给 Kernel 搜索或编译器演化

```

四个组件承担不同决策：

| 组件 | 负责的决策 | 产物 |
| --- | --- | --- |
| Agent | Warp 分工、Buffer 分层、Pipeline 深度、Barrier 交接、指令组合 | CAKE IR 候选 |
| CAKE 编译器 | 类型与合法性检查、资源分析、成本估计、机械信息推导、代码生成 | CUDA/PTX 与结构化诊断 |
| NVIDIA 后端 | 物理寄存器分配、后端指令调度、最终机器码编码 | SASS/Cubin |
| Workload contract 与评测器 | Shape、Oracle、容差、目标硬件、Benchmark 与 Profiler | 正确性和性能证据 |

CAKE 论文经常使用 **compiler harness** 这个整体概念。它指 CAKE IR 周围的 Agent-facing environment，核心包括构造检查、Verifier、成本模型和 Lowering。Workload contract、外部 Oracle、Benchmark 与 Profiler 为它提供任务边界和运行期证据。Compiler 是其中负责分析与代码生成的核心部分。

## 抽象层选择

Kernel Agent 需要同时获得硬件控制能力与稳定的编辑接口。现有三类表示各有明确边界：

| 表示 | Agent 看到的主要对象 | 搜索特征 |
| --- | --- | --- |
| Tile 级 DSL | Tile、Block、少量调度参数 | 编辑面紧凑，Warp specialization、Barrier choreography、Memory tier placement 多由编译器处理 |
| CUDA/PTX 与低层 DSL | 线程、地址、寄存器、布局和指令细节 | 控制充分，机械细节多，错误定位成本高 |
| CAKE IR | Warp 角色、资源、Pipeline、Barrier 和硬件指令语义 | 性能决策显式，地址与编码细节由 Lowering 推导 |

CAKE IR 选择“物理调度”作为抽象对象。数学语义由 Workload contract 固定，Agent 负责决定硬件如何执行这项计算。这个边界把专家 Kernel 中真正影响性能的结构暴露出来，同时让编译器承担重复、机械且容易出错的实现工作。

## CAKE IR

### 自底向上的词汇

CAKE IR 的操作集合来源于生产 Kernel。Agent 分析 FlashInfer、CUTLASS、DeepGEMM、FlashAttention-4、Alpha-MoE、TileLang 等实现，提取反复出现的调度结构，例如：

- Warp 角色划分；
- Barrier 协作与跨角色交接；
- 多级 Pipeline staging；
- TMA Descriptor 配置；
- TMEM Accumulator 生命周期；
- Persistent schedule 与多 CTA 协作。

候选抽象会经过硬件原则审查，再通过 Kernel 移植验证表达能力。新 Kernel 暴露缺口后，系统继续扩展 IR、分析和 Lowering。

![](https://pic3.zhimg.com/v2-a8ccd9bbb72ab575af185cfd3b42eb80_r.jpg)
*图 2　从生产 Kernel 提取抽象、修订 CAKE IR、移植验证的循环*

附录给出了八项设计原则：编辑模型贴近 NumPy/PyTorch、性能决策透明、每种操作保持规范形式、静态类型检查、便于分析、IR 变更通过 Kernel 矩阵测试、数据模型与分析规则同步演进、每个操作都对应明确硬件行为。

### 显式调度

CAKE IR 的词汇分为计算、内存搬运、同步、控制与调度四组。程序还会声明五类资源：Shared Memory、Tensor Memory、同步对象、Warp 角色和 Pipeline。资源声明携带 Shape、Dtype、Ownership 与 Lifetime，编译器可以沿着数据流检查生产者、消费者与资源生命周期。

![](https://pic2.zhimg.com/v2-60ce83dfbebc6d3de041bfa01fcc67c3_r.jpg)
*图 3　CAKE IR 的 FMHA 前向调度片段*

图 3 展示了一段 FMHA 前向调度：

- `smem_q` 和 `tmem_acc` 声明 Shared Memory 与 Tensor Memory 资源；
- `load` 和 `mma` 把不同工作交给指定 Warp；
- `pipe` 声明三级 Pipeline；
- `q_full` 显式连接生产者 `load` 与消费者 `mma`；
- `tma_load`、`wait`、`fence_proxy` 和 `mma` 构成数据搬运与计算顺序。

Agent 在 IR 中写下“哪个角色在什么阶段对什么资源执行什么操作”。Lowering 根据这些声明推导 Barrier 地址、Phase bit、TMEM offset、TMA Descriptor encoding 和 Warp identity。

### 布局与资源

CAKE IR 使用具体的存储和访问承诺表示布局，包括 SMEM view offset、Operand byte offset、TMEM column range、Swizzle tag 和 TMA descriptor coordinate。编译器沿数据流检查这些承诺是否一致，并核对目标指令与资源契约。

这种表示让布局错误能够定位到某个 Buffer、Operand 或 Descriptor 决策。Agent 可以直接修改对应调度结构，避免在独立布局代数中继续追踪变换关系。

## 编译器 Harness

### 分析接口

Harness 把反馈分成三种形式：

- **阻断项**：在编译或执行前淘汰违反程序安全、硬件契约、数据一致性和调度语义的候选；
- **报告项**：估计成本，指出主要性能瓶颈；
- **提示项**：给出后续可尝试的优化方向。

GPU 数值验证和实测延迟承担最终裁决。成本模型用于低成本过滤与排序，Profiler 用于核对真实硬件行为。

**表 1 CAKE Harness 暴露的分析与验证类别**

| 类别 | 处置方式 | 作用 |
| --- | --- | --- |
| 程序安全 | 编译前门禁 | 定位同步、时序和内存使用风险 |
| 硬件一致性 | 编译前门禁 | 约束资源、指令和架构契约 |
| 数据一致性 | 编译前门禁 | 检查数据流及生产者、消费者表示的兼容性 |
| 调度语义 | 编译前门禁 | 检查声明式调度的结构约束 |
| 数值验证 | 执行门禁 | 将编译结果与权威外部参考逐项比较 |
| 性能分析 | 报告 | 估计成本并识别主要瓶颈类型 |
| 优化建议 | 提示 | 推荐有潜力的修改方向 |

### 代码生成

CAKE 编译器对合法 IR 执行确定性 Lowering，生成可检查的 CUDA/PTX。CUDA/PTX 随后进入标准 NVIDIA 工具链，由 PTXAS 等后端组件完成物理寄存器分配、后端调度和 SASS/Cubin 生成。

因此，CAKE IR 能够一直走到可执行 GPU Binary，路径中仍然保留 NVIDIA 后端。CAKE 负责前端调度表示、静态语义和代码展开；PTXAS 负责最终机器实现。

同一套角色、Barrier 与 Pipeline 结构可以映射到 Ampere、Ada、Hopper 和 Blackwell。各架构的指令准入、资源规则与 Lowering 分别实现，编译器要求目标架构精确匹配。

一次任务包含四个阶段：

1. Agent 生成结构差异明显的 CAKE IR 候选。
2. IR 构造检查、Verifier 和成本模型筛选候选。
3. 存活候选接受数值验证、Benchmark 和 Profiler 分析。
4. 系统把证据路由给 Kernel 候选、Verifier、成本模型或 IR 词汇。

Workload contract 在任务开始前固定 Shape、正确性 Oracle、Tolerance、Hardware 和允许访问的参考实现。这个契约保证编译器演化始终围绕同一项数学任务和测量口径进行。

## 编译器演化

编译器能力通过两类证据增长。

第一类证据来自生产 Kernel 和硬件文档。Agent 识别新的 Blackwell 指令形式、资源类型、Descriptor 变体和同步模式，提出 IR 与 Lowering 修改。

第二类证据来自搜索过程。Sanitizer 报告、数值错误、非法 Lowering、性能模型误差和调试日志揭示高频失败模式。系统将这些模式分别沉淀为 Verifier 规则、静态检查、Lowering 修复或校准任务。

![](https://pica.zhimg.com/v2-295177855d32219ae35ee6f51aa44362_r.jpg)
*图 4　生产语料与动态反馈共同推动 IR 和 Harness 更新*

每次修改都要同时处理四个方面：

```text
IR 数据模型
   + 合法性与分析规则
   + Lowering 语义
   + Kernel corpus 回归测试

```

编译器改动由 Agent 主要实施，并经过人工 Merge gate。新的 IR 原语扩大后续 Kernel 的表达空间；新的 Verifier 规则让同类错误在 GPU 执行前被识别；新的成本校准改善候选排序。

实验中的 GPT-5.6-sol、模型权重与 Agent Scaffold 保持固定。CAKE 所说的“Harness 演化”指上述编译器环境持续增长。

## Flash-KMeans 冷启动

### 实验设置

Flash-KMeans 用于 Sparse VideoGen2 的语义感知 Token permutation。一次 Lloyd 迭代的主要时间来自 `assign` 与 `centroid_update` 两个 BF16 Kernel，两者占端到端时间的 95% 以上。论文选择计算密集的 `assign`，固定 $B=32$、$N=65{,}536$、$K=1024$、$D=128$，输入为 BF16，累加为 FP32。

两组 Agent 都只能读取数学定义、测试契约、正确性 Oracle、高层代码和黑盒性能基线。CAKE IR 组编写类型化调度，控制组直接编写 CUDA C++ 与内联 PTX。两组使用相同 GPT-5.6-sol、相同 Scaffold 和 8000 万 Provider token 预算，各独立运行三次。经过调优的 FlashML KMeans Triton 实现是性能基线，在 B200 上延迟为 0.938 ms。

**表 2 B200 上三次配对 Flash-KMeans 冷启动结果**

| 表示 | 8000 万 Token 内达到平台期 | 活跃演化时间，中位数 [最小值, 最大值] | 8000 万 Token 时最佳性能，中位数 [最小值, 最大值] |
| --- | --- | --- | --- |
| CAKE IR | 3/3 | 1.89 h [1.02, 2.33] | 1.144\times [1.041, 1.205] |
| 直接 CUDA/PTX | 0/3 | 3.73 h [3.59, 4.34] | 0.928\times [0.852, 1.151] |

![](https://pic2.zhimg.com/v2-21d6c564e7ee176df4e02200f412f821_r.jpg)
*图 5　Flash-KMeans 三次冷启动运行的最佳性能轨迹*

CAKE IR 三次运行都在预算内达到预设平台期，均值在约 5500 万 Token 时越过 FlashML 基线，并继续提升到 8000 万 Token。直接 CUDA/PTX 三次运行在截止点的均值为基线的 0.928 倍，活跃演化时间中位数为 3.73 小时。

这组实验隔离了论文最重要的变量：Agent 与任务保持一致，编程表示和反馈环境发生变化。结果说明结构化调度表示、静态门禁与局部诊断能够把更多搜索预算留给有效的性能决策。

## 前沿 Kernel 合成

前沿 Kernel 任务只向 Agent 提供数学规格、测试、高层接口和黑盒性能基线。具体 Warp 分工、内存分层、Pipeline 和同步方案都由 Agent 在 CAKE IR 中搜索。

### Kimi Delta Attention

Kimi Delta Attention 的 Prefill 包含跨 Chunk 保持的递归状态。CAKE 生成的实现支持固定长度、Packed variable length 和 Tail input，在六个 B200 BF16 Shape 上相对官方 FlashKDA 达到 $2.05\times$ 几何平均加速，通过 Bitwise correctness，并在 SGLang 的 Kimi-K3 端到端 Serving 中验证。生成的 CUDA 已进入 [FlashInfer PR #4262](https://github.com/flashinfer-ai/flashinfer/pull/4262)。Decode 路径在 30 个公开 API Shape 上相对上游 FlashInfer 达到 $1.14\times$ 几何平均加速，对应 [FlashInfer PR #4279](https://github.com/flashinfer-ai/flashinfer/pull/4279)。

![](https://pic1.zhimg.com/v2-1a91f7779865d00501f0e101600e5170_r.jpg)
*图 6　KDA Prefill 在固定 Shape 与六 Shape 目标上的演化轨迹*

图 6 中，橙线记录 $H=96$、$S=8192$ 的固定 Shape 启动，蓝线记录六个 Shape 相对官方 FlashKDA 的几何平均性能。图中采样点均通过正确性检查，六 Shape 阶段在约 10 亿 Token 附近达到两倍以上。

Gated DeltaNet 的 Prefill 与 Speculative decode 也取得相对 FlashInfer 的性能提升，同时保留模型递归状态。MiniMax Sparse Attention 进一步覆盖 Prefill 与 Decode 两类稀疏注意力调度。

### TinyGEMM

TinyGEMM 从 FlashInfer 中源于 TensorRT-LLM 的 Small-M BF16 Kernel 出发。Agent 形成了浅 Pipeline、深 Pipeline、PDL 变体，以及 Batch size 小于 8 时使用的专用实现。在 35 个标准 Shape 上，Kernel time 的几何平均下降 18% 至 23%，对应 [FlashInfer PR #4274](https://github.com/flashinfer-ai/flashinfer/pull/4274)。

GPT-OSS-20B 与 GPT-OSS-120B 在 B200、GB300 上的贪心解码保持 Bitwise identical。另一组 SGLang GPT-OSS-120B 实验中，TP1、并发 128 的输出吞吐最高提升 7.6%，TP4 差异处在测量噪声范围内。

![](https://pic1.zhimg.com/v2-78170be7b3e0d71588f124976facf1aa_r.jpg)
*图 7　TinyGEMM 四 Shape 演化与小 Shape 补强*

首次四 Shape 搜索把几何平均性能推到 $1.274\times$，其中 $N=8$、$M=2048$、$K=2048$ 的目标 Shape 为 $0.940\times$。后续定向搜索把该 Shape 提升到 $1.020\times$，四 Shape 均值达到 $1.334\times$。

### Alpha-MoE

Alpha-MoE 原始实现面向 Hopper。CAKE Agent 将 W8A8 Fused MoE Megakernel 改写到 Blackwell，把 Routed gather、两次 Projection、Activation、Requantization 和 Route-weighted output accumulation 融合进一个 Device program。

相对 FlashInfer 中源于 TensorRT-LLM 的 Pre-routed API，端到端 API 级加速在 $N=256$ 和 $N=512$ 时分别达到 $6.204\times$、$4.025\times$。CUPTI GPU span 复测给出 $1.215\times$、$1.170\times$。API 级收益还包括更少的调度间隙与更简单的 Workspace 管理：参考实现启动五个 GPU activity，Alpha-MoE 只包含一次输出重置和一个 Megakernel。对应代码见 [FlashInfer PR #4287](https://github.com/flashinfer-ai/flashinfer/pull/4287)。

![](https://pic1.zhimg.com/v2-09db84a1c49b4b4c721fad53faac31a4_r.jpg)
*图 8　Alpha-MoE 从 Hopper 到 Blackwell 的五 Shape 演化*

图 8 以第一个正确的 CAKE Checkpoint 作为 1.0 基准。TMA gather4、Persistent schedule、Warp-broadcast metadata 与 Scales 等变化依次进入候选，最终五 Shape 几何平均达到初始 CAKE 的 $1.137\times$。TensorRT-LLM 对照采用前述 API span 与 GPU span 数据。

## Kernel 组合与库级泛化

单个 Shape 上的最快 Kernel 还需要覆盖生产库的完整输入域。CAKE 将这项工作拆成第二阶段：以强单点 Kernel 为 Seed，按 Shape bucket 组织共享或专用变体，再通过 Guard、Fallback 和 Dispatcher 形成可调用的 Kernel Family。

验证集覆盖代表性输入、Held-out input、边界与 Tail case、Guard 重叠与空洞、Fallback 路径。有效 Shape 域在调优前固定，扩展覆盖时使用同一来源的确定性 Unseen shard。性能偏弱的 Seed 会返回单点搜索环节继续优化。

CAKE 的验证语料包含 400 多个静态及编译测试、399 个 GPU 正确性测试、约 28 个 Kernel Family，并包含 100 多个 TensorRT-LLM 移植项。Kernel Family 覆盖 Attention、Dense/Sparse GEMM、MoE、Quantization、Normalization、State-space model、KNN 和 KMeans。

KNN Build、KNN Search、KMeans 在 GB200 上的 Dispatcher-inclusive 几何平均加速分别为 $1.418\times$、$2.116\times$、$1.803\times$，覆盖 112、198、124 个 Shape；全部输出通过正确性检查，KNN Recall 为 1.0。

KNN Build 使用 8 个外层 Family，112 个 Shape 最终落到 80 条观察到的 Route；不同 Family 的几何平均加速分布在 $1.130\times$ 至 $1.909\times$。Flash-KMeans 使用 12 条最终 Route 覆盖 124 个 Shape，其中通用 Gap-fused Route 覆盖 64 个 Shape，D352 Split-K Route 达到 $3.757\times$，整体几何平均为 $1.803\times$。

Dispatcher 的复杂度由测量收益约束。一个物理调度尽量覆盖较大的 Shape 区间，显著不同的调度需求才会产生新 Route。每条 Route 保持独立 CAKE IR 程序，可以单独分析、验证和计时。

## 方法价值

CAKE 把 Kernel Agent 的编程接口提升为一个可以持续演化的系统对象。Agent 在内层搜索显式物理调度，编译器把调度变成可检查、可执行的 CUDA/PTX；外层循环再将高频能力缺口沉淀进 IR、Verifier、Lowering 和成本模型。

这套方法的长期资产有两类：已经生成的高性能 Kernel，以及下一批 Kernel 可以直接复用的编译器知识。论文最有价值的 insight 也在这里：**固定 Agent 的能力可以通过改善其的编译环境被持续放大。**
