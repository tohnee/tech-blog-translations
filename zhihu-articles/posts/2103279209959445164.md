> 编译 | 段小草 + Astra

在 Claude Platform 上构建智能体时，减少子智能体的使用，转而渐进式披露上下文和工具，可以提高质量，同时降低成本和延迟。本文介绍何时迁移，以及如何迁移。

*如果你已经在 Claude Platform 上构建了包含多个子智能体的智能体，可以使用我们的[迁移工具包](https://github.com/anthropics/single-agent-loop-kit)，看看哪些子智能体适合并入主智能体循环。它会运行一个引导式工作流，识别你的设计模式、评估替代方案，并验证最佳做法。其中包含一个演示，你可以先在模拟系统上试用，再在自己的智能体上运行。*

子智能体是拥有独立上下文窗口、工具和指令，并[由协调器编排](https://claude.com/resources/articles/multi-agent-coordination-patterns)的智能体，也是智能体设计的核心组成部分。它们在验证、并行工作和模块化权限管理方面很有效。我们使用 Claude Platform 构建的许多自有智能体都采用了子智能体，例如我们的[多智能体研究系统](https://www.anthropic.com/engineering/multi-agent-research-system)。

不过，最近 Applied AI 团队发现了一类企业智能体部署：将路由器、规划器和领域子智能体并入主智能体循环，会带来收益。在[我们对多项企业部署的比较中](https://claude.com/resources/articles/the-anatomy-of-effective-commerce-agents#:~:text=In%20our%20comparisons%20across%20several%20enterprise%20deployments,latency%20per%20task)，[配备技能的单个智能体](https://claude.com/resources/articles/building-agents-with-skills-equipping-agents-for-specialized-work)在质量上经常优于“一条提示词包办一切”的设计和子智能体设计，而且每项任务的成本和延迟往往也更低。

例如，一家公司发现，其面向客户的智能体包含十几个专门子智能体，这使得符合品牌调性的一致体验难以维持，还增加了延迟，损害了用户体验。

我们也经常看到一些智能体设计方案沿着熟悉的路径发展：意图分类器、固定的多步推理流水线、用户细分分组、独立的推荐分支，最上面再加一个多智能体编排器。

在这些情况下，我们经常得到的反馈是，这套结构中的大部分都在替模型做它已不再需要别人代劳的工作；一条清晰的系统提示词、4-5 个轻量的数据工具，以及严格的输出护栏，就足以覆盖用例的大部分需求。

需要明确的是，子智能体仍有用武之地，包括在前沿研究中。遇到以下情况时，可以使用子智能体：

- 单智能体循环因上下文膨胀而出现可测量的性能下降；或者
- 多项任务需要使用全新的上下文窗口并行处理，而且这些窗口可以在任务完成后丢弃；或者
- 单个智能体难以选择合适的工具，或系统提示词中存在相互冲突的指令。

但我们太常看到企业为每个团队或每类问题都配上独立的子智能体，结果智能体架构变成了组织架构图的翻版——这就是康威定律在起作用。

本文将结合我们在大型组织中构建智能体时积累的最佳实践，解释何时应考虑将子智能体并入主智能体循环。

## 大型组织构建智能体时的常见失败模式

企业往往希望构建一个智能体，将多种产品和能力整合到一个统一的客户界面中。

通常，每种能力由不同的团队负责，因此企业会先让各个团队分别构建自己的智能体，再由一个中央平台团队在上面构建编排器。这可以采用多种结构，包括“编排器—子智能体”，或者由一个智能体通过 MCP 工具调用特定的其他智能体。

这看似是最简单的解决方案，却会立即在以下方面引入复杂性：

- **上下文管理：** 你需要决定智能体之间交换哪些上下文，而细节往往会在来回传递中丢失。
- **子智能体泛滥：** 每个团队都交付自己的子智能体，最终企业拥有数百个功能重叠的子智能体，却没有强制执行的标准，也没有明确的负责人。
- **拼接怪物般的提示词：** 每个团队都往系统提示词中加上一句话，结果规则彼此冲突，表达风格也不统一。
- **未经审核、过度局部化的评估：** 每个人都添加自己的评估，过度针对各自的子任务进行优化。没有人负责或维护整套评估，而管理层却根据这些被稀释、过度局部化的分数做决策。
- **延迟：** 多智能体架构的复杂性会增加延迟。一位客户将自己的多智能体运行框架与单智能体循环进行比较，发现后者的运行速度大约是前者的 2 倍。

## 使用渐进式披露的智能体循环

上述“编排器—子智能体”设计，是协调跨团队构建的专门智能体的一种合理方式；但通常，更有效的做法可能是**通过技能渐进式披露上下文**，以及**通过工具搜索渐进式披露工具**。换句话说，智能体看到的是技能和工具的简短描述，只有在需要时才会完整加载它们。

这种方法之所以可能合理，有三个原因：

- **共享上下文能产生更好的答案：** 对于运行时间较长的智能体，我们希望多个不同任务的上下文都留在主上下文窗口中。见过前面每一步结果的智能体，可以将这些结果联系起来，得到比子智能体返回的一组摘要更丰富的输出和更好的洞见。这也意味着[更少的上下文窗口，以及更少的有损交接](https://claude.com/resources/articles/building-multi-agent-systems-when-and-how-to-use-them)。
- **渐进式披露可以防止上下文膨胀：** 这项技术让团队能够构建可完成多种任务的单个智能体，而不必把全部上下文立刻加载到一条很长的系统提示词中。这消除了过去团队将工作拆分给多个子智能体的主要原因。事实上，我们[将 Claude Code 面向更先进模型的系统提示词缩减了 80% 以上](https://claude.dev/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models/)，其中一部分缩减就来自对技能和工具的渐进式披露。
- **模型能力更强了：** 从 Opus 4.5 开始，模型在单个循环中能够处理的事情，远超大多数团队的预期。Opus 5.5 和 Fable 5.1 的思考功能无法关闭，而近期的模型也越来越多地在执行过程中叙述进展、检查工作，这使运行框架中的某些组成部分变得多余。每一个新模型，都让你能够将更多决策从运行框架转交给模型本身。更简单的循环也更容易迁移到下一代模型；在我们帮助客户完成的迁移中，僵化的多智能体结构往往恰恰阻碍了新模型承担更多工作。

单智能体循环设计需要严格管理：精心维护系统提示词，让技能和工具描述在恰当的时机触发，并有意识地处理上下文窗口、记忆和笔记。本文将在后续章节中深入讨论迁移和设计方面的考量。

应该由一个中央团队负责端到端质量和系统提示词，在每个新工具和评估发布之前进行审核。保持这个中央团队规模精简，有助于快速迭代，并降低大型组织内部的协调成本。

如果你选择多智能体路线，就从可能奏效的最简单模式开始，例如“生成器—验证器”、“编排器—子智能体”或其他模式。**按上下文划分：给每个子智能体分配一项不太依赖系统其他部分的工作，并让它返回精炼的结果**，以此有效划定分工边界。独立的研究路径、具有清晰接口的独立组件，以及黑盒验证，都是合适的候选任务。当智能体按问题类型拆分时，它们就会陷入“传话游戏”，来回传递信息，而每次交接都会降低信息的保真度。

## 如何将子智能体并入主智能体循环

许多团队已经在生产环境中运行一个编排器和一组专门智能体。我们建议逐步朝以下单循环设计演进：

- 一个模型和一个上下文窗口运行开放式工具循环，并由运行框架设置限制，包括轮次预算、成本预算和写入门禁。
- 每一轮，模型发出一批工具调用。运行框架并行执行这些调用，并将原始结果返回给同一个模型；模型随后决定下一步：再发起一批调用、向用户提问，或者给出答案。
- 模型作答或触及[预算](https://platform.claude.com/docs/en/build-with-claude/task-budgets)时，循环停止。作答后，还可以选择运行目标检查或验证器检查。
- 模型在第一轮将计划写入上下文，并随着结果返回而修订计划。这是相较于“编排器加专门智能体”配置的主要变化：制定计划的模型也是执行计划的模型，因此它可以在一轮执行过程中修改计划。
- 上下文仍然会被加载，但由智能体自行管理： - 不再需要一个依据规则目录重写计划的代码步骤，因为每一步都由模型决定。
- 执行顺序和领域流程移入**技能**。
- 硬性限制，例如验证和审批门禁，以及对话过程中出现的其他需求，例如记忆查询，移入**工具**。
- 仍然可以使用代码加载成本低廉且几乎总是相关的内容，例如实体消歧步骤；也可以在循环调用的工具内部，用代码处理机械性环节，例如构造载荷、解析数据流，以及恢复澄清流程。

这种单循环设计也有助于实现许多团队努力追求的最终形态：一个理解用户高层目标并代其行动的智能体，因为它将智能体学到的一切都保存在同一份上下文中。

以下建议说明，团队可以如何分阶段从多智能体系统过渡到单智能体循环，以及多个团队在这一过程中如何持续为这个智能体贡献能力。

### 任务完成评估

第一步是创建一套评估集，帮助你确定是否应该将某个子智能体并入主智能体循环。我们见过有效的评估结构是：由中央团队负责一套共享的端到端评估集，同时，各技能的负责团队随技能一起交付规模较小的评估集。即使只有 10 个黄金样例，也足以起步。

按照评分标准评判智能体的最终消息，是跟踪答案质量的良好起点。在你仍然保留编排器时，还应该跟踪路由准确率：它是否选对了子智能体？子智能体并入主循环后，则改为检查智能体是否加载了正确的技能，或者调用了正确的工具。逐步朝任务完成评估演进很有帮助，因为在比较架构时，任务是否完成最为重要。

如果内部系统难以回放、用户参与又难以模拟，这件事可能会很复杂。我们内部有一种有效做法：为重要事件记录时间戳，以便之后回放这些事件，运行有针对性的评估。

### 逐步减少子智能体

向单智能体循环演进，需要将子智能体并入工具和技能。这可以通过合并领域子智能体、将它们作为工具调用，或用技能和工具替代它们来实现。

### 合并领域智能体

在第一次合并之前，先构建一个小型端到端评估。然后，**从使用最多的子智能体开始，按共享上下文逐步合并。**

[合并那些专门智能体](https://claude.com/resources/articles/building-multi-agent-systems-when-and-how-to-use-them)：它们可能依赖彼此的输出形成调用链、处理相同的数据，或经常一起被调用。例如，如果相当一部分生产流量都先调用一个专门智能体、再调用另一个，那么这两者就是紧密耦合的一对，适合考虑合并为一个领域智能体。

### 将子智能体作为工具调用

当上述三个条件之一成立，因此你决定保留某个子智能体时，让主智能体将子智能体作为工具调用，可能会很有效，这样主智能体就能继续与用户对话。

只有当子智能体需要直接与用户交谈时，我们才建议进行完整交接，让子智能体接管对话。除此之外，都可以转为主循环中的技能加工具。

这样，你就能为子智能体定义统一的响应结构，让主智能体根据真实数据核验结论，并精简最终综合步骤所需的输入。这是一个不错的第一步，因为你不必**重写**子智能体。在决定是否将任何子智能体并入主智能体之前，它还能为任务完成评估提供一个**基线**。

不过，某些失败模式仍会存在：

- 每个专门智能体都有自己的提示词、上下文、负责团队和评估
- 每次调用仍然返回一份有损摘要
- 每次调用都是一个嵌套的模型循环，会增加延迟

### 通过技能和工具将子智能体并入主智能体

每次并入一个子智能体：将它的提示词转为技能，将 API 调用转为 MCP 工具。比较保留和不保留该子智能体时的评估表现，再决定保留哪种方案。

比较时，不要只看最终分数，还要看看哪些任务的结果发生了逆转。我们曾在一个示例客服智能体上测试这种做法：将一个子智能体并入另一个，降低了延迟，却也破坏了一个原本能够通过的流程。主智能体拿着订单查询工具自行回答，没有向负责配送的专门智能体询问送达日期。

每次改动之前，都要确保评估中为生产环境里每条协同运行的智能体链，以及智能体不能违反的每条规则，分别安排了任务；而且每个任务都要运行不止一次，因为上述这类故障在两次运行中只出现了一次。

## 多个团队如何共同贡献于一个智能体

领域推理知识可以从知识库、技能和 MCP 工具中检索获得。各团队可以将自己负责的对象从智能体转为技能和工具，由一个精简的中央团队继续负责系统提示词和端到端质量。这包括在新的技能、工具和评估发布之前进行审核。

### MCP 工具

当智能体需要执行操作、从系统中读取实时数据，或以固定结构返回结果时，工具是合适的选择。迁移过程中，你也可以借助工具继续调用子智能体。我们建议按用户意图对工具分组，而不是每个 API 对应一个工具，因为系统提示词中的工具定义一旦超过 30-50 个，工具选择表现往往就会下降。

使用支持延迟加载的[工具搜索](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)，减少硬性前置条件，并将确有必要的前置条件移入工具。例如，如果 Y 需要 X 的输出，Y 的工具就检查该输出是否存在，并返回模型可以据此行动的指令。按用户设置权限也采用同样的方式：每个工具检查调用它的用户可以查看什么、执行什么，并返回模型能够读懂的明确拒绝信息。这样，一个循环就能服务于具有不同访问权限的用户，而不必为每个权限级别配置独立的智能体。

### 技能

当智能体需要了解某个团队如何工作时，技能是合适的选择，例如过去保存在专门子智能体提示词中的步骤、规则，以及需要判断的事项。

我们扩展技能库的方法，是将维护工作交还给编写技能的人。Claude 可以借助那些能够构建、测试和精简其他技能的技能，承担其中的繁重工作。

为了防止技能泛滥，可以让每个团队的直接负责人（DRI）负责本团队的技能，确保它们精心编写、彼此有清晰区别，并在交付时附带适当的评估。

- **/skill-creator** 可以让你编写从一开始就结构完善的新技能，也可以审查已有技能，对其进行精简、去重和重构。
- **/skill-doctor** 可以让你看到技能库中每项技能的成本，以及它实际被使用的频率，并删除无用的负担。

### 知识库

对于智能体只在部分时候需要的参考资料，知识库是合适的选择。事实和参考资料，例如政策、指标定义和产品规格，可以放在模型调用的搜索或查询工具背后，也可以作为技能内部的参考文件一同交付。避免让[代码检索这些上下文，再粘贴到提示词中](https://claude.com/resources/articles/seeing-like-an-agent)。

## 加快这项工作的工具

我们最近[发布](https://code.claude.com/docs/en/commands)了一组 Claude API 技能，可以协助完成上述大部分工作。我们的[迁移工具包](https://github.com/anthropics/single-agent-loop-kit)将这些技能串成一个引导式工作流，用于评估多智能体系统，并将其迁移到单智能体循环。它包含一个演示，你可以先试用，再在真实系统上运行：

- **/claude-api build-eval：** 可以帮助创建由中央团队负责的第一套端到端评估集，或由各团队随技能交付的小型评估。
- **/claude-api prompt-audit：** 可以标记提示词、技能和工具描述中为旧模型编写的指令，并以差异补丁的形式提出修正建议。你可以对系统提示词运行它，找出那些为较早模型添加、如今却让智能体变慢或更僵化的规则。各团队的 DRI 也可以对自己的技能和工具描述运行它。
- **/claude-api hillclimb：** 可以针对已有评估迭代改进应用。它可以用于“并入还是保留”的比较：将一个子智能体转为技能加工具后，让它迭代优化技能和工具描述，看看并入后的版本能否达到或超过子智能体的表现；它也可以用于改进系统提示词。
- **/claude-api cost-optimize：** 分析调用的去向，并从提示词缓存、削减不必要的输入和输出 Token、思考投入程度以及模型选择等方面提出节省方案，每次只改变一项。这有助于在给定设计下降低成本和延迟。

随着模型演进，我们对如何最好地使用模型的理解，以及最佳实践方面的指导，也会随之演进。因此，相比任何一种具体架构，其背后的原则更重要：进行测量，每次只改变一件事，保留经得起检验的做法。

这里讨论的正是这样一种情况。随着模型能力增强、智能体持续运行的时间延长，你的更多子智能体都可以转为技能和工具。不过，你不必一步到位。先构建一个小型端到端评估，并入一个子智能体；只有当并入后的版本得分更差时，才继续将它保留为子智能体，然后重复这个过程。
