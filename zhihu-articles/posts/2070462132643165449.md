## 任务调度模型

下图展示了从 CPU 任务到 GPU 计算核心的调度流水线。CPU 任务将内核启动命令插入到 CUDA Stream 中，而这些 CUDA Stream 会被映射到数量更少或相等的 GPU Channel 上。某一时刻哪些 GPU Channel 可以访问计算/图形引擎，由运行列表 Runlist 来决定，因此运行列表 Runlist 是核心仲裁者。

![](https://pic2.zhimg.com/v2-2fe3374e5b0545a39a92e8bb51776f1b_r.jpg)

GPU 运行列表 Runlist 由若干通道组成的时间片组（TSG）构成。默认情况下，TSG 以工作保持型（work-conserving）、可抢占的轮询顺序执行。一个 TSG 被调度上引擎后，只要它里面还有通道有命令没发完，调度器就不会主动把它换下去（除非被抢占或时间片耗尽）；当某个 TSG 处于活动状态时，其包含的所有通道中的命令会被拉取并在运行列表关联的引擎上执行。每个 TSG 都关联一个时间片；该时间片耗尽后，运行列表调度器会抢占正在执行的命令，并切换到下一个 TSG。若 TSG 内所有通道的命令均已执行完毕，也会触发此类切换。需注意，同一 TSG 中的所有通道必须来自同一上下文。

## 任务调度示例

按照内存布局在下图中展示了一个包含三个任务的运行列表示例：在此例中，TSG 0 将执行 2 毫秒，期间计算/图形引擎会接收并执行来自通道 0 和通道 1 的命令；2 毫秒后，通道 0 和通道 1 中所有活跃命令将被抢占，GPU 转而执行 TSG 1 各通道中持续 2 毫秒的命令。此过程对 TSG 2 重复执行，随后循环回到 TSG 0。

![](https://pic1.zhimg.com/v2-03715ca7ac130f5bc13b7f028231f9a4_r.jpg)

这种 GPU 调度算法确保计算/图形引擎在同一时刻仅有一个上下文处于活跃状态，也就是说切 TSG 的那一刻，其实就是切上下文的那一刻。

## 任务调度流程

调度模型图如下所示：

![](https://picx.zhimg.com/v2-2d1c963de363aa821e01412847d79fc7_r.jpg)

### 1、调度初始化

任务通过 GPU 内核驱动程序初始化其调度状态。该状态包含一个 pushbuffer，并被封装为通道（channel）。所有任务的通道与上下文信息一同封装到时间片组（TSG）中。TSG 通过插入 GPU 的运行列表（runlist）变为可运行状态，同时用户可访问的 pushbuffer 指针会被传递到用户空间。

### 2、command -> stream -> channel

当请求 GPU 操作时，相关命令会被排入流（stream）中，而这些流会被映射到 pushbuffer 中。命令可能包括内核启动、复制操作以及其他各类指令。如果没有显式指定流，则会构造一个默认或隐式流。由于通道的推送缓冲区被映射到用户可写内存中，命令入队无需系统调用。

### 3、channel -> runlist

命令会在 pushbuffer 中累积，直到 GPU 硬件调度器（GPU Host Interface）选择一个通道进行调度。选择过程分为两个层次：首先，GPU 全局以轮询方式在各 TSG 之间分配时间片；其次，在当前活跃的 TSG 中，所有通道会被循环扫描，以查找有待处理命令的 pushbuffer。

### 4、runlist -> engine

一旦 GPU 硬件调度器识别出有待处理命令的通道，便会利用硬件推送缓冲区 DMA（PBDMA）单元将命令从 CPU 拉取到 GPU。随后，这些命令会被解析并传递给特定引擎的调度器。

## 任务调度流程实例

这部分参考了下面这篇 Blog：

[GPU隔离技术的分析与改进](https://juejin.cn/post/7633957934821310502)

![](https://pica.zhimg.com/v2-6580544234b1311452626f47a2245e98_r.jpg)

GPU Host Interface 是 CPU 与 GPU 之间的桥梁，由 runlist processor 和 context switcher 组成：

- **runlist processor** 负责扫描 runlist，选择下一个待运行的 channel。
- 选定 channel 后，如果该 channel 的 context 与当前正在运行的 context 不同，则由 **context switcher** 执行上下文切换操作。

具体调度流程如下：

1. 从驱动角度看，为了向 GPU 提交计算或数据拷贝等请求，会为每个程序创建一个或多个 channels。
2. 这些 channels 被组织成时间片组（TSG），同一 TSG 内的 channels 共享相同的 GPU context 信息。
3. 每个 TSG 会根据所分配的 Engine type 找到对应的 runlist。
4. GPU Host Interface 通过读取 runlist 来查找下游 Engine 需要完成的工作。具体来说，GPU Host 识别出有待处理命令的 channel 后，会从相应 runlist 上按时间片轮转方式摘取一个 TSG，再从该 TSG 中选择相应的 channel，并将其调度到特定的 Engine 上运行。
5. Engine 执行 channel 中提交的命令，完成计算或数据拷贝任务。

以 X86_64 平台的 A10 机器上的 trace 结果为例，一个常见的 CUDA 程序默认会创建 16 个 channels、3 个 TSG 以及 3 个 runlist。其中，8 个用于计算的 channels 被加入到一个 TSG 中，该 TSG 默认分配 Compute/Graphics Engine；另外 8 个用于数据拷贝的 channels 被分别加入到两个 TSG 中，分别对应两种 COPY Engine。A10 卡上的默认映射关系如表所示。

![](https://pic1.zhimg.com/v2-d9ac93213f5d8eb4e4e9779ea9de664c_r.jpg)

每种 Engine 会被绑定到一个 runlist，在 A10 机器上，CUDA 程序用到的 Engine 和 runlist 的对应关系，通常下表所示：

![](https://picx.zhimg.com/v2-cee26362799138eaa1c8fc8fd4c67ac9_r.jpg)

在上表中，Timeslice 指的是 runlist 中每个条目（即 TSG）在一次调度中默认最多可执行的时间。以 runlist0 上的 TSG 为例，其时间片为 2ms。这意味着，在不发生抢占的情况下，该 TSG 被调度到 Compute/Graphics Engine 上后，默认最多可连续运行 2ms。只有当 TSG 用满 2ms 的时间片，或在 2ms 以内就已将所有命令执行完毕时，TSG 之间才会发生调度切换。

由此可见，在单个 GPU 上混合运行多个任务时，TSG 之间的切换以及上下文切换是影响任务延迟的主要因素。

> **TSG 的切换会带来 Context 的切换。**

可运行 context 被称为通道（Channel）。此外，通道包含用于将 GPU 虚拟内存地址解析为物理内存地址的内存状态，以及指定执行任务的引擎状态的引擎状态。每个通道的持久化状态存储在 RAMIN 中，而执行状态（亦称主机状态）则驻留在 RAMFC 中。
