## 一、先说结论

把 KV cache 从 BF16 压到 INT2，理论上内存流量降到 1/8，decode 注意力就该快 8 倍。实测不是：论文给出的数字是，现有 2-bit 融合 kernel 在 H100 上只跑到峰值 HBM 带宽的 30.7%，在 B200 上只有 14.5%。

FOSCAR 的答案是：**瓶颈不在带宽，在指令发射（instruction issue）**。把每个 KV 值解包成浮点、再乘 scale 加 offset，这两步在每个值上都要花指令；位宽越低，字节搬得越快，这部分固定成本占比越高，最后把 kernel 钉在指令上而不是内存上。

它的做法叫**仿射折叠（affine folding）**：scale 和 offset 不再施加到每个 KV 值上，而是施加到矩阵乘的**另一个操作数**（Q 或 P），或者施加到**部分积/输出**上。数学上恒等，算术上把「每值一次乘加」变成「每组每头几次乘加」，减少最多两个数量级。

结果：H100 上 INT2 kernel 对 FlashInfer BF16 的几何平均加速 3.36×，对 TensorRT-LLM FP8 是 2.03×；B200 上分别是 2.67× 和 1.48×。接进 SGLang 做 100K 长上下文服务，峰值吞吐比 2-bit 基线高 170%、比 16-bit 基线高 341%。

## 二、decode 注意力在流什么

自回归 decode 每一步，都要为每个活跃请求把整条 KV cache 从 HBM 读一遍：QK 乘一遍、PV 乘一遍。上下文越长、batch 越大，这份流量越大。所以把 cache 打包成 2/4-bit 整数，是最直接的省带宽手段——KIVI、KVQuant、Kitty、OSCAR、SAW-INT4 都是这个路子。

但「字节少了」和「时间少了」是两件事。低比特 kernel 仍要在矩阵乘之前把整数值还原成浮点：解包、INT 转浮点、乘 scale、加 offset。如果这些工作在寄存器里做，它不占 HBM 带宽，占的是 warp scheduler 的发射槽。

论文先把这件事量化了。下图是 batch=128、上下文 32K 时，各 kernel 的**有效 KV 访问吞吐**（一次读取的 KV 字节数除以 decode 时间，再除以峰值 HBM 带宽）：

![](https://pica.zhimg.com/v2-de9c4b7e4a0690f1c83d1c2e692f46c0_1440w.jpg)

图 1：各 kernel 的有效 KV 访问吞吐占峰值 HBM 的百分比（batch 128、32K 上下文）

看两组数就够：FlashInfer BF16 在 H100/B200 上都超过 90%；而 BitDecoding 的 INT2 kernel 只有 30.7% 和 14.5%，KIVI、Kitty、OSCAR 也都在同一量级。FOSCAR 自己做到 91.3%（INT4）/60.6%（INT2）和 68.6%/44.4%。

注意一个反直觉的现象：**位宽越低，吞吐占比越差**。这不是因为低比特 kernel 写得差，而是因为分子（字节）在缩小、分母（时间）没同步缩小。

## 三、算一笔指令账

论文的核心论证是一道除法。记：

- 构造一个操作数并算出 s·q + z 需要 a_issue 个 lane-slot（一个 warp lane 上发射一条指令 = 一个 lane-slot）
- GPU 峰值指令发射率 C_issue（lane-slot/s）
- 峰值 HBM 带宽 B_HBM（byte/s）
- 每个量化值占 B_elem 字节（INT4 = 0.5，INT2 = 0.25）

那么「以峰值带宽流 KV」这件事本身，就要求每字节的指令数不超过 C_issue / B_HBM。H100 这个预算是 **9.99 lane-slots/byte**，B200 只有 **4.65**。

而逐值重建要花多少？H100 上，四个 BF16 操作数需要 2 条 SHF + 2 条 LOP3 做 INT→FP，再用 2 条 HFMA2 算 s·q+z（每条产出 2 个 BF16）——共 6 条指令。四个值在 INT4 里占 2 字节、INT2 里占 1 字节，于是需求是 3 和 6 lane-slots/byte。也就是说，**光是反量化，INT4 吃掉 H100 预算的 30%，INT2 吃掉 60%**，还没算 softmax、PV、归约。

B200 更紧张：峰值 HBM 涨了 2.39 倍，指令发射只涨了 11%。重建四个值要 6 + 2 = 8 个 lane-slot（多两条 F2FP 转成 FP8/FP4），INT4 就是 4 lane-slots/byte（86% 预算），INT2 是 8——**超过硬件预算 1.7 倍，无论怎么写都不可能跑到峰值带宽**。

![](https://picx.zhimg.com/v2-886c235bc94fb2dba68e2283361cde59_1440w.jpg)

图 2：左：各代 GPU 的峰值吞吐缩放（Rubin 相对 H100：指令发射 1.94×、HBM 6.57×、Tensor Core 17.69×）；右：每打包字节的指令槽需求

这张图右边的对比最有信息量：H100 上 INT2 需求 6、预算 9.99；B200 上需求 8、预算 4.65。**同一段代码换到新卡上，反而更不可行**——因为 B200 的带宽涨得比发射率快得多。FOSCAR 把需求压到 2.13（H100 INT4）、4.25（H100 INT2）、0.88 和 1.00（B200）。

## 四、仿射折叠：把 s 和 z 从每个值上挪走

原理非常朴素。设 C = A·(s·q + z)，其中 A 是另一个矩阵（Q 或 P），q 是量化值，k 是归约轴。如果每一行 k 共享一个 scale s_k 和 offset z_k：

C[i,j] = Σ_k A[i,k]·(s_k·q[k,j] + z_k) = Σ_k (s_k·A[i,k])·q[k,j] + Σ_k z_k·A[i,k]

左边那项是「把 A 按列缩放后和 q 乘」，右边那项是「A 的行和按 offset 加权，作为输出修正」。论文叫 **operand-fold**：scale 折进另一个操作数，offset 变成一次额外的输出修正——两者都不需要还原 q 的每个元素。

如果换成每一列 j 共享 s_j、z_j（沿归约轴不变），则两项都能提出求和号：

C[i,j] = s_j·Σ_k A[i,k]·q[k,j] + z_j·Σ_k A[i,k]

这就是 **acc-fold**：scale 乘在累加结果上，offset 乘在 A 的行和上。两种折叠在精确算术下与「逐值反量化」完全等价。

![](https://pica.zhimg.com/v2-92a47fdea4d4435e2a2a09f183033754_1440w.jpg)

图 3：C = A(sq+z) 的两种折叠方式，上为 operand-fold，下为 acc-fold

关键是**哪种量化方式配哪种折叠**，这一步错了就白算。因为 K、V 在注意力里都是 [L, D] 的 tile：

- QK 沿 D 归约。token-wise 的 s、z 沿 D 变化 → 只能落到部分积上，用 acc-fold；channel-wise 的 s、z 沿 L 不变 → 可以折进 Q，用 operand-fold。
- PV 沿 L 归约。token-wise V 的 s、z 沿 D 不变 → 折进 P，用 operand-fold；channel-wise V 的 s、z 沿 L 变化 → 用 acc-fold。

![](https://pic1.zhimg.com/v2-a13a492561cf09d6895514b7104b1630_1440w.jpg)

图 4：K 和 V 在 token-wise / channel-wise 两种分组下各自对应的折叠方式

由此带来两条工程约束。第一，acc-fold 的部分积**不能跨量化组**：跨组的归约必须在组边界把当前部分积乘上该组的 scale、加上 offset 修正，再累加。operand-fold 没这个问题，因为 scale 早在乘法之前就进了另一个操作数，累加器可以跨组连续累加。第二，修正的顺序不能错：QK 的修正必须在 softmax **之前**（否则 exp 会把误差放大），PV 的修正必须在除以 softmax 分母**之前**。

收益可以直接算：每存储值原本一次乘加，折叠后是每组每头 2 次（一次 scale、一次 offset 乘加），摊到每个值上是 2·hq/g 次，hq 是共享同一 KV 头的 query 头数、g 是组大小。hq=4、g=128 时是 16 倍削减；**盈亏平衡点是 g = 2·hq**，而 GQA 模型通常 g ≥ 32，所以最多能省 64 倍。

## 五、连 INT→FP 转换也省掉

折叠解决了仿射运算，但「把整数变成浮点操作数」这一步还在。FOSCAR 的做法是**直接用位模式造浮点数**：

Hopper 上用 mantissa injection：把 4-bit 或 2-bit 的 q 与固定常量 0x4300 做按位或，得到的 BF16 恰好等于 q + 128。一条指令一个值。

Blackwell 上更巧：把整数位模式直接放进浮点操作数的低位、高位补零。INT2 的 0/1/2/3 位模式在 FP4（E2M1）里正好表示 0/0.5/1/1.5，即 y = q/2；INT4 的低 4 位放进 E4M3 的尾数，得到 y = q·2⁻⁹。代价只有 0.19 和 0.38 条 ALU 指令每元素。

代价是操作数的数值变成了 y = α·q + β，和存储的整数不一样。补偿办法还是折叠：把 q = (y−β)/α 代回 x = s·q + z，得到 x = s′·y + z′，其中 s′ = s/α、z′ = z − β·s′。s′、z′ 在写 cache 时就以 FP32 算好，运行时零成本。

![](https://pica.zhimg.com/v2-d6596fc47447b50fa822d5e794dfde58_1440w.jpg)

图 5：INT2 K 的寄存器打包布局（左）与从 global memory 到 Tensor Core 的操作数流（右）

打包布局必须配合 Tensor Core 的操作数格式：Hopper 上每个 32-bit 寄存器交错放成对的 2-bit 值，一次移位加一次掩码合并就产出两个 BF16；Blackwell 上 16 个 2-bit 值排成 8 个通道对，一次移位加两次掩码直接产出 16 个 FP4 操作数。TMA 负责 global→shared 的搬运，剩下的在寄存器（Hopper）或 shared memory（Blackwell）里完成。

论文顺手报了一个容易踩的坑：16 个 INT4 位模式里有 7 个落在 E4M3 的 subnormal 区间，而 PTX 规范对 subnormal 作为矩阵操作数的行为**未定义**。作者在 B200 上把两种操作数位置、两种 shared 布局都测了一遍，结果与 FP64 参考一致——但这属于「实测可用」，不是「规范保证」。

## 六、两代 GPU，两套流水线

Hopper 和 Blackwell 的累加器位置不同，流水线也就不同。

Hopper 的 wgmma 累加到发起它的 warpgroup 自己的寄存器里。所以 FOSCAR 用 1 个 producer warpgroup 跑 TMA，2 个 consumer warpgroup 交替处理偶数/奇数 KV tile，各自维护 online softmax 状态和输出累加器，最后合并。tile 是 64 token。

Blackwell 的 tcgen05 累加到 tensor memory（TMEM），CTA 内其他 warpgroup 也能读。于是拆成 4 个 warpgroup：一个管搬运与 mma 发射，一个在 shared memory 里构造操作数，一个从 TMEM 读 QK 结果做 softmax、顺便把 P 量化成 E4M3，最后一个读 PV 结果、维护 running output、做 V 的修正。tile 变成 256 token。

![](https://pic1.zhimg.com/v2-dec8080e99d85e04a7b3367957a3aa22_1440w.jpg)

图 6：Hopper（上）与 Blackwell（下）的 warp-specialized 流水线

这套「按 GEMM 累加器位置决定谁来算 softmax」的思路，和 FlashAttention-3/4 的结论是一致的；FOSCAR 的增量是把折叠修正插进了这条流水线的正确位置。

## 八、这份工作的边界

**第一，折叠只还了一半的账。** FOSCAR 在 H100 INT2 上有效吞吐 60.6%、B200 INT2 上 44.4%，都还没到峰值。指令预算从 8 降到 1.00（B200）之后，剩下的瓶颈转移到 softmax、修正的串行依赖和 split-KV 归约上——论文没有进一步拆解这部分。

**第二，对硬件原生 FP4 并没有赢。** B200 上 INT4 对 TensorRT-LLM NVFP4 是 1.00×（区间 0.88–1.20×）。卖点是「输出 BF16 而不是 FP8」，以及提供了 offset（NVFP4 的 block-scaled 指令没有 offset）。如果只需要 FP8 输出且能接受无 offset，直接用 NVFP4 更省事。

**第三，收益强烈依赖 query/KV 头比。** 折叠省的是「每个 KV 值上重复施加的仿射」，KV 值被几个 query 头复用决定了摊薄效果。HKV=1（每个 KV 头只有一个 Q 头）时，H100 上只有 0.91×/1.10×，等于没赚；HKV=32 时升到 3.89×/7.68×。所以这套优化天生适合 GQA/MLA 这类头比大的模型，对 MHA 风格的结构意义有限。

**第四，channel-wise 组合更慢。** 单个 channel-wise 轴在 B200 上只有 token-wise 的 0.77–0.87×，K 和 V 都 channel-wise 时掉到 0.57–0.73×。原因有二：Blackwell 的 tile 是 256 token，g=128 会把一个 tile 切成两组，Q′ 构造和每组 PV 累加器排空都得进修正 warpgroup；加上 tcgen05 的 QK 吃的是 FP8 Q，channel-wise K 每组都要重算 per-row 最大值和 2 的幂缩放。

**第五，服务场景偏乐观。** 100K 输入 + 99% 前缀命中，是 decode 绝对主导、且 KV 压力最大的场景。把命中率降到 95%，H100 上的收益从 +88% 变成 +62%（346 vs 214 tok/s）。真实业务里前缀命中有多少，直接决定这篇论文的收益。

**第六，评估范围窄。** 单卡、8B 模型、只测 decode 侧，没有 prefill 对比，也没有多卡/PD 分离下的表现。

## 九、给工程实践的三条

- **先算 g 和 hq，再决定要不要做折叠。** g = 2·hq 是盈亏平衡点。如果你的量化组大小是 32、头比是 8（g = 32 = 2hq），收益只有 2 倍；头比 4、组 128 才是 16 倍。
- **打包格式必须对齐 Tensor Core 的操作数布局。** FOSCAR 的 0.19 ALU/元素不是靠「更聪明的解包」，而是靠「写 cache 时就按目标位模式排好，运行时只做移位和掩码」。这一步要在量化器里做，不能留给 kernel。
- **别把「字节减半」当成「时间减半」。** 先算 C_issue / B_HBM 这个预算，再看你的反量化需求是它的几倍。B200 上 INT2 的需求是预算的 1.7 倍——这种时候任何 kernel 微调都救不回来，必须换算法。
