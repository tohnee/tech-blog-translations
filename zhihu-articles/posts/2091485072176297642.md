### 一、智能体路由与中间件：用标准化机制根治模型随机行为

传统多智能体项目最大的技术债务： **路由逻辑散落在 Prompt 中** ，无版本、无校验、无约束，微小改动即可引发全域未知故障，完全不可运维。本项目彻底重构路由体系，实现 **可量化、可测试、可收敛** 的智能体调度机制。

### 1.1 核心方案：意图路由标准化，构建单一事实源

将「用户意图→目标智能体」的调度逻辑，从模糊 Prompt 收敛为 **可执行常量表** ，统一驱动三大核心能力：快车道路由规则、路由工具输出结果、离线评测期望值。通过 **强制一致性测试** 实现三重校验，任意模块数据不一致即刻报错，彻底解决路由逻辑隐性错乱问题。

针对快车道路由做精细化工程取舍：规则命中后不绕过框架状态机，而是生成携带标准 ToolCallBlock 的模拟模型响应，保持状态为 PENDING。既实现意图识别的调用节流，又完整保留框架原生的权限校验、人工确认能力，避免自研状态机带来的语义丢失与重复造轮子风险。

### 1.2 典型线上事故根治：收窄模型工具集，治理随机过度编排

模型存在天然随机性：实测住宿标准查询场景中，前7次请求均4-7秒正常响应，第8次模型无诱因触发多任务组队编排，耗时飙升至50.6秒。

核心解法： **确定性工具集收窄** ，为固定业务意图绑定专属可用工具，从源头限制模型自由编排。将「模型随机异常行为」定义为可治理的工程故障，而非不可控的模型运气问题。

### 1.3 中间件顺序：无报错的致命语义陷阱

中间件执行顺序决定核心业务语义，错序不会触发报错，但会导致业务逻辑静默失效：

- **路由中间件置于最外层** ：优先拦截请求，提前短路无效模型调用，降低资源消耗
- **守卫校验中间件置于最内层** ：覆盖完整链路，校验最终输出结果，兜底业务准确性

同时规避框架隐性坑：框架钩子存在默认空实现，部分自定义中间件未完成钩子适配，却被框架判定为正常实现，导致全链路逻辑失效、单元测试全绿、线上全崩。最终通过 **显式顺序注释+专属顺序测试用例** 彻底闭环。

### 1.4 超时与熔断：重构流式场景容错逻辑

通用异步方案在 Agent 场景完全失效：原生 `asyncio.wait_for` 依靠任务取消判定超时，但框架会吞掉 CancelledError 并做优雅收尾，导致超时判定失效、故障无感知。

自研方案：通过 **独立任务调度 + 时钟原生判定** 重构超时逻辑，彻底规避框架异常吞掉问题。

流式熔断器核心坑：建流成功 ≠ 请求成功。传统方案以建流结果记账，导致连续流式失败时熔断器无法触发熔断。最终修正为： **以流完整消费结果作为成败唯一判定依据** ，实现流式场景精准熔断。

### 二、回复守卫算法：5021行代码构建输出防火墙

大模型普遍存在幻觉泄露、思考链外露、无效痕迹输出、虚假数字生成等问题。本项目自研整套输出守卫机制，以 **「扣留从宽、放行从严」** 为核心原则，全方位拦截非法输出，适配 SSE 流式不可回撤的特殊场景。

### 2.1 全链路多通道监控

覆盖文本块、思考链、工具参数、工具返回、块边界载荷等7大输出通道，不依赖模糊语义匹配，完全基于 **结构化规则判定** ：常规工具调用过程中的中间文本，一律禁止作为最终答复对外暴露（仅特殊只读工具背诵场景例外）。

### 2.2 数字幻觉精准拦截

杜绝子串匹配的误判漏洞，定义4类合法数字来源：工具返回文本、用户输入文本、提示词注入数字、可推导倍数关系。采用 **精准整数比对** ，彻底解决「1200被200误匹配」等传统校验漏洞，拦截所有无依据虚假数字输出。

### 2.3 流式异常重试机制

独创流式重试逻辑：主动吞掉本轮异常结束事件，阻断无效收尾，主动注入修正提示词，强制模型重答，所有异常轮次统一走标准流水线，保证流式输出完整性。

### 2.4 性能极致优化与工程诚实边界

旧方案逐块迭代清洗，17KB数据耗时67秒；优化为批量处理机制后，耗时压缩至0.09-0.15秒，性能提升两个数量级。

客观工程取舍：本方案为启发式规则体系，无法实现100%杜绝幻觉，存在中文数字绕过、正文草稿计数不删除等边界场景，不夸大能力，保持工程落地的真实性与严谨性。

### 三、RAG 体系：攻克三类「零报错、全错误」隐性致命坑

RAG 最大的工程隐患：故障无日志、无报错、无告警，仅业务结果完全失真。针对检索、建库、一致性、链路稳定性四大核心问题，做底层架构修复。

### 3.1 切片优化：杜绝语义截断，构建可追溯检索链

摒弃传统固定字数切片方案，采用 **按业务小节精准切分** ，8篇政策规整为32个标准语义切片。核心优化：所有切片正文强制拼接「文档标题+小节标题」前缀，将追溯链路写入向量本体，而非仅依赖元数据装饰，检索结果可直接定位至具体政策条款。

### 3.2 向量库建库校验：修复幂等静默故障

向量集合创建具备幂等性，已存在集合会直接跳过创建，导致 **错误配置永久留存** 。最隐蔽故障：向量维度、参数一致，但度量方式不匹配（L2/COSINE 混用），写入、检索、打分全部正常，但排序逻辑完全失效。最终新增 **建库后强制回读核验机制** ，不依赖系统默认成功状态。

### 3.3 数据一致性：解决读写可见性延迟

默认一致性等级下，写入/删除操作存在毫秒级可见延迟（实测0.56s-0.58s），出现「用户删除记忆，模型即时复现」的诡异问题。通过升级 **强一致读写模式** ，彻底实现数据增删即时可见。

### 3.4 线程安全防护：规避事件循环卡死故障

客户端同步建连会占用事件循环线程，Milvus 不可达时会直接卡死循环，超时回调完全失效。工程解法：将所有建连逻辑异步抛至独立线程，实现单飞重试，保证核心链路不阻塞、超时机制真正生效。

### 四、长短记忆分离：结构化与语义化双轨存储架构

打破单一向量存储的通用误区，根据数据属性拆分双轨记忆体系，明确存储边界、优先级与防御机制，兼顾精准性与语义灵活性。

### 4.1 双轨存储核心设计

- **结构化记忆（PostgreSQL）** ：存储常旅客号、成本中心、审批人等硬事实精准数据。规避向量库近似检索的误差问题，适配精准匹配、数据更新场景，杜绝相似数据混淆、历史数据无法覆盖的问题。
- **语义记忆（Milvus 派生集合）** ：存储用户随口提及的非结构化信息，仅作为辅助提示、带分数召回，不参与业务校验、不覆盖结构化精准数据。

统一优先级规则： **结构化数据永久优于语义记忆** ，并固化至 Prompt 层，避免模型优先采信模糊语义数据，保证业务准确性。

### 4.2 幂等去重：为召回质量而非存储空间服务

采用「用户ID+原文哈希」跨进程幂等去重，通过多种子哈希校验保证唯一性。去重核心目的不是节省存储，而是 **防止重复记忆挤占 Top-K 召回名额** ，避免有效记忆被过滤、召回结果失真。

### 4.3 防御性架构：隔离业务库与用户记忆

将用户长期记忆独立为「政策库名_memory」派生集合，与核心政策库物理隔离。规避运维常规操作（清空重建政策库）误伤用户个人记忆的隐性事故，实现业务迭代与用户记忆解耦。

### 4.4 记忆读写权限收敛

明确读写边界：记忆召回为每轮对话自动注入，记忆写入仅支持显式接口调用。日常对话的「记住指令」不会触发写入，通过工具层收敛记忆权限，杜绝无意识脏数据写入。

### 三步跑起来

```bash
cp .env.example .env

```

首次构建要拉镜像，需数分钟。 **零密钥也能起** ——Mock 模型兜底。

⚠️ 但请留意：没有真实 Embedding 密钥时，知识库用的是 Mock 向量—— **检索不报错、有结果、有分数，只是结果没有语义，从输出根本看不出来** 。想验证 RAG 得先配密钥重灌。

### 为何值得 Star 🌟

很多工程里的底层工作都有一个共性： **不做好就会引发线上事故，做好了却完全没有感知，属于典型的隐形基建** 。

落到多智能体（Multi-Agent）落地场景，最大难点从来不是调教大模型输出通顺文本，而是两件事： **不该输出的时候主动收敛、该精准输出的时候保证可靠** 。

如果你正在做 Agent 工程化落地，这套实践沉淀可以帮你少踩大量深坑：

- ASGI 中间件编排顺序带来的隐性陷阱
- 智能体熔断器（Breaker）实战踩坑经验
- SSE 流式响应改造的工程细节
- 「没有报错，恰恰是最大风险」的质检设计思路

我们的目标，是打通业务需求与前沿智能体技术，打造一套 **可扩展、可复现的 Agent Harness 脚手架** ，支撑各类业务场景快速接入、低成本迁移。
