训练任务挂掉以后，大家第一反应通常是：模型 checkpoint 有没有保存成功？

但在大规模多模态训练里，经常会遇到一个更隐蔽的问题：模型恢复成功了，训练却迟迟跑不起来。权重、优化器、学习率、global step 都加载回来了，GPU 却还在等数据。原因不是模型慢，而是 dataloader 在空转。

所谓空转，就是恢复任务启动后，数据管线需要重新读取、解码、tokenize、packing 已经训练过的数据，然后一路丢弃，直到追上 checkpoint 所在的 step。这个过程不会产生有效训练，却会消耗大量 CPU、IO 和等待时间。对于图像、视频、音频混合的多模态训练来说，这个成本会非常明显。

这篇文章想讨论的就是这个问题：在流式数据加载和 online packing 场景下，断点续训为什么不能只保存模型状态？我们到底应该保存哪些 dataloader 状态？以及工程上有哪些可行方案？

### 1. 传统 Dataset 为什么容易恢复？

先从最简单的情况说起。

PyTorch 里常见的 Dataset 可以粗略分成两类：map-style Dataset 和 iterable-style Dataset。

map-style Dataset 实现的是 `__getitem__` 和 `__len__` ，它的抽象很直观：给我一个 index，我返回一个样本。比如 `dataset[123]` 读第 123 张图片或者第 123 条文本。

这种 Dataset 的恢复相对简单，因为数据位置是显式的。只要 sampler 顺序可复现，恢复 epoch、global step、随机种子之后，就基本知道下一批样本应该是谁。

很多纯文本预训练也会走类似思路：先把文本 tokenize 成二进制文件和 index 文件，训练时按 offset 读取 token block。此时数据加载更像是“按位置 seek”，checkpoint 恢复也更自然。

问题出现在另一类 Dataset 上。

iterable-style Dataset 实现的是 `__iter__` ，它的抽象不是“按 index 取样”，而是“一条持续向前的数据流”。它适合随机读取很贵，甚至不现实的场景，比如数据库、远端对象存储、大规模 tar 分片、实时日志流。

大规模多模态训练里，这类 Dataset 很常见。原因很简单：图像、视频、音频如果都以小文件形式随机读取，文件系统和对象存储会很痛苦。工程上更常见的做法，是先把数据打成大的 shard，再顺序流式读取。

这就引出了 WebDataset 和 Megatron Energon 这类方案。

### 2. WebDataset / Energon 解决的是大规模读取问题

WebDataset 的核心思路是：把样本打包进 tar shards。

一个样本可能包含图片、视频、音频和一段 json 对话文本，它们共享同一个 key，被放在同一个 tar 分片里。训练时按 shard 顺序读取，避免大量小文件随机 IO。

以 PAI-Megatron-Patch 的 Qwen3-VL 示例为例，它的数据准备流程大致是：

```text
原始多模态数据
    |
    | convert
    v
多个 WebDataset tar shards
    |
    | generate_configs / prepare metadata
    v
Energon 可识别的数据集目录
    |
    v
训练时流式读取
```

这里的 `convert` 会把原始多模态样本打包成 tar 分片； `generate_configs` 会扫描 tar 包并生成 `.nv-meta` 、 `dataset.yaml` 、split/index 等元数据，让 Megatron Energon 能识别和切分数据集。

这样做的收益很明显：顺序 IO 更友好，远端对象存储更友好，多节点多 worker 切分也更自然。Energon 还提供了多模态 sample type、数据混合、分布式加载，以及可保存和恢复的 loader state。

但注意，这里解决的是“如何高效读取大规模数据”的问题，不代表业务侧所有数据状态都自动简单了。尤其是 online packing 场景。

### 3. Online packing 让 dataloader 变成状态机

大模型训练里，packing 是一个很常见的优化。

如果每条样本都 padding 到最大长度，短样本会浪费大量 token 位置。packing 的目标就是把多个短样本拼成一个更接近最大长度的训练序列，提高 token 利用率。

packing 可以离线做，也可以在线做。

离线 packing 是在预处理阶段就把样本 tokenize 并拼好，训练时直接读取已经构造好的 token block。它恢复简单，吞吐稳定，但灵活性差。多模态数据尤其麻烦，因为图片、视频、音频的处理策略可能会频繁变化。

online packing 则是在训练时动态完成：worker 持续读样本，做图片/视频处理、tokenize、构造 labels，然后把样本塞进 buffer，直到可以产出一个 packed sample 或 batch。

这时 dataloader 就不再是一个简单的数据读取函数，而是一个状态机。

它内部至少有这些状态：

| 状态 | 含义 |
| --- | --- |
| dataset index | 每个 worker 当前读到哪个数据集、哪个样本 |
| shard / sample order | 流式数据当前走到哪个 shard、哪个样本 |
| packing buffer | 已读取但尚未训练的中间样本 |
| shuffle buffer | 为了随机性暂存在内存中的样本 |
| RNG state | 随机裁剪、随机帧采样、replacement、shuffle 等随机状态 |
| worker queue | DataLoader 主进程和 worker 之间已经分发或返回的数据 |

因此，第 1000 step 的模型 checkpoint 并不等价于“数据集读到了第 X 条”。每个 worker 可能读到了不同位置，每个 buffer 里可能有不同的半成品，有些样本已经被处理过但还没有真正参与训练。

如果这时候任务挂掉，只恢复模型是不够的。模型知道自己训练到了第 1000 step，但 dataloader 不知道自己当时内部长什么样。

### 4. 为什么“从 global step 推回数据位置”不可靠？

一个常见想法是：既然 checkpoint 里有 global step，那我根据 global step 算一下消耗了多少数据，再让 dataloader 跳过去不就行了吗？

在简单 map-style Dataset 中，这个思路通常可行。但在 online packing 和多 worker 流式加载中，它会遇到几个问题。

第一，样本和 batch 不是固定比例。一个 packed sample 可能由多条原始样本组成，不同长度样本进入 buffer 后，组合方式不同，消耗的原始样本数量也不同。

第二，每个 worker 的进度不同。DataLoader 主进程会给 worker 分发任务，worker 处理速度受 IO、解码、样本长度影响。checkpoint 时刻，各 worker 并不一定刚好停在整齐的位置。

第三，随机处理会改变结果。同一个样本 index，如果图像随机裁剪、视频随机抽帧、坏样本 replacement、dataset blending 的随机状态不同，重新处理出来的结果也可能不同。

第四，buffer 里有“已读取但未训练”的数据。如果恢复时只从下一个 index 开始读，这些 buffer 中的数据可能丢失；如果从更早的位置开始读，又可能重复训练。

所以，断点续训真正要恢复的不是一个 step 数，而是训练输入流的状态。

### 5. 方案一：给现有 Dataset 增加状态快照

第一种方案，是不替换现有数据加载框架，而是在当前 `LazySupervisedDataset` 和 `PackedDataset` 上补充状态保存/恢复能力。

核心思路是：模型保存 checkpoint 的同时，dataloader 也保存 checkpoint。

需要保存的状态大致分三层。

第一层是底层 Dataset 的读取位置。比如当前 dataset id、sample index、replacement count。恢复时每个 worker 能从自己的位置继续读，而不是从头开始。

第二层是 packing buffer 状态。 `PackedDataset` 里通常有 `buffer_list` 和 `buffer_max_len_list` 。它们保存了正在 packing 的中间结果，以及已经拼好的部分结果。

这里有一个关键选择：buffer 里到底保存真实数据，还是保存样本索引？

直接保存真实数据最简单，恢复时把 buffer 放回去就行。但多模态样本很大，尤其是 `pixel_values` ，每个 worker 的 buffer 可能占用大量空间，保存会慢，checkpoint 体积也会膨胀。

更推荐的方式是保存组成 buffer 的样本索引，例如：

```text
buffer_list:
[
  [(dataset_0, sample_12, replace_0), (dataset_0, sample_19, replace_0)],
  [(dataset_1, sample_7, replace_1)]
]
```

恢复时再根据这些 index 重新读取原始样本，按原顺序重建 buffer。这样 checkpoint 很小，但要求样本处理过程可复现。

第三层是随机状态。只保存 index 不够，因为同一个 index 再处理一次不一定得到同样结果。至少要保存每个 worker 当前的 `torch` 、 `numpy` 、Python `random` 状态。更严格的做法，是保存每条样本处理前的 RNG state：

```text
rng_states:
{
  (dataset_id, sample_idx, replacement_count): {
      torch: ...,
      numpy: ...,
      random: ...
  }
}
```

恢复 buffer 时，每处理一条样本，就先恢复它对应的 RNG state。这样可以尽量保证重建出的 buffer 和中断前一致。

整体恢复流程可以写成：

```text
load model checkpoint
load dataset checkpoint for current iteration

for each worker:
    restore dataset index
    restore worker rng state

    new_buffer_list = []
    for buffer in saved_buffer_index_list:
        new_buffer = empty
        for sample_index in buffer:
            restore rng state before this sample
            sample = dataset[sample_index]
            new_buffer = update_buffer(new_buffer, sample)
        new_buffer_list.append(new_buffer)

    restore buffer_max_len_list
    continue yielding data
```

这个方案的优点是低侵入。现有数据格式、现有 Dataset、现有 packing 逻辑都可以保留，只是在关键类里增加 `state_dict` 、 `load_state_dict` 、 `save_state_dict_to_disk` 等接口。

它适合作为短期止血方案：训练任务已经在线上跑了，不能大规模重构数据管线，但又必须减少恢复空转。

缺点也很现实。实现时要非常仔细处理 worker 对齐、RNG 对齐、坏样本 replacement、buffer 重建顺序，以及 checkpoint iteration 对齐。否则很容易出现“能恢复，但数据顺序变了”或者“少训/重训部分样本”的问题。

### 6. 方案二：迁移到 Megatron Energon 的 savable loader

第二种方案，是把数据加载迁移到 Megatron Energon 这类原生支持 save/restore 的 dataloader。

Energon 的设计目标就是大规模多模态训练。它基于 WebDataset 格式，支持多 rank、多 worker、数据混合、packing/grouping，并提供可保存和恢复的 loader state。

典型用法是：

```text
from megatron.energon import get_train_dataset, get_savable_loader, WorkerConfig

ds = get_train_dataset(
    "dataset.yaml",
    batch_size=4,
    shuffle_buffer_size=100,
    max_samples_per_sequence=100,
    worker_config=WorkerConfig.default_worker_config(),
)

loader = get_savable_loader(ds)

# 保存
state = loader.save_state_rank()

# 恢复
loader.restore_state_rank(state)
```

在分布式场景中，也可以选择每个 rank 单独保存自己的 loader state，或者由主 rank gather 全局状态再统一保存。

这条路线的本质是标准化：不要每个训练框架都自己维护一套复杂的流式加载、worker 切分、shuffle、packing 和恢复逻辑，而是把这部分能力交给专门的数据加载框架。

它的优点是体系更完整。WebDataset 解决大规模顺序读取问题，Energon 解决多模态样本抽象、分布式加载和 deterministic resumability 问题。长期看，这比在业务 Dataset 里不断打补丁更容易维护。

但迁移成本不能低估。首先，现有数据要转换成 WebDataset/Energon 格式。其次，当前 Dataset 的字段映射、样本处理、task encoder、packing 方式都要适配。再次，packing 逻辑变化后，吞吐、显存、样本顺序、训练收敛是否一致，都需要重新压测和验证。

所以 Energon 更像是中长期基础设施方案，而不是一天两天能替换掉的热修复。

### 7. 两种方案怎么选？

如果当前最大痛点是“任务挂了以后恢复太慢”，优先做方案一。它的目标很明确：在现有框架里补 dataloader checkpoint，让恢复时不再从头空转。

如果你们正在重构多模态数据平台，或者未来会持续接入更多数据源、更多模态、更多训练任务，那么方案二更值得投入。数据格式和恢复能力标准化之后，后续维护成本会更低。

可以简单总结成一句话：

```text
短期止血：保存现有 Dataset / PackedDataset 的 buffer、index 和 RNG 状态。
长期演进：迁移到 WebDataset + Megatron Energon，把可恢复数据加载做成基础能力。
```

真正需要避免的是中间状态：模型 checkpoint 很完整，但 dataloader 没有状态。这样所谓断点续训，只是模型接上了，数据还在从头追赶。

### 8. 结语

断点续训恢复的不是一个文件，而是一个训练系统。

在简单训练里，dataloader 看起来几乎是无状态的；但在大规模多模态训练里，它本身就是一个复杂状态机。它决定哪些样本已经训练过，哪些样本还在 buffer 里，哪些随机处理已经发生，哪些 worker 已经向前推进。

因此，只保存模型、优化器和 global step，并不能保证真正从断点继续。尤其是在 iterable dataset、WebDataset 分片、online packing、多 worker 并发加载的场景下，dataloader state 必须成为 checkpoint 的一部分。

否则，训练任务虽然恢复了，但数据流没有恢复。GPU 等的不是模型，而是 dataloader 重新走完过去。
