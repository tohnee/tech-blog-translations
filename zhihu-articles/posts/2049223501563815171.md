在 2026 年 2 月 17 日发出上一篇《从零写一个 Rust 推理引擎》之后，过了 116 天。回过头看，用 Rust 写推理引擎到底带来了什么好处，又经历了哪些困难？Pegainfer 现在又是什么状况？

![](https://pic1.zhimg.com/v2-7e7a432f76781a7d860088900007a0b2_r.jpg)

当时写 Pegainfer（这个名字来自我更早的一个项目，叫 Pegaflow，是一个用于 vLLM 的 KV cache offloading 系统，详见 vLLM blog）——它们都叫 pega，源自希腊语的 Pegasus（天马座），这也是 logo 的来源：我们希望以飞马般的速度交付推理服务。出发点的确很简单：我喜欢 Rust，也喜欢研究推理技术，不喜欢现在 Python 生态的那种臃肿感，再加上实际生产中踩过不少 Python 相关的坑，于是就有了「用 Rust 写一个自己的推理引擎」这个念头，之后越写越发现一些有意思的点，无论是写 kernel，设计一些模块，满足了我很多好奇心。

一开始它还是个「刻意空白」的东西(我一开始只想将其用作教学目的）：一次只能处理一个请求，没有采样器、没有前缀缓存、没有调度器、没有 CUDA Graph，kernel 也没怎么调，5070ti 上跑 Qwen3-4B 大概 70 tokens/s，精度对齐了 HuggingFace。

半年过去，采样、前缀缓存、连续批调度、CUDA Graph、kernel 优化，然后是线性注意力、KV offloading、LoRA、张量并行，再到主流大 MoE 的 EP 并行。我在前几天将其重命名为了 OpenInfer，因为我发现它逐步可以步入生产了。在适当准备之后，今天正式发布了 OpenInfer 0.1.0。

当然后文大部分 feat 都只在 Qwen3 4B 上实现，不同模型 feat 覆盖率不同。

### 架构：不再从 0 开始做轮子

虽然说我想写推理引擎，但这不意味着我需要完整重写每一部分，tokenizer，请求解析，tool call parser 等。所以我接入了很多来自 Rust 生态的 优秀的库和组件。

虽然我在开始的时候引用Feynman 那句「What I cannot create, I do not understand」，对我来说，理解一个系统不等于每行代码都得我亲手敲。所以 openinfer 是**用 Rust 把几个我觉得写的不错的组件粘在一起**，拼接成了一个推理引擎

![](https://pica.zhimg.com/v2-fc64e6fd68cca58785c9358cc109e8f0_r.jpg)

- **vLLM 的 Rust 前端**：OpenAI 协议、流式、LoRA 路由，直接复用 vLLM 上游的 Rust 前端（最早是 Inferact 的 vllm-frontend-rs，后来并进了 vllm-project/vllm）——tokenizer、chat template ，协议层 vLLM Rust 前端已经做得很好。BTW，因为 openinfer 也给上游 vLLM Rust 前端贡献了 3 个 pr（来自 openinfer 社区中的其他人和我）。
- **dynamo 的 kvbm**：dynamo 是 NVIDIA 开源的用来在数据中心等大规模部署下提供高质量 推理服务的生态系统。我们接入了它管理 KV Cache 的组件，叫做 kvbm，我们接入了它的逻辑层，管理 token 前缀缓存，驱逐（未来也可以顺势接入 dynamo 的 kv event，提供高质量的分布式路由，还有 p/d 分离）。并没有接入它的物理层，物理层我选择了 pegaflow。
- **pegaflow**：KV offloading，放到后面单独讲。
- **kernel 层**：主要采用了 Flashinfer 的算子，当然也有一些我们自己维护的算子(cuda,triton,tilelang,cutedsl)。

kernel 的来源有这几个

- 热路径的 GEMM 和融合算子（QKV、gate-up、attention），手写 CUDA + cuBLAS；
- 采样、attention、norm、MLA decode，走 FlashInfer。
- Qwen3.5 的 GDR 线性注意力，Triton AOT（来自 FLA 仓库）
- DeepSeek-V4 的 MoE / compressor / indexer，CuTe DSL + TileLang 构建期 codegen；
- TVM FFI，把 Triton 编出来的 CUBIN 包成可直接调用的 launcher。

我们的 kernel 采用 feature 门控，每个模型只编译自己用的上的算子，Qwen3 4B 不需要编译 Qwen3.5 4B 的算子，也不需要编译 Deepseek v4 flash 的 Tilelang 算子，包括 kimi 的 moe 算子。这样可以大幅度减少编译 kernel 数量，加快迭代效率。

修改一个算子，到整体 binary 编译完成，可以再次压测，只需要 50s 左右。

### 所以选择 Rust 有什么好处？

**CPU 内存占用**。也许是因为没有 PyTorch ，和其他各种组件，进程本身就轻很多。

在一轮压测里量了内存占用——压测开始前（模型加载完、空载就绪）和压测跑完后（5090，Qwen3-4B BF16，权重 7.6GB）。同时因为 Rust 语言本身带来的内存安全等，openinfer 内存问题可能会更少。

![](https://pic4.zhimg.com/v2-daf9f3e4b1c1ec39ecd797c747305049_r.jpg)

之后因为我们没有各种 jit, compile等，我们启动速度非常快，在我的 PC 上，模型提前预热过，**openinfer 3.0s vs vLLM 热启动 32.7s，约 11 倍**（vLLM冷启动需要70s 左右），与之相对的，我们没有任何运行时的编译，编译好，服务 ready 后，给予的就是稳定的可靠的服务。

![](https://pic3.zhimg.com/v2-bad3a720e0d2a1c978bef3e0c84b728a_r.jpg)

### 推理性能上的实测

数据在一张 RTX 5090上，用同一个 `vllm bench serve` 客户端、同样的 Poisson 到达、同样的 seed 42，先后驱动 openinfer 和 vLLM 0.22.1 跑出来的。两个引擎看到的是一模一样的请求流。

![](https://pic1.zhimg.com/v2-4fbe4cb1fc89efa26413be41ebc9502e_r.jpg)

低负载，QPS 4 以下。TTFT、TPOT 两边基本贴着走，openinfer 小赢一点——QPS 2 和 4 的 TPOT p50 都比 vLLM 低。

中负载，QPS 8 到 12。这里确实确实比 vLLM 性能低一些，TPOT 全面落后。

饱和点，QPS 16。两边都过载了，TTFT 干到秒级， openinfer 反而更好——吞吐 1794 vs 1692，高了 6%，过载 TPOT 65 vs 78，比 vLLM 低。

不过，怎么看都是 kernel 的问题，想要更好的性能，调 kernel 就完事了。

### kv cache 相关的压测：我的老本行

在 coding agent 爆火的现在，请求的 hit ratio 极高的现在（openrouter 上 kimi 的 hit ratio 达到了 98%)，意味系统需要处理大量高命中率的缓存，所以我们测量了请求全部 hit gpu kv cache 的性能，（同一组 prompt，先冷发一次把前缀灌进 GPU 缓存，再发 warm 的（命中缓存），随输入长度扫 TTFT：

![](https://picx.zhimg.com/v2-7ceb4492aff9da61a3d0f8539a8caedd_r.jpg)

warm TTFT **最大的单项是 CPU 分词**，也就是 tokenizer，大概占据 30-40% 的性能左右，之后是查询和 GPU 实际执行。

### pegaflow：也是我主要参与的Rust 项目

pegaflow 是我大部分时间维护的系统，它是一个已经跑在生产里的 KV 卸载引擎，五月还和 vLLM 团队一起写过一篇介绍它的博客，PyPI 上能直接装，体验，性能，正确性等都有保障（看了下线上最长运行记录接近 一个月了，是的驻留在服务器上一个月，没有任何问题）。Pegaflow做 的是推理里的KV cache offloading, 在 HBM、DRAM、SSD 之间分层落盘，跨节点用 RDMA 共享。得益于我们是一直接入的 vLLM的 kv connector 设计的，这让我们的 rust 服务只关心 kv cache，几乎零改动的接入了 Openinfer 中。

性能，在纯 L2 模式下测——把 GPU前缀缓存关掉、每个命中都强制从 CPU mem 中拉取，对比的是同长度下冷发的全量 prefill：

![](https://pic2.zhimg.com/v2-39ecf095ce421153cc78df241d77fa5f_r.jpg)

由于 vLLM 没有官方认定的 cpu memory，测其他组件我也不知道谁性能更好，所以就没有测。

这里 Rust 提供了一个有意思点，就是现在 KV Cache 强调异步（各种异步，pd 异步，i/o 异步等），比如我们在异步 SAVE 的时候，任务会持有保存 block 的强引用（`ImmutableBlock`）一直持有到 D2H 真正落地才释放。Rust 在语言层面给了生命周期和数据的绝对正确性（其他组件通过 block id，和 zmq ，scheduler worker，如果出问题，是很难排查的）。

### Future: 我不想再做一个大而全的推理引擎

vllm rust, dynamo, pegaflow，其实指向了一个我越想越确定的方向。

openinfer 虽然现在是一个仓库，但我没打算把它做成那种「什么都自己有、什么都长在一起」的大一统引擎。那种引擎我们见得太多了：前缀缓存、调度器、kernel、卸载层彼此缠在一起，各种feat 混在一起，重构还需要保持兼容，v1,v2,v3，同时想换掉其中一部分，得先把整个引擎读一遍，最后谁也不敢改。提 pr 也很难有人看，如果 fork 自己搞，和上流的冲突又很麻烦，同时有时候上流的一些 feat，与 fork 合并后，谁知道有什么问题呢？It’s python.

所以接下来的方向是反过来的：我打算**把 openinfer 拆成更多各自独立的 sub-repo**。每一个都是接口相对稳定清晰、能快速读懂、能单独替换的项目。pegaflow 已经是这种形态了——它能独立发版、独立 link，openinfer 只是它众多宿主里的一个。

我想要的未来是是：这些项目在 rust 的包管理器上，crates.io, **你可以挑几个，拼出属于你自己的推理引擎**。想用xxx的调度器配 pegaflow，再搭配 LORA，没问题；调优 kernel(mega 化） 包装去搭自己的推理服务，也可以。做实验，LORA 效果，RL 定向调度算法，稀疏化，推测解码实验等，更激进的调度算法（类似 nanoFlow 那样），都是可以的，创建项目，在`Cargo.toml`中填入依赖，就可以了。

对于openinfer 这个仓库本身，对于 0.1.0，与其说是起点，不如说是第一个基于前面的思想拼出来给的样例——这些组件确实能拼到一起，提供生产级的性能和可用性。
