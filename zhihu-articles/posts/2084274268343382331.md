很多人还不知道， **ChatGPT 的普通聊天也能通过 MCP 调用本地电脑上的程序，读写文件、执行任务** 。这台电脑能访问的远程资源，也可以通过相应工具接进来。我这次就用它查询了计算集群的资源、读取日志，还提交了计算任务。

上一篇《 [Codex 额度不够用？用 ChatGPT 聊天连接 GitHub，改文件、跑测试](https://zhuanlan.zhihu.com/p/2083286579972419820) 》里，我介绍了用 GitHub 插件读写仓库、调用 GitHub Actions 跑测试的方法。代码和文档放在仓库里，就能直接在聊天中让它读取、修改。

但我平时还要查看集群上有哪些 GPU，检查计算进度，找出没处理的数据，再提交下一批任务。这些操作涉及集群的调度系统和运行目录，现成的 GitHub 插件没有提供对应的工具。

于是，我让 Codex 根据现有项目做了一个 MCP Server，接到 ChatGPT 的普通聊天里。最后，10 个计算任务确实提交成功了。不过，中间也折腾了几轮：生成任务清单太慢，拖垮了连接；修好之后，任务已经跑起来，确认框却还在没完没了地弹。

## 把自己的工作流程做成 ChatGPT 能调用的工具

MCP（Model Context Protocol，模型上下文协议）让我们可以把自己的程序接给 ChatGPT 使用。负责提供这些工具、执行调用并返回结果的程序，就是 MCP Server。比如，把现有的集群查询和提交脚本封装进去，ChatGPT 就能调用“查询作业”“提交测量任务”等工具。

**现成插件没有的功能，可以按自己的需要补上** 。先看接好后的效果：我这次做的服务在 ChatGPT 里显示为 `NSC3 Measure 2412` 。新建聊天，选中这个应用，就能向它提出要求[1]。

我先问了一个平时经常关心的问题：

> 查看一下 trlan 单次测量在不同 GPU 卡的节点上的运行时间。

TRLan、D1、D4 是项目中不同的计算阶段。这里不用了解具体的物理含义，只需知道：后续测量依赖前面的计算结果，提交前要检查所需结果是否齐全。

ChatGPT 随即查询作业、读取日志，按 GPU 型号整理计算耗时（图 1）。一个作业可能连续运行好几天，它也注意到了这一点，采用日志中每次计算的计时来比较速度。

![](https://pic3.zhimg.com/v2-f83c4a5a4fb106984149bef680f975ce_r.jpg)
*图 1*

图 1：ChatGPT 调用工具查询作业、读取日志，比较不同 GPU 上的单次计算耗时。

原来需要我去终端查队列、找日志，再复制进聊天框的材料，现在它可以直接读取了。

## 让 Codex 制作并安装 MCP

再回头说这套服务是怎么做出来的。我把之前的项目任务记录发给 Codex，提出要求：

> 给测量 trlan、D1、D4 的代码、任务提交流程、集群操作，制作一个 MCP Server，可读可写。然后给 ChatGPT chat 安装这个 MCP Server。

项目里已经有能工作的代码、提交脚本和说明文档。Codex 先读这些材料，弄清楚已有流程，再把相关操作封装成工具，省去了我重新解释整个项目的工夫。

这次制作和修复用的是 Codex 中的 GPT-5.6 Sol，思考程度选了“极高”。第一轮，它建立运行环境，实现了 22 个工具，完成测试，又连上集群验证读取功能。界面显示用时 **44 分 11 秒** （图 2）。

![](https://pic4.zhimg.com/v2-688fddcdd48d62653dcc4e994a2d9b09_r.jpg)
*图2*

图 2：首版制作、测试和只读联调完成。图中“Pro 只能使用读取工具”是 Codex 当时给出的判断，后面我的 Pro 账号实际完成了写入和提交，不能把这句话当成使用限制。

这 22 个工具涵盖文件读写、集群查询、日志读取、任务清单生成和作业控制。修改文件要先预览、备份；提交任务要先生成清单，核对数量和重复项。如果正式提交时清单已经变了，服务端就会拒绝执行。 **这些检查写在程序里，每次调用都要经过** 。

接下来，要让 ChatGPT 连上本机的服务。我这次采用 OpenAI 的 Secure MCP Tunnel，也就是安全 MCP 隧道。它把 ChatGPT 的工具请求转交给本机服务，不需要给私有 MCP 服务另外开放公网监听端口[2]。

我回复“继续安装”后，Codex 配置隧道、启动服务，让 ChatGPT 扫描工具列表，再实际调用一次只读工具，确认连接可用。这轮用了 **23 分 45 秒** （图 3）。

![](https://pic4.zhimg.com/v2-ce717dd9e04ba70b27af9359ec6a410f_r.jpg)
*图 3*

图 3：ChatGPT 已识别全部 22 个工具，并成功完成一次只读调用。任务提交能力还要接着试。

**首版制作和安装，两轮合计约 68 分钟** ，其中包含读项目、装依赖、写代码、测试和操作安装页面的时间。

安装时也碰到了权限问题：隧道客户端默认往系统的应用数据目录写运行状态，受限环境不允许，Codex 就改用项目内的专用目录。安装完成后，背后的本机服务、隧道和集群连接仍要保持可用，接下来就要检验它们能否完成一次提交。

## 第一次提交，卡在了生成任务清单

查询可以正常使用后，我接着让 ChatGPT 做一次小规模提交：

> 你能提交任务到集群吗？试一下提交少量（10 个）组态的 D1 测量任务。

“组态”可以先理解为要逐个处理的数据样本。我只挑 10 个，先试一次小规模提交。

它先检查有没有正在运行或排队的 D1 作业，再检查前置计算的结果。原脚本没有现成的 `--limit 10` 参数，它便尝试临时修改生成器的数量限制，并请求把脚本同步到集群（图 4）。

![](https://pica.zhimg.com/v2-6a46674b7397ccf3a92a894a71a721cc_r.jpg)
*图 4*

图 4：先检查依赖和已有作业，再调整生成数量。图中是最初的修改方案，后面又修正了计数和退出条件。

结果，卡住了。

后面附的分享对话中，这次失败的尝试显示用了 **6 分 58 秒** 。它停在生成任务清单的 `prepare` 阶段，尚未执行最终的 `submit` ，也就是正式提交。再让它重试，连最基本的连接检查都报 `Session terminated` ：会话已经终止（图 5）。

![](https://pic3.zhimg.com/v2-2c408a4db02b350f9412f039f3c61538_r.jpg)
*图 5*

图 5：连接失效后，ChatGPT 无法继续检查清单、提交任务，也无法恢复它临时改过的脚本。

我把故障交给 Codex 排查。它发现，本机通过 SSH 远程连接集群仍然正常，退出的是隧道进程。顺着隧道日志查下去，问题指向了前面那个迟迟没结束的清单生成操作（图 6）。

![](https://picx.zhimg.com/v2-5c37846540314ab87a66c4d033cf7ae7_r.jpg)
*图 6*

图 6：Codex 检查了 SSH、隧道日志和远端脚本，定位到清单生成调用超时。

脚本确实只写了 10 条记录， **但写够以后，还在继续扫描剩下的候选数据** 。大量目录和文件仍要逐个检查，限制了写入数量，却没有让程序及时停下来。

首版 MCP 服务会让一次工具调用一直等到脚本运行完成。这次调用超过了隧道约两分钟的响应期限，日志中出现连续超时，随后通信管道关闭，隧道进程退出。于是，一个生成清单的操作卡住，后面的简单查询也跟着用不了了。

## 别让一个慢操作拖垮整个服务

Codex 先把数量上限整理成明确的参数，并让生成器在达到全局上限后，立即退出相关的扫描循环。随后备份、同步修好的脚本，恢复隧道，再通过 ChatGPT 调用一次只读工具，确认连接恢复（图 7）。

![](https://pica.zhimg.com/v2-a87e2b4ec45fe3109ff2b82471455bac_r.jpg)
*图 7*

图 7：脚本和连接已经修复，原有的 10 条任务清单保留，此时还没有正式提交作业。

但以后换一个更大的目录，或者集群文件系统临时变慢，仍然可能等很久。只修眼前这个脚本还不够，所以我继续要求：

> 从根本上修复，确保以后发生类似情况也不会拖死 runtime。

这一次，Codex 把生成清单、扫描进度、提交等耗时操作改为 **后台执行，并立即返回操作编号** 。ChatGPT 可以拿着编号查询进度，完成后再取结果，每次工具调用都不必从头等到尾。

普通查询也加了 75 秒的总响应时限，超时就返回错误，并终止相关命令。同一时间只允许一个这类后台长操作，避免反复重试堆出多份扫描；服务重启后，未完成的操作会标成“已中断”（图 8）。这样，耗时工作可以继续在后台运行，其他查询也能得到响应。

![](https://pic3.zhimg.com/v2-6f817e28123021c4ebd1d7b8078bd09e_r.jpg)
*图 8*

图 8：服务层改造用了 47 分 21 秒。工具从 22 个增加到 24 个，新增两个工具用于查询后台操作。

改造后，15 项测试通过。Codex 又刷新了 ChatGPT 中的工具列表，实际调用新版工具，确认连接和读取正常。

这几轮故障定位、连接修复、服务改造和复核，按截图中的用时相加，又花了约 77 分钟。 **连同首版制作和安装，共约 2 小时 25 分钟** ，还不包括我在 Chat 里试用、等待和来回确认的时间。这些问题都是在实际提交任务时暴露出来的。

## Chat 为什么能操作本地电脑

这套流程跨过了三处：OpenAI 的云端服务、我的本地电脑，以及计算集群（图 13）。 **ChatGPT 理解要求、选择工具，本机程序负责执行相应操作；需要访问集群时，再通过已有连接执行远程命令** 。

![](https://pic3.zhimg.com/v2-41bcaf670536d1174371d3b150fe2f76_r.jpg)
*图 13*

图 13：本文的部署方式。实线表示调用或执行，虚线表示结果或状态返回。箭头表示消息传递方向；隧道的网络连接由本机主动向外建立[2]。

### 先让 Chat 知道有哪些工具可用

接入应用时，ChatGPT 会获取工具的名称、用途和参数格式：哪些工具能查询，哪些能修改文件，提交测量时要指定什么。MCP 规定了这些信息以及调用、结果的传递方式[1]。

我说“提交 10 个 D1 测量任务”，Chat 就根据这些工具定义安排操作。每次发出的调用都包含明确的工具名和参数，比如测量阶段是 D1。MCP Server 收到调用，找到对应的函数，再按参数执行程序。

**Chat 能做什么，取决于接入了哪些工具，以及这些工具具有什么权限** 。本文接入的是文件和科研任务相关工具；如果要让它看屏幕、点击窗口，还需要另外接入相应工具。

### 请求怎样到达我的电脑

两边靠安全隧道通信。本机启动隧道客户端，主动向 OpenAI 的隧道服务建立 HTTPS 连接，取回工具请求，交给本机 MCP Server，再把执行结果送回去。私有 MCP 服务不需要额外开放公网监听端口[2]。

这就要求本地电脑开着，网络和相关进程也正常。前面的故障恰好说明了这一点：本机虽然还能连集群，隧道一断，Chat 的新请求就传不过来了。

### 本机再通过 SSH 访问集群

SSH 用来远程登录和执行命令。我平时就用这台电脑访问集群，已经有相应的账号和连接配置。MCP Server 收到提交调用，完成清单和作业上限等检查后，就通过这条连接，在集群上运行提交程序。

**Chat 能提交集群任务，依赖的是本机已有的访问能力，以及集群账号本来具有的权限** 。

随后，集群的 Slurm 调度系统接收作业、分配 GPU，计算程序在集群节点上运行。作业编号和查询到的状态沿原路返回，ChatGPT 再把结果整理成回答。

MCP 服务也可以部署在远程服务器上。我这次把它放在本机，是为了复用电脑上已有的项目文件、程序和集群连接。接入其他工具，也可以让 Chat 整理本地文件、调用分析脚本；访问集群只是其中一种用途。

## 使用官方入口，在授权范围内操作

**本文使用的是 OpenAI 官方支持的接入方式** 。官方文档介绍了自定义 MCP 的连接、工具发现和外部系统读写，也提供了 Secure MCP Tunnel 来连接私有服务[1,2,3]。

操作也在原有授权范围内：本机服务使用已有权限，集群访问使用我自己的账号，作业照常交给 Slurm 调度，程序还保留了前面提到的 12 个作业上限。换成聊天操作，并不会增加账号的资源权限。

上一篇说到 Codex 额度用完后，可以让 Chat 接着处理仓库，前提也是： **Chat 和相关插件仍然可用，并且操作在各自现有的权限和额度内** 。这不会重置或增加 Codex 额度。OpenAI 的条款要求遵守使用限制，并拥有处理输入内容所需的权利和许可[4]。

本文所说的合规，就是使用官方支持的入口，在授权范围内完成操作。用于单位或课题组的项目时，还要遵守其集群接入和数据管理要求，确认哪些代码、文件和日志可以交给外部 AI 服务处理。

## 能做更多事，但要算上制作和维护的成本

这次试下来，Chat 确实能通过自制 MCP 接着做事：处理文件、查询集群，再把任务提交出去。Codex 帮我完成了服务制作、安装和排错，我通过对话提出要求、限制试跑规模，遇到问题再让它继续查。

本文记录的是 2026 年 9 月 17—18 日的实测。我用 Pro 账号完成了读取、写入和任务提交；其他账号能否使用相同功能，还要看各自的入口和权限设置[1]。

不过，实际体验还不如 Codex 顺手。这次提交慢了不少，确认框也有没解决的 bug。更要算进去的是， **制作、安装和修复 MCP 本身，就已经花了不少 Codex 额度** 。前面两个多小时的操作之外，还有我试用、等待和确认的时间。以后项目脚本或连接方式变了，服务也可能要跟着维护。

所以最后还是要实诚地说： **如果任务不需要长期维护、反复执行，预计也不会消耗很多额度，其实不值得先花这么多额度去制作 MCP 服务** 。只是临时改几个文件、提交一小批任务，直接让 Codex 做完通常更省事。只有后面确实要长期使用，预计能把大量重复操作交给 Chat，才值得考虑这笔前期投入。

## 评论区推荐的现成工具 RDC

文章发布后，评论区有读者推荐了 Desktop Commander，感谢分享！它的远程服务 **Remote Desktop Commander（简称 RDC）** 已经提供了文件读写和终端操作工具。在电脑上运行配套的设备代理，再把服务接入 ChatGPT，就能在聊天中让它修改文件、运行脚本、查看程序输出。请求经 RDC 的托管服务转发，具体操作仍由自己的电脑执行，使用本机账号已有的权限[5]。

这也为本文的集群操作提供了另一种选择。从官方列出的能力看，只要本机已经能通过 SSH 连接集群，ChatGPT 就可以借助 RDC 调用现有脚本，查询作业、读取日志或提交任务，不必先像我这样制作一套 MCP。这次实测用的是自制 MCP，RDC 在这套流程中的实际表现还有待验证。前面那些核对清单、防止重复提交和限制作业数量的检查，也要保留在调用的脚本或服务中。

截至 2026 年 9 月 19 日，RDC 官网列出的免费方案包含每月 10,000 次工具调用[6]。如果只是想让 ChatGPT 帮忙处理文件、运行程序，可以先看看这类现成工具是否够用，再决定要不要花时间制作专用 MCP。

## 把 Codex 上下文带进 Chat 继续讨论

如果只是想让 Chat 接着 Codex 中已经聊过的内容分析问题、推敲方案，改文件和运行程序仍交给 Codex， **直接用 Codex 里的 Chat 入口就更方便，不必为此配置 MCP** 。

在 Codex 客户端中打开当前任务，保持在 Codex 栏目，点击“新对话”右边带加号的小气泡。这样打开的 Chat 会自动带入当前会话的上下文，可以直接接着提问，不用自己复制聊天记录、重新交代背景。方案讨论好后，点击“添加到 Codex”，就能把讨论带回原任务，再让 Codex 按商定的方案执行。

特别长的会话可能无法完整带入，可以先让 Chat 复述关键条件，确认后再继续讨论。入口截图、回传步骤和上下文长度限制，见《 [这个 Chat 入口能继承 Codex 上下文，还能把方案交回去执行](https://zhuanlan.zhihu.com/p/2084652733618046475) 》。
