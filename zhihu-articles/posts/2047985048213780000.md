Independent Thread Scheduling（ITS），通常翻译成独立线程调度。它解决的问题很具体：一个 warp 里有 32 个 lane，如果它们遇到分支、循环、提前退出，走到了不同的 PC，执行器应该怎么继续推进，又怎么在需要的时候重新汇合？

### 0x01. warp 分歧

一个 warp 有 32 个 lane。理想情况下，32 个 lane 执行同一条指令，只是操作的数据不同：

```text
lane 0  算 a[0] + b[0]
lane 1  算 a[1] + b[1]
...
lane 31 算 a[31] + b[31]e
```

但真实程序有分支：

```text
if (x > 0) {
    y = a + b;
} else {
    y = a - b;
}
```

同一个 warp 里，有些 lane 的 `x > 0`，有些 lane 的 `x <= 0`。于是它们要走不同路径，这就是 control divergence，控制流分歧。

传统直觉里，可以把 warp 想成一整队人：先让走 `then` 的人干活，其他人等；再让走 `else` 的人干活；最后大家在 join 点重聚。

![](https://pic3.zhimg.com/v2-c62272cc929b20dd1c913ad2fe090d8e_r.jpg)

ITS 的核心变化是：warp 仍然是调度组织单位，但每个 lane 可以拥有自己的 `pc[lane]`。调度器每一步把当前同 PC 的 lane 临时分成一组，只执行这一组。

```text
某一时刻：

PC=10: lane 0, lane 1, lane 4
PC=14: lane 2, lane 3
PC=18: lane 5, lane 6, lane 7

调度器选择一个 PC group。
执行该 PC 上的一条指令。
被执行 lane 各自更新 pc[lane]。
下一步重新按 PC 分组。
```

所以 ITS 不是把 32 个 lane 变成 32 个完整 CPU 线程。它仍然尽量把同 PC 的 lane 合并执行，只是控制流状态从“全 warp 一个 PC”变成了“每 lane 一个 PC”。

### 0x02. ITS 最小状态

为了让这套机制可执行、可验证，一个 warp 至少需要这些状态：

```text
pc[32]              每个 lane 的当前位置
lane_state[32]      active / blocked / yielded / exited
active_mask[32]     lane 是否还参与当前 warp 执行
predicate Pn[32]    每个谓词寄存器是 32-bit lane mask
vgpr Rn[32]         每个向量寄存器跨 32 lane 存一组值
Bx[16]              16 个 warp 内收敛屏障槽
```

`pc[32]` 是 ITS 的核心。只要不同 lane 的 `pc` 不同，分歧就能被直接表示出来。

但仅有 `pc[32]` 不够。因为程序还需要表达“这些 lane 虽然分头走了，但必须在某个点等齐再继续”。这就是 `Bx[16]` 收敛屏障的作用。

每个 `Bx` 槽在对外 有三个字段：

```text
participation_mask  这次收敛需要等待哪些 lane
reconv_pc           这次收敛的 join/BSYNC 位置
valid               这个槽当前是否 armed
```

实现里还需要私有状态区分 `unarmed`、`armed`、`dissolved`，并记录每个 blocked lane 当前阻塞在哪个 barrier 上。

### 0x03. 调度规则：per-PC grouping

每一步调度做三件事：

1. 收集 `lane_state == active` 的 lane。
2. 按 `pc[lane]` 分组。
3. 按某个确定顺序选一个 PC group 执行。

![](https://pic1.zhimg.com/v2-7d27c3cae8f14c4edf37d32c3582cef2_r.jpg)

确定顺序可以有很多种，例如：

```text
min_pc_first
max_pc_first
round_robin
oldest_group_first
```

这些顺序不是为了模拟某一块真实硬件的逐周期行为，而是为了验证语义：对于同步写得清楚、没有数据竞争的程序，换不同 group 调度顺序，最终架构态应该一致。也就是说，合法程序不应该依赖“then 组先跑还是 else 组先跑”。

这就是 ITS 功能模型最重要的验收标准之一：调度序无关。

### 0x04. 指令总览

我们当前定义的 ITS 相关指令可以分成四组。

第一组是生成 per-lane 数据：

```text
S2R Rd, SR_LANEID
```

`S2R` 从特殊寄存器读值。当前只定义了 `SR_LANEID`，也就是每个 lane 在 warp 内的编号 `0..31`。它是构造真实 per-lane 分歧的基础。

第二组是收敛屏障：

```text
BSSY  Bx, target
BSYNC Bx
BREAK Bx
YIELD
EXIT
```

`BSSY` 建立一个 barrier token；`BSYNC` 在 join 点等待并消费 token；`BREAK` 把当前 lane 从 token 的参与集合里移除；`YIELD` 是调度提示；`EXIT` 让 lane 退休，并从所有 live barrier 的参与集合中清掉这个 lane。

第三组是 collective：

```text
ELECT Pd, membermask
VOTE.<mode> Pd, Psrc, membermask
VOTE.BALLOT Pd, Psrc, membermask, Rd
```

`ELECT` 在一个 membermask 指定的 lane 集合里选 leader。`VOTE` 做 warp/subwarp 级布尔归约或 ballot。

第四组是普通控制和标量/向量操作：

```text
ISETP
IADD3
LOP3
BRA
```

它们不是 ITS 专属，但分支谓词、寄存器更新和 PC 更新都靠它们配合完成。

### 5. `S2R`: 制造真正的 per-lane 分歧

如果所有 lane 的输入都一样，程序很难真正分歧。`S2R Rd, SR_LANEID` 给每个 lane 一个不同的值：

```text
S2R R1, SR_LANEID
```

执行后：

```text
R1[lane 0]  = 0
R1[lane 1]  = 1
...
R1[lane 31] = 31
```

接下来可以用 `ISETP` 基于 lane id 生成谓词：

```text
S2R  R1, SR_LANEID
IADD3 R2, RZ, RZ, 16
ISETP P0, R1, R2, lt
```

这会得到：

```text
P0 = true   for lane 0..15
P0 = false  for lane 16..31
```

然后一条带谓词的 `BRA` 就会让 warp 分裂：

```text
@P0 BRA then_path
```

满足 `P0` 的 lane 跳到 `then_path`，不满足的 lane fallthrough。执行完这条分支后，`pc[0..15]` 和 `pc[16..31]` 就可能不同，ITS 调度器会在后续步骤里按 PC group 分别推进。

### 6. `BSSY` 和 `BSYNC`: 给分歧路径一个汇合点

最基本的 if/else 形状是：

```text
BSSY  B0, join
        @P0 BRA then_path

else_path:
        IADD3 R2, RZ, RZ, 20
        BRA   join

then_path:
        IADD3 R2, RZ, RZ, 10

join:
        BSYNC B0
        IADD3 R3, R2, RZ, 1
        EXIT
```

这里 `BSSY B0, join` 的意思是：在 `B0` 这个槽上建立一个收敛 token。参与者是当前 PC group 的 lane，也就是当时一起执行 `BSSY` 的 lane。`target` 指向 join 位置，也就是后面的 `BSYNC B0`。

分支发生后，lane 被拆到不同 PC group：

```text
then_path: lane subset A
else_path: lane subset B
```

它们可以按任意确定顺序执行。某一组先到 `join` 时，执行 `BSYNC B0`，这组 lane 会进入 `blocked`。等另一组也到达同一个 `BSYNC B0`，如果 `B0.participation_mask` 里的所有存活 lane 都已经到达，那么 barrier fire：

```text
blocked lane -> active
B0.valid     -> false
所有到齐 lane 从 BSYNC 的 fallthrough 继续
```

于是 `IADD3 R3, R2, RZ, 1` 会在重聚后执行。

这就是 `BSSY`/`BSYNC` 的核心：`BSSY` 标记“这批 lane 后面需要重聚”，`BSYNC` 是“到这里等齐再继续”。

这里有两个限制：

- `BSSY` 不能覆盖一个仍然 live 的 `Bx`，否则是 `bssy_clobbers_live_barrier`。
- `BSSY` 和 `BSYNC` 当前不支持谓词化；带非默认 guard 会触发 `predicated_barrier_unsupported`。

如果只让部分 lane 建立或消费 barrier，参与集合会变得不清楚，容易制造死锁或序相关行为。

### 0x07. `BREAK`: 从收敛集合里退出

循环里的提前退出不能简单靠 `BRA done`。如果某个 lane 还留在 barrier 的 `participation_mask` 里，但它跳走后再也不到 `BSYNC`，其他 lane 会永远等它。

所以 loop break 要先执行 `BREAK Bx`：

```text
loop_head:
        BSSY  B0, loop_join
        ISETP P1, R2, R7, ge
        @P1 BREAK B0
        @P1 BRA   done

loop_body:
        IADD3 R2, R2, RZ, 1
        BRA   loop_join
loop_join:
        BSYNC B0
        BRA   loop_head

done:
        EXIT
```

这里的语义是：

```text
@P1 BREAK B0
```

对 guard-true 的 lane，把它们从 `B0.participation_mask` 里清掉。它们后面可以跳到 `done`，不再参与这轮 loop 的 `BSYNC B0`。

如果 `BREAK` 清掉了最后一个参与者，`B0` 会进入 `dissolved` 状态。之后遇到 `BSYNC B0` 时，它不是非法未初始化 barrier，而是直接 fallthrough。这一点很关键：break-all 的循环是合法形状，不应该误报 trap。

### 0x08. `EXIT`: 退休 lane 也必须清 barrier

`EXIT` 会让 guard-true lane 进入 `exited`，并清掉 `active_mask`。在 ITS 下它还有一个同步含义：退出的 lane 必须从所有 live barrier 的 `participation_mask` 中移除。

否则会出现这种死锁：

```text
lane 0 提前 EXIT
lane 1..31 到 BSYNC 等 lane 0
lane 0 已经不可能再到达
```

所以 `EXIT` 的语义不是单纯“这个 lane 不跑了”，还包括“所有正在等待它的 warp 内收敛 token 都不再等待它”。

这也是为什么 early-exit 可以成为合法 ITS 形状：

```text
BSSY B0, join
        @P0 EXIT
        IADD3 R2, RZ, RZ, 7
join:
        BSYNC B0
        EXIT
```

`@P0 EXIT` 的 lane 会从 `B0` 的参与集合里移除；剩余 lane 到 `BSYNC B0` 后可以正常继续，不会等已经退休的 lane。

### 0x09. `YIELD`: 调度提示

当前语义里，`YIELD` 对 guard-true lane 做的是：

```text
lane_state = yielded
```

它没有寄存器效果，没有 PC 重定向效果，也不会让 barrier fire。调度器在没有 active group 可跑时，会先尝试 fire barrier，再把 yielded lane 提升回 active。

所以 `YIELD` 更像是“我可以让别人先跑一下”的调度提示。它不能替代 `BSYNC`，也不能说明某个 shared result 已经可见。需要重聚时，仍然要用明确的 barrier 形状。

一个简单形状是：

```text
YIELD
        BSSY  B0, join
        IADD3 R1, RZ, RZ, 1
join:
        BSYNC B0
        EXIT
```

这个程序不应因为 `YIELD` 改变最终架构结果。`YIELD` 只影响调度机会，不改变同步契约。

### 0x0A. `ELECT`: 在 membermask 中选 leader

`ELECT Pd, membermask` 是一个 collective。它在 `membermask` 指定的 lane 集合中选出最小 lane id 作为 leader：

```text
ELECT P1, 0x0000000F
```

`0x0000000F` 表示 lane 0..3。执行后：

```text
P1[lane 0] = true
P1[lane 1] = false
P1[lane 2] = false
P1[lane 3] = false
P1[lane 4..31] 保持原值
```

这里有一个严格约束：`membermask` 必须是当前参与集的子集。当前参与集指当前 PC group 中 guard-true 且 active 的 lane。也就是说，collective 不能声称“我要让 lane 0..31 都参与”，但实际当前只有 lane 16..31 在这个 PC 上执行。

如果违反这个约束，会触发：

```text
membermask_not_subset
```

如果 `membermask` 是 0，或者没有任何可参与 lane，会触发：

```text
self_not_in_membermask
```

这个约束是 ITS 下 collective 正确性的关键。因为在 per-PC grouping 下，warp 中不同 lane 可能不在同一个动态位置。collective 必须只覆盖真正同时到达同一动态位置的 lane。

### 0x0B. `VOTE`: subwarp 布尔归约和 ballot

`VOTE` 也是 collective，支持四种 mode：

```text
VOTE.ANY    Pd, Psrc, membermask
VOTE.ALL    Pd, Psrc, membermask
VOTE.EQ     Pd, Psrc, membermask
VOTE.BALLOT Pd, Psrc, membermask, Rd
```

假设：

```text
P0[lane 0..3] = true, false, true, false
membermask    = 0x0000000F
```

那么：

```text
VOTE.ANY P1, P0, 0xF
```

会把 `true` 广播给 lane 0..3 的 `P1`，因为至少一个 member 的 `P0` 为 true。

```text
VOTE.ALL P2, P0, 0xF
```

会把 `false` 广播给 lane 0..3 的 `P2`，因为不是所有 member 的 `P0` 都为 true。

```text
VOTE.EQ P3, P0, 0xF
```

会把 `false` 广播给 lane 0..3 的 `P3`，因为 member 的 `P0` 不全相等。

```text
VOTE.BALLOT P4, P0, 0xF, R2
```

会把 bitmask `0b0101` 写到 lane 0..3 的 `R2`，也把 ballot 是否非空等结果写到 `P4`。`Rd=RZ` 时可以丢弃寄存器结果。

和 `ELECT` 一样，`VOTE` 的 `membermask` 必须是当前参与集的子集。ITS 下不允许 collective 偷偷跨越还没重聚的分歧路径。

### 0x0C. 一段完整 diamond 的执行过程

用一个 8-lane 简化例子看完整流程：

```text
lane: 0 1 2 3 4 5 6 7
P0:   T F T F T F T F
```

代码形状：

```text
0: BSSY  B0, join
1: @P0 BRA then_path
2: IADD3 R2, RZ, RZ, 20
3: BRA   join
4: then_path:
5: IADD3 R2, RZ, RZ, 10
6: join:
7: BSYNC B0
8: IADD3 R3, R2, RZ, 1
9: EXIT
```

执行到 `@P0 BRA then_path` 后：

```text
PC=2: lane 1,3,5,7
PC=5: lane 0,2,4,6
```

调度器可能先选 `PC=2`：

```text
lane 1,3,5,7 执行 R2=20
它们跳到 join，执行 BSYNC B0，进入 blocked
```

再选 `PC=5`：

```text
lane 0,2,4,6 执行 R2=10
它们到 join，执行 BSYNC B0
```

此时 `B0.participation_mask` 中所有存活 lane 都到达了 `BSYNC`，barrier fire，所有参与 lane 从 `BSYNC` 后继续：

```text
R3[lane 0,2,4,6] = 11
R3[lane 1,3,5,7] = 21
```

如果调度顺序反过来，先跑 `then_path` 再跑 `else_path`，最终 `R2/R3` 也应该相同。这就是调度序无关。
