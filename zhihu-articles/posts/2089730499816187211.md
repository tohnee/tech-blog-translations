最近开始系统学习 RDMA。最初接触这个概念时，我把它简单理解成“远程版 DMA”：DMA 是本机设备和内存之间的数据搬运，那么 RDMA 就是跨主机、跨网络进行数据搬运，这个理解有一定道理，但还不完整。

RDMA 真正有价值的地方，并不只是“能够访问远端内存”，而是它重新设计了数据从应用程序到网络、再到远端应用程序的传输路径，尽量减少系统调用、内核协议栈处理、CPU 拷贝和中断开销，并把大量数据传输工作交给专用网卡，也就是 RNIC 来完成。

本文想从几个问题出发，梳理 RDMA 的基本思想：

- RDMA 到底是什么？
- 它相比传统 TCP 网络快在哪里？
- InfiniBand、RoCEv2 和 iWARP 有什么区别？
- 为什么 RoCEv2 经常和 PFC、ECN、DCQCN 一起出现？
- RDMA 的 MR、QP、CQ、WR 到底是什么？
- RDMA 为什么适合数据中心，却很难直接推广到普通广域网？

### 一、RDMA 到底是什么

RDMA 的英文全称是 **Remote Direct Memory Access**，中文通常翻译为“远程直接内存访问”。

它描述的是一种高性能通信架构和编程模型：一台主机上的应用程序，可以通过 RDMA 网卡，直接访问另一台主机上已经注册并授权的内存区域。

这里有几个关键词需要注意。

### 1. RDMA 不等于 DMA

DMA 的全称是 **Direct Memory Access**，它描述的是设备直接访问主机内存的能力。

例如，普通网卡收到数据后，可以通过 DMA 把数据写入主机内存。磁盘、GPU、存储控制器等设备，也都可以使用 DMA。

因此，DMA 主要解决的是：

> 如何让设备和主机内存之间搬运数据时，减少 CPU 的参与。

RDMA 在 DMA 的基础上进一步扩展了访问范围：

> 不仅让本地设备直接访问本地内存，还允许本地 RNIC 通过网络访问远端主机中经过注册和授权的内存。

所以，DMA 是 RDMA 的底层基础之一，但 RDMA 不是“把 DMA 搬到远端”这么简单。RDMA 还包括：

- 远程内存访问语义；
- 内存注册与权限控制；
- 队列对 QP；
- 完成队列 CQ；
- 工作请求 WR；
- 工作完成 WC；
- 网卡硬件卸载；
- 可靠传输或不可靠传输；
- 拥塞控制；
- 不同底层网络的承载方式。

### 2. RDMA 是架构和编程模型，不是单一协议

严格来说，RDMA 更像一套通信架构和编程模型，而不是某一个单独的网络协议。

常见的 RDMA 承载方式包括：

- InfiniBand：使用专用的 InfiniBand 网络；
- RoCE：RDMA over Converged Ethernet，在以太网上承载 RDMA；
- iWARP：RDMA over TCP，在 TCP/IP 网络上承载 RDMA。

可以简单理解为：

- RDMA 定义了“应用如何使用远程内存”；
- InfiniBand、RoCEv2、iWARP 定义了“这些 RDMA 语义如何通过具体网络传输”。

TCP、UDP、IP、RoCEv2、iWARP 等更偏向具体协议，它们需要定义报文格式、字段、交互流程和传输语义。

### 二、传统 TCP 通信的开销在哪里

为了理解 RDMA 为什么快，可以先看一条典型的 TCP 数据路径。

这里以传统的 `send()` 和 `recv()` 为例。

### 发送路径

1. 应用程序在用户态调用 `send()`；
2. 发生系统调用，CPU 从用户态进入内核态；
3. 内核把用户态数据复制到内核中的 socket 缓冲区；
4. 内核 TCP/IP 协议栈处理数据；
5. 内核添加协议头，进行分段、校验和、拥塞控制等处理；
6. 网卡驱动把内核缓冲区交给网卡；
7. 网卡使用 DMA 从内核缓冲区读取数据；
8. 网卡把数据发送到网络；
9. 系统调用返回，CPU 从内核态回到用户态。

### 接收路径

1. 网卡收到数据；
2. 网卡通过 DMA 把数据写入内核接收缓冲区；
3. 内核协议栈进行校验、排序、重组和 ACK 处理；
4. 应用调用 `recv()`；
5. 发生系统调用，CPU 进入内核态；
6. 内核把数据从内核缓冲区复制到用户态缓冲区；
7. 系统调用返回，应用拿到数据。

这条路径并不意味着所有 TCP 实现都一定存在完全相同的拷贝次数。现代系统也有 sendfile、内核旁路、零拷贝扩展等优化方式，但是，以经典的 `send/recv` 路径为例，主要开销通常来自以下几个方面。

### 1. 系统调用和上下文切换

应用调用 `send()` 或 `recv()` 时，需要进入内核。

对于大消息来说，这部分开销可能相对有限；但对于大量小消息、高并发通信和微秒级延迟场景，频繁的用户态与内核态切换会变得非常明显。

### 2. CPU 拷贝

数据可能需要在用户缓冲区和内核缓冲区之间复制。

这种复制不仅消耗 CPU 周期，也会占用内存带宽。对于分布式训练、存储系统和高性能计算来说，数据量非常大，拷贝成本不能忽略。

### 3. 内核协议栈处理

TCP 的可靠传输、排序、重传、确认、拥塞控制和连接状态维护，都需要经过内核协议栈。

这意味着 CPU 需要参与大量网络数据包的处理。

### 4. 中断和调度开销

网卡收到数据后，通常需要通过中断或轮询机制通知 CPU。高吞吐通信下，如果每个数据包都引发大量处理，CPU 可能会把相当多的时间花在网络协议和中断上。

### 三、RDMA 快在哪里

RDMA 的核心思路可以概括成三句话：

> 让应用直接提交通信请求。<br>让网卡直接访问用户内存。<br>让 RNIC 硬件处理尽可能多的传输工作。

### 1. 内核旁路

RDMA 应用通常通过用户态 verbs 库操作 RDMA 资源。

在数据面上，应用可以在用户态构造工作请求，并通过门铃机制通知 RNIC。这样，普通数据传输不需要每次都通过传统的 `send()` 和 `recv()` 系统调用进入内核。

需要注意的是，RDMA 并不是“从头到尾完全不需要内核”。

设备打开、资源创建、内存注册、地址映射、权限设置等控制面操作仍然需要操作系统和驱动参与。更准确的说法是：

> RDMA 尽量绕过内核数据路径，而不是完全绕过内核。

### 2. 零拷贝或少拷贝

应用注册一块用户态内存后，RNIC 可以直接通过 DMA 读取或写入这块内存。

这避免了经典 TCP 路径中用户缓冲区和内核 socket 缓冲区之间的 CPU 拷贝。

不过，“零拷贝”不应该理解成系统中绝对不存在任何数据复制。应用可能仍然需要准备数据、组织缓冲区，硬件内部也可能存在分段、重组或缓存过程。

更严谨的说法是：

> RDMA 避免了数据面上很多由 CPU 执行的用户态与内核态之间的数据复制。

### 3. 网卡硬件卸载

在传统 TCP 通信中，CPU 和内核协议栈需要处理很多传输任务。

在 RDMA 中，大量工作由 RNIC 硬件完成，例如：

- 分段和组装；
- DMA 数据搬运；
- 包序号处理；
- ACK 和重传；
- 访问权限检查；
- 可靠传输状态维护；
- RDMA Read、RDMA Write 等操作；
- 完成队列更新。

RNIC 的优势不一定是单个硬件模块“比 CPU 更聪明”，而是它被专门设计成持续、高并发、流水线地处理网络数据，因此可以减少 CPU 在数据面上的工作。

### 4. 远端 CPU 可以不参与数据搬运

以 RDMA Write 为例：

1. 发送方 RNIC 从本地用户缓冲区读取数据；
2. 数据经过网络传输；
3. 接收方 RNIC 校验目标地址和访问密钥；
4. 接收方 RNIC 直接把数据写入接收方用户内存；
5. 接收方 CPU 不需要执行一次传统的收包、拷贝和唤醒流程。

这就是 RDMA 的重要特点：

> 数据可以直接到达远端内存，而不必先经过远端内核缓冲区。

但是，应用层仍然需要设计通知和同步机制。远端 CPU “没有参与搬运数据”，并不等于应用程序完全不需要知道数据已经到达。

### 四、RDMA 的基本数据路径

一条简化的 RDMA 数据路径如下：

```text
发送方应用
    ↓
用户态工作请求 WR
    ↓
发送方 RNIC
    ↓
DMA 读取发送缓冲区
    ↓
RoCEv2 / InfiniBand / iWARP
    ↓
网络交换机
    ↓
接收方 RNIC
    ↓
DMA 写入接收方用户内存
    ↓
接收方应用读取数据
```

RDMA 的性能优势主要来自两方面：

1. 减少数据路径上的软件步骤；
2. 让专用硬件完成大量传输和协议处理。

可以把通信总时间粗略写成：

```text
总时间 =
发送端处理时间
+ 网络传输时间
+ 接收端处理时间
```

RDMA 主要优化的是发送端和接收端的处理路径。

如果网络本身存在严重拥塞、带宽不足、排队严重或丢包，端点优化并不能解决全部问题。因此，RDMA 的性能不仅取决于 RNIC，也取决于：

- 网卡带宽；
- PCIe 带宽；
- CPU 与网卡的 NUMA 关系；
- 交换机缓存；
- 网络拥塞；
- 消息大小；
- RTT；
- 拥塞控制参数；
- 应用是否能够持续提交足够多的工作请求。

### 五、InfiniBand、RoCEv2 和 iWARP

目前常见的 RDMA 实现路线主要有三种。

| 技术 | 底层网络 | 主要特点 | 主要问题 |
| --- | --- | --- | --- |
| InfiniBand | 专用网络 | 性能稳定、延迟低、专用协议栈 | 需要专用设备，成本和运维门槛较高 |
| RoCEv2 | 以太网、IP、UDP | 可以复用数据中心以太网，性能高，可路由 | 对网络拥塞和 QoS 配置敏感 |
| iWARP | TCP/IP | 可以运行在普通 IP 网络上，天然使用 TCP 可靠传输 | 协议处理复杂，延迟和性能通常不如前两者 |

### 1. InfiniBand

InfiniBand 从物理层到传输层都围绕高性能计算设计。

它使用专用网卡、专用交换机和专用网络协议，网络本身具有较强的流控和可靠传输能力。

优点包括：

- 延迟低；
- 吞吐稳定；
- 抖动较小；
- 适合 HPC、AI 训练和高性能存储；
- 网络协议与设备整体协同设计。

缺点包括：

- 需要专用设备；
- 设备和线缆成本较高；
- 网络生态相对封闭；
- 部署和运维需要专门经验；
- 与普通以太网环境的互通需要额外设备或网关。

InfiniBand 可以理解为“从头设计的一套高性能 RDMA 网络”。

### 2. RoCEv2

RoCE 的英文全称是 **RDMA over Converged Ethernet**。

RoCE 有两个常见版本：

- RoCEv1：直接运行在以太网链路层；
- RoCEv2：封装在 UDP/IP 中，可以通过三层网络路由。

RoCEv2 的典型封装可以简化表示为：

```text
以太网头
    ↓
IP 头
    ↓
UDP 头
    ↓
RDMA 传输头，例如 BTH、RETH
    ↓
RDMA 数据
    ↓
ICRC
    ↓
以太网 FCS
```

RoCEv2 的 UDP 目的端口通常是 4791。

需要特别澄清：

> RoCEv2 使用 UDP 封装，不代表 RDMA 传输本身完全不可靠。

UDP 本身不负责可靠传输，但 RoCEv2 中具体的 RDMA 传输类型，例如 RC，会由 RNIC 实现确认、序号、重传等机制。

因此：

- UDP 是 RoCEv2 的网络承载方式；
- RDMA 传输类型决定具体的可靠性；
- RC 可以提供可靠连接语义；
- UC 和 UD 则提供不同程度的不可靠语义。

RoCEv2 的优点包括：

- 可以使用以太网布线；
- 可以使用 IP 路由；
- 可以与数据中心网络设备结合；
- 性能通常接近专用 RDMA 网络；
- 适合大规模数据中心和 AI 集群。

但 RoCEv2 对网络配置要求较高，通常需要配合：

- PFC；
- ECN；
- ETS；
- 合理的队列和优先级配置；
- 拥塞控制算法；
- 交换机缓冲区管理。

RoCEv2 并不是数学意义上的“绝对无损网络”。更准确的说法是：

> 许多 RoCEv2 数据中心部署会建设近似无损或低丢包网络，以减少 RNIC 重传和性能抖动。

### 3. iWARP

iWARP 的全称是 **Internet Wide Area RDMA Protocol**。

它在 TCP 之上承载 RDMA 语义，通常涉及：

- MPA；
- DDP；
- RDMAP。

iWARP 的优点是：

- 可以运行在 TCP/IP 网络上；
- 可以使用普通 IP 路由；
- 对交换机不要求 PFC；
- 对网络丢包的适应性更好；
- 更容易穿过传统 IP 网络环境。

但它也存在一些代价：

- TCP 本身包含较复杂的可靠传输和拥塞控制机制；
- 延迟和抖动通常高于 InfiniBand 和高质量 RoCEv2；
- 硬件实现和协议处理较复杂；
- 产业生态和应用普及度相对有限。

iWARP 的核心思路可以理解为：

> 牺牲一部分极致性能，换取更好的 IP 网络兼容性和丢包适应能力。

### 六、RoCEv2 为什么需要 PFC

PFC 的英文全称是 **Priority Flow Control**，即优先级流控。

PFC 属于链路层机制，主要作用范围是相邻设备之间的一跳链路。

它的基本工作方式是：

1. 交换机检测到某个优先级队列接近拥塞；
2. 交换机向上游设备发送暂停帧；
3. 上游设备暂时停止发送对应优先级的流量；
4. 队列压力下降后，再恢复发送。

PFC 的目标是尽量防止交换机缓存溢出。

但是，PFC 并不会让网络自动变成“绝对可靠”。它只是通过暂停发送来降低丢包概率，同时也会带来新的问题。

### 1. 队头阻塞

同一个优先级队列中，可能同时存在多个不同流。

如果其中一个流导致队列拥塞，整个优先级的流量都可能被暂停，其他本来没有问题的流也会受到影响。

### 2. PFC 风暴

PFC 是逐跳传播的。

一个端口发生拥塞后，可能向上游发送暂停；上游继续向更上游传播暂停，最终造成大范围流量停顿。这种现象通常被称为 PFC 风暴。

### 3. PFC 死锁

在某些拓扑和流量条件下，多个设备之间可能形成循环等待：

```text
A 等待 B
B 等待 C
C 等待 A
```

如果队列和暂停关系形成循环，就可能出现长时间无法恢复的阻塞。

### 4. 公平性问题

PFC 通常按照优先级暂停，而不是精确区分每一个流。

一个大流造成队列拥塞时，同一优先级下的其他流也可能被一起暂停。

因此，PFC 更像是一道安全阀，而不是理想的拥塞控制算法。

### 七、ECN 和 DCQCN 如何协同工作

### 1. ECN 是什么

ECN 的英文全称是 **Explicit Congestion Notification**，即显式拥塞通知。

传统网络通常在队列完全满之后丢包，然后发送端通过丢包和重传感知拥塞。

ECN 的思路是：

> 在队列真正溢出之前，先在 IP 头中标记拥塞，让发送端提前降速。

ECN 字段有四种状态：

- Not-ECT：不支持 ECN；
- ECT(0)：支持 ECN；
- ECT(1)：支持 ECN；
- CE：发生拥塞，需要通知发送端。

一个简化的 ECN 流程如下：

1. 发送端发送带有 ECT 标记的数据包；
2. 交换机发现队列超过阈值；
3. 交换机把 IP 头中的 ECN 标记改为 CE；
4. 接收端收到 CE 标记；
5. 接收端向发送端反馈拥塞通知；
6. 发送端降低发送速率。

### 2. DCQCN 是什么

DCQCN 的英文全称是 **Data Center Quantized Congestion Notification**，是面向数据中心 RDMA 网络的一种拥塞控制机制。

它通常与 RoCEv2、ECN 和 CNP 配合使用。

DCQCN 的简化闭环如下：

```text
交换机拥塞
    ↓
ECN 标记 CE
    ↓
接收方 RNIC 识别 CE
    ↓
发送 CNP
    ↓
发送方 RNIC 收到 CNP
    ↓
降低发送速率
```

其中：

- ECN 负责标记拥塞；
- CNP 负责把拥塞信号反馈给发送端；
- DCQCN 负责根据反馈调整发送速率；
- PFC 负责在拥塞进一步恶化时提供保护。

### 3. α 参数的作用

DCQCN 中通常会维护一个反映拥塞程度的参数，例如 α。

可以把它理解成：

> 收到的拥塞通知越多，说明网络越拥塞，α 越大，发送速率下降得越明显。

一个用于理解的简化表达是：

```text
新速率 ≈ 当前速率 × (1 - α / 2)
```

当拥塞持续发生时，发送端会持续降速；当一段时间没有继续收到拥塞通知时，α 会逐步衰减，发送速率再慢慢恢复。

实际 RNIC 的参数、定时器、增加策略和实现细节会因协议版本、厂商和配置而不同，因此不应把某一个固定公式或固定微秒数当作所有设备的统一实现。

### 4. DCQCN 是否天然公平

不能简单说 DCQCN“天然公平”。

DCQCN 的设计目标之一是改善不同流之间的带宽分配：发送较快、造成更多拥塞的流，更可能收到更多反馈，也会受到更明显的降速。

但最终公平性还取决于：

- ECN 标记位置；
- 队列阈值；
- 流量模式；
- RTT；
- 拓扑结构；
- 发送速率；
- 交换机和 RNIC 的参数；
- 不同流是否经过相同的瓶颈。

所以更准确的表述是：

> DCQCN 试图通过端到端速率调节改善公平性和拥塞稳定性，但公平性并不是无条件保证的。

### 八、RDMA 的核心对象：MR、QP、CQ 和 WR

理解 RDMA 编程，通常要先掌握几个基本对象。

### 1. MR：Memory Region

MR 是注册到 RDMA 网卡的内存区域。

应用调用类似 `ibv_reg_mr()` 的接口，将一段用户态缓冲区注册给 RNIC。

注册过程通常包括：

- 检查内存区域；
- 固定内存，避免 DMA 过程中被换出；
- 建立设备访问所需的地址映射；
- 设置本地和远程访问权限；
- 返回内存区域句柄；
- 生成本地密钥 lkey 和远程密钥 rkey。

### 2. lkey 和 rkey

- lkey：本地网卡访问本地内存时使用；
- rkey：远端网卡访问本地内存时使用。

远端访问不是“知道地址就可以随便读写”。

远端访问通常需要同时具备：

- 目标 QP 状态正确；
- 远端虚拟地址正确；
- rkey 正确；
- 目标内存区域允许对应操作；
- 访问长度合法。

因此，rkey 既是访问凭证，也是权限控制的一部分。

### 3. QP：Queue Pair

QP 是 RDMA 通信的核心队列对象，通常包含：

- SQ：Send Queue，发送队列；
- RQ：Receive Queue，接收队列。

应用把工作请求提交到 SQ 或 RQ，RNIC 再异步处理这些请求。

QP 通常需要经过以下状态转换：

```text
RESET → INIT → RTR → RTS
```

其中：

- RESET：初始状态；
- INIT：完成本地初始化；
- RTR：Ready to Receive，可以接收数据；
- RTS：Ready to Send，可以发送数据。

在正式通信之前，双方通常还需要交换：

- QP number；
- GID；
- LID 或网络地址信息；
- rkey；
- 远端虚拟地址；
- 其他连接参数。

这些信息可以通过 TCP、控制面协议或其他带外方式交换。

### 4. CQ：Completion Queue

CQ 是完成队列。

当 RNIC 完成某个工作请求后，可以向 CQ 写入一个完成队列条目 CQE。应用通过轮询或事件通知读取 CQE，从而知道某个操作已经完成。

一个典型流程是：

```text
应用构造 WR
    ↓
WR 提交到 SQ
    ↓
RNIC 执行操作
    ↓
RNIC 写入 CQE
    ↓
应用轮询 CQ
    ↓
应用确认操作完成
```

### 5. WR：Work Request

WR 是应用提交给 RNIC 的工作请求。

一个 WR 通常会描述：

- 操作类型；
- 缓冲区地址；
- 数据长度；
- lkey；
- 远端地址；
- rkey；
- 是否生成完成通知；
- 是否携带 immediate data。

常见 RDMA 操作包括：

- Send；
- Receive；
- RDMA Write；
- RDMA Write with Immediate；
- RDMA Read；
- Atomic。

### 九、RDMA Write 和 RDMA Write with Immediate

这两个操作很容易混淆。

### 1. RDMA Write

RDMA Write 的基本流程是：

1. 发送方 RNIC 从本地缓冲区读取数据；
2. 通过网络发送 RDMA Write 请求；
3. 接收方 RNIC 检查目标地址和 rkey；
4. 接收方 RNIC 将数据直接写入远端用户内存；
5. 接收方 CPU 不需要参与数据搬运；
6. 发送方根据完成信息判断本地 WR 是否完成。

普通 RDMA Write 不需要消耗接收方的 RQ，也通常不会在接收方生成一个普通的接收 CQE。

因此，如果接收方应用需要知道数据什么时候到达，就需要额外设计通知机制，例如：

- 在共享内存中写入标志位；
- 使用 RDMA Write with Immediate；
- 使用 Send/Receive；
- 使用其他应用层同步协议。

### 2. RDMA Write with Immediate

RDMA Write with Immediate 除了写入远端内存，还携带一个立即数通知。

它通常需要接收方提前在 RQ 中准备接收工作请求。

当接收方 RNIC 收到这个操作后：

1. 数据被写入远端内存；
2. 立即数被传递给接收方；
3. 消耗接收方的一个接收工作请求；
4. 接收方 CQ 中生成完成条目；
5. 接收方应用轮询 CQ 后得知数据已经到达。

因此，两者的区别可以概括为：

| 操作 | 是否写远端内存 | 是否需要接收方 RQ | 是否通知接收方 |
| --- | --- | --- | --- |
| RDMA Write | 是 | 通常不需要 | 通常不直接通知 |
| RDMA Write with Immediate | 是 | 需要 | 可以通过 CQE 通知 |

### 十、RoCEv2 中一个 RDMA Write 的大致过程

下面用一个简化的 RoCEv2 RDMA Write 流程串起来。

### 第一步：准备 RDMA 资源

发送方和接收方分别完成：

- 打开 RDMA 设备；
- 创建保护域 PD；
- 创建 CQ；
- 注册 MR；
- 创建 QP；
- 完成 QP 状态转换；
- 交换 QP number、GID、rkey 和远端地址。

### 第二步：发送方提交工作请求

发送方构造一个 RDMA Write WR，其中包含：

- 本地缓冲区地址；
- 本地 lkey；
- 数据长度；
- 远端虚拟地址；
- 远端 rkey。

然后将 WR 提交到 QP 的 SQ。

### 第三步：发送方 RNIC 读取数据

发送方 RNIC 根据本地地址和 lkey 检查权限，然后通过 DMA 从用户态缓冲区读取数据。

### 第四步：RNIC 封装 RoCEv2 报文

报文可以抽象表示为：

```text
Ethernet
    ↓
IP
    ↓
UDP
    ↓
BTH
    ↓
RETH
    ↓
RDMA Payload
    ↓
ICRC
    ↓
Ethernet FCS
```

其中：

- BTH 是 Base Transport Header；
- RETH 中可以携带远端虚拟地址、rkey 和数据长度；
- ICRC 是 RDMA 传输相关的校验；
- FCS 是以太网帧校验序列。

需要特别注意：

> BTH 不是 ACK。BTH 是 RDMA 传输头的一部分，ACK 是具体的传输控制语义或确认报文。

### 第五步：交换机处理

交换机根据以太网地址进行转发，根据 IP 地址进行三层路由。

如果队列出现拥塞，交换机可能：

- 根据 ECN 配置给 IP 包打 CE 标记；
- 根据 PFC 配置发送暂停帧；
- 在严重拥塞时丢弃数据包。

### 第六步：接收方 RNIC 处理

接收方 RNIC 收到报文后，需要检查：

- 报文校验；
- 目标 QP 是否存在；
- 操作码是否合法；
- 包序号是否正确；
- 远端地址是否合法；
- rkey 是否有效；
- 目标内存区域是否具有对应权限。

检查通过后，接收方 RNIC 通过 DMA 将数据写入目标用户内存。

### 第七步：完成通知

对于可靠连接 RC，发送方 RNIC 会根据可靠传输状态处理确认、重传和完成。

发送方完成 WR 后，会在 CQ 中生成 CQE。应用轮询 CQ 后，就知道发送缓冲区可以重新使用。

如果操作是普通 RDMA Write，接收方可能不会得到 CQE；如果操作是 RDMA Write with Immediate，则接收方可以通过 RQ 和 CQ 得到通知。

### 十一、RC、UC 和 UD

RDMA 中常见的 QP 类型包括 RC、UC 和 UD。

| QP 类型 | 全称 | 通信关系 | 可靠性 | 常见能力 |
| --- | --- | --- | --- | --- |
| RC | Reliable Connection | 一对一 | 有确认、可重传 | Send/Receive、RDMA Read、RDMA Write、Atomic |
| UC | Unreliable Connection | 一对一 | 不保证可靠、不负责重传 | 常见为 Send/Receive 和 RDMA Write |
| UD | Unreliable Datagram | 一对多 | 不保证送达、不重传 | 主要用于消息发送 |

### 1. RC

RC 是最常见的可靠连接类型。

它通常是一个本地 QP 对应一个远端 QP，支持较完整的 RDMA 操作，并由 RNIC 处理确认、序号和重传。

代价是：

- 需要维护更多连接状态；
- 占用更多硬件资源；
- 大规模连接时资源管理更复杂。

### 2. UC

UC 仍然是一对一连接，但不提供完整的可靠传输能力。

它不负责重传，也不保证数据一定送达。由于需要维护的状态更少，资源消耗通常低于 RC。

### 3. UD

UD 更接近数据报模型。

一个 QP 可以向多个目标发送消息，不需要为每个目标维护完整的可靠连接状态。

它的资源开销较低，但不支持完整的远程内存读写语义，也不保证消息送达。

### 十二、为什么 RoCEv2 更适合数据中心

RoCEv2 的优势是把 RDMA 的高性能和以太网/IP 的基础设施结合起来。

但是，它的性能依赖网络环境。

在数据中心内部，运营者可以统一控制：

- 交换机型号；
- 网卡型号；
- 队列配置；
- PFC；
- ECN；
- 拥塞控制；
- 路由策略；
- 缓冲区大小；
- 链路带宽；
- 故障检测。

这就是为什么 RoCEv2 很适合大型数据中心、AI 集群和高性能存储系统。

但在普通公网或复杂广域网中，情况完全不同：

- 网络设备不由单一组织控制；
- 丢包不可避免；
- RTT 更大；
- 路由变化更频繁；
- NAT 和防火墙更复杂；
- 带宽和拥塞状态不稳定；
- 不同运营商设备之间的 QoS 语义不一致；
- 远程内存访问还涉及权限和安全边界。

因此，RoCEv2 并不是“技术上绝对不能跨广域网”，而是：

> 它对网络质量和端到端协同配置较敏感，不适合直接作为普通公网的通用通信方式。

### 十三、广域 RDMA 可能的发展方向

要让 RDMA 更适合广域网，需要解决的核心问题是：

> 在有损、高 RTT、路径不稳定的网络中，如何同时维持高吞吐和低延迟？

目前可以看到几类思路。

### 1. iWARP

iWARP 使用 TCP 承载 RDMA，可以利用 TCP 的可靠传输和拥塞控制。

它更容易适应有损 IP 网络，但 TCP 的处理复杂度、延迟和拥塞控制行为，也会限制极致性能。

### 2. 有损 RDMA

另一类思路是在 UDP 或类似承载方式上重新设计 RDMA 传输机制，包括：

- 更高效的选择性重传；
- 更适合大 RTT 的确认机制；
- 更精细的丢包恢复；
- 多路径传输；
- 更智能的拥塞控制；
- 对乱序和路径变化的适应。

这类方向仍然包含大量研究空间，不能简单等同于已经统一标准化并广泛部署的协议。

### 3. QUIC 与 RDMA 思想结合

QUIC 运行在 UDP 之上，支持用户态实现、可靠传输、多路复用和连接迁移。

因此，有研究尝试把 RDMA 的一些思想，例如：

- 用户态数据路径；
- 少拷贝；
- 低延迟；
- 多路复用；
- 更灵活的拥塞控制；

与 QUIC 结合。

不过，QUIC 的通用软件处理路径仍然存在，和 RNIC 直接硬件卸载相比，通常难以达到同样的极致性能。

### 十四、学习 RDMA 时最容易产生的几个误解

### 误解一：RDMA 就是完全不经过内核

更准确的说法是：

> RDMA 尽量绕过内核数据路径，但资源创建、内存注册、设备管理和驱动交互仍然需要内核参与。

### 误解二：RDMA 就是完全没有任何拷贝

更准确的说法是：

> RDMA 避免了许多用户态和内核态之间由 CPU 执行的数据拷贝，但不代表系统内部绝对不存在任何复制。

### 误解三：RoCEv2 因为使用 UDP，所以必须依靠 PFC 才能可靠

更准确的说法是：

> UDP 本身不提供可靠传输，但 RC 等 RDMA 传输类型可以由 RNIC 实现确认和重传。PFC 的主要作用是降低交换机队列溢出和丢包概率，减少重传，而不是直接替 UDP 提供可靠性。

### 误解四：RDMA 可以随意访问远端内存

更准确的说法是：

> 远程内存访问必须经过内存注册、权限配置、QP 状态检查、地址检查和 rkey 验证。RDMA 不是无条件地开放远程内存。

### 误解五：DCQCN 天然保证公平

更准确的说法是：

> DCQCN 通过 ECN、CNP 和发送速率调节改善拥塞和公平性，但最终效果依赖交换机配置、流量模式、拓扑和设备参数。

### 误解六：RDMA 一定比 TCP 快

RDMA 的优势主要体现在特定场景中，例如：

- 大规模数据传输；
- 高频小消息通信；
- 低延迟通信；
- 高吞吐存储；
- 分布式训练；
- 高性能计算；
- GPU 集群通信。

如果应用本身数据量很小、并发很低、网络不是瓶颈，RDMA 复杂的资源管理和部署成本未必值得。

### 十五、总结

RDMA 的核心价值可以总结为：

> 通过用户态数据路径、注册内存、DMA 直达、网卡硬件卸载和远程内存操作，减少传统网络通信中的软件开销，让 CPU 更少参与数据搬运。

它主要优化了：

- 系统调用；
- 用户态与内核态切换；
- 用户态与内核态之间的数据拷贝；
- 内核协议栈处理；
- 网络中断和调度；
- 远端 CPU 的收包和拷贝。

但 RDMA 并不是一种“自动变快”的魔法。

它把一部分复杂性从 CPU 和内核转移到了：

- RNIC；
- 交换机；
- 网络 QoS；
- 拥塞控制；
- 内存注册；
- QP 状态管理；
- 应用层同步；
- 运维和故障排查。

三种主要路线可以这样理解：

- **InfiniBand**：性能和确定性较强，但需要专用网络；
- **RoCEv2**：兼顾以太网基础设施和高性能，适合数据中心；
- **iWARP**：兼容普通 IP 网络，但性能和生态存在取舍。

RoCEv2 中几个重要机制的关系是：

```text
PFC：
逐跳暂停，防止队列溢出

ECN：
交换机标记拥塞，提前发出信号

CNP：
把拥塞反馈传回发送端

DCQCN：
根据反馈调整发送速率
```
