11 月 13 日，llama.cpp 和底层张量库 ggml 同时发布 v1.0.0。项目做了三年半，一直用 `b12xxx` 这种按提交数编号的 nightly 版本，这是第一次正式承诺 API 稳定。

只看「1.0」，这次发布像是改了个版本号。我更想讲 release notes 里排在前面的两项：**显存里的 MoE 专家缓存**和 **FP8 KV 缓存**。一张消费级显卡能不能跑动近百 GB 的 MoE 模型、能跑多快，主要看它们。

### 专家缓存：把显存当成 MoE 的 L2

### 以前：按层切

MoE 模型总参数大，每个 token 只激活一小部分专家。PR 里用的 Qwen3.8-Flash-Next Q4_0，模型文件 93.7 GiB，专家权重占 65.4 GiB，24 GB 的 4090 放不下。

llama.cpp 之前的办法是按层切：`-cmoe` 让所有专家留在内存由 CPU 算，`-ncmoe N` 让前 N 层的专家留在 CPU，`--fit` 自动算显存够放几层。这些都是**静态**划分，哪层在 GPU 上，跑起来就不变。可专家的调用并不均匀，按层整块搬，显存里难免混进很少用到的专家。

### 现在：按专家缓存

10 月 7 日合入的 PR #29887（移植自 Tether 的 qvac-fabric）换了思路：专家权重仍放在主机内存，GPU 划出一块显存当缓存，大小由 `--moe-cache-mib` 指定。

```text
token 进来 → 路由选出 k 个专家
   │
   ├─ 命中：专家已在显存缓存里 → 直接在 GPU 上算
   │
   └─ 未命中：从主机内存经 PCIe 上传到缓存 → 在 GPU 上算
                （缓存满了就按替换策略踢掉一个）
```

缓存只在小 batch（≤ 32 个 token）时启用，也就是逐字生成的解码阶段；prefill 这种大 batch 仍走原来的整块搬运路径。

PR 作者自测的数据（EPYC 7742 16 核、PCIe 4.0 x16，SPEED-Bench，温度 0，不开 MTP）：

| GPU | 配置 | 显存里的专家（整层 + 缓存） | 解码 t/s | 提速 | 命中率 |
| --- | --- | --- | --- | --- | --- |
| RTX 4090 | master --fit | 16.5 + 0 GB | 25.0 | 1.00x | - |
| RTX 4090 | -cmoe --moe-cache-mib 11000 | 0 + 10.7 GB | 40.7 | 1.62x | 77% |
| RTX 5090 | master --fit | 24.5 + 0 GB | 30.8 | 1.00x | - |
| RTX 5090 | -cmoe --moe-cache-mib 19000 | 0 + 18.6 GB | 67.8 | 2.20x | 89% |

4090 这两行最说明问题：缓存方案放进显存的专家（10.7 GB）比按层切（16.5 GB）还少，速度反而快了六成。缓存只占专家总量约六分之一，命中率就有 77%，被频繁调用的专家集中在一小部分。这些是贡献者在自己机器上测的，换模型、CPU 或 PCIe 代数都会变。

### 进 1.0 之前又改了三轮

**替换策略。** 最早是普通 LRU，10 月 19 日换成 50⁄50 的分段 LRU（SLRU），11 月 6 日又换成 ClassLRU（PR #31233）。ClassLRU 给每个专家记一个随时间衰减的使用分（CRF，兼顾最近用没用过和用得多不多）：

```text
new CRF = old CRF × 2^(-经过的 token 数 / 128) + 1
```

半衰期 128 个 token，按分数分进 8 个等级，等级越高越难被踢。作者给的命中率：SLRU 86.5%，ClassLRU 87.6%，能预知未来的理论最优（Belady）93.8%；热缓存下解码比 SLRU 快 6% 到 7%。他还提了一个还没实现的方向：拿 MTP 头当「预言机」，提前猜下一个 token 要用哪些专家。

**未命中时让 CPU 分担（PR #30966）。** 缓存满了以后，未命中的专家不一定要上传。`--moe-cache-cpu-share` 设一个 0 到 1 的比例，这部分直接由 CPU 用内存里的权重算，省掉 PCIe 传输。哪边划算取决于机器，所以同一个 PR 带了调参脚本 `scripts/moe-cache-tune.py`。作者的例子里，缓存 6464 MiB 时 share 从 0 调到 0.95，速度从 24.2 涨到 47.6 t/s；缓存加到 19392 MiB 后，0.95 反而比 0 慢。

**修掉 CPU 空等 GPU（PR #31888）。** Gemma 4 这类模型的路由器和专家读的不是同一个输入张量，原来的计算图顺序让 CPU 每层都要等 GPU。修好后 Gemma 4 26B-A4B 在 RTX 5090 上解码快了 7% 到 9%（作者自测）。

用法大致如下（参数名以 v1.0.0 的 server README 为准，本文未实测）：

```bash
# 专家全部留在内存，显存划 11000 MiB 当专家缓存
llama-server -m model.gguf -ngl 999 -fa on -cmoe --moe-cache-mib 11000

# 缓存满后，一半未命中交给 CPU 算
llama-server -m model.gguf -ngl 999 -fa on -cmoe \
  --moe-cache-mib 6000 --moe-cache-cpu-share 0.5

# 先跑调参脚本找本机最合适的组合
python3 scripts/moe-cache-tune.py -- build/bin/llama-server -m model.gguf -cmoe -t 8 -c 32768
```

多卡时缓存按 `--tensor-split` 的比例分到各卡；投机解码的草稿模型不走专家缓存（PR #31497）。

### FP8 KV 和外部 PLE 分片

**FP8 KV（PR #28392）。** `-ctk` / `-ctv` 新增 `f8_e4m3`，用 OCP 标准的 FP8 存 KV，每个元素 8 bit，是默认 f16 的一半。以前也能用 `q8_0` 压 KV，FP8 的好处是能对上模型本身用的格式。PR 举的例子是 NVIDIA 的 Mistral-Medium-3.5-128B-NVFP4，它的 FP8 KV 带非 1 的缩放系数，这次支持了可选的逐张量静态缩放，可以照原样加载。实现上没改 flash attention 算子，缩放放在计算图层面做。

**外部 PLE 分片（PR #31185）。** Gemma 4、Qwen3.8Next、GLM 5.3 Flash 带逐层嵌入（PLE，也叫 engram），这部分对不同量化版本是同一份。新增的 `--ple` / `--shard`（两者是别名）能把它放进单独的 GGUF，甚至放在另一块硬盘上，换量化版本时不用重复下载。

### 1.0 本身承诺了什么

**删旧 API**（PR #30565）：`llama_set_warmup`、`llama.h` 里 35 个标了 DEPRECATED 的函数、`defrag_thold` 和 `--defrag-thold` 全部删除。原来在 `llama-ext.h` 里的 NextN / 投机解码接口（18 个函数）提进 `llama.h`，`llama_set_embd_state_src` 改名为 `llama_set_ctx_state_src`。直接链接 libllama 的项目升级要改代码。

**定版本规则**：破坏 API / ABI 只在主版本号出现。另有一条容易漏看：llama.cpp 仓库里带着一份 ggml 副本，只有它和正式发布的 ggml 完全一致时才打正式版 tag，这样 Debian、Homebrew 这类动态链接系统 ggml 的发行版不会错配。`bNNNNN` nightly 照常发，追新功能的人用 nightly，要稳定的下游跟正式版。

**收紧 `llama-server` 默认安全设置**：

| 改动 | 以前 | 现在 |
| --- | --- | --- |
| 监听非回环地址时开工具 / MCP | 不带 API key 也能开 | 拒绝启动，需显式加 --allow-unauthenticated-tools |
| CORS 代理访问内网地址 | 允许 | 只允许公网地址，没有开关 |
| 媒体 URL 指向内网（如 NAS 上的图片） | 允许 | 需要 --media-allow-private-urls |
| --cors-origins | 不校验端口 | 严格校验端口，并防 DNS 重绑定 |
| HF_TOKEN | 不限主机 | 只发往 [http://huggingface.co](http://huggingface.co) 的主机 |
| 客户端断开或超时时的 MCP 工具调用 | 不主动取消 | 取消并通知 MCP 服务器 |

维护者 ngxson 在 PR #32113 里说得很直白：这些「本来不算漏洞」，但很多人直接在自己电脑上跑 server、不放沙箱，只好牺牲一点易用性。llama-server 现在自带 web UI、MCP 客户端和 JS 沙箱工具，越来越像一个本地 Agent 运行时，默认值偏安全是对的。

### 和其他方案对比

|  | llama.cpp 专家缓存 | 按层切（-ncmoe / --fit） | 全部进显存 | vLLM / SGLang 类服务端引擎 |
| --- | --- | --- | --- | --- |
| 显存怎么用 | 动态放热门专家 | 静态放整层 | 全放 | 全放，多卡并行 |
| 适合的硬件 | 单张消费卡 + 大内存 | 同左 | 显存够大 | 数据中心多卡 |
| 解码速度 | 取决于命中率和 PCIe | 受 CPU 算力限制 | 快 | 快，高并发吞吐好 |
| prefill | 不受益 | 不受益 | 快 | 快 |
| 调参 | 缓存大小 + CPU 比例，有脚本 | 层数，--fit 可自动 | 不需要 | 并行策略 |

专家缓存不是 llama.cpp 首创，PR 写明是从 qvac-fabric 移植的；KTransformers 这类 CPU/GPU 混合推理框架也早就在做「专家放 CPU、其余放 GPU」的分工。做进主线的意义在后端覆盖：CUDA、Metal、Vulkan、SYCL、ROCm 都能用，大量下游应用又直接链接 libllama。

### 适用场景和局限

适合：一张 16 到 32 GB 显存的卡加 64 到 128 GB 内存，想跑近百 GB 的 MoE 模型做单人对话或本地编程 Agent；已经在用 `-cmoe` / `-ncmoe` 的人，加上 `--moe-cache-mib` 再跑一遍调参脚本，值得一试；打包 llama.cpp 的发行版和桌面应用，可以改跟正式版。

要注意：

- **只加速解码。** 长提示词的 prefill 不走缓存，首 token 延迟不会变好。
- **命中率看负载。** 写代码和闲聊调用的专家分布可能不同，任务切换时缓存要重新热身。PR 里的数字都是热缓存测的。
- **PCIe 是硬约束。** 带宽低的插槽未命中代价更高，可能要调高 CPU 比例。
- **数字都是贡献者自测。** 还没看到独立第三方测评，Unite.AI 等报道也只是转述官方说明。
- **升级有破坏。** 用了被删函数或 `--defrag-thold` 的代码要改；以前局域网里不带 key 开 MCP、让模型读 NAS 图片的用法会报错，要加对应开关。

### 我的判断

专家缓存比 1.0 这个版本号更重要。Kimi K3.1、DeepSeek V4.1、Qwen3.8、Gemma 4 都是 MoE，本地玩家的瓶颈一直是显存装不下专家，按层切只是凑合。按专家缓存利用的是路由本身的局部性，显存从「装模型」变成「装热数据」，和 CPU 的 L2 缓存是一个思路。我估计其他本地推理工具也会往这走，下一步大概就是 PR 里提到的用 MTP 预测要哪些专家、提前上传。

还有个细节：这批 PR 的 AI 使用声明大多写着 YES。ClassLRU 作者说是配合 Claude 写的；SLRU 那个 PR 是作者让 GPT-6 Astra 在两张卡、两个模型上跑了一大轮替换策略实验，再由 Astra 写实现；FP8 KV 配合了 Codex。Gerganov 做 1.0 的 API 清理（PR #30565），AI 声明写的是 Mac Studio（M5 Ultra，256GB）上跑的 DeepSeek V4.1 Flash GGUF 版，harness 一栏是 `dsh:llama.cpp`，也就是**用 llama.cpp 本地跑的模型**。官方博客说会「审慎地」在开发中引入 LLM，同时坚持维护者要掌控架构、理解实现。一个本地推理引擎开始用跑在自己身上的模型维护自己，这比跑分更能说明本地模型现在能用到什么程度。

保留意见：1.0 的稳定承诺只覆盖 C API，不覆盖性能和命令行默认值；专家缓存的效果目前全部来自贡献者自测，等更多机器上的独立数据出来再下定论更稳。
