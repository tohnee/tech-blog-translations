## RAG 到底分为几类？

> 本文不采用“朴素 RAG、Advanced RAG、Modular RAG”的经典演进式分类，而是从知识组织、检索机制、流程控制、数据模态、记忆机制和可靠性等技术特征出发。

---

## 一、先说结论：RAG 没有固定的分类数量

很多文章会说 RAG 分为三类、五类或七类，但这些分类往往观察的是不同维度：

| 名称 | 关注的技术维度 |
| --- | --- |
| Hybrid RAG | 如何检索 |
| Graph RAG | 如何组织知识 |
| Agentic RAG | 如何控制流程 |
| Multimodal RAG | 数据是什么模态 |
| Memory RAG | 如何保存长期状态 |
| Self-RAG | 如何判断和纠错 |

所以，它们不是互斥关系。一个企业知识库系统完全可能同时具备：

```text
Hybrid RAG
+ Graph RAG
+ Agentic RAG
+ Memory RAG
+ Self-Reflective RAG

```

更准确的表述是：

> **RAG 是一个由多个技术维度组成的系统范式，而不是一组互斥的固定类别。**

本文将这些技术方向归纳为七类：

1. 检索增强型 RAG
2. 结构化知识型 RAG
3. 自适应与纠错型 RAG
4. Agentic RAG
5. 多模态 RAG
6. 记忆增强型 RAG
7. 可信与自反思型 RAG

这七类可以单独使用，也可以组合使用。

## 二、统一案例：企业制度知识库

为了避免每一类 RAG 都停留在概念层面，本文使用同一个企业知识库案例。

```text
data/
├── 报销制度.md
├── 审批制度.md
├── 员工手册.pdf
└── 项目预算.xlsx

```

> 示例文件名中的“员工手册.pdf”仅用于演示。实际项目中可以根据知识库目录替换文件。

用户可能提出以下问题：

```text
差旅费报销需要哪些材料？
发票编号 BX-2026-001 的审批人是谁？
张三负责的项目使用了哪些数据库？
如果项目超预算，需要经过什么审批流程？
我上次提交的报销为什么被驳回？

```

这些问题分别对应不同技术能力：

| 问题 | 更适合的技术 |
| --- | --- |
| 差旅费需要哪些材料 | 基础 RAG / Hybrid RAG |
| 查询发票编号 | Hybrid RAG |
| 查询项目和数据库关系 | Graph RAG |
| 判断超预算后的流程 | Agentic RAG |
| 查询上次个人报销记录 | Memory RAG |
| 资料来自扫描 PDF 或图片 | Multimodal RAG |
| 资料不足时不能编造 | Self-RAG / Verified RAG |

## 四、基础 RAG：所有复杂实现的起点

在讨论七类技术之前，先实现最小可用的 RAG。

### 4.1 准备文档

LangChain 使用 `Document` 表示一段带有元数据的文档内容。

```text
from langchain_core.documents import Document

documents = [
    Document(
        page_content=(
            "差旅费报销需要提供发票、出差申请单和行程记录。"
        ),
        metadata={
            "source": "报销制度.md",
            "section": "差旅费报销",
            "document_id": "expense-policy-v1",
        },
    ),
    Document(
        page_content=(
            "单次报销金额超过一万元时，需要部门负责人审批。"
        ),
        metadata={
            "source": "审批制度.md",
            "section": "金额审批",
            "document_id": "approval-policy-v1",
        },
    ),
]

```

### 4.2 文档切分与向量索引

```text
from langchain_core.vectorstores import InMemoryVectorStore
from langchain_openai import OpenAIEmbeddings
from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,
    chunk_overlap=80,
)

splits = splitter.split_documents(documents)

embedding_kwargs = {
    "model": EMBEDDING_MODEL,
}
if OPENAI_BASE_URL:
    embedding_kwargs["base_url"] = OPENAI_BASE_URL

embeddings = OpenAIEmbeddings(**embedding_kwargs)

vector_store = InMemoryVectorStore(
    embedding=embeddings
)
vector_store.add_documents(splits)

retriever = vector_store.as_retriever(
    search_kwargs={"k": 3}
)

```

生产环境可以把 `InMemoryVectorStore` 替换成 Chroma、Milvus、Qdrant 或 PGVector，但上层 Retriever 的使用方式可以保持一致。

### 4.3 生成答案

```text
from langchain_core.prompts import ChatPromptTemplate
from langchain_openai import ChatOpenAI

model_kwargs = {
    "model": CHAT_MODEL,
    "temperature": 0,
}
if OPENAI_BASE_URL:
    model_kwargs["base_url"] = OPENAI_BASE_URL

model = ChatOpenAI(**model_kwargs)

prompt = ChatPromptTemplate.from_messages([
    (
        "system",
        "你是企业制度问答助手。"
        "只能根据给定资料回答问题。"
        "资料中没有答案时，必须明确说明。",
    ),
    (
        "human",
        "资料：\n{context}\n\n问题：{question}",
    ),
])

def format_documents(docs):
    return "\n\n".join(
        (
            f"[来源：{doc.metadata.get('source', '未知')}]\n"
            f"{doc.page_content}"
        )
        for doc in docs
    )

def answer_question(question: str) -> str:
    retrieved_docs = retriever.invoke(question)

    messages = prompt.invoke({
        "context": format_documents(retrieved_docs),
        "question": question,
    })

    response = model.invoke(messages)
    return response.content

print(answer_question("差旅费报销需要哪些材料？"))

```

基础流程可以概括为：

```text
问题
 ↓
Retriever.invoke()
 ↓
Document 列表
 ↓
Prompt
 ↓
ChatModel.invoke()

```

后面的所有技术方向，都是在这个流程中增加新的模块。

## 五、检索增强型 RAG：Hybrid + Rerank

### 5.1 为什么需要混合检索

纯向量检索擅长语义匹配，但对于以下内容可能不够准确：

- 发票编号；
- 产品型号；
- 文件编号；
- 代码符号；
- 专有名词；
- 精确关键词。

例如：

```text
发票编号 BX-2026-001 的审批人是谁？

```

这类问题既需要理解“审批人”的语义，又需要准确匹配 `BX-2026-001` 。

### 5.2 BM25 与向量检索

LangChain Community 提供了 `BM25Retriever` 。它可以和向量 Retriever 并行使用。

```text
from langchain_community.retrievers import BM25Retriever

bm25_retriever = BM25Retriever.from_documents(
    splits,
    k=5,
)

vector_retriever = vector_store.as_retriever(
    search_kwargs={"k": 5}
)

```

中文 BM25 的效果和分词质量有关。生产环境中可以在入库前使用中文分词器，或者使用支持中文分析器的搜索引擎。

### 5.3 使用 RRF 合并结果

RRF，也就是 Reciprocal Rank Fusion，可以把多个检索器的排名融合起来。

```text
def document_key(document):
    return (
        document.metadata.get("document_id"),
        document.metadata.get("source"),
        document.page_content,
    )

def reciprocal_rank_fusion(result_lists, top_k=5):
    scores = {}
    documents = {}

    for result_list in result_lists:
        for rank, document in enumerate(result_list, start=1):
            key = document_key(document)

            scores[key] = scores.get(key, 0.0)
            scores[key] += 1.0 / (60 + rank)
            documents[key] = document

    ranked_keys = sorted(
        scores,
        key=scores.get,
        reverse=True,
    )

    return [documents[key] for key in ranked_keys[:top_k]]

def hybrid_retrieve(question: str, top_k=5):
    vector_docs = vector_retriever.invoke(question)
    keyword_docs = bm25_retriever.invoke(question)

    return reciprocal_rank_fusion(
        [vector_docs, keyword_docs],
        top_k=top_k,
    )

```

### 5.4 增加重排序

混合检索通常用于扩大候选集，然后由重排序模型重新判断相关性。

```text
def retrieve_candidates(question: str):
    vector_docs = vector_store.similarity_search(
        question,
        k=20,
    )
    keyword_docs = bm25_retriever.invoke(question)

    return reciprocal_rank_fusion(
        [vector_docs, keyword_docs],
        top_k=20,
    )

def rerank(question, documents, reranker, top_k=5):
    ranked_documents = reranker.rank(
        query=question,
        documents=documents,
    )

    return ranked_documents[:top_k]

```

`reranker` 是项目中的重排序模型适配器。不同供应商的输入输出格式不同，因此不在文章中伪造一个统一的第三方接口；核心流程是“先召回，再重排”。

### 5.5 适用场景

检索增强型 RAG 适合：

- 企业制度问答；
- 代码搜索；
- 商品检索；
- 订单号查询；
- 产品型号查询；
- 法律条款检索。

它通常是企业 RAG 最先应该实现的增强能力。

## 六、结构化知识型 RAG：Graph RAG 与 SQL RAG

### 6.1 为什么需要结构化知识

普通向量检索寻找的是“相似内容”，但下面的问题本质上是关系查询：

```text
张三负责的项目使用了哪些数据库？

```

这个问题需要经过多跳关系：

```text
张三
  └── 负责 → 项目 A
                └── 使用 → PostgreSQL

```

### 6.2 使用 LangChain 抽取实体和关系

可以使用 `with_structured_output()` 将模型输出约束为 Pydantic 结构。

```text
from pydantic import BaseModel, Field

class Relation(BaseModel):
    source: str = Field(description="关系的起点实体")
    relation: str = Field(description="关系类型")
    target: str = Field(description="关系的终点实体")

class RelationExtraction(BaseModel):
    relations: list[Relation]

extractor = model.with_structured_output(
    RelationExtraction
)

def extract_relations(text: str) -> list[Relation]:
    result = extractor.invoke([
        {
            "role": "system",
            "content": (
                "从文本中抽取实体关系。"
                "没有明确关系时返回空列表。"
            ),
        },
        {
            "role": "user",
            "content": text,
        },
    ])

    return result.relations

```

### 6.3 构建简单图结构

为了方便理解，先使用 Python 字典保存图结构。生产环境可以替换成 Neo4j 等图数据库。

```text
from collections import defaultdict

graph = defaultdict(list)

def add_relations(relations: list[Relation]):
    for relation in relations:
        graph[relation.source].append(
            (relation.relation, relation.target)
        )

relations = extract_relations(
    "张三负责项目 A，项目 A 使用 PostgreSQL，属于支付系统。"
)
add_relations(relations)

```

### 6.4 图遍历

```text
def graph_search(entity: str, max_depth=2):
    results = []
    current_nodes = [entity]
    visited = set()

    for _ in range(max_depth):
        next_nodes = []

        for node in current_nodes:
            if node in visited:
                continue

            visited.add(node)

            for relation, target in graph.get(node, []):
                results.append({
                    "source": node,
                    "relation": relation,
                    "target": target,
                })
                next_nodes.append(target)

        current_nodes = next_nodes

    return results

facts = graph_search("张三")

graph_context = "\n".join(
    f"{item['source']} {item['relation']} {item['target']}"
    for item in facts
)

answer = model.invoke([
    {
        "role": "system",
        "content": "只能根据给定事实回答问题。",
    },
    {
        "role": "user",
        "content": (
            f"事实：\n{graph_context}\n\n"
            "问题：张三负责的项目使用了什么数据库？"
        ),
    },
])

print(answer.content)

```

### 6.5 接入 Neo4j 的边界

如果使用 Neo4j，建议将“图数据库访问”单独封装成工具或 Repository，而不是在 Prompt 中拼接 Cypher：

```text
class ProjectGraphRepository:
    def find_related_facts(self, entity: str) -> list[dict]:
        """执行参数化查询并返回结构化事实。"""
        raise NotImplementedError

```

真实实现中需要：

- 使用参数化查询；
- 限制可访问的标签和关系；
- 限制遍历深度；
- 限制返回数量；
- 记录查询日志；
- 对图数据库连接设置超时。

### 6.6 SQL RAG

如果知识存储在关系型数据库中，SQL RAG 通常比“把所有表转成文本”更可靠：

```text
自然语言问题
   ↓
生成 SQL
   ↓
执行 SQL
   ↓
把查询结果交给模型解释

```

核心代码可以设计成：

```text
def sql_rag(question, schema, database, sql_model):
    sql_response = sql_model.invoke([
        {
            "role": "system",
            "content": (
                "根据数据库结构生成只读 SQL。"
                "禁止执行 INSERT、UPDATE、DELETE。"
            ),
        },
        {
            "role": "user",
            "content": (
                f"数据库结构：\n{schema}\n\n"
                f"问题：{question}"
            ),
        },
    ])

    rows = database.execute_readonly(
        sql_response.content
    )
    return rows

```

实际项目还必须增加 SQL 只读限制、表字段白名单、查询超时、返回行数限制和执行前审核。

## 七、自适应与纠错型 RAG

### 7.1 固定检索的问题

基础 RAG 通常是：

```text
问题 → 检索一次 → 生成答案

```

但实际可能出现：

- 问题本身不需要检索；
- 第一次召回的文档不相关；
- 查询表达过于口语化；
- 需要改写查询后重新检索；
- 需要扩大检索范围。

### 7.2 使用结构化输出做相关性判断

```text
class RelevanceGrade(BaseModel):
    relevant: bool
    score: float = Field(ge=0.0, le=1.0)
    reason: str

grader = model.with_structured_output(
    RelevanceGrade
)

def grade_documents(question, documents):
    context = format_documents(documents)

    return grader.invoke([
        {
            "role": "system",
            "content": (
                "判断资料是否能够回答问题。"
                "score 必须在 0 到 1 之间。"
            ),
        },
        {
            "role": "user",
            "content": (
                f"问题：{question}\n\n"
                f"资料：{context}"
            ),
        },
    ])

```

### 7.3 查询改写与重试

```text
def rewrite_query(question: str) -> str:
    response = model.invoke([
        {
            "role": "system",
            "content": (
                "把用户问题改写成适合企业知识库检索的查询。"
                "保留专有名词、编号和关键约束。"
            ),
        },
        {
            "role": "user",
            "content": question,
        },
    ])

    return response.content.strip()

def adaptive_retrieve(question: str, max_retry=2):
    current_query = question

    for _ in range(max_retry + 1):
        documents = hybrid_retrieve(current_query)
        grade = grade_documents(current_query, documents)

        if grade.relevant and grade.score >= 0.7:
            return documents

        current_query = rewrite_query(current_query)

    return []

```

完整流程是：

```text
第一次检索
   ↓
相关性评分
   ├── 相关 → 生成答案
   └── 不相关 → 改写问题 → 重新检索

```

需要限制最大重试次数，否则系统可能产生无限循环，导致延迟和调用费用不可控。

## 八、Agentic RAG：让 Agent 动态选择工具

### 8.1 普通 RAG 与 Agentic RAG 的区别

普通 RAG：

```text
问题 → 固定 Retriever → 生成答案

```

Agentic RAG：

```text
问题 → Agent 规划 → 动态选择工具
      → 多步执行 → 汇总证据 → 生成答案

```

例如：

```text
张三负责的项目今年预算是多少？
如果超预算，需要经过什么审批流程？

```

Agent 可能拆成：

### 8.2 定义检索工具

LangChain 1.0.x 使用 `@tool` 定义工具，并使用 `create_agent` 创建 Agent。

```text
from langchain.agents import create_agent
from langchain.tools import tool

@tool

def search_policy(query: str) -> str:
    """搜索企业制度文档。"""
    documents = hybrid_retrieve(query, top_k=5)
    return format_documents(documents)

@tool

def search_project(owner: str) -> str:
    """查询员工负责的项目。"""
    project_documents = project_retriever.invoke(owner)
    return format_documents(project_documents)

@tool

def search_budget(project_name: str) -> str:
    """查询项目预算信息。"""
    budget_documents = budget_retriever.invoke(project_name)
    return format_documents(budget_documents)

```

上面 `project_retriever` 和 `budget_retriever` 需要按照项目数据源初始化。它们不是 LangChain 内置全局变量，应在实际项目中显式创建并注入。

### 8.3 创建 Agent

```text
agent = create_agent(
    model=model,
    tools=[
        search_policy,
        search_project,
        search_budget,
    ],
    system_prompt=(
        "你是企业预算和制度助手。"
        "遇到复杂问题时，先调用工具获取证据。"
        "不得编造工具没有返回的信息。"
    ),
)

result = agent.invoke({
    "messages": [
        {
            "role": "user",
            "content": (
                "张三负责的项目今年预算是多少？"
                "如果超预算，需要经过什么审批流程？"
            ),
        }
    ]
})

final_message = result["messages"][-1]
print(final_message.content)

```

### 8.4 Agentic RAG 的工程边界

Agent 并不是越自由越好，需要设置：

- 最大工具调用次数；
- 工具参数校验；
- 只读和写操作分离；
- 单个工具超时；
- 失败重试次数；
- 敏感工具人工确认；
- 最终答案必须引用工具结果。

对于简单的“制度内容是什么”问题，直接使用 Hybrid RAG 通常比 Agent 更简单、更快、更稳定。

## 九、多模态 RAG：处理图片、表格和扫描文档

### 9.1 为什么文本切分不够

企业知识并不只存在于纯文本中，还可能存在于：

- PDF 表格；
- 产品图片；
- 设备故障照片；
- 流程图；
- 扫描件；
- 音频和视频；
- Excel 文件。

如果只抽取 PDF 中的文本，表格布局、图片和流程图信息可能会丢失。

### 9.2 先将多模态内容结构化

可以统一表示为带模态字段的 `Document` ：

```text
from langchain_core.documents import Document

multimodal_documents = [
    Document(
        page_content="设备出现红灯时，应检查电源模块。",
        metadata={
            "source": "设备手册.pdf",
            "page": 3,
            "modality": "text",
        },
    ),
    Document(
        page_content="设备红灯故障示意图：红色指示灯持续闪烁。",
        metadata={
            "source": "设备手册.pdf",
            "page": 4,
            "modality": "image",
            "image_path": "images/error-light.png",
        },
    ),
]

```

图片、表格和扫描件通常需要在入库阶段完成：

```text
原始 PDF
   ↓
页面解析
   ├── 文本抽取
   ├── 表格抽取
   ├── 图片抽取
   └── OCR
        ↓
统一 Document + metadata

```

### 9.3 使用多模态消息生成答案

如果模型支持图片输入，可以通过 LangChain 消息内容传入图片和文本：

```text
from langchain_core.messages import HumanMessage

def answer_with_image(image_url: str, question: str):
    message = HumanMessage(
        content=[
            {
                "type": "text",
                "text": question,
            },
            {
                "type": "image_url",
                "image_url": {
                    "url": image_url,
                },
            },
        ]
    )

    response = model.invoke([message])
    return response.content

```

真正的多模态 RAG 还需要解决：

1. 图片如何编码为向量；
2. 文本和图片是否位于同一个向量空间；
3. 图片和原始页面如何关联；
4. 表格行列关系如何保留；
5. 最终答案如何引用具体页码。

多模态 RAG 不只是“把图片传给模型”，还包括多模态数据的解析、索引、检索和来源追踪。

## 十、Memory RAG：把用户历史作为可检索知识

### 10.1 普通对话的局限

普通 RAG 检索的是企业知识库，但不会自动记住：

- 用户身份；
- 用户偏好；
- 用户历史任务；
- 用户已经确认过的信息；
- 多轮任务的长期状态。

### 10.2 写入长期记忆

可以使用带元数据的 `Document` 保存记忆：

```text
from langchain_core.documents import Document

def build_memory(user_id: str, content: str):
    return Document(
        page_content=content,
        metadata={
            "user_id": user_id,
            "memory_type": "long_term",
        },
    )

memory_documents = [
    build_memory(
        user_id="user-001",
        content="用户负责支付项目，常用 Python 开发。",
    )
]

memory_store = InMemoryVectorStore(
    embedding=embeddings
)
memory_store.add_documents(memory_documents)

```

### 10.3 检索用户记忆

具体向量数据库的过滤参数可能不同。下面展示通用的“先召回、再按用户过滤”方式：

```text
def retrieve_memory(user_id: str, question: str, k=10):
    candidates = memory_store.similarity_search(
        question,
        k=k,
    )

    return [
        document
        for document in candidates
        if document.metadata.get("user_id") == user_id
    ][:3]

```

生产环境应优先使用数据库原生 metadata filter，避免先召回其他用户的数据再在应用层过滤。

### 10.4 组合知识库与用户记忆

```text
def memory_rag(user_id: str, question: str) -> str:
    memories = retrieve_memory(user_id, question)
    documents = hybrid_retrieve(question, top_k=5)

    context = format_documents(
        memories + documents
    )

    messages = prompt.invoke({
        "context": context,
        "question": question,
    })

    response = model.invoke(messages)
    return response.content

```

### 10.5 记忆写入不能无条件进行

不能把所有对话直接写入长期记忆，否则会造成：

- 错误信息长期污染；
- 过期信息持续影响回答；
- 敏感信息被不必要地保存；
- 记忆库规模不断膨胀。

可以先使用结构化判断决定是否写入：

```text
class MemoryDecision(BaseModel):
    should_save: bool
    memory_type: str
    content: str

memory_classifier = model.with_structured_output(
    MemoryDecision
)

```

生产系统还应该增加：

- 用户查看和删除记忆的能力；
- 敏感信息脱敏；
- 记忆过期时间；
- 用户隔离；
- 记忆来源追踪。

## 十一、Self-RAG：让答案能够被证据支持

### 11.1 RAG 不等于不会产生幻觉

即使召回了正确文档，模型仍可能：

- 混淆不同实体；
- 把推测写成事实；
- 添加资料中不存在的金额；
- 引用错误来源；
- 忽略资料中的限制条件。

因此，最终答案应该经过事实核验。

### 11.2 定义事实核验结果

```text
class ClaimVerification(BaseModel):
    supported: bool
    reason: str

verifier = model.with_structured_output(
    ClaimVerification
)

```

### 11.3 拆分并核验答案

```text
def split_claims(answer: str) -> list[str]:
    normalized = answer.replace("。", "。\n")
    return [
        claim.strip()
        for claim in normalized.splitlines()
        if claim.strip()
    ]

def verify_answer(answer: str, documents) -> str:
    evidence = format_documents(documents)
    verified_claims = []

    for claim in split_claims(answer):
        result = verifier.invoke([
            {
                "role": "system",
                "content": (
                    "判断答案中的事实是否被资料直接支持。"
                    "资料没有明确说明时，返回 supported=false。"
                ),
            },
            {
                "role": "user",
                "content": (
                    f"事实：{claim}\n\n"
                    f"资料：{evidence}"
                ),
            },
        ])

        if result.supported:
            verified_claims.append(claim)

    return "\n".join(verified_claims)

```

### 11.4 组合成 Verified RAG

```text
def verified_rag(question: str) -> str:
    documents = adaptive_retrieve(question)

    if not documents:
        return "当前知识库中没有找到足够的资料。"

    messages = prompt.invoke({
        "context": format_documents(documents),
        "question": question,
    })

    draft_response = model.invoke(messages)

    return verify_answer(
        draft_response.content,
        documents,
    )

```

例如，模型初始答案是：

```text
张三负责支付项目，该项目预算为 500 万元。

```

但资料只支持：

```text
张三负责支付项目。

```

那么核验后的答案应该删除没有依据的预算金额，而不是为了让答案“完整”继续保留它。

## 十二、如何把这些技术组合起来

一个企业 RAG 可以设计成如下路由结构：

```text
用户问题
   ↓
问题分类器
   ├── 简单事实问题 → Hybrid RAG
   ├── 关系查询问题 → Graph RAG / SQL RAG
   ├── 复杂多步问题 → Agentic RAG
   ├── 图片和表格问题 → Multimodal RAG
   └── 个性化问题 → Memory RAG
              ↓
         结果重排序
              ↓
         答案生成
              ↓
         事实核验

```

可以使用结构化输出实现路由判断：

```text
class RouteDecision(BaseModel):
    route: str
    reason: str

router = model.with_structured_output(RouteDecision)

def route_question(question: str) -> RouteDecision:
    return router.invoke([
        {
            "role": "system",
            "content": (
                "将问题分类为 simple、relationship、complex、"
                "multimodal 或 personalized。"
            ),
        },
        {
            "role": "user",
            "content": question,
        },
    ])

```

路由器只是教学示例。实际项目中还需要：

- 未知类别回退到普通 RAG；
- 记录路由结果；
- 评估误路由率；
- 为高风险问题设置人工兜底；
- 限制 Agent 和外部工具的权限。

## 十三、知识库数据处理同样重要

很多 RAG 项目的问题并不来自模型，而是来自文档解析和切分。

企业知识库经常包含：

```text
Markdown
TXT
PDF
DOCX
HTML
Excel
图片
扫描件

```

因此，数据处理阶段至少要考虑：

- 不同格式使用不同解析器；
- PDF 保留页码信息；
- DOCX 保留标题、列表和表格；
- Markdown 不要破坏原有层级；
- 表格不能简单拼接成无结构文本；
- 图片和原始页面建立关联；
- 每个 Chunk 保存来源信息。

建议每个 Chunk 至少包含以下元数据：

```text
chunk.metadata = {
    "source": "报销制度.pdf",
    "page": 3,
    "section": "第三章 差旅费",
    "document_id": "policy-001",
    "chunk_id": "policy-001-003",
    "version": "v2",
}

```

这些元数据可以支持：

- 答案引用；
- 原文定位；
- 单文档删除；
- 文档版本更新；
- 旧知识清理；
- 结果过滤；
- 权限隔离。

RAG 的完整数据链路应该是：

```text
源文档
  ↓
解析
  ↓
清洗
  ↓
切分
  ↓
Embedding
  ↓
向量索引 / 关键词索引 / 图索引
  ↓
检索与生成

```

只要其中任何一层没有同步更新，就可能出现“后台显示更新成功，但用户仍然得到旧答案”。

## 十四、如何选择技术方向

| 问题特征 | 优先选择 |
| --- | --- |
| 关键词、编号、术语很多 | Hybrid RAG |
| 需要实体关系和多跳查询 | Graph RAG |
| 查询质量不稳定 | Adaptive / Corrective RAG |
| 需要调用多个系统 | Agentic RAG |
| 包含图片、表格和扫描件 | Multimodal RAG |
| 需要记住用户历史 | Memory RAG |
| 对准确性和引用有要求 | Self-RAG / Verified RAG |
| 只是简单文档问答 | 向量检索 + 重排序 |

不要一开始就把所有能力叠加起来。

更合理的建设顺序是：

```text
第一步：正确解析和切分文档
第二步：建立基础向量检索
第三步：加入 BM25 混合检索
第四步：加入重排序
第五步：加入引用和来源追踪
第六步：加入相关性判断和失败重试
第七步：根据业务需要增加图谱、Agent 或多模态能力

```

## 十五、如何评估 RAG 系统

RAG 不能只看最终答案是否“听起来不错”，至少要分别评估检索、上下文和生成三个环节。

### 15.1 检索质量

关注：

- 是否召回正确文档；
- 正确文档排在第几位；
- 是否包含足够证据；
- 是否混入大量无关内容。

常用指标包括：

```text
Recall@K
Precision@K
MRR
NDCG

```

### 15.2 上下文质量

关注：

- 上下文是否覆盖问题；
- 是否存在重复片段；
- 是否存在互相冲突的信息；
- 上下文是否过长；
- 文档来源是否可信。

### 15.3 生成质量

关注：

- 答案是否正确；
- 是否忠于检索资料；
- 是否存在幻觉；
- 是否引用正确；
- 资料不足时能否拒答；
- 是否完整回答问题。

一个测试样本可以表示为：

```text
evaluation_case = {
    "question": "差旅费报销需要哪些材料？",
    "expected_answer": [
        "发票",
        "出差申请单",
        "行程记录",
    ],
    "expected_sources": [
        "报销制度.md",
    ],
}

```

最终可以统计：

```text
答案正确率
检索命中率
来源准确率
无依据内容比例
拒答准确率
平均响应延迟
平均 Token 消耗

```

## 十六、总结

截至 2026 年 10 月 8 日，RAG 没有一个所有人都认可的固定分类数量。

如果按照技术特征，可以归纳为：

但这七类不是互斥分类，而是可以组合的技术维度：

```text
Hybrid RAG
    负责提高召回质量

Graph RAG
    负责处理实体关系和全局信息

Agentic RAG
    负责多步规划和工具调用

Memory RAG
    负责长期状态和个性化

Multimodal RAG
    负责图片、表格和复杂文档

Corrective / Self-RAG
    负责判断、核验和纠错

```

因此，理解 RAG 的关键不是背诵几个名词，而是回答下面几个工程问题：

```text
知识以什么形式存在？
应该使用什么方式检索？
是否需要多步推理？
是否需要调用外部工具？
是否需要记住用户状态？
答案是否需要事实核验？

```

当这些问题被明确之后，RAG 就不再是一个模糊的概念，而会变成一组可以设计、实现、测试和迭代的工程组件。
