在 2024 年前后，我们团队按照教程搭了一套标准的多智能体：Researcher、Writer、Editor、Manager。每个智能体都有职位、性格和协作指令。演示时很好看，几个智能体会“讨论”，草稿在彼此之间来回传递。但是到了生产环境，报告质量也算过得去，不过成本是原来单智能体的 12 倍，耗时是 4 倍；真正做质量评测时这套团队系统还比一个 Prompt 写得好、工具配置合理并带压缩循环的单智能体低了 2 分。

![](https://pic1.zhimg.com/v2-378c555aba2945dcb4b9dc7ff67272a6_r.jpg)

所以这里的问题不在于“多智能体不起作用”，而是在一个根本不需要团队的任务上交了团队税。把他们带到这一步的是拟人化思路：把智能体看成同事。有职位、有分工，看起来很自然，于是底层那个工程问题反而没人继续灌注——工作拆进多个上下文窗口，究竟能换来什么？因为有时候什么也换不来。

这一篇要把多智能体将清楚：有哪些模式，真正起作用的机制是什么，成本为什么会迅速上升，以及工程上应该怎样做选择。

### 1、多智能体真正带来的是什么

去掉拟人化包装，“多智能体系统”可以收缩成一个很简单的定义：多个 LLM 循环，各自拥用独立的上下文窗口，围绕同一个目标协同工作。

所以所谓的“专家智能体更聪明”有时并不成立。一个名叫 Security Reviewer 的智能体，底层还是同一个模型，只是 Prompt 换了。职位名称不会凭空增加专业知识。Prompt 层面的专业化确实有作用，但幅度有限；很多时候，在一个智能体里直接要求它从指定视角审视问题，已经能得到大部分收益。

真正拉开差异的是上下文隔离（context isolation）。子智能体拿到一个干净的上下文窗口，可以把整个窗口都花在单个子任务上：读完整个子系统，消化一份 400 页文档，或者完成一次包含 60 次工具调用的调查。完成后只返回压缩过的摘要。父智能体保存结论，不背负完整工作历史。10 个子智能体合起来可以“阅读”200 万 Token，而编排器（orchestrator）的窗口仍然很轻。

这套表述听起来像概念辨析，却给出了一条很实用的判断线：任务的工作集（working set）超过一个上下文窗口时多智能体才开始有意义；能能装进一个窗口时大多数情况不值得拆。比如：跨大量来源做研究、从多个维度审查、跨很多文件做迁移，都会迅速把工作集撑大，属于典型的广度型任务。一个难解的 bug、一份文档、一条长推理链，更偏向深度型任务，通常应该留在一个窗口里。

### 2、六种模式

生产环境里常见的多智能体系统基本可以归到六种形态。把它们当作有适用条件的工程工具，会比按“团队角色”想象它们更可靠。

![](https://pic4.zhimg.com/v2-00069698a45ca6a85f1ec58fed10a851_r.jpg)

覆盖生产级多智能体系统的六种拓扑结构——每一种都有真正适合它的工作。

编排器—工作智能体（Orchestrator-workers）是主力模式，也是大多数人谈“多智能体”时更应该指的东西。主智能体先拆目标，再写任务简报，生成工作智能体；很多时候这些工作智能体会并行执行，并按工具设计文章里的原则拿到更窄的工具集，最后由主智能体综合它们的摘要。它最适合研究扫描、多维代码审查、审计这类广度任务。不过难点主要有两个：任务简报写得够不够好（见第 5 部分），以及工作量分配（effort scaling）是否合理。工作智能体必须知道一个子任务值得投入多少精力，否则简单查询也可能被做成 50 次搜索。Anthropic 早期版本就出现过这种情况：“东京人口是多少”这样的问题，也会生成 50 个子智能体。

![](https://picx.zhimg.com/v2-a6e4f40317321d16a47ef375e91585a1_r.jpg)

Pipeline 把多个智能体串成顺序流程，每一段都处理上一段的输出：草稿 → 批评 → 修订，抽取 → 规范化 → 验证。某些阶段确实需要不同上下文、不同工具，或者需要一份“洁净室式”的第二意见时，这种结构有价值。比如批评智能体完全没看过作者的推理过程，只根据成品文本判断质量，得到的是刻意保留的新鲜视角。反过来，如果阶段只是为了让流程看起来更整齐，拆分就没有必要。每次交接都会损失信息并增加延迟；三个阶段如果实际上共享同一批信息，更合适的做法是让一个智能体按三个阶段完成。

Router / handoff 更像分诊系统。入口智能体先判断任务类型，再把完整任务交给某个专业智能体，比如账单、退款或技术支持；每个专业智能体都有自己的工具和策略。OpenAI Agents SDK 原生支持 handoff，这也成了面向客户系统里的常见结构。这里的核心收益往往不是上下文隔离，而是策略隔离。退款智能体没有处理其他事务的工具权限，边界直接落在工具层面。表面看像组织架构，实际是安全边界。

辩论 / 专家组 + 裁判（Debate / panel + judge）的做法是让 N 个智能体独立解同一个问题，再交给一个裁判比较并综合。一个答案要付 N 份推理成本，价格天然不低；裁判本身还会带着评测文章里谈过的各种偏差，需要单独校准。它更适合高风险、又不容易直接验证的问题。当独立答案之间的一致性本身具有证据价值，比如安全审查、架构决策，或者一次自信错误的代价高于 4 倍 Token 成本，额外支出才比较容易成立。

黑板 / 共享工作区（Blackboard / shared workspace）把协调媒介从消息换成制品（artifact）：共享文件系统、任务列表、所有智能体共同读取和更新的计划文档。它可以看作上下文工程里“文件即记忆”思路的多写入者版本，也很接近优秀 coding-agent 集群的真实工作方式。少聊，把世界状态写到磁盘上，需要的人自己去读。只要协作时间足够长，而且制品本身就是协作中心，这种结构就很合适。代价是必须管理写冲突，比如隔离 git worktree、明确文件所有权；两个智能体编辑同一个文件，早晚会变成一次真实的冲突。

层级式（Hierarchy）允许编排器继续生成编排器。规模足够大时偶尔有必要，不过更常见的结果，是协调问题开始递归。真要采用这种结构，深度上限和预算保护应该提前放进系统里。失控式生成子智能体，是它最有代表性的事故类型。

### 3、成本问题

多智能体会把 Token 消耗成倍放大，而且倍数通常比直觉更高。Anthropic 公布过研究系统的数据：普通智能体大约消耗聊天交互 4 倍的 Token，多智能体系统大约是 15 倍。成本不是来自某一个环节。每个工作智能体都会带一份 system prompt 和工具定义；父智能体已经知道的上下文，工作智能体可能还要重新发现；摘要写完要被读取，之后还可能再次被摘要；编排器管理整个过程也持续消耗 Token。

![](https://pic4.zhimg.com/v2-c15c39d9685e87cb7aa196fad574111b_r.jpg)

这笔成本会直接改变三件事。15 倍的开销把价值门槛抬得很高，结果本身至少要值得这 15 倍投入，所以研究、审计、迁移这类高价值广度任务更适合，日常小任务很难算得过账。并行也不能把延迟全部抹掉：扇出只在综合之前减少墙钟时间，Pipeline 如果各阶段本来就不是瓶颈，只会比单智能体更慢。错误还会跨智能体累积，一个工作智能体写出细微但错误的摘要，编排器读进去以后很可能把它当成事实；可观测性文章里的追踪树就是用来找这种问题的，按分支汇总成本则能发现某个工作智能体是不是悄悄吃掉了一半预算。

经济上也有一处可利用的空间：工作智能体可以按任务路由到不同模型。格式化、抽取这类机械工作交给更小的模型，编排器继续留在前沿模型上，往往就能把 15 倍压到接近 6 倍。

### 4、什么时候不要用多智能体

工作集能放进一个窗口。上下文隔离在这里没有收益，团队税只剩下展示效果。大多数任务都属于这一类，包括很多看起来规模不小的任务。

工作具有顺序依赖。深度调试、单文档写作、高度依赖思维链的分析，都要求第 N 步能看到第 1 步到第 N−1 步的全部信息。拆成多个上下文窗口，恰好会破坏这条连续链。深度型任务更需要一个窗口。

智能体会共享可变状态。如果拆完以后两个工作智能体还要碰同一批文件或记录，那就不是可并行单元，而是带着 Token 账单的合并冲突。要么重新拆，要么回到单智能体。

这这就需要统一判断标准。四个智能体拼出来的文档，常常就是四种写法拼在一起。后面再做一轮综合可以补救，但相当于再付一份第二稿的 Token，去修复拆分本身制造的问题。

在大多数任务上，一个配有精准工具和压缩机制的单个前沿智能体非常难打败。决定上多智能体之前，可以先按评测文章里的方法做直接对比。因为多智能体一侧本来就背着 15 倍成本，证明收益足够大的责任也应该由它承担。实际评测里，它输给单智能体的频率，比生态里的宣传给人的印象高得多。

![](https://pic2.zhimg.com/v2-e41792c81bc0c64e997a9a5c1cc049f3_r.jpg)

真实的决策路径。大多数任务都会很早退出多智能体路线，而这正是正确结果。

### 5、当多智能体确实合理时，工程上要怎么做

任务简报就是 API。编排器发给工作智能体的那段文字，是整个系统里杠杆最高的接口之一。接收方很聪明、按字面执行，而且看不到别的信息。生产级任务简报至少要带上几类内容：用工作智能体自己的任务语言写清目标；补充它无法自行发现、但父智能体已经掌握的上下文和既有决策；规定结构化输出格式，因为这是机器到机器接口，最好直接用 schema 约束；给出工作量预算，比如“搜索 3–5 次，然后报告”；最后写清边界，例如“不要修改 /billing 之外的文件”。简报写得模糊，是重复劳动和工作智能体跑偏最常见的原因。Anthropic 复盘系统改进经验时，“教会编排器写详细任务简报”排在很靠前的位置。

摘要就是返回值。工作智能体的报告首先是工程接口，不是散文。结论要写清，路径、ID、引文等精确标识符必须原样保留；文章三提到的改述衰减，一跨智能体边界会更严重。置信度和未解决问题应该显式标记，完整工作历史不要带回父智能体。多跳传话确实会损失含义，结构化摘要能把损失压住。

影响范围要隔离。并行工作智能体最好各自拥有独立工作区，coding-agent 集群可以直接用不同 git worktree；工具集要收窄，预算也要分别设。很多失控智能体的事故复盘，结尾都会变成“后来加了每个工作智能体的上限”。这类保护更适合一开始就写进设计：最大步骤数、最大 Token 数、最大生成深度。

编排过程需要 checkpoint。5 个工作智能体跑到第 4 个时失败，正确行为应该是继续，而不是把前面全部重跑。harness 里的持久执行（durable execution）模式放到这里更有价值，因为单次运行更长，也更贵。部分失败同样要有明确处理方式：某个工作智能体返回 null 结果时，综合结果可以降级，但不能把错误当事实吃进去，也不能直接把整次运行撞崩。

追踪和评测对象应该是整个系统。多智能体系统最麻烦的故障经常发生在智能体之间：任务简报写歪了，摘要丢信息了，综合阶段没真正用上某个分支。评测除了端到端用例，还要看这些接缝：拆解合理吗？不同工作智能体是否做了重复工作？最终综合到底有没有用到第三个工作智能体的结果？带按分支成本汇总的追踪树，是定位这些问题最可靠的手段之一；阅读追踪本身也要计入工程成本。

### 7、决策框架

在创建多智能体之前先问：工作集是否超过一个上下文窗口？没有，就用一个智能体，结束。超过了，再看溢出的是广度，也就是可并行单元，还是深度，也就是一条长链。深度问题仍然留给一个智能体，配压缩和外部记忆。只有广度问题才继续往下问：各单元能不能在不共享可变状态的前提下独立运行？不能，就重新拆，直到能做到，或者停止。能做到，再上编排器—工作智能体，并配任务简报、预算、隔离、追踪和评测；评测基线必须是当前最好的单智能体方案。如果团队系统带来的提升没有超过它的成本倍数，就直接下线，不必留恋。

### 总结

智能来自模型围绕模型搭起来的 harness、上下文、工具和评测，要么把模型的能力送到任务上，要么在传递过程中把它耗掉。多智能体是这个原则最容易被看见的地方，因为架构在这里也最容易变成表演。几个有职位的智能体排在一起，很像组织，演示起来也很有未来感；可任务如果没有那个关键特征，架构本身不会增加价值。这个特征只有一个：相关工作多到一个上下文窗口装不下。

任务具备这个特征时，编排确实会改变结果。90% 的数字是真的，迁移集群是真的，上下文隔离的收益也是真的。任务不具备这个特征时，更合适的系统还是一个强模型放在构建良好的 harness 中，只看到完成任务真正需要的信息。

当工作量超过一个“脑子”的工作记忆时，再组建团队。否则，先把这个“脑子”造得更好。

by Shrashti Singhal
