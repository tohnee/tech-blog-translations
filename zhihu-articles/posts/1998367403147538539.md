## 学习目标

在本章节中，我们沿着 InfiniBand 的协议分层继续向上，来到紧邻网络层之上的传输层。正是在这一层，InfiniBand 展现出与传统网络明显不同的独特优势：它把端到端通信的可靠性、队列化的发送接收机制、以及 RDMA 这类硬件卸载能力组合在一起，使应用能够以更低的时延、更高的吞吐进行数据交换。在完成本章节后，你将能够掌握以下关键知识点：

- 描述传输层的定义与定位以及核心职责；<br>
- 描述队列对（QP）操作及 RDMA 等核心概念；
- 列出传输层提供的服务类型；
- 了解基准测试的常见 OFED 命令。

## 传输层概述

传输层负责在互连结构（fabric）中，在两个端点之间发送与接收消息。它为应用程序提供端到端的通信服务。这样的端到端通信通过一条连接两端应用的虚拟通道来实现，并在需要时跨越不同的地址空间。当消息的总长度超过端口的最大发送单元（MTU）时，传输层会把一条消息分段成多个数据包；而接收端随后会将这些分段的数据重新组装，并写入其内存中指定的数据缓冲区。如下图所示传输层在模型中的位置：

![](https://pica.zhimg.com/v2-7c0152ea2f54b5f4af903f707d6b1424_1440w.jpg)

## 传输层定义

这条虚拟通道的两端称为 QP（Queue Pair，队列对）。每一个 QP 都代表通道的一端。传输层中的传输部分会将数据包投递到正确的 QP，并指示该 QP 应当如何处理数据包中的数据。QP 为应用提供了一套机制，使其在进行数据传输时能够绕过操作系统内核，同时借助 InfiniBand 硬件自身的可靠性，在应用之间交换可靠的数据。QP 逻辑如下图所示，由于 QP 是传输层运作的核心组件之一，我们将对它进行更进一步的探讨。

![](https://pic2.zhimg.com/v2-840a1a08db14f9d251b3cd999e401f75_r.jpg)

### QP (队列对)

一个 QP（Queue Pair，队列对） 由一个发送队列和一个接收队列组成。每个 QP 都代表一条通道的一端，对应 **发送** 和 **接收** 两个方向，队列总是成对创建的；QP 通过它的 QP 编号（QP number）来标识，为了避免操作系统介入，应用程序可以直接访问这些 QP，这通常通过将每个应用的虚拟地址空间直接映射到 QP 来实现，下图展示了两个QP队列：

![](https://pic2.zhimg.com/v2-ecd6b72f9cb744aa1591de56f7115af3_r.jpg)

### QP 工作流

假设某个应用需要不止一条连接，就会创建额外的 QP。工作队列（work queue）是应用与 fabric 之间的接口，接着来看 QP 的工作流程，应用提交一个工作请求（work request）后，会在相应的工作队列上放入一条指令，这条指令称为工作队列元素（work queue element，WQE）；当通道适配器（channel adapter）完成某个 WQE 后，会在工作完成队列（work completion queue）中放入一个完成队列元素（completion queue element，CQE）；完成队列（completion queue）就是适配器用来通知应用、告知已完成工作请求状态的接口，逻辑如下图所示：

![](https://pic2.zhimg.com/v2-c57a553aa41abc763a8dac6ccb22bca5_r.jpg)

## 传输层职责

传输层主要负责三件事，第一是分段与重组。当一条消息的数据载荷超过端口的最大传输单元（MTU）时，传输层会把这条消息切成多个报文（packets）发出去；到了接收端，由接收侧的 QP 把这些分段的数据按序重组，并写入到本端内存中预先指定的数据缓冲区里。

第二件事与 QP 的传输服务类型有关。QP 在创建时必须绑定四种 IBA 传输服务类型中的一种，这个服务类型本质上定义了这条传输在可靠性上做到什么程度、以什么语义把数据从一端交付到另一端。按工程上常见的划分，可以理解为 面向连接（connection-oriented）和数据报（datagram）两类；而数据报又分为需要确认（acknowledged）和不需要确认（unacknowledged）两种交付方式。

第三件事是 InfiniBand 分区（Partition）。分区机制允许把一个大型集群按逻辑切分成多个彼此隔离的子集群，类似在同一套物理 fabric 上做强隔离的**域**划分，方便做多租户、业务隔离和权限控制。后续我们会在本单元里对这三项职责分别展开细讲。

### 分段与重组

在讲解 **分段（Segmentation）与重组（Reassembly）** 的职责之前需要先把 **包载荷（packet payload）** 这个概念说明白，每个数据包里都会带一个用于传输的事务载荷（transaction payload），载荷里装的就是实际要搬运的业务数据。

**MTU（Maximum Transfer Unit，最大传输单元）** 是用来定义一帧 InfiniBand 数据包最多能承载多大的数据载荷，InfiniBand 的 MTU 可以配置为 256 字节到 4096 字节，默认值是 4096 字节，如下图所示：

![](https://pic3.zhimg.com/v2-93ef9a1ac20e9dc5cd40ecbdde7463a0_r.jpg)

理解了载荷 和 MTU 之后，再来看分段与重组是怎么发生的，从传输行为上讲，MTU 直接决定了报文怎么发，如图所示，只有当数据包大小小于或等于 MTU时，才能不做额外处理直接发到链路上，如下图所示一个 1024 字节数据表在传输时的 MTU 是不用分段的：

![](https://pica.zhimg.com/v2-a50763e9a9b1e6e48fced97c01d637de_r.jpg)

而当一条消息的长度超过 MTU 时，就必须在发送侧把它切分成多个更小的包，才能跨链路传过去。由于 MTU 是可配置项，它给了工程上很大的灵活性，你可以根据应用的业务特性、链路情况和性能目标来调整，以更好地匹配实际需求，如下图所示的数据包大小为 16384 字节超过了 4096 字节需要分为四次发送：

![](https://pic3.zhimg.com/v2-cf2333a90fd8755e5645ae9d0e0b8706_r.jpg)

## 传输服务类型

现在把视线转到 **传输服务类型（Transport Service Types）** 上来，每个 QP 在创建阶段就会被分配一个传输模式，这四种传输服务类型分别是：可靠连接（Reliable Connection）、不可靠连接（Unreliable Connection）、可靠数据报（Reliable Datagram）、不可靠数据报（Unreliable Datagram）。选哪一种，完全取决于你的应用对可靠性、连接规模、时延与开销的取舍，在实际部署时要特别注意：源端和目的端的 QP 必须配置成同一种传输模式，否则两端语义对不上导致无法通信。

从工程上来看最常用的两个大类说起：连接型（Connected）和 数据报型（Datagram）。InfiniBand 的连接可以配置为这两种模式，核心差异在于传输层要和对端建立的是哪类 QP 关系。

在 **数据报模式** 下，一个 QP 可以同时服务多个会话，也就是它可以同时向多个远端 QP 发送、并从多个远端 QP 接收，适合一对多、多对多这种连接规模大、变化频繁的场景，逻辑如下图所示：

![](https://pic2.zhimg.com/v2-947e2b1ec3996727ee2fe907ca15070d_1440w.jpg)

在 **连接模式** 下，通信双方会在连接两端各自打开一个专用的 QP，双方就是固定的一对一互发互收，语义清晰、行为可控，代价是连接数上来之后 QP 资源占用也会随之增长，逻辑如下所示：

![](https://pic1.zhimg.com/v2-0f4aa7261b5f743b19e9333217af560a_r.jpg)

不管你选连接型还是数据报型，最终 QP 都将运行在某一种传输服务类型之下，而源端与目的端的 QP 必须配置为相同的服务类型，这样两端的交互规则才能对齐，数据才能按预期被传输和处理。

### 连接式服务类型

在连接型（connected） 服务里，一条连接两端各自会专门分配一个 QP，也就是一条连接占一对 QP，资源是独占的。用连接模式时，如果采用**可靠连接（RC，reliable connected）** 这种队列对类型，即便要发送的消息大于 InfiniBand 链路层的 MTU，也不用应用自己操心——主机通道适配器（HCA/Host Adapter）会在两端自动完成 分段与重组 。因此在连接模式下，从适配器来看，能发送的消息大小基本不受限制，不会被 MTU 直接卡在单包大小上。

连接模式通常提供的性能更高，但代价是会消耗更多的内核内存（更准确说是系统侧的资源开销更大）。多数环境里大家更看重性能而不是省内存，所以连接模式也就成了最常用的选择。

### 数据报服务类型

再看数据报模式（datagram），一个 QP 可以同时服务多个连接，可以对多个远端 QP 同时收发数据，这在规模上更友好。但是 QP 不支持消息分段，也就是说任何要发的包都不能超过 MTU，超过就发不出去。整体性能通常不如连接型服务，但可扩展性更强，特别适合一对多和多对多的通信场景。

举个典型场景，同一份数据要发给几百、几千个远端节点。你当然可以用连接模式给每个远端都拉一条连接，但这意味着本地要分配成百上千个 QP，连接数一多资源压力和管理成本都会显著上升；而用数据报模式时，一个 QP 就能覆盖多个远端，扩展起来更轻量。

### 可靠传输与不可靠传输

对于**可靠传输**服务来说，QP 需要承担把数据可靠送达的职责，它会跟踪数据包的发送与接收进度，并在检测到丢包时执行重传。为此，每个数据包都会携带一个包序列号 **PSN（Packet Sequence Number）**。接收端通过 PSN 来判断数据包是否按序到达以及是否存在缺失，从而用序列号机制维持端到端的包流有序性。

当接收端确认数据包按照期望顺序到达时，会返回 ACK 作为确认；如果发现中间有包缺失、乱序或其他异常，则会返回 NAK（负确认）提示发送端采取补救措施。与此同时，发送端 QP 还会维护超时计时器，用来发现包没有到达接收端或确认报文在途中丢失这类情况，一旦超时触发，就会进入相应的重传流程，如下图所示：

![](https://pica.zhimg.com/v2-2af0051bc794fe1da39d211b39f0ec1a_r.jpg)

需要注意的是，重传在网络工程视角里通常意味着链路状态不健康，它会显著拉低吞吐与时延表现，严重时甚至可能导致连接异常中断。链路质量差、线缆或光模块问题、接口误码等因素，都可能让重传变得频繁。

在**不可靠传输**模式下，则不存在可靠性保障，不能保证消息一定送达，也不提供对到达顺序的保证，应用侧必须自行承担相应的容错与一致性处理，如下图所示：

![](https://pic4.zhimg.com/v2-9141681c44da882153230057cb64603b_r.jpg)

理解了这些机制之后，我们就可以把可靠与不可靠、连接与数据报的差异放在同一框架下重新审视各类传输模式，从而更有把握地根据业务对性能、资源占用和扩展性的要求做出选择。

### 传输服务类型对比

如下表所示，这里我们对两种传输服务的关键差异做一个对比，便于你在实际选型时快速把两类传输模式放在同一维度下理解到底该用哪一种。总体来说，连接模式（connected）通常能提供更高的性能表现，但相应也会占用更多的内核内存和系统资源。由于大多数落地实现更看重性能而非内存开销，连接模式也就成为最常用的选择。

| 考量因素 (Considerations) | RC (可靠连接) | RD (可靠数据报) | UC (不可靠连接) | UD (不可靠数据报) |
| --- | --- | --- | --- | --- |
| 消息分段 (Message Segmentation) | ✅ |  | ✅ |  |
| 性能 (Performance) | ✅ |  | ✅ |  |
| 可扩展性 (Scalable) |  | ✅ |  | ✅ |
| 多连接支持 (Multiple Connections) |  | ✅ |  | ✅ |
| 可靠性 (Reliability) | ✅ | ✅ |  |  |

这并不是二选一的固定答案。在同一套系统里，你完全可以针对不同的业务流、不同的通信关系，分别在不同的 QP 上选择不同的传输模式，从而在性能、资源占用与可扩展性之间获得更灵活、更贴合业务的组合方案。

## 卸载数据传输语义

这一部分将说明卸载式（offload）数据传输语义。在进入这些语义细节之前，有必要先简要回顾一下什么是 RDMA（Remote Direct Memory Access，远程直接内存访问），以及它为什么重要。

RDMA 可以说是一项改变游戏规则的技术，它允许一台主机对另一台远端服务器的内存直接执行读写操作，而在数据搬运的关键路径上不需要端点任意一侧的 CPU 参与处理。这正是我们稍后要讨论的卸载式数据传输语义的核心所在——把原本需要 CPU 介入的数据拷贝与协议处理，尽可能交给网卡或者主机通道适配器来完成。

因此，RDMA 带来的直接收益主要体现在三个方面，首先是降低网络时延，因为减少了 CPU 参与与上下文切换等开销；其次是提升网络吞吐，数据路径更短、处理更硬件化；最后是释放 CPU 周期，让 CPU 能把算力更多投入到业务计算等与网络无关的任务中。理解了这些背景之后，我们再来看卸载式数据传输具体是如何工作的。

### 卸载式语义传输

第一类语义是通道语义（Channel Semantic），也就是常说的 Send/Receive。发送端只负责把消息发送出去，接收端必须事先在接收队列中预置（pre-post）接收缓冲区对应的接收工作请求。发送端并不知道接收端具体使用哪个缓冲区，它只是把消息交付给对端，由对端按其预置的接收资源来接收并落地，这种方式更像同步式的消息流动，接收端必须提前准备好接收槽位，如下图所示：

![](https://pic3.zhimg.com/v2-5df32dcb51a024b02bd34b7ec78c243e_r.jpg)

第二类语义是内存语义（Memory Semantic），主要是 RDMA Read 与 RDMA Write。接收端会把自身虚拟内存空间中的某个缓冲区注册（memory registration）后，将该缓冲区的地址与权限键（key）交给远端。随后，发送端可以使用 RDMA Read 从对端直接读取数据，或使用 RDMA Write 直接写入对端指定缓冲区。与 Send/Receive 相比，这种方式更像异步的远程内存访问，其工作方式也常被类比为存储系统的数据传输模型，如下图所示：

![](https://pic1.zhimg.com/v2-79e85d2bf6a4cb1b4f036e0ed7579e42_r.jpg)

### 通道语义操作示例

如下图所示，首先，接收端在用户态的虚拟内存中分配一个接收缓冲区，并将该缓冲区注册到 HCA（Host Channel Adapter，主机通道适配器）。

随后，接收端把一个工作请求（Work Request）投递到接收队列（Receive Queue）中，表明自己已经准备好用这块缓冲区来接收即将到来的数据；接着，发送端在用户态虚拟内存中分配一个发送缓冲区，并同样将其注册到本端的 HCA。发送端把对应的工作请求投递到发送队列（Send Queue）中，指示适配器从这块发送缓冲区取数据并发往对端。

然后，本端 HCA 开始执行发送工作请求：它从主机内存中的发送缓冲区读取数据，将数据发送到远端，并生成一个完成标识（通常可理解为完成事件，用于通知该次操作完成）

最后，当数据到达接收端时，接收端 HCA 执行接收工作请求：它把收到的数据放入先前预投递的接收缓冲区中，并同样生成一个完成标识，通知接收端应用该次接收已经完成，数据已经就绪可用。

![](https://pic4.zhimg.com/v2-5245bec37c2946e8ae4e76cc1db44301_r.jpg)

### 内存语义操作示例

RDMA 支持零拷贝网络传输，网络适配器可以直接在应用程序内存与网络之间搬运数据，从而避免在操作系统内核缓冲区与应用内存之间来回拷贝，操作步骤如下图所示，首先，接收端（也就是被写入的一端）对目标缓冲区进行内存注册（memory registration），并把这块缓冲区的虚拟地址以及对应的访问权限 key（远端访问密钥）交给远端发送方。与 Send/Receive 不同的是，这里不需要在接收队列里预投递接收工作队列元素（ receive WQE），因为这次数据落点是已授权的远端内存，而不是接收队列里预先准备好的接收缓冲。

接着，发送端在用户态虚拟内存中分配发送缓冲区，并将其注册到本端 HCA。然后发送端在发送队列中投递一个 RDMA Write 的发送工作请求（Send WQE），其中携带接收端缓冲区的虚拟地址，以及接收端提供的远端权限 key，用于让对端 HCA 验证写入权限。

随后，本端 HCA 执行该工作请求，从主机内存的发送缓冲区读取数据，将数据发往远端，并生成完成标识（可理解为完成事件），通知发送侧该次写入操作已经完成。

最后，当数据到达接收端 HCA 时，接收端 HCA 会检查请求中携带的目标地址与内存 key 是否匹配、权限是否正确；验证通过后，它会把数据直接写入接收端主机内存中已注册的那块缓冲区，从而完成一次 RDMA Write。

![](https://pic1.zhimg.com/v2-9a17d17122ef97886428c1cd0495ea0a_r.jpg)

## 分区（Partition ）

本节介绍 InfiniBand 分区（partition）的职责。InfiniBand 分区用于将一个较大的 InfiniBand 子网（subnet）划分为多个更小、彼此隔离的子网，从而在同一物理网络之上实现逻辑上的分段与隔离。

一个分区会定义一组被允许彼此通信的 InfiniBand 节点。需要注意的是，同一个节点可以同时属于多个分区，这使得系统管理员能够根据实际需求配置相互重叠的分区集合，以满足不同业务之间的互通与隔离要求。与此同时，不同分区之间在端口与通信层面是完全隔离的，分区边界之外的节点默认无法互相访问。

分区最常见的用途之一是实现不同客户之间的隔离，可以把它类比为多租户（multi-tenancy）场景下对客户与应用的逻辑隔离手段。分区也常用于出于安全目的的访问控制，确保只有被授权的节点集合才能在同一分区内通信。此外，分区在进行服务质量（QoS，Quality of Service）相关的规划与划分时也非常灵活，便于按业务类型、优先级或带宽策略对通信域进行组织。

### 分区 ID - P_Key

接下来我们来看分区 ID，也就是 P_Key（Partition Key，分区密钥）。它是实现 InfiniBand 分区的核心机制，用来在正常数据通信中完成分区标识与隔离控制。每个数据包都会携带一个 16 位的 P_Key（分区键），用以标记该数据包所属的唯一分区， Pkey在数据包中的位置如下图所示：

![](https://pic3.zhimg.com/v2-d346f8fc2ae02083c91a937aa2c2a86c_r.jpg)

子网管理器（SM）会为每个节点的通道适配器（Channel Adapter）配置一组允许使用的 P_Key。 当一个数据包到达某个节点时，通道适配器会根据子网管理器下发的配置，检查该数据包携带的 P_Key 是否有效；如果 P_Key 无效，数据包会被直接丢弃。通过这种 P_Key 校验机制，才能防止服务器与分区之外的其他服务器进行通信，从而在网络层面强制实现隔离。

从概念上看，InfiniBand 分区类似于传统 I/O 网络技术中由硬件强制执行的安全隔离能力，例如以太网的 VLAN、以及光纤通道（Fibre Channel）的分区 等机制。

### 成员类型

分区成员关系（Partition Membership）用于描述一个分区内部的成员构成方式，以及这些成员在同一分区内彼此通信时所遵循的规则。一个分区包含一组成员，但在同一个分区中可以同时存在不同类型的成员。借助成员关系，管理者不仅能够控制分区与分区之间的隔离，还能进一步精细化地定义分区内部哪些成员之间允许通信、哪些成员之间禁止通信，从而实现更强的访问控制能力。

分区成员关系主要分为两类：完全成员（Full Membership）与 受限成员（Limited Membership）。完全成员具备最完整的通信权限，它可以与分区内的所有其他成员进行通信，无论对方同样是完全成员还是受限成员；受限成员的通信权限则受到约束：受限成员不能与其他受限成员直接通信，但它仍然可以与分区内的完全成员进行通信；通过这种权限划分，可以在同一分区内形成一种中心—边缘式的通信结构，完全成员能够与所有成员交互，而受限成员之间相互隔离，只能通过完全成员实现必要的数据交换或服务访问。

这种成员关系的设计在实际场景中非常常见，尤其适用于存储网络等需要强隔离的环境。例如在存储系统中，发起端（Initiator）需要访问目标端（Target）以发起读写请求，但通常并不希望不同发起端之间能够互相通信，以避免横向访问带来的安全风险或不必要的耦合。此时可以将目标端配置为完全成员，而将各个发起端配置为受限成员，使发起端能够访问目标端，但发起端之间无法互通。类似地，在网络管理场景中，也经常希望在管理子网内阻止节点与节点之间的直接通信，只允许节点与特定的管理实体交互，从而降低攻击面并提升管理边界的清晰度。通过合理组合完全成员与受限成员，就能够在保持必要连通性的同时，实现更严格、更可控的隔离策略。

### 成员类型示例

在如下示例用例中，可以看到有三个端点属于同一个成员组，因为它们共享相同的 P_Key（数值为 3）。其中包含两个发起端（Initiator）和一个目标端（Target）。由于这两个发起端被配置为受限成员（Limited Membership），它们彼此之间无法通信，但都可以与目标端通信。这样的配置将各个发起端相互隔离开来，一方面提升了安全性，另一方面也避免了发起端之间不必要的通信开销。

![](https://pica.zhimg.com/v2-2436d9dcefa99d772b2c97c5d3b6c304_r.jpg)

如果没有为某个端点显式指定成员类型，那么它会采用默认的成员关系设置。通常情况下，系统会将其视为**完全成员（Full Membership）**，从而允许它与同一分区内的所有成员通信，包括完全成员与受限成员。这样做的结果是，该端点在分区内拥有更宽泛的通信权限，因此在需要严格隔离的场景中，通常应当明确配置成员类型，以免由于默认行为而引入超出预期的互通范围。

### 默认分区

子网管理器（Subnet Manager）会自动配置一个默认分区，它的 P_Key 固定为 `0x7FFF`。默认分区用于覆盖并管理所有已连接的端口；在默认情况下，网络中的一切对象都会以 **完全成员（full member）** 的身份加入默认分区，逻辑下图所示：

![](https://pic4.zhimg.com/v2-ea6fcb861c11d68ea1773d55fe30dda3_r.jpg)

默认分区号为 `0x7FFF`，但作为完全成员时，在报文中看到的 P_Key 值为 0xFFFF (65535)。

### P_Key 示例

我们可以通过抓包来判断当前的成员类型。P_Key 是一个 16 位的字段，其**最高位（MSB，第 15 位）** 决定了成员权限：

- 1 (Full Member)：完全成员，可以与分区内所有节点通信。
- 0 (Limited Member)：受限成员，只能与完全成员通信。<br>

如下图所示，抓包显示的 P_Key 数值为 65535（十六进制 0xFFFF）。将其转换为二进制为 `1111 1111 1111 1111`，可以看到最高位为 1，因此该端点是完全成员。除去最高位，剩下的 15 位（0x7FFF）即为该分区的编号（Partition Key）。

![](https://pic3.zhimg.com/v2-035aa22f0d0ce9734dce66a39647a0fc_r.jpg)

## OFED - 传输层管理命令

下面我们来了解一些实用的 OFED 命令。正如前面的内容所提到的，OFED 工具集主要用于对 InfiniBand Fabric 进行管理与监控。在接下来的一组内容中，我们将介绍若干条 InfiniBand 管理员常用的命令，用于对传输层进行日常管理、运行状态观察以及故障排查与验证工作。

### RDMA 性能测试

PERF test 包是一组用于性能微基准（performance micro-benchmark）的测试程序，既可用于性能调优，也可用于功能验证。整体而言，这些测试主要分为两大类：时延性能测试与带宽性能测试。在实际使用时，你可以针对 RDMA Read、RDMA Write 以及 Send 等不同操作分别运行时延或带宽测试，以便从不同维度评估链路与端到端传输能力，常用命令如下表所示：

| 延迟测试（Server） | 延迟测试（Client） | 带宽测试（Server） | 带宽测试（Client） |
| --- | --- | --- | --- |
| ib_read_lat | ib_read_lat <主机名/IP> | ib_read_bw | ib_read_bw <主机名/IP> |
| ib_write_lat | ib_write_lat <主机名/IP> | ib_write_bw | ib_write_bw <主机名/IP> |
| ib_send_lat | ib_send_lat <主机名/IP> | ib_send_bw | ib_send_bw <主机名/IP> |

需要注意的是，为了保证测试结果的可比性与准确性，参与测试的两端节点最好具备一致的 CPU 主频，否则可能影响计时与结果解读。这些命令通常也提供了大量可选参数，能够根据不同场景进行细致配置。回到你的网络环境后，可以对任意一个命令加上 `-h` 参数查看帮助信息，从而结合自身用例探索更合适的运行方式与配置选项。

### 延迟测试

下面我们通过一个贴近实际运维的例子来说明如何进行 RDMA Write 时延测试。在这个场景中，你需要在一台服务器节点和一台客户端节点上同时使用 `ib_write_lat` 命令，用来测量两端之间的写入时延。

在服务端（server）上，直接运行 `ib_write_lat`。启动后你会看到提示信息，表明程序正在等待客户端连接，如下所示：

![](https://pic1.zhimg.com/v2-797161106d686208f702bb8ee13c5f52_1440w.jpg)

随后在客户端（client）上运行相同的 `ib_write_lat mtlacad05` 命令，但与服务端不同的是，客户端需要额外指定服务端的主机名或 IP 地址，以便明确要连接到哪一台服务器。运行一段时间后，客户端会输出测试结果，即本次 RDMA Write 时延测试的统计信息，如下所示：

![](https://pic4.zhimg.com/v2-f32a9a6e6e6ec3b84dbfc77983f43995_r.jpg)

输出中最常关注的是 `t_typica` 这一列，它给出典型时延，单位通常是微秒（microseconds）。示例结果显示时延低于 1 微秒，这代表链路与端到端通信具有非常低的延迟水平。对于 InfiniBand 管理员而言，这类工具不仅适用于日常性能监控，也非常有助于建立一套期望性能基线。当网络性能出现波动时，你就能通过对比基线迅速判断当前表现是否偏离正常范围，从而更快定位问题与采取措施。

### 速率测试

下面我们再来看一个带宽测试的例子。在这个场景中，我们需要在客户端与服务端节点上同时使用 `ib_write_bw` 命令，以测试 RDMA Write 的吞吐能力。

如下所示，在服务端侧，先运行 `ib_write_bw`，并配合 `--report gbits` 选项，将统计结果以千兆比特（Gb）为单位输出。命令启动后，你会看到提示信息，表明程序正在等待客户端连接。

![](https://pic3.zhimg.com/v2-648db6c410fb095cc480d13039a4a174_r.jpg)

如下所示，随后在客户端侧运行与服务端相同的 `ib_write_bw --report_gbits mtlacad05` 命令，不同之处在于客户端需要指定服务端的主机名或 IP 地址，以便知道要连接到哪台服务器。运行一段时间后，客户端会输出本次写带宽测试的结果。

![](https://pica.zhimg.com/v2-ce65bbd1a02f03655808080aca5fc586_r.jpg)

在客户端输出中，`BW average` 这一列给出了平均带宽，单位通常是 Gb/s（千兆比特每秒）。示例结果显示吞吐接近 100 Gb/s，这符合 EDR Fabric 中常见的高带宽预期。与 PERF test 套件中的其他工具一样，这条命令不仅能够用于性能监控，也能帮助你建立期望性能基线，从而在后续运维中快速识别性能是否偏离基线、并及时开展排查。
