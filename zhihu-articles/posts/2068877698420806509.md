## 5. 视觉大模型微调

前面我们已经完成了 Qwen3-VL 的环境配置、模型下载和基础调用。接下来就可以进入视觉大模型微调环节。

所谓微调，就是在已有基础模型的能力之上，使用我们自己的数据继续训练模型，让它更适应某一类任务、某一种回答风格，或者某一个垂直业务场景。对于 VLM 来说，微调不再只是普通的文本问答训练，而是需要同时考虑文本、图片、视频等多模态输入。

这一节我们分成两部分来完成。

第一部分是 **快速训练脚本** 。我们先使用 ms-swift 官方或社区已经整理好的数据集，直接跑通一次 LoRA 微调流程。这个阶段的重点不是追求模型效果，而是先理解训练命令、路径设计和关键参数含义。

第二部分是 **自定义训练数据** 。我们会学习 VLM 微调数据应该长什么样，然后以 ModelScope 上的 `LaTeX_OCR:human_handwrite` 数据集为例，从测试集中抽取一部分样本，转换成 ms-swift 可以读取的本地 JSONL 格式，最后再使用自定义数据集进行训练。

## 5.1 快速训练脚本

在正式写训练脚本之前，我们先把这一小节的训练思路理清楚。对于第一次进行 VLM 微调的同学来说，不建议一开始就直接使用大规模自定义数据集，也不建议一开始就解冻视觉模块做复杂训练。更稳妥的做法是先用少量现成数据跑通一次完整流程，确认环境、模型、数据加载、显存占用、checkpoint 保存都没有问题。

因此，这里的快速训练并不是为了马上得到一个效果明显提升的模型，而是为了完成一次“最小可运行”的 VLM LoRA 微调实验。只要这一步跑通，后面再替换成自定义数据集、调整训练轮数、扩大样本数量，都会更加清晰。

### 5.1.1 快速训练的整体思路

本次快速训练主要采用以下设计：

```text
本地 Qwen3-VL-2B-Instruct 模型
        ↓
混合少量文本、图片、视频样本
        ↓
冻结视觉编码器和视觉-语言对齐模块
        ↓
只用 LoRA 轻量微调语言模型侧的线性层
        ↓
将训练结果保存到数据盘

```

这样设计有几个原因。

第一，模型使用的是前面已经下载好的本地模型：

```text
/root/autodl-tmp/qwen3-vl-2b-instruct

```

这样训练时不需要重复从远程下载模型，速度更快，也更稳定。

第二，训练数据采用少量混合数据，包括中文文本指令数据、图片公式识别数据和视频理解数据。这样可以更直观的看到 VLM 微调并不是只能训练图片问答，也可以同时混合文本、图片和视频样本。

第三，训练方式选择 LoRA，而不是全参数微调。Qwen3-VL 虽然是 2B 级别模型，但由于还包含视觉编码器和多模态输入处理，显存占用仍然高于普通文本模型。LoRA 可以显著降低训练显存压力，更适合快速入门实验。

第四，冻结视觉编码器和对齐模块（前面提到的跨模态连接器）。也就是说，这次训练不会大幅改变模型“怎么看图”的基础能力，而是主要让模型学习如何根据已有视觉特征生成更符合训练数据的回答。

第五，把缓存和输出都放到 `/root/autodl-tmp` 数据盘中。云服务器的系统盘空间通常比较有限，而模型、数据集缓存和训练 checkpoint 都比较大，所以这些内容最好统一放到数据盘中。

### 5.1.2 路径设计说明

在编写训练脚本前，需要先明确各类文件应该保存在哪里。这个问题看似只是目录设置，但在云服务器实验中非常关键。如果路径设计不合理，很容易出现系统盘被占满、缓存散落、训练结果找不到等问题。所以需要确保这些内容会下载到数据盘 `/root/autodl-tmp` 中，以免出现系统盘存储不足的情况。

本次训练主要涉及三类路径。

### 5.1.2.1 模型路径

```text
MODEL_PATH="/root/autodl-tmp/qwen3-vl-2b-instruct"

```

这里指向前面已经下载好的 Qwen3-VL-2B-Instruct 模型目录。后续无论是训练、推理还是部署，都可以复用这个路径。

### 5.1.2.2 缓存路径

```text
export MODELSCOPE_CACHE="/root/autodl-tmp/modelscope_cache"
export HF_HOME="/root/autodl-tmp/hf_cache"
export HF_DATASETS_CACHE="/root/autodl-tmp/hf_cache/datasets"
export HF_HUB_CACHE="/root/autodl-tmp/hf_cache/hub"

```

这些路径用于保存数据集缓存和可能产生的模型缓存。虽然我们当前主要使用 ModelScope 数据集，但部分底层依赖仍然可能调用 Hugging Face 生态中的缓存机制，所以这里同时配置 ModelScope 和 Hugging Face 缓存路径。

### 5.1.2.3 输出路径

```text
OUTPUT_DIR="/root/autodl-tmp/output/qwen3-vl-2b-lora"

```

训练产生的 LoRA checkpoint、训练日志和配置文件都会保存在这个目录下面。由于 checkpoint 可能比较大，所以建议保存到数据盘，而不是系统盘。

所以，本节脚本的路径设计原则可以总结为：

```text
代码脚本放在 /root/ms-swift
模型、数据集缓存、训练结果放在 /root/autodl-tmp

```

这样既方便管理代码，也能避免系统盘空间不足。

### 5.1.3 数据集设计说明

在快速训练阶段，我们不直接从零制作数据，而是先使用 ms-swift 已经适配好的公开数据集。这样可以减少数据格式处理带来的干扰，把重点放在训练流程本身。

本次训练脚本中使用三个数据集：

```text
--dataset 'AI-ModelScope/alpaca-gpt4-data-zh#100' \
          'AI-ModelScope/LaTeX_OCR:human_handwrite#50' \
          'swift/VideoChatGPT:Generic#20'

```

其中， `AI-ModelScope/alpaca-gpt4-data-zh#100` 是中文文本指令数据，用来保留模型基础中文问答和指令跟随能力。

`AI-ModelScope/LaTeX_OCR:human_handwrite#50` 是图像到文本数据，任务是根据手写公式图片生成对应的 LaTeX 表达式。这类数据可以很好地展示 VLM 的 OCR 类任务。

`swift/VideoChatGPT:Generic#20` 是视频理解数据，用来演示 VLM 微调时也可以处理视频输入。

每个数据集后面的 `#100` 、 `#50` 、 `#20` 表示只抽取部分样本。这里总样本量很小，所以训练速度会非常快，也更适合大家进行快速测试。

需要注意的是，这种小规模混合训练主要用于验证流程，不适合直接拿来判断模型能力是否显著提升。真正做任务优化时，需要准备更多高质量、分布一致的数据。在官方文档中推荐的数量是：

```text
--dataset 'AI-ModelScope/alpaca-gpt4-data-zh#10000' \
          'AI-ModelScope/LaTeX_OCR:human_handwrite#5000' \
          'swift/VideoChatGPT:Generic#2000' \

```

### 5.1.4 相关参数说明

### 5.1.4.1 VLM 相关参数说明

相比普通文本模型，VLM 训练中最需要关注的是视觉输入规模和视觉模块是否参与训练。

首先是图片 token 数量：

```text
export IMAGE_MAX_TOKEN_NUM=1024

```

模型不会直接把图片原样送入语言模型，而是先通过视觉编码器把图片转换成视觉 token。 `IMAGE_MAX_TOKEN_NUM` 用来控制一张图片最多保留多少视觉 token。

这个值越大，图像细节保留越多，但显存占用也越高。教学实验中设置为 `1024` 比较稳。如果显存不足，可以先降低到 `512` 。

然后是视频相关参数：

```text
export VIDEO_MAX_TOKEN_NUM=128
export FPS_MAX_FRAMES=16

```

视频可以理解为多帧图片，因此比单张图片更容易占用显存。 `FPS_MAX_FRAMES=16` 表示最多从视频中抽取 16 帧； `VIDEO_MAX_TOKEN_NUM=128` 表示限制视频转换后的 token 数量。

这两个参数越大，模型看到的视频信息越多，但训练显存也会增加。第一次实验建议保守一些，先保证能跑通。

接下来是视觉模块冻结参数：

```text
--freeze_vit true
--freeze_aligner true

```

- `-freeze_vit true` 表示冻结视觉编码器。视觉编码器负责把图片或视频转换成视觉特征，如果参与训练，显存和计算成本都会明显增加。
- `-freeze_aligner true` 表示冻结视觉特征和语言模型之间的对齐模块。这个模块负责把视觉侧输出转换到语言模型可以理解的表示空间。小样本训练时冻结它更稳，不容易破坏原来的视觉-语言对齐能力。

所以，这个快速脚本的训练策略可以总结为：

```text
视觉编码器不动，对齐模块不动，只用 LoRA 轻量调整语言模型侧。

```

### 5.1.4.2 LoRA 与训练参数说明

训练方式这里选择的是 LoRA：

```text
--tuner_type lora

```

LoRA 的作用是在部分线性层旁边增加少量可训练参数，训练时只更新这些新增参数，而不是更新整个模型。这样可以明显降低显存占用，也方便后续保存和加载 adapter。假如我们想要进行全参数微调的话可以设为 `full` ，但是这个对显存要求比较高，这里就不进行设置了。

除此之外，通常在训练过程中需要设置其他 lora 相关参数：

```text
--lora_rank 8
--lora_alpha 32
--target_modules all-linear

```

- `-lora_rank 8` 表示 LoRA 的低秩维度为 8。rank 越大，可训练参数越多，模型调整能力越强，但显存占用也会增加。
- `-lora_alpha 32` 是 LoRA 分支的缩放系数，会影响 LoRA 更新对模型输出的影响强度。
- `-target_modules all-linear` 表示把 LoRA 应用到所有线性层上。当然这里我们也可以选择设置部分线性层，比如设为 `--target_modules q_proj k_proj v_proj o_proj` 。

另外，这里也需要设置其他常规训练参数，包括训练轮数和学习率以及预热值等：

```text
--num_train_epochs 1
--learning_rate 1e-4
--warmup_ratio 0.05

```

这里训练 1 轮即可，因为当前目标是跑通流程。 `learning_rate=1e-4` 是 LoRA 微调中比较常见的起步值， `warmup_ratio=0.05` 表示前 5% 的训练步骤用于学习率预热。

另外为了节省显存消耗，因此设置了以下优化参数：

```text
export PYTORCH_CUDA_ALLOC_CONF="expandable_segments:True"
--gradient_checkpointing true
--per_device_train_batch_size 1
--gradient_accumulation_steps 2

```

这一组参数主要用于降低单卡训练时的显存压力。首先， `PYTORCH_CUDA_ALLOC_CONF="expandable_segments:True"` 可以缓解 PyTorch 的显存碎片问题，减少由于显存分配不连续导致的 OOM。其次， `--gradient_checkpointing true` 会开启梯度检查点机制，用额外的计算开销换取更低的显存占用。

在 batch size 设置上，这里将 `--per_device_train_batch_size` 设为 1，也就是每张 GPU 每次只处理 1 条样本。由于 VLM 样本可能包含图片或视频，显存开销通常比纯文本任务更高，因此不建议一开始就把 batch size 调大。为了在小 batch size 下仍然获得更稳定的更新效果，这里设置 `--gradient_accumulation_steps 2` ，表示累积 2 次梯度后再进行一次参数更新，等效 batch size 可以近似理解为 2。

### 5.1.5 写入训练脚本

在理解了路径、数据集和关键参数之后，我们再来编写训练脚本。这样学生看到脚本时，就能知道每一部分为什么这样写。

首先在 `/root/ms-swift` 目录下新建脚本文件 `train_qwen3_vl_lora.sh` 并写入以下内容：

```python
#!/bin/bash

# =========================
# 1. 基础路径配置
# =========================

# 模型路径
MODEL_PATH="/root/autodl-tmp/qwen3-vl-2b-instruct"

# 数据盘缓存目录
export MODELSCOPE_CACHE="/root/autodl-tmp/modelscope_cache"
export HF_HOME="/root/autodl-tmp/hf_cache"
export HF_DATASETS_CACHE="/root/autodl-tmp/hf_cache/datasets"
export HF_HUB_CACHE="/root/autodl-tmp/hf_cache/hub"

# 训练输出目录
OUTPUT_DIR="/root/autodl-tmp/output/qwen3-vl-2b-lora"

# 创建必要目录
mkdir -p "$MODELSCOPE_CACHE"
mkdir -p "$HF_DATASETS_CACHE"
mkdir -p "$HF_HUB_CACHE"
mkdir -p "$OUTPUT_DIR"

# =========================
# 2. 显存与多模态输入配置
# =========================

export PYTORCH_CUDA_ALLOC_CONF="expandable_segments:True"

# 控制图片输入 token 数量
export IMAGE_MAX_TOKEN_NUM=1024

# 控制视频输入 token 数量
export VIDEO_MAX_TOKEN_NUM=128

# 控制视频最大抽帧数量
export FPS_MAX_FRAMES=16

# 使用第 0 张 GPU
export CUDA_VISIBLE_DEVICES=0

# =========================
# 3. 启动 LoRA 微调
# =========================

swift sft \
    --model "$MODEL_PATH" \
    --dataset 'AI-ModelScope/alpaca-gpt4-data-zh#100' \
              'AI-ModelScope/LaTeX_OCR:human_handwrite#50' \
              'swift/VideoChatGPT:Generic#20' \
    --load_from_cache_file true \
    --split_dataset_ratio 0.01 \
    --tuner_type lora \
    --torch_dtype bfloat16 \
    --num_train_epochs 1 \
    --per_device_train_batch_size 1 \
    --per_device_eval_batch_size 1 \
    --learning_rate 1e-4 \
    --lora_rank 8 \
    --lora_alpha 32 \
    --target_modules all-linear \
    --freeze_vit true \
    --freeze_aligner true \
    --gradient_checkpointing true \
    --vit_gradient_checkpointing false \
    --gradient_accumulation_steps 2 \
    --eval_steps 20 \
    --save_steps 20 \
    --save_total_limit 2 \
    --logging_steps 5 \
    --max_length 2048 \
    --output_dir "$OUTPUT_DIR" \
    --warmup_ratio 0.05 \
    --dataset_num_proc 4 \
    --dataloader_num_workers 4

```

保存后，执行下面命令给脚本添加运行权限：

```text
chmod +x train_qwen3_vl_lora.sh

```

然后启动训练：

```text
bash train_qwen3_vl_lora.sh

```

### 5.1.6 训练结果解析

### 5.1.6.1 训练日志解析

训练启动后，终端会持续输出日志。下面是一条典型的训练日志：

```text
{'loss': '1.306', 'grad_norm': '1.861', 'learning_rate': '9.137e-05', 'token_acc': '0.6155', 'epoch': '0.2395', 'global_step/max_steps': '20/84', 'elapsed_time': '17s', 'remaining_time': '54s', 'memory(GiB)': '9.74', 'train_speed(s/it)': '0.8429'}

```

这里重点关注几个指标。

- `loss` 表示当前训练损失。一般来说，训练过程中 loss 有下降趋势是正常的。但由于这里混合了文本、图片和视频数据，而且样本数量很少，所以 loss 不一定会非常平滑。
- `token_acc` 表示 token 级别的预测准确率，可以粗略理解为模型预测下一个 token 的命中情况。它越高通常越好，但它不是最终任务效果的唯一标准。
- `learning_rate` 表示当前学习率。从日志可以看到，训练一开始学习率会从较小值上升，之后逐步下降，这对应脚本中的 `warmup_ratio` 和学习率调度策略。
- `global_step/max_steps` 表示当前训练到了第几步。例如 `20/84` 表示总共 84 步，现在训练到了第 20 步。
- `memory(GiB)` 表示当前显存占用。从这次日志可以看到，显存大约稳定在 9GB 到 10GB 左右，说明在当前参数配置下，训练压力并不大。
- `train_speed(s/it)` 表示每一步训练大约需要多少秒。这里大约在 0.8 到 0.9 秒左右，说明这个快速实验可以在较短时间内完成。

训练中还会出现类似信息：

```text
qwen-vl-utils using decord to read video.

```

这表示 qwen-vl-utils 正在使用 decord 读取视频数据。因为训练数据中包含 `VideoChatGPT` 视频样本，所以出现这条日志是正常的。

有时还可能看到类似信息：

```text
[h264 @ 0x55aaaa0cd040] mmco: unref short failure

```

这通常来自视频解码过程，属于 ffmpeg 或 decord 在读取某些 H.264 视频时输出的警告。如果训练没有中断，后面仍然正常继续，一般可以先不用处理。

### 5.1.6.2 验证结果解析

训练过程中，每隔一定步数会进行一次验证。例如日志中出现：

```text
{'eval_loss': '1.257', 'eval_runtime': '1.169', 'eval_samples_per_second': '2.566', 'eval_steps_per_second': '2.566', 'eval_token_acc': '0.5362', 'epoch': '0.9581', 'global_step/max_steps': '80/84', 'elapsed_time': '1m 11s', 'remaining_time': '4s', 'memory(GiB)': '10.29', 'train_speed(s/it)': '0.8916'}

```

这里的 `eval_loss` 表示验证集损失， `eval_token_acc` 表示验证集 token 准确率。

从这次日志来看，验证损失大致在 `1.305 → 1.263 → 1.257 → 1.258` 附近变化，整体略有下降，然后趋于稳定。这说明训练流程是正常的，但由于验证样本很少，不能过度解读这个数值。

验证集每次只有 3 条样本：

```text
Val: 100%|...| 3/3

```

这是因为我们设置了：

```text
--split_dataset_ratio 0.01

```

训练总样本量本来就不大，加起来就 270 条，因此划分出的验证集更小，所以这里的验证指标只能作为流程是否正常的参考，不能作为严肃模型评估结论。

### 5.1.6.3 Checkpoint 保存结果解析

训练过程中还会看到类似日志：

```text
[INFO:swift] Saving model checkpoint to /root/autodl-tmp/output/qwen3-vl-2b-lora/v0-20260424-214956/checkpoint-20

```

这表示 ms-swift 已经把当前训练得到的 LoRA 权重保存到了输出目录中。由于脚本中设置了：

```text
--save_steps 20
--save_total_limit 2

```

所以每 20 步会保存一次 checkpoint，但最多只保留 2 个 checkpoint，避免输出目录越来越大。

本次训练最后会保存到类似下面的目录：

```text
/root/autodl-tmp/output/qwen3-vl-2b-lora/v0-20260424-214956/checkpoint-84

```

其中：

- `qwen3-vl-2b-lora` 是我们设置的输出目录；
- `v0-20260424-214956` 是 ms-swift 自动生成的一次训练运行目录；
- `checkpoint-84` 表示第 84 步保存的 checkpoint，也就是本次训练结束时的权重。

后续如果要加载微调后的模型，一般就需要使用这个 checkpoint 路径。

### 5.1.6.4 训练结束汇总信息

最后在训练结束时会输出汇总信息：


## 5.2 自定义训练

前面通过快速训练脚本，我们已经跑通了 Qwen3-VL 的 LoRA 微调流程。不过，快速训练主要依赖的是现成数据集，更适合用来验证环境、熟悉参数和理解整体流程。

在真实项目中，我们通常需要根据具体业务场景构造自己的训练数据。例如：

- 做票据识别，让模型读取发票、收据或表格截图；
- 做公式识别，让模型将手写公式转换成 LaTeX；
- 做工业质检，让模型判断图片中是否存在缺陷；
- 做医学影像辅助描述，让模型生成结构化报告；
- 做视频理解，让模型总结视频内容或回答相关问题。

这些任务虽然形式不同，但本质上都需要我们提前整理好图片、视频以及对应的标注结果，并将它们转换成模型可以读取的训练格式。

因此，从这一节开始，我们不再只使用现成数据集，而是尝试手动构造一个简单的自定义数据集，并将其用于后续微调。需要说明的是，本节仍然以演示为主，目标是帮助大家理解自定义数据集的组织方式和训练接入流程；在真实项目中，通常还需要准备更大规模、更高质量的数据。

### 5.2.1 VLM 微调数据格式

ms-swift 支持使用 JSONL 格式组织训练数据。JSONL 的意思是：文件中的每一行都是一个完整的 JSON 对象，每一行表示一条训练样本。

最简单的纯文本样本如下：

```text
{"messages": [{"role": "user", "content": "浙江的省会在哪？"}, {"role": "assistant", "content": "浙江的省会在杭州。"}]}

```

这类数据和普通大语言模型 SFT 数据类似，只有用户问题和助手回答。

如果样本中包含图片，就需要在用户输入中用 `<image>` 作为图片占位符，并在同一条 JSON 中通过 `images` 字段提供图片路径：

```text
{"messages": [{"role": "user", "content": "<image><image>两张图片有什么区别？"}, {"role": "assistant", "content": "前一张是小猫，后一张是小狗。"}], "images": ["/xxx/x.jpg", "/xxx/x.png"]}

```

这里有两个 `<image>` ，因此 `images` 列表中也需要提供两张图片路径。它们是一一对应的关系：第一个 `<image>` 对应 `images` 中的第一张图，第二个 `<image>` 对应 `images` 中的第二张图。

如果样本中同时包含图片和视频，也可以按照类似方式组织：

```text
{"messages": [{"role": "system", "content": "你是一个有用无害的助手。"}, {"role": "user", "content": "<image>图片中是什么？<video>视频中是什么？"}, {"role": "assistant", "content": "图片中是一头大象，视频中是一只小狗在草地上奔跑。"}], "images": ["/xxx/x.jpg"], "videos": ["/xxx/x.mp4"]}

```

这里的核心规则可以总结为三点：

第一， `messages` 用来保存对话内容，通常至少包含一条 `user` 消息和一条 `assistant` 消息。

第二，图片和视频不是直接写进文本里，而是在文本中用 `<image>` 、 `<video>` 作为占位符，再通过 `images` 、 `videos` 字段提供真实文件路径。

第三，占位符数量要和文件列表数量一致。文本里有几个 `<image>` ， `images` 里就应该有几个路径；文本里有几个 `<video>` ， `videos` 里就应该有几个路径。

对于本节的公式识别任务，我们希望模型看到一张手写公式图片，然后输出对应的 LaTeX 公式。因此一条训练样本可以设计成下面这样：

```text
{"messages": [{"role": "user", "content": "<image>请识别图片中的手写数学公式，并输出对应的 LaTeX 表达式。"}, {"role": "assistant", "content": "\\frac{x+1}{y-2}"}], "images": ["/root/autodl-tmp/datasets/latex_ocr_custom/images/000001.png"]}

```

这个样本中：

- 用户输入包含一张图片；
- 图片内容是一条手写公式；
- 助手回答是这条公式对应的 LaTeX 表达式。

这就是一个典型的图像到文本微调样本。

### 5.2.4 转换为 ms-swift 训练数据

在确认数据集字段之后，接下来就可以正式编写转换脚本了。本节的目标是把 ModelScope 中的 `LaTeX_OCR:human_handwrite` 数据集转换成本地的 ms-swift 训练数据。

整体思路可以分成四步：

- 第一步，加载原始数据集，并自动识别图片字段和 LaTeX 标注字段；
- 第二步，将数据集中的图片保存到本地 `images/` 目录；
- 第三步，将每条样本整理成 ms-swift 支持的多模态 JSONL 格式；
- 第四步，按照一定比例划分训练集和验证集，分别保存为 `train.jsonl` 和 `val.jsonl` 。

转换完成后，我们希望得到如下结构：

```text
/root/autodl-tmp/datasets/latex_ocr_custom/
├── images/
│   ├── 000000.png
│   ├── 000001.png
│   └── ...
├── train.jsonl
└── val.jsonl

```

其中， `images/` 用来保存公式图片， `train.jsonl` 用作训练集， `val.jsonl` 用作验证集。

那为了实现该操作，首先需要新建脚本 `build_latex_ocr_swift_dataset.py` ，并写入以下代码：

```python
import json
import os
import random
import shutil
from pathlib import Path

from PIL import Image
from modelscope.msdatasets import MsDataset

# =========================
# 1. 路径配置
# =========================

DATASET_NAME = "AI-ModelScope/LaTeX_OCR"
SUBSET_NAME = "human_handwrite"
SPLIT = "test"

OUTPUT_ROOT = Path("/root/autodl-tmp/datasets/latex_ocr_custom")
IMAGE_DIR = OUTPUT_ROOT / "images"
TRAIN_FILE = OUTPUT_ROOT / "train.jsonl"
VAL_FILE = OUTPUT_ROOT / "val.jsonl"

MAX_SAMPLES = 50
VAL_RATIO = 0.1

IMAGE_FIELD_CANDIDATES = ["image", "img", "file", "image_path", "path"]
TEXT_FIELD_CANDIDATES = ["text", "latex", "formula", "label", "caption"]

# =========================
# 2. 工具函数
# =========================

def find_field(sample, candidates):
    for field in candidates:
        if field in sample and sample[field] is not None:
            return field
    raise KeyError(f"无法从字段 {list(sample.keys())} 中找到候选字段：{candidates}")

def save_image(image_obj, save_path):
    """将不同形式的图片对象保存成本地图片文件。"""
    save_path.parent.mkdir(parents=True, exist_ok=True)

    if isinstance(image_obj, Image.Image):
        image_obj.convert("RGB").save(save_path)
        return

    if isinstance(image_obj, str):
        if os.path.exists(image_obj):
            shutil.copy(image_obj, save_path)
            return
        raise ValueError(f"图片路径不存在：{image_obj}")

    if isinstance(image_obj, dict):
        if "path" in image_obj and os.path.exists(image_obj["path"]):
            shutil.copy(image_obj["path"], save_path)
            return
        if "bytes" in image_obj:
            with open(save_path, "wb") as f:
                f.write(image_obj["bytes"])
            return

    raise TypeError(f"暂不支持的图片字段类型：{type(image_obj)}")

def build_one_record(image_path, latex_text):
    """构造一条 ms-swift 多模态 SFT 数据。"""
    return {
        "messages": [
            {
                "role": "user",
                "content": "<image>请识别图片中的手写数学公式，并输出对应的 LaTeX 表达式。"
            },
            {
                "role": "assistant",
                "content": str(latex_text).strip()
            }
        ],
        "images": [str(image_path)]
    }

def write_jsonl(records, file_path):
    file_path.parent.mkdir(parents=True, exist_ok=True)
    with open(file_path, "w", encoding="utf-8") as f:
        for record in records:
            f.write(json.dumps(record, ensure_ascii=False) + "\n")

# =========================
# 3. 主流程
# =========================

def main():
    OUTPUT_ROOT.mkdir(parents=True, exist_ok=True)
    IMAGE_DIR.mkdir(parents=True, exist_ok=True)

    dataset = MsDataset.load(
        DATASET_NAME,
        subset_name=SUBSET_NAME,
        split=SPLIT
    )

    print("原始样本数量：", len(dataset))

    first_sample = dataset[0]
    image_field = find_field(first_sample, IMAGE_FIELD_CANDIDATES)
    text_field = find_field(first_sample, TEXT_FIELD_CANDIDATES)

    print("自动识别图片字段：", image_field)
    print("自动识别标注字段：", text_field)

    records = []
    sample_num = min(MAX_SAMPLES, len(dataset))

    for idx in range(sample_num):
        sample = dataset[idx]

        image_obj = sample[image_field]
        latex_text = sample[text_field]

        image_path = IMAGE_DIR / f"{idx:06d}.png"
        save_image(image_obj, image_path)

        record = build_one_record(image_path, latex_text)
        records.append(record)

    random.seed(42)
    random.shuffle(records)

    val_size = max(1, int(len(records) * VAL_RATIO))
    val_records = records[:val_size]
    train_records = records[val_size:]

    write_jsonl(train_records, TRAIN_FILE)
    write_jsonl(val_records, VAL_FILE)

    print("转换完成！")
    print("训练集样本数：", len(train_records))
    print("验证集样本数：", len(val_records))
    print("训练集路径：", TRAIN_FILE)
    print("验证集路径：", VAL_FILE)
    print("图片目录：", IMAGE_DIR)
    print("示例样本：")
    print(json.dumps(train_records[0], ensure_ascii=False, indent=2))

if __name__ == "__main__":
    main()

```

然后运行脚本：

```text

```

运行成功后，可以看到类似输出：

### 5.2.5 自定义数据制作时的注意事项

制作 VLM 训练数据时，需要重点检查以下几个问题。

第一，图片路径必须存在。因此 JSONL 文件中的 `images` 字段建议使用绝对路径，例如：

```text
"images": ["/root/autodl-tmp/datasets/latex_ocr_custom/images/000001.png"]

```

不要只写相对路径，否则在不同工作目录下启动训练时，程序可能找不到图片。

第二， `<image>` 数量必须和 `images` 数量一致。例如下面这条数据是错误的：

```text
{"messages": [{"role": "user", "content": "<image><image>请比较两张图。"}, {"role": "assistant", "content": "第一张是公式 A，第二张是公式 B。"}], "images": ["/root/a.png"]}

```

因为文本里有两个 `<image>` ，但 `images` 里只有一张图片。正确做法是提供两个图片路径。

第三，回答内容要尽量稳定、规范。

以公式识别为例，如果希望模型输出 LaTeX，就尽量让所有 assistant 回答都只输出 LaTeX，不要一部分样本输出解释，一部分样本只输出公式。训练数据格式越统一，模型越容易学到稳定的输出模式。

第四，小样本训练只适合演示，不适合得出严肃效果结论。

本节中我们只取了几十条样本进行训练，主要目的是验证微调流程和数据格式。真正要让模型明显提升某个任务能力，需要更多样本、更高质量标注，以及严格的训练集、验证集、测试集划分。

第五，不要一开始就解冻视觉模块。对于入门实验来说，建议先保持：

```text
--freeze_vit true
--freeze_aligner true

```

也就是先冻结视觉编码器和视觉-语言对齐模块。等确认 LoRA 训练流程稳定后，再考虑是否解冻部分模块进行更深入的多模态适配。

### 5.2.6 自定义数据集训练脚本

自定义数据集准备完成后，就可以在前面快速训练脚本的基础上做一个小改造：不再使用 ModelScope 上的远程数据集名称，而是让 `--dataset` 和 `--val_dataset` 指向我们刚刚生成的本地 JSONL 文件。

也就是说，本节训练使用的是：

```text
--dataset "$TRAIN_DATA"
--val_dataset "$VAL_DATA"

```

其中， `TRAIN_DATA` 指向训练集 `train.jsonl` ， `VAL_DATA` 指向验证集 `val.jsonl` 。这样做的好处是数据完全可控，后续只需要替换图片和标注内容，就可以迁移到自己的业务任务中。

接下来就可以新建脚本 `train_qwen3_vl_lora_custom.sh` ，写入以下内容：

```python
#!/bin/bash

# =========================
# 1. 基础路径配置
# =========================

MODEL_PATH="/root/autodl-tmp/qwen3-vl-2b-instruct"

TRAIN_DATA="/root/autodl-tmp/datasets/latex_ocr_custom/train.jsonl"
VAL_DATA="/root/autodl-tmp/datasets/latex_ocr_custom/val.jsonl"

export MODELSCOPE_CACHE="/root/autodl-tmp/modelscope_cache"
export HF_HOME="/root/autodl-tmp/hf_cache"
export HF_DATASETS_CACHE="/root/autodl-tmp/hf_cache/datasets"
export HF_HUB_CACHE="/root/autodl-tmp/hf_cache/hub"

OUTPUT_DIR="/root/autodl-tmp/output/qwen3-vl-2b-lora-custom-latex-ocr"

mkdir -p "$MODELSCOPE_CACHE"
mkdir -p "$HF_DATASETS_CACHE"
mkdir -p "$HF_HUB_CACHE"
mkdir -p "$OUTPUT_DIR"

# =========================
# 2. 显存与多模态输入配置
# =========================

export PYTORCH_CUDA_ALLOC_CONF="expandable_segments:True"
export IMAGE_MAX_TOKEN_NUM=1024
export VIDEO_MAX_TOKEN_NUM=128
export FPS_MAX_FRAMES=16
export CUDA_VISIBLE_DEVICES=0

# =========================
# 3. 启动自定义数据集 LoRA 微调
# =========================

swift sft \
    --model "$MODEL_PATH" \
    --dataset "$TRAIN_DATA" \
    --val_dataset "$VAL_DATA" \
    --load_from_cache_file true \
    --tuner_type lora \
    --torch_dtype bfloat16 \
    --num_train_epochs 1 \
    --per_device_train_batch_size 1 \
    --per_device_eval_batch_size 1 \
    --learning_rate 1e-4 \
    --lora_rank 8 \
    --lora_alpha 32 \
    --target_modules all-linear \
    --freeze_vit true \
    --freeze_aligner true \
    --gradient_checkpointing true \
    --vit_gradient_checkpointing false \
    --gradient_accumulation_steps 2 \
    --eval_steps 10 \
    --save_steps 10 \
    --save_total_limit 2 \
```

## 6.2 模型量化

完成 LoRA 合并之后，模型已经可以作为一个完整模型单独加载和推理。不过在实际部署时，我们还会遇到另一个很现实的问题，那就是模型体积和显存占用仍然比较大。

因此，模型合并之后通常还可以继续考虑量化。所谓量化，可以简单理解为在尽量减少模型效果损失的前提下，把模型中的部分参数从更高精度的数据格式压缩到更低精度的数据格式中，从而降低模型体积、显存占用，并在部分推理框架中提升推理速度。

不过需要注意的是，量化并不是一个对所有模型都通用的“压缩按钮”。它能不能成功，不仅取决于 `ms-swift` 是否提供了对应参数，也取决于底层量化库、模型架构、模型类型以及推理框架是否支持。尤其是 Qwen3-VL 这类视觉语言模型，它的结构比普通文本大模型更复杂，因此并不是所有文本模型上常见的量化方法都能直接套用。

### 6.2.1 ms-swift 中常见的量化方式

在 `ms-swift` 中，常见的量化方式大致可以分成两类：一类是训练或推理时的加载量化，另一类是导出阶段的模型量化。

加载量化通常是指在加载模型时通过低比特方式减少显存占用，例如在 QLoRA 训练中经常使用的 4bit 加载。这类方式更多用于“让模型训得动、跑得动”，不一定会导出一个真正独立的低比特模型。

导出量化则更接近部署场景。它通常是在模型已经训练完成、LoRA 已经合并之后，再通过 `swift export` 对模型进行后训练量化，生成一个新的量化模型目录。

在 `ms-swift` 的导出命令中，比较常见的量化方法包括：

- `awq` ：常见的 4bit 权重量化方法，很多文本大模型部署中会使用；
- `gptq` ：另一类常见的 4bit 后训练量化方法，也主要用于文本大模型；
- `fp8` ：将部分权重或计算表示转换为 FP8 精度，常用于新一代 GPU 和推理框架中的高效推理；
- `bnb` ：基于 bitsandbytes 的低比特加载方式，常用于 QLoRA 训练或低显存推理；
- `hqq` 、 `eetq` 、 `quanto` 等：属于其他量化后端或实验性量化方案，具体可用性同样依赖模型和环境支持。

也就是说，从参数层面看， `ms-swift` 提供的量化入口是比较丰富的。但在真实实验中，我们不能只看参数是否存在，还要看当前模型是否被底层量化库支持。

### 6.2.2 VLM 量化需要额外注意的问题

对于普通文本大模型来说，AWQ、GPTQ 这类 INT4 量化方式已经比较常见。但对于 Qwen3-VL 这类视觉语言模型，情况会复杂一些。

这是因为 VLM 不只是一个单纯的语言模型，它通常还包含视觉编码器、视觉特征投影模块、多模态输入处理逻辑以及语言模型主体。量化工具如果只适配了普通文本大模型，就可能无法正确识别 VLM 的模型结构。

虽然在文档中显示对于多模态模型已经支持包括 FP8 、GPTQ 和 AWQ 等量化方法。然而在实际对合并后的 Qwen3-VL 模型执行 AWQ 4bit 量化时发现当前环境并不能顺利完成，报错显示核心原因是相关量化后端暂时还不支持 `qwen3_vl` 这种模型类型。

![](https://picx.zhimg.com/v2-23368b8607c8e8abeabaed6b59b26ced_r.jpg)

也就是说，这不是路径写错，也不是校准数据集参数写错，而是当前量化方法和 Qwen3-VL 模型结构之间存在兼容性问题。

### 6.2.3 FP8 量化实战

因此在本实验中，我们不再强行使用 AWQ 或 GPTQ，而是选择使用最通用的 FP8 量化作为 Qwen3-VL 的量化演示路线。

我们可以新建脚本 `quant_qwen3_vl_fp8.sh` ，用于对合并后的模型进行 FP8 量化。

```python
#!/bin/bash

# =========================
# 1. 路径配置
# =========================

# LoRA 合并后的完整模型路径
MODEL_PATH="/root/autodl-tmp/output/qwen3-vl-2b-lora-custom-latex-ocr-merged"

# FP8 量化模型输出目录
OUTPUT_DIR="/root/autodl-tmp/output/qwen3-vl-2b-lora-custom-latex-ocr-fp8"

# 校准数据路径
CALIB_DATA="/root/autodl-tmp/datasets/latex_ocr_custom/train.jsonl"

# =========================
# 2. 环境配置
# =========================

export CUDA_VISIBLE_DEVICES=0
export PYTORCH_CUDA_ALLOC_CONF="expandable_segments:True"

# 控制视觉输入 token 数，避免量化校准阶段占用过高显存
export IMAGE_MAX_TOKEN_NUM=1024
export VIDEO_MAX_TOKEN_NUM=128
export FPS_MAX_FRAMES=16

# =========================
# 3. FP8 量化导出
# =========================

swift export \
    --model "$MODEL_PATH" \
    --quant_method fp8 \
    --dataset "$CALIB_DATA" \
    --quant_n_samples 32 \
    --quant_batch_size 1 \
    --max_length 2048 \
    --output_dir "$OUTPUT_DIR"

```

保存脚本后执行：

```text
bash quant_qwen3_vl_fp8.sh

```

这里几个参数需要重点说明：

- `--model` ：指向前面已经完成 LoRA 合并的模型目录，而不是原始基础模型目录；
- `--quant_method fp8` ：表示使用 FP8 方式进行量化；
- `--dataset` ：指定校准数据，量化过程中会用这些样本统计模型激活或权重分布；
- `--quant_n_samples 32` ：表示使用 32 条样本进行校准。教学实验中可以先设置得小一些，减少运行时间和显存压力；
- `--quant_batch_size 1` ：单卡环境下建议设为 1，更稳妥；
- `--max_length 2048` ：限制校准时的最大序列长度，避免输入过长导致显存溢出；
- `--output_dir` ：指定量化后模型的保存目录。

### 7.2.1 云端测试

服务启动后，我们可以先在云服务器内部进行一次 API 调用测试。也就是说，测试脚本和模型服务运行在同一台云服务器上，此时客户端可以直接访问本机的 `6006` 端口：

```text
base_url="http://127.0.0.1:6006/v1"

```

这里需要注意， `127.0.0.1` 表示当前这台服务器自身。也就是说，请求不会经过公网，而是在云服务器内部直接访问已经启动的模型服务。

接下来新建脚本 `test_qwen3_vl_api.py` ：

```python
import base64
from openai import OpenAI

client = OpenAI(
    api_key="EMPTY",
    base_url="http://127.0.0.1:6006/v1"
)

def image_to_data_url(image_path: str) -> str:
    with open(image_path, "rb") as f:
        b64 = base64.b64encode(f.read()).decode("utf-8")
    return f"data:image/jpeg;base64,{b64}"

img = image_to_data_url("/root/VLM/tiger.jpeg")

resp = client.chat.completions.create(
    model="qwen3-vl-2b-local",
    messages=[
        {
            "role": "user",
            "content": [
                {"type": "image_url", "image_url": {"url": img}},
                {"type": "text", "text": "请详细描述这张图片里的主要内容。"}
            ]
        }
    ],
    max_tokens=256,
    temperature=0
)

print(resp.choices[0].message.content)

```

然后在终端运行脚本：

```text
python test_qwen3_vl_api.py

```

如果终端能够正常返回图片描述结果，就说明模型服务已经可以通过 OpenAI 兼容接口在云服务器内部正常调用。

这里有两个地方需要重点确认。

第一，云端本机测试时， `base_url` 应该指向本机地址：

```text
base_url="http://127.0.0.1:6006/v1"

```

其中， `127.0.0.1` 表示当前服务器自身。虽然服务启动时可能使用的是 `0.0.0.0` ，但 `0.0.0.0` 主要用于服务端监听所有网卡，并不是客户端访问时使用的具体地址。

第二，调用时填写的模型名称必须和部署时设置的服务模型名称一致：

```text
model="qwen3-vl-2b-local"

```

它对应部署命令中的：

```text
--served_model_name qwen3-vl-2b-local

```

## 8. 测评与上传

完成训练、合并、量化和部署之后，最后还需要做两件事：一是对模型进行简单测评，观察模型效果是否符合预期；二是将模型上传到 ModelScope，方便后续复用、部署或分享。

## 8.1 模型测评

在真实项目中，模型训练完成后，不能只验证它“能不能正常跑起来”，还需要进一步观察两个问题：

第一，模型经过微调之后，目标任务能力是否真的发生变化；第二，模型经过量化之后，效果是否出现明显退化。

因此，这里可以使用 `ms-swift` 提供的 `swift eval` 命令，对模型进行一次快速基准测评。使用前可以先安装测评相关依赖：

```text
pip install ms-swift[eval] -U

```

需要说明的是，本节测评主要用于流程验证和简单对比，并不能代表模型的真实能力。

### 8.1.1 原始模型测评

首先，我们可以对 LoRA 合并后的模型进行一次简单测评，作为后续对比的基准：

```text
CUDA_VISIBLE_DEVICES=0 \
swift eval \
    --model /root/autodl-tmp/output/qwen3-vl-2b-lora-custom-latex-ocr-merged \
    --eval_backend Native \
    --infer_backend vllm \
    --eval_limit 10 \
    --eval_dataset gsm8k \
    --eval_dataset_args '{"gsm8k": {"few_shot_num": 0}}' \
    --eval_generation_config '{"max_tokens": 128, "temperature": 0}' \
    --extra_eval_args '{"ignore_errors": true}' \
    --vllm_gpu_memory_utilization 0.6 \
    --vllm_max_model_len 8192

```

这里使用的是 `gsm8k` 数据集，它主要用于测试模型的数学推理能力。并且由于 EvalScope 里支持该数据集，因此这里的 `eval_backend` 设置为 `Native` ：

![](https://pica.zhimg.com/v2-b450457b22f0ca8dd7a2a9bcab36f742_r.jpg)

假如要使用其他数据集的话，可以考虑通过 OpenCompass 或 VLMEvalKit 实现：

![](https://picx.zhimg.com/v2-0205bcc2697d9c8598cde6734adba4e5_r.jpg)

另外，为了节省时间，示例中通过 `--eval_limit 10` 只抽取 10 条样本进行快速测试，用来减少测评时间。

> 与前面讲解 EvalScope 不同的是，这里并不是直接通过普通 Transformers 方式逐条推理，而是使用 `vllm` 作为推理后端先拉起一个 API 服务。 `swift eval` 会调用对应推理后端完成批量测评，因此整体速度通常会比单纯使用 Transformers 逐条生成更快。 
> 

本次返回结果如下：

![](https://pic1.zhimg.com/v2-1af0a765e5f8cfebc4293e6c8d474568_r.jpg)

从结果来看，模型在 `gsm8k` 上表现并不好。不过这也比较符合预期：我们当前使用的是 Qwen3-VL 2B 视觉语言模型，并且本节微调任务是手写公式 OCR，而不是通用数学推理增强。因此， `gsm8k` 更适合作为一个快速流程测试集，而不是评价本模型真实任务能力的核心指标。

### 8.1.3 对比量化模型与原始模型

接下来，为了观察 FP8 量化是否对模型效果造成明显影响，可以继续对量化后的模型执行同样的测评命令：

```text
CUDA_VISIBLE_DEVICES=0 \
swift eval \
    --model /root/autodl-tmp/output/qwen3-vl-2b-lora-custom-latex-ocr-fp8 \
    --eval_backend Native \
    --infer_backend vllm \
    --eval_limit 10 \
    --eval_dataset gsm8k \
    --eval_dataset_args '{"gsm8k": {"few_shot_num": 0}}' \
    --eval_generation_config '{"max_tokens": 128, "temperature": 0}' \
    --extra_eval_args '{"ignore_errors": true}' \
    --vllm_gpu_memory_utilization 0.6 \
    --vllm_max_model_len 8192

```

这里仍然使用 `vllm` 作为推理后端。原因是 FP8 量化模型更依赖推理框架支持，普通 Transformers 推理方式未必能够直接稳定加载和运行 FP8 模型。

本次返回结果显示：

![](https://pic3.zhimg.com/v2-6805f568bbbdc2242afa9a9a08431c7c_r.jpg)

表面上看，FP8 模型的结果甚至比合并后的原始模型更好。不过这里不能简单得出“FP8 量化提升了模型能力”的结论。因为当前只测试了 10 条样本，样本数量太少，结果很容易受到题目抽样、生成稳定性、评测判定等因素影响。

不过这也可以看出，在这次小规模快速测试中，FP8 量化模型没有表现出明显不可用或严重退化的问题。

如果要进行更严谨的模型评估，应该扩大样本数量，并结合具体任务选择更合适的测试集。比如本节训练目标是手写公式识别，那么更合理的评估方式应该是准备一批没有参与训练的公式图片，让模型输出 LaTeX 表达式，再和标准答案进行对比。
