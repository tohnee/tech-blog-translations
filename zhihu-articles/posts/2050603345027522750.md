每当新的大模型或者新的大模型版本发布后，我们第一时间关注的一般都是大模型的“ **推理能力** ”。但是，反过来讲，现阶段的大模型的推理能力到底来源何处？他们是否真的拥有推理能力？

其实，如果把“推理模型”定义为： <u>能通过多步分解、反思、自我纠错、增加推理时计算来提高复杂任务正确率的模型</u> ，那么o系列、DeepSeek-R1、Gemini Thinking这类模型，已经可以算是推理模型。

但如果把“推理”定义为： **<u>具备稳定的因果理解、形式逻辑一致性、可验证的中间状态、可迁移的抽象规则和可靠的世界模型</u>** ，那么现在的大模型还不是。更准确的说法是：当前的大模型是“ **基于语言token的神经近似推理器** ”，或者说是“ **学出来的启发式搜索系统** ”，而不是传统意义上的逻辑推理机。

## **大模型的推理能力来源何处？**

大模型本质上是自回归的Transformer：通过给定的上下文来预测下一个token。它不是先天带着逻辑规则、证明系统、因果图谱去运行的。但从o1、o3、DeepSeek-R1之后，模型不再是“直接回答”，而是被训练成先在内部生成较长的思考轨迹，再输出答案。OpenAI 在o1技术说明里明确提到， <u>o1的能力会随着更多训练时强化学习计算和更多推理时思考时间提升，并且会学习分解问题、识别错误、修正策略、换方法求解</u> 。

![](https://pic2.zhimg.com/v2-e35025b05bb79941bd3d4235ecbc72f1_r.jpg)

从技术上说，当前大模型的推理并不是像数学证明器那样通过公理和规则进行推导，从而得到结论。它更像是针对问题生成若干可能的解决路径，之后在语言空间中展开中间步骤，根据训练中学到的模式和奖励偏好选择更可能正确的路径，最终输出答案。这有点像人做题时打草稿，但又不完全一样。人类的草稿背后有物理直觉、因果经验、目标意识和现实反馈，而模型的“草稿”本质上还是token序列。因此， <u>大模型的推理不是硬逻辑推理，而是 **概率生成+模式匹配+隐式搜索+自我修正** 的混合体。</u>

那么，它为什么还不能算“真正意义”的推理模型？关键在于它的推理过程不一定忠实、稳定、可验证。首先，Chain of Thought不一定是真实原因。研究发现，模型生成的推理可能只是事后合理化。也就是说，它嘴上说“我是这样推出来的”，但真正影响答案的因素可能是别的，比如选项顺序、提示偏置、训练记忆等。此外，它仍然容易走捷径。大模型可能依赖数据中的表面相关性，而不是掌握了真正的抽象规则。Shortcut learning相关研究指出，大模型在某些任务上会利用数据偏差和非鲁棒特征，导致泛化能力被高估。

![](https://pica.zhimg.com/v2-56b8d976ca9942d46da543ffc4dffcc4_r.jpg)

同时，它的抽象推理和组合推理仍不稳。多项测试表明，大模型在自然语言任务上很强，但面对需要严格组合关系、抽象模式迁移、复杂约束保持的问题时，仍会出现明显失败。

![](https://pic4.zhimg.com/v2-48f28cc71cf7c13468c56dc7763909e1_r.jpg)

最主要的是，大模型没有天然的“证明状态”。数学证明器、SAT 求解器、规划器都有明确状态和约束检查；大模型的中间过程主要藏在激活和token轨迹里。除非接入verifier、代码执行器、形式化工具，否则它很难保证每一步都可靠。

因此， **现在的大模型已经具备工程意义上的推理能力，但还没有达到强定义下的真正推理系统** 。

## **如何训练一个具有真正推理能力的模型？**

那么我们如何设计或者训练一个具有真正意义上的“推理能力”的模型呢？真正推理模型的核心是 **给定一个问题，模型能把问题转成内部状态，拆解目标，执行中间操作，检查每一步是否合法，发现错误后回退，并在分布外场景中仍能保持规则一致** 。

## **一、改变训练目标：把模型训练成“会回答”变成“会求解”**

大模型的训练目标是：

![](https://pic3.zhimg.com/v2-81e0c9594cbfee8d42f198cb6eba4432_1440w.jpg)

即根据已有上下文预测下一个 token。如果要训练真正的推理模型，目标函数要改成：

![](https://pica.zhimg.com/v2-303c4501d1c310c9e36171e2b42c78b2_1440w.jpg)

其中，a_t是下一步的推理动作；s_t是当前问题状态。

也就是说，模型不应该只学“下一句话怎么写”，而应该学“下一步怎么处理”。普通大模型学的是 **文本续写分布，而** 真正推理模型要学的是 **问题状态转移分布** 。这也是OpenAI o1、DeepSeek-R1这类reasoning model的核心启发：它们并不是只靠prompt让模型“慢慢想”，而是通过强化学习和推理时计算，让模型在复杂任务中学会花更多计算进行多步求解。

## **二、给模型添加一个“推理状态空间”**

这是我觉得最关键的一层。现在的大模型推理多是在一维token流里模拟草稿，从题目到思考步骤到中间结果再到最终答案。问题是，题干、约束、变量、假设、结论全混在同一个上下文里，模型容易出现条件遗忘、变量混淆等各种问题。

所以可以考虑给模型设计一个显式状态空间，把一次推理过程表示为：

```text
State = {
  Problem: 原始问题，
  Constraints: 约束集合，
  Variables: 变量表，
  Scratchpad: 草稿步骤，
  Claims: 已产生的中间命题，
  Tools: 工具执行结果，
  Verifier: 当前校验状态，
  Goal: 最终目标
}
```

然后模型每一步不是直接生成答案，而是在状态空间里选择动作：

```text
Action = {
  Decompose: 拆解子问题，
  Derive: 推导一个中间命题，
  Compute: 调用计算器 / 程序 / 符号引擎，
  Prove: 尝试证明某个命题，
  Check: 校验当前步骤，
  Revise: 修改错误步骤，
  Backtrack: 回退到某个历史状态，
  Answer: 输出最终答案
}
```

这样，模型从“文本生成器”变成了“状态机选择”的的策略模型。它的训练目标也从生成一段漂亮答案变为选择下一步最优推理动作。

## **三、构建校验器（Verifier）**

真正推理模型必须有独立verifier，可以分三类：一是 **结果校验器，用于校验** 比如答案对不对，代码能不能跑通，定理证明能不能被Lean接受。Lean是一个开源证明助手，可以用于形式化验证数学和程序正确性。二是 **过程校验器，看每一步是否合法。例如Step_i是否由前置条件推出、是否引入了未声明假设、是否和已有结论矛盾等。三是策略校验器，** 判断模型当前的解题路线是否合理。例如是否应该先分类讨论、是否遗漏边界条件、是否需要调用工具、是否应该尝试反证法等。

推理时，模型生成多个候选路径，verifier负责筛选和淘汰。这也是为什么“模型推理”不能只靠prompt，必须有外部或独立的评价信号。

## **四、单路生成进化为多路搜索**

大模型的生成方式是单路自回归：

```text
token1 → token2 → token3 → token4 → ...
```

这很像一条路走到黑，但真正推理是需要试错的。所以推理时应该从“单路生成”升级为“多路搜索”。

最简单可以用 **Best-of-N** ，首先生成N条解法路径，然后使用verifier打分后，选最高分。

进一步是 **Tree of Thoughts（思维树，ToT）** ，每一步不是生成一个token，而是生成一个“思考节点”，每个节点可以继续扩展多个子节点，搜索树中保留高价值分支，剪掉错误分支。Tree of Thoughts论文明确指出，传统语言模型被限制在从左到右的token级决策中，容易在需要探索、前瞻和全局选择的任务中失败；ToT通过多条推理路径、自评估和回溯来增强复杂问题求解能力。

![](https://pica.zhimg.com/v2-ca7709ee2983aeadb991730b3b73fc5e_r.jpg)

更强一点的话可以用 **MCTS** ，这时模型不再是“直接输出答案”，而是变成一个搜索策略：

![](https://picx.zhimg.com/v2-8d3a8631cc84e024ef2660adebe4ced7_1440w.jpg)

verifier或reward model则近似价值函数：

![](https://pic2.zhimg.com/v2-c8c126763afbacd37a2c292df050c409_1440w.jpg)

这就很接近AlphaZero那套思想了，模型负责提出动作，搜索负责探索，评价器负责筛选。

## **五、强化学习不再奖励“说得像”，而是“推得对”**

现在很多模型的问题是回答很像推理，但实际上不一定真的对。所以强化学习阶段的奖励函数要重写。不要再奖励语言流畅、格式漂亮等，而是奖励步骤可验证、工具调用合理、结论和约束一致等情况。可以设计一个混合奖励函数：

![](https://picx.zhimg.com/v2-307f375a788a890849ec58e654163e69_r.jpg)

其中，R_answer是最终答案正确，R_process是每一步推理合法，R_verify是主动调用校验器并通过，R_backtrack是发现错误后能回退修正，R_generalization是换数字、换场景、换表述后仍然正确，R_shortcut是跳步、猜测、硬套模板则惩罚。

这和普通RLHF不一样，RLHF更偏“人类觉得这个回答好不好”，而推理的RL更应该偏“这个状态转移是否合法、这个结论是否可验证”。DeepSeek-R1的一个重要启发就是推理能力可以通过RL被明显激发出来，而不是完全依赖人工写好的推理样本。但R1-Zero也暴露出问题，比如可读性差、语言混杂，所以真实训练中仍需要冷启动数据、多阶段训练和格式约束。

![](https://picx.zhimg.com/v2-a7c4f2486ffb6e8c2bec0c5746eb5d5d_r.jpg)

**六、模型原生化实现“可验证操作”**

真正推理模型不应该死靠神经网络心算，实际上，数学计算、代码执行、逻辑证明、数据库查询、仿真计算等操作本来就应该交给工具来实现。但是，关键不是模型“能调用工具”，而是把工具调用变成推理状态的一部分。比如模型生成一步：

```text
Action: SolveEquation
Input: 2x + 3 = 11
Tool: SymPy
Output: x = 4
Verifier: passed
```

这个结果不能只是普通文本拼回上下文，而应该写入状态：

```text
Action: SolveEquation
Input: 2x + 3 = 11
Tool: SymPy
Output: x = 4
Verifier: passed
```

这样因为状态里已经有verified fact，模型后续就不能随便改写：

```text
x = 5
```

这就是“ **工具原生化（Tool-Native）** ”的含义，不是说一定要把工具做进Transformer参数里，而是要让工具输出具备更高可信等级，进入模型的工作记忆和verifier链路。DeepMind的AlphaGeometry就是典型的神经符号路线。它把语言模型和符号推理引擎结合起来，在奥赛几何问题上取得了接近人类金牌水平的表现。DeepMind后续的AlphaProof和AlphaGeometry 2在2024年IMO问题上达到银牌标准该方案在严格推理任务上非常有价值。

![](https://picx.zhimg.com/v2-6c46eee80efae42dd7540c829552c759_r.jpg)

**Transformer的状态化、动作化、校验化、工具化、搜索化**

根据我们前文的一些思考和设想，那么典型的Transformer是不是也可以做一些改变，让其从“Token序列建模器”变为“状态感知的推理策略网络”。

经典的Transformer学的是：

![](https://pica.zhimg.com/v2-574f438f73e307c86241aedef65fa552_1440w.jpg)

现在我们把它变为：

![](https://pic1.zhimg.com/v2-e36fd1fadf75e8da93b8d588c5ba79be_1440w.jpg)

我们改变的根本目的是想把Transformer从之前把所有信息都压缩到一条token流，改进为具有推理意识的工作流。典型的Transformer输入简单，即Token embedding+位置编码（Position encoding），但现在输入具备了显示的状态空间：

```text
State = {
  Problem,
  Constraints,
  Variables,
  Scratchpad,
  Claims,
  Tools,
  Verifier,
  Goal
}
```

所以输入层不能再只区分Token的位置，还要区分token的状态。因此可以改成：

```text
Token Embedding
+ Position Embedding
+ State-Type Embedding
+ Segment Embedding
+ Trust-Level Embedding
```

其中，State-Type Embedding表示token属于Problem、Constraints、Variables、Scratchpad、Claims、Tools、Verifier、Goal等哪一类，Segment Embedding区分题干区、约束区、草稿区、工具结果区、答案区等，Trust-Level Embedding则区分普通文本、模型猜测、工具返回结果、Verifier已验证事实等。

如此，比如如果x=4来自模型猜测，那只是一个普通的claim，但如果来自SymPy求解，并且verifier passed，那它应该被标记为Verified Fact，后续模型就不能随便改成x=5。因此，输入的改动是让Transformer一开始就知道哪些是题目，哪些是约束，哪些是草稿，哪些是事实。

类似的，Transformer的上下文也是一条线：

```text
[x1, x2, x3, ..., xt]
```

但推理不适合这种结构，因为题干、约束、变量、草稿、结论混在一起，模型容易忘条件、混变量、错把假设当事实。所以应该把上下文改成分区结构：

```text
[Problem 区]      原始问题，只读
[Constraints 区] 约束条件，只读或高可信
[Variables 区]   变量表，可更新
[Scratchpad 区]  草稿推导，可修改
[Claims 区]      中间命题，可验证
[Tools 区]       工具结果，高可信
[Verifier 区]    校验状态，高可信
[Answer 区]      最终输出，只在最后写入
```

对应到Transformer里就是修改attention mask。普通的causal mask是让当前位置只能看前面的token。改进后则变为：

```text
草稿区可以看题干区、约束区、变量区
答案区必须看草稿区、校验区、工具区
题干区不能被后续草稿覆盖
Verifier 区必须能读取完整推理链
工具结果区写入后具有高可信权重
```

也就是说，注意力不再只是时间顺序控制，而是状态权限控制。这会让Transformer从“续写文本”变成“读写工作区”。

Transformer 的核心是多头自注意力机制：

![](https://pic4.zhimg.com/v2-36c50ebb052e6cb5e5e6211b1841c401_r.jpg)

它本质上是在算 token 之间的相关性，但是推理不只需要“相关性”，还需要变量、约束等绑定，以及前后步骤一致性、工具结果优先级、已验证事实优先级、与原始题干是否冲突等。

所以 attention score 可以加入一个额外的逻辑偏置项：

![](https://pica.zhimg.com/v2-fffd8234314346cd495fa9c6419ccce8_r.jpg)

其中，B_{state}是状态分区偏置，比如草稿区必须强关注约束区，B_{logic}是逻辑关系偏置，比如同一变量、同一命题、依赖关系增强，B_{trust}是可信度偏置，比如工具验证结果、Lean 证明结果优先级更高。

这样，自注意力机制就不再只是“语义相似度注意力”，而是变成语义相关性+状态关系+逻辑依赖+可信度控制了。可以把多头注意力拆成几类专用头：

```text
Content Head：普通语义理解
Constraint Head：专门关注题干约束
Variable Head：追踪变量绑定
Claim Head：追踪中间命题
Tool Head：读取工具结果
Verifier Head：读取校验状态
```

正常，attention后面就需要FFN，做通用非线性转换。但推理任务里，不同操作类型差异很大，不同的动作不应该完全共用同一套FFN。可以把 FFN 改成Gated FFN/MoE，即：

```text
Gated FFN = Router(Action-Type) → Expert_i
```

不同专家负责不同推理功能：

```text
Decompose Expert：问题拆解
Derive Expert：逻辑推导
Compute Expert：计算表达式构造
Prove Expert：证明路径生成
Check Expert：错误检测
Revise Expert：修正错误步骤
Backtrack Expert：定位回退点
Answer Expert：组织最终回答
```

这样，Transformer 内部不再是一个单一的语言生成网络，而是具备多个“推理技能子网络”。这和MoE的思想很接近，但路由依据不是普通语义，而是推理动作类型。

之后，输出头也需要改变，从一个LM Head改成多头结构：

```text
Action Head：预测下一步动作 a_t
Argument Head：生成动作参数
Verifier Head：预测当前步骤是否可靠
Tool Router Head：决定是否调用工具
Value Head：估计当前状态价值 V(s_t)
Language Head：必要时生成自然语言
```

其中， L_LM是自然语言生成能力，L_action是下一步推理动作预测，L_state是状态更新是否正确，L_verify是步骤校验是否正确，L_tool是工具选择和工具参数是否正确，L_value是当前状态价值估计是否准确。

**结语**

当本文更多是一种纸上谈兵式的技术设想，并不是说现有的大模型一定要沿着这条路线演进，也不是说真正的推理模型已经有了确定答案。但至少可以看到，当前以生成式为核心的大模型，在复杂任务、长链路任务、强约束任务中依然存在明显局限。未来的大模型发展，大概率不会只停留在“参数更大、语料更多、上下文更长”这条路上，而是会进一步走向推理型研发，让模型不只是会回答，而是实现可验证推理的能力。
