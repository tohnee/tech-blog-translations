最近扒拉了扒拉整个代码。

这是一个微软推出的 Transformer 模型的前向推理框架。

比较香的点是，这个框架可以把一个很大的模型分到多块卡（多机）上去跑。比如当你手头有个 150G+ 显存占用的模型，同时你最大卡的显存只有 24G 的卡，不过有很多块卡，那么如果有这种框架就很香，随便跑。

## 疑问点

- 框架是怎么做到的这种并行的？

---

有两个工程，[DeepSpeed-MII](https://github.com/microsoft/DeepSpeed-MII) [DeepSpeed](https://github.com/microsoft/DeepSpeed-MII) 。两个编译都都一样也很容易，

```text
pip install -v . 
```

或者直接安装官方版本更方便：

```text
pip install deepspeed
pip install deepspeed-mii
```

然后按主页提示就能用了，[官方（传说中）的四句话就能跑](https://github.com/microsoft/DeepSpeed-MII#non-persistent-pipeline)。

```text
import mii
pipe = mii.pipeline("mistralai/Mistral-7B-v0.1")
response = pipe(["DeepSpeed is", "Seattle is"], max_new_tokens=128)
print(response)
```

当然四句话保存成 example.py

```text
deepspeed --num_gpus 2 mii-example.py
```

如果阅读代码的话，你会发现 MII 是个壳，主要封装了服务 api。

核心并行机制都在 DeepSpeed 里。

## 机制：

看推理之前，我们先看一下训练。

DeepSpeed 实现的 ZeRO ，出发点也是为了减少显存使用，跨机器跨节点进行更大模型的训练。一般的是按层切分模型分别载入参数，**看起来好像是模型并行**。但是**运行时其实质则是数据并行**方式，不同的数据会在不同的卡运行，且同一组数据一般会在一块卡上完成全部前向和后向过程。而被切分的参数和梯度等数据会通过互联结构在运行态共享到不同节点，只是复制出的数据用后即焚删除了，不再占用空间。

这里有一段[动图](https://www.microsoft.com/en-us/research/blog/zero-deepspeed-new-system-optimizations-enable-training-models-with-over-100-billion-parameters/)画的比较清晰。

![](https://pic1.zhimg.com/v2-145e05075831ece0553d65a577daaab4_r.jpg)
*例如，反向传播时，M2机器上计算的它所分几层的梯度、更新等等数据都会由M2机器分发给M013几台机器，然后每台机器根据自己机器的数据块分别计算。同理，其他步骤时均是如此，这里不展开了。*

![](https://pic3.zhimg.com/v2-d2c6ab7c0b7a78fd3081ec0496dda97e_r.jpg)
*官方针对训练过程的示意图*

现在我们来看推理过程，区别是首先我们不需要考虑数据在哪，另外整个过程没有反向传播不需要考虑计算梯度。

打个比方，一个 80 层模型 150G 的参数，一块 24G 的卡放不下，但是如果有 8 块卡，每块卡 18.75G 是可以放下的。

**现在的问题是，怎么切？**

*要么横着切要么竖着切。*

还是按前面的 ZeRO 数据并行方式切，这个模型有 80 层，可以切成 8 组，一张卡 10 层，但是头一张卡没跑完之前后边的卡都得等着，这个显然不好，甚至还不如单卡排队一组一组跑。同时，假如有些模型的计算图本身不规则，不一定能平均分，会造成每一组都不均匀。

*这样切也行，但是太不优雅了。*

DeepSpeed 在推理中则按另一个方式切，即张量并行方式切分。具体到每一层中间，该层中非常耗时耗空间的矩阵乘法，会被平均切到了每一块卡上，如下图所示独立载入参数并单独运行计算，每一层所有节点都结束时通过 all_reduce 操作汇总数据，完成同步，再开始下一层的计算，以此类推。图中分割线上方是一块足够大的卡正常运行模型时的流程，下方是切好之后的运行方式。

![](https://pic3.zhimg.com/v2-7d4e814ca3482cfba6d6b0a80dbe8db4_r.jpg)
*随手画了一下它的逻辑结构图，回头再改好看点*

这样汇总数据的操作和一些比较小规模的层，都可以留在主节点上运行，可并行的参数量计算量大的计算就可以交给并行处理的卡了。并且更重要的是，这样切分的话可以保证基本的均匀。而均匀的好处就是能够让多卡协调之间相互等待的时间片段尽量短。同时可以叠加后续的流水线并行方法，并且流水粒度更小。

这是一种典型的**基于张量并行的模型并行**方法。

相比串行切分模型的方式，这个方法操作粒度更低，小 batch 的时候也可以做到很小的设备空闲，同时可以应对不同的输入向量长度等等。不过潜在的压力是，all_reduce 时的数据流量很大，多机时可能带来较大的带宽挑战。

## 代码实现：

DeepSpeed 的工程实现中，这个机制的实现还是很优雅的。

**数据加载：**

首先每个 GPU 卡都会先计算自己 partition 的 Transformer container，放在 container map 里面，这个类明确了自己需要载入的参数部分，会按 tensor parallel (tp_size) 先来切好。

每个 GPU 卡都会把整个 checkpoint 的结构加载进来，这里在日志输出的时候很有迷惑性，好像它把整个参数都载入到了每块卡上，其实不然，这里只加载了结构。数据加载（flatten_inference_model）的时候，才按照前面的container map 中规划好的数据往挨个卡中加载数据。

这应该就是，**预分片的权重仓库**。

**计算部分：**

其实大部分比较小而碎的层，都是在GPU1 也就是主节点（rank0）所在的进程上做的，而较大的 transformer 层在运算时才是分布并行处理的。

all reduce 部分的代码就是直接调用了 backend 的 dist.all_reduce 函数，这个 backend 可以是 torch 的 distributed 库也可能是nccl、mpi等等的库。

这时问题就可以转换为矩阵并行处理的切分问题了。

**工厂类兼容各种模型：**

基于 DSTransformerModelBase 类，DeepSpeed 实现了 llama-v2，mistral，opt 三个模型，对其中的部分模型结构进行了针对性优化，其他模型如果有特殊之处，直接继承父类再实现就好了。

## 实验测试：

单机 8 卡 4090 下比较顺利的就能跑起来 llama2-70b-chat，输出的 max_length 是 128，模型参数载入时间大约在 140s （不包括前续准备环境编译算子等时间），一次完整的推理时间大约在 8.7s ，这个速度暂时还不能说的上是很快，应该是有其他的环境因素形成的瓶颈。更多对比测试以后会慢慢补上来。
