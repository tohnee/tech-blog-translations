### 一、基础概念题（Q1-Q6）

### Q1：什么是 LLM 推理？为什么 LLM 推理比训练难？

**问题**：什么是 LLM 推理？为什么 LLM 推理比训练更具挑战性？

**考察点**：自回归解码的本质、推理与训练的区别、推理的特殊挑战。

**参考答案**：

LLM 推理（Inference）是用训练好的大语言模型对新输入生成输出的过程。和训练相比，推理有几个本质挑战：

1. **延迟敏感**：训练可以跑几天，推理每个请求要在秒级返回
2. **算力利用率低**：训练是 GPU 满载，推理往往 10-30% 利用率
3. **显存压力大**：要存 KV cache（训练时不需要）
4. **请求动态**：batch 大小、序列长度不可预测
5. **QPS 要求高**：生产环境可能 100+ QPS

**核心挑战**：训练是把矩阵算满，推理是”算一个 token，读一堆历史”，访存密集。**这个差异决定了所有推理优化的方向**。

**追问**：

- Q1.1：为什么 KV cache 占用这么多显存？（答：和序列长度 × 层数 × 头数线性增长）
- Q1.2：decode 阶段为什么算力利用率低？（答：访存密集，每个 token 要读所有历史的 K、V，但只算 1 个 token）
- Q1.3：prefill 和 decode 有什么本质区别？（答：见 Q2）

### Q2：什么是 LLM 推理的 prefill 和 decode 阶段？

**问题**：LLM 推理有 prefill 和 decode 两个阶段，它们的区别是什么？

**考察点**：自回归解码的细节、两个阶段的算力模式。

**参考答案**：

LLM 自回归解码分两个本质不同的阶段：

**Prefill（预填充）**：

- 输入：完整的 prompt（如 4096 token）
- 一次 forward 算出所有 token 的 K、V
- 算力密集（compute-bound），GPU 利用率 90%+
- 单次耗时 50-200ms（7B 模型，4096 token）

**Decode（解码）**：

- 输入：1 个新 token + 历史 K、V
- 一次 forward 只算 1 个 token 的 K、V
- 访存密集（memory-bound），GPU 利用率 10-30%
- 单次耗时 30ms 左右（取决于历史长度）

**关键差异**：

| 维度 | Prefill | Decode |
| --- | --- | --- |
| 单次算的 token 数 | 全部 prompt | 1 个 |
| 算力模式 | 算力密集 | 访存密集 |
| GPU 利用率 | 90%+ | 10-30% |
| 耗时 | 50-200ms | 30ms |

**这两个阶段用同一台机器 = 互相干扰**——这正是 Disaggregated Inference 想解决的问题（见 Q29）。

**追问**：

- Q2.1：为什么 decode 阶段是访存密集？（答：每个新 token 要 attend 到所有历史 K、V，但 QKV 计算本身很小，所以算力被访存瓶颈限制）
- Q2.2：能不能把 prefill 和 decode 一起做？（答：可以，这就是 Chunked Prefill 的核心思想）
- Q2.3：能不能把多个 decode 一起做？（答：可以，这就是 Continuous Batching 的核心思想）

### Q3：什么是 KV Cache？为什么需要它？

**问题**：什么是 KV Cache？为什么推理需要它？

**考察点**：自回归解码的冗余、KV Cache 的本质、显存占用。

**参考答案**：

KV Cache 是把 Transformer 推理时每一步的 K（Key）和 V（Value）缓存起来，避免重复计算。

**为什么需要它**：

自回归解码时，每一步都要算”当前 token 对历史的 attention”。如果不缓存，每步都要重新算所有历史的 K、V：

```text
不缓存:
step 1: forward([BOS, query]) → 算全部 K、V → 生成 "我"
step 2: forward([BOS, query, 我]) → 重新算全部 K、V → 生成 "同"
step 3: forward([BOS, query, 我, 同]) → 重新算全部 K、V → 生成 "意"
...
每次 O(n²) 算力
```

**缓存后**：

```text
缓存:
step 1: forward([BOS, query]) → 算 K、V，存 KV cache → 生成 "我"
step 2: forward([我]) → 只算 1 个新 K、V，存进 cache → 生成 "同"
step 3: forward([同]) → 只算 1 个新 K、V，存进 cache → 生成 "意"
...
每步 O(1) 算力
```

**显存占用**：

```text
单 token KV = 2 (K, V) × num_layers × num_heads × head_dim × dtype_bytes

Llama-2-70B, FP16, 80 层, 128 头, head_dim=128:
单 token = 2 × 80 × 128 × 128 × 2 = 5 MB
4096 token: 5 MB × 4096 = 20 GB
```

**这就是为什么 KV cache 显存管理是 LLM 推理的核心问题**。

**追问**：

- Q3.1：KV cache 显存和模型权重比，比例如何？（答：70B 模型，权重 140GB，KV cache 20GB/千 token——KV cache 容易超过权重）
- Q3.2：能不能不要 KV cache？（答：理论上可以，但每次重新算 K、V 会让延迟从 30ms 涨到 30s+，不可接受）
- Q3.3：KV cache 量化能省多少？（答：FP16 → INT8 省 50%，到 INT4 省 75%，但要小心精度损失）

### Q4：什么是连续批处理（Continuous Batching）？它和 Static Batching 有什么区别？

**问题**：什么是 Continuous Batching？和 Static Batching 相比有什么优势？

**考察点**：调度层核心概念、为什么 vLLM 比 HuggingFace 快。

**参考答案**：

**Static Batching**（传统方案）：

```text
时刻 0: 接收 10 个请求 → 组成 batch
时刻 1: 10 个请求各生成第 1 个 token
...
时刻 50: 9 个请求生成 50 token 后完成
时刻 50: 但 batch 必须等其他请求，最长那个 2000 token 后才完成
时刻 2000: batch 释放
```

**问题**：90% 的 GPU 算力在”等待”最长的请求——浪费严重。

**Continuous Batching**（vLLM 方案）：

```text
时刻 1: 10 个请求各生成第 1 个 token
时刻 1: 完成 1 个，**立即从 batch 移除**
时刻 1: 新请求 11 加入 batch
时刻 2: 继续生成，完成 1 个，加入新请求
...
```

**核心**：每一步迭代后，调度器重新决定”下一批跑什么”。

**收益**（vLLM 论文实测）：

| 调度 | 吞吐 | P99 TTFT |
| --- | --- | --- |
| Static | 1800 tok/s | 8500ms |
| Continuous | 5200 tok/s | 380ms |

吞吐提升 **2.9x**，P99 TTFT 降低 **95%**。

**追问**：

- Q4.1：Continuous Batching 的实现难点是什么？（答：抢占、chunked prefill、spec decode、multi-modal 都要适配）
- Q4.2：所有请求都等长时，Continuous Batching 还有用吗？（答：基本没用，Continuous Batching 收益主要来自”请求长度差异大”的场景）
- Q4.3：vLLM 是怎么实现的？（答：每个请求维护 num_computed_tokens 状态，每步调度重新选择）

### Q5：什么是 PagedAttention？它解决了什么问题？

**问题**：什么是 PagedAttention？它解决了什么核心问题？

**考察点**：vLLM 的核心创新、显存管理。

**参考答案**：

**PagedAttention**（Kwon et al., SOSP 2023）是 vLLM 的核心创新，**借鉴操作系统虚拟内存的分页思想**来管理 KV cache。

**传统问题**（HuggingFace 风格）：

- 给每个请求预分配 `max_seq_len` 长度的连续 KV cache 显存
- 实际只用了 10-30%，但占着的不能动
- 显存利用率 20-40%

**PagedAttention 的解法**：

把 KV cache 切成固定大小的 block（默认 16 token），用 block table 做”逻辑到物理”的间接寻址：

```text
逻辑视图（请求看到）: [0..16][16..32][32..48][48..64]...
物理视图（实际存储）: block 17, block 42, block 8, block 91...
Block Table: R: [17, 42, 8, 91]
```

**类比**：

| 操作系统 | vLLM |
| --- | --- |
| 虚拟页 | KV block（16 token） |
| 页表 | Block Table |
| TLB | Block Table 缓存 |
| 缺页中断 | Block 分配 |

**收益**：

- 显存利用率从 20-40% 提升到 80-95%
- 最大并发数从 4-6 提升到 20+（70B 模型）
- 内部碎片最多 1 个 block（< 6%）
- 零外部碎片

**追问**：

- Q5.1：block_size 选多大合适？（答：默认 16，详见 Q5）
- Q5.2：为什么不能直接用 FlashAttention？（答：FlashAttention 假设 KV 连续，PagedAttention 要自定义 kernel）
- Q5.3：PagedAttention 和 Paging 内存的关系？（答：直接借鉴，思路完全一致）

### Q6：vLLM 比 HuggingFace Transformers 快多少？为什么？

**问题**：vLLM 比 HuggingFace Transformers 推理快多少？为什么？

**考察点**：vLLM 的综合性能、为什么能赢。

**参考答案**：

vLLM 比 HuggingFace Transformers 快 **2-4x**（典型场景），部分场景 **10x+**。

**为什么快**（三大核心优化）：

1. **PagedAttention**：显存利用率从 20-40% 提升到 80-95%<br>

- 同等显存能跑更多并发
- 吞吐线性提升

1. **Continuous Batching**：消除 batch 之间的”等待气泡”<br>

- 短请求不再被长请求阻塞
- 吞吐提升 2-3x

1. **PagedAttention + Prefix Caching**：复用跨请求的 KV<br>

- 多轮对话节省 50%+ prefill
- TTFT 降低 50%+

**实测数据**（Llama-2-7B，A100）：

| 方案 | 吞吐 (tok/s) | P99 TTFT |
| --- | --- | --- |
| HF Transformers | 1500 | 4500ms |
| TGI (HF 优化版) | 2400 | 2800ms |
| vLLM v0.7 | 5200 | 380ms |
| vLLM + Prefix Cache | 5800 | 200ms |

**vLLM 比 HF 快 3.5-5x 的核心**：不是单个优化”特别强”，而是三个优化**叠加协同**。

**追问**：

- Q6.1：vLLM 在哪些场景下优势最大？（答：长 prompt + 多轮对话 + 高并发）
- Q6.2：vLLM 在哪些场景下优势小？（答：单请求短 prompt、低 QPS、模型 < 7B）
- Q6.3：vLLM 和 TensorRT-LLM 比谁快？（答：TensorRT-LLM 在 NVIDIA 硬件上略快，但 vLLM 生态更好、迭代更快）

### 二、PagedAttention 原理题（Q7-Q12）

### Q7：Block Table 的数据结构是什么？怎么用？

**问题**：vLLM 的 Block Table 是什么数据结构？怎么用？

**考察点**：PagedAttention 的核心数据结构。

**参考答案**：

**Block Table 是”逻辑位置 → 物理 block ID”的映射**：

```text
# CPU 侧：Python 对象
block_table_cpu = {
    "req_1": [17, 42, 8, 91, ...],   # 物理 block ID 列表
    "req_2": [23, 56, 71, 102, ...],
    ...
}

# GPU 侧：扁平化的 int32 tensor
block_table_gpu = torch.tensor([
    [17, 42, 8, 91, 0, 0, ...],     # req_1 的物理 block
    [23, 56, 71, 102, 0, 0, ...],   # req_2 的物理 block
], dtype=torch.int32, device='cuda')
```

**形状**：`[num_reqs, max_blocks_per_seq]`，padded 到统一长度。

**怎么用**：

在 attention 计算时，CUDA kernel 通过 block_table 做”间接寻址”：

```text
// 简化版 CUDA kernel
__global__ void paged_attention_kernel(
    const half* K_cache,        // [num_blocks, block_size, num_kv_heads, head_dim]
    const int* block_table,     // [num_reqs, max_blocks]
    ...
) {
    int req_id = blockIdx.y;
    int block_idx = ...;  // 循环变量
    
    // ★ 关键：通过 block_table 找物理 block
    int physical_block_id = block_table[req_id * max_blocks + block_idx];
    
    // 加载这个物理 block 的 K、V
    const half* K_block = K_cache + physical_block_id * block_size * num_kv_heads * head_dim;
    
    // 算 attention
    ...
}
```

**关键设计**：

- 物理 block 可以**分散在显存各处**（不需要连续）
- block_table 是个**轻量级**结构（每个 req 几十个 int32）
- 间接寻址在 GPU 上**几乎没成本**（寄存器级）

**追问**：

- Q7.1：block_table 数组的最大长度怎么决定？（答：取决于 `max_model_len / block_size`）
- Q7.2：PagedAttention 怎么和 FlashAttention 配合？（答：vLLM 0.5+ 把 PagedAttention 的”分页”和 FlashAttention 的”算法”解耦）
- Q7.3：block_table 频繁更新会不会影响性能？（答：block_table 只在分配新 block 时更新，attention 计算时是只读）

### Q8：PagedAttention 的 hash 链是怎么实现的？为什么要用 parent hash？

**问题**：PagedAttention 的 prefix cache 用 hash 链，怎么实现？为什么要用 parent hash？

**考察点**：prefix cache 的正确性、hash 链设计。

**参考答案**：

**Hash 链实现**（`vllm/v1/core/kv_cache_utils.py`）：

```text
def compute_block_hash(
    block_tokens: list[int],  # 这个 block 内的 token
    parent_hash: BlockHash | None,  # 前一个 block 的 hash
    hash_fn: Callable,
) -> BlockHash:
    # 把 parent_hash + block_tokens 序列化
    h = hash_fn((parent_hash, block_tokens))
    return BlockHash(h)
```

**为什么要用 parent hash**：

考虑两个场景：

**场景 1：相同内容、不同位置**

```text
请求 1: `[A, B, C, D]` `[E, F, G, H]`
请求 2: `[I, J, K, L]` `[E, F, G, H]`
```

两个请求的第二个 block 内容相同（`[E, F, G, H]`），但**位置不同**（一个在中部、一个在末尾）。

**纯内容 hash 会错误命中**——vLLM 设计就是为了避免：

- 请求 1 的 block 1 hash = hash(block0_hash, `[E, F, G, H]`)
- 请求 2 的 block 1 hash = hash(block0’_hash, `[E, F, G, H]`)
- 因为 block0_hash ≠ block0’_hash，所以两个 block hash 不同 → **不会错误命中**

**场景 2：相同前缀**

```text
请求 1: `[A, B, C, D]` `[E, F, G, H]` `[I, J, K, L]`
请求 2: `[A, B, C, D]` `[E, F, G, H]` `[M, N, O, P]`
```

- 请求 1 的 block 1 hash = hash(hash(`[A,B,C,D]`), `[E,F,G,H]`)
- 请求 2 的 block 1 hash = hash(hash(`[A,B,C,D]`), `[E,F,G,H]`) ← **相同！**

✓ **正确命中**。

**parent hash 保证了 prefix cache 的”上下文正确性”**——只有**内容相同 + 前缀相同**的 block 才能命中。

**追问**：

- Q8.1：为什么不用简单的字符串 hash？（答：字符串 hash 不能保证”上下文正确性”，会产生 false positive 命中）
- Q8.2：hash 函数怎么选？（答：默认 xxhash，速度快且可重现）
- Q8.3：多模态输入怎么参与 hash？（答：vLLM 0.6+ 把图片 embedding 也参与 hash 计算）

### Q9：PagedAttention 的 block_size 怎么选？为什么默认 16？

**问题**：PagedAttention 的 block_size 应该选多大？为什么 vLLM 默认 16？

**考察点**：工程权衡、实测数据。

**参考答案**：

**block_size 选择的三个约束**：

1. 必须整除 `max_seq_len`
2. 必须整除 `max_num_batched_tokens`
3. 显存”浪费率”权衡

**实测数据**（Llama-2-7B，A100，ShareGPT 流量）：

| block_size | P50 TTFT | P99 TTFT | 吞吐 (tok/s) | 显存利用率 | prefix cache 命中率 |
| --- | --- | --- | --- | --- | --- |
| 8 | 88ms | 380ms | 5300 | 92% | 78% |
| 16 (默认) | 90ms | 395ms | 5200 | 88% | 75% |
| 32 | 95ms | 420ms | 5000 | 80% | 70% |
| 64 | 110ms | 480ms | 4700 | 65% | 60% |

**为什么默认 16**：

- **block_size=8**：更细粒度，命中率略高，但元数据开销大
- **block_size=16**：各项指标均衡，是 sweet spot
- **block_size>=32**：元数据开销小，但 hash 粒度粗、命中率下降

**选 block_size 的建议**：

```text
block_size=8:  大量短 prompt（< 1000 token）+ 极致碎片敏感
block_size=16: 大多数业务场景（默认）
block_size=32: 超长 prompt（> 32K）+ 想减少元数据
block_size>=64: 不推荐
```

**追问**：

- Q9.1：能动态调整 block_size 吗？（答：vLLM 当前不支持，但未来可能）
- Q9.2：不同请求能用不同 block_size 吗？（答：vLLM 0.7+ 支持多 group KV cache，可以不同）
- Q9.3：为什么不用 1？（答：元数据开销太大，KV cache hash 粒度太细）

### Q10：PagedAttention 和 FlashAttention 是什么关系？

**问题**：PagedAttention 和 FlashAttention 是什么关系？

**考察点**：澄清常见误解。

**参考答案**：

**误解**：PagedAttention 是 FlashAttention 的替代品。

**真相**：两者是不同维度的优化，**互补**。

| 维度 | FlashAttention | PagedAttention |
| --- | --- | --- |
| 解决问题 | 单个 attention 的访存效率 | 多个请求的显存管理 |
| 优化对象 | 单个 attention 计算 | 整个推理服务的 KV cache |
| 解决的事 | attention matrix 物化开销 | KV cache 碎片 |
| 时间点 | 2022 | 2023 |

**vLLM 中两者的关系**：

```text
PagedAttention = 分页显存管理 + FlashAttention 风格的高效计算
                        ↑                  ↑
                  Block Table        Online Softmax
```

在 vLLM 0.5+ 中，**PagedAttention 的”分页”**和**FlashAttention 的”tiling + online softmax”**被解耦，分别由不同模块负责：

- **Block Table 间接寻址**（PagedAttention 的核心）
- **FlashAttention 算法**（高效 attention 计算）
- **结合**：vLLM 0.5+ 后的 vllm_flash_attn fork

**vLLM 的”现代 PagedAttention”** = Block Table 间接寻址 + FlashAttention 风格的高效计算。

**追问**：

- Q10.1：vLLM 0.5 之前是怎么实现的？（答：完全自研的 CUDA kernel，~2000 行）
- Q10.2：vLLM 的 flash attention fork 有什么不同？（答：支持 block_table 间接寻址 + GQA + sliding window 等 vLLM 特性）

### Q11：vLLM 怎么把 PagedAttention 嫁接到 FlashAttention 上？

**问题**：vLLM 是怎么把 PagedAttention 的”分页”和 FlashAttention 的”算法”结合的？

**考察点**：vLLM 0.5+ 的架构演进。

**参考答案**：

**vLLM 0.5 之前**（v0.1-v0.4）：完全自研的 CUDA kernel

```text
csrc/attention/attention_kernels.cuh  # ~2000 行自定义 kernel
```

支持多种 dtype、多种 head size、多种 block size、多种并行策略。代码复杂，性能也 OK，但维护成本高。

**vLLM 0.5+ 的关键重构**：

**核心思想**：把”分页”和”算法”解耦

```text
PagedAttention 的"分页" →  Block Table 间接寻址（轻量级）
FlashAttention 的"算法" →  Tiling + Online Softmax（重计算）
```

**实现方式**：

1. **Block Table 间接寻址**：在 attention kernel 之前，把物理 K、V 按 block 加载到 shared memory
2. **Shared Memory 内的连续 attention**：用 FlashAttention 风格算法
3. **多 block 合并**：用 online softmax 合并多个 block 的结果

**vllm_flash_attn 模块**（`vllm/vllm_flash_attn/`）：

- vLLM 维护的 FlashAttention fork
- 专为 vLLM 适配：支持 block_table、GQA、sliding window 等

**关键函数**：

```text
# vllm/v1/attention/backends/flash_attn.py
output = flash_attn_varlen_func(
    q=q,
    k_cache=K_cache,    # 所有 block 共享的 K 缓存
    v_cache=V_cache,    # 所有 block 共享的 V 缓存
    block_table=block_table,  # 物理 block 列表
    cu_seqlens_q=cu_seqlens_q,  # 序列边界
    cu_seqlens_k=cu_seqlens_k,
    max_seqlen_q=max_seqlen_q,
    max_seqlen_k=max_seqlen_k,
    ...
)
```

**`flash_attn_varlen_func`** 内部调用 PagedAttention kernel（带 block_table 间接寻址），结合了 FlashAttention 的算法。

**追问**：

- Q11.1：vLLM 为什么 fork FlashAttention 而不是直接用？（答：直接用 FlashAttention 不支持 block_table，vLLM 维护 fork 可以定制）
- Q11.2：未来会不会有”分页 + FlashAttention”的更优解？（答：可能有，比如 Mamba-based attention、linear attention）
- Q11.3：vLLM 的 PagedAttention 比 TensorRT-LLM 的方案差吗？（答：性能上略差，但生态和迭代速度领先）

### Q12：PagedAttention 在 GPU 上到底怎么用？写一段伪代码

**问题**：PagedAttention 在 GPU 上是怎么用 block_table 的？能写一段伪代码吗？

**考察点**：源码级理解。

**参考答案**：

GPU 上 PagedAttention 的核心是**自定义 CUDA kernel**：

```text
// 简化版 CUDA kernel
template <typename scalar_t>
__global__ void paged_attention_kernel(
    const scalar_t* __restrict__ q,          // [num_heads, head_size]
    const scalar_t* __restrict__ k_cache,    // [num_blocks, block_size, num_kv_heads, head_size]
    const scalar_t* __restrict__ v_cache,
    const int* __restrict__ block_table,     // [num_reqs, max_blocks]
    const int context_len,
    float* __restrict__ output,
    ...
) {
    // 1. 当前 thread block 负责 (head, kv_block) 子任务
    const int head_idx = blockIdx.x;
    const int kv_head_idx = head_idx / (num_heads / num_kv_heads);
    const int batch_idx = blockIdx.y;
    
    // 2. 加载当前请求的 block_table
    const int* req_block_table = block_table + batch_idx * max_blocks;
    
    // 3. 加载 Q（一个 token）
    // ...
    
    // 4. 遍历 KV blocks（★ 关键：间接寻址）
    float max_score = -INFINITY;
    float sum_exp = 0.0f;
    
    for (int kv_block_idx = 0; kv_block_idx < num_kv_blocks; kv_block_idx++) {
        // 通过 block_table 找物理 block
        const int physical_block_id = req_block_table[kv_block_idx];
        
        // 计算这个物理 block 的地址
        const scalar_t* K_block = k_cache 
            + physical_block_id * block_size * num_kv_heads * head_size
            + kv_head_idx * head_size;
        const scalar_t* V_block = v_cache 
            + physical_block_id * block_size * num_kv_heads * head_size
            + kv_head_idx * head_size;
        
        // 计算这个 block 的 attention 子结果
        // (online softmax 累加)
        // ...
    }
    
    // 5. 输出
    // ...
}
```

**关键点**：

1. **每个 thread block 处理一个 (batch, head, kv_block) 的子任务**
2. **通过 block_table 做”间接寻址”**——这是 PagedAttention 的本质
3. **Online softmax 合并**——避免物化完整 attention matrix
4. **GQA 优化**——多个 Q head 共享一个 KV head

**vLLM 0.5+ 的实现**：用 `vllm_flash_attn::flash_attn_varlen_func` 调用，把”分页”和”算法”结合。

**追问**：

- Q12.1：每个 block 处理 16 token 的 K、V，shared memory 装得下吗？（答：装得下，16 × 128 × 2 byte = 4KB，远小于 shared memory 限制）
- Q12.2：为什么用 online softmax？（答：避免存完整 attention matrix，参考 FlashAttention 论文）
- Q12.3：能不能用更小的 block？（答：能，但元数据开销会增大，详见 Q9）

### Q13：vLLM v1 引擎的进程模型是什么？为什么要分多个进程？

**问题**：vLLM v1 引擎的进程模型是什么？为什么要分多个进程？

**考察点**：vLLM 整体架构理解。

**参考答案**：

vLLM v1 引擎由 **3 个进程**组成：

**进程 1：Driver Process（主进程）**

- 跑 `AsyncLLM` 包装类
- 负责：HTTP/请求接入、token 化、OutputProcessor
- **不直接做模型推理**

**进程 2：EngineCore Process（vLLM 引擎核心）**

- Driver 通过 ZMQ spawn 出来
- 跑 `EngineCore` 类（`vllm/v1/engine/core.py`，~1500 行）
- 包含：Scheduler、KVCacheManager、InputProcessor
- 是”调度大脑”
- **不直接做模型推理**

**进程 3：Worker Processes（GPU 工作进程）**

- EngineCore 通过 Executor spawn
- 跑 `Worker` 类（`vllm/v1/worker/gpu_worker.py`）
- 包含：ModelRunner、KV cache 物理存储、TP/PP 通信
- **唯一直接接触 GPU 的进程**

**为什么要分进程**：

1. **模型权重隔离**：Worker 进程可以独立重启，权重保留
2. **GPU context 隔离**：Driver 进程不持有 CUDA context
3. **可扩展性**：未来 EngineCore 可以跑在 CPU 机器、Worker 跑 GPU 机器
4. **故障隔离**：Driver 崩溃时 EngineCore 仍可运行

**追问**：

- Q13.1：Driver 和 EngineCore 怎么通信？（答：ZMQ + msgpack）
- Q13.2：v0 引擎也是分进程吗？（答：v0 是单进程，更简单但没 v1 灵活）
- Q13.3：3 个进程会不会有性能开销？（答：ZMQ 通信有几毫秒延迟，但收益远大于成本）

### Q14：vLLM 一次推理请求的完整生命周期是什么？

**问题**：vLLM 一次推理请求的完整生命周期是什么？

**考察点**：端到端理解。

**参考答案**：

一次 HTTP 请求 `POST /v1/chat/completions` 走过的路径：


### Q16：vLLM 怎么用 Token Budget 限制每轮调度？

**问题**：vLLM 是怎么用 Token Budget 限制每轮调度的？

**考察点**：调度核心抽象。

**参考答案**：

**Token Budget** 是 vLLM v1 调度的核心抽象——限制每轮总共处理多少个 token，而不是限制请求数。

**为什么不用”请求数限制”**：

- 请求长度差异大（有的 100 token，有的 4000 token）
- 简单限制”32 个请求”会导致短请求”白占位置”
- 应该限制”算力消耗”——而 token 数就是算力消耗的代理

**实现**：

```text
# vllm/v1/core/sched/scheduler.py
self.max_num_scheduled_tokens = (
    self.scheduler_config.max_num_scheduled_tokens
    if self.scheduler_config.max_num_scheduled_tokens
    else self.scheduler_config.max_num_batched_tokens
)
# 默认: 2048

def schedule(self):
    token_budget = self.max_num_scheduled_tokens
    
    while req_index < len(self.running) and token_budget > 0:
        request = self.running[req_index]
        
        num_new_tokens = (
            request.num_tokens_with_spec
            + request.num_output_placeholders
            - request.num_computed_tokens
        )
        
        # 不超过 token_budget
        num_new_tokens = min(num_new_tokens, token_budget)
        
        # 累加
        num_scheduled_tokens[request_id] = num_new_tokens
        token_budget -= num_new_tokens
        req_index += 1
```

**关键设计**：

- 一个 4096 token 的 prompt 不会霸占整个 batch
- 多个小请求可以共享一个 batch
- **Chunked Prefill 自动支持**——大 prompt 会被 token_budget 切碎
- Spec decode 的草稿 token 也算入 budget

**调优**：

- `max_num_batched_tokens = 2048`（默认）
- 长 prompt 场景：`4096` 或 `8192`
- 低延迟场景：`1024`

**追问**：

- Q16.1：为什么 Chunked Prefill 能”自然”支持？（答：因为 token_budget 是 token 粒度，不是请求粒度）
- Q16.2：vLLM 0.7+ 还有什么 token 维度的限制？（答：`max_num_seqs` 限制请求数）
- Q16.3：Token Budget 和 max_num_seqs 的关系？（答：实际是两者的”交集”）

### Q18：vLLM 的 ModelRunner 做什么？

**问题**：vLLM 的 ModelRunner 做什么？

**参考答案**：

- **block_table 间接寻址**：attention kernel 用的物理 block 列表

### 四、调度优化题（Q19-Q24）

### Q19：什么是 Chunked Prefill？为什么需要它？

**问题**：什么是 Chunked Prefill？为什么需要它？

**考察点**：调度层核心优化。

**参考答案**：

**Chunked Prefill** 是 vLLM 的关键调度优化：**把长 prompt 切成多个小块，分多次处理**。

**为什么需要它**：

考虑一个 4096 token 的 prompt：

```text
不切块（传统）:
- 一次 forward 算 4096 token
- 耗时 ~200ms
- 在这 200ms 内，decode 请求被暂停
- 所有 decode 请求延迟被拖累

切块（Chunked Prefill）:
- 切成 4 块，每块 1024 token
- 每次 forward 1 块 + decode 请求
- 每次耗时 ~50ms
- decode 请求每 50ms 就能跑一次
- 长 prompt 不会"霸占" GPU
```

**数学正确性**：

K、V 的计算是**逐 token 独立**的，块与块之间没有”跨块依赖”。所以切块前后结果**完全一致**。

**vLLM 实现**：

```text
# vllm/v1/core/sched/scheduler.py
def schedule(self):
    token_budget = self.max_num_scheduled_tokens  # e.g., 2048
    
    while req_index < len(self.running) and token_budget > 0:
        request = self.running[req_index]
        
        num_new_tokens = (
            request.num_tokens_with_spec
            - request.num_computed_tokens
        )
        
        # ★ 关键：长 prefill 强制 chunk
        if 0 < self.scheduler_config.long_prefill_token_threshold < num_new_tokens:
            num_new_tokens = self.scheduler_config.long_prefill_token_threshold
        
        # 不超过 token_budget（自动 chunked）
        num_new_tokens = min(num_new_tokens, token_budget)
        ...
```

**关键参数**：

- `max_num_batched_tokens`：每轮最多多少 token
- `long_prefill_token_threshold`：超过此长度的 prefill 强制 chunk
- `enable_chunked_prefill`：是否启用（默认 True）

**收益**：

- 长 prompt 场景：P99 TTFT 降 50%+
- 混合场景：P50 TTFT 略升（+10-20ms），P99 显著下降（-50%）

**追问**：

- Q19.1：Chunked Prefill 影响最终结果吗？（答：不影响，数学上完全正确）
- Q19.2：什么时候不应该开 Chunked Prefill？（答：业务需要”一个请求必须 prefill 完才能 decode”——极少见）
- Q19.3：vLLM 0.7+ 的 `long_prefill_token_threshold` 怎么用？（答：超过此值的 prefill 强制 chunk）

### Q20：vLLM 的抢占（Preemption）是怎么实现的？为什么选 Recompute？

**问题**：vLLM 的抢占是怎么实现的？为什么选 Recompute 而不是 Swap？

**考察点**：v1 设计哲学。

**参考答案**：

**抢占的实现**（`scheduler.py` 的 `_preempt_request`）：

```text
def _preempt_request(self, request: Request, timestamp: float) -> None:
    """
    Preempt a request and put it back to the waiting queue.
    """
    assert request.status == RequestStatus.RUNNING
    
    # 1. 释放所有 KV block
    self.kv_cache_manager.free(request)
    self.encoder_cache_manager.free(request)
    
    # 2. 重置状态（recompute 策略）
    request.status = RequestStatus.PREEMPTED
    request.num_computed_tokens = 0  # ★ 关键：清空
    if request.spec_token_ids:
        request.spec_token_ids = []
    request.num_preemptions += 1
    
    # 3. 放回 waiting 队首
    self.waiting.prepend_request(request)
```

**两种抢占策略**：

| 策略 | 做法 | 优势 | 劣势 |
| --- | --- | --- | --- |
| Recompute | 释放 KV，下次重新算 | 简单、零 I/O | 长 prompt 浪费时间 |
| Swap | 把 KV 拷到 CPU 内存 | 恢复快 | 复杂、需 CPU 内存 |

**vLLM v1 选 Recompute 的原因**：

1. **v0 的 swap 实现复杂，bug 多**
2. **v1 设计哲学：简洁优于完备**
3. **大多数场景下，Recompute 性能损失可接受**
4. **长 prompt 可以用 prefix cache 加速 Recompute**

**抢占的代价**：

```text
场景: 1000 token prompt + 已生成 500 token 的请求被抢占

成本:
1. 释放 KV block: O(1)
2. 重新 prefill 1000 token: ~50ms (7B)
3. 重新生成 500 token: ~15s (decode)

总成本: ~15.05s
```

**抢占率应该 < 1%**。如果 > 5%，需要排查配置。

**追问**：

- Q20.1：能不能用 Recompute + Swap 混合？（答：v1 取消了 swap，未来可能重新支持）
- Q20.2：抢占的请求会被优先调度吗？（答：是的，vLLM 把被抢占的请求 prepend 到 waiting 队首）
- Q20.3：怎么监控抢占率？（答：看 `vllm:request_preemptions_total`）

### Q21：vLLM v1 调度器为什么取消 prefill/decode 阶段划分？

**问题**：vLLM v1 调度器为什么取消 prefill/decode 阶段划分？

**考察点**：v1 设计哲学。

**参考答案**：

**v0 调度器**：

- 显式区分 prefill 阶段和 decode 阶段
- 不同阶段用不同调度逻辑
- 不能混跑（或混跑代价大）

**v1 调度器**：

- **没有 prefill 阶段，也没有 decode 阶段**
- 每个请求只有 `num_computed_tokens` 和 `num_tokens_with_spec`
- 调度器只关心”让这两个数对得上”

**取消划分的理由**（vLLM 源码注释）：

```text
# vllm/v1/core/sched/scheduler.py
def schedule(self) -> SchedulerOutput:
    # NOTE(woosuk) on the scheduling algorithm:
    # There's no "decoding phase" nor "prefill phase" in the scheduler.
    # Each request just has the num_computed_tokens and
    # num_tokens_with_spec. num_tokens_with_spec =
    # len(prompt_token_ids) + len(output_token_ids) + len(spec_token_ids).
    # At each step, the scheduler tries to assign tokens to the requests
    # so that each request's num_computed_tokens can catch up its
    # num_tokens_with_spec. This is general enough to cover
    # chunked prefills, prefix caching, speculative decoding,
    # and the "jump decoding" optimization in the future.
```

**收益**：

1. **代码简化**：取消两套调度逻辑
2. **Chunked Prefill 自然支持**：不需要特殊处理
3. **Spec Decoding 无缝集成**：spec token 算入 `num_tokens_with_spec`
4. **未来优化空间大**：jump decoding 等新优化不用动调度逻辑

**追问**：

- Q21.1：v0 调度器是怎么分两阶段的？（答：先 decode 后 prefill，或反过来）
- Q21.2：取消阶段划分后，最大的收益是什么？（答：Chunked Prefill + Continuous Batching 自然组合）
- Q21.3：v2 引擎还会保持这个抽象吗？（答：很可能保持，已被验证有效）

### Q22：什么是 AsyncScheduler？vLLM 0.7+ 怎么支持 streaming 输入？

**问题**：什么是 AsyncScheduler？vLLM 0.7+ 怎么支持 streaming 输入？

**考察点**：v1 异步调度。

**参考答案**：

**AsyncScheduler**（`vllm/v1/core/sched/async_scheduler.py`，60 行）是 Scheduler 的子类，**支持 streaming 输入**。

**什么是 streaming 输入**：

传统推理：

```text
请求: prompt → 完成 → 返回
       ^^^^^^^^
       一次性处理完整 prompt
```

Streaming 输入：

```text
请求: chunk1 → chunk2 → chunk3 → 完成 → 返回
       ^^^^^^^^  ^^^^^^^^  ^^^^^^^^
       增量处理 prompt
```

**适用场景**：

- 多轮对话中，用户的输入是”打字中”
- Agent 场景中，下游工具的输出是流式的
- 长文档处理，分块输入

**实现**：

```text
# vllm/v1/core/sched/async_scheduler.py
class AsyncScheduler(Scheduler):
    """支持 streaming 输入的调度器"""
    
    def __init__(self, *args, **kwargs) -> None:
        super().__init__(*args, **kwargs)
    
    def _update_after_schedule(self, scheduler_output):
        # 异步特有的更新逻辑
        # 处理 output placeholders（为未来 token 占位）
        ...
    
    def _update_request_with_output(self, request, new_token_ids, ...):
        # 异步特有：处理 streaming token
        ...
```

**关键差异**：

- `output_placeholders` 的处理：异步调度为未来的 token “占位”
- `is_prefill_chunk` 标记：区分当前是在 prefill chunk 还是 decode

**追问**：

- Q22.1：AsyncScheduler 怎么和 EngineCore 配合？（答：通过 `output_placeholders`）
- Q22.2：异步调度有什么限制？（答：实现复杂，对 LLM 服务框架有要求）
- Q22.3：vLLM 0.7+ 哪个是默认？（答：vLLM 0.7+ 默认是 AsyncScheduler，因为 v1 整体是异步的）

### Q23：vLLM 的优先级抢占怎么实现？默认优先级是什么？

**问题**：vLLM 的优先级抢占怎么实现？默认优先级是什么？

**考察点**：调度的优先级机制。

**参考答案**：

**默认优先级**：

- 所有请求 `priority = 0`（相同）
- FIFO（FCFS）调度

**自定义优先级**：

```text
from vllm import SamplingParams

# VIP 用户
sampling_params = SamplingParams(priority=10)
output = llm.generate(prompts, sampling_params)

# 普通用户
sampling_params = SamplingParams(priority=0)
```

**`priority` 越大越优先**（注意：vLLM 内部是 `-priority` 实现 max-heap）。

**调度策略**：

```text
# vllm/v1/core/sched/request_queue.py
class PriorityRequestQueue(RequestQueue):
    def __init__(self):
        # heapq: (-priority, arrival_time, request)
        # -priority: 大数优先级高（小根堆变成大根堆）
        # arrival_time: 同优先级内按到达时间排
        self._heap = list[Request]()
    
    def add_request(self, request: Request) -> None:
        heapq.heappush(self._heap, (
            -request.sampling_params.priority,
            request.arrival_time,
            request,
        ))
```

**抢占的选择**：

```text
# 默认：选最低优先级的 victim
def _select_victim(self) -> Request:
    return min(
        self.running,
        key=lambda r: r.sampling_params.priority
    )
```

**实际使用建议**：

- 大多数业务不需要改优先级
- 多租户场景（VIP vs 普通用户）可以分级
- 抢占仍然以”低优先级优先被换出”为原则

**追问**：

- Q23.1：priority 是负数会怎样？（答：被 vLLM 内部取反，负数变成”最优先”）
- Q23.2：同 priority 的请求怎么排？（答：按 arrival_time 排，FIFO）
- Q23.3：能不能给某些请求”绝对优先”？（答：可以，但可能导致其他请求饿死）

### Q24：vLLM 的 Multi-Step Processing 是什么？

**问题**：vLLM 的 Multi-Step Processing 是什么？什么时候用？

**考察点**：vLLM 0.7+ 的新优化。

**参考答案**：

**Multi-Step Processing** 是 vLLM 0.7+ 引入的优化：**一次调度跑多步**（在 batch 不变的情况下）。

**传统**：

```text
step 1: schedule() → forward → update
step 2: schedule() → forward → update
step 3: schedule() → forward → update
```

**Multi-Step**：

```text
step 1: schedule() → forward × 3 → update
step 2: schedule() → forward × 2 → update
```

**为什么有用**：

1. **CPU 开销摊薄**：调度器的 Python 开销在多步间分摊
2. **KV cache 访问模式更优**：同一 batch 连续访问
3. **部分 kernel 融合可能**

**配置**：

```text
vllm serve ... --num-lookahead-slots 4  # 一次调度跑 4 步
```

**适用场景**：

- 流量稳定、batch 大
- 流量波动大：反而**增加延迟**（multi-step 等不到 batch 变化）

**实测**：

| 配置 | 吞吐 | CPU 占用 |
| --- | --- | --- |
| num-lookahead=1（默认） | 5200 | 中 |
| num-lookahead=4 | 5400 | 低 |

吞吐提升约 4%，CPU 占用降低——主要是 CPU bound 场景的优化。

**追问**：

- Q24.1：Multi-Step 怎么保证 batch 不变？（答：请求不能进入/退出，K 和 V 全部在 shared memory）
- Q24.2：Multi-Step 和 Spec Decoding 冲突吗？（答：不冲突，但 spec decode 内部已经实现了类似的多步）
- Q24.3：vLLM 默认开 Multi-Step 吗？（答：默认 `num-lookahead-slots=1`，即单步）

### Q26：Tensor Parallel、Pipeline Parallel、Expert Parallel 有什么区别？

**问题**：TP、PP、EP 有什么区别？什么时候用哪个？

**考察点**：并行策略。

**参考答案**：

**Tensor Parallel（TP，张量并行）**：

```text
模型按"层内切分"
- 70B 模型，TP=4：每张卡 17.5B
- 切的是 Linear 层的 weight
- AllReduce 通信
- 适合：单请求延迟敏感
```

**Pipeline Parallel（PP，流水线并行）**：

```text
模型按"层间切分"
- 70B 模型，PP=4：每张卡 17.5B（不同层）
- 切的是 layer
- 流水线气泡
- 适合：吞吐敏感、batch 大
```

**Expert Parallel（EP，专家并行，MoE 专用）**：

```text
模型按"专家切分"
- Mixtral 8x7B，EP=2：每张卡 4 个专家
- 切的是 MoE 的 experts
- AllToAll 通信
- 适合：MoE 模型
```

**对比表**：

| 维度 | TP | PP | EP |
| --- | --- | --- | --- |
| 切分维度 | 层内 | 层间 | 专家 |
| 通信原语 | AllReduce | P2P | AllToAll |
| 通信量 | 高 | 低 | 中 |
| 气泡 | 无 | 有 | 取决于负载 |
| 适合 | 通用 LLM | 大模型 | MoE |
| 上限 | TP ≤ 8 | PP ≤ 8 | 取决于专家数 |

**组合使用**：

```text
# Llama-3-405B（810GB FP16）
vllm serve ... \
  --tensor-parallel-size 8 \
  --pipeline-parallel-size 4 \
  --quantization fp8

# DeepSeek-V2（236B MoE）
vllm serve ... \
  --tensor-parallel-size 4 \
  --enable-expert-parallel
```

**追问**：

- Q26.1：为什么 TP 上限 8？（答：NCCL 通信成为瓶颈）
- Q26.2：PP 怎么减少气泡？（答：用 micro-batching）
- Q26.3：EP 怎么负载均衡？（答：EPLB，vLLM 0.6+ 提供）

### Q29：什么是 Disaggregated Inference？vLLM 怎么实现？

**问题**：什么是 Disaggregated Inference（P/D 分离）？vLLM 怎么实现？

**考察点**：业界前沿架构。

**参考答案**：

**Disaggregated Inference**（P/D 分离）是把 **Prefill** 和 **Decode** 拆到不同机器的架构。

**为什么需要**：

传统 monolithic 架构下，prefill 和 decode 在同一台机器：

- Prefill 跑 200ms 时，decode 请求被暂停
- 显存分配互相挤兑
- 流量高峰时，prefill 长 prompt 阻塞一切

**P/D 分离的架构**：

```text
┌──────────────────┐  ┌──────────────────┐
│  Prefill Server  │  │  Decode Server   │
│  (1× GPU)        │  │  (1× GPU)        │
│                  │──│                  │
│  - 只跑 prefill  │  │  - 只跑 decode   │
└──────────────────┘  └──────────────────┘
   ↑ KV cache 跨节点传输 ↑
```

**vLLM 0.7+ 实现**：

- `kv_connector/v1/` 下有多种 connector：NixL / P2P / Mooncake / LMCache
- `examples/online_serving/disaggregated_serving/` 提供完整 demo
- 0.7+ 引入 PDController（PR 15343）

**KV Connector 接口**：

```text
# vllm/distributed/kv_transfer/kv_connector/v1/base.py
class KVConnectorBase_V1:
    # Scheduler 端
    def get_num_new_matched_tokens(self, request, ...): ...
    def request_finished(self, request, block_ids): ...
    
    # Worker 端
    def start_load_kv(self, request, ...): ...  # 分层加载
    def wait_for_layer_load(self, layer_idx): ...
    def save_kv_layer(self, layer_idx, ...): ...  # 分层保存
    def wait_for_save(self): ...
```

**拓扑**：

- 1P1D：流量 < 30 QPS
- 1PnD：长 prompt + 短输出
- XpYd：流量 > 100 QPS

**实测收益**（Llama-3.1-8B，2×H100 prefill + 4×H100 decode）：

| 指标 | Monolithic | Disaggregated |
| --- | --- | --- |
| P50 TTFT | 110ms | 45ms |
| P99 TTFT | 1800ms | 280ms |
| 吞吐 | 5800 | 9200 |
| 抢占率 | 2.1% | 0.3% |

**追问**：

- Q29.1：P/D 分离的 KV 传输延迟怎么解决？（答：用 RDMA / NixL）
- Q29.2：什么时候不该用 P/D 分离？（答：短 prompt + 低 QPS + 无 RDMA）
- Q29.3：Moonshot 的 Mooncake 是什么？（答：基于 RDMA 的 KV 传输方案，Kimi 生产环境验证）

### Q30：vLLM 的 Speculative Decoding 怎么实现？有什么收益？

**问题**：vLLM 的 Speculative Decoding 怎么实现？有什么收益？

**考察点**：前沿优化。

**参考答案**：

**Speculative Decoding（投机解码）**：

用一个小模型（draft model）”猜”后续 N 个 token，然后让大模型（target model）一次验证。

**基本流程**：

```text
草稿（小模型）:  [我, 同, 意, 加, 入, 项, 目]  (7 个 token)
验证（大模型）:  一次 forward 验证这 7 个 token
                  假设前 5 个接受，后 2 个拒绝

收益: 一次 forward 算 7 个 token（而不是 1 个）
      加速比 = 5 / 1 = 5x
```

**vLLM 中的实现**：

`vllm/v1/spec_decode/` 目录下有完整实现：

- `medusa.py`：Medusa 风格（多 head 并行预测）
- `eagle.py`：EAGLE 风格（自回归 draft）
- `ngram_proposer.py`：N-gram 风格（用历史 token 预测）

**调度器集成**：

```text
# vllm/v1/core/sched/scheduler.py
num_new_tokens = (
    request.num_tokens_with_spec      # ★ 包含 spec token
    + request.num_output_placeholders
    - request.num_computed_tokens
)
# spec token 也算入 token_budget
num_new_tokens = min(num_new_tokens, token_budget)
```

**关键设计**：

- 投机解码的草稿 token 算入 `num_tokens_with_spec`
- 调度器**统一对待**草稿和真实 token
- 开不开投机解码，调度器逻辑**不变**

**收益场景**：

| 任务 | 草稿命中率 | 加速比 |
| --- | --- | --- |
| 代码补全 | 高 | 2-3x |
| 闲聊对话 | 中 | 1.5-2x |
| 摘要 | 低 | 1.2-1.5x |
| 数学推理 | 中 | 1.5-2x |

**实现选择**：

- **Medusa**：训练一个轻量级 head，并行预测
- **EAGLE**：用更小的模型做 autoregressive draft
- **N-gram**：不用模型，用历史 token 找规律

**追问**：

- Q30.1：Spec Decoding 怎么保证结果一致？（答：拒绝采样，目标模型的概率分布和草稿一致）
- Q30.2：vLLM 0.7+ 的 Spec Decoding 怎么用？（答：vllm serve … –speculative-model xxx）
- Q30.3：Spec Decoding 和 Chunked Prefill 冲突吗？（答：不冲突，都在 num_tokens 层面统一处理）
