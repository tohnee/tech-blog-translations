Kubernetes 使容器化应用程序的部署和管理变得容易，但当出现问题时，故障排除可能会变得困难，尤其是在涉及多个 Kubernetes 组件时。

Pod 可能卡住`Pending`，容器可能不断重启`CrashLoopBackOff`，应用程序可能在集群内部运行但从外部无法运行，或者节点可能突然变成`NotReady`。

好消息是，如果我们遵循系统的故障排除方法，Kubernetes 会提供足够的信息来确定根本原因。

在本指南中，我们将探讨 Kubernetes 的十大问题，并使用实用**`kubectl`**命令进行故障排除。

以下示例使用虚拟应用程序名称，例如 `<application_name>` `webapp`、` <application_name> `payment-api`` 和 ` `mysql`<application_name>`。您可以将其替换为您实际的 Kubernetes 资源。

## Kubernetes 问题及故障排除：从以下命令开始

在深入研究具体问题之前，我通常会先学习一些基本的 kubectl 命令。

```text
kubectl 获取节点复制
```

检查所有 Kubernetes 节点是否运行正常。

```text
kubectl get pods -A复制
```

这样可以全面了解所有命名空间中的 Pod。

对于特定命名空间：

```text
kubectl get pods -n production复制
```

了解更多信息：

```text
kubectl get pods -n production -o wide复制
```

当 Pod 显示意外状态时：

```text
kubectl describe pod <pod-name> -n <namespace>复制
```

另请查看近期事件：

```text
kubectl get events -n production --sort-by = .lastTimestamp复制
```

这些指令通常足以找到第一个线索。

## 1) CrashLoopBackOff

`CrashLoopBackOff`这是 Kubernetes 最常见的问题之一。

这意味着容器启动后崩溃，Kubernetes 会不断尝试重启它。Kubernetes 会逐渐增加重启尝试之间的等待时间。

例如：

```text
kubectl 获取 pods复制
```

输出：

```text
名称 就绪状态 重启
payment-api-7d8f9c7d8-xk2lm 0/1 CrashLoopBackOff 8复制
```

**如何排查 CrashLoopBackOff 故障**

首先，查看日志：

```text
kubectl logs payment-api-7d8f9c7d8-xk2lm复制
```

如果容器已重启，请检查之前容器的日志：

```text
kubectl logs payment-api-7d8f9c7d8-xk2lm --previous复制
```

这条命令特别有用。

例如，您可能会看到：

```text
错误：无法连接到数据库
连接被拒绝：mysql:3306复制
```

现在我们有了方向。

查看舱体详情：

```text
kubectl describe pod payment-api-7d8f9c7d8-xk2lm复制
```

**常见原因包括：**

- 应用程序配置错误
- 缺少环境变量
- 数据库连接失败
- 命令或入口点错误
- 缺少密钥或配置映射
- 应用程序监听了错误的端口
- 权限不足

**实用方法**

不要立即重启 Pod。

首先检查：

```text
kubectl logs <pod>
kubectl logs <pod> --previous
kubectl describe pod <pod>复制
```

应用程序日志通常会告诉你容器终止的原因。

## 2) ImagePullBackOff

另一个非常常见的问题是 ImagePullBackOff。

例如：

```text
kubectl 获取 pods复制
```

![](https://pic2.zhimg.com/v2-74ac5de96873aeea4636aba438a3ad95_r.jpg)

这意味着 Kubernetes 无法拉取容器镜像。

**查看 Pod 活动**

跑步：

```text
kubectl describe pod webapp-6f7c9d8d5c-pq2wx复制
```

在底部，您可能会找到：

```text
无法拉取镜像“registry.example.com/webapp:v2.5”：
未授权：需要身份验证复制
```

这立即告诉我们，问题与注册表身份验证有关。

另一个常见的例子是：

```text
未知复制
```

这通常意味着请求的图像标签不存在。

例如：

```text
图片：nginx:1.99复制
```

如果该标签不存在，Kubernetes 将无法拉取镜像。

**常见原因**

- 图片名称错误
- 图片标签错误
- 私有注册表身份验证失败
- 图片不存在
- 网络连接问题
- 错误`imagePullSecrets`

检查部署情况：

```text
kubectl get deployment webapp -o yaml复制
```

如果使用私有注册表，请检查：

```text
kubectl get secret
```

并验证`imagePullSecrets`配置。

## 3) Pod 卡在待处理状态

有时你创建了一个 Deployment，但 Pod 仍然存在。`Pending`

例子：

```bash
kubectl get pods
```

不要假设容器存在应用程序问题。

Pod`Pending`通常意味着 Kubernetes 无法将其调度到节点上。

**检查一下舱体。**

```bash
kubectl describe pod webapp-7c8f9d8d5-x7k2p
```

请查看**“活动”**部分。

您可能会看到：

```text
0/3 nodes are available:
2 Insufficient cpu,
1 node(s) had untolerated taint
```

现在原因很清楚了。

**常见原因**

- CPU不足
- 内存不足
- 节点污染
- 节点选择器
- 亲和/反亲和规则
- PVC材质不可用
- 没有合适的节点

检查节点资源：

```bash
kubectl describe nodes
```

您还可以查看：

```bash
kubectl top nodes
```

如果已安装指标服务器。

**例子**

假设您的部署请求：

```yaml
resources:
  requests:
    cpu: "4"
    memory: "8Gi"
```

但是您的所有节点都没有足够的可分配资源。

舱体将保留`Pending`。

## 4) Kubernetes 服务无法连接到 Pod

这是一个非常常见的问题。您的应用程序 Pod 正在运行：

```text
webapp-7c8d9f7b6-xk2lm   1/1   Running
```

但是无法通过 Kubernetes 服务访问该应用程序。

首先检查服务：

```bash
kubectl get svc webapp
```

然后检查端点：

```bash
kubectl get endpoints webapp
```

或者：

```bash
kubectl get endpointslices
```

如果服务没有端点，则 Kubernetes 没有任何匹配的后端 Pod。

例如：

```text
NAME     ENDPOINTS
webapp   <none>
```

这强烈表明服务选择器与 Pod 标签不匹配。

例如，Pod 标签：

```yaml
labels:
  app: payment-api
```

服务选择器：

```yaml
selector:
  app: payment
```

这些信息不匹配。因此，服务找不到该 Pod。请检查：

```bash
kubectl get pods --show-labels
```

然后将 Pod 标签与 Service 选择器进行比较：

```bash
kubectl describe svc webapp
```

**故障排除清单**

```bash
kubectl get svc
kubectl describe svc <service-name>
kubectl get endpoints <service-name>
kubectl get pods --show-labels
```

## 5) Ingress 无法正常工作

另一个常见的 Kubernetes 问题是应用程序在内部运行正常，但无法使用其主机名访问。

例如：

```text
https://app.example.com
```

返回：

```text
404 Not Found
```

或者：

```text
502 Bad Gateway
```

**首先检查 Ingress**

```bash
kubectl get ingress
```

然后：

```bash
kubectl describe ingress app-ingress
```

查看：

- 主机名
- 小路
- 后端服务
- 后端端口
- 入口控制器
- TLS 配置

例如：

```text
Rules:
  Host              Path
  app.example.com   /
  webapp:8080
```

现在检查该服务是否实际暴露了端口`8080`：

```bash
kubectl get svc webapp
```

并检查其端点：

```bash
kubectl get endpoints webapp
```

**一个常见的错误**

Ingress：

```yaml
backend:
  service:
    name: webapp
    port:
      number: 8080
```

但该服务揭示了：

```yaml
port: 80
```

这种不匹配会导致连接问题。

**故障排除流程**

```text
Client
  |
  v
Ingress
  |
  v
Service
  |
  v
Pod
```

逐层排查故障。

## 6) Kubernetes 节点未就绪

有时，Pod 问题实际上是节点问题。

检查节点：

```bash
kubectl get nodes
```

例子：

```text
NAME       STATUS     ROLES
worker01   Ready      <none>
worker02   NotReady   <none>
worker03   Ready      <none>
```

现在展开调查`worker02`。

```bash
kubectl describe node worker02
```

请看：

```text
Conditions:
```

您可能会发现：

```text
Ready   False
```

检查系统 Pods：

```bash
kubectl get pods -n kube-system -o wide
```

根据 Kubernetes 环境，检查以下服务：

```bash
systemctl status kubelet
```

另请查看 kubelet 日志：

```bash
journalctl -u kubelet -n 100
```

### 常见原因

- Kubelet 已停止
- 盘压
- 记忆压力
- 网络问题
- 容器运行时问题
- 节点不可达
- 证书问题

例如：

```text
DiskPressure=True
```

这可能表明节点磁盘空间不足。

查看：

```bash
df -h
```

和：

```bash
df -i
```

## 7) 部署未更新

您已更新应用程序镜像：

```bash
kubectl set image deployment/webapp webapp=registry.example.com/webapp:v2
```

但旧的 Pod 仍在运行。

首先检查：

```bash
kubectl rollout status deployment/webapp
```

然后：

```bash
kubectl rollout history deployment/webapp
```

检查部署情况：

```bash
kubectl describe deployment webapp
```

另请查看副本集：

```bash
kubectl get rs
```

你可能会发现类似这样的内容：

```text
NAME                 DESIRED   CURRENT   READY
webapp-5c78d9f       3         3         3
webapp-7d9f8c2       3         0         0
```

检查 Pod 中实际运行的镜像：

```bash
kubectl get pods -o wide
```

和：

```bash
kubectl describe pod <pod-name>
```

### 实用命令

```bash
kubectl rollout status deployment/webapp
kubectl rollout history deployment/webapp
kubectl rollout undo deployment/webapp
```

如果新版本出现问题，您可以快速回滚：

```bash
kubectl rollout undo deployment/webapp
```

## 8) CPU或内存使用率过高

有时 Kubernetes 本身运行正常，但应用程序却消耗了过多资源。

检查舱位：

```bash
kubectl top pods
```

对于特定命名空间：

```bash
kubectl top pods -n production
```

例子：

```text
NAME              CPU(cores)   MEMORY(bytes)
payment-api       1800m        3500Mi
frontend          120m         250Mi
```

这里`payment-api`消耗的资源明显更多。

检查 Pod 配置：

```bash
kubectl get pod payment-api -o yaml
```

寻找：

```yaml
resources:
  requests:
    cpu: "500m"
    memory: "512Mi"
  limits:
    cpu: "2"
    memory: "2Gi"
```

如果容器反复达到内存上限，您可能会看到：

```text
OOMKilled
```

查看：

```bash
kubectl describe pod payment-api
```

**重要区别**

- **请求**告诉 Kubernetes Pod 调度需要多少资源。
- **限制**定义了容器可以使用的最大资源量。

资源设置不正确可能导致：

- 剩余待处理 Pod
- CPU降频
- OOMKilled 容器
- 应用程序性能差

## 9) etcd 和 Kubernetes 控制平面问题

对于自管理的 Kubernetes 集群，控制平面出现问题可能会影响整个集群。

最重要的组件之一是**etcd**，它存储 Kubernetes 集群状态。

如果 API 服务器不可用或控制平面无法与 etcd 通信，则可以使用如下命令：

```bash
kubectl get pods
```

可能会失败。

例如：

```text
The connection to the server was refused
```

或者：

```text
Unable to connect to the server
```

对于自管理集群，请检查控制平面组件：

```bash
kubectl get pods -n kube-system
```

如果使用静态 Pod，请检查：

```bash
kubectl get pods -n kube-system -o wide
```

根据你的 Kubernetes 发行版，检查 API 服务器和 etcd 日志。

**重要提示**

如果您使用的是托管式 Kubernetes 服务（例如**AKS）**，通常情况下您无需直接对底层控制平面 etcd 部署进行故障排除或管理。在这种情况下，请重点关注集群和托管服务诊断中显示的症状。

## 10) 基于角色的访问控制 (RBAC) 和权限被拒绝错误

RBAC 问题也很常见，尤其是在应用程序或用户尝试访问 Kubernetes 资源时。

例如：

```bash
kubectl get pods
```

返回：

```text
Error from server (Forbidden):
pods is forbidden:
User "devuser" cannot list resource "pods"
```

这是一个基于角色的访问控制（RBAC）问题。首先检查用户的权限：

```bash
kubectl auth can-i get pods
```

对于命名空间：

```bash
kubectl auth can-i get pods -n production
```

您还可以测试特定用户：

```bash
kubectl auth can-i get pods --as=devuser -n production
```

如果结果是：

```text
no
```

您需要检查角色/集群角色及其对应的绑定。

例如：

```bash
kubectl get role -n production
kubectl get rolebinding -n production
```

和：

```bash
kubectl describe rolebinding <rolebinding-name> -n production
```

**典型的基于角色的访问控制（RBAC）错误**

你在一个`production`命名空间中创建了一个角色，但在另一个命名空间中创建了一个角色绑定。

记住：

> ***Role 和 RoleBinding 的作用域是命名空间范围的。***

错误的命名空间可能导致完全有效的基于角色的访问控制 (RBAC) 配置，但仍然无法提供预期的访问权限。

## 一个简单的 Kubernetes 故障排除方法

在排查 Kubernetes 问题时，避免随意运行命令，而应跟踪流量和资源流向。

一个简单的办法是：

```text
1. Check the Pod
       ↓
2. Check Pod logs
       ↓
3. Check Pod events
       ↓
4. Check Deployment / ReplicaSet
       ↓
5. Check Service and Endpoints
       ↓
6. Check Ingress
       ↓
7. Check Node
       ↓
8. Check CPU / Memory
       ↓
9. Check RBAC / Network / Storage
```

例如，如果用户说：

> *“我的申请无法访问。”*

不要立即重启 Pods。

首先：

```bash
kubectl get pods -n production
```

然后：

```bash
kubectl get svc -n production
```

然后：

```bash
kubectl get endpoints -n production
```

然后：

```bash
kubectl get ingress -n production
```

这可以帮助您确定**请求失败的原因**。

## 用于故障排除的实用 Kubernetes 命令

以下是我在排查 Kubernetes 环境故障时经常使用的一些命令。

**列出资源**

```bash
kubectl get all -n production
```

**获取详细的 Pod 信息**

```bash
kubectl describe pod <pod-name> -n production
```

**查看日志**

```bash
kubectl logs <pod-name> -n production
```

**查看之前的容器日志**

```bash
kubectl logs <pod-name> --previous -n production
```

**关注日志**

```bash
kubectl logs -f <pod-name> -n production
```

**检查事件**

```bash
kubectl get events -n production --sort-by=.lastTimestamp
```

**检查节点**

```bash
kubectl get nodes
```

**检查资源消耗**

```bash
kubectl top nodes
kubectl top pods -n production
```

**检查服务**

```bash
kubectl get svc -n production
```

**检查端点**

```bash
kubectl get endpoints -n production
```

**检查部署推出情况**

```bash
kubectl rollout status deployment/<deployment-name>
```

**检查基于角色的访问控制 (RBAC) 权限**

```bash
kubectl auth can-i get pods -n production
```

## 最后想说的话

了解**哪个组件导致了问题，就能让**[Kubernetes](https://kubernetes.io/)故障排除变得容易得多。

A`CrashLoopBackOff`通常代表应用程序/容器问题。A`ImagePullBackOff`指向容器镜像或镜像仓库。Pod`Pending`通常需要检查调度、资源、污点或存储。如果 Pod 运行正常但用户无法访问应用程序，则应将故障排除工作转移到**Service、Endpoints 和 Ingress**。

最重要的是不要简单地重启 Pod，然后指望问题就消失了。

相反，应使用以下方法收集证据：

```bash
kubectl get
kubectl describe
kubectl logs
kubectl get events
kubectl top
kubectl auth can-i
```

一旦你熟悉了这些命令，大多数日常 Kubernetes 问题就更容易隔离和修复。
