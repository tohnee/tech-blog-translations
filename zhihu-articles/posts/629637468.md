## 前置知识

其实在数据并行之后，讲流水线并行是会让人有一些误解的。为了将流水线描述清楚，会基于下图先解释下几个前提：

![](https://picx.zhimg.com/v2-5a6f8630e7613b1fc03a987b2b6acb59_1440w.jpg)

1. 流水线并行应用在模型并行（区别于张量并行，我这里统一将模型并行定义为op间并行，即通常看到的我们可以将模型的不同layer放置不同的计算设备），如上图部分，可简单理解为模型的四个层，分别放置在计算设备0-3上；
2. 将模型不同的层放置不同的计算设备后，会增加额外的通信成本；
3. 简单地将模型不同层放置在不同的计算设备上，虽然能解决模型载入，并且也能训练，但是如上图Device1部分，在Device1计算时，其他计算设备均在等待，等于在浪费算力，这里设备的等待时间，我们称为bubble，后续流水线并行的相关优化点主要是为了降低bubble占比， 上面bubble时间占比为(n-1)/n；

同步流水线并行解释：“即使在多个计算设备上，仅仅是提升了效率，其计算与收敛与单个计算设备上完全一致”。

### GPipe

更大的模型为多个领域带来了显著的提升，更大的模型参数规模也带来了重大的实际挑战。包括计算设备（如GPU或TPU）上的内存限制和通信带宽在内的硬件限制，迫使用户将较大的模型切分为不同分片，并将不同分片分配给不同的计算设备。高效的模型并行算法非常难以设计和实现，需要从扩展能力、灵活性（或特定任务和架构）和训练效率等不同维度上作出考量。为了解决这些挑战，[1]文章中提出GPipe，可以实现任意架构的模型的高效训练。GPipe 通过将模型的不同部分切分到不同计算设备上上，可以超越单个加速器的内存限制，扩展任意规模神经网络架构。使用GPipe，每个模型可视为层的序列，连续的层组合为一个cell，每个cell被放置在一个计算设备上。基于这种分片设置，[1]提出了基于micro batch size的流水线并行：

1. 首先将训练过程的batch样本拆分为更小的micro batch 样本；
2. 其次在cell上流水行执行每组micro batch的操作（前向->反向）；
3. 训练过程中，梯度在所有micro batch上累积，并在每个batch结束时更新模型参数（梯度累计->模型参数更新）；

![](https://picx.zhimg.com/v2-bc1e864c1ceb5d8ed8032264e53830ab_1440w.jpg)

降低bubble将每次需要计算的batch size减小为micro batch size，在micro batch的样本计算完成后，即将相关的activation send到下一个计算设备，进行接下来的计算，如上图相对于为进行micro batch 拆分的，整体bubble的占比为(n-1)/(n-1+m)，m为micro size数目，文中也指出，在实验中当m>=4*n时，bubble比例几乎可以忽略不计，这其中也部分因为反向计算中的recompute可以提前一定时间计算，而不需要一定等依赖的梯度计算完成；

减少显存GPipe支持recompute，和上篇文章中提到的activation checkpoint其实是一个东西：在正向计算过程中，每个计算设备在分片边界处存储activation， 仅传输边界activation， 在反向传递过程中，计算设备会重新计算activation，减少activation占用的显存；

负载均衡上图中的切分策略比较完美，计算设备间负载比较均衡，但是在真实的场景中并不是如此，因而，更好地切分策略可以提高训练的综合性能。DeepSpeed 提供了多种计算设备切分策略，可使用 PipelineModule的 partition_method 关键字参数设置这些策略：

- partition_method="parameters"尽量保证流水线中每个计算设备的可训练参数的数量一致， 这在内存受限的环境中以及层的大小与计算时间成正比时特别有效；
- partition_method="type:[regex]" ，正则表达式不区分大小写，尽量保证符合正则的层数一致。例如，partition_method="type:transformer" 将平衡每个计算设备的transformer数量；
- partition_method="uniform" 按层数来进行策略切分，尽量保证层数均衡；

减少模型构造时的显存使用

使用Sequential将序列层提供到PipelineModule是指定流水线并行的比较友好的方式。然而会遇到每一个计算设备都会保存整个模型的副本， 假定8个计算设备的本地机器CPU内存必须要先消耗8倍的计算设备的显存来用来做模型构造，而显然是十分低效且没必要的方式：

DeepSpeed提供了一个 LayerSpec 类，它可以延迟模型的构建，直到模型层在不同计算设备之间进行分片。每个计算设备只分配被分配到的层占用的显存大小。因此，本地机器CPU在多个计算设备上仅需要一个模型大小的内存用于提供模型的构造。

DeepSpeed LayerSpec类的使用十分简单，以下是一个alexnet的展示：

```text
from deepspeed.pipe import PipelineModule, LayerSpec
class AlexNetPipe(PipelineModule):
    def __init__(self, num_classes=10, **kwargs):
        self.num_classes = num_classes
        specs = [
            LayerSpec(nn.Conv2d, 3, 64, kernel_size=11, stride=4, padding=2),
            LayerSpec(nn.ReLU, inplace=True),
            ...
            LayerSpec(nn.ReLU, inplace=True),
            LayerSpec(nn.Linear, 4096, self.num_classes),
        ]
        super().__init__(layers=specs, loss_fn=nn.CrossEntropyLoss(), **kwargs)

```

### DAPPLE

在具有多样化互连功能的复杂 GPU 平台上训练大模型(DAPPLE不仅限于LLM)是一项具有挑战性的任务。最近，流水线训练被提议作为提高设备利用率的有效方法。然而，仍然有几个棘手的问题需要解决：

1. 在保证收敛的同时提高计算效率，在不产生额外计算成本的情况下减少内存使用；
2. DAPPLE结合了大模型的数据并行和流水行并行，通过一种新颖的并行化策略规划器来解决分片问题，并探索数据并行和流水行并行最佳混合策略；
3. DAPPLE提出调度算法来减少设备内存使用，这与recompute正交并且不会以训练吞吐量为代价；
4. 实验表明，在同步训练场景下，DAPPLE Planner始终优于 PipeDreams Planner生成的策略，加速高达 3.23 倍，DAPPLE 运行时训练吞吐量加速优于 GPipe 1.6 倍，同时节省 12% 的内存消耗。

同步流水线训练的效率问题

流水线训练引入了相连计算设备之间的数据依赖。如GPipe[1]所描述， 提高计算设备利用率的一种常见方法是将mini-batch分成多个micro-batch。这些micro-batch以流水线方式安排在不同计算设备上同时执行。如文章GPipe所示，mini-batch被拆分的micro-batch越多，整体的流水线效率越高，但是却会引入两个问题：

1. 额外的内存消耗：GPipe的前向计算过程将所有的micro-batch连续计算， 然后计算出的activation用于反向计算。activation必须保存在所有微批次的内存中，直到它们相应的反向计算开始。因此，虽然更多的micro-batch意味着更高的效率，但内存限制限制了允许的micro-batch数量；
2. 冗余计算：GPipe等采用recompute来减少峰值内存消耗，即在前向计算丢弃一些activation，并在需要时在反向阶段重新计算它们，这里引入的冗余计算会带来额外的执行时间成本；

流水线规划遇到的问题

为了最大限度地提高流水线并行的资源利用率和训练吞吐量，找到一个好的策略来切分stage和将stage映射到计算设备是至关重要的。DAPPLE将stage划分和计算设备设备映射称为流水线规划。流水线会遇到以下问题：

1. 同步流水线能够保障收敛，而收敛是训练的前提。与异步流水线训练相比，同步流水线在所有micro-batch结束时需要一个额外的步骤来同步参数更新，比如allreduce， 这里会引入一定的通信开销，当前的流水线规划器没有考虑这种开销，因此无法准确地对端到端流水线训练时间进行建模；
2. 以前的方法没有考虑阶段数量的影响，在固定micro-batch数量和通信/计算开销比的情况下，阶段数越少，流水线效率越高；
3. 现有方法尚未对不均匀的模型切分有很好的研究，前面我们提到DeepSpeed有常见的三种模型切分方法，尽量保证计算设备负载均衡；

DAPPLE整体架构

![](https://pic1.zhimg.com/v2-ea10da11aac7a9690c158853750f6750_1440w.jpg)

上图展示了DAPPLE的workflow， 包括DAPPLE Profiler、DAPPLE Planner、DAPPLE Runtime，基本流程如下：

1. DAPPLE Profiler用户的 DNN 模型，每一层的执行时间、activation大小和模型参数大小作为输入；
2. Profiler产生的结果作为输入， DAPPLE Planner在给定的全局批量大小上生成优化的（混合）并行化计划；
3. DAPPLE Runtime获取Planner的结果，并将原始模型图转换为流水线并行图。

DAPPLE Planner其中，planner旨在最小化一次训练迭代的端到端执行时间（考虑通信开销、global batch size等），如解决不均匀的模型stage切片。该模块负责Stage切分、设备分配，并生成最优并行化计划。特别是，设备分配是会考虑到硬件的拓扑信息；

DAPPLE还探索了将pipeline的单个stage映射到多个计算设备上。下图给出了一个示例，其中模型分为两个阶段，每个stage内部为DP组，通过高效的Nvlink来进行参数的更新，不同stage组成PP组， 通过以太网传递activation和grad：

DAPPLE Schedule

为了提高流水线训练效率，GPipe [1] 提出将全局批次拆分为多个micro-batch。然而，必须为所有micro-batch保留前向计算产生的激活函数，直到相应的反向计算开始，从而导致显存需求与micro-batch数成正比（如上图C所示，注意图中表示有问题红色为DAPPLE，蓝色为GPipe），这与我们尽量保证较大的micro-batch以提到较高的性能有冲突。而在DAPPLE 中，我们提出尽早地向后调度以减少内存消耗，即1F1B：

![](https://pic2.zhimg.com/v2-e979be00e4dfefc713bf71502d4ffb05_1440w.jpg)

1F1B主要思想是尽早地反向计算，从而释放用于存储相应前向计算产生的激活的内存。如上图b:

1. 开始计算时，不是一次性喂入所有microbatch，以释放内存压力，同时保持高流水线效率；
2. 其次，严格地约束每个micro-batch的前向计算完成后进行反向计算，以保证反向计算能更早地进行。

上图C为GPipe 和 DAPPLE中的内存消耗如何随时间变化。开始时，DAPPLE 中的内存使用量随时间增加，直到喂入K个micro-batches（K<整个microbatch数，通常为stage数），随后开始反向计算，释放显存。由上图也可发现，这里与GPipe的bubble时间占比一致，但peak memory不随micro-batch数量增加，而是和stage数相关。

Planner和runtime的角色功能以及要解决的问题前面有描述， 具体的算法这里因为没有涉及到pipeline本身，就不详细讲了（后续在自动并行的总结中再做介绍）， 直观来说DAPPLE的架构设计比较全面，比较复杂。因为其复杂性，也约束在开源社区的支持，目前看起来DAPPLE本身架构在开源社区的支持比较少，但是1F1B的思路目前在DeepSpeed已是默认选择。

### interleaved 1F1B

[3]提出了一套interleaved 1F1B的方法(当然这篇文章更重要的是tensor并行的工作)，可以进一步地减少bubble耗时占比，其基本思路也是减少计算设备计算时地依赖， GPipe从数据层面切，而interleaved 1F1B则是从模型stage层面考虑，减少每次计算的粒度以获取更大的并行性：
