### 一、一个自助餐厅的比喻

一家自助餐厅，每位顾客平均待 40 分钟（延迟 W），餐厅想做到每分钟接待 2 位顾客的翻台率（吞吐 λ）。那么餐厅里**平均同时得有 80 位顾客**（并发 L）。

```text
L = λ × W     并发 = 吞吐 × 延迟
```

这就是 Little 定律。它不关心顾客怎么来、怎么走、餐厅里怎么排队——只要系统稳定，这个等式就成立（Little 1961 年的证明只用了“长期平均”这一个假设）。它的用法有两个方向：

- **正向**：知道吞吐和延迟，算出需要多少并发——“要打满这个带宽，得有多少请求在途”。
- **反向**：知道并发上限和延迟，算出吞吐上限——“这个硬件只能跟踪 N 个在途请求，所以它最多跑多快”。

第二个方向就是所有“带宽明明够，却打不满”问题的来源。

### 二、从 HBM 开始：一颗 GPU 要多少访存并发

### 2.1 先把延迟选对：空载 300 ns，满载 600 ns

H100 的 HBM3 带宽 3.35 TB/s。延迟用哪个数？公开的实测：Chips and Cheese 用指针追逐测得 H100 本地 HBM3 **不到 300 ns**——这是空载、一次只有一个请求在飞的延迟。而 Werner 等（HCDS 2025）在 Grace-Hopper 上测到，随着并发线程数上升，同一条访存路径的延迟从 807 ns 升到 1022 ns——负载上去，延迟就上去。打满带宽时排队已经发生，SM 看到的 HBM 延迟在 600 ns 上下是合理的工程取值。两个数字算出来的在途需求差一倍：

```text
空载 300 ns：3.35 TB/s × 300 ns ≈ 1.0 MB 在途，按 128 B 的缓存行算 ≈ 7,850 行，每 SM（132 个）约 59 行
满载 600 ns：3.35 TB/s × 600 ns ≈ 2.0 MB 在途 ≈ 15,700 行，每 SM 约 119 行
```

**要用满载的那个**，否则会得出“这点并发就够了”的结论，然后在真机上怎么调都到不了带宽（第四季第二十篇专门讲这个坑）。

### 2.2 谁来提供这 119 行

一个 warp 一条 32 位的 load（32 线程各 4 字节）恰好搬一个 128 B 的行；一条 128 位的向量 load 搬 512 B = 4 行。一个 SM 最多驻留 64 个 warp。如果每个 warp 只有一条 32 位 load 在飞，64 个 warp 只能提供 64 行——**光靠 warp 数量打不满 HBM**。要么每个 warp 同时有多条独立的 load 在飞（指令级的访存并行，MLP——编译器把多条不依赖的 load 提前发出），要么用更宽的向量化访问（一条指令 4 行），要么用 Hopper 的 TMA（张量内存加速器，一条指令搬一个几 KB 的块，几十行）。

Volkov 的博士论文（2016）在几代 GPU 上系统地测了这件事，结论正是 Little 定律：**打满带宽需要的是“在途字节数”，占用率只是提供在途的手段之一**；用足够的 ILP / MLP，远低于 100% 的占用率就能达到接近峰值的带宽，而 100% 占用率配上每 warp 一条 load 反而打不满。

B200 的 HBM3e 是 8 TB/s，同样延迟下在途要求翻到 4.8 MB、37,500 行。**带宽每翻一倍，需要的并发就翻一倍，而延迟并没有变短**——这是 GPU 一代代把寄存器、MSHR（未命中状态保持寄存器）、访存队列做大的原因，也是 TMA 出现的原因：用更大的请求粒度换更少的请求数。

### 2.3 最底层也有在途上限：bank

链条的最底端是 DRAM 的 bank。H100 的 5 个 HBM3 栈 × 16 通道 × 2 伪通道 × 16 bank = **2560 个 bank**，每个 bank 一次只能打开一行、一个行周期 tRC 约 48 ns。如果访问完全随机、每次只取 64 B，最多能做到 2560 / 48 ns × 64 B ≈ **3.4 TB/s**——恰好和峰值带宽同量级。也就是说 HBM 的“最大在途”从底层看就是 bank 数，随机访问下它刚好够用，任何 bank 冲突（两个请求落在同一 bank 的不同行）都会把有效并发打下去（第四季第三篇细讲）。

### 2.4 同样的账在每一层

| 资源 | 吞吐 | 延迟（满载） | 打满所需在途 | 由谁提供 |
| --- | --- | --- | --- | --- |
| HBM（H100） | 3.35 TB/s | ~600 ns | ~2 MB / ~15.7k 行 | warp 数 × 每 warp MLP × 请求粒度 |
| L2 缓存 | 数 TB/s 到十几 TB/s | ~200~300 ns | 数百 KB | 同上 |
| NVLink 4（每方向） | 450 GB/s | ~1 µs | ~450 KB / ~7000 个 64 B 事务 | 端点请求追踪表（第三季第二篇） |
| PCIe Gen5 x16 | ~50 GB/s | ~1 µs（pcie-bench 实测读 547 ns 空载） | ~50 KB | DMA 引擎的在途描述符 |
| 400G 网卡 | 50 GB/s | 2~10 µs（网络往返） | 100~500 KB | 传输层窗口 / 在途表 |
| UCIe 链路（第一季第一篇） | 256 GB/s | ~11 ns | ~2.8 KB / ~11 个 flit | 信用数 |
| HBM bank | 3.35 TB/s | tRC ~48 ns | 2560 个 bank | 地址映射的 bank 并行度 |

每一行都是同一个公式，区别只在“谁提供并发”。**并发是一种资源，和带宽一样要被设计、被分配。**

### 三、反过来用：从在途上限推吞吐上限

Little 定律反过来是一个不等式：

```text
吞吐 ≤ 最大在途 / 延迟
```

### 3.1 封闭系统的膝点

“在途上限”对应的排队论模型叫**封闭系统**：系统里永远只有 N 个请求在循环（发出 → 服务 → 返回 → 再发出）。运筹学里的运行分析（Denning & Buzen）给出两条渐近界：

```text
设 Z = 请求在“外面”的时间（往返、思考时间），D = 瓶颈资源的每请求服务时间
吞吐 X(N) ≤ min( N / (Z + D) ,  1 / D )
膝点 N* = (Z + D) / D ≈ Z / D
```

N < N* 时吞吐随 N 线性涨（延迟主导），N > N* 时吞吐封顶在 1/D（瓶颈主导），再加 N 只是排队。**这个 N* 就是在途表该有的深度。** 算一个：网卡消息速率 3.7 亿 / 秒（第三季第二篇）意味着 D ≈ 2.7 ns，网络往返 Z = 2 µs，N* ≈ 740——在途表低于 740 项，这张网卡的小消息吞吐就到不了它的消息速率上限；往返变成 10 µs（跨机架、有排队），N* 变成 3700。

### 3.2 三个典型场景

**网卡的在途表**（第三季第二篇）：表深 N，网络往返 RTT，则单流吞吐 ≤ N × 消息大小 / RTT。跨机架的 RTT 比机架内长几倍，同一张网卡的单流吞吐就掉几倍——这不是带宽问题，是并发问题。

**RoCE 的窗口**：go-back-N 传输的窗口大小就是最大在途。窗口 1 MB、RTT 10 µs → 单流最多 100 GB/s；RTT 变成 50 µs（拥塞排队）→ 20 GB/s。**拥塞通过拉长延迟压低了吞吐，即使没有任何丢包。**

**推理服务**：一个 decode 实例每步处理 batch 个序列（并发 L），每步 TPOT（延迟 W），则吞吐 λ = batch / TPOT。但 TPOT 不是常数——它随 batch 增长，因为每步要读的 KV 字节数随 batch 线性增加。用第二季第二篇的数字（Llama-3-70B、8 × H100、8K 上下文，每卡权重 17.5 GB、每序列 KV 每卡 328 MB，HBM 有效带宽按 80% 算）：

| batch | 每步读的字节（权重 + KV） | TPOT | 吞吐（8 卡合计） | KV 占比 |
| --- | --- | --- | --- | --- |
| 1 | 17.8 GB | 6.7 ms | 150 token/s | 2% |
| 8 | 20.1 GB | 7.5 ms | 1,070 | 13% |
| 32 | 28.0 GB | 10.4 ms | 3,060 | 37% |
| 64 | 38.5 GB | 14.4 ms | 4,460 | 55% |
| 128 | 59.4 GB | 22.2 ms | 5,770 | 71% |
| 256 | 101 GB | 37.8 ms | 6,770 | 83% |

读法：batch 从 1 到 64，吞吐涨 30 倍、TPOT 只涨 2 倍——这是 Little 定律“用并发换吞吐”的甜蜜区；到 128 以上 KV 读取占了七成以上，TPOT 随 batch 接近线性增长，吞吐趋于饱和在“HBM 带宽 / 每 token KV 字节”这个上限。**Little 定律把推理服务的三个指标锁在了一起，改一个必动另一个**，而 KV 量化（第四季第十六篇）之所以是 decode 的第一优化项，就是因为它同时缩短 W 和放大可容纳的 L。

### 四、并发的反面：排队

Little 定律说的是“平均”，它成立的前提是系统稳定。但并发一上去，延迟不是常数——它随利用率上升。最简单的排队模型（M/M/1，泊松到达、指数服务）给出：

```text
平均延迟 = 服务时间 / (1 − 利用率 ρ)
```

| 利用率 ρ | 延迟是空载的几倍 |
| --- | --- |
| 50% | 2× |
| 70% | 3.3× |
| 80% | 5× |
| 90% | 10× |
| 95% | 20× |
| 99% | 100× |

### 4.1 利用率只是一半，突发性是另一半

M/M/1 假设到达和服务都是“随机得恰到好处”。更一般的 Kingman 近似（G/G/1）把到达间隔和服务时间的变异系数 C_a、C_s 放进来：

```text
排队等待 ≈ 服务时间 × ρ / (1 − ρ) × (C_a² + C_s²) / 2
```

把总延迟 / 服务时间列成表（c = (C_a² + C_s²) / 2）：

| ρ | c = 0.5（确定性服务） | c = 1（M/M/1） | c = 2（中等突发） | c = 5（强突发） |
| --- | --- | --- | --- | --- |
| 50% | 1.5× | 2× | 3× | 6× |
| 80% | 3× | 5× | 9× | 21× |
| 90% | 5.5× | 10× | 19× | 46× |
| 95% | 10.5× | 20× | 39× | 96× |

两个读法：**服务时间越规整，排队越少**——定长的 cell（第三季第一篇）、定长的 flit、固定大小的请求，都是在把 C_s 压到接近 0；**到达越突发，排队越多**——incast、同步集合通信的齐发、第一季第四篇里 PFC 解除后的爆发，都是把 C_a 抬上去的东西，在同样 80% 利用率下延迟可以差四倍。这张表解释了系列里反复出现的几个现象：为什么拥塞控制要把队列压到接近零（第一季第四篇的 HPCC），为什么交换机的延迟在高负载下和 cut-through / store-and-forward 无关了（第一季第二篇），为什么推理服务的 P99 TPOT 在利用率 80% 以上会失控。**“打满带宽”和“延迟可控”是互斥的，工程上的甜点通常在 60%~80% 利用率。**

而 Little 定律和排队公式合在一起是一个闭环：并发↑ → 利用率↑ → 延迟↑ → 打满同样吞吐需要更多并发。这个正反馈是尾延迟的来源，也是第一季第三篇“路径延迟差必须闭环”的数学根源。

### 4.2 三个真实系统的 Little 定律读数

把公式套到三个能查到数的系统上，每一个都给出一条“上限”：

```text
① 一块 NVMe SSD：4 KB 随机读，队列深度 1 时延迟约 80 µs → 吞吐 = 1 / 80 µs = 12.5K IOPS
   标称 100 万 IOPS 需要在途 = 1e6 × 80 µs = 80 个请求 → 所以规格书里的 IOPS 总是标着“QD32 × 8 线程”这类条件
② 一个 RDMA 队列对：ConnectX 默认每 QP 最多 16 个在途 RDMA 读（max_rd_atomic）
   4 KB 的读、网络往返 5 µs → 单 QP 上限 = 16 × 4 KB / 5 µs ≈ 13 GB/s，打不满 400G 的 50 GB/s
   → 要么开 4 个以上 QP，要么把消息做大（第三季第二篇网卡的在途表就是这一项的硬件上限）
③ 一张 H800 的 decode（DeepSeek 2025-02 的生产数据）：每卡 1,850 tok/s，每个用户 20~22 tok/s
   → 在途 = 1,850 × (1 / 21 s) ≈ 88 个并发序列 / 卡；乘上平均 4,989 token 的 KV，就是第一季第六篇算的 31 GB
```

三个例子里，“延迟”分别是介质延迟、网络往返和用户看到的每 token 间隔，“容量”分别是 SSD 队列、QP 的在途表和显存里的 KV——**同一条公式，三个完全不同的层，都是“在途 = 吞吐 × 延迟”决定了上限在哪一侧。** ESL 里最省事的校验就是这样：拿一个公开的吞吐、一个公开的延迟，算出隐含的在途量，再和硬件的容量比——对不上就是模型漏了一层。

### 五、并发的层级：谁在提供、谁在消耗

把一次 GPU 访存从头到尾拆开，并发是逐层提供、逐层消耗的：

```text
应用 / 编译器：   决定每个线程有几条独立的 load（ILP / MLP），向量宽度，TMA 块大小
SM 调度器：       驻留 warp 数（占用率），每周期发射多少访存
L1 / MSHR：       每个 SM 能跟踪多少未命中（几十到上百个）
片上网络：        每个方向的信用 / 缓冲（第四季第六篇）
L2 切片：         每个切片的请求队列深度
内存控制器：      每个通道的命令队列（第四季第七篇）
HBM：             bank 并行度 2560、每 bank 的 tRC（第四季第三篇）
```

**任意一层的在途上限不够，整条链的吞吐就被它卡住**，而且卡住的那一层从带宽数字上完全看不出来。这是芯片性能分析里最常见的“带宽够但跑不满”的解释框架——也是第四季第二十篇讲的“用并发流微基准反推硬件结构”的原理：并发数 k 递增、吞吐先线性涨后饱和，拐点就是这一层的 N。

### 六、★ ESL 建模视角：每个资源都是三元组

前面都是铺垫，这一节是我真正想写的。

### 6.1 资源模型

系列里每一层的模型，最终都能归结为同一个骨架：

```text
资源 R：
  吞吐上限  B_R
  延迟      W_R(ρ) = W_R(0) × [1 + ρ/(1−ρ) × c_R]     ← Kingman 形式，c_R 由到达 / 服务的变异系数定
  最大在途  N_R（信用、表深、窗口、MSHR、bank 数……）

有效吞吐 = min( B_R ,  N_R × 粒度 / W_R(ρ) )
```

注意第二项里 W_R 本身依赖于 ρ，而 ρ 又依赖于吞吐——这是一个不动点，解析上要迭代，仿真里自然收敛。一条从 SM 到 HBM、或从 GPU 到远端 GPU 的路径，是一串这样的资源串联，**整体吞吐 = 各层有效吞吐的最小值**。仿真的价值在于：延迟 W_R 随负载变化时，这个最小值会从一层跳到另一层——这是解析算不出来的动态。

### 6.2 校验用法

Little 定律是仿真的第二把校验尺（第一把是第三季第三篇的 α-β 公式）：

- **稳态一致性**：仿真里任意资源的平均在途量，必须等于测得的吞吐 × 测得的平均延迟。不等说明统计口径有错，或者系统没进入稳态。这条检查几乎零成本，应该对每个资源自动做。
- **瓶颈定位**：对每个资源算 N_R × 粒度 / W_R 与实际吞吐的比值，最接近 1 的那层就是瓶颈。
- **参数合理性**：任何“最大在途”参数都能反推出它支持的吞吐上限，超出物理带宽的配置没有意义，远低于的配置说明这一层是刻意的瓶颈。
- **膝点校验**：封闭系统的 N* = Z / D 可以手算，仿真里在途数扫过 N* 时吞吐曲线应该有一个清晰的拐点。

### 6.3 必须参数化的量

| 参数 | 含义 | 典型值 / 注意 |
| --- | --- | --- |
| N_R | 各层最大在途 | 信用、表、窗口、MSHR、队列深度、bank 数 |
| W_R(0)、c_R | 各层空载延迟与排队系数 | 不能是常数；空载 vs 满载差一倍 |
| granularity_R | 请求粒度 | 32 位标量 load 128 B，向量 load 512 B，TMA 几 KB |
| mlp_per_warp、occupancy | 计算核提供的访存并发 | 编译器与调度器决定 |
| batch、tpot(batch) | 推理服务的并发与延迟 | TPOT 随 batch 增长，与显存容量联动 |
| rho_target | 目标利用率 | 60%~80% 的甜点 |
| burstiness（C_a²） | 到达的突发性 | 同步集合通信、incast 时远大于 1 |

### 6.4 该盯的指标

- **每层在途量的分布**：平均值对照 Little 定律，峰值对照 N_R。
- **利用率-延迟曲线**：每个资源一条，拐点位置；对照 Kingman 表看 c_R 是多少。
- **有效吞吐 / 物理带宽**：按层报告，最小的那层是瓶颈。
- **并发不足导致的空闲时间**：资源空闲但上游有需求的时间比例。
- **吞吐-并发曲线的膝点**：与 Z / D 的手算值对照。

### 6.5 最常见的建模坑

1. **只建带宽不建在途上限。** 长延迟路径上的吞吐会被高估几倍。
2. **延迟当常数，或者用空载延迟。** 排队让延迟随利用率上升，空载和满载差一倍，Little 定律的闭环就断了。
3. **在途粒度混淆。** 字节和请求数之间要用粒度换算，TMA 与 32 位标量 load 差几十倍。
4. **只看一层。** 并发是逐层提供的，任意一层不够整条链都卡。
5. **只看利用率不看突发。** 同样 80% 利用率，强突发的延迟是泊松的四倍。
6. **追求 100% 利用率。** 排队公式说 90% 利用率的延迟是 10 倍，尾延迟在那之前就已经失控。

### 七、小结

```text
L = λ × W：并发 = 吞吐 × 延迟；反过来 吞吐 ≤ 最大在途 / 延迟
HBM：空载 300 ns（实测）→ 1 MB；满载 600 ns → 2 MB ≈ 15.7k 行，每 SM ~119 行 → 靠 warp 数 × MLP × 粒度（TMA）
  最底层：2560 个 bank × tRC 48 ns ≈ 3.4 TB/s 随机 64 B——bank 数就是 HBM 的在途上限
每层同一账：L2、NVLink（~7000 个 64 B 事务）、PCIe、网卡在途表、UCIe 信用
封闭系统膝点：N* = Z / D；网卡 2 µs 往返 / 2.7 ns 服务 → 在途表 ≥ 740
推理：吞吐 = batch / TPOT，但 TPOT 随 batch 涨；Llama-3-70B 8×H100：batch 64 → 14 ms / 4460 tok/s，256 → 38 ms / 6770
排队：M/M/1 的 1/(1−ρ) 只是一半，Kingman 的 (C_a²+C_s²)/2 是另一半；80% 利用率下强突发延迟是泊松的 4 倍
并发逐层提供、逐层消耗，任意一层不足整条链卡住

ESL：每个资源 = (吞吐, 延迟(ρ, c), 最大在途) 三元组；整体 = min；Little 定律是稳态校验尺、瓶颈定位器和膝点计算器
```

**下一篇预告：《分层 Roofline 与算术强度计算：一个 kernel 落在哪个屋顶下》**——经典 roofline 只有一条内存屋顶，真实芯片有 HBM、L2、L1 / shared memory、寄存器四层；怎么算一个 GEMM、一个 attention、一个 elementwise 在每一层的算术强度，tiling 怎么把一个 kernel 从 HBM 屋顶下挪到 L2 屋顶下，以及为什么 MFU 的上限往往不是算力而是某一层的带宽。
