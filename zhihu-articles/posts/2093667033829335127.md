**让不同厂商的大模型进同一个「群聊」按能力干活：dsh-teamcast 的设计与实现**

## 一、写这篇文章的初衷

大家好，我是 dsh-teamcast 的作者，一个还在成长中的开发者。这个项目是我最近持续投入的一个开源小项目，目前跑通了一个基础版本。开发过程中我收获很多，但也越来越清楚地意识到：一个项目如果只靠我一个人闭门造车，很多设计问题、代码习惯问题很难被发现。

所以想通过这篇文章把项目介绍给社区里的各位开发者和前辈，希望得到一些真实的反馈。代码结构、实现方式、命名、文档，或者任何您觉得可以改进的地方，都可以直接告诉我，我会认真看、认真改。

## 二、dsh-teamcast 是什么

先说痛点。现在做多智能体协作，主流思路是「编排」：提前画好 DAG / workflow，把每个节点绑死某个模型，然后照着图执行。但我自己日常用下来，总觉得这不太像真实团队干活的样子——真实团队更像一个群聊：群里有个 Lead，任务来了临时拉人、按每个人的能力派活，而不是提前把组织架构和每个人的岗位焊死。

dsh-teamcast 就是冲着这个场景做的：它是一个 deepseek-harness（dsh）的 **群聊分派插件** ，构建在官方 Agent Teams（Lead + 具名 teammate + 持久邮箱 + 共享任务板）之上，让 Lead 在对话过程中，按「成员能力画像」把子任务分派给 **不同厂商、不同型号的模型** 去执行。比如 Lead 自己用强推理模型做设计，把批量机械性工作派给快而便宜的模型，代码审查交给一个独立成员——成员的 provider/model 是不是合法，由一份「成员名册」硬性约束；可用范围由用户自己随时编辑，Lead 不能越界挑模型，不带路由的成员默认继承 Lead 自己的模型。

一句话概括： **把「这个子任务用哪个模型」从提前配置变成对话中的一等公民，同时用白名单守住边界** 。

它不是追求技术炫技的玩具，也不是大而全的平台，就是一个我从自己日常痛点出发的小工具。目前远谈不上成熟，但我希望它能真正有用。

项目地址： [https://gitee.com/luo_yixuan/dsh-teamcast](https://gitee.com/luo_yixuan/dsh-teamcast)

## 三、目前已经完成的部分

- **核心流程闭环** ：包装官方 `spawn_teammate` 工具，增加 `provider` / `model` / `reasoning_effort` 三个可选参数；Lead 派活时指定成员模型，路由经底层注入生效，官方的任务板、邮箱、记账逻辑原样保留。
- **成员名册（roster）+ fail-closed 闸门** ：spawn 时的显式路由必须命中名册或额外放行规则（ `allowedRoutes` ），否则直接拒绝并给出可操作的错误提示；不带路由（继承 Lead）永远放行，模板里的推荐模型只作展示提示。
- **24 个内置职业团队模板（共 122 名成员）** ：覆盖前后端、移动、游戏、嵌入式、DevOps、数据分析、翻译、安全、法务金融、电商、教育、供应链等场景，每队 4-7 人，成员描述写到工具级，每份 SOP 是带质量门禁的流水线；设置页一键导入即建队（导入为整册替换，单团队模式）。
- **两个只读发现工具** ： `list_group_models` 返回按团队分组的名册能力表， `list_team_templates` 返回模板构成与分工 SOP——Lead 派活前先查表。
- **Web 设置卡片** ：两级导航（模板网格 ↔ 团队详情）、三步向导添加成员、级联 provider→model 选择器（选择面从全量 592 条收敛到单家几十条）加插件总开关，全部可视化编辑，改完即热生效。
- **63 条单元测试全绿** ：覆盖路由闸门、透传层、工具包装三大模块（ `pnpm test` 可复现）。

当前版本 v0.1.0（2026-10-09 发布），定位是实验包，这些主要用来验证方向，细节还有很多要补。

## 四、项目结构与技术思路

技术选型上我尽量选自己熟悉、社区资料多的：TypeScript 5.6 + cordis 插件体系（声明式 `inject` 依赖）+ schemastery 配置 + vitest 单测 + esbuild 构建 Web 客户端，Node ^22.19 || >=24，MIT 协议。源码约 2600 行，其中路由策略 `route-policy.ts` 刻意写成 **纯函数、零框架依赖** ，方便单测和移植。

获取代码：

```text
git clone https://gitee.com/luo_yixuan/dsh-teamcast.git
pnpm install
pnpm build:all     # 宿主（tsc）+ Web 客户端（esbuild）
pnpm test          # vitest，63 条单测
pnpm typecheck     # tsc --noEmit

```

下面几个设计点，是我最没把握、也最希望前辈们看看的。

### 4.1 名册：一份数据，三种身份

roster 条目是 `{name, description, provider, model, team}` ，我让它同时充当三样东西： **spawn 白名单** （provider/model 必须命中）、 **能力画像** （description 动态注入 Lead 的 systemPrompt，成为 Lead 「看人派活」的依据）、 **团队分组** （配合团队 SOP 做模板化分工）。

好处是配置面小、Lead 天然知道「队里都有谁、各擅长什么」；但我也怀疑这是不是把三个概念耦合得过早了，见第六节。

### 4.2 路由闸门：宁可拒绝，不放脏路由

闸门语义是 fail-closed 的：

```text
// route-policy.ts
if (!gate.allows(provider, model)) {
  throw new Error(
    `child LLM route "${provider}/${model}" is not in the group-chat roster; allowed: ${gate.describe()}`
  )
}

```

名册条目缺字段、配置写坏、provider 未注册，一律拒绝，且错误信息里带上当前合法路由清单，引导用户去设置页补名册。模型给什么畸形入参（类型用 `unknown` 接）也要给出可读错误。我担心的是：对个人开发者太严了会不会烦？要不要加一个 warn-and-allow 的宽松模式？

### 4.3 最 tricky 的部分：用 AsyncLocalStorage 补上跨层路由透传

这是整个项目里我做得最不安、也最想请教的一段。

调研中发现：官方 `agentTeams.spawnTeammate()` 内部调用 `subagents.startContinuable(...)` 时 **硬编码了请求体，不透传 `agentOptions`** （0.1.7 / 0.2.0-rc.2 实测均如此）；而底层的 `resolveChildAgentOptions()` 本身完全支持 `agentOptions` 覆盖父路由。也就是说，缺的只是「工具层 → 服务层」这最后一公里。

我的方案是用 `AsyncLocalStorage` 携带路由，而不是 fork 官方包：

```text
spawn 包装层 execute
   └─ als.run(route, 官方 execute)          ← 路由进 ALS
          └─ 官方 agentTeams.spawnTeammate() ← 官方记账原样保留
                 └─ startContinuable（包装） ← 读 ALS，注入
                        └─ request.agentOptions = { provider, model }

```

这样官方的 journal / roster 记账一行不改，升级兼容面最小；ALS 跨 await 传播，并发 spawn 各走各的 store 互不串扰；没有 store 时包装层纯透传，行为与未装插件完全一致。代价是 monkey patch 了官方服务的 `startContinuable` ——卸载时我用 `Object.getOwnPropertyDescriptor` **精确还原原属性描述符** （而不是 delete，避免把实例自有方法删没），并用 `Symbol.for` 做跨模块副本的幂等标记。

这个做法长期是否健康？有没有更优雅的扩展点我漏掉了？真心求指点。

### 4.4 热生效：volatile + 现读，不持有快照

全部配置字段标了 cordis 的 `.volatile()` ：设置页表单写入 profile 的 `cordis.patch.yml` ，Loader 原地热更，不重启 fiber、不重挂工具。有个我踩过才理顺的细节：插件自带的 bundle 补丁文件只在首次安装时兜底默认值，它不在热更监视列表里，用户编辑的真正落点是 profile 的同名文件——两个「长得一样」的配置文件，职责并不相同。配套地，我让所有读取点 **每次现场读** （ `readVolatile` ），systemPrompt 段也注册成动态函数 `() => string` ，名册改完下一次装配立刻生效。我尚未想明白的坑是：热更发生在一个工具调用中途时，前后两次现读可能拿到不同版本配置，要不要做调用内快照？

### 4.5 分层策略：分配规则与 skill 都做了分层

Lead 怎么决定「活给谁」？我调研后的结论是 description 匹配是主流且有效的（竞标制没有产品先例、多轮广播烧 token），所以做了三层，逐层降级：

1. **模板固定分工** ——用户点名某职业团队，按该队 SOP 切分；
2. **描述匹配** ——按名册 description 把子任务对到最合适的成员（难活给强推理模型，批量活给快模型，审查给非作者成员）；
3. **用户点名** ——用户 @ 了谁就用谁。

skill 也分两层：Lead 的指派方法论（五步指派程序 + 四要素 + 「何时不要委派」）固定注入 prompt、不受开关控制；12 条执行类角色 skill 由 `enableSkills` 开关控制，默认不注入、不自动匹配。

### 4.6 角色 skill：站在开源社区的肩膀上改造

我不是提示词工程专家，所以写角色 skill 时没有闭门造车，而是站在开源社区已有成果上改造。来源与授权都在代码注释里做了说明，均允许复用：

- **Lead 的指派方法论** ，融合了四家的长处： - **Anthropic Claude Code subagent 官方模式** 的指派方法论（仅借鉴思路，未复制任何文本）——「读名册 → 拆分写域 → 四要素指派 → 验证路由 → 评审交付」的五步程序；其中四要素指派要求每条派活消息必须同时包含目标（GOAL）、输出格式（OUTPUT FORMAT）、边界（BOUNDARIES）、上下文（CONTEXT），缺任何一项就说明任务还不具备派发条件，宁可先自己补齐，避免成员返工；
- **MetaGPT** 的 SOP 流水线思想——按角色职责把任务拆成带质量门禁的工序；
- **LangGPT** 的结构化工作流写法——把方法论写成可逐步遵循的流程，而不是散落的形容词；
- **CrewAI 示例** 的 goal 表达——动词开头 + 可交付的验收标准。
- **122 个成员的执行类角色 skill** ，基于 [awesome-chatgpt-prompts](https://github.com/f/awesome-chatgpt-prompts) （CC0 1.0）、 [MetaGPT](https://github.com/geekan/MetaGPT) （MIT）、 [LangGPT](https://github.com/langgptai/LangGPT) （MIT）、 [CrewAI examples](https://github.com/crewAIInc/crewAI-examples) （MIT）改造。这份来源与授权清单也同步放在仓库 README 的「致谢」一节。

改造过程中我总结了几条「专业 skill 和普通 skill 的差距」，也放在代码注释里，顺带求做提示词工程的前辈帮我看看这些总结是否以偏概全：

1. 交付物要具名——写成可验收的名词短语，而不是「帮我分析一下」；
2. 负面约束要显式——NEVER / DO NOT 必须真实存在；
3. 输出结构提前给定——结构即质量；
4. 人设用可核验的特异点替代形容词——「检查缺失的 import」比「优秀的 QA 工程师」有用；
5. 精简——1-4 句足够，不写 2000 词的人设小作文。

## 五、我自己觉得还不够好的地方

写这篇文章，很大一部分原因就是我知道项目还有不少问题。我自己已经看到的：

- **实验包，无稳定性承诺** ：本插件 monkey patch 了官方内部服务，Agent Teams 的 journal / mailbox 接口随 dsh 升级就可能失效；我对 0.1.7 / 0.2.0-rc.2 两个版本做过实测（peer 依赖也按 0.1.x / 0.2.x 的并集声明），但这不是长久之计；
- **只有单测，没有端到端** ：63 条单测覆盖了闸门、透传、包装，但真实多模型并发 spawn 的场景压测还没做；
- **写冲突只靠 prompt 软约束** ：官方限制所有成员共享同一工作目录，本插件只解决「谁用什么模型干活」，不解决文件锁；写域不相交目前只写在指派规则里，没有硬性拦截；
- **成本账没算过** ：跨 provider 不共享 KV cache，同样的任务拆给多个厂商模型，token 成本是否反而更高，我没有数据；
- **文档不足** ：README 有安装运行说明，但设计决策的来龙去脉大多埋在代码注释里。

## 六、希望大家重点帮我看看的几个方向

如果各位愿意花一点时间看看代码，这几个具体问题是我最想请教的：

1. **跨层透传的方案选择** ：AsyncLocalStorage 注入 vs 改用参数逐层透传 vs fork 官方包，哪条路长期更健康？
2. **fail-closed 闸门的松紧** ：现在名册外路由一律硬拒绝，是否应该提供 warn-and-allow 的宽松模式？名册「白名单/画像/分组」三合一是不是过度耦合？
3. **热更与一致性** ：volatile 现读有没有我没想到的一致性坑？
4. **后续迭代优先级** ：是先补端到端测试和成本统计，还是先做路由的观测性（比如每次 spawn 记录实际模型与耗时）？又有哪些设计您觉得应该果断砍掉？

我不怕问题多，只怕问题一直藏在那里。哪怕听起来很小的建议，我都会认真看、认真改。
