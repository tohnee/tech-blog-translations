DeepInfer 和 deepseek-recipe 可以接成怎样的一套系统？我的判断是：两者具备在 token ID 层面衔接的条件，拼起来有望得到推理与协议编解码的核心。要接住线上流量，还需要补齐服务级缓存、计算阶段分离和副本负载均衡。

这个判断有个前提：我没有做端到端实测。官方没有提供把两个仓库接好的集成包或教程，下面讨论的是接口职责、公开机制和服务边界。

2026 年 10 月 20 日，DeepSeek 正式开源 DeepInfer，仓库创建于 10 月 16 日。deepseek-recipe 的仓库创建得更早，是 9 月 10 日。截至 10 月 20 日，两个仓库分别约有 7800 和 1200 颗星；DeepInfer 发布当天就突破了 5000 颗星。这些数字只是当时的热度快照，不能作为性能或成熟度的证明。

我认为，判断这次开源的工程价值，可以先读 DeepInfer README 的这一节：“Required for a complete inference service (not included in this release)”。官方把完整服务还缺什么列了出来，选型的边界也写在这里。

Q&A 把 recipe 描述为推理系统的编解码组件。两个 README 没有互相指引，许可证和用途也不同；recipe 自带的 server-rs 和 server-py 是 mock 推理示例。把这几条放在一起，才能准确理解“可以拼起来”的含义。

## 两个仓库在什么地方交接？

先沿一条请求看职责。用户发出的请求，可能采用 OpenAI Chat Completions、OpenAI Responses，也可能采用 Anthropic Messages。它们的字段、消息结构和流式事件各有约定，同一套服务想兼容三者，需要先统一输入。

recipe 把外部请求解析成内部对象 Conversation，再根据模型的对话模板生成 prompt，最后通过 tokenizer 编码成 token ID。Conversation 管对话的结构，prompt 管模型实际看到的模板，token ID 则是模型计算时接收的整数序列。

DeepInfer 接手计算。Prefill 处理整段输入，并建立引擎本地的 KV cache；decode 随后逐步生成 token，直到满足停止条件。KV cache 保存模型已经算过的中间状态，后续计算可以复用。批处理、采样、显存管理，也由引擎这一层处理。引擎本地缓存和跨节点的服务级缓存，需要分开理解。

生成的 token ID 还要经过 recipe。它负责解码文本，识别思考结束标记和 DSML 标记，再组织成相应 API 的响应及流式事件。对应用而言，请求和回答都表现为协议数据，底下经过了输入编码、模型计算、输出解码。

![](https://pic1.zhimg.com/v2-63ce5489beeea39924d6cf92c9cf948c_r.jpg)
*两端编解码、中间计算。接口职责可衔接，服务化能力仍须补齐，本文未做端到端实测。*

两者的交接点因此落在 token ID。但“双方都处理 token ID”只能说明接口方向能够衔接，接入时仍要核对 tokenizer 版本、特殊 token 的位置和对话模板。这几项一旦不一致，同一串整数就可能失去原本的语义。

对应用开发者，这条链的实用之处在于定位问题：协议字段和流式事件由编解码层处理，生成速度与显存使用主要看引擎，跨副本路由和缓存复用还需要服务层参与。接口清楚了，延迟或输出异常才有地方追。

## DeepInfer 把哪些事情做深了？

DeepInfer 自称驱动 DeepSeek 大规模生产服务的高性能推理框架，本次开源提供的是离线推理能力。生产部署的经验进入了代码，开源交付的范围则停在离线推理，线上接入、排队和延迟承诺仍要另外建设。

它采用 Apache-2.0 许可。支持范围也列得很具体：模型仅 DeepSeek-V4.1-Flash，硬件仅 NVIDIA SM100 和昇腾 950。其他模型、其他代际的卡，不能从当前支持声明里获得兼容保证。准备采用它时，模型和硬件是否匹配，应当排在性能讨论之前。

官方给出的部署策略同样有明确条件。Prefill 使用 8 卡机器，EP2 至 8、DP2 至 8，在显存允许时尽量采用较小并行度；decode 使用 64 至 128 卡超节点，EP64 至 128、DP64 至 128，在卡数允许时尽量采用较大并行度；Vision Encoder 通常可以单卡部署。EP 是专家并行，DP 是数据并行。不同阶段对算力和带宽的需求不同，适合的部署规模也不同。

支持范围收窄之后，算子、注意力实现和调度器可以围绕固定组合优化。README 说明，项目最初主要基于 vLLM 构建，也参考了 SGLang 与 TensorRT-LLM；它使用独立代码库，没有 fork vLLM。

这里有几项值得具体看代码的机制。

DSpark 使用投机解码：先起草 5 个 token，再根据置信度决定验证多少。它按各 draft token 的预期接受率评估前缀，选择预期有效吞吐更高的前缀子集送去验证。这样做是在减少价值较低的验证计算，保留较有把握的草稿。

官方线上报告称，从固定验证 5 个改成变长验证后，每步验证数降到 3.2 至 4.4 个，平均接受长度几乎不变，吞吐提升约 6%。这是报告给出的生产工作点收益，不能直接套到任意模型、硬件或离线任务上。

异步调度处理的是 CPU 与 GPU 之间的等待。CPU 的 schedule(N+1) 与 GPU 的 forward(N)/sample(N) 重叠执行，让下一步调度尽可能提前准备，减少计算设备等调度结果的时间。

batch-invariant 和确定性采样则服务于复现：同一请求放进不同 batch，仍能保持结果一致。两项能力目前都只支持 NVIDIA。启用 batch-invariant 需要设 `DEEPINFER_BATCH_INVARIANT=1`；确定性采样还要设 `DEEPINFER_ENABLE_MTP_VARLEN=0`，并向 `SamplingParams` 传固定 `seq_seed`。把两个开关条件混在一起，排查结果差异时容易漏项。

还有 SWA Bounded Replay，针对滑动窗口注意力进行有界重放，重算最近 128 个 token 的窗口。这里的 128 描述重算窗口，使用时需要与缓存保留长度等其他配置分开核对。

我认为 DeepInfer 最值得借鉴的，是它对适用范围的取舍。模型、硬件和场景确定之后，优化就能深入到每一层；相应地，拿它运行自己任意一种模型的空间也很有限。研究推理机制的人可以从中获益，做通用服务选型的人则要先接受这些限制。

## 77K 输入、400 毫秒首 token，该怎样理解？

官方部署报告给出的线上统计是：平均输入 77K token，缓存命中率 96%，TTFT 400 毫秒。TTFT 指从请求到首个输出 token 的等待时间。Q&A 还披露，单集群每天处理 155 万亿 token，按谷价计算的每卡每小时收入为 38 美元，原文口径是 overall revenue。

155 万亿除以一天的 86400 秒，平均每秒约为 18 亿 token。这个折算有助于理解系统量级；38 美元则是收入指标，不能据此推算利润。更重要的口径是，这些数字来自官方对完整生产系统的披露，开源版 README 没有给出同样基准下的复现成绩。

96% 的缓存命中率依赖本次没有开源的服务级缓存。报告中，Block KVCache 存放在 3FS 集群，使用约 100 PiB SSD；agent 流量的 TTL 为 3 天，chatbot 为 7 天，峰值聚合读带宽为 10 TiB/s。TTL 表示缓存保留时间。命中链路里，前缀哈希匹配进入关键路径，取回 KV 和换入则异步执行。

这组配置解释了长输入和较低首 token 延迟为什么要放在一起看。平均 77K 的上下文，如果大部分能从缓存复用，和每次重新计算整段输入，是两种负载。缓存位置、路由和换入能否配合，直接影响用户实际等多久。

对技术管理者，这里可以得到一条明确的评估边界：采用开源引擎后，需要用自己任务的缓存条件重新测量。不能把完整生产系统的 96% 命中率、400 毫秒 TTFT，直接当成部署开源版后的服务承诺。

在每秒约 18 亿 token 的量级上，调度等待、重复计算和资源空转会累积成显著差异。复现能力则帮助工程团队判断，一次修改究竟改变了计算行为，还是只碰上了不同的批处理组合。这些细节值得学，收益仍要在自己的环境里确认。

## 两张性能图，先看轴，再看结论

![](https://pic4.zhimg.com/v2-de081f67e8761b27945471a061181d6b_r.jpg)
*官方 prefill 测量：4 张 SM100，上下文 131072；横轴为每步延迟，纵轴为每 GPU 非缓存输入吞吐。*

Prefill 图使用 4 张 SM100 GPU，输入上下文为 131072 token。横轴是每步延迟，纵轴是每张 GPU 的非缓存输入吞吐。这里的“非缓存”意味着输入需要实际参与计算，线上统计中的 96% 缓存命中率不能带入这张图。

这张图能帮助判断该测试条件下吞吐与延迟怎样变化。它不能单独说明，带缓存、带路由和排队的线上请求能获得怎样的首 token 时间，也不能被解释成所有工作负载的性能上限。

![](https://pic2.zhimg.com/v2-af0aa888b5b6dcf7e6a55c0908d4e6a9_r.jpg)
*官方 decode 测量：64 张卡；横轴为每用户生成速度，纵轴为每 GPU 输出吞吐，不能与前图直接比较数值。*

Decode 图使用 64 张卡，横轴是每个用户的 token 生成速度，纵轴是每张 GPU 的输出吞吐。读横轴时要注意方向：每用户 token/s 越高，表示单用户生成越快。图中展示的是单用户速度和整体吞吐之间的取舍。

Decode 逐步输出，往往更受 KV cache 访问和显存带宽影响。增大 batch 可以提高整体吞吐，却可能牺牲单请求速度；减小 batch，资源利用和吞吐又可能下降。Prefill 更偏重整段输入的计算，两阶段的资源需求不同。

两张图的集群规模、输入输出条件和坐标口径不同，数值不能直接横比。它们共同支持一个部署判断：prefill 和 decode 值得分别寻找合适的并行与调度策略，阶段分离有明确的资源依据。

看类似报告，可以先核对坐标轴、输入输出长度、卡数和缓存状态。这几项对齐之后，性能曲线才有比较意义。

## recipe 怎样减少协议适配的重复工作？

多协议兼容的麻烦，常常落在细节上。工具调用怎样表达，system prompt 放在哪里，停止原因怎样映射，流式事件在什么边界结束，都要按各自协议处理。一处映射出错，业务层可能就会把正常结束当成截断。

recipe 用 Conversation 承接这些差异。消息、角色、内容块、工具调用和思考内容，都先进入统一结构。协议解析负责把外部请求转进来，模型适配负责把 Conversation 渲染成目标模型的对话模板。

这让协议与模型的变化可以分别处理。增加协议时主要增加解析器，换模型时主要调整模板适配；HTTP 业务代码不必到处重复判断三套协议的字段。对已有后端，这是一层可以嵌入的编解码库。

输入编码还划了一条值得注意的安全边界。角色、思考边界、工具调用会用到特殊 token，而用户文本、工具返回、工具参数里，也可能出现这些标记的字面量。recipe 在构建 prompt 时记录主动插入的特殊 token 及其位置，再把它们映射到对应 token ID；普通文本则按基础词表编码。

因此，用户输入里一段与思考结束标记长得相同的文字，不会自动获得控制 token 的身份。这个保证针对编码行为，语义层面的提示注入仍需要调用方另行处理。

图片 URL 也有调用方必须接住的边界。`ReqwestImageFetcher` 默认可以连接任意地址。如果服务接受不可信请求中的图片 URL，需要自行配置 `DestinationFilter`，约束可访问的目标；否则会留下 SSRF 入口，也就是让外部输入诱使服务端请求不应访问的地址。

输出端同样区分控制 token 与普通文本。思考结束标记、DSML 标签按 token ID 识别，模型用普通 token 拼出的同样文字仍会保留为内容。跨 chunk 的分隔标记用增量 KMP 匹配，避免流式分块把一个标记截成两段后漏识别。KMP 在这里承担的是连续匹配分隔符的工作。

使用条件也需要一起看。Python 要求 3.10+，安装包是 `deepseek-recipe`；Rust 可使用 `cargo add deepseek-recipe@0.2`。请求没有填写 `max_tokens` 时，库会按模式补默认值：非思考 8192，思考 65536，思考加 max effort 131072。接入时应确认这些默认值符合自己的输出预算。

recipe 支持 V4 和 V4.1，DeepInfer 当前仅支持 V4.1-Flash；V4 请求里的图片会被替换为 `[Unsupported Image]`。两者选型时，模型范围要分别核对，协议层能表达一个请求，并不能保证引擎可以执行它。

recipe 采用 MIT 许可，不提供模型推理、工具执行和 HTTP 传输。模型后端由调用方提供，编解码本身不接管 GPU 推理。团队可以把它作为同语言库或 sidecar 嵌入现有服务，但仍要负责 HTTP 服务、推理后端和工具执行。

## 从离线核心到线上服务，三块缺口难在哪里？

这三块都有跨节点状态。只在一台机器上跑通计算，不能验证它们在集群里的行为。

第一块是服务级分布式 KV cache。请求前缀能不能复用，缓存在哪张卡，路由到没有缓存的副本后要不要重算，显存不足先淘汰什么，都需要共同决策。96% 的命中率属于这套完整机制的表现，开源引擎只覆盖其中的计算与本地状态管理。

第二块是 Vision Encoder / Prefill / Decode 分离。视觉编码、整段输入计算、逐步生成，资源需求不同，拆开部署有机会各自选择更合适的并行方式；拆开以后，缓存必须跨阶段传输，调度器还要安排各阶段的衔接。某一段排队或传输抖动，会继续影响下一段。

官方说，阶段分离在引擎侧大部分已经实现。本次未包含的部分，是把这些能力组织成可运维的服务。评估缺口时应保留这个区别，不能把它写成所有底层实现都不存在。

第三块是 P/D 的 DP 副本负载均衡。Prefill 和 decode 有多个数据并行副本，请求长短、缓存位置和阶段占用又各不相同。按轮询简单分配，可能把长请求和缓存未命中集中到一个副本。调度器需要掌握更广的状态，并在吞吐与等待时间之间做选择。

Q&A 披露的生产策略可以说明它细到了什么程度。Prefill 按输入长度分四桶：小于 16K、16K 至 64K、64K 至 256K、不小于 256K。每桶根据上一轮 compute-quota 需求动态分配引擎，桶内再把请求交给当前 compute-quota 最低的 DP rank。

Decode 同时考虑请求数和 KVCache 总长度：短请求交给并发较小、缓存较长的卡，长请求交给缓存较短的卡。MoE 侧还在每张卡保留冗余专家，并根据最近 N 步统计定期重排。这些细节说明，均衡对象既包括请求，也包括缓存和专家的负载。

官方 Q&A 点名 KV cache management 和 load balancing 与内部基础设施耦合很深；阶段分离则属于引擎侧大部分已有、服务化还需补齐。可复用代码与集群运营之间的界线，需要按这三个具体条件理解。

我认为最难补的是负载均衡。调度器无法预知后续请求，却必须现在决定请求去哪里；这次决策又会改变下一轮的缓存位置和负载。它需要持续反馈，单次离线测试很难覆盖运营中的变化。

## 谁值得用，应该先验证什么？

| 维度 | DeepInfer | deepseek-recipe |
| --- | --- | --- |
| 定位与许可 | 生产推理框架的离线能力；Apache-2.0 | 协议与 token 编解码库；MIT |
| 当前支持范围 | V4.1-Flash；NVIDIA SM100、昇腾 950；复现相关两项能力仅 NVIDIA | V4、V4.1；CPU 侧编解码；V4 图片有替换限制 |
| 调用方仍需负责 | 服务级分布式缓存、阶段分离服务化、P/D 数据并行副本负载均衡 | 模型推理、工具执行、HTTP 传输 |

推理工程师可以先看 DeepInfer 的离线能力和调度实现。模型、卡型满足条件时，用自己的任务建立吞吐基线，再评估具体机制是否值得采用。离线批处理成功，只覆盖计算链路的一部分，线上还要观察缓存、路由和排队。

后端开发者可以单独评估 recipe。它能减少三种 API 的重复编解码工作，适合已有服务逐步接入。实际验证应覆盖停止原因、工具调用、特殊 token 和跨 chunk 输出，同时明确图片访问过滤由谁配置。

管理者需要把预算分成两个问题：现有模型和硬件是否在支持范围内，团队是否有能力承担那三块服务工程。前者决定是否适用，后者决定集成与运维的投入。两个仓库有机会降低推理核心的起步成本，运营成本仍需单独估算。

只关注行业进展的读者，也可以据此判断这次交付的范围：引擎和编解码已经成为可复用的代码，完整服务还包含与特定集群基础设施紧密相关的控制面。能运行一个计算任务，和能长期接住真实请求，需要不同证据。

沿用 DeepInfer 这套栈，需要自行补齐上述服务能力。若采用 vLLM、SGLang、Mooncake、LMCache 等通用栈，可以先考察已有组件；它们与 DeepInfer 能否直接对接，仍要另外验证，不能从“有对应组件”跳到“即插即用”。

我的建议是按三步决定投入：先用 recipe 把目标协议请求转成 prompt，核对 token 序列；再在受支持的模型和硬件上，用 DeepInfer 跑离线基线；最后根据服务级缓存、阶段分离和均衡的建设成本，决定继续自建还是采用通用栈。把这三步的证据做出来，再讨论上线时间。
