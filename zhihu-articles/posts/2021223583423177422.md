近年来，视觉-语言模型（VLM）正在快速进入自动驾驶领域。早期的工作把VLM生成语义描述或高层意图，再交给下游规划器完成控制；在此基础上，有些工作进行了进一步探索，尝试把感知、推理和动作统一进单一的 VLA（Vision-Language-Action）框架中。这样的方向看起来更完整，也更有吸引力，但真正落到自动驾驶场景时，一个核心矛盾会变得非常突出：高层理解与推理往往是慢频的，而底层控制与轨迹更新却必须是快频的。这个关系其实很像人类的行为机制——大脑负责理解环境、局势推演、形成决策，小脑则通过控制四肢以更高的频率持续响应外界变化。二者并不是一个完全同步、同频的模块，而是在分工明确的基础上根据需求协同工作。自动驾驶系统也面临类似问题：语言理解能力很强，但动作生成和实时闭环控制对时延极其敏感，如果强行把所有模块捆绑在同一频率下统一运行，往往会在实际部署中遇到效率和实时性上的冲突。

针对这些问题，**南洋理工大学AutoMan Lab**携手**小米汽车**提出了 **AutoMoT**。这篇工作想回答的核心问题是：能不能既保留大规模预训练 VLM 的通用推理能力，又让模型具备自动驾驶所需的高频决策与规划能力，同时还能满足实时闭环部署的时延要求？

论文给出的答案是：可以，但前提不是把所有模块都硬塞进一个同步大模型里，而是让理解和动作在同一个框架中协作，同时在时间频率上异步运行。

## 一、为什么现有自动驾驶 VLM / VLA 方案还不够理想？

从现有研究看，把 VLM 接进自动驾驶系统大致有三条路线。

第一类路线，是把 VLM 作为上游场景编码器。模型先看图、理解场景，再把语义特征传给规划器。这类方案通常能增强可解释性，但高层语义和底层动作之间仍然存在明显的分布鸿沟。

第二类路线，是把 VLM 作为辅助系统或“第二系统”来使用，比如先输出高层决策、文本指令或中间条件，再去引导传统 planner 完成后续控制。这类方法的优势在于更灵活，也更容易和现有自动驾驶系统结合。但从整体流程来看，它还是把“理解”和“动作”拆成了两步，前面给出的高层信息，未必总能在后端顺畅地转化成具体动作。与此同时，为了适配具体驾驶任务，通用 VLM 往往还需要围绕任务重新设计和调整，最后真正发挥出来的可能只是其中一部分能力，原本更强的通用理解和推理潜力并没有完全释放出来，多少有点“大材小用”。

第三类路线，是让 VLA 直接端到端输出动作。这个方向最诱人，因为感知、推理、动作全都能统一起来。但问题也最尖锐：如果高层 reasoning 和低层 planning 被强行绑定到同一时间频率，系统推理成本会非常高，尤其是在需要快速重规划的闭环驾驶中，延迟会直接拉低性能。

因此，这篇论文抓住的核心矛盾非常明确：大模型的“理解”通常是低频但高价值的，自动驾驶的“控制”通常是高频且对时延敏感的。如果两者完全同步，系统就会变慢；如果两者完全解耦，又会丢掉统一建模带来的优势。AutoMoT 的目标，就是在这组矛盾之间找到一个更合理的平衡点。

## 二、AutoMoT 的核心想法是什么？

一句话概括，AutoMoT 不是简单地把 VLM 接到 planner 前面，而是把“场景理解专家”和“动作专家”放进同一个 VLA 框架里，通过分层联合注意力共享信息，再让两者以不同频率异步运行。

直观来看，它想实现的是：高层理解模块负责“慢思考”，动作模块负责“快反应”，两者共享语义上下文，但不必每一步都一起重算。这也是论文标题里 Asynchronous Mixture-of-Transformers 的真正含义。

## 三、方法设计：AutoMoT 到底做了什么？

论文整体围绕两个核心模块展开：Understanding Expert（UE，理解专家）和 Action Expert（AE，动作专家）。

![](https://pic1.zhimg.com/v2-22487299c74f858631246e6fdce306d8_r.jpg)
*AutoMoT 整体框架图*

### 1. Understanding Expert：保留预训练 VLM 的场景理解能力

AutoMoT 的理解专家直接采用 Qwen3-VL-4B 作为视觉-语言骨干，输入多视角、多帧 RGB 图像，以及系统提示词和用户提示词，输出场景理解与语义推理结果。

这里一个很值得关注的点在于，AutoMoT 最终没有继续微调这个理解专家，而是选择将其冻结。这个决定并不是拍脑袋得来的，而是作者在实验比较之后做出的判断。论文其实借此讨论了一个很有意思的问题：通用 VLM 进入自动驾驶之后，到底要不要继续调？

AutoMoT 真正想回答的，不是“要不要微调”这么简单，而是通用 VLM 在自动驾驶里到底应该承担什么角色。作者并不是反对专用化，而是认为代价要算清楚。预训练 VLM 最宝贵的地方，本来就在于它已经具备较强的通用理解和推理能力。如果为了适配驾驶任务去做深度微调，确实可能换来局部指标上的提升，但也可能同时削弱模型原本的推理能力。基于这样的考虑，AutoMoT 选择尽量保留 VLM 的通用能力，再把后续更高频、更专用的决策与控制交给动作专家来完成。

### 2. Action Expert：真正面向自动驾驶动作学习

动作专家主要负责两类任务：一类是决策，也就是输出未来 1 秒、2 秒、3 秒的 meta-action；另一类是规划，也就是输出未来轨迹点与空间路径点。

与很多只做轨迹回归的工作不同，AutoMoT 的动作专家不是单纯地“吐一条轨迹”，而是显式联合建模高层语义决策、时间序列轨迹和空间路径结构。论文中，AE 会输出未来 3 秒的离散 meta-action、0.5 秒间隔的时间轨迹点，以及表征参考路径的空间 route points。

这个设计的意义在于，规划不再只是几何拟合，而是带有决策语义的规划。模型学到的不是单纯“往哪里开”，而是同时学习“为什么这么开、接下来应该怎么开”。

### 3. 联合注意力：让理解、决策和规划在统一空间里协同

AutoMoT 的另一个关键点，是它不是把理解 token 和动作 token 粗暴拼接在一起，而是专门设计了一套混合注意力机制。

它的核心思想是：任务内部采用双向注意力以充分融合信息，任务之间采用带因果约束的跨任务注意力。这样一来，决策 token 可以看到理解 token，规划 token 则可以同时看到理解 token 和决策 token，但整体仍然保持任务层级上的因果顺序。

于是，模型内部形成了一个清晰的层级链路：理解 → 决策 → 规划。这个顺序不是通过传统模块串联硬编码实现的，而是在统一潜空间里的 attention mask 中完成的。

### 4. 异步推理：把“慢思考”和“快控制”拆成不同频率

这是 AutoMoT 最有特点的设计。

作者观察到，在自动驾驶中，场景语义理解并不需要每个控制时刻都完整重算，但动作输出必须高频刷新，否则闭环性能会明显下降。基于这个观察，论文把推理过程设计成一个多速率异步系统：UE 低频运行，负责周期性更新latent语义；AE 高频运行，负责每一步输出决策和规划；中间再通过 layer-wise KV cache 共享状态，让 AE 在高频前向时复用 UE 的上下文。

这个设计的价值，不只是把计算开销降下来了。更重要的是，AutoMoT 并没有简单把“高层 reasoning”丢给下游模块，而是通过 rollout joint 的整体架构，让 decision 和 planning 在每一层都能通过 layer-wise joint attention，对 latent reasoning 里真正有用的信息进行筛选和吸收。这样一来，即使高层 reasoning 中存在噪声甚至局部幻觉，也不会像传统 hierarchical pipeline 那样被原样传递到下游 policy，进而放大成决策误差。换句话说，AutoMoT 一方面保留了自动驾驶系统中感知、理解、决策和规划这些必要功能，另一方面又在结构上尽量减轻了层级式串联带来的误差传递问题。

## 四、实验结果：

论文主要从三个层面验证方法有效性：闭环驾驶、开环规划，以及预训练 VLM 能力边界。

### 1. 闭环 Bench2Drive：在真实驾驶式评估中展现出更强综合能力

![](https://pic3.zhimg.com/v2-c74f135e12c5da01ebbc2d45a96c7004_r.jpg)
*Bench2Drive 闭环结果表*

在 CARLA Bench2Drive leaderboard 上，AutoMoT 取得了 87.34 的 Driving Score 和 70.00% 的 Success Rate，整体表现优于表中的 SimLingo（85.07 / 67.27）以及多种 VLM 增强型端到端驾驶方法，体现出更强的闭环驾驶能力。

这组结果尤其值得注意的一点在于，论文专门提到 SimLingo 使用了基于 action dreamer 的仿真数据增强，而 AutoMoT 仅基于原始数据进行训练。换句话说，AutoMoT 的性能提升并不是建立在额外合成数据之上，而更能体现其模型架构本身的作用，尤其是理解模块与动作模块的分工设计，以及异步协同带来的效率收益。 除此之外，论文还专门比较了不同动作头的表现差异。其中一个有意思的现象是 Diffusion Head 虽然展现出更高的性能上限，但在行为稳定性上仍然存在一定挑战。相关细节作者放在了 appendix 中进一步分析。

### 2. 开环 nuScenes：预测精度与安全性取得了较好平衡

![](https://picx.zhimg.com/v2-395795104b42f86f5cd3e994c000f3e3_r.jpg)
*nuScenes 开环结果表*

在 nuScenes 开环规划评测中，AutoMoT 的 L2@1s / 2s / 3s 分别达到 0.14 / 0.29 / 0.54，平均 L2 为 0.32，平均碰撞率为 0.07%。

这组结果的价值不只在于误差低，更在于它同时把碰撞率控制在了很低的水平。对于自动驾驶规划来说，单纯追求更小的轨迹误差并不一定意味着更好的驾驶表现，因为有些方法虽然数值上更贴近真值轨迹，但在安全性上并不稳定；也有一些方法为了降低风险会变得过于保守。相比之下，AutoMoT 在预测精度和安全约束之间表现出了更好的平衡，这也说明它生成的轨迹不仅更准，而且更符合真实驾驶对可执行性和安全性的要求。

一个值得注意的细节是论文在 Open-Loop Planning Benchmark Results 中专门提到，OpenEMMA 和 AutoMoT 都没有对 understanding 模块做进一步微调。原因在于，这类微调虽然可能带来局部收益，但也可能引入灾难性遗忘，损伤模型原本的通用理解与推理能力。也正因为如此，AutoMoT 的提升并不是靠“把理解模块越调越专”换来的，而是在尽量保留通用能力的前提下实现的。论文后面也专门围绕这个问题做了进一步分析。

### 3. 冻结 VLM backbone 不是保守，而是在划清能力边界

![](https://pic2.zhimg.com/v2-ecd7b4fc499b048a56256a392a9d14f1_r.jpg)
*AutoMoT 范式对比图*

论文这一部分其实讨论了一个很关键的问题：通用 VLM 进入自动驾驶之后，到底哪些能力值得微调，哪些能力更应该保留下来。

作者对 AutoMoT 的 VLM backbone 做了自动驾驶数据微调，并在 LingoQA 和 OmniDrive 上进行了测试。结果发现，微调对 LingoQA 这类场景理解任务带来的提升非常有限，但在 OmniDrive 这类更贴近规划和动作层的任务上，收益会更明显。

与此同时，作者还把微调后的模型拿去测试一些通用基准，例如 ScienceQA 和 TallyQA。结果显示，前者变化不大，但后者这类更依赖复杂推理的任务却出现了明显退化。也就是说，面向自动驾驶的专门微调，真正受影响的往往不是基础识别能力，而是更高层的通用推理能力。

这也解释了 AutoMoT 为什么选择冻结 UE、重点训练 AE：预训练 VLM 更适合承担高层场景理解，而真正需要面向自动驾驶去强化的，是后续动作层模块。

### 4. 异步推理不仅可行，而且速度提升很明显

这部分是整篇论文最有说服力的实验之一。作者把同步版本 AutoMoT-S 和异步版本 AutoMoT 做了直接比较。结果显示，同步版平均 L2 为 0.322，异步版平均 L2 为 0.326；同步版时延为 0.38 秒，异步版时延为 0.05 秒。

也就是说，在规划精度只出现很小变化的情况下，推理时延下降了 86.8%，整体达到 7.6 倍加速。

这组结果很重要，因为它回答了一个很实际的问题：异步会不会因为信息变旧而明显伤害驾驶性能？论文的结论是，会有一点影响，但在合理的缓存和共享机制下，这个损失足够小，而速度收益非常可观。

## 五、总结

AutoMoT 这篇工作的价值，不只是又做了一个性能不错的端到端驾驶模型，而是提出了一种更合理的自动驾驶 VLA 组织方式。

它把高层理解和低层动作统一到同一个框架里，但又在执行频率上明确地区分“慢思考”和“快控制”；它尽量保留预训练 VLM 的通用推理能力，同时通过专门的动作专家去学习真正面向驾驶的策略与规划。

从这个角度看，AutoMoT 给出的重点并不只是“把大模型接进车里”，而是重新设计理解、决策和规划之间的协作关系。对于当前自动驾驶 VLA 这条线来说，这篇论文是一个很有代表性的工作，也给后续研究提供了一个非常清晰的方向：统一不一定意味着同步，异步也可以成为模型设计本身的一部分。
