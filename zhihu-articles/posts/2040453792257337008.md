## 1. 术语表（前置阅读）

| 术语 | 英文 | 说明 |
| --- | --- | --- |
| GPU 集群 | GPU Cluster | 多台带 GPU 的服务器，通过网络、调度器和存储组成统一计算资源池。 |
| Kubernetes | Kubernetes, K8s | 容器编排系统，负责调度 pod、管理资源和维护服务状态。 |
| Device Plugin | Kubernetes Device Plugin | 让 kubelet 发现并分配 GPU 等扩展设备的插件机制。 |
| MIG | Multi-Instance GPU | NVIDIA A100/H100 等支持的硬件级 GPU 分区机制，把一张 GPU 切成多个隔离实例。 |
| MPS | Multi-Process Service | NVIDIA 的多进程共享服务，让多个进程更高效共享同一 GPU 上下文。 |
| DCGM | Data Center GPU Manager | NVIDIA 数据中心 GPU 监控和诊断工具。 |
| GPUDirect RDMA | GPUDirect RDMA | 网卡直接访问 GPU 显存，减少 CPU 中转。 |
| GPUDirect Storage | GPUDirect Storage | 存储设备与 GPU 之间减少 CPU 拷贝路径。 |
| Topology | Topology | GPU、CPU、PCIe、NVLink、网卡之间的连接关系。 |
| NUMA | Non-Uniform Memory Access | 多 CPU socket 下内存访问距离不同，影响 GPU/网卡亲和性。 |
| 调度隔离 | Scheduling Isolation | 通过资源配额、污点、亲和性等机制避免作业互相干扰。 |
| 可观测性 | Observability | 用指标、日志、trace 判断 GPU 是否被正确使用和隔离。 |

## 2. 集群部署解决的不是“能跑”，而是“稳定地跑”

单机脚本只关心一个进程能否拿到一张 GPU。集群部署要同时回答：谁能用哪张卡，多个用户如何隔离，训练作业如何跨节点通信，推理服务如何弹性扩缩，GPU 异常如何被发现和摘除。

![](https://pic4.zhimg.com/v2-e3b246c1461a2b661b4ee52085443d2b_r.jpg)

追踪这张图时看两条链：调度链从用户请求到具体 GPU；观测链从 GPU 指标回到告警和调度决策。任何一条断了，集群都会出现“资源显示可用但作业慢/挂/互相影响”的问题。

用一次作业提交走一遍：用户提交一个申请 8 张 GPU 的训练 pod；scheduler 只看到节点标签和资源余量；kubelet 再通过 device plugin 分配具体 GPU；容器启动后 NCCL 根据可见 GPU 和网络接口建通信拓扑；训练开始后 DCGM 才能看到温度、ECC、利用率和 Xid。这里每一层只知道部分事实，所以排障不能只盯一个界面。

| 层级 | 它知道什么 | 它不知道什么 | 常见错觉 |
| --- | --- | --- | --- |
| Scheduler | 节点资源、label、taint | GPU 与网卡真实距离 | Pending 只等于没资源 |
| Device Plugin | 可分配设备和 MIG profile | 作业内部通信模式 | 申请到 GPU 就一定能跑快 |
| 容器运行时 | 设备节点、驱动库挂载 | NCCL rank 是否配对 | 容器能看到卡就配置正确 |
| DCGM/监控 | 温度、错误、利用率 | Python 队列和业务 SLA | GPU 利用率高就一定健康 |

## 3. Kubernetes 如何把 GPU 变成可调度资源

### 3.1 Device Plugin 的机制

Kubernetes 本身不知道 GPU 细节。NVIDIA device plugin 运行在每个节点上，向 kubelet 报告可用 GPU，并在 pod 启动时把设备节点、驱动库和环境变量注入容器。

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: cuda-worker
spec:
  restartPolicy: Never
  containers:
    - name: worker
      image: nvidia/cuda:12.4.1-runtime-ubuntu22.04
      command: ["nvidia-smi"]
      resources:
        limits:
          nvidia.com/gpu: 1
```

具体发生什么：

1. device plugin 向 kubelet 注册 `nvidia.com/gpu`。
2. scheduler 根据 pod 的 resource limit 找有空闲 GPU 的节点。
3. kubelet 调用 device plugin 的 allocate 接口。
4. 容器运行时把对应 GPU 设备暴露给容器。
5. 进程看到 `CUDA_VISIBLE_DEVICES` 中的逻辑 GPU。

失效信号包括 pod 一直 Pending、容器内 `nvidia-smi` 看不到 GPU、driver/runtime 版本不匹配。先查 `kubectl describe pod` 的 events，再查节点上的 device plugin 日志。

一个具体故障链是：pod 写了 `nvidia.com/gpu: 1`，但节点被打了 `gpu=true:NoSchedule` taint，pod 没有 toleration，于是 scheduler 从未把它放到 GPU 节点。此时容器还没启动，查容器日志没有意义；应先看 events。另一个链是 pod 已经 Running，但容器内 `nvidia-smi` 报错，说明问题更可能在 runtime hook、driver mount 或 device plugin allocate 阶段。

### 3.2 调度亲和性与拓扑

多 GPU 训练不只需要“任意 8 张卡”。同一节点内 NVLink 连接、GPU 与网卡距离、CPU NUMA 都会影响 NCCL 通信。一个 8 卡作业被拆到两个 PCIe 拓扑较差的节点上，可能比单节点 8 卡慢很多。

```bash
nvidia-smi topo -m
```

看拓扑时重点找：GPU 间是否 NVLink，网卡离哪些 GPU 最近，CPU affinity 是否跨 socket。K8s 里可用 node label、pod affinity、拓扑感知调度器或专用 batch scheduler 约束作业落点。

把 8 卡节点想成两组各 4 张 GPU，只有组内 NVLink 很强，组间走 PCIe/CPU。一个 TP=8 的训练作业如果跨两组频繁 AllReduce，每层都可能经过慢路径；同样 8 张卡用于 DP，则每 step 的梯度同步可以被 bucket overlap 部分隐藏，拓扑压力不同。映射回部署：TP rank 应尽量放在 NVLink 紧密组内，DP 组可以跨节点但要确认 IB/RoCE 带宽和网卡亲和性。

## 4. MIG：硬件级分区适合推理和小作业

### 4.1 MIG 分的是什么

MIG 把一张 GPU 的 SM、L2 slice、显存控制器和显存容量按 profile 切成多个实例。它不是简单的软件限额，而是硬件级隔离。

![](https://pic3.zhimg.com/v2-60c9da0cb2d2644005170f084d4d587e_r.jpg)

这像把一间实验室切成独立工位，每个工位有自己的电源和桌面。映射回 CUDA：工位是 MIG instance，桌面是显存切片，电源/工具是 SM 和 cache 资源。比喻不覆盖所有细节：MIG 仍共享整卡的外部系统、驱动和部分管理路径。

### 4.2 什么时候用 MIG

| 场景 | 是否适合 MIG | 理由 |
| --- | --- | --- |
| 多个小推理服务 | 适合 | 隔离稳定，资源利用率高。 |
| 教学和小实验 | 适合 | 防止一个用户占满整卡。 |
| 大模型单实例训练 | 通常不适合 | 需要整卡显存和全部 SM。 |
| 多 GPU NCCL 训练 | 谨慎 | MIG 实例间拓扑和带宽限制复杂。 |

失效信号是 pod 拿到了 MIG 设备但性能不稳、显存 profile 不够、NCCL 发现的设备拓扑不符合预期。先固定 profile，再用小基准测算每个 profile 的可用显存、吞吐和延迟。

## 5. MPS：共享上下文，不等于硬隔离

MPS 让多个 CUDA 进程共享同一 GPU 上下文，减少上下文切换，让小 kernel 更容易填满 GPU。它适合许多短小 kernel 或轻量推理并发，但隔离性弱于 MIG。

```bash
export CUDA_MPS_PIPE_DIRECTORY=/tmp/nvidia-mps
export CUDA_MPS_LOG_DIRECTORY=/tmp/nvidia-log
nvidia-cuda-mps-control -d
```

MIG 和 MPS 的区别：

| 机制 | 隔离级别 | 适合 | 风险 |
| --- | --- | --- | --- |
| MIG | 硬件级资源切分 | 多租户推理、小作业隔离 | profile 固定，灵活性较低。 |
| MPS | 软件级共享上下文 | 多进程小 kernel 并发 | 一个进程异常可能影响共享环境。 |
| 独占 GPU | 最强资源保证 | 大训练、性能敏感任务 | 利用率可能低。 |

如果目标是安全多租户，优先 MIG 或独占；如果目标是让可信进程提高并发利用率，MPS 更合适。

MPS 的典型收益场景是很多小 kernel：单个进程每次只发很短的 layernorm、采样或小 batch 推理 kernel，独占运行时 SM 经常空着；多个可信进程通过 MPS 共享上下文后，调度器更容易把小 kernel 填进空档。它的边界也要明确：MPS 不会把显存、cache、带宽硬切开，一个进程的异常内存访问、超大 allocation 或长 kernel 仍可能影响同一共享环境中的其他进程。

## 6. 网络和存储：训练慢常常不在 GPU kernel

跨节点训练的路径是：GPU 产生梯度，NCCL 通过 NVLink/PCIe 到网卡，再通过 IB/RoCE 到另一台机器，最后写回目标 GPU。任何一段慢，step time 都会拉长。

```text
GPU memory -> PCIe/NVLink -> NIC -> fabric -> NIC -> PCIe/NVLink -> GPU memory
```

检查顺序：

1. 单机多卡 NCCL all_reduce 基准，确认 NVLink/PCIe 路径。
2. 跨节点 NCCL 基准，确认 IB/RoCE 带宽和延迟。
3. 对比训练 step 的 NCCL trace，确认通信是否与计算重叠。
4. 检查数据加载是否拖慢 GPU，必要时看 GPUDirect Storage 或本地缓存。

跨节点慢的排查要把路径拆开，不要直接怪 NCCL。先用单机 all_reduce 看 GPU-GPU 路径；再用跨节点 NCCL tests 看 NIC-fabric-NIC；最后回到训练 trace，看通信是否暴露在 step 尾部。若独立 NCCL 基准很好，但训练仍慢，常见原因是 rank 拓扑和模型并行维度不匹配、数据加载让 GPU 等输入，或某些 rank 因热降频/错误重试变成尾部。

## 7. 可观测性和故障处理

GPU 集群应持续记录：利用率、显存、功耗、温度、ECC 错误、Xid 错误、PCIe replay、NVLink 错误、MIG 使用率、pod 到 GPU 的映射。

```bash
# 节点侧快速检查
nvidia-smi
nvidia-smi topo -m
nvidia-smi dmon

# K8s 侧定位
kubectl describe pod <pod>
kubectl logs -n gpu-operator <device-plugin-pod>
```

常见故障路径：

| 症状 | 首查位置 | 可能原因 |
| --- | --- | --- |
| Pod Pending | scheduler events | GPU 资源不足、label/taint 不匹配。 |
| 容器看不到 GPU | device plugin 日志 | runtime 未启用 NVIDIA hook。 |
| NCCL hang | NCCL 日志、网络 | 防火墙、IB 配置、rank 拓扑错误。 |
| 训练偶发变慢 | DCGM、Nsight Systems | 热降频、共享干扰、数据加载抖动。 |

一个简单 runbook 是先定位“作业是否启动”，再定位“GPU 是否可见”，最后定位“性能是否健康”：Pending 看 scheduler events；Running 但看不到 GPU 查 device plugin/runtime；能跑但慢查拓扑、NCCL、DCGM 和 Nsight Systems。每一步只回答一个问题，避免在驱动、K8s、网络和训练框架之间来回猜。

## 8. 思考题与练习

### 8.1 思考题

1. MIG 为什么比单纯设置显存上限更强隔离？
2. MPS 为什么能改善小 kernel 并发？它为什么不适合作为强隔离方案？
3. K8s 里申请 `nvidia.com/gpu: 1` 为什么不保证拿到拓扑最优的那张卡？
4. NCCL 训练慢时，为什么要先做独立通信基准？

### 8.2 动手练习

1. 在单节点上运行 `nvidia-smi topo -m`，画出 GPU、CPU、网卡拓扑。
2. 写一个申请 1 张 GPU 的 pod YAML，并观察 device plugin 注入的环境变量。
3. 对比独占 GPU、MPS、MIG 三种方案的适用场景。
4. 用 DCGM exporter 设计一组 GPU 告警规则。
