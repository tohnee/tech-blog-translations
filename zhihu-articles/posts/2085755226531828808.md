Megatron-LM 训练里目前有三种 CUDA Graph 模式：layerwise（partial）、full iteration 和 chunkwise。它们有各自的适用场景，本文将介绍它们的区别和选择方法。

## 一、LLM 训练适配 CUDA Graph 的难点

LLM 训练里上 CUDA Graph，主要有下面几类麻烦：

1. **一个训练 step 非常复杂。** 相比推理只抓 forward，训练的一个 step 内还要处理 saved activation、backward、gradient accumulation、recompute 和 optimizer 等众多模块的协同问题。
2. **遇到 dynamic shape 不能简单做 max padding。** 最典型的是 MoE EP 的 received token buffer size 问题。这个 size 是 runtime 决定的，在推理场景下 capture graph 直接预留 max size buffer 即可；但在训练里，这个 buffer 需要 save for backward，如果每个 layer 都做 max padding 显存直接爆炸。
3. **训练过程在变得越来越动态。** Padding 只能固定一部分物理 shape，但 THD 序列长度、一个 global batch 内的 microbatch 数、每个 microbatch 的并行配置（这里主要指 dynamic CP）都可能根据样本情况动态配置。
4. **PyTorch 很多操作是不 graphable 的。** 很多 PyTorch op 都可能隐式触发 host sync 或 dynamic shaped output；开发者写新一个 feature 时，早期通常只关注正确性，不会特意检查有没有引入 graph-breaking op。后面部署上线时要针对每个 feature 单做一遍 CUDA Graph 兼容，费时费力。幸好现在有 agent，做 CUDA Graph 的兼容和正确性验证比以前轻松多了。这个 [PyTorch CUDA Graph Best Practice 文档](https://docs.nvidia.com/dl-cuda-graph/latest/index.html)[^1] 也记录了在 PyTorch 里做 CUDA Graph 兼容的 best practices。
5. **Memory overhead。** PyTorch 的 CUDA Graph private mempool 机制给 CUDA Graph 提供了显存安全的保障，但如果不精心管理，也有加重显存负担的风险。比如本文我们介绍的是在 forward-backward 阶段抓 CUDA Graph，途中用到的 memory 被放到 private pool 里防止 eager allocation 污染。后面进入 optimizer step 时，private pool 大部分 block 已经空闲出来，但如果 optimizer step 走 eager 模式，就无法复用到 private pool 的空 block，造成显存异常增长。另外，CUDA Graph 本身也需要永久的 static input/output buffer 显存占用。

针对这些问题，Megatron 设计了一套完整的 CUDA Graph 方案：提供 layerwise（partial）、full iteration 和 chunkwise 三种 capture 粒度。它们本质上是在兼容性、调度弹性和收益之间做取舍。在典型 workloads 如 Qwen/DeepSeek/GLM 上，Megatron 都做了 CUDA Graph 的端到端验证和 memory overhead 调优，对开发者在自己的私有 workload 上做 CUDA Graph 支持有珍贵的借鉴意义。

## 二、从 Layerwise (partial) CG 做起

Megatron 训练侧最早落地的 CUDA Graph 模式是 layerwise，即每个 Transformer Layer 各自抓 graph：

![](https://picx.zhimg.com/v2-99f80cf55c30cf227510c4dd4a95ad7f_r.jpg)

在 PP 的配置下，为避免后续 microbatch 的 forward 覆盖尚未执行 backward 的 context，我们实际每卡要抓 `num_layers × num_microbatches × 2` 个 graph。具体分析见 [Megatron-Core MoE technical report](https://arxiv.org/abs/2603.07685)[^2] 第 4.3.6 节，这里不再展开。

Layerwise 模式把 microbatch loop、TransformerLayer 外的主 loss/loss reduction、PP P2P、gradient accumulation 的外层调度和 optimizer 等都留在 eager，只抓最 critical 的 TransformerLayer forward & backward。同时还支持在一个 Transformer Layer 内更细粒度地选取 capture 范围：如果整个 Transformer Layer 的 shape、地址和执行路径都稳定，可以直接做 whole-layer capture；如果层内仍有一段不兼容，也可以只选其他部分做 capture。后一种更细粒度的抓法我们常称为 ***partial CUDA Graph***。

普通 dropless MoE 是最典型的例子。Attention、router 和一部分 preprocess 的输入输出 shape 可以固定，但 routing 结束后，每个 expert 实际收到多少 token 要到运行时才知道。Token dispatch 的通信量、grouped GEMM 的 M 维以及临时 buffer 大小都会跟着变。于是可以先这样配置：

```bash
--cuda-graph-impl transformer_engine \
--cuda-graph-modules attn moe_router moe_preprocess
```

这时 attention、router、preprocess 等静态部分走 graph，token dispatch、routed expert GEMM 和 token combine 继续走 eager。

不过随着技术发展，MoE 这块做静态化的解决方案越来越成熟，包括 Megatron-LM 原生的 Paged Stashing[^3] 和 ECHO[^4]，以及业界的 [UltraEP](https://github.com/Dots-Infra/UltraEP)、[MoonEP](https://github.com/MoonshotAI/MoonEP)、[Mixture-of-Kittens](https://github.com/cursor/mixture-of-kittens) 等，都能帮助实现 MoE 的 static shape 和 graphable。相反地，我们观察到 attention 部分倒是不断涌现出越来越多的变种，各种线性、稀疏 attention 结构，以及 Dynamic CP 引入的动态 attention CP group 等，都需要我们一个一个去看 CUDA Graph 的适配。这时 partial CG 的优势再次展现，可以先把稳定的 MoE graph 推上线，attention graph 慢慢做适配：`--cuda-graph-modules moe`。

这种“哪里稳定就先抓哪里”的方式很适合快速迭代的 LLM infra。新 attention、新 dispatcher、新 overlap 或新 precision path 暂时不兼容时，不必把整套 CUDA Graph 关掉；只要把有问题的 scope 留在 eager 即可。代价也很直接：没抓到的 CPU overhead 仍然存在，graph 与 eager 之间还会反复切换，host 每轮仍需提交大量 layer graph replay，不能做到极致的 CPU overhead reduction。而且最近我们也看到越来越多的模型在搞跨层操作，比如 DSA 跨 Transformer Layer 的 IndexShare 和 KVShare 等，这使得以 layer 为粒度的 capture 越来越难以满足需求。

## 三、Full-iteration CG：抓整个 forward-backward

Full-iteration CG，也常被简称为 ***full CG***，是一套更彻底的方案。它不再逐层选择 capture scope，而是直接从最上层包住当前 rank 的 `forward_backward_func`，整个 forward-backward 抓成一个大 graph。Capture 时 pipeline schedule 提交的多个 microbatch forward/backward、loss、PP P2P 和 grad acc 都会被录进同一张 graph；代价是这套 schedule 也随 graph 一起固定下来：

![](https://pica.zhimg.com/v2-810f786bc7b033997f00aa6b1d7b158c_r.jpg)

这件事早期很难做，因为 full iteration 是 all-or-nothing：其中任何一个 op 存在 D2H sync、data-dependent allocation，或者依赖会随 replay 改变的 Python control flow，整张 graph 都抓不起来。后来 Megatron、Transformer Engine 和 PyTorch 里的兼容性问题逐步被修掉，使得 full CG 开始变得可行。

注意：Optimizer 部分不在 full-iteration graph 里。optimizer CUDA Graph 有自己专门的 `--optimizer-cuda-graph` 开关。打开 `--optimizer-cuda-graph` 时，Megatron 会给 `optimizer.step()` 再抓一张独立的 graph；两张 graph 可以共享 memory pool 以优化显存使用。

Full CG 基本配置：

```bash
--cuda-graph-impl full_iteration \
--no-check-for-nan-in-loss-and-grad
```

Full CG 最大的问题就是失去调度弹性。Tensor shape 固定还不够，microbatch 数、PP/VPP schedule、collective 顺序和所有 graph 内分支也必须固定；到了 THD 训练的 dynamic GA / dynamic CP 场景，这个限制会直接暴露出来。于是 Megatron 进一步推出了介于 full 和 layerwise 之间，兼具灵活性和收益的 chunkwise CG。

## 四、Chunkwise CG：为 Dynamic GA / Dynamic CP 留下调度空间

严格来说，THD layout 本身不必然导致 gradient accumulation 次数变化。真正让问题出现的，是建立在 THD 上的 variable-length packing 和动态 data schedule：为了在每轮处理相近数量的有效 token，不同 global batch 可能需要不同数量的 packed microbatch。比如某个 global batch 的样本恰好都比较短，这个 global batch schedule 出的 microbatch 数就会少一些，反之亦然。这里把 `num_microbatches` 在各 step 间变化的问题简称为 dynamic GA。

Full iteration 一次抓住了整个 microbatch loop，因此一张 graph 只能锚定一个 GA 值。Capture 时是 8 个 microbatch，replay 时就必须还是 8 次 forward/backward 调度；下一轮有 7 个或 9 个 microbatch 时就没法处理了。虽然 7 个可以强行 pad 出 1 个空 microbatch，9 个也可以暂时回退到 eager，但实测下来，一些场景里会出现性能回退。

Dynamic CP 的问题类似：不同 microbatch 可能选择不同的 CP size，而 graph 仅能烧录 capture 时使用的那个值。

更灵活的 Layerwise CG 则能处理这些动态性，因为我们可以为一个 layer 准备足量的 microbatch graph slots`[num_microbatches_max][num_cp_groups_max]`：到对应的 layer 要 replay 时，从 slots 里选合适的 graph 就好了（只说明大致思路，实际实现细节更复杂，具体可看相应 PR）。不过 layerwise 抓得太碎，仍然会带来额外的 graph 数量、io 接口和 host launch 开销，因此，如果 layer 本身已经完全 graphable，Megatron 更推荐的是 ***chunkwise CG*** 方案：

![](https://pic1.zhimg.com/v2-f206bb1f01c472c9de0c8c224006d6e6_r.jpg)

Chunkwise 取了一个中间边界：不再以单层为单位，而是把当前 PP/VPP rank 上的一个本地 model chunk，也就是一个完整的 decoder `TransformerBlock`，作为 graph callable（不开VPP时一个chunk就是该卡上所有layer）。外层 microbatch loop、pipeline scheduler 和跨 stage P2P 仍然走 eager。它同样支持事先准备足量的 microbatch graph slots，同时 capture 粒度比 layerwise 更大，单个 graph 内包含的操作更多，一些 chunk 内部的跨层 share tensor 操作也能一起抓进去。

Chunkwise CG 对应的配置是：

```bash
--cuda-graph-impl transformer_engine \
--cuda-graph-granularity chunk \
--cuda-graph-dynamic-microbatches \
--cuda-graph-warmup-steps 3
```

Chunkwise 的 graph 数量比 layerwise 少，也能覆盖层间 gap；foward-backward pipeline schedule 仍交给 eager。是 full iteration 失效时的最佳替代方案。

## 五、方案选择

![](https://pic1.zhimg.com/v2-46d3aa95dead4d266e3d3af6c94dac52_r.jpg)

上图总结了如何在三种 CG 方案中做选择。主要就看两个问题：

1. **一个 layer 能不能完整 capture？** 不能时先用 partial CG，把不兼容模块留在 eager；同时继续做这些模块的 CUDA Graph 适配。适配好后再看：
2. **是否存在 Dynamic CP 或 dynamic GA？** 两者都没有时，优先使用 full CG；只要存在其中一个，就需要把 microbatch 和 data/pipeline scheduler 留在 eager，目标方案是 chunkwise CG。

不过现在 LLM 的结构千变万化，估计未来还会有更多 dynamic 的 pattern 出现，CUDA Graph 的兼容性问题还需要持续探索。
