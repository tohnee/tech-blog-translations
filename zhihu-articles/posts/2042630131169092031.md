当单个智能体的能力边界无法覆盖任务全貌， 将多个专业化智能体组织成协作集群便成为必然选择。 本章深入探讨单 vs 多智能体的决策框架、 两大编排拓扑的权衡、A2A 协议的崛起、 主流框架的选型指南，以及 Meta REA 的工业级案例。

## 6.1  开篇案例：Meta REA，让 AI 集群管理多日 ML 实验流水线

2025 年下半年，Meta AI 研究团队公开了 **REA（Research Engineering Agent）** 系统的设计细节。REA 的核心任务是自动化 ML 实验的完整生命周期：从实验设计、代码实现、任务提交，到训练监控、结果分析和下一轮实验迭代——一个典型的实验周期跨越 3 到 7 天。

显然，单个智能体无法胜任如此宽泛的任务域。REA 的架构将整个流水线分解为四个专业化子智能体的协作：

![](https://picx.zhimg.com/v2-2f5a2bd17c34e3b0d54b487dd4af13df_r.jpg)

REA 的工程实践揭示了多智能体系统的核心价值： **不是将一个智能体替换为多个，而是通过专业化分工和并行执行，突破单个智能体在上下文宽度、工具集中度和任务时长上的固有局限。**

但 REA 的工程团队也坦诚了一个教训：他们最初的设计过于激进地引入了 6 个子智能体，结果智能体间的通信协调开销远远超过了并行化带来的收益。最终精简到 4 个，才找到了复杂度与效率的平衡点。这个教训在本章的决策框架中将被详细展开。

> *多智能体不是银弹。每增加一个智能体，你就增加了一个通信边界、一个状态同步点、一个潜在的故障来源。在引入多智能体之前，先确认你已经穷尽了单智能体的优化空间。* 
>  Meta REA 工程团队 · 2025 工程报告

## 6.2  决策框架：单智能体还是多智能体，一个严肃的决策框架

多智能体架构不是默认选项，而是在特定条件下的主动选择。在引入多智能体之前，你需要诚实地回答一组问题：

![](https://pica.zhimg.com/v2-25003a993d93ab73401caf88df7c54d0_r.jpg)

> ⚠ 多智能体的隐性成本 
>  多智能体系统的收益直观可见（并行加速、专业分工），但隐性成本往往被低估。每增加一个子智能体，你就需要设计：智能体间的通信协议（消息格式、调用方式）；共享状态的同步机制（谁有写权限？）；部分失败的恢复策略（子智能体 B 失败时，子智能体 A 的中间结果如何处理？）；整体的可观测性（如何追踪一个横跨 4 个智能体的任务链路？）。 **如果这四个问题你还没有清晰的答案，先不要引入多智能体。**

## 6.3  两大编排拓扑：管理者模式与去中心化协作

确定需要引入多智能体之后，下一个核心架构决策是： **这些智能体应该如何组织？谁指挥谁？** 多智能体系统存在两种基本拓扑，它们在权力结构、灵活性和可维护性上有着根本的不同。

![](https://pic3.zhimg.com/v2-8c7a576c808e8d734c329efcbef0cf5c_r.jpg)
*图 6-1　两大编排拓扑：管理者模式（左）与去中心化协作（右）*

![](https://pica.zhimg.com/v2-4f1cff14f8f19abe981ad71cc8f6a420_r.jpg)

📐 拓扑选择建议 
 对于绝大多数团队的第一个多智能体系统， **管理者模式是更稳健的起点** ——它的行为可预测，调试路径清晰，失败后的故障排查有据可查。去中心化协作适合已经运行了稳定管理者系统并且遭遇了明确的瓶颈（比如编排者上下文耗尽、调度延迟过高）之后的演进选择。不要在系统第一天就试图构建完全去中心化的智能体网络。

## 6.4  角色专业化: 子智能体的角色专业化, 分工的工程学

多智能体系统的核心价值之一，是允许每个子智能体只携带完成其特定角色所需的最小工具集和上下文。这与第 4 章的最小权限原则相呼应： **专业化不仅是能力的聚焦，也是安全边界的划定。**

以下是编码智能体集群中最常见的六种角色分工，每种角色都有明确的职责边界和工具配置：

![](https://pic2.zhimg.com/v2-b8c37da6e6260bcd78401aa54cc4ce8b_r.jpg)

> 💡 角色边界即信任边界 
>  子智能体的角色划分不仅是能力边界的设计，也是 **信任边界的设计** 。一个 Researcher 角色的子智能体永远不应该持有文件写权限；一个 Coder 角色的子智能体永远不应该能直接触发生产部署。角色配置应该在 Harness 层通过权限系统强制执行，而不是仅仅靠系统提示告诉它"不要这样做"。提示词是概率性的，权限控制是确定性的。

## 6.5  A2A 协议：智能体间通信的标准化

如果说 MCP 解决了"智能体如何连接工具"的标准化问题，那么 **A2A（Agent-to-Agent）协议** 解决的就是"智能体如何与其他智能体通信"的标准化问题。

2025 年，Google 发布了 A2A 协议规范，随后得到了 Salesforce、SAP、Atlassian、Accenture 等 50+ 家合作伙伴的支持。A2A 定义了智能体之间交换消息、发现能力、协商任务分配的标准接口，使得不同厂商、不同框架构建的智能体可以互相调用，而不需要为每对智能体组合编写特定的集成代码。

![](https://pic2.zhimg.com/v2-8d1370f86f936abd8cd3ba97b5b9c98b_r.jpg)
*图 6-2　A2A 协议架构：统一接口让不同厂商的智能体互相调用*

### A2A 的四种核心交互原语

| 交互类型 | 语义 | 同步/异步 | 典型用例 |
| --- | --- | --- | --- |
| Task（任务委托） | 将一个明确定义的子任务委托给另一个智能体执行，等待或订阅结果 | 可同步/异步 | 编排者将"搜索最新论文"委托给 Researcher 智能体 |
| Query（能力查询） | 询问目标智能体是否具备处理某类任务的能力，获取其能力声明 | 同步 | 编排者在委托前先查询哪个智能体擅长"数学推理" |
| Message（异步消息） | 无需等待响应的单向消息推送，用于状态通知和事件广播 | 异步 | Coder 完成代码后通知 Evaluator 可以开始验证 |
| Stream（流式输出） | 支持长任务的增量结果推送，订阅者可以实时消费中间输出 | 流式异步 | 长文档生成过程中，用户实时看到已完成的段落 |

### 智能体名片（Agent Card）：能力声明的标准格式

A2A 协议中，每个智能体通过一个 **Agent Card** 声明自己的能力、接受的任务类型、支持的输入输出格式。这类似于 HTTP 中的 OpenAPI 规范，使得编排者可以在运行时动态发现和选择合适的子智能体： 
 
 agent_card.json  ·  Evaluator 智能体的能力声明

```text
{
  "agent_id":      "evaluator-agent-v2",
  "name":          "Code Evaluator Agent",
  "description":   "专注于代码质量评估：单元测试、静态分析、安全扫描",
  "version":       "2.1.0",
  "endpoint":      "https://agents.internal/evaluator/a2a",

  "capabilities": {
    "tasks": [
      "run_unit_tests",
      "run_static_analysis",
      "run_security_scan",
      "generate_coverage_report"
    ],
    "input_formats":  ["file_path", "git_diff", "pr_url"],
    "output_formats": ["json_report", "markdown_summary"],
    "max_file_size_mb": 50,
    "supported_languages": ["python", "typescript", "go", "rust"]
  },

  "constraints": {
    "execution_environment": "sandboxed",
    "no_network_access": true,
    "no_filesystem_write": true,
    "max_execution_seconds": 120
  },

  "authentication": "bearer_token",
  "protocol_version": "a2a/1.0"
}
```

🔗 MCP + A2A：工具层与智能体层的双重标准化 
 MCP 和 A2A 是互补的，不是竞争的。 **MCP 是智能体与工具之间的连接标准** （纵向，模型↔工具）； **A2A 是智能体与智能体之间的通信标准** （横向，智能体↔智能体）。一个完整的 Harness 生态，最终会同时使用这两个协议：通过 MCP 接入外部工具，通过 A2A 协调子智能体。这正是"智能体操作系统"的完整基础设施图景。

## 6.7  通信与状态设计，智能体间通信与共享状态：最容易出错的工程细节

多智能体系统中，最容易出错的环节不是单个智能体的逻辑，而是 **智能体之间如何传递信息、共享状态、处理冲突** 。这些细节决定了整个系统是否能在生产环境中可靠运行。

### 消息传递的三种模式

| 模式 | 机制 | 优点 | 适用场景 | 注意事项 |
| --- | --- | --- | --- | --- |
| 直接调用 | 编排者通过 A2A / HTTP 直接同步调用子智能体，等待返回 | 简单可靠，易调试 | 顺序依赖强的子任务 | 阻塞，编排者无法并行 |
| 消息队列 | 子智能体通过消息队列（Kafka/Redis Streams）异步通信 | 解耦，高并行 | 独立子任务，事件驱动流程 | 需要处理消息顺序和幂等性 |
| 共享状态 | 所有智能体读写同一个共享状态存储（Redis / 数据库） | 状态一致，易于追踪 | 需要频繁协调的协作任务 | 并发写入冲突，需乐观锁 |

### 共享状态的写权限管理

当多个子智能体可以写入共享状态时，写权限的管理是最容易引入 Bug 的地方。本书推荐的原则是： **写权限单一化——每个状态字段有且只有一个子智能体拥有写权限，其他智能体只读。**

```text
# 共享状态的写权限声明：每个字段只有一个 owner

SHARED_STATE_PERMISSIONS = {
    # field_name: (writer_agent, reader_agents)
    "task_plan":        ("planner",   ["coder", "evaluator", "documenter"]),
    "code_artifacts":   ("coder",     ["evaluator", "documenter", "deployer"]),
    "eval_results":     ("evaluator", ["planner", "deployer"]),
    "docs_artifacts":   ("documenter",["deployer"]),
    "deployment_status":("deployer",  ["planner"]),    # 只有 planner 关心结果
    "audit_log":        ("harness",   ["*"]),          # 只有 Harness 可写审计日志
}

class SharedStateGuard:
    def write(self, agent_id: str, field: str, value) -> bool:
        owner, _ = SHARED_STATE_PERMISSIONS.get(field, (None, []))
        if owner != agent_id:
            self.audit_log.record(
                event="unauthorized_write_attempt",
                agent=agent_id, field=field
            )
            raise PermissionError(f"{agent_id} 无权写入字段 {field}，owner 是 {owner}")
        return self.store.set(field, value)
```

### REA 的休眠/唤醒检查点设计

REA 最具工程价值的设计是其跨越数天的状态管理。当 Job Executor 提交训练任务后，整个智能体集群进入休眠状态（不占用计算资源、不消耗 API 调用），同时保存四个关键文件作为跨会话状态： 
 
 REA 跨会话状态文件结构（休眠时保存，唤醒时恢复）

```text
rea_session_state/
├── experiment_plan.md       # Planner 的完整实验设计（含假设、变量、评估标准）
├── results_so_far.json      # 已完成实验的结构化结果（损失曲线、指标数值）
├── next_actions.md          # 当前状态：等待哪个任务完成，唤醒后第一步做什么
└── constraints.md           # 不变的约束：资源上限、截止时间、禁止操作

# 唤醒后的上下文构建（4 个文件注入上下文头部）：
# 总 token 消耗 < 3K，恢复延迟 < 3 秒
# Analyst 直接读取 results_so_far.json 开始分析
# Planner 读取 results_so_far.json + experiment_plan.md 决定下一轮
```

这个设计的精妙之处在于： **唤醒后的每个子智能体只需要读取与自己角色相关的文件子集，** 不需要加载整个历史对话。这与第 3 章的分层记忆架构和外部状态文件模式完全一致——只是应用于多智能体场景。

## 6.9  反模式警示：多智能体系统的五个经典反模式

| 反模式 | 症状 | 根本原因 | 正确做法 |
| --- | --- | --- | --- |
| 智能体数量膨胀 | 系统中有 8–10 个以上的子智能体，但大多数几乎不执行任何有价值的工作 | 用智能体数量代替架构深度思考 | 从最小有效集合出发（3–4 个），只有在有明确瓶颈时才增加 |
| 编排者知识过载 | 编排者的系统提示超过 8K token，需要理解每个子智能体的内部实现细节 | 边界划分不清，子智能体封装不充分 | 编排者只需知道"每个子智能体能做什么"（Agent Card），不需要知道"怎么做" |
| 共享状态无秩序 | 多个子智能体可以写入同一个状态字段，导致数据竞争和不可预期的覆盖 | 缺少写权限管理，状态所有权不清晰 | 每个状态字段有且只有一个 writer，通过 SharedStateGuard 强制执行 |
| 子智能体黑盒 | 无法观测单个子智能体的执行链路，只能看到整体任务的输入输出 | 可观测性在多智能体层面没有单独设计 | 每个子智能体都应有独立的 Trace Context，并通过 correlation_id 与父任务关联 |
| 部分失败无策略 | 一个子智能体失败后，整个任务无法继续，也无法回滚到一致状态 | 没有设计子任务级别的错误处理和补偿逻辑 | 设计"补偿事务"：每个写操作有对应的撤销操作；失败后编排者收集残局信息再决策 |

## 本章要点 

- 多智能体不是默认选项，而是在特定条件下的主动选择：任务需要不同专业工具集（>15个工具）、有可并行的独立子任务、超出单个上下文窗口承载范围、或需要多角色互相校验时，才引入多智能体。
- 两大编排拓扑各有适用场景：管理者模式（Orchestrator-Worker）行为可预测易调试，是绝大多数团队的起点；去中心化协作高并行但协调复杂，是在遭遇明确瓶颈后的演进选择。
- 子智能体的角色专业化不仅是能力边界，也是安全边界。每个角色只携带完成其职责所需的最小工具集，且通过 Harness 权限系统强制执行，而非仅靠提示词约束。
- A2A（Agent-to-Agent）协议为智能体间通信提供标准化接口，与 MCP（工具连接标准）形成互补：MCP 是纵向的模型-工具连接，A2A 是横向的智能体-智能体通信。
- 共享状态的写权限应遵循"写权限单一化"原则：每个状态字段有且只有一个 writer，通过 SharedStateGuard 在 Harness 层强制执行，防止并发写入冲突。
- Meta REA 的核心工程洞察：子智能体专业化（4个精准角色）+ 休眠/唤醒检查点（跨越数天执行）+ 角色专属状态文件（恢复延迟<3秒）= 83% 无需人工干预的完成率。

## Harness Checklist · 第 6 章

在引入多智能体之前，用以下问题确认决策的必要性和准备度：

- 你已经通过本章决策框架的五个判断问题了吗？引入多智能体的理由是需求驱动的，而非"感觉更厉害"？
- 你的单智能体 Harness 是否已经稳定运行，且具备完善的可观测性基础设施？（这是引入多智能体的前提条件）
- 你选择了哪种编排拓扑？如果选择了去中心化协作，你能明确说明为什么管理者模式不够用吗？
- 每个子智能体的角色边界是否清晰到可以写成一段 Agent Card？如果不能，边界划分还需要细化。
- 共享状态的每个字段，你能说出它的 writer 是谁吗？是否通过代码（而非文档）强制执行了写权限？
- 你为子智能体设计了独立的 Trace Context 和 correlation_id 吗？出了问题你能追踪到是哪个子智能体在哪一步失败的吗？

多智能体是 Harness Engineering 在编排维度的延伸。在引入协作集群之前，必须先给每个智能体一个安全的执行环境——这正是下一章"沙盒与执行环境"的主题。
