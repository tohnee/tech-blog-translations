本文以如下命令为例，梳理 `vllm serve` 从命令行到可对外提供 HTTP 推理服务的完整启动链路，以及各模块、进程之间的关系。

```text
vllm serve /mnt/100420/105631 \
  --served-model-name $Model_Name \
  --port 9422 \
  --tensor-parallel-size 8 \
  --pipeline-parallel-size 1 \
  --trust-remote-code \
  --block-size 32 \
  --gpu_memory_utilization 0.9 \
  --no-enable-prefix-caching \
  --max-num-batched-tokens 2048 \
  --compilation-config '{"cudagraph_mode":"FULL_DECODE_ONLY","mode":0}' \
  --speculative_config '{"method":"draft_model_mtp","num_speculative_tokens":3,"enable_multi_layers_mtp":true}'
```

### 1. 总体架构：三层进程模型

在默认配置下（单 API Server、`data_parallel_size=1`、8 卡 TP），启动完成后大致存在 **10 个相关进程**：

| 层级 | 进程 | 数量 | 职责 |
| --- | --- | --- | --- |
| Frontend | API Server（主进程） | 1 | HTTP 接入、请求解析、分词/反分词、与 Engine 通信 |
| Engine | EngineCore | 1 | 调度（Scheduler）、KV 管理、驱动 Executor |
| Worker | GPU Worker | 8（= TP） | 模型加载、前向推理、采样、投机解码 draft |

```text
┌─────────────────────────────────────────────────────────────────────────┐
│  主进程: API Server (uvicorn + FastAPI + AsyncLLM)                       │
│  ┌──────────────┐  ┌─────────────────┐  ┌──────────────────────────┐   │
│  │ HTTP Router  │→ │ InputProcessor  │→ │ AsyncMPClient (ZMQ 客户端)│   │
│  │ /v1/chat...  │  │ OutputProcessor │← │ output_handler 协程       │   │
│  └──────────────┘  └─────────────────┘  └───────────┬──────────────┘   │
└────────────────────────────────────────────────────│────────────────────┘
                                                     │ ZMQ (ipc://...)
                                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│  子进程: EngineCore (busy loop)                                          │
│  ┌────────────┐   ┌──────────────────┐   ┌─────────────────────────┐   │
│  │ Scheduler  │→ │ MultiprocExecutor │→ │ collective_rpc 广播调度输出│   │
│  │ KV 块管理  │← │ (不跑 GPU 计算)   │← │ 收集 ModelRunnerOutput   │   │
│  └────────────┘   └──────────────────┘   └───────────┬─────────────┘   │
└──────────────────────────────────────────────────────│──────────────────┘
                                                       │ SharedMemory MQ
                         ┌─────────────────────────────┼─────────────────────────────┐
                         ▼             ▼               ▼             ▼               ▼
                    Worker-0       Worker-1  ...    Worker-6       Worker-7
                    (GPU 0)        (GPU 1)         (GPU 6)        (GPU 7)
                    driver         follower        follower       follower
                         └──────────── NCCL / torch.distributed (TP=8) ─────────────┘
```

**通信方式小结**：

- **API Server ↔ EngineCore**：ZeroMQ（`PUSH`/`PULL`/`ROUTER`），序列化格式为 msgpack（`EngineCoreRequest` / `EngineCoreOutputs`）。
- **EngineCore ↔ Workers**：共享内存 `MessageQueue` 广播 `SchedulerOutput`，各 Worker 通过独立 MQ 回传 `ModelRunnerOutput`。
- **Workers 之间**：`torch.distributed`（NCCL）做张量并行 AllReduce / AllGather 等集合通信。

### 2. 启动时序（按时间顺序）

### 阶段 0：CLI 入口

```text
python -m vllm.entrypoints.cli.main
  → 解析子命令 serve
  → vllm.entrypoints.cli.serve.ServeSubcommand.cmd()
```

入口文件：

- `vllm/entrypoints/cli/main.py` — CLI 总入口
- `vllm/entrypoints/cli/serve.py` — `serve` 子命令分发

默认走单 API Server 路径：

```text
# serve.py
uvloop.run(run_server(args))
```

### 阶段 1：API Server 前置准备

`run_server()` → `setup_server()`（`vllm/entrypoints/openai/api_server.py`）：

1. 打印版本与模型路径
2. 校验 tool/reasoning parser 等参数
3. **提前 bind 监听 socket**（端口 9422），避免与后续引擎初始化抢端口
4. `set_ulimit()` 提高文件描述符上限
5. 注册 SIGTERM 处理器

### 阶段 2：构建配置对象 VllmConfig

`build_async_engine_client()` 内调用：

```text
engine_args = AsyncEngineArgs.from_cli_args(args)
vllm_config = engine_args.create_engine_config(usage_context=OPENAI_API_SERVER)
```

`create_engine_config()`（`vllm/engine/arg_utils.py`）将 CLI 参数聚合为多个子配置：

| 子配置 | 本例中的关键值 |
| --- | --- |
| ModelConfig | 模型路径、trust_remote_code、量化 w4a8 相关 |
| ParallelConfig | tensor_parallel_size=8, pipeline_parallel_size=1, distributed_executor_backend="mp" |
| CacheConfig | block_size=32, gpu_memory_utilization=0.9, enable_prefix_caching=False |
| SchedulerConfig | max_num_batched_tokens=2048 |
| CompilationConfig | mode=0（无 torch.compile）, cudagraph_mode=FULL_DECODE_ONLY |
| SpeculativeConfig | method=step3p5_mtp, num_speculative_tokens=3, enable_multi_layers_mtp=True |

同时选择 Executor 实现：

```text
executor_class = Executor.get_class(vllm_config)
# TP>1 且 backend=mp → MultiprocExecutor
```

### 阶段 3：创建 AsyncLLM（Frontend 引擎客户端）

`AsyncLLM.from_vllm_config()`（`vllm/v1/engine/async_llm.py`）在 **API Server 进程** 内初始化：

| 组件 | 作用 |
| --- | --- |
| renderer / InputProcessor | 将用户 prompt 转为 EngineCoreRequest（token ids、采样参数等） |
| OutputProcessor | 将 EngineCoreOutputs 反分词为 RequestOutput 流 |
| EngineCoreClient（AsyncMPClient） | 与后台 EngineCore 进程通信 |
| StatLoggerManager | Prometheus / 日志统计（可选） |

### 阶段 4：拉起 EngineCore 子进程

`AsyncMPClient.__init__()` → `launch_core_engines()`（`vllm/v1/engine/utils.py`）：

1. 分配 ZMQ 地址（`get_engine_zmq_addresses`）
2. `CoreEngineProcManager` 启动 **1 个** `multiprocessing.Process`：

- target: `EngineCoreProc.run_engine_core`
- 进程名: `EngineCore`

1. EngineCore 子进程启动后，与 Frontend 做 **ZMQ 握手**（`HELLO` → 接收地址 → `READY`）
2. Frontend 等待所有 Engine 发送 READY（含 `num_gpu_blocks` 等信息）

握手完成后，API Server 才认为引擎就绪。

### 阶段 5：EngineCore 内部初始化

`EngineCore.__init__()`（`vllm/v1/engine/core.py`）在 **EngineCore 子进程** 内顺序执行：

```text
load_general_plugins()
  ↓
MultiprocExecutor(vllm_config)          # 拉起 8 个 Worker 子进程
  ↓
_initialize_kv_caches()
  ├─ get_kv_cache_specs()               # 各 Worker 上报 KV 规格
  ├─ determine_available_memory()       # 显存 profiling（受 gpu_memory_utilization 约束）
  ├─ get_kv_cache_configs()             # 计算 num_gpu_blocks
  └─ initialize_from_config()
       ├─ collective_rpc("initialize_from_config")  # 各 Worker 分配 KV cache
       └─ collective_rpc("compile_or_warm_up_model") # CUDA Graph 预热等
  ↓
Scheduler(vllm_config, kv_cache_config) # 创建调度器
  ↓
StructuredOutputManager                 # 结构化输出（如 JSON schema）
  ↓
启动 ZMQ input/output 线程
  ↓
run_busy_loop()                         # 进入主循环（阻塞在此）
```

### 阶段 6：MultiprocExecutor 拉起 8 个 GPU Worker

`MultiprocExecutor._init_executor()`（`vllm/v1/executor/multiproc_executor.py`）：

1. 计算 `world_size = TP × PP × PCP = 8 × 1 × 1 = 8`
2. 创建 `distributed_init_method`（本机 loopback + 随机端口）
3. 创建共享内存广播 MQ（`MessageQueue`）用于下发 `SchedulerOutput`
4. **循环 8 次** `WorkerProc.make_worker_process()`，每个 Worker 是独立子进程

每个 Worker 进程内（`WorkerProc.__init__`）：

```text
WorkerWrapperBase.init_worker()
  ↓
init_device()
  ├─ torch.cuda.set_device(local_rank)
  ├─ init_worker_distributed_environment()   # 初始化 NCCL process group
  ├─ 显存 snapshot + request_memory()
  └─ 构造 GPUModelRunner
  ↓
load_model()                                 # 从 /mnt/stepcloud/... 加载权重
  ↓
_init_message_queues()                       # 连接 SchedulerOutput 广播 MQ
  ↓
向父进程发送 READY
```

**Driver Worker**：`rank % tensor_parallel_size == 0` 的 Worker（rank 0、8 步长下的 rank 0）负责采样输出、与 EngineCore 通信。

### 阶段 7：KV Cache 分配与模型预热

仍在 EngineCore 进程中，`_initialize_kv_caches()` 完成后：

- `cache_config.num_gpu_blocks` 被写入（受 `gpu_memory_utilization=0.9` 与模型权重大小影响）
- `block_size=32` 决定每个 KV block 容纳的 token 数
- Workers 执行 `compile_or_warm_up_model`：

### 阶段 8：构建 FastAPI 应用并开始监听

引擎 READY 后，`build_and_serve()`：

1. `engine_client.get_supported_tasks()` — 查询模型支持的任务（generate 等）
2. `build_app()` — 注册路由（`/v1/chat/completions`、`/v1/completions`、`/health` 等）
3. `init_app_state()` — 注入 `OpenAIServingModels`、`OpenAIServingRender` 等 handler
4. `serve_http()` — uvicorn 在已 bind 的 socket 上开始服务 **9422** 端口

至此服务对外可用。

### 4. 本例命令参数与进程/模块映射

```text
vllm serve <model_path>
│
├─ ModelConfig
│    ├─ model = /mnt/stepcloud/prod/100420/105631
│    ├─ trust_remote_code = True
│    └─ served_model_name = model_name（仅 API 展示名）
│
├─ ParallelConfig
│    ├─ tensor_parallel_size = 8  → 8 个 Worker 进程
│    ├─ pipeline_parallel_size = 1 → 无流水线并行
│    └─ distributed_executor_backend = "mp"（默认多进程）
│
├─ CacheConfig
│    ├─ block_size = 32
│    ├─ gpu_memory_utilization = 0.9
│    └─ enable_prefix_caching = False
│
├─ SchedulerConfig
│    └─ max_num_batched_tokens = 2048（覆盖 32768）
│
├─ CompilationConfig
│    ├─ mode = 0 (NONE)            → 不 torch.compile
│    └─ cudagraph_mode = FULL_DECODE_ONLY → decode CUDA Graph
│
└─ SpeculativeConfig
     ├─ method = draft_model       →  MTP 投机解码
     ├─ num_speculative_tokens = 3  → 每步最多 draft 3 个 token
     └─ enable_multi_layers_mtp = True → 多层 MTP 头
```

**投机解码在运行时的位置**：

- Scheduler 为 speculative slots 预留调度空间
- `GPUModelRunner` 内 MTP proposer 生成 draft tokens
- 目标模型一次前向验证多个 token
- Scheduler `update_from_output` 做 acceptance / rejection

### 5. 运行时请求路径（服务就绪后）

以 `POST /v1/chat/completions` 为例：

```text
1. uvicorn 接收 HTTP 请求
      ↓
2. FastAPI Router → OpenAIServingChat
      ↓
3. Renderer 渲染 chat template → token ids
      ↓
4. AsyncLLM.generate()
      ├─ InputProcessor.process_inputs() → EngineCoreRequest
      ├─ OutputProcessor.add_request()   → 注册输出队列
      └─ engine_core.add_request_async() → ZMQ 发往 EngineCore
      ↓
5. EngineCore input 线程收到 ADD 请求
      ↓
6. Scheduler.add_request() → 加入等待队列
      ↓
7. run_busy_loop → step():
      ├─ scheduler.schedule()           → 组 batch（≤2048 tokens）
      ├─ executor.execute_model()       → 广播到 8 Workers
      ├─ workers forward + sample       → TP 集合通信 + 投机解码
      └─ scheduler.update_from_output() → 更新序列状态
      ↓
8. EngineCore output 线程 → ZMQ PUSH 回 API Server
      ↓
9. AsyncLLM output_handler 协程
      ↓
10. OutputProcessor → detokenize → RequestOutput
      ↓
11. SSE/JSON 流式返回客户端
```

**EngineCore 单步核心逻辑**（`EngineCore.step`）：

```text
scheduler_output = self.scheduler.schedule()
future = self.model_executor.execute_model(scheduler_output, non_block=True)
model_output = future.result()  # 或 sample_tokens()
engine_core_outputs = self.scheduler.update_from_output(scheduler_output, model_output)
```

### 6. 其他启动模式（本例未使用）

| 模式 | 触发条件 | 差异 |
| --- | --- | --- |
| 多 API Server | --api-server-count > 1 | Launcher 进程先 launch_core_engines，再 fork 多个 API Worker |
| Headless | --headless 或 api_server_count=0 | 只起 EngineCore，无 HTTP |
| Data Parallel | --data-parallel-size > 1 | 多个 EngineCore + 可选 DPCoordinator 做负载均衡 |
| Ray Executor | --distributed-executor-backend ray | Worker 由 Ray Actor 管理，非 mp |

本例为最常见的 **单 API Server + 单 EngineCore + TP=8** 拓扑。

### 7. 启动失败常见卡点

| 阶段 | 现象 | 常见原因 |
| --- | --- | --- |
| 配置构建 | 启动即报错 | 模型 config 不兼容、trust_remote_code 未开 |
| Worker init | 卡在 loading | 权重路径错误、8 卡可见性不足 |
| KV profiling | OOM | gpu_memory_utilization 过高或 max_num_batched_tokens 过大 |
| Engine READY 超时 | VLLM_ENGINE_READY_TIMEOUT_S | 大模型加载慢，需调大环境变量 |
| warmup | CUDA Graph 捕获失败 | 与 enforce_eager、动态 shape 冲突 |

### 9. 总结

`vllm serve` 的启动可以概括为 **「配置聚合 → 三层进程拉起 → 握手就绪 → HTTP 监听」**：

1. **主进程**负责 HTTP 与请求前后处理（`AsyncLLM`）。
2. **EngineCore 子进程**负责连续批处理调度，不直接做 GPU 计算。
3. **8 个 Worker 子进程**各持一张 GPU，通过 NCCL 做张量并行，执行模型前向与 Step3.5 MTP 投机解码。
4. 三层之间通过 **ZMQ（Frontend↔Engine）** 和 **共享内存 MQ（Engine↔Worker）** 解耦，使 HTTP 事件循环不被 GPU 计算阻塞。

本例在 `--compilation-config` 下对 decode 启用 CUDA Graph，在 `--speculative_config` 下启用 3 token 多层 MTP，在 `max_num_batched_tokens=2048` 约束下做连续批处理，整体构成一个面向 Step-3.5-Flash 量化模型的 8 卡推理服务。
