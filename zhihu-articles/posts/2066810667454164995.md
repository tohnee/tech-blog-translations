> 从训练、推理和多租户治理三个场景，梳理 GPU 调度的核心问题、主流方案与选型思路。

---

## 引言

Kubernetes 已经成为云原生资源编排的事实标准。进入 AI 时代后，一个自然的问题是：

> 在 GPU 资源调度领域，是否也有一个类似 Kubernetes 的标准答案？

目前还没有一个项目能够覆盖所有 GPU 工作负载。更准确地说，GPU 调度已经形成了分层体系：

- •**Kubernetes**负责通用容器和节点编排；
- •**Volcano**负责 Kubernetes 上的 AI/HPC 批作业调度；
- •**Kueue**负责 Kubernetes 上的作业排队、准入和配额；
- •**Slurm**负责 HPC 和超大规模离线训练；
- •**Run:ai**负责企业级 GPU 池化和多租户治理；
- •**vLLM、SGLang**等负责推理引擎内部的请求调度。

如果必须选一个最接近“云原生 AI 调度标准”的开源项目，**Volcano 是当前较合适的答案**；如果不限定 Kubernetes，Slurm 仍是 HPC 与大型训练集群中最成熟的调度系统之一。

---

## 一、为什么 Kubernetes 默认调度器还不够

Kubernetes 原生调度器可以识别 GPU 资源，并将请求 GPU 的 Pod 放置到合适节点，但 AI 工作负载还有一些更复杂的要求。

### 1. 多机多卡任务必须同时获得资源

分布式训练通常由多个 Worker 共同完成。假设一个作业需要 8 个 Pod，每个 Pod 使用 8 张 GPU，如果集群只能调度其中 4 个，已经启动的 Pod 往往无法有效工作，却仍然占用 GPU。

这要求调度系统支持**Gang Scheduling**：

```text
资源全部满足 → 整个作业一起启动
资源不能满足 → 整个作业继续等待

```

### 2. GPU 是异构资源

GPU 不能只按“张数”进行调度，还需要考虑：

- • GPU 型号与代际；
- • 显存容量；
- • 计算能力；
- • FP16、BF16、FP8 等能力；
- • NVLink、NVSwitch 和 PCIe 拓扑；
- • NUMA 亲和性；
- • InfiniBand/RDMA 网络；
- • MIG 或其他切分方式。

同样是 8 张 GPU，位于同一台 NVSwitch 服务器、跨两台服务器或分散在普通网络节点上，实际性能可能有明显差异。

### 3. 资源昂贵，需要提高利用率

GPU 集群通常面临两个相反的问题：

- • 有些团队长期占有资源但使用率不高；
- • 另一些团队的任务长期排队。

因此调度器需要提供：

- • 队列和配额；
- • 公平共享；
- • 空闲配额借用；
- • 优先级和抢占；
- • Binpack 与碎片整理；
- • GPU 共享或切分；
- • 利用率和成本计量。

### 4. 训练和推理的调度目标不同

所以，很难由一个调度器同时把训练和推理的所有问题都解决好。

## 二、GPU 调度不是单一层次

完整的 GPU 调度可以拆成四层：

```text
┌─────────────────────────────────────────────┐
│ 请求级调度                 │
│ 路由、Continuous Batching、KV Cache     │
│ vLLM / SGLang / TensorRT-LLM        │
├─────────────────────────────────────────────┤
│ 服务与作业编排               │
│ 模型副本、训练任务、弹性伸缩、生命周期    │
│ KServe / Kubeflow / Ray / GPUStack     │
├─────────────────────────────────────────────┤
│ 集群资源调度与准入             │
│ 队列、配额、Gang、优先级、抢占、拓扑     │
│ Volcano / Kueue / Slurm / Run:ai      │
├─────────────────────────────────────────────┤
│ 设备管理                  │
│ 驱动、设备发现、MIG、监控          │
│ GPU Operator / Device Plugin / DCGM     │
└─────────────────────────────────────────────┘

```

### 设备管理

这一层让操作系统和 Kubernetes 能够发现并使用 GPU。NVIDIA GPU Operator、Device Plugin 和 DCGM 等组件分别负责驱动及组件生命周期、设备资源暴露和监控。

它们是 GPU 平台的基础设施，但不是作业调度器。

### 集群资源调度与准入

这一层决定：

- • 作业什么时候可以启动；
- • 可以使用多少 GPU；
- • 被放置到哪些节点；
- • 是否允许借用其他队列的配额；
- • 高优先级任务能否抢占资源；
- • 多个 Worker 能否一起启动。

Volcano、Kueue、Slurm 和 Run:ai 主要位于这一层。

### 服务与作业编排

这一层管理训练任务或模型服务的生命周期，例如创建 PyTorch 分布式任务、部署模型副本以及配置推理引擎。它通常依赖下层调度器完成实际资源分配。

### 请求级调度

这一层发生在模型已经运行之后，决定请求由哪个实例执行，以及如何动态组批、复用 KV Cache。它影响推理吞吐和延迟，但不能代替集群级 GPU 调度。

## 三、主流 GPU 调度方案对比

需要注意：NVIDIA GPU Operator、KServe、vLLM 和 GPUStack 虽然都与 GPU 使用有关，但不属于同一类底层批作业调度器。

---

## 四、Volcano：云原生 AI 调度的代表

Volcano 是面向 Kubernetes 批处理、AI 和 HPC 工作负载的调度系统。与默认调度器相比，它补充了训练任务最需要的能力。

### Gang Scheduling

一个分布式任务的所有成员达到最小数量后才能一起运行，避免部分 Worker 占着 GPU 等待其他 Worker。

### 队列与配额

可以按部门、项目或租户建立队列，对 GPU 资源进行分配和隔离，并控制不同队列之间的资源使用关系。

### 优先级和抢占

高优先级任务可以在策略允许时抢占低优先级任务，适用于紧急训练、生产任务和实验任务并存的环境。

### 调度策略

Volcano 支持面向批作业的多种策略，例如：

- • Binpack：尽量集中放置，减少资源碎片；
- • Spread：尽量分散，降低单节点故障影响；
- • Fair Share：提高租户之间的公平性；
- • Predicate/Priority：完成节点过滤和优先级计算。

### 适用边界

Volcano 适合以下场景：

- • Kubernetes 上的多机多卡训练；
- • PyTorch、TensorFlow、MPI 等分布式作业；
- • 多团队共享 GPU 集群；
- • 需要队列、优先级和抢占；
- • 训练、数据处理和 HPC 批任务混合运行。

它不负责模型仓库、推理 API、请求动态批处理或 KV Cache 管理。

---

## 五、Kueue：将排队和准入留在 Kubernetes 原生体系

Kueue 的设计思路与 Volcano 不同。它通常不替换 Kubernetes 默认调度器，而是在工作负载启动之前完成排队、配额判断和准入。

其核心抽象包括：

- •**LocalQueue**：命名空间内提交任务的入口；
- •**ClusterQueue**：集群范围的资源池和配额；
- •**ResourceFlavor**：表示不同型号、区域或节点类型的资源；
- •**Cohort**：允许多个 ClusterQueue 在一定规则下共享和借用资源。

例如，可以把 H100 和 A100 定义成不同的 ResourceFlavor，让作业声明可接受的资源类型，并由 Kueue 根据配额和可用性准入。

Kueue 更适合：

- • 已经采用 Kubernetes 原生调度器；
- • 希望低侵入地增加队列和配额；
- • 需要区分不同 GPU 型号；
- • 需要部门间配额借用；
- • 同时使用多种训练控制器或 Job 类型。

简单概括二者差异：

```text
Kueue：重点决定作业何时有资格运行
Volcano：进一步提供面向批作业的完整调度能力

```

两者的能力存在交叉，选型时应避免为了“组件齐全”而无必要地叠加复杂度。

---

## 六、Slurm：HPC 与大规模训练的成熟标准

在非 Kubernetes 环境中，Slurm 仍然是 HPC 和大型训练集群的重要选择。它经过超算中心和科研环境的长期验证，擅长：

- • 大规模批作业队列；
- • 节点和 GPU 资源分配；
- • 作业优先级、依赖和预约；
- • 拓扑与网络感知；
- • 裸机、InfiniBand/RDMA 和高性能计算环境；
- • 稳定的运维和计费体系。

典型技术组合是：

```text
Slurm + PyTorch + NCCL + InfiniBand + Apptainer

```

Slurm 的不足在于云原生应用编排、服务发现、网关、弹性在线服务和 Kubernetes 生态集成不如 Kubernetes。因此，部分大型平台采用双集群架构：

```text
Slurm：预训练、微调和科研批作业
Kubernetes：Notebook、数据服务、模型 API 和在线推理

```

## 七、GPU 共享、切分和碎片治理

调度策略只能决定资源分配，GPU 利用率还取决于设备如何共享。

### 独占 GPU

一个任务独占整张 GPU，隔离和性能可预测性最好，适合大模型训练和高负载推理，但小任务容易浪费显存和算力。

### MIG

MIG 可以将支持的 NVIDIA GPU 切成若干硬件隔离实例。它提供相对稳定的显存和计算隔离，适合多租户推理，但切分规格固定，动态调整通常需要重新配置。

### 时间片共享

多个容器轮流使用同一张 GPU，部署简单且能提高轻量任务的设备利用率，但不提供严格的显存隔离，性能也可能相互影响。

### 软件级显存切分

HAMi 等方案可提供更细粒度的显存和算力配额，适合开发测试和中小模型推理。采用此类方案时，需要评估性能隔离、稳定性、硬件兼容性和故障边界。

### Binpack 与碎片

如果多个小任务分散占用每台机器的一部分 GPU，后续多卡任务可能找不到完整节点。调度器通常通过 Binpack 优先填满少量节点，从而保留连续的 GPU 节点给大型任务。

因此，提高 GPU 利用率不能只看平均利用率，还要观察：

- • 显存碎片；
- • 节点间资源碎片；
- • 不同 GPU 型号的供需错配；
- • 排队时间；
- • 任务因拓扑不佳导致的性能损失。

## 八、训练调度与推理调度

### 训练侧

训练调度关注的是作业级资源分配：

```text
提交作业
 → 进入队列
 → 配额与优先级判断
 → Gang 准入
 → 拓扑感知放置
 → 启动训练
 → 完成并释放资源

```

推荐重点评估：

- • Gang Scheduling；
- • 队列和公平共享；
- • 抢占和断点恢复；
- • GPU、NUMA 和网络拓扑；
- • 失败重试；
- • 作业等待时间和集群吞吐。

### 推理侧

推理调度包含两个不同层次：

1. 1. 集群调度器负责把模型副本放到 GPU 节点；
2. 2. 推理网关和引擎负责请求路由、动态批处理和 KV Cache。

典型链路是：

```text
请求
→ 网关/路由
→ 模型副本
→ vLLM/SGLang 动态批处理
→ GPU 执行

```

推理场景需要关注：

- • 首 Token 延迟和每 Token 延迟；
- • 吞吐量；
- • KV Cache 命中和占用；
- • 模型加载时间；
- • 副本扩缩速度；
- • Prefill 与 Decode 的资源特征；
- • 服务可用性和灰度发布。

因此，Volcano 或 Kueue 只能解决其中的集群资源部分，不能替代推理引擎内部调度。

## 九、选型建议

### Kubernetes 上的分布式训练

推荐：

```text
Kubernetes
+ NVIDIA GPU Operator
+ Volcano
+ Kubeflow Training Operator
+ DCGM Exporter

```

适合需要 Gang Scheduling、队列、优先级和抢占的训练平台。

### Kubernetes 原生配额与排队

推荐：

```text
Kubernetes
+ NVIDIA GPU Operator
+ Kueue
+ 对应训练控制器

```

适合已经使用默认调度器，希望补充多租户配额、ResourceFlavor 和作业准入的团队。

### 超大规模裸机训练或科研集群

推荐：

```text
Slurm
+ NCCL
+ InfiniBand/RDMA
+ Apptainer

```

适合性能优先、批作业为主且拥有成熟 HPC 运维团队的环境。

### 企业 GPU 资源池

如果核心诉求是 GPU 共享、动态配额、部门公平、成本计量和利用率治理，可以评估 Run:ai。坚持开源时，可组合 Kubernetes、Volcano/Kueue、GPU Operator、监控计量和 GPU 共享方案，但平台建设成本会更高。

### 中小型私有推理平台

如果主要需求是部署 vLLM/SGLang、统一管理 GPU 节点并提供模型 API，可以评估 GPUStack；它解决的是模型服务交付问题，而非完整的训练调度问题。

### 训练与推理并存

规模较大时建议隔离资源池：

```text
训练资源池：Kubernetes + Volcano，或 Slurm
推理资源池：Kubernetes + KServe/vLLM，或 GPUStack

```

这样可以避免批量训练抢占在线推理资源，也便于分别优化训练吞吐和推理延迟。

## 十、评估调度系统时应该看什么

不要只比较功能列表，还应通过真实工作负载验证以下指标。

### 资源效率

- • GPU 平均与峰值利用率；
- • 显存利用率；
- • GPU 碎片率；
- • 空闲但不可分配的 GPU 数量；
- • 单位训练任务或推理请求成本。

### 调度效率

- • 平均和 P95 排队时间；
- • 大型作业获得连续资源的时间；
- • 每小时完成的作业数量；
- • 抢占后恢复时间；
- • 调度器在大规模 Job/Pod 下的吞吐。

### 性能与拓扑

- • 单机与跨机训练性能差异；
- • GPU Direct、NVLink 和 RDMA 是否正确利用；
- • 跨 NUMA 放置比例；
- • 因拓扑不佳造成的通信等待时间。

### 多租户治理

- • 配额是否可借用；
- • 公平策略是否符合组织目标；
- • 高优任务是否会造成低优任务饥饿；
- • 资源使用是否可计量和追溯；
- • 共享 GPU 是否具备足够隔离性。

最终选型应由业务目标驱动，而不是由项目热度决定。

---

## 十一、结论

GPU 调度领域还没有一个像 Kubernetes 那样覆盖所有场景的单一标准。当前更接近分工协作的事实标准：

```text
Kubernetes：通用容器与节点编排
Volcano：云原生 AI/HPC 批作业调度
Kueue：Kubernetes 作业准入、队列与配额
Slurm：HPC 和大型离线训练调度
Run:ai：企业 GPU 池化与资源治理
KServe/GPUStack：模型服务与实例编排
vLLM/SGLang：推理请求和引擎内部调度

```

可以用三句话概括选型：

1. 1.**云原生分布式训练优先评估 Volcano。**
2. 2.**Kubernetes 原生队列和配额优先评估 Kueue。**
3. 3.**大型 HPC 与裸机训练集群优先评估 Slurm。**
