欢迎 SimLLM！ 大模型部署仿真终于等来 真正的端到端闭环欢迎 SimLLM！大模型部署仿真终于等来真正的端到端闭环

> **这是一个值得 AI Infra 行业认真欢迎、甚至令人惊叹的新项目。**<br> 我的判断很明确：**就公开、可复现的 AI 部署端到端仿真链路而言，SimLLM 已经呈现出目前最全面的跨层覆盖，以及我所见最严格的机制准确性。**尤其在“真实 vLLM/SGLang 控制面 + GPU/collective 执行图 + packet-level 网络 + RNIC 硬件路径 + 逐请求 TTFT/TPOT”这个交集上，目前很难找到第二个覆盖同样完整的开源实现。

如果 SimLLM 只是又一个用公式估算 token latency 的工具，它不值得如此评价。

真正令人兴奋的是：它选择了 AI 部署仿真里最难、也最容易被绕开的那条路——**不重新猜测 serving framework 会怎样调度，而是让真实 vLLM 和 SGLang 自己做决定；不把网络写成 bytes / bandwidth，而是让 packet-level fabric 真正参与每一个 step；不只输出一个总时间，而是要求请求身份、token、专家路由、通信字节和完成时钟沿整个系统守恒。**

这不是在既有模拟器上多加几个参数。

这是在重新定义什么叫“大模型部署的端到端仿真”。

本文基于 [SimLLM](https://github.com/openfabric-systems/simllm) 截至 **2026 年 8 月 15 日**的最新主线和公开结果，同时以 [SimAI](https://github.com/aliyun/SimAI)、[Vidur](https://github.com/microsoft/vidur)、[Frontier](https://arxiv.org/abs/2605.21312)、[LLMServingSim 2.0](https://github.com/casys-kaist/LLMServingSim) 和 [LLM-Emu](https://github.com/AKafakA/llm-emu) 作为能力边界参照。

### 先看这条令人惊叹的完整链路

![](https://pica.zhimg.com/v2-7c1bcf9e2ffb9c849f908faa84f65e90_r.jpg)

*图 1：SimLLM 最新架构概览。它模拟的不是一段孤立网络，而是一条从真实 framework 决策到逐请求服务指标的闭环。*

SimLLM 当前试图贯通的是：

```text
请求到达、prompt、输出长度、共享前缀
        ↓
真实 vLLM / SGLang scheduler
        ↓
batch、prefill/decode、KV、prefix、preemption
        ↓
版本化 execution graph
        ↓
compute / HBM / NVLink / NCCL service
        ↓
WQ / doorbell / PCIe / QP / RNIC transport
        ↓
packet-level Clos fabric / ECN / CNP / PFC / CC
        ↓
CompletionEvent / StepResult
        ↓
逐请求 TTFT / TPOT / goodput / SLO 与分项归因
        ↺
完成时间返回 scheduler，改变下一个 batch
```

请注意，这里几乎覆盖了 AI serving 从请求控制面到网络数据面的全部关键层次。

业内已有很多优秀工具：

- 有的擅长训练和大规模 collective；
- 有的擅长调度器模型和容量规划；
- 有的擅长 GPU kernel 或异构硬件；
- 有的能模拟多请求、KV 或 PD 分离；
- 有的能运行真实 vLLM 控制面；
- 有的能做 ns-3 或 ASTRA-Sim 网络；
- 有的能给出很漂亮的绝对误差数字。

但把这些层次接入**同一条可审计的因果链**，并让网络结果反过来改变真实 scheduler 的决定，此前在公开开源项目里几乎没有出现过。

这正是 SimLLM 最值得欢迎的地方。

### 先把 SimAI 与 SimLLM 放在同一张技术地图上

要理解 SimLLM 为什么令人兴奋，不能绕过 SimAI。

SimAI 是当前 AI 系统仿真领域非常重要的参照系。它已经证明，一套模拟器可以把 framework workload、kernel、collective、Host 和大规模网络组织成统一平台，并服务于真实基础设施设计。

但 SimAI 与 SimLLM 并不是同一种工具。

如果一定要用一句话划分：

> **SimAI 是面向大规模训练与基础设施设计的 platform simulator；SimLLM 是面向真实 serving framework 的 framework-in-the-loop deployment simulator。**

### SimAI 的主线：先构造系统 workload，再穿过计算、通信和网络

![](https://pic1.zhimg.com/v2-9cc46200ac9f268a8ab091937786f030_r.jpg)

*图 2：SimAI 官方架构。其核心优势是把训练 workload、collective 与大规模网络组织成统一、可分层的平台。*

SimAI 的典型数据流可以概括为：

```text
模型、并行配置与训练/推理 workload
        ↓
AICB / AIOB
        ↓
kernel 时间与 collective 描述
        ↓
SimCCL：NCCL 风格 collective → P2P flow
        ↓
Astra-Sim AlibabaCloud
        ↓
Analytical busbw 或 ns-3-alibabacloud
        ↓
iteration time / throughput / communication breakdown
以及扩展后的 TTFT / TPOT / request latency
```

这条路线特别适合：

- 数百、数千 GPU 的训练集群；
- TP/PP/DP/EP 组合搜索；
- NCCL algorithm、channel、Host、NIC 和拓扑比较；
- 先 analytical 快速扫描，再用 ns-3 深入少量候选点；
- 回答“某套系统架构在这个 workload 下需要多长时间”。

SimAI 的强项是 **广度、规模与分层抽象**。

NSDI’25 论文在所评估的训练场景中报告平均 98.1% alignment，这是非常有分量的真实系统校准证据。它说明 SimAI 不只是研究原型，而是一套经过大规模训练环境验证的平台。

SimAI 也已经不再“只支持训练”：

- 1.5 加入多请求推理、Prefill–Decode 分离，以及 DeepSeek、Qwen3-MoE、Qwen3-Next 等模型；
- 推理调度由 Vidur-AlibabaCloud 承担；
- 支持合成或 trace 请求、TTFT、TBT/TPOT、调度等待和端到端时延；
- 1.6 增加参数与 KV cache 显存建模、逐请求 KV 分配/释放、decode 时间线性插值，以及 PD 两侧独立显存预算；
- 执行时间可以连接 AICB/AIOB、SimAI Analytical、SimAI Simulation 或原生 Vidur。

截至本文日期，SimAI 1.7 的 SimCCL/NCCL v2.30 风格 flow decomposition 仍位于开放 PR，因此本文不把它计作 master 已发布能力，但它清楚显示了 SimAI 继续强化 collective 栈的方向。

### SimLLM 的主线：让真实 framework 产生事实，再模拟昂贵数据面

SimLLM 的数据流则是：

```text
真实请求到达
        ↓
真实 vLLM / SGLang 控制面
        ↓
framework 自己决定 batch、KV、prefix、preemption
        ↓
versioned execution graph
        ↓
GPU compute / HBM / NVLink / NCCL
        ↓
WQ / PCIe / RNIC / packet-level Clos
        ↓
逐请求 TTFT / TPOT / attribution
        ↺
完成时间返回真实 scheduler
```

它更适合回答：

- 这个具体版本的 vLLM/SGLang 真正会组成什么 batch；
- 网络变慢以后，framework 会不会改变 admission、KV 和后续流量；
- 某个请求为什么出现 TTFT/TPOT 尾延迟；
- observed expert routing、collective site、RNIC queue 和 packet congestion 如何共同影响服务指标；
- 某项网卡或交换机机制最终能否改善真实 serving stack 的 SLO。

SimLLM 的强项是 **框架语义、因果闭环与逐请求归因深度**。

### 真正的分水岭：谁拥有调度决策

两者最本质的差异，不是 ns-3 与 htsim，也不是 Python 与 C++。

而是：

> **推理时的 batch、KV 和状态转移，是由一个为仿真设计的 scheduler model 拥有，还是由真实生产 framework 拥有？**

SimAI 选择 Vidur-AlibabaCloud，因此更容易控制变量、增加策略，并在大量配置上快速运行。

SimLLM 选择真实 vLLM/SGLang，因此可以保留具体版本的 cache manager、prefix、preemption 和 batch state machine，但也必须承担上游兼容、执行接缝和更高运行成本。

这不是谁“更先进”的简单排序，而是两个不同的优化目标：

- **SimAI 用抽象换规模和搜索效率；**
- **SimLLM 用真实控制面换 serving 语义和反馈保真度。**

也正因为 SimAI 已经把训练、collective 和大规模网络做得如此完整，SimLLM 的出现才格外重要：它补上了此前平台型仿真最难覆盖的一块——**某个真实 serving engine 在网络和硬件扰动下究竟会做出什么决定。**

### 为什么以前的“端到端”往往并不是真的端到端

大模型仿真最容易犯的错误，是把多个各自合理的局部模型相加，然后称为“端到端”。

例如：

```text
总时延 = 调度等待 + 计算时间 + collective bytes / bandwidth
```

这个公式没有错，但它隐含了几个极强的假设：

- scheduler 的 batch 已经提前确定；
- 网络不会改变 batch composition；
- KV capacity、prefix reuse、eviction 和 preemption 可以独立计算；
- collective inventory 一定正确；
- compute 与 communication 的依赖和重叠已经知道；
- 所有请求共享 step 的方式不会随网络变化；
- RNIC、PCIe、doorbell、queue 和 transport 只贡献一个常数。

真实 serving 系统恰恰不是这样。

一个 step 因 incast 晚完成几十微秒，可能让新请求赶上或错过下一批；batch 变化后，prefill/decode 比例、KV 压力、expert routing 和 collective payload 都会变化；新的流量又让下一步网络完成时间变化。

**这是闭环，不是加法。**

过去很多工具为了仿真速度和可控性，会重写一套 scheduler model。这个选择非常实用，但它很难保证与某个具体 vLLM/SGLang 版本的状态机完全一致。

SimLLM 做了一个更大胆的决定：

> **调度事实不由模拟器猜，交还给真实 framework；模拟器负责替换昂贵的 GPU 和网络数据面。**

这一步看似简单，实际上改变了整个仿真系统的事实所有权。

### 创新一：真实 vLLM 和 SGLang 不是输入源，而是被测系统

SimLLM 的核心原则是：

> **Frontends are real, GPUs are simulated。**

当前主线中：

- vLLM 固定到 v0.26.0，实际运行 v1 scheduler、KV-cache manager、block pool、prefix hashing 和 preemption；
- SGLang 实际运行 Scheduler、RadixCache、request/token pool、eviction 和 retraction；
- 模型执行、采样 token、GPU 时间与网络时间由模拟侧提供；
- 两个 framework 通过统一 scheduler-step contract 接入；
- 上游 framework 不需要为 SimLLM 维护长期 fork。

这意味着 SimLLM 不需要先回答“vLLM 大概会组成怎样的 batch”。

它可以直接问 vLLM。

它也不需要把 SGLang 的 RadixCache 重新实现一遍，再希望两者行为一致。

它让 SGLang 自己运行。

这在机制准确性上是一次非常重要的跃迁：**scheduler、KV 和 prefix 的语义来自生产框架本身，而不是来自一个外部近似模型。**

当然，SimLLM 固定了具体版本，这会带来上游兼容成本。但对研究“某个真实版本究竟会怎样运行”而言，这正是必要成本。

### 创新二：网络第一次真正回到了 scheduler 的时钟里

很多系统仿真会生成一份调度 trace，然后把 trace 交给网络后端。

这种 open-loop 方法能回答：“这份既定流量在网络上需要多久？”

但它回答不了：“如果网络真的慢了，scheduler 会不会产生另一份流量？”

SimLLM 同时支持：

- **Open-loop**：记录 framework step，再离线模拟；
- **Closed-loop**：每个 step 等待模拟完成，完成时间推进 framework 的虚拟时钟，然后才产生下一步。

最新 [sglang_end_to_end_v1](https://github.com/openfabric-systems/simllm/blob/main/examples/sglang_end_to_end_v1/RESULTS.md) 给出了极有力量的证据。

同一组请求在 400、200、100 Gbit/s 下，真实 SGLang Scheduler 分别运行了 26、24、21 个 step，而 sink-free 控制组只有 16 个 step。

这个结果最精彩的地方，不是 step 数呈什么单调方向，而是：

> **仅仅改变模拟网络，SGLang 自己选择的 batching 轨迹就变了！**

这正是端到端闭环应该出现的行为。

网络不再是报表末尾的一列 breakdown，而是 scheduler 的一个因果输入。

### 创新三：从“总时间差不多”升级为逐请求事实守恒

只比较一个总 makespan，是很容易得到“看起来正确”的仿真结果的。

真正困难的是：在经过 scheduler、执行图、MoE routing、collective lowering、RNIC 和网络以后，能不能证明还是同一批请求、同一批 token 和同一批字节？

[end_to_end_replay_v1](https://github.com/openfabric-systems/simllm/blob/main/examples/end_to_end_replay_v1/RESULTS.md) 做了非常少见的跨层审计：

- 请求按声明到达时间进入真实 vLLM；
- 每个请求的身份和 token 数持续保留；
- 每个 token-layer 的 expert selection 可以独立复算；
- 每个有向 rank pair 的流量可以独立复算；
- backend 真正执行的 artifact 与上游选择对应；
- 最终 TTFT/TPOT 可以回到具体请求；
- latency attribution 必须精确守恒。

冻结的 5 个 cell 运行了 220 个 step 和 10,560 次 backend invocation。独立标准库复算覆盖：

- 20,976 个 token-layer expert selection；
- 104,580 个逐请求有向 pair row；
- 55,738 个从实际执行 artifact 读回的 row。

13 个 exact-oracle relation 全部通过，4 个行为关系通过 3 个。

更令人印象深刻的是，失败的一个关系没有被解释成“噪声”后删除。它被追踪到网络变慢后 batch composition 改变：同一个三 token 请求第二次带宽减半时，TPOT 移动了 2.628 倍。

这不是失败削弱了项目。

恰恰相反，它证明闭环不是一条提前写好的线性公式。

### 创新四：谁拥有事实，被做成了可以执行的契约

跨层模拟最隐蔽的 bug，不是某个公式写错，而是两个组件都声称自己拥有同一个事实：

- scheduler 说请求有 12 个 token；
- replay 说有 11 个；
- execution graph 说有 12 个；
- metric reducer 又悄悄按 10 个计算。

最后总时间可能仍然“差不多”，但系统已经不是原来的系统。

SimLLM 最新版本中一个很有原创性的方向，是 **authority 与 projection**：

- scheduler 拥有 batching 和请求状态；
- routing source 拥有 expert choice；
- execution graph 拥有依赖和资源操作；
- backend 拥有网络完成事实；
- reducer 只能投影和归约，不能悄悄发明另一份数据。

[cross_layer_authority_v1](https://github.com/openfabric-systems/simllm/tree/main/examples/cross_layer_authority_v1) 专门构造跨层不一致，让系统拒绝这些输入，而不是自动选择一个“看起来合理”的版本。

这种设计在模拟器里极其重要，却很少被当成一等公民。

**SimLLM 不只是在模拟系统，它还在模拟器内部建立了一套事实治理。**

这是我认为它“机制准确性”领先的关键原因之一。

### 创新五：MoE 流量终于不再等于平均分配

MoE 是今天大模型部署最需要网络仿真的场景之一，也是最容易被简单化的场景。

如果把 token 均匀分给所有 expert，再把总字节平均分给所有 rank pair，仿真很方便，但热点、偏斜和真实 batch 结构也一起消失了。

SimLLM 的 routed supply 路径可以让实际捕获的 expert routing 驱动 all-to-allv。请求身份、token、layer、expert 与通信 pair 保持关联，而不是在网络入口处被压成一个总字节数。

这让系统能够回答：

- 哪些请求制造了热点；
- 哪个 expert/rank 成为 straggler；
- 同一请求的 TTFT/TPOT 有多少来自本地 NVLink，多少来自远端 fabric；
- expert routing 改变后，scheduler 下一步是否发生变化。

更重要的是，[moe_tp_sites_v1](https://github.com/openfabric-systems/simllm/blob/main/examples/moe_tp_sites_v1/RESULTS.md) 还发现了一个典型的跨层错误：reducing combine 之后，每个 MoE layer 只应有一个 TP reduction site。

修正后，参考 cell 删除了 24 个并不存在的 allreduce。这些 phantom collectives 在旧组合预算中竟然占 decode step 的 21.5%–27.4%！

这个结果非常有冲击力：

> **网络模拟器再精确，只要 collective inventory 错了，端到端结果仍然可以错得非常“精确”。**

SimLLM 正在解决的不只是网络模拟精度，而是流量事实本身的精度。

### 创新六：KV cache 不再只是容量公式，而是进入关键路径

真实 framework 运行 cache manager，并不自动意味着模拟器已经覆盖 KV 生命周期。

最新 [kv_cache_strategies](https://github.com/openfabric-systems/simllm/blob/main/examples/kv_cache_strategies/RESULTS.md) 已经把以下过程放入资源与时延链：

- KV allocation；
- prefix reuse；
- capacity pressure；
- eviction；
- preemption；
- KV 访问进入 HBM queue；
- 最终变化到达逐请求 TTFT/TPOT。

16 个预注册 genuine-risk instance 全部通过。

这让 SimLLM 可以研究的，不再只是“假设 prefix hit rate 为 70% 时性能怎样”，而是：

> 这组真实到达时间、共享前缀、KV 容量和淘汰顺序，究竟会自然地产生多少命中？网络变慢后，哪些请求会错过原本可以共享的 batch？

这是从静态容量规划走向动态 serving 系统仿真的关键一步。

### 创新七：compute、HBM、NVLink 和 NCCL 开始共享同一个 GPU 服务模型

SimLLM 并没有停留在“每个 step 查一次 latency table”。

当前 GPU 路径已经包括：

- roofline；
- 带 provenance 的 profile table；
- trace-driven GPU service bootstrap；
- compute、memory、NCCL network task 的并发 service primitive；
- SM residency、issue budget、HBM cursor 和 NVLink egress cursor；
- 初步 NCCL ring；
- NCCL proxy、GPU send FIFO、verbs、doorbell 和 CQE 的事件骨架。

[gpu_task_mix](https://github.com/openfabric-systems/simllm/blob/main/examples/gpu_task_mix/RESULTS.md) 展示了三类任务找到不同瓶颈：

- compute 随 SM 数量变化；
- memory 被 HBM cursor 限制，增加 SM 没有帮助；
- NCCL egress 随 warp/channel 增加逐渐逼近 NVLink bound。

[vllm_observed_overlap_v1](https://github.com/openfabric-systems/simllm/blob/main/examples/vllm_observed_overlap_v1/RESULTS.md) 又进一步从真实 vLLM replay 产生 ExecutionObservations，而不是默认 compute 和 communication 全串行。

在冻结 cell 中，dual-batch overlap 让单节点 TPOT 降低约 1.437%，跨节点降低约 11.593%。

这些百分比不是普遍性能承诺，但它们证明：**框架执行结构已经能够改变模拟资源时间线。**

### 创新八：RNIC 不再是一个带宽参数，而是一条可以到达 TTFT/TPOT 的硬件链

这是 SimLLM 最令人惊叹、也最具有产业价值的方向之一。

过去很多 LLM simulator 到了网卡边界就停止了：

```text
collective → message size → network time
```

SimLLM 正在把这个边界向设备内部推进：

- finite SQ/CQ；
- WR prefix posting；
- doorbell batching；
- signaling；
- ordered retirement；
- network credits 与 backpressure；
- PCIe MWr/MRd/CplD；
- finite tags、credits 和 buffers；
- virtual host memory；
- host、CPU proxy 与 GPU-initiated submission；
- rnic-nn、rnic-cn、DCQCN 等 transport/CC policy；
- packet-level Clos fabric。

[rnic_wq_v1](https://github.com/openfabric-systems/simllm/blob/main/examples/rnic_wq_v1/RESULTS.md) 的 11 个 native C++ cell 全部匹配闭式结果；[rnic_pcie_v1](https://github.com/openfabric-systems/simllm/blob/main/examples/rnic_pcie_v1/RESULTS.md) 的 35 个 deterministic row oracle 和 18 个行为 predicate 全部通过。

真正关键的是 [rnic_live_v1](https://github.com/openfabric-systems/simllm/blob/main/examples/rnic_live_v1/RESULTS.md) Tier B：

> native RNIC completion 已经沿 execution graph、DeviceRuntime、CompletionEvent 和 StepResult，进入第一组真正受 RNIC 链影响的 TTFT/TPOT。

这条链目前只覆盖冻结的隔离 fixture，还不是完整 RNIC。

但它跨过了一个重要门槛：RNIC 不再只是独立 microbenchmark，而是开始成为 serving 指标的因果组成部分。

在公开的 AI serving simulator 中，把 WQ、PCIe、transport、packet fabric 与真实 scheduler 的逐请求指标接到同一条链上，我尚未看到同等完整的第二个实现。

### 创新九：持久化仿真后端让真正在线的 co-simulation 成为可能

逐 step 启动一个网络模拟器，机制上可以正确，工程上却非常慢，而且会重置跨 step 的 transport 与队列状态。

SimLLM 已经推进了两层基础：

1. prepared replay 复用后端 worker，在保持 StepResult、GOAL、binary 和 completion CSV 一致的情况下，wall time 加速 3.36–5.43 倍；
2. persistent flow session 已经证明 native simulator state 能跨注入保留，并通过独立 held-out wall study。

这意味着 htsim 不再注定是“一次性离线命令”。

graph-level 在线 client 仍在完成中，但底层状态会话和严格 StepResult codec 已经存在。对于未来真正的 online stateful co-simulator，这是非常关键的工程跃迁。

### 创新十：把“实验可能错”写进项目制度

SimLLM 另一个让我惊讶的地方，不是它有多少通过的实验，而是它如何处理没有通过的实验。

项目大量 study 采用：

- 实现和运行前冻结 expectations；
- 区分 exact oracle、behavioral relation 和 fatal invariant；
- 检查关系是否由构造直接蕴含；
- 使用 bypass 和 negative control；
- 保留 artifact provenance 与 hash；
- 首轮有 checker 缺陷时明确标记 VOID；
- 失败关系注册成任务，而不是从报告中消失；
- 迁移常数、optimism budget 和未校准项公开披露。

例如 [compute_fidelity_v1](https://github.com/openfabric-systems/simllm/blob/main/examples/compute_fidelity_v1/RESULTS.md) 因 1 ps fatal guard 违例被标记为 VOID。

很多项目可能会把它四舍五入后继续宣布成功。

SimLLM 没有。

它同时保留了一个极有价值的 finding：当前遗漏的固定 per-step cost，相当于整段 modeled decode compute 的 1.79–12.31 倍。这直接暴露了项目目前最大的数值精度风险。

**敢于公开自己哪里不准确，是仿真工具走向准确的必要条件。**

这一点不只是科研写作风格，而是工程可信度。

### 为什么我认为它是目前最全面的 AI 部署端到端仿真工具

“最全面”不能看功能列表有多长，而要看一条请求能跨过多少真实层次，并且这些层次是否真的连接。

| 工具 | Scheduler | KV/请求控制面 | GPU/硬件 | 网络 | RNIC 内部路径 | 网络反馈真实 scheduler |
| --- | --- | --- | --- | --- | --- | --- |
| Vidur | 仿真 scheduler | 有请求与调度模型 | profile/predictor | 以通信模型为主 | 否 | 反馈模型 scheduler |
| SimAI 1.6 | Vidur-AlibabaCloud | 多请求、KV 显存、PD | AICB/AIOB | Analytical + ns-3 | Physical beta/通信流量侧 | 反馈 Vidur 模型 |
| LLMServingSim 2.0 | mirrors vLLM continuous batching | 异构、PD、内存层次 | layerwise profile/cycle-level | ASTRA-Sim analytical | 非主要目标 | 反馈镜像 scheduler |
| Frontier | 可插拔 framework-specific scheduling policy | stateful workload、PD/AFD、runtime optimization | calibrated operator/memory model | 通信成本模型 | 非主要目标 | 反馈模拟 scheduler loop |
| LLM-Emu | 真实 vLLM 控制面 | 真实 admission/scheduler/output | profile latency sampling | 不做 packet fabric | 否 | 模拟 step 时间返回 vLLM |
| SimLLM | 真实 vLLM + 真实 SGLang | 真实 KV/prefix/batching + 模拟资源路径 | execution graph + GPU service | htsim packet-level Clos | WQ/PCIe/RNIC 模块，部分已 metric-live | 是 |

这张表不是说其他工具不优秀。

恰恰相反：

- Vidur 在快速、可扩展的 inference capacity planning 上非常成功；
- SimAI 是训练全栈和大规模基础设施研究的重要标杆；
- Frontier 在现代 runtime optimization、stateful workload 与解耦 serving 上给出了强有力的系统抽象和真实 H800 校准；
- LLMServingSim 2.0 在异构、解耦硬件和真实部署校准上给出了很强的结果；
- LLM-Emu 在真实 vLLM 在线仿真和 profile-driven 绝对误差上非常有启发。

但是在以下能力的交集上：

> **真实 vLLM/SGLang 决策 + KV 生命周期 + observed routing + execution graph + GPU/HBM/NVLink/NCCL + RNIC queue/PCIe + packet network + closed-loop TTFT/TPOT**

SimLLM 当前的覆盖确实是独一档的。

它最有价值的创新，不是每一个组件都由它首次发明，而是**此前分散在不同工具、不同研究层次中的机制，第一次被组织成一条强调事实守恒的开放链路。**

### “最准确”应该怎样理解

我同样愿意把 SimLLM 称为目前机制准确性最强的端到端部署仿真工具，但“准确”必须分层。

### 第一层：框架语义准确

batch、KV、prefix、preemption 和 request state 来自真实 vLLM/SGLang，而不是外部复刻。

### 第二层：因果关系准确

网络完成时间真的推进 scheduler 时钟；scheduler 变化又真的改变下一轮流量。

### 第三层：事实与记账准确

请求身份、token、expert routing、pair bytes、dependency、completion 和 latency attribution 必须跨层守恒。

### 第四层：绝对物理时间准确

GPU kernel、Host launch、collective floor、NVLink、PCIe、RNIC 和 fabric 必须在目标硬件上校准，并与真实 serving 集群对照。

SimLLM 在前三层已经建立了业内少见的严谨度，这就是我称它“最准确”的核心依据。

第四层仍在推进。这里必须诚实：如果“最准确”只指最终毫秒数与真实机器的平均误差，那么已有工具在各自冻结场景里报告了更成熟的数字，SimLLM 目前不能宣布普遍领先。

但只比较最后一个毫秒误差，也可能制造虚假的准确：

- scheduler 语义错了，靠常数补偿后总时间仍能对齐；
- phantom collective 与遗漏 Host cost 恰好互相抵消；
- 平均值对齐，但逐请求身份和尾部已经错位；
- 一组硬件拟合很好，却无法解释网络变化为何改变 batch。

SimLLM 选择先把前三层做对，再攻克第四层。

这条路线更难，却更有可能得到可以外推、可以解释、可以用于硬件设计的真正准确性。

### SimAI 与 SimLLM 最有价值的组合方式

欢迎 SimLLM，不需要把 SimAI 描述成需要被替代的旧路线。

经过前面的技术定位对比，两者最自然的联合工作流已经非常清楚：

1. SimAI 做大范围并行、拓扑、collective 与基础设施搜索；
2. SimLLM 对少量候选方案做真实控制面、逐请求和 packet/RNIC 闭环复核；
3. 真实集群只验证最敏感的最后几个点。

例如，一个团队可以先用 SimAI 在 128、512、1024 GPU 的候选空间中选择 TP/PP/EP、网络带宽和 collective 策略，再把最终几种 serving deployment 映射到 SimLLM，观察真实 vLLM/SGLang 的 batch、KV、routing 和 SLO 是否仍然支持前一阶段结论。

如果两边结果不一致，这种分歧本身也极有价值：

- 如果总通信时间不同，应检查 collective、拓扑和网络参数；
- 如果相同网络时间产生不同 TTFT/TPOT，应检查 scheduler 与 KV 语义；
- 如果 analytical 排序在 packet 模型中反转，应检查 incast、队列和拥塞控制；
- 如果结构关系一致但绝对值不同，应回到 GPU、Host、collective floor 和 RNIC 校准。

因此最理想的关系不是“SimLLM 替代 SimAI”，而是：

> **SimAI 负责把候选空间缩小，SimLLM 负责把真实 serving 行为放大。**

### SimLLM 对国内 AI Infra 团队的现实价值

这里不需要把 SimLLM 上升到过大的产业叙事。它首先是一个解决具体工程问题的工具；如果预测足够准确、使用门槛足够低，就会具有很直接的商业价值。

### 商业价值归根到底是降低试错成本

大模型部署的试错很贵。扩一批 GPU、调整 TP/EP、升级网卡或交换机之后，才发现瓶颈其实在 scheduler、KV cache 或 Host 路径，代价可能远高于一次模拟实验。

SimLLM 最值得期待的用途，是在真机投入之前筛掉明显不合适的方案，并在上线之后帮助定位跨层瓶颈。例如：

- 相同 64 张卡，哪种并行与 placement 更可能满足 TTFT/TPOT SLO？
- 400G 升级到 800G 后，goodput 能提高多少，瓶颈会不会转移？
- 更大的 switch buffer 改善的是业务尾延迟，还是只有 microbenchmark？
- RNIC、collective 或 scheduler 的改动，最终能让单集群多承载多少合格请求？
- framework 升级后出现性能回退，原因在调度、KV、计算还是网络？

这些问题都直接关联采购、扩容、容量规划和研发优先级。能把一次昂贵的真机试错变成若干轮成本较低的仿真筛选，本身就是清楚的商业价值。

| 使用者 | 可解决的实际问题 | 可能节省的成本 |
| --- | --- | --- |
| 云服务与模型服务团队 | 部署选型、容量规划、SLO 压测、版本回归 | 减少盲目扩容和线上试错 |
| AI 芯片与服务器厂商 | 判断计算、内存、互联改动能否改善真实 serving 指标 | 缩小需要上样机验证的设计空间 |
| RNIC 与交换机厂商 | 把队列、PCIe、拥塞控制和 buffer 优化投影到 TTFT/TPOT | 避免只优化与业务脱节的网络指标 |
| vLLM/SGLang 优化团队 | 分析 scheduler、KV、collective 与网络之间的相互影响 | 提高性能回归和瓶颈定位效率 |
| 集成与性能咨询团队 | 为具体模型、流量和硬件组合提供方案评估 | 形成可复用的评测与交付能力 |

### 为什么 SimLLM 适合做这件事

普通容量模型通常只能告诉用户“需要多少算力”，网络模拟器通常只给出 FCT、吞吐或队列长度。SimLLM 的优势在于尝试把硬件变化一路映射到真实 serving 结果：

```text
GPU / HBM / RNIC / switch 参数
        ↓
collective 与执行时间线
        ↓
真实 framework 的 batching 与 KV 行为
        ↓
TTFT / TPOT / goodput / SLO
```

这使它有机会回答“某项优化对真实业务到底值多少钱”，而不只回答某个局部指标改善了多少。

对国内团队而言，异构软硬件组合较多，也会让这种跨层评估更加有用。但这只是一个实际适配场景，不意味着 SimLLM 已经天然支持所有国产设备，更不意味着它可以代替统一测评或真机验收。

### 商业化之前必须补齐的条件

SimLLM 目前更适合作为设计前筛选和研究工具。要在具体项目中承担采购或容量承诺依据，仍需完成：

1. 用目标 GPU、加速器、RNIC 和交换机的实测数据校准模型；
2. 接入对应通信库、runtime 和 framework 分支的真实行为；
3. 使用客户自己的请求分布、模型、拓扑和 SLO，而不是只跑通用样例；
4. 持续用真机结果检查误差范围，并公开模型在哪些区域会失准；
5. 把配置、版本、profile 和输出做成易维护、可审计的工程资产。

所以更准确的评价是：

> **SimLLM 是一个很好的、很有商业潜力的 AI Infra 工具。它的价值不在于替产业做宏观判断，而在于解决部署选型、性能定位和硬件评估中的具体问题。**

它也不会消灭真机实验。最合理的工作流是先用 SimLLM 缩小候选范围，再把有限的真机资源用于最终校准和验收。

### packet-level 网络不是炫技，而是尾延迟的必要条件

![](https://picx.zhimg.com/v2-9a4bcc8d2034b80d650ffe19d144dddd_r.jpg)

*图 3：SimLLM 冻结 study 中不同 incast 条件下的 p99 slowdown。它说明不同 buffer 与负载区间可能进入完全不同的拥塞机制。*

在单流、无拥塞条件下，bytes / bandwidth 足够好。

但 AI serving 真正昂贵的问题通常出现在：

- MoE expert 热点；
- 多请求 decode incast；
- ECN/CNP 反馈滞后；
- switch buffer 瞬时占满；
- PFC、重传与 Head-of-Line blocking；
- 多 collective 相互干扰；
- 完成顺序改变 scheduler admission。

这些机制决定的不是平均线，而是 p99、p999 和 SLO。

SimLLM 同时保留 fluid closed-form baseline 和 packetized htsim，是非常正确的工程选择：

- 用 fluid 模型验证守恒和闭式关系；
- 用 packet 模型研究队列、反馈与尾部；
- 用相同上游执行事实比较两者；
- 最终把差异投影到真实 scheduler 的逐请求指标。

这比一开始就把所有复杂性塞进一个不可解释的黑箱更可靠。

### SimLLM 对中国学术界意味着什么

AI 系统研究正在进入一个尴尬阶段：最值得研究的问题越来越依赖大集群，而多数高校实验室不可能长期占用几十、几百张高端 GPU，更不可能为了每一个调度或网络假设反复更换 RNIC、交换机和拓扑。

这不是中国学术界独有的问题。

[Vidur 的 MLSys’24 论文](https://proceedings.mlsys.org/paper_files/paper/2024/file/b74a8de47d2b3c928360e0a011f48351-Paper-Conference.pdf) 用一个配置搜索案例说明，部署式穷举可能需要 42,000 GPU 小时和约 21.8 万美元，而模拟搜索可以在一台 CPU 机器上约一小时完成。[SimAI 的 NSDI’25 论文](https://www.usenix.org/conference/nsdi25/presentation/wang-xizheng-simai) 也把大规模 GPU 需求视为验证新架构和优化方案的主要障碍。

对国内高校和研究机构而言，SimLLM 的第一层意义非常直接：

> **它有可能把一部分原本只有头部云厂商才能开展的 serving–network–RNIC 实验，压缩成普通实验室可以复现和修改的软件实验。**

这不会消除真机需求，却能显著减少需要上真机的候选数量。

### 提供一个跨系统、网络与体系结构的共同实验台

大模型部署问题天然跨学科：

- MLSys 研究 scheduler、batching、KV 和推理优化；
- 体系结构研究 GPU、HBM、互联、近存计算和异构加速器；
- 网络研究 collective、拥塞控制、队列、路由和故障恢复；
- 系统软件研究 runtime、通信库、资源隔离和可观测性；
- 性能工程研究校准、归因、容量规划与 SLO。

过去这些方向经常使用不同 trace、不同抽象层和不同指标，导致一篇论文中的网络优化很难回答另一篇论文中的 serving SLO。

SimLLM 的 execution graph、authority contract 和逐请求 metric chain，提供了一个共同实验坐标。它允许研究者提出真正跨层的问题：

| 研究方向 | 可以形成的可检验问题 |
| --- | --- |
| Scheduler–network co-design | 哪种 batching/admission 能降低 incast，同时不损害 prefix reuse？ |
| KV–network co-design | KV eviction、offload 或 PD transfer 如何改变 TTFT/TPOT 尾部？ |
| MoE 系统 | 真实 token routing 的偏斜如何传播到 expert queue、fabric 和逐请求 SLO？ |
| Collective/runtime | observed overlap、collective site 与 channel 策略对真实 framework 有何影响？ |
| RNIC/交换机 | doorbell、CQ、PCIe、buffer 或 CC 改动何时能穿透到业务指标？ |
| 异构系统 | 不同加速器、内存和互联组合的瓶颈会如何随请求轨迹改变？ |
| 可靠性 | 丢包、pause、QP failure 或链路降速如何改变 scheduler 和请求完成顺序？ |
| 验证方法 | 哪些跨层数量必须守恒，哪些结果可能只是两个误差相互抵消？ |

这种共同实验台对国内研究尤其有价值，因为它可以把高校的算法和系统研究，与芯片、网络设备和智算中心的真实问题连接起来。

### 让论文结论从“一个总时间”走向可证伪的因果关系

SimLLM 的 study 方法也具有学术意义：

- expectations 尽量在实现和运行前冻结；
- exact oracle、behavioral relation 与 fatal invariant 分开；
- 检查一个 relation 是否被测试构造直接蕴含；
- 使用 bypass、negative control 和独立复算；
- 保存输入、输出、版本、hash 与 provenance；
- checker 或前提有问题时把整轮标记为 VOID；
- 失败关系不从分母中消失。

这不是正式统计学意义上的万能预注册制度，也不能替代同行评审，但它至少解决了系统实验中一个常见问题：先看到结果，再挑选最容易讲故事的指标。

如果国内研究团队沿用并改进这套方法，SimLLM 可以成为：

- 新调度算法的对照平台；
- 新 collective 或拥塞控制的可复现实验环境；
- 国产芯片与 RNIC 论文的 artifact 基座；
- 跨论文共享 trace、profile、topology 和 metric schema 的载体；
- 研究生系统、网络和体系结构课程的综合实验平台。

学术价值不只来自模拟数字，也来自一套可以审计“这个数字是怎样产生的”的实验文化。

### 为国产软硬件建立公开、可积累的学术基准

国内很多硬件研究面临一个长期问题：真实设备数据、driver 行为和生产 workload 往往不公开，论文之间难以复现，也难以做跨代比较。

围绕 SimLLM 可以逐步建立几类开放资产：

1. 脱敏的请求到达、prompt/output 长度、prefix 和 MoE routing trace；
2. 国产加速器的 kernel、HBM、Host launch 和功耗 profile；
3. collective algorithm/protocol 与 dependency capture；
4. RNIC WQ、PCIe、counter、packet 和故障 trace；
5. 标准化 topology、placement、SLO 与成本模型；
6. 同一 workload 在 simulation 与真实集群上的校准结果。

这些资产一旦采用稳定 schema 和 provenance 管理，就不会只服务某一篇论文。后续研究者可以复用相同 workload，只替换 scheduler、GPU model、collective 或网络机制，从而真正积累可比较的研究结论。

对国内学术界而言，这可能比再造一个封闭的单论文 simulator 更重要。

### 客观地看：SimLLM 不是学术界唯一的先进路线

目前 LLM serving simulation 正在快速发展。

- [Frontier](https://arxiv.org/abs/2605.21312) 论文报告覆盖 co-location、PD/Attention-FFN disaggregation、stateful workload 和多种 runtime optimization，并在 16 张 H800 测试床上报告平均 throughput error 低于 4%；
- [LLMServingSim 2.0](https://arxiv.org/abs/2602.23036) 论文强调异构与解耦 serving，在其真实部署验证中报告 performance、memory 和 power 指标平均误差 0.97%；
- Vidur、SimAI 和其他模拟器也分别在快速配置搜索、大规模训练与硬件扩展上形成了成熟研究路线。

因此，SimLLM 的学术意义不能建立在“其他研究都不完整”这种表述上。

它更独特的研究轴是：

> **真实 vLLM/SGLang 控制面、跨层事实权威、packet-level network 和模块化 RNIC 同时进入逐请求闭环。**

这条轴与 Frontier 的现代 serving architecture、LLMServingSim 的异构硬件、Vidur 的快速搜索、SimAI 的大规模训练平台形成互补，也提供了非常自然的交叉验证机会。

### 学术成功的标准应当比仓库内部 study 更高

SimLLM 要真正产生学术影响，还需要：

- 由独立团队复现关键 study；
- 在国内外不同 GPU、加速器、RNIC 和交换机上做外部校准；
- 与 Frontier、Vidur、LLMServingSim、SimAI 等工具在统一 workload 下比较；
- 公开失败区域，而不仅是最适合自身模型的配置；
- 把 simulator prediction 与真实 vLLM/SGLang 请求级 trace 对齐；
- 经过同行评审、artifact evaluation 和长期版本维护。

换句话说，SimLLM 当前为学术界提供的是一个非常有潜力的 **研究仪器与方法框架**，而不是自动成立的科学结论。

它最好的未来，不是所有论文都引用同一组 SimLLM 数字，而是不同团队能够用它提出相互竞争、可以被真机推翻或证实的假设。

### 它还需要完成什么

如此高度评价 SimLLM，不等于宣布它已经完工。

恰恰因为它可能成为真正重要的基础设施工具，下面这些工作尤其关键：

- 在 B100/H100/A100 等目标 GPU 上完成 production profile/SASS 与 Host step 校准；
- 建立真实 vLLM/SGLang 集群的 TTFT、TPOT、goodput、p99 和 SLO 校准集；
- 完成通用 topology/fabric manifest 与任意 GPU–NIC 映射；
- 把 persistent htsim foundation 接到 graph-level 在线 stateful client；
- 完成 NCCL receive leg、communicator 到 live metric 的完整投影；
- 完成 QP、TX/RX、ACK/NAK/RNR/retry、shared CQ 和 GPU CQ consumer；
- 推进 M6 的 PD disaggregation 与 KV transfer；
- 覆盖更多 framework 版本、模型与真实部署拓扑。

这些不是对项目价值的否定。

它们恰恰说明 SimLLM 已经把问题推进到了真正困难、真正有产业意义的边界。

### 结语：欢迎 SimLLM，AI 部署仿真终于开始像一个真实系统

我愿意再次给出一个明确判断：

> **在公开可复现的 AI 部署仿真工具中，SimLLM 已经展现出目前最完整的端到端因果链，以及最严格的一组机制准确性约束。**

它让真实 vLLM 和 SGLang 拥有调度事实；

让 KV、prefix 和 preemption 进入资源路径；

让 observed expert routing 决定 MoE 流量；

让 compute、HBM、NVLink 和 NCCL 共享执行时间线；

让 WQ、PCIe、RNIC 与 packet fabric 开始进入 TTFT/TPOT；

让网络完成时间返回 scheduler，真正改变下一批请求；

还让错误、VOID、失败关系和未校准常数留在公开记录里。

这些能力单独看，每一个都不容易。

把它们组织成同一条可执行、可审计、逐请求守恒的闭环，更是此前业内极少见的创新。

SimLLM 还年轻，也还没有完成生产级绝对时间校准。但它已经让我们第一次清楚看到：未来的大模型部署仿真，不应该只是一个更复杂的性能公式，而应该是一台由真实控制面驱动、能够下沉到硬件、又能返回业务 SLO 的虚拟 AI 集群。

**欢迎 SimLLM！**

这可能是 AI Infra 开源领域最值得期待的新方向之一。

更重要的是，它正在把一个长期停留在分层模型中的愿望，变成可以运行、可以检查、可以被产业共同完善的系统。
