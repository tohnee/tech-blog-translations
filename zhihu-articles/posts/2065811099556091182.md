先把 Simple 这件事定个位。SimpleFSDP 和 FSDP2 通信量一模一样，参数要 all-gather，梯度要 reduce-scatter，前向后要不要保留完整参数照样是取舍。

所谓 Simple，指的是把这些动作用什么形式写下来。

FSDP2 用一整套 hook 加状态机去命令式地编排，SimpleFSDP 把它们缩成两句 DTensor 操作，把调度决策全部搬到 `torch.compile` 的图变换里做。

这个搬迁不是无损的，它换来了两样 FSDP2 拿不到的能力：跨层重排的自由度，还有用 GPU 实测代价来选择合并粒度。

### 1. 从一层 Linear 说起

假设有 8 张 GPU，模型只有一个 `nn.Linear(4096, 4096)`，走 fully_shard 模式。SimpleFSDP 想让下面这段用户代码在完全不改的情况下跑成分布式版本。

```text
class TinyModel(nn.Module):
    def __init__(self):
        super().__init__()
        self.fc = nn.Linear(4096, 4096)

    def forward(self, x):
        return self.fc(x)
```

先看看 SimpleFSDP 期望这段代码进入前向后发生什么，然后再回到源码逐段验证。

`self.fc.weight` 常驻内存的形态是分片 DTensor。8 张卡，每张卡本地只留 `weight[i*512:(i+1)*512, :]`，形状 `[512, 4096]`。

用户写 `self.fc(x)` 进入 `nn.Linear.forward` 之后，PyTorch 会读 `self.weight`。这时候 SimpleFSDP 已经把 `weight` 换成了一个 property，读它会调用 `ReplicateComputation.forward`，触发 all-gather，把 8 份分片拼回完整的 `[4096, 4096]`。

拿到完整权重后 `F.linear(x, full_weight)` 正常算。这里 `full_weight` 是 DTensor 经过 `to_local()` 剥出来的 plain tensor，autograd 会记住这次剥离时声明的 `grad_placements=[Partial]`。

反向来到 `full_weight.grad` 这一层时，DTensor autograd 引擎看到 `Partial → Shard` 这条 placement 转换，自动插一个 reduce-scatter，把梯度还原成分片形态。

从头到尾用户没写一句通信，也没注册一个 hook。所有 collective 都是 DTensor placement 转换派生出来的副作用。下面看代码怎么做到这一点。

### 2. `data_parallel` 是唯一的入口

`simple_fsdp.py` 中的 `data_parallel` 是一切的起点。

TorchTitan 里给 Llama 3 加数据并行就一句话：

```text
model = data_parallel(
    model,
    parallel_dims.world_mesh[("dp_shard_cp",)],
    mode="fully_shard",
    mp_policy=mp_policy,
)
```

`data_parallel` 内部做的事其实很简单，就是遍历模型里所有 `nn.Module`，对每个模块的每个 direct-owned 参数做两件事：

> 把参数换成分片 DTensor，然后把这个参数名替换成一个自动触发 all-gather 的 property。

先看 mode 的分派：

```text
if mode == "replicate":
    param_sharding = (Replicate(),)                # DDP
elif mode == "fully_shard":
    param_sharding = (Shard(shard_dim),)           # FSDP
elif mode == "hybrid_shard":
    param_sharding = (Replicate(), Shard(shard_dim))  # HSDP
```

三种数据并行模式共用后面的所有代码，只有这个 tuple 不同。

这就是为什么后面 `ReplicateComputation` 里能一份逻辑覆盖 DDP、FSDP、HSDP。

遍历模块的循环核心逻辑长这样：

```text
for mod in list(model.modules()):
    params_dict = dict(mod.named_parameters(recurse=False))  # 只看 direct-owned
    if "SimpleFSDP" in mod.__class__.__name__:
        continue  # 已经装过 property 的模块跳过

    for p_name, p in params_dict.items():
        if p is not None and p.numel() > 0:
            distribute_tensor_func = (
                _distribute_dtensor if isinstance(p, DTensor) else distribute_tensor
            )
            mod.register_parameter(
                p_name,
                nn.Parameter(distribute_tensor_func(p, device_mesh, param_sharding)),
            )

    _register_parametrization(mod, list(params_dict.keys()), ReplicateComputation(...))
```

我们来看源码这里做了什么。

`named_parameters(recurse=False)` 只处理当前模块直接拥有的参数，不会把子模块的参数重复处理。这样递归时每个参数只被访问一次。

`distribute_tensor` 把普通 `torch.Tensor` 变成分片 DTensor。如果参数已经是 DTensor（说明前面 TP 已经切过一次）就走 `_distribute_dtensor` 做 mesh 拼接，这个分支后面单独讲。

最后 `_register_parametrization` 给整个模块装 property 拦截。这一手是全篇最有意思的元编程，也放到后面细看。

跑完这个循环后，模型的参数存储形态和访问方式都变了。这一点非常关键，后面所有事情都建立在此。

### 3. 参数切片

对于普通 tensor，走的是 `torch.distributed._tensor.distribute_tensor(tensor, mesh, placements)`。 传入 `Shard(0)` 时它会在 dim 0 上按 mesh 的 world_size 切块，本地保留自己那一片。

回到那个 Linear 的例子，`weight` 是 `[4096, 4096]`，8 卡上每张卡本地只留 `[512, 4096]`。

对于已经被 TP 或 EP 切过的 DTensor，就要走 `_distribute_dtensor`。这一段是 SimpleFSDP 兼容 nD 并行最麻烦的部分，主要要处理三件事。

最麻烦的是 mesh 拼接。原参数在 `tp_mesh` 上是 DTensor，SimpleFSDP 要把它变成 `spanned_mesh = concat(dp_mesh, tp_mesh)` 上的 DTensor，让 dp 维度出现在最外层。这里靠 `DeviceMesh._concatenate([outer_mesh, inner_mesh])` 完成。

接下来要判断新的 dp 维度用 `Shard` 还是 `_StridedShard`。当 TP 已经沿 dim 0 切成 8 份，FSDP 再沿同一个 dim 0 切一次，两次切法的 stride 关系不对齐。这时候 `_StridedShard(shard_dim, split_factor=inner_spec.num_shards_map[shard_dim])` 出场，记住 stride 因子，让 DTensor 知道要按什么步长拼回来。这个细节我第一次读的时候看漏了，直到自己 dump 出参数 layout 才反应过来是 stride 不对齐惹的祸。

最后一步是 local tensor 的重分布。因为要把参数从 `(Replicate,)` on outer mesh 迁移到 `(dp_placement,)` on outer mesh，得调 `redistribute_local_tensor` 一次。这一步只在初始化时做，不进 forward。

```text
current_spec = DTensorSpec(mesh=outer_mesh, placements=(Replicate(),), ...)
target_spec = DTensorSpec(mesh=outer_mesh, placements=(dp_placements[-1],), ...)
result_tensor = redistribute_local_tensor(
    tensor._local_tensor,
    current_spec=current_spec,
    target_spec=target_spec,
)
return DTensor(result_tensor, DTensorSpec(mesh=spanned_mesh, placements=tensor_placement, ...))
```

这段代码看起来复杂，本质就是「原来参数在 tp_mesh 上是 DTensor，现在要额外加一层 dp mesh 的分片」。

用户不用手动写它，只要在 `parallelize_llama` 里按顺序 `apply_tp → data_parallel`，`data_parallel` 内部会自动判断走哪条路径。

参数状态到这一步就固化了。后续所有对 `self.weight` 的访问都是从这个分片 DTensor 出发的。

### 4. 通过 `_register_parametrization` 实现动态子类

参数切好了，接下来的问题是：怎么让 `nn.Linear.forward` 里那句 `F.linear(x, self.weight)` 在读 `self.weight` 的时候触发 all-gather？

PyTorch 本身有一个 `nn.utils.parametrize.register_parametrization`，它会把参数换成子模块，读取时经过一个可 trace 的函数。

SimpleFSDP 没直接用它，主要是「为了兼容 DCP」，因为 `state_dict()` 保存 checkpoint 时会绕开参数化，直接访问 `self._parameters`。

SimpleFSDP 用一个手写的极简版本，我们看下面的源码：

```text
def _register_parametrization(module, param_names, parametrization):
    param_name_to_property = {
        param_name: property(
            lambda self, pn=param_name: parametrization(self._parameters[pn])
        )
        for param_name in param_names
    }
    module_cls = type(
        f"SimpleFSDP{module.__class__.__name__}",
        (module.__class__,),
        param_name_to_property,
    )
    module.__class__ = module_cls
```

这是纯 Python 元编程。回到那个 Linear 例子，跑完这四行后：

- `self.fc.__class__` 从 `nn.Linear` 变成动态生成的 `SimpleFSDPLinear`。
- `SimpleFSDPLinear.weight` 是一个 property，读它会调 `parametrization(self._parameters["weight"])`。
- `parametrization` 是 `ReplicateComputation` 的实例，实际上是一个可调用的 `nn.Module`。
- `self._parameters["weight"]` 是刚才切好的分片 DTensor。

三层 dispatch 串起来：读 `self.weight` → property getter → `ReplicateComputation.forward(shard_dtensor)` → 返回完整 tensor。

用 `type()` 动态建子类比给实例挂 attribute 好在两处地方。property 定义在类上而不是实例上，对同一个类的所有实例统一生效；这个新类又只挂到当前模块类型上，不污染其他 `nn.Linear`。挂完 `module.__class__ = module_cls` 只影响这个具体模块。

留意 `data_parallel` 循环里那句 `if "SimpleFSDP" in mod.__class__.__name__: continue`。 它就是拿类名做幂等检查，跑第二次不会重复挂 property。

### 4.1 state_dict 为什么不受影响 ？

正常你调 `nn.Module.state_dict()` 时，PyTorch 源码走的是 `self._parameters[name]`，直接读字典，不走 property。

所以 checkpoint 存的是分片 DTensor（DCP 天然能处理 DTensor），加载时也是直接写字典，没有触发 all-gather 的机会。

TorchTitan 里 `checkpoint.py::get_model_state_dict` 走的是稍微不同的路径，那条路径可能会走 property，会引发不必要的 all-gather。

所以，这个坑现在还在，如果你要接自定义 checkpoint 逻辑，得手动包 `disable_active_parametrization`：

```text
with disable_active_parametrization():
    model.init_weights()
    # 或者你的 checkpoint 加载逻辑
```

`disable_active_parametrization`（是一个 contextmanager，它把模块级全局 `_active_parametrization` 设为 False，`ReplicateComputation.forward` 会检查这个标志并直接返回 `x` 而不做 redistribute。

### 5. 如何一个函数搞定 DDP、FSDP、HSDP

property 拦截到读取动作后，实际执行的是 `ReplicateComputation.forward(shard_dtensor)`。它转手调 `replicate_compute`。剔除 TP/EP 兼容分支的核心逻辑就这几行：

```text
def replicate_compute(self, x: DTensor) -> torch.Tensor:
    output = x.redistribute(
        placements=[Replicate()] * self.device_mesh.ndim,
        forward_dtype=self.param_dtype,
        backward_dtype=self.reduce_dtype,
    )
    if not self.full_dtensor:
        output = output.to_local(grad_placements=self.grad_placements)
    return output
```

要看的就两个动词。`redistribute` 把 `Shard` 变成 `Replicate`，这是 DTensor 的原生操作，内部对应 all-gather；接着 `to_local` 把 DTensor 剥成 plain tensor 供下游 `F.linear` 使用，用 `grad_placements=[Partial]` 声明「这个 tensor 的梯度是 Partial 状态」。

关键点在于 `redistribute` 和 `to_local` 都是可微算子。DTensor 的 autograd 引擎会记录每一次 placement 转换，反向的时候按逆向路径重新走一遍。

前向路径是 `Shard → Replicate`，对应 all-gather。反向时 autograd 沿路返回，走 `Partial → Shard`，对应 reduce-scatter。如果 mode 是 replicate，起点是 `Replicate`，反向路径是 `Partial → Replicate`，对应 all-reduce。同一段代码，DDP 走 all-reduce，FSDP 走 reduce-scatter，全部通过 placement tuple 的不同表达出来。

这一手让我第一次意识到 DTensor 的 placement 系统不仅是「表示」，还是「计算」。三种数据并行模式的差别被压到了 tuple 的元素上，走到运行时之后由 autograd 引擎自动展开。之前 FSDP、FSDP2、DDP 各占一个模块的写法看起来就冗余了。

这里几个字段值得停一下看清楚。`compute_placements = [Replicate()] * device_mesh.ndim` 说明前向永远走到 replicate。`grad_placements = [Partial(reduce_op="avg")] * device_mesh.ndim` 说明本地梯度是 partial 状态、按平均聚合；这里如果配了 `reduction_divide_factor`，用的是 `_ScaledPartial`。至于 `param_dtype` 和 `reduce_dtype`，是混合精度控制字段，传给 `redistribute` 后，前向 all-gather 直接用 `param_dtype`（比如 bf16），通信量减半；反向的 reduce-scatter 用 `reduce_dtype`（一般 fp32），保住数值精度。这一层 dtype 转换是通信路径内部的，不影响用户看到的参数存储 dtype。

### 6. `_ScaledPartial`：给 MoE 场景补的一小块

`_ScaledPartial` 是 `Partial` 的子类，只做一件事，在 reduce 之前先 `tensor.div_(reduction_divide_factor)`，然后走父类的 reduce：

```text
class _ScaledPartial(Partial):
    def _reduce_shard_value(self, tensor, mesh, mesh_dim, shard_spec):
        # for reduce_scatter in FSDP
        tensor.div_(self.reduction_divide_factor)
        return super()._reduce_shard_value(tensor, mesh, mesh_dim, shard_spec)
```

它服务的场景是 DeepSeek-V3 那种 EP 加 FSDP 混用。非 MoE 参数在整个 `dp_mesh` 上做 FSDP，MoE 参数只在 `dp_mod_ep_mesh`（去掉 EP 维度之后的 dp 子网）上做 FSDP。但数据是按整个 `dp_mesh` 均匀切分的，所以 MoE 参数的梯度平均因子应该等于「dp_mesh 大小」而不是「dp_mod_ep 大小」。让 DTensor 内部自己算的话它只知道自己的 mesh 大小，所以要在 `Partial` 的子类里插一个自定义 divide factor。

这个扩展点在 SimpleFSDP 里是一行子类就搞定的，因为通信路径本来就是「触发一个 Partial 的 reduce」，reduce 的除法系数正好可以做一个自然的钩子。FSDP2 里做同一件事要伸手到 reduce hook 里去改。

### 7. TP、EP 组合时的 mesh 塌缩

如果参数已经是 TP 上的 DTensor（1D 或 2D DTensor），SimpleFSDP 前向想沿 dp 维度做 all-gather，不想沿 tp 维度做 all-gather。这需要一个「暂时把 tp 那一维摘掉」的操作。`replicate_compute` 里有一段兼容分支就是干这个：

```text
non_dp_mesh_dims = x._spec.mesh.ndim - self.device_mesh.ndim
if non_dp_mesh_dims > 0:
    # 把 nD DTensor 剥回 local tensor，再 wrap 成 1D DTensor（只有 dp_mesh）
    sharded_local_tensor = x.to_local()
    sharded_dtensor = DTensor.from_local(sharded_local_tensor, dp_mesh, self.param_sharding)

    # 只在 dp_mesh 上做 all-gather
    replicated_dtensor = sharded_dtensor.redistribute(
        placements=self.compute_placements, forward_dtype=..., backward_dtype=...
    )

    # 剥回 local tensor
    replicated_local_tensor = replicated_dtensor.to_local(grad_placements=self.grad_placements)

    # 再包回原来的 nD mesh，保持 TP 语义
    output = DTensor.from_local(replicated_local_tensor, non_dp_mesh, non_dp_placements)
```

四步转换。剥掉 TP 层的 DTensor 包装 → 在 dp 上做 all-gather → 再剥回 local → 重新加上 TP 包装。中间那次 `redistribute` 只在 dp mesh 上做，所以 all-gather 只沿 dp 维度发生。

注释里明确写着 `TODO: DTensor should support this mesh collapsing operation`。作者也认这段代码不干净，应该由 DTensor 侧原生支持「在 spanned mesh 的某一维做 redistribute」，等上游支持后这一整段可以删掉。

站在使用者角度不用管这段。只要按顺序调 `apply_tp(model, tp_mesh)` 然后 `data_parallel(model, dp_mesh, ...)`，SimpleFSDP 会自动挑分支。

### 8. 编译入口：`parallelize_llama` 里的 4 步流水线

现在跳到 `llama3/parallelize.py::parallelize_llama`，看 SimpleFSDP 是怎么和整个训练流水线接上的。省掉配置校验后的骨架长这样：

```text
def parallelize_llama(model, parallel_dims, job_config):
    if parallel_dims.tp_enabled:
        apply_tp(model, tp_mesh, loss_parallel=..., enable_float8_tensorwise_tp=...)
        maybe_enable_async_tp(job_config, tp_mesh)

    if job_config.activation_checkpoint.mode != "none":
        apply_ac(model, ac_config, ..., op_sac_save_list=_op_sac_save_list, ...)

    if dp_enabled:
        mp_policy = MixedPrecisionPolicy(param_dtype=..., reduce_dtype=...)
        model = data_parallel(model, dp_mesh, mode=dp_mode, mp_policy=mp_policy)

    if compile_enabled:
        backend = get_compile_backend_with_passes(
            job_config.compile,
            fsdp_reshard_after_forward,
            get_transformer_block_buckets(model),
        )
        model = torch.compile(model, backend=backend, fullgraph=True)

    return model
```

顺序有讲究。TP 先做，因为 TP 会把参数变成 DTensor，data_parallel 里判断 `isinstance(p, DTensor)` 时才能命中 `_distribute_dtensor` 分支。AC（激活检查点）在 data_parallel 之前，因为 AC 只包用户层的模块（TransformerBlock），不介入 SimpleFSDP 的参数化。data_parallel 之后再 `torch.compile`，这样编译器看到的 `forward` 已经包含所有的 `redistribute` 调用。

`torch.compile(..., fullgraph=True)` 强制一整张前反向图，不允许 graph break。这是 SimpleFSDP 的硬要求，因为它的通信调度全靠图变换，中断了图就没法 bucket 和 reorder。

### 9. `get_compile_backend_with_passes`：真正干活的编译后端

SimpleFSDP 的自定义 `torch.compile` 后端住在 `backend.py`。它包了一层，做两件事：先取默认后端（`torch._dynamo.lookup_backend(...)`），再套上 pass 装饰。

先看返回结构。`get_compile_backend_with_passes` 返回一个 callable：

```text
def simple_fsdp_custom_pass(*args, **kwargs):
    with functorch_config.patch("joint_custom_pass", joint_ac_pass):
        return backend(*args, **kwargs)
```

`functorch_config.patch("joint_custom_pass", joint_ac_pass)` 是 AOTAutograd 提供的一个钩子。AOTAutograd 在生成 joint graph（前反向合并的中间图）之后、切分成前反向图之前，会调用 `joint_custom_pass` 让你改这张 joint graph。SimpleFSDP 在这里插的就是 `reshard_after_forward` 那段 AC 标注（后面详细讲）。

再看 bucketing 分支。有两种 pass，`auto_bucketing` 和 `transformer_block_bucketing`，控制的是 fwd/bwd 图上的 collective 合并策略。

`auto_bucketing` 调 `torch._inductor.fx_passes.overlap_scheduling.schedule_overlap_bucketing`，它自动扫图找 `all_gather_into_tensor` 和 `reduce_scatter_tensor`，按拓扑距离合并相邻的 collective，再做 reorder 让通信藏在计算里。相关上游是 [pytorch/pytorch#163960](https://github.com/pytorch/pytorch/pull/163960)。README 提醒它不保证最优。

`transformer_block_bucketing` 调 `torch._inductor.fx_passes.overlap_manual_scheduling.manual_overlap_bucketing`，需要你传一个 `module_bucket_plans` 列表告诉它哪些模块归成一个 bucket。TorchTitan 里 `get_transformer_block_buckets` 给的默认方案是 `[tok_embeddings, [norm, output]]` 加上每个 `TransformerBlock`，也就是每个 transformer 层一个 bucket。

两种 pass 都可以搭配 `aot_eager` 或 `inductor` 两个后端。`aot_eager` 适合验证图变换和数值路径，`inductor` 是训练性能路径。

### 10. `reshard_after_forward` 是一个 3 行的 AC pass

现在讲最有意思的一块。FSDP2 里 `reshard_after_forward` 是 runtime flag，前向完之后要不要显式释放完整参数。SimpleFSDP 没有 runtime 状态，那这件事怎么表达？

答案在 `reshard_after_forward.py`。它是一个 fx graph pass，在 AOTAutograd 的 joint graph 上跑，做的事概括起来是「找到所有 FSDP 触发的 all-gather 节点，把它们标记为 `MUST_RECOMPUTE`」。核心逻辑：

```text
def annotate_fsdp_all_gather(gm, reshard_after_forward):
    graph = gm.graph

    def force_recompute_node(node):
        if reshard_after_forward:
            node.meta["recompute"] = CheckpointPolicy.MUST_RECOMPUTE
        else:
            node.meta["recompute"] = CheckpointPolicy.MUST_SAVE
        node.meta["ac_graph_id"] = 100000

    for node in graph.nodes:
        if is_wait_tensor_from_fsdp(node):
            ag_node = node.args[0]
            force_recompute_node(ag_node)       # all_gather 本身
            force_recompute_node(node)          # 后面跟的 wait_tensor
            for user in node.users:
                if user.target == torch.ops.aten.slice.Tensor:
                    force_recompute_node(user)
            if ag_node.all_input_nodes[0].target == torch.ops.prims.convert_element_type.default:
                force_recompute_node(ag_node.all_input_nodes[0])

    return gm
```

节点识别是 `is_wait_tensor_from_fsdp`：一个节点是 `wait_tensor`，它的输入是 `all_gather_into_tensor`，并且 `all_gather` 的输入沿着单输入算子链回溯到 graph 的 placeholder（也就是模型参数）。这个模式匹配把「来自 FSDP 的 all-gather」和「来自 all2all 或 EP collective 的 all-gather」区分开来。

标注三个节点。all_gather 自己、后面的 wait_tensor、还有可能出现的 slice（all-gather 出来的完整参数可能被 slice 掉 pad）和前面的 dtype cast（mixed precision 会插一个 fp32 → bf16 转换）。这几个如果不一起标注 recompute，partitioner 一看「有节点必须保存」就会把整段的中间结果都保留，把显存收益抹掉。

AC 标注怎么变成 reshard？这一步靠的是 AOTAutograd 的 min-cut partitioner。partitioner 拿着 joint graph 决定哪些中间张量存到 tape 里、哪些反向重算。看到 `MUST_RECOMPUTE` 时它就不保存，前向 graph 里保留 all_gather 输出给下游用，但不流向反向；反向遇到「需要这个 tensor」时，partitioner 会自动在反向图里重新插入相同的 all_gather。

于是 `reshard_after_forward = True` 表达为「反向再来一次 all-gather」；`reshard_after_forward = False` 表达为「保存完整参数到 tape」。这本来就是 FSDP2 里对应两个 runtime 选择的物理效果，SimpleFSDP 用 AC 决策把它们统一起来了。

`ac_graph_id = 100000` 是一个 hack。AOTAutograd 内部 AC 区域按 `ac_graph_id` 分组，边界节点默认保存不重算。塞一个大数字保证这些节点单成一区，才不会被相邻区域的默认 MUST_SAVE 覆盖。这是 [pytorch/pytorch#136433](https://github.com/pytorch/pytorch/issues/136433) 里绕开的一个已知限制。

回过头看这一节其实挺哲学的。FSDP2 里 `reshard_after_forward` 是一个「运行时选择」，SimpleFSDP 把它翻译成「重算 vs 存储」的老问题，然后甩给 activation checkpoint 那套已经有的机制。同一件事换个说法后，就搭上了别人 20 年的基建。

### 11. 自己写一个 pass

前面每一步都涉及 graph pass。

既然 SimpleFSDP 的哲学是「优化交给 compiler」，那 pass 到底是什么形状？下面写一个玩具例子帮助理解。

假设想加一个 pass，把所有 all-gather 之前的 dtype cast（`fp32 → bf16`）加一次日志打印，看编译到底给我插了几次 cast。写法如下：

```text
import torch
import torch.fx as fx

def log_ag_casts(gm: fx.GraphModule, example_inputs) -> fx.GraphModule:
    """遍历 fx graph，找 all_gather 前的 dtype cast 并打点。"""
    graph = gm.graph
    count = 0

    for node in graph.nodes:
        if not (
            node.op == "call_function"
            and node.target == torch.ops._c10d_functional.all_gather_into_tensor.default
        ):
            continue

        # all_gather 的第一个输入
        in_node = node.args[0]
        if (
            in_node.op == "call_function"
            and in_node.target == torch.ops.prims.convert_element_type.default
        ):
            src_dtype = in_node.args[0].meta.get("val", None)
            dst_dtype = in_node.args[1]
            print(f"[AG cast] {src_dtype} -> {dst_dtype} at node {node.name}")
            count += 1

    print(f"[AG cast] total {count} casts before all-gather")
    return gm

# 挂到 aot_eager 后端上
from torch._dynamo.backends.common import aot_autograd

backend = aot_autograd(
    fw_compiler=log_ag_casts,
    bw_compiler=log_ag_casts,
    keep_inference_input_mutations=True,
)

model = torch.compile(model, backend=backend, fullgraph=True)
```

这就是一个最短的 pass。它做的事覆盖了所有 fx graph pass 的基本套路。

最外层是遍历 `gm.graph.nodes`。fx graph 是一个 SSA 形式的中间表示，每个 `Node` 有 `op`（`placeholder` / `call_function` / `get_attr` / `call_module` / `output`）、`target`（要调用的算子）、`args` / `kwargs`（输入依赖）。你要做的匹配基本上就是「哪种 op 类型加哪个 target」。

匹配到之后通过 `node.args` 沿依赖链回溯。fx graph 是显式 DAG，直接翻 `node.args[i]` 就能拿到前驱。SimpleFSDP 的 `is_wait_tensor_from_fsdp` 就是靠这个从 wait_tensor 一路追到 placeholder。

追到目标节点后再做点什么，这里分两种。标注 meta（`node.meta["recompute"] = ...`）不会改变图的形状，只是给下游 pass 留信息；改图（`graph.erase_node(node)`、`graph.inserting_after(node)`）才会真正插入或删除节点。SimpleFSDP 的 reshard pass 只做 meta 标注，把改图动作留给 partitioner。

回过头看 `reshard_after_forward.py`，就会发现它其实就是这个模板的一个稍复杂版本：一个匹配（`is_wait_tensor_from_fsdp`），一个动作（`force_recompute_node`），加一点边界处理。90 行的文件，20 行是真正的逻辑，其余是节点识别工具函数。

如果要写一个「找到所有 reduce_scatter 之后的 dtype cast 并强制 bf16」的 pass，套路一样：换匹配条件（`reduce_scatter_tensor` 加下游 cast），换动作（改 `cast.args[1]` 或插一个新的 cast 节点）。核心难度不在 fx，而在你要精准描述「什么模式的节点应该被改」。

### 12. 为什么 SimpleFSDP 能比 FSDP2 更快

前面全部是 SimpleFSDP 的实现细节。回到开头的问题：三分之一的墙钟时间到底怎么省出来的。

有两件事得先钉死。SimpleFSDP 和 FSDP2 通信量完全一样，都是每个参数 all-gather 一次前向、每个梯度 reduce-scatter 一次反向。反过来 SimpleFSDP eager 模式性能其实更差，每次读 `self.weight` 都发一次 collective，没有 bucket 也没有 prefetch。所以性能差异只可能来自开 compile 之后的调度层。

我读源码时归纳出四条差异，都可以对上代码。

### 12.1 调度粒度：从模块到算子

FSDP2 是模块级调度。它的 `FSDPParamGroup` 就是一个模块（或者几个被 `fully_shard([a, b, ...])` 分到同一组的模块）。前向路径长这样：

```text
def pre_forward(self, module, args, kwargs):
    ...
    self.unshard(self.unshard_async_op)   # 发一次 all_gather，把这一组参数拼出来
    self.wait_for_unshard()               # 等 all_gather 到位
    ...

def post_forward(self, module, input, output):
    ...
    if not is_bw():
        self.reshard()                    # 前向完释放完整参数
        self._record_post_forward()
```

关键点是 `unshard` 里那个 `foreach_all_gather(self.fsdp_params, ...)`。一次 all-gather 处理整个 `FSDPParamGroup` 里的所有参数，也就是那个模块的所有 `nn.Parameter` 打包成一次 collective 发出。粒度是「你调 `fully_shard` 时选的模块」，用户挂在哪一层，all-gather 的合并单位就是那一层。

代价是这个粒度在 forward 开始那一刻就被冻结了。假设你按 `fully_shard(each_TransformerBlock)`，一层 block 一个 all-gather，那 attention 里的 QKV 和 FFN 就必然打成一个 collective 发出。哪怕 QKV 只用了 300µs、FFN 前向要 2ms，QKV 那 300µs 完成后就在那空等 attention 才能开始。你想「让 QKV 单独早发一步」，只能重新 wrap 模型的 fully_shard 边界。

SimpleFSDP 把这个绑定关系解开。每次读 `self.weight` 就产生一个孤立的 all-gather 节点，编译器看到的是最细粒度的 collective 序列。合并成什么 bucket、按什么模块边界合并，是 inductor 里的 `_bucket_collectives` pass 在已经拿到完整 fx graph 之后决定的：

```text
def _bucket_collectives(self) -> None:
    from torch._inductor.fx_passes.overlap_preserving_bucketer import (
        OverlapPreservingBucketer,
    )
    bucketer = OverlapPreservingBucketer(
        graph=self.graph,
        collective_info=self.collective_info,
        scheduled=self.scheduled,
        max_bucket_memory_gb=2.0,
        max_coll_distance=self.max_node_distance,
        ...
    )
    bucketer.bucket_collectives()
```

`OverlapPreservingBucketer` 拿着依赖图和调度顺序，能决定「哪几个 all-gather 合并起来正好塞满 NCCL 带宽」，还不破坏 overlap 依赖。用户模型的 fully_shard 层级不再是硬边界。

这个自由度直接体现在 `manual_overlap_bucketing` 的文档里：

```text
Step 1: bucket all-gather/reduce-scatter in each module in module_bucket_plans
Step 2: reorder all-gather to overlap with last module_bucket &
    reorder reduce-scatter to overlap with next module_bucket
```

两个动作是分开的。先按模块列表合并 collective，然后跨模块做 reorder，让第 N 层的 all-gather 藏进第 N-1 层的 matmul 里去。FSDP2 是没法「跨模块 reorder」的，它的 pre_forward hook 只能在自己模块进入前触发，跳不到别的模块前面。

这就是为什么 SimpleFSDP 的第一份加速来自「没有 hook」。它把「什么时候发 collective」这个决定从模块的时间线上摘下来，交给拿到全图后能自由排位置的编译器。

### 12.2 prefetch：从静态规则变成基于代价的规划

FSDP2 的 prefetch 是硬编码规则：

```text
def _backward_prefetch(self) -> None:
    if self._training_state == TrainingState.PRE_BACKWARD:
        ...
        curr_index = self._post_forward_indices.pop()
        if self._num_param_groups > 1:
            if self._param_group_index != 1:
                return
            ...
            self._prefetch_unshard(target, "backward")
        elif curr_index > 0:
            target = self.comm_ctx.post_forward_order[curr_index - 1]
            self._prefetch_unshard(target, "backward")
```

规则是「反向 pre_backward 时，如果我是当前 group 的最后一个，就 prefetch 前一层的 unshard」。距离固定是 1（前一层），策略固定是「一个一个抓」。这是一个不涉及代价估计的启发式。它能 work，是因为 transformer 的层大小基本均匀，前一层 all-gather 的时间大致等于当前层的反向 compute 时间。

SimpleFSDP 的 prefetch 交给 inductor 的 `OverlapScheduler.run` 决定。开 `custom_runtime_estimation` 或 `collective_estimator="benchmark"` 时，它会：

- 用 GPU 实测的 kernel benchmark 估计每个 matmul、attention、collective 的执行时间。
- 拿这个时间对 collective 做优先级调度，让最费时间的 collective 最早启动。
- 用 `max_in_flight_gb=5` 和 `max_memory_increase_gb` 约束，避免同时 in-flight 的 collective 撑爆显存。
- 用 `max_compute_pre_fetch=200` 限制单次预取的深度，避免太深的 prefetch 反而挤掉当前 compute 的时钟。

它的成本模型里有这么两行值得看：

```text
total_exposed = sum(c.exposed_time_ms for c in self.collective_info.values())
hideable_exposed_ms = sum(
    self.collective_info[c].exposed_time_ms
    for c in potentially_hidden_collectives
)
```

它显式地跟踪「有多少 ms 通信没被 compute 藏住」和「有多少 ms 本来是能被藏住的」。调度算法就是在减少 `hideable_exposed_ms`。这不是 FSDP2 那种「反正 prefetch 前一层」的静态规则，而是拿着预算做 reorder 决策的规划问题。

结果是当模型层大小不均匀时（比如 MoE 或者混合结构），FSDP2 的固定 prefetch 会有大量 GPU 空转，SimpleFSDP 能自动识别「这一层反向 compute 短，得提前两层预取才够」。DeepSeek-V3 那种 MoE 层 compute 时间跳跃巨大的结构，是这个差异最能拉开的场合。

### 12.3 stream 编排：从显式 event 同步变成隐式 dependency

FSDP2 用多个 CUDA stream 和显式 event 做 overlap。挑一段典型代码看：

```text
if (
    not async_op
    and self._training_state == TrainingState.FORWARD
    and world_size > 1
):
    self.comm_ctx.all_gather_state = AllGatherState(
        self._all_gather_result, all_gather_copy_out_event
    )
else:
    self._wait_all_gather_streams_on_event(all_gather_copy_out_event)
```

有 `all_gather_stream`、`reduce_scatter_stream`、`all_reduce_stream`、`all_gather_copy_in_stream`。每一段 collective 结束时 `Event().record()`，下一步在正确的 stream 上 `wait_event`。写这段代码要人手规划「哪些操作可以并行、需要几条 stream、event 等在哪个位置」。

问题是这个规划是基于假设的。假设 all-gather 会比 compute 快，就把 all-gather 提前 launch；假设 reduce-scatter 不会撞上 next-forward 的 all-gather，就用同一条 stream。假设错了就 overlap 不上，得手工调 event 等待的位置。FSDP2 里那些 `max_input_buffers` 之类的参数是「同时 in-flight 的 reduce-scatter 上限」，撑爆了会有显存问题，撑不满会有 overlap 损失，这个平衡点靠人调。

SimpleFSDP 完全不写 stream 代码。它靠什么保证 overlap？靠编译器生成的 stream 分配和 event 插入。inductor 里的 `_reorder_graph` 就是在算完 exposed time 之后重排 graph 节点顺序：

```text
def _reorder_graph(self) -> None:
    exposed = [...]                                    # 计算已经暴露的 collective
    potentially_hidden_collectives = ...               # 计算本来能藏但没藏起来的
    ...
    self.reorder_graph()
```

真正的 stream 分配落在 inductor 后端。inductor 拿到重排后的 fx graph，按依赖关系发射 CUDA kernel 到不同 stream 上，让没有依赖的 collective 和 compute 并行执行。这些 stream 决策是看着整张 graph 做的，能保证 overlap 依赖不被破坏。而 FSDP2 的 stream 编排只能看当前模块，无法感知「三层之后有一个反向的 matmul 会等这个 all-gather」这种远距离依赖。

### 12.4 mixed precision 的通信量减半是「免费」的

FSDP2 想在 all-gather 前先 cast 到 bf16，需要在 `foreach_all_gather` 内部维护 cast buffer，还得处理 cast 的时机（在 all_gather_copy_in_stream 上做，不能挤到主 stream）。相关代码在 `_fsdp_collectives.py`，大约几百行。

SimpleFSDP 就一行：

```text
output = x.redistribute(
    placements=[Replicate()] * self.device_mesh.ndim,
    forward_dtype=self.param_dtype,     # e.g. torch.bfloat16
    backward_dtype=self.reduce_dtype,   # e.g. torch.float32
)
```

DTensor 的 `redistribute` 支持 `forward_dtype` 和 `backward_dtype` 两个字段，编译到 fx graph 后是 `convert_element_type → all_gather_into_tensor` 这两个前后紧挨的节点。graph pass 层已经知道这一对模式，`reshard_after_forward` 里那个「cast 也一起标注 recompute」的分支就是在处理它。

这不是「更快」的一部分，是「同样快的功能，代码量差 100 倍」的一部分。但它间接影响性能：dtype cast 是一个普通 fx 节点，`OverlapScheduler` 能把 cast 也放进 overlap 决策里去调度。FSDP2 里 cast 藏在专用 stream 上，调度器看不到。

### 12.5 反过来 FSDP2 快在哪

老实说 FSDP2 也有 SimpleFSDP 现在追不上的地方。

冷启动是最扎眼的一条。SimpleFSDP 强制 `fullgraph=True`，第一次编译要几分钟，模型稍大点半小时起，做小实验时经常等到怀疑人生。FSDP2 是 eager，进模型就能跑。

动态形状同样棘手。FSDP2 对 dynamic shape 没有额外要求，SimpleFSDP 走 compile 路径遇到 dynamic 形状会 recompile。recompile 触发是很多用户的痛点，我自己就在变长序列上被坑过一次。

再往细里说是 per-parameter 精细控制。FSDP2 允许在 module 级别配 `MixedPrecisionPolicy`、`OffloadPolicy`、`ReduceOp`，甚至给不同 module 用不同的 process group。SimpleFSDP 的所有决策都是 graph pass 层面的，per-parameter 的差异化很难表达。

最后是成熟度。FSDP2 是主线，SimpleFSDP 还在 experimental 目录，边缘 case 一堆 TODO 待补。生产上要不要现在就上，得掂量下风险。

### 13. 边界与代价

到目前为止 SimpleFSDP 看起来很爽，但不该忽略几件事。

首先，它是建立在DTensor 成熟完美这个假设上。`_distribute_dtensor`、`replicate_compute` 里的 mesh 塌缩、`_StridedShard` 兼容，都是在补 DTensor 现在没做完的能力。任何一个 collective 语义 DTensor 支持不好，SimpleFSDP 就要在源码里插一个兼容分支。

其次，它绑定了 `torch.compile` 的可用性。`It is always recommended to open compile` 已经在告诉你这不是可选优化。eager 模式下每读一次 `self.weight` 就发一次 all-gather，没有 bucket 也没有 prefetch，性能会显著劣于 FSDP2。而且 `reshard_after_forward` 是 pass 实现的，不开 compile 完全不生效，只能落到「所有完整参数常驻」这一档。

最后，它绑定了 `fullgraph=True`。任何一处 graph break 都会破坏后续 pass。用户自己的模型如果有 Python 副作用或 dynamic control flow，得先解决 graph 完整性问题才能用 SimpleFSDP。

代码规模也要客观理解。`simple_fsdp.py` 是核心前端，`backend.py` 加 `reshard_after_forward.py` 是编译后端，模型接入代码另有 150 行左右。

加上论文提到 TorchInductor 里那 2K LoC 的 bucketing 和 reorder pass，全景规模并不小。它的「简单」是分层意义上的：语义层小、优化层交给 compiler，而不是总代码量小。

说白了，SimpleFSDP 不是把 FSDP2 的复杂度消掉了，而是搬到了别人家里。搬走的这部分复用了 inductor 已经在做的调度基础设施，也就顺便享受了它未来的迭代。这也是我最想强调的一件事，所谓 Simple 不是「代码量少」，是「不重复造轮子」。

### 14. 现在怎么跑

DeepSeek-V3：

```text
CONFIG_FILE="./torchtitan/models/deepseek_v3/train_configs/debug_model.toml" \
  ./run_train.sh \
  --model.name simple_fsdp.deepseek_v3 \
  --compile.enable \
  --activation_checkpoint.mode "none" \
  --job.custom_config_module=torchtitan.experiments.simple_fsdp.job_config
```

三个开关值得记：

- `--compile.enable` 必须开，否则性能非常差，`reshard_after_forward` 也依赖 compile 侧的 AC pass 才能生效。
- `--compile.graph_passes` 有 `auto_bucketing` 和 `transformer_block_bucketing` 两档。规模小可以先默认，规模上来后开手动 bucketing。
- `--parallelism.fsdp_reshard_after_forward` 有 `always`、`never`、`default` 三档。PP 场景默认 `never`，因为 per-microbatch 的 all-gather 无法 overlap，划不来。

面向训练性能时后端应该用 `inductor` 而不是 `aot_eager`，`aot_eager` 只是 pass 验证路径。上面命令用 `aot_eager` 是因为例子给的是可读性优先的配置。

我自己第一次跑起来时因为漏了 `--compile.enable`，跑了半天纳闷「说好的快呢」，后来才反应过来 SimpleFSDP 不是「eager 也能跑，加编译更快」，而是「离了编译连能跑都算不上」。这个心智模型的切换比任何 flag 都重要。
