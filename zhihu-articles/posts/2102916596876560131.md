## 一点闲话

又来炒点冷饭了，对于熟悉go和llvm的开发者，似乎或多或少都会有关于go和llvm的融合的脑洞。在很长的一段时间内，我的主业也是干这个，但是因为各种原因，没能把那个项目做到底。时隔好几年，体会到现在AI的强大，就借助AI向我理想的融合方案做了一些尝试，发现效果不错，想把这个尝试推进到比较高的完成度，也算是在技术上弥补下之前的遗憾。

这次的项目叫 GoALLC。我想从它的设计思路说起，再沿着一次编译的过程，介绍它怎样把 Go 和 LLVM 接起来。

### 背景

在开发者社区里，其实已经有不少试图把 Go 编译器和 LLVM 融合在一起的项目，虽然看起来都是融合，但是实际的思路差别很大。

比较早的一个代表是 [​gollvm](https://go.googlesource.com/gollvm/)。它使用与 gccgo 共用的 gofrontend，通过桥接层生成 LLVM IR，再交给 LLVM 优化和生成机器码。通过前后端分离，已有的 Go 语言实现得以使用 LLVM 的优化和代码生成能力。它同时采用 libgo，以及与标准 Go 编译器不同的调用约定和部分运行时实现，形成了自己的工具链路线。

[​TinyGo](https://tinygo.org/docs/concepts/faq/what-is-tinygo/) 的目标更鲜明：让 Go 能够进入微控制器、WebAssembly 等对资源和产物体积有不同要求的环境。为了适应这些环境，它对编译器和运行时作了相应的设计。这些设计让 Go 更适合在嵌入式和资源受限的环境中使用。

[​LLGo](https://github.com/xgo-dev/llgo) 则把 Go 与 C 生态的融合放在很重要的位置。采用 C ABI，使 Go 代码能够直接与大量已有的原生库交互，并进一步连接 Python 等生态。围绕互操作设计调用方式和运行时，可以降低跨语言调用的成本，也能让 Go 更方便地用于这些库已经很成熟的领域。

这几条路线各有创新，也各有需要承担的取舍。对我来说，另一个很有吸引力的方向，是把现有 Go 生态尽可能完整地保留下来，再把 LLVM 接到其中。

Go 的生态积累远不止语言语法。标准库、goroutine 调度、GC、汇编实现、cgo、反射，以及构建、测试和诊断工具，都建立在编译器与运行时之间的一系列约定之上。大量项目又继续建立在这些基础上。如果更换编译器意味着逐个修改依赖、替换运行时能力，迁移的成本就会很高。我希望已有项目能够直接使用 LLVM 后端，让收益逐步进入日常开发流程。

去年，也就是 2025 年，字节跳动在 LLVM 开发者大会上分享了 [​TangoLLVM：为 Go 编译器增加 LLVM 后端](https://llvm.org/devmtg/2025-10/slides/quick_talks/gu.pdf)。会议材料展示的方案复用 Go 编译器，将 Generic SSA 转换成 LLVM IR，经过 LLVM 生成代码及相关信息，再接回 Go 的对象文件和链接流程。这与我理想中的融合方式非常接近。

因此，我也希望自己实现这样一套方案，并进一步完善其中的细节设计。GoALLC 就是沿着这个方向展开的一次尝试。

### GoALLC 想做到什么

从使用者的角度看，我希望目标尽可能简单：**用 Go 能构建的项目，用 GoALLC 就应该能够构建，使用方法保持一致，后端则交给 LLVM。**

已有的代码和依赖继续使用，构建还是 go build，测试还是 go test，运行还是 go run。对于应用开发者，换用工具链之后，原来积累的项目结构和工作方式应该继续有效。

完整保留 Go 的使用体验，是 GoALLC 的兼容性目标。在这个基础上，再引入 LLVM 的循环优化、向量化和针对不同处理器的代码生成能力。

### 从前端到 Go SSA

执行 go build 时，Go 命令先处理包依赖和构建缓存，再调用编译器、汇编器、链接器等工具。GoALLC 继续使用这套组织方式。

进入编译器之后，源码要经过语法分析、类型检查、泛型相关处理，以及内联、去虚拟化、逃逸分析等过程。Go 中不少语言特性的实现，也会逐渐转成更基础的操作或 runtime 调用。随后，函数被转换成 Go SSA，继续接受通用优化。

这些步骤里已经包含了很多 Go 特有的知识。例如，一个对象能否留在栈上、一个接口调用是否能够确定具体目标、某个边界检查是否可以消除，都值得继续利用。GoALLC 因此选择复用这一段编译流程。

接入点的选择很关键。太早进入 LLVM，就要重新实现许多 Go 已经完成的分析和变换；太晚进入，Go SSA 又已经被拆成面向某个架构、寄存器和栈布局的操作，LLVM 很难重新获得完整的优化空间。

GoALLC 在通用 Go SSA 与原生目标后端之间接入。这里仍能看到逻辑上的 Go 参数、返回值和内存操作，同时又已经利用了前端和一批通用优化的结果。

这个位置可以在 [​ssa/compile.go](https://github.com/goallc/go/blob/737cff72e320b5a65082dd1cf9d8e802fae116c2/src/cmd/compile/internal/ssa/compile.go#L504-L512) 中直接看到。下面是相邻的 pass 定义：

```text
// LLVM consumes generic SSA after Go's normal optimizations, before
	// target-specific rewriting and physical call lowering.
	{name: "llvm dead auto elim", fn: elimDeadAutosGeneric, llvmOnly: true},
	{name: "llvm direct iface", fn: llvmDirectIfacePass, required: true, llvmOnly: true},
	{name: "llvm late cse", fn: cse, llvmOnly: true},
	{name: "llvm deadcode", fn: deadcode, required: true, llvmOnly: true},
	{name: "llvm", fn: LLVMCompile, required: true, llvmOnly: true},
	{name: "rewrite tern", fn: rewriteTern, required: false, disabled: !buildcfg.Experiment.SIMD},
	{name: "lower", fn: lower, required: true},
```

执行到 llvm pass 后，LLVM 路径会在同一个 pass 循环中退出：

```text
if base.Flag.EnableLLVM && p.name == "llvm" {
			// LLVM owns instruction selection, scheduling, register allocation,
			// and frame layout. The remaining passes prepare native codegen.
			break
		}
```

这两处代码确定了后端的分工：Go SSA 的通用优化完成后，LLVM 接手后续的指令选择、寄存器分配和栈帧布局。

当然，复用也需要选择。例如，原生 Go 后端的参数展开、部分条件选择形成和内存合并，包含了它自己的后端假设。LLVM 路径会跳过这些步骤，把对应工作留给 LLVM。具体边界已经整理在项目的 [​Go SSA 与 LLVM pipeline 说明](https://github.com/goallc/go/blob/737cff72e320b5a65082dd1cf9d8e802fae116c2/doc/goallc-llvm-pipeline.md)中。

### 从 Go SSA 到 LLVM IR

接下来的工作主要由 ssa2llvm 等模块完成。它们把 Go SSA 中的基本块、控制流、运算、内存访问和函数调用转换成 LLVM IR，同时保留后续生成 Go 代码需要的信息。

编译一个包还要处理类型描述、接口方法表、全局变量、字符串常量，以及它们之间的符号和重定位关系。GoALLC 继续利用 Go 前端准备的这些信息，再将它们组织到 LLVM module 和相关元数据中。

普通编译路径以包为单位形成 LLVM module，通过 Go LLVM binding 在编译器进程内完成优化和代码生成。LLVM 侧负责指令选择、寄存器分配、机器指令调度和栈帧布局；GoALLC 的 pass 则在合适的阶段补充 Go 运行时需要的处理。

LLVM 路径在这里退出原生 Go 后端的后续流程，由 LLVM 统一完成目标代码生成及栈帧布局。原生 Go 路径则继续执行目标 SSA lowering、寄存器分配、AllocFrame 和 genssa。

### 从机器码回到 Go 工具链

LLVM 通常输出 ELF、Mach-O、COFF 等对象文件，而 Go 工具链还使用自己的 linker object 格式。要继续走 Go 的归档和链接流程，就需要把这层接口接好。

GoALLC 在 LLVM 中增加了 GoObj 的支持，使后端能够直接输出 Go linker 可以读取的对象数据。这里包括机器码，也包括 Go 符号、重定位和函数相关数据。包的导出信息仍按 Go 的方式处理，最终与编译器对象、汇编或 cgo 等其他成员一起进入 package archive。

之后继续由 Go linker 完成符号解析、可达性分析、布局、重定位，以及运行时相关表的组织，生成目标平台上的可执行文件。

因此，LLVM 是构建工具链的一部分。生成的普通 Go 程序运行时，不需要再加载 LLVM。

这条对象链路也可以直接观察。这里用一个只有静态字符串赋值函数的 [​Go 文件](https://zhuanlan.zhihu.com/evidence/source/example.go)，在本机已有的 GoALLC 开发工具链上执行：

```text
go tool compile -pack -llvm-keep-ir -p sample -o example.a ../source/example.go
go tool pack t example.a
```

归档成员的实际输出为：

```text
__.PKGDEF
_go_.o
```

这个例子使用的是 2026-11-07 的 macOS arm64 开发工具链 go1.27.3-goallc.538304df7e2f。

保留 IR 后，同一次编译还留下了三个阶段的文件：.raw.ll 是前端生成的 IR，.ll 是准备后的 IR，.opt.ll 是优化后的 IR。其中，[​优化后的 IR](https://zhuanlan.zhihu.com/evidence/work/example.a.opt.ll)明确指定了 GoObj 目标：

```text
target triple = "aarch64-apple-darwin-goobj"
```

goobj 目标生成的机器码进入 _go_.o，再与导出信息一起组成包归档。后面还会用到这次编译的 IR 和反汇编，看看调用约定与写屏障的具体实现。

### 为了兼容 Go，LLVM 需要怎样配合

接通编译流程之后，接下来要处理的是 LLVM 生成的代码与 Go runtime 之间的约定。

栈增长、GC、异步抢占和异常处理，都依赖机器指令与运行时元数据的配合。编译器需要同时生成这两部分内容，并让它们在每个关键位置保持一致。

### 函数调用与 Go ABI

函数调用首先涉及参数放在哪里、返回值怎样传递、哪些寄存器有特殊用途，以及栈上的参数区如何安排。Go 的 ABIInternal 与 C ABI 有自己的区别，汇编交互还涉及 ABI0 和相应的包装函数。

为了与 Go runtime 和已有汇编互调，LLVM 目标后端需要实现 Go 的调用约定与栈帧规则。

GoALLC 在 LLVM 中实现了相应的 Go 调用约定支持，并在 Go SSA 转换时保留调用所需的信息。普通调用之外，还要处理闭包的上下文、接口方法调用、多个返回值，以及结构体和数组等聚合值。

前面例子的 LLVM IR 中，可以看到两种调用约定的实际声明。写屏障入口使用 goabiinternal，栈增长入口使用 goabi0：

```text
declare goabiinternal void @"runtime.gcWriteBarrier1<builtin.234>"() #0

declare goabi0 void @"runtime.morestack_noctxt<builtin.246><ABI0>"()
```

这些声明让调用约定成为 LLVM IR 的一部分，目标后端据此完成参数、寄存器和栈的处理。

聚合值尤其容易把调用问题与栈问题连在一起。有些值需要在内存中传递，参数和结果也可能涉及调用方或被调用方的固定栈区域。LLVM 优化时可能把一次聚合访问拆成多个字段访问。拆分后的每个地址，仍必须对应原来的 Go 存储位置，跨越调用时也要继续有效。

因此，ABI 的支持贯穿 IR 表达、调用 lowering、栈帧布局和元数据生成，各阶段都要遵循同一套约定。

### goroutine 的栈会增长，也会移动

Go 的 goroutine 从较小的栈开始执行，空间不够时再扩展。函数入口的栈检查、进入 morestack 的慢路径、参数保存与恢复，都是这套机制的一部分。

LLVM 后端既然负责栈帧布局，就需要负责生成与 Go runtime 匹配的入口序列。检查位置、栈大小、特殊寄存器、慢路径中的活跃值，以及重新进入函数时的状态，都必须协调起来。

更进一步，栈增长可能复制栈内容。指向栈内对象的指针，跨越一次可能导致栈增长的调用后，其地址可能已经改变。

这会直接影响优化。例如，某个局部字段的地址可以在调用前算出来，但调用后如果继续使用旧地址，就可能访问旧栈。编译器需要知道这个地址属于哪个对象，调用后应当从哪里重新获得它。对固定栈对象，可以根据新的栈帧位置和字段偏移重新形成地址；对于需要被运行时调整的指针，则要通过相应的活跃性和重定位机制处理。

Go 的堆 GC 保持对象地址稳定，goroutine 栈复制则会改变栈内对象的地址。编译器需要分别处理这两类情况。

### GC、安全点与优化后的指针

GC 扫描一个栈帧时，需要知道哪些位置保存着活跃指针。这个信息和执行位置有关：同一个栈槽，在不同指令位置可能保存不同的值，也可能已经不再活跃。

原生 Go 后端会生成自己的活跃性和栈图信息。换成 LLVM 后，这些信息就必须与 LLVM 优化后的指令、寄存器分配和最终栈位置重新对应。

GoALLC 使用 LLVM 的 statepoint 相关机制，把跨安全点仍然活跃的指针显式表达出来，并使用 gc.relocate 等表示调用之后应当使用的值。固定栈对象和聚合参数则按各自的存储规则处理。

![](https://picx.zhimg.com/v2-0f2ec945c9d50815833e8124cab09fdd_r.jpg)

*图 2：statepoint 与 Go 栈图的配合。左侧是编译过程，右侧是运行时消费的信息；下方示意调用后如何继续使用指针和固定栈对象。*

GoALLC 将完整的 statepoint 重写放在较晚的指令选择前阶段。这样，前面的 IR 优化可以先充分简化代码，再根据优化后的指针活跃性完成安全点处理，最后由机器码阶段记录实际位置。

对应的注册逻辑在 [​GoALLCStatepointPlugin.cpp](https://github.com/goallc/go/blob/737cff72e320b5a65082dd1cf9d8e802fae116c2/src/cmd/llvmplugin/GoALLCStatepointPlugin.cpp#L178-L191) 中。addPreISelPass 将 GoALLCPreISelPass 接到指令选择之前；下面同时保留了相邻的 GoObj 回调注册，便于看到它所处的上下文。

```text
void registerGoALLCTargetPasses() {
  static RegisterTargetPassConfigCallback Registration(
      [](TargetMachine &TM, PassManagerBase &, TargetPassConfig *TPC) {
        if (!TPC)
          return;

        TPC->addPreISelPass(
            [TMPtr = &TM]() { return new GoALLCPreISelPass(*TMPtr); });
        if (TM.getTargetTriple().isOSBinFormatGoObj())
          TPC->addPreBranchRelaxationPass(
              []() { return createGoALLCInlineAnchorPass(); });
      });
  (void)Registration;
}
```

最终，机器码阶段得到的栈位置会转换为 Go 所需的指针位图和函数数据。runtime 根据 PC 找到对应记录，知道哪些位置需要扫描，栈复制时哪些指针需要调整。

写屏障也属于这条链路。Go 前端的分析决定哪些写入需要屏障；经过 LLVM 优化后，相关记录再在合适的阶段展开，形成符合 Go runtime 约定的操作。这样既保留 Go 对 GC 正确性的判断，也给中间优化留下空间。

异步抢占又增加了一层要求。运行时可能在函数内部尝试暂停 goroutine，因此还需要标记哪些指令区间可以安全抢占，哪些区间需要避开。GoALLC 为此结合机器指令阶段的信息生成相应的安全区间描述。

### 对象文件是编译器与运行时之间的接口

把前面这些内容放在一起，可以看到 Go 对象文件承担的职责相当多。

![](https://pic2.zhimg.com/v2-5837290b070013a26fe84649481719cb_r.jpg)

*图 3：代码和元数据共同进入 Go 工具链。__.PKGDEF 是包导出信息，_go_.o 是编译器对象成员；其他成员可能来自汇编或 cgo。运行时信息由对象记录经链接器组织后进入最终程序。*

机器码和重定位决定程序怎样执行；PC 与栈高度的对应关系帮助 runtime 遍历栈帧；指针位图和栈对象记录支持 GC 与栈复制；文件、行号、内联关系和调试信息，又影响栈回溯、性能分析和调试体验。

这些信息还会受到优化影响。例如，函数被内联之后，用户仍希望看到合理的调用位置；指令经过调度和分支调整之后，元数据中的 PC 范围也必须跟着最终布局走。

GoALLC 因此把 GoObj 输出作为后端的一部分来实现，让机器码和对应元数据沿着同一条代码生成流程产生，再由 Go linker 组织成运行时需要的形式。

到这一步，“兼容 Go”才逐渐落实成可以检查的具体接口：函数调用能否互通，GC 能否正确找到指针，栈复制后程序能否继续运行，工具能否正确解释生成的程序。它们需要一起成立。

### 接入 LLVM，实际能够带来什么

完成这些适配之后，Go 程序就能进入 LLVM 已经积累多年的优化体系。收益既来自通用优化，也来自不同架构上的指令选择、调度和寄存器分配。

具体效果取决于 Go 前端提供的信息、LLVM IR 的表达方式，以及后端对 Go runtime 约定的处理。下面结合正式发布版的性能数据和机器码来看。

### 哪些用例已经更快

GoALLC 的首个正式版本是 [​GoALLC 0.1.0（Go 1.27.3）](https://github.com/goallc/go/releases/tag/go1.27.3-goallc.0.1.0)，工具链版本为 go1.27.3-goallc.0.1.0，LLVM 基线为 23.1.4。我们用这份发布包，在 Linux amd64 的 Intel Core Ultra 9 185H 上，与官方 Go 1.27.3 做了性能对比。

### 优势怎样落到机器码上

第一组是 **Gonum Min 的循环展开与控制流处理**。这个函数不仅比较大小，还保留 NaN 处理和最小值下标。实测二进制中，官方 Go 逐项推进循环；LLVM 生成的标量浮点热循环每轮处理两个元素，保留 NaN 检查，并在下标更新中使用条件移动。由此减少了单位元素的循环控制开销，也改变了分支与指令调度方式。[​LLVM 反汇编](https://zhuanlan.zhihu.com/evidence/performance/disassembly/llvm-releaseperf.BenchmarkNumeric.func1.txt)和[​官方 Go 反汇编](https://zhuanlan.zhihu.com/evidence/performance/disassembly/official-releaseperf.BenchmarkNumeric.func1.txt)可以直接对照。

第二组是 **Bitset Count 的 CPU 特化与循环展开**。官方 Go 的逐字计数循环中，会读取 runtime.x86HasPOPCNT，再决定执行 POPCNT 还是通用实现。GoALLC 在 LLVM IR 层实施函数多版本处理：生成不同 CPU 特征对应的函数体，设置 target-features，并在已知特征的版本中化简能力检查；运行时分派选择并缓存适合当前机器的实现。这部分由 [​GoALLCCPUFeatures.cpp](https://github.com/goallc/go/blob/98a7240a92558e3c6f5348575489311f4c89d2e5/src/cmd/llvmplugin/GoALLCCPUFeatures.cpp#L558-L578) 实现，再交给 LLVM 优化和代码生成。

在本轮二进制的 POPCNT 专用路径中，热循环直接连续处理四个 uint64，循环内不再反复查询 CPU 能力。下面摘取同一段连续反汇编，仅省略地址与机器码列：

```text
popcnt (%rcx,%rsi,8),%r9
add    %r9,%rax
popcnt 0x8(%rcx,%rsi,8),%r9
popcnt 0x10(%rcx,%rsi,8),%r10
add    %r9,%r10
add    %rax,%r10
popcnt 0x18(%rcx,%rsi,8),%rax
add    %r10,%rax
add    $0x4,%rsi
add    $0x4,%r8
cmp    %rdi,%r8
jne    572120 <releaseperf.BenchmarkBitset.func1+0x1e0>
```

四条 POPCNT 对应四个数据字，末尾索引一次增加 4。本轮主机的 CPU 能力与默认配置满足该专用路径的分派条件。[​分派函数](https://zhuanlan.zhihu.com/evidence/performance/disassembly/llvm-bitset-0x572360.txt)、[​完整专用循环](https://zhuanlan.zhihu.com/evidence/performance/disassembly/llvm-bitset-0x571f40.txt)和[​官方 Go 循环](https://zhuanlan.zhihu.com/evidence/performance/disassembly/official-releaseperf.BenchmarkBitset.func1.txt)可以对照阅读。

这组优化由 GoALLC 与 LLVM 共同完成：Go 侧保留 CPU 能力语义，GoALLC 在 LLVM IR 层实现函数多版本和能力检查的特化，LLVM 再利用这些已知条件展开循环、选择指令。这种配合让同一份 Go 代码在保留通用版本的同时，也能充分利用当前处理器的能力。

### Go 前端分析与 LLVM 配合：写屏障

还有一些优化，需要前端语义与后端处理共同完成。看下面这段代码：

```text
func setStatic(dst *any) {
    *dst = "static"
}
```

把静态字符串放进接口并写到目标位置，表面上是一条赋值。对编译器来说，它还涉及接口数据的表示，以及覆盖旧指针时的写屏障。

如果静态数据地址藏在尚未拆开的接口构造里，写屏障分析可能无法充分利用“新值来自静态数据”这一事实。把相应的 builtin 结构在合适阶段拆开之后，原有的 Go 写屏障分析就能看到它：新值不需要作为普通堆指针再记录一次，但被覆盖的旧指针仍需要处理。

前面生成 example.a 的小例子使用了相同的赋值方式。先看优化后 IR 中的写入基本块：

```text
nilcheck.notnil:                                  ; preds = %b1
  %0 = getelementptr i8, ptr %dst, i64 8, !dbg !33
  store ptr @"type:string<builtin.293>", ptr %dst, align 8, !dbg !33
  tail call void @goallc.gc.write.record(ptr nonnull @sample..stmp_0, ptr %0, i32 2) #5, !dbg !33
  store ptr @sample..stmp_0, ptr %0, align 8, !dbg !33
  ret void, !dbg !34
```

goallc.gc.write.record 记录待处理的写屏障信息，随后才是实际的指针写入。第三个参数 i32 2 表示省略新指针的记录，保留旧指针的记录。这与新值来自静态数据的分析结果对应。后续展开写屏障时，再生成检查屏障状态和调用 runtime 的控制流。

继续检查最终对象：

```text
go tool objdump -s sample.SetStatic example.a
```

调用附近的反汇编显示了 runtime.gcWriteBarrier1 的重定位名称，以及随后读取旧指针并记录的指令：

```text
example.go:6		0x74b			d10023fd		SUB $8, RSP, R29		
  example.go:5		0x74f			94000000		CALL 0(PC)			[0:4]R_CALLARM64:runtime.gcWriteBarrier1<1>	
  example.go:5		0x753			f9400408		MOVD 8(R0), R8			
  example.go:5		0x757			f9000328		MOVD R8, (R25)
```

Go 前端对静态数据的判断，经过 LLVM 流程保留到了最终指令中，让这次写屏障只需记录被覆盖的旧指针。

### 支持 Go 1.27 的实验性 SIMD，并交给 LLVM 继续优化

GoALLC 也支持 Go 1.27 仍处于实验阶段的 SIMD 功能，使用相同的 GOEXPERIMENT=simd 开关。面向可移植代码的 simd 包，以及面向具体架构的 simd/archsimd 包，都已接入 LLVM 后端，接口与操作覆盖基本跟上了 Go 1.27 的 SIMD 实现。

在 amd64 上，GoALLC 已实现 128、256、512 位向量的转换与代码生成，覆盖算术、比较、掩码、移位、重排、类型转换、FMA，以及 AES、SHA、无进位乘法等操作；arm64 路径则接入对应的向量操作与 CPU 能力检查。可移植 simd 继续沿用 Go 的向量宽度选择与模拟实现，架构相关操作根据对应 CPU 特性使用。相关适配与验证见 [​SIMD 集成记录](https://github.com/goallc/go/pull/273)。

```text
GOEXPERIMENT=simd go build ./...
GOEXPERIMENT=simd go test ./...
```

LLVM 在这里提供了更丰富的 SIMD 优化能力。GoALLC 会保留向量的元素类型与通道数，把它们表达为 LLVM 向量 IR，例如四个 float32 对应 <4 x float>。这样，向量运算可以参与常量折叠、重排化简、指令合并、寄存器分配和目标指令选择，并与周围的标量代码一起优化。CPU 特化后的函数还会带上对应的 target-features，让 LLVM 按当前处理器的能力继续优化。[​向量类型转换实现](https://github.com/goallc/go/blob/98a7240a92558e3c6f5348575489311f4c89d2e5/src/cmd/compile/internal/ssa/ssa2llvm.go#L201-L225)。

对于普通标量代码，LLVM 的 [​Loop Vectorizer 和 SLP Vectorizer](https://llvm.org/docs/Vectorizers.html)还会尝试将循环迭代或相邻运算组合成向量操作，并根据数据依赖、别名关系和目标 CPU 的成本模型选择实现。显式 SIMD 与自动向量化由此进入同一套优化流程，这也是接入 LLVM 后值得继续发挥的一项优势。

### 更大的优化空间，以及相应成本

包内优化之外，LTO 可以让编译器在链接阶段看到更大的范围，PGO 可以用真实执行情况帮助优化决策。这些都是继续演进的重要方向。

项目中已经有 LTO 相关实现，后续会继续完善它与不同构建方式的配合。本文介绍的默认编译流程使用普通 GoObj 路径。

相应的成本也很实际：LLVM 会增加工具链的体积和构建复杂度，更充分的优化通常也会增加编译工作。Go 本身在编译速度和工程体验上有很强的优势，GoALLC 需要在兼容性、编译成本和运行性能之间持续做平衡。

### 后续准备做什么

接下来首先还是继续补齐兼容性。已有测试发现的问题需要逐个分析和回归，平台覆盖、调试信息以及不同构建方式之间的组合，也需要持续验证。上游 Go 的语言、ABI 和运行时都在演进，跟进这些变化本身就是长期工作。

另一个方向是性能。现在已经可以沿着 Go 源码、Go SSA、LLVM IR、机器指令和运行结果追踪问题，后续希望把实际项目中的热点逐个分析清楚，让向量化、跨过程优化和目标架构优化发挥更稳定的作用。

这次重新做编译器，AI 在阅读代码、整理接口、补充测试和尝试实现上帮了很多忙。很多原本需要花较长时间摸索的问题，现在可以更快地做出原型、运行测试，再根据结果继续修改。这也让我有机会把更多精力放在 GC、栈和 ABI 这些需要反复推敲的细节上。

对我来说，能把几年前的想法重新做起来，已经是一件很有意思的事情。希望 GoALLC 能继续往前走，让现有 Go 项目用上 LLVM，也把这次尝试推进到一个足够扎实、值得长期使用的状态。
