## MCP（Model Context Protocol）的演进是自相矛盾的

最初的 MCP 很像传统的软件通信协议。客户端和服务器需要先建立连接，确认双方支持的功能，再维护会话，并向模型提供可用的工具列表。这些设计对软件工程师来说再自然不过。几十年来，我们一直在用类似的方式连接不同的软件系统。

但真正让 AI Agent 大规模使用这些工具之后，问题开始出现。一个 Agent 可能只需要查询某个客户的订单，却不得不在上下文窗口中加载几十甚至上百个工具的定义。大量 Token 被用于描述它根本不会调用的接口。模型不仅需要完成用户任务，还需要花费推理资源理解这些工具的用途、参数和调用关系。

于是，整个生态开始调整方向。工具不再需要一次性全部暴露，而是可以按需发现。多个工具调用可以放到代码沙箱中执行，减少模型与工具之间反复交换 JSON 的开销。协议本身也在朝着更轻量、更少依赖持久会话的方向发展。这些变化通常被解释为工程优化：减少 Token、降低延迟、提高扩展性。

但我觉得，背后还有一个更值得讨论的问题。我们一开始就假设，AI Agent 只是另一种软件客户端。只要把现有 API 包装成模型能够理解的 JSON Schema，它就能像普通程序一样使用这些接口。然而，这个假设可能忽略了传统软件开发中最重要的一部分工作。

## 传统软件在开发时理解业务，Agent 却要在运行时理解业务

假设我们要开发一个企业客户管理系统。系统提供一个接口：`get_customer(id=123)`对于传统程序来说，调用这个接口非常简单。传入客户 ID，等待返回结果即可。但这只是整个软件开发过程的最后一步。在程序真正运行之前，开发者已经做了大量工作。他需要知道客户数据存储在哪个系统，哪些字段代表客户的真实状态，什么情况下允许修改，接口失败之后是否需要重试，以及一个操作可能对其他业务系统产生什么影响。这些知识经过理解、设计和测试，最终被固化为代码。使得传统软件在运行时（runtime）并不需要重新理解这些业务规则。程序只是沿着开发者预先确定的路径执行。**也就是说，传统软件把理解成本放在开发阶段，把执行成本放在运行阶段。**

但 AI Agent 改变了这个分工。假设用户对 Agent 说：“把 XX 公司的订阅升级到企业版。”Agent 首先要找到客户，查询当前套餐，确认支付状态，判断是否符合升级条件，然后修改订阅，并开通新的使用权限。如果系统只向它提供一些基础 API，那么这些步骤之间的关系就需要 Agent 自己推断。它必须判断先调用哪个工具，后调用哪个工具，哪些操作可以重复执行，哪些操作可能造成不可逆的后果。过去由程序员在开发阶段完成的理解工作，现在被推迟到了运行阶段。每当 Agent 遇到一个新的任务，它可能都需要重新进行这部分推理。

AI Agent 并没有消除软件系统的业务复杂性，而是改变了复杂性的承担者。过去，复杂性主要由开发者承担，并通过代码转化为确定性的执行流程。现在，复杂性转移到模型的上下文窗口。而模型的理解需要 Token，推理需要时间，判断还可能出错。这也是为什么给 Agent 开放更多 API，并不必然意味着它能够完成更多任务。

## 为什么 CLI 有时候比 MCP 更高效

此前有一个受到广泛讨论的 GitHub 工作流测试。根据测试结果，使用 CLI 完成任务大约消耗 1365 个 Token，而通过 MCP 则消耗超过 44000 个 Token。表面上看，这似乎证明了 CLI 比 MCP 高效得多。但我认为，这个比较需要考虑一个经常被忽略的因素：模型究竟已经知道多少关于工具的知识？

例如：`gh pr view 214` 对于熟悉 GitHub 的开发者来说，这条命令几乎不需要解释。对于今天的前沿编程模型来说，同样如此。模型在预训练过程中接触了大量 Git、GitHub、Shell 和 SQL 的使用案例。这些知识已经被压缩进模型参数。当它看到 `gh pr view` 时，并不需要重新阅读一份详细文档才能理解这条命令的基本含义。但如果我们通过 MCP 向它提供几十个 GitHub 工具定义，就相当于每次执行任务时，都把模型已经知道的知识重新解释一遍。这当然会造成浪费。然而换一个场景，情况就不同了。假设 Agent 要操作一家企业内部开发的物流管理系统，其中有一个接口：`reconcile_manifest_variance`模型可能从来没有见过这个接口。它不知道所谓的 Manifest Variance 指什么，也不知道执行对账操作是否会修改库存、生成财务记录，或者触发后续物流流程。这时，详细的接口说明就不再是浪费，而是 Agent 正确完成任务的必要条件。

所以真正值得比较的不是 CLI 和 MCP，而是两种不同的知识来源。一种是模型在训练阶段已经掌握的知识。另一种是模型在运行阶段必须临时获取的知识。当然 CLI 的优势也不完全来自预训练。成熟的命令行工具通常提供帮助文档、子命令发现、输出过滤和脚本组合能力。模型可以先执行 `--help`，只了解当前需要的命令，而不必一次性加载所有接口。它还可以通过 Shell 将多个操作组合起来，只把必要的结果返回上下文。这些能力恰恰也是 Agent 工具系统正在努力实现的方向。当然我们不能断言未来的工具协议需要变成 CLI，但应该具备类似的按需发现和局部执行能力。一个好的 Agent 接口，不应该要求模型在执行任务之前，先理解整个软件系统。它应该允许模型随着任务的推进，逐步获得必要的知识。

## 工具粒度：Agent 不应该成为临时的工作流引擎

传统软件接口通常遵循一种非常自然的设计原则：将复杂业务拆解为独立、可复用的基础操作。例如，一个订阅系统可能提供：

- 查询客户
- 查询订阅
- 验证支付方式
- 修改套餐
- 开通使用权限

这种设计非常适合传统软件开发。因为程序员可以根据业务需要，将这些基础接口组合成不同的工作流。但如果把这些接口直接暴露给 Agent，就会出现一个问题。我们实际上是在要求模型充当一个临时的工作流引擎。假设 Agent 要完成一次套餐升级。它需要连续调用五个接口。如果前四个接口都成功了，第五个接口却失败了，会发生什么？客户的订阅状态可能已经升级，但新套餐的权限却没有开通。如果 Agent 再次尝试整个流程，是否会重复扣费？如果需要回滚，它又应该调用哪些接口？这些并不是语言理解问题，而是典型的软件事务一致性问题。传统软件早就有成熟的方式处理它们。这种情况下，我们可以简单把整个过程封装为一个更高层次的业务操作：`upgrade_customer_tier`Agent 只需要提供客户 ID 和目标套餐。至于支付验证、权限开通、事务回滚和状态更新，都由后端系统负责。这就是所谓的面向任务的操作原语（Task Primitives）。它与传统 CRUD 接口的区别在于：**CRUD 描述的是系统中有哪些资源可以被修改。Task Primitive 描述的是系统能够完成什么业务任务。**

不过，如果所有操作都被封装为预定义的业务流程，Agent 可能只是一个能够理解自然语言的菜单系统。它可以完成开发者提前设计好的任务，却很难处理那些没有预先定义的特殊情况。例如，一位客户提出：“产品有一点损坏，但我不想退货。能不能给我部分退款，再寄一个替换零件？”这个请求可能需要同时考虑订单金额、客户价值、库存情况、物流成本和售后政策。如果系统只有退款、换货、取消订单三个固定操作，Agent 就很难灵活处理。

因此，架构上很自然地会分出层次。对于高频、标准化、涉及资金或数据一致性的业务，提供完整的任务级操作。对于低频、非标准化的需求，保留可以组合的基础能力，但对高风险操作设置明确的权限和审批机制。这样，确定性的业务逻辑仍然由软件负责，而 Agent 可以发挥它在理解需求和组合能力方面的优势。

## 行为契约：API 不仅要描述参数，还要解释操作后果

即使我们将多个基础接口封装为一个高级操作，问题仍然没有完全解决。因为 JSON Schema 能够描述参数，却无法充分描述行为。例如：`cancel_enterprise_subscription`

参数只有两个：

- `subscription_id`
- `immediate`

从语法角度看，这个接口非常简单。但如果 `immediate=true`，究竟意味着什么？是立即停止下一次扣费，还是马上终止所有用户的访问权限？是否会自动退款？是否会删除客户数据？是否可以撤销？如果调用超时，重新执行会不会产生第二次退款？

这些信息对传统程序来说，通常已经由开发者在设计阶段理解，并写入了代码。但 Agent 需要在运行时做出决策。它需要的不仅是一个语法层面的 Schema，还需要一份行为契约（Behavioral Contract）。这份契约至少应该说明五件事。

1. 前置条件。 执行操作之前，系统必须满足哪些要求？
2. 副作用。 操作除了返回结果，还会影响哪些数据、用户或外部系统？
3. 可逆性。 如果执行错误，能否撤销，代价是什么？
4. 幂等性。 如果网络超时，Agent 能否安全重试？
5. 结果验证。 执行之后，Agent 应该通过什么信号确认操作真正成功？

我认为第五点尤其重要。因为在传统软件中，接口返回 HTTP 200，通常可以作为一次成功调用的信号。但对于 Agent 完成的业务任务来说，调用成功并不一定意味着业务目标已经实现。退款接口返回成功，可能只代表退款请求已经提交，并不意味着客户已经收到退款。创建物流订单成功，也不意味着包裹已经交给承运商。

因此，Agent 需要区分三个状态：操作被接受、操作已执行、业务目标已实现。这三个状态有时候发生在不同的时间，甚至由不同的系统负责。如果接口能够明确告诉 Agent 如何验证这些状态，它就不必根据模糊的返回信息自行猜测。

行为契约告诉模型必须遵守什么规则，并不等于这些规则一定会得到执行。例如，契约规定立即取消企业订阅之前必须获得人工确认。如果底层系统没有真正验证审批权限，那么模型仍然可能绕过这一步。所以，行为契约应该同时具有两种作用。一方面，它是提供给 Agent 的语义说明，帮助模型理解操作的条件和后果。另一方面，关键约束必须由后端系统强制执行。权限、审批、事务一致性、幂等性和审计不能只依赖模型遵守文字说明。换句话说，Agent 可以负责理解规则，但不能成为所有规则的最终执行保障。

## Skills、MCP 和行为契约，究竟是什么关系

如果从这个角度重新观察当前的 Agent 技术生态，就会发现一些看似相互竞争的技术，其实在解决不同的问题。MCP 主要解决能力连接，让 Agent 能够发现和调用外部系统提供的工具。Skills 主要解决任务知识，将某类任务的操作流程、判断规则、异常处理方式和辅助脚本组织起来，让 Agent 在需要时加载。而行为契约（Behavioral Contract）描述的是具体操作的规则和后果，包括前置条件、副作用、可逆性、幂等性以及结果验证方式。

但行为契约和 Skill 的内容可能高度重叠。比如一个售后 Skill，完全可以包含退款工具的使用条件、操作风险和验证方法。那么，这些规则究竟应该放在哪里？我更倾向于把与具体工具有关的行为规则，交给工具提供者统一维护，而不是分散在不同的 Skills 中。因为同一个退款工具可能被售后、财务和订单管理等多个 Skill 调用。如果退款规则发生变化，不应该要求所有 Skill 分别更新。

具体实现上，也不必把所有行为规则都塞进工具的 JSON Schema。对于简单操作，可以直接在工具描述中说明；对于复杂或高风险操作，可以只提供简短描述，让 Agent 在需要时进一步获取详细的行为契约，而不必每次调用前都重新加载。

不过，还有一类规则不应该只靠文字描述。例如退款额度、审批权限、订单状态等动态业务条件，更可靠的方式是由后端提供校验能力，让 Agent 在执行前直接查询是否满足条件。真正执行操作时，后端仍然需要独立验证这些约束。这样，Skill 负责指导 Agent 如何完成任务，工具接口负责解释具体操作，后端系统负责判断和执行关键业务规则。行为契约不一定需要成为独立的技术层，它可以是工具接口语义的一部分。

我认为，这种设计背后其实延续了一条传统软件工程原则：一项业务规则应该尽可能由真正负责执行它的系统维护，而不是依赖每一个调用者分别记住。过去，这样做是为了避免不同客户端之间出现业务逻辑不一致。现在，当调用者变成 AI Agent，这条原则反而更加重要。

因为 Agent 可以灵活理解和组合任务，但不应该每次都重新推断那些早已确定的业务规则。我们真正需要做的，不是把更多业务规则写进 Skill 或 Prompt，而是让 Agent 能够在需要时获取这些知识，并让负责执行的系统保证规则得到遵守。只有这样，才能在保留 Agent 灵活性的同时，避免把整个业务系统的可靠性都押在模型的推理能力上。

## 从 MCP 的演进，看 Agent-Native 软件真正需要改变什么

回到最初 MCP 的变化，我们会发现，减少 Token 消耗只是表面上的工程优化。更深层的问题是，传统 API 主要告诉程序如何调用一个功能，却默认调用者已经理解了背后的业务逻辑。而 Agent 恰恰缺少这部分预先确定的知识。所以，未来软件接口的设计重点，可能不再只是提供更多功能，而是让 Agent 能够按需发现功能、理解操作后果，并验证任务是否真正完成。**过去，我们为软件设计接口，是因为程序已经知道自己要做什么。现在，我们需要为 Agent 设计接口，是因为它还需要判断自己应该做什么。**
