过去一年里，我们与数十个来自不同行业、正在构建大语言模型（LLM）智能体的团队合作。有一个结论始终一致：最成功的实现，往往并没有使用复杂的框架或专门的类库，而是用简单、可组合的模式搭建起来的。

在这篇文章中，我们分享与客户合作以及自己构建智能体过程中学到的经验，并为开发者提供构建高效智能体的实用建议。

### 什么是智能体？

“Agent（智能体）”有多种定义方式。有些客户把智能体定义为完全自主的系统——它们长时间独立运行，使用各种工具完成复杂任务；另一些客户则用这个词描述遵循预定义工作流的、更偏指令式的实现。在 Anthropic，我们把所有这些变体统称为**智能体系统（agentic systems）**，但在架构上会明确区分**工作流（workflows）**与**智能体（agents）**：

- **工作流**是通过预定义的代码路径来编排 LLM 和工具的系统。
- **智能体**则是让 LLM 动态地主导自身流程和工具使用、并始终掌控”如何完成任务”的系统。

下文将详细探讨这两类智能体系统。在附录 1（”智能体实践”）中，我们介绍客户反馈价值尤为突出的两个应用领域。

### 何时该用（以及何时不该用）智能体

在构建基于 LLM 的应用时，我们建议先寻找尽可能简单的方案，只在确有需要时才增加复杂度。这意味着某些情况下根本不需要构建智能体系统。智能体系统通常是以延迟和成本换取更好的任务表现，你需要判断这种取舍是否划算。

当确实需要更高复杂度时：对于定义清晰的任务，工作流能提供可预测性和一致性；而当需要灵活性、需要由模型在规模化场景下做决策时，智能体是更好的选择。不过对很多应用而言，用检索增强和上下文示例来优化单次 LLM 调用，通常就已经足够了。

### 何时以及如何使用框架

有很多框架可以降低智能体系统的实现门槛，例如：

- [Claude Agent SDK](https://platform.claude.com/docs/en/agent-sdk/overview)；
- AWS 的 [Strands Agents SDK](https://strandsagents.com/latest/)；
- [Rivet](https://rivet.ironcladapp.com/)，一款拖拽式 GUI LLM 工作流构建器；以及
- [Vellum](https://www.vellum.ai/)，另一款用于构建和测试复杂工作流的 GUI 工具。

这些框架通过简化调用 LLM、定义与解析工具、串联调用等标准底层任务，让上手变得容易。但它们往往也会引入额外的抽象层，把底层提示词与响应藏起来，使调试更困难；同时还会诱使你在简单配置就够用的情况下增加不必要的复杂度。

我们建议开发者从直接使用 LLM API 开始：很多模式用几行代码就能实现。如果确实要用框架，务必理解其底层代码。对”底层到底做了什么”的错误假设，是客户出错的常见根源。

一些示例实现可参考我们的 [cookbook](https://platform.claude.com/cookbook/patterns-agents-basic-workflows)。

### 构建块、工作流与智能体

本节将探讨我们在生产环境中观察到的智能体系统常见模式。我们从最基础的构建块——增强型 LLM（augmented LLM）出发，逐步提升复杂度，从简单的组合式工作流一直到自主智能体。

### 构建块：增强型 LLM

智能体系统的基本构建块，是一个通过检索、工具、记忆等增强能力武装过的 LLM。我们当前的模型能够主动使用这些能力：自己生成搜索查询、选择合适的工具、决定保留哪些信息。

![](https://pic3.zhimg.com/v2-ee49392ceba5c6f29d8ba15d6ed33ae2_r.jpg)
*增强型 LLM*

我们建议重点关注实现的两个方面：让这些能力贴合你的具体用例，并确保它们为 LLM 提供简单、文档完善的接口。实现方式有很多种，其中一种是通过我们近期发布的[模型上下文协议（Model Context Protocol）](https://www.anthropic.com/news/model-context-protocol)，开发者只需一个简单的[客户端实现](https://modelcontextprotocol.io/tutorials/building-a-client#building-mcp-clients)，就能接入不断壮大的第三方工具生态。

本文后续默认每次 LLM 调用都能使用这些增强能力。

### 工作流：提示链（Prompt chaining）

提示链把任务拆解为一串步骤，每次 LLM 调用处理上一步的输出。你可以在任意中间步骤加入程序化检查（见下图中的”gate”，即闸门），确保流程没有跑偏。

![](https://pic3.zhimg.com/v2-80020fdd915a436be8c67c08de971bac_r.jpg)
*提示链工作流*

**适用时机**：当任务可以轻松、干净地拆解为固定的子任务时，这一工作流最为理想。其主要目标是用延迟换取更高的准确率——让每一次 LLM 调用都变成更简单的任务。

**适用示例**：

- 先生成营销文案，再把它翻译成另一种语言。
- 先写文档大纲，检查大纲是否满足某些标准，再基于大纲撰写文档。

### 工作流：路由（Routing）

路由对输入进行分类，并把它导向专门的后续任务。该工作流实现了关注点分离，也便于构建更专用的提示词。如果不用路由，针对一类输入做优化可能会损害其他输入上的表现。

![](https://pic2.zhimg.com/v2-6ababf4c5aa6598b53827387db4f0a09_r.jpg)
*路由工作流*

**适用时机**：路由适用于这样的复杂任务——存在明显不同的类别，分开处理效果更好，并且分类可以由 LLM 或更传统的分类模型／算法准确完成。

**适用示例**：

- 把不同类型的客服请求（一般咨询、退款申请、技术支持）导向不同的下游流程、提示词和工具。
- 把简单／常见问题路由到更小、更省成本的模型（如 Claude Haiku 4.5），把困难／异常问题路由到能力更强的模型（如 Claude Sonnet 4.5），以优化整体表现。

### 工作流：并行化（Parallelization）

LLM 有时可以同时处理同一任务，其输出再由程序聚合。并行化工作流主要有两种变体：

- **分段（Sectioning）**：把任务拆成彼此独立、并行运行的子任务。
- **投票（Voting）**：多次运行同一任务，获得多样化输出。

![](https://pic1.zhimg.com/v2-d4c2ac2e8ac0cf0b481688d3715ba5be_r.jpg)
*并行化工作流*

**适用时机**：当拆分出的子任务可以并行以提速，或需要多视角、多次尝试来提高结果置信度时，并行化很有效。对于涉及多个考量因素的复杂任务，让每个因素由一次独立的 LLM 调用处理，通常表现更好，因为模型能把注意力集中在每个具体方面。

### 工作流：编排者－执行者（Orchestrator-workers）

在编排者－执行者工作流中，一个中心 LLM 动态拆解任务，分派给多个执行者 LLM，并综合它们的结果。

![](https://pic4.zhimg.com/v2-1f2d0bba8656f6ad4e8a7fd3c5aa46c1_r.jpg)
*编排者－执行者工作流*

**适用时机**：适合无法预先确定所需子任务的复杂任务（例如在编码场景中，需要修改多少文件、每个文件改什么，往往取决于任务本身）。它在结构形态上与并行化相似，关键区别在于灵活性——子任务不是预先定义好的，而是由编排者根据具体输入来决定。

**适用示例**：

- 每次需要对多个文件做复杂改动的代码类产品。
- 需要从多个来源收集、分析信息以寻找相关线索的搜索任务。

### 工作流：评估者－优化者（Evaluator-optimizer）

在评估者－优化者工作流中，一次 LLM 调用生成响应，另一次调用在循环中提供评估与反馈。

![](https://pic3.zhimg.com/v2-6a8c134558ad64414108060f3c496e00_r.jpg)
*评估者－优化者工作流*

**适用时机**：当我们有清晰的评估标准、且迭代精修能带来可衡量的价值时，这一工作流特别有效。判断是否适配有两个信号：其一，当人类把反馈明确说出来时，LLM 的响应确实能获得可验证的改进；其二，LLM 本身也能提供这类反馈。这类似于人类作者打磨一篇文稿时的迭代写作过程。

**适用示例**：

- 文学翻译：翻译 LLM 最初可能捕捉不到某些细微之处，而评估者 LLM 能给出有用的批评意见。
- 复杂搜索任务：需要多轮搜索与分析才能收集到全面信息，由评估者判断是否有必要继续检索。

### 智能体（Agents）

随着 LLM 在理解复杂输入、推理与规划、可靠使用工具、从错误中恢复等关键能力上逐渐成熟，智能体开始在生产环境中出现。智能体的工作始于人类用户的指令，或与其展开的交互式讨论。任务一旦明确，智能体便独立规划与执行，必要时可能回到人类那里索取更多信息或判断。在执行过程中，至关重要的一点是：智能体每一步都要从环境中获得”真实反馈”（如工具调用结果、代码执行结果），以评估自身进展。随后，智能体可以在检查点或遇到阻碍时暂停，等待人类反馈。任务通常在完成时终止，但为了保持可控，也常常加入停止条件（例如最大迭代次数）。

智能体可以处理很复杂的任务，但其实现往往相当直接：通常就是”在循环中基于环境反馈使用工具的 LLM”。因此，清晰、周到地设计工具集及其文档就变得极为关键。我们在附录 2（”为你的工具做提示工程”）中详细展开工具开发的最佳实践。

![](https://pic4.zhimg.com/v2-fc87b5e172ff96c0378afa8ab5b90ae9_r.jpg)
*自主智能体*

**适用时机**：智能体适用于开放式问题——难以或无法预测所需步骤数，也无法硬编码一条固定路径。LLM 可能要运行很多轮，因此你必须对其决策能力有一定信任。智能体的自主性使它非常适合在可信环境中扩展任务规模。

### 组合与定制这些模式

这些构建块并非硬性规范，而是开发者可以按不同用例塑形、组合的常见模式。与任何 LLM 功能一样，成功的关键在于**衡量表现并持续迭代实现**。再强调一次：只有当复杂度能带来可验证的结果改善时，才应该增加复杂度。

### 小结

在 LLM 领域，成功不在于构建最复杂的系统，而在于构建**适合你需求的**系统。从简单的提示词开始，用完备的评测去优化它，只有当简单方案确实不够用时，才引入多步智能体系统。

实现智能体时，我们尽量遵循三条核心原则：

1. 在智能体设计中保持**简单性**。
2. 通过显式展示智能体的规划步骤，优先考虑**透明性**。
3. 通过充分的**工具文档与测试**，精心打磨智能体－计算机接口（ACI）。

框架可以帮你快速起步，但在走向生产环境时，不要犹豫去减少抽象层、直接用基础组件来构建。遵循这些原则，你就能创造出不仅强大，而且可靠、可维护、被用户信任的智能体。

### 附录 1：智能体实践

我们与客户的合作揭示了 AI 智能体两个尤其有前景的应用方向，它们充分体现了上述模式的实际价值。这两个应用都说明：当任务同时需要对话与行动、具备清晰的成败标准、支持反馈闭环、并融入有意义的人工监督时，智能体能带来最大价值。

### A. 客户支持

客户支持把人们熟悉的聊天机器人界面，与工具集成带来的增强能力结合在一起。它天然适合更开放式的智能体，原因在于：

- 支持交互天然遵循对话流程，同时需要访问外部信息与执行外部动作；
- 可以集成工具来拉取客户数据、订单历史与知识库文章；
- 退款、更新工单等动作可以通过程序化处理；以及
- 成败可以通过用户定义的”问题解决”清晰衡量。

已经有多家公司通过”按成功解决计费”的用量定价模式证明了这一路径的可行性，这本身就体现了它们对智能体效果的信心。

### B. 编码智能体

软件开发领域展现出 LLM 功能的巨大潜力，能力从代码补全一路演进到自主解决问题。智能体在这里特别有效，是因为：

- 代码方案可以通过自动化测试验证；
- 智能体可以把测试结果当作反馈来迭代方案；
- 问题空间定义清晰、结构良好；以及
- 输出质量可以客观衡量。

在我们自己的实现中，智能体现在仅凭拉取请求（PR）描述，就能在 [SWE-bench Verified](https://www.anthropic.com/research/swe-bench-sonnet) 基准上解决真实的 GitHub issue。不过，尽管自动化测试有助于验证功能正确性，人工评审对于确保方案契合更广泛的系统需求，仍然不可或缺。

### 附录 2：为你的工具做提示工程

无论你在构建哪种智能体系统，工具都很可能是智能体的重要组成部分。[工具](https://www.anthropic.com/news/tool-use-ga)通过在 API 中精确定义其结构与规格，让 Claude 能与外部服务和 API 交互。当 Claude 打算调用某个工具时，API 响应中会包含一个[工具使用块（tool use block）](https://docs.anthropic.com/en/docs/build-with-claude/tool-use#example-api-response-with-a-tool-use-content-block)。工具的定义与规格，应当和你的整体提示词一样，投入同等力度的提示工程。在这篇简短的附录里，我们讲讲如何为工具做提示工程。

同一个动作往往有多种描述方式。例如，一次文件编辑既可以写成 diff，也可以重写整个文件；结构化输出既可以把代码放进 Markdown，也可以放进 JSON。在软件工程里，这类差异只是形式上的，可以无损互相转换。但对 LLM 来说，某些格式写起来要困难得多：写 diff 需要在写新代码之前，就知道块头（chunk header）里有多少行发生变化；把代码写进 JSON（相比 Markdown）则需要对换行符和引号做额外转义。

我们对选择工具格式的建议如下：

- 给模型足够的 token，让它在”把自己写进死胡同”之前先想一想。
- 让格式尽量贴近模型在互联网文本中自然见过的形式。
- 避免任何格式”额外开销”，例如必须精确统计数千行代码，或对它写出的每段代码做字符串转义。

一条经验法则是：想一想人机交互界面（HCI）投入了多少设计精力，就计划在*智能体*－计算机接口（ACI）上投入同样多的精力。以下是几点具体思路：

- **站在模型的角度想**：仅凭描述和参数，这个工具怎么用是否一目了然？还是你得仔细琢磨才行？如果是后者，模型大概率也一样。一份好的工具定义通常包含用法示例、边界情况、输入格式要求，以及与其他工具之间的清晰界限。
- **怎样改参数名或描述能让含义更明显**？把它当作给团队里一位初级开发者写一份出色的文档字符串（docstring）。当你有很多相似工具时，这一点尤其重要。
- **测试模型如何使用你的工具**：在我们的 [workbench](https://console.anthropic.com/workbench) 里跑大量示例输入，观察模型会犯什么错，然后迭代。
- **给工具做**[防错设计（Poka-yoke）](https://en.wikipedia.org/wiki/Poka-yoke)：调整参数，让它更难被用错。

在为 [SWE-bench](https://www.anthropic.com/research/swe-bench-sonnet) 构建智能体时，我们花在优化工具上的时间，实际上比花在整体提示词上的还多。例如，我们发现当智能体离开根目录后，模型在使用相对路径的工具上会出错。修复办法是把工具改成始终要求绝对路径——结果模型使用得毫无差错。
