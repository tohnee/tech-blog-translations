## 第 6 章 数据并行与梯度桶：mcore 自研 DDP

> **本章源码锚点**（Megatron-Core `core_v0.18.0`）<br>

- `megatron/core/distributed/distributed_data_parallel.py`（`DistributedDataParallel`）
- `megatron/core/distributed/param_and_grad_buffer.py`（`_ParamAndGradBuffer` / `_ParamAndGradBucket` / `_ParamAndGradBucketGroup`）
- `megatron/core/distributed/finalize_model_grads.py`

---

### 6.1 本章导读

数据并行（DP）是最古老、最直观的分布式训练方式：每张卡放一份完整模型，各自算不同数据的梯度，反向后 all-reduce 同步。PyTorch 自带 `torch.nn.parallel.DistributedDataParallel`，为什么 Megatron 要自己写一个 `DistributedDataParallel`？

答案藏在两个词里：**梯度桶（bucket）** 与 **通信-计算重叠（overlap）**，以及一个 PyTorch DDP 难以优雅支持的需求——**为分布式优化器（第 10 章）铺路**。本章讲清 Megatron 自研 DDP 的三层数据结构、梯度如何从 backward hook 一路流到 all-reduce/reduce-scatter，以及如何把通信藏进反向计算里。

---

### 6.2 背景介绍：数据并行的梯度同步

DP 的数学极简：`dp` 张卡各自用不同 microbatch 算梯度 `g_i`，同步后每卡得到平均梯度 `(1/dp)·Σ g_i`，再各自用相同梯度更新（保证模型副本一致）。同步靠 **all-reduce**。

朴素实现：反向全部结束后，对每个参数逐个 all-reduce。问题有二：

1. **通信与计算串行**：反向算完才通信，GPU 在通信时空闲。
2. **小张量太多**：逐参数 all-reduce，每次都有 NCCL 启动开销，小张量通信效率极低。

---

### 6.3 问题提出与已有方案的不足

PyTorch DDP 已经用”梯度分桶 + 反向 hook 触发异步 all-reduce”解决了上述两点。但它对 Megatron 有几处不够：

1. **难以对接分布式优化器**：ZeRO-1 需要把梯度 buffer 按 DP rank 切分做 **reduce-scatter**（而非 all-reduce），并让每个 rank 只更新自己那片。PyTorch DDP 的 all-reduce 语义与此不符。
2. **fp32 梯度累加**：大模型需要 bf16 计算 + fp32 梯度累加（`main_grad`）来保证数值稳定，PyTorch DDP 对这种”分离的高精度累加缓冲”支持不佳。
3. **精细的显存/通信控制**：Megatron 需要连续显存 buffer、可控桶大小、多实例分层 all-reduce 等。

于是 Megatron 自研了一套 DDP，核心是三层缓冲结构。

---

### 6.4 核心思想：连续显存 + 分桶 + 反向即通信

Megatron DDP 的三个核心决策：

1. **连续显存 buffer**：把同类型（同 dtype、是否 expert）参数的梯度放进一整块连续显存，而非每个参数一块。这让 reduce-scatter/all-gather 可以对整块高效操作，也便于分布式优化器按偏移切片。
2. **分桶（bucketing）**：把连续 buffer 再切成若干桶（默认约 40MB），以桶为单位触发通信——桶足够大以摊薄 NCCL 启动开销，又足够小以尽早开始通信、与反向重叠。
3. **反向即通信**：参数梯度一算完就触发其所在桶的通信，不等整个反向结束。

---

### 6.5 数据结构：三层缓冲结构

### 6.5.1 `_ParamAndGradBuffer`：连续显存底座

`param_and_grad_buffer.py` 的 `_ParamAndGradBuffer` 是最底层。构造时（`__init__`，约 `param_and_grad_buffer.py:941`）：

- 按 `(param_dtype, grad_dtype, is_expert_parallel)` 对参数分组；
- 为每组分配一整块连续显存 `param_data` 和 `grad_data`；
- 参数按 NCCL 效率做 padding 对齐；
- 每个参数的梯度是 `grad_data` 的一个 **view**——梯度累加在 view 上原地进行，无需额外拷贝。

### 6.5.2 `_ParamAndGradBucket`：桶

`_ParamAndGradBucket`（`param_and_grad_buffer.py:72`）是 buffer 上的一段区间，持有：

- `params_list`：本桶包含的参数集合；
- `grad_data` / `param_data`：指向 buffer 对应区间的 view；
- `offset` / `numel_unpadded`：在大 buffer 中的偏移与有效元素数；
- `gradient_scaling_factor`：本桶梯度的缩放因子（用于平均 / MoE）；
- `param_to_index`：每个参数在桶内的 `(start, end)`。

### 6.5.3 `_ParamAndGradBucketGroup`：桶组

`_ParamAndGradBucketGroup`（`param_and_grad_buffer.py:159`）把多个桶聚合起来做统一通信，负责：

- `per_param_grad_ready_counts`：跟踪每个参数的梯度是否就绪；
- `param_gather_handle` / `grad_reduce_handle`：异步通信句柄；
- 通信-计算重叠的核心调度逻辑。

三层关系：

### 6.6 核心流程：梯度从 hook 到 all-reduce

### 6.6.1 反向 post-hook：累加到 main_grad

`distributed_data_parallel.py:449` 的 `_make_backward_post_hook`：每个参数梯度算完即触发：

```text
def hook(*unused):
    ...
    param.main_grad.add_(param.grad.data)   # 累加进 fp32 main_grad（buffer 的 view）
    param.grad = None                        # 立即释放 bf16 的 param.grad
    if self.ddp_config.overlap_grad_reduce:
        self._bucket_group_for_param[param].register_grad_ready(param)
```

三步：**累加到 fp32 main_grad → 释放 bf16 grad → 登记就绪**。fp32 累加正是第 4 章”梯度累加融合”衔接的地方（TE/CUDA kernel 可把 wgrad 直接写进 main_grad）。

### 6.6.2 register_grad_ready：就绪计数与自动派发

`register_grad_ready`（`param_and_grad_buffer.py`）为参数就绪计数；当**一个桶内所有参数都就绪**时，立即调用 `start_grad_sync()` 派发该桶的通信。这样早算完的桶先通信，与后面还在算的桶的反向计算重叠。

### 6.6.3 start_grad_sync：all-reduce 还是 reduce-scatter

`start_grad_sync`（`param_and_grad_buffer.py:557`）是通信派发中枢：

```text
# 1) 把高精度 main_grad 拷进通信 buffer
# 2) 可选 NaN/Inf 检查
# 3) 按 gradient_scaling_factor 缩放
# 4) 派发集合通信：
if self.ddp_config.use_distributed_optimizer:
    dist_reduce_scatter_func(local_data_view, bucket.grad_data, ...)   # ZeRO-1：reduce-scatter
else:
    torch.distributed.all_reduce(bucket.grad_data, ...)                # 传统 DDP：all-reduce
```

**这是本章最关键的分叉：**

- **不开分布式优化器**：`all_reduce`，每卡得到完整平均梯度；
- **开分布式优化器**：`reduce_scatter`，每卡只得到自己负责的 `1/dp` 梯度分片——因为它只更新那一片参数（第 10 章）。

### 6.6.4 异步与重叠

```text
async_op = (self.ddp_config.overlap_grad_reduce
            and self.ddp_config.num_distributed_optimizer_instances == 1)
```

`async_op=True` 时通信立即返回、句柄存起来，反向继续；`finish_grad_sync` 里 `grad_reduce_handle.wait()` 等待完成。这与第 4 章 TP 的异步通信一样，依赖 `CUDA_DEVICE_MAX_CONNECTIONS=1` 保证调度顺序。

---

### 6.7 梯度缩放因子：平均与 MoE

`distributed_data_parallel.py:169` 计算每个桶的 `gradient_scaling_factor`：

- **普通参数**：若 `average_in_collective`，则缩放 1.0 由集合通信内部求平均；否则缩放 `1/dp_size`，通信只做 sum。
- **专家参数**：缩放 `expert_dp_size / dp_cp_size`——因为专家梯度在更小的 expert-dp 组内归约，需要校正系数保持等效平均（第 9 章）。

`start_grad_sync` 里在通信前统一施加：`bucket.grad_data *= bucket.gradient_scaling_factor`。

---

### 6.8 finalize_model_grads：跨并行维的梯度收尾

`finalize_model_grads.py` 在所有 DP 同步后做最后收尾，处理**跨其它并行维**的梯度一致性：

- **embedding 梯度**：PP 首尾 stage 共享 word embedding 权重，需在 `_EMBEDDING_GROUP`（第 3 章）内 all-reduce，否则首尾发散。
- **序列并行的 LayerNorm 梯度**：SP 下某些参数在 TP 组内需要额外归约（第 7 章）。
- 各类”重复参数”的梯度统一。

这一步是”多维并行梯度正确性”的最后保险，容易被忽视却至关重要。

---

### 6.9 性能分析

- **重叠收益**：桶级异步通信可把 DP all-reduce 几乎完全藏进反向计算，理想下 DP 通信开销趋近于 0。
- **桶大小权衡**：桶太小→NCCL 启动开销占比高；桶太大→通信开始得晚、重叠窗口小。默认 ~40MB 是经验平衡点。
- **reduce-scatter vs all-reduce**：reduce-scatter 通信量约为 all-reduce 的一半（`Φ` vs `2Φ`），这也是分布式优化器附带的通信收益。
- **多实例分层**：`num_distributed_optimizer_instances > 1` 时用分层 all-reduce（intra + inter），在超大 DP 组下降低跨节点通信（第 10 章）。

### 6.10 与其它框架对比

| 维度 | Megatron DDP | PyTorch DDP | DeepSpeed ZeRO | FSDP |
| --- | --- | --- | --- | --- |
| 梯度分桶 | ✓（连续 buffer + view） | ✓ | ✓ | ✓（flat param） |
| fp32 main_grad | ✓（分离缓冲） | 不原生 | ✓ | ✓ |
| 同步语义 | all-reduce 或 reduce-scatter | all-reduce | reduce-scatter（ZeRO-2/3） | reduce-scatter |
| 为 DistOpt 铺路 | ✓（核心设计目标） | ✗ | 内建 | 内建 |
| 通信重叠 | ✓ 桶级异步 | ✓ | ✓ | ✓ |

Megatron DDP 与 FSDP/ZeRO 的共同点是”连续 buffer + reduce-scatter”，区别在于 Megatron 把”梯度同步（DDP）”与”参数/优化器分片（DistOpt）”解耦成两个模块，组合更灵活。

### 6.11 常见误区

1. **以为 Megatron 用的是 torch DDP**。是自研 `megatron.core.distributed.DistributedDataParallel`。
2. **忽视 main_grad 的 fp32 累加**。bf16 直接累加会因舍入误差损失精度，尤其梯度累积步数多时。
3. **桶大小随意设**。影响重叠效率，需结合模型和网络实测。
4. **忘了 finalize_model_grads**。embedding / SP 梯度不收尾会导致隐蔽的数值不一致。
5. **开 DistOpt 却期待 all-reduce 语义**。此时是 reduce-scatter，每卡梯度只是自己那片，别的片是”垃圾”。

---

### 6.12 本章总结

- Megatron 自研 DDP，核心是三层结构：`_ParamAndGradBuffer`（连续显存）→ `_ParamAndGradBucket`（~40MB 桶）→ `_ParamAndGradBucketGroup`（聚合通信 + 重叠）。
- 梯度流：反向 post-hook 累加进 fp32 `main_grad` → `register_grad_ready` 计数 → 桶就绪即 `start_grad_sync` 派发。
- 关键分叉：不开 DistOpt 走 all-reduce，开 DistOpt 走 reduce-scatter（ZeRO-1）。
- 桶级异步通信 + `CUDA_DEVICE_MAX_CONNECTIONS=1` 实现 DP 通信与反向重叠。
- `gradient_scaling_factor` 处理平均与 MoE 校正；`finalize_model_grads` 收尾跨并行维（embedding/SP）梯度。
- 自研的动机：对接分布式优化器、fp32 累加、精细显存/通信控制。
