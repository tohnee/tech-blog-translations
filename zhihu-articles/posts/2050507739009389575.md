最近本地 LLM 推理的讨论有两个方向特别有意思：一个是 llama.cpp 这样的轻量运行时正在把模型推到越来越多的硬件上；另一个是 CXL 正在把“内存”和“加速器”从传统 PCIe 外设变成更接近共享内存语义的系统组件。

我想把这两个方向放在一起想象一下：如果未来有一张 CXL Type-2 AI card，上面同时有 GPU、ternary NPU、HBM/GDDR 本地内存，并且能通过 CXL.cache / CXL.mem 与主机共享一致性内存，那么 llama.cpp 这类运行时应该如何利用它？更具体一点：能不能把 LLM 推理拆成 prefill、decode attention、FFN 三类不同负载，分别映射到最合适的硬件上？

这不是说今天 llama.cpp 已经开箱即用支持“CXL Type-2 + ternary NPU + GPU + operator-level disaggregation”。我更愿意把它看成一张路线图：哪些部分今天已有雏形，哪些部分需要 runtime、kernel、memory allocator 和 scheduler 一起补齐。

1. 为什么是 llama.cpp？

llama.cpp 的价值不是“它一定比所有框架都快”，而是它足够贴近系统底层。它的核心目标是用 C/C++ 做低依赖、高可移植性的 LLM 推理，并且已经支持多种量化格式和硬件后端，包括 CUDA、HIP、Vulkan、SYCL、Metal、CPU+GPU 混合推理等。官方 README 也明确写到它支持 1.5-bit 到 8-bit 量化、CUDA、HIP、Vulkan、SYCL，以及 CPU+GPU hybrid inference。

这意味着 llama.cpp 很适合作为一个“硬件实验平台”：不是先假设统一硬件，而是把不同硬件能力暴露成 GGML backend，再让 graph partition、tensor placement、KV cache 管理和 kernel selection 去匹配硬件。

现在它也已经开始碰到 NPU 方向。例如 OpenVINO backend 文档写到，该 backend 面向 Intel CPU、GPU、NPU，并保持与 GGUF 模型生态兼容；不过文档也明确提醒，性能、内存优化、精度验证、更广泛的量化和算子覆盖仍在进行中。 Ascend 方向也有 CANN backend，目标是让 llama.cpp 直接使用 Ascend NPU；文档中列出了 FP16、Q4_0、Q8_0 等模型/数据类型支持情况，但也能看出不同芯片和量化格式的支持并不完全一致。

所以，llama.cpp 不是终点，而是一个适合做异构推理编排的起点。

2. 为什么是 CXL Type-2？

很多人提到 CXL 时先想到 Type-3 memory expander，也就是“给服务器外挂一块更大的内存”。但对 AI 推理来说，真正有想象力的是 Type-2 device。

Linux CXL 文档里对 Type-2 的描述很直接：Type-2 CXL device 支持 [CXL.io](http://cxl.io/)、CXL.cache、CXL.mem，通常是带高带宽本地内存的加速器。关键区别在于它有 Host-Managed Device Memory，设备可以在本地内存上工作，而 CPU 仍然可以以 coherent DMA 的方式访问同一片内存。

这和传统 PCIe GPU 的心理模型不一样。传统 PCIe 更像“host 发命令、device 干活、显存和内存靠显式 copy 或 DMA 同步”。CXL Type-2 更接近“设备有自己的高速本地内存，但主机和设备之间可以有更强的一致性内存语义”。CXL Consortium 也把 CXL 定义为面向处理器、内存扩展和加速器的 cache-coherent interconnect，用来维持 CPU memory space 与 attached devices 上内存之间的一致性。

更重要的是，CXL 还在往更高带宽和更复杂拓扑发展。CXL 4.0 已经发布，官方资料称其把带宽从 64 GT/s 提升到 128 GT/s，并加入 bundled ports、memory RAS 增强等特性。

换句话说，Type-2 的问题不是“能不能把模型塞到一块内存里”，而是：能不能把权重、KV cache、activation buffer 和不同计算单元的访问关系，重新设计成一个接近共享内存的推理数据流。

3. 为什么是 ternary NPU？

Ternary 这里指的是 BitNet b1.58 这类权重取值为 {−1, 0, 1} 的原生低比特模型，而不是简单把任意 FP16 模型后量化到 1.58 bit。

BitNet b1.58 的论文页面说明，每个参数都是三值 {−1, 0, 1}，并声称在相同模型大小和训练 token 数下，可以接近 FP16/BF16 Transformer 的困惑度和下游任务表现，同时在 latency、memory、throughput、energy 等方面更低成本。 微软后续的 bitnet.cpp 工作则针对 ternary BitNet b1.58 做了 CPU kernel，报告了在 x86 上 2.37x 到 6.17x、ARM 上 1.37x 到 5.07x 的加速区间。

这对硬件的启发很明显：如果模型权重真的是 ternary，那么 FFN/MLP 里的大规模矩阵乘不再一定需要传统 FP16/BF16 tensor core 的完整能力。一个专门做 ternary dot product、lookup-table accumulation、scale fusion 的 NPU tile，可能在能效上比通用 GPU 更合适。

GPU 仍然有价值。它适合高吞吐、成熟 kernel、复杂 attention、batch prefill、采样、通用算子 fallback。但如果 FFN 权重是 ternary，那么把 FFN 交给 NPU，把 attention/KV 交给更高带宽的 GPU/HBM/CXL memory path，就变成一个很自然的系统拆分。

4. 从 Prefill/Decode 解耦，到 Attention/FFN 解耦

LLM 推理不是一个均匀负载。

Prefill 阶段处理整个 prompt，矩阵计算密集，适合大 batch、大 GEMM、较高算力密度。Decode 阶段每次生成一个 token，主要压力变成 KV cache 读取、memory bandwidth 和低延迟调度。Splitwise 的论文摘要就把这点说得很清楚：LLM 请求有两个阶段，prompt computation 是 compute-intensive，token generation 是 memory-intensive，二者在 latency、throughput、memory、power 特征上都不同；它提出把两个阶段拆到不同机器上做 phase-specific resource management。

这已经进入工程框架。NVIDIA Dynamo 的文档也明确支持 disaggregated serving：prefill worker 和 decode worker 是独立 pool，请求先进入 prefill，再把 KV cache 状态转移或暴露给 decode worker，最后由 decode worker 继续生成。文档同时提醒，这并不总是更好；小模型、短 prompt、低并发或者没有高速 KV transfer 的场景，聚合式部署可能更简单更快。

但下一步会更细：不是只拆 prefill/decode，而是拆 Attention/FFN。

在 decode 阶段，Attention 是 stateful 的，需要读越来越长的 KV cache；FFN 通常更接近 stateless 的 token-wise 计算，尤其在 MoE 模型里，attention、expert FFN、dispatch/combine 的资源需求差异更大。2026 年的 AFD 论文就把这个趋势概括为：LLM inference 正在从 chunked-prefill aggregation，到 prefill-decode disaggregation，再到 operator-level Attention-FFN Disaggregation；它把 memory-bound attention 和 compute-intensive expert FFNs 放到不同 GPU groups 上研究。

我的判断是：CXL Type-2 + ternary NPU + GPU 的组合，最适合做的不是“把整个模型跑在某一个设备上”，而是把推理路径拆成多个硬件亲和的 stage。

5. 一个“Type-2 Ternary+NPU+GPU all-in-one”设想

可以想象这样一张卡：

主机侧是 x86/ARM CPU，运行 Linux、llama.cpp、HTTP server、tokenizer、sampling、调度器。卡侧是 CXL Type-2 device，包含一个 GPU tile、一个或多个 ternary NPU tile、一块 HBM/GDDR 本地内存，以及通过 CXL.mem 暴露给 host 的 host-managed device memory 区域。CXL.cache 让设备更自然地访问 host memory，CXL.mem 让 CPU 更自然地访问 device memory。

数据可以这样放：

模型权重分层放置。Embedding、norm、small ops 可以在 CPU/GPU fallback；attention projection 和部分 dense ops 在 GPU；ternary FFN 权重常驻 NPU 近端 SRAM/HBM；冷权重或者较少访问的专家权重可以放在 CXL memory 区域。

KV cache 放在 CXL-visible 的 device memory 或者分层 KV pool 里。长上下文 decode 时，attention engine 优先从高带宽本地内存读热 KV；冷 KV 可以通过 CXL memory tier 做扩容。注意这里不能把 CXL 当 HBM 用，CXL latency 和带宽特征不同；正确做法是把它当成可一致访问、可调度、可分层的内存池。

Activation buffer 用 ring buffer 或 double buffer 在 GPU 和 NPU 之间传递。每层的 hidden state 从 attention 输出进入 FFN，FFN 输出再回到 residual stream。因为 FFN 的输入输出相对 KV cache 小得多，Attention/FFN disaggregation 的通信量有机会被 pipeline 隐藏。

执行路径可以这样拆：

Prefill 阶段，GPU 做 prompt attention 和大批量矩阵计算，NPU 并行跑可映射的 ternary FFN。Prefill 输出 KV cache，写入 CXL-visible KV pool。

Decode 阶段，每步 token 先走 attention。Attention 读 KV cache，偏 memory bandwidth，适合 GPU tile 或专门的 memory-side attention engine。随后 FFN 被派发给 ternary NPU tile。NPU 做三值权重矩阵计算，输出回 GPU/host 做 residual、norm、sampling 或下一层输入。

如果是 MoE 模型，router 可以在 GPU/CPU 上做，expert FFN 分发到 NPU tile 或 CXL-attached expert memory。这里真正的难点不是“能不能算”，而是 expert 权重驻留、dispatch/combine 通信和 tail latency。

6. llama.cpp 需要补哪几块？

第一，需要一个 CXL-aware allocator。今天 llama.cpp 里已经有多 backend 和 device offload 的基础，但 CXL Type-2 场景需要更细的 tensor placement：哪些 tensor 在 host DRAM，哪些在 CXL device memory，哪些必须在 GPU HBM，哪些可以是 DAX/file descriptor 映射出来的 coherent region。Linux 文档也提到 Type-2 device memory 可以通过 DAX devices 或 file descriptors 暴露，程序能直接访问 device memory，而不是完全依赖 block-transfer semantics。

第二，需要 operator-level graph partition。现在常见的做法是按 layer offload，或者按 backend 支持情况 fallback。但 Attention/FFN disaggregation 需要更细：同一层里的 attention subgraph、FFN subgraph、norm、residual、MoE routing 可能要落到不同设备上。

第三，需要异步队列和 fence。CXL coherence 不是免费午餐。CPU、GPU、NPU 如果频繁抢同一 cache line，会把系统拖进 coherence ping-pong。runtime 必须明确 tensor ownership、读写阶段、barrier、prefetch 和 eviction 策略。

第四，需要 ternary kernel backend。BitNet-style 模型不是“把 Q4 kernel 改成 Q1.58”这么简单。它需要专门的数据布局、scale 融合、lookup-table 或 bit-serial accumulation、activation quantization 处理，以及和 GGUF metadata 的约定。

第五，需要服务级 scheduler。Prefill/Decode 解耦的目标不是单次 benchmark 漂亮，而是同时优化 TTFT、TPOT、吞吐、能耗和 P99。Dynamo 文档也强调 disaggregated serving 的关键路径是 KV transfer，并且是否适合取决于 prompt 长度、并发、KV transfer 能力等条件。

7. 我希望看到的命令行长什么样？

下面这段不是今天 upstream 已经支持的命令，而是我希望未来 llama.cpp 或类似 runtime 能提供的抽象：

cmake -B build \

-DGGML_CUDA=ON \

-DGGML_OPENVINO=ON \

-DGGML_CXL=ON \

-DGGML_TERNARY_NPU=ON

llama-server \

-m bitnet-b1.58-xxb.gguf \

--ctx-size 32768 \

--kv-placement cxl:/dev/dax0.0,hot=hbm,cold=cxl \

--graph-map prefill=gpu,attention=gpu,ffn=npu,small_ops=cpu \

--pd-policy split \

--af-policy ratio:auto \

--scheduler ttft=500ms,tpot=30ms,p99=target

这几个 flag 背后的意思是：

--kv-placement 不是简单“KV 放哪里”，而是声明热 KV、冷 KV、long-context KV 如何在 HBM/CXL/host DRAM 之间分层。

--graph-map 不是传统 layer split，而是 operator split。Prefill、attention、FFN、small ops 可以有不同硬件目标。

--pd-policy 控制 prefill/decode 是否拆分；--af-policy 控制 attention/FFN 是否拆分，以及 attention side 和 FFN side 的资源比例。

scheduler 不是平均 tokens/s 导向，而是面向 TTFT、TPOT 和 P99 的服务质量导向。

8. 今天可以怎么验证这个方向？

可以分三步做。

第一步，用现有 llama.cpp 跑 CPU/GPU baseline，记录 prompt processing speed、token generation speed、KV cache 大小、不同 context length 下的 TTFT/TPOT。llama.cpp 已有多种后端和量化支持，足以建立一个基线。

第二步，用 OpenVINO 或 CANN backend 试 NPU 路线，但要接受限制。OpenVINO backend 文档明确列出当前 NPU 上下文长度、多并发、模型支持等限制；例如 NPU context 太大可能失败，llama-server -np > 1 在某些模式下不支持，多种量化和模型还在 work in progress。 CANN backend 也有模型和数据类型支持矩阵，不同芯片对 Q4_0/Q8_0/FP16 的支持差异需要实测。

第三步，用现有 disaggregated serving 框架理解调度问题。llama.cpp 自带 RPC backend 可以暴露远端 GGML devices，但官方文档也明确说 RPC backend 目前是 proof-of-concept、fragile and insecure，不应该跑在开放网络或敏感环境。 所以它适合做实验，不适合直接当生产级 P/D 或 A/F disaggregation 方案。生产级思路可以参考 Dynamo 这类已经把 prefill/decode worker pool、KV transfer、routing 做成一等概念的系统。

验证指标应该至少包括：

TTFT：长 prompt 下第一 token 是否变快。

TPOT：decode 每 token 延迟是否稳定。

P99：高并发时尾延迟是否恶化。

KV transfer GB/s：disaggregation 是否被 KV 搬运吃掉。

CXL link utilization：CXL 是在帮忙，还是成了瓶颈。

NPU occupancy：ternary NPU 是否真的被喂饱。

Energy/token：NPU 的能效优势是否抵消了通信成本。

9. 最大风险在哪里？

第一，CXL 不是魔法 HBM。CXL 能提供更好的内存语义和扩展性，但如果每个 decode step 都把长 KV cache 从远端 CXL memory 线性扫一遍，latency 很可能会很难看。CXL 更适合作为分层内存、共享内存、扩容内存和跨单元协调机制，而不是替代本地 HBM 的热路径。

第二，ternary 模型不是任意模型的无损压缩按钮。BitNet b1.58 的重点是原生 1.58-bit 训练范式和相应 kernel/runtime，而不是把所有 Llama/Qwen/DeepSeek 模型随便转成三值就能保持效果。

第三，NPU 软件栈经常比硬件更难。LLM decode 有动态 shape、KV cache、分支、采样、长上下文、连续 batching。很多 NPU 更擅长静态图和固定 shape 视觉模型，要跑好 LLM 需要 compiler、runtime、kernel 和模型结构一起配合。

第四，operator-level disaggregation 会放大调度复杂度。AFD 论文也指出，每一层拆得越细，调度设计空间就越深，工作负载、资源分配、互连拓扑都会影响最终收益。

第五，llama.cpp 的优点是轻量，代价是很多服务级能力需要重新设计。P/D router、KV transfer、topology-aware scheduling、operator partition，这些都不是简单加一个 backend flag 就能完成。

10. 结论：未来的本地推理不是“GPU vs NPU”，而是“谁做哪一段”

我认为未来的 LLM 推理硬件不会只有一个胜者。GPU 继续负责通用高吞吐和成熟 kernel；NPU 负责更专用、更低能耗的矩阵和低比特计算；CXL Type-2 负责把设备本地内存和 host memory 的边界打薄；llama.cpp 这类 runtime 则负责把模型 graph、KV cache、activation、backend kernel 和服务级 scheduler 拼在一起。

所以，“CXL Type-2 + ternary NPU + GPU all-in-one”的真正意义，不是把所有东西塞进一张卡里，而是给 LLM 推理提供一种新的分工方式：

Prefill 交给算力密度更高的 GPU。

Decode attention 交给内存带宽和 KV locality 更好的单元。

FFN 交给 ternary NPU。

KV cache 交给 HBM/CXL/host DRAM 分层管理。

Runtime 根据 TTFT、TPOT、P99 和 energy/token 动态调度。

如果说过去的本地 LLM 优化关键词是“量化”和“显存够不够”，那么下一阶段的关键词可能是：phase-aware、operator-aware、memory-aware、topology-aware。

llama.cpp 的下一个有趣方向，也许不是再多支持一种显卡，而是让我们能对一个 Transformer layer 说：

attention 去靠近 KV cache，FFN 去靠近 ternary compute，prefill 和 decode 不要互相打架。

这才是 CXL Type-2 时代异构推理真正值得期待的地方。
