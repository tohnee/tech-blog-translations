**<u>Agentic Transformation 观察</u>**

企业 Agentic AI 转型中，成本痛点不再只是 Token 消耗，容易被忽视的**交接税**才是预算失控关键：多智能体协作时，信息传递、版本同步、重试返工带来隐性损耗，协作链路越长损耗越高，且不计入模型计费。单纯压低 Token 单价治标不治本，根源在于交接设计。 Token 单价是行业通用变量，而交接损耗由企业自身流程决定，Agent 成本竞争的核心，最终落在内部协作链路与编排层能力上。

如今，企业客户关注点正从「能不能做」转向「值不值、跑得稳不稳、投入产出如何衡量」。长时间运行的智能体、多智能体协作与高频工具调用会显著抬升 Token 消耗与总体成本。

看到这里，很多人第一反应往往是压 Token 单价：换更便宜的模型、缩短 prompt、加缓存。这些动作有效，但只作用在账面上最显眼的那一栏。真正让预算失控的部分，发生在智能体把任务交给下一个智能体的过程中间。

但大多数企业给 Agent 做预算时，表上通常只有一栏：Token 单价乘以预估调用量。这一栏算得出模型花了多少钱，算不出协作花了多少钱。如何应对企业Agentic AI 转型过程中的“交接税” 成本？企业用什么承接交接？本篇将重点探讨此种情况。

## **算不清的那部分，是交接**

把一次多智能体协作拆开，成本结构是一段连续工作被切成 N 段，段间要有 N 减 1 次交接，每一次都是一次有损传递。

本文把这几次损耗合起来称为**交接税**：协作链越长，税率越高，而且它不出现在模型的计费单上。交接税由三项构成。

**传递损耗。**上游完成任务后把结果交给下游，交出去的只是一段压缩过的描述，完整的工作状态没有跟着走。哪些信息必须带走、哪些可以丢，取决于上游怎么总结。总结做得糙，下游就要重新取数、重新试错。这部分重做的调用记在下游账上，根源在上游的交接设计。

**同步损耗。**多个分支并行时会对同一个对象形成各自的版本，分支越多，版本漂移越大。合并阶段先要对齐「我们讨论的还是不是同一件事」，对齐不产出任何交付物，但消耗调用。

**重试损耗。**上游交接不完整，下游做到一半发现前提不对，回退、重来、再交接一次。一次重试的成本远高于一次调用，因为它包含已花掉的全部，加上重来的全部。

三者有方向：传递是源头，同步把它放大，重试是它最终长成的样子。只治重试，等于每次从最下游开始灭火。

## **这个框架的边界在哪**

交接税只在一种条件下成立：任务确需被切成多段，且段间由不同智能体承接。而这一步正是企业复杂任务面临的现状。

只有当一个智能体从头做到尾，交接次数为零，成本全部由调用量决定，压单价才是有效的。任务虽多段但由同一智能体连续完成、状态不中断，交接税也接近零。

真正适用的是第三种情况：任务跨时间、跨系统、跨角色，必须由多个智能体分担，且各段能力边界不同。**企业的内容生产、知识转译、营销协作多属此类——任务要持续推进、跟踪版本、维护跨段一致性，就必须有人把状态交出去。**

判断场景在不在框架内，问一个问题：链路里有没有哪一段，下游拿到结果后需要重新理解上游意图。有，交接税就在。

## **交接为什么比 Token 更难算**

Token 是计量的，交接不是。计费单上看得到调用次数和字符数，看不到某次调用里有多少在重建上一次交接丢掉的东西。

这会造成两个后果。

**第一，预算会低估：**按单价做的预算隐含假设每次调用都在推进任务，而相当一部分调用在原地重建状态，表里没有对应科目。

**第二，优化会走偏**：账面上只有 Token，资源就全押在单价上；换模型能降单价，交接设计不变则重做量不变，总账降不下来多少。

反过来，如果交接设计改好，单价一分未降，总账可能降一大截。事实上，评估体系的建设已经在往这个方向走。沙利文《2026 年全球桌面 AI 智能体市场研究报告》把产品技术领先指数拆成 Agentic 能力、Harness 工程、模型适配与可用性、扩展与开放能力，细分项含任务规划、工具调用、多 Agent 协作、记忆管理、错误恢复、权限控制。报告没直接谈成本，但评估项正好覆盖交接损耗的三个来源：协作对应传递，记忆对应同步，错误恢复对应重试。评估体系已把交接当作能力，企业核算还停在单价上。

## **降交接税的四个动作**

以下动作按投入产出排序，都作用在交接环节，不作用在模型选择上。

**动作一：把交接物定成结构化的交付契约。**

别让上游用自然语言自由总结。给每一类交接定义固定字段：任务目标、已完成的部分、未决的部分、下游需要的前置条件、可回退的边界。字段固定后，下游不必猜上游的意思。

举一个例子。一条内容生产链从洞察到策略到文案到审核，四段之间只传结论，审核发现前提不对就只能整条回退；传的是结论加依据加未决项，审核可在未决项上做局部修正，不必重跑前三段。关键是交接物的结构，长度帮不上忙。**特赞的 Model Hub ，通过 Creative Trajectory 把交接物从「一段压缩描述」改成「一份结构化工件」**：任务定义（目标、输入、成功标准、约束、人工确认点）、路径探索（候选、假设、证据、反例）、评价与剪枝（哪些被保留、合并、淘汰及原因）、人工决定（专家修改、未决分歧、正式选择）。这正好是动作一要的固定字段，只不过字段不是团队自己拍，而是平台按任务保留。下游拿到的是可比较、可复盘的记录，不必再猜上游的意思。

**动作二：并行分支先对齐对象，再对齐结论。**

并行之前先把「要处理的同一个对象是什么」固定下来：同一份资料、同一版数据、同一套判定标准。对象一致，结论分歧才是真分歧；对象不一致，后面每一次对齐都白做。

并行分支对不齐，通常不是结论分歧，是各自手里的对象不是同一版。特赞通过建立上下文系统（**Context System）**把对象、关系、来源、时间、版本、权限和决策状态组织成同一套 Context，并保留「哪些结论已被替代、哪些规则只在特定条件下成立」。分支启动前锁定同一份 Context 版本，合并时才有共同的比较基准。

**动作三：把重试预算显性化。**

预算表里单列一栏「重试与返工」，按历史比例估，不按理想值估。它的作用是让团队看见这项成本，省钱是顺带结果。看不见的成本不会被优化。重试之所以沉淀不下来，是因为企业只看到模型总账单。**特赞的Model Hub**的任务级成本运营把同一业务任务里的多次调用关联起来，按模型、应用、智能体、团队和任务观察总 Token、成本、时延、重试与模型错配。识别出的是具体环节的重试与错配，不是年底的一栏汇总，可以直接变成动作三要的那个科目。

**动作四：优先缩短链路。**

三段链路的交接税低于五段，即使每段都变慢。合并职能重叠的智能体、砍掉不必要的中间层，比提升单段速度更有效。这一层正是由特赞 Model Hub 的编排能力实现的。**Model Orchestration**按任务的难度、模态、质量要求、成本和数据边界，判断需要什么模型能力：简单步骤不必动用旗舰模型，复杂任务才拆分子任务、组合模型或切换路径，一个模型够用时不增加调用。它减少的不是交接次数，是每段内部被迫外包给更强模型的次数，链路不必为迁就能力不足而变长。但要划清：编排解决的是「该用哪个模型或模型组合」，不是「能不能少一次交接」。

## **Model Hub 不能做什么？**

href="[https://mp.weixin.qq.com/s?__biz=MjM5NTMzNzg3NA==&mid=2650730917&idx=1&sn=58897efb3ddf4dfeebc96fc05937aa9f&scene=21#wechat_redirect](https://mp.weixin.qq.com/s?__biz=MjM5NTMzNzg3NA==&mid=2650730917&idx=1&sn=58897efb3ddf4dfeebc96fc05937aa9f&scene=21#wechat_redirect)" data-draft-type="text-link">特赞的Tezign Model Hub是一个发散推理与多模型编排平台。它不替代企业已有的 AI Gateway，定位差异在于它直接做推理与编排，而不只是把请求转交给某个模型。

它站在智能体与底层模型之间，做两件事：

**第一，直接做推理**——Creative Reasoning Model 把开放商业问题拆成多条差异化路径，在目标、证据、约束与风险中比较并动态收敛，输出候选路径、比较依据与未决问题，它本身就是可调用、可部署的模型供给；

**第二，为任务做编排**——Model Orchestration 理解任务的难度、模态与质量要求，同时评估成本、时延、部署与数据边界，动态选择单一模型，或组合、切换多个模型。

对应到交接链，大致是这样一张分层：

![](https://pic1.zhimg.com/v2-1ed98c12468ea4f07f3137fcd6010560_r.jpg)

说到底，企业级 Agent 的成本竞争最后会落在协作设计上。Token 单价是行业共享的公开数字，谁都能拿到；交接损耗由每家企业的流程决定，每家企业都不同。**当采购门槛从「能不能做」移到「值不值」，值不值这道题的答案写在自己的协作链路里，不在模型供应商的价目表上。**

这也是为什么编排层值得单独拿出来看。它不解决流程臃肿，也不替你决定该不该砍掉一个中间环节——它只做两件更难被别人替代的事：让上游的判断以结构化方式交出去，让下游的每个子任务配上合适的模型，而不是一味选贵的模型。对已经在多智能体上跑长任务的企业，这两件事通常比再谈一次折扣更能动总账。
