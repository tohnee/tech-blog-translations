**项目地址：** [https://github.com/zhanghaifeng9988/quant_qlib_mlops](https://github.com/zhanghaifeng9988/quant_qlib_mlops)

**先说定位：这不是一个交易策略项目。**

它是一个**端到端 MLOps 工程项目**，量化只是载体。项目用 Microsoft Qlib + LightGBM 在美股日频数据上走通了一条完整的工程链路：数据处理 → 特征工程 → 训练 → 实验追踪 → 模型注册 → 在线推理 → 监控 → CI/CD 镜像发布。重点不是“能不能赚钱”，而是**一个机器学习模型怎么从研究脚本变成一套可重复运行、可监控、可维护的工程系统**。

---

### 这个项目具体做了什么

**数据与特征层**

- 用 yfinance 获取美股日频行情，做数据质量检查和 Qlib `.bin` 数据转换，用 `manifest.json` 记录数据版本和血缘。
- 用 Qlib Alpha158 生成特征，存成 Parquet 离线文件，供后续训练和推理读取。

**模型生命周期**

- Qlib + LightGBM 训练，配合多窗口 Walk-forward 验证，对预测结果进行回测，并将回测结果，记录在mlflow中。
- MLflow 做实验追踪和模型注册，用别名管理版本，FastAPI 加载已注册模型提供按日期的批量预测接口。

**监控与可观测性**

- 预测结果和实际收益回填到 PostgreSQL，计算滚动 IC / Rank IC 和特征 PSI 漂移。
- Grafana 做可视化面板和 Webhook 告警。你可以点这两个快照直接看面板长什么样：<br>

**工程化**

- Docker 多阶段构建 + Docker Compose 管理本地服务，GitHub Actions 做依赖锁定检查、Ruff、编译检查和 GHCR 镜像发布。

架构上做了一个关键取舍：**离线特征计算和在线推理解耦**。数据处理和特征工程在批处理环境跑完，生成 Parquet；FastAPI 只读特征做截面预测，不在请求里实时算全量特征。这个设计让推理服务保持轻量，也让特征和模型可以各自独立演进。

### 重要说明：原始数据不在仓库里

**仓库里没有原始行情数据，也没有训练好的模型产物。** 这是有意为之——数据体积大、且涉及第三方数据源的分发限制。你可以把源码拉回去，从 yfinance 重新拉数据、重新跑数据处理和特征工程、重新训练和注册模型，**完整地从零验证整条链路**。

但前提是：**请在理解项目结构和各模块职责的前提下再操作**，不要把它当成一个 `docker compose up` 就万事大吉的“一键项目”。数据准备、Qlib 数据转换、MLflow 注册、FastAPI 服务、监控脚本之间是有先后依赖和配置耦合的，先读 `architecture.md`（358 行，记录了架构决策和当前不实施的范围），再决定从哪个模块开始跑。

### 适合谁看

- 想了解 **MLOps 在真实项目里到底包含哪些环节**、而不是只看概念的人。
- 已经有一定 ML 基础，想看到一个**从数据到监控的完整工程骨架**长什么样的人。
- 对 Qlib 感兴趣，但不想只停留在 Notebook 层面的人——这个项目展示了 Qlib 的训练产物怎么进入 MLflow、怎么被 FastAPI 服务化、怎么被 Grafana 监控。

不适合想找“能赚钱的量化策略”的读者。项目本身也没有接真实交易账户，没有 Point-in-Time Universe，没有自动模型晋升和回滚——这些“当前不实施的范围”在 `architecture.md` 里写得很清楚。
