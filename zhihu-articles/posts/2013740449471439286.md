## 0. 引言

一个训练框架代码量庞大、特性繁多，想要面面俱到往往会陷入流水账。对于 ZeRO 这类切分框架，**显存**和**通信**是理解其精髓的两条主线。第一篇先把"静态"的显存分配搞清楚：在训练开始之前，各类张量究竟存在哪里、占多少、从哪来。

ZeRO 并行策略分三档，切分粒度依次递进，下面给出经典示意图：

![](https://pic2.zhimg.com/v2-b176156438206a815075419458b88963_r.jpg)

因为在实际工作中涉及到的模型往往比较大，因此使用 ZeRO-3 会比较多，本文也只介绍 ZeRO-3 的相关内容。ZeRO-3 的核心实现分布在两个类中：

- `deepspeed/runtime/zero/init.py` 的 `Init` 类：负责模型构建阶段的参数分片
- `deepspeed/runtime/zero/stage3.py` 的 `DeepSpeedZeroOptimizer_Stage3` 类：负责优化器侧的显存分配

初始化阶段涉及以下五类张量，它们共同构成了 ZeRO-3 的静态显存格局：

| 张量类型 | 变量名 | 精度 | 存放位置 | 初始化来源 |
| --- | --- | --- | --- | --- |
| 参数原始分片 | param.ds_tensor | BF16/FP16 | GPU / CPU / NVMe | Init._zero_init_param |
| 模型参数连续分片 | fp16_partitioned_groups_flat | BF16/FP16 | GPU | stage3.py，从 ds_tensor 整理 |
| 主权重（优化器更新对象） | fp32_partitioned_groups_flat | FP32 | GPU / CPU / NVMe | stage3.py，从 fp16 clone |
| 梯度分区缓冲区 | grad_partitions_flat_buffer | BF16/FP32 | GPU / CPU(pinned) | stage3.py |
| 优化器状态（m, v） | state["exp_avg"] 等 | FP32 | GPU / CPU / NVMe | Adam/AdamW |

## 1. 权重分片的真正起点 —— `param.ds_tensor`

一个容易被忽视的前置问题：**BF16 权重在进入优化器之前，究竟存在哪里？**

ZeRO-3 的参数切分**不是**从优化器初始化开始的，而是在模型构建阶段就已经完成——通过 `deepspeed.zero.Init()` 上下文管理器。每个 `nn.Module` 子类的 `__init__` 完成后，DeepSpeed 会自动触发 `_post_init_method`，对该层所有参数执行 ZeRO-3 初始化：

```text
# deepspeed/runtime/zero/init.py
# Init._post_init_method（节选）

def _post_init_method(self, module):
    for name, param in module.named_parameters(recurse=False):
        if not is_zero_param(param):
            # 1. 迁移到本地 GPU
            if not get_accelerator().on_accelerator(param):
                param.data = param.data.to(self.local_device)
            # 2. 执行 ZeRO-3 核心初始化：属性挂载 + 多卡广播 + 分片
            self._zero_init_param(param)
```

`_zero_init_param` 内部按序做三件事：

```text
# deepspeed/runtime/zero/init.py
# Init._zero_init_param

def _zero_init_param(self, param):
    # 步骤1：将原生 Parameter 转换为 ZeRO-3 增强型参数对象
    # 挂载 ds_id / ds_status / ds_shape / ds_tensor 等核心属性
    # 同时在参数上绑定 all_gather / partition / partition_gradients 等方法
    self._convert_to_deepspeed_param(param)

    # 步骤2：广播参数数据，确保所有 rank 的初始值完全一致
    dist.broadcast(param.data, 0, self.get_dp_process_group())

    # 步骤3：执行分片 —— ZeRO-3 显存优化的核心
    # 将完整参数按 dp_world_size 均匀切分，当前 rank 只保留自己的那一段
    # 完整参数的显存立即释放，分片结果存入 param.ds_tensor
    param.partition()
```

![](https://picx.zhimg.com/v2-49f2b14215237a771944e82dd109ecf9_r.jpg)

`_convert_to_deepspeed_param` 中为每个参数挂载的核心显存相关属性：

```text
# deepspeed/runtime/zero/init.py
# Init._convert_to_deepspeed_param（节选）

# 参数运行状态机：AVAILABLE（完整可用）/ NOT_AVAILABLE（仅有分片）/ INFLIGHT（通信中）
param.ds_status = ZeroParamStatus.AVAILABLE

# 参数原始完整形状（分片后 param.shape 会变化，通过此属性留存原始维度）
param.ds_shape  = param.shape
# 参数原始总元素数（无 padding）
param.ds_numel  = param.numel()

# ★ 核心字段：当前 rank 持有的参数分片张量
# partition() 执行后，完整权重释放，分片数据存入此字段
# 这是 inference-only 模型（如 ref model）BF16 权重的唯一存储位置
param.ds_tensor = None

# 参数常驻显存策略：小参数可以不分片，全程常驻显存，减少通信开销
# 条件：开启常驻策略 + 单参元素数 ≤ param_persistence_threshold
#       + 累计常驻元素数 ≤ model_persistence_threshold
param.ds_persist = (
    Init.apply_param_persistence
    and param.ds_numel <= Init.param_persistence_threshold
    and Init.num_persisted_elements + param.ds_numel <= Init.model_persistence_threshold
)
```

`partition()` 执行后，参数的完整权重被释放，分片数据存入 `param.ds_tensor`，`param.data` 退化为仅含本 rank 分片的视图。这是 ZeRO-3 最基础的显存形态，也是所有模型（无论是否参与训练）共有的起点。

## 1.1 两类模型的 BF16 权重存储位置

理解上述流程后，RLHF 中一个常见的困惑就迎刃而解了：**为什么 ref model 和 actor model 的 offload 实现方式不同？**

本质原因在于两类模型**经历了不同的初始化路径**，BF16 权重最终落在不同的字段中。

![](https://pica.zhimg.com/v2-0d6261731dce6f53d6547df9ef4187cc_r.jpg)

**公共路径（所有模型都经历）：**

```text
with deepspeed.zero.Init()
  → _post_init_method → _zero_init_param
      → _convert_to_deepspeed_param  （挂载 ds_tensor / ds_status 等属性）
      → broadcast                    （多卡广播，对齐初始值）
      → partition()                  （完整权重释放，分片存入 param.ds_tensor）
```

**分叉点：有无优化器决定了 BF16 权重的最终归宿：**

|  | ref model（仅推理） | actor model（训练） |
| --- | --- | --- |
| BF16 权重最终存储位置 | param.ds_tensor | fp16_partitioned_groups_flat |
| 是否经历 defragment | 否 | 是（ds_tensor → 连续 lp_param_buffer） |
| 是否有 FP32 主权重 | 否 | 是（fp32_partitioned_groups_flat） |
| offload 操作对象 | param.ds_tensor | fp16/fp32_partitioned_groups_flat |

💡 **一句话总结**：`param.ds_tensor` 是 ZeRO-3 参数分片的**原始存储**，是所有模型共有的基础字段；`fp16_partitioned_groups_flat` 是优化器对 `ds_tensor` 分片数据**重新整理后的连续化版本**，只有训练模型才有。搞清楚这一点，是正确实现 RLHF 多模型显存管理的前提。

## 2. BF16 权重的连续化整理 —— `fp16_partitioned_groups_flat`

进入本节时，模型各参数的 BF16 分片已存放在 `param.ds_tensor` 中。优化器初始化做的事是：把这些分散的 `ds_tensor` 分片**重新整理为一块连续显存**，以提升后续 AllGather 的通信效率。

### 2.1 sub_group 的划分

![](https://picx.zhimg.com/v2-ce5013839cf6098a5e8cffb28a910ead_r.jpg)

在整理之前，参数首先被划分为多个 **sub_group**，这是 ZeRO-3 优化器管理粒度的基本单位：

```text
# deepspeed/runtime/zero/stage3.py
# _create_fp16_sub_groups（简化）

def _create_fp16_sub_groups(self, params_group):
    params_group_numel = sum(p.partition_numel() for p in params_group)
    sub_group_size = self.sub_group_size

    # sub_group_size=None 或超过总量：不拆分，整组作为单个 sub_group
    if sub_group_size is None or sub_group_size >= params_group_numel:
        return [params_group]

    # 按分片后元素数贪心累加，超过阈值切一刀
    sub_groups, sub_group, local_size = [], [], 0
    for param in params_group:
        sub_group.append(param)
        local_size += param.partition_numel()  # 注意：用分片后的元素数，不是完整参数
        if local_size >= sub_group_size or id(param) == id(params_group[-1]):
            sub_groups.append(sub_group)
            sub_group, local_size = [], 0
    return sub_groups
```

划分完成后，`_create_fp16_partitions_with_defragmentation` 完成 bookkeeping 并走两条路径：

```text
# deepspeed/runtime/zero/stage3.py
# _create_fp16_partitions_with_defragmentation（主路径，offload_param=False）

# bookkeeping：建立 sub_group_id → group_id 映射、记录 numel、padding 等元数据
for param_group_idx, param_group in enumerate(param_groups):
    for sub_group in param_group:
        sub_group_idx = len(self.fp16_groups)
        self.fp16_groups.append(sub_group)
        # 直接引用各参数的 ds_tensor，是后续 defragment 的输入
        self.fp16_partitioned_groups.append([param.ds_tensor for param in sub_group])
        self.fp16_partitioned_groups_flat_numel.append(
            sum(p.partition_numel() for p in sub_group)
        )
        # 最后一个 rank 需要 padding 以对齐 world_size，其余 rank 全为 0
        rank_requires_padding = dist.get_rank() == dist.get_world_size() - 1
        self.groups_padding.append(
            [p.padding_size() if rank_requires_padding else 0 for p in sub_group]
        )

# offload_param=False：参数常驻 GPU，执行 defragment
parameter_partitions = self._get_parameter_partitions()
self.lp_param_buffer = __class__.defragment(parameter_partitions)
self._set_fp16_partitioned_groups_flat()
# fp16_partitioned_groups_flat[i] 指向 lp_param_buffer 的对应切片
```

**`sub_group_size` 的意义**：它同时控制了 `optimizer.step()` 中每次"换入→更新→换出"的操作粒度。越小则 step 期间的显存峰值越低，但 IO 调用次数越多；越大则反之。这一参数将初始化阶段的显存布局与训练阶段的显存峰值直接关联起来。

### 2.2 defragment：碎片化 ds_tensor → 物理连续大块

![](https://pic1.zhimg.com/v2-2a8d12085911ed8c374b1dca48354df2_r.jpg)

各参数的 `ds_tensor` 是在模型构建时逐参数独立分配的，物理地址分散。AllGather 操作需要高效读取连续内存，因此 defragment 将所有分片整理为一块连续显存：

```text
# deepspeed/runtime/zero/stage3.py
# defragment（静态方法）

@staticmethod
def defragment(tensors):
    # ① CPU 侧一次性申请 pinned memory（总元素数 = 各张量 numel 之和）
    cpu_buffer = torch.empty(
        sum(t.numel() for t in tensors),
        dtype=tensors[0].dtype,
        pin_memory=True,        # pinned memory 加速后续 CPU→GPU 传输
    )

    # ② 建立映射表：记录每个张量在连续内存中的 (offset, numel)
    offsets, offset = [], 0
    for t in tensors:
        offsets.append((offset, t.numel()))
        offset += t.numel()

    # ③ GPU → CPU 批量非阻塞拷贝，同步等待完成
    for t, (off, numel) in zip(tensors, offsets):
        cpu_buffer.narrow(0, off, numel).copy_(t, non_blocking=True)
    torch.cuda.synchronize()

    # ④ resize_(0) 将各原张量的 Storage 尺寸置零，使引用计数归零
    #    再 empty_cache() 将碎片真正归还给 CUDA 驱动
    #    注意：resize_(0) 本身不释放显存，empty_cache() 才是真正释放的那一步
    for t in tensors:
        t.data.resize_(0)
    gc.collect()
    torch.cuda.empty_cache()

    # ⑤ CPU buffer 整块搬回 GPU（物理连续），同步等待
    gpu_buffer = cpu_buffer.to(tensors[0].device, non_blocking=True)
    torch.cuda.synchronize()

    # ⑥ 按映射表用 narrow 重新切片，赋回各原张量的 .data 指针
    #    此后各张量在逻辑/物理层面均指向 gpu_buffer 的对应区段
    for t, (off, numel) in zip(tensors, offsets):
        t.data = gpu_buffer.narrow(0, off, numel)

    # ⑦ 返回整块连续 GPU Tensor 作为母 buffer
    return gpu_buffer
```

💡 `tensor.data.resize_(0)` 只是把 Storage 尺寸置零、使引用计数归零，并不会立即释放 CUDA 显存。`torch.cuda.empty_cache()` 才是将碎片真正归还给 CUDA 驱动的那一步，两者缺一不可。

## 3. FP32 主权重 —— `fp32_partitioned_groups_flat`

FP32 主权重是优化器实际更新的对象（混合精度训练的标准做法）。分配逻辑在 `_create_fp32_partitions` 中，以 sub_group 为单位从 `fp16_partitioned_groups_flat` clone 而来：

```text
# deepspeed/runtime/zero/stage3.py
# _create_fp32_partitions（简化，主路径 offload_optimizer=False）

for i, sub_group in enumerate(self.fp16_partitioned_groups_flat):
    # 直接在 GPU 上分配 FP32 显存，将 BF16 sub_group clone 为 FP32
    fp32_partitioned = sub_group.clone().float().detach()
    fp32_partitioned.requires_grad = True   # 确保优化器可以更新
    self.fp32_partitioned_groups_flat.append(fp32_partitioned)

# 清空优化器参数列表，param_groups 平时保持为空
for group in self.optimizer.param_groups:
    group["params"] = []
```

![](https://pica.zhimg.com/v2-9f3fd83b041e1789e1a51e3164472e08_r.jpg)

**为什么 `param_groups` 平时是空的？**

标准 PyTorch 优化器在 `step()` 时会遍历 `param_groups` 里的所有参数并持有它们的引用。如果把所有 sub_group 的 FP32 主权重都常驻在 `param_groups` 里，它们对应的显存就无法被释放，无论当前是否在更新这个 sub_group。

ZeRO-3 的做法是 `param_groups` 平时保持空列表，只在当前 sub_group 执行 `optimizer.step()` 的瞬间动态填入，执行完立刻清空：

```text
# _optimizer_step（节选）
self.optimizer.param_groups[param_group_id]['params'] = [fp32_param]  # 填入
self.optimizer.step()
self.optimizer.param_groups[param_group_id]['params'] = []             # 清空
```

这样 PyTorch 优化器内部对参数的引用随 `step()` 的结束而消失，配合 `_release_sub_group` 里的 `.grad = None`，实现了在 sub_group 粒度上精确控制 FP32 主权重显存生命周期的目标。优化器状态（`exp_avg`、`exp_avg_sq`）通过 `self.state[fp32_param]` 以对象 id 为 key 查找，不依赖 `param_groups`，因此不会因动态填充/清空而丢失。

## 4. 梯度分区缓冲区 —— grad_partitions_flat_buffer

ZeRO-3 反向阶段涉及两块独立的梯度缓冲区：一块是反向期间临时中转的桶 buffer，一块是跨 micro-step 持久存在的归约结果 buffer。理解这两块的分工，是理解整个反向链路的前提。

### 4.1 两块缓冲区的初始化

```python
# deepspeed/runtime/zero/stage3.py
# _setup_for_real_optimizer（节选）

# 第一块：归约前的桶 buffer
if self.contiguous_gradients:
    self.__ipg_bucket_flat_buffer: Tensor = torch.empty(
        self.reduce_bucket_size,
        dtype=self.dtype,                   # 模型参数精度（BF16/FP16/FP32）
        device=get_accelerator().current_device_name()
    )

# 第二块：归约结果的持久存储
self.grad_partitions_flat_buffer = None
self.__param_id_to_grad_partition: Dict[int, Tensor] = {}

all_params = list(itertools.chain.from_iterable(self.fp16_groups))

self.grad_partitions_flat_buffer: Tensor = torch.zeros(
    sum(p.partition_numel() for p in all_params),
    dtype=self.gradient_accumulation_dtype,  # 累积精度，由配置独立决定
    device=self.device,
)
```

两块缓冲区的对比：

| 缓冲区 | 大小 | 精度 | 生命周期 | 作用 |
| --- | --- | --- | --- | --- |
| __ipg_bucket_flat_buffer | reduce_bucket_size（默认 5×10⁸ 元素） | 模型参数精度（BF16/FP16/FP32） | 反向期间反复复用 | 桶 buffer：反向时各 param.grad 的中转站，归约时整块喂给 NCCL |
| grad_partitions_flat_buffer | 所有参数 partition_numel 之和 | 由 gradient_accumulation_dtype 配置决定 | 训练全程持久 | 归约结果 buffer：跨 micro-step 累加，step 从此读取 |

grad_partitions_flat_buffer 的精度由 gradient_accumulation_dtype 单独控制，不简单跟随训练精度。源码里 engine.get_data_types 的默认逻辑是：

```python
if self._config.grad_accum_dtype is None:
    if model_dtype == torch.bfloat16 and not self.zero_optimization():
        grad_accum_dtype = torch.float32   # 裸 BF16 训练：升 FP32 保精度
    else:
        grad_accum_dtype = model_dtype     # ZeRO + BF16：跟随训练精度
```

ZeRO-3 + BF16 训练默认下，grad_partitions_flat_buffer 的精度就是 BF16。这不意味着精度丢失——ZeRO 路径上 step 阶段有 FP32 主权重兜底：**averaged_gradients 在进入 Adam 前会通过 flatten(…).to(fp32.dtype) 升精度，参数更新全程在 FP32 上进行，再 copy 写回 BF16。**

具体路径是 _prepare_fp32_grad_for_sub_group → _optimizer_step → _reassign_or_swap_out_partitioned_parameters 三步。

```python
# _prepare_fp32_grad_for_sub_group（节选）
single_grad_partition = self.flatten(self.averaged_gradients[sub_group_id]).to(
    self.fp32_partitioned_groups_flat[sub_group_id].dtype)  # BF16 梯度在此升 FP32
```

**__param_id_to_grad_partition 是反向链路的中枢映射，建立后训练全程不变。**所有梯度操作都通过它访问 grad_partitions_flat_buffer 的对应区段。

### 4.2 __ipg_bucket_flat_buffer：反向期间的梯度中转站

contiguous_gradients 开关决定了反向阶段梯度是否会被提前收敛到统一 flat storage 中。

- contiguous_gradients=True（默认）：训练开始前预分配好 __ipg_bucket_flat_buffer，**反向期间每个参数的碎片化 param.grad** **会先 copy 进这块连续 buffer**，再参与后续归约。
- contiguous_gradients=False：不预分配 __ipg_bucket_flat_buffer，反向期间梯度保持碎片化状态。后续 ReduceScatter 阶段会直接基于离散 grad tensor 构建通信 buffer。

前者的代价是常驻一块 reduce_bucket_size 大小的显存，并增加一次前置 D2D copy；后者的代价则是通信阶段更重的碎片 tensor 处理与临时 buffer 构建开销。

真正发生的 D2D copy 过程如下：

```python
# deepspeed/runtime/zero/stage3.py
# __add_grad_to_ipg_bucket（节选）

def __add_grad_to_ipg_bucket(self, param: Parameter) -> None:
    if not get_accelerator().resolves_data_dependency():
        self.reduce_and_partition_stream.wait_stream(get_accelerator().default_stream())

    if self.contiguous_gradients and \
       self.elements_in_ipg_bucket + param.grad.numel() <= self.reduce_bucket_size:
        with get_accelerator().stream(self.reduce_and_partition_stream):
            new_grad_tensor = self.__ipg_bucket_flat_buffer.narrow(
                0, self.elements_in_ipg_bucket, param.grad.numel()
            ).view_as(param.grad)
            new_grad_tensor.copy_(param.grad, non_blocking=True)   # ★ 一次真实的 D2D 拷贝
            if not get_accelerator().is_synchronized_device():
                param.grad.record_stream(get_accelerator().current_stream())
                # record_stream 的作用：告知 caching allocator，
                # 这块显存在 reduce_and_partition_stream 上的 copy_ 完成前不可回收，
                # 防止 allocator 提前将其重新分配给其他 tensor，引发数据竞争
            param.grad.data = new_grad_tensor

    self.params_in_ipg_bucket.append(param)
```

这里有一次真实的 device-to-device 拷贝：**autograd 产生碎片化的 param.grad，hook 触发后立即将其 copy_ 进 flat buffer 的 narrow 段，再把 param.grad.data 指针重定向过去。**

原来那块碎片显存随着 param.grad.data = new_grad_tensor 失去最后一个引用，由 PyTorch caching allocator 回收复用。碎片显存只活在两个相邻 hook 触发之间的瞬时窗口，对峰值显存影响有限——但”零额外分配”的说法并不成立，有一次真实拷贝发生在这里。

__ipg_bucket_flat_buffer 这块物理内存在反向期间反复复用：每次桶满归约后 params_in_ipg_bucket.clear()，下一桶从 offset 0 开始重新覆盖写入。**因此这块 buffer 的尺寸 reduce_bucket_size 决定的是反向期间的瞬时显存占用。**

### 4.3 桶满归约：默认走 ReduceScatter，不是 AllReduce

ZeRO-3 默认配置下，归约使用的是 ReduceScatter，而非 AllReduce。源码里的分支条件如下：

```python
# deepspeed/runtime/zero/stage3.py
# __reduce_and_partition_ipg_grads（节选）

if self.contiguous_gradients \
   and self.elements_in_ipg_bucket <= self.reduce_bucket_size \
   and not self.reduce_scatter:          # 需要显式关闭 reduce_scatter 才走此分支
    # 分支①：AllReduce + 本地切片（非默认路径）
    grad_bucket = self.__ipg_bucket_flat_buffer.narrow(0, 0, self.elements_in_ipg_bucket)
    grad_partitions = self.__avg_scatter_contiguous_grads(grad_bucket)
else:
    # 分支②：ReduceScatter（默认路径，兜住所有其他情况）
    self.params_in_ipg_bucket.sort(key=lambda p: p.ds_id)
    grad_partitions = self.__avg_scatter_grads(self.params_in_ipg_bucket)
```

进入分支①需要三个条件同时成立，缺一不可：

| 条件 | 作用 |
| --- | --- |
| self.contiguous_gradients | 必须有预分配的连续 buffer，dist.all_reduce 需要整块连续内存 |
| self.elements_in_ipg_bucket <= self.reduce_bucket_size | 桶内元素不超过 buffer 物理容量，防止 narrow 越界 |
| not self.reduce_scatter | 最关键，默认 True，所以默认永不走此分支 |

DeepSpeedZeroConfig 的默认值：

```python
# deepspeed/runtime/zero/config.py
reduce_scatter: bool = True
"""使用 reduce/scatter 替代 allreduce 来平均梯度，减少单卡通信量"""
```

只有 `contiguous_gradients=True` 且 `reduce_scatter=False` 同时成立，才会走 AllReduce 路径，其余三种组合全部走 ReduceScatter。

**分支①的核心：narrow 零拷贝截取**

```python
grad_bucket = self.__ipg_bucket_flat_buffer.narrow(0, 0, self.elements_in_ipg_bucket)
```

`narrow` 在底层不发生任何数据拷贝，也不分配新显存，只是创建一个指向原 buffer 起始地址、长度为 `self.elements_in_ipg_bucket` 的视图。这个 `grad_bucket` 的 shape **严格等于实际梯度元素数**，没有任何 Padding——这是 AllReduce 路径通信量零膨胀的关键。

**分支②的前置排序：分片算法的前置条件**

```python
self.params_in_ipg_bucket.sort(key=lambda p: p.ds_id)
```

在进入通信前需要按 `ds_id` 排序。因为 `reduce_scatter_coalesced` 的重排逻辑是**按参数列表的顺序**依次切分、交错拼接——它并不感知参数本身的语义，只是机械地对 `tensors[0], tensors[1], ...` 做 `chunk_sz` 切片，然后按 `rank0_chunk0, rank0_chunk1, ... , rank1_chunk0, rank1_chunk1, ...` 排列。

如果各卡的参数顺序不一致，同样的 `tensor_idx` 在不同卡上指向的是不同参数，切出来的 `rank0_part0` 根本不是同一个东西的梯度，ReduceScatter 的求和就毫无意义。

**两条路径的内部差异**

分支②调用的 `__avg_scatter_grads` 内部走的是 `reduce_scatter_coalesced`。它的行为因 `contiguous_gradients` 开关而异：

**当 `contiguous_gradients=True` 时**，多个参数梯度已收敛到 `__ipg_bucket_flat_buffer` 中。`reduce_scatter_coalesced` 的输入是 `len(tensors) > 1` 的列表，需要先把这些参数整理成一块连续通信 buffer，再通过单次 NCCL ReduceScatter 完成整桶梯度的归约与分片：

```python
# 步骤1：构建连续通信 buffer（两条子路径）
if len(tensors) == 1 and tensors[0].numel() % world_sz == 0:
    # contiguous_gradients=False 时逐参数通信，或 contiguous=True 时 bucket 内恰好单参数
    # 直接复用原张量展平视图，零拷贝零分配
    tensor_partition_flat_buffer = tensors[0].view(-1)
else:
    # - contiguous_gradients=True：多张量 bucket 聚合，需重排为 rank-major
    # - contiguous_gradients=False：单参数但不能整除，需 padding 补零
    # 统一按 rank × tensor 顺序交错拼接
    tensor_partition_flat_buffer = torch.cat(tensor_partitions_lst_with_padding)

# 步骤2：提前除以 world_size 完成平均（ReduceScatter 只做求和）
tensor_partition_flat_buffer.div_(world_sz)
# 步骤3：单次 ReduceScatter
# NCCL kernel 仍会作为 CUDA stream work 异步提交到 reduce_and_partition_stream 上执行
_torch_reduce_scatter_fn(...)
```

此时 `__ipg_bucket_flat_buffer` 的连续性是 param-major（按参数顺序平铺）：

```text
[param0][param1][param2]...
```

而 ReduceScatter 需要的是 rank-major（按 rank 分片交错排列）：

```text
[rank0_part0][rank0_part1]...[rank1_part0][rank1_part1]...
```

两者不等价。因此即使梯度已收敛到连续 buffer，仍需要在 `reduce_scatter_coalesced` 内部通过 `torch.cat` 重排为 rank-major 布局，并补零对齐到 `world_size` 整除。

**当 `contiguous_gradients=False` 时**，每次 hook 触发只处理一个参数，`reduce_scatter_coalesced` 的输入永远是 `len(tensors) == 1`。此时：

- 若该参数 `numel % world_sz == 0` → 走 fast-path，`view(-1)` 零拷贝，无需重排
- 若不能整除 → 仍需 `torch.cat` + padding 补零

但关键区别在于：**每个参数单独触发一次 NCCL ReduceScatter**。没有 bucket 聚合，kernel launch 开销完全无法摊薄。对于参数多而小的模型，这会成为显著的通信瓶颈。

**分支①：AllReduce + 本地重排切片**

`__ipg_bucket_flat_buffer` 本身已是整块连续 buffer，直接送进 `dist.all_reduce`，**通信前无需任何重排**。但通信完成后，需要按 rank 逐参数跳跃切片，这本质上是一种**本地反向重排**：

```text
chunk_sz = math.ceil(grad.numel() / world_sz)
start_offset = grad_offset_in_buffer + min(rank * chunk_sz, grad.numel())
end_offset = grad_offset_in_buffer + min(rank * chunk_sz + chunk_sz, grad.numel())
partition = buffer_to_reduce[start_offset:end_offset]
```

`grad_offset_in_buffer` 按参数累加，而 `rank * chunk_sz` 在每个参数内部跳跃，导致取出的 partition 是**非连续的 strided tensor**。当参数不能被 `world_sz` 整除时，尾部 rank 的实际有效数据小于 `chunk_sz`，代码必须分配新显存补零：

```python
if param.partition_numel() != partition.numel():
    padded_partition = torch.zeros(param.partition_numel(), device=grad.device, dtype=grad.dtype)
    if partition.numel() > 0:
        padded_partition[:partition.numel()] = partition
    grad_partitions.append(padded_partition)
```

因此，两条路径真正的差异：

| 维度 | ReduceScatter（默认） | AllReduce + 本地切片 |
| --- | --- | --- |
| 通信原语 | ReduceScatter | AllReduce |
| 通信前重排 | 需要 | 不需要 |
| 通信后重排 | 不需要（通信层直接完成分片） | 需要（逐参数跳跃切片 + 补零） |
| 通信聚合度 | contiguous=True 时多参数聚合；contiguous=False 时逐参数通信 | 多参数聚合（整块 buffer） |
| 通信量 | ≈ 2N（但有 Padding 膨胀） | ≈ 4N（零膨胀） |
| 本地切片显存 | 通信层直接完成分片，无额外分配 | 非整除时需补零分配 |

AllReduce 路径省掉了通信前重排，但通信后的本地重排同样昂贵——跳跃切片产生非连续张量，补零时触发额外显存分配。加上通信量翻倍的代价，ZeRO-3 默认选择 ReduceScatter，用更低的网络流量换取整体吞吐。

### 4.4 通信量与计算开销：从理论到代码的真实代价

设 W 张卡、桶内梯度理论总大小为 N = Σ param.numel()。基于 NCCL Ring 算法，单卡理论收发量：

- **ReduceScatter**：≈ **2N**
- **AllReduce** = ReduceScatter + AllGather：≈ **4N**

理论上看，AllReduce 流量是 ReduceScatter 的 2 倍。但深入代码发现，两条路径送入 NCCL 的**实际数据量**因 Padding 机制而有所不同。

分支②进入 `reduce_scatter_coalesced` 时，NCCL 要求输入必须能被 `world_size` 整除。对于不能整除的参数，源码通过 `math.ceil(param.numel() / W)` 计算分片并补零对齐，然后 `torch.cat` 拼接成通信 buffer。

一般地，ReduceScatter 的实际通信量：

$$ N_{rs} = \sum \lceil param.numel() / W \rceil \times W \ge N $$

分支①的 `buffer_to_reduce` 通过 `narrow` 截取，shape 精确等于 N，**无需任何 Padding**。

但 AllReduce 路径的代价在于通信后的本地切片。由于 `chunk_sz` 向上取整，当参数不能被 W 整除时：

```text
if param.partition_numel() != partition.numel():
    padded_partition = torch.zeros(...)  # 补零对齐
```

AllReduce 后的跳跃切片（`grad_offset_in_buffer` 按参数累加，`rank * chunk_sz` 在每个参数内部跳跃）产生的是**非连续的 strided tensor**，补零时更是要 `torch.zeros` 分配新内存再拷贝，本地开销比 ReduceScatter 路径的集中式 `torch.cat` 更高。

代入实际通信量：

$$ \frac{Traffic_{AllReduce}}{Traffic_{ReduceScatter}} = \frac{4N}{2N_{rs}} = 2 \times \frac{N}{N_{rs}} \le 2 $$

因为 $N \le N_{rs}$，**AllReduce 的实际网络流量严格小于 ReduceScatter 的 2 倍**。

## 5. 优化器状态 —— Adam 一/二阶动量

优化器状态的申请发生在 `_init_group` 函数中，形式最为简洁：

```text
# deepspeed/ops/adam/cpu_adam.py（或 torch 原生 Adam）
# _init_group（节选）

for p in group["params"]:
    state = self.state[p]
    # 一阶动量 m_t：梯度的指数移动均值
    state["exp_avg"] = torch.zeros_like(p, memory_format=torch.preserve_format)
    # 二阶动量 v_t：梯度平方的指数移动均值
    state["exp_avg_sq"] = torch.zeros_like(p, memory_format=torch.preserve_format)
    # AMSGrad 变体还会额外分配 max_exp_avg_sq
```

由于 `group["params"]` 在 `step()` 前才按 sub_group 动态填充，`zeros_like(p)` 申请的动量张量与 `fp32_partitioned_groups_flat` 的 sub_group 分片形状一致，大小为全量的 1/N。

## 6. 初始化阶段显存全貌

![](https://pic2.zhimg.com/v2-5440c7b44aeb027ac94ca8667c1f15d3_r.jpg)

五类张量在初始化完成后各就各位，构成训练启动前的静态显存格局。下表按调用顺序列出每一步分配了什么：

| 调用入口 | 分配的张量 | 说明 |
| --- | --- | --- |
| Init.partition() | param.ds_tensor | 每个参数独立分配，此时物理地址分散 |
| _create_fp16_partitions_with_defragmentation | lp_param_buffer（即 fp16_partitioned_groups_flat） | defragment 将碎片化的 ds_tensor 整理为连续大块 |
| _create_fp32_partitions | fp32_partitioned_groups_flat | 从 fp16 clone 并升精度，param_groups 同时置空 |
| _setup_for_real_optimizer | __ipg_bucket_flat_buffer、grad_partitions_flat_buffer | 两块梯度 buffer 一次性 malloc，建立 ds_id → 视图 映射 |
| optimizer._init_group（首次 step 触发） | exp_avg、exp_avg_sq | 与 fp32 分片等大，延迟到首次更新才分配 |

以 8B 模型、8 卡训练（N=8）为例，单卡各张量的静态显存占用：

| 张量 | 精度 | 计算 | 大小 |
| --- | --- | --- | --- |
| fp16_partitioned_groups_flat | BF16 | 8B × 2B / 8 | ≈ 2 GB |
| fp32_partitioned_groups_flat | FP32 | 8B × 4B / 8 | ≈ 4 GB |
| grad_partitions_flat_buffer | BF16 | 8B × 2B / 8 | ≈ 2 GB |
| exp_avg + exp_avg_sq | FP32 | 8B × 4B × 2 / 8 | ≈ 8 GB |
| __ipg_bucket_flat_buffer | BF16 | reduce_bucket_size | ≈ 1 GB |
| 合计静态显存 |  |  | ≈ 17 GB |

`param.ds_tensor` 与 `fp16_partitioned_groups_flat` 共享物理内存（defragment 后 `ds_tensor.data` 指向 `lp_param_buffer` 的切片），不额外占用显存。

其中优化器状态（`exp_avg + exp_avg_sq`）占据了约一半，是 ZeRO-3 显存节省最显著的部分——如果不做切分，8B 模型的优化器状态单卡就需要约 64 GB（FP32 × 2 × 8B）。

## 7. 小结

| 张量 | 分配时机 | 本质 |
| --- | --- | --- |
| param.ds_tensor | Init.partition() | 所有模型的 BF16 分片原始存储 |
| fp16_partitioned_groups_flat | 优化器初始化，defragment | ds_tensor 的连续化重排，训练模型专有 |
| fp32_partitioned_groups_flat | 优化器初始化，clone | FP32 主权重，优化器实际操作对象 |
| grad_partitions_flat_buffer | 优化器初始化，一次性 malloc | 梯度分片的持久存储，梯度累积在此 |
| exp_avg / exp_avg_sq | 首次 step() 触发 | Adam 动量，与 FP32 分片等大 |

ZeRO-3 的显存节省来自一个简单的原则：**每张卡只存 1/N 的一切**——参数、梯度、优化器状态全部按 `dp_world_size` 切分，缺什么临时 AllGather，用完立刻释放。代价是每次 forward/backward 都需要额外的 AllGather 通信，显存与通信的 tradeoff 贯穿始终。
