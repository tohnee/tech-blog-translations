## 1. 产生背景与核心痛点

在大语言模型（LLM）的自回归生成（Decoding）阶段，模型每生成一个新 Token，都需要将对应的 Key 和 Value 向量存入显存缓存（即 **KV Cache**），供后续注意力机制计算使用。

在 PagedAttention 提出之前，传统推理框架采用**连续物理显存分配**方案，导致了严重的显存浪费：

- **预分配浪费（Over-reservation）：** 系统无法预知每个请求最终生成的长度，必须按最大生成长度（如 `max_length = 2048`）提前预留大块连续显存。
- **内部碎片（Internal Fragmentation）：** 预留了 2048 个槽位，但如果模型在生成 50 个 Token 时提前停止（`EOS`），剩余 1998 个槽位被死锁闲置，无法复用。
- **外部碎片（External Fragmentation）：** 请求的生命周期各异，显存频繁申请与释放后会被切成碎片。即使剩余总显存充足，也因缺乏**足够大的连续显存块**而无法接入新请求。

> **传统方案瓶颈：** 实际有效利用的显存往往只有 **20% ~ 40%**，严重压低了并发推理的 Batch Size 和吞吐量。

## 2. 核心架构与设计思想

PagedAttention（由 UC Berkeley 团队在 vLLM 中提出）的核心思想源自操作系统的**虚拟内存分页机制（Virtual Memory Paging）**：

> **“逻辑上保持连续，物理上允许离散，按需分配，零碎片浪费。”**

```c
逻辑视图 (用户序列):  [ Token 0~15 (Block 0) ] ──> [ Token 16~31 (Block 1) ] ──> [ Token 32~47 (Block 2) ]
                                                     │                               │                               │
                                                      ▼                               ▼                               ▼
页表映射 (Block Table):   逻辑 Block 0                  逻辑 Block 1                  逻辑 Block 2
                               │                               │                               │
                               ▼ (映射指针)                    ▼ (映射指针)                    ▼ (映射指针)
物理显存池 (GPU Memory): [ 物理块 PB #7 ]               [ 物理块 PB #2 ]               [ 物理块 PB #15 ]
```

### 核心三大组件

1. **分块机制（Block-based Allocation）：**<br>

- **逻辑块（Logical Block）：** 将序列的 KV Cache 划分为固定大小的单元（如 $B = 16$ 或 $32$ 个 Token）。
- **物理块池（Physical Block Pool）：** GPU 显存预先划分为等长物理块，按需动态分配。

1. **页表映射（Block Table）：**<br>

- 每个请求维护一张私有页表，记录逻辑块索引到实际物理块指针的映射关系。
- 物理块可以分散在显存的任意位置，彻底消除外部碎片。

1. **定制算子（PagedAttention Kernel）：**<br>

- 重写底层 CUDA 算子，在计算 Attention 时根据页表指针直接从非连续的物理块中读取 KV 数据，并在 GPU 共享内存（Shared Memory）中完成矩阵乘法。

## 3. 典型场景全流程剖析：长文档问答（Prefix Caching）

### 场景设定

- **共享文档（《流浪地球》梗概）：** 长度 64 Token，每块 16 Token，共占 **4 个物理块（PB #0 ~ #3）**。
- **多用户请求：** 10 个用户针对该小说提出不同问题。

### 显存与页表流转流程

| 阶段 | 传统模式处理 | PagedAttention 机制 |
| --- | --- | --- |
| 1. 初始前缀计算 (Prefill) | 小说被拷贝/计算 10 遍，各自分配连续大显存。 | 小说仅计算 1 遍，写入共享物理块 PB #0 ~ #3。 |
| 2. 页表绑定 | 10 个请求显存物理隔离。 | 10 个请求的页表前 4 个条目同时指向 PB #0 ~ #3，引用计数为 10。 |
| 3. 各自生成 (Decoding) | 继续在各自预留的连续显存槽位中写入。 | 用户 A 申请空闲块 PB #8 存私有数据；用户 B 申请 PB #15 存私有数据。 |
| 4. Attention 计算 | 顺序读取自身连续显存。 | 算子通过各请求的页表，拼接读取 [PB #0~#3 + 私有块] 完成计算。 |

## 4. 前缀匹配与分支处理原理

### Q1：系统如何识别哪些文本可以作为共享前缀？

- **主流机制（自动动态）：** 结合 **前缀树（Radix Tree / Trie）+ LRU 淘汰策略**（如 SGLang 的 RadixAttention 或 vLLM 的 APC）。<br>

- **业务预热（静态指定）：** 针对固定超长 System Prompt、Agent 工具定义或爆款大促规则，通过调度脚本主动发送 Prefill 预热请求并常驻（Pin）显存。

### Q2：若用户修改了文档内容（如编写改编版），会不会产生串台或错误？

- **绝对不会产生内容混淆**：<br>

1. **精确到 Token 的分叉检测：** 前缀树做严格逐 Token 校验。一旦检测到分叉点（如“行星发动机”被改为“超大宇宙飞船”），立刻停止复用后续原版块，为改编分支开辟全新物理块。
2. **因果注意力（Causal Mask）隔离：** 模型的 Attention 计算仅能访问自己页表内绑定的物理块指针，物理隔离保证了数学上无法读取原版被替换的内容。

### Q3：用户微调改动后，还能提高推理效率吗？

提升效率取决于**改动发生的位置**：

1. 尾部/后半段改动 (如续写、改结局): [ 原版前缀 90% (命中 Cache, 0计算开销) ] ──> [ 改编后 10% (仅计算该部分) ] ── 🚀 效率提升极大 2. 头部/开头改动 (如最前加了一句话): [ 新增首句 (分叉) ] ──> [ 后续内容位置偏移，缓存全部失效 (全量重新计算) ] ── ❌ 无效率提升<br>

## 5. 核心收益与架构对比

| 维度 | 传统连续 KV Cache | PagedAttention 机制 |
| --- | --- | --- |
| 显存分配方式 | 静态、连续大块分配 | 动态、离散固定小块（Page） |
| 显存浪费率 | 60% ~ 80%（预留空间 + 内外部碎片） | < 4%（仅序列末尾块存在未满碎片） |
| 前缀共享（Prefix Sharing） | 困难（需显式内存拷贝） | 原生支持（基于页表引用，写时复制 CoW） |
| 系统吞吐能力 | 显存受限导致 Batch Size 较小 | 显存利用率提升 2~4 倍，高并发吞吐提升明显 |

## 6. 提示词工程（Prompt Engineering）最佳实践

1. **前缀静态化：** 将长文本、固定背景、知识库、System Prompt 尽量置于 Prompt **最前面**。
2. **变量后置化：** 将用户具体提问、动态改动、单次参数放在 Prompt **最后面**。
3. **格式标准化：** 保持多轮对话模板（Chat Template）与特殊标记符严格一致，避免因细微空格或格式变动导致前缀树缓存失效。
