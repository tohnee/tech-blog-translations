## Spark 这台 128 GB 的小机器，装下 124B 的 MoE 不难，难的是单路 decode 的速度。因为 batch=1 时每生成一个 token，都要把这一步用到的权重从 LPDDR5X 里读一遍，273 GB/s 的带宽基本决定了上限，肯定是不如 RTX Pro 6000 或者 5090 这种大带宽显卡的。

NVIDIA 10 月 27 日发了一篇拿 Ling-3.0-flash 做的优化记录：换 MoE kernel、把 LM head 在线量化成 FP8、再接上模型自带的 MTP。合成负载下单路 decode 从 36.09 tok/s 到 102.88 tok/s，换成 GSM8K 这种更接近真实请求的任务，是 37.81 到 53.89 tok/s。

三项单拿出来都不新，比较有意思的是叠在一起之后的细节。LM head 在 MTP 一轮里要算 4 次，FP8 在这里省得比单步更多。而量化后的 LM head 如果没和 draft 正确共享，服务照样能起来，速度却掉到 baseline 以下。这些经验很适合我们当前的个人小主机，比如 DGX Spark、RTX Spark 或者 AI MAX 395，这种显存大，但是带宽小的 AI 主机，比较适合这个方法和经验。

![](https://pic4.zhimg.com/v2-57a47fbc7bd990286164598c286b5da9_r.jpg)

### 1 模型和带宽

### 1.1 模型配置

先简单介绍下模型。Ling-3.0-flash 是 inclusionAI 开源的原生混合推理模型，主打用较少的激活参数支持推理、指令跟随、长上下文和 Agent 任务。官方定位偏速度、计算效率和实际部署，不是单纯往上堆参数。[模型卡](https://huggingface.co/inclusionAI/Ling-3.0-flash)

它有两处设计和这篇优化直接相关：一是把 KDA 线性注意力和 MLA 按 5:1 混合，配合稀疏 MoE，减少长上下文和逐 token 计算的开销；二是训练时就带了 MTP，推理时能用自带的预测层做投机解码。本文用的是它的 FP4 量化版本，不是原始 BF16 权重。至于这些设计在 Spark 上能换来多少速度，还得看下面的 kernel、量化和验证开销。

Ling-3.0-flash 总参数 124B，每个 token 激活 5.1B，config 里的 `max_position_embeddings` 是 262,144。[3](https://huggingface.co/inclusionAI/Ling-3.0-flash-fp4/blob/3bae1cf4011b48475b2cc038fff283af49053ebc/config.json) 本文看的是 `Ling-3.0-flash-fp4` 在单台 DGX Spark 上、batch size 为 1 的 decode，结论不往高并发服务上套。[2](https://github.com/inclusionAI/ling-cookbook/blob/5d93a6c1389e3bad8d451790baf4d352b7421251/guide/local-deploy/ling-3.0-flash/dgx-spark-sglang-ling-3-flash-mxfp4-humming.ipynb)

和推理有关的 shape 简单列一下：

| 项目 | 配置 |
| --- | --- |
| 主干层数 | 42 |
| 注意力 | 每 6 层一组，5 层 KDA 线性注意力 + 1 层 MLA，共 35 + 7 |
| FFN | 前 2 层 dense（intermediate 6,144），后 40 层 MoE |
| 每个 MoE 层 | 512 个 routed experts 选 8 个，另有 1 个 shared expert |
| Hidden size | 2,560 |
| routed expert 的 intermediate size | 768 |
| 词表 | 157,184，embedding 和 LM head 不共享权重 |
| NEXTN 预测层 | 1 |

注意力和 FFN 是两套独立的排布：KDA 和 MLA 按 `layer_group_size=6` 交替，每组最后一层是 MLA，dense 和 MoE 则按 `first_k_dense_replace=2` 切开。[3](https://huggingface.co/inclusionAI/Ling-3.0-flash-fp4/blob/3bae1cf4011b48475b2cc038fff283af49053ebc/config.json) [4](https://github.com/inclusionAI/sglang/blob/079d4046003daf757d8a2daa44a3bb8935174b5e/python/sglang/srt/models/bailing_moe_v3.py)

KDA 是 Kimi 那套线性注意力，状态大小固定。上下文变长时，真正跟着涨的是 7 层 MLA 的 KV cache。

![](https://pic3.zhimg.com/v2-f6c005178673b41990de2cf4e9b50192_r.jpg)

FP4 这个名字也要拆开看。config 里的 `quant_method` 其实是 `fp8`，routed experts 单独走 MXFP4（由 FP8 128×128 block 量化的权重转过来），其他线性层是 FP8 block 量化，激活动态量化。`lm_head`、`word_embeddings`、MLA 的几个投影和 router 的 `mlp.gate` 在 `modules_to_not_convert` 里，保持 BF16。[3](https://huggingface.co/inclusionAI/Ling-3.0-flash-fp4/blob/3bae1cf4011b48475b2cc038fff283af49053ebc/config.json)

MXFP4 把 32 个 E2M1 权重放成一组，共享一个 E8M0 scale，平均是 `(32 × 4 + 8) / 32 = 4.25 bit/weight`。

我按 config 粗算了下，40 层 routed experts 一共 `40 × 512 × 3 × 2560 × 768 ≈ 120.8B` 参数，占总参数的 97%。按 4.25 bit 算约 64.2 GB（59.8 GiB），和 notebook 写的权重约 60GB 在同一个量级。再算上其余几 B 的 FP8/BF16 参数和 NEXTN 那一层（它也是 512 专家的 MoE 层），整个 checkpoint 应该在 65 GiB 上下，notebook 给的是个粗略值。

### 1.2 batch=1 的 decode

DGX Spark 用的是 128 GB LPDDR5X 统一内存，标称带宽 273 GB/s，notebook 里写的可用容量是 121GB 左右。[9](https://docs.nvidia.com/dgx/dgx-spark/hardware.html) [2](https://github.com/inclusionAI/ling-cookbook/blob/5d93a6c1389e3bad8d451790baf4d352b7421251/guide/local-deploy/ling-3.0-flash/dgx-spark-sglang-ling-3-flash-mxfp4-humming.ipynb) 容量够装下模型，单步生成时把权重读出来是另一回事。

以一个线性层为例，输入为 `[M, K]`，权重为 `[N, K]`，乘加工作量约 `2MNK`。batch=1、一次只生成一个 token 时，`M` 很小，同一批权重只服务很少几个输入向量。

假设权重读取占主导，忽略激活和输出流量，这个 GEMM 的算术强度近似为：

$$ I \approx \frac{2MNK}{b_w NK} = \frac{2M}{b_w} $$

`b_w` 是每个权重的字节数。BF16 下 `M=1` 时约 1 FLOP/byte，MXFP4 也就 3.8 FLOP/byte 左右，离 Tensor Core 的算力差得很远，单路 decode 基本就是在等内存。

那每个 token 到底读多少？按 config 粗算，每个 token 激活 8 个 routed expert，40 层加起来是 1.89B 参数，MXFP4 下约 1.00 GB。LM head 是 BF16 的 `157184 × 2560`，有 0.80 GB，相当于前者的八成。

![](https://pic1.zhimg.com/v2-83e494395ac41f7d384cd21d5cfeec80_r.jpg)

NVIDIA 的 profile 结论也是这样：decode 是 memory-bound，最显眼的两块是 MoE 计算和输出层投影。[1](https://developer.nvidia.com/blog/3-ways-to-boost-moe-inference-on-nvidia-dgx-spark/) 前两项优化正好分别对着这两块。

把几个 token 合起来算，一次权重读取能服务更多计算，MTP 的验证就是靠这个省时间。不过 MoE 多了一层路由，几个 token 未必选到同一组专家，第 4 节会说到。

### 2 Humming MoE kernel

第一项优化把 `--moe-runner-backend` 从 `flashinfer_mxfp4` 换成 `humming`。权重格式没变，变的是专家计算用的 kernel。[2](https://github.com/inclusionAI/ling-cookbook/blob/5d93a6c1389e3bad8d451790baf4d352b7421251/guide/local-deploy/ling-3.0-flash/dgx-spark-sglang-ling-3-flash-mxfp4-humming.ipynb)

Humming 是 vllm-project 下面的一个 JIT GEMM 库，专门做量化推理，dense 和 MoE GEMM 都支持，包本身只有 100 多 KB。它按实际的 M/N/K、数据类型和 GPU 架构现场生成 kernel，用 NVRTC 编译，二进制缓存在 `~/.humming/cache`。[10](https://github.com/vllm-project/humming) notebook 里显式设了 `HUMMING_COMPILER=nvrtc`。按 humming 当前 main 的代码，不设的话只要能 import `cuda.bindings` 也会默认走 NVRTC，分支锁的 0.1.12 我没对过。

baseline 那条 `flashinfer_mxfp4` 在 SM120 这一代走的是 FlashInfer CUTLASS，激活用 MXFP8、权重用 MXFP4，原文把它叫做 cookbook 的 W4A8 配置。

Humming 这边，SGLang 上游本来就有 MoE runner，默认用 indexed 方式做 MoE GEMM。MXFP4 专家接 Humming 的那层量化方法，上游原本是给 DeepSeek-V4 的 FP8 checkpoint 写的，Ling 直接复用，这次的分支没动它。[16](https://github.com/inclusionAI/sglang/blob/079d4046003daf757d8a2daa44a3bb8935174b5e/python/sglang/srt/layers/quantization/mxfp4_humming_moe.py) [15](https://github.com/inclusionAI/sglang/blob/079d4046003daf757d8a2daa44a3bb8935174b5e/python/sglang/srt/layers/moe/moe_runner/humming.py)

换 kernel 为什么能快，可以看下 batch=1 时专家的 shape。每个被选中的专家只处理 1 个 token，gate 和 up 合在一起的 w13 是 `[1536, 2560]`，w2 是 `[2560, 768]`。MXFP4 下一个专家约 3.1 MB，一层 8 个加起来 25 MB 左右。

这种 M=1、矩阵又很小的 GEMV，通用 kernel 的 tile 配置很难把带宽吃满，按实际 shape 生成的 kernel 更有机会贴近上限。原文也说 Humming 的 kernel 是针对 `moe_intermediate_size=768` 这类 shape 特化的。[1](https://developer.nvidia.com/blog/3-ways-to-boost-moe-inference-on-nvidia-dgx-spark/) 合成负载下这一项把 TPOT 从 27.71 ms 降到 25.35 ms，吞吐 +9.3%。

编译时间是另一回事。原文说 FlashInfer CUTLASS 这条路径要用 ninja 编 97 个 target，耗时在几十分钟量级，Humming 按单个 kernel 编，几秒就完。[1](https://developer.nvidia.com/blog/3-ways-to-boost-moe-inference-on-nvidia-dgx-spark/) notebook 把 FlashInfer 单独拿出来预编译，独占内存、最多 8 路并行，也要 6–8 分钟。[2](https://github.com/inclusionAI/ling-cookbook/blob/5d93a6c1389e3bad8d451790baf4d352b7421251/guide/local-deploy/ling-3.0-flash/dgx-spark-sglang-ling-3-flash-mxfp4-humming.ipynb)

cold start 和 warm decode 要分开看。上面的 +9.3% 是稳态 TPOT，第一次启动的 JIT、权重加载、CUDA Graph capture 都不在里面，notebook 的启动日志里光加载权重就用了 342 秒。

另外，换成 Humming 并没有把 FlashInfer 拿掉。notebook 依然保留了 FlashInfer CUTLASS 的预编译步骤，attention backend 也是 `flashinfer`。

单独预编译的原因 notebook 写得很直白：在 121GB 的统一内存上，边 JIT 编译边加载 60GB 权重，会把物理内存吃满，进程被杀或者驱动卡死。

### 3 FP8 LM head

### 3.1 输出投影有多大

LM head 把 hidden states 投影成整个词表上的 logits。下面写的是 BF16 权重的逻辑 shape，量化后的实际存储布局可以不同：

```text
hidden_states: [1, 2560]
W (BF16 / logical): [157184, 2560]
logits = hidden_states @ W.T: [1, 157184]
```

每生成一个 token 都要做一次完整词表的投影。这里没有 hot-token 这类裁剪词表的手段，15.7 万行权重每步都得读一遍。

按 shape 算下：

$$ N_w = 157184 \times 2560 = 402391040 $$

这一个 LM head 就有约 4.02 亿个权重。BF16 裸权重是 804,782,080 bytes，约 0.805 GB，即 767.5 MiB。FP8 裸权重减到约 0.402 GB（383.75 MiB），另加少量 scale。

273 GB/s 跑满的话，BF16 读一遍的下限是 `0.805 / 273 ≈ 2.95 ms`，FP8 是 1.47 ms，理论上能省 1.47 ms。baseline 的 TPOT 是 27.71 ms，LM head 这块大概占一成。

实测这一步 TPOT 从 25.35 ms 降到 22.76 ms，少了 2.59 ms，比按带宽算出来的 1.47 ms 还多。原文提到 FP32 开关走的是一条更慢的词表 GEMM 路径，这一步同时把 `--enable-fp32-lm-head` 去掉了，多出来的那部分大概来自这里，原文没给分项计时。结合 3.2 节要说的情况，公开分支上这 2.59 ms 甚至可能全部来自去掉 FP32 开关。

单步来看它省的是一成左右，开了 MTP 之后分量更重，第 4 节会算。

### 3.2 Online FP8 在哪里发生

对应分支只在构造 LM head 时换了量化配置，其他层继续用 checkpoint 自己的配置。核心是这几行：[4](https://github.com/inclusionAI/sglang/blob/079d4046003daf757d8a2daa44a3bb8935174b5e/python/sglang/srt/models/bailing_moe_v3.py)

```python
lm_head_quant_config = Fp8Config(
    is_checkpoint_fp8_serialized=False,
    activation_scheme="dynamic",
)
```

`is_checkpoint_fp8_serialized=False` 表示磁盘里这层还是 BF16。加载完之后，`process_weights_after_loading` 才把它转成 FP8。在支持 CUTLASS FP8 的路径上是按输出通道量化，也就是词表每一行一个 scale，一共 157,184 个，存下来的是转置后的 FP8 权重。[5](https://github.com/inclusionAI/sglang/blob/079d4046003daf757d8a2daa44a3bb8935174b5e/python/sglang/srt/layers/quantization/fp8.py)

这里没设 `weight_block_size`，所以 LM head 是 per-channel，和其他层的 128×128 block 量化不一样。`activation_scheme="dynamic"` 说的是激活，推理时 hidden states 按 token 动态量化成 FP8。

online 指的是加载后转一次，推理时不会每个 token 再从 BF16 现转，要是每步都现转，想省的读取量又回来了。

不过在公开分支上，这个配置可能根本没生效。在 `079d404` 这个提交里，`Fp8Config.get_quant_method` 只给 `LinearBase`、`FusedMoE` 和 `RadixAttention` 返回量化方法，而 `ParallelLMHead` 继承的是 `VocabParallelEmbedding`，不在其中。[5](https://github.com/inclusionAI/sglang/blob/079d4046003daf757d8a2daa44a3bb8935174b5e/python/sglang/srt/layers/quantization/fp8.py)

拿到 `None` 之后，LM head 会退回 `UnquantizedEmbeddingMethod`，也就是还是 BF16。启动日志里那句 `Online FP8 quantization enabled for lm_head.` 只要设了环境变量就会打印，不能说明权重真的转成了 FP8。

第 5 节那个只在 FP8 下才会出现的共享问题，说明 NVIDIA 跑的版本里 LM head 确实是 FP8，公开分支和他们的环境应该有出入。+11.4% 本身当不了证据，同一步还去掉了 FP32 开关。我没有在机器上跑，只当成待确认的问题：加载完之后看下 `type(model.lm_head.quant_method).__name__` 是不是 `Fp8LinearMethod`，`lm_head.weight.dtype` 是不是 `torch.float8_e4m3fn`。

开关是：

```bash
export SGLANG_ENABLE_FP8_LM_HEAD=1
```

同时去掉 baseline 里的 `--enable-fp32-lm-head`，这是 cookbook 给的组合配置。[2](https://github.com/inclusionAI/ling-cookbook/blob/5d93a6c1389e3bad8d451790baf4d352b7421251/guide/local-deploy/ling-3.0-flash/dgx-spark-sglang-ling-3-flash-mxfp4-humming.ipynb)

这个 FP32 开关容易让人误会。它管的是 logits 的输出精度，实现上是 BF16 输入和 BF16 权重做 `torch.mm(..., out_dtype=torch.float32)`，内存里并没有一份 FP32 权重。原文表格里 LM head 那一行的 FP32 指的就是这个。[6](https://github.com/inclusionAI/sglang/blob/079d4046003daf757d8a2daa44a3bb8935174b5e/python/sglang/srt/layers/logits_processor.py)

LM head 挂上 FP8 的 `quant_method` 之后，`LogitsProcessor` 会先走量化方法那条分支，FP32 开关管的普通 matmul 路径本来也走不到了。

### 4 NEXTN 与 MTP

### 4.1 三步 draft，四个验证位置

前两项是在一次 decode 里省时间，MTP 则是让 draft 先猜几个 token，target 一次验证，每轮多推进几个。

Ling 的 checkpoint 自带 1 层 NEXTN 预测层（`num_nextn_predict_layers=1`），所以 `--speculative-draft-model-path` 直接指向同一个模型目录，不用另外训练或下载 draft 模型。一层预测层也可以重复跑，逐步往后猜。[2](https://github.com/inclusionAI/ling-cookbook/blob/5d93a6c1389e3bad8d451790baf4d352b7421251/guide/local-deploy/ling-3.0-flash/dgx-spark-sglang-ling-3-flash-mxfp4-humming.ipynb) [3](https://huggingface.co/inclusionAI/Ling-3.0-flash-fp4/blob/3bae1cf4011b48475b2cc038fff283af49053ebc/config.json)

这次的参数是：

```text
speculative_algorithm = NEXTN
speculative_num_steps = 3
speculative_eagle_topk = 1
speculative_num_draft_tokens = 4
```

`topk=1` 表示只走一条候选链，这时 SGLang 会把 `num_draft_tokens` 自动调成 `num_steps + 1`。[11](https://docs.sglang.io/docs/advanced_features/speculative_decoding) 这 4 个位置是上一轮确认的最后一个 token t0，加上 3 个 draft token，target 一次前向把 4 个位置都算掉。

验证之后，前 k 个 draft 被接受（k ≤ 3），target 在第一个对不上的位置（或者末尾）再给出 1 个 token，一轮推进 k+1 个，最多 4 个。greedy 下可以直观理解成逐个比较 draft 和 target 的 argmax，随机采样时还有接受和修正的过程。

![](https://pic2.zhimg.com/v2-7de52f0b4b7c3cff9e6d8b408540d0ff_r.jpg)

日志里的 accept length 就是每轮平均推进的 token 数，包含 target 补的那 1 个，上限是 4。合成负载是 3.90，基本每轮都全中，GSM8K 是 2.68。所以 3.90 不能理解成“接受了 3.90 个 draft token”，这个配置一轮只有 3 个 draft。

稍微特殊的一点是 LM head。draft 每猜一个 token 也要过一次完整词表的 LM head（和 target 共用同一个，没开 hot-token 裁剪），一轮 3 次 draft 加 1 次验证，LM head 要读 4 遍。

我粗算了下，BF16 下一轮光 LM head 就要读 3.22 GB，跑满带宽也要 11.8 ms，FP8 减到 1.61 GB、5.9 ms。所以 FP8 LM head 在开了 MTP 之后省得更多，这也是第 5 节那个共享问题影响这么大的原因。

### 4.2 MoE 的验证开销

对 dense 权重来说，一次验证处理几个 token，有机会摊薄权重读取。但 MoE 的专家选择跟着 token 走，几个位置选到的专家可能不同。

设第 `i` 个位置选出的 routed expert 集合是 `E_i`，每个集合大小为 8。4 个位置在某一层涉及的不同 routed experts 数量是：

$$ U = |E_1 ∪ E_2 ∪ E_3 ∪ E_4|,\qquad 8 \leq U \leq 32 $$

4 个位置全选同一批专家，`U=8`。完全不重合，`U=32`。这里没把 shared expert 算进去。

![](https://picx.zhimg.com/v2-452b73d6ad84f259c3d66977e325113d_r.jpg)

这个范围说的是专家集合，实际读多少字节还看 kernel 怎么分组、缓存和复用权重。原文把验证的额外开销主要归到专家激活上：普通 decode 一个 token 激活 8 个专家，验证 4 个 token 最多激活 32 个，attention 不是大头。[1](https://developer.nvidia.com/blog/3-ways-to-boost-moe-inference-on-nvidia-dgx-spark/)

原文还给了一个 verification-cost ratio，定义是一次验证相对一次普通 decode 的耗时，实测约 2.26。不过按表里的数反推，开 MTP 后一轮的墙钟约 `9.72 ms × 3.90 ≈ 37.9 ms`，这已经包含 draft 和验证，也只是普通 decode 步 22.76 ms 的 1.67 倍。

两个数对不上，2.26 应该不是在表格那组条件下测的，原文没有说明，这里就不拿它做预测。

判断 MTP 划不划算，可以用这个简化模型：

$$ S \approx \frac{A \cdot T_{\mathrm{decode}}} {T_{\mathrm{draft}} + T_{\mathrm{verify}} + T_{\mathrm{extra}}} $$

`A` 是每轮平均推进的 token 数，分母是 draft、target 验证和额外调度的总耗时。代入合成负载的数，`S ≈ 2.34`，这只是把表里 22.76 ms 到 9.72 ms 换了个写法。这个模型的用处在于拆分母，看 draft、验证和调度各占多少。

对比时 `T_decode` 要用相同后端、相同量化配置下的普通 decode，有重叠执行时以每轮墙钟为准。调参时拉长 draft 能提高 `A`，也会让 draft 和验证都更贵，单看 accept length 往上走，说明不了整体变快。

### 5 FP8 和 MTP 的模块共享

这篇里最有工程价值的细节，是 target 和 draft 之间 LM head 的共享。

先看共享是怎么做的。EAGLE worker 初始化 draft 时会调 `init_lm_head`，NEXTN 走的分支先执行 `set_embed_and_head(embed, head)`，把 draft 自己那个 LM head 的 `weight` 换成 target 的那块张量。[8](https://github.com/inclusionAI/sglang/blob/079d4046003daf757d8a2daa44a3bb8935174b5e/python/sglang/srt/speculative/eagle_worker_v2.py)

BF16 时这样没问题。假设 LM head 真的转成了 FP8（也就是 NVIDIA 环境里的情况），target 的 `lm_head.weight` 在加载后已经是转置过的 FP8 张量，scale 放在 `weight_scale` 里，执行靠 `Fp8LinearMethod`。

draft 的 LM head 是 NEXTN 模型按 checkpoint 的 `Fp8Config` 构造的。3.2 节说过，`Fp8Config` 不给 `ParallelLMHead` 返回量化方法，所以它拿到的是 `UnquantizedEmbeddingMethod`，也没有 `weight_scale`。[7](https://github.com/inclusionAI/sglang/blob/079d4046003daf757d8a2daa44a3bb8935174b5e/python/sglang/srt/models/bailing_moe_nextn.py)

NVIDIA 的描述是 draft 拿到了 FP8 权重，却当成 BF16 来解释，logits 是错的，框架 silently fall back。按公开分支的代码，FP8 权重是转置存的，这条普通 matmul 路径更像会直接报 shape 错误，原文没给出具体复现环境。[1](https://developer.nvidia.com/blog/3-ways-to-boost-moe-inference-on-nvidia-dgx-spark/)

按 NVIDIA 记录的现象，这个错误不会报出来。draft 猜的几乎全被拒，每轮只剩 target 补的那 1 个 token，accept length 正好 1.00，还白白多付了 draft 和验证的开销。notebook 的 FAQ 里记的吞吐掉到 24 tok/s 左右，比未优化的 baseline 还慢。[2](https://github.com/inclusionAI/ling-cookbook/blob/5d93a6c1389e3bad8d451790baf4d352b7421251/guide/local-deploy/ling-3.0-flash/dgx-spark-sglang-ling-3-flash-mxfp4-humming.ipynb)

而且输出内容是对的。验证由 target 负责，draft 猜错只影响速度，所以跑准确率测试发现不了，只能从 accept length 和速度上看出来。

修复是在 NEXTN 模型里加了一个接口，核心几行如下：[7](https://github.com/inclusionAI/sglang/blob/079d4046003daf757d8a2daa44a3bb8935174b5e/python/sglang/srt/models/bailing_moe_nextn.py)

```python
def set_lm_head_from_target(self, target_lm_head):
    if getattr(self.config, "tie_word_embeddings", False):
        return
    self.lm_head = target_lm_head
```

直接共享整个 module，weight、scale 和 `quant_method` 一起复用。这个模型 `tie_word_embeddings=false`，会走到模块赋值。

![](https://pic4.zhimg.com/v2-658d6ae23b6722ae2ec425e7f6a429f3_r.jpg)

调用端的 `init_lm_head` 在 `set_embed_and_head` 之后调用 `maybe_share_target_lm_head`，后者会检查 target head 是否存在、有没有 hot-token 映射、draft 是否提供了这个接口。[8](https://github.com/inclusionAI/sglang/blob/079d4046003daf757d8a2daa44a3bb8935174b5e/python/sglang/srt/speculative/eagle_worker_v2.py)

这段调用逻辑上游本来就有。整个分支相对上游只改了 3 个文件（+26/−2）：一个环境变量、LM head 的 FP8 配置、上面这个接口，外加一处 `enable_dp_lm_head` 的取值修正。[14](https://github.com/inclusionAI/sglang/commit/079d4046003daf757d8a2daa44a3bb8935174b5e)

反过来，accept length 接近 1 也不一定是这个 bug，任务、采样参数和 draft 能力都会影响接受率。只有打开 FP8 之后突然掉到 1，才更有理由先查这里。

### 6 两组测试结果

下面是原文最关键的两组对比，数字来自 NVIDIA 2026 年 10 月 27 日的文章，我自己还没在 Spark 上复测。[1](https://developer.nvidia.com/blog/3-ways-to-boost-moe-inference-on-nvidia-dgx-spark/)

| 合成负载，batch=1 | TPOT（ms） | Decode（tok/s） | 相对 baseline |
| --- | --- | --- | --- |
| Baseline | 27.71 | 36.09 | — |
| 加 Humming | 25.35 | 39.45 | +9.3% |
| 再加 FP8 LM head | 22.76 | 43.94 | +21.7% |
| 再加 NEXTN MTP | 9.72 | 102.88 | +185.1% |

条件是 32K 输入、2K 输出、greedy。表格是逐项叠加的，21.7% 是 Humming 加 FP8 的累计值，FP8 单独在 Humming 基础上是 +11.4%。MTP 再把吞吐拉到上一行的 2.34 倍，最终是 baseline 的 2.85 倍。

| GSM8K，batch=1、1,319 题 | Baseline | 三项全开 |
| --- | --- | --- |
| TPOT（ms） | 26.45 | 18.56 |
| Decode（tok/s） | 37.81 | 53.89 |
| 平均延迟（s） | 15.21 | 11.49 |
| P50 / P95 延迟（s） | 8.36 / 50.20 | 6.11 / 38.60 |
| 平均 TTFT（s） | 0.207 | 0.214 |
| 平均输出长度（token） | 567 | 607 |
| 准确率 | 96.89% | 96.82% |
| MTP accept length | — | 2.68 |
| 请求错误 / 截断 | 0 / 0 | 0 / 0 |

这组是 five-shot，示例取自训练集，测完整的 test set，开了思维链。采样参数为 `temperature=0.6`、`top_p=0.95`、`top_k=29`、`max_tokens=32768`，原文说两次运行的其他配置保持一致。

![](https://pic1.zhimg.com/v2-a18ab1deeef45ffee575ec50b0644a3c_r.jpg)

GSM8K 上 decode 吞吐 +42.5%，TPOT 降 29.8%，平均请求延迟降 24.5%，P50 和 P95 分别降 27% 和 23%。吞吐和延迟的百分比对不上很正常，请求延迟里还有 prefill 和首 token，两次运行的平均输出长度也不一样。

合成负载的 accept length 是 3.90，GSM8K 是 2.68。重复程度、采样方式和输出长度分布都变了，没法把差异全归到某一个因素上。原文自己也提醒合成负载会高估投机解码的收益，185.1% 别当成线上收益。

准确率 96.89% 对 96.82%，换算成题数是 1,278 对 1,277，差一道题（原文表里写的是 −0.08 pt）。原文说没有检测到统计上的变化，这能说明这项测试上没看到明显退化，但推不到任意任务、任意采样参数都无损。notebook 开头写的 verified lossless，指的也是这个 GSM8K 结果。

严格的 speculative sampling 在相应条件下能保持 target 的输出分布，但 LM head 从 BF16 换成 FP8 是另一项数值近似，前者的理论性质替后者做不了精度保证。[12](https://arxiv.org/abs/2211.17192)

### 7.2 组合配置

baseline 和三项全开的差别就这几处，其他参数两边一样：

| 项目 | Baseline | 三项全开 |
| --- | --- | --- |
| MoE backend | flashinfer_mxfp4 | humming，HUMMING_COMPILER=nvrtc |
| LM head | --enable-fp32-lm-head | SGLANG_ENABLE_FP8_LM_HEAD=1，去掉 FP32 开关 |
| MTP | 不开 | NEXTN，3 步，topk=1，4 个 draft token |

下面是从官方启动示例里摘出的关键参数，方便看三项优化分别接在哪里。这是参数摘要，不是完整启动命令：

```text
环境变量
  HUMMING_COMPILER=nvrtc
  HUMMING_CACHE_DIR=~/.humming/cache
  SGLANG_ENABLE_FP8_LM_HEAD=1

后端
  --moe-runner-backend humming
  --fp8-gemm-backend cutlass
  --attention-backend flashinfer
  --disable-shared-experts-fusion

MTP
  --speculative-algorithm NEXTN
  --speculative-draft-model-path <Ling-3.0-flash-fp4 模型目录>
  --speculative-num-steps 3
  --speculative-eagle-topk 1
  --speculative-num-draft-tokens 4

单路和内存配置
  --max-running-requests 1
  --tp-size 1
  --ep-size 1
  --mem-fraction-static 0.68
```

完整 notebook 还设了 context length 262144、chunked prefill 8192、page size 64、关掉 DeepGEMM 的 JIT，并用 `--json-model-override-args` 把 RoPE 设成 YaRN、factor 2.0、`original_max_position_embeddings=131072`。直接从它的启动单元开始改比较稳。[2](https://github.com/inclusionAI/ling-cookbook/blob/5d93a6c1389e3bad8d451790baf4d352b7421251/guide/local-deploy/ling-3.0-flash/dgx-spark-sglang-ling-3-flash-mxfp4-humming.ipynb)

CUDA Graph 只开了 decode，batch size 固定为 1，prefill 的 CUDA Graph 关掉。`mem-fraction-static=0.68` 是这套配置的选择，notebook 说内存压力大时调到 0.75 有 GPU OOM 和驱动卡死的风险，也不代表它是所有上下文长度下的最优值。

### 8 踩坑和验证

这个我还没有测，如果测的话会按 baseline、只加 Humming、再加 FP8、最后加 MTP 的顺序跑，每次用相同的请求集和采样配置，出了回退能知道是哪一步引进来的。需要单独留意的有这几条：

- **先确认三项都生效。** 启动日志里要有 `Using indexed gemm for humming moe`，decode 日志里的 `accept len` 不能贴着 1.00。FP8 LM head 那句日志只说明开关打开了，按 3.2 的方法直接看 `quant_method` 和权重 dtype 更可靠。
- **FP8 和 MTP 一起开，必须用这个分支。** 上游没有 `set_lm_head_from_target`，表现就是第 5 节说的 accept len 1.00、吞吐 24 tok/s 左右，生成结果却完全正常。
- 统一内存要留余量。FlashInfer kernel 先单独预编译再起服务，`--mem-fraction-static` 用 0.68。内存不够时的症状是启动卡住，驱动报 `rmapiLockAcquire` 后不再响应。
- token 数按服务端计数。SSE chunk 不等于 token，开 MTP 后一个 chunk 里可能有多个 token。notebook 的测速脚本用的是 `stream_options={"include_usage": True}` 返回的 `completion_tokens`，自己写脚本也建议这么算。

另外，短问答、长上下文和连续工具调用最好分开测，记下 TTFT、decode 吞吐、端到端延迟和输出长度，免得把负载变化当成优化收益。notebook 自带的流式测速示例，三项全开、temperature=0.6、输出 2,048 token，打出来的是 34.87 tok/s，单条请求的数字和 GSM8K 的平均值差得不少。原文全部是单路 decode，高并发下权重复用、调度和每个专家接到的 token 数都会变，需要重新跑。

### 9 最终结论

这套方案对在 Spark 上单路跑 MoE 很有参考价值，三项里 MTP 提速最多，LM head 这块最容易被忽略。

前两项都是在省每步要读的字节。Humming 让小 shape 的专家 GEMM 更贴近带宽，FP8 把 0.8 GB 的 LM head 砍掉一半，开了 MTP 之后 LM head 一轮要算 4 次，这一项的分量还会更重。MTP 的收益则很看任务，合成负载是 baseline 的 2.85 倍，GSM8K 上三项全开是 1.43 倍。

如果你想自己测试的话，可以先从 notebook 的固定配置开始，先确认 LM head 真的是 FP8、共享路径也生效，再拿自己的请求集逐项对比。GSM8K 的结果可以参考，最后还是要看自己服务里的延迟和输出质量。

这种极致稀疏的模型多出些就好了（128B 级别 + 激活不超 6B 的）～
