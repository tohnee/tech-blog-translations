## 1. 前言

大约是 24 年底的时候，我整理过一份 LLM 推理相关的学习资料。25 年因为工作原因，主要在做 DiT 相关的推理，LLM 这边学得少了一些。今年工作调整，又回来做 LLM，结果发现自己对 LLM 推理的理解还停在 24 年，很多时兴的技术都得重新学。

## 2. Prefill 与 Decode

现在的 LLM 都是基于 Transformer 的 Decoder-only 架构，带因果掩码，第 i 个 token 只看前 i 个，生成只能一个 token 一个 token 地往后吐。

因为已经算过的 token 的 K、V 不会再变，可以存下来复用，这就是 KV Cache（之前写过一篇：[一文读懂 KV Cache：它到底省了哪部分计算](https://mp.weixin.qq.com/s?__biz=Mzg4NDU1Mzc5Nw==&mid=2247484855&idx=1&sn=c221a10ccf8f7b6944635351cc926707&scene=21#wechat_redirect)）。有了 KV Cache，推理自然分成了两个阶段：

- Prefill：把整段 prompt 一次算完，顺便写入 KV Cache。权重读一次能被几百上千个 token 复用，算术强度高，是计算受限（Compute-bound）。
- Decode：每步只出 1 个 token，但整份权重和全部 KV 都要从显存里读一遍，算单元大部分时间在等数据，是访存受限（Memory-bound）。

怎么判断一个阶段是算力瓶颈还是访存瓶颈，可以看之前那篇[Roofline 模型：如何判定算子是计算瓶颈还是访存瓶颈](https://mp.weixin.qq.com/s?__biz=Mzg4NDU1Mzc5Nw==&mid=2247485038&idx=1&sn=76c8d0bc7f101026262f42ea2118c29c&scene=21#wechat_redirect)。这里只要记住一句话就够了：两个阶段的瓶颈不一样，所以后面的优化手段也分成了好几路。

## 3. 我们要优化什么？

优化之前得先想清楚，服务是给谁用的。不同场景，在意的东西很不一样：

- 聊天界面、流式输出：用户盯着屏幕等。首个字要尽快出来，之后吐字速度要比人读得快，同时在大规模部署下成本还得压得住。
- 离线批量推理，比如跑评测、造数据：没人在屏幕前等，单条请求慢一点无所谓，只关心整体跑完花多少钱。

这两类需求对应到指标上，就是推理里最常说的四个：

- TTFT（Time To First Token）：从请求到达到吐出第一个 token 的时间，主要由排队和 prefill 决定。
- TPOT（Time Per Output Token）：相邻两个输出 token 的间隔，主要由 decode 决定。vLLM 的指标里现在叫 ITL（inter-token latency）。
- E2E 时延：一个请求从进到出的总时间，约等于 TTFT + TPOT × (输出长度 − 1)。
- 吞吐（Throughput）：整机每秒产出多少 token，直接对应成本。

聊天场景主要看前两个，离线场景主要看吞吐。麻烦的是这几个指标经常互相打架：batch 开大了吞吐上去了，TTFT 和 TPOT 往往跟着变差。所以在线服务里还常用一个综合指标 Goodput，只统计 TTFT 和 TPOT 都满足 SLO 的那部分吞吐。吞吐翻了倍但 P99 TTFT 从 1 秒涨到 30 秒，对用户来说是净亏，看吞吐看不出来，看 Goodput 一眼就能看出来。

到这里，「模型结构 → 两个阶段 → 指标」这条线就铺好了。接下来的问题是：指标上不去，到底卡在哪？又该用哪个方法去解？这就是那张图要回答的。

### 4.1. 从左往右读

整张图分五列，从左往右是一条因果链：

模型结构决定推理怎么跑，推理方式决定用什么指标衡量，指标卡在某个瓶颈上，瓶颈逼出了各种优化方法。

对应到五列就是：根源（Transformer、Decoder-only、KV Cache）→ 两个阶段（Prefill、Decode）→ 评估指标（TTFT、TPOT、E2E、吞吐、Goodput）→ 卡在哪里（8 个瓶颈）→ 优化方法（8 个方向、28 个具体方法）。

最开始我想的其实是一棵「指标 → 优化方法」的树，指标下面直接挂方法。画了一下发现画不成树：一个方法往往同时影响好几个指标，比如 Continuous Batching 既提吞吐又改善 TTFT，挂在哪个指标下面都不对，连线会乱成一团。

后来中间加了一列「瓶颈」，就顺了。指标是结果，瓶颈是原因，方法针对的其实是原因。TPOT 高可能是访存带宽不够，也可能是 CPU 发 kernel 太慢，还可能是卡间通信拖的，这三种情况的解法完全不一样。先定位卡在哪，再去找方法，这也是平时做性能分析的顺序。

### **4.2.**点一个节点，看它从哪来、往哪去

点左边四列的任意一个节点，图上会把跟它相关的链路高亮出来，其余的变淡。高亮规则是上游全部亮、下游只亮一列。比如点 TPOT，能看到它从 Decode、KV Cache 一路来，往右连到访存带宽、调度互相干扰、CPU 与 launch 开销、单卡装不下、卡间通信这五个瓶颈。只往下走一列，是因为点最左边的 Transformer 时，如果下游全亮，整张图就全亮了，等于没高亮。

![](https://picx.zhimg.com/v2-223adf2a6a8940ece83cf6dd7c03ea7d_r.jpg)
*图 2：点中 TPOT，高亮它的上游和下一列瓶颈*

右侧面板会显示这个节点的解释、「来路」（上游经过了哪些节点）、对应的优化方向，以及学习资料。对应的优化方向可以直接点，跳过去接着看。

### **4.3.**点一个方法，看它改善了什么、牺牲了什么

这是我觉得这张图最有用的地方。点右边任意一个具体方法，指标列上会打标记：绿色 ✓ 表示改善，红色 ! 表示可能变差。面板里会写它解决的是哪个瓶颈，以及代价是什么。

举几个例子：

- Chunked Prefill：TPOT 和 Goodput 打 ✓，TTFT 打 !。长 prefill 切成小块和 decode 拼着跑，decode 不再被一个大 prefill 卡住，吐字更平稳；代价是单个请求的首 token 会稍微晚一点。
- 投机解码：TPOT 打 ✓，吞吐打 !。它本质是用一次前向验证多个 token，把访存受限的 decode 变得「更像计算受限」。所以只在 batch 小、带宽没吃满的时候有用，batch 一大收益就没了，甚至会变负。
- PD 分离：TTFT、TPOT、Goodput 都打 ✓，但吞吐没有标。面板里的代价写的是「不提升吞吐」，这是 vLLM 文档的原话。它是一个控尾延迟的工具，不是提吞吐的工具，这一点很多人第一次接触时会搞错。

![](https://pic3.zhimg.com/v2-9f2699b10c94882250d12a83b99b10b6_r.jpg)
*图 3：点中一个具体方法，指标上出现 ✓ 和 !*

每个方法都写了「代价」这一栏，是我特意加的。看论文的时候大家都在讲收益，代价往往要读到实验部分甚至别人的复现才知道。比如 KV FP8，vLLM 实测每 token 的 KV 只降到 BF16 的 54%，因为多出来的 scales 也要存；未校准时 KV scale 默认是 1.0，这是生产里最常见的精度坑。这类信息放在一起看，比单独记一个「FP8 省一半显存」要靠谱得多。

### **4.4.**八个瓶颈

瓶颈这一列是整张图的枢纽，简单过一下：

- 算力：长 prompt 的 prefill、超大 batch 会撞上。
- 访存带宽：decode 每步都要把权重和 KV 读一遍，最常见的瓶颈。
- 显存容量：KV 随 batch × 上下文长度线性增长，放不下就只能减 batch。
- 碎片与重复计算：显存不是不够，是没用好，预分配留空洞、相同前缀各算各的。
- 调度互相干扰：长短请求混跑，prefill 插进 decode 批里把一整步都拖慢。
- CPU 与 launch 开销：小 batch decode 时 kernel 只跑几微秒，CPU 准备输入、发 kernel 反而成了大头。
- 单卡装不下：权重或 KV 太大，只能切到多卡。
- 卡间通信：切到多卡之后的 all-reduce、all-to-all、KV 传输。

CPU 开销这一项是我回来补课时才认真对待的。24 年那会儿脑子里基本只有「算力」和「带宽」两种瓶颈，但现在 decode 越来越快，GPU 在 kernel 之间空等的时间占比越来越显眼，CUDA Graph、SGLang 的重叠调度都是冲着它去的。之前写过一篇[深度学习系统性能优化，先搞清楚瓶颈在哪？](https://mp.weixin.qq.com/s?__biz=Mzg4NDU1Mzc5Nw==&mid=2247484983&idx=1&sn=cd77d552c73bfb453875b036198381ba&scene=21#wechat_redirect)讲过计算、带宽、开销三分法，这张图算是把它落到了 LLM 推理上。

### **4.5.**八个优化方向

右边一列按方向分组，每组下面是具体方法。一句话概括：

- 改注意力结构：MQA、GQA、MLA、跨层共享 KV、稀疏注意力。从源头少存 KV，要在训练前定好。
- 压缩已有的 KV：KV 量化、驱逐/选择、低秩。模型不动，推理时存得更省。
- 管好 KV 显存：PagedAttention、Prefix Cache、KV 分层卸载。不减总量，消灭浪费。
- 调度：Continuous Batching、Chunked Prefill、PD 分离、重叠调度。决定谁和谁一起跑。
- 算子：FlashAttention、Flash-Decoding、FlashInfer、CUDA Graph。少走 HBM、少 launch。
- 减少 decode 步数：投机解码、Medusa/EAGLE、MTP。一次出多个 token。
- 并行：TP/PP、EP、CP（PCP/DCP）、通信计算重叠。切到多张卡。
- 权重与激活量化：W4A16、W8A8/FP8。让每个字节更值钱。

点方向的标题，会看到这个方向一共在解决哪几个瓶颈；点方向里的具体方法，才会出现指标上的 ✓ 和 !。

### **4.6.**学习资料都挂在节点上

每个节点、每个方法下面都挂了学习资料，大部分是原始论文，也有一些我觉得讲得特别清楚的博客和设计文档，比如 vLLM 的各个 design doc、Databricks 那篇推理性能工程、kipply 的推理算术。有些条目我还加了一行备注，说明这篇适合拿来看什么，比如 「The Sparse Frontier」 标的是「反面证据」，vAttention 标的是「反面立场」。只读支持某项技术的论文容易被带偏，放一两篇唱反调的进来，判断会更稳一些。

## **5**写在最后
