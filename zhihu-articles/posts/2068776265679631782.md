## 引言

过去，Prompt Engineering 几乎是每个 LLM 应用开发者的必修课：如何写出更好的 System Prompt、如何用 Few-shot 示例引导模型、如何用"Let’s think step by step"激发推理能力……但当你真正开始构建一个需要跑几十甚至上百轮工具调用的 Agent 系统时，会很快发现一个残酷的事实—— **再精妙的提示词，也救不了一个被垃圾信息淹没的上下文窗口** 。

这正是行业在 2025 年集中讨论"上下文工程"（Context Engineering）的背景。Cognition AI 直言，"上下文工程"已经是构建 AI Agent 工程师的 **第一职责** ；Anthropic 在 2025 年 9 月发表的《Effective Context Engineering for AI Agents》中，将其正式定义为一套独立于 Prompt Engineering 的系统性策略；LangChain 也在同期给出了自己的方法论框架。三家公司的表述略有差异，但共识是清晰的： **当模型从"单次问答"走向"多轮自主运行的 Agent"，管理的对象已经从"一句话怎么写"升级为"一整套动态信息供给系统怎么设计"** 。

本文将系统梳理上下文工程的定义、与 Prompt Engineering 的本质区别、核心技术方法（RAG、上下文管理优化、工具调用），并给出一个可运行的 RAG 实践案例，最后讨论这一领域当前面临的挑战与未来方向。

## 一、什么是上下文工程？

### 1.1 明确定义

Anthropic 给出的定义相当精确： **Context Engineering 指的是在 LLM 推理过程中，用于筹划和维护"最优 Token 集合"的一整套策略，这里的"最优 Token"不仅包括提示词本身，还包括推理时落入上下文窗口的所有其他信息** ——系统指令、工具定义、外部检索到的数据、历史消息记录等。

用更工程化的语言表述：LLM 的上下文窗口就像操作系统里的 RAM——容量有限、按需分配、需要精心管理；而模型本身则像 CPU。Andrej Karpathy 把这件事描述得很传神：“上下文工程是一门精妙的艺术与科学，核心是在下一步推理时，往上下文窗口里填入恰到好处的信息”。

### 1.2 与 Prompt Engineering 的本质区别

Prompt Engineering 和 Context Engineering 不是替代关系，而是 **范围包含与阶段演进** 的关系：

| 维度 | Prompt Engineering | Context Engineering |
| --- | --- | --- |
| 关注对象 | 提示词本身的措辞、结构、示例设计 | 整个上下文窗口中所有 Token 的来源、组织与生命周期 |
| 典型场景 | 单轮问答、一次性分类/生成任务 | 多轮 Agent 循环、长时间跨度任务 |
| 工作性质 | 一次性的、静态的写作任务 | 迭代的、动态的系统构建过程 |
| 涉及组件 | System/User Prompt、Few-shot 示例 | Prompt + 工具定义 + 检索结果 + 历史消息 + 记忆系统 |

Anthropic 的表述很直接：Prompt Engineering 是 Context Engineering 的一个子集和历史前身。早期做 LLM 应用，多数场景是一次性分类或文本生成，写好 System Prompt 就基本解决问题。但当 Agent 需要跨越多轮推理、长时间运行，我们要管理的就是"系统指令、工具、MCP、外部数据、消息历史"这一整套不断演化的状态。 **Prompt Engineering 关心的是"这句话怎么写"，Context Engineering 关心的是"这个系统该往模型脑子里塞什么、什么时候塞、塞多少"。**

### 1.3 为什么这件事现在变得如此重要：Context Rot

这里有一个容易被忽视但至关重要的机制性原因。Transformer 架构的自注意力机制让每个 Token 都要与上下文中所有其他 Token 计算两两关系，对于

这意味着上下文必须被当作 **一种边际收益递减的稀缺资源** 来对待，而不是"越大越好"。这也是为什么单纯扩大上下文窗口长度，并不能替代精细的上下文工程——正如人类的工作记忆是有限的，往里面塞得越多，反而越容易丢失关键细节。

## 二、核心技术与方法

### 2.1 检索增强生成（RAG）：上下文工程的基石

RAG 是上下文工程中最基础、最成熟的技术范式，其核心流程包含三个环节：

1. **Embedding（向量化）** ：把文档切分为语义片段（Chunk），通过 Embedding 模型将每个片段转换为高维向量，这个向量捕捉了文本的语义特征
2. **Vector Store（向量存储）** ：将所有片段的向量存入向量数据库（如 Pinecone、Chroma、Milvus），建立可高效检索的索引结构
3. **Retrieval（检索）** ：当用户提出问题时，把问题同样转换为向量，通过近似最近邻（ANN）算法在向量库中找出语义最相似的若干片段，将这些片段作为上下文注入 Prompt，再交给 LLM 生成答案

RAG 解决的核心问题是 **LLM 知识的时效性和幻觉问题** ：模型的参数化知识在训练完成那一刻就已经"冻结"，无法获知训练截止日期之后的信息，也无法访问企业私有数据。RAG 相当于给模型配了一个"外接大脑"，让模型在生成前先"翻书"，用检索到的真实文档内容作为生成依据，而不是完全依赖参数中可能过时或模糊的记忆。

不过需要指出的是，简单的 Embedding 检索在真实生产场景中远非万能。Windsurf 团队在讨论代码 Agent 的检索实践时提到过一个关键洞察： **“索引代码"不等于"上下文检索”** ——随着代码库规模增长，单纯的 Embedding 相似度检索会变得不可靠，实践中往往需要结合 AST 语法树解析、按语义边界分块、grep/文件搜索、知识图谱检索，以及检索后的**重排序（Re-ranking）**步骤，才能把真正相关的内容排到最前面。

### 2.2 上下文管理与优化：Write / Select / Compress / Isolate

LangChain 在其 Context Engineering for Agents 一文中，把 Agent 场景下的上下文管理策略归纳为四个核心动作—— **写入（Write）、选取（Select）、压缩（Compress）、隔离（Isolate）** ，这个框架非常适合用来理解长上下文场景下的各类优化手段。

### （1）Write：把上下文写到窗口之外

最典型的实践是 **Scratchpad（草稿本）和长期记忆（Memory）** 。Agent 在执行任务过程中，把关键的中间状态（如任务计划、已确认的决策）写入外部存储（文件、状态对象），而不是全部塞在对话历史里。Anthropic 的多 Agent 研究系统就是这样做的：LeadResearcher 会先把执行计划写入 Memory 持久化，因为一旦上下文超过 20 万 Token 就会被截断，提前保存计划能保证关键信息不丢失。

### （2）Select：把外部信息按需拉回窗口内

这对应的正是 RAG 的检索环节，但适用范围更广——不仅是知识检索，还包括 **工具选择** 。当 Agent 可用工具数量庞大时，把所有工具描述一次性塞进 Prompt 反而会造成模型"选择困难"，导致工具调用混乱。研究表明，对工具描述做检索增强（只召回与当前任务最相关的工具子集），能将工具选择准确率提升数倍。

### （3）Compress：只保留任务必需的 Token

这是应对长时程任务（Long-Horizon Tasks）最核心的手段，主要包括：

- **上下文摘要（Summarization）** ：当对话逼近上下文窗口上限时，用 LLM 对历史消息做高保真度摘要，重新开启一个更精简的上下文窗口继续任务。Claude Code 的"Auto-Compact"机制正是当上下文使用超过 95% 时自动触发：模型会保留架构决策、未解决的 Bug、实现细节，同时丢弃冗余的工具调用原始结果。
- **上下文裁剪（Trimming）** ：相比摘要需要额外调用 LLM，裁剪更多依赖硬编码规则，比如直接砍掉早于某个时间点的历史消息，或使用专门训练的裁剪模型（如 Provence）针对问答场景做定向修剪。

### （4）Isolate：把上下文隔离在子系统中

典型实践是 **多 Agent 架构** ：让每个子 Agent 拥有独立、干净的上下文窗口去处理具体子任务，只把浓缩后的结果（往往是原始探索过程的几十分之一 Token 量）返回给主 Agent 做汇总。Anthropic 的研究表明，这种关注点分离能让复杂研究任务的表现明显优于单 Agent 方案，代价是 Token 消耗可能高达单 Agent 聊天场景的 15 倍 [ref:11]。此外，使用代码执行沙箱（Sandbox）也是一种隔离手段——Agent 生成的代码在沙箱中运行，庞大的中间结果（图片、音频、大规模数据）留在沙箱环境中，只有真正需要的部分才被选择性传回 LLM。

下表总结了长时程任务中三类核心技术的适用场景对比：

| 技术 | 适用场景 | 优点 | 局限性 |
| --- | --- | --- | --- |
| 压缩（Compaction） | 需要保持连续对话流的长交互任务 | 保持任务连贯性，用户无感知 | 压缩策略需精细调优，激进压缩可能丢失后续才显现价值的细节 |
| 结构化笔记（Note-taking） | 有清晰里程碑的迭代式开发任务 | 开销极低，持久化成本小 | 依赖 Agent 自身养成良好记笔记习惯，早期需引导 |
| 多 Agent 架构 | 需要并行探索的复杂研究/分析任务 | 上下文隔离彻底，并行效率高 | Token 成本显著增加，子 Agent 间协调复杂度高 |

### 2.3 工具与函数调用（Tools & Function Calling）

工具调用是让 LLM 从"纯文本生成器"转变为"能感知和操作真实世界的智能体"的关键机制。其基本原理是：开发者预先定义一组工具（函数签名+描述+参数 Schema），模型在推理时根据当前任务判断是否需要调用某个工具，并生成结构化的调用参数（通常是 JSON），由外部程序实际执行该函数，再把执行结果（Observation）作为新的上下文回传给模型，供其继续推理。

在工具设计上，Anthropic 给出了一个重要的工程原则： **工具集合应当追求"最小可行集"，而不是功能大而全** 。一个常见的失败模式是工具集过于臃肿、功能相互重叠，导致模型面临模糊的决策点——如果一个人类工程师都无法明确判断某个场景该用哪个工具，就不能指望模型做得更好 [ref:11]。这也是为什么 Model Context Protocol（MCP）这类标准化协议开始受到重视：它提供了一种统一的方式让开发者以简单的客户端实现，对接不断增长的第三方工具生态，避免每个工具都要重新设计一套调用契约。

值得一提的是当前一种更前沿的思路——“即时上下文”（Just-in-Time Context）。与传统的"预先检索所有可能相关的数据"不同，这种方式让 Agent 只维护轻量级的引用（文件路径、存储的查询语句、网页链接），在运行时按需通过工具动态加载数据。Claude Code 处理大型数据库分析任务时就采用这种模式：模型编写有针对性的查询、存储中间结果，并借助 Bash 命令（如 `head` 、 `tail` ）分析海量数据，而从不需要把完整数据对象载入上下文——这种设计理念高度模仿了人类认知：我们从不会把整个知识库都记在脑子里，而是依靠文件系统、收件箱、书签等外部索引机制按需检索。

## 三、挑战与未来展望

### 3.1 当前面临的挑战

**评估困难** ：与 Prompt Engineering 相比，上下文工程涉及的组件更多（检索质量、压缩保真度、工具选择准确率），任何一个环节的退化都可能导致端到端效果下降，但很难定位具体是哪个环节出了问题。LangChain 团队强调，在动手做上下文工程之前，首要前提是先建立起 **可观测性** （Observability）——能够追踪 Agent 每一步的 Token 使用情况，并有一套简单可靠的评估手段来判断某项上下文优化究竟是"帮助"了效果还是"损害"了效果 [ref:1]。

**系统复杂性高** ：一旦引入多 Agent 隔离、结构化记忆、即时检索等多种机制组合，系统的可维护性会显著下降。ChatGPT 曾出现过一个广为讨论的案例：系统自动从用户的长期记忆中取出了地理位置信息，并意外地将其注入到一次图片生成请求中，让用户产生"这个上下文窗口好像已经不完全属于我自己"的困惑感 [ref:1]。这提示我们，记忆的自动选择机制如果缺乏透明度和用户可控性，反而会制造新的信任问题。

**压缩与保真度的权衡** ：无论是摘要还是裁剪，本质都是有损处理。过于激进的压缩可能丢弃了当时看起来无关、但后续任务中才显现关键价值的细节，而这种损失往往要等到很久之后才会暴露出来，排查成本很高。

### 3.2 未来发展方向

**多模态上下文管理** ：随着模型原生支持图像、音频、视频输入，上下文工程需要处理的不再是单一的文本 Token 序列，如何在多模态混合上下文中做统一的检索、压缩与隔离，将是新的技术难点。

**更智能的自主 Agent 系统** ：Anthropic 观察到一个趋势——随着底层模型能力提升，工程师需要做的"预先规定式"上下文工程会逐渐减少，转而让模型自主决定何时检索、何时压缩、何时调用哪个工具，人类的角色从"精细雕刻每一步上下文"逐渐转向"设计良好的工具和环境边界，让智能模型自己在其中智能地行动"。

**标准化协议的普及** ：以 Model Context Protocol（MCP）为代表的标准化上下文/工具接入协议，有望降低不同 Agent 框架、不同工具生态之间的集成成本，成为上下文工程走向工程化、规模化的重要基础设施。

## 四、结论

上下文工程的核心价值，在于把 LLM 应用开发从"依赖直觉的提示词调优"，提升为 **一套有原理支撑、可迭代优化的系统工程实践** 。它承认了一个朴素但常被忽视的事实：无论模型多么强大，其推理质量都受限于当下这个上下文窗口里究竟装了什么——装得太多会稀释注意力、引发 Context Rot；装得太少又会导致信息缺失、推理跑偏。真正的技术难度不在于"写出一句聪明的提示词"，而在于设计一整套 **动态判断该写入什么、该检索什么、该压缩什么、该隔离什么** 的系统。

对于正在构建 Agent 系统的开发者而言，这意味着一次角色转变：从专注打磨"魔法咒语"的 **提示词工匠** ，成长为统筹检索系统、记忆机制、工具契约与压缩策略的 **上下文架构师** 。这个转变过程注定伴随更高的系统复杂度，但也正是这种复杂度的驾驭能力，将成为下一阶段 AI 应用工程师的核心竞争力。
