## 一、什么是RAG

RAG（Retrieval-Augmented Generation，检索增强生成）：不改变大模型本身， **在 LLM 生成回答之前，先从外部知识库检索相关信息，把检索结果塞进 Prompt，让 LLM 基于事实生成答案。**

**核心价值：解决LLM三大痛点**

1. **知识时效性** ：可以接入不断更新的外部知识，而不需要重新训练模型。
2. **私有知识** ：可以让 LLM 使用企业内部文档、业务知识等模型训练阶段没有见过的数据。
3. **降低幻觉** ：通过给模型提供相关的外部上下文，让回答有事实依据，并可以进一步要求模型基于检索结果回答。

在 Agent 系统中，RAG通常可以作为 Agent 的一个知识获取能力： **Agent 根据用户任务决定什么时候需要检索，再通过 RAG 获取外部知识，结合自身推理能力完成任务。**

## 二、 RAG 完整工业级链路

标准落地七步流水线： **原始文档解析 → 分块Chunking → 向量化Embedding → 向量库入库 → 混合检索召回 → Rerank精排 → LLM生成应答** 
 每一步核心作用+工程决策（面试官重点考察点）：

1. **文档解析** ：首先对 PDF、Word、Markdown、网页等原始数据进行解析，提取正文、表格、图片等内容；对于扫描版 PDF 等无法直接提取文本的内容，可以通过 OCR 进行文字识别，同时清洗页眉、页脚、乱码等无效内容。

**核心目标：将非结构化原始数据转换成后续可以检索和处理的有效知识。**

1. **Chunk分块** ：根据文档结构和语义完整性，将长文档切分成适合检索和模型上下文的语义片段。
2. **Embedding向量化** ：使用 Embedding 模型将 Chunk 文本映射到高维向量空间，
3. **入库存储** ：将 Chunk 的 **向量、Chunk ID 以及必要的 Metadata** 建立关联并进行存储。
4. **检索召回** ：通过向量+关键词多路召回，粗筛高相关片段
5. **Rerank重排** ：对粗筛结果精准打分，过滤噪声、提升相关性
6. **LLM生成** ：基于检索真实内容，约束生成、输出可溯源答案

## 三、核心模块深度面试解析（高频考点）

### 1、Chunk分块机制（RAG效果核心瓶颈）

在 RAG（检索增强生成）中， **Chunking** 是指将一篇较长的文档，按照 **一定的长度、结构和语义边界** 切分成多个较小的文本片段（Chunk），再分别进行 Embedding 和检索。

（1） 为什么要分块？

原因有三：

- Embedding 模型通常有最大 Token 输入长度，过长的文档无法直接完整进行向量化，因此需要先切分。
- 控制检索粒度，避免语义信息被稀释
- 控制 LLM 上下文长度和 Token 成本

面试回答：为什么 Chunk？——模型有长度限制只是第一层原因，更核心的是控制检索粒度：既不能太大导致语义稀释和噪声增加，也不能太小导致上下文丢失。

（2） Overlap（重叠）的作用

**Overlap：** 是指相邻两个 Chunk 之间 **重复包含的文本部分** 。

相邻分块保留部分重复文本， **用少量存储冗余，解决语义截断问题** 。避免完整语义被拆分到两个块中，导致检索漏召。 
 工业界通用标准： **Overlap = 分块大小的10%~20%** ，过大会冗余重复，过小会语义断裂。

（3） **分块策略选型（面试必问）**

1、 **固定长度分块** ：速度快、均匀，适合快速原型，缺点是容易切断语义

2、 **递归字符分块** （工业基线）：一种分层、递归式的文本切分策略。

字符：["\n\n", "\n", ". ", "! ", "? ", ";", ",", " "]

优先用 **大粒度分隔符** （段落、换行）切；如果切出来的片段依然超过设定 `chunk_size` ，就递归降级，使用更小粒度分隔符（句子、逗号、空格）继续切分；直到所有 chunk 都小于最大长度。

目标： **尽量在语义断点处切割，而不是硬在一句话中间截断；同时保证 chunk 不超过 token 上限。**

3、 **结构化分块** ：基于文档本身自带的层级标签 / 结构元信息做切分，而不是单纯靠标点、字符长度。

针对带目录、标题层级的文档（Markdown、带书签 PDF、Word、HTML），利用文档原生的层级标记（标题、章节、小标题、列表、表格）进行分块， **保留文档的层级父子关系** 。

4、 **语义分块** ：通过向量相似度判断语义边界，精度最高，成本高、速度慢，适合高精度场景

（5）分块过大/过小的问题

- **块过大** ：向量语义模糊、检索匹配度低，冗余信息多，容易引发LLM幻觉、token成本高
- **块过小** ：上下文缺失、语义不完整，召回内容碎片化，回答逻辑断裂

### 不同文档类型分别怎么处理？

| 文档类型 | 处理策略 |
| --- | --- |
| Markdown | 按标题层级切分，保留标题层级信息 |
| PDF | 先解析表格和图片，再按段落切分 |
| 代码 | 按函数/类切分，保留完整代码块 |
| FAQ | 每个问答对作为一个 chunk，不要拆开 |

### 2. 长文档/书籍高阶处理方案（加分项）

长文档，不建议简单采用固定长度“一刀切”，而是可以结合 **文档结构、分层索引、父子 Chunk 和 Metadata** 进行处理。

### 第一步：结构化解析

首先解析文档的目录和层级结构

```text
书籍
├── 第一章
│   ├── 1.1 小节
│   ├── 1.2 小节
│   └── 1.3 小节
├── 第二章
│   ├── 2.1 小节
│   └── 2.2 小节

同时提取页码、标题、段落、表格等信息。
```

**核心目的** ：保留原始文档的层级关系，为后续检索和溯源提供基础。

### 第二步： **三级分层索引：** 章节摘要（宏观问题）、小节内容（中观）、段落细块（微观细节）

（1）宏观层：章节摘要

对章节内容生成摘要，例如：

- 核心观点
- 主要概念
- 关键结论

然后对摘要进行 Embedding，用于回答宏观问题。

（2）中观层：章节 / 小节

以完整小节作为语义单元，必要时继续向下切分。

适合回答：

> 原理、流程、机制、规则等问题。

（3）微观层：细粒度 Chunk

将较长的小节进一步切分成较小的 Chunk，例如按照 300～500 Token 左右作为初始配置，再根据实际效果调整。

适合：

> 定义、参数、具体事实、细节等精准检索。

“对于长文档，可以建立多粒度的向量表示，具体是一套还是多套索引，需要根据检索策略、数据规模和工程成本决定。”

### 第三步：父子分块（Parent-Child Chunking）

这是处理长文档最关键的技术。具体做法是：

- **子块（Child）** ：切得比较小，比如 200~300 字，用于 Embedding 和检索。子块小，向量表达精准，检索时匹配度高。
- **父块（Parent）** ：子块对应的完整上下文，比如整个小节或 1500 字的大段，不用于检索，只用于最终喂给 LLM。

检索时，用子块做向量匹配，找到最相关的子块后， **回溯到它对应的父块** ，把完整的父块内容传给 LLM。这样既保证了检索的精准度（小块匹配准），又保证了 LLM 拿到的上下文完整（大块信息全），解决了 "小块检索准但上下文不够、大块上下文全但检索不准" 的矛盾。

**最容易被面试官追问的地方：**

分层索引：解决“不同粒度的问题怎么检索”

Parent-Child Chunking：解决“检索粒度”和“上下文完整性”的矛盾

### 第四步：元数据增强

整本书的每个 Chunk 都必须带上丰富的元数据，至少包括：

- 书名
- 篇章号和篇章标题
- 章节号和章节标题
- 小节号和小节标题
- 页码范围
- 块在章节中的位置（开头 / 中间 / 结尾）

这些元数据有两个作用：一是检索时可以做过滤，比如用户明确问 "第三章里的某个概念"，可以先过滤出第三章的 Chunk 再检索；二是 LLM 回答时可以引用来源，告诉用户答案来自第几章第几页，增加可信度。

### 第五步： **跨章节关联：** 摘要挂载关联章节概念，复杂场景可搭配知识图谱解决引用断层问题

书里经常有 "如第三章所述"" 参见第 5.2 节 " 这样的跨章节引用。简单分块会丢失这种关联。处理方式有两种：一是在生成章节摘要时，把该章节引用的其他章节的关键概念也带进来；二是建立 **知识图谱** ，把书中的实体、概念、人物及其关系抽出来，检索时不仅找文本块，还沿知识图谱的关联扩展相关内容。不过知识图谱方案成本高，一般只在高质量要求的场景用。

### 面试总结版（可直接口述）

> 对于长文档的处理不能简单按固定长度切分，需要用分层策略： 
>  第一步先提取目录结构，建立篇 - 章 - 节的树形索引。 
>  第二步分层分块，为每章生成摘要作为高层级检索入口，小节和段落作为细粒度块。 
>  第三步用父子分块技术，小块用于检索保证精准度，检索命中后回溯到对应的大块喂给 LLM，保证上下文完整。 
>  第四步每个块都带上书名、章节、页码等元数据，支持过滤和来源引用。 
>  第五步对于跨章节引用，可以在摘要中带入相关概念，或者用知识图谱建立实体关联。 
>  核心思想是：书是有结构的，分块必须尊重和利用这个结构，而不是把书当成无结构的纯文本暴力切分。

**父子分块：长文档RAG核心最优解（解决精度与完整性矛盾）**

核心答案（你最关心的两点）

1、父子分块 不需要新建第四套向量索引

2、父子分块 只作用在【三级分层的微观层】

宏观、中观 **完全不动**

**先解决你的终极疑惑：三级索引 vs 父子分块 关系**

三级分层索引 = 横向三层知识库（宏观 / 中观 / 微观三套向量索引）

父子分块 = 微观层内部的纵向优化机制

**递进关系：**

1. 先建好三级索引（宏观、中观、微观）
2. **只对微观细块** 做父子分块优化
3. 宏观、中观 **不做父子分块、不需要、不改动**

2、到底什么是父子分块（彻底大白话）

普通 RAG 的 **致命矛盾** ：

- 块切大：上下文完整、回答通顺 → **向量太糊、检索不准**
- 块切小：向量精准、检索超准 → **上下文残缺、回答断片**

1. 子块（检索块）：固定200-300Token，语义最小单元，无冗余、语义聚焦，专门用于Embedding向量化、向量检索、多路召回、Rerank精排，保障检索精准度，避免大块向量平均化导致的匹配偏差。

2. 父块（生成块）：子块对应的完整上下文单元，一般为对应小节、完整段落，1000-1500Token， **不参与检索、不入库向量** ，仅做内容挂载。

3. 联动逻辑：用户提问→子块精准检索命中高相关小块→通过绑定关系回溯对应父块完整上下文→将完整父块内容投喂给LLM生成答案。 核心优势：既保留小块检索的高精度，又解决小块上下文不足、语义断裂问题，是目前长文档RAG的 **工业标配方案** 。

问题：父块就是 段落所在的小节，那不就 中观层吗？

**父块 ≠ 中观层小节！！！** 看着像、内容重合，但 **架构职责、索引机制、触发场景、运行逻辑 100% 不一样** 。

1. **三级分层索引 = 横向三层知识库（三套向量索引，各司其职）**
2. **父子分块 = 微观层内部的纵向 检索 / 生成 解耦机制（无新索引）**

## 5. 混合检索

（1） **纯向量检索的三个致命问题** :

- 无法精准匹配 **专有名词、编号、缩写** （如RFC协议号、HPA、业务专属术语）
- 专业术语语义匹配偏差，口语提问无法精准命中专业文档
- 仅靠语义相似度，容易丢失关键精确信息

### （2）混合检索 = 向量检索 + BM25关键词检索

- 向量检索：抓 **语义相似** ，解决模糊、同义提问
- BM25检索：抓 **精确关键词** ，解决专有名词、编号匹配
- 结果融合：采用 **RRF倒数排名融合** ，无需手动调权重，适配所有提问场景，稳定性远超固定权重配比

![](https://pic1.zhimg.com/v2-7a98f5bbf2674f900764e816082a8618_r.jpg)

### 合并策略：RRF（Reciprocal Rank Fusion）倒数排名融合

最常用的合并方法，公式很简单：

RRF_score(d) = Σ 1 / (k + rank_i(d))

**6. Rerank 是什么？为什么检索之后还要重排序？**

检索和 Rerank 的区别:

**检索** 是粗筛——从百万文档里快速捞出 Top-20，速度快但精度有限。用向量相似度或 BM25 打分，这种打分是 **近似** 的，不一定反映真实相关性。

**Rerank** 是精排——对 Top-20 重新计算相关性分数，用更精确的模型（通常是 Cross-Encoder）逐个打分，把真正最相关的排到前面。

为什么检索的打分不够准？

向量检索用的是 Bi-Encoder：问题和文档分别编码成向量，再算相似度。 **问题和文档在编码时互不知道对方的存在** ，所以只能算"大概相关"。

Rerank 用的是 Cross-Encoder：把问题和文档拼在一起送进模型，模型可以同时看到双方内容，做更精确的相关性判断。 **代价是慢** ——Cross-Encoder 不能预计算，每个 (问题, 文档) 对都要过一遍模型，所以只能对少量候选做精排。

![](https://picx.zhimg.com/v2-ee30e76412be072122ff2c0d1c485577_r.jpg)

| Cohere Rerank | API 调用，效果好，英文为主 |
| bce-reranker-base_v1 | 中文场景，轻量级 |

**答法** ："检索是粗筛快捞，Rerank 是精排提准。检索用 Bi-Encoder 快但粗，Rerank 用 Cross-Encoder 慢但准。先用检索从百万级捞 Top-20，再用 Rerank 精排取 Top-5，这是生产环境的标配流程。"

## 四、 RAG 的幻觉问题

### 1、幻觉的两种类型

**① 内在幻觉** ——生成内容与给定的检索上下文或事实依据发生冲突。

比如检索说"准确率 91%"，LLM 说"准确率 95%"。

**② 外在幻觉** ——生成内容无法从给定上下文或可靠外部依据中得到支持，模型引入了额外的、未经证实的信息。

检索只提到了 A，LLM 自己编了 B。

**2、六种幻觉处理策略：**

1. **Prompt强约束** ：强制模型仅基于检索内容回答，无相关信息直接兜底
2. **参数调优** ：降低temperature（0.1~0.3），减少生成随机性
3. **结果自校验** ：LLM二次审核生成内容，校验每句话是否可溯源
4. **溯源标注** ：提高可追溯性，帮助发现和约束幻觉
5. **阈值兜底** ：检索相似度低于阈值，直接返回「未找到相关信息」
6. **内容对齐** ：比对生成内容与检索片段相似度，过滤无关编造内容

**五、 RAG 检索效果不好怎么优化？**

如果 RAG 检索效果不好，我一般会从 **数据预处理、Chunk、Embedding、Query、召回、Rerank 和上下文构建** 几个环节排查。

（1） 数据预处理

首先保证进入知识库的数据质量。

包括：

- 文档清洗
- OCR
- 表格结构化
- 去除页眉页脚、重复内容和无效内容
- 保留标题、章节、页码等结构信息

因为如果原始数据质量有问题，后面的检索优化效果也会受到影响。

（2）Chunk 优化

调整 Chunk 大小、Overlap 和切分策略。

（3）Embedding 优化

如果语义召回效果不好，可以评估 Embedding 模型是否适合当前业务。

（4）Query 优化

对于用户 Query 过短、口语化或者信息不完整的情况，可以使用 Query Rewrite。

（5）多路召回 / Hybrid Search

不要只依赖单一的向量检索，可以结合：

- 向量检索、BM25、Query Rewrite、Query Expansion、子问题拆解

最后合并多个召回结果。

向量检索擅长语义匹配，BM25 对关键词、专有名词、数字等精确匹配通常更有优势。

（6）Rerank

先通过向量检索和 BM25 快速召回 Top-50 或 Top-100，再使用 Cross-Encoder 等 Rerank 模型进行精排，最终选出 Top-5 或 Top-10。

（7） Parent-Child 和上下文扩展

如果发现召回的 Chunk 很精准，但上下文不完整，可以采用 Parent-Child

所以整体思路是：

> **先保证数据质量，再优化 Chunk 和 Embedding；然后通过 Query 改写、Hybrid Search 提高召回率，再通过 Rerank 提高精排质量，最后通过 Parent-Child 和上下文扩展保证 LLM 获得完整上下文。**

**六、 Agentic RAG 是什么？和普通 RAG 有什么区别？**

（1）普通 RAG 的局限

它的问题是流程比较固定，通常不会根据当前任务和检索结果动态调整策略。对于复杂问题，如果第一次检索结果不好，可能直接把低质量上下文交给 LLM。

（2）Agentic RAG 则是在 RAG 基础上引入 Agent 的 **规划、决策和反思能力** ，由 LLM 根据当前任务动态控制检索流程。

例如 Agent 可以：

- 判断当前问题是否需要检索
- 决定使用什么检索方式
- 对复杂问题进行 Query Rewrite 或子问题拆解
- 判断当前检索结果是否足够
- 如果结果不足，重新检索
- 对多轮检索结果进行汇总和推理

**3. 场景选型**

- **普通RAG** ：简单FAQ、静态知识库、低复杂度问答（够用、低成本）
- **Agentic RAG** ：法律、金融、医疗等高精度、复杂推理场景

**七、高频面试绝杀问答（直接背诵）**

Q1：RAG 和微调怎么选？

**RAG 主要解决：知识问题。**

适合：

- 知识频繁更新
- 企业私有知识问答
- 需要引用来源和可溯源
- 希望快速增加或删除知识

优点是 **不需要重新训练模型，知识更新成本低** 。

**微调主要解决：能力和行为问题。**

适合：

- 固化特定任务能力
- 统一回答风格
- 固定输出格式
- 学习特定任务模式
- 提升特定领域任务表现

但如果只是修改知识，例如公司制度、产品文档更新，通常不应该依赖微调。

**Q：你们的混合检索权重怎么调的？向量检索和 BM25 各占多少？**

两种常见做法：

一是手动调权重（向量 0.7 + BM25 0.3），在验证集上试出最佳比例；

二是用 RRF 合并，不设权重，靠排名融合，更稳健。生产环境推荐 RRF，因为不同 query 的最佳权重差异很大，固定权重不一定好。

**Q：Top-K 设多少？设大了设小了各有什么问题？**

- 过小：召回不足、遗漏关键信息，回答不完整
- 过大：引入大量噪声、增加幻觉风险、token成本飙升
- 工业最优解：检索Top20 + Rerank筛选Top5

**Q3：文档更新如何同步向量库？**

- 小体量低频更新：全量重建索引
- 中高频更新：增量入库、仅更新变更文档
- 大规模生产：双索引切换，实现零停机更新

**Q：如果用户的问题很模糊，检索效果差，怎么办？**

首先判断问题是“用户意图不明确”，还是“用户意图明确但 Query 不适合检索”。

情况一：用户意图本身不明确

例如：

> “这个怎么设置？”

这种情况下缺少必要的上下文，直接检索或者 Query Rewrite 都可能产生错误的理解。

所以可以让 Agent：

> **主动追问用户，补充必要的信息，明确用户意图后再进行检索。**

### 情况二：用户意图明确，但 Query 不适合检索

例如：

> “IVF 怎么查？”

用户意图基本明确，但 Query 比较口语化、信息量较少，不利于直接检索。

这时候可以使用 **Query Rewrite** ：

也可以进行 **Query Expansion / 多路 Query** ：

```text
原始 Query + Query Rewrite + 关键词 Query + 扩展 Query ↓ 分别检索 ↓ 结果融合 ↓ Rerank
```

**Q：设计一个面向 10 万用户的 RAG 知识库系统，你会怎么设计？**

如果让我设计一个面向 10 万用户的 RAG 系统，我会先确认几个核心指标：

- 峰值 QPS
- 文档和 Chunk 的规模
- 知识库更新频率
- 接口延迟 SLA
- 是否存在多租户和权限隔离

然后从 **数据、检索、生成、工程、安全和评估** 几个方面进行设计。

从五个维度展开：

**数据层** （文档解析→Chunk→Embedding→向量库 + ES 双写）、

**检索层** （混合检索 + Rerank，Top-20 检索 + Top-5 精排）、

**生成层** （模型加速+幻觉约束）、

**工程层** （缓存+异步+监控）、

**安全层** （权限隔离+防注入）。

**Q：RAG 的幻觉怎么处理？**

RAG 幻觉不能只依赖 Prompt 解决，我会从 **检索、生成和校验** 几个环节进行治理。

（1）检索阶段

首先保证提供给 LLM 的 Context 是高质量的：

- Hybrid Search
- Rerank
- Metadata Filter
- 检索置信度判断

如果检索结果不足，可以进行 Query Rewrite、再次检索，必要时主动追问或最终兜底。

（2）Prompt / 生成阶段

通过 Prompt 约束模型：

> 仅基于提供的 Context 回答，如果 Context 中没有足够依据，应明确说明信息不足，不要编造。

同时可以适当降低 Temperature，减少随机性。

但 Temperature 只能影响生成随机性， **不能从根本上解决事实性幻觉** 。

### （3）生成后校验

对生成结果进行：

- Citation / 来源标注
- Self-check
- Claim Verification
- Grounding / Faithfulness 检测

核心是检查：

> **LLM 生成的关键结论是否能够被检索到的证据支持。**

**###** RAG 落地最难的地方

"RAG 落地最难的不是某一个环节，是三个环节都有坑，而且级联放大。

（1）最容易被低估的是文档预处理。很多团队上来就调 Embedding 和检索，但文档没清干净、表格解析乱了、知识库没更新，后面的召回和生成都是在脏数据上工作。我做过一个项目，80% 的工期花在数据上，20% 花在模型和检索上。

（2）最难调的是召回质量。核心难点是用户问法和文档写法之间的语义鸿沟，以及分块策略的两难——切太碎丢上下文，切太大引入噪声。我的解法是混合检索加 Rerank，粗召回保证不漏，二次排序保证精度。

（3）最容易被忽视的是生成忠实度。召回对了但模型不忠实，幻觉和正确信息混在一起，用户很难分辨。还有 Lost in the Middle 问题——关键文档落在上下文中间，模型注意力不够。解法是文档排序优化和引用溯源。

这三个问题的共同点是： **都是工程问题，不是算法问题。调模型参数解决不了，得在链路的每个环节做约束和保障。** "
