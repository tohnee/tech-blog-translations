## 第2章：KV Cache 的存储结构——从连续张量到 PagedAttention

### 2.1 连续存储的痛点

最早期的框架（如 HuggingFace Transformers）采用**连续张量存储**：为每个请求预分配一块足够大的连续内存，形状为 `[batch_size, max_seq_len, num_layers, 2, num_kv_heads, head_dim]`。

这种方式有三个致命缺陷：

**1. 内存浪费**：如果设置 `max_seq_len=8192`，但实际请求只有 512 tokens，剩余的 7680 个位置全部浪费。

**2. 内存碎片**：连续批处理（Continuous Batching）下，新请求加入时需要找到足够大的连续内存块。当内存中充满了大小不一的已分配区域时，即使总剩余内存足够，也可能因为没有足够大的**连续**空间而分配失败。

**3. 共享困难**：同一 batch 内不同请求的公共前缀无法共享，每个请求都需要独立存储一份完整的 KV Cache。

**实测数据**：在 13B 模型、4 路并发、不同长度分布的场景下，连续存储的内存利用率仅为 **35-60%**。

### 2.2 PagedAttention 原理

vLLM 提出的 PagedAttention 是 KV Cache 存储领域的革命性设计，核心思想来自操作系统的**虚拟内存分页**：

**核心观察**：KV Cache 并不需要在物理上连续。只要注意力计算时能按正确的顺序读取 K 和 V，它们可以分散在任意物理位置。

**设计要点**：

1. **将 KV Cache 分割为固定大小的 block**：每个 block 存储固定数量的 tokens（通常为 16）的 K 和 V。对于 7B 模型、head_dim=128、num_kv_heads=32、FP16：<br> block_size = 16 tokens bytes_per_token = 2 × 32 × 128 × 2 bytes = 16,384 bytes = 16 KB block_total = 16 × 16 KB = 256 KB (含所有 layers)
2. **物理内存池（Physical Memory Pool）**：所有 block 从一个大的连续内存池中分配，避免外部碎片。
3. **Block Table 映射**：每个请求维护一个 block table，记录其逻辑 block 到物理 block 的映射。

```text
逻辑视图：[Token0-15] [Token16-31] [Token32-47] ...
                      ↓         ↓         ↓
物理视图：  Block#3     Block#7     Block#1    ...
```

### 2.3 Block 管理机制

**分配**：新请求到来时，从 free list 中分配 block。需要更多空间时，动态分配新 block。

**释放**：请求完成后，其所有 block 回收到 free list，供后续请求复用。

**共享（Copy-on-Write）**：当两个请求有公共前缀时，它们的 block table 可以指向同一个物理 block。只有当某个请求需要修改该 block 内的 token 时，才进行复制。

**内存使用率对比**：

| 存储方式 | 内存利用率 | 支持动态长度 | 支持共享前缀 | 支持连续批处理 |
| --- | --- | --- | --- | --- |
| 连续张量 | 35-60% | ❌ 预分配 | ❌ | ❌ |
| PagedAttention | 85-95% | ✅ 动态 | ✅ COW | ✅ |

### 2.4 代码级理解

以 vLLM 中 PagedAttention 的核心逻辑为例：

```text
# 简化的 block table 示意
class BlockTable:
    def __init__(self, block_size: int):
        self.block_size = block_size
        self.block_ids: List[int] = []  # 逻辑 block 到物理 block 的映射

    def allocate(self, num_tokens: int, allocator: BlockAllocator):
        num_blocks = (num_tokens + self.block_size - 1) // self.block_size
        for _ in range(num_blocks):
            self.block_ids.append(allocator.allocate())

    def get_physical_offset(self, token_idx: int) -> Tuple[int, int]:
        block_idx = token_idx // self.block_size
        offset = token_idx % self.block_size
        return self.block_ids[block_idx], offset
```

在 CUDA kernel 中，这个映射被并行化处理，以避免 CPU 端的开销：

```text
// CUDA kernel 中的简化逻辑
__device__ void get_kv_cache_addr(
    int token_idx,
    int* block_table,
    int block_size,
    int64_t* block_ptrs,
    void** out_k_addr,
    void** out_v_addr
) {
    int block_idx = token_idx / block_size;
    int offset = token_idx % block_size;
    int physical_block = block_table[block_idx];
    int64_t base = block_ptrs[physical_block];
    *out_k_addr = (void*)(base + offset * head_dim * sizeof(half));
}
```

### 2.5 PagedAttention 的局限

PagedAttention 并非完美：

1. **Block 大小设计**：太小则 block table 开销增大，太大则内部浪费增加。vLLM 默认 16 tokens 是经验值。
2. **内存池管理开销**：分配/释放 block 需要 CPU 端的同步，在极高并发下可能成为瓶颈。
3. **外部碎片**：当 GPU 内存池耗尽时，需要 offload 到 CPU 或磁盘，这时 block 的物理位置变更需要额外管理。

### 本章小结

- 连续存储导致严重内存浪费（35-60%利用率）和碎片
- PagedAttention 通过 block 化 + block table 映射实现了动态分配和前缀共享
- 内存利用率提升至 85-95%
- Block 大小和内存池管理仍是设计 trade-off
