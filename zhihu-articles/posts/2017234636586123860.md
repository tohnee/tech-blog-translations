昨晚读了一篇文章，让我兴奋到直发抖。有一个叫Percepta的AI实验室，干了一件很疯狂的事情：在LLM里面做了一台计算机。

[Can LLMs Be Computers?](https://www.percepta.ai/blog/can-llms-be-computers)

在详细解释他们做了什么之前，先说说我为什么这样激动。过去一年，我对LLM几个方面的话题特别感兴趣。而Percepta所做的事情，把这几个课题全都连接起来了，而且给出一个让我很满意的答案。

## 三个AI课题

第一个，大语言模型不能做结构化推理的问题。关于大语言模型这个能力局限，看我这个回答的第三点（ [2026 年还有哪些问题能难倒AI ？](https://www.zhihu.com/question/2003061872035849394/answer/2006102082034344367) ）。迄今为止，LLM还是有结构化推理的缺陷，例如汉诺塔、数独还有象棋等这种需要形式化推理的问题，大语言模型往往都不能胜任。为了解决这一缺陷，去年一些研究团队做过很有创新性的尝试，比如HRM [^1] 和后面出现的TRM [^2] 模型。它们仍然采用了Transformer，但是对模型架构做了非常大的创新，本质上来说，已经不属于LLM，而是针对特定推理问题专用的解题模型了。我当时有一个很大胆的设想，就是能不能把HRM这样的模型“融入”到LLM结构内部 [^3] ，让它变成一个全能的模型。Percepta的实验，就是把一个推理模块嵌入LLM内部的尝试。

第二个，就是Elon Musk前一段时间提出的暴论： [跳过编程，让AI模型可以直接生成二进制代码](https://www.zhihu.com/pin/2007036388558791745) 。从原理上来说，如果能用神经网络实现一个编译器/解析器，那么可以让模型的前面若干层生成代码，后面的层次对代码进行编译/解析，这样就能生成可执行的代码。Percepta好像真的把这件事情干成了（严格说，他们做的是执行代码，不只是生成代码）。

第三个，就是Andrej Karpathy所说的， [software 1.0和software 2.0的区别](https://www.zhihu.com/pin/1905393794393805016) 。1.0是传统的代码程序，而2.0就是AI模型。Percepta做的这件事，意味着将来可以把这两种不同的软件融合在一起：一个AI模型里面可以既包含LLM，也包含传统代码执行的路径。甚至这个代码模块，可以做到可插拔、可替换。

## LLM计算机的实现

言归正传，看一看Percepta到底做了什么。

前面说到，现在的大语言模型的结构化推理能力非常有限。看一看SudokuBench上面各个大模型的表现，最顶尖的GPT5模型对9x9的Sukoku，解决率也只有百分之二十左右，很多大模型都是0。

![](https://pic3.zhimg.com/v2-c03dde48f4a1c6b31ae730919a2db9ec_r.jpg)

为了解决这样的问题，现在的做法有两种。

一种是让LLM编一段解题代码，把代码放在模型外部执行，再把执行的结果返回给大模型。这就是Agent的工具调用。让模型和代码，各自去解决自己善于处理的问题。即 **Software2.0去调用Software1.0** 。

另一种就是用一些外部架构来维护一个状态机，外部循环负责存储中间状态，分解任务，并在短上下文中重复调用LLM模型。即 **用Software1.0包裹Software2.0** 。

![](https://picx.zhimg.com/v2-836dc087eab10c534a2b4bfa4909af55_r.jpg)

Percepta面对这个问题的思路是：能不能让1.0的代码放到2.0的模型里面去执行？他们认为可以， **只要在LLM里面搭建一个计算机** 。

从理论上来说，LLM是图灵完全的，它可以进行任何形式的计算。那么用它实现一个计算机，也是可行的。但是理论归理论，在实践中却有很多问题。对于自回归生成模型来说，最大的问题是它的“内存”不是可以任意读写的。历史数据对于大模型都是可读的，但是它却没办法更改，它所有的写操作都只能在Decoding过程中向后进行。所以，用LLM只能做一个append-only的Computer，用文章中的话，“ **Computation as a trace that only appends”** 。

> We tackle this by implementing a modern RAM computer inside the transformer rather than a purely theoretical model of computation. In our construction, each instruction maps to only a handful of tokens (at most 5).

另一个问题，就是执行效率。在我们理解的通用计算机中，每一个指令操作的数据都是有限的（寄存器、内存堆栈）。但是对于自回归模型来说，它每产生一个新token的计算，都会跟前面所有的token发生关系，所以每一个操作是和 **不断增长的Context大小** 成正比的，而不是一个常数。就是说，复杂度是 **O(N)** 而不是 **O(1)** 。 
 Percepta用了一个技巧，让这个复杂度降到了 **O(log(N))** 。

> We remove this handicap by showing that the same transformer architecture admits an efficient decoding scheme for execution-style traces. The key technical unlock is to restrict lookup heads to head dimension 2, which enables a decoding path where the dominant retrieval/update operations can be computed in log time in the sequence length (for this structured executor regime), rather than by a full prefix-sized attention sweep.

为了实现这个Computer，它们在transformer的权重中实现了一个 **WebAssembly解释器** （WebAssembly是一种低级指令集，专为快速、确定性执行和通用目标而设计）。LLM可以生成wasm的代码，权重中的wasm解释器对代码解释执行，在token中生成执行每一条指令后SVM堆栈的状态：

```text
03 00 00 00  commit(+1,sts=1,bt=0)
05 00 00 00  commit(+1,sts=1,bt=0)
08 00 00 00  commit(-1,sts=1,bt=0)
out(08)
halt
```

看这个动画右侧，就是这个LLM内部计算机执行指令的过程。

[In-Model Executionhttps://www.zhihu.com/video/2017237790681760596](https://www.zhihu.com/video/2017237790681760596)

整个过程可以这样理解：

```text
C program
 ↓
compile to WASM
 ↓
generate execution traces
 ↓
train transformer on state transitions
 ↓
LLM predicts next VM state
 ↓
program executes inside transformer
```

他们用解Sudoku的例子，来证明这个LLM计算机的确能以100%的准确度运行Solver代码：

> Our system executes a fully correct compiled Sudoku solver inside the transformer itself. The transformer executes the solver step by step. If the compiled solver is correct, the transformer's execution is correct as well. In practice, this lets the model solve even famously hard instances such as Arto Inkala's Sudoku, reaching the correct solution in under 3 minutes.

[https://www.zhihu.com/video/2017238099416090070](https://www.zhihu.com/video/2017238099416090070)

计算的问题解决了，下面解决计算效率问题。为了能优化这个计算机的执行效率，他们把每一个Transformer的Head设定为二维。因为在2D的条件下，可以做到一个优化：

> For Turing completeness, 2D attention is all you need! And it is still flexible enough to represent a whole RAM computer as we show in this blog. Despite the maximization queries being global over the whole history, there exist efficient data-structures that can answer such 2D attention queries in logarithmic time in the number of points. That is exactly **the classic “supporting point” query in computational geometry** : given a direction q, find the point on the convex hull furthest in that direction. We speed up decoding by maintaining such a data-structure as tokens get generated which lets us efficiently search over the whole set of past points.

有了这个优化，LLM计算机的效率就大大提升了。

在文章最后，作者提出了一些畅想。

第一个畅想是，实现一种双路径的大模型。一个路径用于执行传统LLM的推理和思考；另一个路径就是今天所讲的LLM计算机，用来执行代码，作者把它称为Fast Path。

![](https://pic2.zhimg.com/v2-0b29daac996353eed8af3d3945a135a9_r.jpg)

第二个畅想是，既然可以在大模型里面实现一个解析器，原则上就可以实现任何的程序。我们可以把任何代码“编译”成模型权重，嵌入在整个大模型里面。这样的话，软件1.0就可以变成大模型的一个可插拔的模块。在这个模式下，软件的生态也会呈现一个完全不同的样子。

![](https://pic1.zhimg.com/v2-72415e6b9c99b4d772307c93f1ef9eca_r.jpg)

我和ChatGPT讨论这篇文章的时候，它提出了一个很好的类比：这就像是CPU和FPGA的区别。LLM内部的wasm解析器就像是通用CPU，而把程序直接编译成权重，就像是内嵌了FPGA。

| Concept | Analogy |
| --- | --- |
| CPU | executes software |
| FPGA | hardware compiled for program |
| LLM | could become neural hardware |

这让我想起了赛博朋克作品中的Cyborg，他们可以随时安装、替换组件升级自己的身体机能和智力。

## 评价和展望

对于Percepta这个大胆的尝试，很多人都是交口称赞，其中也包括Karpathy：

![](https://pic3.zhimg.com/v2-8d69be86a38d076afcce1bd5a63f1da2_r.jpg)

但是也有很多人提出了疑虑。

一是执行效率的问题。因为这个LLM计算机本质上是一个“纸面计算机”(或者《三体》中的阵列计算机），它相当于我们在纸上一行一行写出执行每一条指令后的机器状态。即便提升了Transformer的执行效率，能更快吐出Token，它和CPU原生机器的执行速度也相差上千倍。这么做有什么价值呢？

我想说，仅仅以效率作为质疑的理由是不够充分的。在Python语言刚刚开发出来的时候，大多数人也都认为它的效率和C语言程序相差了上百倍，仅仅是个玩具。但是现在，Python是一个主流的编程语言。关键还要看有没有合适的使用场景，以及开发的难度和成本。

另一个质疑：是不是所有的程序都能够训练成模型的权重？这要看程序的输入输出的空间是不是有限的，以及模型的参数容量是不是足够容纳所有的可能性。

无论如何，这是一个非常疯狂的尝试，科技的探索就应该这样“不走寻常路”。我们也看到，在AI领域，还有很多没有探索的空间，仍然是大有可为的。
