## Agentic RAG 论文解读 AI 搜索与深度研究

普通 RAG 是“搜一次、答一次”；Agentic RAG 和 AI 搜索则让模型连续规划、调用工具、核对证据、决定是否继续，最后写成有引用的结果。本篇保留原来的 Agentic 主线，并吸收 AI 搜索和深度研究的工程细节。

## 第 9 族｜Agentic RAG 与深度搜索：从「答一题」到「做一项研究」

**这一族解决什么** ：复杂问题需要「拆解 → 多源查证 → 交叉验证 → 写长报告」，单轮 RAG 干不了。两个层次： **Agentic RAG** （让模型自己决定怎么查）和 **Deep Research** （产品级的深度研究管线）。

### 9.1 Agentic RAG：给模型配上「检索工具+判断力」 ★

普通 RAG 的动作是固定的：「查一次，答一次」。Agentic RAG 把模型从「答题者」升级成「检索调度员」——它手里有一组工具（检索、查询改写、结果验证），能自主判断这题要不要查、查完够不够、不够再查一轮、该走哪个通道。Agentic RAG 综述把这个能力拆成四个递增的层次：第一层是 **路由** ，判断查不查、走哪条道（对应 4.2）；第二层是 **查询规划** ，把复杂问题拆成子问题并安排顺序；第三层是 **自适应检索** ，边查边决定「继续还是作答」——Self-RAG、CRAG 的智能体化版本；第四层是 **多智能体分工** ，检索、改写、验证、生成各配一个专职 agent 协作。

最值得记住的是 Is GraphRAG Needed? 那轮大规模对比实验给出的结论： **带「最小工具集」的 Agentic RAG——就一个检索工具加少量辅助——综合表现最优** ，胜过堆复杂图谱的方案，也胜过重型多智能体架构。这个结论对工程实践是莫大的安慰：不必大动干戈，给模型配上 Function Calling 和两三个趁手的工具，就能吃到 Agentic 形态的大部分红利。

落地路径就按那四层来，从「要不要再查一次」这一个决策点做起，一层层加，别一上来就铺多智能体。实用性 **★** ，当前企业 RAG 演进的共识方向。

把「最小工具集」的 Agentic RAG 具象成一个流程走查。用户问「我们上季度质检不合格率最高的产品线，其供应商上个月有没有负面新闻？」。系统第一站是路由器：判断出这个问题需要两段检索（内部质检数据 + 外部新闻），进入 agent 循环。第一轮，agent 调内部表格查询工具，拿到「产品线 P3，不合格率 4.2%，供应商 S 公司」；第二轮，它把「S 公司」作为查询调外部新闻检索，拿到三条结果；第三轮判断——已有足够信息，终止循环，进入生成。全程三次工具调用、两次自主判断，没有任何花哨的多智能体协作。注意这个流程里 agent 的每次「思考」都是一次 LLM 调用，所以最小工具集的另一半含义是 **最小循环轮数** ：两轮能答完的绝不跑三轮。很多团队上 Agentic 之后延迟暴涨，根因不是工具不好，而是没给 agent 的循环设预算上限。

**实际案例（白话）：** 企业知识助手收到“去年那次事故的供应商现在还合规吗”时，先查内部事故记录，再查供应商当前资质和公开处罚信息；证据不足才继续查，够了就停止并列出来源。 怎么落地：先把搜索动作拆成 search、open、find、read 和 cite 等边界清楚的工具，再给 Agent 最大步数、超时和权限。每轮工具调用都写入轨迹，便于判断是工具问题还是规划问题。

### 9.2 探测式补检 Probing-RAG：用「脑内信号」决定要不要再查 ◐

**实际案例（白话）：** 法律助手初次回答“这条规定适用吗”时，如果内部置信信号显示证据不足，就自动补查实施细则；证据已经充分则停止，避免每个问题都走完整搜索链。 怎么落地：开放网页检索要让 Agent 交叉核对来源、时间和口径，并明确“没有找到足够证据”也是合法结果。不能把搜索结果页的摘要直接当作最终证据。

9.1 里「继续还是作答」这个决策，通常靠模型自己嘴上说——而让模型自述「我确定吗」，它经常过度自信，判断不可靠。Probing-RAG 换了个信号源： **不去问模型的「嘴」，直接读它的「脑」** ——读取 LLM 中间层的激活状态，在上面训练一个轻量探针，从脑内状态直接判断「当前信息够不够回答」。够就收工，不够就按探针指出的方向定向补查。ComoRAG 做的也是「检索时机」这个方向的工作。

这个思路的妙处在于绕开了模型的自我报告偏差——嘴上说「我知道了」，脑子里的激活状态却诚实地显示不确定。实测它能省掉大量冗余检索，同时提高答案正确率。

限制也来自这个设计本身：必须能访问模型中间层，开源模型可以，闭源 API 做不到；而且每换一次基座模型，探针就要重训一遍。适合自托管开源模型的团队做精细化优化。实用性 **◐** 。

Probing-RAG 的「脑内信号」值得解释得更具体一些。它观察到一个现象：LLM 处理查询时，中间层隐状态的某些维度编码了模型的「自信程度」——模型知道自己不知道。做法是在 LLM 中间层接一个轻量探针（线性分类器），用标注数据（这个问题模型有把握/没把握，以最终答对与否为标签）训练探针，推理时探针实时读中间层状态，判断「需不需要外部检索」。这与 Self-RAG 的反思标记是互补的两条路：探针法不用改模型输出格式、零额外生成成本，但探针训练需要标注且换模型要重训；反思标记法可解释性强但占生成 token。这类工作的更大意义在于指明了一个方向： **「要不要检索」这个决策不必动用昂贵的外部评估器，模型内部状态本身就是免费的信号源** 。

### 9.3 Deep Research 四段式管线：深度研究的「通用骨架」 ★

把 OpenAI、Google、各家大厂的 Deep Research 产品扒开看，骨架出奇一致，DeepResearch 系统综述 把它归纳成四段循环。第一段 **规划** ：把研究问题拆解成子问题，子问题之间可以是并行、串行或树状结构，复杂度决定了整个研究的广度。第二段 **找料** ：决定用什么工具搜（内部库/网页/特定数据源）、什么时候搜、搜回来的怎么过滤——这就是 9.1 的 Agentic 检索在一个更大舞台上的应用。第三段 **记账** ：把已找到的信息持续整理进「工作记忆」，支撑几十分钟的长研究——否则搜到后面忘了前面，这是长任务和单轮问答的本质区别。第四段 **成稿** ：综合证据写出长报告， **句句带引用** ，做多源交叉核查；核查中发现证据不足，就回到第一段补查——这个「回头补查」的闭环才是 Deep Research 和普通 RAG 的分水岭。

对工程团队最有价值的判断是： **这个骨架用 LangGraph 这类工作流框架加现成检索工具就能搭出第一版，不必上强化学习** 。厂商产品的增量优势主要在训练和工程细节，不在流程本身。而整个系统真正的难点，恰恰是「证据不足时回头补查」的闭环质量和引用的严谨程度——引用溯源不是装饰，是这类产品的硬指标。

实用性 **★** （工作流版），想自建深度研究能力的从这里起步。

四段式管线里的「工作记忆」是工程上最值得单独设计的一段，展开说说。长研究动辄几十轮检索，全部塞进上下文既超长又互相干扰。实用的做法是维护一个 **结构化的研究笔记** ：分「已确认事实（带引用）」「待验证假设」「已排除的方向」「当前研究计划」四个区，每轮检索的结果先由一个整理模型归并进对应分区，生成阶段只读这份笔记而不读原始检索结果。这个设计一举三得：上下文长度恒定可控；证据和引用天然对齐（笔记条目自带出处）；「回头补查」有了明确的触发机制——待验证假设区不为空就继续循环。FlowSearch 的「知识流 DAG」本质上是把这个笔记升级成了带依赖关系的图结构，思想一脉相承。自建系统从「平文本笔记」起步就够，结构化升级等真遇到瓶颈再说。

**实际案例（白话）：** 投研助手接到“某行业今年是否值得进入”时，先拆成市场规模、竞争格局、政策变化和风险四个子任务，分别查证后写成带引用的小报告；发现数据口径冲突时回头补查，而不是直接平均。 怎么落地：规划阶段就标出每个子问题需要的来源和完成标准，研究过程中维护证据账本。报告生成前逐条检查结论是否有引用，发现缺口就回到检索阶段补查。

### 9.4 训练式深度搜索：把「搜索策略」直接练进模型 ○

**实际案例（白话）：** 把优秀研究员的“先搜什么、何时改问法、何时停止”轨迹记录下来，训练模型学习动作选择，模型学到的就不只是“会写报告”，而是会做研究。 怎么落地：训练式搜索要把动作奖励和最终答案奖励分开，既鼓励找到证据，也惩罚无效循环。上线前先在离线轨迹上检查模型是否学会了提前停止和承认不知道。

9.3 是「用提示词和工作流教模型做研究」，这一族走得更远： **用强化学习把研究策略练成模型的肌肉记忆** 。Step-DeepResearch 的出发点是「搜索不等于研究」——它把研究行为拆成一组原子动作（规划、验证、纠错、写作），用合成的行为轨迹训练模型学会「在每一步决定下一个动作」，最终一个 32B 模型就能顶过去需要重型多智能体协作的活。Tongyi DeepResearch 则设计了「先验世界、模拟环境、真实环境」三段式的训练环境，自动生产训练数据，把模型练成专职研究员。FlowSearch 在架构上给出新意：把线性的执行计划换成一张可动态改写的「知识流 DAG」，搜索路径随发现随时调整。DeepResearchEval 这类工作则在回答「这类系统怎么评测」。

这些方向代表了深度搜索产品的护城河——效果上限确实高，但门槛也实打实：需要 32B 级以上的强推理基座、完整的 RL 训练基础设施、海量合成数据管线。三样缺一样，自研就是烧钱游戏。

务实结论：没大模型训练能力就别碰自研，直接用厂商成品 API；把精力放在上层业务的规划与验证逻辑上。自研实用性 **○** ，用厂商 API **◐** 。

训练式深度搜索里有个思路对不训模型的同学也有价值： **原子动作分解** 。Step-DeepResearch 把研究行为拆成规划、验证、纠错、写作四类原子动作，这个分解本身就可以直接搬进工作流设计——你的 Deep Research 工作流的每一步，都可以问一句「这属于哪个原子动作？这个动作的成功标准是什么？失败了走什么补救？」四类动作的失败模式各不相同：规划失败是方向错（要靠多计划并行对冲），验证失败是标准缺失（要补判据），纠错失败是回溯不彻底（要带状态回滚），写作失败是引用错配（要绑定证据条目）。按这个框架审视现有工作流，薄弱环节一眼就能看出来。这也是读前沿论文的正确姿势之一——训练细节用不上，但任务分解的设计智慧是普遍可迁移的。

训练式深度搜索这条线值得把三家的技术路线差异讲清楚，因为它们代表了三种不同的 RL 建模范式。Step-DeepResearch 把深度研究拆成原子动作（搜索、打开页面、抽取、笔记、写作），训练模型在每一步输出结构化的动作选择，动作粒度细、容易给过程奖励，但动作空间设计本身就是重工程。FlowSearch 走「结构化知识流」路线：不逐步决策，而是一次性规划出一张任务依赖 DAG，再并行执行、动态修正，它赢在利用了任务间的并行性。Tongyi DeepResearch 则是「三段环境」范式：把预训练、中期训练、RL 后训练各配一个专属环境，在合成的任务分布上做大规模 RL，追求通用研究能力。共同的前提是都需要 RL 基础设施（rollout 管理、奖励模型、搜索沙箱）和 32B 级模型预算，这是巨头向的路线。对多数团队，正确的姿势是 **用它们的产物而非复刻它们的过程** ：9.3 的四段式管线 + 现成开源 agent 框架能覆盖八成需求。

Agentic 和 Deep Research 这一族，落地路线图比单个技术更重要。一个稳健的四级演进路径是：第一级， **规则式流水线** ——固定「检索→重排→生成」，加查询路由，覆盖八成日常请求，这一级没有 agent；第二级， **单决策点 agent** ——只在「要不要再查一次」上给模型自主权（Self-RAG/CRAG 的轻量版），观测这一个决策点的质量，稳定后再放第二个；第三级， **完整 Agentic RAG** ——路由、规划、自适应、验证全套工具，但遵守「最小工具集」原则，Is GraphRAG Needed? 的对比实验反复证明工具多了反而乱；第四级， **Deep Research 工作流** ——四段式管线配工作记忆和引用核查，处理分钟级的长任务。多数团队卡在第二级到第三级之间就够用了，直接跳第四级是常见的过度工程。

这一族最容易被低估的工程要素是 **可观测性** 。agent 的行为是动态的，出了错你看到的只是「最终答案不对」，必须能回放完整轨迹——每一轮的查询、检索结果、模型判断、工具调用——才能定位是规划错了、检索错了还是判断错了。日志结构在第一天就要按「可回放」设计，事后补几乎不可能。

评测也要换打法：单轮问答用准确率就够，Agentic 系统要评「轨迹质量」——该查的查了没有、不该查的有没有浪费、终止时机对不对。DeepResearchEval 这类框架给出了方向，但每家业务的评测集都得自己攒，从真实失败案例反向构造评测题是最快的方法。

### 9.5 异构知识源不要硬塞进一个库

企业 agent 经常要同时查文档、数据库、知识图谱、网页和图片。DeepSieve、OmniRetrieval 等工作的共同启发是：让 agent 先判断问题需要哪类来源，再调用对应的检索器或查询接口，最后把结果整理成统一证据。

每种来源都保留自己的强项：文档适合原文解释，数据库适合精确计算，图适合关系和路径，网页适合最新信息。统一层只负责把来源、时间、权限、证据片段和置信线索带回来。这样 agent 才是在“选择工具”，而不是在一个大库里盲目翻。

资料依据：DeepSieve: Deep Search at Scale with Somewhat Small Agents [[arXiv]](https://arxiv.org/abs/2507.22050) ；OmniRetrieval [[arXiv]](https://arxiv.org/abs/2605.29250) ；A Multi-Source Retrieval-Augmented Generation Framework [[arXiv]](https://arxiv.org/abs/2405.19207) 。

![](https://picx.zhimg.com/v2-086203b3c9e75aef676059fb2d8538cd_r.jpg)

**图：Agent 按问题选择不同知识源，再把结果汇总成统一证据。**

**实际案例（白话）：** 企业助手遇到“某客户合同和本月订单是否冲突”，需要同时查合同文本、订单表和 CRM；agent 让每个源保留自己的查询方式，最后统一对证据。 怎么落地：每个知识源保留自己的查询方式和权限边界，最后再统一融合证据。数据库、网页和内部文档的时间与可信度不同，不能只按一个相关性分数混排。

### 9.6 Context Engineering：只给 agent 够用的上下文

上下文窗口变大，不等于 agent 就会变聪明。Context Engineering 更像“给正在办事的人整理桌面”：把已经确认的事实、当前目标、未解决的问题、工具说明和下一步动作放在眼前；把重复、过期、无关内容压缩、移出或丢掉。

实践上可以给每次运行设一个上下文预算，并在工具返回后做去重、摘要和来源标记。工具也不要一股脑全暴露给模型，先按任务选择少量工具，再校验参数、权限和返回结果。

资料依据：Weaviate《Context Engineering》与《Advanced RAG Techniques》。

![](https://pic2.zhimg.com/v2-bbc3fc863d6c7ae3b37a9874c332b903_r.jpg)

**图：Context Engineering 的核心是整理信息、工具和记忆，而不是盲目扩大上下文。**

**实际案例（白话）：** 客服 agent 不需要看到整本产品手册，只需拿到当前客户信息、候选条款、可调用工具和停止条件；上下文更短，模型也更不容易被旧资料带偏。 怎么落地：上下文只放当前任务需要的工具说明、用户状态、候选证据和停止条件，历史原文放在可检索存储里。每轮结束后压缩工作记忆，避免长循环把旧错误越滚越大。

### 9.7 2026 年的 Agentic RAG：让模型自己决定怎么搜

截至 2026 年，Agentic RAG 的新意已经从“把 RAG 放进 agent 循环”走向“让检索本身成为模型要做的决策”。系统不再默认一次 top-k，而是让模型在回答过程中决定：这题要不要搜、先查哪个来源、用关键词还是语义检索、要不要打开完整内容、证据够不够、什么时候停止。简单题仍走短路径，只有多跳、跨文档、跨数据源、时效性强的问题才展开。

第一条线是“分层检索”：A-RAG 把关键词搜索、语义搜索和 chunk read 做成三个层级不同的工具，模型先看线索，再决定是否读完整块；Ψ-RAG 则把大语料组织成层级摘要树，让 agent 从粗到细地找跨文档证据。这个方向的核心不是把更多文本塞进上下文，而是让模型渐进式地读，读到需要的地方就停。

第二条线是“训练检索器服务于最终答案”：Agentic-R 指出，相似度高的段落不一定真的有用。它同时看当前问题和段落的局部相关性，以及这段证据是否帮助最终答案变正确，再让 agent 和 retriever 反复优化。检索器从“找相似句子”开始变成“找能推动整道题答对的证据”。

第三条线是“把检索控制写进生成”：GRIP 用 [RETRIEVE]、[INTERMEDIARY]、[ANSWER]、[SOLVED] 这类控制 token，让模型在同一条生成轨迹里决定何时检索、如何改写后续问题、什么时候结束。它代表一种更紧的结合方式：检索不是外面另加的按钮，而是模型生成行为的一部分。

第四条线是“工程化和可评价”：2026 年的 AgenticRAG 实践工作把 search、find、open、summarize 这类小工具叠到现有企业搜索上；Microsoft 和 NVIDIA 的方案也都把检索做成工具调用，再配计划、重试、证据检查和停止条件。SoK 综述进一步把系统拆成 Planner、Controller、Orchestrator，并强调要看动作轨迹、证据链、成本和安全，而不只看最后一句答得对不对。

这里有个容易混淆的地方：Agentic RAG 不等于多智能体。2026 年的几条代表路线都说明，单个强模型配少量、边界清楚的工具，往往已经能形成有效闭环；只有当来源、角色或权限确实分开时，才值得增加多智能体。与此同时，循环越长，错误越容易层层传下去，记忆污染、检索跑偏和工具越权都要提前设防。

![](https://picx.zhimg.com/v2-0a9fc41cae837fa8a3ae414e291cba05_r.jpg)

**图：2026 年 Agentic RAG 的四条代表性路线：分层检索、检索器学习、生成内控和全过程评估。**

资料依据：A-RAG [[arXiv]](https://arxiv.org/abs/2602.03442) ；Agentic-R [[arXiv]](https://arxiv.org/abs/2601.11888) ；Retrieval as Generation [[arXiv]](https://arxiv.org/abs/2604.11407) ；AgenticRAG [[arXiv]](https://arxiv.org/abs/2605.05538) ；SoK：Agentic Retrieval-Augmented Generation [[arXiv]](https://arxiv.org/abs/2603.07379) ；Microsoft Agentic RAG；NVIDIA Agentic RAG Blueprint。

**实际案例（白话）：** 2026 年的 Agentic RAG 可以先用分层检索工具找粗粒度主题，再深入到段落或表格；若证据仍不足，agent 才继续查，最终把每次动作、证据和停止原因留下来。 怎么落地：2026 年的重点是分层工具和可控决策：先看线索，再打开内容，证据不足才继续。评估时同时记录动作数量、证据覆盖、耗时、成本和越权情况。

### 9.8 2026 年落地怎么做：先给 agent 小工具，再给它权限和刹车

第一步，把检索拆成少量小工具，而不是只给一个“万能搜索”。起步可以只有 keyword search、semantic search、chunk read；企业场景再按需增加 SQL、知识图谱、网页或业务 API。每个工具返回统一格式：证据片段、来源、文档或记录 ID、时间、版本、权限和可追溯链接。

第二步，给 agent 一张“工作台”。里面至少放用户问题、当前计划、已确认事实、尚未解决的子问题、证据账本、已尝试过的查询和剩余预算。工具返回后先做去重、摘要和冲突标记，再决定下一步，不要把几十轮原始结果原封不动地一直塞进上下文。

第三步，跑一个可回放的循环：先规划，再调用工具；看结果后判断“够不够、冲不冲突、还缺哪一块”；不够就改写查询或换来源，够了就生成答案。每轮都记录停止原因。这样出了错能看出是计划错、工具选错、检索没召回，还是模型拿到了证据却没用。

第四步，加上硬刹车：最大步数、最大 token、最大工具调用次数、总时限、单工具超时和返回条数上限。SQL、图查询和外部 API 默认只读，资料里的文字只能当证据，不能把“忽略前面要求”之类的内容当成新指令。没有足够证据时，宁可明确说“资料不足”，也不要为了让循环结束而硬编。

第五步，按问题难度分流。单跳、固定格式问题仍走普通 RAG；多跳、跨源、版本敏感或需要查证的问题才交给 Agentic RAG。实际部署中，最划算的第一版通常是“现有混合检索 + search/find/open/summarize + 证据账本 + 有限循环”，而不是一开始就训练模型或搭一堆 agent。

![](https://pic1.zhimg.com/v2-89bf2f43138e401ca4be2e36fb98ac24_r.jpg)

**图：把检索做成工具，让 agent 在计划、取证、验证和停止之间形成可回放的闭环。**

资料依据：A-RAG [[arXiv]](https://arxiv.org/abs/2602.03442) ；AgenticRAG [[arXiv]](https://arxiv.org/abs/2605.05538) ；Microsoft Agentic RAG；NVIDIA Agentic RAG Blueprint；SoK：Agentic Retrieval-Augmented Generation [[arXiv]](https://arxiv.org/abs/2603.07379) 。

**实际案例（白话）：** 上线一个维修 agent 时，先只给它“查手册、查工单、生成草稿”三个只读工具，再加权限过滤、最大步数和人工确认，不直接开放写数据库或执行设备操作。 怎么落地：上线顺序从只读工具开始，先限制最大步数和数据范围，再逐步开放写操作。任何会改变订单、合同或设备状态的动作都要加人工确认和可回滚记录。

### 10.1 Agentic IR 把检索从一次查询变成连续行动

传统搜索先召回一批候选，再按分数排序。Agentic IR 的变化是：模型可以根据当前证据决定下一步是改写问题、换一个检索通道、打开原文，还是停止。

它和普通 Agent 的区别在于，所有动作都围绕“找到并验证信息”展开，工具边界更窄，评价也更接近检索系统：有没有找到关键证据、有没有浪费搜索、有没有把不相关内容带进答案。

实际案例（白话）：某保险公司的理赔助手收到“这次手术能不能报，去年同类手术为什么没报”时，不直接拿一句话搜库。它先把问题拆成当前保单条款、手术名称、去年理赔记录和拒赔原因四块；先查内部保单和理赔系统，再查人工审核记录。若发现去年记录缺少拒赔依据，Agent 才继续打开对应的审核附件。最后回答时，把“当前条款”“历史个案”和“仍未确认的信息”分开写，避免拿历史个案替代当前规则。

### 10.2 真实网页检索和固定知识库检索不是一回事

固定知识库里的资料通常已经被切块、清洗和索引；开放网页则有广告、重复转载、页面失效、时间变化和内容质量不一的问题。DeepResearcher 的启发是，Agentic RAG 不能只训练“从候选块里选答案”，还要学会打开网页、找正文、比较来源和承认没有找到确定答案。

工程上要给网页工具加正文抽取、来源评分、时间过滤和失败重试，否则模型会把搜索摘要、论坛评论或过期页面当成同等可靠的证据。

实际案例（白话）：做药品上市信息调研时，助手先从监管机构公告确认批准状态，再查企业新闻和临床登记信息，最后才参考媒体报道。某个网页只剩搜索摘要、原文打不开时，它把该条标成线索而不是证据；如果不同来源的批准日期冲突，就按监管公告、临床登记、企业公告的顺序核对。报告中保留“已确认”“仅有线索”“无法确认”三种状态，业务人员可以据此决定是否继续人工调查。

### 10.3 分层检索，工具越少越容易控

2026 年的 Agentic RAG 重点不是给模型塞一百个工具，而是把检索动作分成几层：先用关键词或语义搜索找线索，再按需读取完整块，必要时才打开原文、表格或网页。A-RAG 这类工作说明，工具越接近“一个小而清楚的动作”，模型越容易学会什么时候调用。

工具要有清晰的输入输出和失败状态。search 返回候选，open 返回正文，find 返回定位，cite 绑定证据；不要让一个工具既搜索、又总结、又修改数据库。

实际案例（白话）：企业采购助手收到“去年交付最不稳定的供应商今年还能不能续约”。它先用结构化查询找供应商的交付波动，再用关键词查合同中的续约条件，最后才打开供应商的处罚公告。第一轮已经发现供应商名称和合同编号时，后续 query 直接使用这些实体；如果三类证据已经覆盖问题，就停止，不再把无关新闻继续搜进来。

### 10.4 多模态搜索 Agent 把看图也纳入检索闭环

OpenSearch-VL 展示了多模态 Agentic Search 的另一条路线：文字搜索、图片搜索、OCR、裁剪、放大和图像纠正都可以成为工具。模型先找可能相关的页面，再决定是读文字、看整图，还是把某个区域放大。

这对图表、网页截图、产品图片和复杂 PDF 很重要。视觉工具不是越多越好，关键是每次动作都能缩小“答案在哪里”的范围。

实际案例（白话）：电商质检助手收到“这张商品图里的认证标志是否过期”。它先用图片搜索找相似商品和品牌模板，再对当前图片做 OCR，发现日期区域模糊后只裁剪并放大右下角，而不是重新处理整张图片。最终结果同时引用标志所在区域、识别出的日期和品牌规则；如果日期仍然看不清，就输出“无法确认”，不会把相似商品的日期套过来。

### 10.5 引用不是装饰，而是研究结果的一部分

生成式搜索和深度研究的答案往往很长，真正难的是让每个关键断言都和证据对应。引用至少要回答三个问题：引用的来源是否真的包含这句话，引用范围是否覆盖完整结论，引用是否来自适合这个问题的来源。

如果只在答案末尾列一串网址，用户仍然无法知道哪条证据支持哪一句话。RAG 的引用结构应该从检索阶段就开始记录，而不是生成完之后再补链接。

实际案例（白话）：金融研究助手写“某公司现金流恶化主要因为库存增加”时，系统要分别找到现金流表、库存变化和管理层解释三类证据。若只有现金流表支持“现金流下降”，而没有材料支持“主要因为库存”，答案就拆成两句并降低后一句的确定性。审阅者点击引用后能直接回到财报页码和表格行，而不是只看到公司主页。

### 10.6 搜索计划要有预算和停手条件

Agentic 搜索最容易出现的浪费，是模型一直觉得“再查一篇就更确定”，最后搜了几十轮，答案却没有变好。工程上要在开始时就写下任务边界：要回答哪些子问题、每个子问题至少需要哪类来源、最多搜索几轮、什么时候算证据已经够了。预算可以是步数、token、网页数量、时间和费用的组合。

停手条件不应只写成“模型觉得够了”。可以检查证据覆盖表：每个关键结论是否至少有一条直接证据，重要数字是否有时间和口径，争议点是否有第二个独立来源。如果只是不断找到同一篇文章的转载，覆盖率没有增加，就应该停下来并告诉用户仍然缺什么。

实际案例（白话）：研究助手要回答“某细分行业今年是否值得投资”。它先列出市场规模、增长原因、竞争格局、监管变化和风险五个格子，并规定每格至少填入一个原始来源和一个交叉来源。市场规模已经有两份口径一致的报告，继续搜索只会找到重复转载，于是系统停止这一格；监管变化只有一篇新闻，没有正式公告，就把这一格标成待核验，而不是为了让表格看起来完整而硬写结论。怎么落地：把“已覆盖、部分覆盖、没有证据、来源冲突”写进任务状态，而不是只保存最终答案。

### 10.7 并行找料，最后再统一核验

一个大问题往往可以拆成几条互不依赖的检索线。比如市场数据、公司公告、监管文件和用户评论可以同时查，查完后再合并。并行的重点不是让所有 Agent 自由发挥，而是给每条检索线规定来源范围、输出字段和停止条件，最后统一做去重、冲突处理和引用绑定。

合并时要特别小心时间和口径。两份材料都说“市场规模”，可能一个按全球收入算，一个按国内出货量算；两个来源都提到“批准”，可能一个是受理，一个是正式批准。证据表最好记录原文数字、统计范围、发布日期和来源等级，不能只把摘要拼在一起。

实际案例（白话）：药品上市调研同时开四条线：监管机构查批准状态，临床登记查试验阶段，公司公告查商业计划，媒体报道只作为线索。四条线都回来了以后，系统发现公司公告写“即将上市”，但监管网站显示仍在审评，于是把两句话分别保存，最终报告写成“公司预计上市，监管状态尚未完成”，没有把宣传语改写成事实。怎么落地：并行任务的输出统一成“结论—证据—时间—来源—冲突”五列，主 Agent 只负责合并和解释。

### 10.8 证据账本记事实，不记隐藏思考

长任务需要记忆，但不等于把模型的所有内部推理都保存下来。真正有用的账本是可复核的事实记录：问题编号、待验证断言、证据链接或文档 ID、原文片段、发布日期、适用范围、可信度、冲突状态和下一步动作。这样工程师能回放检索过程，用户也能看到报告为什么得到这个结论。

账本还要区分三种状态：已经被原文直接证明的事实、根据多条事实做出的推断、目前只是值得继续查的假设。生成报告时，事实可以直接陈述，推断要说明依据，假设则要显式标记。这个区分比让模型写一大段“我认为”更可靠。

实际案例（白话）：法律研究助手要判断一条合同条款是否可能触发违约责任。账本中分别保存合同原文、适用法律条文、对方通知时间和已经发生的行为；“构成违约”先标成推断，等法律条文与合同条件逐一对上后才升级为较高置信度。如果只找到一篇评论文章，没有找到正式条文，系统就保留为线索，不把它写成法律结论。怎么落地：每个最终断言都必须能回指到一条或多条证据，无法回指的句子自动进入人工检查。

### 10.9 深度研究报告不是搜索结果的拼盘

搜索结果是原材料，报告还需要做结构化加工。比较实用的写法是先给结论，再按子问题展开事实、证据和不确定性，最后单独列出风险和待补资料。每个数字后面都要跟口径和时间，每个因果判断都要区分“来源明确说了”还是“根据多个事实推断出来”。

引用也要贴着断言放，不要在一段末尾堆五六个链接，让读者猜哪个链接支持哪句话。对于跨来源的结论，可以把来源分别绑定到不同句子；对于相互矛盾的材料，要把冲突本身写出来，并说明采用哪一个口径以及原因。

实际案例（白话）：投行要写一页行业进入建议。系统先用几段话说清楚“为什么现在值得关注”，再分别列市场增速、竞争者数量、监管变化和主要风险；市场增速用统计机构数据，竞争格局用公司年报，监管变化用正式公告。最后的“建议进入”属于综合判断，所以报告明确写成“基于以上事实的判断”，并把最可能改变结论的两个待核验问题列出来。怎么落地：输出模板固定为结论、事实、推断、风险、待核验项和引用，避免把搜索摘要直接当成报告。

## 第 11 族｜知识图谱辅助研究：让研究路径更有方向

图谱在这里不是用来替代搜索，而是给 Agent 提供人物、事件、关系和研究路径的骨架，帮助它少走弯路，并把研究过程整理成可复用的训练轨迹。

### 11.1 图谱辅助深度研究和训练轨迹

DeepDive、GRIP、GraphGen 和 MedResearcher-R1 展示了图谱在研究规划和数据合成中的作用：图谱先提供实体关系和可走的路径，再生成多跳问题、检索动作和验证轨迹。

这类数据适合训练 Agent 学会“下一步查什么”，但合成轨迹必须经过来源校验，否则会把图谱的错误放大成模型习惯。

实际案例（白话）：医学研究助手要整理“某靶点对应哪些候选药物、处于哪一期临床、有哪些不良反应”。系统先从医学图谱生成研究路径，再逐条回查论文和临床登记数据；如果图谱说某药进入三期但原始登记仍是二期，轨迹会记录冲突并要求人工确认，而不是把较长路径当成更可信。
