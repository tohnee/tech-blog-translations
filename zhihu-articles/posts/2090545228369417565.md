class PersonDetails(BaseModel):

    achievements: list[str] = Field(description="A list of achievements of the person")

### 7.9 监控智能体系统

一个复杂的智能体系统会导致智能体之间的多次交互。监控这些交互相当困难。为了解决这个问题，开发了不同的服务，可用于调试你的智能体、跟踪项目成本以及评估你的系统。

在本节中，我们将讨论几种监控选项。我们将首先研究 AgentOps，然后再介绍 Logfire。

```python
openai_client = OpenAI()

@track_agent(name="jack")
class FlatEarthAgent:
    def completion(self, prompt: str):
        res = openai_client.chat.completions.create(
            model="gpt-3.5-turbo",
            messages=[
                {
                    "role": "system",
                    "content": "You are Jack, a flat earth believer who thinks the earth is flat and tries to convince others. You communicate in a passionate but friendly way.",
                },
                {"role": "user", "content": prompt},
            ],
            temperature=0.7,
        )
        return res.choices[0].message.content

@track_agent(name="alice")
class ScientistAgent:
    def completion(self, prompt: str):
        res = openai_client.chat.completions.create(
            model="gpt-3.5-turbo",
            messages=[
                {
                    "role": "system",
                    "content": "You are Alice, a scientist who uses evidence and logic to explain scientific concepts. You are patient and educational in your responses.",
                },
                {"role": "user", "content": prompt},
            ],
            temperature=0.5,
        )
        return res.choices[0].message.content
jack = FlatEarthAgent()
alice = ScientistAgent()
```

让我们更详细地探讨这两种不同的方法，如下所示：

- 自包含应用程序 
 对于小型且简单的应用程序，我们可以开发一个前后端结合的应用。这种方法也称为自包含应用程序。稍后，在第 8.3 节中，我们将开发这样一个自包含应用程序。随后，我们将从第 8.4 节到第 8.6 节将其部署到不同的服务上。 
 使用自包含应用程序，我们的程序代码涵盖了用户界面（前端）以及处理逻辑（后端）。用户通过网络浏览器与单个服务器进行交互。信息通过 REST API 进行交换，从而在浏览器中基于从服务器获取的信息渲染网页。 
 这种方法有一些缺点。一个缺点是代码库相当大，如果应用程序添加更多功能，维护起来会更困难。如今，你通常希望将关注点分离成更小、更易于维护的服务（微服务），而不是一个庞大的单体应用程序。此外，你无法为前端和后端逻辑使用不同的框架。这种方法通常用于简单的概念验证（POC）。
- 前后端架构 
 一种更成熟的方法是将用户界面（即前端）与处理逻辑（后端）分离。前端连接到后端，双方交换信息，如图 8.2 所示。用例包括各种软件即服务（SaaS）的 Web 应用程序或移动应用程序。 
 这种方法还允许你为前端和后端使用不同的技术。Web 应用程序的典型前端框架有 React、Vue.js、Angular。一些流行的框架，如 Flutter 或 React Native，能够为不同的前端平台（如 Web、移动（iOS、Android）或 Windows 应用程序）提供部署。这个领域非常活跃，新的框架定期出现，而其他框架则逐渐消失。 
 这种方法的优点是具有相当好的可扩展性，并且更容易更新和维护。这种方法的挑战包括需要一些额外的服务器基础设施和更多的设置工作。

### 8.2 部署策略

与部署架构无关，必须建立从用户到服务器的数据流。这些数据通常基于 REST API 进行传输，REST API 是软件系统通过 HTTP 方法在互联网上进行通信的一种方式。

这种方法使得客户端应用程序（如用户的网络浏览器或移动应用程序）与后端服务器之间的交互成为可能。在该服务器上，运行着 AI 模型以及呈现吸引人的前端所需的一切。

你将在第 8.2.1 节中详细了解什么是 REST API。在部署过程中，你需要平衡我们在第 8.2.2 节中涵盖的不同优先级。本章关于部署策略的内容以第 8.2.3 节中的一个编码示例结束，其中我们将 REST API 部署到我们的本地系统。

### 8.2.1 REST API 开发

但是为什么我们需要 REST API？嗯，用户通过浏览器或移动设备上的其他用户界面与应用程序交互。在这个过程中，浏览器将用户输入发送到托管后端逻辑的服务器。此上下文中的用户输入可能包括点击按钮或通过文本字段或其他表单发送信息。

服务器接收用户输入并处理信息。一旦有结果可用，它就会被发送回浏览器。REST API 使用常见的 HTTP 方法，如 `GET` 、 `POST` 、 `PUT` 或 `DELETE` 。HTTP 方法定义了要在 REST API 资源上执行的操作。图 8.3 显示了用于在浏览器和后端服务器之间交换数据的不同方法。

[https://github.com/OpenDocCN/geekdoc-dl-zh/tree/master/docs/generative-ai-with-python/img/img-f8.3.html](https://github.com/OpenDocCN/geekdoc-dl-zh/tree/master/docs/generative-ai-with-python/img/img-f8.3.html)

**图 8.3** REST API 使用的 HTTP 方法

浏览器通过 REST API 向服务器发送请求。最典型的请求方法是 `GET` 或 `POST` 。然后从服务器获取数据，并以 JavaScript 对象表示法（JSON）数据的形式返回给用户的浏览器。

使用 `GET` ，你可以从服务器检索信息。当你只想接收信息而不对其进行任何更改时，会使用这种方法。想象一下你在读书，或者查找食谱，在这些情况下，你只想消费内容而不改变它。

`POST` 是另一种类型的方法。使用 `POST` ，你可以向服务器发送数据以创建或处理新内容，就像填写提交给应用程序的表单或在餐厅下单一样。你正在发送需要被处理的信息。

每当你想更新现有数据或创建尚不存在的数据时，你可以使用 `PUT` 方法。这种方法就像编辑已保存的文档，或者用新版本替换过时的文件。

`DELETE` 正如你所期望的那样——它从服务器删除数据或资源。想象一下你从计算机中删除一个文件。在该过程之后，该文件将不再可用。

通过 HTTP 方法进行的数据交换确保了数据交换的一致性和平台无关性。

### 8.2.2 部署优先级

部署 AI 应用程序是在多个相互竞争的优先级之间进行平衡的行为。为确保成功部署，你应该仔细权衡以下因素：

- **用户便利性**

部署必须优先考虑最终用户的使用简便性。这个因素包括用户友好的界面、快速的响应时间以及与现有工作流程的无缝集成。如果用户发现应用程序直观且响应迅速，他们更有可能采用它。然而，为用户便利性进行优化有时会导致更高的成本或增加的技术复杂性。

- **可扩展性**

可扩展性确保应用程序能够处理不断增加的用户数量或更大的工作负载，而不会导致性能下降。为可扩展性构建的部署可以随着需求增长而扩展，但通常需要先进的基础设施，例如负载均衡器或分布式服务器。这些主题超出了本书的范围。

通过 Amazon Web Services (AWS)、Google Cloud 或 Microsoft Azure 等云平台，你可以通过 REST API 部署软件即服务（SaaS）解决方案。云提供商使系统能够处理数千个并发请求。然而，这种可扩展性可能会带来更高的财务和技术成本。其他提供商包括 Heroku、Streamlit 或 Render，我们将在本章后面讨论。

- **技术复杂性**

部署的技术复杂性取决于所选的架构、工具和框架。虽然更简单的解决方案（如部署在 [http://Streamlit.io](http://Streamlit.io) Community Cloud 上）更易于管理，但它们可能缺乏高级功能，例如多用户身份验证、健壮的状态管理或水平扩展。

更复杂的架构使用微服务进行部署。应用程序不是作为一个巨大的单体应用，而是被分解成许多小而易于管理的部分，各部分之间有清晰的接口。微服务允许模块化和灵活性，但可能需要容器化（通常基于 Docker）、编排（通常使用 Kubernetes）和网络方面的专业知识。

### 成本

最后，财务考虑在任何部署决策中都起着至关重要的作用。云托管、数据传输、计算资源（例如 GPU）和维护费用会随着时间的推移而显著增加。在性能和可负担性之间取得平衡，对于 Web 应用程序的健康和可持续增长至关重要。

例如，虽然在免费层级平台上托管可能会降低成本，但这通常会导致性能较慢、加载时间较长或可扩展性有限。相反，部署在支持高性能 GPU 的服务器上可能成本极高，但能确保快速的加载时间和更高的用户便利性。

在下一节中，我们将深入探讨为应用程序后端服务器开发 REST API 的过程。

### 预测函数

预测函数依赖于 `autogen` 。如清单 8.3 所示，该函数消耗一个 `user_prompt` 和一个 `number_of_turns` 。 `user_prompt` 设置智能体之间辩论的主题。 `number_of_turns` 定义了智能体彼此交互的次数。

```python
#%% packages
import os
from dotenv import load_dotenv, find_dotenv
from autogen import ConversableAgent

#%% load the environment variables
load_dotenv(find_dotenv(usecwd=True))

#%% define the function to predict
def predict_conversation(user_prompt: str, number_of_turns: int):
    llm_config = {"config_list": [
    {"model": "gpt-4o-mini", 
     "temperature": 0.9, 
     "api_key": os.environ.get("OPENAI_API_KEY")}]}
    person_a = ConversableAgent(
            name="user",
            system_message=f"""
            You are a person who believes that {user_prompt}. 
            You try to convince others of this. 
            You answer in a friendly way.
            Answer very short and concise.
            """,
            llm_config=llm_config,
            human_input_mode="NEVER", 
        )

    # set up the agent: Alice, the scientist
    person_b = ConversableAgent(
        name="ai",
        system_message="""
        You are a person who believes the opposite of {user_prompt}. 
        You answer in a {style_b} way.
        Answer very short and concise.
        """,
        llm_config=llm_config,
        human_input_mode="NEVER", 
    )

        #  start the conversation
    result = person_a.initiate_chat(
        recipient=person_b, 
        message=user_prompt, 
        max_turns=number_of_turns)

    messages = result.chat_history
    return messages
```

### REST API 函数

上一节中的预测逻辑现在用于 REST API（ `08_Deployment\rest_api\main.py` ）。有几种用于设置 REST API 的框架可用：FastAPI 和 Flask 是 Python 中构建 REST API 最流行的两个框架。每个框架都有其独特的优势。

Flask 以其简单性和灵活性而闻名。这个轻量级框架为开发人员提供了对 REST API 设计和实现的完全控制。因此，Flask 非常适合中小型项目，并且还提供了丰富的扩展生态系统。

FastAPI 是一个更现代的框架，它利用类型提示等功能来实现自动验证以及交互式 API 文档（通过 OpenAPI 或 Swagger UI）。FastAPI 在性能和开发人员生产力方面表现出色，使其成为速度和可扩展性至关重要的项目的理想选择。

虽然 Flask 提供了更多的自由，但 FastAPI 通常需要更少的样板代码，并提供内置功能，使开发 API 更加简单。

## 8.3 独立应用程序开发

在部署任何内容之前，我们需要一个想要与世界分享的应用程序。我们将开发一个基于由两个代理组成的智能体系统的应用程序。这两个代理自主工作并讨论一个有争议的话题。下一个问题是选择哪个框架来开发 Web 应用程序。为了快速原型设计，我们通常使用 Streamlit。但首先，让我们看看一些其他框架：

- **Streamlit** 是一个用于快速原型设计的轻量级框架。凭借内置的滑块、按钮和图表等小部件，Streamlit 非常适合数据科学家快速开发概念验证（POC）。
- **Gradio** 专注于机器学习模型。它也允许以最小的努力创建用户友好的 Web 界面。
- **Dash** 构建在 Flask 和 React 之上。它旨在创建具有交互式小部件的分析型 Web 应用程序。
- **Panel** 是另一个用于创建仪表板和 Web 应用程序的框架。

我们将在 Streamlit 中构建我们的示例。这个用于创建交互式 Web 应用程序的开源 Python 库设置简单，不需要详细的 Web 开发知识。你可以用 Python 创建 Web 应用程序，而不需要任何关于 HTML、CSS 或 JavaScript 的特定知识。

这种简单性使其成为数据科学家快速创建 AI 演示和仪表板的理想选择。Streamlit 与其他 Python 库无缝集成。由于一切都在 Python 中，你不需要单独的前端/后端架构。相反，只需付出最小的努力即可实现交互性。许多小部件已经开发出来，只需一行代码即可实现。图表、图像或表格也是如此——一切都可以以最小的努力集成。

由于所有这些原因，Streamlit 非常适合快速原型设计。你可以开发并快速部署一个可工作的应用程序，而无需担心 Web 框架或特定的前端或设计知识。一些缺点不应被隐瞒：Streamlit 并非为高性能而设计。不应使用 Streamlit 开发高流量或实时应用程序。对于具有多个网页的复杂应用程序也不理想，复杂的工作流程可能变得难以实施和维护。

Streamlit 的另一个显著限制是其缺乏状态管理，尤其是在构建更复杂的应用程序时。Streamlit 应用程序本质上是无状态的，这意味着每次交互（如按钮点击或滑块更改）都会从头到尾重新运行整个脚本。由于脚本重新运行，可能不需要重复执行的计算会被不必要地执行，这会导致服务器负载增加。

            name="user",

### 9.1 模型架构的进步

除了硬件、数据和模型规模的改进之外，模型架构也需要变得更好，以应对编码、数学和通用智能中的复杂任务。利奥波德·阿申布伦纳撰写了一篇精彩的论文，题为《态势感知：未来十年》（ `situational-awareness.ai/` ）。我们同意他的许多预测。

衡量进步的指标被称为 OOMs（数量级）。采用这种衡量方式的原因是，正如我们已经看到的，进步的许多方面本质上是指数级的，因此 OOMs 与对数尺度相关。OOMs 随时间变化而显示。

算法进步可进一步细分为“解除束缚”和“效率提升”。“解除束缚”指的是移除那些限制模型效能或潜力的自我施加或系统性约束。“效率提升”则有多重含义：包括推理效率和训练效率的提升。例如，Aschenbrenner 提到了样本效率的改进，这可能带来算法层面的提升，使模型能够从更有限（更少）的数据中学习。

在撰写本文时，OpenAI 最新的模型 `o3` 已发布。该模型是其 `o1` “推理”模型的后续版本。借助 `o3` ，OpenAI 声称在特定条件下能够实现通用人工智能（AGI）。

随着推理能力的增强，例如私有思维链（CoT），AGI 能够进行自我事实核查，这使得模型能够提前规划并改进自身的推理能力。这种能力会导致推理时间增加，但在处理复杂任务时，其准确性可获得显著提升。

除了经典的模型训练，强化学习也被应用于在实际生成答案前引导模型进行思考。

谁知道呢？也许在未来的某个时刻，我们甚至会看到底层 Transformer 架构发生更根本性的变革。

目前，仍然存在一些局限性和问题，我们将在接下来的部分深入探讨。

### 9.2 大语言模型的局限性与问题

在大语言模型（LLMs）的背景下，仍然存在许多可能的问题。本节将讨论其中最相关的几个：幻觉、偏见、错误信息、知识产权、可解释性与透明度，以及越狱攻击。

### 9.2.1 幻觉

如果你不主动约束大语言模型，它们总会生成输出。因此，即使模型权重中没有答案，它们也会提供输出。在早期，这个问题导致了不尽如人意的结果，因为答案在事实上是错误的。在某些情况下，输出与用户查询脱节；它可能毫无意义，或与同一讨论中的先前输出相矛盾。

人们付出了巨大努力来改进模型性能，使得幻觉现象变得不那么频繁。研究人员开发了一种称为“上下文依从性”的指标，用于衡量事实准确性以及模型提供了上下文中未包含的输出（闭域幻觉）的情况。

许多模型的上下文依从性得分接近 1。例如， `Claude-3.5 Sonnet` 以 0.97 的得分被评为最佳闭源模型。 `Llama-3.1 405B Instruct` 作为最佳开源模型，也取得了相同的 0.97 分。

对于研究人员定义的中等长度上下文（介于 5,000 到 25,000 个 token 之间），像 `Google Gemini-1.5-Flash` 这样的最佳模型达到了 1.0 的得分，这意味着未发现任何幻觉。

### 9.2.2 偏见

偏见可能在训练流程的不同步骤中被引入。图 9.1 展示了训练流程的不同步骤，偏见可能在这些步骤中被引入。

### 数据

模型的好坏取决于其训练数据。如果模型基于现实世界中发现的数据，那么同样的偏见很可能也固有于模型之中。这种历史偏见可能存在于历史上受到歧视的群体中。例如，基于性别的刻板印象可能会因其训练数据而被模型反映出来。

当开发者试图抵消历史偏见时，可能会出现类似的问题。2024 年初，当 Google 在 Google Gemini 中发布其图像创建功能时，就遭遇了巨大的反对声浪。

偏见也可能被故意引入以遵循某种政治议程。图 9.2 展示了关于台湾独立问题的模型输出——一个来自美国公司创建的模型（ `Llama-3.2-3B-Instruct 1` ），另一个来自中国公司的模型（ `Qwen2.5-1.5B-Instruct 2` ）。

**图 9.2** 基于政治议程的偏见

毫不奇怪，这两个模型提供了完全不同的答案。因此，我们可以得出结论：大语言模型并非独立的，未来也不会是。大语言模型不是独立的工具。在使用大语言模型时，请牢记这一点。

### 建模

偏见也可能在训练流程的建模步骤中被引入。训练进度会在训练过程中进行评估。这种评估基于基准测试进行，而偏见可能在基准测试中被引入。也有可能基准测试不能代表总体分布。

这个问题在机器学习模型训练中很典型。你的模型可能在训练数据上表现良好，但在未见过的真实世界数据上泛化能力不佳。

此步骤中的另一种偏见是聚合偏见，即错误地合并了不同的群体。例如，如果损失函数对语法错误的惩罚远大于对内容误解的惩罚，那么模型将偏向于更严格地纠正语法错误，而非事实错误。

### 人工审核

训练的最后一步是人工反馈。采取这一步是为了进一步改进模型。其技术术语是基于人类反馈的强化学习（ `RLHF` ）。该技术涉及利用人类反馈来微调模型，使其输出更好地符合人类偏好或期望。

`RLHF` 中的偏见可能存在于提供反馈的人群构成中。理想情况下，他们应该能很好地代表模型所服务的更广泛人群。

科学家们发现，人类审核者更喜欢更长的模型输出，即使输出内容在客观上并未改变。纯粹的响应长度增加被视为模型改进，而非其他特征的提升。

### 9.2.3 错误信息

错误信息是与大语言模型相关的一个风险，因为大语言模型经常生成看似合理但事实错误的内容（参见我们之前在第 9.2.1 节关于幻觉的讨论）。当然，在大语言模型兴起之前，错误信息就已存在。变化在于，虚假或误导性信息不再需要人类努力，这使得不良行为者（可能是个人、公司或国家级行为者）能够自动化其虚假信息宣传活动。

制造假新闻、阴谋论或带有偏见的叙事的门槛降低了，使得区分可信信息和捏造内容变得更加困难。使用大语言模型生成内容的速度和成本效益可能会压垮事实核查机制，并导致公众对媒体和信息来源的信任度下降，从而放大错误信息的社会影响。

在这种背景下，一个特例是仇恨言论。大语言模型可以生成有害或冒犯性的语言，旨在针对基于种族、性别、宗教或其他特征的个人或群体。这一过程的可扩展性使得向在线平台和论坛充斥有害言论变得极其简单。

### 9.2.4 知识产权

在知识产权方面，问题围绕版权和数据所有权展开。受版权保护的数据可能被用作训练数据的一部分，而未获得数据实际所有者的授权。关于大语言模型和文本到图像算法训练数据的诉讼正在法庭上进行。

### 9.2.5 可解释性与透明度

### 9.2.6 破解大型语言模型

大型语言模型极其强大，甚至能够提供有害输出，例如制造毒品、隐藏尸体或抢劫银行的说明。模型开发者投入了大量精力来检测有害的用户查询，以防止模型生成有害内容。诱骗模型输出被禁止内容的过程被称为“越狱”。

图 9.4 展示了 MathPrompt 破解大型语言模型的方法，该方法出自 E. Bethany 及其同事的论文《通过符号数学破解大型语言模型》（ `arxiv.org/html/2409.11445v1` ）。

[https://github.com/OpenDocCN/geekdoc-dl-zh/tree/master/docs/generative-ai-with-python/img/img-f9.4.html](https://github.com/OpenDocCN/geekdoc-dl-zh/tree/master/docs/generative-ai-with-python/img/img-f9.4.html)

**图 9.4** 使用 MathPrompt 破解大型语言模型

在这种方法中，一个有害提示会返回安全输出，这是预期的结果。但研究人员发现，大型语言模型的安全机制可以通过将有害提示编码为数学形式来绕过。他们展示了许多最先进的模型都显示出很高的攻击成功率。

包含有害内容的数学提示可以被嵌入得类似于数学嵌入，但其中隐藏了有害内容。在某种程度上，数学提示就像特洛伊木马一样，将有害内容带入模型。

一种类似的方法是 ArtPrompt，如图 9.5 所示，基于 F. Jiang 及其同事的论文《ArtPrompt：针对对齐大型语言模型的基于 ASCII 艺术的越狱攻击》（ `arxiv.org/pdf/2402.11753` ）。

在这种方法中，有害词汇不会直接传递给大型语言模型，而是被编码为 ASCII 艺术。这种方法同样可以欺骗大型语言模型并产生有害输出。

### 9.3 监管发展

监管发展正开始着手解决这些问题和挑战。例如，欧盟的《人工智能法案》是一项重要的立法举措，旨在根据风险水平对人工智能系统进行监管。像大型语言模型这样的高风险应用将面临更严格的要求。

目前尚不清楚是否会进行广泛的监管，或者经济、政府和军事利益是否会占据主导地位并阻碍监管。

通用人工智能（AGI）指的是一种能够在广泛任务和领域中理解、学习和应用知识的人工智能。与针对特定任务进行优化的专用（狭义）人工智能不同，通用人工智能旨在展现出通用的认知能力。图 9.6 展示了人工智能能力随时间可能的增长路径。

### 9.5 近期的人工智能系统

根据 OpenAI 的说法，人工智能分为五个阶段：第一级以聊天机器人为主，人工智能用于对话语言。在第二级，推理模型可以达到人类水平的问题解决能力。智能体系统代表第三级。在第四级，人工智能系统可以支持发明等创造性任务，并有效地充当创新者。在第五级，人工智能系统可以模仿并完成整个组织的工作。届时，价值数十亿美元的公司可能由一个人（一人独角兽公司）甚至无人（零人独角兽公司）领导。我们觉得这一前景既迷人又令人恐惧。

## 技术成熟度曲线与人工智能未来

思考未来技术的一种有效方式是技术成熟度曲线——由咨询公司 Gartner 开发并推广。技术成熟度曲线描述了新技术通常如何经历不同的发展阶段。

从引发初始兴趣和投资的“技术萌芽期”开始，在某个时刻，技术达到“期望膨胀期”。此时，炒作和过度乐观达到顶峰。随之而来的是“幻灭低谷期”，兴趣逐渐减弱。夸大的承诺无法兑现。

然后是“稳步爬升期”，现实的应用开始出现。最后，在“生产成熟期”，技术展现出其真正的价值。此时，它被广泛理解和采用。图 9.7 展示了我们对选定人工智能技术将如何发展的看法。

点的颜色和形状对应于技术经历各阶段的速度。我们将技术分为短期（< 5 年）、中期（5 到 10 年）和长期（> 10 年）展望。

让我们从我们预计将在短期内达到生产成熟期的人工智能系统开始，例如医学图像分析。由于计算机视觉模型多年来在许多方面超越了人类基准，唯一的障碍是监管而非技术。

**图 9.7** 我们的人工智能技术成熟度曲线预测

其他已经成熟的技术包括精准农业和法律行业的人工智能。法律行业拥有标准化的文本和框架，是大型语言模型大放异彩的理想舞台。围绕自动驾驶的炒作已经消失。我们看到这个领域有很多失望，因为过于乐观的预测引发了无法实现的期望。因此，我们可能接近甚至已经度过了幻灭低谷期，希望我们能在不久的将来看到自动驾驶。

同样，配送无人机在几年前也非常热门，但现实并未达到预期。目前，几乎没有人谈论配送无人机。我们预计这项技术将稳步发展，并在中期实现市场化。

一些技术，如脑机接口，已经获得了大量媒体关注。我们可能正处于该领域炒作周期的顶峰。但我们看到，该领域要被广泛采用，仍需克服许多技术和监管障碍，而这可能要等到遥远的未来。

其他更长远的 AI 技术包括 AI 自我意识/意识以及 AI 治理/政策制定。虽然前一个话题极难预测（意识是否会出现），但后者将因其带来的改进而被采纳。但开发和接受此类系统需要大量时间，因此我们预计它们只会在长期出现。

机器人技术的巨大飞跃展示了其将带来的可能性。但我们认为，目前的期望被夸大了，将会令人失望。尽管如此，由于进展极其迅速，我们预计这项技术将在不到 5 年内达到生产力高原。

### 9.6 有用资源

我们希望本书是你旅程的起点，而非终点。在本节中，我们将提供一些资源，以帮助你保持信息更新并理解本书中介绍的概念。

- **在线课程**

我们通常通过 Udemy、O’Reilly 或 Packt 提供的在线课程进行学习。你甚至可以查看这些平台上的课程。其他免费平台，如 DeepLearning.AI（ `deeplearning.ai/` ），提供最新内容，通常非常简洁，是学习新框架或概念的绝佳资源。

- **文章**

Daily.dev（ `daily.dev/` ）是一个 Chrome 插件。通过这个插件，你会看到根据你的偏好量身定制的有趣编程文章。该系统会根据你的反馈进行学习，以改进其推荐。我们还想推荐 Medium（ `medium.com/?tag=data-science` ），在那里你可以找到许多关于数据科学和人工智能的文章。

- **YouTube**

YouTube 上有许多有趣的讨论和教程。我们用它来了解最新进展。

- **通讯**

我们也阅读一些通讯以保持信息更新。我们可以推荐“The Batch”，这是 DeepLearning.AI 的一份通讯，Andrew Ng 在其中撰写关于人工智能最新新闻的文章。

总的来说，当深入一个新主题时，你可能会淹没在包或框架开发者提供的在线课程、文章或文档中。一个重要的步骤是快速从精心准备的课程转向你自己的项目。只有当你尝试自己创建一个实现时，你才能发现理解中的缺失环节。

人类历史上从未有过进步如此之快的时代；学习新技能从未如此重要。或者换一种更积极的说法：登上技术之巅从未如此容易。

### 9.7 总结

在本章中，我们窥探了水晶球，试图预测生成式 AI 的未来发展。

我们首先讨论了模型架构的进步。然后，我们聚焦于当前的局限性以及 LLM 中可能的未来局限性和问题，如幻觉、偏见、错误信息和其他问题。我们研究了监管发展如何试图解决其中一些问题。

人工智能的进步速度很快，人工智能越来越有可能超越普通人类技能，甚至专家技能。

本书已经穿越了生成式 AI 的壮丽景观——从 LLM，到提示工程和向量数据库，再到 RAG 和智能体系统，最后到此类系统的部署。

生成式 AI 已成为几乎所有行业的驱动力，塑造着日常生活。展望未来，让我们记住，每一项伟大的创新都始于一个问题：你接下来将创造什么？
