### 0. 引言：Ulysses 在搬什么，为什么值得优化

长序列 video DiT 的多卡推理，序列并行几乎是标配。以 Wan2.1-T2V-14B 为例，720P、81 帧的视频对应的 latent 序列长度是 75600，这个长度的 full attention 单卡跑很慢，主流方案就是 Ulysses（DeepSpeed-Ulysses）。

Ulysses 的数据流很简单。设并行度为 P（本文 P=4），每卡平时持有序列的 1/P：

```text
q/k/v 投影输出:  [b, s/P, h, d]      每卡：局部序列 × 全部 head
    │  all-to-all（进 attention）
    ▼
attention 输入:  [b, s, h/P, d]      每卡：完整序列 × 1/P 的 head
    │  full attention（任意实现，FA3 直接用）
    ▼
attention 输出:  [b, s, h/P, d]
    │  all-to-all（出 attention）
    ▼
恢复布局:        [b, s/P, h, d]
```

一次 a2a 中，每卡把自己数据的 (P−1)/P 发出去、收回同样多，通信量以 Wan2.1 参考计算流程为：

Wan2.1 的 shape 是 s=75600、h=40、d=128、bf16，P=4 时每卡每个 tensor 持有 18900×40×128×2B ≈ 185 MB，一次 a2a 收发各 ≈ 139 MB。每个 transformer block 有 4 次 a2a（q/k/v 进 + attention 输出出），14B 模型 40 个 block，**每卡每个 denoise step 的 a2a 流量约 22 GB**。

和 ring-attention 对比一下通信量（都按 Wan 的 shape、MHA、每卡每层计）：

Ulysses 每个元素最多被重排一次：4 次 a2a × 每次发送本地数据的 (P−1)/P，即 4×(P−1)/P × 185 MB，P=4 时 ≈ **555 MB**。

ring 则保持序列切分不动，把 K、V 块沿环转 (P−1) 轮、让完整的 KV 流过每张卡：(P−1)×2 × 185 MB，P=4 时 ≈ **1.11 GB**。两者之比是个很干净的式子：

```text
ring / ulysses = [2(P−1)/P] ÷ [4(P−1)/P²] = P/2
```

P=2 打平，P=4 时 ring 要多搬一倍，P=8 时多搬三倍。（目前按 MHA 算；GQA 下 ring 只转 kv head、通信量按分组数缩小，结论要重算——Wan 的自注意力是 MHA，不受影响。）

计算量的话，核心 GEMM（QK^T 和 PV）两边总量完全一样，都是 4·s²·h·d FLOPs，只是切法不同：

Ulysses 每卡算完整序列的 h/P 个头，ring 每卡算 s/P 个 query 对全序列的 h 个头。

差别在 ring 的 online softmax 要跨块合并：每个 ring step 产出的部分和 O 带着 LSE，下一步要做 exp 重标定再累加。

这部分**纯 FLOPs 可以忽略**——每卡每层约 s·h·d 次乘加，相对核心计算的占比是 P/(4s)，Wan 的 shape 下是十万分之一量级。

**真正的代价在 HBM**：ring 的每一步隔着一次通信，是独立的 kernel launch，部分和 O 必须以 fp32 在 HBM 落地（387 MB/步，而最终 bf16 输出只有 194 MB），(P−1) 次 merge 又各是一轮 elementwise 读写——按 Wan P=4 估算，每卡每层额外 ~5 GB 的 HBM 往返。

Ulysses 的 attention 就是一次标准 FA 调用，online softmax 的重标定全程在寄存器/SMEM 里完成，O 只落一次 bf16，这项开销严格为零。

当然 ring 也有优势：它的通信天然嵌在 attention 的分块循环里、结构上就是 overlap 的，而且 attention 计算是 O(s²)、通信是 O(s)，序列越长越容易隐藏。

但对本文的场景，Ulysses 全面占优：流量少一半（P=4）、没有 merge 开销、attention 完全解耦（FA/任意后端直接用，ring 则与 attention kernel 深度耦合），代价只是并行度受 head 数整除约束（Wan 40 头，8 卡以内都好切）。对单机 NVLink 全互联、MHA、P≤8 的推理场景，Ulysses 是更省事也更省流量的选择。

但是 a2a 的实现上，torch.distributed 的标准姿势是 permute + contiguous → `all_to_all_single`（NCCL）→ permute，在 nsys 里看这条链路有三个很差的地方：

1. **NCCL 的通信 kernel 跑在 SM 上**，和 cuBLAS GEMM 抢同一批计算资源；
2. a2a 前后的 **permute 是纯搬运的 elementwise kernel**，把 185 MB 读一遍写一遍，纯属陪跑；
3. 目前通信计算是同步语义，**没法和计算 overlap**。

总上，就是 [fast-ulysses](https://github.com/triple-mu/fast-ulysses.git) 诞生的目的，下面直奔主题。

### 1. fast-ulysses：三条 a2a 路径与使用方法

仓库在这里：

[https://github.com/triple-mu/fast-ulysses](https://github.com/triple-mu/fast-ulysses)

核心思路一句话：

输出 buffer 放在 NVSHMEM 对称堆上，`nvshmem_ptr` 拿到 peer 显存的 P2P 直接映射地址，数据**按目标布局直接写进对面卡**——重排在写的过程中顺便完成，permute 从根上消失，然后跨卡用自定义 flag barrier 同步。

在把数据写其他卡上，仓库提供了三条路径，数据流动方式各不相同：

| 路径 | 数据怎么走 | SM 占用 | 特点 |
| --- | --- | --- | --- |
| non-TMA（默认候选） | SM 线程向量化直写 peer 显存，相邻线程拼出大块 NVLink 写事务 | 占 | 延迟最低，launch 参数按 shape 现场 autotune |
| TMA（sm90+） | cp.async.bulk.tensor 走 4D tensormap，单线程发射 + 软件流水 | 几乎不占 | 与 non-TMA 谁快看 shape，use_tma=None 时现场跑分二选一 |
| CE（copy engine） | 拆成对每个 peer 的 cudaMemcpy2DAsync，跑在 DMA 引擎上 | 零 | 标称延迟最高，但和计算完全并行——overlap 场景的正解 |

CE 路径值得多说一句：它单独跑是三条里最慢的（standalone 0.70 ms vs others 0.48 ms），但 cuBLAS 的 nvjet GEMM 是 cooperative launch，不释放 SM，SM 上的通信 kernel 只能干等 GEMM 跑完；只有 DMA 引擎上的拷贝能在 GEMM 满负荷时同时把 NVLink 拉满。

这是用延迟换零 SM 占用的方法，配合异步接口（`all_to_all_single_4d_ce_async` + 组共享 barrier）就能享受到完全 overlap 的收益。

编译安装命令（依赖 NVSHMEM 3.7+、CUDA 12/13、PyTorch）：

```bash
NVSHMEM_HOME=<nvshmem install root> FAST_ULYSSES_CUDA_ARCH=90 pip install -e . --no-build-isolation
```

使用与 torch.distributed 习惯一致：

```python3
from fast_ulysses import UlyssesGroup

group = UlyssesGroup(process_group=dist.group.WORLD)

# 同步版：mode0 = [b, s/P, h, d] -> [b, s, h/P, d]
out = group.all_to_all_single_4d(x, mode=0, tag="demo")

# 异步 CE 版：三次传输共享一次 barrier 握手，只有最后一个带 barrier=True
hv = group.all_to_all_single_4d_ce_async(v, mode=0, tag="v", barrier=False)
hq = group.all_to_all_single_4d_ce_async(q, mode=0, tag="q", barrier=False)
hk = group.all_to_all_single_4d_ce_async(k, mode=0, tag="k", barrier=True)
# ... 中间塞计算 ...
v, q, k = hv.wait(), hq.wait(), hk.wait()
```

sglang 侧的适配在笔者的分支上（含 Wan 的 QKV 流水线改造与一个配套的 norm+rope JIT kernel，后文会讲为什么需要它）：

[https://github.com/triple-mu/sglang/tree/feat/fast-ulysses-integration](https://github.com/triple-mu/sglang/tree/feat/fast-ulysses-integration)

打开方式是三个环境变量：`SGLANG_DIFFUSION_ENABLE_FAST_ULYSSES=1` 启用，`SGLANG_DIFFUSION_FAST_ULYSSES_PIPELINE_QKV=1` 开 QKV 流水线，`SGLANG_DIFFUSION_FAST_ULYSSES_TYPE=ce` 选传输路径。

### 2. nsys 对比：overlap 做成了什么样

测试环境：4×H200（NVSwitch），Wan2.1-T2V-14B，720P 81 帧，40 步，bf16，sglang。baseline 是 NCCL 路径，实验组是 fast-ulysses CE + QKV 流水线。

先看 baseline 的 timeline（图 1）：

![](https://pica.zhimg.com/v2-dc1d91b2c45eb43d3310c2b5f8e64c00_r.jpg)
*【图 1：baseline，Q/K/V GEMM → Norm+RoPE → 三段串行的 A2A（permute + ncclDevKernel + permute）】*

Q/K/V 三个 GEMM 跑完，flashinfer 的联合 Norm+RoPE 处理完 q/k，然后 Q-A2A、K-A2A、V-A2A 三段**串行**排开——每段都是 permute、NCCL SendRecv、permute 三件套，全程占着 SM，计算流在这段时间里就是停的。

要把这段时间藏掉，光换一个异步 a2a 还不够。原实现里 q/k 的 Norm+RoPE 是一个联合 kernel，意味着 q 和 k **同时**就绪，它们的 a2a 同时出发，overlap 的力度变粗。

所以 sglang 侧做了两件事：

1. 把 Norm+RoPE 拆成**单 tensor 调用**（新写的 tvm-ffi JIT kernel，cross-head 归约 + RoPE 一个 kernel 完成，且比 flashinfer 联合版更快：27.4 → 18.9 ms/step）；
2. 重排流水线：v 没有 norm/rope 最先出发，q 处理完立刻出发，此时 k 的 GEMM 才开始——**q 的传输压在 k 的 GEMM 下面**：

```text
V-GEMM → 发 V-A2A             ─┐
Q-GEMM → norm+rope → 发 Q-A2A ─┤ 三次传输共享一次 barrier
K-GEMM → norm+rope → 发 K-A2A ─┘
attention 前统一 wait
```

效果看图 2：

![](https://pic1.zhimg.com/v2-3572e9b21014136c5711a7cd941c3444_r.jpg)
*【图 2：CE 流水线，V/Q/K-A2A 的 Memcpy P2P 分别在 GEMM 的下面】*

三组 Memcpy P2P（V-A2A、Q-A2A、K-A2A）在独立的 timeline ，分别与 Q-GEMM、K-GEMM 及后续计算完全重叠；计算行上只剩 GEMM 和 norm+rope，中间不再有通信的 kernel。

图中同一阶段的窗口时长从 8.35 ms 缩到 5.46 ms。

端到端数字（已做 warmup）：

|  | baseline（NCCL） | fast-ulysses CE 流水线 | Δ |
| --- | --- | --- | --- |
| 每 step | 5.2355 s | 5.0110 s | −4.3% |
| Denoise（40 步） | 209.4 s | 200.4 s | −9.0 s |
| 端到端 | 213.0 s | 204.4 s | −8.5 s |
| 峰值显存 | 43.0 GB | 62.5 GB¹ | +19.5 GB¹（异常待排查） |

¹ 初版异步实现的 allocator 膨胀，已定位并修复：修复后与 baseline 持平（+0.6 GB）。

nsys 的 kernel 时间拆解（每 step 每卡，8 step 窗口均值）说明收益的来源：

| 项 | baseline | CE 流水线 |
| --- | --- | --- |
| NCCL SendRecv（SM） | 138 ms | 0 |
| permute 拷贝（SM） | ~85 ms | ~0 |
| flag barrier（SM） | — | 80 ms（必要的 barrier， 耗时很短） |
| P2P 传输（DMA 引擎） | — | 71 ms，全部藏在计算下 |
| QK Norm+RoPE | 27.4 ms | 18.9 ms |

整体结论：

实测每 step 快了 224 ms，与 baseline 通信 kernel 的 223 ms 吻合——SM 上的通信时间被整体被 overlap；

CE 单条拷贝 48.4 MB 用时 148 µs，折合 **~330 GB/s**，DMA 引擎在 GEMM 满负荷的同时把 NVLink 拉满（baseline 的 NCCL SendRecv 折算下来只有 ~161 GB/s，还是独占 SM 换来的）；

sglang 目前的 NCCL 路径不支持这种异步流水线（NCCL 的 a2a 需要配合额外的通信流与拆分改造），所以本文没有 NCCL + overlap 的对照实验。

已知代价与局限：

峰值显存更高（NVSHMEM 对称堆、通信 buffer 等有额外占用），待排查原因，这里非常奇怪；

上述显存膨胀全是 allocator 的 reserved 池开销。根因是初版异步路径用 `record_stream` 把输入张量交给通信流：eager 模式下 host 领先 GPU 几十层，被 Python 按时释放的 q/k/v 块全部认为”事件未完成、不可复用”态，allocator 只能不断开新段——35 层 × 555 MB ≈ 19.4 GB。

修复是把 `record_stream` 换成 per-tag 持久 staging 缓冲：异步输入在调用者流上拷贝一份，通信流只读副本，输入张量从此不跨流持有；修复后峰值回到 baseline +0.6 GB（正好是三个 staging 缓冲的体积），代价是每次调用一份 D2D 拷贝（实测 step +0.5%）。

`record_stream` 配上跑得很远的 host，是个经典的显存膨胀问题。

只测试了单机 NVLink、world_size ≤ 8、uniform 切分、无 backward 测试，理论上通过 mode 可以支持。

### 3. 结论

**fast-ulysses 通过使用 copy engine（零 SM 占用）做数据搬运 + QKV 流水线拆分，几乎实现了通信和计算完美掩盖**。

在 4×H200 的 Wan2.1-T2V-14B 上，每 step 5.24 s → 5.01 s（−4.3%），整体上看 V/Q 的通信可以被完美掩盖，K/O 的通信则因为数据依赖的问题没法掩盖，但是可以消除掉数据重排。
