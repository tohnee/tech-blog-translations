[模型上下文协议（MCP）](https://modelcontextprotocol.io/docs/getting-started/intro)能让 LLM 智能体调用数以百计的工具去解决真实世界任务。但我们要怎样让这些工具尽可能高效？

本文描述我们在多种智能体 AI 系统中验证过的、最有效的性能改进方法。

先讲你可以如何：

- 构建并测试工具原型
- 借助智能体创建并运行针对工具的全面评测
- 与 Claude Code 这类智能体协作，自动提升工具的表现

最后，是我们一路总结出的高质量工具编写原则：

- 选对要实现（以及**不要**实现）的工具
- 用命名空间为工具划清功能边界
- 把有意义的上下文返回给智能体
- 针对 token 效率优化工具响应
- 为工具描述与规格做提示工程

### 什么是”工具”？

在计算领域，确定性系统在相同输入下每次都产生相同输出；而*非确定性*系统——比如智能体——即便起点相同，也可能给出不同响应。

传统软件开发，本质上是在确定性系统之间订立契约。例如 `getWeather("NYC")` 这样的函数调用，每次都会以完全相同的方式获取纽约的天气。

工具则是一类新型软件，它体现的是**确定性系统与非确定性智能体之间的契约**。当用户问”我今天该带伞吗？”，智能体可能调用天气工具，可能凭常识作答，也可能先反问一句地点。偶尔，智能体还会产生幻觉，甚至压根没弄明白该如何使用某个工具。

这意味着为智能体写软件时，必须从根本上重新思考方法：不能再像给其他开发者或系统写函数、写 API 那样去写工具和 [MCP 服务器](https://modelcontextprotocol.io/)，而要**为智能体而设计**。

我们的目标，是让智能体借助工具去尝试多种成功策略，从而扩大它能有效解决的任务范围。所幸按我们的经验，对智能体最”顺手”的工具，对人来说往往也出奇地直观易懂。

### 如何编写工具

本节讲如何与智能体协作，既写出工具、又改进你交给它的工具。先搭一个快速原型并本地测试；接着运行全面评测来衡量后续改动；再与智能体一起反复”评测 → 改进”，直到智能体在真实任务上取得稳定表现。

### 构建原型

不亲自上手，很难预判哪些工具对智能体顺手、哪些不顺手。先搭一个快速原型。如果你用 [Claude Code](https://www.anthropic.com/claude-code) 写工具（也许一次生成就够），把工具所依赖的软件库、API、SDK 的文档一并给 Claude 会很有帮助（可能包括 [MCP SDK](https://modelcontextprotocol.io/docs/sdk)）。对 LLM 友好的文档通常能在官方文档站点的扁平 `llms.txt` 文件里找到（这是[我们 API 的](https://docs.anthropic.com/llms.txt)）。

把工具包进一个[本地 MCP 服务器](https://modelcontextprotocol.io/docs/develop/connect-local-servers)或[桌面扩展](https://www.anthropic.com/engineering/desktop-extensions)（DXT），就能在 Claude Code 或 Claude 桌面应用里连接并测试。

连接本地 MCP 服务器到 Claude Code，运行 `claude mcp add <name> <command> [args...]`。

连接本地 MCP 服务器或 DXT 到 Claude 桌面应用，分别进入 `Settings > Developer` 或 `Settings > Extensions`。

工具也可以直接传入 [Anthropic API](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/overview) 调用，用于程序化测试。

自己动手测一遍工具，找出粗糙之处；收集用户反馈，建立对”工具应当支撑哪些用例与提示词”的直觉。

### 运行评测

接下来，你需要通过评测衡量 Claude 使用工具的水平。先生成大量**扎根真实用途**的评测任务。我们建议与智能体协作分析结果、判断如何改进工具。完整流程见我们的[工具评测 cookbook](https://platform.claude.com/cookbook/tool-evaluation-tool-evaluation)。

### 生成评测任务

有了早期原型，Claude Code 能快速探查你的工具，生成几十组”提示词－响应”对。提示词应取材于真实用途，基于真实的数据源与服务（例如内部知识库、微服务）。我们建议避免过于简单、浮于表面的”沙箱”环境——它们无法用足够复杂度给工具做压力测试。好的评测任务往往需要多次工具调用，有时多达几十次。

**好任务的例子：**

- 下周安排一次与 Jane 的会议，讨论我们最新的 Acme Corp 项目。附上上次项目规划会议的笔记，并预订一间会议室。
- 客户 ID 9182 反映，一次购买被重复扣款三次。找出所有相关日志记录，并判断是否有其他客户受同一问题影响。
- 客户 Sarah Chen 刚提交了注销申请。准备一份挽留方案，并确定：(1) 她为何离开；(2) 哪种挽留优惠最有说服力；(3) 给出方案前我们需要留意哪些风险因素。

**较弱任务的例子：**

- 下周安排一次与 jane@acme.corp 的会议。
- 在支付日志里搜索 `purchase_complete` 和 `customer_id=9182`。
- 按客户 ID 45892 找到那份注销申请。

每条评测提示词都应配一个**可验证的响应或结果**。验证器可以简单到”标准答案与采样响应做精确字符串比对”，也可以高级到请 Claude 来评判响应。避免过于严格的验证器——它们会因为格式、标点、合理的另一种措辞这类无关差异而误杀正确答案。

对每组提示词－响应对，你还可以（可选地）指定预期智能体会调用哪些工具，用来衡量智能体在评测中是否真正理解了每个工具的用途。不过，由于正确解题往往存在多条有效路径，尽量不要过度指定或过拟合到某一种策略。

### 运行评测

我们建议用直接的 LLM API 调用以程序化方式运行评测。使用简单的智能体循环（包住”LLM API 调用 ↔ 工具调用”交替的 `while` 循环）：每个评测任务一个循环。每个评测智能体只拿到一条任务提示词和你的工具。

在评测智能体的系统提示词里，我们建议不仅要求输出结构化的响应块（供验证），也输出**推理块与反馈块**。要求智能体在工具调用块和响应块**之前**输出这些，能通过触发思维链（CoT）行为，提升 LLM 的有效智能水平。

如果你用 Claude 跑评测，可以开启[交错思考（interleaved thinking）](https://docs.anthropic.com/en/docs/build-with-claude/extended-thinking#interleaved-thinking)，”开箱即用”地获得类似能力。这有助于探查智能体为何调用／不调用某些工具，并凸显工具描述与规格中值得改进的具体位置。

除了顶层准确率，我们建议同时采集其他指标：单次工具调用与整个任务的运行时长、工具调用总次数、token 总消耗、工具报错。追踪工具调用能揭示智能体常走的工作流，也能提示哪些工具可以合并。

### 分析结果

在发现问题方面，智能体是得力伙伴——从自相矛盾的工具描述、低效的工具实现，到令人困惑的工具 schema，它都能给反馈。但请记住：**智能体在反馈和响应里”没说”的部分，常常比”说了”的部分更重要**。LLM 并不总是[言如其意](https://www.anthropic.com/research/tracing-thoughts-language-model)。

观察智能体在哪里卡住、困惑。通读评测智能体的推理与反馈（或 CoT），找出粗糙点。查看原始对话记录（含工具调用与工具响应），捕捉 CoT 里没有明确描述的行为。要会读弦外之音；记住评测智能体未必知道正确答案与正确策略。

分析工具调用指标。大量冗余调用可能说明分页或 token 上限参数需要重新调整；大量因参数非法导致的工具报错，可能说明工具需要更清晰的描述或更好的示例。我们上线 Claude 的[网页搜索工具](https://www.anthropic.com/news/web-search)时，就发现 Claude 会多余地在 `query` 参数后面追加 `2025`，使搜索结果产生偏差、拉低表现（我们通过改进工具描述把 Claude 引回正轨）。

### 与智能体协作

你甚至可以让智能体分析结果、替你改进工具。做法很简单：把评测智能体的对话记录拼接起来，粘贴进 Claude Code。Claude 擅长分析对话记录，也擅长一次性重构大量工具——例如在新改动之后，确保工具实现与描述仍保持自洽。

事实上，本文的大部分建议，都来自我们用 Claude Code 反复优化内部工具实现的过程。我们的评测建立在内部工作区之上，镜像了内部工作流的复杂度，包含真实的项目、文档与消息。

我们依靠留出测试集确保没有对”训练用”评测过拟合。这些测试集表明，即便相对于”专家级”工具实现，我们仍能榨出额外的性能提升——无论那些工具是研究员手工写的，还是由 Claude 自己生成的。

下一节，我们分享这一过程中的若干心得。

### 编写高效工具的原则

本节把经验提炼为几条指导性原则。

### 为智能体选对工具

工具越多，结果未必越好。我们观察到的一个常见错误是：只是把现有软件功能或 API 端点包一层就算工具，全然不顾它是否适合智能体。原因在于，智能体相对于传统软件有不同的”可供性（affordances）”——也就是说，它感知”自己能用这些工具采取哪些潜在动作”的方式不一样。

LLM 智能体的”上下文”是有限的（即一次能处理的信息量有上限），而计算机内存便宜且充裕。以”在通讯录里找一个联系人”为例：传统软件可以高效地存储并逐条处理联系人列表，检查完一条再移向下一条。

但如果 LLM 智能体用的工具返回**全部**联系人，它就得逐 token 读完每一条，把宝贵的上下文空间浪费在无关信息上（想象一下为了找联系人，把通讯录从头到尾每页读一遍——也就是暴力搜索）。对智能体和人来说，更好、更自然的做法都是**先翻到相关的那一页**（比如按字母序定位）。

我们建议：先针对少数高影响力工作流，构建几个经过深思熟虑、与评测任务相匹配的工具，再从此扩展。在通讯录的例子里，你该实现 `search_contacts` 或 `message_contact`，而不是 `list_contacts`。

工具可以**合并功能**，在内部处理*多个*离散操作（或 API 调用）。例如，工具可以给响应补上相关元数据，或在一次调用里完成常被串在一起的多步任务。

举例：

- 与其实现 `list_users`、`list_events`、`create_event` 三个工具，不如实现一个 `schedule_event`——它自己找空档并安排会议。
- 与其实现 `read_logs`，不如实现 `search_logs`——只返回相关日志行及少量周边上下文。
- 与其实现 `get_customer_by_id`、`list_transactions`、`list_notes`，不如实现一个 `get_customer_context`——一次性汇总该客户近期所有相关信息。

确保你构建的每一个工具都有清晰、独特的用途。工具应当让智能体像人一样（在拥有相同底层资源时）把任务拆解并解决，同时减少本来会被中间输出消耗掉的上下文。

工具过多或功能重叠，也会分散智能体、妨碍它走高效策略。审慎、有选择地规划”要做哪些工具、不做哪些”，回报非常可观。

### 为工具设置命名空间

你的 AI 智能体将来可能接入几十个 MCP 服务器、上百个不同工具——其中还包括其他开发者写的。当工具功能重叠或用途模糊时，智能体会搞不清该用哪个。

**命名空间**（把相关工具归到共同前缀下）有助于在大量工具之间划出边界；MCP 客户端有时会默认这么做。例如按服务命名（`asana_search`、`jira_search`）、按资源命名（`asana_projects_search`、`asana_users_search`），都能帮智能体在恰当时机选对工具。

我们发现，选择前缀式还是后缀式命名空间，对工具调用评测有不可忽略的影响；且效果因 LLM 而异，建议你依据自己的评测来选命名方案。

智能体可能调错工具、用错参数调对工具、调用次数过少，或错误处理工具响应。有选择地实现那些”名称反映任务自然切分”的工具，你既能减少加载进智能体上下文的工具数量与描述量，又把一部分智能体计算从上下文卸载回工具调用本身，从而降低整体出错风险。

### 从工具返回有意义的上下文

同理，工具实现应当注意**只把高信息量的内容**返回给智能体。要优先保证上下文相关性，而不是灵活性；要避开底层技术标识符（例如 `uuid`、`256px_image_url`、`mime_type`）。像 `name`、`image_url`、`file_type` 这样的字段，更可能直接支撑智能体的下游动作与回答。

相比晦涩的标识符，智能体处理自然语言名称、术语或标识也明显更得心应手。我们发现，仅仅把任意字母数字 UUID 解析成语义更明确、更易理解的语言（甚至换成从 0 开始的 ID 方案），就能通过减少幻觉，显著提升 Claude 在检索任务上的精确度。

某些情况下，智能体确实需要同时拿到自然语言与技术标识符输出，哪怕只是为了触发下游工具调用（例如 `search_user(name='jane')` → `send_message(id=12345)`）。你可以在工具里暴露一个简单的 `response_format` 枚举参数，让智能体控制工具返回 `"concise"`（精简）还是 `"detailed"`（详细）响应。

你还可以增加更多格式以获得更大灵活性，类似 GraphQL 那样精确挑选想要的信息片段。下面是控制工具响应详略的 `ResponseFormat` 枚举示例：

```text
enum ResponseFormat {
   DETAILED = "detailed",
   CONCISE = "concise"
}
```

Slack 会话串及其回复由唯一的 `thread_ts` 标识，拉取回复时必须用到它。`thread_ts` 及其他 ID（`channel_id`、`user_id`）可以从 `"detailed"` 响应中取得，以支撑后续需要这些 ID 的工具调用；`"concise"` 响应只返回会话串内容、不含 ID。在这个例子里，用 `"concise"` 只花了约 ⅓ 的 token。

甚至工具响应的**结构**——XML、JSON 还是 Markdown——也会影响评测表现：没有放之四海皆准的方案。这是因为 LLM 是按”预测下一个 token”训练的，对贴合训练数据的格式表现更好。最优响应结构会因任务和智能体而大不相同，建议依据自己的评测来选择。

### 针对 token 效率优化工具响应

优化上下文的**质量**很重要，优化工具响应返回给智能体的上下文**数量**同样重要。

对于任何可能吃掉大量上下文的工具响应，我们建议组合使用分页、范围选择、过滤和／或截断，并设置合理的默认参数值。在 Claude Code 中，我们默认把工具响应限制在 25,000 token。我们预计智能体的有效上下文长度会随时间增长，但对”上下文高效型工具”的需求会长期存在。

如果你选择截断响应，务必用有用的指令引导智能体。你可以直接鼓励它采取更省 token 的策略，比如在知识检索任务里做多次小而精准的搜索，而不是一次宽泛的大搜索。类似地，当工具调用报错（例如输入校验失败）时，你可以对错误响应做提示工程，清楚传达具体、可执行的改进建议，而不是丢回晦涩的错误码或堆栈跟踪。

### 为工具描述做提示工程

现在来到改进工具最有效的方法之一：**为工具描述与规格做提示工程**。因为它们会被加载进智能体上下文，能够共同把智能体引导向高效的工具调用行为。

写描述和规格时，想象你在向团队里一位新同事介绍这个工具。把那些你习以为常、默认对方知道的隐含上下文——专用查询格式、小众术语的定义、底层资源之间的关系——都明确写出来。清晰描述（并用严格数据模型强制执行）预期输入与输出，消除歧义。尤其输入参数要命名明确：与其叫 `user`，不如叫 `user_id`。

有了评测，你就能更有把握地衡量提示工程的效果。工具描述上哪怕很小的打磨，也可能带来显著改善。我们对工具描述做了精确改进后，Claude Sonnet 3.5 在 [SWE-bench Verified](https://www.anthropic.com/engineering/swe-bench-sonnet) 评测上取得了当时的最优成绩，错误率大幅下降、任务完成率明显提升。

工具定义的其他最佳实践见我们的[开发者指南](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/implement-tool-use#best-practices-for-tool-definitions)。如果你为 Claude 构建工具，还建议阅读工具是如何被动态加载进 Claude [系统提示词](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/implement-tool-use#tool-use-system-prompt)的说明。最后，如果你在给 MCP 服务器写工具，[工具注解（tool annotations）](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)有助于声明哪些工具需要访问开放世界、或会做出破坏性改动。

### 展望

要为智能体构建高效工具，我们需要把软件开发实践从可预测的确定性模式，重新定向到非确定性模式。

通过本文描述的这套迭代式、评测驱动的过程，我们识别出工具之所以成功的若干一致模式：**高效的工具被有意且清晰地定义，审慎地使用智能体上下文，能在多样工作流中相互组合，并让智能体凭直觉就能解决真实世界任务**。

未来，智能体与世界交互的具体机制还会演进——从 MCP 协议的更新，到底层 LLM 本身的升级。只要对工具改进采取系统化、评测驱动的方法，我们就能确保：随着智能体能力变强，它们所使用的工具也会同步进化。
