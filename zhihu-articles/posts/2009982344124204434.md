## 引言

单个GPU卡内存有限，从而引发的各种问题，可分为两个维度来看：

- 数据维度：对于小模型而言，虽然单卡能放下一个模型，但没法放下一个batch所要的全部数据，所以数据得切分到不同卡上计算最终汇总，从而引入数据并行DP
- 模型维度：对于大模型而言，单卡无法放下一个模型，必须将模型切分到多张卡上，由此引入了除DP之外的各种并行（TP/PP/EP/SP），可统称为模型并行

换句话而言，如果模型又小，单个batch数据不多，一张卡跑就够了，也不需要各种并行。

如果模型一张卡能放下，但单个batch的数据放不下，那只需要DP，这样计算效率最高。在这种情况下再加入其他并行策略反而拖累训练效率。

只有在模型单卡也放不下的时候，这时才必须考虑DP之外的并行。不同的并行策略根据模型结构的不同，采取的策略也不一样。

DP/TP/PP/EP/SP都可以同时开启（**EP依赖于DP**，只有DP开启的情况下，才可能开启EP；**SP依赖于TP**，只有在TP开启的情况下才能用SP）。

### 5D并行概览

1. 数据并行（DP）——按批次维度并行
2. 张量并行（TP）——按隐藏维度并行
3. 序列并行 & 上下文并行（SP/CP）——按序列维度并行
4. 流水线并行（PP）——按模型层并行
5. 专家并行（EP）——按模型专家并行

此外，还有三种 ZeRO 策略可以与数据并行结合，以减少内存占用：

| 阶段 | 分片内容 | 显存节省效果（以Adam + 混合精度为例） | 通信开销 |
| --- | --- | --- | --- |
| ZeRO-1 | 仅分片优化器状态 | 显存占用约为原版的 4/16（降低约4倍） | 与标准DP 相同 |
| ZeRO-2 | 分片优化器状态 + 分片梯度 | 显存占用约为原版的 2/16（降低约8倍） | 与标准DP 相同 |
| ZeRO-3 | 分片优化器状态 + 分片梯度 + 分片模型参数 | 显存占用约为原版的 1/16（降低约16倍） | 增加约50%（需额外通信参数） |

> **注**：16倍是基于Adam优化器（fp16参数+fp32状态）的经典计算公式得出的理论峰值。

- **选 ZeRO-1**：模型刚放不下，且你的训练**通信带宽是瓶颈**（如慢速集群）。它不增加通信量，最稳。
- **选 ZeRO-2**：最常用折中方案。能训百亿级模型，且通信量不变，性价比极高。
- **选 ZeRO-3**：要冲击**千亿或万亿**参数时必选。代价是通信变慢，通常需配合**梯度累积**来掩盖通信延迟。如果卡间NVLink带宽不足，ZeRO-3会导致训练速度显著下降。

## Data Parallelism（数据并行）

通过在 DP 秩上分片优化器状态和梯度（相对于传统方法中在数据并行秩上复制优化器状态）来减少内存占用。例如，当使用 Adam 优化器进行混合精度训练时，每个参数占用 12 字节的内存。这会均匀分布在 GPU 上，即，如果我们有 4 个 GPU，每个参数将占用 3 字节（12/4）。

![](https://picx.zhimg.com/v2-1087e85f922b7c73dff8be7205d4f34f_r.jpg)

1. 模型复制：将相同的初始模型复制到所有 `N` 个GPU上。
2. 数据切分：将当前训练批次（Batch）的数据平均分为 `N` 份（子批次，Sub-batch），每个GPU获得一份。
3. 前向传播：每个GPU使用自己获得的子批次数据，独立地进行前向计算，得到局部损失。
4. 反向传播：每个GPU独立地进行反向传播，计算得到相对于当前模型参数和本地数据的局部梯度 `g_i`。
5. 梯度同步：这是最关键的一步。所有GPU通过高速互联（如NVIDIA的NVLink）或网络，使用 `All-Reduce` 集合通信操作，**将所有局部梯度 `g_i` 求和，并将求和结果广播回每个GPU**。这样，每个GPU都得到了全局梯度 `G = Σ g_i`。
6. 参数更新：每个GPU使用这个完全一致的全局梯度 `G`（通常还会除以总样本数 `N` 得到平均梯度，即 `G/N`）来独立地、同步地更新自己本地的模型参数。

数据并行中，梯度相对于不同的训练数据线性的。将数据切分到不同的GPU设备上分别计算梯度，最后将这些梯度相加（或平均），在理论上等价于在单个设备上使用全部数据计算的梯度。

为了减少梯度同步过程中的通信量，可以使用Ring All Reduce的思路。

### **Ring All Reduce**

假设 **P** 是进程的总数，每个进程都由一个 1 到 P 之间的数字唯一标识。如图 2 所示，这些进程构成了一个单向环状结构。

1. **分块（Chunking）**：首先，每个进程将其自身的数组划分为 P 个子数组，我们称之为“数据块（chunks）”。令 `chunk[p]` 代表第 p 个数据块。
2. **初始传输**：接下来，以进程 `[p]` 为例。该进程将自己的 `chunk[p]` 发送给下一个进程，与此同时，它也从上一个进程接收 `chunk[p-1]`。
3. **规约与转发**：随后，进程 `p` 对接收到的 `chunk[p-1]` 与其自身原有的 `chunk[p-1]` 执行**规约操作**（如求和），并将规约后的数据块发送给下一个进程 `p+1`（如图 4 所示）。
4. **循环迭代**：通过重复执行这种“接收-规约-发送”的步骤 **P-1** 次，每个进程最终都会获得结果数组中一个不同的、已完成全局规约的部分。

![](https://pic2.zhimg.com/v2-2d518a614b4da72d2f8d58c39cd52b01_r.jpg)

- **传统的 Data Parallelism (DP)**：在这一步之后，必须紧接着进行 P-1 次 **All-Gather**，把大家手里那 1/P 的结果再拼成一个完整的模型拷贝，然后每个 GPU 才能更新权重。
- **ZeRO**：它说：“既然每个进程现在手里已经有了这 1/P 的完美梯度，那这个进程就只负责更新这 1/P 对应的权重好了。” 这样，每个进程就只需要存 1/P 的优化器状态和权重，从而省下了巨大的内存。

有关详细信息，请参阅研究论文 [ZeRO：迈向万亿参数模型训练的内存优化](https://arxiv.org/pdf/1910.02054.pdf)。

## Pipeline Parallelism（流水线并行）

**流水线并行**的核心思想是将模型的层（Layers）按纵向切分，分布到不同的 GPU 上。

- **分配逻辑：** 若模型有 24 层，4 个 GPU 参与 PP，则每个 GPU 负责连续的 6 层。
- **执行逻辑：** 数据像工厂流水线一样，在 GPU 0 计算完前 6 层后，将中间激活值（Activations）传给 GPU 1，以此类推。

<br>但是这种切分方式会导致其中一个GPU在运算时，其余GPU都要闲置，必须等他运算完再开始计算，所以到导致性能并不是那么好。

### GPipe：Micro-batches

[GPipe: Efficient Training of Giant Neural Networks Using Pipeline Parallelism](https://arxiv.org/abs/1811.06965)<br>论文提出流水线并行方法，相当于模型并行+数据并行，因为数据并行之间是没有关联的，**通过把数据进行更细致的切分，提升模型并行的效率（即减少Bubble时间）**

![](https://pica.zhimg.com/v2-4814971b63d714fe00701dbf86edfba6_r.jpg)

GPipe 提出将一个大的 Batch 切分为 $m$ 个更小的 Micro-batches。

既然不同样本间的梯度计算是独立的，GPU 0 在处理完第一个 Micro-batch 后，立刻将其传给 GPU 1，并同时开始处理第二个 Micro-batch。

气泡率公式： 假设流水线级数为 $p$，Micro-batch 数量为 $m$，气泡占总时间的比例约为 $\frac{p-1}{m}$

。注：当 $m \gg p$ 时，气泡会被极大地压缩。

局限性： GPipe 采用的是 Flush 调度，即必须等所有 Micro-batch 跑完前向，再统一跑反向。这导致 GPU 需要缓存所有 $m$ 个微批次的激活值，显存压力随 $m$ 线性增长。

### **1F1B (One-Forward-One-Backward)**

为了解决 GPipe 的显存瓶颈，**1F1B (One-Forward-One-Backward)** 调度应运而生：

- **执行策略：** 只要某个微批次的前向计算（Forward）一结束，节点就尽可能快地执行其对应的反向计算（Backward）。
- **稳定状态：** 在流水线填满后，每个 GPU 进入“做一个前向、做一个反向”的交替循环。

优势： 激活值在反向传播后立即释放。显存占用只与流水线层数 $p$ 相关，而与微批次数量 $m$ 无关，从而支持更大规模的训练。

![](https://pic3.zhimg.com/v2-8946966ed5bedd881c3c035940c55f5e_r.jpg)

### **交错式 1F1B (Interleaved 1F1B)**

这是由 NVIDIA Megatron-LM v2 提出的进阶方案。

- **非连续切分：** 不再让 GPU 1 只负责第 1-6 层，而是让它负责第 1-3 层和第 13-15 层。
- **效果：** 通过更细粒度的切分，进一步缩短了单个微批次在每个阶段的停留时间。在相同通信开销下，比标准 1F1B 减少了约 **50% 的气泡时间**。

### **Breadth-First Pipeline Parallelism（广度优先流水线并行）**

源自论文《[Breadth-First Pipeline Parallelism](https://arxiv.org/abs/2211.05953)》，Megatron Interleaved 调度的详细解释。

**循环流水线（Interleaved Pipeline）**：

核心思想：让单个微批次（micro-batch）在模型的不同设备间“快速流动”，而不是让一批微批次在流水线中“整体推进”。

- **深度优先（PP_DF）**：**优先处理更早的微批次（Micro-batch）**。它会让同一个微批次在流水线中走完尽可能多的层（即完成整个“循环序列”），然后再处理下一个微批次。这种方式类似于“先纵深挖掘，再横向扩展”。
- **广度优先（PP_BF）**：**优先处理更早的模型阶段（Stage/Layer）**。它让所有微批次尽量同步向前推进，当一个微批次完成某一层的计算后，**立即被送往下一层设备**，而不是等待同一批次中的其他微批次。这种方式类似于“先横向铺开，再纵深推进”。

![](https://picx.zhimg.com/v2-000044fbf0a3a69f01408885e1a95747_r.jpg)

BF-PP能够在保持高GPU利用率的同时，使用**非常小的批次大小（per-GPU batch size）**，甚至可低至理论最小值1。

## Tensor Parallelism（张量并行）

在节点内秩上减少内存占用，而无需太多额外通信。每个张量被分成多个块，每个分片驻留在不同的 GPU 上。在每一步中，同一个小批量数据由每个分片独立并行处理，然后所有 GPU 进行同步（`all-reduce` 操作）。**在一个简单的 Transformer 层中，这会在前向传播中产生 2 次 `all-reduces`**，在后向传播中产生 2 次。

## Sequence Parallelism（序列并行）

参考文章：[【分布式训练技术分享四】聊聊序列并行Sequence parallelism](https://zhuanlan.zhihu.com/p/653067104)

SP 的核心目标是**优化显存占用**，特别是针对 Transformer 中的 **Activation（激活值）**。<br>在标准的数据并行或张量并行（TP）中，有些层（如 LayerNorm 和 Dropout）会在所有显卡上重复计算并保存相同的激活值。在大规模训练中，这部分显存浪费非常严重。<br>既然 TP 已经把权重拆分了，SP 进一步把序列维度 (S) 也切开。原本每个 GPU 都要存整个序列的激活值，现在每个 GPU 只负责存序列的一小部分。<br>**SP**通常与张量并行（TP）结合使用，**通过 `All-Gather` 和 `Reduce-Scatter` 操作在计算时临时同步数据。由于 `all-reduce = reduce-scatter + all-gather`，这在不增加通信成本的情况下节省了大量的激活内存。**

![](https://picx.zhimg.com/v2-4fdae160715d70029ea662115c67d717_r.jpg)

<br>简单来说，**它将每个 Transformer 层的输出沿序列维度分片**，例如，如果序列长度为 `1024`，TP 大小为 `4`，那么每个 GPU 将为每个样本处理 `256` 个标记（1024/4）。这增加了训练所能支持的批量大小。<br>在传统的 TP 中，LayerNorm 的输入输出激活值在所有 GPU 上都是冗余保存的。SP 把这些原本冗余的激活值均匀分布到了各个 GPU 上。<br>假设我们有 4 个 GPU，输入张量的形状是 [s, b, h]（序列长度，Batch 大小，隐藏维度）：

1. **切分维度：** SP 将 s 维度切成 4 份，每个 GPU 拿到 [s/4, b, h]。
2. **计算 LayerNorm：** 因为 LayerNorm 是在 h 维上做归一化，而每个 GPU 手里的 h 维是**完整**的。所以，每个 GPU 可以独立地对自己那部分序列（s/4）进行 LN 计算，完全不需要和别人商量。
3. **无缝衔接：**当进入 **Linear 层（全连接层）** 时，我们需要做 TP 计算。这时通过一个 **All-Gather** 通信，把 s 维度重新拼回来，再把 h 维度切开。计算完 Linear 层后，再通过 **Reduce-Scatter 通信，把 h 维度合起来，同时重新把 s 维度切开，回到 SP 状态**。

> 序列并行与张量并行紧密相关，适用于dropout和层归一化操作。然而，当我们转到更长的序列时，注意力计算将成为瓶颈，这就需要诸如Ring-Attention等技术。为了区分这两种方法，一般称其为“上下文并行（Context Parallelism）”。所以每当你看到序列并行时，请记住，它是与张量并行一起使用的，而上下文并行可以独立使用。

下图是一个完整的示例：（重点看LayerNorm和Dropout层前的处理，之前是(b, s, h)，有了SP并行后就变成(b, s/2, h)，减小了每张GPU上的激活值占用）

**初始LayerNorm（SP区域）**

- 输入张量X1 *和 X2*（b,s/2,h）进入LayerNorm，已经在序列维度上进行分割
- 每个GPU在其序列块上独立计算LayerNorm，并给出Y1 *和 Y2*

**第一次过渡（SP → TP）**

- “g”操作（all-gather）将Y1 *和 Y2*重新组合成完整的序列长度
- 恢复Y（b,s,h），因为列线性需要完整的隐藏维度h

**第一次线性（TP区域）**

- A1是列线性，因此它沿着隐藏维度分割Y
- GeLU在每个GPU上独立应用
- Z1*是（b,s,h/2）

**第二次线性（TP区域）**

- B1是行线性，因此它恢复了隐藏维度
- W1是（b,s,h）

**最终过渡（TP → SP）**

- “g*”操作（reduce-scatter）在进行行线性时减少梯度的正确性，同时在序列维度上进行分散
- W1*是（b,s/2,h）

## Context Parallelism (上下文并行)

解决SP中未完成的self-attention序列并行问题，核心目标是处理极长序列（Long Context），解决 Attention 计算的瓶颈。 在Megatron-LM框架中，CP实现主要思想有两点：

- 用Flash-attention2方式进行分块运算， 最后对分块结果进行修正。
- 设备之间用ring的方式传递KV值来获得分块运算的结果，原理类似ring-attention；

| 特性 | Sequence Parallelism (SP) | Context Parallelism (CP) |
| --- | --- | --- |
| 主要矛盾 | 消除冗余激活值，节省显存 | 解决 O(S^2) 瓶颈，支持超长文本 |
| 切分方式 | 在 Linear/LayerNorm 层切分序列 | 在 Attention 计算中切分序列 |
| 通信模式 | 紧耦合同步 (All-Gather/Reduce-Scatter) | 环形通信 (Ring-based P2P) |
| 对长度的影响 | 适度增加支持长度 | 理论上可线性扩展至极长文本 |

### Ring Self-Attention

[https://arxiv.org/pdf/2105.13120](https://arxiv.org/pdf/2105.13120)

该算法主要解决了 Transformer 模型在处理**长序列**时的显存瓶颈问题。

核心贡献：让每个 GPU 只存一部分序列，却能计算出完整的、等价于单机效果的 Attention 结果。

![](https://pic2.zhimg.com/v2-9b81a68952db0ef4400c85e0ee8c240d_r.jpg)

![](https://pic1.zhimg.com/v2-b94f3b31548407c34924ae0f33e3427e_r.jpg)

> **序列并行能否和TP一起使用，如果可以，具体该如何切分？**

把 GPU 排成一个二维 grid：

```text
GPU(0,0) — GPU(0,1) — GPU(0,2)
  |          |          |
  |          |          |
GPU(1,0) — GPU(1,1) — GPU(1,2)
```

TP：纵向通信（All-Reduce / All-Gather） SP：横向通信（Ring） TP 和 SP 是正交并行：TP 切 head / hidden，SP 切 sequence； Attention 中 TP rank 各算各的 heads，SP rank 通过 Ring Attention 共享 K/V。

## Expert Parallelism（专家并行）

专门用于MoE的

![](https://pica.zhimg.com/v2-cba981383f8e9c53d4aef5a50878e22e_r.jpg)

从架构图中我们可以发现，MoE其实就是将Transformer中的FFN层替换成了MoE-layer，其中每个MoE-Layer由一个gate和若干个experts组成。这里gate和每个expert都可以理解成是`nn.linear`形式的神经网络。<br>首先，所有tokens正常过Attention层得到MoE-layer的输入，我们记输入数据的尺寸为`(S, M)`，其中:

- S : 输入batch中的token数量，例如图中S=8
- M: token_embedding维度

需要注意的是，我们一般是以batch的形式组织输入数据的（图中batch_size = 1），假设Attention层输入数据的维度是`(batch_size, seq_len, M)`，那么有`S = batch_size * seq_len`<br><br>接下来，我们就要使用线形层Gate帮助我们判断token应该送去哪个expert了。在别的MoE架构中，Gate有时也被称为Router（路由）。Gate的尺寸大小为`(M, E)`，其中E表示expert的数量。 输入数据`(S, M)`过Gate`(M, E)`后，得到prob数据`(S, E)`，它的含义是：每个token去向每个expert的概率。 由于在Gshard中我们使用的是top2Expert，因此对每个token，我们只关心它概率最大的两个expert。

![](https://pic2.zhimg.com/v2-56e7ee0ba68377e964985fc812840c45_r.jpg)

**Dispatch 过程**

在 Dispatch 之前，模型的一层（Layer）会输入一堆 Token（向量）。

第一步：门控计算（Gating/Routing） 每个 Token x 会先经过一个很小的线性层（Router），计算它对每个专家的“匹配度”分数。通常我们只取分数最高的 k 个专家（比如 Top-2）。 $G(x) = \text{Softmax}(\text{TopK}(W_g x))$

- 第二步：生成索引与掩码（Indexing & Masking） 系统会记录：Token A 去专家 1 和 5，Token B 去专家 2 和 5。为了并行计算，通常会生成一个巨大的“分发矩阵”（Dispatch Mask）。
- 第三步：搬运（The Actual Dispatch）：触发 All-to-All 通信。

**Combine 过程**

当专家们算完了分配给自己的 Token，我们需要把这些散落在各地的结果收回来，拼回原来的样子。

- 第一步：回收（Gather / All-to-All）：如果用了 EP（专家并行），各张显卡要把算好的结果原路返回，发给 Token 原本所在的显卡。

第二步：加权求和（Weighted Sum）：这是一个关键点。Token A 去了专家 1 和 5，两个专家都会给出一个输出向量。我们要根据之前 Router 给出的权重分数，对它们进行加权。 $Output = G(x)_1 \cdot Expert_1(x) + G(x)_5 \cdot Expert_5(x)$

- 第三步：还原顺序：把所有 Token 按照原始的句子顺序排好，交给下一层（通常是下一个 Attention 层）。

![](https://pic2.zhimg.com/v2-a98876c9011138c2d3b9f54c569c2791_r.jpg)

<br>EP分离的难点在于：<br>1、**负载不均（Load Imbalance）：** 如果 90% 的 Token 都想去 1 号专家，那么 GPU 1 会累死，其他 GPU 都在吃瓜。这会导致整个集群的效率被最慢的那张卡拖死。<br>token发去expert的概率不是我们能控制的，在实际操作中，可能某些expert接收到了好多token，而某些expert接收的token寥寥无几，我们管这种现象叫expert负载不均。我们希望不同expert处理的token数尽量均衡，所以我们同时采取三方面优化：

- Capacity: **为每个expert设置capacity（expert buffer）**，限制它能处理的最大token数量，多出来的token算为溢出，在top2Expert都溢出的情况下，该token会被直接发去下一层attention。
- Random Routing: **每个token一定会被发去1st Expert，在此基础上我们通过random routing加噪的方式，重新选出2nd expert**。在做完capacity + random routing后，我们最终确认了每个token要发去的top2expert和其对应的权重，通过加权计算的方式，确认Moe-Layer最终的输出结果。
- Auxiliary Loss：**添加辅助损失函数**，对expert负载不均的情况做进一步惩罚。

<br>2、**通信瓶颈：** 如果网络带宽不够快，Token 在路上花的时间比 GPU 计算的时间还长，那分布式训练就失去了意义。<br>这就是为什么会有 **Large-EP（优化调度）**和高性能网络（NVLink/InfiniBand）的原因。<br><br>不管是`EP + DP`，`EP + TP +DP`等等，它们都在特指MoE层的并行方式；而对non-MoE层，你采取什么样的并行方式，是不在这些并行符号的表示范围中的。

下图展示了 不同的并行方式的示意图

![](https://pica.zhimg.com/v2-3067c5112c4e9e202a76268782425c66_r.jpg)

(a) Data + Expert Parallelism (DP + EP)<br>GPU1 和 GPU2 拥有**不同**的输入数据（数据并行），但它们也拥有**不同**的专家（FFN1 和 FFN2）。除专家部分外，每张卡都有一份完整的参数，通过 **All-to-All Dispatch**，GPU1 把属于专家 2 的 Token 发给 GPU2，同时从 GPU2 接收属于专家 1 的 Token。<br>**适用场景：** 专家数量较多，且单张显卡能放下几个完整专家的场景。<br>(b) Data + Expert + Tensor Parallelism (DP + EP + TP)<br>当“专家”本身变得非常巨大（比如单个专家的参数量就超过了单张显存）时，就需要引入 TP。看图中的 FFN1 和 FFN2，它们横跨了 GPU1 和 GPU2。这意味着**一个专家被切成了两半**，计算时两张显卡需要协同。**且每个GPU卡都需要有Gate**<br>数据并行（DP）意味着不同的 GPU 组处理不同的 Token。比如 GPU1/2 处理 X_1，GPU3/4 处理 X_2。为了知道 X_1 里的每个 Token 应该发往哪个专家，处理 X_1 的 GPU 必须**立刻**算出路由结果。如果只有某一张卡有 Gate，其他卡还得等它算完传过来，这会产生不必要的延迟。<br>**计算代价极低：**Gate 通常只是一个极小的线性层（全连接层）。相比于动辄几十亿参数的专家层，Gate 的计算量几乎可以忽略不计。**冗余计算**（每张卡都算一遍同样的路由逻辑）的代价远远小于**通信代价**（在一张卡算完后分发路由索引）。<br>**参数的一致性：**在训练过程中，所有 GPU 上的 Gate 参数是通过 **All-Reduce** 保持同步的（就像普通的 DP 分布式训练一样）。这意味着：对于同一个 Token，无论它跑在 GPU1 还是 GPU3 上，Gate 给出的路由目标都是完全一样的。<br>**适用场景：** 这是目前顶级模型（如 175B 以上规模）常用的方案，因为它能同时处理“专家太多”和“单个专家太大”两个难题。<br>(c) Data + Expert + Pipeline Parallelism (DP + EP + PP)<br>这是在纵向（层与层之间）做的切分。模型被切成上下两段。GPU1 和 GPU2 负责处理模型的前几层（Stage 1），算完后再把结果传给负责后几层（Stage 2）的 GPU3 和 GPU4。在每个 Stage 内部，依然保持着 DP 和 EP 的结构。<br>**适用场景：**主要用于解决超大规模集群中的层数堆叠问题，能进一步降低单张卡的显存压力，但会引入流水线气泡（Bubble）。<br>(d) Expert + Tensor Parallelism (EP + TP)<br>这种方式更强调在**计算专家层时的极致加速**。<br>与 (b) 不同，这里没有明显的 DP 组。所有的 GPU 共同维护一组专家。注意图中的 Self-Attention 层也做了横向切分（TP）。这意味着不仅专家层，连注意力层都是分布在不同 GPU 上的。<br>**特点：** 这种配置下，通信非常频繁（既有 TP 的 All-Reduce，又有 EP 的 All-to-All），通常只在具有极高带宽（如 NVLink 直连）的机柜内部使用。
