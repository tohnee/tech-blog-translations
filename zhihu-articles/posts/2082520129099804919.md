**第 6 族｜GraphRAG：把"知识之间的关系"也利用起来**

**这一族解决什么**：普通 RAG 里块与块互不认识。问"这批资料整体讲了什么主题""A 和 B 之间什么关系""跨三份文档才能推出来的结论"时，普通 RAG 抓瞎。GraphRAG 先把知识连成"关系网"（图），再从网上取料。

**先记住一个总结论**（Is GraphRAG Needed? 等实证）：**具体的事实问答（答案就在原文某段）用普通 RAG 就够，硬上纯图方案反而可能因为丢了原文而变差**；图的价值集中在"全局总结"和"多跳关系推理"两类问题上。

### **6.1 微软 GraphRAG：先建"知识图谱+社区摘要"，专攻全局问题 ◐**

普通 RAG 拿"这个语料库整体在讲什么主题？"完全没办法——答案不在任何一个块里，它分布在整库之中。微软 GraphRAG 就是为这类"全局性、综述性"问题设计的。它的做法分四步走：第一步，用 LLM 把全部语料扫一遍，抽取实体和关系，建成一张"谁认识谁、谁属于谁"的知识图谱；第二步，用 Leiden 算法把图上抱团紧密的节点一层层划成"社区"——类似把人分成小区、楼栋、住户的层级；第三步，**逐个社区让 LLM 写摘要报告**，自底向上，低层社区摘要再聚合成高层摘要；第四步才是查询——遇到"整库讲什么"的全局问题，挑出相关社区的摘要喂给模型，多份摘要分片生成再归约汇总；遇到局部问题则走实体匹配加邻居扩展的传统路线。

它在"全局综述、主题归纳"这类问题上确实是标杆，代码也开源了（microsoft/graphrag）。但成本要敢看：逐社区 LLM 摘要的 token 消耗比树索引方案高一个数量级，一个中等语料库的建图费用可能让人咋舌；语料更新还得重跑社区发现；而对普通的单点事实问答，它并不比普通 RAG 强，甚至因为摘要丢了原文细节而更差。

结论很清晰：只有"全库综述"是真实需求、且预算经得起烧，才上它。实用性 **◐**。

用一个具体例子走一遍微软 GraphRAG 的全局查询流程，感受它为什么贵、又为什么值得。假设语料是某公司五年的全部会议纪要，用户问"这几年公司的战略重心发生了哪些变化？"。普通 RAG 会检索出几段跟"战略"沾边的纪要，答案支离破碎。微软 GraphRAG 的管线则是：建图阶段已经把"某项目""某部门""某高管"这类实体连成了网，并聚出了层级社区——低层社区可能是"某产品线项目群"，高层社区可能是"公司级战略举措"；查询阶段，系统判断这是全局问题，把相关高层社区的摘要（比如"2021-2023 社区摘要：重心在硬件出海；2023-2025 社区摘要：转向 AI 平台"）分发给多个 LLM 并行生成要点，最后归约成一份综述。你看，答案的原料根本不是任何一段原文，而是抽象一层的摘要网络——这就是它贵的原因（要维护这张摘要网），也是它独有的能力（普通检索永远拼不出这种视角）。

**实际案例：**集团管理者问“过去三年研发投入下降的原因是什么”，答案分散在财报、会议纪要和项目复盘里，GraphRAG 可以先做社区摘要，再从多个部门的关系网里汇总全局结论。 具体做法：先用 LLM 把实体和关系抽出来，再做社区发现和社区摘要；全局问题先读摘要，局部问题再回到原文。建图和摘要成本较高，适合把“讲清楚整个库”作为核心需求的场景。

### **6.2 LightRAG：省掉社区摘要的"轻量版 GraphRAG**

微软 GraphRAG 最烧钱的就是第三步——给每个社区写摘要。LightRAG 的立场很明确：这步我省了。它同样建一张"实体+关系"的图，但不写逐社区摘要，而是**给节点和关系打标签、分成两层**——低层管细节事实，高层管抽象主题。检索时按问题的粗细定位：问具体的事就去低层找，问宏观的主题就去高层找，在对应层用关键词在图上圈出相关子图，最后把"图结构 + 原文块"一起交给模型。

相比微软方案它便宜得多，还支持增量更新——新文档进来只动图的局部，不用全量重建，这对持续运营的知识库是刚需。开源实现成熟、社区使用广泛，是"想上轻量图 RAG"的默认选择。

代价也别忽略：语料级的宏大综合（"整库讲了什么"）它还是不如微软 GraphRAG——毕竟没写社区摘要；建图本身仍要 LLM 抽实体，token 成本仍是树索引的数倍，只是比社区摘要方案低了很多。实用性 **★**（图方案里最值得先试的）。

LightRAG 的双层关键词设计值得再看一眼，因为它体现了图方案里少见的"成本自觉"。低层关键词对应具体实体和事实——"A 公司""收购案"，检索时直接锚到图的局部；高层关键词对应抽象主题——"行业整合趋势""监管风险"，检索时沿图的邻域扫出一片相关子图。打标签这个动作在建图时一次完成（给每个实体和关系标注它属于哪些高层主题），查询时按问题粒度选层，避免"问宏观主题却检索到一堆孤立三元组"的常见失败。增量更新是它的另一个工程亮点：新文档进来，只抽取新实体、更新涉及节点的邻域标签，社区结构不需要重算——对比微软 GraphRAG "语料一变就要重跑社区发现"的运维成本，这个差异在长期运营中会被急剧放大。代价前面说过：没有社区摘要，"整库综述"类问题它接不住，这类问题要么转给 RAPTOR 路线，要么在业务上明确不支持。

**实际案例：**工厂知识库既有“某阀门怎么换”的细节，也有“整条产线有哪些风险”的高层主题；LightRAG 用低层实体和高层主题两级检索，避免只会找局部句子。 具体做法：LightRAG 保留低层实体关系和高层主题两个入口，减少全量社区摘要的成本，并支持更轻量的增量更新。上线时要分别测试局部事实题和跨主题总结题，确认轻量化没有牺牲覆盖面。

### **6.3 HippoRAG：把"多跳联想"变成一次图上的"水流扩散" ◐**

人脑记忆有个特点：一提起 A，顺着关联就想到 B、再想到 C——联想是顺着关系网自然扩散的。HippoRAG 受海马体记忆机制启发，把这种联想变成了图上的数学操作：先建好实体关系图，同时维护"实体 → 原文段落"的映射表；查询时把问题里的实体当作"水源"，在图上跑一次**个性化 PageRank**——能量沿着关系边向四周扩散，和问题实体关系越紧密的节点聚到的"水"越多；最后按能量排序，把高分实体对应的原文段落捞回来。

这个设计的精妙在于**一次检索完成多跳联想**：不需要"先查 A、再查 B"的多轮循环，能量扩散天然覆盖了多跳关联，所以它在 HotpotQA 这类多跳基准上明显强于普通检索，成本却只相当于一次检索。

风险集中在图的质量上：实体抽取得烂，图就是烂的，扩散出来的也是噪音。另外它只召回"提到相关实体"的段落，对需要整段语义理解的任务不合适；新版 HippoRAG v2 开始考虑和树摘要结合来补这块短板。实用性 **◐**。

HippoRAG 的适用判别可以总结成一个"联想测试"：**如果回答这个问题需要"由一个概念自然联想到另一个概念"，它就对口**。比如"和 X 公司用同一套供应链的还有谁？"——这需要从 X 联想到供应链节点、再联想到其他公司，典型的多跳联想，PPR 扩散一次就能把相关实体都带出来。反过来，"X 公司的财务状况怎么样？"是单点定位问题，普通检索直接命中，用 PPR 反而多绕一圈。工程上它还有个容易被忽略的运维特性：图谱构建一次之后，查询阶段的 PPR 是纯图计算，不花 LLM 调用——相比每跳一次 LLM 的 ToG 路线，它的查询成本几乎可以忽略，这对高并发场景是个实打实的优势。实体抽取的质量问题可以靠"抽取时带置信度、低置信实体不建边"来部分缓解。

**实际案例：**个人助理记住“用户喜欢早班机、不要红眼航班”，以后订票时不必再次翻完整聊天记录，只需在记忆图上沿用户—偏好—航班条件做联想扩散。 具体做法：把问题中的实体作为种子，在图上做关系扩散或个性化 PageRank，再从高分节点回取原文。扩散半径和候选数必须设上限，否则一个热门实体会把大量无关邻居带进答案。

### **6.4 RAPTOR：不建图也能有"全局视角"——递归摘要树 ★**

不想花大钱抽实体建图，又想要"全局感"？RAPTOR 给了一条绕开图的路线：**把相似的块聚成团，每团让 LLM 写一句摘要，再把摘要往上聚，形成一棵"摘要金字塔"**。它的实现很干净：底层是原文块，用 GMM 聚类把语义相近的块归团，每团生成摘要成为上层节点，对摘要递归聚类，直到塔顶。查询时叶子和各层摘要一起参与检索，谁和问题像就取谁——问细节自然命中叶子，问全局自动命中高层摘要。

相比图方案，它的好处是没有"关系边"这个甜蜜的负担：不用抽实体、不用对齐 schema，成本可控，是**最便宜的"准图式全局能力"**。在"具体问答为主、偶尔要全局总结"的典型业务里，它往往比直接上 GraphRAG 更划算——这也是为什么附录选型里把它排在图方案之前。

短板同样源于"没有边"：跨实体的多跳关系推理它做不了，聚类不稳定时树结构会漂，摘要层还可能引入失真。实用性 **★**，全局需求的第一选择。

RAPTOR 实操中还有一个取舍点：**摘要层的"厚度"**。摘要写得太薄（一句话），全局问题检索到了也缺细节，还要下钻一层，延迟上去；写得太厚（几段），摘要层的向量彼此相似，检索区分度下降。实测较优的做法是每簇摘要控制在 150 到 300 字，并且**摘要时强制保留关键实体和数字**——普通摘要会把这些"可检索的锚点"稀释掉，导致摘要层根本检索不到。另一个技巧是摘要层不做 embedding 检索、而是用 BM25 检索：摘要文本短而信息密，关键词匹配反而更准，还省一套向量索引。RAPTOR 和 1.5 的其他树方案、6.1 的社区摘要方案在"摘要怎么写"这个问题上是共通的，这套经验可以通用。

RAPTOR 为什么是"最便宜的准图"值得算一笔账。它对文档块递归做聚类（GMM 软聚类，允许一个块属于多个簇），每簇用 LLM 生成摘要，摘要再聚类再摘要，直到形成金字塔；检索时问题可以命中叶子（原文细节）也可以命中高层节点（全局概括），检索器只需在"树的所有节点平铺成的向量集合"里做普通 ANN。对比微软 GraphRAG：省掉了实体抽取（这是最烧 token 的一步，社区摘要建图的 token 开销可达树索引的数十倍）、省掉了社区检测、省掉了全局/局部两套查询管线，代价是没有显式的实体关系边，做不了"A 和 B 什么关系"这种精确多跳。所以选型判据很清晰：**问题以"概括/综述/主题"类为主，RAPTOR 够用且便宜一个数量级；问题里有大量实体间关系推理，才需要真建图**。RAPTOR 树的维护也简单——文档更新只需对增量块重新聚类挂树，不用像 KG 那样处理实体对齐。

**实际案例：**面对几百页投研报告，RAPTOR 的叶子节点可以回答某季度收入，上层摘要可以回答“公司增长主要靠什么”，同一份资料支持不同粒度的问题。 具体做法：RAPTOR 先对叶子块聚类、摘要，再递归形成更高层摘要；局部题落到叶子，全局题从上层开始找。摘要只能帮助定位，最后仍要回到原始段落做事实核对。

### **6.5 领域知识图谱注入（KAG / CommunityKG-RAG / KG-RAG）：手里有图就把它用起来 ★**

很多行业**本来就有一张高质量的专业图谱**：药品-疾病-禁忌、法规条款-处罚情形、公司股权穿透……如果 RAG 系统完全无视它，等于捧着金饭碗要饭。这一族策略的核心是"把图上的知识也喂给模型"。KAG（蚂蚁开源）解决了最关键的"模型和图各说各话"问题：把自然语言问题翻译成能对着图谱执行的逻辑查询，图上查回的结果再和文本证据互相校验，两边对得上才往答案里放。CommunityKG-RAG 换了个切入角度：把"图上的一簇关系"当检索单元——一簇关系本身就自带上下文，比单条三元组信息密度高。KG 路径选择一类工作则研究怎么在图上挑出最相关的推理路径喂给模型。

通用落地流程是三步：实体链接，把问题里的词锚定到图谱实体；图检索，取出相关三元组或社区；图结果与文本块双通道进上下文，交叉验证后作答。

这是垂域（医疗/法律/金融）手里有现成结构化知识时的首选路线——图谱自带的确定性是任何向量检索都给不了的可信度。成败完全押在图谱质量和实体链接上：schema 对不齐、实体链接错，后面全错。有图就用，实用性 **★**。

KAG 这类"领域 KG 注入"方案的落地细节值得展开。它的核心主张是：专业领域（金融、政务、医疗）本来就有高质量的知识图谱或结构化资产（术语表、分类法、业务规则），RAG 应该把它们"请进来"而不是从零用 LLM 抽图。**KAG 的知识构建器做三件事：把结构化资产对齐到统一的 schema（实体消歧、单位归一**）；把非结构化文档抽出的三元组与 KG 对齐（这一步用 LLM+规则混合，规则管格式、LLM 管语义）；给每个知识单元挂上逻辑形式的可执行表示（logical form），查询时可以直接编译成计算。求解器则在回答时做"推理规划"——把问题拆成多个知识单元的查取与运算，逐步执行。这套东西重在建库工程，但对已有 KG 的机构，它把" KG 和文档两张皮"缝成了一体，官方报告在政务场景的准确率远超纯向量 RAG。关键判断依据：**手里有没有高质量领域 KG？有，这条路性价比极高；没有，先掂量建 KG 的成本**。

### **6.6 查询时图上逐跳推理（Think-on-Graph / Fast ToG）：让模型在图上"一步一个脚印"地走 ◐**

前面几招的共同模式是"先把图的相关部分切下来喂给模型"，推理本身还是模型在文本上完成的。Think-on-Graph（ToG）换了个玩法：**让模型真的在图上一跳一跳地走**。从问题里的实体出发，每一步让模型在候选关系里挑"最可能通往答案的那条边"，走到答案节点或者走不动为止——像在地图上按路标步行，而不是把整张地图塞进脑子。

Fast ToG 在此基础上限制每步的宽度和深度、加剪枝，让它走得更快更远；ToG 2.0 加入了知识引导的检索增强，让每步选择更有依据；StepChain 则把"逐步推理"用在多跳问答的全流程上。

它最适合的场景是**显式关系链推理**："X 的供应商的供应商有没有资质问题？"这种问题必须沿着关系边走，普通检索根本无从下手。

但两次大规模实证都给这项技术泼了冷水：每跳一次 LLM 调用，又慢又贵；图不完整的地方直接无路可走；更扎心的是，在大多数"具体问答"任务上，它的表现**反而不如普通 RAG**——很多看似需要"图推理"的问题，其实文本检索就能答对。所以务实定位是：只给明确要沿关系链走的问题开这条路，别当默认。实用性 **◐**。

**实际案例：**反洗钱调查要从账户走到公司、股东和关联交易，系统每走一步都验证当前证据，再决定下一跳，能把“看起来相关”的节点挡在路径外。 具体做法：让模型每走一跳都读取当前邻居和证据，再决定下一跳，而不是事先盲走固定路径。设置最大跳数和每跳停止条件，路径过长或关系不明确时转回文本检索或请求澄清。

### **6.7 子图检索（SubgraphRAG / GRAG / GEAR）：捞"相关的那一小块图" ◐**

整张图太大，不可能喂给模型；逐跳走又慢。第三条路是折中：**以问题实体为中心，往外扩一圈，把相关的那一小块图（几十条三元组）捞出来**，格式化成文本交给模型。SubgraphRAG 把这条路线打磨得最实用：用结构距离和方向控制子图扩展的形状，甚至训练了一个轻量编码器来打分子图相关性——8B 的小模型配合它也能打出接近 GPT-4 的 KGQA 水平。GRAG 多留了个心眼：捞出来的子图可能结构残缺，它专门检查图的连通性和完整性，缺了就补。GEAR 更进一步，训练一个专职的"捞图 agent"，让它学会怎么在图上定位最有价值的区域。

**对有 KG 的垂域——医疗实体关系问答、金融风控关联分析——这是主力方案之一：比整图便宜、比逐跳快、还给模型保留了足够的结构信息。**

依赖项也很清楚：实体链接的质量决定子图的起点对不对；适用面偏知识图谱问答，对自由文本为主的语料没得用。实用性 **◐**。

### **6.8 把图算法做成工具给模型调（GDS Agent / Graph RAG Tool Fusion）★**

很多所谓的"图问题"根本不需要模型在图上瞎推理。"谁在集团里人脉最广？"——跑一遍 PageRank，答案秒出。"A 和 B 之间隔几层关系？"——最短路径算法一步到位。让 LLM 靠"想"去回答这些问题，又慢又容易错；正确姿势是**把这些成熟图算法封装成工具，让模型学会"该查算法就调算法"**。GDS Agent 就是这么干的：把 Neo4j GDS 里的 PageRank、社区发现、最短路等算法暴露成工具接口，LLM 接到问题后判断该调哪个工具、传什么参数，把算法返回的数值和局部子图再组织成自然语言答案。Graph RAG Tool Fusion 研究的也是"模型与图算法工具的融合调度"，TuGraph 这类国产图平台也在往这个方向做配套。

这条路线的价值在于**用确定性对抗幻觉**：图算法的结果是精确的，LLM 只负责翻译和叙述，不负责计算。已有图库的项目可以直接套，几乎是从零成本到高收益。

要注意的坑：模型得把自然语言正确翻译成图查询或算法选择——翻译错了结果就错，所以要配重试和参数校验机制。实用性 **★**。

**实际案例：**物流调度助手遇到“从仓库 A 到门店 B 哪条线路风险最低”，可以调用最短路、中心度和故障边统计等图算法，再让模型解释为什么选这条路径。 具体做法：把最短路、中心度、连通性、社区发现等图算法封装成小工具，模型只负责选择工具和解释结果。每个工具要有输入约束和超时，避免模型用图算法替代业务规则。

### **6.9 动态/事件/因果图谱（DyG-RAG / EventRAG / CausalRAG / EraRAG）：给图加上"时间、事件、因果" ◐**

普通实体图是一张"静态关系网"，它缺三样东西：**时间**——事情是几月发生的？后来变了吗？**事件过程**——发生了什么、谁参与、先后顺序如何？**因果**——到底是谁导致了谁，别把"相关"当"因果"。这一族工作分别在图上补这三样：DyG-RAG 以事件为中心做动态图的检索推理；EventRAG（ACL 2025）把事件知识图谱接进生成流程，让模型叙述事件链时有序可循；CausalRAG 干脆把因果图融进来，检索时沿着因果边走，防止模型把相关关系错当因果关系。EraRAG 解决的则是另一个实际到不能再实际的问题：**语料一直在涨，图怎么增量维护**——新文档只更新图的局部区域，不用全量重建，这让图方案在持续更新的业务里变得可行。

这些方向的共同实现套路是：

靠 LLM 做事件抽取、时间标注、因果标注，建对应类型的图，检索时把时间线、事件链或因果链作为骨架喂给模型。

适用场景对得很准：新闻追踪、病历时序、风控归因。但事件/因果标注的成本高，通用性弱，属于垂域专项投入。

动态/事件/因果这条线的各个方案针对的问题形态差异很大，值得分清楚。DyG-RAG 处理"随时间变化的事件"：从文本里抽"事件-时间-地点"三元组，按时间轴组织成动态图，查询"某时间段发生了什么、事件之间时间顺序"时沿时间轴检索，解决静态索引"新旧混杂、时序混乱"的老问题。

EventRAG 用事件知识图谱（ACL 2025）把新闻流组织成事件节点，同源多报道聚合到一个事件下，适合舆情、突发新闻类语料。

CausalRAG 最激进：把因果图（而不是相关图）作为检索的骨架，回答"如果 X 会怎样"这类反事实/干预问题时，沿因果边检索"被干预节点的下游证据"，避免把"相关"当"因果"的推理错误。三者共同的工程现实是：抽事件/因果的准确率远低于抽实体，关系错了图越准检索越偏，所以上线前必须对抽取质量单独建评测。时序类（DyG/Event）落地门槛较低，因果类目前研究性质更浓。

CausalRAG Integrating Causal Graphs into Retrieval-Augmented Generation<u>[arXiv]</u>；

**实际案例：**分析一次设备故障时，不只记录“设备和部件有关”，还记录发生时间、先后事件和可能因果；系统才能回答“哪次维护之后故障率开始上升”。 具体做法：事件图要记录事件类型、参与者、时间和顺序，因果图还要区分“相关”和“导致”。增量更新只重算受影响的局部图，并单独评测事件抽取和因果判断的错误率。

### **6.10 目录里更多图方案速查（一句话定位，细节见原文）**

论文库里还收了一批各有侧重的图方案，这里一句话给个定位，细节按名翻原文。垂域建图检索一派：Do-RAG 从领域文档里抽知识图谱再检索，DSRAG 专做"文档衍生的多模态知识图谱"（GraphRAG/ 同名文件）。新派轻量图一派：NodeRAG 用异构节点入图、MiniRAG 面向小模型友好场景、Mixture-of-PageRanks 用实时稀疏图替代长上下文。

把图 RAG 做成 agent 的一派：GraphSearch 设计多轮图搜索工作流、Youtu-GraphRAG 做垂直领域多智能体分工、HetaRAG 跨异构数据源协同。

评测与反思一派：GraphRAG under Fire 专门挑 GraphRAG 的毛病，In-depth Analysis 把各家图方案塞进统一框架做横向剖析，LEGO-GraphRAG 把图 RAG 拆成可组合模块做设计空间探索。

综述一派：Graph Retrieval-Augmented Generation Survey、A Survey of Graph RAG for Customized LLMs 等，查谱系先看它们。医疗法律垂域还有 Medical Graph RAG、Biomedical KG、LegalGraphRAG、CuraView 一批专项工作。这些方案大多还在"论文到产品"的半路上，选型时优先 6.1 到 6.8 那几条被反复验证过的主线。<br>DO-RAG<u>[arXiv]</u>；<br>DSRAG<u>[arXiv]</u>；<br>LEGO-GraphRAG<u>[arXiv]</u>；<br>LEGO-GraphRAG<u>[arXiv]</u>。

GraphRAG 是整个技术栈里"期望管理"最重要的板块，这里把成本账和决策账摊开算一次。

**成本侧**，以一个一万篇文档的库为例：RAPTOR 的两级摘要大约几千次 LLM 调用；LightRAG 建图要抽取实体关系，调用量上一个台阶；微软 GraphRAG 的社区摘要是数量级式的开销，外加每次语料更新的重算。**收益侧**，这三种方案吃的是不同的问题：RAPTOR 吃"跨章节总结"，LightRAG 吃"主题关联与增量更新"，微软 GraphRAG 吃"整库宏观综述"。所以图方案的决策顺序永远是：**先确认"全局性问题"在你的业务里占比有多少——低于一成，RAPTOR 就够；占比可观且语料常更新，LightRAG；确有"给我讲讲整个库"的产品需求且预算充足，才轮到微软 GraphRAG。**

另一条容易走偏的路是 ToG 式逐跳推理（6.6）。它看起来"最智能"，实证却显示大多数具体问答上不如普通 RAG。一个务实的判别法：**把问题里的关系链用箭头写出来**——能写成一跳到两跳的（"A 的供应商"），普通检索加重排就够；必须三跳以上且每跳都有明确定义关系（"A 的供应商的供应商是否有诉讼"）的，才真的需要图推理或 PPR 类方案（6.3）。

给垂域团队一个组合建议：医疗、金融这类手里有专业图谱的场景，最优解通常是**双通道**——普通文本管线管自由问答，图谱通道（6.5 实体链接 + 6.8 算法工具化）管关系与计算类问题，入口路由（4.2）决定走哪边。这套架构把"图的确定性"和"文本的覆盖面"各用其长，比任何单通道都稳。

**实际案例：**同一个项目若有图表 PDF、领域知识图谱和通信网络数据，不必强行只选一种 GraphRAG；先看数据形态，再选 **DO-RAG、DSRAG、LEGO-GraphRAG**等更合适的路线。 具体做法：速查表适合做方案初筛：先按数据形态选多模态图、轻量图、图 Agent 或模块化方案，再用小样本比较质量和成本。不要因为名字里有 GraphRAG 就默认它比混合检索更适合。

### **6.11 图不是越复杂越好：先做适配性测试**

GraphRAG 很适合回答“谁和谁有什么关系”“沿着几跳关系找答案”“把一堆资料归纳成全局主题”这类问题，但不代表所有问题都应该上图。When to use Graphs in RAG 和 GraphRAG under Fire 都提醒了一件很实际的事：图的构建、更新和查询都有成本，不能只看离线准确率。

上线前可以把问题分成几类做小实验：事实查找、关系/路径、多跳推理、全局总结、时间敏感问题。分别比较向量检索、图检索、混合检索和迭代检索，并把答案质量、延迟、建图成本、更新难度一起记下来。最后让路由器把“确实适合图”的问题送进图，而不是把图当成默认答案。<br>

### **7.1 先把文档中的实体和关系抽出来**

图谱 RAG 的第一步不是建库，而是从合同、订单、报告和工单中识别实体、关系、属性、时间和来源。ChatIE、RUIE、OneKE 等工作说明，抽取最好做成有 schema 的任务，而不是让模型自由发挥。

一个关系如果没有原文句子、页码和置信度，后面沿图推理时就很难判断它是真是假。

实际案例（白话）：制造企业要回答“哪些供应商给哪条产线供过货，并且最近一次是否发生过延期”。系统先从采购单抽供应商、产线、批次和日期，再从工单抽延期事件，把每条边绑定到原始单据。查询时先沿供应商到产线的关系找候选，再按日期过滤延期记录，答案中列出批次和证据单号，而不是只给一个供应商名字。<br>

### **7.2 Schema 和本体决定图能不能长期维护**

临时知识图谱可以边抽边长，企业图谱却需要统一的实体类型、关系名称、单位、状态和时间语义。AutoSchemaKG 这类工作提供了自动发现 schema 的思路，但候选 schema 仍需要业务确认。

本体的作用不是增加名词，而是让“订单已发货”“订单已签收”“订单已取消”这些状态有清楚的边界和时间条件。

实际案例（白话）：零售企业把“客户、订单、商品、仓库、配送”建成统一本体。客服问“这单为什么还没到”时，系统不是全文搜索“没到”，而是查订单当前状态、配送节点、承诺时间和异常规则；如果订单已经签收但客户说没收到，系统转入争议流程，不把“签收”简单改写成“已完成”。<br>

### **7.3 图谱不是事实数据库，还要保留来源和时间**

同一实体可能在不同时间有不同状态，同一关系也可能来自不同可信度的来源。图上的边应至少带来源、时间、生效状态和置信度，检索时按问题时间点选择有效事实。

对冲突事实不要简单覆盖，保留冲突本身，必要时让 Agent 触发进一步核验。

实际案例（白话）：保险条款图谱中同一产品有 2024 和 2025 两个版本，且不同地区的等待期不一样。用户问“我在上海投保的 2025 版保单能否报销”时，系统先用地区、投保日期和版本筛选，再沿产品到疾病和等待期关系查证；旧版本仍保留，但不会被当前问题误召回。<br>

![](https://pic1.zhimg.com/v2-6ba2efc1a93b6ed3421326904e1c60e4_r.jpg)
*图：图谱关系需要沿路径保留时间、来源和核验状态（依据 [30][32] 整理绘制，非论文原图）*

### **7.4 个性化图谱要分开公共事实和个人偏好**

PersonaAgent 这类工作把个人历史、社区信息和图结构结合起来，让同一个问题能根据用户偏好得到不同的上下文。工程上要把公共事实、用户偏好和临时任务状态分层，且每层都能单独删除和更新。

实际案例（白话）：学习助手知道学生最近在准备生物竞赛，但不能因此把所有问题都解释成生物问题。用户问“推荐一本入门书”时，系统同时检索公共书籍知识和用户已经读过的书，最后说明“这是根据你的阅读记录做的推荐”；用户修改偏好后，下一次检索只使用新偏好。<br>

### **7.5 什么时候不要上 GraphRAG**

如果问题主要是找原文、查最新公告、处理高频 FAQ，混合检索和重排通常更便宜。图谱建设需要 schema、实体对齐、关系抽取、更新和冲突处理，只有当关系推理、跨文档连接或结构化约束确实是核心需求时才值得投入。

实际案例（白话）：客服团队想解决“退货多久到账”这类高频问题时，先做版本过滤、关键词加向量召回和规则校验就能覆盖大多数请求。只有当问题升级为“这次订单涉及的供应商、合同约定、历史异常和当前政策是否互相冲突”时，才引入订单、合同和供应商之间的图关系。这样图谱服务的是难题，而不是替代所有检索。

![](https://pic3.zhimg.com/v2-3ed5a7d1fb4ee38ba4ddba4d389edb66_r.jpg)
*图：是否采用 GraphRAG 要同时比较问题类型、质量、延迟、建图成本和更新难度（依据 [7][8] 整理绘制，非论文原图）*

### **7.6 图谱构建先过质量门禁**

图谱 RAG 的第一道风险不在推理，而在建图。实体可能重复，关系可能抽错，别名可能没有对齐，时间和来源可能丢失。建议给实体和关系都设质量门禁：实体是否能回到原文，关系两端是否类型正确，来源是否明确，时间是否完整，置信度是否达到阈值。低置信度内容可以进入候选区，但不要直接成为强证据。

实体对齐也不能只看字符串相似度。公司简称、产品型号和人名经常重名，最好结合类型、上下文、时间和外部标识做判断。图谱中的每条边都应能回指原文片段，后续发现错误时可以删除或修正，而不是只能整库重建。

实际案例（白话）：制造企业想查“哪些供应商给哪条产线供过货，最近一次是否延期”。系统先从采购单、入库单和工单中抽实体与关系，再检查供应商简称是否对应同一个统一编号。发现两个名称相近的供应商其实不是同一家公司后，系统拒绝合并，并把这条关系标成待确认。这样最终答案少了一条未经确认的关系，却比看起来完整但混淆供应商的答案更可靠。怎么落地：图谱上线前抽查实体合并、关系方向、时间和来源四类错误。

![](https://pic3.zhimg.com/v2-3ed5a7d1fb4ee38ba4ddba4d389edb66_r.jpg)
*图：图谱上线前应把实体对齐、关系方向、时间和来源纳入质量门禁（依据 [25][27][31][32] 整理绘制，非论文原图）*

### **7.7 本体设计不要一开始就把所有业务统一成一套**

企业本体不是把所有名词列成一张大表。更实用的做法是先确定少数稳定概念：客户、合同、订单、产品、供应商、事件和时间，再把领域特有概念作为可扩展层。稳定层负责跨系统连接，业务层负责回答具体问题，避免一开始就定义几百种关系，最后谁也不敢维护。

关系名称也要写清楚方向和条件。“供应商—服务—产线”和“供应商—曾经服务—产线”不是一回事，后者带有时间边界。查询时模型可以使用自然语言，但底层 schema、枚举值和关系约束必须稳定，否则同一个问题今天走“供货”，明天走“合作”，结果无法比较。

实际案例（白话）：零售企业把“客户、订单、商品、仓库、配送”接进统一知识库。客服问“这单为什么还没到”时，只需要订单、物流节点和承诺时间；客服问“这个客户过去半年是否经常退货”时，才需要客户和历史订单的聚合关系。两类问题共享基础概念，但不必把所有业务细节都塞进同一张超级图。怎么落地：先为高频问题建立最小 schema，新的概念必须有实际查询需求和维护负责人。<br>

*图：本体设计先建立少量稳定概念，再按查询需求扩展业务层（依据 [28][29][30] 整理绘制，非论文原图）*

资料依据：见文末参考资料 [28] AutoSchemaKG、[29] Knowledge Graph Guides Large Language Model for Domain Question Answering、[30] Palantir Foundry Ontology。最小稳定 schema 和可扩展业务层的建议是本文的工程归纳。

### **7.8 图、向量和 SQL 按问题分工**

向量检索擅长找相似内容，图谱擅长沿关系找路径，SQL 擅长精确过滤和计算。真正的企业 RAG 通常需要一个路由层：问原文时优先向量和关键词，问“谁和谁有关”时走图，问金额、数量、同比时走 SQL。复杂问题可以先分别取证，再统一合并。<br>

![](https://pic1.zhimg.com/v2-6ba2efc1a93b6ed3421326904e1c60e4_r.jpg)
*图：路由层按问题类型选择向量、图或 SQL，并统一保留证据（依据 [1][7][8][30] 整理绘制，非论文原图）*

路由的判断最好由问题中的动作和对象共同决定，而不是只看关键词。比如“某客户为什么流失”可能需要订单数据、客服记录和合同条款；“某客户和哪些供应商存在关联”则更适合沿图查关系。系统要把每条结果保留来源、时间和粒度，不能把 SQL 数字和文本摘要混成一句没有出处的话。

实际案例（白话）：金融风控助手收到“这家公司是否通过关联公司间接暴露在受制裁主体风险下”。它先用图谱沿股权和控制关系找路径，再用文档库核对公告和制裁名单，最后用 SQL 检查关系生效日期和持股比例。如果三层证据不能同时对上，系统只报告“发现一条待核验关系”，不会因为图上存在一条边就直接判定违规。怎么落地：路由结果和每个工具返回的证据都进入同一份审计记录。

### **7.9 图谱更新要支持增量、纠错和时间回放**

图谱最容易被低估的成本是更新。新文档来了以后，不一定要整库重建，可以只找受影响的实体和关系，重新抽取相关邻域。关系被改正时保留修订记录，旧事实在历史查询中仍然可见，但默认检索要按问题时间点选择有效版本。

遇到冲突时不要简单地“最后写入覆盖前面”。应同时保留两个来源，并记录冲突原因、来源等级和人工处理结果。对于医疗、法律和金融等场景，图谱中的“曾经这样”与“现在仍然这样”必须分开，否则模型会把历史关系当成当前事实。

实际案例（白话）：医学知识图谱中显示某药已经进入三期临床，但最新登记页面仍显示二期。系统不直接覆盖其中一个，而是把两条记录放进冲突队列，标明来源和更新时间；回答用户时说明“图谱记录与最新登记不一致”，并把登记页面作为当前优先核验来源。等人工确认后，再更新有效状态，同时保留旧记录供审计。怎么落地：增量更新要同时处理实体、关系、来源、时间和冲突，不要只更新节点名称。
