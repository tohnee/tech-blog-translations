## hipfire v0.4.2.1 · Qwen3.8-27B MQ4-XTS · RX 7900 XTX 基准测评与部署报告

> **结论摘要**：AR 基线与 [《7900 XTX 的可能性探索｜单卡篇（五）》](http://lcz.me/2347)参考文章吻合 98%–101%； DFlash 推测解码五档全部达到文章的 105%–124%，加速比 3.08×–4.11×。 本报告取代初版结论——初版因测量方法缺陷误判「DFlash 未复现」， 根因与证据链见第 5 节。<br> 2026-10-18 起本配置已作为本机生产推理引擎上线，部署状态见第 8 节。

### 2. 测量方法

```bash
hipfire bench qwen3.8:27b-mq4-xts \
  --prompt-file <PROMPT> \
  --runs 3 --warmups 1 \
  --max-tokens 2048 \
  --max-seq <TIER_LIMIT> \
  --spec dflash --kv-mode q8 --kv-backend legacy \
  --json
```

AR 基线用完全相同的参数，仅将 `--spec` 改为 `off`。 每档独立进程，模型与 KV 均为 Cold，不复用 prefix cache。

**与参考文章的差异**：原文输出长度为 256 token，本报告为 2048 token。 第 5 节说明这一改动为何是结论成立的关键。

### 5. 根因分析：初版为何误判

初版报告称「DFlash 仅达文章 22%–34%，加速比 0.42×–1.16×，未复现」。 该结论错误，根因是**测量方法**，非引擎缺陷。

### 5.1 排除项

| 怀疑 | 核查结果 |
| --- | --- |
| 模型选错 | 否。主模型与 draft 均与 registry 映射一致，sha256 双校验通过 |
| 草稿窗口配置错误 | 否。dflash_spec.rs 确认 W=2048 取自 draft metadata，属正确路径 |
| KV 后端影响草稿 | 否。日志中 HIPFIRE_DFLASH_WINDOW=0 for Legacy 仅为提示另一模式，非当前状态 |
| DFlash 未启用 | 否。日志确认 spec_route=['dflash','dflash','dflash']，dflash_mode=on |

### 5.2 真正的变量：prompt 类型 × 输出长度

8K 上下文下 2×2 对照：

| Prompt 类型 | –max-tokens | 实际生成 | τ | Decode |
| --- | --- | --- | --- | --- |
| 散文（”用三句话总结”） | 256 | 97 tok（提前 EOS） | 1.85 | 56.8 |
| 散文（”用三句话总结”） | 2048 | 97 tok（仍提前 EOS） | 1.85 | 56.8 |
| 代码 | 256 | 256 tok | 2.07 | 64.8 |
| 代码 | 2048 | 2048 tok | 7.67 | 181.0 |

**机制**：散文指令使模型在 97 token 后结束输出，无论上限设多大都不变，因此整个测量窗口 都落在草稿接受率的爬升段。代码 prompt 触发模型持续生成，τ 随输出推进由 2.07 升至 7.67。

这与 hipfire 官方文档一致——DFlash 在 code prompt 上可达 ~4× decode，在开放式散文上收益显著更低。 初版同时踩中「散文 prompt」与「256 token 短窗」两个因素，导致 τ 被压到 1.25–2.03。

### 5.3 修正后的结论

DFlash 推测加速在这台 7900 XTX 上**完整复现并略超参考文章**。 AR 基线 98%–101% 的吻合度独立佐证了这一点。

### 6. 已知限制

### 6.1 VMM KV 后端不可用（已定位根因）

`--kv-backend vmm` 加载失败：

```text
load failed: HipError(2): hipMemAddressReserve: out of memory.
GPU: gfx1100 (8924 MB free / 24560 MB total)
```

**这不是显存预算问题，也不是 hipfire 的缺陷。** 逐层排查结论：

| 排查项 | 结果 |
| --- | --- |
| 是否尺寸相关 | 否。--max-seq 2048（极小 KV）与 --max-seq 134144 报同一错误，预算行完全相同 |
| vm.max_map_count | 已从 65530 提升至 2097152，无效 |
| hipfire 自身是否有问题 | 否。仓库自带隔离测试 crates/hip-bridge/examples/vmm_arena_smoke（不加载模型、不涉及 KV 配置）在本机复现同一错误 |
| ROCm 版本 | ROCm 10.0.0 / HIP 7.15 |
| Large BAR | 已启用，可见显存 = 完整 24 GB |

用最小 HIP 程序（`/tmp/vmm2.cpp`）在驱动层直接测试，结果为决定性的：

```text
device=gfx1100  totalGlobalMem=23.98 GB
  reserve sz=4096      align=4096   -> out of memory     ptr=(nil)
  reserve sz=1048576   align=4096   -> out of memory     ptr=(nil)
  reserve sz=1073741824 align=2097152 -> out of memory   ptr=(nil)
  reserve sz=2147483648 align=2097152 -> out of memory   ptr=(nil)
  reserve sz=68719476736 align=2097152 -> out of memory  ptr=(nil)
hipMalloc 256MB (non-VMM path) -> no error
```

**连 4096 字节的虚拟地址都预留不出来，而 `hipMalloc` 正常。** 说明 GPU 侧虚拟地址空间本身不可用，与显存余量无关。

**最可能的原因**：本机该 GPU 同时承担显示输出。

```text
fbcon: amdgpudrmfb (fb0) is primary device
/dev/dri/card0  <- Xorg (PID 2083) 持有 DRM master，存在 1 路连接显示器
```

Xorg 持有 DRM master 且显示管线占用 GPU 虚拟地址孔径，HIP VMM 因此找不到可用 VA 空洞。 系统无第二块显示设备，无法把桌面切到核显。

ROCm 运行时二进制中未发现任何 VMM 相关的可调环境变量，无软件侧规避手段。

**验证与修复方案**（需停止桌面会话，会中断当前图形界面）：

```bash
# 1) 切到纯文本环境，释放显示占用
sudo systemctl isolate multi-user.target

# 2) 复测
/tmp/vmm2          # 期望：reserve sz=4096 不再报 out of memory

# 3) 确认可用后跑 hipfire VMM
hipfire bench qwen3.8:27b-mq4-xts ... --kv-backend vmm

# 4) 永久生效（可选，需重启）：让 AMD GPU 不再承担显示
#    在 GRUB 的 linux 行追加 amdgpu.dc=0
```

**当前处置**：已回退至 `legacy` KV 后端并写入 `~/.hipfire/config.toml`。 鉴于本报告第 3、4 节的结果已全面超过参考文章，VMM 不可用未构成实际制约。

附带影响：legacy 后端在 128K 上下文下显存占用略高于 VMM， 这解释了 6.2 节中本机 128K 需将输出降至 1024 token 而文章可用 2048 token 的差异。

### 6.2 128K 上下文对输出长度敏感

128K 上下文（128,158 token）配 2048 token 输出时，KV 预算超出 24 GB 显存可承受范围： prefill chunk 被迫降级（`requested=8192 admitted=1024`），并触发 `HipError(719): hipStreamSynchronize: unspecified launch failure`。

将输出降至 1024 token 后该档完全稳定，AR 与 DFlash 均正常完成， 剩余显存 2104 MB。文章在 128K 可用 2048 token 输出，说明其显存占用略低 （可能与 VMM 后端的分配效率有关，见 6.1）。这是本机 24 GB 显存下的容量边界， 非正确性问题。

### 7. 结论

1. **AR 基线与参考文章吻合 98%–101%**，五档全部命中，证明引擎、内核、量化、驱动、 GPU 配置均正确，基础推理性能无疑问。
2. **DFlash 推测加速完整复现并超过文章**：五档 decode 全部达到文章的 105%–124%， 加速比 3.08×–4.11×（128K 为 2.01×）vs 文章 2.77×–3.39×（128K 为 1.86×）。
3. 初版「DFlash 未复现」的结论系测量方法缺陷所致（散文 prompt + 256 token 短窗）， 已撤回。
4. 结论的适用边界：加速比随任务类型显著变化。代码类任务可达 ~3–4×， 开放式短输出散文任务收益有限。评估 DFlash 时应使用与目标工作负载匹配的 prompt， 并保证输出长度足以越过草稿接受率爬升段。
5. 128K 上下文在 24 GB 显存下建议将输出长度控制在 1024 token 以内， 否则 KV 预算超限会导致 prefill 降级并可能触发 GPU 故障。

### 8. 生产部署状态（2026-10-18 起）

本报告的结论已落地为本机实际使用的推理引擎，取代原先的 llama.cpp + Vulkan 路线。

### 8.1 当前运行配置

| 项 | 值 |
| --- | --- |
| 服务 | hipfire.service（systemd user，enabled，唯一自启的模型服务） |
| 端点 | [http://127.0.0.1:8080/v1](http://127.0.0.1:8080/v1)（OpenAI 兼容） |
| 上下文 | 65536（--max-seq 65536） |
| KV 后端 | legacy（VMM 在本机不可用，见 6.1） |
| thinking | off（agent 负载不需要，节省 token 与延迟） |
| DFlash | 自动开启（registry 为 qwen3.8:27b-* 声明了配套 draft） |
| 显存 | 21.34 / 25.75 GB |

```text
# ~/.hipfire/config.toml
[memory]
kv_backend = "legacy"
[reasoning]
mode = "off"
```

### 8.2 与 llama.cpp 共用端口

hipfire 服务的是**同一个模型**（Qwen3.8-27B），只是量化与引擎不同，因此与原 llama.cpp 档位**共用 :8080**，客户端配置无需改动。已并入既有统一入口 `~/llama-bin/llama.sh`：

```bash
cd ~/llama-bin
./llama.sh hf        # 起 hipfire（自动停掉其它模型）
./llama.sh 38        # 切 llama.cpp
./llama.sh hf --use  # 原地切换
./llama.sh status    # 能区分两个引擎谁在占用 :8080
```

集成细节见 `~/llama-bin/OPTIMIZATION.md` §14。

### 8.3 互斥与自启约束

显存 25.75 GB 只够一个模型。`llama.sh` 的互斥停机会与 systemd 的 `Restart=on-failure` 冲突形成重启循环，因此**同一时刻只能 enable 一个模型服务**：

| 服务 | 状态 |
| --- | --- |
| hipfire.service | enabled |
| qwen38.service | disabled |
| strata-q2_0.service | disabled |

`Linger=no`，故为登录后自启；如需开机即跑用 `sudo loginctl enable-linger hnz`。

### 8.4 接入 OpenCode

`~/.config/opencode/opencode.jsonc` 的 `local` provider 指向 :8080， 默认模型 `local/qwen3.8:27b-mq4-xts`。切换引擎 = 先 `./llama.sh 38|hf`， 再改该文件 `model` 行，重启 OpenCode。
