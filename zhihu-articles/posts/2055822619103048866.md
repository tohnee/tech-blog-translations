系统中会有不同的请求处于不同状态，理论上我们可以独立推进每个请求，就像我们可以独立处理每个 SQL 一样。但实际上我们不会，这也分为两类，对于 prefill 也许可以，但对于 decode，batching 有超乎想象的红利空间，这也是 wideep 是现在大 MOE 部署的必需品的原因之一。但即使我们在 prefill 侧，做到了 kernel 级别的控制，似乎也没有什么收益。GPU 只能串行处理 kernel（因为 Prefill 计算很重）。

所以所谓的支持了一个新模型，简单来说，就是支持了 prefill forward，decode forward（对于推测解码可能多一条）。 forward 本身应该是个纯函数，无状态的，但它会返回结果，也就是 kv cache，或者说线性状态，因为这是“推理引擎”侧唯一需要感知的东西，或者说接受 token 数。

所以不同模型的差异就在 两个forward function 输入和输出不同。或者说引擎核心在处理的是那些“有状态”的部分，kv cache，线性状态， MTP 接收，请求是否 eos，还有多 rank 的协调。

但没有人开源模型是开源这两个高性能 forward function 的，毕竟这是内部很多算子工程师可能数个月的心血。所以这就要求推理引擎侧编写维护这些算子，这很头疼，这不仅关乎性能，更是正确性的保证。

坦白说，90% 的 openinfer 维护工作都在和 kenrel 作斗争，精度有问题，快了，慢了。想要 ttft 好看？优化 Kernel! 更高的 tps，优化 kernle!

反倒是引擎侧的东西很快搞定，比如 kv cache + offloading + routing 感觉两天搞定，甚至 p/d 分离，两天写完都小事。但优化 kernel，甚至从如何 profile，如何确定并行，tp,pp,dp,ep,cp，开多大，混着开？怎么开？一方面涉及到理论计算，tp 能并行， pp 通信代价低。更重要的是切分后的 kernel shape 是否高效。甚至一些奇怪的并行，比如 tilert 把 indexer 专门放到卡 0，我想背后也是有动机的。tilert 能做出这么优秀的工作，相信背后是一群优秀的算子工程师。如果我不是一个很好的 算子哥，我又怎么去确定真正正确的架构呢，算子决定了太多太多。

更多的 IR，更多的 DSL，似乎每一周就能写看到一个新的，甚至我感觉我有兴趣，明天也能写一个（实际上还写了一个，不过非常 toy）。我们在试图填补什么空白吗？DSL，IR，是否是算子哥自己的语法糖，如果我不知道足够多的高性能 kernel，我怎么开发一个新 DSL 呢？如果我已经知道，有 context 了，这个 DSL 是否就是我的语法糖呢？这个 DSL 更多在描述“我认为该怎么定义和描述要给 kernel”的抽象。

所以当我说，我维护了一个开源引擎，支持了 xx 模型，本质上是我维护了这个模型的 kernels。其他层面的东西都太过简单，太过 naive。

当然说这么多，主要是因为 openinfer 维护过程中，有太多 kernel 问题，我花在引擎层面的时间很少。我想在引擎侧探索更多可能性，但总被 kernel 拖住前进的脚步。

Openinfer 缺一个 完整的生产可用的机会（其实 Qwen3 应该），但奈何 Qwen3 4B 量不大。我想在大 MOE 上发力，比如 glm52，如果我有一个能跑的 MVP，我可以探索非常多的东西。另一方面，也可能是 rust 偷代码比较费劲，vllm,sglang, tokenspeed，都是用 python 写的，很多 kernel 也是发的 python 包，用 rust，需要先拿到.cu 源码，然后 ffi。当然其实用 python 也很复杂。

OpenInfer 本来想探索 engine 层面的设计空间，比如 Rust、tracing、metrics、无 GIL、通信、offloading、routing、P/D 分离，但实际 90% 时间被 kernel 拖住了。

我造了一把好枪（引擎），但我缺子弹（kernel）。没有子弹，枪再好也打不了仗。而造子弹这件事，既不是我最想做的，也不是我一个人能高效做的，还因为我选了 Rust 而变得更难。

在当前阶段，一个推理引擎的核心竞争力不是"引擎"，而是"kernel 覆盖度 × kernel 性能"。引擎层的架构优雅度是锦上添花，不是雪中送炭。<br><br>但别担心，即使没有算子哥，openinfer 这两个月会搞定 glm52 的大规模部署的，而且应该会有一些有意思的 insight ，因为已经有一些了。
