AI 编程助手越用越多——Cursor、Claude Code、GitHub Copilot、Codex、ChatGPT——但有个共同的问题一直没解决：在一个工具里调教好的规则，换个工具就完全失效。

当我们在 Cursor 里写好的 React 组件规范，切到 Claude Code 里它一无所知；当我们在 ChatGPT 里调试好的提示词，想搬到 Codex 里得重写一遍。 **经验被困在了工具里** ，搬不出来。

而这一篇想把这个问题的两个核心思考一下： **Skill** （经验怎么写、怎么管）和 **上下文工程** （AI 决策前怎么准备”原料”）。

### 一、Skill 是什么

人有一种记忆叫”程序记忆”——存的是”遇到这种情况该怎么办”，不是”什么是什么”（那是语义记忆），也不是”上次发生了什么”（那是情景记忆）。

我们会骑车但不一定能说清楚骑车要领；我们做 code review 有套路但不一定能写出一份 SOP。这种”知道怎么做但说不清楚”的知识，就是程序记忆。

AI Agent 也有类似的机制。但程序记忆有个问题： **它藏在 Agent 内部，是隐式的，和特定实例绑定的** 。一旦换工具、换项目、换人，这套规则就消失了。

**Skill 要解决的，就是这个问题。**

Skill 本质上是把”怎么做”的知识显式化、结构化、独立化——写成文档，让人能编写、让系统能管理、让任何 Agent 都能调用。

用人话讲：

> 程序记忆是”我知道怎么做”。Skill 是”我把’怎么做’写成操作手册，让谁都能照着做”。

**举例对比：**

| 形态 | 描述 | 例子 |
| --- | --- | --- |
| 程序记忆 | Agent 脑子里的隐式规则 | “这个用户喜欢简洁回答” |
| Skill | 写出来的显式文档 | 一份完整的”API 文档写作 Skill” |

学术上，CoALA 论文（ *Cognitive Architectures for Language Agents* ）把这套认知架构做了系统化。 **P4 这节专门讲的就是程序记忆的”外化”形态——Skill。**

Skill 在当前工具生态里有多种形态：Cursor 的 `.cursor/rules/` 、Claude Code 的 `.claude/skills/` 下的 `SKILL.md` 、ChatGPT 的自定义指令、System Prompt 模板。名字不一样，平台不一样，但做的是同一件事—— **把”该怎么做”以文档形式交给 AI** 。

### 为什么 Skill 突然成了热词

几个时间节点值得提一下：

- **2024 年 11 月** ，Anthropic 提出了 **MCP** （Model Context Protocol），让 AI 工具和数据源有了统一的”USB 接口”
- **2025 年 3 月** ，Manus（由 Monica 团队推出）作为通用 AI 智能体引发广泛关注，”工具调用”概念被大众认知
- **2025 年 6 月** ，Cursor 1.0 正式发布， `.cursor/rules/` 目录被确立为 Skill 的标准承载形式
- **2025 年下半年** ，Anthropic 推出 Claude Code Skills 体系，把 `SKILL.md` 作为标准入口

这些事件把”AI 经验管理”从民间实践推到了行业标准化阶段。

### 二、Skill 怎么写：四件套

Skill 本质上是数据资产。它应该怎么写才方便被检索、被复用？

借鉴 MCP Tool 的设计思路，一个最小可用的 Skill 建议至少包含 **四块信息** 。

### 第一件：稳定的名字

名字是给系统索引用的。 **好的名字稳定、具体、机器友好** ：

```as3
api-doc-writing         # 推荐
npm-package-release     # 推荐
docs                    # 太宽泛
helper                  # 啥意思
```

### 第二件：清晰的描述

描述是 Skill 的”语义入口”，决定 Agent **什么时候** 会想到调用它。好的描述包含三层信息：

- **适用任务** ：解决什么问题
- **触发场景** ：什么情况下使用
- **边界范围** ：什么情况下不要用

反例：”帮助写 API 文档”——这种描述太宽，Agent 看了一脸懵。

正例：

```as3
description: 当用户需要按团队规范编写或修改 API 文档时使用，
             适用于接口说明、请求参数、响应示例和错误码整理；
             不用于生成后端接口代码。
```

### 第三件：明确的输入范围

告诉 Agent **完成这个任务需要哪些信息** ：

```yaml
inputs:
  required:
    - endpoint_path
    - http_method
    - request_params
    - response_schema
  optional:
    - auth_requirement
    - error_codes
    - example_request
    - example_response
```

**核心原则** ：区分必填和可选、说明参数来源、不要把业务实现写进 Skill。

### 第四件：示例

示例是”对齐器”，告诉 Agent “正确执行应该长啥样”：

```yaml
examples:
  - user: 帮我给 POST /api/orders 写接口文档
    agent_behavior: >
      先确认接口路径、方法、请求参数和响应结构；
      缺失时读取代码或追问，不直接编造字段。
  - user: 字段你随便补一下
    agent_behavior: >
      不编造字段，要求提供代码上下文或业务说明。
```

### 拼起来：一个完整的 Skill 模板

```yaml
name: api-doc-writing
description: >
  当用户需要按团队规范编写或修改 API 文档时使用，
  适用于接口说明、请求参数、响应示例和错误码整理；
  不用于生成后端接口代码。

goal: 生成结构完整、字段可信、符合团队格式的 API 文档。

inputs:
  required: [endpoint_path, http_method, request_params, response_schema]
  optional: [auth_requirement, error_codes, example_request, example_response]

constraints:
  - 缺少请求参数或响应结构时，先追问或读取代码，不直接编造
  - 不修改接口实现代码，只生成或更新文档
```

> **📌 注意** ：不同平台的 Skill 文件格式可能不一样——有的写在 `SKILL.md` ，有的写在 `.cursor/rules/` ，有的写进系统提示词。但无论外层格式怎么变， **底层都应该保留这四类信息** 。否则 Skill 就会退化成一段散文：人读着有感觉，Agent 用起来不稳定。

### 三、碎片化困境与检索机制

Skill 写好了，下一个问题是： **它能在哪里被使用？**

### 碎片化的三个层面

这事儿 2025 年下半年在工程师圈里被讨论了无数次。拆开看是三个层面：

**第一层：项目隔离**

同一个工具、不同项目之间规则无法自动共享。我们在项目 A 配好的 React 规范，开项目 B 时得手动搬一次。那些通用规则（”代码要有类型注解”、”错误信息用中英双语”）在每个项目里都有用，但每次都要重新配置。

**第二层：工具隔离**

不同 AI 工具的 Skill 格式不兼容：

- Cursor 的 Rules 是 `.mdc` 文件，存在 `.cursor/rules/`
- Claude Code 读的是 `.claude/skills/` 下的 `SKILL.md`
- Codex 默认读 `.agents/skills/`
- ChatGPT 的自定义指令是一段纯文本

即使描述同一条规则，你也得用四种不同方式写四遍。

**第三层：人员隔离**

团队成员之间没法便捷共享 Skill。工程师 A 有一套前端规范存在自己的 Cursor 里，工程师 B 有一套后端最佳实践存在自己的 Claude Code 里。 **新人入职，找不到一个地方能系统了解”我们部门的最佳实践是什么”。**

### 用检索解决碎片化

当 Skill 数量增长到几十个时，Agent 该怎么知道该用哪个？

最朴素的做法是全部塞进上下文窗口——但上下文有限、不相关的 Skill 还会造成干扰。 **解法和 RAG 是一模一样的** ：

**用户请求 → 语义召回 → 混合检索 → Skill 匹配 → 上下文加载 → Agent 执行**

P2 讲过 RAG 的检索机制——从知识库中召回最相关的文档。 **Skill 检索做的是同一件事，只是对象从”知识文档”换成了”技能文档”** 。

这意味着：

- 混合检索（向量+关键词）在这里同样适用
- Agentic 决策（”这个请求要不要调用 Skill”）同样必要
- P2 讨论过的所有检索策略， **在这里完全复用**

这个复用不是巧合。 **Agent 的各种能力，拆到底都是数据的存储与检索** ——RAG 是知识数据的检索，记忆是用户数据的检索，Skill 是经验数据的检索。底层机制相通，只是数据类型不同。

### 数据视角的根因分析

把”知识库”替换成”Skill”，下面这个判断成立：

> **Skill 分散在不同的文件系统、不同的项目目录、不同的平台配置中——无法被统一检索、无法被团队共享、无法被跨 Agent 复用。这不是一个工程问题，这是一个数据管理问题。**

| 场景 | 数据层的问题 | 结果 |
| --- | --- | --- |
| 知识库数据分散 | 文档散落不同系统 | RAG 检索不到正确内容 → AI 回答质量差 |
| Skill 数据分散 | 经验散落不同工具、不同人 | Agent 找不到最佳技能 → AI 行为不够专业 |
| 记忆数据分散 | 用户画像散落不同实例 | Agent 不”懂”你 → 个性化体验差 |

**同一类问题，同一个根因——经验数据没有被结构化地管理。**

### 四、上下文工程：AI 决策前的”最后一公里”

讲完 Skill，再往上看一层—— **当 Agent 收到请求、准备开始工作之前，它在做一件更重要的事：准备上下文。**

### 上下文 ≠ 把更多内容塞进提示词

上下文工程讨论的是 Agent 在每次决策前如何获得 **足够、相关且可追溯** 的上下文。完整的准备链路包含四个方向：

| 上下文来源 | 内容 | 特点 |
| --- | --- | --- |
| Source | 用户输入、对话历史、工具返回 | 实时性强，量不可控 |
| Memory | 语义、情景、程序记忆 | 历史积累，需定期召回 |
| PreparedContext | 筛选、压缩、排序后的上下文 | 质量可控，需维护 |
| Handoff | 多 Agent 之间的任务状态传递 | 跨 Agent 协作的关键 |

### 三个核心权衡

实际工程中，上下文管理通常要在三个维度上做权衡：

**⚖️ 相关性 vs 完整性**

上下文不是越多越好。给 Agent 塞太多不相关信息会分散注意力。 **做法是从大量候选中筛选最相关的那部分** ，而不是全部塞进去。

**⚖️ 上下文预算 vs 信息密度**

大模型的上下文窗口是有限的。在有限空间里应该优先放什么？

- 🥇 用户当前的问题
- 🥈 相关记忆
- 🥉 最必要的 Skill
- ⏸️ 历史对话的细枝末节（按需压缩）
- ⏸️ 边缘场景的备选方案（按需召回）

**⚖️ 可追溯性 vs 系统复杂度**

当 Agent 给出某个回答时，我们需要知道：参考了哪条上下文？来自哪里？是否最新？没有可追溯性，就很难做错误溯源和质量评估。

> **这三个权衡互相制约** ——想更全面就要更多 token 和更高延迟；想更精准就要更复杂的筛选逻辑；想要可追溯就要额外的元数据存储。 **上下文工程的核心挑战，就是在保证上下文质量的前提下，在延迟和成本之间找到最优的平衡点。**

### 一个可参考的实现

如果想看到上下文工程的实际代码实现，可以看一下 **PowerContext** （OceanBase 开源）。它把整个上下文准备链路拆成四个明确的部分：

```as3
Source → Memory → PreparedContext → Handoff
```

每个环节的输入输出都定义清楚，让数据在它们之间流动起来。 **这是一种工程化思维——把”靠人想”的事变成”靠系统跑”的事。**

### 五、几个核心观点

学习完 P4 和 I6 之后，有几个点我觉得是真正值得记住的。

**观点 1：Skill 不是 Prompt，是经验资产**

Prompt 是消耗品——每次对话用完就没了。Skill 是资产——可以被积累、管理、复用、检索。写一个 Skill 和写一段 Prompt 的区别，就像写一篇博客和发一条朋友圈。

**观点 2：碎片化的根因是”数据没被当作数据”**

Skill 散落在各个工具里，不是因为工具不争气，而是因为我们没有把 Skill 当作需要被管理的数据资产来对待。 **所有的 AI 经验问题，归根结底都是数据管理问题。**

**观点 3：Skill 检索和 RAG 是同一个机制**

把 Skill 检索理解成 RAG 之后，事情就清晰了——我们不需要为 Skill 检索发明新系统，可以直接复用 RAG 的成熟方案。 **Agent 的各种能力，拆到底都是数据的存储与检索。**

**观点 4：上下文工程是 Skill 和 Memory 的”汇聚点”**

P3 学了记忆系统，P4 学了 Skill 管理，I6 把这两件事接起来了—— **上下文工程就是把记忆和 Skill 在正确的时间、以正确的方式、送到正确的位置** 。

用三句话总结：

- **记忆 = Agent 经历过什么**
- **Skill = Agent 该怎么做**
- **上下文工程 = 怎么把这两样用好**

**观点 5：工程化思维 = 把”靠人传”的事变成”靠系统传”**

师徒传承、经验沉淀、SOP 文档化——这些事情在传统行业里做了几千年。AI Skill 解决的是同一件事，只是用了更工程化的方式：结构化、可检索、可共享、可演进。
