## OverView

如果把 NVIDIA GPU 近二十年的架构演进概括成一句话，核心主线就是**执行域、供数域、同步域与协同边界不断外扩**；功能堆叠只是表层现象。

最初那台机器更接近这样一种形态：

- 执行上以 `warp lockstep` 为默认推进方式
- 数据上主要围绕 `RF -> collector -> ALU` 这样的近端供数链
- 同步上主要围绕寄存器依赖、`busy-bit/scoreboard` 就绪状态，以及 `SM` 内的发射阻塞与恢复条件
- 协同上主要以单个 `SM` 作为默认的硬件协同与共享状态边界
- `memory-side`（即 `L2/partition/DRAM` 一侧）和互连已经存在，但还没有承担今天这样强的软件可见语义

后续每个真正重要的架构断点，都在打破其中至少一个边界：

- **Fermi** 的断点在于：`global` 访问的缓存策略、按地址映射到的 `L2/partition` 处理域，以及部分原子/顺序问题，开始成为软件可观察、可调优的 memory-side 边界。
- **Volta** 的断点在于：通用路径失去独占地位，隐式 warp 锁步也失去默认前提。
- **Hopper** 的断点在于：shared-memory 风格的 CTA 协同第一次以 `Thread Block Cluster / DSM / TMA` 这组明确硬件原语跨过单个 `SM` 边界。

本文围绕三个问题展开：**上一代到底卡在哪里，下一代引入了什么机制，这个机制又把新矛盾推向哪里。**

这里关注的不是每一代新增了什么，而是**上一代到底卡在哪里，下一代引入了什么机制，这个机制又把新矛盾推向哪里。**

本文的证据分三层读：官方公开文档可以确认的事实、专利文本，以及基于前两者串联出来的归纳。文中说演进思路时，指的是这三类材料共同支持的架构压力链，不等同于 NVIDIA 官方声明过的内部设计路线。

从这个角度读，近二十年的主线大致可以归纳为三层压力：

- **memory-side 控制/语义压力**：当 `L2`、atomic、residency、coherence 从后台细节升格，memory-side 必须变成真正的硬件域。
- **datapath specialization 压力**：当矩阵计算、低比特格式、warp-uniform 数据流难以继续塞进同一条通用路径，执行与供数就必须分流。
- **coordination 压力**：当 `cp.async`、`TMA`、`WGMMA`、cluster 协同成为主角后，同步原语和互连边界都必须跟着升级。

## 2. 演进思路：从基线机器到 cluster 级协同执行域

### 2.1 Tesla：定义最初那台通用、锁步、以单 `SM` 为主要边界的机器

Tesla 先把几条最重要的边界固定下来：

- `US8539130B2`（申请于 2009 年）表明核外 `crossbar` 与 virtual channels 已具雏形，说明片上流量组织并非后来的附加项。
- `US7339592B2`（申请于 2004 年）与 `US7490208B1` 为 banked `RF` 和 operand supply 的早期结构提供了源头，说明靠近执行单元的本地供数组织很早就已存在。
- `SIMT + warp` 锁步推进、单 `SM` 内的 shared memory / scoreboard / execution 聚合，构成了这台机器最初的默认执行模型。

如果先从机器骨架看，Tesla 已经把 `SM` 本地执行、核外 `crossbar` 与 memory-side 路径这几层关系摆了出来；后面讨论 `virtual channels`，只是把其中“片上流量如何组织”这件事进一步展开。

![](https://picx.zhimg.com/v2-8d3d80b2e58c60bea09b145aa1410a93_r.jpg)

这里的 `virtual channels` 指：在同一张核外 `crossbar` / on-chip fabric 上，把共享物理通道按不同 `traffic class` 切成逻辑隔离的通道或队列；物理连线仍共享同一套基础通道。它要处理的核心矛盾在于：`compute`、`memory`、`graphics` 这类不同请求共用交换平面时，怎样分类、排队、仲裁、传播背压，避免一类流量把另一类流量整片拖住。

```text
+------------------------------------------------------------+
| one physical crossbar/link, multiple logical channels      |
| VC-compute  --\                                            |
| VC-memory   ---+--> [ arbitration / shared switch ] -> out |
| VC-graphics --/                                            |
+------------------------------------------------------------+
```

因此本文说的“片上流量组织”，指 `SM/GPC -> crossbar -> partition/L2/memory interface` 这一层核外请求怎样在芯片内部流动：谁和谁共享链路，哪些流量需要逻辑隔离，阻塞会沿哪条路径回传，系统如何在有限面积和功耗预算下维持可用吞吐。`virtual channels` 只是这个组织问题里的一个机制；更大的问题是，GPU 从一开始就需要一张能同时承接多客户端、多目的端、多类请求的统一交换层。

```text
+---------------------------------------------------------------------------+
| request sources -> on-chip fabric -> memory-side destinations             |
| SM0   --\                                                                 |
| SM1   ---+--> [ crossbar / fabric ] --> [ partition0 ] -> [L2_0] -> DRAM0 |
| GPC_A ---+--> [ crossbar / fabric ] --> [ partition1 ] -> [L2_1] -> DRAM1 |
| GPC_B --/               |                                                 |
| busy destination <------+----- backpressure / queue state upstream        |
+---------------------------------------------------------------------------+
```

这也是为什么 Tesla 作为起点代就已经要考虑片上流量组织。原因是从第一代通用 GPU 开始，就已经有很多不同来源的请求同时走同一张片上交换平面：多个 `SM/GPC` 会并发争用共享 `memory-side` 资源，图形与计算流量也可能同时存在，而芯片又不可能为每一类流量都单独铺一套互连。这样一来，最先要解决的问题就是“现在这么多请求一起上路，应该怎么分流、怎么排队、冲突时谁先走、下游堵住时怎么避免把其他请求一起拖死”。若没有早期的流量分类与隔离机制，共享 `crossbar` 很快就会因为 `head-of-line blocking`、端口争用和背压传播变成整机瓶颈。

这里的 `head-of-line blocking` 可以直接理解为：队头那个请求因为目标端繁忙而暂时发不出去，后面本来可能发往空闲目标、理论上可以继续前进的请求，也因为共用同一 `FIFO` 或同一仲裁入口而不能绕过它。重点是“队头先卡住后，把后面原本有机会前进的请求也一起拖住”，即使其他目标端并没有全部繁忙。

```text
+------------------------------------------------------------------+
| head-of-line blocking                                            |
| head -> [A: busy dest] [B: free dest] [C: free dest]             |
| A cannot leave first, so B/C cannot bypass it in one FIFO        |
| later requests are blocked by the stalled front request          |
+------------------------------------------------------------------+
+-----------------------------------------------------------------+
| without traffic organization                                    |
| SM0(mem)  --\                                                   |
| GPC(gfx)  ---+--> [ one shared queue ] --> [ busy destination ] |
| SM1(comp) --/                                                   |
| all unrelated traffic waits behind the blocked head entry       |
| with virtual channels                                           |
| SM0(mem)  ----> [ VC-memory   ] --> memory path                 |
| GPC(gfx)  ----> [ VC-graphics ] --> graphics path               |
| SM1(comp) ----> [ VC-compute  ] --> compute path                |
+-----------------------------------------------------------------+
```

如果把这个机制再往硬件实现上想一步，可以把它理解成：输入端口前面拆出多条彼此隔离的逻辑队列，再通过仲裁共享后面的交换资源。这样某个方向或某一类流量暂时堵住时，只有对应队列被卡住，同一输入端上原本可以继续前进的其他请求仍有机会绕开阻塞。

Tesla 代表性产品 `G80` 发布于 `2006` 年，而本文引用的 `US8539130B2` 申请于 `2009` 年。因此本文只把它作为以下判断的证据：最晚到 Tesla 这一早期代际，NVIDIA 已把核外 `crossbar + virtual channels` 当作正式的架构问题写出来；它足以支撑“片上流量组织很早就是基础问题”这个判断，但不能单靠这一件专利就反推出 `G80` 已公开采用完全同名、同形态的实现。

### 2.2 Fermi：memory-side 从被动缓存背景变成可调优处理域

Tesla 时代真正的限制，同时来自缓存容量和 memory-side 语义边界：memory-side 更像“地址请求最终落到哪里”的后台路径，还没有成为稳定的软件可见控制边界。换句话说，这一节关注的主要矛盾不在 `SM` 本地执行结构，而在于软件仍缺少清晰接口来控制或解释 cache 行为、写回路径和 atomic 执行位置。

从 `SM` 本地执行视角看，Fermi 仍主要是一台由 dual warp scheduler 和 instruction dispatch 驱动的单 `SM` 机器；这恰好反衬出它这一代真正的关键转折点，并不在执行域外扩，而在于 memory-side 控制点第一次被写成稳定硬件边界。

![](https://pic4.zhimg.com/v2-d0f5dc5c9c2d720e074087afe7154057_r.jpg)

Fermi 把一部分控制点推到 memory-side，有三个直接原因。

1. `global` 访问已经不再只是把地址送到 DRAM 再把数据拿回来这么简单；软件开始需要区分哪些访问应该尽量利用 cache，哪些只是 streaming 数据，哪些访问希望弱化局部副本、重新取数或走 write-through 风格路径。

2. 把这些决定留在 SM/L1一侧并不稳，因为 L1是每个 SM各自本地的，不能作为不同 SM访问同一 global地址时的共同处理点；如果没有一个更靠近 L2/partition/DRAM的共同 memory-side owner，也就是同一地址按映射落到的 L2 slice / partition处理域，程序就很难稳定讨论这次访问主要在哪里被处理、怎样被缓存、怎样流向 backing store。

3. 随着 atomic、写回、驻留和更强的同步需求出现，硬件也需要一个按地址稳定落点，好让顺序判定、回压、清理和完成路径不必悬在更上层 做模糊协调。

`US9639479B2`（申请于 2010 年）是这条线的第一个关键转折点。它的重要性在于把下面几件事固化成同一组硬件边界，而非单纯引入 `L2` 这个事实本身：

- `partition unit`
- `L2 slice`
- `FB DRAM interface`
- `.cg/.cs/.cv/.wt` 这类 load/store policy modifier

其中 `FB DRAM interface` 可以直接理解为该 memory-side partition 通向外部显存 `DRAM` 的接口边界；它和 `L2 slice` 一起把 `partition -> L2 -> DRAM` 这条路径固定成一个完整的本地 memory-side 处理域，本身不承担新缓存层的角色。

这里中间写的 `global load/store` 指的是全局地址访问本身，并未命名某个独立硬件节点。 对 `global load/store` 这类全局地址访问而言，缓存策略、写回路径和按地址归属的处理点，正在从更局部的 `SM/L1` 视角，迁到 `L2 slice + policy + order` 所在的 memory-side owner。

从这里开始，`L2` 从被动大缓存升级为软件可感知、可通过 cache policy 调优、可讨论驻留与写回策略的 memory-side 域。Fermi 的关键在于给 `global` 访问建立一个独立于发起 `SM` 的按地址处理域：同一个全局地址不再主要由发起访问的某个 `SM/L1` 局部决定，而会更稳定地落到按地址映射到的 `L2 slice / partition` 一侧，由那里处理缓存策略、atomic 顺序、写回时机和完成路径。

这里的“稳定”指处理域稳定：无论请求来自哪个 `SM`，同一个全局地址都能落到一致的 memory-side 处理域。它不保证访问一定命中 `L2`，不表示所有数据都永久停在 `L2`，也不赋予 cache operator 同步语义。比如一个 `SM` 写 completion flag，另一个 `SM` 随后轮询这个 flag；程序仍然要用正确的 fence、atomic、barrier 或 CUDA/PTX memory model 机制表达可见性，但硬件需要一个共同位置来处理“写入是否已经完成、是否需要弱化旧副本、同地址 atomic 谁先谁后、什么时候可以向其他观察者交付”这些问题。

硬件看到的只是一串地址流，软件知道的却是访问意图：这批数据是否很快还会再用，是否只是顺序扫一遍，这次访问是否应该减少对局部 cache 的污染，这次 store 是否更适合走 write-through 风格路径。也正因为如此，软件才需要开始区分普通 cache 访问和 streaming 数据；否则一次性扫过的大块输入会把真正有复用价值的热点数据挤出 `L2`，而需要特殊缓存路径的访问又会和普通访问混在一起，性能和可解释性都变差。

`.cg/.cs/.cv/.wt` 可以把这种访问意图编码成 cache policy / locality hint。这里要特别收住：这些 modifier 影响缓存路径、逐出倾向或取数位置，但官方 PTX 语义中 cache operator 是性能提示，不改变内存一致性行为；真正的同步与可见性仍要由 CUDA/PTX memory model、barrier、fence、atomic 等机制承担。下面这些例子只用于建立直觉，并不覆盖所有用法：

| Modifier | 语义 | 适合什么访问 | 例子 |
| --- | --- | --- | --- |
| .cg | 偏向只在 global/L2 层次缓存，不优先占用每个 SM 的 L1 | 希望避免 L1 局部副本干扰，但仍想利用 L2 共享缓存 | 多个 block 都会反复读取同一张参数表或查找表，希望它主要在 L2 共享，避免在各个 SM 的 L1 里各留一份 |
| .cs | 这批数据更像“过路客”，即使缓存也应优先逐出 | 单次使用、顺序扫过、复用价值很低的 streaming 数据 | 一次性扫描一大段输入样本、像素流或激活值，读完后基本不会立刻再访问 |
| .cv | 对系统内存相关访问，偏向重新取数，减少对可能陈旧缓存行的复用 | 希望降低陈旧缓存命中的风险，但不把它当同步原语 | 读取可能由 host 或外部 agent 更新的数据时，配合正确同步机制减少缓存复用干扰 |
| .wt | write-through 风格 store，偏向把写入推向 memory-side / system memory | 不希望写入长期停留在局部脏状态，但仍不替代 release/fence | 写 host-mapped buffer、mailbox 或队列元数据时，和正确的内存顺序机制配合使用 |

今天很多看起来更现代的主题，都可以从这里看到早期动机：

- `US9639466B2`（申请于 2012 年）继续推进了 `L2` 脏数据何时对 backing store / `DRAM` 可见、何时触发清理与回压的问题
- ordered atomic 最终也沿着这条路线下沉：同一地址先稳定落到某个 `L2 slice`，再由该 slice 负责顺序判定、等待与执行，避免在更上层做模糊的全局协调
- `residency control` 开始回答：哪些数据该尽量留在 `L2`，哪些数据可以按普通或 streaming 策略更快逐出
- `memory synchronization domains` 开始回答：一次 barrier / fence 到底要对哪一类 memory effect、哪一类观察者生效，而不再默认整个 memory world 一起等待
- 更大范围的 coherence / completion visibility 则开始回答：即便已经进入 coherent domain，远端写入什么时候才真正对另一侧观察者成立

Fermi 的真正贡献是**重写了 memory-side 的可见控制边界**：很多原本只能在 `SM` 一侧模糊处理的问题，从这里开始可以围绕 `L2/partition` 被独立讨论。

Fermi 之后，**Kepler 和 Maxwell 更像这条路线的演进**。

- Kepler 沿一条线把 `RF -> crossbar -> collector` 供数闭环写完整：banked `RF` 先把分散在不同寄存器 bank 中的源操作数读出，经 `crossbar` 路由到 `collector`，再由 `collector` 在近 datapath 位置累积并复用操作数，让算子入口不必每次都回 `RF` 重读。这里的 `collector` 更像靠近算子入口的一层 operand 暂存/复用层，而非第二个 `RF`。
- Maxwell 沿另一条线把同步从 busy-bit 推向 barrier 化；`US9612836B2`（申请于 2014 年）的 software scoreboard 和 `US10067768B2`（最早优先权日为 2014-07-18）的 convergence barrier，相当于提前把 Volta 需要的执行协议准备好了。这里的“最早优先权日”指同一专利族最早可追溯的提交日期，用来判断技术构思出现的时间窗口；它不等同于公开日或授权日。这里可以先做一个最短的理解：software scoreboard 的重点，是把“这条指令要等待哪个依赖就绪”从硬件隐式判断，推进成软件/编译器可显式声明的等待对象；convergence barrier 的重点，则是把“分歧后的线程怎样重新汇合”从早期依赖 `active mask + token stack` 的隐式机制，改成一种显式 barrier 机制：进入分歧区的线程先登记到 barrier，先到汇合点的线程先等待，后到的线程继续执行；等所有该到的线程都到齐后，再一起恢复。也就是说，硬件会把“谁在等、在等哪个 barrier、满足条件后从哪里继续”保存成明确状态，而不再只是隐含在控制流栈里。如果再往实现上看，可以把它想成硬件里多了一项 barrier 状态记录：线程进入分歧区时通过 `ADD` 把自己登记进去，到汇合点时执行 `WAIT` 进入 blocked，硬件同时保存恢复执行的 `PC`；scheduler 每周期只挑当前 barrier 条件允许继续前进的线程子集发射，等 barrier 判断所有参与线程都到齐后，再统一解除等待。
- 软件scoreboard的设计参考文章：

[深入解析Modern GPU的control bits设计](https://zhuanlan.zhihu.com/p/1985083294845510474)

换句话说，Fermi 把语义推至 memory-side，Kepler/Maxwell 则在 `SM` 侧把供数与同步重新整理干净。到这一步，下一轮更大范围的结构改写条件才得以齐备。

### 2.3 Volta：通用路径不再独占，隐式 warp 锁步被改写

Volta 是第二次关键改写，两条线同时重组。

第一处关键改写发生在执行路径组织。`US10338919B2`（申请于 2017-11-29）直接把一条新的供数与执行路径画成硬件现实：

`register bank -> crossbar -> operand collectors -> HMMA datapath -> result queue`

![](https://pic2.zhimg.com/v2-106a54b122ec1aa4d80632787ad47d49_r.jpg)

参考该专利，`HMMA datapath` 的设计可以先压成一个简单模型：

```text
RF banks
  -> crossbar
  -> operand collectors
  -> HMMA datapath
  -> result queue
  -> RF writeback
```

这条链的关键在于把矩阵运算的“取数、复用、执行、写回”重新分层。`RF banks` 仍然是线程寄存器的来源，但它们的读带宽有限，不能每个 dot-product 子步骤都无代价地重新读出整块 `A/B/C`。`crossbar` 负责把已经从寄存器 bank 读出的值路由到正确的 `operand collectors`。`operand collectors` 是靠近 datapath 入口的向量暂存层，而非第二套通用寄存器文件：专利正文明确把它描述成可在多个 clock cycle 内从 `RF` 预装操作数，然后在一次 `MMA` 执行时并行送入 datapath 的结构。这样，同一组 `A/B` 向量可以在多个 dot-product pass 里反复使用，而不必每个 pass 都回到 `RF -> crossbar` 重取。

真正的 `HMMA datapath` 则消费这些已经到位的向量组合，生成结果矩阵中的多个元素。`Fig. 7` 说明矩阵乘加本质上会把输入矩阵的行/列向量组合成多个 dot-product；后面的 datapath 图给出几种实现方式：可以在一个 pass 里并行生成多个 dot-product，也可以通过多个 pass 复用 collectors 里的向量组合。最后结果先进入 `result queue`，再等待合适时机写回 banked `RF`，这说明写回本身也需要仲裁和缓冲，datapath 算完后未必立刻完成写回。

还有一个边界要讲清楚：这条专利没有证明 `HMMA` 完全脱离原有浮点机器。`Fig. 9` 同时画出了 `HMMA datapath 930` 和 `FP64 datapath 940`，二者在图中共享 `operand collectors` 与 `result queue`；`Fig. 14` 还说明某些 HMMA 实现可与 double-precision FMA datapath 共享部分 pipeline stage。因此更准确的说法是：Volta 把矩阵 dot-product 的前半段和中段专用化，但供数、完成和写回结构并未全部重造。当前专利足以支撑 `RF -> crossbar -> collectors -> HMMA -> result queue` 这条主链，但还不足以把 Volta 的 warp/lane fragment 映射、collector allocation 策略和每一级内部流水时序写成定论。

具体的设计参考文章：

[Tensor Core 微架构深度解析](https://zhuanlan.zhihu.com/p/2028548125518755193)

这件事的意义非常深远。Volta 保留原有通用路径，同时让矩阵乘加拥有独立入口、独立中段、独立结果回流组织的专用途径，不再只能挤在通用浮点管线里作为一种操作模式存在。后续 `BF16`、`TF32`、`FP8`、`FP4` 的演进，都是沿着这条被剥离出来的路径持续下沉。

为什么必须这样做？因为矩阵乘加已经不适合像普通标量/向量浮点那样继续塞在同一条通用 `FPU` 路径里。它有三层额外压力：

第一，矩阵乘加会在固定 tile 上重复做大量 dot-product，吞吐目标远高于一般 `FMA`，如果仍和通用算子共用同一条执行路径，很容易让通用路径既喂不饱也排不开。

第二，它的供数方式也不同；矩阵块数据需要在 `operand collector` 附近被成组缓存，并在 `HMMA datapath` 的多轮内部子计算中反复使用，避免每一步都回到通用寄存器/交叉开关路径里重取。这里的“多轮内部子计算”可以理解为：一次矩阵 tile 运算要把一组 `A/B` 矩阵片段拆成多个 dot-product 或 micro-op 去累计结果，同一组输入片段在这些子步骤里会被多次读取；与每个子步骤都重新访问 `RF -> crossbar` 相比，把它暂存在靠近 Tensor Core 入口的位置更合理。

第三，它的数值类型开始和通用浮点明显分叉，Volta 第一代 Tensor Core 采用的就是 `FP16 input + FP32 accumulate`，这已经更像一条专用计算路径，超过了通用 `FPU` 多支持一种模式的范围。也正因为如此，Volta 才要把矩阵乘加单独拆成 `HMMA datapath`：这样既能把矩阵吞吐拉起来，又能为后续 `BF16`、`TF32`、`FP8` 这些格式演进预留稳定扩展位置。

第二处关键改写发生在执行模型。Volta 保留 warp 这个对象本身，同时把隐式锁步前进从默认前提改写成可被显式打破和重组的执行语义。其关键意义在于：**线程不再只能被当作一个默认会整齐同步、共同前进的 warp 单位来理解，分歧、等待、前进都开始成为更细粒度的硬件对象。**

这里的“隐式 warp 锁步”需要拆开理解。`warp 锁步` 指的是：在 Pascal 及更早的主执行模型里，同一 warp 内的活动线程默认共享同一份前进点与控制流状态，分歧时主要靠 `active mask + reconvergence stack` 让不同路径串行执行，再在硬件认定的汇合点重新收拢。`隐式` 指的则是：这种“同一 warp 内线程会整齐到达、整齐前进、整齐汇合”的同步感由硬件默认提供，无需程序每次都显式下 barrier。

因此 Volta 带来的变化不止调度器更灵活；默认执行语义也被改写了：同一 warp 不再天然等于“所有线程此刻都在同一个 `PC` 上”。这也是为什么后来的 `_sync` 家族和 `__syncwarp()` 变得重要；它们本质上是在告诉硬件：这一次我要求哪一组线程显式在同一个汇合点上成立共同前进。

所以 Volta 的关键在于同时改写两件更底层的事：

- 硬件开始按数据形态分流，通用计算路径不再独占所有主要算子
- 硬件开始按执行形态分流，隐式 warp 锁步不再是默认前提

这里还有一个容易被误解的点：所谓“按数据形态分流”，并不等于简单按 `FP` 和 `INT` 把寄存器文件硬拆成两套。对大多数普通线程私有值来说，更合理的做法仍是共用 general `RF`，因为整数地址计算、位操作和浮点计算在真实代码里往往交织出现；如果仅按数值类型强行拆开，编译器搬运、端口平衡和写回压力反而会更难处理。真正值得被单独分出来的，通常取决于“它怎么被使用”：例如 warp-uniform 值更适合走只存一份、可广播读取的 `URF/UDP` 路径，矩阵 tile 和累加值更适合走 `HMMA` 这类专用 datapath，barrier / predicate 这类控制状态也更适合放在小而专门的状态存储里。换句话说，硬件更应该按“数据如何被复用、广播、累加和消费”来拆路径，而不只按数值类型拆存储。

Volta 之后，Turing 和 Ampere 更像把这些新机制做成熟、做稳定的阶段。

- Turing 把精度主线正式分叉到 `INT8/INT4`，说明 Tensor Core 不再只是半精度训练加速器，而开始为推理形成独立分支。
- Ampere 则把 Volta 时代隐约显出的异步搬运和格式扩张固化为稳定机制：`cp.async`、`BF16/TF32` 与结构化稀疏一起出现，说明分流后的机器已经进入“怎样喂饱并调稳”的阶段。另有专利材料描述了 warp 内部分歧后按线程子集交错推进的 `shard scheduling` 思路，可以作为“细粒度调度继续下探”的旁证，但它在本文中应按专利侧推断阅读，不和 `cp.async/TF32/BF16` 这类官方公开主特性等同。

### 2.4 Hopper：cluster 级协同成为明确硬件执行域

Volta 到 Ampere 解决的是单个 `SM` 内怎样分流、怎样搬运、怎样等待，而 Hopper 把 shared-memory 风格的 CTA 协同推进到了下一层：**多个 `SM` 怎样通过 cluster 级硬件原语共享数据、等待事务并共同消费。**

先看官方 `H100 SM` 图，容易得到一个刻板的印象：Hopper 当然强化了单个 `SM` 内的 `Tensor Core`、`FP32/INT`、`LD/ST`、`L1/SMEM`、scheduler 与寄存器资源，但完整问题已经延伸到单 `SM` 之外。真正的新压力来自：单 `SM` 内部已经能把矩阵算子、异步 copy 和等待机制组织得很满，下一步瓶颈变成**多个 `SM` 之间怎样共享工作集、怎样让数据搬运与矩阵消费跨更大执行域闭环**。

但 Hopper 的架构创新不只在单 `SM` 图里，而在它怎样被放进 cluster 级协同设计框架。

这也是为什么 Hopper 的核心不能被写成一张新增特性清单。真正重要的是，下面五层接口形成了一个闭环：

- **数值契约**：`FP8 (E4M3 / E5M2) + Transformer Engine` 把低比特格式选择、scale 管理和矩阵算子绑到一起
- **消费者粒度**：`WGMMA` 把矩阵消费侧从单个 warp 推到 warp group
- **搬运路径**：`TMA` 让大块、多维 tensor tile 的地址生成和搬运从线程循环中移到专用硬件路径
- **共享作用域**：thread block cluster 与 `DSM` 把 shared-memory 风格的协作从单 `SM` 扩到一组共同调度的 `SM`
- **异步与barrier**：transaction-aware barrier 不只等待线程到达，也等待数据搬运 transaction 到达
- `US20230289189A1`（申请于 2022 年）把 shared memory 的有效作用域从单 `SM` 扩到 cluster，形成 `DSM`
- `US12141082B2`（申请于 2022 年）让大块 tile 搬运脱离传统 LSU 直通路径，形成 `TMA`
- `US20230289242A1`（申请于 2022 年）让 barrier 不只等待线程，也等待 transaction arrival
- `WGMMA` 则把消费侧从单个 warp 推到 warp group

官方 CUDA 编程模型也把这个边界变化写得很直接：[compute capability 9.0 引入 thread block clusters](https://docs.nvidia.com/cuda/cuda-c-programming-guide/index.html#thread-block-clusters)，cluster 内的 thread blocks 保证共同调度到一个 `GPC` 上，并能访问 [distributed shared memory](https://docs.nvidia.com/cuda/cuda-c-programming-guide/index.html#distributed-shared-memory)。换句话说，Hopper 增加的是一个新的 locality / cooperation 层次，超出了普通“更多 shared memory”的范畴：过去 block 之间默认要靠 global memory 或更粗的 kernel 边界交换状态；到了 cluster，多个 block 可以在硬件保证的共同驻留范围内同步，并直接读写彼此的 shared memory 分片。

这里的“共享”要理解成分布式共享，避免误读成所有 block 共用一块无归属的大 shared memory。每个 thread block 仍然拥有自己的 per-block shared memory 分片，容量声明和生命周期也仍以 block 为单位；`DSM` 做的是把同一个 cluster 内这些分片映射进一个可跨 block 访问的地址空间。比如 `Block 0` 可以把 tile 写进自己的 shared memory，`Block 1` 在 cluster 同步后通过 `DSM` 读这个分片，甚至对其中的数据做 atomic；但如果 `Block 0` 已经退出，其他 block 就不应继续访问它的 shared memory 分片。因此，`DSM` 的关键在于给 cluster 内 block 之间提供一个硬件保证的近端共享视图，而非把 shared memory 物理合并。

![](https://pic1.zhimg.com/v2-f4d1de72c63e1cc94024ccefcc4368b8_r.jpg)

上图左侧仍是传统 grid -> thread block；右侧多了一层 thread block cluster。这个层次是理解 `DSM`、cluster barrier 和 `WGMMA` 周边协同的前提。

`TMA` 则解决供数路径的问题。Ampere 的 `cp.async` 已经让 global -> shared 的 copy 可以异步化，但很多地址生成、循环切分和 copy 编排仍由线程承担。Hopper 的 `TMA` 把 tensor tile 的维度、stride、边界和布局放进 descriptor，由单个发起线程提交大块异步搬运，后续地址生成和数据移动由硬件处理。这样做的重点在于让生产者线程从逐段搬运里解放出来，使矩阵主循环能围绕大块 tile 的生产、等待和消费来调度，而不只是让单条 copy 指令更快。

![](https://picx.zhimg.com/v2-40b3ca85e26fbd20131a1d898671f3b5_r.jpg)

上图讲的是：Hopper 把 tensor tile copy 的地址生成和搬运责任从线程循环转到 `TMA`，为后面的 barrier 与 `WGMMA` 消费提供更清晰的 producer 事件。

tma专利分析参考：

[Nvidia TMA专利分析](https://zhuanlan.zhihu.com/p/1999510078827544585)

但 tile 被提交给 `TMA` 之后，消费者还不能立刻读。这里才是 transaction barrier 的意义：传统 barrier 主要回答“线程都到齐了吗”；Hopper 的 transaction-aware barrier 还要回答“承诺的数据 transaction 都到齐了吗”。这对 Tensor Core 很关键，因为 `WGMMA` 消费的是一整块矩阵 tile；如果只看线程到达，不看 copy transaction 完成，就会把“发起了搬运”和“数据已经可被消费”混在一起。

![](https://pica.zhimg.com/v2-ef012565914c8266fe9f715cc706f3d6_r.jpg)

右侧 Hopper 的关键变化，是 barrier state 同时包含 thread arrival 和 transaction arrival；这正好对应本文说的“完成与放行”接口。

mbarrier的具体设计参考：

[Nvidia Mbarrier专利分析](https://zhuanlan.zhihu.com/p/1996698248342152937)

把这几件事连起来看，Hopper 的主线可以写成下面这条 producer-consumer 链：

```text
global / L2 tensor tile
  -> TMA descriptor-driven bulk copy
  -> local SMEM or DSM resident tile
  -> transaction-aware barrier confirms data arrival
  -> scheduler releases the waiting consumer group
  -> warp-group / WGMMA consumes the prepared matrix
```

这条链比“多了 `WGMMA`”更重要。PTX 手册把 wgmma.mma_async 写成 warpgroup-level MMA，并要求 warpgroup 内所有线程执行同一条 `.aligned` 指令；因此它需要一个超出单线程或单 warp 的就绪条件：相关 tile 在 `SMEM/DSM` 中已经可读，相关 transaction 已完成，barrier 已释放，参与消费的 warpgroup 也处于一致的执行点。可以把这个条件压成一句话：

```text
WGMMA-ready = resident tile + transaction completion + visibility + group release
```

这几件事必须放在一起看。只看其中任何一件，都会把 Hopper 误读成某个模块更强；只有放在一起，才能看出它在重新定义执行域边界：

- `DSM` 提供了 cluster 级共享媒介
- `TMA` 负责把大块数据送进这个媒介
- transaction barrier 让**数据真的到了**成为可等待的硬件条件
- `WGMMA` 才能在 warp group 尺度上稳定消费这些数据

这个理解还有一点不确定的因素。

第一，`FP8/Transformer Engine` 是 Hopper 的数值控制面，但当前仓库还没有足够直接的专利证据去写死 scale 存储位置、舍入边界或 TE 与 `WGMMA` datapath 的内部接口。

第二，`SMEM/DSM -> WGMMA` 的最后一跳目前仍只能写成接口级判断：公开资料能说明 tile 驻留、barrier 完成和 warpgroup 消费之间的契约，但不能据此反推出完整的 operand collector 或内部流水结构。

所以 Hopper 的历史地位，不是又一代 `Tensor Core` 增强，而是**把 GPU 从以单 `SM` 为主要 shared-memory 协同与共享状态边界的执行机器，推向 Thread Block Cluster / DSM 这一类 cluster 级协同执行机器**。官方材料中的 thread block clusters、`DSM`、`TMA`、transaction barrier 与 PTX `wgmma.mma_async` 共同支撑这一点；

### 2.5 Blackwell：问题继续向 package 与 chiplet 边界外推

Hopper 并非终点。它只是把问题从单个 `SM` 内部怎么组织推进到了 cluster 怎样协同。Blackwell 接手的问题则进一步外推：

- 精度继续下沉到 `FP4 / MX`
- `Tensor Memory (TMEM)` 被写成显式 on-SM 对象，把 Tensor Core 附近的 tile / 中间结果存储正式抬到前台
- Tensor Core 继续和更大粒度的数据搬运、执行编排绑定
- 互连与封装从跨 `GPU` 链路继续推进到更紧的 die-to-die / package 级结构

官方正文已经把 Blackwell 写成 `two reticle-limited dies`、`10 TB/s chip-to-chip interconnect` 和 `unified single GPU`。这说明它不是单纯把 Hopper 做大，而是在软件仍看到一个 CUDA GPU 的前提下，把物理实现拆成两个受 reticle 限制的 die，再通过封装内互连重新合成一个统一 GPU 对象。

![](https://pica.zhimg.com/v2-12ede2cf282beac6976554334d8c688c_r.jpg)

这里给的是加速效果对比，根据整个计算平台来比而非单SM、单条 Tensor Core 指令或某个 datapath 的固定倍率：`FP8/FP6` 峰值被写成 `20 PFLOPS`，约为 Hopper 的 `2.5X`；新增 `FP4` 被写成 `40 PFLOPS`，约为 `5X`；`HBM Model Size`、`HBM Bandwidth` 和 `NVLINK All-Reduce with SHARP` 分别给出 `6X`、`5X`、`4X` 的系统侧提升。它说明 Blackwell 的性能提升来自低比特 Tensor Core、HBM 容量/带宽、NVLink collective 和软件栈共同作用，而不只是一条矩阵管线变快。

这三条线要分开理解。

第一条是 **single-die -> unified multi-die single GPU**。Blackwell 官方材料没有说 CUDA 程序员要把它当成两颗 GPU 编程；相反，[Blackwell Tuning Guide](https://docs.nvidia.com/cuda/archive/12.8.0/blackwell-tuning-guide/index.html) 仍强调它延续并扩展既有 CUDA 编程模型。因此，这里的变化发生在过去常被默认绑定在一起的两件事之间：软件看到的 `GPU` 仍是统一对象，物理实现却已经可以由两个 GPU die 和封装内高速互连共同组成。

```text
software view:
  one CUDA GPU

physical implementation:
  die 0  <->  package chip-to-chip fabric  <->  die 1
```

第二条是 **FP4 / MX / Transformer Engine Gen2**。如果只写 `FP8 -> FP4`，读者会误以为 Blackwell 只是把 payload 位宽再减半；实际更关键的是 scale、metadata、block size、packing 和格式选择也进入了矩阵任务的描述空间。NVIDIA 官方页把第二代 `Transformer Engine` 和 `micro-tensor scaling` 放在一起讲；后续 [NVFP4 技术博客](https://developer.nvidia.com/blog/nvfp4-trains-with-precision-of-16-bit-and-speed-and-efficiency-of-4-bit/) 又把 NVFP4 写成 micro-block scaling、E4M3 scale factor、Hadamard reshape、2D block quantization 和 stochastic rounding 共同成立的一套 recipe。也就是说，Blackwell 的低比特是一组组合契约：

```text
payload bits
  + scale factor
  + block granularity
  + metadata / packing
  + Transformer Engine format policy
```

![](https://pic2.zhimg.com/v2-ae5040a0a0ace9291f346c90dbdb90a1_r.jpg)

图源： [NVFP4 Trains with Precision of 16-Bit and Speed and Efficiency of 4-Bit](https://developer.nvidia.com/blog/nvfp4-trains-with-precision-of-16-bit-and-speed-and-efficiency-of-4-bit/)。

第三条是 **implicit operand residency -> explicit Tensor Memory object**。根据 CUDA Binary Utilities 的 Blackwell 指令集，`tmem[URX]` 已被列成合法位置，`LDT/LDTM` 被写成从 `Tensor Memory` 载入矩阵到寄存器文件，`STT/STTM` 被写成从寄存器文件把矩阵写回 `Tensor Memory`，而 `UTCCP/UTCSHIFT` 又把 shared memory 与 `Tensor Memory` 之间的搬运和重排写成独立对象。也就是说，Blackwell 关心的不止是“怎样把 tile 送到 `SMEM/DSM`”，还包括哪些 operand、accumulator、scale 和 metadata 应该停在 Tensor Core 更近的一层专用存储里。

这也解释了为什么 Blackwell 不能被简单理解成“取消 Tensor Core”或“退回 warp-level Tensor Core”。它取消 / 替换的是 Hopper 那种显式 `WARPGROUP` / `*GMMA` / `WGMMA` 风格的 SASS 编码与执行接口，新的主线变成 `tcgen05.mma`、`OMMA/QMMA`、`TMEM` 与 `UTC*` 这组对象。关键变化是发起语义和数据驻留位置被拆开：Hopper 仍强绑定 warp-group collective issue，多个 warp 要共同执行 `wgmma.mma_async` 并用 group commit / wait 管完成；Blackwell 的 `tcgen05.mma` 则把 MMA 发起写成 single-thread semantics，也就是一个线程可以启动整次矩阵操作，但 operands、scale、metadata 和结果更新由 Tensor Memory 上的任务与布局承载。这里的 single-thread semantics 描述的是“谁发起计算”，不等于一个线程真的完成全部矩阵乘加；它也打破了“整个 warpgroup 必须同步执行同一条 MMA 指令”这个表面约束。因此，更准确的读法是：

```text
Hopper:
  warpgroup collective issue
    -> WGMMA consumes SMEM / DSM resident tile
    -> result path returns through the group-level MMA protocol

Blackwell:
  one issuer
    -> TMEM-resident MMA task
    -> tcgen05.mma / OMMA-QMMA consume task descriptors
    -> TMEM-resident accumulator / D update
```

矩阵指令的“语义中心”从 warpgroup 持有的寄存器 fragment，迁移到了 TMEM 中的矩阵状态 + descriptor 描述符 + tcgen05 的CTA/CTA-pair 指令协议。

在 Hopper wgmma 里，d accumulator 和可选的 a fragment 是分布在参与线程上的寄存器操作数，指令语义天然围绕 warpgroup collective 展开；PTX 也明确说 d 是分布在参与线程上的 accumulator/destination，访问前要用 wgmma.wait_group 同步。到了 Blackwell tcgen05，PTX 把 5th-gen TensorCore 的专用 Tensor Memory 定义成每 CTA 的二维片上存储，D 在 TMEM，A 可在 TMEM 或 shared，B 在 shared；[tcgen05.mma](http://tcgen05.mma/) 用 [d-tmem]、[a-tmem] 或 a-desc、b-desc、idesc、[scale-A-tmem]、[scale-B-tmem] 这类地址/描述符来表达操作。更关键的是，[tcgen05.mma](http://tcgen05.mma/) 是 single-thread issue semantics，不再是 mma.sync / wgmma.mma_async 那种 collective issue 语义。在 Hopper wgmma 里，d accumulator 和可选的 a fragment 是分布在参与线程上的寄存器操作数，指令语义天然围绕 warpgroup collective 展开；PTX 也明确说 d 是分布在参与线程上的 accumulator/destination，访问前要用 wgmma.wait_group 同步。

到了 Blackwell tcgen05，PTX 把 5th-gen TensorCore 的专用 Tensor Memory 定义成每 CTA 的二维片上存储，D 在 TMEM，A 可在 TMEM 或 shared，B 在 shared；[tcgen05.mma](http://tcgen05.mma/) 用 [d-tmem]、[a-tmem] 或 a-desc、b-desc、idesc、[scale-A-tmem]、[scale-B-tmem] 这类地址/描述符来表达操作。更关键的是，[tcgen05.mma](http://tcgen05.mma/) 是single-thread issue semantics，不再是 mma.sync / wgmma.mma_async 那种 collective issue 语义。

最后是系统互连。Blackwell 不只在封装内把两个 die 合成一个 GPU，还把外部互连继续推向更大的 GPU 域。NVIDIA 官方页把第五代 `NVLink`、`NVLink Switch` 和 `NVL72` 放在同一段里讲；这里的架构含义是，单 GPU 内部的 die-to-die 统一视图和多 GPU 之间的 NVLink / NVSwitch 域开始共同服务一个问题：怎样让更大的模型、更多 GPU 和更细的低比特矩阵任务保持足够高的互连效率。

它支撑的是系统级外推：Blackwell 的问题已经不只在 `SM` 内部，而是从 Tensor Core 近端存储、封装内互连一直推到 rack-scale NVLink 域。

因此，Blackwel传递的信息不是故事已经完结，而是**后续问题已不再局限于 `SM`，而是越来越涉及 package、fabric、format 与协同域之间的整体组织**。如果说 Fermi 的关键是把 `global` 访问语义推到 memory-side，Volta 的关键是把矩阵 datapath 和执行语义从通用机器里拆出来，Hopper 的关键是把协同执行域推到 cluster，那么 Blackwell 更像是在 Hopper 之后继续推开两条此前还没有完全显式化的边界：一条是 Tensor Core 近端存储从隐含实现层变成显式 ISA / 工具链对象，另一条是单 die 物理实现不再天然等同于软件看到的单 GPU。

### 2.6 其他公司也在把 tensor-near storage 写成显式对象

严格说，Blackwell 的 `TMEM` 这一命名方式目前仍很 NVIDIA；但如果把视角放宽到“把张量 tile / 中间结果 / 高复用 operands 固定在算子近端的专用存储层里”，其他公司其实也已经把相近问题写成了专利，只是命名口径不同，常见写法包括 `tensor register file`、`tile registers`、`activation/weight/output buffer`，以及 memory-side 的 tensor-aware buffer。

- `US10372456B2`（Microsoft，最早优先权日为 2017 年）把 `tensor memory manager`、input queue 与按算子类型划分的 `tensor register file` 写成明确对象；其关键点是不同 tensor calculators 旁边可以有各自 dedicated 的 tensor register files，张量按操作类型被路由到近端寄存存储，而不是只经一个统一大存储反复转发。
- `EP4020173B1`（Intel，最早优先权日为 2020 年）把 matrix operations accelerator 的 `data buffers` / `tile registers` 与 vector registers 之间的 `load-to-tile` / `store-from-tile` 直连路径写成 ISA 对象；这和 Blackwell 把 `LDT/LDTM`、`STT/STTM` 显式化的思路很接近，只是它对应的是 CPU-side matrix engine。
- `US11922306B2`（Meta，最早优先权日为 2020 年）把 `multi-bank activation memory`、`weight buffer`（可实现为 register file）、`output buffer` 和 tensor controller 串成一条本地数据编排链；重点不是单个 `MAC`，而是 activations、weights 与 partial sums 如何在 tensor processor 的本地层次里被调度和复用。
- `US10956315B2` / `US12229044B2`（Micron，同一 family，最早优先权日为 2018 年）从 memory-side 反向切入：memory controller 为 tensor-friendly address pattern 保留 `data buffer`，让频繁复用的 matrix data 可直接从 buffer 重读，而不必每次回到 memory array；这说明“tensor-aware memory” 也可以先从 memory subsystem 一侧长出来。
- `US11609785B2`（AMD，最早优先权日为 2019 年）没有直接叫 `TMEM`，但它把 `GEMM` 中的 shared matrix block 在一次访问后广播到多个 compute unit 的 `local data stores`；关注点同样是让同一份 matrix / tensor 数据在近端多次复用，而不是重复走远端存储路径。

把这些专利和 Blackwell 放在一起看，会更容易发现：行业共识其实不是某个名字，而是同一个方向。只要矩阵/张量算子变成主路径，传统 `RF + SMEM/L1 + L2` 往往不足以同时承载吞吐、复用与编排需求，于是各家都会把 `tensor-local storage` 抬成更显式的对象，只是有人叫 `tensor register file`，有人叫 `tile buffer`，有人从 `activation/weight/output buffer` 或 `tensor-aware memory controller` 来表达。

## 3. 不同技术维度的演进

### 3.1 执行模型：从 `warp lockstep` 到 cluster 级协同 launch

**核心问题：** 早期 GPU 把 `warp` 视为天然的同步推进单位，这让控制逻辑得以简化，但也把分歧、长等待和异步事件都压缩成了整个 warp 先一起停一下。

**关键改变：** Volta 第一次系统性改写了这条默认假设。与其说 `ITS` 是一项调度优化，不如说它把线程前进语义从 warp 这个默认同步前进单位里拆了出来。

**成熟阶段：** Ampere 的公开主线更明确地体现在 `cp.async`、格式扩张和结构化稀疏；专利侧的 `shard scheduling` 则提示调度粒度仍在继续下探，但这里应作为旁证而非官方特性清单。Hopper 的 `CGA` 和 cluster launch 再把协同粒度往上提。于是执行模型不再只是一个 warp 怎样前进，而变成哪些更小的对象可以独立等待、哪些更大的对象可以一起协同启动。

### 3.2 供数链：从 `RF/collector` 到 `cp.async/TMA` 驱动的 staging

**原始问题：** 只要执行核心还是通用 `ALU/FPU`，近端供数链主要回答如何把寄存器值及时送到执行口。一旦专用矩阵路径出现，这条链就会立刻承压。

**关键改变：** Kepler 用 collector cache 把 `RF -> collector` 的局部复用写清，Volta 用 `US10338919B2` 把 `HMMA datapath` 的入口直接固定下来，说明供数已不再只是在喂通用 `ALU`。

**成熟阶段：** Ampere 的 `cp.async` 把 staging 从传统 LSU 路径中剥离成显式协议，Hopper 的 `TMA` 再把大块 tile 搬运交给专用单元，Blackwell 则进一步把 `Tensor Memory (TMEM)` 写成显式对象：`tmem[URX]`、`LDT/LDTM`、`STT/STTM`、`UTCCP` 说明供数问题已经从 staging protocol 继续推进到 Tensor Core 近端专用存储与移动对象。此后怎么把数据送到算子入口，就不再只是 register-level 的问题，而成了 protocol-level 加 dedicated-storage-level 的问题。

### 3.3 精度：从通用浮点路径到按计算语义分流的格式体系

**原始问题：** 当计算仍主要围绕通用浮点路径组织时，格式变化更像同一条管线支持更多模式；这还不是今天 Tensor Core 精度主线的写法。

**关键改变：** Pascal 的 dual `FP16` 是一个前兆，但真正的关键转折在 Volta：一旦 `HMMA` 变成独立 datapath，格式就开始跟着专用路径走，而不再只是通用 `FPU` 的参数表。于是 `FP16 input + FP32 accumulate` 成为第一组稳定类型。

**成熟阶段：** Turing 让 `INT8/INT4` 成为显式分支，Ampere 把 `BF16/TF32` 和结构化稀疏并列推进，Hopper 把 `FP8` 与 Transformer Engine 纳入进来，Blackwell 再把问题继续推向 `FP4 / MX`。这条线的真正主题不是格式越来越多，而是**格式开始服务不同计算语义与不同吞吐路径**。

### 3.4 同步原语：从寄存器相关性到 transaction 与 domain

**核心问题：** Tesla/早期 GPU 的同步更多围绕 pending write、scoreboard 与本地前进条件；它解决的是这条指令能否发出，而非这批异步工作是否真正可被消费。

**关键改变：** Maxwell 的 software scoreboard 与 convergence barrier 首先把同步对象从硬件隐式相关性推向可编程 barrier；Volta 之后，随着 `ITS`、异步搬运和更复杂的 reconvergence 进入主路径，同步原语不再只是调度系统的附属功能。

**成熟阶段：** Ampere 的 execution barrier 元数据让 `Join/Wait/Cancel` 稳定下来，Hopper 的 transaction barrier 与 memory sync domain 则把等待线程、等待事务、等待某个 domain 的可见性区分成不同层级。

### 3.5 互连：从片上 `crossbar` 到跨 `GPU` 与跨封装协同

**核心问题：** 早期互连问题更像是如何将 `SM` 侧请求送达 partition / memory interface，所以它很容易被视为后台布线问题，而非架构语义问题。

**关键改变：** Pascal 之后，互连不再只回答带宽是否充足，而开始回答协同边界应扩展到何处、一致性和可见性如何保障。随着 `NVLink`、`NVSwitch`、`C2C`、`NV-HBI` 的引入，互连就不再只是传输层，而成为协同模型的一部分。

**成熟阶段：** 互连问题已经从片上路由推进到跨 `GPU`、跨 CPU-GPU 域、再到封装内部协同。

## 4. 指令集层演进：SASS 变化如何把上面的硬件演进暴露出来

前面五条主线主要是在讲硬件边界如何变化；到了指令集层，问题就变成：**哪些新硬件对象已经重要到需要被写成明确的 SASS 指令，哪些旧协议又被新的编码与执行模型替换掉了。** 这里不把 SASS 当成一张孤立的 opcode 表，因为 opcode 本身只说明这个编码存在；真正有解释力的是 opcode 成组出现、成组退场时，它们把哪一类硬件状态、等待对象、供数路径或协同边界暴露了出来。

因此，指令集层并不是另一条与前面五条完全平行的物理主线，而更像它们在机器指令层的投影。一个执行协议如果仍然只是微架构内部细节，通常不会稳定出现在 SASS 读法里；一旦它变成 `BSSY/BSYNC`、`DEPBAR`、`LDGSTS`、`UTMA*`、`UCGABAR_*`、`LDT/LDTM` 这类指令或位置，说明编译器、汇编器、调度器和分析工具都必须开始正面处理它。也正因为如此，SASS 变化适合拿来做架构演进的旁证：它不替代专利和官方架构资料，但能帮助判断某个机制是否已经从“实现内部可能存在”推进到“工具链和机器码都必须承认”的阶段。

从这个角度看，可以先抓几组最有解释力的指令变化：

- 当执行模型被改写时，`SSY/SYNC` 这类旧 reconvergence 习惯会退场，`BSSY/BSYNC/WARPSYNC/DEPBAR` 这类新对象会出现
- 当矩阵路径从通用 `FPU` 里分流出来时，`HMMA/IMMA/BMMA/DMMA/GMMA` 先把矩阵路径写成 SASS 对象；到 Blackwell，Hopper 的部分 `*GMMA` / `WARPGROUP` 形式被移除，`OMMA/QMMA` 与 `TMEM` 相关指令成为新的观察点
- 当 warp-uniform datapath 被正式做出来时，`R2UR/S2UR/UIADD3/U*` 这类 uniform 路径指令会成批出现
- 当异步 staging、cluster 协同和 `TMA` 进入主路径后，`LDGSTS/LDGDEPBAR/UTMA*/WARPGROUP/UCGABAR*/UTCBAR` 这类指令会把新的等待对象、搬运对象和协同对象直接暴露出来

从这个角度看，SASS 指令历史不是零散的“新增指令清单”，而是另一种更贴近硬件边界变化的代际证据。完整 opcode 清单不适合继续压在总览 README 里；它应该放在 SASS 专题文档中，README 只保留这条线如何解释架构断点。

把指令的历史放回 Tesla 到 Blackwell 的主线里，可以得到一个很清楚的读法：

- **Maxwell / Pascal** 仍以传统 `SIMT`、经典 load/store、texture/surface、旧式 reconvergence 与整数/浮点混合算术为主，说明这时的 ISA 主体仍服务于那台“通用、锁步、单 `SM` 为主要边界”的机器。
- **Volta** 是第一次真正的大改写。新增的 `BSSY/BSYNC/WARPSYNC/DEPBAR` 把执行同步对象改写了，`HMMA/IMMA` 把矩阵路径正式写成指令，`FADD32I/FFMA32I/IADD32I/MOV32I` 这类形式则说明立即数和新 datapath 组织都被重新编码。与此同时，`SSY/SYNC/XMAD` 等旧对象退场，说明旧执行协议和旧整数乘加习惯不再是中心。
- **Turing** 的新增指令最能说明 uniform datapath 正式落地：`R2UR/S2UR/UIADD3/UIMAD/UISETP/ULDC/ULEA/USEL/USHF/VOTEU` 等一整串 `U*` 指令，说明 warp-uniform 值已经有了明确的数据路径与操作集合；`LDSM` 和 `BMMA` 则继续把矩阵供数与低比特矩阵计算往前推进。
- **Ampere / Ada** 没有像 Volta 那样改写基本方向，而是把新机器做成熟、做稳定。`LDGSTS` 和 `LDGDEPBAR` 让异步 staging 与等待协议直接进入指令层，`DMMA` 继续扩张矩阵路径，`F2IP/I2FP/UF2FP` 等则把格式转换与路径转换进一步做成常规操作。
- **Hopper** 让 cluster 协同、`TMA`、warp-group 和大块异步搬运第一次完整地长成一组 ISA 对象。`UTMA*`、`UCGABAR_*`、`WARPGROUP`、`UBLK*`、`ENDCOLLECTIVE`、`SYNCS`、`CGAERRBAR`、`PREEXIT` 这些名字本身就说明：等待的对象、搬运的对象和协同的对象，都已经不再局限于单个 warp 或单个 `SM`。
- **Blackwell** 则继续把问题推到更大的矩阵算子、更细的 uniform 浮点路径、更强的工作分发/传输协议，以及显式 `Tensor Memory` 对象上。`OMMA/QMMA`、`LDT/LDTM/STT/STTM`、`UTC*`、`UGETNEXTWORKID`、`UVIRTCOUNT`、大量 `UF*` / `UI*` 变体，说明 package/fabric/tensor/uniform 这些方向已经在 ISA 层继续外扩；同时，公开 SASS history 不再列出 Hopper 的 `WARPGROUP/WARPGROUPSET` 与部分 `*GMMA` 形式，所以这里不能写成 WGMMA SASS 形式继续增强，而应写成编码与执行协议继续收敛，矩阵任务从 warpgroup 指令表面下沉到 `TMEM + descriptor + tcgen05` 这一套新接口里。

## 5. 总结：三次架构重写

如果把近二十年最关键的三次架构重写，可归结为以下三条：

| 专利 | 代际 | 代表意义 |
| --- | --- | --- |
| US9639479B2 | Fermi | L2/partition 从被动缓存背景变成软件可观察、可调优的 memory-side 域 |
| US10338919B2 | Volta | HMMA datapath 从通用浮点路径中剥离出来 |
| US20230289189A1 | Hopper | shared memory 的有效作用域扩到 cluster 级 DSM |

十代架构总览

| 代际 | 执行 | 供数 | 精度 | 同步 | 互连 | 备注 |
| --- | --- | --- | --- | --- | --- | --- |
| Tesla | ⚠️ | ✅ | ❌ | ⚠️ | ✅ | 基线机器较清楚，早期 SIMT / scratchpad 根专利仍偏薄 |
| Fermi | ⚠️ | ❌ | ❌ | ❌ | ✅ | memory-side 很强，前端执行与统一地址空间仍待补 |
| Kepler | ⚠️ | ✅ | ❌ | ❌ | ⚠️ | 供数闭环很强，互连与 Dynamic Parallelism 仍偏骨架 |

将这三条串联起来，会得到一条清晰的主线：

- 先是**处理归属与控制语义**从 `SM` 内部往 memory-side 外扩
- 再是**执行与供数路径**从通用机器往专用机器分流
- 最后是**协同边界**从单 `SM` 向 cluster、互连和封装层继续外推

理解了这三步，Tesla 到 Blackwell 的十代时间线就不再松散，而更像同一机器不断被下一代压力重写的连续变革。
