面试进行到一半，面试官问：“我们这边三十多万份东西，制度文件、工单记录、会议纪要，客户提问，要给出带出处的答案。你会怎么搭？”

二面，对面是技术负责人，四十上下，说话不快，每句话都接着上一句的漏洞。

我说上 RAG。解析、切块、embedding 进向量库，查询来了先召回 top-k，把片段拼进上下文，让模型基于片段回答，答案后面带文档 ID 和段落号。

他点头，翻了一页纸：“那换个场景。一个代码仓库，有人问‘这个接口为什么一直 500’，你还建索引吗？”

我说不建。代码天天变，索引今天建完明天就过期，维护成本不划算。让 Agent 自己 grep、自己读文件，找到哪算哪。

“所以你的判断标准，是资料变不变？”

“……差不多。”话出口我就知道不结实。

他把笔放下：“那我问你。同一份代码仓库，报错字符串藏在某个日志样例里，或者被字符串拼接拆成了两段，grep 没命中。这时候你是认为这份代码里没有这个问题，还是知道它可能有、只是没搜到？”

我停了两秒：“可以多搜几轮，换个关键词再试。”

“多搜几轮是谁决定的？是它自己突然想到该换词，还是资料里有东西提示它该换？”

……

“你第一句话就把两件事混一起了。”他说，“一件是拿什么方式去找，另一件是谁来决定怎么找、找到什么程度算够。你把这两个当成一个东西在挑，后面怎么答都缺一半。”

他把纸推回来：“重新答一遍，两分钟。”

## 先把标答放这儿

如果这段只背一段，背这段：

> 这两个东西不在一个层面上，所以严格讲不能直接二选一。<br><br>RAG 的原意是检索增强生成：先去外面取证据，再让模型基于证据说话。它没有规定你用向量还是关键词，也没规定只检索一次。工程里说的 RAG，通常指“预建索引加固定检索链路”这一套，这是我们自己窄化出来的用法，不是定义。<br><br>所以要选的其实是两件事。一件是拿什么方式匹配：精确字符串、关键词、语义、还是混着来。另一件是取资料的流程由谁主导：写死的链路，还是让模型在运行时看着工具返回的结果决定下一步。这两件事可以自由组合。Agent 完全可以调向量检索，预建索引里也完全可以塞一个“改写查询再召回一次”的小循环，那不是矛盾，是同一套东西的两层。<br><br>落到具体任务，先看三个条件。资料量大、问题重复、答案落在明确的范围内，预建索引更划算：解析和建索引的钱只花一次，后面每个请求都在复用；出了问题能分段查，是没召回到，还是召回到了但排错序。反过来，如果一开始只能描述症状，读哪份材料要等读了上一份才知道，那就得把搜索放进运行时的循环里。这条路的代价有两个：轮数和延迟不稳定；以及它没搜到的东西，它并不知道存在。<br><br>工程上更常见的不是二选一，是组合。索引负责把候选范围缩到能读完的大小，Agent 负责打开原文、核对版本、顺着引用继续查。第一批候选只是入口，不是边界。验收看的是证据覆盖到哪、版本对不对、没读到的部分是不是真的不需要，而不是相似度分数或者搜索轮数。

这段话说完了，但里面有几个地方得展开，不然只是背下来。下面逐个说。

## 你比的可能不是同一个东西

RAG 这个词是 2020 年那篇论文带出来的，原意就一句话：生成之前，先从外部取一批证据，让模型基于证据回答。它解决的是模型参数里没存这些知识的问题，跟向量数据库没有绑定关系，也没说只能检索一次。后来工程界把它做成了一个固定套路：离线解析、切块、建索引，线上召回、重排、拼上下文、生成。大家嘴上说 RAG，指的往往就是这个套路。

“Agent 自己搜文件”说的是另一层：把搜索动作交给模型，在运行时一轮一轮决定。看目录、grep、读某个文件的某几行、发现一段配置、再顺着配置去查另一个仓库。

这两件事分属不同的层，而且每一层都能单独换。拆开看大概是这样：

- **切什么**：按文档切、按标题层级切、按函数切、按工单切，还是干脆不切，让模型自己定位行区间。
- **怎么匹配**：精确字符串、正则、BM25 这类词项匹配，稠密向量的语义匹配，或者两路一起召回再融合。
- **谁控制流程**：固定链路（查一次、排一次序、拼一次上下文），还是循环（查、读、判断缺口、再查）。
- **给模型看什么**：整篇原文、切好的片段、带行号的命中区间，还是只给路径让模型自己打开。

把这四层摆出来，很多争论就散了。有人跟你说“我们不做 RAG，我们让 Agent 自己搜”，你去问一句它的搜索工具背后是什么，十有八九是一个 Elasticsearch 或者向量服务。那它做的仍然是检索增强，只是控制流从固定链路换成了循环。反过来，一套标准的索引流水线里，如果加了“召回为空就改写查询重试”或者“答案里出现没见过的条款号就回原文补读”，那它已经有循环了，只是循环小一点。

还有一种更常见的糊弄法：把二十份文档整个塞进上下文，号称“长上下文 RAG”。那连检索都没有，是硬塞。短资料、一次性任务这么做没问题，资料一多就会撞上两件事：上下文放不下；以及放在中间位置的内容更容易被忽略，这个现象有专门的研究，不是玄学。

还有一个更容易骗人的地方：评测。

如果你拿一批“报错码是什么”“字段名叫什么”的题去比 grep 和向量检索，grep 大概率赢，因为答案是字面存在的，语义模型反而会把“ERR_CONN_REFUSED”和“连接失败”混成一类。但如果题目换成“出差住宿超标了怎么报”，正确答案分散在三份文件里，措辞跟提问完全不一样，grep 就开始吃亏。很多“grep 干掉 embedding”或者“向量库没用”的结论，往前追一步，是评测集只考了一种题型。

所以第一个要改的习惯：不要把“用向量还是用关键词”当成方案层面的选择。它是入口的选择，跟“流程由谁控制”是两回事，分开调，才谈得上选型。

## 预建索引：把理解资料的活儿提前干完

预建索引干的事情，说白了是把“资料长什么样、大概在讲什么”这件事，在用户提问之前先算一遍，然后把结果存起来复用。

整条链路五步，每一步都会掉东西，而且掉了以后很难发现：

**解析。** PDF 双栏排版读成乱序，扫描件走 OCR 把“1.5 万元”认成“15 万元”，Excel 一个 sheet 里三十个字段合并单元格，代码里的注释和字符串被当成正文。这一步错了，后面全错，而且模型会非常自信地基于错误文本回答。

**切块。** 很多默认值是 512 个 token、重叠一成到两成。这个值对新闻稿合适，对制度文件就不合适：一条“住宿标准按城市分三档”的表被拦腰切开，上半段在块 A，下半段在块 B，召回块 A 的时候模型只能看到“不得超过”却看不到后面的数字。所以更稳的做法是按结构切，标题到下一个标题之间算一块，表格单独处理，代码按函数切。

**建索引。** 稠密向量管语义近似，BM25 管词项命中，元数据管过滤（部门、生效日期、文档类型、版本）。三样都有，才叫能用的索引。只上向量，遇到专有名词和编号就瞎；只上 BM25，遇到同义改写就哑。

两路召回怎么合，是个容易被糊弄过去的细节。把分数直接相加基本不可行，余弦相似度和 BM25 分数量纲完全不同，加出来的排序没有意义。常见做法是各取前若干条，用倒数排名融合合并，或者各自归一化后按权重相加。这一步做不好，混合检索只是把两路的噪声叠在一起。

**查询侧。** 用户的问法往往不是文档里的说法。“报销超标怎么办”要改写成“差旅费 住宿费 标准 上限 超标 处理”，还要带上时间过滤，不然 2019 年作废的办法会被召回上来。

**排序和组装。** 召回 50 条，重排模型取前 8，去重，按来源和时间排，控制总长度。重排这一步值得单独留着，因为召回看的是“像不像”，重排看的是“这段能不能回答问题”：前者快而粗，后者拿问题和原文一起进模型打分，慢，但差距明显。不少系统省掉这一层，然后抱怨“明明召回了，答得还是不对”。

收益有三条，第三条最容易被忽略。

**一是复用。**三十万份文档解析一次，之后服务几百万次查询。算个粗账：每份切三块，就是九十万个向量，构建费用是固定的；问答量越大，摊得越薄。这是索引方案最实在的地方。

**二是可观测。**答错了，你能分段定位：是解析把表格读坏了，是召回根本没进来，是召回来了但重排排到第八位被截断，还是上下文太长把关键段挤掉了。产品要交付，这条比省钱重要。没有分段观测，你只能看着一个错误答案猜。

**三是延迟稳。**一次检索加一次生成，P95 好压，也容易做缓存和限流。

代价也得说清楚，不然就成了给索引站台。

**召回有天花板。** 切块切断了跨段关系；同义改写覆盖不全；表格和公式无论怎么解析都会损失结构。更麻烦的是“相似不等于适用”：一份制度里“住宿标准”和“住宿费上限”字面很近，但一个讲的是按城市分级的标准，一个是财务入账的口径。向量会认为它们几乎一样，答案却必须分清楚。摘要式的片段还会把限定条件省掉，“原则上不予报销”后面那半句“经分管领导审批可例外”经常不在同一块里。

**时效和构建成本，是同一件事的两面。** 文档改了、索引没刷，系统会继续拿旧条款回答，而且答得很流畅。所以索引里必须存版本号和内容哈希，检索结果要能回到原文位置，让下游发现“这段跟现在文件不一致”。全量重建贵，增量更新会漏，尤其是删改，周更加变更触发是常见折中，代价是永远有一段不一致窗口，你得承认它存在。不做这些，索引越用越像一份过期的复印件。

**top-k 是个两头堵的活。** 取少了漏，取多了噪声进来，真正有用的那段被稀释在中间。这不是调参能彻底解决的，只能在重排和上下文组装上补。

**权限要在检索前做。** 索引里混进无权文档，模型就已经看过内容了，生成阶段再过滤没有意义。ACL 必须进索引的元数据，过滤发生在召回之前。

一句话概括这一节：索引给你的是候选，不是判断。它算的是一个相似度的近似，替不了“这条到底适不适用”。

## 让 Agent 自己翻：把判断挪到运行时

自主检索的结构是一个循环：看当前问题和已知线索，决定下一步动作（列目录、grep、读文件某段、调语义检索），拿到返回结果，判断还缺什么证据，再决定下一步。停下来的时候，它得能说清自己读了什么、还有什么没解决。

灵活性到底从哪来，举一个具体的链条。线上 500 变多，网关日志里能看到 upstream timeout，指向 order-service；它的超时配置不在代码里，在 helm 的 values.yaml；改成 3 秒是因为下游 inventory 的 p99 已经到 2.8 秒；而 inventory 慢，是因为最近加的一个批量查询没走索引。

这条链在提问的那一刻不存在。“这个接口为什么 500”这六个字里，没有 helm、没有 inventory、没有批量查询。人能顺着线索走，Agent 也能，前提是它每一步都能读到新东西再改方向。预建索引也能支持这类追查，但要预先建一张“服务—配置—依赖”的图；图不存在的时候，边读边建反而更便宜。

代价同样具体。

**轮数和成本是浮动的。** 简单问题三轮就完，复杂问题十五轮也不稀奇。每一轮一次模型调用加一次工具调用，读进来的文件会一路累积。问答量一大，账单和延迟的方差都会很难看。

**结果不稳定。** 同一个问题跑两次，路径可能不同。这给评测带来麻烦：单次通过不能说明稳定，得多次采样看分布，还要把失败样本翻出来看它错在哪一步。

**覆盖不全是结构性的，这才是面试官那句反问的要害。** 它没搜到，通常有四种原因：

关键词猜错。报错信息说 timeout，代码里的变量叫 deadline；用户说“回款”，文档里写“应收账款回收”。

目录被忽略。vendor、dist、生成代码、另一个仓库，模型看一眼目录名就跳过了。

提前收工。找到一份看起来相关的 README，读了两段，觉得对上了，就不再往下查。

关系没跟。答案不在任何单份文件里，而在“A 的配置引用了 B 的默认值，B 的默认值在三年前的 changelog 里被改过”。

这四种，没有一种是“资料里没有”，全都是“它没想到去那儿”。所以“它没搜到就当不存在”不是一句刻薄话，是这类方案的召回边界：边界由模型想到的东西决定，不由资料全集决定。

靠提示词写“要仔细、别漏”压不住这件事，能压住的只有流程。结论必须配证据清单，每条结论对应文件路径和行号；有未解决的引用就不许收尾；跨目录的动作要留痕，事后能看出它绕过了哪里。

**工具返回的形态会直接影响探索质量。** 一次返回整份两千行的文件，和返回“路径、命中行号、前后三十行”，后者明显更利于模型继续判断，因为它能看见结构、知道自己读的是哪一段、下一轮还能定位。工具设计得糙，模型再聪明也在信息里淹着。

**搜索入口要和线索类型对上。** 精确的错误码、字段名、函数名，grep 和 rg 最快最准；模糊的业务描述，得靠语义召回，或者先读目录说明和 README，把用户嘴里的词换成资料里的词，再去精确搜。只会一种入口的 Agent，遇到另一种线索就废。

**上下文会膨胀。** 读了十个文件以后，最早的观察已经被挤出窗口。常见的处理是把观察落盘、写摘要、或者拆子任务隔离，代价是信息在传递中又损失一层。

**只读和权限要卡死。** 路径白名单、禁写、禁网、超时上限，这些不是可选项。一个能 rm 的搜索 Agent，迟早会 rm 掉点什么。

Agent 的长处是读到东西之后能改主意，短处是它不知道自己的盲区在哪。所以它必须留轨迹：搜了什么、读了哪些、哪条线索放弃了，否则你连复盘都没法做。

## 三个问题问完，答案基本就定了

**第一个问题：答案的位置，在提问的时候能不能描述出来？**

能描述，就是预建索引的主场。报销上限、某个接口的鉴权方式、某条制度的生效日期，这些都是“局部事实”，位置大概能圈定。不能描述，只能描述症状，就得靠循环。注意这里的分界不是“文档还是代码”，代码里也有大量能直接定位的局部事实，制度库里也有需要顺三条引用才能拼出来的答案。

现实里大多数任务不是纯的。一个客服系统，八成问题是重复的局部事实，两成要顺着单号往下追。这种就别争论到底哪个对，做分流：意图清楚、候选唯一的走快路径；命中几条互相矛盾的，或者问题里带“为什么”“一直”“还没”这种追查信号的，转慢路径。分流规则写在哪一层，比选哪个框架更影响结果。

**第二个问题：资料怎么组织，怎么变？**

目录清楚、命名规范、更新不频繁，直接搜很划算。二十万文件的 monorepo，三层目录，命名有约定，grep 就够用，建索引反而是多余的一层。反过来，三万个文件堆在共享盘里，命名靠各人习惯，同义词一堆，索引帮你把范围缩小是值得的。

高频变化的工作区，索引要付同步成本，直接读能读到当下的内容。但直接读也有坑：你可能读到旧副本、错误分支、没更新的挂载。两种方式都得回答同一个问题——我读的到底是哪一份。这不是方案差异，是两种方案共同的义务。

更新频率可以再往下拆一层。制度文件一年改两次，全量重建完全承受得起，顶多加个变更触发。工单和聊天记录每天新增几千条，你要么做增量同步，要么干脆别往索引里放，只在需要核对原始记录的时候让 Agent 去读。把“哪些资料值得进索引”当成一个独立问题，比笼统问“要不要建索引”省钱得多。

**第三个问题：响应和预算给到多少？**

固定链路容易给每一步设上限，延迟好预测。循环必须设闸门：最多几轮、最多读几个文件、单问多少 token、超了怎么降级。不设的话，一个模糊问题能烧到几十轮，还没人觉得不对。另外，别按架构名字推速度。向量库冷启动、文件系统 IO、外部服务抖动，都会让“理论上更快”的那条路实际更慢。

我一般还会追问第四个：出错的时候，你能不能看出来？

索引路线错在召回还是排序，可以分段查。循环路线错在“它没想到去那儿”，日志里能看到它搜过什么，但看不到它没搜什么。所以要留轨迹、做抽样复核，重要任务还得人工过一遍证据清单。这一问答不出来，说明方案只在顺利的时候成立。

四种典型任务大致这么对应：

- 大量资料上的高频局部问答，比如制度库、产品手册、客服 FAQ，走预建索引加相对固定的链路，成本可控、可观测。
- 依赖新观察、需要顺线索追查的，比如线上排障、合同条款的交叉核对、代码影响面分析，走 Agent 自主探索。
- 大范围里入口难找、找到以后还得深读的，比如几万份工单里找同类问题再逐份核对，先索引定位，再让 Agent 读原文。
- 资料很少、需要整体理解的任务，比如一份八十页的规范、一份刚签的合同，直接从头读，别先检索把它切碎。

有三条底线不随方案变化，值得单独记住：搜到答案不等于检查了所有文件；一个文件能被搜到，不代表提问的人有权读它；候选相关不等于内容适用。这三条踩了，方案再漂亮也是白搭。

## 组合怎么搭：索引给门牌号，Agent 进屋看

组合不是把两个东西并排放着，是分工。索引负责把候选范围缩到人读得完、模型读得完的尺寸，Agent 负责打开原文、核对版本、顺着引用继续查。

先看一个跑得顺的例子。客服工单里问“这个客户的退款为什么还没到”，索引召回三样东西：退款时效的制度条款、这笔单子的工单记录、支付渠道的对账说明。Agent 打开原文核对，制度写着 T+3 个工作日，工单显示第三天提交、第四天渠道受理，对账说明里还有一条遇节假日顺延。这三份材料谁都没法单独回答，但每一份都能被索引定位，最后的判断交给读原文那一步。整个过程四轮上下，比让 Agent 从几万份工单里瞎翻便宜得多。

一条具体的流水线大概长这样：

1. 查询改写，加权限和时间过滤，混合召回 30 条，向量和 BM25 各出一半。
2. 重排取 8 条，交给 Agent 的不是正文，是标题、路径、命中位置、八十来字的摘要、版本号。
3. Agent 打开其中两到四份原文，核对条件和上下文。摘要里被省掉的“经审批可例外”，就在这一步补回来。
4. 出现没见过的条款号、配置项、服务名，或者几份文件互相矛盾，触发 grep 或再检索一轮。
5. 组装答案，出处精确到段落，附版本和生效日期。

四个设计点决定这套东西好不好用。

**索引结果必须能回到原文。** 路径、偏移或行号、内容哈希，三样至少要有两样。只给一段摘要，Agent 没法核对，最后只能拿摘要当原文答，错的还很自信。

**第一批候选不能变成围墙。** 候选解释不了问题的时候，要允许改查询、扩大范围、去别的目录找。实现上就是：候选是提示，不是唯一可搜的集合。这一条听着像常识，实际系统里经常做不到，因为工具只暴露了候选文件，Agent 想出去也出不去。

**收尾要有规则，不能靠感觉。** 证据条数够不够、有没有未解决的引用、几份材料冲不冲突，这些可以写成检查项。让模型自己判断“差不多了”，它会在读完第三份的时候就差不多。

**成本要有闸门。** 候选里已经有直接答案、不涉及引用和条件分支的短问题，不进入探索循环，直接答。明确要通读的任务，先读全文，不要先用检索切一遍。这两种情况下硬套组合，等于花钱买慢。

组合最常见的四种翻车，我也列一下：

把摘要当原文，条件被省略，答案在边界情况上全错；索引和文件版本不一致，答案引用了一条已经删掉的条款；Agent 在候选文件里反复找不存在的答案，越找越确信；以及成本翻倍，一轮检索加五轮探索，本来三秒能答的问题变成半分钟。

上线以后，这套方案要盯的指标和单方案不一样：候选命中率、原文核对率（有多少答案其实是直接从摘要出的）、补查触发率、每问的平均工具轮数。前两个往下掉，说明索引在虚胖；后两个往上飙，说明分流条件没设好。

## 面试答题卡：四句话，十个追问

如果只让你说四句：

我一开始把“用什么方式搜”和“谁控制搜索流程”混成了一件事。RAG 不等于向量库，grep 也不等于 Agent。

预建索引拿的是复用和可观测，付的是维护成本和召回天花板；自主检索拿的是顺线索的灵活，付的是轮数波动和覆盖不全。

选型看三件事：证据能不能提前定位，资料怎么变，延迟预算多少。三个条件不同，答案就不同，没有通用最优。

组合是常态。索引定位，Agent 读原文并补查，验收看证据覆盖和版本一致性，不看相似度分数，也不看搜索轮数。

几个高频追问，可以直接拿去用：

**索引多久重建一次？** 全量周更，变更触发增量，查询时校验版本。不承诺实时一致，但承诺不一致能被发现。

**召回怎么评测？** 离线标一百到两百条“问题—正确文档”对，看 recall@k 和最终答对率。只看相似度分数会骗自己，相似度高的经常是不适用的那一条。

**Agent 怎么防止提前收工？** 要求它交证据清单和未解决引用，未解决引用不为零不许收尾。这条比任何提示词技巧都管用。

**上下文超了怎么办？** 观察落盘加摘要，读文件用行区间不读整份，长任务拆子任务隔离。

**权限怎么控？** 检索前过滤，ACL 进索引元数据，工具层做路径白名单，只读沙箱。

**成本怎么估？** 按每问的平均检索次数、读入 token、生成 token 三段算，设 P95 上限，别按平均值做容量规划。

**两种都上会不会更贵？** 会。所以要有快路径和慢路径的分流条件，短问答不进循环。

**表格和图片怎么处理？** 表格单独走结构解析，转成 HTML 或结构化行，别塞进文本切块；图片走 OCR 加图注，索引里存图的位置和说明。

**你这个方案什么情况下会失败？** 内部黑话和新术语、跨文档引用链、版本高频变动、权限边界复杂，这四种最容易出事。能自己说出失败条件，比背三条优点更像做过。

**预算只够上一套，先上哪个？** 先上索引，前提是问题重复度高、资料相对稳定。理由不是索引更先进，是它出错的方式更容易被发现。自主检索在资料不规整的时候确实更灵活，但它的失败往往长得像“答得挺像，只是漏了一份关键材料”，这种错误上线以后最难被抓到。

这类题真正在问的，不是让你站哪一边。它在问：你知不知道把哪部分工作交给了谁，前置多少，运行时留多少。

资料有多规整，问题有多模糊，出错的时候你能不能查出来，这三件事定了，选哪条路都不算错。反过来，这三件事没想过，选哪条路都只是碰运气。
