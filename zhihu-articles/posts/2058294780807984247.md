GraphMind · 开源 · 2026 年 7 月

[https://github.com/johnson7788/graphmind](https://github.com/johnson7788/graphmind)

先说结论

过去几个月，我断断续续做了一个叫 GraphMind 的项目——一个基于知识图谱的 RAG（检索增强生成）平台。你可以上传 PDF、图片、Word 文档、甚至手写笔记的照片，系统会自动解析里面的文字、表格、公式和插图，用大模型把实体和关系抽出来建成一张知识图谱，然后你可以在一张交互式的力导向图上浏览这些知识，也可以用自然语言向它提问。

项目已经开源，代码在这里： [https://github.com/johnson7788/graphmind](https://github.com/johnson7788/graphmind)

这篇文章不是教程，更像是我个人的一次技术复盘。聊聊为什么做、怎么做的、中间踩了哪些坑，以及最终的效果。如果你也在折腾 RAG 或者知识图谱方向的东西，希望这些经验能帮你少走点弯路。

## 为什么要做这个东西

故事的起点其实很简单：我手上有大量非结构化的文档——技术白皮书、行业报告、产品手册、会议记录。我想用大模型来问答这些文档里的内容，但普通的 RAG 方案（把文档切块→向量化→检索→喂给 LLM）总是差点意思。

具体来说，传统 RAG 有几个让我很头疼的问题：

实体之间的关系丢了。比如"张三在 A 公司担任 CTO"和"A 公司收购了 B 公司"，这两条信息在不同的文档里，但张三和 B 公司之间其实有隐含的关联。纯向量检索很难发现这种跨文档的关系。

全局理解能力弱。问"这批文档整体在讲什么"，传统 RAG 只能给你检索到几个最相关的文本块，很难给出一个全局性的总结。

多模态内容处理不了。PDF 里的图表、表格、公式，大多数 RAG 方案直接就忽略了。但很多时候，最有价值的信息恰恰在图表里。

所以我就想：能不能把知识图谱和 RAG 结合起来？用图谱把实体和关系结构化地存起来，查询的时候既能利用图的结构做推理，又能利用向量检索做语义匹配。

## 技术选型的纠结

最早我试过微软的 GraphRAG，说实话理念很好，但实际用起来有几个问题：一是它的索引流程太重了，动不动就要跑很长时间；二是它对多模态内容的支持基本为零——PDF 里的图片、表格直接跳过；三是社区检测（Leiden 算法）虽然能给出宏观概览，但在我的场景下效果一般，反而增加了很多复杂度。

后来我发现了两个项目：LightRAG 和 RAG-Anything。LightRAG 是香港大学开源的轻量级知识图谱 RAG 框架，索引速度快得多，而且提供了 5 种检索模式（naive、local、global、hybrid、mix），灵活性很好。RAG-Anything 则是建在 LightRAG 之上的多模态扩展，它集成了 MinerU 做文档解析，能把 PDF 里的图片、表格、公式都提取出来，作为独立的实体节点写进知识图谱。

这两个项目组合起来，基本完美覆盖了我的需求。于是我做了一个决定：把原来基于微软 GraphRAG 的后端全部换掉，迁移到 LightRAG + RAG-Anything 上来。这就是 GraphMind 的由来。

## 整体架构

先放一张技术栈全景：

| 层级 | 技术 |
| --- | --- |
| 后端框架 | FastAPI + Uvicorn |
| 知识图谱引擎 | LightRAG 1.5 + RAG-Anything 1.3 |
| 文档解析 | MinerU 3.4（多模态 OCR） |
| LLM / Embedding | 阿里云 qwen-plus / text-embedding-v3（OpenAI 兼容 API） |
| 前端框架 | React 19 + TypeScript + Vite |
| UI 组件 | Ant Design 6 |
| 图谱可视化 | sigma.js + graphology（ForceAtlas2 布局） |
| 状态管理 | Zustand |

整个系统分为前后端两部分。后端负责文档管理、索引构建、图谱读取和搜索问答；前端负责交互界面，包括数据集管理、图谱可视化浏览、智能问答和数据浏览四个页面。

## 用起来是什么样

用一个实际的例子来说明整个流程：

第一步，创建数据集。在前端页面点一下就行，后端会在 data/ 目录下创建一个独立的文件夹，每个数据集互不干扰。

第二步，上传文档。支持 PDF、图片（JPG/PNG 等）、Office 文档（Word/PPT/Excel）、纯文本（.txt/.md/.csv）。原始文件会保留在 input/ 目录下。

第三步，构建图谱。这是核心步骤——MinerU 先用 OCR 把文档解析成结构化的 Markdown + 多模态资源（图片截图、表格截图等），然后 RAG-Anything 调用 LLM 从解析结果中抽取实体和关系，写入 LightRAG 的知识图谱。一个 3 页的 PDF 大概能抽出 200 多个实体和 500 多条关系，包括图片、图表这类多模态节点。

第四步，浏览图谱。在图谱可视化页面，所有实体以力导向图的形式展示。你可以按实体类型筛选（人物、组织、图片、图表等），点击节点查看详情，双击节点展开它的邻域子图。图片类型的节点会直接显示缩略图。

第五步，问答。在搜索页面选择检索模式（mix/local/global/hybrid/naive），输入问题，系统流式返回答案。如果你附带了一张图片提问，还会触发 VLM（视觉语言模型）增强问答。

## 五种搜索模式，到底有什么区别

这个我觉得值得单独说一下，因为 LightRAG 的 5 种模式确实容易搞混。

naive（基础 RAG）：最简单，不用知识图谱，纯向量检索。把问题向量化，找最相似的文本块，喂给 LLM。适合"文档里有没有提到 XX"这种关键词匹配型问题。

local（本地搜索）：以实体为中心。先从问题中识别出实体名，在图谱中定位到这些实体，展开它们的邻居，拿到相关的文本块和关系描述，一起喂给 LLM。适合"XX 和 YY 之间是什么关系"这种聚焦性问题。

global（全局搜索）：以关系为中心。利用图谱中的高层关系信息做聚合。适合"这篇文档整体在讲什么"这种概括性问题。

hybrid（混合模式）：local + global 的结合，同时在图谱内做实体检索和关系检索，然后合并结果。兼顾细节和全局视角。

mix（混合检索）：在 hybrid 的基础上，再额外叠加一路纯向量文本块检索。这是最全面的模式，也是默认推荐的模式。

简单记：hybrid 在图谱内做两路检索，mix 是 hybrid 的超集，在图谱之外再加一路向量检索。日常使用直接用 mix 就行，除非你想对比不同模式的效果差异。

## 踩过的坑（这部分可能最有用）

迁移过程比我预想的要曲折得多。这里把几个主要的坑记下来，算是给后来者的避坑指南。

### 坑 1：Embedding 维度的"套娃"问题

LightRAG 的 openai_embed 函数本身已经被包装成了一个 EmbeddingFunc 对象（默认维度 1536）。如果你按照文档示例，再把它用 functools.partial 包一层传给 EmbeddingFunc，就会触发一个很诡异的错误——"total elements (N) cannot be evenly divided by expected dimension (1536)"。

原因是 EmbeddingFunc 的 __post_init__ 方法会检查 func 参数是不是 EmbeddingFunc 类型来做自动解包，但 partial 对象不是 EmbeddingFunc，所以解包失败，内层的 1536 和外层你设置的 1024 打架了。

解法：直接用 openai_embed.func（拿到原始的未包装函数），然后设 send_dimensions=True，这样维度信息会正确传给 API。

### 坑 2：MinerU 模型下载在国内网络环境失败

MinerU 首次运行时会从 Hugging Face 下载解析模型（VLM 模型大约 2.3GB），在国内网络环境下基本必挂。解决方案是在代码里设置环境变量 MINERU_MODEL_SOURCE=modelscope，让它从 ModelScope 下载。ModelScope 的模型和 Hugging Face 是一样的，但国内速度没问题。

### 坑 3：pypdfium2 版本冲突的死锁

这个坑最恶心。MinerU 依赖的 pdftext 库硬编码了 pypdfium2==5.9.0，但 5.9.0 删掉了 PdfImage.get_pos 方法，而 MinerU 的分类模块还在用这个方法。降版本？不行，pdftext 直接崩。不降？MinerU 报 error（虽然实际上 fallback 了，但 RAG-Anything 看到 stderr 里有 error 就认为失败了）。

最终的解法出奇地简单：把 MinerU 的 parse_method 从 "auto" 改成 "ocr"。因为那个有问题的分类逻辑只在 auto 模式下运行，ocr 模式直接跳过了。一行配置解决了一个让我折腾了两天的问题。

### 坑 4：RAG-Anything 和 LightRAG 的版本漂移

LightRAG 在 1.5 版本引入了 role_llm_funcs 这个运行时配置项（不是 dataclass 字段），但 RAG-Anything 1.3.1 还是按老方法用 asdict() 做配置拷贝，这个操作直接把 role_llm_funcs 丢了——结果就是所有多模态内容（图片、表格、公式）在处理时全部报错被丢弃，最终建出来的图谱里一个多模态节点都没有。

解法是写了一个 patch 函数，在每次创建 RAG-Anything 实例后手动把缺失的配置项补回去。而且这个 patch 必须在所有创建实例的代码路径上都调用——我一开始只在查询路径上调了，忘了在索引构建路径上也调，结果通过前端构建的数据集仍然没有多模态节点，排查了好久才发现。

### 坑 5：依赖安装不能用 uv sync

因为 RAG-Anything 在 pyproject.toml 里钉了 lightrag-hku<1.5，但我们需要用 1.5.4 的 API 特性。所以 raganything 必须用 --no-deps 安装，然后手动管理依赖顺序。我写了一个 prepare.sh 脚本来自动化这个过程：先装 lightrag-hku[api]==1.5.4，再装 mineru[core]，再装 raganything==1.3.1 --no-deps。不优雅，但能跑。

## 多模态是怎么串起来的

很多人问我"知识图谱里怎么会有图片节点"，这里展开说一下。

MinerU 在解析 PDF 的时候，不仅会提取文字，还会把页面中的图片、图表、表格、公式等区域单独截图保存为 .jpg 文件，同时输出一份 content_list.json 记录每个区域的类型、位置和截图路径。

RAG-Anything 拿到这些多模态内容后，会调用多模态 LLM（比如 qwen-vl-max）对每张图/表/公式生成一段文字描述，然后把这些描述当作普通文本一样做实体抽取。抽取出来的实体带有 image 类型的 entity_type，并且保留了指向原始截图的文件路径。

在前端，图谱可视化页面检测到节点有 image 属性时，会用 sigma.js 的 NodeImage 渲染器直接在图上显示缩略图。点击节点后，详情抽屉里也能看到完整截图。

这样就实现了一个完整的闭环：PDF 里的图表 → 被 MinerU 截图 → 被 LLM 描述 → 变成知识图谱节点 → 在前端可视化展示 → 可以被检索和问答。

## 前端可视化的选择

图谱可视化是这次项目里花心思比较多的部分。最早用的是 vis-network，功能全面但是性能不太好——节点多了以后明显卡顿，而且对图片节点的支持不够原生。

后来换成了 sigma.js + graphology 的方案，这也是 LightRAG 官方 WebUI 用的技术栈。sigma.js 是专门为大规模图可视化设计的，基于 WebGL 渲染，几千个节点也很流畅。配合 graphology 的 ForceAtlas2 布局算法，效果很好。

做了一些交互上的设计：

单击节点：右侧弹出详情抽屉，显示实体类型、描述、来源文件、截图（如果有的话）

双击节点：以该节点为中心展开 N 层邻域子图，方便探索局部关系

悬停节点：高亮该节点及其邻居，其余节点变暗

按类型筛选：通过实体类型（人物、组织、图片、图表等）过滤显示

图片缩略图：多模态节点直接在图上显示截图缩略图

## 项目结构一览

整体目录结构比较清晰，后端和前端分开，数据目录按数据集隔离：

graphmind/ 
 ├── backend/          # FastAPI 后端 
 │   ├── app/ 
 │   │   ├── routers/    # API 路由（datasets, documents, indexing, graph, search） 
 │   │   ├── services/   # 业务逻辑（rag_engine, indexing, search, graph, document, dataset） 
 │   │   ├── models/     # Pydantic 数据模型 
 │   │   ├── config.py   # 配置管理 
 │   │   └── main.py     # 应用入口 
 │   └── pyproject.toml 
 ├── frontend/         # React + Vite 前端 
 │   └── src/pages/    # DatasetManager, DataBrowser, GraphView, SearchQA 
 ├── data/             # 运行时数据（每个数据集一个子目录） 
 ├── doc/              # 设计文档与截图 
 ├── prepare.sh        # 后端环境准备 
 └── start.sh          # 一键启动

## 快速上手

如果你想自己跑一下，步骤很简单：

git clone [https://github.com/johnson7788/graphmind](https://github.com/johnson7788/graphmind) 
 cd graphmind 
 ./prepare.sh              # 安装 Python 依赖 + 下载 MinerU 模型 
 # 编辑 backend/config.local.yaml，填入你的 LLM API Key 
 ./start.sh                # 启动后端 (8777) + 前端 (5777)

然后浏览器打开 http://localhost:5777 就能看到界面了。后端 API 文档在 http://localhost:8777/docs（Swagger UI）。

支持的 LLM 服务：所有兼容 OpenAI API 格式的都可以，比如 OpenAI、阿里云通义千问（DashScope）、DeepSeek 等。我测试用的是阿里云的 qwen-plus + text-embedding-v3 + qwen-vl-max（视觉模型）。

## 写在最后

这个项目做下来，最大的感受是：RAG 这个方向，"能用"和"好用"之间的差距比想象中大得多。简单的向量检索 + LLM 确实能跑通，但加上了知识图谱的结构化表示之后，在跨文档关系推理、全局理解、可解释性这几个维度上的提升是质的飞跃。

而多模态的加入更是打开了一扇新门——文档里那些以前被忽略的图表和公式，现在也能成为可检索、可问答的知识了。这对于技术文档、科研论文、产品手册这类图表密集型资料来说，价值很大。

当然，这个项目还有很多可以改进的地方，比如索引速度可以进一步优化、图谱可视化可以加入更多交互、权限管理还没有做。但作为一个起步，它已经能满足我日常的知识管理和问答需求了。
