> 本文按「通信距离」从近到远分层 + Volta→Blackwell 代际演进(聚焦 Hopper/Blackwell)，系统熟悉GPU的通信方式

### 概览

**距离决定一切。** GPU 通信的性能由「通信距离」决定 —— 越远,延迟越高、带宽越低、软件栈越复杂。理解这条谱系,是理解后面所有通信方式的钥匙。

| 距离层级 | 方式 | 带宽 | 典型访问/通信延迟量级 | 引入代际 | 核心接口 |
| --- | --- | --- | --- | --- | --- |
| SM 内 | Shared Memory | ~128B/cycle/SM(聚合 TB/s) | ~10 ns | 历代 | __shared__ |
| 跨 SM(同 GPU) | DSMEM / Thread Block Cluster | ~SMEM 带宽 | ~10 ns | Hopper | cluster.sync |
| GPU 内 global↔shared | cp.async / TMA | 受 HBM 限制 | ~100 ns | Ampere / Hopper | cp.async / cuda::memcpy_async |
| 主机↔设备 | PCIe 5.0 x16 | 64 GB/s | ~1 us | 历代 | cudaMemcpy |
| 主机↔设备 | NVLink-C2C(GH200) | 900 GB/s | ~100 ns | Grace Hopper | 一致内存(透明) |
| 节点内 GPU 间 | NVLink / NVSwitch | 160→1800 GB/s | ~100 ns | Pascal→Blackwell | nvidia-smi topo |
| 节点内 GPU 间 | GPUDirect P2P | ~NVLink/PCIe | ~100 ns | Kepler | cudaDeviceEnablePeerAccess |
| 节点内/跨节点 | NVSHMEM | ~NVLink | ~100 ns | 库 | nvshmem_put/get |
| 节点间 | RDMA / RoCE | ~50 GB/s(NDR) | ~1 us | 库 | ibv_post_send |
| 节点间 | GPUDirect RDMA | ~NIC 带宽 | ~1 us | Kepler | GDRCopy |
| 集合通信 | NCCL | 组合(以上全部) | — | 库 | ncclAllReduce |

1. **延迟大致分为三档,带宽随距离逐级衰减**: SM 内 / 跨 SM **~10 ns** → 硬件直连(NVLink/C2C)与 GPU 内搬运 **~100 ns** → 协议栈(PCIe/RDMA)**~1 us**,相邻两档相差约一个数量级;带宽则由 **TB/s 级 → 百 GB/s 级 → 几十 GB/s** 递减。这正是「算力增长、通信跟不上」这一瓶颈的根源,也直接催生了 TMA、NVSHMEM、GPUDirect 等技术。
2. CPU 在物理上紧邻 GPU,但经 **PCIe 的访问延迟(~1 us)** 高于 GPU 间 **NVLink(~100 ns)** 约一个数量级 —— Grace Hopper 以 NVLink-C2C 取代 PCIe,正是为消除这一落差。

GPU 多卡节点具有明显的 NUMA-like 特征：不同 GPU、CPU、NIC、内存之间的访问路径和代价不同。

### 代际演进

**演进主线**:算力增长快于通信带宽,数据搬运跟不上,于是每一步都在把「搬运」从阻塞 SM 变成异步、再交给专用硬件。

| 代际 | 年份 | 代表卡 | NVLink 带宽(双向) | 显存带宽 | 通信相关关键特性 |
| --- | --- | --- | --- | --- | --- |
| Volta | 2017 | V100 | 300 GB/s(2.0) | 900 GB/s | NVLink 2.0、独立线程调度 |
| Ampere | 2020 | A100 | 600 GB/s(3.0) | ~2.0 TB/s | cp.async、NVLink 3.0、MIG |
| Hopper | 2022 | H100 / H200 | 900 GB/s(4.0) | 3.35 / 4.8 TB/s | TMA、Thread Block Cluster、DSMEM、mbarrier、L2 multicast、NVLink-C2C |
| Blackwell | 2024 | B200/GB200 | 1800 GB/s(5.0) | ~8.0 TB/s | NVLink 5.0、GB200 NVL72、更大 Cluster |

Turing 2018 通信增量少,略。Pascal 2016（NVLink 1.0 = 160 GB/s）,是 NVLink 的起点。

### 各代特性的设计动机

- **Volta**:单卡算力已无法满足需求 → 引入 NVLink 2.0,将 GPU 间带宽提升至 300 GB/s,多卡协同由此成为可能。
- **Ampere**:Tensor Core 性能持续提升,但 SM 内「加载 → 等待 → 计算」的模式使数据搬运占据大量执行时间 → 引入 **`cp.async`**,将 global→shared 拷贝异步化,SM 无需阻塞等待。
- **Hopper**:`cp.async` 仍需每个线程各自发指令、占用线程资源 → 引入 **TMA(专用硬件搬运单元)**,由单个线程发起整块数据搬运;同时引入**Thread Block Cluster + DSMEM**：为 GPU 内跨 block 的低延迟数据交换提供硬件支持；NCCL 则在更高层利用 NVLink/NVSwitch 等硬件能力实现集合通信优化。
- **Blackwell**:单机 8 卡已达 NVLink 4.0 拓扑上限 → **NVLink 5.0** 将带宽翻倍至 1.8 TB/s,并通过 **GB200 NVL72** 以 NVSwitch 全互联 72 块 GPU,形成一个高度互联的 GPU 计算域。

### 主机 ↔ 设备通信

CPU 和 GPU 之间隔着 PCIe 总线,这是最经典、也最容易被忽视的瓶颈之一。理解这一层,可循三个问题依次展开:**数据走哪条路**(物理通路)、**数据如何存放**(内存类型)、**如何高效搬运**(拷贝方式)。

### PCIe 与 NVLink-C2C

先看物理通路:数据在 CPU 与 GPU 之间走两条路 —— 传统的 **PCIe**,以及 Grace Hopper 上的 **NVLink-C2C**。

| 版本 | 速率 | x16 带宽(单向) |
| --- | --- | --- |
| PCIe 3.0 | 8 GT/s | ~16 GB/s |
| PCIe 4.0 | 16 GT/s | ~32 GB/s |
| PCIe 5.0 | 32 GT/s | ~64 GB/s |
| PCIe 6.0 | 64 GT/s | ~128 GB/s |

- `cudaMemcpy` 的 host→device 拷贝由 DMA(Direct Memory Access)引擎完成:CPU 只下发一条拷贝指令,DMA 硬件自行把数据搬进显存,不占 CPU 核心;但数据物理上仍须经由 **PCIe 的 root complex**(CPU/内存与所有 PCIe 设备之间的枢纽),这才是带宽与延迟的瓶颈所在。
- **NVLink-C2C**(Grace Hopper):CPU(Grace)和 GPU(Hopper)之间不走 PCIe,而是用 NVLink 直连,双向 900 GB/s,比 PCIe 5.0 高一个数量级,还带内存一致性。这是超算/大模型推理常用的「CPU-GPU 紧耦合」形态。

### 内存类型

物理通路既定,下一个问题是数据以何种形态存放 —— 内存类型决定了拷贝的代价,以及数据能否被两个处理器直接寻址。

- **页锁定内存(pinned / page-locked)**:`cudaMallocHost` 分配,物理页不会换出,是 DMA 直接搬的前提。普通 `malloc` 的可分页内存要先拷到一块临时 pinned 缓冲才能 DMA,多一次拷贝。
- **统一虚拟寻址(UVA)**:所有内存(CPU + 所有 GPU)共享一个虚拟地址空间,`cudaMemcpy` 能自动判断源/目标在哪个设备上。
- **托管内存(managed / unified memory)**:`cudaMallocManaged`,页按需迁移,编程最简便,但迁移有隐式开销,性能敏感场景要小心。
- **映射内存(mapped,即零拷贝)**:`cudaHostAlloc` 加 `cudaHostAllocMapped` 标志,把 pinned 内存映射进 GPU 地址空间,GPU 直接读写、免显式拷贝;但每次访问都走 PCIe,适合小数据、偶发访问,大批量数据仍应显式拷贝进 HBM。

### 调用方式

内存形态既定,便进入搬运环节:除零拷贝(直接访问)外,最常用的是显式拷贝,分同步与异步两种;异步配合 stream 可与计算重叠:

```text
// 同步拷贝(阻塞,拷贝完成才返回)
cudaMemcpy(dst, src, bytes, cudaMemcpyHostToDevice);

// 异步拷贝 + stream(可与计算重叠)
cudaMemcpyAsync(dst, src, bytes, cudaMemcpyHostToDevice, stream);
```

**Tips**:

- 用 **pinned 内存**承载待拷贝数据 —— 普通 `malloc` 的可分页内存需先经临时 pinned 缓冲,多一次拷贝。
- 用 **异步拷贝 + 非默认 stream**,使拷贝与计算重叠 —— 默认 stream 隐式同步,`cudaMemcpyAsync` 会退化为同步。
- 大批量、反复读的数据采用**显式拷贝**(后续从 HBM 读取);小数据、偶发访问才用**零拷贝** —— `cudaHostAlloc` + `cudaHostAllocMapped` 分配映射内存,拿 GPU 端指针直接交给 kernel,全程无 `cudaMemcpy`。
- pinned 内存存在 **NUMA 亲和性**:分配落在发起线程所在 NUMA node,若 GPU 挂在另一 socket,传输需跨 socket 互联;多 GPU 场景可用 `cudaHostAllocPortable` 或 `numactl --membind` 规避。
- 频繁的小拷贝每次有 ~1 us 启动开销,应合并为批量拷贝或走异步流水线。

### GPU 内部通信

数据在单块 GPU 内部的搬运与同步。下面三个例子:`cp.async` / TMA 是「global→shared 搬运」的两种方式,DSMEM 则是 shared memory 的跨 block 扩展。

### Shared Memory

block 内所有线程共享,`__shared__` 声明,`__syncthreads()` 同步。带宽极高(每 SM 每周期 ~128B),但要小心 **bank conflict** —— 同一 warp 里多个线程访问同一 bank 的不同地址会串行化。

### `cp.async`(Ampere)

**动机**:传统 `ld.global → st.shared` 要经寄存器、线程阻塞等待;`cp.async` 直接 `global → shared`,绕寄存器、且异步,发完指令线程即可继续。

```text
// smem_addr = shared 地址,gmem_ptr = global 地址,16 = 字节数
asm("cp.async.cg.shared.global [%0], [%1], 16;" :: "r"(smem_addr), "l"(gmem_ptr));
asm("cp.async.commit_group;");   // 提交一组
asm("cp.async.wait_group 0;");   // 等最旧一组完成
```

要点:

- `.cg` 绕 L1 只进 L2(`.ca` 进 L1+L2,`.cs` 流式 evict-first)。
- `commit_group`/`wait_group` 以「组」为单位同步,可流水线化 —— 提交多组后只等最旧一组,使拷贝与计算重叠。

### TMA / Tensor Memory Accelerator(Hopper,重点)

**动机**:`cp.async` 仍需**每个线程**发指令;TMA 是**专用硬件引擎**，由单个线程发起**整块 bulk**拷贝，并支持多维 tensor 数据搬运。并可通过 swizzle 等布局机制减少 shared memory bank conflict。

**核心调用**:host 编码描述符 → kernel 单线程发起:

```text
// host:编码 128B 的 Tensor Map 描述符(源地址/维度/tile/swizzle)
cuTensorMapEncodeTiled(&tmap, CU_TENSOR_MAP_DATA_TYPE_FLOAT32, 2, d_in,
                       dims, strides, box, elem_stride,
                       CU_TENSOR_MAP_INTERLEAVE_NONE, CU_TENSOR_MAP_SWIZZLE_128B,
                       CU_TENSOR_MAP_L2_PROMOTION_L2_128B, CU_TENSOR_MAP_FLOAT_OOB_FILL_NONE);

// kernel:单个线程发起整块拷贝 + mbarrier 同步
cde::cp_async_bulk_tensor_2d_global_to_shared(&smem, &tmap, 0, 0, bar);
bar.wait(...);   // 等 barrier 收到「字节到达」通知
```

要点:

- 同步用 **mbarrier**(`cuda::barrier`),完整链路 `init(bar)` → `fence_proxy_async_shared_cta()` → `barrier_arrive_tx(bar, 1, bytes)` → `bar.wait()`;TMA 完成后提交「字节到达」。
- 编译须用 **`sm_90a`**(`a` 后缀启用 Hopper arch-specific 特性)。
- 1D 场景可简化为 `cuda::memcpy_async(smem, gmem, cuda::aligned_size_t<16>(bytes), bar)`。

### Thread Block Cluster + DSMEM

**动机**:传统上 block 之间完全隔离,数据共享只能回 global memory 绕一圈。Hopper 引入 **cluster**,让同一 cluster 内多个 block 直接访问彼此的 shared memory(DSMEM)。

**核心调用**:

```text
cluster.sync();                                // cluster 内全局同步
int* peer = cluster.map_shared_rank(&smem, 0); // 把 rank0 block 的 shared 地址映射进本 block
*peer = 42;                                    // 跨 block 直接读写
```

要点:

- `__cluster_dims__(x,y,z)` 声明 cluster 形状;`map_shared_rank(&smem, rank)` 做跨 block 地址映射。
- **同步顺序是硬性要求**:写 shared → `__syncthreads()` → `cluster.sync()` → 读远端,缺一步即数据竞争。
- 这是 **NCCL 在 Hopper 上硬件加速 AllReduce 的基础**(block 间直接交换 partial sum,不回落 global)。

### 其他内部机制

- **L2 multicast**(Hopper):`cuda::multicast`,一次写 L2 可广播给多个 GPU/多个消费者,减少重复读。

**`mbarrier` vs `barrier`**(场景:线程发完 TMA 拷贝后,需等数据搬进 shared 才能继续计算):

- `__syncthreads` 数的是「线程到达」,因此只能同步线程彼此;
- 但 TMA 的搬运由**硬件后台异步完成**,期间没有线程在”等”——只数线程的 barrier 无从同步;`mbarrier` 在「线程到达」之外新增「字节到达」:TMA 搬完数据后向 barrier 汇报字节数,等待数据就绪的线程据此**结束等待、继续读 shared 做计算**。

### 同节点 GPU 间通信

一个节点内(通常是 8 卡)的 GPU 之间如何通信。本节自底向上展开:**物理拓扑**(NVLink/NVSwitch)→ **进程内直访**(GPUDirect P2P)→ **高级编程模型**(NVSHMEM)→ **跨进程共享**(CUDA IPC)。

### NVLink / NVSwitch 拓扑

先看硬件层:同节点内多块 GPU 通过 NVLink/NVSwitch 互联,这是后面所有通信方式的物理基础。

| NVLink 代际 | 架构 | 双向带宽 |
| --- | --- | --- |
| 1.0 | Pascal(P100) | 160 GB/s |
| 2.0 | Volta(V100) | 300 GB/s |
| 3.0 | Ampere(A100) | 600 GB/s |
| 4.0 | Hopper(H100) | 900 GB/s |
| 5.0 | Blackwell(B200) | 1800 GB/s |

- **NVSwitch**作为交换结构，将多块 GPU 接入统一的高速 NVLink fabric，使 GPU 间能够通过交换网络进行高带宽通信。
- 看拓扑用 `nvidia-smi topo -m`,矩阵里的代号含义:

| 代号 | 含义 | 好坏 |
| --- | --- | --- |
| NV1 ~ NV18 | 两块 GPU 之间有 N 条 NVLink | 最好 |
| PIX | 经过一个 PCIe switch | 好 |
| PXB | 经过多个 PCIe bridge | 中 |
| PHB | 经过 PCIe host bridge(到 CPU) | 中 |
| SYS | 走系统/CPU 之间(NUMA) | 差 |

**注意**:高频通信的 GPU 应落在 `NV*` 或 `PIX`,避免 `SYS`。

### GPUDirect P2P

拓扑确定后,进程内两块 GPU 便可直接互访显存——拷贝或 kernel 直接读写对端内存,不经 CPU 中转。

**核心调用**:

```text
cudaDeviceCanAccessPeer(&can, devA, devB);   // 先查:这对卡能否直访
cudaSetDevice(devA); cudaDeviceEnablePeerAccess(devB, 0);  // devA 授权直访 devB
cudaMemcpyPeer(dst, devB, src, devA, n);     // 跨卡直接拷贝,不经 CPU 中转
```

**注意**:P2P 是否可用、走 NVLink 还是 PCIe,由拓扑决定 —— 两卡不在同一 NVSwitch 下、或走 `SYS` 时,`cudaDeviceCanAccessPeer` 可能返回 false; 即便返回 true，也不代表性能一定理想；实际性能还取决于 GPU 间是通过 NVLink、PCIe 等哪条路径连接。

### NVSHMEM

P2P 只提供「直访显存」的底层能力;NVSHMEM 在其上构造 **PGAS(Partitioned Global Address Space,分区全局地址空间)编程模型**——在 GPU 间建立「对称堆」,每个 PE(Processing Element,相当于一个 GPU/rank)分配到同一块对称内存,用 `put/get/atomic` 做**单边**(one-sided)通信,发起方一个 PE 即可完成,无需对端像 MPI 那样配对收发。

**核心调用**:

```text
nvshmem_init();                                    // 初始化
int* dst = (int*)nvshmem_malloc(sizeof(int));      // 对称堆:每个 PE 同一地址
nvshmem_int_p(dst, mype, peer);                    // 把本 PE 的编号(mype)单边 put 到 peer 的 dst
nvshmem_barrier_all();                             // 全局屏障
```

三类单边操作,均无需对端配合:

```text
nvshmem_int_p(dst, 42, peer);              // put:主动往 peer 写(把 42 写到 dst)
int v = nvshmem_int_g(src, peer);          // get:主动从 peer 读(从 src 读回 v)
nvshmem_int_atomic_add(counter, 1, peer);  // atomic:对 peer 的值做原子操作(加 1)
```

要点:

- `nvshmem_malloc` 分配的**对称堆**,所有 PE 看到同一布局;`nvshmem_*_p` 是 typed put,另有 `get`/`atomic`/`collect` 等。
- **单边语义**:put/get 只需发起方一个 PE 参与,对端无需主动配合,延迟低、适合细粒度通信(如 DeepEP 的 expert 分发)。
- **底层依赖**:单机内走 NVLink 直连(本质是 P2P + 对称地址映射);跨节点需额外传输层(IB/NVLink-C2C)。
- 细粒度同步:`nvshmem_fence` 保证本 PE 之前操作有序,`nvshmem_quiet` 保证操作对远端可见。

### CUDA IPC

P2P 与 NVSHMEM 都限于**同一进程内**;跨进程共享显存则用 CUDA IPC(Inter-Process Communication):

```text
cudaIpcMemHandle_t handle;
cudaIpcGetMemHandle(&handle, ptr_A);      // 进程 A:导出句柄
cudaIpcOpenMemHandle(&ptr_B, handle, cudaIpcMemLazyEnablePeerAccess); // 进程 B:打开
```

与 P2P 的区别:P2P 是**进程内**多卡直连,IPC 是**跨进程**共享同一段显存。

### 节点间通信

跨机器通信以 RDMA 为基础,并针对 GPU 场景逐步演进。本节依次展开:**RDMA 基础 → GPUDirect RDMA → 更大规模互联**。

### RDMA 基础

先看最基本的跨节点手段:**RDMA(Remote Direct Memory Access)**。它有两种承载方式:

- **InfiniBand(IB)** vs **RoCE(v2)**:IB 是专用网络(有独立交换机、网卡、子网管理器);RoCE 是把 RDMA 语义跑在普通以太网上。两者编程接口都是 **verbs API** —— 无论底层是专用网络还是普通以太网,都用同一套 verbs 函数,换底层网络不用改代码。
- **零拷贝 + 内核旁路**:网卡(NIC)直接读写用户态内存,不经过内核协议栈,也几乎不占 CPU。这就是 RDMA(Remote Direct Memory Access)「直接」的含义。

核心概念(verbs 编程):

| 概念 | 含义 |
| --- | --- |
| PD(Protection Domain) | 资源保护域,QP/MR 都挂在它下面 |
| MR(Memory Region) | 注册一段可被网卡访问的内存(含本地/远端 key) |
| QP(Queue Pair) | 收发队列对,通信的基本单位 |
| CQ(Completion Queue) | 完成队列,收/发完成的异步通知 |
| GID | 全局地址(RoCEv2 下是 IPv6 风格地址) |

最小 verbs 流程:`ibv_get_device_list → ibv_open_device → ibv_alloc_pd → ibv_reg_mr → ibv_create_qp → ibv_post_send / ibv_post_recv → ibv_poll_cq`,按阶段拆:

| 阶段 | 函数 | 作用 |
| --- | --- | --- |
| 打开设备 | ibv_get_device_list → ibv_open_device | 枚举并打开一块 RDMA 网卡 |
| 建资源(一次性) | ibv_alloc_pd → ibv_reg_mr → ibv_create_qp | 分配 PD、注册 MR(把内存暴露给网卡)、建 QP(通信通道) |
| 收发(反复执行) | ibv_post_send / ibv_post_recv → ibv_poll_cq | 投递收发请求由网卡异步执行,再轮询完成队列 |

其中 **MR 注册** 与 **QP** 是核心,其余 PD/CQ/GID 是配套资源。

### GPUDirect RDMA

普通 RDMA 只能直读 CPU 内存;要发 GPU 数据,默认路径是 `GPU → CPU 内存 → 网卡`,多一次跨 PCIe 的搬运。**GPUDirect RDMA** 让网卡**直接读写 GPU 显存**,省掉 CPU 中转:

- 前提：RDMA NIC 和 GPU 支持 GPUDirect RDMA，GPU 显存可被 NIC 直接注册并访问。 典型路径：GPU 显存 ↔ RDMA NIC，避免 GPU → CPU 内存 → NIC 的中间拷贝。
- GDRCopy：提供 CPU 对 GPU 显存的低延迟映射访问，适合小块数据、flag 等控制信息的 CPU↔GPU 交互。
- 典型收益:跨节点训练里,梯度 AllReduce 的 RDMA 段不再经过 CPU,端到端通信延迟显著下降。

### 更大规模互联

单条 RDMA 之外,更大规模的训练集群还有几种互联形态:

- **NVLink over Fabric / NVSwitch 跨机箱**:把 NVLink 从「节点内」延伸到「机柜级」。
- **GB200 NVL72**:一个机柜里 72 块 B200 通过 NVSwitch 全 NVLink 互联,形成超大共享内存域,跨 GPU 通信不再走网络,速度接近单机多卡。
- **RoCEv2 + 以太网**:多数中小规模训练集群用 RoCEv2(400G/800G 以太网)跑 NCCL,成本远低于 IB。

### 集合通信

前面讲的是各层硬件的「点对点」能力;集合通信在其上提供多卡协同的原语,NCCL 再自动选择底层路径实现。本节依次展开:**集合通信原语 → NCCL**。

### 集合通信原语

集合通信解决多个 rank 之间的协同数据交换，不同原语对应不同的数据流模式和结果分布方式（per-rank algorithmic data volume 口径）:

| 原语 | 语义 | 典型 per-rank 通信量* | 典型场景 |
| --- | --- | --- | --- |
| AllReduce | 所有人归约，结果分发给所有人 | 2(N-1)/N × D | 数据并行 DP 梯度同步 |
| AllGather | 所有人贡献数据，最终每人拥有完整数据 | (N-1)/N × D | TP 中的激活/参数聚合 |
| ReduceScatter | 所有人归约，结果按 rank 切分 | (N-1)/N × D | TP / ZeRO 等 |
| Broadcast | 一个 root 将数据分发给所有 rank | 1 × D | 参数/配置分发 |
| AlltoAll | 每个 rank 向所有其他 rank 发送不同数据 | (N-1)/N × D | MoE 专家分发 |

### NCCL

原语只定义「要做什么」;真正落地的是 NCCL(NVIDIA Collective Communications Library)——事实标准的集合通信库,PyTorch/DeepSpeed 等训练框架底层都依赖它。

- **算法选择**:NCCL 会根据消息大小、通信拓扑等因素，在 Ring、Tree 等算法之间进行选择；在支持的 Hopper/Blackwell 平台上，还可利用 NVLS 等硬件加速路径。
- **拓扑感知**:NCCL 会自动探测 NVLink/NVSwitch 拓扑,为每个 `channel`(并行传输通道)分配不同的 NVLink/网络路径,尽量避开 `SYS`。
- **底层路由**:同节点走 NVLink(P2P);跨节点走 RDMA(IB/RoCE),GPUDirect RDMA 开启后直接读写显存。
- **关键指标**:`bus bandwidth`(总通信带宽)与 `algorithm bandwidth`(业务数据带宽)是两个不同口径,AllReduce 的 bus bandwidth 理论上是 algorithm 的 2(N-1)/N 倍,阅读 benchmark 时需注意区分。

常用环境变量(排障/调优):

| 变量 | 作用 | 典型取值 |
| --- | --- | --- |
| NCCL_DEBUG | 打印拓扑、channel、算法选择 | INFO |
| NCCL_P2P_LEVEL | 控制 P2P 走 NVLink 还是 PCIe | NVL(仅 NVLink 直连才用)、PIX;禁用则 NCCL_P2P_DISABLE=1 |
| NCCL_NET_GDR_LEVEL | 控制 GPUDirect RDMA 开关 | PIX(网卡-GPU 同 switch 才用)、DISABLE |
| NCCL_SOCKET_IFNAME | 指定 RoCE 网卡 | ib0 / eth0 等网卡名 |

**排障流程**:先 `NCCL_DEBUG=INFO` 看日志,确认 NCCL 实际探测到的拓扑与路径;路径不对再用其余三个变量纠正 —— 多网卡指错用 `NCCL_SOCKET_IFNAME`,P2P 走坏路径用 `NCCL_P2P_LEVEL`,GDR 不支持或变慢用 `NCCL_NET_GDR_LEVEL`。

### 通信生态与优化

前面按「通信距离」分层讲完了核心方式;本节补三块横切主题 —— **存储侧直读**(GDS)、**通信框架生态**(UCX/UCC/MPI)、**贯穿各层的优化思想**(计算通信重叠)。

### GPUDirect Storage(GDS)

- **动机**:数据加载(读 checkpoint、读训练数据)原来要 `NVMe → CPU 内存 → GPU 显存` 中转两次。GDS 让 NVMe 通过 DMA **直接写进 GPU 显存**。
- 接口:`cuFile`(`cuFileRead`/`cuFileWrite`),配合 `cudaMalloc` 的显存缓冲区。
- 适用场景:大模型 checkpoint 的快速加载/保存、数据加载流水线。

### UCX / UCC 与 CUDA-aware MPI

- **UCX**:统一通信抽象层,抽象出底层的 RDMA/TCP/shared memory 传输,很多库(NCCL 的某些后端、OpenMPI)构建其上。
- **UCC**:建立在 UCX 上的集合通信框架,是 NCCL 的开源替代思路。
- **CUDA-aware MPI**:MPI 实现能识别设备指针,`MPI_Send(dev_ptr, ...)` 直接传显存数据,底层自动走 GPUDirect RDMA,免手动搬回 CPU。

### 计算通信重叠

- **核心思想**:计算与通信使用不同硬件(计算用 SM,通信走 NVLink/RDMA/NIC),可用 CUDA Stream / TMA / `cp.async` 使二者并行,而非串行等待。
- 手段:**CUDA Graphs**(固化整段 kernel 图、减少启动开销)、流水线(计算当前 batch 的同时传输上一个 batch)、异步拷贝。
- 与前面的呼应:TMA 的异步 bulk 拷贝、NVSHMEM 的单边 put,本质都是为「重叠」提供更细粒度的原语。

---

### 总结

**「距离决定性能」**:从 SM 内 ~10 ns 到跨节点 ~1 us,每跨一层带宽掉一个数量级,这套谱系本质是 NUMA 思想在 GPU 系统上的延伸。**「搬运的异步化与硬件化」**:Volta 到 Blackwell 的每个新特性,都在把「搬运」从阻塞 SM 的同步操作,变成不占 SM 的异步/专用硬件动作(`cp.async` → TMA → NVSHMEM 单边 put → GPUDirect RDMA/GDS)。按场景选型,对照下表:

| 场景 | 用什么 |
| --- | --- |
| 数据在同一 block 内共享 | shared memory / __syncthreads |
| global→shared 搬运,想不阻塞 SM | cp.async(Ampere)/ TMA(Hopper, bulk) |
| 同一 cluster 多个 block 交换 | Cluster + DSMEM(Hopper) |
| 同一节点多卡,要细粒度单边通信 | NVSHMEM |
| 同一节点多卡,要集合通信 | NCCL(内部走 NVLink P2P) |
| 跨节点,要低延迟直连 | RDMA(IB/RoCE),开 GPUDirect RDMA |
| 加载 checkpoint/数据 | GDS(NVMe 直读显存) |

选好方式后,再用 `nvidia-smi topo -m` / `NCCL_DEBUG=INFO` 确认底层实际走的硬件。
