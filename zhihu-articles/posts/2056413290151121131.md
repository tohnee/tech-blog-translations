## 背景

最近在用Qwen的0.5B预训练权重搞了一个属于自己的小模型，但在进入后训练和部署阶段时，我遇到了一个非常棘手且尴尬的问题：现成的轮子，我一个都用不上。

原因是我的模型架构代码是完全自己手搓的，不兼容 HuggingFace 的标准生态。这就意味着，市面上那些针对标准模型做过极限优化的“神器”，我统统用不了，只能硬着头皮用自己写的原生 PyTorch 代码做推理。

当我把模型扔到 ModelScope的免费创空间上测试时，灾难发生了。免费空间的配置通常是 2核 CPU + 16G 内存，用纯Python + PyTorch在这台机器上跑自回归生成，速度简直感人，吐字像是在“挤牙膏”。

## 为什么会这么慢？

<br>在排查之后，我发现这锅不能全让 CPU 的算力来背，真正的瓶颈在于：

1. 内存墙：原生FP32模型大约 2GB。生成每个Token，CPU都要把这 2GB 数据从内存条完整地搬运到CPU缓存里算一次。2核CPU的内存带宽根本扛不住这种折腾。
2. 框架层开销与GIL锁：在生成时的for循环里，每步都伴随着Python的GIL锁切换、张量对象的频繁创建与销毁、以及torch.cat拼接KV Cache带来的显存碎片化。

## 方案

所以，我决定使用rust从零构建自定义推理内核！

为了彻底榨干CPU的性能，我使用了hf推出的极简Rust张量库Candle，配合PyO3，为我的自定义模型量身定制了一套底层推理引擎。

这套方案不仅完美复刻了我的模型架构，还带来了几个“降维打击”级别的优化：

1. Mmap零拷贝秒开与 FP16 加载

我写了一个脚本，将原本的 .bin 权重强制转换为 FP16 并保存为 .safetensors。在 Rust 端，我直接使用操作系统的 mmap 技术把文件映射到物理内存。

2. 下沉自回归循环，彻底消灭 Python 开销

我没有只在Rust里写前向传播，而是把整个推理过程（包括 Temperature, Top-P, Top-K 采样和重复惩罚机制）全部用Rust实现了。<br>向Python端只暴露了一个原生的接口。这样在推理期间，Python进程被完全“架空”，所有的矩阵乘法、KV Cache维护都在底层的内存空间内完成，完全没有垃圾回收的干扰。

3. 完美适配 GQA 与底层指令集优化

我的模型架构使用了GQA。在 Rust 中，我精细地处理了unsqueeze -> repeat_interleave -> reshape 的内存连续性操作，完美对齐了PyTorch的逻辑。<br>同时，利用rust的Cargo配置开启了lto = "fat"和opt-level = 3，让编译器自动绑定机器底层的AVX/Neon向量化加速指令。

### 结果

当我把这套代码编译好，并在ModelScope的2核免费空间上替换掉原来的PyTorch推理代码后，效果极其明显：

- 冷启动：从点击运行到模型就绪，几乎是瞬间完成。
- 推理速度：肉眼可见的提速，原本不能忍受的推理速度变快N倍。

### 总结

如果你的模型是标准的llama/qwen架构，那么直接用llama.cpp当然是最高效的。

但如果你也在搞底层架构创新、自定义模型设计，又或者想在极端受限的硬件（比如边缘设备、低配云服、树莓派）上部署你的LLM，强烈建议你尝试一下rust。
