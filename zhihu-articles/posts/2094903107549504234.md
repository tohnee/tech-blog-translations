### 一、先分清：你手上到底是 910B 还是 910C？

这是昇腾部署最容易踩的第一个坑，因为两代卡的部署形态完全不同：

| 机型 | 芯片 | 单卡显存 | 容器内设备数 | 官方验证状态 |
| --- | --- | --- | --- | --- |
| Atlas 800 A2 | 910B | 64 GB | 8 个 /dev/davinci* | 四机 Colocated（此版未重新验证） |
| Atlas 800 A3 | 910C | 128 GB | 16 个逻辑设备 | 单机 Colocated + 双机 PD 分离（已验证） |

注意两个反直觉的地方：

- **A3 单机是 8 颗 NPU，但容器里暴露 16 个设备**（一颗物理芯片两个逻辑 die），Docker 要挂全部 16 个
- 官方教程对 A3 单机给了验证过的配置；**A2 只有四机形态，且标注”此更新未重新验证”**

怎么确认自己的卡？跑一下：

```bash
npu-smi info
```

看 `Memory` 一列：64 GB → 你是 A2/910B；128 GB → A3/910C。

**本文主线按 910B（A2）写，A3 命令作为对照放在第六节。**

### 二、显存账：为什么 512 GB 反而装不下

很多同学的第一反应是：”910B 是国产卡，是不是对量化格式更友好？”

恰恰相反。**昇腾的强项是 INT8 GEMM，不支持 MXFP4**。所以昇腾生态的做法是：把原生 FP4 的专家权重**重新量化成 W8A8（INT8 权重 + INT8 激活动态量化）**——专家体积直接翻倍。

### W8A8 权重仓库的构成

`Eco-Tech/DeepSeek-V4.1-Flash-w8a8`，272 个 safetensors 分片（目标每片 2 GB）：

| 模块 | 精度 | 说明 |
| --- | --- | --- |
| 主干 Linear（注意力、384 专家、共享专家） | W8A8 Dynamic (INT8) | 计算大头，约 544 GB |
| DSpark（MTP 投机层）Linear | W8A8 Dynamic | 草稿头同步量化 |
| ViT / Aligner（视觉部分） | BF16 | 精度优先，不压 |
| Engram 记忆表（第 1、14 层） | BF16（可运行时转 INT8） | 由原始 FP8 直接解码，避免二次误差 |

配套技术：QuaRot 旋转 + norm folding 压离群值，旋转矩阵单独放在 `optional/quarot.safetensors`。

### 算账时间

```text
8 × 910B-64GB          =  512 GB HBM
W8A8 Linear 层          ≈  544 GB          ← 光这一项就超了
Engram INT8（运行时）    ≈  197 GB
────────────────────────────────────────
官方 W8A8 总需求         ≈  741 GB          ❌ 超 229 GB
```

**就算把 Engram 全部卸载到主机内存，Linear 那 544 GB 也塞不进 512 GB。** 这就是官方给 910B 配 4 机 32 卡的根本原因——32 卡共 2048 GB，装 741 GB 权重后还能留一大半给 KV Cache 和激活。

### 单机 8 卡的唯一出路：W4A8

社区有专门的优化仓库（`chiro2001/deepseek-v4.1-flash-ascend910B`），把专家权重进一步压到 **W4A8（4-bit 权重 + 8-bit 激活）**：

```text
专家 W4A8              ≈  279 GB
其余 Linear W8A8        ≈   15 GB
Engram INT8             ≈  197 GB
─────────────────────────────────
合计                    ≈  490 GB         ⚠️ 擦边进 512 GB
```

能塞进去，但余量极小，必须配合 Engram 卸载和激进的显存参数。**这是社区方案，精度回归和生产验收要自己做**——官方教程原话是”当前版本尚未签核完整推理与整模型任务精度”，这句话对 W4A8 更要打个折扣听。

### 3.3 下载权重（约 900 GB，留足磁盘！）

```bash
pip install -U modelscope
```

### 四、路线一（官方形态）：A2 四机 Colocated，DP4/TP8/EP32

这是官方教程给 910B 的部署形态：**4 台 Atlas 800I A2，每台 8 卡，共 32 NPU**。

架构：4 个数据并行副本（DP4），每个副本内部 TP8 + 专家并行 EP32。Node 0 对外暴露 API（端口 8000），其余节点 headless。

### 4.1 起容器（每台机器都执行）

```bash
export IMAGE=quay.io/ascend/vllm-ascend:deepseek-v4.1-flash

docker run -d --name deepseek-v41 \
  --net=host --ipc=host --privileged=true \
  --shm-size=512g \
  --device /dev/davinci0 --device /dev/davinci1 \
  --device /dev/davinci2 --device /dev/davinci3 \
  --device /dev/davinci4 --device /dev/davinci5 \
  --device /dev/davinci6 --device /dev/davinci7 \
  -v /data/weights:/data/weights \
  -v /usr/local/Ascend/driver:/usr/local/Ascend/driver \
  -v /usr/local/dcmi:/usr/local/dcmi \
  -v /usr/local/bin/npu-smi:/usr/local/bin/npu-smi \
  "$IMAGE" bash
```

> A2 不需要像 A3 那样挂 16 个设备，8 个就够；但 `--shm-size=512g` 是教程明确要求的。

### 4.2 公共环境变量（每台机器的容器内都设）

```bash
export VLLM_USE_V2_MODEL_RUNNER=0        # 硬性要求！该模型在昇腾上只支持 model runner V1
export VLLM_ENGINE_READY_TIMEOUT_S=36000 # 引擎就绪超时 10 小时——741GB 权重加载就是这么慢
export HCCL_BUFFSIZE=1024
export HCCL_OP_EXPANSION_MODE="AIV"
export MODEL_PATH=/data/weights/DeepSeek-V4.1-Flash-w8a8
```

### 4.3 Node 0（对外提供 API 的主节点）

```bash
vllm serve "$MODEL_PATH" \
  --host 0.0.0.0 --port 8000 \
  --served-model-name dsv41 \
  --max-model-len 1048576 \
  --max-num-batched-tokens 8192 \
  --max-num-seqs 32 \
  --gpu-memory-utilization 0.90 \
  --data-parallel-size 4 --tensor-parallel-size 8 \
  --enable-expert-parallel \
  --tokenizer-mode deepseek_v41 \
  --reasoning-parser deepseek_v41 --tool-call-parser deepseek_v41 \
  --enable-auto-tool-choice \
  --quantization ascend \
  --block-size 128 \
  --safetensors-load-strategy lazy \
  --model-loader-extra-config '{"enable_multithread_load":true,"num_threads":128}' \
  --engram-config '{"cpu_offload":true}' \
  --compilation-config '{"cudagraph_mode":"FULL_DECODE_ONLY"}' \
  --async-scheduling \
  --additional-config '{
      "ascend_compilation_config":{"enable_npugraph_ex":true,"enable_static_kernel":false},
      "enable_cpu_binding":true,"enable_fused_mc2":1,"enable_dsa_cp":true,
      "enable_flashcomm1":true,"enable_shared_expert_dp":true
  }'
```

### 4.4 Node 1 / 2 / 3（headless 工作节点）

```bash
# NODE_RANK 分别为 1、2、3
vllm serve "$MODEL_PATH" \
  --headless \
  --data-parallel-start-rank $NODE_RANK \
  --data-parallel-size 4 --tensor-parallel-size 8 \
  --enable-expert-parallel \
  ...  # 其余参数与 Node 0 完全一致
```

> headless 模式下不对外暴露 API，只作为 DP rank 加入集群。DP rank 与节点的对应关系由 `--data-parallel-start-rank` 决定。

### 4.5 网络放行清单

多机部署最容易死在网络上，这些端口和配置要提前弄好：

- `HCCL_IF_IP`、`GLOO_SOCKET_IFNAME` **必须指向高速服务网络**（RoCE/IB 那张网卡），别用管理网
- DP RPC 端口、引擎通信端口、防火墙全部放行
- 节点间主机名互通（`/etc/hosts` 配好）

### 五、路线二（社区方案）：A2 单机 8 卡，W4A8

如果你只有一台 8 卡机，又必须单机跑——只能走社区 W4A8 路线。**先泼三盆冷水：**

1. 官方 W8A8 权重单机装不下（544 GB Linear > 512 GB），**没有官方单机形态**，这不是参数能调出来的
2. W4A8 把专家压到 4-bit，精度损失比 W8A8 大，**必须自己跑精度回归**
3. 社区仓库的补丁更新快，用之前先看它的 README 和 issue 区有没有踩雷记录

### 5.1 获取 W4A8 权重与补丁

社区仓库（`chiro2001/deepseek-v4.1-flash-ascend910B`）提供针对 910B（A2）/ 910C（A3）的 W4A8 vLLM 部署补丁、一键启动脚本和自检工具，按其 README 执行 patch 和权重准备。它的 README 里还给出了 KV Cache 容量的实测口径（例如 A3 TP8 默认形态约 400 万 token 的 KV 容量），可作参考——**但 A2 单机的数字要自己实测**。

### 5.2 单机启动命令（基于官方命令裁剪）

```bash

export VLLM_ENGINE_READY_TIMEOUT_S=36000
export HCCL_BUFFSIZE=1024
export MODEL_PATH=/data/weights/DeepSeek-V4.1-Flash-w4a8

vllm serve "$MODEL_PATH" \
  --host 0.0.0.0 --port 8000 \
  --served-model-name dsv41 \
  --max-model-len 32768 \
  --max-num-batched-tokens 4096 \
  --max-num-seqs 16 \
  --gpu-memory-utilization 0.95 \
  --tensor-parallel-size 8 \
  --enable-expert-parallel \
  --tokenizer-mode deepseek_v41 \
  --reasoning-parser deepseek_v41 --tool-call-parser deepseek_v41 \
  --enable-auto-tool-choice \
  --quantization ascend \
  --block-size 128 \
  --safetensors-load-strategy lazy \
  --model-loader-extra-config '{"enable_multithread_load":true,"num_threads":128}' \
  --engram-config '{"cpu_offload":true}' \
  --compilation-config '{"cudagraph_mode":"FULL_DECODE_ONLY"}' \
  --async-scheduling
```

### 5.3 相对官方四机命令，为什么这么改

| 参数 | 官方四机 | 单机改法 | 原因 |
| --- | --- | --- | --- |
| --data-parallel-size | 4 | 去掉 | 单机只有一个 DP 副本，没有余量做 DP |
| --gpu-memory-utilization | 0.90 | 0.95 | 0.90 只有 460 GB，装不下约 490 GB 权重 |
| --max-model-len | 1048576 | 32768 | KV 虽然只占 890 B/token，但调度预留和激活峰值吃显存，先封顶 |
| --max-num-batched-tokens | 8192 | 4096 | prefill 激活峰值和它成正比，单机余量小 |
| --max-num-seqs | 32 | 16 | 并发越大激活和调度开销越大，先保启动 |
| --additional-config（fused_mc2 等） | 开启 | 去掉 | fused-MC2/DSA 是为多机 PD 形态设计的，单机混用需重新验证 |
| --engram-config | cpu_offload:true | 保留，去掉 dp_shared_memory | 见第七节 |

### 5.4 如果还是 OOM，按这个顺序退让

1. `--gpu-memory-utilization` 提到 0.97（再高 NPU 侧连运行时上下文都建不起来）
2. `--compilation-config` 改成 `{"cudagraph_mode":"NONE"}` 或加 `--enforce-eager`
3. `--max-num-batched-tokens` 降到 2048、`--max-num-seqs` 降到 8
4. `--max-model-len` 降到 16384
5. 全都不行 → 确认 W4A8 权重里 Engram 是不是以 INT8 加载（BF16 的话是 393 GB，必炸）；再不行就老老实实四机

### 七、Engram 在昇腾上怎么配（和 NVIDIA 不一样）

昇腾侧的 Engram 开关比 NVIDIA 那条多一个参数：

```bash
--engram-config '{"cpu_offload":true,"dp_shared_memory":true}'
```

两个开关各管一件事：

**`cpu_offload: true`** —— Engram 表留在主机内存，省显存。和 NVIDIA 侧同一个道理，这里不赘述。

**`dp_shared_memory: true`** —— 这个是昇腾特有的坑：

- 这个模型有 **24 个 Engram head**
- A3 容器暴露 **16 个逻辑设备**，24 无法被 16 整除，head 分不均
- 解决办法：让 DP rank 之间通过**主机内存共享** Engram 分配（所以 A3 容器必须 `--ipc=host`）
- A2 官方四机形态是 8 设备/机：24 ÷ 8 = 3，**能整除**，所以四机命令里我没加这个参数
- 单机 A2 同理不用加；加了如果报共享内存相关错误，先检查 `--ipc=host` 和 `/dev/shm` 大小

**主机内存需求**：Engram 卸载后主机至少 **512 GB**（BF16 形态下 Engram 约 393 GB + 预取缓冲），推荐 1 TB，多通道高带宽优先——Engram 是逐 token 随机哈希查表，内存带宽直接决定 decode 延迟。

### 八、部署后验证：四件必查的事

**1. 先确认引擎真的起来了**

`VLLM_ENGINE_READY_TIMEOUT_S=36000` 不是随便给的——700+ GB 权重从 NVMe 加载加反量化，首次启动按小时计。别等了 20 分钟就断定挂了。用 `docker logs -f` 盯到看到 API 就绪日志。

**2. 思考模式默认开启**

和 NVIDIA 侧一样：不传参数时思考默认开、推理强度 50。`max_tokens` 给小了会返回空 content + `finish_reason=length`。

```python
resp = client.chat.completions.create(
    model="dsv41",
    messages=[{"role": "user", "content": "17*19 等于多少？只返回整数。"}],
    extra_body={"chat_template_kwargs": {"thinking": True, "reasoning_effort": 25}},
)
```

`reasoning_effort` 接受 1~100；`minimal` 和 `medium` 会被拒。

**3. 工具调用是 DSML 格式**

带前导空格的 `<｜DSML｜ calls>` 标签，和 V4 不兼容。好在四件套参数（`--tokenizer-mode deepseek_v41` + 两个 parser + `--enable-auto-tool-choice`）已经在命令里配齐了，官方服务端会帮你解析。

**4. 跑一遍精度评测**

官方教程明确说了：**精度评估和性能基线尚未发布，建议用 AISBench 自行评测**。这对 W8A8 已经是必做项，对社区 W4A8 更是生死线——重点回归数学、代码、长上下文召回三类任务。

### 十、和 A800 那篇放一起看

三套”非 Hopper 硬件”跑同一个模型，处境完全不同：

|  | 4×A800 (320 GB) | 8×910B (512 GB) | 8×910C/A3 (1 TB) |
| --- | --- | --- | --- |

### 写在最后

回到标题的问题：**8 卡昇腾 910B 能不能跑 V4.1 Flash 1017？**

> **能，但”官方认证的单机 8 卡”这条路不存在。**

昇腾生态的真实状态是这样的：

- **框架层**很成熟——vllm-ascend 有专门教程、专用镜像、Engram 卸载这类关键特性都是一等公民，比 Ampere 靠社区 backport 的处境好得多
- **权重层**是瓶颈——昇腾不支持 FP4，专家必须重量化成 INT8，体积翻倍直接把单机 8 卡挤出局
- **单机 8 卡**的唯一通路是社区 W4A8，代价是精度自担
- **官方给 910B 的答案是 4 机 32 卡**；如果预算只够一台 8 卡机，认真考虑一下你的场景是否真的需要本地部署

**我的建议顺序：**

1. 先跑 `npu-smi info` 确认是 910B（64 GB）还是 910C（128 GB）——两者命令完全不同
2. 910C/A3：直接照抄第六节官方命令，W8A8 原版权重
3. 910B 且有 4 台机：走第四节官方四机形态（注意教程标注”此版未重新验证”，留出调参时间）
4. 910B 只有 1 台：W4A8 社区版 + 第五节命令，**上线前必须做精度回归**
5. 都不满足：API 的 `deepseek-flash` 已经是 1017，别硬扛
