一个退款请求进来。系统可以只把订单政策和知识库塞进一次模型调用，直接生成回复。也可以先分类，再按固定步骤走：查订单、对政策、起草回复、程序核对金额，通过了再发起退款。还可以让模型自己决定下一步，循环到问题解决，或者在卡点交给人。

这三档都在用大模型。Anthropic 在 2024 年底把它们拆开写清楚：路径写在代码里的，叫工作流；下一步由模型自己定的，叫智能体。两者都算 agentic system，架构不一样。

这篇笔记来自他们和几十个行业团队一起落地的经验。屈定的博客转载了全文。下面按原文重讲一遍，并把散落在各节里的「什么时候用」收成一张可以对照的选型图。判断来自原文。文中标明「本文」的部分——选型图、示意数字、伪代码、客服叠法——是为了读完就能对照自己的任务，原文没有这些图和代码。

### 1. 工作流和智能体

「Agent」这个词在客户嘴里有两套意思。一套是长时间自己运转、调用各种工具去完成复杂任务的系统。另一套是按人事先定好的流程往下走。Anthropic 把这些都归进 agentic system，然后在架构上切开：

- **工作流** ：模型和工具按预先写好的代码路径编排。
- **智能体** ：模型动态决定自己的过程和工具用法，掌握任务怎么完成。

![](https://pica.zhimg.com/v2-656471941856c0960d813de23caf4d02_r.jpg)
*构建有效的智能体：把 Anthropic 的架构笔记讲清楚*

左图每一步的名字在上线前就定了。右图只定了循环：计划、行动、观察，未完成就回到计划。下一步叫什么，要等这一步的观察回来才知道。

这个区分决定了你要调试的对象。工作流出错，去看那一段代码分支。智能体出错，去看它为什么在这一步选了这个工具，以及它看到的观察是什么。

### 2. 先用够用的复杂度

原文的建议是：做大模型应用，先找能用的最简单方案，只有不够时才加复杂度。加出来的系统往往用更高的延迟和成本，换更好的任务表现。这个交换要先算清楚。

任务边界清楚时，工作流给出可预测性和一致性。需要灵活、需要模型在规模上自己做决定时，智能体更合适。很多应用再往前一步就够了：把单次模型调用做好，加上检索，加上放进上下文的例子。

![](https://pica.zhimg.com/v2-f323dc6574ea5b1e0feabf3090f6dc1e_r.jpg)
*先用够用的复杂度*

往右走，系统更能应付事先写不完的路径，每一档也更贵、更慢、更难查。原文的经验是，真正跑起来的实现，用的是简单、可组合的模式，用的是这张梯子上刚好够用的那一档。

### 3. 框架放在哪一层

2024 年原文点名的框架有四个：LangChain 的 LangGraph，Amazon Bedrock 的 AI Agent 框架，拖拽式的 Rivet，以及用来搭建和测试复杂工作流的 Vellum。

它们把几件琐事变容易了：调用模型、定义和解析工具、把多次调用串起来。抽象层也挡住了底层的提示词和响应，调试变难。框架还容易让人在一个简单问题外面套上复杂结构。

原文的建议是开发者先直接调用模型 API。这些模式很多用几行代码就能写出来。如果用框架，要读懂它底下实际发出去的是什么。对底层的错误假设，是他们在客户侧常见的故障来源。示例实现放在他们的 cookbook 里。

框架适合用来起步。进到生产，原文建议把抽象层减下来，用基本组件把系统搭住。

### 4. 底座：增强型 LLM

后面每一种模式，都站在同一块积木上：一个被增强过的模型。增强指三类能力：检索、工具、记忆。当时的模型已经能主动使用它们——自己生成检索查询，自己选工具，自己决定哪些信息留下来。

![](https://pic3.zhimg.com/v2-12e4760154ffe72cd84686b34be4d4da_r.jpg)
*增强型 LLM*

实现上原文只强调两件事。第一，按你的场景去裁这些能力，用不上的不要堆进去。第二，给模型一份好读、文档清楚的接口。增强可以有很多接法。文中提到的一种是当时刚发布的 Model Context Protocol：用一个简单客户端，接上正在增长的第三方工具生态。

下文默认每一次模型调用都带着这些增强。模式之间的差别，在于调用怎样被编排。

### 5. 五种工作流

工作流的共同点是：路径在代码里。模型负责某一格里的判断或生成，下一步去哪一格，人已经写好了。

下表按原文各节的适用条件整理。

| 模式 | 谁决定下一步 | 子任务 | 是否转圈 | 你换到的东西 |
| --- | --- | --- | --- | --- |
| 增强型 LLM | 一次调用结束 | 不拆 | 否 | 最低的延迟和成本 |
| 提示链 | 代码 | 事先固定 | 否，中间有门 | 用更多调用换准确率 |
| 路由 | 分类器 | 按已知类别分发 | 否 | 每类输入有自己的提示词和工具 |
| 并行 | 代码 | 事先固定，同时跑 | 否 | 速度，或多种视角 |
| 编排者–工人 | 编排者模型 | 看过这次输入才知道 | 通常拆一次再汇总 | 子任务无法预写时的灵活 |
| 评估–优化 | 评估模型决定是否再改 | 同一份结果反复打磨 | 是 | 有标准时的质量 |
| 自主智能体 | 模型每一步决定 | 步数事先未知 | 是 | 开放问题的完成能力 |

### 5.1 提示链

提示链把任务拆成一串步骤，后一次调用处理前一次的输出。任一步后面都可以加程序检查，原文图里叫门，用来确认流程还在轨上。

![](https://pic4.zhimg.com/v2-d36b903c28236e870dd16df711af53eb_r.jpg)
*提示链*

门是程序，不一定是另一次模型调用。格式对不对、必填字段在不在、金额有没有超出政策，都可以用代码挡在下一步前面。挡下来就停，或者回到上一步重做。错误停在门里，就不会整段流进最终回复。

适合能干净拆成固定子任务的场合。目的是用延迟换准确率：每一次调用面对的题目更小。

原文的例子：

- 先写营销文案，再翻译成另一种语言。
- 先写大纲，检查大纲是否满足标准，再按大纲写成正文。

它和后面的评估–优化相邻，但停的方式不同。提示链的步骤表在写代码时已经定完，走到最后一格就结束。评估–优化没有固定的「第 3 步」，它停在标准被满足的那一轮。

### 5.2 路由

路由先给输入分类，再把它送进专门的后续任务。这样关注点分开，每条下游可以有自己的提示词、工具和模型。少了这一步，为某一类输入调好的提示词，会伤到其他类输入。

![](https://picx.zhimg.com/v2-e64131566d8a5a59c3ae387046660233_r.jpg)
*路由*

分类要做得准。分类器可以是模型，也可以是传统分类模型或算法。类别本身得是事先说得清、分开处理确实更好的那些。

原文的例子：

- 客服里的一般问题、退款、技术支持，进入不同的下游流程、提示词和工具。
- 容易、常见的问题交给更小的模型（原文写的是 Claude 3.5 Haiku），难的、少见的交给能力更强的模型（Claude 3.5 Sonnet），用来平衡成本和速度。

本文补一个落地时的检查：路由的收益建立在「分得准」上。分错的请求会走进一套为另一类问题准备的工具。上线前用真实流量里的类别分布看分类错误率，和每一类的满意回复分开统计。

### 5.3 并行

多个模型调用可以同时进行，输出再用程序汇总。原文把并行分成两种。

- **分段** ：把任务拆成彼此独立的子任务，一起跑。
- **投票** ：同一任务跑多次，取得不同的输出。

![](https://pic4.zhimg.com/v2-4ae44b82f4fa38830dd08932d371f707_r.jpg)
*并行的两种做法*

分段用来换速度，也用来让每次调用只盯一件事。投票用来换把握：多个视角、多次尝试。原文的观察是，考虑因素多的任务里，每个因素单独一次调用，模型通常比把所有因素塞进同一次调用更好。注意力分开了。

分段的例子：

- 一个模型实例处理用户问题，另一个检查不当内容或不当请求。同一调用既做回答又做护栏，效果通常更差。
- 自动评测时，每次调用只评模型在这条提示词上的一个方面。

投票的例子：

- 几套不同提示词同时审查一段代码，发现漏洞就标记。
- 多套提示词判断一段内容是否不当，用不同的投票阈值去平衡误报和漏报。

汇总方式要跟着变体走。分段的汇总是把各块结果拼成一份完整输出。投票的汇总是计数、取交集或按阈值裁决。把三次漏洞审查的原文拼接在一起，那是分段的汇总，用在投票上会把互相矛盾的意见都留下来。

### 5.4 编排者–工人

一个中心模型动态拆开任务，派给工人模型，再把结果合成。

![](https://pic1.zhimg.com/v2-8203b4ce501c283970e50fd650ccfd02_r.jpg)
*编排者 - 工人*

它和并行外形接近。差别在灵活性：并行的子任务是预先写死的；编排者的子任务由这一次输入决定，事先不知道要拆成几块、每块做什么。

原文举的场景很具体。改代码时，要动几个文件、每个文件改什么，取决于这次的任务，写代码的人在看到任务之前定不下来。搜索也一样：要去哪些来源、各取什么，要等编排者看过问题再定。

- 每次都要对多个文件做复杂修改的编码产品。
- 从多个来源搜集并分析信息的搜索任务。

它仍是工作流：外层的「拆—派—汇总」是固定形状，变的是里面的工人列表。工人列表一旦定了，这一轮里工人之间通常不再互相改计划。若工人还要根据上一个工人的结果继续决定要不要再找新工人，形状就滑向第 6 节的自主循环。

### 5.5 评估–优化

一次调用负责生成，另一次调用负责评价和反馈，两者转圈。

![](https://picx.zhimg.com/v2-1e5fb5fd3a4787a8d7dd1ae48293c03b_r.jpg)
*评估 - 优化*

它在两件事同时成立时特别有效：评价标准清楚，反复修改能带来可衡量的收益。原文给了两个信号，用来判断这个模式配不配你的任务。第一，人把反馈说清楚之后，模型的回答明显变好。第二，模型自己也能给出这种反馈。这和人写一篇东西的过程同构：起草，对照标准改，改到达标停。

原文的例子：

- 文学翻译。第一遍会漏掉语气和细微差别，评估模型可以指出这些差别。
- 复杂搜索。搜一轮、分析一轮，由评估者决定信息够不够、要不要再搜。

标准必须是评估模型真的能执行的。标准若只存在于资深编辑的口味里，又写不进提示词，这个循环会稳定地产出「看起来改过、其实没对准」的版本。原文把「人说得清反馈时结果会变好」放在前面，就是这个原因。

### 6. 自主智能体

模型在几项能力上成熟之后，智能体开始进入生产：理解复杂输入，做推理和规划，可靠地使用工具，从错误里恢复。

它从人的一句命令开始，或者先跟人对话，把任务说清。任务清楚之后，它自己计划和执行，必要时回到人那里要信息或要判断。执行过程中，每一步都要从环境拿到地面真值，用来评估进度。地面真值在原文里的例子是工具调用结果和代码执行结果。它可以在检查点停下来等人，也可以在碰到阻碍时停下来等人。任务可以在完成时结束。为了把控制权留在人这边，通常还要写停止条件，原文举的例子是最大迭代次数。

![](https://pica.zhimg.com/v2-f2fb45e26cf7f4e62e397ebc1604a9e6_r.jpg)
*自主智能体*

实现往往比名字简单。原文把它收成一句话：智能体通常就是模型在循环里根据环境反馈使用工具。因此工具集和工具文档要设计清楚。工具怎么写，放在第 9 节。

适合开放问题：需要几步很难或无法预知，路径也无法写死。模型可能会走很多轮，你得对它的决定有一定信任。自主性适合在受信任的环境里把任务规模铺开。代价写在原文里：成本更高，错误会叠加。他们建议在沙箱里充分测试，并加上相应的护栏。

错误叠加的机制可以直接从这句话推出来：下一步的输入包含上一步的观察。观察里若已经歪了，后面的计划会沿着歪的方向继续。本文做一个数量级示意，不是原文数据：假设每步独立做对的概率是 0.9，连续 10 步都对的概率大约是 0.35。步数写得出来的任务，不值得付这笔账，回到提示链或路由。步数写不出来、环境又能在每步把真值交回来的任务，这笔账才对得上。

原文自己的两个实现：

- 一个编码智能体，用来解决 SWE-bench 任务：根据任务描述，修改很多文件。
- computer use 的参考实现：Claude 使用一台计算机去完成任务。

下面这段循环是本文按原文那句话写成的示意，方便对照上图，不是原文代码。

```python
# 示意：环境反馈上的循环
for step in range(MAX_STEPS):          # 停止条件：最大迭代次数
    action = llm.next_action(goal, history)
    if action.type == "finish":
        return action.result
    if action.type == "ask_human":     # 检查点或阻碍
        history.append(human_reply(action.question))
        continue
    observation = tools.run(action)    # 地面真值：工具结果、执行结果
    history.append((action, observation))
return "stopped: max steps"
```

实践里常和最大步数放在一起的，还有费用上限、以及「连续几步观察没有变化」。这两条原文没有写，最大迭代次数才是原文点名的停止条件。

### 7. 怎么选，怎么叠

这些积木在原文里是常见模式，开发者可以按场景改形状、叠在一起。成功的办法和任何大模型功能一样：测量表现，再迭代实现。复杂度只在它确实让结果变好时才加。

下图把各节的适用条件收成一条提问顺序。它是本文的整理，方便选型，不是原文中的图。一条任务可以在不同环节回答「是」，于是几种模式叠在同一个产品里。

![](https://pic4.zhimg.com/v2-a18dc5687d7f46f4c1002042723eb059_r.jpg)
*先问任务，再选模式*

用退款这条线做一次本文的叠法示例。模式都来自原文，组合方式是一种落地排法。

```text
用户消息
  → 路由：一般咨询 / 退款 / 开放投诉
  → 一般咨询：一次调用 + 知识库
  → 退款：提示链
        查订单 → 对照政策 → 起草回复
        → 门：金额、原因、订单状态是否允许
        → 通过则调用退款工具
  → 开放投诉：步数看内容，进入智能体
        工具包括查物流、改地址、部分退款、升级人工
```

退款政策若是一张写得完的表，提示链足够。投诉若每次都要临时决定查什么，编排者或智能体才付得起那个灵活性。测量时分开看：分类错了多少、门挡住了多少不该退的款、智能体在最大步数内解决了多少。某一档的数字没有变好，就不要为它保留复杂度。

### 8. 两类已经跑通的场景

原文从客户实践里抽出两类特别有希望的应用。智能体加分最多的任务，四件事同时在：既要对话也要行动，成功标准清楚，有反馈回路，关键处有人看。

![](https://pic3.zhimg.com/v2-8853df7c96ea43cbb550df6e94df5624_r.jpg)
*四件事同时在*

### 客服

客服是熟悉的对话界面，加上工具之后的行动能力。它适合更开放的智能体，原文给了四条理由：

- 交互本来就是对话，同时又要外部信息和动作。
- 工具可以拉取客户数据、订单历史和知识库文章。
- 退款、更新工单这类动作可以用程序完成。
- 成功可以用用户定义的「已经解决」来衡量。

有些公司用按成功解决计费的定价，只对解决了的会话收费。原文把这看成他们对自己智能体效果有信心的表现。

### 编码

软件开发里，模型能力从代码补全走到了自主解决问题。智能体在这里有效，原文同样给了四条：

- 代码方案可以用自动测试验证。
- 智能体可以把测试结果当作反馈，继续改。
- 问题空间清楚，结构也清楚。
- 输出质量可以客观测量。

他们自己的实现已经能只根据 pull request 的描述，去解决 SWE-bench Verified 基准里的真实 GitHub issue。自动测试负责核对功能。方案是否符合更大的系统要求，人的审查仍然关键。测试绿了，只说明地面真值里的那一部分过了。

两条场景都对上了那四件事。客服的反馈是用户是否承认问题已经解决，行动是退款和改工单。编码的反馈是测试，行动是改文件。两边都在自动反馈盖不住的地方留了人。

### 9. 工具是界面

不论做的是哪一种 agentic system，工具都很可能是其中一块。工具让 Claude 按 API 里写明的结构和定义，去调用外部服务。模型若决定调用工具，响应里会带上一个工具使用块。原文要求：工具的定义和规格，要拿到和整份提示词同等级的提示工程注意力。

同一件事可以有多种写法。改文件可以写 diff，也可以重写整个文件。结构化输出可以把代码放进 Markdown，也可以放进 JSON。对工程来说，这些格式往往能无损互转。对模型来说，难度差很多。写 diff 时，模型得在写下新代码之前，就在块头里知道这一段改了多少行。把代码放进 JSON，相比放进 Markdown，还要额外转义换行和引号。

![](https://pica.zhimg.com/v2-9d1d0c77a9ced6464bb590f3b930237a_r.jpg)
*工具格式*

原文对格式的三条建议：

1. 给模型足够的 token 去想，再落笔，避免它先把自己写进死角。
2. 格式靠近模型在互联网正文里常见的样子。
3. 去掉格式负担。不要让它维持成千上万行代码的准确行数，也不要让它给写下的代码做字符串转义。

diff 的块头就是一个死角：行数是结果，却被格式要求写在正文之前。模型还没写完改动，就要承诺改了几行。给它「先想」的空间，一种直接的做法是让它按普通文本把改动写出来，行号和补丁头交给程序算。JSON 转义同理，容量花在引号和换行上，代码本身拿到的注意力就少了。Markdown 代码块更接近模型读过的正文。

原文用一个人机界面的类比收束：人机界面（HCI）上花多少功夫，智能体–计算机界面（ACI）上就计划花多少功夫。具体四条：

- 站在模型的位置看这个工具。只靠描述和参数，用法是否显而易见。若你自己得想一下才知道怎么填，模型多半也得想。好的工具定义通常包括用法示例、边界情况、输入格式要求，以及和其他工具的边界。
- 改参数名和描述，让事情更明显。把它写成给团队里初级开发者的 docstring。相似工具多的时候尤其要这样做。
- 测试模型实际怎么用这些工具。在 workbench 里跑很多样例输入，看它犯什么错，再改。
- 给工具做防错（poka-yoke）。改参数，让错误更难发生。

他们做 SWE-bench 智能体时，优化工具的时间多于优化总提示词。一个具体故障是：智能体离开根目录之后，相对路径的工具会被用错。工具改成一律要求绝对路径之后，模型就能稳定用对。

下面两份定义是本文的示意，用来把这个故障写成接口，不是原文中的 schema。

```json
{
  "name": "edit_file",
  "description": "修改一个文件。path 必须是绝对路径。",
  "parameters": {
    "path": "绝对路径，例如 /repo/src/app.py",
    "content": "修改后的完整文件内容，使用普通文本"
  }
}
```

相对路径在离开根目录后会指错地方。绝对路径把这个错误从模型的记忆里挪到了参数约束上：填相对路径，调用在进模型的下一步之前就失败。这就是原文说的防错。

相似工具要在边界上写清楚。例如「查看文件」和「修改文件」如果参数长得一样，模型会用查看去改、或用修改去读。描述里写明谁会改动磁盘、谁只返回内容，比在系统提示词里重复一句「请正确使用工具」更靠近它做决定的位置。

### 10. 三条原则

原文把成功定义成：做出任务所需要的那个系统。从简单提示词开始，用充分的评测把它调好，只有更简单的方案不够时，才加多步的 agentic system。

实现智能体时，他们遵循三条：

1. 设计保持简单。
2. 把规划步骤显式展示出来，优先透明。人要在检查点介入，就得看得见它打算做什么。
3. 认真做 ACI：工具文档和测试都要做到位。

框架可以让起步变快。进生产时，把挡在提示词和响应外面的抽象层减掉，用基本组件把系统留住。按这三条做出来的智能体，能力在，也可以被维护，也可以被使用者信任。

三条和前面的图是同一件事。简单，对应第 2 节那张梯子：停在够用的一档。透明，对应第 6 节的循环：计划和观察要留在人看得到的地方。ACI，对应第 9 节：模型每一步的地面真值，从工具的形状里来。工具形状歪了，循环转得再完整，看到的也是歪的世界。
