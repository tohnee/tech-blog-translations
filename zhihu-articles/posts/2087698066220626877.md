## 1. 性能分析与瓶颈定位

[13. Profiling and Bottleneck Analysis | 性能分析与瓶颈定位 | 大模型算法实战教程](https://datawhalechina.github.io/llm-algo-leetcode/01_Hardware_Math_and_Systems/13_Profiling_and_Bottleneck_Analysis.html)

[torch.profiler — PyTorch 2.14 documentation](https://docs.pytorch.org/docs/2.14/profiler.html)

### 1. 核心目的：先找慢在哪里，再决定怎么改

Profiling（性能分析）就是记录程序的**耗时、计算、访存**和**等待情况**，用证据定位瓶颈，而不是凭感觉优化**。**

基本流程是：**固定测试条件 → 测量耗时 → 定位瓶颈 → 修改实现 → 重新验证。**

**benchmark和profling**

| 工作 | 回答的问题 | 示例 |
| --- | --- | --- |
| Benchmark，性能基准测试 | 整体有多快？ | 每步 100 ms，每秒处理多少 token |
| Profiling，性能剖析 | 时间和资源具体消耗在哪里？ | 哪些算子耗时、哪里发生拷贝、GPU 在什么时候等待 |

### 2. 测量之前，先保证“测得准”

**保持条件一致：**固定模型、精度、batch、序列长度和硬件环境；先预热，再重复测量，避免把首次编译、初始化和偶然波动当成正常性能。

**注意 GPU 异步执行：**CPU 提交完任务，不代表 GPU 已经算完。使用 CPU 时钟计时，需要在测量区间开始前、结束读数前同步 GPU；也可以正确使用 CUDA Event。不要为了计时在每个算子后都同步，否则会改变原有并行行为。

**至少记录三个指标：**

| 指标 | 回答什么问题？ |
| --- | --- |
| 耗时：step time / latency | 完成一次更新或请求需要多久？ |
| 吞吐：samples/s、tokens/s | 单位时间能处理多少数据？ |
| 峰值显存：peak memory | 最多需要多少显存？ |

训练主要看完整更新耗时和吞吐；推理还应看首 token 延迟（TTFT）、后续 token 平均耗时（TPOT）及请求延迟的 P50/P99。

### 3. 最重要的区别：四类瓶颈

| 瓶颈 | 典型观察信号 | 优先考虑的优化方向 |
| --- | --- | --- |
| 算力瓶颈：计算能力受限 | 矩阵计算耗时大，相关计算单元吞吐接近上限 | 更高效的矩阵算子、合理使用混合精度和 Tensor Core |
| 访存瓶颈：GPU 内部读写受限 | 显存带宽压力大，访存成为限制 | 减少读写、提高数据复用、融合算子 |
| 搬运瓶颈：CPU↔GPU 传输受限 | H2D/D2H 拷贝占时明显，计算等待数据 | 减少搬运、优化输入管线、争取传输与计算重叠 |
| 调度瓶颈：启动和等待开销大 | 大量短 kernel、频繁同步、GPU 执行有空档 | 合并小操作、减少启动次数和不必要的同步 |

**这些是判断线索，不是看到一个指标就能下结论；多个瓶颈也可能同时存在。**需要结合时间线和硬件指标验证。

尤其注意：**访存瓶颈是“读写受限”，不等于“显存容量不够”。**带宽、访存指令吞吐等都可能成为限制。

### 4. 三个工具，分别回答什么问题？

`torch.profiler`：时间花在哪？<br>查看 PyTorch 算子的 CPU/GPU 耗时、调用次数和内存分配，先找出热点。

Nsight Systems：为什么在等？<br>查看整体时间线，将 CPU 调用、GPU kernel、数据复制和 CUDA stream 联系起来，检查执行空档、同步及重叠情况。

Nsight Compute：这个 kernel 为什么慢？<br>深入检查单个 GPU 计算内核的计算吞吐、访存吞吐、线程占用率和停顿原因。线程占用率高，并不自动代表性能好。

> 工具的顺序通常是：先用 `torch.profiler` 找大方向，再用 `Nsight Systems` 看系统级重叠，最后用 `Nsight Compute` 钻到 kernel 细节。

| 工具 | 主要观察层级 | 最适合回答的问题 |
| --- | --- | --- |
| torch.profiler | PyTorch 算子、CPU 侧调用、GPU 活动 | 哪些代码阶段和算子消耗最多时间？ |
| Nsight Systems | 整个程序的 CPU/GPU 时间线 | GPU 为什么在等待？拷贝、计算、通信有没有重叠？ |
| Nsight Compute | 单个或少量目标 kernel 的硬件指标 | 这个 kernel 内部为什么慢？ |

### 5. 如何判断优化真的有效？

**最终比较整个任务，而不是只比较某个算子。**算子统计可能包含父子调用，计算和搬运也可能重叠，因此不能把所有耗时直接相加，当成真实 step time。

Profiler 本身会增加开销。建议用它定位原因，再**关闭详细采集，独立复测端到端耗时和吞吐**，同时确认数值结果仍符合要求。

原文中的 CPU 评分函数只是分类练习，**不是 GPU 实测，也不是通用瓶颈判定标准**。

## 2. 训练性能分析

[73. Training Performance Analysis | 训练性能分析 | 大模型算法实战教程](https://datawhalechina.github.io/llm-algo-leetcode/02_PyTorch_Algorithms/73_Training_Performance_Analysis.html)

测准一次训练的成本，解释时间和显存花在哪里，再判断优化是否值得保留。

### 1. 理解一次训练step做了什么？

典型训练过程：

```python3
optimizer.zero_grad(set_to_none=True)  # 清理上一轮梯度
outputs = model(inputs)               # 前向计算
loss = loss_fn(outputs, targets)       # 计算损失
loss.backward()                       # 反向计算梯度
optimizer.step()                      # 更新参数
```

性能分析的关键是明确计时边界。数据读取、CPU 到 GPU 的传输是否包含在内，会改变结果。本文 GPU 示例提前准备好了 GPU 输入，因此不能直接把它的耗时当成包含数据加载的完整业务耗时。

### 2. 理解训练显存由哪些部分组成

| 对象 | 保存什么 | 什么时候占用显存 |
| --- | --- | --- |
| 参数 | 模型权重 | 模型驻留 GPU 期间 |
| 梯度 | 每个参数的损失导数 | 反向传播产生，清理时释放或归零 |
| 优化器状态 | AdamW 的一阶矩、二阶矩等 | 首次更新时建立，随后保留 |
| 激活值 | 反向传播需要的前向中间结果 | 前向保存，反向使用后逐步释放 |
| 临时空间 | 算子中间张量、工作区 | 执行特定操作时出现 |

计算张量的大小：

```text
tensor_bytes = tensor.numel() * tensor.element_size()
```

字节数=元素数量 x 每个元素的字节数

FP32 每个元素占 4 字节，FP16/BF16 占 2 字节。

若有 $P$ 个参与训练的参数，参数、梯度和 AdamW 的两份主要状态均为 FP32，则这几项约占：

$$ 4P+4P+8P=16P\ \text{字节} $$

这里还没有包括激活值、临时空间和分配器开销。AdamW 保存两份主要状态，是训练显存明显大于权重大小的重要原因

还要理解：**batch、序列长度增加，**即使参数量不变，激活显存也通常会增加**。**

### 3.区分静态账本、allocated 和 reserved

> allocated：张量正在占用的空间：例如，模型参数、梯度和中间结果当前占着的显存。<br>reserved：PyTorch 分配器管理的空间：PyTorch 为了提高分配效率，会缓存一部分暂时不用的显存，方便以后复用。

| 概念 | 含义 |
| --- | --- |
| 静态账本 | 在某个时刻统计参数、梯度、优化器状态的大小 |
| allocated | PyTorch 当前用于张量的显存 |
| reserved | PyTorch 缓存分配器管理的显存，包括暂时空闲的缓存 |
| peak | 测量区间内的最大值 |

因此：

- 静态账本不能代表训练峰值，因为没有完整捕捉激活和临时分配。
- `reserved` 包含 `allocated` 对应的占用，**两者不能相加**。
- `reserved` 较高不等于所有显存都被活跃张量使用。
- `empty_cache()` 释放的是未使用的缓存，不能释放仍被张量占用的显存。[CUDA 显存管理说明](https://docs.pytorch.org/docs/2.14/notes/cuda.html#memory-management)

### 4. 会计算耗时、吞吐和优化收益

设正式测量运行了 $N$ 步，总耗时为 $T$ 秒，每步 batch size 为 $B$。

**平均单步耗时**

$$ \text{step time}=\frac{T}{N}\times1000\ \text{ms} $$

**吞吐量**

$$ \text{samples/s}=\frac{B\times N}{T} $$

例如，batch=4，运行 10 步共用 2 秒：

- 单步耗时：200 ms。
- 吞吐：20 samples/s。

单步耗时反映一步有多快，吞吐反映单位时间处理多少数据。 比较时必须同时看 batch 和序列长度；不同工作量下的数字不能直接比较。

统一收益的正负方向

```text
耗时收益 = baseline 耗时 − tuned 耗时
显存收益 = baseline 显存 − tuned 显存
吞吐收益 = tuned 吞吐 − baseline 吞吐
```

这样三个差值都是正数表示改善。

还要区分：

$\text{耗时下降比例}=\frac{t_{\text{base}}-t_{\text{tuned}}}{t_{\text{base}}} $

$ \text{加速倍数}=\frac{t_{\text{base}}}{t_{\text{tuned}}} $

例如 100 ms 降到 50 ms，是耗时下降 50%，加速 2 倍。、

> tune表示继续调整，优化后再验证

### 5. 掌握可靠的测量方法

① 先预热，再正式计时

最初几步可能包含初始化、缓存建立等额外成本，不能直接代表稳定运行速度。

```python
for _ in range(warmup):
    train_step()

start = time.perf_counter()
for _ in range(iters):
    train_step()
total_seconds = time.perf_counter() - start
```

预热要执行，但不计入正式耗时。

②多步平均，再重复实验

这两个概念不同：

- **`iters`**：一次测量连续运行多少步。
- **`repeats`**：整个测量重复多少次。

多步平均能减少单步偶然波动；重复实验能判断结果是否稳定。若收益与波动幅度接近，就需要更多证据。[PyTorch 基准测试教程](https://docs.pytorch.org/tutorials/recipes/recipes/benchmark.html)

③GPU计时要处理异步执行

GPU 操作通常异步提交。CPU 函数返回时，GPU 可能还没算完。

使用 CPU 计时器测 GPU 时，应在计时前后同步，或者使用 CUDA Event：

```python
torch.cuda.synchronize()
start = time.perf_counter()

# 执行正式训练迭代

torch.cuda.synchronize()
total_seconds = time.perf_counter() - start
```

否则可能低估实际耗时。

测正式区间的峰值显存，还要先调用 `reset_peak_memory_stats()` 重置峰值记录。

### 6. 会设计公平的对照实验

比较 baseline 和 tuned 时，需要固定：

- 模型及初始权重。
- 输入数据、batch、序列长度。
- 优化器、学习率。
- 硬件、软件环境和测量边界。
- 预热步数、正式步数和重复次数。

**每次只改变研究的那个因素。** 例如测试 AMP，就不要同时缩短序列、减小 batch，否则无法判断收益来自哪里。

还要注意：

- 两组应从可比较的模型和优化器状态开始。
- 固定 seed 有助于控制随机性，但不保证不同平台完全一致，也不能消除运行时间波动。[可复现性说明](https://docs.pytorch.org/docs/2.14/notes/randomness.html)
- 小规模 `smoke` 运行用于检查流程；更大工作量的测试才用于观察实际压力。
- 报告应保留配置、原始数据、均值、波动、loss 和 OOM 状态，方便复查。

### 7. 理解 AMP 为什么能提速，却未必明显省显存

AMP 是**自动混合精度**：根据算子特点选择计算精度，让适合的操作使用 FP16/BF16，同时保留部分 FP32 计算。

必须区分：

> **计算使用什么精度，与参数实际保存成什么精度，是两件事。**

本文通过 `autocast` 改变部分计算精度，模型参数仍以 FP32 加载。因此，不能据此认为参数、梯度和优化器状态全部减半。

这就解释了：**部分计算可以明显加速，但总显存只小幅下降。**

补充一个实操点：FP16 训练通常需要配合 `GradScaler`，减少小梯度下溢带来的问题；不能只看运行速度，还要检查数值是否正常。[AMP 官方说明](https://docs.pytorch.org/docs/2.14/amp.html)

### 8. 会根据结果做判断，并说明结论的范围

示例规则是：

| 条件 | 判断 |
| --- | --- |
| 耗时至少减少 10 ms，显存至少减少 512 MiB | accept |
| 至少一项改善，但没有同时达标 | tune |
| 两项均未改善 | reject |

**这些是示例阈值，实际项目需要根据目标设置。**

文章历史实验中，AMP 的单步耗时约减半，但峰值显存只减少约 305 MiB，未达到显存门槛，所以判断为 `tune`。[原文实验与决策](https://github.com/datawhalechina/llm-algo-leetcode/blob/main/02_PyTorch_Algorithms/73_Training_Performance_Analysis.ipynb)

同时，要理解证据的限度：

- 跑通几步，只能说明这几步能执行。
- 重复性能测量，支持当前配置下的速度和显存判断。
- 少量步骤的 loss，不能证明长期收敛和最终模型质量。
- 只有 AMP 的单组测量，不能证明它比 FP32 更好。

```python
    def run_train_mode(use_amp, repeat_index=0):
        """在一次独立模型实例上执行 warmup 和正式训练 step 测量。"""
        torch.manual_seed(SEED + repeat_index)
        model = AutoModelForCausalLM.from_pretrained(model_path, dtype=torch.float32)
        model.config.use_cache = False
        model.to(device).train()
        optimizer = torch.optim.AdamW(model.parameters(), lr=LEARNING_RATE)
        input_ids = shared_input_ids_cpu.to(device)
        labels = input_ids.clone()

        def train_step():
            optimizer.zero_grad(set_to_none=True)
            with torch.autocast(device_type='cuda', dtype=amp_dtype, enabled=use_amp):
                loss = model(input_ids=input_ids, labels=labels).loss
            loss.backward()
            optimizer.step()
            return float(loss.detach().item())

        result = measure_training_run(
            train_step, torch_module=torch, batch_size=BATCH_SIZE,
            warmup=WARMUP, iters=ITERS,
        )
        del optimizer, model, input_ids, labels
        torch.cuda.empty_cache()
        return result
```

```python
            'baseline': {**baseline, 'runs': baseline_runs},

            'summary': summary,
            'loss_delta_tuned_minus_baseline': round(tuned['loss'] - baseline['loss'], 6),
            'evidence_level': 'fixed_workload_performance_smoke',
            'decision': decision,
        }
    # 阶段 4：补充统一报告字段，并将单次结果和均值写入 JSON。
    result['experiment'] = standard_experiment_config(result['config'])
    if 'baseline' in result:
        result['standard_metrics'] = {name: standard_training_metrics(result[name]) for name in ('baseline', 'tuned')}
    elif 'candidate' in result:
        result['standard_metrics'] = {'candidate': standard_training_metrics(result['candidate'])}
    output_path = Path(OUTPUT_PATH)
    output_path.parent.mkdir(parents=True, exist_ok=True)
    output_path.write_text(json.dumps(result, ensure_ascii=False, indent=2), encoding='utf-8')
    print(json.dumps(result, ensure_ascii=False, indent=2))
```

## 问题

（1）如何区分“计算慢”“内存访问慢”和“调度或同步等待”？如何根据 compute、memory、transfer 和 scheduling 等证据判断主要瓶颈？

先用 PyTorch Profiler 或 Nsight Systems 看 CPU/GPU 时间线，定位真正拖长整个 step 的区间，再分析具体原因。

- 计算瓶颈：热点 kernel 的计算单元吞吐接近上限。
- 访存瓶颈：显存或缓存带宽接近上限，或者存在明显的访存等待，需要用 Nsight Compute 进一步确认。
- 传输瓶颈：CPU/GPU 拷贝或多卡通信耗时较大，而且没有被计算充分覆盖。
- 调度或同步瓶颈：GPU 出现空闲区间，对应 CPU 数据准备、任务提交或依赖等待。 最后只改变一个因素，检查对应耗时和完整 step 是否同时下降，验证瓶颈判断。

（2）如何固定模型、数据、batch size、sequence length、dtype 和重复次数，建立可复查的 baseline？

固定并保存三类信息：

第一是任务配置：模型版本和初始权重、数据及顺序、batch size、sequence length、参数与计算精度，以及优化器配置。

第二是运行环境：GPU、PyTorch/CUDA 版本、代码版本和随机种子。

第三是测量口径：是否包含数据加载和传输、预热步数、正式迭代数和重复次数。

每组从可比较的模型和优化器状态开始，先预热，再重复测量；GPU 计时在整个测量区间前后同步。保存每次原始结果、均值和波动，以及吞吐、峰值显存、loss 和 OOM 状态。

（3）如何把训练结果拆分为 forward、backward、optimizer、data loading 和 communication 等阶段？

用 record_function 给训练阶段加标签，同时采集 CPU 和 CUDA trace：

- next(iterator)：data loading；
- .to(device)：数据传输；
- 模型调用和 loss：forward；
- loss.backward()：backward；
- optimizer.step()：参数更新；
- 多卡通信：查看 trace 中的 NCCL 等通信事件。

然后把阶段标签与实际 GPU kernel、拷贝和等待对应起来。DDP 通信通常与 backward 重叠，所以要重点看未被计算覆盖的通信，以及拖慢训练的等待部分。
