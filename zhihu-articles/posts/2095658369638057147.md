### 前言

做过大模型的同仁们都知道，兵马未动，code 先行。没有一份好的代码，什么 research 的 idea 都是白搭。而在整个大语言模型的开发过程中，预训练又是很重要的一环。预训练的 code 说难也不难，但也绝非容易，一点点小错误都有可能导致整个预训练环节白费。这一系列文章，作者想从实战的角度，分析 Megatron-LM 库的代码使用方式，结合自己使用过程中踩过的一些坑，给出一份不完全指南。

这一篇是整个不完全指南系列的第 0 篇，序言——主要介绍为什么非得用 Megatron-LM 这个其实非常不好用的库，以及给一些完全没用过 Megatron-LM 的人一些预警。如果一个从来没用过 Megatron-LM 的人直接上手用这个库的话，一定会踩一堆坑然后破防（作者本人也是这么坑坑洼洼地踩过来的）。

### 先分清几个主流概念

- **Megatron-LM**：英伟达发布的一个基于 PyTorch 的分布式训练框架，用来训练基于 Transformer 的大型语言模型。PyTorch 自身已经是一个完备的深度学习框架，可以说是深度学习代码的基石。Megatron-LM 在这个基础上添加了许多优化技术，并做了额外封装，能更好地在 Nvidia 显卡上高效地训练大模型。
- 理论上完全仅借助 PyTorch 来训练一个模型是可行的。然而实际应用中可能会遇到代码复杂、计算效率低、过大模型无法训练等问题。因此绝大部分情况下，我们会利用开源社区内比较成熟的更高层框架来进行模型训练。
- **HuggingFace Accelerate**：最大名鼎鼎的高层训练框架，我们所熟知的 transformers 库底层就是它。最大优势在于完备性高、生态丰富，几乎任何与深度学习有关的任务都有集成与实现——大语言模型训练之外，语言模型微调、推理、后训练，图像理解与生成，音视频、多模态等任务基本都有支持；社区力量庞大，教程完备，issue 和 PR 都很活跃，非常适合新手或者小规模任务使用。
- **PyTorch-Lightning**：Lightning-AI 团队提出的模型训练框架，本质上也是在 PyTorch 上进行高层封装，让整个模型的训练更为系统化和规范化。

- reduce-scatter 类似地也是分两步，先做 NVLink 再做 RDMA；

### TL; DR

作者最近在看 Megatron 框架，被里面很多分布式训练通信原语搞得头晕眼花，于是决定系统地学习与总结一遍常用的通信原语，并整理成适合自己的笔记以供之后查阅，也分享给大家。

通信原语，是多 GPU/多进程分布式训练中，数据传输与聚合的标准化、原子化操作，是 NVIDIA NCCL 通信库的核心，更是 Megatron 等大模型框架实现 TP/PP/DP/SP 混合并行的底层基石。一些同样基础的概念，如梯度规约、张量分片传输、流水线激活值传递，最终都会落到这些通信原语上。

本文从基础概念 → 基础原语 → 核心进阶原语 → 大模型训练落地场景，逐层系统讲解，贴合新手学习的大模型分布式训练场景。

### 一、前置核心基础概念

所有通信原语的理解，都基于这几个核心概念：

1. **通信域（Process Group/进程组）**：通信的「边界」，只有同一个组内的 rank 才能互相通信，组外进程完全无感知。比如 Megatron 里的 `TP_GROUP`（张量并行组）、`DP_GROUP`（数据并行组）、`PP_GROUP`（流水线并行组），都是独立的通信域，通信只在组内发生，互不干扰。
2. **Rank**：通信域内的唯一进程编号，从 0 开始。比如一个 TP=2 的张量并行组，就有 rank0 和 rank1 两个进程，对应 2 张 GPU。
3. **张量分片（Chunk/Slice）**：把一个完整大张量，沿某个维度切成多个等长的小块，每个 rank 持有其中一块。比如完整张量 shape=[8]，TP=2 时切成 2 块，每块 shape=[4]，rank0 拿前 4 个元素，rank1 拿后 4 个元素。
4. **规约操作（Reduce Operation）**：把多个张量合并成一个张量的计算操作，从数学上来讲有点像向量→值的概念。
5. **通信的两大核心成本**：

- **带宽成本**：传输的数据量越大，耗时越长；
- **延迟成本**：通信的启动固定开销，和数据量无关，和通信次数正相关。

所有分布式通信优化，本质都是围绕降低这两个成本展开。

### 二、基础集体通信原语

先讲 4 个最基础的集体通信原语，后续的核心进阶原语都是它们的组合与扩展。（集体通信：通信域内所有 rank 都必须参与的通信操作，是分布式训练的核心。）

1. **Broadcast（广播）**：

- 核心定义：一对多的单向通信。从一个根节点（Root Rank），把完全相同的数据，发送给通信域内所有其他 rank，最终所有 rank 都持有和 root 完全一致的数据；
- 直观示例：4 个 rank，root=0。（摘要至此截止。）

### 论文精读：输出嵌入层（Output Embedding）的并行

- Transformer 语言模型有一个输出嵌入层，其维度为隐藏大小（H）乘以词汇大小（v）。由于现代语言模型的词汇大小通常在数万个标记的量级（例如 GPT-2 的词汇大小为 50,257），因此并行化输出嵌入的 GEMM 操作是有益的。
- 然而，在 Transformer 语言模型中，输出嵌入层与输入嵌入共享权重，因此需要对两者进行修改。将输入嵌入的权重矩阵 `E_{H×v}` 沿词汇维度 `E = [E1, E2]`（按列）进行并行化。由于现在每个分区只包含嵌入表的一部分，所以在输入嵌入之后需要进行一个全局归约（all-reduce）操作（用 g 表示）。
- 对于输出嵌入，一种方法是执行并行 GEMM 操作 `[Y1, Y2] = [XE1, XE2]` 以获得逻辑概率（logits），然后进行全局收集（all-gather）操作，将结果发送给交叉熵损失函数。但在这种情况下，all-gather 将会传输 `b × s × v` 个元素（b 是批量大小，s 是序列长度），词汇大小很大时代价极高。
- **为了减少通信量，将并行 GEMM 的输出 `[Y1, Y2]` 与交叉熵损失融合在一起**，将维度减小为 `b × s`（即对每个词汇的输出先计算出标量损失，再归约为总的 loss）。传输标量损失而不是 logits 是通信量的巨大减少，提高了模型并行方法的效率。

### 并行方法优势的总结

Megatron 几乎所有的模型并行方法旨在尽可能减少通信开销，并保证训练过程是计算密集型的，从而保证训练的可扩展性——**只要卡够，多大的模型都可以训练，单卡内存和通信开销不会成为瓶颈**。

论文到这里，Megatron 的模型并行方法就介绍完了，后面就是实验，以及如何调整模型架构和超参数以达到更高准确率的经验方法。

### 七、哲philosophy：Megaton-LM 训练大模型实战不完全指南 ｜ 0-序

> 作者：哲philosophy ｜ 赞同：19 ｜ 原文链接：[https://zhuanlan.zhihu.com/p/1959619969617729323](https://zhuanlan.zhihu.com/p/1959619969617729323) ｜ 全文来源：知乎搜索摘要

### PyTorch 自带方案：FSDP

与之相对应地，PyTorch 自身其实也有他们自己的一版 ZeRO-3——**FSDP（Fully Sharded Data Parallel）**。这个可以看作 data parallel 的伴生技术：正常当模型没有那么大，单张 GPU 能放下一整个 model、不需要做切分时，我们往往也会使用很多张 GPU 同时训练，此时的多卡并行叫做数据并行（Data Parallel），此时每张卡都会存储一整份 model，不同卡上只有数据是不同的，这样就可以用相同的时间处理 n 份数据（n 为 GPU 总数）。FSDP 就是在此基础上，当 model 很大时，将 model 也完全地分块（Fully Sharded），同时做数据并行，整体的思路和 ZeRO-3 是一样的，但优化上做得比 ZeRO-3 要更好。

### Megatron-LM 的多维度模型并行（5D 并行）

而 Megatron-LM 在模型并行这一块，采用的是不太一样的思路。Megatron-LM 提出了多维度的模型并行，例如：

- 张量并行（Tensor Parallel）
- 序列并行（Sequence Parallel，可以看作是张量并行的附带）
- 上下文并行（Context Parallel）
- 流水线并行（Pipeline Parallel）
- 专家并行（Expert Parallel）

实战中还可以将这 5D 并行进行有机结合。牛逼的地方在于，Megatron-LM 对这一系列模型并行的优化很不错，尤其是在 Nvidia 系列显卡上，通过各种通信和计算的 overlap 或者算法层面的设计，使得整体的通信 overhead 不大。更关键的是，由于并行度高，当涉及到超大规模模型（例如 100B 级别规模的模型）时，Megatron-LM 能同时开启多个维度上的并行，从而让这种大模型能在分布式环境下跑起来，而且训练速度是可接受的。

### 实战中的 3D 并行组合

实战中一般采用 **数据并行（DP）+ 张量并行（TP）+ 流水线并行（PP）** 的方式：

- 上下文并行只用于 Long-context training；

### 模型并行与 GPU 集群

大语言模型的预训练和 GPU 显卡是息息相关的。从 Infrastructure 的角度来说，预训练的重要课题之一，就是尽可能地保证模型能在由大量 GPU 显卡构成的显卡集群上，顺利、高效地进行计算。分布式计算是大规模集群预训练的重要特性之一，**模型的权重、激活值和梯度都需要在不同 GPU 之间进行分摊**，以合理而高效地利用所有的显卡。更重要地，如果模型尺寸非常大，单 GPU 的显存无法容纳模型时，我们不得不使用模型并行技术来将模型进行切分，从而保证模型预训练的正常进行。

Megatron-LM 作为一个分布式计算实现比较完善的代码库，其对于分布式计算，尤其是模型并行的实现，效率还是非常高的，**其官方声称的多 GPU 训练效率能接近于线性**（即：使用 N 个 GPU 进行训练，其速度可达到单 GPU 的 N 倍）。在未经优化的代码上，这种线性增益是很难做到的，多 GPU 之间的通信额外开销会极大程度地拖慢训练效率，**比如 2 卡的速度可能只有 1 卡的 1.3-1.5 倍**。然而，Megatron-LM 库的入门门槛还是很高的，需要花不少时间去了解分布式计算的基础以及 Megatron-LM 的使用方法。

这篇文章主要介绍在 Megatron-LM 中，如何使用上篇指南文章（3-模型并行）中讲述到的各种分布式计算技巧，尤其是如何使用模型并行。这对于使用 Megaton-LM 进行超大规模模型预训练是非常重要的，只有理解代码上的这些实现细节，对于调试分布式训练中的各种问题非常关键——**当训练 hang 住、梯度不同步、显存 OOM 时，知道底层在做什么，才能快速定位问题**。

### 1. 模型越来越大，单卡怎么办？

2018 年的 ELMo 只有 9400 万参数，到了 2020 年，GPT-3 已经膨胀到 1750 亿——短短两年增长了近 2000 倍。如果试图用一块 V100 GPU 训练 GPT-3，**需要大约 288 年**。

更残酷的现实是：即使是最新的 80GB A100，也装不下这些巨型模型。你必须把模型切分到多块 GPU 上。这就引出了模型并行的概念。但问题来了——怎么切？

### 2. 三种并行的「三板斧」

论文系统地梳理了三种并行方式，并将其比作可以「组合出拳」的工具箱：

**2.1 数据并行（Data Parallelism）**

- 最直观的方式：每块 GPU 持有完整模型副本，数据分片到各 GPU，梯度周期性同步。
- 优点：实现简单，通信友好（梯度同步是一次性的）。
- 缺点：模型必须能塞进单卡——对大模型直接失效。

**2.2 张量并行（Tensor Model Parallelism）**

- 把单个 Transformer 层的矩阵乘法切分到多块 GPU 上。
- Megatron-LM 做的就是这件事：**把 MLP 的权重矩阵按列切分，把 Attention 的多头按 GPU 分配**。

### 八、监控指标（必须观测）

1. **MFU（Model FLOP Utilization）**：核心指标，H100 大模型理想 **45-48%**；低于 35% 说明并行/通信配置有问题。
2. **GPU SM 利用率**：**80-95%**；如果很低，大概率是通信瓶颈、气泡、micro-batch 太小。
3. **迭代时间拆分**：计算时间、all-reduce/all-gather 通信时间、dataloader 时间。
4. **MoE 额外监控**：路由损失、专家 token 分布标准差。
5. **loss、grad norm**：grad norm 剧烈震荡 → 学习率过高或梯度裁剪不合适。

### 九、数据加载

1. 使用 Megatron 原生的 **mmap 二进制数据集**；避免在线 tokenization。
2. 开启数据预取、多线程 loader；dataloader 不要成为瓶颈。
3. 数据集 blending 做确定性混合，dist-checkpoint 下可以恢复数据迭代器状态。

### 十、常见坑与避坑清单

1. ❌ **TP 跨节点**：TP 尽量约束在单节点 NVLink 内；跨节点 TP 带宽暴跌，MFU 直接垮掉。
2. ❌ **PP 设置过大**：PP 越大气泡越大，MFU 下降；层数少的模型不要盲目开大 PP。
3. ❌ **一上来就 full-recompute**：优先 selective，full 会严重降吞吐。
4. ❌ **MoE 下 router 用 BF16**：路由计算要用 FP32，否则精度退化。
5. ❌ **不开启通信 overlap**：`overlap-grad-reduce` / `overlap-param-gather` / `tp-comm-overlap` 不打开，MFU 上不去。
6. ❌ **使用老的完整 checkpoint 而非 distributed checkpoint**：无法跨并行度恢复，保存加载慢。
7. ❌ **FP8 直接上大模型**：先 BF16 跑通收敛，再切换 FP8，监控 loss 曲线不要漂移。

### 十一、Megatron-Core vs Megatron-LM vs Megatron-Bridge

- **Megatron-Core**：底层库，提供 TP/PP/CP/EP 算子、transformer 模块，用于嵌入自定义训练框架。
- **Megatron-LM**：上层示例，完整训练脚本，快速跑 GPT/LLaMA/MoE 预训练。
- **Megatron-Bridge**：HuggingFace ↔ Megatron 权重双向转换，推理部署必备工具链。
