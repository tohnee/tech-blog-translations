《AI as a Compiler》让 agent 直接把 Triton 翻成 PTX，拿到了最高 3.34× 的性能，比较对象是经过调优的 Triton 基线。到了摘要结尾，作者把愿景推到了用 AI 替代手写 IR 和检查器。[1] 我对这个推论有个很直接的疑问：模型既然能找到编译器缺的优化，为什么不让它把这些优化补进编译器？

这篇论文让我看到的，恰好是 agent 有能力参与编译器开发了。它能改布局、排流水、处理架构相关的指令，也能根据错误反馈反复调试。过去费人力的工作，现在有机会交给模型。可一讨论未来，编译器却先被安排成了需要绕开的对象。这里面跳过了一个问题：做出的优化，最后以什么形式留下来？

## 一 这 3.34× 到底是谁的功劳

TAIC 拿到的是 Triton 源码，以及确定的 shape、编译期常量、启动配置和目标 GPU。模型生成 PTX，环境负责编译、测试和计时，再把报错、性能和 profiler 信息送回来，模型接着修改。它花了一轮又一轮搜索，尝试当前 Triton 流程没有生成的实现。

这组结果里，有比基线快的，也有持平和退步的。论文报告的总体区间是 0.83× 到 3.34×，最高的收益来自 BitDelta。看一下附录，原因相当具体。[1]

![](https://pica.zhimg.com/v2-433f5452372a3eead362e97d5b32f80c_r.jpg)
*图1　论文 Fig. 5：B200 上各算子的最佳数值验收结果，虚线为 Triton 基线。[1]*

BitDelta 的 Triton 实现把二值权重逐个解包，算出正负一，转成 FP16，再存进共享内存。生成的 PTX 用位操作直接构造打包的 FP16 值，还调整了矩阵乘法的方向，让解码后的权重直接进入 Tensor Core 使用的 tensor memory，省掉共享内存的一次存取。再配合更深的流水和更大的归约步长，最后得到 3.34×。

FlashAttention 也一样。Triton 把一行 score 分给两个 lane，归约需要跨 lane 通信；生成的 PTX 让一个线程持有完整的一行，最大值和求和就能在自己的寄存器里完成。再扩大 query tile、提高 K/V 复用、调整流水与同步，合起来得到 1.37×。[1，附录 A.2]

少搬一次数据，少做跨线程归约，同一块 K/V 多服务一些 query，性能就这样省出来了。把这些改动列出来，没有哪一项叫“去掉 IR”。作者在附录里也明确把收益归于指令、数据移动、同步和任务分解的联合调整。沿着这段分析，我能接受模型已经会做复杂的底层优化；再往前推到替代手写编译抽象，中间还隔着一段论证。

基线的设置也得放进来。论文用了 Triton 3.6.0，做过手工优化和 autotuning，但不使用实验性特性和手写 inline assembly。Agent 则可以直接重写 PTX，重新分配线程、换布局、换指令。[1，§4] Autotuning 在已有候选里选配置，重写实现会改变候选本身。两边同时改变了搜索方式和能动的范围，最后得到的加速比，很难只归到绕过编译流程这一个选择上。

假如某个 Triton 后端还没实现一种布局优化，那就说明它缺这项优化。假如现有接口很难表达某种硬件能力，那就说明接口需要改。把这两种缺口统统算到 IR 头上，结论就粗了。编译器今天没做出来的东西，agent 做出来了，完全可以成为编译器明天新增的能力。这些性能结果还没有说明，把能力积累在编译器里为什么就不如直接生成。

## 二 后端绕过去了，麻烦还在

先看它绕到了哪里。PTX 是 NVIDIA 的虚拟指令集，后面仍然要经过 NVIDIA 工具链，才能得到 GPU 执行的机器指令。[3] TAIC 绕过了 Triton 的优化与 lowering，下面的 ptxas、CUDA driver 和 GPU 执行路径照常工作。它是在成熟工具链上换了一段生成流程。把这个结果继续推广到新芯片的软件建设，指令语义、工具支持和验证能力都还得有人补。

![](https://picx.zhimg.com/v2-1df3590003826f8314ef6a1abb5ef909_r.jpg)
*图2　论文 Fig. 2：TAIC 共用 NVIDIA 底层执行路径，并依赖测试、计时与验证环境。[1]*

论文自己的验证部分，就把这笔工作摆了出来。模型可以大胆改代码，负责收下代码的验证器却得知道：异步加载什么时候结束，数据什么时候可见，一个缓冲区还有没有线程在读。硬件不会因为上面接了大模型，就放宽这些要求。

Table 2 很直接。把原版 Volta 放进搜索流程，要求候选通过符号验证，B200 上 FP16 GEMM 的最佳结果只有 Triton 的 0.24×；只做数值验收时，能找到 1.03× 的实现。FlashAttention 的两组结果则是 0.78× 和 1.37×。原版验证器支持不了一部分现代 GPU 特性，模型就得退回它能接受的范围。[1]

![](https://picx.zhimg.com/v2-6edadc02d294a5091ccc2510d25896db_r.jpg)
*图3　论文 Table 2：两种验收条件下分别搜索到的最佳实现，左列使用原版 Volta。[1]*

为了接住这些高性能实现，作者继续扩展 Volta，加入异步复制、现代 Tensor Core 指令和更多同步机制，可信计算基从约 4.2 万行长到 6 万行。覆盖范围扩大了，附录 B 同时写得很明白：这些扩展还没有建立 soundness 和 completeness 的保证，形式化工作留待后续完成。[1，§4.5、附录 B]

Completeness 不足，会让一些正确程序过不了检查。Soundness 的保证没有建立，问题就落在检查器自己的判断是否可信。论文让验证器承担这么重的责任，验证器的建模却还没完成；摘要又进一步谈到替代手写检查器。这个愿景最依赖的一环，恰好还没补齐。

浮点数也是绕不开的一笔账。Volta 把浮点计算抽象成实数计算，实数表达式相等，不能直接推出硬件上的浮点结果在整个输入范围内都满足误差要求。归约顺序、精度转换和近似指令，各有各的数值行为。测试可以筛掉一批错误，符号检查可以提供它所建模范围内的保证，但这些工作没有随着 lowering 的消失一起省掉。

我不接受的是只拿传统后端的维护负担说事，然后把新路线依赖的硬件建模和验证基础设施放到后面。判断是否省了工程量，要把两边的工作都算进去。模型越敢用新的硬件能力，验收端越得跟上；让模型参与编写验证器，这个验证器也仍然需要被检查。

公开实现里还有人工知识的身影。仓库会按算子类别加入专用提示，卷积提示写到了地址计算，FlashAttention 提示写到了 shape、causal mask 和 online softmax 的状态更新。[2] 这些知识当然能帮助模型完成任务。可同样的知识，写进 prompt 就成了模型的上下文，写成 pass 就成了需要摆脱的维护负担，这个取舍我看不出有什么必然性。

## 三 模型会写 PTX，也可以给编译器补课

我更愿意让 agent 直接参与编译器的生长。已有的 pass，让它选择、组合；缺少的变换，让它补；某块硬件特别适合一个局部实现，就让它写 micro-kernel。需要直接生成 PTX 的地方照样生成。这些办法可以在同一套系统里共存，没必要一上来就把中间几层全部绕开。

一个 pass 保存的，是某项优化怎么做、什么条件下能做。比如一轮调试终于搞定了布局变换，除了当前 kernel 的代码，还应留下识别适用结构的规则、变换本身，以及边界处理。下一个相似程序来了，系统可以检查条件、执行规则，接着往下编译。模型已经解决过的那部分问题，就不必再从头推导和调试。

![](https://pic2.zhimg.com/v2-65589e24de59f0495f2a3ac5b8c366a3_r.jpg)
*图4　Agent 补写并调试优化；验收后留下适用条件、变换和局部实现，供后续程序匹配与复用。*

这也正是只缓存一个成品没有回答的部分。论文说生成成本可以被后续执行摊薄，这点成立：同一个配置跑很多次，第一次生成贵一些，未必是问题。[1，§5] 但换了 shape、布局或者融合方式，旧成品还能用多少，要看它覆盖了什么。缓存保存了这次找到的实现，pass 可以保存产生一类实现的方法。后者要多做适用条件和泛化的工作，换来的也是更大范围的复用。

当然，给特化代码套一个函数名，不会自动变成通用 pass。模型还得把适用范围弄清楚，处理参数和边界，把依赖关系落实到程序里。适合泛化的部分进入 pass，架构相关的局部代码进入 micro-kernel，剩下的保留专用实现就好。把优化推广到一类程序，就得做这些工作，agent 可以接着做下去。

我更在意下一批任务要重做多少工作。按这种方式积累，编译器可以多一项能力，agent 也能接着处理新的缺口。花掉的推理和调试成本，留下了可以继续使用的东西。编译器开发难，正好给了 agent 一个该干的活，怎么就直接跳到绕开编译器了？

## 四 很多优化卡在做不对，agent 正好可以接手

再往前走一步，连“寻找优化点”都未必每次要从头开始。双缓冲、加载与计算重叠、换一种归约分工、复用相邻窗口的数据，这些方向并不神秘。知道方向以后，把索引、布局、状态和同步一起改对，才经常是最耗时间的部分。一个改动牵出好几个地方，方案明明有道理，代码就是跑不对。

我的想法是，允许人或 agent 先提出激进的优化，先把结构写出来，哪怕初稿有错，再让 agent 在性能要求下把它修好。人不必先把每个实现细节想得滴水不漏，模型也不必每次都扮演从零发现优化的专家。它能读报错、追依赖、改代码、反复运行，这些能力正适合接手难调试的实现。

双缓冲就是个很直观的例子。下一轮加载提前覆盖了上一轮还在使用的数据，取消加载与计算的重叠，错误可能马上消失。可原本想省掉的等待也回来了。把“会重叠但有错”修成“完全串行所以没错”，任务只完成了一半。我希望它继续处理缓冲区的生命周期、等待位置、流水的启动与收尾，让那个优化成立。

![](https://pica.zhimg.com/v2-5727437412b2b343cf13764f7be0ee96_r.jpg)
*图5　双缓冲修复示意：A、B 为两个缓冲区，k 为数据块编号。右侧为稳态重叠，缓冲区读完后才能复用；图中宽度不代表实测耗时。最终实现还须通过正确性与性能验收。*

这里也不能拿错误代码的计时当标准。漏算一半当然快，修复后的性能要和可信基线比较。优化结构有潜力，只说明它值得继续修；最终留下来的实现，正确性和性能都得过关。结构可以重写，线程分工可以换，原先想解决的性能问题不能被悄悄删掉。

TAIC 本来就会根据正确性和性能反馈反复修改。我希望这项能力再多产出一些东西：调试确定的适用条件、已经修对的变换、能够重复调用的局部实现。一次难做的优化修好了，下一次类似任务就能沿用这次成果。PassNet 已经在研究模型生成图编译 pass，CUDABeaver 也在研究保持性能的 CUDA 修复。[4][5] 把这些能力接起来，比把 agent 和编译器放到互相替代的位置上，更符合我对这条路线的期待。

读到最后，我对这篇论文最大的分歧，仍然是它怎么使用模型已经展示出来的能力。性能收益能解释到具体的优化，验证和人工知识又都还在；这时候就把愿景指向替代编译抽象，我不认同。我的选择是让 agent 继续写 pass、补 micro-kernel，把这次修好的东西留给下一个程序。编译器还有一大堆活没干完，正好让 agent 来干。
