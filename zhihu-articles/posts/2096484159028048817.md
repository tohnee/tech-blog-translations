MoE（混合专家）推理有两个几乎无法同时满足的性质：一是极度**访存受限**，decode 阶段每个专家只收到几个 token，GEMM 退化成又小又碎、数据复用极差的形状；二是负载**极度倾斜且随时在变**，某一步可能有专家吃到 20 倍于平均的 token 数，下一步又换人。

3D-stacked DRAM 的近存计算（NMP，Near-Memory Processing）看起来是天生匹配：把计算放进 DRAM 逻辑die，带宽直接怼到内存旁边。但 NMP 的 tile 化组织带来一个残酷的成本不对称——**本地访问快且带宽足，远程访问要过 NoC、还要抢共享带宽**。于是 MoE 在 NMP 上的部署陷入三方拉扯：要保持局部性（专家并行 EP），就会吃到负载倾斜；要做分布式均衡（张量并行 TP），通信开销又会吃掉带宽优势。

中科院计算所（SKLP/ICT）与爱丁堡大学合作的 3D-MoE 给了一个挺有意思的答案：**先承认倾斜不是随机的**——预训练出来的专家有领域偏好，不同领域的请求会激活不同专家子集，于是不同专家的负载会在时间上"此消彼长"。他们把这个现象叫**专家互补性（expert complementarity）**，用它做离线分组，把均衡问题从"逐专家"降级成"逐组"；组内残留的热点，则用一条硬件快路径（CMN）"一次读取、广播多核"来兜底。

结果：MoE 层解码平均比 EP 快 4.63 倍，端到端吞吐比最强的 NMP 基线高 1.58–1.86 倍，比 GPU 高 5.5–7.9 倍，额外逻辑 die 面积只有 2.11%。

## 一、问题：为什么 EP 在 NMP 上必然崩

先看数字。作者在 batch size 64 下做 profiling，**MoE 层占端到端延迟的 83–92%**；最热的专家能拿到超过 20 倍的步均负载；每个专家自己的负载在不同步、不同层之间波动 2–7 倍。

![](https://pic3.zhimg.com/v2-f5057be79f5e4f3bc0a9ff7c07dbcf42_1440w.jpg)

图 2：Qwen3-30B-A3B 上的专家激活分析。(a) 数学类与代码类请求的专家命中率热图，领域偏好非常明显；(b) 专家负载在层间的波动。

图 2(a) 是整篇论文的起点：不同领域的请求命中的是明显不同的专家子集（论文还提到，数学/代码负载中超过 90% 的命中落在各自的偏好子集内）。这不是训练不充分，而是 MoE 在共享专家吸收通用模式后，路由专家自然分化出的领域专精。

NMP 的组织形态决定了并行的选择：

![](https://pic4.zhimg.com/v2-d181b82690458c3471e6024a69aae3c3_1440w.jpg)

图 3：堆叠 DRAM 的 NMP 系统组织。每个 NMP stack 由 DRAM die 加底层逻辑 die 组成，逻辑 die 上每个核紧耦合一个 HBM 通道，构成一个"计算—存储单元"，核间通过 NoC 通信。

在这种结构上，四种并行策略的代价被论文画成了一张对照图：

![](https://pic3.zhimg.com/v2-5a3cff961728bf1c196308a23c1263c6_1440w.jpg)

图 4：既有 MoE 部署策略与本文方法的对比。(a) 专家并行 EP：局部性好但热点核成为 straggler；(b) 张量并行 TP：负载平了但每次调用都要分布式执行加归约；(c) 预定义热点专家复制：复制了却不一定对上真实热点；(d) 本文：互补专家分组加组内协作。

- **EP**：专家权重留在本地，聚合后 GEMM 形状也更大，但热点专家所在的核必然变成木桶短板。
- **TP**：负载被摊平，但每次专家调用都变成分布式执行 + 归约；论文实测在 32 核时 **NoC 开销占到专家执行时间的 52%**，而且权重切分削弱了单核 GEMM 的局部复用。
- **在线修复型 EP**（重映射、复制、work stealing）：步级/层级的波动让热点预测很难准（既有工作报告的准确率低于 50%），而权重迁移和远程协助本身又在消耗 NoC 带宽——恰好是 NMP 最贵的东西。

所以作者的结论是：EP 是 NMP 上唯一合理的主干，剩下的问题只是"怎么在不破坏局部性的前提下均衡负载"。

## 二、核心观察：互补性是可测量、可泛化的结构

把每个专家在每一步的 routed token 数看作一条时间序列 F(e,d)。如果两个专家长期"此消彼长"，把它们放进同一组，组的**聚合**负载就会比单个专家平稳得多。这正是 RACE 之外的另一类"统计结构"用法：不去预测单点，而是利用长期的反相关。

判定"显著互补"的方法挺讲究：直接设一个相关系数阈值不够稳，作者给每个模型—数据集组合构造一个**经验零分布**——把一条序列相对另一条做循环移位（circular shift），破坏时间对齐但保留各自的边际分布，重算相关系数；观测值低于该零分布 5% 分位才算显著互补。

结果相当稳定：

- **普遍存在**：82.2%–88.3% 的专家至少有一个显著互补伙伴，平均每专家 9.6 个；
- **跨数据集保留**：在一个数据集上找到的伙伴，有 70.6%–80.5% 在另外两个数据集上仍然显著；
- **跨时间窗保留**：用前 256 步找伙伴，接下来三个 256 步窗口的保留率是 94.5%、92.7%、90.8%；
- **组级均衡效果**：三种模型上平均 M2M（最大组负载 / 平均组负载）降低 17%，压到 1.1 附近。

![](https://pic4.zhimg.com/v2-dff82f1336b1b771332cec8c27a86f25_1440w.jpg)

图 5：DeepSeek-V2-Lite 第 10 层的互补性示例。(a) 高互补专家组：两条曲线反相，聚合后（下方）明显更平；(b) 低互补性组：曲线同相，聚合后依然起伏。

![](https://pic2.zhimg.com/v2-93b94df7dc4d81317bcb6ca1cd0403ab_1440w.jpg)

图 6：组间负载均衡。三个 MoE 模型在 LMSys 负载、每组 8 专家的设置下，M2M 随解码步的变化；理想值为 1。

作者还做了一个交叉验证：互补对的领域偏好余弦相似度确实**低于**正相关对和随机对（DeepSeek-V2-Lite 上 0.19 vs 0.67 / 0.43），说明"互补"确实对应着"服务不同领域子集"，而不是统计巧合。

## 三、系统：三件套

![](https://pica.zhimg.com/v2-14a0de9414aa00cc696cfb7e39651364_1440w.jpg)

图 7：3D-MoE 的软件框架。(a) 离线互补性引导的专家分组与映射；(b) 运行时组内专家调度，用性能表把 token 数换算成核延迟，选出瓶颈专家与协助核；(c) 在线自适应重映射。

### 3.1 离线：两级 ILP + 二次规划映射

分组写成**分层多目标 ILP**，用 Gurobi 求解，按优先级依次最小化：组间计算量 T 的极差（所有解码步上求和）、组间协作量 M 的极差、总协作量。协作量来自一个"负载偏移分"——只有当两个专家分别处于步均线两侧时才计分，取两者偏离量的较小值，物理含义是"能从热专家挪给冷专家的可转移工作量"。

映射则是**二元二次规划**：既要让协作密切的专家放得近（降低组内协作距离），又要让经常被同一 token 同时选中的专家放得近（它们是多播的共同目的地，共享路由段可以省链路）。后一项由权重 λroute 控制，消融显示去掉它会让 Qwen3-30B-A3B 的 dispatch/gather 延迟平均上升 47%。

求解设置：3% 相对 MIP gap 或 3 分钟超时，68% 的运行能达到 3% 目标，超时的最差 gap 为 7.1%。**每个模型只解一次**，用 256 条 prompt × 256 步的代表性 trace，预处理 1–3 小时，然后跨负载复用。

### 3.2 硬件：CMN，把"一次读、多核收"做成一条临时总线

组级均衡之后，组内还有残留热点。这时有三条常规路，作者都量了代价（2/4/8/16 个核协作一个热专家，单位 ms）：

| 方案 | 2 核 | 4 核 | 8 核 | 16 核 |
| --- | --- | --- | --- | --- |
| 理想下界 | 0.84 | 0.42 | 0.21 | 0.105 |
| 按需远程取权重 | 1.08 | 0.69 | 0.45 | 0.36 |
| 单次读取 + 常规 NoC 广播 | 0.94 | 0.56 | 0.33 | 0.20 |
| 组内 TP | 1.00 | 0.64 | 0.42 | 0.30 |
| CMN（本文） | 0.88 | 0.46 | 0.25 | 0.14 |

表：单热专家协作延迟。按需远程取比理想值高 29–242%，组内 TP 高 19–185%，单次读加常规 NoC 广播平均仍高 48%；CMN 把差距压到 5–33%。

为什么常规 NoC 广播还是慢？论文给了 flit 级拆分：**固定路由器流水线占平均 flit 延迟的 63.2%**，动态等待只占 7.8%。也就是说瓶颈不是拥塞，而是每一个 hop 都要走一遍流水线。CMN 的做法是把这段流水线**旁路掉**：

![](https://pic3.zhimg.com/v2-33ddbb2740c80e818df5a8886c7b080a_1440w.jpg)

图 8：CMN 的微架构与资源共享。(a) 热专家权重通过临时广播路径从宿主核流向协助核；(b) 每个 NMP 核内含数据转发单元 DFU、数据接收单元 DRU 与可重构协作链路 RCL：DFU 挂在内存控制器的读返回缓冲之后，把匹配地址范围的 tile 同时送往本核权重缓冲和 RCL；协助核的 DRU 收流写入本地缓冲。

关键设计点有三个：

- **地址范围 + 协助核掩码**：协作开始前，控制器把热专家的地址区间和协助核集合写进 DFU；只有落在该区间的 DRAM 读返回才被转发，不干扰正常流量。
- **RCL 复用现有 NoC 链路**：token 分发/聚合走常规包交换，热专家协作走"临时总线"广播。两种模式在时间上分相，所以同一条物理链路可以两用而不冲突；路由器里的 Bus Switch 把选定链路从包流水线上摘下来，Session Arbiter 负责协作会话间的互斥。
- **切换成本可忽略**：RTL 推导的切换是 40 个周期（16 周期会话建立 + 8 周期链路排空保护 + 16 周期恢复），650 MHz 下 61.5 ns，不到 CMN 延迟的 0.05%。

CMN 用 7nm 综合，含 DFU/DRU/RCL 的额外逻辑 die 面积是 **2.11%**。

### 3.3 在线：三级重映射，91% 的迁移被藏起来

离线方案在负载漂移下最多损失 15% 性能。3D-MoE 用 EMA（α = 0.3）预测专家负载，按迁移成本分三级调整：

- **Tier-1**：只改现有副本之间的负载分配比例，不搬权重，每个 MoE 层前都跑；
- **Tier-2**：给过载专家加一个副本、从空闲专家撤一个副本，一次权重传输；
- **Tier-3**：跨组交换专家，两次迁移，用于严重的组间失衡。

Tier-2/3 每 8 个解码步检查一次（或检测到持续失衡时提前），触发条件是 EMA 预测的组级 M2M 连续三步超过稳态 20%。每个候选动作都要先算收益、再减迁移成本（权重体积 × 距离 / 可用带宽），净收益为正才执行，传输与计算重叠。Qwen3-30B-A3B 上平均每层每 256 步有 24 次搬权重的重映射，**91% 的传输时间被 xPU 稠密计算或 NMP 空闲窗口掩盖**，端到端暴露开销 0.87%。

## 四、实测

### 4.1 离线方案真的能泛化

这是审稿人最会质疑的点：一次离线 ILP 出来的分组，换个数据集/换个时间窗/换个 batch 还成立吗？

![](https://pic2.zhimg.com/v2-a8c8e1f30d849d366694edfa9d6535ff_1440w.jpg)

图 9：一次性离线分组的泛化性。(a) 跨数据集：固定分组在 ShareGPT/HumanEval/MATH 上的组级 M2M；(b) 跨时间窗：同一服务流上连续 256 步窗口的 M2M，虚线为加了在线重映射的版本；(c) 跨 batch：32 到 768 的稳定性。

- 跨数据集：比基于粗粒度历史负载的 History-Reuse 低 20%–24%，**补上了到 Oracle-Reopt（每个条件重新求解）86% 的差距**；
- 跨时间窗：跨窗口只退化 9%；
- 突变场景：Qwen3-30B-A3B 从代码负载突然切到数学负载时，峰值 M2M 是 1.21（History-Reuse 为 1.62），加在线重映射后 16 步内回到 1.15；
- 跨 batch：32→768 全程稳定，比 History-Reuse 低 22%，距 Oracle 在 25% 以内。

## 五、对做架构/系统的人有什么用

- **"负载均衡"不一定要靠预测。** 这套方法的核心不是把热点算得更准，而是找一个**在时间上反相**的组合，让聚合量自然变平。凡是"请求类型决定资源使用"的系统（MoE、多模态路由、推荐的多兴趣召回），都值得先看看有没有类似的反相关结构——它比预测模型更便宜，也更稳。
- **NMP/PIM 上的并行策略要按"成本不对称"重排。** 在 GPU 上，EP 的负载倾斜可以用弹性调度、抢占、更大 batch 掩盖；在 NMP 上，任何跨核动作都要过 NoC，而 NoC 的固定流水线开销（这里占 63.2%）对小消息尤其致命。所以"少动、动一次给多人用"的设计（单次读 + 广播）比"多动但每次小"更划算。
- **离线重规划 + 在线微调的分层是合理工程折中。** 1–3 小时的离线求解换来跨数据集的稳定分组，在线只做低成本修正，且 91% 的迁移成本能被计算掩盖——这个比例是这类方案能否落地的关键指标，值得在设计阶段就当作目标。
- **注意 λroute 这类"看起来次要"的项。** 只做协作局部性、忽略 token 路由的共目的地局部性，会让 dispatch/gather 延迟涨 47%。多播型流量在 NoC 上的收益常常被低估。

## 六、批判性评估

论文的实验密度很高（三个模型、四档 batch、跨数据集/时间窗/batch、Op/B 扫描、scale-out），但它的性质决定了结论要打折看：

- **全部结果来自周期级模拟器，没有流片。** 系统模型是 Ramulator 2.0 + BookSim 的扩展（HBM3 时序、NMP 核访存、包交换、RCL 预留链路），xPU 侧的稠密算子直接用 GPU 实测延迟拼接。CMN 只做到 7nm 综合（面积/功耗），没有布局布线、没有时序收敛、也没有真实 DRAM 上的广播功耗测量。**2.11% 面积和 61.5 ns 切换都是 RTL 推导值，不是硅上数据。**
- **离线求解的开销被"每模型一次"轻描淡写。** 1–3 小时/模型、68% 的运行能收敛到 3% gap、最差 7.1%，这些在论文里是脚注级信息，但工程上意味着换模型/换主要负载分布就要重跑，且解的质量有 1/3 概率不达标。
- **互补性的前提是"混合领域负载"。** 论文自己承认：同质负载下，偏好相近的专家不太可能落进同一组，组级均衡的收益会缩水。真实线上流量如果长时间单一（比如纯代码补全服务），这套分组的价值会明显下降——此时剩下的只有 CMN 的协作加速。
- **CMN 是硬件改动，不是纯软件优化。** DFU 挂在内存控制器读返回路径上、RCL 要能重配 NoC 链路、路由器要加 Bus Switch 与 Session Arbiter——这意味着它只能在设计 NMP 时一起做，无法在现有 GPU/NPU 上"部署即用"。
- **没有开源。** 论文未提供 RTL、模拟器或 trace 的 artifact 链接，我们按标题与关键词在 GitHub 检索也无命中。复现门槛较高（需要自己搭 NMP 周期级模型）。
- **对比基线的实现细节有限。** HD-MoE、PS（EPLB 式预测复制）、WS（work stealing）都按作者自己的理解重建，缺少与原论文实现对齐的说明；这类"基线复现差异"在体系结构论文里是常见的隐性偏差来源。

总体判断：这是一篇**问题选得准、机制讲得透**的软硬协同工作。它最有价值的不是 4.63× 这个数字，而是把"MoE 负载倾斜"从"要预测的随机性"重新表述成"可以利用的结构性互补"，并且用一套可测量的统计检验（循环移位零分布）把这个结构坐实了。至于 NMP 本身能不能成为主流部署形态，那是另一个更大的问题——但当近存计算的带宽真的可用时，这篇论文给出了一个相当完整的"如何在其上跑 MoE"的答案。
