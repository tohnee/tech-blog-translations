最近维护一套由 `A 集群`和 `B 集群`两个计算集群组成的 InfiniBand 网络时，`A 集群`主节点突然无法访问子节点，同时 Slurm 的 `squeue`、`scontrol` 也无法正常工作。

最初怀疑的方向包括：

- IB 网卡驱动或 OFED 异常
- IPoIB 地址配置错误
- 交换机端口或线缆故障

但检查 `A 集群` 主节点 IB 网卡后，出现了一个很典型的状态：

```text
State: Initializing
Physical state: LinkUp
Rate: 56
Base lid: 0
SM lid: 0
```

这组状态非常有信息量。

`Physical state: LinkUp` 说明网卡、线缆和交换机端口之间的物理链路已经建立，56Gb/s 速率也说明并非简单的断线问题。

真正异常的是：

```text
State: Initializing
Base lid: 0
SM lid: 0
```

InfiniBand 与普通以太网不同。即使物理链路已通，仍需要 Subnet Manager（SM）完成拓扑发现、LID 分配、路由表和分区表配置，端口才能进入 `Active` 状态。

因此，`Initializing + LID=0` 的含义是：设备已经接入 fabric，但没有被有效的 SM 完成初始化。

本集群使用 Mellanox SB7890 IB 交换机。该类交换机需要依赖外部 OpenSM 进行 Subnet Manager 管理。检查后发现，A 集群上的 OpenSM 没有作为稳定的开机服务运行，导致主节点在重启后无法获得 LID。

最终采用主备 OpenSM 架构：

| 角色 | 主机 | 优先级 | 状态 |
| --- | --- | --- | --- |
| 主 SM | A 集群 | 15 | MASTER |
| 备用 SM | B集群 | 1 | STANDBY |

核心配置如下：

```text
# A 集群
OPTIONS="--priority 15 --master_priority 15"

# B 集群
OPTIONS="--priority 1 --master_priority 1"
```

并用原生 systemd 服务托管：

```text
[Unit]
Description=Cluster InfiniBand OpenSM
Requires=openibd.service
After=openibd.service network-online.target

[Service]
Type=forking
EnvironmentFile=/etc/sysconfig/opensm
PIDFile=/run/opensm.pid
ExecStartPre=/usr/bin/rm -f /run/opensm.pid
ExecStart=/usr/sbin/opensm --daemon --pidfile /run/opensm.pid $OPTIONS
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

恢复后验证：

```text
systemctl status cluster-opensm.service
ibstat
scontrol ping
sinfo
```

结果：

```text
A 集群:  State Active, Base lid 1, SM lid 1
B 集群: State Active, SM lid 1, STANDBY
Slurmctld(primary) at master is UP
```

这次排查留下三个经验：

1. `LinkUp` 只代表物理链路正常，不代表 IB 网络已可用。
2. `Initializing + Base lid=0` 应优先检查 SM，而不是盲目重启全部节点。
3. 集群最好部署主备 OpenSM，并明确优先级，避免多个同优先级 SM 造成不稳定选举。
