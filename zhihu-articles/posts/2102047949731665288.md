在大模型推理中，多卡并行并不只是简单地将模型拆分到不同 GPU 上。随着 MoE、MLA 和长上下文等技术的发展，不同模型组件对计算、通信和显存的需求存在显著差异，传统的 TP、PP、DP 也逐渐演化出更加细粒度的并行方式。

同样一组 GPU，可以在 Attention 阶段按请求分工，在 MoE 阶段按 experts 分工，也可以沿上下文维度划分计算与 KV cache。本文结合 SGLang 的具体参数配置，梳理这些并行机制的原理、组合关系及适用场景，理解它们分别解决什么问题，又付出了哪些代价。

### 1 并行参数的作用范围

Attention 会结合当前 Q 与上下文 K/V 进行计算；FFN 处理各 token 的 hidden states。MoE 模型的 FFN 又可能包含普通 Dense MLP、由 router 选择的 routed experts，以及 shared experts。

Prefill 处理一组新输入 token，建立或补充 KV cache；Decode 在已有上下文上继续生成 token。下面这些参数虽然都使用 TP、DP、CP 等缩写，但它们分别作用于模型、组件、请求或上下文，控制的对象并不相同。

| 参数 | 切分或复制的对象 | 主要解决的问题 |
| --- | --- | --- |
| --tp-size | 每个模型副本、每个 PP stage 内的 GPU 执行组宽度 | 确定层内协作范围，组件可在组内进一步分工 |
| --pp-size | 模型层 | 将模型放到多个 stage |
| --dp-size | 完整模型执行组的副本 | 增加独立处理请求的能力 |
| --attn-dp-size | Attention 的请求组 | 让 Attention 按请求分工 |
| --ep-size | routed experts 集合 | 让不同 GPU 承担不同 experts |
| --moe-dp-size | routed experts 集合的副本 | 在支持的布局下让多个 MoE 组分别处理 token |
| --moe-dense-tp-size | MoE 模型中的普通 Dense MLP | 单独调整 Dense MLP 的并行宽度 |
| --shared-experts-tp-size | shared experts 权重 | 单独调整 shared experts 的并行宽度 |
| --enable-prefill-cp | Prefill CP 策略的开关 | 启用沿输入 token 分工的计算方式 |
| --attn-cp-size | Attention 的 context 分区 | 指定 Attention CP 的分工规模 |
| --dcp-size | Decode 使用的历史 KV | 分摊同一请求的 KV 存储和读取 |

其中，`--enable-prefill-cp` 和 `--attn-cp-size` 是一组互相关联的配置：前者控制是否启用相应计算策略，后者控制分组大小。

`tp_size` 表示一个模型副本的每个 PP stage 内，有多少张 GPU 共同组成执行组。常规静态部署中，总 GPU 数按 **dp_size × pp_size × tp_size** 计算；只有 DP 和 PP 都为 1 时，`tp_size` 才恰好等于总卡数。例如，两个副本、每副本一个四卡执行组，共使用八张 GPU。

Attention-DP、Attention-CP、EP、MoE-DP 和 DCP 都是在这个执行组内部安排分工。下文的组合配置用 `tp_size=8` 表示外层八卡组；组件实际采用的 TP 则明确写成“Attention TP”或“MoE TP”。

对于支持这些组合并行方式的模型，各组件的实际 TP 大小可以通过下面两条关系确定：

- **Attention TP = tp_size / (Attention-DP × Attention-CP)**：分出更多请求组或 context 分区后，每个分区内部参与 Attention TP 的 GPU 数量会减少。
- **MoE TP = tp_size / (EP × MoE-DP)**：分出更多 expert 分区或 MoE 副本后，每个 expert 内部参与 TP 的 GPU 数量会减少。

例如，`--tp-size 8 --ep-size 8` 在其他并行维度为 1 时，表示一个八卡执行组。Attention 在这八张卡上使用 TP8，routed MoE 则在同一批卡上使用 EP8，expert 内部实际 TP 为 1。两种分工复用同一批 GPU，因此总共仍是八张卡。

如果说的是“MoE 实际 TP8、EP8、MoE-DP1”，按分组关系就需要一个 64 卡执行组；它与启动参数 `tp_size=8、ep_size=8` 的含义不同。具体模型和后端还会限制哪些组合可用，不能只看整除关系。

### 2 TP 让多张 GPU 共同承担一层模型

在普通 TP 配置下，`--tp-size` 决定 Tensor Parallel 的实际并行度。一层的权重与计算由多张 GPU 共同承担：Attention 通常按 heads 及相关投影分工，Dense FFN 则分摊同一层的计算。参与 TP 的 GPU 共同完成同一批 token 的计算。

模型在单卡上放不下，或者希望把一层的计算交给多卡共同完成时，TP 可以减少每张卡需要保存的权重和承担的计算量。不过，各卡还需要交换和汇总计算结果，才能继续执行后续层，因此这种分摊也伴随着频繁通信。GPU 间的互联条件会直接影响它的效果。

继续增大 TP，每张卡承担的计算量会变少，但通信开销不会按同样比例减少。如果每张卡分到的计算量太少，还可能难以充分利用 GPU。因此，当通信已经占据较多时间，继续增加 TP 未必能缩短延迟。如果模型已经能在较小执行组内运行，而主要压力来自大量独立请求，也值得比较 DP 布局。

TP 对权重和 KV cache 的影响也需要分别看。GQA 的 KV heads 数量较少时，继续增大 TP 可能出现 KV head 复制；absorbed MLA 的 latent KV 在普通 Attention TP 下也可能重复保存。这时，单纯增加 TP 无法让所有显存占用同比例下降。Attention-DP 和 DCP 分别从请求分工和历史 KV 分工两个角度处理这类问题。

### 3 PP 把不同模型层放到不同 stage

`--pp-size` 控制 Pipeline Parallel。PP 按模型层划分 stage，每个 stage 只持有并执行自己的那部分层，结果依次传给下一个 stage。一个 stage 内部仍然可以使用 TP。

例如，32 层模型采用 `PP2、tp_size=4` 时，可以由四张 GPU 承担前 16 层，另外四张 GPU 承担后 16 层。这时，一份模型由八张卡共同承载，具体的层数分配也可以调整。按层分工降低了每个 stage 需要承载的权重规模，也允许在扩大部署规模时保留较小的 stage 内 TP。跨节点部署时，可以考虑在节点内使用 TP，再通过 PP 连接不同节点。

同一批数据必须依次经过各 stage，因而存在 stage 间的传输和等待。要让流水线持续工作，需要让不同 microbatch 或输入 chunk 同时处于不同 stage。能够同时安排的 microbatch 或 chunk 太少，或者各 stage 的执行时间不均衡时，就会出现 pipeline bubble。

如果需要把模型层分布到更多 GPU 或节点上，并且有足够的 microbatch 或输入 chunk 可以填入流水线，就可以考虑使用 PP。对于低并发、短输入、主要追求单请求最低延迟的服务，如果模型已经能在较小执行组内运行，增加 stage 就需要权衡模型分摊的收益与流水线利用不足带来的等待。

PP 的实际效果还同时受到 microbatch、Prefill chunk 和层分配的影响。`--pp-max-micro-batch-size` 控制一个 microbatch 的请求数量，`--pp-async-batch-depth` 调整可调度的流水线深度；它们不改变模型层由哪个 stage 持有。

### 4 DP 复制完整模型执行组

`--dp-size` 控制完整模型执行组的副本数。每个副本处理分配给自己的请求；一个副本既可以放在单卡，也可以通过 TP 或 PP 分布到多张卡上。例如 `DP2、tp_size=4` 使用八张 GPU，其中四张卡组成一个 TP4 副本，另外四张组成第二个 TP4 副本。

当单副本能够承载模型，但请求量超过其处理能力时，增加副本可以扩展服务容量、缓解排队。独立副本之间不需要为同一请求的逐层计算协作，一个请求仍然在自己的副本内执行。因此，DP 增加的是独立处理请求的资源，无法把同一个请求分给多个副本共同加速。如果单个副本仍然装不下模型，需要先确定副本内部的 TP、PP 等配置。

每增加一个副本，都需要再保存完整的一份模型权重，并维护相应的运行状态。流量分配也会影响这些资源能否被充分利用：请求分配不均时，一部分副本可能拥堵，另一部分却空闲。SGLang 内置 DP 可以按轮转、请求数或 token 数等方式分配请求。

这一版本的内置 DP 在 `--dp-size > 1` 时只支持单节点部署，而且不能同时设置 `--attn-dp-size > 1`。这些限制针对的是内置启动方式。独立启动多个实例、再通过 SGLang Model Gateway 分配请求，是另一种多副本部署方式。

### 5 Attention-DP 让 Attention 按请求分工

`--attn-dp-size` 主要解决 Attention 与 FFN/MoE 使用同一套并行分工时的资源浪费。其中最典型的问题是：模型需要多张 GPU 共同承载，但在 absorbed MLA 的普通 TP 布局下，同一请求的 latent KV 会在这些 GPU 上重复保存，限制了能够同时容纳的请求和上下文总量。

MLA 的多个 Q heads 共享压缩后的 latent KV。TP 可以让不同 GPU 负责不同的 heads，但这些 heads 仍然需要访问相同的历史。因此，计算被分摊了，同一请求的 latent KV 却不一定随之分摊。

假设同时有八个等长、互不共享前缀的请求 A～H，每个请求的一份 latent KV 占 1 GB。在八卡 TP 下，八张卡共同处理这些请求，每张卡都要保存 A～H 的 latent KV。逻辑上只有 8 GB 不同的 KV 数据，但八张卡一共保存了 64 GB。

Attention-DP 改变的是请求归属。设为 `tp_size=8、Attention-DP8` 时，Attention 分成八个单卡请求组：GPU0 处理 A，GPU1 处理 B，依此类推。每张卡只需维护自己请求的 KV，八张卡合计保存 8 GB。若采用 `Attention-DP2`，则是两个请求组，每组四张卡以 Attention TP4 协作；一组负责 A～D，另一组负责 E～H，同一请求的 KV 仍会在它所属组的四张卡上复制。

在 Attention-CP 和 DCP 都为 1、请求均匀分配的前提下，上述例子可以整理为：

| 八卡配置 | 每组 Attention TP | 每张卡负责的请求数 | 每张卡的 latent KV 数据量 | 八卡合计的 latent KV 数据量 |
| --- | --- | --- | --- | --- |
| tp_size=8、Attention-DP1 | 8 | 8 | 8 GB | 64 GB |
| tp_size=8、Attention-DP2 | 4 | 4 | 4 GB | 32 GB |
| tp_size=8、Attention-DP8 | 1 | 1 | 1 GB | 8 GB |

这里的 1 GB 是便于比较的假设值。表格只计算这些请求的 latent KV 数据量，不包含权重、工作区和其他状态，也不代表服务进程的总显存。对于预分配 KV pool 的服务，减少重复保存后，同样大小的 KV pool 可以容纳更多有效 token，但监控中看到的显存占用不一定会下降。

减少重复保存后，原来用于存放副本的 KV 空间就可以留给更多请求，或者为现有请求留出更多 KV 存储空间。如果此前服务受 KV 容量限制，这就给扩大活跃请求规模、提高总体 Decode 吞吐创造了条件。吞吐是否提升、提升多少，仍取决于计算和通信是否成为新的瓶颈，不能从表中的存储比例直接推导。

之所以只对 Attention 做 DP，是因为模型其他部分仍可能需要多卡共同承载。直接使用整模型 DP，需要为每个副本保存完整的模型权重；对于大型 MoE，routed experts 的权重可能根本无法放进单卡。Attention-DP 则允许 Attention 按请求分工，同时让后续 FFN 继续使用 TP，或让 routed experts 通过 EP 分布在这八张卡上。例如 `tp_size=8、Attention-DP8、EP8` 中，GPU0 在 Attention 阶段处理请求 A，而 A 的某个 token 在 MoE 阶段仍可交给 GPU3 上的 expert 计算。它没有复制八份完整模型，也不要求必须开启 EP。

这种布局也有自己的成本。请求组之间需要相应复制 Attention 权重，Attention 与 FFN/MoE 之间还要跨组传递数据。在固定总 GPU 数下，增加 Attention-DP 会减少每组的 Attention TP 宽度，并改变每组的 batch 大小。因此，如果原本并不缺 KV 容量，或者 Attention、FFN/MoE 的计算与通信已经占据主要时间，收益就需要重新评估。GQA 等模型若已经有效分摊 KV heads，也不能直接套用上面的 MLA 存储比例。

Attention-DP 对多请求服务尤其有意义，但它没有把请求 A 自己的历史 KV 切成八份。采用 Attention-DP8 后，A 的完整 KV 仍由处理 A 的那张卡保存；只有一个请求时，也不会出现八个请求组共同加速它的效果。如果问题是单个请求的历史 KV 太大，就需要考察 DCP，并确认对应模型是否支持按历史 token 分摊 KV。

### 6 EP 把 routed experts 分给不同 GPU

`--ep-size` 用来设置 Expert Parallel 的并行度。EP 把 routed experts 划分成不同的子集，交给不同 GPU 组负责；每个 expert 的计算仍可以由多张 GPU 通过 MoE TP 共同完成。router 为 token 选好 experts 后，token 就会交给负责这些 experts 的 GPU 进行计算。

以 256 个 routed experts 为例，使用一个八卡执行组（`tp_size=8`），组内采用 EP8、MoE-DP1，expert 内部实际 TP 为 1。忽略冗余 expert 和特殊布局，每张卡持有 32 个完整的 routed experts。这样，大量 routed experts 的权重和计算就可以分布到不同 GPU 上，也可以与 Attention-DP 的请求分工配合。

token 的路由结果决定它需要去哪里计算。在采用跨卡路由的后端上，这会带来通信开销；各 expert 收到的 token 数也可能不同，形成负载不均。SGLang 提供 EPLB、冗余 experts 等机制来处理或观察这种分布。如果跨卡路由成本已经很高，或少数 experts 承担了过多工作，仅靠增大 EP 不足以解决问题，还需要同时看互联条件和专家负载。

在相同 GPU 数量下，TP 将每个 expert 的权重分给多张卡，EP 则将不同 experts 分给不同卡。对于大小相同、均匀分配且没有额外副本的 experts，两种方式每卡承担的 expert 权重总量可以相同，主要区别在于计算和通信如何组织。

EP 配置是面向 routed experts 的。Dense 模型没有对应的 expert 分布问题，普通 Dense MLP 和 shared experts 的并行方式也需要分别配置。EP 的有效值还受后端约束：当前 DeepEP 等多个 A2A 后端会将 EP 解析为外层 `tp_size` 的大小，输入 `tp_size=8、EP2` 不一定按 EP2 运行。

### 7 MoE-DP 复制 routed experts 集合

`--moe-dp-size` 控制执行组内 routed experts 集合的副本数。每份集合内部仍可使用 EP 或 MoE TP。如果模型支持相应的 context 分工方式，不同 MoE 组就可以分别处理各自的 token，让每份 experts 集合在更小的 GPU 组内完成计算。

这一版本的 MoE-DP 与 CP 布局紧密相关。`MoE-DP > 1` 时要求 `PP=1`、`MoE-DP=Attention-CP`；若 `EP>1`，还要求 `EP × MoE-DP = tp_size`。具体模型的实现还有额外的兼容性要求，满足这些等式也不代表所有模型都能使用。

在这些条件下增加 MoE-DP，相当于用额外的 routed experts 权重副本换取更小的 MoE 协作组。同一个执行组内保存了更多份 experts 集合，每份集合能够使用的 GPU 数也随之减少，最终效果取决于权重容量、token 分工和通信开销。

因此，MoE-DP 通常需要和具体 CP 布局一起考虑。它不会增加完整模型副本，也不会自动创建更多 Attention 请求组。如果只是希望处理更多独立请求，可以先考察 DP 方案。

### 8 Dense MLP 与 shared experts 的独立 TP 配置

MoE 模型中的普通 Dense MLP、routed experts 和 shared experts 承担的工作不同，它们不必采用完全相同的并行宽度。

### moe-dense-tp-size 调整普通 Dense MLP

`--moe-dense-tp-size` 是用来调整 MoE 模型中普通 Dense MLP 的 TP 大小的。以支持该配置的 DeepSeek 路径为例，设为 1 时，每卡保留完整的普通 MLP 权重，并可在自己的 token 上完成这部分计算；使用 TP 时，则由多卡分摊该 MLP。

当整体部署需要较大 TP，但普通 MLP 在这个宽度下被分得过细时，可以单独让这部分使用 TP1。这样能够减少它对 TP 协作的依赖，但每卡需要保存更多 MLP 权重。在显存已经紧张的部署中，这种复制未必合适。

参数定义中的说明特别提到，大 TP 可能使部分 GEMM 无法满足最小维度要求，这也是该配置处理的问题之一。它并不控制 routed experts 内部的 TP，而且当前只接受未设置、1 或 `tp_size` 的值；模型本身也需要支持这项参数。

### shared-experts-tp-size 调整 shared experts

shared experts 是模型中的一条独立分支，不通过 routed experts 的 top-k 选择来决定是否参与计算。`--shared-experts-tp-size` 用来指定由多少张 GPU 通过 TP 共同承担这个分支的计算，使它可以采用与 routed experts 不同的权重布局。

在支持的 Kimi-K3 路径中，TP1 对应复制 shared experts 权重；使用更大的 shared experts TP，可以由组内多卡分摊权重，同时也需要组内数据交换和协作。当 shared experts 的显存占用或执行开销需要单独调整时，就可以改变这一分支的 TP 大小，而无需让它跟随 routed experts 的 EP 布局。

模型拥有 shared experts，并不代表它就支持这项显式参数。这一版本只有 Kimi-K3 在使用指定的 EP A2A 后端时，才支持这项参数。参数值必须是 Attention TP 的正约数，也要满足模型自身的维度要求。例如 Attention TP4 时，可以选择 1、2 或 4，不能直接设置为 8。

### 9 Prefill CP 沿输入 token 分摊计算

TP 已经可以让多张 GPU 共同处理长输入。在普通 Attention TP 布局中，各卡负责不同的 heads，共同分摊 Prefill 计算。不过，继续增加 TP，并不保证 Prefill 执行时间能按比例缩短。

TP 对 KV 存储的分摊受到 KV heads 数量的限制。GQA/MQA 的 KV heads 较少，当 Attention TP 达到 KV heads 数量时，每卡已经只保存一个 KV head；继续增大 TP，就需要在多张卡上复制同一个 KV head，但 Q heads 仍按 TP 分配给不同 GPU。因此，依靠 TP 减少每卡 KV 存储的收益会较早达到上限。对于 absorbed MLA，多个 Q heads 共享同一份 latent KV，普通 Attention TP 下各卡重复保存这份数据，这部分 KV 占用也不会随 TP 增大而按比例下降。

以 Qwen3.8-2.4T-A95B 为例，它是混合 Attention 模型，其中 Full Attention 层只有 4 个 KV heads。对这些层使用普通 Attention TP4 时，每张卡各自保存一个 KV head；增加到 Attention TP8 后，由于没有更多 KV heads 可分，同一个 KV head 就需要在两张卡上复制。因此，继续增加 TP 并没有减少每卡为相同输入保存的这部分 KV 数据量。

DeepSeek-V4.1-Flash 的官方配置则只有 1 个 KV head。在普通 Attention TP 布局下，各卡仍使用这一共享 KV head，增加 TP 也无法让 KV 数据沿 heads 维度继续细分。它还采用了 KV 压缩、滑动窗口和跨层 KV 共享，这些机制影响实际的缓存占用，但不会增加可供 TP 划分的 KV heads 数量。

在模型和 batch 不变时，增大 TP 会把参与分片的 GEMM 进一步切细，较小的计算任务未必能保持原有效率，而跨卡 collective 仍需执行。每卡计算时间缩短后，通信和同步的成本不一定同比例下降，在总耗时中的占比反而可能上升。因此，更多 GPU 和更少的每卡计算量，并不保证更低的 Prefill 延迟。

Context Parallelism 把分工扩展到上下文的 token 维度。Prefill 阶段有大量 query，可以让不同 GPU 组分别处理一部分 query，并在组内使用较小的 Attention TP；这就是 Prefill CP，也常简称 PCP。在总 GPU 数不变时，每卡会处理更多 heads、更少 query，执行效率是否改善取决于模型和后端。对 SGLang 支持的 DSA 路径，原本在纯 TP 下重复执行的 indexer 工作也可以随 query 分摊，从而减少这部分重复计算。

在 SGLang 中，`--enable-prefill-cp` 启用这种计算方式，`--attn-cp-size` 指定 context 分区数量。Attention-DP 将不同请求交给不同组，而 Prefill CP 可以把同一个长请求的 query 分给多个组。

下面用一个独立算例比较 TP 与 CP 的分工。假设模型有 32 个 Q heads，本次需要处理 128K 个新输入 token，并且模型与后端支持相应的长输入和 TP/CP 组合，八张 GPU 可以采用下面两种分工：

| 八卡配置 | 每张卡负责的 Q heads 数 | 每张卡负责的 query token 数 |
| --- | --- | --- |
| 纯 Attention TP8，CP1 | 4 | 128K |
| CP4，每个分区内 Attention TP2 | 16 | 32K |

第二种布局对应 `tp_size=8、Attention-CP4、Attention-DP1`，仍然只使用八张卡。每卡的 query 减少了，heads 则增加了，因此不能仅凭 token 数减少四倍就推导出四倍加速；同样，每卡只有 4 个 heads 也不代表第一种布局一定低效。

这些 query 分区仍然属于同一个请求。各组通过交换所需 K/V，为自己的 query 完成 Attention；每个 query 能访问的上下文仍由原来的 causal 或 sparse Attention 规则决定，并不会缩小到本组负责的 token。因此，按 query 分摊计算不等于把输入拆成几段互不相关的文本，也不等于每卡只需保存相同比例的 KV。当前默认 CP KV 布局保留复制存储，KV 容量是否增加还要看是否另有存储分片。

Prefill CP 主要值得在长输入处理成为瓶颈时考察，目标是缩短 Prefill 执行时间和 TTFT。它用跨分区的 KV 交换、与 FFN/MoE 的协作开销，换取重复计算减少或执行效率改善；缩小组内 Attention TP 也可能增加每卡相关权重的占用。CP 同样不是越大越好：分区越多，每卡分到的 query 越少；尤其在输入短、batch 小时，可分摊的计算可能不足以抵消新增通信。单请求长输入则仍有大量 query 可分，不应仅凭 batch 小就排除 CP。

启用时还需要设置有效的 CP 并行度，并显式指定 `--cp-strategy`。Zigzag、Interleave 的支持范围依赖模型与后端；例如，当前 DSA 路径不能直接照搬上面的混合 Attention TP/CP 算例。部分 batch 还可能因输入长度等条件不进入 CP 路径，评估性能时需要确认实际采用的分工。

### 10 DCP 分摊同一请求的历史 KV

DCP（Decode Context Parallel）是一种面向 Decode 的 Context Parallel 策略。Prefill 和 Decode 的计算特征不同，因此适合的分工方式也不同。 在 Decode 中，每个请求每步通常只增加一个 query，却可能需要访问很长的历史上下文。对单个请求继续沿 query token 划分，已经没有 Prefill 阶段那样的空间；此时可以让多张 GPU 分别处理这个 query 所需的不同 KV 分片。`--dcp-size` 控制的 Decode Context Parallel（DCP）就是这种分工。

已有 TP 仍然可能需要 DCP，是因为分摊 heads 不一定能分摊 KV 存储。以 absorbed MLA 为例，不同 Q heads 共享同一份 latent KV，纯 Attention TP 下各卡会重复保存、读取同一请求的历史 KV。DCP 沿历史 token 位置分片，让各卡只保留其中一部分，从而减少这类重复。

例如，在上述 MLA 布局下，一个请求有 128K 历史 token，使用 `tp_size=8、Attention-DP1` 时，每卡原本保存完整的 128K latent KV；加入 DCP8 后，同样八张卡按 token 位置轮转分担，每卡保存约 16K token 的 KV。腾出的 KV 空间可以用于更长的上下文或更大的 Decode batch，降低每卡 KV 读取量也可能改善 TPOT 和吞吐。

计算时，组内各卡获得所需的 Q，分别对本地 KV 分片执行 Attention，再通过通信将局部结果合并成该 query 的最终 Attention 输出。因此，DCP 减少 KV 存储和读取的同时，也增加了每步生成时的跨卡协作。它更适合长上下文下 KV 容量或 HBM 读取带宽成为瓶颈的负载。上下文较短时，能够节省的 KV 读取较少；batch 较小、每步工作较少时，也更需要关注通信和启动开销的占比。DCP 的大小应由这些收益与成本共同决定，不能只按可用 GPU 数设置。

DCP 的收益与模型的 Attention 架构及 KV heads 布局有关。上述存储比例适用于 absorbed MLA 的特定布局，不能直接推广到 GQA/MHA；还需要确认对应后端是否支持 DCP。

混合模型中的其他状态也不一定由 DCP 分摊；例如 Kimi-K3 的 DCP 作用于 MLA 层，不改变 KDA 的请求状态容量。

与 Attention-DP 组合时，DCP 组必须完全位于一个 Attention TP 组内。例如 `tp_size=8、Attention-DP2、DCP4`，每个 Attention 请求组由四张卡协作，DCP4 可以放在组内；若改成 `Attention-DP8`，每组只剩一张卡，就无法再划分出 DCP4。

### 11 根据瓶颈选择配置

选型可以先从实际受限的资源出发，再检查模型支持范围和组合限制。

| 当前问题 | 优先考察的配置 | 需要同时确认的代价或边界 |
| --- | --- | --- |
| 模型权重无法在现有执行组中容纳 | TP、PP；MoE 还可考察 EP | 层内通信、stage 等待，以及具体权重布局 |
| 单副本能够运行，但独立请求持续排队 | DP | 额外权重副本与请求分配；固定 GPU 数下还需比较副本内 TP |
| MLA 服务中 Attention KV 重复限制并发 | Attention-DP | Attention 权重布局、FFN/MoE 数据交换和每组请求量 |
| 长输入导致 Prefill 成为瓶颈 | Prefill CP | 后端支持、跨分区通信、KV 存储是否另有分片 |
| 长上下文 Decode 的 KV 容量或读取成为瓶颈 | DCP | 每步通信、Attention 架构和其他状态容量 |
| MoE 整体并行很大，但普通 MLP 不适合该宽度 | --moe-dense-tp-size | 更多本地 MLP 权重和模型支持范围 |
| shared experts 需要独立权衡显存与通信 | --shared-experts-tp-size | Kimi-K3 支持范围及 Attention TP 约束 |
| CP 布局下需要让 MoE 分组分别处理 token | --moe-dp-size | experts 副本成本及 CP、EP、PP 的组合限制 |

评估结果时，要分别看容量、延迟和吞吐。能装下更长上下文，不代表每个 token 都生成得更快；能同时处理更多请求，也不代表单请求延迟会下降。

比较配置应固定模型、精度、总 GPU 数、互联条件以及请求长度和并发分布。重点观察 TTFT、ITL 或 TPOT、延迟分位数、吞吐与 KV 容量；MoE 还需要关注专家负载分布。
