## GPU 集群网络专题：从百卡到万卡的演进与最佳实践

> 面向”运维工程师 → AI 平台运维”的深度专题：覆盖 RDMA 技术选型、**交换机拓扑结构**、从百卡到万卡的拓扑演进、**网络隔离与分离架构**、K8s 网络插件、拓扑感知调度与可观测性。所有架构均引用公开真实案例（NVIDIA DGX SuperPOD、GB200 NVL72、Azure NDv5、阿里灵骏 HPN），数据可溯源。

---

### 0. 总览：一条主线，四个阶段

GPU 集群网络的演进，本质是回答一个问题：**“跨节点通信每步要花多少时间、能不能随规模线性扩展？”** 大模型训练（LLM）的每一步都依赖全局梯度同步（AllReduce），通信开销随 GPU 数增长而计算开销随单卡摊薄——网络成为万卡集群的第一瓶颈。[^1][^2]

```text
机内 NVLink（scale-up）              ← 单节点 8×GPU 全互连
    ↓ 跨节点 RDMA（scale-out）       ← 百卡~千卡：fat-tree / rail-optimized
    ↓ 超节点（scale-up 上探）        ← 千卡~万卡：NVL72 机架级 NVLink 域
    ↓ 两层组网（超节点 + 高速 DCN）  ← 万卡+：Scale-Up 域内消化 + Scale-Out 跨域
```

| 阶段 | 规模 | 典型拓扑 | 每 GPU 出口带宽 | 代表架构 |
| --- | --- | --- | --- | --- |
| 单机 | 8 GPU | NVSwitch full-mesh（NVLink 600~900 GB/s） | — | 8×A100/H100 机 |
| 百卡 | 64~256 GPU | 2 层 fat-tree / 1 层 rail | 100~400 Gbps | 小集群、DGX POD |
| 千卡 | 1K~4K GPU | rail-optimized 3 层 fat-tree | 400 Gbps | DGX SuperPOD、Azure NDv5 |
| 万卡 | 8K~64K GPU | 超节点 Scale-Up + 高速 DCN | 800 Gbps + NVLink 域 | GB200 NVL576、阿里灵骏 |

**核心结论先行**：跨机通信带宽比机内 NVLink 慢 **10~24 倍**（H100 机内 900 GB/s vs 跨机 50 GB/s@400G）——这决定了两个工程铁律：① 并行切分（TP/PP/DP）要尽量把高频通信留在 NVLink 域内；② 跨机网络必须用 RDMA + 无损网络把 400~800G 压满。[^2][^3]

### 1. 机内互联：NVLink / NVSwitch / PCIe（一切的地基）

### 1.1 单节点拓扑（8×GPU 主流的”2-2-4-6-8-8”）

业界部署最广的 8 卡 GPU 主机模板（A100 时代定型，H100 沿用）：[^3]

```text
2  CPU（双路 → 2 个 NUMA 节点）
2  存储网卡（直连 CPU，管理面/存储面）
4  PCIe Switch 芯片（CPU↔GPU/NIC 交换层）
6~4  NVSwitch 芯片（GPU 间 full-mesh）
8  GPU
8  GPU 专属网卡（每 GPU 独占一张，计算网络）
```

关键设计理念：

- **GPU 专属网卡直连（GPU→PCIe Switch→NIC）**绕开 CPU，这是 GPUDirect RDMA 的物理前提；
- **存储网卡直连 CPU**，走非性能敏感路径（读数据/写 checkpoint/管理）——即”两张网”分离：

### 1.2 NVLink 代数与带宽（真实数据）

| 代际 | 每 link 带宽 | 典型 GPU | link 数 | GPU 总带宽（双向） |
| --- | --- | --- | --- | --- |
| NVLink 1 | 40 GB/s | P100 | — | ~80 GB/s |
| NVLink 2 | 50 GB/s | V100 | 6 | 300 GB/s |
| NVLink 3 | 50 GB/s | A100 | 12 | 600 GB/s |
| NVLink 3（阉割） | 50 GB/s | A800 | 8 | 400 GB/s |
| NVLink 4 | 50 GB/s | H100 | 18 | 900 GB/s |
| NVLink 4（阉割） | 50 GB/s | H800 | 8 | 400 GB/s |
| NVLink 5 | 100 GB/s | B200 | 18 | 1,800 GB/s = 1.8 TB/s |

*每代递增来自两个维度：link 数量（8→12→18）与每 link 带宽（50→100 GB/s）。NVLink 4→5 时 link 数不变（仍 18），是**每 link 翻倍到 100 GB/s** 带来总带宽 900→1,800 GB/s；NVLink 5 的 1.8 TB/s 是 PCIe Gen5 x16（~128 GB/s）的约 14 倍。数据来源：NVIDIA 官方规格。[^5]*

### 1.3 PCIe 版本与网卡带宽的匹配陷阱

| PCIe | 双向带宽（x16） | 能否喂饱网卡 |
| --- | --- | --- |
| Gen4 | 64 GB/s（单向 32 GB/s） | 撑不满 400G（50 GB/s>32 GB/s） |
| Gen5 | 128 GB/s（单向 64 GB/s） | 可支撑 400G（≈50 GB/s） |

**运维含义**：A100 时代标配 100G（CX6）；H100/H800 标配 **400G（CX7）**是因为 PCIe Gen5 才能让 400G 网卡跑满。给 400G 网卡配 Gen4 平台是常见的”买了带宽用不上”坑。[^2][^3]

### 2. RDMA 技术选型：IB / RoCEv2 / iWARP

RDMA（远程直接内存访问）让数据绕过 CPU 内核直接在两主机内存间搬运。三种实现对比：[^2][^3][^4]

| 维度 | InfiniBand（IB） | RoCEv2 | iWARP |
| --- | --- | --- | --- |
| 协议 | 专有（IBTA） | 以太网+RDMA 语义 | TCP 之上 |
| 性能 | 基准（同带宽高 20%+） | 接近 IB | 略逊 |
| 价格 | 约贵一倍 | 相对便宜 | — |
| 无损保证 | 硬件原生 | 需 PFC+ECN 软件配置 | TCP 重传 |
| 生态/运维 | 专有、运维复杂、人才少 | 以太网生态、门槛低 | 一般 |
| 典型配置 | CX7 NDR 400G、CX8 800G | 200~400G | 少用 |
| 适用 | 超大规模训练、延迟敏感 | 公有云、性价比集群 | 兼容场景 |

**业界主流判断**：

- **自建 IDC 追求极致训练性能**：首选 InfiniBand（DGX SuperPOD、Meta、OpenAI 早期集群均如此）；
- **公有云 / 性价比**：基本清一色 **RoCEv2**（Azure 的 RoCE 后端、阿里灵骏自研 51.2T 以太网均基于 RoCE 演进）；[^4][^6]
- **趋势**：InfiniBand 市场份额小、运维人才稀缺、厂商锁定；RoCEv2 成为大规模 RDMA 应用的主流方向；NVIDIA 近年力推 Spectrum-X 以太网（无损 RoCE + DPU）与 IB 并行。[^4][^7]

### 2.1 无损网络：RoCE 为什么需要 PFC+ECN

RoCE 跑在以太网上，而以太网默认会丢包（拥塞时丢并靠上层重传）——RDMA 一旦丢包性能骤降（重传风暴）。工程解法是”无损以太网”：[^8][^9]

- **PFC（Priority Flow Control，802.1Qbb）**：按优先级用 XOFF/XON 暂停帧防止缓冲溢出丢包；代价是可能引发 **PFC 风暴**（head-of-line blocking）——一个慢速率端口拖住整条链路；
- **ECN（显式拥塞通知）**：交换机在队列拥塞时给数据包打 CE 标记，接收端反馈 CNP 让发送端降速——比 PFC 粗暴暂停更精细；
- **DCQCN**（微软 Azure，SIGCOMM 2016）：结合 ECN 标记 + 接收端反馈 + 发送端降速/升速，是大规模 RoCE 的事实标准拥塞控制。[^9]

**运维坑**：光配置 PFC 不配 ECN，遇拥塞就产生 PFC 暂停帧风暴，NCCL 吞吐骤降、训练变慢但”链路 up”——排查要看 `mlx5_port_pfc_rx_pause_total` 等计数器。[^8]

### 2.2 InfiniBand 的关键特性（不止是带宽）

NVIDIA 的 Quantum 系列交换机提供软件定义网络（UFM/SM）、**自适应路由（AR）**、**网络内计算（SHARP，把 AllReduce 卸载到交换机）**、动态网络愈合（SHIELD）。这些是多租户高利用率的差异化能力。[^1][^10]

### 3. 交换机拓扑结构：Leaf / Spine / Core 与连接原则

交换机拓扑决定了”流量从 GPU A 到 GPU B 要经过几次转发、有没有瓶颈”。GPU 训练网络的核心拓扑是 **fat-tree（胖树）** 变体，按规模分两到三层。

### 3.1 三层结构（Leaf → Spine → Core）

标准 fat-tree 的**连接规则**是”每一层交换机全连接到上一层”（full-mesh）、且同一层内**两两不相连**——这是它能”无收敛 + ECMP 多路径”的数学基础。下图是最清晰的表达（每 Leaf 连全部 4 台 Spine、每 Spine 连全部 2 台 Core）：

![](https://picx.zhimg.com/v2-3115ccccd9cb5222cc7ca8b4c8286cdb_r.jpg)

*图 3-1：三层 fat-tree 全连接矩阵（Leaf↔Spine 全互连、Spine↔Core 全互连；同一层内不相连）*

对应的”同层次数”结构速记（真实连接关系，虚线只表示”还有更多”，不是省略连接）：

```text
Core 层:   C1 ───── C2          （Core↔Core 也可互联，供跨域）
           │  \   /  │
Spine 层:  S1 ─┴─ S2 ┴─ S3      （每个 Spine 上行连所有 Core）
           ││\   / ││\  /
Leaf 层:   L1  L2  L3  L4       （每个 Leaf 上行连所有 Spine）
           │   │   │   │
节点层:    └┬──┴───┴───┬┘
          （每节点 NIC 分散接入多个 Leaf = rail 对齐）
```

- **Leaf（叶/接入层）**：GPU 节点接入层，端口密度决定每层能挂多少节点。例如阿里 HPN 的 Leaf 为 128×400G 端口的 51.2T 交换芯片，对联 8 台 8×400G 节点（64 下联 + 64 上联）；[^18]
- **Spine（脊/汇聚层）**：聚合多个 Leaf 的流量，是全网东西向流量的必经之路。多个 Spine 构成平行平面，转发用 ECMP（等价多路径）哈希；
- **Core（核心层）**：只有集群大到超出单 Spine 域（典型 >4K GPU）才引入，连接多个 Spine 平面。DGX SuperPOD 在 >4 SU（1024 GPU）时才上 Core 层（参考架构 16/32/56 SU 表格里的 Core 列）。[^1][^12]

### 3.2 关键参数：端口数、收敛比、跳数

| 参数 | 值/原则 | 说明 |
| --- | --- | --- |
| 单 Leaf 端口密度 | 51.2T 芯片=64×800G 或 128×400G | 决定单层规模上限 |
| 收敛比（oversubscription） | 必须 1:1（无收敛） | 训练是全到全流量，任何收敛=跨机瓶颈 |
| 同叶跳数 | 1 跳 | 同 Leaf 下节点通信 |
| 跨叶（同 Spine） | 2 跳 | 最常见跨节点模式（Leaf→Spine→Leaf） |
| 跨 Core | 3 跳+ | 罕见路径，仅超大集群（Leaf→Spine→Core→Spine→Leaf） |
| 上联数 | 每 GPU 1×400G（千卡）；超节点 4×800G/托盘 | 与网卡数匹配 |

**连接数数学（规划资产时直接套用）**：设 L=Leaf 数、S=Spine 数、C=Core 数。

- Leaf↔Spine 连接数 = **L×S**（每 Leaf 的 S 个上联分别接每台 Spine 的下联口）；
- Spine↔Core 连接数 = **S×C**；
- 若每 Leaf 有 d 个下联口（接 GPU/节点）、u 个上联口（接 Spine），**1:1 无收敛要求 u=d**，即每 Leaf 的上下联口数量必须相等——这就是上表中”128×400G（64 下 + 64 上）”的由来；
- 常见工程示例（DGX SuperPOD 4 SU）：32 Leaf + 16 Spine，则 Leaf-Spine 连线 = 32×16=512 条，与官方线缆表（Spine-Leaf Cable Count 1024）对应（双向上联计双倍）。[^1][^12]

### 3.3 端口拆分（port splitting）——交换机选型要点

现代 51.2T 交换芯片（Spectrum-4 / Quantum-2 / 阿里自研）支持**端口拆分**：一个 800G 物理端口可拆为 2×400G 或 4×100G；一个 400G 可拆 2×200G 或 4×100G。例如 Quantum QM9790 支持 64×400G → 128×200G 或 256×100G。[^19]

**运维含义**：拆分配置影响流量模型——同 rail 的 GPU 必须落在**同一组端口/同一 Leaf**，拆分选择要先于布线规划，改起来代价高。

### 3.4 布线约束（物理层决定拓扑能怎么画）

- **光纤 vs 铜缆**：机架内 NVLink 用铜缆（短距离低延迟），跨机架 RDMA 用光模块；[^16]
- **距离**：DGX SuperPOD 节点→Leaf ≤50m（优化 ≤30m），Leaf↔Spine 单模 ≤500m——拓扑的”两层”受机房物理布线与长度反推，不是随便画的；[^1]
- **multi-rail（多轨）**：同一节点多个 NIC 分别接入不同 Leaf/Spine，让流量分担在多个平面——既提高带宽又降低单交换机故障影响（对应阿里”双上联/双平面”）。[^6][^18]

### 4. 百卡 ~ 千卡：fat-tree 与 rail-optimized

### 4.1 什么是 rail-optimized（轨道优化）

普通 fat-tree 里任意两点间经过的层数相同但**同”轨道”（rail）的通信只需一跳**。rail-optimized 把**每台服务器同一编号的网卡**接到**同一组 leaf 交换机**（一个 rail）：

```text
DGX H100（8×400G NIC）:
  NIC0..NIC7 → 8 个不同 leaf（rail-0..rail-7）
  rail-0 上的设备之间：1 跳（leaf 内）
  跨 rail：2 跳（leaf→spine→leaf）
```

**意义**：NCCL 的 AllReduce 主要在同 rail 的 GPU 间做 ring——**同 rail 内 1 跳**避免跨 spine 的哈希不均；这是千卡以上集群性能的关键。[^1][^11]

### 4.2 DGX SuperPOD（H100）：百卡~千卡的参考实现

NVIDIA 官方参考架构，以 **SU（Scalable Unit，32 节点/256 GPU）** 为构建块：[^1][^12]

| SU 数 | 节点数 | GPU 数 | Leaf | Spine | Core | 备注 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 31 | 248 | 8 | 4 | — | 1 台让位给 UFM |
| 2 | 63 | 504 | 16 | 8 | — |  |
| 4 | 127 | 1,016 | 32 | 16 | — | 官方验证规模 |
| 8 | 256 | 2,048 | 64 | 32 | — |  |
| 16 | 512 | 4,096 | 128 | 128 | 64 | 超 4 SU 引入 Core 层 |
| 32 | 1,024 | 8,192 | 256 | 256 | 128 | 三层 |
| 56 | 2,048 | 16,384 | 512 | 512 | 256 | 万卡级 |

参数要点：[^1][^12]

- 每 DGX H100 8×400G **NDR InfiniBand（ConnectX-7）**，单节点双向 3.2 Tbps；
- **四张网**：计算网（IB）／存储网（IB 独立）／带内管理网（以太网）／带外管理网（BMC，1G）；
- 存储网对每节点 ≥40 GB/s，与计算网物理隔离——训练流量与 checkpoint/数据加载互不干扰；
- **光缆距离约束**：节点→leaf ≤50m（优 30m）、leaf↔spine 单模 ≤500m——机房布局受此反推；
- 每节点多张大流（400G × 8），**哈希极化**是隐忧——缓解靠 rail 对齐 + 自适应路由（AR）。[^11]

### 4.3 Azure ND H100 v5：云上的千卡实现（含重要排障知识点）

Azure 的 `Standard_ND96isr_H100_v5`（8×H100，每 GPU 独立 400G Quantum-2 CX7，单 VM 3.2 Tbps）：[^13]

- 内部 8 GPU 通过 NVSwitch + NVLink 4.0（900 GB/s）互连；跨 VM 走 IB 并自动配置，支持 GPUDirect RDMA；
- **云天拓扑文件 `ndv5-topo.xml`**（`/opt/microsoft/`）：虚拟化隐藏了真实 PCIe 层级，NCCL 无法自动发现”GPU0 挨着 NIC0”——Azure 用 synthetic 拓扑提示恢复该信息，使 NCCL 走同 NUMA 的 GPU↔NIC（GPUDirect，~2µs）而不是跨 UPI（~3-5µs，带宽减半，AllReduce 掉 30-40%）。**没有它，训练吞吐肉眼可见地掉**[^14]
- 运维含义：**NCCL 拓扑文件是跨节点 RDMA 训练正确性的关键配置**（`NCCL_TOPO_FILE`/`/etc/nccl.conf`）；实测有拓扑 ~370 Gb/s、无拓扑 ~250 Gb/s per 400G link。[^14]

### 5. 千卡 ~ 万卡：超节点（Scale-Up 上探）+ 两级组网

从 2024 起，业界共识是**不能让所有通信都走跨机 RDMA**——把机架内 GPU 用 NVLink 做成一个”超节点”（Scale-Up 域），超大模型的大部分通信（TP/EP 等高频）留在域内，跨域才走 RDMA。这是万卡可扩展的关键转变。[^1][^15]

### 5.1 NVIDIA GB200 NVL72（超节点基准架构，公开数据）

| 项 | 值 |
| --- | --- |
| 组成 | 36 Grace CPU + 72 Blackwell GPU，单机架液冷 |
| Scale-Up 互联 | NVLink 5，GPU↔GPU 1.8 TB/s，NVLink 域共 130 TB/s（72 GPU 全互连） |
| 拓扑 | 18 计算托盘（每托盘 2×GB200=4 GPU）+ 9 NVSwitch 托盘 |
| 机内连 | >5000 根高速铜缆（NVLink 专用）经背板连接 |
| Scale-Out | 每计算托盘 4×CX8 800G IB + 每机 BlueField-3 DPU（400GE 管理） |
| 跨机架 | 800G 光模块 |

- 72 GPU 被当作**一台大 GPU**（统一内存，全 NVLink 访问）——MoE/TP 高频通信不出机架；[^15][^16]
- 机架内用铜缆（低延迟低成本），跨机柜用光纤（距离/信号）——**铜缆 vs 光纤的分界**是 5 千卡级设计的具体决策；[^16]
- 扩展单位 **NVL576 = 8×NVL72**；2026-27 规划 Vera Rubin NVL144 / Rubin Ultra NVL576。[^15][^17]

### 5.2 阿里灵骏 HPN（以太网路线的万卡实现）

阿里云灵骏 HPN7.0 是自研 51.2T 以太网交换芯片驱动的高性能网络：[^6][^18]

| 特性 | 数据/说明 |
| --- | --- |
| 拓扑 | 多轨 + 双平面：每 GPU 2×NIC Port 构成两个完全镜像的 plane，消除 ECMP 哈希极化 |
| 扩展 | 单层千卡 Segment、两层万卡；万卡显性扩展度 96%+ |
| 双上联 | 每个 GPU 双 200G 上联到不同 leaf，缓解单点硬件故障 |
| 拥塞 | 自研 HPCC 流控（CCF 论文同源）+ 多路径优化，端到端 2us |
| 算存分离 | 计算 RDMA 网与存储/管理网物理分离，互不干扰 |
| 超节点 | 真武 M890 超节点：64 卡全带宽互联，Scale-Up 51.2 TB/s，支持 12 万卡；磐久 AL128（128 GPU/柜，ALink 协议） |
| K8s 落地 | ACK 拓扑感知调度（基于 NCD 网络通信距离，多层 Gather/Binpack/Spread） |

**对比结论**：NVIDIA 走 IB 超节点 + NVLink；阿里走 51.2T 以太网 + RoCE/自研 + 超节点——**两条路线的共同点**是都做”Scale-Up 域消化高频通信 + Scale-Out 域只管低频跨域”，这是万卡唯一的可行方向。[^1][^6][^18]

### 5.3 万卡组网的两种经典形态

| 形态 | 二级多轨（<8K GPU） | 三级多轨（~32K GPU） |
| --- | --- | --- |
| Spine | 64 平面 × 1 spine/平面 | 三级：Core-Spine-Leaf |
| Leaf | 8 轨道，同号网卡同轨 | 同但更深 |
| 收敛比 | 1:1（无收敛） | 1:1（关键） |
| 服务器 | 16 组 × 64 台 = 1024 台（8K GPU） | 扩展至 32K |
| 适配 | DGX H100 级 8×400G 节点 | 大规模集群 |

**收敛比 1:1 是硬约束**：万卡训练 AllReduce 是全到全流量，任何收敛都会造成跨机带宽不可用的拥塞点。[^19]

### 6. 网络隔离与分离架构：四张网 + 逻辑隔离

GPU 集群的工程铁律之一是**“不能把所有流量挤在同一张网上”**——训练的计算流量（RDMA 全到全）、数据加载/checkpoint（存储流量）、管控（SSH/API）、带外（BMC）四类流量特征完全不同，混在一起会互相干扰。业界标准是**物理或逻辑分离**。[^1][^3][^4]

### 6.1 “四张网”分离架构（DGX SuperPOD 标准）

NVIDIA DGX SuperPOD 参考架构明确规定**四张相互独立的网络**：[^1]

| 网络 | 流量 | 技术 | 关键要求 |
| --- | --- | --- | --- |
| 计算网（Compute Fabric） | 梯度/激活同步（AllReduce 全到全） | IB / RoCE，每 GPU 独占 400/800G | 1:1 收敛、低时延、无损 |
| 存储网（Storage Fabric） | 数据集加载、checkpoint 读写 | IB / 高性能并行文件系统 | ≥40 GB/s/节点，可靠 |
| 带内管理网（In-Band Mgmt） | SSH、日志、监控数据、API | 以太网（25/100G） | 低带宽但高可用 |
| 带外管理网（OOB） | BMC/IPMI（电源/硬件状态） | 1G 以太网（独立） | 独立于业务网，故障也能管 |

**为什么分离**：训练 AllReduce 是全到全突发流量——如果不与存储/管理流量分开，checkpoint 写入引发的抖动会**直接抹平训练的 p99 吞吐**（”最慢的 rank 决定全局步进”）。[^3][^23]

### 6.2 计算网 vs 存储网分离的落地形态

- **物理分离**（自建 IDC 主流）：两张独立 IB/RoCE 网络、独立交换机、独立布线。代价是双倍网络硬件成本；
- **逻辑分离**（云上主流）：同一物理网络用 VLAN/VXLAN/PFC 优先级队列隔开，计算流量走高优先级无损队列、存储走普通队列。阿里灵骏即”计算网络与存储管理网络分离，可共享同一个 DC 集群 + 多个 HPN 集群”。[^6]
- **中间形态**：管理/存储共享一套以太网，但计算网必须独立——”两张网”（计算 + 其他）是最低配置。[^3][^4]

### 6.3 逻辑隔离技术（多租户/多作业安全）

| 技术 | 隔离粒度 | 适用 |
| --- | --- | --- |
| VLAN/VXLAN | L2/L3 网络分段 | 不同租户/环境的流量隔离 |
| PFC 优先级（802.1Qbb DSCP） | 流量类别隔离 | 计算流量与存储流量不同优先级的无损保证 |
| InfiniBand PKey（partition key） | IB 子网内分区 | 多租户共享 IB 网，PKey 隔离（Network Operator 的 ibKubernetes 管理） |
| RoCE 子网 / 存储-计算分流 | 出口级分流 | 云上租户 RDMA 隔离 |
| K8s NetworkPolicy | Pod 级网络策略 | 应用层访问控制（不影响数据面性能） |

**运维要点**：IB 的 PKey 需要与 UFM/OpenSM 配合，一个 Pod 只能属于一个 PKey 域；RoCE 的优先级队列要全局一致（网卡/交换机 DSCP 映射同步），否则 PFC 无法正确工作。[^21]

### 6.4 高可用与故障域分离

- **双控制器/双上联**：每个 GPU 双 NIC 上联不同 Leaf（阿里”双上联”），单网卡/单交换机故障不中断训练；[^6][^18]
- **双平面（dual-plane）**：两个完全镜像的网络平面，流量 50⁄50 分流并消除 ECMP 哈希极化；[^18]
- **管理面与控制面分离**：带外（OOB）独立于与业务网——即使计算网故障，仍能通过 BMC 远程管理服务器；[^1]
- **故障域设计**：训练作业的副本/并行组应分布在”同一故障域”（同 Leaf 域）以最大化性能，但实际 TCO 平衡点需要结合容灾要求（跨故障域 vs 单域性能）。

### 7. 前沿负载对网络的要求与支撑：UCCL / LMCache

网络专题的价值，最终要看”上层负载（集合通信、KV cache）对网络提出了什么要求、网络怎么支撑”。2025-2026 两个前沿方向（UCCL 与 LMCache）正好把这两个问题推到台前。[^24]

### 7.1 UCCL：新一代集合通信库，对网络”要求不变、支撑更强”

**UCCL（Unified Collective Communication Layer）** 是 UC Berkeley/UC Davis 的开源集合通信库（Apache-2.0，`github.com/uccl-project/uccl`），与 NCCL 并列的实质竞争者。[^24]

**对网络的要求**（核心结论：**与 NCCL 相同**）：

- 传输仍基于 RDMA（`libibverbs`），因此**无损网络、拓扑对齐、PFC/ECN 排障方法与 NCCL 完全一致**——网络专题前面讲的一切都适用；
- 差异化在于**架构**：UCCL 用 CPU 代理（proxy）做便携中间层，把”GPU 厂商×NIC 厂商”的 O(m×n) 移植量降到 O(m)——左侧只接自家 GPU 内核，右侧走标准 ibverbs 支持任意 RDMA 网卡（CX7 RoCE / Broadcom Thor-2 / AMD Pollara AI）。[^24]

**网络如何支撑 UCCL-EP（专家并行）性能**（OSDI’26 实测）：

- EP dispatch/combine 比 DeepEP 快最多 **2.3×**（AWS EFA）；SGLang EP=32 吞吐比 NCCL 快 ~40%；vLLM TPOT 降最多 25%；Megatron 训练（128 AMD GPU）比 RCCL 快最多 45%；[^24]
- **运维注意**：新网卡（Thor-2/Pollara AI）高负载下可能 **CQE error 12（Transport Retry Counter Exceeded）**，需调流控（`UCCL_IB_MAX_INFLIGHT_BYTES`），与 NCCL 的 `NCCL_BUFFSIZE` 同类——**网络侧仍要保证无丢包/拥塞可控**。

### 7.2 LMCache：KV cache offload，把”存储网络”变成推理性能的一部分

**LMCache**（`github.com/LMCache/LMCache`，LMCache/Tensormesh 团队）是 KV cache 存储与复用系统：把生成的 KV cache 存下来供后续请求复用（Agent/RAG 多轮场景收益大），并**offload 到 CPU 内存与对象存储（如 S3）**。[^24]

**带宽量级的关键洞察**（官方介绍数据）：[^24]

| 层级 | 带宽量级 | 对比 |
| --- | --- | --- |
| GPU HBM（B200） | ~1.5 TB | Agent 上下文可能耗尽 |
| CPU 内存 | ~2 TB | 与 GPU HBM 同量级 |
| GPU→CPU（PCIe） | ~6 GB/s | — |
| SSD | ~2-3 GB/s | — |
| Llama3 prefill 吞吐 | ~3-5 GB/s | 与 SSD 带宽同量级 → offload 可行 |

**对网络/存储的要求与支撑**：

- **CPU 内存 offload**：瓶颈是 PCIe 带宽（~6 GB/s），走主机的内存总线，不占网络；
- **存储 offload（S3 等）**：瓶颈变成**网络**——需求是”对象存储的读带宽 ≥ prefill 生成带宽（GB/s 级）”；对万卡推理集群意味着**存储网要能支撑 KV cache 的高吞吐回读**，否则 prefill 卡在取缓存；
- **K8s/可观测**：LMCache 已是 K8s 原生（对接 vLLM，`vllm` 侧做 `LLMEngine` 钩子），监控要覆盖”缓存命中率 + CPU/存储读带宽”，避免缓存 miss 时突发回读压垮管理网。

**一句话**：UCCL 回答”集合通信怎么更高效”（网络要求不变、架构更便携），LMCache 回答”推理状态怎么存”（把存储网络纳入性能方程）——两者都提醒运维：**网络不是被动的管道，而是上层 AI 负载性能的组成部分。**

### 7.3 小结：网络与上层负载的耦合

UCCL 与 LMCache 共同揭示的运维认知：**网络不是被动的管道，而是 AI 负载性能的组成部分**——集合通信的每一次优化（NCCL/UCCL）都依赖网络无丢包、拓扑对齐；KV cache 的每一次 offload 都依赖存储网络带宽。

### 8. K8s 网络插件与设备插件（GPU 训练的云原生网络栈）

Kubernetes 上跑 RDMA/GPUDirect 训练，核心是”**一个控制面 + 两张数据面**“：Pod 要同时有普通 eth0（管理/服务）和 RDMA 高性能接口。业界标准组合：[^20][^21]

```text
Pod ── eth0 ── 主 CNI（Calico/Cilium/VPC CNI）── 管理/服务流量
   └── rdma/ib0 ── Multus（secondary network）── CNI 插件（SR-IOV/host-device/ipoib）
            └── Device Plugin（SR-IOV / RDMA shared）── 把网卡资源暴露给调度器
```

### 8.1 组件分工

| 组件 | 职责 | 代表 |
| --- | --- | --- |
| 主 CNI | Pod 默认网络（eth0） | Calico、Cilium、阿里 VPC CNI |
| Multus | 多网络接口（给 Pod 挂第二个网卡） | k8snetworkplumbingwg/multus-cni |
| SR-IOV CNI | 把 VF（虚拟功能）挂进 Pod 提供直通性能 | sriov-cni |
| host-device CNI | 把宿主 PF 整个挂进 Pod（独占） | host-device-cni |
| IPoIB CNI | InfiniBand 子接口进 Pod | ipoib-cni |
| SR-IOV 设备插件 | 暴露 VF 为可调度资源 | sriov-network-device-plugin |
| RDMA 共享设备插件 | 多 Pod 共享一个 HCA，暴露 [http://nvidia.com/rdma_](http://nvidia.com/rdma_)* 资源 | k8s-rdma-shared-dev-plugin |
| IPAM | secondary network 分配 IP | nv-ipam（NVIDIA）、whereabouts |

### 8.2 NVIDIA Network Operator：一站式管理（当前主流）

**Network Operator** 通过 CRD（`NicClusterPolicy`）自动化部署网卡驱动、设备插件、secondary network，配合 **GPU Operator** 提供 GPUDirect RDMA：[^20][^21]

```text
NicClusterPolicy:
  ├─ ofedDriver        # 安装/加载 MLNX_OFED/DOCA 驱动（容器化）
  ├─ rdmaSharedDevicePlugin  # RDMA 共享设备插件（多 Pod 共卡）
  ├─ sriovDevicePlugin       # SR-IOV 设备插件（直通 VF）
  ├─ nvIpam                  # NVIDIA IPAM（secondary net IP 分配）
  ├─ ibKubernetes            # IB PKey 管理（配 UFM）
  └─ secondaryNetwork        # Multus + CNI 插件 + IPoIB
```

三种主流接入模式（按网络模型选）：[^21]

| 模式 | 资源形态 | 适用 |
| --- | --- | --- |
| SR-IOV | 每 Pod 一个 VF（直通、性能最好） | 训练大作业、独占带宽 |
| RDMA 共享 | 多 Pod 共享一个 HCA（低成本高密度） | 推理/小作业、利用率优先 |
| host-device | 整个 PF 给一个 Pod | 极高性能、单 Pod 独占 |

**GPUDirect RDMA 关键**：GPU 与网卡在同一 PCIe 域时，数据可 GPU↔NIC **绕过 CPU/主机内存**直接搬运。实现有两代：新 `DMA-BUF`（需 Open Kernel Module + CUDA≥11.7）与旧 `nvidia-peermem`。运维验证：`lsmod | grep nvidia_peermem` / pod 内 `ibv_devices` + `ib_write_bw`。[^20][^21]

### 8.3 拓扑感知调度：让 Pod 落在”物理上近”的地方

万卡集群里”GPU 落在哪台机器”直接决定 NCCL 性能（跨 spine vs 同 leaf 差一跳）。两类方案：[^6][^22]

- **NVIDIA GPU Operator + CAI（Cluster Autoscaling） / Volcano + 拓扑标签**：用 NFD 暴露 GPU/NUMA/PCIe 标签，调度器按节点拓扑做亲和；
- **阿里 ACK 拓扑感知调度**：定义 `ClusterNetworkTopology`（PoD/ASW/Hypernode/Node 四层），`JobNetworkTopology` 配 Binpack（聚拢到超节点）或 Spread（分散）；NCD 查询接口把”哪些节点物理近”暴露给调度器；
- **NVIDIA DRA/ComputeDomains（新，GB200 K8s）**：用 DRA 动态资源分配把 **IMEX 域**（多节点 NVLink 通信域）与 K8s 调度绑定，让跨节点 NVLink 训练像普通 Pod 一样调度，不再手动固定 IMEX 配置。[^22]

**共同原则**：调度器必须感知”网络通信距离”，把同一作业的 Pod 尽量聚到同一物理域（同 leaf → 同超节点），这是千卡以上的性能刚需。

### 9. 可观测性：GPU 网络怎么监控、怎么排障

### 9.1 全栈可观测性框架（NVIDIA 官方方法）

NVIDIA 把 AI 工厂可观测性分为五域，并给出工具映射：[^23]

| 域 | 工具 | 关键指标 |
| --- | --- | --- |
| 平台（BMC/电源/风扇） | Redfish/IPMI | 风扇转速、PSU 状态、关键温度 |
| GPU | DCGM | DCGM_FI_DEV_GPU_UTIL、MEM_COPY_UTIL、POWER_USAGE、XID_ERRORS、NVLink 吞吐 |
| 节点互连（NVSwitch） | DCGM / NVSM | NVLink 计数器、XID |
| IB 网络 | UFM | PortXmitDataExtended、SymbolErrorCounterExtended、Effective_BER、Chip_Temp |
| 以太网/RoCE | NetQ | 链路、拥塞、丢包 |
| 集群/作业 | BCM / Slurm | 运行作业、GPU 预留、排队等待 |

**选型判断（官方给的原则）**：IB 用 UFM、以太网用 NetQ（不要两个都上）；DCGM 用于 GPU 遥测（配合 Prometheus exporter），NVSM 管 DGX 系统健康；BCM 只做聚合不做深遥测。[^23]

### 9.2 GPU 集群监控落地（Prometheus 栈）

```text
dcgm-exporter（每节点） ────┐
UFM Telemetry / NetQ ────────┼──→ Prometheus ──→ Grafana（分层看板）
node_exporter（平台） ────────┘        │
                                       └──→ Alertmanager（告警）
```

关键指标（与调优/排障直接相关）：[^8][^23]

- GPU：`DCGM_FI_DEV_GPU_UTIL`、`DCGM_FI_DEV_XID_ERRORS`（Xid 79 掉线立即告警）、`DCGM_FI_DEV_ECC_DBE_AGG`（双 bit ECC，显存故障前兆）；
- 网络：PFC 计数器（`mlx5_port_pfc_rx_pause_total`，PFC 风暴）、`PortXmitData`/`Effective_BER`（误码率回归是慢速大问题）、丢包；
- 训练：`training_step_time_seconds`（卡住检测）、NCCL 日志（NCCL_DEBUG）。

### 9.3 常见网络故障与排查锚点

| 症状 | 根因方向 | 排查入口 |
| --- | --- | --- |
| 训练变慢但链路 up | PFC 风暴 / BER 误码 / 哈希不均 | PFC 计数、UFM BER、NCCL busbw |
| NCCL hang（约 80% 在网络层） | 丢包/拥塞/拓扑不均 | NCCL_DEBUG_FILE、ib_write_bw 对照 |
| GPU 掉线（Xid 79） | 硬件/驱动/固件 | DCGM XID、dmesg、nvidia-smi -q |
| 跨机带宽不达标 | 拓扑 XML 缺失 / NUMA 错配 / PCIe 版本 | NCCL 日志 PXB/PIX/SYS、ib_write_bw |
| 单请求时快时慢 | 哈希极化 / ECMP 不均 | rail 对齐检查、流量统计 |

### 10. 最佳实践清单（可直接照做）

**硬件/组网**

1. 计算网与存储/管理网**物理分离**（两张网），互不干扰；[^3][^4]
2. 每 GPU **独占网卡**；收敛比保持 **1:1**（万卡必守）；[^3][^19]
3. 400G 网卡必须配 **PCIe Gen5**，否则带宽用不上；[^2][^3]
4. 机柜间光缆**按距离约束布线**（节点-叶≤50m、叶-脊单模≤500m）；[^1]
5. 千卡以上用 **rail-optimized 或等效多轨对齐**，消除哈希极化。[^1][^11]

**RDMA/无损**

1. 自建极致性能用 IB；公有云/性价比用 **RoCEv2 + PFC + ECN + DCQCN**；[^4][^6][^9]
2. 配了 PFC 必须配 ECN，否则 PFC 风暴；[^8]
3. IB 一定部署**高可用 SM/UFM**（单一 SM 是单点）。[^10]

**网络隔离/分离**

1. 至少”两张网”：**计算网独立**，存储/管理可共享或再分（四张网是 SuperPOD 级标准）；[^1][^3]
2. 训练 AllReduce 流量与 checkpoint/数据加载**必须隔离**，否则存储抖动抹平训练 p99；[^3][^23]
3. 多租户共享 IB 用 **PKey 隔离**（配 UFM/OpenSM）、RoCE 用 **VLAN/VXLAN + DSCP 优先级**；[^21]
4. 关键作业 **双上联/双平面**冗余，单交换机故障不中断训练（阿里双平面思路）。[^6][^18]

**K8s 网络**

1. 用 **Network Operator + GPU Operator** 管理驱动/设备插件（避免手装 MLNX_OFED）；[^20][^21]
2. RDMA 训练 Pod 用 **Multus + SR-IOV（或 RDMA shared）**双网卡；[^20]
3. **NCCL 拓扑文件（`/etc/nccl.conf`/`NCCL_TOPO_FILE`）**在虚拟化/非标拓扑下必须配；[^14]
4. 调度器做**拓扑感知**（标签/NCD/ComputeDomains），Pod 聚到同一物理域。[^6][^22]

**前沿负载（UCCL / LMCache）**

1. UCCL 与 NCCL 并存时，**RDMA 无损/拓扑/PFC 排查方法通用**——网络要求不变，只多了”选哪个库”的决策；[^24]
2. 异构集群（NVIDIA+AMD / 多 NIC 厂商）优先评估 **UCCL**（一次移植处处可用，EP 场景比 DeepEP 快最多 2.3×）；[^24]
3. 引入 **LMCache/KV cache offload** 前，先算”存储网读带宽 ≥ prefill 生成带宽（GB/s 级）”，否则缓存 miss 回读会压垮管理网；[^24]

**可观测性**

1. 五域全覆盖：Redfish/IPMI + DCGM + UFM/NetQ + 作业调度器；[^23]
2. 告警绑定**SLO/runbook**，别堆指标转储；[^23]
3. 建 **NCCL 性能基线**（`nccl-tests` all_reduce busbw），变更后对比——这是网络回归的雷达。[^14][^19]
