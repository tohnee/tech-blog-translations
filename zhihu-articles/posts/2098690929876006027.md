## 背景

且说当下就没见过不谈AI和AI应用的高科技企业，那之前工作重心还在传统IT、互联网应用的企业自然也必须要及时跟进喽。加上这段时间众所周知的芯片涨价风潮，往年那些不差钱的大厂在设备投入上也变得斤斤计较起来。

我是说假如有这么一家厂子，准备把之前用来看电视的老旧机器通过环保回收领域重塑去蒸包子，通过RDMA实现高速KV cache。机器是早些年的两路SPR Xeon，每路CPU搭载了4根DDR4-4，为了减少两路CPU之间的交互，于是在两颗CPU下各自安装了单独的2张mellanox CX7 400G网卡。测试中主机两两结对互为Server-Client，双方均通过RDMA实现互联——实际上是通过[perftest](https://github.com/linux-rdma/perftest)工具的ib_write_bw工具相互通过RDMA互访。那么理论上2张400Gbps的网络带宽可以支撑 100GB/s——这个预期很重要。

ib_write_bw的测试方法也没什么特别的，甚至可以说大多数都保持了默认参数，这里简单罗列一下

```bash
# Server
~# ib_write_bw \
    -d mlx5_0 \    # -d 指定RDMA的设备
    -s 1048576 \   # -s 指定message size
    -D 30 \       # -D 指定测试时常 
    --report_gbits # 报告格式

# Client
~# ib_write_bw \
    -d mlx5_0 \
    -s 1048576 \
    -D 30 \
    --report_gbits \
    192.168.1.10 # 指定Server IP
```

做了几个初步测试，就暴露了一堆问题：

- 大包问题：测试中通过-s参数增加message size大于1M（1048576）之后，测得网络实际带宽极速下滑。
- 小包问题：测试中-s参数为64K的时候，有较小概率出现网络带宽减半的情况。

这次就分开讲讲吧~

## RDMA数据链路

首先，先要搞清楚一个问题：在RDMA测试中，数据从Client写入Server内存，究竟经过了哪些系统的组件？

这不是简单的一句“网卡DMA”就可以讲清楚的事情，先麻烦AI画个时序图吧

![](https://pic3.zhimg.com/v2-6d4f20796fb66add752b2b53650aec44_r.jpg)

实际上AI给出的图并不严谨，但足够说明问题了，我还是尽可能的简化一下这个流程，描述一下跟性能相关的主要过程的逻辑。

1. 链接建立，这部分没什么好说的，就是打开一个通路罢了，跟整体的测试性能没什么关联关系。
2. 真正意义上的RDMA操作：Client CPU从内存上获得数据，再经由LLC->IRP->IIO将数据写入网卡的缓存。网卡负责将数据拷贝到Server网卡的缓存，再由Server网卡走一个反向的IIO->IRP->LLC，视情况将数据保存到物理内存（DDR RAM）。

当代CPU和网卡都会对针对传统的DMA作出优化——一旦条件允许，网卡的数据包不会直接操作DRAM，取而代之的是MMIO直接操作LLC（L3缓存）。考虑到DRAM的带宽和时延远小于LLC，所以对于大吞吐的网络操作优先考虑的就是LLC的命中率。

## 数据分析

在同一轮的测试中抓了Server和Client端的PCM数据，放在一起做参考，需要强调的是由于测量中不可避免的误差，我通常默认5%以内，部分指标10%以内的差异都视为数据一致。

![](https://pic4.zhimg.com/v2-177bc04a0f3f0c5c305ee5be48a74679_r.jpg)

- 排除perftest自身可能存在的误差，实测NIC speed 两边基本一致，Server 617Gbps，Client 620Gbps。
- Server端的“read”实际上对比的是Client的“write”，反之亦然。那对应的request per sec系列指标也对齐了。server read 583M ～ client write 588M；Server write 624M～Client read 611M。同时也证实了从server端来看这是个Write大于Read带宽的操作——废话，ib_**write**_bw测试嘛！
- 具体的读写Bandwidth也一笔带过吧，没什么异常。
- IO read/write cache misses bandwidth子项就很特别，它描述的是由于MMIO操作没能命中LLC而不得不操作内存导致的内存带宽。参考上边的IO bandwidth，你会发现Server端几乎所有的write，以及大部分的read都没有命中LLC。造成了37GB/s的内存读和35GB/s的内存写。
- 回头看一眼实际的内存带宽，好家伙全被LLC misses的MMIO操作占满了，72GB/s的总内存带宽。
- 继续看RPQ/WPQ这类内存操作队列的长度，16/30个等待的操作说明内存带宽已经出现显著的瓶颈了，而且单锁数值上看client应该比server的内存瓶颈更高。

## 结论

问题应该明确了：在大包测试的情况下，由于message size太大，收发数据时LLC被击穿，内存带宽瓶颈凸显，最终表现为网络带宽的下降。而由于ib_write_bw是一个双向操作，数据显示是client端首先出现了瓶颈，进而拖累到整体测试结果。

通过增加了内存条，启用了更多的内存通道，该问题得到解决。不过话说加内存提升网卡性能的问题也是够搞笑了，何况现在服务器上ECC DDR4内存这价格……
