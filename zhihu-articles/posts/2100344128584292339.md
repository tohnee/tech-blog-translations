投机解码让草稿模型先写几个 Token，再由目标模型一次验证。它能否加速，至少取决于草稿延迟、验证成本、接受率、草稿长度和内存带宽。

![](https://pica.zhimg.com/v2-6818e947a75b7a66939687699506a702_r.jpg)

Apple Silicon 的研究很能说明问题：服务器 GPU 上常见 2–6 倍收益的投机方案，在四台 Apple 设备的单请求聊天负载里都没有稳定兑现，反而降低了吞吐。草稿和验证的额外开销超过了 Decode 省下的时间。

MoE 更复杂。连续草稿可能重复选中同一专家，但“专家复用”不等于“少读字节后一定更快”。MoE 投机解码必须比较两类 kernel：去重后的字节占比和有效带宽比。实测交叉点常常在每次 5–8 个 Token，或者根本不存在。

分布式场景先被通信卡住。DISCO 把草稿 SLM 副本放到服务器端，设备只发送 Token 索引和标量概率，避免完整词表分布传输。1 Mbps 低带宽下仍约 1.5 倍，RTX 4090 到 A100 的异构 LAN 环境最高 1.92 倍。不过它目前是单请求评估，多用户排队和公平性还没解决。

所以投机解码上线前，先测接受率、草稿延迟、端到端 Prefill 成本和网络通信。任何一个变量不合适，它都会从加速器变成额外负担。

可以先用一个极简公式算边界。

假设草稿长度为 4，目标模型验证一次的时间记作 1，草稿每 Token 成本是 0.05。几何接受率下，每轮期望输出 Token 和相对速度大致是：

| 接受率 | 期望 Token/轮 | 相对速度 |
| --- | --- | --- |
| 0.2 | 1.25 | 1.04× |
| 0.5 | 1.94 | 1.62× |
| 0.8 | 3.36 | 2.80× |

![](https://pic1.zhimg.com/v2-a7f5c79e277a6e93f6612c7c2ed93fb4_r.jpg)

接受率一低，草稿和验证成本立刻吞掉收益。这还没算草稿 Prefill、KV 管理、采样和网络。

MoE 又会让“专家复用”误导判断。去重 Kernel 读的字节更少，但它的有效带宽往往更低。必须比较去重后的字节占比和两种 Kernel 的带宽比，不能只看复用率。论文实测的加速交叉点常在每次 5–8 Token，或者根本不出现。

DISCO 解决的是另一个约束：设备与服务器之间不要传完整词表分布。它把草稿 SLM 副本放到服务器端，只传 Token 和标量概率。1 Mbps 低带宽下仍约 1.5 倍，RTX 4090 到 A100 的 LAN 实测最高 1.92 倍。

但 DISCO 目前主要是单请求。多用户并发后，服务器端草稿副本会增加计算、显存和排队成本。

投机解码上线至少有四道验收：

1. 目标模型是否真的被 Decode 限制？
2. 业务分布下接受率是否稳定？
3. 草稿路径能否藏在目标验证后面？
4. MoE 和分布式场景是否增加了新的字节/通信成本？

多算几个 Token 不是问题，多算之后没有减少关键路径，才是问题。

还有一个很实用的反例：某些投机实现有“单个配置看起来更快”的案例，但固定聊天负载整体降速。原因通常是长 Prompt 上的草稿 Prefill 被隐藏了，或者测试只统计 Decode 阶段。

因此验收表必须拆阶段：

| 阶段 | 要记录 |
| --- | --- |
| 草稿 Prefill | 是否新增首响 |
| 草稿 Decode | 每 Token 成本 |
| 目标验证 | 一次验证多少 Token |
| 拒绝回退 | 重采样和下次循环成本 |
| 并发 | 草稿与目标争多少 GPU |

把这几段分开后，投机解码的收益和亏损都能落到具体路径，不再是一个孤立倍数。

如果只看一个硬指标，我会看“端到端每 Token 时间”，并同时记录拒绝率。拒绝率高时，草稿模型虽然让目标验证一次处理多个候选，但有效 Token 很少，草稿成本占主导。

还要防止一个隐性误判：草稿模型的 Prefill 可能在聊天短请求里不明显，在长系统 Prompt 或 RAG 文档里却很大。业务输入变长后，投机解码必须重新验收。
