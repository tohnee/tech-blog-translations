> **Q1: 一条 raw document 到底是怎么进入 K40 的？**

[assign.py](https://github.com/marin-community/marin/blob/main/experiments/datakit/cluster/domain/v0/assign.py)

先给结论：

> Marin 不是先人工定义 40 个标签，然后训练一个 40 分类器，把 document 分类成 K13/K14。当前 Datakit reference pipeline 更接近：<br> **document → embedding 向量 → 很细的聚类 → 合并成 40 个大簇 → 得到 cluster ID。**

而且还有一个特别重要的细节：

> 他们不是直接 KMeans(K=40)，而是先做 K=5000，再把 5000 个细粒度 cluster 合并成 K=40。

严格来说，进入 K40 聚类的并不是刚刚从互联网抓下来的原始 HTML。

Marin 的 Datakit 前面先会把各种 source：

```text
JSONL
HTML-derived text
Parquet
Code dataset
PDF text
Agent trajectory
...

```

统一做 normalization，变成类似：

```text
{
    id: "...",
    text: "真正的 document 文本..."
}

```

之后，从这个 **normalized document** 出发，同时跑很多属性计算：

```text
                         normalized document
                                │
            ┌───────────────────┼───────────────────┐
            ↓                   ↓                   ↓
        embedding          quality score         minhash
            ↓                   ↓                   ↓
       domain K             quality Q            dedup
            │                   │                   │
            └───────────────────┼───────────────────┘
                                ↓
                              store

```

Marin 当前 reference pipeline 就是这样组织的：normalized source 一路进入 embedding/domain assignment，另外几路独立做 quality、decontamination、dedup，最后在 store 阶段把这些属性重新 join 起来，再按 `(cluster, quality)` 分桶。

**这里重点关注Domain K的产生过程**：

首先把 embedding space 切成：5000个簇。

```text
                  所有 documents
                        ↓
                 embedding space
                        ↓
                  KMeans K=5000
                        ↓

         ┌────────┬────────┬─────────────┐
         ↓        ↓        ↓             ↓
       C0000    C0001    C0002  ...    C4999
```

然后从5000个类别再合并成40个类别。这一步不是重新拿所有 document 再 KMeans 一次。而是拿5000个Centroid (**聚类中心**)，计算 centroid 之间的 cosine distance：

$d(c_i,c_j) = 1 - cos(c_i,c_j)$

按照cosine distance，从小到大合并（参照哈夫曼树的构造过程）。最后得到40个类别以及一张lookup表格，维护了对应的映射。

```text
细粒度 cluster     最终 K40 cluster

C0000             →  K13
C0001             →  K14
C0002             →  K39
C0003             →  K13
...
C4999             →  K30
```

以后给**全量几十亿 document**分 K 时，不需要重新做 clustering。只需要embedding之后按照最近的 5000-centroid 是谁，然后查表，就可以得到K40的结果了。

> **Q2: Q5 的“质量分数”究竟是怎么来的？**

对语料评分的思路基本上就是LLM as a judge。不过此处，作者定义了一个rubric。

> Judge the document as an example of its OWN type.

定义这个rubric是因为作者前期的quality classifier 实际上出现了严重的 **domain bias**：

```text
干净 code
→ 低分

dense math
→ 低分

非英语
→ 普遍低分

漂亮 English prose
→ 高分
```

[官方rubric.py](https://raw.githubusercontent.com/marin-community/marin/main/experiments/datakit/cluster/quality/fast_transformer/rubric.py)

官方 rubric 相关的点主要是：

- 输出1到5分
- source-blind。不要向LLM透露这个文档来自哪个来源（防止LLM从来源推断质量）
- 打了5,578个标签，然后训了一个很小的**document-quality regression model**。

### FastTransFormer的训练细节

普通的transformer 如果看到 512 token，会让 transformer 直接在 512 个 token 上做 attention。他们先每64 tokens压成一个super-token，再做attention。

官方 model 代码的 pipeline 是：token embedding → pooling → transformer layers → document pooling → scalar quality logit。

> **这里的池化，就是分别计算 mean、max、min 三个向量，然后拼接。**

[fast_transformer源代码](https://raw.githubusercontent.com/marin-community/marin/main/experiments/datakit/cluster/quality/fast_transformer/model.py)

```text
512 tokens
    ↓
每 64 token 做一次 pooling
    ↓
8 个压缩表示
    ↓
tiny Transformer
    ↓
整个 document representation
    ↓
Linear Head
    ↓
quality score
```

以上是正常document的打分思路。如果对于一条trajectory，或者碰到long-horizon的任务的时候，这种judge方式明显不合理。因为cc/codex等等的trajectory充斥着漫长的system prompt和harness文本。

这个case下，打分器只看前512 tokens的标准差会很小。拉不开差距。

[scorer.py](https://raw.githubusercontent.com/marin-community/marin/main/experiments/datakit/cluster/quality/fast_transformer/scorer.py)

于是他们用了 **BME scoring（**Begin / Middle / End**）。**对于长document，开头中间结尾各自打分，然后再平均一下。

> 这里要注意下，这个 scorer **并不知道 Agent 最终任务有没有真正做成功**。FastTransformer 判断的是 **surface text quality**，而不是 trajectory success。solved trajectory和failed trajectory的scorer分数差异接近0。这里给的Quality其实更多是作为**pretraining document，关键是有多完整、连贯、信息密集、结构良好、少噪声。**

**……以上内容主要是Judge的过程。那这个FastTransformer本身是怎么训的呢？**

前面我们说“用 Oracle 给少量 document 打分，再训练 FastTransformer 扫全量 23T 数据”。

现在真正的问题变成：

> **这“少量 document”到底怎么选？为什么是 5,578 条？怎么避免全是英文 prose？为什么两个 Oracle 要重复打分？junk-gate 又是什么？**

首先，为什么不能随机抽5000条数据打分直接训？因为语料分布数量不同，随机抽对偏少的语料种类有bias。因为模型会发现：

> “只要学好 English Web，我的总体 loss 就已经很好了。”

最后得到一个**总体 accuracy 看着不错，但 minority domain 完全不能用的 scorer**。

所以训练 Quality Scorer 时，重要的不是：

> “训练样本能不能完全代表 corpus 的自然比例？”

而是：

> **“训练样本有没有覆盖 scorer 将来需要处理的各种情况？”**

作者第一次训的时候，用了2,089 个 document，来自 38 个 source。而且其中**380 条做了 double labeling。**也就是说，同一篇 document 让两个独立的 Oracle judgment 去打分。这里的用处有两块吧。

- 测试Teacher Model的打分一致性
- 对同样的一个样本，可以取consensus分数，这样子可以避免样本的ground truth的偏差

作者团队有相关的实验可以看这里 [打分器摸索](https://github.com/marin-community/marin/pull/7040/changes/cc56b0cdf9c7743d8e005987ab83c2712c3d476e) 。

一开始是：

```text
Document X

Oracle pass #1
→ quality = 4
```

用这些 single-rater labels 训练 pooled FastTransformer。结果：

```text
Spearman ≈ 0.59
pair accuracy ≈ 0.67
```

看起来已经比旧 fastText 好很多。但他们发现一个有意思的现象：**瓶颈可能已经不是模型，而是 label noise**。

> 把模型放大 7 倍，Spearman也只能做到大约 0.61。

然而在引入了consensus之后。

```text
Spearman = 0.69
pair accuracy = 0.74
```

核心就是：**没有单纯靠把模型做得更大，而是把 label 做得更干净**。

---

最后就是在训练了一个版本的打分器之后，需要对打分器做**Junk-Gate（俗称修Badcase）。**

```text
Q4
│
├── 很好的 Wikipedia
├── 很好的 Code
├── 很好的 Math
├── 很好的 multilingual
└── 某条特别烂的网页  ← !!!
```

为什么badcase值得修？因为Q4会被upsample，多次采样的情况下，可能会导致问题放大。因此，我们要**每个 bucket 内部足够 coherent**。

这里大概的sop是这样子的。

```text
某些 Web/Wiki 样本
被错误放到高质量

某些 Code/Math junk
模型区分得不好
```

解决思路：针对模型最容易犯错的样本，补充对应的数据，再加入training set里面去即可。

---

**Calibration：为什么Q5 (五种质量级别) 用“绝对质量桶”，而不是每桶固定 20%（正态分布排名这块……）？**

得到FastTransFormer的judge之后，还没结束。因为模型输出的 raw score 本身不能直接拿来当绝对质量。这里就需要**Calibration**。

Marin 自己代码注释说：

> raw pooled-FT score 呈 bell-shaped；如果直接按 0.2、0.4、0.6、0.8 切，会导致绝大多数 document 堆在中间桶。

这里主要就是要避免低质量的数据由于排名较高，还是进入到了较高的Q级别。这会破坏跨 级别的可比性。作者希望一个 bucket 有一定的**absolute meaning**（德要配位(^_^)），但是这样子的坏处是**极端 bucket 可能特别小**。

具体怎么做Calibration呢？大概的思路如下：

- 在有 Oracle label 的文档上跑 scorer；
- 分别算 Oracle level 1~5 对应 raw score 的中位数；
- 相邻 level 的中位数取 midpoint；
- 得到 4 个分界点；

### 为什么低分数据要拿进来做训练，而不是直接删去

有两种完全不同的数据处理思想：一种是设置硬过滤（把质量低于某个级别的去除），另外一种是设置软权重weight sampling（降低采样)。

> 为什么在 pretraining 里，“不要一刀切掉所有低分数据”是合理的?

- **Quality Model 不是真理，可能会出错**：Quality Score（根据 quality model，这条数据有多像“高质量训练文本”）和Training Utility（这条数据实际对训练最终模型有多大帮助）不可能完全正比
- **低Quality可能会有高的diversity：** 如果训练数据只剩下漂亮prose,QA,code，模型可能会失去一定的分布多样性
- **Q0 本身也不是同质的**：实际上,一个 bucket 是**按 score 范围切出来的一大批数据**。里面会混合很多不同原因导致的低分。例如：真正的垃圾网页，重复模版，乱码，奇怪格式，scorer不理解的code/log等等。**因此Q0不等于一个语义一致的垃圾类别**

**最后在数据分类质量这里总结下。几个核心的重点如下：**

- **source coverage：把每个类型都完整覆盖到，类别如何定义，可以先做细分聚类，再按照聚类中心做合并**
- **type aware：打分的rubrics，分数区间分布需要提前定义**
- **打分器训练：小样本transformers训练，初始数据来自LLM，训练完再做badcase回流**

```text
1. 采样 labels
      ↓
2. Oracle 打分
      ↓
3. Train scorer
      ↓
4. Holdout eval
      ↓
5. Production corpus scoring
      ↓
6. 按 source/type/bucket audit
      ↓
7. 找哪里表现差
      ↓
8. 针对性补 labels
      ↓
9. Retrain
      ↓
10. 再 audit
```

## 数据清洗和配比

### **Mixture Weight和边界训练价值**

模型训练的过程中，并不会完全按照数据配比来训练，而是会有一个采样概率。

**例如：**

```text
c13q0 = 2.56e-7
```

**可以理解成这个 cell 在 Phase 0 mixture 里的采样权重/概率**。

完整过程是

```text
先选 cell
   ↓
P(cell = c13q0) = 2.56e-7
   ↓
如果选中了 c13q0
   ↓
再从 c13q0 内部的数据流里取 document/token
```

**Q4也不一定采样最多。因为**

> **Quality Score 只是 mixture optimization 的一个输入维度，不是最终目标函数。**

因此Q ≠ w ！ Q只是数据本身的属性，w才是训练时给多少采样概率。

最终的training utility 还涉及：

```text
数据量
多样性
domain
重复次数
learning dynamics
benchmark 效果
数据互补性
```

> 例如有段Q4的数学证明，但是只有10B tokens，你的训练预算是18T tokens。假如你给他10%的训练预算，那就是1.8T Q4 math。也就意味着平均重复1.8T/10B = 180次！

因此，即使数据质量再好，也不能够无限采。反过来，某个低质量数据，可能有海量的diverse,unique，训练价值并不低。

我们不应该问“某个sample的质量如何”，而最应该关注**边际训练价值**：

> **“如果我多花 100B tokens 的训练预算在这个 cell 上，模型最终能力能提升多少？”**

```text
Q4 Math
第一遍非常有用
第二遍有用
第三遍收益下降
第十遍可能没什么价值

Q2 diverse web
虽然单条质量一般
但一直有新知识
新语言
新格式
新概念
```

Candidate proportion 是：

> **现实世界给了我多少。**

Mixture weight 是：

> **我决定让模型吃多少。**

### Data Mixture Optimization

对于K40Q5这个情况而言，Data Mixture的优化实际上是求一个 $w^{(0)} = (w_1,w_2,…,w_{200})$

且满足 $\sum_{i=1}^{200}{w_i} = 1$ 的优化问题。

你当然不可能全部训练一遍再看结果。因此需要**Proxy Model**。

**正确的思路是：**

```text
不同 mixture
     ↓
训练很多个小模型
     ↓
观察表现
     ↓
从这些实验学习：
“mixture → performance”
     ↓
预测一个更好的 mixture
     ↓
最后才给大模型使用
```

**一组实验如何组织？**

首先提出一套recipe，用他去训练一个小的d768模型。训练完之后测：

```text
HumanEval
GSM8K
GPQA
MMLU-Pro
HellaSwag
LAMBADA
PIQA
...
```

官方 Harrier 数据表中的每一行，都记录一套这样的实验，包括 `run_name`、`group`、两阶段 weights、每个 cell 分配到的 token、epochs，以及最终 eval/BPB。

**总体实验安排**

| 实验族 | 数量 | 核心问题 |
| --- | --- | --- |
| Proportional seeds | 10 | baseline 本身有多大随机波动？ |
| Domain cooldowns | 40 | 某一个 K-domain 多吃一点，会发生什么？ |
| Quality cooldowns | 4 | 更偏向不同质量层级，会发生什么？ |
| Aggressive priors | 32 | 去更极端的 mixture 区域探索 |
| Earlier mixture priors | 8 | 以前已经觉得不错的配方在新体系里怎么样？ |
| Targeted mixtures | 2 | 针对目标能力定向设计的候选 |
| Next-round mixtures | 8 | 第一轮结果出来后，再提出下一批候选 |
| Joint mixtures | 8 | 多个好方向同时组合会怎样？ |
| Intuitive mixtures | 4 | 人工凭经验设计的 recipe 能不能打赢 optimizer？ |
| 总计 | 116 |  |

首先是10 个 **Proportional Seeds**，跑10次取相关指标的均值，建立baseline。

> **“如果我什么聪明操作都不做，直接按照数据配比里每个 cell 的自然比例训练，会怎么样？”**

获得baseline之后，现在要回答的是

> **“到底哪种数据更值得多吃？”**

最自然的方法就是：

> **一次只动一个方向。**

也就是**40组Domain Cooldowns**。为什么是40，因为正好有40个semantics domains。

实验的组织过程如下: 先有一个 baseline：

```text
K00 新闻        3%
K01 健康        2%
...
K13 Agent       2%
K14 Code        7%
...
K39 Math        2%
```

现在我们想知道：

> **K13 Agent 是不是值得更多训练预算？**

于是做一套实验。

Phase 0：

```text
还是 baseline
```

到了最后 cooldown：

```text
K13 ↑
```

相应其他 domain 稍微下降，重新归一化到 100%。

然后看：

```text
HumanEval 怎么变？
GSM8K 怎么变？
GPQA 怎么变？
General BPB 怎么变？
```

实际上的Harrier mixture 实验组织不会从step 0 重新训练，而是从同一个 step checkpoint 接着训。

从0开始训练：

```text
step 0
```

这就是 exploration。

**第五类实验是8 个 Earlier Mixture Priors**。这部分主要是作者利用其过往的一些已经有依据、已经有希望的 mixture idea 带进当前 Harrier experiment set 里重新测试。

> 老 mixture 权重可以原封不动复制。

> **带着历史 prior 进入新实验。**

> **Mixture weights实验中proxy model的训练数据组织**

[datasets.py](https://raw.githubusercontent.com/marin-community/marin/main/lib/levanter/src/levanter/data/text/datasets.py)

一句话解释：原模型的总预算tokens数，缩小到proxy model的预算tokens数时，每个类别分到的tokens数量也应该等比例缩小。把“可见的 unique data pool”也缩小，从而让小实验经历类似 full-scale run 的数据稀缺度和重复程度。

```text

↓
Simulated Epoching
↓
人为缩小 data pool

真正昂贵的大实验
↓
已经有能力消费大量真实数据
↓
关闭 simulation
↓
尽量看真实 corpus
```

### Proxy Model实验迁移

> **如何确定当下最好的mixture？如何从当下仅有的116组runs，确定可用的mixture。**

假设真实的跑了6组实验。

| Run | Web | Math | Code | 最终 Target BPB |
| --- | --- | --- | --- | --- |
| A | 80% | 10% | 10% | 2.40 |
| B | 70% | 20% | 10% | 2.34 |
| C | 70% | 10% | 20% | 2.36 |
| D | 60% | 20% | 20% | 2.28 |
| E | 50% | 30% | 20% | 2.27 |
| F | 30% | 40% | 30% | 2.45 |

这里希望做的事情本质是：根据已经跑过的 6 个实验，猜哪些没跑过的 mixture 更值得试。这里也就引入了surrogate。

surrogate的作用是：评价 candidate mixture。

也就是：

```text
Candidate mixture
       ↓
Surrogate
       ↓
Predicted performance
```

例如我们生成 100 万套 candidate：

```text
candidate 1
candidate 2
candidate 3
...
candidate 1,000,000
```

Surrogate 很快给它们全部打分。

[mixture实验结果](https://huggingface.co/datasets/marin-community/grug-moe-mix-swarm)

但是Surrogate的压力在于，只有116组数据，如何确保效果呢？理论上这是一个高维度向量。

如果真的让 400 个 weight 完全自由：几乎不可能可靠学习。所以一个非常重要的事实是：**那 116 个 experiment 本身就是经过结构化设计的。**不是随机 400 维乱动。例如：

```text
40 Domain Cooldowns
```

是在有意识地测试：

> 增加 K00 会怎样？增加 K01 会怎样？ 增加 K39 会怎样？

还有：

```text
4 Quality Cooldowns
```

是在测试：

> 质量 distribution 改变会怎样？

Prior experience是代表一个靠谱的baseline。那么 candidate mixture可以在baseline周围改变。也就是，我们知道：

- natural/proportional mixture 是合理起点；
- 某些过去的 mixture 已经不错；
- Math/Code/Agent 等 domain 有实验信号；
- 某些极端重复不可接受；
- weights 必须 sum=1；
- epoch 不能太高。

这些都限制了 optimizer 的搜索范围。

> 为什么不能只选 surrogate 预测最好的那个？

假设 surrogate 说：

```text
Candidate A
预测 Target = -2.3%
```

而：

```text
Candidate B
预测 Target = -3.5%
```

看起来 B 更好。

但是 B 所在区域可能完全没跑过真实 experiment。所以 B 的：

```text
-3.5%
```

可能只是模型胡猜。

这就是 Bayesian Optimization 比单纯 regression search 多考虑的一件事：**uncertainty。**

**这里的优化过程不是回答“谁看起来更好”，而是“下组实验更加值得跑谁”。**

无论下组实验成功失败，Mixture weights的优化空间都会更加的收敛。这里本质是一个“做实验 → 更新认知 → 再做实验”的Loop。

直到在d768这个case得到想要的结果为止。

> **Proxy Model实验怎么Scaling？为什么小模型认为好的 mixture，大模型也会认为好？**

Proxy Model的mixture实验本质是：**获得一个mixture的ranking，也就是相对好。**绝对的improvement不重要。具体看：

[RegMix: Data Mixture as Regression for Language Model Pre-training](https://arxiv.org/pdf/2407.01492)

结论：**data mixture 的相对优劣，在相当大的 scale range 内具有一定可迁移性**。

但是这里也有失败的case，论文叫做**Ranking Inversion (也就是小模型的实验难以迁移上去)**：

- 小模型过拟合数据。相同的epoch数对大小模型效果不一样。mixture weight迁移不上去
- 小模型能力不足，没有足够 capacity 吃透复杂任务

因此这里就需要出现scaling ladder。

[scaling_ladder.py](https://github.com/marin-community/marin/blob/main/experiments/grug/moe_hero_ep/launch_scaling_ladder.py?utm_source=chatgpt.com)

| rung | active params | tokens |
| --- | --- | --- |
| d768 | ~61M | ~48B |
| d1024 | ~162M | ~128B |
| d1536 | ~481M | ~381B |
| d2048 | ~1.2B | ~926B |
| d6144 Hero | ~23B | ~18T |

> 控制变量：same EP hero recipe、routed experts、tokenizer 、**token预算和激活参数的比值**等，主要变化是 width 和运行规模。

这里主要就是看一个趋势。同样的mixture，hidden size从768慢慢上升，效果稳定即可。

> **Mixture weights如何真的变成训练batch？**

已经得到了采样概率weight，那是不是意味着每一个token都按照一定的采样概率来选cell()呢？训练器到底怎么执行？

真实过程更像：

```text
200 个 target weights
        ↓
构造一定长度的数据 mixing block
        ↓
block 中决定各 cell 消费多少
        ↓
每个 cell 内继续读取 dataset stream
        ↓
tokenize / sequence
        ↓
形成 batch
        ↓
training
```
