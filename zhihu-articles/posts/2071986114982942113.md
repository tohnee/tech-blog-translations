## 很多人嫌 DeepSeek Harness 太重，但 Pi 的作者却开始反思自己了

DeepSeek Harness 发布之后，一个很有意思的分裂出现了。

一边是大量开发者吐槽：

**太重、太复杂、太工程化。**

甚至有人把它形容成：

> 开发者会喜欢，但普通人永远不会喜欢。

另一边，却是 Pi 阵营里非常关键的一个人——Flask 作者、Pi 背后的 Earendil 联合创始人 **Armin Ronacher**，连续几条表达了完全不同的态度。

![](https://pic3.zhimg.com/v2-1d8a3818387717fb57be24d4b43802fa_r.jpg)

他说自己很喜欢 DeepSeek Harness 里的很多设计。

更重要的是：

**它让他开始重新思考 Pi 自己的 Harness 架构。**

这件事其实比 DeepSeek Harness 到底有多少 GitHub Star 更值得关注。

因为 Pi 和 DeepSeek Harness，刚好代表了 Agent 工程里两条几乎相反的路线。

---

## Pi：把 Harness 做到尽可能不存在

Pi 的哲学一直很明确：

**Harness 越薄越好。**

默认情况下，Pi 给模型的核心工具甚至只有：

`read / write / edit / bash`

其他能力通过 extension、skill、prompt package 再往上加。Pi 也支持 runtime extension、session state、RPC 等机制，但整个产品刻意维持一个非常小的核心。

![](https://pic3.zhimg.com/v2-00758d2d8df239fa509c99265c2088b8_r.jpg)
*今天 Pi 发布的技术博客，讲述他们的compaction机制，极简到极致。*

Armin 自己此前形容 Pi 时，甚至强调过一种非常激进的思路：

**不要提前替 Agent 设计太多能力，让 Agent 自己写能力。**

也就是说，与其给 Agent 搭一个巨大工作台，不如给它 Bash 和少量原语，让模型自己组合。

这也是为什么很多人喜欢 Pi。

它有一种很强的 Unix 味道：

> 提供少量强原语，把复杂性留给组合。

这套思路在模型越来越聪明的时候尤其诱人。

因为一个自然推论是：

**模型越强，Harness 理论上应该越薄。**

---

## DeepSeek 却几乎反着来

DeepSeek Harness 的核心口号也是一句很 Unix 的话：

**Everything is a Plugin。**

但落地方式完全不同。

在 DSH 里，模型、Tool、Skill、Session、Sandbox、Storage、Agent Loop、Orchestration，甚至 UI，本身都可以是插件。

Cordis Kernel 自己只负责插件生命周期、依赖关系和组合，不直接承载 Agent 能力。

所以你甚至可以：

换模型；

- 换 Tool System；
- 换 Context 管理方式；
- 换 Agent Loop；
- 换 Session；
- 换 Subagent 调度逻辑；

甚至把整套 Agent 重新拼一遍。

DeepSeek 还直接提供了 Standard、PTC、Minimal、Creation 等不同模式。

其中 Creation Mode 最有意思：

**Agent 可以观察自己的 Runtime，实验插件，然后构造新的 Agent Preset。**

换句话说：

Pi 更像是在说：

**“少给 Agent 东西，它自己会想办法。”**

DeepSeek Harness 则是在说：

**“把 Agent 的一切拆成可操作对象，让 Agent 连自己的 Harness 都能改。”**

这两个方向表面上相反，实际上却都指向同一个目标：

### Self-modifying Agent。

---

## 为什么很多人第一眼会讨厌 DSH？

因为从“写代码工具”的视角看，DeepSeek Harness 确实很容易显得过度设计。

仓库里不是几十个简单模块，而是完整的 Plugin Runtime、Service、Event、Scope、Session Projection、Preset、Workflow、Subagent、Compaction、Trajectory、UI Plugin……

连 TypeScript module graph 都已经相当庞大。

如果你的需求只是：

> “帮我改一下这个 repo。”

那确实很容易产生一个问题：

**为了调用 Bash，为什么我要理解一个操作系统？**

而且“Everything is a Plugin”本身并不是免费午餐。

已经有开发者在官方 Discussion 里提出了很现实的问题：

当所有东西都能插件化以后，就会开始出现 Tool 名称冲突、Service 注入顺序、Plugin 修改 Session 行为、共享 Context 带来的耦合等问题。

这其实是任何大型插件生态最终都会遇到的问题：

**可扩展性提高，系统熵也会提高。**

所以批评 DSH “too engineered”，并没有错。

甚至 DeepSeek 自己都明确提醒：

这是 **Developer Preview**，会有大量 rough edges，并且未来可能存在 compatibility-breaking changes。项目作者也在 Hacker News 上专门强调了这一点。

因此现在把 DSH 当“Claude Code 替代品”去评价，本身可能就用错了尺子。

---

## 但 Armin 为什么反而觉得它有意思？

关键在一个词：

## Explicit seams。

也就是：

**明确的系统切面。**

今天 Agent 最大的问题之一，是大量重要行为实际上隐藏在 Harness 内部：

- Context 怎么拼？
- 什么时候 compaction？
- Tool Result 怎么进入下一轮？
- Session 如何恢复？
- Subagent 的结果怎么注入？
- 权限判断在哪里发生？
- Agent Loop 什么情况下结束？

这些东西看起来都是工程细节。

但模型能力越来越接近之后，真正影响 Agent 表现的，恰恰越来越是这些工程细节。

今年一系列 Harness 研究已经开始反复说明这件事。

例如 Agentic Harness Engineering 的实验里，通过持续修改 Tool、Middleware、Memory 等 Harness 组件，可以显著改变同一个模型在 benchmark 上的结果；而且消融实验显示，真正贡献最大的并不只是 System Prompt，而是工具、中间件和长期记忆结构。

当然，另一项 7 月份的研究也给出了反面提醒：

自动 Harness Evolution 很容易在 benchmark 上过拟合，部分提升可能只是来自更多 test-time search，而不是发现了真正可泛化的 Harness。

这两篇论文放在一起，反而说明了一个很关键的问题：

### Harness 已经开始变成一个可以被“优化”的对象。

而 DeepSeek Harness 真正激进的地方，就是：

**它把 Harness 本身彻底对象化了。**

Agent Loop 不再是框架内部的一段 if/while。

Context 不再只是某个隐藏函数。

Storage、Session、Tool、Memory 都成为明确组件。

这就意味着未来可以：

- 观察它；
- 替换它；
- 实验它；
- A/B Test 它；
- 甚至让另一个 Agent 修改它。

---

## 我觉得这才是 DSH 最值得看的地方

很多人现在把 DeepSeek Harness 理解成：

> DeepSeek 做了一个自己的 Claude Code。

我认为这个理解明显低估它了。

DeepSeek 真正想开放的，很可能并不是一个 Coding Agent。

**而是：Agent Runtime 的控制权。**

模型时代，大家竞争的是：

**谁拥有最好的 Model。**

Agent 时代开始以后，竞争逐渐变成：

**Model + Harness。**

再往后一步：

**谁拥有可以持续演化 Harness 的 Runtime。**

这三层完全不是一回事。

---

## DeepSeek Harness 真正有野心的是第三层

尤其值得注意的是它的 Trajectory 设计。

DSH 会把模型看到的 System Prompt、Tool Call、Tool Result、Subagent 调度、Context Injection 等内容持续记录进 append-only Session Log。

同一份事件流可以用于：

- 恢复、
- 分叉、
- Replay、
- Trajectory 分析。

这看起来只是 Observability。

但如果往下一步推演：

Trajectory + Evaluator + Harness Editor

其实就形成了：

**Agent Harness 的自我优化闭环。**

最近 Harness-R1 做的事情已经非常接近这个方向：

收集 Agent Failure Trajectory，让另一个 Harness Engineer Agent 修改实际 Runtime，再重新运行任务，用结果作为反馈。

于是你再回头看 DSH：

Everything is a Plugin

- 完整 Trajectory
- Creation Mode
- Runtime inspection

它们突然就不只是四个独立 feature。

而像是在为同一个未来做准备：

## Harness 自己开始成为 Agent 的操作对象。

---

## Pi 和 DSH，最后可能反而殊途同归

所以 Armin 的反应特别有意思。

因为 Pi 和 DSH 看起来是一场：

### 极简主义 vs 工程主义

Pi：**Four tools are enough.**

DSH：**Everything is a plugin.**

但真正往未来走，两者可能会在一个地方汇合：

### Agent 应该能够改造自己的环境。

Pi 的路径是：

给模型极少的 primitive，让它自己写扩展。

DSH 的路径是：

把 Runtime 全部拆成显式组件，让模型修改组件。

Pi 是：**从下往上生长。**

DSH 是：**先搭出一套可重构系统，再允许 Agent 重构它。**

这可能也是为什么一个如此推崇 Pi 极简路线的人，在看到 DSH 后，并没有简单说：

“这玩意太复杂了。”

而是说：

**这让我重新思考我们在 Pi 中怎么做 Harness。**

---

## 所以现在争论 DSH “好不好用”，可能还太早

它当然不好用。

至少现在还是一个明确标注为 Developer Preview 的项目。

它当然也很重。

而且插件化架构未来一定会面对依赖、隔离、版本兼容、调试复杂度等现实问题。

但这反而不是最重要的问题。

真正值得观察的是：

**DeepSeek 把 Harness 从“Agent 背后的工程代码”，第一次非常彻底地变成了“Agent 可以操作的系统”。**

如果这个方向成立，那么未来我们调优 Agent 的方式，也许会发生很大变化。

以前是：

Prompt Engineering。

后来是：

Context Engineering。

现在开始出现：

Harness Engineering。

而再下一步可能会是：

## Harness Evolution。

也就是说，人类不再精心设计唯一正确的 Agent 架构。

我们设计的是：

**一套允许 Agent 自己寻找更好架构的元架构。**

从这个角度看，DeepSeek Harness 最大的价值，也许根本不是今天能不能替代 Claude Code。

而是它提出了一个非常激进的问题：

> **如果未来 Agent 足够聪明，我们还应该替它把 Harness 设计死吗？**

Pi 的答案可能是：

**少设计一点。**

DeepSeek 的答案则更像是：

**可以设计，但一切都必须允许被替换。**

这两个答案，我现在都不敢说谁一定对。

但可以确定的是：

Agent 下一轮真正激烈的竞争，可能已经开始从模型参数，转向模型外面的这层东西了。
