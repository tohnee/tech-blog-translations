> 一句话：**RAG = 四件套，其中只有「LLM」这一件在云上** —— 前三件在你自己的机器上跑，断网也能入库和检索。<br>

---

## ① 先说结论

先说结论，再展开。

大多数文章讲 RAG 会从"检索增强生成"这四个字开始拆： 「检索」是先去数据库捞几段相关的资料，「增强」是把资料塞进 prompt， 「生成」是让大模型基于这些资料写答案。

**但这个拆法有个问题**：它没告诉你**检索那一步到底是怎么"相关"的**。 于是你脑子里剩下一团模糊的印象："好像是把文字变成向量，然后比距离？"

我更愿意用**四件套**来讲。因为 RAG 的每一个坑， 都能对应到"四件套里的哪一件配错了"。

---

## ② 一个反直觉的结论

> **RAG 的四件套里，只有一件需要联网、需要花钱。**<br>

| 组件 | 干什么 | 在哪跑 | 要钱吗 |
| --- | --- | --- | --- |
| ① AI 编排 | 把 ②③④ 串起来的胶水 | 你的 JVM | ❌ |
| ② LLM | 生成答案的大脑 | 云端 API | ✅ 只有它要钱 |
| ③ Embedding | 文本 → 向量 | 你的 JVM（本地模型） | ❌ |
| ④ 向量存储 | 存向量 + 快速 Top-K | 你的 JVM | ❌ |

**这个分工是故意的，而且带来两个很实用的性质**：

**性质一：断网也能入库和检索。** 关掉网，你的知识库照样能用 —— 只有最后"生成答案"那一步会失败。 做内部知识库的时候，这意味着一半的功能不受网络影响。

**性质二：换 LLM 几乎零成本。** ② 是唯一有"外部依赖"属性的组件，所以换厂商 = 改 yml 三个字段，**数据和向量一动不动**。 （我实测过切 6 款模型，全程没重新入过库。）

> 📌 而 ③ Embedding 是**最敏感**的那一件 —— 换它不像换 LLM 那样零成本， **整个知识库的向量都得重算**。原因见 §④。<br>

## ③ 跑一遍看看

### 3.1 完整流程图：入库和检索是两条路

![](https://pica.zhimg.com/v2-9298ffe1c97ff780d84f7bcd97ac4d68_r.jpg)

**注意两个地方**（大多数文章不讲，但恰恰是坑最多的地方）：

| # | 容易错的地方 | 错了我会怎样 |
| --- | --- | --- |
| 1 | 入库和检索必须用同一个 Embedding 模型 | 两套坐标系混用，相似度算出来是噪声，而且不报错 |
| 2 | 切片要一致 | 问句和片段粒度不匹配，检索质量断崖式下降 |

### 3.2 四步分别是什么

**第 ① 步：切片（Chunking）**

把一篇长文切成一段段。参数就两个：

```text
document:
  chunk-size: 300        # 每段多少字
  chunk-overlap: 50      # 相邻两段重叠多少字

```

**为什么要重叠**：一句话被切在中间，两段都变成半句，检索出来模型也读不懂。 重叠 50 字是为了让边界信息在两段里都出现。

**第 ② 步：Embedding（文本 → 向量）**

把一段文本变成**固定长度的数字数组**（我用的是 512 维），让"语义相近"变成"方向接近"：

```text
score = cos(问题向量, 文档向量)

```

这不是玄学，是**训练出来的** —— 模型见过海量"意思相近的句子对"， 学会把它们放在相近的位置（对比学习：正样本拉近、难负样本推开）。

**第 ③ 步：存 + 检索**

向量存起来（我用的是进程内 + JSON 持久化），提问时把问题也变成向量， **算一遍余弦相似度，取 Top-K**（我默认 3 段）。

**第 ④ 步：拼 prompt + 生成**

```text
【上下文】
[来源 1] score=0.9234
LangChain4j 是 LangChain 在 Java 生态的官方实现……
[来源 2] score=0.8871
……

【用户问题】
什么是 LangChain4j？

请基于上面的资料回答。

```

### 3.3 30 行 Java，把骨架搭出来

**这是完整的最小 RAG**（不含 Spring 配置）：

```text
// ① 编排：三个 Bean
ChatModel         chatModel   = OpenAiChatModel.builder()
        .apiKey(System.getenv("DEEPSEEK_API_KEY"))
        .baseUrl("https://api.deepseek.com/v1")
        .modelName("deepseek-chat")
        .build();

EmbeddingModel    embedding   = new BgeSmallZhEmbeddingModel();  // 512 维，本地

EmbeddingStore<TextSegment> store = new InMemoryEmbeddingStore<>();

// ② 入库：切片 → 向量 → 存
List<TextSegment> segments = DocumentSplitters.recursive(300, 50)
        .split(Document.from("LangChain4j 是 LangChain 在 Java 生态的官方实现，"
                + "提供统一的 ChatModel / EmbeddingModel / VectorStore 接口。"));

store.addAll(embedding.embedAll(segments).content(), segments);

// ③ 检索：问题 → 向量 → Top-K
Embedding queryVector = embedding.embed("什么是 LangChain4j？").content();
List<EmbeddingMatch<TextSegment>> hits =
        store.search(EmbeddingSearchRequest.builder()
                .queryEmbedding(queryVector)
                .maxResults(3)          // Top-K
                .build()).matches();

// ④ 生成：把片段拼进 prompt
String context = hits.stream()
        .map(h -> h.embedded().text())
        .collect(Collectors.joining("\n\n"));

String answer = chatModel.chat("""
        请基于下面的资料回答问题，资料里没有的不要编。

        【资料】
        %s

        【问题】
        什么是 LangChain4j？
        """.formatted(context));

```

**就这么点东西。** 你项目里那些"高级特性"——多轮对话、流式输出、Agent 调工具、 评估体系 —— **全是在这 30 行上做扩展**。

**三行是重点**：

```text
// 入库和检索，用的是同一个 embedding 对象
store.addAll(embedding.embedAll(segments).content(), segments);
Embedding queryVector = embedding.embed("什么是 LangChain4j？").content();

```

**换 Embedding 模型 = 换掉这两个对象，但旧向量还在库里** → 见 §④。

### 3.4 数据长什么样

向量库就是个普通 JSON 文件：

```text
{
  "entries": [
    {
      "id": "4c4967d8-470f-48a4-a498-2779b83a1a67",
      "embedding": { "vector": [0.0231, -0.1187, ...] },
      "embedded": {
        "text": "LangChain4j 是 LangChain 在 Java 生态的官方实现……",
        "metadata": { "metadata": { "index": "0", "source": "langchain4j-intro" } }
      }
    }
  ]
}

```

**就这些。** 没有索引文件、没有特殊格式 —— 我的知识库 16 段内容，磁盘上一个 79 KB 的 JSON。

> 💡 **这带来一个很实用的性质**：知识库是**纯文本 + 数字**， 你可以直接打开看、直接改、直接备份。不像某些向量库， 你根本不知道它存了什么。<br>

## ④ 踩过的坑

### 坑 1：换了 Embedding 模型，检索 score 全是 0

**现象**：我把 BGE 换成另一个模型（维度从 512 变成 1024），重新入库，重新提问 —— **所有检索结果的 score 都是 0**，或者说"什么都不相关"。

**根因**：旧库里的向量是 512 维的，新模型产生 1024 维的向量。 **两套向量根本不在同一个空间里**，拿 1024 维去比 512 维 —— 数学上无意义。

更糟的是：**它不报错**。程序 happily 地返回了结果，只是每个都是 0 分。

**解法**：

> **换 Embedding 模型，必须先清空向量库，再重新入库。**<br>

这条我在代码注释里也写死了：

```text
/**
 * ⚠️ 入库和检索用的是同一个 embeddingModel 字段，这是刻意的：
 * 保证入库和检索用同一个 Embedding 模型（同一套坐标系）。
 * 换 Embedding 模型时务必【先清空旧知识库】，
 * 否则新旧向量不在一个空间里，相似度算出来是噪声，而且【不报错】。
 */

```

**怎么快速确认自己踩了这个坑**：

```text
# 看两边的维度对不对得上
curl -s -X POST http://localhost:8081/api/rag/search -d '{"question":"test","topK":1}'
# 全部 score 相同且接近 0 → 八成是坐标系混了

```

### 坑 2：改了切片大小，检索效果一点没变

**现象**：`chunk-size` 从 300 改成 100，重新入库、重新提问 —— **参数没生效**。

**根因**：`@Value` 的键名和 yml 里的对不上（`vector.lucene.chunk-size` vs `document.chunk-size`）， **而且默认值恰好也是 300**，所以完全看不出来。

**解法**：改键名；**更重要的是**，以后改配置要**改成明显不同的值**并看日志确认。

> 📌 完整的排查过程见同系列第 12 篇《配置改了不生效，而且不报错》。<br>

### 坑 3：`minScore(0.7)` 在我这儿形同虚设

**现象**：我以为"相似度低于 0.7 的片段就别给模型了"，结果**过滤没起作用**。

**根因**：不同向量库的 **score 刻度不一样**：

| 向量库 | score 是什么 | 范围 |
| --- | --- | --- |
| InMemoryEmbeddingStore（我用） | (cos+1)/2 | [0, 1] |
| Lucene 社区模块 | 原始 BM25 + KNN 混合分 | 无上界（常见 5~30） |

**在 Lucene 上设 `minScore(0.7)` = 几乎全放行** —— 因为 Lucene 的分是 5~30，这个阈值根本够不着。

**而且你也别想「反过来」救。** LangChain4j 的 `EmbeddingSearchRequest` 在**构造那一刻**就校验：

```text
this.minScore = ensureBetween(getOrDefault(minScore, 0.0), 0.0, 1.0, "minScore");

```

**传 10.0 会直接抛 `IllegalArgumentException`，根本走不到过滤那一步。** 换句话说，`minScore` 这个旋钮只能在 `[0,1]` 里拧 —— 而不同向量库的 score 刻度不同， **这个旋钮在某些库上压根不够用**。

**解法**：换向量库时，**所有跟阈值有关的参数都要重新校准**。 我用 InMemory 的原因之一就是 `score = (cos+1)/2` 这个刻度**可解释**—— 0.7 就是"70% 相关"，符合直觉。

> 完整的 6 处差异见同系列第 3 篇《做 RAG 一定要上 Milvus？我把源码扒了一遍》。<br>

### 坑 4：MiniMax 的 embedding 接口调不通

**现象**：调 MiniMax 的 embedding 接口，返回：

```text
{"vectors": null, "status_code": 2013, "status_msg": "invalid param"}

```

**根因**：MiniMax 的 embedding 接口协议和 OpenAI 不兼容，而主流客户端按 OpenAI 协议解析。

**解法**：**Embedding 用本地模型**（BGE 系列，权重直接打进 jar，90 MB，CPU 单条几十毫秒）。

这一步反而让整个项目变简单了：

|  | 用云端 Embedding | 用本地 Embedding |
| --- | --- | --- |
| 成本 | 每次入库 + 每次检索都花钱 | 0 元 |
| 网络 | 入库检索都要联网 | 断网也能用 |
| 数据安全 | 文档要发出去 | 数据不出门 |
| 速度 | 网络往返 | 本地几十毫秒 |

## ⑤ 什么场景别用它

RAG 不是万能的，这些场景**别上 RAG**：

| 场景 | 为什么不用 RAG |
| --- | --- |
| 问题答案是固定的（"退款怎么申请"） | 写死 or 查 FAQ 表更快更准，RAG 是杀鸡用牛刀 |
| 需要精确计算（"帮我算下总金额"） | RAG 只会找到相关片段，算不对 —— 这要用工具/代码 |
| 知识库很小（< 50 条） | 全塞进 prompt 都行，还不用维护向量库 |
| 实时性要求极高（毫秒级） | 向量化 + 检索有延迟，不如直接查 |
| 知识需要频繁更新 | 每次改都要重新入库，不如换个方案 |

**RAG 适合的场景有一个共同特征**：

> **答案需要从"大量、相对静态、会变"的文本里找依据。**<br>

比如：内部制度文档、产品手册、历史工单、技术 wiki。

**另一个边界**（很多人踩）：

> **RAG 提升的是"有据可依"，不是"必然正确"。** 检索到的片段可能是**过时的**、**不相关的**、或者**互相矛盾**的。 模型基于错资料生成，答案就是错的 —— 而且它答得很自信。<br>

所以我给自己的项目加了**自检回路**：答案出来后再让模型审一遍 "这个结论有片段支撑吗"。它是**兜底**，不是保证。

### 先说清楚：我这套是 MVP

这句话我想放在前面讲，因为后面的选型和边界都建立在这个前提上。

**我这个 RAG 的全部家当**：一个 Spring Boot 进程、一份 90MB 的本地 embedding 模型、一个 JSON 文件。一台最低配的机器。

它能回答「值不值得做 RAG」，回答不了「你的业务能不能扛住」。

真上企业级，这四个环节逐个都要换：

| 环节 | 我的 MVP | 企业级常见做法 | 什么时候该换 |
| --- | --- | --- | --- |
| Embedding | 本地 bge-small | 云厂商 / 自建 BGE-M3 | 语种多、文档长、质量不够 |
| 向量库 | 一个 JSON 文件 | Milvus / pgvector | 十万条以上、要多实例 |
| LLM | 调一家 API | 多模型路由 + 降级 | 有 SLA、账单开始疼 |
| 切片 | 固定 300/50 | 按文档结构切 | 文档格式杂、效果不好 |

**换的顺序也有讲究**：先换向量库（最影响性能），再换 embedding（最影响质量），LLM 放最后 —— 它最好换，也最贵。
