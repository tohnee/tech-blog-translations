> 本文基于 3FS 源码分析，结合在 GKE A4 (NVIDIA B200) 集群上使用 SR-IOV RDMA VF 的实际部署经验，深入剖析其架构设计、数据路径、一致性语义和并发控制机制。

### 为什么关注 3FS

在大规模 GPU 训练场景中，模型 checkpoint 的读写、训练数据的加载，都对分布式文件系统提出了极高的吞吐和延迟要求。3FS 的核心设计目标是：**让数据面（read/write）通过 RDMA 直连 Storage，绕过元数据服务器**，将元数据操作限制在 open/close/sync 等低频路径上。

这个设计带来了极高的数据吞吐，但也引入了独特的一致性语义。本文将从一次实际的 “边写边读为什么看到旧数据” 的问题出发，逐层拆解 3FS 的实现。

### 一、架构概览

3FS 由四个核心组件构成：

```text
┌─────────────────────────────────────────────────────────┐
│                      用户进程                            │
│                 open / read / write / close             │
└───────────────────────┬─────────────────────────────────┘
                        │
┌───────────────────────▼─────────────────────────────────┐
│              Linux 内核 (Page Cache + FUSE 驱动)         │
└───────────────────────┬─────────────────────────────────┘
                        │
┌───────────────────────▼─────────────────────────────────┐
│           hf3fs_fuse_main (FUSE Daemon, 用户态)          │
│                                                         │
│     MetaClient (TCP)          StorageClient (RDMA)      │
│         │                            │                  │
└─────────┼────────────────────────────┼──────────────────┘
          │                            │
    ┌─────▼──────┐              ┌──────▼──────┐
    │ Meta Server │──── RDMA ──▶│   Storage   │
    │ (meta_main) │             │   Server    │
    └─────┬──────┘              └─────────────┘
          │
    ┌─────▼──────┐
    │FoundationDB│
    │  (元数据)   │
    └────────────┘
```

- **FUSE Daemon** (`hf3fs_fuse_main`)：用户态文件系统进程，接收内核 FUSE 请求
- **Meta Server** (`meta_main`)：元数据服务，管理 inode、目录树、文件 session
- **Storage Server** (`storage_main`)：数据存储服务，管理 chunk 的读写
- **FoundationDB**：元数据的持久化层，提供事务语义

关键设计原则：**数据面和控制面彻底分离。** FUSE Daemon 拥有两个独立的客户端——MetaClient 走 TCP 处理元数据，StorageClient 走 RDMA 处理数据 I/O。

几个值得注意的部署细节：

- **Fuse + Meta 合并部署在 Node-3**：两者共享同一个 RDMA VF（原因见第八节）

### 二、每个文件操作到底走了什么路径

### 2.1 open：只读 FDB，不碰 Storage

```text
open("/mnt/3fs/a/b/file.txt", flags)
  │
  内核 FUSE 路径解析 (lookup):
    lookup(root, "a")       ──TCP──▶ Meta ──▶ FDB: DirEntry → InodeId=100
    lookup(100, "b")        ──TCP──▶ Meta ──▶ FDB: DirEntry → InodeId=200
    lookup(200, "file.txt") ──TCP──▶ Meta ──▶ FDB: DirEntry → InodeId=300
  │
  内核已缓存 entry_timeout(默认30s) 内的 lookup 结果，重复访问不再穿透
  │
  Fuse ──TCP──▶ Meta: OpenOp(InodeId=300)
                  │
                  └──▶ FDB: snapshotGet(packKey(300))
                  └──▶ 返回 Inode {length, layout, truncateVer, ...}
                  └──▶ 写模式: 创建 FileSession
```

***meta和fuse部署在同一个pod，所以使用localhost TCP***

`open` 分两个阶段：先由内核 FUSE 驱动逐级 `lookup` 将路径解析为 InodeId（每级都会查 FDB 的 DirEntry），再通过 `OpenOp` 从 FDB 加载 Inode 元数据。整个过程**不调用 Storage**。这意味着 `open` 拿到的 `length` 是上一次 `sync/close` 时写入 FDB 的值，可能是过时的。

这是一个重要的设计决策：为了 open 的低延迟，牺牲了 length 的实时性。

> **源码参考**：`OpenOp::run()` (Open.cc:44) → `Inode::snapshotLoad()` (Inode.cc:86) → FDB `snapshotGet`

### 2.2 read：RDMA 直连 Storage，不经过 Meta

```text
read(fd, buf, size)
  │
  内核 Page Cache 命中？ → 直接返回（不经过 FUSE Daemon）
  │ miss
  FUSE Daemon:
    1. flush write buffer（如果有未刷数据）
    2. PioV::executeRead ──RDMA──▶ Storage
    3. 返回数据
```

read 是最简洁的路径——**不调用 Meta，不查询 FDB**。FUSE Daemon 直接通过 RDMA 从 Storage 读取 chunk 数据。

唯一的附加逻辑是：如果当前 inode 有未刷写的 write buffer，read 会先将其 flush 到 Storage，确保同进程内的 read-after-write 一致性。

```text
// FuseOps.cc:1482-1493
std::unique_lock lock(pi->wbMtx);
if (wb->len) {
    flushBuf(req, pi, wb->off, *wb->memh, wb->len, true);
    wb->len = 0;
}
```

> **源码参考**：`hf3fs_read()` (FuseOps.cc:1473) → `PioV::executeRead()` (PioV.cc:132)

### 2.3 write：数据到 Storage，元数据不动

```text
write(fd, data, size)
  │
  O_DIRECT → 立即 RDMA 写 Storage
  │
  非 O_DIRECT → 写入 per-inode write buffer (1MB)
                 buffer 满 / offset 不连续 / fsync 时 → flush 到 Storage
  │
  更新本地 DynamicAttr.hintLength（不发送给 Meta）
```

write 只负责把数据送到 Storage，**不更新 FDB 中的 length**。这意味着写入后、sync 前，FDB 里的文件大小是旧的。

这个设计的意义在于：write 是热路径，每秒可能调用数万次。如果每次 write 都更新 FDB，元数据服务会成为瓶颈。3FS 选择将 length 更新延迟到 sync/close。

> **源码参考**：`hf3fs_write()` (FuseOps.cc:1552)，`finishWrite()` (FuseOps.cc:2655) 更新 `hintLength`

### 2.4 flush / fsync：数据和元数据的汇合点

```text
fsync(fd)
  │
  Step 1: flushBuf() ──RDMA──▶ Storage    （刷写 write buffer）
  │
  Step 2: sync() ──TCP──▶ Meta
                     │
                     ├── BatchedOp 处理 SyncReq
                     ├── mergeHint (取 MAX length)
                     ├── 可能 queryLastChunk ──RDMA──▶ Storage (验证真实 length)
                     └── FDB: 更新 Inode.length
```

**这是 length 真正持久化到 FDB 的时刻。** FUSE Daemon 先把脏数据刷到 Storage，再告诉 Meta “我写了这么多”。Meta 可能会去 Storage 验证实际长度（通过 `queryLastChunk`），然后将验证后的 length 写入 FDB。

为什么 Meta 不信任 FUSE 报告的 length？因为 FUSE 可能崩溃、可能报告不准确的值。Meta 通过直接询问 Storage 来确保元数据的正确性。

> **源码参考**：`flushAndSync()` (FuseOps.cc:593)，`BatchedOp::queryLength()` (BatchOperation.cc:260)

### 2.5 close：收尾，不传数据

```text
close(fd)
  │
  Fuse ──TCP──▶ Meta: CloseOp
                  │
                  ├── 可能 queryLastChunk（同 sync）
                  ├── FDB: 更新 length, 删除 FileSession
                  └── 失败则后台重试（指数退避）
```

close 不传输数据（数据在之前的 write/flush 已经到了 Storage），只做元数据收尾。如果 close RPC 失败，FUSE Daemon 会通过 `bgCloser_` 在后台无限重试，防止 FileSession 泄露。

> **源码参考**：`hf3fs_release()` (FuseOps.cc:1737)，后台重试 (MetaClient.cc:220)

### 三、Meta 为什么需要连接 Storage

一个常见的误解是 “Meta 只管元数据，不碰数据”。实际上 Meta 需要访问 Storage，但不是为了读写用户数据，而是为了**验证和管理**：

操作 RPC 触发时机验证文件真实长度 queryLastChunksync / close 删除文件数据 removeChunks 文件删除后的 GC 截断最后一个 chunktruncateChunksftruncate 查询存储空间

| 操作 | RPC | 触发时机 |
| --- | --- | --- |
| 验证文件真实长度 | queryLastChunk | sync / close |
| 删除文件数据 | removeChunks | 文件删除后的 GC |
| 截断最后一个 chunk | truncateChunks | ftruncate |
| 查询存储空间 | querySpaceInfo | statfs，后台每 200ms 轮询 |

querySpaceInfostatfs，后台每 200ms 轮询

`queryLastChunk` 是最关键的一个——Meta 去 Storage 询问 “这个文件的最后一个 chunk 实际有多长”，用来校正 FDB 中的 length。这是 3FS 对 “FUSE 可能不可信” 的防御性设计。

### 四、一致性模型：Close-to-Open

3FS 的一致性模型类似 NFS v3 的 close-to-open consistency：**只有 writer 执行 sync 或 close 之后，其他 reader 重新 open 才能看到完整的新数据。**

### 4.1 同 Pod 内：强一致

```text
Thread A: write(data)     → 数据进入 write buffer
Thread B: read(same range) → 先 flush buffer，再从 Storage 读
                           → 看到最新数据 ✓
```

同一个 FUSE Daemon 内，read 前会自动 flush write buffer，保证 read-after-write 一致性。

### 4.2 跨 Pod：最终一致（依赖 sync/close）

```text
Pod A (Writer)                    Pod B (Reader)
──────────────                    ──────────────
write(5000 bytes)
  → Storage 有数据
  → FDB length 还是 0
                                  open() → Meta → FDB: length=0
                                  read() → 不知道有 5000 字节
sync()
  → Meta 更新 FDB: length=5000
                                  close()
                                  open() → Meta → FDB: length=5000 ✓
                                  read() → 读到 5000 字节 ✓
```

Writer 未 sync 时，Reader 看到的 length 是旧的。即使 Storage 上已经有了新数据，Reader 也不知道该读多少。

### 4.3 覆盖写（长度不变）的特殊情况

如果 Writer 只是覆盖已有数据而不改变文件大小，情况更微妙——**FDB 中的 length 始终不变，Meta 完全不参与**。数据可见性纯粹取决于：

1. **Write buffer**：同 Pod 的 Reader 会先 flush，看到新数据；跨 Pod 的 Reader 看不到别人 buffer 里的数据
2. **Storage chunk 版本**：Storage commit 前，chunk 处于 DIRTY 状态，Reader 读到的是旧的 committed 数据
3. **内核 Page Cache**：即使 Storage 已经 commit 了新数据，Reader 的内核可能还缓存着旧数据

第三层是最容易被忽视的——下一节详细讨论。

### 五、内核 Page Cache：跨 Pod 一致性的最大隐患

3FS **没有自己的用户态读缓存**。配置项 `enable_read_cache`（默认 `true`）实际控制的是 FUSE 的 `direct_io` flag——告诉 Linux 内核 “你可以缓存从 FUSE 读到的数据”。

当 `enable_read_cache=true` 时：

```text
Pod B 第一次 read:
  用户进程 → 内核: Page Cache miss
           → FUSE 驱动 → hf3fs_fuse_main → RDMA → Storage
           → 返回 「hello」
           → 内核将 「hello」 存入 Page Cache

Pod A 覆盖写 「world」 → Storage commit ✓

Pod B 第二次 read（同一 offset）:
  用户进程 → 内核: Page Cache 命中！
           → 直接返回 「hello」 ❌
           → 根本不经过 FUSE Daemon
           → Storage 上明明是 「world」
```

内核认为自己缓存的数据仍然有效，直接返回给用户进程。FUSE Daemon 和 Storage 都不知道有人在读。每个 Pod 有独立的内核 Page Cache，Pod A 写入的新数据无法通知 Pod B 的内核失效缓存。

这与本地文件系统（如 ext4）不同——ext4 中所有进程共享同一份 Page Cache，write 会自动更新缓存。但在分布式场景下，缓存分散在各个节点，没有失效通知机制。

### 何时用 `enable_read_cache=true`

- 模型权重加载：只读场景，读一次缓存住，后续访问内存速度
- Checkpoint 读取：写完关闭后再读，close-to-open 语义足够

### 何时用 `enable_read_cache=false`

- 多 Pod 并发读写同一文件：必须每次穿透到 Storage

### 六、USRBIO：彻底绕过内核，告别 Page Cache 问题

上一节讨论的 Page Cache 问题，根源在于 I/O 路径必须经过 Linux 内核的 FUSE 驱动。3FS 提供了一个更激进的解决方案——**USRBIO（User Space Ring Based IO）**，让用户进程与 FUSE Daemon 之间通过共享内存直接通信，**完全绕过内核**。

### 传统 FUSE 路径 vs USRBIO 路径

```text
传统 FUSE 路径:
  用户进程 → syscall → 内核 FUSE 驱动 → [Page Cache] → FUSE Daemon → RDMA → Storage
                              ↑
                        Page Cache 在这里
                        内核可能直接返回缓存数据
                        不经过 FUSE Daemon

USRBIO 路径:
  用户进程 → 共享内存 (Iov + Ior) → FUSE Daemon → RDMA → Storage
                 ↑
           不经过内核
           没有 Page Cache
           零拷贝
```

USRBIO 绕过了内核 FUSE 驱动，也就绕过了 Page Cache。每次读操作都会直达 Storage，不存在 “内核缓存命中返回旧数据” 的问题。

### 核心概念

USRBIO 的设计类似 Linux 的 `io_uring`，由两个核心组件构成：

- **Iov（I/O Vector）**：一块在 `/dev/shm` 中分配的共享内存区域，同时在用户进程和 FUSE Daemon 之间共享。FUSE Daemon 负责将这块内存注册到 InfiniBand（IB MR），使其可以直接参与 RDMA 传输。所有读写数据都通过 Iov 传递，实现**零拷贝**。
- **Ior（I/O Ring）**：一个共享内存环形队列，用于用户进程与 FUSE Daemon 之间的请求提交和完成通知。用户进程向 Ior 写入 I/O 请求，FUSE Daemon 从 Ior 读取并执行，完成后将结果写回。

```text
用户进程                              FUSE Daemon
  │                                      │
  │  1. 将数据写入 Iov (共享内存)           │
  │  2. 在 Ior 提交 I/O 请求               │
  │──────── Ior (共享内存环) ────────────▶ │
  │                                      │  3. 从 Ior 取出请求
  │                                      │  4. 通过 RDMA 读写 Storage
  │                                      │     (Iov 已注册为 IB MR，零拷贝)
  │◀──────── Ior (完成队列) ─────────────  │
  │  5. 从 Ior 获取完成结果                 │
  │  6. 从 Iov 读取数据                    │
```

### 使用示例

```text
#include <hf3fs_usrbio.h>

// 创建共享内存数据区 (Iov)
struct hf3fs_iov iov;
hf3fs_iovcreate(&iov, 「/mnt/3fs」, 32 * 1024 * 1024, 0, -1);  // 32MB

// 创建提交环 (Ior)
struct hf3fs_ior ior;
hf3fs_iorcreate4(&ior, 「/mnt/3fs」, 1024, true, 0, 0, -1, 0);

// 注册 fd（内核 fd 与 FUSE inode 的映射）
int fd = open(「/mnt/3fs/data.bin」, O_RDONLY);
hf3fs_reg_fd(fd, 0);

// 提交读请求
hf3fs_prep_io(&ior, &iov, true, iov.base, fd, 0, 4096, NULL);
hf3fs_submit_ios(&ior);

// 等待完成
struct hf3fs_cqe cqe;
hf3fs_wait_for_ios(&ior, &cqe, 1, 1, NULL);
// 数据已在 iov.base 中，零拷贝
```

### 注意事项

USRBIO 只影响**数据面**（read/write）。文件的 open、close、stat、fsync 等元数据操作仍然走传统的 FUSE → Meta → FDB 路径。这意味着：

- Close-to-open 一致性语义不变——跨 Pod 仍然需要 writer sync/close 后 reader 重新 open
- 文件 length 的更新时机不变——仍然在 sync/close 时持久化到 FDB
- USRBIO 解决的是**同一文件被多 Pod 读写时的数据可见性**问题，特别是覆盖写场景下的 Page Cache 缓存失效问题

### 七、并发写同一文件：length 会不会混乱

多个 Pod 同时写同一个文件、同时 sync，FDB 中的 length 会不会出错？

答案是**不会**。3FS 有三层保护。

### 6.1 Per-inode 操作串行化

Meta Server 内部，同一个 inode 的所有 sync/close 请求通过 `BatchedOp` 机制排队执行：

```text
// MetaOperator.h:207
Shards<std::map<InodeId, Batch>, 63> batches_;
```

以 InodeId 为 key 分片，每个 inode 有独立的操作队列。同时到达的请求会被合并到同一个 batch，串行处理。

### 6.2 Hint 合并取最大值

当多个 writer 的 sync 请求被合并到同一个 batch 时，length hint 通过 `mergeHint` 合并：

```text
// Schema.h:233-239
static std::optional<VersionedLength> mergeHint(h1, h2) {
    return h1->length >= h2->length ? h1 : h2;  // 取 MAX
}
```

Pod A 报告 length=5000，Pod B 报告 length=8000，合并结果是 8000。length 只会变大，不会因为合并而变小。

### 6.3 FDB 事务冲突检测

每个 `BatchedOp` 在提交前会注册 read conflict：

```text
// BatchOperation.cc:100
co_await inode->addIntoReadConflict(txn);
co_await inode->store(txn);
```

如果两个 BatchedOp 并发修改同一个 inode，FDB 的乐观并发控制会让其中一个事务失败并重试。

### 6.4 queryLastChunk 兜底

当 hint 不可信时（比如发生过 truncate，或 hint 为空），Meta 直接通过 RDMA 去 Storage 查询真实长度：

```text
// BatchOperation.cc:289-295
if (hintLength 可信 && hint > current) {
    return hint;              // 快速路径：信任 hint
} else {
    return fileHelper().queryLength(inode);  // 慢速路径：问 Storage
}
```

这是最后的兜底机制，确保 FDB 中的 length 永远不会偏离真实值太远。

### 八、Storage 层的 Chunk 原子性

如果两个 Pod 同时读写同一个 chunk 的同一个 offset，会不会读到 “一半新一半旧” 的数据？

**不会。** Storage 层有两个机制保证原子性。

### Chunk Lock

每个 chunk 在写入时持有排他锁：

```text
// StorageOperator.cc:366
auto lockGuard = target->storageTarget->lockChunk(baton, chunkId, ...);
```

同一时刻只有一个 writer 可以修改一个 chunk，其他 writer 排队等待。

### Chunk 版本状态机

```text
COMMIT ──write──▶ DIRTY ──commit──▶ COMMIT
  │                 │                  │
  │ (可读)           │ (不可读)          │ (可读，新版本)
  │                 │                  │
commitVer=N        commitVer=N        commitVer=N+1
```

Reader 只能读到 `COMMIT` 状态的数据。当 chunk 处于 `DIRTY` 状态时（正在写入），Reader 拿到的仍然是上一个 committed 版本的数据。commit 完成后 `commitVer` 递增，后续 Reader 才能看到新数据。

这意味着 Reader 要么看到**完整的旧数据**，要么看到**完整的新数据**，不存在中间状态。

### 九、RDMA 部署实践：GKE SR-IOV 的约束

在 GKE A4 集群上部署 3FS 时，我们遇到了一个棘手的网络问题：Meta 和 Storage 都需要 RDMA 连接，但 GKE 的 SR-IOV VF 分配有严格约束。

### GKE 多网络 SR-IOV 机制

每个 A4 节点有 8 张 Mellanox ConnectX-7 RDMA 网卡（`gpu0rdma0` 到 `gpu7rdma0`），GKE 将每张网卡映射为一个 Network 资源（`rdma-0` 到 `rdma-7`）。Pod 通过 resource request 获取 VF：

```text
resources:
  requests:
    networking.gke.io.networks/rdma-0: 「1」
```

**关键约束：每个 rdma-N 网络在每个节点上只有 1 个 VF。** VF 被注入到 Pod 的 network namespace，对 host 不可见。

### 问题：hostNetwork Pod 无法使用 VF

最初我们尝试让 Meta 使用 `hostNetwork: true` 来访问主机上的 RDMA 设备。但 VF 的网络接口（`ethrdma`）只存在于被分配 VF 的 Pod 的 netns 中，host netns 看不到它的 IP 地址。Meta 的 IBDevice 初始化时发现地址为空，RDMA 连接失败。

### 解决方案：Fuse + Meta 合并部署

由于 Fuse 和 Meta 都需要 RDMA 连接到 Storage（Fuse 读写数据，Meta 验证 length、GC 等），而每个节点的 `rdma-0` 只有一个 VF，**最直接的方案是把两者放在同一个 Pod 里共享 VF**。部署在没有 Storage 的 Node-3 上（Node-1 和 Node-2 的 `rdma-0` VF 已被 Storage 占用）：

```text
# fuse-meta-rdma.yaml
spec:
  containers:
  - name: fuse-meta
    args:
    - |
      # 后台启动 Meta
      /opt/3fs/bin/meta_main --launcher_cfg ... &
      sleep 10
      # 前台启动 FUSE
      exec /opt/3fs/bin/hf3fs_fuse_main --launcher_cfg ...
    resources:
      requests:
        networking.gke.io.networks/rdma-0: 「1」
```

Meta 作为后台进程运行，FUSE 作为前台进程运行，两者共享同一个 network namespace 和 RDMA VF。

### 不同 rdma-N 之间不互通

每个 `rdma-N` 是一个独立的 `/22` 子网（如 `rdma-0: 10.107.224.0/22`，`rdma-1: 10.107.228.0/22`），它们之间**没有路由**。所以不能让 Fuse 用 `rdma-1`、Meta 用 `rdma-0`——两者必须在同一个 `rdma-0` 子网上才能和 Storage 通信。

总结部署约束：

```text
Node-1: Storage (占用 rdma-0 VF) + Mgmtd + FDB + Monitor
Node-2: Storage (占用 rdma-0 VF) + Mgmtd + FDB
Node-3: Fuse+Meta (占用 rdma-0 VF) + FDB        ← 不能放 Storage，VF 已被 Fuse+Meta 占用

每个节点的 rdma-0 只有 1 个 VF，谁先占谁用。
Storage 和 Fuse+Meta 不能在同一节点共存（除非共享 Pod）。
```

### 十、总结

3FS 的设计哲学可以用一句话概括：**数据面极致性能，控制面保证正确性。**

- **read/write** 通过 RDMA 直连 Storage，不经过 Meta，不查询 FDB——延迟最小化
- **sync/close** 时 Meta 通过 queryLastChunk 向 Storage 验证文件真实长度——正确性兜底
- **close-to-open** 一致性模型，在性能和一致性之间取得平衡
- **Chunk 版本状态机 + 排他锁**，保证 Storage 层的原子性
- **BatchedOp + mergeHint + FDB 事务**，保证并发 length 更新不会混乱

理解这些机制后，很多看似 “诡异” 的行为就有了解释：

现象原因跨 Pod 读到旧数据 Writer 未 sync，FDB length 还是旧的覆盖写后读到旧数据内核 Page Cache 命中，没穿透到 Storage（可用 USRBIO 规避）close 很慢 Meta 在通过 RDMA queryLastChunk 验证长度 Meta 进程需要 RDMA

| 现象 | 原因 |
| --- | --- |
| 跨 Pod 读到旧数据 | Writer 未 sync，FDB length 还是旧的 |
| 覆盖写后读到旧数据 | 内核 Page Cache 命中，没穿透到 Storage（可用 USRBIO 规避） |
| close 很慢 | Meta 在通过 RDMA queryLastChunk 验证长度 |
| Meta 进程需要 RDMA | 不是读写数据，而是验证 length、GC、truncate |

不是读写数据，而是验证 length、GC、truncate

对于需要跨 Pod 强一致读的场景，可以使用 `O_DIRECT`、将 `enable_read_cache` 设为 `false`，或直接使用 USRBIO 接口彻底绕过内核 Page Cache。对于只读场景（如加载模型权重），默认的 Page Cache 反而能提供显著的性能优势。
