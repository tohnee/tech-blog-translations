> 目标：把人工操作变成可审计、可重放、可协作的流水线。 本层的核心矛盾：自动化的收益随规模增长，自动化的风险也随规模增长。

### 1. 编排层的五个职责

| 职责 | 输出 | 失败后果 |
| --- | --- | --- |
| 工作流编排 | 有依赖关系的任务图 | 步骤乱序或卡住 |
| 资源调度 | 任务按策略分配到集群 | 互相抢占或活锁 |
| 实验追踪 | 元数据与产物的完整记录 | 无法复现、无法对比 |
| 模型注册 | 版本、审批、状态流转 | 上线无门禁 |
| 治理合规 | 权限、审计、供应链安全 | 合规风险、供应链投毒 |

### 2. DAG 工作流编排

### 2.1 DAG 的基本要素

| 要素 | 含义 |
| --- | --- |
| Task | 一个执行单元 |
| Dependency | 任务间的先后关系 |
| Schedule | 触发时机 |
| Retry | 失败重试策略 |
| Timeout | 超时限制 |
| Resource | 资源需求 |

### 2.2 编排框架对比

| 框架 | 抽象 | 强项 | 弱项 |
| --- | --- | --- | --- |
| Airflow | 任务 DAG | 生态成熟、调度可靠 | 任务间传数据不便、延迟分钟级 |
| Dagster | 资产与任务 | 数据血缘清晰、测试友好 | 生态小于 Airflow |
| Argo Workflows | 容器任务 | K8s 原生、每任务独立容器 | 复杂逻辑表达不便 |
| Kubeflow Pipelines | 机器学习流水线 | 原生支持 ML 组件 | 运维复杂 |
| Flyte | 类型化任务 | 数据版本内建 | 需 Python SDK |
| Prefect | Python 优先 | 上手快 | 大规模需谨慎 |

### 2.3 Airflow 与 Argo 的选择

| 维度 | Airflow | Argo |
| --- | --- | --- |
| 运行环境 | 可独立部署 | K8s 内 |
| 任务隔离 | 进程或容器 | 每任务独立 Pod |
| 秒级调度 | 不支持 | 支持 |
| 依赖管理 | 成熟 | 简单 |
| 适用 | 数据管道为主 | 计算密集、需要弹性 |

推论：训练任务通常需要弹性与独立环境。Argo 或 Kubeflow 更合适。

### 2.4 DAG 设计的三条原则

1. **幂等。** 同一任务重跑不产生副作用，或副作用可覆盖。
2. **无隐藏依赖。** 所有依赖显式声明。不靠「正好先跑了这个」。
3. **可局部重跑。** 任一节点失败后，能从该节点继续，不重跑全链。

```python
from airflow import DAG
from airflow.operators.python import PythonOperator
from datetime import datetime, timedelta

with DAG(
    dag_id="ml_retrain_pipeline",
    schedule="0 3 * * 0",                       # 每周日 3 点
    start_date=datetime(2025, 1, 1),
    catchup=False,                                # 不回补历史，避免一次跑爆
    default_args={
        "retries": 2,
        "retry_delay": timedelta(minutes=10),
        "execution_timeout": timedelta(hours=6),  # 显式超时，防挂死
    },
    tags=["ml", "production"],
) as dag:

    validate_data = PythonOperator(
        task_id="validate_data",
        python_callable=check_data_quality,
    )

    build_features = PythonOperator(
        task_id="build_features",
        python_callable=materialize_features,
        op_kwargs={"dt": "{{ ds }}"},             # 显式传入日期，不隐式取今天
    )

    train = PythonOperator(
        task_id="train",
        python_callable=run_training,
        op_kwargs={"feature_dt": "{{ ds }}"},
    )

    evaluate = PythonOperator(
        task_id="evaluate",
        python_callable=run_evaluation,
        op_kwargs={"model_uri": train.output["model_uri"]},
    )

    gate = PythonOperator(
        task_id="release_gate",
        python_callable=check_release_gate,
        op_kwargs={"report": evaluate.output["report"]},
    )

    deploy = PythonOperator(
        task_id="deploy",
        python_callable=deploy_to_staging,
        op_kwargs={"model_uri": train.output["model_uri"]},
    )

    validate_data >> build_features >> train >> evaluate >> gate >> deploy
```

### 2.5 任务失败的处理

| 策略 | 说明 | 适用 |
| --- | --- | --- |
| 立即重试 | 失败后马上重跑 | 网络抖动 |
| 指数退避重试 | 逐步增加等待时间 | 外部服务限流 |
| 跳过 | 失败则跳过下游 | 非关键分支 |
| 挂起等待人工 | 失败则暂停 | 审批门禁 |
| 回滚 | 恢复到上一个成功状态 | 部署失败 |

推论：区分「可重试失败」与「不可重试失败」。配置错误重试一百次也无用。

### 2.6 失败类型的判定

| 失败类型 | 特征 | 重试策略 | 通知 |
| --- | --- | --- | --- |
| 瞬时故障 | 网络超时、限流 | 立即重试 3 次 | 不通知 |
| 短暂资源不足 | GPU 抢占、OOM 抢占 | 退避重试 | 不通知 |
| 依赖服务异常 | 数据库连接失败 | 退避重试 5 次 | 通知 |
| 数据问题 | 校验失败 | 不重试 | 立即通知责任人 |
| 配置错误 | 参数非法 | 不重试 | 立即通知提交者 |
| 代码缺陷 | 空指针、断言失败 | 不重试 | 立即通知提交者 |
| 资源不足 | 显存不够、任务被驱逐 | 降配重试一次 | 通知 |
| 超时 | 超过执行时间上限 | 不重试 | 通知 |

```python
class RetryPolicy:
    """按错误类型决定重试行为。"""

    RETRYABLE = {
        "ConnectionError", "TimeoutError", "RateLimitError",
        "ResourceUnavailable", "ClusterOverloaded",
    }
    # 这些错误重试没有意义，必须立即失败
    TERMINAL = {
        "ValidationError", "ConfigError", "AssertionError",
        "PermissionDenied", "SchemaMismatch",
    }

    def should_retry(self, error, attempt, max_attempts=3):
        if attempt >= max_attempts:
            return False
        name = type(error).__name__
        if name in self.TERMINAL:
            return False
        return name in self.RETRYABLE

    def backoff(self, attempt):
        # 指数退避加抖动，避免重试风暴
        base = min(2 ** attempt, 300)
        return base * (0.5 + random.random() * 0.5)
```

推论：重试必须加抖动。无抖动的指数退避会在故障恢复瞬间产生重试风暴，把系统再次打垮。

### 2.7 幂等性的实现边界

| 操作 | 天然幂等 | 需要额外处理 |
| --- | --- | --- |
| 写入对象存储 | 是，同 key 覆盖 | 版本号控制 |
| 写入数据库 | 否 | 先查后写，或用 upsert |
| 写特征表 | 否 | 按分区覆盖写 |
| 覆盖式发布 | 是 | 检查指针是否已前进 |
| 追加式写日志 | 否 | 用幂等键去重 |
| 调用外部 API | 否 | 请求带幂等键 |
| 发送通知 | 否 | 按业务键去重 |

```python
def idempotent_write(key, fn, store, ttl=86400):
    """幂等执行：同一 key 在 TTL 内只执行一次。"""
    if store.exists(f"done:{key}"):
        return store.get(f"done:{key}")

    result = fn()

    # 用 set 而非 setnx 写入，避免重复执行时的竞态
    store.setex(f"done:{key}", ttl, result)
    return result
```

推论：幂等键必须由业务语义决定，不能用随机值。用随机值等于没有幂等。

### 2.8 工作流的六个常见故障

| 故障 | 现象 | 根因 | 对策 |
| --- | --- | --- | --- |
| 任务空转 | DAG 运行但无实际计算 | 缓存命中被误判为失败 | 显式跳过而非重试 |
| 依赖未就绪 | 上游刚完成下游就启动 | 状态同步延迟 | 加健康检查缓冲 |
| 时区错误 | 跨时区调度错位 | 用了本地时区 | 全链路 UTC |
| 重跑覆盖新数据 | 回填任务覆盖当日结果 | 分区键相同 | 回填用独立分区 |
| 定时任务堆积 | 上一轮未完成下一轮已触发 | 无并发限制 | 设置并发策略 |
| 门禁误放行 | 评估不达标仍部署 | 门禁逻辑有漏洞 | 门禁逻辑做单测 |

### 3. 训练任务调度

![](https://pic2.zhimg.com/v2-bef98fdccd7a33c8869a4756945f013f_r.jpg)
*Gang Scheduling 与资源调度*

### 3.1 为什么需要 Gang Scheduling

分布式训练任务的所有 Pod 必须同时启动。默认调度器逐个分配，会造成半分配。

**没有 Gang 的后果。**

1. 8 卡训练任务 A 先拿到 4 张卡，其余 Pending。
2. 任务 B 请求 8 卡，全部 Pending。
3. 4 张卡空转到 NCCL 超时，A 白跑。
4. 多个任务同时半分配时互相卡死，形成集群活锁。

**有 Gang 的后果。**

1. A 声明 minMember 为 8，凑齐才启动。
2. A 运行时 B 整体排队，不占卡。
3. A 正常跑完，B 获得资源。
4. 无半分配，无空转，无活锁。

### 3.2 PodGroup 声明

```yaml
apiVersion: scheduling.volcano.sh/v1beta1
kind: PodGroup
metadata:
  name: llm-pretrain
spec:
  minMember: 64                 # 凑齐 64 个成员才调度
  queue: team-llm
  priorityClassName: high
```

### 3.3 队列、配额与抢占

| 机制 | 作用 | 配置要点 |
| --- | --- | --- |
| 队列 | 按团队或优先级隔离资源 | 训练队列与在线推理队列必须分开 |
| 配额 | 硬上限 | 可超发，但必须可抢占 |
| 抢占 | 高优抢低优 | 训练可抢，推理默认不可抢 |
| 公平共享 | 按比例长期分配 | 防止网格搜索饿死其他团队 |

### 3.4 训练与推理必须分队列

| 场景 | 混队列的后果 |
| --- | --- |
| 在线推理被训练挤占 | 用户请求超时，SLO 破线 |
| 训练被推理挤占 | 训练任务反复重启 |
| 双方都受影响 | 双方都不稳定 |

推论：两条队列的扩容节奏、资源画像、优先级都不同。混在一起必然出问题。

### 3.5 弹性训练的四种策略

| 策略 | 做法 | 适用 |
| --- | --- | --- |
| 节点故障自动重启 | 从最近 checkpoint 恢复 | 所有训练任务必备 |
| 抢占式训练 | 利用低谷，节点被抢则保存并恢复 | 有 checkpoint 能力 |
| 按需扩缩 | 数据少时减少并行度 | 训练后期或小数据 |
| 抢占回退 | 高优任务来时主动让出 | 与平台方协商 |

### 5. 模型注册表与发布门禁

### 5.1 模型状态机

```text
None → Pending → Validating → Staging → Production
                     ↓           ↓          ↓
                  Rejected    Archived   Archived
```

| 状态 | 含义 | 进入条件 |
| --- | --- | --- |
| Pending | 刚产出，未验证 | 自动 |
| Validating | 正在跑评估 | 评估任务触发 |
| Staging | 影子或金丝雀 | 评估达标 |
| Production | 承载真实流量 | A/B 达标 |
| Rejected | 评估不达标 | 自动 |
| Archived | 历史版本 | 人工或自动 |

### 5.2 发布门禁的检查项

| 检查项 | 阈值 | 阻断 |
| --- | --- | --- |
| 主指标 | 不低于基线 | 是 |
| 主指标显著性 | p 小于 0.05 | 是 |
| 护栏指标 | 不退化 | 是 |
| 安全测试 | 攻击成功率达标 | 是 |
| 推理冒烟 | 全部通过 | 是 |
| 延迟回归 | 小于阈值 | 是 |
| 成本回归 | 小于阈值 | 否，可带风险发布 |
| 人工审批 | 高风险场景需要 | 视场景 |

```python
def release_gate(report, baseline, is_high_risk=False):
    """发布门禁。任何硬性检查不通过则阻断。"""

    failures = []

    # 硬性检查
    if report["primary"]["delta"] <= 0:
        failures.append("主指标未提升")
    if report["primary"]["p_value"] >= 0.05:
        failures.append("主指标无统计显著性")
    for name, value in report["guardrails"].items():
        if value < baseline["guardrails"][name]:
            failures.append(f"护栏退化：{name}")
    if report["safety"]["attack_success_rate"] > 0.02:
        failures.append("安全测试不达标")
    if not report["smoke"]["all_passed"]:
        failures.append("推理冒烟未通过")
    if report["latency"]["p99_delta"] > 0.20:
        failures.append("延迟回归超过 20%")

    # 软性检查：仅告警
    warnings = []
    if report["cost"]["delta"] > 0.10:
        warnings.append("成本上升超过 10%")

    # 高风险场景强制人工审批
    needs_approval = is_high_risk or failures

    return {
        "pass": len(failures) == 0,
        "failures": failures,
        "warnings": warnings,
        "needs_approval": needs_approval,
    }
```

### 5.3 门禁的设计原则

1. **门禁必须自动。** 人工门禁会被跳过或事后补签。
2. **门禁必须可绕过但留痕。** 紧急情况可绕过，但记录绕过人、原因。
3. **软硬分离。** 安全与质量是硬门禁。成本与性能劣化是软告警。
4. **门禁指标不可事后调整。** 调整即失去意义。

### 5.4 门禁的八个失效场景

门禁本身会失效。失效时模型照样上线。

| 失效场景 | 机制 | 后果 | 对策 |
| --- | --- | --- | --- |
| 样本量不足 | 小样本上主指标波动大 | 假阳性放行 | 门禁加最小样本量 |
| 指标不可比 | 换了评测集或分词器 | 对比无效 | 绑定评测集指纹 |
| 边际提升放行 | 提升 0.1% 也放行 | 无实际收益 | 加最小效应量门槛 |
| 回归被平均 | 少数分层严重退化被总分掩盖 | 特定人群受损 | 分层硬门禁 |
| 门禁被关 | 紧急时关闭后未恢复 | 长期失效 | 门禁状态纳入监控 |
| 门禁用错指标 | 指标与业务目标错位 | 通过但无价值 | 定期复核指标映射 |
| 护栏指标太少 | 未覆盖关键风险 | 隐患上线 | 护栏按业务逐项列 |
| 只看单次结果 | 随机波动被当结论 | 决策不稳 | 要求多次复现 |

最小效应量门槛：

$$ \text{MDE} = z_{\alpha} \sqrt{\frac{p(1-p)}{n}} + z_{\beta}\sqrt{\frac{p(1-p)}{n}} $$

变量含义：$\alpha$ 为显著性水平，$\beta$ 为检验功效，$n$ 为样本量。

| 目标 | MDE 门槛 | 说明 |
| --- | --- | --- |
| 只要正向 | 大于 0 | 噪声内也放行 |
| 有实际意义 | 基线的 2% | 常用设置 |
| 保守 | 基线的 5% | 高风险场景 |
| 极保守 | 基线的 10% | 仅接受显著提升 |

推论：门禁必须同时设统计显著性门槛与最小效应量门槛。只有显著性会让噪声通过。

### 5.5 分层门禁

总体指标通过不代表所有分层都通过。

```python
def layered_gate(report, baseline, critical_slices, min_delta=0.02):
    """分层门禁：总体加关键分层都要通过。"""
    failures = []

    # 总体门禁
    if report["primary"]["delta"] < min_delta:
        failures.append(f"总体提升小于 MDE {min_delta}")

    # 关键分层门禁：任何一个退化都阻断
    for slice_name in critical_slices:
        cur = report["slices"].get(slice_name)
        base = baseline["slices"].get(slice_name)
        if cur is None or base is None:
            failures.append(f"分层缺失：{slice_name}")
            continue

        delta = cur["primary"]["delta"]
        if delta < -0.01:                    # 关键分层不允许退化
            failures.append(f"关键分层退化：{slice_name} ({delta:.2%})")
        elif delta < min_delta:
            # 关键分层至少不能无提升
            failures.append(f"关键分层无提升：{slice_name}")

    return {"pass": not failures, "failures": failures}
```

| 分层策略 | 说明 | 适用 |
| --- | --- | --- |
| 全分层硬门禁 | 任何分层退化都阻断 | 安全关键场景 |
| 关键分层硬门禁 | 只对关键人群设硬门禁 | 通用推荐 |
| 加权总分门禁 | 按流量加权求总分 | 分层样本不均衡 |
| 观察模式 | 只记录不阻断 | 新业务初期 |

### 5.6 门禁的运行约束

| 约束 | 要求 | 原因 |
| --- | --- | --- |
| 确定性 | 同样输入必须同样结论 | 避免无法复现 |
| 无状态 | 不依赖上次运行结果 | 避免状态漂移 |
| 快速 | 低于 5 分钟 | 太慢则被绕过 |
| 可解释 | 输出失败原因 | 便于修复 |
| 有版本 | 门禁逻辑本身版本化 | 逻辑变更需评审 |
| 可旁路 | 旁路需记录与告警 | 处理紧急情况 |

推论：门禁运行超过 5 分钟，人就会绕过它。快的门禁比严的门禁更有效。

### 6.1 四种交付方式

### 7. 安全与供应链

### 7.1 模型格式的安全风险

| 格式 | 反序列化风险 | 处理方式 |
| --- | --- | --- |
| pickle | 高。可执行任意代码 | 禁止用于不可信模型 |
| PyTorch .pt | 高。基于 pickle | 转 safetensors |
| safetensors | 低。只读张量数据 | 首选 |
| GGUF | 低 | 可接受 |

### 7.2 safetensors 的安全优势

safetensors 格式只包含头部元数据加连续的字节缓冲区。

它不包含任何可执行代码。加载时不会触发反序列化钩子。

推论：这是模型供应链安全的第一道防线。必须强制使用。

### 7.3 模型供应链的五个环节

| 环节 | 风险 | 对策 |
| --- | --- | --- |
| 训练 | 代码被篡改 | 代码审计、签名 |
| 存储 | 模型被替换 | 完整性校验 |
| 传输 | 中间人攻击 | TLS 加校验 |
| 加载 | 恶意格式 | 只用 safetensors |
| 运行 | 提示注入 | 输入输出过滤 |

### 7.4 完整性校验

```python
import hashlib

def verify_model(model_path, expected_sha256):
    """校验模型文件完整性。"""
    h = hashlib.sha256()
    with open(model_path, "rb") as f:
        for chunk in iter(lambda: f.read(1 << 20), b""):
            h.update(chunk)

    actual = h.hexdigest()
    if actual != expected_sha256:
        raise ValueError(
            f"模型完整性校验失败\n"
            f"  期望：{expected_sha256}\n"
            f"  实际：{actual}"
        )
    return True
```

### 7.4.1 safetensors 头部校验

safetensors 的安全性来自头部声明的偏移量与长度。恶意文件可以用它做越界读。

```python
import json
import struct
import os

def validate_safetensors_header(path, max_tensor_bytes=500 << 30):
    """校验 safetensors 头部，拒绝越界声明。"""
    file_size = os.path.getsize(path)

    with open(path, "rb") as f:
        header_len = struct.unpack("<Q", f.read(8))[0]

        # 边界一：头部长度必须合理，防止超大分配
        if header_len <= 0 or header_len > 100 << 20:
            raise ValueError(f"非法头部长度：{header_len}")

        header = json.loads(f.read(header_len))
        data_start = 8 + header_len

    for name, meta in header.items():
        if name == "__metadata__":
            continue

        # 边界二：偏移量与长度必须合法且在文件范围内
        begin, end = meta["data_offsets"]
        if begin < 0 or end <= begin:
            raise ValueError(f"非法偏移：{name} [{begin}, {end})")
        if data_start + end > file_size:
            raise ValueError(
                f"越界读取：{name} 声明到 {end}，文件仅 {file_size} 字节"
            )

        # 边界三：张量大小必须在合理上限内，防内存耗尽
        if (end - begin) > max_tensor_bytes:
            raise ValueError(f"张量过大：{name}")

    return True
```

推论：safetensors 不执行代码，但可以用巨大偏移量做内存耗尽攻击。必须校验头部。

### 7.4.2 供应链签名的边界

| 校验项 | 解决什么 | 不解决什么 |
| --- | --- | --- |
| 哈希比对 | 文件被改动 | 攻击者同时改了哈希 |
| 数字签名 | 来源可信 | 签名密钥泄露 |
| 签名加时间戳 | 防回滚攻击 | 时间戳服务被攻破 |
| 透明日志 | 公开可审计 | 日志服务被攻破 |
| 硬件密钥 | 密钥不外泄 | 内部人员滥用权限 |

| 攻击 | 对策 |
| --- | --- |
| 传输中篡改 | TLS 加哈希 |
| 存储中替换 | 存储侧开启不可变与审计 |
| 哈希与文件同时替换 | 数字签名 |
| 回滚到旧的有漏洞版本 | 签名中含版本与时间戳 |
| 内部人员恶意发布 | 双人审批加审计日志 |

### 7.5 密钥管理

| 阶段 | 做法 |
| --- | --- |
| 生成 | 用 Vault 或云 KMS，不写在代码里 |
| 存储 | 加密存储在 Vault，不在环境变量明文 |
| 分发 | 短期令牌，配合工作负载身份 |
| 轮换 | 自动轮换，定期强制 |
| 审计 | 记录每次访问 |

推论：不要把密钥放环境变量或配置文件。必须用短期令牌加工作负载身份。

必须记录的操作。

| 操作 | 记录内容 |
| --- | --- |
| 数据访问 | 谁、何时、访问了哪张表的哪些列 |
| 模型发布 | 谁审批、依据什么指标 |
| 生产变更 | 谁改了什么配置 |

### 10. 常见错误

| 错误 | 后果 | 正确做法 |
| --- | --- | --- |
| 用 pickle 存模型 | 供应链投毒风险 | 只用 safetensors |

| 元数据只记超参 | 无法复现 | 四维版本都要记 |
| 密钥写在代码里 | 泄漏 | 用密钥管理服务 |
| 无审计日志 | 违规无法追溯 | 关键操作全审计 |
