### SSE理解

首先需要明确SSE(Server-Sent Events) 并不是一种新的协议， **其本质还是基于HTTP的，关键是利用其长连接特性，在客户端和服务器之间建立了一条持久化的连接** ，并通过这条链接实现了服务器向客户端的实时数据推送。SSE服务端响应如下所示:

```json
HTTP/1.1 200 OK  
Content-Type: text/event-stream; charset=utf-8  # 这是一个SSE流，客户端需要持续接受服务端写入的数据
Cache-Control: no-cache  
Connection: keep-alive
```

SSE服务端响应示例如下:

```json
Client                           Server  
  
GET /events ----------------> 建立 SSE 长连接  
  
<------------------ data: hello                       (chunk1)
  
<------------------ data: world                       (chunk2)
  
<------------------ data: {"content":"你好"}          (chunk3)
  
<------------------ data: [DONE]                      (chunk4) 结束标志
```

业务中常搭配 `fastapi` 来实现基于sse的服务端主动推流，完整实现如下所示:

```python
# -*- coding: utf-8 -*-
"""
FastAPI + SSE 流式 LLM 服务
依赖: pip install fastapi uvicorn openai

运行: OPENAI_API_KEY=sk-xxx uvicorn fastapi_sse_llm:app --host 0.0.0.0 --port 8000
"""
import json
import os

from fastapi import FastAPI
from fastapi.responses import StreamingResponse
from pydantic import BaseModel
from openai import OpenAI

app = FastAPI(title="SSE LLM Service")

# OpenAI 在线 API 客户端
client = OpenAI(
    api_key=os.getenv("OPENAI_API_KEY", "sk-xxx"),
    base_url=os.getenv("OPENAI_BASE_URL", "https://api.openai.com/v1"),
)
MODEL = os.getenv("OPENAI_MODEL", "gpt-4o-mini")

class ChatRequest(BaseModel):
    message: str
    history: list[dict] | None = None  # 例如 [{"role": "user", "content": "hi"}]
    model: str | None = None

@app.post("/chat")
def chat(req: ChatRequest):
    """SSE 流式对话接口: 前端用 EventSource 不行(只支持GET),
       需用 fetch 读取流 或 POST + ReadableStream"""
    messages = req.history or []
    messages.append({"role": "user", "content": req.message})

    def event_stream():
        try:
            resp = client.chat.completions.create(
                model=req.model or MODEL,
                messages=messages,
                stream=True,
                temperature=0.7,
            )
            for chunk in resp:
                delta = chunk.choices[0].delta.content if chunk.choices else None
                if delta:
                    # SSE 格式: "data: <内容>\n\n"
                    yield f"data: {json.dumps({'content': delta}, ensure_ascii=False)}\n\n"
            yield 'data: {"done": true}\n\n'
        except Exception as e:
            yield f"data: {json.dumps({'error': str(e)}, ensure_ascii=False)}\n\n"

    return StreamingResponse(
        event_stream(),
        media_type="text/event-stream", # 响应类型必须是text/event-stream
        headers={
            "Cache-Control": "no-cache",
            "Connection": "keep-alive",
            "X-Accel-Buffering": "no",  # 防止 Nginx 缓冲
        },
    )

@app.get("/chat")
def chat_get(message: str = "你好"):
    """GET 版本, 方便直接用 EventSource 测试"""
    return chat(ChatRequest(message=message))
```

### MCP消息格式

需要注意的是，所有MCP消息都必须是JSON-RPC 格式，且所有JSON-RPC消息必须使用UTF-8编码，一共有三类消息: **Request(请求)** 、 **Response(响应)** 、 **Notificatiion(通知)** , 具体格式如下:

1. Request(请求)

```json
{
  "jsonrpc": "2.0",
  "id": 42,
  "method": "tools/call",
  "params": {
    "name": "get_weather",
    "arguments": {
      "city": "beijing"
    }
  }
}
```

2. Response(响应)

```json
{
  "jsonrpc": "2.0",
  "id": 42,    # id必须和请求请求的一致
  "result": {
    "content": [
      {
        "type": "text",
        "text": "北京今天晴，25°C"
      }
    ],
    "isError": false
  }
}
```

3. Notificatiion(通知)

```json
{
  "jsonrpc": "2.0",  # 没有id,且不需要回复
  "method": "notifications/initialized"
}
```

### MCP传输机制

- **stdio**

标准输入输出是MCP最简单的传输方式： **客户端作为父进程启动服务器子进程，通过子进程的标准输入(stdio) 和 标准输出 (stdout) 交换 JSON-RPC消息** 。

具体流程如下:

```json
┌──────────────┐                    ┌──────────────┐
│   MCP 客户端  │ ── stdin (写) ──▶ │   MCP 服务器  │
│ (如 Claude   │                    │  (子进程)     │
│  Desktop/IDE)│ ◀── stdout (读) ──│              │
└──────────────┘                    └──────────────┘

```

1. 客户端用命令启动服务器进程(例如 npx my-mcp-server)
2. 客户端把JSON-RPC 消息写入服务器的stdin
3. 服务器处理请求，把响应写到自己的stdout
4. 客户端读取stdout 得到结果

适用场景:

1. 桌面应用/IDE插件: Claude Desktop、Cherry studio等，服务器和客户端在同一台机器上
2. 快速开发调试：无需网络配置，端口管理

不适用场景:

1. 不能跨机器， **跨机器需要考虑SSE或Streamable HTTP**
2. 作为公共服务部署: **没法放到云端让多个其他用户调用**

- **HTTP + SSE**

**2024-11-05提出的规范，现已标记为deprecated, 具体步骤如下图所示:**

![](https://pic4.zhimg.com/v2-a74d14ff5edb35e5ef6cc7aebef951e7_r.jpg)
*HTTP + SSE 传输过程*

1. 客户端先向 `/sse` 发送get 请求，建立一条常驻的SSE (Server-Sent Evnets) 长连接；服务器通过该连接发送一个endpoint事件(通常会附带会话标识,如 `/messages?sessionID=xxx` )，该事件告知客户端应POST到哪个地址
2. 客户端把JSON-RPC消息POST到/messages 端点，服务器仅返回 202 Accepted, 不携带任何业务数据
3. 真正的 **请求结果，流式进度，通知全部** 通过第1步建立的SSE长连接推送回去

- **Streamable HTTP**

**MCP通信现行标准，2025-03-26规范**

![](https://picx.zhimg.com/v2-9d09ac56150aee7fa0e19abafb269227_r.jpg)
*Streamable HTTP 传输过程*

回归 **单一端点** /mcp, **普通请求-响应** 模型，流式响应变成 **”非必须”** :

- 每个JSON-RPC消息就是一个 `POST /mcp` , 服务器可以返回 `application/json` (一次性简单响应)，也可以升级为 `text/event-stream` (流式返回)，由请求头 `Accept: application/json, text/event-stream` 协商
- `GET /mcp` 是可选的：客户端可打开这条SSE流接受服务器主动推送，但不需要推送能力的服务器可以直接返回 `405 Method Not Allowed`

两种传输方式核心比较：

| 比较维度 | HTTP + SSE | Streamable HTTP |
| --- | --- | --- |
| 端点数量 | (/sse + /messages) 2个 | /mcp 1个 |
| 服务器→客户端推送 | 只能走常驻SSE流 | POST响应本身(JSON或SSE流) |
| 无状态/Serverless | 难以支持 | 原生支持 |
| 服务器主动推送 | 必须长连接 | GET /MCP 流可选 |

- 稳定性比较

![](https://pic2.zhimg.com/v2-de561c1d8290255981c4d9f59b917b99_r.jpg)
*SSE 与 Streamable HTTP 稳定性比较*

- HTTP + SSE: 依赖大量长连接，TCP连接数持续增长
- Streamable HTTP: 按需建立连接，但TCP连接数较低

- 请求响应成功率比较

![](https://pic1.zhimg.com/v2-ed4ac0d36b0803c1067c1110b372d4bc_r.jpg)
*SSE 与 Streamable HTTP 请求成功率比较*

- HTTP + SSE: 随着并发用户数增加，成功率显著下降
- Streamable HTTP: 即使在高并发条件下也能保持相对较高的成功率
