这一系列打算讲清楚 FSDP 的演进。从 FSDP1 时代，到 FSDP2 时代，一直到 SampleFSDP 时代。

在开始前，我们先从最简单的问题问起：单卡训练不够用，多卡训练要怎么做？

把这个问题一层层拆开，DDP、ZeRO、FSDP1 这几个方案就自然浮现出来了。

## 1. 单卡到多卡：DDP 想解决什么

单卡时代，训练一个模型是这样的：

- 前向传播：把一批数据喂进网络，得到 loss。
- 反向传播：算梯度。
- optimizer step：用梯度更新参数和 optimizer state。

一次迭代结束，进下一批数据。

模型能塞进单卡显存但数据太大的时候，最直白的加速办法是加卡。

![](https://picx.zhimg.com/v2-a5173bde3f44ce60bd9c17cac80575b1_r.jpg)

把一个大 batch 平均分给 N 张卡，每张卡处理 1/N 的数据，各算各的前向、反向。但每张卡算出来的梯度只反映自己看到的那 1/N 数据，如果直接用这个梯度更新，N 张卡就会跑向不同的方向。想让它们等价于”一张超大显存卡跑完整 batch”，就得在梯度上做一次共识，让所有 rank 达成一致后再更新。

这就是 DDP 要解决的目标：单机训练的语义不变（前向、反向、step 三步），只是数据被切开，加一次梯度平均。

### 1.1 DDP 怎么实现

梯度平均用 all-reduce。

![](https://pic1.zhimg.com/v2-9c4ae305dab31b44cec7906e654752a0_r.jpg)

NCCL 的 all-reduce 实际是 Ring-AllReduce：先 reduce-scatter，再 all-gather。假设参数总量为 P，有 N 张卡，两个阶段各通信 N-1 次，单次通信量 P/N，总通信量 `P/N × (2N-2) ≈ 2P`。它的一个好处是通信量跟 N 无关，可以近似线性扩展。

第二件事是通信跟计算重叠。DDP 把参数按 25MB 一个 bucket 分组，每个 bucket 的梯度算完就立刻发起 all-reduce，此时下一个 bucket 还在算。计算流和通信流互相隐藏，实际训练里 all-reduce 的时间大部分能被吃掉。

### 1.2 DDP 有什么问题

举个具体的例子。Llama 70B、bf16 混合精度、Adam 优化器，一张卡上要存什么：

- 参数副本（bf16）：70 × 2 = 140 GB
- 梯度副本（bf16）：70 × 2 = 140 GB
- fp32 master weight：70 × 4 = 280 GB
- Adam 的 m、v（fp32）：70 × 4 × 2 = 560 GB

加起来一张卡要 1.12 TB。H200 是 141 GB。8 卡起步也没法装。

DDP 的心智模型简单干净，代价是每张卡都要一份完整的副本。参数一旦到百亿、千亿量级，这堵墙立刻就撞上了。

## 2. ZeRO 的目标：把冗余压回去

DeepSpeed 团队 2019 年那篇《ZeRO: Memory Optimizations Toward Training Trillion Parameter Models》要解决的就是上面这堵墙。既然每张卡都存一份是纯浪费，那就让每张卡只存 1/N，用的时候从别的 rank 借。

ZeRO 有三个阶段，从轻到重：

- Stage 1：只切优化器状态（m、v、master weight）。参数和梯度还是每张卡一份。
- Stage 2：优化器状态和梯度都切。参数每张卡一份。
- Stage 3：参数、梯度、优化器状态全切。每张卡只留 1/N。

### 2.1 ZeRO Stage 3 怎么实现

Stage 3 是最激进的一档，也是理解 FSDP 的基础。它的运行时是这样的：

- forward 一层前，通过 all-gather 把这一层的参数从所有 rank 收回完整状态；forward 用完就丢。
- backward 一层前，再 all-gather 一次拿到完整参数；backward 算完梯度后用 reduce-scatter 把梯度切回分片。
- optimizer step 每张卡只更新自己那 1/N 参数和 optimizer state。

H100 是 141 GB 8 卡起步, 同一个 70B 模型在 Stage 3 下算一遍单卡显存：

- 参数：140 / 8 ≈ 17.5 GB
- 梯度：140 / 8 ≈ 17.5 GB
- Adam + master weight：840 / 8 = 105 GB
- 单卡合计：约 140 GB

从 DDP 的 1.12 TB 压到 140 GB，8 张卡刚好塞得下，当然这里忽略了激活。代价是通信量：forward 一次 all-gather（P），backward 一次 all-gather（P），一次 reduce-scatter（P），单卡单向 3P，是 DDP 的 1.5 倍。

DeepSpeed 依靠异步参数加载把这些通信藏起来。第一次迭代记录参数使用顺序，后续迭代按顺序异步发起 all-gather，当前层计算的时候下一层已经在飞。跑得好的时候通信基本被计算盖住。

### 2.2 DeepSpeed ZeRO 有什么问题

用过 DeepSpeed 训练大模型的人都能列出下面几条：

**通信粒度和计算粒度对不上**。NCCL 集合通信有一条基本规律：单次消息越小，带宽利用率越差。消息小于 64KB 会走 latency-bound 路径，实际带宽利用率通常只有 10-30%；消息大于 1MB 才进入 bandwidth-bound 区间，能吃到 80%+。

DeepSpeed 它在 `deepspeed.zero.Init()` 里做了持久 flatten：同一个 `sub_group` 内所有参数的 `ds_tensor` 拷进一段连续 buffer，也就是 `fp16_partitioned_groups_flat`。各个 `ds_tensor` 从此是这段 buffer 的 slice，共享 storage。fetch 时走 `all_gather_coalesced` 把多个参数打包成一次 NCCL group 调用。

> DeepSpeed 至少有五个跟通信粒度相关的配置项，都得根据模型和集群规模手工调：<br>sub_group_size：默认 1e9 elements，决定 flat buffer 边界。太小会切碎连续内存，太大会导致 offload 时单块太大装不下 CPU 或触发 GPU OOM。<br>reduce_bucket_size：默认 5e8，梯度 reduce 的 bucket。太小的话小消息 latency-bound，太大的话反向 hook 触发不及时。<br>stage3_prefetch_bucket_size：默认 5e7，前向 fetch 参数的 bucket。太小的话 NCCL 跑不起带宽，太大的话 prefetch 占的显存吃掉一层甚至几层的空间。<br>stage3_param_persistence_threshold：小于这个 numel 的参数常驻不参与分片。用来抢救 layernorm、bias 这些小参数。<br>stage3_max_live_parameters / stage3_max_reuse_distance：控制同时有多少参数处于 unshard 状态。手工调节 in-flight collective 上限。

因为 DeepSpeed 的 flatten 边界（sub_group）跟模型结构、通信规模、显存预算三个东西都不匹配，用户得手动把它们对齐到当前的训练场景。

一个具体的例子。1024 卡训 Llama 70B：

- stage3_prefetch_bucket_size 默认 5e7（100MB）在 fp16 下听起来挺大，但 1024 卡摊下来一次 all-gather 每卡只有 100 KB 的本地贡献，NCCL 还是跑不到带宽。
- 想拉大 bucket 到 5e8（1GB）？可以，但这时候一层 TransformerBlock 加 prefetch 一层的完整参数就要 4GB 左右，加上激活、梯度、optimizer state 直接 OOM。
- 想把 stage3_max_live_parameters 调低点省显存？调低了 prefetch 深度就不够，通信重叠不上，训练速度立刻掉。

于是每次换个模型、换个集群规模、换个 seq_len，都得重新过一遍这几个 size。DeepSpeed 官方 tuning guide 里专门有一节讲怎么调，社区里也有一堆经验帖。

**动态图适配差**。ZeRO 需要模型按固定顺序调用模块才能正确 prefetch。碰上分支控制流、多次调用同一层这种情况，DeepSpeed 就不好办了。

**跟 PyTorch 生态耦合弱**。DeepSpeed 提供自己的优化器实现，要通过 `deepspeed.initialize()` 构建优化器。它把分片当作系统状态，optimizer 必须理解参数、梯度、状态是怎么分布的。想混用其他优化器或者接一个新框架，改动量都很大。DeepSpeed 必须为每种精度组合实现一个”optimizer 语义版本”，因为它接管了参数、梯度、optimizer state 的所有语义。

**代码质量**。这一点没什么好辩的，用过就知道。

正是这些问题给了 PyTorch 团队重做一遍的动机。FSDP1 就是这条路线的第一版答卷。

## 3. FSDP1 时代：把 ZeRO Stage 3 塞进 PyTorch

FSDP1 想解决的核心问题有两个。

**通信效率**。DeepSpeed 的 flatten 边界（sub_group）跟模型结构、通信规模、显存预算三个东西都不匹配。要想办法把多个参数打包成一次比较合适的 collective 需要手动调整 bucket_size。

**PyTorch 兼容**。让 optimizer 看到的还是 `nn.Parameter`，让用户不需要为分片改写 optimizer、不需要重写 checkpoint 逻辑、不需要用一套新的 API 构建模型。

### 3.1 FSDP1 怎么实现：FlatParameter

FSDP1 的核心抽象叫 FlatParameter。它是 `nn.Parameter` 的子类，语义上是一个 1D 张量。构造方式非常物理：

1. 取一个 FSDP unit 里所有的原始 `nn.Parameter`（一般是一个 `TransformerBlock` 里 `wq`、`wk`、`wv`、`wo` 加两个 layernorm）。
2. 每个参数 `view(-1)` 后拼在一起。
3. 补 padding 让总长度能被 world_size 整除。
4. 均匀切给 world_size 个 rank，每个 rank 只留自己那 1/N。

举个例子。一个简化的 TransformerBlock 里有 4 个矩阵 `[4096, 4096]`，共 67 M 参数。8 卡切分后每张卡持有 8.4 M。这块内存物理上连续，`param.q.weight` 变成 offset 0 的一个 view，`param.k.weight` 是 offset 16M 的 view，以此类推。

为什么要拍成 1D？两个考虑：

- NCCL 的 `all_gather_into_tensor` 和 `reduce_scatter_tensor` 要求各 rank 输入等长、shape 简单。FlatParameter 天然满足。这两个 API 比 `all_gather` 和 `reduce_scatter` 快得多。
- 一次 collective 带上多个参数能显著减少 NCCL launch 次数。大块数据传输 NCCL 也跑得更快。

FSDP1 允许用户通过 `auto_wrap_policy` 自定义 unit 边界。最常见的粒度是每个 `TransformerBlock` 一个 unit，一次 all-gather 覆盖整层权重，通信效率高。

FSDP1 的 bucket 边界就是 auto_wrap_policy 定的 FSDP unit。用户只需要选”每个 TransformerBlock 一个 unit”这个粒度，剩下的自动对齐：

- 通信边界 = FSDP unit
- flatten 边界 = FSDP unit（一个 FlatParameter 覆盖整个 unit）
- prefetch 边界 = FSDP unit（默认前一个 unit）

三个边界是同一个东西，参数从 32MB 到 500MB 之间自然落在 NCCL bandwidth-bound 区间。用户不用去调 sub_group、bucket、prefetch 三套 size。

### 3.2 初始化流程

一段典型的 FSDP1 调用：

```text
fsdp_model = FSDP(
    model,
    device_id=torch.cuda.current_device(),
    sharding_strategy=ShardingStrategy.FULL_SHARD,
    auto_wrap_policy=lambda module: isinstance(module, nn.Linear),
)
```

背后主要发生四件事：wrap、构造 FlatParamHandle、shard、把参数指针换掉。

**Wrap 是后序遍历**。`auto_wrap_policy` 决定哪些子模块要单独包成一个 FSDP unit。遍历顺序是后序（先叶子后父），保证叶子先包好，父模块看到的已经是嵌套好的 FSDP。BatchNorm、LayerNorm 这种数值敏感的算子会单独包一层并禁用低精度。

**构造 FlatParamHandle**。每个 FSDP unit 会调 `_init_param_handle_from_module` 构造一个 `FlatParamHandle`：

```text
handle = FlatParamHandle(
    params,
    fully_sharded_module,
    state.compute_device,
    SHARDING_STRATEGY_MAP[state.sharding_strategy],
    ...
)
handle.shard()
state.params.append(handle.flat_param)
state._handle = handle
```

内部两件事。

第一是拼接，`_init_flat_param_and_metadata` 遍历 params，把每个 tensor `view(-1)` 后拼在一起。如果总元素数不能被 world_size 整除就补 padding。同时它会把一大堆元数据记下来：每个原始参数在 FlatParameter 中的起始 offset、原始 shape、原始 stride、padding 长度、跨 rank 边界信息。这些元数据是后面所有 FlatParameter 相关脆弱性的根源，混合精度、checkpoint、debug 都要靠它把 1D 张量翻译回原始参数视图。

第二是 view 化，`_use_unsharded_views(as_params=False)` 让原始模块的 `wq.weight` 变成 FlatParameter 的一个 view，两边共享底层存储。

**Shard**。到这一步 FlatParameter 还是完整的，`handle.shard()` 才是真正分片：

```text
def shard(self):
    sharded_flat_param, numel_padded = FlatParamHandle._get_shard(
        flat_param, self.rank, self.world_size)
    if flat_param._typed_storage()._size() > 0:
        flat_param._typed_storage()._resize_(0)
    flat_param.set_(sharded_flat_param)
```

`_get_shard` 把 flat_param 均分为 world_size 份，取本 rank 那一份。拿到本地 shard 后，先把完整 flat_param 的 storage `resize_(0)` 释放，再用 `flat_param.set_(sharded_flat_param)` 让 flat_param 指向本地 shard。每个 rank 只留下 1/N 的显存。

至此参数的初始状态是：`flat_param.data` 是本地分片，形状 `[N_total / world_size]`；模块里的 `wq.weight` 之类还是 view，但底下的 storage 是 0 长度，直接读没有意义。

### 3.3 前向

FSDP1 的 forward 逻辑：

```text
def forward(self, *args, **kwargs):
    handle = self._handle
    args, kwargs = _pre_forward(self, handle, _pre_forward_unshard,
                                 self._fsdp_wrapped_module, args, kwargs)
    output = self._fsdp_wrapped_module(*args, **kwargs)
    return _post_forward(self, handle, _post_forward_reshard, self, unused, output)
```

三件事：`unshard` 恢复完整参数、跑原模块 forward、`reshard` 释放完整参数。

`unshard` 内部：

```text
unsharded_flat_param = self._alloc_padded_unsharded_flat_param()
padded_unsharded_flat_param = self._all_gather_flat_param(unsharded_flat_param)
self._use_unsharded_flat_param(padded_unsharded_flat_param)
```

分配一块能装下完整 FlatParameter 的空间，调 `dist.all_gather_into_tensor` 从所有 rank 收参数，把模块的参数指针切到完整 buffer。切完之后 `wq.weight` 就是完整参数了。

`_pre_forward` 还会做一件重要的事：给 FlatParameter 挂 post-backward hook：

```text
if handle._needs_pre_backward_unshard:
    _register_post_backward_hook(state, handle)
```

这个 hook 挂在 FlatParameter 的 `AccumulateGrad` 上，反向传播算完 FlatParameter 的梯度会触发它。

`_post_forward` 里的 `reshard` 反向操作：

```text
def reshard(self, free_unsharded_flat_param):
    self._use_sharded_flat_param()
    if free_unsharded_flat_param:
        self._free_unsharded_flat_param()
```

把 flat_param 指针切回本地 shard，然后 `_free_unsharded_flat_param` 把完整 buffer 的 storage `resize_(0)`。它还会给输出张量挂一个 pre-backward hook，反向传播到达本 unit 前触发再一次 unshard。

### 3.4 反向

反向流程跟前向对称。

autograd 引擎沿计算图走到某个 FSDP unit 的输出张量时触发 pre-backward hook：

```text
def _pre_backward_hook(state, module, handle, grad, *unused):
    handle._training_state = HandleTrainingState.BACKWARD_PRE
    if handle._needs_pre_backward_unshard and not handle._prefetched:
        _unshard(state, handle, state._unshard_stream, state._pre_unshard_stream)
    state._device_handle.current_stream().wait_stream(state._unshard_stream)
    _prefetch_handle(state, handle, _PrefetchMode.BACKWARD)
```

三件事：参数没被 prefetch 就发起 all-gather，等 all-gather 完成，顺手 prefetch 前一个 unit。

参数恢复后 autograd 正常算反向，得到 FlatParameter 的完整梯度。梯度算完的一刻触发之前挂的 post-backward hook：

```text
@torch.no_grad()
def _post_backward_hook(state, handle, flat_param, *unused):
    flat_param._post_backward_called = True
    _post_backward_reshard(state, handle)
    with state._device_handle.stream(state._post_backward_stream):
        if flat_param.grad.dtype != handle._reduce_dtype and not handle._force_full_precision:
            flat_param.grad.data = flat_param.grad.to(handle._reduce_dtype)
        if handle.uses_sharded_strategy:
            _reduce_grad(state, handle)      # reduce-scatter
        else:
            _reduce_grad_no_shard(state, handle)  # all-reduce
```

四件事：先重新分片释放完整参数、切到专门的通信流让通信和计算并行、如果配了低精度 reduce 做 dtype cast、发起 reduce-scatter 把完整梯度按 rank 切分求和。结果存到 `flat_param._saved_grad_shard`，等 optimizer step 使用。

`_post_backward_reshard` 内部还会做 backward prefetch，让前一个 unit 的 all-gather 跟当前 unit 剩下的收尾计算重叠。这是 FSDP1 通信-计算重叠的核心机制。

### 3.4 混合精度：master weight 是 shard 状态

FSDP1 的混合精度做法跟 apex/amp 有一点不同：fp32 master weight 始终以 shard 形态存在，unshard 出来的完整参数直接是低精度（fp16 或 bf16），不额外维护低精度副本。

参数存储是 fp32（对应 `flat_param._local_shard`），要用的时候通过 all-gather + dtype cast 拿到完整 bf16 参数。峰值显存不由所有参数决定，只由最大 FSDP unit 的完整参数副本决定。

这里 FSDP1 相对 DeepSpeed 的一个隐藏优势就体现出来了：optimizer 什么都不用改。DeepSpeed 那边为什么必须重写 optimizer？因为 ZeRO 接管了参数、梯度、optimizer state，参数在 unshard 前后的 dtype 语义、梯度的 scaling 逻辑都是 DeepSpeed 的 optimizer 自己控制。所以 DeepSpeed 必须为每种精度组合实现一个 optimizer 版本。

FSDP1 的设计原则是不让 optimizer 感知分片。optimizer 看到的是合法的 `nn.Parameter` 列表（就是本 rank 的 sharded FlatParameter），完全不知道参数曾经 unshard 过、也不知道通信存在。混合精度问题被限制在”参数 materialization 阶段”，每个 FlatParameter 在其前向之前以及反向之前各产生一次精度转换。

一句话：FSDP 重写了 Parameter，DeepSpeed 重写了 optimizer。

### 3.5 对标：FSDP1 与 DeepSpeed 对比

用了 FSDP1 之后能感受到几个直接的收益：

**显存效率更高**。DeepSpeed 会额外维护一份独立的 FP32 Master Weight，与用于计算的 BF16 分片参数同时存在于显存中；而 FSDP1 将分片参数直接以 FP32 格式存储，这个 FP32 参数本身就充当了优化器更新的“主权重”角色，计算时通过 all-gather 收集完整参数并临时转换为 BF16，计算完成后 BF16 临时副本即被释放。所以 FSDP1 显存占用少一点。

**通信兼容更好**。FSDP 把三种边界合成一个概念（FSDP unit），用户只需要选一次粒度。

**兼容任意 optimizer**。FSDP1 只影响模型本身，向优化器提供的还是它自己参数集的权重和梯度。用户可以直接用 `torch.optim.Adam`、`torch.optim.SGD`，不需要 DeepSpeed 那套 initialize。

**动态图支持**。FSDP1 靠 hook 触发通信，不依赖固定的模块调用顺序。分支控制流、多次调用同一层都能处理（虽然有 hook 挂错的边界情况，后面会讲）。

**Bug 少一些**。至少在高频场景下，FSDP1 的坑比 DeepSpeed 少得多。

### 4. FSDP1 有什么问题

用 FSDP1 对下面几个坑应该都不陌生。

**元数据脆弱**。FlatParameter 是 1D 张量，但用户看到的 `wq.weight` 应该是 `[d, d]` 的矩阵，FSDP1 靠一大堆元数据把两者对起来。原始 shape、stride、offset、padding、cross-rank 边界都要维护。要接一个新的抽象（TP、DTensor、量化）时都要重新处理这些元数据。

**LoRA 类场景显存浪费**。冻结和非冻结参数必须分到两个 FlatParameter 上，否则 frozen 参数也会分配 grad buffer。这就要求用户按 `requires_grad` 属性手动拆分 wrap 粒度。

**混合精度和量化受限**。所有参数摊在同一个 1D buffer 里、且必须同 dtype。fp8、NF4 这种数据加 scale 的量化格式没办法直接接入 FlatParameter。

**Prefetch 简单粗暴**。FSDP1 有个 rate_limiter 默认设为 2，意思是最多允许 2 层的 all-gather 同时在飞。这个数字选大了，某层计算慢时会有连续几层的完整参数一起堆在显存里，OOM；选小了通信重叠不足，性能损失。FSDP1 的解法是在每个 TransformerBlock 后阻塞 CPU，等前一层 all-gather 完成再开下一层。比较粗暴。

**record_stream 导致显存不稳**。FSDP1 为了在通信 stream 和 compute stream 之间共享 buffer，到处调 `tensor.record_stream(comm_stream)`。这个 API 告诉 caching allocator “这块内存还在另一条流上用，别急着回收”。问题在于回收时机依赖 allocator 的内部状态，非常不确定，显存峰值经常飘。真跑起来能看到同样的配置每次 OOM 的 step 都不一样。

**AccumulateGrad hook 触发时机不稳**。FSDP1 把 post-backward hook 挂在 FlatParameter 的 `AccumulateGrad` 上。这个 hook 的语义是”参数梯度累加完成时通知你”，但如果参数被共享使用（同一个 Linear 在 forward 里被调两次）、有梯度累积、或者 `retain_graph=True`，”何时累加完”这件事的语义并不清晰。真实测试里能观察到 hook 触发时 `.grad` 属性还是 None 的情况。这个坑要到 FSDP2 才被彻底修好。

这些痛点大多不是修个补丁能解决的。它们跟 FlatParameter 这个基础抽象绑得太紧。要根除必须从底层重来，这就是下一篇 FSDP2 要讲的事。

## 5. FSDP2 时代：用 DTensor 重写

FSDP1 的 FlatParameter：把一层参数拍成 1D、切给 world_size 个 rank、靠一堆元数据把 1D 视图翻译回原始参数。

这套抽象通信效率高，但也留下了不少坑：LoRA 场景显存浪费、fp8/NF4 接不进来、`record_stream` 让显存峰值飘忽、`AccumulateGrad` hook 触发时机不稳。那么 FSDP2 是怎么把这些坑一次性刨掉的。

### 5.1 FSDP2 的目标：让每个参数自己就是分布式张量

FSDP1 的问题几乎全都指向一个根：FlatParameter 不是一个”语义上有意义的张量”。它是一堆参数拼起来的 1D 数据，用户看到的 `wq.weight` 是个假的 view，混合精度、checkpoint、TP 叠加都得绕开这个 view 去操作元数据。

FSDP2 想问的是：如果每个参数自己就是一个分布式张量，我知道自己在什么 mesh 上、以什么方式切分，会不会所有事情都变简单？

答案是会。这就是 DTensor 出现的动机。

FSDP2 具体想解决的问题有四个：

- 让 optimizer 看到的参数就是合法 `nn.Parameter`，还能自然叠加 TP、EP、HSDP 等其他并行维。
- 让 checkpoint 保存和加载不需要跨 rank 通信。
- 让 fp8、NF4 这种”数据+scale”的量化格式能作为参数直接进入 all-gather 流程。
- 让显存管理确定：不再依赖 `record_stream` 的隐式回收，也不再让 hook 挂在语义不清的 `AccumulateGrad` 上。

### 5.2 DTensor：张量自己就知道自己怎么切

DTensor 是 `torch.Tensor` 的子类，本质是一个三元组：

```text
DTensor = (local_tensor, DeviceMesh, Placements)
```

- `local_tensor` 是这一个 rank 上实际持有的那部分数据。
- `DeviceMesh` 是一个多维的进程网格，比如 `[dp=8, tp=4]` 描述了 32 个 rank 怎么排布。
- `Placements` 描述这个张量在 mesh 的每一维上是怎么放的：

举个例子。8 卡上一个 `[4096, 4096]` 的权重，在 FSDP 语义下就是 `DTensor(local_tensor=[512, 4096], mesh=[dp=8], placements=[Shard(0)])`。每张卡本地持有 dim 0 上的 512 行，读它的 `.shape` 会告诉你完整是 `[4096, 4096]`。

跟 FlatParameter 相比，DTensor 有两个直接的好处：

**shape 是原始 shape**。`wq.weight.shape` 就是 `[4096, 4096]`，不是 1D。用户和下游代码不需要知道分片存在。

**分片信息是张量自己的一部分**。TP、EP、HSDP 只是 mesh 多一维、placement 换个组合，`[Shard(dp), Shard(tp)]` 就是”先按 dp 切 dim 0、再按 tp 切 dim 1”。FSDP1 想叠加 TP 得从头改代码。

### 5.3 FSDP2 怎么用 DTensor 做参数分片

FSDP2 给每个 `nn.Parameter` 包一个 DTensor。对外可见的 `module.weight` 不是 FlatParameter 里的假 view，而是一个真实的、带 mesh 和 placement 的 DTensor。

一件看上去简单的事，实际带来的连锁反应非常大：

**Optimizer 零改动**。Adam 看到的是合法的 `nn.Parameter` 列表，只不过它们恰好是 DTensor。element-wise 运算（加减乘除）在 DTensor 上会自动分派到 local_tensor 上执行。每个 rank 上 Adam 只对本地那 `[512, 4096]` 做 element-wise，根本不知道什么叫分片。这跟 DeepSpeed 必须为每种精度重写 Adam 是两条完全不同的路。

**Checkpoint 零通信**。每个 rank 自己保存自己的 shard 元信息，加载时按 mesh 重建。FSDP1 存 checkpoint 时要先 all-gather 或者靠 `FULL_STATE_DICT`，很慢；FSDP2 默认走 `SHARDED_STATE_DICT`，每个 rank 直接把自己那份写盘，还支持异步 checkpoint。

**TP、EP、HSDP 自然叠加**。参数已经是 DTensor 之后，再套一层 FSDP 只是在 mesh 上加一维。TorchTitan 里的做法就是先 `apply_tp`，让参数变成 `[Shard(tp)]` on tp_mesh 的 DTensor，然后 `data_parallel` 再加一层 `[Shard(dp), Shard(tp)]` on spanned_mesh。这是 DTensor 抽象最直接的收益，后面 TorchTitan 那篇会细说。

**Padding 局部化**。FSDP1 是”一个超大 1D buffer 整体补齐”，某个参数补一点就要顺带把整个 buffer 的 padding 边界都算清楚。FSDP2 是每个参数自己补齐：

```text
chunks = _chunk_with_empty(param_data, shard_world_size, dim=shard_dim)
padded_sharded_size = chunks[0].size()    # rank 0 永远最大
padded_sharded_param = param_data.new_zeros(padded_sharded_size)
padded_sharded_param[: chunks[self.rank].size(shard_dim)].copy_(chunks[self.rank])
self._sharded_param_data = padded_sharded_param.view(-1)
```

每个 `FSDPParam` 维护自己的 padding，互不干扰。

### 5.4 显存管理：抛弃 record_stream

FSDP1 的显存不稳来自 `record_stream`。FSDP2 换了两个机制。

**用 `storage.resize_()` 控制实际占用**。unsharded 参数的 `nn.Parameter` 对象只构造一次，状态切换时只是把底下的 storage 在 0 和 `numel` 之间来回 resize。这保留了 autograd 在 forward 里保存的 view 别名——即使 storage 被释放，view 也不会变成野指针。

**跨流生命周期用 NamedTuple + Event 显式管理**。看一段 `_fsdp_param_group.py` 里的代码：

```text
class AllReduceState(NamedTuple):
    # Holding all_reduce_input keeps the caching allocator from reusing the block
    # across layers. This is a structural invariant, not bookkeeping: without it,
    # the next layer's RS can reuse the same physical block before this layer's
    # AR finishes under slow AR, causing gradient aliasing.
    all_reduce_input: torch.Tensor
    event: torch.Event | None
```

读懂这段注释才知道它在防什么。HSDP 模式下 all-reduce 跨节点可能很慢。下一层的 reduce-scatter 如果复用了同一块物理内存，前一层 AR 的结果会被覆盖——一个极隐蔽的梯度串味 bug。FSDP2 的做法是直接用一个 Python 引用攥住那块 tensor，allocator 看到引用就不会回收，等 event 触发后再一起释放。

“用 Python 对象生命周期加 Event 等待来代替 record_stream”这套做法，是 FSDP2 显存稳定且可预测的根本原因。同样的 batch size 每次跑，显存峰值不再飘忽。

### 5.5 运行时：hook 挂在哪、什么时候触发

FSDP2 的 forward 和 backward 靠模块的 pre/post hook 加自定义 `autograd.Function` 驱动。以一个 TransformerBlock 为例：

```text
forward 进 block 之前：
  _pre_forward
    └─ unshard()           # 发起 all_gather，等待
    └─ register_post_backward_hook  # 把反向阶段的入口挂上
    └─ prefetch 下一个 block

执行原 block 的 forward

forward 出 block 之后：
  _post_forward
    └─ reshard()           # 释放 unsharded buffer
    └─ register_pre_backward_hook   # 在输出张量上挂"反向时通知我"

backward 进 block 之前：
  _pre_backward (输出张量的 hook)
    └─ unshard()
    └─ prefetch 前一个 block

backward 算完之后：
  _post_backward (RegisterPostBackwardFunction 的 backward)
    └─ reshard()
    └─ foreach_reduce()    # reduce_scatter 梯度
```

跟 FSDP1 最大的区别在最后一步。FSDP1 把 post-backward hook 挂在 FlatParameter 的 `AccumulateGrad` 上，语义是”参数梯度累加完成时通知你”。这个语义在参数被共享、有梯度累积、`retain_graph=True` 的时候会出问题。

FSDP2 换了做法：把”反向时触发 reduce-scatter”挂在一个自定义 `autograd.Function` 上，让 autograd 引擎按图论顺序保证触发时机。

### 5.6 为什么 AccumulateGrad hook 不可靠

看一个具体例子。一个共享 `Linear` 在两个地方使用：

```text
import torch
import torch.nn as nn

torch.manual_seed(0)

class Outer(nn.Module):
    def __init__(self):
        super().__init__()
        self.shared = nn.Linear(4, 4, bias=False)
        self.tail = nn.Linear(4, 4, bias=False)

    def forward(self, x):
        h = self.shared(x)          # shared 第一次使用
        m = self.tail(h)
        return self.shared(m)        # shared 第二次使用

mod = Outer()

def on_backward(module, grad_input, grad_output):
    g = mod.shared.weight.grad
    norm = None if g is None else g.norm().item()
    print(f"tail hook fired, shared.weight.grad = {norm}")

mod.tail.register_full_backward_hook(on_backward)

x = torch.randn(8, 4, requires_grad=True)
mod(x).sum().backward()
print(f"after backward, shared.weight.grad = {mod.shared.weight.grad.norm().item()}")
```

实测输出（PyTorch 2.10）：

```text
tail hook fired, shared.weight.grad = None
after backward, shared.weight.grad = 3.698394536972046
```

hook 触发时 shared 参数的第一段梯度还没累加进来。也就是说，如果 FSDP1 靠 hook 的这个触发时刻去发起 reduce-scatter，它拿到的 `.grad` 是不完整的。

换成 autograd 节点之后，触发时机由 autograd 引擎本身按图论顺序保证，跟参数是否被共享、是否累积无关。这是 FSDP2 反向更稳健的根本原因。

### 5.7 FSDP2 多流并行机制

在 ZeRO-3 分片策略下，前向传播需要先通过 all-gather 从各 GPU 收集完整参数，再进行计算。随着集群规模扩大，all-gather 通信时间已显著超过计算时间（实测中可达计算耗时的 2 倍）。

传统的两级流水线（通信 → 计算）已无法有效掩盖通信延迟，FSDP2 因此将 all-gather 拆解为更细粒度的阶段，通过多 CUDA Stream 实现三级甚至四级流水线。

在 `fsdp_param_group.py` 中，FSDP2 管理了以下 CUDA Stream：

| Stream | 职责 |
| --- | --- |
| all_gather_copy_in_stream | 将分散的 sharded 参数拷贝拼接成连续的 all-gather 输入缓冲区 |
| all_gather_stream | 执行节点内（GPU 间）的 all-gather 集合通信 |
| reduce_scatter_stream | 执行节点内的梯度 reduce-scatter 通信 |
| all_reduce_stream | 执行节点间（跨机器）的梯度 all-reduce 通信 |
| 默认流 (default) | 执行前向/反向的核心计算 |

实际运行时，通常只有 **2 个通信流 + 1 个计算流** 同时活跃，形成三流并行；多节点场景下会临时激活 `all_reduce_stream`，扩展为四级流水线。

**前向：三级流水线**

`foreach_all_gather` 实现了前向的三流并行调度：

```text
时间轴 →
Layer N   |    [Compute N]
Layer N+1 |        [Copy-in N+1] → [All-Gather N+1]
Layer N+2 |             [Copy-in N+2] → [All-Gather N+2]
          ↑               ↑                  ↑
      default        all_gather_       all_gather_
      stream         copy_in_stream    stream
```

三个流各司其职：

- `all_gather_copy_in_stream` 准备第 **N+2** 层的数据
- `all_gather_stream` 执行第 **N+1** 层的通信
- 默认流计算第 **N** 层

形成稳定的流水线，通信开销被后续层的计算完全掩盖。将 copy-in 单独拆分是关键优化点——DeepSpeed 未做此拆分，导致该操作常阻塞主计算流。

**反向：三级（或四级）流水线**

反向传播的调度在 `foreach_reduce` 中实现：

1. **默认流**：计算第 **N** 层的梯度
2. **`reduce_scatter_stream`**：对第 **N+1** 层的梯度执行节点内 reduce-scatter
3. **`all_gather_stream`**：预取第 **N-1** 层的参数（为下一层反向做准备）

**多节点场景**：额外在 `all_reduce_stream` 中异步同步第 **N+2** 层的跨节点梯度，形成四级流水线。

| 维度 | DeepSpeed ZeRO-3 | FSDP2 |
| --- | --- | --- |
| 流水线粒度 | 粗粒度，all-gather 不可拆分 | 细粒度，copy-in/通信/copy-out 拆分到不同流 |
| 通信掩盖 | 仅通信与计算粗糙重叠 | 通信内部各阶段之间相互重叠 |
| Copy-in 处理 | 未单独优化，常阻塞主计算流 | 独立流处理，与通信并行 |
| 显存稳定性 | 大集群下碎片和超时频发 | 显存管理更稳健，确定性更好 |
| 多节点扩展 | 无额外流水线 | all_reduce 独立流，形成四级流水线 |

FSDP2 正是通过这些精细的流调度，在多节点训练场景下实现了对 DeepSpeed ZeRO-3 优化。

### 5.8 如何支持fp8 量化格式

FSDP2 还在 `FSDPParam` 上开了两个协议方法，让自定义 Tensor 子类可以参与 all-gather：

```text
class Float8Tensor(torch.Tensor):
    def fsdp_pre_all_gather(self, mesh, ...):
        # 把 fp32 master shard 量化为 fp8 数据 + scale
        return (fp8_data, scale), metadata

    def fsdp_post_all_gather(self, all_gather_outputs, metadata, ...):
        # 收完之后重构成 unsharded fp8 tensor
        return Float8Tensor(fp8_data, scale), [fp8_data]
```

这个能力 FSDP1 做不到。FlatParameter 强制把所有参数摊成同 dtype 的 1D buffer，”数据 + scale”这种复合结构塞不进去。

FSDP2 因为每个参数是独立的 DTensor，而且 all-gather 协议允许多输入多输出，fp8、NF4（QLoRA）这类量化格式可以直接接入。这也是 FSDP2 能成为 torchao、torchtune 等下游项目默认底座的原因。

### 5.9 对标：FSDP2 相比 FSDP1 拿到了什么

用一张表看得清楚：

| 维度 | FSDP1 | FSDP2 |
| --- | --- | --- |
| 参数表示 | FlatParameter（1D 张量+一堆元数据） | 每个参数是 DTensor |
| Optimizer 感知 | 看到的是 1D 张量，需要 handle 元数据翻译 | 看到 nn.Parameter，其实是 DTensor |
| 混合精度 | 靠 handle 元数据管理 | DTensor 的 forward/backward dtype 参数 |
| Checkpoint | 需要通信或者按 rank 存元数据 | 每个 rank 直接存自己的 shard 元信息 |
| 显存管理 | record_stream，回收时机不确定 | storage.resize_() + Event 显式管理 |
| Post-backward hook | 挂 AccumulateGrad，共享参数场景有坑 | 自定义 autograd.Function，autograd 保证顺序 |
| LoRA 混合冻结 | frozen 和 trainable 必须拆两个 FSDP unit | 同一 unit 内混用，不多花梯度显存 |
| fp8 / NF4 | 接不进来 | 通过 fsdp_pre_all_gather 协议接入 |
| TP / EP 叠加 | 需要手写胶水 | 通过 mesh 多加一维、placement 换组合自动处理 |

## 6. FSDP2 有什么问题

FSDP2 也不是没坑。

**冷启动稍慢**。DTensor 的 dispatch 路径比 FlatParameter 的直接调用长一些。第一次 iteration 有 dispatch 开销，虽然不至于像 SimpleFSDP 那样要等编译几分钟，但相比 FSDP1 感觉得到。

**Prefetch 是启发式的**。FSDP2 的 `set_modules_to_forward_prefetch` 和 `set_modules_to_backward_prefetch` 允许用户显式指定 prefetch 顺序，但默认是”按 forward 记录顺序 prefetch 下一层”。碰上 MoE 这种执行顺序被 D2H sync 打乱的场景，隐式 prefetch 会失效，得手动接管。这个坑在 TorchTitan 的 MoE 部分体现得很明显。

**MoE 里专家和非专家的 DP 除数不同**。FSDP2 默认按 mesh 大小做 gradient average，MoE 里专家参数的有效 DP mesh 比非专家小，直接用默认除数会让梯度 scale 不一致。FSDP2 通过 `set_gradient_divide_factor` 或者用 `_ScaledPartial` 让用户显式修正，但这是一个”不显式配就错”的隐藏地雷。

**大规模 TP overlap 相比 Megatron 还是差一截**。DTensor 的 redistribute 是 lazy 的，编译器一般会把 all-gather 和后续计算做 stream 级 overlap，但很难做到 Megatron 那种”AG 内部 kernel 交错在 GEMM 里面”的极致 overlap。这一点也放到 TorchTitan 加 Megatron 细讲。

**默认全参数分片，显存换通信换得多**。FSDP2 默认 ZeRO-3，参数、梯度、optimizer state 全切。相比 Megatron 默认”每 rank 完整参数副本，只切 optimizer”，FSDP2 通信量更大、显存更省。哪种适合，看你的瓶颈在哪。

## 7. 小结

FSDP1 的 FlatParameter 用一个 1D 张量把整层参数打包，通信效率上去了，但通用性和显存稳定性差。FSDP2 把每个参数换成 DTensor，让每个张量自己就知道自己在什么 mesh 上、以什么 placement 分布。这一步换来了：optimizer 零改动、TP/EP 自然叠加、fp8/NF4 能接入、checkpoint 无通信、显存管理确定、post-backward hook 挂在语义清晰的位置。代价是抽象层多了一点，冷启动慢一点。

有了 FSDP2 这套原语（mesh、DTensor、`fully_shard`、`parallelize_module`），真正训练一个能跑 TP + CP + FSDP + EP + PP 五维并行的大模型时会碰到哪些问题？

TorchTitan 给出了一份工程化的参考答案，Megatron 给出了一份几乎相反的答案。下一篇就讲这两条路。
