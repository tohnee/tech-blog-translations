## 把模型跑起来

首先，在 Gemini 大人的指导下。在 HF 上下载模型的权重和算法描述，并且转成 irpa 权重格式（这个格式就是 IREE 的数据表达方式）以及 mlir 格式的网络结构。

```bash
optimum-cli export onnx --model Qwen/Qwen2.5-0.5B \
  --task text-generation ./my_qwen_onnx/

iree-import-onnx ./my_qwen_onnx/model.onnx \
  --large-model \
  --externalize-params \
  --save-params-to qwen.irpa \
  --opset-version 17 \
  -o qwen.mlir
```

然后，就可以把模型编译起来了。IREE提供了选项把中间步骤给整理到文件夹里面，而不是全输出到 stdout 里面。

```bash
iree-compile \
  --iree-hal-target-backends=llvm-cpu \
  --iree-llvmcpu-target-cpu=host \
  --mlir-print-ir-tree-dir=./qwen_ir_steps \
  --mlir-print-ir-after-all \
  --mlir-print-ir-after-change \
  qwen.mlir \
  -o qwen.vmfb
```

也可以直接编译到目标步骤，IREE 的 iree-compile过程设计了三层 IR，首先是 Input 层，产出整图的 linalg IR 负责算法描述。其次是 flow 层，它决定了哪些 op 会被融合在一起，我理解就是算子融合。最后是 stream 层，这一层进一步划分，做Bufferization 、以及把 flow 层产生的 host 侧代码进一步 Lowering 成类似 cudaEvent + cudaStream 的形式。

```bash
iree-compile \
  --iree-hal-target-backends=llvm-cpu \
  --iree-llvmcpu-target-cpu=host \
  --mlir-print-ir-tree-dir=./qwen_ir_steps \
  --mlir-print-ir-after-all \
  --mlir-print-ir-after-change \
  --compile-to=input \
  qwen.mlir \
  -o qwen_input.mlir
```

## 输出vmfb

简而言之就是调度逻辑与编出来的算子二进制打包塞进了一个文件里面。

IREE 实现了一个自己的 runtime（非常轻，不到100K），在嵌入式场景里面，编出来的runtime跑在主控 CPU 上（比如说人民群众喜闻乐见的 riscv cpu 吧）。vmfb 中的 host 部分代码可以被 runtime 解释执行。对于 device 部分，vmfb 中 host 的 kernelCall 会被解释成 rtKernelLaunch，kernel 部分的二进制 bin 会被作为 rtKernelLaunch的参数。这样就实现了把 vmfb 里面打包的 .so 核函数给加载到对应的 device 上面去。我理解是这么一个过程，简单画了一下：

## 各部分探究

### 编译到 input 阶段

使用 `--compile-to=input`将直接导出的 ONNX 网络编译到了 linalg 层。它的 IR 长下面这样（为了简化，我请 HaGimi 4 Argon 保留 IR 骨架重写了一下，仅仅展示 IR）：

```c
#map = affine_map<(d0, d1) -> (d0, d1)>
#mapS = affine_map<(d0, d1) -> ()>
module {
  util.global private @embed_tokens_weight = #stream.parameter.named<"model"::"model.embed_tokens.weight"> : tensor<151936x896xf16>

  util.func public @main_graph$async(%ids: !hal.buffer_view, %wait: !hal.fence, %signal: !hal.fence) -> !hal.buffer_view attributes {inlining_policy = #util.inline.never, iree.abi.model = "coarse-fences", iree.abi.stub} {
    %c0 = arith.constant 0 : index
    %d0 = hal.buffer_view.dim<%ids : !hal.buffer_view>[0] : index
    %d1 = hal.buffer_view.dim<%ids : !hal.buffer_view>[1] : index
    %ok = arith.cmpi sgt, %d0, %c0 : index
    cf.assert %ok, "Expected dim size > 0."
    %t = hal.tensor.import wait(%wait) => %ids : !hal.buffer_view -> tensor<?x?xi64>{%d0, %d1}
    %w = util.global.load @embed_tokens_weight : tensor<151936x896xf16>
    // keep the scalar as a 0-d tensor so it stays on device
    %bias = tensor.extract_slice %w[0, 0] [1, 1] [1, 1] : tensor<151936x896xf16> to tensor<f16>
    %init = tensor.empty(%d0, %d1) : tensor<?x?xf16>
    %r = linalg.generic {indexing_maps = [#map, #mapS, #map], iterator_types = ["parallel", "parallel"]} ins(%t, %bias : tensor<?x?xi64>, tensor<f16>) outs(%init : tensor<?x?xf16>) {
    ^bb0(%in: i64, %b: f16, %out: f16):
      %v = arith.sitofp %in : i64 to f16
      %s = arith.addf %v, %b : f16
      linalg.yield %s : f16
    } -> tensor<?x?xf16>
    %done = hal.tensor.barrier join(%r : tensor<?x?xf16>) => %signal : !hal.fence
    %out = hal.tensor.export %done : tensor<?x?xf16>{%d0, %d1} -> !hal.buffer_view
    util.return %out : !hal.buffer_view
  }

  util.func public @main_graph(%ids: !hal.buffer_view) -> !hal.buffer_view attributes {iree.abi.stub} {
    %c0 = arith.constant 0 : index
    %timeout = arith.constant -1 : i32
    %null = util.null : !hal.fence
    %dev = hal.devices.get %c0 : !hal.device
    %fence = hal.fence.create device(%dev : !hal.device) flags("None") : !hal.fence
    %r = util.call @main_graph$async(%ids, %null, %fence) : (!hal.buffer_view, !hal.fence, !hal.fence) -> !hal.buffer_view
    %status = hal.fence.await until([%fence]) timeout_millis(%timeout) flags("None") : i32
    util.return %r : !hal.buffer_view

```

`util.global`。它定义了跨 func 的常量，即权重数据。后续在函数内使用 `util.global.load`来表示将此静态数据加载进来。这个表达方式很合理。

- 权重数据一般会驻留在显存上面，在后面 flow dispatch 的时候，会把这load变成从 host 到 device 的复制指令。比如说 cuda 的 `copy_host_to_device`之类的 runtime 接口。
- 上面的节选，没把这些 load 出来的 tensor 的 user 给截到。一般来说他们会直接被 `linalg.generic`所使用。这些 load 的位置在 host 侧，而我们 `linalg.generic` 就被打包到 device 上面了。打包的方式就是 flow 把他们划分到同一个 region 里面，后面的融合只会在 region 内进行。

`util.func` ，我理解它和 `func.func`没有本质区别。 从源码角度看，也确实如此，它在 TableGen 里面的定义与后者基本相同。在AI帮助下，我们聚集于不同之处：

1. 复用属性：支持写“第y个返回值复用了第x个输入”的复用逻辑表达。comment: 这个特性我们当前的例子里面没有用到，也许之后会探究吧。我觉得这个功能其实 func.func 用 attributes 做也是可以的。不过把它固化成 Op 本身的可选 Attributes 貌似**更符合 MLIR 编程规范**。总之还是合理的。
2. 内联控制属性：InliningPolicy 属性控制 func 是否可以/应该被内联。这玩意其实类比 `func.func` 的 `no_inline`，不过 no inline 只是一个 bool 属性，只能由被调用的函数声明自己是否可以内联，调用处无法参与判断 。而 inliningPolicy 则是 AttributeInterface。用户可以实现判断逻辑来判断要不要进行内联。常见场景就是只有当调用者和被调用者都在 device 侧的时候才可以内联。
3. SignatureExpand：遇到签名展开，即类似 MLIR 中的 memref 类型被展开成 `llvm.struct< ptr, ptr, ptr, i32, i32 >`的情况，IREE 也需要在某一时刻从结构化表达的内存引用，转换到指针。而前者是通过 ConversionPattern 而自然实现的。由于**IREE 中相关场景并不符合 `TypeConversion`这个名词，通过自定义 Pass 来实现这件事情**。

总之，这些事情都不是 `func.func`+ Attribute无法做到的。但常言道，IREE 这么做，一定有他的道理。我能想到的道理就是增加代码可读性，减少代码量。

`@main_graph`与`@main_graph$async`的区别。这俩后者是异步函数，前者是对后者的同步版本薄封装。

在异步函数内，存在着一些`!hal.fence`以及对它的 wait & join：

```java
    %8 = hal.tensor.import wait(%arg3) => %arg2 : !hal.buffer_view -> tensor<?x?xi64>{%6, %7}
    %2014 = hal.tensor.barrier join(%2013 : tensor<?x?x151936xf16>) => %arg4 : !hal.fence 
```

所截的部分，能看到上面这两条。**我怀疑**是网络级别的同步机制？其中 `%arg3`的类型是`!hal.fence`，其实就是一个信号量。在读取时，要先等某个信号就绪。在做完某件事后，要释放某个信号。一个整图级别的信号同步，很合理。

这样，如果我们用异步的 style 来使用这个函数，就可以把这些 buffer 当作一个 future 变量传下去，不阻塞住调度逻辑。让调度器能够往执行机里面不断狂暴塞入新的算子。只有在真正需要同步的时候再调用 await.

**关于 distributed 的调度**

`module`上面被加上了一个属性 `attributes{stream.affinity.default= #hal.device.affinity<@__device_0>}`， 意思是这个整个module都被放在 device_0 上面计算。换言之，IREE 不会自动帮我们做 distribute 调度。

**关于 kernelLaunch 参数**

其次是 `flow.executable`，这就是我们刚刚说到的 device 部分的代码。注意到每个 region 内部都有一个这个玩意：

```java
    flow.executable.export public @main_graph$async_dispatch_0_elementwise_broadcast_Dx896_i64xf16 workgroups(%arg0: index) -> (index, index, index) {
      %x, %y, %z = iree_tensor_ext.dispatch.workgroup_count_from_slice(%arg0)
      flow.return %x, %y, %z : index, index, index
    }
```

它的意思很简单，就是计算 `rtKernelLaunch<<<gridDim, blockDim, stream>>> ("@main_graph$async_dispatch_0_elementwise_broadcast_Dx896_i64xf16")` 里面的 gridDim 参数。为什么只计算 gridDim 不计算 blockDim 呢？因为一般来说 blockDim 是固定大小的，编译器会根据最大的 block （所谓的 `vector shape`）大小切分低维。同时，也因为它对应我们模型的 feature 维度。而 gridDim 一般是动态大小的，它对应我们的 batch 维度、 sequence 维度和 expert 维度。（当然，如果 feature 维度放不下了，也需要切 feature 维度吧。）因此需要根据实际的长度，在运行时决定切分大小。

说了这么多，好像并没有说到这里的代码的意思。它的意思就是，根据host侧传入的值 `%arg0`，动态计算 `%x, %y, %z`，作为 rtKernelLaunch 的 gridDim 启动参数传给 kernel。

另外，在 kernel 里面也可以注意到参数 `%arg0`，其实它和上面的 `%arg0`是同一个东西。 注意到这几句

```java
    builtin.module {
      func.func @main_graph$async_dispatch_0_elementwise_broadcast_Dx896_i64xf16(%arg0: index, %arg1: !iree_tensor_ext.dispatch.tensor<readonly:tensor<151936x896xf16>>, %arg2: !iree_tensor_ext.dispatch.tensor<readonly:tensor<?xi64>>, %arg3: !iree_tensor_ext.dispatch.tensor<writeonly:tensor<?x896xf16>>) {
        // ...
        // 本函数里的 %arg0 和上面那个 flow.executable.export 里面的 0 号参数对应
        %0 = iree_tensor_ext.dispatch.workload.ordinal %arg0, 0 : index
        // 本函数的 %arg2 的动态维度，就等于 %arg0。为什么会是动态的？因为对于 LLM 场景，本来就要支持 bs 和 seqLen 动态的。
        %1 = flow.dispatch.tie_shape %arg2 : !iree_tensor_ext.dispatch.tensor<readonly:tensor<?xi64>>{%0}
        %2 = flow.dispatch.tie_shape %arg3 : !iree_tensor_ext.dispatch.tensor<writeonly:tensor<?x896xf16>>{%0}
        // ...
        return
      }
    }
```

一个核函数，计算的规模有多大？这个问题，Host 侧在运行时才有答案，Device侧需要知道这个答案。Host 侧在运行时，根据固定算法计算出 gridDim，启动核函数。这是从编写算子的角度而言的。

从调度器者的视角，现在这样的实现合理。在调度阶段，留一个占位符，说明以后会根据 `%argxxx`这些动态维度大小做切分，但在调度阶段不关心切分。Host只需要知道，无论动态维度多大，这个 Kernel 都实现了功能。对于 Kernel 而言，也不用管切分动态维度。我只知道我需要计算的是 `tensor<?xf16>`还是 `tensor<?x896xf16>`就好了。

说来说去好像啥也没说，好像一句话就能概括 flow dialect 干的事：把要放到一个核函数里的东西，放进同一个 Region 里面。动态切分参数没有处理，但是留了几个占符方便之后切分处理。

**FlowIR 的算子融合**

说到把 linalgOp 放到同一个 region 里面这件事情，自然会想到算子融合。IREE是做了算子融合的。Flow 就是把合适放到同一个核里面的 Op 放到同一个核心里面。但是他的具体融合策略，之后再看。这篇笔记先不展开了。

**从 flow 到 stream 的变化**

可以观察到，flow 到 stream 对于 device 函数，控制流没有变化，数据流输入从 `tensor`变成了 `!stream.binding`（但是 linalg 还是通过 `stream.subbind`来抽出一个 view 来进行计算出新 tensor，然后再 `store`回去。熟悉 MLIR 的同学都知道，这是典型的 bufferize 的做法，只做了前半部分。后半部分对 `linalg.generic`的 bufferize 还没做）。

主要工作在 host 做。首先还是`bufferize`把一些 `flow.xxx`和`tensor`的dialect 变成了`stream.xxx`， 其中**数据流**由 `tensor<?xf16>`变成了`!stream.resource<transient>{%xx}`或者`!stream.resource<constant>{%cxx}` 这两种。控制流原本各个call之间的可并行关系是通过IR来控制的，现在显式的使用 `stream.concurrent`来并行。

相比 flow 使用 ssa 的 tensor use-define 链表示各条计算之间的顺序。stream 这里引入了 `stream.timepoint.*` 这个系列的 OP 以及对应的 `!stream.timepoint`类型和 `#stream.timepoint`属性来标识最后交由硬件之后，计算是什么样子的。
