模型越来越会推理，但真正接入数据需要外部程序参与。MCP 把这层连接方式做成了开放协议。这份报告沿着它的诞生、普及与重构，解释它为什么出现、解决了什么，以及今天已经走到哪里。

| MCP 发展重要节点 | 日期 / 版本 | 说明 |
| --- | --- | --- |
| 首次公开发布 | 2024-11-25 | Anthropic 发起并开源 |
| 最新稳定规范 | 2026-07-28 | 无状态协议核心 |
| 最近官方博客动态 | 2026-10-30 | Ruby SDK 达到 Tier 1 |

> 顺便提一下，MCP 目前最大的痛点是：每轮对话中都要给大模型注入较长的上下文（包括tool list等），接入MCP服务器后一般先拉取全部工具列表+每个工具完整JSON Schema、参数说明、描述。每一轮对话，都要把这一大段工具定义塞进给LLM的上下文里，哪怕你这一轮根本不用里面大部分工具，这一堆schema照样占token，越接多MCP服务，上下文膨胀越夸张。

当然后续引进一些优化思路，如：应用可以获取完整目录，却只向模型提供与任务相关的少数工具。也可以先提供一个搜索入口，等模型需要时再加载具体定义。提示缓存可以减少重复计算、费用和延迟，**但不等于工具定义不再占用模型的上下文窗口**。按需加载才是在减少实际进入上下文的内容。

MCP 的 **2026 年 8 月路线图**也明确提出“渐进式发现”：按需要了解工具和资源，避免预先接收完整目录。

CLI 调用工具的构想：

> 模型 → CLI 或代码执行环境 → MCP 客户端 → MCP 服务 → 行情 API

CLI 提供操作入口，MCP 负责后面的工具连接，两者可以配合。

## 01 · 会回答 ≠ 能完成一件事

先看一个常见需求。你打开 AI 助手，对它说：

```text
> 查一下腾讯控股 00700.hk 的最新股价，读读它最近的公告，再把摘要保存到我的笔记里。
```

这句话对人不难理解，但它要求助手做三类不同的事： **获取刚刚更新的数据、读取外部资料、向另一个应用写入内容** 。如果只有模型本身，没有外部工具和相应权限，就会遇到这些缺口：

- **知道概念，缺少现状**：模型可以解释什么是股价，却不能仅凭训练得到的知识确定此刻的价格。实时数据需要向行情服务查询。（大语言模型训练数据都会有覆盖的最后时间点，如 DeepSeek-V4.1-Flash-1017）
- **会做摘要，缺少原文**：模型擅长归纳文字，但先得拿到这家公司最新公告。你没有提供、应用也没有取回的内容，不会自动出现在模型眼前。（获取最新广告需要大模型具有调用外部工具的能力）
- **能写正文，缺少执行**：生成一段简报，不等于已经把它存进你的笔记。保存动作需要笔记服务实际执行，并获得相应授权。（模型需要文件操作等元工具）

信息不足时，模型可能说明不确定，也可能给出看似合理却没有依据的答案，也就是常说的“幻觉”。我们当然可以接入可靠工具来补充依据，但**工具结果仍具有一定的不确定性，特别是股票行情数据，如果数据的口径对不上，数据的准确性就不能保证** 。

而 Anthropic 一开始想解决的，就是大模型接入外部工具的连接方式太分散，不好统一管理的问题。

在 MCP 出现之前，AI 应用已经能借助外部工具（Function calling）做事。麻烦在于：一个助手接行情系统要写一套代码，换一个助手又要适配一次；再接笔记、文件和数据库，重复工作就越来越多。

以“**查询腾讯的最新行情**”这个场景为例，价格采用模拟数据。接入真实行情时，将查询函数内部替换为数据供应商的 HTTP 请求或 SDK 调用即可。

1. 传统 API：程序直接指定市场和股票。

```python
def get_hk_quote(code: str) -> dict:
    「」「查询港股行情，这里返回模拟数据。」「」
    return {
        「code」: code, 
        「last」: 123.45,
        「currency」: 「HKD」, 
        「source」: 「mock」
    }

def get_us_quote(symbol: str) -> dict:
    「」「查询美股行情，这里返回模拟数据。」「」
    return {
        「symbol」: symbol, 
        「price」: 234.56,
        「currency」: 「USD」, 
        「source」: 「mock」
    }

# 程序员明确写好：调用哪个接口、查询哪只股票
print(get_hk_quote(「00700」))
print(get_us_quote(「AAPL」))
```

2. Function Calling：模型理解需求，应用执行查询。

应用先向模型提供工具名称、用途和参数定义。用户说“帮我查一下腾讯最新股价”，模型提出调用请求：

```python
# 模拟模型返回的工具调用请求
call = {
    「name」: 「get_hk_quote」,
    「arguments」: {「code」: 「00700」},
}

# 当前助手自行维护工具与执行函数的对应关系
handlers = {
    「get_hk_quote」: get_hk_quote,
    「get_us_quote」: get_us_quote,
}

result = handlers[call[「name」]](**call[「arguments」])
print(result)  # 应用随后把查询结果交回模型
```

现在用户可以用自然语言提需求。**模型负责选择工具和填写参数，行情价格仍来自外部系统。** 换一个助手时，工具注册、参数说明和执行对接仍可能需要适配。

3. MCP：将行情查询封装为可复用的工具服务。

使用 `fastmcp` 注册原来的函数，客户端通过共同协议发现和调用：

```python
import asyncio
from fastmcp import FastMCP, Client

# 服务端：注册行情工具，自动生成工具描述和参数定义
mcp = FastMCP(「行情服务」)
mcp.tool()(get_hk_quote)
mcp.tool()(get_us_quote)

async def main():
    # 为便于演示，客户端与服务端运行在同一进程
    async with Client(mcp) as client:
        tools = await client.list_tools()
        print(「可用工具：」, [tool.name for tool in tools])

        # 将模型提出的调用，通过 MCP 发给服务端
        result = await client.call_tool(
            call[「name」], call[「arguments」]
        )
        print(result.data)

asyncio.run(main())
```

行情 API 的适配代码仍然存在，但可以集中维护在 MCP 服务端。不同的兼容助手通过相同方式发现、调用这些工具，减少重复接入工作。**MCP 统一的是连接方式；选择哪只股票由模型和应用处理，数据是否实时由行情源决定。**

2024 年 11 月 25 日，Anthropic 宣布开源 **Model Context Protocol** ，即“模型上下文协议”。它由 **David Soria Parra** 和 **Justin Spahr-Summers** 创建，目标是用一套开放规则减少这些零散的集成。[01](https://www.anthropic.com/news/model-context-protocol)

> 一项开放标准，使开发者能够在数据源与 AI 驱动的工具之间建立安全的双向连接。

用更直接的话说： **大家约定好工具怎么介绍自己、请求怎么发、结果怎么返回，AI 应用和工具服务就不用每次重新商量一套接法。**

发布时，Anthropic 同时给出了规范、SDK（方便开发者实现协议的工具包）、Claude Desktop 支持和一批现成连接示例，例如 GitHub、Slack、Google Drive 与 Postgres。开发者可以立即尝试。

它也借鉴了 **LSP，语言服务器协议** 的思路：编辑器与编程语言各自遵守同一接口，就能减少逐对适配。MCP 把这个办法用在 AI 应用与外部系统之间。[02](https://modelcontextprotocol.io/specification/2024-11-05)

## 02 · 先学会用工具，再统一接法

### 第一步：业务系统先提供一个入口，也就是 API

假设行情公司提供了一个接口：你给它股票代码，它返回价格和更新时间。这个供程序调用的入口，就是 **API** 。开发者原本就可以写程序去查询；难点是怎样让一句自然语言请求触发正确的查询。

### 第二步：模型给出调用意图，也就是 Function Calling

Function Calling 可以理解为 **让模型填写一张“工具调用单”** 。应用先告诉模型有哪些工具、各自能做什么、需要哪些参数。模型根据用户请求选择工具并生成参数，随后由应用执行。

1. **应用先介绍可用工具** 。例如：“有一个查询行情的工具，需要股票代码；有一个保存笔记的工具，需要标题和正文；还有一个查询天气的工具，需要经纬度和时间”
2. **模型选择工具，并填好参数。**看到“查询最新股价”，模型提出调用 `get_quote`，同时给出需要查询的代码。代码不明确时，可以先向用户确认。
3. **应用执行请求，外部系统返回数据。**应用检查请求与权限，再调用行情接口。真正的价格来自行情系统，模型没有凭空算出或刷新它。
4. **模型根据返回结果继续回答**。拿到价格与公告后，模型整理成简报；保存笔记或者获取天气数据则是另一次工具调用，执行成功后才能说“已保存”。

**一张“工具调用单”大致长什么样**

以下仅说明结构，`00700.hk` 是示例标识，不代表实际股票查询。函数名称和参数由服务提供者定义。

```json
{
  「name」: 「get_quote」,
  「arguments」: { 「symbol」: 「00700.hk」 }
}
```

它表达“希望调用什么”，不会自行完成查询。调用是否执行，以及结果如何返回，由应用和工具程序处理。

### 第三步：工具多了，需要共同规则，也就是 MCP

Function Calling 让模型能提出调用请求，但开发者仍要处理工具从哪里来、怎样列出可用功能、参数如何描述、请求怎样传过去，以及结果和授权怎么处理。换一个 AI 应用，这些工作又可能重做。

**MCP 把应用与工具服务之间的共同部分约定下来。** 工具提供者按规范开放能力，支持 MCP 的应用按规范接入。它和 Function Calling 通常配合使用。

| 名称 | 放到简报例子里 | 一句话理解 |
| --- | --- | --- |
| API（业务入口） | 行情服务接收股票代码，返回价格与更新时间。 | 外部系统提供“能做什么”的入口。 |
| Function Calling（模型的调用意图） | 模型提出“调用查询行情工具，参数是这个股票代码”。 | 让模型选择工具、填写参数，再由程序执行。 |
| MCP（共同连接规范） | 行情、公告和笔记服务，用约定的方式介绍工具、接收调用、返回结果。 | 让不同应用更容易复用同一套工具服务。 |

API 提供业务能力，Function Calling 表达模型的调用意图，MCP 统一应用与工具服务的连接方式。

### 以 4 个 AI 应用，连接 4 类业务系统为例

| 连接方案 | 示例中的适配工作 | 概念公式 |
| --- | --- | --- |
| 逐一适配 | 16 组定制连接 | M × N = 4 × 4 = 16次协议适配 |
| 使用 MCP | 4 份客户端接入 + 4 份服务端适配 | M + N = 4 + 4 = 8次协议适配 |

这里的 MCP 表示共同协议，不要求必须部署一个中央网关。MCP 方案对应 4 份客户端接入与 4 份服务端适配；减少的是重复集成，不是业务系统本身的复杂度。

把 4 个应用分别接到 4 个系统，可能需要维护 16 组连接。采用共同规则后，可以由 4 个应用各自支持客户端，再由 4 个系统各自提供服务端。推广到 M 个应用与 N 个系统，就是常说的 **M × N 向 M + N 收敛** 。这个公式说明重复适配的减少，不代表所有开发成本都能照此精确计算。

### 几个容易混淆的边界

**没有 MCP，也可以调用工具、完成多步任务。**MCP 主要改善连接与复用；选错工具、参数理解错误、任务规划不合理，仍需在模型和应用层面解决。它也不会自动统一各家模型的 API。

**RAG 让回答参考检索到的资料，MCP 可以连接这类检索服务。** RAG（检索增强生成）会先查找相关材料，再让模型据此回答。例如，先检索公告原文，再生成简报；其中的检索能力可以通过 MCP 提供给助手。它们可以协作，解决的不是同一个问题。

## 03 · 谁来连接？实际怎么用？

继续看那份公司简报。可以把整套系统理解为一个协作办公室：模型负责理解需求、分析材料；AI 应用提供工作台；里面的联络组件负责把请求送到对应的服务窗口。 **工作台、联络组件、服务窗口** ，分别对应 Host、Client、Server。

| 角色 | 职责 |
| --- | --- |
| Host（你使用的 AI 应用，如WorkBuddy、Chatgpt） | 例如桌面助手或带 AI 的编辑器。它接收你的需求，组织模型与工具协作，并管理数据访问和操作权限。一般说“在某个应用里添加 MCP”，就是在配置 Host。 |
| Client（应用里的联络组件） | 通常内置在 Host 中，负责按 MCP 规则与 Server 通信。普通使用者一般不需要再单独安装一个叫 Client 的软件。 |
| Server（提供工具与资源的程序） | 例如对外提供“查行情、读公告”的程序。一个 Server 可以提供多个工具，也可以连接多个后台系统；它既能在本地运行，也能部署在远程。 |

### 为什么名字里有“上下文”？

你让同事写简报，通常会把价格表、公告原文和格式要求一起给他。模型同样需要这些任务材料。 **Context 就是模型处理当前任务时能看到的信息** ，不只包括聊天记录，也包括应用提供的文件、工具结果等。MCP 帮助应用取得这些材料，再由应用决定怎样交给模型。

服务端主要可以提供三类能力。它们可以看成： **资源、工具、任务模板** 。

| 能力 | 通俗理解 | 提供什么 | 贯穿示例 |
| --- | --- | --- | --- |
| Resources | 资源：有什么可读 | 提供可读取的内容，例如某份公告原文、文件内容或数据表结构。 | 简报例子：一份公告原文 |
| Tools | 工具：可以做什么 | 提供可执行的功能，例如按代码查行情、搜索公告或保存笔记。 | 简报例子：查询、搜索、保存 |
| Prompts | 模板：按什么要求做 | 提供可复用的提示模板，约定摘要的角度、结构与所需输入。 | 简报例子：公司简报写作模板 |

这三类能力并不要求每个 Server 全部实现。公告原文可以作为资源读取，也可以由搜索工具返回。 **“工具”还可以执行只读查询，并非只有修改数据的操作才叫工具。**

普通使用者通常只需要明确以下四件事情：

1. **选择支持所需 MCP 能力的 AI 应用** 确认它能连接本地或远程服务，并支持你要用的功能。不同客户端的支持范围和配置入口可能不同。（如 stdio，sse 或者 streamableHttp）
2. **添加一个已有的 MCP Server** 远程服务通常提供地址；本地服务通常提供安装方法与启动命令。按该服务的官方说明配置即可，无须为了使用 MCP 先自己写一个服务器。
3. **配置账户和访问权限** 例如登录数据服务、配置服务端需要的凭证，或授权笔记应用。只读行情与写入笔记可能需要不同权限。
4. **提出需求，并确认操作结果** 助手发现可用工具后，根据任务发起调用。需要确认的操作由应用交给你审核；是否保存成功，应以工具返回的执行结果为准。

工具在本机还是远程，连接方式有所不同：

### 本地：stdio

AI 应用启动本机的工具程序，通过程序的标准输入和输出交换消息。它常用于本地文件、开发环境等场景。

连接的是本机程序；该程序也可能再访问远程 API。

### 远程：Streamable HTTP

AI 应用通过 HTTP 地址访问工具服务，适合服务集中部署、多人使用和在线数据接口。

2025 年后的规范已用它替代早期 HTTP+SSE 设计。

**“接上了”不等于“什么都能做”。** 实际能力取决于 Server 提供了什么、Host 支持什么，以及账户获得了什么权限。MCP 不会自动增加模型的长期记忆，也不会消除工具选择与执行中的错误。

### 04 · 从接通工具，到规模化基础设施

把前面的例子放大到很多用户、很多公司，就会出现新问题：服务能不能放在云端？谁有权查询或写入？任务太慢怎么办？这些实际需求推动了 MCP 的演进。它逐渐从“方便让大模型接上工具”，发展到“让大量应用和服务能够稳定协作”。

- 2024-11-25 · Anthropic 发布并开源 MCP

**起点 / 统一连接**：同时提供规范、SDK、Claude Desktop 支持和开源服务器。早期以桌面和本地接入为重要入口，解决 AI 应用与外部系统的连接问题。([Anthropic 发布公告 [01]](https://www.anthropic.com/news/model-context-protocol)）

- 2025-03-26 · 服务走向远程，接入需要授权

**远程化 / 部署与授权** :引入更灵活的 Streamable HTTP，以及基于 OAuth 2.1 的授权框架。可以理解为：除了约定“怎么连接”，也开始系统地约定“应用如何获得访问许可”。还增加了描述工具是否只读、是否具有破坏性的注解。（[MCP 远程连接能力[03]](https://modelcontextprotocol.io/specification/2025-03-26/changelog)）

- 2025-06-18 · 返回的数据更规整，缺少信息可以追问

增加结构化工具输出和资源链接，让应用更容易处理结果；加入 Elicitation，让服务端可以请求用户补充缺失信息。授权规范也继续细化。([规范变更 [04]](https://modelcontextprotocol.io/specification/2025-06-18/changelog)）

- 2025-09-08 · 官方 MCP Registry 发布预览版

**生态化 / 服务发现**：提供公开 MCP 服务器的目录与发现 API。客户端和企业可以在其基础上建立自己的目录或子注册表。（[Registry 公告 [05]](https://blog.modelcontextprotocol.io/posts/2025-09-08-mcp-registry-preview/)）

- 2025-11-25 · 处理需要等待的任务与浏览器交互

加入实验性 Tasks，跟踪暂时不能完成的请求；增加 URL 模式交互，让某些流程能在浏览器中完成。也扩充了模型调用和授权能力，并完善社区治理与 SDK 分级。（[规范变更 [06]](https://modelcontextprotocol.io/specification/2025-11-25/changelog)）

- 2025-12-09 · MCP 加入 Agentic AI Foundation

**中立治理 / 跨厂商协作**：Anthropic 将 MCP 捐赠给 Linux Foundation 旗下的 AAIF，成为创始项目之一。基金会提供中立归属与基础支持，协议技术方向和日常运作仍由维护者与社区推进。([基金会公告 [07]](https://blog.modelcontextprotocol.io/posts/2025-12-09-mcp-joins-agentic-ai-foundation/))

- 2026-01-26 · MCP Apps 成为正式扩展

工具能够提供对话中的交互界面，例如仪表盘、表单、可视化与多步骤流程。宿主在沙箱 iframe 中渲染 UI，具体可用能力取决于客户端支持。（[MCP Apps 公告 [08]](https://blog.modelcontextprotocol.io/posts/2026-01-26-mcp-apps/)）

- 2026-07-28 · 无状态核心成为新稳定规范

**规模化 / 协议核心重构**：取消协议级会话与初始化握手，重构多轮请求和通知机制，加入缓存提示、HTTP 头路由与正式扩展框架。（[版本发布说明 [09]](https://blog.modelcontextprotocol.io/posts/2026-07-28/)）

这次变化主要服务于一个现实需求： **当使用人数增加，工具服务要能增加机器、分摊请求，而不用一直依赖某条连接的历史状态。** 这就是“无状态协议核心”背后的目的。

每次带齐必要信息，换一台机器也能接着处理

以前需要先完成初始化，并可能依赖协议会话。新版让每次请求携带必要的协议版本和客户端能力信息，减少对特定连接或实例的依赖。

实际意义：用户多了，更容易增加服务器来分摊工作。

**生态推动普及：** 到 2025 年底，官方已列出 Claude、ChatGPT、Gemini、Cursor、Microsoft Copilot、VS Code 等平台的支持。更多客户端吸引服务提供者接入，更多服务又提高客户端采用 MCP 的价值。
