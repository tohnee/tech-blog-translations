> 本文系统梳理 KV 存储技术栈：从”为什么需要 KV Cache”的第一性原理出发，到推理引擎内部的 KV 管理（PagedAttention / RadixAttention / vAttention / MLA / KDA），再到突破 HBM 容量墙的 Attention Store 系统（CachedAttention / Mooncake / LMCache / HiCache / Phoenix），最后落到决定其商业价值的命中率经济学。本文聚焦**存储视角**，不覆盖 KV 压缩、量化、Eviction 等”减量”策略（它们与存储正交，可叠加使用）。

## 1. 为什么需要 KV Cache，为什么没有 Q Cache

### 1.1 KV Cache 的由来

Transformer 自回归生成中，每产生一个新 token 都要与之前所有 token 做 Attention 计算：

$$ \text{Attention}(Q, K, V) = \text{softmax}\left(\frac{QK^\top}{\sqrt{d_K}}\right)V $$

由于因果掩码的存在，**历史 token 的 K、V 向量只取决于它自己和它之前的 token，与后续生成无关**——算一次就可以永久复用。把历史 K/V 缓存下来、避免每步从头重算，就是 KV Cache：**用空间换时间**。没有它，生成长度为 $T$ 的序列计算量是 $O(T^2)$ 级别的重复计算。

推理因此分成两个阶段：

- **Prefill（预填充）**：对 prompt 做一次并行前向，把每一层 KV Cache 灌满。长上下文下是密集矩阵计算，主导 **TTFT**（首 token 延迟）。
- **Decode（解码）**：逐 token 串行生成，每步只用当前 token 的 Q 与缓存的全部历史 K/V 计算注意力。每步计算量小，但要把整个 KV Cache 从 HBM 读一遍——**受内存带宽约束**，主导 TPOT。

![](https://pica.zhimg.com/v2-9111231d5e5a266462e2f46409c25e94_r.jpg)
*图 1：Prefill 并行灌满 KV Cache，Decode 每步读取全部缓存并追加新 K/V*

KV Cache 的大小随上下文线性膨胀：$\text{KV Size} = 2 \times L_{layers} \times n_{ctx} \times n_{kv\_heads} \times d_{head} \times \text{sizeof(dtype)}$。

直观感受：以 DeepSeek-V4-Pro 为例，把一条 100K 上下文请求的 KV Cache 一层一层算清楚。

**第一步：每层存什么。** V4-Pro 有 61 层注意力，每层 = 一个局部滑窗（SWA）分支 + 一个全局压缩分支；全局分支按压缩比分两种——30 层 CSA（压缩比 4，记 C4）+ 31 层 HCA（压缩比 128，记 C128），30 个 C4 层还各带一个 lightning indexer。落到显存上是 7 个 cache pool，”单 slot”一列是该 pool 的一条条目跨全部层的字节数：

| Cache Pool | dtype | 条目宽 | 层数 | 单 slot |
| --- | --- | --- | --- | --- |
| SWA-KV-Cache | uint8（1B） | 584 | 61（MTP 态 62） | 35,624 / 36,208 B |
| C128-Cache | uint8（1B） | 584 | 31 | 18,104 B |
| C4-Cache | uint8（1B） | 584 | 30 | 17,520 B |
| C4-index-Cache | uint8（1B） | 132 | 30 | 3,960 B |
| C128-State | FP32（4B） | 512 × 2 | 31 | 126,976 B |
| C4-State | FP32（4B） | 512 × 2 × 2 | 30 | 245,760 B |
| C4-index-State | FP32（4B） | 128 × 2 × 2 | 30 | 61,440 B |

三处要点：**单 slot = 条目宽 × 层数**（如 SWA = 584 × 61 = 35,624 B）；**KV 条目是 uint8 量化存储，而 State 是 FP32 无损环形缓冲**——状态比 KV 贵 4 倍且不吃压缩；**C4 系的 State 宽是 C128 的两倍**（512×2×2 vs 512×2）。引擎侧把后三个 State pool 合并管理，就是我们前文说的五池（`swa_kv_pool` / `c4_kv_pool` / `c128_kv_pool` / `c4_indexer_kv_pool` / `compress_state_pools`）。

**第二步：固定存储项。** 固定项只由两件事构成——滑窗内驻留的 SWA KV，以及三个 State 环形缓冲。环深分别是 `window_size = 128`、`C4_ring_size = 8`、`C128_ring_size = 128`：

```text
KV_fixed = SWA_slot × window_size
         + (C4_State_slot + C4_index_State_slot) × C4_ring_size
         + C128_State_slot × C128_ring_size

         = 35,624 × 128  +  (245,760 + 61,440) × 8  +  126,976 × 128
         = 4,559,872     +  2,457,600               +  16,252,928
         = 23,270,400 B  ≈ 22.2 MiB（文档记作 22.2MB）
```

拆占比：**C128-State 环 15.5 MiB（70%）**、SWA 滑窗 4.35 MiB（20%）、C4 两个 State 环 2.34 MiB（10%）。这里藏着一个反直觉的事实：**C128-State 环（15.5 MiB）比它服务的 C128 压缩 KV 本身还大**——100K 上下文下 C128-Cache 全长只有 13.8 MiB（交叉点约在 11.5 万 token）。固定开销的大头不是”要缓存的历史”，而是”维护压缩状态所需的无损缓冲”。

**第三步：线性增长存储项。** 7 个池里只有三个全局池随上下文增长，压缩比决定它们每多少 token 才落一条条目：

```text
KV_linear = C128_slot × CTX/128 + (C4_slot + C4_index_slot) × CTX/4
          = 18,104 × CTX/128    + (17,520 + 3,960) × CTX/4
          = 141.4 × CTX         + 5,370 × CTX
          = 5,511 B / token     ≈ CTX × 5.4KB
```

两项相加，就是那条官方线性公式：

$$ \text{KV} = 22.2\text{MB} + \text{CTX} \times 5.4\text{KB} $$

**第四步：100K 上下文（102,400 token）一条请求的账。** 固定项 22.2 MiB，线性项 538.2 MiB，合计 **≈560 MiB（≈587.6 MB）**：

```text
线性部分 538.2 MiB（564.4 MB = 102,400 × 5,511 B）
   C4-Cache：       17,520 B × 25,600（= CTX/4）  = 448.5 MB  （79.5%）
   C4-index-Cache：  3,960 B × 25,600             = 101.4 MB  （18.0%）
   C128-Cache：     18,104 B ×    800（= CTX/128）=  14.5 MB  （ 2.6%）
固定部分 22.2 MiB（23,270,400 B）
   SWA 滑窗 128 token × 35,624 B                  =   4.35 MiB
   C4 + C4-index State 环 8 槽                    =   2.34 MiB
   C128 State 环 128 槽                           =  15.50 MiB
合计 ≈ 560 MiB / 请求
```

可以看到，及时有了各种压缩技术，KV 仍随上下文线性膨胀、随并发线性叠加：50 路并发 100K 请求就是约 29GB——直逼单卡 HBM 去掉权重后的全部余量，这就是”内存墙”。**KV Cache 已从”一个优化技巧”变成”一类存储对象”**：不仅要缓存，还要高效地存储、管理、调度、传输它。

### 1.2 为什么没有 Q Cache？

一个自然的疑问：K、V 都能缓存，Q 为什么不行？答案藏在 Attention 的计算链里：

1. **Decode 时只有当前 token 的 Q 参与计算**。第 $t$ 步生成只需要 $q_t$ 与缓存的 $K_{1..t}$、$V_{1..t}$ 做点积，历史 token 的 Q 在此刻不再被任何计算引用——缓存它们是纯粹的浪费。Q 是”一次性输入”，K/V 是”跨步复用的中间状态”；缓存的本质是保存需要跨步复用的中间状态。
2. **历史 Q 的信息并没有丢，而是”隐式存储”在下一层的 KV 里**。第 $l$ 层某 token 的 K/V 由第 $l-1$ 层的输出变换而来，而那个输出本身就是上层 Q 参与注意力的结果——**第 $l$ 层的 KV Cache 实际上已包含第 $l-1$ 层的 Q 信息**。Decode 阶段新算出的 Q 流向下一层参与生成新的 K/V，等价于把”Q Cache”换了一种方式存进了 KV Cache。
3. **这也是 Prefill 不可跳过的原因**。如果不 Prefill，第一层只有当前 token 的 Q，第二层连合法的历史 K 都构造不出来，注意力建模与训练时完全不对齐。Prefill 的本质是为每一层准备”携带了上层 Q 信息”的 K/V。

![](https://pic3.zhimg.com/v2-09f98db4a16fa223667d82199cb1e23c_r.jpg)
*图 2：Q 用完即弃、不被后续步骤引用；其贡献经输出 z 流入下一层的 K/V（”隐式 Q Cache”）*

所以缓存系统只需缓存 KV：Q 的历史贡献已经折算进 KV 链。

## 2. 引擎里的 KV 存储技术

推理引擎层面的 KV 存储技术主要解决两个问题：**显存利用率**（碎片）和**跨请求复用**（前缀缓存）。二者已收敛为现代引擎的标准范式：**分页（解决碎片）+ 前缀树（解决复用）**。

### 2.1 PagedAttention（vLLM）：把 OS 分页做进 kernel

PagedAttention（SOSP 2023）借鉴操作系统**虚拟内存分页**管理 KV Cache，解决传统方案的三大内存浪费：

- **内部碎片**：按”最大可能序列长度”预分配连续内存，实际输出远短于上限；
- **外部碎片**：请求长度各异，内存块之间产生无法组合的空隙；
- **冗余复制**：并行采样、beam search 下多条序列共享相同前缀却各存一份。

**核心设计**：把逻辑连续的 KV Cache 切成固定大小的**块（block）**，通过**页表**做逻辑到物理的映射，KV Cache 在物理显存中可以非连续存储。调度器每步显式分配/回收块；不同请求共享相同前缀（如 system prompt）时，前缀页指向同一物理块，用**引用计数**管理生命周期，写入时才触发 **Copy-on-Write**。显存利用率从 20%–40% 提升到 **>90%**，同延迟下吞吐提升 2–4×。

![](https://pica.zhimg.com/v2-64ab93364c3217644045741e5af426d6_r.jpg)
*图 3：传统连续预分配的三种浪费 vs PagedAttention 的页表映射与前缀块共享（ref=2 + CoW）*

**vLLM V1 的完整链路**：调度器维护三队列（WAITING → RUNNING → SWAPPED）。显存不足时触发**抢占**，两种策略——**RECOMPUTE**（释放全部 KV 块、下次重算）与 **SWAP**（KV 从 GPU 换出到 CPU、之后换回），这是引擎级 GPU↔CPU 分层存储的实现。执行层的 `blocks_to_swap_in/out/copy` 在 forward 前完成，其中 `blocks_to_copy` 正是 prefix cache 命中后共享块的写时复制路径。V1 还集成了 **Automatic Prefix Caching（APC）**——基于 token 块哈希的前缀复用。

### 2.2 RadixAttention（SGLang）：基数树前缀复用

RadixAttention（2023）的核心目标是**跨请求的自动 KV 复用**，数据结构是**基数树（Radix Tree）**：

- 树的每条边标记一段 token 序列，节点持有 KV pool 的 slot 索引；
- 新请求到来时做**最长前缀匹配**：命中部分直接复用其 KV，未命中部分追加为新节点；
- LRU 等策略淘汰旧节点释放显存。

多轮对话、few-shot、RAG、self-consistency 等场景自动受益，吞吐提升 3–5×。相比无缓存基线，SGLang 已支持 MHA/MLA/GQA/Mamba 等多种注意力架构下的前缀复用。

![](https://pic3.zhimg.com/v2-5d676d9aea549d6a36518394a4569a70_r.jpg)
*图 4：基数树上的最长前缀匹配——命中部分直接复用 KV，新 token 追加为新节点，未加锁叶子按 LRU 淘汰*

**实现细节（sglang `mem_cache/`，main 分支）**——三个设计值得注意：

1. **树只存索引、不存张量**：`TreeNode.value` 指向 KV pool 的 slot 索引，与 `PagedAllocator`（页粒度分配/回收）咬合；命中前缀时 `value` 就是可直接喂给 attention backend 的物理位置。`insert` 只登记索引不分配 slot，`cache_finished_req` 在请求完成时插树并去重释放已被树覆盖的前缀 slot。
2. **锁沿父链传播**：只要某请求持有叶子节点的 lock（`lock_ref`），整条前缀链都不可淘汰；evict 从增量维护的 `evictable_leaves` 集合按策略建堆逐个释放，复杂度与淘汰量成正比而非树大小。淘汰策略有 7 种（LRU/LFU/FIFO/MRU/FILO/priority/SLRU），默认 LRU。
3. **统一锚点贯穿多层存储**：`TreeNode` 同时持有 `value`（GPU slot 索引）、`host_value`（CPU slot 索引）、`hash_value`（每页一个哈希，作外部存储 key）——一棵树天然索引三层存储，是后文 HiCache 的基础。

`extra_key`（LoRA id / cache salt）进入键空间实现命名空间隔离；树只在 page 边界分裂节点，**page 对齐贯穿全栈**。

### 2.3 vAttention：把分页做进 MMU

PagedAttention 把虚拟内存布局从连续变为非连续，代价是注意力 kernel 必须感知分页（block table 间接寻址），编程复杂且损失 kernel 性能。**vAttention**（Microsoft，arXiv 2405.04437）走另一条路：用 CUDA Virtual Memory Management API **解耦虚拟/物理内存分配**——虚拟地址空间预先分配连续大块，物理显存按需映射。物理层碎片通过延迟映射解决，而**虚拟连续性保留**：原生兼容未改造的注意力 kernel（FlashAttention 等），吞吐比 PagedAttention kernel 最高 1.23×。

两条路线的对比本质是：**PagedAttention 把分页做进 kernel，vAttention 把分页做进 MMU**。后者依赖 CUDA VM API 且物理碎片仅缓解不消除，但思路代表了”OS 虚拟内存思想进一步下沉”。

### 2.4 架构演进对 KV 存储的冲击：MLA 与 KDA

**MLA（DeepSeek）**：把多头 K/V 压缩为低秩 latent 向量 $c_{KV}$，只缓存 latent、推理时解压。DeepSeek-V3 的 KV 维度从 GQA 的 2048 降到 576，压缩约 3.6×。代价是 TP 切分困难：每个设备都需加载完整 latent，内存优势被并行度抵消——**TPLA**（ASPLOS 2026）用 Hadamard/PCA 重参数化使 latent 可沿特征轴切分，免训练加载 MLA checkpoint，32K 上下文加速 1.79×/1.93×。

**KDA（Kimi K3）打破 per-token 假设**：K3（2.8T 参数、1M 上下文）的注意力骨架是”三 KDA + 一 MLA”交替（93 层中 69 层 KDA）。KDA 不存逐 token KV，历史递归压缩为**固定大小的 Recurrent State**（$S_t \in \mathbb{R}^{128\times128}$，与序列长度无关）+ 卷积窗口，KV Cache 降低约 75%。但这**根本改变了缓存性质**：

- 递归状态无法任意截断回退——token 级前缀匹配成功 ≠ 状态可恢复，必须在选定前缀边界显式存 checkpoint；
- 单个 KDA checkpoint ≈ 0.4 GiB；128 token 间隔下 1M 上下文需 ~3TB，10K 间隔也要 ~40GB——**checkpoint 越稀疏，命中后重算的后缀越长**；
- MLA KV 与 KDA State 必须在同一前缀边界对齐。

![](https://pic2.zhimg.com/v2-5f9239e74aa2155b13a9a819208a6d83_r.jpg)
*图 5：Full Attention 的 KV 随序列线性增长、可任意截断复用；KDA 只存固定状态 + 稀疏 checkpoint，命中需从最近 checkpoint 分叉并重算后缀*

SGLang 的解法（`MambaRadixCache`）：树节点同时持有 `value`（MLA per-token KV 索引）和 `mamba_value`（KDA per-prefix 状态 slot），**两套独立 LRU/引用计数**；节点分裂时 `mamba_value = None`（状态无子结构可切）。关键机制：**track/donate/branching 闭环**（递推中定期快照状态 → 零拷贝”过户”给基数树 → 命中时从最深状态节点分叉重算尾巴）、**ping-pong track buffer**（2 个 track slot 交替写/取，给 donate 2 轮 chunk 余量，是 overlap 调度的前提）、**INT8 冷池**（per-(head,k-channel) 对称量化，同显存缓存约 4× 前缀状态）。实测 60K 上下文下 KDA 混合 cache 比纯 MLA 省 70%。vLLM 社区（K3 团队贡献）则用**三粒度解耦**：hash 粒度（前缀匹配探测）× 物理状态块（摊销存储）× 调度对齐粒度，4,096-token 的物理块内部可在任意位置记录命中点直接恢复。TokenSpeed 的 **Flat KV** 更进一步：一页既可存 1,536 token 的 MLA latent，也可存一个完整 KDA 快照——统一页分配器与地址空间，prefix cache / CoW / PD 传输协议全部复用。

### 2.5 小结：引擎技术的坐标与取舍

本章的技术都在回答两个正交的问题：**如何管好一块显存**（碎片与利用率），**如何复用一段历史**（跨请求前缀）。一张表看清各自的位置与代价：

| 技术 | 解决的问题 | 核心机制 | 优势 | 劣势与代价 |
| --- | --- | --- | --- | --- |
| PagedAttention（vLLM） | 显存碎片 | 软件页表 + 引用计数 + CoW | 利用率 20–40% → >90%，同延迟吞吐 2–4×，支持前缀块共享 | 注意力 kernel 必须感知分页（block table 间接寻址），编程复杂且有 kernel 性能损失 |
| RadixAttention（SGLang） | 跨请求复用 | 基数树最长前缀匹配 | 复用全自动，多轮/RAG/few-shot 吞吐 3–5×；树只存索引，与分页分配器天然咬合 | CPU 侧树操作开销随命中率上升；收益依赖负载的前缀分布，低命中负载反受其累 |
| vAttention | 消除分页的 kernel 代价 | CUDA VM API：虚拟连续 + 物理按需映射 | 原生兼容未改造 kernel（FlashAttention 等），吞吐最高 1.23× | 依赖 CUDA VM API，平台绑定；物理碎片只是延迟出现而非消除 |

三点判断：

1. **正交可叠加是常态**：分页与基数树并不竞争——SGLang 的实现正是 PagedAllocator 管物理块、RadixTree 管逻辑前缀，vLLM 的 APC 同样是”分页 + 哈希前缀”。现代引擎的标准范式 = **分页（空间效率）+ 前缀树（复用效率）**。
2. **两条分页路线的分野在 kernel**：PagedAttention 把分页做进 kernel（软件页表，成熟通用），vAttention 把分页做进 MMU（硬件页表，kernel 透明但依赖新 API）。
3. **分页与前缀树之上，架构是更大的变量**：MLA 与 KDA（见 2.4 节）正在改变“被缓存的对象”本身——从 per-token 张量走向 per-prefix 状态，引擎的存储数据结构也随之演化。

## 3. Attention Store 系统

单卡 HBM 装不下 KV Cache 时，就需要把它扩展到 CPU DRAM、SSD 和分布式存储——这类系统统称 **Attention Store**。核心思想是**“以存换算”**：用更多的存储资源换取更少的计算。

### 3.1 存储层次谱系

容量递增、带宽递减的四级介质构成了所有 Attention Store 的物理基础：

| 层级 | 介质 | 典型容量（单节点） | 典型带宽 |
| --- | --- | --- | --- |
| L1 | GPU HBM | 80–96 GB | 2–3.3 TB/s |
| L2 | CPU DRAM | 0.5–2 TB | 50 GB/s |
| L3 | NVMe SSD | 4–100 TB | 7 GB/s（单盘）~25 GB/s（RAID） |
| L4 | 分布式池 / 远端对象存储 | PB 级 | 10–100 Gbps 网络带宽 |

![](https://pic1.zhimg.com/v2-78c9e87677c84d363bb8a8362a91c83c_r.jpg)
*图 6：四级存储层次——容量递增、带宽递减，各系统把不同温度的 KV 放在不同层级*

带宽落差是数量级的（NVMe→HBM 差约 480×），因此所有系统都在做同一件事：**用预取、重叠、粒度设计把搬运藏进计算**。三个反复出现的技术母题：

1. **重叠隐藏**：逐层 load/store 与计算重叠（Mooncake/LMCache/CachedAttention/LayerKV）、多 CUDA stream 并行、预取窗口；
2. **未来信息 > 历史信息**：用调度器队列的前瞻而非 LRU 的历史做放置与驱逐，命中率差距是数量级的（86% vs 48–58%）；
3. **粒度选择**：传输粒度要大（聚合到 chunk 才能饱和带宽），管理粒度要细（页/层/会话各取所需）。

### 3.2 CachedAttention / AttentionStore：会话级 KV 外存的奠基

**CachedAttention**（USENIX ATC 2024，NUS/上交/华为云）盯住多轮对话：ShareGPT 中 73% 为多轮，每轮结束后 KV 被丢弃，下一条消息要对全部历史重新 prefill——历史 token 占比超 99%，重复计算占 TTFT 的 99%。

**架构**：Controller（调度器）+ AttentionStore Manager（DRAM+SSD 两级）+ GPU 集群（含专用读写 buffer），Load/Save 走独立 CUDA stream，Fetch/Evict 走独立 IO 线程。四大机制：

- **逐层预载**：算第 $i$ 层时并发预载第 $i+1$ 层；
- **异步保存**：prefill 产生的 KV 逐层与 decode 重叠写回；
- **调度器感知放置/驱逐**（本质创新）：用 job queue 的”未来信息”替代 LRU/FIFO 的历史信息，窗口内即将被访问的 KV 豁免驱逐——命中率 86% vs LRU 58% / FIFO 48%；
- **位置编码解耦**：存不含 RoPE 的 K/V，加载时再嵌入新位置编码，上下文截断不使缓存失效。

**效果**：KV 命中率 71–90%，TTFT 降低 61–87%，prefill 吞吐提升 2.6–7.8×，成本最多降 70%（存储开销仅占总成本 9–16.4%）。HBM-only 命中率约 0%，加 10TB SSD 后达 71–90%——**跨 DRAM/SSD 分层是命中率的根本来源**。局限：单机本地、无跨节点路由（Mooncake 沿此方向工业化）。

### 3.3 Mooncake：KVCache-Centric 分离架构的生产标杆

**Mooncake**（FAST 2025 最佳论文，月之暗面+清华）是 Kimi 的生产推理平台，核心洞察：**调度请求本质上是调度 KVCache 在哪里、谁来算、传给谁**。架构四件套：

- **Prefill 池**（max cache reuse，s.t. TTFT SLO）+ **Decode 池**（max throughput，s.t. TBT SLO）；
- **全局分布式 KVCache 池**：把 GPU 服务器闲置的 CPU/DRAM/SSD/NIC 池化，通过 GPUDirect RDMA 传输（Messenger 组件）；
- **Conductor 全局调度器**：以前缀命中长度、实例负载、传输时间、SLO 统一权衡路由——TTFT = 排队 + prefill（+ 传输）；SLO 不可达直接 HTTP 429 提前拒绝；
- **热点迁移**：请求路由到非最佳实例时顺带拉取 KV 复制热块（trace 显示 >50% 缓存块从未复用、最热块被访问数万次——复制热块收益极高）。

![](https://pic3.zhimg.com/v2-272af22e3d2e0f35dc0e95f6284501fe_r.jpg)
*图 7：Mooncake 四件套——Conductor 全局调度 + Prefill/Decode 分离池 + 分布式 KVCache 池，五步请求工作流*

数据按 **512-token 块**组织，前缀哈希级联去重；**Layer-wise Prefill** 让逐层 load/store 与计算重叠，prefill 时间 ≈ max(加载, 计算)。长上下文流水（CPP）把多节点 prefill 流水化。

**效果**：已在数千节点部署、日处理超千亿 token；长上下文模拟吞吐 +50%~+525%；真实负载多处理 75% 请求且 TBT 达标率 ~100%（vLLM 57%）；平均 TTFT 6.26s vs 负载均衡 60.41s。

**工程视角的双重身份**（SGLang 集成）：Mooncake 既可以是 HiCache 的 **L3 持久后端**（共享缓存池，跨实例/重启复用，`--hicache-storage-backend mooncake`），也可以是 **PD 分离的 KV 传输通道**（请求级一次性搬运，`--disaggregation-transfer-backend mooncake`）——前者是”可复用资产”，后者是”过路数据”。Kimi K3 编程场景靠这套分离架构做到 **>90% 缓存率**。

### 3.4 LMCache：引擎中立的 KV 存储传输层

**LMCache**（arXiv 2510.09665，TensorMesh+芝加哥大学）不是引擎，而是横跨引擎与存储后端的**可插拔中间件**——把 KV Cache 从”GPU 显存里的临时中间状态”升级为可持久化、可迁移、可调度的**基础设施资源**。

它抓住了一个被忽视的物理约束：PagedAttention 的页粒度 I/O 太小，无法饱和带宽——16-token 页仅 62.5KB，而实测**消息 ≥16MB 才能饱和 400Gbps NIC**。

![](https://pic2.zhimg.com/v2-cf91b5016337a7775a33c2c25c7ba25f_r.jpg)
*图 8：传输粒度决定带宽——页级小消息只能吃到 88Gbps，聚合成 16MB 大消息才能饱和 400Gbps*

核心机制：

- **批量化搬运**：多页多层聚合为 chunk（默认 256 token），定制聚合/打散 CUDA kernel + DMA，延迟批写；
- **计算-IO 重叠**：逐层流水（只需单层 KV 大小的 GPU 缓冲）+ 排队期预取；
- **零拷贝**（引用计数）与三指针动态 offloading 状态机；
- **标准化接口**：KV Connector API（7 个函数，已被 NVIDIA Dynamo / llm-d / AIBrix / vLLM Production Stack 采纳）+ 分布式 Cache Controller（lookup/move/pin/batched_evict），支撑 KV-aware 路由与跨实例共享。

**效果**：CPU→GPU 加载带宽 **400 Gbps**（vLLM 原生 88 Gbps——根源就是页粒度 vs chunk 粒度）；TTFT 降低 1.9–8.1×、吞吐提升 2.3–14×；PD 分离下 mean TTFT 再降 1.53–1.84×。

**设计哲学**：主要缓存 **Prefill KV**（system prompt、文档片段——下次请求必然复用）而非 Decode KV（复用率极低且频繁写盘造成 I/O 竞争）。生产数据：Agent 负载（Codex SWE-bench Pro trace）input/output 比 131:1、缓存命中率 94.2%、轮间隔中位数仅几秒——这是 LMCache 们的目标画像。

### 3.5 HiCache：分层基数树（SGLang/阿里云 Tair）

**HiCache** 把 RadixAttention 的基数树扩展为 **HiRadixTree（分层基数树）**：L1 GPU HBM（热数据）→ L2 CPU 锁页内存（`--hicache-ratio 2.0`，L2 = ratio × L1）→ L3 外部存储（file/mooncake/hf3fs/nixl 等后端）。一个 `TreeNode` 的 `value / host_value / hash_value` 三字段分别锚定三层（见 §2.2）。

**关键机制**：

- **双 CUDA stream**：write_stream（device→host DMA）与 load_stream（host→device，按 layer 分步）分离，配合 ack 队列 + TP all_reduce 同步；
- **write_through 策略**：平时异步备份到 host，evict 时只释放 device 槽、保留 host 数据（`evict_device()`）；命中已驱逐节点时沿父链收集并 DMA 回来（load_back）；
- **L3 预取状态机**：先探测命中长度、**命中页数 ≥ 256 token（`prefetch_threshold`）才分配 host 内存并真正预取**——避免为小命中浪费带宽与内存。

![](https://pic1.zhimg.com/v2-ccb2528a15eabdc0a973b76c43fa4c40_r.jpg)
*图 9：HiRadixTree——同一个 TreeNode 的三个字段锚定三层存储，前缀在层间升降级而不换数据结构*

**最易误解的点**：SGLang 中 L3 有两条**互斥**集成路径——HiCache 的存储后端（`HiCacheStorage`，page 哈希寻址、同步 batch get/set）与 **RadixCache 装饰器**（LMCache/FlexKV 以 `RadixCache` 子类整体替代 L2+L3，只覆盖 `match_prefix/init_load_back/cache_finished_req/evict` 四个方法，用 token 序列寻址 + LOOKUP→RETRIEVE 两阶段）。一个进程只实例化一个 cache 类，不能自由组合。

阿里云 Tair 团队加入后演进为分布式版本：真实生产（Novita AI）中命中率 40%→80%，TTFT 降 56%，QPS 翻倍。

### 3.6 端到盘与直通存储：KVSwap 与 Phoenix

**KVSwap**（arXiv 2511.11907）面向端侧：统一内存设备上 GPU→CPU 卸载无意义，必须下盘，而盘带宽比内存低 2–3 个量级。做法是全量 KV 存盘 + 内存只留”低秩 K 摘要（只做预测、不参与计算，可激进压缩 σ 高达 32）+ 分组关键 KV 预测（对齐磁盘块读）+ 滚动/复用缓冲”。Jetson Orin 上 vs 最强基线提速 1.8×（NVMe）/4.1×（eMMC）。

**Phoenix（[http://xPU.IO](http://xPU.IO)，SC’25 + LMCache PR #4673）**：SSD 是 Agent 时代唯一划算的大容量介质（单机 100TB 级），但传统路径”盘→主机内存→显存”两次穿 PCIe + CPU 全程参与——实测 4×NVMe RAID0 裸盘 25GB/s，端到端只剩 10.2GB/s；Codex 回放中 TTFT 1101ms 里加载占 600ms、真正 prefill 只 313ms。Phoenix 基于 Linux 标准 I/O 栈 + ZONE_DEVICE 为显存建 `struct page`，让 GPU 显存指针成为合法 I/O 地址，直接走 pread/io_uring：8×H20 生产 trace 下，平均 TTFT 是 SSD 中转的 2.2×、纯 DRAM 的 5.6×；TTFT 5s 红线下并发 7（DRAM-only）→13（SSD 中转）→**37（Phoenix）**。机制收益的本质：加载快于计算后，”KV 加载与前一批推理 overlap”的调度重新生效。

### 3.7 其他系统一览

- **NVIDIA CMX**：DPU 做多租户调度 + SSD 大容量，KV 管理从引擎解耦为专用存储栈；
- **英特尔 KV Shrink**：QAT 硬件加速 + 分层卸载，L1(HBM)→L2(DDR)→L3/L4(SSD/分布式) 四级；
- **中科曙光 ParaCache**：依托 ParaStor 的四级缓存，”从存数据到存智能”，KV 作为可复用数据资产管理；
- **华为 UCM**：昇腾 NPU 的 KV 池化，经 KV Connector 对接 Mooncake 等后端，灵衢总线跨节点传输。

### 3.8 命中率经济学：Attention Store 的商业闭环

Attention Store 的价值最终由**命中率 × 定价**决定，工业界给出了几个反直觉结论：

**命中部分定价仅为未命中的 10%–25%**（无问芯穹，服务 GLM/Kimi）。由此推出**浴盆模型**：TPS_hit 随命中率单调上升，TPS_miss 近似线性下降；命中率 40%→70% 时未命中吞吐再降 20%，而命中部分提升不足 3 倍——中段（”偶然失效区间”）可能**命中率越高越亏钱**；且存在 20%/40%/70% 奇异点（末尾残块不满 chunk 独立计算）。优化方向：把浴盆变浅、加大 cache 容量逃离盆底、cache-aware 负载均衡。

![](https://picx.zhimg.com/v2-22639408fa205fdd228aefcefbbefbd9_r.jpg)
*图 10：浴盆模型——命中部分吞吐上升、未命中部分吞吐下降，中段”偶然失效区间”可能越命中越亏；20/40/70% 为残块奇异点*

**命中率天花板由 trace 决定，容量只是入场券**（kvcache.ai 模拟器逆向）：Mooncake 真实 trace 的复用天花板（无限容量）仅 **59.1%**——Belady 最优在 16GiB 就到顶（有效复用工作集极小，仅 ~3.7% 唯一块有未来复用价值），LRU 却要 256GiB 才追平（分不清”将复用”与”死块”）。**trace 的复用结构决定上限，模型结构只决定多少 GiB 换多少块**。 **Agent 负载改变命中率来源**：传统对话输入 8K、命中率 50%；Agent 任务输入 64–128K、输出 ≤1K、命中率 90%。但**前缀易变字段破坏命中**：Agent ID、工作目录、时间戳、工具 schema 每次微变即 miss。**TokenPilot**（浙大）证明仅把易变字段替换成静态占位符 + 摄入边界确定性整理，就把宏观命中率 38.7%→79.2%、费用降 61–87%——**上下文管理与 KV 存储是同一枚硬币的两面**。

## 4. 总结

KV 存储技术沿两条主线演进，且正加速融合：

1. **引擎内管理**（PagedAttention → RadixAttention → vAttention → KDA 状态缓存）：从分页分配到前缀复用到虚拟内存下沉。分页+前缀树已是标准范式；架构演进（MLA/KDA）正在把缓存对象从”per-token 张量”变为”per-prefix 状态”，前缀缓存被重新定义。
2. **跨介质存储系统**（CachedAttention → Mooncake → LMCache → HiCache → Phoenix）：从单机两级到分布式全局池。**“以存换算”已成行业共识**；决定性工程问题是粒度（16MB 才饱和 400Gbps）、重叠（加载快于计算调度才生效）与寻址（页哈希 vs token 序列）。

一个正在成形的判断：**KV Cache 是 Agent 时代的第一等数据**。Agent 负载（输入 64–128K、输出 ≤1K、命中率 >90%、轮间隔秒级）天然是 KV 存储的最佳场景，其经济学（命中定价 10–25%、浴盆模型、trace 决定天花板）已经反过来塑造系统设计——命中率的竞争前移到了上下文管理（TokenPilot）与 KV-aware 路由（kv_events/Dynamo）。未来的 KV 存储不再是孤立模块，而是横跨推理引擎、存储系统、网络传输与硬件介质的**全栈协同设计**。

> 本文聚焦 KV 存储技术本身。KV 压缩（量化、低秩、token 裁剪）与 KV Eviction（H2O、StreamingLLM 等）是正交的”减量”路线，与本文的“存储”路线可叠加使用。
