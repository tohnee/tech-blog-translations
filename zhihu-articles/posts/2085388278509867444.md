很多人比较本地大模型工具时，习惯只看一个数字：每秒输出多少 Token。

但对大家来说，真正决定日常体验的，往往不是推理速度，而是下面这些问题。

真正拉开体验差距的，是这几件事：

> ▪ 模型能不能顺利下载？<br>▪ 模型列表能不能正常加载？<br>▪ 新模型能不能及时找到？<br>▪ 本地模型能不能接入agent，实现token 自由？<br>▪ 只有 16GB 内存、512MB 显存，能不能运行更大的模型？<br>▪ 长对话中，KV Cache 能不能复用？

所以这篇文章不只对比五款工具的功能，还会把网络环境、模型获取、Agent 接入、推理性能差异等一起纳入评估。

## 一、LM Studio：最好上手，但不是最透明

LM Studio 现在早已不只是聊天软件：它支持 GGUF，也支持 Apple Silicon 上的 MLX；同时提供 OpenAI 兼容 API、Anthropic 兼容 API、MCP、RAG、结构化输出、并行请求与无界面服务模式。0.4.x 版本加入的 llmster，还能让它在服务器、CI 或没有图形界面的环境中运行。

优 点

> ▪ 图形界面成熟，模型搜索、下载、加载、聊天集中在一个界面<br>▪ 对新手友好，显存、内存、上下文与量化选项直观<br>▪ 支持本地文档问答、MCP、工具调用与结构化输出<br>▪ 同时提供 OpenAI / Anthropic 兼容接口，接入 Claude Code、Codex 等更省事<br>▪ 覆盖 macOS、Windows 与 Linux<br>▪ 纯本地聊天与文档处理可离线运行

缺 点

> ▪ 闭源软件，无法像 llama.cpp 那样审查和修改底层代码<br>▪ 中文界面汉化没做好，对于中文用户不友好<br>▪ 模型搜索与下载依赖 Hugging Face，国内访问与速度存在不确定性<br>▪ GUI 隐藏了大量底层参数，遇到特殊模型、模板错误或 GPU offload 问题时，不如直接使用 llama.cpp 灵活<br>▪ 产品中同时存在 Bionic、云模型与联网搜索，需要用户自己分清哪些是本地能力

我 的 评 价

如果你想最快在电脑上跑起 Qwen、Llama、Gemma 或 DeepSeek，LM Studio 依然是最好的入口之一。但如果你更在意长期可控性、稳定的模型下载速度、供应链透明度与企业部署，它不是最稳妥的底层选择。

## 二、Unsloth：最适合「训练完立刻部署」

Unsloth 与其他四款最大的不同，是它不只负责运行模型，而更像一套模型生产工作台：

**下载模型 → 训练 / LoRA / QLoRA 微调 → DPO / GRPO量化 → 导出 GGUF → 部署到本地 API**

如果你只想聊天，它会显得偏重；但如果你想训练一个属于自己的模型，它的优势就非常突出。

优 点

> ▪ 支持 LoRA、QLoRA、DPO、GRPO、全量微调与强化学习<br>▪ 训练结果可导出为 GGUF，继续交给 llama.cpp、Ollama 或 LM Studio 运行<br>▪ 覆盖文本、视觉、音频、Embedding 与扩散模型<br>▪ 对新模型、新量化方式与模型特定问题跟进较快<br>▪ 支持 OpenAI 兼容 API、RAG、MCP、工具调用、Docker 与局域网部署<br>▪ 核心包使用 Apache 2.0，Studio UI 等部分组件使用 AGPL-3.0

缺 点

> ▪ 安装与维护成本高，需要处理 Python、PyTorch、Transformers、CUDA、ROCm、MLX 等一整套组件<br>▪ 模型搜索与模型列表高度依赖 Hugging Face<br>▪ 国内网络环境下，可能出现模型列表加载不出来、下载失败或速度不稳<br>▪ 桌面版迭代很快，部分功能仍处于 beta 阶段<br>▪ 对只想跑一个模型的用户来说，功能明显过剩

我 的 评 价

Unsloth 适合这样的人：手里有自己的数据，想微调模型，想控制权重与量化方式，并希望把训练、导出、部署放在同一条工作流里完成。如果只是本地聊天，Ollama 或 LM Studio 通常更省事。

## 三、Herdsman 牧马人：不只是本地推理，而是本地模型入口

Herdsman 常被低估的一点，是很多人把它当成「又一个本地聊天软件」。实际上，它已经包含了几项关键能力：

> ▪ 本地模型管理<br>▪ llama.cpp 推理<br>▪ OpenAI / Anthropic 兼容 API<br>▪ Token Router<br>▪ aiDAPTIV 推理加速<br>▪ 本地模型应用集成

其中，Token Router 是它与其他工具拉开差距的地方。

过去要把本地模型接进 WorkBuddy、Codex 或 Claude Code，用户得手动配置下面这一长串内容，而且不同 Agent 的配置文件位置还不一样：

**接口地址 · API Key · 模型名称 · 协议类型上下文参数 · 工具调用参数**

Herdsman 的 Token Router 把这些配置统一起来：已经部署在 Herdsman 里的本地模型，可以一键配置到 WorkBuddy、Codex、Claude Code 等工具中。

于是 Herdsman 不再只是一个「本地模型聊天窗口」，而成为一个本地模型网关——模型在 Herdsman 中运行，Agent 通过 Token Router 调用：

**本地模型 → Herdsman → Token Router→ WorkBuddy / Codex / Claude Code**

这对本地 Coding Agent 用户尤其重要：真正难的往往不是把模型跑起来，而是让它稳定地进入实际工作流。

Herdsman 的底层同样基于 llama.cpp——从官方 API 文档中的 OpenAI / Anthropic 兼容接口、思考参数与推理预算等设计，可以看出它与 llama.cpp 运行时的关系。它的另一项重要能力，则是 aiDAPTIV 推理加速。

传统本地推理通常受制于内存层级：模型权重放不进显存，KV Cache 放不下，上下文一长速度就明显下降，模型还要反复计算已经处理过的 Token。

aiDAPTIV 的思路不是简单地把模型文件丢到 SSD 上，而是通过 AI SSD 与配套中间件，把 SSD 纳入模型运行的内存层级：

> ▪ 把部分模型权重在 GPU、内存与 SSD 之间分层调度<br>▪ 把暂时不用的权重放到 AI SSD<br>▪ 把被挤出的 KV Cache 预缓存到 SSD<br>▪ 在后续对话与 Agent 循环中重新调用缓存，减少重复计算<br>▪ 通过 KV Cache 复用降低长上下文、多轮对话的 TTFT

这带来一个关键变化：本地模型能不能运行，不再只取决于显存大小。在特定硬件、量化模型、PCIe、SSD 与软件配置下，即使设备只有 16GB 内存、512MB 级别显存，也有机会把 80B 级别的大模型放进「可运行范围」。

必 须 说 清 楚

能运行，不等于高吞吐。AI SSD 解决的是容量、缓存与重复计算问题，并不会让一块低性能硬件瞬间获得高端 GPU 的算力。

模型很大时，Decode tok/s 依然可能偏低——模型架构、活跃参数、上下文长度、SSD 带宽与预缓存命中率，都会影响最终效果。

在预缓存充分、模型与硬件匹配的情况下，Herdsman + aiDAPTIV 可以把 TTFT 做到秒级，部分场景约 2 秒级响应。这对长上下文、知识库问答、Coding Agent 与多轮任务很有价值。

Phison 官方资料也显示，aiDAPTIV 主要通过扩展可用内存、保留被淘汰的 KV Cache、减少 Token 重算来改善推理响应；官方测试中，特定设备与场景下的 TTFT 和整体响应速度有明显提升（具体数值请以官方最新测试口径为准）。

Herdsman的优势

> ▪ Windows 环境安装简单<br>▪ 模型下载、组件安装与运行配置更完整<br>▪ 底层使用 llama.cpp，兼容主流 GGUF 模型<br>▪ 内置 Token Router，可把本地模型接入 WorkBuddy、Codex、Claude Code 等 Agent<br>▪ 支持 OpenAI 与 Anthropic 兼容接口<br>▪ 支持 AI SSD、aiDAPTIV 与 KV Cache 预缓存方案<br>▪ 对小内存、小显存但希望运行大模型的用户更有吸引力

Herdsman的 不 足

> ▪ 目前主要面向 Windows 用户<br>▪ 需要登录账号，首次部署与更新仍需联网<br>▪ 底层代码与完整架构未公开，透明度不如 llama.cpp、Ollama 与 Unsloth 核心<br>▪ AI SSD 加速需要硬件、驱动、SSD 与软件版本相互匹配，并非装完软件后所有电脑都能得到同样效果<br>▪ 能否达到「秒级响应」取决于模型大小、上下文、缓存命中率与硬件配置，不能理解为普遍保证

我 的 评 价

如果只打算在电脑上聊天，Herdsman 看起来可能和 LM Studio 差不多。但如果你希望：

> ▪ 本地模型接入各种 Agent<br>▪ 不想手动配置一堆 API<br>▪ 用 AI SSD 跑更大的模型<br>▪ 通过 KV Cache 预缓存降低长对话延迟

那它的产品定位，已经和普通本地聊天软件不在同一层。

官网 [https://www.flowyaipc.cn/ai-engine](https://www.flowyaipc.cn/ai-engine)

## 七、llama.cpp：性能与控制力的基准

llama.cpp 是这五款里最底层的运行时。它基于 C/C++ 与 ggml，围绕 GGUF 模型格式构建，后端覆盖 CUDA、Metal、Vulkan、HIP、SYCL、OpenVINO、CANN、MUSA、OpenCL，以及 CPU + GPU 混合推理。

优点

> ▪ 性能通常非常强<br>▪ 硬件覆盖最广<br>▪ 支持多种量化格式<br>▪ 支持多 GPU、CPU / RAM offload 与 KV Cache<br>▪ 支持连续批处理、多用户并发、工具调用、结构化 JSON、Embedding 与 Rerank<br>▪ llama-server 提供 OpenAI 与 Anthropic 兼容接口<br>▪ 支持 Docker、Android 与嵌入式部署<br>▪ MIT 许可证，代码透明，长期可控

缺点

> ▪ 对普通用户门槛偏高<br>▪ 编译、后端、线程、上下文、GPU 层数与模型模板都需要自己处理<br>▪ 没有完整的模型商城、账号体系与桌面聊天界面<br>▪ 模型管理、监控、鉴权与业务路由需要自己搭建

我 的 评 价

llama.cpp 最适合作为「底座」，但它更像发动机，而不是整车。愿意自己调校的人，能拿到最大的性能与自由度；只想点几下就开始聊天的人，会觉得它过于复杂。

GitHub [https://github.com/ggml-org/llama.cpp](https://github.com/ggml-org/llama.cpp)

## 八、Ollama：开发者最容易用起来的本地 API

Ollama 的核心优势，是把本地模型运行包装成了简单的命令行与 API 服务：一条 **ollama run model** 就能跑模型，也可以通过 REST API、Python SDK、JavaScript SDK 接入自己的应用。

![](https://pic4.zhimg.com/v2-62fdfe5e4ac86f37b47b86ea0f265961_r.jpg)

![](https://pic2.zhimg.com/v2-aae5ed0d505905fc066568f89c5680c5_r.jpg)

优 点

> ▪ 安装与使用简单<br>▪ 模型拉取、缓存与版本管理比较成熟<br>▪ 有自己的模型库与 Modelfile<br>▪ 兼容 OpenAI 生态中的大量应用<br>▪ 支持 Docker、Python、JavaScript、LangChain、LlamaIndex、Open WebUI 等<br>▪ 目前同时使用 llama.cpp 与 Apple Silicon 上的 MLX<br>▪ AMD、Intel 等硬件的 Vulkan 支持越来越完善

缺 点

> ▪ 对模型底层参数的控制不如 llama.cpp<br>▪ 自定义模型与最新量化格式有时需要额外转换<br>▪ 国内使用时，官方模型库与自定义模型下载仍可能受网络和速度影响<br>▪ 默认本地 API 不校验认证，暴露到局域网时必须注意安全<br>▪ 想要完整聊天界面，通常还要另装 Open WebUI 等前端

我 的 评 价

Ollama 是「本地模型 API 服务」的默认答案：比 llama.cpp 简单，比 LM Studio 更适合脚本与后端，比 Unsloth 更轻量。但如果你的第一优先级是国内下载体验、Token Router 或 AI SSD 加速，它并不是最有优势的方案。

官网 [https://ollama.com/](https://ollama.com/)

GitHub [https://github.com/ollama/ollama](https://github.com/ollama/ollama)

## 九、五款工具到底怎么选

如果你是普通用户

优先考虑 **LM Studio** 或 **Herdsman**。网络稳定、喜欢图形界面，网络环境复杂、使用 Windows、不用在模型下载上反复折腾。

如果你是开发者

优先考虑 **Ollama** 或 **llama.cpp**。想快速提供一个本地 API，选 Ollama；想把推理引擎嵌进产品，选 llama.cpp。

如果你要训练自己的模型

选 **Unsloth**。训练完成后导出 GGUF，再交给 llama.cpp、Ollama、LM Studio 或 Herdsman 运行。

如果你的硬件配置不错，想实现Token自由

优先考虑 **Herdsman**。它的价值不只是运行模型，而是把本地模型快速接入 WorkBuddy、Codex、Claude Code 等工具，省下手动改配置文件的时间。

如果你内存和显存都不大，却想跑大参数模型

重点关注 **Herdsman + aiDAPTIV + AI SSD**。但请记住：「跑得起来」和「跑得快」是两件事——真正的速度取决于模型量化、活跃参数、SSD 带宽、上下文长度、KV Cache 命中率与具体硬件。

## 十、最终结论

这五款工具没有绝对的第一名，因为它们解决的是不同问题：

**LM Studio** 解决「如何简单地运行模型」

**Unsloth** 解决「如何训练和导出模型」

**llama.cpp** 解决「如何把推理性能与硬件控制做到极致」

**Ollama** 解决「如何快速把模型变成 API」

**Herdsman** 解决「如何在 Windows 上低门槛部署模型并接入各种 Agen」

站在国内用户的实际体验角度，评价本地大模型工具不能只看跑分，还要看这六件事：

> ▪ 模型能不能下载<br>▪ 模型列表能不能加载<br>▪ 本地模型能不能进入真实工作流<br>▪ Agent 配置是不是足够简单<br>▪ 长上下文响应是不是足够快<br>▪ 小硬件能不能运行更大的模型

本地模型的竞争，已经从「能不能跑」，进入了「能不能真正用起来」。
