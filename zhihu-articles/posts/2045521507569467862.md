## 介绍

详解推理任务如何在多 GPU、多机器之间调度，模型热加载/热替换，以及大规模推理服务的架构设计

## 1. 推理服务架构概述

> 前面几篇讲了单帧数据如何在 GPU 上流转。但实际生产环境不是跑一帧，而是 100+ 路视频流、多种算法、多张 GPU、7×24 小时运行——这需要完整的推理服务架构。

### 1.1 从单帧推理到服务化

```text
单帧推理（开发/测试阶段）：
  一张图片 → 预处理 → GPU 推理 → 后处理 → 结果
  → 只关注精度和单帧延迟

推理服务（生产环境）：
  100+ 路视频流 × 5fps × 3 种算法 = 每秒 1500+ 次推理请求
  → 需要管理视频流接入、帧分发、GPU 调度、结果收集
  → 需要处理流断线重连、GPU 故障、算法更新
  → 需要保证 7×24 稳定运行，延迟可控，结果不丢失

  从"推理"到"推理服务"，复杂度提升了一个数量级
```

### 1.2 推理服务的核心组件

```text
推理服务架构：

  摄像头 ×100
      │ RTSP
      ▼
  ┌──────────────────────────────────────────────────┐
  │                 推理服务                          │
  │                                                  │
  │  ┌──────────┐   ┌───────────┐   ┌────────────┐  │
  │  │ 流管理器  │──→│ 帧调度器   │──→│ 推理 Worker │  │
  │  │          │   │           │   │            │  │
  │  │ ·接入流   │   │ ·帧分发    │   │ GPU0: 模型A │  │
  │  │ ·断线重连 │   │ ·负载均衡  │   │ GPU1: 模型B │  │
  │  │ ·抽帧控制 │   │ ·优先级    │   │ GPU2: 模型C │  │
  │  └──────────┘   │ ·路由      │   │ GPU3: 模型D │  │
  │                  └───────────┘   └──────┬─────┘  │
  │  ┌──────────┐                          │        │
  │  │ 模型管理器│   ┌───────────┐          │        │
  │  │          │   │ 结果收集器 │←─────────┘        │
  │  │ ·加载模型 │   │           │                    │
  │  │ ·热替换   │   │ ·格式化    │                    │
  │  │ ·版本管理 │   │ ·去重/过滤 │                    │
  │  └──────────┘   │ ·推送      │                    │
  │                  └─────┬─────┘                    │
└──────────────────────────┼─────────────────────────┘
                           │
                           ▼
                    业务系统（告警、大屏、数据库）
```

**各组件职责**：

| 组件 | 职责 | 关注点 |
| --- | --- | --- |
| 流管理器 | 接入 RTSP/GB28181 视频流，控制抽帧频率 | 断线重连、流状态监控 |
| 帧调度器 | 将抽取的帧分发到合适的 GPU Worker | 负载均衡、优先级调度 |
| 模型管理器 | 管理模型的生命周期（加载/卸载/替换） | 热加载、版本管理 |
| 推理 Worker | 每个 GPU 一个，执行实际的推理计算 | 推理性能、显存管理 |
| 结果收集器 | 汇聚推理结果，格式化并推送给业务系统 | 去重、过滤、可靠推送 |

> **业界推理服务框架对标**：上面描述的是自研推理服务的典型架构。生产中也可以直接使用成熟的开源框架，避免重复造轮子：<br>

| 框架 | 定位 | 核心能力 | 适用场景 |
| --- | --- | --- | --- |
| NVIDIA Triton Inference Server | 通用推理服务框架 | 多后端（TensorRT/ONNX/PyTorch）、动态批处理、多模型并发、模型版本管理、HTTP/gRPC 接口 | 视频推理的主力选择，可替代自研的推理 Worker + 模型管理器 |
| TensorRT-LLM | LLM 专用推理引擎 | 内核级优化、KV Cache 管理、连续批处理 | 如需在视频分析中集成 LLM（如场景描述、事件总结） |
| vLLM | LLM 推理服务 | PagedAttention、OpenAI 兼容 API、高吞吐 | LLM 推理的灵活方案，与 Triton 互补 |
| Ray Serve | 可组合 ML 管道 | 多模型编排、自动扩缩容、异构计算 | 需要多模型串联/并联的复杂推理管道 |

视频推理场景中，**Triton** 是最常用的选择——它内置了动态批处理（本章 §2.2 详述）、模型热替换、多模型并发等能力，可以替代大部分自研组件。如果业务需要更复杂的模型编排（如检测→跟踪→行为分析的多级流水线），可以在 Triton 之上用 Ray Serve 或自研调度层进行编排。<br> 参考链接：[Triton 官方文档](https://docs.nvidia.com/deeplearning/triton-inference-server/user-guide/docs/index.html)｜[Triton + YOLO 部署指南](https://docs.ultralytics.com/guides/triton-inference-server)｜[Triton vs vLLM vs TGI 对比](https://www.clarifai.com/blog/model-serving-framework/)

## 2. 单机多 GPU 调度

> 一台 GPU 服务器通常有 2~8 张 GPU（如 4×L4、8×L40S）。每张 GPU 有独立的显存和算力，模型加载到特定 GPU 上，帧调度器需要决定”这一帧送到哪张 GPU”。

### 2.1 多 GPU 任务分配

```text
典型 4 卡服务器（4 × L4，24GB GDDR6，INT8 稀疏 485 TOPS / 密集 242.5 TOPS）：

┌─────────────────────────────────────────────┐
│                服务器                        │
│                                             │
│  ┌────────┐  ┌────────┐  ┌────────┐  ┌────────┐
│  │ GPU 0  │  │ GPU 1  │  │ GPU 2  │  │ GPU 3  │
│  │        │  │        │  │        │  │        │
│  │模型A   │  │模型A   │  │模型B   │  │模型C   │
│  │(检测)  │  │(检测)  │  │(行为)  │  │(人脸)  │
│  │        │  │        │  │        │  │        │
│  │ 路1~25 │  │ 路26~50│  │ 路1~50 │  │ 路1~50 │
│  └────────┘  └────────┘  └────────┘  └────────┘
│                                             │
│  调度方式：                                  │
│  · GPU 0/1 跑同一个检测模型，各负责 25 路     │
│  · GPU 2 跑行为分析，处理所有 50 路          │
│  · GPU 3 跑人脸识别，处理所有 50 路          │
│  · 同一帧可能送到多个 GPU（先检测再分析）     │
└─────────────────────────────────────────────┘
```

**模型到 GPU 的分配原则**：

| 策略 | 说明 | 适用场景 |
| --- | --- | --- |
| 同模型多卡 | 同一个模型加载到多张 GPU，分摊路数 | 单算法路数多（如 100 路只做检测） |
| 不同模型分卡 | 不同模型加载到不同 GPU | 多算法叠加（检测+行为+人脸） |
| 混合 | 部分卡跑相同模型，部分跑不同模型 | 复杂场景（主算法多路+辅助算法少路） |

### 2.2 GPU 选择策略

当一帧需要送到某类模型的 GPU 时，如果该模型加载在多张 GPU 上，调度器需要选择哪一张：

| 策略 | 原理 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 轮询（Round-Robin） | 依次分配：帧1→GPU0, 帧2→GPU1, 帧3→GPU2… | 简单，实现容易 | 不考虑实际负载，可能不均衡 |
| 最少负载（Least Load） | 选当前队列最短的 GPU | 均衡性好 | 需要实时监控每个 GPU 的队列长度 |
| 亲和性路由（Affinity） | 同一路视频始终送到同一 GPU | 缓存友好（跟踪算法的跟踪状态在同一 GPU） | 某些 GPU 可能过载 |

```text
三种策略对比（4 张 GPU 跑同一个检测模型，50 路视频）：

轮询：
  GPU 0: 路1,5,9,13,17,21,25,29,33,37,41,45,49    → 各 12~13 路
  GPU 1: 路2,6,10,14,18,22,26,30,34,38,42,46,50
  GPU 2: 路3,7,11,15,19,23,27,31,35,39,43,47
  GPU 3: 路4,8,12,16,20,24,28,32,36,40,44,48

最少负载：
  帧 → 检查各 GPU 队列 → 选最短的
  如果某路场景复杂（帧处理慢），对应的 GPU 队列会变长
  → 新帧自动分配到其他 GPU
  → 动态均衡，但需要额外的监控开销

亲和性路由：
  路1~13 → GPU 0（固定）
  路14~26 → GPU 1（固定）
  ...
  → 跟踪算法的状态（目标 ID、运动轨迹）在同一个 GPU 上
  → 不需要跨 GPU 同步跟踪状态
```

> **实践建议**：检测类算法用轮询或最少负载；跟踪类算法用亲和性路由，避免跨 GPU 传递跟踪状态。

### 2.3 动态批处理（Dynamic Batching）

> GPU 的推理吞吐量在 batch 较大时远高于逐帧推理。但视频流是持续产生的，帧到达的时间不统一——如何将多路的帧”凑”成一个 batch，是推理服务提升吞吐的关键。

```text
无批处理（逐帧推理）：

  帧1(路A) → GPU → 结果1    延迟 5ms，吞吐 ~200 fps
  帧2(路B) → GPU → 结果2    每个 GPU 调用只处理 1 帧
  帧3(路C) → GPU → 结果3    GPU 利用率低（~30%）
  帧4(路D) → GPU → 结果4

动态批处理：

  等待窗口（如 10ms）
    帧1(路A)、帧2(路B)、帧3(路C)、帧4(路D) 到达
    → 凑成 batch=[帧1,帧2,帧3,帧4] → GPU 一次推理 → 结果[1,2,3,4]
    延迟 ~8ms（含等待），吞吐 ~800 fps
    → GPU 利用率高（~80%），吞吐提升 4 倍

  关键 trade-off：
    等待窗口越长 → batch 越大 → 吞吐越高 → 但延迟也越高
    等待窗口越短 → batch 越小 → 延迟低 → 但吞吐提升有限
    → 视频场景通常设 5~20ms 等待窗口
```

| 批处理策略 | 原理 | 适用场景 | 延迟影响 |
| --- | --- | --- | --- |
| 静态批处理 | 固定 batch size，凑满才推理 | 请求量稳定且可预测 | 可控但死板 |
| 动态批处理 | 设等待窗口，窗口内到达的帧凑 batch | 视频推理主力方案 | 有等待窗口开销（通常 5~20ms） |
| 连续批处理 | 迭代级调度，完成一个请求立即加入新请求 | LLM 推理为主，视频场景较少用 | 最优（无空等） |

```text
视频场景的批处理实践：

  配置示例（Triton Inference Server）：
    dynamic_batching {
      max_queue_delay_microseconds: 10000   ← 等待窗口 10ms
      preferred_batch_size: [4, 8]          ← 优先凑 4 或 8 的 batch
    }

  效果（以 YOLOv8s 检测为例，L4 GPU）：
    batch=1：~5ms/帧，200 fps
    batch=4：~12ms/帧，330 fps（吞吐 +65%）
    batch=8：~20ms/帧，400 fps（吞吐 +100%）
    batch=16：~35ms/帧，457 fps（吞吐 +128%，但延迟偏高）

  → 视频场景推荐 batch 4~8：吞吐提升明显，延迟仍在可接受范围
```

> **实践建议**：动态批处理是推理服务吞吐优化的首选手段，通常能提升 50%~100% 吞吐，代价是增加 5~20ms 等待延迟。对于视频 5fps 的场景（帧间隔 200ms），这个延迟完全可以接受。Triton Inference Server 内置了动态批处理支持，开箱即用。

### 2.4 显存与算力的双重约束

GPU 的容量受两个因素制约，而不只是算力：

```text
GPU 容量的二维约束：

算力（TOPS/FPS）
  ▲
  │        ┌─────────┐
  │        │ 可用区域 │ ← 算力和显存都够
  │        │         │
  │  ──────┤─────────┤────── 显存上限
  │        │ 显存不足 │ ← 算力有余，但模型装不下
  │        └─────────┘
  │  算力不足区域          ← 显存有余，但推理速度跟不上
  └──────────────────────→ 显存（GB）

场景举例（L4 GPU，24GB GDDR6 显存，INT8 稀疏 485 TOPS）：

场景 1：加载 1 个 YOLOv8s（6MB）+ 50 路视频
  → 显存够（6MB + 输入缓冲区 << 24GB）
  → 算力够（50路×5fps=250fps，INT8 吞吐 ~200fps，接近上限）
  → 瓶颈：算力

场景 2：同时加载 8 个不同模型
  → 8 个模型 × ~10MB = ~80MB（权重不大）
  → 但每个模型的输入/输出缓冲区 + 中间激活占 ~2GB
  → 8 个模型 × 2GB = 16GB，接近 24GB 上限
  → 算力可能只用了 30%
  → 瓶颈：显存

场景 3：3 个模型 + 100 路视频
  → 模型显存：~20GB（接近上限）
  → 算力需求：100×5fps×3模型 = 1500fps（远超单卡吞吐）
  → 瓶颈：算力和显存都不够 → 需要多卡或多机
```

### 2.5 GPU 虚拟化：MIG、时间分片与 MPS

> 有时一张 GPU 的算力/显存对一个模型来说绰绰有余，但”一个模型独占一张卡”又很浪费。GPU 虚拟化技术允许将一张 GPU 分给多个推理任务使用。

```text
三种 GPU 共享方式：

一、MIG（Multi-Instance GPU）—— 硬件级隔离

  A100（80GB）通过 MIG 分割：
  ┌──────────────────────────────────┐
  │          A100 (80GB)             │
  │  ┌──────┐ ┌──────┐ ┌──────┐    │
  │  │实例 1 │ │实例 2 │ │实例 3 │    │
  │  │20GB  │ │20GB  │ │40GB  │    │
  │  │检测  │ │行为  │ │人脸  │    │
  │  └──────┘ └──────┘ └──────┘    │
  │  各实例隔离：显存、算力、缓存独立  │
  └──────────────────────────────────┘
  支持 GPU：A100、A30、H100、H200
  → 适合高-end GPU，每个实例有确定性性能

二、时间分片（Time-Slicing）—— 软件级共享

  L4（24GB）通过时间分片共享：
  ┌──────────────────────────────────┐
  │          L4 (24GB)               │
  │  时间片 1: 模型A（检测）          │
  │  时间片 2: 模型B（行为）          │
  │  时间片 3: 模型A（检测）          │
  │  ...                             │
  │  共享显存（有 OOM 风险）          │
  └──────────────────────────────────┘
  支持 GPU：所有 NVIDIA GPU（包括 L4、T4、L40S）
  → 简单但有性能波动，适合低负载场景

三、MPS（Multi-Process Service）—— 多进程共享

  多个进程共享同一 GPU 的计算资源：
  → 显存共享，计算资源通过 MPS Server 协调
  → 比时间分片开销小，但隔离性弱
  → 适合同一应用的多个推理进程
```

| 方式 | 隔离级别 | 显存隔离 | 性能影响 | 支持的 GPU |
| --- | --- | --- | --- | --- |
| MIG | 硬件级 | ✅ 独立 | 无影响（确定性） | A100、A30、H100、H200 |
| 时间分片 | 软件级 | ❌ 共享 | 上下文切换开销 | 所有 NVIDIA GPU |
| MPS | 软件级 | ❌ 共享 | 较小（协作式） | 所有 NVIDIA GPU |

> **实践建议**：如果使用 A100/H100 等支持 MIG 的 GPU，优先用 MIG 做推理隔离；如果使用 L4/L40S 等中端 GPU，在负载不高时可以用时间分片让多个模型共享一张卡，提高利用率。注意时间分片不适合高负载场景——切换开销会导致延迟波动。

**参考链接**：[NVIDIA MIG 官方页](https://www.nvidia.com/en-us/technologies/multi-instance-gpu/)｜[MIG + Time-Slicing + MPS 指南](https://www.spheron.network/blog/run-multiple-llms-one-gpu-mig-time-slicing-guide/)

## 3. 多机调度与负载均衡

> 单机 GPU 数量有上限（通常 8 张），超过 200~300 路就需要多台服务器协同工作。

### 3.1 为什么需要多机

```text
单机 vs 多机：

单机（4 × L4）：
  ├── 最大路数：~80 路（3 种算法叠加）
  ├── 显存上限：4 × 24GB GDDR6 = 96GB
  ├── 算力上限：4 × 485 TOPS（INT8 稀疏）
  └── 单机故障 → 全部路数中断

多机（3 台，各 4 × L4）：
  ├── 最大路数：~240 路
  ├── 显存：3 × 96GB = 288GB
  ├── 算力：12 × 485 TOPS（INT8 稀疏）
  ├── 容错：1 台故障 → 只影响 80 路，其余 160 路正常
  └── 代价：需要调度器协调多台机器
```

**多机调度的挑战**：

| 挑战 | 说明 |
| --- | --- |
| 机器异构 | 不同服务器可能有不同型号的 GPU（L4、L40S、T4 等混用） |
| 网络延迟 | 机器之间通过以太网通信，帧数据不能跨机器传输（太大） |
| 故障处理 | 某台机器宕机，上面的路数需要迁移到其他机器 |
| 状态同步 | 跟踪算法的状态（目标轨迹）绑定在特定机器上，迁移会丢失 |

> **GPU 型号与代际说明**：本章以 L4（2023 年发布，24GB GDDR6，INT8 稀疏 485 TOPS）为主力示例。2026 年主流推理 GPU 还包括 L40S（48GB GDDR6，L4 升级版）、H100（80GB HBM3，高端推理与训练）、B200（192GB HBM3e，Blackwell 架构，最新一代）。早期 T4（2018 年，16GB GDDR6，130 TOPS）仍在部分存量项目使用，但已逐步退场。调度器需要感知不同 GPU 的算力差异，按权重分配任务（详见 §3.3）。<br>GPU 算力标注注意：NVIDIA 官方通常标注”稀疏（Sparsity）”算力，实际密集推理场景约为稀疏值的 50%。例如 L4 INT8 稀疏 485 TOPS，密集约 242.5 TOPS。规划容量时建议以密集值为准。

**服务容量规划方法**：

```text
单台服务器容量估算（以 L4 为例）：

  1. 算力约束路数 = 单卡吞吐(fps) / (路数 × 每路fps × 算法数)
     例：YOLOv8s INT8 ~200fps ÷ (每路 5fps × 1 个检测算法) = 40 路/卡
     4 卡服务器 → 160 路（仅检测）

  2. 显存约束路数 = (总显存 - 模型占用) / 每路缓冲区占用
     例：24GB - 6MB(模型) - 2GB(系统预留) ≈ 22GB 可用
     每路帧缓冲 ~20MB → 22GB ÷ 20MB ≈ 1100 路/卡（显存通常不是瓶颈）

  3. 单卡路数 = min(算力约束, 显存约束) = min(40, 1100) = 40 路

  4. 多算法叠加时：3 种算法 × 40 路/算法 = 需要 3 张卡
     → 4 卡服务器可支持 ~40 路 × 3 算法 或 ~160 路 × 1 算法

扩容判断标准：
  · GPU 利用率持续 >85% 且队列有积压 → 需要扩容（加机器或优化模型）
  · 显存使用率 >85% → 需要减少模型或加卡
  · 预留冗余：生产环境建议预留 20~30% 资源应对峰值和故障转移
```

### 3.2 调度模式：推模式 vs 拉模式

```text
推模式（Push）—— 调度器主动分发：

  ┌────────┐     帧      ┌──────────┐
  │ 调度器  │ ──────────→ │ Worker 1 │
  │        │ ──────────→ │ Worker 2 │
  │ (中心)  │ ──────────→ │ Worker 3 │
  └────────┘             └──────────┘

  优点：调度器掌握全局信息，可以做精细的负载均衡
  缺点：调度器是单点，如果调度器挂了全停；调度器需要跟踪每个 Worker 的状态

拉模式（Pull）—— Worker 主动取任务：

  ┌────────┐   帧队列    ┌──────────┐
  │ 生产者  │ ──→ 队列 ──→│ Worker 1 │
  │        │             │ Worker 2 │ ← 各 Worker 空闲时从队列取帧
  │ (流管理)│             │ Worker 3 │
  └────────┘             └──────────┘

  优点：Worker 自驱，不需要调度器跟踪状态；Worker 挂了不影响队列
  缺点：Worker 之间不知道彼此的状态，难以做精确的全局均衡
```

| 对比项 | 推模式 | 拉模式 |
| --- | --- | --- |
| 调度精度 | 高（全局视角） | 中（各自视角） |
| 单点风险 | 有（调度器） | 无（队列可集群化） |
| 扩展性 | 调度器有上限 | Worker 可自由扩展 |
| 适用规模 | 中小规模（<20 台） | 大规模（20+ 台） |
| 典型实现 | 自研调度器 | Kafka/Redis 队列 |

> **视频 AI 的特殊性**：与 HTTP 请求不同，视频流是长连接（持续数小时甚至数天）。一旦某路视频分配给某台机器，通常不会频繁迁移，因为迁移意味着重建 RTSP 会话、重新加载跟踪状态——这个过程需要几秒到几十秒。所以视频 AI 更偏向**静态分配 + 动态微调**。

### 3.3 负载均衡策略

```text
策略一：静态分配（最简单）

  部署时人工规划：
  服务器 1：路1~路80
  服务器 2：路81~路160
  服务器 3：路161~路240

  优点：零运行时开销，配置即生效
  缺点：不灵活，某台机器过载时无法自动分担
  → 适合摄像头数量固定、场景稳定的项目

策略二：按权重分配

  根据各服务器的 GPU 能力分配路数：
  服务器 1（4×L4，485 TOPS/卡 INT8 稀疏）→ 分配 80 路
  服务器 2（4×T4，130 TOPS/卡 INT8）     → 分配 25 路（算力弱，少分）
  服务器 3（2×L40S，366 TOPS/卡 INT8 稀疏）→ 分配 40 路

  → 考虑了机器异构，比均分更合理

策略三：动态分配 + 心跳监控

  调度器定期收集各机器的负载：
  服务器 1：GPU 利用率 85%，队列 12 帧 → 偏忙
  服务器 2：GPU 利用率 45%，队列 2 帧  → 空闲
  服务器 3：GPU 利用率 70%，队列 5 帧  → 正常

  新增视频流时 → 分配到服务器 2
  服务器 1 故障 → 其路数迁移到服务器 2 和 3

  → 最灵活，但实现最复杂
```

### 3.4 任务路由维度

实际调度不只是”帧送到哪台机器”，还要考虑多个路由维度：

```text
路由决策树：

收到一帧
  │
  ▼ 按算法类型路由
  ├── 检测算法 → 送到跑检测模型的 GPU（可能多卡）
  ├── 行为分析 → 送到跑行为模型的 GPU
  └── 人脸识别 → 送到跑人脸模型的 GPU
      │
      ▼ 按路数路由（同算法多卡）
      ├── GPU 0（检测）→ 当前 20 路，队列 3 帧
      └── GPU 1（检测）→ 当前 18 路，队列 1 帧  ← 选这个
          │
          ▼ 按优先级路由
          ├── VIP 路（银行金库、重要出入口）→ 优先处理，保证延迟
          └── 普通路（一般监控区域）→ 正常处理

  → 多个维度组合：算法类型 + 负载均衡 + 优先级
```

### 3.5 容器化与 Kubernetes GPU 调度

> 前面讨论的调度是”推理服务内部”的帧级别调度。在基础设施层面，推理服务本身也需要被编排和调度——这就是 Kubernetes 的角色。2026 年，K8s 已成为 GPU 推理集群管理的事实标准。

```text
K8s GPU 调度架构：

  ┌─────────────────────────────────────────────────────┐
  │ Kubernetes 集群                                     │
  │                                                     │
  │  ┌──────────────┐  ┌──────────────┐                │
  │  │ Node 1       │  │ Node 2       │                │
  │  │ 4×L4         │  │ 4×L40S       │                │
  │  │              │  │              │                │
  │  │ Pod-A (2 GPU)│  │ Pod-C (4 GPU)│                │
  │  │ Pod-B (1 GPU)│  │ Pod-D (2 GPU)│                │
  │  └──────────────┘  └──────────────┘                │
  │                                                     │
  │  核心组件：                                         │
  │  · NVIDIA Device Plugin → 发现并暴露各节点的 GPU    │
  │  · K8s Scheduler → 根据 GPU 资源请求调度 Pod        │
  │  · HPA → 基于 GPU 利用率自动扩缩容                   │
  └─────────────────────────────────────────────────────┘
```

**K8s GPU 调度的核心机制**：

| 机制 | 说明 |
| --- | --- |
| NVIDIA Device Plugin | 在每个节点上运行，向 K8s 汇报 GPU 数量和状态；Pod 通过 [http://resources.requests.nvidia.com/gpu:](http://resources.requests.nvidia.com/gpu:) 1 请求 GPU |
| 节点选择（Node Selector） | 通过标签将 Pod 调度到特定 GPU 型号的节点（如 gpu-type: l4） |
| GPU 时间分片（Time-Slicing） | 在 L4/T4 等不支持 MIG 的 GPU 上，通过时间片让多个 Pod 共享同一张 GPU |
| MIG 分割 | 在 A100/H100 上将单卡分成多个隔离实例，每个实例分配给不同 Pod（见 §2.5） |
| HPA 自动扩缩容 | 基于 GPU 利用率等指标自动增减推理 Pod 副本数 |
| DRA（Dynamic Resource Allocation） | K8s 新一代资源调度方案，支持更精细的 GPU 资源声明（如”我需要 2 个 MIG 切片，每个 10GB 显存”） |

> **视频 AI 的 K8s 部署模式**：视频推理服务通常是**长运行 Pod**（每个 Pod 绑定若干 GPU，持续运行 7×24），而不是 HTTP 那样的无状态弹性部署。因此 K8s 主要解决的是**部署编排**（批量部署、滚动升级、故障恢复），而不是**逐帧调度**（帧调度仍由推理服务内部完成）。

**参考链接**：[K8s GPU 编排 2026 指南](https://www.spheron.network/blog/kubernetes-gpu-orchestration-2026/)｜[NVIDIA K8s Device Plugin](https://github.com/nvidia/k8s-device-plugin)｜[GKE Multi-Instance GPU](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/gpus-multi)

| 维度 | 说明 | 影响 |
| --- | --- | --- |
| 算法类型 | 不同算法送到加载了对应模型的 GPU | 硬约束（GPU 上没这个模型就不能跑） |
| 负载均衡 | 同算法多卡时选负载最低的 | 软约束（影响性能，不影响正确性） |
| 优先级 | VIP 路优先处理，保证低延迟 | 业务约束（影响用户体验） |
| 亲和性 | 跟踪算法绑定 GPU，保持状态连续 | 算法约束（跨 GPU 会丢失跟踪状态） |

## 4. 模型热加载与热替换

> 算法团队会持续迭代模型（修复误报、提升精度、新增类别）。生产环境需要在不停止服务的情况下更新模型——这就是模型热加载。

### 4.1 什么是模型热加载

```text
冷部署（传统方式）：

  时间线：
  ────────────────────────────────────→
  [服务运行 v1] [停机] [部署 v2] [启动] [服务运行 v2]
                 ↑                       ↑
                 服务中断 5~30 分钟        新模型生效

  → 需要停机维护窗口
  → 对 7×24 运行的视频 AI 服务不可接受

热加载（无中断）：

  时间线：
  ────────────────────────────────────→
  [服务运行 v1] [后台加载 v2] [切换] [服务运行 v2]
                               ↑
                               无中断，v2 瞬间生效

  → 服务全程在线
  → 切换过程中不丢帧、不丢流
```

| 对比项 | 冷部署 | 热加载 |
| --- | --- | --- |
| 停机时间 | 5~30 分钟 | 0 |
| 帧丢失 | 有（停机期间所有帧都丢） | 无 |
| 操作复杂度 | 简单（重启服务） | 复杂（需要双缓冲等机制） |
| 回滚 | 容易（重新部署旧版本） | 需要设计（保留旧模型） |

### 4.2 需要热替换的场景

```text
场景一：算法更新
  v1 模型：误报率高，夜间误报多
  v2 模型：优化了夜间场景，误报率降低 50%
  → 需要在不中断服务的情况下切换到 v2

场景二：新增算法
  现有：人脸检测 + 行为分析
  新增：烟火检测（客户要求加烟雾报警）
  → 加载烟火检测模型，不影响已有的两个算法

场景三：模型参数调整
  现有：YOLOv8s，640×640 输入
  调整：改为 YOLOv8m，1280×1280 输入（精度优先）
  → 加载新模型（不同尺寸），替换旧模型

场景四：弹性扩缩容
  白天：加载 3 个模型（人流大，需要更多算法）
  夜间：只保留 1 个关键模型（人少，释放显存给其他用途）
  → 按时间策略动态加载/卸载模型
```

### 4.3 热替换的挑战与方案

模型热替换需要解决三个工程挑战：

**挑战一：显存竞争**

热替换时，新旧模型需要短暂共存——旧模型还在处理在途推理，新模型已经加载到显存。如果两张模型的显存总和超出上限，加载就会失败。

```text
显存竞争问题：

  GPU 显存 24GB，当前模型 v1 占用 8GB
    → 加载 v2 也需要 8GB
    → 切换瞬间：v1(8GB) + v2(8GB) = 16GB → 显存够 ✅

  但如果 GPU 上已有多个模型（总共占用 20GB）：
    → 再加载新模型 → 20GB + 8GB = 28GB > 24GB → 加载失败 ❌

解决方案：提前规划显存预算
  ┌────────────────────────────────────────────────────┐
  │ GPU 显存（24GB）                                     │
  │ [模型A 6GB][模型B 8GB][模型C 6GB][预留 4GB]          │
  │                                ↑                    │
  │                          热加载预留空间               │
  │                    （建议预留 ~20% 显存）              │
  └────────────────────────────────────────────────────┘
  → 如果预留不够，先卸载低优先级模型，腾出空间再加载新模型
```

> **实践建议**：规划 GPU 显存时，不要把模型塞满——为热加载预留约 20% 的空间。如果临时不够，可以先卸载低优先级模型腾空间。

**挑战二：切换一致性**

热替换的”切换瞬间”，前后两帧可能由不同版本的模型处理，导致结果风格突变（如 v2 突然检测到 v1 没检测到的目标）。这不是错误，但需要平滑过渡。有两种主流方案：

```text
方案 A：双缓冲（Double Buffering）—— 原子切换

  GPU 显存：
  ┌──────────────────────────────────────────┐
  │ v1 模型（8GB）  │ v2 模型（8GB）           │  ← 同时存在
  │ (正在服务)       │ (加载完毕)              │
  └──────────────────────────────────────────┘
  切换：指针从 v1 → v2（原子操作，瞬间完成）
  → 新请求全部走 v2
  → 等待 v1 的在途推理完成 → 卸载 v1
  → 切换瞬间无中断，但需要双倍显存

方案 B：渐进式迁移（Gradual Migration）—— 分批切换

  多 GPU 环境下，逐张卡切换：
  时间 →    t1          t2          t3
  GPU 0:   v1    →     v1    →     v2    ← 最后切换
  GPU 1:   v1    →     v2    →     v2    ← 中间切换
  GPU 2:   v2    →     v2    →     v2    ← 最先切换

  → 每阶段只迁移一部分路数
  → 出问题可以随时停止迁移，回滚到 v1
  → 适合大规模部署（100+ 路），降低风险
```

| 对比项 | 双缓冲 | 渐进式迁移 |
| --- | --- | --- |
| 切换速度 | 快（瞬间） | 慢（逐步推进） |
| 显存需求 | 高（双倍） | 低（每次只多一个模型） |
| 风险控制 | 低（一次性切换） | 高（可随时停止回滚） |
| 适用规模 | 单卡 / 小规模 | 多卡 / 大规模 |

**挑战三：引用计数与安全卸载**

热替换时旧模型不能立即卸载——可能还有帧正在推理中（”在途推理”）。必须等所有在途推理完成后再安全卸载，这通过**引用计数**机制实现。

```text
引用计数工作原理：

  v1 的引用计数 = 当前正在使用 v1 推理的帧数

  热替换时间线：
  ─────────────────────────────────────────────→ 时间
  t1: 帧 A 送到 v1 推理     → v1 引用计数 = 3
  t2: 收到热替换指令         → 新帧全部送 v2，v1 不再接收新帧
  t3: 帧 B 送到 v2 推理     → v2 引用计数 +1
  t4: 帧 A 在 v1 推理完成   → v1 引用计数 -1，= 2
  t5: 帧 C 在 v1 推理完成   → v1 引用计数 -1，= 1
  t6: 帧 D 在 v1 推理完成   → v1 引用计数 -1，= 0
      → v1 引用计数归零 → 安全卸载 v1，释放显存 ✅

  关键：在引用计数归零之前，v1 必须保留在显存中
```

> **为什么不能直接卸载**：如果 v1 还有帧在推理就卸载，那些帧的推理结果会丢失或产生非法内存访问。引用计数确保”所有在途推理完成后才释放”。

### 4.4 版本管理与灰度发布

**模型版本管理流程**

一个模型从训练完成到线上运行，经过四个阶段：

```text
模型版本管理流程：

  ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
  │ 训练产出  │──→│ 模型仓库  │──→│ 推理节点  │──→│ 服务运行  │
  │ .pt 文件  │    │ (MinIO)  │    │ .engine  │    │ v1.2.3   │
  └──────────┘    └──────────┘    └──────────┘    └──────────┘
       │               │               │               │
       │ 版本化存储      │ 按版本存储      │ 按节点部署      │ 运行版本
       │ model_v1.pt    │ model_v1.onnx  │ gpu0: v1      │ 配置中心
       │ model_v2.pt    │ model_v2.onnx  │ gpu1: v2      │ 记录每张 GPU
       └───────────────┘               └───────────────┘ 当前版本

  每个阶段都要记录版本号，确保可追溯、可回滚
```

**灰度发布流程**

灰度发布（Canary Release）是模型上线的关键安全机制——先让少量流量使用新模型，观察指标正常后再逐步扩大：

```text
灰度发布步骤：

  步骤 1：算法团队提交 v2 模型到模型仓库
  步骤 2：部署系统选择 1 张 GPU 做灰度（如 GPU 3）
  步骤 3：GPU 3 热加载 v2，10% 的视频流送到 GPU 3
  步骤 4：监控 30 分钟：精度、延迟、误报率
  步骤 5a：指标正常 → 扩大到 30% → 50% → 100%
  步骤 5b：指标异常 → 回滚 GPU 3 到 v1，排查问题

  推进比例：10% → 30% → 50% → 100%
  每阶段观察：30~60 分钟
  关键场景（银行、监狱）：灰度时间延长到 24 小时
灰度发布的监控重点：

  ┌──────────┬──────────────────┬──────────────────────┐
  │ 监控维度  │ 对比方法          │ 判断标准              │
  ├──────────┼──────────────────┼──────────────────────┤
  │ 检测精度  │ v2 vs v1 精度对比 │ 精度 ≥ v1（不能退化） │
  │ 误报率   │ v2 vs v1 误报数   │ 误报率下降（改进目标）│
  │ 推理延迟  │ v2 vs v1 p99 延迟 │ 延迟不能显著增加      │
  │ 显存占用  │ v2 vs v1 显存使用 │ 不超过可用显存        │
  │ 业务指标  │ 实际场景准确率     │ 人工抽检确认          │
  └──────────┴──────────────────┴──────────────────────┘
```

> **灰度发布的核心原则**：永远不要一次性全量上线新模型。即使测试集上表现很好，生产场景（不同光照、角度、遮挡）可能出现意外。灰度发布把风险控制在 10% 的流量内，出问题只影响少量路数，可以快速回滚。

## 5. 模型与数据的存储管理

### 5.1 模型文件的生命周期

```text
模型文件从训练到运行的完整路径：

  ┌────────┐   导出    ┌────────┐   优化  ┌────────┐   部署    ┌──────────┐
  │ .pt    │ ──────→ │ .onnx  │ ──────→  │ .engine│ ──────→ │ GPU 显存  │
  │ 训练产出│         │ 通用格式 │          │ 优化后  │         │ 运行中    │
  └────────┘         └────────┘          └────────┘         └──────────┘
  算法团队            中间产物             部署团队            推理服务
  ~100MB              ~50MB               ~10MB              ~6MB（INT8）

存储位置选择：

  ┌───────────────────────────────────────────────────┐
  │ 存储方案      │ 读取速度 │ 适用阶段       │ 说明    │
  ├───────────────────────────────────────────────────┤
  │ 共享文件系统   │ 中       │ 模型仓库       │ NFS/CIFS│
  │ (NFS)        │ (~500MB/s)│ 集中管理       │ 所有节点│
  │              │          │               │ 可访问   │
  ├───────────────────────────────────────────────────┤
  │ 对象存储     │ 低       │ 归档备份       │ MinIO   │
  │ (MinIO/OSS) │ (~100MB/s)│ 版本历史       │ /OSS    │
  ├───────────────────────────────────────────────────┤
  │ 本地 SSD     │ 高       │ 推理节点加载   │ NVMe    │
  │              │ (~3GB/s) │ .engine 文件   │ SSD     │
  │              │          │               │ 最快    │
  ├───────────────────────────────────────────────────┤
  │ GPU 显存     │ 极高     │ 推理运行       │ GDDR6   │
  │ (VRAM)      │ (~300GB/s │ 模型权重+激活  │ (L4)    │
  │              │  或更高)  │               │ HBM3    │
  │              │          │               │ (A100   │
  │              │          │               │ ~2TB/s) │
  └───────────────────────────────────────────────────┘
```

> **实践建议**：推理节点启动时从 NFS 拉取 .engine 文件到本地 SSD，然后从本地 SSD 加载到 GPU 显存。热加载时也从本地 SSD 读取（避免网络波动影响加载速度）。

### 5.2 GPU 显存中的模型管理

```text
模型在 GPU 显存中的三种管理模式：

模式一：预加载（Preload）—— 服务启动时全部加载
  ┌──────────────────────────────┐
  │ GPU 显存                      │
  │ [模型A 6MB][模型B 10MB][模型C 8MB]...[预留空间] │
  └──────────────────────────────┘
  优点：首次推理无延迟（模型已就绪）
  缺点：启动慢（加载多个模型需 10~60 秒）；显存占用高
  → 适合模型固定的生产环境

模式二：按需加载（Lazy Load）—— 首次使用时加载
  ┌──────────────────────────────┐
  │ GPU 显存                      │
  │ [空闲] → 首次请求模型A → [模型A 6MB][空闲] │
  └──────────────────────────────┘
  优点：节省显存（未使用的模型不占空间）
  缺点：首次推理慢（需先加载模型，~1~5 秒）
  → 适合模型种类多但不是同时使用的场景

模式三：动态加载/卸载（Dynamic Load/Unload）
  ┌────────────────────────────────────────┐
  │ GPU 显存（24GB）                        │
  │                                        │
  │ 白天：[模型A][模型B][模型C] + 空闲 8GB   │
  │         ↓ 策略切换                       │
  │ 夜间：[模型A][模型D（夜间专用）]+ 空闲 14GB│
  │                                        │
  │ 卸载模型B/C → 加载模型D                  │
  └────────────────────────────────────────┘
  优点：按需使用显存，最大化 GPU 利用率
  缺点：切换有延迟（卸载+加载需几秒）；实现复杂
  → 适合模型多但显存有限的场景
```

**模型预热（Warm-up）**：

加载模型后，第一次推理通常比后续推理慢 2~5 倍（因为 GPU 需要编译和缓存 CUDA 内核）。生产环境在模型加载后会做**预热**——用几张假图跑几次推理，让 GPU 完成内核编译，然后再接入真实流量。

```text
预热过程：

  模型加载完成
    → 用随机数据推理 3~5 次（~0.5 秒）
    → 推理延迟从 20ms 稳定到 5ms
    → 预热完成，开始接收真实帧

  不预热的后果：
    第一帧推理 20ms（冷启动），后续 5ms
    → 如果不预热，第一帧的延迟会触发超时告警
```

### 5.3 推理结果的存储与分发

推理结果的处理也涉及存储策略：

```text
结果流转路径：

  GPU 推理完成
    │
    ▼ D2H 传输
  CPU 内存（结果缓冲区）
    │
    ├── 实时推送（低延迟路径）
    │     → HTTP 回调 / MQTT / Kafka
    │     → 业务系统实时消费（告警、大屏）
    │     → 不落地存储，推完即丢
    │
    ├── 批量写入（持久化路径）
    │     → 每 100ms 或每 100 条批量写入数据库
    │     → 关系型数据库（告警事件）
    │     → 时序数据库（统计数据）
    │     → 向量数据库（特征向量）
    │     → 对象存储（抓拍图）
    │
    └── 结果队列（缓冲区）
          → 当下游消费慢时，结果暂存在队列中
          → 队列满 → 丢弃最老的结果（保实时性）
          → 或 → 降频（从 5fps 降到 2fps，减少结果量）
```

**结果积压处理**：

当推送速度跟不上推理速度时，需按积压程度分级应对（正常缓冲 → 降频 → 丢弃最老结果）。核心原则：宁可丢历史结果，不能影响实时推理。

**结果推送方案对比**：

| 方案 | 实时性 | 可靠性 | 复杂度 | 适用场景 |
| --- | --- | --- | --- | --- |
| HTTP 回调（Webhook） | 中（~100ms） | 中（需重试机制） | 低 | 告警推送、事件通知；业务系统已有 HTTP 接口 |
| MQTT | 高（~10ms） | 高（QoS 保证） | 中 | 实时大屏、移动端推送；IoT 场景友好 |
| Kafka | 中（~50ms） | 高（持久化+回放） | 高 | 大规模结果流、需要多消费者订阅、需要历史回溯 |
| WebSocket | 高（~5ms） | 低（断线需重连） | 中 | 浏览器端实时展示（大屏、管理后台） |
| gRPC 流 | 高（~5ms） | 中（需流控） | 高 | 服务间高性能实时传输 |

> **选择建议**：小项目用 HTTP 回调即可；需要多系统同时消费结果时用 Kafka；实时大屏用 MQTT 或 WebSocket。生产环境通常组合使用：实时告警走 MQTT，结果持久化走 Kafka，历史查询走数据库。

### 5.4 运行监控

推理服务上线后，需要持续监控关键指标来发现问题和评估容量。

**核心监控指标**：

| 指标 | 含义 | 关注点 |
| --- | --- | --- |
| GPU 利用率 | GPU 计算单元的使用比例 | 持续过高需扩容 |
| GPU 显存使用率 | 显存占用 / 总显存 | 过高有 OOM 风险 |
| 推理延迟 p99 | 99% 的请求在此时间内完成 | 超过单帧处理时间需关注 |
| 队列深度 | 等待推理的帧数 | 持续增长说明推理速度跟不上 |
| 丢帧率 | 因队列满或超时被丢弃的帧比例 | 过高需关注 |
| NVDEC 利用率 | 硬件解码引擎使用率 | 接近满载说明解码通道不够 |
| 流状态 | 各路视频流是否正常拉取 | 断流告警 |
| GPU 温度/功耗 | GPU 芯片温度和实际功耗 | 过热会降频导致性能骤降 |

```text
指标关联分析——如何通过指标组合定位问题：

场景 1：队列深度↑ + GPU 利用率↓
  → 推理没瓶颈，瓶颈在上游（解码/预处理）
  → 检查 NVDEC 利用率是否满载，或 CPU 预处理是否卡住

场景 2：GPU 利用率↑ + 显存使用率↓
  → 算力瓶颈（模型小但路数多）
  → 考虑动态批处理提升吞吐，或增加 GPU 卡

场景 3：显存使用率↑ + GPU 利用率↓
  → 显存瓶颈（模型太多挤占显存，算力有余）
  → 考虑模型卸载/合并，或用 MIG 分割

场景 4：推理延迟突增 + GPU 温度↑
  → GPU 过热降频（Thermal Throttling）
  → 检查散热、风扇转速，必要时降负载

场景 5：丢帧率↑ + 所有指标正常
  → 可能是网络抖动导致帧未到达
  → 检查网络和视频源质量
```

**告警阈值建议**：

| 告警级别 | 条件 | 含义 | 建议动作 |
| --- | --- | --- | --- |
| 🟡 警告 | GPU 利用率持续 >85%（10 分钟） | 接近满载 | 准备扩容或优化 |
| 🔴 严重 | GPU 利用率持续 >95%（5 分钟） | 过载 | 立即扩容或减少路数 |
| 🟡 警告 | 显存使用率 >85% | 接近 OOM | 检查是否有模型泄漏 |
| 🔴 严重 | 推理延迟 p99 > 帧间隔的 50% | 帧积压风险 | 排查瓶颈 |
| 🔴 严重 | 队列深度持续增长（不收敛） | 推理跟不上 | 减少路数或增加 GPU |
| 🔴 严重 | GPU 温度 >85°C | 降频风险 | 检查散热 |
| 🔴 严重 | 丢帧率 >5% | 结果不可靠 | 排查原因 |

```text
推荐监控技术栈（2026 主流方案）：

  GPU 指标采集  → DCGM-Exporter（NVIDIA 官方 GPU 指标导出器）
  指标存储/展示 → Prometheus + Grafana（事实标准）
  自定义指标   → 应用内埋点，通过 /metrics 端点暴露给 Prometheus
  告警规则     → Prometheus AlertManager（基于阈值的规则引擎）
  日志         → 各组件输出结构化日志，由 ELK/Loki 收集
```

> 监控不是可选项。生产环境中，**没有监控的推理服务等于黑盒**——出问题只能靠用户反馈，定位极慢。<br> 参考链接：[NVIDIA DCGM 文档](https://developer.nvidia.com/dcgm)｜[DCGM-Exporter](https://github.com/NVIDIA/dcgm-exporter)

### 5.5 常见故障与处理

```text
常见故障分类速查表：

  ┌──────────────┬──────────────────────┬────────────────────────────┐
  │ 故障现象      │ 典型原因              │ 排查方向                    │
  ├──────────────┼──────────────────────┼────────────────────────────┤

  │ 视频流冻结   │ RTSP 断线/网络抖动     │ 检查网络/重连机制           │
  │              │ 源端摄像头重启         │ 检查流管理器重连策略         │

  ├──────────────┼──────────────────────┼────────────────────────────┤
  │ 精度突然下降 │ 模型版本错误          │ 检查当前加载的模型版本号     │
  │              │ 量化校准问题           │ 对比 FP32/INT8 结果         │
  ├──────────────┼──────────────────────┼────────────────────────────┤
  │ 延迟逐渐增大 │ 显存泄漏/碎片化       │ 监控显存趋势/定期重启        │
  │              │ 负载逐渐增加          │ 检查是否新增了视频流         │
  └──────────────┴──────────────────────┴────────────────────────────┘
```

### 5.6 服务可靠性模式

> 推理服务需要 7×24 运行，可靠性不只是”出故障后排查”，更要在架构层面预防故障、快速恢复。

```text
核心可靠性模式：

一、健康检查（Health Check）

  ┌──────────┐  每 5s   ┌──────────┐
  │ 调度器    │ ──────→ │ Worker 1 │ → GPU 正常 + 队列 < 阈值 → ✅ 健康
  │          │         │ Worker 2 │ → 3 次未响应 → ❌ 不健康
  └──────────┘         └──────────┘

  · 每个 Worker 定期上报：GPU 状态、队列深度、最近推理延迟
  · 调度器根据健康状态决定是否继续向该 Worker 分发帧
  · 不健康的 Worker → 停止分发 + 触发告警

二、优雅关闭（Graceful Shutdown）

  收到终止信号（如 K8s 发送的 SIGTERM）
    │
    ├── 停止接收新帧
    ├── 等待在途推理完成（通常 <100ms）
    ├── 推送缓存中的推理结果
    ├── 卸载模型、释放 GPU 显存
    └── 进程退出

  → K8s 默认给 30 秒优雅关闭时间（terminationGracePeriodSeconds）
  → 视频推理通常 5~10 秒内可完成清理

三、滚动升级（Rolling Update）

  更新推理服务版本时，逐台替换：

  时间线：
  ────────────────────────────────────→
  [Node1 v1] [Node2 v1] [Node3 v1]   ← 初始状态
       ↓
  [Node1 v2] [Node2 v1] [Node3 v1]   ← Node1 升级完成
       ↓
  [Node1 v2] [Node2 v2] [Node3 v1]   ← Node2 升级完成
       ↓
  [Node1 v2] [Node2 v2] [Node3 v2]   ← 全部完成

  · K8s 原生支持：kubectl set image → 自动滚动更新
  · 每次只替换 1 台，确保始终有足够的 Worker 在线
  · 替换前先做健康检查，新版本不健康则暂停更新

四、流量重分配（Failover）

  节点故障时的流迁移：
  Node2 宕机
    │
    ├── 调度器检测到 Node2 不健康（心跳超时）
    ├── 将 Node2 上的路数重新分配给 Node1 和 Node3
    ├── 流管理器重建 RTSP 连接（每路 ~1~3 秒）
    ├── 跟踪算法状态丢失（从零开始重建跟踪）
    └── 恢复正常（总耗时 ~10~30 秒）

  → 视频流迁移比 HTTP 请求迁移慢得多（需重建 RTSP + 恢复状态）
  → 因此视频推理更依赖"预防"（冗余部署）而非"快速迁移"
```

> **可靠性设计原则**：视频推理服务与 Web 服务不同——视频流是有状态的（RTSP 长连接 + 跟踪状态），迁移成本高。因此可靠性设计更侧重于**冗余部署**（多台机器互相备份）和**快速检测**（秒级发现故障），而不是**快速迁移**。

## 6. 关键术语速查表

| 术语 | 英文 | 说明 |
| --- | --- | --- |
| 推理服务 | Inference Service | 封装了流管理、调度、推理、结果收集的完整系统 |
| 流管理器 | Stream Manager | 负责视频流的接入、断线重连、抽帧控制 |
| 帧调度器 | Frame Scheduler | 负责将帧分发到合适的 GPU Worker |
| 推理 Worker | Inference Worker | 绑定一张 GPU，执行实际的模型推理 |
| 模型管理器 | Model Manager | 负责模型的加载、卸载、热替换、版本管理 |
| 结果收集器 | Result Collector | 汇聚推理结果，格式化并推送给业务系统 |
| 多 GPU 调度 | Multi-GPU Scheduling | 将推理任务分配到同一服务器上的不同 GPU |
| 轮询 | Round-Robin | 依次将任务分配到各 GPU，简单但不精确 |
| 最少负载 | Least Load | 将任务分配给当前最空闲的 GPU |
| 亲和性路由 | Affinity Routing | 同一路视频始终送到同一 GPU，保持状态连续 |
| 推模式 | Push Mode | 调度器主动将任务推送给 Worker |
| 拉模式 | Pull Mode | Worker 空闲时主动从队列拉取任务 |
| 热加载 | Hot Loading | 不停止服务的情况下加载新模型 |
| 热替换 | Hot Swapping | 不停止服务的情况下替换运行中的模型 |
| 双缓冲 | Double Buffering | 同时保留新旧两个模型，原子切换指针实现无中断替换 |
| 渐进迁移 | Gradual Migration | 分批次将视频流从旧模型迁移到新模型 |
| 引用计数 | Reference Counting | 跟踪当前使用模型的推理数量，归零后安全卸载 |
| 灰度发布 | Canary Release | 先在小范围部署新模型验证，逐步扩大范围 |
| 模型仓库 | Model Registry | 集中管理模型版本和文件的存储系统（如 MinIO、MLflow） |
| 模型预热 | Model Warm-up | 加载后用假数据推理几次，消除首次推理的延迟抖动 |
| 预加载 | Preload | 服务启动时将所有需要的模型一次性加载到 GPU |
| 按需加载 | Lazy Load | 首次使用某模型时才加载到 GPU |
| 结果积压 | Result Backlog | 推理结果产生的速度超过下游消费速度 |
| 动态批处理 | Dynamic Batching | 将等待窗口内到达的多个推理请求凑成一个 batch，提升 GPU 吞吐 |
| 连续批处理 | Continuous Batching | 迭代级调度，完成一个请求立即加入新请求，最大化 GPU 利用率 |
| Triton Inference Server | Triton | NVIDIA 官方推理服务框架，支持多后端、动态批处理、多模型并发 |
| MIG | Multi-Instance GPU | 将 A100/H100 等 GPU 硬件分割为多个隔离实例 |
| 时间分片 | Time-Slicing | 软件级 GPU 共享，通过时间片让多个任务轮流使用 GPU |
| MPS | Multi-Process Service | 多进程共享 GPU 的轻量方案，协作式资源共享 |
| 健康检查 | Health Check | 定期检测 Worker 的 GPU 状态和推理能力 |
| 优雅关闭 | Graceful Shutdown | 收到终止信号后等待在途任务完成再退出 |
| 滚动升级 | Rolling Update | 逐台替换推理节点，保证服务不中断 |
| Device Plugin | NVIDIA Device Plugin | K8s 插件，向集群暴露节点上的 GPU 资源 |
| DRA | Dynamic Resource Allocation | K8s 新一代资源调度方案，支持精细的 GPU 资源声明 |
