Agent 执行长任务时，往往要反复搜索、阅读材料、调用工具。随着交互轮次增加，消息历史不断变长：一方面，模型的上下文窗口有上限；另一方面，保存和反复读取历史 KV cache 的开销也在增加。常见的处理方式，是删掉较早的内容，或者把它们压成摘要。不过，我们在实验中发现，文本变短，并不一定意味着推理成本更低。要理解这个看似矛盾的现象，需要看一看：修改文本之后，底层缓存发生了什么？

这篇 **《Cache Engineering for Agents》** 就从这个问题出发，尝试让 Agent 直接管理 KV cache，并为此实现了推理服务系统 **AKV**。核心思路是：让不再需要的缓存退出后续注意力计算，同时继续复用保留的状态，不必先改写文本历史，再重新计算缓存。

- **GitHub**：[thu-nics/AKV](https://github.com/thu-nics/AKV)
- **项目网站**：[AKV 项目主页](https://fuvty.github.io/thinking_yard_project_page/projects/akv/)

### 1. Context Engineering：压缩历史文本的收益与代价

先看一个具体场景。Agent 已经搜索了多轮网页，并根据搜索结果完成了一部分分析。任务继续推进后，早期的大段网页内容不再需要频繁查阅，于是我们把这些工具回复从消息历史中删掉。

文本确实变短了，但缓存不能直接照搬。后续消息的 KV 状态，是在旧内容仍然存在时计算出来的；一旦修改前面的文本，这些状态就不再对应新的上下文。为了得到与修改后文本一致的状态，服务端需要重新计算保留部分的缓存，这就是 **re-prefill**。

我们在 GPT-OSS-120B 的 BrowseComp-Plus 实验中测试了一种直观的文本裁剪策略：保留推理等其他消息，只保留最近 12 轮工具回复，逐步移除更早的工具回复。例如，第 13 轮工具回复加入后，就删除第 1 轮的工具回复。然而，第 1 轮之后保留的推理和工具回复，其 KV 都是在原有文本前缀下生成的，因此服务端还要对这段保留历史重新做 prefill。随着裁剪不断进行，这类重算也会反复发生。

完整上下文基线每一步需要访问更多 KV，却能复用未改动的历史缓存；文本裁剪减少了后续注意力需要访问的内容，却增加了重算开销。在这组实验中，重算的代价超过了裁剪带来的节省，总推理成本反而达到完整上下文基线的 **1.85 倍**。因此，衡量上下文管理的成本，既要看每一步访问多少缓存，也要看已有缓存能否持续复用。

摘要可以进一步压缩要重算的内容，但压缩得越狠，也越容易丢掉后续任务需要的细节。

这让我们把问题重新表述为：**如果目标是减少每一步实际访问的 KV，能否直接操作缓存，让剩下的状态继续用？**

### 2. Cache Engineering：直接控制 KV cache

Cache Engineering 的做法很直接：保留完整的文本轨迹，选择性地让部分 KV 退出后续注意力计算，复用其余缓存。

![](https://picx.zhimg.com/v2-b35eac31d3e78a182827b71c5c155901_r.jpg)
*图 1：修改前面的文本，需要重算后续缓存；直接移除部分 KV，可以继续使用保留的状态。图中嵌套色块表示保留状态可能携带此前历史的信息。*

继续用刚才的例子：一段旧搜索结果已经参与了后续推理。即使移除它自己的 KV，后续推理的 KV 仍然是在读过这段材料的条件下生成的，可能保留其中的部分信息（当然，这不等于能无损记住被移除内容的所有细节）。

为了让这种控制可以被明确执行，我们定义了三个操作：

- **Append**：加入新 token 的 KV，也就是常规推理中的缓存追加。
- **Drop**：让选中的 KV 不再参与后续注意力计算，其余 KV 不受影响。
- **Repos**：重新安排保留缓存的位置编码，防止位置编号继续增长，超过模型支持的上下文范围。

对于使用 RoPE 的模型，Repos 可以通过调整缓存 Key 的旋转编码实现，无需为此重新进行一次完整模型前向计算。

### 3. AKV 解决的关键：同样的文本，可能对应不同的缓存

要把这个想法放进推理服务系统，还需要解决一个问题：缓存状态取决于缓存操作发生的顺序。

假设历史包含 A、B、C 三段内容。我们可以先生成 C，再移除 A 的 KV；也可以先移除 A 的 KV，再生成 C。

两种情况最终都留下 B 和 C，但第一种情况下，C 计算时可以直接看到 A；第二种情况下不能。因此，**最终保留的文本相同，KV 状态也可能不同**。仅凭 token 前缀匹配，已经不足以判断缓存能否复用。

![](https://pic1.zhimg.com/v2-ee447dc35e895b145176a1d4b0f485c4_r.jpg)
*图 2：论文中的三条缓存操作轨迹。它们最终都保留 B 和 C，但 C 计算时可访问的历史不同，因此得到不同的 KV 状态。右侧扩展的 radix tree 记录删除操作发生的位置，在共享兼容缓存的同时区分不同状态。*

为此，我们基于 SGLang 构建了 AKV，让服务端同时理解文本历史和缓存操作历史：

- **正确复用**：扩展 radix tree，记录操作发生的位置，区分不同历史产生的缓存状态。
- **及时释放**：把“某个请求不再使用这段 KV”和“物理释放这段 KV”分开处理，避免影响仍依赖它的其他请求。
- **恢复缺失状态**：用 segment-batch attention 表示各阶段可见的缓存和位置编码，在一次 prefill 中恢复所需状态。

对 user 来说，接口仍然很简单：照常提交消息，再附上缓存操作指令。下面是一个用法的接口示例：

![](https://pica.zhimg.com/v2-11aecad8052ac7bc6fbb57dc29086086_r.jpg)
*图 3：AKV 请求示例。消息从 0 开始编号，右侧标注对应的缓存操作，用于解释含义，不属于实际请求的 JSON。*

- **`messages`**：保留完整的消息历史。这里的用户消息、模型回复和工具返回分别是 `m₀`、`m₁`、`m₂`，处理每条消息时会追加对应的 KV。
- **`cache.drop`**：指定“在哪条消息处理完后，移除哪些消息的 KV”。例如，`「1」: [0]` 表示处理完 `m₁` 后移除 `m₀` 的 KV；`「2」: [1]` 表示处理完 `m₂` 后移除 `m₁` 的 KV。消息文本仍保留在 `messages` 中。
- **`cache.reposition`**：指定何时调整保留缓存的位置编码。这里的 `[2]` 表示在处理完 `m₂` 后执行 Repos。

这样，Agent 只需描述**操作什么、何时操作**。具体哪些状态还驻留在服务端、哪些需要恢复，都由 AKV 处理。

### 4. 实验：更低的成本，也能得到更好的结果

我们在 MiniMax-M2.7、GPT-OSS-120B 和 MiroThinker-1.7-Mini 上进行了 benchmark evaluation，覆盖 BrowseComp-Plus、GAIA-Text、SWE-bench Verified 和 xbench-DeepSearch-2510，包含搜索与软件工程任务。

我们比较了以下三种模型历史管理设置：

- **Standard**：在模型上下文达到较高阈值后触发摘要。GPT-OSS-120B 和 MiniMax-M2.7 的阈值为 96K token，MiroThinker-1.7-Mini 为 192K token。
- **Text Engineering**：采用与 Standard 相同的摘要策略，但将所有模型的触发阈值统一降低到 48K token，更早压缩历史。
- **AKV**：采用简单的 tool response KV 滚动删除策略，并在达到一定阈值时触发 repos 操作。保留推理状态和最近 12 条 tool response 的 KV，移除更早的 tool response 的 KV。Repos 的触发阈值与对应模型的 Standard 摘要阈值保持一致。

在 3 个模型、4 个 Agent benchmark 上，相比 Standard，AKV 实现了**平均推理成本降低 27.7%，平均成绩提升 1.7 个百分点**；相比更早触发摘要的 Text Engineering，平均成本也降低了 **21.9%**。

![](https://pic3.zhimg.com/v2-a1b5c7c627b829b5169f37f7172ea218_r.jpg)
*表 1：论文主结果表。Score 为成功率（%），Cost 为平均单任务成本（美分），灰色行表示 AKV。*

系统效率也有实际收益。在 8 张 A800-80GB GPU 上，使用 GPT-OSS-120B 回放 80 个长上下文 SWE-bench Verified 任务，按各方法达到最高系统吞吐量的并发配置比较，AKV 的**输出吞吐量达到 Standard 的 1.18 倍，P95 请求延迟降低 1.51 倍**。

![](https://picx.zhimg.com/v2-da35c6519a4e28abdaff61e6efb7a15f_r.jpg)
*图 4：根据论文 Table 2 绘制的系统效率曲线。紫色为 AKV，蓝色为 Text Engineering，灰色为 Standard。上排为输入、输出吞吐量，越高越好；下排为 P95 首 token 延迟和请求延迟，越低越好。输入吞吐量按逻辑 token 统计，包含已被 Drop 的 token。*

随着并发提高，Standard 的 KV 容量压力增大，更多时间花在重新 prefill 上，吞吐量下降、请求延迟上升。AKV 通过减少活跃 KV，在较高并发下仍能维持较高吞吐量和较低延迟。

![](https://pica.zhimg.com/v2-6362018b8d5929784dba5403a2b70162_r.jpg)
*图 5：另一组在线评测中，AKV 用更少的 GPU 时间达到更高的最终成功率。实验使用 GPT-OSS-120B、SWE-bench Verified 前 100 个任务，每种方法运行三次；它与上述 80 任务回放实验是两组独立评测。*

### 5. RSI：让 Agent 迭代优化 Cache Engineering 策略

有了 AKV 提供的缓存操作接口，我们进一步开展了 **RSI（Recursive Self-Improvement，递归自我改进）实验**：让 Agent 自己搜索、评估并迭代改进 Cache Engineering 策略，探索比手工设计的滚动删除策略更好的成本与准确率权衡。

具体来说，我们让 MiniMax-M2.7 在 **20 个 BrowseComp-Plus 任务**上迭代搜索缓存管理策略，再用独立的 **100 个任务**评估得到的策略。

结果表明，RSI 找到的策略在维持 Standard 准确率的同时，**相对手工设计的策略进一步降低成本 7.1%**。如果以 Standard 为比较基线，第 3 轮找到的策略降本 **15.6%**，第 6 轮达到 **17.8%**。

![](https://picx.zhimg.com/v2-7896f955813f87c7ce390394ca2e0bcd_r.jpg)
*图 6：实心点表示达到基线准确率的候选策略，空心点表示未达到；紫线记录满足准确率要求的当前最低成本。图中的 15.6% 和 17.8% 均相对 Standard 计算。*

### 6. 总结与展望

这项工作的核心，是提出 **Cache Engineering，为模型的上下文管理增加一个新的维度：KV cache。** 除了在文本层组织和压缩历史，Agent/Harness 还可以直接控制哪些 KV 状态参与后续推理，在保留完整文本轨迹的同时，调整模型实际使用的上下文。

为了让这个维度便于探索，我们实现了 AKV serving system，通过简单的接口开放缓存操作，并由服务端处理缓存的复用、释放和恢复。这样，开发者可以把精力放在策略本身：哪些信息值得保留、何时移除旧缓存，以及如何根据任务进展调整这些决策。

文中的滚动删除策略和 RSI 实验，是我们沿着这个方向做的初步探索。我们希望 Cache Engineering 和 AKV 能支持更多研究者尝试面向不同模型、任务和预算的上下文管理策略，也欢迎大家一起探索，Agent 如何更有效地使用自己的 KV Cache。
