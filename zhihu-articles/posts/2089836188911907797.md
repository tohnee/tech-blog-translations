## 一、理论知识

## 1. 大模型的本质是什么？

大模型的本质，其实就是一个极其复杂的数学函数，而它的“灵魂”则藏在数以亿计的参数之中。所谓训练，本质上就是一场寻找最优参数的“寻宝之旅”。我们常说模型“智能”，是因为它每次吐出一个词时，背后都在做同一件事——根据当前已有的词，计算下一个词出现的概率。这个概率计算，正是由那个巨型函数完成的。函数里的参数，就像是模型的“记忆细胞”和“知识仓库”，模型回答得准不准、灵不灵，很大程度上取决于这些参数是否被调教得足够好。当然，模型结构本身也至关重要，但说到底，训练的全部努力，就是为了让这些参数无限逼近“最优解”。

![](https://pic3.zhimg.com/v2-1ab0ba7dbfdd2360184c46f3dfe565ca_1440w.jpg)

![](https://pic1.zhimg.com/v2-e9a1ea6d226d686a5cd678498f3c0d5c_1440w.jpg)

> 从数学视角看，大模型本质上是一个高维非线性函数，其核心能力由模型参数承载。训练过程，正是为了求解一组能使预测分布尽可能贴近真实数据分布的优质参数。模型推理时，每一个输出 token 的生成，都依赖于当前上下文对下一个词的概率估计，而这一计算完全由该函数的前向传播完成。因此，参数的质量直接决定了模型输出的准确性与泛化能力——可以认为，模型所学的知识和技能，最终都以权重形式固化在这些参数中。当然，参数的有效性也受模型架构的制约，但归根结底，模型训练就是在高维空间中寻找那个“最优参数点”的优化过程。

## 2. 如何得到优质参数？

小时候解方程，我们总有一个现成的公式可以把未知数直接算出来。但大模型的参数可没这么“老实”——它们不是算出来的，而是一步一步“试”出来的。

具体怎么试呢？整个过程像一场盲调：

**（1）随机起跑** ：既然不知道最优参数在哪，那就先闭着眼睛随机给所有参数赋个初始值。

**（2）试跑一次** ：把训练数据喂进去，让模型根据当前参数预测下一个词。比如正确答案是“学习”，模型却只给了0.0001的概率——这错得简直离谱。

**（3）记录偏差** ：这个离谱的程度我们给它起个名字，叫 **损失** 。损失越大，说明刚才那组参数越不靠谱。

**（4）寻找方向** ：接下来，我们要对损失求导，看看每个参数该往哪个方向调才能减少损失。这个求导结果，我们称之为 **梯度** （过程极其复杂，咱们只管用它）。

**（5）迈出一步** ：有了梯度，再用一个简单的更新公式： **新参数 = 旧参数 - 学习率 × 梯度** 。看不懂公式没关系，本质就是：用旧参数加上或减去一个数，得到新参数。

![](https://pic1.zhimg.com/v2-9a8f2c0e163d2a5740adc3cd2d5082d4_1440w.jpg)

就这样，我们不停地“试跑→算损失→求梯度→更新参数”，反复循环，参数就会从“完全随机”慢慢变成“越来越靠谱”。至于要循环多少次才停下来？如下。

## 3. 怎么知道模型学得好不好？

模型训练的终止时机，本质上取决于对模型泛化能力的评估。最直观的监控指标即前文所述的 **损失函数** ——若损失持续居高不下，表明模型尚未有效拟合，训练仍需继续。

![](https://picx.zhimg.com/v2-07776b40777d5e767bb5cca242975c29_1440w.jpg)

然而，仅凭训练集损失下降并不足以证明模型真正“学会”。这如同学生熟记习题答案而非理解原理，在机器学习中即为 **过拟合** （Overfitting）风险。为解决此问题，我们引入 **验证集** （Validation Set），该数据集不参与训练，仅用于测试模型对未见样本的泛化表现。

通过对比训练集与验证集上的损失曲线，可精准判断模型状态：

| 现象 | 训练集损失 | 验证集损失 | 诊断结论 |
| --- | --- | --- | --- |
| 欠拟合 | 高 | 高 | 模型未充分学习，表达能力不足或训练轮次不够 |
| 过拟合 | 低 | 高 | 模型过度记忆训练数据，丧失泛化能力 |
| 理想状态 | 低 | 低（且同步下降） | 模型学到通用规律，拟合良好 |

![](https://pic1.zhimg.com/v2-23c85010ecdb434ec2ba8c9b9f32b530_1440w.jpg)

理想状态是两条损失曲线均平稳下降且趋于收敛。此外，评估维度远不止损失一项，后续将展开介绍更多评价指标及其适用场景。总而言之，在微调过程中，实时、多维度的效果评估是确保训练质量的核心环节。

## 4. 到底什么是微调？

**微调** （Fine-tuning）的核心定义是：在预训练模型的基础上，针对特定下游任务，继续对模型参数进行有监督的迭代优化。

为什么要这么做？因为通用的预训练模型虽已具备较强的特征提取能力，但未必与你的具体任务分布完全对齐。此时有两种技术路线可选：

| 对比维度 | 从头训练（Train from Scratch） | 微调（Fine-tuning） |
| --- | --- | --- |
| 参数初始化 | 随机初始化（缺乏先验） | 预训练权重初始化（富含先验） |
| 训练成本 | 极高（数据、算力、时间） | 较低（仅需少量任务数据） |
| 收敛速度 | 慢（需从零拟合） | 快（已处较优起点） |
| 适用场景 | 无合适预训练模型时 | 有高质量预训练模型可用时 |

![](https://pic2.zhimg.com/v2-95620d291d51c700cfb346c82d87f56d_1440w.jpg)

两者的本质差异在于 **初始参数的知识含量** ——随机初始化相当于“白纸一张”，而预训练权重则承载了模型在大规模数据上学到的通用知识。微调的本质，是将这些通用知识“迁移”到你的特定任务中，用少量任务数据进行定向打磨。

形象地说，从头训练是“从北京徒步到罗马”，微调则是“先乘飞机到罗马城郊，再步行至终点”——殊途同归，但后者在效率上具有压倒性优势。

## 5. 微调的流程是什么？

微调的整体流程可归纳为三个核心环节： **基座模型选型、微调数据准备、训练策略选择** 。三者共同决定了最终效果的上限与训练效率。

![](https://pica.zhimg.com/v2-b5a5eb48173882a0ceb86ac0bf86e242_1440w.jpg)

### **（1）步骤一：基座模型选型**

微调的本质是在已有参数基础上继续优化，因此选择一个合适的预训练模型作为起点至关重要。这个起点模型称为 **基座模型** （Base Model）。选型时需综合考虑模型规模（参数量）、预训练领域与目标任务的匹配度，以及推理效率等因素。

### **（2）步骤二：微调数据准备（关键环节）**

数据质量是微调效果的基石。业界共识 **“Garbage In, Garbage Out”** 精准概括了这一点——输入数据的质量直接决定了输出质量。高质量微调数据应具备以下特征：标注准确、覆盖目标任务的核心场景、分布与真实应用尽可能一致。此环节投入的精力，往往与最终效果成正比。

### **（3）步骤三：训练策略选择**

目前主流的微调方法可归纳为三类：

| 方法 | 调整范围 | 算力消耗 | 适用场景 |
| --- | --- | --- | --- |
| 全量微调（Full Fine-tuning） | 全部参数 | 高 | 任务差异大、算力充裕 |
| 冻结微调（Freeze Fine-tuning） | 仅调整输出层或顶部若干层 | 中 | 资源受限、模型规模庞大 |
| LoRA微调（Low-Rank Adaptation） | 注入低秩模块，不直接修改原参数 | 低 | 性价比优先、快速迭代 |

![](https://pic4.zhimg.com/v2-7aa482c543203397ecc8324953cacc2f_1440w.jpg)

其中， **LoRA微调** 的核心思路是：不直接调整原始权重矩阵，而是在其旁路引入一个低秩可训练模块，仅训练该模块参数。推理时将原权重与训练好的旁路参数合并，从而以极小的可训练参数量实现对模型的有效适配。具体原理与代码实现，我们将在后面详细展开。

## 6. 什么时候要使用微调？

何时引入微调？业界虽有诸多讨论，但归结起来无非两种驱动因素： **能力瓶颈** 与 **资源瓶颈** 。

![](https://pic1.zhimg.com/v2-2ed76287bb88b79fd893d8c374e16b9c_1440w.jpg)

### **（1）驱动因素一：提示工程触及能力上限**

当你在目标场景中穷尽了提示词优化策略（调整指令、引入Few-shot示例、设计思维链等），模型仍无法稳定达到预期效果时，即构成微调的第一类触发条件。

典型案例如 **Agent工具调用** 场景：模型需从用户自然语言输入中精准识别目标工具及其参数结构。此任务若纯依赖提示词，通常要求基座模型具备较强的语义理解与推理能力（即必须使用高性能大模型）。即便如此，当工具数量超过一定规模（如20+）或参数逻辑较为复杂时，纯提示词方案仍可能力不从心。此类场景，即为微调的强信号。

### **（2）驱动因素二：推理成本与延迟不可接受**

另一类场景是：提示词方案在技术上可行（效果达标），但工程上不可行——具体表现为提示词过长（需嵌入大量示例或背景知识），且必须搭配大模型才能运行。

长序列上下文 + 大参数量模型 将直接导致：

- **显存/算力消耗激增** （资源成本高）
- **推理延迟显著上升** （用户体验差）

在实际业务部署中，这两项约束往往具有刚性。微调的价值在此得以彰显：通过定向微调，将“大模型 + 长提示词”方案替换为“小模型 + 短提示词”方案，在保留甚至提升任务精度的同时，大幅降低资源开销与响应延迟。

## **1. 方法一：WebUI 图形化界面**

**启动命令**

```text
llamafactory-cli webui
```

启动成功后，终端输出 `Running on http://localhost:7860` ，即表示服务已就绪。

**各环境的访问配置**

- **WSL 本地** ：直接访问 `http://localhost:7860`
- **AutoDL 云服务器** ：在本地终端执行端口转发：

```text
ssh -L 8901:localhost:7860 -p 44898 root@<服务器公网IP>
```

转发成功后，本地访问 `http://localhost:8901`

- **魔搭免费服务器** ：该环境的网络策略限制了外部端口访问，配置 WebUI 端口转发步骤较为繁琐。 **建议魔搭用户直接采用配置文件方式** ，在 Notebook 中通过命令行执行微调任务。

> **SSH 命令补全说明：** 
>  您原文中的命令 `ssh -L 8901:localhost:7860 -p 44898 root` 缺少了服务器IP地址，完整格式为：ssh -L 本地端口:localhost:7860 -p 服务器SSH端口 root@服务器IP 
>  其中 `8901` 是本地访问端口（可自定义）， `7860` 是 WebUI 默认端口， `44898` 是 AutoDL 分配给你的 SSH 端口（每台实例不同）， `root@IP` 需要替换为实际地址。

### `（3）合并模型 export`

前文提到，推理验证时需要同时加载基座模型和LoRA适配器（分别对应 `model_name_or_path` 和 `adapter_name_or_path` 两个参数），二者共同构成完整模型。那能否将这两个合并成一个独立的完整模型文件呢？

**答案是可以的** 。LLaMA-Factory 提供了 `export` 命令，可以将基座模型与 LoRA 适配器权重合并，导出为一个完整的模型文件，便于后续部署与分发。

如图修改下列参数：

```text
# 必填：基座模型路径（与训练时保持一致）
model_name_or_path: Qwen/Qwen3-0.6B-base

# 必填：训练时输出的LoRA适配器路径
adapter_name_or_path: saves/Qwen3-0.6B/lora/sft

# 必填：模板（与训练时保持一致）
template: default

# 必填：输出路径
output_dir: output/Qwen3-0.6B
```

![](https://pic2.zhimg.com/v2-f33f3bc2d9f6e26d1a9f310e9aa7de09_1440w.jpg)

执行以下命令：

```text
USE_MODELSCOPE_HUB=1 llamafactory-cli export examples/merge_lora/qwen3_lora_sft.yaml
```

![](https://pic2.zhimg.com/v2-68c859d83ff3585c626b6baaae845c5b_1440w.jpg)

这样就可以把两个模型合并成一个了。

![](https://pic2.zhimg.com/v2-df0948a48c4b6e820318cce7b0edaf23_1440w.jpg)

### `（4）接口 api`

前一步我们通过 `export` 命令将基座模型与 LoRA 适配器合并成了一个完整模型。但合并出来的模型到底能不能用？最直接的验证方式就是 **把它部署成一个 API 接口，然后实际调用一下** 。

LLaMA-Factory 提供了 `api` 命令，可以一键将模型包装成 OpenAI 风格的 API 服务，方便外部程序调用。

与 `chat` 类似， `api` 的核心配置同样包含模型路径、模板格式等推理所需参数——本质原因在于： **无论是 `chat` （命令行对话）还是 `api` （接口服务），底层都是加载同一份模型进行推理** ，区别仅在于交互形式：一个通过终端，一个通过 HTTP 请求。

### **第一步：修改配置文件**

修改 `api.yaml` 配置文件：

```text
model_name_or_path: output/Qwen3-0.6B          # export 导出的完整模型路径

# adapter_name_or_path: saves/Qwen3-0.6B/lora/sft       # LoRA适配器路径，直接注释或者删掉，因为刚刚已经合并了

```

![](https://pic1.zhimg.com/v2-d5317ae15fa3f5695cf5ef5014764278_1440w.jpg)

### **第二步：执行部署命令**

```text
USE_MODELSCOPE_HUB=1 llamafactory-cli api examples/merge_lora/qwen3_lora_sft.yaml
```

![](https://pic3.zhimg.com/v2-c5a9355a472e8dc766075d7855ce5460_1440w.jpg)

启动成功后，终端会显示类似以下信息：

![](https://pic4.zhimg.com/v2-616cf77dcc77b3c6db5cd72df3c74667_1440w.jpg)

这表示 API 服务已在 `http://localhost:8000` 上成功运行。

**第三步：验证接口是否可用**

打开一个新的终端窗口，执行：

```text
curl http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "qwen",
    "messages": [
      {"role": "user", "content": "你好，请介绍一下自己"}
    ]
  }'
```

![](https://picx.zhimg.com/v2-edd6a3b9c4feba5b49b0dec618ea2605_1440w.jpg)

如果一切正常，你会收到模型返回的 JSON 响应，其中 `choices[0].message.content` 字段即为模型的回复内容。说明合并后的模型已成功部署，可正常提供推理服务。
