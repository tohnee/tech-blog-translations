在上一章节，我们介绍了DDP训练的核心原理。在DDP训练中，每一张GPU都需要保存完整的模型权重、优化器参数、梯度等信息。如果单卡的显存放不下这么大的参数怎么办？这一章介绍的ZeRO、FSDP、HSDP就是为了解决这个问题。

## ZeRO-1

ZeRO-1 是大模型分布式训练中非常重要的一种显存优化技术。它的核心思想是：模型参数和梯度仍然在每张 GPU 上完整保存，但优化器状态只在 GPU 之间分片保存。

要真正理解 ZeRO-1，关键是把一个训练迭代拆成四个问题：

1. 参数、梯度、优化器状态分别存在哪里？
2. 反向传播后，梯度如何在 GPU 之间通信？
3. 每张 GPU 如何使用自己持有的优化器状态更新参数？
4. 更新后的参数如何同步到其他 GPU？

### 如何分片

**我们从一个具体的例子开始。**

假设有 4 张 GPU，使用数据并行训练一个包含 12 亿参数的模型。

普通数据并行（DDP）会在每张 GPU 上保存一份完整的模型、梯度和优化器状态。

以 FP16/BF16 模型参数、FP32 主权重、FP32 梯度，以及 Adam 优化器为例，每个参数的典型显存开销如下：

| 模型参数(FP16/BF16) | 2B |
| --- | --- |
| 梯度(FP32) | 4B |
| 主权重(FP32) | 4B |
| Adam状态(一阶矩m+二阶矩v) | 8B |
| 总开销 | 18B |

对于 12 亿参数的模型，单是这些状态就大约需要**21.6GB**。这是每张 GPU 的状态显存，不包含激活值、临时张量、通信缓冲区等。而 DDP 的一个特点是：4 张 GPU 虽然分担了训练数据，却各自重复存储这 21.6 GB 的状态。

ZeRO-1 到底怎么切？

先把 4 张 GPU 编号为 GPU0、GPU1、GPU2、GPU3。在经典 ZeRO-1 设计中，切分的是优化器状态（Optimizer States），不是把模型层拆给不同 GPU。

| 训练状态 | GPU0 | GPU1 | GPU2 | GPU3 |
| --- | --- | --- | --- | --- |
| 模型参数 W | 完整 | 完整 | 完整 | 完整 |
| 梯度 G | 完整 | 完整 | 完整 | 完整 |
| FP32 主权重 | 第 0 片 | 第 1 片 | 第 2 片 | 第 3 片 |
| Adam 一阶矩 m | 第 0 片 | 第 1 片 | 第 2 片 | 第 3 片 |
| Adam 二阶矩 v | 第 0 片 | 第 1 片 | 第 2 片 | 第 3 片 |

假设模型只有 12 个参数：$W=[w_0,w_1,...,w_{11}]$

4 张 GPU 平均分配，每张负责 3 个参数对应的优化器状态。

![](https://pic2.zhimg.com/v2-2cd5115bd93485b80391940421903c07_r.jpg)

为什么切分优化器状态就够了？

以 Adam 为例，每个参数更新时，需要用到：

- 当前梯度 $g_t$；
- 一阶矩 $m_t$，相当于梯度的指数移动平均；
- 二阶矩 $v_t$，相当于梯度平方的指数移动平均；
- 当前主权重 $w_t$。

这些计算是逐参数独立的。更新$w_0$时，并不需要知道$w_1$的一阶矩或二阶矩。**因此，各GPU只需拿到各自参数分片对应的梯度，就能更新自己的参数。**

### 整体流程

![](https://pic2.zhimg.com/v2-ca15f5ab6e0189a7e3d1ef105fcb5ed9_r.jpg)

这里的 All-Gather 是把各 GPU 更新好的参数片段组合成完整模型参数，供下一次前向和反向传播使用。**进入下一轮前，每张 GPU 再次拥有一致的完整模型参数。**

值得注意的是，All-Reduce梯度这一过程也可以和普通DDP训练一样，分为多个bucket使All-Reduce与backward计算重叠。

### 性能分析

回到最初的例子：在普通DDP中，每个参数使用 18 Byte 的训练状态。

$$ M_{DDP}=2+4+4+8=18B $$

在N张 GPU 的 ZeRO-1 中，只有主权重和 Adam 状态被分片，因此理想情况下：

$$ M_{ZeRO1}=2+4+\frac{4+8}{N} $$

例如N=4时，$M_{ZeRO1}=9B$

对于 12 亿参数模型，以上估算对应：

| 状态 | 每张 GPU 的理想显存 |
| --- | --- |
| DDP | 21.6 GB |
| ZeRO-1（4 GPU） | 10.8 GB |

实际占用可能更高，因为还有激活值、CUDA 工作区、通信缓冲区、内存对齐和其他框架开销。

## ZeRO-2

ZeRO-2 在 ZeRO-1 的基础上，进一步将梯度（Gradients）也切分到不同 GPU 上保存。

它的核心变化是：

- ZeRO-1：优化器状态分片，梯度完整保存。
- ZeRO-2：优化器状态和梯度都分片保存。
- ZeRO-3：在 ZeRO-2 的基础上，模型参数也分片保存。

最值得理解的是：**ZeRO-2 为什么不再使用普通 All-Reduce，而是使用 Reduce-Scatter？**

我们从一个 4 GPU 的具体例子讲起。

假设有 4 张 GPU，训练一个包含 12 个参数的模型：$W=[w_0,w_1,...,w_{11}]$

ZeRO-1 将优化器状态切成 4 份：

| GPU | 模型参数 | 梯度 | 优化器状态 |
| --- | --- | --- | --- |
| GPU0 | 完整 | 完整 | 第 0 片 |
| GPU1 | 完整 | 完整 | 第 1 片 |
| GPU2 | 完整 | 完整 | 第 2 片 |
| GPU3 | 完整 | 完整 | 第 3 片 |

注意，这里的模型参数和梯度都是完整的。

假设 GPU0 负责 $w_0,w_1,w_2$对应的优化器状态，那么 GPU0 虽然持有全部梯度，但只使用$G_0=[g_0,g_1,g_2]$来更新自己的参数。

问题在于：既然 GPU0 只需要前三个参数的梯度，为什么还要在 GPU0 上保存全部 12 个梯度？这就是 ZeRO-2 要解决的问题。

### 如何分片

ZeRO-2 的切分方式非常直接：

除了模型参数仍然完整复制在每张 GPU 上，梯度和优化器状态都按照相同的方式分片。

![](https://pic4.zhimg.com/v2-43623d9367476f13a693bace93e5f5e3_r.jpg)

### 通信过程

这是ZeRO-2最重要的部分。先看普通 DDP 和 ZeRO-1 的梯度同步方式：

假设有 4 张 GPU，每张 GPU 都计算出一个长度为 4 的本地梯度：

$$ G_0=[1,2,3,4],G_1=[2,1,4,3],G_2=[3,4,1,2],G_3=[4,3,2,1] $$

All-Reduce 对它们求和：

$$ G=G_0+G_1+G_2+G_3=[10,10,10,10] $$

如果每张 GPU 的 batch 大小相同，再除以 4：

$$ \hat{G}=[2.5,2.5,2.5,2.5] $$

最终每张 GPU 都拿到完整的平均梯度。

但 ZeRO-2 不需要这个结果。因为 GPU0 只负责第 0 片，GPU1 只负责第 1 片，以此类推。

因此我们希望得到：

- GPU0：只拿到第 0 片梯度。
- GPU1：只拿到第 1 片梯度。
- GPU2：只拿到第 2 片梯度。
- GPU3：只拿到第 3 片梯度。

这就是 Reduce-Scatter 的作用。

Reduce-Scatter 可以理解为两个操作的组合：

$$ ReduceScatter=Reduce+Scatter $$

先对不同 GPU 的梯度求和，再把结果切分成 4 份，每张 GPU 只拿到其中一份。

上面的例子中：

$$ G=G_0+G_1+G_2+G_3=[10,10,10,10] $$

然后切分：

| GPU | 得到的梯度 |
| --- | --- |
| GPU0 | [10] |
| GPU1 | [10] |
| GPU2 | [10] |
| GPU3 | [10] |

如果需要平均梯度，则在归约过程中除以 4，或者在后续处理中完成缩放：

| GPU | 最终梯度分片 |
| --- | --- |
| GPU0 | [2.5] |
| GPU1 | [2.5] |
| GPU2 | [2.5] |
| GPU3 | [2.5] |

这里需要特别注意：Reduce-Scatter 并不是先让某一张 GPU 收集全部梯度、算完之后再分发。它是一个集体通信操作，归约和分发由通信算法共同完成。NCCL 可以通过 Ring 等算法实现 Reduce-Scatter。对于较大的梯度张量，它还可以分成多个 bucket，分批进行通信。

## ZeRO-3/FSDP

### 如何分片

ZeRO-1 分片优化器状态，ZeRO-2 进一步分片梯度，**而 ZeRO-3 连模型参数本身也分片。**

这意味着每张 GPU 不再长期保存完整模型，而是只保存自己负责的那一部分。真正要计算某一层时，再通过通信临时把需要的参数收集起来。

![](https://pic1.zhimg.com/v2-4751241169492630f76da253669a3b96_r.jpg)

这和 ZeRO-2 最大的区别是：ZeRO-2 每张 GPU 仍然有完整模型参数，ZeRO-3 则没有。

### 通信过程

假设模型有两个计算层：

```text
Input
  |
Layer 1 (w0 ~ w5)
  |
Layer 2 (w6 ~ w11)
  |
Output
```

4 张 GPU 分别持有：

- GPU0：w0、w1、w2
- GPU1：w3、w4、w5
- GPU2：w6、w7、w8
- GPU3：w9、w10、w11

现在要计算 Layer 1，它需要 w0～w5。但 GPU0 只有 w0～w2，GPU1 只有 w3～w5。怎么办？

在计算 Layer 1 之前，GPU0～GPU3 执行 All-Gather，把参数分片收集起来。

![](https://pic4.zhimg.com/v2-c61865bbfdd1702f21298f0889f80769_r.jpg)

All-Gather 完成后，每张 GPU 都拿到了 Layer 1 所需的完整参数，于是可以执行计算。计算完成后，如果不需要继续保留这些完整参数，就释放非本地分片，只保留自己原本负责的参数。

接下来计算 Layer 2，再重复这个过程。

所以 ZeRO-3 并不是一次性把整个模型 All-Gather 到每张 GPU，而是按需聚合当前计算单元的参数。

**反向传播时，再次 All-Gather，然后 Reduce-Scatter。**

前向传播结束后，模型还需要反向传播来计算梯度。这里有一个容易忽略的细节：反向传播不仅需要梯度计算，还需要对应的前向参数。

但是前向结束时，我们已经释放了聚合出来的完整参数。因此反向传播前，需要再次 All-Gather 对应参数。然后各 GPU 计算梯度，并通过 Reduce-Scatter 完成梯度归约和分片。

| --- | --- |

| FP32 梯度 | 4 Byte |
| FP32 Master Weight | 4 Byte |
| Adam 一阶矩 m | 4 Byte |
| Adam 二阶矩 v | 4 Byte |
| 合计 | 18 Byte |

| 方案 | 单卡训练状态显存 |
| --- | --- |
| DDP | 18 B/param |
| ZeRO-1 | 6+12/N B/param |
| ZeRO-2 | 2+16/N B/param |
| ZeRO-3 | 8/N B/param |

假设 4 张 GPU，模型有 10 亿参数：

![](https://picx.zhimg.com/v2-1cd27f6d045a618e45cd7594da4ad645_r.jpg)

### 通信开销

对比 ZeRO-2：

| 阶段 | ZeRO-2 | ZeRO-3 |
| --- | --- | --- |
| Forward | 直接使用完整参数 | All-Gather 参数 |
| Backward | 使用完整参数 | All-Gather 参数 |
| 梯度同步 | Reduce-Scatter | Reduce-Scatter |
| 参数更新后 | All-Gather / Broadcast 参数 | 不需要立即同步完整参数 |

ZeRO-3 多了前向和反向过程中的参数 All-Gather。

这意味着：

- 显存压力更小；
- 参数通信更多；
- 对 GPU 间互联带宽更加敏感；
- 参数调度不合理时，GPU 可能等待通信，导致计算单元利用率下降。

因此，ZeRO-3 并不一定比 ZeRO-2 快。它主要解决的是模型状态无法放进单卡显存的问题。

### FSDP Unit

至于FSDP，原理上和ZeRO-3其实是一样的。主要区别在于：ZeRO-3 是 DeepSpeed ZeRO 优化体系中的一个阶段，而 FSDP 是 PyTorch 原生提供的分布式训练方案。

**这里主要讲一下FSDP Unit这个概念。**

如果整个模型被看成一个 FSDP Unit，那么每次前向传播之前，都需要 All-Gather 整个模型的参数。假设模型有 70B 参数，这显然会造成非常大的显存峰值。因此，通常会将模型拆分为多个 FSDP Unit。

例如一个 Transformer：

```text
Transformer
│
├── Embedding
│
├── Transformer Block 0  ← FSDP Unit 0
│
├── Transformer Block 1  ← FSDP Unit 1
│
├── Transformer Block 2  ← FSDP Unit 2
│
├── Transformer Block 3  ← FSDP Unit 3
│
└── LM Head
```

每个 FSDP Unit 独立进行参数 All-Gather 和梯度 Reduce-Scatter。

例如：

```text
All-Gather(Block 0)
       |
Forward(Block 0)
       |
All-Gather(Block 1)
       |
Forward(Block 1)
       |
All-Gather(Block 2)
       |
Forward(Block 2)
```

实际实现还可以预取 Block 1 的参数，同时计算 Block 0，从而隐藏部分通信延迟。

这里存在一个权衡：

- Unit 太大：临时聚合参数占用显存较多。
- Unit 太小：通信次数增加，通信启动开销变大。

所以 FSDP 的性能优化，很大程度上取决于如何划分 FSDP Unit，以及如何安排通信和计算重叠。

## HSDP

**HSDP（Hybrid Sharded Data Parallel，混合分片数据并行）**是将**数据并行（Replicated Data Parallel）**和**分片数据并行（Sharded Data Parallel）**结合起来的一种分布式训练方式。

它的核心思想是：先把 GPU 分成多个组，在组内进行 FSDP 分片，在组间进行数据并行复制。这样既能减少单卡显存占用，又能利用高速 GPU 互联完成组内通信，避免所有 GPU 都参与同一个分片通信组。这在多机多卡训练中尤其有用。

**先从FSDP的问题说起。**

假设有 8 台 GPU（这里是 8 张 GPU，不是 8 台机器），全部参与 FSDP FULL_SHARD。每张 GPU 都只保存模型的 $1/8$ 参数、梯度和优化器状态。优点是显存占用非常低，但是，FSDP 需要频繁执行：

- All-Gather：收集完整参数；
- Reduce-Scatter：归约并分发梯度。

如果这 8 张 GPU 分布在不同服务器上，那么通信可能需要经过跨服务器网络，例如 InfiniBand 或 RoCE。跨节点通信通常比单机 NVLink/NVSwitch 慢，通信延迟和带宽都可能成为瓶颈。

那么有没有办法减少跨节点通信？

HSDP 就是为了解决这个问题而设计的。

### 如何分片

假设有 8 张 GPU，分布在两台服务器上：

- Server 0：GPU0、GPU1、GPU2、GPU3
- Server 1：GPU4、GPU5、GPU6、GPU7

HSDP 将它们分成两个 FSDP 组：

![](https://pic3.zhimg.com/v2-db87d2d84cc198d41fa7564949b18620_r.jpg)

这里有一个非常重要的区别：

- 组内：4 张 GPU 共同保存一份模型的分片。
- 组间：两个组各自拥有一份相同的模型状态（按相同规则分片）。

也就是说，HSDP 并不是让 8 张 GPU 一起分片整个模型，而是让两组 GPU 分别维护一份模型副本，每份副本内部再进行 4 路分片。

假设模型有 8 个参数：

$$ W=[w_0,w_1,...,w_7] $$

每个 FSDP 组有 4 张 GPU，因此每组把参数切成 4 份。

| GPU | Server 0 | Server 1 |
| --- | --- | --- |
| GPU0 / GPU4 | w_0,w_1 | w_0,w_1 |
| GPU1 / GPU5 | w_2,w_3 | w_2,w_3 |
| GPU2 / GPU6 | w_4,w_5 | w_4,w_5 |
| GPU3 / GPU7 | w_6,w_7 | w_6,w_7 |

注意，这张表表示两组各自拥有一份相同的模型，只不过每份模型都在组内切成了 4 份。

因此：

- GPU0 和 GPU4 保存相同的参数分片。
- GPU1 和 GPU5 保存相同的参数分片。
- GPU2 和 GPU6 保存相同的参数分片。
- GPU3 和 GPU7 保存相同的参数分片。

参数、梯度和优化器状态都遵循这个分布方式。

需要注意的是，HSDP 的显存节省程度取决于组内分片数量，而不是 GPU 总数。8 张 GPU，组内分片数为 4，那么优化器状态就是按照 4 路切分，而不是 8 路切分。

### 通信过程

我们把通信分为两个维度：

- Sharding Dimension：分片维度。
- Replication Dimension：副本维度。

在我们的例子中：

$$ Sharding Size=4,Replication Size=2 $$

可以把它理解成一个二维 GPU 网格：

![](https://pic4.zhimg.com/v2-14c790d85c314f7759cecf5b0bc9adcd_r.jpg)

### 整体流程

![](https://pic2.zhimg.com/v2-a6b9f55a137e602cac5909c0385dd0d7_r.jpg)

**为什么要跨组对梯度做All-Reduce？**

例如：

- GPU0 管理$w_0,w_1$的优化器状态；
- GPU4 也管理$w_0,w_1$的优化器状态。

但是 GPU0 和 GPU4 处理的是不同的数据，因此它们计算出来的梯度分片可能不同。为了让两个副本组的模型保持一致，需要同步对应分片的梯度。

经过组内 Reduce-Scatter 和组间 All-Reduce 后：

- GPU0 和 GPU4 拿到相同的$w_0,w_1$梯度；
- GPU1 和 GPU5 拿到相同的 $w_2,w_3$梯度；
- 其他 GPU 同理。

由于对应 GPU 的参数和 Adam 状态也是相同的，因此它们可以独立执行相同的 Adam 更新。

最终，两个副本组中的模型参数仍然保持一致。

下一轮前向传播时，各组再分别执行组内 All-Gather。

### 性能分析

假设总共有 8 张 GPU：

- FSDP：8 张 GPU 全部参与参数分片。
- HSDP：分成 2 组，每组 4 张 GPU。

仍然假设每个参数需要 18 Byte 的训练状态。

| 指标 | FSDP | HSDP |
| --- | --- | --- |
| GPU 总数 | 8 | 8 |
| 分片数量 | 8 | 4 |
| 副本数量 | 1 | 2 |
| 每参数理想状态显存 | 2.25 B | 4.5 B |
| 参数分片通信 | 8 卡组内 | 4 卡组内 |
| 梯度跨副本同步 | 不需要 | 需要 |

可以看到：

- FSDP 的显存利用率更高，因为分片数量更多。
- HSDP 的显存利用率稍低，但可以将高频参数 All-Gather 和梯度 Reduce-Scatter 限制在局部 GPU 组内。
- HSDP 需要额外的跨副本组梯度同步。

所以 HSDP 并不是无条件比 FSDP 快，而是在显存、通信带宽和训练吞吐量之间做权衡。
