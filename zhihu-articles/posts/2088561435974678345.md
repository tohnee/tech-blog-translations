如果你一年前打开 pi.dev，会看到一句很骄傲的声明：Pi 不支持 MCP。作者 Mario 还专门写过一篇文章，标题大意是"也许你根本不需要 MCP"。

今天，Pi 背后的团队 Earendil 发了篇文章，标题就叫《You Said No MCP!》

现在 MCP 已经是 Pi 的核心功能了。

为什么改主意？

原文给了几个理由，我概括一下：

第一，MCP 自己变了。过去一年 MCP 进化了不少，今天的 MCP 已经不是当初那个 MCP。

第二，Pi 需要的东西和 MCP 需要的东西其实很像：一个能跑代码的沙箱。为了接入 MCP 做的改造，对 Pi 本身也有用。

第三，他们认为想影响一件事，最好的方式是拥抱它，而不是站在场外评论。

他们对 MCP 的批评并没有消失

MCP 最大的问题还是难以组合。很多 MCP server 仍然是为"把所有工具一股脑塞进上下文"的客户端设计的，返回一大段文本来省 token。

Earendil 的看法是，MCP 应该更像 OpenAPI：工具返回结构化数据，能通过文档和描述被智能发现。CLI 之所以好用，是因为模型可以用 bash 把各种命令串起来。MCP 没有理由做不到这一点。

Codemode 是什么

这是这篇文章的关键概念。

简单说，Codemode 是一个跑在 agent 主循环这一侧的 JavaScript 沙箱。模型不再一个一个地调用工具，而是写一段 JS，把多个工具调用编排、组合起来，按需要的顺序执行，还能并发。中间状态保存在会话里，不需要落盘，也不占上下文。之所以选 JS，是因为小型 JS 引擎可以编译成 WASM，隔离性不错。

原文举了个例子：让 Pi 用 Codemode 从 Linear 拉出 167 个未关闭的 issue，把每个 issue 的评论交给一个分类模型判断语气，最后找出最"暴躁"的用户。结果 156 个是中性，11 个轻度不满，没有特别愤怒的。整个过程是一段脚本跑完，而不是几百次工具调用把上下文撑爆。

我的看法

之前我很多次推荐过 Pi，一个原因就是它极简、不堆功能。这次加 MCP，我不觉得是"打脸"，反而说明这个团队在认真做判断：不喜欢的时候说清楚为什么，改主意的时候也说清楚为什么。

对开发 MCP server 的人来说，这篇文章有一个很实际的提醒：别再只返回一大段文本了。返回结构化数据，把工具描述写清楚。以后越来越多的客户端会用"写代码调工具"的方式，而不是把工具一个个塞给模型。

工具之争没有终点。今天说不要的，明天可能就真香。重要的是知道自己为什么选、为什么变。
