## **引言：把 4 张 GPU 放在一起，为什么不是 4 倍速度？**

假设你正在训练一个 Transformer。单卡每秒能够处理 1,000 个 token，现在新增三张 GPU，速度是否自然变成 4,000 token/s？未必。因为每张 GPU 除了执行本地前向和反向传播，还必须与其他设备交换梯度或模型状态；GPU 之间的网络、数据加载速度、算子效率以及各卡负载，都会影响最终吞吐量。

更重要的是，“跑得快”和“放得下”并非同一问题。普通数据并行可以让四张卡同时处理不同样本，但模型参数、梯度、优化器状态仍可能在每张卡上各有完整副本。假如单卡放不下完整训练状态，仅仅增加 DDP 的 GPU 数量并不能直接解决 OOM。

本文从一条主线出发：数据如何拆、梯度如何合、参数如何保持一致、显存如何进一步分片，以及实际训练程序里每个步骤是如何落地的。将经典机制和 PyTorch 中的 DDP、DeepSpeed ZeRO、FSDP2 放在同一张知识地图里理解。

## **一、数据并行的核心逻辑：数据拆开，模型保持一致**

### **1.1 什么是数据并行？**

数据并行（Data Parallelism）的核心不是“把模型分成四份”，而是“将输入样本分给四个训练进程，每个进程运行同一模型”。例如数据集有 10,000 条训练样本，4 个 GPU 分别读取不重叠的样本子集；在相同的一轮参数更新中，各卡计算不同 micro-batch 的梯度，并协同形成用于更新的一致梯度。

这里的“模型相同”意味着架构、初始参数和同步更新所需状态一致，但输入样本不相同，所以各 GPU 计算出来的局部梯度也不相同。同步后，每个设备再在各自本地执行相同的 optimizer.step()，从而继续保持模型参数一致。

![](https://pic2.zhimg.com/v2-9e39c83630be1707c84305783b8d0c1b_r.jpg)
*图1  四卡 DDP 训练闭环：分数据、算梯度、AllReduce、更新参数*

### **1.2 为什么要“平均梯度”？**

先看最简单的例子：两张 GPU 分别计算到梯度 g₀=2 和 g₁=4，如果每张卡在本地随意更新，参数很快就分叉。同步 DDP 通常把它们聚合并按进程数求平均，即 g=(2+4)/2=3。之后两卡用相同的梯度和优化器状态更新，自然能够继续保持一致。

对于 N 张 GPU、每个进程等量样本且采用 mean reduction 的常见情形，全局梯度可写为 g=(1/N)×Σᵢgᵢ。若每卡样本量不同、损失缩放方式不同，不能直接断言“简单平均局部 mean 梯度”与全局样本级平均完全一致，需要处理样本权重。

**训练时另一个必须算清的量是：全局 Batch Size = 每卡 micro-batch × 数据并行进程数 × 梯度累积步数。假设每卡 micro-batch 为 4，4 张卡，梯度累积 2 次，全局 Batch Size 就是 32。它会影响显存、优化器更新频率及训练动力学。**

### **1.3 数据并行和模型并行到底差在哪里？**

| 维度 | 数据并行（DP/DDP） | 模型并行（TP/PP 等） |
| --- | --- | --- |
| 切分对象 | 样本 / batch | 模型层、张量或计算图 |
| 常见目的 | 提高吞吐量 | 容纳大模型，或扩大并行计算规模 |
| 每卡模型状态 | 普通 DDP 通常完整复制 | 根据并行方式拆分 |
| 主要通信 | 梯度同步 | 激活或中间张量交换 |
| 关系 | 可和 TP、PP 组合 | 可与数据并行联合使用 |

在实际的大模型系统中，两者经常不是“二选一”。一组 GPU 可以先做张量并行（TP）把单层算子拆开，不同 TP 组之间再做数据并行。这也是为什么不能用“一张 GPU 放不下，就只开更多 DDP 卡”来解决所有问题。

## **二、AllReduce 的底层本质：不是神秘的“梯度广播”**

### **2.1 AllReduce 究竟做了什么？**

AllReduce 是集体通信操作：参与的每个进程贡献一个张量，系统执行求和、取最大值等归约运算，然后让每个进程都拿到归约结果。例如四个进程分别提供向量 [1,2]、[2,3]、[3,4]、[4,5]，SUM AllReduce 的结果就是 [10,14]，所有参与进程都会收到同样的 [10,14]。DDP 通常在相应语义下再完成缩放，使最终梯度成为平均值。

概念上，AllReduce 可以理解为 Reduce + Broadcast；但这并不意味着工程实现一定先通过中央服务器做归约，再从中央节点广播。NCCL 可以根据设备拓扑和数据规模等因素选择不同的集体通信实现。

### **2.2 Ring-AllReduce 如何让四张 GPU 协作？**

经典 Ring-AllReduce 将进程组织成环，每张 GPU 只和环上的相邻节点交换数据；完整向量先切成 N 块。第一阶段 ReduceScatter：每一轮交换一个分块并累加，N−1 轮后每卡保留一个已经对所有参与者归约完成的数据分块。第二阶段 AllGather：再用 N−1 轮把这些结果块沿环分发，最终每卡重建完整归约结果。

![](https://pic3.zhimg.com/v2-f1ddacacaa55f5b7071429c3fce23be8_r.jpg)
*图2  经典 Ring-AllReduce：4 卡各执行 3 轮 ReduceScatter + 3 轮 AllGather*

这里有个容易写错的概念：Ring-AllReduce 采用分段传输与流水线执行，并不代表每张 GPU 可以拿到旧梯度就各自“异步参数更新”。典型同步 DDP 仍然需要在当前更新步使用聚合一致的梯度。通信操作在 GPU 上异步发起，与训练算法层面的异步更新是两回事。

如果每个进程同步 S 字节梯度，经典环形算法的单进程发送量约为 2×(N−1)/N×S（忽略协议开销，接收量同阶）；因此其带宽利用特征与把所有信息集中给单一主节点不同。不过通信算法不是只有 Ring：树形及其他拓扑相关实现也可能更合适，实际应依赖通信库策略与性能分析。

## **三、PyTorch DDP 不是“训练结束后才同步”**

### **3.1 从 Autograd Hook 到 Gradient Bucket**

在 PyTorch 的 DistributedDataParallel 中，每个进程通常绑定一张 CUDA GPU。DDP 构造阶段会将模型参数组织进若干梯度 Bucket，并在需要的位置注册 Autograd Hook。反向传播不是一口气把所有梯度都计算完才交流：只要一个 Bucket 所需梯度已经就绪，Reducer 就可以发起这个 Bucket 的 AllReduce；其他尚未完成的层可以继续反向计算。

![](https://pica.zhimg.com/v2-d050b993b6b07215069d2bba737a5148_r.jpg)

这就叫通信与计算重叠（Communication-Computation Overlap）。它提升效率的前提是：部分通信确实能被后续计算时间覆盖，设备与网络也允许并发推进。Bucket 划得太小可能增加通信调用与调度开销；太大则可能要等待更多梯度就绪，减少重叠机会，所以 bucket_cap_mb 不是越小越好。

### **3.2 三个最关键的运行概念**

· Rank：全局进程编号；LOCAL_RANK：本机进程对应的设备序号；WORLD_SIZE：参与进程总数。不要将它们简单等同于“显卡数量”。

· DistributedSampler：让每个进程拿到不同的数据样本；每一轮训练通常需要 sampler.set_epoch(epoch) 以确保合理的分布式 shuffle。

· NCCL：面向 NVIDIA GPU 的高性能通信库。PyTorch DDP 使用通信后端执行集体操作，而不是规定只使用 Ring 算法。

还有一个经常被误解的细节：普通 DDP 的优化器不是由中央服务器统一运行。只要各进程从一致的模型与优化器状态起步，并在每步获得一致梯度，进程就可以分别执行相同的 optimizer.step()。这和早期参数服务器式分布式训练的概念应分开讲。

## **四、为什么 DDP 能多卡加速，却解决不了很多 OOM？**

### **4.1 训练显存究竟花在哪里？**

显存不只有模型权重。完整训练还要保存梯度、优化器状态、反向传播所需激活值，以及 CUDA/通信临时缓冲。为了建立直觉，我们只算一个非常简化的 7B 参数模型：如果参数以 BF16 每参数约 2 字节保存，需要约 14 GB；如果梯度也为 BF16，约 14 GB；采用每参数两份 FP32 动量状态的 Adam 类优化器，还需约 56 GB。三者合起来已经约 84 GB，尚未计入激活值、临时缓冲、可能存在的 FP32 master weights 和框架开销。

注意：这是帮助理解量级的示例，而不是任何模型在任意框架中的精确显存需求。实际是否保留 FP32 master weights、梯度以何种 dtype 存储、是否使用 8-bit optimizer、参数是否共享等都会改变结果。

普通 DDP 的特点是每张卡保存一份完整模型与相应训练状态，所以增加 GPU 数量并不会按 GPU 数均摊上述主要状态。要“真正把模型状态拆开”，就要进入 ZeRO / FSDP 一类分片数据并行技术。

### **4.2 ZeRO-1、ZeRO-2、ZeRO-3 到底分别拆什么？**

![](https://pic2.zhimg.com/v2-eeca5cba53e7e88fd6bbe4213aff6f6d_r.jpg)
*图4  训练状态在 DDP、ZeRO 分阶段与 FSDP2 中的典型存储方式*

DeepSpeed ZeRO 的逻辑很容易记：Stage 1 先拆优化器状态；Stage 2 在此基础上再拆梯度；Stage 3 连模型参数也一起拆。拆分后每张 GPU 不必永久保留完整训练状态，但执行算子时仍可能需要把正在计算的参数重新收集起来，计算结束后再释放或重新分片。

ZeRO-3 不是“参数永远只有四分之一而且完全不需要交换”。真正的成本转移是：减少单卡常驻存储，增加按需 AllGather/ReduceScatter 以及相关调度、缓冲和网络带宽的要求。

### **4.3 FSDP2 为什么要按 Transformer 层来包装？**

PyTorch FSDP2 提供 fully_shard 接口，通常通过 DTensor 表示按维度切分后的参数。它可以在某个模块前向或反向计算之前，用 AllGather 临时恢复所需参数，并在反向计算后使用 ReduceScatter 归约与分散梯度。一般对 Transformer Block 逐层做细粒度包装，再对外层模型包装，更容易在不同模块之间形成计算与通信的流水重叠。

如果只对整个模型最外层调用一次 fully_shard，可能把所有参数聚成一个很大的通信组，发生大块 AllGather → 全模型计算 → 大块 ReduceScatter，失去分层预取和重叠的优势。这也是“用了 FSDP 就一定最快”不成立的原因。

工程提示｜FSDP2 与 ZeRO-3 的共同点是面向分片训练状态；但它们的 API、内部调度、通信分组、Checkpoint 与生态集成并不完全相同。不要仅凭一张“都分片”示意图将二者当成完全等价的实现。

*图5  定位数据加载、计算、通信和显存四类瓶颈的工程排查路径*

### **5.1 梯度累积：增加全局 Batch，不等于自动降低通信量**

梯度累积指连续执行 K 次 micro-batch 的前向与反向，将梯度累计起来后只进行一次 optimizer.step()。这能在每卡显存有限时模拟更大的全局 Batch。但在普通 DDP 中，如果每次 backward 都触发梯度同步，那么只是少做了优化器更新，并不会自动少做 AllReduce。

真正减少同步次数，需要在中间 micro-step 使用 DDP.no_sync()，并让最后一次 micro-step 正常完成同步。关键是将 forward 和 backward 都放在 no_sync 上下文中，同时按照累积步数适当缩放 loss。

from contextlib import nullcontext<br><br>optimizer.zero_grad(set_to_none=True)<br>for micro_step, (x, y) in enumerate(loader):<br> sync_now = (micro_step + 1) % accum_steps == 0<br> cm = nullcontext() if sync_now else ddp_model.no_sync()<br> with cm: # forward + backward 都包含在内<br> logits = ddp_model(x)<br> loss = criterion(logits, y) / accum_steps<br> loss.backward()<br> if sync_now:<br> optimizer.step()<br> optimizer.zero_grad(set_to_none=True)

上面的片段用于解释机制；当 epoch 末尾不足 K 次、不同 rank 的数据步数不一致或采用不均等样本权重时，还应额外处理尾批缩放与同步语义。文末提供的完整演示通过固定数据集长度和 drop_last 保证每一轮更新步完整。

### **5.2 混合精度、Bucket、梯度检查点应该怎么选？**

· BF16：常用于支持 BF16 的硬件，可降低部分计算与激活开销并改善训练性能；并不能笼统理解成“所有优化器状态都减半”。

· 通信重叠：先观察 NCCL 和反向计算是否已重叠，再决定是否调整 Bucket 大小、通信分组或调度。

· Activation Checkpointing：保留更少激活，中途重算一部分前向；节省激活显存，但增加计算量。

· 数据管线：num_workers、pin_memory、异步 Host-to-Device 传输、存储与缓存往往会显著影响端到端吞吐。

· 拓扑：同机 NVLink 与跨机网络带宽/时延不同，跨机变慢不能只归咎于 DDP 框架。

优化顺序最好是先测量，再动参数。记录 tokens/s、每步用时、GPU peak memory、通信耗时和数据读取耗时，保持相同硬件、序列长度、数值精度和 Batch 语义做前后比较。否则看似“多卡提速”可能只是换了更大的全局 Batch 或更短的序列。

## **七、实际项目中的常见故障与排查**

| 现象 | 优先怀疑 | 可操作的检查 |
| --- | --- | --- |
| 训练卡住不动 | collective 调用次序不一致或进程掉队 | 检查各 rank 步数、分支逻辑、NCCL 日志 |
| 多卡不比单卡快 | 负载小、通信重、数据读取慢 | Profiler 拆分数据/计算/通信时间 |
| 显存仍然爆掉 | DDP 完整复制状态、激活值过大 | 减少 micro-batch；评估 FSDP/ZeRO |
| 不同卡 loss 不同 | 不同数据导致本地 loss 不同 | 这是常见现象；需核对全局指标归约 |
| 训练不收敛 | 全局 Batch 或学习率改变 | 核对 loss 缩放、优化器与种子、数据切分 |
| 保存后无法恢复 | 仅保存了部分分片状态 | 按分布式框架规范保存/恢复 checkpoint |

对偶发挂起问题，建议先设定可控小数据集，用最少 GPU 复现；然后打印每个 rank 的 epoch、step、输入形状和通信前后标记。收集通信日志是定位方式之一，但日志不会自动保证 collective 顺序正确。

## **八、面试时最容易追问的五个问题**

## **问题1：DDP 为什么通常比 PyTorch DataParallel 更推荐？**

标准回答：PyTorch 的 DataParallel 在单进程中拆分输入、复制模型并收集输出，容易引入主设备负载与 Python 线程开销。DDP 通常使用每 GPU 一进程，通过高效集体通信同步梯度，并可以将通信和反向传播重叠，因此在多 GPU 训练中常是更合适的基线。

## **问题2：梯度没有全部算完，AllReduce 怎么能开始？**

标准回答：DDP 的 Reducer 按 Bucket 管理梯度。反向传播的 Autograd Hook 在梯度就绪后标记相应 Bucket；当一个 Bucket 的梯度都准备好，就能立即发起该 Bucket 的 AllReduce，与剩余反向计算重叠。

## **问题3：为什么普通 DDP 不能让超大模型跨卡分摊显存？**

标准回答：DDP 主要并行处理数据，各 rank 一般保存完整参数及其训练状态，显存并不会随数据并行度按比例下降。要降低单卡训练状态显存，需要用 ZeRO 或 FSDP 等状态分片技术；必要时再叠加 TP、PP。

## **问题4：使用梯度累积以后，通信量一定降低吗？**

标准回答：不一定。梯度累积只是延迟优化器更新，如果每次 backward 仍做 AllReduce，就不能自动降低同步频率。通常要在非最后一次 micro-step 使用 no_sync，并正确处理 loss 归一化与最后一次同步。

## **问题5：FSDP 为什么可能比 DDP 慢？**

标准回答：FSDP 通过模型状态分片节省显存，但需要 AllGather 参数与 ReduceScatter 梯度；如果模型较小、通信带宽有限或分层包装不合理，这些额外通信和调度成本可能超过收益。选型应同时考虑模型是否放得下、实际吞吐与训练稳定性。

## **结语：理解数据并行，记住三个“不是”**

第一，数据并行不是模型并行。前者主要拆数据；普通 DDP 不负责把参数永久分到不同 GPU。第二，AllReduce 的非阻塞执行不是异步参数更新；典型 DDP 更新仍建立在一致的梯度同步之上。第三，FSDP 与 ZeRO 不是“免费显存”：它们是拿更多通信和调度复杂度换取更低的常驻训练状态显存。

因此实际工程选型可按三个问题推进：单卡能否容纳模型与训练状态？如果能，先建立 DDP 基线并优化数据管线和通信重叠；如果不能，评估 ZeRO/FSDP，并测量额外通信成本；如果模型层本身仍难以计算，再考虑与张量并行、流水线并行组合。这样，分布式训练就不再是一串缩写，而是一套可以验证的工程决策。
