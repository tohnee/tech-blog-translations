部署过 LLM 或核算过推理服务成本的人，往往会遇到 GPU 显存带宽与容量的限制，计算能力（FLOPS）也会影响服务性能。

![](https://pic4.zhimg.com/v2-417b1db11e95f8c1697b9b8e1fe3c291_r.jpg)

主要的显存占用来自键值缓存（Key-Value Cache，KV Cache）。vLLM 借鉴传统操作系统的分页机制，设计了 PagedAttention，用于改善 LLM 推理服务的内存管理。

LLM 以自回归方式生成文本，一次生成一个词。生成下一个词时，模型需要参考此前的所有词，计算注意力应该落在哪些位置。为避免反复计算历史 Token 的键（Key，K）和值（Value，V）投影向量，推理引擎将这些向量保存在 GPU 显存中，形成 KV Cache。

FasterTransformer、Orca 等传统服务框架要求张量占用连续内存（Contiguous Memory）。请求刚开始时，系统就要按照最大可能序列长度预留一整块连续的 GPU DRAM；假设最大长度是 2048 个 Token，就需要提前分配对应空间，但是实际输出长度却未必能达到这个上限。

显存浪费主要有 3 种情况：

1. 过量预留（Over-provisioning，Reservation Waste）：即使最终只生成 50 个 Token，也可能先为 2,048 个 Token 预留空间。
2. 内部碎片（Internal Fragmentation）：模型输出序列结束标记（`<eos>`）时，已经分配的部分 Token 槽位仍未使用。
3. 外部碎片（External Fragmentation）：GPU 上还有空闲显存，但空间零散，单个区域太小或彼此不连续，无法放入新请求。

传统服务系统的可用 KV Cache 显存最多可能浪费 60% 至 80%。

## PagedAttention

PagedAttention 沿用了传统计算机内存管理中的分页思路。一个序列的 KV Cache 被划分成多个 KV 块（KV Blocks），每块存储固定数量 Token 的键和值，块大小记为 B，比如说最优默认值是 16。

KV 块对应的物理块（Physical Blocks）可以分散存放在 GPU 显存中。vLLM 维护一张块表（Block Table），记录连续逻辑块（Logical Blocks）到物理块的映射。模型按逻辑块顺序访问缓存，底层物理地址可以不连续。

下面的 3 个场景分别涉及单序列生成、并行采样和束搜索。

### 场景 1：单序列生成（自回归循环）

![](https://pic3.zhimg.com/v2-9320c3f7ee4c9e86f8406e6fe21193fa_r.jpg)

```text
 [Logical Block L0]  ---> Block Table (L0 -> P7) ---> [Physical Block P7 in DRAM]  
 [Logical Block L1]  ---> Block Table (L1 -> P3) ---> [Physical Block P3 in DRAM]
```

收到 Prompt 后，vLLM 执行预填充阶段（Prefill Phase）。假设输入是“Four score and seven years”，共 5 个 Token，块大小 B=4。显存中的分配和写入顺序如下：

1. vLLM 创建逻辑块 L0，放入“Four”“score”“and”“seven”，并将其映射到随机选取的物理地址，例如物理块 P7。
2. 剩余的“years”进入逻辑块 L1。L1 对应物理块 P3，此时只占用了 1/4 的槽位。
3. 解码生成“ago”后，vLLM 直接把新 Token 写进 L1 / P3 的下一个空槽位，占用变为 2/4。
4. 等 L1 填至 4/4，vLLM 再申请新的物理块，例如 P11，将它映射给逻辑块 L2，后续 Token 继续写入其中。

物理块按需申请后，剩余的空槽位集中在最后一个尚未填满的块内。原文给出的显存浪费比例由约 70% 降至 4% 以下。

### 场景 2：并行采样与写时复制（Copy-on-Write，CoW）

![](https://pic4.zhimg.com/v2-ede8c84d18cbc19e749455986257cc2f_r.jpg)

同一个 Prompt 也可能生成多份结果，例如编程助手针对一次输入给出 3 份代码补全。各份结果的输入完全一致，传统实现却需要在多个连续内存块中分别保存 Prompt 的 KV Cache。

PagedAttention 让不同分支共享尚未分叉的缓存块：

1. 两条输出分支将 Prompt 对应的逻辑块 L0、L1 映射到相同的物理块 P7、P3。
2. 共享物理块的引用计数（Reference Count）为 2。
3. 分支 A 和分支 B 开始生成不同 Token 时，vLLM 在块级别触发写时复制（CoW）25：<br>

- 把共享块的数据复制到新申请的物理块，例如从 P3 复制到 P12。
- 原始 P3 的引用计数减 1。
- 两条分支随后各自向独占的物理块写入不同的后续 Token。

采用这种共享方式，并行生成期间最多可共享 30% 的 KV 显存。

### 场景 3：束搜索（Beam Search）、剪枝

![](https://picx.zhimg.com/v2-a5be44f732a0a6d93b68438ad6dce0f9_r.jpg)

束搜索会保留多个候选句子（beam），并在每轮解码后比较它们的概率。概率较高的路径继续参与搜索，其他路径则被剪枝。候选路径会不断变化，标准实现需要频繁复制大量内存，才能同步新选中 beam 的 KV Cache。

PagedAttention 的块管理方式类似动态进程树：

1. 历史 Token 相同的 beam，把各自逻辑块映射到相同的物理块。
2. 某条候选路径被剪枝后，对应逻辑块销毁，相关物理块的引用计数减 1。
3. 物理块的引用计数降至 0 时，系统立即回收该块，并将空间归还空闲 GPU DRAM 池。
4. 路径分叉时，只复制一个块。

对于束搜索负载，原文给出的显存节省幅度为 37% 至 55%。

## 总结

显存碎片减少后，服务器可以把更多请求放进同一批次处理。在相同硬件上，vLLM 的有效批大小（Effective Batch Size，即同时处理的请求数）最多可以提高 4x，整体推理服务吞吐量由此提升 2–4×。

本文的作者还制作了一个可交互的仪表盘模拟器，涵盖单序列生成、并行采样和束搜索。模拟器支持逐步执行，可以实时观察块表的更新以及写时复制发生的过程。
