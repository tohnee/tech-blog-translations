### 延迟组成：模型只是冰山一角

一次完整的风控推理请求中，时间花在哪里？

模型推理本身通常只占总延迟的15-25%。真正的优化杠杆在于：

1. **特征获取**：从Redis/数据库拉取用户画像
2. **特征计算**：基于原始数据计算衍生特征
3. **数据转换**：类型转换、缺失值处理、WOE编码

因此优化顺序应该是：特征计算 > 模型推理 > 数据序列化。

### 第一部分：特征计算向量化——50倍提速的起点

### 1. Python循环是性能杀手

风控特征计算中常见的反模式：

```text
# 反模式：逐行Python循环
def compute_features_slow(df):
    results = []
    for idx, row in df.iterrows():
        # WOE编码
        age_woe = woe_lookup(row['age'], age_bins)
        # 特征交叉
        cross = row['income'] / max(row['debt'], 1)
        # 条件判断
        flag = 1 if row['overdue_days'] > 30 else 0
        results.append([age_woe, cross, flag])
    return pd.DataFrame(results)
```

这段代码在100K样本上要跑4-5秒。原因：

- Python解释器逐行执行，每次循环都有巨大的overhead
- 每次 `row['age']` 都是一次字典查找
- 无法利用CPU的SIMD指令和缓存

### 2. NumPy向量化：让CPU做它擅长的事

同样的逻辑，向量化后：

```text
import numpy as np

def compute_features_fast(df):
    # WOE编码：用np.digitize + 向量查表
    age_bins_edges = np.array([18, 25, 35, 45, 55, 65])
    age_woe_values = np.array([0.3, -0.1, -0.4, -0.2, 0.1, 0.5])
    bin_idx = np.digitize(df['age'].values, age_bins_edges)
    age_woe = age_woe_values[np.clip(bin_idx, 0, len(age_woe_values)-1)]
    
    # 特征交叉：向量除法
    cross = df['income'].values / np.maximum(df['debt'].values, 1)
    
    # 条件判断：布尔索引
    flag = (df['overdue_days'].values > 30).astype(np.int8)
    
    return np.column_stack([age_woe, cross, flag])
```

性能差异的根本原因：

$$ \text{Loop: } T = N \times (t_{\text{interpret}} + t_{\text{compute}}) \approx N \times t_{\text{interpret}} $$

$$ \text{Vectorized: } T = t_{\text{setup}} + t_{\text{compute\_batch}} \approx \frac{N \times t_{\text{compute}}}{k_{\text{SIMD}}} $$

其中 $k_{\text{SIMD}}$ 是SIMD并行度（AVX2可以同时处理8个float32），$t_{\text{interpret}} \gg t_{\text{compute}}$。

### 3. WOE编码的极速实现

WOE编码是风控推理中最频繁的操作。三种实现方式的性能对比：

```text
import numpy as np
from collections import OrderedDict

# 方式1：字典循环（最慢）
def woe_encode_loop(values, bin_edges, woe_values):
    result = []
    for v in values:
        for i in range(len(bin_edges) - 1):
            if bin_edges[i] <= v < bin_edges[i+1]:
                result.append(woe_values[i])
                break
    return result

# 方式2：Pandas cut（中等）
def woe_encode_pandas(series, bin_edges, woe_values):
    bins = pd.cut(series, bins=bin_edges, labels=False, include_lowest=True)
    return bins.map(dict(enumerate(woe_values)))

# 方式3：NumPy digitize（最快）
def woe_encode_numpy(values, bin_edges, woe_values):
    """
    values: np.ndarray
    bin_edges: 分箱边界（不含-inf和inf）
    woe_values: 每个bin的WOE值
    """
    bin_idx = np.searchsorted(bin_edges, values, side='right')
    woe_array = np.array(woe_values)
    return woe_array[np.clip(bin_idx, 0, len(woe_array) - 1)]
```

100万样本benchmark：

| 方法 | 耗时 | 相对速度 |
| --- | --- | --- |
| 字典循环 | 3200ms | 1× |
| Pandas cut | 85ms | 38× |
| NumPy searchsorted | 8ms | 400× |

### 4. 完整特征Pipeline向量化

```text
class VectorizedFeatureEngine:
    """向量化特征计算引擎——纯NumPy实现"""
    
    def __init__(self, woe_configs, feature_specs):
        """
        woe_configs: {feature_name: (bin_edges, woe_values)}
        feature_specs: 特征计算规则列表
        """
        # 预编译WOE查找表为连续数组
        self.woe_edges = {}
        self.woe_values = {}
        for name, (edges, values) in woe_configs.items():
            self.woe_edges[name] = np.asarray(edges, dtype=np.float64)
            self.woe_values[name] = np.asarray(values, dtype=np.float64)
        
        self.feature_specs = feature_specs
    
    def transform(self, raw_data: dict) -> np.ndarray:
        """
        raw_data: {feature_name: np.ndarray} 原始特征值
        returns: (n_samples, n_output_features) 的二维数组
        """
        outputs = []
        
        for spec in self.feature_specs:
            if spec['type'] == 'woe':
                col = raw_data[spec['source']]
                edges = self.woe_edges[spec['source']]
                values = self.woe_values[spec['source']]
                encoded = values[np.clip(
                    np.searchsorted(edges, col, side='right'),
                    0, len(values) - 1
                )]
                outputs.append(encoded)
                
            elif spec['type'] == 'ratio':
                num = raw_data[spec['numerator']]
                den = np.maximum(raw_data[spec['denominator']], spec.get('min_den', 1e-6))
                outputs.append(num / den)
                
            elif spec['type'] == 'clip':
                col = raw_data[spec['source']]
                outputs.append(np.clip(col, spec['min'], spec['max']))
                
            elif spec['type'] == 'indicator':
                col = raw_data[spec['source']]
                outputs.append((col > spec['threshold']).astype(np.float32))
        
        return np.column_stack(outputs)
```

### 第二部分：ONNX Runtime——让模型推理快10倍

### 1. 为什么原生Python推理慢

用 `model.predict(X)` 调用LightGBM推理时，执行路径是：

```text
Python → Pandas/NumPy转换 → ctypes调用C库 → 遍历所有树 → 收集结果 → 转回Python对象
```

Python↔C的边界切换、GIL锁、数据拷贝等都是开销。对于单条数据推理尤其严重（batch=1时）。

### 2. ONNX转换与推理

ONNX（Open Neural Network Exchange）将模型编译为优化的计算图，消除了Python overhead：

```text
import onnxmltools
from onnxmltools.convert.lightgbm.convert import convert as convert_lgb
from onnxconverter_common import FloatTensorType
import onnxruntime as ort
import numpy as np

# Step 1: 转换LightGBM模型为ONNX
def convert_to_onnx(lgb_model, n_features, output_path='model.onnx'):
    initial_type = [('input', FloatTensorType([None, n_features]))]
    onnx_model = convert_lgb(
        lgb_model, 
        initial_types=initial_type,
        target_opset=11
    )
    onnxmltools.utils.save_model(onnx_model, output_path)
    return output_path

# Step 2: 创建优化的推理Session
def create_session(model_path, n_threads=4):
    sess_options = ort.SessionOptions()
    sess_options.intra_op_num_threads = n_threads
    sess_options.inter_op_num_threads = 1
    sess_options.graph_optimization_level = ort.GraphOptimizationLevel.ORT_ENABLE_ALL
    
    # 关闭内存模式优化（减少内存分配）
    sess_options.enable_mem_pattern = False
    sess_options.enable_cpu_mem_arena = True
    
    session = ort.InferenceSession(model_path, sess_options,
                                    providers=['CPUExecutionProvider'])
    return session

# Step 3: 推理
def predict_onnx(session, X):
    """ONNX推理——支持单条和批量"""
    if X.ndim == 1:
        X = X.reshape(1, -1)
    X = X.astype(np.float32)
    
    input_name = session.get_inputs()[0].name
    output_name = session.get_outputs()[1].name  # probabilities
    
    result = session.run([output_name], {input_name: X})[0]
    return result[:, 1]  # P(positive class)
```

### 3. ONNX的优化原理

ONNX Runtime对树模型做了几个关键优化：

**（1）树遍历并行化**

原生LightGBM按tree逐个遍历。ONNX可以同时遍历多棵树（利用CPU流水线）：

$$ T_{\text{native}} = N_{\text{trees}} \times t_{\text{per\_tree}} $$

$$ T_{\text{ONNX}} \approx \frac{N_{\text{trees}}}{k_{\text{pipeline}}} \times t_{\text{per\_tree}} $$

**（2）数据布局优化**

将树结构从”对象指针”重排为连续内存数组，提高CPU缓存命中率。

**（3）批量推理向量化**

多条数据同时在同一棵树上遍历，利用SIMD指令并行比较阈值。

*图3: ONNX Runtime在单样本延迟上比Python原生快6-10倍，批量吞吐量差距更大（log坐标）*

### 4. Treelite：将树模型编译为C代码

比ONNX更极端的方案——将模型直接编译为本地机器码：

```text
import treelite
import treelite_runtime

# 将LightGBM模型编译为共享库
model = treelite.Model.from_lightgbm_model(lgb_model)
model.export_lib(
    toolchain='gcc',
    libpath='./model.so',
    params={'parallel_comp': 4},  # 编译时的并行度
    verbose=True
)

# 运行时加载编译后的模型
predictor = treelite_runtime.Predictor('./model.so', verbose=False)

# 推理
def predict_treelite(predictor, X):
    batch = treelite_runtime.DMatrix(X)
    return predictor.predict(batch)
```

Treelite生成的C代码本质上就是一堆嵌套的if-else语句，经过gcc -O3优化后：

- 零Python overhead
- 完全内联，无函数调用开销
- 编译器自动做分支预测优化

代价是：编译时间较长（大模型需要几分钟），且每次模型更新都需要重新编译。

### 第三部分：多核并行推理

### 1. 两种并行策略

![](https://pic1.zhimg.com/v2-ae2c6a093bcad548b3aa981f9a883400_r.jpg)
*图4: 请求级并行（多worker处理多请求，适合在线服务）vs 批量级并行（单批数据多线程处理，适合离线评分）*

**请求级并行**：启动N个worker进程，每个worker独立处理一个请求。适合在线服务。

**批量级并行**：将一个大batch拆分为子batch，多线程同时推理。适合离线评分。

### 2. 请求级并行：Gunicorn + 多Worker

```text
# gunicorn.conf.py
import multiprocessing

workers = multiprocessing.cpu_count()  # 每核一个worker
worker_class = 'sync'  # 同步worker，每个请求独占一个进程
timeout = 30
bind = '0.0.0.0:8000'
preload_app = True  # 预加载模型，共享内存
```

关键点：`preload_app=True` 让模型在master进程中加载一次，通过fork共享给所有worker——避免每个worker各加载一份模型（节省内存）。

### 3. 批量级并行：ThreadPool + NumPy

```text
from concurrent.futures import ThreadPoolExecutor
import numpy as np

class ParallelPredictor:
    """多线程批量推理"""
    
    def __init__(self, onnx_session, n_threads=4):
        self.session = onnx_session
        self.n_threads = n_threads
        self.pool = ThreadPoolExecutor(max_workers=n_threads)
    
    def predict_batch(self, X: np.ndarray) -> np.ndarray:
        """将大batch拆分，多线程并行推理"""
        n_samples = len(X)
        
        if n_samples < self.n_threads * 100:
            # 数据量太小，不值得并行
            return self._predict_chunk(X)
        
        # 拆分为子batch
        chunks = np.array_split(X, self.n_threads)
        
        # 并行推理
        futures = [self.pool.submit(self._predict_chunk, chunk) for chunk in chunks]
        results = [f.result() for f in futures]
        
        return np.concatenate(results)
    
    def _predict_chunk(self, X_chunk):
        X_chunk = X_chunk.astype(np.float32)
        input_name = self.session.get_inputs()[0].name
        output_name = self.session.get_outputs()[1].name
        result = self.session.run([output_name], {input_name: X_chunk})[0]
        return result[:, 1]
```

注意：ONNX Runtime本身已经在单次推理时利用多线程（`intra_op_num_threads`），因此批量级并行时需要控制总线程数不超过CPU核数，避免过度竞争：

$$ \text{intra\_threads} \times \text{parallel\_workers} \leq N_{\text{CPU cores}} $$

### 4. GIL的影响和规避

Python的GIL（全局解释器锁）不会影响NumPy/ONNX的性能——因为它们在执行C扩展代码时会释放GIL。但以下操作会受GIL限制：

| 操作 | 是否释放GIL | 适合多线程 |
| --- | --- | --- |
| NumPy数组运算 | 是 | 是 |
| ONNX Runtime推理 | 是 | 是 |
| Pandas DataFrame操作 | 部分 | 谨慎使用 |
| 纯Python字典/列表操作 | 否 | 不适合 |
| 自定义Python函数 | 否 | 用多进程替代 |

### 第四部分：端到端优化实战

### 1. 从12.5ms到1.4ms的完整方案

将所有优化组合起来，一个真实的风控推理服务优化案例：

```text
"""
风控模型推理服务 - 极致优化版
目标：单请求P99 < 2ms，吞吐 > 50K QPS
"""
import numpy as np
import onnxruntime as ort
from functools import lru_cache
import redis
import msgpack

class OptimizedRiskEngine:
    """极致优化的风控推理引擎"""
    
    def __init__(self, model_path, woe_config, redis_pool):
        # ONNX Session（预热）
        self.session = self._create_session(model_path)
        
        # WOE查找表：预编译为连续数组
        self.woe_edges = {}
        self.woe_values = {}
        for feat, (edges, values) in woe_config.items():
            self.woe_edges[feat] = np.ascontiguousarray(edges, dtype=np.float64)
            self.woe_values[feat] = np.ascontiguousarray(values, dtype=np.float64)
        
        # Redis连接池
        self.redis = redis_pool
        
        # 预分配输出buffer（避免反复内存分配）
        self._buffer = np.zeros((1, len(woe_config)), dtype=np.float32)
    
    def predict_single(self, user_id: str) -> float:
        """单条推理：完整链路 < 2ms"""
        
        # Step 1: 获取特征（Redis pipeline减少RTT）
        raw_features = self._fetch_features(user_id)
        
        # Step 2: WOE编码（向量化查表）
        encoded = self._encode_features(raw_features)
        
        # Step 3: 模型推理（ONNX）
        prob = self._infer(encoded)
        
        return float(prob)
    
    def _fetch_features(self, user_id):
        """Redis pipeline一次拿所有特征"""
        key = f"user_features:{user_id}"
        raw = self.redis.get(key)
        if raw is None:
            return self._get_default_features()
        return msgpack.unpackb(raw, raw=False)
    
    def _encode_features(self, raw_features):
        """纯NumPy向量化WOE编码"""
        buf = self._buffer[0]  # 复用预分配buffer
        for i, (feat_name, value) in enumerate(raw_features.items()):
            edges = self.woe_edges[feat_name]
            values = self.woe_values[feat_name]
            idx = np.searchsorted(edges, value, side='right')
            buf[i] = values[min(idx, len(values) - 1)]
        return self._buffer
    
    def _infer(self, X):
        """ONNX推理"""
        input_name = self.session.get_inputs()[0].name
        result = self.session.run(None, {input_name: X})[0]
        return result[0][1]  # P(bad)
    
    def _create_session(self, model_path):
        opts = ort.SessionOptions()
        opts.intra_op_num_threads = 1  # 单请求单线程
        opts.graph_optimization_level = ort.GraphOptimizationLevel.ORT_ENABLE_ALL
        opts.enable_mem_pattern = True
        return ort.InferenceSession(model_path, opts,
                                     providers=['CPUExecutionProvider'])
    
    def _get_default_features(self):
        """特征缺失时的默认值"""
        return {name: 0.0 for name in self.woe_edges}
```

### 2. 批量评分优化：1亿样本30分钟内完成

```text
class BatchScorer:
    """亿级样本批量评分"""
    
    def __init__(self, model_path, n_threads=8, batch_size=10000):
        self.batch_size = batch_size
        self.n_threads = n_threads
        
        # 多线程ONNX session
        opts = ort.SessionOptions()
        opts.intra_op_num_threads = n_threads
        opts.graph_optimization_level = ort.GraphOptimizationLevel.ORT_ENABLE_ALL
        self.session = ort.InferenceSession(model_path, opts,
                                             providers=['CPUExecutionProvider'])
    
    def score_file(self, input_path, output_path):
        """流式读取 → 批量推理 → 流式写出"""
        import pyarrow.parquet as pq
        
        parquet_file = pq.ParquetFile(input_path)
        results = []
        total = 0
        
        for batch in parquet_file.iter_batches(batch_size=self.batch_size):
            df = batch.to_pandas()
            X = df.values.astype(np.float32)
            
            # 批量ONNX推理
            input_name = self.session.get_inputs()[0].name
            output = self.session.run(None, {input_name: X})[0]
            scores = output[:, 1]
            
            results.append(scores)
            total += len(scores)
            
            if total % 1_000_000 == 0:
                print(f"  Scored {total:,} samples...")
        
        # 写出结果
        all_scores = np.concatenate(results)
        np.save(output_path, all_scores)
        print(f"Done: {total:,} samples scored")
        
        return all_scores
```

吞吐量估算：

$$ \text{Throughput} = \frac{\text{batch\_size} \times n_{\text{threads}}}{\text{latency\_per\_batch}} $$

ONNX Runtime + 8线程 + batch_size=10000:

- 每batch耗时 ≈ 100ms
- 吞吐量 ≈ 100K samples/sec
- 1亿样本 ≈ 1000秒 ≈ 17分钟

### 1. 正确的Benchmark姿势

```text
import time
import numpy as np
from statistics import mean, stdev

def benchmark_inference(predict_fn, X_test, n_warmup=100, n_runs=1000):
    """
    标准推理性能Benchmark
    
    注意：
    - 必须预热（前100次不计时）
    - 测量单条推理和批量推理
    - 报告P50/P95/P99，而非平均值
    """
    # 预热（JIT编译、缓存预热等）
    for _ in range(n_warmup):
        predict_fn(X_test[:1])
    
    # 单条推理延迟
    single_latencies = []
    for i in range(n_runs):
        x = X_test[i % len(X_test)].reshape(1, -1)
        t0 = time.perf_counter_ns()
        predict_fn(x)
        t1 = time.perf_counter_ns()
        single_latencies.append((t1 - t0) / 1e6)  # ms
    
    # 批量推理吞吐
    batch_sizes = [1, 8, 32, 128, 512, 1024]
    throughputs = {}
    for bs in batch_sizes:
        X_batch = X_test[:bs].astype(np.float32)
        t0 = time.perf_counter()
        for _ in range(100):
            predict_fn(X_batch)
        elapsed = time.perf_counter() - t0
        throughputs[bs] = int(bs * 100 / elapsed)
    
    # 报告
    latencies = sorted(single_latencies)
    print(f"=== Single-Sample Latency (ms) ===")
    print(f"  P50: {latencies[int(n_runs*0.5)]:.3f}")
    print(f"  P95: {latencies[int(n_runs*0.95)]:.3f}")
    print(f"  P99: {latencies[int(n_runs*0.99)]:.3f}")
    print(f"  Max: {latencies[-1]:.3f}")
    print(f"\n=== Batch Throughput (samples/sec) ===")
    for bs, tp in throughputs.items():
        print(f"  batch={bs:4d}: {tp:>8,}")
    
    return latencies, throughputs
```

### 2. 避免常见的Benchmark陷阱

| 陷阱 | 问题 | 正确做法 |
| --- | --- | --- |
| 不预热 | 首次推理包含JIT/缓存加载 | 至少100次warm-up |
| 用time.time() | 精度只有ms级 | 用time.perf_counter_ns() |
| 只测平均值 | 掩盖了长尾延迟 | 报告P50/P95/P99 |
| 固定输入 | CPU分支预测作弊 | 随机打乱输入数据 |
| 忽略GC | Python GC暂停导致spike | 测试前gc.disable() |

import time
from collections import deque

class LatencyTracker:
    """滑动窗口延迟监控"""
    
    def __init__(self, window_size=10000):
        self.window = deque(maxlen=window_size)
    
    def record(self, latency_ms):
        self.window.append(latency_ms)
    
    def report(self):
        if not self.window:
            return {}
        arr = sorted(self.window)
        n = len(arr)
        return {
            'p50': arr[int(n * 0.50)],
            'p95': arr[int(n * 0.95)],
            'p99': arr[int(n * 0.99)],
            'max': arr[-1],
            'count': n,
        }

### 第六部分：优化方案选型决策

不同场景选不同方案：

| 场景 | 推荐方案 | 预期延迟 | 复杂度 |
| --- | --- | --- | --- |
| Python服务 + 低QPS | 原生LightGBM | 3-5ms | 低 |
| Python服务 + 中QPS | ONNX Runtime | 0.5-1ms | 中 |
| 极致延迟要求 | Treelite编译 | 0.1-0.5ms | 高 |
| Java/Go服务 | ONNX/PMML | 0.3-1ms | 中 |
| 批量评分 | ONNX + 多线程 | N/A (高吞吐) | 中 |
| 评分卡部署 | 纯数值计算（无模型） | < 0.1ms | 低 |

核心原则：**先向量化特征计算，再优化模型推理。** 因为前者的ROI几乎总是更高。

### 总结

### 核心要点

1. **80%的延迟在特征，不在模型**：优化推理不要只盯着model.predict()，先把特征获取和计算优化好。NumPy向量化比Python循环快50-140倍，这是最简单有效的第一步。
2. **ONNX Runtime是性价比最高的模型加速方案**：零代码改动（只需转换格式），单样本推理快6-10倍，批量推理快20-40倍。
3. **批量推理要用对batch_size**：太小无法利用SIMD，太大浪费内存。通常128-1024是最优区间。
4. **并行策略因场景而异**：在线服务用请求级并行（多worker），离线评分用批量级并行（多线程）。不要两者混用导致线程竞争。
5. **正确的Benchmark比优化本身更重要**：没有准确的测量就没有有效的优化。P99比平均值更能反映真实用户体验。

### 思考题

1. **ONNX vs Treelite**：如果你的模型每周更新一次，且部署在100+台机器上，选ONNX还是Treelite？如果模型每天更新呢？
2. **特征缓存的失效策略**：在推理服务中缓存了用户的实时特征（如”最近1小时交易次数”）。这个缓存应该设多长TTL？设太短会增加Redis查询，设太长特征就不”实时”了。
3. **长尾延迟优化**：P50=1ms但P99=15ms，大多数请求很快但偶尔有spike。可能的原因有哪些？如何排查和优化？
4. **模型更新零停机**：当新模型需要上线时，如何做到推理服务不中断、不降级？设计一个热加载方案。
5. **多模型串联**：一个请求需要过反欺诈模型→信用评分模型→额度模型三个模型。串行执行总延迟是三个模型之和。有什么方法可以降低总延迟？
