> 目标：在延迟、吞吐、成本、质量四目标之间取得可运营的平衡。 本层的核心矛盾：decode 阶段的物理特性决定了优化路径与训练完全不同。

### 1. 推理层的四个目标

四个目标互相冲突。优化必须显式声明优先哪个。

| 目标 | 指标 | 主要手段 |
| --- | --- | --- |
| 延迟 | TTFT、TPOT、端到端延迟 | 连续批处理、KV 优化、前缀缓存 |
| 吞吐 | QPS、TPS、tokens/s | 批处理大小、并行策略、量化 |
| 成本 | 每百万 token 成本、单位 GPU 产出 | 量化、弹性、缓存 |
| 质量 | 任务完成率、答案正确率 | 不降精度的优化手段优先 |

### 2. 推理的两段结构

![](https://pic4.zhimg.com/v2-b09da84940d6b0d136bbdd9219573617_r.jpg)
*推理两段：Prefill 与 Decode*

### 2.1 两段的物理性质对比

| 维度 | Prefill | Decode |
| --- | --- | --- |
| 处理的 token | 完整 prompt | 每次 1 个 |
| 并行度 | token 维可并行，大矩阵乘 | 并行度为 1，矩阵向量乘 |
| 瓶颈 | compute-bound，算力墙 | memory-bound，带宽墙 |
| 决定指标 | TTFT | TPOT 与总时长 |
| KV cache 行为 | 写入整段 K 与 V | 每步追加一行，反复读出历史 |
| GPU 表现 | 能打满算力 | 只吃带宽，算力用不满 |

### 2.2 两个延迟定义

首 token 延迟：

$$ TTFT = t_{first\ token} - t_{request\ start} $$

单 token 延迟：

$$ TPOT = t_{n} - t_{n-1} \approx \frac{1}{\text{decode\ speed}} $$

端到端延迟：

$$ E2E = TTFT + \text{output\_len} \times TPOT $$

推论：短输出场景 TTFT 主导。长输出场景 TPOT 主导。优化手段不同。

### 2.3 为什么 Decode 打不满算力

Decode 阶段每步做的矩阵向量乘，其算术强度约等于 1。

Roofline 上限：

$$ P \le \min(P_{peak}, \; B_{mem} \times I) $$

代入典型数值。

| 硬件 | 峰值算力 | HBM 带宽 | 拐点强度 |
| --- | --- | --- | --- |
| A100 BF16 | 312 TFLOPs | 约 2 TB/s | 约 156 |
| H100 BF16 | 约 990 TFLOPs | 约 3.35 TB/s | 约 296 |

Decode 的强度约等于 1，远低于拐点。实际性能受带宽限制。

推论：提升 decode 速度的正确方向是减少每 token 读取的字节数，而不是增加算力。

### 3. KV Cache

![](https://pica.zhimg.com/v2-6d270c0cd5341c5fccf778a9b703fef2_r.jpg)
*KV Cache 账本与引擎核心机制*

### 3.1 KV Cache 的显存账本

每个 token 每个层需要存储 K 和 V 各一份。

$$ \text{KV bytes} = 2 \times L \times H_{kv} \times d_{head} \times S \times \text{bytes} $$

变量含义：$L$ 为层数，$H_{kv}$ 为 KV 头数，$d_{head}$ 为每头维度，$S$ 为序列长度，$\text{bytes}$ 为每元素字节数。

若 KV 头数等于注意力头数，则 $H_{kv} \times d_{head}$ 等于隐藏维度 $H$。

### 3.2 具体计算

以 Llama-2-7B 为例。32 层，32 个 KV 头，$d_{head}$ 为 128，FP16 精度。

| 项 | 计算 | 结果 |
| --- | --- | --- |
| 每层每 token | 2 × 32 × 128 × 2 | 16384 字节 |
| 32 层每 token | 16384 × 32 | 512 KB |
| 序列 2048 | 512 KB × 2048 | 1 GB |
| 序列 4096 | 512 KB × 4096 | 2 GB |
| 序列 8192 | 512 KB × 8192 | 4 GB |

推论：单请求占用 2 GB 时，80 GB 的卡只能放 40 个并发。长上下文场景必须先解决 KV 问题。

### 3.3 四种应对手段

### 3.3.1 少存：缩小 KV 体积

| 手段 | 原理 | 收益 |
| --- | --- | --- |
| GQA 或 MQA | 多查询头共享 KV 头 | KV 头数从 32 降到 8，缩 4 倍 |
| KV cache 量化 | 8-bit 或 4-bit 存储 | 缩 2 到 4 倍 |
| 滑窗注意力 | 只保留最近 W 个 token | 与序列长度无关 |
| 稀疏注意力 | 只保留重要位置 | 视稀疏度而定 |

GQA 的 KV 体积：

$$ \text{KV bytes} = 2 \times L \times \frac{H_{q}}{g} \times d_{head} \times S \times \text{bytes} $$

变量含义：$g$ 为分组数。Llama-2 用 MHA，$g = 32$。Llama-3 70B 用 GQA，$g = 8$。

### 3.3.2 巧存：不浪费空间

**PagedAttention** 把 KV 切成固定大小的块，通过块表间接寻址。

| 维度 | 连续分配 | PagedAttention |
| --- | --- | --- |
| 分配粒度 | 整个序列 | 固定大小块 |
| 碎片浪费 | 可能超过 60% | 通常低于 4% |
| 最大并发 | 受碎片限制 | 接近显存上限 |
| 共享前缀 | 不支持 | 支持 |

**前缀缓存** 用 Radix Tree 组织 KV，公共前缀只存一份。

| 场景 | 前缀缓存收益 |
| --- | --- |
| 多轮对话 | 系统提示加历史对话全部命中 |
| 共享系统提示 | 所有请求共享一次计算 |
| Few-shot | 固定的示例部分全部命中 |
| 相同模板 | 模板部分命中 |

**连续批处理** 在每个调度步动态加入新请求，移除已完成请求。

静态批处理的问题是：批内最长的序列决定整批耗时，其余请求在空转。

### 3.3.3 少算：减少重复

| 手段 | 原理 | 风险 |
| --- | --- | --- |
| 前缀缓存命中 | 跳过该段的 prefill | 需前缀稳定 |
| 投机解码 | 小模型草稿，大模型一次验证多个 | 接受率低时变慢 |
| 推测解码的变体 | Medusa、EAGLE 用多头直接预测 | 需训练额外模块 |

投机解码的期望加速比：

$$ \text{speedup} = \frac{1 - \alpha^{k+1}}{1 - \alpha} $$

变量含义：$\alpha$ 为接受率，$k$ 为草稿长度。

| 接受率 α | k = 4 的加速比 |
| --- | --- |
| 0.9 | 4.1 倍 |
| 0.7 | 2.4 倍 |
| 0.5 | 1.9 倍 |
| 0.3 | 1.3 倍 |

推论：接受率低于 0.3 时投机解码得不偿失。必须实测。

### 3.3.4 隔离：控制资源争抢

| 手段 | 原理 | 适用 |
| --- | --- | --- |
| Prefill 与 Decode 分离 | 用不同卡池承担两段 | 长短请求混用严重时 |
| MIG | 硬件级显存分区 | 多租户强隔离 |
| 多 LoRA | 基座一份，适配器热切换 | 多模型少流量 |

Prefill 与 Decode 分离的代价：KV cache 需要在两池之间传输，依赖高速网络。

### 3.4 KV Cache 的四种浪费

| 浪费类型 | 机制 | 量化 | 对策 |
| --- | --- | --- | --- |
| 内部碎片 | 序列在连续内存中的预留大于实际 | 最高 60% | PagedAttention |
| 外部碎片 | 空闲块不连续，无法满足大块请求 | 5% 到 15% | PagedAttention |
| 预留浪费 | 为可能的增长提前预留，实际未用 | 视策略 | 按块惰性分配 |
| 语义浪费 | 注意力实际稀疏，但 KV 全存 | 可达 50% | 滑窗或稀疏注意力 |

PagedAttention 的内部碎片率：

$$ \text{内部碎片率} = \frac{\lceil S / B \rceil \times B - S}{S} $$

变量含义：$S$ 为序列长度，$B$ 为块大小。

| 序列长度 | 块大小 16 | 块大小 256 | 块大小 512 |
| --- | --- | --- | --- |
| 100 | 6.0% | 61.6% | 79.2% |
| 1000 | 0.0% | 2.3% | 48.8% |
| 4096 | 0.0% | 6.2% | 0.0% |

推论：块大小固定时，序列长度越接近块大小的整数倍，浪费越少。短请求场景应选小块。

### 3.5 并发上限的推导

并发上限由三个约束中的最小值决定。

| 约束 | 公式 | 说明 |
| --- | --- | --- |
| 显存约束 | \lfloor V_{kv} / (S \times b_{token}) \rfloor | KV 占用不能超显存 |
| 调度约束 | \lfloor S_{max} / S_{avg} \rfloor | 序列长度决定并发 |
| 计算约束 | \text{TPOT} \ge \text{单 token 计算时间} | 算力决定吞吐上限 |

示例：80 GB 卡，KV 占 60 GB，序列 4096，FP16，每 token 512 KB。

$$ \text{显存约束并发} = \frac{60 \times 1024}{0.5} \approx 122880 $$

但显存不是瓶颈。真正的约束是调度。

| 约束 | 结果 |
| --- | --- |
| 显存约束 | 122880 |
| 单步算力约束 | 约 256（每步每卡可跑 256 个请求） |
| 实际可行并发 | 约 200 |

推论：并发上限由算力决定，不由显存决定。这颠覆了「显存够大并发就高」的直觉。

### 3.6 KV Cache 的清理与淘汰

| 策略 | 规则 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 请求结束即释放 | 完成即删 | 简单，无残留 | 无法复用 |
| LRU 淘汰 | 淘汰最久未用 | 简单 | 可能淘汰正在用的前缀 |
| TTL 过期 | 超过 TTL 释放 | 防止冷请求占位 | 需要后台清理 |
| 前缀树保留 | 只淘汰叶子 | 保留高频前缀 | 实现复杂 |

边界条件：

| 场景 | 问题 | 对策 |
| --- | --- | --- |
| 请求中断 | KV 永久占用 | 设置最大生命周期 |
| 客户端断连 | 推理仍在跑，占 KV | 检测连接状态 |
| 超长输入 | 超过 max_model_len | 入口截断或拒绝 |
| 队列积压 | KV 迅速耗尽 | 准入控制 |

```python
def admit_request(queue_depth, kv_blocks_used, kv_blocks_total,
                  max_model_len, input_len):
    """准入控制：决定是否接纳新请求。"""

    # 边界一：输入超过模型上限，直接拒绝
    if input_len > max_model_len:
        return False, "input_exceeds_context"

    # 边界二：KV 剩余不足，直接拒绝
    if kv_blocks_used > kv_blocks_total * 0.9:
        return False, "kv_cache_full"

    # 边界三：队列过深时拒绝新请求，防止全部请求超时
    if queue_depth > 1000:
        return False, "queue_too_deep"

    return True, "admitted"
```

推论：准入控制比扩容便宜。先实现拒绝逻辑，再考虑加卡。

### 4. 引擎核心机制

### 4.1 六种机制的对照

| 机制 | 解决的问题 | 代价 |
| --- | --- | --- |
| PagedAttention | KV 显存碎片，并发上不去 | 块表间接寻址开销 |
| 连续批处理 | 静态批处理的长尾空转 | 调度器更复杂 |
| 分块 Prefill | 长 prompt 阻塞 decode，TPOT 尖刺 | TTFT 略增 |
| 前缀缓存 | 公共前缀被重复计算 | 需前缀稳定 |
| 投机解码 | Decode 逐 token 读权重 | 草稿计算开销 |
| CUDA Graph | decode 步上百次 kernel 启动 | 需按长度分档 |

### 4.2 连续批处理的执行流程

```python
class ContinuousBatcher:
    """连续批处理调度器。每个 step 动态增删请求。"""

    def step(self):
        # 1. 抢占：已完成的请求释放槽位
        finished = [r for r in self.running if r.done]
        self.running = [r for r in self.running if not r.done]
        for r in finished:
            self.free_slots.append(r.slot_id)

        # 2. 准入：新请求等待槽位与 KV 空间
        while self.waiting and self.free_slots:
            req = self.waiting[0]
            if not self.enough_kv(req):
                break                     # KV 不够，停止准入
            slot = self.free_slots.pop()
            req.slot_id = slot
            self.running.append(req)
            self.waiting.pop(0)

        # 3. 前缀缓存：已有 KV 的部分直接复用
        for req in self.running:
            req.cache_hit_len = self.prefix_cache.lookup(
                req.prompt_ids, req.model_id
            )

        # 4. 分块 Prefill：新请求的 prefill 分块，与 decode 交错
        #    避免长 prompt 阻塞正在 decode 的请求
        prefill_chunks = self.make_prefill_chunks(self.running)

        # 5. 执行：所有 running 请求各推进一步
        outputs = self.engine.forward(self.running, prefill_chunks)

        # 6. 写回缓存与采样
        for req, out in zip(self.running, outputs):
            req.append_token(out)
            self.prefix_cache.append(req)

    def enough_kv(self, req):
        """检查是否有足够 KV 空间容纳该请求的剩余长度。"""
        need_blocks = math.ceil(
            (req.seq_len + req.max_new_tokens - req.cache_hit_len)
            / self.block_size
        )
        return self.kv_manager.can_allocate(need_blocks)
```

### 4.3 分块 Prefill 的必要性

不分块时，一个 32K token 的 prompt 会占满整个 batch，其他请求的 TPOT 出现尖刺。

分块后，长 prompt 被切成若干块，与 decode 请求交错执行。

| 指标 | 不分块 | 分块 |
| --- | --- | --- |
| TPOT 稳定性 | 差，有尖刺 | 好 |
| TTFT | 略优 | 略增 |
| 并发公平性 | 差 | 好 |
| 显存峰值 | 高 | 可控 |

分块大小是权衡参数。过小则调度开销大，过大则尖刺明显。

### 4.4 CUDA Graph 的作用

decode 阶段每步只前向一个 token，包含上百次 kernel 启动。CPU 启动开销可能超过 GPU 计算时间。

CUDA Graph 把整个 step 的 kernel 序列预先录制成图，一次启动。

代价：输入形状必须固定。因此需要按序列长度分档录制多张图。

### 4.5 调度器的边界条件

调度器在极端场景下会失效。必须显式处理。

| 场景 | 现象 | 原因 | 对策 |
| --- | --- | --- | --- |
| 超长单请求 | 独占资源，其他请求超时 | 未分块 | 分块 Prefill |
| 超长单请求被拒 | 返回 400 | 超过 max_model_len | 入口截断并告知 |
| 队列积压 | 所有请求延迟无限上升 | 无准入控制 | 限流与拒绝 |
| KV 碎片 | 显存有剩余但分配失败 | 碎片化 | PagedAttention |
| 请求中断 | KV 永久占用 | 无生命周期 | 超时清理 |
| 批内长度差异大 | 部分请求空转 | 批内对齐 | 连续批处理 |
| 抢占过于频繁 | 吞吐下降 | 阈值过小 | 抢占阈值按 token 数 |
| 端到端超时 | 请求被中途杀掉 | 无分阶段超时 | 分别设 TTFT 与 TPOT 超时 |

### 4.6 过载的三种处置

| 处置 | 触发条件 | 行为 | 用户感知 |
| --- | --- | --- | --- |
| 排队 | 轻度过载 | 等待槽位 | 延迟上升 |
| 拒绝 | 中度过载 | 立即返回错误 | 明确错误 |
| 降级 | 重度过载 | 切换小模型或减精度 | 质量下降 |
| 丢弃 | 极端过载 | 静默丢弃 | 最差 |

准入公式：

$$ \text{准入} = \min\left(\frac{V_{kv}}{b_{avg}}, \frac{C_{gpu}}{t_{step}}, Q_{max}\right) $$

变量含义：$V_{kv}$ 为可用 KV 显存，$b_{avg}$ 为平均每请求 KV 占用，$C_{gpu}$ 为单步可跑请求数，$Q_{max}$ 为队列上限。

三段式降级的判定顺序：

```text
请求到达
  ├─ KV 使用率 < 70% → 正常准入
  ├─ 70% 到 90% → 准入并缩短 max_tokens
  ├─ 90% 到 98% → 仅准入短请求，长请求拒绝
  └─ > 98% → 拒绝全部非优先级请求，返回 429
```

推论：静默丢弃会让用户以为系统正常。必须返回明确的错误码。

### 5. 量化

### 5.1 量化的数学形式

线性量化把浮点值映射到低比特整数。

$$ \hat{x} = \text{clip}\left(\text{round}\left(\frac{x}{s}\right) + z,\; q_{min},\; q_{max}\right) s - z s $$

反量化：

$$ x \approx (\hat{q} - z) \times s $$

变量含义：$s$ 为缩放因子（scale），$z$ 为零点（zero point），$q_{min}$ 与 $q_{max}$ 为量化范围。

$s$ 与 $z$ 的计算：

$$ s = \frac{x_{max} - x_{min}}{q_{max} - q_{min}}, \qquad z = q_{min} - \text{round}\left(\frac{x_{min}}{s}\right) $$

### 5.2 四种主流量化格式对比

| 方法 | 权重量化 | 激活量化 | 代表值范围 | 特点 |
| --- | --- | --- | --- | --- |
| GPTQ | INT4 | 无 | 负值到正值 | 一层内向传播误差补偿 |
| AWQ | INT4 | 无 | 非对称 | 按激活重要性保护显著权重通道 |
| SmoothQuant | INT8 或 W4A8 | INT8 | 平滑后量化 | 迁移激活难度到权重 |
| FP8 | 原生 FP8 | FP8 | E4M3 或 E5M2 | 无需校准，Hopper 原生支持 |

### 5.3 各格式的精度与显存账本

以 70B 模型为例。

| 格式 | 权重占用 | 显存对比（相对 BF16） | 典型质量损失 |
| --- | --- | --- | --- |
| BF16 | 140 GB | 1.0 倍 | 基准 |
| FP8 | 70 GB | 0.5 倍 | 几乎无 |
| INT8 SmoothQuant | 70 GB | 0.5 倍 | 很小 |
| INT4 AWQ | 35 GB | 0.25 倍 | 小，需验证 |
| INT4 GPTQ | 35 GB | 0.25 倍 | 小，需验证 |

注意：以上仅为权重占用。推理总显存还需加上 KV cache 和激活。

### 5.4 量化前的质量评估

量化会引入误差。必须评估后再上线。

| 检查项 | 方法 |
| --- | --- |
| 困惑度变化 | 与原模型对比 |
| 任务指标变化 | 在冻结评测集上跑 |
| 退化样本 | 找出指标下降最多的样本类型 |
| 长文本表现 | 单独评估长上下文 |
| 多语言表现 | 单独评估 |

推论：INT4 的质量损失在特定任务上可能很大。必须按任务验证，不能假设通用。

### 5.5 量化误差的分布

量化误差：

$$ \epsilon = x - \hat{x} $$

$$ \text{MSE} = \frac{1}{N} \sum_{i=1}^{N} (x_i - \hat{x_i})^2 $$

推论：误差与激活分布的动态范围相关。动态范围大的层量化损失更大。这是激活量化更困难的原因。

### 5.6 逐层敏感度与混合精度

不同层的量化敏感度差异可达 10 倍以上。

| 层类型 | 敏感度 | 原因 | 建议精度 |
| --- | --- | --- | --- |
| 第一层与最后一层 | 极高 | 直接影响输入输出分布 | 保持 FP16 |
| 注意力 QKV | 中 | 分布较规则 | INT8 可行 |
| MLP 第一层 | 高 | 激活有离群点 | INT8 加离群点保护 |
| MLP 第二层 | 低 | 分布平滑 | INT4 可行 |
| LayerNorm 与偏置 | 极高 | 影响数值稳定 | 保持 FP32 |

```python
import torch

def layer_sensitivity(model, calib_data):
    """逐层量化敏感度测量。"""
    sensitivities = {}

    for name, layer in model.named_modules():
        if not isinstance(layer, (torch.nn.Linear,)):
            continue

        # 量化该层，其余保持 FP16，测指标下降
        baseline = evaluate(model, calib_data)
        quantized = quantize_layer(layer, bits=4)
        drop = baseline - evaluate(model, calib_data)
        sensitivities[name] = drop

    return sorted(sensitivities.items(), key=lambda x: -x[1])
```

混合精度配置：

| 策略 | 高敏感层 | 其余层 | 显存节省 | 质量损失 |
| --- | --- | --- | --- | --- |
| 全 INT4 | INT4 | INT4 | 4 倍 | 可能很大 |
| 混合 INT8 加 INT4 | INT8 | INT4 | 3.5 倍 | 很小 |
| 关键层 FP16 | FP16 | INT4 | 3.4 倍 | 几乎无 |
| 全 INT8 | INT8 | INT8 | 2 倍 | 很小 |

推论：混合精度用不到 10% 的额外显存，换回几乎全部的质量损失。这是性价比最高的选择。

### 5.7 量化方案的边界条件

| 场景 | 问题 | 正确做法 |
| --- | --- | --- |
| 校准集太小 | 量化范围估计偏 | 至少 128 条样本 |
| 校准集不覆盖长尾 | 离群点被裁掉 | 混入极端样本或用离群点保护 |
| 激活离群点 | INT8 精度崩掉 | SmoothQuant 或按通道量化 |
| 对话模板敏感 | 量化后套模板失败 | 校准集含系统提示 |
| 长上下文 | KV 量化误差累积 | KV 保持 FP16 或 INT8 |
| 批量大小变化 | 量化版本需重编译 | 固定形状或按档编译 |
| 权重分布双峰 | 单 scale 不够 | 双量化或分组量化 |

离群点问题的量化关系：

$$ \text{量化步长} = \frac{\max |x|}{127} $$

若某通道最大值是其他通道的 100 倍，该通道的步长是其他通道的 100 倍。其他通道全部被量化到 0。

SmoothQuant 的平衡公式：

$$ \hat{x}_i = s_i \cdot x_i, \qquad \hat{W}_i = \frac{W_i}{s_i} $$

变量含义：$s_i$ 为每通道的缩放因子。激活的离群点被迁移到权重上。

推论：SmoothQuant 用少量精度换取激活的可量化性。它不减少离群点，只是把它挪到更容易处理的位置。

### 5.8 PTQ 与 QAT 的选择

| 维度 | PTQ 后训练量化 | QAT 量化感知训练 |
| --- | --- | --- |
| 数据需求 | 128 到 512 条校准样本 | 完整训练数据 |
| 时间 | 分钟级 | 天级 |
| 质量 | INT8 好，INT4 有损 | INT4 也可无损 |
| 成本 | 低 | 高 |
| 适用 | 绝大多数场景 | INT4 且质量要求极高 |

推论：先用 PTQ。只有 PTQ 的 INT4 质量不达标时，才考虑 QAT。

### 8.4 推理 TCO 公式

$$ \text{TCO}_N = N \times C_{gpu} \times \text{利用率}_N + C_{工程师} $$

变量含义：$N$ 为 GPU 数量，$C_{gpu}$ 为 GPU 单位成本，利用率表示实际有效利用率。

推论：推理 TCO 通常由硬件成本主导。工程师成本占比远低于训练。这是推理优化比训练优化更划算的原因。

### 9.2 多模型路由

按任务类型、成本、时延路由到不同模型。

```python
class ModelRouter:
    """按任务类型、成本、负载路由到不同模型。"""

    def route(self, request):
        # 1. 按任务类型硬路由
        if request.task_type == "code":
            return "code-specialized"
        if request.task_type == "simple_qa":
            return "small-model"

        # 2. 按复杂度路由：先用小模型试探
        if request.complexity_score < 0.3:
            return "small-model"

        # 3. 按当前负载路由：避开过载实例
        candidates = [m for m in self.models
                      if m.latency_p99 < self.slo_threshold
                      and m.queue_length < self.queue_limit]
        if candidates:
            return min(candidates, key=lambda m: m.cost_per_token)

        # 4. 兜底：全部过载时用大模型保可用性
        return "large-model"
```

路由的四种策略：按任务类型、按能力门槛、按成本、按实时负载。

### 10. 常见问题排查

| 现象 | 可能原因 | 排查顺序 |
| --- | --- | --- |
| TTFT 高 | prefill 排队、KV 不足 | 查队列长度、KV 占用率 |
| TPOT 高 | decode 批太小、KV 读取多 | 查平均批大小、KV 长度分布 |
| 吞吐低 | 批处理未生效、KV 碎片 | 查 GPU 利用率与碎片率 |
| 首 token 慢 | 未预热、动态图编译 | 检查预热配置、启用图捕获 |
| 长请求拖慢短请求 | 未分块 Prefill | 启用分块 Prefill |
| 成本高 | 缓存未命中、并发不足 | 查缓存命中率与利用率 |
| 输出不稳定 | 采样配置、版本不一致 | 检查温度、种子、版本 |

排查顺序固定：先看队列，再看 KV，再看批大小，最后看代码。
