> 后摩是国产芯片的后起之秀，数据流架构令人耳目一新，最近也在大模型方面主动发力。尤其是发布了vllm和llama.cpp的后端，还是很厉害的。这次我们来以后摩为例子，漫谈一下NPU如何接入vLLM和llama.cpp的方案，以及我们发现的一些“苦涩之处”。

翻 llama.cpp 的上游仓库，`ggml/src/` 下面躺着一排后端目录：`ggml-cuda`、`ggml-metal`、`ggml-cann`、`ggml-hexagon`、`ggml-openvino`、`ggml-sycl`。每个目录做的是同一件事——把 ggml 的算子在自家硬件上实现一遍，然后告诉调度器「这些算子我能接」。华为昇腾走的是这条路，高通 Hexagon 也是。这条路铺好之后，上游合进来一个新模型，后端通常不用动，因为新模型拆开也还是那些算子。

后摩走的不是这条路。在 [houmo-ai/llama.cpp](https://github.com/houmo-ai/llama.cpp/tree/postmo) 的 postmo 分支上，确实有一个新建的 `ggml/src/ggml-houmonpu/` 目录，但真正跑计算的代码不在那里，而在一个全新的 `src/houmo/` 目录里，每个模型架构一份手写的 C++ 实现。vLLM 侧是同样的格局。

这个差别是存算一体架构的直接后果：权重在编译期就被摊到存算阵列上，算子边界在那一刻已经消失了。于是适配粒度只能是整张图，而不是一个个算子。

## 开源出来的四个仓库

GitHub 上 [houmo-ai](https://github.com/houmo-ai) 这个组织下面，跟推理框架有关的是四个：

![](https://pic1.zhimg.com/v2-d1116489dc607c9ce9677a5635c82a40_r.jpg)

vLLM 那边的 fork 第一个 commit 写着 `Base vllm_0.18.1.rc1`，插件挂在一个相对新的 vLLM 上。llama.cpp 的 fork 把上游快照留在 master、改动全放在 postmo 分支，两个仓库最后一次 push 都是 2026 年 8 月。不过 `src/houmo/` 里的文件头注释写着 2025-05-23，这条线内部至少做了一年多才开源出来。

两个框架的改法惊人地一致：服务层、协议层、tokenizer、采样、chat 模板全部留着，计算层整个换掉。

![](https://pic3.zhimg.com/v2-59422ec17e2f1303903f755537f46664_r.jpg)

## vLLM 侧：插件把自己注册成了 CPU

`vllm-postmo` 整个仓库才 400 KB，但文件分布很说明问题。`attention/attention.py` 39 行，`distributed/communicator.py` 568 字节，而 `model_runner.py` 有 5096 行、`models/` 下面二十来份手写模型文件，`houmoqwen3_5.py` 单文件 114 KB。算子层薄到几乎不存在，模型层厚得离谱。

先看平台类。`vllm_houmo/platform.py` 里 `HoumoPlatform` 的几个类属性是这样写的：

```python
# vllm_houmo/platform.py:28-35
_enum = PlatformEnum.OOT
device_name: str = "cpu"
device_type: str = "cpu"
simple_compile_backend: str = "eager"  # Disable torch.compile()
ray_device_key: str = "HOUMO"
device_control_env_var: str = "HOUMO_RT_VISIBLE_DEVICES"
dispatch_key: str = "PrivateUse1"
supported_quantization: list[str] = []
```

`device_type` 是 `"cpu"`，`torch.compile` 关掉，`supported_quantization` 是空列表。不是说 PyTorch 里真有一个 houmo 设备，而是在 vLLM 眼里这就是台 CPU 机器——张量该在哪就在哪，芯片在更下面一层自己管。

<br>再看 attention 后端的选择，这段最直接：

```python
# vllm_houmo/platform.py:281-303
def get_attn_backend_cls(cls, selected_backend, head_size, dtype,
                         kv_cache_dtype, block_size, use_v1, use_mla):
    if 1:
        if use_mla:
            logger.info("Using CPU MLA backend.")
            return "vllm.attention.backends.cpu_mla.CPUMLABackend"
        logger.info("Using Torch SDPA backend.")
        if use_v1:
            return "vllm.v1.attention.backends.cpu_attn.TorchSDPABackend"
        else:
            return "vllm.attention.backends.torch_sdpa.TorchSDPABackend"
    else: #szj change
        ...
        return "vllm_houmo.attention.attention.HoumoAttentionBackend"
```

`if 1:` 恒真，自家的 `HoumoAttentionBackend` 整个挂在走不到的 `else` 里。而且就算走到了也没用，因为那个类的 forward 是空的：

```python
 # vllm_houmo/attention/attention.py:36-39

 # 实现其他必要的注意力相关方法
 def forward(self, *args, **kwargs):
     # 调用houmo加速卡的推理接口
     pass
```

注释写着「调用 houmo 加速卡的推理接口」，函数体是 `pass`。这个类从来没被接上过。<br>那权重在哪儿加载？Worker 的 `load_model` 给了答案：

```python
# vllm_houmo/worker/worker.py:255-257
def load_model(self):
    logger.info("szj: run worker load_model just return True")
    return True
```

什么都不做。因为真正要加载的东西在 `model_runner.py` 里，而且它要的根本不是权重文件：

```python
# vllm_houmo/model_runner.py:978-1002
option1 = tcim.runtime.Option(self.weight_manager)
option2 = tcim.runtime.Option(self.weight_manager)
...
self.prefill = tcim.runtime.load(prefill_path, option=option1)
...
self.decode = tcim.runtime.load(decode_path, option=option2)
```

两次 `tcim.runtime.load`，载入的是两份离线编译好的整图二进制。prefill 和 decode 是两个独立产物，连形状都得从里面反查出来——`prefill_length` 读的是 prefill 图输入张量的第二维，`batch` 读的是 decode 图输入的第一维。框架不决定这些值，产物决定。

<br>Worker 里还有一句注释值得单独拎出来：

```python
# vllm_houmo/worker/worker.py:265-267
def determine_available_memory(self) -> int:
    logger.info("szj:determine_available_memory return fixed 1024G")
    return 1024*1024*1024*1024
```

返回一个假的 1 TB。vLLM 的 KV cache 预算机制在这里是关掉的，因为 KV cache 的块数在编译时已经定好了——那个被弃用的 attention 后端里写着 `self.num_kv_blocks = 36  # 固定36块KV缓存`，`supports_dynamic_kv_cache()` 返回 `False`。

> vLLM 侧的粒度：平台层伪装成 CPU，attention 后端用上游的 CPU 实现，自家算子后端是空壳；模型按架构一份份手写，权重以整图二进制形式载入。20 个架构注册在 `models/__init__.py` 里，不在列表上的模型跑不起来。

## llama.cpp 侧：一个bool key把计算图整段绕开

llama.cpp 这边有个 `ggml-houmonpu` 后端目录，490 行，看着像是走了算子路线。读进去会发现它是明确标注的占位实现：

```cpp
// ggml/src/ggml-houmonpu/ggml-houmonpu.cpp:360-382
// TODO: 以下 stub 函数在后端完整实现后替换
static ggml_backend_t ggml_backend_houmonpu_device_init_backend(
        ggml_backend_dev_t dev, const char * params) {
    return nullptr;
}

static ggml_backend_buffer_type_t ggml_backend_houmonpu_device_get_buffer_type(
        ggml_backend_dev_t dev) {
    return nullptr;
}

static bool ggml_backend_houmonpu_device_supports_op(
        ggml_backend_dev_t dev, const struct ggml_tensor * op) {
    return false;
}

```

`supports_op` 恒返回 `false`，意味着 ggml 的调度器永远不会把任何算子派给它；`init_backend` 返回 `nullptr`，连后端实例都建不出来。整个文件里 `GGML_OP_` 出现了零次——真实的算子后端不可能不枚举算子，`ggml-cuda.cu` 单文件里就有将近 400 处这样的算子分派。<br>那这 490 行在干什么？它去加载 `libhal_xh2a.so`，枚举出设备、报出显存和描述字符串。换句话说，让 `--list-devices` 能看见这颗芯片。上游 `ggml-backend.h` 里为此新增了一个设备类型，注释写得相当坦白：

```cpp
// ggml/include/ggml-backend.h        
        GGML_BACKEND_DEVICE_TYPE_ACCEL,
+       // hardware accelerator visible to --list-devices but not auto-initialized for compute
+       GGML_BACKEND_DEVICE_TYPE_HM_ACCEL

```

「可以在设备列表里看到，但不会被自动初始化去做计算」。<br>真正的分叉在 `src/llama.cpp` 的模型加载函数里，就五行：

```cpp
// src/llama.cpp:874-881
model.hparams.is_hmm = model.gguf_kv.count("is_hmm") &gt; 0;
LLAMA_LOG_INFO("%s:%d: loading hmmodes %d\n", __func__, __LINE__, model.hparams.is_hmm);
if (model.hparams.is_hmm) {
    model.load_hmmodels(ml);
    return 0;
}

if (!model.load_tensors(ml)) {
    return -2;
}

```

接管之后干活的是 `src/houmo/` 下的手写整模型。`houmo-qwen35llm.cpp` 单文件 74 KB，`houmo-llmodel.cpp` 33 KB，加上 embed、gptoss、vlmodel 几个，15 个文件合计约 19 万字节。接口长这样：

```cpp
// src/houmo/houmo-llmodel.h
bool houmo_load(llama_model_loader &amp; ml, std::vector&lt;int&gt; device_ids);
int  houmo_prefill(std::vector&lt;llama_token&gt; &amp;tokens, int seq_id, float *logits);

```

粒度就写在函数签名上：`prefill` 和 `decode` 各一个入口，进去是 token、出来是 logits。中间那几十层的算子，框架不参与。

## 同样叫 .gguf，里面装的不是一回事

上面那个 `is_hmm` 键是哪来的？`convert_hm_to_gguf.py`，4062 行，从上游的 `convert_hf_to_gguf.py` 改出来的。它在元数据里写上标记：

```python
# convert_hm_to_gguf.py:1134
self.gguf_writer.add_bool("is_hmm", True)
if self.hmm_info:
    self.gguf_writer.add_string("hmm.info", self.hmm_info)
```

然后，关键在于它往 GGUF 里塞的「张量」是什么：

```python
# convert_hm_to_gguf.py:891-901
required_keys = {
    "quant_embedding.bin": re.compile(r".*embedding\.pt$"),
    "prefill.hmm":         re.compile(r".*prefill\.hmm(s)?$"),
}
optional_keys = {
    "decoder.hmm":   re.compile(r".*decode(r)?\.hmm(s)?$"),
    "prefill_0.hmm": re.compile(r".*prefill_0\.hmm(s)?$"),
    ...
}

.....

with open(file_path, "rb") as file:
    binary_data = np.frombuffer(file.read(), dtype=np.uint8)
    data = torch.from_numpy(binary_data.copy())
yield key, data
```

整个编译产物以 `uint8` 字节流的身份被当成一个张量塞进去。GGUF 在这里退化成了一个容器格式——文件后缀、元数据头、tokenizer 词表都还在，所以 `llama-server` 能把它打开、能正常做 chat 模板和采样；但里面没有 `blk.0.attn_q.weight` 这种具名权重，ggml 拿到的只是一袋不透明的字节。<br>顺带一提，脚本还会把目录里所有 `.json` 和 `.txt` 文件也照这个办法打进去。

![](https://pic2.zhimg.com/v2-387ce39fd6c8cf8a36bcd1b89ee299f5_r.jpg)

唯一还留在主机侧的是 embedding 查表。`quant_embedding.bin` 单独存，运行时用 `F.embedding` 在 CPU 上查，查完的向量再喂给芯片上的 prefill 图。vLLM 插件里 `HoumoWorker.prefill` 这段写得很清楚：先 `get_embedding(input_ids)`，再把 `inputs_embeds` 传下去。

## 文件名就是一张规格单

要判断适配粒度，最硬的证据其实不在代码里，在 checkpoint 的名字上。这些是从 `vllm_houmo` 源码里直接抓出来的真实文件名：


## 那么，丢掉的算子级便利性是什么

上面我们看出来后摩适配开源框架没有走算子级别的适配，而是从整模型级别就接管了。整模型适配不是做不出东西来——能跑 20 个架构，覆盖 LLM、VLM、embedding、reranker、ASR、TTS，这工作量不小。丢掉的是另一类东西。

- **换配置要重新编译。**上下文从 8K 加到 32K、batch 从 1 改到 4、单卡换双卡，在 GPU 上都是改个启动参数的事，在这里每一项都对应一份新的编译产物。`postmo-modelzoo` 里 Qwen3.5 示例的 `config.yaml` 把 `context_length`、`prefill_length`、`ndevice` 列为编译期配置，就是这个原因。
- **新模型要等厂商。**算子后端的好处是上游合进来的新架构基本能白捡——拆开还是那些 matmul 和 rmsnorm。整模型路线下，`models/__init__.py` 里那 20 条 `register_model` 就是支持列表的全部，第 21 个架构得等后摩自己写一份实现。微调版同架构模型不需要新代码，但仍然要重新量化编译一遍。
- **编译链本身有门槛。**按 `postmo-modelzoo` 的 README，量化和编译只支持 linux-x64，推荐用官方镜像，而且**大模型量化需要 GPU**。也就是说想把自己的模型搬上这颗端侧芯片，手里得先有张 GPU 卡。推理侧倒是支持 Linux / Win11 / Android。
- **vLLM 的一部分能力是空转的。**连续批处理和 PagedAttention 是 vLLM 的招牌，但这里 KV cache 块数在编译期固定、`supports_dynamic_kv_cache` 为 `False`、可用内存返回一个假的 1 TB。`block_size` 被平台层强制改成 128，开 prefix caching 时还会打一行警告把它改回来。能用的是服务层那一半：OpenAI 协议、流式返回、chat 模板、采样、GBNF 约束解码。
- 公平地说，**LoRA 是个例外**。llama.cpp 的 fork 里接了 `lora_init` 和 `lora_set_scale`，适配器可以在运行时挂载、调权重、清空，不用重编主图。这是整模型路线下少见的运行时灵活点。

## 为什么只能这么做

存算一体把乘加做在存储阵列上，权重一旦映射进去就是物理布局的一部分，不再是一块可以随时换形状、换精度、重新切分的内存。ggml 那套「给我一个算子和几个张量，我算完还给你」的契约，在这种硬件上没有对应物——算子边界在编译的时候就被融掉了。

<br>所以 `hmatc` 那套工具链才是后摩真正的主场：`quant` 量化、`build` 编译、`golden` 生成参考数据、`check --layers` 逐算子对比精度、`compare` 做 ONNX / 量化后 / 编译后的三端比对。这些能力在算子级后端那条路上是不需要的，在这条路上是必需的。

<br>反过来说，vLLM 和 llama.cpp 在这里承担的角色也很清楚：它们提供的是 OpenAI 协议、tokenizer、chat 模板、采样器、grammar 约束、多模态前处理，以及一个用户已经熟悉的 `llama-server` 命令行。这些东西自己从头写一遍不难，但要和生态对齐就很烦。接上开源框架，省掉的是这一半的工作，不是计算那一半。<br>所以「支持 vLLM 和 llama.cpp」这句宣传，准确的读法是：**服务层和生态接口确实接上了，计算层是整模型离线编译后挂进去的**。拿它当成「把我的 GGUF 丢上去就能跑」会失望；当成「用熟悉的接口去用一颗需要离线编译的端侧芯片」就对了。
