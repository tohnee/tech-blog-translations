**模型结构已经理解了，那么一个 LLM 到底是怎么在一块 AI 芯片上真正跑起来的？**

这时就会遇到 Runtime。

对于边缘 AI 芯片而言，Runtime 往往是连接“模型”和“芯片”的关键一层。它既要理解模型，又要管理推理过程，还要把计算任务交给 CPU、NPU、GPU 等具体硬件执行。

在众多开源项目中，`llama.cpp` 非常适合作为理解 Edge LLM Runtime 的入口。

原因并不在于它一定是最强的 LLM 推理框架，而在于它的架构足够清晰：

> **模型 → Context → Graph → Backend → Hardware**

这条链路，非常接近一款边缘 LLM Runtime 真正需要解决的问题。

## 一、为什么选择 llama.cpp，而不是从 vLLM 开始？

如果目标是学习“大模型推理”，很多资料第一反应都是 vLLM。

但如果目标是：

> **理解 Edge LLM Runtime，以及未来如何把 LLM 映射到 AI 芯片上**

那么从 `llama.cpp` 开始，往往更加合适。

### 1. vLLM 更像“数据中心推理系统”

vLLM 解决的是一个非常现实的问题：

> 如何让大量用户、多个请求、多个 Batch，在 GPU 集群上高吞吐地运行 LLM？

因此它非常关注：

- Continuous Batching
- Paged Attention
- KV Cache 管理
- Scheduler
- Tensor Parallel
- Pipeline Parallel
- GPU Memory 管理
- 多请求并发
- 服务化接口

这些内容对于云端 LLM Service 非常重要。但对于第一次理解 Edge Runtime 的人而言，问题在于：

**系统太复杂了。**

如果直接从 vLLM 开始学习，很容易出现一个问题：

> 还没有理解一个 Token 是如何从模型进入硬件执行，就先陷入 Scheduler、Batch、Paged KV Cache、并行策略等系统问题。

这会导致“会用框架”，但并没有真正建立 Runtime 的底层认知。

## 二、llama.cpp 更适合理解 Edge Runtime

`llama.cpp` 的设计理念更加贴近端侧推理。

典型特征包括：

- 单机运行
- CPU 推理
- GPU 加速
- 小型模型
- 量化模型
- 低内存环境
- 本地推理
- 多种 Backend
- GGUF 模型格式

因此它特别适合回答几个关键问题：

- 模型怎么加载？
- 模型怎么变成可执行计算图？
- Prefill 和 Decode 怎么执行？
- CPU / GPU / NPU 到底在哪里接进去？
- Runtime 为什么需要 Backend？

这些问题，本质上就是 Edge LLM Runtime 的核心问题。

## 三、从 llama.cpp 中应该重点学习什么？

并不是要把 `llama.cpp` 所有代码都研究一遍。

本章真正需要建立的是下面这张逻辑链路：

```text
                    Model
                      │
                      ▼
                Model Loading
                      │
                      ▼
                    Context
                      │
                      ▼
                 Computation
                    Graph
                      │
                      ▼
                  Backend
          ┌────────────┐
          ▼           ▼           ▼
         CPU          GPU           NPU
          │           │           │
          ▼           ▼           ▼
       Kernel        Kernel      Kernel
```

可以把 Runtime 理解成一个“调度和连接层”。

上层告诉 Runtime： “我要让这个模型生成下一个 Token。”

Runtime 负责把这个请求拆解成：

```text
模型参数
   ↓
计算图
   ↓
算子
   ↓
Backend
   ↓
Kernel
   ↓
硬件
```

这就是理解 Edge LLM Runtime 最重要的一条主线。

## 四、llama.cpp 整体架构

从使用者角度看，llama.cpp 可以简单抽象成几个层次：

```text
Application
     │
     ▼
 llama.cpp API
     │
     ▼
 LLM Model / Context
     │
     ▼
 Computation Graph
     │
     ▼
 Backend
     │
     ├── CPU Backend
     ├── GPU Backend
     └── Other Backend
            │
            ▼
         Hardware
```

这里最值得关注的是： **Model、Context、Graph、Backend 并不是一回事。**

很多刚开始接触 Runtime 的人，会把这几个概念混在一起。

实际上，它们分别解决不同的问题。

## 五、Model：模型是什么？

Model 可以理解成：

> **“这个 LLM 需要哪些数据才能运行。”**

其中包括：

- 模型权重
- Layer 数量
- Hidden Size
- Attention 参数
- Vocabulary
- RoPE 参数
- Tensor 信息
- Quantization 信息
- Tensor 数据位置

例如一个 Llama 类模型，可能包含：

```text
Embedding
   ↓
Transformer Layer × N
   ├── RMSNorm
   ├── QKV
   ├── Attention
   ├── Output Projection
   ├── RMSNorm
   ├── FFN
   └── ...
   ↓
LM Head
```

模型加载完成之后，Runtime 才知道：

> 这是一个什么模型，以及这个模型有哪些参数。

## 六、Context：Runtime 的“运行现场”

Model 解决的是：

> “模型是什么？”

Context 解决的是：

> “现在正在运行什么？”

可以把 Context 理解成一次推理会话的运行环境。

它通常会涉及：

- 当前 Token
- 当前 Sequence
- KV Cache
- Context Length
- 临时 Buffer
- 计算状态
- Backend
- Memory
- Graph
- 推理相关的运行信息

因此：

```text
Model
= 模型本身

Context
= 模型的一次运行实例
```

这个区别非常重要。

例如：

```text
同一个 Qwen 模型
        │
        ├── Session A
        │      └── Context A
        │
        ├── Session B
        │      └── Context B
        │
        └── Session C
               └── Context C
```

每一个 Session 都可能拥有不同的：

- KV Cache
- 当前 Token
- 上下文长度
- Sampling 状态

所以 Runtime 设计中，Context 是非常核心的一层。

## 七、Graph：把“模型结构”变成“计算任务”

理解 Graph，是从“模型”进入“芯片执行”的关键一步。

模型结构本身并不是硬件能够直接执行的东西。

例如：

```text
RMSNorm
   ↓
QKV Projection
   ↓
RoPE
   ↓
Attention
   ↓
Output Projection
   ↓
RMSNorm
   ↓
SwiGLU
```

这其实只是模型结构描述。

真正执行的时候，需要变成：

```text
Tensor
   ↓
Operator
   ↓
Operator
   ↓
Operator
   ↓
Operator
```

进一步组织成一个 DAG，这就是 Computation Graph。

因此可以理解为：

> **Model 描述“是什么”，Graph 描述“怎么算”。**

这也是编译器和 Runtime 连接的重要地方。

## 八、Model → Context → Graph

把前面的内容串起来：

```text
Model
  │
  │ 读取模型结构、权重、配置
  ▼
Context
  │
  │ 建立当前推理状态
  ▼
Graph
  │
  │ 构建当前 Token 对应的计算任务
  ▼
Backend
  │
  │ 把计算任务放到具体设备
  ▼
Hardware
```

这条链路非常重要。因为设计一个 Edge LLM Runtime 时，也基本绕不开这几个概念。

## 九、GGUF：为什么 llama.cpp 需要一种自己的模型格式？

要让一个 LLM 在边缘设备上运行，第一步不是计算，而是：

> **如何把模型加载进来。**

传统 HuggingFace 模型通常是：

```text
config.json
tokenizer.json
tokenizer_config.json
*.safetensors
```

这种格式非常适合训练和模型生态。

但是对于端侧推理而言，会有大量额外问题：

- 文件很多
- Tensor 信息分散
- 模型配置与权重分离
- Quantization 信息需要额外描述
- 加载流程比较复杂
- 不利于部署

因此 llama.cpp 采用了 GGUF。

## 十、GGUF 到底解决了什么问题？

GGUF 可以简单理解为：**面向推理部署的模型容器格式。**

它把模型推理需要的信息组织到一个比较统一的文件中。

可以粗略理解：

```text
GGUF
├── Metadata
│    ├── Model Architecture
│    ├── Context Length
│    ├── RoPE Parameters
│    ├── Vocabulary Information
│    └── Other Config
│
├── Tensor Metadata
│    ├── Tensor Name
│    ├── Shape
│    ├── Type
│    └── Offset
│
└── Tensor Data
     ├── Embedding
     ├── Attention Weights
     ├── FFN Weights
     └── ...
```

这样，Runtime 可以更直接地完成：

```text
Load File
   ↓
Read Metadata
   ↓
Identify Model
   ↓
Find Tensor
   ↓
Load Weight
   ↓
Create Runtime Context
```

## 十一、GGUF 对 Edge AI 的启发

对于边缘 AI 芯片，真正值得关注的并不是：

> “以后一定要支持 GGUF。”

而是它背后的设计思想：

> **模型部署格式应该服务于 Runtime。**

一个优秀的端侧模型格式，往往需要同时描述：

```text
Model
+
Tensor
+
Data Type
+
Quantization
+
Memory Layout
+
Metadata
```

进一步还可能需要考虑：

```text
Weight Location
+
Alignment
+
Memory Mapping
+
Compression
+
Hardware Requirement
```

这也是未来设计自己的 Edge LLM Model Package 时值得思考的问题。

## 十二、Prefill：第一次把大量 Token 喂给模型

LLM 推理一般分成两个阶段：

```text
Prompt
  ↓
Prefill
  ↓
KV Cache
  ↓
Decode
  ↓
Token
  ↓
Decode
  ↓
Token
  ↓
...
```

Prefill 阶段的输入通常是一整段 Prompt。

例如：“请介绍一下南京的历史……”

可能包含几百甚至几千个 Token。Runtime 需要一次性处理这些 Token。

## 十三、Prefill 在做什么？

可以把 Prefill 理解成：

> **一次性建立上下文。**

例如：

```text
Input Tokens
[101, 234, 532, 891, ...]
          │
          ▼
     Transformer
          │
          ▼
     Attention
          │
          ▼
      KV Cache
```

Prefill 最大的特点：

> Token 数比较多。

因此矩阵计算通常更容易形成比较大的计算规模。

从硬件角度看：

```text
Prefill
→ 计算量大
→ GEMM 更容易跑满
→ 更偏 Compute Bound
```

当然，具体是否 Compute Bound 还取决于模型、Batch、Sequence Length、Memory Bandwidth 等条件。

## 十四、Decode：一次生成一个 Token

Prefill 完成之后，模型开始生成输出。

例如：

```text
Prompt
   ↓
“人工智能正在……”
             ↓
           “改变”
             ↓
           “世界”
             ↓
           “。”
```

每一次通常只新增一个 Token。

因此：

```text
Decode
  ↓
1 Token
  ↓
Transformer
  ↓
Next Token
```

Decode 的特点与 Prefill 有明显区别：

- Batch 往往更小
- 每次新增 Token 很少
- KV Cache 需要频繁访问
- Memory Access 非常重要

因此 Decode 往往更加容易受到：

> **Memory Bandwidth / Memory Latency / Cache Efficiency**

的影响。

## 十五、Prefill 和 Decode 为什么必须分开理解？

因为这直接决定：

> **芯片到底应该怎么优化。**

简单理解：

| 阶段 | 主要输入 | 典型特征 | 更关注 |
| --- | --- | --- | --- |
| Prefill | 大量 Prompt Token | 计算密集 | Compute |
| Decode | 单/少量 Token | 反复访问历史 KV | Memory |

因此，一款 AI 芯片即使：

> TOPS 很高

也不意味着：

> Decode 一定很快。

这也是评价 Edge LLM 芯片时非常关键的一点。

不能只看：

```text
INT8 TOPS
FP16 TFLOPS
```

还应该关注：

```text
Memory Bandwidth
Memory Capacity
KV Cache Efficiency
Latency
Kernel Efficiency
```

## 十六、llama.cpp 中的 Prefill / Decode 可以怎样理解？

从 Runtime 角度，可以把一次推理抽象成：

```text
Prompt
  │
  ▼
Tokenization
  │
  ▼
Context
  │
  ▼
Build Graph
  │
  ▼
Backend Execute
  │
  ▼
KV Cache Updated
  │
  ▼
Decode
  │
  ├── Build Graph
  │
  ├── Backend Execute
  │
  ├── Sample Token
  │
  └── Repeat
```

因此 Decode 并不是：“调用一次模型，然后自然就得到全部输出。”

而是：

```text
Build / Execute
      ↓
Next Token
      ↓
Update Context
      ↓
Build / Execute
      ↓
Next Token
      ↓
...
```

这就是 LLM Runtime 与传统 CV 推理 Runtime 一个非常重要的差别。

## 十七、为什么 Backend 是 llama.cpp 中非常重要的设计？

这是理解 AI 芯片软件栈最值得掌握的一个概念。

假设计算图是：

```text
RMSNorm
   ↓
GEMM
   ↓
RoPE
   ↓
Attention
   ↓
GEMM
```

Graph 只负责描述：

> “需要执行这些操作。”

但是它并不应该直接写死：

```text
调用 CPU 指令
```

或者：

```text
调用 CUDA
```

更不应该直接写：

```text
调用某一家 NPU 的寄存器
```

这就是 Backend 存在的意义。

## 十八、Backend 到底解决什么问题？

Backend 可以理解成：

> **计算图和硬件之间的适配层。**

上层只需要表达：

```text
“执行 GEMM”
```

Backend 再决定：

```text
CPU → CPU GEMM
GPU → CUDA GEMM
NPU → NPU GEMM
```

这样，Runtime 的上层逻辑就不需要和具体硬件强绑定。

## 十九、为什么这对 Edge AI 芯片非常重要？

假设一款公司要支持：

```text
CPU
GPU
NPU
```

如果没有 Backend 抽象，很容易变成：

```text
LLM Runtime
   ├── CPU implementation
   ├── GPU implementation
   ├── NPU implementation
   └── Another NPU implementation
```

这样随着芯片增加，系统会越来越复杂。

而有 Backend 抽象之后，可以变成：

```text
LLM Runtime
     │
     ▼
   Graph
     │
     ▼
Backend Interface
     │
     ├── CPU Backend
     ├── GPU Backend
     ├── NPU Backend A
     └── NPU Backend B
```

这样上层 Runtime 的逻辑就可以尽量保持统一。

## 二十、Backend 不等于 Kernel

这是非常容易混淆的概念。

可以这样理解：

```text
Backend
   ↓
决定“在哪里执行、如何调度”
   ↓
Kernel
   ↓
真正执行具体计算
```

例如：

```text
NPU Backend
    │
    ├── Memory Allocation
    ├── Tensor Placement
    ├── Command Submission
    ├── Synchronization
    └── Kernel
          ├── GEMM
          ├── RMSNorm
          ├── RoPE
          ├── Softmax
          └── Attention
```

所以：

> Backend 更偏“执行管理”，Kernel 更偏“具体计算”。

## 二十一、把 llama.cpp 映射到 Edge AI 芯片软件栈

如果把前面的概念映射到一套典型的 Edge LLM Software Stack，大致可以形成：

```text
┌───────────────────────────────┐
│       Application             │
│ Chat / Agent / VLM / Demo     │
└───────────────┬───────────────┘
                │
┌───────────────▼───────────────┐
│       LLM Runtime             │
│                               │
│ Session                       │
│ Scheduler                     │
│ KV Cache Manager              │
│ Tokenizer / Sampling          │
│ Prefill / Decode              │
└───────────────┬───────────────┘
                │
┌───────────────▼───────────────┐
│       Graph / Execution       │
│                               │
│ Graph Build                   │
│ Graph Optimization            │
│ Operator Scheduling           │
└───────────────┬───────────────┘
                │
┌───────────────▼───────────────┐
│           Backend             │
│                               │
│ CPU / GPU / NPU               │
└───────────────┬───────────────┘
                │
┌───────────────▼───────────────┐
│      Device Runtime           │
│                               │
│ Memory / Queue / Event        │
│ Device Manager / Dispatch     │
└───────────────┬───────────────┘
                │
┌───────────────▼───────────────┐
│       Kernel Library           │
│                               │
│ GEMM / RMSNorm / RoPE / ...   │
└───────────────┬───────────────┘
                │
                ▼
              NPU
```

这张图实际上就是：

> **Edge LLM Runtime 的软件栈骨架。**

## 二十二、llama.cpp 对边缘 AI 芯片最大的启发

真正值得学习 llama.cpp 的地方，不是“照着它开发一个框架”。

而是理解它背后的几个架构思想。

### 1. Runtime 应该屏蔽硬件差异

上层最好关注：

```text
Model
Context
Graph
Inference
```

而不是：

```text
NPU register
DMA
Command
SRAM address
```

硬件相关内容应该尽可能下沉。因此可以形成：

```text
Application
      ↓
LLM Runtime
      ↓
Backend
      ↓
Device Runtime
      ↓
Kernel
      ↓
Hardware
```

### 2. Graph 是连接模型和芯片的重要桥梁

模型不是直接交给 NPU 的。中间需要经历：

```text
Model
 ↓
Graph
 ↓
Graph Optimization
 ↓
Backend
 ↓
Kernel
 ↓
Hardware
```

因此，Edge LLM 软件栈真正重要的能力之一，就是：

> **把 Transformer 图映射成硬件真正高效的执行图。**

### 3. LLM Runtime 不等于 Graph Compiler

这一点非常重要。

可以把两者简单分开：

### Graph Compiler

负责：

```text
Graph
 ↓
Optimization
 ↓
Fusion
 ↓
Scheduling
 ↓
Codegen
```

例如：

```text
Q
K
V
 ↓
Attention
```

可能被融合成：

```text
Fused Attention Kernel
```

### LLM Runtime

负责：

```text
Session
 ↓
Prefill / Decode
 ↓
KV Cache
 ↓
Scheduler
 ↓
Graph Execution
```

因此： Compiler 决定“怎么算得更高效”。

而： Runtime 决定“什么时候算、算谁、在哪里算”。两者是相互配合的。

## 二十三、LLM Runtime 与 Device Runtime 也需要区分

这也是设计 AI 芯片软件栈时经常遇到的问题。可以简单理解：

### LLM Runtime

解决： **LLM 怎么跑。**

例如：

- Session
- Token
- Prefill
- Decode
- KV Cache
- Sampling
- Scheduler
- Model Context

### Device Runtime

解决：

> **任务怎么在设备上执行。**

例如：

- Device Manager
- Memory Manager
- Command Queue
- Stream
- Event
- Kernel Dispatch
- Synchronization
- Multi-Core Scheduling

两层组合起来：

```text
LLM Runtime
     │
     │ “执行这个 Graph”
     ▼
Device Runtime
     │
     │ “把任务提交给 NPU”
     ▼
NPU
```

这对于边缘 AI 芯片的软件架构非常关键。

## 二十四、如果站在 AI 芯片厂商角度，应该怎么看 llama.cpp？

最值得关注的不是：

> “llama.cpp 支持哪些模型？”

而应该问：

### 第一，模型怎么进入 Runtime？

```text
HF
 ↓
Conversion
 ↓
Quantization
 ↓
Deployment Format
 ↓
Runtime
```

### 第二，Runtime 怎么构建 Graph？

```text
Model
 ↓

```

### 第三，Graph 怎么映射到芯片？

```text
Graph
 ↓
Backend
 ↓
Operator
 ↓
Kernel
 ↓
NPU
```

### 第四，Decode 怎么管理 KV Cache？

```text
KV Cache
 ↓
Memory Manager
 ↓
Device Memory
```

### 第五，如何让 CPU 和 NPU 协同？

例如：

```text
Tokenizer
      ↓
CPU
      ↓
Embedding
      ↓
NPU
      ↓
Attention
      ↓
NPU
      ↓
Sampling
      ↓
CPU
```

这其实已经进入真正的 Edge LLM Runtime 设计问题。

## 二十五、从 llama.cpp 继续往下学，应该看什么？

当 `Model → Context → Graph → Backend` 这条主线理解后，下一步才适合继续深入。

推荐的学习顺序是：

```text
llama.cpp
   ↓
Model Loading
   ↓
Context
   ↓
Graph
   ↓
Backend
   ↓
KV Cache
   ↓
Prefill / Decode
   ↓
Scheduler
   ↓
Memory Management
   ↓
Kernel
```

而不是一上来就：

```text
阅读大量底层源码
```

学习重点应该始终围绕一个问题：

> **一个 Token 从 CPU 上的输入，经过 Runtime，最终是如何变成 NPU 上的一次计算？**

## 二十六、最终形成一张 Edge LLM Runtime 心智模型

把本章全部内容压缩成一张图：

```text
LLM Model
                    │
             HF / GGUF / Package
                    │
                    ▼
              Model Loader
                    │
                    ▼
                 Context
          ┌─────────┼─────────┐
          │         │         │
        Token      KV       State
          │       Cache       │
          └─────────┼─────────┘
                    │
                    ▼
              Graph Builder
                    │
                    ▼
             Computation Graph
                    │
                    ▼
             Graph Optimization
                    │
                    ▼
                 Backend
          ┌─────────┼─────────┐
          │         │         │
         CPU       GPU       NPU
                              │
                              ▼
                       Device Runtime
                              │
                              ▼
                         Kernel Library
                              │
                              ▼
```

## 二十七、本章最重要的结论

学习 llama.cpp 的真正目的，并不是掌握一个开源项目的 API。

而是建立下面这几个认识：

**第一，LLM Runtime 是模型和硬件之间的桥梁。**

```text
Model
 ↓
Runtime
 ↓
Hardware
```

---

**第二，Model、Context、Graph、Backend 是不同层次的问题。**

```text
Model   → 模型是什么
Context → 当前运行状态是什么
Graph   → 当前需要计算什么
Backend → 在什么设备上怎么执行
```

---

**第三，Prefill 和 Decode 是两种完全不同的性能问题。**

```text
Prefill → 更偏计算
Decode  → 更偏内存访问与延迟
```

---

**第四，Backend 是 AI 芯片接入 Runtime 的关键位置。**

```text
Graph
 ↓
Backend
 ↓
Device Runtime
 ↓
Kernel
 ↓
NPU
```
