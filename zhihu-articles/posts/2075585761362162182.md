大模型推理并行策略：切分、通信与工程选型

本文默认讨论 decoder-only Transformer 的在线生成服务，并在每个策略中区分 **prefill**（处理输入、生成 KV cache）和 **decode**（逐 token 生成）两类工作负载。

![](https://pica.zhimg.com/v2-6a3b184d09c5d4456ecfe0d34c8affc6_r.jpg)

### 摘要

大模型推理的“并行”并非一种技术，而是把不同对象沿不同坐标轴分配给设备：**DP/请求并行**切请求副本，**TP**切同一层内的权重与中间张量，**PP**切连续层，**CP**切序列/KV 上下文，**EP**切 MoE 专家；**P/D 解耦**则是在服务阶段切分 prefill 与 decode。这些轴可以在 GPU mesh 上相乘，但它们的通信原语和性能曲线完全不同。[2] [3]

对在线推理而言，最关键的分水岭是 prefill 与 decode。前者通常具有较高算术强度，长 prompt 时可被矩阵乘法充分并行；后者每步只生成少量 token，权重和 KV cache 的读取更容易受显存带宽与同步时延约束。微软工程师 Christin Pohl 在一次推理优化演讲中将其概括为：

输入有多长、输出有多长、批量与并发如何、模型是否 MoE、GPU 间是 NVLink/NVSwitch 还是跨节点 RDMA/以太网、SLO 更看重 TTFT 还是 TPOT。

一条实用原则是：将需要高频 collective 的维度尽量放进高带宽域，将通信频次低、主要传递边界激活的维度放在跨节点域；但这只是拓扑启发，而不是可脱离模型和负载使用的硬规则。[1] [2] [10]

| 策略 | 切分对象 | 一次前向中主要通信 | 对单请求延迟的典型作用 | 最常见的工程位置 |
| --- | --- | --- | --- | --- |
| DP / 请求并行 | 请求、batch、完整模型副本 | 通常无同一次前向的跨副本通信 | 不直接缩短单请求；提高容量、隔离尾延迟 | 多 replica / 多 decode worker |
| TP | 每层权重、heads、中间 hidden | All-Reduce、Reduce-Scatter、All-Gather | 可让模型装入并行 GPU；高度依赖低延迟带宽 | 节点内 NVLink/NVSwitch 域 |
| PP | 连续层 / stage | stage 边界 Hidden State P2P | 降低跨节点 collective；有 pipeline bubble | 跨节点模型深度扩展 |
| CP | token 位置、Q/KV block | Ring P2P 或集合通信 | 长 prefill 扩展与激活/KV 分片；decode 需单独评估 | 长上下文 prefill 域 |
| EP | MoE expert 与被路由 token | dispatch / combine All-to-All | sparse MoE 的关键；decode 的小 token 批很敏感 | 专家所在的高带宽 group |
| P/D 解耦 | 服务阶段与 KV 流 | 一次 KV cache 迁移 | 减少 prefill 对 decode 的干扰；短输出可能亏损 | 独立 prefill / decode pool |

### 1. 统一观察框架：先问“切什么”和“何时交换”

对任意策略，建议以四个问题审视：**切分对象是什么；一个 rank 在本地计算什么；在什么算子边界交换什么张量；通信是否处于关键路径**。同样是“序列并行”，如果一个实现是在 LayerNorm/Dropout 处分片激活，另一个实现是在 attention 中搬运 KV block，它们就不能按相同的通信公式或性能结论处理。

**符号约定**

| 符号 | 含义 | 符号 | 含义 |
| --- | --- | --- | --- |
| B | 有效 batch | T | TP degree |
| S | prompt 序列长度 | C | CP degree |
| H | hidden size | M | PP micro-batch 数 |
| H_KV | K/V 的总 hidden 维度 | P | PP stage 数 |
| L | 层数 | e | 元素字节数 |

对长 prefill，`S` 常主导激活/KV 与 attention 的工作量；对 decode，`S` 是已积累的上下文长度，而每个序列每步新增 query 常接近 1。因此，任何写成 `B·S·H` 的通信量都必须注明是在什么阶段、什么 batch 定义下计数。

### 2. DP / 请求并行：切请求，不切同一请求的模型计算

**本节速览 · 切分对象**：请求、batch、完整模型副本

**主要通信**：通常无同一次前向的跨副本通信 ｜ **常见工程位置**：多 replica / 多 decode worker

![](https://pic1.zhimg.com/v2-f64ad9e37875b67041da399264479698_r.jpg)

在推理中，最直观的扩容方式是部署多个完整模型副本，让调度器把不同请求或不同 batch item 送到不同 replica。每个 replica 独立持有权重和自己所服务请求的 KV cache；在一个请求的正常前向内，replica 间无需像训练 DDP 那样同步梯度。因此 DP 的主要收益是 **总吞吐、故障隔离和请求级伸缩**，而不是使一个不能装入单卡的模型变小。[2] [3]

DP 的关键从“通信优化”转为“路由优化”。如果请求前缀已在某个 replica 的 KV cache 中，盲目按最低负载重路由可能触发重复 prefill；如果只追求 cache hit，又可能把热点 replica 打满。因此服务端通常需要在 queue/load、prefix cache hit、KV 可用空间与 SLO 之间折中。[10] 对超大模型，DP 复制整套权重的显存成本很高，通常在一个 TP×PP×EP 模型副本外层再扩 DP；外层 DP 的总数量由容量、请求相似度和可接受的副本成本决定，而非由单请求延迟决定。

### 3. TP：把一层拆给多个 rank，并在层内恢复依赖

**本节速览 · 切分对象**：每层权重、heads、中间 hidden

**主要通信**：All-Reduce、Reduce-Scatter、All-Gather ｜ **常见工程位置**：节点内 NVLink/NVSwitch 域

![](https://pic3.zhimg.com/v2-396013ca864b9888a17f55cf6a91f27a_r.jpg)

TP 将一个线性层或 attention 的 heads/投影权重沿可分维度切到 `T` 个 rank。Megatron 风格的组合通常让第一个线性层采用**列并行**：`W=[W₁,…,W_T]`，每个 rank 计算本地输出 `Y_i=XW_i`；随后第二个线性层采用**行并行**，将输入和权重相配对地切分，各 rank 得到局部贡献后以 All-Reduce 求和。对 Transformer block，这类“局部 GEMM → 聚合”的边界通常在 attention output projection 和 MLP down projection 各出现一次。[3] [4]

从通信而非代码实现看，TP 的本质是：每层都在同一个请求的 critical path 上发生同步。若使用序列并行，某些 All-Reduce 可实现为 Reduce-Scatter / All-Gather 对，减少激活复制；但它不会消除“层内依赖需要交换”的事实。故 TP 可把大层的权重和计算摊到多 GPU，却会对同步时延、拥塞与小 message 效率高度敏感。[3] [4]

LMSYS 的通信量分析以 ring All-Reduce、每层 attention 与 MLP 各一次归约为假设，给出 long-prefill 的近似：

$V_{TP}=2(T-1)\left(\frac{BSH}{T}\right)\cdot2L\cdot e\ \approx\ 4BSHLe.$

这里的第一个 `2` 是 ring All-Reduce 的数据移动计数，第二个 `2` 是每层两次 All-Reduce；这不是所有 kernel 融合和所有 collective 算法下的通用等式，而是一个说明 **通信量随层数 `L` 线性累积** 的比较模型。[1] 这也解释了为何 vLLM 的部署指南建议：若模型装不进单 GPU 但能装进单机，多 GPU 先用 TP；超过单机时常把 TP size 设为每节点 GPU 数，再用 PP 扩展到更多节点。[2]

### 4. PP 与 Chunked PP：切层深度，以边界 P2P 换取较低跨节点通信频率

**本节速览 · 切分对象**：连续层 / stage

**主要通信**：stage 边界 Hidden State P2P ｜ **常见工程位置**：跨节点模型深度扩展

![](https://pic4.zhimg.com/v2-d509035cdef0be2f10f4e66f983e3343_r.jpg)

PP 将连续层切为 `P` 个 stage。例如 stage 0 执行 layer 0–19，stage 1 执行 layer 20–39。一个 micro-batch 完成某 stage 后，把其 hidden state 通过 P2P 发给下一 stage；最后一 stage 完成后才得到输出。参数和该 stage 生成的 KV 局部保留在所属 rank，跨 stage 的主数据是边界 activation/hidden state。与 TP 相比，PP 的跨设备同步不在每层发生，而仅发生于 `P−1` 个 stage 边界。[1] [3]

在同样符号下，LMSYS 对 `M` 个微批的通信量模型为：

$V_{PP}=M\left(\frac{B}{M}SH\right)(P-1)e=BSH(P-1)e.$

该式强调总的边界激活量与 `P−1` 成正比，而不是与总层数 `L` 成正比。它适合比较“固定模型、`P\ll L`、长 prefill”的通信足迹；不应被误读为“PP 只有一次通信”——一个 micro-batch 仍须依次跨过每个相邻 stage，且 P2P 时延、发送/接收调度与 load balance 均会影响关键路径。[1]

PP 的代价是 **bubble**。当 pipeline 刚启动或将结束时，部分 stage 空闲。在朴素 `M` 微批流程下，LMSYS 文中使用：

$\text{Bubble Ratio}=\frac{P-1}{P-1+M}.$

因此长 prompt 被切成足够多的 chunk/micro-batch 时，若 `M\gg P`，bubble 可被摊薄；短请求、低并发或过高 PP degree 时，bubble 会变得显著。[1] Chunked Pipeline Parallelism（CPP）是在推理 prefill 中将长输入切成可流动的 chunk，并配合 asynchronous P2P、micro-batching 和动态 chunk size 来更早填满下游 stage；它是 **PP 的调度优化**，不是与普通 PP 平行的新的切分轴。[1]

**本节速览 · 切分对象**：token 位置、Q/KV block

**主要通信**：Ring P2P 或集合通信 ｜ **常见工程位置**：长上下文 prefill 域

![](https://pic1.zhimg.com/v2-ba7839cd41d3919df0f61cc0b1f3002a_r.jpg)

**CP（context parallelism）**让每个 rank 持有长序列的一段 token 位置及相应的上下文状态，以降低长序列下单卡激活/KV 压力并并行 attention。一个典型 Ring Attention 路径是：每个 rank 固定本地 Query block，将 KV block 沿环做 P2P 轮转；每轮对本地 Q 与当前 KV block 做 blockwise attention，同时发送当前 KV、接收下一个 KV，并以 online softmax 累积统计量。这让完整 attention 在不物化全矩阵的情况下完成。[6]

$V_{CP}=(C-1)\left(\frac{B S}{C}\cdot2H_{KV}\right)L e\ \approx\ 2BSH_{KV}Le,$

其中 `C` 是 CP size，`2H_KV` 覆盖 K 与 V。该模型指出 CP 在每层都要处理 KV 相关通信；GQA/MLA 等使 `H_KV` 小于 `H` 的架构会改变体积。务必注意，文章的文字叙述和不同框架实现可采用 ring P2P、All-Gather 或其他通信组织；**公式只对应其声明的 Ring-Attention 假设**，不能推广为全部 CP 实现的精确通信量。[1]

与 CP 不同，Megatron 语境中的 **SP（sequence parallelism）**通常把某些非 attention 操作的激活沿 sequence 维度分片，并与 TP 的 All-Gather/Reduce-Scatter 配合来节省激活内存。其并行度通常与 TP group 耦合；它不等价于“把完整长上下文 attention 均匀切到多个 rank”。DeepSpeed Ulysses 则可通过 All-to-All 重排 sequence/head 维来扩张序列并行度，通信形态又与 ring 不同。[3] [5] [7]

![](https://pic3.zhimg.com/v2-62660c74578fde3cc22d5ded4e751974_r.jpg)

对推理，CP 最有说服力的收益通常位于**长 prefill**：长 sequence 提供了足够计算去覆盖或摊薄通信。纯 decode 每步新增的 query 很小，若仍要求跨设备巡游/聚合很长的 KV，通信更难被计算隐藏；因此 decode 侧的 KV 分片策略、模型的 KV head 数和服务端实现必须独立 benchmark，不能直接从训练或 prefill 论文外推。[1] [6] [12]

### 6. EP：让 token 去 expert，而不是让每个 rank 算同一份 FFN

**本节速览 · 切分对象**：MoE expert 与被路由 token

**主要通信**：dispatch / combine All-to-All ｜ **常见工程位置**：专家所在的高带宽 group

![](https://pic2.zhimg.com/v2-f92304f075e177c065a84e8bb6de4ff7_r.jpg)

EP 面向 MoE 层：专家权重被分布到不同 rank，router 为每个 token 选 top-`k` expert。数据路径可写成 `hidden states → router → dispatch → local expert GEMM → combine → original token order`。若 token 所选 expert 不在源 rank，就需要 dispatch All-to-All 将 token hidden state 发往专家所属 rank；expert 计算后，还要 combine All-to-All 把结果送回原序列的 rank 并按 gate 权重聚合。[3] [8]

EP 的关键不是“专家数多就一定更快”，而是 **token-to-expert 的动态稀疏流量是否均衡**。热门 expert 会让一个 rank 忙而其他 rank 等待；在连续 batch 中，这会直接放大 tail latency。权重复制、expert redundancy、capacity/缓冲策略、expert placement 和通信-计算重叠都是工程侧的补救手段。SGLang 的技术分享将这种重叠描述为把逻辑 batch 拆成微批：一个微批计算时，另一个微批做 expert dispatch/combine 通信。[11]

### 7. P/D 解耦：按阶段配置并行，而不是要求所有请求共用一套 GPU 形态

**本节速览 · 切分对象**：服务阶段与 KV 流

**主要通信**：一次 KV cache 迁移 ｜ **常见工程位置**：独立 prefill / decode pool

![](https://pic4.zhimg.com/v2-15bf2279ebd27362b222cbe797e2ea25_r.jpg)

P/D 解耦把一个请求的生命周期拆成两个资源池。Prefill worker 处理 prompt、建立 KV cache，并通常尽力降低 TTFT；随后 KV cache 被迁移到 decode worker，由后者逐 token 生成并优化 TPOT/并发。与 PP 不同，P/D 解耦不是把同一前向的连续层放在相邻 stage，而是把**时间上不同的 serving phase**放在可独立伸缩、可独立选择并行度的 worker pool 上。[9]

### 8. 混合并行与 GPU mesh：维度相乘，不等于成本相加

![](https://picx.zhimg.com/v2-ebeb7a4942011debfc9b6a79056cf965_r.jpg)

将并行 group 抽象成正交 GPU mesh 后，常用的资源数量关系为：

$N_{GPU}=D\times T\times P\times C\times E,$

其中 `D/T/P/C/E` 分别为 DP、TP、PP、CP、EP 的 degree。该式只是 rank 布局的乘积，不代表五种维度可任意等度数、也不代表吞吐可相乘；约束来自模型形状（heads、KV heads、层数、expert 数）、算子实现、batch、显存、网络拓扑以及调度器。[3]

一个常见的层级布局是（由内到外）：

**最内层 TP**

尽量位于 NVLink/NVSwitch 域

**EP 与 CP**

具体位置取决于所选 All-to-All 或 ring 通信算法和 token/sequence 规模

**PP**

用来跨较弱网络切深度

**最外层 DP**

放置完整的模型副本以扩容量

vLLM 的操作性例子是单节点多 GPU 用 TP，跨多节点时通常令 TP size 取每节点 GPU 数、PP size 取节点数；同时也指出，单节点缺少 NVLink 时 PP 可能优于 TP。[2]

| 业务症状 | 首先检查的并行维度 | 优先验证指标 | 典型但非唯一的调整方向 |
| --- | --- | --- | --- |
| 模型权重装不进单 GPU | TP、PP | 单卡权重/KV 余量；collective 时间 | 节点内增加 TP；超过单机再加 PP |
| 跨节点 TP 的同步成为瓶颈 | TP、PP | 每层 collective 时间、链路利用率、TPOT | 缩小跨节点 TP group，以 PP 代替部分深度扩展 |
| 超长 prompt 的 TTFT 很高 | CP、CPP、P/D | prefill tokens/s、TTFT、CP/PP overlap | 以 CP 或 chunked PP 扩长 prefill；必要时独立 prefill pool |
| MoE decode 尾延迟高 | EP、DP、P/D | All-to-All tail、expert load skew、TPOT | 亲和放置/冗余 expert/overlap；把请求分散到更多副本 |
| 连续批中长 prefill 阻塞流式回复 | P/D、DP | P99 TPOT、goodput、KV transfer 时间 | P/D 解耦并单独配比两个池 |

### 9. CP、PP、TP 通信公式的横向解释

![](https://pic3.zhimg.com/v2-2417b120464945e90c2f20a1e7e4fc10_r.jpg)

下表严格沿用用户指定 LMSYS 文章的对比模型，目的是展示三者为何在超长 prefill、跨节点扩展时呈现不同的通信结构；不是跨框架、跨模型的统一性能预测器。[1]

| 维度 | 公式 | 高频单位 | 主要交换对象 | 公式所揭示的结构性含义 |
| --- | --- | --- | --- | --- |
| TP | 2(T−1)(BSH/T)·2L·e ≈ 4BSHLe | 每层两次归约 | hidden / 投影输出 | 随层数 L 线性累积；高频同步是跨节点扩展的压力源 |
| CP（Ring 假设） | (C−1)(BS/C·2H_KV)L·e ≈ 2BSH_KVLe | 每层 KV block 交换 | K/V states | 仍随 L 累积，但与 H_KV 相关；GQA/MLA 影响体积 |
| PP | BSH(P−1)e | stage 边界 | hidden state | 由 stage 边界而非 L 决定；用 bubble 交换较低通信频率 |
| PP bubble | (P−1)/(P−1+M) | pipeline fill/drain | 时间空槽 | 增大 M 可摊薄 bubble；短请求/过高 P 会恶化 |

该比较隐含了一个实践结论：对长 prefill，若高带宽域已容纳适度 TP/CP，继续增加跨节点 TP 常会增加每层同步压力；适度 PP 可把跨节点通信压缩为 stage 边界 P2P，但必须让 chunk/micro-batch 数足以填流水线。对 decode，这张表还不够：每步 token 少、集体通信启动时延和 KV 访问行为会更重要，必须用目标模型与目标请求分布做测量。[1] [2]

### 10. 选型流程与结论

应先用内存约束决定“必须有哪些轴”，再用网络拓扑决定“每个轴放在哪里”，最后按 prefill/decode 的 SLO 评价端到端结果。

**建议从简单基线开始，逐级加轴**

1. 单卡能装下就优先单卡
2. 装不下先形成节点内 TP
3. 跨节点时引入 PP
4. 长上下文 prefill 再引入 CP 或 chunked PP
5. MoE 引入 EP 并把 routing skew 纳入容量模型
6. 仅当阶段异质性和 KV 迁移可摊薄时采用 P/D 解耦 [1] [2] [3] [9]

**最重要的结论**是，不能把“多卡”当作一个连续可调旋钮。

TP、PP、CP、EP 分别在 `layer tensor`、`depth`、`sequence/KV`、`expert/token route` 上切分，它们交换的是不同张量，并在不同频率下把网络拉入关键路径。

高性能推理系统的核心工作不是堆叠更多并行度，而是让 **切分轴、模型结构、prefill/decode 负载、通信原语与物理拓扑相匹配**。
