> 大家好，这里是 Goodnote（好评笔记）。LangChain 的 Jess Weng 在 2026 年 10 月发布了《Context Engineering: How Deep Agents Remember》，讨论长时间运行的 Agent 如何避免上下文腐化。Deep Agents 在模型外围加入一套 harness，通过卸载、摘要、Skills、Subagents 和长期记忆，让主 Agent 只携带当前任务需要的信息。

![](https://pic3.zhimg.com/v2-d993a929116354234902c082f872aa58_r.jpg)

> 这五种机制各管一类问题：大块工具结果先存文件，逐渐累积的历史压缩成摘要，专业操作说明按需加载，过程繁杂的任务交给独立 Subagent，值得跨会话复用的信息保存为长期记忆。**系统可以保存很多内容，模型当前只看任务需要的部分**。<br>

## **核心要点**

长任务中的 Agent 很像临时突击复习的人：新内容越积越多，前面学过的东西越容易混乱。Agent 在执行过程中会不断接收指令、工具结果、文件、搜索内容和对话历史。当这些材料逐渐逼近模型的上下文窗口（context window）容量，历史、噪声和工具输出就会干扰准确性与推理质量。

这种现象称为**上下文腐化（context rot）**。token 数量还没达到硬上限，问题就可能出现。请求虽然还能被模型接收，相关信息却已经埋在大量旧材料和中间过程里。

Deep Agents 基于三个判断：

1. 上下文腐化会随着长任务中的信息积累不断加重，并导致准确性下降。
2. Deep Agents 通过五种机制把内容移出当前活跃窗口，同时尽量保留之后重新取回的能力。
3. 长期记忆以普通文件保存在用户控制的存储中，因此更换模型或模型提供商时仍能继续使用。

### **理解上下文工程的方法**

可以把 Agent 简化为一个模型和包围模型的 harness。模型负责推理和生成下一步动作，harness 负责组织消息、提供工具、执行工具调用、保存结果，并决定下一轮模型实际看到哪些内容。

![](https://pic2.zhimg.com/v2-8d5f648c88235e10ebbf8ae5d2f4f201_r.jpg)
*模型外围的 Agent harness*

图中间是大语言模型（Large Language Model, LLM），外层是 harness。上下文工程不能只靠一段 system prompt，外围程序还要在每轮调用前后整理信息。

应对上下文腐化的方法可以分成两个方向：

1. **阻止不必要的信息进入上下文窗口**。例如，把大工具结果保存到文件，只给模型一个预览；或者只在需要时加载完整 Skill。
2. **管理和过滤已经进入上下文窗口的信息**。例如，把较早的消息压缩成摘要，保留近期消息继续执行。

harness 的职责是在合适的时机，把合适的信息交给模型。实现这件事并不轻松，因为它要判断哪些材料应当保留、哪些可以移出，以及模型之后如何重新找到移出的内容。

Deep Agents 把信息移到文件、摘要或独立 Agent 中，让主 Agent 只携带当前需要的内容：

1. 大工具结果和用户消息通过卸载保存到文件系统，模型只看预览。
2. 上下文接近容量上限时，旧消息通过摘要压缩。
3. Skill 中的专业方法只在相关任务出现时加载。
4. 嘈杂任务由 Subagent 在单独的上下文中完成，只返回结果。
5. Agent 学到的长期信息保存到文件，并延续到下一次会话。

这些机制都减少活跃上下文，但内容没有简单消失。需要时，Agent 仍可读取保存的原始文件或历史记录。

## **在常见任务中应用上下文工程**

竞品分析 Agent 每周一研究五家公司，并按照团队模板生成报告。一次完整运行大致包括：

1. 拉取公司 A 的市场数据，导出结果可能包含数万行。
2. 搜索相关新闻，阅读几篇内容并记录笔记。
3. 对公司 B 到公司 E 重复相同过程。
4. 撰写报告，根据反馈修改，再按照团队模板排版。

执行到排版时，Agent 可能已经在每次模型调用中携带五份原始数据、数十条搜索结果和两版失效草稿。此时只需要结论和模板，前面的大部分材料已经派不上用场。

RAG 或文件搜索能让 Agent 按需找到材料，解决的是“应该把哪些外部信息取进来”。但这只完成了一半工作。即便检索非常准确，Agent 仍会在运行过程中积累消息、工具结果和中间产物。harness 还要处理“已经进入或围绕上下文窗口的信息应该怎样管理”。

## **如何实现这些机制：中间件**

Agent 运行在一个循环中：模型决定下一步动作，调用工具，读取工具结果，然后继续判断，直到任务完成。

中间件（middleware）是插入这个循环特定位置的代码。它可以在 Agent 启动前运行，也可以包围每次模型调用或工具调用。每到一个接入点，中间件都可以读取当前上下文，并在下一步开始前修改它。

可以把流程理解为：

```text
Agent 启动
  → 中间件准备上下文
  → 模型决定下一步动作
  → 调用工具
  → 中间件处理工具结果
  → 模型读取整理后的结果
  → 重复执行，直到任务完成
```

五种上下文工程机制都以中间件形式接入这些位置。常用能力已经内置，直接使用时通常不需要自己编写中间件；需要调整特定行为时再做定制。

## **卸载：让大块内容留在上下文窗口之外**

模型不需要在每次调用中看见工具返回的全部数据。竞品研究中的 `pull_market_report` 会返回数千行数据，但 Agent 可能只需要其中几个数字。让整份结果反复进入上下文，会消耗大量 token，也会增加模型查找关键信息的难度。

![](https://pic4.zhimg.com/v2-b14afbba2bfc743d1cbdc7537445ac4b_r.jpg)

工具结果卸载（tool result offloading）的过程很直接：工具返回大块内容后，`FilesystemMiddleware` 把完整结果写入文件，只把短预览和文件路径交给模型。模型需要更多细节时，再调用读取工具。

`FilesystemMiddleware` 在每次工具调用时工作：

1. 工具结果超过约 20,000 token 时，完整内容在进入对话前写入 `/large_tool_results/{tool_call_id}`。
2. 模型只看到开头和结尾几行组成的短预览，以及保存文件的路径。
3. 后续需要某个精确数字时，例如公司 B 的季度营收，Agent 可以用 `read_file` 对文件分页读取。

超长用户消息也会采用相同策略，只是默认阈值更高。像整段通话记录这样的输入超过约 50,000 token 时，会保存到 `/conversation_history/`。模型仍然能知道这份材料存在，并按需取回其中的片段。

卸载和截断的区别在于能否恢复。截断直接丢掉被裁掉的内容；卸载把完整内容留在文件中，只减少当前模型请求携带的部分。

## **摘要：压缩已经进入上下文的内容**

卸载可以处理突然出现的大工具结果，但无法阻止上下文在长任务中缓慢增长。五家公司的搜索记录、笔记、推理过程和草稿仍会逐轮累积。摘要（summarization）负责压缩这些已经进入历史的内容，让 Agent 能继续执行后面的研究和写作。

![](https://picx.zhimg.com/v2-96f2bdce24ab31b46260cb1a93cd96d9_r.jpg)
*卸载与摘要对上下文增长的影响*

图中的横轴表示任务不断推进，纵轴表示上下文中的 token 数量。曲线上的尖峰来自大型工具结果或用户消息：卸载把每个尖峰替换成短预览，所以曲线只小幅回落。即使没有大尖峰，搜索记录和草稿仍会让整体曲线持续上升。当使用量达到 85% 的默认触发位置时，摘要把较早历史压缩，曲线出现一次明显重置。

`SummarizationMiddleware` 会在每次模型调用前检查 token 使用量：

1. 使用量超过阈值时，默认是模型上下文窗口的 85%，系统调用另一个 LLM，把较早的消息压缩成一份摘要。
2. 较早消息退出当前上下文，近期消息保持原样，不参与改写。
3. 下一次模型调用先看到历史摘要，再看到完整的近期消息。

近期消息原样保留，可以避免模型刚收到的要求、反馈或工具结果被摘要改写。旧消息虽然不再逐条出现，但摘要仍提供任务已经做过什么、得到什么结论的连续记录。

摘要还有两个细节：

1. **可以恢复**。被压缩的消息写入 `/conversation_history/{session_id}.md`。撰写最终报告时，如果 Agent 需要公司 A 的某个研究细节，仍然可以从文件中读取。
2. **循环进行**。任务继续运行后，上下文会再次增长。下一次摘要会把前一份摘要也纳入压缩过程，因此 Agent 可以经过多轮压缩继续工作。

触发条件也不一定只能使用 token 比例。任务主题发生变化时，也可以主动摘要，例如从“收集五家公司资料”切换到“撰写最终报告”时先压缩研究历史。摘要 prompt 同样可以定制，让它优先保留任务所需的特定信息。

![](https://pica.zhimg.com/v2-3c194377159ce702865091025feb3092_r.jpg)
*卸载与摘要的职责对比*

这张对比图把两种机制的边界画得很清楚：卸载拦截尚未进入上下文的大输入，主要解决单次内容过大的问题；摘要处理已经存在于上下文中的历史，主要解决长期累积的问题。两者结合后，大尖峰被提前挡住，缓慢上涨的历史也能定期压缩。

## **Skills：只在需要时加载专业方法**

假设销售团队有固定的季度业务回顾（Quarterly Business Review, QBR）格式。这套说明每季度才使用一次。如果长期写进 system prompt，每次模型调用都会携带它，日常研究任务也要为这段无关说明支付 token 和响应时间成本。

更合适的做法是把它封装成 Skill。Skill 是一个包含指令的文件夹，还可以附带脚本和参考资料，为 Agent 提供完成专门任务所需的方法。

![](https://pic4.zhimg.com/v2-57ac8e4e3bebb1452782f432290886f5_r.jpg)
*Skill 文件夹结构*

图中的 `skills/` 目录可以包含多个 Skill，例如 `qbr-report/`、`weekly-report/` 和 `battlecard/`。每个 Skill 以 `SKILL.md` 为入口，内部还可以包含 `scripts/`、`references/` 和 `assets/`。主 Agent 不需要在启动时读取所有文件。

Agent 一开始只看到 `qbr-report` 的简短描述。任务进入 QBR 排版阶段后，它才读取完整说明。其他任务始终无需携带这套模板。

这种分层加载方式称为**渐进式披露（progressive disclosure）**。模型先看到一份简短“菜单”，确认某个 Skill 与当前任务相关后，再读取完整“做法”。十个 Skill 在初始上下文中只放十条名称和描述，无需一次塞进十份完整说明。

![](https://pic1.zhimg.com/v2-53f55f55221c5c16bd6f468a430a7442_r.jpg)

`SkillsMiddleware` 使用两个接入点完成这个过程：

1. Agent 启动前，扫描 Skill 文件夹，只读取各个 `SKILL.md` 的头部信息。
2. 每次模型调用时，把 Skill 名称和描述加入 system prompt。

完整指令只有在模型判断 Skill 与任务相关，并通过 `read_file` 读取后，才进入上下文。放到竞品研究场景中，Agent 在收集资料阶段无需携带报告模板；等到开始格式化季度业务回顾时，才加载 `qbr-report`。

## **Subagents：隔离过程嘈杂的工作**

卸载适合处理偶然出现的超大结果。如果一个任务从一开始就确定会经历大量搜索和页面阅读，例如研究一家公司，那么把整个任务交给 Subagent 更合适。

Subagent 在自己的上下文窗口中执行任务，只把结果返回主 Agent。几十次搜索、网页正文、失败尝试和中间笔记都留在子任务内部，不会挤占主 Agent 的上下文。

![](https://pica.zhimg.com/v2-aa78161f4bb10b87b42e114b820bf85a_r.jpg)

图中主 Agent 位于中间，Subagent A 和 Subagent B 各自拥有独立上下文与工具。主 Agent 负责分配任务和接收结果；每个 Subagent 在自己的边界内调用工具，再把整理后的输出交回主 Agent。

`SubAgentMiddleware` 允许为 Subagent 配置 system prompt 和可用工具：

```text
market_researcher = {
    "name": "market-researcher",
    "description": "Researches a company and returns the 3 most notable developments.",
    "system_prompt": "Use pull_market_report, then return 3 short bullet points. Do not return the raw report.",
    "tools": [pull_market_report],
}

agent = create_deep_agent(model=model, subagents=[market_researcher])

```

四个字段分别负责：

1. `name` 为 Subagent 指定名称 `market-researcher`。
2. `description` 告诉主 Agent，它负责研究一家公司，并返回三项最重要的进展。
3. `system_prompt` 要求它先调用 `pull_market_report`，最终只返回三条简短要点，不能把原始报告直接交回主 Agent。
4. `tools` 将它的工具范围限制为 `pull_market_report`。

主 Agent 可以把五家公司分别交给这个 Subagent。每次研究的完整报告都留在 Subagent 的上下文中，主 Agent 只收到三条结论，连原始报告的预览也不会进入主上下文。

这类任务通常边界明确、规模较小，可以使用成本更低的模型，也可以并行执行。能否省钱、能否并行，仍取决于任务是否适合拆分，不能把它当成所有 Subagent 都具备的固定优势。

## **长期记忆：跨会话保留信息**

完成一次竞品分析后，Agent 会学到很多信息，其中一部分值得留给后续任务。例如，用户要求“摘要使用要点列表，不要写成段落”。如果没有长期记忆，下周生成报告时还要再说一遍。

Deep Agents 把长期记忆保存为 Markdown 文件。配置好记忆文件后，`MemoryMiddleware` 负责三个环节：

1. **加载**：一次运行开始时读取记忆文件。
2. **注入**：每次模型调用时，把文件内容加入 system prompt。
3. **更新**：Agent 学到值得保留的信息后，例如用户对报告格式的偏好，更新这份文件。

长期记忆保存在普通文件中，不会写进模型参数，也不依赖某个模型提供商的内部存储。应用可以自行查看、修改和继续使用这些文件。

## **更换模型，保留记忆**

Deep Agents 不绑定单一模型提供商。记忆保存在自己的后端存储中，因此可以把同一份文件交给另一个模型：

```text
agent = create_deep_agent(
    model="openai:gpt-6",  # different provider, same memory
    memory=["/memories/AGENTS.md"],
    backend=backend,
    store=store,
)

```

`model` 改成新的模型提供商，`memory` 仍然指向 `/memories/AGENTS.md`。`backend` 和 `store` 继续提供原来的存储，因此新模型能够读到同一份偏好。下一周即使更换模型，报告摘要仍可以按照记忆中的要求使用要点列表。

跨模型保留下来的是文件中的知识和偏好，模型自身的隐藏状态没有迁移。不同模型读取同一文件后，具体执行效果仍可能有所差异。

## **需要牢记的上下文工程策略**

无论使用 Deep Agents、其他 harness，还是自行搭建 Agent，都可以保留六条原则：

1. **大输入应该卸载，不能直接截断**。截断会永久丢失内容，卸载仍允许 Agent 重新读取。
2. **压缩之后应该可以恢复**。摘要负责减小当前上下文，原始历史仍要保留在可读取的位置。
3. **专业方法应该按需加载**。把所有任务说明长期放进 system prompt，会让每次调用都承担无关内容。
4. **嘈杂工作应该隔离**。让 Subagent 在独立上下文中处理搜索和中间过程，主 Agent 才能保持专注。
5. **长期记忆应该由应用自己控制**。自己保存的记忆文件可以跨模型和提供商继续使用。
6. **默认参数应该允许调整**。适合某类任务的阈值，未必适合另一类任务。

其实吧，“Agent 记忆”可以理解成一套信息整理方法。很多时候，Agent 表现不好，问题出在我们把工具结果、历史对话、操作说明和长期偏好全塞进了同一个上下文窗口。信息虽然都在，模型反而很难抓住眼前最重要的部分。

这五种机制真正实用的地方，是让每类信息都有合适的去处：大块结果放进文件，过长历史压成摘要，专业流程按需加载，繁杂过程交给 Subagent，跨会话仍有价值的内容再写入长期记忆。做 Agent 时，先把这些信息放对位置，往往比继续加长 prompt 或盲目更换模型更管用。
