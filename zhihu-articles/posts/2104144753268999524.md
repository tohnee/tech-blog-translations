## 背景

前几天写了一篇[​从RDMA的测试结果说起 - 大包问题](https://zhuanlan.zhihu.com/p/2098690929876006027)，讲了我近期遇到的一个与RDMA测试相关的性能问题。今天就继续接着这个话题，说说与之相对的小包问题。

还是黏贴之前的那篇文章的测试方法

```text
# Server
~# ib_write_bw \
    -d mlx5_0 \    # -d 指定RDMA的设备
    -s 1048576 \   # -s 指定message size
    -D 30 \       # -D 指定测试时常 
    --report_gbits # 报告格式

# Client
~# ib_write_bw \
    -d mlx5_0 \
    -s 1048576 \
    -D 30 \
    --report_gbits \
    192.168.1.10 # 指定Server IP
```

所谓的“小包问题”是指当 -s参数为64KB的时候（65536）的时候，有较小概率出现网络带宽下降的情况。

## 重新定义重现标准

起初，64KB的测试统计结果是这个样子的：长时间疲劳测试300+轮，大多数的带宽稳定在380Gbps附，相对非常稳定；少数几个样本记录了网卡带宽低于客户认定的验收标准的360Mbps（红线水位）。

![](https://picx.zhimg.com/v2-32075f60db5da221c72f035a4e568f87_r.jpg)

尽管是个大工程，不得已只能每一轮测试都采集PCM数据，发现PCM实际观察到的网络带宽（通过PCIe bandwidth计算）相对比较一致——±3%左右的范围，且远远高于红线带宽。

考虑到整个重现过程中为了降低重现成本，每一轮的ib_write_bw的测试时长被设置在了30秒，相对非常短的时间在受到噪声影响的情况下非常容易出现跑分尖刺。本以为适当延长测试时间——比如增加至2分钟会大大减少由于测试噪声导致的“尖刺”，但沟通下来考虑初期到这个case的重现成本高的惊人，我只得认定只有低于275Gbps的带宽（蓝线）才会被认为重现了性能下降的问题。说起来只是简单的调整了一下阈值，但实际上这个过程前后花费了接近一周时间，前后几次拉低了蓝线的水位也是不得已而为之。

换句话说，**对于某些牵扯到概率的单纯性能问题，不妨先从测量方法上入手看看是不是超预期的误差导致的。**

### 从CPU视角看

RDMA（perftest）实测带宽113Gbps，相较正常值全程都在370Gbps以上，可以说是性能有了显著的下降。结合client端给到的数据是一致的；PCM相关的寄存器统计值也出现了从779Gbps -> 272Gbps的性能跌落，多方验证无误，出现明显的性能问题。PS：手搓水印，请忽略单位上的瑕疵。

metric_IO_bandwidth_disk_or_network_writes (MB/sec) 和 metric_IO_bandwidth_disk_or_network_reads (MB/sec) 两项指标下降比例并不一致，分别为40%和30%，IO的read下降更多。考虑到这个测试本身是个rdma write测试，对应的大头应该是IO read（这里被绕晕的同学先别着急，因为后面还有更晕的[狗头]）。Client端发起了RDMA write，对应的Server端就是数据从网卡写入内存；那从PCM或者从CPU的视角来看就是从PCIe bus上读取数据保存到DDR内存。——哲学上的从肯定到否定，再到否定之否定的异样美感！
