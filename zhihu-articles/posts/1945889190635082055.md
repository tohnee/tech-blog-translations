## 🌟 二、 背景

### vllm的提出为了解决什么问题？

答：memory waste，vllm解决了下列三种memory waste：

1. **预留Token**：传统推理会给每个request预留kv cache需要使用的memory，因为LLM本身无法确定这个请求会产生多少token，所以会按照固定的长度预留。
2. **内部碎片**：系统通常也会以“**块**”为单位进行分配，而不是单个 token；一个sequence长度300 ，系统会分配 2 个块（共 512 个 token 的容量），第二个块中就有212 个 token 的位置wasted。
3. **外部碎片**：每个请求使用的块大小不一样，memory在切割时会产生一些外部碎片，这些碎片可能不足以再分给一个新的请求。

![](https://pica.zhimg.com/v2-6de84e37eb7cad1ceef6d3fda9648dd8_r.jpg)
*PagedAttention 原文 Figure3：3种memory waste 图解*

### vllm**的解决方案**

vllm基于PagedAttention算法，通过“分页”机制，替代传统的“预先分配连续最大内存”策略，来减少内存碎片。

1. **解决预留Token**：不再为Sequence预分配整个生命周期的内存。系统维护一个全局的**物理块池**。Sequence只在需要时才申请新的物理块。
2. **解决内部碎片**：将 KV Cache 存储在固定大小的**块**中。一个Sequence的 KV Cache 可以分布在多个非连续的物理块中。最后一个块的未用空间就是内部碎片，但由于块大小固定且相对较小（如16个token），这种浪费被控制在了很低水平。
3. **解决外部碎片**：由于Sequence可以使用非连续的物理块，系统只需维护一个全局的**空闲物理块列表**。任何新请求都可以从列表中获得任意空闲块，而无需寻找连续空间。这从根本上消除了外部碎片。

**注意**：vllm是把waste控制在很低的水平，不是100% none waste，可以看这张图，对比了vllm和传统推理的waste水平：

## 🌟 三、 基本概念

- **Prompt**: 用户输入的文本指令或问题，是LLM生成内容的起点和依据。
- **Token**: 文本的基本单位。模型并不直接理解单词，而是将Prompt和输出都切分成Token进行处理（可能是一个单词、子词或标点）。
- **Sequence**: 由一串Token组成的、独立的生成请求。它可以是一个全新的Prompt，也可以是某个已有生成过程的延续。
- **Sequence Group**: 调度的一个单位，可以包含一个或多个Sequence。例如，对同一提示词进行多次采样（beam search）或并行推理时，这些关联的Sequence会组成一个组。
- **Scheduler**: vLLM的“大脑”，负责管理当前所有等待和执行中的SequenceGroup，决定下一步让Worker执行哪个（批）Sequence，以优化GPU利用率和吞吐量。
- **KV Cache**: 为了加速自注意力计算，模型为每个Sequence预先计算并存储的Key和Value张量。它是内存占用的主要来源，也是vLLM优化的核心。
- **Worker**: 实际执行模型前向传播的计算单元（如GPU），负责处理调度器分配的任务，完成Token的生成。
- **Engine**: vLLM的核心组件，作为系统的总控制器，它接收外部请求，并协调Scheduler、Worker和内存管理（尤其是KV Cache）来完成整个推理流程。

## 🌟 四、 vllm执行推理的逻辑

将vLLM的工作方式想象成一个精心设计的**"并行卡牌桌游"，**玩家携带手牌（prompt）入场，在游戏桌上获取到完整的任务链手牌（生成完整回复）后离场。

### 🃏 4.1 核心角色设定

- **游戏桌**→ LLM Engine：整个游戏的运行平台，拥有固定的"**行动容量**"（计算力）和"**卡牌槽位**"（显存），每个槽位在每个回合都可以生成卡牌。
- **游戏回合**→ `engine.step()`：每轮游戏都按照固定节奏进行，所有参与本轮的玩家同步行动，完成一轮完整的游戏循环。
- **游戏主持人** → Scheduler：每回合的指挥核心，负责管理玩家状态、分配槽位、决定行动顺序，确保游戏流畅进行。
- **玩家**→ 各个请求(Sequence)：每位玩家带着自己的**初始任务卡组**（Prompt）加入游戏，目标是通过多轮行动构建完整的**手牌**（生成完整回复）。
- **卡牌槽位**→ Block：桌面上放置卡牌的物理位置，对应KV Cache的存储块。槽位是稀缺资源，需要精心管理。
- **公共资源池** → BlockManager管理的空闲物理GPU显存块：当前可用于分配、未被任何Sequence占用的、连续的KV Cache显存块。

**注意：**在这个设定中，vllm就像一个游戏运营者，游戏桌是需要付钱的，vllm在租用当前游戏桌的情况下，给主持人的任务是：确保每一轮游戏桌都**坐满**玩家，不空转，最大化利用珍贵的游戏桌资源。

### 🎮 4.2 一个回合的详细流程

**【回合开始：主持人的准备阶段】**

1. **查看游戏状态**

- 主持人扫描所有玩家状态：等待入场的新玩家（WAITING）、正在游戏的活跃玩家（RUNNING）、暂时离场的玩家（SWAPPED）

**2. 资源盘点**

- 检查公共卡牌槽位池（`free_blocks`）还剩多少可用槽位

**3. 制定本轮策略**

- **规则一：**新玩家优先入场 → 优先安排带着厚厚初始卡组的新玩家（Prefill请求）入场，因为他们的"开局行动"（并行计算整个Prompt）效率最高
- **规则二：**动态槽位管理

**4. 组织本轮游戏**

- 最终确定可以行动的玩家名单（混合Prefill和Decode的批处理）
- 将所有选中玩家安排到游戏桌（GPU或其他算力卡）上准备行动

**【回合行动：同步出牌阶段 】**

1. 所有被选中的玩家**同时执行一个游戏动作**（进行一次前向传播，生成一个token）。这就像主持人发出指令后，所有玩家得到打出一张新卡牌。

**PagedAttention**：它就像游戏的**索引系统**，根据每个玩家的"槽位映射表"（Block Table）精准定位他们的卡牌存储位置，高效完成注意力计算。不同玩家甚至可以**共享基础卡组**（同一提示词的多个采样共享前缀块）。

**【 回合结束：结算与更新阶段】**

1. **任务完成判定**

- 抽到**终结卡**（`<eos>`）或达到**手牌上限**（max length）的玩家宣告任务完成，**离场；**
- 他们占用的卡牌槽位立即回收至公共池

**2. 状态刷新**

- 所有继续游戏的玩家，任务链都增加了一张新卡牌（KV Cache新增token）
- 假设有个**观众席（调用方）**可以看到玩家的卡牌，回合结束后，任务链的新增卡牌会刷新，观众席能实时感知到。（补充流式返回节点）
- 如果卡牌堆满了一个新槽位，资源管理器会从公共池分配新槽位
- 游戏桌状态同步更新（内存池状态变化）

**3. 立即开始下一轮**：主持人重新评估所有玩家状态，组织新一轮游戏。新入场玩家、进行中玩家、等待返场玩家都有机会参与。

### ❓️ 4.3 带着问题看vllm（卡牌游戏版）

**问题1：游戏厅初始多少卡牌槽位是怎么设计的？**

初始槽位数量 = GPU总显存 / 每个块大小（block_size），这是一个在游戏开始前就计算好的固定值。

游戏厅（GPU）的“桌面面积”（显存容量）是固定的。初始槽位数量由总显存除以每个槽位的大小（block_size）决定。例如，如果GPU有80GB显存，每个槽位（block）设计为16MB，那么初始槽位总数就是约5000个。

- **槽位大小可定制**：游戏设计师（系统管理员）可以根据常见“卡牌厚度”（模型层数和注意力头数）调整槽位大小。较小的槽位更灵活，但管理开销稍大；较大的槽位减少碎片，但可能浪费空间。
- **启动时一次性分配**：游戏开始时（vLLM引擎初始化），主持人（Scheduler）会直接租下整个游戏桌的所有可用槽位，形成一个公共槽位池（free_blocks）。这样避免了游戏中频繁申请桌位的开销。

**问题2： 如何记录玩家的卡牌编号**

每个玩家（Sequence）都有一个“个人槽位映射表”（Block Table），专门记录自己的卡牌编号：

- **映射表结构**：每个玩家的映射表是一个列表，记录他们当前使用的所有槽位编号（block_id）。例如，玩家A的映射表可能是[0, 5, 12]，表示他的卡牌分别存储在槽位0、5和12中。
- **卡牌编号规则**：
- **PagedAttention**：在回合行动（前向传播）时，主持人使用这个映射表快速定位每个玩家的卡牌位置，即使玩家的卡牌分散在不同槽位，也能高效并行计算。
- **共享卡牌**：如果多个玩家来自同一个团队（SequenceGroup）且共享前缀，他们的映射表会指向相同的槽位编号，实现内存共享。

**问题3：实际何时执行 Swap In/Out (卡牌换入换出)**

Swap In/Out 发生在主持人制定本轮策略时，具体时机是：

- **触发条件**：当主持人发现公共槽位池（free_blocks）不足，无法容纳新玩家（Prefill请求）或老玩家需要扩展时。
- **Swap Out（请玩家暂时离场）**：
- **Swap In（调回玩家）**：
- **执行时机**：严格在回合开始前的“主持人准备阶段”进行，确保行动阶段（GPU计算）不被打断，最大化游戏桌利用率。

**问题4：Sequence和SequenceGroup详细角色解读**

- **Sequence（单个玩家）**：
- **SequenceGroup（玩家团队）**：

**角色分工**：

- **Sequence** 是具体的执行单元，就像每个玩家在每轮中打出一张新卡牌（生成一个token）。
- **SequenceGroup** 是逻辑分组单元，帮助主持人优化资源（内存共享）和调度（整体推进团队进度）。

**问题5：AI对话应用中，每轮对话的前缀相同，这种场景下SequenceGroup会促进内存共享，如果不是共享前缀，SequenceGroup不带来内存的提升?**

正确

- **共享前缀场景**：在AI对话中，如果多个回复基于相同的对话历史（例如，同一提示词的不同采样），这些Sequence可以组成一个SequenceGroup。他们共享前缀部分的KV Cache块，大幅减少内存占用。这就像多个玩家共享同一套基础卡组，只需存储一份副本。
- **非共享前缀场景**：如果每个Sequence的提示词完全不同，SequenceGroup只是逻辑分组，但无法共享KV Cache块，每个Sequence都需要独立存储自己的卡牌，因此不会带来内存提升。这时SequenceGroup主要用于管理相关请求（如并行采样），但内存开销与单独Sequence相同。

vLLM通过PagedAttention和SequenceGroup，在共享前缀时自动实现内存优化，而在非共享时保持灵活性。

**问题6：结合上面的卡牌游戏，每一种模型的哪些角色是定制化的呢**

vLLM的架构是模型无关的，但某些角色需要根据具体模型（卡牌游戏规则）进行定制：

- **游戏桌（LLM Engine）**：核心调度逻辑是通用的，但需要集成具体模型的“游戏规则”（模型结构、注意力机制实现）。不同模型（如LLaMA、GPT）的注意力头数、层数等需要适配。
- **卡牌槽位（Block）**：槽位大小（block_size）可能根据模型维度（hidden_size、num_heads）调整，以优化内存布局。
- **玩家行动（前向传播）**：**模型**的具体计算图（如Transformer层）是定制化的，但vLLm通过抽象接口支持多种模型。
- **主持人（Scheduler）**：调度策略（如FCFS、优先级）是通用的，但如果有**模型**特定优化（如稀疏注意力），可能需要调整。

vLLM通过标准化的API和块管理，使大部分组件模型无关，只有模型推理核心需要定制。

**问题7 ：一般来说 一个游戏有好几块gpu，这时候哪个角色负责协调这些gpu？**

当游戏厅有多个游戏桌（多块GPU）时，主持人（Scheduler）和游戏桌管理器（LLM Engine）共同负责协调：

- **游戏桌管理器（LLM Engine）**：它是总协调者，负责将模型“分身”到多个GPU上（通过模型并行或张量并行），并管理跨GPU的卡牌槽位（显存块）。它确保所有GPU同步行动，就像多个桌子协同完成一个大游戏。
- **主持人（Scheduler）**：它仍然负责全局调度决策（如哪些玩家在哪轮行动），但现在需要考虑多个游戏桌的资源状态。它会从全局视角分配槽位，可能将玩家Sequence分布到不同GPU上。
- **跨游戏桌通信**：如果玩家卡牌存储在多个GPU上，PagedAttention会通过高速互联（如NVLink）协调数据交换，确保注意力计算正确。

这就像一个大型游戏厅有多个桌子，一个总主持人和多个分桌主持人协作，确保所有桌子同时进行游戏，且玩家可以跨桌子共享资源。vLLM的多GPU支持正是通过这种分布式调度实现的。

## 🌟 五、一个推理请求在vllm中的生命周期

一名玩家（推理请求）的生命周期：

1. **入场**：你携带着初始手牌（Prompt）加入游戏，**Scheduler**会根据当前游戏桌的拥挤程度，决定让你立即入场（Prefill），还是先在等待区稍候。一旦入场，你将占据初始的卡牌槽位，并完成prefill。

2. **循环与博弈**：你进入由多个“iteration”组成的核心循环。在每一回合开始前，Scheduler都会重新评估：是让你在本轮生成token，还是请你**暂时离场**。Scheduler内部有一套评估逻辑：

3**. 重返牌桌**：当你被**换出**后，在后续的某个iteration，当资源允许时，Scheduler会从仓库中调回你的状态，并重新分配槽位给你。这就是 **“Swap In”**。

4. **终局与离场**：你不断地被**调度**、**切入**、**切出**，直到你终于抽到终结卡牌（`<eos>`），或手牌达到上限。此时，你完成了任务，带着完整的任务链（生成的回复）离场，你所占用的所有资源都被彻底释放。

vllm推理请求的整个生命周期并非一条平坦的直线，而是一条被Scheduler动态管理、在“活跃”与“等待”状态间多次切换的折线。vllm整体设计为了一个最高目标：**确保昂贵的游戏桌，在任何时刻都座无虚席，高效运转。**

### **LLMEngine.step() 解析**

代码地址：[https://github.com/vllm-project/vllm/blob/39e63dec7c751a28d5a577caf16439e08a878c92/vllm/v1/engine/core.py#L331](https://github.com/vllm-project/vllm/blob/39e63dec7c751a28d5a577caf16439e08a878c92/vllm/v1/engine/core.py#L331)

```python3
    def step(self) -> tuple[dict[int, EngineCoreOutputs], bool]:
        """Schedule, execute, and make output.

        Returns tuple of outputs and a flag indicating whether the model
        was executed.
        """

        # Check for any requests remaining in the scheduler - unfinished,
        # or finished and not yet removed from the batch.
        if not self.scheduler.has_requests():
            return {}, False
        scheduler_output = self.scheduler.schedule()
        future = self.model_executor.execute_model(scheduler_output, non_block=True)
        grammar_output = self.scheduler.get_grammar_bitmask(scheduler_output)
        with self.log_error_detail(scheduler_output):
            model_output = future.result()
            if model_output is None:
                model_output = self.model_executor.sample_tokens(grammar_output)

        engine_core_outputs = self.scheduler.update_from_output(
            scheduler_output, model_output
        )

        return engine_core_outputs, scheduler_output.total_num_scheduled_tokens > 0
```

```python3
@with_cancellation
@load_aware_call
async def create_completion(request: CompletionRequest, raw_request: Request):
    metrics_header_format = raw_request.headers.get(
        ENDPOINT_LOAD_METRICS_FORMAT_HEADER_LABEL, ""
    )
    handler = completion(raw_request)
    if handler is None:
        return base(raw_request).create_error_response(
            message="The model does not support Completions API"
        )

    try:
        generator = await handler.create_completion(request, raw_request)
    except OverflowError as e:
        raise HTTPException(
            status_code=HTTPStatus.BAD_REQUEST.value, detail=str(e)
        ) from e
    except Exception as e:
        raise HTTPException(
            status_code=HTTPStatus.INTERNAL_SERVER_ERROR.value, detail=str(e)
        ) from e

    if isinstance(generator, ErrorResponse):
        return JSONResponse(
            content=generator.model_dump(), status_code=generator.error.code
        )
    elif isinstance(generator, CompletionResponse):
        return JSONResponse(
            content=generator.model_dump(),
            headers=metrics_header(metrics_header_format),
        )

    return StreamingResponse(content=generator, media_type="text/event-stream")
```
