## 0. 引言：初始化后的静态显存格局

与分析 FSDP1 的思路一致，先把「静态」的显存格局搞清楚——在第一次 forward 之前，各类张量究竟存在哪里。理解静态格局是理解后续所有动态行为（all-gather、reshard、offload）的基础，否则看到一个 tensor 在 CPU 上、另一个在 GPU 上，会不知道这是正常还是异常。

FSDP2 初始化完成后，每个被管理参数对应的核心张量如下：

| 张量 | 字段名 | 精度 | 存放位置 | 说明 |
| --- | --- | --- | --- | --- |
| 分片参数（常驻） | _sharded_param_data | 原始精度 | GPU / CPU Pinned | 每个 rank 持有的 1/N 分片，训练全程常驻 |
| 分片参数（DTensor 视图） | sharded_param | 原始精度 | GPU / CPU Pinned | _sharded_param_data 上的 DTensor 封装，替换了 module.weight |
| 完整参数（计算用） | _unsharded_param | 计算精度 | GPU | all-gather 结果，forward/backward 窗口内存在，用完释放 |
| all-gather 输出缓存 | all_gather_outputs | 计算精度 | GPU | all-gather 的原始输出，to_unsharded 后释放 |
| 梯度 | unsharded_accumulated_grad | 规约精度 | GPU / CPU | backward 阶段动态创建，reduce-scatter 后释放 |

与 FSDP1 相比，这张表短了很多——因为 FSDP2 没有 `_mp_shard`、`_full_param_padded`、`_full_prec_full_param_padded` 这些显式 buffer。混合精度的类型转换在 all-gather 的 `all_gather_inputs` 属性里按需完成，不需要提前分配低精度副本。

纵向主链是 FSDP2 的核心层次：`nn.Module` 经 `fully_shard()` 动态注入 `FSDPModule` 能力，每个 `FSDPModule` 绑定一个 `FSDPState`（状态机），`FSDPState` 持有一个 `FSDPParamGroup`（通信调度单元），`FSDPParamGroup` 管理 N 个 `FSDPParam`（单参数管理单元）。

- **常驻**的 `_sharded_param_data`（1D 底层存储）和 `sharded_param`（DTensor 封装，替换 `module.weight`）；
- 以及**按需**存在的 `all_gather_outputs`、`_unsharded_param`（forward 窗口）和 `unsharded_accumulated_grad`（backward 窗口）。

## 1. 为什么 FSDP2 要抛弃 FlatParameter

在动手看 `fully_shard` 的源码之前，有一个前置问题值得先回答：FSDP1 的 `FlatParameter` 设计已经很成熟了，FSDP2 为什么要彻底抛弃它？搞清楚这个问题，才能理解 FSDP2 每一处设计决策背后的动机，而不是把源码当成黑盒背下来。

`FlatParameter` 的「组级」抽象在纯训练场景下是效率优势，但它带来了一个根本性约束：一旦参数被打平进同一个 `FlatParameter`，组内各参数就无法再独立区分。这个问题在多模态大模型训练场景下集中爆发。

最典型的是**冻结参数无法跳过通信**。`patch_embed`、`pos_embed` 等视觉塔参数在微调阶段通常是冻结的（`requires_grad=False`），但只要它们和可训练参数被打进同一个 `FlatParameter`，FSDP1 就无法识别这一点——`requires_grad=False` 对整个 `FlatParameter` 不生效，冻结参数会跟着可训练参数一起走 all-gather 和 reduce-scatter，产生完全无用的通信开销。这也是 FSDP1 需要专门设计 `ignored_modules` / `ignored_parameters` 机制的根本原因——不是 FSDP1 不想跳过冻结参数，而是 `FlatParameter` 的粒度决定了它做不到。

另一个问题是**逐参数操作的退化**。参数被 flatten 之后，单个参数的边界信息退化为元数据（`_param_infos` 里的 offset、size），在 `FlatParameter` 上做逐参数梯度裁剪、梯度掩码、参数统计时，需要先从元数据还原出边界，再切片操作，实现复杂且低效。FSDP1 里有大量代码是在处理这种「从 flat 还原回 per-param」的逻辑，这是结构性复杂度，不是可以优化掉的工程问题。

FSDP2 用 per-parameter DTensor 替换 `FlatParameter`，每个参数独立持有分片信息和梯度状态。冻结参数的 `requires_grad=False` 直接生效，FSDP2 可以在 `_register_post_backward_hook` 时精确判断哪些参数需要梯度归约、哪些可以跳过，不再需要 `ignored_modules` 这类补丁机制。逐参数操作也回归自然——每个 `FSDPParam` 就是一个独立对象，不需要从元数据还原边界。

值得一提的是，这个设计在粒度上反而更接近 DeepSpeed ZeRO-3 的逐参数管理——FSDP2 绕了一大圈，在这一维度上向 DeepSpeed 靠拢了。

> 💡 **小结**：`FlatParameter` 的「组级」抽象是 FSDP1 一切显存优化的物理基础，也是其结构性局限的根源——参数一旦打平，粒度就回不来了。冻结参数无法跳过通信、逐参数操作需要从元数据还原边界，都是这个根本约束的直接后果。FSDP2 用 DTensor 逐参数分片取而代之，是对这一局限的根本性修正，代价是放弃了「一次 alloc、整体通信」的部分效率优势。这是整个 FSDP2 设计的出发点，后续所有机制都建立在这个选择之上。<br>

## 2. `fully_shard`：装饰一个 Module

理解了 FSDP2 的设计动机之后，从入口函数 `fully_shard` 开始读起是最自然的路径。`fully_shard` 是 FSDP2 的唯一公开入口，用户调用它来「装饰」一个 Module，告诉 FSDP2「这个模块需要被分片管理」。它的调用方式、调用顺序，以及它背后做了哪些事，决定了整个 FSDP2 树的拓扑结构和参数归属。

`fully_shard` 的调用规则与 FSDP1 的 `_recursive_wrap` 一样，必须遵循 **bottom-up** 顺序：

![](https://pic1.zhimg.com/v2-aed89f40a531eb0d6e175f999146b2da_r.jpg)

`fully_shard` 函数体的核心步骤：

```python
def fully_shard(module, *, mesh, reshard_after_forward=True,
                shard_placement_fn=None, mp_policy=..., offload_policy=...):

    # Step 1：初始化 FSDPState，绑定 Module + 注册 pre/post_forward hook
    state = fully_shard.state(modules[0])
    state.init(modules, device, mp_policy)

    # Step 2：收集「归自己管理」的参数——排除已被子层接管的
    managed_modules = _get_managed_modules(modules, ignored_params)
    params, buffers = _get_managed_states(managed_modules, ignored_params)

    # Step 3：把参数搬到目标设备
    _move_states_to_device(params, buffers, device)

    # Step 4：把参数封装进 FSDPParamGroup
    if params:
        state._fsdp_param_group = FSDPParamGroup(params, modules, ..., offload_policy)

    # Step 5：动态继承 FSDPModule，注入 FSDP 能力
    for module in modules:
        new_cls = type(f'FSDP{cls.__name__}', (FSDPModule, cls), dct)
        module.__class__ = new_cls  # 原地替换，用户侧无感知
```

### 2.1 `_get_managed_modules`：如何确定「归自己管理」的参数

这个函数解决了嵌套 `fully_shard` 时最核心的问题——参数归属去重，对应 FSDP1 中的 `_is_fsdp_flattened` 标记机制。

FSDP1 的做法是：子模块 wrap 时对其所有参数调用 `_set_fsdp_flattened(param)` 打标记，父模块 wrap 时通过 `_is_fsdp_flattened` 过滤掉已标记的参数。FSDP2 的做法更直接：遍历当前 Module 的所有子模块，跳过已经是 `FSDPModule` 实例（即已被 `fully_shard` 装饰）的子树，只收集尚未被任何 `FSDPParamGroup` 接管的参数。原理相同，实现更简洁。

以 Qwen3-VL 为例，`fully_shard` 完成后的参数归属如下：

![](https://pica.zhimg.com/v2-6b15984f590a4fce81675b778bcc1a8c_r.jpg)

### 2.2 动态注入 `FSDPModule`：不改变模型类型的能力注入

FSDP1 用 `FullyShardedDataParallel` 类包裹模型，`isinstance(model, FullyShardedDataParallel)` 返回 `True`，模型类型发生了改变，用户代码往往需要感知这一点。

FSDP2 走的是另一条路——运行时动态修改类的继承链：

```python
cls = module.__class__          # 例如 Qwen3VLDecoderLayer
new_cls = type(
    f'FSDPQwen3VLDecoderLayer',   # 新类名
    (FSDPModule, cls),             # FSDPModule 排在首位，保证方法优先级
    {'__deepcopy__': _unimplemented_deepcopy}  # 禁止深拷贝
)
module.__class__ = new_cls      # 原地替换，Python 对象不变
```

这样做的好处是双向兼容：`isinstance(module, Qwen3VLDecoderLayer)` 依然返回 `True`（用户代码不需要修改），同时 `isinstance(module, FSDPModule)` 也返回 `True`（FSDP 内部可以识别）。`FSDPModule` 排在继承链首位，保证 FSDP 的 `reshard`、`unshard` 等方法优先级高于原始类的同名方法。

> 💡 **小结**：`fully_shard` 做了三件事——确定参数归属（`_get_managed_modules`）、封装参数组（`FSDPParamGroup`）、注入能力（`FSDPModule` 动态继承）。bottom-up 调用顺序是硬性约束，违反它会导致参数归属混乱且不报错，是最难排查的 bug 之一。<br>

## 3. FSDPState：每个 Module 的状态管家

`fully_shard` 完成参数归属和能力注入之后，每个被装饰的 Module 需要一个地方来存放运行时状态——训练进行到哪个阶段了、参数现在是分片还是聚合状态、通信资源在哪里。FSDP1 把这些状态藏在 `FullyShardedDataParallel` 对象内部，模块和状态耦合在一起。FSDP2 把状态显式独立出来，每个被 `fully_shard` 装饰的 Module 都绑定一个 `FSDPState` 实例，职责边界清晰。

| 属性 | 作用 |
| --- | --- |
| _fsdp_param_group | 当前 Module 持有的分片参数组（可为 None） |
| _is_root | 是否为整棵 FSDP 树的根节点（None=未初始化） |
| _training_state | 训练阶段状态机：IDLE / FORWARD / PRE_BACKWARD / POST_BACKWARD |
| _comm_ctx | 分布式通信上下文，惰性初始化后共享给所有子节点 |
| _state_ctx | 全局训练上下文，包含 all_states 列表、预取队列等 |
| _states_to_forward_prefetch | 前向预取队列：当前计算时，提前 all-gather 的下一批模块 |
| _states_to_backward_prefetch | 反向预取队列：当前反向时，提前 all-gather 的上一批模块 |

### 3.1 `init()`：注册前向 Hook

`fully_shard` 调用 `state.init()` 的核心工作是注册前向 hook：

```python
def init(self, modules, device, mp_policy):
    # 建立 Module -> FSDPState 的反向映射（后续 hook 里可快速拿到状态）
    for module in modules:
        _insert_module_state(module, self)

    # 注册前向 pre/post hook
    # prepend=True：FSDP hook 在所有用户自定义 hook 之前执行，保证参数先就位
    self._pre_forward_hook_handle = modules[0].register_forward_pre_hook(
        self._pre_forward, prepend=True, with_kwargs=True
    )
    self._post_forward_hook_handle = modules[0].register_forward_hook(
        self._post_forward, prepend=False
    )
```

`prepend=True` 是个关键细节。FSDP1 因为是类包裹，forward 的调度权天然在 FSDP 手里，不存在执行顺序问题。FSDP2 改为函数装饰后，**必须通过 `prepend=True` 明确争抢 hook 的执行优先权，**保证 all-gather 在用户 forward 代码运行前完成。如果用户也注册了 pre-hook，FSDP 的一定先跑。

### 3.2 `_lazy_init()`：第一次 forward 时的全局初始化

FSDP1 和 FSDP2 都有惰性初始化，但参数分片的时机不同。

FSDP1 在 `__init__` 阶段就完成了参数扁平化和分片（`FlatParamHandle` 构建、`shard()` 调用）。`_lazy_init` 在 FSDP1 里同样不是空壳——它负责确定根节点、把通信上下文共享给子节点、初始化执行顺序元数据等运行时资源，这部分职责和 FSDP2 是类似的。

**两者的核心差异只有一点：参数分片本身的时机，FSDP1 在构造期完成，FSDP2 推迟到第一次 forward。**

![](https://pic4.zhimg.com/v2-711d44b6b7f8a3a391264919dfd5f4ed_r.jpg)
*FSDP2 lazy init*

FSDP2 中 fully_shard 调用时只创建了 FSDPParamGroup 对象，参数真正切分成 DTensor 是在 _lazy_init 触发的 FSDPParamGroup.lazy_init() 里完成的。这个推迟是必要的——fully_shard 必须 bottom-up 调用，父模块被装饰时无法预知完整的树形结构，只有等到第一次 forward 时才能确定谁是根节点、整棵树有哪些节点，再统一完成全局初始化。

```text
def _lazy_init(self):
    if self._is_root is not None:   # 幂等：只执行一次
        return

    self._is_root = True            # 第一个进入 forward 的即为根节点

    # 遍历整棵树，收集所有 FSDPState，为子节点打标记
    for module_name, module in root_module.named_modules():
        state = _get_module_fsdp_state(module)
        if state:
            state._is_root = False
            self._state_ctx.all_states.append(state)

    # 根节点 forward 后不 reshard
    # 原因：forward 完马上要 backward，reshard 再 unshard 是纯浪费
    if self._fsdp_param_group:
        self._fsdp_param_group.post_forward_mesh_info = None

    self._init_fqns()           # 为所有参数设置 FQN（调试用）
    self._init_shared_state()   # comm_ctx / state_ctx 共享给所有子节点

    # 触发所有参数组的 lazy_init，参数分片最终定型
    for state in self._state_ctx.all_states:
        if state._fsdp_param_group:
            state._fsdp_param_group.lazy_init()
```

根节点 `post_forward_mesh_info = None` 这个细节值得关注。FSDP1 同样对根模块做了类似处理——它在 `post_forward` 时不执行 `_reshard`。背后逻辑完全一致：forward 之后紧接着 backward，还需要完整参数来计算梯度，提前 reshard 只会增加一次无用的通信开销。

> 💡 **小结**：`FSDPState` 是 FSDP2 运行时的核心状态容器，它把「这个模块现在处于训练的哪个阶段」「参数现在是什么状态」「下一个需要预取的是谁」这些信息显式管理起来。`_lazy_init` 是 FSDP2「装饰期轻量、运行时定型」设计哲学的集中体现——把全局拓扑确认、通信上下文共享、参数分片定型这三件重活推迟到第一次 forward，换取更灵活的装饰顺序。<br>

## 4. FSDPParamGroup：以组为单位的通信调度

理解了 `FSDPState` 的职责之后，自然引出下一个问题：参数的实际通信（all-gather、reduce-scatter）是在哪里发起、以什么粒度执行的？答案就是 `FSDPParamGroup`。它是 FSDP2 中「批量通信」的核心抽象，对应 FSDP1 的 `FlatParamHandle`。一个 `FSDPState` 最多持有一个 `FSDPParamGroup`，组内所有参数共享相同的通信策略和 mesh 拓扑，all-gather / reduce-scatter 以组为单位批量执行。

与 FSDP1 不同的是，`FSDPParamGroup` 不再把参数 flatten 成一个大 tensor，而是持有一个 `FSDPParam` 列表，每个元素对应一个独立的参数：

```python
class FSDPParamGroup:
    def __init__(self, params, modules, mesh_info, ..., offload_policy):
        self.fsdp_params = [
            FSDPParam(param, module_info, mesh_info, ..., offload_policy)
            for param, module_info in zip(params, param_module_infos)
        ]
        self.offload_policy = offload_policy
        self._sharded_state = ShardedState.SHARDED
```

### 4.1 `unshard`：all-gather 的发起入口

参数组从分片态变成完整态的入口是 `unshard()`，它有几个值得关注的设计细节：

```python
def unshard(self, async_op: bool = False):
    if self._all_gather_result is not None:  # 已发起过，幂等复用
        return
    if self.is_unsharded:                    # 已是完整态，跳过
        return
    # ...
    self._all_gather_result = foreach_all_gather(
        self.fsdp_params,
        self._all_gather_process_group,
        async_op,
        *self.comm_ctx.get_all_gather_streams(async_op, self._training_state),
        self.device,
    )
```

**幂等设计**是关键：prefetch 预取时会提前调用一次 `unshard`，`pre_forward` 时还会调用一次，幂等保证不会重复发起通信，`_all_gather_result` 作为标志位复用上次的结果。

### 4.2 `foreach_all_gather`：两阶段流水线

真正的通信逻辑在 `foreach_all_gather` 里，它把整个过程拆成两条 Stream 上的两个阶段：

```python
# 阶段1：copy_in_stream — 准备输入数据
with device_handle.stream(all_gather_copy_in_stream):
    # 把组内所有 FSDPParam 的分片 concat 成一个连续 buffer
    all_gather_input, all_gather_output = torch.ops.fsdp.all_gather_copy_in(
        all_gather_inputs, inp_split_sizes, ..., world_size, rank, dtype, device
    )

# 阶段2：all_gather_stream — 执行集合通信
all_gather_stream.wait_stream(all_gather_copy_in_stream)
with device_handle.stream(all_gather_stream):
    all_gather_work = dist.all_gather_into_tensor(
        output_tensor=all_gather_output,
        input_tensor=all_gather_input,
        group=group, async_op=async_op,
    )
```

`all_gather_copy_in` 做了一件关键的事：把组内 N 个 `FSDPParam` 的分片（分散的小 tensor）拼接成一个**连续大 buffer**，再做一次 `all_gather_into_tensor`。这就是「以组为单位」效率高的物理原因——N 个参数合并成 1 次通信，而非 N 次。

两条 Stream 的分工让流水线成为可能：当前参数组在 `all_gather_stream` 上做通信时，下一个参数组的数据已经在 `copy_in_stream` 上开始搬运了，通信和数据准备时间重叠，整体吞吐提升。

![](https://pic3.zhimg.com/v2-b48ddd89fbc504531b15d1456364b6f2_r.jpg)

⭐与下一篇会介绍的的 `foreach_reduce` 相比，all-gather 只需两阶段，而 reduce_scatter 需要三阶段（copy_in → reduce_scatter → 后处理分发）。差异在于 all-gather 的输出可以直接用于前向计算，无需后处理；reduce_scatter 的输出还需要 dtype 转换、`as_strided` 零拷贝分发到各参数的 `sharded_param.grad`，因此多出一个 `post_reduce_stream` 阶段。

> 💡 **小结**：`FSDPParamGroup` 是连接「状态管理（FSDPState）」和「单参数管理（FSDPParam）」的桥梁。它保留了 FSDP1「以组为单位批量通信」的效率优势——`foreach_all_gather` 把组内所有参数分片拼成连续 buffer，一次通信搞定，而非逐参数多次通信。与 FSDP1 的差异在于 FSDP2 的「组」是逻辑分组，每个参数仍独立存储，这带来了更灵活的生命周期管理，也是支持 `CPUOffloadPolicy` 按参数精细控制的基础。<br> <br>

## 5. `FSDPParam`：单参数分片的核心

`FSDPParamGroup` 负责调度，真正执行分片操作的是 `FSDPParam`。它是 FSDP2 的最小参数管理单元，每个原始 `nn.Parameter` 对应一个 `FSDPParam`，承载该参数从「普通 Tensor」到「分布式 DTensor」的完整转换，以及整个训练过程中的显存状态切换。

### 5.1 `_init_sharded_param`：从普通 Tensor 到 DTensor

这是 FSDP2 参数分片的核心函数，完成「原生 `nn.Parameter` → FSDP 分片参数」的完整转换。整个过程分五步，每一步都有其存在的理由。

![](https://pica.zhimg.com/v2-9f93db9c40f71f5bab94e8183bde71d2_r.jpg)

```python
def _init_sharded_param(self, param, device, shard_placement_fn):
    # Step 1：解析分片策略（默认 Shard(0)，即沿第 0 维分片）
    fsdp_placement = shard_placement_fn(param) if shard_placement_fn else Shard(0)
    shard_dim = fsdp_placement.dim

    # Step 2：按 shard_dim 切分，当前 rank 持有自己那份
    chunks = _chunk_with_empty(param_data, shard_world_size, dim=shard_dim)
    sharded_param = chunks[shard_rank]

    # Step 3：padding 对齐（保证各 rank 分片大小一致，all-gather 时无需动态补 0）
    padded_sharded_param = param_data.new_zeros(padded_sharded_size)
    padded_sharded_param.narrow(shard_dim, 0, sharded_param.size(shard_dim)).copy_(sharded_param)

    # Step 4：CPUOffloadPolicy 时搬到 CPU pinned memory
    if self.offload_to_cpu:
        padded_sharded_param = padded_sharded_param.cpu()
        if self.pin_memory:
            padded_sharded_param = padded_sharded_param.pin_memory(device=self.device)

    # Step 5：封装为 DTensor，替换 module 上的原始参数
    self._sharded_param_data = padded_sharded_param.view(-1)    # 底层 1D 存储
    self.sharded_param = nn.Parameter(self.to_sharded_dtensor(sharded_param))
    self._setattr_on_modules(self.sharded_param)                # 替换 module.weight
```

### 5.2 Padding 对齐：all-gather 的效率前提

FSDP1 在构建 `FlatParameter` 时，在末尾追加通信对齐 padding，使总长度能被 world_size 整除。**FSDP2 同样需要 padding，但粒度降到了单参数级别。**

当参数的分片维度大小不能被 world_size 整除时，不同 rank 持有的分片大小不同。FSDP2 在初始化时就做好 padding，以 0 号 rank 的分片大小（`chunks[0].size()`）为基准，其余 rank 不足的部分填 0。这样 all-gather 通信时各 rank 输入尺寸统一，无需运行时动态补 0，通信更高效。

### 5.3 `CPUOffloadPolicy` 下的 Pinned Memory

`CPUOffloadPolicy` 下，分片参数在初始化阶段就被移到 CPU pinned memory，而不是在 forward 时临时搬运：

```text
if self.offload_to_cpu:
    padded_sharded_param = padded_sharded_param.cpu()
    if self.pin_memory:
        # pin_memory 锁页内存，CPU→GPU 的搬运走 DMA 通道，不占用计算带宽
        padded_sharded_param = padded_sharded_param.pin_memory(device=self.device)
```

这意味着初始化完成后，`module.weight` 指向的是 CPU 上的分片 DTensor。`module.weight` 会随训练阶段切换指向：

```text
初始化后（SHARDED）：   module.weight → CPU 上的分片 DTensor
all-gather 完成后（UNSHARDED）：module.weight → GPU 上的完整参数
reshard 后（SHARDED）：  module.weight → 重新指回 CPU 上的分片 DTensor
```

这个切换由 `_setattr_on_modules` 在每次状态转换时完成，对用户代码透明。但有一个隐患：**forward 函数体内部动态创建的 tensor，不在 FSDP 的设备处理范围内**。

**FSDP 只在根节点的 `_root_pre_forward` 里调用一次 `_to_kwargs`，把外部传入的 args/kwargs 搬到目标设备**。forward 体内用 `torch.tensor(...)`、`torch.zeros(...)` 等动态创建的 tensor，FSDP 对它们没有感知，设备完全由创建时的参数决定。

以 Qwen3-VL visual encoder 里的旋转位置编码为例：

```text
idx_tensor = torch.tensor(idx_list, dtype=torch.long,
                          device=self.pos_embed.weight.device)  # ← 用参数设备推断
```

不开启 `CPUOffloadPolicy` 时，`pos_embed.weight.device` 是 `cuda`，没有问题。开启后，如果这行代码在 `pos_embed` 所在参数组的 all-gather 完成**之前**执行（比如 visual encoder 被单独包了一层 `fully_shard`，内部子模块的 all-gather 还在异步跑），`pos_embed.weight` 仍然是 CPU 上的分片 DTensor，`pos_embed.weight.device` 返回 `cpu`，`idx_tensor` 被创建在 CPU 上。等 all-gather 完成、参数切换到 GPU 之后，`idx_tensor` 已经固定在 CPU 上，最终导致 `weight=GPU, input=CPU` 的设备不匹配报错。

![](https://pica.zhimg.com/v2-2b5708d2c729327ef06307b9adac5d2e_r.jpg)

正确做法是从**输入 tensor** 推断设备，而不是从参数推断：

```text
idx_tensor = torch.tensor(idx_list, dtype=torch.long,
                          device=hidden_states.device)  # ← 从输入推断，可信
```

输入 tensor 经过根节点 `_root_pre_forward` 的 `_to_kwargs` 已确定在目标设备上，是 forward 体内推断设备的可信来源。参数的设备随 FSDP 状态机切换，在 forward 体内不可依赖。

### 5.4 DTensor 的语义：`.size()` ≠ `.device` 的存储位置

分片后的 tensor 通过 `to_sharded_dtensor` 封装成 DTensor，携带完整的分布式元信息：

```python
self._sharding_spec = DTensorSpec(
    mesh=self._spmd_mesh,
    placements=(Shard(shard_dim),),
    tensor_meta=TensorMeta(
        param.size(),   # ← 完整参数的原始尺寸，非分片后的大小
        param.stride(),
        param.dtype
    )
)
```

`.size()` 返回完整参数的原始尺寸（让用户代码看到的是「逻辑上完整的参数」），`.device` 返回本地分片 tensor 的实际存储设备（`CPUOffloadPolicy` 下为 cpu，否则为 cuda）。两者语义不同，不能混用——**计算设备应该从输入 tensor 推断，而非从参数设备推断**。

### 5.5 `_setattr_on_modules`：完成参数替换

初始化的最后一步，把 module 上的原始参数替换为 FSDP 分片参数：

```python
def _setattr_on_modules(self, param):
    # 替换主归属 Module 的参数（如 q_proj.weight）
    unsafe_setattr_param(self._module_info.module, self._module_info.param_name, param)

    # 若参数被多个 Module 共享（如 tied embedding），全部替换
    for shared_module, shared_param_name in zip(
        self._module_info.shared_modules, self._module_info.param_name
    ):
        unsafe_setattr_param(shared_module, shared_param_name, param)
```

执行完毕后，`model.layers[0].self_attn.q_proj.weight` 从普通 Tensor 变成了 CPU/GPU 上的 DTensor，optimizer 和用户代码访问参数时，拿到的就是 FSDP 管理的分片参数。

> 💡 **小结**：`FSDPParam` 是 FSDP2 参数生命周期管理的最小单元。`_init_sharded_param` 完成了「切分 → padding → offload → DTensor 封装 → 替换到 module」的完整链路。两个最重要的细节：其一，`CPUOffloadPolicy` 下分片参数在初始化就落到 CPU pinned memory，`param.device` 返回 cpu 是正常行为，在 forward 函数体里用 `param.device` 创建新 tensor 会踩坑；其二，`DTensor.size()` 是完整参数的逻辑尺寸，`DTensor.device` 是分片的物理设备，两者含义不同，计算设备要从输入推断。<br>

## 6. 三种分片状态与显存布局

前面几节介绍了初始化过程，但 FSDP2 的显存管理是动态的——参数在训练过程中会在不同状态之间切换。理解这三种状态，是后续读懂前向和反向传播源码的前提，因为每一次 all-gather、reshard 操作本质上都是在这三个状态之间做转换。

FSDP2 用一个显式的状态枚举管理参数的生命周期，对应 FSDP1 的 `_free_storage` / `_alloc_storage` 机制：

| 状态 | 触发时机 | 显存占用 |
| --- | --- | --- |
| SHARDED | 初始化完成后 / forward 结束 reshard 后 / backward 结束后 | 约 1/N × 完整参数 |
| UNSHARDED | pre_forward all-gather 完成后 / pre_backward all-gather 完成后 | 完整参数大小（各 rank 各持一份） |
| SHARDED_POST_FORWARD | 非根节点 post_forward reshard 后，下次 backward 前 | 介于两者之间 |

三种状态对应的显存示意（CPUOffloadPolicy=True，dp_size=8）：

```powershell
初始化后（SHARDED）
  _sharded_param_data：CPU pinned memory，shape=[orig_size/8]
  module.weight：       CPU DTensor（分片态）

pre_forward all-gather 完成后（UNSHARDED）
  _unsharded_param：    GPU，shape=[orig_size]（完整参数）
  module.weight：       GPU Tensor（替换了分片 DTensor）

post_forward reshard 后（SHARDED，非根节点）
  module.weight：       恢复为 CPU DTensor（分片态）
  GPU 上的完整参数显存被释放
```

![](https://pic2.zhimg.com/v2-7cc0c19c678a806e4588ae8b44306715_r.jpg)

与 FSDP1 的 `_free_storage` 设计哲学相同：完整参数只在 forward/backward 的必要窗口内存在，用完立即释放。不同的是 FSDP1 需要显式调用 `_free_storage` / `_alloc_storage` 管理 buffer 的存储，FSDP2 通过状态枚举 + `_unsharded_param` 的创建/释放隐式完成这一管理。

注意根节点的特殊处理：`_lazy_init` 里把根节点的 `post_forward_mesh_info` 置为 `None`，意味着根节点 forward 后不执行 reshard，参数保持 `UNSHARDED` 直到 backward 结束。原因是 forward 后紧接着 backward，还需要完整参数计算梯度，提前 reshard 是纯浪费。

> 💡 **小结**：三种状态对应三个显存水位。绝大多数时间参数处于 `SHARDED`（最省显存），只在 forward/backward 计算窗口短暂切到 `UNSHARDED`，`SHARDED_POST_FORWARD` 是 HSDP 等特殊场景下的过渡态。根节点是唯一例外——它在 forward 后保持 `UNSHARDED` 直到 backward 完成，以避免一次无用的 reshard + unshard 往返。FSDP2 所有的显存优化都建立在「完整参数按需出现、用完即销」这一原则上。

## 7. 初始化全流程回顾

前六节分别介绍了 `fully_shard`、`FSDPState`、`FSDPParamGroup`、`FSDPParam`、三种分片状态，每一节都是整体拼图的一块。这一节把所有链路串起来，从 `apply_fsdp2` 调用到第一次 `model(input)` 执行完毕，走一遍完整的时序。

```text
# ── 装饰阶段（apply_fsdp2 调用时）─────────────────────────────────────
for layer in model.layers:          # bottom-up
    fully_shard(layer, ...)
    # → FSDPState.init()：注册 pre/post_forward hook（prepend=True）
    # → FSDPParamGroup()：收集归属参数，每个参数封装为 FSDPParam
    # → FSDPParam._init_sharded_param()：
    #       切分 → padding → CPU pinned memory（offload 时）→ DTensor
    #       → _setattr_on_modules()：module.weight 替换为分片 DTensor
fully_shard(model, ...)             # 根模型同上，此时 FSDP 树形拓扑定型

# 此阶段结束后：所有参数已是分片态 DTensor，_lazy_init 尚未执行
# ─────────────────────────────────────────────────────────────────────

# ── 第一次 forward（_lazy_init 触发）─────────────────────────────────
output = model(input)
# → 根节点 pre_forward hook 触发（prepend=True，最先执行）
# → _root_pre_forward()
#     → _lazy_init()：幂等，只执行一次
#         → _is_root = True，子节点标记 False
#         → 遍历 named_modules，收集 all_states 列表
#         → 根节点 post_forward_mesh_info = None（forward 后不 reshard）
#         → _init_shared_state()：comm_ctx/state_ctx 共享给所有子节点
#         → 所有 FSDPParamGroup.lazy_init()：参数分片最终定型
#     → all_gather_copy_in_stream / all_gather_stream wait 计算流
#       （防止通信流读到计算流还在写的张量）
#     → 输入 tensor 搬到目标设备
# → FSDPParamGroup.pre_forward() → foreach_all_gather → UNSHARDED
# → module.forward() 用户代码运行
# → FSDPParamGroup.post_forward() → reshard → SHARDED（非根节点）
#     → 在输出 tensor 的 grad_fn 上注册 _pre_backward hook

# ── 此后每次 forward ────────────────────────────────────────────────
# pre_forward  → all-gather → UNSHARDED → 用户 forward 代码
# post_forward → reshard   → SHARDED   → 注册 pre_backward hook
```

有几个细节值得在这里单独说清楚：

**`all_gather_stream.wait_stream(current_stream)`**：根节点 pre_forward 时，两条通信流必须等计算流执行完毕。原因是异步通信——如果计算流还在写某个 tensor，通信流就开始读它，会产生数据竞争。这个同步点是 FSDP2 多流设计的安全保障。

**`_pre_backward` hook 的注册时机**：post_forward 里把 `_pre_backward` 注册到输出 tensor 的 `grad_fn` 上，而不是 module 的 backward hook。这样 autograd 反向遍历到这个 tensor 时才触发，精确对应「即将进入这个 module 的反向」，比 `register_backward_hook` 时机更准确。

**根节点不 reshard 的意义**：从流程图可以清楚看到，根节点 post_forward 后参数保持 UNSHARDED，直到 backward 结束。这意味着根节点的完整参数在 forward → backward 的整个窗口内都在显存里，换来的是节省一次 reshard + unshard 的通信开销。对于大模型来说，根节点通常只持有 `embed_tokens`、`norm`、`lm_head` 等少量参数，这个权衡是合算的。

## 8. 与 FSDP1、DeepSpeed ZeRO-3 的横向对照

| 维度 | FSDP1 | FSDP2 | DeepSpeed ZeRO-3 |
| --- | --- | --- | --- |
| 封装方式 | 类包裹（FullyShardedDataParallel） | 函数装饰（fully_shard）+ 动态继承 | 参数 hook 注入 |
| 参数抽象 | FlatParameter（组内所有参数 concat） | FSDPParam（逐参数独立 DTensor） | 逐参数 ds_tensor |
| 分片粒度 | FSDP Unit（wrap 策略决定） | FSDP Unit（fully_shard 调用范围） | 逐参数 |
| 初始化时机 | 构造期一次性完成 | 两阶段：装饰期 + 第一次 forward | 模型初始化时逐参数注册 |
| 混合精度副本 | _mp_shard（独立 buffer） | all-gather inputs 里按需 cast | fp16_partitioned_groups_flat |
| 冻结参数处理 | 混入同一 FlatParameter，通信无法跳过 | requires_grad=False 直接生效 | 同 FSDP2 |
| TP 兼容性 | 困难 | 天然兼容（DTensor 统一语义） | 需要额外适配 |

从这张表可以看出 FSDP2 演进的方向：在参数管理粒度上向 DeepSpeed ZeRO-3 靠拢（逐参数），在工程实现上保持 PyTorch 原生的可组合性优势（DTensor、mesh 抽象）。

## 小结

| 张量 | 分配时机 | 本质 |
| --- | --- | --- |
| _sharded_param_data（1D 底层存储） | _init_sharded_param | 分片后的连续存储，训练全程常驻 |
| sharded_param（DTensor） | _init_sharded_param | _sharded_param_data 的 DTensor 封装，替换 module.weight |
| _unsharded_param | pre_forward all-gather 完成后 | 完整参数，forward/backward 窗口内存在，用完释放 |
| all_gather_outputs | all-gather 执行时 | 通信的原始输出，to_unsharded 后释放 |
| unsharded_accumulated_grad | backward 阶段 | 梯度，reduce-scatter 后释放 |

本文从 `fully_shard` 入口出发，依次走读了 `FSDPState` 的生命周期、`FSDPParamGroup` 的通信调度机制、`FSDPParam` 的参数分片核心逻辑，以及三种分片状态之间的切换规则。

FSDP2 的显存节省逻辑与 FSDP1 完全一致：每张卡只长期持有 1/N 的参数（`_sharded_param_data`），完整参数按需 all-gather，用完立即释放。两者的本质区别在于粒度——FSDP1 以 `FlatParameter` 为单位把同层参数打平成一个大 tensor 统一管理，FSDP2 把这套逻辑下沉到逐参数的 `FSDPParam` 层，每个参数独立持有分片和生命周期信息。这个粒度变化带来了两个实质性收益：冻结参数的 `requires_grad=False` 直接生效，不再产生无用通信；`CPUOffloadPolicy` 可以按参数精细控制 offload 行为，参数的设备状态随 FSDP 状态机切换，forward 体内不应依赖 `param.device` 推断计算设备。

下一篇将进入前向与反向的完整链路：Hook 系统如何驱动 all-gather 和 reshard、四条 Stream 如何协作避免数据竞争、预取机制如何把通信延迟隐藏在计算时间里，以及梯度归约流水线与 FSDP1、DeepSpeed ZeRO-3 的横向对照。
