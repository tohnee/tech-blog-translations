## 0x1. 一个 PR 在 Review Inbox 里怎么走

整个流程大概是这样：

```text
Slack @、私信、PR 频道，GitHub 上 @ 我或者 assign 给我的 PR
  -> 分诊：按改动的路径和规模分成 T1 / T2 / T3
  -> Codex 做 review
  -> 另一个 Agent 复核每一个阻塞问题
  -> 有真 bug：把问题发到 PR 上，和作者来回讨论，等作者改
  -> 没有阻塞问题：T1 / T2 直接 approve，T3 留给我看
  -> 跟 CI：触发、重跑、归因，必要时 @ 作者
  -> 合并，然后在原来的 Slack 线程里回一句 Merged

```

点开一个 PR，可以看到分诊结果、改了什么、改动涉及的运行路径流程图，以及 approve、重新 review 这些操作：

![](https://pic1.zhimg.com/v2-fae678a1b1858ee97e0ba498eb4a814a_r.jpg)
*打开一个 PR：分诊、改了什么、执行流程*

往下是每个问题的触发场景、修改建议、复核 Agent 的理由，以及最终会发到 GitHub 上的评论原文，再往下是相关测试和当前 head 的 CI：

![](https://pic3.zhimg.com/v2-1e5090b60589536af04880447d3a3fdc_r.jpg)

这两天Vibe和调试下来，几条比较关键的规则：

- **只有真 bug 才挡 PR。** 缺测试、缺 benchmark 数据这类意见最多算 Non-blocking，同一个要求不会反复提。一开始 Agent 会一遍遍让作者在新 head 上重测性能，作者其实很烦，这个我后来专门改掉了。
- **每个阻塞问题都要再过一遍复核 Agent**，复核不通过的不发。
- **我在 GitHub 上的回复就是指令。** 我在 PR 下面回一句「这个不用管」，它就把对应的意见撤掉；我回 LGTM，它就 approve。它只照做，不会回复我。
- **CI 基本全归 Agent 管。** 它会自己发 `/tag-and-rerun-ci`、`/rerun-failed-ci`，用 `/rerun-test` 跑和改动相关的测试。CI 失败了先按规则判断是不是 runner、磁盘这类基础设施问题，判断不了再交给 Agent 读日志。拿不到日志就只重跑，不去 @ 作者，这条是踩过坑的：之前它把「拉日志失败」的报错当成日志证据贴给了作者，还请作者去看一下。
- **合并要克制。** 每天最多自动合并 10 个，两次之间至少隔 1 小时，标了 WIP 或者 do-not-merge 的不合。遇到 GitHub 规则拦着的情况，比如 commit 邮箱没关联账号，就 @ 作者去处理，不会用 admin 权限绕过去。这里非常敏感，一定要注意

不能暴露给Agent任何的敏感token，只能让他comment和合并pr。

## 0x2. token 得省着用

很幸运有OpenAI送的Pro让我可以完成这个事情。。。

一开始我是全速跑的，结果大概 21 个小时就用了 2600 万左右的 token，Codex 账号的周额度很快就见底了。拆开看，review 占了六成多，剩下是复核、CI 归因、和作者讨论这些。后来做了几件事来省：

- **不再帮作者改代码。** 一开始 Agent 会直接往作者的分支推修复，比如解冲突、修它确认过的 bug。算下来，代修本身加上它引起的重新 review，一天要占三分之一的 token。所以现在只发评论，让作者自己改。
- **分时段批处理。** 每天 10:00、15:00、21:00 三个时段跑 Agent 的活。时段之外只做不花 token 的事，比如拉消息、发 CI 命令、合并、回 Slack。review 这种事其实不需要 Agent 实时盯着，作者那边的节奏一天集中处理几次完全够用。
- **增量复审。** 已经 review 过的 PR 推了新代码，只看新改动，再复查之前提的问题；如果只是合了一下 main，就直接沿用之前的结论。
- **CI 先走规则，翻译按需。** 能用规则判断的 CI 失败不再调 Agent；网页上的中文只有在我打开某个 PR 时才翻译。
- **每天 token 上限。** 我现在设的是 5M，网页上可以直接改，也可以点「立即运行一次」，不用等定时时段。额度用完了，页面顶部会有一个红色的提醒。

![](https://pic4.zhimg.com/v2-894f1cf84c953878426e4242cbcae951_r.jpg)
*agent 栏：今日用量、每日上限和立即运行，上面是额度用完时的提醒*

按现在的量估计，之后每天大概 3～4M，还要再观察几天看看。

## 0x3. 用到你自己的项目里

部署比较简单：

```text
git clone https://github.com/BBuf/sglang-review-inbox.git
cd sglang-review-inbox
cp config.example.json config.json
# 把 config.json 里的 <...> 占位符换成自己的 GitHub 用户名、codex 账号目录和模型名
CODEX_HOME=~/.codex codex login
python3 server.py --config config.json

```

然后浏览器打开 [http://127.0.0.1:8765](http://127.0.0.1:8765) 就可以了。Slack 是可选的，用仓库里的 `slack-app-manifest.json` 建一个 Slack App，再把 user token 粘到网页上。

几点建议：

- **先用影子模式跑几天。** 默认只看不写，先看看 review 的质量合不合自己的标准，再切到自动模式。发意见、approve、合并这些写操作，每一种都有单独的开关。
- **换成别的项目。** 流程本身是通用的，和 SGLang 绑定的地方主要有三处：CI 的 lane 和斜杠命令（`inbox/ci.py`），按路径划分的风险区域（`inbox/triage.py`），以及 review 用的 prompt 和 skill。把 review skill 换成你们自己项目的 review 标准，大部分就能直接用了。

## 0x4. 警惕

当然这套东西也有它的代价。

第一，它用的是你自己的 GitHub 和 Slack 身份，发出去的每一句话都算你说的。所以一定先在影子模式下多看几天。

第二，高风险的 PR 还是要人看。Agent 说 LGTM 不代表没有问题，合并前 CI 的门槛也别放松。

第三，token 消耗确实比较大，上面已经说了，注意自己账号的额度。

第四，别让它去绕过仓库的规则。宁可多 @ 一次作者，也不要给它 admin 权限。
