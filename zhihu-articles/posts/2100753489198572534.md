工具挂几个该算，3 到 8 那道线，7.6 是我实测夹出来的，往低了按真实描述长度能到 3.5。在我这台 Ollama 上，真正贵的在缓存：direct 那档，每轮都得重算一遍。

### 同一份诊断，两家开的药正相反

2026 年 3 月，Perplexity 的 CTO 在 Ask 2026 上说，他们内部已经弃用 MCP，退回 REST API 加 CLI。2026 年 9 月 29 日，Pi 把首页挂了将近一年的「No MCP」划掉，换成了「Now with MCP+Codemode」。Pi 是个编程用的 AI agent，作者是 Mario Zechner，2026 年 4 月被 Armin Ronacher 的 Earendil 收购。

这两条新闻放在一起很怪。同一份诊断：工具的说明书塞进上下文太贵，每个提供工具的服务（后面统称 server）的认证还各搞一套。一家往外走，一家往里收。

同一个病，两家开的药看着相反，往下读你会发现砍的是同一刀：

![](https://pic2.zhimg.com/v2-dfb9ffeee6db19d250d78b85b9f7615f_r.jpg)

图 1｜同一个病，两家开的药正相反

往下读你会发现，两家砍的是同一刀：把工具声明从请求前缀里拿掉，一个搬到公司外，一个搬进运行时。

**MCP**：一套让 AI 连外部工具的通用接口标准，可以理解为插头，谁都能造。

**上下文**：AI 一次能装下的全部内容，位置有限，塞一样就挤掉另一样，按 token 计量和收费。

**沙箱**：给 AI 单独开的一间屋子，它在里面随便折腾，砸了也不影响外面。

这篇只回答一件事：**MCP 工具挂几个算贵**。答案不是工具数自己定的，是默认值定的。下面六节，一节搬一刀、一节算一笔账，最后一节给你一个能直接用的区间。

---

### 两家做的其实是同一件事

先看 Pi 那边。Mario 在 2025 年 11 月 2 日写过一篇《What if you don't need MCP at all?》，实测了两个主流 MCP server：Playwright MCP 的 21 个工具要吃掉 13.7k tokens，占 Claude 上下文的 6.8%；Chrome DevTools MCP 的 26 个工具 18.0k tokens，占 9.0%。他自己那套替代方案，一个 CLI 加一份 README，225 tokens。

十个月后他把 MCP 收进核心，很多人读成了「反对者投降」。我读完官方那篇说明，读到的是另外一层。

**第一，MCP 进核心，但默认档位是 `codemode`。** 在这个档位下模型根本看不见那些工具，工具只注册在沙箱里，脚本要用得自己去找。

**第二，他一句都没撤回原来的批评。** 原文里还写着：MCP 最大的问题仍然是难以组合，即便有了 codemode，MCP 也没有真正解决这一点。他还点了名，说很多 MCP server 至今还在为那种「把工具一股脑倒进上下文」的 harness 做设计。

**第三，他明说了为什么现在做。** 不完美也做，是想在用的同时推动生态往更结构化、更易组合的方向走。

**第四，也是最关键的一条，官方自己把性质挑明了。** 原文说：Pi 有一套不错的扩展生态，MCP 本来完全可以只做个扩展，事实上之前就是这样（社区里就有人做过 adapter）。它现在进核心，是他们坐下来重新想过之后的结果。

**禁掉用法，保留接口。协议留下了，权力拿走了。** 工具声明还在，只是不摆在模型面前了。

再看 Perplexity 那边。它的诊断跟 Pi 完全一样：工具 schema 塞进上下文太贵，认证各搞一套。它的做法是把声明整个撤出去，工具自己实现，每家一整套 REST API 加 CLI，对外只留一个端点一个 key。

两条路摆在一起，动作是同一个：**把工具声明挪出请求前缀**。区别只在于挪到哪儿——挪进 Pi 的运行时沙箱，还是挪进 Perplexity 自己公司。

**这个位置默认给不给，比这个协议支不支持重要得多。** 后面三节的账，都是这句话算出来的。

### 拿掉之后还剩四个开关

用大白话讲 codemode 是什么：模型不再一个个调工具，而是写一段 JavaScript，脚本里并行调十几个工具、过滤掉中间结果，只把蒸馏后的那一小段结果送回上下文。

三个细节值得记。**执行位置**：Pi 里有两层能跑东西的地方，一层是 bash 那种隔离较弱的沙箱，一层是 harness 循环里的受信环境，codemode 跑在后者，权限更高，才需要单独管。**状态放哪**：中间结果存在会话 transcript 里，不落文件系统。**为什么是 JS**：小体积的 JS 能编译成 WASM 二进制，隔离成本可控。

这次改动真正的产品形态是四档 exposure（以 Pi 0.99.2 官方 `docs/mcp.md` 为准）：

| 档位 | 行为 | 适合 |
| --- | --- | --- |
| codemode（默认） | 脚本可调用；既不声明给模型，也不列进 codemode 描述。脚本用 searchTools() / describeTool() / ALL_TOOLS 找 | 一般 MCP server，尤其需要脚本组合过滤时 |
| deferred | 直到 tool_search 命中才声明给模型 | 大型 server，发现后直接调用 |
| direct | 像内置工具一样声明给模型，codemode 里也能调 | 小、高频工具集 |
| hidden | 注册了但够不着 | 该保持不可用的 |

（`codemode-deferred` 在 0.99.2 已降为 `codemode` 的别名，很多教程还在当独立档位讲，那是 0.99.0 的旧说法。我这篇核对的是官方包内的文档。）

四个档位，就是四个「默认给不给」的位置。选一个，你的工具成本曲线就长成另一个形状：

![](https://pica.zhimg.com/v2-daa7ed43c9a4928a230204b6c0d9670c_r.jpg)

图 2｜同一份工具，选了哪一档，账就是两种长法

（第四档 `deferred`：命中了才声明给模型，适合大 server；命中之后跟 direct 一样直接调。）

下面这三档是我自己跑出来的，上一节那两种成本形状就是这么来的。

### 我把这笔账算了两遍

说机制容易空谈，我装了 Pi 0.99.2 自己跑了一遍。

为了让工具数可控、且不受网络和第三方 server 影响，我写了个零依赖的 MCP server，工具数可调，单个工具描述固定 900 字符。模型用本地 Ollama 上的 qwen3.8:27b-mlx，机器是 M5 Pro / 48GB。每轮只发一句「只回一个单词：OK」（原文 `Reply with the single word: OK`），测的就是**光把工具挂上要吃掉多少 token**，跟任务本身无关。

### 第一笔账：codemode 是租金，direct 是按量付费

不接任何 server 时，prompt 是 7,926 tokens，这是基线。接上之后：

| MCP 工具数 | codemode | direct |
| --- | --- | --- |
| 5 | 10,239 | 9,448 |
| 10 | 10,238 | 10,967 |
| 20 | 10,240 | 14,018 |
| 60 | 10,239 | 26,216 |

codemode 是一条水平线。工具从 5 涨到 60，涨了 11 倍，四个读数是 10,239 / 10,238 / 10,240 / 10,239，**最大偏差 2 个 token**，在非零 nonce 抖动的量级里可以视为完全持平。

direct 是一条斜线。同样从 5 涨到 60，从 9,448 到 26,216，涨了 177%。拟合下来单工具边际成本 305 tokens，公式 `7,926 + 305n` 在四个点上误差都在 0.1% 以内。

这里有个必须先自己说破的事实：**codemode 不免费。** 基线 7,926，接上 codemode 变成约 10,239，这 2,313 tokens 是固定租金（codemode 工具自身的描述 + 系统提示里的 `mcp_servers` 段），跟接多少工具无关。准确的说法是：**codemode 把一笔随工具数线性增长的成本，换成了一笔固定租金。**

租金和按量付费之间必然有个交叉点，这个数官方没给，我算了一下：`2,313 ÷ 305 ≈ 7.6`。

而且这个 7.6 是被实测两侧夹住的：n=5 时 direct 是 9,448，比 codemode 的 10,239 **更省**；n=10 时 direct 涨到 10,967，反过来比 codemode 的 10,238 **更贵**。临界点确实落在 5 和 10 之间，跟公式对上了。Pi 文档那句「direct 适合小的高频工具集」，从此有个能算、也量过的阈值。

⚠️ **但这个 7.6 还不能拿去直接用，有两个前提要说清。**

第一，**我的 mock 工具描述偏短。** 单工具 900 字符，折 305 tokens；而 Mario 实测的 Playwright MCP 是 13.7k tokens / 21 个工具，折约 652 tokens 一个，差了一倍多。按真实描述长度重算，`2,313 ÷ 652 ≈ 3.5`。所以真实场景里这个临界点大概率落在 **3 到 8 之间**，取决于你的工具描述有多啰嗦。

第二，**我变的是同一个 server 里的工具数，没测多个 server 并联。** 按官方机制，codemode 下每个 server 只在系统提示里占一个命名空间条目，增长应该远小于 direct 的 305 tokens/工具，但这条我没实测，标为推断。

另外官方还留了一道闸：`codemode.inlineBudget` 默认 3000 估算 tokens，描述放不下的工具不列进描述，改用 `searchTools()` 检索。说明他们自己也在防这个段膨胀。

**到这里，标题里那个数就有了：3 到 8 个，取决于你的工具描述有多啰嗦。** 但只算这一笔账会把人带沟里，因为第二笔账更贵。

### 第二笔账：真正打穿的不是 token，是缓存

Pi 0.99.2 的文档写得挺直白：工具清单挂在系统提示的 `mcp_servers` 段，这段变化时，Pi 把新段**追加到对话末尾，不去改工具声明**，原文给的理由是「这样早先的消息能保持缓存」。

配套的几处细节全是同一个动机：codemode 描述不再包含工具数和 server 指令，因为它不能随 server 连接而变；`tool_search` 描述也不再列出它能加载哪些 server；第一条 prompt 不再等待没有 `direct` 工具的 server。

翻成大白话：**工具声明住在请求前缀里，前缀一变，前面缓存的 token 全废。**

我把这句话做成了实验。同一个 session 连跑四轮，前三轮 codemode，第四轮只把 exposure 改成 direct，别的什么都不动。

看这张表之前先记住一件事：AI 每回答一句，都要把前面说过的话重新读一遍。读过的部分如果对得上就能跳过，这叫缓存命中；对不上就得整段重读。「缓存命中」那一列越高越好，它代表的是**这一次有多少内容不用重新读**：

| 轮 | exposure | 新算 tokens | 缓存命中 | 该轮耗时（仅供旁证） |
| --- | --- | --- | --- | --- |
| r1 | codemode | 422 | 10,515 | 97.8s |
| r2 | codemode | 19 | 10,985 | 22.4s |
| r3 | codemode | 19 | 11,039 | 2.3s |
| r4 | direct | 14,763 | 113 ⬇️ | 57.4s |
| r5 | direct（第二轮） | 11,139 | 2 | — |
| r6 | direct（第三轮） | 11,184 | 0 | — |

到 r3，一万多 token 的 prompt 里只有 19 个是新算的，其余全部命中缓存。改一个配置，缓存命中从 **11,039 崩到 113**，缓存命中从 99% 掉到 1% 以内，一万多个 token 得整个重算一遍。

画成条形看，形状比数字更直接：

![](https://pic1.zhimg.com/v2-1662cc411fb72ece7189df06b88cc6de_r.jpg)

图 3｜同一个会话连跑六轮，画成条形看缓存怎么塌的

r4 那个 113 值得解释一下：它不是 0，因为系统提示最开头那一小段（跟工具无关的部分）还在前缀里，还能命中；工具声明一进前缀，后面就全断了。

关键不在省了多少 token，在还能不能复用。

⚠️ 耗时那一列别当结论看。本机同时还在跑别的东西，MLX 负载不稳，同一配置两次跑能差出一倍，口径声明五里已经声明过它不进结论。要引的是 token 那一列。

我接着又补跑两轮，r5、r6，配置跟 r4 一模一样，只有那一句话不同。**r5 新算 11,139，r6 新算 11,184，两轮只差 45，不到 0.4%**，而缓存命中都掉到个位（2 和 0）。这就把一件事分开了：**在这台 Ollama 上，direct 打穿缓存不是改配置那一下的余波，是之后每一轮都要付的账。** r4 那个 14,763 里确实含着一次性成分（第一次把工具声明灌进前缀那一回），但垫在它下面的那 1.1 万，是后面躲不掉的。codemode 的稳态则是 19：r2、r3 都是 19，第三轮还是 19。

这句得自己把边界说破。我跑的是两轮，二十轮没跑：这两轮够用来把 r4 的一次性重算和之后的稳态分开，也够说明本机 Ollama 上 direct 之后不再回血；但不够用来概括任何一家别家的运行时。换运行时重测，这个 1.1 万得从头量一遍。

⚠️ 补测中有两条得交代。一是 r6 对 r5 的缓存一个都没命中，我没查清 Ollama 在本机按什么规则留前缀缓存（可能是过期时间，也可能它只留最后一段），这个数字我不解释，只用了「r5 和 r6 两次读数贴得极近」这个事实。二是这六轮中间隔了约四十分钟，卡在一道 credential 锁上，期间本机缓存早就冷掉了，r5 属于冷启动读数；这不影响 r5 和 r6 之间的对照，那两轮是紧挨着跑完的。那四十分钟卡在什么问题上的完整过程，我写在文末口径声明五里，绕锁花掉的开销不进本文任何一个数。

### 官方自己也在一天内踩了这个坑

版本记录更有意思：2026-09-29 的 v0.99.0 把工具列在 codemode 描述里，2026-09-30 的 v0.99.2（issue #10212）就改了，工具移出描述，改挂系统提示段加 `searchTools()` 发现。

一天。说明「列表进描述」这个做法上线就暴露了问题：server 一连上来描述就变，缓存就废。方向是对的，落地细节才是真战场。

**两笔账算完了，代价分别落在哪一刻：挂载那一次付 305/工具，之后每一轮付 1.1 万。前一节还能用数算，后一节已经不是钱的事了。**

### 我在开放平台付过这笔账

第二笔账不是模型理论知识，我在这上面真交过学费。

我做过两段开放平台：一个办公 IM 的开放生态，做到几百个接入应用；一个权限开放平台，一周要扛十亿次鉴权。当年我以为这活最难的是把能力接进来，干完才发现最难的是放下自己那套设计，去看客户真实的样子。

做第二个平台时，我对公司里账号体系和权限体系有多乱是有心理准备的。MVP 出来之后去找业务方调研，还是被打脸，我准备得远远不够。

我一开始的路子是尽量抽象，希望每种客户都能把他个性化的逻辑迁进来。真去聊才发现，奇奇怪怪的设计方案比我预想的多得多。里面有一小部分是就我见识不够，有些技术方案压根不了解；更多的跟技术无关，是他们的方案针对自己的业务写死了，不愿意通用化。

后者又分两种。一种是我的方案对他们属于降维打击，换过来还有额外收益。这种好办。

另一种是他们的权限体系耦合了太多业务逻辑，而且他们不认为这是问题。这就变成产品立场和业务立场的对撞：从产品立场看，写死的个性化逻辑是给以后挖坑，必须改；从业务立场看，当下这套最好用，换成我的方案，相当长一段时间里他们是负收益。

那轮调研给我最大的教训就一句话：**别陷在自我感动里。** 你以为你在做一套优雅的通用抽象，客户要的是另一件事。

**在客户眼里，开放平台最大的价值只有一个：你开放出来的那部分能力，能不能替他干掉高频、重复的执行类工作，让他降低经营成本。** 抽象得漂不漂亮，不在他的账本上。

「能力开放出去收不回来」这种事，我印象里没真出过。这跟运气无关，是我在开放这件事上一直比较严。反倒是我周围的人比我急：研发和业务都催，觉得我死脑筋，我认为是个性化需求的东西，他们觉得「先加上再说」。

回头看，「收不回来」的种子恰恰是在那一刻种下的。**不是后面治理得不好，是第一下默认给得太松。** 你今天为了省事答应「先加上」，明天就得为了兼容把它一直养着。

这句话跟 Pi 这次的四档能对上：

| Pi 的档位 | 开放平台里的对应做法 |
| --- | --- |
| direct（默认看得见） | 「先加上再说」 |
| codemode（默认看不见，要用自己找） | 「先不给，你要用你来要」 |
| hidden（注册了但够不着） | 有些能力必须存在，但不能让所有人看见 |

`hidden` 这一档我在开放平台里真留过。三种默认值，三种组织性格。

还有一个我至今还认的原则：**好的开放平台应该是网状的，能灵活调整；别做成树状，树状一旦长成就不好改。** MCP 现在就是树：一个 server 挂一堆 tools。你想跨 server 组合，就得把两边的工具都倒进上下文，再让模型在自己脑子里拼。Pi 那句「组合问题没解决」，说的就是这个形状没变。codemode 给脚本开了跨 server 调用的口子，但工具本身还是挂在各自的 server 下面，树还在。

我挺欣赏 DSH 那套「一切皆插件」的做法：能力不写死在主程序里，挂进来就成默认，默认值由插件自己声明、由平台决定给不给。我自己在做的那个本地 agent 网关也是这个思路，插件只是目录里的一个条目，主程序里不留代码。这跟我当年那两代开放平台是反着来的：当年是我坐在中间猜客户要什么，现在改由插件自己说要什么，我来定给不给。这一套的设计思路我以后单独写一篇讲，这里只挂一句到今天的题上：**默认值到底该由谁给**。Pi 和 MCP 替你定了「工具默认给不给」，我当年那笔学费也是买在这一格上。

至于我实测里那条平线，成因其实更朴素：codemode 下工具声明压根不进请求前缀，所以工具数跟 prompt 长度脱钩了。这是声明侧的账，跟组合能力是两件事，别混着读。

**默认值这个决定权，我当年是按人拍板、按文档约束、靠事后审计，磨了好几年才成形。它在 Pi 里被写成了运行时的一行配置。** 我那笔学费，是拿组织里的几年时间付的。

现在回到第一节那个问题：Pi 把 MCP 从扩展挪进核心，动机跟我是同一类。都是在问「这个位置我要不要占」。

### 谁占着那个位置

这一节底下有三个词：天、地、人。跟 Pi 和 MCP 官方那套分层没关系，是我借《易传》那三层的说法和现代系统论的分层，拼出来的一套看系统坐标，只用来把前面几节的数归位，不展开。坐标先摆在这儿，下面三段看着才不像硬套。

官方那篇说明里有一句很容易被滑过去的话：这次对 MCP 的改动，也让 Jev 更容易在 Pi 里用起来。后面还有一句更直白的：**Pi 需要的和 MCP 需要的本质上一样，一个可以玩耍的沙箱，形式是一个解释器。**

Jev 是 TypeSafe AI 2026-09-15 发布的 System One 决策模型，70 到 500 毫秒出判定，创始人是 Diogo Almeida（前 OpenAI，InstructGPT 一作）。这个模型本身是什么、为什么快、跟生成模型的差别在哪，我在 [让英雄去查英雄，是 AI 时代最容易犯的架构错误](https://mp.weixin.qq.com/s?__biz=MzIwMzE0ODMzNQ==&mid=2650613920&idx=1&sn=e31007a6699c5c964698b55654e04333&scene=21#wechat_redirect) 那篇里拆过，这里不重复，只占它跟沙箱之间那一段位置。

Pi 的 codemode 沙箱里除了 `store()` / `load()`，直接给了 `models.classify()`，就是给这类判别模型留的位置。官方举的例子是组合 Linear MCP 和 Jev，找出 issue 区里最不满的 20 个评论者。

拆开看：**慢活交给脚本，快判断交给决策模型，中间结果不进上下文。** 这不只是一个工具技巧，快慢分工被写进了运行时。

但要说清楚主次：**Jev 是被顺带接进来的乘客，沙箱才是司机。** 官方那句话的重点在后半句，他们要的是「一个解释器」。把这次改动读成「Jev 赢了」，就读反了。

把前面几节的数归到这三个位置，你可以拿我那张表自己复核，顺便看每一层是不是真的多出了点什么。

**天**是物理上限那一层。codemode 从 5 个工具挂到 60 个，prompt 始终停在 10,239 上下，direct 从 9,448 涨到 26,216；官方 `inlineBudget` 默认 3000，超了改用 `searchTools()`。这件事卡不卡得住，不看你有多少工具，看你把它们放在哪一层。

**地**是控制点换手那一层，换手当场就有价：同一会话里把 exposure 从 codemode 改到 direct，缓存命中从 99% 掉到 1% 以内，一万多 token 得整段重算。协议标准谁定都在往下贬值，值钱的是**谁来提供那个能跑脚本的房间**，这一格的代价最后落到用这个运行时的人身上。

**人**是心智换没换那一层，也是三层里唯一一条前面几节没说完的：开发者要从「装一个 MCP server」换成「给 agent 一个能写代码的房间」，中间隔着一次默认值移交。这次四档可见性没进文档，直接进了运行时的默认配置，**你选运行时，就等于选了它替你定好的那套可见性默认值。**

**最后回到两家谁对。** 我的答案是谁掌握沙箱谁对，但这句话得补半句才成立：Perplexity 也掌握沙箱，它只是把复杂度搬进了自己公司内部那个不对外开放的沙箱；Pi 的沙箱则允许任何人的 server 进来。两家都占了位置，区别在开放度：前者是自己的成本工具，后者是别人的生态底座。协议谁都能实现，能长东西的沙箱不是。这两句是判断，不是这轮实测量出来的。

网上那个被转得很广的「MCP 吃掉 72% 上下文」，出自 Apideck 的分析，不是 Perplexity 自己审计出来的数，转的人多半当成了官方口径。Anthropic 那组 15 万降到 2 千、Cloudflare 那组 1.17M 降到 1 千，也别跟它并排比。一个按 token 算，一个按任务算。

### 三条能直接用的动作

1. **先看你手上的运行时有没有这一档。** Pi 默认就是 codemode，多数别的 MCP 客户端没有这层，只有 direct 一种挂法。如果你的客户端只有 direct，这档跟你不构成选择，3 到 8 这条线跟你无关，得按你自己的客户端重跑一遍。确认有得选，再往下数工具数：**少于 3 个、描述又极短，`direct` 更省；超过 8 个、描述啰嗦的，别用 `direct` 当默认。**中间那段（3 到 8 个）是个灰区，按你的描述长度往两头挪。临界点的算法是固定的：用你的单工具 token 数去除那 2,313 的固定租金。
2. **把默认值当成合同看，别当成配置看。** 你选的运行时替你定好了「工具默认给不给模型」，这一格换不回来，我第四节的学费就是交在这儿。换运行时之前先问：它默认给不给？给了多少？这是一次性决定，事后改动的代价比首次选对高得多。
3. **高频小判断尽早剥出去。** 这件事我自己落地过一次：在内容审核里把最高频的那类判定交给模型去做，审核周期从 4 天压到 1.5 天，折算下来省了大约三个人一个月的人工。当年靠的是架构自觉，现在运行时开始替你把这件事做成默认值。不做的会被成本差甩开，慢一点，但方向确定。

顺便把这三条的边界摆明：它们算的都是**挂载账**。真下场算总成本，还得把输出 token、工具调用往返、失败重试、沙箱执行和换运行时的迁移成本加进去，这几项这轮没测，不在任何一个数里。

最后补一句我自己的情况。这一年我在家做代理工具，从多模型路由一路往编排层长，形状跟上面几节很像，我也隐隐觉得它以后可能长成点什么，只是现在还说不清往哪走。差的不在技术上：当年那个平台是长在一家公司里的，技术支持、业务方、客户都现成，我去调研有人接待，判断错了也有人接住；现在这些东西一样都没有，找谁问、找谁用、对错算谁的，全是我一个人的事。

同一个形状，一个长在组织身上，一个长在自己身上。落到我这儿，今年真正要解决的是同一件事：这个位置的默认值，让不让别人往里长。当年这事是被组织替我决定的，现在轮到我一个人拍，拍完也没人替我兜。

往下读你会发现，两家砍的是同一刀：把工具声明从请求前缀里拿掉，一个搬到公司外，一个搬进运行时。

**MCP**：一套让 AI 连外部工具的通用接口标准，可以理解为插头，谁都能造。

**上下文**：AI 一次能装下的全部内容，位置有限，塞一样就挤掉另一样，按 token 计量和收费。

**沙箱**：给 AI 单独开的一间屋子，它在里面随便折腾，砸了也不影响外面。

这篇只回答一件事：**MCP 工具挂几个算贵**。答案不是工具数自己定的，是默认值定的。下面六节，一节搬一刀、一节算一笔账，最后一节给你一个能直接用的区间。

### 两家做的其实是同一件事

先看 Pi 那边。Mario 在 2025 年 11 月 2 日写过一篇《What if you don't need MCP at all?》，实测了两个主流 MCP server：Playwright MCP 的 21 个工具要吃掉 13.7k tokens，占 Claude 上下文的 6.8%；Chrome DevTools MCP 的 26 个工具 18.0k tokens，占 9.0%。他自己那套替代方案，一个 CLI 加一份 README，225 tokens。

十个月后他把 MCP 收进核心，很多人读成了「反对者投降」。我读完官方那篇说明，读到的是另外一层。

**第一，MCP 进核心，但默认档位是 `codemode`。** 在这个档位下模型根本看不见那些工具，工具只注册在沙箱里，脚本要用得自己去找。

**第二，他一句都没撤回原来的批评。** 原文里还写着：MCP 最大的问题仍然是难以组合，即便有了 codemode，MCP 也没有真正解决这一点。他还点了名，说很多 MCP server 至今还在为那种「把工具一股脑倒进上下文」的 harness 做设计。

**第三，他明说了为什么现在做。** 不完美也做，是想在用的同时推动生态往更结构化、更易组合的方向走。

**第四，也是最关键的一条，官方自己把性质挑明了。** 原文说：Pi 有一套不错的扩展生态，MCP 本来完全可以只做个扩展，事实上之前就是这样（社区里就有人做过 adapter）。它现在进核心，是他们坐下来重新想过之后的结果。

**禁掉用法，保留接口。协议留下了，权力拿走了。** 工具声明还在，只是不摆在模型面前了。

再看 Perplexity 那边。它的诊断跟 Pi 完全一样：工具 schema 塞进上下文太贵，认证各搞一套。它的做法是把声明整个撤出去，工具自己实现，每家一整套 REST API 加 CLI，对外只留一个端点一个 key。

两条路摆在一起，动作是同一个：**把工具声明挪出请求前缀**。区别只在于挪到哪儿——挪进 Pi 的运行时沙箱，还是挪进 Perplexity 自己公司。

**这个位置默认给不给，比这个协议支不支持重要得多。** 后面三节的账，都是这句话算出来的。

### 拿掉之后还剩四个开关

用大白话讲 codemode 是什么：模型不再一个个调工具，而是写一段 JavaScript，脚本里并行调十几个工具、过滤掉中间结果，只把蒸馏后的那一小段结果送回上下文。

三个细节值得记。**执行位置**：Pi 里有两层能跑东西的地方，一层是 bash 那种隔离较弱的沙箱，一层是 harness 循环里的受信环境，codemode 跑在后者，权限更高，才需要单独管。**状态放哪**：中间结果存在会话 transcript 里，不落文件系统。**为什么是 JS**：小体积的 JS 能编译成 WASM 二进制，隔离成本可控。

这次改动真正的产品形态是四档 exposure（以 Pi 0.99.2 官方 `docs/mcp.md` 为准）：

| 档位 | 行为 | 适合 |
| --- | --- | --- |
| codemode（默认） | 脚本可调用；既不声明给模型，也不列进 codemode 描述。脚本用 searchTools() / describeTool() / ALL_TOOLS 找 | 一般 MCP server，尤其需要脚本组合过滤时 |
| deferred | 直到 tool_search 命中才声明给模型 | 大型 server，发现后直接调用 |
| direct | 像内置工具一样声明给模型，codemode 里也能调 | 小、高频工具集 |
| hidden | 注册了但够不着 | 该保持不可用的 |

（`codemode-deferred` 在 0.99.2 已降为 `codemode` 的别名，很多教程还在当独立档位讲，那是 0.99.0 的旧说法。我这篇核对的是官方包内的文档。）

四个档位，就是四个「默认给不给」的位置。选一个，你的工具成本曲线就长成另一个形状：

![](https://pica.zhimg.com/v2-daa7ed43c9a4928a230204b6c0d9670c_r.jpg)

图 2｜同一份工具，选了哪一档，账就是两种长法

（第四档 `deferred`：命中了才声明给模型，适合大 server；命中之后跟 direct 一样直接调。）

### 我把这笔账算了两遍

说机制容易空谈，我装了 Pi 0.99.2 自己跑了一遍。

为了让工具数可控、且不受网络和第三方 server 影响，我写了个零依赖的 MCP server，工具数可调，单个工具描述固定 900 字符。模型用本地 Ollama 上的 qwen3.8:27b-mlx，机器是 M5 Pro / 48GB。每轮只发一句「只回一个单词：OK」（原文 `Reply with the single word: OK`），测的就是**光把工具挂上要吃掉多少 token**，跟任务本身无关。

### 第一笔账：codemode 是租金，direct 是按量付费

不接任何 server 时，prompt 是 7,926 tokens，这是基线。接上之后：

| MCP 工具数 | codemode | direct |
| --- | --- | --- |
| 5 | 10,239 | 9,448 |
| 10 | 10,238 | 10,967 |
| 20 | 10,240 | 14,018 |
| 60 | 10,239 | 26,216 |

codemode 是一条水平线。工具从 5 涨到 60，涨了 11 倍，四个读数是 10,239 / 10,238 / 10,240 / 10,239，**最大偏差 2 个 token**，在非零 nonce 抖动的量级里可以视为完全持平。

direct 是一条斜线。同样从 5 涨到 60，从 9,448 到 26,216，涨了 177%。拟合下来单工具边际成本 305 tokens，公式 `7,926 + 305n` 在四个点上误差都在 0.1% 以内。

这里有个必须先自己说破的事实：**codemode 不免费。** 基线 7,926，接上 codemode 变成约 10,239，这 2,313 tokens 是固定租金（codemode 工具自身的描述 + 系统提示里的 `mcp_servers` 段），跟接多少工具无关。准确的说法是：**codemode 把一笔随工具数线性增长的成本，换成了一笔固定租金。**

租金和按量付费之间必然有个交叉点，这个数官方没给，我算了一下：`2,313 ÷ 305 ≈ 7.6`。

而且这个 7.6 是被实测两侧夹住的：n=5 时 direct 是 9,448，比 codemode 的 10,239 **更省**；n=10 时 direct 涨到 10,967，反过来比 codemode 的 10,238 **更贵**。临界点确实落在 5 和 10 之间，跟公式对上了。Pi 文档那句「direct 适合小的高频工具集」，从此有个能算、也量过的阈值。

⚠️ **但这个 7.6 还不能拿去直接用，有两个前提要说清。**

第一，**我的 mock 工具描述偏短。** 单工具 900 字符，折 305 tokens；而 Mario 实测的 Playwright MCP 是 13.7k tokens / 21 个工具，折约 652 tokens 一个，差了一倍多。按真实描述长度重算，`2,313 ÷ 652 ≈ 3.5`。所以真实场景里这个临界点大概率落在 **3 到 8 之间**，取决于你的工具描述有多啰嗦。

第二，**我变的是同一个 server 里的工具数，没测多个 server 并联。** 按官方机制，codemode 下每个 server 只在系统提示里占一个命名空间条目，增长应该远小于 direct 的 305 tokens/工具，但这条我没实测，标为推断。

另外官方还留了一道闸：`codemode.inlineBudget` 默认 3000 估算 tokens，描述放不下的工具不列进描述，改用 `searchTools()` 检索。说明他们自己也在防这个段膨胀。

**到这里，标题里那个数就有了：3 到 8 个，取决于你的工具描述有多啰嗦。** 但只算这一笔账会把人带沟里，因为第二笔账更贵。

### 第二笔账：真正打穿的不是 token，是缓存

Pi 0.99.2 的文档写得挺直白：工具清单挂在系统提示的 `mcp_servers` 段，这段变化时，Pi 把新段**追加到对话末尾，不去改工具声明**，原文给的理由是「这样早先的消息能保持缓存」。

配套的几处细节全是同一个动机：codemode 描述不再包含工具数和 server 指令，因为它不能随 server 连接而变；`tool_search` 描述也不再列出它能加载哪些 server；第一条 prompt 不再等待没有 `direct` 工具的 server。

翻成大白话：**工具声明住在请求前缀里，前缀一变，前面缓存的 token 全废。**

我把这句话做成了实验。同一个 session 连跑四轮，前三轮 codemode，第四轮只把 exposure 改成 direct，别的什么都不动。

看这张表之前先记住一件事：AI 每回答一句，都要把前面说过的话重新读一遍。读过的部分如果对得上就能跳过，这叫缓存命中；对不上就得整段重读。「缓存命中」那一列越高越好，它代表的是**这一次有多少内容不用重新读**：

| 轮 | exposure | 新算 tokens | 缓存命中 | 该轮耗时（仅供旁证） |
| --- | --- | --- | --- | --- |
| r1 | codemode | 422 | 10,515 | 97.8s |
| r2 | codemode | 19 | 10,985 | 22.4s |
| r3 | codemode | 19 | 11,039 | 2.3s |
| r4 | direct | 14,763 | 113 ⬇️ | 57.4s |
| r5 | direct（第二轮） | 11,139 | 2 | — |
| r6 | direct（第三轮） | 11,184 | 0 | — |

到 r3，一万多 token 的 prompt 里只有 19 个是新算的，其余全部命中缓存。改一个配置，缓存命中从 **11,039 崩到 113**，缓存命中从 99% 掉到 1% 以内，一万多个 token 得整个重算一遍。

画成条形看，形状比数字更直接：

![](https://pic1.zhimg.com/v2-1662cc411fb72ece7189df06b88cc6de_r.jpg)

图 3｜同一个会话连跑六轮，画成条形看缓存怎么塌的

r4 那个 113 值得解释一下：它不是 0，因为系统提示最开头那一小段（跟工具无关的部分）还在前缀里，还能命中；工具声明一进前缀，后面就全断了。

关键不在省了多少 token，在还能不能复用。

⚠️ 耗时那一列别当结论看。本机同时还在跑别的东西，MLX 负载不稳，同一配置两次跑能差出一倍，口径声明五里已经声明过它不进结论。要引的是 token 那一列。

我接着又补跑两轮，r5、r6，配置跟 r4 一模一样，只有那一句话不同。**r5 新算 11,139，r6 新算 11,184，两轮只差 45，不到 0.4%**，而缓存命中都掉到个位（2 和 0）。这就把一件事分开了：**在这台 Ollama 上，direct 打穿缓存不是改配置那一下的余波，是之后每一轮都要付的账。** r4 那个 14,763 里确实含着一次性成分（第一次把工具声明灌进前缀那一回），但垫在它下面的那 1.1 万，是后面躲不掉的。codemode 的稳态则是 19：r2、r3 都是 19，第三轮还是 19。

这句得自己把边界说破。我跑的是两轮，二十轮没跑：这两轮够用来把 r4 的一次性重算和之后的稳态分开，也够说明本机 Ollama 上 direct 之后不再回血；但不够用来概括任何一家别家的运行时。换运行时重测，这个 1.1 万得从头量一遍。

⚠️ 补测中有两条得交代。一是 r6 对 r5 的缓存一个都没命中，我没查清 Ollama 在本机按什么规则留前缀缓存（可能是过期时间，也可能它只留最后一段），这个数字我不解释，只用了「r5 和 r6 两次读数贴得极近」这个事实。二是这六轮中间隔了约四十分钟，卡在一道 credential 锁上，期间本机缓存早就冷掉了，r5 属于冷启动读数；这不影响 r5 和 r6 之间的对照，那两轮是紧挨着跑完的。那四十分钟卡在什么问题上的完整过程，我写在文末口径声明五里，绕锁花掉的开销不进本文任何一个数。

### 官方自己也在一天内踩了这个坑

版本记录更有意思：2026-09-29 的 v0.99.0 把工具列在 codemode 描述里，2026-09-30 的 v0.99.2（issue #10212）就改了，工具移出描述，改挂系统提示段加 `searchTools()` 发现。

一天。说明「列表进描述」这个做法上线就暴露了问题：server 一连上来描述就变，缓存就废。方向是对的，落地细节才是真战场。

**两笔账算完了，代价分别落在哪一刻：挂载那一次付 305/工具，之后每一轮付 1.1 万。前一节还能用数算，后一节已经不是钱的事了。**

### 我在开放平台付过这笔账

第二笔账不是模型理论知识，我在这上面真交过学费。

我做过两段开放平台：一个办公 IM 的开放生态，做到几百个接入应用；一个权限开放平台，一周要扛十亿次鉴权。当年我以为这活最难的是把能力接进来，干完才发现最难的是放下自己那套设计，去看客户真实的样子。

做第二个平台时，我对公司里账号体系和权限体系有多乱是有心理准备的。MVP 出来之后去找业务方调研，还是被打脸，我准备得远远不够。

我一开始的路子是尽量抽象，希望每种客户都能把他个性化的逻辑迁进来。真去聊才发现，奇奇怪怪的设计方案比我预想的多得多。里面有一小部分是就我见识不够，有些技术方案压根不了解；更多的跟技术无关，是他们的方案针对自己的业务写死了，不愿意通用化。

后者又分两种。一种是我的方案对他们属于降维打击，换过来还有额外收益。这种好办。

另一种是他们的权限体系耦合了太多业务逻辑，而且他们不认为这是问题。这就变成产品立场和业务立场的对撞：从产品立场看，写死的个性化逻辑是给以后挖坑，必须改；从业务立场看，当下这套最好用，换成我的方案，相当长一段时间里他们是负收益。

那轮调研给我最大的教训就一句话：**别陷在自我感动里。** 你以为你在做一套优雅的通用抽象，客户要的是另一件事。

**在客户眼里，开放平台最大的价值只有一个：你开放出来的那部分能力，能不能替他干掉高频、重复的执行类工作，让他降低经营成本。** 抽象得漂不漂亮，不在他的账本上。

「能力开放出去收不回来」这种事，我印象里没真出过。这跟运气无关，是我在开放这件事上一直比较严。反倒是我周围的人比我急：研发和业务都催，觉得我死脑筋，我认为是个性化需求的东西，他们觉得「先加上再说」。

回头看，「收不回来」的种子恰恰是在那一刻种下的。**不是后面治理得不好，是第一下默认给得太松。** 你今天为了省事答应「先加上」，明天就得为了兼容把它一直养着。

这句话跟 Pi 这次的四档能对上：

| Pi 的档位 | 开放平台里的对应做法 |
| --- | --- |
| direct（默认看得见） | 「先加上再说」 |
| codemode（默认看不见，要用自己找） | 「先不给，你要用你来要」 |
| hidden（注册了但够不着） | 有些能力必须存在，但不能让所有人看见 |

`hidden` 这一档我在开放平台里真留过。三种默认值，三种组织性格。

还有一个我至今还认的原则：**好的开放平台应该是网状的，能灵活调整；别做成树状，树状一旦长成就不好改。** MCP 现在就是树：一个 server 挂一堆 tools。你想跨 server 组合，就得把两边的工具都倒进上下文，再让模型在自己脑子里拼。Pi 那句「组合问题没解决」，说的就是这个形状没变。codemode 给脚本开了跨 server 调用的口子，但工具本身还是挂在各自的 server 下面，树还在。

我挺欣赏 DSH 那套「一切皆插件」的做法：能力不写死在主程序里，挂进来就成默认，默认值由插件自己声明、由平台决定给不给。我自己在做的那个本地 agent 网关也是这个思路，插件只是目录里的一个条目，主程序里不留代码。这跟我当年那两代开放平台是反着来的：当年是我坐在中间猜客户要什么，现在改由插件自己说要什么，我来定给不给。这一套的设计思路我以后单独写一篇讲，这里只挂一句到今天的题上：**默认值到底该由谁给**。Pi 和 MCP 替你定了「工具默认给不给」，我当年那笔学费也是买在这一格上。

至于我实测里那条平线，成因其实更朴素：codemode 下工具声明压根不进请求前缀，所以工具数跟 prompt 长度脱钩了。这是声明侧的账，跟组合能力是两件事，别混着读。

**默认值这个决定权，我当年是按人拍板、按文档约束、靠事后审计，磨了好几年才成形。它在 Pi 里被写成了运行时的一行配置。** 我那笔学费，是拿组织里的几年时间付的。

现在回到第一节那个问题：Pi 把 MCP 从扩展挪进核心，动机跟我是同一类。都是在问「这个位置我要不要占」。

### 谁占着那个位置

这一节底下有三个词：天、地、人。跟 Pi 和 MCP 官方那套分层没关系，是我借《易传》那三层的说法和现代系统论的分层，拼出来的一套看系统坐标，只用来把前面几节的数归位，不展开。坐标先摆在这儿，下面三段看着才不像硬套。

官方那篇说明里有一句很容易被滑过去的话：这次对 MCP 的改动，也让 Jev 更容易在 Pi 里用起来。后面还有一句更直白的：**Pi 需要的和 MCP 需要的本质上一样，一个可以玩耍的沙箱，形式是一个解释器。**

Jev 是 TypeSafe AI 2026-09-15 发布的 System One 决策模型，70 到 500 毫秒出判定，创始人是 Diogo Almeida（前 OpenAI，InstructGPT 一作）。这个模型本身是什么、为什么快、跟生成模型的差别在哪，我在 [让英雄去查英雄，是 AI 时代最容易犯的架构错误](https://mp.weixin.qq.com/s?__biz=MzIwMzE0ODMzNQ==&mid=2650613920&idx=1&sn=e31007a6699c5c964698b55654e04333&scene=21#wechat_redirect) 那篇里拆过，这里不重复，只占它跟沙箱之间那一段位置。

Pi 的 codemode 沙箱里除了 `store()` / `load()`，直接给了 `models.classify()`，就是给这类判别模型留的位置。官方举的例子是组合 Linear MCP 和 Jev，找出 issue 区里最不满的 20 个评论者。

拆开看：**慢活交给脚本，快判断交给决策模型，中间结果不进上下文。** 这不只是一个工具技巧，快慢分工被写进了运行时。

但要说清楚主次：**Jev 是被顺带接进来的乘客，沙箱才是司机。** 官方那句话的重点在后半句，他们要的是「一个解释器」。把这次改动读成「Jev 赢了」，就读反了。

把前面几节的数归到这三个位置，你可以拿我那张表自己复核，顺便看每一层是不是真的多出了点什么。

**天**是物理上限那一层。codemode 从 5 个工具挂到 60 个，prompt 始终停在 10,239 上下，direct 从 9,448 涨到 26,216；官方 `inlineBudget` 默认 3000，超了改用 `searchTools()`。这件事卡不卡得住，不看你有多少工具，看你把它们放在哪一层。

**地**是控制点换手那一层，换手当场就有价：同一会话里把 exposure 从 codemode 改到 direct，缓存命中从 99% 掉到 1% 以内，一万多 token 得整段重算。协议标准谁定都在往下贬值，值钱的是**谁来提供那个能跑脚本的房间**，这一格的代价最后落到用这个运行时的人身上。

**人**是心智换没换那一层，也是三层里唯一一条前面几节没说完的：开发者要从「装一个 MCP server」换成「给 agent 一个能写代码的房间」，中间隔着一次默认值移交。这次四档可见性没进文档，直接进了运行时的默认配置，**你选运行时，就等于选了它替你定好的那套可见性默认值。**

**最后回到两家谁对。** 我的答案是谁掌握沙箱谁对，但这句话得补半句才成立：Perplexity 也掌握沙箱，它只是把复杂度搬进了自己公司内部那个不对外开放的沙箱；Pi 的沙箱则允许任何人的 server 进来。两家都占了位置，区别在开放度：前者是自己的成本工具，后者是别人的生态底座。协议谁都能实现，能长东西的沙箱不是。这两句是判断，不是这轮实测量出来的。

网上那个被转得很广的「MCP 吃掉 72% 上下文」，出自 Apideck 的分析，不是 Perplexity 自己审计出来的数，转的人多半当成了官方口径。Anthropic 那组 15 万降到 2 千、Cloudflare 那组 1.17M 降到 1 千，也别跟它并排比。一个按 token 算，一个按任务算。

### 三条能直接用的动作

1. **先看你手上的运行时有没有这一档。** Pi 默认就是 codemode，多数别的 MCP 客户端没有这层，只有 direct 一种挂法。如果你的客户端只有 direct，这档跟你不构成选择，3 到 8 这条线跟你无关，得按你自己的客户端重跑一遍。确认有得选，再往下数工具数：**少于 3 个、描述又极短，`direct` 更省；超过 8 个、描述啰嗦的，别用 `direct` 当默认。**中间那段（3 到 8 个）是个灰区，按你的描述长度往两头挪。临界点的算法是固定的：用你的单工具 token 数去除那 2,313 的固定租金。
2. **把默认值当成合同看，别当成配置看。** 你选的运行时替你定好了「工具默认给不给模型」，这一格换不回来，我第四节的学费就是交在这儿。换运行时之前先问：它默认给不给？给了多少？这是一次性决定，事后改动的代价比首次选对高得多。
3. **高频小判断尽早剥出去。** 这件事我自己落地过一次：在内容审核里把最高频的那类判定交给模型去做，审核周期从 4 天压到 1.5 天，折算下来省了大约三个人一个月的人工。当年靠的是架构自觉，现在运行时开始替你把这件事做成默认值。不做的会被成本差甩开，慢一点，但方向确定。

顺便把这三条的边界摆明：它们算的都是**挂载账**。真下场算总成本，还得把输出 token、工具调用往返、失败重试、沙箱执行和换运行时的迁移成本加进去，这几项这轮没测，不在任何一个数里。

最后补一句我自己的情况。这一年我在家做代理工具，从多模型路由一路往编排层长，形状跟上面几节很像，我也隐隐觉得它以后可能长成点什么，只是现在还说不清往哪走。差的不在技术上：当年那个平台是长在一家公司里的，技术支持、业务方、客户都现成，我去调研有人接待，判断错了也有人接住；现在这些东西一样都没有，找谁问、找谁用、对错算谁的，全是我一个人的事。

同一个形状，一个长在组织身上，一个长在自己身上。落到我这儿，今年真正要解决的是同一件事：这个位置的默认值，让不让别人往里长。当年这事是被组织替我决定的，现在轮到我一个人拍，拍完也没人替我兜。

- ⚠️ 口径声明二（2026-10-05 订正）：**codemode 的 5 / 10 / 20 / 60 四档均为本机实测，对应正文第一笔账那张表。** 交叉点 7.6 是实测夹出来的：n=5 时 direct 更省，n=10 时 direct 更贵，它就落在这两点之间。临界点随工具描述长度变化：按本机 mock（单描述 900 字符 / 305 tokens）约 7.6，按 Mario 实测的真实描述长度（约 652 tokens/工具）重算约 3.5——**后者是跨源推算值，不是本机实测，别当同一个口径用。**
- ⚠️ 口径声明三：只测了单 server 内工具数变化，未测多 server 并联。

- ⚠️ 口径声明五：耗时受本机负载影响，不进结论。prompt cache 实验在同一 session 连跑六轮；direct 侧已用 r5、r6 两轮分离出稳态代价（每轮重算 1.1 万 tokens 量级），codemode 侧稳态为每轮 19 tokens。r6 相对 r5 缓存零命中的机制未查清，正文只取「两轮读数接近」这一事实。六轮中间隔着约四十分钟，卡在一道 credential 锁上（工具调用要一份带签发方白名单的凭据，换 server 地址就换不到，脚本在重试里空转），期间本机缓存冷掉，所以 r5 是冷启动读数；绕锁花的开销不进本文任何一个数，也不进耗时那一列。
