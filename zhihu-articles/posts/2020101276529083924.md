## 先从一个故事说起

你看传统网卡那个 Ring Buffer，像什么？像一条**单行道上的旋转寿司**。发送和接收的盘子在同一条传送带上转，内核师傅站在中间既要摆盘子又要收盘子，忙得不可开交，最后还得拍拍你的肩膀说：”喂，你的三文鱼到了。”

这就是中断，这就是上下文切换，这就是传统网络栈的宿命。

但 RDMA 不干这种事。它说：**凭什么我吃个寿司还要经过厨师的手？我自己从鱼缸里捞不行吗？**

### Ring Buffer 的原罪

我们先解剖一下传统 Ring Buffer 的灵魂。

传统网卡（以 Linux 的 NAPI 为例）搞的是一个 **TX Ring**和一个 **RX Ring**，看起来已经是分开的了对吧？但问题的核心根本不在于 ring 有几个，而在于——

**谁在操作这些 ring？**

答案是：**内核**。

```text
App → syscall → kernel → driver → NIC TX Ring → wire
wire → NIC RX Ring → driver → kernel → syscall → App
```

每一个箭头都是一次边界穿越，每一次边界穿越都是一次信任的代价。Ring Buffer 本身只是内核与网卡之间的一个**交接区域**，应用程序根本摸不到它。你以为你在发包，其实你在**请求内核替你发包**。这就像你以为你在开车，其实你坐在副驾驶，方向盘在驾校教练手里。

Ring Buffer 的设计哲学是：

> **“我是内核的 ring，应用程序不配直接碰我。”**

这就是原罪。

### RDMA 的三个队列：一场权力的下放

RDMA 搞了 SQ（Send Queue）、RQ（Receive Queue）、CQ（Completion Queue），合在一起叫 QP（Queue Pair）加 CQ。表面上看，不就是把一个 ring 拆成了三个嘛，有什么了不起的？

**了不起的地方恰恰在于：这三个队列都直接映射到了用户态地址空间。**

让我画个对比：

```text
传统 Ring Buffer:
  App ←→ [Kernel] ←→ [Ring Buffer] ←→ NIC
           ↑
       你绕不过去的太监

RDMA SQ/RQ/CQ:
  App ←→ [SQ/RQ] ←→ NIC
  App ←→ [CQ]    ←→ NIC    (内核：你们聊，我先走了)
```

看到了吗？内核这个中间商被干掉了。这不是简单的队列拆分，这是一场**政变**。

## 为什么非得是三个队列？为什么不是一个、两个、或者五个？

这是最值得深挖的灵魂拷问。

### 一个 Ring Buffer 为什么不行？

传统 Ring Buffer 搞一个环用于 TX 或 RX，producer/consumer 模型，头尾指针追赶，简洁优美。但它有一个致命假设：**操作者（producer 和 consumer）是对称的、同步的**。

网卡塞数据进 ring，内核从 ring 取数据。很好，很对称。但这里有个隐含的时序耦合——你得**按顺序消费**。ring 是 FIFO 的，你不能跳着来。

可 RDMA 的世界观完全不同。RDMA 是**以操作为粒度**的，不是以包为粒度的。一个 RDMA SEND 操作和一个 RDMA WRITE 操作，它们的语义完全不同，完成时间天差地别，凭什么要排在一个队列里按序完成？

更致命的是——RDMA 有**单边操作**（READ/WRITE），远端根本不知道你在操作它的内存。如果用单一 ring buffer，这种不对称性根本无法表达。

### 两个队列（发送+接收）为什么不够？

好，那我搞两个队列，一个发一个收，行不行？

不行。因为你还差一个关键的东西：**完成通知**。

传统模型里，完成通知是靠中断实现的。网卡发完了一个包，给 CPU 发个中断，内核收到中断，处理完，通知应用。这条路径上全是内核的活儿。

但 RDMA 要 bypass 内核啊！你绕开了内核，谁来告诉你”活干完了”？

你不能让应用程序去**轮询 SQ 本身**来判断一个 WQE（Work Queue Element）是否完成——因为：

1. **SQ 是提交队列，不是完成队列**。WQE 被提交后，硬件什么时候做完、做没做成，这些信息不应该回写到 SQ 里面去。这会把提交语义和完成语义耦合在一起，设计上是一场灾难。
2. **一个 CQ 可以服务多个 QP**。这是关键中的关键。你可能有 100 个 QP（对应 100 个连接），但你不需要 100 个完成通知渠道。一个 CQ 就够了。这就像一个法院可以判决来自不同派出所的案件——**完成事件的汇聚点和工作提交点不需要一一对应**。
3. **完成的顺序和提交的顺序可能不同**。SQ 里你先提交了 A 再提交了 B，但 B 可能先完成（比如 B 是一个本地 WRITE，A 是一个跨大西洋的 SEND）。CQ 天然就是一个无序完成的收集器。如果把完成信息塞回 SQ，你还要处理乱序回写，ring buffer 的 FIFO 语义直接崩盘。

所以 **CQ 的独立存在是逻辑必然**，不是设计者的审美偏好。

## 为什么 SQ 和 RQ 要分开？

这一点相对直观，但背后的道理比表面上深刻。

传统 TCP 栈里，一个 socket 既能 send 又能 recv，底层对应的 TX Ring 和 RX Ring 已经是分开的了。RDMA 也分开，看起来只是延续传统？

不。SQ 和 RQ 分开的真正原因是**它们的操作语义完全不对称**：

- **SQ**：应用程序是 producer，硬件是 consumer。应用程序往里面塞 WQE，说”帮我发这个”或者”帮我 RDMA WRITE 那块内存”。
- **RQ**：应用程序也是 producer！应用程序往 RQ 里塞的是**空的接收缓冲区**——”如果有数据来了，放到这里”。硬件收到数据后，从 RQ 里取一个 WQE，把数据填进去，然后往 CQ 里扔一个完成通知。

注意到了吗？**SQ 和 RQ 的 producer 都是应用程序，consumer 都是硬件**。这跟传统 Ring Buffer 的 producer/consumer 模型（一端是网卡一端是内核）截然不同。

两个队列的 producer 相同、consumer 相同，但语义完全不同——一个是”我要主动干活”，一个是”我准备好了被动接活”。把它们塞进一个 ring，你需要在每个 entry 上加一个 tag 来区分类型，然后硬件要做分拣，这完全是自找麻烦。

### 深层本质：从”流”到”操作”的范式转移

传统网络是**面向流**的。TCP 给你一个字节流，Ring Buffer 里躺着的是一个个 packet，packet 是流的切片。流是有序的、连续的，所以 FIFO 的 Ring Buffer 天然匹配。

RDMA 是**面向操作**的。每一个 WQE 代表一个独立的操作：SEND、RECV、READ、WRITE、ATOMIC CAS、ATOMIC FETCH_AND_ADD……这些操作有各自的语义、各自的完成时间、各自的成功/失败状态。

面向流 → Ring Buffer（一维的、有序的、同质的） 面向操作 → SQ/RQ/CQ（多维的、可乱序的、异构的）

这就像——

Ring Buffer 是一条**流水线**，寿司一个接一个从眼前经过。 SQ/RQ/CQ 是一个**工单系统**——你提交工单（SQ/RQ），等待回执（CQ），工单之间互不耦合。

### 硬件卸载视角：DoorBell 的秘密

还有一个容易被忽略的角度：**DoorBell 机制**。

应用程序往 SQ 里写完一个 WQE 后，要敲一下 DoorBell（写一个 MMIO 寄存器），告诉硬件”来活了”。硬件从 SQ 里取走 WQE，丢给自己的处理引擎去执行。

这个模型之所以要求队列分离，是因为 **DoorBell 的粒度是每个 Queue 独立的**。你敲 SQ 的门铃不会触发 RQ 的处理，反之亦然。如果 SQ 和 RQ 是一个 ring，硬件收到一次 DoorBell 后要扫描整个 ring 来分辨哪些是新的 send request、哪些是新的 recv buffer？这效率简直是灾难。

更进一步，CQ 的独立还允许了一种关键优化：**事件聚合（Event Coalescing）**。你可以设置 CQ 在积攒了 N 个完成事件后才触发一次通知（通过 Completion Event），而不是每个操作完成都通知一次。这本质上就是 RDMA 版的”中断聚合”，但因为 CQ 是独立的，这种策略可以在 CQ 级别灵活配置，与 SQ/RQ 的提交完全解耦。

### 内存语义视角：Zero-Copy 的必然要求

最后一击。

RDMA 的杀手锏是**零拷贝**和**内核旁路**。这意味着 SQ/RQ/CQ 都必须在用户态可见，且硬件能直接 DMA 访问。

传统 Ring Buffer 呢？它活在内核空间里。即使你 mmap 到用户态（如 AF_XDP 所做的），你仍然面临一个问题：内核需要参与 ring 的管理（比如更新 tail 指针、处理中断）。

RDMA 的 SQ/RQ/CQ 从一开始就为**用户态直接操作**而设计。创建 QP 的时候（通过 ibv_create_qp），verbs 库会：

1. 通过内核态 uverbs 分配物理内存
2. 把 SQ/RQ/CQ 的内存 mmap 到用户进程的虚拟地址空间
3. 把 DoorBell 寄存器也 mmap 给用户态

从此以后，在数据路径（data path）上，**内核完全不参与**。用户态直接往 SQ 里写 WQE，直接敲 DoorBell，直接从 CQ 里 poll 完成事件。

这种设计要求队列结构必须**简单、正交、无需复杂的同步**。一个混合的 Ring Buffer 需要复杂的锁或者 CAS 来协调多种不同语义的操作，而分离的 SQ/RQ/CQ 每个都是单一 producer-单一 consumer 的简单模型，无锁或轻量级同步即可搞定。

## 总结：不是拆了一个 Ring，而是建了一种新范式

让我最后把这件事说透——

RDMA 没有”选择”SQ/RQ/CQ 来”替代”Ring Buffer。它创造了一种全新的硬件-软件交互范式：

|  | 传统Ring Buffer | RDMA SQ/RQ/CQ |
| --- | --- | --- |
| 操作者 | 内核 | 用户态应用 |
| 抽象层次 | 包（packet） | 操作（operation） |
| 完成通知 | 中断→内核→应用 | CQ→应用（直接poll） |
| 完成与提交 | 耦合（同一个ring） | 解耦（独立CQ） |
| 多连接聚合 | 每个ring对应一个/一组队列 | 多QP共享CQ |
| 序模型 | 严格FIFO | 允许乱序完成 |

Ring Buffer 是**内核中心主义时代**的产物——万物皆须经过内核这个中央集权的太监之手。

SQ/RQ/CQ 是**用户态直通时代**的必然——当你把内核踢出数据路径，你就需要一套**自描述、自管理、正交分离**的队列体系，让应用程序和硬件直接对话，而不需要任何中间人翻译。

这不是一个工程优化，这是一次范式革命。就像从马车到汽车，你不是给马装了个发动机，你是把马本身给干掉了。

内核那匹马，在 RDMA 的数据路径上，已经被干掉了。SQ/RQ/CQ 就是那台发动机。
