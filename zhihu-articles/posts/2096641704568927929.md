## TL;DR

本文将分享我们 Vibe Compiler 的实践经验——**面向缺少成熟编译链的新型空间数据流架构（Spatial Dataflow Architecture）AI芯片，如何由人与 Agent 协同完成整套AI编译器的设计和实现**。

我们与 Agent 的协作由三部分构成：以 Agent 承担架构设计（Agent for design），以独立验证保证实现正确、并把确认过的根因与方法沉淀为可复用知识（Agent for implementation），以实测反馈驱动性能优化（Agent for performance）。

经过我们和 Agent 多轮迭代开发，在单卡 16 Tile 下，Vibe Compiler 生成的**Attention 与 GEMM 内核性能均优于专家写的算子库**，时延分别为 2.461 ms（专家库 3 ms）与 1.794 ms（专家库 2 ms）；最近一轮实卡验证中，80 项负载配置通过了完整输出对照。文章最后进一步总结了四条人与 Agent 协作的实践经验。

## 和 Agent 一起，为新芯片写AI编译器

今年年初，Anthropic 让 16 个 Claude Agent 并行工作，两周写出一个能构建 Linux 内核的 C 编译器。中途它们一度卡住：16 个 Agent 撞上同一个 bug，各自修完又互相覆盖。解法是以 GCC 为对照：把大部分内核文件交给 GCC 编译，逐步缩小出错的范围，Agent 们才又能分头去修不同文件里的 bug。

最近几项让人印象深刻的工作，Agent 手边也都有现成的参考实现可以对照。Kimi K3 在维护者指导下，照着 Triton 的编程模型做出 MiniTriton，从编程语言、MLIR 编译器一直做到 GPU 运行时。OpenAI 用 Codex 为自研芯片 Jalapeño 优化模型，部分 GPT-OSS Attention 和 MoE 模块比已有的专家实现快 1.5 到 1.8 倍。CAKE 从大量生产级内核出发，让 Agent 一边优化内核一边扩展编译器，写出的 Kimi Delta Attention 内核比官方实现快 2.05 倍。

我们面对的是一块新的空间数据流芯片，16 个 Tile 靠片上网络交换数据。硬件资料、SDK 和 MLIR 都有，却没有成熟的编译器可以对照。

Vibe Compiler 想回答的是：面对一款缺少成熟编译链的新空间数据流芯片，能否与 Agent 一起完成整套编译器的设计和实现，再让 Agent 围绕真实负载持续研发？

答案是可以。

经过我们和Agent多轮迭代开发，在单卡 16 Tile 下，**Vibe Compiler 生成的 Attention 和 GEMM 内核都已快过专家写的算子库**：**Attention 用时 2.461 ms，专家库为 3 ms；GEMM 用时 1.794 ms，专家库为 2 ms**。最近一轮实卡验证中，80 项负载配置通过了完整输出对照，覆盖单层Llama 2-7B 、ViT、ResNet-18，以及各类 Attention、GEMM、卷积和集合通信。

Agent 的编码能力已经足够强，**决定它能走多远的，是有没有可靠的验证和反馈**。在没有参考实现的新硬件上，人和 Agent 要一起造的不只是编译器，还有让 Agent 能持续改进它的研发环境。

本文想和大家分享的，就是这段经历：**AI编译器在这块新芯片上是怎样设计出来的，人和 Agent 怎样分工、踩过哪些坑，研发环境怎样一步步搭起来，Agent 又是怎样借助它，把 Attention 和 GEMM 的性能做到超过专家库**。希望这些经验，对同样想在新硬件上用 Agent 开发AI编译器和基础软件的团队有所帮助。

### 空间数据流架构及其编译挑战

本节我们先对本次工程的硬件架构进行一个简单的介绍作为背景知识。Vibe Compiler 面向的是一款空间数据流架构芯片，多个计算节点通过片上网络（NoC）连接，每个节点都有自己的计算单元和局部存储。计算分给哪些节点、数据放在哪里、节点之间怎样配合，都需要编译器来安排。

常规 CUDA 程序也要处理共享内存和同步，但线程块通常由硬件调度到计算单元。在这类空间数据流芯片上，软件还要更多地参与节点放置和节点间通信。

Cerebras 就采用了类似的组织方式。如图 1-1 所示，核心里的 SRAM 存放本地数据，路由器把核心连成二维网格（mesh）。数据可以留在本地反复使用，也可以通过 NoC 传给其他核心。核心调度器会检查输入数据和输出缓冲是否就绪，再推进相应的计算。

![](https://picx.zhimg.com/v2-ca21f300aaa0d6cd01e28797109a3f67_r.jpg)
*图 1-1：Cerebras 的核心与片上互连*

对编译器来说，存储要按核心来算。输入、输出、临时结果和流水缓冲得同时放得下。把计算块切大，一份数据可以多用几次，但本地 SRAM 可能不够；切得更碎，数据又可能需要搬更多次。即使全芯片的存储总量够用，也得检查每个核心分到的数据是否超出容量。

计算分给哪些节点，也决定了数据要走多远、哪些传输会共用一段链路。Cerebras 的路由器支持广播和多播，可以把同一份输入送给多个核心；多个核心的计算结果有时还需要做归约。多用几个节点可能算得更快，也可能让更多时间花在通信上。

有的芯片还要求编译器选好通信路径。比如 SambaNova SN40L，编译器要安排计算放在哪里、数据走哪条路，处理路径和通道冲突。网络上既有张量数据，也有控制 token；编译器要在链路、路由和 FIFO 的限制内安排通信，并配合硬件的信用流控。

Tenstorrent 的 Tensix 节点把计算和搬运分开，一个计算内核与两个数据搬运内核协作（图 1-2）。搬运内核通过 NoC 访问 SRAM 与 DRAM，可以在计算进行时搬运数据。软件负责安排缓冲区，并用异步读写、内存屏障和信号量协调计算与搬运；实际的运算、传输和链路流控由硬件完成。

![](https://pic1.zhimg.com/v2-1230780608edec58af8c787f7649675c_r.jpg)
*图 1-2：Tenstorrent 的节点阵列及 Tensix 内部执行分工*

这里要分清发出请求、数据可用和缓冲区可以复用的时机。发出搬运请求，不代表数据已经准备好；发送端的缓冲区可以复用，也不代表接收端已经处理完数据。编译器要按硬件接口的规定安排等待。漏掉必要的等待，计算可能读到还没准备好的数据；等错了条件，后续计算和传输又可能一直卡住。

为这样的空间数据流芯片写编译器并不容易：计算、存储和通信要一起安排，能直接借鉴的工具和经验又没有成熟的 CPU/GPU 平台那么多。接下来简单介绍我们怎样是如何与 Agent 一起，为这款芯片开发的编译器。

### Vibe Compiler 的开发与迭代

我们与 Agent 在 MLIR 的基础上开发了 Vibe Compiler。它接收 PyTorch/XLA 导出的 portable StableHLO 程序，生成目标芯片的可执行文件。计算怎么分给各个节点、数据怎么搬、何时等待，都由编译器自动安排。Agent 参与这套编译器的设计、实现和调试。

这款芯片单卡有 16 个计算节点，称为 Tile，排成 4×4 网格（图 1-3）。每个 Tile 里，RISCV核 负责控制，NE 做矩阵和卷积计算，Vector Engine 做向量和归约等计算，片上暂存存储（SPM）由软件管理。搬运工作也分给不同的部件：DMA 负责 DDR 与 SPM 之间的数据搬运，TDMA 做局部数据变换，Transfer Engine 在 Tile 之间传输数据。编译器要根据各个部件的完成条件，安排计算和搬运之间的等待。

![](https://pic1.zhimg.com/v2-c4cedc86539de95259589f7e30f222e4_r.jpg)
*图 1-3：目标空间数据流架构的单卡硬件与单 Tile 执行资源。左侧为 4×4 Tile 阵列，右侧展开一个 Tile*

这些部件具体怎样配合，答案分散在硬件文档、SDK 和调试记录里。我们与 Agent 一边读文档、查 SDK 代码，一边把确认过的规则写进编译器，并补上相应的检查。

早期，我们试过直接让 Agent 完成整个编译器。代码和测试逐渐齐备，模块之间却没有真正接上。一次检查发现，IR 转换测试和可执行包检查都能通过，但被检查的包来自固定样例，并不是前面的 IR 转换生成的。

后来，我们重新梳理了编译流程，先把单 Tile 的路径接通，再扩展到多 Tile 和小型模型。人先明确各个阶段要解决什么问题、怎样检查结果，Agent 细化 IR 和转换方案，再编写实现。每一步生成的结果，都要真正交给下一步使用。

几轮实现和重构后，工程逐步接通了从源程序到指令、目标代码和可执行包的完整流程。小型 Llama 也能通过统一入口编译，并在主机侧将计算结果与参考结果比较。

开发中遇到具体代码错误，Agent 就沿着 IR 和诊断信息继续修复。如果多个阶段反复对不上，我们则一起回看阶段划分、接口和检查要求，必要时重新设计。图 1-4 把这两种修改都画了出来。

![](https://pica.zhimg.com/v2-66e212cc544e61ea2e94fd67d2c2e9f0_r.jpg)
*图 1-4：我们与 Agent 的协作过程*

验证范围也从单 Tile 扩展到多 Tile 和小型模型，同时检查多块、尾块等情况。包的结构检查通过、功能模型算对了，还需要上板确认实际执行；性能则要在实卡上单独计时。修复确认有效后，我们会补上回归用例，也把设计变化和查明的问题记回仓库，让下一轮 Agent 能接着做。

编译器开始处理真实负载后，新模型暴露的功能缺口和实卡测出的性能瓶颈，就成了 Agent 继续开发的任务。我们与 Agent 讨论改进方向，再用验证和性能分析结果判断修改是否有效。下一章从整体框架讲起，再进入具体的开发和优化过程。

## Vibe Compiler & Agent 开发模式

### 整体框架

先看 Vibe Compiler 的编译框架（图 2-1）。它把 PyTorch/XLA 导出的 portable StableHLO 程序，转换成运行时可以加载的可执行包。围绕这套编译系统，我们还建立了图 2-2 中的协作开发框架，与 Agent 一起根据代码、诊断和验证结果继续改进编译器。

![](https://pic3.zhimg.com/v2-133734f4790c789f515fb41532d35d62_r.jpg)
*图 2-1：Vibe Compiler 编译框架*

Vibe Compiler 接收 PyTorch/XLA 导出的 portable StableHLO 程序，经过验证、卡级 SPMD 和图归一化，形成 `TensorProgram`。空间划分把计算和张量分片分给各个 Tile，生成 `TileModule/TileRegion`。接下来做时域分块与融合，确定数据布局、组织缓冲区，安排 DDR/NoC 搬运和软件流水，再转成指令表示 `Instr`。编译器根据实际读写和依赖确定完成条件与等待位置，并按缓冲区生命周期分配 SPM/DDR 地址，确保相关异步操作结束后再复用内存。

编译器内部，`none` 按固定规则生成基线，`search` 在预算内比较不同的物理执行方案。两者各自生成并验证实际 IR，共用后续编译流程，不互相回退。

所有 Tile 都通过资源和目标约束检查后，编译器形成 `DeviceExecutable`，再做目标转换。生成的目标模块分别供功能模型执行和设备工具链编译、链接。链接产物加上数据和描述信息，组成 `ExecutablePackage`，检查通过后交给运行时加载、执行并取回结果。

开发这套编译器时，我们使用的 Agent harness 包括仓库资料、编程 Agent、工程工具和人工审查。长期规则、当前任务、阶段设计、硬件事实和确认过的问题根因分别保存在仓库里，Agent 可以据此接着工作。

![](https://picx.zhimg.com/v2-d71a781b8018bb470701a618fd7f2099_r.jpg)
*图 2-2：以工程上下文和验证反馈支撑的专家—agent 协作*

专家把握整体框架和验收要求，双方一起明确任务的输入、输出、下一阶段怎样使用结果、允许改动的范围和要覆盖的用例。Agent 再去调研方案、细化设计、实现和调试。

改得好不好，重点看产物能不能被下一阶段正确使用。Agent 通过构建、IR 检查和纵向 runner，核对数据覆盖、依赖和完整输出。具体代码错误就继续定位和修复；如果特判越加越多，或者几个阶段反复对不上，就和专家一起回看设计和接口。任务完成后，确认有效的修改会写回代码与回归测试、设计文档与任务状态，以及已验证的根因记录，供下一轮继续使用。

验证从局部检查逐步做到真实输入的完整编译。包与 no-card 检查确认产物和调用是否合法，功能模型先做数值对照，设备测试再检查实际执行和输出。功能模型使用同一次转换生成的目标模块，不执行包内 ELF；设备性能则要单独测量。

图 2-2 的 4K prefill attention 中，调小计算块仍过不了 SPM 规划。Agent 检查 IR 后发现，状态累积和归一化分在两轮循环里，每个 Tile 都要保留 2 MiB 的完整累加器。把两者合进同一个输出块循环、在相关操作结束后复用局部状态，累加器就缩到 64 KiB，完整输出仍留在 DDR。改写保留了适用条件检查，通过整块和尾块回归及 SPM 容量检查，实卡的 16,777,216 个输出也通过了独立 PyTorch 对照。

下面先看这些计算、循环和状态是怎样在多层次 IR 中表达的，以及我们与 Agent 怎样一起完成这部分设计。

## Agent for design

### 人- Agent协同的多层次IR设计

中间表示即 IR 在编译器开发中占据着至关重要的作用，它描述了相同程序在不同阶段的表示形式，并基于不同层级的表示能力可使能不同的优化，同时对于Agent而言，IR也是其探索空间的组成部分之一。

设计多层次 IR 时，我们先确定每层要表达什么、负责什么，再由 Agent 设计操作、类型、属性和接口，并实现相应转换。区域之间怎样传数据、什么时候引入缓冲区、怎样表达异步完成，都要结合实际 IR 和后续编译结果一起调整。

图 2-3 把各层的用途和设计分工放在一起。从张量计算到设备调用，IR 逐层补充执行细节。这些层次按语义和职责划分，并不与 MLIR dialect 一一对应。

![](https://pic2.zhimg.com/v2-b8458fac0b81f202e9b9ddd1bf72eff9_r.jpg)
*图 2-3：多层次 IR 的设计分工与功能*

在张量层，IR 保留张量算子和完整算法。Portable StableHLO 经卡级 SPMD 和归一化后形成 `TensorProgram`，普通计算沿用 Linalg、Tensor、SCF 等标准表示，attention 则用专门的语义操作表示。这一层保留数学和索引关系，供图变换与空间划分使用，还不指定物理 Tile、SPM 地址和搬运方式。

计算分到具体的物理 Tile 后，Tile 层开始组织各自的计算、循环和数据块。`wafer.tile.module` 标明 Tile 归属，`wafer.tile.region` 组织局部执行。区域先用 tensor SSA 表达计算结构，支持时域分块与融合，再补充布局、缓冲区和搬运。同 Tile 的数据跨区域留在 SPM 中，用 `resident` 表示；跨 Tile 传输则由 `peer_send  / peer_recv`、消息标识和完成 token 描述。

再到 Instr 层，计算和搬运都变成具体的设备操作，记录读写的缓冲区范围、执行单元（worker）和完成关系，外围仍保留循环与控制流。调度和内存规划根据这些信息分析依赖、安排等待，并分配可安全复用的存储。NoC 传输也在这一层转成 `te_send/te_recv/te_wait`。

最后，目标层确定每个 Tile 的入口函数和 ABI 调用。资源检查通过后形成 `DeviceExecutable`，再经目标转换生成 LLVM IR，确定调用签名、地址和参数类型，交给设备工具链生成代码，组装成 `Executable Package`。

具体的 IR 表示还会随着实现和验证调整。图 2-4 按抽象层次从高到低，列出了四个这样的例子。

![](https://pica.zhimg.com/v2-b3ff8a9a24f8dc1ab8301bfd40a29350_r.jpg)
*图 2-4：四个IR设计协作case：张量与递推状态、Tile 驻留、Tile / Instr 通信、Instr 完成关系*

先看分块 attention。完整 attention 只返回最终结果，按 K/V 分块后，却要在每轮计算之间传递三项状态。Agent 按我们确定的算法与执行分层，用 `attention` 保留完整计算，用 `online_attention` 表达局部更新。当时的归约实现不能直接处理三项状态的维度差异，Agent 就调整循环组织，显式传递状态，供后续分块和算子分解使用。

同 Tile 的数据复用也促成了一次调整。原来的规则不允许 SPM 数据跨 `TileRegion` 保留，同 Tile 上的相邻计算也要经过 DDR 交换数据。Agent 引入 `resident`，同步修改验证器和搬运逻辑，区域结束时就不必强制写回。但数据能否继续留在 SPM，仍要检查 Tile 归属、存储别名、容量和生命周期；区域结束也不等于异步访问已经完成。

跨 Tile 的 NoC 通信则要明确收发双方、完成条件和硬件实现。Agent 在 Tile 层表达消息配对和依赖，到 Instr 层再转成 Transfer Engine 操作，满足目标约束时才合并广播。这样，上层的数据交换表示可以保持稳定，低层优化仍要保留接收端操作，并保证发送完成前不覆盖源数据。

异步写回也需要保护源缓冲区。写回发出后，硬件可能还在读取它，另一 worker 提前覆盖就可能破坏结果。Agent 在重构时，用操作接口明确描述提交和完成行为，并把硬件协议与跨指令分析分开。调度和内存规划据此识别尚未完成的访问，再根据 `worker`、`ncc_join` 等信息确定等待和复用位置。

验收时，我们会检查 IR 怎样生成、怎样转换、能否被下一阶段正确使用，也会检查非法用法能不能被识别。如果后续编译反复需要特判，就和 Agent 一起回看抽象本身。

接下来再看空间切分、分块和搬运这些选择，怎样通过硬件相关 Pass 落到 IR 中。

### 空间数据流架构搜索空间设计：一次失败设计的教训

各 Tile 都有自己的 SPM，通过 NoC 交换数据。计算分给哪些 Tile，会影响它们需要哪些数据，存储和通信也要跟着调整，所以空间切分需要和分块、融合一起考虑。设计这些 Pass 时，我们先要判断哪些硬件决策交给搜索，再与 Agent 一起完成实现和验证。

早期，我们用 GSPMD 把任务映射到多个 Tile，将它产生的逻辑 rank 直接绑定到物理 Tile。这样一来，空间切分就被固定了，后续只能在既定分片内搜索分块、融合和搬运方案（图 2-5a）。Agent 沿着这个框架继续实现，没有指出这个遗漏。数值测试也很难发现问题：程序可以算对，但其他空间切分根本没有进入搜索，增加预算也比较不到这些方案。

我们随后调整了框架，把卡内的空间切分交给搜索。GSPMD 负责卡级分区，卡内程序先不绑定 Tile，再由搜索决定切分方向、分片大小、Tile 放置和后续数据流。

改了框架，这些选择也没有立刻全部进入搜索。检查实现时，我们又发现，代码列出了多种选择，默认编译流程却仍只尝试一个方案。我们继续核对不同的空间切分有没有被尝试，Agent 据此修改方案生成和编译流程。几轮迭代后，搜索器才在预算内尝试不同方案，逐步生成分块、通信和指令，并检查内存与同步约束。不满足要求的方案会被调整或放弃，通过检查的方案再由 cost model 估计开销。搜索器从中选出估计开销最小的方案，保留对应的 IR。

图 2-5b 是最终形成的联合搜索空间：S 决定空间切分与 Tile 映射，F 决定区域组合与输入绑定，T 决定时间分块与循环次序，I 决定通信、复用和流水等实现方式。这些主要硬件决策都能参与方案生成、编译检查和开销比较；搜索仍受预算限制，不保证穷举或全局最优。

![](https://pic2.zhimg.com/v2-888f5c27e28b2a3ec65b459bc27258df_r.jpg)
*图 2-5：搜索空间的协作设计与实现*

我们用 GEMM 检查空间切分有没有改变生成的程序，以及结果是否正确（图 2-6）。显式 peer 对照把 M、N 各切成 4 份，A 行片与 B 列片各由四个 Tile 共享；`search` 选中的方案沿 N 切成 16 份，全部 Tile 共享 A，各自读取不同的 B 列片。切分方式不同，需要的通信也不同。时间分块得到 64 KiB 的 A 窗口，由 Tile 0 读取，再经 NoC 逐级传递。对照图中的通信关系和 Tile 1 的 Instr，可以核对接收、计算、转发和等待的顺序。

![](https://pic2.zhimg.com/v2-67c8f3bd56964863f0b01c18d176fe9b_r.jpg)
*图 2-6：用 GEMM 验证搜索设计*

这次重构让我们看到，**Agent 能持续完善一个实现，却未必会质疑它的设计前提**。仅靠数值测试，也很难发现搜索范围设得不合理。面对 CPU/GPU 之外的新型空间数据流硬件，专家需要凭经验分清哪些限制来自硬件、哪些只是人为预设，把本可以探索的选择留给编译器。

### 基于Agent的快速原型的设计及落地

除了调整搜索空间，我们还尝试让 Agent 把新的优化想法做成原型。在布局变换上，我们当时对 e-graph 只有初步了解，希望用等价改写统一处理 reshape、transpose、broadcast 等逻辑访问变换。

e-graph 按预先定义的规则生成等价形式，同时保留原式和改写过程中的中间形式，供后续规则继续使用。这样，不必要求每一步都立刻减少变换，可以在多条规则组合之后，再提取更简洁的程序。

Agent 调研了 egg、TENSAT 和 Glenside，随后完成规则设计和编译集成，形成图 2-7 中的 Pass。它先把 Tensor/Linalg 子图转成 `Input/Access/Concat/Compute`，交给 egg 迭代改写，并用 `IndexRelation` 检查访问关系、类型和迭代域。接着提取更简洁的共享 DAG，确认各个输出都能被后续 Pass 使用，再按依赖顺序重建普通 IR。

![](https://pic1.zhimg.com/v2-a72a5b014bd5c9e70c923c2cf82e7ca8_r.jpg)
*图 2-7：基于 e-graph 的布局变换消除*

图 2-8 中，同一组规则处理了几种不同的结构：长链中的访问变换跨过四个计算后被消除；菱形图的两个分支改为直接读取原输入，再汇合输出；拼接归约先提取三个分段共有的转置，再把它吸收到归约索引中。测试还覆盖了最多 32 个交替计算单元。这些规则可以连续配合，减少了为每条完整计算链单独写匹配模板的需要。

用到真实模型时，首版实现暴露了小用例没覆盖的问题：重建算子时沿用了分散的插入位置，一些值先被使用、后被定义。Agent 据此修正了检查和重建流程。在 FP16 Llama block（B=2，S=1024/1025）的两组记录中，这个 Pass 都消除了 23 个逻辑访问变换；9 个被改写的子图里，有 6 个用到了至少两类规则。后续迭代又补齐了长链和共享输入场景。

![](https://pica.zhimg.com/v2-49bb401573b103ca5c2b0cca9ddd8610_r.jpg)
*图 2-8：长链、共享分支与拼接归约的图改写*

Agent 的价值在于降低新想法的试验成本，让设计更早接受真实程序的检验。有了可接入编译流程的原型，我们就能尽早用复杂用例和真实程序判断方法是否适用，再和 Agent 一起修正规则与实现。验证也不能停在一个 Pass 内，还要看改写后的结果能否被后续编译阶段正确使用。

## Agent for implementation

### 跨阶段多层次验证

工程早期，我们遇到过一个问题：局部 Pass 的测试通过了，生成的结果却没有进入后续编译。代码和测试都由 Agent 编写时，还可能沿用同一个错误假设。为此，我们把检查从单个 Pass 延伸到阶段之间，再到实卡执行，既看数值是否正确，也看性能有没有变化，并记录尚未覆盖的情况。

图 2-9 展示了这些检查怎样接在一起。局部测试检查 IR 是否合法、变换是否保持语义、资源使用是否满足约束；纵向测试则从真实导出的程序进入正式编译入口，让每一阶段实际使用上一阶段的产物，一直到生成并读回可执行包。功能模型与设备工具链使用同一次 lowering 生成的目标模块，让模型验证和设备执行对应到同一次编译。

![](https://pica.zhimg.com/v2-bbbc4ed389c15bc81413a17f6d03f6b2_r.jpg)
*图 2-9：跨阶段多层次验证*

每个用例要检查哪些风险，我们在实现前就确定下来（图 2-10）。测试按分块、归约、共享输入和布局等机制组织，也覆盖真实规模、尾块和非法输入。除了最终结果，还要看分块是否完整、归约有没有漏算。上游通过了，仍要继续验证下游；未注册、跳过或不支持的测试，不能算作通过。

我们也会给验证器输入故意构造的错误产物。比如包的描述字段和文件彼此一致，实际却不符合张量的存储需求。验证器要独立算出所需存储量，识别出这种错误，避免实现和验证沿用同一个错误假设。

![](https://pic2.zhimg.com/v2-3875ec8920942f4db2ceb636d1fe8e5b_r.jpg)
*图 2-10：覆盖设计与 Agent 调试反馈*

到了实卡上，测试会读回全部输出，与同一输入在 PyTorch 中独立计算的参考结果比较。功能模型和无卡检查各有用途，最终的设备行为仍要在实卡上验证。算对以后，还要看改动有没有让实卡变慢。我们在相同配置下重复测量实卡耗时，对照修改前后的性能。Agent 完成修复或重构后，数值和性能要分别确认；出现性能退化，需要查明原因并重测。

这些检查也给 Agent 提供了排查线索：阶段诊断带出错误类别和相关 IR，实卡测试记录输出误差与耗时变化。Agent 据此缩小范围、定位和修复。修复先在最小用例上确认，再回到原始规模，重跑受影响的上下游检查，核对改动对完整编译流程的影响。

这样，专家对整个编译器的要求就变成了可执行的检查。Agent 在分模块修改时，也能据此判断改动有没有影响后续编译、最终结果和实卡性能。修复过程中确认下来的原因和处理方法，也会整理进工程，供后续任务复用。

### 可复用知识的沉淀

排错时确认下来的原因和处理方法，会和硬件行为、各层 IR 的职责一起整理进工程。Agent 接到后续任务时，可以先查这些记录，复用已经弄清楚的结论和做法（图 2-11）。

![](https://pic2.zhimg.com/v2-3ffa4e16f6ae4fc97e6892f636dc60f7_r.jpg)
*图 2-11：可复用知识如何进入后续开发*

整理这些记录时，专家判断结论在什么条件下适用，Agent 写清问题原因、修复方法和对应检查。比如，分块求和曾因各 Tile 重复加入原始初值而算错，修复后只在最终合并时加入一次，并要求测试覆盖非零初值。整数索引搬运曾混用元素数和字节数，导致数据没搬完整；修复统一了长度与步长的单位，并增加实际命令检查。这些原因、修复方法和检查要点都写进了问题手册，后续 Agent 遇到相关问题时可以查用。

为了让 Agent 能找到这些资料，协作原则、编译设计、硬件说明和问题经验分别放在固定位置，其他文档引用同一份规则。Agent 按任务查阅相关条目，使用前仍要核对当前实现和适用条件。重要约束还会写进验证器或回归测试，让后续修改继续接受检查。

这些记录也要跟着工程一起更新。硬件配置、接口或实现变化后，我们会重新核对相关条目，修订失效结论和过时说明，把仍然有效的规则收拢到对应位置，旧方案和问题现场则归档保留。

这样，后续 Agent 查到的既有代码和检查方法，也有当时为什么这么做的解释。已经确认的硬件约束和开发方法可以作为起点，减少重复推断，我们与 Agent 就能把精力放到新的设计选择和未知行为上。

### Agent执行倾向性

前面这些验证和记录约定，是在实际协作中逐步形成的。有时 Agent 一直在改代码，我们最初交给它的问题却没有解决。图 2-12 列出了六种情况，以及我们针对这些问题调整的任务说明和检查方式。

![](https://pic2.zhimg.com/v2-729ab427669eb9853f0b1b62f881db99_r.jpg)
*图 2-12：六类执行倾向及对应的协作约束*

**1. 顾着跑通，漏掉了原有能力**

搜索框架重构时，新接口和默认方案已经能运行，候选比较、搬运优化却没迁全。Agent 还可以继续改进能运行的部分，但我们验收这次重构，要看的是原有能力有没有完整保留下来。哪些能力要保留，需要在实现前列清；改完后再逐项确认它们在新代码里是否真的被调用。

**2. 样例过了，原模型的问题还在**

我们要编译的是原始模型，测试也得保留它的计算和真实输入。开发中却出现过先改写测试模型、再拿去编译的做法：改过的样例通过了，原模型的问题并没有解决。一个修复是否有效，要回到原模型上看，再检查其他形状、分支和边界，确认它解决的不只是眼前这个样例。

**3. 要求审查框架，最后忙着修 bug**

有一次，我们请 Agent 判断框架是否通用、高效，它最后主要修了几个 bug。具体缺陷容易着手，原先的审查问题却没有得到回答。我们后来把讨论拉回了框架本身。对审查中发现的新问题，可以先记录，再按本轮目标决定是否处理；收尾时仍要说清原问题回答到什么程度、还有哪些没有结论。

**4. 只看近期对话，漏掉早先的要求**

多轮协作中，我们既遇到过计划写得很完整、代码却还没跟上的情况，也遇到过摘要太短，下一轮需要的细节没留下来。只接着近期对话做，很难分清哪些已经完成、哪些还待实现、哪些已经取消。Agent 继续之前要重读当前任务和设计，每轮结束再更新记录，下一轮才能接着实际进度做。

**5. 反复加补丁，却没回头看设计**

同类补丁反复出现时，我们需要先回头看设计。早期搜索单独维护一套“候选描述”，提前记录计算、搬运和调度，再据此生成实际 IR。两边不一致，Agent 就补映射、加校验，改一份还得同步另一份。最后我们调整了设计，改为从实际 IR 读取这些信息，省掉了这部分重复维护。

**6. 凭直觉做优化，没有先找出瓶颈**

有些分析复用的修改，回归通过了，提速却没有明显超过测量波动。测试没发现行为错误，并不等于优化有效。我们得先知道时间花在哪里、这次准备减少哪些工作，改完再用相同输入和配置测量，才能判断有没有收益。

**Agent 能继续把实现做下去，却未必会主动停下来判断方向。**具体实现可以交给它，但为跑通而缩小要求、同类补丁反复出现，或者改了很多代码仍看不到收益时，专家就该和 Agent 一起重新核对目标，判断要不要调整设计或方法，不必等到程序报错。

下一节介绍我们为 Agent 准备的性能测量环境，以及它怎样用这些数据定位瓶颈、检验修改。

## Agent for performance

### 为 Agent 准备性能测量环境

要让 Agent 根据实测结果做优化，我们把性能测量接入了 Vibe Compiler 的编译和板测入口。专家确定优化目标和比较条件，Agent 就能围绕同一个用例反复编译、运行，沿着测量结果排查问题。

在主机侧，我们记录编译阶段和各个 Pass 的耗时；到了设备上，则测量整个程序的执行时间，也可以单独测各 Tile 的内核耗时。要继续追查热点，PMU、Count 和 Trace 还提供引擎活动时间、动态调用次数和执行轨迹。

一次完整的 profile 基于同一份编译结果采集数据，输出 JSON 和 HTML 报告。报告保留了调用位置，Agent 可以对照 IR 和生成代码，追查重复搬运、细碎指令或不必要的等待是怎么产生的。修改实现并重新编译后，再用同一个用例检验效果，图 2-13 展示了这个过程。

![](https://pic3.zhimg.com/v2-719fcf3aa2b4a768c74dc7ba8ea29d86_r.jpg)
*图 2-13：性能测量怎样支持 Agent 迭代优化*

图中的 Llama block 优化，就是从大量搬运和加法调用查起的。Agent 沿着调用追到 RMSNorm，发现归约被展开成逐项搬运和累加，原因是旧的长度门槛挡住了原生归约。去掉这道门槛、在满足现有支持条件时优先使用原生归约后，细碎调用明显减少。同输入实卡复测中，整个 block 的未插桩 Primary 耗时从 **37.44 ms 降至 17.68 ms**，全部 65,536 个输出通过了 PyTorch 对照。

这次修改落在通用的指令选择逻辑里，影响不止一个用例。我们也需要保留其他受影响用例的性能基线，检查它们有没有退化。比较性能时，先确认完整输出通过数值检查，再固定输入、配置和计时模式比较耗时，诊断插桩的耗时则单独看。没有收益或出现退化，就重新分析，必要时撤回修改。

原来的热点减少后，Agent 再看剩下的时间花在了哪里，专家则结合这些数据参与原因分析和方案取舍。下一节的 Attention 和 GEMM 案例中，就有几次这样的方向调整。

### 基于 profiling 的性能迭代：Attention 与 GEMM

在 Attention 上，Agent 根据每轮性能报告继续查找开销，专家则提示值得追查的方向。图 2-14 记录了 BF16 causal Attention 的 20 个迭代阶段，以及后续对齐排布版本的结果。Q/K/V 的形状为 `[1,28,2048,128]`，在单卡 16 Tile 上，内核耗时从 **21.340 ms 降至 2.461 ms**，累计约 **8.67 倍加速**。

最初的热点在行最大值、累加器缩放和归一化的广播里。Agent 检查生成指令，发现繁忙 Tile 上共有约 760 万次 4 B 内部搬运。它把符合条件的广播改成先填入一段数据，再成块复制已经写入的内容，逐轮扩大覆盖范围。改完这一轮，耗时从 **21.340 ms 降到 7.664 ms**，这条规则也进入了编译器的通用搬运优化。

搬运减少后，我们继续看指数、归约和布局转换的开销。经专家提示，Agent 把 score 按 `K × Qᵀ` 组织以更好利用指令特性，让行向量直接参与分组计算，减少中间广播。但把输出累加器也转置后，又多了输出重排的开销，两个阶段的单次记录从 **4.865 ms 升到了 5.461 ms**。结合专家提示，Agent 后来保留了 KQ score，恢复累加器原有的计算方向。这轮还在专家允许下采用了低精度指数指令 Explp，输出误差要求保持不变。

累加器还有另一处开销：每处理一个 KV 块，它仍要在 Tensor 布局和对齐排布之间来回转换。Agent 对照 profile 和 IR，发现布局选择低估了这些转换在循环中的累计成本。修正后，累加器在循环内一直保持对齐排布，耗时降至 **2.734 ms**。专家又提示继续检查控制核的命令准备，Agent 把固定参数提前到编译时处理，进一步降至 **2.531 ms**。过程中也比较过串行和流水，实测没有显示流水更快，最终保留了串行实现。

后续对齐排布版本的内核耗时为 **2.461 ms**，低于专家优化算子库对应内核的 **3 ms**，相对专家参考约 **1.22 倍加速**，同时通过了原有数值检查。

![](https://picx.zhimg.com/v2-78c062fa5fb20f9463fd3b4e223774ef_r.jpg)
*图 2-14：Attention 的逐轮优化*

GEMM 上也有类似的重复搬运。在 M=N=4096、K=1024 的用例中，每个 Tile 处理不同的 B 列块时，都要用到同一份 A 分片。Agent 把这份 A 一次读入 SPM，后续计算继续使用，内核耗时从 **3.537 ms 降到 2.807 ms**。

此时同一份输入还会被不同 Tile 从 DDR 分别读取导致重复搬运。专家提示用 NoC 复用输入，Agent 据此让 A、B 在 Tile 间传递，减少重复读取。各 Tile 再把 B 分片留在 SPM 中，换不同的 A 行块计算时继续使用。这轮优化将内核耗时进一步降到 **2.186 ms**。

经专家提示，Agent 把 B 的复用扩展到全卡：各 Tile 沿 M 维分工，B 由 Tile 0 读入，再沿相邻 Tile 组成的 NoC 蛇形链逐级传递。末端 Tile 12 收到后就完成了分发。各 Tile 完成 K 维累加后，通过 DMA 将自己的 C 行块写入 DDR 的对应位置，合起来就是完整输出。配合这条传递路径，输入输出也改为对齐排布，减少中间转换。新布局接入后却一度更慢，Agent 检查 IR 发现，原有的复用分析没有覆盖新布局，前面做好的 B 传递因此失效，数据也仍要绕经 Tensor 布局。

Agent 修复这两处问题后，B 的蛇形传递恢复，对齐排布的数据也能直接搬入 SPM，连续搬运粒度达到 **32 KiB**。最终内核耗时降到 **1.794 ms**，相对基础分块加速 **1.97 倍**，相对专家算子（**2 ms**）加速 **1.11 倍**。

![](https://pica.zhimg.com/v2-253e849c05952891d383f69bf58622b4_r.jpg)
*图 2-15：GEMM 的逐轮优化*

这些改动都来自具体负载暴露的问题，最后留在了编译器的广播搬运、布局选择和输入复用等规则里。专家提供值得尝试的方向，Agent 继续追查和实现，测量结果再帮助双方决定保留什么、下一轮查哪里。后续编译其他程序时，符合条件的优化也可以继续复用。

## 总结与启示

开头我们问：没有成熟的编译器可以对照，人和 Agent 能不能一起把整套编译器做出来，再让 Agent 围绕真实负载持续改进它？答案是能。Vibe Compiler 把 PyTorch 程序直接编译到这块空间数据流AI芯片上运行，80 项负载配置通过了实卡验证，Attention 和 GEMM 内核比专家写的算子库还快，分别是 2.461 ms 对 3 ms、1.794 ms 对 2 ms。

比这些数字更想分享的，是一路上关于人和 Agent 怎样配合的四条经验。

**一、先把问题定义对，再放手交给Agent。** 项目早期，我们让 Agent 直接推进整个编译器，计划和设计越写越完整，各模块却没有真正接通，被检查的可执行包来自一份固定样例。和 Agent 合作，写计划的成本很低，很容易出现计划跑到代码前面的情况。后来我们先让一个真实输入从 PyTorch 一路走到芯片上，后面的设计才有了落脚点。判断哪些事能放手，看的是问题的前提是否完整、结果能否检验，和实现难不难关系不大。我们对 e-graph 只有初步了解，照样能借 Agent 做成一个可用的优化；空间切分被过早定死时，Agent 实现得再完整，也补不回那些从没进入比较的方案。同类补丁反复出现时，值得问一句：新加的抽象是消除了一处不一致，还是只是给不一致又加了一层解释？Agent 很擅长做后一种。

**二、Agent需要独立于它的评价体系。** 在新硬件上，编译器和检查工具是一起长出来的，大多出自 Agent 之手。两者一旦共享同一个错误假设，测试全部通过，也只说明它们彼此一致。所以，原样导出的程序语义、独立算出的参考结果、实卡测量的条件，都不能为了让当前实现过关而随意改动。有了这些依据，Agent 就不必每次改完都等人判断。哪里还没改对、哪个方向没有收益，它可以根据验证和测量结果继续追查，决定下一步怎么尝试。能可靠评价的问题越多，能交给 Agent 连续决策的范围就越大。

**三、先测量，再优化。** Agent 凭直觉做的一些优化，回归测试都过了，提速却没超出测量波动。测试通过只说明程序结果正确，是否提速要另外测。拿到 profile，我们先让 Agent 解释热点是怎么产生的，再决定改什么；改完不只看当前负载，也看别的负载有没有变慢，因为在一个负载上有效的通用修改，换个负载可能就成了退化。没有收益的尝试也记下来，下一轮就不必再走这条路。

**四、把每次解决的问题沉淀下来**。Agent 解决眼前的问题很快，但如果经验只留在对话里，下一轮又得从头摸索。我们的做法是把收获落到工程里：在某个负载上验证有效的优化，写进编译器的通用规则，后续适用的程序自动受益；查清的根因和修复方法写进仓库文档，下一轮 Agent 先读文档再动手。

成熟平台上，GCC、Triton 和专家写好的内核、编译器能够校验正确性、评估性能。新硬件没有现成的这套支撑，需要人和 Agent 把这部分能力补起来。我们不必提前掌握所有解法，但问题怎么界定、用什么标准做评估，需要由人来确定。评价体系能覆盖更多类型问题，能交给 Agent 处理的研发工作也就更多。
