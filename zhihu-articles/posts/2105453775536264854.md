常驻智能体持续运行，在多个会话之间自行决定如何行动、何时行动。本指南将介绍它们的核心基础组件，以及这些组件如何协同工作。

过去几个月里，我们看到常驻智能体重新兴起。

常驻智能体具有状态，并且会主动行动，也就是说，它们能够跨会话管理上下文，并在没有直接监督的情况下采取行动。在底层，它们运行的[核心循环](https://www.anthropic.com/research/building-effective-agents)与其他智能体相同。区别在于外围架构：构成这一架构的基础组件决定了智能体何时唤醒、哪些信息会在各次运行之间保留，以及工作成果如何传递给用户。

这股复兴很大程度上源于近期模型的进步，这些进步使常驻智能体的运行变得更加切实可行。首先，最新模型具备更好的判断力：它们在理解用户意图以及判断何时需要向用户确认方面更加可靠。其次，智能的成本正在下降，而长周期任务受益最多。例如，在[一项长周期编程基准测试](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)中，Opus 5.5 每解决一个任务的成本比 Opus 5 低 78%，相比之下，在典型工作负载上的降幅为 40%。

客户已经开始询问我们，如何将这种体验集成到自己的产品中。一些公司希望让现有智能体更具主动性，另一些公司则希望从零开始构建。

本文将拆解常驻智能体背后的基础组件，并介绍它们如何协同工作。

## 常驻智能体背后的循环

常驻智能体实际上并非“始终在线”。这只是在描述用户体验。

实际上，智能体大部分时间都处于休眠状态，只会定期醒来工作。每一段工作过程称为一次**运行**（run）：智能体接收一个事件，完成任务，然后保存有关这次过程的信息。一次运行在一个**会话**（session）中进行，会话是消息和工具调用的记录。运行结束后，智能体重新进入休眠，而这一循环会无限期地重复。

## 核心基础组件

常驻智能体的外围架构包含五个核心基础组件：事件收件箱、定时器、记忆、权限和发件箱。下面逐一介绍。

### 事件收件箱

大多数 AI 智能体只有在用户发送消息时才会运行。相比之下，常驻智能体可以由多种类型的事件触发，包括 Webhook、计划任务和后台作业。

一种看似很有吸引力的做法，是让每个事件源直接调用智能体，但这种做法存在几种失效情形。例如，两个同时到达的事件可能启动相互竞争的运行，而一次崩溃可能导致某个事件彻底丢失。

这就是事件收件箱发挥作用的地方。每个事件源不再调用智能体，而是将事件发送到收件箱，由工作进程从中领取。

最简单的版本包含三个组件：

- 一个持久化的事件列表，通常是一张数据库表；
- 一个处理器，通常是 HTTP 端点，负责将事件写入列表；以及
- 一个工作进程，通常是后台服务，负责读取列表。

收件箱应跟踪每个事件的状态，并且可以依据事件源提供的唯一标识符对事件去重。关系型数据库很适合用作收件箱，每个事件都作为新行追加。我们建议从每个用户一个收件箱开始，但如果需要更高的并行度，也可以进一步拆分。

新事件到达时，处理器将事件写入收件箱并唤醒工作进程。工作进程读取待处理内容并启动一次运行。延续先前工作的事件，例如用户的回复，会恢复一个已有会话，而其他事件则会启动新会话。

接下来，工作进程将事件传给智能体循环，等待运行结束，再将对应事件标记为已完成。实现细节可能比较棘手，因此这里给出几条最佳实践：

- **处理器应迅速确认收到事件**。某些事件源，例如 Webhook 提供方，会将响应缓慢视为失败。处理器仍然可以执行轻量检查，但任何更深入的验证，例如检查提示词注入，都应在运行期间完成。
- **收件箱应作为事实依据**。工作进程被唤醒时，应先从收件箱拉取最新事件。这样，如果工作进程在运行中途终止，新的工作进程就能领取同一事件并重试。
- **同一时刻，一个收件箱只应有一个活跃的工作进程**。这样可以避免两次运行重复工作或相互覆盖。当新事件在运行中途出现时，可以将其留到下一次运行、并入当前运行，或者中断并重新启动。
- **工作进程应将待处理事件合并为一批。** 例如，如果用户连续发送几条消息，工作进程可以将它们合并到一次运行中，让智能体只需回复一次。

### 定时器

定时器与事件收件箱配合，让常驻智能体能够主动行动。定时器通常分为两类：后续跟进和周期计划。后续跟进是智能体为自己设定的截止时间，例如检查是否收到回复。周期计划则是按已知节奏重复执行的任务，例如每日新闻简报。

定时器保存在独立于收件箱的持久化存储中，通常是另一张数据库表。收件箱只应保存已经可以处理的事件。后续跟进和周期计划可以采用相似的数据结构，但周期计划还需要跟踪重复执行的规则。

定时器本身不会发起运行。相反，调度器——通常是一个后台服务——会按固定间隔轮询存储，并触发所有到期项目。每轮处理时，调度器会：

1. 扫描存储，找出已到期的定时器。
2. 根据类别更新每个定时器。 1. 后续跟进应标记为已完成。
2. 周期计划应将到期时间更新为下一次执行时间。
3. 向收件箱添加事件，并唤醒工作进程。

至于调度器，可以自行构建服务，也可以使用持久化执行引擎。

### 记忆

常驻智能体会在多次彼此分离的运行中工作，并依靠记忆保持连续性。

与事件收件箱和定时器类似，记忆也应有独立的存储。在我们的产品中，例如 Claude Code 的[自动记忆](https://code.claude.com/docs/en/memory)和 Messages API 的[记忆工具](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)，记忆以文件目录的形式实现。对于常驻智能体，这些目录应映射到持久化存储，通常是数据库或对象存储。这样，记忆的生命周期就能长于工作进程。

一条经验法则是：记忆只应保存智能体无法再次查询到的信息。如果某些内容已经存在于另一个系统中，例如问题跟踪系统，就应改为保存一个指向它的引用。以下是常驻智能体应存储的记忆类型：

- **用户指令：** 用户对智能体行为提出的任何指令，都应保存在专门的文件中，并在每次运行开始时加载。用户不会始终在场指导智能体，因此这些指令必须在各次运行之间保留。
- **用户笔记：** 智能体应保存它了解到的用户信息，例如用户的角色、偏好，或用户给出的任何纠正意见。可以先使用一个文件，随着笔记增多，再拆分为多个小文件。后一种情况下，每次运行开始时只加载索引，但智能体在需要更多细节时，可以将各个文件读入上下文。
- **历史消息：** 智能体应跟踪自己已经告诉过用户的内容，避免重复。它可以将这些内容存入一个独立文件，在每次运行开始时加载；也可以由工作进程加载智能体最近几条与用户交流的消息。
- **任务进度：** 对于每个进行中的任务，智能体都应维护一个进度文件，记录已完成的工作和尚未完成的工作。这样，任何一次新运行都可以读取该文件，从上次运行停下的位置继续。与用户笔记类似，每次运行开始时只加载索引，但智能体在需要更多细节时，可以将各个文件读入上下文。

**上下文窗口内部**

在开始任何工作之前，智能体会加载系统提示词、工具定义和记忆文件。这些初始上下文“开销”会出现在每次运行中，因此我们建议尽量保持精简，并使用[提示词缓存](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)降低成本。

新会话启动时，只包含这些上下文开销和触发运行的事件。相比之下，已有会话则会重新带入之前各次运行中的消息和工具调用。

如果会话变得过长，可以[压缩较早的消息](https://platform.claude.com/docs/en/build-with-claude/compaction)，也可以启动新会话。这两种方法都会损失细节，因此任何需要持久保留的信息，都应在过程中及时存入记忆。

### 权限

权限是常驻智能体风险最大的环节。一次运行持有用户的访问权限，而且按设计会在无人值守的情况下执行。对于每次工具调用，智能体都需要决定是自行继续、阻止执行，还是等待批准。

权限方面使用的组件与其他智能体相同：

- **凭据存储：** 常驻智能体往往需要密码或访问令牌等敏感的用户凭据才能发挥作用。[推荐的模式](https://code.claude.com/docs/en/agent-sdk/secure-deployment#credential-management)是在智能体环境之外设置代理，为发出的请求添加凭据。智能体发送不带凭据的请求，代理则在转发之前注入真实凭据。
- **自动模式：** 常驻智能体应能够在不需要用户持续输入的情况下工作。我们已经通过 Claude Code 的[自动模式](https://www.anthropic.com/research/claude-code-auto-mode)处理过这一问题的一种形式。自动模式使用分类器审查风险较高的操作，并阻止被识别为危险的操作，让 Claude 能够寻找更安全的方法。不过，对于最重要的决策，仍然需要用户审查。
- **延后执行的工具调用：** 在 Claude Code 中，[钩子可以延后执行某次工具调用](https://code.claude.com/docs/en/hooks#defer-a-tool-call-for-later)，并等待用户提供进一步输入。同样的模式也适用于常驻智能体：它们在执行某些操作前，可能需要澄清或获得批准。当调用被延后时，本次运行结束，会话则保存在调用进行到一半的状态。请求会展示给用户（例如通过使用 [MCP Apps](https://modelcontextprotocol.io/extensions/apps/overview) 构建的交互卡片），而用户的回答会作为事件返回收件箱。该事件会启动一次新运行，利用用户输入恢复已保存的会话。在延后执行的调用等待响应期间，工作进程仍可领取其他事件，因此智能体不会被阻塞。

### 发件箱

对于大多数 AI 智能体，响应会在生成过程中以流式方式发送给用户，让用户能够跟随 Claude 对问题展开推理、调用工具并撰写回答的过程。

相比之下，常驻智能体的大部分工作在后台进行。用户拿到的是结果和少量细节，而不是完整的逐步过程。

一次运行可以通过以下三种方式之一结束：

- 智能体向发件箱发送一条消息，
- 智能体决定没有任何内容需要发送，或者
- 智能体通过延后执行的工具调用，请求许可或进一步输入。

大多数常驻智能体只需一个直接向用户递送消息的“发送”工具就能满足需求。只有在你希望控制智能体的消息发送节奏，或者让智能体能够从错误中恢复时，才需要正式的发件箱。

发件箱是一张单独存放待发消息的表，与事件收件箱类似。此外，还需要一个类似于工作进程的分发器，通常也是后台服务。分发器读取待发送的消息，决定递送哪些消息，再将它们发送给用户。延后执行的工具调用所产生的请求，既可以经过发件箱，也可以直接展示在界面中。

除了递送机制，调整智能体发送消息的数量也很重要。发送过多消息的智能体会造成干扰，而发送不足的智能体则会遗漏用户需要知道的事情。我们建议构建评估来找到合适的平衡。实践中，最好让智能体一开始保持安静，再随着时间推移逐步赢得用户更多的注意力。

## 各个组件如何协同工作

五个基础组件的配合方式如下：

每次运行都始于收件箱中的一个事件，无论它来自用户消息、Webhook 还是定时器。当工作进程领取事件时，它会启动一次运行，并在新会话或已有会话中唤醒智能体。智能体读取记忆以获得基本背景，在权限范围内采取行动，然后将新了解到的内容更新到记忆中。运行结束后，智能体向发件箱插入一行记录，再由分发器将消息递送给用户。

这些环节共同形成一个循环。一次运行可以设置一个定时器，在稍后再次唤醒智能体；而当用户回复消息时，回答又会作为事件返回收件箱。每次运行都很短暂，但循环会无限期地继续下去，这正是智能体让人感觉始终在线的原因。
