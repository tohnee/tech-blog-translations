同一个模型，同一套 Agent 框架，有人做出来的东西能独立干活，有人做出来的天天翻车。差别很多时候是在于喂给模型的上下文。

这件事在前段时间有个沸沸扬扬的名字：上下文工程（Context Engineering）。

（由于作者比较装，本篇大量的特定名词保留原来的英文）

### 一、从提问到展示

Andrej Karpathy 打过一个比方：大模型是 CPU，上下文窗口是内存，上下文工程就是操作系统，决定每个时刻哪些数据该进内存。他给的定义是——把下一步恰好需要的信息，填进上下文窗口的精细手艺。

提示词工程关心的是这句话怎么措辞。上下文工程关心的是模型在回答那一刻，到底知道什么内容。

后者范围大得多：系统指令、工具定义、示例、对话历史、检索回来的文档、长期记忆、运行状态，全算。提示词只是最上面一层。Anthropic 把它称作提示词工程的自然演进——当任务从一问一答变成一个 Agent 跑几十上百轮、连续干几十分钟，你没法靠打磨一句话解决问题，得管理整个信息状态。

### 二、上下文会是会腐烂的

往窗口里塞的信息越多，模型表现不一定越好，到某个点还会明显变差。

Haystack 类测试给这个现象起了名字，叫上下文腐烂（context rot）：窗口里的 token 越多，模型准确回忆其中信息的能力就越差，没有哪个模型能幸免。

根子在架构。Transformer 让每个 token 都能注意到其他所有 token，n 个 token 就产生 n² 对关系。上下文一拉长，这份注意力被摊薄。加上训练语料里短文本远多于长文本，模型对长程依赖本来就缺乏经验。模型不会在某个长度突然失忆，而是像人疲劳一样，检索精度和长链推理一点点往下掉。

所以要把上下文当成有限资源，而且是边际收益递减的资源。模型也有一笔”注意力预算”，每个新 token 都在花这笔钱。

钱花得乱，具体有四种翻车方式：

- **上下文中毒** ：一句幻觉混进了上下文，后面的推理全建立在假信息上。
- **上下文分心** ：噪声盖过了模型从训练里学到的东西。
- **上下文混淆** ：多余信息干扰了本该给出的回答。
- **上下文冲突** ：上下文里几处内容互相打架，模型不知道听谁的。

### 三、上下文里都有什么

要管理它，先看清它由哪几类东西构成：

| 类别 | 内容 |
| --- | --- |
| 指令 | 系统提示词、工具描述、少样本示例、记忆里的规则 |
| 知识 | 检索回来的文档、事实、数据库查询结果 |
| 工具 | 工具调用的返回结果、环境反馈 |
| 状态 | 对话历史、中间思考、当前任务进度 |

Agent 在循环里一边调用模型、一边调用工具，工具反馈又决定下一步怎么走。每多一轮，可能相关的信息就多一批，必须反复筛选。这就是为什么 Cognition 直接说：做 Agent，上下文工程实际上是第一号工作。

### 四、写、选、压、隔

LangChain 把主流做法归成四个动作。记住这四个字，基本就抓住了上下文工程的全部操作面。

**写（Write）——把信息存到窗口外面。**

人干活会记笔记，Agent 也一样。草稿本会把信息写到文件或运行状态里，等需要时再取。Anthropic 的多智能体研究系统开场就把研究计划存进记忆，因为窗口一旦超过 20 万 token 会被截断，计划不能丢。跨会话的东西则交给长期记忆，ChatGPT、Cursor、Windsurf 都会根据和你的交互自动沉淀记忆。

**选（Select）——把相关信息拉进窗口。**

这是 RAG 的主场，但远不止检索文档。记忆要选示例、规则、事实。工具也要选：工具给太多、描述又互相重叠，模型会有点看花眼，对工具描述做语义检索、只把相关工具摆出来，有论文显示能把工具选择准确率提升三倍。代码库检索更难，单靠 embedding 随库变大会越来越不可靠，得 grep、文件搜索、知识图谱、重排序一起上。

**压（Compress）——只留下完成任务所需的 token。**

Claude Code 在窗口用到 95% 时会自动压缩，把整段交互轨迹总结一遍。最轻、最安全的压缩甚至不用模型，就是清理工具结果——一个工具在历史深处早就调用完了，模型为什么还要再看一遍原始返回？压缩的难点在取舍：压得太狠，会丢掉那些当时不起眼、后来才发现很关键的细节。

**隔（Isolate）——把上下文拆开。**

一个 Agent 扛不下整个项目，就派子 Agent 各自开一个干净窗口去钻具体任务，主 Agent 只负责规划和综合。子 Agent 可以烧掉几万 token 深挖，最后只交回一两千字的提炼。沙箱和状态对象也是隔离：把图像、音频这类吃 token 的中间对象放进环境变量或独立字段，模型只在真正用到时才看到。

### 五、即时检索，而不是预先塞满

早期应用习惯在推理前一次性把相关数据全部检索好、塞进窗口。Agent 时代更有效的做法是即时也就是just-in-time：手里只留文件路径、保存好的查询、网页链接这类轻量引用，运行时靠工具按需加载。

Claude Code 分析大数据库就是这么干的：写精准查询、存结果、用 head、tail 这类命令探数据，从头到尾不把整张表读进窗口。这和人一样——没人会把全部资料背下来，我们靠文件系统、收件箱、书签在需要时调取。

目录结构、命名约定、时间戳本身就是信号：一个叫 test_utils.py 的文件放在 tests 目录和放在 src/core_logic 目录，含义完全不同。Agent 边探索边获取，一层层拼出理解，这叫渐进式披露。代价是运行时探索比读预计算数据慢，还得给它好的工具和导航规则，否则它会在死胡同里浪费上下文。

实际系统多用混合策略：少量稳定内容（比如 CLAUDE.md、规则文件）开场就放进来，其余交给 Agent 即时探索。法律、金融这类内容变化慢的场景，混合策略尤其合适。

### 六、长程任务的三件套

当一个任务的 token 总量超过窗口，比如大规模代码迁移、几小时的研究项目，得靠三个专门手段。

**压缩（Compaction）** ：把接近上限的对话高保真总结，带着摘要在新窗口里重启，保留架构决策、未解决的 bug、关键实现细节，丢掉冗余工具输出。

**结构化记笔记** ：Agent 定期把内容写进窗口外的持久笔记，之后再读回来。有个让 Claude 玩宝可梦的实验很能说明问题——Agent 在数千步游戏里自己记账，记录”过去 1234 步在一号路练级，皮卡丘离目标还差 2 级”，还自绘地图、记录招式克制关系，上下文重置后读笔记接着练，一玩就是几小时。

**子 Agent 架构** ：前面说过，适合并行探索的复杂研究。

三者按任务选：来回对话多用压缩；有清晰里程碑的迭代开发用记笔记；需要并行深挖的研究用子 Agent。代价也要清楚——Anthropic 报告过多 Agent 系统最多会用到普通对话 15 倍的 token。

### 七、看不见的就没办法优化

上下文工程不是一次性的写作，而是每一轮都要重新决策的循环。要让这个循环转起来，先得有两样东西：

一是能看清数据的地方，追踪每一步的 token 消耗和上下文构成，才知道力气该花在哪；二是能快速验证的手段，每次改动到底让 Agent 变好了还是变差了，得靠评估说话，不能凭感觉。可观测性和评估，是上下文工程的地基。

### 结尾

上下文工程的指导原则只有一条：找到那组最小的、高信号的 token，让期望结果最可能发生。注意最小不等于短——该交代的信息不能省的同时每一个进窗口的 token 都得有它的用处。
