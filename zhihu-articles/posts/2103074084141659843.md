## 一、导引：为什么需要引入计算图这个概念？

喜欢本地部署的朋友应该知道，推理框架有很多种，例如 llama.cpp、NInfer、vLLM、SGLang 等。

这些框架在设计上有不同的侧重点。

以 llama.cpp 和 NInfer 为例：

- llama.cpp 追求通用性和硬件适配能力，希望通过统一的计算抽象支持不同模型架构和计算后端。
- NInfer 更强调特定模型和目标硬件上的执行效率，将模型架构、权重绑定和计算路径显式组织起来，减少通用抽象带来的复杂度。

这两种设计思路有什么区别？

其中一个重要区别，就是如何组织模型的计算过程。

llama.cpp 使用 GGML 计算图，将模型中的矩阵乘法、加法、RMSNorm、Softmax、Attention、FFN 等操作组织成一张有向无环图（DAG）。

通过这种方式，模型架构可以被拆分成一系列具有明确计算语义的算子，再通过 Tensor 之间的依赖关系将算子连接起来。

当需要适配一个新的模型时，只要能够将模型的计算过程映射到已有算子，或者补充必要的新算子，就可以利用现有的计算图、内存规划和 Backend 执行体系。

而另一种思路是针对特定模型架构，直接编写对应的计算过程：

```text
模型输入
   |
Embedding
   |
RMSNorm
   |
Attention
   |
  FFN
   |
  输出
```

每个计算步骤由专门的代码组织，不需要先构建一套通用的模型计算图抽象。

这种设计可以更直接地控制计算路径、内存访问和 Kernel 调度，但模型架构适配、维护和扩展也更依赖专门的实现。

需要强调的是，计算图并不是越通用就越慢，也不能简单认为没有通用计算图就一定更快。实际性能还取决于 Kernel、算子融合、内存布局、数据传输、CUDA Graph 和硬件适配等因素。

那么，计算图究竟是什么？

### 1.1 什么是计算图？

我们可以将大模型的计算过程拆分成很多小的计算操作。

例如 Transformer 中的：

- 矩阵乘法（MatMul）
- 加法（Add）
- RMSNorm
- RoPE
- Softmax
- Attention
- FFN
- 激活函数

这些操作就是计算图中的基本计算节点。

通过 Tensor 将这些节点连接起来，就形成了完整的计算关系。

例如，一个简单的 Transformer Block：

```text
              Input
                |
             RMSNorm
                |
          +-----+-----+
          |     |     |
         Wq    Wk    Wv
          |     |     |
          +-----+-----+
                |
            Attention
                |
             Residual
                |
               FFN
                |
             Residual
                |
              Output
```

这张图表示的是计算过程以及各个计算操作之间的数据依赖。

从数学角度，可以将计算图定义为：

$$ G=(V,E) $$

其中：

- $V$：计算节点集合。
- $E$：节点之间的有向边，表示数据依赖关系。

计算图的核心价值是：

**不再单纯按照代码的先后顺序理解计算，而是按照数据依赖关系组织和执行计算。**

例如：

$$ x=a+b $$

$$ z=c\times d $$

这两个运算互相独立，因此理论上可以并行执行。

但是：

$$ y=x\times z $$

必须等待前面两个计算完成。

计算图能够显式描述这种依赖关系，为后续的计算调度、内存管理和计算优化提供基础。

### 1.2 计算图解决了什么问题？

我认为可以归纳为三个方面。

**第一，计算表达。**

将不同模型的计算逻辑统一表达为算子和 Tensor 之间的关系。

**第二，计算调度。**

通过节点之间的依赖关系，确定合法的执行顺序，并为并行执行创造条件。

**第三，计算优化。**

通过分析整个计算过程，可以进行内存规划、算子融合、无效计算消除以及计算图复用等优化。

因此，计算图并不只是将模型拆成几个小算子，它还是连接模型架构、内存管理和实际计算执行的重要抽象。

## 二、计算图的基本组成

理解 GGML 计算图，首先要理解三个基本概念：

1. Tensor
2. Op
3. Graph

### 2.1 Tensor：计算图中的数据载体

在深度学习中，Tensor 是最基本的数据组织形式。

例如：

一个向量：

$$ A\in\mathbb{R}^{4} $$

一个矩阵：

$$ B\in\mathbb{R}^{4096\times4096} $$

一个三维张量：

$$ C\in\mathbb{R}^{d\times n_h\times n_{tokens}} $$

它们都可以使用 Tensor 表示。

在 GGML 中，Tensor 不仅表示数据，还携带与计算有关的信息。

可以抽象为：

```cpp
struct Tensor {
    DataType type;       // 数据类型
    int64_t ne[4];       // 各维度的元素数量
    size_t nb[4];        // 各维度的字节步长

    OpType op;           // Tensor 对应的计算操作

    Tensor * src[...];   // 输入 Tensor

    void * data;         // 数据地址
};

```

这是一个帮助理解的简化结构，并非 GGML 当前源码中的完整定义。

其中：

| 成员 | 作用 |
| --- | --- |
| type | Tensor 的数据类型，例如 FP32、FP16、量化类型 |
| ne[] | 每个维度的元素数量 |
| nb[] | 每个维度的字节步长 |
| op | 当前 Tensor 对应的计算操作 |
| src[] | 当前计算依赖的输入 Tensor |
| data | 与 Tensor 数据关联的地址 |

这里有一个非常重要的设计：

**Tensor 既可以表示输入数据，也可以表示某个计算操作的输出结果。**

例如：

- `a`：输入 Tensor。
- `b`：输入 Tensor。
- `x`：Add 操作的输出 Tensor。
- `y`：Multiply 操作的输出 Tensor。

因此，并不是只有模型权重才是 Tensor，中间计算结果同样是 Tensor。

### 2.2 Op：计算节点

Op 是 Operation 的缩写，表示计算操作。

例如：

```cpp
ggml_add(ctx, a, b);

```

这里的 Add 就是一个计算操作。

GGML 中有大量不同的 Op，例如：

- `GGML_OP_MUL_MAT`：矩阵乘法。
- `GGML_OP_ADD`：加法。
- `GGML_OP_MUL`：乘法。
- `GGML_OP_NORM`：归一化。
- `GGML_OP_ROPE`：旋转位置编码。
- `GGML_OP_SOFT_MAX`：Softmax。

一个 Op 通常由输入 Tensor 和计算语义共同确定。

例如：

$$ x=a+b $$

对应：

```text
Tensor a ──┐
           ├── ADD ── Tensor x
Tensor b ──┘
```

需要注意：

**Op 表示计算语义，不等同于实际执行的 Kernel。**

同一个矩阵乘法 Op，可以根据后端、数据类型、Shape 和硬件架构，选择不同的 CPU 或 CUDA Kernel。

后面会专门介绍这一点。

### 2.3 Graph：组织计算节点及其依赖

现在假设我们有三个计算：

$$ x=a+b $$

$$ y=x\times c $$

那么它们之间形成了：

```text
a ──┐
    ├── ADD ── x ──┐
b ──┘              ├── MUL ── y
c ─────────────────┘
```

可以看出：

- ADD 依赖 a 和 b。
- MUL 依赖 x 和 c。
- y 是最终输出。

这就是一张计算图。

在 GGML 中，通过 `ggml_cgraph` 组织这些计算节点。

它有两个非常重要的概念：

**Nodes：需要执行的计算节点。**

**Leafs：参与计算但本身不需要作为计算节点执行的输入 Tensor。**

例如：

```text
leafs:
    a
    b
    c

nodes:
    x = ADD(a,b)
    y = MUL(x,c)
```

GGML 还会维护节点数量、访问记录以及其他计算图相关信息。

另外，计算图不一定包含所有已经创建的 Tensor，只包含与指定计算输出存在依赖关系的部分。

例如：

```cpp
ggml_tensor * x = ggml_add(ctx, a, b);
ggml_tensor * y = ggml_mul(ctx, x, c);

ggml_tensor * unused = ggml_mul(ctx, a, c);

ggml_build_forward_expand(gf, y);

```

虽然 `unused` 已经创建，但它不参与 y 的计算，因此不会因为存在于 `ggml_context` 中就自动进入以 y 为根的计算图。

这也是计算图能够进行无效计算消除的基础。

## 三、从一个简单的数学运算理解计算图的构建过程

现在从理论进入 GGML 代码。

暂时不考虑 Transformer，假设我们要实现：

$$ y=(a+b)\times c $$

从零开始构建一张计算图。

### 3.1 第一步：创建 Tensor

首先创建三个输入 Tensor：

```cpp
ggml_tensor * a = ggml_new_tensor_1d(
    ctx, GGML_TYPE_F32, 1
);

ggml_tensor * b = ggml_new_tensor_1d(
    ctx, GGML_TYPE_F32, 1
);

ggml_tensor * c = ggml_new_tensor_1d(
    ctx, GGML_TYPE_F32, 1
);

```

这里创建的是 Tensor 对象。

它们首先描述数据的类型、Shape 等信息，并不意味着已经完成了实际计算。

实际执行时，还需要为 Tensor 准备数据存储空间，并设置输入数值。

### 3.2 第二步：调用算子，构造计算关系

接下来：

```cpp
ggml_tensor * x = ggml_add(ctx, a, b);

ggml_tensor * y = ggml_mul(ctx, x, c);

```

注意，这两行代码非常关键。

执行：

```cpp
ggml_add(ctx, a, b);

```

并不是马上执行：

$$ x=a+b $$

而是创建一个新的 Tensor 对象，描述：

```text
Tensor x:

    op = ADD

    src[0] = a
    src[1] = b

    shape = 根据输入 Shape 推导出的输出 Shape
```

同理：

```text
Tensor y:

    op = MUL

    src[0] = x
    src[1] = c

    shape = 根据输入 Shape 推导出的输出 Shape
```

这里就建立了数据依赖关系。

因此：

**调用 GGML 算子，本质上是在创建一个新的 Tensor，并记录这个 Tensor 对应的计算操作和输入依赖。**

### 3.3 第三步：将 Tensor 组织成 ggml_cgraph

到目前为止，我们已经创建了一系列 Tensor。

但是这还不意味着已经有了一张完整的 `ggml_cgraph`。

首先创建 Graph：

```cpp
ggml_cgraph * gf = ggml_new_graph(ctx);

```

然后：

```cpp
ggml_build_forward_expand(gf, y);

```

这一步非常重要。

它会从最终输出 Tensor `y` 开始，沿着输入依赖关系向上遍历，把需要参与计算的节点加入计算图。

可以理解为：

```text
从 y 开始：

y
│
├── x
│   ├── a
│   └── b
│
└── c
```

遍历过程中：

1. 找到 y 的输入 x、c。
2. 继续找到 x 的输入 a、b。
3. 确认 a、b、c 是输入叶子节点。
4. 将需要计算的节点按照依赖顺序组织起来。
5. 使用访问记录避免重复遍历共享节点。

最终得到：

```text
leafs:
    a
    b
    c

nodes:
    x = ADD(a,b)
    y = MUL(x,c)
```

这里还涉及一个非常重要的概念：拓扑顺序。

### 什么是 Topological Sort？

假设计算图是：

$$ A\rightarrow B\rightarrow D $$

$$ A\rightarrow C\rightarrow D $$

B 和 C 都依赖 A，但是二者之间没有依赖关系。

因此合法的执行顺序可以是：

```text
A → B → C → D
```

也可以是：

```text
A → C → B → D
```

只要满足：

- A 必须先于 B 和 C。
- B 和 C 必须先于 D。

这种符合依赖关系的节点排序，就叫作拓扑排序（Topological Sort）。

GGML 的 Forward Expand 会遍历输入依赖，并组织出符合计算依赖的节点顺序。

需要注意，得到一个拓扑顺序，不等于所有无依赖节点一定会被并行执行。

拓扑顺序解决的是执行正确性，具体如何并行，还需要 Backend 的调度和执行机制配合。

### 3.4 第四步：执行计算图

现在计算图已经构建完成。

但是还没有真正完成：

$$ y=(a+b)\times c $$

还需要：

1. 为 Tensor 准备实际的数据存储空间。
2. 设置输入 Tensor 的数据。
3. 确定计算节点的执行后端。
4. 根据数据依赖执行节点。

GGML 可以通过 Backend Scheduler 执行计算图：

```cpp
ggml_backend_sched_graph_compute_async(
    sched,
    gf
);

```

这是简化的执行示意。实际使用中，还需要结合图分配、输入设置和执行同步等步骤。

至此，整个过程可以总结为：

| 阶段 | 主要操作 | 目的 |
| --- | --- | --- |
| 创建 Tensor | ggml_new_tensor_*() | 描述数据 |
| 创建 Op | ggml_add()、ggml_mul() | 建立计算关系 |
| 创建 Graph | ggml_new_graph() | 创建计算图对象 |
| 构建 Graph | ggml_build_forward_expand() | 收集依赖节点 |
| 内存规划 | Gallocr / Backend Scheduler | 准备计算空间 |
| 执行 Graph | Backend Compute | 真正执行计算 |

## 四、模型架构、逻辑计算图与运行时计算图

这一部分是理解 llama.cpp 计算图最重要的内容。

前面我们已经知道，计算图由 Tensor 和 Op 构成。

那么问题来了：

**大模型的架构明明是固定的，为什么 llama.cpp 每次 Decode 还需要根据当前任务构建计算图？**

要回答这个问题，必须先区分四个层次。

### 4.1 第一层：模型架构（Model Architecture）

模型架构定义了模型的基本组成。

例如，一个 Transformer 模型：

- Transformer 层数。
- Hidden Dimension。
- Query Head 数量。
- KV Head 数量。
- FFN Dimension。
- Attention 结构。
- 权重矩阵。

这些属于模型本身的定义。

假设一个模型使用：

```text
32 层 Transformer

Hidden Dimension = 4096

Query Heads = 32

KV Heads = 8

FFN Dimension = 14336
```

这些参数不会因为当前处理的是 1 个 Token 还是 128 个 Token 而改变。

### 4.2 第二层：逻辑计算图（Logical Graph）

根据模型架构，可以抽象出对应的计算关系。

例如：

$$ Q=XW_Q $$

$$ K=XW_K $$

$$ V=XW_V $$

$$ O=Attention(Q,K,V) $$

$$ Y=OW_O $$

对应：

```text
             X
          /  |  \
         /   |   \
       Wq    Wk   Wv
        |     |    |
        Q     K    V
         \    |   /
          Attention
               |
               O
               |
              Wo
               |
               Y
```

这张图表示模型计算的基本逻辑。

只要模型架构没有发生变化，整体计算逻辑就不会发生根本变化。

这就是逻辑拓扑图。

### 4.3 第三层：运行时计算图（Runtime Graph）

模型真正开始推理时，还需要结合当前输入和运行状态。

例如：

$$ X\in\mathbb{R}^{d\times n_{tokens}} $$

这里的 $n_{tokens}$ 表示当前计算批次中的 Token 数量。

假设模型的 Hidden Dimension 为 4096。

在 Decode 阶段：

$$ X:[4096,1] $$

在 Prefill 阶段：

$$ X:[4096,128] $$

两者计算逻辑仍然是：

$$ Q=XW_Q $$

但是具体 Tensor 的形状已经不同。

因此，运行时计算图需要携带具体的 Tensor 元数据，例如：

- Shape。
- Data Type。
- Stride。
- 输入 Tensor。
- KV Cache 索引。
- Attention Mask。
- 当前 Batch 和 Sequence 信息。

这就是为什么 llama.cpp 构建计算图时，不仅需要模型架构参数，还需要当前运行任务的参数。

### 4.4 第四层：执行计划（Execution Plan）

计算图构建完成后，还需要确定实际如何执行。

例如：

- 哪个节点由 CPU 执行？
- 哪个节点由 CUDA 执行？
- Tensor 数据存放在哪个设备？
- 是否需要跨设备传输？
- 如何划分计算子图？
- 内存如何分配和复用？
- 是否能够使用融合 Kernel？

这些已经不只是计算图的逻辑表达问题，而是实际执行计划的问题。

可以用下面的层次来理解：

```text
第一层：Model Architecture
        模型架构
              |
              v
第二层：Logical Graph
        逻辑计算关系
              |
              v
第三层：Runtime Graph
        具体 Tensor、Shape、数据依赖
              |
              v
第四层：Execution Plan
        内存规划、Backend 调度、Kernel
              |
              v
          实际执行
```

最终可以得到一个核心结论：

**模型架构决定计算图的基本逻辑，运行时输入和状态决定具体计算图实例，而后端调度和内存规划决定这张图如何被实际执行。**

## 五、为什么 Tensor Shape 会影响计算图？

前面已经提到，Tensor Shape 是运行时计算图中的重要信息。

下面具体分析 Shape 为什么重要。

### 5.1 Tensor Shape 决定需要多少内存

假设有一个矩阵乘法：

$$ C=AB $$

其中：

$$ A:[4096,4096] $$

如果：

$$ B:[4096,1] $$

那么：

$$ C:[4096,1] $$

但是，如果 B 变成：

$$ B:[4096,128] $$

那么：

$$ C:[4096,128] $$

计算节点仍然是同一个 MatrixMultiply。

但是输出 Tensor 占用的空间发生了变化。

假设使用 FP16：

| 输出形状 | 元素数量 | 内存大小 |
| --- | --- | --- |
| [4096, 1] | 4096 | 8 KiB |
| [4096, 128] | 524288 | 1 MiB |

这意味着图对应的内存规划也可能发生变化。

例如：

```text
A → B → C → D
```

在执行完 B 之后，如果 A 不再被其他节点使用，那么 A 所占据的临时内存就有可能被后续 Tensor 复用。

但如果 B 的输出从 8 KiB 变成 1 MiB，那么内存规划器就需要重新考虑空间大小、内存复用和峰值内存。

因此：

**Tensor Shape 影响内存规划，而内存规划是计算图执行准备工作的重要部分。**

### 5.2 Tensor Shape 决定实际计算规模

继续看矩阵乘法。

如果：

$$ B:[4096,1] $$

输出只有一列。

如果：

$$ B:[4096,128] $$

输出有 128 列。

GPU 在执行时，需要根据矩阵规模决定：

- CUDA Grid 大小。
- Block 的划分。
- 线程数量。
- 矩阵分块策略。
- 临时 Workspace 的大小。

甚至可能选择不同的计算 Kernel。

因此，虽然两种情况的逻辑拓扑可能完全一样，但是实际执行计划可能不同。

### 5.3 Tensor Shape 可能影响计算图拓扑

这里还需要强调一个区别：

Shape 变化不一定导致计算图拓扑变化。

例如：

```text
X → MatMul → RMSNorm → Attention → FFN
```

无论 X 包含 1 个 Token 还是 128 个 Token，都可以保持相同的节点连接关系。

只是 Tensor Shape 不同。

但是在某些模型和运行路径中，输入规模、序列数量、模型分支等因素也可能影响计算节点的组织方式。

例如：

- 某些 MoE 实现可能采用不同的专家选择计算路径。
- 不同 Attention 实现可能使用不同的算子组合。
- Prefill 与 Decode 可能采用不同的计算组织方式。

所以不能简单地说 Tensor Shape 改变了计算图拓扑。

更准确地说：

**Tensor Shape 首先改变的是计算节点的元数据，并可能进一步影响节点数量、算子组织、内存规划和执行计划。**

---

## 六、静态计算图与动态计算图

理解完模型架构和运行时计算图之后，还需要理解静态计算图与动态计算图。

### 6.1 静态计算图

静态计算图的典型思路是：

先定义计算关系，再执行计算。

例如：

```text
A → MatMul → B → Add → C
```

图构建完成之后，计算关系已经确定。

只要执行条件兼容，就可以重复使用这张图。

### 6.2 动态计算图

动态计算图可以在运行过程中，根据当前输入或者控制流程，动态构建计算关系。

例如：

```cpp
if (condition) {
    y = ggml_add(ctx, a, b);
} else {
    y = ggml_mul(ctx, a, b);
}

```

如果 `condition` 在构图之前由运行时逻辑决定，那么构建出来的图就可能不同。

不过需要注意：

**动态计算图不代表每一个数据值发生变化，都需要重新构图。**

例如：

```cpp
Q = ggml_mul_mat(ctx, Wq, X);

```

只要 Wq、X 的 Shape、Type 和计算布局兼容，X 中的数值每次都不同，也不意味着必须重新构建计算图。

相反，即使模型权重没有变化，如果 UBatch 大小、Sequence 数量或者计算路径发生变化，也可能需要构建不同的图。

### 6.3 GGML 属于什么类型？

GGML 更适合这样理解：

它通过 C/C++ 算子接口，在运行时使用具体的 Tensor 元数据构建计算表达，再把这些 Tensor 组织成 `ggml_cgraph`。

因此，它不是完全依赖符号 Shape 的静态计算图系统。

同时，它也不是每次都需要从零构建全部计算关系的简单动态系统。

通过 Graph Reuse 和 Buffer Reserve 等机制，GGML 可以在满足条件时复用之前的计算图和内存资源。

---

## 七、Tensor View：并不是每个 Tensor 都有独立的内存

在前面的 Tensor 介绍中，我们提到了：

```cpp
int64_t ne[4];
size_t nb[4];

```

这两个成员分别表示维度大小和字节步长。

这里需要进一步介绍 View、Permute、Reshape 和 Contiguous。

因为它们与计算图的内存规划密切相关。

### 7.1 View

View 可以理解为对已有 Tensor 的一块数据区域建立新的视图。

它不一定需要复制原来的数据，而是通过新的维度和地址偏移关系解释原有数据。

例如：

```text
原始 Tensor A

[1, 2, 3, 4, 5, 6, 7, 8]
```

我们可以基于它构建一个新的 Tensor 视图：

```text
Tensor B

[1, 2, 3, 4]
[5, 6, 7, 8]
```

B 并不一定需要重新分配一块数据空间。

### 7.2 Reshape

Reshape 改变 Tensor 的维度组织方式。

例如：

$$ A:[2,4] $$

变为：

$$ B:[4,2] $$

如果底层数据布局满足要求，Reshape 可以只改变 Tensor 的元数据，而不需要复制数据。

### 7.3 Permute

Permute 用于调整 Tensor 的维度顺序。

例如：

$$ A:[2,3,4] $$

调整维度顺序后：

$$ B:[4,2,3] $$

Permute 通常通过改变维度和步长的解释方式实现，不一定进行实际数据搬运。

### 7.4 Contiguous

Contiguous 的作用是将 Tensor 整理成连续存储布局。

如果原来的 Tensor 是一个非连续视图，那么为了让后续计算 Kernel 能够高效处理，可能需要重新整理数据。

此时就可能产生实际的数据复制。

因此：

| 操作 | 是否一定复制数据 |
| --- | --- |
| View | 通常不需要 |
| Reshape | 满足布局条件时不需要 |
| Permute | 通常只修改维度和步长解释 |
| Contiguous | 必要时进行数据整理和复制 |

这里有一个重要结论：

**创建一个新的 Tensor 对象，不意味着一定分配一块新的物理内存。**

这也是为什么分析 GGML 内存管理时，不能仅仅统计 Tensor 的数量，还需要分析它们之间的底层存储关系、View 和别名关系。

### 7.5 追踪一次 Tensor 转置：只改变 ne / nb，不移动底层数据

前面介绍了 GGML Tensor 中两个重要的成员：

- `ne[]`：每个维度的元素数量。
- `nb[]`：每个维度的字节步长（Stride）。

理解这两个成员，最直观的方法就是追踪一次 Tensor 转置。

假设有一个二维 Tensor，包含 6 个元素：

```text
a  b  c
d  e  f
```

每个元素占用 4 字节，底层内存连续存储。

### 7.5.1. 转置前：ne = [3, 2]，nb = [4, 12]

GGML 中，`ne[0]` 表示第一个维度的元素数量，`ne[1]` 表示第二个维度的元素数量。

其中，第一个维度的步长为 4 字节，第二个维度的步长为 12 字节。

因此，Tensor 的逻辑布局为：

**逻辑数据布局：**

|  | i0=0 | i0=1 | i0=2 |
| --- | --- | --- | --- |
| i1=0 | a | b | c |
| i1=1 | d | e | f |

**对应的内存偏移（单位：字节）：**

|  | i0=0 | i0=1 | i0=2 |
| --- | --- | --- | --- |
| i1=0 | 0 | 4 | 8 |
| i1=1 | 12 | 16 | 20 |

此时：

```cpp
ne = {3, 2};
nb = {4, 12};

```

例如，元素 e 的内存偏移为：

$$ offset(1,1)=1\times 4+1\times 12=16 $$

### 7.5.2. 转置后：ne = [2, 3]，nb = [12, 4]

现在对 Tensor 进行转置。

转置前：

$$ ne=[3,2] $$

$$ nb=[4,12] $$

转置后：

$$ ne=[2,3] $$

$$ nb=[12,4] $$

可以发现，转置只是交换了两个维度对应的 `ne` 和 `nb`。

**新的逻辑数据布局：**

|  | i0=0 | i0=1 |
| --- | --- | --- |
| i1=0 | a | d |
| i1=1 | b | e |
| i1=2 | c | f |

**对应的内存偏移（单位：字节）：**

|  | i0=0 | i0=1 |
| --- | --- | --- |
| i1=0 | 0 | 12 |
| i1=1 | 4 | 16 |
| i1=2 | 8 | 20 |

此时：

```cpp
ne = {2, 3};
nb = {12, 4};

```

注意观察：转置后的逻辑布局发生了变化，但是每个元素对应的内存偏移并没有发生变化。

### 7.5.3. 底层实际内存：始终没有发生变化

无论转置前还是转置后，底层物理内存始终是：

| 内存偏移（字节） | 0 | 4 | 8 | 12 | 16 | 20 |
| --- | --- | --- | --- | --- | --- | --- |
| 存储元素 | a | b | c | d | e | f |

也就是说，底层数据仍然按照原来的顺序存储：

```text
内存地址偏移：

   0     4     8     12    16    20
+-----+-----+-----+-----+-----+-----+
|  a  |  b  |  c  |  d  |  e  |  f  |
+-----+-----+-----+-----+-----+-----+

              物理内存
```

转置前后，底层数据没有发生任何移动。

### 7.5.4. 追踪同一个元素 b

为了更直观地理解，我们追踪元素 b。

**转置前：**

b 的逻辑坐标为：

$$ (i_0,i_1)=(1,0) $$

其内存偏移为：

$$ offset=1\times4+0\times12=4 $$

**转置后：**

b 的逻辑坐标变成：

$$ (i_0,i_1)=(0,1) $$

其内存偏移为：

$$ offset=0\times12+1\times4=4 $$

可以看到：

$$ 1\times4+0\times12 = 0\times12+1\times4 =4 $$

**同一个元素 b，在转置前后逻辑坐标发生了变化，但最终访问的仍然是同一个内存地址。**

### 7.5.5. 核心原理：ne 决定维度范围，nb 决定内存访问步长

对于二维 Tensor，元素的内存偏移可以表示为：

$$ \boxed{ offset(i_0,i_1)= i_0\times nb[0]+i_1\times nb[1] } $$

其中：

- $i_0,i_1$：元素的逻辑坐标。
- $nb[0],nb[1]$：对应维度的字节步长。
- `ne[]`：限制每个维度允许访问的坐标范围。

对于本例：

**转置前：**

$$ ne=[3,2],\quad nb=[4,12] $$

**转置后：**

$$ ne=[2,3],\quad nb=[12,4] $$

转置操作改变了 Tensor 的维度组织方式和内存访问步长，让同一块物理内存可以按照不同的逻辑矩阵布局进行访问。

因此，转置并不一定需要移动数据。对于这种通过交换维度和步长实现的视图转置，底层数据可以保持不变。

需要注意，这里讨论的是元数据视图式转置。如果后续计算要求连续存储布局，例如调用 Contiguous 操作，就可能需要重新分配空间并复制数据。

另外，本例中每个元素占用 4 字节，因此：

$$ 6\times4=24\text{ Bytes} $$

底层实际占用的是 24 字节，而不是 6 字节。

**最终理解：Tensor 不仅仅是一块内存，它还包含一套解释这块内存的规则。ne 决定逻辑维度，nb 决定如何根据逻辑坐标计算实际内存偏移。转置改变的是这套解释规则，而不一定改变底层数据。**

## 八、计算图与内存管理：Tensor 的生命周期

前面介绍了计算图的构建，现在开始讨论它如何影响内存管理。

这里最重要的概念是：

**Liveness Analysis（活跃性分析 / 生存期分析）。**

### 8.1 什么是 Tensor Lifetime？

假设计算图如下：

```text
Node 1：生成 A
Node 2：生成 B，使用 A
Node 3：生成 C，使用 B
Node 4：生成 D，使用 C
```

那么：

- A 在 Node 1 生成，在 Node 2 被最后一次使用。
- B 在 Node 2 生成，在 Node 3 被最后一次使用。
- C 在 Node 3 生成，在 Node 4 被最后一次使用。
- D 在 Node 4 生成，最后作为输出。

可以得到：

| Tensor | 生成位置 | 最后使用位置 |
| --- | --- | --- |
| A | Node 1 | Node 2 |
| B | Node 2 | Node 3 |
| C | Node 3 | Node 4 |
| D | Node 4 | 输出 |

每个 Tensor 从生成到最后一次使用，都有一个生命周期。

### 8.2 Memory Reuse

假设 A 已经完成最后一次使用，那么它对应的临时内存就可能交给后续 Tensor 使用。

例如：

```text
Node 1：生成 A
Node 2：生成 B，使用 A
Node 3：生成 C，使用 B
Node 4：生成 D，使用 C
```

在 Node 2 之后，A 不再被使用。

因此，A 所占据的内存可以考虑复用给后续 Tensor。

如果两个 Tensor 的生命周期不重叠，那么它们就有机会共享同一块物理内存。

这就是 Memory Reuse。

### 8.3 Peak Memory

Peak Memory 表示执行计算图过程中，某个时刻需要的最大内存容量。

如果每个 Tensor 都独立申请一块空间，那么内存占用可能很大。

但通过生命周期分析，不同时刻不再使用的 Tensor 可以复用内存。

因此，计算图不仅提供了计算依赖关系，还提供了分析 Tensor 生命周期的重要信息。

### 8.4 GGML Gallocr 的作用

这就是 `ggml_gallocr` 的重要作用。

它不是简单地为每一个 Tensor 单独调用 malloc。

而是分析计算图中 Tensor 的使用情况，结合 Buffer 类型、对齐、存储布局以及 Tensor 之间的别名关系，规划实际内存空间。

需要注意：

- 模型权重通常需要在推理过程中长期存在。
- KV Cache 需要跨多个 Decode 阶段持续保存。
- 中间激活 Tensor 通常具有相对较短的生命周期。
- View Tensor 可能与其他 Tensor 共享存储。
- 异步执行还需要考虑实际计算完成时间和资源复用的安全性。

因此，不能把所有 Tensor 都简单看成可以在最后一次使用后立即释放的临时对象。

这里需要区分持久内存和计算过程中的临时内存。

---

## 九、计算图与 Backend Scheduler：如何变成实际执行任务？

到这里，我们已经有了计算图，也了解了 Tensor 的内存规划。

但是计算图仍然没有回答一个问题：

**这些计算究竟由谁来执行？**

例如：

```text
A → MatMul → B → Attention → C
```

MatMul 可以交给 CUDA 执行，Attention 也可能交给 CUDA 或 CPU 执行。

如果不同节点由不同设备负责，还需要考虑设备之间的数据传输。

这就是 Backend Scheduler 的职责。

### 9.1 Op 和 Kernel 的区别

首先需要区分 Op 和 Kernel。

Op 表示计算语义。

例如：

```text
GGML_OP_MUL_MAT
```

表示矩阵乘法。

Kernel 则是实际执行该操作的底层实现。

例如，同一个矩阵乘法 Op，可以根据不同条件选择：

- CPU 矩阵乘法实现。
- CUDA 矩阵乘法实现。
- 不同数据类型对应的计算 Kernel。
- 不同 Shape 对应的专用 Kernel。

所以：

**Op 描述需要完成什么计算，Kernel 描述具体如何完成这项计算。**

计算图通常描述 Op，而不是直接描述 CUDA 的线程、Block 和 Grid。

### 9.2 Backend Assignment

Backend Scheduler 首先需要根据节点的计算类型、输入数据所在位置以及后端能力，为计算节点选择执行后端。

例如：

```text
Node A：MatMul       → CUDA
Node B：RMSNorm      → CUDA
Node C：某个不支持的 Op → CPU
Node D：FFN          → CUDA
```

这里要考虑：

- 当前 Backend 是否支持该 Op。
- 是否支持对应数据类型。
- 是否支持当前 Tensor Shape 和布局。
- 输入 Tensor 位于哪个设备。
- 是否需要进行数据传输。

### 9.3 Graph Split

当一张计算图需要由多个 Backend 执行时，Scheduler 可以将它划分为多个计算子图。

例如：

```text
完整计算图：

A → B → C → D

Backend：

A → CUDA
B → CUDA
C → CPU
D → CUDA
```

可能形成：

```text
Split 1：CUDA
    A → B

Split 2：CPU
    C

Split 3：CUDA
    D
```

不同 Split 之间可能存在 Tensor 数据传输。

### 9.4 Graph Allocation

确定 Backend 后，还需要为具体计算图分配 Tensor 所需要的空间。

包括：

- 为计算节点分配 Buffer。
- 确定 Tensor 在哪个 Backend Buffer 中。
- 对中间 Tensor 进行内存复用。
- 处理跨 Backend 的数据复制。

最后，才是真正的 Graph Compute。

因此，整个流程可以理解为：

```text
ggml_cgraph
     |
     v
Backend Assignment
     |
     v
Graph Split
     |
     v
Graph Allocation
     |
     v
Backend Compute
     |
     v
执行结果
```

实际 GGML 的 Scheduler 将这些工作组织在统一的 Backend 执行体系中，并不意味着每次执行都必须重新完成全部规划。

### 9.5 ggml_backend_sched 的作用

在 GGML 中：

```cpp
ggml_backend_sched_graph_compute_async(
    sched,
    gf
);

```

就是通过 Backend Scheduler 执行计算图的接口之一。

另外还有：

```cpp
ggml_backend_sched_split_graph()

```

用于图划分。

```cpp
ggml_backend_sched_alloc_graph()

```

用于计算图分配。

```cpp
ggml_backend_sched_synchronize()

```

用于同步调度器中的后端执行。

这几个接口可以帮助我们理解 Backend Scheduler 的职责。

需要注意，`graph_compute_async` 表示异步计算接口，并不意味着所有计算节点都会自动并行执行。实际执行顺序仍需要满足数据依赖，具体并行能力由 Backend、Kernel 和执行机制共同决定。

## 十、计算图优化：为什么计算图也可以提升性能？

前面介绍了计算图可能产生的抽象开销。

但是计算图并不一定会降低性能。

如果设计合理，它反而可以成为性能优化的基础。

### 10.1 Dead Code Elimination

无效计算消除。

前面已经介绍过：

```cpp
ggml_tensor * unused = ggml_mul(ctx, a, c);

ggml_build_forward_expand(gf, y);

```

因为 `unused` 不参与最终输出 y 的计算，所以它不会被加入以 y 为根的正常前向计算图。

这样就不需要执行无用计算。

### 10.2 Constant Folding

常量折叠。

如果某些计算只依赖于固定常量，而且可以在运行前完成，那么就可以提前计算结果，减少运行时计算量。

不过，在实际推理框架中，是否能够折叠还取决于算子实现、输入是否真正被视为常量，以及相关优化机制。

### 10.3 Operator Fusion

算子融合。

例如：

```text
MatMul
  |
Add
  |
Activation
```

如果每个操作都单独启动一个 GPU Kernel，就可能产生：

- 多次 Kernel Launch。
- 中间 Tensor 的显存读写。
- 多次 Kernel 间的依赖和同步处理。
- 临时内存占用。

通过算子融合，可以把多个操作合并成一个 Kernel：

```text
Fused Kernel

MatMul + Add + Activation
```

这样可能减少 Kernel Launch 和中间数据读写。

当然，并不是任意几个节点都可以融合，还需要满足算子语义、数据布局、硬件能力和数值精度等约束。

### 10.4 Graph Reuse

计算图复用。

如果下一次执行任务所需要的计算关系，与已有计算图完全兼容，那么就没有必要重新构建整张图。

可以直接复用已有图，更新其中需要变化的输入数据。

后面结合 llama.cpp 继续分析。

---

## 十一、结合 llama.cpp：计算图究竟是如何构建的？

前面的内容主要讲解计算图的通用理论。

现在回到 llama.cpp。

假设模型采用 Transformer + GQA。

当前有一个 UBatch 需要执行：

$$ X\in\mathbb{R}^{d\times n_{tokens}} $$

模型架构已经确定：

- 模型层数。
- Hidden Dimension。
- Query Head 数量。
- KV Head 数量。
- FFN Dimension。
- 各层权重。

那么构图过程可以这样理解。

### 11.1 获取模型及运行时参数

在 llama.cpp 中，构图需要结合模型信息和当前执行任务。

例如：

```cpp
struct llm_graph_params {
    const llama_model * model;

    llama_hparams hparams;

    llama_cparams cparams;

    llama_ubatch ubatch;

    ggml_backend_sched_t sched;

    const llama_memory_context_i * mctx;

    // 其他运行参数
};

```

这里是便于说明的结构示意，具体字段和组织方式需要以正在阅读的 llama.cpp 版本为准。

其中：

| 参数 | 作用 |
| --- | --- |
| model | 当前模型及其架构、权重 |
| hparams | Hidden Dimension、Head 数量等模型超参数 |
| cparams | 当前 Context 的运行配置 |
| ubatch | 本次参与计算的 Token 和 Sequence 信息 |
| sched | Backend Scheduler |
| mctx | 当前 Memory Context，提供 KV Cache 等运行时状态 |

这里有一个特别重要的地方：

构图过程不仅需要模型参数，还需要当前 UBatch 和 Memory Context。

这说明 llama.cpp 构建的不是一张单纯表示模型结构的图，而是结合当前推理任务生成的运行时计算图。

### 11.2 创建输入 Tensor

例如：

- Token Embedding。
- Position。
- KV Cache 索引。
- Attention Mask。
- 其他模型运行时需要的数据。

这些 Tensor 描述本次计算需要使用的输入。

例如：

$$ X:[d,n_{tokens}] $$

如果当前处理 1 个 Token：

$$ X:[d,1] $$

如果当前处理 128 个 Token：

$$ X:[d,128] $$

具体的 Attention Mask、KV 索引等，也可能根据当前 Memory Context 和 Sequence 状态创建。

### 11.3 按照模型架构构建计算节点

例如：

```cpp
Q = ggml_mul_mat(ctx, Wq, X);

K = ggml_mul_mat(ctx, Wk, X);

V = ggml_mul_mat(ctx, Wv, X);

```

然后：

```cpp
Q = ggml_rope(ctx, Q, ...);

K = ggml_rope(ctx, K, ...);

```

接下来进行 Attention：

```cpp
O = ggml_flash_attn_ext(ctx, Q, K, V, ...);

```

这里使用的是简化示意，实际模型可能使用不同的算子组合和 Attention 实现。

最后再构建输出投影、残差连接和 FFN 等节点。

对于 GQA，还需要考虑 Query Head 数量与 KV Head 数量之间的关系。

对于 MLA，则需要构建 Latent KV 相关计算。

对于 Gated DeltaNet，则需要考虑状态更新和门控递归计算。

因此，不同模型架构会对应不同的计算逻辑。

### 11.4 生成 ggml_cgraph

计算节点构建完成后，再以最终需要的输出 Tensor 为根，建立完整计算图。

```cpp
ggml_cgraph * gf = ggml_new_graph(ctx);

ggml_build_forward_expand(gf, output);

```

这里得到的计算图已经包含本次计算实际需要的 Tensor 和 Op 依赖。

### 11.5 Backend Scheduler

计算图构建完成后，交给 Backend Scheduler。

Scheduler 根据计算节点和后端支持情况进行分配、划分、内存规划和执行准备。

最后通过：

```cpp
ggml_backend_sched_graph_compute_async(
    sched,
    gf
);

```

执行计算。

至此，整个流程可以总结为：

```text
1. 获取模型与运行时参数

   model

2. 创建输入 Tensor
```

## 十二、KV Cache 与计算图究竟是什么关系？

这一部分对于理解 llama.cpp 尤其重要。

因为在 `llm_graph_params` 中，我们看到了：

```cpp
const llama_memory_context_i * mctx;

```

这说明运行时计算图需要结合当前 Memory Context。

**KV Cache 是计算图执行时需要访问和更新的运行时状态。**

可以分成三个部分理解：

| 概念 | 作用 | 生命周期 |
| --- | --- | --- |
| 计算图 | 描述 KV Cache 如何参与计算 | 随运行任务构建或复用 |
| KV Cache Buffer | 保存历史 Token 的 K、V 数据 | 跨多个 Decode 持续存在 |
| Memory Context | 描述本次计算如何访问和更新 Memory | 与当前计算批次有关 |

例如：

第一次 Decode：

```text
输入 Token A
    |
计算 K_A、V_A
    |
写入 KV Cache
```

第二次 Decode：

```text
输入 Token B
    |
计算 K_B、V_B
    |
读取 KV Cache 中的 K_A、V_A
    |
与 K_B、V_B 一起参与 Attention
    |
更新 KV Cache
```

两次计算涉及的模型架构完全相同，但访问的 KV Cache 内容和位置不同。

因此，需要区分三个问题：

1. KV Cache 的物理存储是否变化？
2. 本次计算图的输入和访问方式是否变化？
3. 计算图的拓扑结构是否变化？

这三件事情不是一回事。

例如，KV Cache 中历史数据发生变化，并不意味着计算图的拓扑一定发生变化。

同样，Memory Context 发生变化，也不意味着一定需要重新构建整张计算图。

## 十三、GGML 中几个重要对象的关系

最后，将前面涉及的几个重要对象放在一起。

| 对象 | 管理内容 | 主要职责 |
| --- | --- | --- |
| ggml_context | Tensor 元数据对象等 | 创建和管理 Tensor 描述对象 |
| ggml_tensor | Shape、Type、Stride、Op、Src、Data 关联 | 表示数据和计算关系 |
| ggml_cgraph | Nodes、Leafs | 组织计算节点及依赖 |
| ggml_backend_buffer | 后端实际数据存储 | 管理具体后端的内存 |
| ggml_gallocr | Tensor 内存分配规划 | 分析生命周期、规划和复用内存 |
| ggml_backend_sched | Backend 分配和执行调度 | 后端划分、Buffer 分配、数据传输和执行 |

它们之间的关系可以理解为：

```text
ggml_context
     |
     | 创建
     v
ggml_tensor
     |
     | 记录 op / src / ne / nb
     v
ggml_cgraph
     |
     | 组织计算节点
     |
     +-------------------+
     |                   |
     v                   v
ggml_gallocr       ggml_backend_sched
     |                   |
     |                   |
内存规划              后端调度
     |                   |
     +---------+---------+
               |
               v
       ggml_backend_buffer
               |
               v
        Backend Kernel
               |
               v
            计算结果
```

这里需要特别注意：

`ggml_context` 主要管理 Tensor 元数据对象，并不意味着模型权重和全部中间计算数据都存放在它的 Arena 中。

实际数据可以由 Backend Buffer 管理。

因此，Tensor 对象和 Tensor 的实际数据存储，需要分开理解。

## 十四、总结：计算图究竟在整个推理框架中扮演什么角色？

通过上面的分析，可以得到一个比较清晰的认识。

计算图并不是简单地将 Transformer 拆成几个矩阵乘法和加法。

它实际上是连接模型架构与底层计算执行的重要抽象。

它至少解决了三个核心问题。

### 14.1 计算图解决计算表达问题

模型架构决定模型需要完成什么运算。

计算图将这些运算组织成 Tensor 和 Op 之间的依赖关系。

通过统一的计算表达，推理框架可以适配不同模型架构。

### 14.2 内存分配器解决资源问题

计算图中的 Tensor 具有不同的生命周期。

通过分析 Tensor 的 Shape、数据布局、依赖关系和生命周期，内存分配器可以规划 Buffer，复用临时内存，降低峰值内存需求。

这也是为什么 GGML 需要 `ggml_gallocr`。

### 14.3 Backend Scheduler 解决执行问题

计算图中的 Op 需要被转换成实际的计算任务。

Backend Scheduler 负责根据后端能力进行节点分配、计算图划分、内存准备和跨设备数据处理。

最后交给 CPU、CUDA、Metal 等 Backend 的 Kernel 执行。

这也是为什么 GGML 需要 `ggml_backend_sched`。

### 14.4 最终理解

可以用一张图概括整个过程：

```text
             模型架构
                 |
                 v
           逻辑计算关系
                 |
                 v
           运行时计算图
                 |
          +------+------+
          |             |
          v             v
      内存规划         后端调度
          |             |
          v             v
      Gallocr         Scheduler
          |             |
          +------+------+
                 |
                 v
           Backend 执行
                 |
          +------+------+
          |      |      |
          v      v      v
         CPU   CUDA   Metal
          |      |      |
          +------+------+
                 |
                 v
              推理结果
```

最后，我认为可以用三句话总结计算图：

**第一，计算图描述的是模型需要执行什么计算，以及计算之间存在什么依赖关系。**

**第二，计算图提供的信息可以用于分析 Tensor 生命周期、规划内存和优化计算过程。**

**第三，计算图本身不负责完成实际计算，最终还需要 Backend Scheduler 和底层 Kernel 将其转换成真正的执行任务。**

从这个角度看，理解 `ggml_cgraph` 只是理解 llama.cpp 的开始。

只有把 `ggml_tensor`、`ggml_gallocr`、`ggml_backend_buffer` 和 `ggml_backend_sched` 联系起来，才能真正理解 llama.cpp 从模型架构到 GPU 执行的完整过程。
