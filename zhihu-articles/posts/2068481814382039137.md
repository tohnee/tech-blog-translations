前两篇讲了 FSDP1 的 FlatParameter、FSDP2 的 DTensor、以及 TorchTitan 和 Megatron 两种把 FSDP2 落到生产的方式。

到这一篇，问题变成：FSDP2 那套 hook 加状态机的命令式编排还有没有再简化的空间？

SimpleFSDP 的答案是有。它把 FSDP 里 hook、event、prefetch、bucket、stream 编排全部扔掉，只留一个语义化的动作——参数是分片的 DTensor，前向计算前 `redistribute` 成 Replicate。剩下的性能问题全部丢给 `torch.compile` 的 graph pass 去解决。

用户视角完全不变，跑 `data_parallel(model, mesh, ...)` 就能训。

这一篇分四段。

- 第一段讲 SimpleFSDP 到底想解决什么问题。
- 第二段讲它是怎么实现的。
- 第三段讲编译器接手之后为什么能做到 FSDP2 做不到的调度优化。
- 第四段讲它的边界。

## 1. SimpleFSDP 的目标：把调度从运行时状态里搬走

先把 SimpleFSDP 的位置定一下。

它和 FSDP2 通信量完全一样：参数要 all-gather，梯度要 reduce-scatter，前向后要不要保留完整参数照样是取舍。所谓 Simple，指的是把这些动作用什么形式写下来。

FSDP2 用一整套 hook 加状态机命令式编排：`_pre_forward` 调 `unshard`、`_post_forward` 调 `reshard`、`_pre_backward_hook` 挂在输出张量上、`_post_backward` 挂在自定义 autograd.Function 上。每一步都是运行时的命令式执行。任何一个新功能（EP、CP、PP、float8）进来，都要在这套 runtime 里挖一块新地。

SimpleFSDP 想问的是：如果把这些动作用两句 DTensor 操作表达，调度决策全部搬到 `torch.compile` 的图变换里做，会怎么样？

这不是无损的搬迁。它换来两样 FSDP2 拿不到的能力：**跨层重排的自由度，还有用 GPU 实测代价来选择合并粒度。**

与 Spark Catalyst 引擎将数据 Shuffle 抽象为 Exchange 节点类似，SimpleFSDP 的编译器在捕获计算图时，会将所有跨 GPU 的数据移动意图强制归一化为 DTensor 的 redistribute 操作——这让分布式通信在编译器的中间表示（IR）中，退化成了仅涉及 concat、split 与 sum 的简单数学表达式。

而 Spark 的优化除了 RBO 外，还有 CBO 和 AQE 和 弹性资源调度，这都是未来 FSDP 演进方向。

## 2. SimpleFSDP 是怎么实现的

### 2.1 从一个 Linear 说起

假设有 8 张 GPU，模型只有一个 `nn.Linear(4096, 4096)`：

```text
class TinyModel(nn.Module):
    def __init__(self):
        super().__init__()
        self.fc = nn.Linear(4096, 4096)

    def forward(self, x):
        return self.fc(x)
```

SimpleFSDP 想让这段代码在完全不改的情况下跑成分布式版本。

`self.fc.weight` 常驻内存的形态是分片 DTensor。每张卡本地只留 `weight[i*512:(i+1)*512, :]`，形状 `[512, 4096]`。

用户写 `self.fc(x)` 进入 `nn.Linear.forward` 之后，PyTorch 会读 `self.weight`。

这时候 SimpleFSDP 已经把 `weight` 换成了一个 property，读它会调用 `ReplicateComputation.forward`，触发 all-gather，把 8 份分片拼回完整的 `[4096, 4096]`。

拿到完整权重后 `F.linear(x, full_weight)` 正常算。`full_weight` 是 DTensor 经过 `to_local()` 剥出来的 plain tensor，autograd 会记住这次剥离时声明的 `grad_placements=[Partial]`。

反向来到 `full_weight.grad` 这一层时，DTensor autograd 引擎看到 `Partial → Shard` 这条 placement 转换，自动插一个 reduce-scatter，把梯度还原成分片形态。

从头到尾用户没写一句通信，也没注册一个 hook。所有 collective 都是 DTensor placement 转换派生出来的副作用。

### 2.2 SimpleFSDP 如何使用

SimpleFSDP 只有一个用户 API：`data_parallel`。TorchTitan 里给 Llama 3 加数据并行就一句话：

```text
model = data_parallel(
    model,
    parallel_dims.world_mesh[("dp_shard_cp",)],
    mode="fully_shard",
    mp_policy=mp_policy,
)
```

`data_parallel` 内部遍历模型里所有 `nn.Module`，对每个模块的每个 direct-owned 参数做两件事：把参数换成分片 DTensor，然后把这个参数名替换成一个自动触发 all-gather 的 property。

具体代码如下所示：

```text
# 遍历模型的所有模块
modules = list(model.modules())

for mod in modules:
    params_dict = dict(mod.named_parameters(recurse=False))
    for p_name, p in params_dict.items():
        if p is not None and p.numel() > 0:
            # 第一步：把原始参数 p 替换成 DTensor 分片
            mod.register_parameter(
                p_name,
                nn.Parameter(distribute_tensor(p, device_mesh, param_sharding)),
            )
            # 第二步：把这个参数名替换成一个 property
            nn.utils.parametrize.register_parametrization(
                mod,
                p_name,
                ReplicateComputation(...),  # property 的 getter 逻辑
                unsafe=True,
            )
```

第一步：参数分片：distribute_tensor(p, device_mesh, param_sharding) 就是那把“魔法刀”。它会根据 device_mesh 和 param_sharding（比如 Shard(0) 表示按行切），把完整的权重 p 切分成 DTensor 分片，再注册回模块。

第二步：替换为 Property：nn.utils.parametrize.register_parametrization(…) 这一步，就是利用 PyTorch 的参数化（Parametrization）API，把 weight 这个属性的访问行为彻底改写

这里需要注意的是：FSDP2 里 DDP、FSDP、HSDP 是三份不太一样的实现，SimpleFSDP 是一份代码搭配不同的 placement tuple。

### 2.3 不侵入模型代码实现参数劫持

前两步做完，模型参数已经被切成了 DTensor 分片，存在 self._parameters 里。

但问题来了：用户代码里到处都在读 self.weight，期望拿到的是完整 tensor；而现在 self._parameters[“weight”] 里存的是分片。

怎么让 self.weight 的访问行为变成”从分片 DTensor 出发，触发 All-Gather”？FSDP2 的做法是在 _pre_forward 里做状态切换，代码量和心智负担都不小。这里换一种更轻量的方式——把 weight 替换成 property，property 的 getter 里调 redistribute。

关键 trick 在 `_register_parametrization`：

```text
def _register_parametrization(module, param_names, parametrization):
    param_name_to_property = {
        param_name: property(
            lambda self, pn=param_name: parametrization(self._parameters[pn])
        )
        for param_name in param_names
    }
    module_cls = type(
        f"SimpleFSDP{module.__class__.__name__}",
        (module.__class__,),
        param_name_to_property,
    )
    module.__class__ = module_cls
```

回到刚才那个 Linear 例子，跑完这四行后：

- `self.fc.__class__` 从 `nn.Linear` 变成动态生成的 `SimpleFSDPLinear`。
- `SimpleFSDPLinear.weight` 是一个 property，读它会调 `parametrization(self._parameters["weight"])`。
- `parametrization` 是 `ReplicateComputation` 的实例。
- `self._parameters["weight"]` 是刚才切好的分片 DTensor。

三层 dispatch 串起来：读 **`self.weight` → property getter → `ReplicateComputation.forward(shard_dtensor)` → 返回完整 tensor。** 这就是SampleFSDP 的主线逻辑。

用 `type()` 动态建子类比给实例挂 attribute 好在两处地方。property 定义在类上而不是实例上，对同一个类的所有实例统一生效；这个新类又只挂到当前模块类型上，不污染其他 `nn.Linear`。

这个 trick 有几个漂亮的点。

- 纯 Python，不侵入模型代码。任何你能想到的模型都不需要改 forward。
- 完全可 trace。redistribute 是一个普通函数调用，能被 Dynamo/AOTAutograd 完整地捕获到 graph 里，这是后面能靠编译器优化的前提。
- 梯度语义正确。因为 `redistribute` 是可微的，反向自动会产生 `Partial → Shard` 的 reduce_scatter，不需要额外注册 backward hook。

顺带提一个 checkpoint 的坑：

`state_dict()` 保存和加载走的是 `self._parameters` 直接访问，不走 property，所以 checkpoint 保存的是分片 DTensor，不会误触发 all-gather。 但 TorchTitan 里 `checkpoint.py::get_model_state_dict` 走的是稍微不同的路径，可能会走 property 引发不必要的 all-gather，得手动包 `disable_active_parametrization`。

### 2.4 一个函数搞定 DDP、FSDP、HSDP

接上一节，property 无侵入的拦截到 self.weight 后，把分片 DTensor 丢给了 ReplicateComputation.forward，它转手调 `replicate_compute`。它的核心逻辑剔除 TP/EP 兼容分支的核心逻辑就这几行：

```text
def replicate_compute(self, x: DTensor) -> torch.Tensor:
    output = x.redistribute(
        placements=[Replicate()] * self.device_mesh.ndim,
        forward_dtype=self.param_dtype,     # 前向 all-gather 时降 bf16
        backward_dtype=self.reduce_dtype,   # 反向 reduce 时用 fp32
    )
    if not self.full_dtensor:
        output = output.to_local(grad_placements=self.grad_placements)
    return output
```

我们来看下这段代码：

- `redistribute` 把 `Shard` 变成 `Replicate`，这是 DTensor 的原生操作，内部对应 all-gather；
- `forward_dtype` 让 all-gather 直接在 bf16 上做，通信量减半；
- `backward_dtype` 让梯度 reduce 保持在 fp32，精度不掉。

反向 reduce_scatter 是这么触发的：当我们执行上面代码中的 `to_local`，它会把 DTensor 拆回 plain tensor 时，通过 `grad_placements=[Partial]` 声明”这个 tensor 的梯度将来是 partial 状态”，于是反向传播时 DTensor 引擎自然会插入 `Partial → Shard` 的 reduce_scatter。

关键点在于 `redistribute` 和 `to_local` 都是可微算子。DTensor 的 autograd 引擎会记录每次 placement 转换，反向按逆向路径重新走一遍。关键在于正向的起点不同：

- `fully_shard`：正向从 `Shard` 开始，`redistribute` 把它变成 `Replicate`。反向时 autograd 沿着 `Partial → Shard` 走，产出 reduce-scatter。
- `replicate`：正向从 `Replicate` 开始，`redistribute(Replicate())` 不做通信，只是声明”我要保持 Replicate”。反向时 autograd 走 `Partial → Replicate`，产出 all-reduce。
- `hybrid_shard`：同时涉及两个维度，正向在 DP 维度从 `Shard` 开始，反向在 DP 维度走 reduce-scatter；TP 维度全程保持 `Replicate`。

正向的起点不同，反向的终点就跟着不同。正向起点是 `Shard`，终点就是 `Replicate`，反向回到 `Shard`；正向起点是 `Replicate`，反向就回到 `Replicate`。autograd 引擎做的只是”倒着走一遍”，不关心具体是什么模式。

所以同一份 `ReplicateComputation` 能覆盖三种模式，不是因为它内部写了三个分支，而是因为它把模式差异交给了 placement tuple 来表达，把执行交给了 autograd 引擎去推导。

### 2.5 MoE 场景的适配

2.4 节说的 ReplicateComputation 覆盖了纯 DDP、纯 FSDP、HSDP。但在 MoE 场景下，它有一个隐藏问题：梯度平均的系数（divide factor）不对。

正常情况下，FSDP 做 reduce-scatter 时，梯度会用世界大小（world size）做平均。因为每张卡拿到的样本数是总 batch 的 1/world_size，梯度平均后要除以 world_size 才能保证学习率一致。

但 DeepSeek-V3 那种 EP + FSDP 混用的场景里，MoE 参数只在一部分 GPU 上做 FSDP，非 MoE 参数在所有 GPU 上做 FSDP。样本却是按整个集群划分的。如果 MoE 参数的梯度平均只按它所在的子网大小来除，梯度就会偏大，训练就不稳。

DeepSeek-V3 的代码里有一个明确的处理：

```text
transformer_block.moe.experts = data_parallel(
    transformer_block.moe.experts,
    dp_mod_ep_mesh,  # 只在这个子网上做 FSDP
    dp_mode,
    mp_policy=mp_policy,
    shard_dim=experts_shard_dim,
    reduction_divide_factor=parallel_dims.fsdp_gradient_divide_factor,  # 用全局系数
)
```

注意 reduction_divide_factor 传的是 parallel_dims.fsdp_gradient_divide_factor（全局 FSDP 的除系数），而不是 dp_mod_ep_mesh.size()。这个系数会覆盖 FSDP 内部默认的平均因子。

SimpleFSDP 里，这个扩展点是一行子类解决的：

```text
class _ScaledPartial(Partial):
    def _reduce_shard_value(self, tensor, mesh, mesh_dim, shard_spec):
        tensor.div_(self.reduction_divide_factor)
        return super()._reduce_shard_value(tensor, mesh, mesh_dim, shard_spec)
```

原理很简单：grad_placements=[Partial] 里的 Partial 本身就是一个 “reduce 时除以 world size” 的标记。

_ScaledPartial 只是在这个标记上多挂了一个 reduction_divide_factor 参数——先按自定义系数除，再走父类原有的 reduce 逻辑。

为什么这个扩展在 SimpleFSDP 里是一行子类就能搞定？

因为通信路径本来就是”触发一个 Partial 的 reduce”，reduce 的除法系数正好可以做一个自然的钩子。FSDP2 里做同一件事要伸手到 reduce hook 里去改。

### 2.6 TP、EP 如何实现组合

如果参数已经被 TP 切过一次，比如 attention 里的 QKV weight 已经在 tp_mesh 上做了 Shard(0)，然后 SimpleFSDP 拿到这个 DTensor，想继续在 dp_mesh 上再做一次 Shard(0)，会发生什么？

问题是：DTensor 只能有一个 placement。 你不能在一个已经带 tp_mesh 的 DTensor 上再叠加一个 dp_mesh 的 Shard。distribute_tensor 只认一个 mesh，遇到已经是 DTensor 的参数就直接跳过。

所以 SimpleFSDP 需要一种方式把两个 mesh 合并成一个，同时保留两层分片语义。

FSDP2 用 _fsdp_param.py 里的 _StridedShard 来处理这事，得手动构造 spanned mesh、维护双层 placement。

而 SimpleFSDP 把这段逻辑抽出来叫 _distribute_dtensor，大约 70 行，做四件事：

1. 拼一个 spanned_mesh = concat(outer_mesh, inner_mesh)，把 dp_mesh 和 tp_mesh 拼成一个更高维的 mesh。
2. 根据 outer 和 inner 的 placement 组合，决定用普通 Shard 还是 _StridedShard（看外层分片的 stride 是否与内层分片对齐）。
3. 用 redistribute_local_tensor 把 local tensor 在 outer 层做一次 Replicate → Shard，得到 outer 层的分片结果。
4. 构造一个新的 DTensor，mesh=spanned_mesh，placements=(outer_placement, *inner_placements)。

对用户来说这一步是透明的。只要按顺序调用 apply_tp(model, tp_mesh) 然后 data_parallel(model, dp_mesh)，SimpleFSDP 会检测参数是不是已经是 DTensor，是的话就走 _distribute_dtensor，不是就走原生的 distribute_tensor。

runtime 侧还有另一个问题：

前向做 all-gather 时，redistribute 不能沿着 tp 维度也做一遍，否则会把 TP 切好的分片也拉成完整 tensor，破坏 TP 的语义。ReplicateComputation.

replicate_compute 里那段 non_dp_mesh_dims 的分支就是在处理这件事——把 2D DTensor 显式 to_local 再 from_local 到 1D DTensor，让 redistribute 只作用在 dp_mesh 上，完事后再把 DTensor 重新包回 tp_mesh。

它注释里非常明确说明了 “TODO: DTensor should support this mesh collapsing operation”，意思是 DTensor 本身应该支持”只在 mesh 的某个维度上做 redistribute”，SimpleFSDP 只是在等上游补齐这个能力。

## 3. SimpleFSDP 为什么比 FSDP2 快

到这里可能会问，SimpleFSDP 每次读 `self.weight` 都做一次 all-gather，那不是被 FSDP2 的 unshard 缓存和 prefetch 完爆？

对，但这是 eager 模式下的结论。SimpleFSDP 的赌注是：让代码保持”每次都通信”的朴素语义，把 bucket、reorder、prefetch 这些性能优化全部交给 `torch.compile` 的 graph pass 来完成。

一旦开了 `torch.compile`，整张前向和反向 graph 会被 AOTAutograd 抓出来。graph 里能看到所有的 `all_gather_into_tensor` 和 `reduce_scatter_tensor` 节点，以及它们和 matmul、attention 的数据依赖。

这时候做 bucketing（把小 all_gather 合并成大的）、做 reorder（把 all_gather 提前，让通信和前一层计算 overlap），都是纯 graph 层面的图变换，不需要跟运行时状态机搏斗。

### 3.1 如何 3 行实现 AC pass

先看一个具体例子：`reshard_after_forward`。

FSDP2 里这个 flag 控制 forward 结束后是立即释放完整参数（`True`）还是保留到 backward（`False`）。True 省显存但反向要重新 all-gather，False 省通信但占显存。这是典型的内存换通信（Memory-Communication Trade-off）——和 activation checkpointing 是同一个问题。

SimpleFSDP 没有 runtime 状态，不能像 FSDP2 那样在 forward 结束时判断要不要释放。但它有 graph pass：

在 AOTAutograd 的 joint graph 上，可以把 all-gather 节点标记成”反向重算”，让 activation checkpoint 的现有机制来接管这个决策。

具体做法在 `reshard_after_forward.py`。它是一个 FX graph pass，做的事概括起来是”找到所有 FSDP 触发的 all-gather 节点，把它们标记为 `MUST_RECOMPUTE`“：

```text
def annotate_fsdp_all_gather(gm, reshard_after_forward):
    for node in gm.graph.nodes:
        if is_wait_tensor_from_fsdp(node):
            ag_node = node.args[0]
            force_recompute_node(ag_node)       # all_gather 本身
            force_recompute_node(node)          # 后面跟的 wait_tensor
            for user in node.users:
                if user.target == torch.ops.aten.slice.Tensor:
                    force_recompute_node(user)
            if ag_node.all_input_nodes[0].target == torch.ops.prims.convert_element_type.default:
                force_recompute_node(ag_node.all_input_nodes[0])
    return gm
```

我们来分析下上面的代码：

`is_wait_tensor_from_fsdp` 负责识别节点：找的是 `wait_tensor` 节点，它的输入是 `all_gather_into_tensor`，并且这个 all_gather 的输入沿着单输入算子链回溯到 graph 的 placeholder（也就是模型参数）。这个模式匹配能区分”FSDP 的 all-gather”和”all2all 或 EP 的 all-gather”。

标记完之后，怎么变成 reshard 的效果？

靠 AOTAutograd 的 min-cut partitioner。

partitioner 拿到 joint graph 后，要决定哪些中间张量存到 tape 里、哪些在反向重算。看到 `MUST_RECOMPUTE` 标签，它就不保存这个节点的输出。前向 graph 里 all_gather 的输出照常传给下游计算，但不流向反向。等反向真正需要这个 tensor 时，partitioner 会在反向图里重新插入一个相同的 all_gather。

于是 `reshard_after_forward=True` 的效果就出来了：forward 结束后不保留完整参数，反向再 all-gather 一次。`False` 则相反：保存完整参数到 tape，反向直接用。FSDP2 里这两个 runtime 选择的物理效果，在 SimpleFSDP 里被统一成了 AC 的”重算 vs 存储”决策。

同一段代码还处理了两个边缘情况：

- all_gather 后面挂着的 `slice`（切分 pad 出来的多余部分）也要一起 recompute，否则反向拿不到正确形状。
- all_gather 前面如果有 dtype cast（比如 fp32 到 bf16），cast 也要标记 recompute，否则反向会强迫保留 fp32 版本，显存收益就没了。

FSDP2 里 `reshard_after_forward` 是运行时选择的两个分支；SimpleFSDP 把它翻译成”重算 vs 存储”这个编译器已经解决的问题，直接复用 activation checkpoint 的现有机制。同一件事换个说法，就搭上了别人已有的基建。

### 3.2 调度粒度：从模块到算子

FSDP2 的调度粒度是模块级的。

`fully_shard(each_TransformerBlock)` 把每一层 block 打包成一个 `FSDPParamGroup`，一次 all-gather 拉一整层的参数。

这个粒度在 forward 开始时就被冻结了：QKV 和 FFN 必须等同一批 all-gather 完成，哪怕 QKV 前向只要 300µs，FFN 要 2ms，QKV 也只能干等。想”让 QKV 单独提前发”，必须重新拆 fully_shard 的边界。

SimpleFSDP 把这个绑定关系解开了。

每次读 `self.weight` 产生一个独立的 all-gather 节点，编译器拿到的是最细粒度的 collective 序列。合并成多大的 bucket、按什么边界合并，是 inductor 的 graph pass 在拿到完整计算图之后才决定的——和模块边界无关。

用户可以在三种策略里选一种（见 `backend.py`）：

1. 默认后端（inductor / aot_eager）：不做额外 bucket，依赖 inductor 自身的 overlap 能力。
2. `auto_bucketing`：让 inductor 自动分析 graph 中的 collective，合并相邻的 all_gather 或 reduce_scatter，并做通信-计算 reorder。
3. `transformer_block_bucketing`：按 TransformerBlock 的 FQN 列表来 bucket——每个 block 是一个 bucket，加上 embedding 和 output projection。先按模块合并 collective，再跨模块做 reorder，让第 N 层的 all-gather 提前到第 N-1 层的 matmul 里。

第三种策略的效果最接近 FSDP2 的模块级 bucket，但多了一步”跨模块 reorder”，这是 FSDP2 做不到的——它的 pre_forward hook 只能在自己模块进入前触发，没法跳转到别的模块前面。

编译器优化的本质是，它拿到的是完整的 dataflow graph，而不是逐个触发的 hook。

所以它能看到”第 N 层的 all-gather 不依赖第 N-1 层的计算结果”，于是可以把通信提前。这是 FSDP2 的 runtime 编排根本做不到的事。

### 3.3 Prefetch：从静态规则到基于代价的规划

FSDP2 的 prefetch 是硬编码规则，逻辑大致长这样：

```text
def _prefetch_unshard_if_needed(self):
    # 如果当前 group 的反向计算快结束了（最后一个 backward chunk）
    if self._current_backward_chunk == self._num_backward_chunks - 1:
        # 往前数一层，开始 unshard
        prev_group = self._prev_ring_group
        prev_group._all_gather_async()
```

距离固定是 1，策略固定是”当前组快算完了，就拉前一组”。不涉及任何代价估计。它能 work，是因为 transformer 的层大小基本均匀——前一层的 all-gather 时间大致等于当前层的反向计算时间，预取一层刚刚好。

SimpleFSDP 的 prefetch 交给 inductor 的 OverlapScheduler.run。开启 custom_runtime_estimation 或 collective_estimator=“benchmark” 后，它会做四件事：

- 用 GPU 实测 benchmark 估计每个 matmul、attention、collective 的执行时间。
- 用这个时间给 collective 做优先级调度，让耗时最长的 collective 最先启动。
- 用 max_in_flight_gb=5 和 max_memory_increase_gb 约束内存，避免同时 in-flight 的 collective 撑爆显存。
- 用 max_compute_pre_fetch=200 限制单次预取的深度，防止过度预取。

成本模型显式跟踪两个指标：”有多少 ms 通信没被计算藏住”（exposed_ms）和”有多少 ms 本来能被藏住但没藏住”（hideable_exposed_ms）。调度算法本质上是在减少后者——把能藏的尽量藏起来。

静态规则和代价规划在普通 transformer 上差距不大。但在 MoE 或混合结构里，不同层的反向计算时间可能差好几倍——比如 DeepSeek-V3 的 MoE 层 compute 时间跳跃巨大。

FSDP2 固定预取一层，遇到 compute 短的层就来不及，遇到 compute 长的层又预取过多；

SimpleFSDP 拿到实测时间后，能针对每一层算出”当前反向 compute 周期内，预取几层最合适”，自动适配不均匀的结构。

### 3.4 Stream 编排：从显式 event 到隐式 dependency

前面两节主要介绍了，SampleFSDP 图层面的调度——编译器决定 all-gather 提前多少、合并多大、和哪一层 overlap。

但图层面的”串行 vs 并行”只是逻辑上的：reorder 把没有依赖的操作排成”可以并行”的姿势，真正让它们同时跑起来，还要靠 CUDA stream——把没有依赖关系的 kernel 发到不同的 stream 上。

FSDP2 Stream 编排这一步是手工做的。

- 代码里显式管理多个 CUDA stream：`all_gather_stream`、`reduce_scatter_stream`、`all_reduce_stream`、`all_gather_copy_in_stream`。
- 每一段 collective 结束时 `Event().record()`，下一步在正确的 stream 上 `wait_event`。写这段代码的人要自己规划：哪些操作可以并行、需要几条 stream、event 插在哪个位置。

这个规划基于假设：假设 all-gather 比 compute 快，就把 all-gather 提前 launch；假设 reduce-scatter 不会撞上下一个 forward 的 all-gather，就放同一条 stream。假设错了 overlap 就失效，得手工调。

SimpleFSDP 不写 stream 代码。

`_reorder_graph` 重排完节点顺序后，真正的 stream 分配交给 inductor 后端。它拿到重排后的 fx graph，按依赖关系把没有依赖的 collective 和 compute 分配到不同 stream 上并行发射。

这些 stream 决策是看着整张 graph 做的，能保证 overlap 依赖不被破坏。FSDP2 的 stream 编排只能看当前模块，看不到”三层之后有一个反向的 matmul 会等这个 all-gather”这种远距离依赖。

这就是为什么 3.2 的”跨层 reorder”和 3.3 的”代价规划”能真正转化为加速：reorder 创造了 overlap 的机会，stream 编排把机会变成 GPU 上实际并行的 kernel。

### 3.5 混合精度通信量减半是”免费”的

FSDP2 想在 all-gather 前先 cast 到 bf16，需要在 `foreach_all_gather` 内部维护 cast buffer，还得处理 cast 的时机（在 `all_gather_copy_in_stream` 上做，不能挤到主 stream）。相关代码在 `_fsdp_collectives.py`，大约几百行。

而 SimpleFSDP 就一行：

```text
output = x.redistribute(
    placements=[Replicate()] * self.device_mesh.ndim,
    forward_dtype=self.param_dtype,     # e.g. torch.bfloat16
    backward_dtype=self.reduce_dtype,   # e.g. torch.float32
)
```

DTensor 的 redistribute 原生支持这两个字段，编译到 fx graph 后就是 convert_element_type → all_gather_into_tensor 两个相邻节点。

类型转换变成一个普通的 fx 节点，和 matmul、add 没有区别。reshard_after_forward 里那个”cast 也要标记 recompute”的分支，就是因为 cast 在 graph 里是个独立节点，可以被单独标记。OverlapScheduler 也能看到它，把它放进 overlap 决策里一起调度。

FSDP2 把 cast 藏在专用 stream 上，调度器看不到，就没法把 cast 纳入 overlap 决策。SimpleFSDP 把 cast 暴露在 graph 里，让它和其他算子一样参与重排和 overlap。

所谓”免费”，指的不是通信量减半没有代价，而是”把这行优化加进去”这件事本身不需要额外代码——DTensor 的两个 dtype 参数就解决了。

## 4. SimpleFSDP 有什么问题

代价也需要说清楚。

**冷启动**。SimpleFSDP 强制 `fullgraph=True`，第一次编译要几分钟，模型稍大点半小时起，做小实验时经常等到怀疑人生。FSDP2 是 eager，进模型就能跑。

**动态形状**。FSDP2 对 dynamic shape 没有额外要求，SimpleFSDP 走 compile 路径遇到 dynamic 形状会 recompile。变长序列上会被坑。

**Per-parameter 精细控制**。FSDP2 允许在 module 级别配 `MixedPrecisionPolicy`、`OffloadPolicy`、`ReduceOp`，甚至给不同 module 用不同的 process group。SimpleFSDP 的所有决策都是 graph pass 层面的，per-parameter 的差异化很难表达。

**成熟度**。FSDP2 是主线，SimpleFSDP 还在 experimental 目录，边缘 case 一堆 TODO 待补。

除此之外还有几个绑死的假设。

**DTensor 得成熟**。`_distribute_dtensor`、`replicate_compute` 里的 mesh 塌缩、`_StridedShard` 兼容，都是在补 DTensor 现在没做完的能力。任何一个 collective 语义 DTensor 支持不好，SimpleFSDP 就要在源码里插一个兼容分支。

**`torch.compile` 得可用**。README 一句 “It is always recommended to open compile” 已经在告诉你这不是可选优化。eager 模式下每读一次 `self.weight` 就发一次 all-gather，没有 bucket 也没有 prefetch，性能会显著劣于 FSDP2。`reshard_after_forward` 是 pass 实现的，不开 compile 完全不生效，只能落到”所有完整参数常驻”这一档。

**`fullgraph=True` 得能满足**。任何一处 graph break 都会破坏后续 pass。用户自己的模型如果有 Python 副作用或 dynamic control flow，得先解决 graph 完整性问题才能用 SimpleFSDP。

代码规模也要客观理解。`simple_fsdp.py` 349 行是核心前端，`backend.py` 加 `reshard_after_forward.py` 是编译后端，模型接入代码另有 150 行左右。加上论文提到 TorchInductor 里那 2K LoC 的 bucketing 和 reorder pass，全景规模并不小。它的”简单”是分层意义上的：语义层小、优化层交给 compiler，而不是总代码量小。

SimpleFSDP 不是把 FSDP2 的复杂度消掉了，而是搬到了别人家里。搬走的这部分复用了 inductor 已经在做的调度基础设施，也就顺便享受了它未来的迭代。所谓 Simple 不是”代码量少”，是”不重复造轮子”。

## 5. 和 FSDP2 的对比

| 维度 | FSDP2 | SimpleFSDP |
| --- | --- | --- |
| 核心机制 | Module wrap + 4 个 hook + 状态机 | 参数化 property + DTensor redistribute |
| 参数替换 | nn.Parameter 替换成 FSDPParam | module.__class__ 动态换成子类，weight 变 property |
| 通信触发 | 手写 pre-forward hook 调用 all_gather | x.redistribute(Replicate()) 隐式触发 |
| 反向通信 | 手写 post-backward hook 调用 reduce_scatter | .to_local(grad_placements=[Partial]) 隐式触发 |
| overlap / bucket | runtime 手工用 stream + event + prefetch queue | torch.compile 的 graph pass |
| reshard_after_forward | runtime flag，forward 后手工 free | AC 标注 MUST_RECOMPUTE，partitioner 决定 |
| TP / EP 组合 | 专门的 2D DTensor 分支 | _distribute_dtensor 一个函数，ReplicateComputation 一个 mesh 分支 |
| eager 性能 | 好 | 差（设计上不追求） |
| compile 性能 | 好 | 好（设计目标） |
| 代码规模 | 几千行 | 350 行核心 + 90 行 pass + 每模型 150 行胶水 |
| 依赖 | 相对独立 | 深度依赖 DTensor 语义完备性 + compile pass |

## 6. 想快速跑起来的话

Llama3：

```text
CONFIG_FILE="./torchtitan/models/llama3/train_configs/llama3_8b.toml" \
  ./run_train.sh \
  --model.name simple_fsdp.llama3 \
  --compile.enable \
  --job.custom_config_module=torchtitan.experiments.simple_fsdp.job_config \
  --compile.backend "aot_eager" \
  --compile.graph_passes "transformer_block_bucketing"
```

DeepSeek-V3：

```text
CONFIG_FILE="./torchtitan/models/deepseek_v3/train_configs/debug_model.toml" \
  ./run_train.sh \
  --model.name simple_fsdp.deepseek_v3 \
  --compile.enable \
  --activation_checkpoint.mode "none" \
  --job.custom_config_module=torchtitan.experiments.simple_fsdp.job_config
```

三个开关值得记：

- `--compile.enable` 必须开，否则性能非常差，`reshard_after_forward` 也依赖 compile 侧的 AC pass 才能生效。
- `--compile.graph_passes` 决定 bucketing 策略，规模小可以先默认，规模上来后开 `transformer_block_bucketing`。
- `--parallelism.fsdp_reshard_after_forward` 有 `always`、`never`、`default` 三档。PP 场景默认 `never`，因为 per-microbatch 的 all_gather 无法 overlap，划不来。

面向训练性能时后端应该用 `inductor` 而不是 `aot_eager`，`aot_eager` 只是 pass 验证路径。

## 7. 小结

FSDP1 把参数拍扁塞进一个 1D buffer；FSDP2 把每个参数换成带 mesh 和 placement 的 DTensor，让 optimizer、checkpoint 零改动；TorchTitan 和 Megatron 分别用两种哲学落地了 FSDP 到生产；SimpleFSDP 把最后一步走完——运行时的 hook、状态机、prefetch 全部换成两句 DTensor 操作加一堆 graph pass。

这条演进的方向很明确：把分片语义从”运行时命令式代码”往”静态张量类型信息”迁移，然后交给编译器来做调度。

DTensor 会成为整个 PyTorch 生态的通用总线，模型架构的创新速度已经远超框架写死调度的迭代速度，抽象层不得不往上走。

Simple 不代表少做事，Simple 代表选对了抽象。

现在 FSDP 现在还属于”编译时优化已经很强”的阶段，运行时的自适应才刚刚开始。未来 FSDP 演进形态应该是一个能根据真实硬件反馈自我调整的分布式编译器。
