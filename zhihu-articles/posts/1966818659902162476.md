## 背景：图灵说，要有Python DSL

时值2025年，基于C++ Template的大干快上开发torch算子的时代即将落幕。大公司也认识到，机器的时间很值钱，但是人的时间可能更加值钱，于是能够加速开发迭代的各种Python DSL开始愈发重要了。一个标志性的事件是从Cutlass 4.0开始，老黄慷慨地向开发者提供了计算性能和Cuda C++不相上下，但是编译时间和编程难度都大大降低的Cute DSL。而今天，我们的主角是DSL界无可争议的苹果编译器——来自OpenAI的Triton。

## 认识Triton：欢迎来到并发编程的世界

Triton（希腊语：Τρίτων，为海神波塞冬之子特里同）是做高性能GPU算子并行计算开发的语言和编译器，在python代码中的标志是用于定义 Triton 内核的 triton.jit 装饰器。事实上，笔者在第一次看到Triton代码的时候，立刻就觉得“这不就是GPU版本的OpenMP”么。

下面以进行一维向量的加法 $(c = a + b)$ 为例，来品鉴一份OpenMP代码。

```cpp
void add(float *a, float *b, float *c, int n, int block_size, int num_threads) {
    if (num_threads > 0) {
        omp_set_num_threads(num_threads);
    }
    
    #pragma omp parallel for schedule(static)
    for (int i = 0; i < n; i += block_size) {
        int end = (i + block_size < n) ? i + block_size : n;
        for (int j = i; j < end; j++) {
            c[j] = a[j] + b[j];
        }
    }
}

```

该代码和一般的C唯一的区别在于这条编译器指令。

```cpp
#pragma omp parallel for schedule(static)

```

它会指示OpenMP的预处理器，将之后的代码块转译为多线程并行计算的范式，自动的在编译之前写出捕获上下文、Spawn线程、调度线程的语句。

事实上，这是比用户态更高层的抽象，甚至没有用到pthread库。相应的，用户也无法控制计算任务如何被分配到每个线程上，以及每个线程如何被调度到CPU NUMA。即便如此，我们还是对这个for loop做了并行优化，将所有数据分块以提高缓存命中率。

值得一提的是，OpenMP不会自动的为用户解决data harzard，因此我们需要格外注意线程乱序执行的顺序是否会影响计算结果。

（OpenMP计算库的主要先驱者是图灵奖得主Jack Dongarra，笔者有幸分别于Lugano的瑞士国家超算中心和深圳坂田基地的罗马广场得见其人，何其幸运！）

## 实现第一份Triton：今天开始我要自己上厕所

接下来我们尝试将CPU的经验进行迁移，尝试用triton实现该加法。下面的代码块定义了一个加法kernel：

```python
import torch
import triton
import triton.language as tl

@triton.jit
def add_kernel(x_ptr,  # *Pointer* to first input vector. 指向第一个输入向量的指针。
               y_ptr,  # *Pointer* to second input vector. 指向第二个输入向量的指针。
               output_ptr,  # *Pointer* to output vector. 指向输出向量的指针。
               n_elements,  # Size of the vector. 向量的大小。
               BLOCK_SIZE: tl.constexpr,  # Number of elements each program should process. 每个程序应处理的元素数量。
               ):
    # There are multiple 'programs' processing different data. We identify which program
    # 有多个“程序”处理不同的数据。需要确定是哪一个程序：
    pid = tl.program_id(axis=0)  # We use a 1D launch grid so axis is 0. 使用 1D 启动网格，因此轴为 0。
    # This program will process inputs that are offset from the initial data.
    # 该程序将处理相对初始数据偏移的输入。
    # For instance, if you had a vector of length 256 and block_size of 64, the programs would each access the elements [0:64, 64:128, 128:192, 192:256].
    # 例如，如果有一个长度为 256, 块大小为 64 的向量，程序将各自访问 [0:64, 64:128, 128:192, 192:256] 的元素。
    # Note that offsets is a list of pointers:
    # 注意 offsets 是指针列表：
    block_start = pid * BLOCK_SIZE
    offsets = block_start + tl.arange(0, BLOCK_SIZE)
    # Create a mask to guard memory operations against out-of-bounds accesses.
    # 创建掩码以防止内存操作超出边界访问。
    mask = offsets < n_elements
    # Load x and y from DRAM, masking out any extra elements in case the input is not a multiple of the block size.
    # 从 DRAM 加载 x 和 y，如果输入不是块大小的整数倍，则屏蔽掉任何多余的元素。
    x = tl.load(x_ptr + offsets, mask=mask)
    y = tl.load(y_ptr + offsets, mask=mask)
    output = x + y
    # Write x + y back to DRAM.
    # 将 x + y 写回 DRAM。
    tl.store(output_ptr + offsets, output, mask=mask)
```

该kernel可由下方代码launch：

```python
def add(x: torch.Tensor, y: torch.Tensor):
    # We need to preallocate the output.
    # 需要预分配输出。
    output = torch.empty_like(x)
    assert x.is_cuda and y.is_cuda and output.is_cuda
    n_elements = output.numel()
    # The SPMD launch grid denotes the number of kernel instances that run in parallel.
    # SPMD 启动网格表示并行运行的内核实例的数量。
    # It is analogous to CUDA launch grids. It can be either Tuple[int], or Callable(metaparameters) -> Tuple[int].
    # 它类似于 CUDA 启动网格。它可以是 Tuple[int]，也可以是 Callable(metaparameters) -> Tuple[int]。
    # In this case, we use a 1D grid where the size is the number of blocks:
    # 在这种情况下，使用 1D 网格，其中大小是块的数量：
    grid = lambda meta: (triton.cdiv(n_elements, meta['BLOCK_SIZE']), )
    # NOTE:
    # 注意：
    #  - Each torch.tensor object is implicitly converted into a pointer to its first element.
    #  - 每个 torch.tensor 对象都会隐式转换为其第一个元素的指针。
    #  - `triton.jit`'ed functions can be indexed with a launch grid to obtain a callable GPU kernel.
    #  - `triton.jit` 函数可以通过启动网格索引来获得可调用的 GPU 内核。
    #  - Don't forget to pass meta-parameters as keywords arguments.
    #  - 不要忘记以关键字参数传递元参数。
    add_kernel[grid](x, y, output, n_elements, BLOCK_SIZE=1024)
    # We return a handle to z but, since `torch.cuda.synchronize()` hasn't been called, the kernel is still running asynchronously at this point.
    # 返回 z 的句柄，但由于 `torch.cuda.synchronize()` 尚未被调用，此时内核仍在异步运行。
    return output
```

这两段代码有很多亮点，我们来逐一分析。

首先，我们有一行代码定义了一个名为`grid`的lambda函数：

```python
grid = lambda meta: (triton.cdiv(n_elements, meta['BLOCK_SIZE']), )
```

这个lambda函数接受一个参数`meta`，该参数是一个字典，其中包含内核的metadata。在这里，我们使用`meta`字典中的`BLOCK_SIZE`来获取每个块大小（即每个线程块处理的数据量）。然后，我们计算`n_elements`（总元素数量）除以块大小，就得到了需要启动的线程块的数量。总之，这个lambda函数返回一个tuple，其中包含一个元素，即线程块的数量。

需要注意的是，Triton内核启动时需要指定网格大小，由一个tuple表示。并且该tuple包含元素不能超过三个，因为Triton的launch grid是3D的。

接下来，我们有一行代码实际启动Triton内核：

```text
add_kernel[grid](x, y, output, n_elements, BLOCK_SIZE=1024)
```

这里，`add_kernel`是一个Triton内核函数，使用`[grid]`来指定内核启动的网格大小，圆括号内为传递的内核参数。`add_kernel[grid]` 方括号指定执行配置是triton特有的syntax sugar，所以严格的来说triton并不是python的子集。

然后，我们调用`add_kernel`并传递以下参数：

- `x`, `y`: 输入张量
- `output`: 输出张量
- `n_elements`: 总元素数量
- `BLOCK_SIZE=1024`: 这是一个编译时常量，指定每个线程块处理的元素数量。这里我们设置为1024。

具体来说，它会调用`grid`函数并传入一个元数据字典，该字典包含内核中定义的所有编译时常量（在这里，我们传递了`BLOCK_SIZE=1024`）。这一点需要格外注意，这里不会像C++lambda表达式里面的`&`一样捕获当前scope所有符号的引用，就是说这些编译时的变量`x, y, output, n_elements`是不会出现在`meta`里面的。

如果对lambda表达式的写法感到困惑的，请注意以下写法是完全等价的：

```python
def grid(meta):
    return (triton.cdiv(n_elements, meta['BLOCK_SIZE']), )

add_kernel[grid](x, y, output, n_elements, BLOCK_SIZE=1024)
```

最后需要澄清的一句是内核代码中的

```python
pid = tl.program_id(axis=0)
```

这里`tl.program_id` 会返回当前在执行的线程块在指定的维度上的index，根据这个序号我们可以计算出这个线程块要处理的数据开始位置的`offset` ，从而进行计算。相应的，这个`axis`的值只能是0，1，2。

总结的来说，以上triton代码的工作逻辑包括两部分，一部分定义单个线程块内的计算逻辑，另一部分在launch grid中负责启动这些内核。相比较于OpenMP，triton的线程块需要用户自主configure更多的内容，当然和巨大的性能增益相比，这几行代码都微不足道。

## **回头看Ascend C：太美丽了昇腾，还是看看远处的雪山吧家人们**

最后我们来看Ascend C中的加法kernel，举一反三，触类旁通一下。

为了理解下文，建议读者先浏览Atlas 800I A2 推理卡的硬件架构和其抽象拓扑。详情请见 [基本架构-硬件架构与数据处理原理-概念原理和术语-Ascend C算子开发-CANN社区版8.3.RC1.alpha003开发文档-昇腾社区](https://www.hiascend.com/document/detail/zh/CANNCommunityEdition/83RC1alpha003/opdevg/Ascendcopdevg/atlas_ascendc_10_0008.html)

```cpp
#include "add_custom_tiling.h"
#include "kernel_operator.h"
using namespace AscendC;

constexpr int32_t BUFFER_NUM = 2; // tensor num for each queue

class KernelAdd {
public:
    __aicore__ inline KernelAdd() {}
    __aicore__ inline void Init(GM_ADDR x, GM_ADDR y, GM_ADDR z, uint32_t totalLength, uint32_t tileNum)
    {
        this->blockLength = totalLength / GetBlockNum();
        this->tileNum = tileNum;
        this->tileLength = this->blockLength / tileNum / BUFFER_NUM;
        xGm.SetGlobalBuffer((__gm__ half *)x + this->blockLength * GetBlockIdx(), this->blockLength);
        yGm.SetGlobalBuffer((__gm__ half *)y + this->blockLength * GetBlockIdx(), this->blockLength);
        zGm.SetGlobalBuffer((__gm__ half *)z + this->blockLength * GetBlockIdx(), this->blockLength);
        pipe.InitBuffer(inQueueX, BUFFER_NUM, this->tileLength * sizeof(half));
        pipe.InitBuffer(inQueueY, BUFFER_NUM, this->tileLength * sizeof(half));
        pipe.InitBuffer(outQueueZ, BUFFER_NUM, this->tileLength * sizeof(half));
    }
    __aicore__ inline void Process()
    {
        int32_t loopCount = this->tileNum * BUFFER_NUM;
        for (int32_t i = 0; i < loopCount; i++) {
            CopyIn(i);
            Compute(i);
            CopyOut(i);
        }
    }

private:
    __aicore__ inline void CopyIn(int32_t progress)
    {
        LocalTensor<half> xLocal = inQueueX.AllocTensor<half>();
        LocalTensor<half> yLocal = inQueueY.AllocTensor<half>();
        DataCopy(xLocal, xGm[progress * this->tileLength], this->tileLength);
        DataCopy(yLocal, yGm[progress * this->tileLength], this->tileLength);
        inQueueX.EnQue(xLocal);
        inQueueY.EnQue(yLocal);
    }
    __aicore__ inline void Compute(int32_t progress)
    {
        LocalTensor<half> xLocal = inQueueX.DeQue<half>();
        LocalTensor<half> yLocal = inQueueY.DeQue<half>();
        LocalTensor<half> zLocal = outQueueZ.AllocTensor<half>();
        Add(zLocal, xLocal, yLocal, this->tileLength);
        outQueueZ.EnQue<half>(zLocal);
        inQueueX.FreeTensor(xLocal);
        inQueueY.FreeTensor(yLocal);
    }
    __aicore__ inline void CopyOut(int32_t progress)
    {
        LocalTensor<half> zLocal = outQueueZ.DeQue<half>();
        DataCopy(zGm[progress * this->tileLength], zLocal, this->tileLength);
        outQueueZ.FreeTensor(zLocal);
    }

private:
    TPipe pipe;
    TQue<QuePosition::VECIN, BUFFER_NUM> inQueueX, inQueueY;
    TQue<QuePosition::VECOUT, BUFFER_NUM> outQueueZ;
    GlobalTensor<half> xGm;
    GlobalTensor<half> yGm;
    GlobalTensor<half> zGm;
    uint32_t blockLength;
    uint32_t tileNum;
    uint32_t tileLength;
};

extern "C" __global__ __aicore__ void add_custom(GM_ADDR x, GM_ADDR y, GM_ADDR z, AddCustomTilingData tiling)
{
    KernelAdd op;
    op.Init(x, y, z, tiling.totalLength, tiling.tileNum);
    op.Process();
}

```

这份代码有以下需要重点理解的部分。

首先，我们定义了一个微型的三级流水线：

- `CopyIn`：从全局内存复制一个切片的数据到本地内存。
- `Compute`：从输入队列中取出张量，执行加法操作，结果存入输出队列，并释放输入张量。
- `CopyOut`：从输出队列中取出结果张量，复制到全局内存，并释放该张量。

为了保证每一个切片的三级流水线都是按顺序执行的，我们使用了三个指令队列进行信号同步，而队列中的成员都是local tensor的逻辑位置`VECIN` 和`VECOUT`，即AI Core中Vector核心的输入输出。

类似于Triton，我们的`KernelAdd` 中有以下两个内嵌函数：

- `GetBlockNum`：可用核心的个数
- `GetBlockId`：当前运行实例所在核心的序号

根据其序号，我们将对对应位置的切片进行运算。但我们需要认识到这份代码逻辑上和之前的triton代码有本质上的重大区别：在Triton的代码中，我们逻辑上启动了`n_elements/1024`这么多kernel（尽管不同的kernel可能被调度到同一个SM上）；但是在Ascend C的实践中，我们逻辑上启动了和物理核心一样多kernel，并且手动用指令队列进行了消息同步。相比较而言，Ascend C更加接近硬件，开发成本和学习难度也更高。

最后，聪明的你一定发现了我们采用了双缓冲技术，实现了计算与数据传输的并行化，使通信成本被大量掩盖。
