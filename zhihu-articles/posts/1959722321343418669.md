## 一、为何聚焦矩阵乘法？

在 Transformer 模型中，无论是 MLP 层的线性变换、注意力机制的 QKV 投影，还是最终的输出投影，绝大多数浮点运算（FLOPs）都集中在矩阵乘法操作中。这类运算具有“天然并行性”（embarrassingly parallel），能最大程度发挥 GPU 的硬件优势。更重要的是，矩阵乘法核函数的设计涵盖了 GPU 内存管理、计算调度、指令优化等核心技术，掌握它就等于掌握了高性能 GPU 编程的“通用工具箱”。

## 三、NVIDIA GPU 架构基础

要编写高性能 GPU 核函数，必须先建立清晰的硬件“心智模型”。本文以 Hopper H100 GPU 为核心分析对象——掌握 Hopper 架构后，无论是迁移到未来的 Blackwell、Rubin 架构，还是适配更早的 Ampere、Volta 架构，都只需针对性调整细节，核心逻辑保持一致。

从硬件顶层设计来看，GPU 核心承担两大任务：

- **数据移动与存储**（内存系统）
- **数据计算**（计算流水线）

H100 的硬件框图清晰体现了这一分工：蓝色组件对应内存与数据传输模块，红色组件则是高负载的计算单元。

## 3.1 核心硬件组件解析（以 H100 为例）

![](https://pica.zhimg.com/v2-949f42372c31e78afda511d6c1b74104_r.jpg)
*图1. NVIDIA Hopper H100 GPU*

### 3.1.1 流式多处理器（SM）

SM 是 GPU 计算的基本单元。H100 SXM5 型号的裸片（die）上集成 144 个 SM，实际产品中，SXM5 形态暴露 132 个，PCIe 形态暴露 114 个（部分 SM 因硬件良率等原因被“熔断”）。每个 SM 包含：

- **张量核心**：专门处理小分块矩阵乘法（如 `64x16 @ 16x256`），是实现高吞吐量的关键，大型矩阵乘法需拆解为多个小分块由张量核心并行计算。
- **CUDA 核心与 SFU**：CUDA 核心执行标准浮点运算（如 FMA 融合乘加 `c = a*b + c`）；SFU（特殊功能单元）处理超越函数（`sin`/`cos`/`exp`/`log`）与代数函数（`sqrt`/`rsqrt`）。
- **加载/存储（LD/ST）单元**：处理内存读写指令，与 TMA 加速器协同工作。
- **Warp 调度器**：每个 SM 配备多个调度器，负责为 32 线程组成的“warp”分发指令，单个调度器每周期可分发一条 warp 指令。
- **寄存器文件（RMEM）**：紧邻计算单元的高速存储，每个 SM 配备 256 KiB 寄存器（32 位精度），单周期每寄存器可传输 4B 数据，总带宽达 124 TB/s（132 个 SM 合计）。

### 3.1.2 内存层级结构

GPU 内存系统遵循“速度-容量”权衡原则：SRAM 速度快但容量小，DRAM 容量大但速度慢，通过多层级缓存实现“高速近距、低速远距”的存储架构，最大化系统吞吐量。H100 的内存层级如下（按速度从快到慢）：

![](https://pic2.zhimg.com/v2-59c06cfc6d28605c679d87cc0090cefb_r.jpg)
*图2.H100（SXM5）GPU 的内存层级结构*

详细如下表所示：

| 内存层级 | 类型 | 单 SM 容量 | 总容量（132 SM） | 带宽 | 延迟 | 核心特点 |
| --- | --- | --- | --- | --- | --- | --- |
| 寄存器文件（RMEM） | SRAM | 256 KiB | 33 MiB | 124 TB/s | 1 cycle | 线程私有，紧邻计算单元 |
| L1 缓存/SMEM | SRAM | 256 KiB | 33 MiB | 31 TB/s | 20-30 cycle | 共享物理存储，可软件配置比例 |
| GPC 分布式共享内存（DSMEM） | SRAM | 3.5 MiB（16 SM 集群） | - | - | - | GPC 内 SM 共享，支持跨 SM 通信 |
| L2 缓存 | SRAM | - | 50 MiB | 12-14 TB/s | ~200 cycle | 全局共享，分两个分区 |
| 设备内存（VRAM） | HBM（DRAM） | - | 80 GB（H200 达 141 GB） | 3 TB/s | ~500 cycle | 片外存储，全局内存载体 |

**关键结论**：

1. 高频访问数据需尽可能靠近计算单元（如寄存器、SMEM），减少对低速内存的依赖。
2. 设备内存（GMEM）是性能瓶颈重点——每访问一次 GMEM 的延迟，足够执行数百次计算操作，必须通过数据复用、分块加载等方式减少访问次数。

另一个值得关注的组件是张量内存加速器（TMA），它随 Hopper 架构首次推出。TMA 支持全局内存与共享内存之间、以及同一集群内不同共享内存之间的异步数据传输，还支持“地址混洗”（swizzling）以减少存储体冲突

### 3.1.3 数据传输接口

H100 支持两种核心数据传输方式，适配不同场景需求：

- **PCIe Gen 5**：双向带宽 128 GB/s，单向 64 GB/s，适用于多设备间常规数据交互。
- **NVLink v4**：双向带宽 900 GB/s，单向 450 GB/s（含 18 条 25 GB/s 链路），专为 GPU 间高速通信设计，是多 GPU 集群的核心支撑。

## 3.2 计算并行性与内存访问优化

GPU 计算的基本单元是流式多处理器（SM）。如图1所示，SM 按“图形处理集群”（GPC）分组：每个 GPC 包含 18 个 SM，整个 GPU 共有 8 个 GPC。其中 4 个 GPC 直接连接到一个 L2 缓存分区，另外 4 个连接到另一个 L2 缓存分区。

- GPC 也是 CUDA 中“线程块集群”（thread-block cluster）抽象的硬件基础
- 关于集群的一个关键点：前文提到每个 GPC 有 18 个 SM，8 个 GPC 理论上应有 144 个 SM，但 SXM/PCIe 形态的产品仅暴露 132 个或 114 个 SM。为何存在这种差异？因为 18×8 的布局仅对应完整的 GH100 裸片，实际产品中会关闭部分 SM（称为“熔丝熔断”，fused off）。这对编写核函数时选择集群配置有直接影响，例如：若集群跨越多于 2 个 SM，则无法使用所有 SM。
- 最后需注意，“图形处理集群”（GPC）中的“图形”（graphics）是遗留术语。在现代服务器级 GPU 中，这些集群仅作为计算/AI 加速单元，而非图形引擎。同理，GPU 如今更应被视为“AI 加速器”（去掉“图形”属性）。

除了前文提到的 L1/SMEM/TMA/RMEM 组件（均物理位于 SM 内部），每个 SM 还包含以下单元：

- **张量核心（Tensor Cores）**：专门执行小分块矩阵乘法的单元（例如 `64x16 @ 16x256`），吞吐量极高。大型矩阵乘法会被分解为大量此类分块运算，因此有效利用张量核心是达到峰值性能的关键。
- **CUDA 核心与 SFU（特殊功能单元，Special Function Units）**：所谓的“CUDA 核心”（营销术语）执行标准浮点运算，如 FMA（融合乘加，`c = a * b + c`）。SFU 则处理超越函数（如 `sin`、`cos`、`exp`、`log`）以及代数函数（如 `sqrt`、`rsqrt` 等）。
- **加载/存储（LD/ST）单元**：处理加载和存储指令的电路，与 TMA 引擎互补。
- **Warp 调度器**：每个 SM 包含多个调度器，负责为 32 线程组（CUDA 中称为“warp”）分发指令。一个 warp 调度器每周期可分发一条 warp 指令。

每个 SM 在物理上分为四个“象限”（quadrants），每个象限包含上述计算单元的一个子集。

### 3.2.1 并行性与并发的区别

GPU 通过“多 warp 调度”实现高并发与低延迟隐藏：

- **指令并行性**：单个 SM 每周期最多可从 4 个 warp 分发指令，即 128 个线程同时执行（4×32 线程）。
- **线程并发度**：单个 SM 最多支持 2048 个并发线程（64 个 warp），通过 warp 切换隐藏内存访问延迟——当一个 warp 等待内存数据时，调度器可切换到其他就绪 warp 执行计算，避免硬件空闲。

### 3.2.2 理论峰值性能（SoL）与功耗限制

GPU 的“理论峰值性能”由硬件规格决定，计算公式为：

**性能 = 最大时钟频率 × 张量核心数量 × 单个张量核心每周期 FLOPs**

以 H100 SXM 形态为例：

- 最大时钟频率 1830 MHz
- 张量核心数量 = 132（SM 数）× 4（每 SM 张量核心数）= 528
- 单个张量核心每周期 BF16 FLOPs = 1024
- 理论峰值 BF16 性能 = 1830 MHz × 528 × 1024 ≈ 989 TFLOP/s

**注意**：实际性能会受功耗限制影响——当 GPU 功耗接近 TDP（如 H100 PCIe 形态 TDP 350W）时，时钟频率会自动降低，导致性能下降。例如，时钟频率从 1830 MHz 降至 1000 MHz 时，BF16 性能会从 989 TFLOP/s 骤降至约 541 TFLOP/s。

![](https://picx.zhimg.com/v2-410ecf94094548eb58dc59b75f8c19e5_r.jpg)
*图3. 功耗限制导致时钟频率下降，实际峰值性能将低于官方宣传数值！*

## 四、CUDA 编程模型与硬件映射

CUDA 编程模型通过抽象层将 GPU 硬件特性简化为开发者易理解的概念，核心抽象包括：

- 线程（thread）
- Warp（32 个线程）
- 线程块（thread block）
- 线程块集群（thread block cluster）
- 网格（grid，由线程块或集群组成）

各抽象层与硬件一一对应，确保代码能高效映射到 GPU 执行。

## 4.1 核心编程概念与硬件映射

| CUDA 抽象 | 对应硬件组件 | 内存模型 | 同步机制 | 核心作用 |
| --- | --- | --- | --- | --- |
| 线程（Thread） | 寄存器文件（RMEM） | 线程私有寄存器 | - | 最小计算单元，执行独立逻辑 |
| Warp（32 线程） | SM 调度器 | SMEM/L1 缓存 | Warp 内隐式同步 | 指令调度基本单元 |
| 线程块（Thread Block） | 单个 SM | 共享内存（SMEM） | __syncthreads() 同步 | 多线程协同，数据复用 |
| 线程块集群（Cluster） | GPC（多个 SM） | 分布式共享内存（DSMEM） | 集群内 DSMEM 同步 | 跨 SM 协同，扩大计算规模 |
| 网格（Grid） | 整个 GPU | 全局内存（GMEM）/L2 缓存 | L2/GMEM 同步 | 全局任务调度单元 |

### 4.1.2 线程位置与任务分配

每个线程通过内置变量（`gridDim`/`blockIdx`/`blockDim`/`threadIdx`）感知自身在全局任务中的位置，这些变量存储在专用寄存器中，由 CUDA 运行时在核函数启动时初始化。这种“位置信息”使在 GPU 上分配任务变得简单，例如，处理 1024×1024 图像时，可将图像划分为 32×32 的线程块，每个线程负责一个像素的计算，再将结果写回内存。：

![](https://pica.zhimg.com/v2-f919006f1feaf2949139f566f6364744_r.jpg)
*图4. CUDA 内置变量：线程如何感知自身位置*

```text
// 计算线程在图像中的全局坐标
const int x = blockIdx.x * blockDim.x + threadIdx.x;
const int y = blockIdx.y * blockDim.y + threadIdx.y;
// 读取像素、执行计算、写回结果
float pixel = image[x][y];
float result = process(pixel);
output[x][y] = result;
```

**关键优化**：线程块大小需至少包含 4 个 warp（128 线程）——单个 SM 有 4 个 warp 调度器，需足够线程数才能充分利用调度器，避免硬件空闲。

## 五、全局内存（GMEM）与共享内存（SMEM）深度解析

内存访问是 GPU 性能优化的核心——若内存访问效率低，即使计算单元性能再强，也会因“数据喂不饱”导致算力浪费。以下从 GMEM 与 SMEM 的硬件特性、访问模式优化展开分析。

## 5.1 全局内存（GMEM）：原理与访问优化

GMEM 基于 HBM（堆叠式 DRAM）实现，是 GPU 中容量最大但速度最慢的内存层级。要优化 GMEM 访问，必须先理解其硬件工作原理。

### 5.1.1 DRAM 单元与内存访问机制

DRAM 单元由“晶体管+电容器”构成，而 DRAM 单元可看作“带开关的电容器”：

![](https://pic1.zhimg.com/v2-e8e875886fc6e5ed623ee298d3273b60_r.jpg)
*图5. DRAM 单元内部结构：晶体管 + 电容器、字线 + 位线*

- 电容器存储电荷，电压高于阈值（Vt）视为逻辑 1，否则为 0。
- 晶体管作为开关，由“字线”控制——字线通电时，晶体管打开，电容器电荷流向“位线”，由灵敏放大器检测数据。
- **关键特性**：DRAM 读取是“破坏性操作”——读取后电容器电荷会流失，需立即“刷新”（写回电荷），否则数据会丢失。

### 5.1.2 GMEM 访问的“行激活-列读取”模式

GMEM 访问分为两步：

**行激活**：通过行解码器选中目标行，将整行数据读取到“行缓冲区”（需耗时数百周期，是 GMEM 延迟的主要来源）。

**列读取**：在行已激活的前提下，**列解码器**接收列地址，从行缓冲区中选中目标列，将数据传输到 SM（仅需数周期）。

![](https://pic1.zhimg.com/v2-2bfe9ccdaba4863546d54811bfd50cfa_r.jpg)
*图6.GMEM 模型*

**核心优化原则**：**最大化行缓冲区复用**——连续访问同一行的不同列，避免频繁切换行（每次行切换需刷新当前行，耗时极高）。例如，行优先存储的矩阵，应按行遍历而非列遍历，减少行激活次数。

### 5.1.3 访问模式对带宽的影响

假设我们将一个形状为 256×256、数据类型为 float 的矩阵 A 以行优先（row-major）格式存储在内存中：

- 每行大小 = 256 × 4B = 1024B，恰好能放入 GMEM 的一行。
- 行优先存储意味着：每行数据连续存储，并在 DRAM 中按行分块。

![](https://picx.zhimg.com/v2-405dd0cd67b2800fb60e3fd43d4b2dcf_r.jpg)
*图7. GMEM 访问模式的影响*

- **行优先遍历（高效）**：若按行遍历（内层循环为列），则一次行读取后可连续读取 256 个列数据，仅需 256 次行读取，内存带宽接近峰值（如实验中 stride=8 时，A100 的 HBM 带宽达 1418 GB/s）。
- **列优先遍历（低效）**：若按列遍历（内层循环为行），则每个列元素的读取都需激活新行，共需 256×256 次行读取，内存带宽大幅下降（如实验中 stride=1024 时，带宽仅 111 GB/s）。

**结论**：线程需访问连续的 GMEM 地址（即“合并访问”），避免跨步访问——硬件会将连续的小请求合并为一个大请求，减少行激活次数，提升带宽利用率。

若矩阵采用列优先（column-major）存储，情况则相反：列元素连续存储，此时应在了你循环中遍历行，以避免 DRAM 性能损失。

## 5.2 共享内存（SMEM）：高速度与存储体冲突优化

共享内存（SMEM）与全局内存（GMEM）的特性差异显著。它基于 SRAM 单元而非 DRAM 构建，这使其在速度和容量的权衡上与 GMEM 有本质不同。SMEM 是位于 SM 内的高速内存（带宽 31 TB/s，延迟 20-30 周期），由程序员手动管理，是实现数据复用、减少 GMEM 访问的关键。

### 5.2.1 SMEM 硬件结构

SMEM 按“存储体（bank）”组织：32 个存储体并行工作，每个存储体宽度 32 位（4B），单周期可同时从 32 个存储体读取 128B 数据（32×4B）。如下图所示：

- 存储体编号 0-31，每个存储体可独立读写数据。
- H100 的 SMEM 最大容量为 228 KiB，对应 1824 个 128B 行（1824 × 128B = 228 KiB）。

![](https://pic4.zhimg.com/v2-21426ad60556ff8a9ad2272af1a3a4c1_r.jpg)
*图8. SMEM 模型*

### 5.2.2 存储体冲突（Bank Conflict）

SMEM 性能优化的核心是避免“存储体冲突”——同一 warp 中的线程若访问同一存储体的不同地址，请求会被串行执行，导致延迟增加。例如：

- 无冲突：32 个线程访问 32 个不同存储体，1 周期完成。
- 8 路冲突：32 个线程访问 4 个存储体（每存储体 8 个线程），需 8 周期完成。
- 最坏情况：32 个线程访问同一存储体，需 32 周期完成，吞吐量下降 32 倍。

### 5.2.3 存储体冲突避免策略

1. **数据对齐与访问模式设计**：确保同一 warp 的线程访问不同存储体。例如，矩阵转置时，通过地址偏移让线程访问不重叠的存储体。如swizzle等

![](https://pic4.zhimg.com/v2-929a1c09ad7ee2bee1ee7ec014d9e139_r.jpg)
*图9.无冲突模式*

1. **广播（Multicast）利用**：若多个线程访问同一存储体的同一地址，SMEM 会自动“广播”数据，无冲突且 1 周期完成——可利用这一特性实现数据共享，减少重复加载。例如：存储体 1 可将一个值多播给 2 个线程，存储体 2 可将一个值多播给 3 个线程，整个请求在 1 个周期内完成。

![](https://pic2.zhimg.com/v2-438a5d81bbb4c49ea89ea3e3f0ee1eb3_r.jpg)

## 六、L1 缓存模型

前文提到，L1 缓存与 SMEM 共享物理存储，但 L1 缓存在存储之上增加了硬件管理的“框架层”（负责地址映射、缓存命中/缺失判断等）。

![](https://picx.zhimg.com/v2-59ed94c22ec2a775ec66e684edfed563_r.jpg)
*图11. L1 缓存模型*

L1 缓存的逻辑流程如下：

1. 一个 warp 发起内存请求（访问 SMEM 或 GMEM）。
2. 请求进入 MIO（内存输入/输出，Memory Input/Output）流水线，分发到 LSUIN（加载/存储单元输入，Load/Store Unit Input）路由器。
3. 路由器分发请求：SMEM 访问直接从数据数组中读取，GMEM 访问则进入标签比较（tag-comparison）阶段。
4. 标签阶段：将 GMEM 地址的标签与目标组（set）中存储的标签比较，判断数据是否已在 L1 缓存中（即“缓存命中”）。
5. 命中（hit）：直接从数据数组中读取数据（与 SMEM 类似），返回给请求 warp。
6. 缺失（miss）：请求传递到 L2 缓存（必要时进一步传递到 GMEM 或其他 GPU 内存）。当数据从下级内存返回时，会被缓存到 L1 缓存（可能替换现有缓存行），同时并行返回给请求 warp。

**关键差异**：SMEM 请求跳过标签阶段，因此 SMEM 速度略快于 L1 缓存。

## 6.1 k 路组相联缓存（k-way Set-Associative Cache）

L1 缓存采用 k 路组相联结构，本文以“地址解析”和“缓存行结构”为例深入说明：

### 6.1.1 地址解析

GMEM 地址在 L1 缓存中被解析为三个部分：

- **标签（tag）**：用于唯一标识缓存行对应的 GMEM 地址。
- **组索引（set id）**：确定地址映射到缓存中的哪个“组”。
- **字索引（word id）**：确定在缓存行内的具体位置（若按 32B 扇区划分，还需“字节偏移”）。

示例：16 路组相联缓存，含 1024 个组，需 10 位二进制表示组索引（2^10 = 1024）；若缓存行大小为 32B，需 5 位表示字索引（ $2^5 = 32$ ）。

当 GMEM 地址进入标签阶段后，命中/缺失逻辑如下：

1. 标签阶段接收 GMEM 地址，提取组索引（set id），检查该组中的所有缓存行标签。

- L2 缓存容量更大（H100 为 50 MiB），关联度更高。

- L2 缓存支持更精细的持久化和缓存策略。

## 六、GPU 汇编语言：PTX 与 SASS

要极致优化核函数性能，需理解编译器如何将 CUDA 代码转换为硬件可执行的指令。GPU 存在两层汇编语言：PTX（虚拟指令集）与 SASS（原生指令集），二者分工不同但协同工作。

## 6.1 PTX：虚拟指令集（向前兼容的核心）

PTX 是 NVIDIA 定义的“虚拟 GPU 指令集”，不直接对应硬件，而是作为“中间层”实现向前兼容——十年前编译的 PTX 代码，仍可在 Blackwell 等现代 GPU 上通过 JIT（即时编译）转换为原生指令执行（虽无法利用新硬件特性，但能保证正确性）。

PTX 的核心作用：

- **编译器优化载体**：`nvcc` 编译器先将 CUDA 代码编译为 PTX，再由 `ptxas` 工具转换为 SASS。
- **代码可移植性**：PTX 与硬件架构解耦，同一 PTX 代码可适配不同代际的 GPU。

## 6.2 SASS：原生指令集（硬件直接执行）

SASS 是 GPU 硬件直接执行的原生指令集，与具体 GPU 架构强绑定（如 Hopper 对应 SM_90 架构）。SASS 指令高度优化，直接操作硬件资源（寄存器、存储体、计算单元），是性能优化的“最后一公里”。

### 6.2.1 为何关注 SASS？

- **极致性能调优**：部分优化（如避免存储体冲突、指令重排）需通过分析 SASS 代码验证——例如，确认 `#pragma unroll` 循环展开是否生效，或向量加载指令（`LDG.128`）是否正确生成。
- **理解编译器行为**：编译器可能存在优化不足（如冗余初始化、地址计算复杂），通过 SASS 分析可发现问题并针对性调整 CUDA 代码。

## 6.3 CUDA 编译流程

CUDA 代码从编写到执行需经历以下步骤：

1. **前端编译**：`nvcc` 将 CUDA C++ 代码拆分为“主机端代码”（CPU 执行）与“设备端代码”（GPU 执行），设备端代码先编译为 PTX。

## 七、近 SOTA 同步矩阵乘法核函数：warp-tiling 技术

在不依赖 TMA、张量核心等 Hopper 新特性的场景下，warp-tiling 是实现高性能同步矩阵乘法的核心技术。其核心思路是：将大矩阵拆分为小分块（tile），通过 SMEM 实现数据复用，减少 GMEM 访问次数，提升算术强度（每字节数据执行的 FLOPs）。

## 7.1 朴素矩阵乘法的性能瓶颈

朴素矩阵乘法（三层循环嵌套）的核心问题是**GMEM 访问次数过多**：

```text
// 朴素矩阵乘法（CPU 风格）
for (int m = 0; m < M; m++) {
    for (int n = 0; n < N; n++) {
        float tmp = 0.0f;
        for (int k = 0; k < K; k++) {
            tmp += A[m][k] * B[k][n];  // 每次迭代均访问 GMEM，无复用
        }
        C[m][n] = tmp;
    }
}
```

- 每个点积执行 K 次乘加操作，总计算量为 **2 × M × N × K FLOPs，**算术强度极低，性能受限于 GMEM 带宽。

注：性能瓶颈分析

![](https://pic4.zhimg.com/v2-06a086aa70ad0fc66c2ba87fd3ac5bad_r.jpg)
*图14.Roofline 模型*

- **Roofline 模型**：纵轴为性能（FLOP/s），横轴为算术强度（AI，Arithmetic Intensity）。
- **算术强度**：定义为从设备内存/GMEM 加载每字节数据所执行的 FLOPs 数量（默认）。
- **脊点（ridge point）**：计算公式为“峰值性能 / GMEM 带宽”。以 H100 PCIe 为例，峰值性能约 819 TFLOP/s，GMEM 带宽约 2 TB/s，脊点约为 410。仅当算术强度超过该值时，核函数才能进入“计算受限”区域；否则处于“内存带宽受限”区域。

朴素矩阵乘法处于内存带宽受限区域，为充分利用算力，因此需目标是进入计算受限区域。

## 7.2 warp-tiling 核心思想：分块与数据复用

矩阵乘法可以被视为部分点积的和，

- 矩阵 C = A @ B 可分解为：对每个 k，计算 A 的第 k 列与 B 的第 k 行的外积，再将所有外积相加。
- 例如，C[2,3] = A[2,0]×B[0,3] + A[2,1]×B[1,3] + ... + A[2,K-1]×B[K-1,3]。

![](https://pica.zhimg.com/v2-70b38adfec828352b1cda779ecce213e_r.jpg)
*图15.矩阵乘法作为外积部分和的总和*

- 这意味着我们可将计算分解为一系列“块矩阵乘法”（每个块产生部分点积）。通过将这些块加载到 SMEM 中再执行计算，可大幅减少 GMEM 访问，提升性能。
- 若不进行分块，数据无法放入 SMEM（SMEM 容量远小于 GMEM 中的矩阵大小）。

warp-tiling 通过“分块计算+SMEM 缓存”优化，核心步骤如下：

1. **分块划分**：将输出矩阵 C 划分为 Bm×Bn 的正方形分块（如 128×128），每个线程块负责一个分块的计算。
2. **K 维度分块**：将 K 维度划分为 Bk 大小的分块（如 16），每次加载 A 的 Bm×Bk 分块与 B 的 Bk×Bn 分块到 SMEM。
3. **部分结果累加**：通过多次迭代 K 维度分块，将部分矩阵乘法结果累加，最终得到完整分块结果——每次迭代仅需访问 GMEM 加载两个小分块，SMEM 中数据可被多次复用，大幅减少 GMEM 访问量。

### 7.2.1 分块大小选择原则

- **正方形分块优先**：Bm≈Bn，最大化算术强度——正方形分块的“计算量/数据量”比最高，每字节数据执行更多 FLOPs。
- **适配 SMEM 容量**：分块大小需确保 A、B 的分块能同时放入 SMEM（如 H100 SMEM 最大 228 KiB，需预留系统开销）。
- **warp 适配**：分块大小需与 warp 规模（32 线程）匹配，避免线程空闲（如 Bm、Bn 为 32 的整数倍）。

## 7.3 warp-tiling 实现步骤（以 Bm=Bn=128、Bk=16 为例）

![](https://pica.zhimg.com/v2-a2ef81e9a2a96d401988ca24915e6fe6_r.jpg)
*图16.warp-tiling 示意图*

### 7.3.1 数据加载：GMEM → SMEM

- **矩阵 B 加载**：B 的分块（Bk×Bn=16×128）按列优先存储到 SMEM 缓冲区 Bs，无需转置——每个 warp 读取 B 的一行，通过向量加载（`LDG.128`）一次读取 4 个 float（128B），存储到 SMEM 对应位置，无存储体冲突。
- **矩阵 A 加载**：A 的分块（Bm×Bk=128×16）需转置存储到 SMEM 缓冲区 As——转置虽会导致存储时的部分冲突，但后续计算时可通过向量加载（`LDS.128`）高效读取，整体收益更高。

### 7.3.2 分块计算：SMEM 内矩阵乘法

加载完成后，线程块内同步（`__syncthreads()`），确保 SMEM 数据就绪。随后通过四层循环实现分块乘法：

1. **K 维度迭代**：遍历 K 维度的每个分块（Bk=16）。
2. **warp 子分块迭代**：将 As、Bs 拆分为更小的 warp 级分块（如 64×16），适配 warp 调度。
3. **线程级计算**：每个线程负责 8×4 的输出元素计算，从 SMEM 加载数据到寄存器，执行乘加操作并累加到私有寄存器（threadResults）。
4. **结果累加**：多次迭代 K 维度分块，将部分结果累加，最终得到完整分块的矩阵乘法结果。

### 7.3.3 结果写回：SMEM → GMEM

所有 K 维度分块迭代完成后，线程将私有寄存器中的最终结果写回 GMEM 的对应分块，完成一个输出分块的计算。

## 7.4 warp-tiling 性能提升关键

- **GMEM 访问量减少**：通过分块复用，A、B 的 GMEM 访问量从 O(M×N×K) 降至 O((M×K/Bk)×Bm×Bk + (K×N/Bk)×Bk×Bn) = O(M×Bm + N×Bn)，访问量大幅降低。
- **算术强度提升**：正方形分块使算术强度从 O(1) 提升至 O(Bk)（如 Bk=16 时，算术强度提升 16 倍），突破内存带宽瓶颈，接近计算受限状态。

## 八、Hopper 架构 SOTA 异步矩阵乘法核函数

Hopper 架构引入 TMA、异步张量核心、线程块集群等新特性，将矩阵乘法性能提升至新高度。以下解析如何利用这些特性实现 SOTA 异步核函数，性能较 warp-tiling 提升近 10 倍（从 32 TFLOP/s 至 317 TFLOP/s）。

## 8.1 Hopper 核心特性

### 8.1.1 张量内存加速器（TMA）

TMA 是 Hopper 架构专为张量数据移动设计的硬件单元，支持：

- **异步数据传输**：GMEM 与 SMEM 之间、SMEM 与 SMEM 之间的异步传输，可与计算操作重叠，隐藏内存延迟。
- **自动地址混洗**：传输时自动对数据进行“混洗”（swizzling），避免 SMEM 存储体冲突，无需手动调整访问模式。
- **多块协同传输**：支持线程块集群内的 SMEM 数据共享，减少 L2 缓存访问次数。

### 8.1.2 异步张量核心（wgmma.mma_async）

Hopper 张量核心支持异步矩阵乘法指令（`wgmma.mma_async`），核心优势：

- **warp 组协同**：4 个 warp（128 线程）组成一个“warp 组”，协同执行矩阵乘法，适配大分块计算。
- **异步执行**：张量核心计算与 TMA 数据传输可并行，最大化硬件利用率。
- **bf16 优化**：原生支持 bf16 数据类型，单周期可执行更多 FLOPs（H100 BF16 峰值达 989 TFLOP/s）。

### 8.1.3 线程块集群（Thread Block Cluster）

多个线程块可组成“集群”（如 2×1 集群），共享 DSMEM（分布式共享内存），支持：

- **跨 SM 数据复用**：集群内一个 SM 加载的数据可通过 DSMEM 共享给其他 SM，减少 GMEM/L2 访问。
- **协同计算**：集群内线程块协同执行大分块矩阵乘法，突破单个 SM 的资源限制。

## 8.2 异步矩阵乘法核函数实现步骤

保留 warp-tiling 的结构，但做以下关键修改：

- 每个线程块仅需 128 个线程（4 个 warp）。
- 分块大小设置为 Bm = Bn = Bk = 64。

![](https://pic2.zhimg.com/v2-ab2fc287e29f9f4044e04893da0bcb81_r.jpg)
*图17.warp-tiling 算法，分块大小不一样*

- 输出分块大小从 128×128 改为 64×64，K 维度分块大小从 16 改为 64。
- 对于 4096×4096 的矩阵，K 维度需分为 4096/64 = 64 个分块。

### 8.2.1 张量映射与 TMA 异步加载

在数据加载阶段，TMA 取代了前文复杂的 warp 级加载模式，流程大幅简化。只需三步：

1. 为矩阵 A 和 B 构建张量映射（tensor map）。
2. 触发 TMA 操作（由线程块中的单个线程执行）。
3. 使用共享内存屏障（shared-memory barrier）同步。

TMA 不仅负责数据移动，还会自动应用“地址混洗”（swizzling），解决前文 warp-tiling 中遇到的存储体冲突问题。

1. **构建张量映射**：使用 `cuTensorMapEncodeTiled` 函数为 A、B 构建张量映射，指定数据类型（bf16）、形状、步长、混洗模式（128B）等参数，TMA 将根据映射自动完成数据传输。
2. **TMA 异步加载**：线程块中单个线程触发 TMA 传输，将 A 的 Bm×Bk 分块与 B 的 Bk×Bn 分块（Bm=Bn=Bk=64）异步加载到 SMEM，同时通过共享内存屏障（barrier）同步传输完成状态。

```text
__shared__ barrier barA, barB;  // 用于 TMA 同步的屏障
if (threadIdx.x == 0) {
    // 初始化屏障，等待所有 128 线程与 TMA 传输完成
    init(&barA, blockDim.x);
    init(&barB, blockDim.x);
    cde::fence_proxy_async_shared_cta();  // 确保屏障对 TMA 可见
}
__syncthreads();

// 外层 K 循环：异步加载分块
for (int block_k = 0; block_k < num_blocks_k; block_k++) {
    if (threadIdx.x == 0) {
        // TMA 加载 A 分块到 sA（SMEM）
        cde::cp_async_bulk_tensor_2d_global_to_shared(&sA[0], tensorMapA, block_k*BK, block_m*BM, barA);
        tokenA = cuda::device::barrier_arrive_tx(barA, 1, sizeof(sA));  // 关联传输字节数
        // TMA 加载 B 分块到 sB（SMEM）
        cde::cp_async_bulk_tensor_2d_global_to_shared(&sB[0], tensorMapB, block_k*BK, block_n*BN, barB);
        tokenB = cuda::device::barrier_arrive_tx(barB, 1, sizeof(sB));
    } else {
        tokenA = barA.arrive();  // 其他线程仅标记到达
        tokenB = barB.arrive();
    }
    barA.wait(std::move(tokenA));  // 等待 TMA 完成与所有线程到达
    barB.wait(std::move(tokenB));
    // ... 后续计算 ...
}
```

### 8.2.2 异步tensor core计算

TMA 加载数据的同时，可启动异步张量核心计算，实现“数据传输-计算”重叠：

1. **warp 组初始化**：128 线程组成 warp 组，调用 `wgmma.fence.sync.aligned` 确保寄存器访问顺序。
2. **异步矩阵乘法**：通过 `wgmma.mma_async` 指令执行分块矩阵乘法（如 `64x16 @ 16x64`），将结果累加到 warp 组的分布式寄存器中。
3. **计算提交与等待**：调用 `wgmma.commit_group` 提交计算任务，`wgmma.wait_group` 等待计算完成，期间可继续触发下一轮 TMA 加载。

```text
// 异步张量核心计算（示例代码）
asm volatile("wgmma.fence.sync.aligned;" ::: "memory");  // 初始化 warp 组
// 执行 4 次异步矩阵乘法（覆盖 BK=64 分块）
wgmma64<1, 1, 1, 0, 0>(d, &sA[0], &sB[0]);
wgmma64<1, 1, 1, 0, 0>(d, &sA[16], &sB[16]);
wgmma64<1, 1, 1, 0, 0>(d, &sA[32], &sB[32]);
wgmma64<1, 1, 1, 0, 0>(d, &sA[48], &sB[48]);
asm volatile("wgmma.commit_group.sync.aligned;" ::: "memory");  // 提交计算
asm volatile("wgmma.wait_group.sync.aligned %0;" ::"n"(0) : "memory");  // 等待完成
```

### 8.2.3 流水线与集群优化

- **多缓冲流水线**：使用多个 SMEM 缓冲），形成“加载-计算-写回”流水线——TMA 加载下一个分块时，张量核心计算当前分块，同时写回上一个分块结果，最大化硬件利用率。

## 8.3 性能优化效果

通过 TMA 异步加载、张量核心、集群共享等技术叠加，Hopper 架构的矩阵乘法性能实现跨越式提升。以下博客中记录的优化效果（H100 平台）,原文中有以下各种优化方案详细的示意图，作者真的很用心。

| 优化手段 | 优化前性能（TFLOP/s） | 优化后性能（TFLOP/s） | 性能提升幅度 |
| --- | --- | --- | --- |
| warp-tiling → 张量核心 + TMA | 32 | 317 | 9.9 倍 |
| 增大输出分块尺寸 | 317 | 423 | 1.33 倍 |
| 流水线：TMA 加载与张量核心计算重叠 | 423 | 498 | 1.18 倍 |
| 分块扩展：128×128 → 128×256（双消费 warp 组） | 498 | 610 | 1.22 倍 |
| 持久核函数（隐藏写回延迟） | 610 | 660 | 1.08 倍 |
| 快速 PTX 屏障 | 660 | 704 | 1.07 倍 |
| 线程块集群 + TMA 多播 | 704 | 734 | 1.04 倍 |
| 微优化（寄存器重平衡、异步写回） | 734 | 747 | 1.02 倍 |
| TMA 异步写回（寄存器→SMEM→GMEM） | 747 | 758 | 1.01 倍 |
| 希尔伯特曲线调度（提升 L2 命中率） | 758 | 764 | 1.01 倍 |

## 九、总结与展望

本文从 GPU 硬件架构出发，逐步拆解了矩阵乘法核函数的优化思路：从基础的内存层级、并行性设计，到 warp-tiling 分块技术，再到 Hopper 架构的 TMA、异步tensor core等前沿特性应用，每一步优化都围绕“减少内存延迟、提升计算利用率”展开。

高性能 GPU 编程的核心在于“硬件感知”——理解内存层级的延迟/带宽特性、计算单元的并行能力、指令集的优化方向，才能设计出贴合硬件的核函数。未来，随着 Blackwell、Rubin 等新架构的推出，GPU 硬件将进一步提升算力与带宽，但“数据复用、异步并行、集群协同”的核心优化思路仍将保持适用。

正如本文始终强调的：计算机硬件并非黑箱，只要深入理解其底层原理，就能驾驭其性能潜力，设计出超越通用库（如 cuBLAS）的定制化高性能kernel。
