英伟达 11 月 3 日发布的技术报告《You don't need long context》发现，做 agent 任务和长文档问答时，大模型并不需要几十万 token 的上下文。把每次调用的上下文限制在 16K 到 48K token，Claude Opus 4.5 和 GPT 5.6 Sol 在 6 个 agent 基准上的准确率基本持平，在 7 个长文档基准上大多明显提高；如果服务商按上下文长度计价，成本能降到原来的几分之一。

### 长上下文贵在哪里

token 是模型读写文字的单位，一个英文单词约 1.3 个 token。模型每生成一个 token，都要回看上下文里已有的全部 token，所以上下文越长，生成越慢、占显存越多、成本越高。上下文窗口是模型一次最多能看到的 token 数。论文在 H100 上实测：同样的硬件，窗口从 16K 开到 256K，每个输出 token 的成本 GLM 5.2 涨到 3.6 倍，Kimi K2.6 涨到 5.6 倍，Qwen 3 Coder Next 涨到 7 倍。API 通常按每百万 token 固定标价，所以用户平时感觉不到。

![](https://pic3.zhimg.com/v2-951f85bb8bd651aba96fddd558321362_r.jpg)
*Figure 1：H100 上生成 100 万个输出 token 的成本随上下文窗口的变化。横轴是窗口大小（对数刻度），纵轴是美元成本；绿、橙、紫三条线分别是 GLM 5.2、Kimi K2.6 和 Qwen 3 Coder Next。*

在 DGX Spark 这台桌面 AI 主机上也一样，几个开源模型越往后的 token 生成时间大约是开头的 2 倍，内存占用也跟着涨。可模型的窗口还在越开越大：Claude Opus 4.5 的 200K 约能装 15 万个英文单词，是《了不起的盖茨比》的三倍多；GPT 5.6 Sol 的 1.05M 装得下整本《战争与和平》。

长上下文主要来自两类任务。一类是长程任务：agent 是让模型反复发命令、看结果、再决定下一步的程序，任务要做很多步，每一步的命令和输出都追加进对话，历史越堆越长。另一类是长输入任务：把整份财报、整本书直接塞给模型再提问。这两类任务真的需要把所有内容一直放在上下文里吗？

### 他们是怎么做的

实验比较了三种管理上下文的方式：

- **全量历史**（FHA）是基线，每条命令和输出一直留在对话里，这也是所用 agent 框架 mini-swe-agent 的默认做法。
- **会话末压缩**（EoCC）设一个总上限和一个更低的压缩阈值，写作“总上限 / 压缩阈值”，比如 16K / 12K。对话一过 12K，模型就停下来写交接摘要，总上限多出的空间留给写摘要；然后开一个只带原任务和摘要的新对话接着做。设置从 48K / 36K 逐级收紧到 16K / 12K，两个对话类基准最低到 12K / 8K 和 8K / 6K。
- **单动作压缩**（SAC）最极端：每个对话只拿到任务和一段描述当前进度的“语义状态”，只执行一条命令，看到结果后更新语义状态，然后丢掉对话，下一条命令在新对话里执行。

![](https://pic3.zhimg.com/v2-99835951ec8ca75d57967fb2b0515cda_r.jpg)
*Figure 3：三种上下文管理方式。左为全量历史，所有消息留在一个对话里；中为会话末压缩，越过阈值后写出压缩摘要（黄色），新对话只带原任务和摘要；右为单动作压缩，每个对话只调用一次工具，随后更新语义状态（青色）。*

长输入任务则不把文档贴进对话，而是存成文件放进 agent 的沙箱（隔离的命令行环境），让模型用 grep 等命令搜索，再用专门的读取命令按需读，每次最多 8000 个字符。这样长输入任务也变成了一步步查找的长程任务，可以套用同样的压缩办法。

实验主力是 Claude Opus 4.5 和 GPT 5.6 Sol，另外补充了五个能在 DGX Spark 上本地运行的开源模型。基准是固定的一组题目加自动评分，用来横向比较模型，一共 13 个。长程类 6 个，包括 SWE-bench Verified（500 个真实 GitHub issue，模型写的补丁要通过隐藏测试）、Terminal-Bench 2.1（89 个命令行任务）、FRAMES（824 道要综合 2 到 15 篇维基百科文章的多跳问答）、τ²-bench（和模拟用户对话的客服类任务）等。长输入类 7 个，包括 LongBench v2、LOONG、AA-LCR 这类真实长文档问答，以及大海捞针（NIAH）、RULER、Counting-Stars、BABILong 这类把信息藏进长文本再提问的合成测试。

### 发现一：agent 任务不需要长上下文

6 个长程基准上，每个模型各有 22 组压缩设置。相对全量历史，Opus 4.5 的准确率变化在 −3.7 到 +5.6 个百分点之间，GPT 5.6 Sol 在 −3.3 到 +4.4 之间。掉分超过 2 个点的，Opus 只有 1 组，GPT 有 5 组（FRAMES 3 组、Terminal-Bench 2 组）。

- SWE-bench Verified：Opus 全量历史 70.0%，24K 时 74.8%，16K 时 68.8%；GPT 全量历史 84.4%，16K 时 84.6%。
- Terminal-Bench 2.1：Opus 从 47.2% 升到 48.3% 到 52.8%；GPT 从 87.6% 变成 85.4% 到 88.8%。
- FRAMES 是唯一两个模型在所有设置下都略降的基准：Opus 从 81.0% 降到 77.3% 到 79.7%，GPT 从 90.2% 降到 86.9% 到 88.7%。
- τ²-bench：GPT 在 12K / 8K 时反而从 73.9% 升到 77.2%。

![](https://pic3.zhimg.com/v2-158a2b4524204805bc9952f85827891a_r.jpg)
*Figure 5：6 个长程基准上的结果。上半部分是相对全量历史的准确率变化（百分点），下半部分是估算的成本节省倍数；橙色是 Opus 4.5，蓝色是 GPT 5.6 Sol，星号是基线，横轴越往右上限越紧。*

频繁压缩有可能让模型忘了做过的事、反复重做，反而多花 token。论文发现这种情况总体上没有出现：以 SWE-bench Verified 为例，16K 设置下每个任务累计对话长度的中位数，Opus 从 32K 变成 24K，GPT 从 18K 变成 26K，没有成倍膨胀。

### 发现二：长文档按需检索比整篇读更准

和把整篇材料放进对话相比，按需搜索后两个模型在 7 个基准上共 14 组结果，13 组更准，只有 Opus 在 LongBench v2 上从 68.0% 略降到 67.6%。

- AA-LCR：Opus 从 65.0% 升到 84.0%。
- LOONG：平均分 Opus 从 70.1 升到 79.3 到 80.2，GPT 从 79.3 升到 82.7 到 84.6。
- RULER：召回率（应找出的答案里实际找到的比例）Opus 从 62.5% 升到 95.7%，GPT 从 65.5% 升到 96.4%。
- BABILong：Opus 从 67.1% 升到 92.0%，GPT 从 70.7% 升到 94.0%。
- 大海捞针：两个模型分别从 60% 和 80% 升到 100%。

![](https://pic3.zhimg.com/v2-2e8802ac63fbc0f516b6fb39159cdaf0_r.jpg)
*Figure 6：7 个长输入基准上的结果。上半部分是相对整篇输入基线的准确率变化（百分点），下半部分是估算的成本节省倍数；橙色是 Opus 4.5，蓝色是 GPT 5.6 Sol。*

这些提升大多不是压缩带来的。大海捞针和 Counting-Stars 上两个模型一次都没压缩，RULER 上压缩次数的中位数是 0，上下文是靠按需搜索压下来的。文档长度横跨几个数量级，对话总长度却大多落在差不多的区间。论文据此认为，这些任务虽然输入很长，真正用得上的信息并不多。

### 发现三：每个对话只做一个动作也能完成任务

单动作压缩在 SWE-bench Verified 和 Terminal-Bench 2.1 上测试。Opus 分别是 70.2% 和 51.8%（全量历史 70.0% 和 47.2%）；GPT 分别是 82.4% 和 84.3%（全量历史 84.4% 和 87.6%）。每个任务里最长那次调用的上下文，中位数只有 7K 到 9K token，最长 15K 到 37K；全量历史下最长到 130K 到 200K。

![](https://pic1.zhimg.com/v2-14eb4aeb2f7eec586798f60f1c5125b2_r.jpg)
*Table 2：单动作压缩（SAC）与全量历史（mini baseline）、会话末压缩最好成绩（Best EoCC）的对比。左边是准确率，右边是每个任务里最长一次调用的上下文长度（K token，中位数 / 最大值）。*

论文据此提出了“语义状态空间模型”（SSSM）的构想：后训练（预训练之后针对某种行为再做的训练）一个模型，每一轮读入描述进度的文字，推理、执行一个动作、记下结果，再改写这段文字交给下一个实例。它对应 Mamba 这类状态空间模型（SSM），区别是 SSM 在 token 之间传递人看不懂的神经网络状态，SSSM 在轮次之间传递人能读懂的文字。这样的模型还没有训练出来。

### 交接摘要怎么写

论文发现，把压缩当成普通总结效果不理想：总结对所有事实一视同仁，还会过度强调轨迹里反复出现的片段。效果最好的是一份给剩余工作用的简报，包括原任务的原文、当前在做什么和下一步打算、从任务拆出的计划、什么情况下算完成，以及相关信息或存放它们的文件路径。所有任务都用这同一种结构。

代码 agent 的压缩提示词要求写明：目标；已确认的事实，包括精确的路径、命令、数值和报错，观察和猜测分开；改了哪些文件、是否验证；跑过哪些检查、结果如何；哪些路走不通、别再试；剩余计划、下一条命令和完成条件。被截断的输出要留一条能取回它的命令。

### 成本怎么算，结果怎么样

闭源模型按固定单价收费，所以论文用开源模型的实测数据估了一个“优化后零售价”：三个开源模型 16K 与 256K 的单 token 成本比平均约 0.2，于是把模型的标准窗口（Opus 200K、GPT 272K）定为今天的标价，16K 定为标价的 0.2 倍，中间线性插值。按这个估算，长程任务上全量历史的成本是压缩后的 2.2 到 8.8 倍（Opus）和 2.4 到 5.0 倍（GPT）；长输入任务上整篇输入是按需读取的 6.5 到 54.6 倍（Opus）和 4.4 到 233.3 倍（GPT）。

按今天的固定标价重算，长输入任务仍然基本更省，14 组里 13 组更便宜，例外是 GPT 在 LongBench v2 上（从 79.20 美元变成 90.20 美元）。LOONG 上整篇输入每个模型要按全价输入 2.72 亿个 token，Opus 按需读取后全价输入只有 5,460 万到 5,760 万个，其余是缓存输入（服务商已处理过、只收十分之一价格的输入，比如对话里没变的前半段），标价成本从 1,367.50 美元降到 497.75 到 534.05 美元。

长程任务就不一定了。按标价算，22 组设置里 GPT 有 21 组、Opus 有 7 组压缩后反而更贵。比如 GPT 在 SWE-bench Verified 上，全量历史 167.68 美元，压缩后 184.16 到 203.12 美元，因为压缩后输出和全价输入都变多了，省下的主要是便宜的缓存输入。

### 再往下挖一层：开源模型

在 DGX Spark 上跑的五个量化开源模型都没有专门为压缩训练过，对压缩更敏感。SWE-bench Verified 上，收紧到 16K / 12K 时五个都掉了分：Qwen 3.6 27B 从 68.6% 到 65.0%，MiniMax M2.7 从 72.6% 到 67.8%，Gemma 4 31B 从 65.2% 到 58.0%，Step 3.7 Flash 从 70.0% 到 56.6%，Qwen 3 Coder Next 从 53.0% 崩到 3.6%，原因是它每一步的输出太啰嗦，两次压缩之间留不出推进任务的空间。放宽到 48K / 40K 时，Qwen 3.6 27B（69.4%）和 MiniMax M2.7（73.0%）都略高于基线。Terminal-Bench 2.1 上，这两个模型在 16K / 12K 时保住了基线成绩，Step 3.7 Flash 掉得最多，从 41.6% 降到 28.1%。

### 需要注意的地方

- 闭源模型的省钱倍数是估算，前提是按窗口定价，折算比例也来自开源模型；按今天的固定标价，长程任务压缩后常常更贵。
- 闭源模型只测了两个，单动作压缩只测了两个基准，SSSM 还只是构想。
- Terminal-Bench 只有 89 题，一题约等于 1.1 个百分点，论文也没给多次运行的波动范围，一两个点的差别不宜过度解读。
- 压缩会丢信息。论文举的例子是：任务要求说出第 i 次抛硬币的结果，而摘要长度有限，迟早会丢掉某几次记录；办法是把完整对话存成文件，需要时去搜。所以结论是“不必把全部历史一直放在上下文里”，而不是“永远用不到历史”。
- 大海捞针的满分，论文部分归因于“针”和问题之间有直接的词面重合，grep 很容易搜到。另外 RULER（只在 256K 和 500K 上测）、BABILong（最长 1M）等基准的材料有的超过 Opus 4.5 的 200K 窗口，论文没交代整篇输入的基线怎么处理，基线的部分失分可能来自截断。
- 交接摘要是按 agent 自主干活设计的，开发者中途插话指挥的场景论文提到了，但没有测。

### 对实际使用的启发

- 做 agent 可以在几万 token 时就主动压缩，交接摘要写成给剩余工作的简报：任务原文、当前状态和下一步、计划、完成条件、走不通的路、文件路径。
- 完整日志留在磁盘上，需要旧细节时让 agent 去搜。
- 长文档存成文件让模型搜索、分段读，不要整篇贴进对话，在这些基准上几乎都更准，按今天的标价也几乎都更省。
- 换成较小的开源模型时，先在自己的任务上试压缩阈值，输出啰嗦的模型收得太紧会直接失败。
- 长程任务压缩后按今天的标价不一定省钱，要看实际账单。
