## 1 Context Engineering 的定义

**上下文工程（Context Engineering）** ，是指在 Agent 每次调用大语言模型之前，动态选择、组织、压缩和注入当前任务所需要的信息。

上下文工程需要解决的核心问题是

```text
在有限的 Context Window 中，
应该向模型提供哪些信息，
以什么顺序提供，
提供多少，
哪些信息不能提供。
```

Anthropic 将上下文工程描述为：优化模型采样时可见的全部上下文配置，使有限的 Token 能够产生尽可能可靠的行为。LangChain 则进一步将 Agent 上下文划分为模型上下文、工具上下文和生命周期上下文。

因此，上下文工程并不是简单地把所有历史消息都发送给模型，而是

```text
原始信息
    ↓
筛选相关信息
    ↓
删除无关信息
    ↓
压缩重复信息
    ↓
处理权限和安全问题
    ↓
按照合理顺序组织
    ↓
发送给 LLM
```

## 2 Context Engineering 与 Prompt Engineering

**Prompt Engineering** 主要关注指令本身应该如何编写。

**Context Engineering** 关注模型在当前调用中能够看到的全部信息。

| 对比项 | Prompt Engineering | Context Engineering |
| --- | --- | --- |
| 核心对象 | 指令文本 | 模型可见的全部上下文 |
| 主要目标 | 让指令表达清晰 | 提供完成任务所需的信息 |
| 关注内容 | 角色、任务、格式、示例 | 指令、消息、状态、记忆、工具、检索结果 |
| 作用范围 | 单次 Prompt | Agent 整个运行过程 |
| 是否动态变化 | 通常较少 | 通常每一步都会变化 |
| 主要问题 | 指令不清晰 | 信息过多、缺失、冲突或污染 |

示例：用户要求 Agent 查询订单状态。

Prompt Engineering 主要设计

```text
你是一名订单查询助手。
请根据订单信息回答用户问题。
```

Context Engineering 则需要决定是否提供

```text
用户当前问题
用户身份
订单编号
订单查询工具
工具参数说明
最近一次工具结果
历史订单状态
用户权限
输出格式
```

因此： **Prompt 是上下文的一部分，但上下文不仅包含 Prompt。**

## 3 Agent 上下文的组成

一次完整的 Agent 模型调用，通常包含以下信息

```text
系统指令
    +
用户请求
    +
工具定义
    +
当前状态
    +
历史消息
    +
检索结果
    +
长期记忆
    +
中间执行结果
    +
输出格式
```

### 系统指令

系统指令用于定义 Agent 的基础行为

示例

```text
Agent 的角色

Agent 的目标

行为边界

安全规则

工具使用规则

输出格式

任务结束条件
```

示例

```text
你是一名代码审查 Agent。

你的任务是：
1. 检查代码错误。
2. 解释错误原因。
3. 给出修改建议。
4. 未经用户确认，不得修改生产环境文件。
```

系统指令通常属于较高优先级的上下文。不同来源的指令发生冲突时，需要按照预先定义的指令优先级处理，而不能简单采用最后出现的指令。

### 用户请求

用户请求描述当前需要完成的目标。

示例

```text
检查这个 Python 文件为什么运行失败。
```

Agent 需要从用户请求中提取

```text
当前目标

操作对象

约束条件

期望结果

输出形式

是否需要调用工具
```

用户请求可能不完整，因此 Agent 还可能需要结合

```text
历史消息

当前状态

用户长期偏好

已上传文件

工具返回结果
```

进行解释。

### 工具定义

工具定义告诉模型

```text
有哪些工具

工具可以完成什么任务

工具需要哪些参数

工具会返回什么结果

什么情况下应该调用工具
```

示例

```text
{
  "name": "search_order",
  "description": "根据订单编号查询订单状态",
  "parameters": {
    "type": "object",
    "properties": {
      "order_id": {
        "type": "string",
        "description": "需要查询的订单编号"
      }
    },
    "required": ["order_id"]
  }
}
```

工具定义同样会占用 Context Window。

当工具数量较多时，将所有工具同时提供给模型可能导致

```text
Token 消耗增加

工具选择难度增加

相似工具混淆

参数生成错误

无关工具干扰决策
```

因此，可以根据当前任务动态筛选工具

```text
用户询问天气
    ↓
只提供天气查询工具
    ↓
不提供邮件、数据库、文件删除等无关工具
```

### 状态信息

状态信息表示 Agent 当前执行到什么位置。

示例

```text
{
  "goal": "生成项目周报",
  "completed_steps": [
    "读取项目数据",
    "统计已完成任务"
  ],
  "pending_steps": [
    "分析风险",
    "生成最终周报"
  ],
  "current_step": "分析风险",
  "retry_count": 1
}
```

状态与历史消息不同。

```text
历史消息：记录发生过什么。

状态信息：记录当前任务处于什么状态。
```

状态应优先保存结构化结果，而不是依赖模型重新阅读全部历史消息进行推断。

### 历史消息

历史消息包括

```text
用户之前的请求

Agent 之前的回答

工具调用记录

工具执行结果

用户反馈

错误信息
```

历史消息可以帮助模型理解多轮对话。

但是，历史消息越多不一定越好。

过多的历史消息可能导致

```text
Context Overflow

无关信息干扰

早期错误继续传播

用户旧目标干扰当前目标

Token 成本增加

响应延迟增加
```

因此，历史消息通常需要进行裁剪、摘要或检索。

### 检索结果

检索结果通常来自

```text
向量数据库

关键词检索

数据库查询

网页搜索

文件搜索

知识图谱

企业内部知识库
```

示例

```text
用户问题
    ↓
生成检索查询
    ↓
搜索相关文档
    ↓
选择相关片段
    ↓
将片段加入上下文
    ↓
LLM 生成答案
```

检索结果需要保留

```text
原始内容

来源

文档标识

时间信息

相关性分数

必要的前后文
```

不能因为检索到了内容，就直接把大量原始文档全部放入上下文。

### 长期记忆

长期记忆用于保存跨任务或跨会话仍然有价值的信息

示例

```text
用户稳定偏好

项目背景

已确认事实

长期目标

历史重要决策

成功执行经验
```

示例

```text
{
  "user_preferences": {
    "language": "Chinese",
    "output_format": "Markdown",
    "code_language": "Python"
  }
}
```

长期记忆不应在每次调用中全部加载。

正确方式是

```text
当前用户请求
    ↓
检索相关长期记忆
    ↓
筛选与任务有关的记忆
    ↓
加入当前上下文
```

### 中间执行结果

中间执行结果是 Agent 在任务执行过程中产生的数据

示例

```text
搜索结果

代码运行结果

数据库返回记录

文件内容

子 Agent 报告

计划执行结果

错误日志
```

示例

```text
{
  "tool": "run_tests",
  "status": "failed",
  "summary": "共执行 38 个测试，2 个失败",
  "failed_tests": [
    "test_create_user",
    "test_delete_user"
  ]
}
```

中间执行结果通常会不断积累。

如果每次都保留完整输出，Agent 的上下文会迅速膨胀。因此，应保留结构化摘要，并把原始数据保存到外部存储中。

## 4 上下文构建流程

一个常见的上下文构建过程如下

```text
接收用户请求
    ↓
识别当前任务
    ↓
读取当前状态
    ↓
选择相关历史消息
    ↓
检索相关长期记忆
    ↓
检索外部知识
    ↓
选择可用工具
    ↓
加入必要中间结果
    ↓
处理权限与敏感信息
    ↓
压缩和排序上下文
    ↓
检查 Token 预算
    ↓
调用 LLM
```

可以将上下文划分为多个区域

```text
[系统规则]

[当前任务]

[关键状态]

[相关记忆]

[检索证据]

[可用工具]

[最近消息]

[输出要求]
```

上下文工程的目标不是让上下文最长，而是提高上下文的

```text
相关性

准确性

可信度

可读性

时效性

安全性

Token 利用率
```
