截至 **2026 年 8 月 26 日** ，MCP 官方标准 transport 是：

## **stdio**

- MCP Client （ **这里的mcp client指的是mcp要服务的客户端，比如codex，claude code，dsh的agent框架在使用某个mcp的时候，就是这个mcp的client** ） 启动一个子进程。
- 双方通过 stdin/stdout 传 JSON-RPC（就理解为json就好其实。。。）。
- 通常用于本机工具。

stdio = standard input / standard output，它是操作系统给每个进程提供的标准通信通道。

（ **命令行程序** 默认通过 stdin 接收输入，通过 stdout 输出正常结果，）

一个进程通常有三条标准的输入输出通道：

| 名称 | 缩写 | 用途 |
| --- | --- | --- |
| 标准输入 | stdin | 接收输入 |
| 标准输出 | stdout | 输出正常结果 |
| 标准错误 | stderr | 输出日志和错误信息 |

在 macOS/Linux 中，操作系统启动一个进程时，通常给它三个默认接口，举个例子，当我们在terminal中输入python nlp情感分类.py的时候，这个程序运行在某个进程(process)中：

```text
┌────────────────────┐
│      nlp情感分类 进程  │
│                    │
│ 0：stdin  输入口    │
│ 1：stdout 输出口    │
│ 2：stderr 错误口    │
└────────────────────┘
```

**操作系统默认的约定就是，每个启动的进程都会有三个默认数据接口用于和外界发生信息的传输。**

在 macOS/Linux 中，一个进程启动时，通常会有三个默认的标准数据接口：stdin、stdout 和 stderr。它们分别对应文件描述符 `0` 、 `1` 和 `2` （File Descriptor，简称 FD）其实应该叫I/O资源编号，叫文件描述符太误导人了。（每个进程都有自己的一张文件描述符表，编号背后可以指向文件、Terminal、Pipe或Socket，stdin、stdout、stderr就是三个特殊约定的文件描述符：0、1、2）

例如，当我们在 Terminal 中执行：

```text
python nlp情感分类.py
```

Shell 会启动一个 Python 解释器进程，由这个进程执行 `nlp情感分类.py` ：

```text
┌─────────────────────────┐
│ Python 进程              │
│ 正在执行：nlp情感分类.py │
│                         │
│ 0：stdin  标准输入       │
│ 1：stdout 标准输出       │
│ 2：stderr 标准错误       │
└─────────────────────────┘
```

如果希望用户从 Terminal 输入一段文本作为模型的输入，可以在 Python 代码中调用：

```text
model_input = input("请输入文本：")
```

`input()` 默认从当前 Python 进程的 stdin 读取一行文本，并将读取到的字符串赋值给 `model_input` 。

完成模型预测后，可以通过：

```text
prediction = model.predict([model_input])
print("预测结果：", prediction)
```

`print()` 默认将内容写入当前 Python 进程的 stdout。由于正常情况下 stdout 连接到 Terminal，因此最终可以在 Terminal 窗口中看到预测结果。

如果程序发生异常，Python 通常会将异常信息和 Traceback 写入 stderr。由于 stderr 正常情况下也连接到 Terminal，所以错误信息同样会显示在 Terminal 中。

## stdio MCP 怎么运行

假设你有一个 MCP Server（本地运行的一个mcp的进程）：

```text
algorithm_mcp_server.py
```

MCP Client 启动它：

```text
python algorithm_mcp_server.py
```

**注意：这里不是让你手动在终端执行，而是 MCP Client （即agent，例如codex）自动启动这个命令。**

运行结构是：

```text
Claude Desktop / Codex
        │
        │ 启动子进程
        ▼
python algorithm_mcp_server.py
```

然后双方通过管道通信（IPC（Inter-Process Communication，进程间通信））：

```text
MCP Client
   │
   │ JSON-RPC 写入 stdin 
（json-rpc =json+rpc(Remote Procedure Call,远程过程调用，JSON-RPC是一套消息格式和处理规则
通俗地说：
一个程序要求另一个程序执行某个函数，并把结果返回。这里的remote可以是本地的另一个进程，也可以是网络调用远程服务器)）
   ▼
MCP Server 子进程
   │
   │ JSON-RPC 写入 stdout
   ▼
MCP Client
```

完整示意：

```text
父进程：MCP Client
    │
    ├── 启动子进程：python algorithm_mcp_server.py
    │
    ├── stdin  ────────────► MCP Server
    │     发送 JSON-RPC
    │
    └── stdout ◄──────────── MCP Server
          接收 JSON-RPC
```

## 具体例子

Client 向 Server 的 `stdin` 写入一行：

```text
{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"predict","arguments":{"text":"很好用"}}}
```

Server 从 `stdin` 读到这一行，执行算法：

```text
result = predict("很好用")
```

然后向 `stdout` 写回一行：

```text
{"jsonrpc":"2.0","id":1,"result":{"label":"positive","score":0.97}}
```

这里通常是一行一条 JSON-RPC 消息。

## 为什么 stdio 通常用于本地工具

因为 MCP Client 需要执行：

```text
python algorithm_mcp_server.py
```

所以它必须能访问：

- Python；
- 代码文件；
- 模型文件；
- 环境变量；
- 本机目录。

**例如配置通常长这样：**

```text
{
  "transport": "stdio",
  "command": "python",
  "args": [
    "/Users/test/algorithm_mcp_server.py"
  ],
  "env": {
    "MODEL_PATH": "/Users/test/models/bert"
  }
}
```

MCP Client 看到这个配置后， **会在自己所在的机器启动** ：

```text
MODEL_PATH=/Users/test/models/bert \
python /Users/test/algorithm_mcp_server.py
```

## stdio mcp 的特点

### 优点

- 和网络请求没啥关系，就本地运行的一个程序，开发和使用都很简单方便

### 缺点

- 没法多人共享，只能在一台机器上不同的agent工具间共享，本质上是agent去启进程执行这个mcp对应的服务，因此如果存在多个session(对话)，每个对话会单独启动一个独立的进程去执行，比较适用于轻量级的mcp服务，比如fastctx

## **Streamable HTTP**

Streamable HTTP 的核心是：

> MCP Server 自己提前运行，MCP Client 只需要通过 URL 请求它。

比如你先启动一个算法服务：

```text
python algorithm_http_mcp_server.py
```

它监听：

```text
http://0.0.0.0:8000/mcp
```

运行结构是：

```text
MCP Client
    │
    │ HTTP POST
    ▼
http://算法服务器:8000/mcp
    │
    ▼
MCP Server
    │
    ▼
你的算法
```

agent不负责启动这个 MCP Server，这个mcp server是独立启动的。

HTTP 有不同的请求方法，比如：

- `GET` ：读取数据；
- `POST` ：提交数据；
- `PUT` ：更新数据；
- `DELETE` ：删除数据。

Streamable HTTP MCP 主要通过 `POST` 把 JSON-RPC 消息发送给 MCP endpoint。

例如：

```text
POST /mcp HTTP/1.1
Content-Type: application/json
Accept: application/json, text/event-stream
Authorization: Bearer xxx
```

请求体：

```text
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "predict",
    "arguments": {
      "text": "这个产品很好用"
    }
  }
}
```

Endpoint 可以理解为 一个base url：

> 一个服务对外暴露的具体访问地址。

例如：

```text
https://algorithm.example.com/mcp
```

可以拆成：

```text
https://                  协议
algorithm.example.com     域名
/mcp                      路径
```

`/mcp` 就是 MCP endpoint。

它不是普通算法 REST API，例如：

```text
POST /predict
POST /embedding
```

而是一个统一的 MCP 协议入口：

```text
POST /mcp
```

具体调用 `predict` 、 `embedding` 还是 `rerank` ，写在 JSON-RPC 请求体的 `method/params` 中。

### 为什么 HTTP 响应有时是 JSON，有时是 SSE

这里最容易把人绕晕。

**情况一：一次性返回 JSON**

例如你的分类算法很快：

```text
输入文本
  ↓
100ms 完成分类
  ↓
直接返回完整 JSON
```

响应：

```text
Content-Type: application/json
```

内容：

```text
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "label": "positive",
    "score": 0.97
  }
}
```

这和普通 HTTP API 基本一致。

**情况二：通过 SSE 流式返回**

SSE 全称：

```text
Server-Sent Events
服务器发送事件
```

**它允许服务器在一个 HTTP 响应连接里，连续发送多段事件。**

例如一个耗时算法：

```text
开始处理
加载数据完成
预处理完成
推理完成
返回最终结果
```

服务器可以逐步发送：

```text
data: {"type":"progress","value":0.2}

data: {"type":"progress","value":0.6}

data: {"type":"progress","value":0.9}

data: {"jsonrpc":"2.0","id":1,"result":{"label":"positive"}}
```

注意：

> SSE 不是另一个 MCP Server，也不是另一个业务接口；它只是 HTTP 响应的一种流式返回格式。

可以类比大模型聊天：

```text
普通 JSON：
等模型全部生成完，一次性返回。

SSE：
模型每生成几个字，就往客户端推送一段。

```

## 二者对比

| 对比项 | stdio | Streamable HTTP |
| --- | --- | --- |
| Server 谁启动 | MCP Client 启动 | 运维或部署系统提前启动 |
| Server 形态 | Client 的子进程 | 独立服务进程 |
| 通信通道 | stdin/stdout 管道 | HTTP |
| 是否需要端口 | 不需要 | 需要 |
| 是否需要 URL | 不需要 | 需要 |
| 是否需要网络 | 通常不需要 | 需要网络连接，即使是本机回环 |
| 是否容易多人共享 | 不容易 | 容易 |
| 是否方便远程部署 | 不方便 | 方便 |
| 是否适合重型模型 | 一般 | 更适合 |
| 典型配置 | command + args + env | url + headers |
| 生命周期 | 通常跟随 Client | 独立运行 |
| 多 Client | 通常各启一个进程 | 一个服务可接多个 Client |

## 应该怎么选

### 场景一：本地小算法、个人使用

例如：

- 本地读取 CSV；
- 调用一个 Python 函数；
- 本地数据分析；
- 查询本地 SQLite；
- 简单图像处理。

优先考虑：

```text
stdio
```

因为最简单：

```text
Agent
  → 启动 Python 子进程
  → 调算法
  → 返回结果
```

不需要部署服务。

### 场景二：大模型或重型算法

例如：

- GPU 推理；
- 大模型 embedding；
- reranker；
- 图像识别；
- 语音识别；
- 一个模型需要加载十几 GB 显存。

优先考虑：

```text
Streamable HTTP
```

因为模型可以只加载一次：

```text
GPU 服务器
  └── MCP Server
        └── 模型常驻显存
```

多个 Agent 都调用同一个服务：

```text
Agent A ─┐
Agent B ─┼── HTTP ──► MCP Server ──► GPU 模型
Agent C ─┘
```

如果使用 stdio，可能出现：

```text
Agent A 启动一份模型
Agent B 又启动一份模型
Agent C 再启动一份模型
```

显存直接炸掉。

### **场景三：多人共享算法能力**

例如团队统一提供：

- 数据库查询工具；
- 文档检索；
- 日志分析；
- 企业内部知识库；
- 统一算法推理平台。

优先考虑：

```text
Streamable HTTP
```

因为它更接近标准微服务（ **说实话我觉得这玩意就是包了一层mcp概念的微服务** ）：

```text
统一部署
统一鉴权
统一日志
统一限流
统一监控
统一升级
```

### stdio mcp

比如我在本地写了一个py文件，做了一个简单的基于规则的文本分类

```text
from typing import Annotated, Literal

from mcp.server import MCPServer
from pydantic import BaseModel, Field

server = MCPServer(
    name="sentiment-demo",
    title="中文情感分类 MCP",
    description="提供中文文本情感分类工具。",
    instructions=(
        "当用户需要判断中文文本的正面、负面或中性倾向时，"
        "调用 predict_sentiment。"
    ),
)

class SentimentResult(BaseModel):
    label: Literal[
        "positive",
        "negative",
        "neutral",
    ] = Field(
        description="文本的情感类别。",
    )

    score: int = Field(
        description="正面关键词数减去负面关键词数。",
    )

@server.tool(
    name="predict_sentiment",
    title="中文文本情感分类",
    description=(
        "判断一段中文文本是正面、负面还是中性；"
        "适用于评论、反馈和短句。"
    ),
)
def predict_sentiment(
    text: Annotated[
        str,
        Field(
            description="需要分类的中文文本，例如：这个电影很好看。",
            min_length=1,
            max_length=2000,
        ),
    ],
) -> SentimentResult:
    positive = ("喜欢", "好看", "优秀", "满意")
    negative = ("讨厌", "难看", "糟糕", "失望")

    score = (
        sum(word in text for word in positive)
        - sum(word in text for word in negative)
    )

    return SentimentResult(
        label=(
            "positive"
            if score > 0
            else "negative"
            if score < 0
            else "neutral"
        ),
        score=score,
    )
```

**Server级描述**

```text
server = MCPServer(
    name="sentiment-demo",
    title="中文情感分类 MCP",
    description="提供中文文本情感分类工具。",
    instructions="当用户需要判断……时，调用 predict_sentiment。",
)
```

作用是描述整个 MCP Server：

```text
Server名称：sentiment-demo
Server标题：中文情感分类 MCP
Server用途：提供中文文本情感分类
使用指导：遇到什么问题时使用其中的工具

```

**具体作用类似于tool的define，就是告诉agent 这个 mcp 是干啥用的，这样当遇到match的需求的时候，agent会想到去调用这个mcp来解决问题**

**Tool级描述**

```text
@ server.tool(
    name="predict_sentiment",
    title="中文文本情感分类",
    description="判断一段中文文本是正面、负面还是中性；适用于评论、反馈和短句。",
)
```

告诉Agent：

```text
工具名称：predict_sentiment
工具标题：中文文本情感分类
工具作用：判断文本情感
适用场景：评论、反馈、短句
```

agent就能根据 `description` 判断：

```text
用户意图和predict_sentiment的描述匹配
应该调用这个Tool
```

**参数描述**

```text
text: Annotated[
    str,
    Field(
        description="需要分类的中文文本，例如：这个电影很好看。",
        min_length=1,
        max_length=2000,
    ),
]
```

它描述：

```text
参数名：text
类型：字符串
作用：需要分类的中文文本
最短长度：1
最长长度：2000
示例：这个电影很好看
```

SDK会把它生成JSON Schema。

**返回值描述**

```text
class SentimentResult(BaseModel):
    label: Literal[
        "positive",
        "negative",
        "neutral",
    ]

    score: int
```

它告诉agent：

```text
返回一个Object

label只能是：
positive
negative
neutral

score必须是整数
```

## 整个mcp的调用过程（agent视角）

我们把整个过程想成：

```text
Codex = 公司前台兼调度员
大模型 = 负责判断该找谁干活的主管
MCP Server = 外聘的情感分析专家
Tool Definition = 专家的服务说明书
tools/call = 发给专家的任务单
MCP SDK = 专家的秘书，负责检查任务单并调用函数
```

假设用户说：

> 帮我判断“这个电影很好看，我很喜欢”是什么情感。

下面一步一步看， **每一步谁看到了什么，以及内容来自代码哪里** 。

### **第9步：Codex包装成MCP消息**

模型通常不会自己手写完整的JSON-RPC。

**模型先产生逻辑上的Tool Call（和常规的tools 调用的格式是一样的）：**

```text
{
  "name": "predict_sentiment",
  "arguments": {
    "text": "这个电影很好看，我很喜欢"
  }
}
```

Codex程序再把它包装成MCP的JSON-RPC：

```text
{
  "jsonrpc": "2.0",
  "id": 7,
  "method": "tools/call",
  "params": {
    "name": "predict_sentiment",
    "arguments": {
      "text": "这个电影很好看，我很喜欢"
    }
  }
}
```

所以要区分：

```text
大模型生成：
Tool名称和arguments

Codex程序负责：
包装JSON-RPC
添加id
通过stdin发送
等待stdout响应
```

大模型不需要理解stdin、stdout或者JSON-RPC传输细节。

### **第10步：MCP SDK收到任务单并检查**

MCP SDK收到：

```text
{
  "name": "predict_sentiment",
  "arguments": {
    "text": "这个电影很好看，我很喜欢"
  }
}
```

它首先查找：

```text
有没有叫predict_sentiment的Tool？
```

名称来自：

```text
@server.tool(
    name="predict_sentiment",
)
```

找到以后开始检查参数：

```text

    有

text是不是字符串？
    是

text是不是空字符串？
    不是

text是否超过2000字符？
    没有
```

这些规则来自：

```text

    str,
    Field(
        min_length=1,
        max_length=2000,
    ),
```

```text

  "text": ""
}
```

SDK会拒绝，因为：

```text

```

所以：

```text

```

### **第14步：agent看到Tool结果**

此时agent看到：

```text

{
  "label": "positive",
  "score": 2
}
```

同时它已经知道返回值说明：

```text

文本的情感类别

score：
正面关键词数减去负面关键词数
```

这些说明来自：

```text
class SentimentResult(BaseModel):

        description="文本的情感类别。",
    )

    score = Field(
        description="正面关键词数减去负面关键词数。",
```

这非常重要。


```text
置信度是2
或者情感概率是2
```

```text
score是正面关键词数减去负面关键词数
```

模型就知道：

```text
它不是概率
它是关键词差值
```

### streamable http mcp

整体类似

| 对比项 | stdio MCP | Streamable HTTP MCP |
| --- | --- | --- |
| Server由谁启动 | Codex/Agent自动启动子进程 | 你或部署系统提前启动 |
| 启动关系 | Codex → uv/python → MCP Server | 你/Docker → MCP Server，Codex只连接 |
| 常见部署位置 | 本机 | 本机或远程服务器 |
| Codex配置内容 | 启动命令、参数、环境变量、工作目录 | URL、Header、Bearer Token |
| 是否需要端口 | 不需要 | 需要 |
| MCP地址 | 没有URL | 例如http://127.0.0.1:8000/mcp |
| 通信通道 | 操作系统Pipe | HTTP网络连接 |
| Client发送消息 | 写入Server的stdin | HTTP POST请求 |
| Server返回消息 | 写入Server的stdout | HTTP Response或SSE |
| 消息内容 | JSON-RPC | JSON-RPC |
| Server发现/握手 | 相同协议流程 | 相同协议流程 |
| 获取Tool列表 | tools/list | tools/list |
| Agent看到的Tool名称 | 相同 | 相同 |
| Agent看到的description | 相同 | 相同 |
| Agent看到的inputSchema | 相同 | 相同 |
| Agent生成arguments | 相同 | 相同 |
| 调用Tool | tools/call | tools/call |
| SDK参数校验 | 相同 | 相同 |
| 调用Python函数 | 相同 | 相同 |
| 函数返回结果 | 相同 | 相同 |
| 多Client共享 | 通常每个Client启动一份 | 多个Client可连接同一服务 |
| 重型模型 | 可能被多个子进程重复加载 | 可以长期运行并共享一份模型 |
| 网络认证 | 通常不需要 | 通常需要Token、Header或OAuth |
| 日志位置 | 必须使用stderr，避免污染stdout | 正常服务日志即可 |
| Client退出后 | 子进程一般随之退出 | Server通常继续运行 |
| 适用场景 | 本地脚本、文件工具、个人工具 | GPU模型、团队共享、远程服务 |

**对Agent来说，两者完全一样的部分**

| Agent看到的内容 | 来自代码哪里 |
| --- | --- |
| Tool名称 | server.tool(name=...) |
| Tool用途 | server.tool(description=...) |
| 参数名称 | Python函数参数名 |
| 参数类型 | str、int等类型注解 |
| 参数说明 | Field(description=...) |
| 参数限制 | min_length、max_length等 |
| 返回字段 | Pydantic返回模型 |
| 返回字段说明 | 返回模型里的Field(description=...) |

**唯一需要修改的代码**

| stdio | Streamable HTTP |
| --- | --- |
| server.run(transport="stdio") | server.run(transport="streamable-http", host="127.0.0.1", port=8000) |

最终数据流：

| stdio | Streamable HTTP |
| --- | --- |
| Codex → Pipe → stdin → Server | Codex → HTTP POST → /mcp → Server |
| Server → stdout → Pipe → Codex | Server → HTTP Response → Codex |

**Agent不关心Tool来自stdio还是HTTP。它看到的都是同一张Tool说明卡；transport只负责把JSON-RPC消息运过去。**
