### 起因

我本来想靠读 vLLM 的源码学 LLM 推理，没读下去。代码量太大，追一条调度路径追到底，发现相关代码已经重构过了，得重新来。后来换小一点的实现，看了 nano-vllm，骨架确实清楚，但读完发现只学到骨架：没有张量并行，没有 MoE，没有量化，没有投机解码，也没有服务层。想学，就想看个全乎的。

于是我在 nano-vllm 基础上接着写。它是 MIT 的，原作者署名保留在 LICENSE 里。写法上就一条原则：加一个特性，就必须可读、可跑、可测。写完数了下行数，整个包 4,100 行 Python。

仓库：[https://github.com/jijic137/Z-vllm](https://github.com/jijic137/Z-vllm)

### 里面有什么

特性就不列表格了，一口气说完：PagedAttention（256 token 块，prefix cache 是哈希链 + 引用计数共享）、continuous batching、chunked prefill、张量并行 1-8 卡、MoE 专家并行（TP×EP 自由组合）、W8A16 权重量化、KV cache int8、零训练投机解码（草稿来自序列自身历史的 n-gram，不用草稿模型）、CUDA graph + torch.compile、DP 多副本、OpenAI 兼容服务（FastAPI，SSE 流式，客户端断连自动释放 KV 块）。

几个我觉得是核心的实现点，多说两句：

调度循环是最关键的地方。decode 优先，prefill 拿剩下的预算。chunked prefill 不是往上叠的功能，是循环本身的工作方式：队首 prompt 有 2000 token，这步预算只剩 300，那就先 prefill 前 300 个，下步从 301 继续，期间新请求照常得到服务，长 prompt 不会把 GPU 锁死。KV 块用完就抢占最年轻的序列，打回队首，它已经算过的前缀块还在缓存里，不用重算。

KV 块的分配也值得看。块的哈希是链式滚动的（xxh64），本块 hash = 上一块 hash + 本块 token，相同前缀永远命中同一条链，所以共享 system prompt 的多个请求直接复用同一批物理块，prefill 计算省掉。多轮对话和 RAG 场景下这个收益最明显。

decode 的 attention 是自研的 Triton paged kernel，要点是全程不做 host 同步，所以能被 CUDA graph 捕获。prefill 走 flash-attn varlen，没装 flash-attn 就退回 SDPA，正确性一样，就是吞吐略低。

MoE 我用 Qwen3-30B-A3B 测的，128 个专家。专家权重是一个大 buffer 的 view，融合路径零拷贝。decode 路径是排序分桶、两个 grouped GEMM、silu&mul、scatter、all_reduce，融合完单层 MoE 子层从 3.65 ms 到 0.76 ms。

投机解码是零训练的：草稿 token 直接从序列自身历史的 n-gram 匹配里拿，没有草稿模型，也没有额外的 draft forward。目标模型一次 varlen forward 做接受-拒绝，输出分布和目标模型严格相等，投机不改质量。

### 跑起来

Python 3.10-3.12，依赖就四个：torch、triton、transformers、xxhash。flash-attn 可选。

```bash
git clone https://github.com/jijic137/Z-vllm.git
cd Z-vllm
pip install -e .
from zvllm import LLM, SamplingParams

llm = LLM("Qwen/Qwen3-0.6B", enforce_eager=True, tensor_parallel_size=1)
outputs = llm.generate(["你好"], SamplingParams(temperature=0.6, max_tokens=256))
print(outputs[0]["text"])
```

模型权重默认走魔搭，首次自动下载缓存，失败才回退 Hugging Face，不用自己搬权重。AMD 卡是同一套代码路径，NCCL 自动映射 RCCL，没改一行代码。

想当服务用，一行命令的事：

```bash
pip install "z-vllm[serve]"
python -m zvllm.entrypoints.openai.api_server --model Qwen/Qwen3-0.6B --port 8000
```

OpenAI SDK 直接对接，/v1/chat/completions 和 /v1/completions 都支持 SSE 流式。

### 性能

脚本都在 benchmarks/ 目录里，照抄就能复现。

Qwen3-0.6B，4070 笔电 8GB，256 请求，输入 100-1024 token：

|  | 输出 token 数 | 耗时 (s) | 吞吐 (tok/s) |
| --- | --- | --- | --- |
| vLLM | 133,966 | 98.37 | 1361.84 |
| Z-vLLM | 133,966 | 93.41 | 1434.13 |

Qwen3-30B-A3B，8× AMD W7900D 48GB，纯 EP=8，贪心：

| 并发 | decode 步 (ms) | 聚合吞吐 (tok/s) |
| --- | --- | --- |
| 1 | 111.1 | 9.13 |
| 16 | 109.4 | 148.19 |
| 64 | 110.5 | 587.79 |

W8A16：30B 每卡权重从 28.5 GiB 到 14.8 GiB，单张 48GB 卡能跑（bf16 至少 2 卡），实测 ΔPPL +0.08。

亏的数字也放出来，不然不算诚实：

KV int8 是 per-token scale，粒度偏粗，KV 块数翻倍，但实测 ΔPPL +10.6%，目前只建议显存真是瓶颈、能接受质量损失时用。更细的 per-head scale 在 roadmap 里。

投机解码 8 并发贪心，TPOT 从 30.75 ms 到 23.31 ms，接受率 0.958。但小模型高并发下，批里只要有一条带草稿，整批就走 varlen 慢路径，聚合吞吐反而掉到 0.75×。收益区间是大模型、低并发、单流。

DP 多副本有个交叉点：并发 32 以下单引擎宽 EP 占优（C=16 时 +16.1%），并发 64 时 DP 反超（+7.6%）。机制分析（批拆分、all_reduce 流量、eager 逐层开销）我写在 README 里了，那部分值得看。

### 怎么读这份代码

105 个单测全是纯 CPU，没有 GPU 的笔记本也能上手。我读的顺序是这样的：

第一天，example.py，然后 llm_engine.py 的 step()（200 行出头），再 scheduler.py。这时候应该能画出一个请求的完整生命周期。

第一周，block_manager.py 和 attention.py，把块的分配、回收、共享，prefix cache 什么条件命中，搞清楚。

第二周，model_runner.py 和 layers/linear.py（张量并行），然后是 qwen3_moe.py 和 layers/fused_moe.py（专家并行）。

再往后，quantization.py、spec_decode.py、dp_engine.py，每个都是独立一章，顺序随意。

roadmap 基本就是习题集：W4 量化、KV 量化更细的 scale、ROCm 下 flash-attn 兼容、投机解码向量化。挑一个做掉，简历上就多一条”我改过推理引擎”。

最后说下适合谁：想搞清楚推理机制的、想单机搭个小推理服务的、手上只有 AMD 卡的，都可以看。要做生产多机集群的，直接用 vLLM 或 SGLang，不用绕这里。

### 和 nano-vllm、vLLM 的区别

|  | nano-vllm | Z-vLLM | vLLM |
| --- | --- | --- | --- |
| 定位 | 最小骨架，千行级 | 能读完的完整引擎，约 4,100 行 | 生产级标杆，万行级 + C++/CUDA |
| PagedAttention / continuous batching | ✓ | ✓ | ✓ |
| chunked prefill / prefix cache | — | ✓ | ✓ |
| 张量并行 1-8 卡 | — | ✓ | ✓ |
| MoE + 专家并行 | — | ✓ | ✓ |
| 权重量化 / KV 量化 | — | ✓ | ✓（种类更多） |
| 投机解码 | — | ✓ | ✓ |
| 多副本 | — | ✓ | ✓ |
| OpenAI 兼容服务 | — | ✓ | ✓ |
| 学习曲线 | 1-2 天 | 1-3 周 | 数月 |
