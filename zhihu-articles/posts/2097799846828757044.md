## 一、背景：从 Mega MoE 的融合计算到 decode 优化

### Mega MoE 为什么重要

MoE 通过 top-k 路由，让每个 token 只访问部分专家，从而在扩大模型参数规模的同时控制计算量。专家分布在多张 GPU 上时，一次 MoE 前向包含 token 分发、专家计算和结果合并；如果这些步骤逐个执行，通信和计算之间的等待，以及多次内核启动与中间数据处理，都会进入推理的关键路径。

DeepGEMM 的 Mega MoE 将这条链路融合进一个 mega-kernel：

```text
EP dispatch → W1 → SwiGLU / 量化 → W2 → EP combine
```

其中，W1 同时计算 gate 和 up 两个投影，W2 将激活后的中间结果投影回隐藏维度；EP（Expert Parallel）负责跨 GPU 的专家并行。Mega MoE 的价值在于，把通信、矩阵计算和激活处理作为一条流水组织，使 NVLink 数据传输能够与 Tensor Core 计算重叠，减少阶段之间的停顿。[Mega MoE 介绍](https://zhuanlan.zhihu.com/p/2046275229597672923)

### decode 为什么仍有优化空间

与一次处理大量 token 的 prefill 相比，decode 通常只为每条活跃序列生成少量新 token。经过 top-k 分配后，每个专家拿到的输入可能更少，通信、调度和同步成本也就更难被大量矩阵计算摊薄。

以 8 个 rank、256 个路由专家、top-k=8 为例，在均衡路由的期望下，每个专家接收的 token 数为：

```text
平均专家 token 数 = rank 数 × 每 rank token 数 × top-k / 专家总数
                 = 8 × T × 8 / 256
                 = T / 4
```

当每 rank 只有 1 个 token 时，平均每个专家仅有 0.25 条路由输入。此时，尽快准备少量有效数据并推进依赖链，与提高大矩阵的峰值吞吐同样值得关注。

进一步看 `fp8_fp4_mega_moe` 的实现，其单个 CTA（线程块）同时容纳多类工作：

| 线程职责 | 承担的工作 |
| --- | --- |
| dispatch warps | 路由计数、跨卡 token 拉取、数据就绪发布及相关清理 |
| 非 epilogue warps | 激活和权重的 TMA 加载、MMA 发射、任务调度 |
| epilogue warps | 读取累加结果，执行激活、量化、写回与 combine |

代码中，线程总数由这几类职责相加得到：

```cpp
kNumThreads = kNumDispatchThreads + kNumNonEpilogueThreads + kNumEpilogueThreads;

```

各类 warp 会分别调整寄存器配额，但仍受同一个 CTA 的资源预算约束；共享存储也要容纳搬运缓冲区、数学流水和各类 barrier。

从这一代码结构看，decode 的潜在代价主要有两点。首先，少量有效 token 仍要经过路由计数、任务发布、同步和流水启动；计算越短，这些工作的相对占比越高。其次，通信与计算的资源需求不同，却被组织在同一个 CTA 中；即使某一类 warp 暂时无事可做，整个 CTA 的驻留仍需满足整体资源约束。

这为进一步优化提供了方向：**保留完整的融合数学链路，让通信与计算分别使用适合自己的 SM 资源，再按数据就绪状态协作。** GC MoE 使用 CUDA Green Contexts 重新组织 MoE 的执行架构。

## 二、CUDA Context：从执行环境到资源分区

### Context 管什么

CUDA Context 是 GPU 工作所处的执行环境，关联设备地址空间、加载的模块以及 stream、event 等对象。主机线程发起依赖上下文的 CUDA 操作时，需要有对应的 current context；同一主机线程同一时刻只有一个 current context。CUDA Runtime 通常使用每设备、每进程共享的 primary context，Driver API 也可以访问它。[CUDA Context 官方说明](https://docs.nvidia.com/cuda/cuda-programming-guide/03-advanced/driver-api.html#context)

对于应用，可以从三个层面理解 GPU 工作的组织：

| 层面 | 主要回答的问题 |
| --- | --- |
| Context | 工作属于哪个执行环境，关联哪些设备资源 |
| Stream / CUDA Graph | 工作按照什么顺序执行，任务之间有哪些依赖 |
| Kernel / CTA / warp | GPU 上的线程如何分工、搬运数据和计算 |

在普通上下文中，创建两个 stream 可以表达两条独立的任务序列，却没有为它们各自保留一组 SM。如果一个内核已占据可用的执行资源，另一个内核即使处于独立 stream，也可能需要等待。CUDA Graph 同样侧重执行依赖的表达，多节点之间是否能有效重叠，还取决于资源是否可用。

### Green Context 增加了什么能力

Green Context 是能够关联特定 GPU 资源的轻量上下文。应用可先划分 SM 资源，再把工作提交到对应的 Green Context，让不同任务使用各自分配的 SM。它与 primary context 保持紧密关联，适合在同一进程内组织不同类型的 GPU 工作。[Green Contexts 设计说明](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/green-contexts.html)

对通信与计算重叠而言，可以形成下面的资源关系：

![](https://picx.zhimg.com/v2-15142bb078360b033f2ebfde762856df_r.jpg)

分区让 dispatch 能够在分配给自己的 SM 上推进，同时让矩阵计算在另一组 SM 上持续工作。两类工作仍通过共享的数据和就绪信号连接，从而在资源层面支持流水重叠。

工作队列也是影响重叠的因素。即使 SM 分区不同，底层队列的关联仍可能引入执行依赖；支持时可使用 balanced workqueue 配置来减少这类干扰。SM 分区和工作队列配置有助于创造并发条件，实际执行仍受其他共享资源与数据依赖影响。[CUDA Green Context Driver API](https://docs.nvidia.com/cuda/cuda-driver-api/cuda_driver_api/group__CUDA__GREEN__CONTEXTS.html)

这项能力与 MoE 的需求相契合：dispatch 更关注数据与元数据何时准备好，专家计算更关注 Tensor Core 能否持续获得输入，二者可以采用不同的资源配额。

## 三、GC MoE 的架构与优势

GC MoE 以 CuTe DSL 实现 FP8/FP4 MoE 内核，使用 Green Context 分配通信与计算资源，并通过一个三角色 CUDA Graph 连接完整算子。路由专家采用 FP8 激活与 FP4 权重，也支持融合 FP8 共享专家，输出为 BF16。

### 三角色执行架构

![](https://pic2.zhimg.com/v2-178755c769aa5fdd56cb07955bc018f7_r.jpg)

**Role 1 负责 dispatch。** 它处理路由元数据，组织跨 rank 输入访问，为本地专家准备 token 和 scale，并发布数据就绪信号。该角色运行在通信 Green Context 中，资源规模可以独立于数学计算配置。

**Role 2 负责完整数学流水。** 它按就绪状态消费任务，执行 W1、SwiGLU、路由权重与 FP8 量化，再执行 W2。Role 1 尚在准备后续输入块时，Role 2 即可消费已就绪的块。共享专家的两个线性阶段也纳入该角色的调度。

**Role 3 负责 combine 与收尾。** 它在 Role 1、Role 2 完成后启动，执行跨 rank 输出合并、写回本 rank 的 BF16 结果，并完成同步和状态收尾。它复用计算 Green Context 的 SM 分区。

前两个角色之间没有整节点的顺序依赖，依靠设备侧协议分块协作；第三个角色的完成依赖由 Graph 显式表达。三个角色均位于每个 rank 的进程内。

### 数学流水如何保持高效

Role 2 以两个 CTA 构成一个 cluster，通过任务发布与消费协议协调加载、计算和 epilogue：

![](https://pic4.zhimg.com/v2-28d0d42ef13b4c6dc9081c797904e8df_r.jpg)

W1 将 gate 与 up 投影合并计算，epilogue 保留相应的 BF16 舍入、激活和量化顺序。生成的 FP8 激活与 scale 进入循环工作区，由 W2 消费。调度器在 W1 预热后交错推进 W1 与 W2，通过就绪计数和消费完成信号控制槽位复用，缩短中间数据的生命周期。

路由专家与共享专家分别使用对应的数据布局和权重格式，同时复用数学流水。共享专家直接处理本 rank 输入，其 W1/W2 阶段与路由专家任务统一组织。

### 相比单个 mega-kernel，优势体现在哪里

**通信与计算的资源配额更明确。** Mega MoE 在 CTA 内按 warp 划分职责，GC MoE 进一步在 GPU 层面划分 SM。运行时查询设备资源和对齐约束后创建通信、计算两个 Green Context，并把角色节点绑定到对应上下文。默认请求 16 个 dispatch SM，实际数量由驱动对齐后返回；B300 上可形成 20 个通信 SM 与 128 个计算 SM。

**数学角色的资源预算更集中。** Role 2 的 CTA 围绕 TMA、MMA、调度与 epilogue 组织，dispatch 在另一个角色内核中执行。每个角色可以采用自己的线程、寄存器和共享内存配置，也只初始化自己需要的同步对象。对于工作量较小的 decode，这种分工有机会减少无关工作对关键路径的影响。

**保留通信与计算的细粒度重叠。** 分拆后的角色仍通过对称内存、跨卡就绪信号、ring buffer 和设备侧同步协作。输入分块准备好后即可进入数学流水，外层 Graph 则管理完整调用的执行关系。

**适合接入现有 Graph 推理流程。** 三个角色组成可复用的 child Graph，普通调用启动该图，外层 capture 时将其接入应用的 CUDA Graph。内核、TensorMap 和 Graph 在配置准备完成后复用，稳定 decode 通过 replay 推进。

性能收益取决于形状、资源划分和流水效率；下面的性能图展示当前实现相对 Mega MoE 的实际结果。

## 五、总结

GC MoE 的核心是将通信与计算的资源分工落实到 SM 分区，同时保留由数据就绪状态驱动的数学流水。dispatch 可以独立推进，专家计算可以采用更集中的线程、寄存器和共享内存配置，再通过 CUDA Graph 组织完整调用。

这一设计同时适用于 Hopper 和 Blackwell，但内核实现需要贴合硬件：Hopper 使用 WGMMA，并在融合 SE 时增加独立共享专家角色；Blackwell 使用双 CTA cluster、tcgen05 和 TMEM，将路由专家与共享专家纳入统一数学调度。
