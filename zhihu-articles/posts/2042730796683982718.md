## DeepSeek V4 的分布式训练（最简化版）

本文记录了在 128 张 H20 GPU 上训练 DeepSeek-V4-Flash的完整并行化实战过程。从”单卡装不下”到”三层并行协同训练 + checkpoint round-trip”，这不是一篇论文复现教程，而是一个工作过程笔记。

> 本文涉及的代码已在 [Tencent/Wechat-YATT](https://github.com/Tencent/Wechat-YATT) 开源，核心文件位于 `gpatch_v4/models/deepseek_v4/`。文中引用的代码片段均可在开源仓库中找到完整版本。<br> 本文由 AI 生成，人工修正，尚未精修。<br> 本文尚不涉及 fp4 / fp8 训练，会在后续 work 中分开讨论。

---

### 0. 为什么需要三层并行

假设你拿到一个模型，想微调它。通常的操作是：

```text
model = AutoModelForCausalLM.from_pretrained("deepseek-ai/DeepSeek-V4-Flash")
model.train()
```

然后你会看到 OOM。

DeepSeek-V4-Flash 有 256 个 expert，43 层 transformer，即使只加载 bf16 权重也要消耗 ~530 GiB 显存——而 H20 单卡只有 96 GiB。这不是优化能解决的问题，这是物理限制。

所以我们需要**把模型拆开**，让多张卡各持一部分。问题是：怎么拆？

答案是三个正交的维度同时拆：

| 并行方式 | 切什么 | 解决什么问题 |
| --- | --- | --- |
| FSDP2（Fully Sharded Data Parallel） | 参数、梯度、优化器状态 | 单卡装不下完整模型参数 |
| EP（Expert Parallel） | MoE 的 expert 权重 | 256 个 expert 太多，按组分给不同卡 |
| CP（Context Parallel） | 序列轴（激活值） | 长序列的激活值显存爆炸 |

三者正交的含义是：EP 切参数的 expert 维度，CP 切激活的序列维度，FSDP 在此之上再切参数的其余维度。它们可以任意组合，互不干扰——至少理论上是这样。

### 1. FSDP2：把每张卡变成模型的”一个碎片”

### 核心思想

FSDP（Fully Sharded Data Parallel）的思路很简单：既然一张卡装不下完整参数，那就把参数沿第一个维度切成 N 份，每张卡只持有 1/N。forward 时临时 all-gather 拼回完整参数，backward 结束后再 reduce-scatter 把梯度分片存回去。

```text
16 张卡，每张卡持有参数的 1/16
         │
    forward 时：
    ┌──────────────────────┐
    │  all-gather → 完整参数 │  ← 临时拼回来
    │  计算 output          │
    │  释放完整参数          │  ← 用完就扔
    └──────────────────────┘
         │
    backward 时：
    ┌──────────────────────┐
    │  all-gather → 完整参数 │  ← 再拼一次
    │  计算梯度             │
    │  reduce-scatter 梯度  │  ← 梯度也分片存
    │  释放完整参数          │
    └──────────────────────┘
```

FSDP2 是 PyTorch 对原始 FSDP 的重写，核心改进是用 `DTensor`（Distributed Tensor）表示分片后的参数——每个 `DTensor` 知道自己是全局张量的哪一片，属于哪个 mesh 的哪个维度。这使得多层并行的 mesh 拓扑组合变得可行。

### 关键 API

```text
from torch.distributed.fsdp import fully_shard, MixedPrecisionPolicy

mp_policy = MixedPrecisionPolicy(
    param_dtype=torch.bfloat16,    # forward 用 bf16
    reduce_dtype=torch.float32,     # 梯度聚合用 fp32
)

for layer in model.layers:
    fully_shard(layer, mp_policy=mp_policy)
fully_shard(model, mp_policy=mp_policy)
```

一个容易忽略的细节：**fp32 master + bf16 forward**。我们的参数以 fp32 存储（master copy），forward 时 FSDP 自动 cast 到 bf16，梯度聚合回到 fp32。这不是偏好，而是正确性要求——后面会解释这是怎么发现的。

### 2. EP：给 256 个 Expert 分配”工位”

### MoE 的特殊性

DeepSeek-V4 是 Mixture-of-Experts 模型。每一层有 256 个 expert（外加 1 个 shared expert），但每个 token 只激活其中 8 个。这意味着：

- **参数量巨大**（因为有 256 个 expert 的权重）
- **计算量适中**（因为每个 token 只用 8 个）
- **单卡装不下**（即使用 FSDP 分片，256 个 expert 的权重仍然太大）

EP 的做法是：把 256 个 expert 按组分配给不同的卡。

```text
ep_size = 8 → 每张卡持有 256/8 = 32 个 expert

              ┌─────────┐
   token  ──→ │  router  │ ──→ "这个 token 应该去 expert #147"
              └─────────┘
                   │
              ┌────▼────┐
              │ all-to-  │   把 token 发到持有 expert #147 的卡
              │ all      │
              └────┬────┘
                   │
              ┌────▼────┐
              │ expert   │   在目标卡上本地计算
              │ #147     │
              └────┬────┘
                   │
              ┌────▼────┐
              │ all-to-  │   结果发回原来的卡
              │ all      │
              └─────────┘
```

这里有两次 all-to-all 通信：dispatch（送过去）和 combine（拿回来）。这是 EP 的主要通信开销。all-to-all 的 autograd function 实现在 `a2a.py`——backward 就是把 `in_splits` / `out_splits` 对调再做一次 all-to-all（转置即逆）：

```text
class _AllToAllUneven(torch.autograd.Function):
    @staticmethod
    def forward(ctx, group, input, in_splits, out_splits):
        ctx.in_splits, ctx.out_splits = in_splits, out_splits
        out = torch.empty(sum(out_splits), *input.shape[1:], ...)
        dist.all_to_all_single(out, input, output_split_sizes=out_splits,
                               input_split_sizes=in_splits, group=group)
        return out

    @staticmethod
    def backward(ctx, grad):
        # 转置：sender ↔ receiver
        return None, _AllToAllUneven.apply(
            ctx.group, grad, ctx.out_splits, ctx.in_splits), None, None
```

### Mesh 拓扑

EP 需要一个 2D mesh：

```text
ep_2d_mesh = init_device_mesh(
    "cuda",
    mesh_shape=(world_size // ep_size, ep_size),
    mesh_dim_names=("ep_fsdp", "ep"),
)
# 例：world_size=128, ep_size=8 → (16, 8)
# 第一维 ep_fsdp：同一 ep 组内的 FSDP 分片
# 第二维 ep：不同 expert 组
```

Expert 权重在 `ep` 维度按组切分，在 `ep_fsdp` 维度再做 FSDP 分片。两层套娃，但 PyTorch `DTensor` 帮你管理所有的切片语义。

切分逻辑在 `hp.py` 的 `_shard_experts_dtensor` 中——用 `DTensor.from_local(..., Replicate())` 包一层全局视图，再 `redistribute(..., Shard(0))` 沿 expert 维切片，最后 `.to_local().clone()` 落到本地：

```text
def _shard_experts_dtensor(experts, ep_2d_mesh):
    ep_mesh = ep_2d_mesh["ep"]
    num_local = experts.num_experts // ep_mesh.size()
    for name in ("gate_up_proj", "down_proj"):
        p = getattr(experts, name)
        if p.is_meta:
            local = torch.empty((num_local,) + tuple(p.shape[1:]), dtype=p.dtype, device="meta")
        else:
            dt_full = DTensor.from_local(p.data, device_mesh=ep_mesh, placements=[Replicate()])
            local = dt_full.redistribute(ep_mesh, [Shard(0)]).to_local().contiguous().clone()
        setattr(experts, name, nn.Parameter(local))
    experts.ep_size, experts.ep_rank = ep_mesh.size(), ep_mesh.get_local_rank()
    experts.ep_group, experts.num_local_experts = ep_mesh.get_group(), num_local
```

### 一个重要的 API 设计决策

我们把 EP + FSDP + CP 的所有初始化逻辑封装成一个函数 `apply_hp`（HP = Hybrid Parallel）：

```text
model = apply_hp(model, ep_2d_mesh, cp_mesh=cp_mesh)
```

这一行做了五件事：

1. 切分 expert 权重到 ep 组（`_shard_experts_dtensor`）
2. FSDP wrap 所有层 + 设置 `set_gradient_divide_factor`
3. 绑定 `model.clip_grad_norm_`（跨多 mesh 的梯度裁剪）
4. 绑定 `model.load_checkpoint_hp` / `model.save_checkpoint_hp`
5. 如果有 `cp_mesh`，把 `cp_group/cp_size/cp_rank` 绑到每个 attention 上（`_bind_cp`）

模型类本身只需要继承一个空的 marker class `HpModule`，engine 端用 `isinstance(model, HpModule)` 分派到 hybrid-parallel 构建路径：

```text
class HpModule:
    """Empty marker base class for "hybrid-parallel" models."""
    pass

class DeepseekV4ForCausalLM(DeepseekV4PreTrainedModel, GenerationMixin, HpModule):
    ...
```

为什么叫 `hp` 而不是 `ep_fsdp`？因为后来加了 CP，再叫 `ep_fsdp` 就名不副实了。命名是 API 设计中最难的事之一——我们在项目中期做了一次全局重命名（`apply_ep_fsdp → apply_hp`，改了 8 个文件），只为给未来扩展留下语义正确的接口名。

### 3. CP：把长序列切成几段分头算

### 问题

Attention 的显存开销与序列长度的平方成正比。当序列长度从 2048 增长到 8192，attention 的激活值显存翻了 16 倍。H20 的 96 GiB 很快不够用。

### CP 的做法

把输入序列沿位置轴均匀切给 cp_size 张卡：

```text
输入序列 [B, S]，cp_size = 4
─────────────────────────────────────
          ┌────────┬────────┬────────┬────────┐
tokens →  │ S/4    │ S/4    │ S/4    │ S/4    │
          └────────┴────────┴────────┴────────┘
           rank 0    rank 1   rank 2   rank 3
               │        │        │        │
               │  attention 需要跨 rank 的 KV
               ▼        ▼        ▼        ▼
          每个 rank 只计算 S/4 个位置的 output
```

**关键挑战**：attention 的 query 在 rank i，但它需要看到其他 rank 的 key/value。这就是 CP 的通信内容。

DeepSeek-V4 的 attention 非常特殊——它使用了三种不同的 attention 模式：

| 模式 | 特点 | CP 下的通信 |
| --- | --- | --- |
| Sliding Window（SWA） | 只看前后固定窗口 | ring P2P：向下一个 rank 发送尾部 KV |
| CSA（Compressor Sparse Attention） | 每 4 个 token 压缩成 1 个，然后 top-k 选择 | stage-1 ring + stage-2 all-gather |
| HCA（Hierarchical Compressor Attention） | 每 128 个 token 压缩成 1 个，全局 attend | 同上（compress ratio 不同） |

这三种模式在同一个 forward 里交替出现，每种都有自己的 CP 通信模式。实现代码在 `cp.py`，两个核心 autograd function：

**`_SendLastAndPrepend`** — forward 阶段把尾部 m 个 token 发给下一个 rank，**在 Function 内部**拼到头部（caller 拿到的 output 就是拼好的，不需要手动 cat）；backward 阶段拆开 grad 反向传。用于 SWA ring 和 compressor stage-1：

```text
class _SendLastAndPrepend(Function):
    @staticmethod
    def forward(ctx, x, k, cp_group, seq_dim):
        # isend x[..., -k:, ...] → next rank
        # irecv prefix         ← prev rank
        # rank 0: return x; rank > 0: return cat([prefix, x])
        ...

    @staticmethod
    def backward(ctx, grad_out):
        # rank > 0: split grad_out → grad_prefix[:k] + grad_local[k:]
        #           isend grad_prefix → prev rank (它需要 last-k 的梯度)
        # rank < last: irecv grad_recv ← next rank, add to grad_local[-k:]
        ...
```

一个小但关键的细节：P2P 通信必须用 `group_peer=` 而不是 `peer=`——后者期望全局 rank，而我们只有 group-local 的 cp_rank±1。

**`_AllGatherSeq`** — forward all-gather + cat，backward reduce-scatter。用于 compressor stage-2。

这两个原语被包装成三个用户层 API：`swa_ring_kv`（SWA 边界 KV 交换）、`compressor_cp_ring`（compressor stage-1）和 `compressor_cp_ag`（compressor stage-2 去重 + all-gather）。

一个精妙的设计点：compressor 的压缩率 m（CSA m=4，HCA m’=128）意味着 **stage-2 all-gather 的通信量与序列长度无关**——你只需要收集 `S/(m × cp_size)` 个压缩 token，而不是 S 个原始 token。这是 DeepSeek 论文 §3.4.3 设计的核心优势。

> UPDATE：此处 AI summary 错误，stage 2 all-gather 的通信量与序列长度有关，感谢评论区 Victarry 指出。

### Attention 中的集成

在 `modeling_deepseek_v4.py` 的 `DeepseekV4Attention.forward` 里，CP 是一个 `cp_active` 分支——不开 CP 时走 upstream-equivalent 的 vanilla 路径（与 transformers 完全一致），开 CP 时在中间插入通信原语：

```text
cp_active = self.cp_group is not None and self.cp_size > 1

if not use_general_path:
    # ----- vanilla path (upstream-equivalent) -----
    if self.compressor is not None:
        compressed_kv, block_bias = self.compressor(hidden_states, q_residual, ...)
        kv = torch.cat([kv, compressed_kv], dim=2)
else:
    # ----- general path (CP and/or pack-seq, paper §3.4.3) -----
    kv = swa_ring_kv(kv, cp_group, self.sliding_window)          # SWA ring
    swa_prefix_len = kv.shape[2] - s_local

    if self.compressor is not None:
        hs_with_prefix, n_prefix = compressor_cp_ring(hidden_states, m, cp_group)  # stage-1
        compressed_kv_full, block_bias = self.compressor(       # stage-2 内聚在 compressor 里
            hs_with_prefix, q_residual, position_ids,
            start_position=cp_rank * s_local - n_prefix,
            cp_group=cp_group,
            n_prefix_windows=n_prefix // m,
            n_local_windows=s_local // m,
        )
        kv = torch.cat([kv, compressed_kv_full], dim=2)

    attention_mask = build_cp_causal_mask(s_local, cp_rank, swa_prefix_len, ...)
```

HCA 和 CSA 两种 compressor 都走同一个调用模式——stage-2 + block_bias 构建被内聚到各自的 `forward` 里，attention 端只需一次调用。这个设计经历了三个版本的重构才收敛。

### 4. 三层并行如何协同

### 两个独立 mesh

最终方案用**两个完全独立的 mesh**，都横跨全部 GPU：

```text
# EP + FSDP mesh
ep_2d_mesh = init_device_mesh("cuda",
    (world_size // ep_size, ep_size),
    mesh_dim_names=("ep_fsdp", "ep"))

# CP mesh
cp_full = init_device_mesh("cuda",
    (world_size // cp_size, cp_size),
    mesh_dim_names=("dp", "cp"))
cp_mesh = cp_full["cp"]
```

这个设计是多次返工后的结果。早期尝试过 3D mesh `(ep_fsdp, cp, ep)`：

```text
早期 3D mesh（已废弃）：
  world_size=32, ep=8, cp=2
  → ep_fsdp_size = 32/(8×2) = 2   ← 只有 2 张卡做 FSDP 分片！
  → 硬件效率减半
```

3D mesh 的问题是 CP 维度会**挤压** FSDP 维度，导致参数分片不充分。改成两个独立 mesh 后：

```text
两个独立 mesh：
  ep_2d = (32/8, 8) = (4, 8)    ← 4 张卡做 FSDP 分片
  cp    = (32/2, 2) = (16, 2)   ← CP 完全不影响 FSDP
  → FSDP divide factor = world_size = 32，与不开 CP 完全一致
```

### 梯度缩放

三层并行后，`loss.backward()` 产生的梯度在 FSDP reduce-scatter 时会被除以 `world_size`。但开了 CP 后，每个 rank 只看到 `S/cp_size` 个 token，产生的梯度本来就只覆盖部分序列。这导致梯度被多除了 `cp_size` 倍。

最初的修复方案是 `loss *= cp_size`——简单粗暴，数学正确。但后来发现 PyTorch FSDP2 有一个更优雅的原生 API。这段代码直接来自 `ef="https://github.com/Tencent/Wechat-YATT/blob/public/gpatch_v4/models/deepseek_v4/hp.py">hp.py 的 apply_hp 函数：`

```text
cp_size = cp_mesh.size() if cp_mesh is not None else 1
grad_divide_factor = world_size // cp_size

for layer in layers:
    fully_shard(layer.mlp.experts, mesh=ep_fsdp_mesh, mp_policy=mp_policy)
    layer.mlp.experts.set_gradient_divide_factor(grad_divide_factor)
    fully_shard(layer, mp_policy=mp_policy)
    layer.set_gradient_divide_factor(grad_divide_factor)
fully_shard(model, mp_policy=mp_policy)
model.set_gradient_divide_factor(grad_divide_factor)
```

`重要细节：set_gradient_divide_factor 不递归——你必须对每个 FSDP wrap 点单独调用。漏一个，那个模块的梯度就会偏一个整数倍，但不会报任何错误。这种 bug 在数值上表现为”精度差了一点”，极难定位。`

### `5. 实践细节`

### `5.1 加载 88 分钟 → 200 秒`

`原始的 checkpoint 加载方式：rank 0 用 HuggingFace from_pretrained 把完整模型加载到 CPU，然后 broadcast 给所有 rank。`

`问题：`

1. `rank 0 需要 ~40 GiB CPU 内存持有完整 bf16 模型`
2. `其余 N-1 个 rank 都在等 broadcast，纯空转`
3. `全 43 层加载耗时 88 分钟`

`我们的改造经历了 4 个版本：`

| 版本 | 方案 | 43L 耗时 | 问题 |
| --- | --- | --- | --- |
| v1 | broadcast loop | ~88 min | 串行，只有 1 rank 干活 |
| v2 | wave + allreduce | — | size cap 导致大 expert 独占 wave，退化成串行 |
| v3 | 去掉 size cap，sort by size desc | 420s | GPU buf 按 max numel 申请，大模型会 OOM |
| v4 | 固定 chunk buf + 分块 allreduce | 200s | 12.9 倍加速 |

`v4 的核心思路：`

1. `把所有参数按大小降序排列，每 world_size 个为一个 wave`
2. `Wave 内每个 rank “认领”一个参数，各自做 CPU 上的 convert（FP8/FP4 反量化）`
3. `固定 16 GiB 的 GPU buffer，分块 allreduce——即使单个参数 > 16 GiB（比如 DSV4-Pro 的 gate_up_proj 67.5 GiB），也只需多做几次 allreduce`
4. `每个 rank 只拷贝自己 EP+FSDP 分片范围内的数据`

### `5.2 隐形 Bug：_chunk_with_empty`

`这个 bug 值得单独讲。`

`并行 load 跑通所有测试后（bit-equal PASS），我们信心满满地部署到 128 GPU 的生产环境。结果——`

```text
RuntimeError: output with shape [k] doesn't match the broadcast shape [0]
```

`崩在 optimizer.step() 里。`

`根因是 FSDP2 的一个实现细节：当参数的第一个维度 d0 < world_size 时（比如 attn_sink 的 shape 是 (128,)，而 world_size = 128），FSDP2 用 torch.chunk + new_empty(0) 分片——多出来的 rank 拿到一个 shape 为 (0,) 的空张量。`

`我们的 load 代码用 ceil(d0 / world_size) 给每个 rank 分配 shape (1,) 的 padding-zero 张量。在 torch.equal 全局视角下看不出区别（full_tensor() 会按 target.shape 截断 padding），但到了 optimizer.step()，FSDP 的 grad 是 (0,) 而参数是 (1,)，broadcast 炸了。`

`bit-equal 测不出的 bug。只在 production 规模（world_size=128）的特定 small parameter 上触发。`

`教训：分布式系统的正确性边界不在 torch.equal，在框架内部的 layout contract。`

### `5.3 测试的”公平性”陷阱`

`我们的测试用 baseline（纯 FSDP）和 EP+CP 两种配置做数值对比。一个隐蔽的错误是：`

```text
# 旧代码
global_n = (full_labels != -100).sum()
dist.all_reduce(global_n)
loss = CE_sum / global_n
```

`baseline 16 卡：global_n = 16 × S。EP+CP 32 卡：global_n = 32 × S。两边除数不同，loss 差了 cp_size 倍。`

`而且这个 bug 因为 baseline 和 EP+CP 都”错了相同的方向”，数值碰巧”对得上”。直到我们改了测试配置（baseline 16 卡 vs EP+CP 32 卡），差异才暴露：loss = baseline / 2，正好差 cp_size = 2 倍。`

`数值差正好等于某个整数倍，几乎一定是 bug，不是 numerical noise。 这条经验值得裱起来。`

### `6. Checkpoint 保存：从训练到推理的最后一公里`

`训练完了，参数分散在 128 张 GPU 上，怎么收集回来？`

### `保存格式`

`我们支持两种保存格式：`

| 格式 | 大小（43L） | 特点 |
| --- | --- | --- |
| quantized（默认） | ~150 GiB | FP4 packed-int8 experts + FP8 e4m3 dense + E8M0 scale，与 pretrained DSV4-Flash 二进制布局一致 |
| bf16 | ~530 GiB | 全部折叠到 bf16，strip quantization_config |

`quantized 格式保存的 checkpoint 可以直接被 HuggingFace 的 from_pretrained 加载——不需要任何自有的反序列化逻辑。这是 checkpoint 兼容性的终极目标。`

### `Wave-based 并行保存`

`保存也经历了类似的并行化：`

1. `每个 wave 包含 world_size 个参数`
2. `Phase A：全 rank all-gather 收集完整参数到 owner rank 的 CPU`
3. `Phase B：各 owner 并行做 CPU 上的 split + cast + 写盘`

`43 层保存耗时约 5 分钟（其中 88% 是 gather 通信时间）。`

### `FP4/FP8 量化的 round-trip`

`DeepSeek-V4-Flash 的 checkpoint 里存了三种量化格式：`

- `Expert 权重：FP4（E2M1，32-element block，scale 用 E8M0）`
- `Dense attention 权重：FP8（E4M3，128×128 block，scale 也是 E8M0）`
- `少数权重：BF16 或 FP32（norm, bias, sink 等）`

`保存时需要把训练中的 fp32/bf16 master 参数重新量化回这些格式。量化器实现在 fp_quantize.py，checkpoint 保存/加载的完整逻辑在 checkpoint.py。我们的量化器与 OpenAI 的 triton-kernels OCP MXFP8 reference 做了 byte-exact 对比——33792 个 FP4 tensor 全部 bit-identical。`

`一个有趣的发现：我们的 FP8 量化与 DSV4-Flash 磁盘上的 FP8 权重数值等价但不是 byte-exact——它们的 scale 差了恰好 2 倍。我们倾尽全力也没法复现这个 2×（论文没公开 dense weight 的量化公式），最终接受了这个差异并写了详尽的 oracle 测试来证明数值等价性。`
