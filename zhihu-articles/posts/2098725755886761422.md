## 一、摘要

流水线并行（Pipeline Parallelism，PP），是大模型推理的层切分并行策略：**把 Transformer 模型的所有层沿纵向切分成多个 stage，每个 stage 部署在一张 NPU 卡上**；模型第 0~N 层放卡 0，N+1~M 层放卡 1，以此类推。输入数据以**微批次（micro batch）** 的形式像流水线一样依次流过各个 stage，实现多组请求的时间重叠，提升吞吐。

基线环境：MindSpore 2.3+，MindSpore‑Transformers，昇腾 910B 集群，CANN8.0；LLM：Llama2、Qwen 等大模型；区别于张量并行 TP（单层内部切分）、数据并行 DP（多副本处理不同样本）。

### PP 核心机制

1. **模型纵向切分**：将 Transformer 的 decoder 层集合划分到不同 NPU 设备；每个设备只持有自己负责的 layer 权重，单卡显存占用显著下降。
2. **流水线微批次调度**：将推理请求拆成多个 micro‑batch。当 stage0 处理完第一个微批次，将中间激活张量发送给 stage1；stage0 立刻接收第二个微批次，形成流水线重叠，隐藏设备间通信延迟。
3. **两种调度模式**<br>

1. **跨设备通信**：相邻 stage 之间通过 HCCL 发送 / 接收 hidden_states 中间特征；只在 stage 边界通信，相比 TP，通信量更小，适合超大模型跨卡分层部署。

### PP、TP、DP 推理适用场景对比

- **PP 流水线并行**：纵向切层；降低单卡权重显存；适合**模型规模 > 单卡显存**，多卡分层部署；吞吐高，存在流水线气泡。
- **TP 张量并行**：单层矩阵横向切分；单步推理多卡协同计算；适合单步推理时延优先，通信密集。
- **DP 数据并行**：多份完整模型副本；每个副本处理不同请求；提升吞吐，不能解决单卡权重放不下的问题。

工程常用组合：**PP+TP 混合并行**。例如 4 卡：PP 切为 2 个 stage，每个 stage 内部 2 卡 TP。兼顾显存降低与推理吞吐。

## 三、模型 PP 切分配置（MindSpore-Transformers）

MindSpore-Transformers 的`PipelineParallelConfig`用来配置流水线并行，指定 stage 数量和每层归属。

```text
# pp_config.py
from mindspore_transformers import PipelineParallelConfig, AutoModel, AutoTokenizer

# 流水线并行配置：2-stage PP，模型共32层，0~15层stage0；16~31层stage1
pp_config = PipelineParallelConfig(
    num_stages=2,
    stage_layer_map={
        0: list(range(0,16)),
        1: list(range(16,32))
    },
    micro_batch_size=4,  # 微批次大小，控制流水线气泡
    parallel_mode="pipeline"
)

# 加载模型，注入流水线并行配置
model = AutoModel.from_pretrained(
    "./llama2-7b",
    parallel_config=pp_config,
    ms_dtype="float16"
)
tokenizer = AutoTokenizer.from_pretrained("./llama2-7b")
```

## 四、PP 推理主脚本

```text
# llm_pp_infer.py
import mindspore as ms
from mindspore_transformers import AutoModel, AutoTokenizer, PipelineParallelConfig

ms.set_context(device_target="Ascend", mode=ms.GRAPH_MODE)
rank_id = ms.communication.get_rank()

# PP并行配置
pp_config = PipelineParallelConfig(
    num_stages=2,
    stage_layer_map={0:list(range(0,16)),1:list(range(16,32))},
    micro_batch_size=4
)

model = AutoModel.from_pretrained("./llama2-7b", parallel_config=pp_config)
tokenizer = AutoTokenizer.from_pretrained("./llama2-7b")

def infer(prompts):
    inputs = tokenizer(prompts, return_tensors="ms", padding=True)
    output = model.generate(
        **inputs,
        max_new_tokens=128,
        do_sample=False
    )
    return tokenizer.batch_decode(output, skip_special_tokens=True)

if rank_id == 0:
    res = infer(["Hello, introduce openEuler","What is iSula?"])
    for r in res:
        print(r)
```

## 五、msrun 启动多卡流水线推理

```text
#!/bin/bash
```

注意：PP 的`num_stages`必须等于 msrun 的 worker 数量；每个 worker 对应一个流水线 stage。

## 六、性能评估脚本：吞吐、气泡占比统计

```text
# pp_eval_metric.py
import time
import numpy as np

def pp_benchmark(model, tokenizer, prompt_list, micro_bs=4):
    start = time.time()
    output = model.generate(**tokenizer(prompt_list,return_tensors="ms"),max_new_tokens=128)
    cost = time.time()-start
    total_tokens = sum(len(o) for o in output)
    throughput = total_tokens / cost
    # 流水线气泡粗略估算
    bubble_ratio = 1.0 / micro_bs
    print(f"推理耗时:{cost:.2f}s, token吞吐:{throughput:.2f} token/s, bubble_ratio:{bubble_ratio:.2f}")
    return throughput
```

核心观测指标：

1. Token 吞吐（PP 最核心收益指标）；
2. 单请求首 token 时延；
3. 流水线气泡占比；
4. 各卡显存占用（PP 可以显著均衡降低单卡权重显存）；
5. stage 间 HCCL 通信耗时。

## 七、关键调优参数说明

1. `num_stages`：流水线 stage 数量；stage 越多，单卡权重显存越低，但 stage 间通信增多，气泡开销上升；
2. `micro_batch_size`：微批次大小；micro_batch 越大，气泡占比越低；但会提升激活值显存占用；推理场景一般 2~8；
3. `stage_layer_map`：层切分策略；尽量保证每个 stage 的计算量均衡，避免某一个 stage 成为瓶颈（负载不均衡会大幅降低吞吐）；
4. PP+TP 混合并行：超大模型，每个 stage 内部开启张量并行，进一步分摊单卡显存；
5. 推理开启增量解码（KV Cache）：PP 流水线推理必须开启 KV Cache，否则每步重算，性能极差；MindSpore-Transformers generate 默认开启 KV 缓存。

## 八、常见踩坑总结

1. **stage 层负载不均衡** 某一个 stage 层数量多 / 计算量大，流水线被最慢的 stage 卡住。必须均分 decoder 层，保证各 stage 计算量接近。
2. **micro_batch 太小，流水线气泡过大** micro_batch=1 时气泡接近 50%，大量 NPU 空闲，吞吐很低；推理尽量调大 micro_batch。
3. **worker 数量与 num_stages 不匹配** msrun 启动 worker 数目必须等于流水线 stage 数量，否则 HCCL 初始化失败，通信报错。
4. **PP 推理 KV Cache 跨 stage 传递开销** KV cache 在 stage 边界跟随 hidden_states 传递；长序列场景通信量上升，可开启 KV cache 本地缓存优化。
5. **混淆 PP 训练与 PP 推理** 训练 PP 是 1F1B 调度；推理 PP 只有前向，调度逻辑简化；不要复用训练 PP 配置直接推理。
6. **单请求时延上升** PP 适合高吞吐离线推理场景；不适合低延迟单请求在线服务，多 stage 叠加通信会增加首 token 时延。

## 九、并行方案对比

| 并行方式 | 显存收益 | 推理吞吐 | 首 token 时延 | 通信特点 | 适用场景 |
| --- | --- | --- | --- | --- | --- |
| PP 流水线并行 | 高，分层存放权重 | 高（微批流水线） | 偏高 | 仅 stage 边界通信 | 超大模型离线批量推理，显存受限场景 |
| TP 张量并行 | 中，单层权重切分 | 中等 | 低 | 每一步推理都要集合通信 | 低时延在线推理 |
| DP 数据并行 | 无，模型多副本 | 高 | 低 | 仅请求分发 | 模型能单卡放下，提升吞吐 |
| PP+TP 混合并行 | 最高 | 较高 | 中等 | stage 间点对点 + stage 内集合通信 | 超大规模 LLM，多卡集群推理 |

## 十、最佳实践总结

1. 当模型权重无法放入单张昇腾 NPU 显存时，优先考虑 PP 流水线并行；追求极致吞吐，可 PP+TP 混合并行；
2. 切分 stage 时，均衡分配 Transformer 层，保证各 stage 计算负载均衡；
3. 合理设置 micro_batch_size，权衡流水线气泡开销与激活显存；
4. PP 适合**批量离线推理**；面向低延迟在线服务场景优先 TP；
5. 性能验证：分别观测单卡显存占用、token 吞吐、stage 间 HCCL 通信耗时，定位瓶颈。
