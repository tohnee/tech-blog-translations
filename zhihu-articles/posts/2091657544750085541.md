## 前言

笔者出于对深度学习模型运行部署推理的兴趣，最近开始阅读 nano-vllm 项目的代码实现。这个项目主要实现了块表(block table)和调度器以便更好地管理设备的 KV cache；但在阅读过程中，也发现了项目中使用的张量并行(Tensor Parallelism, 后文中简称TP)也非常有趣。但苦于没有相关教程，笔者在直接阅读 TP 实现的相关代码过程一直分心走神，社区中的一些教程又没有足够深入去探讨一些细节问题。所以我决定还是自己写一篇通俗易懂的博客，通过多个图表来阐述 TP 的底层原理。希望像我这样对TP特别感兴趣的菜鸟，也能够更快入门核心概念。

TP 的核心在于将 LLM 庞大的权重矩阵"拆分(split)"、"切割(cut)"成多个"片段(piece)"、"分片(shard)"，并将这些权重分片，均匀存储在单台或多台机器的多个设备(device)上。这么做是基于一个很现实的考量，最近 LLM 参数规模出现了爆炸式增长，但是每个计算设备中 HBM2 内存容量的增长速度却要慢得多，因此LLM 庞大的权重参数无法容纳在单个设备内存(device memory)中。此外，考虑到训练时的梯度张量以及推理时的 KV 缓存也要占据大量设备内存，工程师们不得不将权重矩阵分散存储在多个设备上，以确保 LLM 能够正常运行。

从表面上看，TP 只是实现了分布式的权重存储，但是深处来看，TP还构建了一套分布式计算方案。这就引出了两个核心问题：1) LLM有很多计算模块，它们的权重究竟是怎么切割拆分的？ 2) 计算过程中，运算又是怎么拆解到各个设备上的？这两个问题其实密切相关，因为只有采用了合适的权重切割策略，分布式计算才能以一种合理的方式顺利运行，并在计算过程中尽可能避免昂贵的跨设备数据通信。

为了解答这些问题，并帮助大家更好地阅读这篇博客，读者需要非常熟悉 MHA、GQA 、SwiGLU 和 RMSNorm 的运算机制，并对 LLM 的整体布局和结构有一个基本的认识。如果你觉得已经准备好了，那我们就开始吧！本博客主要探讨推理中用到的 TP，不涉及训练中的 TP。全文将以 Qwen3-0.6B 为例(与 nano-vllm 相同)进行阐述。

## 1. 两种权重切割策略

在详细了解模型的切割策略前，我们先简单回顾下权重矩阵的基础概念。权重矩阵专为线性计算中的矩阵乘法而生，在推理阶段，它们是矩阵运算中学习完毕、固化的权重参数。而那些动态输入到权重矩阵，等待被计算的数据，则被称为激活张量。

![](https://pic2.zhimg.com/v2-9576fbdeebf6c5a1c4b3182548712043_r.jpg)
*这是一个权重矩阵*

权重矩阵的输入维度决定了输入的特征数量，而输出维度则确定了输出的特征数量。权重矩阵的每一个列向量都可以被视为一个神经元；因此，输出的特征数量也就是权重矩阵的神经元数量。为了计算单个输出特征，每个列神经元都必须接收一个大小与输入特征数量相匹配的激活张量。

### 1.1 对权重矩阵按列切分(输出特征维度切分)

![](https://pic2.zhimg.com/v2-9180921f770fb590519c439c5cc12ac3_r.jpg)
*column-cut 权重矩阵*

正如这节标题所示，我们只需沿输出维度均匀地切割原始权重矩阵，并将每个权重分片(shard)存储到单独的计算设备中。如上图所示，假设共有`n`个计算设备，整个权重矩阵 `W` 切割后变成了大小相同的 `W1, W2, ..., Wn`。可将其记为`[W1, W2, ..., Wn] = split(W, dim=1)`。图片中的颜色表示此权重或激活张量位于同一个设备上。

![](https://pic4.zhimg.com/v2-153afc8cdbe853e94939d8f5cd188ecf_r.jpg)
*column parallel 计算*

接下来让我们再看看这种情况下分布式计算是如何实现的。如上图所示，假设有一个激活向量`V`，原始的矩阵运算 `V @ W` 转化为多个独立的矩阵运算 `V @ W1, V @ W2, ..., V @ Wn`。由于每个权重切片都存储在独立的设备中，所以每个设备只需完成自己切片部分的矩阵运算。上图也可以表示为：`V @ W = O` -> `V @ W1 = O1, V @ W2 = O2, ..., V @ Wn = On` ；`concat([O1, O2, ..., On], dim=1) = O`。

看起来还挺简单的，对吧？但为了获得原始完整输出 `V @ W`，必须满足两个条件：1)每个设备共享完全相同的输入张量 V；2)每个分片输出必须跨设备进行拼接，这显然会导致跨设备间的数据通信开销。

这种将权重和计算沿列维度进行切割的做法被称为**列并行**(column parallel)。

事实上，我们也可以反过来操作，将离散的多个权重矩阵按列拼接，合并为一个整体，记为`W = concat(W1, W2, ..., Wn, dim=1)`。这样的话，计算就变为：`V @ W1 = O1, V @ W2 = O2, ..., V @ Wn = On` -> `V @ W = O` ；`O1, O2, ..., On = Split(O, dim=1)`。多个独立的矩阵运算合并，变成一个大矩阵乘法操作。同样地，在权重矩阵被拼接之前，每个小的矩阵运算必须共享完全相同的输入激活 `X`。

### 1.2 对权重矩阵按列切分(输入特征维度切分)

![](https://pic3.zhimg.com/v2-c6ebd11d9e25071f60dabc1bff925ffa_r.jpg)
*row-cut 权重矩阵*

这次我们沿着输入维度均匀地切割权重矩阵，并将每个权重分片(shard)存储在单个设备中。假设共有`n`个计算设备，可将其记为 `[W1, W2, ..., Wn] = split(W, dim=0)`。

![](https://pica.zhimg.com/v2-dee41eda067559bfd1b3955a9feafd56_r.jpg)
*row-parallel 计算*

与列并行相比，上图的计算过程看起来复杂一点。假设有一个激活矩阵`X`，原始的矩阵运算 `X @ W` 被分解为零散的矩阵运算 `X1 @ W1, X2 @ W2, ..., Xn@ Wn`，每个矩阵运算都将在单独的设备上同时进行，从而实现了分布式计算。上图也可以表示为 `X @ W = O` -> `X1@W1 + X2@W2 + ... + Xn@On = O`。

为了获得原始完整输出`X @ W`，这次需要遵循一些不同的规则：1) 每个设备只需要输入激活张量的一部分，而不必像列并行那样完整的输入张量；2) 每个设备上矩阵运算的输出大小与原始输出相同，并且它们是相加(element-wise add)，而不是进行拼接；3) 这里同样需要跨设备的数据通信，但模式似乎有所不同，我们将在后面的章节中详细讨论。

**但或许行切(row-cut)方法最独特的地方在于，它不仅按行切割权重矩阵，还按列切割了输入张量，从而同时产生了一种混合了张量并行(尽管被称为TP，但事实上是权重在进行分布式计算)和输入张量并行的分布式计算模式。**

这种将权重矩阵按行拆分并存储到多个设备中、然后分别进行计算的做法被称为**行并行(row parallel)**。事实上，我们也可以将这种模式视为一种并行的内积计算。

但等等，我们已经有了列切割，为什么还需要这种切割方法呢？按列切割明明更加自然直观，毕竟它拆分了输出神经元，给人一种更直观、更易用的感觉。对于这节讲述的行并行来说，它在计算和数据传输方面并没有比列并行更具优势。那么，我们应该在什么情况、什么场景下优先选择行并行而不是列并行呢？

其实呢，单独使用行并行是很少见的，绝大部分情况下，行并行是搭配列并行才会出现的(此处"我全都要".jpg)。那什么时候会同时出现这两种切割模式呢？答案就是双层MLP。详情请见下一节。

### 1.3 在双层MLP上同时应用两种并行策略

![](https://pic1.zhimg.com/v2-18f5b9ceb9efbb622c52b1755ee9f0a8_r.jpg)
*column-cut切割第一个权重矩阵；row-cut切割第二个*

双层 MLP 中的两个权重矩阵分别记为 `Wup` 和 `Wdown`，其中 `Wup` 按列进行切分，`Wdown` 按行进行切分。为了简化文字说明和绘图，现假设只有两个可用设备，且忽略每层矩阵运算后的激活函数。

![](https://pic4.zhimg.com/v2-227bf51d968a29a3f2db8fed2a2cb28f_r.jpg)
*column parallel和row parallel协同计算*

再看看这里的分布式计算是如何实现的。假设有一个激活矩阵`X`，原本的 MLP 矩阵乘法 `X @ Wup @ Wdown` 将被拆分为两部分独立的计算：`X @ Wup1 @ Wdown1` 和 `X @ Wup2 @ Wdown2`，每一部分都在各自的设备上计算运行。上图也可以表示为 `X @ Wup @ Wdown = O` -> `X @ Wup1 = V1, X @ Wup2 = V2` ；`V1 @ Wdown1 + V2 @ Wdown2 = O`。为了得到原始输出，必须进行跨设备数据传输完成最后的逐元素相加操作。

So far so good，但是不是有什么重要的内容遗漏掉了？第一次并行矩阵乘法(即列并行 `X @ Wup1` 和 `X @ Wup2`)之后的数据同步消失了，从而节省了大量的数据传输成本。**唯一的数据同步仅发生在第二次并行矩阵乘法之后**(即行并行 `V1 @ Wdown1` 和 `V2 @ Wdown2`)。为啥能这么搞？这是因为，对于每一个设备而言，第一次运算列并行的输出分片，正是第二次运算行并行输入所需要的。还记得按行切分的权重只需要原始输入张量的一部分吗(因为它同时沿输入特征维度切分权重矩阵、沿列切分输入张量)？

上文看起来有些拗口，但却是精华。正是这少了一次的数据通信，让"先按列切分第一个权重、后按行切分第二个权重"的策略，变得十分流行。

同样的技术也可以应用于单个设备内的多个张量核心(Tensor Core)，此时跨设备的数据传输将变为设备内的通信。单独的列并行和行并行也可以跨张量核心广泛应用。由于本文主要讨论的是跨设备张量并行，因此不深入探讨这方面更底层的细节。

### 1.4 Summary

在这一章中，我们已经了解了这两种切分策略，以及关于 TP的两个核心问题：1)权重如何在各个设备上被切分和存储；2)计算如何在各个设备之间分配，它们的答案也已了然。

但列并行和行并行在实际中又是怎么运行的呢？我们将通过 Qwen3-0.6B 模型来进行讲解演示。 nano-vllm 所使用的Qwen模型权重来自于Hugging Face，我们从这里开始，来看看这些权重是如何拆分到每个设备上的。

## 2. Qwen3原始权重布局

![](https://picx.zhimg.com/v2-0cb028b0228705e1f97587d7f15400af_r.jpg)
*Hugging Face Qwen3-0.6B 权重布局*

Hugging Face 的Qwen3权重布局非常直观：首先是一个庞大的词表嵌入(Embedding)层，接着是多个 decoder block。每个 decoder block 包含注意力头权重、SwiGLU 前馈网络(FFN)权重以及 RMS 归一化权重。Qwen3-0.6B 在词表嵌入和 LLM Head 之间采用了权重绑定(Weight-Tying)，这意味着它们的权重是共享的，我们将在后续章节中对此进行详细探讨。

在每个注意力头的权重块中，输入投影矩阵权重`W_Q`、`W_K`、`W_V` 以及输出矩阵权重`W_O`是分开的。模型采用了GQA机制，使多个Query values共享相同的KV values。需要说明的是，这里的权重只包含这四个矩阵，因为注意力计算部分`softmax(Q@K) @ V.T`本身并不包含任何需要学习的权重。对于每个 SwiGLU 前馈网络，则存储了三个权重矩阵`Wup`, `Wgate`和`Wdown`，其计算公式为 `X = (SiLU(X@Wup) ⊙ (X@Wgate)) @ Wdown`，其中`⊙` 表示逐元素相乘。

![](https://pic2.zhimg.com/v2-9fadadea899d177e864efa624b5cf6cd_r.jpg)
*单个设备上未使用 TP 的 prefill forward 过程*

上图展示了在单个设备上的 prefill 阶段前向传播过程，因而不涉及跨设备的分布式权重存储与计算。此外需留意，每个 decoder block 中均使用了两个 RMS 归一化向量。在进行 MHA 和 SwiGLU FFN 操作之前，激活张量会先被归一化。在完成 MHA 和 SwiGLU FFN 操作之后，还会和未参与归一化运算的张量进行残差相加。

## 3. 权重分布式存储、张量分布式运算

为简化起见，假设仅有两台可用设备来运行模型，输入仅包含一个序列(即 batch size 为 1)，且推理处于 prefill 阶段，后文所有的图表和描述都将基于此设定展开。

下文将按照每个计算模块，展开说明 TP 是如何应用的。

### 3.1 输入嵌入矩阵 (Input embeddings matrix)

![](https://pic2.zhimg.com/v2-4690a232e04c4883db50b6501750f829_r.jpg)
*按行切割输入嵌入矩阵*

输入嵌入矩阵作用于 LLM 的第一道工序，负责把 prompt 的输入token IDs 转换到模型的 hidden space 中。与其说是"转换"，不如说它更像是一个字典查找操作。这个矩阵本质上就是一个巨大的字典，记录了每一个 token ID 在大模型隐藏空间中的向量表示。

在上图中，词表嵌入矩阵沿行维度被等分为两半，分别存储在两台设备上。与隐藏维度相比，词表大小通常非常巨大。具体到 Qwen3-0.6B，其词表大小高达 151,936，而模型的隐藏空间维度仅为 1,024。

事实上，PyTorch 中的查找操作 `nn.Embedding()` 具有 `O(1)` 的时间复杂度，因此将嵌入矩阵的词表大小减半并不能带来任何速度上的提升。相反，跨设备的数据传输甚至还会引入额外的延迟。不过，考虑到拆分庞大的嵌入矩阵后，可为 KV Cache 腾出宝贵的设备内存，因此在 `nano-vllm`的张量并行设计中还是对其进行了拆分存储。不过，这里所采用的 TP 纯粹是出于内存考量，它并非我们之前讨论过的标准 TP，因为其中完全不涉及分布式矩阵乘法运算。

关于这项查找操作是如何分布到各个设备上，各个设备又是如何恢复原始查找操作结果的，此处不再赘述，感兴趣的读者可以查阅官方仓库的[这里](https://github.com/GeeeekExplorer/nano-vllm/blob/main/nanovllm/layers/embed_head.py#L34)来理解相关实现。

还有一点需要留心的是，在张量并行中，嵌入矩阵被跨设备分布式存储，因此输入到各个设备的相同 sequence 在查找对应 embeddings 时，搜索空间会相应缩小。如果每个设备拥有完整的嵌入矩阵，被拆分的是输入sequence，从而实现了分布式查找运算，这种机制就不再是张量并行了，而是被称为序列并行(sequence parallelism， 简称SP)。

### 3.2 MHA权重矩阵 (MHA block weight matrices)

![](https://picx.zhimg.com/v2-d0aaa7670421e789b3a758acf0ff53f3_r.jpg)
*按行切分输入投影矩阵；按列切分使出投影矩阵*

假设总共只有 4 个注意力头 (Qwen3-0.6B有16个头)，且在 GQA 配置下，每两个 Q 激活张量共享同一个 KV 张量。QKV 输入投影矩阵 `W_Q`、`W_K` 和 `W_V` 沿列方向(column-cut)被拆分为两半，而输出矩阵`W_O`则沿行方向(row-cut)拆分，同样得到两块大小完全相同的矩阵块。这和我们之前见过的，TP在双层 MLP上的应用保持一致："在第一层权重上用列切分，第二层权重则用行切分"。

接着，这些被切割的输入权重块会在每个设备上重新拼接(re-concatenated)。可将上图的拼接过程表示为：`W_QKV1 = concat(W_Q12, W_K1, W_V1, dim=1), W_QKV2 = concat(W_Q34, W_K2, W_V2, dim=1)`。还记得我们之前讨论过的按列进行权重拼接吗？这项技术在这里得到了应用。

但是呢，毕竟 MHA 的计算要比双层 MLP 复杂得多，到底凭什么，双层MLP的分割模式也能在这里运用自如？第一个原因是，从宏观角度来看，MHA 遵循了与两层 MLP 相同的计算模式：输入张量被`W_QKV`投影到隐藏空间，然后又被`W_O`投影回原始空间，不同之处是这里的隐藏空间中加入了额外的 attention 算子，并且隐藏空间中包含了三个投影张量(Q、K 和 V)而不仅仅是一个。下面的计算图中也清晰地展示了这一点。这张图里，FlashAttention 被简化为一个函数调用，且没有绘制 KV 缓存，但这对于理解 MHA 里的 TP 没有任何影响。

![](https://picx.zhimg.com/v2-e1ced6dca91c3a7ff5c65df846dc20bd_r.jpg)
*MHA中的TP计算；各个设备中的计算互不干扰；CTP和RTP分别是列并行和行并行的缩写*

至于第二个原因，则在于 attention 计算是严格限制在各自的 attention head 内部进行的，这为切分输入投影矩阵提供了一种天然的"头切分(head-cut)"方式。如果 attention 计算依赖其自身头以外的输入，那么这种切分(进而包括张量并行)就无从谈起。在上图中的 GQA 和 TP 配置下，每个设备计算两个头的 attention 输出，加起来正好等于原本四个头的计算总量。

当每个设备完成其分片矩阵运算和 attention 计算工作后，如何恢复出原始 MHA 算子运算结果呢，数据通信又是如何运作的呢？这些过程在上图中并未体现。

接下来，让我们详细剖析在前一章"切割策略"中未展开来讲的数据通信模式。棘手的地方在于，这里并没有直接将各个设备的输出 `O1,2` 和 `O3,4`互相传输给对方，随后在每个设备上执行重复的相加 `O1,2 + O3,4`，而是采用了一种更复杂的方案，如下图所示。

![](https://picx.zhimg.com/v2-07a7af4400025e1ae7b472692277281b_r.jpg)
*TP计算后的 all_reduce数据通*

此方案中，每个设备需要进行两次数据传输、一次元素相加操作和一次拼接。

在第一次数据传输中，通过共享的环形总线(ring bus)，每台设备上分布式运算结果的一半(即`O1,2D` 与 `O3,4U`)会被传输至另一台设备，且每个设备将承担一半的矩阵相加计算。因为所有的计算工作(此处为矩阵相加)被均匀地分布到了各个可用设备上，这种"传输与相加"的组合被称为 **reduce_scatter**。

在第二轮传输中，各设备的相加结果(`O_U` 与 `O_D`)会进行互换，从而确保每个设备都收集到一份最终结果的完整拷贝。这也是为什么第二次传输被命名为 **all_gather**。

最后的步骤是每台设各自将这些结果拼接成一个完整的激活张量`O`，这与最初的 `O1,2 + O3,4` 结果完全一致。

所有这些通信和计算操作被 PyTorch 在 `distributed` 包中整合为一个 `all_reduce()` 函数。当设备数量大于两台时，数据传输会更加复杂，这篇博客里对此不再深入探讨，不过"环形总线(ring bus)"这个名字应该能为读者提供一些直观的线索。

其实这个通信过程也可以视作是一次分布式加法计算。

尽管在 MHA 占据主导的是 TP，但在最后分布式加法计算中，仅对激活张量进行了拆分，我们也因此感受到了序列并行(SP)的影子。

### 3.3 SwiGLU权重矩阵 (SwiGLU block weight matrices)

![](https://pic1.zhimg.com/v2-3bd23e60aecc53b8872abbbe9adcd218_r.jpg)
*按行切分up和gate矩阵；按列切分down矩阵*

SwiGLU 的权重拆分策略也与双层 MLP 完全相同。`Wup`, `Wgate`权重矩阵按列切分(就像 MLP 的第一层)，而`Wdown`权重矩阵则按行拆分(与 MLP 的第二层相同)。

为什么这里可以应用相同的拆分策略呢？原因依旧在于，单个分片内部的 SwiGLU 操作不涉及来自其他分片的输入，这一特性与 MHA里 attention 算子所具备的属性如出一辙。唯一的区别在于，MHA 只能按固定大小的 attention head 进行拆分，而 SwiGLU 可以沿列维度以任意分片大小进行拆分(当然实际操作中，都是将维度大小除以可用设备数量得到的)。下图清晰显示了互不干扰这一点。

![](https://picx.zhimg.com/v2-6c0bfdde949fbbfcc4a44dee387c468b_r.jpg)
*SwiGLU 中的TP计算；各个设备中的计算互不干扰*

在每个设备完成其分布式计算并输出 `O1` 和 `O2` 之后，与 MHA 中相同的 `all_reduce()` 操作也会被调用。这确保了通信结束后，每个设备都将拥有完全相同的激活张量，以供下一个计算 block 使用。

### 3.4 RMS 归一化向量权重 (RMS Normalization weight vectors)

![](https://pic1.zhimg.com/v2-8d96870a4a5c407cb5df8476f444f07a_r.jpg)
*RMS权重在各个设备上进行完整拷贝*

RMS 归一化权重会在每个设备上进行完整拷贝，这意味着该算子完全不涉及TP。这是因为 RMSNorm 的计算开销极低，相比于张量并行所带来的数据通信成本，在各个设备上分别执行这些冗余计算反而是更明智的选择。

### 3.5 LLM Head block

头部模块(LLM Head )通过一个简单的矩阵乘法`V @ W_lm`，计算 LLM 输出 token 的 hidden representation 与整个词表的相近程度。这其实十分类似于从 `Q @ K.T` 计算点积 attention matrix，不同之处在于此处的矩阵乘法后面没有接 softmax 进行分数归一化。在推理过程中，其输出会直接进入token sampler，避免了不必要的计算。

在实际应用中，`W_lm` 通常与输入嵌入矩阵`W_emb` 绑定，即`W_lm = W_emb.T`。这使得嵌入矩阵和头部模块所累计产生的参数量减半。对于词表很大但模型较小的架构来说，这部分参数往往占了总参数量的很大一部分。例如，在 Qwen3-0.6B 中，嵌入矩阵在总共 0.6B 的参数中就占了 0.16B。如果不采用 weight tying，总参数量将增加约 27%。

我们在"输入嵌入矩阵"章节中已经知道，`W_emb` 是沿行维度进行切分的，而既然 `W_lm` 是`W_emb` 的转置，我们可以认为 `W_lm` 是沿列维度进行切分的。因此，LLM head 只采用了简单的列并行策略。计算过程如下图所示。

![](https://pic4.zhimg.com/v2-eec8201c3606f8258ce09014743de37b_r.jpg)
*LLM Head 中的 CTP 计算*

每个设备使用切片后的嵌入矩阵分片 `Emb1.T` 和 `Emb2.T` 进行矩阵运算。在对这两个分片计算结果进行最终拼接之前，需要进行一次从从设备(图中的 GPU1)到主设备(图中的 GPU0)的单向数据传输。在上图中，`O2` 被传输到了 GPU0。与 PyTorch 的 `all_reduce()` 中第二轮传输所使用的 `all_gather` 不同，这种传输被称为 `gather`，因为计算结果并没有广播，而是仅被收集到某个特定的设备上。

那么，为什么这里一个简单的 `gather` 就足够了呢？为什么其他设备不再需要原始的运算结果了呢？

因为 LLM head 是最后一个矩阵运算模块，后面不会再有任何权重矩阵和TP了。随后的 token sampler 也仅在主设备上执行，而其他设备则处于空置状态。因此，对于 LLM head 而言，我们只需要保证主设备获取完整的运算结果即可。

这里的拼接仅在主设备上完成，区别与之前使用了 TP 的 decoder block 里的重复拼接操作——在之前的所有 decoder block 中，为了后续 block 中可以使用 TP，每个设备必须获取到完整的激活 tensor。

### **3.6 Summary**

在这一章中，我们以 nano-vllm 和 Qwen3-0.6B 模型为例，详细探讨了 TP 的工作原理。从嵌入矩阵(尽管它沿行维度切分并分布存储在各个设备，但是纯粹出于内存考量，因而未带来任何分布式计算速度上的提升)到 MHA 和 SwiGLU 算子(从宏观视角来看可被视为双层 MLP，从而以"先列切分 、后行切分"的模式进行存储和分布式运算，兼具了内存与速度考量)，再到仅使用列并行的 LLM head，TP 的全貌已清晰地展现在我们眼前。

我们将在下一章中把所有这些部分组装到一起，绘制一个完整的 TP 图。虽然RMS 归一化操作没有使用 TP ，但也需要绘制清楚。

## 4. 完整 TP 推理流图

![](https://pica.zhimg.com/v2-d18cb6f08ab250a6af4d220ec31edb56_r.jpg)
*两个设备使用 TP 后 prefill forward 过程*

最终的推理流图如上所示(RoPE未画出)。首先，输入 ID 向量从 host memory 拷贝到设备的 device memory 中。随后，每个设备在其对应的 embedding 分片上进行查找，并触发一次 `all_reduce` 操作，确保了每个设备上，在后面的 decoder block 计算时拥有相同的输入激活张量。

在每个 decoder block 中，TP 的分布式计算在 MHA 和 SwiGLU 中采用相同的"先列并行、后行并行"的计算路径。此外，行并行之后也加入了一次 `all_reduce`，确保两个设备在进行下一步操作前，拥有相同的激活张量。RMSNorm 则在每个设备上进行了冗余计算，使用了完整的权重和激活张量。

在激活张量历经所有 decoder block 计算之后，其最后一行(即 last token’s representation)与 embedding 矩阵转置的一半相乘(此处只采用简单的行并行方式)，输出其相较于一半词表的相近度得分。接着，通过单向的 `gather` 操作将相近度分数汇聚到主设备上。最后，在主设备上运行 sampler 来生成下一个 token。

至此，结束。完结撒花！
