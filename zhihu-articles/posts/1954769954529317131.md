### 前言

SVG2 的核心方法是，通过 kmeans 将相似的 token 聚合并排列在一起，利用聚类的质心来估计需要参与计算的 token；并且将连续的重要的 token 送到 tensor core 里，可以避免不重要的 token 参与计算，从而减少计算上的浪费。具体的算法我就不在这里赘述了，给大家推荐一个写得非常好的介绍 SVG2 的文章：

[[DiT 稀疏] Sparse VideoGen2：用 Kmeans 聚类对Attention tokens 做选择](https://zhuanlan.zhihu.com/p/1926021638207567139)

众所周知，kmeans 是一个比较慢的操作，在 SVG2 我们用上一个 diffusion step 的质心作为下一个 step 的初始化，可以让 kmeans 在 1-2 个 iteration 内收敛。然而，这仍然有不小的提速空间。为此，我们用 triton 开发了一个非常快的 kmeans。借着这个机会，我和大家分享一下 Flash-KMeans 的设计思路和实现方法，以及如何用 Flash Attention 的思路去优化常见的算子。

### KMeans 背景介绍

kmeans 是最常用的聚类算法，目的是将 N 个样本分为 K 类，使得同一个类的样本非常相似，不同类的样本之间差异很大，而差异的大小靠距离衡量。kmeans 一般有**初始化（initialization）**和**迭代（iteration）**两个步骤：初始化是为了确定一开始的质心，一个好的初始化可以加速收敛的速度；迭代是更新质心和样本分类的步骤，让所有样本选择最近的质心并且更新质心。以欧式距离（Euclidean Distance）的 kmeans 为例，有 N 个样本 $X_i$ 和 K 个质心 $C_j$ ，一个 iteration 通常有以下几个步骤：<br><br>1. 计算所有样本和所有质心之间的距离： $D_{i, j} = ||X_i - C_j||_2^2$

2. 将所有样本分类到最近的质心所在的 cluster： $A_i := \text{argmin}_{j} \{D_{i,j}\}$

3. 确认每个 cluster 内拥有的样本（逆映射）： $G_j := \{X_i | A_i = j\}$

4. 根据 cluster 内的样本更新质心： $C_j := \text{average}(G_j)$

对于 SVG2 来说，因为 attention head 的存在，SVG2 的 kmeans 天然是 batch 进行的，因此函数定义如下：

```python3
def _euclid_iter(x, n_clusters):
    """
    Batched KMeans clustering in PyTorch using Euclidean distance.

    Args:
        x: Tensor of shape (B, N, D), batch_size B, N points per batch, D dims.
        n_clusters: Number of clusters.

    Returns:
        cluster_ids: (B, N) LongTensor, cluster assignment for each point.
        centroids: (B, n_clusters, D) final cluster centers.
    """
```

### 快速实现简单 baseline

首先，我们实现一个快速的距离计算（步骤一）和样本分配（步骤二）。在现代 GPU 上，矩阵乘法远比其他操作快很多，利用初中数学我们可以把距离计算转化成矩阵乘法：<br><br> $D_{i, j} = ||X_i - C_j||_2^2 = ||X_i||_2^2 - 2X_i^TC_j + ||C_j||_2^2$

这样我们就可以先独立计算样本和质心的平方，然后再用交叉项来快速计算出距离，这两步只需要5行 torch 代码实现：

```python3
x_sq = (x ** 2).sum(dim=-1)
cent_sq = (centroids ** 2).sum(dim=-1)
cross = torch.einsum('bnd,bkd->bnk', x, centroids)
dist_sq = (x_sq[:,:,None] + cent_sq[:,None,:] - 2.0 * cross).clamp_min_(0.0)
cluster_ids = dist_sq.argmin(dim=-1)
```

然而对于逆映射（步骤三）来说，torch 的代价实在是太大了。我们可以用非常 naive 的算法并用 triton 简单实现一下：对于每个 token，我们都 launch 一个 threadblock，然后用 atomic add 写到 global memory 来实现对 cluster 内的样本求和计数。核心 triton 代码实现如下：<br>

```python3

def _centroid_update_kernel(

    B: tl.constexpr,
    N: tl.constexpr,
    D: tl.constexpr,
    K: tl.constexpr,
):
    """Each program processes 1 point (token) across D dimensions with atomics."""
    pid = tl.program_id(axis=0)
    token_idx = pid  # range: [0, B * N)

    # ignore index calc, 
    ...

    # Process feature vector in chunks of D
    offs = tl.arange(0, D)
    feats = tl.load(x_ptr + d_start + offs, other=0.0)
    feats = feats.to(tl.float32)

    dest_ptr = sum_ptr + centroid_base + d_start + offs
    tl.atomic_add(dest_ptr, feats)

    # Update counts (only once per point)
    tl.atomic_add(count_ptr + b * K + cluster_idx, 1)

```

本来到这一步，我期望这个 kmeans iteration 能达到一个比较好的性能，结果这个实现在 Wan2.1 上的 setting 上（B=32，N=70k，D=128，K=1000）竟然要 25ms 才能完成一个 iteration！那么究竟是哪里慢了呢？

### Nsight System Profile：快速定位性能瓶颈

我习惯于直接使用 nsys 来定位性能瓶颈，减少思维内耗。下面是 profile 的结果：

![](https://pic2.zhimg.com/v2-b47751c00f907b6170b802ad9fa4998d_r.jpg)
*不难发现，计算交叉项和质心更新速度符合预期，但计算距离和 argmin 竟然占据了大部分时间*

为什么计算交叉项的速度还可以，但是计算 `dist_sq = (x_sq[:,:,None] + cent_sq[:,None,:] - 2.0 * cross).clamp_min_(0.0)` 和 `cluster_ids = dist_sq.argmin(dim=-1)` 花了这么久时间呢？原来在计算交叉项时，我们生成了一个巨大的 intermediate tensor，其大小 `[B, N, K]` 是样本大小的十倍。距离计算中对这个 tensor 的反复读写成为了 kmeans iteration 的性能瓶颈。这个性能瓶颈是可以避免的吗？

回顾一下这个过程，步骤一产生巨大的 intermediate tensor，对其的读写是性能瓶颈；步骤二需要有全局信息（argmin）才能得到结果。这不是 attention 吗！我们直接用 FlashAttention 的思路优化距离计算过程，看看方法是否适用。

### 用 FlashAttention 的思路优化 KMeans 距离计算

FlashAttention 利用 online softmax 来避免生成完整 attention weight，通过不断更新局部结果来得到最终结果。模仿 FlashAttention 的思路，我们可以分块地计算距离，并且维护当前和全局的最小值，这样就可以避免生成完整的 distance tensor。相比于 `softmax`，`argmin` 的局部值维护更新要简单很多，只需要维护 `min` 和 `argmin` 即可。由于 $X_i^2$ 项始终不变，我们可以直接将这个值传入 iteration 函数中，避免重复计算。这个部分可以用一个简单的 triton kernel 实现，通过一定的 pipeline 和 config tuning 我们可以很好地掩盖计算和访存。

```python3
@triton.jit
def _euclid_assign_kernel(
    x_ptr,                 # *f16 / *f32 [B, N, D]
    c_ptr,                 # *f16 / *f32 [B, K, D]
    x_sq_ptr,              # *f32         [B, N]
    out_ptr,               # *i32         [B, N]
    B: tl.constexpr,
    N: tl.constexpr,
    K: tl.constexpr,
    D: tl.constexpr,
    stride_x_b: tl.constexpr,
    stride_x_n: tl.constexpr,
    stride_x_d: tl.constexpr,
    stride_c_b: tl.constexpr,
    stride_c_k: tl.constexpr,
    stride_c_d: tl.constexpr,
    stride_xsq_b: tl.constexpr,
    stride_xsq_n: tl.constexpr,
    stride_out_b: tl.constexpr,
    stride_out_n: tl.constexpr,
    BLOCK_N: tl.constexpr,
    BLOCK_K: tl.constexpr,
):
    """Each program handles a tile of BLOCK_N points for a given batch element.

    The kernel iterates over the centroid dimension K in chunks of BLOCK_K and
    maintains the running minimum distance as well as the corresponding index
    for every point in the tile.
    """
    pid_n = tl.program_id(0)          # tile index along N dimension
    pid_b = tl.program_id(1)          # batch index

    n_start = pid_n * BLOCK_N
    n_offsets = n_start + tl.arange(0, BLOCK_N)
    n_mask = n_offsets < N

    # ------------------------------------------------------------------
    # Load x tile  (BLOCK_N, D)
    # ------------------------------------------------------------------
    offs_d = tl.arange(0, D)
    # Compute pointer for x block: base + b*stride_x_b + n*stride_x_n + d*stride_x_d
    x_ptrs = (
        x_ptr
        + pid_b * stride_x_b
        + n_offsets[:, None] * stride_x_n
        + offs_d[None, :] * stride_x_d
    )
    x_tile = tl.load(x_ptrs, mask=n_mask[:, None], other=0.0)

    # Pre-load x_sq for the tile  (BLOCK_N,)
    xsq_ptrs = x_sq_ptr + pid_b * stride_xsq_b + n_offsets * stride_xsq_n
    x_sq_tile = tl.load(xsq_ptrs, mask=n_mask, other=0.0).to(tl.float32)

    # Init best distance / index
    best_dist = tl.full((BLOCK_N,), 3.4e38, tl.float32)  # large number
    best_idx = tl.zeros((BLOCK_N,), tl.int32)

    # ------------------------------------------------------------------
    # Iterate over centroids in chunks of BLOCK_K
    # ------------------------------------------------------------------
    for k_start in range(0, K, BLOCK_K):
        k_offsets = k_start + tl.arange(0, BLOCK_K)
        k_mask = k_offsets < K

        # Load centroid tile  (D, BLOCK_K)
        c_ptrs = (
            c_ptr
            + pid_b * stride_c_b
            + k_offsets[None, :] * stride_c_k
            + offs_d[:, None] * stride_c_d
        )
        c_tile = tl.load(c_ptrs, mask=k_mask[None, :], other=0.0)

        # Compute centroid squared norms (BLOCK_K,)
        cent_sq = tl.sum(c_tile * c_tile, axis=0).to(tl.float32)

        # Compute cross term (BLOCK_N, BLOCK_K) = x_tile @ c_tile
        cross = tl.dot(x_tile, c_tile).to(tl.float32)  # float32

        # Squared Euclidean distance
        dist = x_sq_tile[:, None] + cent_sq[None, :] - 2.0 * cross
        dist = tl.maximum(dist, 0.0)

        # Mask out invalid centroid columns before reduction
        dist = tl.where(k_mask[None, :], dist, 3.4e38)

        curr_min = tl.min(dist, axis=1)
        curr_idx = tl.argmin(dist, axis=1)

        update = curr_min < best_dist
        best_dist = tl.where(update, curr_min, best_dist)
        best_idx = tl.where(update, k_start + curr_idx, best_idx)

    # ------------------------------------------------------------------
    # Write results
    # ------------------------------------------------------------------
    out_ptrs = out_ptr + pid_b * stride_out_b + n_offsets * stride_out_n
    tl.store(out_ptrs, best_idx, mask=n_mask)
```

利用这个 kernel，我们成功将计算距离和 argmin 从 **23ms** 压缩到 **2.63ms**。此时，质心更新的时间就不可忽略了，我们需要从质心更新中再压榨一点时间出来。

### 利用 argsort 构造逆映射

为什么质心更新非常慢？因为在之前的实现中，我们每个 token 的每个 attention head 都需要进行一次 atomic add，大量的 atomic add 不仅让访存次数大大增多，还引发了互相竞争。一个非常简单的思路是，我们能不能让每个 threadblock 多统计一些 token，在 shared memory 上先算出来部分和，然后再 atomic add 到 global memory 里，这样可以减少访存和竞争？

答案是，直接应用这个方法是不可行的。假设每个 threadblock 处理连续 512 个 token，那么最坏的情况下，每个 token 都属于不同的 cluster，那么 threadblock 要维护 512 个部分和，这显然超过了 shared memory 能承载的上限，并且不会减少访存和竞争。我们假设现在有 32 个 token，一共有 4 个 cluster 和 8 个 thread block，这种情况如下图所示：

![](https://pic2.zhimg.com/v2-b94e56668ab09a22c3e66b0f02fb868d_r.jpg)
*每个颜色对应一种 cluster id，每个 warp 负责 4 个 token*

如图所示，这种情况一共进行了 29 次 atomic add，仅仅减少了三次 atomic add。最坏的情况就是每个 threadblock 要负责 token 的 cluster id 都不同，导致所有的 threadblock 都要进行大量的 atomic add，造成大量访存和竞争。

如果我们能保证同一个 cluster 的 token 都是连续被访问的，那么每个 threadblock 只需要维护非常少的部分和，以及只需要很少的 atomic add 就能得到全局结果。如何让这些 token 被连续访问呢？我们只需要对 cluster id 做 argsort，并且根据 argsort 的结果来读取 token，就能让每个 thread block 访问尽可能少的 cluster 种类，这种情况如下所示：

![](https://picx.zhimg.com/v2-d9609f22f4776a2524a4e7832b99ffef_r.jpg)
*通过对 cluster id 做 argsort，我们可以指定 warp 读取属于相同 cluster 的 token，大大减少 atomic add 的次数*

由于 atomic add 的次数等于 thread block 中出现的 cluster 种类个数，每个 thread block 只需要看负责的第一个 token和最后一个 token 的 cluster id。我们从小到大遍历 cluster id 的种类，分别维护这些部分和并且集中 atomic add 就可以很好地解决问题。示例代码如下：<br>

```python3
@triton.jit
def _centroid_update_chunk_kernel(
    x_ptr,                # *f16 / *f32 [B, N, D] – ORIGINAL ORDER
    sorted_idx_ptr,       # *i32        [B, N]    – indices after sort
    sorted_cluster_ptr,   # *i32        [B, N]    – cluster ids in sorted order
    sum_ptr,              # *f32        [B, K, D]
    count_ptr,            # *i32        [B, K]
    B: tl.constexpr,
    N: tl.constexpr,
    D: tl.constexpr,
    K: tl.constexpr,
    BLOCK_N: tl.constexpr,   # how many tokens (points) each program processes
):
    """Each program processes **BLOCK_N consecutive, already-sorted tokens**.

    Because the tokens are sorted by cluster id, identical ids appear in
    contiguous runs.  We therefore accumulate a local sum/count for the
    current run and perform **a single atomic update per run**, instead of
    per-token.
    """
    # program indices – 2-D launch grid: (chunk_id, batch_id)
    pid_chunk = tl.program_id(axis=0)
    pid_b     = tl.program_id(axis=1)

    b = pid_b
    chunk_start = pid_chunk * BLOCK_N  # position of the first token handled by this program

    # ignore index calc
    ...

    # Load first cluster id to initialise the running accumulator
    first_id = tl.load(cid_batch_base + first_token_idx)
    last_id = tl.load(cid_batch_base + last_token_idx)
    all_ids = tl.load(cid_batch_base + token_idx, mask=valid_tok, other=-1)

    all_tokens_idxs = tl.load(idx_batch_base + token_idx, mask=valid_tok, other=-1) # [BLOCK_N]

    load_mask = all_tokens_idxs[:,None] * D + offs_dim[None,:]

    for cid in range(first_id, last_id + 1):
        cluster_mask = all_ids == cid
        cluster_size = tl.sum(cluster_mask.to(tl.int32))
        if cluster_size != 0:
            cluster_feats = tl.load(x_batch_base + load_mask, mask=cluster_mask[:,None], other=0.0) # [BLOCK_N, D]
            cluster_feats = cluster_feats.to(tl.float32)
            sum_feats = tl.sum(cluster_feats, axis=0)
            dest_ptr = sum_ptr + (b * K + cid) * D + offs_dim
            tl.atomic_add(dest_ptr, sum_feats)
            tl.atomic_add(count_ptr + b * K + cid, cluster_size)
```

经过 argsort 的逆映射，质心更新从原先的 **2.17ms** 变成 **0.94ms**，已经可以满足我们的需要了。
