11 月 13 日，DeepSeek 在 API 文档里挂出一篇公告，核心一句话：App 里那些对话能力，现在 API 里开个参数就有。

以前要在自家产品里做出「DeepSeek 那个味道」，得自己接搜索、自己写文件解析、自己转工具调用的循环、自己拼上下文，最后再糊一层内容审核。每样单拎出来都不算难，但加在一起就是半个月工期。现在这半个月基本可以省掉。

## 四块能力，一套协议

这次没有新模型。模型还是 `deepseek-flash`（DeepSeek-V4.1-Flash-1017），价格也没动：百万 tokens 输入空闲时段 1 元、高峰 2 元，输出空闲 4 元、高峰 8 元。新增的是模型外面那层「应用壳」，对应 App 里你最熟的四种交互。

搜索这一块，请求体里声明 `deepseek_web_search`。非思考模式下，模型自己发起网页或图片搜索，回答里带引用；思考模式下同一个声明变成深度思考搜索，模型在推理途中自己搜、自己开网页、自己页内查找，官方文档说到大约 20 次工具调用为止。另有个 `deepseek_read_url` 专门读用户消息里贴的链接。

文件走 Files API 上传拿 `file_id`，PDF、Word、PPT、Excel、图片都收，服务端做纯文本提取或图文混排解析，再把内容拼进上下文。这个不靠参数开关。

语音是 ASR / TTS 两个独立端点。前端录完音先转文字再发请求，回答再送去合成音频，两步得自己串。

风控靠一条参数 `safety_check: {"level": "high"}`，服务端同时审输入和输出。

外加一个 `title: {"enabled": true}` 的小开关，让模型回答时顺手起个会话标题，省一次额外请求。

Messages、Responses、Chat Completions 三套接口都支持。有个现在还没解决的限制：这几个参数不能和你自己的 function tool 同时声明，会直接报错；`tool_choice` 也不能强制指定成 `deepseek_web_search`，搜不搜由模型决定。所以「搜索 + 自己写好的业务工具」这种组合，眼下只能走两侧独立接口自己编排。

![](https://pic2.zhimg.com/v2-af26703b5fb3f002695bfb5e82cac177_1440w.jpg)

> 图：官方标注的响应块结构，thinking、服务器端工具调用与搜索结果、带引用的正文依次返回

真正省事的地方在「服务端拼上下文」。以前接搜索，工具循环得自己转：模型说要搜，你去搜，结果塞回去，再请求一遍，还要处理模型第二次又不搜了的各种分支。现在这套循环在服务端跑完，客户端只管收流。省掉的那几百行代码其实不心疼，心疼的是那个循环里每次都想不全的分支。

![](https://pic2.zhimg.com/v2-92600bd64e65e7e87fd7f529e88f9475_1440w.jpg)

> 图：思考模式下多轮请求如何把工具、问题、思维链、工具调用与结果逐轮累积成上下文

这几样里我最看重 `deepseek_read_url`。让模型读用户随手贴的一个链接，过去得自己写个抓取服务兜着，还得防 SSRF、防超长页面把上下文撑爆，这块坑太多。现在一条参数解决。

另一条路是不要那层壳，只要零件。Search、Fetch、OCR、ASR、TTS 都开成了独立接口。手上有一套管好的编排逻辑，不想要 DeepSeek 那层的工具循环，就只买搜索和抓取，5 元一千次，比 Tavily 便宜一截。

![](https://picx.zhimg.com/v2-732bb7622b3de4a7951004b00eb60881_1440w.jpg)

## 价格表，和几个不计费的细节

| 能力 | 人民币 | 美元 |
| --- | --- | --- |
| 搜索（文字/图片） | 5 元/千次 | $0.75 |
| 网页抓取 | 5 元/千次 | $0.75 |
| OCR / 文件解析 | 1.5 元/千页 | $0.225 |
| ASR | 0.39 元/小时（刊例 0.78） | $0.058（$0.116） |
| TTS | 1.5 元/万字符（刊例 3.0） | $0.225（$0.45） |

语音那两项官方标注「限时 5 折」，什么时候恢复原价没写。

![](https://pica.zhimg.com/v2-84352d9394685dbbf3075aaf5d192b36_1440w.jpg)

> 图：官方工具 API 价目表，语音两项标着限时 5 折与划线原价

计费口径官方写得比多数厂商细：

- 失败的调用、返回无结果的调用，都不计费。
- 一次搜索调用里塞了 3 个 query，按 3 次算。
- 图片搜索，每张图 1 次；模型在图上每框选一个区域，再加 1 次。
- 深度思考搜索里的网页抓取，只在「真从网上抓了」的那一刻计费。重复打开同一页、翻页、打开随搜索结果一起下发的页面、页内查找文本，全免费。
- 阅读链接是另一套口径：按成功抓取的网页数计费，连抓回来被安全审核替换成 `url_not_allowed` 的页面也照收。
- Search 和 Fetch 这两个独立接口同理，只有 HTTP 200 且产生有效结果才收钱。

「重复打开同一页免费」这条挺实在。深度思考搜索会反复回看已经抓过的页面，碰上按流量计费的方案，这种场景账单一不小心就崩了。代价是 `deepseek_read_url` 那条路没这个优待。

## 上手：最短的一条路

不装 SDK，一条 curl 就够。Messages 接口打开 `deepseek_web_search`，请求体大致长这样：

```text
curl https://api.deepseek.com/anthropic/v1/messages \
  -H "x-api-key: $DEEPSEEK_API_KEY" \
  -H "content-type: application/json" \
  -d '{
    "model": "deepseek-flash",
    "max_tokens": 1024,
    "thinking": {"type": "disabled"},
    "tools": [
      {"type": "deepseek_web_search", "name": "deepseek_web_search"}
    ],
    "messages": [
      {"role": "latest_reminder", "content": "2026-11-14,星期六,上海,Web,中文"},
      {"role": "user", "content": "DeepSeek 最近发布了什么"}
    ]
  }'

```

Messages 的 base_url 是 `https://api.deepseek.com/anthropic`，别把 OpenAI 那套 base_url 直接搬过来。`anthropic-version` 头官方直接忽略，加不加都行，工具对象要同时写 `type` 和 `name`。

`latest_reminder` 这一条最容易漏。

它是告诉模型「现在几点、在哪、用什么设备、说什么语言」的元信息，格式固定为 `<date>,<weekday>,<location>,<platform>,<language>`。星期几要用对应语言的写法，中文场景写 `星期六` 更稳妥。必须紧贴在对应的那条用户消息前面，Messages 和 Chat Completions 支持，Responses API 不接受。

漏了会怎样？有开发者测过：不传这一条，模型把搜索词写成「2026 年 6 月」，用户说发布是 11 月 12 号，它还能反过来「纠正」用户。补上之后 5.2 秒返回，附 13 个引用。

![](https://pica.zhimg.com/v2-695f85d3b5dd56de4de521b9ce1baca6_1440w.jpg)

> 图：第三方实测对照，不传日期时模型把「今天」当成 2 月 27 日，补上日期后答对本次发布

这条不能省。用户问「今天天气」「最近有什么新闻」，模型没有时间锚点，搜出来的东西可能整个错位。接入前先把这行填上。

## 开源的 chat-demo 里有点东西

公告同一天，官方开源了 chat-demo。MIT 协议，版本 0.1.1，React 18.3.1 + zustand + rspack，TypeScript 7，数学公式走 katex，流程图走 mermaid。

README 里堵死了一句退路：「No application backend is required」。浏览器直连 API 服务，默认 `https://api.deepseek.com`，聊天走 Anthropic 兼容的 Messages / Files 接口，语音走 ASR / TTS。API Key 和设置存 localStorage，会话和附件原件存 IndexedDB。仓库 1513 个 star、251 个 fork，对个 Demo 来说不少了。

![](https://pic3.zhimg.com/v2-6f95f158741edc44ad834efde6fc2996_1440w.jpg)

> 图：官方开源仓库 chat-demo 的 GitHub 品牌卡，轻量前端 Demo 也有千级 star

本地跑起来照 README 走，装完改一下设置里的 API 地址和 Key 就能聊：

```text
pnpm install
pnpm dev

```

README 要求 Node.js 22.12+。包里只有 `pnpm-lock.yaml`，别用 npm 装，依赖版本会跑偏。

没有服务端，意味着这玩意可以直接扔对象存储当静态站点用。代价是 Key 落在浏览器的 localStorage 里，只适合自用或者放内网。对外产品得套一层自己的后端转发，顺带把 `safety_check` 这类合规参数管起来。

麻雀虽小，上下文工程上有两处做得挺讲究。

会话结构是树形，不是数组。每条消息用 `parentId` 指向父节点，`selectedChildId` 标出当前走哪个分支。用户编辑提问、或者让模型重新生成，旧回答不被覆盖，而是挂在侧枝上。展示路径和发给模型的上下文走的是同一条分支，不会出现「界面上看到 A、实际发出去是 B」这种经典 bug。

上下文裁剪的规矩也照抄了：只保留「提问 + 有效回答」成对的轮次。失败的回答、空回答、被安全审核拒掉的回答，都不进后续请求；历史轮次的思考过程和引用标记也不回传。这个小细节直接决定了多轮对话的 token 账单。`latest_reminder` 只在内容变化时才插入，不重复塞。

![](https://pic4.zhimg.com/v2-03856153e51873fdafb407603b9f7fdd_1440w.jpg)

附件的处理也顺手：图片映射成 `image` 内容块，其他文件映射成 `document` 内容块，通过 `file_id` 引用。语音那边，ASR 采集单声道 16kHz、16 位 PCM 的 WAV，单次上限 120 秒；TTS 返回 24kHz 裸 PCM 流，前端分片转成 Float32，用 `AudioContext` 排程播放。这些参数自己摸，够摸好一阵。

## 快，但别指望它当爬虫

第三方跑的这组对比数据可以当参考：Search 单次 0.3 秒上下，同场景 Firecrawl 是 2.6 到 4.4 秒，差一个数量级。

普通搜索一轮 5 秒左右，带 13 处引用。但普通搜索只看摘要不开网页，公告里塞在图片、表格里的信息就丢了，这次的价格表恰好就是一张图。换成深度思考搜索，3 个关键词、打开 5 个新闻页，8.7 秒把完整价格表搬了回来。窄问题走普通搜索 2.4 秒收工。

文件解析：35 页、36MB 的 PDF 大约 20 秒，第二次引用时 1.6 万 tokens 全部命中缓存。OCR 单独跑 2.3 秒，但页面图片里的信息靠对话解析会丢；思维导图这类带层级的图，OCR 认得出来字，层级关系会认乱。这块得自己兜。

语音那边，60 秒口播 ASR 3.2 秒转完，280 个字错 1 个。

![](https://pic2.zhimg.com/v2-45b3c4de7c4d09251229fb2550dc4c39_1440w.jpg)

> 图：第三方实测结果表，AI 新闻题自动发起 3 次搜索输出 8 条新闻，朗读回答生成 309.8 秒音频

DeepSeek 抓取不执行 JavaScript。纯静态页面没问题，靠 JS 渲染的文档站会抓空，有个教程目录只读到 495 token。要抓这类站点，还得自己上无头浏览器。

成本是真的低。近 20 次对话、两次 35 页 PDF 解析、OCR、语音、二十多次搜索抓取，加起来 5 毛多。

配额这块：账户级并发 `deepseek-flash` 2500、`deepseek-v4-pro` 500，超了返回 429，要更高可以免费申请扩容。Search 和 Fetch 分两个独立配额，100 QPS 和 25 QPS，Fetch 还额外受单域名 QPS 限制。ASR 单账号最多 50 个进行中的请求，单文件 8 MiB、120 秒。TTS 单请求最多 10000 个计费字符、请求体不超过 64 KiB、单次最多合成 30 分钟，WebSocket 会话 60 秒没有文本就断。

Search 和 Fetch 这两个独立接口 10 月 17 日就随 V4.1-Flash-1017 一起上线了。按钛媒体当时的报道，两个接口此前在 Harness、Claude Code、Codex 里调用一直是免费的，11 月 1 日起正式收费，价格约为 Tavily 的十分之一，限速则是每秒 5 次，跟现在文档里的 100/25 QPS 对不上，按新的来。11 月 13 日这次「全家桶」新增的是对话内的内置搜索、文件输入与解析、OCR、ASR/TTS 独立接口，还有 `safety_check`。

## 安全审核是参数，也是责任

`{"safety_check": {"level": "high"}}` 打开后，服务端同时审输入和输出。输入里不光有 `user` 消息，还有 `tool_result` 这类间接内容，网页抓回来的东西一样要过审。

不通过有两种表现：请求直接返回 `400 Content Exists Risk`，或者响应以 `stop_reason: "refusal"` 正常结束。`level` 设成 `low` 和不传等价。

这个参数有个容易忽略的副作用。开着它，连接不会在模型输出完就关，服务端要审完整个输出才断。客户端得留着连接等，还必须实现拒答分支，不然会卡在等流结束那一步。已经流式下发的文本撤不回来，拒答一到就得自己把已显示的回答删掉。

官方把责任划得很清楚：这参数只是帮你满足合规，不替代服务提供方自己的审核义务。对外提供服务必须开。内容安全审核、大模型登记、AI 标识这些事，一家都不能少。

## 落在哪儿

做一个类 DeepSeek 聊天产品，开工成本基本压到零了：前端拿官方 demo 改，后端逻辑没多少可写的，搜索、文件、语音、风控都在参数里。

门槛挪到了别处。问题变成你拿它的输出去干什么，以及内容安全那笔运营账怎么记。OCR 认不准带层级的图，JS 页面抓不到内容，这两条短期内还是得自己补。官方那句「1:1 复刻」说的是界面和交互能复刻，能力和那款 App 一样，但 App 之外的东西，一样得你自己想。
