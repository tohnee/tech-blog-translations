在“并行计算篇”的第二篇文章中，我们介绍了两类经典的流水线并行（Pipeline Parallelism，PP）方法：GPipe 和 PipeDream。这两种方法能确保对于每一个输入样本，它在前向计算和反向计算时使用**相同的模型参数**，这与通常的模型训练方法一致。我们把在前向计算和反向计算使用**相同模型参数**的 PP 称为 “同步流水线并行”（Synchronous Pipeline Parallelism，SPP）。与之相对的是“异步流水线并行”（Asynchronous Pipeline Parallelism，APP），即前向计算和反向计算使用**不同的模型参数**。

> 在 PP 中，“同步”和“异步”也在另一种情况下经常使用：不同 Worker 之间参数更新的时机是否同步。在本文中，我们将这类称为“同步更新”或“异步更新”。而 PP 的“同步”和“异步”则专指前向计算和反向计算使用的参数是否相同。

GPipe 和 PipeDream 都是 SPP 方法的代表。它们二者为了使得 PP 满足“同步”性质，各自做出了一些权衡和取舍。GPipe 通过统一的 Pipeline Flush 来同步更新不同 Worker 上的参数，但这会导致每个 Worker 都存在明显的空闲时间（Bubble）。也就是说，GPipe 主要是通过牺牲“时间”来换取“同步”性质。

而 PipeDream 则主要是通过牺牲“空间”来换取“同步”：在每个 Worker 上保存多个版本的模型参数来确保前向计算和反向计算使用的参数相同。

文本将介绍一种非常“暴力”的异步流水线并行方法，PipeMare。虽然异步方法在当前 LLM 时代已经不再主流，但文本会借助 PipeMare 来对比分析不同 PP 方法的关键特性，这有助于对之前介绍过的 GPipe、PipeDream、PipeDream-2BW 和 PipeDream-Flush 这四种方法进行更深入的理解。

这篇是“并行计算篇”中唯一一篇会涉及“异步优化”的文章。所以对该概念不熟悉的朋友可以趁机了解一下。本篇内容只有两个部分：

- PART 1：对 GPipe、PipeDream、PipeDream-2BW 和 PipeDream-Flush 这四种方法的 Pipeline Utilization、Memory Overhead 和 Update Delay 进行详细分析。其中 Update Delay 是一个新的概念，可以用它来判断 PP 方法的同步性。
- PART 2：介绍异步流水线并行方法 PipeMare。PipeMare 简单、粗暴的做法容易让人惊讶于它居然有效。这种无奈也是体现深度学习强大的一个方面：即使方法看上去有多么的不合理，模型强大的拟合能力让它仍有机会能 Work。

### 1. PP 的特性分析

为了更好地理解不同 PP 之间的区别，首先定义一些用于分析 PP 关键特性的指标。我们希望通过这些指标可以非常直观、快速且深入地理解不同 PP 方法的优缺点。

- **Pipeline Utilization**：Pipeline 中每个 Stage 在整个训练过程中被**有效利用的比例**。该指标反映了 PP 方法在时间维度上的效率。
- **Memory Overhead**： 在 PP 方法中为了实现流水线并行所需的**额外内存开销**。该指标反映了 PP 方法在空间维度上的效率。本文只考虑因额外模型参数副本导致的开销，而不考虑其它因素（如激活值缓存等）。
- **Update Delay**： 指对于某个参数 $W$，它参与梯度计算（前向或反向）与使用该梯度进行参数更新的 Optimizer Steps 之间的差距。该指标反映了 PP 方法在参数更新上的及时性。Update Delay 这个指标并不像前两个指标那么直观，所以在下面对每个方法的分析中会着重介绍。

除此之外，Peak Memory 也是一个重要指标，但因为它通常涉及到更多的实现细节，直接量化不太容易。所以本文只在需要对比不同方案的 Peak Memory 时进行讨论。

下面将对之前介绍过 GPipe、PipeDream、PipeDream-2BW 和 PipeDream-Flush 这四种方法的 Pipeline Utilization、Memory Overhead 和 Update Delay 进行详细分析。

> 本文不会对这些方法再额外做详细介绍。不熟悉的朋友可以参考本系列之前的文章。

### 1.1 GPipe

![](https://pic4.zhimg.com/v2-4eaa83d59727b45c6037f4422dae10e7_r.jpg)
*图 1.1 GPipe 示意图*

图 1.1 是 GPipe 的示意图。图中每一个数字方块表示一个 Micro-batch，4 个 Micro-batch 构成一个完整的 Batch。作为示例，将该 Batch 记为 Batch 1。为了和之前文章的符号保持一致，记 Worker 数量为 $n$，Micro-batch 数量为 $m$。那么在图 1.1 中，$n=4$，$m=4$。

在第二篇文章中详细分析过 GPipe 的 Pipeline Bubble 占比为：

$ (1.1)\quad \text{Ratio}(\text{GPipe}) = \frac{n-1}{m+n-1} $

那么 Pipeline Utilization 就为：

$ (1.2)\quad \text{Utilization}(\text{GPipe}) = 1 - \text{Ratio}(\text{GPipe}) = \frac{m}{m+n-1} $

当 Worker 数量 $n$ 固定时，增加 Micro-batch 数量 $m$ 可以提升 Pipeline Utilization。但是增加 Micro-batch 数量会带来一些负面效应。分以下两种情况分析：

- <br>**情况一**：如果在总 Batch 不变的情况下增加 Micro-batch 数量，那么每个 Micro-batch 的大小就会变小，从而导致整个 Batch 的计算效率下降。例如，假设一个 Batch 包含 10 个样本。方案 A 将它分成 2 个 Micro-batch，每个 Micro-batch 包含 5 个样本；方案 B 将它分成 5 个 Micro-batch，每个 Micro-batch 包含 2 个样本。显然，方案 A 的计算效率会高于方案 B，因为它一共只需要执行 2 次前向计算和 2 次反向计算，而方案 B 需要执行 5 次前向计算和 5 次反向计算。<br>
- <br>**情况二**：如果保持每个 Micro-batch 大小不变而增加 Micro-batch 数量，那么整个 Batch 的大小就会变大，从而会增大 Peak Memory，带来额外的显存压力。<br>

记 Worker $i$ 对应的模型参数为 $W_i$。因为每个 Worker 只需要始终保存一份模型参数，所以 GPipe 的 Memory Overhead 为：

$ (1.3)\quad \text{MemoryOverhead}(\text{GPipe}) = \sum\limits_{i=1}^{n} |W_i| = |W| $

符号 $|W_i|$ 表示模型参数 $W_i$ 的大小，$|W|$ 表示整个模型参数的大小。也就是说，GPipe 的 Memory Overhead 就是模型参数的大小，不需要保存额外的模型参数副本。

最后来分析 GPipe 的 Update Delay。使用符号 $W^{(j)}_{i}$ 表示第 $i$ 个 Stage 对第 $j$ 个 Batch 使用的模型参数。参考图 1.1，对于 Worker 1，它对 Batch 1 的前向计算和反向计算使用的是参数都是 $W^{(1)}_{1}$（再次强调，Batch 1 是图 1.1 中所有 Micro-batch 的总和）。并且当执行完 Batch 1 的反向计算后，所有 Worker 的参数会统一基于 Batch 1 的梯度进行更新。也就是说，对于 $W^{(1)}_{1}$ 而言，在它参与前向计算和使用基于它计算得到的梯度进行更新之间，没有任何其它的 Optimizer Step。因此，GPipe 中前向计算的 Update Delay 为 0。使用符号 $\tau^{(i)}_{\text{fwd}}$ 表示第 $i$ 个 Stage 前向计算时参数的 Update Delay，那么可知 GPipe 中对于任意 Stage $i$，都有 $\tau^{(i)}_{\text{fwd}}=0$。

同理容易发现，GPipe 中反向计算的 Update Delay 也是 0。使用符号 $\tau^{(i)}_{\text{bwd}}$ 表示第 $i$ 个 Stage 反向计算时参数的 Update Delay，那么 GPipe 中对于任意 Stage $i$，都有 $\tau^{(i)}_{\text{bwd}}=0$。因为 GPipe 中 $\tau^{(i)}_{\text{fwd}}$ 和 $\tau^{(i)}_{\text{bwd}}$ 始终相同，所以它是 “同步的”。

总结一下 GPipe 的三个关键特性：

- Pipeline Utilization：$\frac{m}{m+n-1}$。
- Memory Overhead：$|W|$。
- Update Delay：$\tau^{(i)}_{\text{fwd}}=\tau^{(i)}_{\text{bwd}}=0$。

### 1.2 PipeDream

![](https://picx.zhimg.com/v2-5f9698867b60d46762477548769e4fbf_r.jpg)
*图 1.2 PipeDream 示意图*

在图 1.2 的 PipeDream 示例中，每个数字框表示一个独立的 Batch（注意和 GPipe 中的 Micro-batch 区别），这意味着每个 Batch 都会触发一次优化器更新，而在 GPipe 中是所有的 Micro-batch 共同触发一次优化器更新。

PipeDream 的显著特点是它有一个 Warm-up 阶段，在此之后流水线进入稳定状态（Steady State）。在稳定状态下，Pipeline 中的每个 Stage 都不会有空闲时间（Bubble），所以 PipeDream 的 Pipeline Utilization 为 100%。

因为在整个计算过程中可能会存在多个 Batch 同时在流水线中流动，所以每个 Worker 需要保存多个版本的模型参数。我们从简单情况开始分析。对于 Worker 4，因为它恰好是一次前向计算后紧跟相同 Batch 的反向计算，所以它只需要保存一份模型参数副本，即 $W^{(j)}_{4}$。

对于 Worker 3，因为它的前向计算和反向计算之间会穿插**一次**其它 Batch 的计算，所以它需要保存两份模型参数副本，分别是 $W^{(j)}_{3}$ 和 $W^{(j-1)}_{3}$。

这个规律很容易找，对于 Worker $i$，它的前向计算和反向计算之间会穿插 $(n-i)$ 个其它 Batch 的计算，所以它需要保存 $(n-i+1)$ 份模型参数副本，分别是 $W^{(j)}_{i}, W^{(j-1)}_{i}, \ldots, W^{(j-(n-i))}_{i}$。

因此当总共有 $n$ 个 Worker 时，PipeDream 的 Memory Overhead 为：

$ (1.4)\quad \text{MemoryOverhead}(\text{PipeDream}) = \sum\limits_{i=1}^{n} (n-i+1) \cdot |W_i| $

再来分析 PipeDream 的 Update Delay。我们先来看相对比较简单的 Worker 4。因为 Worker 4 恰好是一次前向计算后紧跟相同 Batch 的反向计算，所以它的 $\tau^{(i)}_{\text{fwd}}=\tau^{(i)}_{\text{bwd}}=0$。

再来看 Worker 3，从它稳定时的情况来分析（不再有空闲）。Worker 3 对 Batch 2 在前向和反向计算使用的参数都是 $W^{(2)}_{3}$。而在 $W^{(2)}_{3}$ 执行更新动作之前，穿插了基于 Batch 1 梯度的更新（对参数 $W^{(1)}_{3}$）。因此，Worker 3 的 $\tau^{(3)}_{\text{fwd}}=\tau^{(3)}_{\text{bwd}}=1$。虽然 PipeDream 中存在 Update Delay，但因为前向计算和反向计算的 Update Delay 始终相同，所以 PipeDream 仍然是 “同步的”。

容易发现，PipeDream 的 Update Delay 等于每个 Worker 前向计算和反向计算之间穿插的 Batch 数量。也就是说，对于任意 Stage $i$，都有：

$ (1.5)\quad \tau^{(i)}_{\text{fwd}}=\tau^{(i)}_{\text{bwd}}=n-i $

总结一下 PipeDream 的三个关键特性：

- Pipeline Utilization：1（100%）。
- Memory Overhead：$\sum\limits_{i=1}^{n} (n-i+1) \cdot |W_i|$。
- Update Delay：$\tau^{(i)}_{\text{fwd}}=\tau^{(i)}_{\text{bwd}}=n-i$。

### 1.3 PipeDream-2BW

![](https://pic2.zhimg.com/v2-a0869fee0dee94a9333f64d79c5bf4f1_r.jpg)
*图 1.3 PipeDream-2BW 示意图*

PipeDream-2BW 就是 PipeDream 的 Micro-batch 版本。图 1.3 的示例中，每个数字方块表示一个 Micro-batch，4 个 Micro-batch 构成一个完整的 Batch。因此图 1.3 中一共包含两个 Batch，分别记为 Batch 1（编号 1 到 4） 和 Batch 2（编号 5 到 8）。每个 Worker 上的梯度更新发生在对当前 Batch 的所有 Micro-batch 计算完成之后，如图中绿色格子方块所示（编号为 4）。

容易看到，PipeDream-2BW 的 Pipeline Utilization 和 PipeDream 一样，都是 100%。PipeDream-2BW 中的每个 Worker 只需要保存两个模型副本（详见“并行计算篇”的第二篇文章）。 因此 PipeDream-2BW 的 Memory Overhead 为：

$ (1.6)\quad \text{MemoryOverhead}(\text{PipeDream-2BW}) = \sum\limits_{i=1}^{n} 2 \cdot |W_i| $

PipeDream-2BW 的参数更新规则为：

$ (1.7)\quad W^{(t+1)}_{i} \leftarrow W^{(t)}_{i} - \eta \cdot \nabla W^{(t-1)}_{i} $

注意此时的上标 $t$ 表示的是迭代次数，而不是 Batch 编号。也就是说，Worker $i$ 在第 $t$ 次迭代中使用参数 $W^{(t)}_{i}$ 进行前向计算，而它使用的梯度是基于它在第 $(t-1)$ 次迭代中使用的参数 $W^{(t-1)}_{i}$ 计算得到。因此在 $(t-1)$ 次迭代中，前向计算和反向计算使用的参数都是 $W^{(t-1)}_{i}$，并且由它们产生的梯度会隔一次迭代后才会被用于更新第 $t$ 次迭代中使用的参数 $W^{(t)}_{i}$。所以 PipeDream-2BW 的 Update Delay $\tau^{(i)}_{\text{fwd}}=\tau^{(i)}_{\text{bwd}}=1$。

在这个意义上，PipeDream-2BW 仍然是“同步的”，因为它对每个样本的前向计算和反向计算使用的参数依然相同。不过由于式（1.7）的更新规则与标准 SGD 并不一致，因此我们说 PipeDream-2BW 不能保持“Optimizer Semantic”（意思是不能保持准确的更新规则）。

总结一下 PipeDream-2BW 的三个关键特性：

- Pipeline Utilization：1（100%）。
- Memory Overhead：$\sum\limits_{i=1}^{n} 2 \cdot |W_i|$。
- Update Delay：$\tau^{(i)}_{\text{fwd}}=\tau^{(i)}_{\text{bwd}}=1$。

### 1.4 PipeDream-Flush

![](https://pic2.zhimg.com/v2-c15b1bf5220cded9fb6c377dd1063559_r.jpg)
*图 1.4 PipeDream-Flush 示意图*

PipeDream-Flush 就是使用 1F1B 的 GPipe。换言之，PipeDream-Flush 仍然像 GPipe 一样使用 Pipeline Flush 来同步更新参数，但它使用 1F1B 的调度策略。与 GPipe 原本的调度策略相比，1F1B 并无法减少 Pipeline Bubble 的占比。这是因为对每个 Worker 来说，它执行的前向计算和反向计算次数没有变化，并且单个 Batch 的总执行时间相较于 GPipe 也没有变化。因此 PipeDream-Flush 的 Pipeline Utilization 和 GPipe 一样，都是 $\frac{m}{m+n-1}$。

PipeDream-Flush 的 Memory Overhead 也和 GPipe 一样，都是 $|W|$，因为它每个 Worker 需要保存一份模型参数。

PipeDream-Flush 的 Update Delay 也和 GPipe 一样，都是 0。因为它使用 Pipeline Flush 来同步更新参数，不存在 Delay。

PipeDream-Flush 相比于 GPipe 的唯一优势它能降低 Peak Memory。在 GPipe 中，对于每个 Worker 来说，因为它首先执行所有 Micro-batch 的前向计算，然后再执行反向计算，所以它在执行反向计算之前需要完整保持所有 Micro-batch 的激活值（Activation）。

而在 PipeDream-Flush 中，因为每个 Worker 交替执行前向计算和反向计算，所以当它执行完某个 Micro-batch 的反向计算后，就可以释放该 Micro-batch 的激活值，从而降低 Peak Memory。

总结一下 PipeDream-Flush 的三个关键特性（与 GPipe 相同）：

- Pipeline Utilization：$\frac{m}{m+n-1}$。
- Memory Overhead：$|W|$。
- Update Delay：$\tau^{(i)}_{\text{fwd}}=\tau^{(i)}_{\text{bwd}}=0$。

PipeDream-Flush 相比于 GPipe 的 Peak Memory 更低。

### 2. 异步流水线并行：PipeMare

可以将 PipeMare 看作是每个 Worker 始终只保存一份模型参数的 PipeDream（参考图 1.2）。也就是说，在 PipeMare 中，每个 Worker 在收到数据需要进行前向或反向计算时，它都直接使用自己拥有的那份参数，完全不关心前向计算和反向计算使用的参数是否相同。对应到图 1.2 中，其实就是只有一份参数 $W_{i}$。

PipeMare 的三个关键特性如下：

- Pipeline Utilization：1（100%），与 PipeDream 相同。
- Memory Overhead：$|W|$，这是因为每个 Worker 只保存一份模型参数。
- Update Delay：$\tau^{(i)}_{\text{fwd}}=n-i$，与 PipeDream 相同。但 $\tau^{(i)}_{\text{bwd}}=0$，因为反向计算始终使用当前的参数。

PipeMare 的做法显得过于粗暴了，所以它需要一些额外的技巧来稳定训练。

第一个采用的技巧是 **Learning rate rescheduling**。由上述分析知道每个 Worker 的前向 Delay $\tau^{(i)}_{\text{fwd}}=n-i$ 不同，而每个 Worker 包含整个模型的不同网络层，这意味着在不同 Worker 上的网络层实际上具有不同的 $\tau^{(i)}_{\text{fwd}}$。

从直觉上看，$\tau^{(i)}_{\text{fwd}}$ 越大表明前向与反向之间所间隔的 Optimizer Steps 越多，这会导致梯度计算与参数更新之间的时序差距越大，从而一致性越差。因此一种容易想到的做法是给不同网络层赋予不同的学习率。如果 $\tau^{(i)}_{\text{fwd}}$ 越大，那么对应的学习率就应该越小，以维持稳定性。

假设基准学习率为 $\eta$，那么对于 Worker $i$ 上的网络层，可以将其学习率设置为：

$ (2.1)\quad \eta_i = \frac{\eta}{\tau^{(i)}_{\text{fwd}} + 1} $

加 1 是为了防止分母为 0。但这么做容易导致某些层的学习率过小。导致过小的原因有两方面：

- 当 Worker 数量 $n$ 较大时，靠近 Pipeline 头部的 Worker 的 $\tau^{(i)}_{\text{fwd}}$ 会非常大，从而经公式（2.1）后导致它们的学习率过小。
- 当训练使用学习率衰减时，随着训练的进行，基准学习率 $\eta$ 会越来越小，从而导致某些层的学习率更小。

PipeMare 的最终方案是：

$ (2.2)\quad \eta_{i,k} = \frac{\eta_k}{(\tau^{(i)}_{\text{fwd}} + 1)^{\alpha_k}} $

其中 $k$ 表示当前的训练阶 Step，$\eta_k$ 表示当前的基准学习率，$\alpha_k$ 是一个随训练 Step 变化的指数衰减因子：

$ (2.3)\quad \alpha_k = 1 - \min(\frac{k}{K_{\max}}, 1) $

其中 $K_{\max}$ 是一个超参数，表示在多少个训练 Step 之后，$\alpha_k$ 会衰减到 0。也就是说，在 $K_{\max}$ Steps 之后，所有层的学习率都会变成相同的基准学习率 $\eta_k$。这可以解决上述第二点问题。

对于第一点问题，因为使用了一个小于 0 的指数 $\alpha_k$，所以即使 $\tau^{(i)}_{\text{fwd}}$ 很大，学习率也不会变得过小。

第二个增加训练稳定性的技巧是 **Discrepancy correction**。简单来说，虽然 PipeMare 是异步，但是我们还是希望它能尽可能同步：反向和前向计算采用的参数尽量相同。

PipeMare 的做法是通过当前反向计算所使用的参数 $W_{i,j}$ 去**估算**前向计算时所使用的参数 $W_{i,j-t}$。这里我们用符号 $W_{i,j}$ 表示 Worker $i$ 在第 $j$ 个 Batch（或 Micro-batch） 上使用的参数，$t$ 表示前向计算和反向计算之间的 Delay 差距（对于 PipeMare 来说，$t=n-i$）。

然后在每个 Worker 中始终保存一个梯度变化率 $\Delta W_{i}$，它表示每次参数更新时，参数的平均变化量。这样就可以通过下面的公式去估算前向计算时所使用的参数：

$ (2.4)\quad \hat{W}_{i,j-t} = W_{i,j} + t \cdot \Delta W_{i} $

梯度变化率 $\Delta W_{i}$ 可以通过指数加权移动平均（Exponential Moving Average，EMA）来计算：

$ (2.5)\quad \Delta W_{i} = \beta_i \Delta W_{i} + (1 - \beta_i)(W_{i,j} - W_{i,j-1}) $

在 PipeMare 中，$\beta_i$ 通过如下参数化方法训练得到：

$ (2.6)\quad \beta_i = D^{1/(n-i+1)} $

其中 $D$ 由训练得到。

其实这么一改，PipeMare 的 Memory 优势就没有了，因为每个 Worker 现在需要保存两份参数：当前参数 $W_{i,j}$ 和梯度变化率 $\Delta W_{i}$，这和 PipeDream-2BW 的开销一致。

### 3. 总结

本文首先对 GPipe、PipeDream、PipeDream-2BW 和 PipeDream-Flush 这四种 PP 方法的 Pipeline Utilization、Memory Overhead 和 Update Delay 进行了较为详细的分析。然后介绍了一种异步流水线并行方法 PipeMare，并分析了它的关键特性以及为了稳定训练所采用的两种技巧：Learning rate rescheduling 和 Discrepancy correction。

虽然异步流水线并行方法在当前 LLM 时代已经不再主流，但通过 PipeMare 的分析可以更好地理解不同 PP 方法的优缺点。本系列的后续文章中不会再关注异步流水线并行方法。
