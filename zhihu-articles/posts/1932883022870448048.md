## Summary

FSDP （Zero3）是用户友好的分布式训练方法，一般对 Transformer Layer 包裹，在上一个 Layer 计算的同时，进行下一个 Layer 参数的 All Gather，prefetch 如果优化得当可以完全 overlap，Llama3 400B 就在 DP 维度使用了 FSDP 切分。

在显式 prefetch 的情况下，我们没有必要关心这种问题，因为所有的操作顺序在 default stream 上执行，用完的 weight buffer 直接 deallocate 便可以扔进 pool 里给下一次的 prefetch 使用。在没有 reorder code 的情况下，后调用的 all gather 如果也想隐式与 compute overlap 就需要在另一个 communication stream 上调用，此时涉及到多 stream 的显存管理，导致了显存的额外开销。

考虑 CPU调度操作的速度快于GPU执行速度的情况: GPU 正在计算 Layer $i$ , All Gather Layer $i + 1$ ，而 CPU 开始 issue Layer $i + 2$ 的 weight all gather，就会让 torch cuda allocator 申请 Layer $i + 2$ 的 buffer, 显存中同时存在 3 个 Layer 的 weight buffer。在 CPU 运行更快的情况下更为严重，可能会退化为 Zero2。

对此 FSDP1/2 和有着不同的解决方法。FSDP1 简单粗暴地限制 all gather queue length，FSDP2 通过 cuda event 控制 buffer free/allocate，笔者不了解 Deepspeed 故不讨论其实现。

## Intro

今天回顾 pytorch FSDP2 blog 的时候，注意到其中一个相较于 FSDP1的改进为

> Improving memory management system that achieves lower and deterministic GPU memory by avoiding `recordStream` ([doc](https://dev-discuss.pytorch.org/t/fsdp-cudacachingallocator-an-outsider-newb-perspective/1486)) and does so without any CPU synchronization.

对其中 FSDP1 需要 CPU Sync 较为费解，遂学习了一下，就有了本文。需要注意，这种 Sync 只会在**多流计算**的情况下出现，在手动指定 prefetch module 并禁用 communication stream 的情况下一般不会遇到这种问题（NCCL Stream 除外）。

首先简单回顾一下 Zero。Zero1-2-3 核心在于切分 DP Group Redundant 的 optimizer state - grad - weight。

一般来说训练至少会用 Zero1，对于 adamw 来说 optimizer state 相当于 weight 的三份 fp32 copy (master weight + first/second moment），均摊到DP Group还是很香的，附带的好处是 gradient fp32 all reduce 变成了 fp32 reduce scatter + bf16 all gather，理论通信量是减少的 ，实际上 Megatron 在不久前也只实现了 Zero1。

Zero2 切分 gradient，由此在 backward 的时候，计算完 layer $i$ weight 的 gradient 就会立刻调用 reduce scatter，与 layer $i - 1$ 的计算 overlap。在 dp group 特别大不需要 gradient accumulation 的情况下只需要进行一次 rs. 实际上就是 zero1 分桶 + overlap。

Zero3 将 weight 也进行切分，前向时需要在计算前 all gather 得到 weight。在前向时与 zero3 类似，layer $i$ computation 与 layer $i + 1$ weight all gather overlap，也是 double buffer。在 backward 时，也需要先 all gather 才能 backward，理想情况下 all gather layer $i - 1$ + reduce scatter layer $i + 1$ + layer i backward 能够 overlap。FSDP 是 Zero3 的一种实现，之后用 FSDP 表述。

![](https://pic1.zhimg.com/v2-9576b69252d615113e1ab0b84e77fc1a_r.jpg)
*Fig1 https://arxiv.org/pdf/2304.11277*

让我们检查一下 FSDP paper 中的图，其实已经暗示了显存管理问题，注意 CPU issue all gather 2 的时候，GPU 还在 FWD0 + AG1，此时 pytorch 就会 allocate layer 2 parameter，导致非预期的显存开销。在 Backward 时也需要考虑 Gradient buffer 的生命周期，不过我们先只考虑解决这个简单的 forward all gather buffer 问题。

## 各显神通

### FSDP1

FSDP1 对上述问题给出了简单的解法：**让CPU等着**。

![](https://pica.zhimg.com/v2-73d4e03b9a7210a2b15caed7a2434aaa_r.jpg)
*FIg2 https://docs.pytorch.org/docs/2.7/fsdp.html#module-torch.distributed.fsdp*

回顾 FSDP1 的接口（Fig2），我们可以注意到 limit_all_gathers 这个选项，默认开启。这就是为了解决预分配显存的强行 Sync CPU。

```python
# https://github.com/pytorch/pytorch/blob/0acbf8039abccfc17f9c8529d217209db5a7cc85/torch/distributed/fsdp/_runtime_utils.py#L272
@no_type_check
def _unshard(
    state: _FSDPState,
    handle: FlatParamHandle,
    unshard_stream: torch.Stream,
    pre_unshard_stream: torch.Stream,
) -> None:
    """
    Unshards the handles in ``handles``. If the handles are in
    :meth:`summon_full_params` and are using mixed precision, then they are
    forced to full precision.

    Postcondition: handle's ``FlatParameter`` 's data is the padded
    unsharded flat parameter on the compute device.
    """
    if not handle:
        return
    with state._device_handle.stream(pre_unshard_stream):
        ran_pre_unshard = handle.pre_unshard()
    if ran_pre_unshard:
        unshard_stream.wait_stream(pre_unshard_stream)
    if state.limit_all_gathers:
        event = state._free_event_queue.dequeue_if_needed()
        if event:
            with torch.profiler.record_function(
                "FullyShardedDataParallel.rate_limiter"
            ):
                event.synchronize()
    with state._device_handle.stream(unshard_stream):
        handle.unshard()
        handle.post_unshard()
```

这里 _free_event_queue 就是保存 unshard 的 event ，即在 Layer $i$ 计算完后 record 的 Event。

你可能会好奇， CPU event sync 并不表示 CPU 对 Tensor 的引用归零而触发 torch 回收。这里实际上 weight 在 python 的 ref 已经清零了，但是 torch allocator 由于其被多个 stream 使用还保留底层的 block。

**Torch CUDACachingAllocator**

首先我们需要理解 torch memory allocator 是个什么运行逻辑。不过，我们为什么需要一个 Allocator？这是因为 cuMemAlloc 和 cuFree 会导致所有 Stream 同步，如果希望愉快地 Let the Tensor Flow 最好还是自己写一个遵循某种 Stream 约束的 Allocator，比如 CUDACachingAllocator，zhihu 上 [@大道始于一](https://www.zhihu.com/people/0f685dbcd1051d27d39417cf6322f423) 已经有介绍。

[Pytorch 1.6 显存管理CudaCachingAllocator剖析](https://zhuanlan.zhihu.com/p/678774654)

为了处理多个 stream 的场景，allocator 对一个 block 会记录其创建的 stream，以及被哪些其他的 stream 使用。在 Free 时如果没有被非 allocate stream 使用则直接释放，否则会对其正在使用的所有 stream create 一个 cuda event，在 [synchronize_and_free_events](https://github.com/pytorch/pytorch/blob/0acbf8039abccfc17f9c8529d217209db5a7cc85/c10/cuda/CUDACachingAllocator.cpp#L3077) 中与所有 Event Sync 然后释放对应 block。在实际使用的时候，可以通过 Tensor.record_stream(s) 将 stream s 加入这个 tensor 对应 block 的 stream list 中，由此保证只有这个 stream 上所有操作完成再 free.

FSDP1 即通过这种方法保证在 CPU 逻辑上 free 的 weight block 不被释放，这些 weight block 在 all gather stream 创建，被 compute stream 使用，故而需要 record stream 保证不提前释放。由此，实际的 BlockFree 实际在 Layer i Compute 结束，这与之前的介绍一致。

回到 cpu sync，如此直接的限制，效果自然也是立竿见影...?

![](https://picx.zhimg.com/v2-89816b672a7bdd56b45129cce3d2fe8b_r.jpg)
*https://dev-discuss.pytorch.org/t/fsdp-cudacachingallocator-an-outsider-newb-perspective/1486*

很遗憾，尽管 forward 的确没有 memory spike了，backward 仍然存在。这与 autograd 的具体实现以及FSDP1 注册 Module hook 的调用有关，笔者并不清楚具体原因。不过种种原因，使用 DTensor 的 FSDP2 来了，其中就顺便解决了这个问题。

### FSDP2

以下内容来自[这里](https://dev-discuss.pytorch.org/t/fsdp-cudacachingallocator-an-outsider-newb-perspective/1486)

我们的目标很简单，在 compute layer i 结束的时候 free weight 同时 allocate layer i + 2 的 weight buffer 并开始 all gahter。那么我们的实现也很简单！

**Event Sync**

![](https://pica.zhimg.com/v2-51c97112eb3e36cd772baebd613b636e_r.jpg)
*https://dev-discuss.pytorch.org/t/fsdp-cudacachingallocator-an-outsider-newb-perspective/1486*

刚刚提到 torch allocator 的 free 与 allocate 只要在同一个 stream 上顺序执行就可以释放，而之所以 FSDP1 没有正确释放是因为 weight buffer 的 free 被 Tensor.record_stream 延迟到实际 layer i compute 结束的时候了。但是我们没有必要延迟，只需要让在 communication stream 上 allocate 的 new weight buffer 在 layer i compute 结束的时候再调用 all gather 就可以了。于是简单地在 communication stream 上插入一个 wait layer $i - 1$ compute 的 event ，然后直接 free layer $i -1$ 的weight buffer就可以了，没有必要 record_stream 等到实际计算结束释放。申请的 layer $i + 1$ weight buffer 可以复用 layer $i - 1$ , CUDA event 会保证 layer $i + 1$ 的 all gather 在 layer $i - 1$ 计算结束后执行。

```python
# torch/distributed/fsdp/_fully_shard/_fsdp_param_group.py
def reshard(self):
    if self._training_state == TrainingState.FORWARD:
        if not self._reshard_after_forward:
            return

            self._to_sharded_post_forward()
            self._reshard_after_forward_event = self.device_handle.Event()
            if self._reshard_after_forward_event is not None:
                self._reshard_after_forward_event.record() # 在这里记录 compute 结束
            return

    ...

def unshard(self, async_op: bool = False):
    ...
    if self._reshard_after_forward_event is not None:
        # Resharded parameter data is allocated in the default stream and
        # used in the all-gather streams
        # 在 all gather 前 wait
        self._wait_all_gather_streams_on_event(self._reshard_after_forward_event) 
        self._reshard_after_forward_event = None
    with record_function(self._with_fqn("FSDP::all_gather")):
        self._all_gather_result = foreach_all_gather(
            self.fsdp_params,
            self._all_gather_process_group,
            async_op,

            self.device,
            self._all_gather_comm,
```

### 显式 Prefetch

尽管一般来说显式 Prefetch 很难有什么问题，所有的 free/allocate 操作和 compute 一样是顺序执行。但是也会有一些惊喜。

[https://github.com/pytorch/pytorch/issues/147168](https://github.com/pytorch/pytorch/issues/147168)

这个 Issue 描述了一个显式 prefetch 时的显存问题，而这也是老朋友 `record_stream` 导致的。

Pytorch 将所有的 nccl kernel 都放在特殊的 nccl stream 上运行，那么为了保证使用的 Tensor 不会在 nccl 操作结束前 free，默认情况下所有的 nccl 操作都会触发 [record stream](https://github.com/pytorch/pytorch/blob/0acbf8039abccfc17f9c8529d217209db5a7cc85/torch/csrc/distributed/c10d/ProcessGroupNCCL.cpp#L5373)。尽管我们已经在 default stream 上 free weight buffer 了，由于其之前被用于 all gather, record nccl stream。直到下一个 torch 查询其 event state 的节点，这部分显存都不会 free。

解决的方法原 Issue 中也提到，是将 `TORCH_NCCL_AVOID_RECORD_STREAMS` 设置为 True。这避免大部分 nccl 操作的 record stream 并将 ref 管理的问题完全交由用户。在目前 stable 的[2.7.1](https://github.com/pytorch/pytorch/blob/e2d141dbde55c2a4370fac5165b0561b6af4798b/torch/csrc/distributed/c10d/ProcessGroupNCCL.cpp#L936)，我们还需要这个设置，而 main branch 已经[去掉了这个环境变量](https://github.com/pytorch/pytorch/blob/6d071bd65de9bdc354f32adf67e00d6e13475e76/torch/csrc/distributed/c10d/ProcessGroupNCCL.cpp#L916)，除去 isend 等操作外不再 record stream。

## End

本文介绍了 FSDP 实现中，隐式 Overlap 的显存管理问题，这主要与 torch cuda mem allocator 的多流 free 行为有关。FSDP1 直接控制 queue length, FSDP2 通过 Event 同步解决，避免多流检查。
