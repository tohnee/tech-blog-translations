<br>**llm_engine执行的核心函数**

```text
 def step(self) -> List[Union[RequestOutput, EmbeddingRequestOutput]]:
 """Performs one decoding iteration and returns newly generated results.

 .. figure:: https://i.imgur.com/sv2HssD.png
 :alt: Overview of the step function
 :align: center

 Overview of the step function.

 Details:
 - Step 1: Schedules the sequences to be executed in the next
 iteration and the token blocks to be swapped in/out/copy.

 - Depending on the scheduling policy,
 sequences may be `preempted/reordered`.
 - A Sequence Group (SG) refer to a group of sequences
 that are generated from the same prompt.

 - Step 2: Calls the distributed executor to execute the model.
 - Step 3: Processes the model output. This mainly includes:

 - Decodes the relevant outputs.
 - Updates the scheduled sequence groups with model outputs
 based on its `sampling parameters` (`use_beam_search` or not).
 - Frees the finished sequence groups.

 - Finally, it creates and returns the newly generated results.
"""
```

<br>注释写的很清晰，分成三步。用更简介的话来表达，就三个事情，预处理，模型执行，后处理。

            logits = self.model.forward(tokens[:, prev_pos:cur_pos], prev_pos)
            if temperature > 0:
                probs = torch.softmax(logits[:, -1] / temperature, dim=-1)

            eos_reached |= (~input_text_mask[:, cur_pos]) & (

<br>**2.3.1 排队队列(scheduler)**

MLSyser大兄弟肯定很熟悉，业务有波峰很正常，波峰很高也很正常。<br>但加机器要钱，支持的并发就这么些，你全打给机器，机器就死给你看。<br>你要把这些撑不住的请求丢了，业务方（例如我）一定来干你。<br> <br>好消息是，内存没那么贵，那么就搞个队列，把处理不完的请求放到队列里（内存），去排队。<br> <br>Scheduler中有 3 个队列<br>waiting（接受到的新请求会先放入 waiting 队列）<br>running（被调度的请求）<br>swapped 队列（swapped 队列用于存放被抢占的请求，即当请求处于生成阶段时，但由于空间的不足，需暂时将 running 队列中优先级低的请求移到 swapped 队列）。<br>Scheduler 会按照先到先处理（first come first served）的原则从 waiting 队列中选择请求放入 running 队列<br> <br>不同业务的排队最优解不同，本科的计算机系统，一堆这样的设计方案（这是MLSyser大兄弟的领域，我就不深入展开了<br> <br>代码如下，可以看到三个队列都是deque

```text
 # Create the block space manager.
 self.block_manager = BlockSpaceManagerImpl(
 block_size=self.cache_config.block_size,
 num_gpu_blocks=num_gpu_blocks,
 num_cpu_blocks=num_cpu_blocks,
 sliding_window=self.cache_config.sliding_window,
 enable_caching=self.cache_config.enable_prefix_caching)

 # Sequence groups in the WAITING state.
 # Contain new prefill or preempted requests.
 self.waiting: Deque[SequenceGroup] = deque()
 # Sequence groups in the RUNNING state.
 # Contain decode requests.
 self.running: Deque[SequenceGroup] = deque()
 # Sequence groups in the SWAPPED state.
 # Contain decode requests that are swapped out.
 self.swapped: Deque[SequenceGroup] = deque()
 # Sequence groups finished requests ids since last step iteration.
 # It lets the model know that any state associated with these requests
 # can and must be released after the current step.
 # This is used to evict the finished requests from the Mamba cache.
 self._finished_requests_ids: List[str] = list()
```

## <br>**3 模型执行**

<br>核心在于两点，kv cache怎么优化，model怎么更好的load和infer。<br>个人觉得，最重要的就是kv cache，这里的挑战实在是太大了

### <br>**3.1 kv cache的挑战**

<br>最近两年内，kv cache的优化，会是横亘在几乎所有大模型公司面前的一个挑战。<br>这里从flash attention的视角来展开，它认为kv cache优化分成两种。

<br>**[a] FLOPS（Floating Point Operations Per Second）**<br>达到同样效果的情况下，降低计算量。如各种efficient transformer的优化。

<br>**[b]MAC（memory access cost）**<br>gpu是三层级的内存结构

![](https://pic4.zhimg.com/v2-a19fe92bce50b97d81eba570db9238ef_r.jpg)

<br>可以看到SRAM存储量级要远小于HBM，但读取速度远高于HBM。这种性能的差异，导致我们如果频繁的做SRAM和HBM之间的内存交互，会极大的降低效率。<br>根据小群讨论，SRAM的价格也没有那么贵，核心卡点是带宽慢，intel的pcie太慢了，老黄看不下去自己撸的nvlink。<br><br>flash attention优化的就是这块，传统transformer有大量的hbm读写。FlashAttention将参与计算的矩阵进行分块送进SRAM，来提高整体读写速度（减少了HBM读写）。<br>但transformer的softmax是没有分块计算的能力，依赖一个全局的分母项。Flash attention，从3-pass变成了1-pass，来实现了分块计算的能力。<br>这块就不展开了，vllm直接调用的flash attention，大家可以自己看细节，参考下面这两篇文章。<br><u>[https://zhuanlan.zhihu.com/p/642962397](https://zhuanlan.zhihu.com/p/642962397)</u><br><u>[https://zhuanlan.zhihu.com/p/668888063](https://zhuanlan.zhihu.com/p/668888063)</u><br><br>以及也有公司针对这种硬件情况做针对性优化，例如groq。好久没听到他们声音，怀疑蹲坑去工厂优化生产工艺了。如果机器架构有质的改变，flash attention价值可能就没那么大了，甚至是负向的，因为它增加了额外的计算量，需要分块算完，再合并起来。

<br>decode的时候才用到flash_attn_with_kvcache（这个函数对paged attention做了一个特殊的支持），prefill的时候用的是flash_attn_varlen_func。

也就是说paged attention只有decode的时候才用，为什么？

这里猜测，跟paged attention的特点有关。<br>paged attention，最大的意义在于，内存分散且不连续的情况下，能更好的打满内存。prefill的内存相对确定，decode的内存没那么确定，paged attention就会变得很好用。

flash_attn_varlen_func本身的价值是通过打平成1 dimension把padding干掉，所以很适合prefill阶段使用。decode则使用paged attention来提高效率(flash_attn_with_kvcache)<br><br>但工业界最近prefill的时候也在考虑用paged attention。因为线上请求长度变化很大，真长文下不page attention没事，长文夹短文就亏了，多攒点batch还是好的，但是prefill page attention肯定不会像decode block那么小了。

所以，还有很多不确定性和可优化点。
