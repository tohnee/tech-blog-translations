做 NPU 的厂商这两年陆续往 vLLM 上接，发布稿里「支持 vLLM」几乎成了标配的一行。这句话听起来特别美好：vLLM 的模型支持更新得勤，社区一有新模型就跟上，接进去应该能跟着享受这份速度。**可是，是否只要接入了 vLLM 就能享受官方的模型支持？为了这份支持，又需要付出什么代价？**

这篇漫谈分析十一家接入了 vLLM 的 NPU 厂商的源码，总结各家做法的异同，从实证的角度具体地评估接入 vLLM 的得与失。

先请这十一家厂商依次入场，排名不分先后：

| 厂商 | 芯片 | 背景 |
| --- | --- | --- |
| 华为 Ascend | 昇腾 910B / 910C / 310P | 达芬奇架构，训练和推理都做。一个插件要覆盖三代芯片加多种卡型 |
| AWS Neuron | Trainium / Inferentia2 | 云厂商自研自用，只服务自家实例 |
| Rebellions | ATOM / REBEL | 韩国 NPU 初创，芯片专为 LLM 推理设计，配套自己的编译器 optimum-rbln |
| Intel Gaudi | Gaudi2 / Gaudi3 | Intel 收购 Habana 得来的产品线，带 HBM，形态最接近 GPU |
| 寒武纪 | MLU370 / MLU590 | 国内较早做通用 AI 加速卡的一家，BANG C 编程模型刻意对齐 CUDA |
| 后摩智能 | 漫界 M50 | 国内存算一体初创，面向端边大模型推理 |
| 阿里 PPU | 真武 810E / M890 | 平头哥的数据中心加速器，走源码级 CUDA 兼容路线，工具链和 CUDA 一一对应 |
| IBM Spyre | AIU | IBM 自研的推理加速器，走自家的 fms 建模栈 |
| 高通 Cloud AI 100 | 基于 NSP 的推理卡 | 手机 SoC 之外的数据中心线。仓库在 qualcomm 组织下，不在它惯用的 quic 组织里 |
| Tenstorrent | Wormhole / Blackhole | 「硅仙人」Jim Keller 那家，RISC-V 内核加 Tensix 张量引擎，靠 2D mesh 互联组设备网格 |
| Intel OpenVINO | 不绑单颗芯片 | Intel 的跨硬件推理引擎，同一套插件覆盖 CPU、GPU 和 VPU |

## NPU 的官方入口和花式用法

vLLM 把自定义 NPU 设备有关的入口集中到一个类上，叫 Platform。厂商接一个新设备，就继承它，再在自己 package 的元数据里声明一个 `vllm.platform_plugins` 的 setuptools entrypoint，返回这个子类的路径字符串。vLLM 启动时会扫描这个 entrypoint，如果扫描到了，之后凡是和设备有关的问题都来问这个类：用哪个 Worker、哪个 attention 后端、KV cache 的 block 多大、要不要做图编译。这类挂在官方仓库外面的后端在 vLLM 的用词里叫 OOT，out-of-tree。下文把 vLLM 官方仓库简称上游。

Platform 子类上有三个 vLLM 重点关注的字段：

- `_enum`：vLLM 内部有若干处「如果是树外设备就走这条分支」的判断，看的就是它。
- `dispatch_key`：PyTorch 的调度键，决定算子分派到哪一套实现上。PyTorch 给树外设备留了一个通用键 `PrivateUse1`，已经在 PyTorch 里注册过的设备则填自己那个键。
- `device_type`：PyTorch 设备命名空间的名字。vLLM 取设备属性时走的是 `getattr(torch, device_type)`，填 `cuda` 就去取 `torch.cuda` 下面的东西，填 `npu` 就去取 `torch.npu`。它还直接当分配张量时的 `device=` 字符串用，以及拼分布式后端的名字。

各家怎么填这三个字段，方法五花八门。最规范的是 Gaudi：`_enum` 如实填 `PlatformEnum.OOT`，`device_type` 如实报 `hpu`，`dispatch_key` 用 PyTorch 里已有的 `HPU` 键。读它的插件不需要额外推测，声明写的就是它做的。

`_enum` 上，十一家里九家如实填 `PlatformEnum.OOT`，另外两家各往一个方向偏：OpenVINO 填 `PlatformEnum.CPU`，vLLM 于是把它当本机 CPU 对待；阿里 PPU 填 `PlatformEnum.CUDA`，那些树外分支一处都不会走到，整条 CUDA 原生路径照常执行。

花样最集中的是 `device_type`：十一家里有六家把它硬编码成 `cpu`，效果是让 vLLM 去取 `torch.cpu` 下的属性、把张量分配在主机内存上。对于自己管显存、或者没在 PyTorch 侧注册过设备命名空间的厂商，这正是想要的效果：让 vLLM 别把张量放到一个它不认识的设备上，搬运交给厂商自己的 runtime。六家各自的情形见备注。

## 接入 vLLM 具体要接什么？

Platform 回答的是配置问题，真要落地需要考虑如何定制七个组件。

| 组件 | 在 vLLM 软件栈中的作用 | 必须自己写吗 |
| --- | --- | --- |
| Platform | 声明设备，回答一组配置问题 | 必须，不提供 vLLM 认不出这个设备 |
| Worker | 设备初始化、显存探测、加载权重 | 必须，设备初始化各家完全不同 |
| ModelRunner | 组输入张量，执行一步前向 | 必须，没人替厂商做这件事 |
| AttentionBackend | attention 的实现，以及 KV cache 的布局 | 看做法，这一行是分界线 |
| 算子层 | 替换 model_executor 里那批层 | 可选，vLLM 有一套注册机制备着 |
| Scheduler | 自定义调度约束 | 可选，但静态形状会把它变成必需 |
| 采样 | 从最后一层 hidden states 出新 token | 可选，十一家里八家一行不改 |

前三行没有选择，后四行各家怎么选各不相同，归拢起来大概是三种做法，后面按这三类分别介绍。

## 接入 vLLM 的三种姿势

vLLM 的七个组件里有四个写着可选，看着设计空间不小。但如果把十一家 NPU 厂商的方案都翻看一下，这四项的选法大半在动手写插件之前就被厂商的工具链锁定了：工具链的软件栈一般分为编译器、runtime 和 SDK，这套软件栈把哪些事情留在自己手里，vLLM 侧就只能动剩下的那些。

具体来说，决定因素落在工具链如何处理下述问题：

- 什么需要在编译期固化
- 设备内存归谁管
- SDK 对齐到 vLLM 软件栈的哪一层

下面具体看看各家厂商的不同选择：

| 工具链的能力或约束 | 厂商 | 对接入的影响 |
| --- | --- | --- |
| batch 和序列长度在编译期固定 | Spyre、Neuron、Rebellions 默认路、高通 AOT、后摩 | 模型连权重一起交给编译器，vLLM 侧拿不到 attention，load_model 无事可做。静态形状还把 Scheduler 从可选变成必需 |
| 并行度随核数和芯片数定，运行期不可调 | Neuron、后摩 | 并行配置成了编译期参数，vLLM 的并行度只能跟着产物走 |
| 设备内存由厂商 runtime 管，vLLM 不碰显存 | Tenstorrent、后摩 | KV cache 的分配权不在 vLLM 这一侧，它那套按剩余显存算 block 数的逻辑空转 |
| SDK 自带 PyTorch 算子层 | Ascend、Gaudi、Rebellions 开关路、高通 PyTorch 模式 | 算子级替换有落点，可以留在 vLLM 的模型脚本里只换几十个层 |
| SDK 的 runtime 接口与 CUDA 高度相似 | 寒武纪、阿里 PPU | 可以直接继承 vLLM 的 CUDA 实现，改硬件参数或打补丁；PPU 做到源码级兼容，连 Platform 类一起继承 |

- 前三行约束导向同一个结果：模型整体交出去。
- 后两行相反，替换能落在层这一级，则可以复用 vLLM 的模型脚本，其中接口像 CUDA 的那一行还能再往上，直接继承现成实现。

稍微总结一下各家厂商的做法，实际可以归为如下三类。注意十一家厂商实际走出十三条路径：Rebellions 和高通各维护两条独立的栈，各有自己的 Worker、ModelRunner 和 Scheduler，用环境变量或者装没装某个运行时库来选，两条路径分属不同的类。

| 做法 | 路径数 | 七个组件怎么改 |
| --- | --- | --- |
| 整图编译，绕过 vLLM 算子层 | 7 | attention 不提供或者只留一个不干活的壳，算子层不参与，ModelRunner 往往没有基类，强制 eager |
| 替换 attention 和算子 | 4 | 用 vLLM 的模型脚本，自己写 attention 后端，用注册机制换掉几十个层 |
| 继承上游 CUDA 实现再改 | 2 | attention 和 Worker 都继承上游 CUDA 的实现，靠劫持或补丁改行为；PPU 连 Platform 类本身一起继承，七个组件一个都不自己写 |

![](https://pica.zhimg.com/v2-046dcf9aff8186ad5da399c0a1a50146_r.jpg)

### 整图编译：架空vLLM的模型和kv管理

这一类的有七种实现，模型先被厂商自己的编译器编成产物，服务时加载的是产物而不是权重文件：

- Spyre、Tenstorrent、OpenVINO、Neuron、后摩
- Rebellions 的默认路径、高通的 AOT 模式

![](https://pic2.zhimg.com/v2-0580b4a9f2f2336d8943ec8f8b80a9d5_r.jpg)

七家的编译器虽然各不相同：`torch_sendnn`、tt-metal、Optimum、NEFF、QEfficient、后摩大道。但在 vLLM 这一侧的表现高度一致，说明这类做法有稳定的形态可循。

当然，vLLM完全不管模型的代价是巨大的，整体的能力直接被厂商工具链锁死：

- OpenVINO ：并行度必须为一、不支持 LoRA、attention 主要方法直接抛未实现、强制 eager。
- Spyre 和后摩 ：显存和 KV cache 规格都虚报，内部相对固定地管理kv cache等资源池，vLLM调度被架空。
- Tenstorrent ：罕见地支持kv cache的block语义，但是内部管理具体kv的gather，vLLM看不到。

### 替换 attention 和算子：狸猫换太子

走这条的有四种实现：

- Ascend、Gaudi
- Rebellions 打开开关那条、高通的 PyTorch 模式

能走这条路的前提是厂商侧有一个 PyTorch 算子层可以落点。有了这一层，替换可以走 vLLM 为树外算子准备的两套注册机制：`CustomOp.register_oot` 换掉层一级的类，`direct_register_custom_op` 把自家的 Python 或 Triton 实现注册成 `torch.ops.vllm` 下的算子。四家里只有 Gaudi 单用前一套，二十九处装饰器；Ascend 和 Rebellions 的重心在后一套，分别十七处和二十处。没有这一层，算子级替换无从谈起。

Ascend 有 CANN 和 `torch_npu`，Gaudi 有 `habana_frameworks.torch`，高通有 `torch_qaic`。

![](https://pic1.zhimg.com/v2-3bd6de1e8429908b981f027717f0d1a6_r.jpg)

### 继承上游 CUDA 实现再改：寒武纪和阿里 PPU

走这条的有两种实现，接入需要的改动量最小的：

- 寒武纪 ：attention 后端继承上游 CUDA 的 `FlashAttentionBackend` 而不是抽象基类，Worker 继承 vLLM 的 GPU `Worker`，六百多行，ModelRunner 的文件名还保留着 `gpu_worker`。不走这条路线的其余九家，Worker 都是从 `WorkerBase` 起从零写的。
- 阿里 PPU ：它继承的是 Platform 类本身，`PPUPlatform` 的基类就是上游的 `NvmlCudaPlatform`。七个组件里它只写了 Platform 一个，Worker、ModelRunner、Scheduler、attention 后端全用上游的，Executor 一处不碰。

这条路省事，但前提都是厂商的 runtime 接口做得够像 CUDA：

- MLU 的 runtime 接口跟 CUDA 接近，`torch.mlu` 模仿 `torch.cuda` 的接口。替换靠一个自建的劫持框架，全仓一百二十五处调用点。
- PPU 更极致，它做到了源码级的 CUDA 兼容，于是把 `_enum` 填成 `PlatformEnum.CUDA`。源码注释管这个叫 compatibility declaration，并说明它是整个插件里最有后果的一个决定，理由两条：让 `is_cuda()` 为真，于是上游约两百零七处按 CUDA 分路的调用点行为正确；让 `is_out_of_tree()` 为假，于是四处抢在 CUDA 逻辑之前的树外短路会落到 CUDA 分支上。改行为全部交给补丁，六十五个补丁文件分三类，一个 bugfix、五十六个 enhancement、三个 performance。代价写在版本号上：钉死 vLLM `>=0.31.0,<0.32.0`，启动时校验。

## 接入工作量和新模型适配效率

分完三种姿势，我们再来横向对比下各家的接入成本，和实际新模型的接入效率，回答最开始我们提出的问题：

> 是否只要接入了 vLLM 就能享受官方的模型支持？为了这份支持，又需要付出什么代价？

| 厂商 | 芯片 | 运行时与编译器 | 代码量 |
| --- | --- | --- | --- |
| Ascend | 昇腾 910B / 910C / 310P | CANN + torch_npu | 141088 |
| Neuron | Trainium / Inferentia2 | Neuron Runtime + neuronx-cc | 76917 |
| Rebellions | ATOM / REBEL | RBLN Runtime + optimum-rbln | 76228（双路径合计，六个核心类各写两份共 8100） |
| Gaudi | Gaudi2 / Gaudi3 | Habana SDK + HPU backend | 62846 |
| 寒武纪 | MLU370 / MLU590 | torch_mlu（BANG C） | 43424 |
| 后摩 | 漫界 M50 | tcim_lite + 后摩大道 | 39980（插件本体 7265） |
| 阿里 PPU | 真武 810E / M890 | SAIL | 34160 加 23885 行 C++ |
| Spyre | AIU | IBM AIU Runtime + torch_sendnn | 37460 |
| 高通 | 基于 NSP 的推理卡 | QAIC Runtime / torch_qaic + QEfficient | 14767 加 2605 行 C++（ModelRunner 分路：AOT 1581、PyT 63） |
| Tenstorrent | Wormhole / Blackhole | tt-metal | 10346 |
| OpenVINO | 不绑单颗芯片 | OpenVINO Runtime + Optimum | 2466 |

代码量这一列有两处要说明。Rebellions 和高通各维护两条路径：

- Rebellions 可以拆到组件一级：ModelRunner 是走 vLLM 建模那条路 2980 行、走 optimum 预编译那条路 1720 行，Scheduler 是 1033 行和 687 行，两个 Worker 只有类名没记行数，所以六个核心类合计 8100 行里还有约一千七百行没有分路归属；
- 高通可以拆，它的 ModelRunner 两个类分属两条路径，**AOT 那个 1581 行、PyT 那个 63 行，差二十五倍**，原因是走编译产物要把 `GPUModelRunner` 做的事重做一遍，走上游建模能复用。

把这两家的分路数字放一起看，会推翻一个直觉。

- 高通是编译产物那条路更贵，ModelRunner 差二十五倍；
- Rebellions 反过来，走 vLLM 建模那条路反而更贵，四千多行对两千四百行。

差别不在走哪一类接入方式，在于**有没有继承上游的 ModelRunner**：高通那六十三行是继承 `GPUModelRunner` 之后只覆盖四个方法，Rebellions 那条路不继承，基类只有一个 mixin，源码注释写着「和上游的 GPUModelRunner 不同」，是照着它重写了一遍。同一类接入方式，一个复用一个重写，代价差一个量级。

后摩那一格有两个数，因为它三万九千多行里有三万两千多行在模型脚本目录，而那些类大部分看来是从社区中搬来的参考版本，实际上并没有被用到。

上游发一个新模型，各家多久能跑起来，取决于一件事：**新模型的建模代码从哪来**。按这一点，十一家分三种做法。

| 做法 | 谁 | 厂商侧建模文件 | 其中复用 vLLM 官方实现 |
| --- | --- | --- | --- |
| 复用上游建模，逐模型改 | Gaudi、Ascend、寒武纪、阿里 PPU、高通的 PyTorch 模式 | 31 / 18 / 8 / 13 / 0 | 25 / 9 / 3 / 13 / 全部 |
| 自带完整建模栈 | Neuron、Tenstorrent | 37 / 20 | 3 / 2 |
| 委托外部转换工具链 | Spyre、OpenVINO、Rebellions、高通的 AOT 模式 | 0 / 0 / 31 / 0 | — / — / 14 / — |

这三种做法和前面那三类接入方式强关联，关联还有机制：**attention 在哪里算，决定了建模代码必须从哪来：**

- 继承上游 CUDA 实现和替换 attention 这两类，attention 都在 vLLM 的算子层里算，建模就必须用上游那一份，于是一律落在复用上游建模。
- 整图编译那一类把模型整个交给编译器，建模代码得另找来源，于是散成两种：自带建模栈，或者委托外部工具链。

特别说明几点：

- Gaudi 那 31 个文件里有 25 个是从上游 import 之后改局部，是薄封装；Neuron 的 37 个里只有 3 个，是独立实现。**文件数接近，性质完全不同。**
- 0 也有两种含义。OpenVINO、Spyre、高通 AOT 那三个 0 是「建模在工具链里」，高通 PyTorch 模式那个 0 是「建模全用上游那一份」。同一个数字，一个绕开 vLLM 的建模层，一个完全依赖它。

复用上游建模这条，新模型上游合了就能跑，发布当天可达。代价是每个模型往往还要补一点厂商侧改动，而这部分会一直累积。Ascend 的四十三个补丁文件里有**十五个是为单个模型打的**，合计两千二百六十行，平均每个模型一百五十行。阿里 PPU 是第二个样本，十三个按模型打的补丁、两千四百七十二行，平均约一百九十行，量级相当。

自带建模栈这条，发布当天day0支持原理上做不到：上游的新模型不在自家目录里，就得自己实现一遍。Neuron 在这条路上做得最完整，一万八千多行按模型分子目录，另有四个公共文件把新模型要对接的接口面固定下来，还是十一家里唯一为「怎么加新模型」单独写了文档的。**它把加新模型的流程标准化了，让这件事能交给别人做，而不只是缩短单个模型的适配时间。**Tenstorrent 的建模工作量和它相当，区别在同步负担：它整仓 fork 了 vLLM，上游升级时要把改动合进 fork，而 Neuron 只需处理插件的接口面。

委托工具链这条，发布当天取决于工具链，不取决于厂商自己。OpenVINO 最彻底，建模文件零个，直接调 optimum-intel 加载。但 optimum-intel 的支持面是一张显式注册表，每个架构都要有人手写一个导出配置类注册进去，**未注册的架构直接抛异常，没有通用兜底**。主流模型基本都在表里，所以实践中够用，但新架构必须等 optimum-intel 先合，这一步不在厂商手里。

所以「多久能跑起来」这件事，三种做法的瓶颈不在同一处：复用上游的受限于自己的补丁跟不跟得上上游重构，自带栈的受限于自己实现的速度，委托工具链的受限于别人的发布节奏。

## 读后感

「vLLM 接入」表面看起来很美好，实际上有自己的开发代价，收益也是不确定的。几点具体的：

- 代价的量级由做法决定。十一家的插件从两千四百六十六行到十四万行，差五十七倍，都能跑通接入。做法又大半由厂商自己那套工具链软件栈决定：输入形状能不能动态、显存归谁管、权重能不能运行期加载、并行度是不是编译期固定，这几个问题的答案基本就把可选范围框定了。
- 最想要的那份收益只有算子层接入和继承CUDA实现两类做法拿得到。「上游合了新模型就能跑」要求建模代码用上游那一份，而这要求 attention 算在 vLLM 的算子层里。走整图编译的那七条路径，发布当天可达在原理上就做不到。
- 这份收益还要持续付出维护成本。复用上游建模的那几家，每个模型往往还要补一点厂商侧改动，这部分会一直累积：Ascend 四十三个补丁文件里有十五个是为单个模型打的。最贵的是直接给上游类的方法赋值那种，上游重构一次就得重新对一遍。

**所以，接入 vLLM，量力而为。**
