Transformer 结构自从问世以来，热度丝毫不减。现在已经有数不胜数的代码库教你从零搭建一个属于自己的 Transformer 结构，也有很多成熟的代码库提供了高度集成化、速度很快的 Transformer 实现。在这些代码实现中，Megatron-LM 不能说是速度最快的，但一定是 code 最复杂的。想在 Megatron-LM 里面自定义地修改一些模型参数，可谓是非常困难。

这篇文章主要针对 Megatron-LM 训练框架，介绍如何从简单到复杂搭建一个可训练的神经网络结构。由于 Megatron-LM 的结构十分复杂冗余，构建模型结构的方法千奇百怪，这一看似简单的步骤实际很容易踩坑，需要仔细斟酌。更进一步地，从做科研的角度出发，具体地介绍如何在 Megatron-LM 代码框架下更改模型结构，并尽可能地避免踩坑。

## 一、Megatron-LM 和模型结构相关的代码组织树

在开始之前，我们需要理解 Megatron-LM 复杂的代码结构。这个框架经历了多个版本的演进，因此存在多套并行的实现方式，这也是踩坑的重要原因。

**核心目录结构**

```json
megatron/
├── core/                    # 新版核心实现（推荐使用）
│   ├── models/             # 各种模型的实现
│   │   ├── gpt/           # GPT 系列模型
│   │   ├── mamba/         # Mamba 模型
│   │   └── multimodal/    # 多模态模型
│   └── transformer/       # Transformer 核心组件
├── legacy/                 # 旧版实现（逐步弃用）
│   └── model/             # 传统模型实现
└── training/              # 训练相关代码
```

**模型构建的入口文件**

> 注意：下列函数及行号来自于 2026 年 1 月份版本的 Megatron-LM，随着版本号的变动，具体函数的行数或者函数本身名字可能会有所变动，但大体的结构应该不会产生大幅变化

我们以训练经典 GPT 模型的入口文件 `pretrain_gpt.py `出发，这个文件位于 Megatron-LM 的根目录下。在这个文件里，有两个和模型构建相关的函数：`model_provider `和 `gpt_builder `的。这个 API 其实已经是更改过一次的，25 年直到 10 月份之前的版本，都只有 `model_provider `这一个函数，而如今的 `model_provider `已经变成了 `gpt_builder `的另一层封装。

- `model_provider.py` 根目录：**- 统一的模型提供接口**

这是整个 Megatron-LM 框架的**模型构建入口**，可以理解为一个"万能的模型工厂"。它接受任何模型构建器（如 `gpt_builder`、`mamba_builder `等）作为参数，并提供统一的调用接口，无论你要建什么模型都通过这个函数。此外，它还可以处理一些通用的配置（如内存监控、ModelOpt 优化等）

- `model_provider.py` 根目录：**- GPT 模型的专门构建器**

这是专门用于构建 GPT 模型的**具体实现**，是 `model_provider `会调用的实际构建器，支持从 YAML 或命令行参数加载配置，通过路径选择决定使用 legacy 还是 core 系统，根据不同需求选择合适的 transformer 层实现，最后执行模型实例化，创建最终的 GPT 模型对象

其实 Megatron-LM 的复杂构建分支在这里就可见一斑，在定义具体的**层规格**时（注意到 Megatron-LM 里面**层规格**和 **GPT 模型规格**定义是不一样的，两者有单独的修改逻辑），Megatron-LM 会提供很多层规格定义的选项：

- 如果指定了自定义规格 → 使用 `args.spec`
- 如果启用了 MoE → 使用 `get_gpt_decoder_block_spec()`
- 如果有异构层配置 → 使用 `get_gpt_heterogeneous_layer_spec()`
- 其他情况 → 调用`_get_transformer_layer_spec()`

其中`_get_transformer_layer_spec()` 函数是一个**层规格选择器**，根据配置参数决定使用哪种 transformer 实现，有**三种主要路径**（后面会细说）：

1. **Transformer Engine 路径** (`config.transformer_impl == "transformer_engine"`)：高性能 GPU 优化实现，也是本篇文章的重点
2. **推理优化路径** (`config.transformer_impl == "inference_optimized"`)：专门为推理场景优化，这里不过多提及
3. **本地实现路径** (`config.transformer_impl == "transformer_engine"`)：标准 PyTorch 实现，比较适合验证一些小规模的模型改动

⚠️ **第一个重要避坑点：选择正确的构建路径**

Megatron-LM 有两套并行的模型构建系统：

1. **新版 core 系统**：位于 `megatron/core/`，功能更完善
2. **旧版 legacy 系统**：位于 `megatron/legacy/`，兼容性更好

关键的控制开关是 `--use-legacy-models` 参数。**如果你修改了 core 系统的代码，但启动时使用了 legacy 模型，你的修改不会生效！**

```text
# gpt_builders.py 第 43 行
if args.use_legacy_models:
    model = megatron.legacy.model.GPTModel(...)  # 走旧版路径
else:
    model = GPTModel(...)  # 走新版路径
```

而且，实际的模型是在 `megatron/training/training.py `里面 build 的，但模型定义的函数却是在上面说到的其他不同的文件里，这很可能会导致初学者想改模型结构却不知道该从何改起。

## 二、Megatron-LM 构建标准 Transformer

Megatron-LM 的 Transformer 构建过程可以分为 4 个主要步骤：**参数解析与配置** → **层规格定义** → **模型实例化** → **权重初始化。**我们一步一步来看这个复杂的过程：

### 2-1 关键文件和类的作用

从逻辑来看，一个完整的 GPT 模型，一开始是编码 input 的词嵌入层（`TextEmbedding`），然后是主体的 Transformer 块（包含若干 Transformer layers），最后是将隐状态编码出 output 的输出层（`LM head`）。虽然整体是一个嵌套的结构，但正如上面所说的，Megatron-LM 把这几部分的代码放到了不同地方，而不是在一个文件内进行直观的定义展开（这是 huggingface transforers 库的定义逻辑），所以学习起来还是需要仔细一些观察：

**1. GPT 模型主类**

- 文件：`megatron/core/models/gpt/gpt_model.py`
- 主类：`GPTModel`
- 作用：整合嵌入层、Transformer 块和输出层

```text
# GPTModel.__init__ 的核心组件构建
self.embedding = LanguageModelEmbedding(...)     # 词嵌入
self.decoder = TransformerBlock(...)             # 主体结构  
self.output_layer = tensor_parallel.ColumnParallelLinear(...)  # 输出层
```

举个简单的例子，如果需要改动词嵌入层，或者更改输出层，则需要从这个文件内进行修改，或者定一个新的 `class MyGPTModel`。 改动主要分为两个部分，一是改动初始化内容，此时修改 `def __init__()`函数；二是改动前向传播方案，此时修改 `def forward()`函数。什么？你说你要改动反向传播函数？啊那太难了，这篇文章没法讲这么细 hhh。但也是可以改动的，改动很小的话则一般来说 torch 的 autograd 机制可以处理，否则需要覆写 `torch.autograd `函数，然后将此算子暴露出来从 Megatron 端进行引用。

**2. Transformer 块**

- 文件：`megatron/core/transformer/transformer_block.py` **（注意子文件夹和上面不同）**
- 主类：`class TransformerBlock`
- 作用：管理多个 Transformer 层的堆叠

如果需要改动不同 layers 之间的计算逻辑，或者采用 mamba-transformer 或者 MLP-MoE 混合堆叠的这种 layers 模式，则可以考虑从这个文件内进行修改。

**3. Transformer 层**

- 文件：`megatron/core/transformer/transformer_layer.py`
- 主类：`TransformerLayer`
- 作用：实现单个 Transformer 层（注意力+MLP）

如果需要改动层内的计算逻辑，例如 pre-norm 和 post-norm 的计算顺序，attention/mlp 的连接计算等，则可以考虑从这个文件内进行修改

再往下，则涉及到具体的 attention 模块，mlp 模块这类，则逻辑开始换为新的一套。这需要我们了解 Megatron-LM 的一个重点设计——**层规格定义**：

### 2-2 层规格定义与模块化设计哲学

在 Megatron-LM 中修改模型结构需要理解其模块化的设计哲学。整个模型通过“**规格(Spec)**”系统来定义，这让我们可以灵活地替换各个组件。文件位置：`megatron/models/gpt/gpt_layer_specs.py`

刚刚我们提到了 GPT 模型 - Transformer 块 - Transformer 层的结构。再往下，模型就会被分解成一个一个具体的小模块（attention，layernorm, mlp, moe 等等），可以看成是整个大 Transformer 的一个个配方。这个文件是 Megatron-LM 架构中的**“配方书”**，它定义了如何组装不同类型的 Transformer 层。可以说，这是整个模型构建系统中最核心的文件之一。这个文件的核心作用有两点：

1. **层规格定义的中央厨房。**这个文件就像一个中央厨房，提供了各种“配方”来组装 Transformer 层。每个函数都代表一种不同的“烹饪方法”。三种主要的配方，对应前文提及的层规格选择器里的 **TE 实现**、**本地实现**和**推理端实现**：

```text
get_gpt_layer_with_transformer_engine_spec()  # TE 高性能版本
get_gpt_layer_with_inference_spec()           # 推理优化版本  
get_gpt_layer_local_spec()                    # 标准 PyTorch 版本
```

**2. Backend 抽象系统的实现。** Backend 系统让代码可以支持多种不同的**底层实现**：

- **TESpecProvider**: 使用 NVIDIA Transformer Engine 的高性能实现
- **LocalSpecProvider**: 使用标准 PyTorch 算子
- **InferenceSpecProvider**: 专门为推理优化的实现
- **KitchenSpecProvider**: 使用 NVIDIA Kitchen 库的实现

使用这种层规格定义的一个非常经典的本地 Transformer layer 的定义：

```python
        return ModuleSpec(
            module=TransformerLayer,
            submodules=TransformerLayerSubmodules(
                input_layernorm=layer_norm,
                self_attention=ModuleSpec(
                    module=SelfAttention,
                    params={"attn_mask_type": AttnMaskType.causal},
                    submodules=SelfAttentionSubmodules(
                        linear_qkv=backend.column_parallel_linear(),
                        core_attention=backend.core_attention(),
                        linear_proj=backend.row_parallel_linear(),
                        q_layernorm=(
                            L2Norm if qk_l2_norm else (qk_norm if qk_layernorm else IdentityOp)
                        ),
                        k_layernorm=(
                            L2Norm if qk_l2_norm else (qk_norm if qk_layernorm else IdentityOp)
                        ),
                    ),
                ),
                self_attn_bda=get_bias_dropout_add,
                pre_mlp_layernorm=layer_norm,
                mlp=mlp,
                mlp_bda=get_bias_dropout_add,
                sharded_state_dict_keys_map={
                    "input_layernorm.": "self_attention.linear_qkv.layer_norm_",
                    "pre_mlp_layernorm.": "mlp.linear_fc1.layer_norm_",
                },
            ),
        )
```

不管你用 TE 还是本地实现，不管你要 MoE 还是标准 Transformer，都通过同一套接口来定义。当熟悉这种设计后，切换实现就变得非常简单。例如，**想换激活函数**，则可以修改 `MLPSubmodules `中的 `activation_func`。想更换 linear 层的实现，可以修改上面定义里的 `linear_qkv`, `linear_proj `等。**想加新的 attention 机制**，则可以自定义新的 `SelfAttentionSubmodules`，并在此文件中进行引用。**想实现异构层**，则可以参考 `get_gpt_decoder_block_spec `的层模式处理。

### 2-3 参数传递的复杂链路

为了更精确地操控模型结构，Megatron-LM 提供了大量的以命令行形式进行的参数控制选项，可以参考 `megatron/training/argument.py `文件。从命令行参数到最终模型的参数传递，经历了多个转换阶段：

1. **arguments.py**：命令行参数解析
2. **core_transformer_config_from_args()** ：转为 TransformerConfig
3. **TransformerConfig.post_init()** ：配置预处理和验证
4. **各模块的 init()** ：最终参数应用

值得注意的是，（几乎）所有和模型结构相关的参数，会被先整理成一个统一的 `TransformerConfig`，这个类的定义在 `megatron/core/transformer/transformer_config.py` 里。这里又涉及到一个大坑：

⚠️ **第二个重要避坑点：参数传递的多重变换**

由 high-level option 导致的一些子 argument 的变化，有些是在 `argument.py `里面完成的，有些（和模型相关的）是在 `argument.py `转 `TransformerConfig `时完成的（大部分和模型相关的 option 是走这里进行的）。

**但尤其要注意的是**，有些是直接在 `TransformerConfig `里面做 pre-check 时完成的，有些又是直接在对应模块里面 init 甚至 forward 时候完成的。例如在 `TransformerConfig `类里的`__post_init__`方法中，如果未设置 `ffn_hidden_size `时，会将其自动设置为 `hidden_size `的四倍。如果使用了门控的激活函数，例如 `GLU `或 `SwiGLU `时，`ffn_hidden_size `又会自动乘 2 因为 MLP 的前半部分会有两个 Linear 层，但这个过程不是在 `TransformerConfig `里面做 pre-check 时完成，而是在 MLP 模块里初始化时完成的。

类似的这种自动校验情况非常多，我们很难从代码层面上完整地检测到其正确性。所以我极度建议从端到端的角度，直接将模型构建好之后再做校对验证，发现问题之后再回过头去检查修改。

### 如何验证模型构建是否正确

在实战中，一个比较常见的方式是通过 `print `函数打印出模型的具体结构，来验证模型的构建是否正确。这段打印的代码并没有在 Megatron-LM 中被默认写出，所以可能需要手动加上

```text
# 在训练脚本中添加调试代码
print(f"Model structure: {model}")
print(f"Total parameters: {sum(p.numel() for p in model.parameters())}")
print(f"Config: {model.config}")
```

## 三、Megatron-LM 结合 Transformer Engine 的模型构建

Transformer Engine (TE) 是 NVIDIA 提供的高性能 Transformer 实现，可以显著加速训练。尤其是，如果想使用 Nvidia 的高性能显卡如 H 卡、B 卡内的低精度数据格式内核（例如 FP8/FP4 Tensor Core），则非常建议使用 TE。

Megatron-LM 对于 TE 的支持已经比较成熟。核心控制机制在于开启关键参数：`--transformer-impl` (可选值: `transformer_engine` 或 `local`)

- 文件：`megatron/core/extensions/transformer_engine_spec_provider.py`
- 函数：`get_gpt_layer_with_transformer_engine_spec()`

一个常见情景是，开发过程在简单的 local 实现基础上验证正确无误后，想要切换到 TE 上实现更高的计算性能。此时需要仔细留意两种实现方式的差异：

Transformer Engine 版本

```text
# 使用融合的高性能算子
self_attention = TELayerNormColumnParallelLinear  # TE 融合 Linear
mlp = TEFusedMLP                                  # TE 融合 MLP
input_layernorm = TENorm                          # TE LayerNorm
```

本地实现版本

```text
# 使用标准的 PyTorch 算子
self_attention = ColumnParallelLinear             # 标准 Linear
mlp = MLP                                         # 标准 MLP
input_layernorm = FusedLayerNorm                  # 标准 LayerNorm
```

TE 实现和本地实现会有兼容性问题。TE 和本地实现的某些函数接口 API 不完全一致，比如上面提到的 Linear, Layernorm, MLP 等。也正是因为两者的权重存储格式可能不同，加载 checkpoint 时需注意。而且某些新功能可能只在 TE 实现中支持。为了确认当前的代码确实使用了 TE 格式而不是本地格式，建议采用简单代码进行验证：

```text
# 在模型构建后打印层信息
for name, module in model.named_modules():
    if 'attention' in name:
        print(f"{name}: {type(module)}")
        break
```

如果看到 `TransformerEngine` 相关的类名，说明使用的是 TE 实现。

如果你是从本地格式实现切换至 TE 格式实现，则需要注意：切换实现通常需要从头训练，或者转换 checkpoint 格式。虽然一般情况下 TE 实现会显著快于本地实现，但性能表现在不同硬件上可能有差异。而且，确保你需要的功能在选择的实现中都支持，有的时候修改 TE 会过于复杂，此时重新切换回本地格式的实现可能更有利于进行自身代码改动的验证。

在细节上修改 TE 类的算子，比较复杂。主要参考 `megatron/core/extensions/transformer_engine.py` 这个文件。这个文件是 Megatron-LM 与 **Transformer Engine (TE)** 集成的**核心桥梁**，可以说是整个高性能训练系统中最重要的文件之一。它的作用就像一个"翻译器"，让 Megatron-LM 能够无缝使用 NVIDIA Transformer Engine 的高性能算子。它将 TE 的各种高性能算子包装成 Megatron-LM 能理解的接口：

```json
# 主要的封装类
TENorm                           # 高性能 LayerNorm/RMSNorm
TELinear                        # 基础 Linear 层
TEColumnParallelLinear          # 列并行 Linear 层  
TERowParallelLinear            # 行并行 Linear 层
TELayerNormColumnParallelLinear # 融合 LayerNorm+Linear 层
TEDotProductAttention          # 高性能 FlashAttention
```

此外还提供了量化训练的完整支持。`TEQuantizationRecipe `定义单个量化"配方"，如 FP8 量化：`fp8_quantization_recipe`；FP4 量化：`fp4_quantization_recipe`；自定义量化：`custom_recipe_factory`。而 `TEQuantizationParams `支持训练/推理不同精度，例如训练时用一套量化策略，推理时用另一套量化策略。

实战中，一般会将上面的 TE 封装类，直接替换掉经典 Transformer Layer 中的各个组件模块，例如使用 `TEColumnParallelLinear` 替换 MLP 的第一个 Linear，`TERowParallelLinear `替换 MLP 的第二个 Linear（至于 Column 和 Row 的区别，会在后面讲 Megatron 并行的时候具体分析）。更特殊地，一般来说第一个 Linear 会进一步被替换为 `TELayerNormColumnParallelLinear`，因为计算此 Linear 之前还要再计算一个 Layernorm，TE 默认会将这两个层 fuse 在一起，以取得更好的性能。当然这里也有个坑，如果你要替换为你自己的 `MyTELinear`，那么记得这里也要实现和 Layernorm 的 fuse，或者把这里默认的写法解耦出来，单独把 Layernorm 加回来！

## 总结

写到这里，相信大家对 Megatron-LM 的复杂架构已经有了一个清晰的认识。回想起刚开始接触这个框架时的困惑，其实很多问题都源于对其设计思路的不理解。**Megatron-LM 之所以复杂，很大程度上是因为它承载着历史的包袱，不会去做额外的清理。**新版的 core 系统代表着未来的方向，功能更丰富、设计更合理；而 legacy 系统则是为了兼容旧代码而保留的。很多初学者（包括我自己）都经历过，明明按照教程修改了代码，却发现训练出来的模型完全没有变化。后来才发现，原来是修改了 core 系统的代码，但启动参数却指向了 legacy 系统。而且随着 Megatron 系统的逐渐庞大，越来越多的实现都会集成进其中，“修改无效”的问题在实际开发中非常常见，所以一定要在开始前确认清楚自己走的是哪条路。

Megatron-LM 的模块化设计其实很优雅，但需要你有清晰的层次化思维。如果是在比较 high-level 的改动，例如跨层连接、改变注意力和 MLP 的组合方式，就在 TransformerBlock 层面和 TransformerLayer 层面进行改动。如果是 low-level 的修改如想要修改具体的计算逻辑，则需要直接改对应的组件类。这种分层的修改策略看起来复杂，但一旦掌握了就会发现其实很有条理。

代码改完了不代表就成功了，验证环节同样重要。打印模型结构是最直观的方法，能立刻看出你的修改是否生效；检查参数数量能发现一些隐蔽的问题，比如 MLP 结构改了但参数数量没变；跑个小规模的前向传播测试则能确保修改后的模型至少不会报错。这三个验证步骤虽然简单，但能帮你及早发现问题。当遇到问题时，不要急着翻代码找 bug。先在关键位置加几个 print 语句，追踪一下参数的流向，往往能快速定位问题所在。如果想要更直观地了解模型结构，可以试试用 `torch.onnx.export()`导出个结构图，有时候一张图胜过千行代码。另外，对比修改前后 checkpoint 文件的大小也是个简单有效的验证方法，参数数量变了，文件大小肯定也会变。

**写在最后的话**

在模型预训练的过程中，除了模型构建，还有很多很复杂的工作，比如训练时的参数设置，优化器的建立，学习率的设置，模型并行的调节，checkpoint 检查点的保存与评估等等……不过，这些流程虽然复杂，但它们的实现都离不开本文介绍的这些基础概念。就像盖房子一样，地基打不牢，再华丽的装修也立不住。掌握了模型搭建的基本原理，理解了 Megatron-LM 的设计哲学，后面学习这些其他特性就会顺利很多。

最后想说的是，Megatron-LM 确实是个复杂的框架，刚开始接触时被它的代码组织吓到是正常的。但正如我们在文章中反复强调的，**理解架构比记住 API 更重要，验证修改比相信代码更关键**。只要抓住了这两个核心原则，再加上一些耐心和实践，相信大家都能在这个复杂的代码迷宫中找到属于自己的路径。

希望这篇文章能帮到正在与 Megatron-LM”搏斗”的你，也希望你能少走一些我们曾经走过的弯路。记住，每一次踩坑都是成长的机会，关键是要从中吸取经验，避免在同一个地方跌倒两次。
