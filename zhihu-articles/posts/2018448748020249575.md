### 1. RDMA 是什么

RDMA全称 Remote Direct Memory Access， 直接访问远程内存。允许两台机器进行直接的内存到内存的传输，路径不需要操作系统，CPU等参与，整个过程由网卡完成，零拷贝，完全bypass，协议卸载到网卡。

RDMA是一种能力，或者说语义。具体实现目前又分为几类

1. InfiniBand：全套自有链路层 + 网络层 + 传输层
2. RoCEv2（目前数据中心最主流）：RDMA 传输层跑在 UDP/IP + 以太网 之上
3. AWS的EFA, Google的Falcon，阿里云的erdma，兼容大部分，有些细节不太一样，我们用不太到，忽略

而libibverbs 是 RDMA 编程的用户态核心库，提供了一套统一的 C API（叫 verbs API），让应用程序可以操作 RDMA 硬件，而不用关心底层是 InfiniBand、RoCE 还是 iWARP。

整体堆栈大概是这样的

```text
┌─────────────────────────────┐
│  应用程序 (比如 NCCL, SPDK) │
├─────────────────────────────┤
│  上层抽象 (libfabric / UCX) │   ← 可选，有些应用直接调 verbs
├─────────────────────────────┤
│  libibverbs                 │   ← 用户态核心库，定义 verbs API
├─────────────────────────────┤
│  provider 驱动插件           │   ← 比如 libmlx5 (Mellanox/NVIDIA)
│  (用户态驱动)               │     通过 libibverbs 的 provider 机制加载
├─────────────────────────────┤
│  内核驱动 (mlx5_ib 等)      │   ← 只做最少的事：建连接、注册内存等控制面
├─────────────────────────────┤
│  RDMA 网卡硬件              │
└─────────────────────────────┘
```

所以后文介绍的RDMA编程都是基于libibverbs这个库。

### 2. 一次 RDMA 传输的完整流程

整体流程类比于读写一个文件

1. 我们需要知道有什么磁盘，磁盘上有什么文件
2. 打开文件，拿到handle（也就是fd）
3. 基于这个fd，如果要读取的话，我们要分配缓冲区，然后调用read
4. 使用完毕我们close对应handle

先看全貌，再逐个展开。

```text
┌─────────────────────────────────────────────────────────────────┐
│ 1. 发现设备    ibv_get_device_list → ibv_open_device → Context  │
│ 2. 创建资源    Context → PD → { MR, QP, CQ }                   │
│ 3. 建立连接    交换寻址信息 → QP 状态机 INIT → RTR → RTS         │
│ 4. 传输数据    post RDMA_WRITE / RDMA_READ → poll CQ            │
│ 5. 清理        deregister MR → destroy QP/CQ → dealloc PD       │
└─────────────────────────────────────────────────────────────────┘
```

对应到代码大概长这样（伪代码，省略错误处理）：

```text
// 1. 发现设备
struct ibv_device **dev_list = ibv_get_device_list(NULL);
struct ibv_context *ctx = ibv_open_device(dev_list[0]);

// 2. 创建资源
struct ibv_pd *pd = ibv_alloc_pd(ctx);
struct ibv_cq *cq = ibv_create_cq(ctx, 16, NULL, NULL, 0);

struct ibv_qp_init_attr qp_attr = {
    .send_cq = cq,  .recv_cq = cq,
    .qp_type = IBV_QPT_RC,
    .cap = { .max_send_wr = 16, .max_recv_wr = 16,
             .max_send_sge = 1, .max_recv_sge = 1 },
};
struct ibv_qp *qp = ibv_create_qp(pd, &qp_attr);

void *buf = malloc(4096);
struct ibv_mr *mr = ibv_reg_mr(pd, buf, 4096,
    IBV_ACCESS_LOCAL_WRITE | IBV_ACCESS_REMOTE_WRITE | IBV_ACCESS_REMOTE_READ);

// 3. 建立连接（通过带外通道交换 gid/lid/qpn/psn，然后推 QP 状态机）
//    modify_qp: RESET → INIT → RTR → RTS  （详见第 6 节）

// 4. 传输数据 — 以 RDMA_WRITE 为例
struct ibv_sge sge = { .addr = (uint64_t)buf, .length = 4096, .lkey = mr->lkey };
struct ibv_send_wr wr = {
    .opcode     = IBV_WR_RDMA_WRITE,
    .send_flags = IBV_SEND_SIGNALED,
    .sg_list    = &sge,
    .num_sge    = 1,
    .wr.rdma    = { .remote_addr = remote_addr, .rkey = remote_rkey },
};
struct ibv_send_wr *bad_wr;
ibv_post_send(qp, &wr, &bad_wr);

// poll 完成
struct ibv_wc wc;
while (ibv_poll_cq(cq, 1, &wc) == 0) ;  // 等完成
assert(wc.status == IBV_WC_SUCCESS);

// 5. 清理
ibv_dereg_mr(mr);
ibv_destroy_qp(qp);
ibv_destroy_cq(cq);
ibv_dealloc_pd(pd);
ibv_close_device(ctx);
```

### 3. 资源层级：从设备到队列

![](https://pic2.zhimg.com/v2-820ef4c1b8ecf712b08f156eca2a94fb_r.jpg)

```text
ibv_get_device_list
 └─ ibv_open_device → Context
     └─ alloc_pd → PD (保护域，资源隔离的 namespace)
         ├─ reg_mr → MR (注册内存，让网卡能直接 DMA 访问)
         ├─ create_cq → CQ (完成队列，网卡写入完成/失败事件)
         └─ create_qp → QP (队列对，需要先有 CQ 才能创建)
```

### 3.1 Protection Domain (PD)

**保护域** 将 QP、MR（内存区域）、MW（内存窗口）关联在一起。只有同一个 PD 下的资源才能一起使用，起到隔离保护的作用。

类似多租户隔离里的 namespace，PD 活着的时候 Context 不能关。PD的作用非常简洁，只有两个用：

1. 注册内存
2. 创建 QP

除此之外没有其他作用。

### 3.2 Memory Region (MR)

RDMA 的核心能力是让对端直接读写本机内存，不经过 CPU。但这不意味着插上网卡后对端就能随意访问所有内存 — 上层需要主动注册一块内存区域，声明”这块内存允许被网卡访问”。注册产生的对象就是 Memory Region（MR）。

注册做了两件事：

1. **建立地址翻译**：进程用的是虚拟地址，网卡 DMA 需要物理地址。注册时内核会遍历页表，把虚拟→物理的映射写入网卡的硬件页表（MTT, Memory Translation Table）。之后网卡拿到虚拟地址就能自己查表找物理地址，不需要 CPU 参与。
2. **Pin 住页面**：OS 随时可能把页 swap 到磁盘或者 fork 后 COW 替换物理页。如果网卡还按旧的物理地址 DMA，数据就写到错误的地方。注册时内核会 pin 住这些页，保证物理地址不变。

注册的接口：

```text
// libibverbs/include/infiniband/verbs.h:1301
struct ibv_mr *ibv_reg_mr(struct ibv_pd *pd, void *addr, size_t length, int access);
```

四个参数：

- `pd`：保护域，MR 只能被同一 PD 下的 QP 使用
- `addr` + `length`：要注册的虚拟地址范围
- `access`：位掩码，控制这块内存**允许谁做什么**。比如你只想让对端读，就只给 `REMOTE_READ`；想让对端也能写，就加上 `REMOTE_WRITE`。不设的权限，网卡硬件会直接拒绝。详见下面的访问权限一节。

返回一个 `ibv_mr`：

```text
// libibverbs/include/infiniband/verbs.h:448
struct ibv_mr {
    struct ibv_context     *context;
    struct ibv_pd          *pd;
    void                   *addr;     // 注册的虚拟地址
    size_t                  length;
    uint32_t                handle;   // 内核侧句柄
    uint32_t                lkey;     // Local Key
    uint32_t                rkey;     // Remote Key
};
```

核心产出是 **lkey** 和 **rkey**。类比酒店房卡：你（MR 的主人）让前台（网卡）制了一张房卡（rkey），把房卡交给客人（对端），客人刷卡才能进你的房间，没有房卡门不会开。你还可以选择制一张只能看不能动的卡（`REMOTE_READ`），或者能看也能动的（`REMOTE_READ | REMOTE_WRITE`）。

- **lkey**：本地 post WR 时填在 `ibv_sge.lkey`，本地网卡用它查 MTT 找物理地址、验证权限
- **rkey**：通过带外方式（SEND/RECV、TCP 等）告诉对端。对端做 `RDMA_WRITE` / `RDMA_READ` 时填 `wr.rdma.rkey`，远端网卡凭此验证”这次访问是否被授权”

```text
本地 post RDMA_WRITE:
  sge.addr   = local_buf         ← 数据从哪读
  sge.lkey   = local_mr->lkey    ← 本地网卡凭此查本地 MTT
  wr.remote_addr = remote_buf    ← 写到对端哪里
  wr.rkey    = remote_mr->rkey   ← 对端网卡凭此验证权限 + 查远端 MTT
```

### 访问权限

```text
// libibverbs/include/infiniband/verbs.h:402
enum ibv_access_flags {
    IBV_ACCESS_LOCAL_WRITE   = 1,       // 本地网卡可写入（RECV 缓冲区、RDMA_READ 的本地目标需要）
    IBV_ACCESS_REMOTE_WRITE  = (1<<1),  // 允许对端 RDMA_WRITE
    IBV_ACCESS_REMOTE_READ   = (1<<2),  // 允许对端 RDMA_READ
    IBV_ACCESS_REMOTE_ATOMIC = (1<<3),  // 允许对端原子操作
    IBV_ACCESS_ON_DEMAND     = (1<<6),  // ODP 按需分页，不 pin（特殊场景）
};
```

硬件规则：**REMOTE_WRITE 必须搭配 LOCAL_WRITE**。远端写入最终也是本地网卡做 DMA 写入，没有 LOCAL_WRITE 网卡会拒绝。Local read 默认永远开启，不需要显式设置。

### 注册的代价

注册不是免费的：

- `ibv_reg_mr` 是 syscall 路径，要遍历页表、`get_user_pages` pin 页，单网卡注册在CX7上约为40GB/s（已经提前page fault过，纯注册开销），换句话说，注册一个40GB的buffer大约到这样一个网卡需要1s，将它注册到8个网卡需要8s。
- pin 住的页不能 swap、不能 NUMA 迁移，系统可用内存减少
- 每个 MR 在网卡占 MTT 条目，`device_attr.max_mr` 有上限

所以实践中的做法是**提前注册大块、反复使用**，而不是每次传输都注册/解注册。Hugepage也可以缓解注册开销（减少了页表数量）。

### 解注册

```text
int ibv_dereg_mr(struct ibv_mr *mr);
```

unpin 页面、释放网卡 MTT 条目。必须确保没有 in-flight 的 WR 还在引用这个 MR。

---

MR 准备好了内存，接下来需要一个地方提交传输请求。RDMA 的接口模型和 io_uring 几乎一样 — 应用往提交队列（SQ）塞请求，硬件完成后往完成队列（CQ）写结果，都是 proactor 模式。

和 epoll 的 reactor 模式区分一下：epoll 通知的是”fd 就绪了，可以读了”，应用自己调 `read()` 搬数据；proactor 通知的是”I/O 已经完成了”，数据已经在 buffer 里。类比：reactor 像快递到柜通知自取，proactor 像送货上门签收。

### 3.3 CQ（Completion Queue）

硬件把 WR 完成/失败的结果（CQE, Completion Queue Entry）写到这里，软件通过 `poll_cq()` 取结果。

CQ 是独立创建的资源，不属于任何 QP。创建 QP 时通过 `send_cq` / `recv_cq` 字段关联，多个 QP 可以指向**同一个 CQ** — 创建一个 CQ，所有 QP 的完成事件都写到这里，poll 一次就能收到所有 QP 的结果。注意这和 SRQ 是两回事：CQ 共享的是**完成通知**，SRQ 共享的是**接收 buffer**，两者独立。

类比 io_uring：io_uring 每个 ring 自带一对 SQ+CQ，不能跨 ring 共享 CQ。RDMA 更灵活，CQ 和 QP 是多对多的关系。

### 创建 CQ

```text
// libibverbs/include/infiniband/verbs.h:1397
struct ibv_cq *ibv_create_cq(struct ibv_context *context, int cqe,
    void *cq_context,
    struct ibv_comp_channel *channel,
    int comp_vector);
```

参数：

- `context`：设备上下文
- `cqe`：CQ 最少能容纳多少个 CQE。实际分配可能更大（硬件可能会向上取整到 2 的幂）
- `cq_context`：用户私有指针，完成事件回调时会带回来，纯透传
- `channel`：完成事件通道，用于事件驱动模式（`ibv_get_cq_event`）。纯 poll 模式填 NULL
- `comp_vector`：完成向量，控制中断路由到哪个 CPU，范围 `[0, context->num_comp_vectors)`。纯 poll 模式填 0 即可

返回的 `ibv_cq`：

```text
// verbs.h:863
struct ibv_cq {
    struct ibv_context *context;
    struct ibv_comp_channel *channel;
    void *cq_context;
    uint32_t handle;
    int cqe; // 实际 CQ 容量（≥ 创建时请求的值）
    // ... 内部同步字段省略
};
```

### Poll 完成

```text
// verbs.h:1443
static inline int ibv_poll_cq(struct ibv_cq *cq, int num_entries, struct ibv_wc *wc);
```

传入 `ibv_wc` 数组，返回值 ≥ 0 表示取到的 CQE 数量，< 0 表示出错。返回值 < `num_entries` 说明 CQ 已经空了。典型用法就是 busy-poll 循环：

```text
struct ibv_wc wc;
while (ibv_poll_cq(cq, 1, &wc) == 0) ; // 等完成
```

每个 CQE 是一个 `ibv_wc`（Work Completion）：

```text
// verbs.h:383
struct ibv_wc {
    uint64_t wr_id;          // 提交 WR 时用户设的 ID，用来关联"这是哪个请求的完成"
    enum ibv_wc_status status; // 完成状态，SUCCESS 或各种错误
    enum ibv_wc_opcode opcode; // 完成的操作类型
    uint32_t vendor_err;     // 厂商自定义错误码
    uint32_t byte_len;       // 实际传输字节数（RECV / RDMA_READ 时有意义）
    uint32_t imm_data;       // SEND_WITH_IMM / WRITE_WITH_IMM 携带的立即数
    uint32_t qp_num;         // 产生此完成的 QP 编号（多 QP 共享 CQ 时用来区分）
    uint32_t src_qp;         // 对端 QP 号（UD 场景下有意义）
    int wc_flags;            // 标志位（是否有 imm_data 等）
    uint16_t pkey_index;
    uint16_t slid;           // 对端 LID（IB）
    uint8_t sl;
    uint8_t dlid_path_bits;
};
```

**`status` 的常见值**（只列实践中会碰到的）：

| status | 含义 |
| --- | --- |
| IBV_WC_SUCCESS | 成功 |
| IBV_WC_WR_FLUSH_ERR | QP 进入 Error 状态后，所有未完成的 WR 被 flush 出来，每个产生这个错误。最常见的”批量失败” |
| IBV_WC_RETRY_EXC_ERR | 超时重传次数耗尽。通常意味着对端挂了或网络不通 |
| IBV_WC_RNR_RETRY_EXC_ERR | 对端接收队列持续为空，RNR 重试耗尽。对端没有及时 post recv |
| IBV_WC_REM_ACCESS_ERR | 远端访问权限错误。rkey 不对、MR 权限不够、或地址越界 |
| IBV_WC_LOC_LEN_ERR | 本地长度错误。RECV buffer 比实际到达的消息小 |
| IBV_WC_LOC_PROT_ERR | 本地保护错误。lkey 对不上、MR 和 QP 不在同一 PD |

**`opcode`**（完成对应的操作类型）：

```text
enum ibv_wc_opcode {
    IBV_WC_SEND,
    IBV_WC_RDMA_WRITE,
    IBV_WC_RDMA_READ,
    IBV_WC_COMP_SWAP,
    IBV_WC_FETCH_ADD,
    IBV_WC_BIND_MW,
    IBV_WC_LOCAL_INV,
    IBV_WC_RECV = 1 << 7,      // 接收完成，可用 (opcode & IBV_WC_RECV) 判断是否是接收类
    IBV_WC_RECV_RDMA_WITH_IMM,  // 收到 RDMA_WRITE_WITH_IMM
};
```

### 两种 CQ API

1. **BasicCompletionQueue**：`ibv_poll_cq` 传入结果数组，内核填充
2. **ExtendedCompletionQueue**：`ibv_start_poll` → `ibv_next_poll` → `ibv_end_poll`，支持硬件时间戳

实际上大部分项目还是基于前者。后者的优势在于有网卡硬件写的完成时间戳，可以用于更高精度的延迟监控。

### 销毁 CQ

```text
int ibv_destroy_cq(struct ibv_cq *cq);
```

必须确保没有 QP 还在引用这个 CQ。销毁顺序：先 destroy QP，再 destroy CQ。

CQ 需要控制大小，因为占用网卡的内存。

### 3.4 QP（Queue Pair）

> QP 是 RDMA 编程中最核心的资源 — PD 和 MR 是准备工作，CQ 是收结果，而所有传输请求的提交和执行都围绕 QP 展开。

**QP = Queue Pair**，本质是两条硬件队列：

- **SQ（Send Queue）** — 提交发送类 WR（SEND / RDMA_WRITE / RDMA_READ）
- **RQ（Receive Queue）** — 预先提交 RECV WR，为 SEND/RECV 操作提供接收 buffer

QP 主要管发送。对于 RDMA_WRITE / RDMA_READ，只有发起方的 SQ 参与，远端的 QP 完全不介入（远端网卡直接读写 MR）。RQ 只有在 SEND/RECV 语义下才消耗。

创建 QP 时需要传入已创建好的 CQ：

```text
// libibverbs/include/infiniband/verbs.h:1568
struct ibv_qp *ibv_create_qp(struct ibv_pd *pd, struct ibv_qp_init_attr *qp_init_attr);
```

创建时通过 `ibv_qp_init_attr` 指定 QP 的全部配置：

```text
// verbs.h:612
struct ibv_qp_init_attr {
    void               *qp_context;
    struct ibv_cq      *send_cq;    // SQ 的完成事件写到哪个 CQ
    struct ibv_cq      *recv_cq;    // RQ 的完成事件写到哪个 CQ（可以和 send_cq 相同，也可以多个 QP 共享同一个 CQ）
    struct ibv_srq     *srq;        // 共享接收队列，多个 QP 可共享一个接收 buffer 池，不用就填 NULL
    struct ibv_qp_cap   cap;        // 容量上限
    enum ibv_qp_type    qp_type;    // RC / UD / ...
    int                 sq_sig_all; // 是否每个 SQ WR 都产生 CQE
};
```

其中 `ibv_qp_cap` 控制队列深度：

```text
// verbs.h:604
struct ibv_qp_cap {
    uint32_t max_send_wr;     // SQ 最大 WR 数
    uint32_t max_recv_wr;     // RQ 最大 WR 数
    uint32_t max_send_sge;    // 单个 send WR 最大 scatter/gather 数
    uint32_t max_recv_sge;    // 单个 recv WR 最大 scatter/gather 数
    uint32_t max_inline_data; // 可内联到 WR 里的小数据上限（省一次 DMA）
};
```

创建完成后拿到的 `ibv_qp`：

```text
// verbs.h:840
struct ibv_qp {
    struct ibv_context *context;
    struct ibv_pd      *pd;
    struct ibv_cq      *send_cq;
    struct ibv_cq      *recv_cq;
    struct ibv_srq     *srq;
    uint32_t            handle;
    uint32_t            qp_num;     // QPN，网卡上这个 QP 的编号，建连时要告诉对端
    enum ibv_qp_state   state;      // RESET → INIT → RTR → RTS
    enum ibv_qp_type    qp_type;    // RC / UD / ...
};
```

`qp_type` 决定了传输模式：

```text
// verbs.h:586
enum ibv_qp_type {
    IBV_QPT_RC = 2,    // Reliable Connected — 可靠、一对一、支持 RDMA_WRITE/READ
    IBV_QPT_UC,        // Unreliable Connected — 不可靠、一对一
    IBV_QPT_UD,        // Unreliable Datagram — 不可靠、无连接、只支持 SEND/RECV
    // ...
};
```

> QP 先是一个**本地硬件对象**，不是”连接本身”。”还没连接”≠”没有 QP”，只是”QP 已创建，但还没绑定对端”。连接是后面通过 QP 状态机（INIT → RTR → RTS）完成的。<br> **留几个问题想想：**<br>

- 各种超参数在控制什么？为什么不直接给一个很大或者很小的值？
- 如果 1000 个 QP 各自维护 RQ，和共享一个 SRQ，内存开销差多少？什么场景下值得用 SRQ，什么场景下不值得？

### 4. QP 类型：RC vs UD

到这里，PD、MR、QP、CQ 这些本地资源都创建好了。接下来要和对端建立连接、开始传输数据。但在建连之前，需要先选定 QP 的类型 — 它决定了连接模型和传输语义。最常用的两种是 RC 和 UD，区别很大 — 一个像 TCP，一个像 UDP。

也像TCP和UDP一样，大部分应用场景还是都采用RC而不是UD.

### RC（Reliable Connected）

- **一对一连接**：创建 QP 后，需要填对端参数（remote qpn / psn / lid / gid）并完成状态切换 INIT → RTR → RTS。建连完成后，这个 QP 就”锁定”了对端 — 所有从它发出的包都只能到那一个目标
- **可靠**：硬件保证重传、顺序、流控。丢包了网卡自动重传，乱序了硬件重排，应用层完全不用管。这也是为什么叫”Reliable” — 可靠性从软件卸载到了硬件
- 支持所有操作类型：SEND/RECV、RDMA_WRITE、RDMA_READ、Atomic

**代价**：每对通信节点需要一个独立的 QP。N 个节点全连接意味着每个节点要维护 N-1 个 QP，每个 QP 在网卡上都占硬件资源（缓冲区、状态表），如果没有控制网卡连接，是平方甚至次方关系的话，QP数量会爆炸。在大规模集群（几千节点）下 RC 的 scalability 是个问题。

### UD（Unreliable Datagram）

- **无连接**：QP 进入 RTS 后即可用，每次 post_send 时通过 Address Handle 指定目标。一个 UD QP 可以和任意多个目标通信
- **不可靠**：报文可能丢失、乱序、重复，硬件不保证重传。需要上层协议自己处理可靠性
- **面向消息**：一次 send 对应一条完整消息，不支持自动拆包 — **单条消息不能超过 MTU**（通常 4096 字节）
- 只支持 SEND/RECV，不支持 RDMA_WRITE / RDMA_READ

**优势**：一个 QP 通吃所有目标，N 个节点只需要 1 个 UD QP，scalability 远好于 RC。

|  | RC | UD |
| --- | --- | --- |
| 连接模型 | 一对一，需建连 | 无连接，AH 指定目标 |
| 可靠性 | 硬件保证 | 不保证，需上层处理 |
| 操作 | SEND/RECV + RDMA_WRITE/READ + Atomic | 仅 SEND/RECV |
| 消息大小 | 无限制（硬件自动拆包） | ≤ MTU（~4KB） |
| QP 数 / N 节点 | N-1 | 1 |
| 典型用途 | 数据面：大块传输 | 控制面：小消息广播 |

### 5. 操作语义

### RDMA_WRITE

远端 RQ **不参与**，最小模型：

1. 本地 SQ post 一个 RDMA_WRITE
2. NIC 把数据直接写到远端 MR（`remote_addr` + `rkey`）
3. 本地 CQ 出一个发送完成 CQE

远端不会因为这次 write 产生”接收完成”事件，RDMA网卡本身不产生事件。远端可以主动检查内存来判断传输是否完成，这需要在数据头或者尾留一个flag值，具体可以看FaRM等论文。

**例外：RDMA_WRITE_WITH_IMM** — 会在远端产生一个带 immediate 的完成事件，此时远端需要有可用的 RQ WQE 来接收这个通知。

### RDMA_READ

同样远端 RQ **不参与**，远端 CPU 完全无感知。但和 WRITE 不同，READ 是一个**请求-响应**操作 — 本地 NIC 发出读请求，远端 NIC 回数据，整体链路会比WRITE复杂，极限吞吐和延迟低于WRITE，在某些负载下极限性能损失在10%-20%下，不同负载，不同网卡，不同参数都会导致损失不同。

1. 本地 SQ post 一个 RDMA_READ（指定 remote_addr/rkey 和 local_addr/lkey）
2. 本地 NIC 向远端 NIC 发起 Read Request
3. 远端 NIC 从远端 MR 取数据，发回 Read Response
4. 本地 NIC 收到数据后通过 DMA 写入本地缓冲区
5. 本地 CQ 生成完成 CQE，App 通过 `poll_cq()` 获取结果

远端同样不产生任何 CQE。和 WRITE 的关键区别：

- **延迟**：WRITE 是 fire-and-forget（发完即完成），READ 要等远端回数据
- **并发限制**：READ 受 `max_rd_atomic` / `max_dest_rd_atomic` 限制（硬件需要为每个 outstanding READ 维护状态，一般为16，小数据下有明显效果，大量数据下效果不明显），WRITE 不受此限制
- **流量方向**：WRITE 的数据和控制流同向（发起方 → 远端），READ 的控制流和数据流反向（请求发起方 → 远端，数据远端 → 发起方）

实践中，如果发起方知道要什么数据，用 READ 更自然（pull 模型）；如果数据的生产方知道该写到哪，用 WRITE 更高效（push 模型）。追求性能使用WRITE。还有一方面的考虑是，避免多对一，把发起数据传输的所有权交给少数方。

### 6. 寻址与建连

要建立 RC 连接，双方需要交换以下信息：

| 概念 | 说明 |
| --- | --- |
| GID | 网卡全局唯一地址，16 字节。一个网卡可有多个 GID。IB 一般选 index 0；RoCE 的 GID 与 IP 绑定，有多少个 IP 就有多少个 GID，需选能跨网的那个 |
| LID | 子网内地址，2 字节，由交换机分配 |
| QPN | Queue Pair Number，网卡上某个 QP 的编号，4 字节（0 = 子网管理，1 = 通用服务，≥2 = 用户） |
| PSN | Packet Sequence Number，24 位包序号，每个 QP 独立维护，用于保证顺序和可靠性 |

### QP 状态机

![](https://pica.zhimg.com/v2-6c9cab68059908c8b6e05a28d485c5de_r.jpg)

RC QP 从创建到可用，经历四个状态：

```text
ibv_create_qp()          ibv_modify_qp() ×3
      |                        |
   RESET  ──→  INIT  ──→  RTR  ──→  RTS
                 ↑           ↑         ↑
            纯本地配置   填对端信息   本端发送参数
```

每一步通过 `ibv_modify_qp` 推进，传入目标状态和该步骤要求的属性。漏填任何必填字段，内核直接返回 `-EINVAL`。

> 题外话：根据我最近学习的情况来看，这个状态机的维护才是RDMA库迈向生产的关键。双方要同步，容灾，错误等处理。或者说RC 链接安全稳定地维护才是一个RDMA库的关键，性能的话，队列深度拉满就好了，现在llm kv cache也没有到us level. 我用claude code我也不在乎多出几十ms的ttft。但是RDMA出错影响的就不是一个请求的TTFT，整个紧凑的推理系统有可能雪崩，造成SLO大幅波动。所以稳定可观测可维护才是核心。

`ibv_qp_attr` 是所有属性的超集，每次只填当前步骤用到的字段，通过 `attr_mask` 位掩码告诉内核”我这次设了哪些”：

```text
// verbs.h:701
struct ibv_qp_attr {
    enum ibv_qp_state   qp_state;           // 目标状态
    enum ibv_mtu        path_mtu;           // 路径 MTU
    uint32_t            dest_qp_num;        // 对端 QP 号
    uint32_t            rq_psn;             // 接收队列期望的起始 PSN
    uint32_t            sq_psn;             // 发送队列起始 PSN
    int                 qp_access_flags;    // 远程访问权限
    struct ibv_ah_attr  ah_attr;            // 地址向量（怎么找到对端）
    uint16_t            pkey_index;         // P_Key 表索引
    uint8_t             port_num;           // 物理端口号
    uint8_t             max_rd_atomic;      // 本端可同时发起的 RDMA Read 数
    uint8_t             max_dest_rd_atomic; // 对端可同时发起的 RDMA Read 数
    uint8_t             min_rnr_timer;      // RNR NAK 等待时间
    uint8_t             timeout;            // ACK 超时
    uint8_t             retry_cnt;          // 超时重传次数
    uint8_t             rnr_retry;          // RNR 重试次数
    // ... 省略不常用字段
};
```

### RESET → INIT：纯本地配置

不需要知道对端任何信息，只配置本地参数：

```text
struct ibv_qp_attr attr = {
    .qp_state        = IBV_QPS_INIT,
    .pkey_index      = 0,
    .port_num        = 1,
    .qp_access_flags = IBV_ACCESS_REMOTE_WRITE | IBV_ACCESS_REMOTE_READ,
};

ibv_modify_qp(qp, &attr,
    IBV_QP_STATE | IBV_QP_PKEY_INDEX | IBV_QP_PORT | IBV_QP_ACCESS_FLAGS);
```

| 必填属性 | 含义 |
| --- | --- |
| pkey_index | Partition Key 索引，子网流量隔离用，通常填 0 |
| port_num | 绑定的物理端口 |
| qp_access_flags | 控制对端能对你做什么 — 不设则不允许远程访问 |

注意 `qp_access_flags` 和 MR 注册时的 `access` 是**双重检查** — 两者取交集。MR 允许 remote write 但 QP 没开，对端的 RDMA Write 也会被网卡拒绝。

进入 INIT 后可以开始 post recv WR（提前准备接收 buffer），但还不能实际收到包。

### INIT → RTR（Ready to Receive）：填对端信息

**关键一步** — 需要对端的寻址信息。双方必须先通过带外通道（TCP socket、共享内存等）交换上面表格中提到的 GID / LID / QPN / PSN：

```text
struct ibv_qp_attr attr = {
    .qp_state           = IBV_QPS_RTR,
    .path_mtu           = IBV_MTU_4096,
    .dest_qp_num        = remote->qpn,       // 对端 QP 号
    .rq_psn             = remote->psn,        // 对端的起始 PSN
    .max_dest_rd_atomic = 1,
    .min_rnr_timer      = 12,
    .ah_attr = {
        .is_global  = 1,                      // RoCE 必须 = 1
        .dlid       = remote->lid,
        .sl         = 0,
        .port_num   = 1,
        .grh = {
            .dgid       = remote->gid,        // 对端 GID
            .sgid_index = gid_index,           // 本端 GID 表索引
            .hop_limit  = 1,
        }
    }
};

ibv_modify_qp(qp, &attr,
    IBV_QP_STATE | IBV_QP_AV | IBV_QP_PATH_MTU |
    IBV_QP_DEST_QPN | IBV_QP_RQ_PSN |
    IBV_QP_MAX_DEST_RD_ATOMIC | IBV_QP_MIN_RNR_TIMER);
```

其中 `ah_attr`（地址向量）告诉网卡怎么找到对端。它里面嵌套了 GRH（Global Route Header），RoCE 环境必须启用：

```text
// verbs.h
struct ibv_ah_attr {
    struct ibv_global_route grh;    // GRH（RoCE 必须）
    uint16_t    dlid;               // 对端 LID（IB 用）
    uint8_t     sl;                 // Service Level
    uint8_t     is_global;          // 是否走 GRH — RoCE 必须 = 1
    uint8_t     port_num;
    // ...
};

struct ibv_global_route {
    union ibv_gid dgid;            // 对端 GID（16 字节）
    uint8_t sgid_index;            // 本端 GID 表索引
    uint8_t hop_limit;
    // ...
};
```

RC 的地址向量在这一步写入 QP 状态，之后所有包都固定发往这个目标 — 这就是”Connected”的含义。对比 UD：UD 不在 QP 里绑定地址，而是每次 post_send 时附带一个独立创建的 Address Handle（`ibv_ah`）。

进入 RTR 后，**QP 已经可以接收数据了**（前提是之前 post 了 recv WR）。

### RTR → RTS（Ready to Send）：配置发送参数

```text
struct ibv_qp_attr attr = {
    .qp_state      = IBV_QPS_RTS,
    .timeout       = 14,            // ACK 超时 = 4.096μs × 2^14 ≈ 67ms
    .retry_cnt     = 7,             // 超时重传次数（0-7）
    .rnr_retry     = 7,             // RNR 重试（7 = 无限）
    .sq_psn        = my_psn,        // 本端起始 PSN
    .max_rd_atomic = 1,
};

ibv_modify_qp(qp, &attr,
    IBV_QP_STATE | IBV_QP_TIMEOUT | IBV_QP_RETRY_CNT |
    IBV_QP_RNR_RETRY | IBV_QP_SQ_PSN | IBV_QP_MAX_QP_RD_ATOMIC);
```

| 属性 | 含义 |
| --- | --- |
| timeout | ACK 超时。0 = 无限等待，1-31 = 4.096μs × 2^val。设太小会假超时，太大则故障恢复慢 |
| retry_cnt | 超时后重传次数，超过后 QP 进入 Error 状态，连接断开 |
| rnr_retry | 对端接收队列空（Receiver Not Ready）时的重试。7 = 无限重试 |
| sq_psn | 本端发送起始序列号 |
| max_rd_atomic | 同时 outstanding 的 RDMA Read/Atomic 数 |

**进入 RTS，双向收发都可以了。**

### PSN 配对

PSN 的交叉对应关系容易搞混：

```text
Node A                          Node B
──────                          ──────
sq_psn = X  ──发送──→          rq_psn = X  (RTR 时设的)
rq_psn = Y  (RTR 时设的)  ←──发送──  sq_psn = Y
```

A 的 `sq_psn` 必须等于 B 在 RTR 阶段设的 `rq_psn`，反之亦然。不匹配会导致序列号校验失败 → 不断重传 → QP 进入 Error。

### 整个过程的时序

```text
Node A                    带外通道                    Node B
──────                    ──────                    ──────
create_qp (RESET)                                  create_qp (RESET)
modify → INIT                                      modify → INIT
   │                                                  │
   ├──── 交换 {qpn, psn, lid, gid} ──────────────►   │
   │  ◄──────────────────────── {qpn, psn, lid, gid} ─┤
   │                                                  │
modify → RTR (填 B 的信息)                          modify → RTR (填 A 的信息)
modify → RTS                                        modify → RTS
   │                                                  │
   ╰──── 现在可以 RDMA_WRITE / READ ─────────────────╯
```

双方独立走自己的状态机，唯一的同步点是带外信息交换 — A 必须先拿到 B 的 qpn/psn/gid 才能进 RTR，反之亦然。

### GID 选择

一个 RDMA 端口可以有多个 GID，通过 `ibv_query_gid(ctx, port, index, &gid)` 按 index 查询。GID 表的内容取决于网络类型：

- **InfiniBand**：GID index 0 就是端口的默认地址，一般直接用 0。
- **RoCE**：每个 GID 对应一个 IP 地址 + GID type 的组合。GID type 有两种：RoCEv1（基于 MAC，不能跨子网）和 RoCEv2（基于 IP，可路由）。实践中几乎只用 RoCEv2。

RoCE 环境下选 GID 的关键：找到 **RoCEv2 类型且绑定了正确网络接口** 的那个 index。可以通过 `sysfs` 查看：

```text
# 查看所有 GID 条目
cat /sys/class/infiniband/<dev>/ports/<port>/gids/<index>
# 查看 GID 类型（v1 或 v2）
cat /sys/class/infiniband/<dev>/ports/<port>/gid_attrs/types/<index>
# 查看绑定的网络设备
cat /sys/class/infiniband/<dev>/ports/<port>/gid_attrs/ndevs/<index>
```

简单做法：遍历 GID 表，找到 type 为 `RoCE v2` 且 ndev 匹配目标网卡的 index。大部分 RDMA 库（如 UCX）内部也是这么做的。
