> 这是「AI 算力网络 · ESL 建模视角」系列的第五篇。前四篇都在网络侧：桥、交换机、多路径、流控。这一篇把视角切回计算侧——**GPU 上的工作是怎么被排队、被触发、被等待的**。原因很直接：做“计算 + 通信”联合仿真时，网络模型再精确，如果计算侧被建成“一个大黑盒、串行跑 kernel”，整个仿真的结论都是错的。通信能不能被计算掩盖、decode 为什么慢、几千张卡为什么会互相等——答案全在这一层。

---

### 一、一个餐厅后厨的比喻

把 GPU 想成一个大后厨，把 CPU 想成前台点单员。

- **Kernel** = 一道菜。后厨真正干活的单位。
- **Kernel launch** = 前台把一张菜单递进后厨。递单本身要花时间：写单、走到窗口、喊一声。
- **Stream** = 一条传菜通道。同一条通道上的菜**严格按下单顺序**出；不同通道之间**没有顺序保证**。
- **Event** = 菜单上的一个便签：“这道菜等 3 号通道的那道汤好了再做”。它是跨通道的依赖。
- **CUDA Graph** = 套餐。前台不再一道一道递单，而是把整套菜单（几百道菜和它们的先后关系）**一次性**交给后厨，后厨自己按图执行。
- **硬件工作队列** = 后厨的接单窗口。窗口数量是有限的（默认 8 个），通道比窗口多的时候，几条通道要挤同一个窗口。

这个比喻里最重要的一点：**前台递单的速度是有上限的。** 如果每道菜只需要 1 秒就能炒好，而前台递一张单要 3 秒，那后厨大部分时间在等单，而不是在炒菜。这就是“launch-bound”，也是 AI 推理 decode 阶段的核心矛盾。

### 二、Kernel Launch：那几微秒是怎么来的

### 2.1 量级

一次 kernel launch 从 CPU 调用到 GPU 真正开始执行，要经过：框架层（PyTorch 的 Python 分发、算子选择、shape 检查）→ CUDA runtime → 驱动（构造命令、写入命令缓冲区）→ PCIe doorbell → GPU 前端解析命令、分配资源、下发线程块。

- 驱动 + 硬件这一段，NVIDIA 自己的口径是 **每个 kernel 约 1~5 µs**。
- 加上框架层（eager 模式的 PyTorch），一个算子的完整开销通常在 **10~20 µs** 量级。
- 而一个小 kernel 在 GPU 上的执行时间可能只有几微秒，甚至更短。

### 2.2 为什么 decode 阶段最惨

LLM 推理分两个阶段（下一篇会专门讲）：prefill 处理整段 prompt，算子都很大，GPU 吃得饱；decode 每次只生成一个 token，每个算子的计算量极小。

做一个量级估算。假设每层 Transformer 大约 10 个 kernel，每次 launch 开销按 3 µs 算，decode 一步的 GPU 时间按“权重从 HBM 读一遍”估（batch 很小时 decode 是访存瓶颈，H100 HBM 带宽按 3.35 TB/s）：

| 模型 | 张量并行 | 每卡权重 | 访存时间/步 | launch 次数 | launch 开销 | 开销占比 |
| --- | --- | --- | --- | --- | --- | --- |
| 7B | TP=1 | 14 GB | 4.2 ms | 320 | 1.0 ms | 23% |
| 7B | TP=8 | 1.8 GB | 0.5 ms | 320 | 1.0 ms | 184% |
| 70B | TP=1 | 140 GB | 42 ms | 800 | 2.4 ms | 6% |
| 70B | TP=8 | 17.5 GB | 5.2 ms | 800 | 2.4 ms | 46% |

（估算口径：bf16 权重，每层 10 个 kernel，未计 NCCL 通信 kernel 的 launch。）

两个观察：

**① 模型越小、并行度越高，launch 开销占比越大。** 张量并行把每张卡的计算切成 1/8，但 launch 次数一次都不少——**计算随并行度缩小，launch 开销不随并行度缩小**。TP=8 的 7B 模型，launch 开销比计算本身还长，GPU 大部分时间在等前台递单。

**② 这不是 GPU 的问题，是 CPU 的问题。** Nsight 抓出来的图很典型：CPU 100% 忙，GPU 上的 kernel 之间全是空隙。加 GPU 不解决问题，减少 launch 才解决。

减少 launch 的办法有两个：**算子融合**（把几道菜合成一道，kernel 数量变少）和 **CUDA Graph**（前台一次递整套菜单）。这篇讲后者。

### 三、Stream：队列，不是线程

### 3.1 语义

Stream 是 GPU 上的**有序命令队列**：

- 同一个 stream 内的操作（kernel、memcpy、event）**按提交顺序执行**，前一个完成后一个才开始（Hopper 的 PDL 可以让下一个 kernel 的前奏提前，后面说）。
- 不同 stream 之间**没有任何顺序保证**，硬件可以并发执行，也可以任意交错。
- 默认 stream（legacy default stream）有特殊的同步语义：它会和其他所有 blocking stream 互相等待。这是很多“为什么我的两个 stream 没有并发”的元凶。

所以 stream 不是线程——它不占用 GPU 资源，它只是一个排队的地方。**并发发生在硬件层面，stream 只是告诉硬件“这些东西之间没有依赖，你可以并发”。**

### 3.2 硬件工作队列与假依赖

Stream 是软件概念，可以开几百个。但 GPU 前端的**硬件工作队列**是有限的：Kepler 起最多 32 个（Hyper-Q），CUDA 默认只启用 8 个（`CUDA_DEVICE_MAX_CONNECTIONS`，默认 8，可调到 32）。

Stream 比硬件队列多的时候，多个 stream 会被映射到同一个硬件队列。同一个硬件队列是**按提交顺序出队**的，于是本来没有依赖关系的两个 stream 之间就出现了**假依赖（false dependency）**：A stream 的 kernel 排在 B stream 的 kernel 后面，即使 A 早就可以跑了，也得等 B 的前面那个跑完。

### 3.3 一个反直觉的真实案例：把队列数设成 1

Megatron-LM 做张量并行的通信-计算重叠时，**要求把 `CUDA_DEVICE_MAX_CONNECTIONS` 设成 1**。这看起来是在主动制造假依赖，为什么？

因为重叠的前提是“通信 kernel 先跑起来，然后计算 kernel 在旁边跑”。通信 kernel（NCCL）只占几个 SM，计算 kernel（GEMM）想占满所有 SM。如果两者在**不同的硬件队列**里，GPU 前端的调度顺序不受控：GEMM 可能先被调度、占满 SM，通信 kernel 被排到 GEMM **结束之后**才开始——重叠彻底失败，变成了串行。NVIDIA 的文档原话是：否则“TP 通信 kernel 可能被调度到 GEMM 的末尾”。

设成 1 之后，所有 stream 走同一个硬件队列，**GPU 严格按软件提交顺序调度**。软件先提交通信 kernel，它就先占上几个 SM；再提交 GEMM，它拿剩下的 SM——两者并发，重叠成立。

这个案例对建模的启示非常大：**“通信和计算能否重叠”不是一个布尔值，它取决于 kernel 的提交顺序、硬件队列的映射、以及两个 kernel 对 SM 的争用。** 一个把 GPU 建成“无限并发”的模型永远看不到这件事。

### 3.4 SM 争用：重叠不是免费的

即使调度顺序对了，通信 kernel 也要占 SM（NCCL 的每个 channel 用一个线程块，通常占 1 个 SM，多 channel 就多 SM），还要占 HBM 带宽和 NVLink/PCIe 带宽。GEMM 拿到的 SM 变少，跑得就慢一点。更麻烦的是有些 kernel 会“霸占”整个 GPU：Megatron 文档提到 Transformer Engine 的持久化 LayerNorm kernel 会**自旋等待所有 SM**，导致它和后续的计算 kernel 只能排在数据并行通信之后——重叠又没了，解法是给通信 kernel 预留 SM。

所以“重叠效率”是一个 0 到 1 之间的数，实际工程里常见 60%~90%，几乎从来不是 100%。

### 四、Event：跨队列的便签

### 4.1 两个动作

Event 只有两个核心动作：

- `cudaEventRecord(e, streamA)`：在 A 队列的当前位置插一个标记。当 A 队列执行到这个位置时，e 变为“完成”。
- `cudaStreamWaitEvent(streamB, e)`：在 B 队列插一个“等 e 完成再继续”的屏障。

关键是：**这个等待是 GPU 侧的，不阻塞 CPU。** CPU 提交完 wait 就可以继续提交后面的东西了，GPU 会在执行到那里时自己等。这和 `cudaEventSynchronize(e)`（CPU 阻塞直到 e 完成）是完全不同的两件事——前者是流水线里的依赖边，后者是流水线的断点。

### 4.2 通信和计算是怎么被缝在一起的

一个典型的“计算 → 通信 → 计算”模式：

```text
compute_stream: kernel_1 → record(e1)
comm_stream:    wait(e1) → NCCL AllReduce → record(e2)
compute_stream: kernel_2（不依赖通信结果，可与 AllReduce 并发）
compute_stream: wait(e2) → kernel_3（依赖通信结果）
```

kernel_2 和 AllReduce 在两个 stream 上并发，这就是重叠。e1 和 e2 是两条依赖边。PyTorch 的 `record_stream`、NCCL 的 group call、各种框架的 async collective，底层全是这套东西。

### 4.3 同步点：流水线的断点

真正让 GPU 空转的不是 event wait，而是 **host-device 同步点**：`.item()`、`cudaDeviceSynchronize()`、同步版 `cudaMemcpy`、打印 loss……每一个都让 CPU 停下来等 GPU 把队列排空，然后 CPU 才能继续递单——**排空之后 GPU 就没菜可炒了**，直到 CPU 重新把队列填起来。这是一个双向的气泡：GPU 等 CPU，CPU 等 GPU。

### 五、CUDA Graph：把整套菜单一次递进去

### 5.1 它做了什么

CUDA Graph 把一段“kernel + memcpy + event 依赖”的序列**捕获成一张 DAG**，实例化一次，之后每次只需要一个 `cudaGraphLaunch` 就能重放整张图。GPU 前端直接按图调度，CPU 侧的 Python、框架、驱动开销全部跳过。

收益有三类，第三类经常被忽略：

**① Launch 开销。** PyTorch 官方博客的数字：Mask R-CNN 的 backbone 部分，图化前 31 ms、图化后 6 ms，kernel 级约 5 倍；整个模型 1.7 倍（因为只图化了一部分）。NVIDIA 的经验表：很多小 kernel 的场景 1.5~3 倍，大 kernel 场景 1.1~1.4 倍，已经 90% 以上利用率的场景 1.05~1.15 倍。

**② SM 利用率。** NVIDIA 给的示例监控：不用图 75%~82%，用图 95%~96%。

**③ 抖动。** 这是对做网络仿真的人最重要的一条。不用图时，每一步的耗时随 CPU 调度波动，变异系数 3%~10%；用图后 %~2%。多卡场景下，**各 rank 之间的步时差异从 5%~20% 降到 %**。为什么重要？集合通信要等所有 rank 到齐，rank 之间的抖动直接变成 AllReduce 里的等待时间。几千张卡的集群里，最慢的那个 rank 决定一切——CUDA Graph 削掉的不只是平均延迟，更是尾部。

### 5.2 代价与约束

- **静态形状**：图里的 kernel 参数是捕获时固定的，batch size、序列长度变了就得换一张图。vLLM 的做法是按 batch size 分桶（1、2、4、8……）各捕获一张图，运行时把请求 pad 到最近的桶。
- **静态控制流**：图里不能有依赖数据的 if/else（Hopper 之后的 device graph launch 部分缓解了这一点）。
- **不能有 host 同步点**：捕获时遇到 `.item()` 直接报错。
- **显存**：每张图要保留自己的中间缓冲区，分桶越多显存越多；vLLM 用“piecewise”图（attention 留在图外）来平衡。

### 5.3 PDL：连 stream 内的间隙也不放过

即使有了 CUDA Graph，同一个 stream 内相邻两个 kernel 之间仍然有一个“前一个完全结束 → 后一个开始下发”的间隙（几微秒量级，包括尾部线程块的等待和下一个 kernel 的前奏）。Hopper 引入的 **PDL（Programmatic Dependent Launch）** 允许下一个 kernel 在前一个 kernel 还没完全结束时就开始前奏（比如加载参数、初始化 shared memory），真正依赖前一个结果的地方再等。这是 stream 语义的一次精细化：从“完成 → 开始”变成“快完成 → 开始准备”。

### 六、★ ESL 建模视角：把 GPU 建成“K 条队列 + S 个 SM + 一个递单的 CPU”

前面都是铺垫，这一节是我真正想写的。

### 6.1 建模对象是一张 DAG，不是一个黑盒

做“计算 + 通信”联合仿真，计算侧的正确抽象是：

```text
节点：kernel（计算）、collective（通信）、memcpy、event
边：  同 stream 的顺序边 + event 依赖边
执行者：一个 host（递单有开销）+ 一个 device（K 个硬件队列、S 个 SM）
```

这正是 MLCommons **Chakra 执行图（Execution Trace）** 定义的东西：计算节点、通信节点、内存节点、依赖、时序，和具体模型/框架解耦。PyTorch、NeMo、vLLM 都已经能原生导出 Chakra 格式，ASTRA-sim 直接消费它。**如果你在做自己的 ESL 联合仿真，强烈建议以 Chakra 图为输入格式**——一来不用自己定义 DAG 格式，二来可以和 ASTRA-sim 对标。

### 6.2 执行模型：一个 kernel 什么时候能开始

```text
kernel k 可以开始，当且仅当：
  ① host 已经把它递进来了：t ≥ t_submit(k)
     eager 模式：t_submit(k) = t_submit(k−1) + t_launch_host
     图模式：    整张图一次 t_graph_launch，节点之间 ≈ 0
  ② 它所在硬件队列里排在它前面的节点已经开始下发（in-order issue）
  ③ 它等待的所有 event 已完成
  ④ GPU 上有足够的 SM 资源（减去正在跑的通信 kernel 占用的部分）

kernel k 的持续时间：
  t_exec(k) = t_profile(k) × slowdown(可用 SM 比例, 带宽争用)

通信节点：
  交给网络仿真器，返回完成时刻；完成后触发它 record 的 event
```

四个条件缺一个，就会漏掉一类真实现象：缺①看不到 launch-bound，缺②看不到假依赖和 Megatron 那个“队列数设 1”的故事，缺③看不到重叠，缺④看不到 SM 争用。

### 6.3 必须参数化的量

| 参数 | 含义 | 量级 / 注意 |
| --- | --- | --- |
| t_launch_host | host 侧每个算子的提交开销 | eager 10~20 µs；图模式摊薄到亚微秒 |
| t_launch_gpu | 驱动 + 硬件下发延迟 | 1~5 µs |
| t_graph_launch | 整张图的一次启动开销 | 常数级，与节点数弱相关 |
| n_hw_queues | 硬件队列数 | 默认 8，可 1~32；stream→队列映射要建 |
| sm_total / sm_demand(k) | SM 总数与每个 kernel 的需求 | NCCL 每 channel 约 1 个 SM |
| overlap_slowdown | 被重叠的计算 kernel 的减速 | 由 SM 与带宽争用推出，不要设常数 |
| t_sync_point | host-device 同步点的位置 | 每一个都是流水线断点 |
| launch_jitter | 各 rank 递单时间的分布 | eager CV 3~10%，图 % |
| pdl_overlap | 相邻 kernel 前奏可提前的时间 | Hopper+，微秒级 |

### 6.4 一个快速判据：launch-bound 还是 compute-bound

```text
launch 开销总和  L = N_kernels × t_launch
GPU 执行总和     C = Σ t_exec(k)

L > C     → launch-bound：GPU 大部分时间在等单，加 GPU 没用，减 launch 才有用
L << C    → compute-bound：launch 可以忽略，重点建 SM 争用和通信重叠
```

第二节那张表就是这个判据的实例。做 decode 仿真时，**先算这个比值再决定模型精度**：launch-bound 的场景，kernel 内部的建模精度完全不重要，launch 路径的建模精度决定一切；反之亦然。

### 6.5 该盯的指标

- **GPU 气泡占比**：GPU 上没有任何 kernel 在跑的时间比例。区分“等 host 递单”和“等 event 依赖”两种气泡，前者靠图/融合解决，后者靠调度顺序解决。
- **重叠率**：被计算掩盖的通信时间 / 总通信时间。同时报告被重叠的计算 kernel 的减速，两者相乘才是真实收益。
- **关键路径**：DAG 上最长的路径。它告诉你优化哪个节点才有用。
- **各 rank 到达集合通信入口的时间偏差**：这个偏差直接变成 AllReduce 的等待。用 `launch_jitter` 扫一遍，看多少抖动会让通信时间翻倍。
- **硬件队列的假依赖次数**：一个 kernel 明明依赖已满足、SM 也空闲，却因为同队列前面的节点没完而等待的次数。

### 6.6 五个最常见的建模坑

1. **把 GPU 建成单 FIFO。** 所有 kernel 串行执行，永远看不到重叠；或者反过来建成无限并发，永远看不到争用。正确的是 K 条队列 + S 个 SM。
2. **忽略 launch 开销。** 在 prefill / 训练大 batch 场景下无所谓，在 decode 场景下结论直接错一倍。
3. **重叠效率设成 100%。** 通信 kernel 占 SM、占 HBM 带宽、占互联带宽，被重叠的计算一定会慢。要么建争用，要么至少给一个经验折扣。
4. **把 event wait 当成 CPU 阻塞。** Event wait 是 GPU 侧的依赖边，不是流水线断点；只有 host 同步点才是断点。混淆两者会把所有异步通信建成同步的。
5. **rank 之间没有抖动。** 单卡模型加个网络就当多卡模型，各 rank 完美同步出发——集合通信的等待时间会被系统性低估。加一个 launch jitter 分布，很多“网络不是瓶颈”的结论会翻转。

### 七、小结

```text
Kernel launch = 前台递单，1~5 µs（驱动+硬件），eager 框架下 10~20 µs
  decode 是 launch-bound 重灾区：计算随 TP 缩小，launch 不缩小

Stream  = 有序队列，不是线程；并发发生在硬件层
  硬件队列默认 8 个，stream 多了有假依赖
  Megatron 把队列数设成 1 反而实现重叠：调度顺序 > 并发能力

Event   = 跨队列依赖边，GPU 侧等待不阻塞 CPU
  真正的断点是 host 同步点（.item() 之类）

CUDA Graph = 整套菜单一次递：launch 开销↓、利用率↑、抖动↓（对集合通信最重要）
  代价：静态形状、静态控制流、显存

ESL 建模：
  对象 = DAG（Chakra 格式）+ host 递单模型 + K 队列 + S 个 SM
  开始条件四件套：递到了、队列前面开始了、event 满足了、SM 够了
  先算 L/C 判据再定精度；重叠率 × 减速才是真收益；rank 抖动必须建
```
