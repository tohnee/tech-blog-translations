### 01｜为什么我觉得这篇论文值得读？

我们经常讨论如何提高 GPU 的计算利用率，如何通过 Continuous Batching、Chunked Prefill、Prefill-Decode Disaggregation 等技术提高推理吞吐。

但随着模型上下文长度不断增加，另一个问题也越来越难以绕开：**KV Cache 到底应该怎么存，才能既节省显存，又不让压缩和解压缩本身成为新的性能瓶颈？**

尤其是在长上下文推理中，KV Cache 的显存占用会随序列长度线性增长。

例如，对于 Llama 3.1 8B：

- Transformer Layers：32
- KV Heads：8
- Head Dimension：128
- KV Cache Precision：FP16
- Context Length：128K Tokens

KV Cache 的理论存储量可以表示为：

```text
KV Size = 2 × Layers × KV Heads × Head Dim × Seq Len × Bytes
```

代入上述参数，单条请求的 KV Cache 就达到约 **16 GiB**。

这还没有考虑模型权重、运行时 Workspace、激活值和其他系统开销。

如果有多个长上下文请求同时执行，显存占用会进一步增加。KV Cache 不仅限制了模型能够支持的上下文长度，也直接限制了推理系统能够承载的并发请求数量。

### 为什么不直接使用低比特量化？

一种直接的思路是将 FP16 KV Cache 量化为 INT4。理论上，每个元素从 16 bits 降至 4 bits，可以将原始数值存储量降低 75%。

但实际情况往往没有这么理想。

为了进行量化和反量化，还需要保存 Scale、Zero Point 等元数据。如果采用较小的量化 Group，元数据所占比例可能明显增加。此外，量化与反量化还会引入额外的 GPU 计算、显存读写和 Kernel Launch。

因此，真正的问题不是能否把数据压得更小，而是：**能否在保持模型推理精度的同时，实现高吞吐、低额外显存开销的在线 KV Cache 压缩？**

VAYNE 就是围绕这个问题展开的。论文给出的核心结果包括：

- 相较于在线量化基线 KIVI，压缩与解压缩处理的综合吞吐平均提升约 **8.4×**。
- 在 A100 上，平均压缩吞吐达到 **307.4 GB/s**。
- 平均解压缩吞吐达到 **402.1 GB/s**。
- 在 LongBench 上，VAYNE-4bit 的有效 Bit Rate 约为 **3.70 bits/element**。
- 对应的 LongBench 平均得分为 **44.18**，接近 FP16 的 **44.13**。

不过，在正式介绍方法之前，需要首先澄清一个容易误解的地方。

> **8.4× 是压缩处理吞吐的提升，不是 LLM 端到端推理速度提升了 8.4 倍。**

论文证明了 VAYNE 的压缩 Kernel 很高效，但这与模型实际部署后的 Tokens/s、TTFT、TPOT 和 Goodput 之间，还存在需要进一步验证的系统问题。

带着这个区别来看论文，才能真正理解它的价值。

### 02｜VAYNE 的核心思想：量化之后，为什么还能继续压缩？

这篇论文在算法层面最有意思的地方，是作者并没有停留在传统的低比特量化。而是进一步提出了一个问题：**量化之后的整数，真的都需要使用固定 Bit-width 来存储吗？**

### 2.1 一个简单的例子

假设我们有 8 个已经完成 3-bit 量化的整数：

```text
[4, 5, 5, 4, 5, 5, 5, 5]
```

按照传统的 3-bit 方式存储，每个整数占 3 bits。

因此，一共需要：

```text
8 × 3 = 24 bits
```

但是仔细观察会发现，这些整数虽然位于 0～7 的量化空间，实际却只包含 4 和 5。也就是说，组内数据的数值范围非常小。那么，能不能只保存一个基准值，再保存每个元素与该基准值之间的差？

VAYNE 提出了：**Min-Cut Bit-Packing**这里的 Min-Cut 并不是图论中的最小割，而更接近一种局部的 Frame-of-Reference Encoding。首先找到当前 Group 的最小值：

```text
min = 4
```

然后让组内每个元素减去这个最小值：

```text
Original:
[4, 5, 5, 4, 5, 5, 5, 5]

Min:
4

Residual:
[0, 1, 1, 0, 1, 1, 1, 1]
```

原本每个元素需要 3 bits。现在每个 Residual 只需要 1 bit。为了恢复原始量化整数，还需要保存 Group Minimum 和 Residual Bit-width。于是可以得到：

```text
原始数据：
8 × 3 bits = 24 bits

Min-Cut：
Minimum Metadata   3 bits
Bit-width Metadata 2 bits
Residual Data      8 bits

Total = 13 bits
```

原本的 24 bits，最终只需要 13 bits。注意：**Min-Cut Bit-Packing 不会引入额外的量化误差。**因为只要保留了组内最小值和 Residual，就可以完整恢复之前的量化整数。

但这里要区分两种压缩：

- FP16 → INT3：有损量化。
- INT3 → Min-Cut 编码：无损整数压缩。

因此，VAYNE 并不是对原始 FP16 KV Cache 进行完全无损压缩。

它的实际思路是：**先通过低比特量化减少数值精度，再利用量化整数的局部相似性进一步压缩存储空间。**

### 2.2 为什么这种方法适合 Key Cache？

这就引出了一个很重要的问题。假设量化后得到：

```text
[0, 7, 2, 6, 1, 5, 3, 7]
```

组内最大值和最小值相差很大。那么即使减去 Minimum，Residual 仍然需要 3 bits。此时 Min-Cut 不仅没有明显收益，还需要额外保存 Metadata。

所以，Min-Cut 并不是对任意数据都能获得高压缩率。

它依赖一个关键前提：**同一个 Group 中的数据具有较强的局部数值相似性。**

作者首先对 Llama 3.1 8B 的 KV Cache 进行了可视化分析。

![](https://picx.zhimg.com/v2-c8feb1065e0aa6b9d2b1d0cfb6f9d59b_r.jpg)

论文 Fig. 3 展示了 Key Cache 和 Value Cache 的数据分布。

一个很直观的发现是：Key Tensor 呈现出较为明显的结构化模式，而 Value Tensor 的分布更接近随机。

进一步研究之后，作者发现 Key Tensor 的这种周期性与 RoPE（Rotary Position Embedding）有关。不过，虽然 RoPE 产生的周期性结构看起来具有规律，却不一定适合直接使用 Min-Cut 进行局部数值压缩。

因此，VAYNE 引入了另一个设计。

### 2.3 Pre-RoPE Quantization

在常规 Attention 计算中，Key 通常需要经过 RoPE 位置编码。VAYNE 选择在 RoPE 之前，对 Key 进行量化和压缩。即：

```text
常规思路：

Key
 ↓
RoPE
 ↓
Quantization
 ↓
Compression
```

改为：

```text
VAYNE：

Key
 ↓
Quantization
 ↓
Min-Cut Compression
 ↓
Compressed Cache
```

当后续 Attention 需要使用缓存数据时，再按照对应的计算路径恢复并处理 Key。

为什么要这样做？

作者发现，Pre-RoPE Key Tensor 在相应维度上具有更强的局部数值规律。通过 Channel-wise Quantization，可以让量化后的整数更适合 Min-Cut 编码。这里实际上体现了一个很重要的设计理念：

> 压缩效率不仅取决于压缩算法，还取决于数据在计算图中所处的位置。

同样一个 Tensor，在应用某些算子之前和之后，其数值分布可能发生明显变化。而数据分布的差异，会直接影响压缩率和精度。不过，Pre-RoPE 也意味着后续 Attention 的读取路径需要与缓存格式协同设计。

这点我们在最后的 Discussion 中再讨论。

### 03｜从算法到硬件：怎样把 Min-Cut 做成高性能 CUDA Kernel？

Min-Cut 的数学原理并不复杂。

但如果真正要把它部署到 GPU 上，就会遇到一系列工程问题。

比如：

- Group Size 应该选择多大？
- 不同 Group 的压缩长度不同，该怎么高效存储？
- 多个 Thread Blocks 如何确定压缩结果的写入位置？
- 怎样减少 Kernel Launch 和中间显存访问？
- 如何同时兼顾 Channel-wise 量化和 Coalesced Memory Access？

我认为这一部分才是 VAYNE 最值得阅读的内容。

### 3.1 为什么 Group Size 选择 32？

Min-Cut Bit-Packing 需要将量化整数划分为若干 Group。每个 Group 独立计算 Minimum 和 Residual Bit-width。

Group 越小，数据的局部数值范围通常越容易保持紧凑。

但 Group 越小，需要存储的 Metadata 也可能越多，同时还会影响 GPU 的执行效率。

作者最终采用：**Group Size = 32**

这个数字非常有代表性，NVIDIA GPU 的一个 Warp 通常由 32 个 Threads 组成。让我想到数学里的e了。

让算法的数据处理粒度与 GPU 的 Warp 规模相匹配，能够减少线程组织与数据交换方面的额外开销。

论文实验发现：在 2-bit 量化下，相比 Group Size = 32，使用 Group Size = 16 虽然能够将压缩率提高约 1%，却会造成约 14% 的计算性能下降。

因此，作者选择了 32 作为默认配置。

这说明一个典型的 GPU 优化原则：**压缩率最优，不一定意味着系统性能最优。**算法参数必须同时考虑硬件执行模型。

### 3.2 Bit-Transposing：不规则 Bit-width 怎么写入显存？

Min-Cut 之后，每个 Group 的实际 Bit-width 可能不同。有些 Group 只需要 1 bit，有些需要 2 bits，还有些需要 3 bits。这种变长编码虽然能够节省空间，但会使 GPU 数据写入变得复杂。

例如：

```text
Group 0: 1-bit Residual
Group 1: 2-bit Residual
Group 2: 3-bit Residual
```

如果让每个线程直接写入自己的不规则 Bit 数据，就可能导致：

- 数据跨越字节边界。
- 多个线程需要操作同一个字节。
- 部分字节存在无效填充位。
- 访存模式不规则。

VAYNE 使用 Bit-Transposing 来重组这些 Bit。

核心思想是：**把不规则的按元素存储形式，转换为更适合 Warp 级位操作和连续写入的布局。**这里使用了一个比较重要的 CUDA Primitive：

```text
__ballot_sync()
```

简单理解，Warp 中的每个 Thread 可以贡献一个布尔结果。`__ballot_sync()` 将 32 个线程的判断结果组合为一个 32-bit Bit Mask。

例如：

```text
Thread 0  → 1
Thread 1  → 0
Thread 2  → 1
Thread 3  → 1
...
Thread 31 → 0

       __ballot_sync()
              ↓

         32-bit Mask
```

这样便可以在 Warp 内完成部分跨线程的 Bit Packing。相较于通过 Shared Memory 进行多轮数据交换，这种寄存器级 Warp Primitive 可以减少中间数据搬运与同步需求。不过，Bit-Transposing 并不是单纯把 Bit 重新排列这么简单。

它还需要兼顾：

- Min-Cut Residual 的变长表示。
- Group Minimum 等 Metadata。
- 最终压缩结果的存储对齐。
- 解压时如何正确恢复各个 Group。

这些因素共同决定压缩 Kernel 的实际吞吐。

### 3.3 Kernel Fusion：为什么要尽量避免中间 Tensor？

最直接的压缩 Pipeline 可以写成：

```text
FP16 Key Tensor
       ↓
Quantization Kernel
       ↓
Quantized Tensor
       ↓
Min-Cut Kernel
       ↓
Compressed Tensor
       ↓
Bit Packing Kernel
       ↓
Final Output
```

这种实现方式比较直观。但对于 KV Cache Compression，它会引入一个问题：**为了压缩数据，反而需要分配额外的 GPU 中间缓冲区。**

例如，量化完成后，需要先把 Quantized Tensor 写入 Global Memory。接下来，压缩 Kernel 再从 Global Memory 读取这些数据。这样会产生额外的读写流量。而 VAYNE 希望将多个处理阶段融合起来，其主要压缩 Kernel 集成了量化、Min-Cut、Bit-Transposing，以及后续的 Offset 计算和写入。

不过，有一个非常重要的细节：**VAYNE 并不是将所有操作都完全融合进一个 Kernel。**

论文 Section III-B 明确说明：Channel-wise Min/Max 计算仍然需要一个独立的 Kernel。

原因是不同阶段的数据处理粒度存在差异。量化需要获取每个 Channel 的统计信息。而 Min-Cut 主要以 32 个元素为 Group 处理数据。如果强行将 Channel-wise Min/Max 计算也融合进主要 Kernel，可能造成寄存器资源消耗过高，反而影响性能。

因此，更准确的描述是：**一个独立的 Channel-wise Min/Max Kernel，加上一个高度融合的压缩主 Kernel。**

这也是一个值得注意的工程经验：

> Kernel Fusion 不是融合得越彻底越好，而是要综合考虑 Kernel Launch、Global Memory Traffic、Register Pressure 和 GPU Occupancy。

### 04｜Decoupled Lookback Prefix-Sum：我认为需要特别澄清的优化

这一部分是我在阅读过程中花了较多时间思考的内容。论文将 Decoupled Lookback Prefix-Sum 作为实现融合压缩 Kernel 的关键机制之一。

乍一看，这似乎是在优化 Prefix-Sum 的计算。但进一步思考后会发现：**Prefix-Sum 本身不过是整数加法，真正复杂的计算发生在各个 Block 的压缩过程中。**那么，Decoupled Lookback 到底优化了什么？

### 4.1 为什么压缩需要 Prefix-Sum？

假设 GPU 上有四个 Thread Blocks。每个 Block 负责压缩一段数据。由于各个 Block 的数据分布不同，最终压缩后的长度也不同。

例如：

```text
Block 0 → 15 Bytes
Block 1 →  7 Bytes
Block 2 → 11 Bytes
Block 3 → 22 Bytes
```

如果希望把压缩结果连续写入显存：

```text
Block 0: Offset  0
Block 1: Offset 15
Block 2: Offset 22
Block 3: Offset 33
```

就需要计算每个 Block 的 Exclusive Prefix-Sum。

设第 i 个 Block 的压缩长度为 `s[i]`。

则其写入地址是：

```text
offset[i] = sum(s[0], ..., s[i-1])
```

这个计算并不复杂。

但问题在于：各个 Block 是由 GPU 并行执行的，而普通 CUDA Kernel 并不提供一个可以任意使用的全局 Thread-Block Barrier。因此，如果使用传统多阶段实现，可能需要：

```text
Kernel 1
计算每个 Block 的压缩长度
            ↓
保存 s[i] 到 Global Memory
            ↓
Kernel 2
执行全局 Prefix-Sum
            ↓
Kernel 3
根据 Offset 写入压缩结果
```

这样就引入了额外的 Kernel Launch 和中间数据读写。

### 4.2 Decoupled Lookback 的关键是什么？

它并不是提前知道还没有计算出来的压缩长度。而是区分了两类状态：

**Local Aggregate：**当前 Block 自己的压缩长度 `s[i]`。

**Complete Prefix：**截至当前 Block 的累计长度 `P[i]`。

例如：

```text
B0:
s[0] = 15
P[0] = 15

B1:
s[1] = 7
P[1] = 22

B2:
s[2] = 11
P[2] = 尚未计算完成

B3:
正在查找自己的写入 Offset
```

此时 B3 不一定需要等待 B2 计算出完整的 `P[2]`。因为 B2 已经发布了自己的 `s[2] = 11`。

同时 B1 已经发布：

```text
P[1] = 22
```

所以 B3 可以自行计算：

```text
offset[3] = P[1] + s[2]
```

即：

```text
offset[3] = 22 + 11 = 33
```

这里的关键是：**B3 不需要等待 B2 的完整 Prefix，只需要它已经发布的局部压缩长度。**

通过向前 Lookback，B3 可以组合多个局部长度与某个已经计算完成的前缀结果，获得自己的 Offset。

### 4.3 但如果 B2 连自己的压缩长度都没有算出来呢？

那么 B3 仍然需要等待。

这一点非常重要。Decoupled Lookback 并没有消除真正的数据依赖。如果不知道 B2 最终输出了多少 Bytes，就无法确定 B3 应该从哪里开始写入。

因此，我认为不能将这一优化理解成：“通过某种巧妙算法，让所有 Block 完全不需要同步。”

实际上，它减少的是对相邻前驱**完整 Prefix 结果**的不必要等待，并允许前缀计算与不同 Block 的压缩执行在一定程度上重叠。

### 4.4 那它的性能收益究竟在哪里？

经过进一步分析，我认为它的价值主要体现在两个方面。

**第一，避免独立的全局 Prefix-Sum 阶段：**不需要专门启动多个 Kernel 来完成 Prefix-Sum 和后续写入，减少 Kernel Launch 与额外数据搬运。

**第二，降低跨 Block 的严格串行前缀依赖：**后续 Block 不一定要等待直接前驱获得完整 Prefix，而可以利用已发布的 Local Aggregate 和较早的 Complete Prefix 自行计算 Offset。

但它仍然需要跨 Block 状态发布和查询。如果某个前驱 Block 长时间无法计算出局部压缩长度，后续 Block 仍然可能等待。因此，这不是一种完全没有同步开销的方案。

### 4.5 论文是否证明了 Decoupled Lookback 单独带来很高的加速？

这是我认为需要进一步讨论的地方。

![](https://pic4.zhimg.com/v2-78b6cfaec23746a69c12119f37ce76e1_r.jpg)

论文 Fig. 13 将朴素实现升级为引入 Kernel Fusion 和 Decoupled Lookback 的版本，取得了约 4.3× 的性能提升。

但这里的 4.3× 是组合优化的结果。

**不能将 4.3× 全部归功于 Decoupled Lookback。**

因为 Kernel Fusion 本身就能够消除部分中间 Tensor 和 Global Memory Traffic。

从这组消融结果中，我们无法精确判断：究竟多少收益来自 Kernel Fusion，多少来自 Decoupled Lookback？

另外，还有一个值得研究的替代方案。既然各 Block 只是需要为变长压缩数据分配空间，能否直接使用全局 `atomicAdd` 分配输出 Offset？

这种方法不要求数据按照 Block ID 的顺序存放。如果允许物理存储乱序，并通过 Offset Table 记录映射关系，就有机会避免有序 Prefix-Sum。当然，这也会引入全局原子竞争、额外索引和解压访问成本。

所以在我看来，更有价值的对比应该是：

- Decoupled Lookback
- AtomicAdd 动态分配
- 独立 Prefix-Sum Kernel

在相同压缩算法与数据布局下，比较三者的吞吐、等待时间和中间显存开销。

**因此，我认为 Decoupled Lookback 对 VAYNE 的主要价值，是作为支撑 Kernel Fusion 的关键协调机制，而不是通过减少几次整数加法带来巨大性能提升。**

### 05｜Coalesced Memory Access 与 PTX：如何继续优化 GPU 执行？

VAYNE 的另一项重要优化，是重新组织 GPU 的内存访问模式。

### 5.1 为什么 Channel-wise 量化可能导致访存效率低下？

假设某一层、某个 KV Head 的 Key Tensor 可以简化为：

```text
K[Token, Channel]
```

如果采用普通的 Row-Major 布局，那么同一个 Token 的不同 Channel 在显存中通常是连续存储的。

例如：

```text
Channel →
          C0  C1  C2  C3 ... C63

Token 0   K00 K01 K02 K03 ...
Token 1   K10 K11 K12 K13 ...
Token 2   K20 K21 K22 K23 ...
...
```

假设有 64 个 Channels，每个元素是 FP16。

那么每个 Token 对应的数据量为：

```text
64 × 2 = 128 Bytes
```

如果一个 Warp 中的不同线程分别读取不同 Token 的同一个 Channel：

```text
Thread 0 → K[0,0]
Thread 1 → K[1,0]
Thread 2 → K[2,0]
...
```

那么相邻线程之间的读取地址会相隔 128 Bytes。

这种访问模式不利于 Coalesced Memory Access。

因为 GPU 更希望一个 Warp 内的线程共同访问较连续的显存区域。

### 5.2 VAYNE 如何调整线程映射？

![](https://pic2.zhimg.com/v2-13fe5e183253db70648073445bbc66bb_r.jpg)

论文 Fig. 8 展示了它的访问设计。

核心思路是：

**让 Warp 内的不同线程负责相邻 Channel，而每个线程沿着 Token 方向遍历自己负责的数据。**

例如：

```text
Thread 0  → Channel 0, 1
Thread 1  → Channel 2, 3
Thread 2  → Channel 4, 5
...
Thread 31 → Channel 62, 63
```

当整个 Warp 同时处理 Token 0 时，各线程读取的是连续的 Channel 数据。

在采用 `__half2` 的情况下，每个线程可以加载两个 FP16。

也就是：

```text
2 × 2 Bytes = 4 Bytes
```

一个 Warp 有 32 个线程，所以总共可以共同读取：

```text
32 × 4 = 128 Bytes
```

这能够使整个 Warp 的访问地址形成较连续的区域，有利于 GPU 合并内存请求。

注意：128 Bytes 是这一示例中 Warp 共同读取的有效数据量，不意味着在任何 GPU 架构和对齐条件下一定只对应一次物理显存事务。

这里最容易误解的地方是论文中提到的 Token-wise 读取。它指的是单个线程沿着 Token 维度处理数据。而整个 Warp 在同一轮执行中，仍然可以访问同一个 Token 上连续的 Channel 数据。

两者并不矛盾。

### 5.3 `__half2` 优化的是什么？

CUDA 中：`__half` 表示一个 FP16 数值。

而：`__half2` 可以将两个 FP16 数值打包到一个 32-bit 数据对象中。

例如：

```text
__half2 a;
__half2 b;

__half2 result = __hsub2(a, b);
```

其中 `__hsub2` 可以对两个 FP16 分量分别执行减法。

如果：

```text
a = (a0, a1)
b = (b0, b1)
```

那么结果就是：

```text
(a0-b0, a1-b1)
```

通过这种打包方式，可以减少部分标量指令开销，并与连续的内存访问布局相配合。

不过需要注意：**使用** `**__half2**` **并不自动意味着实现了 Coalesced Memory Access。**

合并访存关注的是整个 Warp 的线程地址分布。

而 `__half2` 更多涉及单个线程的数据加载粒度和向量化算术。

二者是相关但不同的优化。

### 5.4 `clz.b32` 又解决了什么问题？

在 Min-Cut 中，需要计算一组整数差值的最小表示位宽。

假设：

```text
range = groupMax - groupMin
```

其所需位宽可以写为：

```text
bitLength = ceil(log2(range + 1))
```

例如：

```text
range = 5

Binary:
00000000 00000000 00000000 00000101
```

最高有效位位于第 3 个 Bit。

因此只需要 3 bits。

如果按照通用数学形式计算，可以使用 `log2`。

但对于非负整数，实际上只需要计算最高有效位的位置。

PTX 提供了：

```text
clz.b32
```

用于统计 32-bit 整数的 Leading Zeros。

例如，5 的二进制表示前面有 29 个连续的 0。

所以可以计算：

```text
bitLength = 32 - clz(5) = 3
```

对于 `range = 0`，对应位宽为 0。

CUDA 中可以用类似的形式表示：

```text
unsigned int range = groupMax - groupMin;
int bitLength = 32 - __clz(range);
```

这样可以避免通用的浮点对数计算。

不过，编译器本身也可能对部分整数位宽计算进行优化，因此手工 PTX 调优的实际收益仍然需要通过 Profiling 来验证。

从论文消融结果看，最后的 Warp Primitive 和 PTX 优化提供了额外收益，但最大的性能提升依然来自更前面的 Kernel Fusion 和内存访问优化。

### 06｜为了保持精度，VAYNE 还做了哪些设计？

前面主要讨论了压缩率和 GPU 性能。

但 KV Cache 压缩还有一个核心问题：**压缩之后，模型还能不能保持原来的推理能力？**尤其是在低比特场景下，量化误差可能影响 Attention 计算。

VAYNE 主要采用三种轻量化策略。

### 6.1 Pre-RoPE：改善 Key 的量化表现

前面已经介绍了 Pre-RoPE 的数据分布优势。

它不仅有利于 Min-Cut 压缩，还能明显改善低比特场景下的模型精度。

论文 Table VIII 给出了一组很有代表性的消融实验。

在 Llama 3.1 8B、LongBench-v2、2-bit 量化场景下：

```text
Baseline Quantization: 11.7

+ Pre-RoPE:           24.1

+ Min-Cut:            24.1

+ Residual:           25.8

+ Attention Sink:     26.0
```

可以观察到：Pre-RoPE 带来了最明显的精度改善。而加入 Min-Cut 后，精度保持不变。

这也符合我们前面讨论的结论：**Min-Cut 主要负责对量化整数进行无损编码，并不负责修复量化误差。**

### 6.2 Full-Precision Residual：保留最近一部分数据

VAYNE 还保留了一部分最近的 Key 数据，使用 FP16 存储。

这种 Residual 设计有两个作用：

第一，减少近期上下文的量化误差。

第二，使压缩处理的数据规模更符合 GPU 的批处理粒度。

论文将数据处理组织为每次 1024 个元素的粒度。对于未被压缩的剩余部分，会保留为 Residual。当剩余部分太小（少于 256 个元素）时，还会额外保留一个 1024 元素的数据块。这样既服务于执行效率，也能改善模型精度。

### 6.3 Attention Sink Preserving：保留第一个 Token

作者观察到，第一个 Token 的 Key 数据往往存在明显的 Outlier。这些异常值可能扩大 Channel-wise Quantization 的动态范围。

例如：

```text
Typical Values:

4.8, 5.0, 5.2, 5.4

Outlier:

12.7
```

如果将 12.7 与其他数据共同参与量化范围统计，那么大多数普通数值能够分配到的量化精度就可能下降。

因此，VAYNE 将第一个 Token 的 Key 保留为 FP16。

这里需要注意，它虽然与 Attention Sink 现象有关，但在 VAYNE 中，直接目标主要是减少第一 Token 的异常分布对量化精度造成的影响。

从论文的消融结果来看，Residual 和 Attention Sink 都能进一步提高精度。

但它们的贡献明显小于 Pre-RoPE。

### 07｜实验结果：VAYNE 的优势究竟体现在哪里？

论文主要使用 NVIDIA A100 80GB 进行基线对比，并补充了 H100 80GB 上的性能测试。

涉及的模型包括：

- Llama 3.1 8B Instruct
- Mistral-Nemo-Instruct-2407
- Qwen3-30B-A3B-Instruct-2507

评估数据集包括 LongBench、InfiniteBench、LooGLE 和 LongBench-v2。

### 7.1 压缩处理吞吐

VAYNE 在 A100 上报告的平均性能为：

**Compression Throughput：307.4 GB/s**

**Decompression Throughput：402.1 GB/s**

相较于 KIVI，压缩与解压缩处理的综合吞吐平均提升约 8.4×。

在 H100 上，论文报告最高压缩吞吐达到：

**508.6 GB/s**

最高解压缩吞吐达到：

**567.8 GB/s**

这些结果表明 VAYNE 的压缩与解压算子具有很高的处理效率。

但必须再次强调：

GB/s 衡量的是 Compressor 的数据处理速度，不等于 LLM 的 Tokens/s。

### 7.2 压缩率和模型精度

以 Llama 3.1 8B Instruct 在 LongBench 上的结果为例：

| 方法 | 有效 Bit Rate | 平均得分 |
| --- | --- | --- |
| FP16 | 16.00 | 44.13 |
| KIVI-2bit | 3.00 | 39.60 |
| VAYNE-2bit | 1.98 | 38.16 |
| VAYNE-3bit | 2.67 | 42.51 |
| KIVI-4bit | 5.00 | 43.74 |
| VAYNE-4bit | 3.70 | 44.18 |

从数据可以看出：

VAYNE-4bit 在有效存储开销低于 KIVI-4bit 的情况下，保持了接近 FP16 的平均得分。

VAYNE-3bit 在 Bit Rate 仅为 2.67 的情况下，也取得了 42.51 的得分。

但 VAYNE-2bit 的得分低于 KIVI-2bit。

在 LooGLE 中，也能够观察到类似的低位宽精度问题。

因此不能简单地说 VAYNE 在任何配置下都全面优于 KIVI。

更准确的表述应该是：**VAYNE 在多数测试配置中实现了更低的有效 Bit Rate，并且在 3-bit、4-bit 场景下表现出较好的精度与存储效率权衡。**

尤其是在 4-bit 配置下，整体表现较为稳定。

### 7.3 不同 CUDA 优化的贡献

论文 Fig. 13 给出了不同版本的性能消融。

| 优化阶段 | 相对上一版本加速 |
| --- | --- |
| Fusion + Decoupled Lookback | 4.3× |
| Coalesced Memory Access | 1.7× |
| Warp Primitive + PTX Tuning | 1.1× |

我认为这组结果非常值得关注。

它说明：**真正带来最大性能提升的是整体数据流和内存访问方式的调整，而不是最后的 PTX 指令微调。**

Kernel Fusion 减少了不必要的中间显存读写和 Kernel Launch。

Coalesced Memory Access 改善了 GPU 读取原始 Tensor 的效率。

最后的 Warp Primitive 和 PTX 优化，则进一步降低部分指令开销。

这也是非常典型的 CUDA Performance Engineering 思路：

先优化数据流，再优化执行组织，最后才是局部指令。

### 08｜Discussion：我认为这篇论文仍然存在的问题

虽然 VAYNE 在压缩算法与 CUDA Kernel Engineering 方面做得比较完整，但如果从实际 LLM Serving 的角度考虑，我认为还有几个问题值得讨论。

### 8.1 压缩 Kernel 很快，不代表 Decode 阶段一定更快

这是我最关注的问题。

在 LLM Decode 阶段，Attention 需要反复读取历史 KV Cache。

当 KV Cache 以压缩格式存储时，Attention 必须能够消费这些压缩数据。

一种方法是先执行解压：

```text
Compressed KV Cache
        ↓
Decompression Kernel
        ↓
FP16 / Quantized KV
        ↓
Attention Kernel
```

但是，这样可能引入额外的中间 Tensor、Global Memory Traffic 和 Kernel Launch。

另一种方案是将解压逻辑直接融合进 Attention Kernel。

例如：

```text
Compressed KV Cache
        ↓
Fused Decompression
        +
Attention Computation
        ↓
Attention Output
```

这可以避免部分中间数据搬运，但也会带来新的问题：

- 是否增加 Register Pressure？
- 是否影响 Attention Kernel 的线程组织？
- 是否破坏原有的访存连续性？
- 解压计算是否会影响 Attention 的执行效率？
- 不规则 Bit-width 是否会导致额外的分支和地址计算？

因此，我认为真正关键的不是 Compressor 本身达到多少 GB/s。

而是：**在实际 Attention 数据路径中，压缩后节省的显存带宽，能否覆盖解压和寻址带来的额外成本？**

如果不能，那么高 Compression Throughput 并不一定转化为更好的 TPOT 或 Tokens/s。

### 8.2 变长压缩与 PagedAttention 的适配问题

VAYNE 的 Min-Cut 编码具有变长特性。

不同 Group，甚至不同 Block 的压缩长度可能不同。

但在传统 PagedAttention 中，KV Cache 通常按照固定大小的逻辑 Block 组织，通过 Block Table 映射到物理显存。固定 Block Size 能够让地址计算与缓存管理相对简单。而引入变长压缩后，可能需要为每个压缩 Block 记录实际长度与存储 Offset。

这会引入新的问题：**逻辑 Block ID 如何映射到变长的物理压缩数据？**

如果需要额外读取 Offset Metadata，是否会增加访存开销？

如果为了降低寻址成本而采用固定预留空间，又是否会抵消部分压缩收益？

另外，在 Prefix Sharing、KV Cache Eviction 和动态请求调度场景中，变长压缩数据的分配与回收可能更加复杂。

这些问题在单独的压缩算子评测中未必明显，却可能直接影响整个 Serving System 的性能。

### 8.3 Decoupled Lookback 的收益归因仍不够充分

前面已经讨论过，Decoupled Lookback 并不消除所有数据依赖。

它主要通过 Local Aggregate 和 Complete Prefix 的状态发布与查询，避免不必要的完整前缀等待，并支持单 Kernel 内的变长输出地址计算。

但是论文中的性能消融，将 Decoupled Lookback 和 Kernel Fusion 放在同一阶段。

因此，我们无法单独判断两者分别贡献多少性能收益。

我更希望看到以下实验：

**实验一：** 固定压缩算法与访存布局，比较独立 Prefix-Sum 和 Decoupled Lookback。

**实验二：** 将 Offset 分配改为 AtomicAdd，并使用额外的 Offset Table。

**实验三：** 改变不同 Block 的压缩负载分布，观察 Lookback 等待时间和吞吐变化。

特别是第三项。

假设某个前驱 Block 的局部压缩长度迟迟无法产生，那么后续 Block 仍然可能被阻塞。

如果不同 Block 的压缩工作量差异很大，Decoupled Lookback 的性能可能会受到影响。

因此，单独分析跨 Block 等待时间与状态查询开销，会更有助于解释这一设计的实际收益。

### 8.4 Pre-RoPE 需要与 Attention Backend 协同

Pre-RoPE 的数值分布更利于压缩，是 VAYNE 的重要设计。

但普通 Attention 计算需要正确处理 Key 对应的位置编码。

如果缓存的是 Pre-RoPE Key，那么后续读取时就必须在恰当的位置完成 RoPE 相关计算。

在不同 Attention Backend 中，这可能需要调整计算路径。

特别是在支持多种 RoPE 配置、Paged KV Cache 和 Prefix Sharing 的推理框架中，不能只改变 KV Cache 的存储格式，而忽略位置编码的计算顺序。

因此，Pre-RoPE 的压缩策略虽然有利于精度与存储效率，但其通用工程适配仍然需要进一步验证。

### 8.5 Key 的压缩规律未必可以直接推广到 Value

VAYNE 的 Min-Cut 思路依赖量化整数的局部相似性。

论文对 Key Tensor 的分布进行了分析，并利用 Pre-RoPE 改善其压缩友好性。

但 Value Tensor 的数据分布不具有同样明显的结构特征。

所以我认为，后续还需要更细粒度地研究：

- 不同 Layer 的 Key 压缩率是否存在明显差异？
- 不同 KV Head 是否适合不同的量化位宽？
- Value Cache 的实际有效存储开销是多少？
- 能否根据数据分布动态选择编码方式？

特别是在 GQA 和不同模型架构下，各层 KV Cache 的数据特征可能存在差异。

采用统一压缩方案虽然有利于实现简单，但并不一定能获得最优的 Compression Ratio–Accuracy Trade-off。

### 8.6 离线预处理成本需要考虑部署场景

论文将 KVQuant 和 CommVQ 的离线预处理成本作为一个重要比较点。

实验中：

- KVQuant 的离线预处理时间约为 127.04 分钟。
- CommVQ 约为 5639.66 分钟。
- KIVI 和 VAYNE 不需要相应的离线预处理。

这体现了 VAYNE 在线设计的优势。

不过，我认为离线成本也需要结合部署场景来评价。

对于模型长期固定、请求量非常大的生产环境，部分 Calibration 或训练成本可以在大量请求之间摊销。

因此，单纯比较离线预处理时间，还不足以得出各种部署场景下的总体成本结论。

更完整的比较应该考虑：

模型更新频率、在线推理总请求量、平均请求长度、实际显存节省，以及端到端推理吞吐。

### 8.7 缺少更完整的 Serving-Level 指标

对于一个以 LLM Inference 为目标的系统工作，我更希望看到以下指标：

**TTFT（Time to First Token）**压缩是否增加了 Prefill 完成后的处理延迟？

**TPOT（Time Per Output Token）**Decode 阶段读取压缩 KV Cache 后，每个输出 Token 的延迟是否下降？

**Goodput**在给定服务等级目标下，系统能够完成多少有效请求？

**Peak GPU Memory**除了最终压缩后的 KV Cache 大小，峰值显存占用是否也有明显下降？

**Concurrency**在相同 GPU 显存预算下，压缩是否能够让系统容纳更多并发请求？尤其是 P99 Latency。如果压缩引入不规则处理路径，那么尾部延迟是否会受到影响？

这些指标能够帮助我们判断：VAYNE 带来的压缩效率提升，究竟能在多大程度上转化为 LLM Serving 的实际收益。

### 09｜最后：这篇论文给我的启发

读完 VAYNE，我最大的感受是：

**它真正有价值的地方，不只是提出了一种新的 KV Cache 压缩方法，而是展示了如何围绕 GPU 架构设计一套完整的数据处理流程。**

Min-Cut 本身并不复杂。

它利用局部整数的相似性，通过保存 Minimum 和 Residual 降低存储开销。

但如果没有后续的工程优化，这种方法未必能够在 GPU 上高效运行。

作者进一步通过：

- Pre-RoPE 改善数据分布。
- 通过 Group Size = 32 适配 Warp 处理粒度。
- 使用 Bit-Transposing 处理不规则 Bit-width。
- 利用 Kernel Fusion 减少中间显存访问。
- 通过 Decoupled Lookback 在融合 Kernel 内计算变长输出 Offset。
- 使用 Coalesced Memory Access 改善访存效率。
- 最后通过 `__half2`、Warp Primitive 和 PTX 进行指令级优化。

这些设计共同构成了 VAYNE 的性能优势。

我认为它体现了一个非常重要的系统研究思路：

> **算法最优不等于硬件执行最优，而 Kernel 最优也不等于整个推理系统最优。**

在 GPU 上，数据如何排列、线程如何映射、Kernel 如何融合、不同 Block 如何协调，往往与算法复杂度本身同样重要。

但与此同时，我们也不应该把算子性能直接等同于系统性能。

VAYNE 证明了可以在 GPU 上高效执行低比特量化与无损编码。

下一步真正值得探索的是：

**能否让 Attention Kernel 直接高效消费变长压缩的 KV Cache，而不必完整恢复中间 FP16 Tensor？**

进一步说，能否把压缩存储格式、PagedAttention Block Management、KV Cache 调度和 Attention Kernel 放在同一个设计空间中协同优化？

如果可以，那么这类技术的价值就不仅仅是压缩率更高或 Compressor 更快。

它有机会真正改善大模型推理系统的显存利用率、并发能力和服务成本。

这或许才是 Near-Zero Cost KV Cache Compression 值得继续研究的方向。
