## 从 FlashAttention 到 PagedAttention：大模型推理加速背后的两把钥匙

> **一句话概括：FlashAttention 解决“Attention 怎么算得更快”，PagedAttention 解决“KV Cache 怎么放得更省”。**<br>前者像优化厨师炒菜动作，后者像优化仓库货架管理。一个主要优化计算过程，一个主要优化显存管理。<br>

---

## 0. PageAttention 与 PagedAttention 简介

在大模型推理系统里，常见的说法是 **PagedAttention**，可以翻译为**分页注意力**或**页式注意力**。它是 vLLM 推理系统中的核心设计之一，灵感来自操作系统里的虚拟内存和分页机制。

另一个常被一起讨论的是 **FlashAttention**，可以翻译为**闪存注意力**或**快速注意力**。它来自 Tri Dao 等人的工作，核心是让 Attention 计算更少访问显存、更快完成。

二者都与 Transformer 里的 Attention 有关，但层次不同：

| 技术 | 主要解决的问题 | 通俗比喻 |
| --- | --- | --- |
| FlashAttention | Attention 计算慢，中间矩阵显存读写多 | 厨师炒菜手法更高效 |
| PagedAttention | KV Cache 占显存大、碎片多、并发低 | 仓库货架/酒店房间分配更高效 |

## 1. Attention 为什么会成为大模型推理瓶颈？

### 1.1 Transformer 和 Attention 的基本直觉

现代大语言模型大多基于 **Transformer Architecture（Transformer 架构）**。它的核心组件之一是 **Attention Mechanism（注意力机制）**。

通俗理解，Attention 就像学生做阅读理解：

> 当前这个词提出问题：“我应该重点参考前文哪些词？”<br>前文每个词提供线索：“我这里有一部分信息。”<br>模型根据相关性分配注意力权重，再把有用信息汇总起来。<br>

Attention 的经典公式是：

$ \mathrm{Attention}(Q,K,V)=\mathrm{softmax}\left(\frac{QK^T}{\sqrt{d_k}}\right)V $

这里第一次出现几个专业名词：

- **Q，Query（查询向量）**：当前 token 提出的问题。
- **K，Key（键向量）**：历史 token 的索引标签。
- **V，Value（值向量）**：历史 token 真正携带的内容。
- **Token（词元）**：模型处理文本的基本单位，不一定等于一个汉字或一个单词。
- **Softmax Function（归一化指数函数）**：把一堆分数变成一组概率权重。
- **Attention Score Matrix（注意力分数矩阵）**：`QK^T` 得到的相关性分数表。

如果序列长度是 `N`，普通 Attention 的分数矩阵大小大约是 `N × N`。上下文越长，这张表膨胀越快。

例如 `N = 8192` 时，单个 head 的分数矩阵就约有：

```text
8192 × 8192 ≈ 6700 万个元素

```

这还没有乘上 batch size 和 attention head 数量。

## 2. KV Cache：大模型生成时的“课堂笔记”

理解 PagedAttention 前，必须先理解 **KV Cache，Key-Value Cache（键值缓存）**。

大模型生成文本一般分为两个阶段：

- **Prefill Phase（预填充阶段）**：一次性处理用户输入的 prompt。
- **Decoding Phase（解码阶段）**：一个 token 一个 token 地生成回答。

假设用户输入：

```text
北京 是 中国 的

```

模型要继续生成：

```text
首都 。

```

### 2.1 不用 KV Cache：每生成一个字，都重新读全文

不用 KV Cache 时，模型生成第一个新 token，需要处理：

```text
北京 是 中国 的

```

生成出“首都”后，下一步要生成“。”，上下文变成：

```text
北京 是 中国 的 首都

```

如果没有缓存，模型又要重新处理一遍完整上下文。

这就像：

> 每写一个新字，都把前文重新读一遍、重新做笔记、重新总结。<br>

如果 prompt 有 1000 个 token，要继续生成 100 个 token，不用缓存时，大致会反复处理：

```text
1000 + 1001 + 1002 + ... + 1099

```

这里每个 token 还要经过几十层 Transformer，里面有 Attention、MLP、LayerNorm 等模块，所以非常耗时。

第一次出现的术语说明：

- **MLP，Multi-Layer Perceptron（多层感知机）**：Transformer 层里的前馈网络部分。
- **LayerNorm，Layer Normalization（层归一化）**：让中间特征更稳定的一种归一化操作。

### 2.2 使用 KV Cache：前文笔记已经做好，只查笔记并补新笔记

使用 KV Cache 后，模型在 Prefill 阶段会把历史 token 在每一层 Attention 中算出的 K 和 V 存起来。

缓存可以理解为：

```text
第 1 层:
  K: [K_北京, K_是, K_中国, K_的]
  V: [V_北京, V_是, V_中国, V_的]

第 2 层:
  K: [K_北京, K_是, K_中国, K_的]
  V: [V_北京, V_是, V_中国, V_的]

...

第 N 层:
  K: [K_北京, K_是, K_中国, K_的]
  V: [V_北京, V_是, V_中国, V_的]

```

注意：**每一层都有自己的 KV Cache**，不是整个模型只存一份。

后续生成时，历史 token 的 K/V 不需要重新从文字计算。当前新 token 只需要生成新的 Q，然后拿这个 Q 去和历史 K 做匹配，再根据历史 V 汇总信息。

也就是：

```text
当前 Q_new
  ↓
和历史 K_cache 做相似度计算
  ↓
Softmax 得到注意力权重
  ↓
加权汇总历史 V_cache
  ↓
生成下一个 token
  ↓
把新 token 的 K/V 追加进 KV Cache

```

### 2.3 KV Cache 不是“零成本查表”

这里容易有一个误解：既然 K/V 缓存了，后面是不是只要像数据库一样查表？

不是。

KV Cache 不是普通的：

```text
key -> value

```

它更像：

> 当前问题 Q，要和所有历史 K 逐个比较，判断该关注谁；再根据 V 做加权汇总。<br>

所以缓存后仍然要计算：

$ Q_{new}K_{cache}^T $

也仍然要做 Softmax 和乘 V。

但是它省掉了更重的部分：**历史 token 不用反复通过完整 Transformer，也不用反复计算历史 K/V 和历史 MLP。**

可以这样对比：

| 项目 | 不用 KV Cache | 使用 KV Cache |
| --- | --- | --- |
| 历史 token 的 K/V | 每一步重新计算 | 只算一次，后面复用 |
| 历史 token 的 MLP | 每一步重新计算 | 不再重算 |
| 当前 token 的 Q/K/V | 需要计算 | 仍然需要计算 |
| 当前 Q 和历史 K 的匹配 | 需要计算 | 仍然需要计算 |
| 显存占用 | 较少 | 较多，因为要保存 K/V |
| 生成速度 | 慢 | 快很多 |

所以 KV Cache 的本质是：

> **用显存空间换计算时间。**<br>

## 3. FlashAttention：让 Attention 计算少搬数据

### 3.1 GPU 里谁负责存储，谁负责计算？

理解 FlashAttention，要先理解 GPU 的存储层级。

- **HBM，High Bandwidth Memory（高带宽显存）**：GPU 外部的大容量显存，容量大，但离计算单元较远。
- **SRAM，Static Random Access Memory（静态随机存取存储器）**：GPU 芯片内部的小容量高速存储，速度快，但容量小。
- **Register（寄存器）**：离计算单元最近的小存储空间。
- **Shared Memory（共享内存）**：一个线程块内部共享的片上高速存储。
- **CUDA Core（CUDA 核心）**：NVIDIA GPU 中执行通用计算的核心。
- **Tensor Core（张量核心）**：NVIDIA GPU 中专门加速矩阵乘法的硬件单元。

关键点是：

> HBM 主要负责存数据，不负责大模型里的矩阵乘法。<br>SRAM 也是存储，不是主要计算单元。<br>真正计算的是 CUDA Core 和 Tensor Core。<br>

可以用厨房比喻：

| GPU 部件 | 厨房类比 |
| --- | --- |
| HBM | 大仓库 |
| SRAM / Shared Memory | 灶台旁小货架 |
| Register | 厨师手里的小碗 |
| Tensor Core / CUDA Core | 厨师和锅 |

数据通常长期放在 HBM 中，计算前搬到片上高速存储附近，再由计算单元处理。FlashAttention 要优化的，正是这个“搬数据”的过程。

### 3.2 不用 FlashAttention，也会使用 SRAM

这点非常重要。

普通 Attention 并不是完全不用 SRAM。GPU 做矩阵乘法时，本来就会把 Q、K、V 的小块搬到片上存储中计算。

普通 Attention 的问题不是“不用 SRAM”，而是：

> 每个阶段内部会用 SRAM，但阶段之间的大中间结果会写回 HBM。<br>

普通 Attention 通常分成几个阶段：

```text
1. S = QK^T
2. P = softmax(S)
3. O = PV

```

可以理解为多个 GPU kernel 分开执行。

第一次出现术语：

- **Kernel（计算内核）**：GPU 上执行的一段底层并行程序。
- **Kernel Fusion（内核融合）**：把多个计算步骤合并到一个 kernel 中，减少中间结果读写。
- **Materialize（物化/落地保存）**：把中间结果真实写入显存。

普通流程大致是：

```text
从 HBM 读 Q、K
  ↓
用片上存储计算 S = QK^T
  ↓
把完整 S 写回 HBM
  ↓
从 HBM 读 S
  ↓
做 Softmax 得到 P
  ↓
把完整 P 写回 HBM
  ↓
从 HBM 读 P 和 V
  ↓
计算 O = PV
  ↓
把 O 写回 HBM

```

这里最浪费的是：完整的 S 和 P 都是 `N × N` 大矩阵，会反复写入和读出 HBM。

### 3.3 FlashAttention 的核心：分块、融合、在线 Softmax

FlashAttention 的关键思想是：

> 不把完整的 Attention Score Matrix 和 Softmax 权重矩阵写回 HBM，而是分块计算，在片上存储中尽量完成更多工作。<br>

第一次出现术语：

- **Tiling / Blocking（分块计算）**：把大矩阵切成小块处理。
- **IO-aware Algorithm（IO 感知算法）**：设计算法时不仅考虑计算量，还考虑数据读写量。
- **Online Softmax（在线 Softmax）**：不等整行分数全部落地，而是一边读分块，一边维护 Softmax 所需统计量。

FlashAttention 流程可以简化为：

```text
从 HBM 读一小块 Q/K/V
  ↓
放进片上高速存储
  ↓
计算局部 QK^T
  ↓
在线更新 Softmax
  ↓
立刻乘 V，更新输出累加器
  ↓
丢掉局部分数
  ↓
处理下一块
  ↓
最后只把最终 O 写回 HBM

```

它不是近似算法，不是少看 token，而是**改变计算顺序**，避免把巨大中间矩阵写回 HBM。

## 4. FlashAttention 如何做 Softmax？

这是 FlashAttention 最巧妙的地方。

### 4.1 普通 Softmax：先看完整一行

假设某个 token 对历史 token 的分数是：

```text
[1, 3, 2, 5]

```

普通稳定版 Softmax 会先找最大值：

```text
m = 5

```

然后计算：

$ \mathrm{softmax}(x_i)=\frac{e^{x_i-m}}{\sum_j e^{x_j-m}} $

这里减最大值是为了 **Numerical Stability（数值稳定性）**，避免 `exp(1000)` 这类指数运算上溢。

普通 Attention 往往先得到完整分数矩阵，再逐行做 Softmax。

### 4.2 FlashAttention：分块看，但结果完全一样

FlashAttention 不一次性看到完整 `[1, 3, 2, 5]`，而是分块看：

```text
第一块：[1, 3]
第二块：[2, 5]

```

它对每一行维护三个量：

```text
m   : 当前已经见过的最大值
l   : 当前 Softmax 分母
acc : 当前加权和累加器

```

初始：

```text
m = -∞
l = 0
acc = 0

```

第一块 `[1, 3]` 的最大值是 3，于是先按 3 作为基准计算局部分母和加权和。

第二块 `[2, 5]` 出现了新的最大值 5。此时第一块之前按 3 算的结果，需要统一换算到以 5 为基准。

换算公式来自：

$ e^{x-5}=e^{x-3}\times e^{3-5} $

也就是说，之前的统计量只要乘一个缩放系数 `e^{3-5}`，就能变成以新最大值为基准的结果。

更新公式可以写成：

```text
m_new = max(m_old, m_block)

l_new =
exp(m_old - m_new) × l_old
+
exp(m_block - m_new) × l_block

acc_new =
exp(m_old - m_new) × acc_old
+
exp(m_block - m_new) × acc_block

```

最后输出：

```text
O = acc / l

```

这样虽然是一块一块算，但结果和一次性对完整行做 Softmax 完全一致。

### 4.3 最形象的理解

普通 Attention 像是：

> 先把全校所有学生成绩打印成一张巨大表，再找最高分、算比例。<br>

FlashAttention 像是：

> 一个班一个班地看，只维护当前最高分、累计分母和累计加权结果。如果后面出现更高分，就把前面的统计结果按新最高分重新缩放。<br>

所以 FlashAttention 的 Softmax 不是少算，而是：

> **不把大表完整打印出来。**<br>

## 5. PagedAttention：让 KV Cache 像操作系统内存一样管理

FlashAttention 优化的是 Attention 计算过程；PagedAttention 优化的是大模型推理服务中的 KV Cache 管理。

### 5.1 为什么 KV Cache 管理会成为瓶颈？

在高并发推理服务中，不同用户请求长度不一样：

| 用户 | 输入长度 | 输出长度 | KV Cache 特点 |
| --- | --- | --- | --- |
| A | 很短 | 很短 | 占用少 |
| B | 很长 | 很长 | 占用多 |
| C | 很短 | 生成很长 | 动态增长 |
| D | 提前结束 | 需要释放 |  |

如果系统为每个请求预留一大段连续显存，就像酒店给每个客人都预留一整层楼：

> 有人只住一间，有人要住十间，有人临时续住，有人提前退房。<br>最后很多房间空着，但因为分配不灵活，别人也用不了。<br>

这就是 **Memory Fragmentation（内存碎片）**。

碎片有两类：

- **Internal Fragmentation（内部碎片）**：分配的块内部没用满。
- **External Fragmentation（外部碎片）**：空闲空间散落各处，难以拼成一大块连续空间。

在大模型服务里，KV Cache 很大且动态增长。如果管理不好，即使显存总量看起来还有空闲，也可能无法容纳更多请求。

### 5.2 操作系统分页思想：逻辑连续，物理不连续

PagedAttention 借鉴了操作系统的虚拟内存设计。

首次出现术语：

- **Virtual Memory（虚拟内存）**：程序看到的逻辑连续地址空间。
- **Physical Memory（物理内存）**：真实硬件上的内存。
- **Page（页）**：操作系统中固定大小的内存管理单位。
- **Page Table（页表）**：记录虚拟页到物理页映射关系的数据结构。

操作系统里，程序以为自己拥有一段连续内存，但真实物理内存可以分散在不同位置。页表负责把逻辑地址翻译成物理地址。

PagedAttention 把这个思想搬到 KV Cache 上。

在 vLLM 中，KV Cache 会被切成固定大小的 **KV Block（KV 缓存块）**。每个 block 保存固定数量 token 的 K/V。请求看到的是逻辑连续的 token 序列，但实际物理显存中的 block 可以不连续。

### 5.3 Block Table：PagedAttention 的“前台登记表”

PagedAttention 中最关键的数据结构可以理解为 **Block Table（块表）**。

假设一个请求逻辑上有 6 个 KV block：

```text
逻辑 block:  0   1   2   3   4   5

```

它们在物理显存中可能分布为：

```text
物理 block: 17  03  42  09  28  11

```

Block Table 记录的就是：

```text
逻辑 block 0 -> 物理 block 17
逻辑 block 1 -> 物理 block 03
逻辑 block 2 -> 物理 block 42
...

```

这就像酒店前台：

> 客人以为自己的行李按 1、2、3、4 顺序排放；<br>实际上可能分散在不同储物柜里；<br>前台登记表知道每件行李在哪。<br>

这样做的好处是：

1. 不要求一整段连续显存；
2. 生成到哪里，就分配到哪里；
3. 请求结束后，可以按 block 释放；
4. 多个请求可以共享相同 block。

### 5.4 生成时如何追加 KV Cache？

假设 block size 是 16，也就是每个 block 存 16 个 token 的 K/V。

一个请求刚处理完 35 个 token，就需要：

```text
block 0: token 1-16
block 1: token 17-32
block 2: token 33-35，剩余位置暂时为空

```

当继续生成新 token 时：

- 如果最后一个 block 还有空间，就继续写进去；
- 如果写满了，就申请一个新的物理 block；
- Block Table 增加一条逻辑到物理的映射。

这就避免了一开始为最大生成长度预留巨大连续显存。

### 5.5 PagedAttention 不是让 Attention 少算，而是让 KV Cache 好管理

这里也容易误解。

PagedAttention 不会让当前 token 不看历史 K/V。生成时仍然要做：

```text
Q_new 和历史 K_cache 做注意力打分
根据历史 V_cache 汇总信息

```

不同的是，历史 K/V 可能分散在多个物理 block 中。PagedAttention 的 attention kernel 会根据 Block Table 找到这些 block，再完成计算。

它解决的是：

> KV Cache 存在哪里、怎么分配、怎么释放、怎么共享。<br>

而不是：

> 直接减少 Attention 的数学计算量。<br>

### 5.6 Copy-on-Write：共享前缀，修改时再复制

PagedAttention 还有一个非常重要的能力：**Copy-on-Write（写时复制）**。

首次出现术语：

- **Reference Count（引用计数）**：记录某个物理 block 被多少个请求或序列共享。
- **Parallel Sampling（并行采样）**：同一个 prompt 同时生成多个候选回答。
- **Beam Search（束搜索）**：保留多个候选生成路径，逐步扩展最有希望的路径。

假设一个 prompt 是：

```text
请给我写三个不同版本的项目介绍：

```

模型要同时生成三个候选回答。这三个回答的 prompt 完全一样，所以 prompt 对应的 KV Cache 没必要复制三份。

PagedAttention 可以让三个序列的逻辑 block 指向同一批物理 block：

```text
候选 A 的 prompt block -> 物理 block 10
候选 B 的 prompt block -> 物理 block 10
候选 C 的 prompt block -> 物理 block 10

```

只要它们没有改动这部分内容，就共享。

当某个候选继续生成出不同 token，需要写入新内容时，再为它分配新的 block。

这就像几个人合租：

> 客厅和厨房共享，只有卧室不同。<br>不需要每个人都复制一套完整房子。<br>

### 5.7 Prefix Cache：相同前缀可以跨请求复用

**Prefix Cache（前缀缓存）** 是 PagedAttention 很自然的扩展能力。

很多线上请求有相同开头，例如：

```text
你是一个采购合同审核专家。请根据以下规则审核合同：
...

```

如果每个请求都重复处理这一大段系统提示词，会浪费大量 Prefill 计算。

Prefix Cache 的核心是：

> 已经处理过的相同前缀，其 KV blocks 可以缓存起来；新请求如果拥有相同前缀，就直接复用这些 blocks。<br>

vLLM 的文档中提到，Prefix Caching 会缓存已处理请求的 KV-cache blocks，新请求出现相同 prefix 时可以复用，从而避免重复 prompt 计算。

工程上通常会为 block 计算 hash。第一次出现术语：

- **Hash（哈希）**：把一段内容映射成一个短标识，用于快速判断是否相同。
- **LRU，Least Recently Used（最近最少使用）**：缓存淘汰策略，优先淘汰最久没用的内容。

Prefix Cache 对智能体、RAG、合同审核、代码助手这类场景特别有价值，因为这些应用经常有很长且重复的系统提示词、规则说明、工具说明或文档模板。

### 5.8 Continuous Batching：PagedAttention 的好搭档

**Continuous Batching（连续批处理）** 是大模型推理服务常用的调度技术。

普通静态 batching 像是：

> 一批人一起上车，必须等最慢的人到终点，这辆车才能接下一批人。<br>

Continuous Batching 像是：

> 每一轮生成后，有人结束就下车，新请求立刻补上车。<br>

这能提高 GPU 利用率，但也要求 KV Cache 能动态分配和释放。否则请求频繁进出 batch，显存管理会非常混乱。

PagedAttention 正好适合这种场景：

- 新请求进来：按需分配 block；
- 老请求继续生成：追加 block；
- 请求结束：释放 block；
- 多个请求共享前缀：复用 block。

所以 vLLM 的高吞吐通常不是单靠一个技术，而是由 PagedAttention、Continuous Batching、调度策略、Prefix Cache 等共同构成。

### 5.9 PagedAttention 的代价和边界

PagedAttention 不是没有成本。

第一，物理 block 不连续，attention kernel 读取 K/V 时需要通过 Block Table 间接寻址，会有一定开销。

第二，block size 有权衡：

- block 太大：最后一个 block 可能浪费更多空间；
- block 太小：Block Table 更大，调度和寻址开销更高。

第三，它主要优化 KV Cache 显存利用率和并发吞吐，不直接减少当前 token 对历史 K/V 的注意力计算。

第四，它需要专门的 attention kernel 支持这种分页 KV Cache 布局。不是任意普通 attention kernel 都能直接高效使用 PagedAttention 的内存布局。

所以它最适合：

- 高并发推理服务；
- 长上下文请求；
- 输出长度不确定的在线服务；
- 多候选生成、Beam Search、Parallel Sampling；
- 大量请求共享相同 prompt 前缀的场景。

## 6. FlashAttention 与 PagedAttention 的核心区别

| 对比项 | FlashAttention | PagedAttention |
| --- | --- | --- |
| 优化对象 | Attention 计算过程 | KV Cache 显存管理 |
| 主要阶段 | 训练、Prefill、长上下文 Attention 计算 | Decode、高并发推理服务 |
| 核心思想 | 分块计算 + 在线 Softmax + 减少 HBM 读写 | KV Cache 分块 + Block Table + 按需分配 |
| 是否改变数学结果 | 不改变，精确 Attention | 不改变，主要改变缓存布局 |
| 主要节省 | 中间矩阵 S/P 的显存读写 | KV Cache 的碎片和重复拷贝 |
| 类比 | 厨师炒菜动作优化 | 仓库货架管理优化 |
| 典型收益 | 单次 Attention 更快、更省中间显存 | 更高并发、更大 batch、更高吞吐 |

一句话总结：

> **FlashAttention 管“怎么算”；PagedAttention 管“怎么放”。**<br>

## 7. 两者如何在真实推理系统里配合？

一个真实的大模型服务系统通常同时面临两类问题。

### 7.1 Prefill 阶段：输入长，计算重

用户输入很长 prompt 时，模型要一次性处理所有输入 token。这时 Attention 计算很重，FlashAttention 这类高效 kernel 很重要。

### 7.2 Decode 阶段：并发多，KV Cache 大

生成阶段每一步只生成一个 token，但所有活跃请求都要保留 KV Cache。用户越多、上下文越长、生成越长，KV Cache 越容易成为显存瓶颈。

这时 PagedAttention 更关键。

### 7.3 一起理解

可以用一条生产线来类比：

- FlashAttention：让加工机器更快。
- PagedAttention：让仓库、货架、库存周转更高效。
- Continuous Batching：让生产线不断料，不空转。
- Prefix Cache：常用半成品提前备好，下次直接复用。

如果你部署的是 Qwen、DeepSeek、Llama 这类模型，尤其在 vLLM 这类推理框架中，往往会同时接触到这些优化。

## 8. 工程落地时应该关注哪些参数？

以 vLLM 这类推理框架为例，以下参数和概念经常与 KV Cache / PagedAttention 有关：

### 8.1 `max_model_len`

最大上下文长度。它越大，单个请求最多可能占用的 KV Cache 越多。

### 8.2 `max_num_seqs`

同时处理的序列数。它越大，并发潜力越高，但 KV Cache 压力也越大。

### 8.3 `gpu_memory_utilization`

GPU 显存利用比例。设得太低，吞吐上不去；设得太高，容易 OOM。

首次出现术语：

- **OOM，Out of Memory（内存不足）**：显存或内存不够导致任务失败。

### 8.4 `block_size`

每个 KV block 容纳多少 token。它影响内部碎片、Block Table 大小和 attention kernel 的访问效率。

### 8.5 Prefix Cache 开关

对于大量共享系统提示词、规则文本、工具说明的业务，Prefix Cache 往往非常有价值。

## 9. 用一个采购合同审核系统做类比

假设你要部署一个采购合同审核智能体，很多请求都有相同的系统提示词：

```text
你是采购合同审核专家。
请根据以下审核规则检查合同风险：
1. 供应商信息一致性
2. 金额大小写一致性
3. 设备清单完整性
4. 履约时间逻辑冲突
...

```

然后每个用户上传不同合同。

### 没有 Prefix Cache / PagedAttention

每个请求都要重复处理相同规则 prompt，并为每个请求预留大段 KV Cache，显存浪费严重。

### 有 Prefix Cache + PagedAttention

相同规则部分的 KV Cache 可以复用；不同合同部分按 block 动态分配；请求结束后 block 可以回收。

这就像：

> 审核规则手册不必每个审核员复印一整本；<br>大家共用同一本规则索引，只为各自合同做新增笔记。<br>

在高并发合同审核、招标文件分析、智能问答系统中，这类优化会直接影响吞吐、延迟和部署成本。

## 10. 最终总结

### 10.1 KV Cache

KV Cache 是大模型生成时的“课堂笔记”。

- 不用 KV Cache：每生成一个 token，都重新处理历史上下文。
- 使用 KV Cache：历史 K/V 已经存好，只需要当前 Q 去查历史 K/V，再追加新 K/V。
- 它用显存换时间，显著减少重复计算。

### 10.2 FlashAttention

FlashAttention 是 Attention 计算层面的优化。

- 普通 Attention 也使用 SRAM，但阶段之间会把巨大中间矩阵写回 HBM。
- FlashAttention 通过分块计算、内核融合和在线 Softmax，避免完整物化 `QK^T` 和 Softmax 权重矩阵。
- 它主要减少 HBM 读写，提高 Attention 计算效率。

### 10.3 PagedAttention

PagedAttention 是推理服务显存管理层面的优化。

- 它把 KV Cache 切成固定大小 block。
- 请求逻辑上看到连续 KV Cache，物理上可以分散存放。
- Block Table 负责逻辑 block 到物理 block 的映射。
- Copy-on-Write 支持多候选生成时共享前缀。
- Prefix Cache 支持跨请求复用相同 prompt 前缀。
- 它尤其适合高并发、长上下文、输出长度不确定的大模型服务。

### 10.4 最形象的一句话

> **KV Cache 是模型的笔记本；FlashAttention 是更快的阅读和摘抄方法；PagedAttention 是更聪明的笔记本存放和共享方式。**<br>
