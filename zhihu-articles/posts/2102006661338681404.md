我用 Claude Code、Codex 这类命令行智能体管科研项目已经有一段时间了。用下来的感受是：它相当于一个中等级别的工程师，能实打实提高效率。但它有个绕不开的问题：**每次开会话，都从零开始**。

先说结论：给它一套**分层的目录卡片**。卡片写在智能体启动时自动读取的说明文件里，只写项目里有什么、在哪、什么情况下去看，细节等用到时再读。

- 索引要覆盖完整，但每一项点到为止。
- 判断一行该不该写进去，只问一句：这一行不写，智能体会不会做错事？
- 每一项都写成「遇到这种情况 → 去哪里」，不要只写路径。

例子取自我的电催化 CO₂ 还原课题，做法本身不限学科。下文把说明文件统一叫「说明文件」：Claude Code 用 `CLAUDE.md`，Codex 用 `AGENTS.md`，其他工具也有等价的文件。

## 一、两种极端

科研项目的信息很散：文献和笔记、实验数据、处理和画图脚本、申请审批表格、试剂库存、计算服务器、各种方案模板。智能体每次会话都从零开始，于是容易走向两种极端：

- **什么都不告诉它**：它在目录里乱翻，重写一份已经有的脚本，套错模板，引用的文献也找不到本机 PDF。
- **什么都塞给它**：把所有文件清单、方案细节都写进说明文件，每次会话全量加载。上下文被占满，真正要遵守的规则反而被淹没；写得越细，也越容易过时。

这套工作流取中间：给智能体一份索引，像图书馆的目录卡片。卡片不放书的全文，只告诉你书在哪个架子、什么时候该去翻。

## 二、索引放在项目旁边，还是做成 skill

|  | A：索引放在工作目录的说明文件里 | B：索引做成一个 skill |
| --- | --- | --- |
| 怎么生效 | 在这个目录（或子目录）里开会话就自动加载 | 智能体判断任务和 skill 的描述相符时才加载正文 |
| 适合放什么 | 和具体项目、目录绑定的信息：文献在哪、这个课题的数据和方案在哪、当前任务 | 跨项目通用的流程：怎么提交审批、文档排版规范、某个工具怎么用 |
| 好处 | 和项目文件放在一起，目录调整时顺手就改了；可以按目录分层继承；不依赖触发判断 | 不在目录里也能用；不触发就不占上下文 |
| 代价 | 每次都加载，所以必须精简；离开这个目录就不生效 | 能不能触发取决于描述写得准不准；项目特有的路径写进 skill，容易和项目实际脱节 |

我用的是 **A**：进入课题目录，索引就在，按图索骥。B 也没有被排除：通用流程我做成了 skill（比如钉钉审批、Office 文档排版规范），再在说明文件里写明「遇到什么情况用哪个 skill」。**说明文件管去哪找，skill 管怎么做**。

## 三、索引里放什么

以电催化课题为例，一份完整的索引至少包括下面几类。「索引里写什么」是留在说明文件里的部分，「细节放哪」是用到时才读的部分。

| 类别 | 智能体拿它做什么 | 索引里写什么 | 细节放哪 |
| --- | --- | --- | --- |
| 文献路径与文献索引 | 拟定实验方案、和文献数据对比、写参考文献 | PDF 统一放在哪；每个课题的文献总表在哪；「查文献先看总表」 | 课题的 文献索引.xlsx |
| 实验数据处理脚本 | 算平均电流、换算电位、算法拉第效率 | 「遇到什么数据、要算什么 → 用哪个脚本」；脚本里写死的参数这类坑 | 脚本仓库自己的说明文件 |
| 数据绘图脚本 | 按固定风格出 FE 图、XRD 图 | 「要画什么图 → 用哪个脚本」；一次性调整就复制一份去改，不改原脚本 | 同上 |
| 申请审批表格 | 约仪器测试、申领试剂、申购 | 模板在哪；样品编号规则；填好的放哪；提交审批用哪个 skill | 模板目录的 README.md |
| 试剂与耗材库存 | 写方案的物料部分、写申购清单 | 「先查库房清单、标仓位，没有再申购」 | 库存表本身 |
| 计算资源 | 制定 DFT / MLP 计算方案 | 服务器说明文档在哪；计算目录；默认软件版本和参数 | 服务器说明文档 |
| 方案文件格式 | 写实验方案、计算方案 | 实验方案用什么格式、照哪份版式；计算方案用什么格式 | 那份版式样例文件 |
| 当前任务 | 接着上次的工作往下做 | 现在执行哪份方案，结果放哪 | 方案文件本身 |

## 四、按目录分层

说明文件可以放在不同层级的目录里。在子目录开会话时，上层的会一起加载。我分成这几层：

![](https://pica.zhimg.com/v2-6022e18db333d21c9b6dc559aebf7a86_r.jpg)
*分层的说明文件*

| 层 | 例子 | 写什么 |
| --- | --- | --- |
| 全局 | 用户目录下的说明文件 | 和科研无关的通用约定：文档语言、软件放哪、Python 环境 |
| 科研总目录 | 科研课题\CLAUDE.md | 各课题共用的：本机和服务器怎么分工、方案格式、文献存放规则、脚本索引、共用模板目录 |
| 课题 | SnTi\CLAUDE.md | 只属于这个课题的：计算设置、当前任务、目录、文献总表 |
| 子目录 | SnTi\0922\CLAUDE.md | 只管这个子目录的约定（如脚本一律用相对路径） |
| 按需读取 | 各目录的 README.md、表格里的「说明」页 | 文件清单、每个文件是什么 |

每层只写本层的事，下层不重复上层已经写过的规则。

## 五、规则和描述分开

判断某一行该不该留在说明文件里，只问一句：**这一行不写，智能体会不会做错事**？

![](https://pic4.zhimg.com/v2-180a55619925f0dbe14aa05098e5f055_r.jpg)
*规则留下，描述挪走*

| 留在说明文件（不写会做错） | 挪进 README 或索引表（只是描述） |
| --- | --- |
| 规则：实验方案用 docx，计算方案用 md；PDF 不复制进课题目录 | 某个目录里有哪些文件，每个文件写了什么 |
| 坑：电位换算脚本把参比电位和 pH 写死在代码里 | 已归档目录里每个子目录的内容 |
| 当前任务：现在要执行哪份方案 | 某份实验方案里的具体参数（文件里本来就有） |
| 命名规则：样品编号「人-体系-批次」 | 会变的数据，如墨水配方（放 SOP，索引里只写去哪查） |
| 「遇到什么情况去读哪份文件」 | 目录迁移、整理的完整来历 |

描述放在说明文件里有两个害处：

1. **冲淡规则**：加载的内容越多，每条规则分到的注意力越少，智能体越容易漏掉。
2. **容易过时**：写得越细，和实际文件对不上的地方越多。过时的指令比没有指令更糟，智能体会照着错的做。

我实际做过一次精简：把模板目录 10 行的明细表挪进该目录的 `README.md`，把实验方案目录十几个文件的清单挪进那里的 `README.md`，说明文件里各留一行指向。

## 六、每一项都写明「什么情况下去」

只写「脚本在某目录，详情看那里的说明」是不够的：智能体去那个目录之前，不知道手上的任务和它有没有关系。

![](https://pic2.zhimg.com/v2-8544c1c514a51c9782c96b839ed4c243_r.jpg)
*反例和正例*

反例：

> 脚本在 `AutomaticDataProcessing\`，有哪些脚本、数据格式、参数、风格都看它的 `CLAUDE.md`。

正例：

> 遇到下表任一情况，**先读那里的 `CLAUDE.md`，用现成脚本，不要自己从头写**。

| 遇到这种情况 | 对应脚本 |
| --- | --- |
| 用户给了 H 池恒电位测试的原始文件，要平均电流、槽压或 RHE 电位 | fac_fe\FindAverageCurrent\ |
| 要画法拉第效率图，或给了 FE 数据说「按这个风格画」 | fac_fe\FE_figure\ |
| 新下载的文献 PDF 要按标题、期刊、年份重命名 | LiterPDFRename\ |
| 要修改上面这些脚本本身 | 同上；画图脚本另有公开仓库要同步 |

写触发条件的要点：

- **左列写任务情境**（用户给了什么、要做什么），不写脚本名。智能体是拿手上的任务去对照的。
- **列全**：先读一遍目标目录的说明，把相关工具都列进来。漏掉的那类任务，智能体照样找不到。
- **「修改工具本身」单列一种情况**：改之前往往有额外规则。
- **坑写成条件句**：不写「换了参比电极要改」，写「写方案或处理数据时，只要电解液或参比电极不同，就提醒脚本要改」。这样写方案时就能触发，不用等到处理数据。
- **同一件事只指一个工具**：两个工具都能做的事，只写定好的那个。
- **README 里每项也带「什么时候用」**：只列路径，智能体判断不了要不要点开。

## 七、文献索引表

文献是信息最多的一类，单独做一张表，说明文件里只写「查文献先看这张表」。

- **放在哪**：PDF 统一按月放在文献笔记目录，不往课题目录里复制；每个课题建一张 `文献索引.xlsx`，只记路径、笔记位置、引用位置，不存文件。
- **「说明」页**：列的含义、相关度定义（★★★ 核心 / ★★ 直接相关 / ★ 参考）、类别、收录范围、怎么维护、更新记录。维护规则写在表里，不写进说明文件。
- **「文献索引」页**：每篇一行，包括相关度、类别、作者、年份、期刊、标题、要点（和课题的关系）、本机 PDF、SI、笔记位置、引用位置、DOI。笔记位置写成「哪个笔记 docx + 搜什么词」，打开后 Ctrl+F 就能定位。
- **「性能对标」页**：文献里的关键性能数据，供和自己的结果对比。比之前先看测试条件（电流口径、电解池类型），同类才能比。
- **收录范围宜宽**：间接相关的背景文献，比如其他材料体系的机器学习筛选、通用机理、综述，也收进来，标低星就行。

一个坑：表里有化学式上下标，用 openpyxl 打开要加 `rich_text=True`，不然保存后上下标全丢；改前先备份，改后核对富文本单元格数和超链接数有没有变少。

## 八、维护：索引会过时

索引最大的风险是和实际文件对不上。我遇到过一次：一个存文献全文的目录挪走了，文献总表、4 份方案和数据对照文档、两份说明文件里都还写着旧路径。

搬走或删掉目录时，一次收尾做完：

1. 全项目搜旧路径。md、脚本、说明文件用文本搜索；xlsx 里的文字和超链接要用脚本逐格查。
2. 逐个核对文件实际在哪，不要一律替换。我那次就有一篇文献其实在另一个月的文件夹里。
3. 替换后和已有路径重复的，删掉。
4. 超链接和显示的文字一起改。
5. 搬了什么、搬到哪、哪些文件没跟过去，写进那个目录的 README；说明文件里只留一句结论。

让智能体改说明文件时：先问它的判断，方向定了再改；让它先出草稿、只展示改动的部分；确认后再写入，写之前备份原件；它推断出来、没核实过的内容，要求它标出来；它预估的效果要用实测核对。我那次它预估能精简三分之一，实测只少了 14%。

## 九、篇幅参考

- 字数本身不是标准，标准是第五节那一句。
- 我在一个课题目录下开会话，三层说明文件合计约 9000 字符（中文），占上下文的几个百分点，加载成本可以忽略。
- 精简以后，课题层少了 44%；总目录层只少了 14%，因为脚本索引改写成触发条件后变长了。为了把触发条件写清楚多出来的字数，是值得的。
- 要警惕的信号：智能体反复漏掉某条已经写明的规则；说明文件越写越长，新增的主要是「某某文件里有什么」。

## 十、从零开始照做

1. 在科研总目录建一份说明文件，写各项目共用的规则，比如方案格式、文献存放、计算资源怎么用。
2. 每个课题目录建一份，写课题特有的设置和当前任务。
3. 给文献建一张索引表，说明文件里只写「先看这张表」。
4. 把数据处理、绘图脚本整理成「遇到什么情况 → 用哪个脚本」的触发表。
5. 模板、申请表格目录各放一份 README，每项写「什么时候用」。
6. 跨项目通用的操作流程（提交审批、文档排版等）做成 skill，在说明文件里写明什么情况用它。
7. 每次新加内容先问：这是规则还是描述？规则进说明文件，描述进 README 或索引表，说明文件里补一行触发条件。
