> 论文：PipeSwift: Revisiting Pipeline Parallelism for Large-Scale Completion-Oriented Agentic LLM Serving

这篇论文值得看的地方在于：它不是又造了一个推理引擎，而是先**把 KPI 换掉**——从聊天服务时代的 TTFT/TPOT（首 token 延迟、token 间延迟）SLO，换成 agent 时代的任务完成时间 JCT（Job Completion Time，作业完成时间）——然后顺着这个新目标重新推导调度与并行策略，最后得出一个和当下主流判断相反的结论：被冷落多年的**流水线并行（PP, Pipeline Parallelism）**，在 agent 负载下比事实标准 wide-EP 更划算。实测规模也够硬：**64 张 H800、两个 360B+ 级 MoE 模型、真实 coding / web-search agent 轨迹回放**。

## 一、Agent 时代，服务的 KPI 变了

聊天（chatbot）服务和 agent 服务的差别，不只是「多轮」这么简单：

- **聊天服务**：用户盯着流式输出逐字看，所以要压 TTFT、压 TPOT，引擎的优化目标是「在 SLO 约束下最大化 goodput（吞吐）」。自然的策略是**prefill 优先**——请求一到就立刻准入，同时维持尽量大的 decode batch。
- **Agent 服务**：像 Claude Code、Codex 这类系统会把中间的逐 token 生成**藏起来**，用户感知到的是「这一轮什么时候答完」「这个工具调用什么时候返回」。一整条 agent 轨迹要跑几十上百轮，每轮都要等上一轮的完整回答才能触发下一步工具调用。对 agentic RL rollout 这种离线批处理场景更是如此：唯一重要的数字就是**整批任务跑完要多久**。

所以论文把优化目标重写成三层度量：

- **总体 JCT**：一批任务从提交到最后一条轨迹完成的墙钟时间，即 max(i∈B) Cᵢ − A_B（Cᵢ 是任务 i 的完成时刻，A_B 是批次提交时刻）。
- **轮级 JCT**：某一轮从「就绪」到「完整回答返回」的延迟，JCT_turn,j = rⱼ − sⱼ。它既是线上 agent 服务直接暴露给用户的东西，也是解释调度行为的诊断量。
- **轨迹级 JCT**：一轮一轮加起来，再加轮与轮之间的工具/环境等待时间。

关键区别在于：**新的目标允许引擎「故意延迟一个就绪的 prefill，或者短暂卡一下 decode」**，只要这能让完成时间更短——哪怕这会牺牲 SLO 达成率。这就引出一个很实际的问题：SLO 导向的栈所优化的两件事（TTFT 达成率、decode 吞吐），真的能自动换来低 JCT 吗？

先看 agent 负载长什么样。

![](https://pic3.zhimg.com/v2-4eccbf86e411a270325b336342504d0c_1440w.jpg)

图 1：GLM-4.7 与 Qwen-3.5 在 BrowseComp 上的轮次数与会话长度分布。横轴左图是轮次数、右图是会话长度（累计上下文）。要点是：**轮次不多，但会话很长**——而且相邻轮次之间共享绝大部分上下文，平均**前缀缓存命中率超过 95%**，于是每一次 prefill 实际要算的只是挂在长缓存前缀后面的**一小段增量 token**。

这个「短增量 prefill + 长缓存前缀」的特征，后面会贯穿全文，它是整个优化的物理基础。

## 二、先补三个背景概念

**1）MoE 部署与 DP attention 的「P+D 碎片」。** 大 MoE 模型通常对 MoE 层用专家并行（EP, Expert Parallelism），每层都要做 dispatch/combine 的 all-to-all；注意力层则用张量并行或数据并行。多机场景下 TP 因为 KV cache 复制和跨节点通信而不可行，业界改用 **DP attention**：不同 DP rank 各自维护 KV cache、各自独立调度。

问题来了——既然各 rank 独立调度，同一组里的 rank 就**不必同时处在同一阶段**。论文把 DP2 组的状态分成三类：P+P（都在 prefill）、P+D（一个 prefill、一个 decode）、D+D（都在 decode）。**P+D 是低效的碎片态**：一半的卡在算 prefill，另一半在 decode，谁也跑不满。

论文给出的实测分解很直观（SGLang + GLM-4.7，MoE 用 EP16、注意力用 DP2TP8）：

| 基准 | 设置 | P+P | P+D | D+D | Idle | 总计 (s) |
| --- | --- | --- | --- | --- | --- | --- |
| BC | 无 prefill delay | 369 | 1593 | 1191 | 481 | 3634 |
| BC | 有 prefill delay | 1002 | 0 | 1653 | 377 | 3031 |
| SWE | 无 prefill delay | 460 | 1331 | 1032 | 332 | 3155 |
| SWE | 有 prefill delay | 897 | 0 | 1171 | 181 | 2249 |

可见 P+D 状态**占了端到端时间的 40% 以上**。SGLang 的 prefill-delay 机制（当只有部分 DP rank 有 prefill 需求时，把请求先握在手里等若干个 forward pass）确实把 P+D 压到了 0，端到端从 3634s 降到 3031s。但这只是「prefill 优先」的一个补丁，它对 JCT 一无所知。

**2）流水线并行（PP）。** 把模型按层切成若干 stage，micro-batch 在各个 stage 之间流动重叠。它的跨节点通信**只发生在相邻 stage 传递激活值时**，而不是每层都做一次跨节点 all-to-all。代价是：一条请求仍然是一个 pipeline round 前进一个 token，**PP 压不低 decode 延迟**——这正是它长期被打入冷宫的原因。

**3）多 token 预测（MTP, Multi-Token Prediction）。** 这是近两年大模型标配的投机解码形式：给主干网络挂一个轻量辅助层当 draft model，走「draft → verify → extend」循环，一次目标模型前向验证多个草稿 token，从而成倍加速 decode。

![](https://picx.zhimg.com/v2-28653f541751b8d40423ca476ea3f0d7_1440w.jpg)

图 2：SGLang 的 MTP draft–verify–extend 循环示意。(a) draft 阶段，MTP 层自回归预测草稿 token d(t+1)~d(t+3)；(b) verify 阶段，草稿与 Xₜ 打包后送进目标模型做**一次**前向，确定接受长度并产出隐藏状态；(c) extend 阶段，因为上一轮用的是临时隐藏状态，需要再调度一次前向把 d(t+1)~d(t+3) 的 KV cache 补上。

## 三、反直觉的核心发现：TTFT 刷到最优，整体反而更慢

论文定义了一个旋钮——**PD Orchestration（prefill/decode 阶段编排）**：显式地决定引擎什么时候跑 prefill、什么时候跑 decode，而不是一有请求就立刻准入。参数只有一个，**编排间隔 I**：调度器先跑 I 个 decode step，再重新考虑是否准入 prefill。I = 1 就精确退化成「prefill 优先」。

作者把这个控制做进了 SGLang 的调度器，在单节点 EP8TP8（不带 DP attention，以隔离调度效应）上扫 I，结果如下（Qwen3-VL-235B，SWE-Bench 128 任务 / 80K 上下文 / 并发 24，单位秒）：

| I | Wall | P | D | P50 延迟 | P90 延迟 | P99 延迟 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 3020.3 | 1093.7 | 1873.7 | 5.34 | 28.46 | 57.47 |
| 16 | 2792.3 | 825.2 | 1943.0 | 4.93 | 25.84 | 51.98 |
| 32 | 2652.8 | 640.5 | 1994.6 | 4.79 | 23.94 | 47.71 |
| 64 | 2498.7 | 405.9 | 2071.0 | 4.80 | 21.62 | 43.14 |
| 128 | 2481.9 | 304.6 | 2158.8 | 5.14 | 21.23 | 41.11 |
| 256 | 2739.5 | 244.8 | 2483.9 | 7.34 | 21.45 | 38.91 |
| 512 | 3485.9 | 237.6 | 3232.1 | 12.22 | 23.24 | 38.41 |

三件事一目了然：

- **墙钟时间最多差 1.40×**（3485.9s vs 2481.9s），而且**最优在中间（I = 128），不在任何一端**。
- I = 1 拿到了**最低的 decode 时间（1873.7s）**，却贡献了整张表里**最差的尾延迟**，墙钟比最优差 1.22×。
- 反过来，加大 I 把 prefill 时间从 1093.7s 一路压到 237.6s（I = 512）——**这只有在「单个 prefill 远未打满算力」时才可能发生**，正好印证了第一节里「短增量 prefill」的判断。

为了解释清楚机制，论文把轮级 JCT 拆成四项：

JCT_turn = t_queue + t_prefill + t_decode + t_stall

其中 t_queue 是准入前等待，t_prefill / t_decode 是这一轮自己的执行时间，**t_stall 是它的 decode 被别人的 prefill 打断的时间**。注意 TTFT ≈ t_queue + t_prefill。

于是机制就清楚了：**prefill 优先把 t_queue 压到近乎为零，却完全不管 t_stall**——碎片化的小 prefill 会打断所有在飞请求的 decode。而加大编排间隔、把多个就绪轮次聚合成一个 prefill wave，正是用一点 t_queue 换回大量的 t_stall。

![](https://pic4.zhimg.com/v2-ed4c234abe9210d2d2b72eafa33bdf5d_1440w.jpg)

图 3：PD 编排时间线对比。字母代表不同请求。上一行是调度步与请求到达；中间行是 prefill 优先（I = 1）——每个到达的请求立刻被发出并进入 decode，准入延迟最小，但 prefill 执行碎片化、decode 被频繁打断；下一行是 PD 编排（I > 1）——prefill 被推迟到编排点并聚合成更大的批次（图中的 BCD），prefill 效率提高，代价是新请求要等一等才能加入 decode batch。**编排间隔 I 本质上就是「prefill 效率 vs decode 效率」的旋钮。**

论文由此提炼出三条 insight：

- **Insight #1**：prefill 优先确实专注 decode 效率，但它并不直接优化 JCT。TTFT 达成率和 decode 吞吐**不会自动转化成低 JCT**。
- **Insight #2**：prefill 效率是 agent 负载 JCT 的**一等公民**，且与注意力的布局无关（这一轮扫描里根本没有 DP attention，P+D 状态不存在，墙钟照样差 1.40×）。
- **Insight #3**：JCT 的最优解要求**同时平衡 prefill 与 decode 效率**。短 decode 的请求没多少打断时间可省，多等一等就亏了；长 decode 的请求则从「少被打断」中获益更多——这正好解释了为什么 P50 的最优 I 是 32，而 P90/P99 的最优一路滑到 128/512，同时 P99/P50 的比值从 I = 1 时的 10.8× 收窄到 I = 512 时的 3.1×（尾延迟被显著压平）。

## 四、把结论推广到并行策略：PP 被重新翻出来

既然 JCT 由「prefill–decode 效率的平衡」决定，那任何改变这个平衡的机制都要重估——包括并行策略。多机场景下跨节点 TP 已被排除，候选只剩 **wide EP** 和 **PP**。

- **wide EP + DP attention** 是当下的既成标准，DeepGEMM / DeepEP 把它的通信优化得很好，尤其 DeepEP 用 IBGDA 压低了专家并行的通信延迟，让 wide EP 在低延迟 decoding 上很有优势。但**它的 prefill 每一层都要付跨节点 EP 通信的代价**，而机间带宽有限，规模越大越吃亏。
- **PP** 只在相邻 stage 之间传激活值，天然没有逐层的跨节点专家通信。**代价是 decode 慢。**

论文的 Insight #4 就是：在 JCT 目标下，「decode 延迟最低」并不等于「JCT 最优」，而 PP 提供了更优的 prefill–decode 平衡。案例数据支持这一点：同样是 prefill 优先、kernel 严格对齐，仅换布局，**prefill 时间就从 1962.4s 降到 1122.0s**（SGLang EP16 无 prefill delay → vLLM PP2）；即使 PP 没有 MTP 加持，总体 JCT 也能和前者打平——**prefill 端省下的时间，足以抵掉 decode 端多花的时间**。

**Insight #5** 更进一步：并行策略决定「prefill–decode 成本前沿」，调度只能在这个前沿上选工作点，因此**两者必须联合探索**。PP 的 prefill 更便宜，最优编排间隔就应该更小（更频繁地准入）；wide EP 的 prefill 贵，就该更激进地聚合。消融实验证实了这个预测：从 wide EP 换成 PP，最优 I 从 32 移到 16。

![](https://pic3.zhimg.com/v2-e3f66bce2fdd6cddd25bda2ad0895402_1440w.jpg)

图 4：一个 prefill wave 内的请求数、缓存前缀长度与新增 token 数分布（I = 32，GLM-4.7）。三个分布放在一起看很说明问题：**每条序列的缓存前缀可以长到十万 token 量级，而本轮真正新增的 token 常常不到 1K**。既有 PP 调度器（vLLM/SGLang）对这种高度异构的 wave 是僵硬的，这正是 PipeSwift 要在 runtime 层解决的问题。

## 五、PipeSwift 怎么做的

PipeSwift 是一个优化过的 PP runtime，围绕两个能力：**JCT 感知的调度层**（既编排 prefill/decode 阶段，又在每个阶段内部构造均衡的 micro-batch）和**与流水线集成的 MTP**；底层用 **SPMD 分布式调度器**架构。

### 5.1 prefill 微批划分：先建模，再装箱

一个 prefill wave 里的请求，异构性来自 (ℓ_cache, ℓ_new) 这对组合。论文沿用前人的做法，把 prefill 成本中与长度相关的部分建模成二次函数：

f(x) = αx² + βx

再用 γ 表示每个 micro-batch 的固定开销（调度、kernel launch、小 GEMM 等）。对缓存前缀为 c、新增 x 的请求，其增量成本为 g̃(c, x) = f(c + x) − f(c)。整个 wave 的长度相关总算力记为 W = Σ g̃(ℓ_cache,i, ℓ_new,i)。

接下来是这套设计里最漂亮的一步：假设把 wave 均分成 K 个均衡桶，每个 micro-batch 耗时约 W/K + γ；PP 度为 P 时需要 K + P − 1 个流水步，于是

T_wave(K) ≈ (K + P − 1) × (W/K + γ)

把 K 当作连续变量求极小，直接得到闭式解：

K* ≈ √( (P − 1)W / γ )

也就是**「流水线气泡」与「固定开销」之间的最优折中**：P 越大（气泡越多）就越该多切几刀；固定开销 γ 越大就越该少切。把 K* 取整到满足 token 与显存约束后，用**轻量贪心装箱**（每次都塞进当前最轻的 micro-batch）去逼近

min over {Bⱼ} of max_j Σ (i∈Bⱼ) g̃(ℓ_cache,i, ℓ_new,i)

### 5.2 decode 自适应重划分

decode 期间负载会自然漂移：新请求不断加入、老请求陆续完成。PipeSwift 在两个时机触发 **pipeline flush** 来重划分 decode micro-batch：一是某个 prefill wave 结束后（有新 decode 请求加入），二是任何在飞请求完成生成时。

沿用时延建模的结论（decode 是访存受限），batch 的 decode 时间主要由组内请求的 KV 总长度决定，于是目标变成把活跃请求切成 P 个桶，使

min over {Bⱼ} of max_j Σ (i∈Bⱼ) ℓ_kv,i

同样用贪心装箱近似。开销可忽略：每次 flush 只付一个 decode step 的代价，而重划分的触发频率远低于 decode 总步数；贪心装箱是多项式复杂度，几十微秒内完成。

### 5.3 把 MTP 塞进流水线

这是工程上最难的一块，因为**开源系统里此前没有任何一个把 MTP 集成进 PP**：draft–verify–extend 循环必须在每个 decode step 跨 stage 协同，而集中式调度器（vLLM/SGLang）做这件事很痛苦。

PipeSwift 的做法是：

- prefill 阶段，由**最后一个 stage** 先做一次多步 draft，把草稿 token 通过 P2P 通信广播给所有 stage，供后续验证使用。
- 每个 decode step，所有 stage 都参与目标模型的验证前向：非最后 stage 只跑自己分到的骨干层并向下游传隐藏状态；**最后 stage** 负责收尾——确定接受长度、用接受的 token 扩展 KV cache、跑 MTP 层、采样出下一轮的草稿 token，形成 **verify–extend–draft** 循环（注意与 SGLang 的 draft–verify–extend 顺序不同）。
- 每轮验证后，最后 stage 把「接受长度 + 新草稿」回传给前面的 stage，让它们的调度器更新请求状态、协调下一轮验证。

**1）负载均衡的层划分。** 这个不对称结构意味着：如果骨干层平均分，最后 stage 必然成为稳态瓶颈。PipeSwift 先 profile 每层的验证成本与 KV 扩展、MTP、采样的额外开销，然后**给最后 stage 少分骨干层**，把剩下的层重新摊给前面的 stage，在实测时间上做到大致均衡。

**2）为什么需要 SPMD 分布式调度器。** vLLM/SGLang 由中心化调度器驱动 worker，每个 step 都要把调度决定广播到 TP 组内、并在 stage 之间转发。PipeSwift 换成 SPMD 抽象：批发放、KV page 分配、请求驱逐等决策**在每个 worker 上复制执行**，从根本上取消了中心化调度器。每个 worker 进程自己就知道什么时候该发 NCCL P2P、下一个该跑哪个 micro-batch——这正是 PP + MTP 那种高频、动态的流水线计划所需要的。为保证各副本一致，它只在两个前提上做文章：micro-batch 划分算法**确定性**，以及新请求**在同一步骤加入**。

![](https://pica.zhimg.com/v2-f18666935deead425b8d805607ca0d8c_1440w.jpg)

图 5：PP 与 MTP 集成的整体执行流。每个矩形是一次前向步，不同字母代表不同的序列 micro-batch。除最后一个 stage 外，各 stage 只做 verify 前向；最后一个 stage 执行 verify–extend–draft 循环。第一次多步 draft 紧跟 prefill 之后完成（图中省略）。

## 六、实测：64 张 H800，两个 360B+ MoE

**测试台与基线。** 每台服务器 8 张 H800-80GB，节点内 NVLink 4.0，节点间 8×400 Gbps RoCE v2；PyTorch 2.11 + CUDA 12.9。基线都在 SGLang 0.5.13.post1 与 vLLM 0.23.0 上实现，**统一 64 卡预算**：

- **EP8**：PipeSwift 自己的单节点配置（EP8 + TP8），用来界定「什么时候非得多机不可」。
- **EP16**：两节点 wide-EP，MoE 用 EP16 + DeepEP 跨节点 all-to-all，注意力用节点内 TP8 + 跨节点 DP2。
- **PP2**：两节点、两个 EP8 stage 的流水线配置（用 vLLM，因为 SGLang 的 PP 跑不起来这些模型；且现有 PP 实现都不支持 MTP，所以 PP2 基线无投机解码）。
- **2P2D**：PD 分离，4 个实例各用 2 节点做 prefill、2 节点做 decode——**故意给它两倍的卡（128 张）**，以排除 prefill/decode 资源划分的影响。

所有系统共享同一套 kernel 栈（DeepGEMM、DeepEP、FlashAttention-3），所以差距来自调度与并行，而不是 kernel 实现。

**负载与分析协议。** 两个代表模型：GLM-4.7-360B（GQA 注意力）与 Qwen3.5-397B（GQA–GDN 混合注意力），都用 Hopper 上常见的 FP8 分块量化。两个 agent 负载：SWE-Bench（软件工程）与 BrowseComp（网页检索）。为避免负载随机性干扰系统对比，论文采用**确定性的轨迹回放**：把每条轨迹的每轮请求、MTP 接受长度、工具调用延迟都记录下来重放，保持闭环依赖不变，系统自身的调度与执行机制照旧。支持 MTP 的系统统一开 3 个草稿 token、每次验证 4 个 token；chunked prefill 的 chunk 预算统一 8192；显存利用率 0.8；编排间隔固定 I = 32，**不做任何按负载的调参**。

![](https://picx.zhimg.com/v2-a3ac707b89b8abcb43cf5f3b54d2dc83_1440w.jpg)

图 6：端到端性能全景。柱高为各系统在 12 个设置下的总体 JCT（分钟），柱上数字为归一化 JCT；× 标记表示该次运行因 KV 传输失败而中止。论文的结论是：**在每一个完成的格子里 PipeSwift 都拿到最低 JCT**——相对 SGLang wide EP 快 1.21–1.45×，相对 vLLM PP2 快 1.60–2.33×，相对（用了两倍卡跑完的）2P2D 快 1.14–1.54×。

几个细节值得单独拎出来：

- **EP8 的分水岭**：Qwen3.5-397B 在单节点上根本放不下，多机是硬需求；GLM-4.7 能放下，但单节点在模型权重之后剩下的显存装不下长前缀，上下文一长前缀缓存命中率就掉、被驱逐的上下文要一轮轮重算。所以 EP8 在短上下文下能打平甚至略好（SWE 64K 单元格上甚至是 0.98×，即比 PipeSwift 快 2%），一到长上下文就崩——**BC 512 任务下 PipeSwift 对 EP8 的优势从 64K 的 1.44× 涨到 96K 的 2.59×**。
- **vLLM PP2 的对比量化了 runtime 优化的价值**：同样的硬件布局，因为既不做 prefill 聚合、又没有 MTP，它是所有多机基线里最慢的。
- **即使给 wide EP 配上它自己的最优编排调度，PipeSwift 仍然快 1.24×**（见后面的 Fig 8），说明差距是**架构性**的，而不是调参调出来的。

**扩展性。** 在 GLM-4.7 BC 上做两组压力扫描（图 7）：

- 并发从 12 升到 28（MaxLen 96K）：优势在最高并发处达到峰值，**1.86×**。闭环保真下，并发越高意味着「别人在 decode 时陆续有轮次就绪」的干扰越强——这恰恰是编排要控制的东西，所以争用变大反而放大了 PipeSwift 的优势，而不是侵蚀它。
- MaxLen 从 64K 拉到 192K（并发 16）：加速比**始终保持 1.59× 以上，192K 时峰值 1.72×**。上下文变长同时抬高了每个 prefill wave 的算力和每个 decode step 的 KV 占用，而成本模型划分与自适应重划分让 micro-batch 在大 wave、KV 长度分化的条件下仍然均衡。

**2P2D 为什么缺席？KV 传输压力。** 这一节可能是全文对工程实践最有警示价值的：

agent 的一轮任务是「每轮把 KV 从前端池搬到 decode 池一次」，而上下文还在不断增长——坑在于**开源实现（SGLang/vLLM 都基于 Mooncake 传输引擎）搬的是请求的全量 KV，而不是超出缓存前缀的那部分增量**。agent 负载把这种冗余放大到极端：一轮典型新增不到 1K token，缓存上下文却有数万 token，于是**每一轮都要重发 30 倍以上的 KV**。后果是 decode 侧的传输队列：

| --- | --- | --- | --- | --- | --- |

除了最轻的那一档，**其余运行全部因 KV 传输超时直接崩掉**。这就是它从扩展性扫描里消失、并且在端到端对比里优势不断缩水的原因。

**消融实验。** 最后把 PP 这条路本身的收益拆开（GLM-4.7 SWE，512 任务 / 80K）：

| 系统 | Overall JCT (min) | 加速比 |
| --- | --- | --- |
| vLLM PP2 | 40.35 | 1.00× |
| PipeSwift PP2（关掉 MTP） | 30.73 | 1.31× |
| PipeSwift PP2 | 17.64 | 2.29× |

**光是 JCT 感知的调度层就砍掉 1.31×，再把 MTP 集成进流水线又砍掉 1.74×，合计 2.29×**——而后者是现有 PP 实现根本够不到的，因为没有一个支持投机解码。

图 8：并行策略消融。在同一个 GLM-4.7 SWE 单元格上扫编排间隔 I，对比 PipeSwift PP2 与「跑同样 PD 编排策略的 SGLang EP16」，归一化到带 prefill delay 的 SGLang EP16。三条预测全部兑现：两条曲线都有**内部最优**（Insight #3）；**更便宜的 prefill 把最优点左移**（Insight #5）——PipeSwift 最优在 I = 16，EP16 最优在 I = 32，两个最优点相比 PipeSwift 仍快 1.24×（Insight #4）；而且**这个旋钮很宽容**，PipeSwift 在 I = 8–32 之间表现接近，所以端到端实验统一用 I = 32 并不吃亏。另外，把 PipeSwift 的编排策略搬到 SGLang EP16 上本身就带来 1.14× 加速——说明**调度策略是可以跨 runtime 迁移的**。

## 七、对工程实践的启示

- **先确认你的 KPI，再谈优化。** 如果你的负载是 agent、批处理、RL rollout，TTFT/TPOT 是代理指标而不是目标。「请求一到就准入」在聊天场景是对的，在完成时间导向的场景里会持续为 t_stall 付费。
- **prefill 聚合是最低垂的果实。** agent 负载的前缀缓存命中率极高，单次 prefill 短得远远打不满算力（表 2 里 prefill 总时间能从 1093.7s 压到 237.6s 就是证据）。把就绪轮次攒成 wave，用一点排队时间换掉大量 decode 打断，收益立竿见影——而且这个改动在 SGLang 上就能做（论文就是先改 SGLang 验证的）。
- **并行策略要按 KPI 重估，而不是按 decode 延迟。** 多机 wide EP 的 prefill 每层都要付跨节点 all-to-all；PP 只传相邻 stage 的激活值，prefill 便宜得多，代价是 decode 每轮只前进一个 token。在完成时间目标下，这个交换可能是赚的——论文的边界是 360B+ MoE、64 卡、8K–192K 上下文。
- **PD 分离别忘了算 KV 传输账。** 「全量 KV 搬运」在 agent 这种「长前缀 + 短增量」的形态下会产生 30 倍以上的冗余流量，轻则排队变长，重则直接 timeout 崩掉。上 PD 分离之前，先把「增量 KV 传输」这条路打通。
- **别把调度器写死。** PipeSwift 的 SPMD 复制式调度器（决策在每张卡上确定性重放）是它能灵活实现动态 PP + MTP 协同的前提；中心化调度器在 PP 场景下每步都要转发决策，代价高且难维护。

**边界与局限**：论文自己说得很克制——它主张的是「PP 值得被重新严肃对待」，而不是「PP 永远最优」。作者认为 PP 度会保持在中等水平（例如 Kimi-K3 约 1.5 TB 权重、B300 级节点约 2.3 TB HBM，PP2/PP3 就够用），而且只要部署跨了 scale-up 域，PP 的 prefill 优势就会持续存在。未来的方向是**在线自适应编排**（不再用固定间隔），以及在开源增量 KV 传输成熟后重新评估与 PD 分离方案的对比。

---

**一句话总结**：把优化目标从「每个 token 多快」换成「整批任务多久跑完」之后，prefill 效率和 decode 效率的**平衡**变成了核心变量；顺着这个变量重估并行策略，长期被冷落的流水线并行重新有了竞争力——PipeSwift 用 JCT 感知的调度层 + 流水线内 MTP，在 64 卡 H800、两个 360B+ MoE 上把总体完成时间压到 wide EP 的 1/1.21 到 1/1.45。
