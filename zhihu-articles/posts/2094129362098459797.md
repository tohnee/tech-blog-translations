LangChain 最近发了一篇技术博客，讲他们的开源 Agent 框架 Deep Agents 怎么处理一个常见难题：AI Agent 跑长任务时，越跑越糊涂。这个现象叫 context rot（上下文腐化）。我的判断是，这是 Agent 从”演示惊艳”走向”真能干活”的路上最实际的工程瓶颈，LangChain 给出的思路——上下文工程，值得每个做 AI 应用的人了解。

### 先说清楚：什么是 Context Rot

大模型有个硬性限制：上下文窗口。可以把它理解成一张工作台，桌面上能摊开的东西是有限的。现在模型的窗口动辄几十万 token，听起来很大，但 Agent 干活的方式是不断往里塞东西：用户的原始需求、每一步的思考、工具返回的结果、中间产生的文件。一个稍微复杂的任务跑下来，几十万 token 很快就满了。

问题不只是塞不下。塞得越多，模型的注意力越分散。关键指令混在大量无关的工具返回结果里，模型就容易忘记最初要干什么，或者被中间某个错误信息带偏。就像让你在一张堆满旧文件、外卖小票和草稿纸的桌子上找一张纸条——纸条还在，但你就是容易看漏。已有的实践观察表明，即便上下文没超上限，内容变长变杂之后，模型的表现也会明显下降。这就是 context rot。

### LangChain 的思路：管好桌面，而不是换张更大的桌子

Deep Agents 的做法不是把窗口做大，而是管好桌面上放什么，这就是所谓的上下文工程（Context Engineering）。它通过 middleware 机制，在 Agent 运行的每个环节对上下文做筛选和整理。从公开的技术博客看，核心手段有三类。

一是压缩。早期的对话和工具调用结果不再原样保留，而是提炼成摘要，像会议记录员只记结论和待办事项，不记每个人说的每句话。

二是卸载。大的中间产物，比如一段代码、一份长文档，不放在上下文里，而是存到文件系统，上下文里只留一个路径或引用，模型需要时再取。相当于把不常用的文件收进抽屉，桌面只留一张索引卡片。

三是关键信息置顶。任务的核心目标、当前进度、重要约束，始终放在模型最容易看到的位置，不被新产生的信息挤走。

这样一来，Agent 跑几十步、上百步的长任务时，上下文窗口里装的始终是当前最相关的信息，而不是任务开始以来的一切。

### 这跟我们有什么关系

对普通用户来说，这解释了一个常见体验：让 AI 改一段代码很流畅，让它独立做完一个持续几小时的复杂项目却容易出错、跑偏。模型没有变笨，是桌面乱了。理解这一点后，你在用 Cursor、Claude Code 这类工具时可以主动配合：复杂任务拆小，阶段性地开新会话并交代清楚现状。这其实就是人工在做上下文管理。

对开发者来说，信号更直接：做 Agent 应用，光选个强模型不够，上下文管理是架构层面必须设计的东西。LangChain 把它做成 middleware，意味着这套能力可以模块化复用，不用每个项目重新造轮子。这也代表了行业的一个趋势：模型能力趋同之后，竞争点在工程。

### 结论和边界

上下文工程是目前缓解 context rot 最务实的路径：承认窗口有限、注意力有限，然后用工程手段把有限资源花在刀刃上。但边界也要说清楚：摘要必然丢信息，卸载依赖模型”想起来去取”的能力，这些都不是完美的解法。真正可靠的长任务 Agent，还需要模型本身在长上下文理解上继续进步。在那之前，谁把上下文管得好，谁的 Agent 就更像能干活的，而不是能表演的。
