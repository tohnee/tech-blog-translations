在AI大模型训练与高性能计算（HPC）迅猛发展的背景下，传统以太网已难以满足对低延迟、高带宽和高可靠性的极致需求。本次我们重点聚焦于**InfiniBand作为AI算力时代高速互联基石的核心价值，详细探讨**IB的关键特性，如无损网络、SHARP（可扩展分层聚合与缩减协议）、动态自适应路由、SHELD（网络自修复）及GPUDirect RDMA等核心技术优势，并结合Fat Tree、Dragonfly等典型拓扑结构，探讨了不同规模场景下的组网策略。同时，从BIOS配置、PCIe优化到交换机与网卡参数调优，全面梳理了IB性能调优的最佳实践，为构建高效、稳定的AI基础设施提供实用参考。

### **一、三大互联技术路线：以太网、RoCE 与 InfiniBand**

### **1.1 以太网（Ethernet）——通用但不够快**

- **诞生于 1973 年**，是当今最普及的网络标准。
- 优势：成本低、生态成熟、兼容性强。
- 劣势：

适合 Web 服务、普通数据库等场景，**不适合大规模 AI 训练**。

### **1.2 RoCE——性能与成本的折中方案**

- **2010 年推出**，目标是将 InfiniBand 的 RDMA 能力嫁接到以太网上。
- 优势：复用现有以太网基础设施，成本较低。
- 挑战：

适合中小型 AI 集群或混合云环境，**但稳定性不如原生 IB**。

### **1.3 InfiniBand（IB）——为极致性能而生**

- **1999 年由 IBM、HP、Mellanox 等联合提出**，专为 HPC 和低延迟通信设计。
- 核心特性：

**AI 大模型、科学计算、高频交易等场景的首选**。

### **二、IB的关键特性**

### **2.1 无损网络**

InfiniBand **无损特性 – 不丢包**，由以下技术来保证：

1. **物理层**：更低的误码率目标：10e-15（以太网的1000倍）
2. **链路层**：基于信用的**端口到端口流控机制**，确保**接收侧的 buffer 足够**，不会主动丢包，通过“信用”机制动态控制发送方的数据发送速率，避免接收方缓冲区溢出。

![](https://pic3.zhimg.com/v2-4a62c2bbaf9ba3d901b0d7ec6047d936_r.jpg)

### **2.2 SHARP（可扩展分层聚合和缩减协议）**

### **2.2.1 SHARP产生的背景**

以往的数据中心中是以**CPU为中心的计算**，计算组件等待数据，容易产生性能瓶颈。随着HPC/AI的发展形成了**以数据为中心的计算**，数据传输（交换机、网卡）的同时进行分析和计算，实现更好的性能和扩展，通信延迟降至以前的**1/10** 。

![](https://pica.zhimg.com/v2-1f417d31a85fb3456b2086001d0ca36c_r.jpg)

2.2.2 SHARP功能特性

**基于网络树的数据汇聚机制**

- 利用网络拓扑结构（如树形结构）实现高效的数据聚合与缩减操作，如下图：

![](https://pic2.zhimg.com/v2-737d08be97c6ea291277f6d738f60667_r.jpg)

**多管道的并行操作**

- 支持多个数据流同时进行处理，提升吞吐能力。

**针对 HPC 和分布式机器学习应用场景**

- 专为高性能计算（HPC）和大规模分布式训练（如深度学习）设计。

**可扩展的高性能聚合运算 MPI 支持**

- 提供对 MPI（Message Passing Interface）中常见集合通信操作的硬件级加速支持。

**支持常见的集合通信操作类型**：

- Barrier（同步）
- Reduce（归约）
- All-Reduce（全归约）
- Broadcast（广播）

**支持的运算类型**：

- Sum（求和）
- Min（最小值）
- Max（最大值）
- Min-loc / max-loc（带位置信息的最小/最大值）
- OR、XOR、AND（逻辑运算）

**支持的数据类型和精度**：

- 整数（Integer）
- 浮点数（Floating-Point）
- 精度：16位、32位、64位

### **2.3 动态自适应路由——减少拥塞优化延迟**

- AR PORT GROUP – 到达目标主机地址的，具有同样跳数的转发端口组建成具有权重相同的转发组。
- 交换机可以动态选择同一权重且拥塞状况最轻的端口作为转发出口。
- AR功能通过SM子网管理节点的AR plugin开启。

### **2.4 SHELD——网络自修复**

- 交换机具备自主修复能力，可以快速解决由于特定端口失效而导致的网络问题。
- 基于软件的修复方案在网络故障监测方面延迟太大，1K-10K节点需要5-30s。**SHIELD 大大缩短故障解决时间（毫秒级），故障修复响应速度提高5000倍。网络规模越大，带来的价值越高。**
- 支持EDR，HDR以及后续的技术。

### **2.5 GPUDirect RDMA——带来10倍的性能提升**

GPUDirect RDMA 高性能计算和AI加速技术，绕过CPU，实现网卡或其他I/O设备与GPU显存之间的直接数据传输，从而显著降低延迟、提升吞吐，并减少系统资源开销。

### **三、网络拓扑设计**

### **3.1 Fat Tree**

Fat-tree：经典设计，成熟、低延迟、高带宽，适合中等规模集群，但成本高（需大量高端口交换机）。

### **3.2 Dragonfly**

Dragonfly：更优的可扩展性与成本效率，适合超大规模系统，依赖智能路由避免拥塞。

### **3.3 Dragonfly与Dragonfly+**

传统 Dragonfly 组间只通过 少量全局链路连接到少数几个其他组。

Dragonfly+ 通过端口重分配实现了更高的组间连接度和路径多样性。

![](https://pic3.zhimg.com/v2-076f9d15ecacea0407f51abbabf64c04_r.jpg)

Dragonfly+ 是在传统DF基础上针对“**拥塞”和“路径单一”问题优化。现阶段超算中，许多实际部署（如 Cray Slingshot）虽未直接叫 “Dragonfly+”，但吸收了其多路径思想**，采用更复杂的 Dragonfly 变体（如 Hierarchical Dragonfly）

### **3.4 胖树 VS DF +**

根据集群预估的节点规模，参考如下理论计算值，确定采用哪种结构。上百节点规模采用2层胖树即可满足，如果更高则需要规划3层。

![](https://pica.zhimg.com/v2-1c394f557ecb7791f794ff83c9235d3a_r.jpg)

| 对比维度 | Fat-Tree (FT) | Dragonfly+ (DF+) |
| --- | --- | --- |
| 适用集群规模（无阻塞） | 无限制 | >800 节点（HDR） >2K 节点（NDR） |
| 网络成本 | 较高 | 适中 |
| 优点 | a. 组网简单 b. 网络平衡，路由算法简单 c. 无 Credit loop deadlock 风险 | a. 成本较好（节省交换机和线缆） b. 组网灵活，易于扩展，适合分期建设 |
| 适用场景 | 无限制 | a. 分期建设的大型集群 b. 超算云、多租户分租模式集群 |
| 业界应用现状 | 最广泛使用，市场占有率最高 | 国内超算客户逐步使用 DF+ |

### **4.2 三层胖树典型结构(<=16000 HDR节点)**

**Spine - Director Switch（核心交换机）**

- 下图显示为 **多个高密度机柜式交换机**，相比于小交换能更加节省线缆。

**Leaf - TOR Switch（ 机顶交换机）**

- “TOR” = Top-of-Rack，即每台服务器机架顶部部署的一台交换机。
- 每个 Leaf Switch 连接一个或多个Rack，作为服务器接入网络的入口。
- 下图共展示了 6 台 Leaf Switch，代表 6 个独立的机架组。
- 每个 Leaf 通过多条链路连接到所有的 Spine Switch，保证冗余和负载均衡。

### **5.2 PCIE相关配置**

如下是在高性能计算（HPC）、AI 训练等场景中，常见的**优化 PCIe 通信性能**的四大关键设置项：**MAX READ REQUEST SIZE**；**MAX PAYLOAD SIZE**；**Relaxed Ordering**；**PCIe Switch/Retimer 级联**。

lspci -tv 可以查看 PCIe 树形拓扑结构，可快速识别是否存在过多级联。

### **5.2.1 MAX READ REQUEST SIZE**

该值控制 PCIe 设备发起读请求时的最大数据块大小，推荐设置：4096（即 4KB）。

**设置命令**： setpci -s B:D.F 68.W=5000:f000 # 设置 Max Read Request Size = 4k

**调优原因**：

- 若该值过小，会导致频繁的小包传输，增加协议开销。
- 设置为最大值（如 4KB），可以减少“包拆分”次数，提升内存读取效率。
- 特别对 RDMA 读操作有明显加速效果。

### **5.2.2 MAX PAYLOAD SIZE**

定义 PCIe TLP（Transaction Layer Packet）的最大载荷大小，推荐设置：512 字节（或设备支持的最大值）。

**设置命令**：setpci -s B:D.F 68.W=0040:00e0 # 设置 Max Payload Size = 512

**调优原因**：

- 较大的 payload 可以减少 TLP 数量，降低链路拥塞和延迟。
- 减少 PCIe 收发包的“拆分”现象，提高带宽利用率。
- 在高吞吐场景（如 GPU 数据交换）中尤为重要。

### **5.2.3 Relaxed Ordering (RO) —— 针对 AMD CPU**

允许 DMA 写操作标记 PCIe 头部中的 RO（Relaxed Ordering）位。

**设置命令**： mlxconfig -d $PCI_FUNCTION set PCI_WR_ORDERING=1 # 适用于 AMD CPU

**调优原因**：

- 在 AMD CPU 上，开启 RO 可绕过严格的内存顺序控制，允许非顺序写入。
- 这样可以避免写操作因等待内存一致性而阻塞，从而 **提升带宽** 和 **降低延迟**。
- 是 AMD 平台实现高性能 RDMA 的关键优化之一。

**补充说明**：Intel CPU 通常默认支持宽松排序，无需额外配置。

### **5.2.4 PCIe Switch / Retimer 级联优化**

**推荐策略**：尽量减少 PCIe 级联层级（cascade）；将 GPU 和 NIC 放在同一级 PCIe switch 下。

**原因分析**：

- 每一级 PCIe switch 或 retimer 会引入 **100–150ns 的延迟**。
- 多级级联导致累积延迟上升，影响 RDMA 和 GPU 直通性能。
- 同一 switch 下通信路径最短，延迟最低，带宽最高。

**最佳实践**：

- 使用 **单层 PCIe switch** 连接多个 GPU 和 IB 网卡。
- 避免通过多级 hub 或扩展卡连接设备。

### **七、性能和故障诊断**

### **6.1 物理链路误码率 - BER**

**BER（Bit Error Rate）**：比特误码率，表示在数据传输过程中发生错误的比特数占总传输比特数的比例。 是衡量物理链路质量的关键指标。**数值越小，链路越稳定**。例如：1E-12 表示每传输 10¹² 个比特中有一个错误。

**PCIe 链路监控 —— BER Target ≤ 1E-12 for Gen3**

| 命令 | 功能 |
| --- | --- |
| lspci -s B:D.F -vvv | 查看 PCIe 设备的详细信息，包括： • 链路宽度（Width） • 速度（Speed） • 错误状态（Error Status） |
| mlxlink -d mlx5_0 --port_type PCIe -e | 查询 Mellanox 网卡的 PCIe 接口状态，获取 BER 数据 |

**NIC / IB 网口监控 —— 查看 BER Thresholds**

| 命令 | 功能 |
| --- | --- |
| mlxlink -d mlx5_0 -e | 查询 Mellanox 网卡的 IB/以太网端口状态，包含 BER 统计信息 |

**BER 阈值默认值表**

| BER Type | No-FEC (EDR) | RS-FEC | LL RS-FEC | KP4 RS-FEC |
| --- | --- | --- | --- | --- |
|  | Warn | Alarm | Warn | Alarm |
| Raw BER | 1e-13 | 5e-12 | 1e-6 | 1e-5 |
| Effective BER | 1e-13 | 5e-12 | 1e-13 | 5e-12 |
| Symbol BER | 1e-13 | 5e-12 | 1e-13 | 5e-12 |

BER 类型说明：

- Raw BER：原始物理层误码率，未经过 FEC 校正。
- Effective BER：经过 FEC 校正后的有效误码率，反映实际通信质量。
- Symbol BER：符号级误码率，适用于 100G+ 高速链路。

FEC 类型说明：

- No-FEC：无前向纠错，仅用于 EDR（100Gbps）
- RS-FEC：Reed-Solomon FEC，支持 HDR/NDR
- LL RS-FEC：Low Latency RS-FEC，优化延迟
- KP4 RS-FEC：增强版 FEC，用于长距离或高干扰环境。

**总结**：通过上述命令获取BER值后，参考如下范围判断链路是否异常。

| 指标 | 正常范围 | 异常表现 | 处理建议 |
| --- | --- | --- | --- |
| Raw BER | < 1e-12（Gen3） | > 1e-9 | 检查线缆、连接器、电源 |
| Effective BER | < 1e-13 | > 1e-11 | 可能存在干扰或老化 |
| Physical Errors | 0 或缓慢增长 | 快速上升 | 更换线缆或设备 |
| Status Opcode | N/A 或 0 | 非零 | 查看具体错误代码 |

### **6.2 交换机端口监控-counters**

**查看端口计数**：perfquery lid port -r

例如：perfquery 43 2 -r

- 43：LID（Local Identifier），表示目标交换机或节点。
- 2：端口号。
- -r：显示详细计数器信息。

![](https://pic3.zhimg.com/v2-cc3371c73fee4622ca9a1cd558dc06b6_r.jpg)

**错误计数器快速增长 → 链路质量差**

| 计数器名称 | 含义 | 异常表现 |
| --- | --- | --- |
| SymbolErrorCounter | 符号层错误，反映物理层信号质量问题 | 快速增长 → 可能是线缆老化、接触不良、电磁干扰 |
| LinkErrorRecoveryCounter | 链路重连次数 | 频繁恢复 → 链路不稳定 |
| LinkDownedCounter | 链路断开次数 | 不为零 → 存在间歇性中断 |
| PortRcvErrors | 接收端错误 | 表明接收侧有问题（如缓冲区溢出） |
| PortRcvRemotePhysicalErrors | 远程物理层错误 | 对端设备发送了无效数据 |

若上述任意一项持续增长，说明该端口存在物理链路问题，需检查线缆、连接器或设备本身。

**PortXmitWait 快速增长 → 发生拥塞**

| 计数器名称 | 含义 | 异常表现 |
| --- | --- | --- |
| PortXmitWait | 数据包等待发送的时间总和（单位：微秒） | 快速增长 → 发送队列积压，发生拥塞 |

例如 PortXmitWait = 731735263：表示该端口累计等待时间超过 7.3 亿微秒（约 731 秒）。值越高，说明带宽压力越大，可能成为瓶颈。

如下图，根据端口PortXmitWait值大家可以判断一下哪个位置出现了带宽瓶颈或拥塞？

![](https://pic2.zhimg.com/v2-a40f2c9c03571f79946cf1438804134d_r.jpg)

**问题分析：**

- **P31 是交换机端口**，连接的是 **Server2 的 IB2 网卡接口**。
- P31的PortXmitWait 是Server2 IB2 的**34倍**。高 PortXmitWait 表示该端口在“等待发送”，但**谁在发？谁在收？**
- 在 InfiniBand 或高性能计算网络中，**拥塞通常发生在接收端处理不过来时**，导致反压（backpressure）传导到上游发送端。
- 因此，**P31 的高等待值，很可能是 Server2 的 IB2 接口无法及时处理数据所致**——它才是真正的瓶颈源头。

### **6.3 主机侧的性能诊断**

**监控CPU使用率**：top -d 1

当某个任务所在的CPU核心使用率已达 100%，但带宽仍不足时，说明该核心已满载，可以将新任务进程调度到其他本地CPU核心上运行，避免单核过载。

**监控内存使用率（尤其是NUMA节点）**

内存瓶颈可能出现在特定NUMA节点，导致跨节点访问延迟上升。

watch -n 1 numactl --hardware

动态观察各NUMA节点的内存利用率，及时发现局部内存压力。

**合理选择CPU核心调度**

若本地CPU核心已满载，无法继续分配任务：

- 应优先选择 **NUMA distance 次优的CPU核心**（即距离较近、延迟较低的非本地核心）来运行新任务。
- 避免跨远距离NUMA节点调度，减少内存访问延迟和带宽消耗。

**网口带宽监控**

**mlnx_perf**（Mellanox提供的性能监控工具）：可以查看网卡实际发送/接收的数据量，判断是否存在网络拥塞或流量瓶颈。

**命令示例**：mlnx_perf -i ib0 | grep tx_bytes_phy

- `-i ib0`：指定网卡接口（如ib0）<br>
- `grep tx_bytes_phy`：过滤出物理层发送字节数，反映真实传输负载<br>
- 若 `tx_bytes_phy` 增长缓慢或停滞 → 可能存在发送阻塞<br>
- 若持续接近网卡理论带宽（如100Gbps），则需检查下游设备或应用处理能力。
