llama.cpp 是在本地跑大模型用的比较多的AI部署工具，简单容易上手。llama不依赖 Python 运行时，编译完就是一堆可执行文件，拷到另一台机器上照样能跑；CPU、NVIDIA、AMD、Apple Silicon、Intel 显卡都支持，模型统一用 `.gguf` 格式管理。这篇教程覆盖从编译到部署的全流程：编译怎么选后端、模型去哪下、量化怎么挑、服务怎么起、慢了怎么办、报错怎么查。

![](https://pic4.zhimg.com/v2-060a6c87b091ef183113a3ba192bef6b_r.jpg)

先说清楚一点：llama.cpp 的定位是"把推理做得足够小、足够快、依赖足够少"，不是开箱即用的桌面软件。第一次编译大概十几分钟，之后就是复制命令。如果你的目标只是双击一个图标就能聊天，LM Studio 或 Ollama 更合适，本文第一节会讲什么时候该换工具。

另外提醒一句：这个项目更新非常快，参数名和默认值一两年就会变一轮。**「你在网上搜到的中文教程里，大部分编译选项和命令行参数已经过期了」**，照抄会踩坑。本文按当前主线版本的写法来，末尾专门列了一张"过时写法对照表"。

## **一、它是什么，什么时候该用它**

一句话：**「llama.cpp 是一个纯 C/C++ 的大模型推理引擎」**。最早是为了在 MacBook 上跑 LLaMA 写的，现在已经是本地推理的事实标准之一。它的几个设计选择值得先知道：

- 权重文件用 mmap 映射，加载几乎不花时间，多个进程还能共享同一份内存页
- 量化支持从 1 bit 到 8 bit 的二十来种方案，4 bit 量化后模型体积约为原来的三分之一
- 自带 OpenAI 兼容的 HTTP 服务，现有代码改个 `base_url` 就能接上
- 服务端和命令行共用同一套参数，学会一个就会另一个

### **什么时候别用它**

这几个工具经常被拿来比较，其实分工很清楚：

| 你的需求 | 更合适的选择 | 原因 |
| --- | --- | --- |
| 双击就能聊天，不想碰命令行 | LM Studio | 图形界面，内置模型下载 |
| 一条命令拉起模型，自动管理 | Ollama | 封装了 llama.cpp，自带模型仓库 |
| 生产环境高并发 API 服务 | vLLM / SGLang | 连续批处理吞吐更高，但需要 Python + CUDA |
| 深度定制、嵌进自己的程序、资源受限设备 | 「llama.cpp」 | 依赖少、可裁剪、跨平台 |

判断标准很简单：**「你需要控制细节，或者需要把它塞进别的程序里，就用 llama.cpp」**；只想用，就选封装好的。

### **编译完你会得到什么**

编译产物有十几个可执行文件，日常真正会用到的只有前两个，其余都是遇到具体问题时才翻出来。

![](https://pica.zhimg.com/v2-b6e140a4d0a80e9b2bf58960d4a19630_r.jpg)

除了图里这些，还有几个偶尔用得到的：`llama-tokenize`（看分词结果，排查中文切分问题）、`llama-batched-bench`（测批量吞吐）、`llama-fit-params`（根据显存反推该用什么参数）、`llama-completion`（最底层的补全入口）。新版还提供了一个统一入口 `llama`，`llama cli ...` 等价于 `llama-cli ...`，`llama serve ...` 等价于 `llama-server ...`，写法更短。

## **二、先算账：你的机器能跑多大的模型**

这一步很多教程都跳过，但它决定后面所有选择。跑不动模型，九成是因为一开始就算错了。

实际占用分三块：

1. **「权重」**：模型本身。Q4_K_M 量化后大约是 **「参数量 × 0.57 字节」**，8B 模型约 4.6 GB
2. **「KV cache」**：对话上下文占的地方，随上下文长度线性增长，最容易被忽略
3. **「运行时开销」**：CUDA 上下文、计算缓冲区等，通常 0.5~1.5 GB，显存越小占比越显眼

![](https://pic2.zhimg.com/v2-07fd253b5d20fae8e5412ddbe8cd4983_r.jpg)

### **KV cache 到底占多少**

每个 token 的 KV 占用可以这样估：

```text
每 token 字节数 = 2 × 层数 × KV 头数 × 头维度 × 精度字节数

```

以 Llama-3.1-8B 为例：32 层、8 个 KV 头（GQA 起了作用，不然是 32 个）、头维度 128、F16 精度：

```text
2 × 32 × 8 × 128 × 2 = 131072 字节 = 128 KiB / token

```

8k 上下文要 **「1 GB」**，32k 上下文要 **「4 GB」**——已经超过模型权重的一半。而 Qwen2.5-7B 只有 4 个 KV 头，每 token 只要 56 KiB，同样 8k 上下文只占 448 MB。

记住两个结论：**「上下文翻倍，KV cache 就翻倍」**；**「GQA 头数少的模型，长上下文更省显存」**。显存紧张时把 KV 量化到 `q8_0` 能直接省一半，质量损失基本感觉不到。

### **对照表：什么卡能跑什么模型**

按 Q4_K_M 量化、8k 上下文估算：

| 显存 | 舒服跑 | 需要部分 offload |
| --- | --- | --- |
| 4 GB | 1.5B ~ 3B | 7B（会很慢） |
| 6 GB | 3B ~ 7B | 8B |
| 8 GB | 7B ~ 8B | 14B |
| 12 GB | 14B | 20B ~ 24B |
| 16 GB | 14B（宽裕）、20B | 32B |
| 24 GB | 32B | 70B（体验一般） |
| 48 GB | 70B | 100B 以上 |

只有 CPU 的话，内存是瓶颈：16 GB 能跑 7B~8B，32 GB 能到 14B~32B，64 GB 可以试试 70B，但速度会掉到每秒几个 token。

还有一条容易被忘掉：**「磁盘空间」**。下载 F16 模型再自己量化，中间文件会占两倍空间，70B 的 F16 有 140 GB 左右。建议留出模型体积三倍的余量，量化完再删中间文件。

## **三、系统要求**

### **硬件**

- **「CPU」**：x86_64 或 ARM64。Intel/AMD 建议支持 AVX2（2013 年后的处理器基本都有），AVX512 和 AMX 更快；ARM 平台走 NEON
- **「内存」**：至少 8 GB，跑 7B 模型建议 16 GB 起步
- **「显卡」**（可选）：NVIDIA 走 CUDA；AMD 在 Linux 上用 ROCm，Windows 上优先 Vulkan；Apple Silicon 用 Metal，统一内存越大越好
- **「存储」**：留出模型体积三倍的空间，SSD 优先（加载和换页都吃 IO）

CPU 推理时，**「内存带宽比核心数更重要」**。同样 8 核，DDR5 双通道能比 DDR4 双通道快接近一倍——原因在第八章会讲。

### **软件**

- **「编译器」**：Linux 需要 GCC 9+ 或 Clang 10+；Windows 需要 MSVC 2019+ 或 MinGW-w64；macOS 需要 Xcode 12+
- **「构建工具」**：CMake 3.18+、Git
- **「可选」**：CUDA Toolkit、ROCm、Vulkan SDK、Intel oneAPI（按你的显卡选一个）

CUDA 版本下限官方文档没有明文规定，原则是**「新卡配新 Toolkit」**，能装 12.x 就别停在 11.x。

## **四、安装：四条路线怎么选**

![](https://picx.zhimg.com/v2-1e8b803b677d4ea69c836d13df999ed5_r.jpg)

### **4.1 预编译包 / 包管理器（最快）**

```text
# macOS / Linux (Homebrew)
brew install llama.cpp

# Windows (winget)
winget install llama.cpp

# macOS (MacPorts)
sudo port install llama.cpp

# Nix（注意属性名是 llama-cpp，不是 llama.cpp）
nix profile install nixpkgs#llama-cpp

```

官方还提供了一个跨平台一键脚本，装完就是最新版：

```text
# macOS / Linux
curl -LsSf https://llama.app/install.sh | sh

# Windows PowerShell
irm https://llama.app/install.ps1 | iex

```

想要 GPU 版又不想编译，就去 [GitHub Releases](https://github.com/ggml-org/llama.cpp/releases) 找对应的压缩包。文件名规律是 `llama-<版本号>-bin-<平台>-<后端>-<架构>`：

```text
llama-b6000-bin-win-cuda-12.4-x64.zip      # Windows + CUDA 12.4
llama-b6000-bin-win-cpu-x64.zip            # Windows 纯 CPU
llama-b6000-bin-ubuntu-x64.tar.gz          # Linux（注意是 tar.gz）
llama-b6000-bin-macos-arm64.tar.gz         # Apple Silicon

```

Windows 上选 CUDA 版时，记得把单独的 `cudart-llama-bin-win-cuda-*.zip` 也下下来，解压到同一目录。

**「注意」**：包管理器装的通常是 CPU 版。想用显卡，要么下带 `cuda` 的压缩包，要么自己编译。

### **4.2 Docker（部署最省心）**

```text
docker pull ghcr.io/ggml-org/llama.cpp:server

docker run --rm --gpus all \
  -p 8080:8080 \
  -v ~/models:/models \
  ghcr.io/ggml-org/llama.cpp:server \
  -m /models/qwen2.5-7b-instruct-q4_k_m.gguf \
  --host 0.0.0.0 --port 8080 -ngl all

```

镜像分三个基础 tag：`:server` 只带服务端，`:full` 带全套工具（转换、量化都能在容器里做），`:light` 最精简。后面可以再加硬件后缀，比如 `:server-cuda`、`:server-rocm`、`:server-vulkan`、`:server-intel`、`:server-musa`。

用 Docker 的好处是环境干净、搬迁方便；代价是多一层文件系统开销，加载大模型时启动慢一点。模型务必用 `-v` 挂载进去，别塞进镜像。

另外，容器里的 `--host` 必须写 `0.0.0.0`，写 `127.0.0.1` 的话端口映射进不去。

### **4.3 源码编译（最灵活，推荐）**

只有这条路能完全控制：选后端、开优化、编一个只有几 MB 的精简版本。下一章详细展开。

### **4.4 怎么选**

| 你的情况 | 建议 |
| --- | --- |
| 第一次接触，想先看看效果 | 包管理器或一键脚本 |
| 有 NVIDIA 显卡，要吃满 GPU | 源码编译 CUDA 版 |
| Apple Silicon | Homebrew（Metal 默认就开） |
| 要部署成服务、要环境隔离 | Docker |
| 需要改代码、裁剪体积、跑冷门硬件 | 源码编译 |

## **五、从源码编译**

### **5.1 拉代码**

仓库地址已经换成 `ggml-org`，旧地址 `ggerganov/llama.cpp` 会重定向，但别再用了。

```text
git clone https://github.com/ggml-org/llama.cpp.git
cd llama.cpp

# 拉取子模块（部分构建方式需要）
git submodule update --init --recursive

```

**「版本号这件事值得单独说」**：老教程里让你 `git checkout v2.3.1`，而 llama.cpp 从来没有发布过这个 tag，照抄直接报错。它现在有两套版本号并行：

- **「语义化 tag」**，形如 `v0.4.0`，适合想要稳定版本的场景
- **「夜更编号」**，形如 `b6000`，就是提交数，每天更新

我的建议：想省事直接用 `main` 分支，主线一直比较稳定；想可复现就固定到一个具体 tag 或提交号，**「不同版本之间的性能差异有时能到 20%」**，报性能问题时不带版本号是没法讨论的。

```text
# 固定到某个语义化版本
git checkout v0.4.0

# 或者固定到某个夜更提交
git checkout b6000

```

编译前先装依赖：

```text
# Ubuntu / Debian
sudo apt install build-essential cmake git libcurl4-openssl-dev

# macOS
brew install cmake

```

### **5.2 基础 CPU 版**

```text
cmake -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release -j $(nproc)

```

`-B build` 表示构建产物放到 `build/`，`-j $(nproc)` 按核心数并行编译。这种写法比老教程里的 `mkdir build && cd build && cmake ..` 更干净，也不会污染源码目录。产物在 `build/bin/` 下。

### **5.3 NVIDIA CUDA**

前提是装好 CUDA Toolkit，`nvcc -V` 能输出版本号。

```text
cmake -B build -DGGML_CUDA=ON -DCMAKE_BUILD_TYPE=Release -DCMAKE_CUDA_ARCHITECTURE=86
cmake --build build --config Release -j $(nproc)

```

**「这是踩坑最多的地方」**：几乎所有中文老教程写的都是 `-DLLAMA_CUBLAS=ON`。这个选项名早就改了，正确写法是 `-DGGML_CUDA=ON`。好消息是现在写旧名字会直接报错提醒你，不会默默编出个 CPU 版。（但 `-DLLAMA_ROCM=ON`、`-DLLAMA_OPENBLAS=ON`、`-DLLAMA_VULKAN=ON` 这几个旧名字连报错都没有，写了等于没写——这是最坑的一类。）

显卡比较新的话可以指定计算能力，编译更快、体积更小：

```text
cmake -B build -DGGML_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=89

```

常见对照：30 系是 86，40 系是 89，50 系是 120。不确定就别写，让 CMake 自动检测。

打通用包（换机器也能跑）时加上 `-DGGML_NATIVE=OFF`，关掉针对本机指令集的优化。

### **5.4 Apple Silicon（Metal）**

macOS 上 Metal 后端**「默认就是开的」**，连 Metal 内核库的嵌入（`GGML_METAL_EMBED_LIBRARY`）也默认开启，直接用 5.2 的命令就行。想显式写出来：

```text
cmake -B build -DGGML_METAL=ON -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release -j $(sysctl -n hw.ncpu)

```

### **5.5 AMD 显卡**

Linux 上走 ROCm：

```text
cmake -B build -DGGML_HIP=ON -DGPU_TARGETS=gfx1100 -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release -j $(nproc)

```

`GPU_TARGETS` 填显卡架构代号（7900 XTX 是 `gfx1100`，6800 是 `gfx1030`），用 `rocminfo` 可以查。老版本里这个变量叫 `AMDGPU_TARGETS`，如果报"未使用变量"就换回旧名。

Windows 上 ROCm 支持有限，**「优先考虑 Vulkan」**。

### **5.6 Intel 显卡**

```text
source /opt/intel/oneapi/setvars.sh
cmake -B build -DGGML_SYCL=ON -DCMAKE_C_COMPILER=icx -DCMAKE_CXX_COMPILER=icpx
cmake --build build --config Release -j $(nproc)

```

Intel Arc 独显和较新的核显都支持，效果不错。SYCL 后端开 `GGML_SYCL_ENABLE_FLASH_ATTN=1` 还能省显存。

### **5.7 Vulkan：万能备胎**

不确定选什么后端，或者硬件比较冷门（摩尔线程、老 AMD、部分核显），选 Vulkan：

```text
cmake -B build -DGGML_VULKAN=ON -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release -j $(nproc)

```

需要装 Vulkan SDK。效率通常不如各家原生后端，但基本什么卡都能跑起来。

### **5.8 Windows 编译**

装 Visual Studio 2022 时勾上"使用 C++ 的桌面开发"，然后**「打开 x64 Native Tools Command Prompt」**——这步不能省，普通 PowerShell 里找不到编译器。

```text
git clone https://github.com/ggml-org/llama.cpp.git
cd llama.cpp

# CPU 版
cmake -B build -G "Visual Studio 17 2022" -A x64
cmake --build build --config Release -j

# CUDA 版（需先装 CUDA Toolkit）
cmake -B build -G "Visual Studio 17 2022" -A x64 -DGGML_CUDA=ON
cmake --build build --config Release -j

```

产物在 `build\bin\Release\` 下。我更推荐 Ninja，比 Visual Studio 生成器快不少：

```text
cmake -B build -G Ninja -DCMAKE_BUILD_TYPE=Release -DGGML_CUDA=ON
cmake --build build

```

### **5.9 编译选项对照表**

项目重构后，选项前缀从 `LLAMA_` 换成了 `GGML_`。左边是旧写法，右边是现在该用的：

| 旧写法 | 现在的写法 | 作用 | 旧名还有效吗 |
| --- | --- | --- | --- |
| -DLLAMA_CUBLAS=ON | -DGGML_CUDA=ON | NVIDIA CUDA 加速 | 报错提醒 |
| -DLLAMA_METAL=ON | -DGGML_METAL=ON | Apple Metal（默认开） | 仍映射 |
| -DLLAMA_ROCM=ON | -DGGML_HIP=ON | AMD ROCm | 已失效 |
| -DLLAMA_OPENBLAS=ON | -DGGML_BLAS=ON -DGGML_BLAS_VENDOR=OpenBLAS | CPU 走 BLAS | 已失效 |
| -DLLAMA_VULKAN=ON | -DGGML_VULKAN=ON | Vulkan 后端 | 已失效 |
| — | -DGGML_SYCL=ON | Intel 显卡 | — |
| — | -DGGML_NATIVE=OFF | 关本机指令集优化，产物可移植 | — |
| — | -DCMAKE_BUILD_TYPE=Release | 开优化，务必加上 | — |

哪个硬件该选哪个后端：

### **5.10 验证编译结果**

```text
./build/bin/llama-cli --version
./build/bin/llama-bench

```

第二条命令会输出检测到的后端和硬件。确认 `CUDA` / `Metal` / `Vulkan` 出现在列表里，才算真编对了。这一步花十秒钟，能省掉后面半小时的困惑。

### **5.11 编译常见问题**

- **「`nvcc not found`」**：CUDA Toolkit 没装，或没进 PATH，试试 `export PATH=/usr/local/cuda/bin:$PATH`
- **「链接阶段内存耗尽」**：把 `-j` 的数量减半，编译很吃内存
- **「CUDA 架构报错」**：去掉 `CMAKE_CUDA_ARCHITECTURES`，让 CMake 自动判断
- **「编完发现没有 GPU」**：确认选项名是 `GGML_` 开头；`-DLLAMA_ROCM` 这类旧名字不会报错但也不生效
- **「想确认真的用上了显卡」**：运行时看日志里的 `offloaded N/N layers`，或者用 `nvidia-smi` 看显存占用

## **六、拿到模型**

llama.cpp 只认 GGUF 格式，获取方式按省事程度排：

### **6.1 最省事：让 llama.cpp 自己下**

```text
# 拉取 Q4_K_M 并直接对话（不写量化档位时默认就是 Q4_K_M）
./build/bin/llama-cli -hf Qwen/Qwen2.5-7B-Instruct-GGUF

# 指定其他量化档位
./build/bin/llama-cli -hf Qwen/Qwen2.5-7B-Instruct-GGUF:Q8_0

# 指定具体文件名
./build/bin/llama-cli -hf Qwen/Qwen2.5-7B-Instruct-GGUF -hff qwen2.5-7b-instruct-q5_k_m.gguf

```

下载缓存由环境变量 `LLAMA_CACHE` 控制，默认位置 macOS 是 `~/Library/Caches/llama.cpp`，Linux 一般在 `~/.cache/llama.cpp`。想放到数据盘：

```text
export LLAMA_CACHE=/data/llama-models

```

国内网络不好就设镜像：

```text
export HF_ENDPOINT=https://hf-mirror.com

```

私有仓库要带 token，用 `-hft` 或设 `HF_TOKEN` 环境变量。

### **6.2 Hugging Face CLI**

```text
pip install -U "huggingface_hub[cli]"

# 下整个仓库
hf download Qwen/Qwen2.5-7B-Instruct-GGUF --local-dir ./models

# 只下其中一个量化文件
hf download Qwen/Qwen2.5-7B-Instruct-GGUF \
  qwen2.5-7b-instruct-q4_k_m.gguf --local-dir ./models

```

老版本命令是 `huggingface-cli download`，现在改成了 `hf download`，两个都还能用。

### **6.3 魔搭社区（国内快）**

```text
pip install modelscope

# 下载完整仓库
modelscope download --model Qwen/Qwen2.5-1.5B-Instruct-GGUF

# 只下特定文件
modelscope download --model Qwen/Qwen2.5-1.5B-Instruct-GGUF \
  qwen2.5-1.5b-instruct-q4_k_m.gguf --local_dir ./models

```

### **6.4 自己转换 Hugging Face 模型**

![](https://picx.zhimg.com/v2-e87929bc2a6aaac5b40a4cb319446c19_r.jpg)

手上只有 PyTorch / Safetensors 原始权重时：

```text
# 安装转换依赖
pip install -r requirements.txt

# 转成 F16 GGUF
python convert_hf_to_gguf.py /path/to/model_dir --outfile model-f16.gguf

```

脚本名现在是 `convert_hf_to_gguf.py`，直接放在仓库根目录，老教程里的 `convert.py` 早就删了。`--outtype` 可选 `f32`、`f16`、`bf16`、`q8_0`、`auto`。转出来的 F16 通常有几十 GB，下一步就是量化。

### **6.5 选哪个量化**

以 8B 模型为例，体积数据来自官方量化文档的实测值：

| 类型 | 体积 | 困惑度增量 | 什么时候用 |
| --- | --- | --- | --- |
| F16 | 16.0 GB | 基准 | 只做转换的中间产物 |
| Q8_0 | 8.5 GB | 几乎无损 | 显存充足，或要再量化 |
| Q6_K | 6.6 GB | 很接近原始 | 有点余量，想要最好质量 |
| Q5_K_M | 5.7 GB | 小 | 显存比 Q4 多一点时的优选 |
| 「Q4_K_M」 | 「4.6 GB」 | 「+0.175」 | 「默认选它，性价比最高」 |
| IQ4_XS | 4.5 GB | 小 | 差一点显存塞不下 Q4_K_M |
| Q4_0 | 4.3 GB | +0.469 | 别用了，见下方说明 |
| IQ3_XXS | 3.3 GB | 明显 | 极限压榨显存 |
| IQ2_XXS | 2.4 GB | 较大 | 只求能跑起来 |

**「关于 Q4_0」**：很多老教程把它列为推荐项，还写着"精度损失极低"。这个说法过时了。官方数据里，同样是 8B 模型，Q4_0 的困惑度比 F16 高 0.469，而 Q4_K_M 只高 0.175——**「Q4_0 体积更小一点，质量却差了一倍多」**。原因在于 Q4_K_M 做了混合精度：大部分权重留在 4 bit，注意力输出和部分前馈层升到 6 bit。新项目直接选 Q4_K_M，不用犹豫。

命名规律也有迹可循：`Q4_K_M` 里的 `K` 是 K-quant 系列，`M` 表示 medium 档位，同系列还有 `_S`（small，更小更糙）和 `_L`（large，更大更好）。`IQ` 开头的是更激进的量化，靠重要性矩阵保护关键权重，小体积下表现更好，代价是编解码更慢。

顺带一提，**「量化越狠，生成反而越快」**。官方在 Llama-3.1-8B 上测过：F16 是 29 t/s，Q8_0 到 51，Q4_K_M 到 72，Q2_K 能到 80。省显存和提速度在这里是同方向的。

### **6.6 自己量化**

```text
# 基础量化
./build/bin/llama-quantize model-f16.gguf model-q4_k_m.gguf Q4_K_M

# 带重要性矩阵（4 bit 以下强烈建议）
./build/bin/llama-imatrix -m model-f16.gguf -f calibration.txt -o model.imatrix -ngl 99
./build/bin/llama-quantize --imatrix model.imatrix \
  model-f16.gguf model-iq4_xs.gguf IQ4_XS

```

`llama-imatrix` 先用一段语料统计每层权重的重要性，量化时把重要的保护起来。对 IQ 系列提升明显，Q4_K_M 也能受益。语料用几百 KB 到几 MB 的通用文本就够，换成你要部署领域的文本效果更好。

还有其他几个参数值得知道：`--output-tensor-type` 指定输出层的类型、`--token-embedding-type` 单独指定词嵌入、`--tensor-type` 配合正则做逐层混合量化、`--prune-layers` 直接删层（极度缺显存时的暴力手段）。

量化完记得验一下：

```text
./build/bin/llama-perplexity -m model-q4_k_m.gguf -f wiki.test.raw -c 512

```

困惑度涨得越多，模型越"笨"。Q4_K_M 通常只涨 1%~3%，IQ2_XXS 可能涨 20% 以上——这就是代价。

建议按模型仓库建目录，别全堆在一起：

```text
models/
├── Qwen2.5-7B-Instruct-GGUF/
│   ├── qwen2.5-7b-instruct-q4_k_m.gguf
```

## **七、跑起来**

### **7.1 命令行（llama-cli）**

```text
# 单次生成
./build/bin/llama-cli -m models/model.gguf -p "用一句话解释什么是 GQA" -n 128

# 交互式对话
./build/bin/llama-cli -m models/model.gguf -c 8192 -ngl all

```

对话模式这里有个变化值得注意：**「新版本检测到模型自带对话模板（chat template）就会自动进入对话模式，不用再手动加 `-cnv`」**。老教程里到处都写的 `-cnv` 现在归属 `llama-completion`，在 `llama-cli` 里属于历史遗留。你在旧版本上跑，带上它没问题；在新版本上跑，不加也能对话。

另外 `--jinja` 现在默认就是开的，一般不用管；真要关掉用 `--no-jinja`。模型没带模板或者模板不对时，用 `--chat-template-file` 指定一个。

```text

```

### **7.2 起一个 API 服务（llama-server）**

llama.cpp 自带 OpenAI 兼容的 HTTP 服务，还带一个网页聊天界面：

```text
./build/bin/llama-server \
  -m models/qwen2.5-7b-instruct-q4_k_m.gguf \

```

服务端的结构和能力大致是这样：

![](https://pic2.zhimg.com/v2-e6aa9113499b6abb9daf5bb005b007e7_r.jpg)

启动后浏览器打开 `http://127.0.0.1:8080` 就是聊天界面（不想要用 `--no-webui` 关掉）。常用端口相关参数：

| 参数 | 作用 |
| --- | --- |
| --host / --port | 监听地址和端口，默认 127.0.0.1:8080 |
| --api-key | 简单鉴权，客户端要在 Header 里带 Authorization: Bearer <key> |
| -np / --parallel | 并行处理的请求数，默认自动 |
| -cb / --cont-batching | 连续批处理，默认开 |
| --metrics | 暴露 Prometheus 指标 |
| --embedding | 开启向量化接口 |
| --reranking | 开启重排序接口 |

**「测试接口：」**

```text
curl http://127.0.0.1:8080/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "local",
    "messages": [{"role": "user", "content": "你好"}],
    "temperature": 0.7,
    "max_tokens": 512
  }'

```

`model` 字段写什么都会被忽略，写 `local` 或 `gpt-4` 都行——这是为了兼容那些强制校验模型名的客户端。

**「Python 调用」**（现有 OpenAI 代码几乎不用改）：

```text
from openai import OpenAI

client = OpenAI(
    base_url="http://127.0.0.1:8080/v1",
    api_key="sk-no-key-required",   # 没设 --api-key 时随便填
)

resp = client.chat.completions.create(
    model="local",
    messages=[{"role": "user", "content": "用三句话解释 KV cache"}],
    temperature=0.7,
)
print(resp.choices[0].message.content)

```

**「流式输出」**：

```text
stream = client.chat.completions.create(
    model="local",
    messages=[{"role": "user", "content": "写一首关于编译的五言诗"}],
    stream=True,
)
for chunk in stream:
    if chunk.choices[0].delta.content:
        print(chunk.choices[0].delta.content, end="", flush=True)

```

**「监听哪些端点」**：

| 端点 | 说明 |
| --- | --- |
| /v1/chat/completions | 对话，最常用 |
| /v1/completions | 纯文本补全 |
| /v1/embeddings | 向量化（需 --embedding） |
| /v1/rerank | 重排序（需 --reranking） |
| /v1/models | 列出模型 |
| /v1/responses | 新版 Responses API 格式 |
| /health | 健康检查，不需要 key |
| /props | 服务端属性，需要 POST |
| /slots | 查看各槽位的处理状态 |
| /metrics | Prometheus 指标（需 --metrics） |
| /tokenize、/detokenize | 分词调试 |

**「工具调用」**：模型支持 function calling 时，走 `/v1/chat/completions` 带上 `tools` 字段即可。要保证两点——模型的对话模板里有工具调用格式，以及**「KV cache 别量化得太狠」**。官方明确警告：`-ctk q4_0` 这种极端 KV 量化会严重破坏工具调用能力，需要工具调用时把 KV 至少留在 `q8_0`，或者干脆用 `f16`。

## **八、性能调优**

调优这件事，先找准瓶颈再动手，不然就是瞎调。下面按影响从大到小排。

### **8.1 显存不够时：`-ngl`**

![](https://pic2.zhimg.com/v2-b82b52f2320d36f48477b1765f47dd0d_r.jpg)

`-ngl` 决定把多少层放到 GPU 上算，剩下的留在 CPU。当前版本支持三种写法：

```text
-ngl all     # 全部卸载（推荐，别再用 -ngl 99 或 -ngl -1）
-ngl auto    # 默认值，自己算一个合适的数
-ngl 24      # 精确指定层数

```

调法是从小往大加：先 `-ngl 20` 跑起来，用 `nvidia-smi` 看显存余量，逐步加到快满为止。**「最后几层带来的提速越来越小，占的显存却一点不少」**，在显存红线前停住最划算。另外注意，`-ngl` 写得再大也不会崩，程序会自己裁剪到实际层数，所以"设成 999 会不会炸"这种担心是多余的。

显存实在不够的三种退路：降量化档位、减小 `-c`、上多卡。

### **8.2 线程数：`-t`**

官方文档明确建议：**「`-t` 设成机器的物理核心数，即使你主要用 GPU 也一样」**（prompt 处理和部分计算仍在 CPU 上）。

```text
./build/bin/llama-cli -m model.gguf -t 8

```

默认值是 `-1`，即由程序自行决定。如果发现超线程拖慢了速度（有些平台确实会），手动设成物理核数。线程开太多会导致核心争抢，反而更慢。

### **8.3 上下文与 KV cache**

```text
-c 8192            # 上下文长度；写 0 表示用模型自带的最大值
-ctk q8_0 -ctv q8_0   # K/V cache 量化，显存直接省一半
-nkvo              # KV cache 不放到 GPU，全留内存

```

`-c` 是显存杀手，32k 上下文的 KV 占用是 8k 的四倍。**「不要一上来就设 131072」**，按实际需要给。

KV 可以量化的类型有 `f32`、`f16`、`bf16`、`q8_0`、`q4_0`、`q4_1`、`iq4_nl`、`q5_0`、`q5_1`，默认 `f16`。日常用 `q8_0` 最稳；`q4_0` 只在极端缺显存时考虑，而且会影响工具调用。

`-nkvo` 适合"显存装得下模型但装不下 KV"的场景，把 KV 放到内存里算，速度会掉一些，但能跑更长的上下文。

### **8.4 Flash Attention：`-fa`**

```text
-fa on     # 开（默认 auto）
-fa off    # 关

```

Flash Attention 能显著降低长上下文的显存占用并提速。两个硬约束要知道：

1. **「用 `--split-mode tensor` 或量化 KV cache 时，必须开 `-fa`」**
2. **「CUDA 后端只为少数 K/V 组合编译了 FA 内核」**（默认是 `q4_0`/`q8_0`/`f16`/`bf16` 的自配对）。用别的组合会静默回退到 f16 并给一条警告，效果打折

还有个已知限制：tensor 并行和 KV 量化不能同时用，同时开会在启动时报 `simultaneous use of SPLIT_MODE_TENSOR and KV cache quantization not implemented`，改用 `-sm layer` 或者把 KV 换回 f16。

### **8.5 批处理：`-b` 和 `-ub`**

```text
-b 2048    # 逻辑批大小，默认 2048
-ub 512    # 物理批大小，默认 512

```

这两个参数主要影响 **「prompt 处理速度」**（也就是你发出去到开始出字之间的等待时间）。加大能提升吞吐，但吃显存。长文档摘要、批量处理任务值得调；日常聊天感觉不出来。

### **8.6 采样参数**

```text
--temp 0.7          # 温度，0.6~0.9 是通用范围
--top-p 0.9         # 核采样，截断长尾
--top-k 40          # 只从概率最高的 40 个里选
--min-p 0.05        # 按最高概率的比例过滤，比 top-p 更稳
--repeat-penalty 1.1
--seed 42           # 固定随机种子，结果可复现

```

要确定性输出（写测试用例、做评测）就把 `--temp 0`；要创意写作就往上加，但超过 1.2 容易语无伦次。`min-p` 是目前比较推荐的截断方式，比单纯用 `top-p` 更抗退化。

### **8.7 多卡**

```text
-ngl all -sm layer -ts 0.6,0.4     # 按 6:4 分配到两张卡
-ngl all -sm row                   # 按行切分，长上下文更快
-ngl all -sm tensor                # 张量并行，必须配 -fa，且 KV 不能量化
-mg 0                              # 指定主卡

```

`-sm layer`（默认）适合两张卡显存不均衡的情况，`-ts` 手动分比例；`-sm row` 在长上下文场景更高效；`-sm tensor` 通信开销最大，但单卡放不下的超大模型只能靠它。

### **8.8 瓶颈到底在哪**

模型推理分两个阶段，瓶颈完全不同：

- **「prefill」**：处理你输入的 prompt。所有 token 一起算矩阵乘，**「算力受限」**，通常能到几百甚至几千 t/s
- **「decode」**：一个 token 一个 token 往外蹦。每生成一个 token 都要把全部权重读一遍，**「显存带宽受限」**

![](https://picx.zhimg.com/v2-8c16032903fe82c1cd0aa4ffe3fc61e5_r.jpg)

这张图解释了为什么 CPU 跑大模型慢得离谱：DDR4 双通道只有 50 GB/s 左右的带宽，而一块 4090 有 1 TB/s，差 20 倍。也解释了为什么"显存够用但速度上不去"——瓶颈压根不在算力。

用 `llama-bench` 看 `pp512` 和 `tg128` 两个数就能判断：`pp512` 低说明算力没用上或用错了后端；`tg128` 低说明带宽不够，或者 `-ngl` 没吃满。

### **8.9 一套可照抄的调优流程**

1. `llama-bench -m model.gguf -ngl all -p 512 -n 128` 拿到基准
2. 把 `-t` 设成物理核心数，再测一遍，比较 `pp512`
3. 逐步加大 `-c`（4096 → 8192 → 16384），观察显存和 `tg128` 的变化
4. 开 `-fa on`、加 `-ctk q8_0 -ctv q8_0`，看长上下文下能省多少
5. 显存还有余量就上更大的量化档位（Q5_K_M、Q6_K），质量换性能
6. 每次只改一个变量，改完立刻复测——**「凭感觉调优等于没调」**

## **十、那些过时的写法**

网上流传的中文教程（包括这篇文章最早参考的版本）有不少内容已经失效，这里集中对照一遍，方便你判断搜到的资料还能不能用：

| 老写法 | 现在应该这样 | 说明 |
| --- | --- | --- |
| -DLLAMA_CUBLAS=ON | -DGGML_CUDA=ON | 旧名现在会直接报错 |
| -DLLAMA_ROCM=ON | -DGGML_HIP=ON | 旧名不报错也不生效 |
| -DLLAMA_OPENBLAS=ON | -DGGML_BLAS=ON -DGGML_BLAS_VENDOR=OpenBLAS | 同上 |
| -DLLAMA_VULKAN=ON | -DGGML_VULKAN=ON | 同上 |
| git checkout v2.3.1 | git checkout main 或 v0.x.y / b#### | v2.3.1 从来不存在 |
| [http://ghcr.io/ggerganov/llama.cpp](http://ghcr.io/ggerganov/llama.cpp) | [http://ghcr.io/ggml-org/llama.cpp](http://ghcr.io/ggml-org/llama.cpp) | 组织改名 |
| -ngl -1、-ngl 99 | -ngl all | 现在有专门的关键字 |
| --mlock / --no-mmap | -lm mlock / -lm none | 合并成了 --load-mode |
| --draft-max / --draft-min | --spec-draft-n-max / --spec-draft-n-min | 推测解码参数改名 |
| -cnv（在 llama-cli 里） | 一般不需要 | 有对话模板会自动进对话模式 |
| --defrag-thold | 不再需要 | 已废弃 |
| "Q4_0 精度损失极低" | 首选 Q4_K_M | Q4_0 困惑度增幅是 Q4_K_M 的两倍多 |
| "-t 越大越好" | 设成物理核心数 | 超线程会拖慢 |
| llama.cpp 仓库里的 install.sh | curl -LsSf [https://llama.app/install.sh](https://llama.app/install.sh) \\| sh | 官方脚本已独立出去 |
| nix install nixpkgs#llama.cpp | nix profile install nixpkgs#llama-cpp | 属性名带连字符 |
