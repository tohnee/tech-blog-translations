> 当Ollama和LMStudio在处理连续任务时慢如蜗牛甚至内存溢出，其底层的llama.cpp引擎却能通过灵活的配置，将推理性能提升20%到300%。

## 为何要用llama.cpp？

当用Ollama、LMStudio等工具时，日常聊天的单任务场景没有问题，可如果接入连续任务的场景时（如OpenClaw、Calude code、Copilot），就会遇到两类情况

1. 速度慢的像蜗牛
2. 时间久了OOM

说到底，是因为这些工具的封装虽然方便了使用，但也丧失了参数配置的灵活性。而llama.cpp是它们的底座引擎，我们抛开上层封装，直接用底座来实现高性能推理。

[搞懂Ollama、LM Studio与llama.cpp](https://zhuanlan.zhihu.com/p/2040009030974887425)

上面的连接有助于了解这三者的关系。先说结论：同模型同环境同配置下，直接用llama.cpp要比用Ollama或LMStudio时，性能最低高出20%，最多可高出300%。下图是启用了推测解码后，达到的最高速度：

![](https://picx.zhimg.com/v2-989b12e8f0e2581577a15b74ea5513b9_r.jpg)
*209tok/s*

在同等配置下，llama.cpp的速度稳定在62tok/s-66tok/s，比LMStudio长期稳定的50tok/s相比，速度至少有20%提升。

## **完整命令行**

废话不多说，直接甩出可直接运行的命令，请注意将**-m**参数的路径改为你的实际路径。下面的命令是以42K上下文运行qwen3.6-35b-a3b。此命令的最高成绩就是209tok/s。

```bash
llama-server --host 0.0.0.0 --port 1234 --timeout 600 --reasoning off --reasoning-budget 0 -b 1024 -ub 512 -c 43008 -cb -t 12 -ngl 99 -ncmoe 16 --parallel 1 --flash-attn on --spec-type ngram-mod -dio --mlock --no-mmap  --no-mmproj --repeat-penalty 1.0 --temp 0.7 --top-k 40 --top-p 0.95 --min-p 0.0 --alias qwen3.6-35b-a3b -m "d:\models\Qwen3.6-35B-A3B-GGUF\Qwen3.6-35B-A3B-UD-Q4_K_M.gguf" 
```

**命令行参数解释**

我将参数分为四类：**基础配置**、**上下文配置**、**推理配置**、**高级配置**，并逐一解释。

### **1. 基础配置**

| 参数 | 含义 | 作用 |
| --- | --- | --- |
| --host 0.0.0.0 | 监听地址 | 允许外部设备（如局域网内的其他电脑）通过 IP 访问你的服务。如果是 127.0.0.1，则只能本机访问。 |
| --port 1234 | 端口号 | 服务运行的端口。客户端（如浏览器、API调用）需连接 localhost:1234。 |
| --timeout 600 | 超时时间 | 如果API请求超过 600 秒（10分钟），则强制断开客户端连接。 |
| -m "..." | 模型路径 | 最关键参数。指定 GGUF 模型文件的位置。 |
| --alias qwen3.6... | 模型别名 | 在 API 调用中，可以用这个名字代替长路径，方便识别。 |

### **2. 上下文配置**

| 参数 | 含义 | 作用 |
| --- | --- | --- |
| -c 43008 | 上下文窗口 | 允许模型记忆的最长 Token 数（42K）。注意：这决定了模型能“记住”多长的对话或文档。 |
| -cb | 上下文缓存优化 | 是否启用连续分批（也称为动态分批）功能，有助于在批量请求时更高效地管理内存。 |
| -b 1024 | 逻辑批次大小 | 每次推理处理的 Token 批大小。1024 较大，适合吞吐量，但占用更多显存。 |
| -ub 512 | 实际批次大小 | GPU/CPU 在底层实际计算时，单次内核调用所处理的最大 Token 数，此值不要超过逻辑批次大小。 |
| -t 12 | CPU 线程数 | 使用 12 个 CPU 线程进行数据处理，通常设为物理核心数或略少。 |
| -ngl 99 | GPU 层数 | 强制将 99 层加载到 GPU。对于小模型而言，这通常意味着全模型入显存，速度最快。如果模型装不下显存时，llama.cpp也尽可能多地加载GPU，剩余部分回退 CPU。 |
| -ncmoe 16 | CPU 专家数 | 仅对MoE混合模型有效。保留前N层混合专家（MoE）权重在CPU中推理。这个参数与ngl参数互为配合。 |

### **3. 推理配置**

| 参数 | 含义 | 作用 |
| --- | --- | --- |
| --reasoning off | 推理模式关闭 | 禁用思维链（CoT）模式的特殊处理。 |
| --reasoning-budget 0 | 推理预算 | 设为 0 表示不限制推理步数（配合 off 使用）。 |
| --flash-attn on | 快速注意力 | 启用快速注意力，显著降低显存占用并提升速度，尤其对长上下文有效。 |
| --repeat-penalty 1.0 | 重复惩罚 | 1.0 表示无惩罚。模型可能会重复啰嗦。建议设为 1.1 - 1.2 以抑制重复。 |
| --temp 0.7 | 温度系数 | 控制随机性。0.7 是平衡创意和准确性的常用值。0 最确定，1 最随机。 |
| --top-k 40 | Top-K 采样 | 每次只从概率最高的前 40 个词中选择。有助于避免生成生僻词。 |
| --top-p 0.95 | Top-P 采样 | 累积概率达到 95% 的词被纳入候选集。与 Top-K 配合使用，控制多样性。 |
| --min-p 0.0 | 最小概率 | 过滤掉概率低于 0.0 的词。0.0 表示不额外过滤。 |

### **4. 高级配置**

| 参数 | 含义 | 作用 |
| --- | --- | --- |
| --spec-type ngram-mod | N-gram 推测解码 | 类似于MTP，用于提前推测解码,加快推理速度。 |
| --parallel 1 | 并行请求数 | 同时处理 1 个请求。增加此值可提高吞吐量，但需更多显存。 |
| -dio | 直接 I/O | 绕过操作系统缓存，直接读写磁盘/显存。可能提升大文件加载性能，但增加系统负担。 |
| --no-mmproj | 禁用多模态投影器 | 如果是多模态模型则移除多模态能力，如果是纯文本模型，则无影响。 |
| --mlock | 内存锁定 | 防止模型数据被交换到硬盘（Swap）。对大模型性能至关重要，但会占用更多物理内存。 |
| --no-mmap | 禁用内存映射 | 不使用内存映射文件加载模型。配合 --mlock 使用，确保数据常驻内存。 |

## **`spec-type`的特别说明**

默认情况下，llama.cpp禁用spec-type，启用预推测解码有助于提升速度，但也可能拖慢速度，这与具体的任务有很大关系。在llama.cpp中，`--spec-type`与`--spec-XXX-min/max/match`参数定义推测解码（Speculative Decoding）的不同算法模式及其具体行为。

| 模式类型 | 含义 | 特点与适用场景 |
| --- | --- | --- |
| none | 禁用 | 不使用推测解码，标准推理。速度慢，但最稳定。 |
| draft-simple | 简单小模型 | 加载一个独立的、参数量极小的 LLM（如 0.5B-3B）作为草稿模型。✅ 通用性强，适合任何模型。❌ 显存占用高，需要额外加载一个小模型权重。 |
| draft-eagle3 / draft-mtp | 高级小模型 | EAGLE 或 MTP 是更先进的草稿模型架构，预测准确率比 simple 更高。✅ 加速比极高。❌ 需要特定模型支持（可下载Qwen3.6 MTP版的GGUF）。❌ 配置复杂。 |
| ngram-simple | 基础 N-gram | 基于统计学的 N-gram 查找表。从上下文中找重复片段。✅ 零显存占用，无需额外模型。❌ 加速有限，仅对重复性高的文本有效。 |
| ngram-map-k | 映射式 N-gram | 改进版 N-gram，使用哈希映射优化查找效率。✅ 比 simple 更快一点。❌ 依然受限于文本重复率。 |
| ngram-map-k4v | 四值映射 N-gram | 进一步优化的映射算法，针对特定硬件指令集优化。✅ 理论速度最快的纯 N-gram 变体。 |
| ngram-mod | 模块化 N-gram | llama.cpp 目前最高效的无模型推测方案。✅ 零额外显存。✅ 智能缓存，能捕捉长距离依赖，不仅限于局部重复。 |
| ngram-cache | 缓存式 N-gram | 另一种缓存实现，通常性能不如 ngram-mod。 |

### 测试总结

**速度**

影响速度的最关键参数是上下文大小。因为上下文越大，可放在GPU中的层数就越少，相应的就要卸载到CPU和内存中计算。

**资源**

对于MoE模型，ngl参数与ncmoe共同决定模型的推理性能。llama.cpp的聪明之处在于，即使你为ngl指定了较大的值，它也会自动评估是否装得下，如果装不下时自动卸载到内存和cpu中计算。ngl与ncmoe这两个参数，更像是一个期望值，但不是llama.cpp使用的绝对值。

**解码预测**

虽然启用spec-type可以提高速度，但也会拖慢速度。当草稿预测的接收率较高时（>=40%），速度明显提升，否则反而拖慢推理速度。这个预测直接和具体的任务有关，我发现越是大任务，它反而能有更好的预测率。对于创新型的任务（如编码、数学、思考），预测率相对不高；对于创作类任务（如写作、总结、提炼），预测率相对较高。

由于我下载的模型不支持MTP，所以没有测试mtp预测性能，在Hugging-face上，已经有qwen3.6-35b-a3b-mtp的GGUF模型了。有哪位仁兄测试后，请分享一下谢谢。

## 最优解

对于我的设备来说，经过多次测试与尝试，最终选择了**40K上下文+mod预测+kv q8_0**作为最优解，用于日常工作的长期方案。40K上下文，可以满足绝大多数的任务需要，而它的显存占用在14.8-15.2GB上下浮动，从来不会OOM，速度也是这几个方案中最高的。之前要2-3分钟完成的任务，现在很快只要几十秒就能完成了。下图是实际任务的速度，比LMStudio下的40-50tok/s快了一倍不止。
