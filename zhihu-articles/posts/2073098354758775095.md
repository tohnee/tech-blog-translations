2026年6月UnrealEngine 5.8 提供官方的mcp 功能，作为一个UE初学者十分激动，认为个人独立游戏开发的门槛会降低很多，但是在VibeCode 过去的一个月里，我同时使用chatgpt，cursor， Claude 等工具消耗大量token后，踩了很多坑后，总结了一些 UE MCP的使用技巧。这些技巧有一些很大程度也适用其他类型项目。

---

如果你现在用 Unreal Engine + Cursor / Claude Code / Windsurf + MCP，我建议把核心目标定成：

> **不要让 AI“自由操作 Unreal”，而是让 AI 在受控上下文里，执行小粒度、可验证、可回滚的修改。**

这同时能解决两个问题：**修改正确率**和 **Token 开销**。

目前 Epic 在 Unreal Engine 5.8 已经提供了官方 Unreal MCP 集成，Editor Preferences 里可以配置 Model Context Protocol，并启动本地 MCP Server；同时社区也有不少更重型的 MCP Server，能暴露 Blueprint、Actor、Level 等 Editor 操作。[Epic Games Developers](https://dev.epicgames.com/documentation/unreal-engine/unreal-mcp-in-unreal-editor?utm_source=chatgpt.com)

## 一、提高 AI 修改 UE 工程的正确率

![](https://pic4.zhimg.com/v2-d6d1ecd975f76d13ce25e89f39f74fa9_r.jpg)

我认为最重要的不是 Prompt 技巧，而是建立下面这个闭环：

```text
理解
  ↓
定位
  ↓
制定最小修改方案
  ↓
修改
  ↓
Compile
  ↓
验证
  ↓
发现错误
  ↓
修复
```

不要：（虽然无脑编程速度很快，但越到后期越寸步难行）

```text
Prompt
 ↓
AI 大改一堆代码/Blueprint
 ↓
你进 UE 看哪里炸了
```

## 1. 强制 AI「先读后改」

![](https://pic1.zhimg.com/v2-f7946e839bae1981cc2c5518f7442756_r.jpg)

这是正确率提升最大的一条。

例如你不要直接说：

```text
帮我优化 CharacterMovement
```

改成：

```text
先不要修改代码。

1. 找到 CharacterMovement 相关实现
2. 找到调用路径
3. 找到涉及的 Blueprint / C++ 类
4. 总结当前逻辑
5. 给出最小修改方案
6. 等方案确定后再修改

禁止修改无关文件。
```

对于 MCP 更进一步：

```text
第一阶段只允许使用：
- search
- inspect
- get_actor
- get_blueprint
- get_asset

禁止：
- create
- delete
- rename
- modify
```

也就是：

**Read Phase → Write Phase**

这比单纯说「小心一点」有效得多。

## 二、每次只解决一个问题

![](https://pic2.zhimg.com/v2-9c45fe5f1d08d115ecbcbc6b683e6695_r.jpg)

UE 项目里 AI 最容易出错的是这种 Prompt：

```text
优化角色系统，修复动画问题，
顺便优化性能，然后整理代码，
并把 Blueprint 改好。
```

这是 Agent disaster prompt。

应该拆成：

```text
Task 1:
修复 Character.cpp 中冲刺状态切换。

Acceptance:
- Shift 开始冲刺
- 松开 Shift 恢复
- Stamina == 0 自动停止
- 不修改 AnimationBP
```

完成以后再：

```text
Task 2:
让 AnimationBP 使用新的 sprint state。
```

## 三、给 AI 明确的 Acceptance Criteria

这个东西对 AI 编程非常重要。

例如：

```text
目标：
减少 Niagara 粒子更新 CPU 开销。

限制：
- 不改变视觉表现
- 不改变 Niagara System asset hierarchy
- 不修改材质
- 不引入新的 Tick
- 不改变现有接口

完成条件：
1. Unreal Editor compile 成功
2. 无新增 warning
3. 3000 particles 场景正常运行
4. 修改文件 <= 3
```

这比：

```text
帮我优化粒子性能
```

准确率高很多。

## 四、强制 Minimal Diff

你可以给 AI 一个长期规则：

```text
Prefer minimal diff.

Do not:
- rename unrelated symbols
- reformat unrelated code
- refactor unrelated classes
- change public interfaces unless required
- create new abstractions unless necessary
```

对于 UE 尤其有用。

因为 AI 特别喜欢：

```text
修一个 Bug
↓
顺手重构 class
↓
改 include
↓
改 module dependency
↓
改 Build.cs
↓
改 Blueprint API
```

然后：

UnrealBuildTool 爆炸。

## 五、让 AI 优先修改 C++，MCP 负责 Editor

如果你的项目是偏 Engine / Graphics / Gameplay C++，我建议：

```text
Claude Code / Cursor
       │
       ├── C++ source
       │
       ├── Build.cs
       │
       └── config
       
MCP
       │
       ├── inspect Blueprint
       ├── inspect Actor
       ├── inspect Level
       ├── set property
       └── run editor validation
```

而不是：

```text
所有事情
   ↓
MCP
   ↓
UE Editor
```

MCP 最适合解决：

> **传统 Coding Agent 看不到的 Unreal Editor 状态。**

比如：

```text
这个 Blueprint 到底绑定了哪个 AnimBP？

这个 Material Instance 当前参数是多少？

这个 Actor Component hierarchy 是什么？

这个 Niagara System 引用了什么材质？

这个关卡里哪些 Actor 使用 BP_Enemy？
```

社区 UE MCP 项目已经支持 Level、Actor、Blueprint、Animation Blueprint 等直接操作。[GitHub](https://github.com/Natfii/ue5-mcp-bridge?utm_source=chatgpt.com)

## 六、一定加入自动验证

![](https://pic1.zhimg.com/v2-7a3420cf871c52d9c77d82a8fae92d60_r.jpg)

这是 AI 正确率从「能用」到「靠谱」最关键的一步。

建议做成：

```text
AI 修改
   ↓
UBT Compile
   ↓
失败？
 ┌──────┐
 Yes    No
 ↓       ↓
分析错误  Editor Validation
 ↓
修复
```

最少应该自动跑：

```text
UnrealBuildTool
clang/MSVC compile
Automation Test
Editor log check
```

Prompt 可以规定：

```text
After every code modification:

1. Compile the affected module.
2. Read compiler errors.
3. Fix only errors introduced by this change.
4. Do not continue to the next task until compilation succeeds.
```

如果是 Blueprint：

```text
modify Blueprint
↓
compile Blueprint
↓
inspect errors
↓
save
```

而不是：

```text
修改 10 个 BP
↓
一起 compile
```

## 七、Token 开销最大的来源，其实经常是 MCP Tool

很多人以为：

```text
token = source code
```

实际上 Agent 模式下还会有：

```text
System Prompt
+
MCP tool schemas
+
MCP tool descriptions
+
MCP responses
+
source code
+
tool history
+
reasoning/history
```

特别是：

> **MCP 暴露 100~1000 个 tools**

很容易浪费大量上下文。

现在部分 Unreal MCP Server 已经暴露 200+ 工具；还有项目能提供更大规模的 Editor command surface。[Epic Developer Community Forums](https://forums.unrealengine.com/t/strayspark-unreal-mcp-server-200-ai-tools-for-ue5-editor-automation-via-mcp/2707474?utm_source=chatgpt.com)

研究也已经观察到：MCP tool description 的质量和长度会直接影响 tool selection 与 agent 效率；更完整的描述可能提高成功率，但也会提高执行步骤和成本，所以并不是「tool 描述越多越好」。[arXiv](https://arxiv.org/abs/2602.14878?utm_source=chatgpt.com)

## 八、最重要的 Token 优化：减少 Tool 数量

不要给 AI：

```text
200 Unreal tools
```

同时全部暴露。

最好按照领域分组：

```text
UE_Core
├── project_info
├── compile
├── log
└── asset_search

UE_Blueprint
├── get_blueprint
├── modify_blueprint
└── compile_blueprint

UE_Level
├── get_actor
├── create_actor
├── delete_actor
└── set_transform

UE_Material
├── get_material
├── set_parameter
└── inspect_shader
```

例如当前任务：

```text
修 Blueprint
```

只加载：

```text
UE_Core
UE_Blueprint
```

而不是：

```text
Niagara
Sequencer
Landscape
ControlRig
Material
PCG
Animation
Level
...
```

## 九、最好控制在几十个甚至十几个 relevant tools

这是很值得注意的。

2026 年一篇 MCP 架构研究在其测试环境中观察到：随着同一上下文里的工具数量增加，tool selection accuracy 会下降；不同模型的拐点不同，但研究报告的测试模型大约在 **10–30 个工具**范围开始出现明显影响。这个数字不能机械套到所有模型，不过方向非常明确：

> **只暴露当前任务需要的工具。** [arXiv](https://arxiv.org/abs/2606.30317?utm_source=chatgpt.com)

所以我会设计成：

```text
200 MCP Tools
      ↓
Tool Router
      ↓
当前任务识别
      ↓
8~20 tools
      ↓
LLM
```

而不是：

```text
200 tools
   ↓
LLM 自己选
```

## 十、避免 MCP 返回整个 Blueprint / Level

例如：

```text
get_level()
```

返回：

```text
800 actors
+
components
+
properties
+
transforms
+
references
```

非常烧 Token。

应该设计：

```text
search_actor(
    class=「Enemy」
)
```

先返回：

```text
BP_Enemy_21
BP_Enemy_34
BP_Enemy_47
```

然后：

```text
get_actor(
    actor=「BP_Enemy_21」,
    fields=[
        「components」,
        「movement」
    ]
)
```

也就是：

## Search → Narrow → Read

不要：

## Dump Everything

---

## 十一、MCP 返回 ID，不返回重复的大对象

差的设计：

```text
{
  「actor」: {
      「name」: 「...」,
      「transform」: 「...」,
      「components」: [...],
      「properties」: [...],
      「assets」: [...]
  }
}
```

每调用一次重复返回。

好的设计：

```text
actor_id:
A17F31
```

后面：

```text
get_actor_property(A17F31, 「Movement」)
```

这样 token 可以明显下降。

## 十二、对于重复工作，让 MCP 自己执行 Workflow

例如 AI 每次执行：

```text
find Blueprint
↓
open Blueprint
↓
modify property
↓
compile
↓
save
↓
read error
```

6 次 tool call。

应该直接做：

```text
modify_blueprint_property(
    blueprint,
    property,
    value,
    compile=true,
    save=true
)
```

或者更进一步：

```text
run_workflow(
    「modify_and_validate_blueprint」
)
```

Agent 只做：

```text
decision
↓
workflow
```

不是：

```text
decision
↓
tool
↓
decision
↓
tool
↓
decision
↓
tool
```

类似的 MCP workflow 研究已经展示了把「LLM 逐步决策」变成「一次规划 + 确定性 workflow 执行」后，可以显著降低重复任务的 token 消耗；论文里的特定测试甚至报告了 99%+ 的执行阶段 token 降低，不过这个数字属于其特定工作负载，不能直接当成 UE 的保证值。[arXiv](https://arxiv.org/abs/2605.00827?utm_source=chatgpt.com)

## 十三、给 UE 项目建立一个 AI Context Layer

这个是我最推荐你做的。

不要让 AI 每次重新理解：

```text
Source/
Plugins/
Config/
Content/
```

建立：

```text
.ai/
├── architecture.md
├── ue_rules.md
├── modules.md
├── gameplay.md
├── rendering.md
└── known_issues.md
```

但这些文件必须 **短**。

比如：

```text
architecture.md
```

只写：

```text
Game
├── Core
├── Gameplay
├── Rendering
├── UI
└── Editor

Rendering:
PostProcessManager
SceneLutManager
TileMapRenderer

Gameplay:
Character
AbilitySystem
Combat
```

不要写 50 页项目文档。

目标是：

```text
1000 token
```

让 AI 理解：

```text
整个项目骨架
```

而不是：

```text
读取 100 个 cpp
```

## 十四、Context 做三级缓存

这是非常适合你的方式。

### L1：Project Summary

长期加载：

```text
500~1500 tokens
```

包含：

```text
architecture
coding rules
module dependency
important conventions
```

### L2：Module Summary

任务需要的时候加载：

```text
Rendering
Gameplay
Animation
```

大约：

```text
500~2000 tokens
```

### L3：Source

最后才真正读取：

```text
Character.cpp
Character.h
```

变成：

```text
Project Summary
       ↓
Module Summary
       ↓
Search
       ↓
Relevant Source
```

而不是：

```text
grep 整个工程
↓
疯狂塞 context
```

## 十五、代码不要整文件返回

假设：

```text
Character.cpp
```

3000 行。

AI 只需要：

```text
StartSprint()
StopSprint()
TickStamina()
```

那 MCP / Coding Agent 应该返回：

```text
symbol
+
dependencies
+
±30 lines
```

而不是：

```text
3000 lines
```

尤其你以后做 UE Rendering：

```text
RenderGraph
SceneView
Pass
Shader
```

文件可能非常大，这个优化非常重要。

## 十六、建立 UE 专属 AI Rules

我建议你项目里长期保留这一类规则：

```text
Unreal Rules

1. Prefer minimal diffs.
2. Never modify generated code.
3. Never edit Intermediate/.
4. Never edit DerivedDataCache/.
5. Never edit .uasset as binary.
6. Use Unreal naming conventions.
7. Respect UObject lifetime.
8. Respect UPROPERTY/UFUNCTION reflection.
9. Do not introduce Tick unless necessary.
10. Avoid UObject access from arbitrary worker threads.
11. Check module dependencies before adding includes.
12. Prefer forward declarations when appropriate.
13. Compile affected module after modifications.
14. Do not modify unrelated files.
15. Never delete assets without explicit permission.
```

这一类规则：

**100~300 tokens**

却能防止大量错误。

## 十七、针对你这种 UE / 图形开发，我会进一步限制 MCP

你以后如果拿 AI 做 Rendering，我建议：

```text
AI
│
├─ Code Agent
│   ├─ C++
│   ├─ Shader
│   ├─ RDG
│   └─ Build.cs
│
└─ Unreal MCP
    ├─ Query Asset
    ├─ Query Material
    ├─ Query Scene

    ├─ Compile
```

而不是让 MCP 去：

```text
自动重构 Renderer
```

> Code Agent 更适合。

Editor 状态：

> MCP 更适合。

## 十八、我推荐你的完整工作流

最终可以变成：

```text
User
                       │
                 「优化水面渲染」
                       │
                       ▼
                Task Planner
                       │
             ┌─────────┴────────┐
             ▼                  ▼
        Project Context      MCP Router
             │                  │
        Rendering.md       Rendering Tools
             │                  │
             └─────────┬────────┘
                       ▼
                   Code Agent
                       │
                Search symbols
                       │
                 Read minimum
                       │
                propose patch
                       │
                 modify code
                       │
                       ▼
                     UBT
                       │
                  compile
                       │
                  ┌────┴────┐
                FAIL       PASS
                  │           │
                repair      MCP
                              │
                         open editor
                              │
                         run validation
                              │
                         inspect log
                              │
                              ▼
                            DONE
```

这套结构实际上就是：

> **LLM 做推理，MCP 做感知和执行，Compiler/Test 做裁判。**

不要让：

> **LLM 同时当程序员 + UE Editor + Compiler + QA。**

## 给你几个很实用的 Token 控制指标

你可以把 Agent 系统目标设成：

| 项目 | 建议 |
| --- | --- |
| 常驻 Project Context | < 1500 tokens |
| Module Context | < 2000 tokens |
| 当前相关代码 | < 5k–10k tokens |
| 同时暴露 MCP Tool | 10–25 |
| 单次任务修改文件 | 1–5 |
| MCP response | 尽量 < 1k tokens |
| 一次 Agent Task | 一个明确目标 |

这些不是协议硬限制，而是我建议你用来约束 Agent 行为的工程指标；具体阈值可以根据模型上下文窗口和项目规模调整。

---

## 最值得你先做的 5 件事

如果你现在已经搭好了 Unreal MCP，我会按这个优先级改：

1. **MCP Tool Router**：不要一次暴露全部 Tool。
2. **Read → Plan → Write → Compile → Validate**：强制状态机。
3. **Project / Module Summary**：避免每次重新扫描工程。
4. **Symbol-level retrieval**：不要把整个 `.cpp` / Blueprint dump 给模型。
5. **Workflow Tool**：把 Compile、Save、Validate 等确定性操作合并，减少反复 LLM 决策。

这五项做完，通常比单纯从普通模型换成旗舰模型更能改善 UE Agent 的**稳定性 / Token / 修改速度**。

对于你的使用场景，我尤其推荐进一步做成一个 **「UE AI Coding Agent + Unreal MCP Router + UBT 自动验证」** 的工程化工作流，而不是单纯装一个 Unreal MCP 插件。[Epic Games Developers](https://dev.epicgames.com/documentation/unreal-engine/unreal-mcp-in-unreal-editor?utm_source=chatgpt.com)
