**背景**：自回归生成一次只能出一个 token，且每一步都要把整个模型跑一遍。而生成是访存瓶颈的——计算单元大部分时间在等权重从显存搬过来。

**思路**：既然算力有富余，就让一个「猜得快」的东西一次猜好几个 token，再让「算得准」的模型一次前向把好几个位置全部验证掉。猜对了就白赚，猜错了就退回。

## 二、两个角色：target 与 draft

| 角色 | 职责 |
| --- | --- |
| target | 出真值分布、做验证 |
| draft | 提候选 token |

## draft 的实现谱系

| 档位 | 方法 | 需要额外下载模型？ |
| --- | --- | --- |
| 无模型 | ngram / suffix | ❌ 纯查表 |
| 寄生在 target 里 | mtp / dspark / dflash | ❌ 同一 checkpoint |
| 独立模型 | eagle / eagle3 / draft_model / medusa | ✅ 需要 |

## MTP是什么？

Multi-Token Prediction（多 token 预测）

目的：在主干之外挂几个额外的 transformer block，训练时让模型不只预测下一个 token，还预测下下个、下下下个。

```text
主干:   预测 t+1
MTP-1:  预测 t+2
MTP-2:  预测 t+3
...
```

推理时怎么用：串行，一次一个 token

```text
# AutoRegressiveSpeculator.propose 的骨架
for step in range(num_speculative_tokens):
    hidden = mtp_module(input_ids[step], positions[step], prev_hidden)
    tok = sample(draft_logits(hidden))
    draft_tokens[req, step] = tok
    prev_hidden = hidden          # ← 喂给下一步
    input_ids[step+1] = tok       # ← 串行依赖
```

所以 MTP 是 `O(N)` 串行的：想要 3 个草稿 token，就得跑 3 次 MTP 前向。

## MTP 的输入和输出是啥？

```text
输入 previous_hidden_states [T,16384]  ←──┐
                                       │  循环复用
输出 hidden_states          [T,16384]  ───┘
```

## 模型怎么判断MTP生成的token是正确的？

MTP 不判断。target 把草稿 token 当普通输入再跑一次前向，target 一次前向就同时算出每个位置的正确分布`p_target`。

**p_target是怎么算出来的？**

```text
没有投机解码时（正常 decode）：
  输入 [sat] @ pos=2
  → logits = P(· | The cat sat)          ← 就一个分布
有 MTP 时：
  输入 [sat, on, the, mat] @ pos=[2,3,4,5]      ← 一次前向，4 个 token
  → logits[0] = P(· | The cat sat)              ← 验证 "on"   ✅
  → logits[1] = P(· | The cat sat on)           ← 验证 "the"  ✅
  → logits[2] = P(· | The cat sat on the)       ← 验证 "mat"  ✅
  → logits[3] = P(· | The cat sat on the mat)   ← bonus token ✅
```

**为什么这么做是合法的？**

因为在因果 attention 下，位置 i 的 hidden 只依赖位置 ≤ i 的 token。**target 不需要知道自己在做验证，它只是正常地做了一次 causal forward**

> 「N+1 个 token 前向耗时≈1 个 token」是 decode 阶段的普遍特性

**MTP是target模型一起训出来的，它有自己的权重？**

是的。MTP和target模型共享的只有 `embed_tokens` 和 `lm_head`（两端接口必须在同一词表空间），中间那整套注意力 + MoE 全是 MTP 独有的。

## DSpark 是什么？

**MTP 和 DSpark 在权重来源上是同一类**（都寄生在 target checkpoint 的 `mtp.*` 命名空间里）； 真正的区别是执行方式：MTP 是「串行逐 token」，DSpark 是「一次并行出一整块 + 廉价的串行修正」。

MTP 有一个 `spec_step_idx` 参数，每一步调用一次。这就是串行。

```text
# 串行：每一步都依赖上一步的输出
h = target_hidden            # 主干最后一层的 pre-hc_head 残差
t = last_token
draft = []
for k in range(N):
    # 完整的一层 transformer（注意力 + MoE）
    h = mtp_layer(
        input_ids=t,
        previous_hidden_states=h,   # ← 依赖上一步
        spec_step_index=k,
    )
    logits = shared_head(h)
    t = sample(logits)
    draft.append(t)
```

DSpark

```text
# ===== DSpark =====
# transformer 只调 1 次，一次算 N 个 token
main_x = main_proj(target_aux_hidden)
for layer in layers:                       # ← 只过一遍（不是 N 遍）
    layer.store_context_kv(main_x)
H = backbone_forward(                      # ← 1 次前向，出 N 个位置
    query_block, non_causal=True
)
base_logits = head(H)                      # [N, V]
# 补依赖：不用 transformer，只加一个小 bias
for i in range(N):                         # ← 循环 N 次，但每次极便宜
    logits_i = base_logits[i] + markov_bias(prev)
    prev = sample(logits_i)
```

Dspark它不懂整句话在说什么，它只知道一件事：这两个词经常连在一起出现。

同时开工的麻烦是——位置 3 不知道位置 2 猜了什么。

举个例子，让它接着「New」往下猜 3 个：

> 理想答案： New → York → City 同时猜的结果可能是： <br>位置1: York ✓ <br>位置2: Delhi ✗ ← 它没看到位置1已经猜了York，自己瞎猜的 <br>位置3: City ✗ ← 它看到的都是些"占位符"，也不知道前面猜了啥

所以 DSpark 想了个补救办法：

> 第 1 步：3 个位置同时猜（快）→ York / Delhi / City<br>第 2 步：从左到右捋一遍<br> 看到位置1是 York → 用联想功能把位置2的 Delhi 压下去，把 City 提上来

这个「捋一遍」用的就是 Markov 头。代码里就是加一个偏置：

```text
for i in range(n_spec):
    # Sequential stage: Markov bias from the previously sampled token.
    markov_embed = self.model.markov_embed(prev)
    bias = self.model.markov_bias(markov_embed)
    logits_i = base_logits[:, i] + bias
```

这个偏置其实可以当作一次GEMM

```text
logits = torch.mm(flat, lm_head.weight.t(), out_dtype=self.head_dtype)
```

什么是MTP？什么是Dspark？

N=1 用 MTP，N=7 用 DSpark。 中间的 N（2~4）对两边都不友好——MTP 开始重复计算，DSpark 又够不到块大小下限。

## ngram 又是什么 ？

draft 谱系里最特殊的一档：它根本不是模型，是个「复制粘贴器」。`load_model` 是空的。 没有权重、没有网络、没有 GPU kernel。

```text
def load_model(self, *args, **kwargs):
    # No model to load.
    pass
```

ngram 的做法：

> 第 1 步：拿末尾几个 token 当"钥匙"<br> "The capital of" ← 这是要找的 n-gram<br><br>第 2 步：往前翻，看这句话之前出现过没有<br> "The capital of France is Paris"<br> "The capital of Germany is Berlin"<br> → 找到了！而且出现两次<br><br>第 3 步：把上次后面跟着的数拿来当草稿<br> 第一次后面是 " France"<br> → 草稿 = ["France"]<br><br>第 4 步：交给 target 验证<br> target: "Italy is" 后面确实是 "France" 吗？<br> 大概率是否，那就拒绝

猜错了也没关系——拒绝采样兜底。这个机制的全部价值在于：当文本确实在重复时，猜中的概率极高。

跑在 CPU 上，不是 GPU

**最凝练的一句：**ngram 是投机解码里的「零成本彩票」——不花显存、不花 GPU，猜中了白赚，猜不中由 target 拒绝采样兜底。适合当「默认开启也无害」的选项，但真正想要高加速比还得靠 MTP 这类基于模型的方法。
