> **导语**：模型部署不是"跑通 demo"，而是一条从**模型文件到线上服务**的完整工程链。本文以 TensorRT 为核心，串联 C++ 对象模型、Host/Device 内存交互、离线 Build / 线上 Load、动态合批与消息队列等底层原理，帮你建立一套可落地的部署世界观。内容覆盖 YOLO（2D 检测）与 CenterPoint（点云 3D 检测）两大典型场景。

## 1. TensorRT 是什么？

### 1.1 一句话定义

**TensorRT 是 NVIDIA 推出的高性能深度学习推理 SDK，用于将训练好的模型编译成针对特定 GPU 架构优化的推理引擎。**

### 1.2 三个角色的定位

| 角色 | 类比 |
| --- | --- |
| PyTorch | 源代码（灵活、易读） |
| ONNX | 中间汇编（跨框架通用表示） |
| TensorRT | 针对特定 GPU 编译的二进制可执行文件 |

### 1.3 它解决了什么问题？

- **算子融合**：Conv + BN + ReLU 融合为单个 kernel，减少显存读写
- **精度校准**：支持 FP16 / INT8 / FP8，显存减半、速度翻倍
- **内核自动调优**：为每一层选择当前 GPU 上最快的 CUDA 内核
- **动态张量内存**：复用显存，减少分配开销

## 2. TensorRT C++ 的世界里有哪些对象

C++ 里所有操作都围绕下面几个核心对象展开，先把它们记牢，后面代码就是"拼乐高"。

| 对象 | 作用 |
| --- | --- |
| ILogger | 日志回调（必须，捕获 build/run 警告） |
| IBuilder | 用来"编译"模型 |
| INetworkDefinition | 网络结构定义 |
| IParser | 读取 ONNX / UFF / Caffe |
| IBuilderConfig | 编译配置（FP16/INT8/workspace/dynamic shape） |
| ICudaEngine | 编译后的推理引擎（plan） |
| IRuntime | 从磁盘反序列化加载已有 engine |
| IExecutionContext | 一次推理的"运行上下文"（绑定显存、设置 shape） |

> ONNX → Builder + Network + Parser → Engine → Context → 推理

## 3. 内存与 GPU 之间的交互

### 3.1 硬件架构基础

CPU 与 GPU 是**两台独立的计算机**，各自拥有独立的内存空间：

- **Host（主机）**：CPU + 系统内存（RAM）
- **Device（设备）**：GPU + 显存（VRAM）

两者通过 **PCIe 总线**连接，数据交互必须通过 DMA（直接内存访问）完成。

### 3.2 为什么必须用指针？

- DMA 控制器只认**物理地址 + 长度**
- `cudaMalloc` 返回的是 GPU 虚拟地址，CPU 不能直接解引用
- TensorRT 的 `enqueueV2` 只接受**显存指针数组**

```text
// ❌ 错误：直接把 CPU 指针喂给 GPU
context->enqueueV2({input_host, output_host}, stream, nullptr);

// ✅ 正确：用 cudaMalloc 的显存指针
context->enqueueV2({d_input, d_output}, stream, nullptr);

```

### 3.3 PCIe 带宽的影响

| PCIe 版本 | 单 Lane 单向带宽 | x16 双向总带宽 |
| --- | --- | --- |
| 3.0 | ~1 GB/s | ~32 GB/s |
| 4.0 | ~2 GB/s | ~64 GB/s |
| 5.0 | ~4 GB/s | ~128 GB/s |

**工程启示**：前处理尽量在 GPU 完成（如 CUDA 版 voxelization），避免频繁 H2D/D2H 拷贝；Orin 等嵌入式平台需特别注意 PCIe 通道数限制。

## 4. TensorRT C++ 入门：离线 Build + 线上 Load（生产推荐）

### 4.1 两种使用模式

| 模式 | 适用场景 | 特点 |
| --- | --- | --- |
| ① 离线 Build + 线上 Load | 生产环境（推荐） | 启动快、稳定性高、engine 预编译 |
| ② C++ 内实时 Build | 调试 / Demo | 灵活但启动慢（几秒~几分钟） |

> **生产铁律**：线上程序**不编译模型**，只做 `deserialize → 分配显存 → 推理`。engine 由 Python / `trtexec` 离线生成，避免线上因 GPU/TensorRT 版本变化导致 build 失败或耗时抖动。

### 4.2 离线 Build（生成 .engine）

```text
class Logger : public nvinfer1::ILogger {
    void log(Severity severity, const char* msg) noexcept override {
        if (severity <= Severity::kWARNING) std::cout << msg << std::endl;
    }
} logger;

IBuilder* builder = createInferBuilder(logger);
const auto flags = 1U << int(NetworkDefinitionCreationFlag::kEXPLICIT_BATCH);
INetworkDefinition* network = builder->createNetworkV2(flags);

nvonnxparser::IParser* parser = nvonnxparser::createParser(*network, logger);
parser->parseFromFile("yolov8.onnx", static_cast<int>(ILogger::Severity::kWARNING));

IBuilderConfig* config = builder->createBuilderConfig();
config->setMemoryPoolLimit(MemoryPoolType::kWORKSPACE, 1ULL << 30); // 1GB
config->setFlag(BuilderFlag::kFP16);

// Dynamic shape profile（YOLO: batch 维度）
IOptimizationProfile* profile = builder->createOptimizationProfile();
profile->setDimensions("images", OptProfileSelector::kMIN, Dims4{1, 3, 640, 640});
profile->setDimensions("images", OptProfileSelector::kOPT, Dims4{4, 3, 640, 640});
profile->setDimensions("images", OptProfileSelector::kMAX, Dims4{8, 3, 640, 640});
config->addOptimizationProfile(profile);

ICudaEngine* engine = builder->buildEngineWithConfig(*network, *config);

// 序列化落盘
IHostMemory* serialized = engine->serialize();
std::ofstream f("yolov8.engine", std::ios::binary);
f.write((const char*)serialized->data(), serialized->size());

```

> 更简单的离线方式（工程里最常用）：`trtexec --onnx=yolov8.onnx --saveEngine=yolov8.engine --fp16`

⚠️ engine **不能跨 GPU 型号、不能跨 TensorRT 版本，要保证环境一致**。

### 4.3 线上 build 和 Load（只做推理）

从 ONNX 构建 Engine

```text
using namespace nvinfer1;

IBuilder* builder = createInferBuilder(logger);
const auto flags = 1U << int(NetworkDefinitionCreationFlag::kEXPLICIT_BATCH);
INetworkDefinition* network = builder->createNetworkV2(flags);

nvonnxparser::IParser* parser =
    nvonnxparser::createParser(*network, logger);

parser->parseFromFile("yolov8.onnx",
    static_cast<int>(ILogger::Severity::kWARNING));

IBuilderConfig* config = builder->createBuilderConfig();
config->setMemoryPoolLimit(MemoryPoolType::kWORKSPACE, 1ULL << 30); // 1GB
config->setFlag(BuilderFlag::kFP16);

ICudaEngine* engine = builder->buildEngineWithConfig(*network, *config);

```

保存engine：

```text
IHostMemory* serialized = engine->serialize();
std::ofstream f("yolov8.engine", std::ios::binary);
f.write((const char*)serialized->data(), serialized->size());

```

加载 Engine（线上代码）

```text
// 1. 读 engine 文件
std::ifstream f("yolov8.engine", std::ios::binary);
std::vector<char> blob((std::istreambuf_iterator<char>(f)),
                         std::istreambuf_iterator<char>());

// 2. 反序列化 + 创建上下文
IRuntime* runtime = createInferRuntime(logger);
ICudaEngine* engine = runtime->deserializeCudaEngine(blob.data(), blob.size());
IExecutionContext* context = engine->createExecutionContext();

// 3. 分配 GPU 显存（一次）
int inputIdx  = engine->getBindingIndex("images");
int outputIdx = engine->getBindingIndex("output");
cudaMalloc(&buffers[inputIdx],  1 * 3 * 640 * 640 * sizeof(float));
cudaMalloc(&buffers[outputIdx], 1 * 84 * 8400 * sizeof(float));

```

## 5. 一个"能抄"的 C++ 推理骨架

下面是生产可用的**最小推理循环**，每一行都标注了 Host/Device 归属（对应图 2 的数据流）：

```text
// ========== 初始化（一次）==========
load_engine("yolov8.engine", engine, context);  // 4.3 节内容
cudaStream_t stream;  cudaStreamCreate(&stream);
// 分配 Host 页锁内存（pinned memory，拷贝更快）
cudaMallocHost(&input_host,  in_bytes);
cudaMallocHost(&output_host, out_bytes);
cudaMalloc(&buffers[inputIdx],  in_bytes);
cudaMalloc(&buffers[outputIdx], out_bytes);

// ========== 推理循环（每帧）==========
while (running) {
    // 3. 预处理（Host / CPU）—— OpenCV
    preprocess(frame, input_host);          // BGR→RGB, resize, /255, HWC→CHW

    // 4. Host → Device（过 PCIe）
    cudaMemcpyAsync(buffers[inputIdx], input_host,
                    in_bytes, cudaMemcpyHostToDevice, stream);

    // 5. 设置 dynamic shape（若用了动态 batch）
    context->setBindingDimensions(inputIdx, Dims4{current_batch, 3, 640, 640});

    // 6. GPU 推理（异步）
    context->enqueueV2(buffers, stream, nullptr);

    // 7. Device → Host
    cudaMemcpyAsync(output_host, buffers[outputIdx],
                    out_bytes, cudaMemcpyDeviceToHost, stream);
    cudaStreamSynchronize(stream);          // 或用回调，避免阻塞

    // 8. 后处理（Host）—— NMS / 坐标变换 / 画框
    postprocess(output_host, results);
}

```

**关键说明**：

- 用 `cudaMemcpyAsync` + `stream` 而非同步版本，让拷贝与计算重叠
- 输入用 **pinned memory**（页锁内存），DMA 才能高效传输
- `enqueueV2` 的 `bindings`**必须全是显存指针**
- `warm-up` 几轮后再测 FPS，否则首帧包含 kernel 加载

## 6. TensorRT 知识点与注意点

### 6.1 Dynamic Shape 三要素

| 参数 | 含义 | 设置建议 |
| --- | --- | --- |
| kMIN | 最小输入尺寸 | 覆盖最低负载 |
| kOPT | 最优输入尺寸（性能最佳点） | 设为常见 batch |
| kMAX | 最大输入尺寸 | 不超过显存上限 |

> `kOPT` 是最重要的：builder 围绕它做优化。设错 → 实际 batch 很慢。

### 6.2 精度模式对比

| 精度 | 显存 | 速度 | 精度损失 | 适用 |
| --- | --- | --- | --- | --- |
| FP32 | 1× | 1× | 无 | 调试基准 |
| FP16 | 0.5× | ~2× | 极小 | 生产首选 |
| INT8 | 0.25× | ~4× | 需校准 | 高吞吐 2D 检测 |
| FP8 | 0.25× | ~4× | 需校准 | H100+ |

⚠️ CenterPoint（3D/点云/BEV）建议 **FP16 起步**，INT8 精度风险高。

### 6.3 Workspace Size 真相

- **不是推理显存上限**，而是 Builder 阶段尝试 kernel 的临时显存
- 太小 → 用不上最优 kernel；太大 → 多模型同卡 OOM
- 推荐：桌面卡 1–2GB，Orin 512MB–1GB

### 6.4 常见坑位速查

| 现象 | 根本原因 |
| --- | --- |
| 推理结果全 0 | 未执行 H2D 拷贝 |
| 随机崩溃 | 把 CPU 指针传给了 GPU |
| 性能不达预期 | kOPT batch 设错 |
| Orin 延迟抖动 | 用了 pageable memory |
| CenterPoint 框乱飞 | 坐标变换 / voxel 参数错误 |
| 多线程序共享 context 崩溃 | 每线程应各自创建 context |

## 7. 工程化实战技巧（消息队列 + 动态合批）

这是**从"能跑"到"能上线"的分界线**。单张推理只用于调试；生产环境必须用**消息队列 + 动态合批**，见图 3。

![](https://pic1.zhimg.com/v2-1126108217d67f94331f525d8ebe9118_1440w.jpg)

### 7.1 为什么需要消息队列

- **解耦采集与推理**：相机/LiDAR 采集线程不直接调推理，避免互相阻塞
- **削峰填谷**：突发流量先入队，推理线程按能力消费
- **背压机制**：队列满时触发 REJECT/丢弃，防止内存暴涨拖垮整机

### 7.2 动态合批：超过最大值会怎样？

合批触发条件 = **数量达到 `max_batch`** 或 **超时**。规则如下：

| 层 | 超过 max_batch 时的行为 |
| --- | --- |
| Triton 调度层 | 自动拆分批次（8+8+4），绝不超发；队列满可 REJECT |
| 自研合批层 | 需自行实现截断 / 排队 / 丢弃逻辑 |
| TensorRT 引擎层 | 超 optimization profile → 直接报错或结果异常 |

> ❌ “为了快每次只推理一张” → GPU 利用率低、吞吐差<br><br>❌ “batch 越大越好” → 延迟、显存、实时性都会炸<br><br>✅ 正确做法：`kOPT` 对准常见 batch + 合批延迟可接受 + p99 达标

### 7.3 实战要点清单

1. **GPU 推理异步 + 双缓冲**：采集与推理并行，一帧推理一帧准备
2. **数量 + 超时双触发**：到点或满批立即 flush，兼顾吞吐与延迟
3. **永远不超发**`> max_batch`，多出来的拆分到下一波
4. **多模型 → 多实例**：起多个 model instance，由调度器分发
5. **自动驾驶特殊处理**：相机 6 张天然 batch=6；LiDAR 按 10ms 时间片，不等人
6. **监控指标**：QPS、TTFT、TPOT、GPU 显存、队列长度、p99 延迟

## 8. 记忆锚点（可直接用在文章/分享里）

> **TensorRT 是 GPU 上的编译器，Host 是准备食材的厨房，Device 是炒菜的灶台，cudaMemcpy 就是传菜口。**<br><br>**PCIe 是 CPU 和 GPU 之间的桥梁；指针是仓库编号，带宽是桥的车道数。**<br>**单张推理是外卖小哥一单一单跑；多张推理是公交车满载跑；动态合批是拼车系统——目标不是最快，而是单位时间运最多。**<br><br>**合批像公交车：车最多坐 8 人（max_batch），凑满或到点就发车；你要硬塞 16 人（超 profile），车直接散架。**

## 9. 总结

### 9.1 能力模型

```text
底层原理 (PCIe / 内存 / CUDA / 合批)
    ↑
模型导出 (ONNX / TorchScript)
    ↑
推理引擎 (TensorRT / ONNX Runtime)
    ↑
服务封装 (FastAPI / Triton / K8s + 消息队列)
    ↑
生产运维 (监控 / 扩缩容 / 灰度)

```

### 9.2 核心认知

1. TensorRT 是**编译器**，不是运行时
2. Host/Device 数据交互**必须通过指针和 PCIe**
3. 生产用 **离线 Build + 线上 Load**
4. Dynamic Shape 的 **kOPT 决定性能上限**
5. 工程化 = **模型 + 引擎 + 消息队列 + 合批 + 监控**

### 9.3 学习路径

```text
YOLOv8 PyTorch 推理 → ONNX → ONNXRuntime
→ TensorRT(Python) → C++ 推理骨架
→ 动态合批 + Triton + 消息队列
→ CenterPoint 点云部署 → CUDA 插件 + 车端优化

```
