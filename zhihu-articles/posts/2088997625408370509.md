*介绍我们的新论文 “Beyond Parallel Blindness: Information Floors and Model Gaps in Block Drafting”*

论文：[arXiv](https://arxiv.org/abs/2608.27339) ｜ 代码和数据：[github.com/tie-pilot-qxw/specfloor](https://github.com/tie-pilot-qxw/specfloor) ｜ 模型：[Hugging Face](https://huggingface.co/TIE-Pilot/dspark-attnconv-block7-qwen3-4b)

### 一分钟讲清投机解码

大模型生成慢，是因为它一次只能写一个 token，每个 token 都要把整个模型跑一遍。

投机解码（speculative decoding）的思路是”先猜后验”。一个又小又快的 drafter 先猜接下来的几个 token，大模型（target）再一次性把这些猜测全部检查一遍。target 认可的留下，最后 target 自己再补一个 token。

好处是输出质量完全不变。验证规则保证了最终的文本分布和 target 自己生成的一模一样。模型还是那个模型，只是更快了。

快多少，主要看一个数：每一轮平均能留下几个 token，也就是 accepted length。这个方向上大家都在想办法把它往上推。

### 从”一个一个猜”到”一整块一起猜”

传统的 drafter，比如 EAGLE 系列，还是一个 token 一个 token 地猜。drafter 很小，每一步都便宜。但要猜 7 个 token，就得跑 7 步。

Block drafter 换了个思路：一次前向就把一整块都猜出来。在上下文后面接 7 个 mask token，跑一遍，7 个位置的猜测一起出来。

最直接的好处是快。但更重要的是，省下来的时间可以拿去换一个更大的 drafter。自回归的 drafter 每猜一个 token 就要跑一遍，所以只能做得很小，EAGLE-3 只有一层 transformer。block drafter 不管猜多少个 token 都只跑一遍，所以可以做得大得多。DFlash 的论文讲的正是这一点：drafter 越深，接受率越高；一个 5 层的 DFlash drafter 一次猜 16 个 token，速度和接受率都比一次猜 8 个的 EAGLE-3 更好。我们研究的 DFlash 和 DSpark 官方模型也都是 5 层。

所以并行其实是一笔交易：换来一个强得多的 drafter，代价是盲猜。drafter 在猜第 3 个位置的时候，并不知道第 1、2 个位置最后到底是什么。每个位置都得在”看不到前面”的情况下先把答案定下来。

我们把这个叫做 **parallel blindness**（并行导致的”盲猜”）。这篇文章想回答的就是：这笔交易里盲猜这一侧，到底要付出多大代价？

### 先理一下这条技术路线

block drafter 这条路其实有很清楚的来龙去脉，放在一起看会更清楚。

**Apple 的 “Your LLM Knows the Future”（2025）。** 核心观察就写在标题里：普通 LLM 的 hidden state 里，本来就藏着后面好几个 token 的信息。所以他们在输入后面接上 mask token，让同一个模型一次预测多个未来 token，再用 gated LoRA 保证原模型的行为不受影响。他们还加了一个很小的 sampler：一个两层的 MLP，输入是”刚采样出来的那个 token”加上”下一个位置的 hidden state”，让整块内容读起来是连贯的。

**DFlash。** DFlash 保留了”一次出一整块”的做法，并把它做成一个独立的小 drafter：读 target 的 hidden feature，一次并行预测整块的所有位置。块内是完全并行的，位置之间互相看不见。

**DSpark。** DSpark 在并行主干上又接回了一个小的顺序模块，叫 Markov head，让每个位置能根据前一个 token 调整自己的预测。它还加了 confidence-scheduled verification：在高并发的线上服务里，动态决定每个请求验证多长。DSpark 已经在 DeepSeek-V4 的线上服务里跑起来了。

放在一起看，这几个工作其实是同一个套路：一个并行主干负责猜整块，再加一个”看前一个 token”的小修正。Apple 的 sampler 和 DSpark 的 Markov head，就是这个小修正的两种写法。

换句话说，这一整条路线都默默押了两个注：第一，盲猜是有损失的；第二，看一眼前一个 token 就能把大部分损失补回来。但据我们所知，这两件事之前都没有人真正量过。

### 被拒绝，其实有两种原因

一个猜出来的 token 被 target 拒绝了，可能是两种原因：

1. **看不见。** 正确答案取决于 drafter 没被允许看到的 token。
2. **没用好。** 该看的信息其实都看到了，只是 drafter 自己没学好。

这两种情况的解法正好相反。第一种要给 drafter 更多历史信息，哪怕这样会更”串行”、更慢。第二种不需要多看，要的是更好的模型。

麻烦在于，accepted length 把这两种损失混在了一起。一个 drafter 的 accepted length 一般，可能是因为看不见，也可能是因为没用好，也可能两者都有。光看这个数是分不出来的。

### Information floor：给”看不见”定个价

先看论文里的一个小例子：

![](https://pic2.zhimg.com/v2-fa70cf846dee22f8cc3c1203d635afdf_r.jpg)

假设在某个上下文之后，target 有一半概率接”of course”，一半概率接”no problem”。我们只看第二个词。

一个盲猜的 drafter 在猜第二个词的时候，不知道第一个词是”of”还是”no”。它能做到的最好情况就是两边各押一半：”course”一半，”problem”一半。这样不管它多聪明，都有一半的概率被拒绝。这 0.5 不是模型学得不好，而是”看不见”本身的代价。

现在让 drafter 能看到第一个词。看到”of”就猜”course”，看到”no”就猜”problem”，拒绝率直接降到 0。

这就是全部的想法：给定 drafter 能看到的信息，存在一个*任何* drafter 都没法再低的拒绝率下限。我们把它叫做 **information floor**。一个真实的 drafter 在 floor 之上多出来的那部分拒绝，叫做 **model gap**。

还是上面的例子。一个真实的 drafter 在 [course, problem, 其他] 上给出 [0.3, 0.3, 0.4]，拒绝率是 70%。其中 50 个点是 floor，20 个点是 gap。

这个量能真正测出来，靠的是两个很好用的性质：

- 在投机解码的验证规则下，一个猜出来的 token 能留下的概率，恰好等于 1 减去 draft 分布和 target 分布之间的 total variation 距离。所以拒绝率其实就是一个距离，floor 就是能达到的最小距离。
- floor 只需要 target 模型本身。我们从 target 采样很多条续写，在每个上下文里找出最优的那个猜测就行，完全不需要 drafter。

有一点要说明：floor 是一个理想上限，它允许针对每个上下文都给出最完美的猜测。所以 model gap 说的是”还有多少空间”，不代表任何具体架构都能把它全部填平。

### 我们看到了什么

我们在四个开源 target（Qwen3-4B、Qwen3-8B、Qwen3-14B、Gemma-4-12B）、四类 prompt（数学、代码、指令、长对话），以及一个只能通过 API 访问的前沿模型（DeepSeek-V4-Pro）上测了 floor 和 gap。主要结论如下。

### 1. 盲猜确实有代价，而且越往后越大

![](https://pic3.zhimg.com/v2-48af3b37b8ee9fd576220ee61aad6f58_r.jpg)

盲猜的 floor 在块里第一个位置是 0，因为那时还没有什么被藏起来。之后一路往上涨。在 Qwen3-4B 上，7 个 token 的块走到最后一个位置时，哪怕是完美的盲猜 drafter，接受率最多也只有大约 71%。

块越长越严重。块长到 16 的时候，最后一个位置的接受率上限只剩一半左右。

而且这个代价分布得很不均匀。在块的前几个位置，大部分上下文几乎没有损失，损失主要集中在少数”确实可以往好几个方向走”的上下文里。越往后，损失会摊得开一些，但依然很集中。开放式对话比数学、代码付出的代价更大，因为它能接的方向本来就更多。

### 2. 看一个 token，几乎全补回来

现在让每个位置只看它前面那一个真实的 token。floor 在每个位置都下降了 86–100%。块长到 16 的时候，一个 token 依然能去掉大部分 floor。

一个完全独立的测量也得出了同样的结论：我们不测TV距离，而是换成互信息 (mutual information) 来衡量，前一个 token 就能拿回几乎所有有用的路径信息，前两个 token 基本就是全部了。

为什么一个 token 就够？因为 target 的续写其实非常集中。通常只有两三条可能的路径，就像”of course”和”no problem”那样。一旦知道文本走了哪条路，后面的内容基本就定了。

前沿模型上也是同样的规律。

所以这条路线在结构上押对了。像 Apple 的 sampler、DSpark 的 Markov head 这样”看前一个 token”的小修正，原理上足以把盲猜的损失补回来。

### 3. 但现在的 drafter 离 floor 还差得很远

![](https://pic2.zhimg.com/v2-a17adea9829a454b353c25f053fdcced_r.jpg)

对 DFlash 来说，在 Qwen3-4B 上，每个位置的拒绝里 model gap 都占大头。跨四个 target 看，最后一个位置的拒绝里大约有 40% 到 65% 是 model gap。

DSpark 的情况更明显。它的 order-1 floor 非常小。可即使我们直接把*真实*的前一个 token 喂给它的 Markov head，它的拒绝里依然有 85% 以上是 model gap。信息它都有，只是没有转化成接受率。

如果 DSpark 用的是自己猜出来的前一个 token，而不是真实的那个，拒绝率还会更高。我们把多出来的这部分叫做 exposure difference，它反映的是 head 对自己犯错有多敏感。不过这在真实 serving 里不算损失：验证遇到第一个被拒的 token 就停了，一个位置只有在它前面的 token 被接受之后才会被用到。在真正起作用的地方，head 看到的永远是正确的前一个 token。

前沿模型我们没法自己跑 drafter，所以只能间接比较，但方向是一致的：它的 order-1 floor 很小，而公开的 serving 数据推算出来的拒绝率要大得多。

所以瓶颈不在于 drafter 能看到什么，而在于它把看到的东西用得怎么样。

### 4. 真实 serving 里还有个”幸存者效应”

真实服务里，验证遇到第一个被拒绝的 token 就停了。后面的位置只有在前面全部通过时才会用到。而能一路走到后面的，恰恰是那些比较好猜的路径。

所以在真实服务里，靠后位置的拒绝率要比直接测出来的低很多。另一方面，越靠前的位置修好了越值钱。对 DFlash 来说，model gap 随位置越来越大，但单独修好一个位置带来的收益却随位置越来越小。前面的位置护着后面的一切。这也和 DSpark 作者自己的看法一致：前几个位置猜得准才是最重要的。

### 那应该改什么？

不是让 drafter 看更多历史。一个 token 在信息上已经够了。

要改的是：drafter 怎么用好这一个 token。

看一下 DSpark 的 Markov head。它加的修正只取决于前一个 token 本身。所以前一个 token 换了之后，drafter 对下一个 token 的偏好，在*所有*上下文里都是按同一个方向调整的。backbone 再强也改变不了这一点。

但信息本身允许更丰富的关系。同样的前一个 token，在不同上下文里可能要接不同的词。”of”在一句话里后面接”course”，在另一句话里可能接”the”。一个加性的修正很难表达这种关系。Apple 的 MLP sampler 把前一个 token 和当前位置的状态非线性地混在一起，表达能力更强一些。我们想再往前走一步：让前一个 token 真正回头去看上下文。

### 我们的做法：prefix-attention head

这个 head 很简单：

1. 用前一个 token 的 embedding 和 drafter 在这个位置的状态，生成一个 query；
2. 用这个 query 对已经确定的上下文做 attention；
3. 结果再过一个小 MLP，加到主干输出的 logits 上。

说白了就是让前一个 token 去问上下文：”我排在你后面的话，下一个应该是什么？”

关键在于，这个 head 能看到的信息和 DSpark 完全一样：已经确定的上下文，加上前一个 token。它的 floor 没变。所以任何提升都只能来自”用得更好”，而不是”看得更多”。

另外我们还借鉴了几个和这个更重的 head 搭配的设计。其中最重要的是 DFlash2 的 lattice walk，值得多讲两句。

一个看前一个 token 的 head，天然是顺序执行的：先采样第 1 个位置，把它喂给 head 得到第 2 个位置的分布，再采样，依此类推。这就是一个 Markov walk。DSpark 的 head 很轻，这样一步一步走没问题；我们的 head 要做 attention，每个位置调用一次就太慢了。

lattice walk 其实就是同一个 walk，只多了一步：提前猜好这个 walk 可能经过哪些 token。先让主干在每个位置提名 top-16 个候选，再让 head 在一次并行调用里，把每个位置上所有”前一个候选 → 下一个候选”的组合都打好分。这样每个位置都有一张小表，walk 本身就只剩几次很便宜的查表。

所以它不是一种新的 proposal，而是限制在候选集里的 Markov walk。如果把候选集放大到整个词表，它选出来的 token 和顺序 walk 一模一样。能并行，全靠提前猜的这一步。

但这个猜测是有代价的。如果 target 想要的 token 不在这 16 个候选里，drafter 就永远提不出它，所以这个限制可能会损失一部分接受长度。在我们的一次测量里，把 DSpark 的 head 限制在它自己的 top-16 里，接受长度掉了大约 2%。这也是我们加 nomination loss 的原因：它训练主干，让 top-16 尽量包含 target 的选择。加了这个 loss 之后，同样的限制几乎没有损失。

除了 lattice，我们还在主干里加了一个小的两抽头卷积和可学习的 slot embedding。

在 Qwen3-4B 上和 DSpark 官方发布的 checkpoint 相比：

![](https://pic3.zhimg.com/v2-6bf01c67bd5f034a44f98347e4ab24a8_r.jpg)

- 第一个位置之后，每个位置的 model gap 都下降了。最后一个位置下降了大约四分之一，而 floor 完全没变。
- 九个 benchmark 上的平均 accepted length 提升了 3–4%。
- 虽然 head 更重了，端到端速度在两个温度下都更快：相对普通解码，temperature 0 下从约 3.6× 提到 3.8×，temperature 1 下从 3.3× 提到 3.5×。

exposure difference 确实变大了。但就像前面说的，这在 serving 里不造成损失：一个位置只有在前一个 token 被接受之后才会被用到，所以 head 在起作用的地方看到的都是正确的前一个 token。真正重要的是给对前一个 token 时预测得准不准，而变好的正是这一项。

### 训练和部署上的优化

head 变重了，如果训练和推理都跟着变慢，那也没什么意义。所以我们在 infra 上花了不少功夫，训练和 serving 两边都做了优化。

**训练：从每步约 30 秒降到约 15 秒。** 我们的起点是 DSpark 作者开源的训练代码 [DeepSpec](https://github.com/deepseek-ai/DeepSpec)，用的是它发布的 Qwen3-4B 配置（4 张 H100，global batch 512）。在做任何优化之前，我们只改了一处：DeepSpec 训练时读的是预先算好、存下来的 target 输出（target cache），Qwen3-4B 的这份 cache 大约要 38 TB。我们存不下，所以改成在训练循环里实时跑冻结的 target。

在这套代码上，DSpark 原版结构每个优化步大约要 24 秒，我们更重的 drafter 大约要 30 秒。做完下面这些优化后，我们的 drafter 每步只要大约 15 秒，硬件相同，每张卡上的计算量也完全一样。差不多正好快了 2 倍，甚至比优化前的 DSpark 原版结构还快，10 个 epoch 也从预计的 8.4 天缩短到了 4.6 天。

这里面没有什么神奇的技巧。每一项优化，都是先用 profiler 抓 trace，看清时间到底花在哪，再对症下药。

- **每个优化步只归一化一次 loss，而不是每个 micro-batch 一次。** 每个优化步里，每张卡要跑 128 个 micro-batch。以前每个 micro-batch 都要先在所有卡之间同步一次 token 数，卡之间一直在互相等。现在每个 micro-batch 只累加自己的部分，整个优化步最后同步一次就行。原版 DeepSpec 里也是每个 micro-batch 同步一次。快了约 6%。这一项也会稍微改变 loss 的加权方式，所以不完全是纯粹的加速。不过我们觉得新的加权方式反而更合理：同一个优化步里，每个 token 的权重都一样，和 batch 怎么切到各张卡、各个 micro-batch 上无关。而按 micro-batch 归一化的话，一个 token 的权重取决于同一个 micro-batch 里恰好还分到了哪些序列。
- **融合的 teacher 前向。** 冻结的 Qwen3 target 每个 micro-batch 都要跑一遍，而它是整个训练循环里唯一还在用 Hugging Face 原生 eager 实现跑的部分。我们把它重写成只做 prefill 的前向：合并 QKV 和 gate/up 的矩阵乘，融合 norm、RoPE 和激活函数的 kernel，再换上 FlashAttention-3。光 teacher 这一块就快了 1.7–2.3 倍。（这一项只对像我们这样实时跑 target 的训练有用。）
- **编译 loss。** 全词表上的 L1 loss 原来会生成两个巨大的 fp32 概率张量，用 `torch.compile` 之后这两个张量就不需要了。加上融合 teacher，这两项一起让每步快了约 22%。
- **top-k 只算一次。** trace 显示，全词表上的一次 top-k 比 lm_head 还贵，而且算了两遍，其中一遍还毫无必要地转成了 fp32。现在只在 bf16 上算一次。
- **把冻结的 embedding 和 lm_head 移出 FSDP。** 这是收益最大、也最出乎意料的一项。FSDP 把整个模型压平成了一个大参数。冻结的 embedding 和 lm_head 占了全部权重的一半以上，但因为被压进了这个大参数里，每一次梯度操作它们都要跟着参与。原版 DeepSpec 也是这样包装模型的。把它们拿出来之后，每步又快了 13%，还省了 3 GB 显存。

每一项改动都和改之前的代码对比验证过：第一步的 loss 完全一致，checkpoint 的加载方式也不受影响。这些开关都包含在开源的训练代码里。

**Serving：head 更重，速度反而更快。** 在 SGLang 这一侧，head 的投影是预先算好的，上下文的 key/value 用一个融合 kernel 一次写入，短卷积用 Triton kernel 实现，整个候选 lattice walk 都放进了 CUDA graph。所以虽然新 head 要做更多计算，端到端速度反而更快。

### 总结

1. 一次盲猜一整块，是有真实、可测量的代价的，而且块越长代价越大。
2. 只要看一个真实的前一个 token，几乎就能把这个代价全部补回来。
3. 现在的 block drafter，损失主要来自”没用好”，而不是”看不见”。
4. 所以接下来的提升空间，在于 drafter 怎么用好前一个 token 和上下文，以及怎么把块里前几个位置猜准。
5. 工程和建模一样重要：把训练循环仔细 profile 一遍，每步时间就减半了，10 个 epoch 的训练才变得跑得起。
