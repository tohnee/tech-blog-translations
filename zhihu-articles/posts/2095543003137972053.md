## PagedAttention 与 vLLM：用操作系统分页思想管理大模型推理的 KV Cache

**论文标题**：Efficient Memory Management for Large Language Model Serving with PagedAttention

**发表**：ACM SOSP 2023

**链接**：arXiv:2309.06180

**代码**：[https://github.com/vllm-project/vllm](https://github.com/vllm-project/vllm)

### 摘要

大模型在线推理的吞吐瓶颈往往不在算力，而在 KV Cache 的显存管理：现有系统按请求的最大可能长度连续预分配显存，造成空间浪费。论文提出 PagedAttention，把每条序列的 KV Cache 切分为固定大小的块，用类似操作系统页表的 block table 把逻辑块映射到非连续的物理块，并按需分配，在相同显存和相近延迟下容纳更多请求，从而提升吞吐。

### 1. 问题背景

### 1.1 KV 缓存 —— 自回归推理的显存瓶颈

大语言模型（Large Language Model, LLM）的推理是自回归的：给定输入 token 序列 $(x_1,\ldots,x_n)$，模型逐个生成后续 token。语言模型对整个序列的联合概率做自回归分解：

$$ P(x)=P(x_1)\cdot P(x_2\mid x_1)\cdots P(x_n\mid x_1,\ldots,x_{n-1}) $$

其中 $x_i$ 是第 $i$ 个 token，$P(x_i\mid x_{<i})$ 是模型在给定前文时对当前 token 的预测分布。Transformer 的自注意力层需要把每个位置的 query 与所有历史位置的 key 做点积，再用得到的权重对 value 加权求和。为了避免每生成一个 token 都把整个前缀重新计算一遍，推理系统会缓存历史 token 的 key 和 value，这就是 **KV Cache**。

对标准多头注意力，单条序列的 KV Cache 大小为：

$$ M_{\mathrm{KV}}=2\times L\times H\times d\times S\times b\times \mathrm{sizeof(dtype)} $$

其中 $L$ 是层数，$H$ 是 KV 头数，$d$ 是每个头的维度，$S$ 是序列长度，$b$ 是并发批大小，系数 2 表示 key 和 value 各一份。论文给出的具体例子是 13B 参数的 OPT 模型：hidden size 为 5120，层数为 40，使用 FP16（2 字节）。单个 token 的 KV Cache 为

$$ 2\times 5120\times 40\times 2=819{,}200\ \text{字节}\approx 800\ \text{KB}. $$

在 NVIDIA A100 40GB 上，13B 模型权重约占 26GB（65%），KV Cache 约占 30%，留给激活值的空间很小。也就是说，能同时服务多少请求，主要取决于 KV Cache。

![](https://pic4.zhimg.com/v2-5a81fcb20c34c4b95d0c356789cc1989_r.jpg)

*图1:13B OPT 的显存布局与吞吐随 batch 的变化（来源:论文 Figure 1）*

推理过程分为两个阶段。

**预填充阶段（prefill）** 一次处理整个用户 prompt，计算第一个新 token 的概率，并生成 prompt 中所有 token 的 KV；这一步可以并行，且计算密集。

**解码阶段（decode）** 每次只输入一个新 token，计算下一个 token 的概率，并只新增该 token 的 K/V；由于每步只处理一个 token，GPU 计算单元大量空闲，瓶颈落在显存带宽上。解码阶段是单请求延迟的主要来源。

把多个请求合批（batching）可以提高 GPU 利用率；但 batch 越大，KV Cache 占用越高。因此，**KV Cache 的显存管理方式直接决定了最大 batch size，进而决定了服务吞吐**。

### 1.2 连续预分配的三类内存浪费

现有 LLM 服务系统（以 FasterTransformer 和 Orca 为代表）通常把一条请求的 KV Cache 存放在一段**连续**的显存中。为了容纳不断生成的 token，系统会在请求开始时按该请求的最大可能长度预留一整块连续显存。

> To store the KV cache of a request in contiguous space, they pre-allocate a contiguous chunk of memory with the request’s maximum length (e.g., 2048 tokens).<br> — *Section 1, Introduction*

这种做法的根本问题在于，KV Cache 与传统深度学习张量不同：它在生成过程中动态增长，事先并不知道最终长度。

> The KV cache has unique characteristics: it dynamically grows and shrinks over time as the model generates new tokens, and its lifetime and length are not known a priori.<br> — *Section 1, Introduction*

按最大长度连续预分配会带来三类浪费：

- **内部碎片（internal fragmentation）**：实际生成长度往往远小于最大长度，预留块尾部永远不会被使用到的空间。
- **预留（reservation）**：预留块尾部未来会被使用到，但暂时没被使用到的空间，理论上应该可以暂时分配给其他请求使用
- **外部碎片（external fragmentation）**：不同请求的预留块大小不一，频繁分配和释放后，显存中会留下许多不连续的空洞；即使空洞总量足够，也可能凑不出一块满足新请求最大长度的连续空间。

*图3:连续分配下的三类内存浪费（来源:论文 Figure 3）*

### 1.3 无法共享

除了浪费，连续分配还让**内存共享**变得困难。LLM 服务中常见的两类解码算法都需要共享：

- **并行采样（parallel sampling）**：对同一个 prompt 生成多个随机样本，多个输出在 prompt 部分拥有完全相同的 KV。
- **束搜索（beam search）**：保留概率最高的 $k$ 条候选序列，不同候选在共享前缀上的 KV 也相同。

如果每条序列都独占一段连续显存，即使前缀完全相同，也只能各存一份。

如果 KV Cache 在物理上不必连续，那么就可以让多个逻辑块指向同一个物理块。这样，碎片和共享问题可以在同一个机制下解决。

### 2. 主要贡献

1. **提出 PagedAttention**：一种直接在非连续 KV 块上计算注意力的算法，把操作系统的分页思想引入注意力算子。它允许 KV Cache 按固定大小的块分配，物理块可以分散，并通过 block table 在逻辑块和物理块之间建立映射。
2. **设计并实现 vLLM**：一个完整的 LLM 服务系统，包含块级 KV Cache 管理器、抢占式调度、分布式张量并行执行，以及为分页访问定制的 GPU 内核；系统开源，支持 GPT、OPT、LLaMA 等模型。

### 3. 前置知识

### 3.1 虚拟内存与分页

操作系统把物理内存划分为固定大小的**页（page）**，为每个进程维护一张**页表（page table）**，把进程看到的连续**逻辑地址**映射到可能分散的物理页。进程不需要知道数据实际在哪一页，只要按逻辑地址访问，操作系统负责翻译。

### 3.2 写时复制与引用计数

**写时复制（Copy-on-Write, COW）** 是操作系统 `fork` 等场景中的经典技术：多个进程初始时共享同一份物理页，只有当某个进程要写入时，才为它复制一份私有副本。为了知道一份物理页被多少个逻辑页引用，系统维护**引用计数（reference count）**；计数归零时才能回收。

在 PagedAttention 中，多个序列可以共享同一个物理块。只要它们都不修改该块，就无需复制；当某个序列要写入共享块时，才触发 COW，分配新块并复制旧内容。引用计数决定何时可以安全释放物理块。

### 3.3 迭代级调度与连续批处理

传统批处理以**请求**为调度单位：一个 batch 要等其中最慢的请求结束后才能整体结束，短请求会“陪跑”，新请求也要等待。

**迭代级调度（iteration-level scheduling）**：每轮迭代后，已完成的请求立即移出 batch，新到达的请求可以立即加入，从而减少空闲和填充浪费。

### 3.4 并行采样与束搜索

**并行采样**对同一个 prompt 独立生成多条输出，每条输出在 prompt 部分的 KV 完全相同，只有生成部分不同。**

束搜索**在每一步保留概率最高的 $k$ 条候选序列（$k$ 称为 beam width），不同候选可能共享前缀，也可能在某个位置生成相同的 token 而继续共享。

### 4. 方法

### 4.1 整体架构

vLLM 采用集中式调度器（scheduler）协调多个 GPU worker，整体结构如图4所示。系统中有三类主要组件：

- **调度器**：决定每个解码迭代要运行哪些序列，为它们准备输入 token ID 和 block table，并把控制信息广播给 GPU worker。
- **KV Cache 管理器**：维护逻辑块到物理块的映射（block table），管理 GPU 上的物理块分配与回收，以及 CPU 上的交换空间。它包含 GPU block allocator 和 CPU block allocator。
- **GPU worker**：执行模型的前向计算。每个 worker 只负责一部分注意力头，因此只存储对应头的 KV Cache。

这种设计把**内存管理的控制面**放在 CPU 侧，把**计算的数据面**放在 GPU 侧。调度器在每轮迭代开始时把 block table 和输入 token 一起发给 worker；worker 不需要在解码过程中同步内存管理状态，只需要按 block table 读取 KV。这样，复杂的共享和回收逻辑不会侵入模型执行路径。

### 4.2 PagedAttention：在非连续块上做注意力

PagedAttention 的核心是把每条序列的 KV Cache 划分为固定大小的 **KV 块（KV block）**。论文的定义是：

> PagedAttention partitions the KV cache of each sequence into KV blocks. Each block contains the key and value vectors for a fixed number of tokens.<br> — *Section 4.1, PagedAttention*

也就是说，每条序列的 KV 在逻辑上被切成固定大小的块，每块存放固定数量 token 的 K/V，块与块之间不必物理相邻。

设块大小为 $B$（即每个块容纳 $B$ 个 token 的 K/V）。第 $j$ 个逻辑块中的 key 和 value 分别为

$$ K_j=(k_{(j-1)B+1},\ldots,k_{jB}),\qquad V_j=(v_{(j-1)B+1},\ldots,v_{jB}). $$

标准的注意力计算对每个 query $q_i$ 与所有历史 key 做点积，再用 softmax 得到权重并对 value 加权求和。PagedAttention 把这个计算改写为**按块求和**：

$$ A_{ij}=\frac{\exp(q_i^\top K_j/\sqrt{d})} {\sum_{t=1}^{\lceil i/B\rceil}\exp(q_i^\top K_t/\sqrt{d})}, \qquad o_i=\sum_{j=1}^{\lceil i/B\rceil}V_jA_{ij}^\top . $$

其中 $q_i$ 是第 $i$ 个 token 的 query 向量；$K_j$ 和 $V_j$ 是第 $j$ 个 KV 块中的 key、value 矩阵；$B$ 是块大小；$\lceil i/B\rceil$ 是覆盖位置 $1$ 到 $i$ 所需的块数；$A_{ij}=(a_{i,(j-1)B+1},\ldots,a_{i,jB})$ 是 query $i$ 对第 $j$ 个块内各 token 的注意力权重行向量；$o_i$ 是输出向量。对最后一个未填满的块，内核会屏蔽超出当前位置的 slot，因此计算结果与标准注意力一致。

![](https://pic2.zhimg.com/v2-fab8a5d97c97abcc5411b542c9c0d615_r.jpg)

*图5:PagedAttention 示意（来源:论文 Figure 5）*

代价是内核需要额外的间接寻址：读每个块之前要查 block table，还要处理变长序列和不同块的分支。

### 4.3 KV Cache 管理器：逻辑块、物理块与块表

vLLM 的内存管理器直接借用了虚拟内存的思想：

> The key idea behind vLLM’s memory manager is analogous to the virtual memory in operating systems. OS partitions memory into fixed-sized pages and maps user programs’ logical pages to physical pages.<br> — *Section 4.2, KV Cache Manager*

具体来说，每条请求的 KV Cache 被表示为一串**逻辑 KV 块（logical KV block）**，从左到右编号；GPU 上的物理显存被划分为同样大小的**物理 KV 块（physical KV block）**。系统为每条请求维护一张 **block table**，每个表项记录一个逻辑块对应的物理块编号，以及该块中已经填入了多少个 token。逻辑块 0、1、2 可以映射到物理块 7、1、3，物理上完全不连续。

分配是**按需**的：序列增长到需要新块时才分配；块写满后再分配下一块。系统不需要在请求开始时预留最大长度，因此不会出现“为 2048 个位置预留、实际只用 200 个”的情况。一块中尚未填满的位置仍然属于该请求，但浪费被限制在**最后一个块**内。论文对此的总结是：

> vLLM limits all the memory waste for a request within one block, so it can effectively utilize all the memory, as shown in Fig. 2.<br> — *Section 4.3, Decoding with PagedAttention and vLLM*

由于所有物理块大小相同，外部碎片也被消除：任何空闲块都可以分配给任何需要新块的序列，不会出现“总量够但凑不出连续大块”的问题。内部碎片则被限制在每条序列最后一个未填满的块中，最多浪费 $B-1$ 个 token 的位置。

图6展示了一次具体的映射过程。假设一个 prompt 有 7 个 token，块大小为 4。vLLM 把前 4 个 token 放进逻辑块 0，把后 3 个 token 放进逻辑块 1；两个逻辑块分别映射到物理块 7 和物理块 1。逻辑块 1 还剩一个空位。解码生成第 8 个 token 时，它被填入逻辑块 1 的最后一个位置；生成第 9 个 token 时，逻辑块 1 已满，vLLM 分配一个新的物理块（例如物理块 3）作为逻辑块 2，并在 block table 中记录映射。

![](https://pica.zhimg.com/v2-d7acc755ffd6aa1c24b73af81bffca3c_r.jpg)

*图6:逻辑块到物理块的翻译（来源:论文 Figure 6）*

**补充说明**：与操作系统页表不同，vLLM 的 block table 由软件维护，通常存放在 CPU 内存中，每轮迭代随输入一起发送给 GPU worker；GPU 上没有为这套 block table 提供硬件地址翻译，实际是由注意力内核根据 block table 显式地 gather 各个物理块。这是“软件分页”而非“硬件分页”。

### 4.4 一次解码迭代的完整流程

把上面的组件串起来，vLLM 的一轮解码迭代大致如下：

1. 调度器从等待队列和运行队列中选择本轮要处理的序列，组成 batch。
2. KV Cache 管理器为这些序列新增的逻辑块分配物理块，更新 block table。
3. 调度器把本轮所有序列的输入 token（prefill 时是完整 prompt，decode 时是上一步生成的新 token）拼接成一条输入序列。
4. 调度器把输入 token ID 和每条序列的 block table 广播给 GPU worker。
5. GPU worker 执行模型前向计算；注意力内核根据 block table 读取历史 KV，并把新生成的 KV 写入对应的物理块。
6. 采样得到下一个 token，更新 block table 中最后一个块的填充计数；如果该块已满，下一轮再分配新块。
7. 若序列遇到结束符或达到最大长度，释放其全部物理块，供其他请求使用。

这里有一个容易忽略的点：**prefill 和 decode 可以共用同一套分页机制**。prefill 阶段可以先用常规自注意力算出 prompt 的 KV，再按块写入；decode 阶段则用 PagedAttention 内核逐块读取历史 KV。两者的区别只在于一次处理多少 token，内存布局是一致的。

### 4.5 内存共享：引用计数与写时复制

PagedAttention 的块级映射让“多个逻辑块指向同一个物理块”成为可能，而引用计数和写时复制负责保证正确性。

### 并行采样

图7展示了并行采样的例子。两条输出序列 A1 和 A2 共享同一个 prompt，它们的 prompt 逻辑块被映射到相同的物理块（物理块 7 和 1），因此 prompt 的 KV 只存一份。生成阶段，两条序列开始产生不同的 token：

- 当 A1 要写入逻辑块 1 时，vLLM 发现对应物理块 1 的引用计数大于 1（A1 和 A2 都在引用它），于是分配一个新的物理块 3，把物理块 1 的内容复制过去，并将物理块 1 的引用计数减 1；A1 后续的 KV 写入物理块 3。
- 当 A2 要写入物理块 1 时，引用计数已经降为 1，说明它现在是独占的，可以直接写入，无需复制。

这样，除了第一个发生分叉的块需要复制一次，后续块都是各写各的。对于长 prompt，绝大部分 KV 仍然共享，节省的显存非常可观。

### 束搜索

图8给出了 beam width $k=4$ 的例子：初始时 4 条候选共享 prompt 块；随着解码推进，候选可能在某些位置分叉，也可能在另一些位置生成相同的 token 而继续共享。当某些候选被剪枝（不再进入 top-$k$）时，它们占用的逻辑块被释放，对应物理块的引用计数减 1；计数归零的物理块被回收。新进入 top-$k$ 的候选需要新的物理块，而如果它们在某些位置生成了相同的 token，又可以共享同一批新块。

传统系统在束搜索中经常需要频繁复制 KV Cache 来跟随候选的变化；vLLM 的块级共享把复制限制在“新生成的 token 落在旧的共享块内”这一种情况，而且每次只需复制一个块。这大幅降低了束搜索的内存搬运开销。

![](https://pic2.zhimg.com/v2-70c3b8a6a8daa3ca3dcc5ae431d3c331_r.jpg)

*图8:束搜索中的动态共享（来源:论文 Figure 9）*

### 混合解码方法

不同请求可能使用不同的解码算法（贪心、并行采样、束搜索），它们的共享模式各不相同。vLLM 把这些差异隐藏在统一的 block table 映射层之下：模型执行内核只看到每条序列的物理块 ID 列表，不需要知道这些块是否被其他序列共享。因此，使用不同解码算法的请求可以同时批处理，系统整体的批处理机会更多。

### 4.6 调度与抢占

请求的输入长度和输出长度都不可预知，KV Cache 可能在运行过程中耗尽。vLLM 需要在这种情况下做**抢占（preemption）**：暂停某些请求，释放它们的块，等显存空出来后再恢复。

调度策略方面，vLLM 采用**先来先服务（First-Come-First-Serve, FCFS）**，保证公平性并防止饥饿。需要抢占时，最早到达的请求优先保留，最晚到达的请求优先被抢占。

抢占时有两个设计选择：

- **驱逐哪些块**：vLLM 采用**全有或全无（all-or-nothing）**策略，要么驱逐一条序列的全部块，要么一个都不驱逐。原因是同一序列的所有块在每轮迭代中都会被访问；只驱逐一部分既不能释放足够空间，也会让恢复逻辑变复杂。
- **如何分组**：一个请求内部的多个序列（例如束搜索的多条候选）被组成一个**序列组（sequence group）**，组内序列总是一起被抢占或一起被重新调度，因为它们之间可能存在块共享。

释放块之后，还需要决定如何恢复被抢占的序列。vLLM 支持两种机制：

- **交换（swapping）**：把被驱逐的块复制到 CPU 内存，需要时再复制回 GPU。
- **重计算（recomputation）**：直接丢弃 KV Cache，等序列被重新调度时重新计算。一个有利的性质是，重计算的延迟可能明显低于最初的计算：已经生成的 token 可以和原始 prompt 拼接成一个新的 prompt，在一次 prefill 中并行算出所有位置的 KV，而不是像原来那样逐个 token 解码。

### 4.7 分布式执行与内核优化

当模型大到单卡放不下时，vLLM 采用 Megatron-LM 风格的**张量模型并行（tensor model parallelism）**：把每一层的线性层按列或按行切分到多张 GPU 上，注意力算子则按注意力头维度切分，每个 GPU worker 负责一部分头。由于每个 worker 处理的是同一组输入 token，只是负责不同的头，因此全局只需要一个 KV Cache 管理器；每条序列的逻辑块到物理块的映射对所有 worker 一致，每个 worker 只在自己的显存中存储自己负责的那些头的 KV。

在实现层面，vLLM 还做了三项内核优化来降低分页带来的开销：

1. **融合 reshape 与块写入**：把新生成的 KV 切块、reshape 成适合块读取的布局、写入 block table 指定的位置，合并成一个内核，减少内核启动次数。
2. **融合块读取与注意力计算**：注意力内核按照 block table 读取 KV，一边读一边算，而不是先把块复制到连续缓冲区再做注意力；每个 GPU warp 负责读取一个块，以改善合并访存。
3. **融合块复制**：写时复制可能涉及多个不连续的块；vLLM 把不同块的复制操作合并到一次内核启动中，避免大量小的 `cudaMemcpyAsync` 调用。

vLLM 的实现约为 8.5K 行 Python 和 2K 行 C++/CUDA：调度器和块管理器等控制逻辑用 Python，PagedAttention 等关键内核用 C++/CUDA。前端提供兼容 OpenAI API 的接口，用户可以设置最大序列长度、beam width 等采样参数。

### 4.8 完整流程串联

把一条请求的完整生命周期串起来：

1. 请求到达，调度器把它放入等待队列，KV Cache 管理器暂不分配显存。
2. 轮到时执行 prefill：计算 prompt 的 KV 和第一个输出 token，按块写入物理块，建立 block table。
3. 进入解码循环：每轮迭代，调度器选择 batch，管理器按需分配新块，GPU worker 用 PagedAttention 读取历史 KV、写入新 KV，采样出下一个 token。
4. 如果请求使用并行采样或束搜索，多个输出序列共享前缀块，分叉时通过引用计数和 COW 复制；被剪枝的候选释放块。
5. 如果显存不足，按 FCFS 抢占最晚到达的请求，选择交换或重计算来恢复。
6. 请求结束，释放全部物理块，归还给空闲池，供后续请求使用。

### 5. 实验：设计取舍与适用边界

### 5.1 适用边界：什么时候收益会变小

PagedAttention 解决的是**显存约束**。如果系统本来就不缺显存，收益自然会缩小。

论文在 Alpaca 数据集和 OPT-175B 上观察到了这一点：OPT-175B 的服务器配置（8 张 A100-80GB）为 KV Cache 留出了很大的空间，而 Alpaca 的序列又比较短，因此 Orca 的 Oracle 和 Pow2 版本即使内存管理有浪费，也能同时批处理大量请求；此时系统瓶颈从显存转移到了计算，vLLM 相对 Orca 的优势就不如 ShareGPT 上明显。

### 5.2 块大小的权衡

块大小 $B$ 是 PagedAttention 最重要的实现参数之一：

- $B$ 太小：块数变多，block table 变长，内核需要处理更多小块，每次块读取的并行工作量不足，可能无法充分利用 GPU 的并行度；同时块级共享的粒度更细，元数据开销更大。
- $B$ 太大：最后一块的内部碎片最多可达 $B-1$ 个 token；共享的粒度变粗，两条序列只有在更大的前缀完全相同时才能共享，共享概率下降。

![](https://pica.zhimg.com/v2-89eb674eab11cd64bf40f438789c17f2_r.jpg)

*图9:块大小对性能的影响（来源:论文 Figure 18）*

**16 是论文在其实验负载上的经验折中，不是 PagedAttention 的定义要求**。实际系统中块大小可以配置，需要结合序列长度分布、共享模式和内核实现来选择。

### 5.3 重计算与换出的取舍

被抢占的序列如何恢复，与块大小有直接关系。论文的微基准和端到端实验（图10）给出了两个结论：

- **换出对块大小敏感**：块太小时，换出会产生大量小的 CPU–GPU 数据传输，无法充分利用 PCIe 带宽，开销显著上升；块较大时，数据传输更连续，换出更高效。
- **重计算对块大小不敏感**：重计算不使用 KV 块，其开销主要取决于需要重新计算的 token 数，在不同块大小下大致恒定；并且论文观察到，重计算的开销最高不超过换出延迟的 20%。

因此，块很小时重计算更划算，块很大时换出更划算。

![](https://pic4.zhimg.com/v2-8dcb960fb84ff3e8e4fa0e1ee4c6b47b_r.jpg)

*图10:重计算与换出的开销对比（来源:论文 Figure 19）*

### 5.4 分页的内核开销

PagedAttention 不是免费的。动态块映射要求注意力内核访问 block table、执行额外的分支、处理变长序列和分散的块。论文的微基准显示，这会使注意力内核的延迟比高度优化的 FasterTransformer 实现高 **20%–26%**。不过，这一开销只作用在注意力算子上，不涉及线性层等其他算子；由于分页带来的显存节省能让 batch 更大，端到端性能仍然更优。

### 7. 延伸阅读

- **Y. Yu et al., Orca: A Distributed Serving System for Transformer-Based Generative Models, OSDI 2022.** 迭代级调度/连续批处理的代表工作，是 vLLM 的重要对照与互补系统；理解 Orca 才能看清“调度”和“内存管理”各自解决什么问题。
- **T. Dao et al., FlashAttention: Fast and Memory-Efficient Exact Attention with IO-Awareness, NeurIPS 2022.** 从 IO 角度优化注意力内核的经典工作，与 PagedAttention 正交；vLLM 的块读取与注意力融合也受这类内核设计影响。
- **Y. Sheng et al., High-throughput Generative Inference of Large Language Models with a Single GPU, arXiv 2023.** FlexGen 研究在有限 GPU 显存下如何通过 offloading 和内存调度跑大模型，是“显存受限推理”的另一条技术路线。
- **R. Pope et al., Efficiently Scaling Transformer Inference, MLSys 2023.** 系统分析大模型推理中的模型并行、内存布局和通信开销，有助于理解 vLLM 分布式执行部分的背景。
- **M. Shoeybi et al., Megatron-LM: Training Multi-Billion Parameter Language Models Using Model Parallelism, arXiv 2019.** vLLM 的分布式执行采用 Megatron-LM 风格的张量模型并行；读它可以补足“按注意力头切分”这一实现的来龙去脉。
