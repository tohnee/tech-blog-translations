## 第一部分：RDMA 理论基础 — 深度详解

> 面向 RDMA 零基础初学者，每一个概念都配有代码位置和源码引用，让我们对着代码学理论。

---

### 1.1 什么是 RDMA

### 1.1.1 一句话定义

**RDMA = Remote Direct Memory Access。一台机器的网卡可以直接读/写另一台机器的内存，而对方 CPU 完全不知情。**

如果你有后端开发经验，对应关系是：

| 传统 TCP 编程 | RDMA 编程 |
| --- | --- |
| socket() | ibv_create_qp() |
| connect() / accept() | rdma_connect() / rdma_accept() 或手动 ibv_modify_qp() |
| send() / recv() | ibv_post_send() / ibv_post_recv() |
| epoll_wait() | ibv_poll_cq() —— 主动轮询，不是事件通知！ |
| bind() 的地址 | GID（128位，类似 IPv6） |

### 1.1.2 传统 Socket 为什么慢

让我们从一段真实的 Linux 内核代码开始理解。当你调用 `write(fd, buf, len)`，内核做了什么？

```text
// linux-kernel/fs/read_write.c → ksys_write()
// 1. 用户空间 buf 可能没在物理内存中 → 触发缺页中断
// 2. 从用户空间 copy 到内核空间 (copy_from_user)
// 3. 内核 TCP/IP 协议栈处理：分段、校验、拥塞控制、重传逻辑
// 4. 从内核空间 copy 到网卡 DMA 缓冲区
// 5. 网卡发送
```

**TCP 的数据路径上有 2~4 次 CPU 内存拷贝，且每一步都要经过内核。** 这就是延迟高和 CPU 高的根本原因。

### 1.1.3 RDMA 怎么做到”零拷贝 + 内核旁路”

**关键机制：数据路径和控制路径分离。**

```text
控制路径（建连、注册内存 — 经过内核）：
  用户程序 → libibverbs → write(/dev/uverbsX) → 内核 uverbs_cmd.c → 硬件
  这是一次性的、慢路径。

数据路径（发数据 — 绕过内核！）：
  用户程序 → libibverbs → 直接写硬件门铃寄存器 → 网卡 DMA 用户内存 → 网络
  每次 ibv_post_send() 都是一次函数调用 + 一次 MMIO 写，没有任何内核参与。
```

**在代码中体现**：看 `ibv_post_send` 的实现：

```text
// rdma-core/libibverbs/verbs.c (简化版)
int ibv_post_send(struct ibv_qp *qp, struct ibv_send_wr *wr,
                  struct ibv_send_wr **bad_wr) {
    // 直接调用厂商的 post_send，不经过内核！
    return qp->context->ops.post_send(qp, wr, bad_wr);
}
```

注意：**没有 `write(fd)` 系统调用**。厂商的 `post_send` 直接把 WQE（工作请求）写到网卡的环形队列 + 写一个门铃寄存器，硬件就开始 DMA 了。这是 RDMA 高性能的根因。

### 1.1.4 一张图对比

```text
传统 TCP 发数据（CPU 重度参与）：
  App Buffer →[copy_from_user]→ 内核 skb →[TCP/IP栈]→ 网卡 → 网络
       ↑                            ↑
   缺页中断                    CPU 密集处理

RDMA 发数据（CPU 基本旁观）：
  App Buffer →[HCA DMA 直接读]→ 网卡 → 网络
       ↑
  必须预先 pin 住（ibv_reg_mr），确保物理页不会换出
```

### 1.1.5 量化的性能差异

| 指标 | TCP/IP | RDMA (RoCE v2) | 原因 |
| --- | --- | --- | --- |
| 小消息延迟 | 10~50 μs | 1~3 μs | 无内核切换 + 硬件级协议卸载 |
| 100Gbps 线速 CPU 占用 | ~50-80% 单核 | % 单核 | 数据路径不走内核 |
| 内存拷贝次数 | 2-4 次 | 0-1 次 | HCA 直接 DMA 用户空间 buffer |
| 远端 CPU 参与 | 必须 | 单边操作为 0 | RDMA WRITE/READ 对方 CPU 不参与 |

### 1.2 三种传输协议对比

### 1.2.1 为什么会有三种？

RDMA 的操作语义（SEND / WRITE / READ / ATOMIC）是**统一的上层接口**。但底层用什么链路跑，有三种选择：

```text
上层（Verbs API）：              ibv_post_send(opcode=IBV_WR_RDMA_READ)
                                      ↓
中层（IB Transport）：            可靠传输协议、分段重组、ACK/NACK/重传
                                      ↓
下层（三种链路选一）：
  ┌──────────────┐  ┌──────────────────┐  ┌──────────────────┐
  │ InfiniBand   │  │ RoCE v2          │  │ iWARP            │
  │ IB 链路 + 网络│  │ UDP/IP + Ethernet│  │ TCP/IP + Ethernet│
  └──────────────┘  └──────────────────┘  └──────────────────┘
```

**IB Transport 层**是核心，它定义了操作的种类（opcode）、可靠传输的逻辑（ACK/NACK、重传、分段重组）。三种协议的区别就在于这层 IB Transport 是跑在什么链路/网络层上。

### 1.2.2 InfiniBand — 祖师爷

IB 是 RDMA 的原生协议，自身有完整的链路层、网络层、传输层。需要**专用 IB 交换机、IB 网卡、IB 线缆**。

**IB 的特性**：

- 链路层带**链路级流控**（Credit-based），天然无损
- 子网管理器 (SM) 统一管理拓扑、路由
- LID (16位 Local ID) 而不是 IP 地址
- 不可跨 IP 路由器（仅限一个 IB 子网内）

**代码中怎么看**：IB 路径中 `dlid`（destination LID）有效而 `dgid` 可以不设置：

```text
// perftest_resources.c:3506-3508 — IB 使用 dlid (Destination LID)
attr.ah_attr.dlid = rem_dest->lid;
```

### 1.2.3 RoCE v2 — 今日王者

**RoCE (RDMA over Converged Ethernet) v2** 把 IB Transport 封装在 UDP/IP 上，让 RDMA 可以跑在标准以太网上。

```text
RoCE v2 的封装：
  Ethernet Header (Ethertype=0x8915)
    └─ IP Header (Protocol=17 UDP)
         └─ UDP Header (dst_port=4791, 这是 IANA 专门分配给 RoCEv2 的端口)
              └─ IB BTH (Base Transport Header)  ← IB 传输层从这里开始
                   └─ Data Payload
```

**RoCE v1 vs v2 的关键区别**：

|  | RoCE v1 | RoCE v2 |
| --- | --- | --- |
| 有无 IP 头 | 没有 — IB Transport 直接放以太网帧 | 有 — 封在 UDP/IP 中 |
| Ethertype | 0x8915 | 0x8915（一样） |
| UDP 端口 | 无 | 4791 |
| 可路由 | 否 — 仅限 L2 广播域 | 是 — 有 IP 头就能路由 |
| 工业界地位 | 已淘汰 | 当前主流 |

**为什么 RoCE v2 胜利**：

1. 不需要 IB 交换机——用已有以太网基础设施
2. IP 可路由——适合云数据中心的三层 Clos 拓扑
3. 生态兼容——和容器网络（Calico/Flannel）、SDN 无缝协作

**代码体现**：perftest 中 `-R` 参数启用 RDMA CM 后，内核 `cma_resolve_iboe_route()` 处理的正是 RoCE 的路径解析——把目标 IP 转成 GID：

```text
// linux-kernel/drivers/infiniband/core/cma.c:3285-3316
static int cma_resolve_iboe_route(struct rdma_id_private *id_priv) {
    // ...
    route->path_rec->packet_life_time_selector = IB_SA_EQ;
    // packet_life_time 的计算直接影响最终的 QP timeout！
    if (id_priv->timeout_set && id_priv->timeout)
        route->path_rec->packet_life_time = id_priv->timeout - 1;
    else
        route->path_rec->packet_life_time = CMA_IBOE_PACKET_LIFETIME; // = 16
}
```

这正是你之前深入分析的 timeout 问题的核心代码。

### 1.2.4 iWARP — TCP 信徒

iWARP 把 IB Transport 层跑在 TCP/IP 上，利用 TCP 的可靠传输来代替 IB 自己的可靠传输机制。

- 优点：TCP 天然处理拥塞控制、可靠传输，不需要 PFC 等复杂配置
- 缺点：TCP 的延迟/CPU 开销 > IB Transport 的硬件卸载，且需要网卡支持 TCP offload
- 现状：相比 RoCE v2，市场份额小很多

### 1.2.5 为什么学习时应聚焦 RoCE v2

1. **市占率最高** — NVIDIA/Mellanox、华为、Intel、Broadcom、阿里云、微软 Azure 都做 RoCE v2
2. **有软件实现** — Soft-RoCE (rxe) 让你在没有硬件的情况下也能学习和调试
3. **代码丰富** — 内核 rxe 驱动是”代码即文档”的最佳例子
4. **以太网生态** — 可以利用所有以太网调试工具（tcpdump/Wireshark）

### 1.3 核心概念速查表

### 1.3.1 对象的创建依赖关系

学习 RDMA 编程的第一个要点：**对象有严格的创建顺序**。你必须按这个顺序来：

```text
ibv_get_device_list()  →  获取设备列表
ibv_open_device()      →  获取设备上下文 (context)
ibv_alloc_pd()         →  分配保护域 (PD)
  ├─ ibv_create_cq()   →  创建完成队列 (CQ)
  ├─ ibv_reg_mr()      →  注册内存区域 (MR) ← 必须在 QP 之前！
  └─ ibv_create_qp()   →  创建队列对 (QP)  ← 同时需要 PD 和 CQ
```

**为什么 MR 必须在 QP 之前？** 因为创建 QP 时不会用到 MR，但**在 post WQE 之前必须有 MR**。WQE 里的 SGE 需要 lkey 来让 HCA 验证本地内存访问权限。

### 1.3.2 逐一详解每个概念

### ibv_context — 设备上下文

```text
// verbs.h 中的定义（简化）
struct ibv_context {
    struct ibv_device      *device;     // 指向底层设备
    struct ibv_device_attr  device_attr; // 设备能力（max_qp, max_cq 等）
    struct verbs_provider_ops ops;      // ★ 函数指针表！
};
```

**类比**：打开一个文件返回 `FILE*`；打开一个 RDMA 设备返回 `ibv_context*`。

**在 perftest 中**：`ctx_open_device()` 做了三件事：

1. 遍历设备链表找到目标设备
2. `ibv_open_device()` 获取 context
3. `ibv_query_device()` 获取设备能力（max_qp、max_cq、max_mr 等）

### PD (Protection Domain) — 保护域

```text
struct ibv_pd {
    struct ibv_context *context;  // 所属设备
    uint32_t           handle;   // 内核中的句柄
};
```

**理解**：PD 是一个**安全隔离边界**。同一个 PD 内的资源（MR、QP、AH）可以互相操作；不同 PD 之间完全隔离。

**代码中怎么用**：

```text
// perftest 中: perftest_resources.c
pd = ibv_alloc_pd(ctx->context);
// 之后创建的 QP、MR 都绑定到这个 PD
qp = ibv_create_qp(pd, &attr);   // QP 在 pd 中
mr = ibv_reg_mr(pd, buf, len, flags); // MR 在 pd 中
```

### MR (Memory Region) — 内存注册

这是 RDMA 区别于 TCP 编程最关键的概念之一。

```text
struct ibv_mr *ibv_reg_mr(struct ibv_pd *pd, void *addr,
                           size_t length, int access_flags);

// 返回:
struct ibv_mr {
    struct ibv_context *context;
    struct ibv_pd      *pd;
    void               *addr;    // 起始虚拟地址
    size_t              length;  // 长度
    uint32_t            lkey;    // ★ 本地访问键
    uint32_t            rkey;    // ★ 远端访问键
};
```

**`ibv_reg_mr()` 做了什么（在内存中）**：

1. 调用 `get_user_pages()` — 把 addr~addr+length 范围内的虚拟页全部 pin 到物理内存
2. 用 IOMMU 为 pin 住的物理页建立设备可访问的映射表
3. 生成 32 位随机数作为 lkey 和 rkey，存入网卡的 key 查找表
4. 返回 lkey 和 rkey 给用户

**什么场景需要 MR？**

- 任何你要发送/接收的数据 buffer（`ibv_post_send/post_recv` 的 SGE 指向的地址）
- 任何你要让远端 RDMA WRITE/READ 访问的内存

**在 perftest 中的代码位置**：`perftest_resources.c:ctx_init()` → 调用 `ibv_reg_mr()` 注册完整的收发缓冲区。

### CQ (Completion Queue) — 完成队列

```text
struct ibv_cq *ibv_create_cq(struct ibv_context *context, int cqe,
                              void *cq_context,
                              struct ibv_comp_channel *channel,
                              int comp_vector);
```

**CQ 的本质**：一个**环形缓冲区**，HCA 把完成事件（CQE）写进去，用户态主动轮询读取。

**和 epoll 的区别**：

- epoll：内核写通知 → 阻塞唤醒用户态
- CQ：硬件（HCA）直接写共享内存 → 用户态 busyloop 轮询

**典型 poll 代码**（perftest 中）：

```text
// perftest_resources.c: run_iter_bw() 中
struct ibv_wc wc;         // Work Completion (= CQE)
int ne = ibv_poll_cq(ctx->send_cq, 1, &wc);
if (ne > 0) {
    // wc.status == IBV_WC_SUCCESS → 操作成功
    // wc.opcode  → 完成了什么操作
    // wc.byte_len → 传输了多少字节
    ctx->ccnt[index]++;  // completion count 递增
}
```

### QP (Queue Pair) — 队列对

```text
struct ibv_qp {
    struct ibv_context     *context;
    struct ibv_pd          *pd;
    struct ibv_cq          *send_cq;   // ★ 发送完成放入哪个 CQ
    struct ibv_cq          *recv_cq;   // ★ 接收完成放入哪个 CQ
    uint32_t                qp_num;    // ★ QP 号（硬件层面的标识）
    enum ibv_qp_state       state;     // RESET/INIT/RTR/RTS/ERR
};
```

**QP 的本质**：通信的端点，包含两个独立的队列：

- **Send Queue (SQ)**：存放发送 WQE（SEND/WRITE/READ/ATOMIC 请求）
- **Receive Queue (RQ)**：存放接收 WQE（等待接收 SEND 数据）

**注意**：

- **只有 SEND 操作才需要 RQ**。WRITE/READ/ATOMIC 不需要远端 RQ。
- **SQ 和 RQ 是完全独立的管道**。发送方写 SQ，接收方必须事先 POST WQE 到自己的 RQ。

### SGE (Scatter-Gather Element) — 内存描述符

```text
struct ibv_sge {
    uint64_t addr;    // 虚拟地址
    uint32_t length;  // 长度
    uint32_t lkey;    // 本地访问键
};
```

**SGE 数组描述一段不连续的内存**。例如一个 WQE 可以用多个 SGE 把不同位置的数据”拼”在一起发送：

```text
struct ibv_sge sge[2] = {
    { .addr = header_buf, .length = 64, .lkey = mr->lkey },   // 先发头部
    { .addr = payload_buf, .length = 4096, .lkey = mr->lkey }, // 再发正文
};
// 一次 SEND 操作就把 header + payload 一起发出去了
```

### WR / WQE / CQE — 请求的生命周期

```text
WR (Work Request)                 →  用户态填写的结构体
    ↓ ibv_post_send/post_recv()
WQE (Work Queue Element)          →  硬件格式的请求，入 SQ/RQ
    ↓ HCA 处理
CQE (Completion Queue Element)    →  完成通知，入 CQ
    ↓ ibv_poll_cq()
用户读取完成结果
```

### 1.3.3 操作类型对比表（含 `has_recv_comp` 判断）

这来自 perftest 源码 [perftest_parameters.h:994](file:///D:/desktop/RDMA/perftest/src/perftest_parameters.h#L994)：

```text
static inline bool has_recv_comp(VerbType verb) {
    return verb == SEND || verb == SEND_IMM || verb == WRITE_IMM;
}
```

| 操作 | 双边/单边 | 远端需否预 POST RECV | has_recv_comp() | 远端 CPU 参与 |
| --- | --- | --- | --- | --- |
| SEND | 双边 | 必须 POST RECV，否则 RNR NAK | true | ✓ |
| SEND_WITH_IMM | 双边 | 必须 | true | ✓ |
| RDMA WRITE | 单边 | 不需要 | false | ✗ |
| WRITE_WITH_IMM | 单边 | 不需要 WQE，但产生 CQE | true | ✗(仅通知) |
| RDMA READ | 单边 | 不需要 | false | ✗ |
| ATOMIC_CMP_SWAP | 单边 | 不需要 | false | ✗ |
| ATOMIC_FETCH_ADD | 单边 | 不需要 | false | ✗ |

**关键结论**：

- `has_recv_comp() == true` → perftest Server 端必须执行 `run_iter_bw_server()`（poll Recv CQ）
- `has_recv_comp() == false` → Server 端不需要处理完成事件，RDMA READ/WRITE 对远端 CPU 完全透明

### 1.4 RoCE v2 协议栈逐层解析

### 1.4.1 完整报文结构

这是学习 RDMA 底层时必须背下来的结构。以后读 rxe 源码时，你会反复看到这些字节偏移量的代码。

```text
字节偏移    字段                      大小   说明
══════════════════════════════════════════════════════════════════
0x00   Eth Dst MAC                 6B    以太网目标 MAC
0x06   Eth Src MAC                 6B    以太网源 MAC
0x0C   VLAN Tag (可选)             4B    TPID=0x8100, PCP=优先级
0x10   Ethertype                   2B    ★ 0x8915 = RoCE

───── IP 头部 (IPv4) ─────
0x12   Version/IHL/DCSP-ECN       2B    ECN=拥塞标记(用于 DCQCN)
0x14   Total Length               2B
0x16   Identification             2B
0x18   Flags/Fragment Offset      2B    DF=1 (禁止分片！)
0x1A   TTL                        1B
0x1B   Protocol                   1B    ★ 17 = UDP
0x1C   Header Checksum            2B
0x1E   Src IP                     4B
0x22   Dst IP                     4B

───── UDP 头部 ─────
0x26   Src Port                   2B    任意值

0x2A   UDP Length                 2B

0x36   ACK Req | PSN              4B    Bit31=请求ACK, Bit0-23=包序列号

───── 可变扩展头部 (取决于 Opcode) ─────
0x3A   [RETH] 仅 READ/WRITE/ATOMIC 请求:
        VA (Virtual Address)       8B    ★ 远端目标地址
        R_Key (Remote Key)         4B    ★ 远端内存访问键

        Immediate Data             4B    32位立即数

        Swap/Compare/Add 值        8B

───── Payload / ICRC / FCS ─────

```

**为什么有些字段标了 ★？** 因为以后你在 rxe 源码中会反复看到它们被代码引用的痕迹：

```text
// rxe 源码中构造 BTH 的典型代码（伪代码）
bth->opcode = IB_OPCODE_RDMA_WRITE_ONLY;
bth->psn    = htonl(qp->req.psn);
bth->dest_qp = htonl(remote_qpn & 0xFFFFFF);
```

### 1.4.2 Opcode 详解

IB BTH Opcode 是 1 字节字段，前 5 位是操作码，后 3 位是子类型。关键 opcode：

| 值 | 名称 | perftest 中对应的 WR | 说明 |
| --- | --- | --- | --- |
| 0x00 | RC_SEND_FIRST | — | 分段 SEND 的首包（> MTU） |
| 0x01 | RC_SEND_MIDDLE | — | 分段 SEND 的中间包 |
| 0x02 | RC_SEND_LAST | — | 分段 SEND 的末包 |
| 0x03 | RC_SEND_LAST_WITH_IMM | — | 末包 + 立即数 |
| 0x04 | RC_SEND_ONLY | IBV_WR_SEND | 非分段 SEND |
| 0x05 | RC_SEND_ONLY_WITH_IMM | IBV_WR_SEND_WITH_IMM | SEND + 立即数 |
| 0x06 | RDMA_READ_REQUEST | IBV_WR_RDMA_READ | READ 请求 |
| 0x07-09 | RDMA_READRESPONSE* | — | READ 响应（由 HCA 自动生成） |
| 0x0A | RDMA_WRITE_FIRST | — | 分段 WRITE 首包 |
| 0x0B | RDMA_WRITE_ONLY | IBV_WR_RDMA_WRITE | 非分段 WRITE |
| 0x0C | RDMA_WRITE_ONLY_WITH_IMM | IBV_WR_RDMA_WRITE_WITH_IMM | WRITE + 立即数 |
| 0x10 | ACKNOWLEDGE | — | 传输层 ACK（确认包，无 payload） |

**perftest 中的 opcode 映射** — 这是连接应用层操作和协议层的关键代码：

```text
// perftest_resources.c:40-46
static enum ibv_wr_opcode opcode_verbs_array[] = {
    IBV_WR_SEND,                // SEND → 0x04 (RC_SEND_ONLY)
    IBV_WR_SEND_WITH_IMM,       // SEND_IMM → 0x05
    IBV_WR_RDMA_WRITE,          // WRITE → 0x0B (RDMA_WRITE_ONLY)
    IBV_WR_RDMA_WRITE_WITH_IMM, // WRITE_IMM → 0x0C
    IBV_WR_RDMA_READ            // READ → 0x06 (RDMA_READ_REQUEST)
};
// 索引 = user_param.verb 的枚举值 (SEND=0, SEND_IMM=1, WRITE=2, WRITE_IMM=3, READ=4)
```

**最容易被忽略的关键区别**：

```text
SEND(0x04)：接收方的 HCA 必须找到预 POST 的 RECV WQE 来放数据。
           没有 → RNR NAK → 对方收到 RNR NAK → retry → 延迟暴涨。

WRITE(0x0B)：接收方 HCA 直接写目标内存，不需要 RECV WQE。
             对方的 CPU 根本不感知这件事！

READ(0x06)：请求方发出极小报文（BTH+RETH≈28B），
            对方 HCA 从内存读数据 → 回复 READ_RESPONSE(0x07-09) 带数据。
```

### 1.4.3 GID — RoCE 的地址标识

**GID = Global Identifier**，128 位，格式类似 IPv6。

```text
RoCEv2 的默认 GID 格式：
  fe80:0000:0000:0000:<EUI-64 从 MAC 转换>
  └──── IPv6 Link-Local 前缀 ────┘└── 接口 MAC 的 EUI-64 转换 ──┘
```

**一个物理端口可以有多个 GID**：

- 每个 VLAN 接口一个 GID
- 每个 IP 地址一个 GID
- IPv4 地址会被映射成 IPv6-mapped GID 格式：`::ffff:<IPv4>`

**代码中如何获取 GID**：

```text
// perftest_resources.c 中获取本地 GID
ibv_query_gid(ctx->context, ib_port, gid_index, &my_dest->gid);
```

**内核 GID 管理**：`roce_gid_mgmt.c` — 当网卡的 IP 地址变化或 VLAN 增删时，这个文件负责增删对应的 GID 条目。
