## 前言

近期我们在分析&量化Megatron 3D并行训练中的通信开销。我们观测到一个有趣的现象——在使用1F1B流水线并行时，我们观测到每次p2p通信所花费的时间并不是完全相同或相近的，而是在不同的阶段呈现出不同的规律，例如，在1F1B的稳态阶段，p2p通信的时间呈现了一种“一短一长”的规律，这是我们使用8台A100服务器（每台服务器8张A100，网卡为RDMA 4 * 200Gb/s）训练LLaMA 2 70B的Profile Timeline：

![](https://pic1.zhimg.com/v2-4f7bdf3b9e6a15edecc870cb62fc3192_r.jpg)
*图1*

除了第一个流水线Stage和最后一个流水线Stage，这种规律性的p2p通信存在于所有的中间的流水线Stage当中。接下来，我们就来分析一下，为什么会出现这种现象。

## 原因分析

为了简化问题的分析，我们选择使用一台A100服务器训练LLaMA 7B，我们设置PP=8，完全使用流水线并行的方式进行训练，避免TP，DP并行的额外通信干扰我们分析的过程。我们对训练过程进行Profile，并抽取中间的流水线Stage进行观察，可以观察到，在这种配置下，“一短一长”的规律性更加明显：

![](https://pic4.zhimg.com/v2-44449a98f150ecbb3cd4ace29ef81771_r.jpg)
*图2*

首先，基于1F1B流水线并行的原理，我们可以确定的是，每次p2p通信的通信量是相同的，由于我们现在是在单机内部做p2p通信，通信使用的是高带宽的NVLink，其通信带宽通常不会存在性能上的抖动。因此，我们可以排除通信量和网络性能抖动的影响。

那么，基于以往的经验，通信时间的差异可能是由于相互通信的两个Rank不同步所导致的——这个所谓的不同步，是指一个Rank率先执行到通信操作，而另外一个Rank还未执行到通信操作，因此，前一个Rank必须等待后一个Rank执行到通信操作，才能真正的发起通信。在分析Timeline的过程中，我们发现，在第一个Stage（Stage 0）和最后一个Stage（Stage 7）中，不存在这种现象：

![](https://pic2.zhimg.com/v2-78d7801db7783b97df238401acd12b77_r.jpg)
*图3: Stage 0*

![](https://pica.zhimg.com/v2-ec096477e80a886b492b8b19c181ee08_r.jpg)
*图4: Stage 7*

从图3和图4中我们观察到，Stage 0中存在的都是长时间的p2p通信，而Stage 7当中存在的都是短时间的p2p通信，那么基本可以确定，**Stage 7——也就是最后一个流水线Stage，可能是通信不同步问题中，比较慢的那一个Rank。**

由于我们将并行策略设置为完全的流水线并行，没有TP和DP的干扰，因此，导致各个流水线Stage不同步的原因也只剩下了一个，那就是计算的速度不一致。

我们对比了Stage 7的计算一个mini batch的时间与其他中间Stage计算一个mini batch的时间：

|  | Forward Compute Time | Backward Compute Time |
| --- | --- | --- |
| Stage 7 | 约40ms | 约80ms |
| Stage intermediate | 约35ms | 约70ms |

可以观察到，Stage 7确实额外多花费了一些时间，其原因也很明显，作为最后一个Stage，除了计算对应的Transformer Layer外，还需要计算logits和交叉熵Loss，额外的计算过程中包含了一个尺寸较大的矩阵乘法，用于将hidden states映射为词表大小（32k），因此最后一个Stage的计算时间较长。

![](https://picx.zhimg.com/v2-9d2f76ab1e45a99409655866c894d8a3_r.jpg)
*图5: 最后一个流水线Stage的额外计算带来的延迟*

Stage 7每执行完一组1F1B后，发起一次通信，由于Stage 7每次执行1F1B都需要额外消耗大约15ms左右的时间，那么，Stage 6也必须额外等待这15ms，而且这种等待也会引起连锁反应，进一步影响到前面的Stage。从Timeline上我们也可以确认，这些长时间的p2p通信基本都在15ms以上：

![](https://picx.zhimg.com/v2-6af1a786fda29100c55ac18ec8dc7865_r.jpg)
*图6: Duration 15ms+*

## 流程梳理

现在我们已经知道，最后一个Stage的额外计算会导致额外的通信延迟，那么现在，我们结合Megatron的代码（Megatron Core v0.4.0），对整个流水线并行的执行过程进行梳理，彻底弄清为什么会有“一短一长”的现象。我们以图7为例，展开流水线并行各个阶段，并结合代码描述每个阶段所执行的操作。

![](https://pic3.zhimg.com/v2-9f9183cfe3b6bc507d7d5c0516cb1bf0_r.jpg)
*图7: 计算负载不均衡的1F1B流水线的执行过程*

流水线并行分为3个阶段——warmup, 1F1B, cooldown

### warmup

warmup阶段仅执行前向传播，执行的mini batch数量为PP_size - PP_rank - 1，例如，在上图中Stage 2的warmup mini batch的数量为4 - 2 - 1 = 1。从代码层面，warmup执行3个步骤：

1. recv_forward——从前一个Stage收Fwd的激活值（Stage 0不需要），用黄色表示。
2. forward_step
3. send_forward——将上一步Fwd的结果发送给下一个Stage（Stage Last不需要，一般Stage Last不存在warmup阶段，而是直接进入1F1B阶段），用蓝色表示。

```python3
    # Run warmup forward passes.
    for i in range(num_warmup_microbatches):
        # ...
        input_tensor = recv_forward(recv_tensor_shapes, config)
        output_tensor = forward_step(
            forward_step_func,
            data_iterator,
            model,
            num_microbatches,
            input_tensor,
            forward_data_store,
            config,
            collect_non_loss_data,
            checkpoint_activations_microbatch,
        )
        send_forward(output_tensor, send_tensor_shapes, config)
```

### 1F1B

进入1F1B稳态阶段后，代码循环执行4个步骤：

1. forward_step
2. send_forward_recv_backward——先将上一步Fwd的结果发送给下一个Stage，再从下一个Stage接收Bwd的梯度，两个动作以一个batched kernel的形式执行（最后一个Stage不需要执行这个操作，因为上一步Fwd的结果会直接用于下一步的Bwd，Bypass当前步骤），这部分通信以绿色表示。
3. backward_step
4. send_backward_recv_forward——先将上一步Bwd的结果发送给前一个Stage，再从前一个Stage接收Fwd的激活，两个动作以一个batched kernel的形式执行，（第一个Stage不需要执行这个操作），这部分通信以红色表示。

```text
    # Before running 1F1B, need to receive first forward tensor.
    # If all microbatches are run in warmup / cooldown phase, then no need to
    # receive this tensor here.
    if num_microbatches_remaining > 0:
        input_tensor = recv_forward(recv_tensor_shapes, config)
    
    # Run 1F1B in steady state.
    for i in range(num_microbatches_remaining):
        # ...
        output_tensor = forward_step(
            forward_step_func,
            data_iterator,
            model,
            num_microbatches,
            input_tensor,
            forward_data_store,
            config,
            collect_non_loss_data,
            checkpoint_activations_microbatch,
        )

        # ...
            output_tensor_grad = send_forward_recv_backward(
                output_tensor, send_tensor_shapes, config
            )

            # ...
            input_tensor_grad = backward_step(
                input_tensor, output_tensor, output_tensor_grad, model_type, config
            )
            # ...
                input_tensor = send_backward_recv_forward(
                    input_tensor_grad, recv_tensor_shapes, config
                )

```

### cooldown

cooldown阶段仅执行Backward，执行的mini batch数量与warmup阶段正好相对应。代码循环执行3个步骤：

1. recv_backward——从下一个Stage接收Bwd的梯度，用紫色表示。
2. backward_step
3. send_backward——上一步计算出的梯度发送给前一个Stage（第一个Stage不需要这个操作），用黑色表示。

```text
    # Run cooldown backward passes.
    if not forward_only:
        for i in range(num_warmup_microbatches):
            # ...
            input_tensor = input_tensors.pop(0)
            output_tensor = output_tensors.pop(0)

            output_tensor_grad = recv_backward(send_tensor_shapes, config)

            input_tensor_grad = backward_step(
                input_tensor, output_tensor, output_tensor_grad, model_type, config
            )

            send_backward(input_tensor_grad, recv_tensor_shapes, config)
```

### “一短一长”的原因分析

从前面的分析我们可以看到，中间的流水线Stage中，所谓的“一短”其实是1F1B稳态阶段的send_backward_recv_forward，**由于这个通信是与前一个流水线Stage进行同步，而前一个流水线Stage并没有额外的计算，因此不会有通信延迟的问题。**

而“一长”，则是指1F1B稳态阶段的send_forward_recv_backward，**这个通信是与后一个流水线Stage进行同步，那么Stage 6一定会受到Stage 7额外计算的影响，并在后续的执行过程中进一步将额外的延迟传递给Stage 5，以此类推，影响整个流水线的运行。**

除此之外，除了最后一个Stage，第一个Stage也包含了额外的计算操作，比如Embedding层的index_select，RoPE计算等，我们可以在图7中观察到这个额外开销，不过，由于这些额外的计算并不包含大规模的矩阵乘法运算，因此其额外花费的时间较少，略微的弱化了最后一个Stage导致的额外通信延迟在第一个Stage上的表现。

## 总结

本篇文章介绍了1F1B流水线并行中，计算负载不均衡是如何引发额外的通信延迟的。在Interleaved流水线并行中，虽然p2p通信可以Overlapping，但是计算负载不均衡仍然会引发一些额外的通信延迟，这里我们先留个坑，后续有机会继续介绍Interleaved流水线中存在的此类性能问题。
