## 1. 检索源

目前，ReadLess的RAG资料来源有4类：

1. 用户指定的本地文件夹；
2. 网站上的“精选解读”内容（如图2所示的中英对照博客）；
3. 网站上的“原创博客”内容（如图3所示）；
4. 网站上的“知识｜论文”内容（如图4所示）。

入库格式为 Markdown（`.md`）、UTF-8 文本（`.txt`）、文字型 PDF（`.pdf`）。

*图3 社区原创博客*

![](https://pic4.zhimg.com/v2-847a773081c247b9e3804f408fbf40b3_r.jpg)
*图4 知识库及中英对照论文*

PDF 按页提取文本；扫描件和图片不做 OCR。正文中的 Base64 图片编码会排除，避免把图片编码当成文字计算向量。

中文文本按每块**最多 1800 个字符、相邻最多重叠 200 个字符**切分；英文文本则先用无需训练模型的 spaCy Sentencizer 识别句子边界，再按每片**最多 300 词、重叠最多 30 词切分**。

注意这里是按字符/词来计算，不是 token 数。之所这样做，是因为切分阶段的目标只是把长文本切成大小可控、边界尽量合理的片段，只需要知道长度和边界；字符数与具体 tokenizer 无关，稳定、可复现、跨模型通用，不会因为嵌入模型更换而改变切分结果、导致索引重建。此时也没必要分词——后续生成 embedding 时，会由 nomic-embed-text 自带的 tokenizer 一并完成子词切分并输出 768 维向量。

另外，相比固定长度硬切，英文侧用 Sentencizer 先分句再组块，能让片段边界尽量落在句子边界上，避免把句子、从句或语义单元从中间切断，片段更自包含，检索和生成时上下文也更完整。中文侧也以字符数为上限，优先在段落和标点边界处切分。

重叠（overlap）则用于尽量保留跨分块边界的上下文，也是防止语义被切断，并降低因切分位置不佳导致的漏召回。

切分后得到的每个片段还要保存文件路径、内容版本哈希、原文位置和正文。博客还保留文章 ID、修订号、发布状态及原文件来源，详见下文的数据库表结构。这么做本质上是给每个片段建立**可追溯、可校验、可过滤、可重建**的元数据体系。毕竟RAG 不只是“切块+向量化”，还要回答：这个片段从哪来、是不是最新、能不能用、出问题怎么回溯，这也能显著提升开发过程中的问题排查能力。

## 2. 数据存储

随后，通过本机 Ollama 的 `nomic-embed-text` 将“文件名＋片段正文”转成 **768 维向量**，存入私有 SQLite 索引。带上“文件名”目的是**给片段补一层正文里可能没有的上下文和来源语义**，让检索更容易命中。

针对用户自定义的本地检索源，当前采用按需手动刷新的形式，没有文件变化自动监听，刷新时程序会重新扫描指定文件夹及其子文件夹，按以下方式处理：

| 文件变化 | 索引处理 |
| --- | --- |
| 新增文件 | 提取文本 → 切块 → 计算向量 → 写入索引 |
| 修改文件 | 根据内容哈希识别变化，重新处理该文件并替换旧索引 |
| 没有变化 | 跳过，复用已有向量 |
| 删除文件 | 完整扫描时清理对应索引 |

当前代码是 SQLite Schema v3：**4 张普通业务表＋1 张 FTS5 虚表，另有 4 张由 FTS5 自动管理的内部表**。

> FTS5 的全称是 **Full-Text Search version 5**，即 SQLite 的**全文搜索扩展模块第 5 版**。它是 SQLite 内置的虚拟表模块，用来在 SQLite 里做全文检索（关键词匹配、BM25 排序等）。“虚拟”指的是**逻辑上表现为表，物理实现由扩展模块接管**，不是真的有一张按行存储的普通表。创建方式就是：<br> CREATE VIRTUAL TABLE chunks_fts USING fts5(content);

**1．`files`：每个文件一条记录**

负责记录文件来源、版本和索引状态。

| 字段 | 含义 |
| --- | --- |
| path | 主键，文件在资料目录中的相对路径 |
| revision | 文件内容 SHA-256，用于判断是否修改 |
| size_bytes、`mtime_ns` | 文件大小、修改时间 |
| status、`error` | 索引状态与失败原因；状态为处理中、成功或失败 |
| title、`source_type` | 标题和来源类型 |
| article_id、`article_revision` | 网站文章 ID 和修订号，可为空 |
| published | 是否发布；未知时为空 |
| provenance_json | 原始来源信息，如网址、原文件路径 |
| index_signature | 切分、向量模型等索引规则标识 |
| indexed_at、`updated_at` | 成功索引／复查时间、状态更新时间 |

`revision` 是文件哈希，`article_revision` 是文章修订号，两者用途不同。

**2．`chunks`：每个文本片段一条记录**

负责保存可引用的正文，以及检索所需的分词文本。

| 字段 | 含义 |
| --- | --- |
| rowid | 整数主键，供全文索引关联 |
| id | 唯一片段 ID，保留原有引用标识 |
| path | 外键，指向 files.path |
| chunk_index | 片段在文件中的序号 |
| text、`content_hash` | 原文片段及其 SHA-256 |
| location | 兼容原有引用接口的位置字符串 |
| start_char、`end_char` | 原文字符起止位置 |
| page_no、`line_no` | PDF 页码或文本行号 |
| embedding_id | 外键，指向对应向量 |
| search_path | 路径的分词结果 |
| search_title | 标题的分词结果 |
| search_text | 正文的分词结果 |

**引用使用 `text`，BM25 使用三个 `search_*` 字段。** 分词不会改写原文。

**3．`embedding_cache`：保存向量并支持复用**

虽然叫缓存表，它也是当前向量的实际存储表，没有再复制到另一张向量表。

| 字段 | 含义 |
| --- | --- |
| id | 向量记录主键 |
| input_hash | 实际送入向量模型的文本哈希 |
| model | 模型名称，目前是 nomic-embed-text |
| input_version | 输入构造规则版本，不是模型权重版本 |
| dimensions | 向量维度，目前为 768 |
| vector | float32 二进制向量，768 维占 3072 字节 |
| created_at | 创建时间 |

文件修改后，**实际输入未变的片段可以复用向量**；输入包含文件路径，因此移动文件可能需要重新计算。

**4．`chunks_fts`：BM25 全文索引**

这是 FTS5 虚表，通过 `rowid` 关联 `chunks`，分别索引：

| 字段 | 当前 BM25 权重 |
| --- | --- |
| search_path | 0.25 |
| search_title | 3.0 |
| search_text | 1.0 |

片段增删改时，数据库触发器同步更新全文索引。它引用 `chunks` 中的分词文本，不另外维护一份原文正文。

**5．`metadata`：整个索引的管理信息**

只有 `key`、`value` 两列，主要保存：

- `schema_version`：数据库结构版本，目前为 3。
- `tokenizer_version`：分词规则版本。
- `text_index_version`：文本索引处理版本。
- `progress`：当前处理进度。
- `report`：处理结果、向量复用数量和失败原因。

**FTS5 自动生成的 4 张内部表**

| 表名 | 作用 |
| --- | --- |
| chunks_fts_data | 保存倒排索引数据及部分整体统计 |
| chunks_fts_idx | 帮助定位倒排索引中的数据 |
| chunks_fts_docsize | 保存每个片段各字段的词项数量，供长度归一化使用 |
| chunks_fts_config | 保存 FTS5 配置 |

词频、命中文档数等信息由这些内部结构支持，**IDF 在评分时根据统计计算，没有单独的 IDF 表**。这里的“文档”指一个片段。

整体关系是：

```text
files：文件
  └─ chunks：多个正文片段
       ├─ embedding_cache：关联向量 → 语义检索
       └─ chunks_fts：关联全文索引 → BM25 检索

metadata：管理整个索引的版本、进度和报告
```

当然，SQLite 作为本地嵌入式数据库无法支撑多用户线上 RAG 服务，它在写并发、服务化部署、向量检索和运维能力上都有明显局限，因此要升级为 PostgreSQL + pgvector。

> 其中，PostgreSQL 负责结构化元数据存储、事务与 MVCC 行级锁带来的并发控制、多租户隔离与权限、业务过滤查询，以及备份、复制、监控等运维能力。项目研究后台已经使用 PostgreSQL，可以沿用这套基础设施。<br>pgvector 负责提供 `vector(768)` 向量类型、余弦/内积/L2 距离操作符和 HNSW/IVF 等 ANN 索引，让向量相似度检索可以下推到数据库内，并与元数据过滤在同一条 SQL、同一事务中完成，避免向量库与元数据库不一致；后续数据规模或检索需求进一步增长时，还可以引入独立向量数据库。

## 3. 召回检索

检索时系统收到问题后，先整理已有对话、理解用户意图，再由独立的 Query Rewrite 步骤产生如下结构化字段：

| 字段 | 用途 |
| --- | --- |
| standalone_query | 将“它”、“上面那个”等指代补全，得到可独立理解的问题 |
| local_query | 用于查询本地笔记与博客 |
| search_terms | 用于公开网络搜索 |
| scope | 决定仅本地、仅网络，还是混合检索 |

例如，用户问“我的笔记里怎么解释 Prefix Caching？”，RAG会倾向于本地检索；反之，明确要求只查互联网时，则跳过本地检索。如果两者都查，命中私有资料后，公开搜索只能使用此前生成的查询词，避免把笔记内容继续扩写进搜索请求。

下面介绍具体的双路召回：**BM25＋向量检索**和RRF 融合流程。

系统首先将 `local_query` 与原始问题拼接，计算查询向量，各资料库复用同一个查询向量。每个库分别执行两路召回：

- **向量检索**：计算余弦相似度，以寻找语义相关的片段。
- **BM25 检索**：根据**词频**、**逆文档频率**和**片段长度**进行关键词排序。中文采用 jieba 搜索模式分词；全文索引分别记录路径、标题和正文。

> BM25 计算公式：<br> $$ -\sum_{t\in q} \operatorname{IDF}(t) \cdot \frac{f_w(t,d)(k_1+1)} {f_w(t,d)+k_1\left(1-b+b\frac{|d|}{\operatorname{avgdl}}\right)} $$

两路结果通过 **RRF（**Reciprocal Rank Fusion，**倒数排名融合）** 合并。它使用排名，不直接相加 BM25 原始分数与向量相似度（60只是一个超参）： $$ \frac{1}{60+r_{\mathrm{BM25}}(d)} + \frac{1}{60+r_{\mathrm{vector}}(d)} $$

$r_{\mathrm{BM25}}(d)$ 和 $r_{\mathrm{vector}}(d)$ 分别是片段在两路结果中的名次，从 1 开始。某一路未召回该片段，该路贡献为零。两路都排名靠前的片段通常更优先。**RRF 分数越大，融合排名越靠前。**

**具体筛选流程**

1. **有效性检查**：排除过期、索引未完成或无权读取的资料。
2. **两路召回**：各库分别进行向量检索和 BM25 检索，每路最多保留 **50 个候选**。向量相似度需满足：

$$ \operatorname{sim}(q,d) =\frac{\mathbf{v}_q\cdot\mathbf{v}_d} {\|\mathbf{v}_q\|\,\|\mathbf{v}_d\|} \geq 0.3 $$

其中，$\mathbf{v}_q$ 和 $\mathbf{v}_d$ 分别为查询与片段的向量。BM25 候选还需满足查询词覆盖率：

$$ \frac{|Q\cap T_d|}{|Q|}\geq 0.5 $$

其中，$Q$ 是有效查询词集合，$T_d$ 是片段路径、标题和正文中的词项集合。

3. **融合排序**：各库通过 RRF 融合两路结果，返回最多 **50 个片段**；跨库汇总、去重后再次融合，最终保留最多 **8 个片段**。

4. **来源合并**：同一资料库、同一文件、同一版本的片段合并为一份来源，因此最终来源数量可能少于 8 份。

当前向量检索仍采用 SQLite 中向量的精确扫描，没有使用近似最近邻索引，也没有接入独立的模型重排器。上述候选数量和相关性阈值是当前默认配置，仍需结合真实查询评估效果。

## 4. 后续流程

1. **冻结证据：保存“这次回答实际看到了什么”**

检索结果不会只作为临时提示词使用。系统会把选中的片段正文保存为本次研究的不可变来源快照，并记录：

- 来源 ID；
- 文件版本与原文位置；
- 组成这份来源的片段 ID；
- 博客的文章 ID、修订号等信息。

这样，即使后来修改了笔记，历史回答仍能追溯到当时使用的内容。

需要注意，**本地来源快照通常只包含命中的片段，并不代表模型读完了整份文件。** 笔记和草稿也只作为材料，不自动成为已核实事实。

**2. 补充网页、阅读材料，判断证据是否够用**

接下来根据搜索范围分流：

- **仅本地**：关闭网页搜索和抓取，直接使用本地来源。
- **仅网络**：搜索网页候选，由模型选源，再抓取正文。
- **混合检索**：将本地片段与抓取的网页正文合并进入研究流程。

网络路径不是预先把整个互联网建成向量库，而是按本次问题即时搜索和阅读。搜索摘要用于挑选来源，最终证据来自抓取保存的正文。

阅读阶段会整理来源笔记、选出支持问题的原文段落，并记录尚未解决的问题。系统再判断资料能否解释用户关心的内容；不足时，在预算内继续阅读或补查。

**3. 生成回答、关联引用、核验和修订**

写作模型收到的是问题、读者目标、来源信息以及筛选出的证据段落。回答通过段落 ID 关联证据，再进入整篇核验；有实质问题时进行编辑和复核。

这里有两个不同层次的检查：

- **程序检查**：引用 ID、原文位置与快照内容是否对应。
- **模型核验**：证据是否支持回答，解释是否充分，有没有遗漏或过度推断。

引用位置正确，并不自动代表结论正确。未通过核验时，当前产品会保留可用正文，并明确显示“没有通过检验”。

另外，若本地命中得分达到 `0.8`，且启用先行初稿功能，系统会用前两份本地来源并行生成一份**未验证初稿**，让用户先看到内容；主研究和核验仍继续。

整个流程可以概括为：

```text
提前：资料 → 文本提取 → 切块 → 本机向量化 → 私有索引

提问 → 对话整理与问题理解 → 查询改写
     → 本地召回 → 冻结片段 → 记忆召回
     → 按范围补充网页 → 阅读并提取证据
     → 判断缺口、必要时补查
     → 写作 → 核验与修订 → 带引用回答
```
