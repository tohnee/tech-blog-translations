```text

def launch_server(
    server_args: ServerArgs,
    pipe_finish_writer: Optional[mp.connection.Connection] = None,
):
    """
    Launch SRT (SGLang Runtime) Server

    The SRT server consists of an HTTP server and the SRT engine.

    1. HTTP server: A FastAPI server that routes requests to the engine.
    2. SRT engine:
        1. Tokenizer Manager: Tokenizes the requests and sends them to the scheduler.
        2. Scheduler (subprocess): Receives requests from the Tokenizer Manager, schedules batches, forwards them, and sends the output tokens to the Detokenizer Manager.
        3. Detokenizer Manager (subprocess): Detokenizes the output tokens and sends the result back to the Tokenizer Manager.

    Note:
    1. The HTTP server and Tokenizer Manager both run in the main process.
    2. Inter-process communication is done through ICP (each process uses a different port) via the ZMQ library.
    """
```

def step(self) -> List[Union[RequestOutput, EmbeddingRequestOutput]]:
 """Performs one decoding iteration and returns newly generated results.

 .. figure:: https://i.imgur.com/sv2HssD.png
 :alt: Overview of the step function
 :align: center

 Overview of the step function.

 Details:
 - Step 1: Schedules the sequences to be executed in the next
 iteration and the token blocks to be swapped in/out/copy.

 - Depending on the scheduling policy,
 sequences may be `preempted/reordered`.
 - A Sequence Group (SG) refer to a group of sequences
 that are generated from the same prompt.

 - Step 2: Calls the distributed executor to execute the model.
 - Step 3: Processes the model output. This mainly includes:

 - Decodes the relevant outputs.

```text
    @torch.inference_mode()
    def event_loop_normal(self):
        """A normal blocking scheduler loop."""
        self.last_batch = None

        while True:
            recv_reqs = self.recv_requests()
            self.process_input_requests(recv_reqs)

            batch = self.get_next_batch_to_run()
            self.cur_batch = batch

            if batch:
                result = self.run_batch(batch)
                self.process_batch_result(batch, result)

                # Decode multiple steps to reduce the overhead
                if batch.forward_mode.is_decode():
                    for _ in range(self.server_args.num_continuous_decode_steps - 1):
                        if not self.running_batch:
                            break
                        self.update_running_batch()
                        if not self.running_batch:
                            break
                        result = self.run_batch(batch)
                        self.process_batch_result(batch, result)
            else:
                self.check_memory()
                self.new_token_ratio = self.init_new_token_ratio

            self.last_batch = batch
```

vllm是分成了三步，预处理，模型执行，后处理，sglang这里基本一致。<br><br>**第一步，预处理**<br>获取用户request。<br>然后根据现在的显存，current batch，排队的情况，基于各种规则，返回接下来要执行的batch<br>核心代码get_next_batch_to_run()<br> <br>**第二步，模型执行（跑batch）**<br>run_batch()<br> <br>**第三步，结果处理**<br>核心代码process_batch_result()<br><br>跟上一篇文章一样，重点基于第一步和第二步展开。

### <br>**2.1 核心类**

<br>**2.1.1 ScheduleBatch**<br>**代码路径**<br>sglang/srt/managers/schedule_batch.py<br>**作用**<br> 关于batch的相关操作，都在这里做，合并batch，移除已经计算完的batch，等。<br><br>**2.1.2 SchedulePolicy**<br>**代码路径**<br>sglang/srt/managers/schedule_policy.py<br>**作用**<br> 现在有一堆请求排队，优先处理哪个？用什么策略来计算？<br> 提供了几种调度策略，业务上如果觉得无法满足，你自己也可以加一个。<br> <br> <br>**附加题——为什么叫做 extend rather than prefill？**<br>sglang的代码里面，prefill在逐渐被extend替换。<br>why，为什么叫做 extend rather than prefill？<br><br>这里参看晨阳的这篇文章<br><u>[https://zhuanlan.zhihu.com/p/718715866](https://zhuanlan.zhihu.com/p/718715866)</u><br>我觉得定义非常清晰了<br>chunked prefill的特性，决定了它在chunked的时候，捎带一点decode请求，反而能更大化的利用利用率。<br><br>所以，这里定义为extend，我理解更多是指prefill捎带少量decode的情况

### <br>**2.2 流程**

<br>开头定义了runing_batch和last_batch，分别都为空<br> <br>Runing_batch是指当前运行的batch数据，last_batch是一个临时数据（暂时理解，不一定全对<br> <br>后期晨阳会画一个专门的详细流程图出来，大家可以期待下<br> <br>**Step 1 merge the prefill batch into the running batch**<br>如果不是decode阶段，上一轮prefill没执行完，那么就要做个合并，合并到runing_batch（这个有点像batch的全局变量）<br> <br>**Step 2 prefill first**<br>如果这个时候batch size打满，或者waiting_queue为空（也就是没有新请求进来）<br>那么就不填充新的prefill了<br> <br>否则就要从waiting list获取prefill数据，如何获取就是根据之前的policy类定义的策略来获取。<br>跟现有的runing_batch做合并，这个就是接下来要执行的batch。<br> <br>**Step 3 执行decode**<br>正如上面说的，发现batch size打满了，或者waiting_queue为空。<br>则需要执行decode的流程。<br>这里也一堆细节，例如update_running_batch()，要查询当前内存状态，batch的filter等操作，但问cursor能问清楚，这里就不展开了。

## <br>**5 OpenRLHF的训练加速**

### <br>**5.1 背景**

<br>PPO现在基本上是各个大厂的主流配置了，它的上限对比DPO高太多了。<br>但PPO对比SFT训练的过程中，不仅仅next token来决定loss，多个模型的产出都决定了最后的loss。<br>推理成本一下子就乘以N，如果是O1，这个就更不好说。。。<br><br>我这两篇文章也说的蛮清楚了，推理引擎的一堆细节决定了最后的效果，这个事情术业有专攻。<br>自然而然的，推理过程中使用SGLang，vllm这些推理引擎来加速是一个不错的选择。<br><br>下面是最近OpenRLHF和SGLang开会后讨论的todo list，大家训练的时候有碰到什么问题，评论区也欢迎留言。

### <br>**5.2 推理引擎的加速和稳定**

<br>推理引擎本身其实就做了非常多的各种corner case的压力测试。<br>大家可能想来想去要调很多 server 参数，但是实际上 SGLang 的 default 参数就很好。<br>所以，这里SGLang的默认配置理论上就能有不错的性能，当然具体还要根据我们提供的评估数据来看是否还有优化空间。<br><br>稳定也很重要，推理引擎服务线上业务，挂了大不了我重启。但训练的过程中，这个挂了，PPO训练的回滚就相对麻烦不少，很有可能得重来。

### <br>**5.3 推理引擎和训练引擎的一致性**

<br>感谢SGLang mercy老师的解答。<br>推理引擎的 kernal fusion 和 training engine 差距不小，batch size 不一样时，推理请求 dispatch 到不同的 kernal 上，然后 numerical 误差逐层累计，到了 logits 这层就到了不可忽视的程度了。<br>所以现在推理引擎在 RLHF 中更多是加速 sampling，reward 和 embedding 还得用训练脚本来算<br>这个问题在 bert 时代就有了，training engine 和 inference engine 的精度差异无法规避。<br>估计需要至少一个季度的事件来修复这个问题。
