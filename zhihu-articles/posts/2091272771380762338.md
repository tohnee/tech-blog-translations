RDMA 入门编程记录：在 Linux 云电脑上用 Soft-RoCE 学习 SEND、WRITE 和 READ 上周主要学习了 RDMA 的一些基础知识，这周开始尝试把这些概念放进代码里，做一些简单的编程练习。 我的实验环境是一台租来的 Linux 云电脑，内存为 4GB，没有支持 RDMA 的硬件网卡。因此，这次使用 Soft-RoCE（RXE） 来学习 RDMA 编程。它通过软件实现 RoCEv2 协议，让没有 RDMA 硬件网卡的环境也能进行相应的功能实验。关于这一点，可以参考 rdma-core 的 RXE 文档。 这次练习的重点，是了解一个 RDMA 程序需要准备哪些资源，以及 SEND/RECV、RDMA WRITE 和 RDMA READ 分别怎样使用。 程序使用 C++ 编写，按 C++20 标准编译，通过 libibverbs 调用 RDMA 接口。实验中使用的设备是绑定在本地环回接口 lo 上的 rxe_lo，两个通信端点都在同一个进程里，因此做的是本地功能实验。 我使用的设备创建命令如下：

## 查看本地环回接口的地址

ip -br addr show dev lo

## 创建绑定到 lo 的 Soft-RoCE 设备

sudo rdma link add rxe_lo type rxe netdev lo 这一步的前提是系统已经具备相应的内核模块和用户态支持。如果 rdma_rxe 模块尚未加载，可以先执行： sudo modprobe rdma_rxe 创建后，可以通过以下命令检查设备是否出现，以及端口的状态： rdma link show ibv_devices ibv_devinfo -d rxe_lo 开始写程序以后，我接触到了几个之前只在概念介绍里见过的对象：

- PD（Protection Domain，保护域）：用于关联和隔离 RDMA 资源，本例中的 MR 和两个 QP 都属于同一个 PD。
- MR（Memory Region，内存区域）：把指定的缓冲区注册给 RDMA 设备，并设置相应的访问权限。
- QP（Queue Pair，队列对）：包含发送队列和接收队列，程序通过它提交通信操作。
- CQ（Completion Queue，完成队列）：保存操作的完成记录，程序需要检查这些记录，判断操作是否成功。 这些对象的关系，可以结合程序的执行顺序来理解：先打开设备，分配 PD，注册缓冲区，再创建 CQ 和 QP；随后配置两个 QP，最后提交具体的通信操作。 本例创建了两个 RC（Reliable Connection，可靠连接）类型的 QP，分别是 qp 和 peer_qp。程序让它们互为通信对端，并依次完成下面的状态转换： RESET → INIT → RTR → RTS 配置过程中，需要填写端口、对端 QP 编号、GID、MTU 和 PSN 等信息。因为两个 QP 都在同一个进程里，程序可以直接取得对端的 QP 编号和内存信息；以后拆成两个进程或两台机器时，就需要增加这些信息的交换过程。 这次练习主要安排了三组操作： 操作 本例中的数据流向 需要关注的区别 SEND/RECV send_buffer → buffer 接收侧先投递 RECV，提供接收缓冲区 RDMA WRITE send_buffer → buffer + 8 发起侧指定对端地址和 rkey，普通 WRITE 不需要对端为这次操作投递 RECV RDMA READ buffer + 8 → read_buffer 发起侧指定对端地址和 rkey，并准备本地缓冲区存放读回的数据

SEND 的数据放在哪里，由接收侧提前投递的接收缓冲区决定；WRITE 和 READ 则由发起侧在请求中指定对端内存地址。后两种操作也要求对端提前注册内存并设置合适的权限。相关语义可以参考 NVIDIA 的 RDMA 编程指南。 程序里准备了三个缓冲区：

char send_buffer[64] = {‘A’, ‘B’, ‘\0’, ‘C’, ’D’};

char buffer[64]{}; char read_buffer[64]{};

const std::size_t send_length = 5; const std::size_t target_offset = 8;

实际传输的长度是 5 字节。这里的数据中间包含一个 ‘\0’，因此不能用普通 C 字符串的显示方式来判断数据是否完整。 在本例所用的 Linux 环境中，这 5 个字节对应的十进制值是： 65 66 0 67 68 所以，代码使用 std::memcmp() 按指定长度比较数据，并逐字节打印内容。这样可以检查中间的零字节，以及它后面的 C 和 D 是否都被正确传输。 实验先通过 SEND/RECV，把这 5 个字节发送到 buffer，检查接收长度和内容。随后清空 buffer，通过 WRITE 将数据写到偏移 8 字节的位置。最后，再通过 READ 从这个位置把数据读回 read_buffer，与最初的数据比较。 还有一点需要注意：调用 ibv_post_send() 返回成功，表示请求已经成功投递，仍然需要检查后续的完成记录。 本例通过 ibv_poll_cq() 轮询 CQ，并检查完成状态；每个阶段还设置了超时，避免出错时一直等待。关于投递和完成的区别，可以参考 libibverbs 的 ibv_post_send 文档。 对于普通 RDMA WRITE，对端不会自动收到一条 RECV 完成记录。因此，以后把程序拆成两个独立进程时，还需要考虑接收方怎样知道数据已经写好，以及什么时候可以读取或复用缓冲区。 程序只有在三组数据检查都通过后，才会输出： All payloads MATCH. 目前这份代码主要用于帮助我理解 RDMA 的基本编程流程。设备名 rxe_lo 和 GID 索引等参数都写在代码里，换到其他环境时需要重新检查，不能直接假定相同的配置仍然适用。 接下来，我想先把这次用到的接口和参数理解得更扎实，再尝试将两个通信端点拆成独立进程，逐步学习连接信息交换和应用层同步。 下面是这次练习的完整代码，我按设备初始化、资源创建、QP 配置、数据操作和资源释放几个阶段添加了注释。
