一个 Kubernetes 集群可以状态全绿，GPU 打满 100%，然后用户投诉回答太慢。

这件事听起来矛盾，其实是推理服务监控里最常见的误判。上周 The New Stack 发了一篇讲这个问题的文章，观点来自 HPE 的三位产品负责人。文章是 HPE 赞助的系列第四篇，通篇没有量化数字，但它点出的指标错位值得单独拆一遍，因为大多数团队的推理仪表盘确实停在这一层。

HPE Morpheus 的高级首席产品经理 Marius Bogoevici 在文里复述了一句他常听到的话：「我们的 GPU 利用率是 100%，所以跑得很好。」

这句话对服务实际表现的说明力，接近于零。

## 发生了什么：一个被当成健康指标的忙碌度

文章的主张可以压成一句：GPU 利用率是有用的信号，但它定位不了瓶颈。

运维真正要做的事，是把「AI 服务的行为」和背后的 Kubernetes、GPU、计算、存储、网络状态关联起来。服务行为包括首 token 延迟、完整响应时间、答案质量三项，分层各看各的看不出问题。

HPE OpsRamp 的产品管理副总裁 Mahesh Ramachandran 给的行动建议是「上线前先做 profile」，用有代表性的 prompt 长度、上下文长度、输出量和流量水平压测一遍，记录基线，上线后持续和基线比对。

这套说法在推理工程圈里不算新，但值得展开，因为「GPU 利用率会骗人」有明确的物理原因。

## 为什么 GPU 打满不等于跑得快

先看这个指标的定义。`nvidia-smi` 报的 GPU 利用率，是「采样周期内至少有一个 SM（流式多处理器）处于活动状态的时间占比」。注意它统计的是「有没有在干活」，不是「干得有多满」。

推理有两个阶段，资源形状完全不同。

预填充阶段把输入上下文读完，把注意力状态写进 KV cache。这一步是计算密集的，矩阵乘一个接一个，SM 真在算。

解码阶段一次只生成一个 token，每生成一个都要把整个 KV cache 读一遍。这一步是访存密集的，SM 大部分时间在等内存返回数据。在等待期间，SM 仍然被标记为「活动」。

结果就是：一块显卡可以显示 98% 的利用率，其中只有一小部分时间在做真正的计算，其余时间在等内存。你看到的是一个忙碌的 GPU，用户感受到的是一个排队中的请求。

第二条误导来自首 token 时间和生成速度的分离。TTFT 快，只说明请求进得快；后面每个 token 花多久，要看 token 间延迟（ITL）或者每输出 token 时间（TPOT）。一个服务可以 TTFT 200 毫秒、TPOT 40 毫秒，让用户觉得流畅；也可以 TTFT 200 毫秒、TPOT 400 毫秒，前十秒就吐两个字。

第三条来自请求组合的变化。不同模型的延迟和容量需求不一样，请求里混了长上下文检索、多模态输入、或者一个特别长的系统提示，用户体验就变了，而 GPU 的活跃度看起来一切正常。

第四条在 GPU 之外。网络配置、数据库和向量库的响应时间、GPU 分区是不是小到装不下这个模型，都会拖慢推理。这些因素一个都不体现在 `nvidia-smi` 里。

## 从 KV cache 到用户投诉，中间有一条链

把上面几条接起来，会得到一条很具体的因果链，这条链比任何单个指标都好用：

**KV cache 占用上升 → 可用块变少 → scheduler 无法准入新请求 → 等待队列变长 → TTFT 的 P99 突然抬头 → 用户看到卡顿。**

链条的价值在于它告诉你该在哪一环设告警。KV cache 是原因，TTFT 是症状。只盯 TTFT，你会在用户已经受影响之后才知道；只盯 KV cache，你会收到一堆没有用户影响的告警。两个都盯，一个防患，一个定性。

vLLM 已经把这条链上的每一环都暴露成 Prometheus 指标：`vllm:gpu_cache_usage_perc` 是缓存块占用，`vllm:num_requests_running`（以及 `_waiting`、`_swapped`）是运行中和排队中的请求数，`vllm:request_queue_time_seconds` 是排队时长，加上 TTFT、TPOT、prefill、decode、端到端延迟的直方图。这些名字比「GPU 利用率」精确一个量级。

还有两个容易踩的坑。

**排队时间不能看平均值。** 排队时长是双峰的：大多数请求等 0 毫秒，少数请求等几百毫秒。平均值会把两头抹成「25 毫秒，还行」，而你真正该看的是 P95 和 P99，因为那是用户感受到的那一次。

**批大小要看曲线，不要看单点。** 批大小决定引擎的聚合吞吐，从 1 拉到 64，吞吐提升很大；过了某个拐点，再加请求只会让 TPOT 变长。仪表盘上把批大小和输出 token 速率画在一起，能看出自己站在曲线的哪一段。

| 你习惯看的 | 它实际回答的问题 | 该换成什么 |
| --- | --- | --- |
| GPU 利用率 | 有没有 SM 在活动 | 输出 token 速率 + 批大小 |
| 平均延迟 | 平均体验（不存在的人） | TTFT / TPOT 的 P95、P99 |
| 平均排队时长 | 被抹平的两极 | 排队时长的直方图与分位 |
| GPU 显存「空闲」 | 引擎预留后的余量 | KV cache 占用率 |
| 请求成功率 | HTTP 200 的比例 | 5xx 率 + 空响应率 + 终止原因分布 |

## 上线前该测什么，上线后该看什么

HPE 那篇文章给的指标清单可以拆成两组。

上线前的一组，目标是拿到基线：首 token 时间、每输出 token 耗时、完整响应时间、可靠性、容量、资源效率、成本。每一项都要记录「在哪个区间测的」——网关侧、推理服务侧、还是客户端侧，三个位置量出来的数不一样。

上线后的一组，目标是发现回归：Kubernetes 事件、模型服务指标和 trace、网络与数据库信号、CPU/GPU/内存/存储遥测，以及扩缩容是不是按匹配负载的指标在动。

有一条特别值得抄：请求是不是被路由到了预期的模型。在多模型部署里，路由错配比资源不足更常见，而且它不会让任何基础设施指标变红。

质量必须单独评估。平台遥测只能证明请求被处理了，证明不了答案是好的。Bogoevici 的说法是「prompt 就是数据」，意思是 prompt、响应、检索到的文档都会进日志和 trace，得先想清楚采什么、存哪里、留多久、谁能看。

上线决定也不该由一个人拍。Subramanian 的原话是「这不能是一个人的事」，平台管理员、算法团队、安全团队、业务负责人得一起看代表性负载和故障场景，把容量、质量、成本、恢复能力的证据留下来。

## 一个更根本的指标：goodput

如果只记一个词，记 goodput。

普通吞吐统计的是「一秒处理多少请求」，goodput 统计的是「一秒处理多少个满足 SLO 的请求」。这个概念的来源是 DistServe 那篇论文，vLLM 的基准工具里已经直接支持：跑压测时给 `--goodput` 传 `ttft:500 tpot:50` 这样的键值对，它会把不满足这两个门槛的请求从有效吞吐里剔除。

这个改动的意义在于，它把「快」和「有用」统一到一个数上。一个把批大小拉到极限、TPOT 掉到 800 毫秒的服务，普通吞吐可能很漂亮，goodput 会很难看，而后者才对应账单和口碑。

## 一个能照着走的排障顺序

线上报警之后，按这个顺序看，比打开 GPU 面板有用。

第一步，确认症状落在哪一段：TTFT 破了还是 TPOT 破了。TTFT 破说明请求进不来，问题在准入和排队；TPOT 破说明生成慢，问题在解码阶段的资源。两段同时破，通常意味着整体过载。

第二步，看队列深度。请求数在涨但输出速率不涨，就是准入被卡住，往上找 KV cache。请求数不涨而延迟涨，问题可能在模型服务之外，去看网络和下游存储。

第三步，看 KV cache 占用率和 preemption（抢占）事件。占用接近上限时，引擎会开始换出请求，换出又会让后续解码更慢，形成负反馈。

第四步，看请求构成有没有变。长上下文请求的比例上升会同时抬高 TTFT 和显存压力，而这类变化不会在资源指标上留下明显痕迹。

第五步，确认路由。请求有没有打到预期的模型版本、有没有打到冷启动的副本。多模型部署里，这一步经常是原因，而且所有基础设施指标都是绿的。

## 对谁有影响

**推理平台的 SRE。** 你现在的仪表盘如果有 GPU 利用率，没有 TTFT 的 P99，那这一轮要改的就是它。改的顺序建议是先加 SLO 面板（TTFT、TPOT 的分位对照阈值线），再补队列深度和 KV cache 占用作为先行指标，最后才是 GPU 侧的解释性指标。

**扩缩容的负责人。** HPA 支持自定义指标和外部指标，但扩容策略不能让 GPU 容量瞬间出现。把扩缩容的触发指标从 CPU 换到队列深度，能提前几分钟开始动作，这几分钟往往就是 SLO 有没有破的差别。

**负责成本的人。** 批大小曲线的拐点就是性价比最优点。站在拐点左边是浪费硬件，站在右边是牺牲 TPOT 换吞吐。这个取舍要显式做，别让它由默认参数决定。

**采购与架构评审。** 文章提到的 2027 方向包括模型路由、内容感知路由、相关组件共调度、分离式服务（disaggregated serving），这些都不是装上就有的能力，要按自己的架构单独评估。分离式服务对预填充和解码的资源配比有要求，套在现有集群上不一定划算。

## 边界：这篇材料的可信度要打折

得说清楚：The New Stack 那篇是 HPE 赞助的系列文章，观点来自 HPE 三位产品负责人，通篇没有一个量化数字，也没有客户案例。它列的指标是「应该测什么」，不是「测出来是多少」。

所以这篇文章能提供的是一套判断框架，不能提供基准值。TTFT 的 SLO 定 500 毫秒还是 2 秒，取决于你的模型、上下文长度和用户预期，别人给的数字没有参考价值。

`nvidia-smi` 利用率的具体采样语义在不同驱动版本上有细微差别，跨厂商（尤其是国产加速器）时更要对一遍文档，别假设定义一致。

goodput 的门槛一旦定死，团队会不自觉地围着这两个数优化，可能牺牲别的维度，比如长上下文的成功率。SLO 要定期复核。

最后一点：这套指标只在「你自己能改推理服务」时成立。用托管 API 的团队拿不到队列深度和 KV cache 占用，只能在外围测端到端延迟，这时候更该关注的是客户端侧的分布，而不是任何服务端指标。

## 接下来看三个信号

第一，你们集群里 TTFT 的 P99 和 GPU 利用率的相关系数。如果两者几乎不相关，说明当前瓶颈不在算力，加卡是白花钱。

第二，队列深度的峰值出现在什么时候。出现在流量高峰属于正常，出现在低谷就是配置问题。

第三，goodput 和普通吞吐的比值。这个比值越小，说明越多的算力花在了不满足 SLO 的请求上。

三个数都能在一周内测出来，不需要换任何工具。
