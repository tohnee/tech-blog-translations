### 0. 引子：大模型的知识，为什么不能只装在参数里？

2020 年 Lewis 等人在论文 *Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks* 中首次系统提出 RAG 时，它还只是开放域问答的一个分支。没有人预料到，五年后它会成为大模型落地几乎绕不开的基础设施。

要理解 RAG 的必然性，先要承认**纯参数化模型（Parametric Memory）在工程上的三个结构性缺陷**：

1. **知识截止（Knowledge Cutoff）与更新成本**。模型的知识冻结在预训练那一刻。更新一条事实，理论上需要重新训练或微调，代价是数千 GPU 小时，且会引发灾难性遗忘（Catastrophic Forgetting）。
2. **幻觉（Hallucination）的不可消除性**。自回归模型的本质是按概率分布采样下一个 token，它优化的是 “看起来合理”，而非 “事实为真”。只要生成是概率性的，幻觉就只能抑制、无法根除。
3. **不可溯源（No Provenance）**。参数里的知识是亿万文档压缩后的分布式纠缠表示，你无法让模型指出 “这句话出自哪份文件第几页”，而这恰恰是金融、医疗、法律、企业合规场景的硬性要求。

RAG 的思路极其朴素：**既然把知识写进参数又贵又不可靠，那干脆不写进去，在生成时临时去外部知识库 “开卷考试”。** 它把记忆从参数中剥离出来，变成可增删、可审计、可溯源的**非参数化记忆（Non-Parametric Memory）**。

这是一次典型的架构权衡：用一次在线检索的延迟，换取知识的时效性、可维护性与可验证性。

### 1. 第一性原理：RAG 在数学上到底做了什么

抛开工程术语，RAG 可以用一个生成模型的边缘概率来精确刻画。

给定输入问题 $x$，普通语言模型直接建模 $P(y|x)$。而 RAG 引入了一个隐变量 —— 检索到的文档块 $z$（可以是多个），并对其进行边缘化（marginalization）：

$P_{RAG}(y|x) = \sum_{z \in \mathcal{Z}} P_\eta(z|x) \cdot P_\theta(y|x, z)$

这里有两个可训练 / 可设计的组件：

- **检索器** ：定义了 “ 在问题 $x$ 下，证据块 $z$ 被选中的概率分布 “，对应 ANN 检索 + 相关性打分；
- **生成器** ：在证据 $z$ 作为条件被注入后，答案的生成分布，对应 LLM。

这个公式揭示了一个常被忽视的事实：**RAG 不是一个模型，而是一个由两个分布耦合而成的概率系统。** 系统的最终误差，是检索误差与生成误差的复合。这也直接决定了后面要讲的评估体系 —— 为什么必须把 “检索质量” 和 “生成忠实度” 分开度量。

从信息论的角度看，检索的本质是**一次条件互信息的最大化**：我们希望选出的 $z$ 能为回答 $y$ 提供最大的信息增益，即最大化 $I(y; z \mid x)$。一个与问题无关的 chunk，其条件互信息趋近于零，甚至为负（噪声会挤占有限的上下文窗口、稀释注意力）。这为 “上下文不是越多越好” 提供了理论依据。

需要强调的是，RAG 并非凭空出现。它背后是一条清晰的学术脉络：从记忆网络（Memory Networks, 2015）、神经图灵机，到 ORQA、REALM 的可微检索，再到 RAG 把 “检索 - 生成” 端到端化。理解这条脉络，才能看懂今天的 Agentic RAG 其实是在更高层次上回归 “显式记忆 + 推理控制” 的初心。

### 2. 全景架构：两个阶段，一条数据流

一个生产级 RAG 系统在物理上被切成两个生命周期完全不同的阶段：**离线索引（Indexing）** 与 **在线服务（Serving）**。

![](https://picx.zhimg.com/v2-6ab50530cf560f4792402811a74874b5_r.jpg)
*RAG 系统两阶段全景架构*

**为什么必须离线 / 在线分离？** 因为二者的计算量级与频率完全不对等。索引要对整个语料（可能是百万、千万级文档）做全量编码，是重计算、批处理、低频的；而在线查询要求百毫秒级响应，是轻计算、高并发、实时的。把文档侧的编码全部预计算并沉淀为索引，在线只编码一条 query—— 这是 RAG 工程可行性的根本前提。

下面我们沿着数据流，逐模块拆解。

### 3. 离线索引：RAG 质量的 “原罪” 往往在这里埋下

### 3.1 文档解析：被低估的第一公里

很多人把 RAG 效果差归咎于大模型或向量库，但我的经验是：**一半以上的线上问题，根源在数据进入索引之前。**

真实语料不是干净的纯文本。PDF 里有双栏混排、页眉页脚、跨页表格、脚注、图片公式；扫描件需要 OCR；HTML 有大量导航噪声。解析阶段的目标是恢复**阅读顺序（Reading Order）与语义结构**，并保留标题层级、表格边界等结构化信息。这一步丢失的上下文，后面任何检索技巧都补不回来。

工程上通常会同时抽取**元数据（Metadata）**：来源、章节标题、日期、文档类型。元数据不是附属品，它是在线阶段做 ** 预过滤（Pre-filtering）** 和权限隔离的依据 —— 例如 “只在 2026 年的财报里检索”。

### 3.2 语义分块：一个偏差 - 方差权衡问题

分块（Chunking）是 RAG 的第一工程难题，因为它要在一对矛盾中取平衡：

- **块太大**：单个 chunk 混入多个主题，向量表示被 “平均化”，主题不聚焦，检索精度下降；同时浪费上下文窗口。
- **块太小**：语义不完整，丢失必要的上下文（一个代词 “它” 可能指代上一段的实体），召回的证据无法支撑生成。

这在统计学习语言里就是经典的**偏差 - 方差权衡**：块越大，单个表示的偏差越大；块越小，对完整事实的估计方差越大。

常见策略各有适用边界：

| 策略 | 机制 | 适用场景 |
| --- | --- | --- |
| 固定长度切分 | 按 token 数硬切 + 重叠窗口 | 语料规整、快速基线 |
| 递归 / 结构切分 | 优先按段落、句子边界递归切 | 通用文本，最常用 |
| 文档结构切分 | 按标题 / 章节树切分 | 层级清晰的文档、手册 |
| 语义切分 | 按相邻句 embedding 突变点切 | 主题切换明显的长文 |

**重叠窗口（Overlap）** 是个关键细节：相邻块保留 10%–20% 的重叠，能避免一句话被从中间截断而丢失语义。更进阶的做法是**父子文档（Parent-Child / Small-to-Big）**：用小块去检索（保证命中精度），命中后返回它所属的大块 / 父文档给 LLM（保证上下文完整），一举解决 “好检索” 与 “好生成” 对块大小的相反诉求。

### 3.3 Embedding：把语义压缩进一个向量

Embedding 模型（通常是双塔 Bi-Encoder）把文本映射为一个稠密向量，使语义相近的文本在向量空间中距离相近。其训练目标多为**对比学习（Contrastive Learning）**：拉近正样本对（query - 相关文档）、推远负样本对，损失函数常用 InfoNCE：

$\mathcal{L} = -\log \frac{\exp(\text{sim}(q, d^+)/\tau)}{\sum_{d} \exp(\text{sim}(q, d)/\tau)}$

其中 $\tau$ 是温度系数，控制分布的尖锐程度。

这里有两个值得博士层面关注的点：

1. **各向异性（Anisotropy）**。原生语言模型输出的向量往往挤在向量空间的一个狭窄锥形区域，导致相似度区分度低。实践中通过对比学习微调、向量白化（Whitening）或归一化来缓解。
2. **归一化与余弦相似度**。对向量做 L2 归一化后，内积等价于余弦相似度，检索退化为比较夹角而非模长，这让 ANN 索引的距离度量更稳定。

### 3.4 向量数据库与 ANN：在精度与速度之间做工程妥协

百万级向量下，精确计算 query 与所有文档的相似度是 $O(N)$ 的暴力扫描，不可接受。近似最近邻（ANN）用可控的精度损失换取数量级的加速，主流索引是 **HNSW（Hierarchical Navigable Small World）**：它构建一个多层近邻图，上层稀疏、长程连接用于快速定位，下层稠密、用于精细查找，期望对数复杂度内完成检索。

IVF（倒排聚类）、PQ/SQ（乘积 / 标量量化）则从 “聚类分区” 和 “向量压缩” 两个维度进一步降低内存与延迟。记住一个核心认知：**ANN 的每一分速度提升，都是用召回率换来的**，参数调优就是在这条 Pareto 前沿上选点。

### 4. 在线检索：两阶段漏斗与查询侧增强

即使索引完美，在线阶段仍要面对 RAG 最棘手的矛盾：**用户的提问方式，与文档的书写方式，往往用的不是同一套词。** 这就是 “词汇鸿沟（Vocabulary Mismatch）”。

![](https://pic2.zhimg.com/v2-7d3c4b4d97b2e8a12bd54645387688b7_r.jpg)
*检索核心机制深度剖析*

### 4.1 查询侧增强：在检索之前先 “理解问题”

- **Multi-Query**：让 LLM 把原问题改写成多个语义等价、措辞不同的查询，分别检索后合并，扩大召回覆盖面。
- **HyDE（Hypothetical Document Embeddings）**：一个很聪明的逆向操作。先让 LLM 不看资料、”臆想” 出一个假设性答案（哪怕含错误事实），再用这个假设答案的向量去检索。逻辑是：**答案与真实文档在表达空间上比短问题更接近**，从而绕过词汇鸿沟。
- **Step-Back Prompting**：把具体问题抽象为上位的原理性问题（”某药 2026 年价格”→”该药物的定价机制”），先命中背景性知识，再回答具体问题。
- **子问题分解（Decomposition）**：把多跳复杂问题拆成可顺序回答的子问题链，逐跳检索、逐跳聚合，是处理多跳推理的基础手段。

### 4.2 为什么必须是 “双塔召回 + Cross-Encoder 精排” 两级？

这是整个检索链路最精妙的设计，核心在于**交互的时机与成本**。

**双塔 Bi-Encoder（召回阶段）**：query 和 document 分别通过两个独立的编码器，各自压缩成一个向量，再算余弦相似度。因为两者在编码时互不见面、没有交互，所以**文档侧的向量可以全量离线预计算**，在线只需编码一条 query 并走 ANN。代价是：独立编码丢失了 query 与 doc 之间的细粒度交互信号，精度有限，但它能从百万级语料中快速捞出 Top-K（约 50–200）。

**Cross-Encoder（精排阶段）**：把 query 和每个候选文档**拼接**成一个序列，喂进同一个 Transformer，让二者的 token 在自注意力中全交互，最后输出一个相关性标量分。这种深度交互带来高得多的语义匹配精度，但它**无法预计算**—— 每来一个 query，都要对每个候选重新做一次完整前向推理，成本是 $O(K)$ 次 Transformer 计算。

于是两级架构形成完美互补：

> 用便宜的双塔在大海里<br> **快速捞起一个小范围**<br> （保证 Recall，控制成本），再用昂贵的 Cross-Encoder 只对这一小范围<br> **精挑细选**<br> （保证 Precision）。

绝不能对全库直接上 Cross-Encoder，那是工程自杀；也不能只靠双塔，精度天花板太低。这个 “漏斗” 是成本约束下的必然结构。

### 4.3 混合检索与 RRF：稀疏与稠密的融合

稠密向量擅长语义匹配（”汽车” 能匹配 “轿车”），却对**精确关键词、专有名词、数字编号**不敏感；以 BM25 为代表的稀疏检索恰好相反，精确匹配强、语义泛化弱。二者互补，因此生产系统几乎都采用**混合检索（Hybrid Search）**。

问题在于如何融合两路分数 —— 它们的尺度完全不可比。**RRF（Reciprocal Rank Fusion）** 巧妙地绕开分数校准，只看排名：

$\text{score}(d) = \sum_{i} \frac{1}{k + r_i(d)}$

其中 $r_i(d)$ 是文档 $d$ 在第 $i$ 路结果中的排名，$k$ 是平滑常数（通常取 60）。排名越靠前、贡献越大，且无需任何分数归一化，对异构排名天然鲁棒。这是我在工程中最推荐的默认融合方案，简单、稳定、几乎无需调参。

### 5. 生成侧：上下文工程决定了检索成果能否兑现

检索再准，若生成阶段不能正确使用证据，前功尽弃。这一环节的核心是**上下文工程（Context Engineering）**。

**Lost in the Middle 效应**：研究表明，LLM 对位于上下文窗口**开头和结尾**的信息利用率高，对埋在中间的证据容易 “视而不见”。因此在组装多条证据时，应把最相关的 chunk 放在首尾，而非按原始顺序平铺。

**Token 预算分配**：上下文窗口是稀缺资源，需要在系统指令、检索证据、对话历史、输出预留之间做预算切分。证据并非越多越好 —— 无关 chunk 的条件互信息为负，会诱发注意力稀释和 “过度引用”。

**引用约束与拒答机制**：在 Prompt 中强制要求模型为每个论断标注来源编号（Citation），并显式给出 “证据不足时应拒答” 的指令。这把 “自由发挥” 约束为 “基于证据的受控生成”，是压低幻觉、实现可溯源的关键。一个典型的系统指令片段如下：

```text
你是严谨的企业知识助手。请严格遵守：
1. 只能基于 <context> 中的内容回答，每个论断后用 [编号] 标注来源；
2. 若上下文不足以支撑答案，直接回复"根据现有资料无法确定"，禁止推测；
3. 不要使用 <context> 之外的参数化记忆补全事实。
```

### 6. 范式演进：五代 RAG，自主性的逐级跃迁

理解 RAG 的最佳方式，是看它如何一级级解决上一代的局限。

![](https://pic2.zhimg.com/v2-89c340bad30312e62bd496b9921b2a5f_r.jpg)
*RAG 范式五代演进*

- **Naive RAG（2020）**：线性 “检索→拼接→生成”，固定 Top-K、无查询理解、无拒答，多跳问题基本失效。
- **Advanced RAG（2022–23）**：检索前（查询改写）后（Cross-Encoder 重排）双向增强，混合检索 + RRF，召回精度显著提升，但路径仍是静态固定的。
- **Modular RAG（2023–24）**：检索器、记忆、路由全部模块化解耦、可插拔，支持条件路由与多源统一，工程可维护性大增，但缺乏自主决策。
- **Agentic RAG（2024–26）**：Agent 用 ReAct（推理 - 行动）范式自主规划工具调用，能多轮自反思、判断证据充分性并动态改写重试，真正 “知道自己何时不知道”，代价是延迟与 token 成本上升。
- **GraphRAG 融合（2024–26）**：以知识图谱承载结构化关系，通过社区检测生成分层摘要，攻克向量 RAG 不擅长的全局性、多跳关系问题，并与 Agentic 架构深度融合。

演进主线非常清晰：**检索自主性、推理深度、全局上下文持续上升，而系统复杂度与成本同步上升。**

### 7. 前沿专题：GraphRAG 与 Agentic RAG

### 7.1 GraphRAG：让 RAG 回答 “全局性问题”

传统向量 RAG 有一个致命盲区：它通过局部相似性检索零散 chunk，**无法回答需要跨文档全局归纳的问题**，例如 “整个语料库中反复出现的核心主题是什么？”。

微软提出的 GraphRAG 流程分两步破解：

1. **建图**：用 LLM 从语料中抽取实体（节点）与关系（边），构建知识图谱；
2. **社区检测与摘要**：用 Leiden 等算法对图谱做社区聚类，再让 LLM 为每个社区生成分层摘要。查询时，既可以做**局部搜索**（实体邻域 + 相关社区），也可以做**全局搜索**（map-reduce 式地聚合多个社区摘要来回答全局性问题）。

图谱让关系推理变得显式且可解释（可沿 n-hop 路径追溯），代价是建图阶段的 LLM 调用成本高昂。学术界 2025–26 年进一步出现了把图谱、Agent 与层级检索接口结合的工作（如 A-RAG、TechGraphRAG），用 13 步级别的自主流水线做证据充分性评分与漂移防护式改写。

### 7.2 Agentic RAG：从 “执行固定流水线” 到 “自主决策”

Agentic RAG 的本质是把检索的控制权从硬编码流程交给 LLM 的推理循环。一个典型的 Agent 循环是：

```text
规划（Plan）→ 选择检索工具（Act）→ 观察证据（Observe）
→ 评估证据是否充分（Reflect）
   ├─ 充分 → 生成答案
   └─ 不足 → 改写查询/换检索源 → 回到 Act（带最大迭代次数）
```

这与静态 RAG 的根本区别在于**引入了测试时计算（Test-time Compute）**：系统可以通过增加检索 - 反思的迭代次数来换取更高的回答质量，类似于推理模型用更多思考步换正确率。它还能在向量库、BM25、图谱、甚至外部 API / 数据库之间做工具路由。但要警惕：自主性带来非确定性的延迟和成本，生产环境必须设置最大迭代次数、漂移检测（防止改写偏离原问题）与成本熔断。

### 8. RAG vs 微调：这不是一道二选一的题

一个被反复争论的问题：该用 RAG 还是 Fine-tuning？我的结论是**二者解决不同层面的问题，生产中常常协同**。

| 维度 | RAG | Fine-tuning |
| --- | --- | --- |
| 知识更新 | 实时、改库即可，成本极低 | 需重新训练，成本高、易遗忘 |
| 时效性 / 溯源 | 强，可引用、可审计 | 弱，知识仍纠缠在参数中 |
| 作用本质 | 注入知识（Knowledge） | 塑造行为 / 风格 / 格式（Behavior） |
| 幻觉控制 | 外部证据约束，更有效 | 能改善但无法根治 |
| 推理成本 | 每次多一次检索 + 更长上下文 | 单次推理，无额外检索 |
| 适用数据 | 海量、动态、需溯源的外部知识 | 固定的语气、领域术语、输出格式、推理范式 |

**经验法则**：用 RAG 解决 “知道什么”，用微调解决 “怎么说话 / 怎么推理”。Modular RAG 阶段出现的 RAG-FT 协同，正是用微调让模型更好地利用检索到的上下文（例如训练它习惯引用格式），二者叠加而非互斥。

### 9. 评估体系：RAG 最难、也最被偷懒的一环

“看着好像能用” 是 RAG 部署的最大风险。因为 RAG 是检索与生成耦合的系统，出了错你必须先定位是哪一环。业界在 2026 年已收敛到 **RAG 三元组（RAG Triad）** 框架。

![](https://pic2.zhimg.com/v2-a8f9b9bff535d74063896ba270864d23_r.jpg)
*RAG 评估体系*

三个独立维度分别捕捉不同的失败面：

1. **上下文相关性（Context Relevance，检索侧）**：召回的证据是否相关、是否漏检。对应 `context_precision` / `context_recall`。
2. **忠实度（Faithfulness/Groundedness，生成侧，核心）**：答案的每个论断能否被证据支撑。对应 `faithfulness`。**一个检索完美却编造答案的系统，比检索差但会拒答的系统更危险。**
3. **答案相关性（Answer Relevance，对齐侧）**：答案是否切题、完整回应了问题。对应 `answer_relevancy`。

为什么不用 BLEU/ROUGE？因为它们基于**字面重叠**，会惩罚正确的释义、也抓不住幻觉 —— 而 RAG 的核心价值恰恰是 “用不同的话讲正确的事”。因此 **LLM-as-Judge（用校准过的大模型当裁判）** 成为主流，它无需人工标注即可对开放式答案做蕴含判断。

工程上，正确的姿势是把评估做成**自动化回归闭环**：维护 20–50 条覆盖典型、边界与对抗场景的 Golden Set，用 RAGAS 等框架在 CI 中像跑单元测试一样自动评分，任一指标退化即阻断上线，线上再做采样评分与漂移监控。**没有评估门禁的 RAG，本质上是在裸奔。**

### 10. 工程实践：一个最小可用 RAG 的核心实现

下面用 Python 给出一个**不依赖重型框架、逻辑透明**的最小 RAG 骨架。`embed`、`rerank` 保留为可替换接口（实际接 BGE、Cohere 或自研模型），重点展示两阶段检索、RRF 融合与引用约束的完整数据流。

```text
import numpy as np
from typing import List, Dict

# ---------- 可替换的模型接口（生产中替换为真实 API/本地模型）----------
def embed(texts: List[str]) -> np.ndarray:
    """返回 L2 归一化后的稠密向量，shape=(len(texts), dim)"""
    v = np.random.randn(len(texts), 768)
    return v / np.linalg.norm(v, axis=1, keepdims=True)

def rerank(query: str, docs: List[str], top_n: int = 5) -> List[int]:
    """Cross-Encoder 精排：对 query-doc 拼接交互打分，返回 top_n 的索引"""
    scores = np.random.rand(len(docs))          # 真实场景为 Cross-Encoder 输出
    return list(np.argsort(-scores)[:top_n])

# ---------- 离线索引 ----------
class VectorIndex:
    def __init__(self, chunks: List[str], metadata: List[Dict]):
        self.chunks = chunks
        self.metadata = metadata
        self.vectors = embed(chunks)            # 全量离线预编码

    def dense_search(self, q_vec: np.ndarray, k: int) -> List[int]:
        sims = self.vectors @ q_vec[0]          # 归一化后内积即余弦
        return list(np.argsort(-sims)[:k])

    def bm25_search(self, query: str, k: int) -> List[int]:
        # 生产中接 Elasticsearch / Lucene 倒排，这里用占位实现
        return list(np.argsort(np.random.rand(len(self.chunks)))[:k])

# ---------- RRF 融合 ----------
def rrf(rank_lists: List[List[int]], k_const: int = 60) -> List[int]:
    scores: Dict[int, float] = {}
    for ranks in rank_lists:
        for rank, doc_id in enumerate(ranks):
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k_const + rank + 1)
    return sorted(scores, key=scores.get, reverse=True)

# ---------- 在线查询 ----------
def answer(query: str, index: VectorIndex, recall_k: int = 50, top_n: int = 5):
    # 1. 查询侧（此处可插入 HyDE / Multi-Query 改写）
    q_vec = embed([query])

    # 2. 双塔粗排：稀疏 + 稠密两路召回
    dense_hits = index.dense_search(q_vec, recall_k)
    sparse_hits = index.bm25_search(query, recall_k)

    # 3. RRF 融合，收敛候选
    fused = rrf([dense_hits, sparse_hits])

    # 4. Cross-Encoder 精排
    cand_docs = [index.chunks[i] for i in fused]
    final_idx = rerank(query, cand_docs, top_n)
    evidence = [(fused[i], cand_docs[i]) for i in final_idx]

    # 5. 上下文组装 + 引用约束（Prompt 工程）
    context = "\n".join(f"[{n+1}] {doc}" for n, (_, doc) in enumerate(evidence))
    prompt = (
        "只能基于以下资料回答，每个论断后标注 [编号]；"
        "资料不足则回复'根据现有资料无法确定'。\n\n"
        f"<context>\n{context}\n</context>\n\n问题：{query}"
    )
    return prompt, [doc_id for doc_id, _ in evidence]

# HyDE 查询改写的最小实现
def hyde_query(query: str, llm) -> str:
    hypothetical = llm.generate(f"请直接回答（无需保证正确）：{query}")
    return hypothetical                          # 用假设答案的向量去检索
```

对应的 RAGAS 自动评估，只需准备好问题、答案、检索上下文与标准答案：


### 11. 灵魂拷问：长上下文时代，RAG 会消亡吗？

这是近两年最尖锐的问题。当上下文窗口从 4K 一路扩展到百万 token，”把整个语料塞进 Prompt” 似乎让检索变得多余。我的判断是：**长上下文会改变 RAG 的形态，但不会让它消亡，原因有四。**

1. **上下文长 ≠ 上下文用得好**。Lost in the Middle 在超长窗口中更严重，模型对海量塞入信息的实际利用率并不随窗口线性增长，”大海捞针” 测试的高分往往是精心构造的理想条件。
2. **成本与延迟的非线性**。注意力计算与 KV Cache 开销随上下文增长，百万 token 的推理成本和首 token 延迟，对高并发生产场景是不可接受的；而 RAG 本质上是**在模型外部做了一次高效的信息筛选**，只把少量高相关证据送进窗口。
3. **检索的价值不止于压缩**。权限隔离、元数据过滤、可溯源引用、知识的实时增删 —— 这些是长上下文本身不提供的治理能力。
4. **真正的趋势是融合而非替代**。未来的形态是 RAG 负责 “选对证据、做治理与溯源”，长上下文负责 “在选中的更大范围内做复杂推理”。Agentic RAG 会把 “是否需要检索、检索几次、检索什么” 变成动态决策。

一句话总结：**RAG 的长期价值从来不是 “省 token”，而是为概率性的生成系统提供一个可治理、可验证、可更新的外部知识层。** 只要大模型依旧是概率性的、知识依旧需要治理，这个外部记忆层就有存在的理由。

### 12. 结语

回到最初的公式 $P(y|x)=\sum_z P(z|x)P(y|x,z)$。RAG 的全部复杂性，都来自我们要同时驯服两个分布：让检索器在词汇鸿沟下选出高互信息的证据，让生成器在证据约束下保持忠实而非自由发挥。

从 Naive RAG 到 Agentic / GraphRAG 的演进，本质上是**把知识治理与推理控制从模型参数中不断外化、显式化的过程**。对工程师而言，真正拉开差距的不是用了哪个框架，而是能否建立第一性原理的认知、守住数据与分块的基本盘、并用严格的评估闭环让每一次优化都可度量。
