先说结论：[WordPress.org](http://WordPress.org) 官方发布的 MCP Adapter，一个月下载破 10 万，是 WordPress 拥抱 AI 最重的一步棋。但先把预期摆正：这插件自身不提供任何 AI 功能，装上它你的站不会多出一个能聊天的助手。它真正值得看的，是两件事——协议层上少见的自律（只认两个 schema 版本、非法字段直接拒），以及 CMS 厂商第一次亲自下场定义“AI 能通过什么接口碰我的站点”。

![](https://pic2.zhimg.com/v2-b3b3c02ec63b48ee80f9de4e77e41287_r.jpg)

MCP Adapter 是 [WordPress.org](http://WordPress.org) 官方发布的 MCP 插件（GPL-2.0），属于 WordPress AI Team“AI Building Blocks for WordPress”计划的一部分。它把站点上注册的 ability 自动翻译成 MCP 客户端看得懂的 tool、resource、prompt，任何兼容 MCP 的 AI 客户端都能直接调用你 WordPress 站点上的能力。

WordPress 插件市场里出现了一个不太常见的插件：作者页面写着 [WordPress.org](http://WordPress.org)，而不是某个人的昵称。这是官方推出的第一个 MCP 适配器，2026 年 10 月 2 日上架，截至 11 月 8 日累计下载 105,288 次——上架一个月就破了 10 万。

**先说清楚一个预期落差**

这插件自身不提供任何 AI 功能。它是服务端和传输层，装上它并不会多出一个能聊天的助手。

站点还得满足两个条件才有意义，一是用的 WordPress 6.9 或更新版本（Abilities API 已并入核心），二是真的注册了能力。如果你的站点目前只有文章、页面、媒体这些传统内容模型，没人写过 ability 的注册代码，那装了 MCP Adapter 等于什么都没装。

这个预期落差值得写在前头，因为它决定了你会不会用完就删。

**0.7.0 的协议取舍比功能列表更值得看**

版本从 0.7.0 开始就是破坏性升级，官方在 changelog 里写得很直接。

适配器只服务两个 MCP schema 版本，2025-11-25 和 2026-07-28。客户端如果提出 2025-06-18 或 2024-11-05，仍能连上，但会被降级服务到 2025-11-25。0.7.0 同时带来了 2026-07-28 支持，包括无会话的 server/discover 生命周期。

更硬的几条改动如下：生成的 DTO 类、McpToolValidator、McpResourceValidator、McpPromptValidator 以及 mcp_adapter_validation_enabled 过滤器全部移除，线上校验一律走选定 schema；非法协议字段不再静默丢弃或修补，无法被支持版本表达的组件直接拒绝；JSON-RPC 批量请求直接拒绝；WP\MCP\Cli 类定为 final。

这组取舍合起来就是一个态度，不迁就客户端。多数项目遇到老客户端会想办法兼容、想办法加开关。这份代码选择在还只有一个用户（WordPress 自己）的时候就砍掉模糊地带，把版本收敛到两个已知的点。代价是升级时客户端得跟着动，收益是协议行为可预测。

0.7.1 是补丁版本，修的是持久化的会话初始化参数被限制在 4 KiB 以内并自动恢复超限数据，受影响的客户端需要重连一次；客户端图标不再入库，避免大内联图标卡住连接。

**暴露是双层的**

这是整件事里安全上最该被认真读的部分。

ability 必须显式标记为 public 才会被暴露出去，而且执行前仍然按当前登录用户跑一遍权限检查。暴露开关和权限校验是两层，不是一层。也就是说，一个能力对外可见，不代表调用者就能随便用。攻击者拿到的仍然只是“一个已经登录的用户能做的事”。

不过话说回来，装上这个插件本身就是在开一个新面。HTTP transport 意味着站点多了一个可被外部调用的接口，Application Password 意味着多了一条机器凭证路径，站点作者的密码强度、你给 AI 客户端开的权限范围，都得自己把关。插件默认不暴露任何东西，这个默认是对的，但前提是你别急着去勾那个 public 标记。

**官方身份的分量**

插件由 [WordPress.org](http://WordPress.org) 自己发布，作者页就是 [profiles.wordpress.org/wordpressdotorg。仓库](http://profiles.wordpress.org/wordpressdotorg%E3%80%82%E4%BB%93%E5%BA%93) [github.com/WordPress/mcp-adapter](http://github.com/WordPress/mcp-adapter) 是 PHP 写的，1900+ 星、230+ fork、100 多个 open issue，2025 年 7 月建仓，最后一次 push 是 2026 年 11 月 4 日。协议 GPL-2.0，插件目录页面的 license 字段是空的，以仓库为准。

Abilities API 是 WordPress 6.9 引入的核心 API。与之配套的还有 PHP AI Client SDK 等客户端侧构建块，官方规划的目标是在 7.0 时让普通用户也能直接用上这些 AI 能力。加上 MCP Adapter，这四块拼图凑齐了：站点侧提供能力、客户端侧提供 SDK、中间用 MCP 协议接。

这条路线比“等第三方插件来接”更值得看。CMS 厂商主动做 AI 接入层，意味着它想自己定义“AI 能通过什么接口碰我的站点”，而不是把这个定义权让给插件生态里的某个明星项目。

**我的看法**

10 万次下载里有多少是真实站点在用、多少是好奇点一下就走的，官方数据给不出答案。插件评分 100 分，但只有 1 个评分，这个数字没有参考价值，别当真。100 多个 open issue 对 1900+ 星的仓库算偏高的比例，关心维护响应速度的读者可以去 issue 区翻翻。

协议层的干净是这份代码最值钱的地方。只认两个 schema 版本、非法字段直接拒、批量请求不接、用插件方式替代 bundled library 依赖，这些选择让适配器的行为边界是清楚的，在一个大量项目还在“先兼容着，以后再说”的阶段，这算是少见的自律。

至于 Abilities API 本身，仓库 2025 年 7 月就建了，插件 10 月才上架，中间这段打磨时间不短。能看出 WordPress 是在认真做一件事，而不是赶 AI 的时髦。

有件事对写代码的人是坏消息。用 bundled library 方式依赖适配器的路径已经被废弃，以后得改用装插件加 Requires Plugins: mcp-adapter 的方式。
