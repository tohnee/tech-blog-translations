## 16GB显存跑26万Token，14图请求快近70倍：RTX 5070 Ti上的KVMem＋NInfer调优全记录

从启动失败、INT8与RK4V4取舍，到GPU视觉与10K生成工作区：一套有限硬件上的参数推导方法。

实验日期：2026年10月14—15日。文章整理日期：2026年10月17日。

一张16GB显存的RTX 5070 Ti，装入约11GiB级别的27B模型权重后，长上下文、视觉编码、推测解码和运行时状态开始争夺余下空间。把某个参数单独拉满，通常只会把瓶颈移到另一个位置。

这次调优的目标很具体：尽量保留长历史，接受接近256K的输入；把历史图片重处理的等待降下来；不把生成工作区误设成单次输出上限；最后固化成可以运行、验证和回退的服务。

最终选择是：Swift-1.5-Qwen3.8-27B GSQ-RCO IQ3_S权重、RK4V4 KV、256K逻辑上下文、160K历史选择预算、10K生成工作区，以及GPU常驻视觉。

在最终配置的一次近满上下文测试中，实际输入为260,185 token，5个指定记录与随机暗码的映射全部正确。配对图片测试中，14张1024×1024图片的请求耗时从685.566秒降到9.803秒，约为原来的1/69.93。请求完成后的显存快照为15,778 / 16,303MiB，约96.8%。

这些数字说明这套配方在已测负载上可用，并不意味着“256K历史全部常驻显存”“永不丢针”，也不证明它是所有任务的质量最优配置。下面展开它的推导过程。

## 1. 先固定实验对象：我们到底在优化什么

| 模型 | Swift-1.5-Qwen3.8-27B-GSQ-RCO-IQ3_S-mtp-vision.ninfer |

| KVMem源码记录 | 主仓库快照dea1f22；NInfer基线8319e8f512477d0cfdef89e16c17c1ba9f9bc7b3及其集成补丁 |
| 服务形态 | 单进程、单活动请求，systemd托管 |

这里有两种不同的量化：IQ3_S描述模型权重，RK4V4描述运行时KV缓存。 调整KV格式不会把IQ3_S权重恢复成更高精度；增加思考预算也不会逆转权重量化。

## 2. 256K、160K和10K：三个容易混淆的数字

本文以1K＝1,024 token记预算，以MiB/GiB记内存；“26万token”只是便于阅读的十进制概称。

| 符号 | 最终值 | 实际含义 |
| --- | --- | --- |
| C：逻辑上下文 | 262,144 token | 输入与后续生成共同受这个上限约束 |
| B：历史选择预算 | 163,840 token，160K | KVMem为当前执行选入GPU的历史token预算，不是整份Host历史长度 |
| R：生成追加工作区 | 10,240 token，10K | 为追加计算预留的工作容量，不是单次回复token上限 |
| H：Host KV预算 | 12,288MiB，12GiB | 原生KV payload的主机预算，不等于进程总内存上限，也不是启动即全部占用 |

KVMem把长期KV历史放在Host侧，再将选中的工作集放到GPU。单路最终配置的B＋R为174,080 token，即170K。sink和recent等保留项计入B，不能在160K之外再免费追加一份。

生成继续推进、工作区需要刷新时，系统会重新组织驻留历史。因此，10K工作区可以产生超过10K的输出，但不能由此推出任意长输出都没有重选、传输或召回代价。

在逻辑层面，完整输入、模板与视觉展开token和新输出共同占用上下文。默认输出上限设为262,144，只是避免额外的较小服务端默认值；剩余上下文、客户端限制、停止标记和模型自身结束行为仍然生效。[KVMem预算说明](https://github.com/kvmem/kvmem/blob/master/docs/multi-backend.md)

## 3. 第一轮：先找能启动的容量边界

第一轮使用CPU视觉、R＝16K。我们先扫描KV格式与历史预算，再决定哪种候选值得做召回测试。

prefill chunk＝1,024时，INT8的B＝64K、80K、96K、104K，以及RK4V4的B＝128K、144K均在运行时容量规划阶段被拒绝。这里的“失败”是启动检查明确拒绝，不是测试已经开始后发生CUDA OOM。

将prefill chunk降到256后，同一轮CPU视觉条件下得到了更大的可启动集合：

| KV格式 | 成功启动的B | 启动被拒的B | R | prefill chunk |
| --- | --- | --- | --- | --- |
| INT8 | 64K、72K、80K | 84K、86K、88K、96K | 16K | 256 |
| RK4V4 | 112K、128K、144K、160K | 168K、172K、176K、192K | 16K | 256 |

​

![](https://pic1.zhimg.com/v2-cd58a1535f9189218f5fc98fa1df69a2_r.jpg)

​

数据来自capacity-sweep*.json​。这里的最大值是“扫描中通过的最大档位”，不是逐64-token页求出的数学极限。特别是160K与168K之间没有穷尽搜索，不能把160K写成唯一硬顶。

这一轮解决了一个经常被忽略的问题：prefill块大小也参与显存规划。 大块可能有利于计算效率，但它的workspace成本会挤占KV预算。对这台机器，先把chunk降下来，比一开始就缩短逻辑上下文更有效。

于是候选从“INT8更精细，应该优先”变成了一个真正的约束优化问题：INT8能留80K历史，RK4V4能留160K；哪一组更符合长历史召回目标？

## 4. 第二轮：高精度的小工作集，还是低精度的大工作集

我们用同一份长文回答这个问题。实际prompt为260,194 token，在原始语料约10%、30%、50%、75%、90%的位置，插入5个独立14字符暗码。查询要求返回“记录号→暗码”的JSON映射。全部采用temperature＝0、关闭思考，每个候选只测一次。

评分分成两层：

1. 完整暗码是否出现：答案是否包含某个正确字符串。
2. 记录号与暗码是否配对正确：是否真正回答了指定记录。

只有第一项会把“记得部分字符串，但对应关系错位”的答案错误算成通过。

| 配置 | 完整暗码出现 | 记录号—暗码精确配对 | 引擎prompt阶段耗时 | 请求总耗时 |
| --- | --- | --- | --- | --- |
| INT8，B80K / R16K，chunk256 | 3/5 | 0/5 | 425.346s | 426.322s |
| RK4V4，B160K / R16K，chunk256 | 5/5 | 5/5 | 538.020s | 539.112s |
| RK4V4，B144K / R16K，chunk512 | 5/5 | 5/5 | 515.679s | 516.753s |

数据来自tuning-bench.jsonl​及tuning-summary.json​。早期汇总曾将prompt阶段耗时标为TTFT；此表按原始timings.prompt_ms​纠正口径，它与客户端首个内容到达时间不是同一个测量值。

### 一个具体的错位案例

正确答案的前两条应该是：

```json
{"1":"8LJ46VWU7WJ81T","2":"21RPD2U6ZUQ1ME"}
```

INT8/80K的实际回答则是：

```json
{
  "1": "8T1T",
  "2": "VNHYGADXRZH1YF",
  "3": "IJRXDXIDNAS79A",
  "4": "ARFX85GWAQAH4B",
  "5": "8T1T"
}
```

后三个完整暗码确实出现了，却被移到了错误记录下。这就是“字符串命中3/5，正确配对0/5”的来源。

这组结果支持的结论很有限、也很具体：在这份长文和这些问题上，RK4V4/160K配方的召回结果优于INT8/80K配方。 它不是量化精度的纯A/B，因为KV格式、B以及部分候选的chunk同时变化。不能据此宣称“4位KV比8位更准”，也不能把0/5全部归因于工作集大小。

INT8另有一次独立10%位置单针测试失败；随后原定的逐针请求序列被取消，改为上述同文多针比较。这项未完成实验也保留在原始记录中。

RK4V4/144K＋chunk512比RK4V4/160K＋chunk256的prompt阶段少了22.34秒，约4.15%，两者都找全5针。最终仍选择160K，因为本轮优先目标是保留更大的历史选择预算；一次约4%的时间差不足以证明144K方案普遍更快。

另一个53-token短输入的代码生成检查中，INT8/80K为137.0 tok/s，RK4V4/160K为133.2 tok/s。它们与26万token捞针是不同请求；生成代码没有经过独立执行验证，因此这不是“满上下文133 tok/s”或“代码质量通过”的证据。

## 5. 第三轮：图片慢，先测清楚慢在哪里

CPU视觉保住了长历史预算，却把图片处理变成了突出等待项。早期896×896色块图测试中，同一张图片、各一次冷请求：CPU视觉32.147秒，GPU视觉1.024秒，约31.39倍差距。GPU重复请求仅0.142秒，但812/813个prompt token已经命中缓存，不能拿这个数字与CPU冷请求直接相比。

早期GPU配置还通过了14张不同896×896图片的单请求测试，总耗时8.003秒。它只作为迁移方向的验证，不与后面的1024×1024测试混算。

问题随即转为显存：视觉组件实际权重约282.01MiB，运行时还需要额外workspace。原B160K / R16K直接启用GPU常驻视觉时，容量规划报出：

```text
requested runtime reservation: 4,136,260,353 bytes
available runtime capacity:    3,932,684,288 bytes
```

差额203,576,065字节，约194.15MiB。CPU视觉被恢复，没有把失败配置留在线上。

既然目标是保留160K历史，就先压缩R，而不是先削减B。R从16K降到4K后，GPU视觉成功启动；随后逐档尝试恢复R。

## 6. 不是“显存还剩500MiB，就能全填进去”

调试日志显示，默认CUDA Graph allowance为258MiB，启动阶段实际Graph使用约26MiB。我们曾把allowance压到48MiB，让GPU视觉＋B160K / R16K成功启动。

但这次启动后，CUDA实际可用内存只剩36.5MiB。此前冷图片执行曾使观测显存增加约70MiB，因此这套R16K配置没有继续做图片负载，直接退回已测配置。

这里必须区分三件事：

- ​nvidia-smi​展示的设备显存占用；
- CUDA当时报告的可分配余量；
- 规划器预留的workspace、Graph allowance和slack。

它们并不是一笔可以互相直接抵扣的“零钱”。降低Graph allowance，是调整容量规划假设，不代表运行时真实需求随之消失；26MiB也只是启动观测，不能当成所有负载的Graph上限。

最终将Graph allowance选为128MiB，并以“启动后CUDA可用内存至少128MiB”作为本轮图片负载的保守门槛。这个阈值来自约70MiB冷图片增长的观测和额外余量，属于操作准则，不是普适安全定律。

## 7. 第四轮：4K、8K、10K、12K、14K，怎么选

下表保留每个档位真正完成的测试，不把“启动成功”改写成“稳定可用”。

| GPU视觉配置 | Graph allowance | 启动后CUDA可用 | 图片负载 | 结论 |
| --- | --- | --- | --- | --- |
| B160K / R4K | 默认258MiB | 258.5MiB | 14×896图，8.003s | 早期可用起点 |
| B160K / R8K | 128MiB | 184.5MiB | 14×1024图，10.410s | 完成图片及短输入输出检查 |
| B160K / R10K | 128MiB | 146.5MiB | 14×1024图，10.378s | 完成图片及短输入输出检查，进入最终复验 |
| B160K / R12K | 128MiB | 110.5MiB | 未执行 | 能启动，但低于本轮门槛，未选择 |
| B160K / R14K | 128MiB | 未就绪 | 未执行 | 容量规划被拒，差约26.96MiB |
| B160K / R16K | 实验性48MiB | 36.5MiB | 未执行 | 启动成功但余量过小，退回 |

R4与R8的Graph allowance不同，因此不能把两行内存差全部归因于R。R14的精确缺口为3,960,951,553－3,932,684,288字节；这个失败只对应本轮配置，不能推出任何改法下R14都绝对不可能启动。

为什么选10K而不是12K？因为本轮追求的是经过负载验收的配方。12K仅完成启动，没有经过图片压力检查；它没有发生过实测OOM，也没有被证明稳定。 10K则是本轮满足余量门槛、且通过负载验证的最大已测R档位。R8仍保留为更宽松的回退选择。

## 8. 最终图片配对：从11分26秒到9.8秒

为避免早期图片尺寸、缓存状态与提问方式混杂，我们重新生成一组1024×1024 PNG：中央为红色矩形，各图片含不同标记；CPU与GPU收到完全相同的图像。单图请求与14图请求使用不同图像，避免单图测试预热批量图的媒体结果。

测试条件为temperature＝0、思考关闭、最多16个输出token，询问中央矩形的共同颜色。CPU一侧为R16K，GPU一侧为最终R10K；图片请求只有约1.1K或14.4K输入，不触发长文工作集重选。这是整套配置切换后的请求耗时对照，不是纯视觉encoder kernel微基准。

| 负载 | CPU视觉总耗时 | GPU视觉总耗时 | 加速倍数 | 耗时降低 |
| --- | --- | --- | --- | --- |
| 1张1024×1024图 | 47.842s | 0.944s | 50.68倍 | 98.03% |
| 14张不同1024×1024图 | 685.566s | 9.803s | 69.93倍 | 98.57% |

​

​

14图请求的平均耗时由48.969秒/图降到约0.700秒/图；GPU批量吞吐约1.43图/秒。CPU批量耗时接近逐图累加，说明在这类负载上，视觉移到GPU带来的收益远大于微调几K工作区。

两侧回答均为Red。CPU单图与14图的引擎prompt阶段分别为47.719秒、685.357秒；GPU分别为0.822秒、9.596秒。两侧最终回答都只有2个输出token，主要等待显然发生在输出之前。

不过，识别红色矩形只验证基本视觉路径与请求效率，不代表OCR、复杂图表或UI截图理解质量。每项只有一次配对观测，没有延迟分布或置信区间。早期10.378秒与本轮9.803秒来自不同图片和实验阶段，也不能宣称是进一步提速5.5%的严格A/B。

## 9. 10K工作区，会不会把输出卡在10K

我们分别在R4K、R8K和R10K配置下，发起不显式设置max_tokens​的短输入请求，要求输出编号句子：

| 工作区 | 实际输出 | 请求总耗时 | 引擎生成速度 | 结束方式 |
| --- | --- | --- | --- | --- |
| 4K | 7,392 token | 63.449s | 117.22 tok/s | 自然停止，编号到500 |
| 8K | 8,892 token | 75.630s | 118.21 tok/s | 自然停止，编号到600 |
| 10K | 11,892 token | 102.526s | 116.84 tok/s | 自然停止，编号到800 |

每项输入约64 token。输出超过对应R，直接证明R不是单次输出上限。但这些请求的总历史远小于B，不能证明它们经历了长历史压力下的工作集刷新，更不是262K输出耐久测试。

服务端默认最大输出设为262,144，也不保证模型一定写满。自然结束、客户端输出限制和上下文剩余空间依然有效。

## 10. 同文复验：16K降10K，到底损失了什么

为了隔离R的影响，两侧都使用CPU视觉，其余参数相同，B固定160K。使用一份全新的229,241-token输入，放置5个随机暗码，先要求返回JSON，再输出1,500行编号句子，最后重复JSON。

| 指标 | R16K | R10K |
| --- | --- | --- |
| 输入token | 229,241 | 229,241 |
| 初始暗码精确配对 | 5/5 | 5/5 |
| 客户端首个内容到达 | 456.353s | 459.011s |
| 实际输出token | 5,741 | 5,755 |
| 引擎生成速度 | 78.18 tok/s | 81.72 tok/s |
| 请求总耗时 | 529.891s | 529.548s |

这轮首字时间几乎相同，总耗时也接近。没有观察到10K降低初始召回或明显拖慢生成。

但实验还有一个不理想结果：两侧都在约384—385行时自然结束，没有完成1,500行，也没有末尾第二份暗码JSON。原始自动评分器的first/last字段此时实际上指向同一份JSON，不能据此声称“输出前后两次召回都通过”。

因为只生成约5.7K，这轮没有验证跨16K工作区边界。这个缺口必须补测，不能用“5/5捞针”遮过去。

## 11. 固定20,480-token压力输出：补上边界测试

补测使用165,173-token输入、相同B160K，两侧仍是CPU视觉以隔离R。请求临时启用ignore_eos=true​，固定输出上限20,480 token；正式服务的正常停止策略没有因此改变。

| 指标 | R16K | R10K |
| --- | --- | --- |
| 完成输出token | 20,480 | 20,480 |
| 结束原因 | length | length |
| 客户端首个内容到达 | 146.336s | 146.569s |
| 引擎生成阶段耗时 | 241.802s | 228.262s |
| 引擎生成速度 | 84.69 tok/s | 89.72 tok/s |
| 最长可见内容间隔 | 1.129s | 1.072s |
| 请求总耗时 | 390.378s | 374.896s |
| 结束后另发追问的暗码配对 | 5/5 | 5/5 |

两侧输入超过B、输出超过R，覆盖了追加压力下的工作集容量边界。没有观察到崩溃或OOM；本次10K生成阶段耗时反而少约5.60%。由于只有一次观测、生成内容与草稿接受率也可能不同，不能据此宣称缩小R必然提速。

这项测试同样有明确局限：强制忽略EOS之后，后半段产生大量空行。它是机械容量与稳定性负载，不是20K有效回答质量验收。

后续追问把输出文本重新分词，输入约176.8K，而不是原生成token序列对应的185.7K；两侧都命中165,172-token前缀缓存，5个BOUNDARY RECORD映射全部正确。可见内容间隔还受流式事件与输出形态影响，没有为每次选页单独打点，因此不能把约1秒停顿全部归因于KV刷新。

## 12. 最后再验一次：当前GPU配置的近满上下文召回

前面的R对照是CPU视觉环境，还不能直接充当最终GPU配置的满上下文验收。于是最终GPU视觉＋R10K使用另一组独立暗码，再做一次近满上下文测试。

| 项目 | 实测 |
| --- | --- |
| 实际输入 | 260,185 token，约占262,144上限的99.25% |
| 暗码位置 | 原始语料10%、30%、50%、75%、90% |
| 精确记录—暗码配对 | 5/5 |
| 客户端首个内容到达 | 542.149s |
| 引擎prompt阶段 | 541.887s |
| 请求总耗时 | 542.901s |
| 输出 | 94 token |
| prompt缓存命中 | 0，冷请求 |

这也是整篇文章最需要一起呈现的两面：接近256K的输入确实成功找回了全部5个指定记录，但一次冷请求的首字等待仍超过9分钟。 “能接收长上下文”与“长上下文交互很快”是两种不同的能力。

单次5针成功不能换算成丢针概率，也不能代替跨段综合推理、代码修改质量或长历史工具执行验收。

## 13. 最终配方：已测候选中的折中最优

| 参数 | 最终选择 |
| --- | --- |
| 逻辑上下文C | 262,144 |
| 历史选择预算B | 163,840，160K |
| 生成工作区R | 10,240，10K |
| KV格式 | rk4v4 |
| Host KV预算 | 12,288MiB |
| prefill | 256，启用fast prefill kernel |
| 视觉 | GPU resident，每图最多1,024 merged token |
| CUDA Graph allowance | 128MiB |
| 推测解码 | MTP，draft-tokens＝4，adaptive MTP |
| ngram | draft tokens＝31，min match＝12 |
| GDN state | FP16存储 |
| 历史保留 | sink＝12,288，recent＝1,024，均计入B |
| 检索策略 | LRFU λ＝0.5、top-frac＝0.9，GQA score aggregation＝max |
| 活动并发 / retained sessions | 1 / 1 |
| 默认思考强度 | xhigh，保留thinking，无显式服务端thinking budget |
| 默认最大输出 | 262,144，实际仍受请求及上下文剩余容量约束 |
| SSD tiering | 未启用 |

测试中的reasoning_effort=none​是为控制变量与耗时而逐请求设置，不是生产默认关闭思考。同理，测试请求的16、256、30,000或20,480输出上限都不是服务端永久配置。

这里的“最优”是带目标的：在本机已测候选中，优先保留160K历史、显著降低图片等待，同时获得一个通过负载检查的较大R。它不是全参数穷举结果，也不是已验证的代码修改质量最优解。用户后来反馈“代码修改欠考虑、需要反复纠正”，恰好说明这轮验收尚未覆盖真实软件工程质量，不能拿捞针成功替代。

## 14. 可复现的服务入口与回退

下面给出脱敏后的关键启动命令，保留实验使用的主要执行参数。模型和模板路径需要按实际部署替换；新机器必须重新检查容量，不能照抄后就视为验收通过。

```bash
/root/kvmem/build-ninfer/apps/ninfer-serve \
  /share/AI/ninfer-gsq/models/Swift-1.5-Qwen3.8-27B-GSQ-RCO-IQ3_S-mtp-vision.ninfer \

  --max-concurrency 1 --prefill-chunk 256 \
  --kvmem-budget 163840 --kvmem-gen-reserve 10240 \
  --kvmem-host-mib 12288 --kvmem-sessions 1 \
  --kvmem-sink-tokens 12288 --kvmem-recent-tokens 1024 \
  --kv-dtype rk4v4 --device-profile off \
  --spec mtp --draft-tokens 4 --adaptive-mtp \
```

原部署使用kvmem-ninfer.service​，配置位于/etc/systemd/system/​；设置Restart=on-failure​、RestartSec=15​，日志写入journal，并启用开机自启。最终Chat Completions、Responses和严格工具调用的基本检查通过：分别返回预期算术结果、READY及合法工具参数。它们验证接口连通和基本协议，不是业务正确性保证。

旧CPU视觉/R16K、GPU/R4K、GPU/R8K和更早后端的配置及恢复脚本均保留。切换或重启会清空进程内KV，下一次长文请求可能重新经历冷预填充，这也是部署验收的一部分。

服务器上的完整证据归档为/root/kvmem/artifacts/optimized-20261015-144404/​，另有同名tar.gz及SHA256。该原始归档包含私有服务配置，适合内部保存；本文附件仅选取测试数据、脚本与语料，不包含API密钥、SSH凭据或原始systemd unit。

## 15. 这次推导真正留下了什么

这轮调优没有找到一个能同时最大化所有指标的开关。它形成的是一条可检查的决策链：

降低prefill工作区成本 → 扫描可启动B → 用精确配对检验长文召回 → 保留160K历史 → 将视觉搬到GPU → 在R与Graph预算之间找余量 → 对最终配置补做近满上下文与接口检查。

实践中最容易误判的地方，也都出现在这条链上：把“启动成功”当稳定，把“字符串出现”当回答正确，把“NVML还剩显存”当可分配空间，把“输出超过R”当长历史刷新验收，再把“捞针通过”当代码推理能力。

最终配方值得保留的理由，是它在明确的约束下交付了可核验收益：160K历史选择预算、近满上下文5针成功，以及14图请求从11分26秒降到约9.8秒。尚未解决的问题同样明确：冷长文首字仍慢、通用丢针概率未知、复杂视觉与真实代码修改质量未建立配对证据、接近满文本同时叠加14图的混合负载未验收。

后续若继续优化质量，应该用真实代码修改任务比较KV精度、模型与执行流程；若继续优化速度，应分别测冷预填充、缓存续写、视觉编码和生成阶段。每次只让新的数据推动下一步选择。
