## 做了个 LLM 推理系统的可视化工具，拖滑块看 PD 分离、TTFT/TPOT 和 Roofline

做推理这段时间老碰到一个问题：大家嘴上都在聊 TTFT、TPOT、MFU、KV cache、PD 分离，可这些量之间到底怎么互相牵动，光靠一张架构图很难说清楚。

比如 QPS 拉高一点，TTFT 为什么先稳住、到某个点突然崩？命中率从 0 提到 0.9，prefill 时间为什么直接塌下去？decode 批次里多塞几个长上下文的请求，TPOT 为什么就线性往上爬？KV 池打满以后，系统靠什么把自己救回来？

这些东西讲公式一会儿就忘，翻源码又太劝退。所以我写了 InferFlux，一组能拖着参数玩的推理系统可视化页面，改一个值马上看到系统行为跟着变。

在线地址： [https://Abatom.github.io/inferflux/](https://abatom.github.io/inferflux/) （纯静态页面，打开就能用，不用装环境也没有后端。）

![](https://pic2.zhimg.com/v2-b6607d17b01836fb0df8cb6eb0db981b_r.jpg)

下面按三个页面分别说。

## 一、PD 分离模拟器：把 SGLang 的请求生命周期跑给你看

这是项目里最主要的一个页面，还原了 SGLang 的 Prefill/Decode 分离（PD-Disaggregation）请求生命周期。每个请求是一个小圆点，你能看着它从 client 出发，在 P 实例和 D 实例之间来回走。

### 请求怎么走的

```text
client → router（同时扇出到 P 和 D）
  P 实例：Tokenizer → 排队 → chunked prefill → KV 传输
  D 实例：Tokenizer → prealloc（握手 + 预分配）→ 排队
          → 拿到首 token → decode 循环（连续批处理）→ 流式返回
```

有意思的一点是 router 会用 `asyncio.gather` 同时往 P 和 D 发请求（对应 SGLang `mini_lb.py` 里的 bootstrap_room 配对），P 端算完 prefill 把 KV 传给 D 端，D 端从 metadata 拿到首 token 就进 decode 循环了。圆点的颜色对应 KVPoll 的几个状态：Bootstrapping 是琥珀色，WaitingForInput 灰色，Transferring 蓝色，Success 绿色，decoding 紫色。

### 指标是测出来的，不是套公式算的

这点我做的时候比较在意。TTFT、TPOT 不是拿闭式公式算的，而是从模拟里的事件时间戳测量出来的，跟你在真实系统里用日志时间戳算延时是一个道理。

TTFT 会拆成 7 段，每段对应引擎里一个真实的时间戳差：

```text
TTFT = tokenize + bootstrap 握手 + P 端排队 + prefill
     + 残余 KV 传输 + D 端 prealloc/排队 + detokenize
```

引擎按 5ms 一步推进模拟时钟，每个时长都实时读当前参数，所以你拖动滑块的改动会立刻作用到后面的事件，不用做什么事件取消。渲染跑在 requestAnimationFrame 上，跟模拟时间是分开的，可以 0.25× 到 64× 调速，也能暂停、单步、重置。

### 几个拖一下就能看到的反直觉现象

- chunked prefill 切得越小，TTFT 反而越低。因为算和传能更好地重叠，末块传输被压在了计算的尾巴后面。
- 命中率一拉高，prefill 和传输这两段直接塌下去。命中的前缀既不重算也不重传。
- KV 池打满以后，就算把 QPS 降下来，TPOT 也迟迟不回落。这就是真实 SGLang 里 retraction（抢占）和 new_token_ratio（自适应准入背压）要解决的问题。模拟器把这套自愈也还原了：KV 满的时候按「已吐 token 最少、prompt 最长」的顺序把请求弹出去，KV 丢掉但保留已经生成的 token，过会儿再重新入队。
- 混合注意力（比如 MiMo）为什么能便宜地撑起 1M 上下文。只有全注意力层的 KV 会随上下文涨，滑窗层（SWA）被窗口封住了。切一下模型预设，KV cell size 的差距一眼就看出来。

### 一个实际问题：TTFT 涨了，该扩 P 还是扩 D

这大概是模拟器最有用的地方。生产里 TTFT 一涨，不少人第一反应是「prefill 慢了，加 P 实例」，但这个判断经常是错的。

回到刚才那 7 段拆解，TTFT 里 P 和 D 的贡献都有：

- P 端：P 排队 + prefill 计算
- D 端：bootstrap 握手 + D-prealloc/排队

这里容易忽略的是，bootstrap 握手其实被 D 端的 KV 卡着。D 实例的 KV 池一紧张，P 端算完了 KV 也传不过去，请求就堵在握手那步等 D 腾地方。模拟器自检里这段差距大得吓人：D 宽松的时候握手 9.6ms，D 紧张的时候能飙到 32450ms。这种情况你再怎么加 P 都没用，堵点在 D。

所以排查顺序大概是这样：先看 TTFT 拆解里哪段在涨；如果是 P 排队或 prefill 占大头，那就扩 P；如果是 D-prealloc 或握手（被 D 的 KV 卡住）占大头，就该扩 D，这时候加 P 反而让 D 更堵。心里有数之后，直接拖 `# Prefill 实例` / `# Decode 实例` 的滑块，看 TTFT 是不是真降下来了，相当于买卡之前先在模拟器里试一把。

### 另一个问题：TPOT 涨了、吞吐上不去，是批太大还是 KV 在抢占

TPOT 和 TTFT 是两码事，排查思路也不一样。模拟器里 decode 每一步的耗时正比于当前批次里所有 running 请求的上下文长度之和（ `decodeStepMs ∝ Σ context` ），而且每 decode 一步，每个 running 请求的 KV 就多占 1 个 token。上下文越长、批次越大，每步就越慢。

所以 TPOT 涨一般是两种情况，模拟器能帮你分清楚：

一是批次自然变大变长。QPS 高、输出长，running batch 顶到 `max_running` ，Σcontext 大了每步自然慢。这算是健康的满载，解法是扩 D 或者提升单卡 decode 能力。

二是 KV 满了触发 retraction 抢占。KV 池打满之后，模拟器会按「已吐 token 最少、prompt 最长」把请求弹出去，丢掉 KV（生成的 token 留着），过会儿重新入队 re-prefill。这些被抢了又重算的请求会一直拖着延时，就是开头说的那个「QPS 降了 TPOT 还不回落」。页面上能看到红色的 retract 状态点闪， `new_token_ratio` 也会被抬上去做背压。

具体怎么摸：把 QPS 往上推，盯着 KV 利用率的 gauge 和 retract 有没有触发。如果 TPOT 高但 KV 没满、也没 retract，那就是批次和上下文本身大，扩 D 或者调 `max_running` 。如果 TPOT 高、KV 又打满、retract 还很频繁，说明 D 的 KV 不够，请求在反复抢占重算，这时候扩 D 或者把 `max_running` 降一点，并发压下来每步反而更快、整体更稳。想确认降 QPS 能不能恢复，就把 QPS 拖低，看 retract 停没停、TPOT 回没回来，这正好是 retraction 加 new_token_ratio 那套自愈在起作用。

吞吐（token/s）其实是 TTFT 和 TPOT 一起决定的，prefill 端喂不上、或者 decode 端消化不动，都会把吞吐压下来。把顶部的吞吐读数和排队深度（P 等待 / D 等待）对着看，哪边队列在堆，瓶颈就在哪边。

## 二、输入吞吐计算器：prefill 能跑多快，瓶颈在不在算力

第二个页面 `calc-input.html` 是纯公式计算器，不带模拟，专门看 prefill。填进去模型、GPU 型号、TP/DP/EP、输入长度、命中率、KV 显存占比，它实时给你算三样东西：理论峰值输入吞吐（tok/s）、单请求 prefill 时间（拆成 GEMM 和 Attention 两项）、KV 能装多少 token 以及最大并发请求数。

底子是 roofline 的那条计算屋顶。MFU（Model FLOPs Utilization）就是实际 FLOPs 除以硬件峰值 FLOPs，prefill 是计算瓶颈，所以：

```text
prefill 速度 = 峰值算力 × TP × MFU / (2 × 激活参数量)
```

有几个点我在页面里特意讲清楚了：

一是 MFU 为什么只算 GEMM。GPU 标称的 TFLOPS 是给 Tensor Core（矩阵乘）的，而 RMSNorm、激活、RoPE 这些非 GEMM 算子只能在 CUDA Core 上跑，算力只有 Tensor Core 的 1⁄16 到 1/32。它们不贡献 GEMM FLOPs，却照样吃墙钟时间，于是就被藏在了偏低的 MFU 数字里。实测 prefill 的 MFU 一般也就 0.3 到 0.5，到不了 0.9。

二是长上下文为什么会变慢。公式里那个 `2N` 只算权重矩阵乘，不含 attention。命中率高、prompt 长的时候，attention 的 O(query × KV长度) 会变成主项。你在页面里把命中率从 0 拉到 0.9，单请求 prefill 时间明显往上走。

三是 TP / DP / EP 各管什么，这三个很容易混。TP 同时放大算力和显存预算；DP 只增加并发副本数；EP 只进显存预算，不改单 token 的算力（专家分散并不改变每个 token 实际过的浮点运算量）。把这三个轴当成一回事是很常见的坑。

我自己用得最多的是 MFU 反推：把实测吞吐填进去，它反推出真实 MFU 和 prefill 利用率。如果反推出来的 MFU 远低于 0.3，基本能断定瓶颈不在 prefill 算力，而在 decode、KV 传输或者排队，这样就知道该去优化哪一层了。

## 三、输出吞吐计算器：decode 看的是带宽，不是算力

第三个页面 `calc-output.html` 对应 decode。decode 时 batch 小，GEMM 退化成矩阵-向量乘，算术强度极低，基本就是显存带宽瓶颈：每一步都要把整个激活权重从 HBM 读一遍，只为了算一个 token。这时候看 MFU 没意义（会低到 0.05 到 0.15），要看 MBU（Memory Bandwidth Utilization，显存带宽利用率）。

```text
decode 每步 GEMM 时间 = 权重字节数 / (峰值带宽 × MBU)
TPOT（每 token 延时）= decode step 时间 / 有效 token 数
```

页面里还有 MTP（多 token 预测）之类的参数，能看到草稿 token 的接受率怎么摊薄 TPOT，也能反过来用实测 TPOT 推真实 MBU。

roofline 两条屋顶记起来其实很简单：prefill 看 MFU（计算瓶颈），decode 看 MBU（带宽瓶颈）。FlashAttention 之所以「快」但 FLOPs 没变，就是因为它省的是显存 IO，提升的是 MBU 那一侧。

## 四、几个设计上的取舍

为什么做成单文件、零依赖的静态页面？每个页面就是一个自包含的 HTML（CSS、DOM、JS 全塞在里面），拷一个文件走就能用，能离线打开，也能随手改。我不太想让「先装个环境」挡在理解一个概念前面。

为什么用事件驱动而不是直接套公式？闭式公式（比如直接上 Little’s law）会把排队、抢占、流水线重叠这些真正有意思的动态给盖掉。让模拟器实打实跑一遍、从时间戳测量，你才能看到 QPS 逼近临界点时 TTFT 那个非线性的崩，也才能看到 retraction 触发的那一下。

可信度怎么保证？PD 分离模拟器带了一套 headless 自检（浏览器控制台跑 `runSelfTest()` ，或者用 node 跑），21 项不变量检查，覆盖了 Little’s law（L ≈ λW）、token 守恒、KV 池不超限、带宽减半传输翻倍、命中率到 100% 时 prefill 塌缩、小 chunk 降 TTFT、SWA 窗口封顶这些。改代码的时候靠它兜底，物理行为不至于跑偏。
