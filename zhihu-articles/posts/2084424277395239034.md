2020–2026：从数据并行复制到多维并行组合

## 大模型训练中的状态分片

一张GPU卡要同时放下三份东西：参数、梯度、Adam 状态。分布式数据并行（DDP）把这三份在每张卡上各复制一份；前向、反向本地算完，只对梯度做 AllReduce，再各自更新。

模型比卡大，复制参数、梯度、Adam状态的切分就要有讲究了：

1. 状态还要不要复制？（ZeRO / FSDP）<br>2. 一层算子本身能不能切开？（Megatron TP / PP）<br>3. 激活和超长序列怎么办？（SP / CP / Ulysses / Ring Attention）

全分片数据并行（FSDP）和零冗余优化（ZeRO）是第一种方式：把三份切到多卡，用 All-Gather / Reduce-Scatter 换回计算所需的完整切片。2020 到现在，语义没怎么变化——三份状态从每卡一份，改成多卡拼一份。变的是切什么、用什么原语切、能不能和张量并行、流水线、长序列、编译叠在同一张 `DeviceMesh` 上。

## 训练状态的显存构成：$2\Psi+2\Psi+12\Psi$

设可训练参数量为 $\Psi$。混合精度训练中，常见的状态显存预算如下：

• 参数 FP16 / BF16：约 $2\Psi$ 字节<br>• 梯度：约 $2\Psi$<br>• Adam：FP32 主权重 + 动量 + 方差，约 $12\Psi$

$2\Psi + 2\Psi + 12\Psi\\$

DDP 每张卡都存完整三份。ZeRO-3 / FSDP 默认把模型状态体积降到约 $1/N$。后面所有切分都围绕这些展开。

![](https://pic3.zhimg.com/v2-ae67c89dcd491d0b04d79fc36073796a_r.jpg)
*图1 DDP and ZeRO*

DDP 每卡复制 $2+2+12$；ZeRO-1/2/3 逐级切开，体积减小到 $(2+2+12)\Psi/N$。示例是使用 4 张卡。

## 模型状态、激活与计算图并行

FSDP 主要**分片**模型参数和相关状态，对应分布式训练的**切分方式**之一。预训练大模型还涉及另外两类切分方向：

| 切分方向 | 具体对象 | 典型方案 |
| --- | --- | --- |
| 模型状态 | 参数 / 梯度 / 优化器 | FSDP / ZeRO / Offload |
| 激活 | 序列长度、层间驻留 | SP、CP、Ulysses、Ring |
| 计算图结构 | 宽/深（参数）、专家路由 | TP（张量并行）、PP（流水线并行）、EP（专家并行） |

**切计算图**其实往往还是落实到参数怎么拆，比如张量并行切层宽，流水线切层深，专家并行切 Mixture-of-Experts 的路由与参数。三类方案可以叠加，用在一张 `DeviceMesh` 上。

`DeviceMesh` 是一张逻辑设备网格：每个点一块卡，每条轴一种切法。1D 只切状态（FSDP / ZeRO）；2D 常见是「节点内 shard、节点间 replicate」（HSDP）或 FSDP $\times$ TP；3D 才是 TP $\times$ PP $\times$ DP。维数需要与通信需求匹配，每增加一维就增加一类通信。PyTorch 和 Megatron-Core 都把并行策略放在同一张 mesh 上，统一管理进程组。

早期 FSDP 通常与 TP、PP 等经典模型并行区分。到 2025 年，生产预训练已经组合使用FSDP/ZeRO 与 TP/PP/CP。

## FSDP unit 的参数生命周期与集合通信

FSDP unit 是进行分片管理的一层或一组层。参数沿分片维度切分后，每张卡只保留其中一段。例如，$W$ 可切成 $W0$–$W3$，分别驻留在四张卡上。

算子要整块权重。四条碎片做一次 All-Gather，临时拼回完整的 $W$。算完可以丢掉整块，只留碎片。反向再收集一次。梯度做 Reduce-Scatter，每张卡拿回自己那一片，交给 Adam。

![](https://pic1.zhimg.com/v2-925d38afb17b37a61408754ff36bcab4_r.jpg)
*图5 AG and RS*

All-Gather 拼回 $W$；用完释放完整参数。反向再收集一次，梯度 Reduce-Scatter。状态体积约为 $1/N$。

前向后要不要丢掉整块，看 `reshard_after_forward`：

• `True`：对齐 ZeRO-3，省显存，反向多一次 All-Gather<br>• `False`：对齐 ZeRO-2，省一次通信，多占一份参数

![](https://pic2.zhimg.com/v2-53123982e12ef489c7dc334373def14f_r.jpg)
*图6  reshard*

上排 `reshard=True`（ZeRO-3）：前向后只保留本地分片。下排 `reshard=False`（ZeRO-2）：完整 $W$ 保留在卡上。

2024 以后的接口中心是网格维数和这个开关，`ShardingStrategy` 枚举不再是主要抽象。

HSDP / MiCS：节点内 shard、节点间 replicate，跨机只做 AllReduce，避免全局 All-Gather。张量并行沿隐藏维切开，落在 `DeviceMesh` 的 `tp` 维。它和 FSDP 的 DP-Shard 方向不同，属于独立的并行维度。这两种切分见后边图14、图15。

## 2019–2022：状态分片与算子并行分别成形

![](https://pic1.zhimg.com/v2-c2e97f6e9b0e058c79830517be86489c_r.jpg)
*图7 总体演进时间表*

2019–2026：从切状态，到切计算图，再到可组合默认栈。

### **2019–2020**

ZeRO 把数据并行里的冗余拆成三级：

| 级别 | 切什么 | 通信 | 后来的别名 |
| --- | --- | --- | --- |
| ZeRO-1 | 优化器状态 | 更新后广播 / Reduce-Scatter | FSDP SHARD_GRAD_OP 的一半 |
| ZeRO-2 | + 梯度 | Reduce-Scatter | reshard_after_forward=False |
| ZeRO-3 | + 参数 | 用前 All-Gather，用后丢掉 | FULL_SHARD / FSDP2 默认 |

相对数据并行，ZeRO-3 把模型状态内存降到约 $1/N$，并演示到万亿参数量级。

Megatron-LM 走另一条路了：不切 Adam，把 $W \in \mathbb{R}^{d_\text{in} \times d_\text{out}}$ 按 $d_\text{out}/N$ 竖切开。每张卡计算 $X W_i$，再 AllReduce 拼回。单层算力利用率高，但需要改动模型代码。

PyTorch DDP 的系统实现包含梯度分桶、计算与通信重叠、`ProcessGroup`。FSDP 后来的 prefetch / bucket 建立在这套集合通信机制上。

DeepSpeed 是 ZeRO 的工业实现：JSON 打开 ZeRO-1/2/3，几乎不改模型。预训练里它负责切状态，Megatron 负责切算子，两条线叠成 3D。

这一阶段的代码现实：DeepSpeed 配置驱动；Megatron-LM 是 TP（以及随后的 PP）参考实现；PyTorch 核心只有 DDP，还没有 FSDP。

### **2021**

三个事儿同时落地。ZeRO-Offload 把 Adam（和部分梯度）卸到 CPU，支持单卡训练 130 亿参数模型；ZeRO-Infinity 再把参数卸到 CPU / NVMe，在 512$\times$V100 上超过 25 PFLOPS、峰值 40%。

![](https://pica.zhimg.com/v2-4999ee70499335595bb9cca918a3cdcc_r.jpg)
*图8 offload*

Megatron 变成 3D：TP × PP × DP，面向当时的 GPU 集群训练千亿到万亿参数模型。**3D parallelism** 的系统化实践由此形成。

FairScale FSDP 开源，语义对齐 ZeRO-3。对 FSDP unit All-Gather 参数 → 前向/反向 → Reduce-Scatter 梯度。FairScale 是 PyTorch 上游之前的实现。

![](https://pic4.zhimg.com/v2-42216f8474f52292ca86c0faccd5340f_r.jpg)
*图9 2021 三路*

### **2022**

PyTorch 1.11 将 FairScale FSDP 合并进了主线。DDP 要求整个模型能够放入一张显卡，而 FSDP 通过参数分片打破了这个限制。

这次合并的核心设计是 **FlatParameter**：将一个 wrap 单元内的 $W$、$b$、LN 等参数先拼接成一根长向量，再按 rank 切分。这样在 eager 模式下便于分桶和通信重叠。但缺点是冻结参数、混合精度、state_dict 以及与 TP 组合时都比较麻烦——这也直接促成 2024 年切换到 DTensor + DeviceMesh。

![](https://pic3.zhimg.com/v2-b1232fcd045e61d70f69fd65a2e6b01e_r.jpg)
*图10  FlatParameter*

顺序：1 wrap 的 $W$ / $b$ / LN → 2 flatten 成长条 → 3 shard 成 $W0$–$W3$ → 4 All-Gather 拼回 $W$ → 5 Reduce-Scatter 得到 $g0$–$g3$。冻参、dtype、state_dict、TP 别扭。FSDP2 换成 DTensor + DeviceMesh。

NVIDIA 侧补上激活：TP 已经切了 GEMM，但 LayerNorm / Dropout 的激活还是按完整序列复制。Sequence Parallelism 沿序列维切开这两个关键位置，几乎不增加通信量。Megatron-Core 里是 `--sequence-parallel`，且 **TP>1** 才能开。

Megatron-Turing NLG 530B 在 Megatron 的 TP / PP 基础上叠加了 DeepSpeed ZeRO。

![](https://pic4.zhimg.com/v2-a136a9ca24b91fabe333d06458ee5c41_r.jpg)
*图11 Megatron切分*

MiCS：节点内进行 shard，节点间进行 replicate，跨节点只需要执行 AllReduce，不再需要全局 All-Gather。后来的 HSDP、`HYBRID_SHARD` 和二维 `DeviceMesh` 都延续了这种结构。

![](https://pic4.zhimg.com/v2-f78054191ff255f4c8ba3db1d1178969_r.jpg)
*图12 MiCS*

## 2023–2024：从 FlatParameter 迁移到 DTensor

生产环境中的关键问题包括 wrapping、prefetch、混合精度，以及与 autograd 的衔接；前向和反向各需要执行一次 All-Gather。实验范围涵盖了从 T5-611M 到 T5-11B，以及 minGPT-175B；11B 这种 DDP 装不下的大模型，也可以用 FSDP 进行训练。

这一代 FSDP1 的局限性也很明确：小模型不太适用，BF16 需要 Ampere 架构，冻结参数或部分微调使用起来不够顺畅，默认的 auto wrap 通信策略也不是最优。FSDP2 解决了后三个问题；但“小于约 $10^{8}$ 参数、单卡能放下的模型，还是优先考虑用 DDP 或 checkpoint”。

ZeRO++ 优化了通信体积：通过量化 All-Gather、节点内权重副本（hpZ）以及量化梯度，通信量大约降低了 $4\times$。在 384 块 GPU 上最高实现 $2.16\times$ 吞吐提升。FSDP2 的 `reshard_after_forward: int`（例如 8）参数与 hpZ 相对应。

Ulysses 沿序列维进行切分，attention 利用 all-to-all 通信在序列维和头维间交换数据，并与 ZeRO-3 结合进行状态切分。Ring Attention 采用环形通信传递 KV，后被 NVIDIA 命名为 Context Parallel。CP（Context Parallel）切分整个输入及几乎所有激活，SP（Sequence Parallel）只切分 LayerNorm 和 Dropout，他俩使用范围不同。

同时，PyTorch 内部推出了 DTensor + DeviceMesh：用 n 维网格来描述集群结构，并通过 `Shard`、`Replicate`、`Partial` 等方式来表达逻辑张量的分布。FSDP2 的参数形式也从 FlatParameter 变为在 dim-0 维度上的 `DTensor`。

**FSDP2** 删掉 FlatParameter，改成：

```text
fully_shard(module, mesh=..., reshard_after_forward=True)
```

`fully_shard` 通过 `@contract` 给模块挂状态，并动态更换类。参数名称保持不变，优化器和 grad clip 能直接访问到 `DTensor`。移除了 `auto_wrap_policy`、`use_orig_params`、`limit_all_gathers` 等参数。在 meta device 上，先进行 shard，然后再 `to_empty`，权重由用户自定义的 `init_weights` 填充。

8×H100 跑 Llama-7B 时，相比 FSDP1，峰值显存降低约 7%，loss 结果保持一致。

Megatron-FSDP 的 `DeviceMesh` 结构为 `dp_outer × dp_shard × cp × tp`（EP 使用辅助网格）。同一 `(TP)` 行上的 DP0–DP3 组成一个 FSDP 组，张量并行对应另一维度。

TorchTitan 是 PyTorch 官方提供的预训练参考实现，集成了 FSDP2、TP、PP 和 CP，并默认启用 `torch.compile`、Float8 和 DCP。主程序入口是 `torchtitan/train.py`，并行策略实现在 `models/llama3/parallelize.py`，参数对应关系是在 `docs/fsdp.md`。

**SimpleFSDP** 将传统 FSDP 的语义重构为 `DTensor.redistribute`、参数重参数化（parametrization）、选择性激活检查点（selective activation checkpoint），使`torch.compile` 能够识别和优化覆盖“计算 + 通信”的完整计算图，支持端到端的编译级优化。在 Llama 3（包括 405B）等模型上，和 eager FSDP2 相比，SimpleFSDP 峰值显存最多降低了 28.54%，吞吐量最高提升 68.67%。

PyTorch 的编译流程可以分为三步：首先由 Compiled Autograd 捕获反向计算图，其次 Compiled FSDP 会把 All-Gather 和 Reduce-Scatter 操作保留在计算图中，最后 Compiled FSDP2 进一步完成自动分桶（auto-bucketing）。FSDP2 还特别设计为允许编译器灵活改写通信组。

MegaScale：字节用超过 1 万张 GPU 训练 175B 模型，MFU 达到 55.2%，效率比 Megatron-LM 高 $1.34\times$。在万卡规模下，效率瓶颈还包括系统稳定性、可观测性和跨层通信重叠等问题。

NVIDIA 方面，把深度学习相关库分成了三块：底层的 Megatron-Core 负责分布式核心、TransformerEngine 主要做高性能 Transformer 算子和混合精度、NeMo 是大模型训练与应用框架。对于来说，主流的微调和训练工具链都已支持最新的 FSDP 体系：

• `torchtune`：开箱即用，直接用 PyTorch 的 `fully_shard`（FSDP2）接口实现大模型分片和高效训练。<br>• Axolotl：通过 YAML 配置文件，灵活选择 FSDP（PyTorch 原生）或 DeepSpeed 作为分布式训练后端，可以根据硬件和场景权衡切换。<br>• Accelerate： HuggingFace 的训练/微调引擎，同时兼容 FSDP1 和 FSDP2 两种模式（FSDP2 需要 PyTorch 2.6 以上版本），满足对不同分片策略和兼容性的需求。

整体结构是：NVIDIA 负责底层库的拆分与高性能实现，主流用户工具则提供选择和集成各类分片/分布式方案的能力，基本都已覆盖 FSDP2 的主路线。

### **2025–2026：同一套 `fully_shard`，两种底层**

FSDP2 沿 dim-0 对每个参数进行切分，支持参数冻结、FP8 All-Gather，以及无需通信的 sharded state dict，并为 `torch.compile` 后续改写通信组预留空间。当前的性能瓶颈在于集合通信前后需要额外的 COPY 操作，Meta 通过自定义 copy kernel 来降低这部分开销。在 8$\times$H100 上训练 Llama-7B 时，FSDP2 相比 FSDP1 的峰值显存降低了约 7%。

Megatron-FSDP 对外还是 `fully_shard`，内部采用模块级连续缓冲：把一个 FSDP unit 里的参数放进一条 persistent communication buffer，参数只是这条缓冲上的切片视图。通信直接使用 NCCL user buffer，端到端零 COPY。FSDP2 需要在参数与通信缓冲之间复制；Megatron-FSDP 把连续缓冲的视图直接赋给 unit 内的参数。

![](https://pic3.zhimg.com/v2-b84b88b2e3b11073c3340e1d5098d8e4_r.jpg)
*图16 同一套 fully_shard，分片结构不同*

左：FSDP2 把 Linear1/2/3 各自均匀切到 Rank0/1，再 permute 进按参数形状的模块通信缓冲。右：Megatron-FSDP 把模块参数摊平后按 DP 均匀切开，参数是这条缓冲上的非均匀视图。

这就带来了三项 FSDP2 特意没做的几个改动：

1. **更少的 NCCL 调用。** 只有当 unit 的 dtype 或拓扑结构不同，才会额外发起一次 collective。<br>2. **dim-0 连续且按 LCM 对齐。** 分片边界不会切开量化块，这样 MXFP8 / NVFP4 的 block scale 才有意义。<br>3. **硬件卸载。** 在用 NCCL user buffer 和对称内存后，NVLink-SHARP / IB-SHARP 能把 All-Gather / Reduce-Scatter 对 SM 的占用从大约 16–32 降低到 1–6；NCCL 2.28+ 还可以用 copy engine 执行 All-Gather，把 SM 空出来给 GEMM 用。

![](https://pic4.zhimg.com/v2-af770fb038d49337977f34ee3f6c596d_r.jpg)
*图17 反向一层*

上：FSDP2 每次 All-Gather / Reduce-Scatter 都走 `CUDACachingAllocator`（`torch.empty`）建临时缓冲。下：Megatron-FSDP 训练开始时预分配双缓冲，集合通信轮流复用，参数是视图。

当与 TP / EP 叠加使用时，FSDP 通常在最后进行分片：即先完成算子维度的切分，FSDP 只在计算前后进行 unshard / reshard 操作。Llama 3.1 405B 的官方 Megatron 配方还是采用 TP $\times$ PP $\times$ CP 的组合；Megatron-FSDP 则可以作为 DP 的另一种实现方式。

异构内存走另一条线。SuperOffload 针对 GH200 / GB200 / MI300A 的 C2C，让 CPU Adam 与 GPU 计算重叠，相对旧 offload 大概 $2.5\times$ 吞吐；Ulysses 变体在 $8\times$GH200 上把 13B 推到大概百万 token、MFU 55% 左右。

## 并行策略选型

小于约 $10^{8}$ 参数、单卡显存足够：首选 DDP（数据并行），理由是实现简单、运维成熟、PyTorch 原生支持好，无需额外参数切分和通信优化，代码改动成本极低。同时可按需加 activation checkpointing 减少显存压力，适合学术/快速迭代。FSDP 对小模型增加分布式开销，没有显著收益，建议别用。

超大模型预训练：使用 1D FSDP 或 ZeRO-3 做参数状态分片，跨节点 All-Gather 推荐采用 HSDP 或 MiCS，节点内做 shard、节点间执行 AllReduce。层宽选择 TP，层深使用 PP，超长序列建议用 CP 或 Ulysses，不建议把 SP 当作 CP。对于同一套 `fully_shard`：如果需要参数冻结、无需通信的 checkpoint，并和 `torch.compile` 协作，建议选用 PyTorch FSDP2；如果需要零 COPY、FP8 参数 All-Gather，以及 NCCL user buffer / SHARP 支持，则可选择 Megatron-FSDP。

微调：技术演进导致主流微调框可直接用 `fully_shard`（FSDP），如 torchtune, Accelerate 已原生适配。推荐在 YAML（Axolotl）里灵活切换 FSDP 或 DeepSpeed，可适用不同硬件、团队有历史（如混用 checkpoint, optimizer 格式）时注意优先方案对齐，避免分布式和恢复的兼容性风险。

单机或异构内存场景：PCIe 服务器推荐使用 ZeRO-Offload 或 Infinity，GH200 / GB200 推荐采用 SuperOffload。这两类带宽的数据不能直接和 PCIe offload 做对比。异构内存相关的两种主流方案，建议沿用现有已发表路线，不要额外开发还没合入 PyTorch 主线的 CXL API。

状态分片、算子并行，以及 TP / PP / CP 在同一张 mesh 上的组合，应该根据模型体积、集群带宽和团队熟悉的技术栈来选择。
