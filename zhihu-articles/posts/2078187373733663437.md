这很说明问题：大体量 App 不会把「改个标题」「客服先分流」「弱网答一句」全部打到云端大模型上。更现实的路径是——

**小模型静默下到手机，简单请求本地算；难的、要查库的、要工具调用的，再上云。**

顺着这条线，算一笔「端侧挡住一部分云调用」的账，再给出可跑的 Android Sample（llama.cpp + GGUF，推荐 Qwen2.5 0.5B Instruct）。

## 开源声明里出现千问，意味着什么

内置或分发了第三方模型权重 / 推理运行时，应用通常要在「开源软件声明」里保留版权与协议信息。能写进声明的，往往不是概念 Demo，而是已经进包、或会随包下发的组件。

Qwen 的 **0.5B / 1.5B Instruct** 体积可控（Q4 量化大约几百 MB），适合：

- 意图分类、FAQ 初筛、短文案润色
- 弱网、飞行模式下的降级体验
- 「内容先不出设备」的隐私诉求

对头条这类产品，关键问题很少是「端侧能不能打过 GPT‑4」，而是：

> 延迟和功耗可接受的前提下，小模型能不能稳定挡住三成到八成的简单请求。

挡得住，云账单才有意义；挡不住，下载包和工程成本就是沉没成本。

## 静默下载 + 端云分层

生产里常见链路是这样的：

```text
安装 / 升级
   → 仅 Wi‑Fi（或充电 + 空闲）后台拉取 model.gguf
   → SHA256 + 版本校验，写入本地 Model Pack
   → 场景分流：
        · AI 客服入口 → 端侧意图 / FAQ
        · 短润色     → 端侧限长生成
        · 复杂投诉   → 升级云端大模型 + 业务系统
```

不是要在手机上跑 72B，而是把请求切成两层：

- 层级 | 模型量级 | 干什么 | 钱花在哪
- 端侧 L0 | 0.5B～1.5B GGUF | 分类、模板答、短生成 | 几乎无按次云费，摊销 CDN / 电量
- 云端 L1 | 更大模型 / 闭源 API | 难例、长上下文、工具调用 | 按 token 计费

### 用 AI 客服估一笔数量级

用一组假设对齐量级——不是任何一家公司的真实账单，数字可调，公式不变。

假设某内容 App：

- 日活 1 亿
- 每天约 3% 用户点 1 次「智能客服 / 帮助中心」
- 每次平均 800 tokens（含 system、历史、回复）
- 云端小模型综合价按 **¥1 / 百万 tokens**（便宜托管价常在「角～元 / 百万 token」，以合同为准）

推算：

```text
日请求 ≈ 1e8 × 3% = 300 万次
日 token ≈ 300 万 × 800 ≈ 24 亿 ≈ 2400 M tokens
日云费 ≈ 2400 × ¥1 = ¥2,400
年云费 ≈ ¥2,400 × 365 ≈ ¥88 万
```

若端侧能稳定承接 **60%** 简单咨询（账号常见问题、功能入口、话术模板），则：

```text
年可省云费用量级 ≈ 88 万 × 60% ≈ ¥50 万上下
```

把触发率、次均 token、单价再抬一档（例如 8% 触发、1500 tokens、¥2 / 百万），同一公式会落到 **数百万 / 年** 的量级。线性关系很清楚：

**可省费用 ≈ DAU × 触发率 × 次均 token × 云单价 × 端侧分流率**

ROI 看的是分流率，不是榜单名次。同时还要扣掉另一本账：模型包 CDN、包体与灰度、中低端机功耗、ANR（应用无响应）、崩溃。只算 API、不算工程，账是假的。

不适合硬上端侧的情况也很明确：要实时查库存 / 定责的纠纷、上下文经常超过两三 K、必须统一审计与风控——这些仍应云端 + 业务系统，端侧最多做初筛。

## Sample：android-local-agent

我们把「手机上跑 Qwen 小模型聊天」做成可开源复现的 Android Sample。

- 项 | 选择 | 为什么
- 格式 | GGUF（不要直接丢 safetensors） | 易内存映射加载，量化生态成熟
- 推荐模型 | Qwen2.5-0.5B-Instruct Q4 | 约 0.4GB，手机可加载
- 推理 | llama.cpp（`llama-android`） | 任意 Instruct GGUF 走文件系统
- UI | planet-components（Java View） | 与技趣星球组件栈一致
- 隐私默认 | 无 INTERNET；对话不落盘 | 演示「数据可留在本机」

仓库：[https://github.com/techskillplanet/android-local-agent](https://github.com/techskillplanet/android-local-agent)

模拟器里连续点了 3 个快捷提问，全部本地回复：

分层很简单：

```text
MainActivity（壳 + 对话三态）
  → ChatController（单线程串行 load / generate）
    → GgufLlamaEngine + ModelFileStore
      → LlamaModel.generateChat（流式 token）
```

产品里的「静默下载」，在 Sample 里先简化为 **系统文件选择器（SAF）选文件 / adb 指定路径**。上线时只要把输入换成「已下载的版本化目录」，推理层不用动。

## 关键代码

**加载：CPU、优先可复现。** Sample 固定 `setGpuLayers(0)`，真机和 x86 模拟器都能跑通；开源先保证别人能复现，再谈峰值 tok/s。

```text
ModelParameters mp = new ModelParameters()
        .setModel(modelPath)
        .setCtxSize(settings.contextSize)
        .setGpuLayers(0);model = new LlamaModel(mp);
```

**生成：走 chat template**，让 Qwen Instruct 的 role 格式生效。

```text
InferenceParameters ip = new InferenceParameters("")
        .setTemperature(settings.temperature)
        .setNPredict(settings.maxTokens)
        .setNThreads(settings.threads)
        .withMessages(chatMessages);for (LlamaOutput out : model.generateChat(ip)) {
    listener.onToken(out.toString());
}
```

**线程：磁盘与 llama.cpp 进单线程 Executor，回调回主线程**——避免并发 load，也避免卡 UI。

对话区三态：未加载显示「选择 GGUF」；加载后去掉选模大卡，只留「可以开始聊天了」；有消息后进气泡。快捷提问在对话中保持可见，方便连续点。

扩到静默下载时，目录大致是：

```text
files/models/qwen25-0.5b-q4/model.gguf
files/models/qwen25-0.5b-q4/manifest.json   # version / sha256 / minApp
```

下载器管 Wi‑Fi、断点、校验、灰度；`loadModelFromPath(manifest.path)` 复用同一套 Engine。

## 怎么跑

```text
git clone https://github.com/techskillplanet/android-local-agent.git
cd android-local-agent
配置 local.properties 里的 sdk.dir
./gradlew :app:assembleDebug
```

模型请用 **Instruct 的 GGUF**（例如 `Qwen/Qwen2.5-0.5B-Instruct-GGUF`），不要用原始的 `model.safetensors`——llama.cpp 只认 GGUF。App 内点「选择 GGUF」即可；自动化可以：

```text
adb shell am start -n com.skillplanet.localagent/.MainActivity \
  --es com.skillplanet.localagent.MODEL_PATH /data/local/tmp/qwen.gguf
```

## 小结：端侧小模型该不该上

- 开源声明里的千问，是「端侧小模型已进大体量 App」的公开信号，而不只是云端 API。
- 省钱看 **分流率**：客服、帮助中心、短润色这类高频短请求，最适合 0.5B～1.5B。
- 亿级 DAU × 几个点的日触发，一年简单请求的云费用差，数量级常在 **数十万到数百万**（随单价和 token 长度线性变）。
- 工程上先打通 GGUF + llama.cpp + 对话状态机，再接静默下载和云端升级。Sample 已开源，可直接二次开发。

如果要在自己项目里试，最低成本路径：clone 仓库 → 模拟器跑通 → 换一个 1.5B Instruct GGUF → 压测延迟和功耗 → 再决定要不要接静默下载。
