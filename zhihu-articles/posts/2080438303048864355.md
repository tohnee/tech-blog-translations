谈到 InfiniBand（IB），经常会听到“原生无损”“低时延”“高性能 RDMA”等描述。但“无损”究竟来自哪里？是交换机缓存足够大，还是网卡能够快速重传？既然使用了 Credit，为什么还需要拥塞控制？

理解 IB，关键是把三个问题分开：**下一跳有没有空间接收、源端应该以多快的速度发送，以及数据最终是否被可靠交付。** 它们分别由链路流控、拥塞控制和可靠传输解决，而不是某一个机制包办全部。 [1](https://infinibandta.org/ibta-specification/)[2](https://www.ieee802.org/1/files/public/docs2014/new-dcb-crupnicoff-ibcreditstutorial-0314.pdf)[6](https://network.nvidia.com/pdf/whitepapers/deploying_qos_wp_10_19_2005.pdf)

本文以经典 IB 协议机制和常见 Fat-Tree 组网为主；涉及新一代硬件或厂商增强功能时，另行说明其适用边界。

## 一、“无损”不等于“任何情况下都不丢包”

IB 的原生无损，主要指：**在协议正常运行、资源配置正确的前提下，受 Credit 流控保护的数据链路不会因为接收缓存溢出而丢包。**

![](https://picx.zhimg.com/v2-6073dbaba0fad3d9bd0677e899e207d1_1440w.jpg)

这并不排除物理误码、链路故障、无效报文、分区检查失败，以及报文等待时间超过限制等情况。NVIDIA 的 IB 管理文档明确列出了接收错误、发送丢弃和队首等待时间等相关机制。因此，“IB 没有丢包计数器”或“IB 永远不需要重传”都不正确。 [14](https://networking-docs.nvidia.com/ufmenterpriseum/6221/appendix-supported-port-counters-and-events)[15](https://networking-docs.nvidia.com/ufmsdnappswum/41815/subnet-manager-tab)

![](https://pic4.zhimg.com/v2-1d140a3bd3e74e4953aee8da59d8f913_1440w.jpg)

可以先建立如下分工：

| 机制 | 主要作用范围 | 解决的问题 |
| --- | --- | --- |
| Credit 链路流控 | 相邻端口之间，按数据 VL 管理 | 下一跳缓存是否装得下 |
| 拥塞控制 | 交换机反馈、端点调节 | 源端是否发得过快 |
| RC 可靠传输 | 端到端 QP | 数据是否按协议可靠交付 |
| 路由与拓扑设计 | 整个 Fabric | 数据如何到达目的端，并避免不合理的资源依赖 |

**无损解决的是缓存安全，可靠传输解决的是交付语义，高性能还需要合理的路由、带宽与拥塞管理。**[2](https://www.ieee802.org/1/files/public/docs2014/new-dcb-crupnicoff-ibcreditstutorial-0314.pdf)[6](https://network.nvidia.com/pdf/whitepapers/deploying_qos_wp_10_19_2005.pdf)[7](https://networking-docs.nvidia.com/mlnxofedswum/24.10-5.1.6.1lts/nvidia-sm)[13](https://networking-docs.nvidia.com/doca/archive/3-5-0/enhanced-connection-establishment)

## 二、Credit 的本质：先获得缓存额度，再发送数据

### 2.1 接收端不是只指最终目的服务器

假设路径如下：

```text
HCA A ───── Switch 1 ───── Switch 2 ───── HCA B

```

这里，HCA 是 Host Channel Adapter，即主机接入 IB 的适配器。

对于 A 发往 B 的数据，每一跳都有独立的接收方：Switch 1 接收 HCA A 的数据，Switch 2 接收 Switch 1 的数据，HCA B 接收 Switch 2 的数据。

```text
数据方向：
HCA A ───────► Switch 1 ───────► Switch 2 ───────► HCA B

对应的 Credit 通告方向：
HCA A ◄─────── Switch 1 ◄─────── Switch 2 ◄─────── HCA B

```

反向数据传输也有自己独立的 Credit 状态。因此，IB 的底层无损机制是 **Hop-by-Hop，逐跳流控**，而不是“最终接收服务器统一给整个路径发额度”。Credit 在这里更适合理解为“缓存额度”，而不是金融意义上的“信用证”。 [2](https://www.ieee802.org/1/files/public/docs2014/new-dcb-crupnicoff-ibcreditstutorial-0314.pdf)[4](https://network.nvidia.com/pdf/whitepapers/IB_Intro_WP_190.pdf)

![](https://pic1.zhimg.com/v2-03fa097197eff36a5205a71d95d61104_1440w.jpg)

### 2.2 发送前，必须确认下一跳装得下整个报文

经典 IB 流控以 64 字节为一个 Flow Control Block。报文消耗整数个 Block，发送方只有在额度足够容纳整个报文时才可以发送。计费不能只看应用负载，还要考虑按协议计入的报文开销与取整。 [3](https://www.openfabrics.org/images/eventpresos/workshops2015/UGWorkshop/Thursday/thursday_09.pdf)

下面是一个**简化算例，不代表某款交换机的实际缓存参数**。

假设某个接收 VL 有 16 KiB 缓存：

```text
可用缓存：16 × 1024 = 16384 字节
每个 Block：64 字节
可用额度：16384 / 64 = 256 Blocks

```

再假设每个示例报文按流控规则恰好消耗 64 Blocks，即计费大小为 4096 字节：

```text
发第 1 个报文：剩余 192 Blocks
发第 2 个报文：剩余 128 Blocks
发第 3 个报文：剩余  64 Blocks
发第 4 个报文：剩余   0 Blocks
发第 5 个报文：必须等待

```

如果接收端尚未释放缓存，发送端就不能继续注入数据。它不是“发过去再看看会不会溢出”，而是先确认空间，再占用空间。

![](https://pic2.zhimg.com/v2-095521cba81b14a5dd64e4a084a1ac6b_1440w.jpg)

### 2.3 真实机制不是简单地“发一个，减一个”

IB 使用累计计数来同步双方状态。核心量包括：

| 名称 | 含义 |
| --- | --- |
| FCTBS：Flow Control Total Blocks Sent | 发送方累计发送的 Block 数 |
| ABR：Adjusted Blocks Received | 接收方维护、可校正的累计接收 Block 数 |
| FCCL：Flow Control Credit Limit | 接收方通告的累计发送上限 |

忽略计数器回绕和异常校正，逻辑可以写成：

```text
FCCL = ABR + 当前可提供的接收缓存 Block 数

允许发送的条件：
FCTBS + 本报文所需 Block 数 ≤ 最近收到的 FCCL

```

这是一种**累计发送进度与累计授权上限的同步机制**。接收方通过链路流控报文更新授权，并不是靠 RC 的端到端 ACK 来返还链路 Credit。实际协议还规定了有限位宽计数、模运算及同步规则。 [2](https://www.ieee802.org/1/files/public/docs2014/new-dcb-crupnicoff-ibcreditstutorial-0314.pdf)[3](https://www.openfabrics.org/images/eventpresos/workshops2015/UGWorkshop/Thursday/thursday_09.pdf)

例如，连续发出四个各占 64 Blocks 的报文，再等待接收方释放空间：

```text
初始：
FCTBS = 1000，FCCL = 1256，剩余额度 = 256 Blocks

发出四个报文后：
FCTBS = 1256，FCCL = 1256，剩余额度 = 0

接收方释放 64 Blocks，并通告新上限后：
FCCL = 1320，剩余额度 = 1320 - 1256 = 64 Blocks

```

发送方就可以再发一个报文。**缓存释放推动授权上限前进；报文发送消耗尚未使用的授权。**

累计通告也有助于同步恢复：如果某次 Credit 更新丢失，后续累计更新仍可覆盖它；数据异常造成计数不一致时，则需要协议规定的同步与校正机制，而不能永远靠简单加减维持状态。 [2](https://www.ieee802.org/1/files/public/docs2014/new-dcb-crupnicoff-ibcreditstutorial-0314.pdf)

![](https://pica.zhimg.com/v2-45ef5bb92a8032e61bdc5833b8adca2c_1440w.jpg)

### 2.4 在途数据也占用了额度

一个常见疑问是：Credit 通告也有传播时延，接收缓存会不会被“已经在路上的数据”撑满？

关键在于：**发送方在报文离开发送端时就消耗额度，不会等报文到达对端才扣除。** 因此，在途数据已经包含在缓存承诺中。 [2](https://www.ieee802.org/1/files/public/docs2014/new-dcb-crupnicoff-ibcreditstutorial-0314.pdf)

可以用一个理想化模型验证这一点。假设某 VL 固定拥有 `B` 个缓存 Block，且暂不考虑误码和计数器回绕：

```text
S：累计已发送的 Block
R：累计已接收的 Block
D：累计已从接收缓存释放的 Block

```

那么可以直接推导：

```text
接收缓存占用 = R - D
在途数据     = S - R
两者之和     = S - D

接收方授权上限：
FCCL = R + [B - (R - D)] = B + D

发送方遵守 S ≤ FCCL，因此：
接收缓存占用 + 在途数据 = S - D ≤ B

```

这就是无溢出的核心约束。旧的 Credit 通告最多让发送端等待更久，不会凭空增加额度。上述推导用于解释原理；真实共享缓存实现还必须保证各端口、各 VL 的授权总量不超额。

![](https://pic1.zhimg.com/v2-9424c4fedf7f634df891a04aace74b14_1440w.jpg)

## 三、当 800G 流量挤向 400G 出口，会发生什么？

考虑一个典型的多对一汇聚场景：

```text
HCA A ──400G──┐
              ├── Switch ──400G── HCA C
HCA B ──400G──┘

```

A、B 各以 400G 发送，而出口只有 400G。输入需求达到 800G，持续超过出口能力，交换机内部就会积压报文。

此时，即使 HCA C 完全正常、始终能够以 400G 接收，拥塞也仍然存在。**拥塞不一定来自最终接收端变慢，也可能只是多个入口竞争同一个出口。**

![](https://pic2.zhimg.com/v2-275462403396a10114b7803c2031f2e5_1440w.jpg)

根据前面的 Credit 模型，可以推导出以下过程：

```text
出口最多释放 400G 的数据
            ↓
交换机相关缓存积压
            ↓
向上游补充新额度的速度受到限制
            ↓
A、B 消耗完既有额度后等待
            ↓
持续注入速率受到限制，避免缓存溢出

```

注意，通常不是把已经授权的 Credit 撤回，也不是累计上限 FCCL 不断下降，而是**授权上限推进得不够快，剩余可用额度逐渐耗尽**。

结果是“等待”，而不是通过普通的缓存溢出丢包来调节流量。但 Credit 本身不保证 A、B 恰好各得到 200G；公平性还取决于仲裁和拥塞控制。 [2](https://www.ieee802.org/1/files/public/docs2014/new-dcb-crupnicoff-ibcreditstutorial-0314.pdf)[6](https://network.nvidia.com/pdf/whitepapers/deploying_qos_wp_10_19_2005.pdf)

## 四、Credit 与 PFC 的差别，不是“有没有在途数据”

传统 RoCE 无损以太网中，PFC（Priority-based Flow Control）按优先级暂停链路上的部分流量；IB 的 Credit 则通过发送前授权保护接收缓存。 [2](https://www.ieee802.org/1/files/public/docs2014/new-dcb-crupnicoff-ibcreditstutorial-0314.pdf)[18](https://networking-docs.nvidia.com/doca/archive/3-5-0/flow-control)[21](https://www.cisco.com/c/en/us/td/docs/dcn/whitepapers/cisco-data-center-networking-blueprint-for-ai-ml-applications.html)

| 维度 | IB Credit | Ethernet PFC |
| --- | --- | --- |
| 基本模式 | 先授权，再发送 | 正常发送，达到条件后暂停 |
| 发送依据 | 下一跳尚未使用的缓存额度 | 对应优先级是否处于暂停状态 |
| 流控粒度 | 链路上的数据 VL | 链路上的优先级 |
| 在途数据如何处理 | 已发送数据已经消耗额度 | 预留 Headroom 吸收暂停生效前的到达数据 |
| 是否可能传播反压 | 会 | 会 |
| 是否自动消除拥塞 | 不会 | 不会 |

可以将两者概括为：

> **Credit：你最多可以发到这里。**<br>**PFC：请暂停这一类流量。**

![](https://pic2.zhimg.com/v2-46200485d25f1ffb08e7370bbdb1ed2d_1440w.jpg)

但不能进一步推导出“Credit 不需要缓存，也不受距离影响”。Credit 循环本身有时延：数据到达下游、占用被释放、新额度返回上游，都需要时间。 [2](https://www.ieee802.org/1/files/public/docs2014/new-dcb-crupnicoff-ibcreditstutorial-0314.pdf)[21](https://www.cisco.com/c/en/us/td/docs/dcn/whitepapers/cisco-data-center-networking-blueprint-for-ai-ml-applications.html)

从流水线利用率出发，一个简化估算是：

```text
为维持满速所需的有效窗口 ≳ 链路字节速率 × Credit 循环时间

```

例如，假设链路速率为 400 Gb/s，完整 Credit 循环时间为 1 微秒，忽略协议开销：

```text
400 Gb/s ÷ 8 × 1 μs = 50,000 字节，约 50 KB

```

这是根据假设推导的窗口量级，不是某款设备的实际缓存配置。它说明：**Credit 可以提前约束缓存使用，但无法消除带宽时延积，也不保证很小的缓存一定能跑满链路。**

## 五、为什么必须按 Virtual Lane 管理 Credit？

### 5.1 一条物理链路，可以承载多条逻辑通道

IB 使用 Virtual Lane（VL，虚拟通道）划分链路资源。经典架构最多定义 15 条数据 VL，即 VL0～VL14，另有特殊用途的 VL15；实际可用的数据 VL 数量取决于设备能力和配置。数据 VL 有各自的流控状态，并通过仲裁共享物理链路。 [4](https://network.nvidia.com/pdf/whitepapers/IB_Intro_WP_190.pdf)[5](https://networking-docs.nvidia.com/doca/archive/3-5-0/infiniband-qos)

```text
同一条物理链路
  ├─ VL0：独立的链路额度状态
  ├─ VL1：独立的链路额度状态
  ├─ VL2：独立的链路额度状态
  └─ ……
             ↓
         VL 发送仲裁
             ↓
          物理端口

```

如果 VL0 暂时缺少 Credit，而 VL1 仍有额度且获得仲裁机会，VL1 就可以继续发送。这有助于隔离不同流量类别，但不代表无限带宽，也不意味着每个 VL 都对应一块完全独立的物理缓存芯片。

### 5.2 SL 是服务标记，VL 是本地链路资源

报文携带 Service Level（SL）标记。交换机根据入口、出口和 SL，选择本跳使用的 VL：

```text
VL = SL-to-VL-MAP（入口端口，出口端口，SL）

```

因此，SL 和 VL 不是同一个概念，也不要求“一条连接经过所有交换机时始终使用相同编号的 VL”。它们的关系类似于：**SL 表达服务类别，VL 承担本地排队、流控与调度。**[5](https://networking-docs.nvidia.com/doca/archive/3-5-0/infiniband-qos)

### 5.3 VL15 是重要例外

VL15 用于承载子网管理报文 SMP，经 QP0 通信，**不受普通数据 VL 的 Credit 流控约束**，可能发生丢弃。不能把“所有 16 条 VL 都采用同样的无损流控”写成 IB 原理。

另外，并非所有管理业务都走 VL15；这里特指子网管理报文。NVIDIA 的架构文档明确将其标为有损的管理 VL。 [8](https://networking-docs.nvidia.com/nvidiainfinibandsecurityoverviewandguidelines/security-in-infiniband)

![](https://pica.zhimg.com/v2-f812a12be6011ed12a0f3b80e6fd6bd0_1440w.jpg)

## 六、不丢包，为什么还需要拥塞控制？

### 6.1 反压可能把局部拥塞扩散出去

假设某个热点目的端接收不及，相关缓存不能及时释放。上游交换机随之缺少 Credit，缓存继续积压，进一步限制更上游的发送。

```text
热点目的端
    ↓
下游缓存积压
    ↓
上游等待 Credit
    ↓
更上游缓存积压
    ↓
更多发送端受到影响

```

当不同业务共享 VL、队列或交换资源时，原本不经过热点的流量也可能被牵连，形成拥塞扩散和队头阻塞。无损网络并不会自动免疫这些问题。 [20](https://conferences.sigcomm.org/sigcomm/2021/files/papers/3452296.3472899.pdf)

### 6.2 FECN/BECN 将拥塞信息反馈到源端

经典 IB 拥塞控制通过显式反馈，调节源端注入速率：

```text
源 HCA ──数据──► 拥塞交换机 ──FECN 标记──► 目的 HCA
   ▲                                        │
   └──────────────── BECN 反馈 ──────────────┘
   │
   └─ 调整相关通信的注入速率

```

FECN 是 Forward Explicit Congestion Notification，即前向显式拥塞通知；BECN 是 Backward Explicit Congestion Notification，即后向显式拥塞通知。反馈可以利用相应的应答或通知机制返回源端，源端据此节流并按算法恢复速率。实际标记阈值、反馈方式和调速算法取决于规范支持及设备配置。 [6](https://network.nvidia.com/pdf/whitepapers/deploying_qos_wp_10_19_2005.pdf)

Credit 与拥塞控制是相互配合的两套机制，不是“Credit 失败后才启动拥塞控制”。合理的拥塞控制应尽量减少长期排队和反压，而 Credit 持续保护下一跳缓存。

![](https://picx.zhimg.com/v2-3b5b56324904da4fea8eaa81f7b595fd_1440w.jpg)

### 6.3 无损网络还必须考虑死锁

当报文占着当前缓存、等待下一跳空间，而下一跳又等待别处空间时，资源依赖可能形成环：

```text
资源 A 等资源 B → 资源 B 等资源 C → 资源 C 又等资源 A

```

这类问题不是“缓存再大一些”就必然能解决。IB 路由设计需要约束通道依赖关系；不同拓扑可能使用不同的路由算法和 VL 规划。例如 OpenSM 的 Up/Down 路由专门考虑环路死锁问题，Fat-Tree 路由也具有相应的 Credit 环路规避设计。 [7](https://networking-docs.nvidia.com/mlnxofedswum/24.10-5.1.6.1lts/nvidia-sm)<br>

![](https://picx.zhimg.com/v2-87eadecf02d2d6ebf6f41b3f615679d3_1440w.jpg)

所以，**不能把任意交换机连接起来，只要开启 Credit，就认为得到了正确的无损 Fabric。**

## 七、真正丢了包怎么办？可靠性还需要另外两层

### 7.1 CRC 检错，FEC 纠错

经典 IB 报文使用 VCRC 与 ICRC 保护数据完整性。VCRC 主要用于逐跳完整性检查；ICRC 用于保护端到端不应变化的内容，计算时对允许变化的字段作相应处理。CRC 的主要职责是检测错误，不是重新发送数据。 [4](https://network.nvidia.com/pdf/whitepapers/IB_Intro_WP_190.pdf)

高速物理链路还使用相应的 FEC（Forward Error Correction，前向纠错）机制，修复其能力范围内的误码。具体编码与能力随链路代际而变化，不能把某一代的 FEC 参数当成所有 IB 链路的通用参数。 [16](https://infinibandta.org/ibta-expands-interoperability-with-new-infiniband-architecture-specification-release-extends-virtualization-support/)

### 7.2 RC 使用序号、确认和重试实现端到端可靠传输

当使用 RC（Reliable Connection）传输时，通信建立在端到端 Queue Pair（QP）之间。HCA 根据报文序号 PSN、确认、否定应答和超时等机制，处理传输异常。 [4](https://network.nvidia.com/pdf/whitepapers/IB_Intro_WP_190.pdf)[13](https://networking-docs.nvidia.com/doca/archive/3-5-0/enhanced-connection-establishment)

例如发送序列为 `PSN 100 → 101 → 102 → 103 → 104`。

如果 102 因异常丢失，链路 Credit 不能把它找回来；恢复交付属于可靠传输层的工作。

传统机制采用 Go-Back-N 思路，重发缺失报文及其后的相关报文，而不只是补发一个缺口。NVIDIA 的增强连接建立文档还介绍了协商 Selective Repeat 的能力。因此，“所有 IB 实现永远只能使用 Go-Back-N”也过于绝对，必须区分基础行为与实际启用的增强能力。 [13](https://networking-docs.nvidia.com/doca/archive/3-5-0/enhanced-connection-establishment)

即便如此，可靠传输也不是无限承诺：持续链路故障、端点失效或重试耗尽，仍可能使操作失败。IB 还提供 UC、UD 等非可靠传输服务，不能因为底层采用 Credit，就认为所有传输模式都具有相同的重传保证。 [4](https://network.nvidia.com/pdf/whitepapers/IB_Intro_WP_190.pdf)[17](https://www.usenix.org/system/files/nsdi23-kong.pdf)

![](https://pic3.zhimg.com/v2-1647dc1e875ddb5bba5ef90762010202_1440w.jpg)

### 7.3 链路 Credit 不是应用接收队列 Credit

还有一个容易混淆的层次：**网卡链路缓存有空间，不代表应用已经准备好接收资源。**

对于需要接收 WQE 的操作，例如 SEND，接收端未准备相应资源时，可能出现 RNR（Receiver Not Ready）。这是端点传输资源的问题，不是下一跳链路缓存是否溢出的问题。普通 RDMA WRITE 与 SEND 的接收资源要求也不能混为一谈。 [17](https://www.usenix.org/system/files/nsdi23-kong.pdf)

因此需要区分：

```text
链路 Credit：相邻端口还能接收多少数据。
传输 ACK：端到端传输已经完成到什么进度。
接收 WQE：应用是否准备好了相应接收资源。

```

![](https://pic1.zhimg.com/v2-9e37f44be60eb60fc2ce6c170474f1ee_1440w.jpg)

## 八、IB 网络由谁组织起来？Subnet Manager

### 8.1 IB 不靠 MAC 学习来建立子网内转发表

在典型 IB 子网内，Subnet Manager（SM，子网管理器）负责发现拓扑、分配本地标识、计算路径，并配置交换机和端点。

```text
                  Subnet Manager
                 /       |       \
             Switch    Switch    HCA
                 \       |       /
                  发现、配置与管理

```

HCA 和交换机通过 Subnet Manager Agent（SMA）与 SM 交互。SM 还负责相应的 QoS、分区及拓扑变化管理。它是 Fabric 的控制与管理实体，**不是承载全部业务数据的中转节点**。 [8](https://networking-docs.nvidia.com/nvidiainfinibandsecurityoverviewandguidelines/security-in-infiniband)

一个子网正常运行时由一个 Master SM 管理，可以部署备用 SM。OpenSM 是 SM 的一种实现；UFM 是更完整的 Fabric 管理平台，可以包含 SM 及监控、告警等能力，不能把 UFM 与 IB 协议本身等同起来。 [8](https://networking-docs.nvidia.com/nvidiainfinibandsecurityoverviewandguidelines/security-in-infiniband)[19](https://networking-docs.nvidia.com/doca/archive/3-4-0/nvidia-sm)

![](https://picx.zhimg.com/v2-258a142cac591307c34421d7527c0acd_1440w.jpg)

### 8.2 GUID、LID 与 GID 分别承担什么角色？

可以先做如下概念区分：

| 标识 | 主要作用 |
| --- | --- |
| GUID | 设备、端口等对象的全局身份标识 |
| LID | 子网内使用的本地转发标识，由 SM 分配 |
| GID | 全局寻址使用的标识，与全局路由头相关 |

在经典单播转发中，交换机读取本地路由头 LRH 中的目的 LID，即 DLID，并查找转发表：

```text
DLID = 0x0200
       ↓
LFT：0x0200 → 出端口 17
       ↓
根据本跳 SL/VL 映射、Credit 与仲裁状态执行转发

```

LFT 是 Linear Forwarding Table。这里的基础思路是“SM 计算并配置，交换机按表转发”，而不是让每台交换机通过以太网式的源 MAC 学习建立地址表。 [7](https://networking-docs.nvidia.com/mlnxofedswum/24.10-5.1.6.1lts/nvidia-sm)[23](https://arxiv.org/html/2310.03742v3)

### 8.3 跨 IB Subnet，需要 IB Router

当需要连接不同的 IB 子网时，可以使用 IB Router：

```text
IB Subnet A ───── IB Router ───── IB Subnet B
   SM A                              SM B

```

跨子网转发利用 GRH（Global Routing Header）中的全局地址信息。路由器执行全局查找，并为下一子网构建相应的本地路由头。 [9](https://networking-docs.nvidia.com/doca/archive/3-5-0/ib-router)

“子网内主要依据 LID 转发”不等于“同子网报文绝对不允许携带 GRH”。同样，IB Router 也不等于 IB 与 Ethernet 之间的协议网关。 [9](https://networking-docs.nvidia.com/doca/archive/3-5-0/ib-router)

这里的 IB Subnet 也不是按 IP 掩码划分的 IP 子网。IPoIB 可以在 IB 之上承载 IP，但这不意味着原生 IB RDMA 数据必须经过 TCP/IP 协议栈。 [1](https://infinibandta.org/ibta-specification/)[22](https://networking-docs.nvidia.com/doca/archive/3-4-0/ip-over-infiniband)

![](https://picx.zhimg.com/v2-f59e4ead970b04bc83cb2b1dd63049eb_1440w.jpg)

## 九、从单交换机到 Fat-Tree：IB 如何扩展规模？

### 9.1 小规模可以直接连接一台交换机

```text
HCA A ───── IB Switch ───── HCA B

```

结构简单，但规模受交换机可用端口限制。需要更多端口和更多并行路径时，就可以使用多级交换网络。

### 9.2 两层 Fat-Tree / Leaf-Spine

常见方案是在 Leaf 上接入服务器，由 Spine 连接不同 Leaf。下面只画出两个 Leaf 和两条可选路径：

```text
                   ┌── Spine 1 ──┐
HCA A ── Leaf 1 ───┤             ├──── Leaf 2 ── HCA B
                   └── Spine 2 ──┘

```

NVIDIA 的 IB 集群部署资料将 Fat-Tree 作为主要拓扑方案，并将 Rail-Optimized 布线用于多接口 GPU 节点。 [10](https://networking-docs.nvidia.com/ibclusterbringupproc/setting-the-infiniband-cluster-topology)

这里有一个容易算错的地方：

```text
HCA A → Leaf 1 → Spine → Leaf 2 → HCA B

```

**两层交换网络，是两种交换层级，不是端到端只经过两台交换机。** 上述路径实际经过 3 台交换机和 4 段物理链路。

按下面的典型路径计数：

| 组网形态 | 典型路径 | 经过交换机数量 | 物理链路段数 |
| --- | --- | --- | --- |
| 单交换机 | HCA—SW—HCA | 1 | 2 |
| 两层网络，跨 Leaf | HCA—Leaf—Spine—Leaf—HCA | 3 | 4 |
| 三层网络，跨顶层 | HCA—Leaf—Spine—Core—Spine—Leaf—HCA | 5 | 6 |

这些数量是对所示路径的直接计数，不代表所有通信都必须走到最高层。同一 Leaf 下的端点可以走更短路径。

![](https://picx.zhimg.com/v2-e310770fb4a2dc5438fa2630a9a5b3c7_1440w.jpg)

### 9.3 用 64 端口交换机推导网络容量

下面构造一个理想化、无带宽收敛的两层 Clos。假设全部交换机均有 64 个同速逻辑端口，不考虑管理占用、预留端口及设备内部限制。

每台 Leaf 将端口均分：

```text
32 个端口接服务器
32 个端口接 Spine

```

如果每个端口为 400 Gb/s：

```text
下行总带宽 = 32 × 400 Gb/s = 12.8 Tb/s
上行总带宽 = 32 × 400 Gb/s = 12.8 Tb/s

```

两者均按单方向计算，因此 Leaf 的上下行带宽比为 1:1。

再配置 32 台 Spine，让每台 Leaf 分别连接全部 32 台 Spine。每台 Spine 有 64 个端口，可以连接 64 台 Leaf，因此：

```text
Leaf 数量：64
Spine 数量：32
接入端口：64 × 32 = 2048
交换机总数：64 + 32 = 96

```

更一般地，在这一均分端口、完整连接的特定构造中，若交换机有 `k` 个同速端口：

```text
接入端口数 = k × (k / 2) = k² / 2

```

**2048 是接入 HCA 端口数，不是天然等于 2048 台服务器。** 假设每台服务器的 8 个 HCA 端口都接入这个 Fabric，那么对应的是 `2048 ÷ 8 = 256` 台服务器。

这只是拓扑容量推导。实际采购还需要区分逻辑网络端口、物理连接器和线缆分拆方式。

![](https://pic1.zhimg.com/v2-4f3e8cab0d80909b78cd49e7956a7d4e_1440w.jpg)

### 9.4 “无收敛”仍不等于“永不拥塞”

上述 1:1 设计解决的是结构性的上行带宽不足，并不改变一个事实：**多个源端同时发往一个 400G 目的端，最后一跳仍然只有 400G。**

因此，满配 Fat-Tree 并不保证任意业务模式、任意路由分配都能同时跑满所有端口。目的端热点、路径分配和端点处理能力，仍会影响吞吐。

规模超过两层设计能力时，可以继续增加交换层级；但端口、链路数量、路径长度和管理复杂度也会随之变化。拓扑提供的是通信容量与可选路径，不替代流控和拥塞控制。

## 十、Rail-Optimized：让布线匹配多网卡通信

假设一个 GPU 节点有 8 个对外 IB 接口。Rail-Optimized 的基本思想，是把不同接口接入不同的一级 Leaf，让各节点对应位置的接口形成有规律的通信路径。 [10](https://networking-docs.nvidia.com/ibclusterbringupproc/setting-the-infiniband-cluster-topology)

```text
节点 A                       对应 Rail / Leaf 组                    节点 B
NIC 0 ───────────────────────── Rail 0 ─────────────────────────── NIC 0
NIC 1 ───────────────────────── Rail 1 ─────────────────────────── NIC 1
NIC 2 ───────────────────────── Rail 2 ─────────────────────────── NIC 2
 ……                                                                  ……
NIC 7 ───────────────────────── Rail 7 ─────────────────────────── NIC 7

```

在合适的扩展单元内，对应接口接到同一 Leaf，可以缩短部分节点间通信路径。更大规模下，同一 Rail 也可能跨越多台交换机，不能把“一跳可达”推广到整个集群的任意两个端点。 [10](https://networking-docs.nvidia.com/ibclusterbringupproc/setting-the-infiniband-cluster-topology)

布线还需要与通信库协同。NCCL 文档解释了为何会尽量让相关 Ring/Tree 通信使用不同节点上的对应 NIC，并说明这种选择与网络是否 Rail-Optimized 有关。 [11](https://docs.nvidia.com/deeplearning/nccl/archives/nccl_2287/user-guide/docs/env.html#nccl-cross-nic)

必须分清三个不同维度：

> **Fat-Tree 是交换拓扑；Rail-Optimized 是布线与流量组织方式；IB Subnet 是管理与寻址边界。**

因此，8 条 Rail 不必然等于 8 个彼此隔离的 IB 子网。Rail 可以通过上层交换网络互通，也可以按部署需求形成独立 Fabric；只有确实划分成不同子网时，才需要分别考虑各自的 SM。不能仅从“Rail 数量”推导“Subnet 数量”。 [10](https://networking-docs.nvidia.com/ibclusterbringupproc/setting-the-infiniband-cluster-topology)[19](https://networking-docs.nvidia.com/doca/archive/3-4-0/nvidia-sm)

![](https://pic1.zhimg.com/v2-ddec606971f4e2de0059113f9a198832_1440w.jpg)

## 十一、有多条路径后，IB 如何选择？

传统静态转发可以概括为：SM 计算路径，交换机根据 DLID 查表选择出口。它不等同于传统 IP Fabric 中按五元组进行 ECMP 哈希。 [23](https://arxiv.org/html/2310.03742v3)

支持 Adaptive Routing（AR，自适应路由）的设备，可以在配置允许的出口集合中，根据负载状况选择出口。例如：

```text
                   ┌── Spine 1：繁忙 ──┐
Leaf A ────────────┤                  ├──────────── Leaf B
                   └── Spine 2：较空 ──┘

```

在这类场景中，AR 有机会利用较空闲的路径。具体选路粒度以及如何处理潜在乱序，属于实现和配置问题，不能把所有 IB AR 都描述成“任意逐包喷洒”。NVIDIA 的 AR 文档区分了相应路由与工作模式。 [12](https://enterprise-support.nvidia.com/s/article/How-To-Configure-Adaptive-Routing-and-Self-Healing-Networking-New)

三种机制的职责可以概括为：

```text
Credit：下一跳有没有空间让我发？
AR：有多条可用路径时，走哪一条？
拥塞控制：我应该以多快的速度注入网络？

```

AR 能缓解某些路径热点，但无法把最终目的端的一条 400G 接收链路变成 800G。

![](https://pic1.zhimg.com/v2-d87432a8703d73619b08674233926574_1440w.jpg)

## 十二、把完整原理串起来

一次基于 RC 的 IB 数据传输，可以从两个平面理解。

**在通信之前，控制面建立可用的 Fabric：**

```text
SM 发现拓扑
    ↓
分配地址标识、计算路径
    ↓
配置转发表、分区与 QoS
    ↓
端点准备传输资源与连接

```

**在通信过程中，数据面执行分工：**

```text
源 HCA 处理传输请求
    ↓
沿已配置的路径转发
    ↓
每一跳检查对应 VL 的 Credit，并参与发送仲裁
    ↓
拥塞时通过反压保护缓存，通过拥塞反馈调节注入
    ↓
发生可恢复的传输异常时，由可靠传输机制重试
    ↓
目的端按相应操作语义完成数据交付

```

![](https://pica.zhimg.com/v2-f3c0e585dc21e9dd03c1d3b0079b4670_1440w.jpg)

这不是所有硬件都严格串行执行的时序图，而是对不同机制职责的归纳。 [2](https://www.ieee802.org/1/files/public/docs2014/new-dcb-crupnicoff-ibcreditstutorial-0314.pdf)[5](https://networking-docs.nvidia.com/doca/archive/3-5-0/infiniband-qos)[6](https://network.nvidia.com/pdf/whitepapers/deploying_qos_wp_10_19_2005.pdf)[8](https://networking-docs.nvidia.com/nvidiainfinibandsecurityoverviewandguidelines/security-in-infiniband)[13](https://networking-docs.nvidia.com/doca/archive/3-5-0/enhanced-connection-establishment)

由此也能理解一个重要的工程现象：**“没有丢包，但应用很慢”完全可能发生。** 例如端口一直有数据，却因 Credit 不足或仲裁原因等待发送。NVIDIA 的 `PortXmitWait` 类计数正是记录此类等待；它不是一个可以不加区分地解释成“纯拥塞时长”的指标。 [14](https://networking-docs.nvidia.com/ufmenterpriseum/6221/appendix-supported-port-counters-and-events)

![](https://pic1.zhimg.com/v2-556959a397ab0d70df5400db10901638_1440w.jpg)

IB 的原生无损，不是用一个开关消灭所有网络问题，而是把“下一跳装不下”的问题转换为受控等待。可靠传输处理交付异常，拥塞控制限制长期积压，拓扑和路由提供容量与正确的通道依赖关系。

**理解 IB，不应停留在“Credit 让网络不丢包”，而应看到完整的因果链：先保证每一跳不会超额接收，再用端到端控制与合理组网，让整个系统持续、有效地向前推进。**
