Triton 是现在，TileLang 是复杂融合算子的强竞争者，cuTile 是 NVIDIA 的未来官方路线，PTO-ISA/PyPTO 是昇腾生态建立 tile 编程标准的关键尝试

### 1. 它们都在回答同一个问题

这些项目本质上都是在争夺下一代 AI 加速器编程的中间层：**不要让开发者直接写 thread-level CUDA、Ascend C 或复杂手工调度，但也不能退回到只能调用固定库算子的高层框架。**

它们共同的关键词是 **Tile**。现代 GPU/NPU 的核心计算单元越来越像“矩阵/张量 tile 处理器”：Tensor Core、WGMMA、TMA、shared memory、L1/UB/L0、DMA、Cube/Vector 单元、跨卡通信，都是围绕 tile 数据块组织的。传统 SIMT 线程视角太细，PyTorch 这类框架又太粗，所以中间出现了 Triton、TileLang、cuTile、PTO-ISA、PyPTO 这类“tile 级编程系统”。NVIDIA 的 Tile IR 文档也明确把 Tile IR 描述成不同于 PTX/SIMT 的 tile-based 虚拟 ISA，用来把 tile-native 程序映射到底层线程、内存层级和 Tensor Core；Triton 最初的目标也是让研究者不需要完整 CUDA 经验就能写高性能 GPU kernel。([NVIDIA Docs](https://docs.nvidia.com/cuda/tile-ir/latest/sections/introduction.html))

我的判断是：**未来不会一个工具吃掉所有场景**。Triton 会继续是 PyTorch/AI 研究里的主流自定义 kernel DSL；TileLang 会在复杂融合算子、attention、MLA、稀疏/量化 kernel 上变强；cuTile/CUDA Tile 是 NVIDIA 官方想把 tile 编程纳入 CUDA 主线的战略动作；PTO-ISA/PyPTO 则是昇腾生态想建立跨代 NPU tile 编程标准的核心尝试。

### 2. 它们为什么会出现？

过去十年 AI kernel 开发大致经历了三个阶段。

第一阶段是 **库调用时代**：GEMM 用 cuBLAS，卷积用 cuDNN，通信用 NCCL，框架层调用固定算子。这对 ResNet、BERT 这类标准模型很有效。

第二阶段是 **自定义 kernel 时代**：Transformer、MoE、FlashAttention、量化、KV cache、paged attention、MLA、speculative decoding、稀疏 attention 之后，模型性能不再只取决于单个 GEMM，而取决于大量融合 kernel、特殊 memory layout、特殊 epilogue 和跨层调度。OpenAI 在 Triton 1.0 发布时就指出，原生框架算子组合会产生临时 tensor，自定义 GPU kernel 又很难，所以需要更高生产力但仍高性能的语言。([OpenAI](https://openai.com/index/triton/))

第三阶段就是现在的 **tile 编程时代**：硬件越来越复杂，单纯写线程已经不够表达“数据如何在 DRAM、shared memory、register、Tensor Core 之间流动”。NVIDIA CUDA Tile 的官方介绍说，它把抽象层级提升到 SIMT 之上，由编译器和 runtime 自动处理 block 内并行、异步、内存搬运，并利用 Tensor Core、shared memory、TMA 等硬件能力；PTO-ISA 也类似，定义 90+ 个标准 tile 指令，用统一 tile 抽象屏蔽昇腾不同代际实现差异。([NVIDIA Developer](https://developer.nvidia.com/blog/simplify-gpu-programming-with-nvidia-cuda-tile-in-python/))

所以这些项目产生的根本背景是：

| 压力 | 具体表现 | 对应工具的回答 |
| --- | --- | --- |
| AI kernel 越来越定制化 | FlashAttention、MLA、MoE、量化、稀疏、长上下文 | Triton、TileLang、PyPTO |
| 硬件越来越 tile 化 | Tensor Core、WGMMA、TMA、TMEM、Ascend Cube/Vector/L0/UB | cuTile、Tile IR、PTO-ISA、CuTe DSL |
| 手写 CUDA/Ascend C 门槛过高 | 调度、同步、内存搬运、bank conflict、pipeline 难维护 | Triton、TileLang、PTO-DSL、PyPTO |
| 跨架构迁移困难 | NVIDIA Ampere/Ada/Blackwell、AMD MI300X、Ascend A2/A3/A5 | Triton、TileLang、PTO-ISA、cuTile |
| 标准库不够灵活 | 标准 GEMM 很快，但融合/特殊 layout 难覆盖 | TileLang、Triton、CuTe DSL、PyPTO |

### 3. 各项目定位对比

| 项目 | 本质定位 | 更像哪一层 | 最大优势 | 最大风险/短板 |
| --- | --- | --- | --- | --- |
| Triton | Python 风格 GPU kernel DSL + 编译器 | 高层 tile/block kernel DSL | 生态成熟，PyTorch 关系深，NVIDIA/AMD/Intel 后端都在发展 | 对极底层硬件控制不如 CuTe/CUTLASS 或厂商专用 DSL |
| TileLang | 基于 TVM 的 tile-level kernel DSL | Triton 与底层调度之间 | 更显式控制内存、调度、tile；适合复杂融合算子 | 年轻，生产生态和稳定性还在成长 |
| cuTile / CUDA Tile | NVIDIA 官方 tile DSL + Tile IR | NVIDIA CUDA 新 tile 编程层 | 官方路线，理论上能直接继承 CUDA driver/compiler/hardware 优化 | 很新；架构支持、性能一致性还在成熟 |
| CuTe DSL | CUTLASS/CuTe 的 Python DSL | 更底层的 NVIDIA kernel DSL | 对 NVIDIA 硬件控制强，适合追峰值性能 | 学习曲线更高，主要面向性能工程师 |
| PTO-ISA | 昇腾 CANN 定义的 tile 虚拟 ISA | Ascend NPU 的低层 tile 标准 | 统一 A2/A3/A5 等代际，给 PyPTO/TileLang-Ascend/PTO-DSL 做底座 | 生态新，主要绑定昇腾 |
| PyPTO | 面向昇腾的 Python 高性能编程框架 | Tensor→Tile→Block→PTO 的多层系统 | 既能写复杂融合算子，也能覆盖更大图/网络级别 | Beta 阶段，生态接受度需要时间 |
| PTO-DSL | PTO-ISA 的 Pythonic JIT 前端 | 更接近 cuTile/CuTe DSL 的低层 DSL | 显式 NPU 原语、DMA、pipeline，适合底层优化 | 更偏专家工具 |

可以把它们理解成三条路线：

**NVIDIA 路线**：CUDA / PTX / CUTLASS / CuTe DSL / cuTile / Tile IR。 **开源跨厂商路线**：Triton / TileLang / TVM / MLIR / LLVM。 **昇腾路线**：CANN / Ascend C / PTO-ISA / PyPTO / TileLang-Ascend / PTO-DSL。

### 4. cuTile / CUDA Tile：NVIDIA 官方的 tile 编程入口

**cuTile** 是 NVIDIA 在 CUDA 13.x 时代推出的新 Python DSL，配套底层是 **CUDA Tile IR**。官方文档把 cuTile 定义为 NVIDIA GPU 的并行编程模型和 Python DSL，可以自动利用 Tensor Core 和 Tensor Memory Accelerator，并且面向 NVIDIA GPU 架构做可移植映射；CUDA Tile 的官方介绍也说，它的目标是把程序员从 SIMT 线程细节中抬高到 tile kernel 层。([NVIDIA Docs](https://docs.nvidia.com/cuda/cutile-python/))

它的战略意义很大：NVIDIA 过去的通用虚拟 ISA 是 PTX，但 PTX 的核心仍然偏 SIMT/thread。Tile IR 则试图把 Tensor Core、tile load/store、tile MMA、内存层级和调度提示变成更自然的抽象。Tile IR 文档明确说，它是 portable low-level tile VM/ISA，和 PTX 的 SIMT 模型不同，它把 GPU 建模为 tile-based processor。([NVIDIA Docs](https://docs.nvidia.com/cuda/tile-ir/latest/sections/introduction.html))

cuTile 的优势主要有三个。第一，它是 NVIDIA 官方路线，最有机会长期跟 CUDA driver、compiler、Tensor Core、TMA、Blackwell 之后的新硬件能力深度绑定。第二，它的抽象比 CuTe/CUTLASS 更高，开发者写 Python 风格 tile kernel，不必显式管理每个线程。第三，它保留了进入底层 Tile IR 的可能性，未来也可以成为 Triton、TileLang 等前端的后端之一；NVIDIA 已经公开了 Triton-to-TileIR backend 的方向，目标是让 Triton kernel 可以选择通过 CUDA Tile IR 而不是 PTX 路径编译。([NVIDIA Developer](https://developer.nvidia.com/blog/advancing-gpu-programming-with-the-cuda-tile-ir-backend-for-openai-triton/))

但 cuTile 还很新，不能简单理解成“已经替代 CUDA/Triton/CUTLASS”。CUDA 13.2 的资料显示 cuTile 已扩展到 Ampere/Ada 与 Blackwell 的若干 compute capability，但 Tile IR 稳定性文档也特别列出 Hopper sm_90 在 13.2 中不支持，这说明架构覆盖还在演进。cuTile release notes 到 2026 年 4 月 20 日的 v1.3.0 已加入 AOT export、autotuning API、Array.tiled_view、load/store memory order/scope 等能力，说明它正快速补齐工程功能。([NVIDIA Developer](https://developer.nvidia.com/blog/cuda-13-2-introduces-enhanced-cuda-tile-support-and-new-python-features/))

性能上也要谨慎。2026 年 4 月一篇独立预印本评测认为，cuTile 在 B200 的 fused attention 上可以表现很强，但标准 GEMM 仍未替代 cuBLAS，且不同架构/工作负载差异明显；同一篇评测还指出 Triton 在其测试平台上对 cuBLAS 的覆盖率更稳定。这类结果需要随 CUDA/cuTile 版本继续复测，但它提醒我们：**cuTile 是战略上很重要的新层，不等于短期内所有场景都该迁移。**([arXiv](https://arxiv.org/html/2604.23466v1))

我的判断：cuTile 的长期价值很高，尤其是在 Blackwell 及之后的 NVIDIA GPU 上。它更像 NVIDIA 对 Triton/TileLang 这类高层 DSL 潮流的官方回应：既提高生产力，又把最终编译控制权留在 CUDA 体系内。短期选型上，如果是标准 GEMM/Conv，仍应优先 cuBLAS/cuDNN/CUTLASS；如果是新 fused attention、特殊 layout、研究型 kernel，可以把 cuTile 作为 NVIDIA-only 的前沿选项来 benchmark。

### 5. Triton：当前最实用的自定义 GPU kernel DSL

Triton 是这批工具里最成熟、最广泛使用的一个。OpenAI 最初发布 Triton 1.0 时的定位非常清楚：让没有完整 CUDA 经验的研究者也能写出高效 GPU 代码，用少量 Python-like 代码实现接近 cuBLAS 的 FP16 matmul，并避免 PyTorch 原生算子组合产生大量临时 tensor。([OpenAI](https://openai.com/index/triton/))

Triton 的核心抽象是 **program/block/tile**。开发者不是直接写每个 CUDA thread，而是写一个 program instance 处理一个 block/tile 的数据。Triton 编译流程会把 Python AST 降到 Triton IR，再到 tile-level 的中间表示、TTGIR、LLVM IR，最后走不同后端。PyTorch 官方的 Triton 编译说明也把 Triton 描述为 high-level Python-based blocked programming approach。([PyTorch](https://pytorch.org/blog/triton-kernel-compilation-stages/))

它最大的优势是生态。Triton GitHub 明确说目标是给深度学习 primitive 提供比 CUDA 更高生产力、比其他 DSL 更灵活的开源环境；PyTorch 2.x 的 TorchInductor 也把 Triton 作为 GPU 代码生成的重要组成部分。Triton 还在扩展多后端：AMD ROCm 已有 Triton 支持教程，Intel 也有 out-of-tree XPU backend。([GitHub](https://github.com/triton-lang/triton))

Triton 的短板也来自它的定位。它比 CUDA 简洁得多，但当你要精确控制最新硬件特性、复杂 pipeline、特殊 shared-memory layout、TMA/WGMMA/TMEM、跨层内存复用时，Triton 有时不如 CuTe/CUTLASS、TileLang 或厂商 DSL 灵活。Triton 3.6.0 已经继续增强 Blackwell、AMD GFX950、automatic warp specialization、MMAv5 pipelining、TMA 等能力，但这些优化仍依赖具体后端和编译器成熟度。([GitHub](https://github.com/triton-lang/triton/releases))

我的判断：**Triton 仍会是未来几年 AI kernel 的默认入口**。原因不是它每个 kernel 都最快，而是它综合了“够快、够短、够生态化、够容易集成 PyTorch”。当团队需要快速写 fused op、量化 kernel、attention 变体、inference kernel，Triton 通常是第一选择。但如果目标是 NVIDIA 某一代 GPU 的绝对峰值，或者 Ascend NPU 的底层优化，Triton 未必是最终答案。

### 6. TileLang：更显式、更偏复杂融合算子的 tile DSL

TileLang 的定位是“用 Pythonic 语法写高性能 GPU/CPU kernel，同时保留低层优化能力”。官方文档说它面向 GEMM、Dequant GEMM、FlashAttention、LinearAttention 等高性能 kernel，底层基于 TVM 编译基础设施。([TileLang](https://tilelang.com/))

TileLang 和 Triton 的区别在于：Triton 更像“把 CUDA kernel 写简单”，TileLang 更像“把 tile-level schedule、memory placement、data movement、parallel scheduling 变成可控但仍简洁的 DSL”。TileLang 的 ICLR 2026 Oral 论文摘要也强调，现有编译器如 Triton 在细粒度控制上不足，所以 TileLang 提供显式 tile-level primitives，并配合 tile inference/recommendation；论文声称 fused attention 可以在 80 行以内表达，代码量最多减少 90%，在 H100 和 AMD GPU 上相对 Triton 有显著速度提升。这里要注意，这是作者论文中的报告结果，不应无条件推广到所有 kernel。([OpenReview](https://openreview.net/forum?id=Jb1WkNSfUB))

TileLang 的另一个重要方向是多后端。它的公开仓库显示，2025 年到 2026 年间陆续加入 CuTeDSL backend、Apple Metal、AscendC/AscendNPU IR backend、2:4 sparse tensor core、AMD MI300X FlashMLA 等方向；截至 2026 年 4 月，TileLang release 已到 v0.1.9。([GitHub](https://github.com/tile-ai/tilelang))

TileLang 的优势是：它比 Triton 更愿意暴露底层调度结构，又比手写 CUDA/CuTe/Ascend C 更短。AMD ROCm 侧的文章也把 TileLang 描述为用 tile 作为核心编程单元，通过高层 API 封装底层细节，以更少代码实现接近手写低层代码的性能；其示例强调 FlashAttention 从 500+ 行 CUDA 降到 80 行以内。([ROCm 博客](https://rocm.blogs.amd.com/ecosystems-and-partners/rocm-tilelang-kernel/README.html))

我的判断：TileLang 的机会在 **“难 kernel”**，不是普通 elementwise 或标准 GEMM。比如 FlashAttention 变体、MLA、稀疏 attention、量化 GEMM、fused MoE、dispatch/combine、跨后端 attention kernel。它未来可能不会取代 Triton，而是形成分工：**Triton 做主流快速开发，TileLang 做更复杂、更需要 schedule 控制的高端 kernel。**

### 7. CuTe DSL：不要和 cuTile 混淆

因为你提到的是 cutile，我这里特别补一段。NVIDIA 生态里还有 **CuTe DSL**，它属于 CUTLASS 体系，是从 C++ CuTe/CUTLASS 演化出的 Python DSL。NVIDIA 的 CuTe DSL 文档把它描述为用于动态编译高性能 GPU kernel 的 Python DSL，强调 zero-cost abstraction、JIT、DLPack、缓存、以及对 layout、tensor、硬件 atom 的低层控制。([NVIDIA Docs](https://docs.nvidia.com/cutlass/latest/media/docs/pythonDSL/cute_dsl_general/dsl_introduction.html))

简单区分：

| 名称 | 更高层还是更底层 | 典型用户 |
| --- | --- | --- |
| cuTile / CUDA Tile | 更高层，官方 tile kernel DSL + Tile IR | 想用 Python 写 tile kernel，并让 NVIDIA 编译器处理更多细节的人 |
| CuTe DSL | 更底层，CUTLASS/CuTe 风格 layout algebra 和硬件 atom | 追求 NVIDIA 上极致性能、愿意控制 layout/schedule 的性能工程师 |
| CUTLASS C++ | 更传统、更底层 | 生产级 GEMM/Conv/template kernel 专家 |

我的判断：CuTe DSL 会继续服务于 NVIDIA 极限性能路线；cuTile 会服务于更广的 CUDA tile 编程路线。两者可能长期共存，而不是谁替代谁。

### 8. PTO-ISA：昇腾生态的 tile 虚拟 ISA

**PTO-ISA** 是 Ascend CANN 定义的 **Parallel Tile Operation** 虚拟 ISA。公开仓库把它描述为面向 tile-oriented programming 的虚拟 ISA，用于在不同代昇腾硬件之间迁移和优化；它定义了 90+ 个标准 tile 指令，并强调统一跨代 tile 抽象、兼顾性能调优、作为框架/算子/工具链的共同接口。([GitHub](https://github.com/PTO-ISA/pto-isa))

这和 NVIDIA Tile IR 的动机非常像：底层硬件越来越复杂，直接用每代硬件特有实现写算子会导致迁移困难。PTO-ISA 希望在 Ascend A2/910B、A3/910C、A5/950 等代际之间提供更稳定的 tile 抽象。其公开资料还提到 CPU simulator、tile shape、mask、event sync、unit/pipeline modeling，以及 Auto/Manual 两种工作流。([GitHub](https://github.com/PTO-ISA/pto-isa))

PTO-ISA 的意义不只是一个 ISA 文件，而是昇腾软件生态的底座。公开资料显示，它已经被集成到 PyPTO 和 TileLang Ascend，路线图还包括 PTO Auto Mode Bisheng compiler support、PTO Tile Fusion、PTO-AS Bytecode、Convolution extension、Collective communication extension、System scheduling extension 等。([GitHub](https://github.com/PTO-ISA/pto-isa))

我的判断：PTO-ISA 是昇腾生态非常关键的一步。过去 Ascend C/CANN 自定义算子开发门槛较高，跨代迁移也复杂；PTO-ISA 如果做成，就相当于给 Ascend 建立一个“tile 时代的 PTX/TileIR 式底层契约”。但它的影响力主要会局限在昇腾生态内，除非未来有更多开源前端、benchmark 和模型级案例支撑。

### 9. PyPTO：昇腾上的高层 tile/graph 编程框架

**PyPTO** 是基于 PTO 范式的高性能 AI 加速器编程框架。它不是单纯的 low-level ISA，而是提供更高层的 Python API，把高层 Tensor graph 编译成 Tile graph、Block graph、Execution graph，最后生成 PTO 虚拟指令并落到可执行程序。PyPTO 公开资料强调 tile programming、多级图变换、MPMD scheduling、可视化工具链、动态形状和符号编程。([GitHub](https://github.com/hw-native-sys/pypto))

PyPI 页面显示 PyPTO 目前处于 Beta 状态，面向 Python 3.9–3.12，并把目标用户分成算法开发者、性能专家、系统开发者：算法开发者可以在 Tensor 层写，性能专家可以深入 Tile/Block 层，系统开发者可以把框架或工具连接到 Tensor/Tile/Block/PTO ISA 各层。([PyPI](https://pypi.org/project/pypto/))

PyPTO 和 PTO-DSL 的关系可以这样理解：

| 工具 | 抽象层级 | 类比 |
| --- | --- | --- |
| PTO-ISA | 最低层虚拟 tile ISA | 类似 Ascend 生态里的 tile ISA 合约 |
| PTO-DSL | Pythonic JIT，显式 NPU 原语 | 更像 cuTile/CuTeDSL 风格的低层 kernel DSL |
| PyPTO | Tensor→Tile→Block→Execution 多层框架 | 更像面向复杂 fused op / 网络级生成的系统 |
| TileLang-Ascend | TileLang 在 Ascend 上的后端路线 | 跨后端 DSL 接入 Ascend/PTO |

PTO-DSL 的公开资料明确说，它是 PTO-ISA 的 Pythonic interface 和 JIT compiler，抽象类似 cuTile 但 native to NPU，并支持 automatic software pipelining、torch-npu 接口、PTO Assembler；同一资料也区分了 PyPTO：PyPTO 是 full MPMD dynamic runtime，Tensor API 更接近 PyTorch/JAX，而 PTO-DSL 更偏 SPMD、接近 cuTile/CuTeDSL。([GitHub](https://github.com/huawei-csl/pto-dsl))

我的判断：PyPTO 的价值不只在“写一个 kernel”，而在昇腾上做更大粒度的融合、图级调度和模型级优化。它适合 Ascend 生态里那些 PyTorch/CANN 标准路径覆盖不好、但又不想完全手写 Ascend C 的场景。短期它仍会受制于生态成熟度、文档、benchmark、与 torch-npu/CANN 的集成体验；长期如果 PTO-ISA 成为稳定底座，PyPTO 有机会成为 Ascend 自定义高性能算子的主力入口之一。

### 10. TileLang-Ascend：TileLang 与 PTO/Ascend 的交汇点

TileLang-Ascend 是一个很值得关注的分支，因为它说明未来可能不是每个厂商都用完全孤立的 DSL，而是一个高层 tile DSL 可以接多个后端。TileLang-Ascend 公开资料称，它面向 Huawei Ascend NPU，使用 Pythonic syntax 和 TVM，backend 支持两条路线：**Ascend C & PTO** 以及 **AscendNPU IR**。([GitHub](https://github.com/tile-ai/tilelang-ascend))

它还明确给出了 Ascend 的 memory hierarchy 映射：GPU 的 global/shared/register 可以对应到 Ascend 的 global、L1/UB、L0 等层级；开发者可以用 alloc_L1/alloc_ub 等方式表达内存分配，并通过 T.Parallel 自动向量化或显式 tile primitive 控制计算。([GitHub](https://github.com/tile-ai/tilelang-ascend))

我的判断：TileLang-Ascend 的战略意义在于，它可能把 TileLang 的跨后端能力和 PTO-ISA 的昇腾底层能力结合起来。对开发者来说，这比单独学习每个厂商的底层 DSL 更有吸引力；对昇腾生态来说，这能借助 TileLang/TVM 社区扩大开发者入口。

---

### 11. 它们的优势本质上是什么？

### 第一，代码量下降，但不是简单“语法糖”

Triton、TileLang、cuTile、PyPTO 都声称能用更少代码写高性能 kernel。这个优势不是因为它们少写几行循环，而是因为它们把很多重复、脆弱、硬件相关的部分交给编译器：tile 划分、vectorization、pipeline、异步搬运、同步、memory layout、mask、边界处理、部分 autotuning。

### 第二，它们更贴近现代 AI 硬件的真实执行方式

现代 Tensor Core/NPU Cube 单元并不是逐 scalar 计算，而是吃一块矩阵 tile。Tile 编程让开发者直接表达“这块数据怎么搬、怎么算、怎么复用”，比 thread-level 更自然。CUDA Tile IR 和 PTO-ISA 都是在把这种 tile 结构标准化。([NVIDIA Docs](https://docs.nvidia.com/cuda/tile-ir/latest/sections/introduction.html))

### 第三，它们服务于“融合算子”而不是只服务于单算子

大模型推理/训练的瓶颈经常是内存带宽、临时 tensor、layout 转换和 kernel launch，而不是单个 GEMM 峰值。TileLang、Triton、PyPTO 的价值就在于把多个操作融合到一个 tile 数据流里，减少中间写回和重复读写。

### 第四，它们给自动调优和编译器优化留下空间

cuTile v1.3.0 已加入 autotuning API，TileLang 也强调 tile inference/recommendation，PTO-ISA 路线图里有 Auto Mode 和 cost model。未来 kernel 开发很可能不是手工写死一个 schedule，而是开发者描述 tile 级意图，编译器/搜索器/AI agent 自动找 schedule。([NVIDIA Docs](https://docs.nvidia.com/cuda/cutile-python/generated/release_notes.html))

---

### 12. 它们的局限也很明显

第一，**标准算子不一定值得自己写**。标准 GEMM、Conv、LayerNorm、常见 attention，在成熟库里已经高度优化。独立评测对 cuTile 的结论也提醒：标准 GEMM 上不应轻易认为新 DSL 能替代 cuBLAS。([arXiv](https://arxiv.org/html/2604.23466v1))

第二，**可移植不等于免调优**。Triton 可以跨 NVIDIA/AMD/Intel 后端，TileLang 也在扩展多后端，PTO-ISA 可以跨 Ascend 代际，但每个硬件的 tile size、memory hierarchy、pipeline、向量单元、矩阵单元都不同。真正高性能仍需要 benchmark、autotune 和硬件知识。

第三，**生态成熟度差异很大**。Triton 最成熟；TileLang 增长很快但仍年轻；cuTile 是 NVIDIA 新路线，官方潜力强但仍处于快速变化期；PTO-ISA/PyPTO 也在 2025–2026 期间才开始更公开地成体系发展。PTO-ISA 仓库显示其正式开源时间是 2025 年 12 月 27 日，说明生态还很新。([GitHub](https://github.com/PTO-ISA/pto-isa))

第四，**工具链锁定不可避免**。cuTile 深绑定 CUDA/NVIDIA，PTO-ISA/PyPTO 深绑定 Ascend/CANN，CuTe DSL 深绑定 CUTLASS/NVIDIA。Triton 和 TileLang更开放，但也无法完全避免后端差异。

---

### 13. 未来发展判断

### 2026 年：Triton 继续主流，cuTile/TileLang/PTO 快速追赶

短期最稳的是 Triton。PyTorch、vLLM、FlashAttention 生态、研究社区都已经大量使用 Triton，团队招人和维护成本最低。TileLang 会在复杂 attention、MLA、稀疏、量化、AMD/Ascend 等场景持续被试用。cuTile 会在 NVIDIA Blackwell 及后续 GPU 上快速扩展，尤其是当 Triton-to-TileIR backend 更成熟后，它可能成为 Triton kernel 的 NVIDIA 官方优化路径之一。PTO-ISA/PyPTO 会在 Ascend A2/A3/A5 生态内快速补齐算子和模型案例。

### 2027–2028 年：前端 DSL 与后端 tile ISA 分离

未来更可能出现这种结构：

| 前端 | 中间层 | 后端 |
| --- | --- | --- |
| Triton / TileLang / PyPTO / cuTile | Tile IR、Triton IR、TVM/TIR、PTO-ISA | NVIDIA、AMD、Intel、Ascend、Metal |
| 用户写 tile/dataflow | 编译器做 schedule/search/fusion | 硬件执行 Tensor Core/NPU tile 指令 |

也就是说，开发者未必关心底层是 PTX、Tile IR、PTO-ISA、LLVM AMDGPU，更多会关心“我的 tile 数据流表达是否清楚，编译器能否自动找到好 schedule”。

### 更长期：kernel 编程会从“手写实现”变成“描述约束 + 自动搜索”

AI 模型变化太快，手工为每个模型写 CUDA/Ascend C 不现实。未来更合理的方式是：开发者描述计算图、tile shape、memory placement、fusion 边界和性能约束，编译器、autotuner 甚至 AI agent 自动生成多版本 kernel 并 benchmark。cuTile 的 autotuning API、TileLang 的 tile recommendation、PTO-ISA 的 cost model/Auto Mode 都指向这个方向。([NVIDIA Docs](https://docs.nvidia.com/cuda/cutile-python/generated/release_notes.html))

---

### 14. 实际选型建议

如果你是做 **NVIDIA + PyTorch 自定义 kernel**，优先学 **Triton**。它是当前性价比最高的入口，尤其适合 fused elementwise、reduction、attention 变体、量化、推理 kernel。

如果你是做 **复杂融合算子、FlashAttention/MLA/稀疏/量化 GEMM**，并且愿意投入更深的 schedule 控制，关注 **TileLang**。它未来可能是 Triton 之外最值得跟踪的开源 tile DSL。

如果你是做 **NVIDIA 极致性能 kernel**，尤其是 GEMM/attention 的底层专家路线，关注 **CuTe DSL / CUTLASS**。这是更硬核的路线，开发难度更高，但控制力更强。

如果你想跟进 **NVIDIA 官方下一代 tile 编程模型**，关注 **cuTile / CUDA Tile / Tile IR**。它现在还不一定是所有生产场景的首选，但战略价值很高，尤其值得在 Blackwell 及后续架构上试验。

如果你在 **昇腾 Ascend** 上做高性能算子，底层必须关注 **PTO-ISA**，高层可以看 **PyPTO、PTO-DSL、TileLang-Ascend**。其中 PyPTO 更偏多层图/复杂融合，PTO-DSL 更偏底层 kernel，TileLang-Ascend 更偏跨后端 tile DSL 接入 Ascend。
