### 写在前面

做嵌入式AI部署，绕不开一个问题：推理框架选谁？

这就像买车——你不能光看发动机参数，还得看你跑什么路况。城市代步选个省油的轿车，翻山越岭得上四驱越野车，去赛道飙车那是另一个预算量级。推理框架也一样，没有”最好的”，只有”最合适的”。

今天就来把TensorRT、ONNX Runtime和TFLite这三个”主角”拉出来遛遛，看看各自的本事和脾气。

### 一、三大框架概览

### 1.1 TensorRT：NVIDIA的亲儿子

**定位**：专门为NVIDIA GPU/Jetson优化的高性能推理引擎。

TensorRT是NVIDIA出品的，天然只在自家硬件上跑。你要在Jetson Nano上跑AI？TensorRT大概率是你的最优选。你要在树莓派上跑？它压根不支持。

**核心特点**：

- 针对NVIDIA GPU做了极致的底层优化
- 支持FP32/FP16/INT8，混合精度自动调度
- 强大的图优化能力（算子融合、内核自动调优等）
- 闭源，黑盒优化

### 1.2 ONNX Runtime：微软的跨平台选手

**定位**：以ONNX为中心的跨平台推理引擎。

ONNX Runtime（简称ORT）的最大卖点是**跨平台**。同一个ONNX模型，可以在Windows/Linux/Mac上跑，可以在CPU/GPU/NPU上跑，可以用不同的”执行提供者”（Execution Provider）适配不同硬件。

**核心特点**：

- 跨平台跨硬件，一个框架打天下
- 通过Execution Provider插件化支持各种加速器
- 支持PyTorch/TensorFlow/Keras等多种框架导出的模型
- 开源，社区活跃

### 1.3 TFLite：谷歌的移动端专家

**定位**：为移动端和嵌入式设备设计的轻量推理引擎。

TFLite是TensorFlow生态的一部分，专门为移动端和嵌入式场景优化。它的运行时极其轻量，核心库只有几百KB，可以跑在手机、树莓派甚至MCU上。

**核心特点**：

- 运行时极轻量（TFLite Micro甚至可以在Cortex-M上跑）
- 对TensorFlow模型的支持最好
- 内置Delegate机制可调用GPU/NPU/DSP加速
- 有专门的MCU版本（TFLite Micro）

### 二、关键技术对比

### 2.1 算子融合（Operator Fusion）

算子融合是推理框架最核心的优化手段之一。思路很简单：把多个连续的小算子合并成一个大算子，减少中间结果的内存读写。

**经典的融合模式**：

- Conv + BN + ReLU → 一个融合算子
- Conv + Add + ReLU → 一个融合算子（ResNet的残差连接）
- MatMul + Add → 一个Gemm算子

```text
融合前：                    融合后：
Conv → 写内存              Conv-BN-ReLU（一个kernel）
读内存 → BN → 写内存       
读内存 → ReLU → 写内存     

// 省了4次内存读写
```

**三大框架的融合能力**：

TensorRT的融合最激进，它会尝试各种复杂的融合模式，甚至会自动重排算子顺序来创造融合机会。有时候TensorRT融合出来的kernel你在网络图里根本认不出原来是哪些算子——因为它把好几层都塞进一个kernel里了。

ONNX Runtime的融合走的是规则匹配路线，预定义了一系列融合Pattern，匹配上就融合。融合能力不如TensorRT激进，但胜在透明可控。

TFLite的融合相对保守，主要做标准的Conv+BN+Act融合。但TFLite的优势在于它的算子实现本身就是为嵌入式设备优化的——即使不做太多融合，单个算子的执行效率也不差。

### 2.2 内存优化

嵌入式设备的内存是稀缺资源，推理框架的内存管理能力直接决定能跑多大的模型。

**TensorRT**：在构建引擎时会分析整个计算图的内存生命周期，自动做内存复用。不同层的中间结果如果不会同时存在，就共享同一块内存。用户基本不需要操心内存问题——TensorRT会搞定。

**ONNX Runtime**：有Arena分配器，也支持内存复用。但因为要兼顾跨平台，内存策略没有TensorRT那么”量身定制”。好处是你可以手动配置内存Arena的大小和策略。

**TFLite**：使用**Arena机制**——预先分配一块固定大小的内存作为”竞技场”，所有的中间结果都在这块内存里分配和释放。这种方式的好处是内存使用量完全可预测（在模型加载时就确定了），不会出现运行时的内存碎片或意外分配——非常适合嵌入式场景。

```text
// TFLite的Arena大小估算
// arena_size ≈ max(sum of concurrent tensor sizes)
// TFLite在加载模型时会自动计算所需的Arena大小

tflite::MicroInterpreter interpreter(
    model, resolver, tensor_arena, 
    kTensorArenaSize,  // 预分配的Arena大小
    error_reporter
);
```

### 2.3 多线程调度

**TensorRT**：在GPU上天然是并行执行的，CPU端的调度开销很小。支持多Stream实现pipeline并行。

**ONNX Runtime**：支持线程内并行（一个算子用多个线程执行）和线程间并行（不同算子并行执行）。可以配置线程数和亲和性。

```text
# ONNX Runtime的多线程配置
import onnxruntime as ort

sess_options = ort.SessionOptions()
sess_options.intra_op_num_threads = 4  # 算子内并行线程数
sess_options.inter_op_num_threads = 2  # 算子间并行线程数
sess_options.execution_mode = ort.ExecutionMode.ORT_PARALLEL
```

**TFLite**：支持多线程但方式相对简单。对于CPU推理，可以指定使用的线程数。对于Delegate（GPU/NPU），调度由Delegate内部控制。

```text
# TFLite的多线程配置
interpreter = tf.lite.Interpreter(
    model_path="model.tflite",
    num_threads=4
)
```

### 三、平台适配指南

### 3.1 Jetson系列（Nano / Xavier NX / Orin）

**推荐框架**：TensorRT（首选），ONNX Runtime（备选）

理由不用多说——Jetson是NVIDIA的亲儿子，TensorRT在上面的优化深度无人能及。FP16推理几乎免费（Jetson的GPU原生支持FP16），INT8量化配合TensorRT的校准器效果也很好。

ONNX Runtime在Jetson上也能用（通过TensorRT Execution Provider），本质上还是调TensorRT，但多了一层抽象。

**实测数据（MobileNet-V2, Jetson Nano, batch=1）**：

- TensorRT FP16: 约8ms
- TensorRT INT8: 约5ms
- ONNX Runtime (TRT EP): 约9ms
- TFLite GPU Delegate: 约15ms

### 3.2 树莓派（Raspberry Pi 4/5）

**推荐框架**：TFLite（首选），ONNX Runtime（备选）

树莓派是ARM CPU，没有NVIDIA GPU，TensorRT直接出局。TFLite对ARM CPU的优化非常好（NEON SIMD指令集、XNNPACK后端），在树莓派上的推理速度通常比ONNX Runtime快20%-30%。

```text
# 树莓派上安装TFLite
pip3 install tflite-runtime
```

**实测数据（MobileNet-V2, RPi 4, 4线程）**：

- TFLite (XNNPACK): 约45ms
- ONNX Runtime (CPU): 约60ms

### 3.3 STM32 / MCU

**推荐框架**：TFLite Micro（首选），STM32Cube.AI（STM32专用）

MCU上的选择很有限。TFLite Micro是目前最通用的MCU推理框架，支持Cortex-M系列。STM32Cube.AI是ST自家的工具，对STM32的优化更深入（能自动利用DSP指令和DMA），但只能在STM32上用。

ONNX Runtime和TensorRT在MCU上都跑不了——别想了。

### 3.4 手机SoC（骁龙/联发科/麒麟）

**推荐框架**：TFLite + GPU/NNAPI Delegate，或各厂商SDK

手机上的情况最复杂：有CPU、有GPU、有NPU，每家厂商的NPU还不一样。

TFLite通过**Delegate机制**可以调用不同的加速器：

- GPU Delegate：调用手机GPU（OpenCL/OpenGL ES）
- NNAPI Delegate：调用Android NNAPI（会自动分发到NPU/DSP/GPU）

但如果要发挥NPU的全部性能，可能还是得用厂商自己的SDK：

- 高通：SNPE / QNN
- 联发科：NeuroPilot
- 华为：HiAI

### 3.5 瑞芯微/全志/算能等国产AI芯片

**推荐框架**：各厂商的自有框架

瑞芯微用RKNN-Toolkit，算能用TPU-MLIR，全志用AWQ。这些框架通常接受ONNX或Caffe格式的输入模型，转换成自家NPU能执行的格式。

不要指望用通用框架就能发挥这些NPU的全部性能——它们的硬件架构跟通用GPU差异很大，必须用专用工具链才能做到高效映射。

### 四、模型转换中的兼容性问题

模型转换是部署流程中最容易翻车的环节。以下是常见的坑和填坑方法。

### 4.1 算子不支持

**症状**：转换时报错”Unsupported op: XXX”。

**常见的”问题算子”**：

- 自定义算子（自己写的C++/CUDA op）
- 动态形状操作（torch.where、条件分支）
- 高级索引操作（gather、scatter、非连续slice）
- 一些新的激活函数（如SiLU/Mish在老版本框架中可能不支持）

**解决思路**：

1. 先看看新版本框架是否已支持
2. 用等价的已支持算子组合替代
3. 注册自定义算子（TensorRT支持Plugin，TFLite支持Custom Op）
4. 实在不行，把模型拆成两段：不支持的部分用CPU跑，其余部分用加速器跑

### 4.2 动态形状 vs 静态形状

TensorRT传统上更喜欢静态形状（编译时确定输入尺寸），虽然新版本支持了动态形状，但性能可能不如静态形状。

TFLite和ONNX Runtime对动态形状的支持相对友好一些。

**建议**：嵌入式部署时尽量用静态形状。输入图片统一Resize到固定尺寸，batch size固定为1。这样推理框架可以做更多的预优化。

### 4.3 精度不一致

转换后的模型输出跟原始PyTorch/TensorFlow模型的输出对不上——这种情况比你想象的要常见。

**常见原因**：

- 浮点精度差异（FP32在不同平台上的计算顺序不同，结果可能有微小差异）
- BN层的折叠方式不同
- Padding方式的差异（SAME vs VALID在不同框架的实现可能有像素级偏差）
- Resize/Upsample的插值实现差异

**排查方法**：

1. 逐层对比输出——找出第一个出现差异的层
2. 用简单输入（如全1、全0、单位矩阵）测试——排除数据相关的问题
3. 检查模型转换时的配置选项——有没有什么默认参数被改了

```text
# ONNX模型的精度验证
import onnxruntime as ort
import numpy as np

ort_session = ort.InferenceSession("model.onnx")
ort_output = ort_session.run(None, {"input": test_data})[0]

# 与PyTorch输出对比
torch_output = pytorch_model(torch.tensor(test_data)).numpy()

max_diff = np.max(np.abs(ort_output - torch_output))
print(f"最大绝对误差: {max_diff}")
# FP32下，max_diff < 1e-5 一般认为是正常的浮点误差
# 如果 > 1e-3，可能有问题需要排查
```

### 4.4 PyTorch导出ONNX的常见问题

PyTorch的`torch.onnx.export`是动态trace的方式，有些Python控制流在trace时会被”固化”：

```text
# 这段代码在export时会被固化为其中一个分支
if x.shape[0] > 1:
    x = batch_norm(x)
else:
    x = instance_norm(x)

# 解决方案：用torch.jit.script或重构代码避免动态控制流
```

建议导出前先用`torch.onnx.verification`做一轮验证，确认导出的ONNX模型在数值上跟原始模型一致。

### 五、选型决策树

说了这么多，来一个简化版的决策流程：

```text
你的目标硬件是什么？
│
├── NVIDIA GPU / Jetson
│   → TensorRT（不接受反驳）
│
├── ARM CPU（树莓派 / 通用Linux Board）
│   → TFLite（XNNPACK后端）
│   → 备选：ONNX Runtime
│
├── MCU（Cortex-M系列）
│   → TFLite Micro
│   → STM32专用：STM32Cube.AI
│
├── 手机
│   → TFLite + NNAPI/GPU Delegate
│   → 追求极致性能：厂商SDK
│
├── 国产AI芯片（瑞芯微/算能/全志等）
│   → 厂商自有工具链
│   → 输入格式通常是ONNX
│
└── 需要跨平台部署？
    → ONNX Runtime（一个模型到处跑）
```

### 六、一个省心的建议

如果你刚开始做嵌入式AI部署，不确定用什么框架，有一个省心的策略：

**先把模型导出成ONNX格式。**

ONNX是目前最通用的模型交换格式，几乎所有推理框架都支持导入ONNX。你先用ONNX Runtime跑通整条Pipeline，验证精度和功能；然后再根据目标硬件选择最优框架做进一步优化。

这样做的好处是：万一目标硬件换了（项目需求变更这种事太常见了），你的模型不用从头转换，换个框架就行。
