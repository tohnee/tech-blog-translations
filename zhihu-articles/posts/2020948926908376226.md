## 前言

第一篇以纯 DP 视角走读了 Megatron 的训练主循环、DDP 和分布式优化器，建立了无 CP 时的梯度基线：

```python
grad_final = loss_scale × mean(token_loss) × ∂param
```

并在末尾预留了四个扩展点：`with_context_parallel=True` 的优化器通信组、`calculate_per_token_loss=True` 的归一化路径、`gradient_scaling_factor` 从 `1/dp` 到 `1/(dp×cp)` 的变化、以及梯度基线成立的隐含前提——DP 通信组覆盖所有参与训练的卡。本文从这四个扩展点出发，逐一兑现。

理解本文需要先回答一个问题：**为什么要以 DP 视角为 CP 做铺垫？** 这和 Megatron 的设计哲学直接相关——Megatron 把 CP 吸收进 DP 维度，作为"扩展 DP"统一处理。

> 从本质上讲，DP 和 CP 都是数据维度的切分：DP 切 batch，CP 切 seq。两者的通信组在初始化时就合并成 `_DATA_PARALLEL_GROUP_WITH_CP`，**DDP 和分布式优化器直接复用这个扩展组，运行时无需任何额外逻辑。**

第一篇介绍了 DP 路径上的细节，本文引入 CP 时变化的只是通信组的范围、loss 归一化的分母、梯度缩放系数——**训练循环本身的框架**不需要任何改动。

## 一、CP 初始化：通信组的建立

### 1.1 设计哲学与核心问题

第一篇提到分布式训练框架的并行初始化要解决一个根本问题：在 N 张卡上，如何让每张卡知道自己在整个并行拓扑里的位置，以及和哪些卡通信？

这个问题在只有 DP 时还比较简单——所有卡等分数据、梯度求平均即可。引入 CP 后，问题变得微妙：

> CP 组内的卡处理同一序列的不同片段，它们的梯度语义是求和而非平均（完整序列的 loss 等于各片段 loss 之和），和 DP 组内"不同样本、梯度取平均"截然不同。如果把 CP 当作独立维度处理，就需要在训练的热路径上为 CP 梯度单独设计一套归约逻辑，运行时开销不可避免。

Megatron 的答案是：**把 CP 吸收进 DP 维度，作为"扩展 DP"统一处理**。通信组构建时用 `dp×cp` 的笛卡尔积生成扩展 DP 组，数据读取时在进模型前就完成序列切分，DDP 和分布式优化器直接复用扩展 DP 组做梯度归约——**框架层面唯一需要为 CP 额外做的事，是在前向计算 loss 之后乘以 `cp_size` 做补偿（详见第三章）。**

### 1.2 RankGenerator：正交分组的数学基础

第一篇提到 Megatron 会在 `_initialize_distributed` 中完成分布式初始化，`order='tp-cp-ep-dp-pp'` 决定了全局 rank 的排列方式，所有并行组的 rank 编号由 `RankGenerator` + `generate_masked_orthogonal_rank_groups` 统一生成。

**order 的排列逻辑**

`order` 从内到外，TP 在最内层（要求最高带宽），PP 在最外层（通信量最小）。这个顺序不是约定，而是各维度通信特征决定的。这里简单概述一下各并行策略的通信特征：

- **TP（张量并行）**：每个 `decode_layer` 前向有两次 AllReduce，反向同样。通信量大且难以被计算掩盖，放在最内层。
- **CP（上下文并行）**：Ring Attention 在 FA 计算期间引入 `cp-1` 轮 P2P 通信，通信开销仅次于 TP，放在 TP 的紧外层。
- **EP（专家并行）**：每层前向有两次 all-to-all，通信开销通常小于 CP，取决于专家数和 token 路由密度。
- **DP（数据并行）**：反向梯度 AllReduce，或分布式优化器的 reduce-scatter + all-gather。通信相对容易被掩盖，放在外层。
- **PP（流水线并行）**：只在 stage 边界发生一次 P2P，通信频率最低，放在最外层。

> **在极致性能调优场景，也可以根据实际情况合理调整order逻辑。**

**RankGenerator 的工作方式**

大约在 2024 年做集群性能调优时，遇到过快慢卡问题——很多同学通常能定位到哪个通信算子慢，却不能马上知道是和哪些卡通信慢，可能是哪台机器通信链路出现问题。现在不少 profiling 工具已经能直接给出通信拓扑信息，但理解 rank 生成逻辑本身仍然有价值——**能够迅速知道某台机器上的进程属于哪些通信组，会做什么通信。**

RankGenerator 的核心思想是把 `world_size` 张卡看成一个多维数组，`order` 决定各维度的排列顺序（内层步长小，外层步长大），`mask` 决定"沿哪些维度切片"——`mask=True` 的维度是组内变化的维度，`mask=False` 的维度是组间固定的维度：

```python
def generate_masked_orthogonal_rank_groups(world_size, parallel_size, mask):
    for group_index in range(num_of_group):
        decomposed_group_idx = decompose(group_index, unmasked_shape)
        for rank_in_group in range(group_size):
            decomposed_rank_idx = decompose(rank_in_group, masked_shape)
            real_gpu_id = (
                inner_product(decomposed_rank_idx, masked_stride)
                + inner_product(decomposed_group_idx, unmasked_stride)
            )
```

以 `world=8, order='tp-cp-dp', tp=1, cp=2, dp=4` 为例，`ordered_size=[1,2,4]`，`global_stride=[1,1,2,8]`。调用 `get_ranks('cp')`，`mask=[False,True,False]`，cp 维度步长为 1：

```python
group_index=0（dp_rank=0）: [0, 1]
group_index=1（dp_rank=1）: [2, 3]
group_index=2（dp_rank=2）: [4, 5]
group_index=3（dp_rank=3）: [6, 7]
```

CP 组内 rank 连续——这是 `order` 里 CP 在 DP 内层（步长更小）的直接结果。如果把 `order` 改成 `'tp-dp-cp'`，cp 步长变为 2，CP 组变成 [0,2]、[1,3]，组内 rank 不再连续，**物理拓扑上可能跨机，P2P 通信延迟上升。**

调用 `get_ranks('dp-cp')` 时，`mask=[False,True,True]`，dp 和 cp 两个维度同时打开，生成的每个组包含同一 TP+PP 位置上所有 `dp×cp` 张卡——这正是 `_DATA_PARALLEL_GROUP_WITH_CP` 的构建依据。

*【图示：world=8, cp=2, dp=4 的 rank 拓扑】*

### 1.3 通信组的初始化

所有并行组集中在 `parallel_state.initialize_model_parallel` 里初始化：

```python
# _CONTEXT_PARALLEL_GROUP：同一条序列被切分到的所有卡
# 职责：loss_func 里的 CP AllReduce
for ranks in generator_wrapper('cp'):
    group = create_group(ranks, group_desc='CONTEXT_PARALLEL_GROUP')
    if rank in ranks:
        _CONTEXT_PARALLEL_GROUP = group

# _DATA_PARALLEL_GROUP_WITH_CP：扩展 DP 组，CP 维度被吸收进来
# 职责：DDP 梯度归约 + 分布式优化器 reduce-scatter
for ranks_with_cp in generator_wrapper('dp-cp'):
    group_with_cp = create_group(ranks_with_cp, group_desc='DATA_PARALLEL_GROUP_WITH_CP')
    if rank in ranks_with_cp:
        _DATA_PARALLEL_GROUP_WITH_CP = group_with_cp
```

两个 group 职责不同，不可混淆。

1. `_CONTEXT_PARALLEL_GROUP` 用在 `loss_func` 里用于**聚合同一序列各片段的 loss；**
2. `_DATA_PARALLEL_GROUP_WITH_CP` 是梯度归约和参数分片的通信域，是 CP 对整个框架影响最深的设计——它把 CP 组内的卡当作"扩展 DP 维度"，**DDP 和分布式优化器直接用这个 group，切分优化器，缩放梯度。**

### 1.4 分层 CP：跨节点场景的通信分级

当 `cp_size` 超过单机卡数，CP 组必然跨节点，节点间走 InfiniBand，P2P 延迟远高于 NVLink。Megatron 的解法是分层 CP（`hierarchical_context_parallel_sizes`）：把大 CP 组按物理拓扑拆成多级子组，节点内和节点间用不同的通信原语。以 `cp=8, hierarchical_group_sizes=[2,4]`，单机 2 卡（共 4 节点）为例：

```python
level0（size=2，节点内）：[0,1], [2,3], [4,5], [6,7]  ← NVLink P2P
level1（size=4，跨节点）：[0,2,4,6], [1,3,5,7]        ← IB AllGather
```

每个 rank 最终持有一个长度为层级数的 group 列表。Ring Attention 里 `cp_comm_type='a2a+p2p'` 时，节点内走 all-to-all，节点间走 P2P，两级通信叠加把跨节点通信量压到最低。

![](https://pica.zhimg.com/v2-56239fd3e80889534d3eb77ad117e31c_r.jpg)
*【图示：分层 CP 示意】*

💡 **小结**

CP 初始化的核心是两个通信组的正确建立：`_CONTEXT_PARALLEL_GROUP` 用于 `loss_func` 里聚合同一序列的 loss，`_DATA_PARALLEL_GROUP_WITH_CP` 用于 DDP 和分布式优化器的梯度归约。

两者的构建都依赖 `RankGenerator` 的正交分组算法——`order` 里 CP 在 DP 内层保证了组内 rank 连续，`get_ranks('dp-cp')` 把 CP 维度吸收进 DP 维度生成扩展组，"CP 作为扩展 DP"的设计哲学在初始化时就已完全确定，运行时无需任何额外开销。

跨节点场景下分层 CP 把大 CP 组按物理拓扑拆成多级，是 `cp_size` 超过单机卡数时的必要设计，也是下篇 `cp_comm_type='a2a+p2p'` 的硬件基础。

## 二、数据流：序列切分的时机与实现

### 2.1 设计哲学与核心问题

CP 的数据切分在哪一层做，对显存效率有决定性影响。Megatron 的选择是**在数据读取阶段就完成序列切分**——进模型之前序列已经是 `seq/cp` 长度，embedding、FFN、LayerNorm 全程只处理自己那段序列，显存节省覆盖整个前向路径。**代价是 attention 层需要感知 CP 的存在**——每张卡只有部分序列，causal attention 的跨卡依赖必须通过 Ring Attention 解决，这是下篇的主题。

### 2.2 切分时序：从训练循环到数据读取

序列切分发生在每个 micro_batch 前向开始之前。调用链如下：

```python
forward_backward_no_pipelining
  → forward_step（框架层）
    → forward_step（pretrain_gpt.py，用户定义）
        tokens, labels, loss_mask, ... = get_batch(data_iterator)
          → get_batch_on_this_tp_rank(data_iterator)  # Step 1: TP 组内广播完整序列
          → get_batch_on_this_cp_rank(batch)           # Step 2: CP 维度序列切分
        output_tensor = model(tokens, position_ids, attention_mask, labels=labels)
```

两步顺序不可颠倒。`get_batch_on_this_tp_rank` 由 TP rank 0 从 `data_iterator` 读取完整序列，广播给同组其他 rank——**广播完成后 TP 组内所有卡持有完全相同的完整序列。**此后各卡按自己的 `cp_rank` 独立做 zigzag 切分，结果天然一致，不需要任何额外通信。

### 2.3 zigzag 切分：causal attention 下的负载均衡

直接把序列均分成 `cp_size` 份会导致严重负载不均。causal attention 下 token $i$ 需要 attend 到所有位置 $\leq i$ 的 token，计算量正比于 $i+1$ 。均分时后段卡计算量远大于前段卡：

```python
均分方案（cp=2，seq=8）：
  GPU0: [0,1,2,3]  计算量 = 1+2+3+4 = 10
  GPU1: [4,5,6,7]  计算量 = 5+6+7+8 = 26   ← 2.6 倍不均衡
```

`get_batch_on_this_cp_rank` 的解法是切成 `2*cp_size` 份再做交叉分配：

```python
val = val.view(*val.shape[0:seq_dim], 2 * cp_size, val.shape[seq_dim] // (2 * cp_size), ...)
index = torch.tensor([cp_rank, (2 * cp_size - cp_rank - 1)], device="cpu", pin_memory=True).cuda(non_blocking=True)
val = val.index_select(seq_dim, index)
val = val.view(*val.shape[0:seq_dim], -1, ...)
```

分配规则是关于序列中点镜像对称，前段计算量小的片段和后段计算量大的片段配对：

```python
zigzag 方案（cp=2，seq=8，切成 4 份）：
  GPU0: [0,1] + [6,7]  计算量 = (1+2) + (7+8) = 18
  GPU1: [2,3] + [4,5]  计算量 = (3+4) + (5+6) = 18   ← 完全均衡
```

更一般地，GPU $k$ 分到第 $k$ 段和第 $2N-k-1$ 段，两段计算量之和严格等于总计算量的 $1/N$ ，负载完全均衡。`index` 用 `pin_memory=True` + `non_blocking=True` 创建，是热路径上有意义的工程优化。

`position_ids` 和 `tokens` 走完全相同的 zigzag 路径，切出来的是全局位置编号的子集（GPU0 持有 `[0,1,6,7]`，GPU1 持有 `[2,3,4,5]`），**保留全局编号是 RoPE 正确性的前提，也是下篇 Ring Attention 里 `max_seqlen *= cp_size` 能正确还原完整序列长度的隐含前提。**

`attention_mask` 的切分维度是 `seq_dim=2`，与普通张量的 `seq_dim=1` 不同。但现代训练配置下 `attention_mask` 通常为 None——FlashAttention 内部处理 causal mask，这里是对旧配置的兼容。PP 场景下部分字段为 None，`val is not None` 的判断保证这些字段直接跳过，`get_batch_on_this_cp_rank` 对 PP 完全透明。

![](https://pic3.zhimg.com/v2-03417aae7cde1788528f9f8dea7a43d2_r.jpg)
*【图示：zigzag 切分负载均衡示意】*

💡 **小结**

序列切分在每个 micro_batch 前向开始之前完成，发生在 `get_batch` 内部的 `get_batch_on_this_cp_rank` 调用里。

切分后模型全程只处理 `seq/cp` 长度的序列，显存节省覆盖 embedding、FFN、LayerNorm 等所有层。

zigzag 切分在数学上严格保证每张卡的 causal attention 计算量为总量的 $1/N$ ，负载完全均衡。`position_ids` 沿相同路径切分且保留全局编号，是 RoPE 正确性和下篇 Ring Attention 的隐含前提。

## 三、CP 引入后的梯度变化

### 3.1 设计哲学与核心问题

第一篇建立了无 CP 时的梯度基线：

```python
grad_final = loss_scale × mean(token_loss) × ∂param
```

这个基线成立有一个隐含前提：**DP 通信组覆盖所有参与训练的卡，`1/dp` 的平均是全局平均。**引入 CP 后，这个前提被打破——**同一条序列被切给 cp 张卡，这 cp 张卡的梯度在语义上应该求和而非平均。**

Megatron 的选择是把 CP 吸收进 DP 维度统一处理——DDP 和分布式优化器直接复用扩展 DP 组，框架无需为 CP 单独设计一套归约逻辑。代价是 DDP 会对 CP 维度也做平均，梯度语义错误，需要人工补偿。**补偿的手段是在 loss 层面预乘 `cp_size`，把初始梯度放大 cp 倍，抵消 DDP 多除的那一个 cp。**

本章按训练时序展开——从 loss 计算到反向传播，逐一描述三个变化点和补偿机制，**第4章会用 `calculate_per_token_loss=True` 路径作为对照。**

### 3.2 为什么 CP 组内的梯度应该求和而非平均

在分析具体代码变化之前，先建立一个直觉：CP 和 DP 在梯度语义上有根本区别。

**DP 的情形**：两张卡处理的是完全不同的样本，各自独立计算 loss。样本 A 的梯度和样本 B 的梯度都是对同一参数的独立估计，取平均才能得到期望梯度——这是随机梯度下降的基本语义。

**CP 的情形截然不同**。以序列 `[t0,t1,t2,t3]` 切成两段为例，GPU0 持有 `[t0,t1]`，GPU1 持有 `[t2,t3]`，两者处理的是**同一条序列的不同片段**。完整序列的 loss 是：

$$$L = L_{\text{GPU0}} + L_{\text{GPU1}}$$$

对参数 $\theta$ 求偏导：

$$$\frac{\partial L}{\partial \theta} = \frac{\partial L_{\text{GPU0}}}{\partial \theta} + \frac{\partial L_{\text{GPU1}}}{\partial \theta}$$$

两段的梯度贡献是**加法关系**，不是平均关系。如果对 CP 组内的梯度取平均（除以 cp），就相当于把完整序列的梯度缩小了 cp 倍，参数更新量不足，等效学习率被压低。

DDP 把 `_DATA_PARALLEL_GROUP_WITH_CP`（world size = `dp×cp`）当作通信域，`gradient_scaling_factor = 1/(dp×cp)`，通信在 `dp×cp` 张卡上做 SUM 后再乘缩放系数，等价于对所有 `dp×cp` 张卡的梯度取平均——对 DP 维度正确，对 CP 维度多除了一个 cp。`loss × cp_size` 的预补偿正是为了抵消这个多余的除法。

![](https://pica.zhimg.com/v2-c4d227e0864e8c7b3ba49c803dbfeff2_r.jpg)
*【图示：DP vs CP 梯度语义对比】*

### 3.3 第一个变化点：`loss_func` 里的两次 AllReduce

`loss_func` 是梯度链路的起点，引入 CP 后这里发生了第一个关键变化——新增 CP AllReduce，把各片段的局部 loss 聚合成完整序列 loss：

```python
# 第一次：CP AllReduce，梯度正确性保证
if args.context_parallel_size > 1:
    torch.distributed.all_reduce(loss, group=mpu.get_context_parallel_group())

# 第二次：DP AllReduce，仅用于日志打印
reporting_loss = loss.clone().detach()
torch.distributed.all_reduce(reporting_loss, group=mpu.get_data_parallel_group())
```

两次 AllReduce 目的完全不同，不可混淆。

1. 第一次在 `_CONTEXT_PARALLEL_GROUP` 上聚合，执行后 CP 组内所有 rank 持有相同的 `loss[0]`（完整序列 token loss 之和）和 `loss[1]`（完整序列 token 数）。**这次 AllReduce 参与反向传播，是梯度正确性的保证**——没有它，`loss[0]` 只是当前卡序列片段的局部 loss sum，`loss[1]` 只是局部 token 数，两者相除得到的 `mean(token_loss)` 在数学上就是错的：分子漏掉了其他片段的 loss 贡献，分母也不是完整序列的 token 总数，反向传播的起点从根本上就偏离了"完整序列 per-token 平均 loss"的语义。
2. 第二次在纯 DP 组（不含 CP）上聚合 `reporting_loss`，**结果仅用于日志打印**，`clone().detach()` 保证不参与反向传播。`loss[1]` 已经是 CP AllReduce 后的完整 token 数，日志语义正确，不需要再跨 CP 组聚合。

`local_num_tokens` 从第一次 AllReduce 之后的 `loss[1]` clone 出来，是完整序列的有效 token 数，**向上返回给 `forward_step` 用作归一化分母——这是下一节的输入。**

### 3.4 第二个变化点：`forward_step` 里的 `× cp_size`

`loss_func` 返回完整序列 loss 之后，框架层 `forward_step` 立即对其归一化，这是第二个变化点，也是整个梯度链路里最核心的补偿操作：

```python
if len(outputs) == 3:
    output_tensor, num_tokens, loss_reduced = outputs
    if not config.calculate_per_token_loss:
        output_tensor /= num_tokens      # ① 除以完整序列 token 数 → per-token 平均 loss
        output_tensor *= parallel_state.get_context_parallel_world_size()  # ② × cp_size 预补偿
        output_tensor /= num_microbatches  # ③ 梯度累积归一化
```

注意调用顺序：`loss_func` 在 `forward_step` 内部被调用，CP AllReduce 发生在 `loss_func` 里，`× cp_size` 紧随其后在 `forward_step` 里完成——先有完整序列 loss，再做归一化和补偿。

- ① `num_tokens` 已经是经过 CP AllReduce 的完整序列 token 数，`/= num_tokens` 得到完整序列的 per-token 平均 loss，而非局部片段的平均。
- ② `× cp_size` 正是 3.2 节分析的补偿：**DDP 通信时会多除一个 cp，在这里提前乘回来。**
- ③ `/num_microbatches` 控制每步梯度累积的贡献比例。`num_microbatches` 个 microbatch 的梯度在 `grad_data` 里逐步累加，`/num_microbatches` 与累加的 `×num_microbatches` 相消，**最终梯度量级不含 `num_microbatches`。**

`× cp_size` 不只出现在三元组路径里，`loss_func` 返回二元组时同样有：

```python
else:
    output_tensor, loss_reduced = outputs
    output_tensor *= parallel_state.get_context_parallel_world_size()
    output_tensor /= num_microbatches
```

两条路径都需要补偿，补偿系数相同。**这里需要注意的是开启calculate_per_token_loss，是不需要乘以cp系数的，具体内容还是放在第四章阐述。**

### 3.5 第三个变化点：DDP 通信组扩展

反向传播触发 DDP 梯度归约，这是第三个变化点：

```python
# calculate_per_token_loss=False 时
gradient_scaling_factor = 1.0 / parallel_state.get_data_parallel_world_size(with_context_parallel=True)
# = 1 / (dp × cp)
```

通信域从 `_DATA_PARALLEL_GROUP` 扩展到 `_DATA_PARALLEL_GROUP_WITH_CP`，`gradient_scaling_factor` 从 `1/dp` 变为 `1/(dp×cp)`。**这正是 3.2 节说的"多除了一个 cp"，3.4 节的 `× cp_size` 正是为了抵消它。**

`calculate_per_token_loss=True` 时 `gradient_scaling_factor` 直接设为 `1.0`，框架加了防御性校验：

```python
if config.calculate_per_token_loss:
    gradient_scaling_factor = 1.0
else:
    target = 1.0 / parallel_state.get_data_parallel_world_size(with_context_parallel=True)
    assert gradient_scaling_factor == target
```

**为什么开启calculate_per_token_loss逻辑会不一样，第4章重点阐述。**

DDP 和分布式优化器均通过 `with_context_parallel=True` 接收扩展 DP 组，内部逻辑无任何 CP 特判，CP 对这两个模块完全透明。

将三个变化点串成完整推导：

```python
单个 microbatch 反向起点：
  loss_scale × local_mean(token_loss) × cp_size / num_microbatches

num_microbatches 个 microbatch 累加（/num_microbatches 与累加相消）：
  grad_accumulated = loss_scale × cp_size × local_mean(token_loss) × ∂param

DDP 通信（gradient_scaling_factor = 1/(dp×cp)，SUM over dp×cp）：
  grad_final = loss_scale × cp_size × local_mean(token_loss) × ∂param
             = loss_scale × global_mean(token_loss) × ∂param
               ↑ cp_size × local_mean = global_mean，与无 CP 基线语义完全一致
```

三个变化点共同保证梯度语义的正确性——**`cp_size × local_mean(token_loss)` 恰好等于 `global_mean(token_loss)`，与无 CP 基线完全等价，是完整序列梯度本来应有的量级。**

![](https://pic1.zhimg.com/v2-5fd79b3de70d3b2c162a62cce0e5b698_r.jpg)
*【图示】完整梯度链路*

**至此三个变化点都已分析完毕。回头看第一章提到的 Megatron 和 VERL Ulysses 在补偿时机上的差异，现在可以精确描述了：**

这个补偿思路和 VERL 集成 Ulysses 时的梯度处理如出一辙，但触发时机和原因各有不同：

- **Megatron 的情形**：`loss_func` 在 `_CONTEXT_PARALLEL_GROUP` 上做 AllReduce，CP 组内所有 rank 此后持有相同的完整序列 loss。这次 AllReduce 参与反向传播。随后 DDP 把 `dp×cp` 张卡当作扩展 DP 统一处理，`gradient_scaling_factor = 1/(dp×cp)`，相当于对 CP 维度也做了平均——多除了一个 cp。补偿在前向出口完成：**`forward_step` 里对 loss 预乘 `cp_size`**，使反向起点的梯度量级放大 `cp_size` 倍，恰好抵消 DDP 多除的那一个 cp。
- **VERL Ulysses 的情形**：`gather_outputs_and_unpad` 在 Step 5 把各卡的局部 `log_probs` AllGather 成完整结果，之后每张卡基于完整结果独立计算 `pg_loss`——AllGather 之后还有前向计算，不能在前向预乘补偿。**因此补偿推迟到 `Gather.backward`，在反向出口乘以 `sp_world_size`**，事后撤销 FSDP 按 `world_size = dp×sp` 归一化时多除的那一个 sp。

![](https://picx.zhimg.com/v2-28374a46c5a5e4e63eb7931323ee4a07_r.jpg)
*【图示：Megatron CP 补偿 vs VERL Ulysses 补偿的时机对比】*

两者的本质相同：通信组的归一化行为多除了一个并行系数，需要在某处乘回来。差别只在补偿的时机——Megatron 在前向出口预乘（AllReduce 后 loss 已经完整，可以立刻补偿）；VERL 在反向出口补偿（AllGather 后还有前向计算，不能提前介入）。

> 切分、聚合、归一化时机三者是非常重要的，在多模态场景开发CP往往需要重点考量。

**当然 Megatron 还有 `calculate_per_token_loss=True` 的路径，梯度处理会更复杂，第四章详述。**

### 3.6 `finalize_model_grads`：不同参数的梯度归约域

`finalize_model_grads` 里不同类型的参数走不同的通信域，背后的逻辑是"谁切分了这个参数的哪个维度，谁就需要参与归约"：

**普通参数**：梯度在 `_DATA_PARALLEL_GROUP_WITH_CP` 上归约。CP 切分了序列维度，序列上的梯度贡献分散在 CP 组内各卡，必须跨 CP 聚合。

**LayerNorm 参数（TP-SP 下）**：走纯 TP 组，触发条件是 `sequence_parallel=True` 或 `qk_layernorm=True`。CP 只切分序列维度，不切分 LayerNorm 的参数维度——每张 CP 卡本地的 LayerNorm 梯度已经是完整的，只需要在 TP 组内 AllReduce。纯 CP 不开 TP-SP 时这个 AllReduce 不执行。

**embedding 参数（PP 首尾共享）**：走 PP embedding 专用组，与 CP 无关。

| 参数类型 | 归约组 | 原因 |
| --- | --- | --- |
| 普通参数 | _DATA_PARALLEL_GROUP_WITH_CP | CP 切分了序列，梯度在 CP 维度不完整 |
| LayerNorm（TP-SP） | TP 组 | CP 不切分参数维度，本地梯度已完整 |
| embedding（PP） | PP embedding 专用组 | PP 首尾共享，与 CP 无关 |

前文提到，若开启了 `calculate_per_token_loss`，`gradient_scaling_factor` 会强制设为 `1.0`——**DDP 梯度同步阶段只做聚合，不做缩放，真正的缩放逻辑留在 `finalize_model_grads` 里：**

```text
if num_tokens is not None:
    # Step 1：PP 广播，num_tokens 从 last stage 同步到所有 pipeline stage
    torch.distributed.broadcast(
        num_tokens,
        src=parallel_state.get_pipeline_model_parallel_last_rank(),
        group=parallel_state.get_pipeline_model_parallel_group(),
    )

    # Step 2：DP AllReduce，得到全局有效 token 数（纯 DP 组，不含 CP）
    torch.distributed.all_reduce(
        num_tokens,
        group=parallel_state.get_data_parallel_group()
    )

    # Step 3：用全局 token 数缩放所有参数的梯度
    for model_chunk in model:
        if num_tokens > 0:
            model_chunk.scale_gradients(1.0 / num_tokens)
```

Step 2 用的是纯 DP 组（不含 CP），而非 `_DATA_PARALLEL_GROUP_WITH_CP`。这里是有意为之——**`num_tokens` 在 `loss_func` 里已经经过了 CP AllReduce，每张卡持有的已经是完整序列的 token 数；**Step 2 只需要在 dp 张卡之间汇总各 microbatch 的完整序列 token 数，得到全局分母。**若误用含 CP 的组，分母会再乘一次 cp，梯度量级反而偏小。**这条路径的完整数学推导和与 `False` 路径的等价性分析，见第四章。

### 3.7 CP 引入的变化总结

| 环节 | 无 CP 时 | 引入 CP 后 | 变化原因 |
| --- | --- | --- | --- |
| loss_func 第一次 AllReduce | 无 | CP AllReduce → 完整序列 loss sum | CP 组内序列被切分，需聚合完整 loss |
| loss_func 第二次 AllReduce | DP AllReduce（日志） | 同左，通信域不变 | 纯日志用途，不参与反向 |
| num_tokens | 本卡 token 数 | CP AllReduce → 完整序列 token 数 | 同上 |
| forward_step | / num_tokens / num_microbatches | / num_tokens × cp_size / num_microbatches | 补偿 DDP 多除的 cp |
| DDP group | _DATA_PARALLEL_GROUP（dp 张卡） | _DATA_PARALLEL_GROUP_WITH_CP（dp×cp 张卡） | CP 组内卡共享参数，需参与梯度归约 |
| gradient_scaling_factor | 1/dp | 1/(dp×cp)（或 1.0） | 通信域扩大；True 路径交由后续缩放 |
| 最终梯度量级 | loss_scale × mean(token_loss) | loss_scale × cp_size × local_mean(token_loss) = loss_scale × global_mean(token_loss) | cp_size × local_mean = global_mean，语义等价 |

💡 **小结**

CP 对梯度链路的影响集中在三处，按训练时序排列：

- `loss_func` 新增 CP AllReduce 得到完整序列 loss；
- `forward_step` 里 `× cp_size` 在前向出口预补偿；
- DDP 通信组扩展为 `_DATA_PARALLEL_GROUP_WITH_CP`，`gradient_scaling_factor` 变为 `1/(dp×cp)`。

`/num_microbatches` 与梯度累积相消，三个变化点共同保证梯度语义的正确性——`cp_size × local_mean(token_loss)` 恰好等于 `global_mean(token_loss)`，**与无 CP 基线完全等价，是完整序列梯度本来应有的量级。**

**`calculate_per_token_loss=True` 路径跳过 `× cp_size`，`gradient_scaling_factor=1.0`，改在 `finalize_model_grads` 里用全局 token 数精确缩放。**

等长序列时两条路径完全等价；变长序列时 `True` 路径按 token 数加权，各 microbatch 贡献与实际 token 数成正比，梯度语义更准确，是长序列训练的推荐配置。**第四章对两条路径的数学等价性和 bug 演进有完整推导，可对照阅读。**

## 四、`calculate_per_token_loss`：两条归一化路径的设计与取舍

### 4.1 设计哲学与核心问题

第三章分析了 CP 引入后梯度链路的三处变化，其中 `× cp_size` 补偿是最核心的一步。但这个补偿是否对所有场景都适用？

答案是否定的——**Megatron 提供了 `calculate_per_token_loss` 开关，对应两条完全不同的归一化路径，两者在梯度加权语义上有本质差异：等长序列时完全等价，变长序列时 `True` 路径按 token 数加权，梯度方向更准确。**

这个开关的设计背景来自 SFT 训练的一个经典问题：

> 当 batch 内各样本 token 数不等时（packing 场景），用 microbatch 数做归一化分母会给 token 少的样本过高的权重，导致梯度方向偏移。`calculate_per_token_loss=True` 的目标是用全局 token 总数做分母，让每个 token 的贡献权重相等。

然而这个开关和 CP 的交互并不简单——**Megatron 在 0.8.0 版本引入过一次真实的 bug，两条路径对 cp 倍的处理方式截然不同。**本章从数学上完整推导两条路径，并还原 bug 的来龙去脉。

### 4.2 `False` 路径：microbatch 间等权平均

`calculate_per_token_loss=False`（默认）时，归一化在 `forward_step` 里完成，`gradient_scaling_factor = 1/(dp×cp)`：

```python
if not config.calculate_per_token_loss:
    output_tensor /= num_tokens        # ① 除以完整序列 token 数
    output_tensor *= cp_size           # ② × cp_size 预补偿
    output_tensor /= num_microbatches  # ③ 梯度累积归一化
```

以 `dp=1, cp=1, num_microbatches=2, loss_scale=1`，两个 micro_batch 各 4 个 token 为例：

```python
micro_batch 0：token loss = [1,2,3,4]，sum=10，mean=2.5
micro_batch 1：token loss = [5,6,7,8]，sum=26，mean=6.5
```

micro_batch 0 反向起点：`2.5 / 2 = 1.25`，micro_batch 1：`6.5 / 2 = 3.25`

两个 micro_batch 梯度累加，DDP 归约（`gradient_scaling_factor=1`）：

```python
grad_final = (1.25 + 3.25) × ∂param = 4.5 × ∂param
```

`/num_microbatches` 在每个 microbatch 的反向起点上做，累加 `num_microbatches` 次后与 `×num_microbatches` 相消，最终梯度量级不含 `num_microbatches`：

```python
grad_final = loss_scale × mean_over_mb(mean(token_loss)) × ∂param = 4.5 × ∂param
```

各 micro_batch **权重相等**，和 token 数无关。

### 4.3 `True` 路径（修复后）：全局 token 数加权

`calculate_per_token_loss=True` 时，**`forward_step` 里的归一化块完全跳过**，`gradient_scaling_factor=1.0`，loss 直接进入反向传播，**缩放推迟到 `finalize_model_grads`**：

```python
# finalize_model_grads：
torch.distributed.broadcast(num_tokens, src=last_rank, group=pp_group)
torch.distributed.all_reduce(num_tokens, group=get_data_parallel_group())
model_chunk.scale_gradients(1.0 / num_tokens)
```

同样的例子，micro_batch 0 反向起点 `loss[0]=10`，micro_batch 1 反向起点 `loss[0]=26`：

```python
grad_accumulated = (10 + 26) × ∂param = 36 × ∂param
total_num_tokens = 1 × (4+4) = 8
grad_final = 36 / 8 × ∂param = 4.5 × ∂param
```

最终量级：

```text
grad_final = loss_scale × global_mean(token_loss) × ∂param
```

这里**不含显式 cp 倍**。`gradient_scaling_factor=1.0` 使 DDP 做纯 SUM，CP 组内 cp 张卡的 `local_grad` 之和等于完整序列梯度；`total_num_tokens` 是经过 CP AllReduce 的完整序列 token 数，**两者相除 cp 自然对消，不需要任何显式 `× cp_size`。**

### 4.4 等长序列时两条路径完全等价

等长序列时 `global_mean = mean_over_mb(mean)`，两条路径数值完全相同。用四种组合验证（token loss = [1,2,3,4]，dp=1，num_microbatches=1）：

**cp=1，`False`**：反向起点 `2.5`，`gradient_scaling_factor=1` → `grad_final = 2.5 × ∂param`

**cp=1，`True`**：`loss_sum=10`，`total_num_tokens=4` → `grad_final = 2.5 × ∂param`

**cp=2，`False`**：

```python
CP AllReduce 后 loss[0]=10，num_tokens=4
反向起点 = 10/4 × 2 = 5，gradient_scaling_factor=0.5
grad_final = 5 × ∂param_full_seq × 0.5 = 2.5 × ∂param_full_seq  ✓
```

**cp=2，`True`**：

```python
loss[0]=10，gradient_scaling_factor=1.0
grad_accumulated = 10 × ∂param_full_seq
grad_final = 10/4 × ∂param_full_seq = 2.5 × ∂param_full_seq  ✓
```

**四种组合结果完全相同。`False` 路径的 `× cp_size` 和 `gradient_scaling_factor=1/(dp×cp)` 相消；`True` 路径的纯 SUM 让 cp 自然对消。等长序列时两条路径在任意 cp 下都等价。**

![](https://pic1.zhimg.com/v2-7005370959ba873f051eaa501070f672_r.jpg)
*【图示：cp=1 vs cp=2 时两条路径梯度量级对比】*

### 4.5 变长序列下的差异

`dp=1, cp=1, num_microbatches=2`，micro_batch 0 有 2 个 token，micro_batch 1 有 6 个 token：

```python
micro_batch 0：token loss = [1,2]，sum=3，mean=1.5
micro_batch 1：token loss = [3,4,5,6,7,8]，sum=33，mean=5.5
```

**`False` 路径**：

```python
grad_final = (1.5/2 + 5.5/2) × ∂param = 3.5 × ∂param
```

两个 micro_batch **权重相等**，micro_batch 0 只有 2 个 token 却和有 6 个 token 的 micro_batch 1 享有同等权重。

**`True` 路径**：

```python
grad_accumulated = (3 + 33) × ∂param = 36 × ∂param
total_num_tokens = 8
grad_final = 4.5 × ∂param
```

**按 token 数加权**，micro_batch 1 贡献是 micro_batch 0 的三倍，符合"每个 token 贡献相等"的语义。

`True` 路径"更准确"的真正原因：**各 microbatch 按实际 token 数加权，不受 microbatch 切分方式影响。**等长时两者等价，变长时 `False` 路径的等权平均会给 token 少的 microbatch 过高权重，`True` 路径天然避免了这个问题。

![](https://pic1.zhimg.com/v2-e73abbd59e073042fa1389ced99070b6_r.jpg)
*【图示：等长 vs 变长序列下两条路径的梯度量级对比】*

### 4.6 bug 的来龙去脉：两个版本的演进

**阶段一：0.8.0 旧版本**

`× cp` 统一放在 `loss_func` 的返回值里，此时 `_DATA_PARALLEL_GROUP_WITH_CP` 已经存在，`gradient_scaling_factor=1/(dp×cp)`：

```python
# loss_func
return (loss[0] * args.context_parallel_size, local_num_tokens, ...)

# forward_step
if not config.calculate_per_token_loss:
    output_tensor /= num_tokens
    output_tensor /= num_microbatches  # 无 × cp
# True 路径跳过整个块
```

`False` 路径：

```python
反向起点 = loss_scale × loss_sum × cp / num_tokens / num_microbatches
         = loss_scale × cp × local_mean(token_loss) / num_microbatches
累加后：loss_scale × cp × local_mean(token_loss)
DDP（gradient_scaling_factor=1/(dp×cp)）后：loss_scale × local_mean(token_loss)  ✓
```

`True` 路径（`gradient_scaling_factor=1.0`）：

```python
反向起点 = loss_scale × loss_sum × cp（已含 cp）
DDP 纯 SUM，不消 cp
scale_gradients(1/total_num_tokens)
grad_final = loss_scale × cp × global_mean(token_loss) × ∂param  ✗ 多了 cp 倍
```

`True` 路径拿到的 loss 已经含 cp，`gradient_scaling_factor=1.0` 不会消掉这个 cp，最终梯度多了 cp 倍——**阶段一 `False` 路径正确，`True` 路径有 bug**。

**阶段二：修复（当前版本）**

修复把 `× cp` 从 `loss_func` 移到 `forward_step` 的 `False` 路径分支里：

```python
# loss_func（修复后）
return (loss[0].clone(), local_num_tokens, ...)  # 干净的 loss

# forward_step（修复后）
if not config.calculate_per_token_loss:
    output_tensor /= num_tokens
    output_tensor *= cp_size   # × cp 只对 False 路径显式执行
    output_tensor /= num_microbatches
# True 路径跳过，gradient_scaling_factor=1.0，cp 自然对消 ✓
```

两条路径修复后均正确：

```text
False 路径：loss_scale × global_mean(token_loss) × ∂param  ✓
True  路径：loss_scale × global_mean(token_loss) × ∂param  ✓
```

修复的关键洞察：`True` 路径 `gradient_scaling_factor=1.0`，cp 由 DDP 纯 SUM 自然对消，不需要显式 `× cp`。把 `× cp` 统一放在 `loss_func` 里，`True` 路径会多乘一次；移到 `forward_step` 的 `False` 分支，两条路径才能各自正确。

### 4.7 两条路径的对比与选择

|  | False 路径 | True 路径 |
| --- | --- | --- |
| gradient_scaling_factor | 1/(dp×cp) | 1.0 |
| × cp_size | 显式执行，与 gradient_scaling_factor 相消 | 跳过，cp 自然对消 |
| 归一化分母 | num_tokens（单个 microbatch 完整序列） | total_num_tokens（全局所有 microbatch） |
| 各 microbatch 权重 | 相等 | 按 token 数加权 |
| 等长序列等价性 | 与 True 路径完全等价 | 与 False 路径完全等价 |
| 变长序列梯度语义 | 各 microbatch 等权，token 少的样本权重偏高 | 按 token 数加权，语义更准确 |
| 推荐场景 | 等长序列、简单训练 | 变长序列、packing、长序列 CP 训练 |

`True` 路径的本质优势：用全局 token 数做分母，自然吸收了梯度累积和 CP 带来的梯度累加，等长序列时与 `False` 路径完全等价，变长序列时语义更准确——这正是长序列 CP 训练推荐开启 `calculate_per_token_loss=True` 的根本原因。

💡 **小结**

`calculate_per_token_loss` 的两条路径等长序列时完全等价——`False` 路径的 `× cp_size` 和 `gradient_scaling_factor=1/(dp×cp)` 相消，`True` 路径的 `gradient_scaling_factor=1.0` 让 cp 自然对消，四种组合（cp=1/cp=N × False/True）最终梯度量级相同。

**变长序列时差异显现：`False` 路径各 microbatch 等权，`True` 路径按 token 数加权，后者更符合"每个 token 贡献相等"的语义。**

Megatron 0.8.0 版本的 `True` 路径有一个真实 bug——**`× cp` 统一放在 `loss_func` 里，`True` 路径 `gradient_scaling_factor=1.0` 不会消掉这个 cp，最终梯度多了 cp 倍。**修复把 `× cp` 移到 `forward_step` 的 `False` 分支，两条路径才各自正确。

## 💡 全文小结

本文以纯 DP 视角为基线，走读了 Megatron CP 在初始化、数据流、梯度链路三个层面的完整实现。三章内容不是并列的，而是层层递进、共同服务于"把 CP 吸收进 DP 维度"这一核心设计哲学的：

**初始化阶段**确定了 CP 在整个并行拓扑里的位置。`RankGenerator` 的正交分组算法通过 `order='tp-cp-ep-dp-pp'` 保证 CP 组内 rank 连续，最大化通信局部性；`get_ranks('dp-cp')` 把 CP 维度吸收进 DP 维度生成 `_DATA_PARALLEL_GROUP_WITH_CP`，是"CP 作为扩展 DP"在代码层面最直接的体现。

两个 CP 相关通信组职责不同：`_CONTEXT_PARALLEL_GROUP` 只在 `loss_func` 里聚合同一序列的 loss，`_DATA_PARALLEL_GROUP_WITH_CP` 承担梯度归约和参数分片的全部通信，框架其余部分对 CP 完全无感知。跨节点场景下分层 CP 通过 `hierarchical_context_parallel_sizes` 把大 CP 组按物理拓扑拆成多级，节点内走高带宽 NVLink、节点间走低延迟 IB，是 `cp_size` 超过单机卡数时的必要扩展。

**数据流阶段**确定了序列切分的时机与方式。切分在每个 micro_batch 前向开始之前完成——TP 广播先于 CP 切分，广播完成后各卡按自己的 `cp_rank` 独立做 zigzag 切分，结果天然一致，不需要任何额外通信。zigzag 切分（`2*cp_size` 份镜像对称分配）在数学上严格保证每张卡的 causal attention 计算量为总量的 $1/N$ ，负载完全均衡。`position_ids` 沿相同路径切分且保留全局编号，是 RoPE 正确性和下篇 Ring Attention 里 `max_seqlen` 还原逻辑的隐含前提。

**梯度链路阶段**确定了 CP 引入后三处关键变化的来龙去脉。CP 和 DP 在梯度语义上有根本区别：DP 组内不同样本的梯度取平均，CP 组内同一序列不同片段的梯度求和。DDP 把 `_DATA_PARALLEL_GROUP_WITH_CP` 当作通信域，把 CP 当 DP 处理多除了一个 cp；`loss_func` 新增 CP AllReduce 得到完整序列 loss；`forward_step` 里 `× cp_size` 在前向出口预补偿抵消这个多除。`finalize_model_grads` 里不同参数走不同的归约域——普通参数跨 CP+DP 聚合，LayerNorm 只跨 TP 聚合，embedding 只在 PP 首尾同步，根本逻辑是"谁切分了这个参数的哪个维度，谁就需要参与归约"。

把三章的梯度链路串成一条公式：

```python
grad_final = loss_scale × cp_size × local_mean(token_loss) × ∂param
           = loss_scale × global_mean(token_loss) × ∂param
```

`/num_microbatches` 与梯度累积相消后不出现在最终量级里。`cp_size × local_mean(token_loss)` 恰好等于 `global_mean(token_loss)`。

`calculate_per_token_loss=True` 路径跳过 `× cp_size`，`gradient_scaling_factor=1.0`，cp 由 DDP 纯 SUM 自然对消，改在 `finalize_model_grads` 里用全局 token 数精确缩放。

等长序列时两条路径完全等价；变长序列时 `True` 路径按 token 数加权，各 microbatch 贡献与实际 token 数成正比，梯度语义更准确，是长序列训练的推荐配置。

**第四章对两条路径的数学等价性和 bug 演进有完整推导，可对照阅读。**
