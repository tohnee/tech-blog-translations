> 普通 Attention 会把巨大的中间矩阵 $S=QK^T$ 和 $P=\operatorname{softmax}(S)$ 写入 HBM；FlashAttention 则把计算分块，在 GPU 片上高速存储中完成局部计算，并通过 online softmax 直接累积最终输出，从而避免保存完整的 $N\times N$ 中间矩阵。<br>本文为个人借助大模型理解所得，写下来作为个人笔记，里面有大量公式，谨慎参考。如有错误，欢迎指正！。

[https://juejin.cn/spost/7698176323931422783](https://juejin.cn/spost/7698176323931422783)

要理解 FlashAttention，首先必须理解 GPU 的内存层次、Kernel、Block 和 SM。

## GPU 硬件基础：HBM、SRAM、SM、Kernel、Block

### 1.1 HBM 是什么？

HBM 是 High Bandwidth Memory，也就是高带宽显存。

在 PyTorch 中，如果创建一个 CUDA tensor：

```text
q = torch.randn(
    batch,
    heads,
    seq_len,
    head_dim,
    device="cuda",
    dtype=torch.float16,
)
```

这个 tensor 的主体数据通常位于 GPU 的 global memory 中。对于使用 HBM 的 NVIDIA GPU，可以粗略把 global memory 理解成 HBM。

HBM 的特点：

- 容量大，通常是几十 GB
- 所有 SM 都可以访问
- 用来保存模型参数、Q/K/V、输出和中间张量
- 带宽很高，但访问延迟仍然高于片上存储
- 适合保存大规模数据，不适合频繁保存和读取中间结果

例如，NVIDIA A100 的 HBM2 带宽可以达到约 2 TB/s，它属于 GPU 的全局主存储层。虽然 HBM 通过先进封装与 GPU 紧密连接，但仍不属于 SM 内部的片上存储。[NVIDIA GPU Performance Background](https://docs.nvidia.com/deeplearning/performance/dl-performance-gpu-background/index.html)

---

### 1.2 SRAM 是什么？

SRAM 是 Static Random Access Memory，静态随机存储器。

GPU 内部常见的片上高速存储包括：

```text
Register：寄存器
Shared Memory：共享内存
L1 Cache：一级缓存
```

这些存储位于 GPU 芯片内部，容量远小于 HBM，但离计算单元更近，访问速度更快。

可以把 GPU 存储层次粗略表示为：

```text
容量越来越大
速度越来越慢

Register
   ↓
Shared Memory / L1 Cache
   ↓
L2 Cache
   ↓
HBM / Global Memory
```

NVIDIA 的典型层次关系是：

```text
Register：
    每个线程私有，最快，容量最小

Shared Memory：
    同一个 block 内的线程共享

L2 Cache：
    多个 SM 可以访问

HBM / Global Memory：
    整个 GPU 上的线程都可以访问，容量最大
```

NVIDIA 对 GPU 内存层次的描述也明确指出：global memory 容量最大但速度较慢，shared memory 更小但更快，register 最小且由线程私有。[NVIDIA CUDA Memory Hierarchy](https://developer.nvidia.com/blog/register-cache-warp-cuda/)

---

### 1.3 为什么 SRAM 对 FlashAttention 很重要？

假设：

```text
N = 4096
head_dim = 128
```

注意力分数矩阵：

$$ S=QK^T $$

形状是：

```text
[4096, 4096]
```

如果使用 FP16：

$$ 4096\times4096\times2\text{ bytes} \approx32\text{ MB} $$

softmax 后的概率矩阵 $P$ 也是同样大小。

但是 GPU 的 shared memory 并不是一个几十 MB 的统一内存池，而是分散在每个 SM 上、容量很小的片上存储。一个 block 通常只能使用几十 KB 到几百 KB 量级的 shared memory。

因此：

```text
完整 S[4096,4096]：几十 MB
单个 block 的片上存储：几十 KB 级别
```

完整 $S$ 无法放入 SRAM。

FlashAttention 的策略不是把完整的 $S$ 从 HBM 搬到 SRAM，而是：

```text
每次只加载 Q/K/V 的一个小 tile
在片上计算一个小的 score tile
立即处理它
处理完后丢弃
```

例如：

```text
Q_tile: [64, 128]
K_tile: [64, 128]
V_tile: [64, 128]
S_tile: [64, 64]
```

这些 tile 可以被编译器映射到寄存器、shared memory 或其他片上资源中。实际布局取决于 kernel、GPU 架构、tile 大小和寄存器压力；如果寄存器压力过高，还可能发生 register spilling。

---

### 1.4 Kernel 是什么？

Kernel 是提交给 GPU 执行的函数。

例如 CUDA 代码：

```text
flash_attention_kernel<<<grid, block>>>(Q, K, V, O);
```

这里：

```text
flash_attention_kernel
```

就是一个 GPU kernel。

一次 kernel 启动后，GPU 会创建许多执行实例：

```text
一个 Kernel
    ↓
很多个 Block
    ↓
每个 Block 中有很多 Thread
```

Kernel 可以理解成：

> “请 GPU 用大量线程并行执行这个函数。”

---

### 1.5 Block 是什么？

Block，也叫 Thread Block，是一组协同工作的线程。

例如：

```text
dim3 grid(64);
dim3 block(128);

kernel<<<grid, block>>>();
```

表示：

```text
64 个 block
每个 block 有 128 个线程
```

同一个 block 内的线程可以：

- 共享 shared memory
- 进行同步
- 合作加载一个数据 tile
- 协作计算矩阵乘法
- 做 reduction，例如求最大值和求和

在 FlashAttention 中，一个 block 常常负责一块 query：

```text
Block 0：负责 Q[0:64]
Block 1：负责 Q[64:128]
Block 2：负责 Q[128:192]
```

也就是说：

> 一个 block 通常负责输出矩阵 $O$ 的一部分行。

---

### 1.6 SM 是什么？

SM 是 Streaming Multiprocessor，可以理解为 GPU 内部的一个计算集群。

一个 GPU 通常由多个 SM 组成：

```text
GPU
├── SM 0
├── SM 1
├── SM 2
├── ...
└── SM n
```

每个 SM 中包含：

- CUDA cores
- Tensor Cores
- registers
- shared memory
- warp scheduler

SM 是真正执行 block 的硬件单元。

例如：

```text
Block 0 → SM 3
Block 1 → SM 7
Block 2 → SM 1
```

Block 本身不能指定运行在哪个 SM 上，GPU 调度器会自动安排。

同一个 block 的线程不会被拆到多个 SM 上。一个 block 会完整地驻留在某个 SM 中执行。

但是一个 SM 可以先后执行多个 block：

```text
SM 3：
    先执行 Block 0
    Block 0 完成后
    再执行 Block 5
```

如果资源足够，一个 SM 也可以同时驻留多个 block。

---

### 1.7 Thread 和 Warp 是什么？

Thread 是最小执行单位。

例如一个 block 有 128 个线程：

```text
Block 0
├── Thread 0
├── Thread 1
├── ...
└── Thread 127
```

GPU 通常以 32 个线程为一个 warp 执行：

```text
128 threads = 4 warps
```

线程通常负责：

- 加载 Q/K/V 的一部分
- 计算矩阵元素的一部分
- 参与最大值和求和
- 写回输出的一部分

---

### 1.8 Block 和 SM 的关系

可以把它们理解为：

```text
Block：软件层面的任务单元
SM：硬件层面的执行单元
```

一个 block 执行时占用某个 SM 的资源：

```text
registers
shared memory
线程槽位
```

如果一个 block 使用的 shared memory 很多，那么一个 SM 同时能运行的 block 数量就会减少。

因此，FlashAttention 中的 tile 大小不仅影响计算，也影响：

- shared memory 占用
- register 占用
- occupancy
- 并行度
- 性能

## 普通 Attention 的数学公式

标准 Attention：

$$ O=\operatorname{softmax}\left(\frac{QK^T}{\sqrt d}\right)V $$

定义：

$$ S=\frac{QK^T}{\sqrt d} $$

$$ P=\operatorname{softmax}(S) $$

$$ O=PV $$

其中：

```text
Q: [N, D]
K: [N, D]
V: [N, D]

S: [N, N]
P: [N, N]
O: [N, D]
```

用 PyTorch 表示：

```text
scores = q @ k.transpose(-1, -2)
scores = scores * scale
probs = torch.softmax(scores, dim=-1)
out = probs @ v
```

这三行代码在底层通常对应多个 GPU kernel。

## 普通 Attention 在 GPU 中的完整数据流

假设：

```text
N = 4096
D = 128
BLOCK_M = 64
BLOCK_N = 64
```

将 Q、K、V 分块：

```text
Q0 = Q[0:64]
Q1 = Q[64:128]
Q2 = Q[128:192]
...

K0 = K[0:64]
K1 = K[64:128]
K2 = K[128:192]
...

V0 = V[0:64]
V1 = V[64:128]
V2 = V[128:192]
...
```

每个 V tile 的形状是：

```text
Vj: [64, 128]
```

也就是说，V 沿 sequence/token 维度分块，但保留完整的 head dimension。

### 3.2 Kernel 1：计算 $S=QK^T$

完整的 $S$ 可以按 block 表示：

```text
S =
┌──────┬──────┬──────┬──────┐
│ S00  │ S01  │ S02  │ ...  │ ← Q0
├──────┼──────┼──────┼──────┤
│ S10  │ S11  │ S12  │ ...  │ ← Q1
├──────┼──────┼──────┼──────┤
│ S20  │ S21  │ S22  │ ...  │ ← Q2
├──────┼──────┼──────┼──────┤
│ ...  │ ...  │ ...  │ ...  │
└──────┴──────┴──────┴──────┘
```

每个 tile 的含义：

```text
S00 = Q0 @ K0.T
S01 = Q0 @ K1.T
S02 = Q0 @ K2.T

S10 = Q1 @ K0.T
S11 = Q1 @ K1.T
S12 = Q1 @ K2.T
```

其中：

```text
Q0: [64, 128]
K0: [64, 128]

Q0 @ K0.T:
[64,128] @ [128,64]
→ [64,64]
```

一个 block 的数据流：

```text
从 HBM 读取 Qi
从 HBM 读取 Kj
        │
        ▼
加载到 SM 的寄存器/shared memory
        │
        ▼
计算 Sij = Qi @ Kj.T
        │
        ▼
得到 Sij[64,64]
        │
        ▼
把 Sij 写回 HBM
```

因此：

```text
S00 → HBM 中 S[0:64,   0:64]
S01 → HBM 中 S[0:64,  64:128]
S10 → HBM 中 S[64:128, 0:64]
S11 → HBM 中 S[64:128,64:128]
```

最终，所有 block 把自己的 tile 写到 HBM 的不同位置，拼成完整的：

```text
S[4096,4096]
```

```text
                          │
       ┌──────────────────┼──────────────────┐
       │                  │                  │
       ▼                  ▼                  ▼
    Block(0,0)         Block(0,1)         Block(1,0)
    计算 S00           计算 S01           计算 S10
       │                  │                  │
       ▼                  ▼                  ▼
写 HBM 的 S00 区域   写 HBM 的 S01 区域   写 HBM 的 S10 区域
```

```text

┌────────┬────────┬────────┐
│  S00   │  S01   │  S02   │
├────────┼────────┼────────┤
│  S10   │  S11   │  S12   │
├────────┼────────┼────────┤
│  S20   │  S21   │  S22   │
└────────┴────────┴────────┘
```

### 3.4 为什么 Kernel 1 必须把 S 写回 HBM？

因为 Kernel 1 和 Kernel 2 是两个独立的 kernel。

Kernel 1 中临时产生的：

```text
register
shared memory
```

只能在 Kernel 1 执行期间使用。

Kernel 2 启动后，不能直接访问 Kernel 1 的：

```text
register
shared memory
```

而且不同 block 可能运行在不同的 SM：

```text
Block(0,0) → SM 0
Block(0,1) → SM 1
Block(1,0) → SM 2
```

不同 SM 之间不能直接把各自的 shared memory 当成一块全局共享内存使用。

因此，Kernel 1 必须把结果写入一个：

```text
跨 SM
跨 block
跨 kernel
```

都可以访问的位置，这个位置就是 HBM/global memory。

### 3.5 Kernel 2：计算 $P=\operatorname{softmax}(S)$

Kernel 2 启动后，从 HBM 读取已经保存好的 $S$。

例如：

```text
Block 0：
    读取 S[0:64, :]
    对这些行做 softmax
    得到 P[0:64, :]
    写回 HBM

Block 1：
    读取 S[64:128, :]
    对这些行做 softmax
    得到 P[64:128, :]
    写回 HBM
```

数据流：

```text
HBM 中的 S tile
       │
       ▼
加载到 SM 的寄存器/shared memory
       │
       ▼
计算一行或多行 softmax
       │
       ▼
得到 P tile
       │
       ▼
P tile 写回 HBM
```

结果：

```text
P =
┌──────┬──────┬──────┬──────┐
│ P00  │ P01  │ P02  │ ...  │
├──────┼──────┼──────┼──────┤
│ P10  │ P11  │ P12  │ ...  │
├──────┼──────┼──────┼──────┤
│ P20  │ P21  │ P22  │ ...  │
├──────┼──────┼──────┼──────┤
│ ...  │ ...  │ ...  │ ...  │
└──────┴──────┴──────┴──────┘
```

又发生了一次：

```text
HBM 读取 S
HBM 写回 P
```

### 3.6 Kernel 3：计算 $O=PV$

Kernel 3 需要：

```text
P：从 HBM 读取
V：从 HBM 读取
```

假设 Block 0 负责：

```text
O0 = O[0:64, :]
```

它需要计算：

$$ O_0=P_0V $$

其中：

```text
P0: [64, 4096]
V:  [4096, 128]
O0: [64, 128]
```

将中间的 4096 维切成 64 一块：

$$ O_0= P_{00}V_0+ P_{01}V_1+ P_{02}V_2+\cdots+ P_{0,63}V_{63} $$

这里必须区分：

```text
P00 只对应 V0
P01 只对应 V1
P02 只对应 V2
...
P0,63 只对应 V63
```

完整流程：

```text
acc0 = 0

读取 P00 和 V0
acc0 += P00 @ V0

读取 P01 和 V1
acc0 += P01 @ V1

读取 P02 和 V2
acc0 += P02 @ V2

...

读取 P0,63 和 V63
acc0 += P0,63 @ V63

O0 = acc0
写入 O[0:64, :]
```

每一项的形状：

```text
P0j: [64, 64]
Vj:  [64, 128]

P0j @ Vj
    ↓
[64,128]
```

所以，普通 Attention 中，一个负责 $O_0$ 的 block 需要遍历完整的 V：

```text
V0, V1, V2, ..., V63
```

但它是分块读取的，不是一次把完整 V 放进 SRAM。

---

```text
Block 0：负责 O[0:64]

初始化 acc0[64,128] = 0
        │
        ▼
读取 P00、V0
        │
        ▼
acc0 += P00 @ V0
        │
        ▼
读取 P01、V1
        │
        ▼

        │

        ▼

        ▼

        │

```

Block 1 类似：

```text

读取 P11、V1

...

读取 P1,63、V63
acc1 += P1,63 @ V63

写入 HBM：O[64:128]
```

### 3.8 普通 Attention 的完整 HBM 读写路径

```text
初始：

Q、K、V 保存在 HBM

第一阶段：Kernel 1

从 HBM 读取 Q、K
        │
        ▼
片上计算 S tile
        │
        ▼
S tile 写回 HBM
        │
        ▼
完整 S 保存在 HBM

第二阶段：Kernel 2

从 HBM 读取完整 S
        │
        ▼
片上计算 softmax
        │
        ▼
P tile 写回 HBM
        │
        ▼
完整 P 保存在 HBM

第三阶段：Kernel 3

从 HBM 读取 P
从 HBM 读取 V
        │
        ▼
片上计算 P @ V
        │
        ▼
O tile 写回 HBM
```

压缩成一张图：

```text
Q ───────────────┐
                 ▼
K ───────> [Kernel 1: QKᵀ]
                 │
                 ├── S tile 写入 HBM
                 ▼
           完整 S 在 HBM
                 │
                 ├── S 从 HBM 读出
                 ▼
          [Kernel 2: softmax]
                 │
                 ├── P tile 写入 HBM
                 ▼
           完整 P 在 HBM
                 │
                 ├── P 从 HBM 读出
                 ▼
V ───────> [Kernel 3: P@V]
                 │
                 ├── O tile 写入 HBM
                 ▼
           完整 O 在 HBM
```

## 普通 Attention 的问题

### 4.1 中间矩阵是 $O(N^2)$

```text
S = [N, N]
P = [N, N]
```

序列长度加倍时，中间矩阵大小约增加四倍。

因此长序列下，显存占用快速增长。

---

### 4.2 S 和 P 都要写回 HBM

传统流程：

```text
计算 S → 写 HBM
读取 S → 计算 P → 写 HBM
读取 P、V → 计算 O → 写 HBM
```

也就是：

```text
HBM → 片上 → HBM
HBM → 片上 → HBM
HBM → 片上 → HBM
```

大量数据在 HBM 和片上存储之间来回搬运。

---

### 4.3 计算量不一定是主要瓶颈

标准 Attention 的主要矩阵乘法计算复杂度是：

$$ O(N^2D) $$

FlashAttention 并没有把这个数学计算量完全消除。它主要减少的是：

```text
中间矩阵的显存读写
```

所以 FlashAttention 是一种 IO-aware，也就是面向内存访问优化的算法。

---

## FlashAttention 的核心思想

FlashAttention 仍然计算：

$$ O=\operatorname{softmax}(QK^T)V $$

但它不再按照：

```text
完整 S
→ 完整 softmax
→ 完整 P
→ 完整 PV
```

的方式执行。

而是：

```text
Q/K/V 分块读取
        ↓
片上计算一个 score tile
        ↓
立即完成局部 softmax 更新
        ↓
立即与 V tile 相乘
        ↓
更新输出累加器
        ↓
丢弃 score tile
        ↓
处理下一个 K/V tile
```

核心原则：

> 不生成需要长期保存的完整 $N\times N$ 矩阵。

---

### 从普通 Attention 到分块 Online Softmax

FlashAttention 的关键不只是把矩阵切成 tile，而是要解决一个更具体的问题：**标准 softmax 看起来必须先看到一整行 score，才能知道这一行的最大值和归一化分母；FlashAttention 却只一次看到一小段 score，它如何仍然得到正确的概率和最终输出？**

下面先从普通 Attention 的单行计算开始，再逐步改造 softmax 的计算顺序。全文采用以下下标约定：$i$ 表示当前 Q block，$t$ 表示当前正在处理的 K/V block，因此局部 score tile 完整写作 $S_{i,t}$。在固定 $i$ 的循环中，也会把它简写为当前 tile；这里保留完整下标以避免把 Q block 和 K/V block 混淆。

### 1. 普通 Attention 如何计算一行输出

先只看一个 query 行 $q_i$。它会和所有 key 做点积：

$$ s_{ij}=\frac{q_i k_j^T}{\sqrt d} $$

这一行 score 是：

```text
s_i = [s_i0, s_i1, s_i2, ..., s_i,N-1]
```

标准 softmax 对这一整行计算：

$$ p_{ij}=\frac{e^{s_{ij}}}{\sum_{t=0}^{N-1}e^{s_{it}}} $$

然后用概率对所有 value 加权：

$$ o_i=\sum_{j=0}^{N-1}p_{ij}v_j $$

把 $p_{ij}$ 代入：

$$ o_i=\sum_{j=0}^{N-1} \frac{e^{s_{ij}}}{\sum_{t=0}^{N-1}e^{s_{it}}}v_j $$

由于分母对这一整行都是同一个值，可以提出来：

$$ o_i= \frac{\sum_{j=0}^{N-1}e^{s_{ij}}v_j} {\sum_{t=0}^{N-1}e^{s_{it}}} $$

这说明，一个输出行本质上只需要两个结果：

```text
分子：sum_j exp(s_ij) * v_j
分母：sum_j exp(s_ij)
```

普通实现通常先得到完整的 score 行，再计算完整 softmax。问题在于：如果只读到 score 行的一部分，直接计算出来的 softmax 概率还不是最终概率。

### 2. 为什么不能对 score 的每个小块单独做 softmax

假设把一行 score 分成两个 block：

```text
Block A：[s_i0, s_i1, ..., s_i,r-1]
Block B：[s_ir, s_i,r+1, ..., s_i,N-1]
```

错误做法是分别计算：

$$ p^A_j=\operatorname{softmax}(s^A)_j $$

$$ p^B_j=\operatorname{softmax}(s^B)_j $$

然后计算：

$$ o_i^{wrong}=\sum_{j\in A}p^A_jv_j +\sum_{j\in B}p^B_jv_j $$

错误在于 A 和 B 各自使用了自己的分母：

$$ Z_A=\sum_{j\in A}e^{s_{ij}} $$

$$ Z_B=\sum_{j\in B}e^{s_{ij}} $$

而完整 softmax 需要的分母是：

$$ Z=Z_A+Z_B $$

因此，局部 softmax 的结果不能直接相加。FlashAttention 要做的是：**每个 block 只计算局部指数项，但不急着把它归一化成最终概率；它保存局部的分子和分母信息，等所有 block 都处理完后再统一归一化。**

### 3. 先解决数值稳定性：减去最大值

直接计算 $e^{s_{ij}}$ 可能溢出。例如 score 很大时，指数可能变成 `inf`；score 很小时，指数可能下溢为 0。

标准稳定 softmax 先求这一整行的最大值：

$$ m_i=\max_j s_{ij} $$

然后把每个 score 减去它：

$$ \tilde{s}_{ij}=s_{ij}-m_i $$

稳定后的概率为：

$$ p_{ij}=\frac{e^{s_{ij}-m_i}} {\sum_t e^{s_{it}-m_i}} $$

为什么这样不会改变结果？因为分子和分母同时乘了 $e^{-m_i}$：

$$ \frac{e^{s_{ij}-m_i}} {\sum_t e^{s_{it}-m_i}} = \frac{e^{s_{ij}}e^{-m_i}} {\sum_t e^{s_{it}}e^{-m_i}} = \frac{e^{s_{ij}}} {\sum_t e^{s_{it}}} $$

于是可以把标准 Attention 的输出写成：

$$ o_i= \frac{\sum_j e^{s_{ij}-m_i}v_j} {\sum_j e^{s_{ij}-m_i}} $$

这一步非常关键：最终只要维护三类信息即可：

```text
m_i：目前已经看到的最大 score
l_i：以 m_i 为基准的稳定化分母
acc_i：以 m_i 为基准的稳定化分子
```

其中：

$$ l_i=\sum_j e^{s_{ij}-m_i} $$

$$ acc_i=\sum_j e^{s_{ij}-m_i}v_j $$

最终：

$$ o_i=\frac{acc_i}{l_i} $$

此时还没有使用分块。接下来要解决的是：我们不知道完整行的 $m_i$，只能一次读取一个 score block，怎么办？

### 4. 只处理第一个 score block

假设当前只读取了 Block A。先求这个 block 的最大值：

$$ m_A=\max_{j\in A}s_{ij } $$

以 $m_A$ 为基准，计算 Block A 的稳定化分母和分子：

$$ l_A=\sum_{j\in A}e^{s_{ij}-m_A} $$

$$ acc_A=\sum_{j\in A}e^{s_{ij}-m_A}v_j $$

如果所有 key 都只有 Block A，那么输出就是：

$$ o_i^A=\frac{acc_A}{l_A} $$

但是现在只处理了部分 key，不能把 $o_i^A$ 当作最终输出。我们必须保留：

```text
m = m_A
l = l_A
acc = acc_A
```

不要提前做 `acc / l`，因为后面还会出现新的 key。

### 5. 读取第二个 score block 后发生什么

现在读到 Block B。计算它自己的局部统计量：

$$ m_B=\max_{j\in B}s_{ij} $$

$$ l_B=\sum_{j\in B}e^{s_{ij}-m_B} $$

$$ acc_B=\sum_{j\in B}e^{s_{ij}-m_B}v_j $$

现在 A 和 B 使用不同的最大值基准：

```text
Block A 使用 m_A
Block B 使用 m_B
```

它们的分母和分子不能直接相加，必须先换到同一个基准。

### 6. 合并最大值

A 和 B 合并后的最大值是：

$$ m_{new}=\max(m_A,m_B) $$

如果 $m_B$ 更大，A 中的指数项都要缩小；如果 $m_A$ 更大，B 中的指数项都要缩小。

### 7. 把两个 block 的分母换到同一基准

A 原来的稳定化分母是：

$$ l_A=\sum_{j\in A}e^{s_{ij}-m_A} $$

改用 $m_{new}$ 后：

$$ \sum_{j\in A}e^{s_{ij}-m_{new}} = \sum_{j\in A}e^{s_{ij}-m_A}e^{m_A-m_{new}} = e^{m_A-m_{new}}l_A $$

B 同理：

$$ \sum_{j\in B}e^{s_{ij}-m_{new}} =e^{m_B-m_{new}}l_B $$

所以合并后的稳定化分母是：

$$ l_{new}=e^{m_A-m_{new}}l_A +e^{m_B-m_{new}}l_B $$

这一步说明了为什么需要保存 `l`：它保存了已经处理部分的归一化分母贡献，遇到新的最大值时可以整体重新缩放。

### 8. 把两个 block 的分子换到同一基准

A 原来的稳定化分子是：

$$ acc_A=\sum_{j\in A}e^{s_{ij}-m_A}v_j $$

改用 $m_{new}$ 后：

$$ \sum_{j\in A}e^{s_{ij}-m_{new}}v_j =e^{m_A-m_{new}}acc_A $$

B 同理：

$$ \sum_{j\in B}e^{s_{ij}-m_{new}}v_j =e^{m_B-m_{new}}acc_B $$

因此合并后的分子是：

$$ acc_{new}=e^{m_A-m_{new}}acc_A +e^{m_B-m_{new}}acc_B $$

这一步说明了为什么需要保存 `acc`：它保存了已经处理的 value 加权结果，遇到新的 score block 后，只需按新的最大值重新缩放。

### 9. 推广到逐块循环

实际情况下，K/V 被切成很多 block：

```text
(K0,V0), (K1,V1), (K2,V2), ..., (KT-1,VT-1)
```

对于固定的 Q block，kernel 按顺序处理这些 K/V block。

初始化：

```text
m = -∞
l = 0
acc = 0
```

处理第 t 个 tile 时，先计算：

$$ S_{i,t}=Q_iK_t^T\times scale $$

然后得到当前 tile 每一行的最大值：

$$ m_{i,t}=\max(S_{i,t},\text{axis}=key) $$

把旧状态和当前 tile 合并：

$$ m_i^{new}=\max(m_i,m_{i,t}) $$

旧状态的缩放因子：

$$ \alpha_i=e^{m_i-m_i^{new}} $$

当前 tile 如果先以自己的最大值 $m_{i,t}$ 为基准：

$$ P_{i,t}^{local}=e^{S_{i,t}-m_{i,t}} $$

那么当前 tile 相对于新基准的缩放因子是：

$$ \beta_i=e^{m_{i,t}-m_i^{new}} $$

于是：

$$ l_i^{new}=\alpha_i l_i+\beta_i\sum P_{i,t}^{local} $$

$$ acc_i^{new}=\alpha_i acc_i+\beta_i(P_{i,t}^{local}V_t) $$

最后更新：

```text
m_i = m_i^{new}
l_i = l_i^{new}
acc_i = acc_i^{new}
```

也可以不单独使用 $m_{i,t}$，直接把当前 score 减去 $m_i^{new}$：

$$ l_i^{new}=e^{m_i-m_i^{new}}l_i +\sum e^{S_{i,t}-m_i^{new}} $$

$$ acc_i^{new}=e^{m_i-m_i^{new}}acc_i +e^{S_{i,t}-m_i^{new}}V_t $$

两种写法数学等价。实际 kernel 常先求 tile 最大值，再用两个缩放因子实现数值稳定的更新。

### 10. 为什么最后得到的是完整 Attention

处理完所有 K/V block 后，归纳地有：

$$ m=\max_j s_{ij} $$

$$ l=\sum_j e^{s_{ij}-m} $$

$$ acc=\sum_j e^{s_{ij}-m}v_j $$

因此最终：

$$ \frac{acc}{l} = \frac{\sum_j e^{s_{ij}-m}v_j} {\sum_j e^{s_{ij}-m}} = \frac{\sum_j e^{s_{ij}}v_j} {\sum_j e^{s_{ij}}} =\sum_j\operatorname{softmax}(s_i)_jv_j $$

这就是标准 Attention 的输出。FlashAttention 不是把多个局部 softmax 结果直接拼接，也不是分别对每个 tile 做归一化；它把每个 tile 对完整 softmax 分子和分母的贡献都转换到同一个最大值基准，再进行在线合并。

### 11. 从一个 query 行推广到一个 Q tile

前面的推导针对一个 query 行。实际一个 block 同时处理 `BLOCK_M` 行，因此状态变成：

```text
m：         [BLOCK_M]
l：         [BLOCK_M]
acc：       [BLOCK_M, HEAD_DIM]
score_tile：[BLOCK_M, BLOCK_N]
V_tile：    [BLOCK_N, HEAD_DIM]
```

每一行独立进行 online softmax，矩阵运算只是把多行并行执行：

$$ S_{i,t}=Q_iK_t^T $$

$$ l_{new}[r]=e^{m_i[r]-m_i^{new}[r]}l_i[r] +\sum_c e^{S_{i,t}[r,c]-m_i^{new}[r]} $$

$$ acc_{new}[r,:] =e^{m_i[r]-m_i^{new}[r]}acc_i[r,:] +\sum_c e^{S_{i,t}[r,c]-m_i^{new}[r]}V_t[c,:] $$

处理完所有 K/V tile 后：

$$ O_i[r,:]=\frac{acc_i[r,:]}{l_i[r]} $$

这就是 FlashAttention 在一个 Q block 上执行的完整数学过程。

## FlashAttention 中的 Online Softmax

### 8.1 为什么不能对每个 tile 单独 softmax？

错误做法：

```text
for k_block in blocks:
    scores = q @ k_block.T
    probs = softmax(scores, dim=-1)
    out += probs @ v_block
```

这会让每个 K block 单独归一化：

```text
Block 0 的概率和 = 1
Block 1 的概率和 = 1
Block 2 的概率和 = 1
```

但完整 Attention 要求：

```text
所有 K block 合起来后，每行概率和 = 1
```

因此不能直接对每个 tile 单独 softmax。

---

### 8.2 Online Softmax 维护三个量

对于某个 Q block，维护：

```text
m：当前处理范围内的最大 score
l：重新缩放后的指数和
acc：重新缩放后的加权 V 累加值
```

初始：

$$ m=-\infty,\qquad l=0,\qquad acc=0 $$

处理新的 score tile $S_j$：

$$ m_j=\max(S_j) $$

$$ m_{\text{new}}=\max(m,m_j) $$

旧结果的修正因子：

$$ \alpha=e^{m-m_{\text{new}}} $$

当前 tile 的指数项：

$$ p_j=e^{S_j-m_{\text{new}}} $$

更新 softmax 分母：

$$ l_{\text{new}} = \alpha l+ \sum p_j $$

更新累加结果：

$$ acc_{\text{new}} = \alpha acc+ p_jV_j $$

最终：

$$ O=\frac{acc}{l} $$

这和完整 softmax 的数学结果一致，只是没有保存完整的 $S$ 和 $P$。

V 沿 sequence/token 维度分块，保留完整的 head dimension。

```text
D = 128
BLOCK_N = 64
```

那么：

```text
V0 = V[0:64, :]
V1 = V[64:128, :]
V2 = V[128:192, :]
...
V63 = V[4032:4096, :]
```

每个 V tile：

```text
Vj.shape = [64,128]
```

完整 V：

```text
V =
```

- K 用来计算 query 对 token 的注意力分数
- V 保存这些 token 的实际内容

## 11. $P$ 和 $V$ 的对应关系

完整的概率矩阵可以写成：

```text
P =
┌──────┬──────┬──────┬──────┐
│ P00  │ P01  │ P02  │ ...  │ ← Q0
├──────┼──────┼──────┼──────┤
│ P10  │ P11  │ P12  │ ...  │ ← Q1
├──────┼──────┼──────┼──────┤
│ P20  │ P21  │ P22  │ ...  │ ← Q2
├──────┼──────┼──────┼──────┤
│ ...  │ ...  │ ...  │ ...  │
└──────┴──────┴──────┴──────┘
```

V：

```text
V =
┌──────┐
│ V0   │
├──────┤
│ V1   │
├──────┤
│ V2   │
├──────┤
│ ...  │
└──────┘
```

计算 $O_0=P_0V$：

```text
P00 只和 V0 相乘
P01 只和 V1 相乘
P02 只和 V2 相乘
...
P0,63 只和 V63 相乘
```

因此：

$$ O_0=P_{00}V_0+P_{01}V_1+\cdots+P_{0,63}V_{63} $$

需要特别注意：

```text
P00 不会遍历 V0 到 V63
```

而是：

```text
P00 → V0
P01 → V1
P02 → V2
...
```

是整个负责 $Q_0$ 的 block 遍历：

```text
P00、P01、P02、...、P0,63
```

```text
Block 0
              负责 Q[0:64, :]
```

## FlashAttention 如何解决普通 Attention 的问题？

### 普通 Attention

```text
Kernel 1：
    Q/K → S_tile → 写 HBM

Kernel 2：
    HBM 中的 S → softmax → P_tile → 写 HBM

Kernel 3：
    HBM 中的 P/V → P@V → O_tile → 写 HBM
```

中间结果：

```text
S：写入 HBM
P：写入 HBM
```

---

### FlashAttention

```text
一个 fused kernel：

Q_tile 从 HBM 读取
K_tile 从 HBM 读取
V_tile 从 HBM 读取
        │
        ▼
SM 片上计算 S_tile
        │
        ▼
立即做 online softmax
        │
        ▼
立即计算当前 tile 对输出的贡献
        │
        ▼
更新 acc
        │
        ▼
丢弃 S_tile 和局部概率
        │
        ▼
处理下一个 K/V tile
        │
        ▼
最终 O_tile 写回 HBM
```

核心差异：

```text
普通 Attention：
    S_tile 写 HBM
    再从 HBM 读 S_tile
    P_tile 写 HBM
    再从 HBM 读 P_tile

FlashAttention：
    S_tile 和局部概率在片上用完即丢
    只把最终 O_tile 写回 HBM
```

## 为什么 FlashAttention 需要遍历完整的 V？

对于一个 query block $Q_i$：

$$ O_i=P_iV $$

如果：

```text
P_i: [BLOCK_M, N]
V:   [N, D]
```

那么必须覆盖 V 的全部 N 行。

分块后：

$$ O_i = P_{i0}V_0+ P_{i1}V_1+\cdots+ P_{i,m}V_m $$

所以：

```text
一个负责 Q_i 的 block
需要遍历完整的 V tile 序列
```

但是它不需要把完整 V 一次性加载到 SRAM：

```text
读取 V0 → 累加
读取 V1 → 累加
读取 V2 → 累加
...
读取 Vm → 累加
```

FlashAttention 和普通 Attention 都需要覆盖所有 V tile，区别是：

```text
普通 Attention：
    P 已经提前完整计算并保存

FlashAttention：
    当前 tile 的权重由 Qi、Kj 即时计算
```

## Causal Attention 如何处理？

因果注意力要求：

$$ j>i \Rightarrow S_{ij}=-\infty $$

也就是当前位置不能看到未来 token。

对于 query 位置 `q_pos` 和 key 位置 `k_pos`：

```text
if k_pos > q_pos:
    score = -inf
```

Triton 风格的写法：

```text
causal_mask = offs_m[:, None] >= offs_n[None, :]

qk = tl.where(
    causal_mask,
    qk,
    -float("inf"),
)
```

实际高效实现会进一步优化：

```text
完全位于对角线下方的 block：
    不需要 mask

完全位于对角线上方的 block：
    整个 block 跳过

位于对角线附近的 block：
    逐元素 mask
```

对于 causal Attention，一个 query 只需要访问当前位置及之前的 V，而不是完整的未来部分。

## Triton 代码中对应什么？

Triton 官方教程提供了一个完整的 FlashAttention 2 教学实现：

- [Triton 官方](https://github.com/triton-lang/triton/blob/main/python/tutorials/06-fused-attention.py)`06-fused-attention.py`
- [官方教程页面](https://triton-lang.org/main/getting-started/tutorials/06-fused-attention.html)

重点函数通常包括：

```text
_attn_fwd_inner
_attn_fwd
_attn_bwd
_attention
```

大致职责：

教学版 Triton forward 逻辑大致如下：

```text
@triton.jit
def flash_attn_fwd_kernel(
    Q, K, V, O,
    N_CTX,
    scale,
    BLOCK_M: tl.constexpr,
    BLOCK_N: tl.constexpr,
    HEAD_DIM: tl.constexpr,
):
    pid_m = tl.program_id(0)

    offs_m = pid_m * BLOCK_M + tl.arange(0, BLOCK_M)
    offs_d = tl.arange(0, HEAD_DIM)

    # 加载一个 Q tile
    q = tl.load(...)

    # online softmax 状态
    m_i = tl.full(
        [BLOCK_M],
        -float("inf"),
        dtype=tl.float32,
    )

    l_i = tl.zeros(
        [BLOCK_M],
        dtype=tl.float32,
    )

    acc = tl.zeros(
        [BLOCK_M, HEAD_DIM],
        dtype=tl.float32,
    )

    # 遍历所有 K/V tile
    for start_n in range(0, N_CTX, BLOCK_N):
        offs_n = start_n + tl.arange(0, BLOCK_N)

        k = tl.load(...)
        v = tl.load(...)

        # 当前 score tile
        qk = tl.dot(q, tl.trans(k)) * scale

        # 当前 tile 最大值
        m_ij = tl.max(qk, axis=1)

        # 合并旧最大值和当前最大值
        m_ij_new = tl.maximum(m_i, m_ij)

        # 修正旧结果
        alpha = tl.exp(m_i - m_ij_new)

        # 当前 tile 的指数权重
        p = tl.exp(qk - m_ij_new[:, None])

        # 更新分母
        l_i = alpha * l_i + tl.sum(p, axis=1)

        # 更新累加器
        acc = alpha[:, None] * acc
        acc += tl.dot(p.to(v.dtype), v)

        m_i = m_ij_new

    # 最终归一化
    acc = acc / l_i[:, None]

    # 写回输出
    tl.store(O_ptrs, acc, mask=...)
```

这段代码中最重要的变量是：

```text
m_i
l_i
acc
```

它们正是 online softmax 的三个核心状态。

## FlashAttention 的反向传播

前向计算中没有保存完整的 $P$，所以反向传播不能直接读取完整的 softmax 矩阵。

通常会保存：

- 输出 $O$
- 每一行的 log-sum-exp，简称 LSE

LSE：

$$ \operatorname{LSE}_i=m_i+\log(l_i) $$

反向时，kernel 会重新遍历 Q/K/V tile，重新计算局部概率。

对于：

$$ O=PV $$

有：

$$ dV=P^TdO $$

$$ dP=dOV^T $$

softmax 梯度：

$$ dS = P\odot \left( dP-\operatorname{rowsum}(dP\odot P) \right) $$

最后：

$$ dQ=dSK $$

$$ dK=dS^TQ $$

这体现了 FlashAttention 的一个重要取舍：

> 少保存中间结果，多做一些重计算。

### FlashAttention 1

## 最后的完整心智模型

普通 Attention：

```text
Q/K
  ↓
计算完整 S = QKᵀ
  ↓
S 写入 HBM
  ↓
读取 S
  ↓
计算完整 P = softmax(S)
  ↓
P 写入 HBM
  ↓
读取 P 和 V
  ↓
计算 O = PV
  ↓
O 写入 HBM
```

FlashAttention：

```text
Q/K/V 保存在 HBM
        ↓
每个 block 负责一段 Q 行
        ↓
加载 Q tile
        ↓
遍历全部 K/V tile
        ↓
计算局部 QKᵀ
        ↓
online softmax
        ↓
立即累加当前 V tile 的贡献
        ↓
丢弃局部 score 和概率 tile
        ↓
得到当前 Q block 的输出
        ↓
写回对应的 O 行
        ↓
所有 block 按行拼成完整 O
```

最重要的三点是：

```text
1. Block 通常负责一块 query 行和对应的输出行。

2. 一个 Q block 必须遍历完整的 K/V sequence tile，
   因为一个输出行要看到所有 key/value。

3. FlashAttention 不保存完整 S 和 P，
   而是在片上逐 tile 完成 score、softmax 和 PV 累加。
```

最终可以用一句话概括：

> FlashAttention 让每个 block 固定处理一段 Q 行，从 HBM 分块读取全部 K/V，在 SM 的寄存器和 shared memory 中逐块计算 $QK^T$、online softmax 和加权 V 累加，最后只把自己负责的输出行写回 HBM；所有 block 通过不同的输出行位置组成完整的 Attention 结果。

## 勘误与补充（只补充实现边界，不改变前文内容）

### 1. 数学阶段不等于 kernel 数量

前文的 Kernel 1、Kernel 2、Kernel 3 是朴素 Attention 的概念划分：

```text
S = QKᵀ
P = softmax(S)
O = PV
```

实际框架可能将部分阶段融合，因此可能是三个或更多 kernel，也可能是融合 kernel：

```text
朴素实现：QKᵀ → 写 S → softmax → 写 P → PV
部分融合：QKᵀ 与 softmax 融合，或 softmax 与 PV 融合
FlashAttention：QKᵀ、softmax、PV 在 tile 循环中融合
```

因此，“普通 Attention 会把 S/P 写入 HBM”应理解为“朴素、未融合的实现通常会这样做”，不是所有现代实现都严格如此。

### 2. 片上存储与 HBM 的严谨说法

本文用 SRAM/片上存储作为帮助理解的总称，但严格区分：

```text
register file：线程私有
shared memory：block 内共享、软件可管理
L1 cache：硬件管理
L2 cache：多个 SM 共享
HBM/global memory：GPU 全局可访问
```

程序访问的是 global memory 地址；一次访问可能命中 L1/L2，也可能最终访问 HBM。从算法角度通常概括为 HBM/global-memory 访问。HBM 通过先进封装与 GPU 紧密连接，但不属于某个 SM 内部的寄存器或 shared memory。

Q/K/V tile、score tile 和 accumulator 可能被编译器映射到寄存器、shared memory 或其他片上资源；实际布局取决于 GPU 架构、tile 大小和寄存器压力。寄存器压力过高时还可能发生 register spilling。

### 3. Block 到 SM 的映射

文中的 `Block 0 → SM 0` 只是示意。真实映射由 GPU 调度器决定，程序通常不能指定 block 固定运行在哪个 SM。本文采用“一个 block/program 负责一个 Q tile”的教学映射；真实实现也可能使用 split-Q、split-K、persistent kernel 或多维 batch/head/sequence grid。

### 4. Online Softmax 的维度

对于：

```text
Qi: [BLOCK_M, HEAD_DIM]
Kj: [BLOCK_N, HEAD_DIM]
Sj = Qi @ Kjᵀ: [BLOCK_M, BLOCK_N]
```

`m_new` 是每个 query 行的向量 `[BLOCK_M]`，减法沿 key 维广播：

$$ P_j[r,c]=\exp(S_j[r,c]-m_{new}[r]) $$

`l` 是数值稳定化后的指数和，而不是未平移的 `sum(exp(score))`：

$$ l_i=\sum_j\exp(s_{ij}-m_i) $$

初始化为：

```text
m_i=-∞
l_i=0
acc_i=0
```

非法的 padding/causal score 被设为 `-inf`，其指数为 0，不参与 `l` 和 `acc`。

### 5. Scale、bias 和 mask 的实际顺序

真实 score tile 通常经历：

```text
Q_tile @ K_tileᵀ
        ↓
乘以 softmax scale，通常是 1/sqrt(head_dim)
        ↓
加入 attention bias（如果有）
        ↓
应用 causal/padding mask
        ↓
online softmax
        ↓
与 V_tile 相乘并累加
```

因此教学记号 `Sij=Qi@Kjᵀ` 更完整地表示为：

```text
Sij = Qi @ Kjᵀ * scale + bias
```

然后再应用 mask 和 online softmax。

### 6. Causal mask 还需要 padding mask

教学代码常只写 causal mask：

```python
causal = offs_m[:, None] >= offs_n[None, :]
qk = tl.where(causal, qk, -float("inf"))
```

实际 tile 可能越过序列尾部，还要处理边界：

```python
valid_m = offs_m[:, None] < N_CTX
valid_n = offs_n[None, :] < N_CTX
causal = offs_m[:, None] >= offs_n[None, :]
mask = valid_m & valid_n & causal
qk = tl.where(mask, qk, -float("inf"))
```

“当前位置及之前的 V”默认是等长 self-attention；cross-attention 的 Q/K 长度和 mask 关系可能不同。

### 7. 复杂度与优化目标

| 项目 | 朴素 Attention | FlashAttention |
| --- | --- | --- |
| 数学计算复杂度 | O(N^2D) | O(N^2D) |
| 中间显存 | O(N^2) | 近似 O(ND) |
| 完整 S 是否保存 | 通常保存 | 不保存 |
| 完整 P 是否保存 | 通常保存 | 不保存 |
| backward 重计算 | 较少 | 较多 |
| 主要优化目标 | 通用计算 | 减少 HBM/global-memory IO |

FlashAttention 主要减少中间结果的显存读写，并没有把矩阵乘法的理论复杂度从 $O(N^2D)$ 变成线性。

### 8. Arithmetic intensity、tile 和 Tensor Core

FlashAttention 使加载到片上的 tile 被反复复用：

```text
Q tile 被多个 K/V tile 使用
K/V tile 被当前 Q tile 的多个线程复用
```

因此同一次 global-memory 读取支持更多计算，提高 arithmetic intensity。

tile 太小会造成 global-memory 访问次数多、复用不足；tile 太大会增加 shared memory 和 register 占用，降低 occupancy，甚至造成 register spilling。`BLOCK_M`、`BLOCK_N` 和 `HEAD_DIM` 需要结合 GPU 和输入形状调优。

`QKᵀ` 和 `P@V` 都是矩阵乘法，适合映射到 Tensor Core/MMA 指令。因此 tile 设计同时服务于减少 HBM IO 和适配 Tensor Core：

```text
tile shape
warp 分工
shared-memory layout
register 使用
异步加载和流水线
Tensor Core 指令
```

### 9. Layout 和扩展功能

真实模型常用 `[B,H,N,D]`，也有实现使用 `[B,N,H,D]`。阅读 kernel 时必须确认 batch、head、sequence、head_dim 的位置、stride 和 contiguous 状态。

工程实现还可能支持：

```text
dropout：训练时对注意力概率随机丢弃
attention bias：softmax 前加入 bias
ALiBi：位置相关 bias
GQA/MQA：Q head 数和 K/V head 数不同
variable-length：不同样本有效长度不同
```

这些功能不改变 FlashAttention 的基本 IO 思想，但会影响 mask、索引、layout、随机数和梯度实现。

### 10. Triton 教学代码的边界

Triton 官方 `06-fused-attention.py` 是学习入口，但主分支会随版本变化，可能使用 TensorDescriptor、TMA、warp specialization 或 FP8，部分路径依赖 Hopper 等新硬件。教学版代码用于说明 Q/K/V tile、QKᵀ、online softmax、P_tile@V_tile 和 O 写回，不保证直接复制即可运行。

真实 kernel 还要处理：

```text
边界和 padding
causal mask
attention bias
dtype 转换
layout 和 stride
不同 head_dim
不同 GPU 架构
```

### 11. Backward 的实现边界

常见实现会保存 O、LSE 等较小状态，但具体保存哪些张量取决于实现。反向时重新遍历 tile，重新计算局部概率，得到 `dQ`、`dK`、`dV`。当多个 program 对同一 K/V tile 产生梯度贡献时，`dK` 和 `dV` 可能使用分块累加、split-K、workspace 或 atomic add。

### 12. FlashAttention 版本边界

FlashAttention 1、2、3 的数学核心都建立在 IO-aware tiling 和 online softmax 上，主要差异在并行划分、调度、流水线、Tensor Core 使用和硬件特化。FlashAttention 3 主要针对 Hopper 等架构进行专门优化，不能简单理解为所有 GPU 上都无条件适用的 FlashAttention 2 升级版。
