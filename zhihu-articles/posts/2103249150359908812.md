随着大模型能力不断增强，模型部署正在从云端数据中心向边缘设备和端侧硬件延伸。对于端侧场景而言，模型能否运行只是第一步，更重要的是：在有限的计算资源下，如何完成模型适配、算子优化和推理性能调优。

本文将详解基于 FlagOS 系统软件栈在端侧硬件做大模型推理实践。在此芯 CIX P1 开发板上，部署 MiniCPM-V-4.7-1B W8A8 多模态模型。通过 vLLM、vLLM-plugin-FL、FlagGems 和 FlagTree-CPU 等组件，完成模型注册、量化接入、CPU 算子执行和推理服务部署。

从最终实践结果看，在 native 控制组测试中，相比最小适配基线，FlagOS 优化组合的 Prefill 吞吐提升了 223.76%，Decode 吞吐提升了 87.12%，整体吞吐提升了 100.56%。

这次实践的价值不只是把一个多模态模型部署到端侧开发板上，更重要的是，展示了一条可落地的端侧 CPU 推理优化路径：通过框架适配打通模型执行，通过算子优化减少关键路径开销，再通过量化和线程配置进一步提升推理效率。

01

整体技术架构：FlagOS 让多模态大模型在端侧硬件 CIX P1 上高效运行

本次部署使用的硬件是 CIX P1，CPU 包含 8 个 ARM Cortex-A720 核心。模型采用 MiniCPM-V-4.7-1B，语言层 Linear 使用 W8A8 量化，视觉模块保留 BF16，以支持图片理解和 OCR 路径。

模型的量化配置并非所有模块统一处理：

- 语言层 Linear：采用 INT8 权重，按输出通道量化；激活采用动态非对称逐 token 量化。
- 输出头：checkpoint 中保存的是 BF16 权重，使用 FlagOS 软件栈加载时将其量化为 W8A8。
- 视觉模块：保留 BF16，维持图片输入和视觉编码路径。

推理上下文设置为 4096 tokens，CPU KV Cache 为 256 MB。

1.FlagOS 的分层协作方式

这套架构不是用一个独立算子库替换整个推理框架，而是在 vLLM 的调度与模型执行体系上，接入适配层、优化算子和 CPU 编译执行能力。

![](https://pic2.zhimg.com/v2-fef13bb56f9c4334d4c63c6fe4a5a13f_r.jpg)

vLLM 0.24 CPU负责请求调度、Processor、采样、KV Cache，以及 GDN state 等模型执行过程中的状态管理。

vLLM-plugin-FL负责模型注册、量化接入、Arm CPU 生命周期适配，以及阶段线程和算子选择等工作，让模型能够在 vLLM CPU 执行路径中运行。

FlagGems提供 W8A8 Linear、LM Head、GDN 和归一化等优化算子接口。其中，部分算子通过 Triton 路径执行，部分自有实现通过 TLE Raw 路径调用。

FlagTree-CPU提供 CPU Triton 编译能力和 TLE Raw 运行支持。普通 CPU Triton 算子通过 MLIR、LLVM 编译执行；TLE Raw 则调用 FlagGems 自有 C++ / Neon 实现。

最终，这些组件在 CIX P1 的 CPU 执行层协同工作，使用 JIT 缓存、raw_call 入口和 OpenMP 等机制，发挥 8 个 A720 核心的执行能力。W8 默认采用 Neon SDOT 路径。

从一次推理的过程来看，客户端提交文字或图片请求后，由 vLLM 完成请求接收、Processor 处理和调度；模型进入 Prefill 阶段建立上下文与状态，再在 Decode 阶段持续更新状态，通过输出头和采样生成回答。FlagOS 的适配与算子优化贯穿模型执行过程，而不是绕开 vLLM 单独运行模型。

2.本次使用的软件组件

![](https://pic1.zhimg.com/v2-865048511805a37f9651e31a3c3cb55c_r.jpg)

本次部署采用两个容器：开发容器 flagos-workshop1018 用于安装组件、算子验收和性能测试；HTTP 推理服务容器 minicpm-1b-workshop1018 用于运行 vLLM 并接收文字和图片请求。两个容器共享基础镜像、模型权重和 /work/envs/dev 安装结果。这样可以在功能验证完成后停止 HTTP 服务，释放模型占用的 CPU 和内存，再进入开发容器开展性能对照。

02

实操：从环境准备到模型推理

本次实操大致可分四个环节完成。需要特别注意：CIX P1 主机 Bash 与开发容器 Bash 不是同一个执行环境。每个代码框应单独执行；执行 exit 后，先确认回到主机提示符，再执行主机侧命令。

阶段零：检查开发板与预置环境

在 CIX P1 主机上使用 `baai` 账号操作。主机需已安装 Docker、Python 3.9+（含 venv）、Git 和 curl，并具备免密 `sudo docker` 权限及 Harbor 仓库拉取权限。执行以下两条命令：

```text
bash
curl -fLO https://raw.githubusercontent.com/flagos-ai/flagtree-cpu/refs/heads/triton_v3.7.x/docs/getting-started/scripts/prepare_workshop.sh
bash prepare_workshop.sh

```

脚本会自动下载模型、预编译软件包、操作脚本和性能对照所需源码，统一放到 /home/baai/workshop1018；同时拉取固定版本的 Harbor 镜像，镜像由 Docker 管理。登录 Harbor 时，按提示输入获授权账号。看到 Materials ready 后，可继续“阶段一操作”。此时只完成材料准备，容器创建、软件包安装和推理启动仍按后续步骤执行。若脚本报错，应先解决错误再继续。已预置材料的开发板可跳过本段，直接从“阶段一”开始。

阶段二：创建开发容器，安装 FlagOS 组件并验证

在 P1 主机上创建开发容器：


进入开发容器后，按顺序执行预编译环境准备、wheel 安装和安装结果检查：

03

性能结果：优化收益来自哪些环节

前次 native 控制组测试结果如下：

![](https://pic3.zhimg.com/v2-0239645809b3aa5513d360d1b1235672_r.jpg)

最终组合相较最小适配基线，PP512 提升 220.51%，TG128 提升 40.05%，Total 提升 56.27%。

需要强调，这里的性能对比是最小适配基线与 FlagOS 优化路径之间的对照；纯开箱 vLLM 因不支持该模型架构，结果为 N/A，并不参与加速比计算。

1.GDN 与数据处理优化

Profile 聚合结果显示，GDN Prefill 核心的 self 时间从 1823.67 ms 降至 246.50 ms；W8 Linear 从 608.63 ms 降至 484.33 ms。

同时，aten::copy_ 的 self 时间从 230.62 ms 降至 83.95 ms，调用次数也从 12263 次降至 5338 次。

这说明优化不仅针对单个算子计算本身，也关注执行过程中的数据搬运和重复处理。GDN 按 head 并行并融合状态更新，W8 路径则复用预打包权重，优先覆盖 Profile 中占比较高的热点。

2.W8A8 Linear 的实现选择

本次自有 W8A8 实现包含几个关键设计：

- 权重采用四通道预排布，并预计算 INT32 通道和与 FP32 scale；
- 激活按 token 打包，每个 token 只进行一次 A8 打包；
- 采用四行块复用权重，减少重复权重访问；
- 通过缓存 JIT 入口，以一次 Raw 调用覆盖完整量化与 GEMM 过程。

普通 Triton 实现已经完成验证，但本次测试中更慢，因此默认采用自有 SDOT Raw 路径。

此外，还给出了开发板 B 上的 16×384×1024 微基准：普通 Triton 为 2.38 ms，自有 Raw 为 70.75 μs。这个结果属于开发板 B 的算子微基准，不应当作 CIX P1 整模型推理性能。

3.输出头量化与 Decode 线程配置

除了语言模型主体中的 Linear 层，输出头也是 Decode 阶段的重要组成部分。

输出头从 BF16 切换为 W8A8 后，在 8 线程配置下，TG128 从 16.40 tok/s 提升到 18.33 tok/s，增幅为 11.78%。

随后将 Decode 线程从 8 调整为 4，TG128 进一步提升到 21.91 tok/s，增幅为 19.57%。与此同时，Prefill 仍保持 8 线程。

这组结果说明，单 token Decode 不仅受权重访问影响，也受到线程开销影响；线程数并非越多越好。GDN、Linear、Norm、输出头和线程配置的收益，最终仍需要通过整模型测试确认，不能直接用单个算子微基准代替。

04

总结

这次 CIX P1 端侧部署实践展示了 FlagOS 与 vLLM 的分层协作方式：vLLM 负责请求调度和模型执行框架，vLLM-plugin-FL 完成模型注册、量化接入和 CPU 生命周期适配，FlagGems 提供优化算子，FlagTree-CPU 提供 CPU Triton 编译与 TLE Raw 执行支持。

在 MiniCPM-V-4.7-1B W8A8 上，视觉模块保留 BF16，语言层 Linear 和加载时量化的输出头采用 W8A8。通过 GDN、Linear、数据处理、输出头和 Decode 线程配置等环节的组合优化，最终测试中的 TG128 达到 21.91 tok/s，Total 达到 95.41 tok/s。

更重要的是，端侧推理优化需要一条完整、可复核的工程链路：固定软件版本和硬件环境，明确模型量化契约，完成组件与算子正确性验证，再建立可运行的最小适配基线，最后以统一口径进行整模型对照。只有把功能正确性、执行路径和性能统计放在同一套证据链中，才能判断优化是否真正有效。
