### 0. 前言：先建立直觉

先忘掉所有名词，想象一个场景：

**传统方式（TCP/IP）发数据**：你想把内存里的一批数据发给对端机器。数据要先从“你的内存” 拷到“内核缓冲区”，内核再封装 TCP/IP 头，交给网卡发出去；对端网卡收到后，先到内核协议栈 解包、排序、校验，再拷到“对端应用的内存”。这个过程中：

- 数据被**拷贝了多次**（用户态↔内核）；
- 收发双方 CPU 要**亲自处理协议栈**（封装、解包、校验、拷贝）；
- 应用要**主动调用** `send/recv`，CPU 全程参与。

**RDMA 方式**：你把内存“注册”给网卡，告诉对端“这块内存的地址和钥匙”，然后网卡就可以**绕过 CPU 和内核，直接 DMA 读写你的内存**。对端的 CPU 甚至全程不知道这件事发生了。

这就是 RDMA 的三个杀手锏：

1. **内核旁路（Kernel Bypass）**：数据收发不经过内核协议栈；
2. **零拷贝（Zero Copy）**：网卡直接读写用户内存，不来回拷贝；
3. **CPU Offload**：协议处理（封装、校验、ACK、重传）交给网卡硬件。

> 注意：严格的“零拷贝”指数据不被 CPU 拷贝、不经过内核缓冲；网卡本身还是通过 DMA 总线 搬运数据的。本文后面会精确表述为“网卡 DMA 直接读写已注册的用户内存”。

### 1. 为什么需要 RDMA

### 1.1 传统网络栈的瓶颈

一次传统 socket 收发的开销主要来自：

| 开销 | 说明 |
| --- | --- |
| 数据拷贝 | 用户缓冲区 ↔ 内核 socket 缓冲区（单次发送约 1 次 CPU 拷贝，收发两端合计约 2 次） |
| 系统调用 | 每次 send/recv 都要陷入内核 |
| 协议处理 | TCP/IP 校验、分段、拥塞控制都在 CPU 上跑 |
| 上下文切换 | 中断 + 软中断 + 唤醒等待进程 |

在高带宽（100G/200G/400G）低时延场景下，这些开销会成为瓶颈——**CPU 忙着搬数据，没空算业务**。

### 1.2 RDMA 的应对

RDMA（Remote Direct Memory Access，远程直接内存访问）把“网络传输”这件事从 CPU 手里夺走， 交给网卡（HCA/RNIC）：

- **双边操作 Send/Recv**：接收方先准备一块接收缓冲，发送方 Send，数据落到对端缓冲；
- **单边操作 RDMA Read/Write**：发送方持有对端内存的“地址+钥匙”，直接读/写，对端 CPU 完全不参与（这正是 `ib_write_bw` 测的东西）；
- **原子操作 Atomic**：对远端内存做原子的比较交换 / 累加。

### 1.3 适用场景

分布式存储、HPC 高性能计算、AI/GPU 集群、数据库集群、消息中间件——一切“低时延、高吞吐、 低 CPU 占用”的网络场景。

### 2. 核心概念词典

这一节逐个解释 RDMA 编程里绕不开的名词。建议先通读一遍有个印象，后面看流程时再回来对照。

### 2.1 HCA / RNIC（网卡硬件）

RDMA 网卡。InfiniBand 里叫 HCA（Host Channel Adapter），以太网里叫 RNIC。它是执行 RDMA 的硬件：读 WQE、DMA 搬数据、生成报文、写 CQE、做 ACK/重传，全部由它完成。

### 2.2 Verbs API（编程接口）

RDMA 的标准编程接口，所有函数都以 `ibv_` 开头（如 `ibv_open_device`、`ibv_post_send`）。 它定义在 `rdma-core-master/libibverbs/verbs.h`。应用通过 Verbs 操作设备，不用关心底层是哪家网卡。

### 2.3 PD（Protection Domain，保护域）

一个“资源归属 + 访问隔离”的容器。MR、QP、AH 都挂在某个 PD 下。只有同一个 PD 内的资源才能 互相配合使用。创建 PD 用 `ibv_alloc_pd`。

代码（`verbs.h:616-618` 访问权限标志）：

```c
IBV_ACCESS_LOCAL_WRITE   = 1,       // 允许本端写
IBV_ACCESS_REMOTE_WRITE  = (1<<1),  // 允许远端写
IBV_ACCESS_REMOTE_READ   = (1<<2),  // 允许远端读
```

### 2.4 MR（Memory Region，内存注册）—— 最重要的概念之一

网卡要直接读写用户内存，必须先“注册”这块内存。注册做三件事（对应内核 `mlx5_ib_reg_user_mr` → `__ib_umem_get_va`）：

1. **pin 页**：把这块内存的物理页固定住，防止操作系统把它换出到磁盘；
2. **DMA 映射**：为每个物理页建立网卡可见的 DMA 地址；
3. **建翻译表（MTT）**：生成一个 MKEY，硬件用 MKEY 查表把虚拟地址翻译成 DMA 地址。

注册返回两个“钥匙”，本质是同一个 MKEY 值（内核 `mr.c:394-395` 把 `lkey` 和 `rkey` 设为 同一个值）：

- **lkey（local key）**：填在本地 WQE 的 DATA 段，告诉网卡“本地数据从这里读”；
- **rkey（remote key）**：通过带外通道告诉对端，对端把它填进 RETH 头，凭它在你的内存上做 RDMA 访问。

**类比**：注册内存 = 把家里的东西（数据）登记进“快递代收点”，拿到两把钥匙——lkey 给自己 用（告诉快递员从哪个柜子取货），rkey 给朋友（朋友凭它直接往你家柜子里放东西）。

### 2.5 QP（Queue Pair，队列对）—— 通信的基本单位

一次 RDMA 连接的两端各有一个 QP。每个 QP 包含两个队列：

- **SQ（Send Queue，发送队列）**：存放“我要发出去的活儿”（发送 WQE）；
- **RQ（Receive Queue，接收队列）**：存放“对方发来的数据该往哪放”（接收 WQE）。

QP 是 RDMA 寻址的目标：报文里带着“目的 QPN（Queue Pair Number）”，对端网卡据此找到 QP， 再决定把数据写到哪块内存。

### 2.6 CQ（Completion Queue，完成队列）

网卡干完活之后，要把结果通知应用。CQ 就是放“完成通知（CQE）”的队列。一个 QP 的 SQ 和 RQ 可以共用或各用一个 CQ。应用通过 `ibv_poll_cq` 轮询 CQ，拿到完成信息（哪个操作完成了、是否 成功、写/读了多少字节）。

### 2.7 WR / WQE / CQE / WC / SGE（核心名词）

| 名词 | 全称 | 谁创建 | 含义 |
| --- | --- | --- | --- |
| WR | Work Request | 应用 | 应用提交的“请求描述”（要发什么、发到哪） |
| WQE | Work Queue Element | 驱动 | WR 被投递到 SQ/RQ 后变成的“队列元素”，硬件真正消费它 |
| CQE | Completion Queue Entry | 硬件 | 硬件完成后写进 CQ 的“完成记录” |
| WC | Work Completion | 驱动（轮询 CQ 时填充） | ibv_poll_cq 把 CQE 翻译成应用可读的完成信息 |
| SGE | Scatter/Gather Element | 应用 | 描述一块内存：(addr, length, lkey)，一个 WR 可含多个 SGE |

**类比**：WR 是“派件单”，驱动把它变成 WQE 放进快递队列（SQ），快递员（网卡）取走派件， 送完写一张“签收单”（CQE）放进 CQ，你（应用）轮询 CQ 把它读成 WC。

### 2.8 门铃（Doorbell）—— 零拷贝数据面的关键

用户态怎么告诉网卡“SQ 里有新活儿了”？答案是**门铃**。

创建 QP 时，内核把一小块寄存器空间（UAR，User Access Region）`mmap` 到用户态。应用拼好 WQE 后，直接往这个地址写一个 64 位的“门铃值”，网卡硬件立刻感知并开始消费 SQ。整个过程 **不需要系统调用、不经过内核**。

对应代码是 `post_send_db`（`rdma-core-master/providers/mlx5/qp.c:754`），它先更新 doorbell record （记录 SQ 生产位置），再 `mmio_write64_be` 敲门铃。

### 2.9 地址类概念：LID / GID / QPN / PSN

| 名词 | 含义 | 作用 |
| --- | --- | --- |
| LID | Local Identifier | IB 网络的本地地址（RoCEv2 基本不用） |
| GID | Global Identifier | 全局地址，RoCEv2 里就是 IP 地址（128 位 GID 低 32 位含 IPv4） |
| QPN | Queue Pair Number | 标识对端 QP 的编号 |
| PSN | Packet Sequence Number | 报文序号，用于可靠传输的排序与重传 |

### 2.10 传输类型：RC / UC / UD / RD

| 类型 | 全称 | 特点 | 支持单边 |
| --- | --- | --- | --- |
| RC | Reliable Connected | 可靠、有序、一对一 | 是（Read/Write/Atomic） |
| UC | Unreliable Connected | 不可靠、一对一 | 是（仅 Write） |
| UD | Unreliable Datagram | 不可靠、一对多 | 否（仅 Send/Recv） |
| RD | Reliable Datagram | 可靠、一对多（较少用） | 是 |

`ib_write_bw` 默认用 **RC**（`verbs.h:933` `IBV_QPT_RC = 2`），可靠、支持单边 Write。

### 2.11 操作类型：Send/Recv vs RDMA Read/Write vs Atomic

```c
IBV_WR_SEND,               // 双边：发到对端 RQ
IBV_WR_RDMA_WRITE,         // 单边：直接写对端内存
IBV_WR_RDMA_WRITE_WITH_IMM,
IBV_WR_RDMA_READ,          // 单边：直接读对端内存
...                        // verbs.h:1136 附近
```

- **Send/Recv（双边）**：接收方必须先 `ibv_post_recv` 投递接收缓冲，否则收不到；
- **RDMA Write（单边）**：发送方持有对端 `(rkey, vaddr)`，直接写，**对端 CPU 无感**；
- **RDMA Read（单边）**：发送方直接把对端内存“拉”过来；
- **Atomic**：对远端 8 字节做原子比较交换/累加。

`ib_write_bw` 测的就是 **RDMA Write 的单边带宽**。

### 2.12 QP 状态机

QP 有严格的状态迁移（`verbs.h:1082` 的 `ibv_qp_state`）：

```text
RESET ──► INIT ──► RTR ──► RTS
                 Ready to Receive  Ready to Send
```

- **RESET**：刚创建，未初始化；
- **INIT**：配好端口、pkey 等本地属性；
- **RTR（Ready to Receive）**：配好对端地址，能收不能发；
- **RTS（Ready to Send）**：能收能发，正式通信。

> 注意：mlx5 的合法迁移是沿上图**单向前进**（外加任意状态 → RESET/ERROR，以及同状态重配）， **不能**沿 RTS→RTR→INIT 逐级后退（见 `qp.c:4263` 的状态机表）。

`ib_write_bw` 里，`ctx_init` 时迁到 INIT，`ctx_connect` 时迁到 RTR 再 RTS。

### 3. RoCE 是什么

RDMA 有三条“落地路线”：

| 技术 | 传输层承载 | 可路由 | 硬件 |
| --- | --- | --- | --- |
| InfiniBand | 专用 IB 链路层 | 否（不在 IP 上路由，走 IB fabric 自身的 LID/GRH 路由） | IB 网卡 + IB 交换机 |
| RoCEv1 | 以太网 + GRH（EtherType 0x8915） | 否（二层） | 以太网卡 |
| RoCEv2 | 以太网 + IP + UDP（端口 4791） | 是（三层） | 以太网卡 |
| iWARP | TCP（RDDP 协议） | 是 | 以太网卡 |

RoCE 的全称是 **RDMA over Converged Ethernet**（融合以太网上的 RDMA）。其中 RoCEv2 把 InfiniBand 的传输层（BTH、RETH 等）**塞进 UDP 报文**，从而能在普通以太网/IP 网络上跑 RDMA （RoCEv1 则直接封装在以太网帧里，没有 IP/UDP，所以只能二层转发）。

RoCEv2 报文结构（自外向内）：

```text
以太网头(14B) → IP头(20/40B) → UDP头(8B) → IB BTH头(12B) → RETH头(16B) → 数据 → ICRC(4B)
```

两个关键数字（来自内核源码）：

- UDP 目的端口固定 `4791`（`include/rdma/ib_verbs.h:151` 的 `ROCE_V2_UDP_DPORT`）；
- UDP 源端口由 flow_label 计算，落在 `0xC000–0xFFFF`（用于负载均衡/哈希）。

> 为什么 UDP 而不是 TCP？因为 RDMA 要自己做可靠传输（由硬件做 ACK/重传），用 TCP 会重复 做一遍、且受 TCP 拥塞控制拖累。UDP 只是“运输壳”，可靠性在 IB 传输层由硬件保证。

### 4. 一次 RDMA WRITE 的完整旅程

以 `ib_write_bw` 客户端向服务端内存写入数据为例，把整条链路串起来。

### 4.1 应用视角的七步

1. **打开设备**：`ibv_open_device` 拿到设备上下文；
2. **建资源**：PD → MR（注册内存）→ CQ → QP；
3. **交换地址信息**：双方通过 TCP 交换 QPN、PSN、rkey、vaddr、GID；
4. **迁移 QP**：把 QP 从 INIT 迁到 RTR 再 RTS；
5. **发 WR**：`ibv_post_send` 提交一条 `IBV_WR_RDMA_WRITE`；
6. **网卡干活**：硬件发 RoCEv2 报文，把数据写到对端内存；
7. **轮询完成**：`ibv_poll_cq` 拿到 WC，确认写入成功。

### 4.2 每一步背后发生了什么

**第 1 步（打开设备）**： `ibv_open_device` 打开 `/dev/infiniband/uverbsX` 字符设备，调用 mlx5 的 `mlx5_alloc_context`，把厂商操作表挂到 context 上。之后所有 `ibv_*` 都通过函数指针分发到 mlx5 provider。

**第 2 步（建资源）**：这一步属于“控制面”，相关的设备命令都要进内核。

- `ibv_reg_mr` 进内核 pin 页 + DMA 映射，返回 `(lkey, rkey)`；
- `ibv_create_qp` 时，用户态分配 SQ/RQ 缓冲和 doorbell record（umem 模型），内核登记并 `mmap` 出 UAR，从此用户态有了零拷贝数据面的“钥匙”。

**第 3 步（交换地址信息）**：RDMA 没有内核自动的连接管理（本例走 TCP 带外），所以双方把 `qpn/psn/rkey/vaddr/gid` 打包通过 socket 发给对方（`ethernet_write_keys/read_keys`）。 对端的 `vaddr + rkey` 就是这次 Write 的“投递地址”。

**第 4 步（迁移 QP）**：`ibv_modify_qp` 把对端 QPN、PSN、GID、MTU 等写进硬件的 QPC。 特别是 `mlx5_set_path` 把 GID 翻译成目的 MAC、UDP 源端口、flow_label 等，**提前把 RoCEv2 报文需要的寻址信息都备好了**。之后发数据就不用再进内核了。

**第 5 步（发 WR）**：`ibv_post_send` 是内联函数，直接调 `mlx5_post_send`。后者在用户态 SQ 缓冲区上拼一条 WQE（控制段 + RADR 远端地址段 + DATA 数据段），更新 doorbell record 后 敲一下门铃。**全程无系统调用**。

**第 6 步（网卡干活）**：硬件读到门铃，消费 WQE：

- 用 DATA 段的 lkey 查翻译表，DMA 读本地数据；
- 用 QPC 里备好的地址生成 Ethernet/IP/UDP/BTH/RETH 头；
- 把报文发出去。对端网卡按 BTH 的 QPN 找到 QP，按 RETH 的 rkey 查表，把数据 DMA 写进对端 内存——**对端 CPU 全程无感**。

**第 7 步（轮询完成）**：硬件写完 CQE（含 owner bit），应用 `ibv_poll_cq` 在用户态直接读 CQ，拿到 WC 确认成功，再更新 CQ 的 doorbell record 释放空间。同样不进内核。

### 4.3 一张图总结

```text
┌─────────────── 控制面（慢，进内核）───────────────┐
                │ open_device / reg_mr / create_qp / modify_qp      │
  应用 ──ibv──► libibverbs ──ops──► mlx5 provider ──uverbs──► 内核  │
  (perftest)                        (用户态)                       │
   │                                                               │
   │         ┌────────── 数据面（快，内核旁路）──────────┐          │
   └─post_send─► 拼 WQE → 敲门铃 ──► 网卡 DMA 发 RoCEv2 报文 ──► 对端内存
   └─poll_cq──► 读 CQE ────────────────────────────────────────────►
```

### 6. 常见疑问 FAQ

**Q1：为什么 RDMA Write 不需要对端 CPU？** 因为对端已经提前注册了内存，并把 `(rkey, vaddr)` 通过带外通道给了发送方。对端网卡收到 Write 报文后，凭 rkey 查翻译表就能自己把数据 DMA 写进去，不需要唤醒对端应用。

**Q2：为什么要注册内存？不注册不行吗？** 不行。网卡 DMA 需要稳定的物理页和 DMA 地址。注册就是把用户虚拟地址“钉住”并建立到 DMA 地址的映射，同时生成访问钥匙。注册后内存才能被网卡直接访问。

**Q3：门铃到底是什么？** 门铃就是用户态往 `mmap` 出来的 UAR 寄存器地址写一个 64 位值，通知网卡“SQ 里有新 WQE”。 它是“用户态直接驱动硬件”的关键——没有系统调用，也没有内核参与。

**Q4：数据面为什么能不进内核？** 因为控制面（建 QP）时，用户态就拿到了直接操作硬件所需的全部“句柄”：SQ/RQ/CQ 缓冲由 用户态自己分配（umem 模型）并由内核登记、DMA 映射给设备，UAR（门铃寄存器）则由内核 `mmap` 进用户态。所以发收数据时就能自己拼 WQE、敲门铃、读 CQE。

**Q5：RDMA 一定“零拷贝”吗？** 对小消息可以用 inline（`IBV_SEND_INLINE`，数据直接塞进 WQE）；对大消息，网卡 DMA 直接从 用户内存读，不经过内核缓冲，也不需要 CPU 拷贝。说“零拷贝”强调的是**不经过内核、不靠 CPU 搬数据**。

**Q6：RC 怎么保证可靠？** 靠硬件：报文带 PSN 序号，对端按序交付，丢包时硬件自动重传（ACK/NACK），这些都不占应用 CPU。

### 结语

一句话记住 RDMA：**控制面进内核搭好舞台，数据面在用户态直接驱动网卡搬数据。**

搞懂“内存注册（MR）→ 队列对（QP）→ 交换钥匙 → 敲门铃 → 网卡 DMA”这条主线，你就入门了。
