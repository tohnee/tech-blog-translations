## 引子

你有没有遇到过：显存明明还有一大块，新的请求却因为”要不到一块连续的显存”而进不来，GPU 算得闲闲的却吞吐上不去？这不是玄学，而是 KV Cache 的**显存碎片**在作祟。PagedAttention 就是 vLLM 在 2023 年给出的解药——借操作系统的「虚拟内存分页」思路，把碎片吃掉的那一大块显存释放出来。按 vLLM 论文的对比口径，它可把 KV Cache 利用率从朴素连续预留的约 20–40% 提升到接近 96%。

### 一、是什么

PagedAttention 是 vLLM 提出的注意力算法 + KV Cache 管理方法，核心是把 KV Cache 切成**固定大小、逻辑连续的 block（页）**，再用一张 **block table** 把逻辑块映射到**物理上不连续**的显存块，请求按需申请 block，不必预先预留一整段连续大块。

- **位置**：推理引擎的 KV Cache 管理层，夹在 Scheduler（调度）和 Attention Kernel 之间
- **长什么样**：每个 block 默认装 16 个 token 的 K/V；一张 block table 记录”第 0 逻辑块在哪块物理显存、第 1 逻辑块在哪块……”
- **一句话**：把”连续预留大块显存”换成”按需分页 + 映射表”，专治 KV Cache 的内部 + 外部碎片

### 二、为什么需要它（因果链）

1. **朴素实现的做法**：每个请求一进来，就按 `max_seq_len` 预留一整段**连续**的 KV Cache 显存（因为自回归要顺序追加，最简单就是开一块大数组）。
2. **内部碎片（internal fragmentation）**：绝大多数请求根本用不到 `max_seq_len`，预留的尾巴全浪费——典型场景利用率只有 **20–40%**。
3. **外部碎片（external fragmentation）**：请求进进出出，连续大块被切成大小不一的”洞”，等新请求要一块更大的连续显存时，明明总空闲够却塞不进任何单个洞。
4. **后果**：预留 + 碎片让可用显存实际有大半被白白空着——这本可容纳 **2–4 倍** batch 的显存被浪费，而推理吞吐恰恰被 batch 大小卡死（decode 是 memory-bound，batch 越大算术强度越高、GPU 越忙）。
5. **所以**：必须让 KV Cache 能**按需分配、物理不连续、靠表寻址**——这就是 PagedAttention 的动机。
6. **量化收益**（vLLM 论文对比口径）：碎片消除后 KV Cache 利用率可从约 20–40% 提升到接近 96%，等价 batch 容量显著扩大（论文给出量级约 2–4 倍），吞吐同步上涨。

**用 Qwen3-8B 算一笔账**（36 层，8 KV 头，d_head=128，FP16，seq=2048），先算单个请求（day01 已算过）：

```text
单请求 KV Cache = 2 × 36 × 8 × 128 × 2048 × 1 × 2 = 301,989,888 字节 ≈ 0.28 GiB
```

batch=32 时线性乘 32：

```text
32 请求 KV Cache = 0.28 GiB × 32 ≈ 9.0 GiB（= 9,663,676,416 字节；按十进制 1 GB=10⁹ 折算为 9.66 GB）
```

朴素连续预留（按 max_seq_len 留白）会额外吃掉 2–4 倍，即 18–36 GiB 被碎片吞掉；PagedAttention 把它压到 9.0 GiB 出头，省下的显存直接换成更大并发。

### 三、怎么办（先讲实现，再补手段）

光说”分页”太抽象。真正落地时，各框架怎么管 KV Cache、碎片怎么消、相同前缀怎么复用？先看vllm框架怎么做，再补代价与配合手段。

### 3.1 主流框架怎么实现

**vLLM：PagedAttention（原生）**

- **block 切分**：KV Cache 按固定 block（默认 16 token/block）分配，请求要几个 block 就申请几个，不用就归还。
- **block table 寻址**：逻辑上请求看到连续序列，物理上 block 散布各处；做 Attention 时按 block table 把分散的物理 block gather 成连续张量再算。
- **共享前缀（Copy-on-Write）**：并行采样 / beam search 多个候选共享同一段前缀 block，只在某分支被改写时才真正复制——省显存也省计算。
- **代码直觉**：`Scheduler` 管 block 的申请/释放/抢占（swap 到 CPU），`Worker` 调 attention kernel 时按 block table 取数。

### 3.2 代价、边界与配合手段

- **代价 1：间接寻址开销**。Attention 要先按 block table gather 物理 block，多一次访存组织；block size 选小→碎片少但元数据（block table）多、kernel 启动多；选大→元数据少但碎片略增。默认 16 是经验折中。
- **代价 2：不是银弹**。它解决的是”碎片”，不解决 KV Cache 总量随序列长线性膨胀——超长上下文仍要靠 KV Cache 量化、多级存储、PD 分离。
- **和 Continuous Batching 的关系**：token 级调度（下篇）必须建立在 PagedAttention 之上——请求能随时新增一个 block，调度器才能按 token 粒度动态塞入/换出。
- **和 Prefix Caching 的关系**：vLLM 的 Prefix Caching 本质就是给 PagedAttention 的 block 加了”按前缀 hash 复用”的能力。

### 3.3 代码直觉（block table 寻址伪码）

```python
# 逻辑序列 t 个 token，分散在若干物理 block 中
# block_table[req_id] = [phys_0, phys_1, ...]，每 block 装 16 token
def paged_gather(k_cache, block_table, req_id):
    blocks = block_table[req_id]
    # 把不连续的物理 block 拼成连续张量供 attention 使用
    return torch.cat([k_cache[phys] for phys in blocks], dim=0)

# attention 时：q 只算当前 token，k/v 来自 paged_gather 出的连续历史
k_hist = paged_gather(k_cache, block_table, req_id)
v_hist = paged_gather(v_cache, block_table, req_id)
out = attention(q_current, k_hist, v_hist)
```
