### 1. deepspeed多机多卡训练踏过的坑

> **作者**：100110 ｜ **赞同**：217 ｜ **原文**：[https://zhuanlan.zhihu.com/p/624223085](https://zhuanlan.zhihu.com/p/624223085) ｜ **全文来源**：知乎搜索摘要（正文节选基本覆盖全文，共 4 个坑）

多机多卡训练的标准启动方式：

```bash
deepspeed --hostfile hostfile \
    your_program.py \
    --deepspeed ds_config.json \
    <args>
```

以下是多机多卡训练中遇到的几个错误及处理办法。

### 坑 1：RuntimeError: Ninja is required to load C++ extensions

从报错来看是缺少 ninja，但实际 ninja 已经安装了。这时候要先**找到 ninja 的安装路径**（通常在当前 conda 虚拟环境的 `bin` 目录下），然后在训练代码的开头把它加入 `PATH`：

```python
local_env = os.environ.copy()
local_env["PATH"] = "/data/.conda/env/llms/bin:" + local_env["PATH"]
os.environ.update(local_env)
```

**根因**：多机启动时子进程继承的环境变量与登录 shell 不同，conda 环境的 `bin` 目录不在子进程的 `PATH` 里，导致 torch 加载 C++ 扩展时找不到 ninja。

### 坑 2：卡死在 “Using /home/nlp/.cache/torch_extensions/py39_cu118 as PyTorch extensions root…..”

运行时卡死在这一行（作者原话：”让人头秃几乎一天了。。。。”），或者卡在这句话前后的某些地方。

**解决办法**：清理 `~/.cache/torch_extensions`，把这个文件夹里的东西全部删掉即可，torch 在程序重新运行时会重新生成。如果不删除这个文件夹，**更换了 deepspeed 或者 transformers 版本之后，再次运行训练程序，就会卡死在这个地方**——因为缓存里的扩展是按旧版本编译的。

### 坑 3：GPU0 上莫名其妙多出来 3 个进程，各占约 1G 显存

单机多卡 / 多机多卡训练时，GPU0 上莫名多出 3 个进程，每个进程占用 1G 左右显存。看样子这三个进程本来应该去 GPU1、GPU2、GPU3 上，但是没有去成。

**根因**：transformers 用了开发版——作者手残 `git pull` 把 transformers 代码拉到最新，用上了 `4.29.0-dev`。

**解决**：把 transformers 换回稳定版本 `4.28.1`，再执行坑 2 中的步骤清除 torch 扩展缓存，再次执行，训练恢复正常，显存正常分配。

**经验**：训练环境不要用 `-dev` 开发版依赖，出现”进程没分到卡上”这类诡异现象时优先排查依赖版本变动。

### 坑 4：训练完改 `--do_predict` 推理，ZeRO stage 不匹配 + torchrun 后 batch 报错

训练完毕，改成 `--do_predict` 做预测时发现：

- deepspeed 默认的 **ZeRO stage 2 不行**，提示要使用 ZeRO stage 3；
- 换成 stage 3 又一堆问题。

于是直接改用 **torchrun 进行分布式推理**。用 torchrun 后又出现新报错：

```text
ValueError: expected sequence of length 109 at dim 1 (got 110)
```

训练的时候并没有这个错误。排查许久，可能的原因是 **inference 阶段数据太小，batch size 不能和训练时一样，得设置小一些**：作者训练时 `batch_size=16`，推理阶段改成 `batch_size=1`，目前可以正常推理，但速度太慢了。

> **作者**：欠拟合 ｜ **赞同**：121 ｜ **原文**：[https://zhuanlan.zhihu.com/p/668527201](https://zhuanlan.zhihu.com/p/668527201) ｜ **全文来源**：知乎搜索摘要（正文节选；评论区部分来自官方搜索接口）

### 坑 0：deepspeed 安装报 CUDA_HOME not exists

```bash
pip install deepspeed
```

报 `CUDA_HOME not exists` 错误。搜索后确认原因是：**cuda toolkit 没有装**——之前装的都是虚拟环境下的 cuda runtime，runtime 不含 `nvcc` 等编译工具，无法满足 deepspeed 编译 CUDA 扩展的需求。（作者参考了 Stack Overflow 上的解答。）

### 一、多机多卡部署：先确保一致性

**0. 确保一致性**（总纲）

1. **代码路径**：执行训练的代码、模型、数据集等相关文件、路径在所有节点上要一致（如果不一致，考虑建立软链接）；
2. **环境配置**：虚拟环境路径也要一样，conda 各个节点的安装路径也要一样（否则会报 `exits with return code = 127`）；各种安装的库版本要保持高度一致（否则会报 `exits with return code = -6`）；
3. **环境路径加载**：主节点上默认虚拟环境路径系统加载可能不正确，python 环境无法正常加载，所以需要在入口 python 文件里加入（作者注：这个问题目前没有在部署中遇到，记录一下别人的坑）：

```python
local_env = os.environ.copy()
local_env["PATH"] = "/home/centos/.conda/envs/pretrain6/bin:" + local_env["PATH"]
os.environ.update(local_env)
```

### 二、配置 ssh

1. **hosts 中加入节点名称**：同时在相关的机器上 `vim /etc/hosts`，输入：

```text
10.58.253.27 model1
10.58.253.26 model2
```

1. **生成 sshkey**：

```bash
ssh-keygen -t rsa
```

1. **互相拷贝 sshkey**：把自己的 sshkey 拷贝到对方以及自己的 `authorized_keys`：

```bash
ssh-copy-id ccwork@10.58.253.27
ssh-copy-id ccwork@10.58.253.26
```

1. **测试**：比如 `ssh model2`，如果不需要输入密码且连接成功，则配置成功。**注意：服务器之间需要使用相同的用户名。**

### 3. deepspeed多机多卡训练（UER-py 双节点容器实践）

> **作者**：Firefly ｜ **赞同**：43 ｜ **原文**：[https://zhuanlan.zhihu.com/p/622051995](https://zhuanlan.zhihu.com/p/622051995) ｜ **全文来源**：知乎搜索摘要（正文节选，两段摘录合并整理）

本文描述了利用微软的 deepspeed 训练大模型，启动 **2 个节点**，两个相同配置的镜像容器。

### 环境准备

两台带有 GPU 显卡的服务器，ssh 服务开启。参考微软的官方教程。

### 容器内 sshd 端口坑

由于之前在服务器启动 ssh 服务时，升级了 openssh 会导致服务器远程连接有问题，需要重启才行。重启了之后发现**容器内部的 sshd 无法启动、转发不了端口**。运维帮忙调试：在容器内部配置 `/etc/ssh/sshd_config`，把 `PORT=22` 的注释打开并换一个端口号（**2222**），成功启动。

原因是不熟悉 linux 的 `sed` 命令，没有看懂微软官方教程里的 shell 脚本，直接复制运行导致端口号一直没有改成功——sshd 一直启动在默认端口 22，容器内部的指定端口没有启动成功。其中 1 台机器运行：

```bash
service ssh status
# 显示：sshd is running
```

但查询端口号占用为空，说明其实没有启动成功——虽然显示 `sshd is running`，大概监听的是 22 端口。

**在 2 台机器都修改了指定端口之后，开始并行运算。**

### deepspeed 与 torch 的免密登录要求差异

并行运算需要两台机器免密登陆，**A 机器免密登陆 B 机器，B 机器也需要免密登陆 A 机器**。这个要求跟 torch 的并行还不太一样：torch 只要在主节点和子节点都启动 dist 并指定同一个端口号，在容器内部就可以直接连起来跑。

这个免密登陆的要求在 deepspeed 的官方教程里就写了一句话：*“which are machines accessible via passwordless SSH”*。而 UER-py 的 wiki 文档对 deepspeed 的描述也没有细说，只是描述需要配置 hostfile，两个节点需要如何配置并没有详细说明，对服务器之间通信不够熟悉的人则难以启动。

官方对 hostfile 的说明原文：

> DeepSpeed configures multi-node compute resources with hostfiles that are compatible with OpenMPI and Horovod. A hostfile is a list of hostnames (or SSH aliases), which are machines accessible via passwordless SSH, and slot counts, which specify the number of GPUs available on the system.

### 数据预处理与训练启动命令

```bash
python3 preprocess.py --corpus_path corpora/CLUECorpusSmall_5000_lines.txt --vocab_path models/google_zh_vocab.txt \
                      --dataset_path dataset.pt --processes_num 8 --dynamic_masking \
                      --data_processor mlm
deepspeed --hostfile=hostfile.txt pretrain.py --deepspeed --deepspeed_config models/deepspeed_config.json \
                                              --dataset_path dataset.pt --vocab_path models/google_zh_vocab.txt \
                                              --config_path models/megatron/bert_3.9B_config.json \
                                              --output_model_path models/output_model \
                                              --world_size 16 --batch_size 16 \
                                              --total_steps 10000 --save_checkpoint_steps 5000 --report_steps 100 --deep_init
```

### 踩坑记录

1. **`'pdsh' not installed`**：两台机器都在容器运行，解决方法：

```bash
apt-get install pdsh
```

1. **`--data_processor` 参数不一致导致报错**：教程代码的配置在 deepspeed 跑起来的时候**没有指定 `--data_processor mlm`**，而数据处理的时候指定了 `--data_processor mlm`。如果不手动指定的话会调用默认的 `--data_processor bert`，导致报错。

### 4. DeepSpeed ZeRO理论与VLM大模型训练实践

> **作者**：凯恩博 ｜ **赞同**：61 ｜ **原文**：[https://zhuanlan.zhihu.com/p/675360966](https://zhuanlan.zhihu.com/p/675360966) ｜ **全文来源**：知乎搜索摘要（正文节选，覆盖文章开头的理论部分）

### DeepSpeed 是什么？

如今的 DeepSpeed 除了训练之外，还在推理、压缩、Science 几个模块做了很多工作，本文主要关注它在训练中的优化。DeepSpeed Training 的官方介绍：

> DeepSpeed 提供了系统创新的融合，使大规模深度学习训练变得有效、高效，大大提高了易用性，并在可能的规模方面重新定义了深度学习训练格局。ZeRO、3D-Parallelism、DeepSpeed-MoE、ZeRO-Infinity 等创新属于培训支柱。

可以看到 ZeRO 技术是非常核心的创新，排在首位。

### DeepSpeed ZeRO 的核心特点

1. **内存优化**：通过创新的内存优化技术，DeepSpeed ZeRO 能够显著减少大规模模型训练所需的 GPU 内存，使研究人员和开发人员能够在现有硬件上训练更大、更复杂的模型。
2. **数据并行性**：通过高效的数据并行方法提高大规模模型训练效率，可跨多个 GPU 和多个节点分布式地训练模型，提高训练速度和扩展性。
3. **模型并行性**：支持模型并行，允许模型的不同部分在不同的 GPU 上运行，进一步增加训练大型模型的灵活性和效率。
4. **通信效率**：优化分布式训练中的通信机制，减少节点间同步模型参数时的网络负载，在大规模分布式环境下更为高效。
5. **易于使用**：与现有深度学习框架（如 PyTorch）无缝集成，易于使用和部署。
6. **支持超大规模模型**：支持数十亿甚至数千亿参数的模型，这对传统训练方法来说是不可能的。

### 使用的三个阶段

- **Stage 1**：优化器状态（例如对 Adam 优化器而言的 FP32 权重及 first、second moment estimates）在进程间（不同 GPU）切分（Split），每个进程仅更新其分区；
- **Stage 2**：用于更新模型权重的梯度（gradients）也被切分，每个进程仅保留与其优化器状态部分相对应的梯度；
- **Stage 3**：16 位模型参数（params）在进程之间被切分。ZeRO-3 会在前向和后向传递过程中自动收集和划分它们。

> **作者**：陈振彬 ｜ **赞同**：1 ｜ **原文**：[https://zhuanlan.zhihu.com/p/20780649384](https://zhuanlan.zhihu.com/p/20780649384) ｜ **全文来源**：知乎搜索摘要（持续更新的踩坑帖；第 2 个坑的细节被截断）

### 坑 1：[ZeRO3] stage3_prefetch_bucket_size should be a valid integer

报错原文：

```text
[rank1]: stage3_prefetch_bucket_size
[rank1]:   Input should be a valid integer, got a number with a fractional part
           [type=int_from_float, input_value=15099494.4, input_type=float]
```

**报错原因**：比较新版本的 deepspeed 中，`stage3_prefetch_bucket_size` 设置为 `"auto"` 的时候，pydantic 会进行类型检查，发现它被设置成了一个浮点数（15099494.4）。

**最终解决办法**：直接设置为一个整数。这个参数涉及 stage 的预取桶（prefetch bucket）的个数，可以根据自己的超参数选择一个合适的整数。

### 坑 2：[ZeRO 3 + offload] AttributeError: ‘Accelerator’ object has no attribute ‘deepspeed_config’

报错原文（截断）：

```text
[rank0]:   File "/home/chenzhb/.conda/envs/Medusa/lib/python3.9/site-packages/accelerate/accelerator.py",
```

### 9. 【踩坑记录】DeepSpeed + HuggingFace Trainer 多卡训练时,保存 checkpoint 导致 NCCL ALLREDUCE 超时

> **作者**：提姆 ｜ **赞同**：3 ｜ **原文**：[https://zhuanlan.zhihu.com/p/2001812270548787674](https://zhuanlan.zhihu.com/p/2001812270548787674) ｜ **全文来源**：知乎搜索摘要（正文节选；根因分析与解决方案代码均已覆盖主要部分）

### 现象

最近在用 **VideoLLaMA2 + HuggingFace Trainer + DeepSpeed** 做多卡训练时，反复遇到：训练正常跑，但**一到保存 checkpoint，过一会儿就报 NCCL ALLREDUCE 超时，而单卡能保存**。错误如下：

```text
Watchdog caught collective operation timeout:
WorkNCCL(OpType=ALLREDUCE, Timeout(ms)=600000)
```

一开始这个错误非常具有迷惑性：表面看起来是 NCCL 的 ALLREDUCE 通信失败，但实际上**根因并不在 NCCL**，而是保存 checkpoint 阶段多进程不同步导致的**典型死锁模式**。

### 问题根因

排查后发现，问题出在**重写了 `Trainer._save_checkpoint`**，并且在保存时：

- 只在 rank0 保存了 optimizer / scheduler / RNG state；
- 其他 rank 并没有参与保存过程。

但在 DeepSpeed ZeRO 模式下需要注意：

- **optimizer state 是分片（sharded）的**；
- **保存 optimizer 时必须所有 rank 都参与**；
- 如果只有 rank0 进入保存逻辑，而其他 rank 继续进入下一步训练，就会出现：

### 解决思路

核心思路可以总结为两点：

1. **共享文件**（config、adapter / LoRA 权重、trainer_state.json）**只允许 rank0 写**；
2. **optimizer / scheduler / RNG state 必须由所有 rank 共同参与保存**（DeepSpeed ZeRO 必需）。

### 稳定跑通的 `_save_checkpoint` 实现（节选）

```python
def _save_checkpoint(self, model, trial, metrics=None):
    def barrier():
        if dist.is_available() and dist.is_initialized():
            dist.barrier()

    from transformers.trainer_utils import PREFIX_CHECKPOINT_DIR
    checkpoint_folder = f"{PREFIX_CHECKPOINT_DIR}-{self.state.global_step}"
    run_dir = self._get_output_dir(trial=trial)
    output_dir = os.path.join(run_dir, checkpoint_folder)

    # 1) 保存前同步：所有 rank 一起进入保存阶段
    barrier()

    is_rank0 = self.is_world_process_zero()

    if getattr(self.args, "tune_mm_mlp_adapter", False):
        keys_to_match = ["mm_projector", "vision_resampler"]
        weight_to_save = get_mm_adapter_state_maybe_zero_3(self.model.named_parameters(), keys_to_match)

        # (A) 共享文件只在 rank0 写
        if is_rank0:
            os.makedirs(output_dir, exist_ok=True)
            self.model.config.save_pretrained(output_dir)
            torch.save(weight_to_save, os.path.join(output_dir, "mm_projector.bin"))
```

### 10. 一文看懂 DeepSpeed ZeRO-3 与 MoE 训练

> **作者**：RobinDevNotes ｜ **赞同**：0 ｜ **原文**：[https://zhuanlan.zhihu.com/p/2087116075406200855](https://zhuanlan.zhihu.com/p/2087116075406200855) ｜ **全文来源**：知乎搜索摘要（正文节选，覆盖摘要与理论核心部分）

### 摘要

训练大模型，最先撞墙的不是算力，而是显存。ZeRO-3 的思路很朴素：**别让每张卡都背一整份模型，把参数、梯度、优化器状态都切开，各卡只管自己那一份，用到别人的再临时借**。MoE 则从另一个方向下手，把模型做得很大，但每个 token 只用其中几个”专家”。

文章用最通俗的方式讲清两者原理，并一步一步带读者把配置、代码、存档和 MoE 层都跑通，顺便讲清一个容易踩的坑：**DeepSpeed 自带的 MoE 层目前不能和 ZeRO-3 一起用**。

### 显存到底被谁吃掉了

先做一道小学算术题。假设训练一个有 Ψ 个参数的模型，用最常见的混合精度加 Adam 优化器，每个参数要占这些显存：

- 半精度参数：2 字节
- 半精度梯度：2 字节
- 优化器状态：12 字节（32 位的参数副本 4 字节，一阶动量 4 字节，二阶动量 4 字节）

加起来是**每个参数 16 字节**。一个 75 亿参数的模型，光这三样就要 120GB，一张卡根本装不下——而且这还没算训练时的中间激活值。

### 普通数据并行为什么浪费

最常见的数据并行（DDP）是这样做的：每张卡都存一整份完整的 16Ψ，各自算不同的数据，再把梯度平均。

想象四个同学合租，每人都买了一整套同样的教材，只是各自做不同的习题。教材是一模一样的，四份里有三份纯属重复。这种”重复”，就是 ZeRO 要消灭的东西——**ZeRO 的全称是 Zero Redundancy Optimizer，零冗余优化器**。

### 另一个方向：稀疏化（MoE）

还有一条思路：模型总参数可以很多，但每次计算只用一小部分。这就是 MoE（Mixture of Experts，混合专家）。**它本身不省显存**（所有专家的参数都得存下来），**省的是计算量**，让”很大的模型”训练起来不至于慢到无法接受。

一句话：**ZeRO 管”怎么装得下”，MoE 管”怎么算得动”，两者可以搭配使用**（但注意 DeepSpeed 自带 MoE 层不能与 ZeRO-3 同用的坑）。

### ZeRO 的三级切分

ZeRO 把三类状态按从易到难分三级切开，分给数据并行的所有卡：

- **Stage 1**：只切优化器状态；
- **Stage 2**：再切梯度。每张卡只保留自己那份优化器状态对应的梯度；
- **Stage 3**：再切参数本身。前向和反向过程中，用到哪一层就临时收集哪一层，用完立刻丢掉。

仍用合租的比喻：”教材”对应参数，”批改意见”对应梯度，”复习笔记”对应优化器状态——

- Stage 1 是复习笔记不再每人抄一整份，四个人各记四分之一；
- Stage 2 是批改意见也各收各的那一部分；
- Stage 3 是连教材也拆成四份，每人只留四分之一；讲到哪一章，大家就把手里那一部分凑到一起、临时拼成完整的一章，用完各自只留回自己那份。
