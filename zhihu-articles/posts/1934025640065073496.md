## 前言

Pytorch2.7 中，官方更新了 FSDP2（Fully Shard Data Parallel2）。相较于 FSDP1，FSDP2 基于 DTensor API 表示对参数的切分。易用性得到了很大的提升。

## fully_shard 接口

> torch.distributed.fsdp**.fully_shard**(*module*,***,*mesh=None*,*reshard_after_forward=True*,*shard_placement_fn=None*,*mp_policy=MixedPrecisionPolicy(param_dtype=None,reduce_dtype=None,output_dtype=None,cast_forward_inputs=True)*,*offload_policy=OffloadPolicy()*,*ignored_params=None*)

当前，FSDP2 的使用核心是通过 fully_shard 接口对 module 进行处理。这里先介绍部分重要的参数：

- ***module***：被 FSDP 处理的 Module。
- ***mesh***：DeviceMesh 类，DTensor 表达的核心数据结果，用于创建 FSDP 通信组。
- ***reshard_after_forward***：有三个可选值：
- ***shard_placement_fn***：自定义分片策略，本文不需要关心。
- ***mp_policy***：混合精度策略，本文不需要关心。
- ***offload_policy***：offload（一种把显存上的数据“卸载”到内存上的技术，用于节省显存），本文不需要关心。
- ***ignored_params***：不希望使用 FSDP 进行分片的参数集合。

官方文档中给出了一个[FSDP2 的例程](https://docs.pytorch.org/tutorials/intermediate/FSDP_tutorial.html)，先看其是如何调用的：

```python3
from torch.distributed.fsdp import fully_shard, FSDPModule
model = Transformer()
for layer in model.layers:
    fully_shard(layer) #对 TransformerLayer 进行 FSDP 处理
fully_shard(model) #对顶层 model 进行 FSDP 处理。

assert isinstance(model, Transformer)
assert isinstance(model, FSDPModule)
print(model)
#  FSDPTransformer(
#    (tok_embeddings): Embedding(...)
#    ...
#    (layers): 3 x FSDPTransformerBlock(...)
#    (output): Linear(...)
#  )
```

关于为什么要这样子调用的问题，先简单进行理解：所谓用 fully_shard 来处理 module，就是递归地查询 module 树中每个 module 持有的 Parameter。如果某个 Parameter 还没有被收编到一个已存在的参数组（下文中对应的 FSDPParamGroup 类）内。我们就把他添加到当前参数组。

比如 fully_shard(layer)就是将一个 TransformerLayer 内的参数打包成一个参数组。

fully_shard(model) 会将当前没有归属于某个 FSDPParamGroup 的参数统一打包到一个参数组。

[官方 FSDP2 RFC](https://github.com/pytorch/pytorch/issues/114299)中给出一个形象化的表达：

![](https://pic4.zhimg.com/v2-df56c289f6bfdb8e34ee843d45e69e4f_r.jpg)
*FSDP Module分配情况*

以这个简单的 Transformer 网络为例，在循环内执行 fully_shard(layer)后，每个 TransformerBlock 内的参数分别纳入一个参数组内（绿色一组，蓝色一组）；最后对顶层 Transformer 模块做 fully_shard(model)后，还没有纳入参数组（下文中的 FSDPParamGroup 类）的 Embedding，Norm， Linear 模块被收编到一个参数组内。

### 为什么要对子层做 fully_shard？

这里有同学可能就会问了：“为什么我们还需要对每个 TransFormerLayer 做一次 fully_shard 处理呢？”

直观上理解，fully_shard 是希望**以 Parameter Group 为单位，每个参数组内管理的参数在每次 forward 之前做 AllGather，形成完整权重后再执行 forward**，执行 forward 完毕后再将不由自己维护的部分丢弃掉。

还是从上面官方的例子出发，如果我们不做 fully_shard(layer)，仅做 fully_shard(model)，model 下所有的参数都会被捕获到同一个参数组中进行管理。在其真正执行 forward 之前，对分片参数做 AllGather 后，参数所消耗显存的峰值和把一个模型完整参数塞进显存里是一样的，这样根本没有起到降低参数峰值占用的效果。

反观如果我们做了 fully_shard(layer）之后，该 layer 前向执行前仅 AllGather 自己组内的参数。该 layer 前向执行后又将不由自己维护的部分丢弃。这样参数显存的峰值占用就降低了。

## 模块设计

![](https://picx.zhimg.com/v2-03cc6a5f682ecf79dae8cf17016dc265_r.jpg)
*FSDP2 模块设计*

这里 FSDPState 类主要是用来处理 Module，为 Module 注册 Hook。下文中我们将仔细分析各 Hook 的用途。

每个 FSDPState 类会持有一个 FSDPParamGroup 类（没错，这个类就是我们第一章频繁提到的“参数组”的概念）；每个 FSDPParamGroup 会持有若干个 FSDPParam 对象。后面我们可以看到，当 FSDPParamGroup 内的参数需要做集合通信时，FSDPParamGroup 会**把组内参数拷贝到同一个缓冲区，以“批处理”的方式对参数进行集合通信**；而非一次一个的为参数做通信。

### 获取 DeviceMesh

![](https://pic2.zhimg.com/v2-9868204dd99d67bf9c7436e10fdb1ab7_r.jpg)
*fully_shard初始化Device Mesh*

这里很简单，若用户不传入 mesh 参数则内部自动创建，同时当前也仅支持 1D Mesh 和 2D Mesh。

1DMesh 下默认的 **Placements 为[Shard(0)]**，即默认切分每个参数的 Batch 维度；

### 获取要管理的 module，parameter

![](https://pic2.zhimg.com/v2-3ddf8a4bb89eaaa24994190ae9c95629_r.jpg)
*获取module，parameter*

`_get_managed_modules` 方法内部会跑一次深度优先搜索，对本 module 以及子 module 递归地进行搜索，若搜索时发现一个已经被 fully_shard 处理过的 module 则跳过收集该 module。

`_get_managed_states` 根据上一步筛选出来的 module，结合 `ignored_params` 参数。进一步将要管理的 parameters 收集起来。

最后创建 `FSDPParamGroup` 对象，`FSDPParamGroup `对象的__init__函数位于 `torch/distributed/fsdp/_fully_shard/_fsdp_param_group.py `内，

![](https://pic1.zhimg.com/v2-07fd7711d52bb47911a4697573a50ebc_r.jpg)
*FSDPParamGroup的创建*

`param_module_infos` 是一个 param -> Module 的映射字典。

`self.fsdp_params` 是一个 `FSDPParam` 对象列表，其中每个参数对应一个 `FSDPParam `对象，在 `FSDPParam `对象创建时，这里先**重点关注**该类的`_init_sharded_param` 方法。

![](https://pica.zhimg.com/v2-44a538ff24d9255f4ea621f746292cf2_r.jpg)
*FSDPParam初始化时调用_init_sharded_param方法*

好的，看到这里，我们对 FSDP2 的初始化流程做一个总结：在调用 fully_shard 接口之后，

1. 我们获取了 DeviceMesh，收集待 FSDP 流程处理的 `Parameters`。
2. 创建了 `FSDPParamGroup` 对象。创建该 `FSDPParamGroup `对象时，我们也初始化了若干 `FSDPParam` 对象（`FSDPParamGroup `中的 `self.fsdp_params `成员）。这些 `FSDPParam` 对象在初始化时会调用`_init_sharded_param` 方法 通过 DTensor API 将完整的权重切片后保存。

也就是说，**调用 fully_shard 接口之后，module 内所持有的参数就已经是参数分片了。**

## **FSDP2 运行时方案**

本小节中，我们将仔细分析 FSDPState 类，该类位于 `torch/distributed/fsdp/_fully_shard/_fsdp_state.py `文件中，FSDP 的核心机制都与这个类有关系。

我们这里先抛开复杂的实现方案，简单理解 FSDP2，从 Runtime 的角度去看一个 module，实际上做了这样几件事：

**Forward**执行**之前**：通过 AllGather 将分片参数聚合为完整参数。

**Forward**执行**之后**：对于那些不属于自己维护的参数，把它们占用的空间释放掉。

**Backward**执行**之前**：通过 AllGather 将分片参数聚合为完整参数。

**Backward**执行**之后**：两件事情，一个是对梯度做 ReduceScatter，另一个是将那些不属于自己维护的参数，把它们占用的空间释放掉。

看到这里聪明的你也肯定想到了可以用 **Pytorch 的 Hook 机制**来完成这件事情，实际上 FSDP2 的实现正是这样做的！本章节下面部分也将逐个场景去分析各个时间节点的 Hook 都做了什么。

### Foward 执行之前

![](https://pic1.zhimg.com/v2-375b1cdced6ae698742dd98f1ce8d40e_r.jpg)
*将self._pre_forward注册为forward_pre_hook*

[module.register_forward_pre_hook](https://docs.pytorch.org/docs/stable/generated/torch.nn.modules.module.register_module_forward_pre_hook.html)的触发时机是在 module 执行 forward 之前。对于这里而言，FSDPModule **在执行 Forward 计算之前，都会先走进 self._pre_forward 函数内的处理逻辑再进行 Forward 计算。**

其中，_pre_forward 内部继续调用 unshard 方法，对参数分片做 AllGather。

![](https://pic1.zhimg.com/v2-652094160f0e7a70c161733e3eb9abba_r.jpg)

### Forward 执行之后

类似 FSDPState._pre_forward 的处理方式，通过 register_forward_hook，让 module 前向执行结束后进入 **self._post_forward**处的执行逻辑。这里，我们**先不考虑多流优化**的内容，仅关注功能上 FSDPModule 在前向结束之后做了什么事情：

![](https://picx.zhimg.com/v2-b80e6828dc931458f07417ddd39ca865_r.jpg)
*_post_forward实现细节，这里仅关注红框中的内容，忽略多流配置*

_post_forward 中核心是两件事情：

1. 继续调用 FSDPParamGroup.post_forward 方法，简单来讲，若 reshard_after_forward 配置为 True，则将不属于自己维护的参数释放掉，降低显存消耗；若 reshard_after_forward 配置为 False，则持有完整的参数不释放。（忘记 reshard_after_forward 配置的朋友，可以回顾下第一小节。）
2. _register_pre_backward_hook，故名思意，为 module 做反向之前的 hook。

### Backward 执行之前

![](https://pica.zhimg.com/v2-8835cfd3016d3245af02929a8dc5e5e2_r.jpg)
*核心是调用FSDPParamGroup.pre_backward方法*

在上一小节中的最后，通过_register_pre_backward_hook 可以让 module 反向执行之前做我们期望的动作。具体来看，调用 FSDPParamGroup.pre_backward 方法，如果正向结束之后，我们选择丢弃不属于自己维护的参数，这里将重新执行 AllGather 达到聚合完整参数以进行反向运算。（官方 RFC 也提到过这一点，**参与计算图构建**的 Parameter 一定是完整的 Parameter）

![](https://pic4.zhimg.com/v2-693560b0736ff8b9d02dcefc8dc698df_r.jpg)
*完整的参数是自动求导的叶子节点*

这里也可以看到，reshard_after_forward 提供了一种取舍的机制：

若设置成 True，我们可以减少峰值显存占用，但是反向前还需要重新 AllGather，这样会带来通信开销。

如若设置成 False，峰值显存占用会增加，但是省去了反向前的通信操作。

### Backward 执行之后

![](https://pica.zhimg.com/v2-62837d390a6e96eb64a5d9f7e80bbcae_r.jpg)
*pre_forward中注册了Backward后的Hook*

![](https://picx.zhimg.com/v2-d6824af6244666c4e3b62549ca21598f_r.jpg)

![](https://pic3.zhimg.com/v2-68059215a1b5e3921ba835cb7c5baf4a_r.jpg)

Backward 执行之后的 hook，注册得比较隐晦，其实在 pre_forward 中进行了注册。其注册方式是通过重载了 autograd.Function 实现；在反向执行之后调用 FSDPParamGroup.post_backward 方法，在该方法内会对梯度做 ReduceScatter，进而达到每个参数分片只持有自己那一部分的梯度。

## FSDP2的多流掩盖与内存管理

流（Stream）是CUDA编程中一个概念，简单来讲，一条流就是一个任务队列，**流内的任务按照任务下发顺序串行执行，流间的任务并行执行**。

在使用Pytrorch做一些简单开发时，你并没有显示地指定算子跑在哪条流上，这是因为Pytorch隐式提供了一个**default stream**即默认流。如果不通过**with torch.cuda.stream(stream):**这样的语句指定stream，那算子就是跑在了default stream上。

流间并发控制通过Event机制，这里借助官方论坛中的一个讨论[FSDP内存管理的博客](https://dev-discuss.pytorch.org/t/fsdp-cudacachingallocator-an-outsider-newb-perspective/1486)里的一张图片来描述Event机制：

![](https://pica.zhimg.com/v2-9721e0bf6a15a24f9a81fba022b61fde_r.jpg)
*通过Event管理Stream间的同步*

解释一下这张图片，在CPU上，我们指定在stream0上记录Ev1，并且命令stream1等待Env1结束；stream1会阻塞直到Ev1结束。Ev2也是类似的。

By the way：这里不知道是不是画错了，按照[torch event官方文档介绍](https://docs.pytorch.ac.cn/docs/stable/generated/torch.Event.html)，阻塞CPU的应该是syncronize()方法。

此外，我们实际上**不希望**CPU阻塞，因为CPU承担着向不同Stream下发任务的职责。

![](https://picx.zhimg.com/v2-61082866d2573a8999e88fc0a535f711_r.jpg)
*event.wait*

![](https://pic1.zhimg.com/v2-8e0d9db43ae9cdede49dd5e168e923fa_r.jpg)
*event.synchronize*

总而言之，通过围绕Event的一系列接口，我们可以实现流与流之间，流与CPU之间的并发控制。

### Prefetch-预取机制

依旧从官方[FSDP2的Tutorial](https://docs.pytorch.ac.cn/tutorials/intermediate/FSDP_tutorial.html)入手，简单来讲就是分两条流并发执行，All-Gather Stream专注做参数的聚合，Default Stream默认流专注做Layer的计算，像官方文档图片这样演示的这样，计算Layer i时第聚合Layer i+1的参数。达到了计算/通信掩盖的目的。

![](https://pic4.zhimg.com/v2-ab1226a35398b4fb880e55f8d25ed20d_r.jpg)
*Prefetch的基本概念，图片源自官方Tutorial*

我们上面提到过，流之间的任务是并行执行的，因此流之间需要仔细地做并发控制，防止AllGather做的太快导致显存占用迅速上涨导致OOM。

![](https://pica.zhimg.com/v2-b4b6182fc7ddf0af9b123bbd625baad2_r.jpg)
*AllGather太快，多个层的完整参数同时存在，拉高显存峰值*

FSDP1对这个问题的解法是设置一个rate_limiter即速率控制器，在每个 Transformer Block 后阻塞 CPU，只有当上一层结束，才去对下一层做AllGather：

![](https://pica.zhimg.com/v2-400e8ab0c7a29f0f41745e9e305cadb6_r.jpg)
*FSDP1 CPU侧速率控制*

这样虽然防止了多层参数同时存在进而导致显存不够分配，但是这种方案阻塞了CPU，降低了吞吐。

除了需要注意控制AllGather流和默认流之间的配合，还有一点要注意的是**Tensor.record_stream(stream)。**

在多流编程中，Pytorch的缓存分配器CudaCachingAllocator只知道张量被分配到哪个流。因此，它已经能够正确管理单一流上的张量生命周期。然而，**如果一个张量在不同于其原始流的其他流上被使用，分配器可能会意外地重用内存**。调用此方法可以让分配器知道哪些流已使用该张量。

![](https://pica.zhimg.com/v2-5d01fff0e6773a2bf779f2a3ec5fbeea_r.jpg)
*record_stream保证了stream1引用A时，A不会被释放掉，虽然安全省事，但是不适合对显存精细管理的场景*

这里看到，请求释放A后需要等一段时间A所占用的空间才能真正被释放，假如在这段间隙时间内（图上的free requested 到 free completed）我们又申请显存。那此时的显存内既有A的显存又有新申请的显存。

当前，Deepspeed，Fairscale， FSDP1也都是用这个方法保障多流下张量使用的安全性，这种方法确实安全，但是在显存管理时却带来不可预见性。

总结一下，FSDP1在实现多流掩盖优化的过程中，主要有两点局限性：

1. 用race limter 阻塞CPU，虽然可以控制显存增长速度，但是耽误了算子下发的时间。
2. 使用record_stream方法管理多流间Tensor的生命周期，虽然安全，但是存在延迟释放的现象。

针对这两个问题，**FSDP2放弃使用record_stream**，通过event手动控制流的同步关系，消除record_event带来的不确定性，可以明确保证layer_i的空间释放后再进行对i+2层参数的AllGather。
