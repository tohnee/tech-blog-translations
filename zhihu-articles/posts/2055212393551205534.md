之前写过一篇介绍 FSDP 的系统性文章，因为代码量和篇幅，只从 Zero 讲到了 FSDP1，本篇文章直接从 FSDP2 开始。

[FSDP 详解：基础原理与源码解析](https://zhuanlan.zhihu.com/p/2003463581727995225)

很多人理解 FSDP2 是从一个 API 开始的：

```python3
fully_shard(transformer_block, ...)
```

但真正训练一个 70B、200B、甚至 MoE 1T 的模型时，没人会只调一行 `fully_shard`。一个能跑的训练脚本，至少要回答下面这些问题：

- TP、CP、EP、PP、DP 这五个并行维怎么排布在同一组 GPU 上？
- TransformerBlock、Embedding、LayerNorm、LM Head 各自该不该 wrap？
- 混合精度、激活重算、`torch.compile`、MoE 的 `all-to-all`，这几件事互相之间的顺序怎么定？
- 反向时的 `reduce-scatter`、`all-gather` 怎么跟下一层重叠？
- MoE 的专家梯度和非专家梯度的通信组是不是一个？除数对不对？

这些问题的答案其实都在 torchtitan 和 Megatron-LM 的源码里。

所以这篇笔记分四段来讲解。

- 第一段，把 FSDP2 的核心机制讲清楚——它和 FSDP1 到底差在哪。
- 第二段，看 torchtitan 是怎么把 FSDP2 + DTensor 这套原语真正落到一个能训 MoE 的训练框架里的。
- 第三段，看 Megatron-LM 走了一条几乎相反的路：手写的连续缓冲区 + DistributedOptimizer + 自己的 TP/EP。
- 第四段，进行对比分析，看它们各自吃了什么、给了什么，哪个适合什么，以及有什么优化空间。

## 1. FSDP2 到底解决了 FSDP1 的什么问题

### 1.1 FSDP1 的核心抽象：FlatParameter

要理解 FSDP2 为什么这么设计，得先回忆一下 FSDP1 是什么样子。

FSDP1 的最小调度单元叫 **FlatParameter**，本质是一个 1D 张量。它把一组 `nn.Parameter`（一般是一个 TransformerBlock 内部所有的 weight）按声明顺序拍扁、拼接、padding，最后变成一个超大的一维张量，再均匀切给 world size 个 rank。

这个设计在通信层面非常合理：

- NCCL 的 `all_gather_into_tensor` 和 `reduce_scatter_tensor` 要求各 rank 输入等长，FlatParameter 天然满足；
- 一次集合通信带多个参数，减少 NCCL launch 次数；
- 大块数据传输 NCCL 跑得更快。

但代价也很明显。优化器看到的是一个 `[N_total]` 的 1D 张量，但用户写的代码里 `model.layers[i].attention.wq.weight` 应该是个 `[d, d]` 的矩阵。FSDP1 用一组元数据把”原始 shape、stride、offset、padding 长度、是否跨 rank 切分”全部记下来，需要用的时候再”展开成 view”。这套元数据非常脆弱：

- mixed precision 要维护一份低精度副本和一份 fp32 主权重，但都得放在 FlatParameter 上做；
- LoRA 这种”冻结+非冻结混搭”的场景，frozen 和 trainable 必须分到两个 FlatParameter 上，否则会浪费 grad 显存；
- DTensor、TP、checkpoint 这些更上层的抽象，根本接不进来——FlatParameter 不是一个语义上有意义的张量。

更具体地，FSDP1 为了在通信流和计算流之间共享 buffer，到处用 `tensor.record_stream(comm_stream)`。`record_stream` 告诉 caching allocator “这块内存还在另一条流上用，别回收”。问题是它依赖 allocator 的内部状态，回收时机不可预测，于是显存峰值经常飘忽不定。

### 1.2 FSDP2 的两件大事：DTensor + 显式生命周期

FSDP2 改了两个最底层的东西。

**第一件：每个参数自己就是 DTensor。**

DTensor 是 `torch.Tensor` 的子类，本质是 `(local_tensor, DeviceMesh, Placements)` 三元组。Placements 描述这个张量在 mesh 的每一维上是怎么放的：

- `Replicate()`：这一维上每个 rank 拷一份；
- `Shard(dim)`：这一维上切张量的某个维度；
- `Partial(op)`：这一维上每个 rank 持有”等待累加”的局部结果。

FSDP2 给每个 `nn.Parameter` 包一个 DTensor。对外可见的 `module.weight` 不再是个被偷偷塞进 FlatParameter 的 view，而是一个真实的、shape 保持原样的 DTensor。这件事看上去只是包装方式不同，实际带来的连锁反应非常大：

- **optimizer 不需要任何改造**。它看到的就是合法的 `nn.Parameter` 列表，只不过它们恰好是 DTensor。Adam 在每个 rank 上只对本地分片做 element-wise 运算，根本不知道什么叫分片。这跟 DeepSpeed 必须重写 `Adam` 是两条完全不同的路。
- **`state_dict()` 不需要通信**。每个 rank 自己保存自己的 shard 元信息，加载时按 mesh 重建。
- **TP/EP/HSDP 等其他并行方式可以通过 mesh 维度自然叠加**。`[Shard(dp), Shard(tp)]` 就是”先按 dp 切 dim 0、再按 tp 切 dim 1”。
- **padding 从”一个超大 1D buffer 整体补齐”变成”每个参数自己补齐”**。代码上的体现是 `_fsdp_param.py:298` 这几行：

```text
chunks = _chunk_with_empty(param_data, shard_world_size, dim=shard_dim)
padded_sharded_size = chunks[0].size()    # rank 0 永远最大
padded_sharded_param = param_data.new_zeros(padded_sharded_size)
padded_sharded_param[: chunks[self.rank].size(shard_dim)].copy_(chunks[self.rank])
self._sharded_param_data = padded_sharded_param.view(-1)
```

每个 `FSDPParam` 维护自己的 padding，互不干扰。

> DeepSpeed 提供了自己高度优化的优化器实现，如 DeepSpeedCPUAdam，甚至需要通过 deepspeed.initialize() 来构建优化器。DeepSpeed 也提供了自己的 `state_dict()` 实现，需要通过 deepspeed.utils.get_state_dict() 来获取。总的来说，deepspeed 将分片作为一种系统状态。优化器必须理解并管理参数、梯度和优化器状态是如何被切分和分布的

**第二件：彻底拋弃 `record_stream`。**

FSDP2 的内存管理只靠两个机制：

第一，`storage.resize_()` 控制实际占用。unsharded 参数的 `nn.Parameter` 对象**只构造一次**，状态切换时只是把它底下的 storage `resize_(0)` 或 `resize_(numel)`。这保留了 autograd 在 forward 里保存的 view 别名——即使 storage 被释放、view 也不会变野指针。

第二，跨流生命周期用 `NamedTuple + Event` 显式管理。在 `_fsdp_param_group.py:141` 你可以看到：

```text
class AllReduceState(NamedTuple):
    # Holding all_reduce_input keeps the caching allocator from reusing the block
    # across layers. This is a structural invariant, not bookkeeping: without it,
    # the next layer's RS can reuse the same physical block before this layer's
    # AR finishes under slow AR, causing gradient aliasing.
    all_reduce_input: torch.Tensor
    event: torch.Event | None
```

读懂这段注释你才知道它在防什么：HSDP 模式下 `all_reduce` 跨节点可能很慢，下一层的 `reduce_scatter` 如果复用了同一块物理内存，前一层的 AR 结果会被覆盖，出现”梯度互相串味”的极隐蔽 bug。FSDP2 的做法是直接用一个 Python 引用攥住那块 tensor，allocator 看到引用就不会回收，等 event 触发后再一起释放。

这种”用 Python 对象生命周期 + Event 等待来代替 `record_stream`“的做法，是 FSDP2 显存稳定且可预测的根本原因。

### 1.3 一组关键的运行时

FSDP2 的 forward/backward 是靠 `register_forward_pre_hook` 和 `register_forward_hook` 驱动的，跑起来是这个样子（以一个 TransformerBlock 为例）：

```text
forward 进 block 之前：
  _pre_forward
    └─ unshard()           # 发起 all_gather，等待
    └─ register_post_backward_hook  # 把反向阶段的入口挂上
    └─ prefetch 下一个 block

执行原 block 的 forward

forward 出 block 之后：
  _post_forward
    └─ reshard()           # 释放 unsharded buffer
    └─ register_pre_backward_hook   # 在输出张量上挂"反向时通知我"

backward 进 block 之前：
  _pre_backward (输出张量的 hook)
    └─ unshard()
    └─ prefetch 前一个 block

backward 算完之后：
  _post_backward (RegisterPostBackwardFunction 的 backward)
    └─ reshard()
    └─ foreach_reduce()    # reduce_scatter 梯度
```

这里有一个细节值得展开：FSDP2 把”反向时触发 reduce-scatter”挂在一个自定义 `autograd.Function` 上，而不是 FSDP1 那样挂在 `AccumulateGrad` 的 post-backward hook 上。差别是什么？

`AccumulateGrad` hook 是”参数梯度累加完成时通知你”，但参数可能被共享（同一个 `Linear` 在 forward 里被调两次）、可能 `retain_graph`、可能有梯度累积。在这些场景下，”何时累加完”这件事的语义并不清晰。不明白的后面可以再展开讲讲这个 hook 的坑。

把它换成 autograd 节点之后，触发时机由 autograd 引擎本身保证——节点对应输入张量的梯度计算完毕的那一刻，引擎会按图论顺序调用它，跟参数是否被共享、是否累积无关。这是 FSDP2 反向更稳健的根本原因。

### 1.4 一个被忽略的扩展点

FSDP2 还在 `FSDPParam` 上开了两个协议方法：`fsdp_pre_all_gather` 和 `fsdp_post_all_gather`。它们让自定义 Tensor 子类可以参与 all-gather：

```text
class Float8Tensor(torch.Tensor):
    def fsdp_pre_all_gather(self, mesh, ...):
        # 把 fp32 master shard 量化为 fp8 数据 + scale
        return (fp8_data, scale), metadata

    def fsdp_post_all_gather(self, all_gather_outputs, metadata, ...):
        # 收完之后重构成 unsharded fp8 tensor
        return Float8Tensor(fp8_data, scale), [fp8_data]
```

FSDP1 因为 FlatParameter 强制把所有参数摊成同 dtype 的 1D buffer，做不到这件事。FSDP2 因为每个参数独立、且允许”多输入/多输出”的 all-gather 协议，fp8、NF4(QLoRA) 这种”数据 + scale” 的量化格式可以直接接入。这是 FSDP2 能够成为 torchao、torchtune 等下游项目默认底座的原因。

## 2. torchtitan 是怎么把 FSDP2 用起来的

FSDP2 提供的是原语：mesh、DTensor、`fully_shard`、`parallelize_module`。但真正训练时，要把这些原语组合成一个能跑 TP+CP+FSDP+EP+PP 五维并行的流水，需要回答一长串”在哪一步做什么”的问题。

torchtitan 给出了一份非常工程化的参考答案。

### 2.1 `parallelize_llama` 的流程总览

打开 `torchtitan/models/llama3/infra/parallelize.py`，最重要的就是 `parallelize_llama` 这个函数。它把一个原始的 nn.Module 改造成可以跑五维并行的模型，按顺序做了这几件事：

```text
1. world_mesh = parallel_dims.world_mesh
   (从 ParallelDims 取出一个多维 mesh)

2. if tp > 1:
       apply_tp(model, world_mesh["tp"], ...)
       maybe_enable_async_tp(...)

3. if activation_checkpoint enabled:
       apply_ac(model, ...)

4. if torch.compile enabled:
       apply_compile(model, ...)

5. if FSDP enabled:
       apply_fsdp(model, world_mesh[...], MixedPrecisionPolicy(...), ...)
   elif dp_replicate > 1:
       apply_ddp(model, ...)
```

这个顺序不是任意的。注释里写得很直白：**“turn on per-TransformerBlock compile after AC wrapping and before FSDP”**。原因：

- AC 在最外层，编译看到的图是 `checkpoint_wrapper(TransformerBlock)`；
- compile 在中间，编译的对象是一个完整的 TransformerBlock，因为它结构重复，缓存命中率高；
- FSDP 在最外层，**它的 forward hook 不在编译图里**，否则 Dynamo 看到 FSDP 的 all-gather 就会断图。

这个先后顺序，是 torchtitan 跑通 `compile + FSDP + AC` 同时启用的关键。

> TP 决定单层内部怎么切，AC 决定 block 怎么省显存，compile 优化稳定的 block 计算，FSDP 最后负责跨 rank 的参数生命周期。 这个顺序就是为了让每一层机制只看到它应该处理的那部分复杂度。

### 2.2 FSDP wrap 的粒度

`apply_fsdp` 的核心是这几行（`parallelize.py:299-319`）：

```text
if model.tok_embeddings is not None:
    fully_shard(model.tok_embeddings, **fsdp_config,
                reshard_after_forward=reshard_after_forward)

for layer_id, transformer_block in model.layers.items():
    fully_shard(transformer_block, **fsdp_config,
                reshard_after_forward=reshard_after_forward)

# 注释:'do not reshard the last layers by default since FSDP would prefetch them
# immediately after the forward pass'
if model.norm is not None and model.output is not None:
    fully_shard([model.norm, model.output], **fsdp_config,
                reshard_after_forward=reshard_after_forward_policy == "always")

fully_shard(model, **fsdp_config)
```

四组 wrap，每组都有自己的考虑：

- **embedding 单独一组**：embedding 的参数量级和 transformer block 不一样，单独一组通信效率更高；
- **每个 TransformerBlock 单独一组**：粒度刚好——一个 block 大约 100M~500M 参数，一次 all-gather 量足够大、又不至于把显存撑爆；
- **norm + output 合成一组，且默认不 reshard**：这是个非常工程化的决定。norm 和 output（lm_head）是 forward 链路的最后一层，跑完它们立刻就进 backward；如果 reshard 释放掉，下一秒又要 all-gather 回来。注释里直接写 “FSDP would prefetch them immediately after the forward pass”，所以默认不释放，省一次 all-gather；
- **整个 model 再套一层**：这是 FSDP2 的”root call”约定。最外层这个 `fully_shard(model, ...)` 负责 lazy init、`train()` 模式切换时的初始 unshard 调度。如果不套这层，前 N-1 个 block 是 FSDP 管理的，model 本身不是，会出现状态不一致。

`reshard_after_forward` 这个参数还有个隐藏的”default”档：在没有 PP 时是 True，启用 PP 时是 False。原因是 PP 的微批会多次走同一组 stage，关掉 reshard 才能避免每个 microbatch 一次额外 all-gather。

### 2.3 TP 计划：经典 Megatron 风格

TP 通过 `parallelize_module + parallel_plan dict` 实现。每个 TransformerBlock 的 plan 大致是这样（`parallelize.py:205-232`）：

```text
layer_plan = {
    "attention_norm": SequenceParallel(),
    "attention": prepare_module_input(
        input_layouts=(Shard(1), None, None, None),
        desired_input_layouts=(Replicate(), None, None, None),
    ),
    "attention.wq": colwise_parallel(),
    "attention.wk": colwise_parallel(),
    "attention.wv": colwise_parallel(),
    "attention.wo": rowwise_parallel(output_layouts=Shard(1)),
    "ffn_norm": SequenceParallel(),
    "feed_forward": prepare_module_input(
        input_layouts=(Shard(1),),
        desired_input_layouts=(Replicate(),),
    ),
    "feed_forward.w1": colwise_parallel(),
    "feed_forward.w2": rowwise_parallel(output_layouts=Shard(1)),
    "feed_forward.w3": colwise_parallel(),
}
```

Q/K/V/W1/W3 是 colwise（按输出维切），O/W2 是 rowwise（按输入维切）。这是 Megatron 经典 pattern——一对 `column→row` 内部只需要一次 all-reduce，而不是两次 all-gather/reduce-scatter。

`attention_norm` 和 `ffn_norm` 用的是 `SequenceParallel()`。它的语义是：activations 在 sequence 维上 sharded，norm（element-wise on seq dim）可以直接在本地分片上算，不需要 all-gather。配合 `prepare_module_input` 把 sequence-sharded 的 hidden 在 attention 入口 all-gather 回来、在 attention 出口（`wo.output_layouts=Shard(1)`）再 reduce-scatter 回去，整个 attention 块的入口 AG 和出口 RS 自动配对。

这套 plan 的妙处在于：**FSDP2 + TP 的复合靠的是 mesh，而不是手写胶水**。TP 先于 FSDP 应用，于是 `fully_shard` 拿到的参数已经是 DTensor（在 TP 维上 Shard），FSDP2 只是在 DP 维上再加一层 Shard，最终形成 `[Shard(dp), Shard(tp)]` 的二维 placement。这是 DTensor 抽象的最直接收益。

### 2.4 MoE / EP：torchtitan 真正复杂的地方

llama4 的 MoE 是 torchtitan 复杂度的一个 peak。展开看看。

**专家怎么切。** `ExpertParallel._partition_fn`（`expert_parallel.py:140`）：

```text
@staticmethod
def _partition_fn(name, mod, device_mesh):
    for name, param in mod.named_parameters(recurse=False):
        dist_param = nn.Parameter(distribute_tensor(param, device_mesh, [Shard(0)]))
        mod.register_parameter(name, dist_param)
```

`GroupedExperts` 的 `w1/w2/w3` 形状是 `(num_experts, hidden, ...)`——专家轴在 dim 0。`Shard(0)` 就是把专家平均分给 EP ranks。如果有 64 个专家、EP=8，每个 rank 持有 8 个完整的专家。**注意：不是把单个专家的权重再切，而是按专家轴切**。这是 torchtitan 和大部分 MoE 框架的共同选择，因为单个专家本身不大、切碎以后 grouped GEMM 的优势会被通信成本吃掉。

MoE Transformer 里的参数可以粗分为两类：普通 dense/shared 参数，比如 attention、norm、embedding、router、shared experts 等；以及 routed experts 参数。EP + FSDP 共存的麻烦点在于：dense/shared 参数通常在 EP 维度上是复制的，需要按 DP/FSDP 维度保持一致；而 routed experts 参数按 expert ownership 分布在 EP ranks 上，只能在拥有对应 expert 的通信域里做 shard / 同步。两类参数的所有权、复制关系、梯度同步范围和运行时通信模式不同，所以不能简单用同一个 FSDP group 一把包完。

torchtitan 的做法（`llama4/infra/parallelize.py:336-376`）：

```text
if transformer_block.moe_enabled and ep_degree > 1:
    fsdp_mod_ep_config = fsdp_config.copy()
    fsdp_mod_ep_config["mesh"] = dp_mod_ep_mesh
    ...
    if dp_mod_ep_mesh.size() * ep_degree > num_experts:
        _experts_shard_placement_fn = lambda param: Shard(1)
    fully_shard(
        transformer_block.moe.experts,
        **fsdp_mod_ep_config,
        reshard_after_forward=reshard_after_forward,
        shard_placement_fn=_experts_shard_placement_fn,
    )
    transformer_block.moe.experts.set_gradient_divide_factor(gradient_divide_factor)

fully_shard(transformer_block, **fsdp_config, ...)
```

- 非专家参数走常规 `dp_shard_cp` mesh；
- 路由专家走 `dp_mod_ep_mesh = ("dp_replicate", "dp_shard_mod_ep")`，**不含 `dp_shard_in_ep`**——因为这一维已经被借走当 EP 用了；
- 如果 `dp_mod_ep × ep > num_experts`，专家轴切不下了，改切 dim 1；
- `set_gradient_divide_factor` 手动修正专家梯度的除数，让它和非专家梯度量纲一致。

> routed experts 和 dense 参数参与梯度平均的有效 DP 范围不同；如果直接使用各自 FSDP mesh 的默认除数，expert 梯度和 dense 梯度的 scale 可能不一致。因此需要显式修正 gradient divide factor，或者像新版 torchtitan 那样禁用 FSDP 自动 gradient division，统一由外部逻辑控制。

其中第四点，set_gradient_divide_factor 的作用是修正 routed experts 的梯度平均系数。因为 EP 把一部分 DP 维度借去做 expert ownership，expert 参数实际使用的 FSDP mesh 小于普通 dense 参数；如果沿用默认 FSDP mesh-size averaging，expert 梯度和非专家梯度的 scale 会不一致，导致 expert 更新偏大或偏小，进而影响早期路由稳定性。

**token 路由：all-to-all 加 D2H 同步。** MoE 真正的运行时是 token dispatch（`expert_parallel.py:76-138`）：

```text
num_tokens_per_expert_group = all_to_all_single(
    num_tokens_per_expert, None, None, group=device_mesh.get_group())
num_tokens_per_expert_group = torch.ops._c10d_functional.wait_tensor(
    num_tokens_per_expert_group)

input_splits = (num_tokens_per_expert.view(ep_degree, -1).sum(dim=1)
                .to(torch.device("cpu"), non_blocking=True))
output_splits = (num_tokens_per_expert_group.view(ep_degree, -1).sum(dim=1)
                 .to(torch.device("cpu"), non_blocking=False))
...
routed_input = all_to_all_single_autograd(
    routed_input, self.output_splits, self.input_splits,
    device_mesh.get_group())
```

注意倒数第二行注释：”this would incur a device-to-host sync”。MoE 跑起来必须有一次 D2H：要先用一次小的 all-to-all 把”每个 rank 要发给我多少 token”传过来，落到 CPU 才能作为下一次 `all_to_all_single` 的 `output_splits` 参数。这是 MoE 性能的硬瓶颈之一，所有 MoE 实现都绕不开。

**显式 prefetch：MoE 必备。** 这个 D2H 同步会把 FSDP2 的隐式 prefetch 顺序打乱。FSDP2 的默认 prefetch 是基于 forward 执行顺序的，但 D2H 一同步，CUDA 流的实际顺序就跟代码顺序不一样了。torchtitan 在 EP 启用时显式接管 prefetch（`llama4/infra/parallelize.py:389`）：

```text
# NOTE: set up explicit prefetching when EP is enabled, as D2H syncs
# in EP could interfere with implicit prefetching in FSDP
if ep_degree == 1:
    return
...
transformer_block.set_modules_to_forward_prefetch(
    [next_transformer_block, next_transformer_block.moe.experts])
...
transformer_block.set_modules_to_backward_prefetch(
    [prev_transformer_block, prev_transformer_block.moe.experts])
```

把”下一个 block + 它的 experts”都加入显式 prefetch 列表。这种细节，FSDP2 文档不会告诉你；只有真踩过 MoE 训练性能坑的人才知道。

为什么要同时 prefetch 两个？ 因为 TorchTitan 里 MoE block 是两层 FSDP：

```text
TransformerBlock
  attention / norm / router / shared_experts  -> 外层 fully_shard(transformer_block)
  routed experts                              -> 内层 fully_shard(transformer_block.moe.experts)
```

它们是两个不同的 FSDP module，所以只 prefetch next_transformer_block 不够的。

显式 prefetch 不是改变 MoE 计算，也不是改变 FSDP shard 方式；它只是提前告诉 FSDP2：“我马上会用这些 module 的完整参数，你现在就把 all-gather 发出去。”这样 MoE 的 D2H sync 即使卡住 CPU，也尽量不让下一层参数 all-gather 发得太晚。

### 2.5 Mesh 构建：dp2ep 的精妙之处

最后看 `ParallelDims.build_mesh`（`parallel_dims.py`）。带 EP 时：

```text
if self.etp == self.tp:
    dp_shard_mod_ep = self.dp_shard * self.cp // self.ep
    dp_shard_in_ep = self.ep // self.cp
else:
    assert self.etp == 1
    dp_shard_mod_ep = self.dp_shard * self.cp * self.tp // self.ep
    dp_shard_in_ep = self.ep // (self.cp * self.tp)
```

这就是 torchtitan 文档里说的 “dp2ep Expert Parallel”。**EP 维不是凭空增加的，而是从 `dp_shard`（必要时还有 `cp`、`tp`）里”借”出来的**。如果有 64 个 GPU、原本 `dp_shard=8, ep=4`，那 `dp_shard_mod_ep=2, dp_shard_in_ep=4`。EP 维度上的 4 个 rank，原本就是 dp_shard 维度上的 4 个 rank，只是换了个用法。

物理上 GPU 数量不变，只是同一组进程在不同维度上被解读成不同的通信组。这是 DTensor 的 mesh 抽象带来的强大灵活性——你不需要为 EP 新开一组进程，只要换一个 mesh 维度的解读方式就行。

之后通过 `_flatten` 把多维 mesh 合并成单一逻辑维，方便上层消费：

```text
mesh[tuple(dp_shard_cp_mesh_dim_names)]._flatten(mesh_dim_name="dp_shard_cp")
mesh[tuple(ep_mesh_dim_names)]._flatten(mesh_dim_name="ep")
```

后续代码就可以用 `world_mesh["dp_shard_cp"]` 直接拿到 FSDP 用的 mesh、用 `world_mesh["ep"]` 拿到 EP 用的 mesh，完全不需要关心底层有几维。

### 2.6 一些工程取舍的细节

此外，你会发现一堆原来还得这样”的细节：

- **梯度累积的处理**：torchtitan 不让 FSDP2 在最后一次 microbatch 才 reduce-scatter（那需要 `no_sync` 上下文），而是每次 microbatch 都 RS，并在 loss 上预先除以累积步数（`rescale_accumulated_loss`）。数学上等价，但每次 microbatch 都有通信、显存峰值不积压，工程上更稳。
- **MoE 下 `torch.compile` 需要打几个补丁**：`capture_scalar_outputs=True`（token-choice 路由器有 unbacked symint）、跳过 `experts` 子模块（FSDP hook 会让 Dynamo 破图）、给 `_run_experts_grouped_mm` 的 token 维标 `mark_dynamic`（all-to-all 后 token 数随 batch 变）。
- **`NoParallel` 这个小工具**：专门处理”什么都不并行但参数要转成 DTensor”的场景。否则 router gate 这种 replicate 计算的 plain Tensor 和 DTensor 混用，fused optimizer 和 gradient norm clipping 会崩。

## 3. Megatron-LM 的”FSDP 平替”

Megatron-LM 和 TorchTitan 最大的区别是：TorchTitan 更强调 PyTorch-native 的组合方式，用 DeviceMesh / DTensor / FSDP2 / torch.compile 把并行策略拼起来；

Megatron-LM 则是一个更完整的大模型训练系统。它的主力路径长期依赖 Megatron-Core 自己的 parallel state、参数/梯度 buffer、distributed optimizer 和通信 overlap 机制。虽然现在 Megatron 也提供 PyTorch FSDP2 和 Megatron-FSDP 入口，但大规模 TP/PP/EP/CP 组合训练里，参数如何放、梯度如何 reduce-scatter、optimizer 如何 step，仍然主要由 Megatron 自己的分布式栈接管。

下面我们将先简单介绍下 Megatron 自己的分布式参数切分，然后再进一步深度介绍 Megatron-FSDP。

### 3.1 DistributedOptimizer 不是 Megatron-FSDP

Megatron 传统数据并行路径的核心是：`_ParamAndGradBuffer + DistributedOptimizer`

它的核心思想可以一句话概括：**所有参数的 `data` 和 `main_grad` 都拼成一个超大的 1D 连续 buffer，每个参数变成 buffer 上的一段 view**。

```text
# 简化版
for param in params[::-1]:        # 反向遍历，跟 backprop 顺序匹配
    this_numel = param.data.nelement()
    param_start_index = pad_if_needed(param_start_index)
    param_end_index = param_start_index + this_numel
    self.param_index_map[param] = (param_start_index, param_end_index, bucket_id)
    bucket_params.add(param)
    if (param_end_index - bucket_start_index) >= bucket_size:
        finalize_bucket()
```

然后**把 `param.data` 重新指向 buffer 上的 view**：

```text
new_param_data = self._get(param.data.shape, param_start_index, buffer_type=BufferType.PARAM)
old_param_data = param.data
param.data = new_param_data
param.data.detach().copy_(old_param_data)
del old_param_data
param.main_grad = self._get(param.data.shape, param_start_index, buffer_type=BufferType.GRAD)
```

这里你可能会愣一下：”这不就是 FSDP1 的 FlatParameter 吗？” 是有几分像，但有本质区别：

- FSDP1 的 FlatParameter 是**整组参数的扁平 1D 张量，跨 rank shard 之后每个 rank 持有 1/N**；
- Megatron 的 `_ParamAndGradBuffer` 是**一个 rank 上完整的参数副本，所有参数拼一起，配 main_grad 副本**。

也就是说，Megatron 默认是 **DDP 的内存布局**——每个 rank 都有完整的参数和梯度。”FSDP 等价物”靠的是上面套一层 **DistributedOptimizer**：

> Megatron _ParamAndGradBuffer 解决的是“把本 rank 的参数/梯度组织成连续大 buffer，方便通信和 optimizer 更新”；DeepSpeed ZeRO/FSDP1 解决的是“DP rank 之间如何分摊参数、梯度、优化器状态的存储”。

```text
DistributedOptimizer 把 buffer 的字节范围按 dp_world_size 等分；
每个 rank 只持有自己那段的 fp32 master 副本和 optimizer state。

reduce-scatter 把 main_grad 按字节范围切到每个 rank；
optimizer step 在各自的 1/dp_world_size 段上跑；
all_gather 把更新后的 bf16 权重广播回完整 buffer。
```

注意这里”字节范围”四个字。`DistributedOptimizer` 把 buffer 切分给 DP rank 时，**完全不管参数边界**——一个 fp32 master 范围可能跨越好几个原始参数。从 `distrib_optimizer.py` 的注释里能直接看到：

> This conceptual partitioning of the grad buffer does NOT respect parameter boundaries, and as such it is assumed that each created range references a shard (or subset) of the full parameter.

所以一个 rank 上每个 optimizer param group 的 entry 是 `param.view(-1)[range.start:range.end]`——一个 plain CUDA tensor，不是 DTensor，连参数概念都没保留。

这是 Megatron 的设计哲学：**把模型当成一段带元信息的字节流来切，而不是一个有结构的张量图**。

### 3.2 手写的通信重叠优化：Bucket + Hook

Megatron 的 backward 通信重叠走的是**纯手写**的路。

`_ParamAndGradBuffer` 把整个 buffer 切成若干 bucket（默认 40MB 一个）。每个参数初始化时挂一个 grad_acc hook：

```text
def _make_backward_post_hook(self, param):
    def hook(*unused):
        if param in self.param_to_bucket_group:
            if param.grad is not None and not param.grad_added_to_main_grad:
                param.main_grad.add_(param.grad.data)
            param.grad = None
            if self.ddp_config.overlap_grad_reduce:
                self.param_to_bucket_group[param].register_grad_ready(param)
    return hook
```

`register_grad_ready` 递增 bucket 的就绪计数；当 bucket 内所有参数 grad ready，触发 `start_grad_sync()`：

```text
with _coalescing_manager(comm_group, async_ops=True) as cm:
    for idx, bucket in enumerate(self.buckets):
        if self.ddp_config.use_distributed_optimizer:
            ...
            grad_reduce_handle = dist_reduce_scatter_func(
                local_data_view, bucket.grad_data,
                op=reduce_op, group=comm_group, async_op=True)
        else:
            torch.distributed.all_reduce(
                bucket.grad_data, op=reduce_op,
                group=comm_group, async_op=True)
```

注意 `_coalescing_manager`：它把同一上下文内的所有 NCCL 调用合并发起。一个 bucket 内 100+ 个参数原本是 100+ 次小 RS，coalesce 之后是一次大 RS。

前向 all-gather 重叠是对称的：`_make_forward_pre_hook` 会等住”本参数所在 bucket 的 AG 完成”。同时 Megatron 维护一个 `next_param_gather_bucket_group` 链表，**反向 bucket 顺序**（因为前向用的顺序就是反向 bucket 完成 grad 的顺序）：

```text
for i in range(1, num_bucket_groups):
    bucket_groups[num_bucket_groups - i].next_param_gather_bucket_group = (
        bucket_groups[num_bucket_groups - i - 1])
```

某个 bucket 收到 forward_pre 时，**顺手把下一个 bucket 的 AG 发起出去**。这就是手写版的 prefetch。

整套机制非常清晰，但和 FSDP2 的差别也非常清晰：

- FSDP2 是**每个 submodule 的 pre/post hook 自己触发自己的通信**，PyTorch autograd 引擎保证顺序；
- Megatron 是**手维护 bucket 边界 + 手维护 prefetch 链 + 手调 `_coalescing_manager`**。

后者的好处是：你想做什么样的重叠都行，链表自己改。坏处是：每出一个新的 case（比如 MoE 的 expert grad 走另一个组），你得手写一条新的链。

### 3.3 Megatron-FSDP 是什么

Megatron-FSDP 是 Megatron-Core 自己实现的 custom FSDP。它不是 PyTorch FSDP2 的简单包装。 在 Megatron Bridge 里，它通过 `use_megatron_fsdp` 开启；

简单来说：Megatron-FSDP 的训练 runtime 不是以 PyTorch FSDP2/DTensor 作为核心调度抽象；但它的 checkpoint / state_dict 路径会使用 fsdp_dtensor，也就是 PyTorch DTensor + Distributed Checkpoint 来保存 sharded state。

在开启 optim_grads_params 后，rank 平时只持有自己负责的参数 shard。某个 FSDP unit module 要执行时，Megatron-FSDP 会把这个 unit 需要的参数 all-gather 出来；这个 unit 的 forward/backward 用完后，再把 unsharded 参数释放掉。 严格说，optim_grads_params shard 的是被 FSDP unit 覆盖的参数。没有归入 fsdp_unit_modules 的参数或子模块不会走这套 sharding。Megatron-LM 默认覆盖支持的 Megatron-Core 模块。

我们可以看到：

`MegatronFSDP` 支持 ZeRO 0/1/2/3 四档（`no_shard / optim / optim_grads / optim_grads_params`），forward/backward hook 长得跟 FSDP2 很像：

```text
def _pre_forward_param_unshard(module, args, kwargs):
    self.all_gather_and_wait_parameters_ready(
        params=param_list, prefetch=True,
        prefetch_order=PrefetchOrder.FORWARD_PASS_ORDER)
    return args, kwargs

def _post_backward(module, *unused):
    if isinstance(module, tuple(fsdp_unit_modules)):
        if self.ddp_config.data_parallel_sharding_strategy == "optim_grads_params":
            release_module_parameters(module)
    if grad_reduce_every_bprop or is_last_microbatch or self.model_auto_sync:
        self.grad_reduce_pipeline.reduce_gradients(param_list, ...)
```

但底下用的还是 `BucketingPolicy + AllGatherPipeline + GradReducePipeline + FixedPoolAllocator + StorageResizeBasedBucketAllocator`，没有任何 DTensor。换句话说，Megatron 哪怕做”ZeRO-3”，也是按自己那套方法做的——不是因为 FSDP2 不能用，而是因为这套已经跟其他模块（TP overlap、TE user buffer）耦合得很深，整体替换成本太高。

### 3.4 Megatron-FSDP 静态调度 double buffer

FSDP 的难点不只是“能不能 shard 参数”，还有：

all-gather 后的完整参数放哪里？ 什么时候释放？ 释放是否真的马上归还显存？ 下一层参数 prefetch 时会不会顶出显存峰值？

如果每个 unit 都频繁 cudaMalloc / cudaFree，或者依赖 PyTorch caching allocator 自己回收临时大 buffer，大模型训练很容易出现显存碎片、峰值抖动和性能下降。

Megatron-FSDP 因此引入了更显式的 buffer 管理：

其实原理类似这篇文章：[GPU 显存的静态调度——从一次训不下去的 OOM 说起](https://zhuanlan.zhihu.com/p/2054607848353616828)

```text
Storage resize based allocator:
  用底层 storage resize 更主动地释放临时 buffer。

Double buffer:
  为交替执行的 FSDP units 准备两块持久 buffer。
  当前 unit 用一块，下一个被 prefetch 的 unit 用另一块。
```

代价是：它要求 FSDP units 在尺寸上尽量规整，尤其依赖 depth-wise symmetry。如果相邻 unit 大小差异很大，double buffer 就没那么容易复用，运行时可能退回到 resize allocator 或其它 fallback 路径。

### 3.5 Megatron-FSDP 和 TP / PP / CP / EP 怎么共存

它要和 Megatron 的组合并行一起工作, 这里的核心问题是：FSDP 不能假设自己看到的是全局完整 dense 参数。 比如 TP 已经把一个 Linear 的权重切到不同 TP rank 上，那么 Megatron-FSDP 看到的是 TP 之后的本地/strided 参数 shard。FSDP unshard / reshard 是在这个基础上，继续沿 FSDP data-parallel submesh 进行的。

MoE 下更复杂。普通 dense 参数和 expert 参数可能对应不同的并行视角, 参考 torchtitian。

所以 Megatron-FSDP API 里会有普通 device_mesh，也会有面向 MoE 的 expt_device_mesh。这和 TorchTitan 里 EP + FSDP 要给 routed experts 单独处理 mesh 是同一个问题：专家参数和非专家参数的所有权、通信组和同步范围不完全一样。

但它和 torchtitian 的区别是：

```text
TorchTitan:
  原始 nn.Module
  -> apply_tp，把 Linear/Attention 改成 TP/DTensor 形态
  -> AC / compile
  -> apply_fsdp，在 TP 后的 module tree 上做 FSDP

Megatron:
  初始化 parallel_state / process groups
  -> 构造 ColumnParallelLinear / RowParallelLinear / MoE experts / PP stages
  -> 参数天然已经是 TP/EP/CP/PP 视角下的本地参数
  -> Megatron-FSDP 对这些本地/strided 参数 shard 做 all-gather / reshard / reduce-scatter
```

可以说，TorchTitan 是先建完整 PyTorch 模型，再按 TP -> FSDP 的顺序逐层改造；Megatron 是模型一出生就是 TP/EP/PP-aware 的本地分片，Megatron-FSDP 只是在这些分片上继续做 DP/FSDP 参数调度。

需要注意的是，Megatron-FSDP 的训练 runtime 是 Megatron 自己的 custom FSDP，但 checkpoint/state_dict 需要进入 DTensor/DCP 体系。这里的 DTensor 主要是作为 sharded weights / optimizer state 的表达和 placement 载体。

## 4. 对比分析

到这一步可以做对比了。我用一张表先列总览，再用几小节展开讨论。

| 维度 | torchtitan（FSDP2 + DTensor） | Megatron-LM（自研栈） |
| --- | --- | --- |
| 参数分片表示 | 每个 nn.Parameter 是 DTensor | 一个连续 buffer 上的 view，配字节范围 |
| 优化器看到的 | DTensor，Adam 自然在分片上跑 | plain Tensor view，DistributedOptimizer 手切 |
| 通信触发 | submodule pre/post hook + autograd Function | 手写 grad_acc hook + bucket + 链表 prefetch |
| TP 表达 | ColwiseParallel/RowwiseParallel plan dict | 自定义 autograd.Function，外加 CUDA_DEVICE_MAX_CONNECTIONS=1 |
| TP 通信重叠 | 依赖 DTensor + Inductor micro-pipeline TP | 依赖 TE user-buffer GEMM（kernel 级） |
| MoE 专家分片 | Shard(0) over expert dim，DTensor | 所有 local 专家拼成大张量，grouped GEMM |
| MoE dispatch | all_to_all_single_autograd + 显式 prefetch | 7 步 dispatcher，可调 D2H sync point |
| Mesh 模型 | dp2ep 借位，多维 mesh + _flatten | 两个 RankGenerator 分别处理 attention/MoE |
| 跨维度梯度同步 | DTensor 自动处理大部分 | 5 个手写 phase 串起来 |
| 与 torch.compile 关系 | 一等公民，layer-wise compile 缓存命中 | 部分模块 compile，更多依赖 TE / apex kernel |

### 4.1 哲学差异：模型是张量图，还是字节流

最大的差异是设计哲学层面的。

**torchtitan 把模型视作一个张量图。**每个张量都有自己的类型（`DTensor` 是 `Tensor` 的子类，带 mesh 和 placement），这个类型本身就承载分片信息。`fully_shard` 不是改变模型结构，而是给参数张量”贴上标签”——告诉它”你在 dp_shard_cp 这维上是 Shard(0)“。optimizer、checkpoint、loss 计算这些下游代码不需要任何改动，因为它们看到的还是 nn.Parameter，只不过这些参数恰好是有类型信息的 DTensor。

**Megatron 把模型视作一段带元信息的字节流。**`_ParamAndGradBuffer` 是一个大的 1D 字节范围，每个参数是这个范围里的一段 view。DistributedOptimizer 切的是”字节范围”而不是”参数”。每个 rank 上 optimizer 看到的是 `param.view(-1)[range.start:range.end]`，是个 plain CUDA tensor，连参数概念都不再保留。

这两种视角各自的代价是不一样的。

张量图视角的代价是**抽象层多了一层**。DTensor 的 redistribute 比手写 NCCL 调用多了一层调度，融合 kernel 接入难（你没法轻易把 TE 的 user-buffer GEMM 塞进 DTensor 的 dispatch 链）。

字节流视角的代价是**所有结构性操作都要手写**。新增一个并行维（CP → EP）、新增一个跨维度同步 phase、新增一种参数类型（fp8、NF4），都要在 buffer 抽象上手写一遍。代码量大、改起来重。

### 4.2 性能优势

性能上 Megatron 在 H100/H200 集群上是有明显优势的，但优势来源很集中：

1. **TE 的 user-buffer GEMM**——把 AG/RS 塞进 GEMM kernel 内部，硬件级 overlap；
2. **apex 的 `wgrad_gemm_accum_fp32`**——wgrad GEMM 直接累加到 fp32 main_grad，省一个 kernel；
3. **grouped GEMM**——一个 kernel 跑完所有 local 专家；
4. **`CUDA_DEVICE_MAX_CONNECTIONS=1` + 手动 issue 顺序**——精确控制 NCCL 调用何时进队列；
5. **`_coalescing_manager` + buckets**——把 100+ 个小 RS 合成一次大 RS；
6. **DeepEP 等可插拔的融合 dispatch**——MoE 路由路径的硬件优化。

这些优化里，**前三项依赖手写或第三方 CUDA kernel**，后三项是**调度顺序的精确控制**。torchtitan 在前三项上做不到（FSDP2 + DTensor 的抽象层不允许把 kernel 整体替换），在后三项上是部分做到（Inductor 的 micro-pipeline TP 是 5 的一种泛化）。

但 torchtitan 也不是没有自己的牌：

1. **`torch.compile` 友好**——layer-wise compile 缓存命中率高，对真实 workload 的端到端编译收益明显；
2. **Async TP**（Inductor 的 micro-pipeline TP）——把 GEMM 和 AG/RS 拆成 micro-stage 交错；
3. **fp8 / NF4 通过 `fsdp_pre_all_gather` 协议自然接入**；
4. **DTensor 的自动 redistribute**让”TP + FSDP + EP” 的组合不用手写胶水。

简单总结：**Megatron 在硬件极限性能上领先，torchtitan 在新场景接入和组合灵活性上领先**。

## 5. 小结

FSDP2 说白了就是把“分片”这事从系统手里夺回来，还给了张量本身。

FSDP1 的 FlatParameter 就像把一堆参数强行揉成一团 1D 大面包，好处是通信 launch 少，坏处是再兼容 LoRA 或者做 per-param 量化很难，而且还有 record_stream 等显存不稳定的问题。

再说说 torchtitan 和 Megatron。

TorchTitan 它的信条是：PyTorch 给我啥我就用啥。比如，你要加个 EP，无非是在 Mesh 里借一维，给专家参数贴个 Shard(0) 标签，剩下的 redistribute 自动帮你干了。好处当然是适配新模型快。

Megatron 它的信条是：它不相信任何黑盒，还是”全部手写”的代码反而更容易 review。从 bucket 划分到 prefetch 链表全是手写的。出问题时，你能直接读 Python 代码定位到 NCCL 调用，不需要追到 PyTorch core 的 dispatch 链。但问题是你想改个并行组合，得在好几段手写的 phase 状态机里跳来跳去，太复杂，不好上手。

不过最近 Megatron 开始捏着鼻子接入 DTensor 了（至少 checkpoint 路径在用），而 PyTorch 那边也在拼命搞 micro-pipeline TP 去补调度的短板。

所以可以明显的看出：未来 DTensor 会成为整个 PyTorch 生态的“通用总线”。这是因为模型架构的创新速度已经远超框架写死调度的迭代速度了。
