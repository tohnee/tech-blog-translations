前一段时间研究过一个有意思的问题，在数据流分析中MLIR是如何分析循环中的迭代变量的lattice的？

要搞清楚这个问题，我们要理解successor operands和的successor inputs。我从MLIR的网站上找到了一个`scf.for` 的IR。对于`scf.for` 来说，`%sum_0`和`%sum_next` 都是successor operands，`%sum_iter`和`%sum`都是successor inputs。

```cpp
func.func @reduce(%buffer: memref<1024xf32>, %lb: index,
                  %ub: index, %step: index) -> (f32) {
  // Initial sum set to 0.
  %sum_0 = arith.constant 0.0 : f32
  // iter_args binds initial values to the loop's region arguments.
  %sum = scf.for %iv = %lb to %ub step %step
      iter_args(%sum_iter = %sum_0) -> (f32) {
    %t = load %buffer[%iv] : memref<1024xf32>
    %sum_next = arith.addf %sum_iter, %t : f32
    // Yield current iteration sum to next iteration %sum_iter or to %sum
    // if final iteration.
    scf.yield %sum_next : f32
  }
  return %sum : f32
}

```

为什么`%sum_0`和`%sum_next` 都是successor operands ？我的理解是它们作为op的操作数进行了传递，可以看到它们分别是`scf.for` 和 `scf.yield`的操作数，`scf.for` 是`RegionBranchOp`，而`scf.yield`是`RegionBranchTerminatorOp`，我们可以通过这两个op对操作数进行转发，所以 `%sum_iter`和`%sum`都是successor inputs。

`%sum`可能同时被`%sum_0`和`%sum_next`影响，如果循环执行了最少一次，肯定会执行进`scf.for` 的region，然后从`scf.yield`出来，然后forward到`%sum`, 如果循环不会执行， `%sum_0`直接forward到`%sum`。

对于`%sum_iter`来说，如果循环不执行，`%sum_0`不会被forward到`%sum_iter`，如果循环只执行一次，`%sum_0`会被forward到`%sum_iter`。如果循环执行了两次，`%sum_next`会被forward到`%sum_iter`。

基于以上分析，直觉上来看只需要让successor inputs的lattices merge successor operands的lattices就行。不过还有一个问题，我们需要搞清楚`%sum_iter` merge 哪些 operands的lattices，循环不执行，region中的代码是死代码，可能我不需要merge，如果只执行了一次，那么我可能只需要merge `%sum_0`的lattice，如果执行多次，那么我要merge `%sum_0` 和 `%sum_next`的lattices。 对于 `%sum` 来说也是一样的。进一步讲，问题就转变为：`scf.for`的 entry block 入口处的前驱有哪些？以及`scf.for`结束位置的前驱有哪些？对于上述例子，由于它是一个 dynamic loop，我们应当假设循环会执行多次。因此，entry block 的前驱应包含`scf.for`本身和`scf.yield`；同理，loop 后的位置，其前驱也同样包含这两个操作。

MLIR于LLVM不同的一个点是拥有region的概念，拥有region的概念它有什么好处呢？现在我认为拥有这个概念，MLIR能够更好的对高层次的IR进行建模，`scf.for` 是一个很好的例子。MLIR 中没有 phi 节点的设计，但是通过 `RegionBranchOpInterface` 的设计实现了类似的功能。
