> **一句话**：decode 卡在显存带宽而不是算力，所以”一次前向验证 k 个候选 token”和”一次前向只出 1 个 token”耗时几乎一样——投机解码就是把这块**本来空着的算力**拿来一次赌 k 个，赌中几个就白赚几个，而且用**拒绝采样**保证最终输出分布和不投机时**逐字节一致**。<br> **前置**：`01-LLM推理入门.md`（prefill/decode、为什么 decode 慢）、`02-GPU入门.md`（显存带宽是 decode 瓶颈、roofline）、`12-采样与logits处理.md`（采样、温度/top-p）。没读过也能跟，关键概念本篇会就地补。 **代码基线**：vLLM v0.30.0

### 1. 先建立直觉

### 1.1 decode 的瓶颈是”读权重”，不是”算”

先复习一个 `01`/`02` 讲过的事实，它是本篇的全部地基：

> **decode（解码）**：LLM 生成阶段，每一步只喂 1 个 token（上一步刚吐出来的那个），算出下一个 token。它**必须串行**——第 n 个 token 依赖第 n-1 个，没法并行。

decode 的每一步都要干一件很亏本的事：**把模型的全部权重从显存（HBM）里读一遍**，只为了算出 1 个 token。

> **显存带宽瓶颈（memory-bound）**：一个 7B 模型的权重约 14GB（FP16）。decode 一步要把这 14GB 全部从 HBM 搬进 GPU 计算单元。GPU 的算力（做乘加）远快于搬数据的速度，所以这一步的时间几乎全花在”搬”上，真正”算”的时间只占零头——算力单元大部分时间在**空等数据**。

用后端工程师的话打个比方：这就像你为了返回一行查询结果，每次都被迫**把整张几十 GB 的表从磁盘完整读进内存**。瓶颈是磁盘 IO，不是 CPU。你顺手在内存里多算几行、少算几行，总耗时基本不变——因为时间都耗在那次全表读上了。

**关键推论**：既然一步的成本主要是”把权重读一遍”这个固定开销，那么在同一步里让模型多处理几个 token（比如 5 个而不是 1 个），额外成本很小——权重只读一次，5 个 token 复用同一次读。**这块被浪费的算力，就是投机解码要占的便宜。**

### 1.2 propose + verify：先猜后验

投机解码把”生成下一个 token”拆成两阶段：

```text
第一阶段  propose（提议）：用某种便宜的办法先猜出接下来 k 个 token（草稿）
                          —— 便宜 = 比跑一次大模型快得多
第二阶段  verify（验证）：大模型对这 k 个草稿 token 做【一次】前向，
                          同时算出"如果我自己来，每个位置该出什么"
                          —— 这一次前向的成本 ≈ 平时 decode 一步的成本
```

> **draft / 草稿 token**：投机器（proposer / drafter）猜出来的候选 token。它们**不一定对**——投机器是个近似,大模型才是权威。<br> **verify / 验证**：大模型一次前向,并行地检查这 k 个草稿。因为草稿 token 已经全在手上,可以把它们**拼成一个长度为 k 的输入序列**一次喂进去（就像一次 prefill 了 k 个 token）,而不用串行 decode k 次。

验证完，从头开始逐个比对：草稿第 1 个 token 大模型认不认？认就接受，继续看第 2 个；一旦某个位置大模型**不认**，就在那个位置停下，用大模型自己的结果替换，后面的草稿全部作废。

图示（k=4，接受了前 2 个）：

```text
草稿:      A    B    C    D          （投机器猜的 4 个）
大模型:    A    B    X    ...         （验证：前 2 个和草稿一致，第 3 个不一致）
           ✓    ✓    ✗
结果:      A    B    X                （接受 A、B，第 3 位用大模型的 X，C/D 丢弃）
```

这一步大模型只前向了一次，却往前推进了 3 个 token（A、B、X）。不投机的话，出这 3 个 token 要串行 3 次前向。

### 1.3 加速上限 ≈ 平均接受长度：一点算术

设投机器每轮提议 k 个草稿 token，大模型每轮平均接受了 `a` 个（`0 ≤ a ≤ k`）。每一轮：

- 成本：**1 次大模型前向**（加上投机器 propose 的开销，先忽略，见 1.5）。
- 产出：`a + 1` 个 token（`a` 个被接受的草稿，再加 1 个大模型在停下位置补的”权威 token”,这个补的 token 在代码里叫 **bonus token**，全接受时是从大模型分布里再采一个）。

> **bonus token（奖励 token）**：见 `vllm/v1/sample/rejection_sampler.py:55-64`。它是”就算一个草稿都没接受，这一轮大模型也至少能白送 1 个自己算的 token”——因为验证那次前向本来就顺带算出了每个位置的分布。

不投机时，出 `a+1` 个 token 要 `a+1` 次前向。投机时只要 1 次。所以：

```text
加速比 ≈ (a + 1) 次前向的活  /  1 次前向  =  平均接受长度（含 bonus）
```

vLLM 的日志就是这么定义”平均接受长度”的——见 `vllm/v1/spec_decode/metrics.py:114`：

```python
# Conventionally, mean acceptance length includes the bonus token
mean_acceptance_length = 1 + (num_accepted_tokens / num_drafts)
```

直觉结论：

- 接受率越高、平均接受长度越长，加速越猛。接受长度 2.5 就意味着理论上 ~2.5x。
- 但加速有天花板：`a` 最多是 `k`，所以**加速上限 ≈ k+1**。可 `k` 也不能无脑调大——猜得越长，越靠后的 token 越容易猜错、白算（见 1.5 和第 3 节）。

### 2. 源码走读

### 2.1 一轮的挂接点：先 verify，后 propose

在 vLLM 的 step 主循环里，两阶段是这样串起来的（都在 `GPUModelRunner` 里）：

1. **verify**：大模型这一步的前向已经把 logits 算出来了。带草稿 token 时，不能直接 argmax/采样，而要走**拒绝采样器**来决定接受几个。调用点在 `vllm/v1/worker/gpu_model_runner.py:3681`：

```python
draft_probs = self._get_spec_decode_draft_probs(spec_decode_metadata)
sampler_output = self.rejection_sampler(
    spec_decode_metadata,   # 这一轮每个请求有几个草稿、logits 该怎么切
    draft_probs,            # 投机器给的草稿分布（greedy 场景可为 None）
    logits,                 # 大模型这次前向的 logits
    sampling_metadata,      # 温度/top-p/top-k/随机数种子
)
return sampler_output
```

这段在干什么：把”大模型算出的 logits”和”投机器提议的草稿”交给 `RejectionSampler`，由它按拒绝采样规则算出**这一轮到底接受了哪些 token**。

1. **propose**：这一步接受下来的 token 定了以后，再为**下一轮**猜草稿。分发在 `vllm/v1/worker/gpu_model_runner.py:5019` 的 `propose_draft_token_ids()`，按 `method` 派发到不同投机器：

```python
if spec_config.method == "ngram":
    draft_token_ids = self.drafter.propose(
        num_spec_tokens_to_schedule,
        sampled_token_ids,                  # 已确定的 token（含刚接受的）
        self.input_batch.num_tokens_no_spec,
        self.input_batch.token_ids_cpu,
        ...
    )
elif spec_config.method == "suffix": ...
elif spec_config.method == "medusa": ...
# eagle / draft_model 等走各自分支
```

投机器实例在初始化时按 `method` 选定，见 `vllm/v1/worker/gpu_model_runner.py:641-699`（`self.drafter = NgramProposer(...)` / `EagleProposer(...)` / `MedusaProposer(...)` / …）。

### 2.2 拒绝采样：怎么保证分布不变

这是全篇最该看懂的一段。`RejectionSampler` 的文档头 `vllm/v1/sample/rejection_sampler.py:45-65` 定义了三类输出 token：

```text
output tokens = accepted tokens + recovered tokens + bonus tokens
```

- **accepted（接受）**：草稿 token，按”草稿分布 q 和目标分布 p 的关系”通过了检验。
- **recovered（恢复）**：某个位置草稿被拒了，从一个**修正过的分布**里重新采一个填上。
- **bonus（奖励）**：全部接受时，末尾再从目标分布采 1 个。

它严格实现了投机采样原始论文（[arXiv:2211.17192](https://arxiv.org/abs/2211.17192)）的算法。**直观解释（不严格证明）**：

设某位置草稿 token 是 `x`，投机器给它的概率是 `q(x)`，大模型（目标）给它的概率是 `p(x)`。规则是：

```text
以概率 min(1, p(x)/q(x)) 接受 x：
  - 如果 p(x) >= q(x)（大模型比投机器还更想要 x）→ 必接受
  - 如果 p(x) <  q(x)（投机器过度自信）→ 以 p(x)/q(x) 的概率接受，否则拒绝
拒绝时：从"修正分布" p'(t) = normalize(max(0, p(t) - q(t))) 里重采一个（这就是 recovered token）
```

为什么这样不改变分布？一句话直觉：**投机器猜得太多的部分（q > p 处）按比例砍掉，猜得不够的部分（p > q 处）用 recovered 补回来**，一砍一补正好把整体拉回目标分布 p。数学上可证明：经过”接受 or 恢复”后，每个 token 落在任意值上的边际概率**恰好等于 p**——所以输出分布和你直接用大模型逐个采样**完全一样**，投机解码是**无损加速**，不是近似。

代码里随机数、修正分布的实现：

- 每个草稿位置一个 `[0,1)` 均匀随机数，用来做”以概率接受”的抛硬币，见 `generate_uniform_probs()`（`rejection_sampler.py`，注释特意用 float64 避免采到 0.0 的坑）。
- 修正分布的重采样在 `sample_recovered_tokens()`（同文件），用 `max(0, p - q)` 那套逻辑造 recovered token。

> **注意**：`draft_probs` 是投机器给的草稿分布 q。像 EAGLE/draft model 这种”有分布”的投机器能提供 q；而 n-gram/suffix 这种纯字面匹配的投机器**没有概率**（它只是”抄”了历史里的 token），这时走的是下面的 greedy 简化路径。

### 2.3 greedy 情形的简化

采样温度为 0（greedy，贪心解码，永远取概率最大的 token）时，不需要抛硬币，规则退化成**逐字比对**。见贪心内核 `rejection_greedy_sample_kernel`（`rejection_sampler.py:560+` 附近）：

```python
draft_token_id = tl.load(draft_token_ids_ptr + start_idx + pos)
target_argmax_id = tl.load(target_argmax_ptr + start_idx + pos)
...
# 非 synthetic 模式：草稿 token == 大模型的 argmax 就接受，否则用 argmax 顶替并停止
token_id = target_argmax_id
# 一旦某位置不等，rejected = True，后面全丢
```

这段在干什么：greedy 下”大模型会怎么选”是确定的（就是 argmax）。所以规则简单到极致——**草稿 token 恰好等于大模型的 argmax 就接受，第一个不等的位置就截断，用 argmax 替换**。这天然就和”不投机时逐个 argmax”产生完全相同的序列，无损性显而易见，连概率都不用算。

### 2.4 调度器要为草稿 token 预留 slot

投机解码给调度器（`Scheduler`）添了个麻烦：每一步除了给”真 token”排预算，还要给”下一轮的草稿 token”**预留 KV Cache 的坑（slot）**——因为草稿 token 一旦被验证接受，它们的 KV 就得有地方存。

> **slot / KV slot**：KV Cache 里能放一个 token 的 K/V 的位置。见 `03-KV Cache与PagedAttention.md`。

`schedule()` 开头就把这块预留量算出来，见 `vllm/v1/core/sched/scheduler.py:582-583`：

```python
spec = self.vllm_config.speculative_config
draft_slots = spec.max_num_new_slots_for_drafting if spec is not None else 0
```

然后在给每个 running 请求分配 token 预算时，把 `draft_slots` 从可用预算里扣掉，见 `scheduler.py:614` 和 `scheduler.py:663-664`：

```python
if input_budget <= draft_slots:
    break                       # 预算连草稿都塞不下，这一步别再收 running 请求了
...
num_new_tokens = min(
    num_new_tokens, token_budget, input_budget - draft_slots   # 给草稿留位
)
```

`schedule()` 顶部的注释（`scheduler.py:562-572`）把这套统一账本讲得很清楚：调度器眼里没有”prefill 阶段/decode 阶段”，只有 `num_computed_tokens` 要追上 `num_tokens_with_spec`，而后者 = `prompt + output + spec_token`。投机的草稿 token 就这样被塞进同一套预算模型里，和 chunked prefill、prefix caching 共用一条逻辑。

### 2.5 各种 proposer 的原理

`method` 的合法取值见 `vllm/config/speculative.py:72` 的 `SpeculativeMethod`：`ngram / medusa / mlp_speculator / draft_model / suffix / eagle / …`。

### (a) n-gram —— 零额外模型，靠”抄”

原理：在**当前上下文（prompt + 已生成）**里找一段和”最近刚生成的后缀”匹配的历史，把历史里那段后面的 k 个 token 直接抄过来当草稿。没有任何额外神经网络，纯字符串匹配。

核心匹配算法在 `vllm/v1/spec_decode/ngram_proposer.py` 的 `_find_longest_matched_ngram_and_propose_tokens()`——它用了类似 KMP 的 LPS 数组找”最长的、既是后缀又在前面出现过的 n-gram”，找到就取其后 k 个 token。用 numba JIT 编译成机器码跑，几乎零开销。

配置：`prompt_lookup_min` / `prompt_lookup_max`（匹配的 n-gram 长度范围），见 `speculative.py:458-461`。

**适用场景**：输出里有**大量字面重复**——代码补全（大段代码复制/改名）、RAG 摘要（答案大量引用原文）、结构化输出（JSON 字段名反复出现）、多轮对话里复述。这些场景 n-gram 接受率能很高且**零成本**，是投机解码里性价比最高的一档。重复少的自由生成（如开放问答）几乎没收益。

### (b) draft model —— 小模型猜大模型

原理：跑一个**同族的小模型**（如 7B 配 1B）当投机器。小模型便宜、方向大致对，猜出 k 个草稿交大模型验证。见 `vllm/v1/spec_decode/draft_model.py` 的 `DraftModelProposer`。

它有个硬约束值得记：`_raise_if_draft_tp_mismatch()` 要求**草稿模型和目标模型的 TP（张量并行）size 必须相同**（`draft_model.py`），否则 torch.compile 缓存会串。另外若两个模型词表不同，会用 `VocabMapping` 把 token id 映射到交集，保证拒绝采样仍然无损。

**适用场景**：通用生成、没有明显重复模式的场景。代价是要**额外加载一个模型**、额外占显存，且小模型自己也要跑前向（不是零成本）。

### © EAGLE —— 复用大模型的隐状态做轻量预测头

原理：不用独立的小模型，而是训练一个**极轻的预测头**，直接吃大模型自己的**隐状态（hidden states，最后一层的中间表示）**来预测下几个 token。因为复用了大模型已经算出的隐状态，投机成本比 draft model 小得多，接受率通常还更高。

vLLM 里 `EagleProposer` 只是薄薄一层，真正逻辑在共享基类 `SpecDecodeBaseProposer`，关键是构造时 `pass_hidden_states_to_model=True`，见 `vllm/v1/spec_decode/eagle.py`：

```python
class EagleProposer(SpecDecodeBaseProposer):
    def __init__(self, vllm_config, device, runner=None):
        super().__init__(vllm_config, device,
                         pass_hidden_states_to_model=True,   # 关键：把大模型隐状态喂给预测头
                         runner=runner)
```

**适用场景**：目前性价比很高的一档，通用场景接受长度往往优于 draft model，额外显存也更小。代价是需要**为你的目标模型专门训练/找到匹配的 EAGLE 头**。

### (d) Medusa —— 多头并行一次猜 k 个

原理：在大模型顶上挂**多个预测头**，第 i 个头专门预测”往后第 i 个 token”，一次前向**并行**吐出 k 个草稿。见 `vllm/v1/spec_decode/medusa.py` 的 `MedusaProposer.propose()`：

```python
blocks = self.model(target_hidden_states)          # 吃大模型隐状态
logits = self.model.compute_logits(blocks)         # 每个头一组 logits
# 每个头取 argmax，堆成 [batch, num_heads] 的草稿
draft_tokens = torch.stack([logit.argmax(dim=-1) for logit in logits], dim=1)
```

这段在干什么：`num_heads` 个头各自预测一个位置，一次算完。和 EAGLE 类似都吃隐状态、都很轻，区别是 Medusa 是”多个独立头并行”，EAGLE 是”一个头自回归地往后滚”。

**适用场景**：同 EAGLE，需要专门训练头。多头并行结构简单，但位置越靠后的头越不准。

### (e) suffix decoding —— 给”重复”配一棵后缀树

原理：n-gram 的加强版。为每个请求维护一棵**后缀树（suffix tree）**缓存历史输出，能匹配更灵活、更长的重复模式，并**动态决定每步猜几个**（不是固定 k）。见 `vllm/v1/spec_decode/suffix_decoding.py` 的 `SuffixDecodingProposer`（底层用 Arctic Inference 的实现）。注意它的 `propose()` 返回的每个请求草稿**长度可以不同**：

```python
# Suffix Decoding will speculate a dynamic number of tokens for each request
draft = self.suffix_cache.speculate(req_id, pattern, max_spec_tokens=..., ...)
draft_token_ids.append(draft.token_ids)   # 每个请求长度可不同
```

**适用场景**：重复模式比朴素 n-gram 更复杂的高重复负载（agent 工具调用循环、长文档反复引用），同样零神经网络成本。

### 3. 关键设计取舍

### 3.1 接受率低时**反而更慢**

这是投机解码最大的坑。每一轮无论接受几个，大模型那次前向的成本是**跑不掉的**（而且验证 k 个 token 的前向比只算 1 个略贵一点点）；投机器的 propose 也有成本（draft model / EAGLE / Medusa 都要额外前向）。如果接受率很低：

```text
一轮成本 = 大模型验证前向(略贵) + 投机器 propose 开销
一轮产出 = a+1 个 token，而 a 接近 0
→ 加速比 < 1，即比不投机还慢
```

**白算**：猜了 k 个、验证了 k 个，结果一个没中，那 k 个草稿的算力全浪费，还搭上了投机器的开销。所以投机解码不是”稳赚”，是**押注接受率**。

### 3.2 显存额外占用

两笔账：

1. **投机器本身**：draft model 是一整个小模型（几个 GB），EAGLE/Medusa 头小一些但也占显存。只有 n-gram/suffix 零显存。
2. **为草稿 token 预留的 KV slot**：即 2.4 里的 `draft_slots`，从每步 token 预算里被扣掉（`scheduler.py:663`）。这意味着**同样的显存，能同时跑的请求（并发）会略少**——投机解码是拿并发换单请求延迟。

### 3.3 batch 大时收益下降

回到 1.1 的地基：投机的免费空间来自”decode 是 memory-bound，算力闲着”。但这个前提在**大 batch 时不成立**：

> **大 batch 摊薄带宽**：continuous batching 把很多请求的 decode 拼进同一步，权重只读一次却服务了整批。batch 越大，”读一次权重”的固定成本被越多 token 分摊，GPU 从 memory-bound **逐渐转向 compute-bound**（算力开始吃紧）。

一旦转成 compute-bound，投机解码”多验证 k 个 token”就不再免费了——那 k 个 token 要占用本已紧张的算力，把 batch 里其他请求的 decode 挤慢。所以：

- **低并发 / 单请求延迟敏感**（如本地对话、代码补全）：投机解码收益最大。
- **高并发 / 吞吐优先**：投机解码收益递减甚至变负，因为算力已经被 batch 填满了。

vLLM 为此提供了**按 batch size 动态调 k** 的机制 `num_speculative_tokens_per_batch_size`（`speculative.py:479`，调度器在 `scheduler.py:274` 读取）：batch 小就多猜，batch 大就少猜甚至不猜。

### 3.4 与 chunked prefill / prefix caching 的交互

- **chunked prefill**：如 2.4 所说，投机的草稿 token 和 chunked prefill 共用调度器同一套 `num_computed_tokens` 预算。多模块 MTP 类投机器在**分块 prefill 边界**会多读 `num_prefill_lookahead` 个 token 当草稿输入，调度器有专门的 `_reserve_prefill_lookahead()`（`scheduler.py:544-559`）处理这个边界，避免污染尾部模块的 KV。
- **prefix caching**：投机器（尤其 n-gram/suffix）本质也在利用”上下文里的重复”，和 prefix caching 是互补的两种”省重复”的手段——一个省 prefill 的重复计算，一个省 decode 的串行步数。

### 4. 给推理优化的启示

### 4.1 什么负载该开投机解码

按”接受率高不高”和”并发高不高”两个轴判断：

| 负载特征 | 建议 |
| --- | --- |
| 输出高度重复（代码补全、RAG 摘要、结构化输出、agent 循环） | 优先 n-gram / suffix，零显存零成本，先试它 |
| 通用生成、有匹配的 EAGLE/Medusa 头 | 上 EAGLE（一般优于 Medusa 和 draft model） |
| 通用生成、只有同族小模型 | draft model，但注意额外显存 + TP size 必须匹配 |
| 高并发吞吐优先的线上服务 | 谨慎——大 batch 下可能负收益，务必压测（见 4.3） |
| 开放式自由生成、低重复、已高并发 | 大概率不开或只在小 batch 时开 |

### 4.2 怎么选 k 和 proposer

- **proposer**：先按 4.1 的表选。能用 n-gram 解决就别上模型型投机器——省显存、零训练、零 propose 开销。
- **k（`num_speculative_tokens`）**：不是越大越好。k 越大，靠后位置的草稿越不准、白算越多。**从小开始**（如 k=3~5），看接受长度曲线再调。若是线上多并发服务，直接用 `num_speculative_tokens_per_batch_size` 让 k 随 batch 自适应：小 batch 多猜、大 batch 收手。

### 4.3 上线前必须测的两条曲线

投机解码是”押接受率”的赌博，**不测就上线等于蒙眼下注**。两条曲线缺一不可：

1. **不同并发下的接受率 / 平均接受长度曲线**。横轴并发（batch size），纵轴平均接受长度。这条曲线告诉你”猜得准不准”以及”大 batch 下接受长度是否还够本”。
2. **不同并发下的端到端收益曲线**。横轴并发，纵轴 = 开投机的 P50/P99 延迟与吞吐 vs 关投机的对比。**接受率高不代表端到端一定快**——大 batch 转成 compute-bound 后，接受长度即使还行，端到端也可能变慢。这条曲线才是最终裁决，用来定”在多大并发以上关闭投机 / 缩小 k”的阈值。

两条一起看：第一条解释”为什么”，第二条决定”开不开、开多大 k”。只看接受率不看端到端，是投机解码最常见的翻车方式。

### 4.4 怎么观测：真实指标名

vLLM 通过 Prometheus 暴露三个 counter，定义在 `vllm/v1/spec_decode/metrics.py` 的 `SpecDecodingProm`：

| 指标名 | 含义 |
| --- | --- |
| vllm:spec_decode_num_drafts | 发起了多少轮草稿（= 多少次 propose） |
| vllm:spec_decode_num_draft_tokens | 一共猜了多少个草稿 token |
| vllm:spec_decode_num_accepted_tokens | 一共接受了多少个草稿 token |
| vllm:spec_decode_num_accepted_tokens_per_pos | 按草稿位置（第 1/2/3…个）分别的接受数——看”靠后位置掉得多快” |

`metrics.py` 的类文档（`metrics.py:180+` 附近）直接给了 PromQL：

```text
# 接受率（草稿命中率）
rate(vllm:spec_decode_num_accepted_tokens_total[$interval])
  / rate(vllm:spec_decode_num_draft_tokens_total[$interval])

# 平均接受长度（含 bonus token）——这就是你的加速上限估计
1 + ( rate(vllm:spec_decode_num_accepted_tokens_total[$interval])
      / rate(vllm:spec_decode_num_drafts_total[$interval]) )

# 逐位置接受率（看第几个位置开始猜不准）
vllm:spec_decode_num_accepted_tokens_per_pos_total[$interval]
  / rate(vllm:spec_decode_num_drafts_total[$interval])
```

日志侧（`SpecDecodingLogging.log()`，`metrics.py:82-114`）会定期打印 `Mean acceptance length` / `Avg Draft acceptance rate` / `Per-position acceptance rate`，压测时直接看日志最快。

**判据**：平均接受长度 ≤ 1.x 且并发不低时，投机解码很可能在拖后腿——要么调小 k，要么换 proposer，要么在高并发下直接关。逐位置接受率若从第 2、3 位断崖式下跌，说明 k 设大了，靠后的草稿纯属白算。

### 5. 小结

- decode 是 memory-bound，一次前向验证 k 个草稿 ≈ 一次前向出 1 个 token 的成本——这块闲置算力就是投机解码的免费空间，**加速上限 ≈ 平均接受长度（含 bonus token）**。
- 两阶段：**propose**（便宜地猜 k 个草稿）+ **verify**（大模型一次前向并行验证）。接受规则逐位置比对，第一个不接受处截断。
- **拒绝采样**（`RejectionSampler`）保证无损：q>p 处按比例砍、p>q 处用 recovered 补，边际分布恰好回到目标 p；greedy 下退化成”草稿等于 argmax 就接受”。
- proposer 谱系：n-gram/suffix（零模型、靠字面重复，代码/RAG 最香）→ draft model（小模型，占显存、TP 要匹配）→ EAGLE/Medusa（吃大模型隐状态的轻量头，性价比高但需训练头）。
- 三大代价：**接受率低反而更慢**、**额外显存（模型头 + 草稿 KV slot）**、**大 batch 收益递减**（算力被 batch 填满，免费空间消失）。上线前必测**接受率曲线**和**端到端收益曲线**两条。

投机解码是”用并发/显存换单请求延迟”的手段，不是万能加速开关。选型和调参见第 16 篇 `16-可观测性.md`（怎么从 `/metrics` 判断 GPU 到底满没满）和第 17 篇 `17-性能调优方法论.md`（把它放进一套完整的定位流程）。

### 术语回顾

| 术语 | 一句话 |
| --- | --- |
| speculative decoding（投机解码） | 先用便宜办法猜 k 个草稿 token，大模型一次前向并行验证，摊薄 decode 的串行代价 |
| proposer / drafter（投机器） | 猜草稿的组件：n-gram / draft model / EAGLE / Medusa / suffix 等 |
| draft token（草稿 token） | 投机器猜的候选 token，不一定对，由大模型验证 |
| propose / verify（提议 / 验证） | 投机解码两阶段：先猜后验；验证靠大模型一次前向并行完成 |
| memory-bound（访存受限） | decode 每步耗时主要花在把权重从 HBM 读一遍，算力空闲——投机的免费空间来源 |
| rejection sampling（拒绝采样） | 按草稿分布 q 与目标分布 p 的关系接受/恢复 token，保证输出边际分布仍是 p，无损 |
| accepted / recovered / bonus token | 拒绝采样的三类输出：接受的草稿 / 拒绝后从修正分布重采的 / 全接受时末尾补的 |
| mean acceptance length（平均接受长度） | 1 + 接受草稿数/草稿轮数，含 bonus token，约等于加速比上限 |
| n-gram / prompt lookup | 从上下文里找重复后缀、抄其后 k 个 token 当草稿的零模型投机器 |
| EAGLE / Medusa | 吃大模型隐状态的轻量预测头投机器（EAGLE 自回归滚、Medusa 多头并行） |
| suffix decoding | 用后缀树匹配复杂重复模式、每步动态决定草稿长度的零模型投机器 |
| draft slot | 调度器为下一轮草稿 token 预留的 KV Cache 位置，从每步 token 预算中扣除 |
