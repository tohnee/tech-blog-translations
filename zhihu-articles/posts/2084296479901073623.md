## 两次通信，竟然比一次更快？拆开 AllReduce，看懂大模型并行的一个关键优化

优化多卡训练或推理时，我们经常盯着一件事：能不能少做一次通信？

但有一种常见优化，看起来恰好反着来。它把原来的：

```text
AllReduce → 计算
```

改成：

```text
ReduceScatter → 计算 → AllGather
```

一次通信变成两次，为什么还可能更快？是不是省下的计算，恰好抵消了翻倍的通信？

先给出两个判断：**通信调用变成两次，不意味着通信字节数翻倍；这项优化是否划算，要看中间的计算能否利用分片，以及拆开以后整条路径的实际成本。**

这里的“可能更快”有明确条件。没有硬件、输入规模和实现方式，就不能承诺加速比例。下面从两张卡的例子开始，一直看到 NCCL 的实际代码。

先看三种操作各自留下什么结果。文中按一张 GPU 对应一个 rank，也就是一个通信参与者来说明。假设两张 GPU 上分别有四个数，归约操作为求和：

```text
GPU 0 输入：[ 1,  2,  3,  4]
GPU 1 输入：[10, 20, 30, 40]
```

AllReduce 完成后，每张卡都拿到完整的和：

```text
GPU 0 输出：[11, 22, 33, 44]
GPU 1 输出：[11, 22, 33, 44]
```

ReduceScatter 则只让每张卡保留一段，但这一段已经完成跨卡归约：

```text
GPU 0 输出：[11, 22]
GPU 1 输出：[33, 44]
```

再对这些结果做一次 AllGather，两张卡就都会得到 `[11, 22, 33, 44]`。

这说明，在相同归约操作、分片顺序和数据规模下，ReduceScatter 后接 AllGather，与 AllReduce 的数学结果等价。NCCL 官方文档也明确给出了这个关系。[NCCL collective 语义](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/usage/collectives.html)

这里尤其容易误解的是 ReduceScatter 的输出。**它持有的是“部分位置的完整数值”，每个位置都已经包含所有 rank 的贡献。** 因此，这些位置后面的很多计算可以立即开始，无须先把其他位置也收集过来。浮点归约顺序可能随算法改变，所以数学等价并不自动保证逐 bit 相同。

再算通信量。设有 `P` 张卡，归约前每卡的完整 Tensor 大小为 `N` 字节。先限定为均匀分片的 Ring 算法，只统计每卡发送的有效载荷，忽略协议标记、控制消息和尾块对齐。

Ring ReduceScatter 中，每张卡经过 `P−1` 步，每步发送约 `N/P` 字节；Ring AllGather 同样如此。因此：

| 操作 | 每卡发送的有效数据量 |
| --- | --- |
| ReduceScatter | (P−1)/P × N |
| AllGather | (P−1)/P × N |
| ReduceScatter + AllGather | 2(P−1)/P × N |
| Ring AllReduce | 2(P−1)/P × N |

例如，8 张卡，每卡归约前的完整 Tensor 为 64 MiB：ReduceScatter 每卡发送 56 MiB，AllGather 再发送 56 MiB，合计 112 MiB；Ring AllReduce 也是 112 MiB。

每卡接收量另有同样一份。如果统计“发送加接收”，两边都要乘二，不能拿一边的双向流量与另一边的单向流量比较。NCCL tests 的带宽说明使用了对应的通信量换算系数。[NCCL tests 带宽定义](https://github.com/NVIDIA/nccl-tests/blob/master/doc/PERFORMANCE.md)

到这里，我们还没有得到性能优化。**只把 AllReduce 拆成两个紧挨着的调用，在相同算法、协议且分别启动 kernel 的常见路径下，通常还会导致性能退化。**

原因是，原本可以在同一个 kernel 内融合、连续推进的两个通信阶段，被拆成了两次独立执行。ReduceScatter 必须先把局部分片物化到显存，再由 AllGather 读取，失去了在阶段交界处直接传递数据的机会；非原地调用还可能增加数据复制。同时，一次通信 kernel launch 变成两次，也增加了启动、调度和执行依赖的开销。**通信有效字节数相同，并不代表执行成本相同。**

真正的优化机会出现在：**两次通信之间，可以放入一段只需要本地分片的计算。** 分片计算省下的时间，需要覆盖上述拆分成本，整条路径才会更快。

考虑一个 `[T,H]` 的激活 Tensor。`T` 是 token 数，`H` 是 hidden width，使用 `P` 张卡，并假设 `T` 能被 `P` 整除。每张卡先得到这整个 Tensor 的一份部分和；接下来需要执行相同参数的逐 token 计算 `f`，例如 RMSNorm（均方根归一化）。

原来的路径是：

```text
每卡部分和 [T,H]
    ↓ AllReduce
每卡完整结果 [T,H]
    ↓ 每张卡都执行 f
每张卡都算完全部 T 个 token
```

改成按 token 分片以后：

```text
每卡部分和 [T,H]
    ↓ ReduceScatter
每卡数值完整的 token 分片 [T/P,H]
    ↓ 每张卡只对自己的 token 执行 f
每卡计算结果 [T/P,H]
    ↓ AllGather
每卡完整的 f 结果 [T,H]
```

AllGather 收集的内容已经变了：它收集的是 `f` 的输出。

用 4 张卡、8 个 token 来看，区别尤其直观：

```text
AllReduce → f：
GPU 0、1、2、3 都计算 token 0～7 的 f。

ReduceScatter → f → AllGather：
GPU 0 计算 token 0、1 的 f。
GPU 1 计算 token 2、3 的 f。
GPU 2 计算 token 4、5 的 f。
GPU 3 计算 token 6、7 的 f。
```

前一种方案，全系统执行了 32 次 token 级 `f`；后一种只执行 8 次。这里统计的是 token 的处理次数，实际可以由 kernel 批量完成，不代表启动了 32 次或 8 次 kernel。每卡的输入规模从 `[8,H]` 降到了 `[2,H]`。

所以，这里同时减少了每卡工作量和跨卡重复计算。对于需要保存逐 token 中间状态的计算，还可能让这一段状态从每卡 `[T,...]` 变成 `[T/P,...]`。这不代表模型总显存也会降到原来的 `1/P`：权重、缓存、完整输入及其他工作区需要分别计算。

这种交换顺序有一个关键条件。假设完整结果由各卡分片拼接而成，那么 `f` 必须满足：

```text
f(concat(x0, x1, ...)) = concat(f(x0), f(x1), ...)
```

也就是，**每一片的结果可以独立算出来**。如果 `f` 还读取参数、残差或历史状态，这些输入也必须在对应 rank 上完整可用。

这并不要求 `f` 是线性函数。按 token 切分时，每张卡仍然拥有每个本地 token 的完整 hidden 向量，因此 RMSNorm、LayerNorm 这样的非线性操作也能独立执行。

但这与“在归约之前先算 `f`”完全不同：我们始终先完成求和，再计算 `f`。不能把它误写成 `f(x0+x1)=f(x0)+f(x1)`，后一个等式对一般非线性函数并不成立。

切分维度也不能忽略。如果把每个 token 的 hidden 维切开，RMSNorm 所需的均方统计量就不完整了，必须先解决跨分片统计的问题。自注意力等跨 token 操作同样不能直接套用上述局部计算：跨分片的依赖仍需要由相应并行算法满足。

还要警惕另一种误判：**多张卡处理相同 token，不代表它们在重复计算。** 张量并行的矩阵乘法中，各卡使用不同的权重分片，产出的贡献各不相同。这类计算不能仅凭输入 shape 都是 `[T,H]`，就认为可以删掉其中大部分工作。

上述变换在大模型中已经有成熟应用。Megatron 的 Sequence Parallelism 将可按序列维独立执行的操作放在分片区域，在进入需要完整输入的张量并行区域前再 Gather。相关论文用这个布局减少复制的激活存储，并分析了 Ring 通信量的等价关系。这里的通信量结论，不应进一步理解成任何设备上都没有额外延迟。[Sequence Parallelism 原论文，第 4.2.2 节](https://arxiv.org/html/2205.05198v1#S4.SS2.SSS2)

不过，**“Ring 的数据量一样”，并没有回答 NCCL 为什么可能跑出不同耗时。** 需要继续看实现。

NCCL 的 Ring AllReduce 在同一个设备执行流程里完成归约和结果传播。在两阶段交界处，源码使用了下面的操作：

```cpp
prims.directRecvReduceCopyDirectSend(offset, offset, nelem, /*postOp=*/true);

```

它接收数据、完成归约、写出结果，同时向下一张卡发送，直接衔接结果传播。这里没有先结束一个独立的 ReduceScatter 调用，再由外部启动 AllGather。[NCCL Ring AllReduce 源码](https://github.com/NVIDIA/nccl/blob/12df1a11afad322be5a204a2db890161cbf8131d/src/device/all_reduce.h)

显式拆开后，设备操作边界可以概括为：

```text
ReduceScatter：
    recvReduceCopy(...)         写出本地归约结果

外部计算 f

AllGather：
    directSend / directCopySend 开始传播计算结果
```

这分别对应独立的 ReduceScatter 和 AllGather 实现。分片结果需要先交给外部计算，再由后续 collective 使用。[ReduceScatter 源码](https://github.com/NVIDIA/nccl/blob/12df1a11afad322be5a204a2db890161cbf8131d/src/device/reduce_scatter.h)、[AllGather 源码](https://github.com/NVIDIA/nccl/blob/12df1a11afad322be5a204a2db890161cbf8131d/src/device/all_gather.h)

这也对应了前面提到的拆分成本：两个阶段无法继续沿用 AllReduce 内部的融合衔接，需要通过显存中的分片结果连接独立的 kernel，还多了一次通信 kernel 的启动与调度。AllReduce 本身也会写出结果，不能把它理解为完全没有显存写入；需要比较的是拆开后增加的中间读取、可能的数据复制，以及执行边界开销。

而且，NCCL 默认并不保证这三个操作都使用 Ring。它支持 Tree、NVLS 等多种算法，并允许不同 collective 使用不同算法和协议；自动选择与拓扑、硬件架构有关。因此，不能把 Ring 的载荷公式直接当成任意 NCCL 配置下物理链路流量完全一致的保证。[NCCL 算法与协议说明](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/env.html#nccl-algo)

现在可以回答最实际的问题：到底什么时候值得拆？

先暂时忽略通信与计算重叠，比较串行路径：

```text
方案 A = AllReduce 耗时 + f(T) 耗时

方案 B = ReduceScatter 耗时 + f(T/P) 耗时 + AllGather 耗时
```

方案 B 更快的条件是：

```text
f(T) − f(T/P) > ReduceScatter + AllGather − AllReduce
```

左边是分片以后真正省下的计算时间，右边是把通信拆开以后真正增加的通信时间。右边可能为正，也可能受算法、调度等因素影响，不能先验地固定成一个常数。

特别注意，`f(T/P)` 不等于 `f(T)/P`。GPU 执行有固定开销，较小的输入也可能无法充分利用设备。工作量降到四分之一，耗时未必也降到四分之一。

下面只是用于理解取舍的假设数字，单位为微秒，不是任何硬件的实测结果：

| 假设场景 | AllReduce → f | ReduceScatter → f → AllGather | 结果 |
| --- | --- | --- | --- |
| 全量计算较重 | 20 + 40 = 60 | 12 + 12 + 12 = 36 | 分片计算节省的时间覆盖了通信额外成本 |
| 原本计算很轻 | 8 + 2 = 10 | 6 + 1 + 6 = 13 | 省下的计算不足以覆盖额外成本 |

这也解释了为什么同一项改动，在较大 batch 上可能有收益，在小 batch decode 上却可能退化。输入规模变了，计算效率和通信启动成本的相对占比也会变化。

实际执行如果存在重叠，就不能简单相加各算子的耗时，要看整段操作的关键路径。另一方面，显存也可能是独立收益：即使某段延迟没有下降，更少的中间状态仍可能让更大的 batch 成为可能。应分别报告固定负载下的延迟，以及扩大负载后的吞吐，避免把它们混成同一种加速。

还有一个容易遗漏的前提：后面的消费者是否真的需要完整 Tensor？如果接下来很长一段都能消费分片数据，AllGather 可以继续后移；如果最终消费者也接受分片结果，甚至可能不需要 Gather。通信应该放在消费者要求改变数据布局的位置。

同样，如果 `f` 改变了输出维度或 dtype，后面 AllGather 的字节数也会变化。此时需要分别定义归约前完整数据量 `N_in` 和 Gather 后完整数据量 `N_out`。在同样的 Ring 假设下，每卡发送量变为：

```text
(P−1)/P × N_in + (P−1)/P × N_out
```

只有 `N_in = N_out` 时，才回到前面的相等关系。量化、压缩或维度扩展都要按实际数据及必要元数据重新计算，不能只数 collective 名称。

真正做性能实验时，应直接对照两条完整路径，并先确认最终输出和布局一致。仅比较一个 AllReduce 与两个 collective 的微基准，无法说明插入计算后的模型收益。

测试数据规模也要对齐。假设归约前完整 Tensor 有 `M` 个元素，均分到 `P` 张卡，NCCL API 的参数对应关系是：

| API | 与这个问题对应的元素数量 |
| --- | --- |
| ncclAllReduce | count = M |
| ncclReduceScatter | recvcount = M/P，每卡输入仍有 M 个元素 |
| ncclAllGather | sendcount = M/P，每卡输出有 M 个元素 |

三个 API 都机械地填写 `M`，测到的就不是相同数据规模了。[NCCL collective API 定义](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/api/colls.html)

一次有解释力的对照，至少要固定 GPU 与互联拓扑、rank 数、dtype、归约操作、输入 shape、内存布局和 NCCL 版本。既要检查浮点误差与 rank 顺序，也要分别观察通信耗时、计算耗时、整段延迟和中间状态显存。小消息与大消息应分开看；在相同算法和协议下解释机制，再回到默认自动选择验证实际部署表现。

如果是训练，还要覆盖反向传播和参数梯度同步；如果中间有随机操作，还要保证分片后的随机数语义符合预期。前向的局部等价关系并不自动完成整个训练图的验证。

下一次看到 `ReduceScatter → f → AllGather`，可以先沿着数据流检查：归约是否已经完成，`f` 需要哪些位置的数据，这些数据和参数是否都在本地，下一次必须恢复完整布局的位置在哪里。把这些条件确认清楚，再用完整路径的测量结果判断是否值得拆，才不会被“一次通信”和“两次通信”的表象带偏。
