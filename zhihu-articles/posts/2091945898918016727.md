> **一句话**：vLLM v1 把”接 HTTP / tokenize”和”调度 + 跑模型”拆成两类进程，用 ZMQ 消息队列连起来，目的只有一个——别让 Python 的 GIL 把 GPU 调度循环拖慢。<br> **前置**：建议先读 `00-序章与代码地图.md`（进程全景）、`04-一个请求的一生.md`（请求怎么流动）。 **代码基线**：vLLM v0.30.0

### 0. 这篇要回答的问题

- 为什么一个 vLLM 服务起来后 `ps` 能看到好几个进程？各自干什么？
- HTTP 前端和引擎为什么必须拆进程，而不是拆线程？（答案是 GIL）
- 这些进程之间怎么通信？为什么选 ZMQ 而不是 gRPC / HTTP？
- 一张几百 MB 的多模态图片张量，从前端传到引擎，怎么做到”不拷贝”？

- 生产里 engine 进程 CPU 打满、前端排队，是什么信号？`--api-server-count` 调它有没有用？

### 1. 先建立直觉

### 1.1 一个进程装不下这套活

先认清一次推理服务同时要干的三类活：

1. **HTTP / 协议层**：收 OpenAI 格式的请求、套 chat template、SSE 流式往回吐。这是纯 CPU 的 Python 工作。
2. **tokenize / detokenize**：文本 ↔ token id 的互转。也是纯 CPU 的 Python 工作，而且 decode 阶段**每生成一个 token 就要 detokenize 一次**，非常高频。
3. **调度 + GPU 前向**：决定这一步谁进 batch、分多少 block，然后把活推给 GPU。调度是 CPU 工作，前向在 GPU 上。

问题出在 Python 的一个基本事实：

> **GIL（Global Interpreter Lock，全局解释器锁）**：CPython 里同一时刻只有一个线程能执行 Python 字节码。所以一个进程内的多个 Python 线程**不能真正并行跑 CPU 工作**——它们轮流持有 GIL。只有当某个线程陷入 C 扩展或 IO 等待并主动释放 GIL 时，别的线程才动得了。

如果把上面三类活塞进一个进程用多线程做，会发生什么？tokenize、HTTP 解析这些”纯 Python CPU”活会和调度循环**抢同一把 GIL**。GPU 前向本身在 C++/CUDA 里、会释放 GIL，但**调度决策（`schedule()`）是 Python**——它一旦被 tokenize 线程抢了 GIL，GPU 就得干等着下一批活。对一个每秒要转几十上百圈的 step 循环来说,这是致命的。

后端工程师的类比：这就像**把 Nginx 和你的业务 worker 塞进同一个单线程事件循环**,一个慢请求的 JSON 解析就能卡住整个 accept 循环。正确做法是拆开:Nginx 一层、worker 一层,各跑各的。

### 1.2 vLLM 的答案：拆进程，不拆线程

进程之间**没有共享的 GIL**——每个进程有自己的解释器、自己的 GIL。所以 vLLM 把活拆成两类进程：

```text
┌─────────────────────────┐         ┌──────────────────────────┐
│  API server 进程（前端）  │  ZMQ    │   EngineCore 进程（引擎）  │
│  - FastAPI / HTTP       │ ──────> │   - Scheduler.schedule() │
│  - tokenize / detokenize│ <────── │   - 忙循环 step()         │
│  - OpenAI 协议 / SSE     │         │   - 驱动 GPU 执行器       │
│  纯 CPU Python，独占一把GIL│        │  调度是 CPU、前向在 GPU    │
└─────────────────────────┘         └──────────────────────────┘
```

前端进程里 tokenize 再忙，也只是抢它自己那把 GIL，碰不到引擎进程的调度循环。引擎进程一心一意转它的 step 循环。这就是 vLLM v1 架构最基础的一刀。

把 DP、TP 都算上，一个”DP=2、每个引擎 TP=2”的完整拓扑长这样（标出了每条边用什么通道）：

![](https://pic3.zhimg.com/v2-53f5a7574877bf3d3f15f5b1923750ce_r.jpg)

三种通道一眼可辨：**实线 ZMQ** 连前端↔引擎↔coordinator（跨进程、可跨机），**实线共享内存 MessageQueue** 连引擎↔它自己的 TP worker（同机一写多读广播），**虚线 NCCL** 是同一引擎内 TP worker 之间的卡间通信（不经过引擎进程）。多模态巨型张量走的是另一条共享内存队列（图中虚线）。

代码里这两类进程的实体：

- 前端侧的引擎客户端在 `vllm/v1/engine/core_client.py`（`SyncMPClient` / `AsyncMPClient`）。
- 引擎侧的进程封装是 `EngineCoreProc`。

> **IPC（Inter-Process Communication，进程间通信）**：进程各有独立内存，要交换数据就得走 IPC——socket、管道、共享内存、消息队列都算。vLLM 用了三种，分别对付三种量级的数据（下面 3.1 节展开）。

### 1.3 为什么是 ZMQ

> **ZMQ（ZeroMQ）**：一个消息队列库,把 socket 编程封装成”发消息 / 收消息”。它支持多种传输：`inproc`（进程内)、`ipc`（同机 Unix domain socket）、`tcp`（跨机）。同一套 API,换个地址前缀就换了传输层。

vLLM 选 ZMQ 而不是 gRPC / HTTP，是因为它要的是**低延迟、点对点、单机为主**的消息通道，不需要 gRPC 那套服务发现、负载均衡、HTTP/2 语义。而且 ZMQ 的 `ipc://`（同机）比走 `tcp://` 回环还省一层协议栈。vLLM 里的 socket 都通过 `make_zmq_socket` 建立，地址在单机部署时用 `ipc://`，跨节点（DP 分布在多机）时用 `tcp://`。

### 2. 源码走读

### 2.1 引擎进程内部：不是单线程，是 1+2 线程

拆进程解决了跨进程抢 GIL，但引擎进程内部还有一个更细的设计：它有**三个角色的线程**，用两个 Python `queue.Queue` 解耦。看 `EngineCoreProc.__init__`：

```python
self.input_queue = queue.Queue[tuple[EngineCoreRequestType, Any]]()
self.output_queue = queue.Queue[tuple[int, EngineCoreOutputs] | bytes]()
...
# Background Threads and Queues for IO. These enable us to
# overlap ZMQ socket IO with GPU since they release the GIL,
# and to overlap some serialization/deserialization with the
# model forward pass.
input_thread = threading.Thread(target=self.process_input_sockets, ..., daemon=True)
input_thread.start()
self.output_thread = threading.Thread(target=self.process_output_sockets, ...)
self.output_thread.start()
```

三个角色：

| 角色 | 干什么 | GIL 影响 |
| --- | --- | --- |
| input 线程 (process_input_sockets) | 从 ZMQ 输入 socket 收字节、反序列化成请求对象、丢进 input_queue | ZMQ 收发和 msgpack 解码大量在 C 里、会释放 GIL |
| 主线程 (run_busy_loop) | 从 input_queue 取活、调度、驱动 GPU、结果丢进 output_queue | 调度是 Python，但此时 input/output 线程多在 IO 等待，不抢它 |
| output 线程 (process_output_sockets) | 从 output_queue 取结果、序列化、经 ZMQ 发回前端 | 同上 |

为什么这么分？注释写得很直白：ZMQ 的 socket IO 和序列化/反序列化都会释放 GIL，把它们挪到独立线程，就能**和 GPU 前向重叠**。主线程在等 GPU 出结果的那段时间（GPU 在 C++/CUDA 里跑、GIL 是放开的），input 线程正好可以解码下一批请求。这是”进程内也要挤出并行”的第二层设计。

注意这里的线程解耦是**安全**的：input/output 线程只碰 ZMQ 和 queue，主线程只碰 scheduler 和 GPU，两条 `queue.Queue` 是它们唯一的交界，`queue.Queue` 本身线程安全。

### 2.2 忙循环：有活才转，没活就睡

主线程的心脏是 `run_busy_loop`：

```python
def run_busy_loop(self):
    """Core busy loop of the EngineCore."""
    while self._handle_shutdown():
        # 1) Poll the input queue until there is work to do.
        self._process_input_queue()
        self._maybe_publish_request_counts()
        # 2) Step the engine core and return the outputs.
        self._process_engine_step()
        self._maybe_publish_request_counts()
    raise SystemExit
```

一圈就是：**先把新请求从 input_queue 收干净 → 跑一个 step → 把输出推进 output_queue**。

关键是”没请求时怎么办”。天真的忙循环会空转把 CPU 打满。vLLM 的做法在 `_process_input_queue`：

```python
while not self.has_work() and self.is_running():
    ...
    block = self.process_input_queue_block
    try:
        req = self.input_queue.get(block=block)   # ← 没活就阻塞在这里
        self._handle_client_request(*req)
    except queue.Empty:
        break
    ...
```

`has_work()` 判断”有没有请求要跑”（scheduler 里有请求 / batch queue 非空 / DP 引擎在运行）。**当没有活时，主线程阻塞在 `input_queue.get(block=True)` 上**——这是一个操作系统级的条件变量等待，不占 CPU。等 input 线程收到新请求塞进 queue，`get()` 立即返回，循环重新转起来。

后端工程师的类比:这就是标准的**阻塞队列 + 工作线程**模型,不是自旋锁。空闲时 CPU 占用应该接近 0。这条对第 4 节的排查很重要:如果一个**没有流量**的 engine 进程 CPU 却打满,那不是正常忙循环,是别的东西在自旋。

（`_process_engine_step` 里还有一处 `time.sleep(0.001)`：当这一步没真正执行模型但 scheduler 还有活（比如在等远程 KV 传输）时,主动让出 GIL 1ms 让后台传输线程推进。这是特例,不是常态。）

### 2.3 前端到引擎的消息流：ROUTER / DEALER / PULL

前端进程（`MPClient`）和引擎进程（`EngineCoreProc`）之间有两条 ZMQ 通道：**输入通道**（前端 → 引擎）和**输出通道**（引擎 → 前端）。socket 类型的选择见 `MPClient.__init__`：

```python
self.input_socket = make_zmq_socket(self.ctx, addresses.inputs[0], zmq.ROUTER, bind=True, ...)
self.resources.output_socket = make_zmq_socket(self.ctx, addresses.outputs[0], zmq.PULL)
```

- **输入**：前端是 `ROUTER`，引擎侧是 `DEALER`（见 `process_input_sockets` 里 `zmq.DEALER`）。`ROUTER`/`DEALER` 是 ZMQ 的一对，`ROUTER` 能按”身份（identity）”把消息发给指定的某一个引擎——这正是 DP 多引擎时前端要”把这个请求路由到第 3 号引擎”所需要的。每个引擎的身份就是它的 `engine_index` 编码成 2 字节。
- **输出**：引擎侧是 `PUSH`（见 `process_output_sockets` 里 `zmq.PUSH`），前端是 `PULL`。多个引擎的输出汇到前端一个 `PULL` socket。

前端发一个请求的代码（同步版 `SyncMPClient._send_input`）：

```python
def _send_input(self, request_type, request):
    # (Identity, RequestType, SerializedRequest)
    msg = (self.core_engine, request_type.value, *self.encoder.encode(request))
    self.input_socket.send_multipart(msg, copy=False)
```

一条消息是**多帧（multipart）**：第一帧是目标引擎身份，第二帧是请求类型，后面是序列化后的请求体（可能不止一帧，见下面零拷贝）。`copy=False` 是零拷贝发送的关键。

引擎侧 input 线程收到后，按类型反序列化、`preprocess_add_request`（这一步里做 tokenize 后的请求初始化、structured output 的 grammar 编译等），然后塞进 `input_queue` 交给主线程。请求类型的分派在 `_handle_client_request`：`ADD`（新请求）、`ABORT`（中止）、`UTILITY`（远程调用引擎的方法，比如 `reset_prefix_cache`）等。

### 2.4 零拷贝：大张量怎么不拷

普通的序列化（比如 JSON、pickle）会把对象的字节**复制**一份进输出缓冲区。对一段几百 KB 的 token id 数组、尤其是多模态那种几十上百 MB 的图像/视频张量，复制的开销就很可观了。

vLLM 的编解码在 `serial_utils.py`，用 `msgpack` 做主体，但对 tensor / numpy 数组做了两级特殊处理。看 `MsgpackEncoder._encode_tensor`：

```python
def _encode_tensor(self, obj):
    oob_consumer = self.oob_tensor_consumer
    if obj.nbytes < self.size_threshold and obj.is_cpu:
        # 小张量：直接内联进 msgpack
        data = msgpack.Ext(CUSTOM_TYPE_RAW_VIEW, tensor_data(obj))
    elif oob_consumer is not None and (data := oob_consumer(obj)) is not None:
        # 有 OOB 通道（多模态张量走共享内存队列）
        ...
    else:
        # 大张量：把它的原始内存视图追加到 aux_buffers，msgpack 里只存一个索引号
        data = len(self.aux_buffers)
        self.aux_buffers.append(tensor_data(obj))
    return dtype, obj.shape, data
```

三条路：

1. **小于阈值**（默认 `VLLM_MSGPACK_ZERO_COPY_THRESHOLD`，见 [第 155 行](https://github.com/vllm-project/vllm/blob/v0.30.0/vllm/v1/serial_utils.py#L155)）的 CPU 张量：内联进 msgpack 主帧，反正小，不值得单独开一帧。
2. **大张量**：msgpack 主帧里**只写一个整数索引**（”我是 aux_buffers 里的第 N 块”），张量的实际内存（`tensor_data(obj)` 返回的是一个 `memoryview`，指向原张量的字节）被 append 到 `aux_buffers`。最后 `encode()` 返回的是一个**帧列表**：`bufs[0]` 是 msgpack 主帧，后面每一帧是一块张量内存的 `memoryview`。ZMQ 用 `send_multipart(..., copy=False)` 直接把这些 memoryview 当作 socket 帧发出去——**从头到尾没有把张量字节复制进任何中间缓冲区**。

接收侧 `MsgpackDecoder._decode_tensor` 按索引从收到的帧列表 `aux_buffers` 里取出对应的那一帧，直接 `frombuffer` 成张量，同样不拷贝。

1. **多模态张量的 OOB（out-of-band）通道**：更进一步，多模态那种巨型张量连 ZMQ 都不走，改走 `torch.multiprocessing.Queue` 的共享内存。实现在 `tensor_ipc.py`，`TensorIpcSender.__call__`：

```python
if not tensor.is_shared():
    tensor = tensor.share_memory_()   # ← 挪进共享内存
...
self.queue.put(ipc_data, timeout=10.0)
```

张量被 `share_memory_()` 放进一块两个进程都能映射的共享内存，队列里只传一个句柄（`sender_id / message_id / tensor_id`）。前端 ZMQ 消息里对应位置存的是这个句柄的 metadata，引擎侧的 `TensorIpcReceiver` 按句柄从共享内存里把张量捞出来。这样一张几十 MB 的图片特征，跨进程传的只是一个几十字节的句柄。

一句话总结这三级：**小的内联、中的走 ZMQ 零拷贝多帧、大的走共享内存传句柄**。

### 2.5 多卡执行：driver worker 与广播

到目前为止说的是”前端 ↔ 引擎”。当 TP>1（张量并行，一个模型切到多张卡）时，引擎进程下面还有一层：**每张卡一个 worker 进程**。

> **TP（Tensor Parallel，张量并行）**：把模型每一层的权重矩阵横着切成 N 份放到 N 张卡上，每张卡算自己那份，再通过卡间通信（all-reduce）合并结果。切法和通信细节见 `13-并行策略.md`。这里只关心进程拓扑。

进程怎么起？执行器类型由 `Executor.get_class` 按 `distributed_executor_backend` 选：`"mp"` → `MultiprocExecutor`（多进程，单机默认），`"ray"` → Ray executor（跨机常用），`"uni"` → 单进程（单卡）。

以单机 `MultiprocExecutor` 为例，它在 `_init_executor` 里为每个 local rank fork 一个 `WorkerProc`（`make_worker_process`）。**注意这些 worker 是引擎进程的子进程，不是前端的**。

引擎主线程要跑一步模型时，走的是 `execute_model → collective_rpc`。广播用的**不是 ZMQ，是共享内存消息队列**。看 `MultiprocExecutor.collective_rpc`：

```python
self.rpc_broadcast_mq.enqueue((send_method, args, kwargs, output_rank))
```

`rpc_broadcast_mq` 是一个 `MessageQueue`（`vllm/distributed/device_communicators/shm_broadcast.py`，基于共享内存的一写多读广播）。引擎把这一步要执行的方法名 + `SchedulerOutput` **enqueue 一次**，所有 worker 各自从这块共享内存里读到同一份。每个 worker 的忙循环 `worker_busy_loop`：

```python
def worker_busy_loop(self):
    while True:
        self._execute_worker_rpc(self.rpc_broadcast_mq.dequeue(indefinite=True))
```

worker 阻塞在 `dequeue(indefinite=True)`（没活就睡，同 2.2 的思路），拿到 RPC 就执行对应方法（`execute_model` / `sample_tokens` 等），把输出 enqueue 到自己的 `worker_response_mq` 送回引擎。

这里有个”谁的输出算数”的细节。TP 里每张卡跑的是模型的一部分，但**采样出的 token 是一样的**（或者只有特定 rank 有完整结果）。所以引擎只收**一个** rank 的输出，由 `_get_output_rank` 算出来——它是”最后一个 PP stage 的第一个 TP worker”。`collective_rpc` 里传 `unique_reply_rank=self.output_rank`，只等那一个 worker 回话。

术语澄清：老 vLLM(V0) 里有明确的”driver worker 在主进程里、其余 worker 是子进程”的说法。v1 的 `MultiprocExecutor` 下**所有 worker 都是独立子进程**,引擎进程本身不持有 GPU;`is_driver_worker`(见 `_is_driver_worker`,`rank % tensor_parallel_size == 0`)只是给每个 TP 组标一个组长,组长承担一些组内协调职责,而不是”跑在主进程里的那个”。这一点和很多老文章说的不一样,别被带偏。

### 2.6 数据并行：多引擎 + coordinator

> **DP（Data Parallel，数据并行）**：起多个**完整的**引擎副本，各自有自己的一套 KV Cache 和 worker，前端把请求分发到不同副本上以提高总吞吐。和 TP 的区别：TP 是”一个模型切到多卡协作跑一个请求”，DP 是”多个独立引擎各跑各的请求”。

DP>1 时进程拓扑多两样东西：

1. **多个 EngineCore 进程**：MoE 模型用 `DPEngineCoreProc`，非 MoE 的 DP 各 rank 完全独立、退化成普通 `EngineCoreProc`（见 `run_engine_core` 的分支）。Ray 部署下则是 `DPMoEEngineCoreActor / EngineCoreActor（同一套逻辑包成 Ray actor）。`
2. `一个 DP coordinator 进程：DPCoordinator。它不碰 GPU，只做两件事：收集每个引擎的队列长度（waiting / running）发布给前端做负载均衡，以及协调 DP 的”请求波（wave）”节奏。coordinator 用 XPUB socket 向引擎广播、PULL socket 收引擎的 stats（见 process_input_socket）。`

`前端怎么决定请求发给哪个引擎？内部负载均衡模式下是 DPLBAsyncMPClient.get_core_engine_for_request。核心打分（第 1571 行）：`

```python
score = max(self.client_count * inflight, waiting + running)
if waiting:
    # KV 越满，对已有排队的惩罚越重
    score += waiting * 6.0 * max(0.0, kv_cache_usage - 0.5)
```

`每个引擎的分 = “这个客户端自己发给它、还没回的请求数（放大 client_count 倍）”和”coordinator 最近一次快照的 waiting+running”取较大值，再叠加一个和 KV Cache 占用率挂钩的排队惩罚（KV 越满、排队越该躲开）。选分最低的引擎。这里能看到一个细节:inflight 是这个客户端本地精确知道的、快照会过期,所以用 max 让本地精确值兜底,避免快照滞后（每 100ms 更新）导致的扎堆。`

> ` 排查分流问题时，这段是唯一的权威——别凭”按副本数轮询”之类的直觉猜。真实公式就在这几行。`

`SchedulerOutput 的广播和 DP 无关：DP 是”多个独立引擎”，每个引擎内部各自有自己的 TP worker 广播（2.5 节那套），互不干扰。`

### `2.7 进程崩溃、健康检查、优雅退出`

`这套多进程拓扑最怕的是”一个进程悄悄死了，其他进程还在傻等”。vLLM 的防护有几层：`

`关闭状态机。引擎进程用一个三态枚举 EngineShutdownState：RUNNING → REQUESTED → SHUTTING_DOWN。收到 SIGTERM / SIGINT 时信号处理器把状态置为 REQUESTED 并唤醒忙循环（往 input_queue 塞一个 WAKEUP 消息，因为主线程可能正阻塞在 get() 上）。_handle_shutdown 根据 shutdown_timeout 决定是立即 abort 所有在飞请求（timeout=0）还是排空（drain）——排空模式下继续跑到请求都完成才退。`

`进程存活监控。前端侧 MPClient.start_engine_core_monitor 起一个后台线程盯着引擎进程；引擎死了就标记 engine_dead=True，后续任何操作抛 EngineDeadError，避免前端无限等一个死引擎的回复。引擎侧 MultiprocExecutor.start_worker_monitor 同理盯着 worker 进程：任一 worker 意外退出，就关掉整个 executor 并触发失败回调。引擎发现自己活不下去时，通过 output socket 发一个特殊的 ENGINE_CORE_DEAD 哨兵消息（定义）通知前端。`

`worker 硬杀兜底。_ensure_worker_termination 是标准的”先礼后兵”：先等它们自己退（grace period），不退发 SIGTERM，还不退发 SIGKILL。另外 worker 进程通过一个”death pipe”感知父进程（引擎）是否还活着，父死了子自己退，避免僵尸进程。`

`check_health（MultiprocExecutor.check_health）就是一个带 10s 超时的 collective_rpc("check_health")——如果哪个 worker 卡死，这个 RPC 会超时，从而暴露问题。`

### `3. 关键设计取舍`

### `3.1 三种 IPC 通道，各管一段`

| 通道 | 传输 | 传什么 | 为什么用它 |
| --- | --- | --- | --- |
| ZMQ（ROUTER/DEALER, PUSH/PULL） | ipc://（同机）/ tcp://（跨机） | 请求 / 输出 / utility RPC | 低延迟、点对点、能按身份路由到指定引擎 |
| 共享内存 MessageQueue（shm_broadcast） | 共享内存 | 引擎 → 各 worker 广播 SchedulerOutput | 一写多读、TP 里同一份数据发给所有卡，广播只写一次 |
| torch shared-memory Queue（tensor IPC） | 共享内存 | 多模态巨型张量 | 张量太大，连零拷贝 ZMQ 都嫌它挤 socket 帧，直接传句柄 |

`为什么不统一成一种？因为三段的数据形态不同：前端↔引擎是跨节点可能存在、点对点、要路由（ZMQ 合适）；引擎↔worker 是同机、一对多、高频（共享内存广播省掉多次拷贝）；多模态张量是偶发的超大块（共享内存传句柄最省）。用一种通道硬扛所有场景，总有一段是浪费。`

### `3.2 拆进程的代价`

`不是没有成本：`

- `序列化开销：跨进程必须序列化。这就是为什么 vLLM 花大力气做零拷贝——把序列化的边际成本压到接近 0，拆进程才划算。`
- `进程管理复杂度：崩溃检测、优雅退出、句柄传递（2.7 节那一大套）全是为拆进程付的税。`
- `多一跳延迟：请求要经过前端→ZMQ→引擎再回来。对单个请求的 TTFT 有微秒~毫秒级的固定加成。但相对于 GPU 前向动辄几十毫秒，这点固定开销可以忽略,换来的是调度循环不被 GIL 拖慢——净赚。`

### `3.3 为什么前端能有多个（api_server_count）`

`单个前端进程的瓶颈同样是 GIL：一个进程里 tokenize/detokenize/HTTP 全挤一把 GIL，QPS 高到一定程度，前端自己会成为瓶颈（GPU 还没满，但前端 CPU 已经打满）。所以 vLLM 允许起多个前端进程，每个都能独立接请求、tokenize，共享后端的引擎。这就是 --api-server-count 的意义（下一节展开）。`

### `4. 给推理优化的启示`

### `4.1 从进程拓扑读症状`

`学会 ps/top 里认这几类进程（进程标题在代码里显式设过，见 set_process_title）：`

- `EngineCore / EngineCore_DP{N}：引擎主进程。`
- `Worker / Worker_TP{N} / Worker_DP{N}_TP{M} …：GPU worker（进程名带并行 rank，见 setup_proc_title_and_log_prefix）。`
- `DPCoordinator：DP 协调器（DP>1 才有）。`
- `前端 API server 进程。`

`对应的排查判据：`

| 症状 | 可能的解释 | 怎么验证 |
| --- | --- | --- |
| 前端进程 CPU 打满，GPU 没满，吞吐上不去 | 前端 GIL 成瓶颈（tokenize/detokenize/HTTP 挤一把锁） | 加 --api-server-count；对比前端 CPU% 和 GPU 利用率 |
| EngineCore 进程 CPU 打满但没流量 | 不正常——正常忙循环空闲时应阻塞在 input_queue.get（2.2 节）；打满可能是某个后台传输在自旋或有 bug | 看 num_requests_waiting 是否真有活；py-spy 抓栈看主线程停在哪 |
| 请求偶发高延迟、engine 队列却不长 | IPC 排队 / 序列化开销（尤其多模态大张量走了非零拷贝的回退路径） | 看日志有没有 Failed to send tensor via IPC queue ... Falling back to standard serialization（tensor_ipc.py）——回退到普通序列化就会拷贝大张量 |
| 多引擎（DP）负载不均 | 负载均衡打分（2.6 节）在特定流量下的行为 | 读 get_core_engine_for_request 的公式，对照 coordinator 发布的 waiting/running 快照 |
| 一个 worker 卡死、整个服务 hang | collective_rpc 在等那个 worker 回复 | VLLM_EXECUTE_MODEL_TIMEOUT_SECONDS 会让它超时暴露；worker monitor 会检测进程死亡 |

### `4.2 --api-server-count 到底怎么用`

`我去 vllm/entrypoints/launchers/cli_args.py:411 和 vllm/entrypoints/cli/serve.py 核实了这个参数（确认参数名就是 --api-server-count）：`

- `它控制起几个前端 API server 进程。多个前端进程共享同一套后端引擎，各自独立 tokenize/接 HTTP，从而突破单前端进程的 GIL 瓶颈。`
- `默认值不是 1：serve.py 里的默认逻辑（第 111-127 行）——内部 LB 模式下默认等于 data_parallel_size，hybrid LB 模式下默认等于 data_parallel_size_local，external LB / 多端口 / Rust 前端 / headless 等情况默认 1。也就是说 DP>1 时它会自动跟着放大。`
- `什么时候手动调大：GPU 没吃满、但前端进程 CPU 打满、QPS 上不去时。典型是短请求、高并发、重 tokenize 的场景。调大它是加前端的并行度,不改引擎和 GPU。`
- `什么时候没用：如果瓶颈在 GPU 前向或引擎调度（GPU 已满），加前端进程只是徒增内存,解决不了问题。先确认瓶颈在前端再动它。`

`判断”瓶颈是不是在前端”的最直接办法：对比前端进程的 CPU% 和 GPU 利用率/iteration_tokens（见 16-可观测性.md）。前端 CPU 顶满而 GPU 有余力,才是它该上场的时候。`

### `4.3 序列化相关的旋钮`

- `VLLM_MSGPACK_ZERO_COPY_THRESHOLD：控制多大的张量走零拷贝多帧（2.4 节）。一般不用动,但知道它存在,能解释”为什么小张量和大张量的传输路径不一样”。`
- `多模态场景：确认 tensor IPC 走的是共享内存队列(mm_tensor_ipc == "torch_shm",见 MPClient.__init__ 附近),而不是回退路径。日志里的 fallback 警告是信号。`

### `5. 小结`

- `vLLM v1 把服务拆成前端 API server 进程和 EngineCore 引擎进程,根本原因是 GIL:tokenize/HTTP 这些纯 Python CPU 活不能和调度循环抢同一把锁。`
- `引擎进程内部还有 1 主线程 + input/output 两条 IO 线程,用两条 queue.Queue 解耦,把 ZMQ IO 和序列化与 GPU 前向重叠。`
- `忙循环有活才转、没活阻塞在 input_queue.get,空闲不占 CPU。`
- `三种 IPC 各管一段:ZMQ(前端↔引擎)、共享内存广播(引擎↔TP worker)、共享内存句柄(多模态大张量)。张量传输三级:小内联 / 中零拷贝多帧 / 大传句柄。`
- `TP>1 时每卡一个 worker 子进程,引擎通过共享内存 MessageQueue 一次广播 SchedulerOutput,只收 output_rank 一个 worker 的结果。v1 里没有”跑在主进程的 driver worker”,所有 worker 都是子进程。`
- `DP>1 时多个独立引擎 + 一个 coordinator 进程;前端按 get_core_engine_for_request 的打分做负载均衡。`
- `崩溃防护:关闭状态机 + 进程存活监控 + ENGINE_CORE_DEAD 哨兵 + worker 硬杀兜底 + death pipe。`
- `生产排查先认进程、看谁的 CPU 满:前端满 → 加 --api-server-count;引擎/GPU 满 → 加前端没用。`

`调度器怎么在 step 里决定谁进 batch,见 07-调度器精读.md;并行策略(TP/PP/DP/EP)切的到底是什么、卡间怎么通信,见 13-并行策略.md。`

### `术语回顾`

| 术语 | 一句话 |
| --- | --- |
| GIL（全局解释器锁） | CPython 同一时刻只有一个线程能跑 Python 字节码;拆进程而非拆线程,就是为绕开它 |
| IPC（进程间通信） | 独立内存的进程之间交换数据的机制:socket / 管道 / 共享内存 / 消息队列 |
| ZMQ（ZeroMQ） | 消息队列库,同一套 API 支持 inproc/ipc/tcp;vLLM 前端↔引擎的通道 |
| ROUTER/DEALER | ZMQ 的一对 socket,ROUTER 能按身份把消息发给指定的某个引擎(DP 路由用) |
| 零拷贝(zero-copy) | 序列化时不复制张量字节,只传内存视图/共享内存句柄,省掉大块内存的拷贝 |
| EngineCore / EngineCoreProc | vLLM 的引擎主循环,EngineCoreProc 是它的多进程 ZMQ 封装 |
| DP coordinator | 数据并行时的协调进程,收集各引擎队列长度做负载均衡、协调请求波节奏 |
| driver worker | 每个 TP 组的组长 worker(rank % tp_size == 0);v1 里它也是子进程,不在主进程里 |
| collective_rpc | 引擎向所有 worker 广播一次要执行的方法(如 execute_model),按 output_rank 收结果 |
| MessageQueue(shm_broadcast) | 基于共享内存的一写多读广播队列,引擎向 TP worker 发 SchedulerOutput 用它 |
| TP(张量并行) | 一个模型切到多卡协作跑一个请求,卡间要通信;详见 13-并行策略.md |
| DP(数据并行) | 多个完整引擎副本各跑各的请求,提高总吞吐 |
