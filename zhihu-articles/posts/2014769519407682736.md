**作者：NVIDIA**

**摘要**

训练混合专家（MoE）模型带来了密集模型所没有的系统性挑战。由于每个 token 只激活一部分专家，这种稀疏性使得总参数的增长速度远超每个 token 的计算量，从而在内存、通信和计算之间产生了紧密耦合的约束。优化其中一者往往会将压力转移给另一者，因此需要在全系统栈上进行协同设计。

我们通过集成优化来应对 MoE 训练的挑战，这些优化涵盖了**内存**（细粒度重计算、卸载等）、**通信**（优化调度器、通信-计算重叠等）和**计算**（Grouped GEMM、算子融合、CUDA Graph等）方面。Megatron Core 框架还提供了用于灵活多维并行的“并行折叠”技术、对 FP8 和 NVFP4 的低精度训练支持，以及高效的长上下文训练。

在 NVIDIA GB300 和 GB200 上，针对 DeepSeek-V3-685B 模型，它实现了每 GPU 1,233/1,048 TFLOPS 的吞吐量；针对 Qwen3-235B 模型，实现了每 GPU 974/919 TFLOPS 的吞吐量。作为一个高性能、可扩展且生产就绪的开源解决方案，它已在学术界和工业界广泛用于训练参数规模从数十亿到数万亿不等的 MoE 模型，集群规模可达数千 GPU。本报告解释了这些技术的工作原理、它们的权衡以及在系统层面的交互，为使用 Megatron Core 扩展 MoE 模型提供了实用指导。

## **1. 引言**

### **1.1 混合专家模型（MoE）**

MoE 模型通过一个路由网络将每个输入 token 动态地分配给一小部分“专家”子网络进行处理。这使得模型的总容量（参数）可以远大于每次计算的实际参数量，从而在增加模型规模的同时，计算成本的增加相对较小。形式化地，给定输入 token 表示 x，路由器计算在 E 个专家上的概率分布： $$ \[ \mathbf{p}(\mathbf{x}) = \mathrm{Softmax}(\mathbf{W}_r\mathbf{x}) \] $$

然后选择 top-k 的专家，输出为加权组合：

$$ \[ \mathrm{MoE}(\mathbf{x}) = \sum_{i\in \mathrm{TopK}(\mathbf{p}(\mathbf{x}))} p_i(\mathbf{x})\cdot E_i(\mathbf{x}) \] $$

这种架构的主要优势包括：模型容量可以独立于计算成本增长（通过增加专家数）、只有部分参数参与计算从而降低 FLOPs、以及不同专家可以对不同类型的输入进行专业化。尽管概念起源于 1990 年代，但与 Transformer 的结合推动了其复兴，如 GShard 引入了专家并行和负载均衡损失，Switch Transformer 展示了扩展到万亿参数的可能性，GLaM 表明 MoE 能以更低的训练成本匹配密集模型的质量。近年来，Mixtral 8x7B、DeepSeek-V2/V3 等模型进一步采用了细粒度专家架构，使用数百个小专家来最大化容量与计算之比。这些趋势放大了系统层面的挑战。

### **1.2 训练大规模 MoE 模型的挑战**

挑战根源于 MoE 的稀疏性，导致了两个核心不匹配问题：

**参数-计算不匹配：** 总参数（随专家数 E 增长）远超激活参数（随激活专家数 K 增长）。例如 DeepSeek-V3，总参数 685B，但每 token 激活仅 37B，差距达 18 倍。这导致需要大量 GPU 来存储参数，但计算量却相对较小，使得通信开销凸显。由此产生三大紧密耦合的“墙壁”：

- **内存墙：** 存储所有专家参数、梯度、优化器状态，导致内存压力巨大。激活内存也因 top-k 复制 token 而增加。
- **通信墙：** 专家并行（EP）所需的 all-to-all 通信量巨大，尤其在跨节点时可能占训练时间的 60%。
- **计算效率墙：** 细粒度专家产生大量小型 GEMM，导致 GPU 利用率低；路由、排列等操作也带来额外开销；负载不均衡导致部分专家过载而其他闲置；大量内核启动造成主机开销。

**密集-稀疏不匹配：** 模型中的注意力层（密集）和 MoE 层（稀疏）对并行策略的最优需求相互冲突。注意力层受益于高张量并行（TP）以处理大矩阵，而 MoE 层若使用高 TP 会破坏其计算效率，更适合专家并行（EP）。传统框架强制所有层使用相同的并行配置，导致无法同时优化两者，且受限于 EP≤DP，使得配置僵化，最低 GPU 要求高，通信可能被迫跨节点。

### **1.3 Megatron-Core MoE**

这是一个基于 PyTorch 的库，通过集成优化方案同时解决上述三大挑战。它提供多维并行（包括 EP 与 TP、PP、CP、DP 的集成），通过“并行折叠”解耦注意力层和 MoE 层的并行配置。在内存方面，实现了细粒度激活重计算、内存高效排列、精度感知优化器、激活卸载和 FSDP 集成。在通信方面，提供高性能 token 调度器（DeepEP、HybridEP）和通信-计算重叠。在计算方面，采用 Grouped GEMM、内核融合、CUDA Graph和同步自由执行。此外，还包括负载均衡、token 丢弃、分布式优化器/FSDP、分布式检查点等生产特性。该框架支持从研究原型到生产级万亿参数模型的训练。

## **2. Megatron-Core MoE 架构**

### **2.1 MoE 层架构与前向传播**

MoE 层由三个模块组成：**路由器**、**token 调度器**和**专家**。前向传播分为四个阶段：路由、调度、专家计算、合并。

![](https://picx.zhimg.com/v2-72ca1eca00a02a08b7dad0ba9e49611f_r.jpg)

- **路由器**：通过线性投影将每个 token 的隐藏状态映射到 E 个 logits，然后通过 softmax 或 sigmoid 得到概率，最后选择 top-k 个专家。路由器输出路由概率和 token-专家分配掩码。对于数值稳定性，路由器可以以 FP32 精度运行。
- **token 调度器**：负责 token 在 GPU 间的移动。首先对 token 进行排列，使目标同一专家的 token 连续，然后使用通信后端将 token 发送到对应的专家 GPU。通信后端包括 AllGather（简单但内存密集）、All-to-All（标准 NCCL 基于点对点）和 Flex（支持 DeepEP 和 HybridEP 等优化后端）。
- **专家**：通常是两层 MLP，可包含 SwiGLU 等激活。使用**Grouped GEMM**将多个专家的计算批量执行，提高 GPU 利用率。实现包括 TEGroupedMLP（支持 FP8/FP4）和 SequentialMLP（用于调试）。对于共享专家（如 DeepSeek-V2/V3 中的设计），它可以与路由专家的计算并行执行，隐藏其延迟。

![](https://pic2.zhimg.com/v2-244a3b3d91e6f83013b591f1fb6c2791_r.jpg)

### **2.2 系统集成：并行性与优化器**

- **并行组管理**：使用 `ProcessGroupCollection` 为注意力层（使用 TP、CP、DP、PP）和 MoE 层（使用 EP、ETP、EDP、PP）分别创建独立的通信组。这种分离是实现“并行折叠”的基础，使得注意力层和 MoE 层可以使用不同的 TP/DP 配置。例如，注意力层可用 TP=4，而 MoE 层可用 ETP=1 且更高的 EP。

![](https://pic1.zhimg.com/v2-e22d36632292b959c8e411766f9c544e_r.jpg)

- **优化器和梯度处理**：使用 `ChainedOptimizer` 分别处理稠密层和专家层的参数。专家参数标记为 `allreduce=False`，其梯度在专家数据并行组（EDP）内规约，而不是全局 DP 组。梯度需要按比例缩放以反映不同有效批次大小。这种设计允许 ZeRO 式优化器状态分片与 MoE 无缝协作：专家参数的优化器状态在 EP 组内分片，而稠密参数的优化器状态遵循标准 DP 分片。

## **3. 扩展 MoE：并行折叠与多维并行**

### **3.1 为什么需要并行及 MoE 的不同**

对于密集模型，参数和计算同步增长，增加并行度时，通信开销占比相对稳定。而 MoE 模型由于参数-计算不匹配，内存需求迫使使用更多 GPU，但计算量并未同比增加，导致通信开销占比大幅上升，训练更易变为通信受限。

### **3.2 MoE 并行性的挑战**

传统并行策略在 MoE 上失效：张量并行（TP）在专家层导致矩阵分片过小，计算效率低下；流水并行（PP）在模型极深时产生大量空闲气泡；数据并行（DP）无法切分参数，单卡存不下整个模型。因此需要第五个并行维度：**专家并行（EP）**。EP 将不同专家放置在不同 GPU 上，每个 GPU 持有 E/EP 个专家。

![](https://pica.zhimg.com/v2-22ec4aae999cb5f848c148336562afd0_r.jpg)

前向过程包括：路由、all-to-all 调度、专家计算、all-to-all 合并。EP 的通信量正比于 token 数和隐藏维度，与专家总数无关。但 EP 仅适用于 MoE 层，注意力层仍需 TP、CP 等策略，从而产生**密集-稀疏不匹配**：同一 Transformer 块中，注意力层和 MoE 层的最优并行配置冲突。

![](https://pic3.zhimg.com/v2-71afb300aeaf734304403af87c951d16_r.jpg)

传统框架强制 EP ≤ DP，导致三个问题：

1）最低 GPU 要求高（例如 CP=8、EP=8 需 64 GPU）；

2）被迫在次优配置中折中（高 TP 伤害专家效率，低 TP 使注意力欠并行）；

3）EP 通信可能被迫跨节点，带宽降低。

### **3.3 Megatron-Core 的解决方案：并行折叠**

**并行折叠**的核心思想是解耦注意力层和 MoE 层的并行映射，允许各自使用最优的拓扑结构。注意力层使用 TP × CP × DP × PP，MoE 层使用 ETP × EP × EDP × PP，唯一约束是流水并行度（PP）必须保持一致。这打破了 EP ≤ DP 的限制：EP 可以“折叠”跨越 TP/CP/DP 组，实现远超 DP 的 EP 度。例如，注意力配置为 TP=4、CP=2、DP=8、PP=4（总共 256 GPU），传统框架 EP ≤ DP =8，而通过并行折叠，MoE 层可用 EP=64，即 EP “折叠”跨越 TP×CP×DP 组，同时注意力层保持原有配置。

![](https://pica.zhimg.com/v2-275b00dd4f6e176b6f1dd99c58c5970a_r.jpg)

这带来了四个优势：

1）EP 可大于 DP；

2）降低最低 GPU 要求（CP 和 EP 可共享 GPU 组）；

3）独立优化各层；

4）可将 EP 和 CP 通信限制在 NVLink 域内，避免慢速跨节点通信。此外，并行折叠框架还集成了分布式优化器和 FSDP 以进一步减少内存占用。

![](https://pic2.zhimg.com/v2-483c344b1c3539d3fd738b0d73884817_r.jpg)

## **4. 突破 MoE 训练的三大瓶颈**

### **4.1 突破内存墙**

内存是训练的第一个硬约束。以 DeepSeek-V3 为例，在 BF16 精度、PP4×VPP4×EP64 配置下，每 GPU 内存需求高达 199.5 GB，远超 H100 的 80 GB。其中激活内存占 131 GB，是最大的优化目标。

- **内存高效排列**：通过改变路由权重的乘法位置（将权重乘在激活函数之后），消除了为计算路由梯度而保存的中间张量，实现**零开销**的内存节省。对 DeepSeek-V3 可节省约 26.3 GB。

![](https://pic1.zhimg.com/v2-ba4ea9f6e9b1f7b3df467475f762c91c_r.jpg)

- **低精度训练**：将激活存储在 FP8/FP4 而非 BF16，内存减半/减75%。对 DeepSeek-V3 可节省约 16 GB。
- **细粒度重计算**：只选择内存占用大但计算代价小的模块（如 MLA 的上投影、SwiGLU 激活、LayerNorm）进行重计算，而非整个层。结合“输出丢弃”策略，进一步减少内存。对 DeepSeek-V3 可节省约 42.4 GB。

![](https://pic3.zhimg.com/v2-f7ce8c6b703545d58e85404031d3b49e_r.jpg)

- **细粒度激活卸载**：将计算代价大的模块（如注意力、专家）的输入激活，在计算完后立即异步卸载到 CPU 内存，需要时再预取回来。通过专用 CUDA 流与计算重叠，隐藏传输延迟。模块级粒度允许混合策略：轻量模块用重计算，重量模块用卸载。在 PP/VPP 场景下，通过 ChunkOffloadHandler 管理多个微批次和虚拟阶段的卸载/重载。相比完全重计算，卸载可将峰值内存从 L 个 layer_input + 1 个中间激活降低到 1 个layer_input + 1 个中间激活，与层深度无关。对于 DeepSeek-V3，卸载可减少 10-18% 内存，仅带来 1.6-2% 吞吐量开销。

![](https://pic1.zhimg.com/v2-ffa68e2bbe826e40a1c9139dd15fd95c_r.jpg)

![](https://pic3.zhimg.com/v2-bebf0f43c8c2bbb4d3bf126e3d61e872_r.jpg)

- **权重和优化器优化**：
- **FSDP for MoE**：结合 FSDP 和 EP，通过双重 DeviceMesh 设计，对稠密层和专家层应用不同的分片策略。使用**非均匀分片**（将模块内参数扁平化后分片，减少通信开销）、**持久双缓冲**和**NCCL 用户缓冲区注册**，实现零拷贝通信，降低 SM 占用，并支持通信-计算重叠。

![](https://pic2.zhimg.com/v2-c0c598c571ec591df71d7d7d8c51f6e7_r.jpg)

![](https://pic4.zhimg.com/v2-3aecc039d18f762f9497a5a8f4297eb7_r.jpg)

### **4.2 突破通信墙**

EP 引入了大量 all-to-all 通信，在跨节点时可能占训练时间的 40-60%。

![](https://pic3.zhimg.com/v2-c10110e2719a05400466491df0640442_r.jpg)

- **通信剖析**：每个 MoE 层需要两次 all-to-all（dispatch 和 combine）。对于 DeepSeek-V3（58 层），每前向就有 116 次 all-to-all，反向加倍。通信量由 EP 配置决定，无法减少，因此优化目标是最大化带宽利用率和隐藏延迟。
- **HybridEP**：优化的 token 调度器，取代标准 NCCL all-to-all。HybridEP 利用 TMA、RDMA 等技术，实现 token 级通信，通过减少 permutation 操作、避免 token 的重复通信、融合归约操作，显著提高带宽利用率，并减少 SM 占用。在跨节点场景下，HybridEP 先通过 RDMA 在相同本地索引的 GPU 间交换数据，再在节点内转发，减少跨节点流量。对于 combine，HybridEP 将归约融合进通信内核。在 GB200 和 H100 上测试，HybridEP 相比 all-to-all 有显著性能提升，在跨节点时提升幅度更大。

![](https://pic3.zhimg.com/v2-7d710e0088af0de83304abf014630338_r.jpg)

![](https://pic1.zhimg.com/v2-b0ad6375ebc62f31ee8eaa2fa3c0875a_r.jpg)

- **EP 通信重叠**：将 all-to-all 与计算重叠。采用**合并的前向-后向调度**（例如将微批次 1 的前向与微批次 2 的后向合并）和**权重/数据梯度拆分**技术，打破依赖关系，使通信能与计算并行。结合交错流水线并行（Interleaved PP），可最大化重叠机会。通过流分离和 W/D 拆分，将 EP 通信开销从 30-40% 降至 5% 以下。在 DeepSeek-V3 训练中，实现了 93% 的通信延迟重叠。

![](https://pic2.zhimg.com/v2-1d9fa7de60f25ec0b44a7c2b856fbd61_r.jpg)

![](https://pica.zhimg.com/v2-996b9cb5d0cf6efe56f3f287e770a504_r.jpg)

## **5. FP8/FP4 低精度训练**

低精度训练同时影响三大瓶颈：减少内存、加速通信（参数 AllGather 减半）、提升计算。但引入量化内核开销，可能影响稳定性。策略是**选择性精度**：保护数值敏感部分（路由器、嵌入层、输出层、梯度、优化器状态）保持高精度，对大部分计算（专家 GEMM）进行低精度量化。

## **7. 生产级特性**

- **负载均衡与 token丢弃**：支持多种负载均衡策略（辅助损失、专家选择路由、基于历史负载的可学习偏置）。支持 token 丢弃模式（可预测内存）和无丢弃模式（模型表现力最大）。丢弃模式下可启用 pad-to-max，将专家输入填充到相同容量，实现静态形状，便于使用 CUDA Graph。

![](https://pic1.zhimg.com/v2-3735abb30156e1689cc5ecd5a84bc7cc_r.jpg)

- **共享专家**：支持 DeepSeek-V2/V3 等架构中的共享专家，并可将其计算与 all-to-all 通信重叠，隐藏其延迟。

![](https://picx.zhimg.com/v2-e26ad1534ed133a42025b791a5e40d99_r.jpg)

- **潜在 MoE**：在路由后、通信前加入下投影，在压缩的潜在空间进行专家计算，然后上投影恢复，以此减少 all-to-all 通信量和专家参数量。
- **分布式检查点**：基于分片张量描述符，实现并行策略无关的检查点保存和加载，支持任意并行配置间的转换（如 TP2/EP4 到 TP4/EP8）。保存时每秩独立写入本地分片，加载时根据新配置读取所需切片。
- **灵活的非对称虚拟流水线并行**：允许每个虚拟流水线阶段包含不同数量和类型的层，以平衡不同计算成本的层（如嵌入层、MoE 层、MTP 层）带来的负载不均。例如 DeepSeek-V3 在 PP=16、VPP=2 时，可将轻量的嵌入层与 3 个稠密解码器放在同一阶段，MTP 层单独一个阶段，实现负载均衡。

![](https://pic3.zhimg.com/v2-c143aa1d2a725af64fb7e2cac9cd7870_r.jpg)

- **升级循环**：将预训练的稠密模型高效地初始化为 MoE 模型。通过虚拟组初始化和专家权重缩放，使初始化后的 MoE 输出与原始稠密模型一致，保证训练稳定性。

![](https://pic3.zhimg.com/v2-e8206fae8e98a3ec7aca6ecfc70a3238_r.jpg)

- **多token预测**：在每个位置预测多个未来 token，加速收敛。与流水并行集成，可灵活放置 MTP 层。
- **Muon 优化器**：矩阵感知优化器，对权重矩阵进行正交化，加速训练。支持分片 QKV 布局、与分布式优化器集成、CPU 卸载。MuonClip 解决注意力爆炸问题。

## **8. 性能评估**

在 GB200/GB300 和 H100 上评估 DeepSeek-V3 (685B) 和 Qwen3-235B，启用全套优化。主要结果：

- DeepSeek-V3：在 256×GB300 上达到 1233 TFLOPS/GPU，在 256×GB200 上达到 1048 TFLOPS/GPU（MXFP8），在 1024×H100 上达到 368 TFLOPS/GPU（FP8-Blockwise）。
- Qwen3-235B：在 256×GB300 上达到 974 TFLOPS/GPU，在 256×GB200 上达到 919 TFLOPS/GPU（MXFP8），在 256×H100 上达到 320 TFLOPS/GPU（BF16）。
- GB200/300 相比 H100 有约 3 倍的吞吐量提升，归功于更大内存、更高带宽和原生 MXFP8 支持。
- Qwen3-235B 在 131k 长上下文下仍能达到 1150 TFLOPS/GPU，证明了长上下文训练效率。

## **9. 性能最佳实践**

### **9.1 系统化优化流程**

1. **第一阶段：建立内存可行的并行策略**。使用内存模拟器（提供交互式 GUI），找到能在 GPU 内存中放下的最小并行配置（尽量减小 TP/EP/PP/CP，最大化 DP）。
2. **第二阶段：选择最优并行策略**。遵循准则：保持 EP 和 TP 通信在 NVLink 域内；用 PP 进行跨节点扩展；对专家层优先用 EP 而非 TP；长序列启用 CP。
3. **第三阶段：剖析并优化瓶颈**。

- **内存瓶颈**：应用 FP8、细粒度重计算、卸载、精度感知优化器等。
- **通信瓶颈**：使用 HybridEP/DeepEP，启用通信重叠，优化 TP 通信等。
- **CPU 开销瓶颈**：启用 CUDA Graph（部分或全部），减少内核启动，禁用 Python GC 等。
- **计算瓶颈**：启用Grouped GEMM、内核融合、FP8。

### **9.2 案例研究：在 GB200 和 H100 上调优 DeepSeek-V3**

- **GB200 (256 GPUs, NVL72)**：最终配置 TP1/PP4/EP64、MXFP8、HybridEP、CUDA Graph、无通信重叠。理由：EP64 在 NVLink 域内，通信不是瓶颈。FP8 加速后 CPU 开销成为主要矛盾，因此 CUDA Graph和 HybridEP 至关重要。大内存允许 PP=4 和较少重计算。
- **H100 (1024 GPUs, NVL8)**：最终配置 TP2/PP8/EP64、FP8-Blockwise、DeepEP、启用通信重叠。理由：EP64 跨节点，通信是主要矛盾，因此启用 DeepEP 和通信重叠。内存较小，需要 PP=8 和更激进的重计算。

## **11. 结论**

Megatron-Core MoE 通过集成优化方案，成功应对了 MoE 稀疏性带来的参数-计算不匹配和密集-稀疏不匹配两大核心挑战。其关键技术包括多维并行与并行折叠、针对内存/通信/计算三大瓶颈的突破方案、FP8/FP4 低精度训练、长上下文和 RL 训练支持。这些优化使得在千卡规模集群上高效训练万亿参数级 MoE 模型成为现实，为学术界和工业界提供了生产就绪的开源解决方案。性能数据表明，在 GB200/300 上 DeepSeek-V3 可达 1048/1233 TFLOPS/GPU，Qwen3-235B 可达 919/974 TFLOPS/GPU，展示了框架的强大能力。
