> 原文：SPARTA: A Sparse Ternary LLM Accelerator with Adaptive Attention and Unified Datapath for Long-Context Edge Inference<br>作者：Yanzhen Zhou、Zhengyu Han、Qunyou Liu、Zheyu Yan、Weihong Xu、Cheng Zhuo（浙江大学 / Veloxis AI）<br>arXiv:2610.34824v1，cs.AR，2026-10-26，16 页

三元量化（ternary，权重只能取 −1、0、+1，1.58 bit）把大模型的权重压到 FP16 的十分之一左右，还保留了 88%–97% 的「智能」——对边缘设备来说这几乎是白送的。于是过去两年，三元加速器基本都在卷同一件事：怎么把「乘加」变成「加、减、跳过」。

这篇论文指出：**这条赛道已经把主矛盾解错了**。权重压得再小，上下文一长，每个 token 要读的 KV cache 就是线性增长的；到了 32K 上下文，每 token 的访存大头已经不是权重而是 KV。更要命的是，现有三元加速器把线性层和 attention 放在两套完全不同的 datapath 上（一套查表做三元 GEMM，一套做多 bit 的 QK/PV），面积和能效都被摊薄。

SPARTA 的三招因此非常对症：**一个统一的条件累加原语**吃掉三元稀疏和 bit 级稀疏；**一块共享 fabric** 同时跑 prefill 的 SpMM、decode 的 SpMV 和 bit-serial attention；**两阶段自适应注意力**（页级 Top-k + token 级 Top-p）把 K 和 V 的读取分开削。

## 一、瓶颈转移：权重不再是那个大头

先看论文开篇的这张图，它把整篇文章的动机讲完了。

![](https://pica.zhimg.com/v2-a6038337106d346c8e03d566521c025c_1440w.jpg)

图 1：(a) 六个三元模型的权重存储与相对全精度基线的智能保留率；(b) 每 token 的权重与 KV cache 流量拆分，随上下文从 4K 到 32K 变化

左边 (a) 是「压缩红利」：BitCPM 与 Ternary-Bonsai 两族模型（1B 到 8B）的权重存储都在个位数 GB，相对 8 bit 模型只有五分之一，智能保留率 88%–97%。右边 (b) 是「新的账单」：每 token 的访存里，权重部分基本是常数（模型不变就不变），KV 部分随上下文长度线性上升。短上下文时权重占主导，长上下文时 KV 占主导——**三元量化把权重这一项按下去，反而让 KV 这一项更早成为瓶颈**。

论文给的判断很直接：KV cache 的每次访问都是每 token 的固定开销，密度再高的算力也救不了访存。所以加速器必须同时做两件事——把线性层的稀疏吃掉，把注意力的 KV 访问砍掉。

## 二、三个观察，撑起三个设计

**(1) 稀疏是异构的，而且分布在完全不同的维度上。** 三元权重的零值比例平均 38%–40%，但按 tile 看是 10%–73%（图 3a）——也就是说粗粒度的结构化稀疏假设会浪费掉大量机会。注意力这边则是 bit 级稀疏：query 的位平面约 69% 是 0，概率 P 的位平面约 83% 是 0。再往外一层是「注意力本身的稀疏」：覆盖 90% 注意力质量所需的 token 数，在不同 head 之间能差三个数量级（图 3b，BitCPM-3B、32K）。

![](https://pica.zhimg.com/v2-c4dc00225e67498ac3fcaace7afa07da_1440w.jpg)

图 3：(a) 六个三元模型的零权重比例（均值 38%–40%，按 tile 10%–73%）；(b) BitCPM-3B 在 32K 上下文下，各 head 覆盖 90% 注意力质量所需的 token 数（对数轴，跨三个数量级）

**(2) 精度是异构的。** 线性层是三元（1.58 bit 权重 + 8 bit 激活），注意力必须保留多 bit——KV cache 用 INT4、P 用 16 位定点、QK 用 INT8。所以「一个 LUT 打天下」的 PE 注定要在某一边低效：TENET/TeLLMe 的 LUT 是为稠密三元计算优化的，做不了稀疏 SpMM/SpMV；FIGLUT/MCBP 的 bit-plane 映射又很难高效表达三元。

**(3) 稀疏注意力的选择器，比注意力本身更难做。** 固定预算的 Top-k（Quest 那一路）硬件友好但预算僵化：预算小了丢重要 token，大了白读 KV。Top-p 自适应，但要先有精确的 QK 分数，于是省不下 K 的读取。Twilight 把两者串起来，代价是要一份额外的低精度 K cache，而且阈值靠二分搜索、最多重扫 17 遍。

三者的定位可以看论文这张表：

| --- | --- | --- | --- | --- | --- |
| MCBP | W8/A8 | 稀疏 | 稀疏（Top-k） | 中 | 8K |
| Vec-LUT | W1.58/A8 | 稠密 | 稠密 | 低 | – |
| TeLLMe | W1.58/A8 | 稠密 | 稠密 | 低 | 1K |

## 三、技巧一：三种算子，其实是一个原语

这是全文最漂亮的一步抽象。三元 SpMM（prefill）、三元 SpMV（decode）、bit-serial QK/PV（注意力）看起来毫不相干，但作者把它们都写成了同一次「带符号、带移位的向量条件累加」：

$z \leftarrow z + s \cdot 2^{b} \cdot v, \qquad s \in \{-1, +1\}$

- **三元 SpMM**：每个非零权重产生一次 ADD 或 SUB，b=0，操作数是激活的一整行，lane 映射到输出列。
- **三元 SpMV**：激活是标量 a，操作数向量里把三元权重折进广播值（+a、0、−a），lane 映射到输出行。
- **bit-serial attention**：把多 bit 系数拆成位平面，每个为 1 的位贡献一次移位；QK 里 s 来自 query 的符号、b 来自置位的位置；PV 里 P 是 16 位定点，每个置位贡献一次移位，s 恒为 +1。

![](https://pic3.zhimg.com/v2-0dac0efb77fde6d11cded74564d00aee_1440w.jpg)

图 7：(a) decode 的 SpMV；(b) prefill 的 SpMM；(c) bit-serial attention——三者都归约成同一个 outer-product 条件累加，区别只在「谁被跳过」

为什么选 outer-product（外积）而不是 dot-product 或 row-wise？论文的解释很实在：dot-product 数据流下每个 lane 算一个输出，非零数不同会让 lane 完成时间参差，而且每个输出都要单独归约；row-wise 数据流一次算一行，但稀疏列索引会让对稠密矩阵行的访问变得不规则、复用也差。外积则是「一次选一个向量操作数，广播到多个 lane 上做更新」——正好匹配这个原语。

于是「跳过」变成了统一的收益来源：三元里跳过零权重（理想加速 1/(1−s_w) ≈ 1.67×，s_w≈40%），注意力里跳过零 bit（QK 约 3.2×，PV 约 5.7×）。

## 四、技巧二：一块 fabric 跑完所有算子

统一原语之后，硬件上就不需要两套 datapath 了。SPARTA 把每个有效的向量更新编码成一条 **request**：`{opcode, shift, bank, accumulator 地址, 32 个操作数}`。控制器选一路 request 流驱动 fabric 直到算子完成——换算子只是换 request 的解释方式，PE 阵列和输出通路完全不动。

![](https://picx.zhimg.com/v2-4524165bb922f6023a50ba31c2855397_1440w.jpg)

图 9：(a) 三个算子如何映射成同一种 request（SpMM 用 sgn(W)+ADD/SUB，SpMV 把 ±W 折进操作数，QK 用符号+移位，PV 恒为加）；(b) 共享 fabric：16 个 bank PE × 32 lane 累加器，bank crossbar 与 per-bank conflict FIFO

跳过零权重之后，SpMM 的 request 流变得不规则：每个存活权重自己决定落到哪个 bank，一个 cycle 里多个 request 可能撞到同一个 bank。SPARTA 用 bank crossbar 做目的路由，每个 bank 前面挂一个 conflict FIFO，每 cycle 收 2 个 request、排 1 个出去——两个入队口是为了让 bitmap 解码器不用停下等 FIFO 排空。SpMV 和 bit-serial attention 的 request 流本来就是 bank 对齐的（每 bank 每 cycle 最多一个），直接绕过 FIFO。

每个 PE 有 32 个累加 lane 和一个 4 entry 的累加器寄存器文件，request 里带目标 PE 和累加器地址，部分和就留在本地寄存器里，算完直接吐出去。

配置搜索的结论：conflict FIFO 深度 8 能达到深度 32 的 96.7% 吞吐，但只花四分之一的寄存器；fabric 选 16 PE × 32 lane——lane 减到 16 会让 prefill 吞吐腰斩，PE 加到 32 多 78% 逻辑面积却换不来 decode 延迟下降（decode 是带宽受限的，早就饱和了）。

## 五、技巧三：两阶段稀疏注意力

注意力这部分是 SPARTA 和别的加速器拉开差距的地方。核心思路是**用便宜的手段削 K，用精确的手段削 V**：

- **页级 Top-k 削 K**。每个 K 页（16 个 token）为每一维记录一个带符号的 INT4 最小值/最大值。对一个 query，页分数用每维的上界来估：

ŝ(g) = Σ(d) max(q(d)·Kmin(g,d), q(d)·Kmax(g,d))

因为每个 key 元素都落在页的极值之间，这个分数是真实分数的上界，所以选页不会漏掉高分页。页预算 k = ⌈ρk·⌈N/16⌉⌉，默认 ρk=1/4——32K 上下文时正好 512 页，也是选择器支持的上限。sink 页和最近的页是强制的，占预算。

- **token 级 Top-p 削 V**。只对进入候选集的 token 算精确 QK，然后把「与候选最大值的差」量化进 64 个有序 bin，用指数 LUT 得到近似质量，累加成直方图，再从头扫 bin 直到累计质量达到 p。保留集合就是 bin 0 到 b*，PV 在保留集合上重新归一化。

这里的关键不是算法，而是**把「排序/二分」换成「直方图」**。Twilight 要二分搜索阈值、最多重扫 17 遍，工作量是 O(ρk·N·L)；SPARTA 是 O(ρk·N + B)，而且 B=64 是固定片上状态。论文实测：64 bin 与精确 Top-p 的困惑度差不超过 0.10，而换成 Twilight 式二分会让注意力慢 2.0–3.0×、TPOT 慢 1.1–1.8×。

![](https://pic1.zhimg.com/v2-28e3a69c535d02845f414a22ef18d55e_1440w.jpg)

图 10：两阶段选择器的硬件：(a) Bitonic 页 Top-k（score pack → 局部排序 → 层次归并，sorter 按时分复用，上下文变长只增加迭代次数）；(b) 流式直方图 Top-p 五步（全局最大 → 分 bin 与指数质量 → 局部直方图 → 归约与阈值 → 选 token 并生成 P 位）

还有两个必须处理的工程问题：

- **GQA 的页选择只能做一次**。所有被评测的模型都用 GQA（2–16 个 query head 共享一个 KV head）。如果每个 head 独立选页，K 流量会按组大小翻倍。所以 SPARTA 每个 KV group 只做一次页 Top-k：各 head 先把页分数 softmax 成概率分布，组内按总概率取前 k 页；候选集 T 和 K 的读取由全组共享，Top-p 仍然逐 head 做，V 取并集。
- **流量账**。把「一个 token 的 KV 向量」记作一个单位，密集注意力 C=2N；只做 Top-k 是 N/8 + 2ρk·N（N/8 是每 16 token 一页读两维元数据的开销）；再加上 Top-p 就变成 N/8 + (1+ρp)·ρk·N。Top-p 只削 V，不额外读 K——这是它与 Twilight 路线的本质区别。

## 六、整体架构：8 个 slice，13.9 mm²

![](https://pic4.zhimg.com/v2-c4f16e0a6139b5f5c570a5552085b8ab_1440w.jpg)

图 8：SPARTA 顶层架构：8 个相同 compute slice 接 HBM2，每个 slice 含共享 fabric、自适应稀疏注意力引擎、操作数缓冲和 APU；顶部时序图显示 decode 时 K/V 生成与 Top-k/Top-p 选择并行

8 个 slice 并行处理不同的 attention head 和输出 tile，fetcher/dispatcher 把三路操作数（bitmap 压缩的三元权重、INT8 激活/query、打包的 INT4 K/V 及其页极值）stage 进每个 slice 的 SRAM，APU 负责 embedding、残差、特殊函数和量化。

时序上有一个巧妙的重叠：sink 页和最近页永远保留，所以新 token 的 K/V 生成可以和页 Top-k、直方图 Top-p 并行——选择器不用等 K/V 写完。实测中 Top-k 完全盖住了 K 生成（8K 的 Bonsai 除外），Top-p 在所有情况下都盖住了 V 生成。

配置与代价（28nm、1 GHz）：总面积 13.9 mm²，片上平均功耗 1.40 W。共享 fabric 占面积 47.6%、功耗 39.6%（它复制了 8 份，而且所有算子都跑在上面）；Top-k 选择器 10.6% 面积、Top-p 引擎 3.7%，两者合计只占 14.3% 面积和 16.6% 功耗。这个比例很值得记：**稀疏注意力的选择器做到了「不像个负担」**。

## 八、批判性评估：哪些数字要打折扣

**1. 全是「综合 + 模拟」。** 硬件用 SystemVerilog 写、28nm 商用库综合，SRAM 面积/能耗用 CACTI 估，性能用「对照 RTL 逐级校准过的 trace-driven 周期级模拟器」，HBM 用 Ramulator2 校验带宽。没有流片，没有硅后数据。这类论文的绝对值要谨慎看待，但相对趋势（选择器只占 14% 面积、fabric 是面积大头）比较可信。

**2. CPU/GPU 基线是「dense attention + FP16 KV」，不是同精度的稀疏方案。** 也就是说 3.9× 吞吐和 8.3× 能效里，混着「专用架构」和「稀疏算法」两部分收益。作者自己在正文里写明了（"these gains combine architectural and sparse-attention benefits"），但表格里并排放在一起时很容易被误读。GPU 上其实也有 Quest/Twilight 这类实现，缺了这一组对照，就无法回答「同样的稀疏算法在 Jetson 上能拿回多少」。

**3. 和加速器对比时的基线也是自己重实现的。** FIGLUT、TeLLMe、TENET、MCBP 都是「用我们的 28nm 流程复现线性 PE、缩放到论文宽度、没有稀疏注意力就接我们的 dense 通路」。TENET 跑在 500 MHz（原论文频率），MCBP 还要用正负两遍映射三元权重。这些处理合理，但基线是被「我们的流程 + 我们的 attention」框住的，不是原样跑原设计。

**4. 质量的损失是 task-dependent 的。** GovReport 上 BitCPM-1B 从 25.9 掉到 21.3，Bonsai-8B 的 GMean 掉了 2.21 分。对长文摘要、检索类任务，页级预算 + 组内共享页这套设计天然吃亏。论文也直接说了短上下文要关掉 Top-k（页太少，削一半质量崩、留多了没得省）。

**5. 32K 是硬上限。** 选择器 512 页、每页 16 token，32K 正好打满。要上 128K 得重新设计选择器（更大的 sorter 或者两级页表），论文没讨论。

**6. 三元模型本身的损失会叠加。** 88%–97% 的智能保留率是相对全精度基线说的，SPARTA 再叠一层稀疏注意力损失——两层损失的组合效果，论文只给了「perplexity 差 ≤0.61 和任务分」这两类指标，没有端到端的应用级评测。

**7. 没有开源。** 没有 artifact 链接。

## 九、对做芯片和做系统的人分别有什么用

**对做加速器的人**，这篇论文最大的贡献是那个抽象：**把「稀疏」定义成「跳过某个不动结果的向量更新」，而不是「某种特定的压缩格式」**。一旦三种算子都写成 z ← z + s·2^b·v，跳过零权重和跳过零 bit 就变成同一个开关，datapath 自然统一。这比「再设计一个 LUT」要省得多。

**对做推理系统的人**，有两个可以直接搬走的结论：

- **页级 min/max 元数据极其便宜**。每 16 个 token 一页、每维一对 INT4 极值，代价是 N/8 的额外读取，换来用上界打分筛页——这套思路在 GPU 上同样成立（Quest 走的就是这条路），不需要任何新硬件。
- **Top-p 的硬件化关键是「别排序」**。64 个 bin 的直方图 + 指数 LUT 就能把阈值搜索从 O(N·L) 降到 O(N+B)，质量差 ≤0.10 困惑度。这条经验对任何要做「按概率质量裁剪」的系统都适用。

最后一个值得记住的比例：两阶段选择器只占 14.3% 面积、16.6% 功耗，却带来了 decode 上 4.0–6.2× 的注意力加速。稀疏注意力的工程难点从来不是「剪哪些」，而是「怎么便宜地决定剪哪些」——SPARTA 的价值就在于把后半句做成了硬件。
