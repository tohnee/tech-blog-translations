## uGDS 从何而来

随着大模型 Scale Up 以及Agent时代到来，大模型推理的瓶颈逐渐从 GPU 算力转移到稀缺的内存资源以及不同层级存储介质之间的数据搬运速率上。各大模型厂商使用各种奇技淫巧来提高端到端的推理速度，比如从模型算法架构出发的MoE 架构，GQA，DSA ；从模型推理层出发的 Paged Attention，RadixTree, 针对具体模型的Megakernel...... 通过阅读前沿的 Deepseek Flash 系列模型的 tech report，我们可以发现单 token KV Cache 的大小从过去的几百 KB 优化到几 KB（甚至到如今 4.1 Flash 的 890 Bytes）。即使是满 1 M 上下文，总 KV 大小也从上百 GB 减小到了不足 1 GB。那么可以得出一个不完全证明的推测：**在上下文窗口越变越长的同时，KVCache 也会越做越小，对于较短的会话而言，Cache 的命中也是碎片化的。**

**上下文窗口变长意味着什么？** 缓存是大模型时代的数字资产，NVMe SSD 作为具有较高性价比的高速存储，非常适合用来持久化存储海量会话的缓存（TB/PB 级别）。**KVCache 越做越小又意味着什么？** 对于 Flash 这类模型，单块消费级 PCIe Gen4/Gen5 x4 NVMe SSD 有 5~12 GB/s 的带宽，企业级 Gen5 盘（比如 PM1743）也有 13 GB/s 左右的带宽，可以在不到 1 s 内加载历史会话缓存到 GPU 显存中。（注意，这里如果做条带化存储加载的话将会更快，因为是聚合带宽）

所以对于今后的 AI infra，NVMe SSD 是高性能 AI存储中不可或缺的一环。比如 LMCache 中就把 GDS 作为 L 1 热缓存层的 backend 之一，Mooncake 主要结合远端分布式存储、GDR 技术做了共享存储池。再往前看，libnvm/ssd-gpu-dma, BaM 等等这些工作虽然不是直接面向 AI 领域，但是也是加速GPU-SSD 传输的重要基建。

但是，我们在实际测试 GDS 性能的时候发现由于要经过文件系统以及内核上下文切换，GDS 在面对 KB 级别细粒度读写时的性能非常不理想，带宽低且延迟大（具体数据放在了后文）。libnvm/ssd-gpu-dma 虽然做了用户态发起 NVMe IO 的基建，但是缺少了高层的抽象，暴露的都是原始的 NVMe 硬件原语，然后又因为是 10 年前的工作，在现代 linux 内核和 CUDA、PCIe 平台上很难直接编译、运行和维护。而 BaM 这类 GPU IO 工作，需要额外占用宝贵的 GPU 计算资源，面向的场景是成千上万个并发的不规则、极稀疏、超细粒度（64 B~4 KB）的访存，和当前可提前编排好的规整、结构化、较粗粒度的 LLM 推理访存不一致。而且从软件工程的角度上来说，现代主流的 AI 系统不论是 vLLM、SGLang 还是TensorRT-LLM 等，都是 host-centric 去做控制与编排，这个工程迁移的代价很大。

所以，我们需要一个高性能 AI 存储库：既能直接从用户态发起 NVMe IO 请求，又能较为轻便地接入当前主流的 AI 系统（**在追求极致性能的同时考虑工程落地的合理性**）----- That is uGDS。

简单来说，uGDS 是一个由 CPU 在用户态发起并管理 IO 的类 SPDK 库，不同的是它处理的是 GPU 显存和 NVMe SSD 之间的 direct IO，数据不经过主机内存。也正因为服务的是 GPU，uGDS 没有照搬 SPDK 的接口，而是围绕 GPU IO 的需求重新设计了抽象。比如 GPU IO 在很多情况下并不需要保证 IO 之间的顺序：一批 KV chunk 谁先落到显存都无所谓，只要在下游 Kernel 读取之前全部完成即可。因此 uGDS 不维护请求间的顺序，同步请求可以分散到多条 QP 上并行推进，batch 请求一次性提交、乱序完成，只在整批结束时同步一次。此外还有显存缓冲区的跨平台注册，以及能嵌入 GPU Stream 的异步接口（后文细讲）。

uGDS 背后还有一个我们想验证的判断：**在大部分场景下，GPU 发起的 IO（如 BaM、Tutti）并不是必需的。** BaM 相比 GDS 的性能优势，很大一部分来自绕开内核的用户态 IO，而不在于 IO 必须由 GPU 线程发起。只要实现合理、抽象设计得当，再把多核扩展做好，由 CPU 管理的用户态 GPU IO 库同样能在大部分场景下满足性能需求，而且不占 GPU 算力，也不用改动现有 AI 系统 host-centric 的控制逻辑。

## uGDS 的系统设计

**uGDS 的核心 insight** 是：

1. **最大化用户态控制路径：** NVMe 命令组装、Doorbell 敲门、CQ 轮询均在 Host CPU 用户态完成（`libugds.so`）
2. **最小化内核态初始化路径：** 内核驱动（`ugds_drv.ko`）完成 PCIe 设备探测之后创建字符设备，完成对应的 BAR0 寄存器映射、DMA 物理总线地址锁定以及可选的 MSI-X 中断桥接绑定
3. **跨平台兼容性：** 同样的上层接口，兼容 NVIDIA CUDA 和 AMD ROCm/HIP
4. **面向生产的上层抽象 IO API 开发：** 提供类似 cuFile 风格的接口（方便用户把已有的 GDS 程序迁移到 uGDS 上），支持同步轮询、Batch 模式，GPU Stream 异步流水线编排模式以及中断模式。

核心方法就是在初次注册 DMA 的显存缓冲区时，先走平台的 Malloc 函数拿到虚拟地址指针，然后再通过平台的特有的转物理地址 API 拿到实际的物理地址数组（注意不同平台的包装方式会不同）。接着再把这些不同的表示方式归一化为 nvm_dma_t 这样的结构体，供之后多次 IO 请求使用。然后会把这块注册的缓冲区标记到一个结构体 Buf_registery中，记录 backend, in_flight 数等信息，之后注册和删除缓冲区的时候会先查询这个结构体，查看已有的缓冲区信息。

### 硬件队列切分与并发设计

如何处理多线程 IO 对 QP 资源的抢占呢？ uGDS 对硬件 QPs 进行了功能划分：

- **同步 IO 专用队列池**：将控制器支持的多个硬件 QP 组成同步资源池。多线程通过无锁的原子轮询计数器绑定独立的硬件 QP，各线程在各自独立的 SQ/CQ 环上无锁推进。当线程数超过同步 QPs 数量的时候，未分配到队列资源的线程会阻塞等待。
- **Batch IO 独占深队列：** 分配一条专用的深队列。这样既保证了 Batch 的密集吞吐不会挤占同步请求的延迟，也允许两者针对各自的队列特性独立优化。

### 具体 IO 模式是如何设计的

这里我们先说轮询模式的 IO 吧。

首先是同步IO。同步 IO 的实现方式其实在前面讲同步IO 专用队列池的时候已经提及了核心，简而言之就是原子轮询，线程绑定 QP，提交请求后马上轮询 CQE，然后多余的线程阻塞等待空闲的队列资源。这样虽然实际的队列深度是 1，但是避免了锁竞争。

然后我们对 Batch IO 模式做了特殊的优化。

1. 我们在初始化的时候会利用 `MAP_HUGETLB` 分配物理地址连续的 2MB 大页（2MB 是大页的最小粒度）作为SQ、CQ 队列内存。NVMe 要求每条队列放在物理连续的内存里，一个普通 4 KB 页只能放下 64 条 SQE（每条 64 B），而一个 2MB 大页可以同时容纳 SQ 和 CQ 的上万条表项，队列深度不再受页大小限制，只受 SSD 控制器上限约束。uGDS 目前把 batch 队列深度设为 512（不超过控制器上限）；拿不到大页时退回到每条队列一个普通页，深度降为 64。
2. 初始化的时候也会预映射得到 128 页的 PRP pool，避免了热路径上的动态内存分配，同时运行时也通过 Bitmap 来进行动态的 PRP pool page 使用、归还。
3. 多个子请求在用户态组装完成后，仅触发一次 MMIO Doorbell 写入。然后一直轮询 CQE，直到所有的子请求都完成。

接着是相对于GPU 计算的异步 IO。uGDS 通过 `cudaLaunchHostFunc` / `hipLaunchHostFunc` 将同步 IO嵌入到 CUDA/HIP 流中。即使传输的偏移量与大小是由上游 GPU Kernel 动态计算出来的，也能无缝接入。

最后是中断模式。同步IO 的轮询会长时间占用 CPU，适合细粒度、延迟敏感型任务；中断 IO 会大大减少 CPU 占用，并且在大块传输的时候只会有轻微延迟波动，因为这个时候数据传输时间占主导。在初始化阶段，如果 SSD 的 MSI-X vector（MSI-X 是 PCIe 设备向 CPU 发中断的一种机制） 资源充足，会给每一个同步 QP 创建 eventfd（`eventfd` 是 Linux 提供的一个计数型通知 fd） 并且绑定一个 vector。然后用户态提交 NVMe 命令之后就会睡眠，SSD 控制器完成 IO 请求后写 CQE 的同时触发 MSI-X 中断程序，通过增加eventfd 计数唤醒用户态线程，然后用户态线程再检查更新CQ 并清空计数。

## 未来的uGDS，ScaleX-IO的愿景

性能的优化背后是 trade-off 的权衡。目前的 uGDS 并非完美无缺，因为不经过文件系统，它需要独占一块裸盘。不过在 LMCache 这类拥有自研 Chunk 分配池的系统中，裸块接口反而是性能最优解。

不妨想的更远一些，不走文件系统其实也打开了一种新的可能：**SSD 不只是持久化存放 KVCache 的地方，也可以当作短期的高速交换空间。** 原因在于，数据无论是从 DRAM 还是从 SSD 搬到 GPU，最后走的都是 GPU 的同一条 PCIe 链路。在带宽敏感的场景下，只要 SSD 的聚合带宽（比如多盘条带化）能把这条链路跑满，SSD 就能做到和 DRAM 相当的性能，而容量和单位成本都远优于 DRAM。未来追求极高 TPS 的 AI 系统可能会舍弃传统的文件系统，转而使用语义简单的用户态文件系统，甚至直接管理裸块，而 uGDS 可以作为这类系统的 IO 基础设施。

uGDS 是 ScaleX-IO 组织的第一个开源项目，目前已经收获了 200+stars。在未来，uGDS 将会支持高层次的 AI 存储语义抽象，条带化 SSD 以及远端分布式存储（如NVMe-oF）。欢迎大家为 uGDS（ScaleX-IO 社区）做贡献，无论是 PR 还是 issue，哪怕简单的建议也很难得！
