- **问题起点** ：ChatGPT/LLM 能生成文本、图片、音频、视频，但不能自己执行“订机票”这类动作。
- **中间桥梁** ：AI Agent 能调用第三方平台、保存/读取记忆、与 LLM 反复交互，直到完成任务。
- **新的麻烦** ：Agent 要通过 tools 调第三方 API，但每家 API 路径、参数、响应都不同，不可能为成千上万服务逐个手写适配。
- **MCP 的定位** ：Model Context Protocol 是一套标准，让 AI/Agent 能发现并理解第三方服务暴露的 tools、resources、prompts，从而以统一方式交互。
- **动手路线** ：先配置实验环境 → 使用已有 MCP Server → 理解 MCP 架构与 JSON-RPC → 用 Python SDK 构建 MCP Server → 用 MCP Inspector 测试 → 构建 MCP Client → 理解 client 侧能力：context、roots、sampling、elicitation。

### 典型 AI Agent 工作流

- 用户向 AI Agent 发请求。
- Agent 调 LLM 从用户输入中抽取关键信息，例如目的地是 London。
- Agent 问 LLM 应该与哪些第三方交互；LLM 可能指出 flights、hotels、rental cars、数据库等。
- Agent 调 airlines 获取航班详情。
- Agent 再问 LLM 下一步；LLM 让它读取用户偏好。
- Agent 从数据库/记忆中读取偏好。
- Agent 把航班和偏好交给 LLM 做决策。
- LLM 选出应订的航班。
- Agent 执行订票，并把详情返回给用户。
- 在多个阶段，LLM 都会参与处理数据和做决定。

### JSON-RPC 与传输机制

- Server 和 Client 使用 **JSON-RPC** 通信。
- JSON-RPC = JSON + Remote Procedure Call。
- 它定义 Client 如何远程调用一个方法/过程，传参数并接收响应。
- 示例：Server 有一个 `add` 方法，Client 可以远程调用它并传参数。
- 请求 JSON 文档包含：
- 响应包含：
- JSON-RPC 本身保持简单、无状态，不规定底层传输方式。
- 底层可以用 HTTP、WebSocket、TCP、UDP、Unix socket、message queue、standard IO 等。
- MCP 支持 **HTTP** 和 **standard IO / stdio** 作为 Client 到 Server 的传输机制。

### 关键易错点与安全提醒

- MCP 连接要求 stateful，但 JSON-RPC 本身是 stateless 的；不要混淆“协议消息格式”和“MCP 连接状态”。
- MCP 支持 HTTP 和 stdio 作为 transport；stdio 适合本地进程通信，HTTP 适合本地共享或远程连接。
- 连接远程 MCP Server 时，必须考虑认证、授权、数据隐私和可信度。
- 使用社区 MCP Server 要自行承担风险，因为它们可能未测试或未跟上 API 更新。
- Roots 是对本地文件系统暴露面的控制，不要默认把整个机器暴露给 Server。
- Server 不应直接控制 LLM；Sampling 由 Client 侧处理，便于控制模型、token 和基础设施。
