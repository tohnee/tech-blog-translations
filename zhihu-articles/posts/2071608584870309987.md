三年前，在手机上跑语言模型只是个玩具级 demo。今天，十亿参数级别的模型已经能在旗舰设备上实时运行。这一转变并非仅仅来自更快的芯片，而是来自我们对模型构建、压缩与部署方式的重新思考。

本文讨论最新进展：什么变了、什么真正有效、以及未来的方向。我们聚焦在实践中被证明有用的技术，而不只是论文里好看的东西。

### 为什么需要端侧大模型？

端侧大模型的价值可以归结为四点：

**延迟。** 云端往返会在你看到第一个 token 之前增加 200–500ms 的延迟。对于 AR 叠加显示、实时翻译或语音助手，这种延迟会直接破坏体验。端侧推理可以做到每个 token 20ms 以内，尤其是在短上下文场景下。

**隐私。** 数据不离开设备，就不会在传输中被窃取，也不会被记录在服务器上。对健康数据、金融信息或任何个人内容来说，这一点很关键。在某些领域，这也正在成为监管要求。

**成本。** 规模化的云端推理很贵，每一次查询都要花钱。端侧把这部分成本转移到了用户已经拥有的硬件上。对高并发应用而言，这种经济性非常有吸引力。

**可用性。** 端侧大模型随时可用。而访问云端依赖网络连通性，后者往往无法做到高可靠。

一直以来的难点在于能力上限。边缘设备的内存、算力和功耗预算都有限。如果你的场景需要前沿推理能力、广博的世界知识或长多轮对话，云端仍然是更好的选择。但对延迟敏感、隐私关键或高并发的应用，端侧的可行性正在迅速提高。

### 约束条件

在讨论解决方案之前，先理解我们究竟在和什么作斗争。

### 内存才是瓶颈

一个常见的误解是边缘设备算力不足。其实并非如此。移动端 NPU 如今能提供相当可观的 TOPS，已经接近 2017 年数据中心 GPU 的水平（例如 V100 是 125 TOPS）！

- Apple A19 Pro 神经引擎：约 35 TOPS
- Qualcomm Snapdragon 8 Elite Gen 5：约 60 TOPS
- MediaTek Dimensity 9400+：约 50 TOPS

但只看 TOPS 说明不了太多问题。NPU 能不能跑你模型所需的算子？很多 NPU 对注意力机制、动态 shape 或某些激活函数的支持有限。工具链是否足够成熟，让你不必靠”英雄式工程”才能部署？真实模型的实际利用率离峰值差得很远。

另一个约束是 RAM 的可用量。由于需要与其他服务共存，加上操作系统本身的开销，即使在高端设备上可用 RAM 通常也被限制在 4GB 以内。这既限制了模型规模上限，也限制了 MoE（混合专家）这类方案的适用性。

更深层的约束是内存带宽。移动设备是 50–90 GB/s，数据中心 GPU 是 2–3 TB/s，差距达 30–50 倍。对 LLM 推理来说这个差距是决定性的，因为 decode 阶段是内存受限的：每生成一个 token 都要把整个模型权重加载一遍，计算单元只能空等内存。这正是模型压缩以及”一次预测多个 token”的技术在移动端具有超额收益的原因。从 16-bit 降到 4-bit 不只是存储小了 4 倍，而是每个 token 的内存流量也少了 4 倍，这直接转化为吞吐量。同理，在每一步预测多个 token 几乎是”免费”的，不会带来延迟惩罚。

### 功耗预算

移动设备依靠电池供电，持续推理会迅速耗电。一个会把电池抽干或触发热降频的模型，不管跑得多快都不实用。

这带来了几个方向上的压力：

- 更小的模型（更少的运算）
- 量化模型（更简单的算术）
- 稀疏模型（跳过不必要的计算）
- 高效调度（需要时爆发，其余时间休眠）
- 并行生成输出（更快吐完结果然后休眠）

常开（always-on）场景（持续聆听、环境感知）尤其受限，你需要的是个位数毫瓦级功耗，而不是几百毫瓦。

### 高效语言模型

理解了约束之后，怎样在这些约束内构建模型？

### 能做到多小？

所有人问的第一个问题：语言模型可以小到什么程度还能保持有用？

答案已经发生了巨大变化。2022 年的普遍认知是，要生成连贯文本至少需要 7B 参数。而今天，十亿参数以下的模型已经能处理很多实际任务。

MobileLLM 发现了一个反直觉的结论：在小规模下，架构比参数量更重要。标准的缩放配方（随规模增长而加宽层）在 1B 参数以下并不适用。深而窄的架构（更多层、更小隐藏维度）持续优于宽而浅的架构。一个架构设计得当的 125M 参数模型在 iPhone 上可以跑到 50 tokens/秒，处理基础任务的表现出人意料地好。

各大实验室此后也都收敛到了这一认知：

| 模型 | 规模 | 关键优势 |
| --- | --- | --- |
| Llama 3.2（Meta, 2024） | 1B, 3B | 128K 上下文，针对 Qualcomm/MediaTek 优化 |
| Gemma 3（Google, 2025） | 270M – 27B | 小尺寸下的极致效率 |
| Phi-4（Microsoft, 2025） | 3.8B (mini), 14B | Phi-4-reasoning 在数学上可与 o1-mini 抗衡 |
| SmolLM2（HuggingFace, 2025） | 135M, 360M, 1.7B | 11T 训练 token，超过 Llama 3.2 1B |
| Qwen2.5（Alibaba, 2024） | 0.5B, 1.5B | 小模型通用能力很强；多语言覆盖好 |

贯穿这些工作的规律是：数据质量和训练方法与架构同等重要。Phi-4 使用高质量合成数据集；SmolLM2 引入了专门的数学与代码数据集（FineMath、Stack-Edu）；Gemma 3 使用来自更大模型的知识蒸馏。你争夺的不只是参数效率，而是在固定尺寸下的每一分能力。

不要一上来就假定自己需要大模型。对很多应用（摘要、简单问答、文本格式化、基础代码辅助）来说，1B 以下的模型就够用。先从小做起，确有必要时再放大。

### 边缘端的推理能力

有些端侧场景需要的不只是模式匹配：分析个人文档、对健康数据做推理、消息分诊。小模型真的能完成这些多步问题吗？早期证据表明可以，但有前提。

**从推理模型蒸馏** 效果很好。DeepSeek-R1 的蒸馏产出了 1.5B 到 70B 的一系列模型，保留了很强的推理能力，其中蒸馏得到的 8B 模型在数学基准上超过了远比它大的基座模型。做法是：用一个强推理模型生成思维链数据，再用这些数据微调更小的模型。

**Qwen3 的小模型** 展示了类似结果。Qwen3-4B 在推理任务上可与 Qwen2.5-72B-Instruct 匹敌。Qwen3-30B-A3B 这个 MoE 模型（仅激活 3B 参数）在激活参数少 10 倍的情况下超过了 QwQ-32B。

**MobileLLM-R1** 与 **MobileLLM-R1.5** 在极端边缘场景上验证了这一点：在推理基准上比两倍大的模型好 2–5 倍，且完全跑在移动 CPU 上。

**Liquid AI 的 LFM 2.5** 系列也表现出很强的性能，得益于更大的训练集和基于 RL 的后训练。

这些结果说明：推理能力并不纯粹是参数量的函数，而是关乎训练方法。从强推理模型蒸馏，再配合基于 RL 的后训练，是关键所在。

但限制依然存在。小模型在长推理链、新颖问题类型以及需要广博世界知识的任务上仍然吃力。对端侧来说，这意味着要谨慎地判断哪些任务交给本地模型、哪些交给云端。

### 小模型的数据策略

在小规模下，数据策略与架构同等重要。你无法靠堆参数来强行获得能力，所以每一个训练 token 都必须发挥作用。

小模型从高质量、有针对性的数据中获益尤其明显。我们在参数受限语言模型缩放上的工作表明，数据质量的提升对小模型带来的收益大于对大模型。用精选数据训练的 1B 模型可以匹敌用网页抓取数据训练的 3B 模型。

**数据混配（data mixing）** 是收益最大的杠杆所在。代码、文本、数学、指令数据之间的比例会显著影响下游能力。AutoMixer（Meta, ACL 2025）发现训练过程中的 checkpoint 产物编码了最优数据配比的信息，从而可以自动调整配比，无需昂贵的消融实验。手工调数据比例代价高，而且无法在不同模型尺寸间迁移。

**细粒度采样** 更进一步。Target-Aware Language Modeling（Meta, EMNLP 2024）表明，在文档和段落层面的采样策略会影响模型学到什么。并非所有文档贡献相同；有选择地上采样高信号内容能提升效率。

如果你要为特定领域训练小模型，请投资于数据治理。花在数据质量上的边际一小时，常常胜过花在架构搜索上的边际一小时。SmolLM2 的专用数据集（FineMath、Stack-Edu）和 Phi-4 的合成数据流水线都体现了这一点。

### 架构

### 混合专家（MoE）

MoE 每个 token 只激活一部分参数。自 2025 年初以来，超过 60% 的前沿模型发布采用了 MoE 设计。例如 DeepSeek-V3 使用 256 个专家和细粒度路由。

内存挑战在于：尽管计算是稀疏的，你仍然要把所有专家载入内存。MoBiLE 针对消费级 GPU 提出”大小专家混合”来缓解这一点：对不重要的 token 减少专家数量，对重要的 token 保留完整专家。这带来 1.6–1.7 倍加速，精度损失可忽略。

对边缘端来说，MoE 的吸引力很明确：用小模型的算力获得大模型的能力。挑战在于把所有专家塞进内存，这正是量化和 offloading 技术变得关键的地方。目前的技术有帮助，但没有彻底解决问题——更多讨论见”下一步是什么”。

### 新的基础模块

LLM 架构目前仍以注意力 + FFN 层为主，但这正在改变。除 MoE 之外，文献中还提出了多种注意力机制变体，主要有几个方向：

1. **提升性能：** 声称优于注意力的架构从 2025 年开始涌现，来自 Qwen 的 Gated Delta-Net 和来自 DeepSeek 的流形约束超连接（mHC）都展现了改进。
2. **在降低延迟的同时支持长上下文：** 结合 Mamba 与注意力的混合方案获得了关注（Qwen3 Next、Nvidia-Nemotron3），作为高效处理长上下文的手段。与此并行，聚焦降低延迟的替代方案（如 LIV 卷积和线性注意力）也已出现。

### 量化

如果说架构决定了你的能力基线，那么量化决定了它能否真正装进设备。

### 4-bit 成为新的默认

部署的标准配方已经收敛：以 16-bit 训练，量化到 4-bit 部署。GPTQ（2022）和 AWQ（2023）表明 4-bit 训练后量化能保留大部分模型质量，同时把内存降低 4 倍。这已成为标准做法。仅 AWQ 一项在 HuggingFace 上的下载量就超过 1900 万次。

挑战在于边缘情况。朴素量化在离群激活值上会崩掉，而大语言模型经常产生离群值。带范围学习的 QAT（ParetoQ）效果很好，也适用于加速器——加速器通常对量化方式有额外约束。如果做不了 QAT，下面这些训练后方法很有前景：

**SmoothQuant**（MIT HAN Lab）通过把量化难度从激活迁移到权重来平滑离群值。洞见是：激活的离群值集中在特定通道，而权重相对均匀。通过一个数学上等价的按通道缩放，你可以在不改变模型行为的前提下让激活更易量化。这使得权重和激活同时做 8-bit 量化成为可能，且损失极小。

**SpinQuant**（Meta）学习旋转矩阵，在量化前重塑激活分布。旋转是正交变换，不改变模型输出，但能大幅减少离群值。结果是：权重、激活和 KV-cache 一起做 4-bit 量化，精度损失低于 3%，而此前的方法在这些任务上会掉 25% 以上。

面向规模化服务，**QServe**（MIT HAN Lab）走得更远，采用 W4A8KV4 量化：4-bit 权重、8-bit 激活、4-bit KV cache。这需要量化方案与服务系统的仔细协同设计，但能带来显著的吞吐提升。

给实践者的建议：先用 AWQ 或 GPTQ 快速拿到基线。如果发现质量下降，再考虑离群值感知的方法。SmoothQuant 无需训练，在 8-bit 上表现良好；SpinQuant 能处理激活与 KV-cache 更难的 4-bit 情形。

最近，对 mxfp4 的硬件支持开始出现在边缘硬件上（Apple A19 Pro），凭借更优的数值格式降低了量化损失。

### 更低比特：2-bit 及以下

4-bit 已经实用了，但还能更低吗？可以，只是规则会变。

BitNet（Microsoft）表明原生以 1.58 bit 训练的模型是可行的。一个 2B 参数模型只占 400MB，在 CPU 上运行高效。但你不能把一个现成模型直接量化到 1.58 bit 就期待它能用——必须从头以该精度训练。

ParetoQ（我们的工作）刻画了完整的量化帕累托前沿，并发现了一个令人惊讶的现象：比特数与精度之间的关系并不平滑。在 3–4 bit 区间，量化的作用像是压缩；到 2 bit 及以下，模型学到的是本质上不同的表示。如果模型体积预算固定，那么”更大的模型量化到 2-bit”优于”参数量减半的模型量化到 4-bit”。这对未来意义重大：如果低比特训练能在规模上成立，我们就不只是在压缩模型，而是在发现高精度训练无法到达的新效率前沿。

你也可以混搭：通过混合精度量化，不同层可以使用不同精度，在保持质量的同时进一步压缩。

### 该用哪一档

| 比特数 | 内存 | 质量 | 适用场景 |
| --- | --- | --- | --- |
| 8-bit | 小 2 倍 | 约无损 | 服务器，无约束 |
| 4-bit | 小 4 倍 | 掉 1–3% | 服务器/移动/边缘，配合 QAT |
| 低于 4-bit | 小 4–8 倍 | 掉 3% | 移动/边缘，最佳权衡，配合 QAT |
| 向量量化 | 小 8 倍 | 掉约 3% | 硬件加速器、Apple 神经引擎 |

### 推理优化

除了压缩，”怎么跑”与”跑什么”同样重要。

### 注意力效率

注意力是长序列的瓶颈。FlashAttention（Tri Dao 等）让注意力变得 IO 感知，通过分块（tiling）减少 GPU HBM 与 SRAM 之间的读写。FlashAttention-2 改进了并行度，在 A100 上达到最高 72% 的模型 FLOPs 利用率。FlashAttention-3 面向 H100，利用率最高 75%（740 TFLOPs/s）。在 Hot Chips 2025 上发布的 FlashAttention-4 针对 Blackwell 优化，又带来 20% 加速。

对端侧而言，原则比具体实现更重要：最小化内存流量、把计算分块以适配快速内存、在可用资源上尽量并行。在架构层面，局部-全局注意力和分组查询注意力（GQA）已成为端侧模型的标配；更新的架构常常在部分层直接跳过注意力，从而大幅缩减 KV cache 的规模与复杂度。

### KV Cache 管理

KV cache 随序列长度线性增长，在长上下文推理中可能主导内存占用，常常超过模型权重本身。对边缘部署来说，在长上下文应用中压缩 KV cache 往往比权重量化更有效；研究表明 KV cache 可以量化到 3 bit 而质量下降可忽略。

MIT HAN Lab 的工作表明，你不需要缓存全部内容，而是要缓存正确的内容。**StreamingLLM** 发现保留”注意力汇聚点”（attention sinks，即最初的若干 token）就能以固定内存实现无限长度生成。**DuoAttention** 发现不同注意力头承担不同职能（检索型 vs 流式型），可以区别处理以同时降低内存和延迟。

压缩策略已经超越了简单的淘汰机制。**ChunkKV** 以语义块而非单个 token 作为压缩单位，在保留语言结构的同时把吞吐比 token 级方法提升 26%。**EvolKV** 用进化搜索寻找每层最优的 cache 预算，在部分任务上仅用原预算的 1.5% 就取得了优于完整 KV cache 的表现。

### 投机解码（Speculative Decoding）

自回归解码本质上是顺序的，一次生成一个 token。投机解码打破了这个瓶颈：用一个小的草稿模型提出多个 token，然后用目标模型并行验证。

有两条主流路线。**Medusa**（Princeton, 2024）增加额外的解码头来同时预测多个未来 token，相比原始解码取得 2.2–3.6 倍加速；原模型保持不变，只微调新增的头。**EAGLE**（SafeAI Lab）通过外推隐状态特征来预测草稿 token，完全不需要微调目标模型，在获得类似加速的同时接受率更高。EAGLE-3 融合低、中、高层语义特征以提升草稿质量。

两者现在都已集成进主流服务框架（vLLM、TensorRT-LLM）。Intel 与魏茨曼研究所（ICML 2025）表明，任意小草稿模型都能加速任意 LLM，与词表差异无关，最高带来 2.8 倍推理加速。Online Speculative Decoding（UC Berkeley, 2025）则在服务过程中持续自适应草稿模型。

对端侧而言，投机解码尤其有吸引力，因为你手上往往本来就有一个更小的模型。草稿模型可以是目标模型的量化或剪枝版本，也可以是专门为投机训练的极小模型。

### 扩散式 LLM

打破顺序瓶颈的另一条路径：扩散式 LLM（LLaDA、SBD、TiDAR）把文本生成当作去噪过程，每一步预测多个 token。它们不是从左到右生成，而是并行地迭代精修所有 token。与投机解码结合后，扩散方法有望比自回归解码快 4–6 倍。该技术仍在成熟中，但早期结果表明它对”延迟比原始吞吐更重要”的端侧场景可能特别有价值。

### 剪枝

剪枝通过移除权重来减小模型体积和计算量，有两种风格：

**非结构化剪枝**（SparseGPT、Wanda）移除单个权重，能达到很高的稀疏率，但要真正获得加速需要稀疏矩阵支持。SparseGPT 可以一次性剪到 50% 稀疏度而无需重训。

**结构化剪枝**（LLM-Pruner、SlimLLM）移除整个通道、注意力头或层。得到的模型在标准硬件上跑得快，但通常需要更仔细的处理来保持质量。SlimLLM 在通道/头级别评估重要性，而不是聚合单个元素。对边缘端来说，结构化剪枝通常更实用，因为大多数移动硬件并不能高效支持稀疏运算。

**协同设计** 方法（Nemotron-Flash、Liquid AI）在延迟与模型精度之间做权衡，以确定模型超参数。搜索空间还可以扩展到包含剪枝、量化甚至基础模块的选择。

### 推理框架

优化技术之外的问题是：到底用什么软件来跑这些模型？这套技术栈已经相当成熟，你不再需要从零开始造一切。

**ExecuTorch**（Meta）在 2025 年 10 月发布 1.0 GA，标志着可用于生产。运行时基础体积仅 50KB，可运行在从微控制器到高端智能手机的各类设备上。它支持 12 个以上硬件后端（Apple、Qualcomm、Arm、MediaTek、Vulkan），HuggingFace 上最流行的边缘 LLM 中超过 80% 可开箱即用。Meta 现在在 Instagram、WhatsApp、Messenger 和 Facebook 上都使用 ExecuTorch，服务数十亿用户。如果你在 PyTorch 生态中，这是自然的选择。

**llama.cpp** 仍然是 CPU 推理的首选。它简单、可移植、持续优化。在没有 GPU 的笔记本、台式机或服务器上跑 LLM，它很难被超越。社区已经支持了远超 LLaMA 的众多模型架构，GGUF 格式也已成为量化模型分发的事实标准。

**MLX**（Apple）针对 Apple Silicon 优化。如果你的目标是 Mac，或者开发流程基于 Mac，它能提供不错的性能和熟悉的类 NumPy API。统一内存让 CPU/GPU 协作更高效。

**MLC-LLM** 把模型编译到多种硬件上部署。当你需要用同一份源码覆盖多个平台时很有用。

我们的建议：按你的部署目标和现有技术栈来选，不要过度纠结——它们都能用。移动端生产用 ExecuTorch，桌面/原型验证用 llama.cpp，Apple 生态用 MLX。

如果你刚开始，可以从 HuggingFace 抓一个量化模型（GGUF 格式的 Llama 3.2 或 Gemma 3），用 llama.cpp 跑起来验证你的场景是否可行，等准备做移动端生产部署时再迁到 ExecuTorch。尽早在真实硬件上做性能剖析；模拟器和仿真器在性能上并不准确。

### 超越文本

上述技术不止适用于语言模型。视觉模型和多模态模型面临同样的约束，也能从同样的方案中受益。

**视觉-语言模型（VLM）** 已大幅缩小。SmolVLM-256M 内存占用不到 1GB，通过优化”哪些视觉 token 才重要”，性能超过了体量为其 300 倍的模型。MiniCPM-V 在手机上运行的同时达到了前沿级性能。FastVLM（Apple）专门针对端侧延迟优化视觉编码器。制胜之道是：把视觉编码器、语言主干和融合机制放在一起协同优化。

**图像生成模型** 现在也能跑在端侧。SnapFusion 和 MobileDiffusion 已让高端手机在一秒内完成图像生成。结合高效的视觉语言模型，端侧图像编辑已成为可能，尽管开销仍然不小。

前面几节的技术（量化、剪枝、高效注意力、KV cache 优化）可以直接迁移。量化后的 VLM 受益于与量化 LLM 相同的离群值处理方式；投机解码适用于任何自回归模型。

**原生多模态模型。** 多模态架构正在向原生方案迁移：所有模态都通过一个轻量的 tokenizer/patchify 层转成 token，共用一个 LM 主干。这一做法在前沿模型上已经流行（Qwen3 Omni、Gemini3）。对端侧而言，原生多模态架构简化了部署——只需一个模型而非多个独立编码器；而共享主干意味着压缩技术可以在各模态间统一应用。

### 面向端侧的训练

端侧推理吸引了大部分注意力，但训练效率决定了谁有能力在一开始就造出这些模型。

### 让预训练平民化

过去认为完整预训练需要庞大的 GPU 集群。这个假设正在被打破。

APOLLO（我们的工作）表明 Adam 的逐参数自适应是过度设计。在通道或张量级别做学习率缩放就能捕获大部分收益。通过投影到一个低秩辅助空间，APOLLO 以 SGD 级的内存达到了 AdamW 级的性能。GaLore（UC Berkeley）独立地发现了类似方法。实际影响是：在单张 12GB GPU 上从头训练 LLaMA-7B——两年前这需要八张 A100。对端侧来说，这扩大了能够创造高效模型的群体。更多团队参与训练，意味着面向边缘部署的架构空间会被更充分地探索。

### 微调

如果你是在适配已有模型而非从头训练，LoRA 及其变体是标准做法。只训练低秩适配器、冻结基座模型，你就能在消费级硬件上微调。

变体已经很多。**QLoRA** 把基座模型保持在 4-bit，而以更高精度训练 LoRA 适配器，使得在单卡上微调 7B+ 模型成为可能。**DoRA**（2024）把权重分解为幅值和方向，两者都微调，其中方向部分使用 LoRA。DoRA 在各种 rank 设置下都稳定优于 LoRA，且在低 rank 下增益更大。**RoRA**（2025 年 1 月）优化缩放因子，把 α/r 替换为 α/√r，使得 rank 增大时表现更好。

对大多数实践者来说，微调是那条路。基座模型已经足够好，价值增量来自对你自己领域或任务的适配。

### 下一步是什么

### 边缘端的 MoE

混合专家用小模型的算力提供大模型的能力，但边缘部署仍然困难。问题在于：即便是稀疏激活，你仍然必须存下所有专家。对 Mixtral-8x7B 这类模型，在消费级硬件上专家加载会主导推理时间——计算很快，内存搬运不快。

EdgeMoE 把专家切分到外部存储，只在被激活时取回，内存降低 5–18%，推理提速 1.2–2.7 倍。协同压缩已把 DeepSeek-V3 从 1.3TB 压到 103GB，手段是专家剪枝加混合精度量化。但这些都还是早期方案。真正让 MoE 在移动端实用（10W 以内、8GB 以内）的架构，目前还不存在。

### 小模型的测试时计算

一个反直觉的发现：小模型可以通过在推理时投入更多算力来超越大模型。HuggingFace 展示了 Llama 3.2 1B 配合 Diverse Verifier Tree Search 超过 8B 模型；Llama 3.2 3B 超过 70B。关键在于计算最优的推理策略：树搜索、自我验证和自适应采样。

对端侧来说，你受限于模型体积，但对高价值查询而言推理预算未必受限。一个”想得更久”的 1B 模型可能击败一个”立刻回答”的 7B 模型。这个方向仍在快速发展，但含义很重要：小模型的能力天花板可能高于其参数量所暗示的水平。

### 端侧个性化

在设备上微调可以实现个性化，既不必把数据传到云端训练，也不必通过冗长 prompt 提供大量上下文。吸引力很明显：你的设备学习你的偏好、写作风格和领域词汇，而这些数据从不离开设备。一个有意思的方向是测试时训练（test-time training）：通过在测试时对自监督任务做优化，让模型把用户上下文迁移进权重。

### 新颖架构

除 MoE 和注意力机制改进之外，一些新架构也在涌现，它们无需增加参数就能提升性能。近期的 ManifoldHC、HyperConnections 以及 Conditional Memory via Scalable Lookup 等创新，展现了在固定参数预算下提升模型质量的潜力。
