### 一、LLM 侧：统一内存在收口

如果只看 release note，你会觉得这个月 LLM 侧没什么大事。但把提交按主题聚起来看，会发现工作量最大的一摊是”统一内存”，而且它几乎不产出任何可宣传的指标。

背景是这样的：SGLang 原本的 KV cache 是按模型特判的。MLA 一套逻辑，SWA 一套，Mamba 类又一套，容量规划和参数调优基本每个模型各来一遍。随着模型结构和并行策略的组合变多，这套打补丁的方式越来越难维护。

这个月在做的，是把它收敛成”一个池子 + 一套容量模型”。具体动作包括：

- 给 Mamba 和混合 SWA 模型划独立子池，容量按 byte 计，配了可行性下界和守恒校验器（#35177、#35158）
- 给 uniform-row 的 MHA / SWA 模型做 dense KV view（#34602）
- 让 fa3、flashinfer、trtllm_mha、flashmla 四家 attention 后端都能直接读统一池（#34613）
- decode context parallelism 覆盖 trtllm_mla 家族与 Kimi-Linear（#37693、#36890）
- prefill 阶段也能做 CUDA graph 捕获（#37418）
- 任意池形状下都能做 PD 分离（#37506）
- 投机解码的 draft KV 接进统一外部 linker，MTP / EAGLE / DSpark 都在内（#37914）
- AMD 上 DeepSeek-V4 的 unified KV 走直连外部 linker（#38269）

我的判断是，这件事会显著影响使用体验，但短期没人会注意到。它的收益体现在：以后换模型或换 attention 变体时，显存规划从”每换一次算一次”变成”算一次全用上”。

从工程信号上看，**一个推理框架开始做这种纯粹的重构而不是加特性，通常意味着它在为现有架构撑不住的模型形态铺路。** MLA、SWA、Mamba、混合注意力、投机解码这几样要同时存在，靠组合补丁是撑不住的。

### 投机解码：组合变多了，但缺口也是真的

这个月的关键词是”组合能力”。

投机 worker 支持 stage prefill 的 shared reads（#38554）。DFlash 的 Mamba state 开始按 checkpoint 边界追踪，修的是状态漂移（#37818）。DSpark 有个共享专家融合的 guard 被静默影响，也修了（#39366）。

这里我想多说一句关于 bug 类型的观察。**在推理框架里，静默产生错误结果的 bug 比崩溃麻烦得多。** 崩溃至少会有人发现，而那个 guard 的问题只会让结果慢慢偏离，测试如果只做 smoke test 根本抓不到。这个月还有好几个同类的，比如 `fast_topk_v2` 在 radix 阈值桶超限时返回错误的 top-k 集合（#36807），以及 DSpark 强制 reject 并非无损、GDN 状态相对 Base decode 存在累积漂移（#35150）。

DFLASH2 落到昇腾 NPU（#35629）。Cookbook 层面，DSpark 已经是 DeepSeek-V4 和 GLM-5.3 的推荐配置。

但缺口是明确的：**投机解码在 PD 分离下目前跑不通。** 社区有个 issue 在追 DFLASH 在 PD 场景下 `spec_info` 为 None 的崩溃（#36140）。如果你正在用这个组合，升级前务必回归测试。

### DCP 和几个危险的边界 bug

DCP（decode context parallelism）是这个月扩张最快的子方向之一。AMD 的 aiter 后端接上 DCP（#34432），默认通信后端改成自动解析（#39165），DCP1 到 DCP-N 的 relayout 也支持了（#37709）。

同时修掉一批”平时看不见、触发就是事故”的问题：

- KV row 释放时 mid-page 拆分导致 double free（#38941）
- MLA retraction 的 CPU backup/restore 里 widened KV id 没有本地化（#39487）
- DeepSeek V4 读 K cache 位置前不等 PDL（#38409）

这类问题集中在月底冒出来， DCP + HiCache + 投机解码这套组合最近才被大规模真实负载压到，边界条件正在被踩出来。这也侧面说明新特性从”能跑”到”稳”之间还有一段距离，我自己在部署 kimi-k3 的时候就踩坑了。

### 模型与量化：NVFP4 站稳了

新增支持里，Mamba 2 和 Mamba 1 可以单独说一句（#34556）。状态空间模型正式进了 SGLang 的推理支持范围。这个方向在长序列推理上有理论优势，业界关注度一直不低，但工程落地一直偏弱，现在算是有个正经的实现可用了。

其他新面孔：GLM-5.3-Flash（DSA 架构）与 NVFP4 加载（#38621）、Qwen3.8-Flash-Next 的 NVFP4 导出与 DGX Spark / RTX PRO 6000 recipe（#37995）、DeepSeek-V4.1 Flash cookbook（#38802）、Nanbeige4.2（#32151）、IFM K2 Horizon（#37654）、Ling-3.0-flash-VL（#38434）、GraniteMoE 分专家量化加载（#37679）。

讨论最热的 PR 是把 TensorRT-LLM 的 DeepSeek-V4 attention 实现集成进来，覆盖 SM100/103（#30805），82 条评论。**把别家已经调好的 kernel 直接接进来，而不是自己再实现一遍，这个取舍我认为是对的。** 注意力 kernel 的调优是重资产投入，重复造轮子的边际收益很低。

量化格局已经很清楚了：Blackwell 用 NVFP4，AMD MI355X 用 MXFP4，Hopper 继续 FP8。标题里出现 NVFP4 的提交 35 条。

更有意思的是做法的变化。以前是”把权重量化成 FP4”，现在是”把量化节点和它前后的算子融进同一个 kernel 的 epilogue”。这个月大量 “Fuse XXX + NVFP4 quantization” 类的提交都在做这个。这种融合的收益只有在特定架构（Blackwell 的 tcgen05、Hopper 的特定路径）上才明显，所以你能看到同一份逻辑针对不同架构各写一遍。

### 二、Diffusion 侧：一年时间从”能跑”到”抠毫秒”

Diffusion 是这个月最大的单一主题，278 条提交。代码在 `pythonPythonpython/sglang/multimodal_gen`，40 个 pipeline 实现，模型目录 35 个条目，覆盖图像、视频、3D、VLA 和世界模型。

但比模型数量更有意思的是，它用的优化方法论和 LLM 完全同构。

### 量化与融合，几乎是 LLM 那套的复印件

Qwen-Image 这条线抠得最细：residual norm 融 NVFP4（#37129）、FP8 QKV 投影加 Blackwell epilogue（#37123）、最终 adaptive LayerNorm 融合（#37144）、FP8 norm 与激活量化（#37156）、输出投影 bias 吸收（#37116）、跨 CFG 分支复用 modulation（#37090）、Hopper 上 Edit 的 attention 优化（#38584）、TP 通信优化（#36680）。

FLUX.2：NVFP4 的 FC1 + SwiGLU + FC2 三层融合（#37096）、ModelOpt FP8 producer 与 QKV packing（#37162）、token 拼接与 NVFP4 量化融合（#37141）、Blackwell 上 gated residual norm（#37112）。

Wan2.2：Blackwell 上 NVFP4 bias + GELU 融合（#37075）、VAE decoder 保持 channels_last 并改用 Triton 做 NHWC 最近邻上采样（#38182）。而且 Wan 的 VAE decoder 快路径被移植到了 Qwen-Image 的 VAE 上（#38020）——这个复用动作很典型，说明这些优化已经开始沉淀成可迁移的资产了。

另外 SANA-WM 优化了 conv 后处理和 streaming GDN（#38529），FLUX.1-dev 开了无损 BCG（#38591）。

套路说白了就三件事：量化、融合、针对具体架构写 epilogue。没什么新东西，但管用。

### 单卡跑大视频模型这件事，靠的是 offload

标题里带 offload 的 17 条提交，做的东西很具体：

- layerwise 的 host store 原地 pin 住，不浪费空间（#39021）
- host 缓存不下时直接读 mapped layers（#39022）
- 用共享的 host/device 池流式加载权重（#38441）
- 大张量像 numpy 一样 spill 到共享内存（#38656）
- 干掉直接的 GPU 参数拷贝（#36832）

再往上一层是”组件驻留”这套抽象：snapshot-offload、显式驻留、精确到组件的精度覆盖（#38535、#36991、#36907），甚至专门做了一套工具去实测每个阶段的 warmup 内存和层使用情况，用来给驻留策略做校准（#37916）。

这实际上是把 LLM 侧积累了好几年的 layerwise offload 经验整体搬了过来。**Diffusion 模型的显存压力比 LLM 大得多**（视频模型的激活和 VAE 都是显存杀手），所以这套东西在 Diffusion 上反而更有价值。

### 往消费级硬件走

有条提交我挺喜欢：给 RTX 5090 单独做了一份 H3 recipe，而且强调是在一台真实物理台式机上实测的（#39373）。

我个人认为这条的象征意义大于技术意义。**它说明 Diffusion 推理的部署正在从数据中心往消费级显卡和桌面工作站迁移。** 同期还有一批 SM120 相关的适配：SubBlock 稀疏注意力支持 SM120（#37332）和 SM90（#37982）、修 nvfp4 在 sm_120 上的问题（#35739）、把 decode cuda-graph 的 max_bs 从 24 提到 48、chunked_prefill 从 2k 提到 4k（#37898）。

多硬件覆盖也在推：昇腾 NPU 上跑 MiniMax-H3（#33569）、LTX-2⁄2.3 的 NPU 性能优化（#34722）、Intel XPU 上跑 MiniMax-H3（#33366）、Xeon CPU 上也能跑（#35147）、AMD 把 FlyDSL 融合 norm kernel 迁到稳定 API（#36349）。

### MiniMax-H3 撑起了一个小生态

标题里提到 MiniMax 的提交有 47 条，绝大多数是 H3。

新增了 singularity hybrid checkpoint（#38455）和 VDN-H3，后者带了一个新的 `hybrid_window_attn_h3` 后端（#37903）。我认为最有价值的是 FastH3——4 步蒸馏版本，配 VSA-H3 attention 后端（#37480）。**4 步出视频对端侧部署的意义远大于云端**，如果这个路线成熟，实时生成的场景会打开。

稀疏注意力上有 cube sparse attention（#34893）和 spargeattention（#37437）。量化侧支持了混合 INT8 embedding 加 Comfy NVFP4 编码器（#38506），还有分层 AdaLN plan cache（#37266）。

其他还有 LTX-2.3 / 2.5、SenseNova-U1.5-8B-MoT（#36606，讨论比较多的一个新模型）、Cosmos3 的 FP8 混合精度（#36380），以及 Wan、FLUX、Qwen-Image、Pi0.5（VLA）、Hunyuan3D、MOVA 等一批的持续维护。

### 一个我认为最重要的架构变化

Diffusion 在大量复用 LLM runtime 的组件：RoPE 统一到了 `RotaryEmbedding` 的 CustomOp 实现（#33555）、CLIP / SigLIP / Qwen3-VL 编码器直接复用 SRT 的、attention 后端统一并约束了回退策略。

SGLang 想要的应该是一套 runtime 同时服务 LLM 和 Diffusion，没必要给 Diffusion 单独维护一个框架。

从工程经济学上看这个选择是对的。融合算子、量化框架、显存管理和图捕获这些东西跟模型语义无关，在 LLM 上验证过的优化搬到 Diffusion 上几乎不需要重新验证。反过来，Diffusion 逼出来的显存技巧（大张量 spill、组件级驻留）未来也可能反哺 LLM 侧。

### 三、issue 里的真实世界

数据是骨架，issue 才是一个项目真实的样子。我按性质分了三类。

**正确性类（最该警惕）**

- `fast_topk_v2` 在 radix 阈值桶超限时静默返回错误的 top-k 集合（#36807）
- Qwen3.8-Flash-Next 的 thinking 配 qwen3_coder 工具解析器，在 token ID 0 上死循环（#36537，本月讨论最多的 bug，15 条）
- GLM-5.3-Flash 走 HiCache host 层回读会损坏生成内容，即使没开投机（#38031）
- QSA extend forward 在 8 并发下 CUDA illegal memory access（#37633）
- DSpark 强制 reject 并非无损，GDN 状态相对 Base decode 有累积漂移（#35150）

**性能与稳定性类**

- 统一缓存默认值翻转后，DGX Spark 和 Thor 上长前缀 decode 吞吐回退（#36131）
- B300 上 MXFP8FP4 / W4A8 的 MegaMoE 路径出 CUDA illegal address（#37559）
- NVFP4 MoE 走 Marlin fallback 时每层泄漏约 0.66 GiB（#38074）
- `tiny_gemm` 在 Blackwell 上让 DeepSeek-R1 NVFP4 decode 变慢——单 kernel 更快但端到端更慢（#38628）
- GGUF I-quant 缺 MMQ kernel，prefill 比 llama.cpp 慢 4~6 倍（#35019）
- GB10 上超过 40k token 的长 prefill 会耗尽统一内存并静默杀死 worker rank（#36941）
- SM121 上 QSA decode 没有可用 kernel 路径，Qwen3.8-Flash-Next 无法服务（#36558）

`tiny_gemm` 那个我特别想拎出来说。**单算子更快但端到端更慢，这在推理优化里是极常见的陷阱。** 融合、量化、换 kernel，每一个动作的收益都要放在完整链路里看，不能只看 microbenchmark。这条 issue 值得所有做推理优化的人引以为戒。

**RFC 与路线图（下一步的大动作）**

本月讨论最多的 RFC 是 HiCache 的进程外数据面加设备内存 IPC（#37372，10 条）。其他有分量的包括：Gluon MegaMoE 的集成与多机支持、KV Hint Envelope（#36224）、量化模块布局重构（#38004）、KV Cache 压缩 API（#36522）、per-token-range 的 KV 保留优先级（#36208）、昇腾 MemCache 作为 HiCache L3 后端（#35620）。

长期路线图层面，比较重要的几份：面向 agentic 负载的分布式 KVCache 系统、Context Parallelism（2026 Q3）、Pipeline Parallelism、Fast Engine Recovery 的 Weight Cache Daemon（#33522）、Apple 设备支持、dLLM Serving。AMD 的 2026 Q3 路线图（#35003）是这个月 reaction 最高的 issue，13 个赞。

`Weight Cache Daemon` 这条我建议做推理服务的同学关注一下。推理服务的弹性扩缩容，最慢的一环通常是新实例加载权重，如果能把这块做成常驻缓存服务，冷启动时间会有数量级的改善。

### 四、给算法工程师的几点建议

**1. 如果你的场景涉及长上下文或多轮 Agent，盯住统一内存和 KV 归属这条线。**

KV block 按 session 归属（#37482）、分布式 KVCache 路线图、per-token-range 保留优先级，这些东西会直接影响你的缓存命中率和调度策略。现在 RFC 还开着，是介入讨论的好时机。

**2. 做视频或图像生成的话，别自己写 kernel 了。**

Diffusion 侧的融合和量化基本每周都在合，自研 kernel 的收益下降很快。把精力放在模型结构和质量与速度的权衡上性价比更高。如果要用 FastH3 这类蒸馏路线，收益会比你自己抠 kernel 大得多。

**3. 选硬件时注意量化路线的分叉。**

Blackwell 对应 NVFP4，MI355X 对应 MXFP4，Hopper 对应 FP8。这三条线的 kernel 成熟度差异是真实存在的，会直接影响你的可用吞吐。SGLang 的 cookbook 在逐机型给实测数据（B200/B300/GB300/DGX Spark/RTX 5090 等），**选型时建议先查对应机型的 cookbook，而不是看通用 benchmark。**

**4. 升级版本前，对核心负载做回归。**

这个月有明确的例子：统一缓存默认值翻转，在特定硬件上让长前缀吞吐退化了。推理框架迭代快，默认值不等于对你更优。
