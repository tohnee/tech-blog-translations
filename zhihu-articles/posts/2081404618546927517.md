### 本体论是什么？

它本身是哲学的一个分支，用来讨论事物的本质，即 **是什么？**

本体论中有诸多复杂的概念，但核心的就只有下面这些：

- 类/子类：代表某一类实体的定义，拥有哪些属性，以及实体间的关系
- 实例：类的具象化，属性包含实际的值
- 约束：某个属性不可违背的规则，伪代码可以写作 IF..THEN
- 公理：就是大家都认为对的东西

当然我们今天不是来讨论哲学的，你只需要知道本体论是一套研究“是什么”的方法论即可，基于本体论的 RAG 只是借用了它最核心的部分。

不过在进一步分享之前，不妨先停下来看下传统 RAG 方案的短板在哪里，这样有助于我们更好的理解本体论到底能解决什么问题。

### 向量检索有哪些不足？

向量检索也可以被称作语义化检索，它的工作原理主要基于点积运算，并最终算出向量间的余弦相似度，值越接近，则两个向量所表示的语义也越相似。

但它并不是完美的，因为 **相似** 没有办法清晰表达 **互斥** 、 **否定** 以及 **阈值** 等逻辑。

先看一个否定场景，比如用户问：

> 这个商品可以通过信用卡购买吗？

而 FAQ 文档里有这么两段（括号中是和问题的相似度，基于 qwen text-embedding-v2）：

> **段落 A：** 商品可以通过信用卡购买，支持信用卡与借记卡在线结账（0.772） 
>  **段落 B：** 部分商品（如礼品卡、特定促销品）仅支持 FPX， **不** 支持信用卡结账。（0.410）

在向量空间中，段落 A 和段落 B 实际上是比较相似的，同时，段落 A 与问题的相似度也更高，Agent 按相似度排序时，都会优先将段落 A 当作更可信的语料。

互斥与否定同理，不再展开，再看一个阈值场景：

> 88 元可以分期买吗？

FAQ 中的语料如下：

> **段落 A：** 可以分期买，3 期或 6 期都行，没有手续费，用银行卡支付（0.609） 
>  **段落 B：** 3 期最低 100 元，6 期最低 1500 元（0.341）

向量按相似度命中段落 A，因为”分期、银行卡、支付”与问题相关性更高，但正确答案实际上在段落 B 中，但因为它仅包含阈值类声明，在向量空间中，它与问题的相关度远低于段落 A。

这两个例子都可以说明，向量检索不是万能的，有些场景下，越相近，反而越有可能南辕北辙。

![](https://pic1.zhimg.com/v2-879e2dbce5a337857e983f13988998e2_r.jpg)

### GraphRAG 很好，但还不够

为了解决上面的问题，当前主流的解决方案是引入图这种数据结构，并用它来储存语料间的关系。这样，检索的对象就从语料本身，变成了语料之间的关系，之后 Agent 则可以根据这些关系，推理出语料之间的逻辑关系（否定、阈值等）。

这种模式当前被称作 GraphRAG，它不仅会捕获语料间的关系，还会进一步提取出语料中的实体，并对实体进行分类，再按照最佳实践分析它们之间的关系。

但 GraphRAG 也是有短板的，它没有办法很好地区分 **互斥** 场景，因为经过多跳查询，只要是有关联的实体，在 Agent 看来，就是有关系的，但现实往往不是如此。

举个例子，比如用户问”两张优惠券可以一起用吗？”，在图中，两张券和同一笔订单都能关联上，多跳路径是通的，但每笔订单限用一张。这便是互斥关系：关联存在，不等于规则允许同时使用。

GraphRAG 这类自动抽取的图谱，不会主动把互斥抽取成显式关系，关系路径存在，不等于它告诉了你选了 A 就不能选 B。

另一个场景是，GraphRAG 也可能会犯”你想要的是一根香蕉，但你得到的却是一只拿着香蕉的大猩猩，以及整片丛林”这样的错误：如果你没有设置合理的多跳查询上限，Agent 可能会查询出过多与当前上下文可能相关的关系和节点，但并不是所有信息对于 Agent 来说，都是有价值的。

![](https://pica.zhimg.com/v2-49821bbeab01f0974df248fd0f02ef12_r.jpg)

因此，GraphRAG 虽然可以告诉你可能的关系有哪些，但是它不会帮你筛选，也不会告诉你哪些满足某个条件，哪些不满足，而这些对于规则类的查询场景，往往是十分重要的。

### Agent 的不可替代性在于推理

上一节中，GraphRAG 把一堆关系交给了 Agent，但这恰恰说明，Agent 的价值不在它接收了多少信息，而在它能不能在信息之间推理。而推理能不能发生，取决于它有没有反馈。

据我观察，虽然当下 AI 已经成为了每个人生活中的一部分，但能很好地利用 AI 推理能力去解决问题的人是很少的。它的不可替代性不在”读得多”、”写得快”，而在于会 **推理** ，就和人一样，举一反三，因此，当你抱怨 AI 不好用的时候，可能也应该仔细想一下，是不是它根本就没有机会收到任何反馈信息，从而可以引导它自己去寻找正确答案呢？

编程场景下，这种做法已经很常见了，比如单元测试和静态代码分析并不告诉 AI “正确答案是什么”，它们只会给一个信号： **你生成的东西，在这里是错的，问题就出在这里** 。然后根据这些失败信息，AI 会自己推理并改出正确的版本，并最终完成任务。

业务场景是一样的。与其给 AI 一摞正确答案，不如给它 **错误的边界以及约束条件** ，比如:

- 这些情况不行
- 这些约束存在
- 这条规则违反会怎样
- …

![](https://pic3.zhimg.com/v2-047af09bae159f34488f5c43c2f67262_r.jpg)

当收到这些反馈时，同样地，AI 会在边界内自己推理出正确的答案。

举个例子，还是前面的场景：用户问”88 元可以分期买吗”，我们不把”最低消费”当答案告诉它，而是让校验层返回：”拒绝，3 期最低 100 元”。AI 拿到这条负反馈之后，自己就会生成”金额不达标”的回答，哪怕没有任何知识库语料明确声明这点。

约束的成本是有限的，而正确答案的空间是无限的，别教 AI 什么是对的，去告诉它什么是错的。

### 基于超图的本体知识图谱

[ograg2](https://github.com/microsoft/ograg2) 正是用”超图”配合本体论，来解决上一节提到的多跳查询痛点。

超图相比较普通图来说，一条边可以同时连接任意多个节点，超就超在这个地方，二元关系变为了多元关系。

如果把边当作描述性事实，一条超边所连接的所有节点就构成了一组参考依据，而在普通图中，类似的抽象是需要多条边构成的。

![](https://pic3.zhimg.com/v2-2b8d8cfad39ea60165a1af20cd7644e4_r.jpg)

超图好就好在：一条超边就是一组高内聚的完整上下文，多个节点被同一条事实绑在一起，Agent 不用在中途逐跳拼接，也就不会被不相关的节点带偏。

这条超边的本质，来源于一份人工维护的 JSON-LD schema。它只声明”作物有哪些属性、每个属性是什么类型”，本身不携带任何业务约束。LLM 要做的是把文档内容按这些槽位填充成结构化数据，一条填充结果就是超图里的一条超边。

上图示例所对应的 schema 定义如下：

```json
{
  "@context": {
    "cropCult": "http://crop-cultivation.org/",
    "schema": "http://schema.org/"
  },
  "@graph": [
    {
      "@id": "cropCult:Crop",
      "@type": "schema:Thing",
      "name": { "@type": "schema:Text" },
      "has_temperature_requirements": { "@type": "schema:Text" },
      "seed_germination_test": { "@type": "schema:Text" }
    }
  ]
}
```

而它对应的本体实例 soybean 是：

```json
{ 
  name: "soybean",
  has_temperature_requirements: "25°C – 30°C（发芽期）",
  seed_germination_test: "required" 
}
```

当模型获取到这组节点，并用它回答”大豆能在 35°C 以上的环境发芽吗？”时，就能给出否定结论：超边声明的发芽温度是 25°C – 30°C，35°C 已经越过了上限，所以大豆不会发芽。

### 基于本体校验的 guardrail

[ontology-rag-firewall](https://github.com/cloudbadal007/ontology-rag-firewall) 是通过本体校验的方式来使用本体论的。

它的原理也非常简单，在检索/抽取之后、Agent 采取行动之前，插入一道确定性规则闸门（guardrail），解决的是”内容找到了、但正确性没被验证”的问题。

它和上一章的 ograg2 走的是相反的路：ograg2 在检索侧做文章，它则在行动前设一道闸。两条路不互斥，可以叠着用。

这里也直接引用官方仓库原文进行说明：

> *RAG pipelines retrieve text. They do not validate meaning. GraphRAG retrieves facts — and still does not validate meaning.*

它适合答错代价极高的场景，比如企业合同审核，涉及责任条款、付款期限、SLA、自动续约。

以合同场景为例子，完整流程如下：

![](https://pic4.zhimg.com/v2-9fd03fcb47cc9cf156b576b04967b1b3_r.jpg)

RDF Builder 和 SHACL Validator 消费的是 Extractor 抽出的同一份 JSON，中间没有第二次抽取。

其中利用到本体论的部分是 RDF Builder 和 SHACL Validator，这里先简单介绍下 RDF 和 SHACL，以及未提及的 OWL：

- OWL：Web Ontology Language，定义类与属性的语言，只声明”有哪些类、类间什么关系”（TBox），仓库里 `ontologies/contract_domain_owl.ttl` 就是这一层
- RDF：Resource Description Framework，”主语-谓语-宾语”三元组，存放本体实例（ABox），RDF Builder 输出的就是它
- SHACL：Shapes Constraint Language，声明约束规则的语言， `ontologies/contract_domain_shacl.ttl` 里是预定义好的校验形状

基于这些规范和标准，最终的 Validator 判定的是抽取结果本身合不合规，并输出 `safe_to_act` ，它表示 Agent 能不能照这份合同行动。

### 怎样判定你真的需要本体论？

以上两种实践虽然看起来很完美，但凡事都是有代价的，本体论也不意外。

最明显的代价在于，它需要消耗一定程度的 **人工** 维护成本，注意，我专门加粗了人工。原因很简单：本体里的类是公理和事实，必须保证 100% 正确。AI 可以帮你起草类、属性这些骨架，但最终拍板的人，只能是人工。

所以使用本体论之前，先回答下面 5 个问题，它们共同衡量一件事：这个域该不该上本体、人工维护成本扛不扛得住。每问 0 到 2 分，代表程度低、中、高：

1. **有硬约束吗？** 答案是不是”能/不能、最低多少、能不能叠加”这类 IF-THEN 规则。如果没有规则，那本体自然也就无法被定义。
2. **变化慢吗？** 规则之所以是规则，就是因为不会天天变，如果是类似促销价这种天天变的，本体还没被定义出来，规则就过期了。
3. **有权威源头吗？** 是否有权威参考，可以是专家或者是文档，它们可以裁决”哪些是对的、哪些是错的”。如果没有权威源，就没办法评估真实性，本体定义也就失去了意义。
4. **答错代价大吗？** 金额、资格、合规相关的问题，答错是要出事儿的，而公司简介的话，明显说错也无伤大雅。
5. **术语受控吗？** 一个领域内的某个概念是否有唯一的术语，而不是多种称呼，比如”分期付款”不会今天叫”分期购物”明天叫”延后付款”。如果术语不固定，本体类自然也就无法做到唯一。

按 10 分制来算：8 分及以上，非常适合上本体；4 到 7 分，掂量掂量再说；低于 4 分，大概率你并不需要它。

举个例子，就拿分期付款这个场景来打分：

1. 首先能不能分期、是否达到门槛，这些规则都是算硬约束，打 2 分
2. 分期付款通常和银行的流程绑定，相对固定，打 2 分
3. 银行是权威源头，打 2 分
4. 涉及钱的无小事，打 2 分
5. 这块可能不同的银行之间是有差异性的，因此打 1 分

综上算起来是 9 分，所以分期付款这个业务场景，就非常适合用本体论。

再看下公司简介：

1. 公司简介基本都是描述性的文本，没有所谓的能不能、行不行，打 0 分
2. 如果大公司可能会比较慢，小公司的话就不一定了，甚至一些通知、活动可能经常会变化，因此打 1 分
3. 可能只有邮箱、电话等是权威信息，大部分是谈不上权威的，打 1 分
4. 和第 3 条同理，名称、邮箱、电话对了就行，打 1 分
5. 描述性文本中没有过多的术语，打 0 分

加起来只有 3 分，所以公司简介的话，仅使用向量检索通过语义查询就可以满足。

同时，有些业务场景即使分数很高，也必须在业务流程里由人工参与，比如售后相关的场景。这种情况下，上本体不会带来任何收益，因为这类场景的可信源头，本来就是人工判定。

### 虽然但是，本体也会变成债务

当你使用了本体论之后，可能初期会发现效果非常好，但如果稍不注意或者没有持续投入维护成本，它马上就会变成债务。

最常见的有三个坑。

第一个是 **本体腐化** 。业务规则改了，本体里的类定义没跟着改，半年之后它还在按旧规则回答。本体本身即代表公理和事实，所以 Agent 自然会把错误当作事实，这本身会比没有本体变得更糟。

第二个是 **过度设计** 。本来 10 条规则就能覆盖的场景，非要建成百科级的本体，类、属性、关系层层叠叠，维护成本远超当初写 10 条规则该花的工时。怎么算过度？建模花的工时比业务本身还多，就是了。

还有一个更隐蔽的坑： **规则变更过快** 。促销价天天改，本体却要人工逐条维护，维护周期永远追不上业务周期。你会发现，上一章五问里”变化慢吗”打低分的域，如果你非要使用本体论，那它从一开始，就已经成为了你的技术债。

![](https://pic4.zhimg.com/v2-72af1f99061c714240bcf2399b4c4323_r.jpg)

所以，人工维护成本才是本体的真成本。一旦本体不再产生价值，维护的每一分投入都在变成债务，这时候，砍掉才是更理智的选择。

### benchmark 对比

下面这个表格对比了不同 RAG 方案的正确率指标，详见 [DEMO](https://github.com/haoliangwu/diagrams/tree/main/ontology-rag/demos) 。

DEMO 中的文档、语料以及问题，有以下三个预设条件：

- **权威事实层等于人工治理的结果态** ，知识图谱、超图以及校验器均是手工构造，而非 LLM 生成
- **禁止 AI 自主纠错** ，通过在 prompt 声明”原样采用片段、不得自行纠错”是为了控制变量，刻意隔离检索缺陷。
- **刻意在语料中埋坑** ，挑选了向量相似度和语义相反的语料和问题

虽然测试数据是刻意设计的，但它们所代表的问题和挑战，在现实中是会真正出现的。

结果如下（详细结果可 [参考](https://github.com/haoliangwu/diagrams/blob/main/ontology-rag/demos/compare_results.md) ）：

| 问题 | original RAG | graph-rag | og-rag | 本体校验 |
| --- | --- | --- | --- | --- |
| Q1 信用卡分期最长可以分多少期? | ✗ | ✓ | ✓ | 拦截 R1 → 合✓·对✓ |
| Q2 Nova X1 只要 88 元吗? | ✗ | ✓ | ✓ | 拦截 R2 → 合✓·对✓ |
| Q3 手机激活之后还能退货吗? | ✗ | ✓ | ✓ | 拦截 R3 → 合✓·对✓ |
| Q4 店铺券和平台券能一起用吗? | ✗ | ✗ | ✓ | 拦截 R4 → 合✓·对✓ |
| Q5 Nova Store 支持哪些支付方式? | ✓ | ✓ | ✓ | PASS |

可以发现，普通 RAG 的正确率只有 20%，使用 GraphRAG 会变成 80%，再配合本体论，最终可以达到 100%。

虽然是 DEMO，但一定程度上可以说明，本体论也许真的是 RAG 的最后一公里。
