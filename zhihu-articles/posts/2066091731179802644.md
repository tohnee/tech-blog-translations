### 先说两句前情

前面我成功将[端侧模型内存占用从2GB优化到500MB](https://blog.csdn.net/lanchifeiyang/article/details/162088322)，本以为"能跑起来就万事大吉"。直到评论区灵魂拷问：“内存降了，但跑一次要5秒，用户等得起吗？”

上线后的数据印证了这个问题——用户打开 AI 功能，盯着转圈三四秒就离开，留存率直线下滑。内存优化解决了"能不能跑"的问题，但**5秒的等待时间正在杀死用户体验**。

所以这篇聊聊——内存降下来之后，怎么让推理速度跟上，通过三层优化将用户感知延迟从 5 秒压缩到 2 秒以内。

## 端侧推理到底慢在哪

先说清楚一件事：端侧推理慢，不是因为浏览器不行。

Chrome 的 V8 引擎跑 JavaScript 已经很快了，但问题是——**大语言模型推理是计算密集型任务，CPU 这种通用处理器不适合干这个活。**

你可以理解成：

- CPU 是"一个什么都会的师傅"，但一次只能干一件事
- GPU 是"一百个只会干一件事的学徒"，但可以同时干一百件事

Transformer 推理的核心是矩阵乘法，这玩意儿天然适合 GPU 并行计算。但浏览器里跑模型，默认走的是 CPU 上的 WebAssembly 路径——单线程或者有限多线程，算力天花板很低。

所以端侧推理的瓶颈就一句话：**算力不够，而且用错了硬件。**

我之前试过一个小模型（Qwen2.5-1.5B INT4），在 CPU 上推理大概每秒能吐 8 到 10 个 token。听起来还行？但生成一段一百来个 token 的回答，用户要等 10 秒以上。你让用户等 10 秒，他不走才怪。

那 WebGPU 呢？理论上能跑在 GPU 上，算力翻几倍不是问题。但实际用起来，坑比想象的多。

## 第一个翻车：WebGPU 在低端机上比 CPU 还慢

这个翻车让我印象很深。

第一次接 WebGPU backend 的时候，我信心满满——WebGPU 嘛，GPU 加速，肯定比 CPU 快一个数量级。跑 benchmark 之前我还特意跟同事说，“你看着，这波肯定起飞”。

结果跑出来，CPU 路径每秒能吐将近 10 个 token，WebGPU 路径只有个位数。

**还慢了。**

当场打脸。

排查了一圈，发现根因是：**低端 GPU 的显存带宽不够，模型权重在 CPU 内存和 GPU 显存之间来回拷贝，开销比计算本身还大。**

你可以做个简单的类比。你有一个工具箱（模型权重），放在厨房（CPU 内存）里。你要用的时候，每次得把整个工具箱搬到车库（GPU 显存）去。搬一次几十斤，你搬过去了，干活（推理）只用了十几秒，然后又得搬回来。搬来搬去的时间，比干活的时间还长。

在我的测试环境里，低端 GPU（Intel UHD Graphics）的推理计算本身只占了不到一半的时间，剩下大半都在数据传输上。

**结论：WebGPU 不是万能的。低端设备上，老老实实走 CPU 反而更快。**

这个坑让我意识到——性能优化不能"一招鲜"，得看设备下菜碟。

## 第一层：硬加速——让 GPU 在合适的设备上干活

先说清楚这一点：**WebGPU 在中高端设备上效果很明显。**

我在一台搭载 M1 芯片的 MacBook Air 上测了同一个模型，WebGPU 路径比 CPU 快了差不多一倍。从每秒不到 10 个 token 干到了每秒将近 20 个 token。生成一段一百来个 token 的回答，用户从等 10 秒变成等 5 秒——体验提升了一个档次。

WebGPU 的 API 设计可以参考 [W3C 的 WebGPU 规范](https://www.w3.org/TR/webgpu/)，不过实际用的时候不用手写底层，[Transformers.js 的文档](https://huggingface.co/docs/transformers.js/index) 对这块有详细的说明。

实现方式其实不复杂，关键就一行代码：

```text
// 为啥要看这段：因为 Transformers.js 默认走 CPU（Wasm）路径，
// 你要手动指定 backend 才能走 WebGPU

import { pipeline } from '@huggingface/transformers';

// 关键：手动指定 device 为 'webgpu'
const generator = await pipeline('text-generation', 'Xenova/Qwen2.5-1.5B-INT4', {
  device: 'webgpu',          // 走 WebGPU 路径
  dtype: 'q4',               // 量化精度对齐
});

```

跑完之后验证了一下，确认 WebGPU 路径确实生效了：

```text
[INFO] Using device: webgpu (backend: Google Dawn)
[INFO] Model loaded: Qwen2.5-1.5B-INT4 (dtype: q4)
[INFO] First inference: 1.2s (cold start)
[INFO] Subsequent inferences: 0.3-0.5s (warm)

```

跑完之后，我对比了一下不同设备的推理速度：

| 设备类型 | CPU 推理（tokens/sec） | WebGPU 推理（tokens/sec） | 提升幅度 |
| --- | --- | --- | --- |
| 低端笔记本（Intel UHD） | 8-10 | 6-8 | ❌ 反而更慢 |
| 中端手机（骁龙 8 Gen 2） | 10-12 | 15-18 | ✅ 提升约五成 |
| 高端笔记本（M1） | 9-10 | 18-20 | ✅ 提升约一倍 |
| 旗舰手机（A17 Pro） | 12-14 | 22-25 | ✅ 提升约七成 |

**所以第一层的结论是：先判断设备，再决定走 CPU 还是 WebGPU。** 低端设备不配用 WebGPU，老老实实走 CPU。中高端设备果断上 WebGPU，收益明显。

判断逻辑其实很简单——检测一下 `navigator.gpu` 是否存在，再跑一个轻量 benchmark 看实际速度。如果 WebGPU 比 CPU 慢，就回退。

```text
// 为啥要看这段：自动判断走 CPU 还是 WebGPU，避免低端设备上翻车

async function getBestDevice() {
  // 不支持 WebGPU 的浏览器，直接走 CPU
  if (!navigator.gpu) return 'wasm';
  
  // 跑一个微型 benchmark，看 WebGPU 是否真的更快
  const cpuSpeed = await benchmarkCpu();    // 先测 CPU 速度
  const gpuSpeed = await benchmarkGpu();   // 再测 WebGPU 速度
  
  // 如果 GPU 不比 CPU 快，就别用
  return gpuSpeed > cpuSpeed * 1.2 ? 'webgpu' : 'wasm';
}

```

跑了一次测试，看看这个自动判断逻辑实际效果：

```text
[Device: Intel UHD Graphics (ThinkPad)]
  CPU benchmark:  9.2 tokens/sec
  GPU benchmark:  6.8 tokens/sec
  → 6.8 < 9.2 * 1.2 → return 'wasm' ✅ 正确回退

[Device: M1 MacBook Air]
  CPU benchmark:  9.5 tokens/sec
  GPU benchmark: 19.1 tokens/sec
  → 19.1 > 9.5 * 1.2 → return 'webgpu' ✅ 正确选择

```

这个 benchmark 跑一次也就一两秒，而且只在第一次加载时跑，后面缓存结果就行。代价很小，但能避免低端设备上"开了 WebGPU 反而更慢"的尴尬。

## 第二层：软感知——让用户觉得快

硬件加速搞定了，但还有一个问题：**WebGPU 推理虽然快了一倍，但用户还是要等 5 秒。**

5 秒在互联网体验里是"不可接受"的阈值。用户等 3 秒开始焦虑，等 5 秒开始划走。

那怎么办？答案是——**别让用户等"全部"生成完。**

之前我的做法是：模型生成完整个回答，再一次性展示给用户。用户看到的是"白屏→等了 5 秒→突然冒出一大段文字"。这个过程用户感知到的延迟是完整的 5 秒。

改成流式输出之后，模型生成一个 token 就展示一个 token。用户看到的是"白屏→等了不到一秒→开始出现文字→文字逐字增加→两三秒后全部展示完"。

**用户感知的首 token 延迟，从 5 秒降到了不到一秒。**

这个优化在代码层面改动不大：

```text
// 为啥要看这段：非流式 vs 流式，区别就是一个参数

// ❌ 非流式——等全部生成完再展示
const result = await generator(prompt, { max_new_tokens: 100 });
display(result[0].generated_text);   // 用户等 5 秒，突然全部展示

// ✅ 流式——逐 token 展示
const stream = await generator(prompt, { 
  max_new_tokens: 100,
  callback: (token) => {
    display(token);  // 每生成一个 token 就展示，用户几乎不用等
  }
});

```

流式输出跑起来的效果，用户端看到的是这样的：

```text
[非流式] 用户等待 5 秒 → 突然展示完整回答
[流式]   用户等待 0.8 秒 → "端" → "端侧" → "端侧模型" → ... → 3 秒后展示完毕

```

流式输出下，用户感知的等待时间从 5 秒降到了不到 1 秒。

不过流式输出有个坑需要注意：**WebGPU 下流式输出的 token 生成速度可能不均匀。** 前几个 token 生成得慢（因为要预热），后面越来越快。如果用户盯着屏幕看，会看到"前几个字卡了一下，后面飞一样"的感受。

我的做法是：在流式输出开始前，先展示一个"正在生成……"的占位动画，让用户有心理预期，等第一个 token 出来了再替换掉。

**第二层的核心思路：技术上不可能让推理速度提升 10 倍，但可以通过交互设计让用户感知到的延迟降低 10 倍。**

## 第三层：精匹配——选对量化策略

前两层解决了"怎么跑"和"怎么展示"的问题，但还有一个隐藏的坑：**量化策略选错了，速度也上不去。**

我之前以为 INT4 一定比 INT8 快——少了一半的数据量，计算量应该更小才对。

但实际测下来，在某些场景下，INT4 比 INT8 还慢。

原因是什么呢？我查了一下，发现是 **INT4 的解包开销**。大部分硬件原生不支持 INT4 计算，实际执行的时候，INT4 数据会被解包成 INT8 或者 FP16 再算。解包本身有开销，对于小模型来说，这个开销可能抵消甚至超过数据量减少带来的收益。

我测了几种量化策略的实际表现：

| 量化策略 | 推理速度 | 内存占用 | 输出质量 |
| --- | --- | --- | --- |
| INT4 纯量化 | 基准 | 基准 | 基准 |
| INT8 纯量化 | 慢了约两成 | 多了约一倍 | 基本持平 |
| 混合精度（敏感层 INT8，其余 INT4） | 快了约一成 | 多了约两成 | 接近无损 |
| 动态精度（运行时根据输入长度调整） | 快了约两成 | 跟混合精度持平 | 略有波动 |

**有意思的是混合精度方案。** 我之前以为混合精度只是"内存和精度的平衡"，没想到它对速度也有正向影响。原因是 attention 层的计算密集度高，INT4 的打包解包开销在 attention 的矩阵乘法中占比很大，换成 INT8 后反而跑得更顺畅；而 FFN 层是内存密集型，数据量小才是关键，所以保留 INT4。各取所长，整体就快了。

**第三层的结论：不要盲目追求 INT4，混合精度可能是更好的选择。** 省了内存但慢了速度，得不偿失。

## 测试环境与局限性

上面所有的数据，基于以下测试环境：

- **浏览器：** Chrome 154.0.6613.84（WebGPU 完整支持）
- **推理框架：** Transformers.js v3.2.0
- **测试模型：** Qwen2.5-1.5B（INT4 量化版，版本号 2026.05）
- **低端设备：** 联想 ThinkPad X1 Carbon（Intel i5-1135G7，UHD Graphics）
- **中端设备：** 小米 13（骁龙 8 Gen 2）
- **高端设备：** MacBook Air（M1，8GB 统一内存）

**这个方案不是万能的，有几个坑需要提前知道：**

- WebGPU 在 iOS Safari 上支持（从 iOS 16.4 开始），但实现跟 Chrome 有差异，部分特性（如 compute shader 的 subgroup 操作）受限，实测性能不如 Chrome 稳定
- 流式输出在 Transformer 模型的 beam search 模式下不支持，只能用 greedy decoding
- 混合精度方案需要自己写量化配置，Transformers.js 默认不提供这个选项
- 低端设备上强行走 WebGPU 不仅慢，还可能因为 GPU 驱动问题导致崩溃

## 性能优化前后对比

为了更直观地展示本文三层优化方案（设备检测、流式输出、混合精度）的综合效果，我将高中低端三种设备上的优化前后数据整理如下：

| 设备类型 | 优化前（仅 CPU + INT4） | 优化后（三层方案） | 提升幅度 |
| --- | --- | --- | --- |
| 低端设备<br>（Intel UHD Graphics） | 推理速度： 8-10 tokens/sec<br>用户感知延迟： 约 10-12 秒（非流式） | 推理速度： 8-10 tokens/sec（回退 CPU）<br>用户感知延迟： 约 1-2 秒（流式输出） | 速度持平，感知延迟降低 80%+<br>（通过流式输出将首 token 延迟降至 1 秒内） |
| 中端设备<br>（骁龙 8 Gen 2） | 推理速度： 10-12 tokens/sec<br>用户感知延迟： 约 8-10 秒（非流式） | 推理速度： 15-18 tokens/sec（WebGPU）<br>用户感知延迟： 约 0.8-1.5 秒（流式输出） | 推理速度提升约 50%，感知延迟降低 85%+ |
| 高端设备<br>（M1 MacBook Air） | 推理速度： 9-10 tokens/sec<br>用户感知延迟： 约 10 秒（非流式） | 推理速度： 18-20 tokens/sec（WebGPU + 混合精度）<br>用户感知延迟： 约 0.8-1.2 秒（流式输出） | 推理速度提升约 100%，感知延迟降低 90%+ |

**说明：**

1. **优化前基准**：指仅使用 CPU（Wasm）后端 + INT4 纯量化模型，且采用非流式输出（用户需等待全部生成完毕）。
2. **优化后方案**：<br>

- **低端设备**：设备检测自动回退到 CPU，但启用流式输出，大幅降低用户感知延迟。
- **中高端设备**：设备检测启用 WebGPU，结合流式输出，并采用混合精度量化（Attention 层 INT8，其余 INT4），实现速度和感知延迟的双重优化。

1. **用户感知延迟**：指从用户触发生成到看到第一个有意义的 token（或占位反馈）的时间。流式输出将其从“总生成时间”压缩为“首 token 时间”。
2. **数据来源**：综合自前文各节的 benchmark 结果与实测数据。

这张表清晰地表明，**即使硬件算力有限（如低端设备），通过流式输出也能极大改善用户体验；而在中高端设备上，三层优化叠加可实现翻倍的推理速度与秒级的响应感知。**

## 回头看

三个层面打下来，Phi-3-mini 的推理速度从 5 秒左右降到了 2 秒上下（中高端设备）。虽然没有"10 倍提升"那种夸张效果，但 2 秒在用户可接受的范围内了。

回头看这次优化，我最深的感受是：**性能优化不是"找到一个最优方案"然后通吃，而是在不同层面做取舍，而且每个层面都要根据设备情况做动态调整。**

下面这张图可以直观看到三个层面的关系：

![](https://picx.zhimg.com/v2-d497b9325859d184b682887a1ec1e15b_1440w.jpg)

你可以把这三个层面理解成一个"从硬到软"的决策链：

1. **先看硬件**——设备支不支持 WebGPU，支不支持就跑，不支持的别硬上
2. **再看交互**——能不能用流式输出降低用户感知延迟，能就用
3. **最后看模型**——量化策略要不要调，混合精度是不是更划算

多说一句：性能优化只是让模型"跑得快"，但跑得快不代表用户觉得好用。模型跑起来之后，我在产品里遇到了另一个问题——用户说"这个 AI 不太聪明"。

## 总结

通过本文的三层优化，我们成功将端侧大模型推理的体验从“不可用”提升到了“可用”甚至“好用”的水平。让我们再回顾一下这三层的核心思想：

1. **硬加速（设备检测）**：**没有银弹，只有合适**。WebGPU 不是万能加速器，在低端设备上强行使用反而会拖慢速度。通过轻量级 benchmark 动态选择 CPU 或 WebGPU 后端，确保硬件资源被用在刀刃上。
2. **软感知（流式输出）**：**用户感知比绝对速度更重要**。技术上难以实现 10 倍的速度提升，但通过流式输出，可以将用户感知的首 token 延迟从 5 秒压缩到 1 秒以内，体验提升立竿见影。
3. **精匹配（量化策略）**：**平衡的艺术**。盲目追求极致的 INT4 量化可能因解包开销而得不偿失。混合精度（如 Attention 层 INT8 + FFN 层 INT4）在速度、内存和精度之间找到了更优的平衡点。

这三层形成了一个从硬件到交互再到模型的完整优化链条：**先确保跑在正确的硬件上，再让用户尽快看到反馈，最后微调模型本身以榨取最后一点性能。**

## 下一步：当模型“跑得快”之后

正如文末提到的，性能问题解决后，用户反馈变成了：“这个 AI 不太聪明。” 这引出了端侧 AI 落地的下一个核心挑战：**效果（Effectiveness）**。速度是体验的基础，但智能才是价值的核心。后续的优化方向可以围绕以下几点展开：

- **模型蒸馏与小模型定制**：Phi-3-mini 虽小，但在某些垂直场景下仍显“力不从心”。下一步可以探索针对特定场景（如代码生成、客服问答）的**模型蒸馏**，在保持小参数量的前提下，提升任务特定能力。或者，直接选用在目标领域表现更优的**超小模型**（如 1B 参数以下）。
- **Prompt 工程与上下文优化**：很多时候模型“不聪明”是因为 Prompt 没喂好。研究如何设计**系统指令**、利用**思维链（Chain-of-Thought）** 提示、构建高质量的**示例（Few-shot）**，以及管理有限的**上下文长度**，都能以极低的成本显著提升输出质量。
- **推理缓存与预热**：对于高频问题或通用回复，可以引入**结果缓存**。首次推理后，将问答对存储起来，下次直接返回，实现“零延迟”。同时，可以探索**模型预热**策略，在用户可能使用前提前加载，进一步消除冷启动延迟。

性能优化打开了端侧 AI 的大门，而效果优化将决定用户是否会留下来。
