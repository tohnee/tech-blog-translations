## FSDP2 源码级深度剖析 —— 逐文件、逐函数、逐行精讲

> 目标读者：已看完第一份入门文档，对 FSDP2 有模糊的整体认知，但对其源码细节、流/事件机制、各模块交互一头雾水的新手。<br> 本文聚焦**源码本身**，按文件拆分，每个函数逐一讲解，配合数据流图，彻底搞清楚 FSDP2 每一行代码在做什么。

---

### 总纲：FSDP2 的核心代码流程

在深入每个文件之前，先记住 FSDP2 源码中**最重要的 6 步**：

```text
1. [初始化]   fully_shard() → 参数切分，注册 hook
2. [前向-A]   pre_forward hook → unshard() → 启动 All-Gather
3. [前向-B]   wait_for_unshard() → Copy-Out → 完整参数可用
4. [前向-C]   post_forward → reshard() → 释放完整参数
5. [反向-A]   pre_backward hook → unshard() → 再次收集参数
6. [反向-B]   post_backward → reduce-scatter 梯度 → reshard
```

所有复杂的 Stream、Event、Overlap 机制都围绕这 6 步展开。

### 文件 1：`_fsdp_api.py` —— API 配置定义

### 1.1 MixedPrecisionPolicy

```text
@dataclass(frozen=True)
class MixedPrecisionPolicy:
    param_dtype: Optional[torch.dtype] = None    # 例如 torch.bfloat16
    reduce_dtype: Optional[torch.dtype] = None   # 梯度规约精度
    output_dtype: Optional[torch.dtype] = None   # 前向输出精度
    cast_forward_inputs: bool = True             # 是否转换前向输入
```

**核心作用**：定义 FSDP 在什么精度下做计算（`param_dtype`）和什么精度下做梯度规约（`reduce_dtype`）。

**为什么要有两个精度？** 典型场景：参数以 bf16 计算（省显存、加速），梯度以 fp32 规约（避免精度损失）。

### 1.2 CPUOffloadPolicy

```text
@dataclass
class CPUOffloadPolicy:
    pin_memory: bool = True
```

**本质**：告诉 FSDP：参数在 CPU 上，每次 All-Gather 前先从 CPU 拷到 GPU。GPU 上的梯度计算完后拷回 CPU。

### 文件 2：`_fsdp_common.py` —— 共享数据结构

### 2.1 Mesh Info 体系

```text
class DataParallelMeshInfo:     # 基类
    mesh: DeviceMesh
    shard_mesh_dim: int | None
    replicate_mesh_dim: int | None

class FSDPMeshInfo(DataParallelMeshInfo):   # 1D FSDP
    shard_mesh_size: int     # mesh.size(shard_mesh_dim)
    shard_process_group      # ProcessGroup
    shard_mesh_rank: int

class DDPMeshInfo(DataParallelMeshInfo):    # 复制维度
    replicate_mesh_size: int
    replicate_process_group
    replicate_mesh_rank: int

class HSDPMeshInfo(FSDPMeshInfo, DDPMeshInfo):  # 2D HSDP
    # 同时有 shard 和 replicate 的信息
```

**理解**：这 4 个类描述的是”参数在哪些 GPU 上怎么分布”。

- `FSDPMeshInfo`：参数沿 dim-0 切分到 `shard_mesh_size` 个 rank
- `HSDPMeshInfo`：先沿 dim-1 切分，再沿 dim-0 复制

### 2.2 TrainingState

```text
class TrainingState(Enum):
    FORWARD = auto()
    PRE_BACKWARD = auto()
    POST_BACKWARD = auto()
    IDLE = auto()
```

**每个 FSDPParamGroup 都有一个 `_training_state`**。FSDP 根据这个状态变量决定：

- 在 `FORWARD` 时：前向隐式预取是否启用
- 在 `PRE_BACKWARD` 时：是否跳过已经 unshard 的组
- 在 `POST_BACKWARD` 时：是否执行 reshard、reduce-scatter

### 2.3 工具函数

- `_chunk_with_empty(tensor, num_chunks, dim)`：切分张量，如果切分数大于实际块数，用空张量补齐
- `_get_dim0_padded_size(size, factor)`：计算 dim-0 向上取整到 factor 倍数后的大小
- `_from_local_no_grad(local_tensor, sharding_spec)`：将本地张量封装成 DTensor，但不注册梯度
- `_to_dtype_if_needed(tensor, dtype)`：需要时做 dtype 转换

### 3.3 `_init_sharded_param()` —— 参数切分（第 259 行）

这是理解 FSDP 切分的核心函数。逐行解释：

```text
def _init_sharded_param(self, param, device, shard_placement_fn):
```

**Step 1：确定切分维度（第 273-280 行）**

```text
fsdp_placement = shard_placement_fn(param) if shard_placement_fn else None
if fsdp_placement is None:
    fsdp_placement = Shard(0)  # 默认是 dim-0
```

用户可以通过 `shard_placement_fn` 指定切分维度，如 `Shard(1)` 表示沿 dim-1 切分。

**Step 2：区分普通张量和 DTensor（第 285-286 行）**

```text
self.is_dtensor = isinstance(param, DTensor)
```

如果是 DTensor，说明已经经过了 Tensor Parallelism（TP）处理。FSDP 需要和 TP 组合。

**Step 3：计算切分（第 372-378 行）**

```text
chunks = _chunk_with_empty(param_data, shard_world_size, dim=shard_dim)
sharded_param = chunks[shard_rank]  # 当前 rank 的分片
self.sharded_size = _get_dim_chunked_size(sharded_param, param_data.size(), dim=shard_dim)
padded_sharded_size = chunks[0].size()  # 0 号 chunk 总是最大（padding 后）
self.padded_sharded_param_size = padded_sharded_size
```

**举个例子**：假设 `param_data.size()` = [10, 20]，`shard_world_size` = 4：

- 10 / 4 = 2.5，向上取整 = 3
- `chunks[0].size()` = [3, 20]（padding 后的基准大小）
- `chunks[rank]` = `chunk_with_empty` 保证每个 chunk 都是 [3, 20]
- 但只有数据部分写入，末尾用零填充（padding）

**Step 4：Padding（第 380-385 行）**

```text
padded_sharded_param = param_data.new_zeros(padded_sharded_size)
if sharded_param.numel() > 0:
    padded_sharded_param.narrow(dim=shard_dim, start=0, 
                                length=sharded_param.size(shard_dim)).copy_(sharded_param)
```

创建一个全零的 `padded_sharded_size` 张量，然后把实际数据拷进去。多余的零是 padding。

**为什么要 padding？**

- All-Gather 要求每个 rank 的输入大小相同
- padding 让所有 rank 的 shard 都一样大，方便 All-Gather

**Step 5：CPU Offload（第 386-391 行）**

```text
if self.offload_to_cpu and not padded_sharded_param.is_meta:
    padded_sharded_param = padded_sharded_param.cpu()
    if self.pin_memory:
        padded_sharded_param = padded_sharded_param.pin_memory(device=self.device)
```

如果开启 CPU offload，分片数据存在 CPU 上。`pin_memory` 让 H2D 拷贝更快。

**Step 6：保存和注册（第 392-403 行）**

```text
self._sharded_param_data = padded_sharded_param.view(-1)  # 1D 保存
self.sharded_param = nn.Parameter(self.to_sharded_dtensor(sharded_param))
self._setattr_on_modules(self.sharded_param)  # 注册到模块
self.sharded_state = ShardedState.SHARDED
```

### 3.4 `all_gather_inputs` 属性（第 687 行）—— All-Gather 的输入从哪来

**情况 B：前向后的 SHARDED_POST_FORWARD（第 755-764 行）**

此时用的是前向后再切分的数据。

**情况 C：有扩展预处理（第 690-748 行）** 如果张量有 `fsdp_pre_all_gather` 方法（例如量化张量），则调用它进行扩展预处理。

### 3.5 `init_unsharded_param()` —— 从 All-Gather 输出构造完整参数（第 462 行）

**这是第二重要的函数。** 它把 All-Gather 的输出转换成可供计算使用的完整参数。

```text
def init_unsharded_param(self):
```

**默认路径（第 510-514 行）**：

```text
unsharded_tensor = self.all_gather_outputs[0]
unsharded_param = torch.as_strided(
    unsharded_tensor, self._orig_size, self._contiguous_orig_stride, storage_offset=0,
)
```

- `all_gather_outputs[0]` 是一个 1D 张量，大小 = `numel * world_size`
- `torch.as_strided()` 把它 view 成原始 ND 形状（`_orig_size`）
- 这行代码**没有数据拷贝**，只是创建视图

**第一次调用 vs 后续调用**：

- 第一次（第 537-539 行）：创建 `nn.Parameter` self._unsharded_param = nn.Parameter(unsharded_param, requires_grad=...)<br>
- 后续调用（第 522-535 行，仅在 compile 模式下）：resize storage → copy_ self._unsharded_param.untyped_storage().resize_(...) torch.ops.fsdp.copy_(self._unsharded_param, unsharded_param)<br> 这里 `torch.ops.fsdp.copy_` 是 FSDP 自定义的算子（第 70 行注册的），为了避免 autograd 追踪问题。

### 3.6 `to_sharded()` / `to_unsharded()` —— 状态切换

这两个函数做的事情很简单：**把正确的参数引用挂在模块上**。

```text
def to_sharded(self):
    self._setattr_on_modules(self.sharded_param)  # 把分片参数给模块
    self.free_unsharded_param()                    # 释放完整参数
    self.sharded_state = ShardedState.SHARDED

def to_unsharded(self):
    set_requires_grad_if_needed(self.sharded_param, self._unsharded_param)
    self._setattr_on_modules(self._unsharded_param)  # 把完整参数给模块
    self.sharded_state = ShardedState.UNSHARDED
```

**核心思想**：`module.weight` 这样一个属性，FSDP 在运行时动态地把它指向分片参数或完整参数。前向计算时指向完整参数，前向结束后指向分片参数。

### 3.7 `free_unsharded_param()` —— 释放内存（第 664 行）

```text
def free_unsharded_param(self):
    for tensor in itertools.chain(self.all_gather_outputs, self._unsharded_inner_tensors):
        free_storage(tensor)  # storage.resize_(0)
```

**关键**：这里用的是 `storage.resize_(0)` 而不是释放对象。为什么？ 因为 autograd 可能持有对 `_unsharded_param` 的引用。如果释放对象，autograd 拿到的引用就悬空了。resize storage 为 0 既释放了显存，又保持了张量对象的生命周期。

### 3.8 `alloc_storage()` / `free_storage()`（第 877-885 行）

辅助函数，通过 resize storage 来分配/释放显存。

```text
def alloc_storage(tensor):
    size = tensor.numel() * tensor.itemsize
    if tensor.untyped_storage().size() != size:
        tensor.untyped_storage().resize_(size)  # 分配

def free_storage(tensor):
    if tensor.untyped_storage().size() != 0:
        tensor.untyped_storage().resize_(0)    # 释放
```

### 3.9 `unsafe_setattr_param()` —— 捷径（第 890 行）

```text
def unsafe_setattr_param(module, param_name, param):
    if getattr(module.__setattr__, "__func__", None) is nn.Module.__setattr__:
        module._parameters[param_name] = param  # 绕过 setattr 检查
    else:
        setattr(module, param_name, param)       # 慢路径
```

**为什么要有这个？** `nn.Module.__setattr__` 有很多检查，FSDP 频繁切换参数时不想承担这个开销。如果用户没有 override `__setattr__`，直接操作 `_parameters` 字典更快。

### 文件 4：`_fsdp_param_group.py` —— 参数组的核心驱动

**这是牵涉最广的文件。** 它驱动整个通信流程，管理 Stream、Event、Prefetching。

### 4.1 `FSDPCommContext` —— 全局通信上下文（第 49 行）

```text
class FSDPCommContext:
    def lazy_init(self, device):
        self.device_handle = _get_device_handle(device.type)
        high_priority = -1
        # 1. All-Gather Copy-In 流
        self.all_gather_copy_in_stream = self.device_handle.Stream(priority=high_priority)
        # 2. All-Gather 流
        self.all_gather_stream = self.device_handle.Stream(priority=high_priority)
        # 3. Reduce-Scatter 流
        self.reduce_scatter_stream = self.device_handle.Stream(priority=high_priority)
        # 4. All-Reduce 流（仅 HSDP 使用）
        self.all_reduce_stream = self.device_handle.Stream()
        
        self.all_gather_state: AllGatherState | None = None    # 前向隐式预取状态
        self.reduce_scatter_state: ReduceScatterState | None = None  # RS 重叠状态
        self.post_forward_order: list[FSDPParamGroup] = []    # 前向执行顺序
```

**为什么要用 4 条流？**

| 流 | 干什么 | 为什么单独分一条流 |
| --- | --- | --- |
| all_gather_copy_in_stream | dtype 转换 + GPU 显存内部的拼接拷贝 | 占 GPU 计算/显存资源，而 All-Gather 占 NCCL 网络资源，两者硬件引擎不同，可并行 |
| all_gather_stream | NCCL All-Gather 集体通信 | 占 GPU 间网络带宽（NVLink/NIC），和计算流可重叠 |
| reduce_scatter_stream | NCCL Reduce-Scatter + divide + dtype 转 | 和反向计算可以重叠 |
| all_reduce_stream | HSDP 的 All-Reduce | 和 Reduce-Scatter 可以重叠（不同网络资源） |

**高优先级**：`high_priority = -1`（值越小优先级越高）。FSDP 的通信流比其他流优先执行，防止通信延迟导致的计算阻塞。

### 4.2 `get_all_gather_streams()` —— 选择流（第 82 行）

```text
def get_all_gather_streams(self, async_op, training_state):
    if not async_op and training_state in (FORWARD, PRE_BACKWARD):
        return self.all_gather_copy_in_stream, self.all_gather_stream  # 使用独立流
    current_stream = self.device_handle.current_stream()
    return current_stream, current_stream  # 使用当前流（主计算流）
```

**关键逻辑**：

- 前向和反向前：用独立流 → 可以实现通信与计算重叠
- 如果 `async_op=True`：用当前流 → 不重叠（简化调试）
- 为什么 `POST_BACKWARD` 不用独立流？因为 Reduce-Scatter 已经在 RS 流上了，不需要额外 All-Gather

### 4.5 `unshard()` —— 启动 All-Gather（第 252 行）

**这是每一次 All-Gather 的开始。** 它调用 `foreach_all_gather()` 在独立流上启动通信。

```text
def unshard(self, async_op=False):
    if self._all_gather_result is not None:  # 已经调用，等待中
        return
    if self.is_unsharded:
        return  # 已经是 unsharded 状态，跳过
    if not self.unshard_in_backward and self._training_state == PRE_BACKWARD:
        return  # 反向后不需要 unshard（如 embedding 层）
    
    # 如果有前向后的重切分事件，等它完成
    if self._reshard_after_forward_event is not None:
        self._wait_all_gather_streams_on_event(self._reshard_after_forward_event)
        self._reshard_after_forward_event = None
    
    self._all_gather_result = foreach_all_gather(
        self.fsdp_params,      # 这组参数
        self._all_gather_process_group,
        async_op,
        *self.comm_ctx.get_all_gather_streams(async_op, self._training_state),
        self.device,
    )
```

**逐行精讲**：

1. **幂等性检查**（第 253-256 行）：如果已经调用过 `unshard()` 且结果未消费，直接返回
2. **特殊情况跳过**（第 257-261 行）：如 embedding 层在反向不需要 unshard
3. **等待 post-forward reshard 完成**（第 262-266 行）：如果前向后重切分到了更小的 world size，那些数据是在计算流上分配的。现在 All-Gather 流需要等它们用完后才能使用
4. **调用 `foreach_all_gather()`**（第 268-274 行）：根据 `training_state` 决定用独立流还是当前流

### 4.6 `wait_for_unshard()` —— 等待并 Copy-Out（第 276 行）

**这是前向预取的核心衔接点。** 它在主计算流上等待 All-Gather 完成，然后做 Copy-Out。

```text
def wait_for_unshard(self):
    if not self._all_gather_result:
        return  # 没有未完成的 unshard
    
    # ====== 隐式预取：在前向时释放前一组的结果 ======
    if self._training_state == TrainingState.FORWARD:
        if prev_all_gather_state := self.comm_ctx.all_gather_state:
            # 让 All-Gather 流等前一组 Copy-Out 完成
            self._wait_all_gather_streams_on_event(prev_all_gather_state.event)
            self.comm_ctx.all_gather_state = None  # 释放前一组结果
    
    # ====== Copy-Out ======
    foreach_all_gather_copy_out(self._all_gather_result, self.fsdp_params, ...)
    for fsdp_param in self.fsdp_params:
        fsdp_param.init_unsharded_param()  # 构造完整参数
    self._to_unsharded()  # 把完整参数注册到模块
    
    # ====== 记录 Copy-Out 完成事件 ======
    all_gather_copy_out_event = self.device_handle.Event()
    all_gather_copy_out_event.record()
    
    # ====== 保存当前结果供下一组使用（前向时） ======
    if not async_op and self._training_state == TrainingState.FORWARD:
        self.comm_ctx.all_gather_state = AllGatherState(
            self._all_gather_result, all_gather_copy_out_event
        )
    else:
        self._wait_all_gather_streams_on_event(all_gather_copy_out_event)
    
    self._all_gather_result = None
```

**逐行精讲**：

**隐式预取部分（第 288-291 行）**：

- 当 `training_state == FORWARD` 时，检查 `all_gather_state` 是否有前一组的结果
- 如果有：让 All-Gather 流等前一组 Copy-Out 完成（`wait_event`），然后释放它
- **效果**：组 N 的 Copy-Out 还没完，组 N+1 的 Copy-In/All-Gather 已经在并行进行了

**Copy-Out 部分（第 292-300 行）**：

1. `foreach_all_gather_copy_out()`：在主计算流上，把 All-Gather 的输出拆分给各个参数
2. `init_unsharded_param()`：每个参数从 All-Gather 输出构造出完整 ND 张量
3. `_to_unsharded()`：把完整参数注册到模块，替换掉分片参数

**事件记录和保存（第 301-311 行）**：

- 在主计算流上 record `all_gather_copy_out_event`
- 如果是前向且非异步：把当前结果保存在 `all_gather_state` 中，供下一组使用
- 否则：直接让 All-Gather 流等这个事件

### 4.7 `_wait_all_gather_streams_on_event()` —— 等待事件（第 313 行）

```text
def _wait_all_gather_streams_on_event(self, event):
    if hasattr(self.comm_ctx, "all_gather_copy_in_stream"):
        self.comm_ctx.all_gather_copy_in_stream.wait_event(event)
    if hasattr(self.comm_ctx, "all_gather_stream"):
        self.comm_ctx.all_gather_stream.wait_event(event)
```

**作用**：在主计算流上做 Copy-Out 时，All-Gather 流需要等待 Copy-Out 完成才能释放内存（或者下一轮的 Copy-In 需要使用这些内存）。

### 4.8 `reshard()` —— 释放完整参数（第 320 行）

```text
def reshard(self):
    if self._training_state == TrainingState.FORWARD:
        if not self._reshard_after_forward:
            return  # 不需要 reshard
        if self._use_post_forward_mesh:
            self._to_sharded_post_forward()  # 重切分到更小的 world size
            self._reshard_after_forward_event = self.device_handle.Event()
            self._reshard_after_forward_event.record()
            return
    self._to_sharded()  # 普通 reshard：恢复到分片状态
```

**三种情况**：

1. `reshard_after_forward=False`：不解释，保持完整参数
2. `reshard_after_forward=int`：重切分到 `int` 个 rank（HSDP），记录事件供下次 All-Gather 等待
3. `reshard_after_forward=True`：恢复到分片状态，释放完整参数

### 4.9 `pre_forward()` / `post_forward()` —— 前向 hook 逻辑

```text
def pre_forward(self, module, args, kwargs):
    self._training_state = TrainingState.FORWARD
    self.unshard(self.unshard_async_op)    # 启动 All-Gather
    self.wait_for_unshard()                # 等待完成，Copy-Out
    args, kwargs = self._register_post_backward_hook(args, kwargs)
    return args, kwargs

def post_forward(self, module, input, output):
    self.reshard()              # 释放完整参数
    self._record_post_forward() # 记录前向顺序
    self._training_state = TrainingState.IDLE
    return output
```

**前向流程时间线**：

```text
[pre_forward]
    1. unshard() → Copy-In + All-Gather 在独立流启动
    2. wait_for_unshard() → 等待完成，Copy-Out 在主流
                            → 同时检查前一组结果（隐式预取）
[forward 计算]   ← 完整参数已可用
[post_forward]
    3. reshard() → 释放完整参数
    4. 记录前向顺序（用于反向预取）
```

### 4.9.X 深度答疑：它到底”预取”了什么？——CPU-GPU 执行模型解耦

> 这是读者问得最多的问题。如果你只理解本节的一个结论，记住这句： **CPU 函数调用是顺序的，但 GPU 流执行是并行的；”预取”的不是 CPU 执行顺序，而是 GPU 流之间的重叠。**

### 4.9.X.1 你为什么会困惑？——一个直觉陷阱

看 `pre_forward()` 的代码：

```text
# _fsdp_param_group.py:332
def pre_forward(self, module, args, kwargs):
    self.unshard(self.unshard_async_op)    # 启动 All-Gather
    self.wait_for_unshard()                # 等待完成，Copy-Out
    return args, kwargs
```

以及 PyTorch hook 的调用顺序：

```text
L1.pre_forward() → L1.forward() → L1.post_forward()
    → L2.pre_forward() → L2.forward() → L2.post_forward()
    → L3.pre_forward() → L3.forward() → L3.post_forward()
```

**直觉告诉你**：L2 的 `unshard()` 明明在 L1 的 `forward()` 和 `post_forward()` 之后才调用，这不是顺序执行吗？怎么叫”预取”？

**这个直觉的错误在于**：你把 CPU 的函数调用顺序当成了 GPU 的执行顺序。实际上，**CPU 提交工作是异步的**——`unshard()` 只是把命令塞进 GPU 流队列就返回了，真正的 GPU 执行在后面。

### 4.9.X.2 先理解 GPU 是一个”异步执行器”

当你在 PyTorch 中写出：

```text
c = torch.mm(a, b)   # 矩阵乘法
d = torch.mm(e, f)   # 另一个矩阵乘法
```

CPU 不会等第一个 matmul 算完再提交第二个。它把两个 matmul 都**提交到 main_stream** 然后立即返回。GPU 在后台**按顺序**执行它们。

更关键的是：**不同流上的操作可以在 GPU 上同时执行**。

```text
main_stream 的 GPU 执行:   [matmul_1] [matmul_2] [matmul_3]
                              ↓ 顺序执行，一个接一个

不同流的 GPU 执行（可以并行）:
  stream_A: [op_A1] [op_A2]
  stream_B: [op_B1] [op_B2]
               ↑ 同时执行（如果硬件资源充足）
```

FSDP 正是利用了这个特性：

- `main_stream`（计算流）：执行前向/反向计算
- `all_gather_copy_in_stream`（拷贝流）：执行数据拷贝 + dtype 转换
- `all_gather_stream`（通信流）：执行 NCCL All-Gather

这三条流的操作**使用的是 GPU 不同的硬件引擎**，所以可以并行：

| 流 | 硬件资源 | 干的事 |
| --- | --- | --- |
| main_stream | GPU 计算单元（SM/CUDA Core） | 矩阵乘法、激活函数 |
| all_gather_copy_in_stream | 显存控制器 + 计算单元 | 数据拼接、dtype 转换 |
| all_gather_stream | NCCL 网卡 / NVLink | 跨 GPU 通信 |

**这就是预取的第一重含义：CI/AG 用独立硬件资源，和计算不打架。**

### 4.9.X.3 画出 CPU 提交顺序和 GPU 执行顺序的对比

假设 3 个 Transformer Layer，每个的 `pre_forward` 内部调用 `unshard()` + `wait_for_unshard()`：

```text
===== 示意图 1：CPU 提交到各流的内容（时间从上往下）=====

CPU 执行 L1.pre_forward():
  unshard() → copy_in_stream 收到: [CI(L1)]
           → all_gather_stream 收到: [等CI(L1)] → [AG(L1)]
  wait_for_unshard() → main_stream 收到: [等AG(L1)] → [CO(L1)]
                     → 保存 L1 结果到 all_gather_state

CPU 执行 L1.forward():
  main_stream 收到: [L1 的一系列 matmul 操作]

CPU 执行 L1.post_forward():
  Python 逻辑（几乎不提交 GPU 操作）

CPU 执行 L2.pre_forward():
  unshard() → copy_in_stream 收到: [CI(L2)] ← CPU 已经提交到这了！
           → all_gather_stream 收到: [等CI(L2)] → [AG(L2)]
  wait_for_unshard() → 释放 L1 的 all_gather_state
                     → main_stream 收到: [等AG(L2)] → [CO(L2)]
                     → 保存 L2 结果到 all_gather_state

CPU 执行 L2.forward():
  main_stream 收到: [L2 的一系列 matmul 操作]

CPU 执行 L3.pre_forward():
  unshard() → copy_in_stream 收到: [CI(L3)]
           → all_gather_stream 收到: [等CI(L3)] → [AG(L3)]
  ...

===== 示意图 2：GPU 上三个流的实际执行（时间从左到右）=====

时间 ─────────────────────────────────────────────────────────►

copy_in_stream:   [CI(L1)] [CI(L2)] [CI(L3)] ...
                       ↑ 各组的 CI 紧挨着提交，因为 CPU 跑得比 GPU 快

all_gather_stream:        [AG(L1)] [AG(L2)] [AG(L3)] ...
                           ↑ AG 用 NCCL 网卡，和主流的计算并行

main_stream:                      [CO(L1)] [L1 matmul...] [CO(L2)] [L2 matmul...]
                                   ↑ CO 必须在主流上（结果直接被计算使用）
                                             ↑ L1 计算时，L2 的 AG 已经完成了！
                                                       ↑ CO(L2) 几乎不用等 AG
```

**关键看时间轴上的重叠**（用 `│` 对齐时间点）：

```text
时间─────►
copy_in:      [CI(L1)]  [CI(L2)]   [CI(L3)]
                    \        \           \
ag:                  [AG(L1)] [AG(L2)]  [AG(L3)]
                         \        \          \
main:                    [CO(L1)][L1 matmul.][CO(L2)][L2 matmul.][CO(L3)][L3 matmul.]
```

看到了吗？**L1 还在 main_stream 上做 matmul 时，L2 的 AG 已经在 all_gather_stream 上跑完了。** 这就是”预取”——L2 的参数在 L1 计算的同时就已经被 All-Gather 好了。当 CPU 执行到 `L2.wait_for_unshard()` 时，`main_stream.wait_event(AG_event)` 几乎不需要等待，因为 AG 早就完成了。

### 4.9.X.4 回答”预取”的含义

```text
预取 = L2 的 AG 在 GPU 上提前执行，和 L1 的 forward 计算重叠
        ↑                  ↑
    函数在 L1 之后调用  硬件上同时进行
```

**打个比方**：

> 你去食堂打饭：<br>

- **顺序执行（无预取）**：先打饭 → 再打菜 → 再打汤 → 坐下吃 → 吃完再去洗碗
- **FSDP 预取**：你还在吃的时候（main_stream 计算），食堂阿姨已经把下一份菜准备好了（AG 在独立流上执行）。你吃完一口喊”打菜”，阿姨直接递给你（CO 几乎不需要等）。

### 4.9.X.5 更尖锐的问题：那会不会 OOM？

现在你已经知道 L2 的 AG 在 L1 计算时就执行了。那 L3 的 CI/AG 呢？CPU 提交很快：

```text
L1.forward() 还在 GPU 上执行时，CPU 已经提交了:
  L1.post_forward() → L2.pre_forward() → unshard(L2) → wait_for_unshard(L2)
    → L2.forward() → L2.post_forward() → L3.pre_forward() → unshard(L3) ...
```

**问：如果 CPU 跑得比 GPU 快得多，会不会提交了太多 AG，导致显存里堆了多层参数？**

答案：**不会。有三个保护机制层层把关。**

### 保护一：`all_gather_state` 是单 slot（`_fsdp_param_group.py:77`）

```text
# FSDPCommContext 中:
self.all_gather_state: Optional[AllGatherState] = None  # 只能保存一组！
```

这是一个**单变量**，只能保存**一组**的 flat AG buffer。当 L3 的 `wait_for_unshard()` 执行时：

```text
# _fsdp_param_group.py:288-291
if prev_all_gather_state := self.comm_ctx.all_gather_state:  # = L2 的结果
    self._wait_all_gather_streams_on_event(prev_all_gather_state.event)
    self.comm_ctx.all_gather_state = None  # 释放 L2 的 flat buffer！
```

L2 的 flat buffer 在 L3 分配新的 flat buffer 之前就被释放了。

### 保护二：`post_forward → reshard` 在 `pre_forward` 之前释放 per-param buffer

```text
# post_forward (按顺序调用):
#   L1.post_forward() → reshard() → to_sharded() → free_unsharded_param()
#     → free_storage(L1_per_param)  ← L1 的完整参数释放了！
#   L2.pre_forward()  → unshard() → alloc(L2_flat) ← 才分配 L2 的
```

**一个层的 per-param 缓冲区（即 `_unsharded_param` 的真实存储）在前一层的 `post_forward` 中已经释放了。**

### 保护三：用 timeline 验证内存峰值

看看每个时刻 GPU 内存里有什么（假设 world_size=8，每层参数量=F）：

```text
时刻 A：L1 前向计算中
  main_stream 上: L1 正在算 matmul
  内存中的 FSDP 缓冲区:
    ├─ L1._unsharded_param 的 storage (= L1 的 per-param all_gather_outputs)  = 1×F
    ├─ comm_ctx.all_gather_state → L1 的 flat AG buffer                      = 1×F
    └─ 其他层: 均处于 sharded 状态 (只占 F/8)
  小计: 2×F + 其他层 sharded

时刻 B：L2 前向计算中
  main_stream 上: L2 正在算 matmul
  内存中的 FSDP 缓冲区:
    ├─ L2._unsharded_param 的 storage                                        = 1×F
    ├─ comm_ctx.all_gather_state → L2 的 flat AG buffer                      = 1×F
    └─ 其他层: 均处于 sharded 状态
  注意: L1 的 unsharded 已经在 L1.post_forward 的 reshard() 中释放了
  小计: 2×F + 其他层 sharded

时刻 C：L3 前向计算中 ... 同理
```

**峰值显存始终是 2×单层全量参数量 + 其余层 sharded。** 对于均匀大小的层（如绝大多数 Transformer），L3_flat 必然复用 L1_flat 的 block，不会出现 3×F。（非均匀层的边界情况见 4.9.X.7。）

对于典型 Transformer，单层参数 ≈ 模型总参数量 / 层数。一个 7B 模型如果有 32 层，单层 ≈ 220M 参数，在 fp16 下 ≈ 420MB。2× = 840MB，远小于 GPU 显存（24GB~80GB）。

### 4.9.X.6 把这张图刻在脑子里

```text
CPU 提交速度: 非常快，像一个"发令员"不停发号施令
                ↓
三条 GPU 流:   ┌─────────────────────────────────────┐
copy_in_stream │ CI(L1)   CI(L2)   CI(L3)   CI(L4)   │  ← 用显存带宽
              ├─────────────────────────────────────┤
ag_stream      │     AG(L1)  AG(L2)  AG(L3)  AG(L4) │  ← 用 NCCL 网卡
              ├─────────────────────────────────────┤
main_stream    │          CO(L1) [L1计算] CO(L2) [L2计算]│  ← 用 GPU 计算单元
              └─────────────────────────────────────┘
                          ↑             ↑
                     L1 还在计算时   几乎不用等 AG
                    L2 的 AG 已经    因为早就算完了
                    在独立流上跑完！

"预取" = 上方两条流替 main_stream 提前准备好了下一层的参数
```

### 4.9.X.7 再深入一层：三个关于内存的尖锐问题

**读者在讨论中提了三个非常尖锐的问题，值得逐条拆解。本节假设你已经理解 4.9.X.1-6，透过表象看本质。**

需要先定义清楚 F 的含义：**F = 单层完整（unsharded）参数的总字节数**，不是分片后的大小。在 `world_size=8` 时，每层的分片参数只占 F/8。

### 内存类型速查

FSDP 中每层有**两类大块缓冲区**和一个**持久占用**：

| 名称 | 符号 | 大小 | 在哪里分配 | 在哪里释放 |
| --- | --- | --- | --- | --- |
| flat AG buffer | Lx_flat | ≈1F | foreach_all_gather → all_gather_copy_in_cuda | 下一组的 wait_for_unshard 中 all_gather_state = None |
| per-param buffer | Lx_param | ≈1F | foreach_all_gather_copy_out → init_all_gather_outputs | post_forward → reshard → free_unsharded_param 的 resize_(0) |
| 分片参数 | Lx_sharded | F/ws | fully_shard 初始化 | 整个训练期间一直活着 |

**关键事实**：`Lx_flat` 和 `Lx_param` 是**两块不同的物理显存**。前者是 All-Gather 的输入/输出缓冲区，后者是前向计算实际读的参数存储。`_unsharded_param` 通过 `torch.as_strided` 视图指向 `Lx_param` 的存储，不额外占用内存。

---

### 问题 1：`_wait_all_gather_streams_on_event(prev_event)` 会不会阻塞下一层的 CI/AG？

**不会。关键在于 wait_event 插入时 CI(L2) 已经提交了。**

在 `L2.wait_for_unshard()` 中调用 `_wait_all_gather_streams_on_event(prev_event)` 时，CI 流上的 GPU 命令队列已经是：

```text
CI 流命令队列（时间从上往下）:
  [CI(L1)]    ← 来自 L1.unshard()
  [CI(L2)]    ← 来自 L2.unshard()  ← wait_event 插入前已经在这了！
  [wait_event(L1_CO)]  ← 来自 L2.wait_for_unshard()，刚插入
                           ↑ 只影响将来提交的命令（如 CI(L3)）
```

**CUDA 的 `wait_event` 语义是”让当前流在 wait_event 之后的所有操作等待 event 完成”**，不影响已经排队的操作。所以时间线上的实际效果是：

```text
copy_in_stream 的 GPU 执行（时间从左到右）:
  [CI(L1)] [CI(L2)] [wait(L1_CO)...等到 L1_CO 完成...][CI(L3)]
              ↑                                ↑
        不受影响，直接排队执行           CI(L3) 要等 L1_CO 完成才能开始
```

源码位置：`_fsdp_param_group.py:313-318`，`_wait_all_gather_streams_on_event` 本质是 `stream.wait_event(event)`。

---

### 问题 2：`self.comm_ctx.all_gather_state = None` 会直接”删掉”显存吗？如果 GPU 还在读怎么办？

**Python 引用立即释放，物理显存回收到 CUDA 缓存分配器的池中，但分配器知道它最后被哪些流使用，不会在未同步时把它给别人写。**

```text
self.comm_ctx.all_gather_state = None 的执行效果:
  ┌─ CPython 引用计数归零 → AllGatherResult 对象析构
  ├─ all_gather_output tensor 析构
  ├─ 底层 Storage 析构
  └─ PyTorch CUDA 缓存分配器收到 deallocate 请求
       └─ block 入池，记录："最后使用流 = main_stream + copy_in_stream"
       └─ 下次 torch.empty(size=F) 在 copy_in_stream 上请求分配时：
            ├─ 如果 pool 中有 block 最后使用流也是 copy_in_stream → 直接复用，不需同步
            ├─ 如果 block 最后使用流是 main_stream（不同流）→ 插入 wait_event(main_stream) 同步
            └─ 如果 pool 中没有合适 block → cudaMalloc 新物理显存
```

分配器不会在未同步的情况下把 L1_flat 正在被 main_stream 读取的内存给 copy_in_stream 去覆盖。同步开销通常是一次 CUDA event wait，非常轻量。

---

### 问题 3（最关键）：CPU 远超 GPU，会不会有三层参数量同时在物理显存中？

要精确回答这个问题，必须**逐帧追踪每块内存的生死**，并且区分”物理显存”和”活跃使用的显存”。

### 先理解 `free_storage` 到底释放了什么

FSDP 的 `free_storage` 调用 `storage.resize_(0)`：

```text
# _fsdp_param.py:883-885
def free_storage(tensor):
    if (storage := tensor.untyped_storage()).size() != 0:
        storage.resize_(0)
```

`resize_(0)` 将 storage 的 `data_ptr` 清空（归还给 CUDA 缓存分配器），`num_bytes` 置零。但需要注意：**`_unsharded_param` 和 `all_gather_outputs[0]` 共享同一个 Storage（因为 `torch.as_strided` 创建的是视图）**。所以 `free_storage(all_gather_outputs[0])` 后：

- 该 Storage 的 DataPtr 已被释放，物理显存回到分配器池中
- `_unsharded_param` 仍然持有该 Storage 的引用，但 storage 的 size=0、data_ptr=null
- **GPU 上已经提交的、正在执行的 matmul 操作不受影响**——这些操作在提交时已经把物理地址编码进了命令中，不会因为 CPU 侧的 `resize_(0)` 而失效
- 但分配器知道这块物理内存”最后被 main_stream 使用”，不会在 main_stream 耗尽前把它给别人

现在逐事件追踪。假设 3 个均匀大小的 transformer 层（每层 1F），`world_size=8`。关键事件按 CPU 执行顺序编号：

```text
事件记号：
  Unsh(Ln)   = Ln.pre_forward 中调用 unshard()，分配 Ln_flat
  Wait(Ln)   = Ln.pre_forward 中调用 wait_for_unshard()，CO 分配 Ln_param，存 Ln_flat
  Fwd(Ln)    = Ln.forward()，在 main_stream 上提交 matmul
  Post(Ln)   = Ln.post_forward()，reshard → free_storage(Ln_param)
```

**各事件前后的 GPU 显存状态：**

| 事件 | 执行后 L1_flat | L1_param | L2_flat | L2_param | L3_flat | L3_param | 活跃合计 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 初始 | — | — | — | — | — | — | 0 |
| ① Unsh(L1) | ① 分配 | — | — | — | — | — | 1F |
| ② Wait(L1) + Fwd(L1) | 存 state | ② 分配 | — | — | — | — | 2F ← 峰值 |
| ③ Post(L1) | 存 state | ③ resize_(0) | — | — | — | — | 1F |
| ④ Unsh(L2) | 存 state | 池 | ④ 分配 | — | — | — | 2F |
| ⑤ Wait(L2) + Fwd(L2) | ⑤ state=None → 池 | 池 | 存 state | ⑤ 分配 | — | — | 2F |
| ⑥ Post(L2) | 池 | 池 | 存 state | ⑥ resize_(0) | — | — | 1F |
| ⑦ Unsh(L3) | 池 | 池 | 存 state | 池 | ⑦ 分配 | — | 2F |
| ⑧ Wait(L3) + Fwd(L3) | 池 | 池 | ⑧ state=None → 池 | 池 | 存 state | ⑧ 分配 | 2F |

**关键观察：**

- **①→⑧ 的每一步，活跃物理显存最高就是 2F，从未到 3F。**
- **③ `Post(L1)` 后 L1_param 就 `resize_(0)` 入池了**。它不是”还在活跃使用”，而是已经归还给分配器了。GPU 上正在执行的 L1 matmul 读的是”已经提交到命令中的物理地址”，不影响。
- **⑤ L1_flat 被释放**（`all_gather_state = None`），此时 L2 的 flat + param 正好接上，总和仍是 2F。
- **⑦ L3_flat 分配时**，池中有 L1_flat 的 block（最近释放，且同是 copy_in_stream 流）→ **大概率直接复用**，即使不复用，池中也有别的 block 可用。

**所以真正可以复用的 block 是 L1_flat（同流同大小），不是 L1_param（不同流）。**

### 为什么你直觉中的”3F”不成立？

你的推理说：L1_param 还在（GPU 没算完）+ L2_flat + L2_param + L3_flat = 3F。

这个推理隐含了一个假设：**`resize_(0)` 后 L1_param 的物理显存还”算”在 L1 头上。** 但实际上，**`resize_(0)` 已经把这块显存归还给分配器了**。它只是在分配器的池中等待 main_stream 耗尽后才能被分配给其他流。但从 FSDP 的角度看，它已经是”空闲”的了。

> 类比：你把旧手机挂到闲鱼上卖（`resize_(0)` 入池），手机还在你手里（物理显存还在 GPU 上），但你已经不算它”在用”了。新手机买来（L3_flat 分配）如果用了闲鱼上卖掉旧手机换来的钱（复用池中 block），实际支出为零；如果闲鱼还没卖掉先用花呗买（cudaMalloc 新 block），那确实多了一笔，但等闲鱼卖掉（L2_flat 释放）就回来了。

### 那什么时候会出现真实的 3F？

只有一种典型场景：**各层参数大小不均匀**，导致 L1_flat 的 block 大小 ≠ L3_flat 需要的大小。

例如：

- Layer1 是 embedding（超大参数矩阵，L1_flat = 8F_embed）
- Layer2 是 transformer（中等，L2_flat = 1F_trans）
- Layer3 是 LM head（超大，L3_flat = 8F_embed）

此时分配器的池中可能没有合适的 block 给 L3_flat 复用，需要 cudaMalloc 新物理显存。但即使如此，在 L3 的 wait_for_unshard 释放 L2_flat 后，又会回到 2F。这个”真实 3F”窗口也只持续**一个 `wait_for_unshard` 调用之间**。

**对于均匀的 transformer 层（绝大多数 LLM），各层 flat buffer 大小完全相同，且都在 copy_in_stream 上分配/释放，L3_flat 必然复用 L1_flat 的 block，峰值锁定 2F。**

### 那么 `all_gather_state` 单 slot 到底在防什么？

**不是防 3F（因为 3F 在均匀层下根本不会发生），而是防 N×F 的无限堆积。**

```text
假设没有 all_gather_state 单 slot：
  CPU 提交 → Unsh(L1) 分配 L1_flat
          → Unsh(L2) 分配 L2_flat
          → Unsh(L3) 分配 L3_flat  ← 全都活着，因为没有释放机制！
          → ...直到所有层都分配完
          → 峰值 = 层数 × 1F → OOM

有 all_gather_state 单 slot：
  CPU 提交 → Unsh(L1) → Wait(L1) 存 L1_flat
          → Unsh(L2) → Wait(L2) 释放 L1_flat，存 L2_flat  ← 只有这一刻 alive
          → Unsh(L3) → Wait(L3) 释放 L2_flat，存 L3_flat
          → ...永远只有 1 个 flat alive → 峰值 = 2F
```

`all_gather_state` = **流量控制窗口**，窗口大小 = 1。无论 CPU 多么超前 GPU，flat buffer 同步活跃的数量最多为 1。

### 三张表总结

**`free_storage` 的实质：**

| 你担心的 | 实际发生的 |
| --- | --- |
| GPU 还在读就 resize_(0) 会导致读脏数据 | GPU 命令在提交时已编码物理地址，不受 resize_(0) 影响 |
| resize_(0) 后显存立刻被回收 | 物理显存回到 CUDA 分配器池，标记”最后使用流”，不会在未同步时被跨流覆盖 |
| resize_(0) 后该 block 还”算”占用显存 | 算分配器的缓存（free list），不算活跃使用。PyTorch CUDA allocator 本来就不会把内存归还 OS |

**稳态下每时刻的活跃显存：**

| 时刻 | 活跃 block | 合计 |
| --- | --- | --- |
| Ln 前向计算中 | Ln_param(1F) + Ln_flat(1F) | 2F |
| Ln.post_forward → 释放 Ln_param | Ln_flat(1F) | 1F |
| Ln+1.unshard → 分配 Ln+1_flat | Ln_flat(1F) + Ln+1_flat(1F) | 2F |
| Ln+1.wait → 释放 Ln_flat + 分配 Ln+1_param | Ln+1_param(1F) + Ln+1_flat(1F) | 2F |

**峰值始终 2F，既不短暂也不长期 3F。**

**不同说法正误表：**

| 说法 | 对错 | 原因 |
| --- | --- | --- |
| “峰值 2F，永远不可能 3F” | ✅ | 均匀 transformer 层时成立 |
| “理论上可能有短暂 3F 窗口” | ⚠️ | 仅在非均匀层大小且分配器无可用 block 时可能，对均匀层不成立 |
| “L1 没算完时 L1_param 还在，加上 L2_flat+L2_param+L3_flat=3F” | ❌ | L1param 在 Post(L1) 已 resize(0) 入池，不算活跃；且 L3_flat 复用 L1_flat 的 block |
| “长期都是 3F” | ❌ | 即使有额外 cudaMalloc，L2_flat 在 L3.wait 中被释放，回落到 2F |
| “all_gather_state 单 slot 是为了防 3F” | ❌ | 是为了防 N×F 的无限堆积，即流量控制 |

### 4.9.X.8 深入验证：两种缓冲区的分离生命周期与跨层复用安全性

**读者再次追问：CPU 在 post_forward 执行 `resize_(0)` 释放了 per-param 缓冲区，然后立即下发 L2/L3 的命令。如果此时 main_stream 还在执行 L1 的 forward，L2 的 copy_out 会不会复用刚刚释放的 per-param 缓冲区的显存？如果复用了，会不会读脏数据？**

答案分两层，先给出结论再逐条验证。

### 4.9.X.8.1 三种缓冲区，而非两种

前文 4.9.X.7 定义了 `Lx_flat` 和 `Lx_param` 两类大块。但 `foreach_all_gather` 内部还分配了一个**中转缓冲区**，它和 copy_out 写入的 per-param 缓冲区是两回事。需要精确区分：

| 名称 | 符号 | 大小 | 创建 | 分配流 | 释放 |
| --- | --- | --- | --- | --- | --- |
| AG 结果缓冲区 | Lx_ag_buf | ≈1F | foreach_all_gather → all_gather_copy_in_cuda() 中的 torch.empty()（_fsdp_collectives.py:82-84） | copy_in_stream | 下一组的 wait_for_unshard 设置 all_gather_state = None（_fsdp_param_group.py:291） |
| per-param 缓冲区 | Lx_param | ≈1F | alloc_all_gather_outputs() → alloc_storage()（_fsdp_param.py:660-662），持久 tensor 的 resize_(full_size) | main_stream（copy_out 运行在 device_handle.current_stream() 上） | post_forward → reshard → free_unsharded_param()（_fsdp_param.py:680-684） |
| 分片参数 | Lx_sharded | F/ws | fully_shard 初始化 | — | 整个训练 |

**关键事实**：前文 4.9.X.7 的”Lx_flat”对应的是 `Lx_ag_buf`（`AllGatherResult.all_gather_output`），而 “Lx_param” 对应的是 per-param 缓冲区（`FSDPParam.all_gather_outputs[0]`）。前者是 NCCL all-gather 直接写入和 split_with_sizes_copy 读取的对象，后者是 `torch.as_strided` 视图 `_unsharded_param` 的 backing storage。

`_unsharded_param` 的源码确认（`_fsdp_param.py:510-518`）：

```text
# 默认路径（无 post-all-gather 扩展）：
unsharded_tensor = self.all_gather_outputs[0]  # ← per-param 缓冲区
unsharded_param = torch.as_strided(
    unsharded_tensor,
    self._orig_size,
    self._contiguous_orig_stride,
    storage_offset=0,
)
```

**所以前向计算 %matmul 实际读取的是 per-param 缓冲区 `Lx_param`，而非 AG 结果缓冲区 `Lx_ag_buf`。**

### 4.9.X.8.2 两种缓冲区的生死时刻

```text
CPU 时间线（各事件按提交顺序）:

L1.pre_forward:
  L1.unshard():      L1_ag_buf = torch.empty(F, stream=copy_in_stream)    ← 分配 L1_ag_buf
                     AG kernel on all_gather_stream
  L1.wait_for_unshard():
                     foreach_all_gather_copy_out(...)                      ← 在 main_stream 上
                       alloc_storage(L1_param) → resize_(full)              ← 分配 L1_param
                       split_with_sizes_copy(L1_ag_buf → L1_param)         ← 读取 ag_buf，写入 param
                     _unsharded_param = as_strided(L1_param)               ← 视图
                     comm_ctx.all_gather_state = L1_ag_buf                 ← 存 L1_ag_buf

   ↑ 此时 main_stream 上队列: [copy_out 写入 L1_param] (还未执行完)

L1.forward:          main_stream: L1 matmul ← 读取 L1_param

   ↑ 此时 main_stream 上队列: [copy_out(L1_param)] [matmul(L1)]

L1.post_forward:
  reshard → _to_sharded_post_forward():
    .clone() → 读取 L1_param，写入新的 sharded tensor
    free_unsharded_param() → resize_(0) 释放 L1_param               ← L1_param 入池！
                             最后使用流 = main_stream
  main_stream 上队列: [copy_out] [matmul] [.clone()]
                              ↑ L1_param 的物理地址已编码，安全
                              ↑ resize_(0) 只是 CPU 操作，不影响 GPU 执行

L2.unshard():
  L2_ag_buf = torch.empty(F, stream=copy_in_stream)                    ← 分配 L2_ag_buf
  AG kernel on all_gather_stream

  ↑ 此时 L1_ag_buf 还在 all_gather_state 里，没释放。所以 L2_ag_buf 不能复用 L1_ag_buf 的 block。

L2.wait_for_unshard():
  all_gather_state = None → L1_ag_buf 释放                            ← L1_ag_buf 入池！
                            最后使用流 = copy_in_stream
  alloc_storage(L2_param) → resize_(full) ← 请求 1F on main_stream
    ↑ 池中有 L1_param 的 block（同流 main_stream, 同大小 1F）→ 直接复用！
  split_with_sizes_copy(L2_ag_buf → L2_param) ← 写入 L2_param

L2.forward:          main_stream: L2 matmul ← 读取 L2_param
```

### 4.9.X.8.3 L2 能否复用 L1 的 per-param 缓冲区？→ 能，且安全

**能的原因**：

- `L1_param` 在 `post_forward` 中被 `resize_(0)` 释放，进入池（最后使用流 = main_stream）
- `L2.wait_for_unshard` 中的 `alloc_storage(L2_param)` 请求 1F block，也在 main_stream 上
- 分配器发现池中有同流同大小的 block → **直接复用，零同步开销**

**安全的原因**：**CUDA 同流顺序执行保证**

```text
main_stream GPU 执行顺序（绝对有序）:
  [1] L1.copy_out (split_with_sizes_copy 写入 L1_param)
  [2] L1.forward  matmul (读取 L1_param)
  [3] .clone()  ← post_forward 中的 clone，读取 L1_param 写入 sharded tensor
  [4] L2.copy_out (split_with_sizes_copy 写入 L2_param = 复用 L1_param 的物理地址)
  [5] L2.forward  matmul (读取 L2_param, 同一块物理地址)

  ↑ [1][2][3] 全部完成之前，[4] 绝不可能开始 —— 同流硬件保证
```

CPU 上的 `resize_(0)`（[3] 和 [4] 之间）只是 CPU 侧的元数据操作。GPU 命令队列中的 [3] `.clone()` 和 [4] `split_with_sizes_copy` 都**已经将物理地址编码进 GPU 命令中**，`resize_(0)` 不影响它们。GPU 严格按照 [1]→[2]→[3]→[4]→[5] 的顺序执行。

**结论：`resize_(0)` 释放 → 立即入池 → 下个 copy_out 同流复用 → GPU 同流顺序执行保证安全。没有竞态条件。**

---

### 4.9.X.8.4 L2 能否复用 L1 的 AG 结果缓冲区？→ 不能（释放太晚）

`L1_ag_buf` 被 `all_gather_state` 持有，直到 `L2.wait_for_unshard` 中设置 `all_gather_state = None` 才释放：

```text
# _fsdp_param_group.py:288-291
if self._training_state == TrainingState.FORWARD:  # implicit prefetch
    if prev_all_gather_state := self.comm_ctx.all_gather_state:
        self._wait_all_gather_streams_on_event(prev_all_gather_state.event)
        self.comm_ctx.all_gather_state = None  # ← L1_ag_buf 在这释放
```

但 `L2_ag_buf` 的分配发生在 `L2.unshard()` 中，**远早于** `L2.wait_for_unshard()`：

```text
# L2.pre_forward:
#   L2.unshard()       → 分配 L2_ag_buf       ← 此时 L1_ag_buf 还活着
#   L2.wait_for_unshard()
#     → all_gather_state = None  → L1_ag_buf 释放（晚了）
```

所以 L2 的 AG 结果缓冲区**必然是新 `cudaMalloc`**，无法复用 L1_ag_buf。

---

### 4.9.X.8.5 L3 复用 L1 的 AG 结果缓冲区 → 能（隔层复用）

`L1_ag_buf` 在 `L2.wait_for_unshard` 中被释放（最后使用流 = copy_in_stream）。`L3.unshard` 调用 `foreach_all_gather` → `all_gather_copy_in_cuda()` 中的 `torch.empty(F, device=device)` 在 copy_in_stream 上分配 → 发现池中有同流同大小的 `L1_ag_buf` → **复用**。

类似地，`L2_ag_buf` 在 `L3.wait_for_unshard` 中被释放，供 `L4.unshard` 复用。**AG 结果缓冲区是隔层复用的，不跳过邻居。**

```text
AG 结果缓冲区复用链:
  L1_ag_buf → (L2 来不及复用) → L3_ag_buf → (L4 来不及复用) → L5_ag_buf → ...
  L2_ag_buf → (L3 来不及复用) → L4_ag_buf → (L5 来不及复用) → L6_ag_buf → ...
```

Per-param 缓冲区也有同样的隔层复用模式（奇数层共享一组 block，偶数层共享另一组）。

### 4.9.X.8.6 Copy-Out 在哪个流上运行？（一个常见的误解）

很多读者直觉认为 “copy-out 应该跑在 copy_in_stream 上”。但实际上：

```text
# _fsdp_param_group.py:292-297
with record_function(self._with_fqn("FSDP::all_gather_copy_out")):
    foreach_all_gather_copy_out(
        self._all_gather_result,
        self.fsdp_params,
        self._all_gather_process_group,
    )
```

`foreach_all_gather_copy_out` **没有切换流**。它运行在 `device_handle.current_stream()` 上，也就是 main_stream（默认流）。对比一下：

| 阶段 | 函数 | 运行流 | 分配的缓冲区 |
| --- | --- | --- | --- |
| Copy-In (CI) | foreach_all_gather → all_gather_copy_in_cuda() | copy_in_stream | AG 结果缓冲区 |
| All-Gather | dist.all_gather_into_tensor() | all_gather_stream | 写入 AG 结果缓冲区 |
| Copy-Out (CO) | foreach_all_gather_copy_out → split_with_sizes_copy() | main_stream（当前流） | per-param 缓冲区 |

所以 per-param 缓冲区在 main_stream 上分配和释放，AG 结果缓冲区在 copy_in_stream 上分配、all_gather_stream 上写入、main_stream 上读取。

这个流归属直接影响复用决策：

- L1_param（main_stream）→ L2 的 copy_out 也在 main_stream → 同流复用
- L1_ag_buf（copy_in_stream 分配，main_stream 读取）→ 释放时 allocator 记录为 copy_in_stream 最后使用 → L2 的 copy_in 在 copy_in_stream 上分配新 ag_buf → **如果 L1_ag_buf 已经释放**，同流复用

| 事件 | L1_ag_buf | L1_param | L2_ag_buf | L2_param | L3_ag_buf | L3_param | 活跃合计 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| ① Unsh(L1) | ① 分配 | — | — | — | — | — | 1F |
| ② Wait(L1) | 存 state | ② alloc | — | — | — | — | 2F |
| ③ Fwd(L1) | 存 state | 活跃 | — | — | — | — | 2F |
| ④ Post(L1) | 存 state | ④ resize_(0) | — | — | — | — | 1F |
| ⑤ Unsh(L2) | 存 state | 池 | ⑤ alloc | — | — | — | 2F |
| ⑥ Wait(L2) | ⑥ state=None | 池 | 存 state | ⑥ alloc←复用④ | — | — | 2F |
| ⑦ Fwd(L2) | 池 | 池 | 存 state | 活跃 | — | — | 2F |

**注**：

- `L2_param` 复用了 `L1_param` 的 block（④→⑥，同流 main_stream，同大小 F）
- `L3_ag_buf` 复用了 `L1_ag_buf`（或 `L2_ag_buf`）的 block（copy_in_stream，同大小 F）
- `L3_param` 复用了 `L2_param` 的 block（main_stream，同大小 F）
- **稳态下不需要任何新的 `cudaMalloc`**（第一次循环除外）

### 4.9.X.8.8 `memory_allocated` vs `memory_reserved`：池中的缓存算不算”FSDP 的内存”？

之前的讨论忽略了 CUDA 缓存分配器的一个重要行为：**`resize_(0)` 归还给池的 block 不会被分配器还给 OS**。池中的缓存反映在 `torch.cuda.memory_reserved()` 中，但 `torch.cuda.memory_allocated()` 已经归零。

```text
tensor_held = torch.cuda.memory_allocated()   # tensor 实际持有的
driver_reserved = torch.cuda.memory_reserved() # 分配器从 CUDA driver 要来的（含池中缓存）
gap = driver_reserved - tensor_held            # 池中缓存
```

FSDP 稳态下：

| 指标 | 值 | 说明 |
| --- | --- | --- |
| memory_allocated | 2F + sharded | 当前层 param(1F) + 当前层 ag_buf(1F) + 各层 sharded |
| memory_reserved | 2~4F + sharded | 上述 allocated + 池中缓存(0~2F) |

池中的 0~2F 来自刚刚释放的 L(n-1)_param（main_stream 池）和 L(n-1)_ag_buf（copy_in_stream 池）。它们之所以在池中，**不是 FSDP 的特殊问题**，而是 PyTorch CUDA 缓存分配器的默认行为：

```text
x = torch.empty(1_000_000_000, device='cuda')  # alloc: 4GB
del x
print(torch.cuda.memory_reserved() / 1e9)      # 仍 ~4GB（没有归还！）
```

**池中缓存不随层数增加**，它是一个固定的小常数（≈1~2F）。对于 OOM 分析，**真正关键的是 `memory_allocated`（= 2F + sharded），池中的缓存只是分配器平滑分配的手段。**

---

### 4.9.X.8.9 总结：三句话回答所有内存问题

1. **Per-param 缓冲区**（`Lx_param`）：post_forward 释放 → 下个 copy_out 同流复用 → 同流顺序执行保安全 → `memory_allocated` 峰值 2F
2. **AG 结果缓冲区**（`Lx_ag_buf`）：下一组的 wait_for_unshard 释放 → 隔层复用 → 不会导致邻居层同时持有两块 AG buf
3. **`memory_reserved` 中的池缓存**（0~2F）：不是 FSDP 特有问题，是 CUDA 分配器的通用行为，不随层数增长，不影响 OOM

**FSDP 的内存安全性不依赖 CUDA 跨流同步，而依赖：**

- **同流顺序执行**（per-param 缓冲区：释放和重分配同在 main_stream）
- **单 slot 流量控制**（AG 结果缓冲区：`all_gather_state` 窗口 = 1，同步活跃不超过 1 个）
- **分配器流跟踪**（跨流场景下，allocator 自动插入 `wait_event` 保证安全）

### 4.10 `pre_backward()` / `post_backward()` —— 反向 hook 逻辑

```text
def pre_backward(self, default_prefetch, *unused):
    self._training_state = TrainingState.PRE_BACKWARD
    self.unshard(self.unshard_async_op)    # 可能是空操作（如果已预取）
    self.wait_for_unshard()                # 等待完成
    if default_prefetch:
        self._backward_prefetch()          # 预取前一组（前向顺序的上一个）

def post_backward(self, *unused):
    self._training_state = TrainingState.POST_BACKWARD
    # 1. 累积梯度
    for fsdp_param in self.fsdp_params:
        fsdp_param.accumulate_unsharded_grad_if_needed()
    # 2. 收集有梯度的参数
    fsdp_params_with_grad = []
    unsharded_grads = []
    for fsdp_param in self.fsdp_params:
        if fsdp_param.unsharded_param.grad is not None:
            fsdp_params_with_grad.append(fsdp_param)
            unsharded_grads.append(fsdp_param.unsharded_grad_data)
            fsdp_param.unsharded_param.grad = None
    # 3. 如果需要，reshard
    if self.reshard_after_backward:
        self.reshard()
    # 4. 执行 Reduce-Scatter
    if len(fsdp_params_with_grad) > 0:
        # 等待上一个 RS 完成
        if self.comm_ctx.reduce_scatter_state is not None:
            self.device_handle.current_stream().wait_event(
                self.comm_ctx.reduce_scatter_state.event)
            self.comm_ctx.reduce_scatter_state = None
        
        # 启动当前 RS
        foreach_reduce(
            fsdp_params_with_grad, unsharded_grads,
            reduce_scatter_group,
            self.comm_ctx.reduce_scatter_stream,
            ...
        )
        # 保存当前 RS 状态供下一个组等待
```

### 4.11 `_backward_prefetch()` —— 反向预取（第 491 行）

```text
def _backward_prefetch(self):
    if self._training_state == TrainingState.PRE_BACKWARD:
        curr_index = self._post_forward_indices.pop()
        target_index = curr_index - 1
        if target_index < 0:
            return
        target_group = self.comm_ctx.post_forward_order[target_index]
        self._prefetch_unshard(target_group, "backward")
```

**原理**：`post_forward_order` 记录的是所有参数组前向执行的顺序。反向时，当前组（例如组 3）预取它前向顺序中的上一个组（组 2）。

```text
前向顺序: [组1, 组2, 组3, 组4]
反向梯度计算顺序: 组4 → 组3 → 组2 → 组1

组4 计算梯度时 → _backward_prefetch() 触发组3 的 unshard()
组3 计算梯度时 → _backward_prefetch() 触发组2 的 unshard()
...
```

这样组 N 的 All-Gather 就和组 N+1 的梯度计算重叠了。

### 4.12 `_register_post_backward_hook()` —— 反向 hook 注册（第 564 行）

```text
def _register_post_backward_hook(self, args, kwargs):
    # 找出需要梯度的输入张量
    inp_tensors = [t for t in args+kwargs if t.requires_grad]
    # 用 RegisterPostBackwardFunction.apply 替换它们
    inp_tensors = RegisterPostBackwardFunction.apply(self, *inp_tensors)
    return args, kwargs
```

**核心机制**：`RegisterPostBackwardFunction` 是一个自定义的 `torch.autograd.Function`：

```text
class RegisterPostBackwardFunction(torch.autograd.Function):
    @staticmethod
    def forward(ctx, param_group, *inputs):
        ctx.param_group = param_group
        return inputs
    
    @staticmethod
    def backward(ctx, *grads):
        ctx.param_group.post_backward()   # ← 在反向传播时被调用！
        return (None,) + grads
```

**原理**：

1. 前向时，用 `RegisterPostBackwardFunction` 包装输入张量
2. 反向传播时，autograd 引擎执行 `RegisterPostBackwardFunction.backward()`
3. 在 backward 中调用 `param_group.post_backward()` → 触发 Reduce-Scatter

这样 FSDP 就”钩”上了 autograd 的反向传播链。

```text
    all_gather_stream.wait_stream(all_gather_copy_in_stream)

    with device_handle.stream(all_gather_stream):

            input_tensor=all_gather_input,
```

### 5.3 `all_gather_copy_in_cuda()` —— Copy-In 自定义算子（第 73 行）

```text
def all_gather_copy_in_cuda(all_gather_inputs, inp_split_sizes, 
                            all_gather_input_numel, world_size, rank, dtype, device):
    # 分配输出：所有 rank 的数据拼在一起
    all_gather_output = torch.empty((all_gather_input_numel * world_size,), dtype=dtype, device=device)
    # 当前 rank 的输入位置：第 rank 段
    all_gather_input = all_gather_output.narrow(0, all_gather_input_numel * rank, all_gather_input_numel)
    # 把多个输入拷贝到正确位置
    foreach_copy_dsts = torch.split(all_gather_input, inp_split_sizes)
    torch._foreach_copy_(foreach_copy_dsts, all_gather_inputs)
    return all_gather_input, all_gather_output
```

**注意**：`all_gather_input` 和 `all_gather_output` 是**同一个 storage 的视图**：

```text
all_gather_output = [ rank0_data | rank1_data | rank2_data | rank3_data ]
                          ↑ 这就是 all_gather_input
```

所以 `dist.all_gather_into_tensor` 的 `input_tensor` 和 `output_tensor` 实际上指向同一块内存的不同部分。NCCL 的 All-Gather 操作会把其他 rank 的数据填充到对应的位置。

- 同步 All-Gather 流，确保前一次的优化器步骤已完成
- 如果用户设置了 `post_optim_event`（`set_post_optim_event()`），用更精确的事件同步替代流同步

### 6.5 `_lazy_init()` —— 懒初始化（第 138 行）

```text
def _lazy_init(self):
    if self._is_root is not None:
        return  # 已经初始化
    
    self._is_root = True
    root_module = self._modules[0]
    
    # 遍历所有子模块，收集 FSDP 状态
    for module_name, module in root_module.named_modules():
        if (state := _get_module_fsdp_state(module)) is None:
            continue
        if module is not root_module:
            state._is_root = False
        self._state_ctx.all_states.append(state)
    
    # 根模块 post_forward_mesh_info = None（不 reshard）
    if self._fsdp_param_group:
        self._fsdp_param_group.post_forward_mesh_info = None
    
    # 共享状态（通信上下文、状态上下文）
    self._init_shared_state()  # ← 关键：所有 state 共享同一个 comm_ctx
    
    # 所有参数组 lazy_init
    for state in self._state_ctx.all_states:
        if state._fsdp_param_group:
            state._fsdp_param_group.lazy_init()
```

### 6.7 `_post_forward()` —— 模块前向后处理 hook（第 237 行）

```text
@disable_if_config_true
def _post_forward(self, module, input, output):
    if self._training_state == TrainingState.PRE_BACKWARD:
        return output  # activation checkpointing 情况
    
    if self._fsdp_param_group:
        output = self._fsdp_param_group.post_forward(module, input, output)  # reshard
    
    output = self._register_pre_backward_hook(output)  # 注册反向 hook
    
    self._training_state = TrainingState.IDLE
    
    # 如果是根模块：释放最后的 all_gather_state
    if self._state_ctx.iter_forward_root is self:
        if all_gather_state := self._comm_ctx.all_gather_state:
            self._comm_ctx.all_gather_copy_in_stream.wait_event(all_gather_state.event)
            self._comm_ctx.all_gather_stream.wait_event(all_gather_state.event)
            self._comm_ctx.all_gather_state = None
        self._state_ctx.iter_forward_root = None
    
    # 混合精度：cast 输出
    if self._mp_policy.output_dtype is not None:
        output = tree_map(partial(_cast_fp_tensor, self._mp_policy.output_dtype), output)
    
    return output
```

### 6.8 `_pre_backward()` —— 反向预处理 hook（第 264 行）

由 `_register_pre_backward_hook` 注册到输出张量上：

```text
def _register_pre_backward_hook(self, output):
    if not torch.is_grad_enabled():
        return output
    flat_outputs, _ = tree_flatten(output)
    for t in flat_outputs:
        if torch.is_tensor(t) and t.requires_grad:
            t.register_hook(self._pre_backward)  # ← 注册 hook
    return output
```

**原理**：PyTorch autograd 在反向传播时，当一个张量的梯度被计算出来即将传给上游时，会调用它的 hook。这个 hook 触发了 FSDP 的反向预处理（重新 All-Gather 参数）。

```text
def _pre_backward(self, grad):
    self._training_state = TrainingState.PRE_BACKWARD
    self._register_root_post_backward_final_callback()  # 注册 final callback
    if self._fsdp_param_group:
        default_prefetch = len(self._states_to_backward_prefetch) == 0
        self._fsdp_param_group.pre_backward(default_prefetch)  # unshard + 预取
    # 显式反向预取
    for fsdp_state in self._states_to_backward_prefetch:
        if (target := fsdp_state._fsdp_param_group) is not None:
            FSDPParamGroup._prefetch_unshard(target, "backward")
    return grad
```

### 6.9 `_root_post_backward_final_callback()` —— 反向最终回调（第 275 行）

```text
def _root_post_backward_final_callback(self):
    for state in self._state_ctx.all_states:
        fsdp_param_group = state._fsdp_param_group
        if fsdp_param_group and fsdp_param_group._training_state != POST_BACKWARD:
            fsdp_param_group.post_backward()  # 处理未被执行 post_backward 的组
        state._training_state = TrainingState.IDLE
        if fsdp_param_group:
            fsdp_param_group._training_state = TrainingState.IDLE
        if self._state_ctx.is_last_backward:
            state._finalize_backward()  # 等待所有通信完成
    
    if self._state_ctx.is_last_backward:
        self._comm_ctx.post_forward_order.clear()
        if self._comm_ctx.reduce_scatter_state is not None:
            # 等待最后一个 RS 完成
            self._device_handle.current_stream().wait_event(
                self._comm_ctx.reduce_scatter_state.event)
            self._comm_ctx.reduce_scatter_state = None
```

**为什么还需要这个 final callback？** 因为有些前向输入可能不需要梯度，导致 `RegisterPostBackwardFunction` 的 backward 不会被调用。这个 callback 确保所有参数组都被正确处理。

### 预备知识：CUDA Stream 和 Event 零基础入门

> 如果你对 CUDA Stream（流）和 Event（事件）完全不了解，本节会从零开始用 Python 代码示例带你入门。

### 1. 先理解 GPU 的执行模型

**CPU 是顺序执行的**：做完 A，再做 B，再做 C。

**GPU 不同**：GPU 可以同时做多件事。例如：

- 一边做矩阵乘法（计算）
- 一边从显存拷贝数据（拷贝）
- 一边做网络通信（NCCL）

但这需要你**显式地告诉 GPU 哪些事情可以并行**。这就是 Stream 的作用。

### 2. Stream（流）是什么？

**Stream 就是 GPU 上的一个执行队列。** 同一个 Stream 里的操作**按顺序执行**。不同 Stream 里的操作**可以并行执行**。

打个比方：

- Stream = 工厂里的一条流水线
- 一个流水线上的工人按顺序做事
- 多条流水线可以同时开工

```text
import torch

# 创建两条 CUDA 流
stream1 = torch.cuda.Stream()
stream2 = torch.cuda.Stream()

# 创建两个张量
a = torch.randn(1000, 1000, device='cuda')
b = torch.randn(1000, 1000, device='cuda')

# ===== 默认流（主计算流）=====
# 不指定流时，所有操作都在"默认流"（default stream）上执行
c = torch.mm(a, b)  # 在默认流上做矩阵乘法

# ===== 使用独立流 =====
with torch.cuda.stream(stream1):
    d = torch.mm(a, b)  # 在 stream1 上做矩阵乘法

with torch.cuda.stream(stream2):
    e = torch.mm(a, b)  # 在 stream2 上做矩阵乘法

# 上面三个矩阵乘法可能同时执行（如果 GPU 资源充足）
```

### 3. 为什么需要多条 Stream？

**一个典型的场景**：

```text
# ===== 场景：没有 Stream 的情况（一切都在默认流）=====
# 假设我们要做三件事：
#   1. 从 CPU 拷贝数据到 GPU（H2D copy）
#   2. 在 GPU 上做计算
#   3. 从 GPU 拷贝结果回 CPU（D2H copy）

# 默认流中：顺序执行，GPU 利用率低
data_cpu = torch.randn(1000, 1000)
data_gpu = data_cpu.cuda()           # 步骤 1：H2D 拷贝（占用拷贝引擎）
result = torch.mm(data_gpu, data_gpu)  # 步骤 2：计算（等步骤 1 完成）
result_cpu = result.cpu()             # 步骤 3：D2H 拷贝（等步骤 2 完成）
# 总时间 = T_copy_in + T_compute + T_copy_out

# ===== 使用多条 Stream =====
# 如果前面还有另一批数据要处理，可以用 Stream 让拷贝和计算重叠
stream_copy = torch.cuda.Stream()
stream_compute = torch.cuda.Stream()

# 下一批数据：在 copy 流上做 H2D
with torch.cuda.stream(stream_copy):
    next_data = next_data_cpu.cuda(non_blocking=True)  # non_blocking 是关键！

# 主计算流可以同时处理当前批次，不需要等拷贝完成
current_result = torch.mm(current_data, current_data)
# ↑ 这和上面的 H2D 拷贝是同时进行的！

# 总时间 ≈ max(T_copy_in, T_compute)（重叠了！）
```

### 4. Event（事件）是什么？

**Event 是一个”时间戳”**，标记某个流在某个时刻已经执行到的位置。

```text
# ===== Event 示例 =====
stream_a = torch.cuda.Stream()
stream_b = torch.cuda.Stream()

# 在 stream_a 上做计算，并记录事件
with torch.cuda.stream(stream_a):
    x = torch.mm(a, b)
    event_a_done = stream_a.record_event()  # 记录"stream_a 的矩阵乘法做完了"

# 在 stream_b 上做其他事，但需要等 stream_a 完成
stream_b.wait_event(event_a_done)  # ← stream_b 在这里等 stream_a 到 event 位置
with torch.cuda.stream(stream_b):
    y = torch.mm(x, c)  # 使用 x，确保 stream_a 已算出 x
```

**关键区别**：

| 方法 | 含义 | 粒度 |
| --- | --- | --- |
| stream_b.wait_stream(stream_a) | stream_b 等 stream_a 所有已提交的操作完成 | 粗粒度 |
| stream_b.wait_event(event) | stream_b 等 stream_a 执行到 event 那个时间点即可 | 细粒度 |

```text
# ===== wait_stream vs wait_event 对比 =====
stream_a = torch.cuda.Stream()
stream_b = torch.cuda.Stream()

# stream_a 上有很多操作
with torch.cuda.stream(stream_a):
    x = torch.mm(a, b)      # 操作 1
    event_mid = stream_a.record_event()  # ← 中间事件
    y = torch.mm(x, c)      # 操作 2
    z = torch.mm(y, d)      # 操作 3

# ===== 方式 1：wait_stream（等所有）=====
stream_b.wait_stream(stream_a)
# stream_b 要等操作 1、2、3 全部完成才能开始
# 安全但可能等太久

# ===== 方式 2：wait_event（等到特定位置）=====
stream_b.wait_event(event_mid)
# stream_b 只要等操作 1 完成即可，不需要等 2 和 3
# 更精细的控制！
```

### 4.1 FSDP 源码中 wait_stream 和 wait_event 的选择规律

这是理解 FSDP 流同步的关键，我们直接看源码中所有同步点：

```text
# ===== wait_stream（共 3 处）：用在"首次建立依赖"时 =====

# ① foreach_all_gather() —— All-Gather 流等 Copy-In 流
all_gather_stream.wait_stream(all_gather_copy_in_stream)
# 原因：这是第一次同步，All-Gather 需要 Copy-In 流上【所有】准备好的数据

# ② foreach_reduce() —— RS 流等主计算流
reduce_scatter_stream.wait_stream(current_stream)  # current_stream = main_stream
# 原因：这是第一次同步，RS 需要主流上【所有】梯度拷贝工作完成

# ③ _root_pre_forward() —— 所有 All-Gather 相关流等主计算流
all_gather_copy_in_stream.wait_stream(current_stream)
all_gather_stream.wait_stream(current_stream)
# 原因：这是新迭代的第一次，需要等上一步优化器【所有】收尾工作完成

# ===== wait_event（共 6 处）：用在"循环流水线中精确同步"时 =====

# ① Copy-Out 时等 All-Gather 完成
main_stream.wait_event(all_gather_event)
# 我只等 All-Gather 完成，后续 RS 流上的其他事（如果有）不必等

# ② 下一组 Copy-In 等上一组 Copy-Out 完成（隐式预取核心）
all_gather_copy_in_stream.wait_event(prev_all_gather_state.event)
all_gather_stream.wait_event(prev_all_gather_state.event)
# 我只等上一组 Copy-Out 那一刻，不必等上一组后续的前向计算

# ③ 下一组等上一组 Reduce-Scatter 完成
main_stream.wait_event(prev_reduce_scatter_state.event)
# 我只等上一组 RS 完成，不必等它后续的后处理

# ④ 反向收尾等 Post-Reduce 完成
main_stream.wait_event(post_reduce_event)
# 我只等本组 RS 后处理完成

# ⑤ 有优化器事件时等的也是 event（比 wait_stream 更精确）
all_gather_copy_in_stream.wait_event(post_optim_event)
```

**规律总结**：

| 场景 | 用哪个？ | 为什么？ |
| --- | --- | --- |
| 两条流第一次建立依赖，需要对方流上全部工作完成 | wait_stream | 简单粗暴，一次性等完所有 |
| 后续循环中，只需要对方流上某一个特定时刻完成 | wait_event | 精确同步，避免等无关操作，最大化重叠 |

**用工厂流水线类比**：

- `wait_stream` = “等 1 号流水线**整条线停工**我再开工”（第一次交接必须这样，确保前一批全部处理完）
- `wait_event` = “等 1 号流水线**某个零件走下传送带**我就开工”（后续循环中，不需要等这个零件的后续加工完成）

FSDP 中 `wait_stream` 只用在 3 处**首次依赖建立**，其余 6 处循环同步全部用 `wait_event`，就是为了在保证正确的前提下最大化通信与计算的重叠。

### 4.2 深入分析：为什么不能全用 wait_event 替代 wait_stream？

有了上面的规律，你可能会问：**既然 `wait_event` 更精确，为什么不把 3 处 `wait_stream` 也换成 `wait_event`？**

我们逐一分析这 3 处：

### ① `all_gather_stream.wait_stream(all_gather_copy_in_stream)`

```text
with device_handle.stream(all_gather_copy_in_stream):
    # Copy-In 是一整块连续的工作：
    param_all_gather_inputs = _get_param_all_gather_inputs(fsdp_params)  # 获取输入
    ...
    all_gather_input, all_gather_output = torch.ops.fsdp.all_gather_copy_in(...)  # 分配+拷贝
    # ↑ 这些操作做完才能开始 All-Gather，中间没有"做到一半就能 All-Gather"的时机

# 如果用 wait_event 替代，你需要在 Copy-In 结束时 record_event：
#     copy_in_done = all_gather_copy_in_stream.record_event()
#     all_gather_stream.wait_event(copy_in_done)
# 但这和 wait_stream 的效果完全等价——都是"等 Copy-In 全部完成"。
```

**结论**：可以换，但效果一样。`wait_stream` 更简洁，还省去了创建 `Event` 对象的 CPU 开销。

### ② `reduce_scatter_stream.wait_stream(current_stream)`

同理——梯度 Copy-In（`foreach_reduce_scatter_copy_in`）也是一整块连续工作，没有中间点可以精确等待。

```text
# 主计算流上的梯度 Copy-In 是一口气做完的：
foreach_reduce_scatter_copy_in(unsharded_grads, reduce_scatter_input, world_size)
unsharded_grads.clear()
# ↑ 这两个操作中间没有"RS 可以做一部分"的时刻
```

**结论**：同样可以换，但等价且冗余。

### ③ `_root_pre_forward()` 中的 wait_stream（最关键！）

```text
# _fsdp_state.py _root_pre_forward()
if (event := self._state_ctx.post_optim_event) is not None:
    # ===== 用户提供了精确事件 → 用 wait_event =====
    self._comm_ctx.all_gather_copy_in_stream.wait_event(event)
    self._comm_ctx.all_gather_stream.wait_event(event)
else:
    # ===== 用户没提供事件 → 退化为 wait_stream =====
    current_stream = self._device_handle.current_stream()
    self._comm_ctx.all_gather_copy_in_stream.wait_stream(current_stream)
    self._comm_ctx.all_gather_stream.wait_stream(current_stream)
```

**FSDP 其实给了你选择！**

- 如果你在优化器步骤后显式调用 `module.set_post_optim_event(event)`，FSDP 就用更精确的 `wait_event`
- 如果你没提供，FSDP **不知道你优化器之后还做了什么**（可能还有数据预处理、其他前向、梯度裁剪等），所以只能用 `wait_stream` 保守地等主流上**所有已提交的工作**完成

### 综合分析

| wait_stream 位置 | 能否替换为 wait_event？ | 为什么不换？ |
| --- | --- | --- |
| AG 流等 Copy-In 流 | 能，效果完全等价 | 等价但省 Event 对象开销 |
| RS 流等主流梯度拷贝 | 能，效果完全等价 | 同上 |
| 根 pre-forward 主流→AG 流 | 能（有 post_optim_event 时已用） | 用户不提供事件时不知道等哪个点，只能 wait_stream 兜底 |

**一句话总结**：不是”不能”，而是：

- **2 处**等价但没必要换（`wait_stream` 更轻量）
- **1 处**已经给了你升级途径——用 `set_post_optim_event` 提供精确事件，否则 `wait_stream` 是保守安全的退路

### 5. 用代码模拟 FSDP 的 Stream 使用模式

让我们用简化的代码来模拟 FSDP 前向时的多流协作：

```text
import torch
import torch.distributed as dist

# ===== 模拟 FSDP 的流设置 =====
# 对应 FSDPCommContext.lazy_init()
device = torch.device('cuda')
high_priority = -1

# 流 1：用于 All-Gather 之前的 Copy-In（dtype 转换 + 数据拼接）
all_gather_copy_in_stream = torch.cuda.Stream(priority=high_priority)

# 流 2：用于 All-Gather 集体通信（NCCL）
all_gather_stream = torch.cuda.Stream(priority=high_priority)

# 主计算流（PyTorch 默认）
main_stream = torch.cuda.current_stream()

# ===== 模拟两个参数组的前向 =====
# 假设：
# - 组 1 有参数 p1（形状 [100, 100]）
# - 组 2 有参数 p2（形状 [200, 200]）
# - world_size = 4

world_size = 4
rank = 0  # 假设是 rank 0

# 组 1 的 sharded 参数（每个 rank 持有 25 行）
p1_sharded = torch.randn(25, 100, device='cuda')
# 组 2 的 sharded 参数
p2_sharded = torch.randn(50, 200, device='cuda')

print("=== 演示 FSDP 前向的 Stream 协作 ===")
print(f"组 1 分片大小: {p1_sharded.shape}")
print(f"组 2 分片大小: {p2_sharded.shape}")

# ========== 组 1 的 pre_forward ==========
print("\n--- 组 1: pre_forward ---")

# Step 1: 在 copy_in_stream 上做 Copy-In
with torch.cuda.stream(all_gather_copy_in_stream):
    # 分配组 1 的 All-Gather 输出缓冲区
    p1_ag_output = torch.empty(25 * 100 * world_size, dtype=p1_sharded.dtype, device='cuda')
    # 把当前 rank 的分片拷到正确位置
    p1_ag_output.narrow(0, 25*100*rank, 25*100).copy_(p1_sharded.view(-1))
    print(f"  [copy_in_stream] 组 1 Copy-In 完成, 缓冲区大小: {p1_ag_output.shape}")

# Step 2: 同步到 all_gather_stream，然后启动 All-Gather
all_gather_stream.wait_stream(all_gather_copy_in_stream)

with torch.cuda.stream(all_gather_stream):
    # 模拟 All-Gather：实际上应该用 dist.all_gather_into_tensor
    # 这里用 torch.distributed 的简化模拟
    # 执行后 p1_ag_output 包含所有 rank 的数据
    p1_ag_event = all_gather_stream.record_event()
    print(f"  [all_gather_stream] 组 1 All-Gather 启动")

# Step 3: 在主计算流上等待 All-Gather 完成，然后 Copy-Out
main_stream.wait_event(p1_ag_event)
# Copy-Out：把 p1_ag_output 拆分成完整参数
p1_unsharded = p1_ag_output.view(world_size, -1).reshape(100, 100)
print(f"  [main_stream] 组 1 Copy-Out 完成, 完整参数形状: {p1_unsharded.shape}")

# ========== 组 2 的 pre_forward（与组 1 的计算重叠）==========
print("\n--- 组 2: pre_forward（与组 1 的计算重叠）---")

# 组 1 的计算可以在 main_stream 上开始...
# 同时，组 2 的 unshard 可以在独立流上开始！

# 组 2 的 Copy-In（在 copy_in_stream 上，和组 1 的计算并行）
with torch.cuda.stream(all_gather_copy_in_stream):
    p2_ag_output = torch.empty(50*200*world_size, dtype=p2_sharded.dtype, device='cuda')
    p2_ag_output.narrow(0, 50*200*rank, 50*200).copy_(p2_sharded.view(-1))
    print(f"  [copy_in_stream] 组 2 Copy-In 完成（和组 1 的计算同时进行！）")

all_gather_stream.wait_stream(all_gather_copy_in_stream)
with torch.cuda.stream(all_gather_stream):
    # 组 2 的 All-Gather 也在独立流上
    p2_ag_event = all_gather_stream.record_event()
    print(f"  [all_gather_stream] 组 2 All-Gather 启动")

print("\n=== 模拟结束 ===")
print("结论: Copy-In / All-Gather 和计算在不同流上，三者可以并行！")
```

运行这个示例，你会看到不同的操作理论上可以在不同流上同时执行。

### 6. FSDP 中的 Event 使用总结

FSDP2 源码中用到的所有 Event：

```text
# ===== 类型 1：All-Gather 完成事件 =====
# 在 all_gather_stream 上 record
# 在 main_stream（for Copy-Out）上 wait
all_gather_event = all_gather_stream.record_event()
# ... 在 main_stream 中：
main_stream.wait_event(all_gather_event)  # 等 All-Gather 完成再 Copy-Out

# ===== 类型 2：Copy-Out 完成事件 =====
# 在 main_stream 上 record
# 在 all_gather_copy_in_stream/all_gather_stream（给下一组）上 wait
all_gather_copy_out_event = main_stream.record_event()
# ... 在下一组的 unshard 中：
all_gather_copy_in_stream.wait_event(all_gather_copy_out_event)  # 等上一组 Copy-Out 完成再开始 Copy-In

# ===== 类型 3：Reduce-Scatter 完成事件 =====
# 在 reduce_scatter_stream 上 record
# 在 main_stream（post_backward 或下一组）上 wait
reduce_scatter_event = reduce_scatter_stream.record_event()
# ... 在下一组的 post_backward 中：
main_stream.wait_event(reduce_scatter_event)  # 等上一组 RS 完成再开始本组 RS

# ===== 类型 4：Post-Reduce 事件 =====
# 标记 Reduce-Scatter 后的所有操作（divide、dtype 转换、梯度赋值）完成
post_reduce_event = post_reduce_stream.record_event()
# 在 finalize_backward 中 wait

# ===== 类型 5：重切分完成事件 =====
# 在 main_stream（post_forward reshard）上 record
# 在 all_gather 流（下次 unshard）上 wait
reshard_after_forward_event = main_stream.record_event()
# ... 下次 unshard 中：
all_gather_copy_in_stream.wait_event(reshard_after_forward_event)
all_gather_stream.wait_event(reshard_after_forward_event)

# ===== 类型 6：梯度卸载完成事件 =====
# 在 reduce_scatter_stream 上 record
# 在 finalize_backward 中 synchronize（阻塞 CPU 线程等待）
grad_offload_event = reduce_scatter_stream.record_event()
# ... finalize_backward 中：
fsdp_param.grad_offload_event.synchronize()  # 确保 D2H 拷贝完成

# ===== 类型 7：优化器完成事件 =====
# 用户提供（在优化器步骤后 record）
# 在 root_pre_forward 中 wait
post_optim_event = current_stream.record_event()  # 用户代码中
# ... root_pre_forward 中：
all_gather_copy_in_stream.wait_event(post_optim_event)
all_gather_stream.wait_event(post_optim_event)
```

### 以 pre_forward 为例：为什么需要这么多 Stream？

### 问题 1：如果不使用多 Stream 会怎样？

假设没有独立流，一切都在默认流（main stream）上顺序执行：

```text
# ===== 朴素版本：无多流，顺序执行 =====
def pre_forward_naive(param_group):
    # 步骤 1：Copy-In（参数拼接 + dtype 转换）
    all_gather_input = concat_and_cast(param_group.params)
    
    # 步骤 2：All-Gather 集体通信
    all_gather_output = dist.all_gather_into_tensor(all_gather_input)
    
    # 步骤 3：Copy-Out（拆分输出到各参数）
    for param in param_group.params:
        param.data = extract_from_all_gather_output(all_gather_output, param)
    
    # 步骤 4：前向计算 ← 要等以上全部完成！
    # 时间线：|Copy-In|AG|Copy-Out|Forward|
    # 没有任何重叠！
```

**问题**（三条流都在默认流上串行）：

- Copy-In 时（dtype 转换 + GPU 显存拼接），NCCL 网卡引擎空闲
- All-Gather 时（NCCL 通信），GPU 计算引擎空闲
- 下一组的 Copy-In 要等当前组全部完成才能开始
- 本应并行利用的不同硬件资源（GPU 计算单元、显存控制器、NCCL 网卡）被迫串行

### 问题 2：FSDP 的 3 条 All-Gather 相关流分别干什么？

```text
# ===== 流 1：all_gather_copy_in_stream =====
# 作用：负责 All-Gather 前的数据准备
# 具体任务：
#   1. dtype 转换（如 fp32 → bf16）—— 走 GPU 计算单元（CUDA core）
#   2. 多个参数的 sharded data 拼接到连续缓冲区 —— 走 GPU 显存带宽（显存←→显存）
#   3. CPU offload 时的 H2D 拷贝 —— 走 PCIe 总线
#
# 为什么单独一条流？
#   - Copy-In 操作的是 GPU 内部的【计算资源 + 显存带宽】
#   - All-Gather 操作的是 GPU 之间的【网络带宽】（NVLink / InfiniBand）
#   - 两者用的是 GPU 完全不同的硬件引擎，所以可以真正并行！
#   - 示例：
#     [copy_in_stream] GPU 计算/显存资源 → wait → [all_gather_stream] NCCL 网卡资源
#     如果 Copy-In 和 All-Gather 在同一条流，则必须串行，硬件资源空闲浪费

# ===== 流 2：all_gather_stream =====
# 作用：负责 NCCL All-Gather 集体通信
# 具体任务：
#   1. 调用 dist.all_gather_into_tensor()
#
# 为什么单独一条流？
#   - NCCL 通信是异步的（提交后立即返回）
#   - 在独立流上启动 NCCL 后，主计算流可以继续做其他事
#   - 下一组的 Copy-In 可以在主计算流做当前组 Copy-Out 的同时开始
#   - 示例：
#     [组1 main_stream] Copy-Out → Forward ...
#     [组1 ag_stream]   All-Gather ────→ [组2 ag_stream] All-Gather ...
#     [组2 copy_in_stream]                Copy-In ...

# ===== 流 3：main_stream（默认流/计算流）=====
# 作用：执行实际的前向/反向计算
# 具体任务：
#   1. Copy-Out（把 All-Gather 输出拆给各参数）
#   2. 前向计算
#   3. 反向梯度计算
#   4. 在 post_backward 中做 Reduce-Scatter 的 Copy-In
#
# 为什么 Copy-Out 在主计算流上？
#   - Copy-Out 的结果要立即用于计算，放在主流上最直接
#   - 不需要额外同步（Copy-Out 完直接开始计算）
```

### 问题 3：为什么 Copy-Out 不在单独一条流上？

**这是很多初学者的疑问：”有 copy_in_stream，为什么没有 copy_out_stream？”**

让我们分析如果 Copy-Out 在独立流上会怎样：

```text
# ===== 假设方案：引入 copy_out_stream =====
def wait_for_unshard_with_copy_out_stream():
    # 在 main_stream 上等 All-Gather 完成
    main_stream.wait_event(all_gather_event)
    
    # 在 copy_out_stream 上做 Copy-Out
    with torch.cuda.stream(copy_out_stream):
        foreach_all_gather_copy_out(...)
        copy_out_event = copy_out_stream.record_event()
    
    # main_stream 要等 Copy-Out 完成才能开始计算
    main_stream.wait_event(copy_out_event)
    
    # 然后开始前向计算
    forward()
```

**问题出在哪？**

1. **额外同步开销**：main_stream 必须 `wait_event(copy_out_event)`，多了一次流同步
2. **Copy-Out 不耗时**：Copy-Out 只是 `split_with_sizes_copy`（把连续缓冲区按参数拆分），本质是 GPU 显存内部的视图操作，不涉及大量数据搬运。Copy-In 才耗时（因为要做 dtype 转换 + 显存拼接拷贝）
3. **延迟计算**：如果 Copy-Out 在独立流，main_stream 必须额外等 Copy-Out 完成。如果 Copy-Out 在 main_stream 上，**做完 Copy-Out 立即就能开始计算**，零延迟

```text
# ===== 实际方案：Copy-Out 在主计算流上 =====
def wait_for_unshard_actual():
    # 在 main_stream 上：
    # 1. 等 All-Gather 完成
    main_stream.wait_event(all_gather_event)
    
    # 2. 立即做 Copy-Out（在 main_stream 上）
    foreach_all_gather_copy_out(...)  # ← 完成即可用于计算
    
    # 3. 不需要同步，直接进 forward！
    # Copy-Out 完接着就能用完整参数
    forward()
    
# 时间线：|...AG...|Copy-Out|Forward|
#                   ^ Copy-Out 完立即 Forward，零等待
```

**关键洞察**：Copy-In 需要单独流是因为它**占用的是 GPU 内部资源**（计算单元做 dtype 转换 + 显存带宽做拼接拷贝），而 All-Gather **占用的是 GPU 之间的网络资源**（NCCL 网卡/NVLink）。两者是 GPU 的不同硬件引擎，天然可以并行。而 Copy-Out 只是对已就位的显存做切片视图操作，放计算流上执行最直接，消除了不必要的流同步延迟。

### 问题 3.5：Copy-In / All-Gather / Copy-Out 本就是串行的，为什么分三条流？

这个问题很关键，也是你最困惑的地方。我们从头理清。

---

### 第一步：先确认一个基本事实——CI 和 AG 是不同硬件引擎

GPU 内部有两类硬件单元：

- **计算单元（SM）** + **显存控制器**：负责 Copy-In（dtype 转换、数据拼接拷贝）
- **NCCL 网卡 / NVLink**：负责 All-Gather（跨 GPU 通信）

它们**物理上是不同的硬件**，可以同时干活互不影响。

---

### 第二步：看实际 FSDP 中每条流上到底排了什么

假设 3 个参数组（G1、G2、G3），只看 `pre_forward` 阶段。对每个组，代码执行顺序是：

```text
unshard()  → 向 copy_in_stream 提交 CI、向 ag_stream 提交 AG
wait_for_unshard()  → 向 main_stream 提交 CO，同时向 copy_in_stream/ag_stream 插入 wait_event
```

GPU 上的实际命令序列（按提交时间先后，从上到下）：

```text
copy_in_stream:     [G1-CI]  [G2-CI]  [G3-CI]
                    （每组 CI 紧挨着提交，没有闲等）

ag_stream:          [等G1-CI] [G1-AG] [等G2-CI] [G2-AG] [等G3-CI] [G3-AG]
                    （每组 AG 等本组 CI 完成后开始）

main_stream:        [等G1-AG] [G1-CO+Fwd] [等G2-AG] [G2-CO+Fwd] [等G3-AG] [G3-CO+Fwd]
                    （每组 CO+Fwd 等本组 AG 完成后开始）
```

看**时间上的重叠**（时间从左到右流动）：

```text
时间轴 →→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→
copy_in: [G1-CI] [G2-CI] [G3-CI]
ag:          [G1-AG] [G2-AG] [G3-AG]
main:              [G1-CO+Fwd] [G2-CO+Fwd] [G3-CO+Fwd]
```

看到了吗：

- **G2-CI 和 G1-AG 同时进行** ← CI 用 GPU 计算单元，AG 用 NCCL 网卡，各干各的
- **继续向右，G1-AG 和 G1-CO+Fwd 也同时进行** ← AG 用 NCCL，CO+Fwd 用计算单元
- **每一条流的内部**：操作是串行的（G1-CI 完才到 G2-CI）

**这就是分三条流的原因**：把原本串行的三个操作放到三条流上，让**跨组的操作可以重叠**。

---

### 第三步：那 `copy_in_stream.wait_event(prev_co_event)` 是干什么的？

你说得对，代码确实有这一行（在 `wait_for_unshard` 里）：

```text
self._wait_all_gather_streams_on_event(prev_all_gather_state.event)
# 等价于：
#   copy_in_stream.wait_event(prev_co_event)
#   ag_stream.wait_event(prev_co_event)
```

但要注意它**被调用的时机**。`pre_forward` 的 CPU 执行顺序是：

```text
def pre_forward(self, ...):
    self.unshard(...)         # 【第1步】提交 CI 到 copy_in_stream、AG 到 ag_stream
    self.wait_for_unshard()   # 【第2步】做 CO，并插入 wait_event
```

所以对于 G2，GPU 命令序列的实际顺序是：

```text
copy_in_stream 上依次收到的命令：
    # 来自 G2.unshard()：
    [G2-CI 分配 G2 自己的 all_gather_output 缓冲区]
    # 来自 G2.wait_for_unshard()：
    [wait_event(G1-CO)]  ← 这个 wait_event 在 G2-CI 后面！
```

**关键结论：G2-CI 已经在 wait_event 之前就提交了，所以 wait_event 不会让 G2-CI 停下来等 G1-CO。**

那这个 `wait_event` 到底有什么用？它的作用是保护**未来的操作**——具体来说：

- G2 的 `wait_for_unshard` 做完后，会把 G1 的 `all_gather_state` 设为 `None`（释放对 G1 的 `all_gather_output` 的引用），这块 GPU 内存就可以被回收重用了
- 但必须等 G1-CO 读完了才能回收（否则 G1 的 forward 在 main_stream 上还在读这块内存）
- 所以插一个 `wait_event(G1-CO)` 到 `copy_in_stream` 上，这样后续任何提交到 `copy_in_stream` 的操作（比如**下一个 iteration** 的 CI）都会等 G1-CO 完成后再开始，不会拿到 G1 还没读完的内存

**打个比方**：

> 餐厅有三个窗口：点单（CI）、备菜（AG）、上菜（CO+Fwd）。三个窗口有各自的队伍。<br> G1 顾客：在点单窗口排队→在备菜窗口排队→在上菜窗口排队 G2 顾客：紧跟在 G1 后面点单→然后去备菜→然后去上菜<br> G2 在点单窗口排队时，G1 同时正在备菜——这就是**点单和备菜在不同窗口**的好处。<br> 而 `wait_event(prev_co_event)` 相当于：上菜窗口告诉点单窗口”G1 已经吃上了”，点单窗口才把 G1 的菜单扔掉（释放内存）。以后来的人（下一个批次）不会拿到被 G1 还在吃的菜。

### 第四步：用代码提交顺序精确验证

下面用伪代码 + 注释，精确展示 3 个组的 CPU 提交顺序和 GPU 执行顺序：

```text
# ========== CPU 提交顺序（从上到下） ==========

# ----- G1 的 pre_forward -----
G1.unshard()
# → copy_in_stream 收到【G1-CI】
# → ag_stream 收到【等G1-CI + G1-AG】

G1.wait_for_unshard()
# → comm_ctx.all_gather_state = AllGatherState(G1结果, G1-CO事件)
#   （此时没有 prev_all_gather_state，不需要 wait_event）
# → main_stream 收到【等G1-AG事件 + G1-CO + G1-Fwd】

# ----- G2 的 pre_forward -----
G2.unshard()
# → copy_in_stream 收到【G2-CI】← 跟在 G1-CI 后面，不等 G1-AG！
# → ag_stream 收到【等G2-CI + G2-AG】

G2.wait_for_unshard()
# → 发现 comm_ctx 里有 prev_all_gather_state = G1的
# → copy_in_stream 收到【wait_event(G1-CO)】← 在 G2-CI 之后！
# → ag_stream 收到【wait_event(G1-CO)】← 在 G2-AG 之后！
# → 释放 comm_ctx.all_gather_state（G1 的内存可以被回收了）
# → main_stream 收到【等G2-AG事件 + G2-CO + G2-Fwd】
# → 保存 G2 的 AllGatherState 到 comm_ctx

# ----- G3 的 pre_forward -----
G3.unshard()
# → copy_in_stream 收到【G3-CI】← 跟在 wait_event(G1-CO) 后面！
#   所以 G3-CI 会等 G1-CO 完成后再开始（不冲突，反正 G3-CI 只要等 G2-CO 就行）
# → ag_stream 收到【等G3-CI + G3-AG】← 也是在 wait_event(G1-CO) 后面

G3.wait_for_unshard()
# → 释放 G2 的 all_gather_state，等 G2-CO 事件
# → 做 G3-CO，保存 G3 的结果
```

**GPU 上实际的时间线**：

```text
时间 →→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→

copy_in_stream:
  [G1-CI]         [G2-CI]         [G3-CI]  ← 注意：G2-CI 在 G1-CI 之后立即开始，不等 G1-AG！
                        ↑G1-AG和G2-CI同时发生（不同硬件引擎）

ag_stream:
           [G1-AG]           [G2-AG]           [G3-AG]
                              ↑G1-CO+Fwd和G2-AG同时发生（不同硬件引擎）

main_stream:
                    [G1-CO+Fwd]        [G2-CO+Fwd]       [G3-CO+Fwd]
```

### 第五步：直接回答你的问题

**你说的”如果 CI 和 AG 在同一条流上，CI 只需要等上一组的 CO 的 event 结束”**——我们来模拟一下这个方案：

```text
pre_fwd_stream (CI+AG 合流): [G1-CI] [G1-AG] [wait(G1-CO)] [G2-CI] [G2-AG] [wait(G2-CO)] [G3-CI] [G3-AG]
main_stream:                          [G1-CO+Fwd]                   [G2-CO+Fwd]                   [G3-CO+Fwd]
```

问题出在哪里？G2-CI 前面排着 G1-AG，**必须等 G1-AG 做完才能做 G2-CI**。即使插了 `wait_event(G1-CO)`，它也在 G1-AG 后面，帮不了 G2-CI 提前开始。

而实际 FSDP 的方案：

```text
copy_in_stream: [G1-CI] [G2-CI] [G3-CI]    ← G2-CI 紧跟在 G1-CI 后面
ag_stream:              [G1-AG] [G2-AG] [G3-AG]
main_stream:                    [G1-CO+Fwd] [G2-CO+Fwd] [G3-CO+Fwd]
```

G2-CI 不用等 G1-AG，因为它们在**不同的流上**。G2-CI 只需要等 G1-CI 完成（同一流上的先后顺序），然后就可以开始了。

---

### 一句话总结

| 你想的方案（CI+AG 合流） | 实际 FSDP（CI 单独流） |
| --- | --- |
| G2-CI 等 G1-AG 完成 + 等 G1-CO 事件 | G2-CI 只等 G1-CI 完成 |
| G2-CI 不能和 G1-AG 重叠 | G2-CI 和 G1-AG 完全重叠 |

**分三条流的收益 = 让 G2 的 CI 和 G1 的 AG 同时运行 + 让 G1 的 AG 和 G1 的 CO+Fwd 同时运行。** 这是两重重叠。

### 问题 4：为什么 post_backward 中的 Reduce-Scatter 要单独一条流？

```text
# ===== 反向中的流使用 =====
def post_backward_actual():
    # ===== 在 main_stream 上：=====
    # 1. 收集梯度
    grads = collect_grads()
    
    # 2. Copy-In（把梯度拼接到连续缓冲区）
    reduce_scatter_input = concat_grads(grads)
    # grads.clear()  ← 释放梯度内存
    
    # 3. 切换到 reduce_scatter_stream
    reduce_scatter_stream.wait_stream(main_stream)
    
    # ===== 在 reduce_scatter_stream 上：=====
    with torch.cuda.stream(reduce_scatter_stream):
        # 4. NCCL Reduce-Scatter
        dist.reduce_scatter_tensor(...)
        reduce_scatter_event = reduce_scatter_stream.record_event()
        
        # 5. divide + dtype 转换 + 赋值梯度
        ...
        post_reduce_event = reduce_scatter_stream.record_event()
    
    # ===== main_stream 可以继续做其他事！=====
    # 下一个组的反向计算可以和本组的 RS 并行
    # 因为在不同流上
    
    # 保存 RS 状态供下一组同步
    reduce_scatter_state = (reduce_scatter_input, reduce_scatter_event)
```

**为什么需要独立的 RS 流？**

1. Reduce-Scatter 涉及 NCCL 集体通信，是异步的
2. 下一个参数组的反向计算可以在 main_stream 上继续（和 RS 并行）
3. HSDP 的 All-Reduce 还要在 all_reduce_stream 上，可以与 RS 进一步并行（利用不同网络资源）

### 问题 5：直观对比 —— 有 Stream vs 无 Stream

```text
无 Stream（顺序执行）：
组1: |Copy-In|AG|Copy-Out|Forward|Copy-In|AG|Copy-Out|Forward|
组2:                                                 |Copy-In|AG|Copy-Out|Forward|
                ↑ GPU 空闲等待 ↑

有 Stream（流水线执行）：
组1: |Copy-In|AG|Copy-Out|Forward.........|
组2:          |Copy-In|AG|Copy-Out|Forward......|
组3:                   |Copy-In|AG|Copy-Out|Forward...|
        ↑ 时间重叠 ↑
```

**总结 Stream 数目问题**：

| 为什么有它？ | 为什么没有它？ |
| --- | --- |
| all_gather_copy_in_stream：Copy-In 占 GPU 计算/显存资源，和 NCCL 网络资源不冲突，可并行 | copy_out_stream：Copy-Out 是轻量切片视图操作，放主流上消除同步延迟 |
| all_gather_stream：NCCL All-Gather 是异步操作，在独立流启动后主流可继续 |  |
| reduce_scatter_stream：NCCL Reduce-Scatter 与反向计算可以重叠 |  |
| all_reduce_stream：HSDP 的 All-Reduce 与 RS 使用不同网络资源，可进一步并行 |  |
