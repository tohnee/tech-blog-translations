如果说前两篇分别回答的是：

- **为什么 AI 计算偏爱 GPU；**
- **为什么 GPU 编程要围绕线程组织和内存层级展开；**

那么这一篇要回答的是另一个更大的问题：

> 为什么一张 GPU 不够时，事情会迅速从“写一个 Kernel”变成“组织一个集群”？<br>

今天训练一个大模型，常常不是几张卡、几十张卡的问题，而是：

- 几百张卡；
- 几千张卡；
- 甚至上万张卡。

这不是因为大家“浪费硬件”，而是因为：

> 大模型训练本质上同时受三件事约束：<br>

1. **计算量太大；**
2. **模型太大；**
3. **训练时间不能无限拉长。**

于是，单 GPU 的问题，最终一定会演化成：

- 多 GPU 如何协同；
- 多节点如何通信；
- 模型参数、激活和梯度如何分布；
- 不同并行策略如何组合。

从这里开始，GPU 不再只是一个计算芯片，而成为一个分布式系统的基本构件。

## 一、为什么单 GPU 很快就不够用了？

先看最直观的两个限制。

### 1. 显存限制：模型根本放不下

训练一个大模型时，显存里不只是模型参数。

通常还要放：

- 参数（Parameters）
- 梯度（Gradients）
- 优化器状态（Optimizer States）
- 激活值（Activations）

如果用一个很粗略的表达式来看，训练时的显存占用可以写成：

$M \approx M_{\text{param}} + M_{\text{grad}} + M_{\text{opt}} + M_{\text{act}}$

其中：

- $M_{\text{param}}$：参数占用
- $M_{\text{grad}}$：梯度占用
- $M_{\text{opt}}$：优化器状态占用
- $M_{\text{act}}$：前向中间激活占用

对于大模型来说，真正可怕的是：

- 参数规模大；
- 序列长度长；
- batch size 也不能太小。

这会让显存迅速爆炸。

也就是说，很多时候不是“算不动”，而是“放不下”。

### 2. 计算时间限制：训练不能等太久

就算模型能勉强塞进一张 GPU，训练时间也常常不可接受。

训练总时间大致可以理解为：

$T \approx \frac{\text{总计算量}}{\text{系统吞吐}}$

如果模型参数规模翻十倍、数据量翻十倍，而吞吐不提升，那么训练时间也会急剧拉长。

但现实里：

- 研究节奏不允许；
- 业务迭代不允许；
- 集群成本也不允许你让单卡慢慢跑几个月。

所以从工程角度看，扩大 GPU 数量并不是“奢侈”，而是必要条件。

## 二、多 GPU 以后，问题的本质变成了“通信”

单卡训练时，我们主要关心：

- Kernel 写得够不够好；
- Tensor Core 利用率高不高；
- 显存访问是否高效。

但一旦进入多 GPU 训练，核心问题会立刻变化：

> 你不再只是在优化计算，而是在优化“计算 + 通信”的整体系统。<br>

因为多张 GPU 不可能天然知道彼此的数据。

它们必须交换：

- 参数；
- 梯度；
- 激活；
- 中间结果。

于是，系统性能不再只取决于单卡算力，还取决于：

1. **GPU 与 GPU 之间怎么连；**
2. **GPU 与 GPU 之间传什么；**
3. **传输和计算能否重叠。**

这时，“互连”就变得和“算力”一样重要。

## 三、从 PCIe 到 NVLink：单机多 GPU 是怎么协同的？

在单机多 GPU 场景下，最基本的结构可以想象成这样：

```text
CPU
 ├── GPU 0
 ├── GPU 1
 ├── GPU 2
 └── GPU 3

```

但真正影响性能的，不只是“有几张卡”，而是这些卡之间怎么互联。

### 1. PCIe：最基础、最通用的互连

PCIe 是最常见的 GPU 连接方式。

它的特点是：

- 通用；
- 成本较低；
- 兼容性强；

但问题也很明显：

- 带宽有限；
- 延迟相对更高；
- GPU 间通信常常要绕更多路径。

如果多 GPU 训练中大量同步都压在 PCIe 上，性能就会很容易被通信拖住。

### 2. NVLink / NVSwitch：为高带宽 GPU 通信而生

为了更高效地让 GPU 之间交换数据，系统引入了 NVLink、NVSwitch 这类高速互连。

你可以把它们理解成：

> 专门为“GPU 和 GPU 高频通信”设计的高速通道。<br>

它们的核心意义在于：

- 提供更高带宽；
- 降低 GPU 间数据交换成本；
- 让模型并行和梯度同步更高效。

对于今天的大模型训练来说，GPU 不是孤立工作的。

很多时候，它们更像是：

> 一组通过高速互连紧密耦合的协同处理器。<br>

## 四、从单机到多节点：为什么一定会引入网络？

即便单机已经有 8 张 GPU、甚至更多，大模型训练仍然很快会继续扩展到多节点。

原因很简单：

- 单机显存总量有限；
- 单机算力总量有限；
- 单机供电、散热与扩展空间也有限。

所以更大的系统通常会变成这样：

```text
Node 0: GPU × 8
Node 1: GPU × 8
Node 2: GPU × 8
...

```

而节点之间再通过网络连接。

这就把问题进一步升级为：

> 不只是 GPU 和 GPU 通信，还包括“节点与节点之间的分布式协作”。<br>

这时，网络质量就会直接影响训练效率。

在大模型系统里，大家常说“扩展性”：

其实本质就是在问：

> 当 GPU 数量继续增加时，系统吞吐能否接近线性增长？<br>

而决定这个问题的关键，往往不是算力，而是网络和通信组织方式。

## 五、多 GPU 训练的 4 种核心并行思路

大模型训练之所以复杂，并不是因为“并行”这个词本身，而是因为并行并不只有一种做法。

不同约束下，要切分的对象不同。

从系统角度看，最常见的四种并行方式是：

1. 数据并行（Data Parallelism, DP）
2. 张量并行（Tensor Parallelism, TP）
3. 流水并行（Pipeline Parallelism, PP）
4. 专家并行（Expert Parallelism, EP）

### 1. 数据并行：最直观，也最经典

数据并行最容易理解。

思路是：

- 每张 GPU 上放一份完整模型；
- 不同 GPU 处理不同 batch 数据；
- 反向之后再同步梯度。

假设全局 batch size 是 $B$，有 $N$ 张卡，那么每张卡大约处理：

$B_{\text{local}} = \frac{B}{N}$

它的优点是：

- 概念简单；
- 易于扩展；
- 对模型结构侵入小。

但问题也很明显：

- 每张卡都要放完整模型；
- 模型太大时放不下；
- 梯度同步开销可能很大。

所以数据并行更适合：

> 模型还能单卡放下，但希望通过更多 GPU 提高吞吐。<br>

### 2. 张量并行：把一个算子拆开算

如果模型本身太大，一张卡放不下，就不能只靠数据并行了。

这时要考虑：

> 把同一个层、同一个矩阵乘法，拆给多张卡一起做。<br>

这就是张量并行。

例如一个线性层：

$Y = XW$

如果权重矩阵 $W$ 太大，可以按列或按行切分到不同 GPU 上。

于是每张 GPU 只负责一部分计算，最后再把结果聚合。

张量并行的优点是：

- 可以直接降低单卡模型存储压力；
- 能把大矩阵乘法分摊到多张卡上。

但它对通信非常敏感。

因为同一个层的前向和反向过程中，经常需要：

- all-gather
- reduce-scatter
- all-reduce

所以张量并行通常更依赖：

- 节点内高速互连；
- 稳定而低延迟的通信路径。

### 3. 流水并行：把模型按层切开

张量并行是在“层内切”。

流水并行则是在“层间切”。

思路是：

- 把模型按层分成多个 stage；
- 每个 stage 放到不同 GPU；
- 不同 micro-batch 依次流过这些 stage。

例如：

```text
GPU 0: Layer 1 ~ 8
GPU 1: Layer 9 ~ 16
GPU 2: Layer 17 ~ 24
GPU 3: Layer 25 ~ 32

```

这样单张 GPU 不需要放完整模型。

它的优势是：

- 降低单卡显存压力；
- 适合超深模型。

但流水并行的核心挑战是：

- 流水线空泡（bubble）；
- stage 切分是否均衡；
- 前后 stage 的激活通信开销。

所以流水并行本质上是在做：

> 模型切分 + 时间调度。<br>

### 4. 专家并行：MoE 模型时代的重要策略

到了 MoE（Mixture of Experts）模型时代，还会出现一种新的并行方式：专家并行。

在 MoE 中，并不是每个 token 都走完整模型，而是会被路由到部分专家。

于是系统需要解决：

- 不同专家放在哪些 GPU 上；
- token 如何 dispatch 到对应专家；
- 专家输出如何再 combine 回来。

这类系统的通信往往非常重，尤其常见：

- all-to-all

因此专家并行的难点不是“有没有并行”，而是：

> 并行之后，路由和通信会不会成为新瓶颈。<br>

## 六、为什么今天的大模型系统常常是“混合并行”？

如果只看定义，四种并行方式似乎可以单独使用。

但现实里，一个足够大的模型通常不会只用一种并行。

原因很简单：

- 单纯数据并行，模型可能放不下；
- 单纯张量并行，通信压力可能过大；
- 单纯流水并行，流水空泡会影响效率；
- 单纯专家并行，也无法覆盖所有需求。

所以今天很多大模型训练系统的真实形态是：

> **混合并行（Hybrid Parallelism）**<br>

例如一个系统可能同时使用：

- 数据并行：扩大全局吞吐；
- 张量并行：切大层；
- 流水并行：切深层；
- 专家并行：支撑 MoE。

这时，整个训练系统就不只是“多张卡一起干活”，而是：

> 把不同维度的切分方式叠在一起，尽量在显存、算力、带宽和调度之间找到平衡点。<br>

也正因为如此，大模型训练框架才会越来越复杂。

它们不只是“把 PyTorch 跑起来”，而是在做一套完整的分布式执行规划。

## 七、通信库为什么重要？从 MPI 到 NCCL

当训练进入多 GPU、多节点阶段，程序就必须依赖通信库来组织数据交换。

从历史上看，大家熟悉的通用分布式通信接口是 MPI。

MPI 很强大，也很通用，在高性能计算领域几乎是基础设施。

但对于 GPU 训练来说，还需要进一步针对以下场景优化：

- GPU 与 GPU 直接通信；
- 大规模 collective 操作；
- 训练中高频 all-reduce、all-gather、reduce-scatter、all-to-all。

这就是为什么后来会出现像 NCCL 这样的 GPU 通信库。

它的重要性在于：

- 更贴近 GPU 训练工作负载；
- 针对多 GPU 集体通信做优化；
- 能更好利用 NVLink、PCIe、网络拓扑。

所以从系统视角看：

> 多 GPU 训练不只是“模型并行怎么切”，还包括“通信栈怎么跑”。<br>

很多时候，训练性能差，并不是算子太慢，而是 collective 没有跑顺。

## 八、大模型训练系统真正追求的，不是“最快单卡”，而是“最高系统效率”

到这里，可以总结一个常见误区：

很多人容易把大模型训练理解成“买更强 GPU”。

但系统真正追求的目标其实不是单卡峰值，而是整体效率。

它至少包含三层含义：

### 1. 让更多 GPU 真正忙起来

不是卡越多越好，而是：

- GPU 利用率够不够高；
- 是否有空等通信；
- 是否有负载不均衡。

### 2. 让通信尽量不拖后腿

理想情况下，系统希望做到：

- 计算和通信尽量重叠；
- 高频 collective 尽量高效；
- 通信拓扑与并行策略匹配。

### 3. 让训练规模和系统规模一起增长

一个真正成熟的大模型系统，不只是能在 8 张卡上跑通，而是：

- 在几十张卡上还能扩展；
- 在几百张卡上还能保持效率；
- 在几千张卡上仍然能管理复杂的并行关系。

这就是“从单 GPU 到万卡集群”的真正含义。

它不是简单地把 GPU 数量乘上去，而是在构建：

> 一个可扩展的大规模并行训练系统。<br>

## 总结

单 GPU 时代，优化的重点往往是：

- Kernel 性能；
- 显存访问；
- Tensor Core 利用率。

但到了大模型时代，问题迅速升级为：

- 模型能不能放下；
- 吞吐能不能扩展；
- 通信会不会成为瓶颈；
- 多种并行方式能否合理组合。

因此，从单 GPU 到万卡集群，本质上是一条非常自然的演化路径：

1. **单卡不够放模型；**
2. **多卡需要解决通信；**
3. **多节点需要解决网络；**
4. **超大模型需要混合并行；**
5. **最终目标是系统级效率，而不是单卡峰值。**

理解这一点，就能看清今天大模型训练系统为什么越来越像一个复杂的分布式计算平台。

GPU 仍然是这个平台的核心计算引擎；

但真正决定系统上限的，已经不只是 GPU 本身，而是：

> **GPU、互连、网络、并行策略与通信栈共同组成的整体系统。**<br>
