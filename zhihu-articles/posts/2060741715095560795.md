## 0x02. 从第一层到最后一层，一个token经历了什么？

### **2.1 Tokenizer与Embedding**

Tokenizer将原始文本转换为模型可处理的token序列。Tokenizer的设计不仅影响训推的效率，也影响着模型对文本结构的理解。

在算法上， **Byte Pair Encoding (BPE)** 及其变体是大部分主流LLM的选择。

- **BPE** 的核心思想是：从最小单元（字节/字符）开始，反复合并最频繁出现的相邻 token 对，直到达到目标词表大小。
- **Byte-level BPE (BBPE)** 是BPE 的一个特定变种。它规定算法的起点必须是256 个单字节，直接在UTF-8字节序列上操作。这样做的好处是能天然表示任何文本，永远不会出现OOV(Out-of-Vocabulary) 问题，因此对多语言更加友好。

在使用工具上， **SentencePiece和tiktoken** 是两个主流的软件库。

- **SentencePiece** 是Google 开发的一个多功能分词工具库。它内置了 BPE 和 Unigram 等多种算法。它的不依赖预分词，把空格也当作一个普通字符（用 `▁` 表示），直接在原始文本流上进行操作。这使得它对所有语言（尤其是中文、日文等不用空格分词的语言）的处理流程完全一致。
- **tiktoken** 是OpenAI 开发的一个 **高性能 BPE 专用工具库** 。它专门为 **Byte-level BPE (BBPE)** 这一种算法做了极致的工程优化，核心用 Rust 编写，速度极快。与sentencepiece不同的是，tiktoken会先用一个精心设计的正则表达式将文本切分成不同的块（比如把单词、数字、标点分开），BPE 的合并操作不会跨越这些块的边界。tiktoken本质上是 BBPE 算法的一个标准的、快速的实现。但tiktoken 的训练器本身并不高效，所以很多团队是用其他工具（如 HuggingFace `tokenizers` ）训练出词表和合并规则，再转换成 tiktoken 格式来使用其高速的推理能力。

有一些量化的指标可以用来衡量tokenizer的优劣，比如fertility和parity：

- **Fertility** ：衡量的是一个词平均被拆分成多少个 token。英文通常在1.0-1.5，而中文在差的 tokenizer 上甚至可达到4-6。
- **Parity（对等性）：** 衡量的是跨语言 token 数量的对等程度。准备一份多语言平行语料（同一个意思的句子，有各语言版本），用同一个 Tokenizer 对它们进行分词，计算每种语言产生的 token 数量，然后算出所有语言 token 数量的差异度。parity 差意味着某些语言的文本总会被拆成更多 token。API 按 token 计费时，说中文、日语、阿拉伯语等用户要付的钱比说英语的多好几倍。

在拿到一段文本之后，首先用tokenizer将它分成token序列，然后输入Embedding Layer，就得到了这句话的向量表示。这就是token进入LLM的第一层—— `token embedding layer` 做的事情。

### **2.2 归一化（Normalization）与残差连接（Residual Connection）**

### **2.2.1 LayerNorm与RMSNorm**

我们知道，LayerNorm 会将每层的激活强行拉回均值 0、方差 1附近，让后续的层始终看到分布稳定的输入。没有Layernorm，深层Transformer结构几乎无法训练。

给定一个样本的 $d$ 维输入向量 $x=(x_1,x_2,…,x_d)$ ，layernorm的计算公式如下：

![](https://pic4.zhimg.com/v2-37bf56200003be86af28092eb80a7cd3_r.jpg)
*减去均值\mu，除以方差\sigma。γ、β是可学习的缩放和偏移，让网络有能力恢复原始分布*

我们可以看到，LayerNorm 需要进行两次全向量遍历：一次求均值，一次求方差（方差计算本身也依赖均值）。2019年的时候，研究者提出一个假设： **减去均值可能不是必须的** ，真正起作用的是根据输入的整体幅度进行缩放，使激活值不至于过大或过小。所以，在 **RMSNorm** 中就移除了均值计算，仅保留均方根（Root Mean Square, RMS）作为缩放因子。现在的主流LLM大都是使用RMSNorm而不是LayerNorm。

RMSNorm的计算公式如下：

### **2.2.2 Post-Norm与Pre-Norm**

Norm层通常和残差连接一起使用，而Norm 层的放置位置也是值得讨论的。原始的Transformer将两个Layernorm层分别放置在 注意力模块和FFN模块的残差连接之后，这也称为 **Post-Norm** 。但是之后出现的大多数 LLM 将Norm层置于注意力模块和FFN模块之前，这被称为 **Pre-Norm** 。下图展示了 Post-Norm 和 Pre-Norm 之间的对比：

![](https://pic4.zhimg.com/v2-bf0d8d0912bb17c57af8ab9ba9e2698b_r.jpg)
*图2. Post-Norm和Pre-Norm的对比*

从公式上看：

- **Post‑Norm** ： $x = \text{LayerNorm}(x + \text{Sublayer}(x)) $
- **Pre‑Norm** ： $x = x + \text{Sublayer}(\text{LayerNorm}(x))$

Post-Norm的好处就是，它在最后做归一化，因此每一层的输出都有稳定的统计量，下游层接收的信号非常干净。但是它有一个很严重的问题，就是反向传播时所有梯度都必须穿过 LayerNorm 的雅可比矩阵。在深层网络中，几十上百个这样的矩阵连乘，只要特征值略微小于 1，就会有梯度消失；略微大于 1 就会梯度爆炸。这就是为什么 Post-Norm 训练极深网络时需要很小心，通常离不开复杂的学习率warmup。

而Pre-Norm中的 **恒等映射** 使得梯度回传时，残差路径会贡献一个+1项。无论sublayer的雅可比矩阵如何，总有一条无损的梯度通道直达底层，解决了深层网络的训练发散问题。当然了，由于残差不断累积未经归一化的输出，激活值的幅值会随层数增长。但这可通过最终输出层前的最后一次 LayerNorm（如图1中的 `Final RMSNorm` ）和合理的初始化来控制。

综上所述，Pre-Norm 用轻微的激活值膨胀，换取了深层 Transformer 的稳定训练能力，因此成为了目前大多数LLM的标准配置。

> **名词解释——【雅可比矩阵】：** 
>  假设有一个函数 y=f(x)，输入是n维向量x=(x_1,...,x_n)，输出是m维向量y=(y_1,...,y_m)。雅可比矩阵就是将所有一阶偏导数排成一个m×n的矩阵：

![](https://pic1.zhimg.com/v2-f74f0c3735378462fb52daf03f36e1e4_r.jpg)

> 第 i 行，第 j 列的元素是输出第 i 分量对输入第 j 分量的偏导数。它完整描述了输入每个微小变化对每个输出的影响。

### 2.3 Attention模块

### **2.3.1 降低KV Cache：从MHA到GQA再到MLA**

![](https://pica.zhimg.com/v2-e9c229c1f27f04f6382a510639c35d10_r.jpg)

**(a) 什么是KV Cache？**

首先，我们需要知道的是，LLM在 **推理** 时，分为两个阶段： **Prefill（预填充）和Decode（解码）** 。

当模型第一次收到用户的完整 prompt 时，此时模型会并行计算整个序列的 Q、K、V矩阵，之后，模型取最后一层的最后一个 token 表示送入 LM Head，生成第一个新 token。与此同时， **每一层产生的完整 K 和 V 矩阵被写入 KV Cache** ，为后续生成奠定基础。 **这个过程就叫做prefill。** 这是典型的矩阵乘法（GEMM），计算高度密集，属于计算受限场景。

从第二个 token 开始，模型就进入了 **解码（Decode）阶段** 。此时，每次只有一个新 token 作为输入，需要用当前这个新 token 的 q 向量去和 **整个历史序列** 的 K、V 进行注意力交互。如果不做任何优化，每生成一个 token 都要为所有历史 token 重新计算 K 和 V，生成 N 个 token 的总计算复杂度将飙升至  $O(N^2)$ ，这显然不可接受。

![](https://pic3.zhimg.com/v2-c5fd04d6a24edbeda4945762013a7564_r.jpg)
*Prefill与Decode*

解决方案也非常直觉：既然历史 token 的 K 和 V 在前面步骤中已经算过且后面不再变化，那为什么不把它们存起来直接复用呢？这就是 KV Cache了。

有了 KV Cache 后，我们在解码阶段的每步只需：

- 用当前单个 token 的 embedding 计算出它的 q、k、v 向量（都是行向量）。
- 将新算出的 k、v 追加到显存中的 KV Cache 末尾。
- 用当前 q 向量与历史所有的K进行点积运算得到注意力分数，并作用于所有的V，得到输出。

因为q是单行向量，这样我们就从矩阵-矩阵乘法（GEMM）退化为矩阵-向量乘法（GEMV），计算量降低了很多。KV Cache用空间换来了巨大的时间节省。

**KV Cache节省了计算，但是带来了新的问题，也就是显存的问题。** 因为它要对每层的每个历史token都做Cache，那么当序列变得非常长的时候，这就是一个很大的问题。现在的模型一般都支持到256K，有的甚至支持到1M，这样才能解决长程的Agent任务。那么这个KV Cache的占用是巨大的。

另外，KV Cache也会给 **显存带宽** 造成压力。我们知道，GPU 内部的计算单元（SRAM）和显存（HBM/VRAM）是分离的。每次做 Attention 计算时，必须把 KV Cache 从 HBM 搬运到 SRAM。这个搬运本身的耗时，往往远大于实际计算耗时。

**(b) MHA，MQA与GQA**

从MHA到GQA的这条路径的核心目标就是： **在保持模型性能的前提下，尽可能地压缩 KV Cache 的大小。**

在标准的 **多头注意力（Multi-Head Attention, MHA）** 机制中，每个注意力头都拥有一套独立的K和V投影矩阵。具体来说，记attention head个数为 $n_h$ ，每个头的维度为 $d_h$ ，那么每个token的key和value向量的维度就是 $n_hd_h$ ，每个token的key和value向量都会被存到KV Cache中去。

![](https://pica.zhimg.com/v2-e9c229c1f27f04f6382a510639c35d10_r.jpg)
*图3. MHA、GQA、MQA、MLA的对比。阴影部分为缓存的KV Cache。MLA只需缓存压缩的隐式KV这一个向量*

为了降低KV Cache的占用，一个最极限的方法就是 **MQA（Multi-Query Attention）** ，也就是当 $n_h=1$ 的这种特殊情况，即让所有 Query Head 共享唯一一组 Key Head 和 Value Head。但是这会让表达能力显著受限，往往导致模型输出质量下降。

**GQA（Group Query Attention）** 则提供了一个灵活的权衡：将 Query Head 分成 G 组，每组内的查询头共享一套 KV Head，也就是 $n_h=G$ 。比如如果采用 $G=8$ 的 GQA，KV Head 数从 32 降至 8，KV Cache 缩减 4 倍，质量却几乎没有明显损失。这也正是很多主流模型选择 GQA 的原因—— **用很小的性能代价，换取节省大量的KV Cache占用** 。

**(b.1) Rotary Positional Embedding(RoPE)**

RoPE（Rotary Position Embedding，旋转位置编码）是一种注入相对位置信息的编码方法，是当前主流大模型的默认位置编码方案。与大多数加法式位置编码不同，RoPE 是一种乘法式编码，它通过 **旋转query向量和key向量** ，使得它们的内积天然地依赖于相对位置，从而具备了相对位置的感知能力。

在self-attention的计算中，对于输入序列第 $m$ 个 token 的embedding $\mathbf{x}_m$ ​，以及第 $n$ 个 token 的embedding $\mathbf{x}_n$ ，首先计算出它们对应的query、key、value向量 $\mathbf{q}_m, \mathbf{k}_n, \mathbf{v}_n$ 。 **之后对query、key向量施加RoPE编码（本质上就是左乘一个旋转矩阵）。**

![](https://picx.zhimg.com/v2-fa3b4ff5baf5334363b74270684fe1f5_r.jpg)

旋转矩阵如下：

![](https://pic2.zhimg.com/v2-a05cb54a36b519799a0f76d3b292b63f_r.jpg)

由于 $\mathbf{R}_m^⊤\mathbf{R}_n=\mathbf{R}_{n−m}$ ，所以： $\tilde{\mathbf{q}}_m^⊤\tilde{\mathbf{k}}_n=\mathbf{q}_m^⊤\mathbf{R}_{n−m}\mathbf{k}_n$ ​

可以看到，注意力矩阵仅依赖相对位置 $(n-m)$ ，具备平移不变性。

![](https://pica.zhimg.com/v2-64211baaec5ce348ca4d000631ec58fc_r.jpg)
*图4. 在计算self-attention时，对q、k分别施加RoPE之后，再使用GQA计算self-attention*

 **(b.2) QK-Norm**

QK-Norm这个改进技巧出自 [ViT-22B](https://arxiv.org/pdf/2302.05442) 。主要是他们发现，Vision Transformer (ViT) 扩展到超大规模时，会出现严重的训练不稳定性问题，损失会突然变成 `NaN` 。经过排查，发现是因为注意力计算中的 logits 值变得极大。 
 由于注意力权重是通过 softmax 函数计算的，当 logits 值极大时softmax 的输出会趋向于一个one-hot向量，即只有当前 token 和自己的注意力权重接近 1，而其他所有 token 的权重都接近 0。

为了解决上述问题，ViT-22B 采纳了一种简单而有效的技术，就是在计算注意力权重之前分别对 Query和 Key 应用一下LayerNorm：

![](https://pic1.zhimg.com/v2-2a444b05d45f13890013a91ea497e180_r.jpg)

通过归一化操作，强制将 Q 和 K 向量的范数控制在稳定区域，从而避免了它们的内积（即注意力 logits）过大。

QK-Norm已经成为后续许多LLM的标准组件，对提升训练的鲁棒性至关重要。当然了，很多LLM都将这个LayerNorm换成了RMSNorm。

**(b.3) Flash Attention**

Flash Attention 是一种精确、IO 感知的注意力加速算法，它与标准自注意力数学上完全等价，但通过减少内存读写来实现数倍的速度提升，以及大幅降低内存占用。

GPU 的片上高速内存（SRAM）速度（19 TB/s）远快于片外显存（HBM）（1.5 TB/s），但容量却小得多：

![](https://pica.zhimg.com/v2-9a19c8925cd3d70faff271a03581a092_r.jpg)

标准注意力的流程如下：

```text
1. 从 HBM 读 Q、K到SRAM，算出 N×N的S = QK^T矩阵，并写回 HBM。
2. 从 HBM 读 S到SRAM，算出 P = softmax(S)，写回 HBM。
3. 从 HBM 读 P、V到SRAM，算出 O = PV，写回 HBM。
```

标准注意力会构建一个完整的 N×N 注意力矩阵，并频繁在 GPU 的HBM和SRAM之间搬运数据。这带来了 $O(N^2)$ 的巨大 I/O 开销，是运行缓慢和内存爆炸的根源。

FlashAttention的核心在于 **分块（Tiling）。** 完整的 $N \times N$ 矩阵从未作为一个整体在任何地方出现过，它只以碎片的形式，短暂地存在于SRAM 中。

![](https://pic4.zhimg.com/v2-35aff690fff8aa9ebce4fc43e53e8809_r.jpg)

FlashAttention的流程如下：

- **外层循环** （红色箭头）：把 K、V 的一小块从 HBM 加载到 SRAM。
- **内层循环** （蓝色箭头）：把 Q 的一小块从 HBM 加载到 SRAM。
- 在 SRAM 内计算这一小块 QK^T、softmax 和加权求和，并用在线 softmax 技术增量更新仍在 SRAM 里的输出 O 块。
- 内层循环跑完一个 Q 块后，把这一个 O 块写回 HBM。接着加载下一个 Q 块。
- 外层循环再加载下一个 K、V 块。

**(c) MLA**

**MLA（Multi-head Latent Attention）** 是在DeepSeek-V2中提出并使用的。它代表的是一条完全不同的优化路径——不减少注意力头的数量，而是改变K和V的计算和存储方式。先将 K 和 V 压缩到一个 **低维潜在空间，只缓存这个压缩后的向量** ，推理时再解压还原。

为了在训练阶段减少激活值（activation）的显存占用，MLA 对Q也进行了低秩压缩，但这部分不会降低 KV Cache。

此外，为了正确计算注意力，MLA 的解决方案是 **解耦 RoPE（Decoupled RoPE）** 。即：额外引入一组专门携带位置信息的Decoupled Query和Decoupled Key，RoPE 只作用在这部分上，而原来压缩恢复的K和Q则保持纯粹的“内容”信息，不带位置编码。示意图如下：

![](https://pic2.zhimg.com/v2-287de298129ce867a8c1cef995544779_r.jpg)

**在这个系列中，我们会更加详细地介绍这些Attention计算的变体，推出它们每个的计算量、显存占用量，甚至我们还会手搓它们的实现代码。**

### **2.3.2 Sparse Attention**

前面我们看到，MLA减少了每个token需要缓存的数据量，但是并没有减少注意力本身的 **计算量** 。对于长度为L的序列，每个query仍然需要与之前所有token计算注意力，因此整体复杂度依旧是$ O(L^2) $。随着上下文长度不断增加，真正的瓶颈开始从 **显存容量（Memory）** 逐渐转向 **注意力计算（Compute）** 。

**DSA（DeepSeek Sparse Attention）** 则是 DeepSeek-V3.2中提出的一种高效稀疏注意力机制，目的是为了解决传统注意力在长序列场景下计算复杂度为 $O(L^2)$ 的效率瓶颈，能够将计算复杂度降为 $O(Lk)$ 。其中 $k$ 是远小于 $L$ 的、被稀疏选中的 token 数。

![](https://pic4.zhimg.com/v2-7934e492c8cb0d5d5d84496c9bc612db_r.jpg)
*DSA和sliding window attention（SWA）的区别。query token只跟最相关的少数token计算注意力*

DSA由两个核心组件构成： **lightning Indexer** 和 **细粒度的token选择** 。

**① Lightning Indexer**

lightning Indexer 头数很少，使用FP8精度计算，用ReLU激活，因此非常轻量（"Lightning"主要是突出的就是它的计算速度很快）。lightning Indexer用来给每个历史token打分，然后只挑出得分最高的top-K（DeepSeek-V3.2中是2048）个token进入真正的注意力计算。

对于query token $ h_t\in R^{d} $和上文中的某个token $ h_s\in R^d $，索引器计算一个索引分数$ I_{t,s} $，决定$ h_t $要不要选择$ h_s $。

![](https://pic3.zhimg.com/v2-174370843800e776553c505ee742792c_r.jpg)

$ H^I $表示索引器的头数（是一个很小的数）；$ q_{t,j}^I \in R^{d_I} $和权重$ w^I_{t,j}\in R $是由query token $ h_t $投影得到的；$ k_s^I\in R^{d_{I}} $由上文token $ h_s $投影得到。

**② 细粒度token选择**

得到query token $ h_t $ 与上文所有token的索引分数$ \{I_{t,s}\} $后，只保留分数最高的top-k个token对应的key-value项$ \{c_s\} $，然后只在这些被选中的KV上计算核心注意力，计算复杂度自然降低到$ O(Lk) $。

### **2.4 Feed Forward层（FFN）**

现代LLM架构在FFN部分一般都使用SwiGLU。SwiGLU分为两部分："Swi-"和"GLU"。下面我们分别来介绍。

**（1）"Swi-"—— Swish激活函数为什么取代了 GELU？**

早期的GPT 系列使用 GELU（Gaussian Error Linear Unit）激活函数，其定义为：

$GELU(x) ≈ 0.5x [1 + erf(x/\sqrt{2})]$

计算时要用多项式逼近误差函数 `erf` ，开销较大。

Swish激活函数则是：

$Swish(x) = x · sigmoid(x)$

Swish用廉价的 `sigmoid` 替代了 `erf` ，计算上更高效而性能差异很小，因此现在的多数LLM出于性价比选择了 Swish。

![](https://picx.zhimg.com/v2-1453ad607549a203268c77f25aa3a3e5_r.jpg)

**（2）"GLU"——Gated Linear Unit**

比激活函数替换更重要的是前馈模块结构的改变，即用GLU（Gated Linear Unit）替代传统两层 MLP。

传统的两层MLP计算公式如下：

$\text{output} = W_2 · Act(W_1·x)$

只有两个全连接层， $W_1$ 负责扩展维度（一般到 $4d$ ），激活之后再映射回原来的维度 $d$ 。

SwiGLU中则是引入了三个矩阵（gate，up，down）：

$output=(W_{up} x⊙Act(W_{gate}x))\cdot W_{down} $

```python3
gate = self.gate_proj(x) 
up   = self.up_proj(x) 
# 激活并逐元素相乘，再投影
output = self.down_proj( F.silu(gate) * up )   
```

为了让参数保持不变，SwiGLU常设计为中间维度为 $\frac{8}{3}d$ ，这样就可以让总参数量和之前保持不变了。SwiGLU门控带来的逐元素乘法交互为网络引入了非线性与条件计算的能力，增强了表达力。

![](https://pic1.zhimg.com/v2-653296e2ae9d359909146b8f63fa2b58_r.jpg)
*传统的两层MLP和SwiGLU的对比*

而在后面的MoE部分，我们将看到：由于FFN 在 Transformer 中占据大量参数，那么用多个专家替代它，就可以在几乎不增加单步计算量的前提下，让模型容量成倍增长。

### **2.5 LM head**

> “.......我们一会儿都不想休息，就向上攀登，一直上到我从一个圆形的洞口见到了天上罗列着的一些美丽的东西。我们从那儿走出去，重新见到了群星。”——但丁，《神曲》

再经过了若干个Transformer层（包含Attention和FFN）之后，会经过一个final RMSNorm层做最后的归一化，然后接linear output layer（也就是LM Head）：

![](https://pic3.zhimg.com/v2-06a8aecb54bb97f00f0c64926d25ca08_r.jpg)

LM Head将Transformer 输出的上下文表示（ $d$ 维向量）映射为词表大小的向量（即logits），并进一步通过softmax转化为下一个 token 的概率分布。

这里还有一个选择，就是要不要让LM Head和Embedding共享参数。在设计一些3B以下的小模型的时候，可能共享参数是一个比较好的策略，因为这可以大幅降低参数量。但是对于大规模参数的模型来说，Embedding的参数只是其中的很小一部分，没有必要为了节约那一点参数而牺牲表达能力。

到目前为止，我们跟随着一个token的脚步，从它刚进入LLM的那一刻开始，一直走到了最后一层。现在我们终于看到了词表中数十万个可能性的璀璨集合，这里闪烁得最明亮的部分，就是最有可能紧接着出现的token。

在解码（decode）的时候，也是利用这样的概率分布，一个一个token地顺序输出。有几种解码方式：

- **贪心解码（Greedy Decoding）** ：直接选概率最高的 token。
- **束搜索（Beam Search）** ：保留 k 条候选序列，最终选整体得分最高的。
- **Top-K 采样** ：温度缩放之后，只保留概率最高的 $K$ 个 token，再随机采样。
- **Top-P 采样** ：温度缩放之后，保留累积概率刚刚超过 $p$ 的最小 token 集合，再随机采样。

> **名词解释——【温度缩放】** 
>  在 softmax 前除以温度 T，调整分布的陡峭度。T越小，分布越sharp，越确定。

### **2.6 Multi-Token Prediction(MTP)**

传统的自回归语言模型在训练时，每个位置只预测下一个 token。MTP 则把预测范围扩展到 **未来多个 token** 。这样做的motivation主要有两个：

1. **增加训练信号密度** ：每个 token 位置不再只产生一个监督信号，而是同时监督它后续 $D$ 个 token 的预测。这让模型从同等量级的训练数据中提取更丰富的学习信号，从而提高数据效率。
2. **促使模型学习更有前瞻性的表示** ：要求模型在当前位置就为未来的多个token做出预测，迫使它学习更具前瞻性的表示，而不是仅仅关注眼前的下一个 token。这种提前规划的能力可以增强模型对长程结构的把握。

![](https://pic2.zhimg.com/v2-24e789a64466627d4e0b0dbce1e5c377_r.jpg)

MTP loss和主LM loss加在一起，同时计算梯度并更新。

MTP 策略的 **主要目的是提升主模型的训练效果** ，因此推理时可以直接丢弃所有 MTP 模块，主模型完全独立运行。训练阶段引入的额外监督信号已经内化到了主模型的参数中。当然了，也可以将 MTP 模块用于投机解码。因为MTP 模块本身就是用来预测未来多个 token 的，那么它们天然可以作为投机解码中的draft model，在一次前向传播中生成多个候选 token，再由主模型进行验证，从而加速生成。

> **名字解释——【投机解码】** 
>  投机解码是一种针对自回归LLM的 **无损** 推理加速技术。其核心思想是用一个轻量级的 **草稿模型 (Draft Model)** 快速生成多个候选 token，再由 **目标模型 (Target Model)** 一次性并行验证这些候选 token，通过接受-拒绝机制保证最终生成的文本分布与目标模型逐 token 生成 **完全一致** ，从而在保持输出质量不变的前提显著降低推理延迟。 
>  每次小模型自回归地快速预测出γ个候选 token，大模型一次性把【原序列 + 这γ个候选 token】吃进去，算出这个γ位置的输出概率，从前往后逐个检查候选 token 是否在大模型自己的top-k 个选择里。如果相同，就接受，接着检查下一个。一旦出现第一个不被接受的候选 token，后面的全部丢弃。对于这个位置，大模型会修正出一个新 token 来替代。

## 0x03. Mixture of Expert (MoE)

### **3.1 MoE的整体结构**

在稠密模型中，每个 token 都会经过同一个FFN；而 MoE 的做法是把 FFN 替换为多个并行的FFN，并引入一个路由器（Router），让每个 token 只激活其中的一小部分最合适FFN专家。

这样做的好处是：模型的总参数量可以非常大，但每个 token 实际只激活极少数专家，因此计算量近似恒定，实现了稀疏的、参数规模与计算量解耦的大模型。

![](https://pic3.zhimg.com/v2-a14450cef034cfc556a5dca588f52934_r.jpg)
*MoE的专家就是多个FFN层*

![](https://pic2.zhimg.com/v2-c583a28ed9fdffaf5b3f464b9aa3154f_r.jpg)

前面使用稠密层，后面使用MoE层的这种方案其实是比较合理的，因为前面的层学到的是一些共性的、关于语义的表示，而在后面的层分化出不同的专家，关注不同token的不同方面，这个在直觉上也是容易理解的。

不过，这种交叉dense层和moe层的坏处就是会带来一些训练/推理调优的困难，因为每个层的参数量不一样、计算量不一样，会给调优带来一些麻烦。

### **3.2 专家的粒度**

早期的MoE专家数量通常很少（比如 8 个或 16 个）。每个专家被分配到的 token 会覆盖多种不同类型的知识。这会导致知识混杂的问题：一个专家不得不把五花八门的知识都塞进自己的参数里，结果就是什么都会一点，但什么都学不精。模型很难在推理时高效调用这些混杂在一起的知识。

细粒度专家，就是把每个标准 FFN 专家的中间隐藏维度缩小为原来的 $1/m$ ，也就是把一个“大专家”切成 $m$ 个“小专家”。总专家数从 $N$ 变为 $mN$ ，但总参数量不变。相应地，把每个 token 激活的专家数量从 $K$ 增加到 $mK$ ，所以总计算量也不变。

（ *当然这只是理论上的啊，实际上因为要考虑到路由和all-to-all通信，细粒度专家会导致训练和推理速度大幅下降，需要在infra层面做很多的优化才可以* ）

拆分后，不同的小专家可以分别学习被拆解得更细的知识，每个专家更 **专精** 。从组合爆炸的角度看，可选的专家组合数量暴增。比如，从 16 个专家选 2 个只有 120 种组合；但拆成 m=4后，变成从 64 个小专家选 8 个，组合数飙升至 44 亿种。这让每个 token 可以 **更灵活、更精准地组合所需的知识模块** 。

![](https://pic4.zhimg.com/v2-48f3da77b8d04caf9445afd6a8fa6aaf_r.jpg)
*从粗粒度专家，到细粒度专家*

### **3.3 共享专家**

不同专家处理的 token 可能都需要某些 **共性知识** 。如果没有共享专家，那么多个专家会在各自的参数中分别学会同一套知识，造成参数空间的浪费，也就是冗余。

所以，可以隔离开一部分专家，指定为共享专家，每个 token 都会无条件地、确定性地经过这些共享专家。那么为了保持总计算量不变，需要相应地减少可路由专家中激活的数量。 
 这样的好处是，共享专家可以专门负责学习共性知识，其他路由专家就不再需要各自学习一遍这些冗余知识，它们就可以 **更加聚焦于自己那部分独特的、非共享的知识** 。这提升了 **参数效率** ，让每个路由专家的 **特化程度更高** 。

![](https://picx.zhimg.com/v2-382952683f538ca53f94dc09942789c5_r.jpg)
*shared Expert一直被激活；Routed Expert激活top K*

结合细粒度专家和共享专家，一个完整的MoE 层的输出 = 所有共享专家的输出之和 + 选中的若干细粒度路由专家的加权输出之和 + 残差连接。

共享专家 $K_s$ 个，始终激活。细粒度路由专家 $mN−K_s$ 个，通过路由稀疏激活。细粒度专家+共享专家的计算公式如下：

### **3.4 负载均衡、Auxiliary Loss与Token Drop**

如果不加干预，router很容易出现负载不均衡的情况。即训练初期某些专家学得更好，router就更频繁地把 token 分配给它们，导致这些专家训练数据更多、越学越好，而其他专家则越来越被冷落。这就是 **路由坍塌** ，被闲置的专家形同虚设，模型实际上退化成了一个更小的稠密模型，浪费了 MoE 的参数量优势。

![](https://pic2.zhimg.com/v2-bb85452f450f63d49c0447c195106307_r.jpg)
*其它Expert充当一个气氛组的作用哈哈哈*

### **3.4.1 辅助损失（Auxiliary Loss）**

辅助损失的核心思想是，在不影响模型主任务（下一个 token 预测）性能的前提下，通过添加额外的损失项，软性地引导Router做出更均衡的专家选择。

**① 专家级平衡损失 (Expert-Level Balance Loss)**

这是最基础的负载均衡损失，旨在防止路由坍塌。确保每个专家都能被充分训练，而不是只有少数几个专家被频繁使用。最终要达到的理想状态是： **每个专家被选中的概率都相等，并且每个专家实际处理的 token 数也完全相等** 。

**② 设备级均衡损失 (Device-Level Balance Loss)**

在专家并行训练中，多个专家被放置在不同的device（如 GPU）上。即使每个专家负载均衡，不同设备上的总计算量仍可能不均衡。处理热门专家的设备会成为计算瓶颈，拖慢整个系统的效率（因为每一步都需要等待最慢的device完成计算）。而处理冷门专家的设备则处于空闲状态，造成算力浪费。

为了解决这个问题，可以将所有路由专家分成 $D$ 组，每组对应一个device。这个损失鼓励每个device接收到的总 token 数量和路由概率保持均衡，因此各 GPU 的计算量相当，避免某些GPU过载而其他闲置。

**③ 通信平衡损失 (Communication Balance Loss)**

不同专家分布在不同设备上，token 的分发和结果聚合会引入额外通信开销。要理解这个balance loss，首先我们要区分网络通信的两个方向：

- **发送 (Send)** ：一个设备上的 token，需要被路由到其他设备上的专家去计算。这是设备向外发送数据。
- **接收 (Receive)** ：一个设备上的专家，收到了来自其他设备发来的 token 进行计算。这是设备从外接受收数据。

在分布式训练中，token 需要被路由到其选中的专家所在的设备上进行计算。这就涉及到了 **All-to-All 通信** ，即每个设备既发送 token 也接收 token。

在此前，Deepseek-V2中为了均衡通信开销，已经提了一个方法： **设备限制路由** （Device-Limited Routing）。即，对于当前 token先计算它与每个设备的总体亲和度。这个总体亲和度通常取该设备上所有专家的路由分数的最大值（或总和）。然后从所有设备中选出亲和度最高的M个设备，然后只在这 M个设备包含的专家集合中执行Top‑K 选择。这样，无论 K有多大，每个 token 至多只与 M 个设备发生通信，最坏情况下的通信开销被严格控制。

Device-Limited Routing解决了 **发送侧** 的问题。它规定了每个 token 的目标专家最多只能分布在 M 个设备上。

**但接收侧是完全没有约束的** 。一种典型的不均衡场景是：某个设备上恰好存放了当前非常热门的专家，导致大量 token 都被路由器选中，需要路由到这个设备来计算。这就会导致接收端的网络带宽被打满。

这里你可能会有一个疑问：之前不是有设备级均衡损失了吗？它不也是让每个设备上的计算量差不多吗？那么为什么还需要通信辅助损失呢？

区别在于统计口径不同：

- 设备级均衡损失统计的是：每个设备上的专家总共被选了多少次。
- 通信均衡损失统计的是：每个设备作为接收方，总共收到了多少个外部来的token。

一个典型的冲突场景是：假设所有 token 都采用这种策略，选一个本地专家 + 一个远程设备 A的专家。那么，从专家计算量看：每个设备上的专家都被均匀地选中，设备级均衡损失为 0，完美！但从接收token数看：设备 1 收到了所有 token 的远程请求，而其他设备接收的远程请求为 0，通信严重失衡。

所以，通信均衡损失通过惩罚接收token过多的热门设备，从而避免接收端出现通信和计算瓶颈 **。**

> **名词解释——All-to-All通信：** 
>  All-to-All通信是一种全局集合通信操作，每个设备都会向其他每个设备发送一份专属的数据块，同时也会从其他每个设备接收一份专属的数据块。 
>  MoE中的第一次All-to-All（Scatter/分发）：每个设备上都有很多 token，经过本地的门控决策，这些 token 的目标专家可能分布在各个设备上。第一次通信结束后，每个设备都收到了“所有想来本设备上专家”的 token。 
>  MoE中的第二次All-to-All（Gather/汇聚）：每个设备对自己收到的 token，都计算完了它所负责的专家。现在，每个设备需要收回自己派发出去的所有 token 的专家计算结果，并可以把这些结果拼接起来，继续后续的运算。 
>  All-to-All的通信复杂度是 O(N²) 的（N 为设备数），通信量会随着设备数量的增加而爆炸式增长。它往往是限制 MoE 大规模扩展的主要瓶颈。

【综上所述】，上面的三个balance loss构成了完整的、分工明确的负载均衡体系：

- **专家级均衡损失** ：在微观层面，确保每个专家个体能够收到数量差不多的token，防止路由坍塌。
- **设备级均衡损失** ：在宏观层面，确保每个设备计算量均衡，解决计算瓶颈。
- **通信均衡损失** ：在网络层面，确保每个设备收发数据量均衡，解决通信瓶颈。

### **3.4.2 Auxiliary-Loss-Free：**

Auxiliary Loss的一个问题就是， **加多了会损害模型性能** ，因为这种强制均匀分配可能与数据本身的自然分布相悖，模型被迫把一些本不该由某专家处理的 token 硬塞给它；调小辅助损失又怕负载失衡。这是一个艰难的权衡。

所以Aux-Loss-free的方法引入了一个为每个专家设置的 **偏置项** $b_i$ ​，并对其进行动态调整。

![](https://pica.zhimg.com/v2-72afb86ce4938937d8b88961959980ce_r.jpg)

关键的细节是，bias只影响路由 **选择** （即 token 分给谁），而不影响分过去之后的权重。这就是说，一旦决定了被选中的专家，真正与该专家 FFN 输出相乘的权重仍然使用原始的权重 $s_{i,t}$ 。这意味着bias项可以为了负载均衡而影响该选择哪些专家，但它不会直接影响模型实际“信任”这个专家的程度，从而保护了模型的上限性能不被损害。

在每个训练步骤结束时，会统计整个批次数据里每个专家的负载情况。然后根据这个统计，以固定的步长 $\gamma$ 更新偏置，使各个专家的 token 负载在整个训练过程中保持动态均衡。

- **如果某专家过载** （收到的 token 超过平均值），说明它太热门了，则门槛需要提高， **偏置** $b_i$ **下调** $\gamma$ 。
- **如果某专家欠载** （收到的 token 少于平均值），说明它太冷门了，门槛需要降低， **偏置** $b_i$ **上调** $\gamma$ 。

### **3.4.3 Token Drop**

辅助损失能鼓励负载均衡，但无法保证严格的负载均衡。实际训练中仍可能偶尔出现某个专家/设备接收的 token 超出其处理能力（capacity）的情况，所以就要用到Token Drop。多余的 token 被直接丢弃，不经过任何 FFN 专家计算，仅依靠残差连接向前传递。比如DeepSeek-V2 就引入了device级的 Token-Drop策略。

为了固定计算/内存开销并保证硬件效率，许多早期 MoE 模型会为每个专家设定一个最大处理 token 数（即容量，capacity）。容量由 `capacity_factor` （容量因子）决定：

`Expert Capacity = (总 Token 数 / 专家数) × capacity_factor`

例如 `capacity_factor = 1.25` 表示每个专家最多处理 1.25 倍于平均负载的 token。

如果某个设备接收到的 token 超过了预算，可以丢弃那些亲和度得分最低的 token，直到满足预算为止。亲和度得分低意味着该 token 本就不太“适合”这个专家，丢弃它们对最终输出的影响相对最小。这些 token只走残差连接，而不会参与MoE的计算。

但这会带来若干问题：

- **信息丢失** ：被丢弃的 token 在当前层没有获得任何专家知识，可能损害模型性能
- **训练‑推理不一致** ：若训练时有 token drop 而推理时没有token drop（或使用不同的 `capacity_factor` ），会导致训推不一致。

所以现在的主流模型大多转向无 token drop的设计，依靠精心设计的辅助损失来实现自然负载均衡。
