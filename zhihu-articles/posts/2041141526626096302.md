[compsac2026_CuTile.pdf](https://boyang.cs.uwm.edu/publication/compsac2026_CuTile.pdf)

我读完《Evaluating CUDA Tile for AI Workloads on Hopper and Blackwell GPUs》后，最大的感受是：这篇论文讨论的并不只是一个新的 CUDA 写法，而是一个更大的问题——AI 系统里的自定义 kernel，到底应该交给谁来写？

过去这个问题的答案很分裂。

如果你只是做标准矩阵乘法，那就用 cuBLAS / torch.matmul。 如果你要写一些灵活的融合算子，很多团队会选 Triton。 如果你追求极致性能，特别是在 Attention、MoE、量化、通信融合这类地方，最后往往还是会走向 CUDA C++、CUTLASS、FlashAttention 这样的手写或半手写路径。

CUDA Tile，也就是 CuTile，想插进这个缝隙里。

NVIDIA 对它的定位是：把 GPU 编程从传统 SIMT 线程视角，提升到 tile 视角。开发者描述“我要在这些 tile 上做什么数学计算”，编译器和 runtime 再决定如何把工作映射到线程、Tensor Core 等硬件资源上；CUDA 13.1 同时发布了 CUDA Tile IR 和 cuTile Python 这两个组件。

这听起来很像一个很诱人的承诺：**用 Python 写出接近手写 CUDA 的 Tensor Core kernel。**

但系统软件里没有免费的抽象。抽象减少了你要写的代码，也会把一部分性能命运交给编译器。于是这篇论文问了一个很工程的问题：

**CuTile 到底该不该用？如果该用，是在哪些 workload、哪些 GPU、哪些场景下用？**

论文在 arXiv 上提交于 2026 年 4 月 25 日，作者是 Divakar Kumar Yadav、Tian Zhao 和 Deepak Kumar；它把 CuTile 和 cuBLAS、Triton、WMMA、raw SIMT 放在一起，在 H100 NVL、B200、RTX PRO 6000 Blackwell Server Edition 三类 GPU 上测试 GEMM、fused multi-head attention 和端到端 LLM inference。

**这篇论文最值得读的地方，不是“CuTile 打败了谁”，而是它告诉我们：NVIDIA 正在把高性能 GPU kernel 编程往更高层的抽象推。**

过去写 AI kernel 大概有三种选择：

最省事的是用现成库，比如 cuBLAS、FlashAttention、cuDNN。问题是灵活性有限。

更灵活的是用 Triton。它让开发者可以用 Python 风格写 GPU kernel，已经被很多 AI Infra 团队接受。

最极致的是手写 CUDA / CUTLASS / WMMA。性能上限高，但开发和维护成本都很高。

CuTile 想做的是第四种路径：让开发者用 tile 级别的方式描述计算，由编译器去处理更多底层 GPU 细节。它的承诺不是“所有场景都最快”，而是“能不能用更少代码写出足够接近手写 CUDA 的性能”。

从这篇论文的结果看，答案是：**有希望，但不能过度解读。**

在标准矩阵乘上，CuTile 不该替代 cuBLAS。cuBLAS 仍然是标准 GEMM 的首选。

在 B200 这种数据中心 Blackwell GPU 上，CuTile 的 fused attention 表现很强，说明它确实能吃到 Blackwell 的新硬件能力。

但论文没有证明 CuTile 超过当前最强的 FlashAttention 系列，因为它主要对比的是 FlashAttention-2，而不是 Hopper 上的 FlashAttention-3，也不是 Blackwell 上的 FlashAttention-4。

在 RTX PRO 6000 这种 workstation Blackwell 上，CuTile 的表现反而不稳定，说明同样叫 Blackwell，不同芯片、不同编译器路径下，结果可能差很多。

所以这篇论文的合理结论应该是：

**CuTile 不是 cuBLAS 的替代品，也不是 FlashAttention 的全面替代品。它更像是 NVIDIA 给 Blackwell 时代准备的一个新 kernel 开发工具。**

如果你在写普通矩阵乘，继续用 cuBLAS。

如果你在做生产级 attention，Hopper 上应该优先看 FlashAttention-3，Blackwell 上应该看 FlashAttention-4、cuDNN 或 TensorRT-LLM 里的最新实现。

如果你在写自定义融合算子，尤其是过去需要用 WMMA 或大量 CUDA C++ 才能完成的 kernel，CuTile 值得认真评估。

如果你的目标是跨 H100、B200、RTX PRO 等多种 GPU 部署，Triton 目前仍然更稳，因为 CuTile 的跨架构成熟度还需要时间验证。

一句话：**这篇论文证明的不是 CuTile 已经赢了，而是 CuTile 可能让“写高性能自定义 kernel”这件事变得更省事。**

### 1. CUDA Tile 真正想解决的问题是什么？

AI Infra 里有一个长期存在的矛盾：模型越来越大，kernel 越来越关键，但能写高性能 kernel 的人并没有变多。

一个 Transformer block 里，看起来都是矩阵乘、Attention、归一化、激活函数。但真要做系统优化，问题会迅速变成：怎么减少 HBM 访问？怎么用 Tensor Core？怎么安排 shared memory？怎么做 double buffering？怎么处理 epilogue fusion？怎么在新一代 GPU 上重新调 tile shape？

这也是为什么 FlashAttention、CUTLASS、TensorRT-LLM、vLLM 这些系统工程会变得如此重要。论文开头就指出，现代 serving 系统依赖 FlashAttention-2、CUTLASS 这类手工优化 kernel 来接近硬件峰值，但这些 kernel 往往有大量架构相关 CUDA 代码，每一代 GPU 都要重调。

CuTile 的野心，就是把“线程、warp、寄存器、shared memory”这些底层细节隐藏一部分，让开发者用 `ct.load`、`ct.mma`、`ct.store` 这类 tile primitive 表达计算，同时仍然利用 Tensor Core 和 TMA。论文把它描述为一种 Python-based、tile-centric 的 GPU kernel abstraction。

换句话说，CuTile 不是想替代 torch.matmul 这种库调用；它真正想替代的是一部分“为了定制化而不得不手写 CUDA”的工作。

这点很关键。因为很多关于新 DSL 的讨论，最后都会被一个错误问题带偏：它能不能干掉 cuBLAS？

大概率不能。 也不应该这么问。

更好的问题是：**它能不能让一个团队用更低的工程成本，写出足够快、足够可维护、还能吃到新硬件红利的自定义 kernel？**

### 2. 先说 GEMM：CuTile 很好，但不该替代 cuBLAS

论文里的 GEMM 结果非常清楚：标准 GEMM 还是 cuBLAS 的地盘。

在 BF16 square GEMM 上，B200 的 cuBLAS 在 8192×8192 规模达到 1671.8 TFLOP/s，CuTile 是 875.8 TFLOP/s，Triton 是 1032.9 TFLOP/s；RTX PRO 6000 上，CuTile 也明显落后于 cuBLAS 和 Triton。论文总结为：CuTile 在 Blackwell 上达到 cuBLAS 的 52–79%，明显强于 WMMA，但不足以替代 cuBLAS。

这件事其实不意外。

cuBLAS 是 NVIDIA 自己长期优化的闭源库，做的是固定 API 下的极致吞吐。你用 torch.matmul，本质上是在买一个“我不关心 kernel 内部怎么写，只要给我最高性能”的结果。

CuTile 的价值不是在这里。

真正有意思的是另一组对比：CuTile 对 WMMA。

论文里，CuTile 在多数 GEMM size 上比 WMMA 快 1.5–5.0 倍，而且 kernel 代码只有 22 行，WMMA 是 123 行。

这个结论比“CuTile 不如 cuBLAS”更重要。

因为如果你能用 cuBLAS，当然继续用 cuBLAS。 但如果你在写的是 fused GEMM + activation、自定义 epilogue、或者某些 cuBLAS 固定 API 覆盖不了的 kernel，那 CuTile 的意义就出来了：它给了你一个比 WMMA 更短、更像 Python DSL、又能触达 Tensor Core 的写法。

所以 GEMM 部分，我会给出一个很工程化的判断：

**标准 GEMM：不要切 CuTile。 自定义 GEMM：可以看 CuTile。 还在维护 WMMA：优先考虑 CuTile。**

这不是性能冠军的问题，而是工程成本的问题。

### 3. 再看 Attention：B200 上，CuTile 打出了最亮的一张牌

这篇论文最抓人的结果在 fused attention。

在 B200 上，BF16 causal attention，batch=8，32 heads，head dim=128，seq=4096 时，CuTile 达到 1007.4 TFLOP/s；同一条件下 FlashAttention-2 是 400.7 TFLOP/s，Triton 是 525.6 TFLOP/s。也就是说，CuTile 在这个点上比 FlashAttention-2 快 2.51 倍，比 Triton 快 1.92 倍。

这很惊人。

因为 FlashAttention-2 不是一个随便写的 baseline。它是现代 LLM 系统里被反复打磨过的 attention kernel。一个 60 行左右的 CuTile Python kernel，在 B200 上跑出这个结果，说明至少在这个组合上，NVIDIA 的 tile abstraction 和 Blackwell 数据中心 GPU 之间确实出现了很强的协同。

但论文的另一半结果也同样重要。

同一个 CuTile attention kernel，放到 RTX PRO 6000 Blackwell Server Edition 上，在 seq=4096 时只有 178.8 TFLOP/s；FlashAttention-2 是 335.4 TFLOP/s，Triton 是 287.7 TFLOP/s。论文把这个现象称为 CuTile attention paradox：同样的代码，在 B200 上比 FlashAttention-2 高 2.51 倍，在 RTX PRO 6000 上却低 47%，两者形成 5.6 倍的跨架构差距。

这就是 CuTile 当前最值得警惕的地方。

它不是简单的“Blackwell 上都很好”。 而是 **sm_100 的 B200 很好，sm_120 的 RTX PRO 6000 并不好**。

论文作者认为，这可能来自 tileiras 编译器对 sm_100 和 sm_120 的优化成熟度差异，也可能来自 TMA、Tensor Core microarchitecture、shared memory 配置等差异；论文特别指出，B200 看起来像是 CuTile 编译器的主要优化目标，开发者必须在自己的具体 GPU 上 benchmark 之后再决定是否采用。

这也是我认为这篇论文最有价值的地方。它没有停留在“新 DSL 很有潜力”，而是把潜力拆成了一个很现实的问题：

**你买的是哪张卡？**

在 GPU 系统里，“Blackwell”不是一个足够精确的答案。 B200 和 RTX PRO 6000 都叫 Blackwell，但对 compiler、shared memory、kernel tuning 来说，它们可能是两种命运。

### 4. Triton 的位置并没有被动摇

读这篇论文时，很容易被 CuTile 在 B200 attention 上的 1007 TFLOP/s 吸引。但如果站在一个 infra 团队的角度，Triton 的价值反而更清楚了。

论文里，Triton 在所有测试平台上都能跑，并且在 GEMM 上保持了 62–101% 的 cuBLAS 性能；相比之下，CuTile 在论文测试环境里不能覆盖 H100，且在不同 Blackwell 变体上的 attention 表现差异很大。

这说明 Triton 的优势不是单点峰值，而是**跨架构稳定性**。

如果你的 fleet 里既有 H100，又有 B200，还有一些 RTX PRO / L40S / Ada 之类的卡，那你大概率不想为每个 GPU 维护一套完全不同的 kernel 策略。此时 Triton 的收益不是“最快”，而是“足够快，并且少踩坑”。

CuTile 在 B200 上给出了一个非常诱人的上界。 Triton 则给出了一个更稳的工程下界。

这两者不是简单替代关系。更可能的未来是：在 B200/B100 这种数据中心 Blackwell 上，对 attention-heavy workload，CuTile 会成为值得专门优化的一条路径；而 Triton 仍然是异构 GPU fleet 上更通用的 kernel DSL。

### 5. 代码量：CuTile 最强的卖点不是性能，而是维护成本

论文有一个很有意思的表，比较了不同实现的代码量。

GEMM kernel：cuBLAS 是 1 行 API，Triton 是 53 行，CuTile 是 22 行，WMMA 是 123 行。Attention kernel：FlashAttention-2 和 PyTorch SDPA 作为库 API 近似 1 行，Triton 是 62 行，CuTile FMHA 是 60 行。

这个结果很能说明 CuTile 的定位。

在 GEMM 上，CuTile 的代码量显著低于 Triton 和 WMMA。论文解释说，CuTile 的 `ct.load`、`ct.mma`、`ct.store` 抽象掉了 shared memory tiling、register allocation、warp scheduling 这条 pipeline；对于正在维护 WMMA kernel 的开发者，这个生产力收益本身就可能足以支持迁移。

但在 Attention 上，CuTile 和 Triton 的代码量差不多。因为 Attention 的复杂度不只来自 tiling，还来自 online softmax、causal mask、running max / sum 等算法结构。论文也指出，Attention 场景下 CuTile 和 Triton 的选择主要取决于性能和可移植性：B200 上 CuTile 赢，其他地方 Triton 更稳。

这背后有一个更一般的判断：

**抽象最值钱的地方，不是把简单事情变简单，而是把复杂但重复的硬件细节变得不再需要每个团队手写。**

CuTile 对 GEMM 的价值，是减少硬件细节。 CuTile 对 Attention 的价值，是在特定硬件上让编译器和 Tensor Core / TMA 打出更高上限。

这两种价值不一样。

### 6. 端到端推理：现在还不能直接把 CuTile 等同于 LLM serving 加速

论文也测了一个 LLaMA-7B-like 的 4 层模型，但这里要非常谨慎。

作者明确说，CuTile 目前提供的是 GEMM、attention 这类 individual kernel primitives，不是完整端到端 inference pipeline；端到端测试更多是为了给已有 PyTorch backend 的性能水平提供上下文。

论文里的端到端结果显示，fused attention backend，比如 SDPA、FlashAttention-2，相对 naive unfused baseline 能带来 1.7–2.4 倍 prefill 加速；但 decode 阶段在使用 fused attention 后更多受 memory bandwidth 约束，B200 batch=32 时几个 fused backend 的 decode 都在 4594–4647 tok/s 左右。

所以不能简单说：

“CuTile attention 快 2.5 倍，所以 LLM serving 就快 2.5 倍。”

这是典型的 kernel-level benchmark 和 system-level throughput 之间的差别。

在 prefill-heavy、long-context、attention-heavy 的场景里，CuTile 可能有明显价值。 但在 decode-heavy 的在线服务里，瓶颈可能转到 KV cache 访问、memory bandwidth、batching、scheduler、通信、speculative decoding 等地方。

这也是做 AI Infra 最容易踩的坑：一个 kernel 的胜利，不自动等于系统的胜利。

### 7. 还有一个版本问题：这篇论文的结论要按“测试环境”理解

这里需要补一刀。

论文的实验环境是 CUDA Toolkit 12.8 + 13.1、CuTile 1.1.0，Blackwell 上使用 CuTile；H100 上 CuTile 不可用。

但 NVIDIA 后续 CUDA 13.2 的官方博客和 cuTile Python 文档已经给出了更新口径：CUDA 13.2 中 CUDA Tile 支持 compute capability 8.x、10.x、11.x、12.x；cuTile Python quickstart 也写明前置条件包括 compute capability 8.x、10.x、11.x 或 12.x 的 GPU、R580 或更新驱动、Python 3.10–3.13，以及 CUDA Toolkit 13.1+ 或 `cuda-tile[tileiras]` 安装路径。([NVIDIA Developer](https://developer.nvidia.com/blog/cuda-13-2-introduces-enhanced-cuda-tile-support-and-new-python-features/))

这意味着，论文里“CuTile 只在 Blackwell 可用”的表述，需要放在它的测试版本和实验设置中理解，而不能当成永久事实。

但是有一点仍然成立：**Hopper，尤其是 H100/H200，在这些官方支持集合里并不是 CuTile 的主战场。**

所以对真实团队来说，最稳妥的读法是：

这篇论文不是 CuTile 永久性能的终局判断，而是 CUDA Tile 早期生态里一次非常有价值的实测快照。它告诉我们：CuTile 的上限很高，但成熟度和架构敏感性也很明显。

### 8. 我会怎么选？

最后给一个更落地的 decision table。

| 场景 | 我的建议 |
| --- | --- |
| 标准 GEMM，直接 torch.matmul / cuBLAS 能解决 | 不要切 CuTile |
| Blackwell 上需要自定义 GEMM fusion | 可以试 CuTile |
| 正在维护 WMMA Tensor Core kernel | 强烈建议评估 CuTile |
| B200 / B100 上做 fused attention，尤其长上下文 prefill | 值得重点看 CuTile |
| RTX PRO 6000 / sm_120 上做 attention | 先别急，FlashAttention-2 / Triton 更稳 |
| GPU fleet 混有 H100 和 Blackwell | Triton 更适合作为统一方案 |
| 需要 FP8 / INT8 生产级量化 kernel | 论文没有给证据，暂时不能下结论 |

这个表基本也和论文结论一致：作者建议，在 B200/B100 数据中心 GPU 上写 fused attention kernel，或者在 Blackwell 上替代 WMMA，可以切 CuTile；但如果需要跨架构可移植性、使用标准 GEMM、目标是 RTX PRO 6000，或者需要 FP8/INT8，就不建议直接切。

### 9. 更大的信号：NVIDIA 在重新定义“写 kernel”的边界

这篇论文最值得关注的，不是 CuTile 今天有没有全面战胜 Triton，也不是某个 benchmark 上 1007 TFLOP/s 的数字。

更大的信号是：NVIDIA 在把 Tensor Core 级别的 kernel 编程，往更高层、更 Python 化、更 compiler-driven 的方向推。

这件事如果成了，会改变很多团队的 kernel 开发方式。

以前，一个模型系统团队想做深度 kernel 优化，常常要在两个极端之间选：要么用库，快但不灵活；要么手写 CUDA，灵活但人力成本很高。Triton 已经把这个边界往上推了一层。CuTile 则代表 NVIDIA 自己试图把这个边界再往硬件内侧推：你写 tile 级逻辑，我来负责更底层的硬件映射。

但这条路不会一夜成熟。

编译器要变好，architecture coverage 要变广，和 PyTorch / vLLM / TensorRT-LLM 这类系统的集成要做起来，profiling 和 autotuning 工具也要跟上。论文自己也承认，它没有做 Nsight Compute 级别 roofline 分析，没有覆盖 FP8/INT8，只测了单 GPU 实例，端到端模型也只是 4 层 proxy，不是完整 32 层 LLaMA-7B。

所以我的判断是：

**CuTile 现在不是 Triton 的全面替代品，也不是 cuBLAS 的替代品。 它更像是 NVIDIA 给 Blackwell 时代准备的一把新刀。**

这把刀在 B200 attention 上非常锋利。 在标准 GEMM 上没必要用。 在混合 GPU fleet 上还不够稳。 在未来，如果 CUDA Tile 编译器成熟、Hopper/更多架构支持改善、并进入 PyTorch 或 vLLM 的关键路径，它才可能真正改变 AI kernel 的开发范式。

现在最合理的姿势不是“All in CuTile”，而是把它放进团队的 kernel toolbox：

**cuBLAS 负责标准算子，Triton 负责跨架构自定义，CuTile 负责 Blackwell 上值得押注的高价值 kernel。**

这可能也是这篇论文最有启发的地方： 新的抽象不会消灭旧的抽象，它会重新划分每种抽象最适合的位置。
