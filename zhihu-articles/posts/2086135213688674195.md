## 结构总览

```text
┌─────────────────────────────────────────────────────────────────┐
│  逻辑层: Radix Tree (radix_cache.py)                             │
│  节点 value = torch.Tensor[int64]，存的是一串「slot 索引」           │
│  作用: token 序列 → slot 索引的映射（前缀匹配、分裂、驱逐）            │  
├─────────────────────────────────────────────────────────────────┤
│  页表层: ReqToTokenPool (memory_pool.py)                         │
│  req_to_token = torch.zeros((max_reqs, max_context_len), int32) │
│  作用: 每个请求一行，记录 「第 i 个 token 的 KV 存在哪个 slot」         │
├─────────────────────────────────────────────────────────────────┤
│  物理层: MHATokenToKVPool (memory_pool.py)                       │
│  k_buffer[layer] = torch.zeros((slots, head_num, head_dim))     │
│  v_buffer[layer] = torch.zeros((slots, head_num, v_head_dim))   │
│  作用: 真正存 KV tensor 的 GPU 显存                               │
├─────────────────────────────────────────────────────────────────┤
│  分配器: TokenToKVPoolAllocator (allocator/token.py)             │
│  free_pages = torch.arange(1, size+1)  ← 就是一个 slot ID 池     │
│  作用: 分配/回收 slot 索引                                        │
└─────────────────────────────────────────────────────────────────┘
```

## 分配器：怎么分配和回收 slot

TokenToKVPoolAllocator极其简单[sglang/Python/sglang/srt/mem_cache/allocator/token.py#L28]

```text
class TokenToKVPoolAllocator:
    def clear(self):
        # 就是一个连续的 int64 tensor 当作 free list
        self.free_pages = torch.arange(1, self.size + 1, dtype=torch.int64, device=device)
        self.free_group = None
        self.release_pages = torch.empty((0,), dtype=torch.int64, device=self.device)

    def alloc(self, need_size: int):
        ......
        # 从头部切 need_size 个 slot
        select_index = self.free_pages[:need_size]
        self.free_pages = self.free_pages[need_size:]
        return select_index  # shape: (need_size,) 的 tensor

    def free(self, free_index: torch.Tensor):
        ......
        # 把 slot 索引拼回 free list
        self.free_pages = torch.cat((self.free_pages, free_index))
        ......
```

## 物理层：KV 数据怎么存

以MHATokenToKVPool为例，每层 layer 都有一个大 tensor

```text
# NHD 布局（默认 Number（序列长度）× Head（头数）× Dim（每个头的维度））:
k_buffer[layer] = torch.zeros((size + page_size, head_num, head_dim))
v_buffer[layer] = torch.zeros((size + page_size, head_num, v_head_dim))

说明：
1. size 整个 KV 池能容纳的“真实 token 总数”（对应 max_total_num_tokens）
2. 每个 token 的 KV 直接通过 slot index 寻址
3. page_size 是 KV Cache 分配与管理的基本单位，定义了“一页（page）里连续存放多少个 token 的 KV 数据”。
4. page_size 影响 attention kernel 怎么按页读取 KV（比如 FlashInfer 的 paged kernel 一次读一页），以及前缀缓存的匹配粒度（按页 hash 匹配，而不是按 token）。
5. 即使 page_size > 1，按 page_size 大小读取 KV，底层仍然是 token slot 索引。
   ex.slot 5 的 K 值 = k_buffer[layer][5]  → shape (head_num, head_dim)
```

### 不同的 attention 机制用不同的 KV 池子类

都继承自同一个基类 KVCache 个基类KVCache [sglang/Python/sglang/srt/mem_cache/memory_pool.py#L1820]

```text
KVCache (抽象基类)
├── MHATokenToKVPool          ← 标准 Multi-Head Attention (LLaMA, Qwen, Mistral...)
│   ├── MHATokenToKVPoolFP4   ← MHA + FP4 量化存储
│   ├── MHATokenToKVPoolMXFP8 ← MHA + MXFP8 量化
│   └── PageMajorMHATokenToKVPool ← MHA + 页优先布局
├── MLATokenToKVPool          ← Multi-head Latent Attention (DeepSeek V2/V3)
│   ├── MLATokenToKVPoolFP4
│   └── DSATokenToKVPool      ← DeepSeek Sparse Attention
├── HybridLinearKVPool        ← 混合模型 (Full Attn + Mamba/SSM 层)
└── MiniMaxSparseKVPool       ← MiniMax 稀疏注意力
```

核心区别：tensor 的 shape 不同

| 池类型 | buffer 结构 | 单 slot shape | 为什么不同 |
| --- | --- | --- | --- |
| MHA | k_buffer[layer] + v_buffer[layer] 分开 | (head_num, head_dim) 如 (32, 128) | K 和 V 独立，多头 |
| MLA | kv_buffer[layer] 只有一个 | (1, kv_lora_rank + rope_dim) 如 (1, 576) | K/V 压缩为一个低秩向量，无多头 |
| Hybrid | 内部同时持有 MHA 池 + Mamba 状态池 | 混合 | Full attn 层用 MHA，SSM 层用 state |

```text
# MHA: 分离的 K、V buffer，每行 = (head_num, head_dim)
k_buffer[layer] = torch.zeros((size + page_size, head_num, head_dim))      # 如 (10000, 32, 128)
v_buffer[layer] = torch.zeros((size + page_size, head_num, v_head_dim))    # 如 (10000, 32, 128)

# MLA: 合并的 KV buffer，每行 = (1, kv_lora_rank + rope_dim)
# KV 被压缩到 kv_lora_rank 维（如 512）+ rope_dim（如 64），不再有「多头」的概念——所有头的信息被压缩到一个 latent 向量中。
kv_buffer[layer] = torch.zeros((size + page_size, 1, kv_lora_rank + qk_rope_head_dim))  # 如 (10000, 1, 576)
```

## 页表层：请求如何找到自己的 token KV

ReqToTokenPool是一个二维表

[sglang/srt/mem_cache/memory_pool.py#L272-L310]

```text
class ReqToTokenPool:
    def __init__(self, size, max_context_len, device, ...):
        # 每行是一个请求，每列是一个 token 位置
        # 值是该 token 的 KV 在物理 pool 中的 slot index
        self.req_to_token = torch.zeros((size+1, max_context_len), dtype=torch.int32, device=device)
        ......

    def write(self, indices, values):
        self.req_to_token[indices] = values  # 直接写 GPU tensor

# 例如请求 3 的第 5 个 token 的 KV 存在 slot 42：
req_to_token[3][5] = 42
```

## 与 vLLM 对比

|  | vLLM | SGLang |
| --- | --- | --- |
| 管理粒度 | Block（固定大小，如 16 tokens） | Token slot（page_size=1 时逐 token 管理） |
| 物理存储 | 预分配固定大小 block，block 内连续 | 一个大 flat tensor，slot 可离散 |
| 间接寻址 | block table: req → [block_ids]，kernel 按 block 跳 | 页表: req_to_token[req][pos] → slot，kernel 逐 token 跳 |
| 前缀匹配粒度 | 只能 block 边界 | 任意 token 位置（通过 split node） |
| 去重 | 不能改写 block table，产生 duplicated blocks | 可以改写页表，指向 canonical indices |

说明：「canonical indices」= 从 radix 树上 `match_prefix `返回的 slot 索引，代表这段 KV 数据的唯一权威位置。
