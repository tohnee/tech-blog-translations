**摘要**：FLOPs（Floating Point Operations）是衡量模型计算量的理论指标，但实际推理中 FLOPs 低的模型不一定快，一个 FLOPs 减半的模型，实测延迟可能仅降低 20%。推理延迟取决于计算量与硬件的匹配程度，内存带宽、并行度和调度开销对延迟的影响可能远超 FLOPs 本身。本文从两个层次介绍推理计算优化：**算子级优化**通过内存布局调整、算子融合、GEMM 分块和 IO 感知算法实现单算子的高效执行；**图级优化**通过推理编译器系统性地消除跨算子冗余并自动生成硬件专用代码。FlashAttention 是算子级 IO 感知设计的代表，TensorRT 与 TVM 代表图级编译的两条路线（专有硬件深度优化 vs 跨平台自动调度）；算子级与图级优化并不互斥，前沿方向正是让图级编译器学会自动发现算子级专家手工设计的优化模式。

**关键词**：推理优化，算子融合，FlashAttention，推理编译器，Roofline 模型，IO 感知算法

## 1. 引言

评估模型效率时，FLOPs（浮点运算次数）是最常用的指标。但在实测中，一个 FLOPs 减半的模型其推理延迟可能仅降低 20%，甚至几乎不变。原因在于：FLOPs 只统计计算量，而实际推理时间由计算、内存访问和调度开销共同决定——当内存访问成为瓶颈时，即使计算量减少，处理器大量时间处于等待数据的状态，FLOPs 减少无法转化为速度提升。

这一现象将推理优化的重点从**减少计算量**（第 1–8 篇讨论的模型压缩与动态网络）转向**提高计算效率**——在相同计算量下通过更好利用硬件特性缩短延迟。推理优化分为两个层次：

- **算子级优化**：聚焦单个算子在特定硬件上的最优实现，核心是最大化数据复用、最小化显存读写；
- **图级优化**：在完整计算图层面消除跨算子冗余，核心是在不改变模型语义的前提下生成最高效的机器代码。

现有方法分为以下三种：

- **面向内存受限算子的融合优化**：Conv + BN+ ReLU 的推理时融合是 CNN 部署的标准做法，消除中间张量的显存读写，加速比约 1.2–2×；
- **面向 Transformer 的 IO 感知优化**：FlashAttention 系列通过分块计算避免 $O(N^2)$ 注意力矩阵的中间存储，长序列推理中加速注意力计算 2–4×，已是 GPT、LLaMA 等模型推理栈的标配组件；
- **面向自动部署的推理编译器**：TensorRT 在 NVIDIA GPU 上提供端到端编译；TVM 通过搜索自动生成任意硬件的调度代码，使算子优化不再依赖手写 CUDA Kernel。

## 2. 理解性能瓶颈

### 2.1 Roofline 模型

Roofline 模型（Williams et al., 2009）是一种可视化性能分析方法，用于回答一个基本问题：一个算子在给定硬件上运行时，瓶颈是计算能力还是内存带宽？它通过将实际性能（FLOPs/s）与算术强度（FLOPs/Byte）的关系绘制为一张图，直观定位瓶颈类型。

**核心思想**：算子的实际性能受两重硬上限约束——硬件峰值算力和内存带宽，较低者即为瓶颈。

算术强度（Arithmetic Intensity）定义为：

$$ \text{Arithmetic Intensity} = \frac{\text{FLOPs}}{\text{Bytes Accessed}} $$

即每从内存读取一字节数据，能在这些数据上执行多少次浮点运算，单位为 FLOPs/Byte。在 Roofline 图上，横轴为算术强度，纵轴为可达到的性能（FLOPs/s）：峰值算力是一条水平线（Compute Roof），内存带宽是一条斜率为带宽值的斜线（Memory Roof），斜线与水平线的交点称为**拐点**——该点对应的算术强度是区分计算受限与内存受限的分界。算子的实际性能不可能超过两条线中的较低者。

**示例**：以 A100 GPU（峰值算力 312 TFLOPS FP16，内存带宽 2.0 TB/s）为例，拐点算术强度为 $312 \times 10^{12} / 2.0 \times 10^{12} \approx 156$ FLOPs/Byte。高于此值的算子是计算受限，低于此值的算子是内存受限。

- **矩阵乘法**（$M=N=K=4096$）：算术强度约为 2048 FLOPs/Byte，高于拐点，落在计算受限区域（Compute Roof 上方），性能取决于 Tensor Core 利用率。
- **逐元素 ReLU**：读写各一次，每个元素执行 1 次 FLOP，算术强度约为 $1/(2\times2)=0.25$ FLOPs/Byte，远低于拐点，落在内存受限区域的极左端，实际性能远低于峰值算力。
- **深度卷积**（$3\times3$，通道数 512）：算术强度约为 56 FLOPs/Byte，低于拐点但高于 ReLU，处于内存受限区域或两区域的过渡带。

通过对比可以发展：ReLU 的 FLOPs 虽然极少，执行时间却可能远超预期——瓶颈不是**算**而是**搬**。优化方向应是减少内存读写或将其与相邻算子融合，而非进一步降低**计算量**。

### 2.2 内存层次结构与访问代价

GPU 的内存体系呈金字塔结构，越靠近计算单元，容量越小但带宽越高，以A100为例：

- **寄存器**：每个 SM（Streaming Multiprocessor）有 65536 个 32-bit 寄存器，延迟约 1 个时钟周期；
- **L1 Cache / 共享内存**：每个 SM 有 192 KB 池，延迟约 30 个时钟周期，可被同一线程块内所有线程访问，是数据复用的关键；
- **L2 Cache**：芯片全局 40 MB，延迟约 200 个时钟周期；
- **全局内存（DRAM/HBM）**：80 GB HBM（High Bandwidth Memory）2e，带宽 2.0 TB/s，延迟高达约 600–800 个时钟周期。

一次全局内存访问的延迟可执行数百次浮点运算，这正是算术强度低的算子必然受限于内存的原因——每个浮点运算都需从 DRAM 加载数据，计算单元大部分时间处于空闲等待。

片上内存（SRAM，即 L1 Cache 与共享内存的统称）是性能优化的核心资源。最大化数据在片上内存中的复用、减少全局内存读写次数，是高性能 Kernel 设计的根本原则。

### 2.3 硬件并行度与利用率

GPU 的吞吐量来源于大量线程同时执行。NVIDIA GPU 以 Warp（32 个线程）为调度单位，一个 SM 同时驻留多个 Warp——当某个 Warp 等待内存数据时，SM 立即切换到另一就绪 Warp 执行计算，以此隐藏内存延迟。这要求 SM 中有足够的活跃 Warp，否则计算单元将无可执行任务而空转。

小 batch 或小通道算子是并行度不足的重灾区。以 batch size = 1 推理、全连接层输出通道为 4 为例，每个 Warp 处理 32 个通道，只有 4⁄32 = 12.5% 的线程在有效工作，SM 利用率极低。

算子碎片化——计算图被分解为过多细碎的小算子——同样降低效率：每个小算子启动一次 GPU Kernel，每次启动有约 5–10 μs 的调度开销，算子之间还需在全局内存中写入读取中间结果。将多个小算子合并为一个 Kernel（算子融合）既能减少调度开销，又能消除中间内存读写。

### 2.4 常见认知误区总结

**FLOPs 减半 ≠ 速度翻倍**：只有在计算受限的前提下，FLOPs 减少才直接转化为延迟降低；在内存受限区域，减少 FLOPs 对延迟几乎无影响。

**参数量小 ≠ 推理内存小**：推理显存由模型权重、激活值、推理框架临时缓冲区三部分构成。大模型推理的激活值显存通常超过权重显存，参数量的节省可能被激活值开销完全淹没。

**理论峰值算力 vs 实测有效算力**：硬件标称峰值 TFLOPS 是在最优条件下测得的。实际场景中，受内存带宽、并行度不足等因素影响，有效算力通常只是峰值的 30%–60%，内存受限算子则更低。

## 3. 算子级优化

**核心问题**：单个算子如何在硬件上实现最高效的执行？

### 3.1 内存布局优化

张量在内存中的物理排布方式决定了访问模式。NCHW 格式（batch-通道-高-宽）中同一通道的空间位置相邻，适合按通道独立计算的算子；NHWC 格式（batch-高-宽-通道）中同一空间位置的不同通道相邻，适合需跨通道计算的算子（如 1×1 卷积、全连接层）。GPU 上 NHWC 通常优于 NCHW——卷积需累加所有通道，NHWC 的连续通道访问提升了缓存命中率；CPU 在某些场景 NCHW 更优，便于 SIMD 向量化。

张量转置的代价常被低估：一次转置相当于读取全部数据再按新顺序写回，对大型特征图可能耗时数毫秒，与整个推理延迟相当。避免方式是在模型设计阶段统一内存布局，或将转置融入前一算子的输出计算中。

### 3.2 高效矩阵乘法

矩阵乘法（GEMM, General Matrix Multiply）是深度网络最核心的基础操作——卷积可转化为 GEMM，注意力中的 $QK^\top$ 和加权求和也是 GEMM，高效 GEMM 实现是算子优化的基石。

**GEMM 分块（Tiling）** 将大矩阵乘法划分为可放入共享内存的子块。一个 $N\times N$ 矩阵乘法共需从全局内存读取 $O(N^3)$ 个元素；分块策略将输入划分为大小为 $T\times T$ 的子块，每次加载到共享内存并复用 $T$ 次，总读取量降至 $O(N^3/T)$。

现代 GPU 的 Tensor Core（张量核心）专为矩阵乘法加速设计——A100 的每个 Tensor Core 每时钟周期可执行一个 $4\times4\times4$ 的矩阵乘加运算。高效 GEMM 实现需将分块策略与 Tensor Core 的矩阵尺寸对齐，确保数据以其期望的布局进入。

**im2col**（image to column）是卷积转化为 GEMM 的标准方法：将每个卷积窗口展开为矩阵的一列，卷积核展开为一行，代价是输入张量膨胀 $K^2$ 倍（$K$ 为卷积核尺寸），内存占用增加。

**Winograd 卷积**（Lavin & Gray, 2016）通过数学变换减少乘法次数。对 $3\times3$ 卷积、步长 1，$F(2\times2,3\times3)$ 算法将 36 次乘法降至 16 次，理论加速比 2.25×。变换需额外加减法，数值精度受变换矩阵条件数影响，FP16 下大尺寸 Winograd（如 $F(4\times4,3\times3)$）可能出现精度退化，实际应用通常限制在这两种配置。

### 3.3 算子融合（Kernel Fusion）

深度网络的推理计算图通常包含几十到数百个小算子，每个算子作为独立 GPU Kernel 执行：读取输入、执行计算、写回全局内存。当两个连续算子的计算量都很小时（如 Conv + ReLU），内存读写时间远超计算时间，中间张量存储成为纯开销。

**具体实现**：以 Conv + BN + ReLU 为例，BN 推理时的标准化公式为 $\hat{x} = \gamma \cdot (x - \mu)/\sqrt{\sigma^2 + \epsilon} + \beta$，其中 $\mu, \sigma^2, \gamma, \beta$ 均为训练后固定的常数。将 Conv 的输出 $x = W \cdot a + b$ 代入 BN 公式，可展开为：

$$ \hat{x} = \frac{\gamma}{\sqrt{\sigma^2 + \epsilon}} \cdot (W \cdot a + b - \mu) + \beta = W' \cdot a + b' $$

其中 $W' = \gamma W / \sqrt{\sigma^2 + \epsilon}$，$b' = \gamma (b - \mu) / \sqrt{\sigma^2 + \epsilon} + \beta$。即 BN 在推理时完全等价于对 Conv 的权重和偏置做一次线性变换，数学上可无损吸收进 Conv 的参数中。吸收后的卷积输出直接经过 ReLU 截断，三者合并为单个 Kernel：从输入 $a$ 到 ReLU 输出只需一次全局内存读和一次写，中间结果 $W \cdot a + b$ 和 $\hat{x}$ 仅存在于寄存器或共享内存中。

**收益量化**：在 ResNet-50 推理中，这一融合通常带来 1.3–1.8× 的延迟降低，收益完全来自内存带宽压力的缓解而非计算量的减少。

融合范围的上限由片上内存容量决定。若融合算子过多，中间数据超过共享内存或寄存器容量，则**溢出**到全局内存——不仅失去融合收益，还可能因不规整的访问模式导致性能反降。因此实践中融合通常限定在内存需求可预测的算子组内。

第 2 篇讨论的结构重参数化在训练时使用多分支结构，推理时等价合并为单个卷积，与算子融合理念一致。区别在于结构重参数化是数学等价变换，算子融合是工程实现层面的合并。

### 3.4 FlashAttention：IO 感知的注意力实现（Dao et al., 2022）

FlashAttention 方法在本系列第 3 篇有更详细的介绍。本节从推理计算优化角度，重点分析其 IO 感知设计。

### 3.4.1 问题分析

标准注意力机制的计算公式为：

$$ \text{Attention}(Q, K, V) = \text{softmax}\!\left(\frac{QK^\top}{\sqrt{d}}\right) V $$

传统实现按序执行：计算 $\mathbf{S}=QK^\top$（形状 $N\times N$，$N$ 为序列长度）并写回全局内存；读取 $\mathbf{S}$ 计算 $\mathbf{P}=\text{softmax}(\mathbf{S})$ 并写回；读取 $\mathbf{P}$ 和 $V$ 计算 $\mathbf{O}=\mathbf{P}V$ 并写回。

这一过程在全局内存中存储了完整的 $N\times N$ 注意力矩阵。对序列长度 $N=2048$、head 维度 $d=64$ 的单头注意力（FP16），$QK^\top$ 与 softmax 输出各占 16 MB，扩展到多头与批量后可能占据数 GB 显存。更重要的是，按 2.1 节的算术强度框架衡量，标准注意力的算术强度约为 $O(1)$，是极端的内存受限算子。

### 3.4.2 设计思路

FlashAttention（Dao et al., 2022）的核心洞察是：$O(N^2)$ 的内存瓶颈并非算法本身的必然属性，而是传统实现方式造成的。Softmax 可以分块计算——将序列划分为小块，逐块计算局部 softmax，通过维护统计量（最大值与指数和）跨块修正结果，最终在不存储完整 $\mathbf{S}$、$\mathbf{P}$ 矩阵的情况下得到精确的 $\mathbf{O}$。

这一思路利用了 GPU 的片上 SRAM：容量虽小（A100 每 SM 192 KB），带宽却可达 19 TB/s，远超 HBM 的 2.0 TB/s。将计算组织为使数据尽可能留在 SRAM 中，可大幅减少对 HBM 的读写，这正是 FlashAttention 名字的由来。

### 3.4.3 原理与结构

FlashAttention 的 tiling 策略将 $Q$、$K$、$V$ 划分为块，确保每个块只需从 HBM 加载一次数据，中间结果累积在 SRAM 中：

1. **外循环遍历 Q 块**：将一个 Q 块加载到 SRAM；
2. **内循环遍历 K、V 块**：依次加载 K、V 块，在 SRAM 中计算 $\mathbf{S}_{ij}=Q_iK_j^\top$，计算局部 softmax，更新输出 $\mathbf{O}_i$；
3. **在线 softmax 修正**：若新加载 K 块的最大值大于当前记录的全局最大值，则修正之前所有块的 softmax 权重，确保最终结果与完整计算等价。

这一过程完全消除了对完整 $\mathbf{S}$、$\mathbf{P}$ 矩阵的存储需求。计算量保持不变——所有 FLOPs 都被保留，只是内存访问被最小化。FlashAttention 是精确算法而非近似，输出与标准注意力在数值上完全等价（仅有舍入误差差异）。

### 3.4.4 数学推导：HBM 访问复杂度

设 SRAM 容量为 $M$（以元素数计），需同时容纳 Q、K、V、O 四个缓冲块，每块可用容量近似为 $M/4$。每行数据维度为 $d$，块大小约为：

$$ B_c \approx \frac{M}{4d} $$

外循环遍历 $N/B_c$ 个 Q 块，内循环对每个 Q 块遍历全部 $N/B_c$ 个 K/V 块，每次加载 K、V 块共 $O(B_cd)$ 个元素。总 HBM 访问量为：

$$ \text{IO}_{\text{Flash}} \approx \left(\frac{N}{B_c}\right)^2 \times B_c d = \frac{N^2 d}{B_c} = \frac{4N^2d^2}{M} $$

即 $\text{IO}_{\text{Flash}}=\Theta(N^2d^2/M)$。标准注意力需完整读写 $\mathbf{S}$、$\mathbf{P}$ 两个 $N\times N$ 矩阵，HBM 访问量为 $\Theta(N^2)$，两者比值为：

$$ \frac{\text{IO}_{\text{standard}}}{\text{IO}_{\text{Flash}}} \approx \frac{M}{4d^2} $$

**数值验证**：以 A100 单 SM 的 192 KB SRAM（FP16 下 $M\approx98304$ 个元素）、$d=64$ 代入：$B_c\approx98304/(4\times64)\approx384$；IO 降低比例约为 $98304/(4\times64^2)\approx6$。即 FlashAttention 的 HBM 访问量约为标准实现的 $1/6$，实际比值会随 SRAM 容量、head 维度等变化，量级通常在几倍到十余倍之间。

> 💡 这一推导表明：FlashAttention 降低的是 HBM 访问的**常数因子**（$d^2/M$），而非对序列长度 $N$ 的**渐近阶数**——两者的 HBM 访问量都是 $\Theta(N^2)$。改变 $N$ 的渐近复杂度需要改变注意力的数学形式（如线性注意力），FlashAttention 与线性注意力解决的是不同层面的问题。

### 3.4.5 优缺点与适用性

**优势**：FlashAttention 是精确算法而非近似，不引入精度损失，可直接替换标准实现而无需重新训练；IO 感知设计不依赖特定模型结构或任务，已成为 GPT、LLaMA 等主流模型推理与训练栈的标配组件。

**局限**：FlashAttention 优化内存访问而非计算量，在计算已受限的场景（如极短序列）下加速有限。分块参数需根据 SRAM 容量与 head 维度调优，跨硬件代际需重新适配。工程实现涉及底层 CUDA 编程与在线 softmax 数值稳定性处理，无法像图级优化那样自动获得。后续 FlashAttention-2（Dao, 2023）与 FlashAttention-3（Shah et al., 2024）分别针对 warp 并行策略与 H100 异步流水线做专项优化，这一持续迭代表明 IO 感知设计的收益高度依赖具体硬件特性。

**适用场景**：长序列 Transformer 推理与训练的标准配置。序列较短或算术强度足够高时，FlashAttention 的差距缩小，此时优化重心应转向计算受限层面的手段。

### 3.5 算子融合与 FlashAttention 的协同

FlashAttention 可视为一种极致的**注意力算子融合**：将 $QK^\top$、softmax、乘以 $V$ 三步融合为单个 Kernel，使中间数据不离开 SRAM。但它仅融合注意力内部的子步骤——完整 Transformer 层中，注意力输出后通常紧跟线性投影和残差连接，将这些步骤进一步融合、消除全局内存往返，是当前推理优化的前沿方向之一。

### 3.6 优缺点分析与综合比较

算子级优化的共同优点在于直接映射到硬件执行，加速效果确定且可量化；除 Winograd 可能引入的舍入误差外均不改变计算语义；多项优化累积后，端到端延迟通常可降低 30%–50%。局限在于高度硬件相关——为一种 GPU 调优的 Kernel 换代甚至换架构后往往需要重写；手写高性能 Kernel 依赖深厚的底层编程知识；极致优化通常对输入 Shape 敏感。

**GEMM 优化 vs Winograd**：GEMM 分块与 Tensor Core 适配是通用基础，适用于所有矩阵乘法场景；Winograd 针对 $3\times3$ 卷积提供额外加速，但适用范围窄，且大尺寸变体的数值精度可能不满足严格需求，选择取决于卷积核尺寸和精度要求。

**算子融合的收益边界**：收益来自消除中间全局内存读写，对算术强度低的**轻量级**算子最明显；融合的算子本身是计算量大的 GEMM 时，内存读写占比低，收益有限；融合范围过大还可能导致寄存器压力过高，反而降低 SM 占用率。

**适用场景**：计算受限算子优先 GEMM 优化与 Tensor Core 适配；内存受限算子优先融合；Transformer 长序列场景标配 FlashAttention；卷积密集的 CNN 模型可评估引入 Winograd。

## 4. 图级优化与推理编译

**核心问题**：如何在计算图层面系统性消除冗余，并自动生成针对特定硬件的高效代码？

### 4.1 计算图优化基础

推理引擎加载模型后，首先对计算图进行一系列与硬件无关的图级优化：

- **常量折叠**：仅依赖权重的子图（如 BatchNorm 的均值方差运算、不依赖输入的 Reshape）可在推理前预先计算，替换为常量节点；
- **死代码消除**：移除不影响输出的节点和分支，如训练时的辅助损失路径、未使用的输出头；
- **公共子表达式消除**：同一计算出现在图的不同分支中时，只需计算一次并复用结果；
- **图级算子融合**：不同于 3.3 节的手动融合，推理编译器自动识别可融合模式（Conv+BN+ReLU、矩阵乘法+Bias+GeLU 等）并生成融合 Kernel，覆盖范围远超人工设计。

### 4.2 TensorRT（NVIDIA, 2024）

### 4.2.1 问题分析

一个典型深度网络推理计算图包含几十到数百个算子。按 2.3 节的估算，每个未融合算子启动一次 GPU Kernel，每次约 5–10 μs 调度开销；对含 200 个算子的计算图，仅调度开销累计即可达约 1.5 ms。若目标延迟预算为 10 ms，调度开销可能占整体延迟的 15% 左右，还不包括未融合算子间的中间张量读写代价。手工识别融合模式、为每层搜索最优 Kernel、并针对量化精度做误差校准，依赖大量工程人力，且需针对每个新模型结构重新进行。

### 4.2.2 设计思路

若图级优化模式（常量折叠、死代码消除、层融合）与硬件专属的 Kernel 选择能够自动化完成，而非依赖工程师逐个模型手工调优，就能大幅降低部署成本。这要求编译器同时具备两方面能力：

- 理解计算图语义以识别可融合模式；
- 掌握目标硬件底层特性，从预先构建的 Kernel 库中为每个算子自动挑选实测最优的实现。

### 4.2.3 原理与结构

TensorRT 的工作流程分为四个阶段。

**阶段一：导入模型**。TensorRT 以 ONNX 为模型交换格式，通过 ONNX 解析器将 protobuf 表示的图结构转换为 TensorRT 内部网络定义（INetworkDefinition）。此处涉及两个工程细节：

- 一是 ONNX 算子集版本的兼容性——较早的 ONNX 中某些算子（如动态控制流）TensorRT 不支持，需退回到 CPU 作为回退；
- 二是输入的静态 vs 动态维度——对于可变 batch size 的情况，ONNX 中 batch 维度标注为 -1 表示动态，TensorRT 在编译时需设置优化配置中显式指定形状范围（最小、最优、最大），以生成覆盖该范围的优化引擎。

**阶段二：图解析与优化**。转换后的图结构经编译器执行一系列与硬件无关的图级优化，主要包括：

- 常量折叠：计算图中所有输入均为常量（不受输入数据影响）的节点在编译期预先求值——典型例子是 BN 推理中 $\gamma, \beta, \mu, \sigma$ 四个统计量卷积权重合并后，融合 Conv 的过程并不依赖输入数据，可以在编译期完成；
- 死代码消除：输出从未被使用的节点（如训练时引入但推理时无关的 loss 分支）从图中移除，减少不必要的计算；
- 层融合（Layer Fusion）：将连续的窄带宽算子合并为单个 Kernel（如 Conv + Bias + ReLU 融合为单个 CBR Kernel，Conv + BN + Add + ReLU 融合为 CBR + Add 等），消除中间张量在全局内存中的读写消耗。TensorRT 维护一个可匹配的算子模式列表，编译器遍历图时将匹配到的子图替换为融合后的单个节点。

**阶段三：Kernel 自动选择（Auto-tuning）**。优化后的图由若干融合节点组成，每个节点（如一个 CBR Kernel）对应多种候选实现，候选间在分块大小（tile size）、向量化宽度（vector length）、流水线深度等维度上排列组合。TensorRT 在编译时针对当前模型的固定输入 Shape 与目标 GPU 型号，对每个节点逐一运行所有候选 Kernel 并测量延迟，选择实测最快的实现。这一步的编译时间与候选 Kernel 数量成正比，通常为数分钟至数十分钟不等；选出的最佳 Kernel 组合被记录为可执行计划（execution plan），直接包含运行时的调度信息。

**阶段四：生成优化引擎**。选定所有 Kernel 后，TensorRT 将计划序列化为二进制文件（.trt 或 .plan），推理时反序列化即可执行，无需重新解析图结构或重新优化。该文件绑定生成时所用的 GPU 型号（如 A100-80GB-PCIE），迁移到不同型号（如 V100）或不同显存容量的 GPU 时需重新编译。序列化格式包含权重张量的二进制副本、各节点的 Kernel 句柄与启动参数、以及执行流上的依赖顺序，引擎运行时直接依次启动各 Kernel，不包含图结构信息。

![](https://pic2.zhimg.com/v2-8edf7db5516b7c60d2c9a109a525aae7_r.jpg)

**图 3：TensorRT 编译流程——模型导入后依次经过图解析优化、Kernel 自动选择与精度校准，最终生成绑定到特定 GPU 型号的序列化推理引擎**

### 4.2.4 优缺点与适用性

**优势**，TensorRT 的图优化与 Kernel 自动选择将大量手工调优工作自动化，且优化深度与 NVIDIA 硬件紧密耦合，在同代 GPU 上的峰值性能通常难以被通用编译器超越。

**局限**，生成的推理引擎通常绑定特定 GPU 型号甚至驱动版本，跨平台能力接近于零；Auto-tuning 编译时间从数分钟到数十分钟不等，在研发迭代阶段会拖慢开发节奏；对动态 Shape 的支持虽逐步改善，优化深度仍不及固定 Shape 场景。

该方法适合模型结构固定、目标硬件明确为 NVIDIA GPU、追求单卡极致性能的生产部署；需跨平台部署或模型频繁迭代时，硬件绑定与编译耗时会成为明显负担。

### 4.3 TVM（Chen et al., 2018）

### 4.3.1 问题分析

TensorRT 式方案依赖 NVIDIA 预先为其硬件手工实现并维护的 Kernel 库，这一模式在覆盖多种硬件后端时面临组合爆炸：深度学习算子类型有数十种，部署目标涵盖 GPU、CPU、ARM、FPGA 等差异巨大的架构，输入 Shape 又存在大量组合。即便保守估计数十种算子、十余种硬件、十余种典型 Shape，需手工实现调优的 Kernel 组合也可轻易达到数千量级，而每个高性能 Kernel 的调优通常需要资深工程师数天到数周——这一规模的人力投入，对除少数硬件厂商外的多数团队并不现实。

### 4.3.2 设计思路

问题根源在于算子的**做什么**（计算逻辑）与**怎么做**（如何映射到具体硬件的循环结构、内存访问顺序）被捆绑在同一份手工代码中，导致每换硬件都要重新实现。若将两者解耦——用硬件无关的方式描述计算逻辑，再用独立的**调度**描述如何映射到具体硬件——就可复用同一计算逻辑，仅需为不同硬件搜索不同调度方案。这一**计算与调度分离**的思路，使调度搜索本身可以被自动化。

### 4.3.3 原理与结构

TVM 将算子的**计算逻辑**与**调度原语**明确分离，二者分属不同抽象层次。

**计算逻辑**描述输出张量各元素如何由输入张量通过数学运算得到，与硬件无关。以两个一维向量的加法为例，其计算逻辑可表达为 **对输出向量的每个索引 i，令 output[i] = input_a[i] + input_b[i]**。该描述只声明了计算结果与输入之间的关系，不涉及循环展开的份数、数据的排列方式或内存访问的顺序。

**调度原语**描述如何将上述计算映射到具体硬件——包括循环分块（tiling，将大循环切分为适合缓存容纳的小块）、循环重排（reordering，改变嵌套循环的执行顺序以改善空间局部性）、向量化（将标量操作转为 SIMD 指令）、内存层级管理（指定中间数据在寄存器/共享内存/全局内存间的存放位置）等。同一份计算逻辑可对应多种调度，这些调度在数学上行为等价（输出相同），但在目标硬件上的实际性能可能相差数倍乃至数十倍。

TVM 的核心贡献在于为调度原语提供了一套类型系统，使调度变换可以被程序化地表达和组合。例如，对一个 2D 卷积的 `Conv2D` 计算，TVM 的调度代码可依次指定 tiling 宽度、重排循环轴、将内层循环向量化——每一步调用一个调度 API，最终生成的底层 CUDA/OpenCL 代码由 TVM 编译器自动完成，无需人工编写。

早期 TVM 依赖模板化的手工搜索：由工程师为每种算子类型编写调度的搜索模板，设定分块选项的取值范围，搜索空间由此确定。**Ansor**（Zheng et al., 2020）将这一过程进一步自动化，其流程分为三步。

- **程序生成**：Ansor 通过程序生成算法自动构造候选调度，而非依赖手工模板。它从计算逻辑的低层级中间表示出发，随机组合一系列调度变换原语（分块、重排、向量化等），生成大量候选。
- **代价模型筛选**：构建一个轻量级机器学习模型（梯度提升树或 MLP），以候选调度的特征（循环层级数、分块大小、内存访问模式等）为输入，预测其在真实硬件上的性能。对所有候选快速打分排序后，将预估最快的部分候选浮出。
- **硬件实测与迭代**：将浮出的候选在真实 GPU/CPU 上运行并记录延迟。实测结果返馈给代价模型作为训练样本，更新模型权重；更新后的模型再用于下一轮筛选。经数十至数百轮迭代后，代价模型的预测精度逐步提高，搜索到高性能调度所需的时间随之缩短。

这一自动化流程的代价是编译时间上升——Ansor 的搜索过程通常需要数十分钟到数小时（取决于搜索空间大小），远超 TensorRT 的量级，但高度特化的搜索可能发掘出与手工调优持平甚至更优的 Kernel。

**图 4：TVM 计算-调度分离与自动搜索——同一份硬件无关的计算逻辑可生成大量候选调度，代价模型筛选后仅对少量候选做真实硬件测量，测量结果反过来迭代优化代价模型**

### 4.3.4 优缺点与适用性

**优势**，计算与调度分离使同一套算子逻辑可复用于任意硬件后端，只需为新硬件补充调度搜索的成本模型，不必重新实现算子本身，这是 TVM 跨平台能力的根本来源；自动化调度搜索大幅降低了对资深硬件工程师的依赖。

**局限**，自动搜索仍需在真实硬件上做一定数量实测，大模型或复杂算子的搜索时间可能长达数小时；在特定硬件（尤其 NVIDIA GPU）上，自动搜索得到的性能通常略低于 TensorRT 这类深度定制方案（经验上有 5%–15% 差距）；对动态 Shape 的支持同样有限。

该方法适合需覆盖多种硬件后端、且团队不具备专用 Kernel 维护能力的场景；部署目标单一为 NVIDIA GPU 时，TensorRT 通常仍是更直接的选择。

### 4.4 其他代表框架

**XLA**（Accelerated Linear Algebra）是 Google 的编译优化后端，用于 JAX 和 TensorFlow。它将计算图转换为 HLO 中间表示，在 HLO 层面进行全图优化和融合，再编译为特定硬件的机器代码。其优势在于与 JAX/TensorFlow 生态的深度集成，可将整个函数编译为单个 Kernel，但动态 Shape 支持有限；这一思路与 TVM 的计算图 IR 有相通之处，区别在于 XLA 更聚焦于与特定框架生态的深度绑定，而非 TVM 式的通用跨平台目标。

**MLC-LLM**（2023）将 TVM 的跨平台编译能力聚焦于大语言模型部署：将 LLaMA、GPT-NeoX 等模型编译为统一中间表示，再生成 GPU、CPU、移动端和 WebGPU 等多平台的原生代码，使同一模型无需修改即可从服务器部署到手机 NPU——是 TVM 计算-调度分离框架在大模型时代的一次垂直领域应用。

### 4.5 优缺点分析与综合比较

自动化图级优化的共同优点在于省去手写 Kernel 的人力成本，跨算子协同优化能发现人工难以覆盖的机会；TVM、MLC-LLM 一类框架还额外提供**一次编译、多硬件部署**的能力。局限在于编译时间偏长（尤其含 Auto-tuning 的流程）；动态 Shape 支持普遍有限；编译器内部决策相对黑盒，性能不达预期时定位失效环节较为困难。

**TensorRT vs TVM**：两者代表图级优化的两种取舍——TensorRT 用硬件绑定换取单一硬件上的极致性能，TVM 用自动化跨硬件调度搜索换取通用性，但特定硬件上的峰值性能通常略逊于专有方案。仅在 NVIDIA GPU 上部署优先 TensorRT，需跨平台或非主流加速器部署优先 TVM 一类框架。

**静态图 vs 动态图**：推理编译的前提是计算图运行时保持不变。PyTorch 的动态图执行模式不直接兼容图级编译——图在每次前向传播中动态构建，编译器没有机会提前优化。TorchScript 和 torch.compile 通过 JIT 追踪或子图编译引入了静态图优化，但灵活性和优化深度仍不及原生静态图框架。

**适用场景**：模型结构与输入 Shape 固定的生产环境首选编译优化；需跨平台部署或缺乏专用调优能力时优先 TVM 一类框架；研究探索阶段优先动态图框架配合 torch.compile 等轻量级加速。

## 5. 小结

### 5.1 综合对比表

下表对比 FlashAttention、TensorRT、TVM 三种代表方法及算子融合、Winograd 两类通用技术在优化层次、复杂度收益、精度损失与适用场景上的差异。

| 方法 | 优化层次 | 复杂度/收益 | 精度损失 | 典型应用场景 |
| --- | --- | --- | --- | --- |
| 算子融合（通用） | 算子级 | 消除中间 HBM 读写，端到端约 1.2–1.8× | 无 | 通用 CNN/Transformer |
| Winograd 3\times3 | 算子级 | 乘法次数降至约 4/9（36→16） | 大尺寸变体有精度风险 | 小卷积核密集推理 |
| FlashAttention | 算子级 | HBM 访问量降至 \Theta(N^2d^2/M)，常数因子约 M/(4d^2) | 无（精确算法） | Transformer 长序列 |
| TensorRT | 图级 | 全图编译，端到端约 1.5–3× | 视精度模式而定（INT8 有损） | GPU 服务端，硬件固定 |
| TVM | 图级 | 自动调度搜索，跨硬件复用同一算子逻辑 | 无（不改变计算本身） | 多硬件后端部署 |

### 5.2 局限性汇总

下表汇总各类方法在实际应用中的主要局限。

| 方法类别 | 主要局限 |
| --- | --- |
| 算子级手工优化（GEMM 分块、Winograd、融合） | 高度硬件相关，为特定 GPU 代际调优的 Kernel 迁移到新硬件通常需要重新调优；融合范围过大会导致寄存器压力过高，反而降低 SM 占用率 |
| FlashAttention | 降低的是 HBM 访问的常数因子而非渐近阶数，对短序列或计算已受限的场景加速有限；分块参数需按 SRAM 容量与 head 维度调优，跨硬件代际需重新适配 |
| TensorRT | 生成的推理引擎绑定特定 GPU 型号与驱动版本，跨平台能力接近零；Auto-tuning 编译耗时数分钟到数十分钟，拖慢频繁迭代场景的开发节奏 |
| TVM/自动调度编译器 | 特定硬件上的峰值性能通常落后专有方案 5%–15%；动态 Shape 支持有限，复杂算子的调度搜索仍可能耗时数小时 |
| 跨类别共性 | 理论上的复杂度或访问量降低，受限于动态 Shape、调度开销、硬件代际差异等因素，未必能完全兑现为实测延迟改善 |

### 5.3 技术演进规律

推理优化领域的早期焦点与前 8 篇讨论的模型压缩、动态网络高度重合——研究者默认**更少的 FLOPs 意味着更快的推理**，几乎所有工作都以降低计算量为直接目标。Roofline 模型（Williams et al., 2009）的提出与普及，标志着这一假设第一次被系统性地证伪：算术强度低的算子（如逐元素操作、归一化）即使 FLOPs 极少，也可能因内存带宽受限而成为实际瓶颈，**减少计算量**与**降低延迟**由此被明确拆分为两个不完全重合的目标。

算子级优化正是对这一认识的直接回应。算子融合率先证明，不改变计算量、仅消除中间张量的内存读写，也能带来实测可见的加速；FlashAttention 将这一思路推向了更精细的层面——它证明了即使是理论上已经最优 FLOPs 的精确算法（标准注意力），其内存访问模式仍有大量可压缩的冗余，且这种压缩不需要以精度为代价。这一认识与算子融合共享同一个底层逻辑：计算量不是唯一的优化目标，IO 模式同样值得被当作一等公民对待。

图级优化的发展路径体现了另一条脉络——从人工到自动化。TensorRT 代表**用硬件深度绑定换取极致性能**的路线，其 Kernel 库与 Auto-tuning 仍依赖 NVIDIA 预先为自家硬件投入的大量工程资源；TVM 与 Ansor 代表**用计算-调度分离与自动搜索换取通用性**的路线，将原本依赖资深工程师手工调优的过程转化为可自动执行的搜索问题。这条脉络与第 4 篇结构化剪枝、第 8 篇 Once-for-All 等方法中**从人工设计走向自动搜索**的演进逻辑高度相似，说明**自动化**是压缩与优化领域跨越多个技术层面的共同趋势，而非某一具体技术路线独有的特征。

当前的开放问题集中在两个方向。

- 其一，算子级与图级优化的边界正在模糊——3.5 节提到的将 FlashAttention 之外的相邻算子进一步融合正是这一趋势的体现，图级编译器开始尝试自动发现并生成过去只能由专家手写的 IO 感知 Kernel。
- 其二，大语言模型推理的特殊性（自回归生成、KV Cache 管理、极致的延迟敏感度）正在催生专门面向这一场景的编译栈（如 MLC-LLM），这类工具能否像 TensorRT 之于 CNN 时代那样成为大模型推理的事实标准，仍是一个开放的工程问题。 可以确定的是，**先用 Roofline 一类工具定位真实瓶颈，再针对瓶颈类型选择计算受限或内存受限的对应优化手段，最后通过图级编译完成硬件适配**这一先诊断、后开药的方法论，已经成为推理优化领域相对稳定的共识。
