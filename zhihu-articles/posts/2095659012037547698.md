### 一、深度复盘：LLM/VLM 微调后训练实战 —— 从数据准备到 LLaMA-Factory 踩坑优化

> 阿龙 ｜ 赞同 18 ｜ [https://zhuanlan.zhihu.com/p/2002499778081206595](https://zhuanlan.zhihu.com/p/2002499778081206595) ｜ 全文来源：知乎搜索摘要

本篇是 LLM/VLM（多模态）后训练实战复盘，覆盖从数据准备到 LLaMA-Factory 训练全流程的踩坑与优化。以下为可获取的分布式训练卡死排查细节（DeepSpeed + LLaMA-Factory 场景）。

### 6.1 故障现象：训练中途进程挂起

真实报错日志（节选）：

```text
[Rank 0] Watchdog caught the process hanging for 1800000ms!
[Rank 3] NCCL WARN: Waiting for ncclComm_t rank 0 to finish...
[ERROR] torch.distributed.elastic.multiprocessing.api: failed (exitcode: -6)
```

### 6.2 排查路径

1. **工具诊断** ：使用 `py-spy dump` 抓堆栈，发现 Rank 0 阻塞在 `fetch_sub_module` ，其他 Rank 阻塞在 `all_gather` 。这指向 DeepSpeed ZeRO-3 的参数分区（Partitioning）在处理特殊算子时进入了同步死锁。
2. **Shape 陷阱** ：检查数据发现，Qwen2.5-Omni 处理多轮视频时， `input_ids` 中的多模态 Token 插入导致 `position_ids` 非线性偏移。若 `cutoff_len` 设置不当或 RoPE 计算越界，会导致 Forward 阶段卡死。
3. **通信调优** ：在 H100 高带宽环境下， `gradient_accumulation_steps > 1` 时的微步同步可能触发伪超时。

### 6.3 解决方案

- **修正 Shape 逻辑** ：在 Dataset 处理类中强制检查 `len(input_ids) == len(labels)` ，处理多模态 Token 展开时的边界对齐。
- **DeepSpeed 配置调优（关键配置）** ：针对 H100 高带宽环境，将通信超时阈值拉大，并禁用不必要的 Bucket 压缩，牺牲少量显存换取稳定性：

```json
// ds_config_h100.json
{
  "train_batch_size": "auto",
  "gradient_accumulation_steps": "auto",
  // 关键：大幅拉大超时时间，防止 NCCL 误判
  "ddp_timeout": 7200,
  "communication_data_type": "bf16",
  "zero_optimization": {
    "stage": 3,
    "overlap_comm": true,
    "contiguous_gradients": true,
    // 关键：增大 Bucket Size 适配 NVLink 带宽
    "reduce_bucket_size": 1000000000,
    "stage3_prefetch_bucket_size": 50000000,
    "stage3_param_persistence_threshold": 100000
  }
}
```

- **架构适配** ：手动修正 transformers（v4.37+）对 Qwen2.5 的 RoPE 缩放系数支持问题。

### 二、大模型 LoRA 微调学不进知识？

> Aura ｜ 赞同 6 ｜ [https://zhuanlan.zhihu.com/p/2065922211123312323](https://zhuanlan.zhihu.com/p/2065922211123312323) ｜ 全文来源：知乎搜索摘要

### 背景：垂域知识类模型，LoRA 训了没效果

作者所在公司要做垂域模型。对小公司来说，想真正交付一个模型，SFT 基本还是最现实的路线。做的是 **知识类模型** （不是数学、代码类）——跑分上不去，主要问题不是推理能力不够，而是 **缺少领域知识** 。

方法对比（原文视角）：

- **全量 SFT** ：相当于把整个大模型的”大脑”从头到脚全部回炉重造一遍，适应新领域和任务。效果通常较好，但烧钱、烧显存、烧时间，且每个任务都要保存一份完整模型，切换任务麻烦。
- **LoRA** ：大脑主体不动，只在旁边挂一个”微型助听器”，训练这个助听器让模型听懂新任务。显存占用小、训练快、存储成本低，切换任务只需更换 LoRA 权重，效果有时不输全量微调。

### 踩坑过程

1. 先洗了一批知识点，通过比较”邪修”的数据处理方法，基本可以保证：这批数据如果真的训进模型，benchmark 跑分一定会提升。
2. 一上来用 LoRA 训练， **一点效果都没有** 。
3. 判断是数据多样性不够 → 混入各种数据，benchmark 分数波动不大，基本不变。
4. 又怀疑数据质量不够 → 继续洗数据、继续训，仍无明显效果。
5. 期间还听了同事的话：”SFT 一个 epoch 基本就差不多了”。
6. 于是开始怀疑核心问题： **是不是这些知识根本没有训进模型？**

### 验证实验设计：知识到底有没有被训进去

用 **同一批数据** 分别训练 LoRA 和 Full SFT，在 **关闭 thinking** 的情况下直接让模型回答训练集里的问题，并对比 1、2、5 轮训练后的输出与参考答案。

预期逻辑：如果 LoRA 真正把知识训进去了，模型输出应与训练参考答案差不多；如果差很多，就是没训进去。

实验记号： `full` = 全量微调； `lora` = LoRA 微调； `ep` = epoch（完整遍历训练集次数），ep1/ep2/ep5 即训练 1/2/5 轮。

本次实验共评测 **4,739 条** 问答数据。

### 评测指标

- **Exact Match** ：答案与参考答案严格字符串匹配，完全一致才算正确。
- **ROUGE-1 F1** ：统计答案与参考答案单词/字词级别的重合程度。
- **ROUGE-2 F1** ：统计连续两个字词的重合程度，比 ROUGE-1 更关注局部表达一致性。

> 注：实验结论数据表（LoRA 与 Full 在各 epoch 下的具体分数）未随摘要保留，但该文的实验设计本身即核心经验： **判断知识是否”训进去”，最直接的办法是用训练集原题回测 + Exact Match/ROUGE 对比 LoRA 与全量 SFT 的差异** 。

### 四、大语言模型微调大家有什么经验可以分享吗？（回答）

> 白露未晞me ｜ 赞同 33 ｜ [https://www.zhihu.com/question/1965924673243023253/answer/2092756403173773442](https://www.zhihu.com/question/1965924673243023253/answer/2092756403173773442) ｜ 全文来源：知乎搜索摘要

### 核心经验：SFT 中的 padding / packing 与样本边界处理

对 Llama、Mistral、Qwen 等 decoder-only 模型，应使用 **能传递边界信息的 padding-free / varlen attention** ，并 **重置每条样本的 position IDs** ；聊天 SFT 优先选择 **保留完整样本的 bfd** （best-fit-decreasing）packing 策略，避免会从中间切断样本的 wrapped 策略。

作者给出的 TRL `SFTTrainer` 示例配置：

```python
import torch
from datasets import Dataset
from trl import SFTConfig, SFTTrainer

dataset = Dataset.from_list([
    {"messages": [
        {"role": "user", "content": q},
        {"role": "assistant", "content": a},
    ]}
    for q, a in [("1+1？", "2"), ("中国首都是？", "北京"), ("水的化学式？", "H2O")]
])

trainer = SFTTrainer(
    model="Qwen/Qwen3-0.6B",
    train_dataset=dataset,
    args=SFTConfig(
        output_dir="out",
        max_length=128,
        packing=True,
        packing_strategy="bfd",      # 关键：bfd 保留完整样本，不用 wrapped
        assistant_only_loss=True,    # 关键：只对 assistant 回复计算 loss
        per_device_train_batch_size=2,
        max_steps=1,
        model_init_kwargs={
            "attn_implementation": "flash_attention_2",  # varlen attention
            "dtype": torch.bfloat16,
        },
    ),
)

# 检查样本边界：packing 后 position_ids 应每条样本从 0 重新计数
batch = next(iter(trainer.get_train_dataloader()))
pos = batch["position_ids"][0]

print("position_ids:", pos.tolist())
```

要点归纳：

1. `padding-free` + `flash_attention_2` （varlen attention）可以让 batch 内多条样本互不串注意力，省掉 padding 浪费。
2. packing 后必须检查 `position_ids` 是否按样本重置，否则模型会把多条拼在一起的样本当成一条长上下文学习。
3. `assistant_only_loss=True` 保证只学回复部分，不把用户输入也纳入损失。

### 五、Loss 收敛不代表学会：腾讯混元 ACL 2026 拆解 SFT 训练中 15.3% 的「假学会」样本

> 量子位 ｜ 赞同 18 ｜ [https://zhuanlan.zhihu.com/p/2064450377018349068](https://zhuanlan.zhihu.com/p/2064450377018349068) ｜ 全文来源：搜狐镜像 [https://m.sohu.com/a/1054687771_610300/（另见](https://m.sohu.com/a/1054687771_610300/%EF%BC%88%E5%8F%A6%E8%A7%81) [http://blog.aitntnews.com/newDetail.html?newId=27612](http://blog.aitntnews.com/newDetail.html?newId=27612) ）

大模型微调（SFT）是当前最主流的 LLM 落地方案——医疗问答、代码生成、法律文书，上到千亿参数大模型、下到端侧小模型几乎都在用。但一个尴尬的事实是：大家都默认 SFT”训练完就是学完了”。腾讯混元团队对 Qwen、LLaMA、OLMo2 等多个模型家族（1.8B–14B）和 10 个数据集做了全面排查，发现每个模型、每个数据集上都有一批训练样本—— **模型在训练中见过，loss 也降下去了，但回头重测就是答不对，平均比例高达 15.3%** 。

这就是论文定义的 **不完全学习现象（Incomplete Learning Phenomenon，ILP）** ——SFT 训练的系统性盲区。

**发表** ：ACL 2026 主会长文（Long Paper，Pages 30186–30213）。

### 背景与痛点

业界默认流程：准备标注数据 → 基座模型跑 SFT → 看 loss 收敛 → 认为训练完成。问题在于： **loss 是全局平均，掩盖了样本间的差异** ——loss 收敛只代表”大部分样本学会了”，那些始终学不会的样本被淹没了。对比之下，预训练阶段的数据质量研究（Dolma、C4 等）很深入，但 SFT 阶段几乎没人追问”模型到底学会了什么、没学会什么”。

### 论文四项工作

- **定义 ILP** ：将 SFT 后无法正确复现训练样本的行为正式命名为”Incomplete Learning”；
- **找到五大根因** ：把每个未学会样本对应到一个可解释的原因，而非笼统归咎”数据不好”；
- **提出四步诊断框架** ：Detect → Attribute → Intervene → Verify，全流程可复现；
- **验证五种干预** ：证明 CPT 补充知识远优于加 epoch，且部分根因无法通过 SFT 本身解决。

### Step 1：检测（Detect）——怎么知道模型”没学会”？

难点在于区分”大致理解”和”真正学会”——SFT 生成自由文本，”答对”太模糊。论文做法：

- **MC 转换（Multiple-Choice Conversion）** ：

- **pass@k 指标（k=5）** ：对每道 MC 题，用训好的模型采样 5 次；5 次中 1 次选对 → 判定”已学会”；5 次全错 → 判定为 ILP 样本。k=5 不是随便取的：温度会带来回答随机性，pass@5 给了 5 次机会，比 top-1 更公允。

### Step 2：归因（Attribute）——为什么没学会？

全文最核心贡献： **2×2 归因矩阵** 。纵轴是”基模型是否已掌握该知识”（预训练阶段），横轴是”SFT 标签是否正确”（标注质量）。

两步快速定位：

- **知识方向判断** ：在基座模型上做零样本测试 → 基模型能答对，说明”知识已经有了”，问题出在 SFT 过程的冲突；基模型答不对，说明”预训练阶段就缺知识”。
- **训练方向判断** ：取 early-20% checkpoint 和 late-20% checkpoint 对比 → 先答对后答错 → 遗忘（IV）；一直答不对 → 优化不足（V）；存在多个冲突标签 → 数据矛盾（III）。

最终锁定 **五大根因** 。两个关键发现：

- **ILP 与标注质量无关** ：即使 SFT 标签正确率超过 98%，ILP 仍然存在——不是”数据错了”的问题，而是 SFT 训练机制本身的系统性不足。
- **ILP 与模型规模弱相关** ：从 Qwen-1.8B 换到 Qwen-14B，ILP 仅降低 2.1 个百分点。更大的模型并不能显著解决”学不会”——这指向 SFT 优化机制，而不是模型容量。

### Step 3：干预（Intervene）——怎么让模型学会？

按五种根因设计对症的五类干预。最惊人的对比实验：

| 干预 | 效果 |
| --- | --- |
| CPT（继续预训练，2 倍训练量） | ILP 降 12.5% |
| 加 epochs（10 倍训练量） | ILP 仅降 2% |

即： **拼命加 SFT 训练轮次几乎没用** ，真正的瓶颈在预训练阶段的知识储备。SFT 本身存在物理上限——它只能”重新组织”已有知识，无法凭空创造新知识。

### Step 4：验证（Verify）——干预真的有效吗？

干预后重新走一遍检测流程，对比前后 ILP 率：

- 使用相同的 MC 转换 + pass@5 评估；
- 引入最小效应量阈值（min_effect=0.01），防止统计噪声；
- 确保干预收益 > 统计波动。

**物理溯源验证** ：将 ILP 样本涉及的知识点在 Dolma 5T 语料库中检索——19.3% 的知识点在 Dolma 中完全不存在（根因 I：知识缺失）；14.5% 存在冲突信息（根因 II：知识冲突）。

### 实践启示

1. **不要迷信 loss 收敛** 。训练完了不等于学会了，需要 pass@k + MC 转换做样本级诊断。
2. **加 epoch 性价比极低** 。10 倍 SFT 算力换 2% 改善，不如把预算投到预训练数据上。
3. **知识缺失是第一大根因** 。如果下游任务有大量模型没见过的新知识，SFT 几乎无能为力——要先做 CPT。
4. **数据去重和一致性是低成本高收益的事** 。全局 shuffle 和动态分桶实现简单，ROUGE-L 能提升 29%。
5. **2×2 矩阵可在几分钟内完成根因定位** 。不需要全量重训，用 early/late checkpoint 对比即可。

### 六、SFT 早已不是最优解，DFT 到底改了什么？聊聊大模型微调容易踩的大坑

> PARAMORPH ｜ 赞同 1 ｜ [https://zhuanlan.zhihu.com/p/2067993083279570155](https://zhuanlan.zhihu.com/p/2067993083279570155) ｜ 全文来源：知乎搜索摘要

### 现象：训练集漂亮，域外拉胯

做微调的常见体会：拿着一套质量还不错的指令数据集跑 SFT，训练集效果看着很漂亮，loss 一路往下掉，开开心心导出模型去测真实业务，结果一到 **域外样本直接拉胯** ，推理能力下降，还很容易 **过拟合死记训练集** 里的内容。

以前遇到这种情况，多半归咎于数据集质量不行，或者调学习率、改 epoch、加 LoRA 约束来回折腾。直到 **DFT（Dynamic Fine-Tuning，动态微调）** 论文出来才把根源讲透： **标准 SFT 本身的梯度机制就自带缺陷** 。

### SFT 的梯度机制缺陷

SFT 本质是交叉熵损失， **平等对待序列里每一个 token** ——标点、连接虚词、核心语义词全部一视同仁去拟合。从强化学习视角拆解会发现：SFT 的梯度里藏了一个 **逆概率权重** ——模型对某个 token 越没把握，对应的梯度就会被放得越大。

带来的现实问题：

- 模型本身置信度很低的 **关键 token** ，训练时会收到巨大梯度更新，模型拼命强行记住训练集里的标准答案，很容易出现 **梯度爆炸、疯狂死记样本** ，域外泛化能力直接受损；
- 而逗号、连接词这类模型本来就擅长的 token，同样被同等力度拟合， **白白消耗训练算力** ，没有实质收益。

SFT 的梯度分配示意（原文）：

```text
SFT:
输入：我 需 要 答 案
模型预测：我 → 需 → 要 → 答 → 案
梯度分配：
 我 [===== 同等权重 =====]
 需 [===== 同等权重 =====]
 要 [===== 同等权重 =====]
 答 [===== 同等权重 =====]
 案 [===== 同等权重 =====]
结果：每个 Token 的梯度一样大，模型对所有位置"一视同仁"
 → 容易在简单 Token 上浪费算力，难 Token 上又学不够
```

### DFT 的改动：一行代码

DFT（动态微调）没有改动整体训练框架，只是 **给损失里每一个 token 加上动态权重** ：借助 **停止梯度（stop-gradient）操作拿模型当下输出概率做加权** ——高置信度 token 的权重压低，把更新资源留给真正有价值的语义部分。

> 注：DFT 与”通用能力/域外泛化”的关系可结合本册其他篇目（如 Aura 的 LoRA 学不进知识、腾讯混元 ILP）对照阅读——三者从不同角度指向同一结论：均匀权重的 token 级损失并不是最优的微调目标。

### 八、一台 MacBook，一个下午，我把 Qwen3.5 训练成了自己的 AI 分类员

> 无言 ｜ 赞同 31 ｜ [https://zhuanlan.zhihu.com/p/2022317487065187386](https://zhuanlan.zhihu.com/p/2022317487065187386) ｜ 全文来源：知乎搜索摘要

一篇完整的”微调大模型 - SFT 篇”实战记录：从 0 跑通、踩了一堆坑，最后成功训练出一个业务垂直的分类模型。

### 选型结论：为什么选 Qwen3.5 + Mac？

1. **Qwen3.5-2B 参数小，适合本地微调，且开源** ：2B 参数量，模型权重只有 4.3GB，Mac 或个人 Windows 电脑基本都能尝试。
2. **Apple Silicon 的 MPS 加速，比 CPU 快 5–10 倍** ：M 系列芯片的 GPU 虽比不上 A100，但跑 2B 模型完全够用。实测每个训练 step 约 15 秒，1 个 epoch 跑完约半小时。
3. **LoRA 让”微调”平民化** ：不需要训练全部参数，LoRA 只训练不到 1% 的参数，显存占用低，电脑扛得住。

一句话总结： **Qwen3.5-2B + LoRA + Mac MPS = 低门槛也能玩大模型微调。**

### 业务场景：POI（兴趣点）分类

真实工作场景：给一个地点名称，判断它属于什么类型。分类微调比较简单、数据有固定答案，适合上手操练。

分类案例：

- “翡翠花园-3号楼” → 楼栋
- “深圳宝创宝马4S店” → 4S店
- “肯德基(北京南站店)” → 室内子（火车站内部的子 POI）
- “张记烧烤” → 其它

实验用 4 个分类：楼栋、4S店、室内子、其它。

### 第一步：造数据——用规则抽取数据模板

构建训练模板： **系统提示词 + 用户输入 + 输出** 。输出格式用 `<answer>` 标签包裹，让模型输出结构化，方便之后嵌入业务程序解析。

### 关键细节：数据均衡（少数类过采样）

训练绕不开的细节： **数据要均衡** 。作者的数据一开始 4S店只有 9 条、室内子 142 条，而”其它”有 1300 多条——如果直接训练，模型预测会严重偏向多数类。

解决办法很直观：把少量类别的数据多补充一点，方式很多，作者强烈推荐 **用大模型帮忙构造数据** ——对少数类做大模型采样，让大模型根据少量数据的特点自主生成，最后保证 **每个分类至少 150 条** 。

### 九、大模型开发避坑指南：数据准备到模型微调的实战要点

> 嗨2021 ｜ 赞同 2 ｜ [https://zhuanlan.zhihu.com/p/2058221695266197558](https://zhuanlan.zhihu.com/p/2058221695266197558) ｜ 全文来源：知乎搜索摘要

### 数据清洗：隐私脱敏与格式统一的”隐形地雷”

很多工程师的误区：只要把数据丢进预处理脚本、跑通流程就算万事大吉。实际上数据清洗环节埋着两个极易被忽视的高风险点—— **隐私泄露风险** 和 **格式噪声干扰** 。这两个问题若在训练初期未察觉，后续微调不仅可能产出合规性灾难，更会导致模型收敛困难甚至完全失效。

### 隐私脱敏的坑

构建垂直领域数据集时，常直接从业务日志、客服记录或内部文档提取语料，往往包含手机号、邮箱、身份证片段甚至内部系统账号。简单的正则替换（如 `re.sub(r'\d+', 'NUM', text)` ）看似有效，实则漏洞百出：

- 某些场景下订单号兼具业务逻辑含义，盲目抹除会破坏上下文连贯性；
- 复杂嵌套结构（如 JSON 中的用户信息字段）若未递归遍历，极易遗漏深层节点；
- 部分脱敏工具对多语言混合文本支持不佳，导致中文姓名被误删而英文缩写保留，造成分布偏移。

**实战检查清单** ：

- [ ] 是否建立了敏感实体识别（NER）规则库，覆盖当前业务特有的标识符模式？
- [ ] 对非结构化文本是否进行了多层级扫描（包括注释、元数据、隐藏字段）？
- [ ] 脱敏后是否抽样人工复核，确认语义完整性未受破坏？
- [ ] 是否验证了脱敏策略在不同编码格式（UTF-8、GBK 等）下的稳定性？

### 格式统一的坑

大模型对输入序列的 token 分布极为敏感。若训练数据混入大量不一致的换行符（ `\n` vs `\r\n` ）、全角/半角标点混杂、或 HTML 标签残留，模型会把这些噪声当特征学习，严重干扰注意力机制。

真实案例：某团队微调对话模型时发现损失函数震荡不降，排查后发现 **30% 的训练样本源自网页爬虫** ，其中包含大量未清理的 `<br>` 和 `&nbsp;` 实体，导致模型学会了生成无意义的空白字符序列。

**解决方案：标准化”数据净化流水线”** ，入库前强制三步走：

1. 统一所有文本为 UTF-8 编码并标准化换行符；
2. 使用专用库（如 bleach 或自定义解析器）剥离所有非内容标记；
3. 针对特定领域制定标点规范化规则（如将中文引号统一为规范写法）。

核心原则： **干净的数据不是”看起来整齐”，而是让模型无法从格式差异中学到任何虚假模式。**

进入微调阶段，许多开发者倾向于直接套用开源项目的默认超参数配置，或盲目跟随社区流行的”最佳实践”。（原文后续展开超参导致发散的具体分析与建议，该部分未随摘要保留——可结合本册第七篇苦猿 lr=2e-5 的案例互为印证。）
