多智能体现在很热，各家都在出方案：框架、平台、新产品，层出不穷。但我观察下来有个感受，说出来可能泼冷水：

**市面上绝大多数”多智能体”，结构上其实是主从编排。**它有个结构性的天花板，而且这个天花板不是算力问题，补多少卡都没用。

我把现在的 agent 架构分成三级，摆出来就清楚了。

### 第一级：单体

一个大脑、一个上下文窗口、串行干活。现在大家日常用的编码助手，默认形态基本都是这一级。

单体的天花板众所周知：任务越大窗口越挤，越挤越笨；一条线干活快不了；会话一死全重来。

但单体有个被低估的优点：**零协调成本**。它不需要跟任何人商量。

### 第二级：主从编排

这是现在”多智能体”的主流做法：一个主 agent 理解任务、拆解、派给若干子 agent，收结果、汇总交付。各家框架、平台的新功能，多数在这个范式里做文章。

有个细节挺说明问题：至少有一家的官方文档，自己就把这个架构叫 **Hub-and-Spoke——中心辐射**：主代理是轮心，子代理是辐条。辐条之间不互相连接，一切经过轮心。（哪家就不说了，搜一下就有——这个命名比任何批评都准确。）

这个结构是：**主 agent 是大脑，子 agent 是手脚**。三个问题都从这儿来：

**一、主 agent 的上下文就是全系统的天花板。**子 agent 各自有干净的小上下文，但所有任务的来龙去脉、所有子 agent 的产出摘要，都要挤进主 agent 那一个窗口。系统越大主 agent 越挤——单体的老毛病，换了个地方复发。也有团队在给 Router 做批处理、做上下文压缩——补丁打得越勤，越说明病是真的。

**二、信息转述税。**子 agent 之间互相不认识。一个子 agent 的发现要影响另一个，路径是”上报主 agent → 主 agent 判断 → 转述下发”，每道弯都丢真、延迟、烧 token。你想象一个团队：三个同事被规定互相不许说话，所有沟通必须经过你——你就是那个主 agent。

**三、规模化的悖论。**任务越多，主 agent 的管理负载越重。一个经理带三个人效率高，带三十个人就崩。有的方案加层级——主 agent 上面再套个总协调——但加层级是加管理，不是减协调，瓶颈只是往上挪了一层。主从编排的规模上限，就是管理者的管理能力上限。

所以这一级能从 1 个 agent 做到 5 个、10 个，做不到 100 个。

### 空着的那一级：群智能体

把两级摆在一起看，空缺很清楚：

单体的协调成本是零，但干活能力封顶；主从编排能并行了，但协调成本全压在一个个体身上，规模一大就崩。

我把缺的这一级叫**群智能体**。它的判定标准不是”agent 数量多”，而是一条性质：

> **协调成本不随规模增长**——任务再多、成员再多，没有哪个个体会先累死，因为协调不住在任何个体的脑子里。

按这个标准，群智能体至少要回答三个问题：

1. **共享状态放哪？**主从架构里放在主 agent 的窗口里；群智能体得放在所有成员都能读写的环境里——而且旧信息要能自动失效，不然状态只增不减，比窗口爆掉还糟。
2. **分工怎么产生？**派活就必然有派活的人，有派活的人就回到主从。分工得从执行历史里自己长出来。
3. **冲突谁仲裁？**两个成员同时动同一份资源，不能找 Leader——没有 Leader。得有不依赖任何个体的规则。

这三个问题我都没看到生产级的答案。我甚至怀疑用”派活”这个思路永远到不了那一级——因为派活本身就是要有个派活的人。

所以不是”要不要多智能体”的问题，是**主从编排放不下群智能体**——这两个词看着像近亲，结构上是两个物种。

想听听实际用过多智能体方案的朋友：你们的系统最多同时跑几个 agent？超过几个之后，汇总质量开始明显劣化？
