如果想入门 GPU 调度，我建议可以按**容器、Kubernetes、调度框架、训练与推理场景**这个顺序学。先跑通实验，遇到问题再回头补概念。

**先了解 Docker、镜像和容器等基础概念。**

镜像是打包好的应用、依赖和运行配置，容器是从镜像启动的运行实例。Docker 提供了构建镜像、分发镜像和运行容器的工具。入门时可以先把一个 Python 程序打成镜像，运行起来，再试着查看日志、传入配置和挂载目录，理解程序怎样进入容器、数据怎样保留下来。

**然后学 Kubernetes，先抓住资源对象和控制循环。**

需要花时间学一下云原生的知识。因为GPU调度很多工作都建立在 Kubernetes 的资源管理和扩展机制上，基础不牢，地动山摇。后面看调度器、训练平台和推理平台都会吃力。

可以从 <u>[https://kubernetes.io/zh-cn/docs/tutorials/](https://kubernetes.io/zh-cn/docs/tutorials/)</u>开始。我的建议是先跟着tutorials部分，部署应用、扩缩容、看日志和排错。

最先要理解的是 Node 和 Pod：Node 是承载工作负载的机器，可以是物理机或虚拟机；Pod 是 Kubernetes 最小的可调度单元，可以包含一个或多个紧密协作的容器。然后把常见组件的职责串起来：

· API Server 提供访问集群资源的入口。

· etcd 保存集群的配置和状态。

· Scheduler 为待调度的 Pod 选择节点。

· kubelet 在节点上协调容器运行时，管理 Pod 的运行。

· Controller 持续观察资源，通过 Reconcile，也就是反复比较期望状态和实际状态，推动系统向期望状态收敛。

Workload 算是其中最核心的部分了，它表达要运行什么，以及怎样管理这些 Pod。先认识 Deployment 的副本管理与滚动更新、StatefulSet 的稳定身份与存储关联、DaemonSet 的节点级部署，以及 Job、CronJob 的一次性任务与定时任务。AI 工作负载进一步带来了多个 worker 成组启动、不同角色协同、拓扑约束和故障恢复等需求。

**接着选一个调度框架，重点学 quota 和任务的完整流程。**

可以先选 <u>[https://github.com/volcano-sh/volcano](https://github.com/volcano-sh/volcano)</u> 或 <u>[https://github.com/kubernetes-sigs/kueue](https://github.com/kubernetes-sigs/kueue)</u>，跟着一个作业把流程走通，再对照另一个框架理解设计差异。Volcano 适合看作业和 Pod 的调度；Kueue 适合看排队、配额、准入，以及它与 Kubernetes 调度器的协作。

Quota，也就是配额，建议重点掌握，准备相关面试时尤其值得深入。它要回答的是：谁能使用多少资源，超出后怎么办，空闲额度能否借给别人，原来的使用方需要时又怎样回收。分配时可以从业务优先级、预算和常态资源需求出发，再设计借用上限与回收规则；不同卡型也需要分别核算，不能只比较 GPU 数量。

读实现时，要看清配额在哪一步校验、怎样计算占用、并发提交如何避免超发，以及任务失败或删除后怎样释放、校准占用。

这里还要区分 Kubernetes 的 ResourceQuota 和调度框架的队列配额。ResourceQuota 可以在创建或更新资源时拒绝超额请求；Kueue 等系统则可以让作业等待额度。**配额校验通过后，任务仍可能因为卡型、节点容量或拓扑不满足要求而继续等待。**<u>[https://kubernetes.io/docs/concepts/policy/resource-quotas/](https://kubernetes.io/docs/concepts/policy/resource-quotas/)[https://kueue.sigs.k8s.io/docs/concepts/cluster_queue/](https://kueue.sigs.k8s.io/docs/concepts/cluster_queue/)</u>

基础流程清楚后，再学 Gang Scheduling 和 Bin Packing之类的调度算法。比如 Gang Scheduling解决多个 worker 的成组资源需求，而 Bin Packling 研究怎样放置任务以减少资源碎片。手头没有 GPU，也可以用 Minikube 安装 Volcano，先用 CPU 任务实验成组调度、队列和优先级。

学到这里，就差不多可以去面试了，这个方向本来就是在企业中才能深入学习掌握的，掌握基本的知识就可以去面试。不过在学有余力的情况下，可以关注以下两个方向。训练调度以及推理调度。

**训练调度**

分布式训练要考虑 worker 之间的通信关系。同样数量的 GPU，放在不同机器和网络位置上，训练速度可能不同。学习放置策略时，要理解数据并行、张量并行、流水线并行等方式对通信的要求，再看调度器怎样表达和满足拓扑约束。

稳定性也是生产过程中很重要的一部分：机器故障、GPU 异常、存储变慢、某个 worker 退出，都可能让整个任务停住。遇到通信 hang，要把各个 worker 的时间线对齐，找最早发生异常的进程和节点，再结合日志、GPU、网络和存储指标缩小范围。**最终看到的通信超时，可能是其他 worker 先失败后的结果。**

故障后要考虑哪些进程需要一起重启、从哪个 checkpoint（训练检查点）恢复、训练状态和数据进度是否一致。以 torchrun 为例，worker 故障可能触发整组进程重启，训练脚本需要配合保存和恢复进度；弹性增减 worker 也需要训练框架支持。<u>[https://docs.pytorch.org/docs/2.15/elastic/run.html](https://docs.pytorch.org/docs/2.15/elastic/run.html)</u>

**推理调度**

推理调度，要将资源供给和请求一起看。推理侧可以区分几个协作的环节：集群层为服务实例分配 GPU，路由层决定请求发给哪个实例，推理引擎决定每轮处理哪些请求、多少 token。读 vLLM 或 SGLang 时，可以沿着请求进入、排队、组批和完成的流程理解引擎，再看它怎样与路由、扩缩容系统配合。

弹性扩缩容是很好的切入点。建议同时观察请求排队、输入输出长度、首 token 延迟、后续 token 的生成间隔和尾延迟，再判断容量是否足够。长短请求对服务的压力不同，只看请求数或 GPU 利用率容易遗漏问题。

扩容还要计入镜像拉取、权重加载、引擎初始化和预热的时间，通过就绪检查确认模型能接流量。缩容通常先停止接收新请求，等待在途请求完成；需要迁移请求时，还要处理 KV Cache 的转移与恢复。

KV Cache 会进一步影响请求的放置和并发。它保存历史 token 的注意力键值，长上下文和高并发会增加其显存占用，共享前缀也会带来复用机会。因此路由时需要权衡实例负载与缓存复用，缓存不足时还可能发生请求抢占和重计算。<u>[https://docs.vllm.ai/en/stable/configuration/optimization/](https://docs.vllm.ai/en/stable/configuration/optimization/)</u>

潮汐调度可以从训练、推理混部的场景理解：在线流量低时，把空闲资源借给可中断的离线任务；流量上升前，再按策略回收资源。这里需要一起考虑训练保存进度的时间、推理服务的启动时间，以及回收过程中对请求延迟的影响。

这些工作与 MaaS，也就是模型即服务平台，会有紧密联系。继续深入时，可以关注不同租户的限流与隔离、多模型资源分配、模型版本切换，以及满足服务延迟目标时的成本。做实验时先固定模型、硬件和请求分布，逐项改变策略，记录吞吐、延迟和成本怎样变化，再形成自己的判断。
