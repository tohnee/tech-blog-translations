**一、引言：大模型的参数，一张卡放不下**

训练 70B 参数的大模型，BF16 精度下光是参数就占 **140GB**。哪怕是当前最大的单卡（如 H200 的 141GB），也几乎没有余量再放梯度和优化器状态，更不用说运行时还会产生激活值。

分布式训练解决这个问题，大致有两条路线：

1. **数据并行（DDP）**：每张卡保存一份完整参数副本，卡数越多，内存浪费越严重；
2. **模型并行/张量并行（TP）**：把单层切开，每卡只算一部分——通信开销大，且需要改模型结构。

FSDP（Fully Sharded Data Parallel）走出第三条路：**把一份参数本身切成 N 份，每张卡只持有 1/N，用的时候临时借齐，用完即还**。本文标题说的“一份参数分散在多张卡上”，指的就是这件事。

**二、核心思想：从 DDP 到 ZeRO-3**

先看 DDP 的问题。DDP 训练时，每张卡都有完整参数，反向传播后通过 AllReduce 把所有卡的梯度求和，再各自更新参数。

随着卡数 N 增大，内存开销线性放大。而真正参与一次计算的，只是其中一份副本——其余 N-1 份纯属冗余。

ZeRO 论文（DeepSpeed）把这份冗余拆成三个阶段逐步消除：先切优化器状态，再切梯度，最后连参数一起切——FSDP 正是第三阶段在 PyTorch 里的原生实现：

![](https://pica.zhimg.com/v2-89a66a06410237e05444438ede3e8a86_r.jpg)

**FSDP 就是 ZeRO-3 思想在 PyTorch 里的原生实现：**参数、梯度、优化器状态全部切分，内存收益随卡数 N 线性增长。代价是——参数“分散”后，前向计算前必须通过 **AllGather** 把参数临时收集回来，反向时通过 **ReduceScatter** 把梯度归约回分片。**用通信换内存，**这是 FSDP 的全部秘密。

![](https://picx.zhimg.com/v2-771560eb8617dd1b8380248309282ffd_r.jpg)

以 4 卡为例：DDP 下每张卡都存着一份完整参数（绿色），冗余 4 倍；FSDP 下每张卡只存 1/4，但计算时需要全量参数临时到位。上图中绿色的“完整参数”只存在于计算瞬间，存储驻留的只有彩色分片。

**三、第一步：参数怎么“分散”——压平与切分**

“切分一份参数”听着简单，但一个 Transformer 模型里有几百个形状各异的张量，直接对每个张量各切各的，AllGather 时要做无数次小通信。FSDP 的思路是：**先压平，再切分**。

**3.1 FSDP1 时代：FlatParameter 压平切分**

FSDP1（经典 API FullyShardedDataParallel）把每个 FSDP 模块的所有参数**压平成一个一维大张量**，再均匀切成 N 份。这个一维张量就是 FlatParameter——一个继承自 nn.Parameter 的特殊参数：

FlatParameter 上维护着 _shard_param_infos，精确记录每个原始参数在压平后张量中的偏移量，以及切分后落在哪张卡上——这样收集回来的完整参数可以精确地“还原”成各个原始参数的形状。

为什么要“先压平”而不是逐个参数切分？除了便于均匀分配，还有两个实际原因。其一，**AllGather 是对连续内存的大块操作**——一个 Transformer 层有十几个形状各异的参数，若逐个通信，通信次数放大十几倍，而每次通信都有固定的启动延迟与元数据开销，小包场景下效率极低；压平后一次通信就是一大块，对 NCCL 这类集合通信库友好得多。其二，压平后只需要维护**一份**切分元信息（_shard_param_infos），而非为每个参数分别记录落在哪张卡、偏移多少。

**3.2 FSDP2 时代：FSDPParam 逐参数切分**

FSDP2（新 API fully_shard，即 torch.distributed.fsdp.fully_shard）做了重构：不再把整个模块压平，而是**每个参数独立按 dim-0 切分**（per-parameter sharding），每个参数由一个 FSDPParam 对象管理：

_chunk_with_empty 把参数沿 dim-0 切成 shard_world_size 片，当前 rank 只保存 chunks[shard_rank]。注意 chunks[0].size（） 这行注释——**如果参数大小不能被卡数整除，FSDP 会把分片补零（padding）到等长**。

**先补齐再通信**：所有卡的分片尺寸一致，AllGather 时就不需要再做对齐处理，代价是尾部多存几个零。

![](https://picx.zhimg.com/v2-b65439c25e2ebc24048c905704453ef7_r.jpg)

**小结**：无论是 FSDP1 的 FlatParameter 还是 FSDP2 的 FSDPParam，本质都是同一件事——把一个完整参数张量按卡数切开，每卡持有 1/N，并记录下如何拼回去的元信息。内存立刻从“一份完整参数”降到“1/N 份”。

**四、前向传播：AllGather 把参数“借”回来**

参数切分之后，前向计算怎么办？每张卡只握着 1/N 的参数，而计算需要的是完整参数。FSDP 的答案：**用到哪个模块，就临时把它的参数收集齐，算完立刻还回去**。

**4.1 unshard：AllGather 收集完整参数**

前向执行到某个 FSDP 模块之前，hook 会调用 _unshard——把当前模块的参数从各卡收集成完整副本。

在 FSDP2 中，这个“收集”过程更直观：每个参数预分配一个 numel × world_size 的输出缓冲区，AllGather 之后，第 i 块就是第 i 号卡的分片：

![](https://picx.zhimg.com/v2-43ae76a71b5dd94fb67e834cbdc8bf0d_r.jpg)

经过一次 AllGather，每张卡都持有**完整参数**了——这就是前向计算使用的临时副本。

**4.2 reshard：算完立刻还**

前向算完这个模块，FSDP 立刻调用 _reshard，把完整副本**释放掉**，恢复为只持有本地分片。

关键点在于 free_unsharded_flat_param 这个参数——**完整副本被显式释放**，内存立刻回到 1/N 状态。这正是 FSDP 与 DDP 的本质区别：**DDP 的参数是“常住”的完整副本，FSDP 的参数是“借来即还”的临时副本**。

![](https://picx.zhimg.com/v2-e63b66a6033f9088247e8f87ef604a4b_r.jpg)

**五、反向传播：ReduceScatter 把梯度归约回分片**

反向传播比前向更复杂——因为**梯度天然是完整的**，每张卡都会为完整参数算出完整梯度。如果每卡都留一份完整梯度，内存又炸了。FSDP 的处理分三步：

**5.1 重新 unshard 参数**

反向计算梯度前，FSDP 会再次把参数 all-gather 回来（前向结束时已经 reshard 了）。这多出来的一次 all-gather，就是 FSDP 通信量比 DDP 多的主要原因之一（详见第 6 节）。

这一步的触发时机很巧妙：反向传播是自后往前走的，而 FSDP 在**每个前向步骤中都会重新注册 post-backward 钩子。**

也就是说，参数在反向中被“借”的行为，是 autograd 执行到该模块的梯度计算**前一刻**才触发的——完整参数既不在前向结束后驻留，也不会在整个反向期间驻留，而是跟着 autograd 的执行节奏“走到哪借到哪”。

**5.2 逐分片计算梯度**

每张卡基于完整参数算出梯度——梯度形状与完整参数一致。但**每张卡只需要更新自己那一份参数**，梯度最终的去向是本地优化器，所以完整梯度在算完之后就成了纯粹的负担：既占显存，又是后续通信的对象。

这里还有一个隐含的约束值得注意：**参数怎么切，梯度就怎么切**。反向结束后，每张卡保留的梯度分片必须与自己驻留的参数分片逐位对齐——这样优化器才能就地更新，无需任何额外搬运。这个“对齐”关系在切分时就已经定死了（FSDP2 的 FSDPParam 中参数分片与梯度分片由同一个 sharded_size 决定）。

**5.3 ReduceScatter：归约 + 切分一步完成**

如果先用 AllReduce 把完整梯度同步一遍再切分，通信量是完整梯度的 2 倍且需要额外内存。FSDP 用 **ReduceScatter** 一举两得：各卡把完整梯度逐块相加，每张卡**只拿回自己负责的那一份**——归约与切分在一步通信内完成。

反向结束时的内存状态：每张卡持有一份**与本地参数分片对齐的梯度分片**。之后优化器只更新本地分片——优化器状态（Adam 的 m/v）也因此天然只存在本地，与参数一样是 1/N。

**六、通信与计算重叠：为什么 FSDP 不算太亏**

FSDP 的代价是通信变多了，但有一笔账要算清楚（按每卡收发量，1 格 = 1× 参数全量）：

![](https://pic4.zhimg.com/v2-e040563a7f6b6063577832385b03860d_r.jpg)

1. **DDP**：梯度 AllReduce ≈ **2×** 参数全量；
2. **FSDP（FULL_SHARD）**：前向 AllGather + 反向 AllGather + 反向 ReduceScatter ≈ **3×** 参数全量，约是 DDP 的 1.5 倍；
3. **FSDP（SHARD_GRAD_OP）**：≈ **2×**，与 DDP 相当。

通信确实多了 50%，但区别在于：DDP 的通信集中在反向末尾，而 FSDP 的通信分散在整个 step 中——这反而给了 FSDP 重叠的机会。

**预取（prefetch）：通信与计算并行**

前向执行第 i 层时，FSDP 可以**提前 all-gather 第 i+1 层的参数**，让通信在计算的同时进行：

![](https://pica.zhimg.com/v2-2cb8af642f1b3debac233062c1e4dfc8_r.jpg)

FSDP1 用独立的 unshard_stream（通信流）与计算流重叠；FSDP2 同样支持 fsdp_prefetch_num 控制预取数量。当网络的带宽不是瓶颈时，通信被计算“藏”起来，FSDP 的吞吐可以非常接近 DDP。

![](https://pica.zhimg.com/v2-7efdf4f1ded059e54438555a7d4c1540_r.jpg)

**七、FSDP 的三种切分策略**

FSDP 允许你只切分一部分，用不同的切分策略换取内存与通信的平衡。官方定义如下（节选）：

![](https://pic2.zhimg.com/v2-294a8b02e4a57852fe4cc2a1babcf7c3_r.jpg)

翻译成一张表：

![](https://pica.zhimg.com/v2-60f52c4a83e4ce49fb1fd750abaf75b2_r.jpg)

直觉：**FULL_SHARD 内存最省、通信最多；SHARD_GRAD_OP 折中——参数前向后不归还，省掉反向那次 AllGather，但显存里要常住完整参数；NO_SHARD 就是 DDP**。HYBRID_SHARD 则是节点内 FULL_SHARD、节点间复制，适合跨机带宽低的多机场景。

那实际怎么选？一个常用的经验法则是按显存压力分层：

1. **显存很紧张、卡数多、模型大** → FULL_SHARD，把参数/梯度/优化器状态全部压到 1/N，这是 FSDP 内存收益最大化的形态，也是大模型训练的主流配置；
2. **显存刚好够放完整参数，但放不下完整优化器状态** → SHARD_GRAD_OP，梯度与优化器状态仍是 1/N，只是参数常驻完整副本——注意它的显存峰值并未下降，所以它适合“显存不紧张、想省通信”的场景；
3. **显存充裕、想最大化吞吐** → NO_SHARD，退化为 DDP 的行为，没有额外收益；
4. **多机训练、跨机带宽低** → HYBRID_SHARD，把昂贵的 AllGather/ReduceScatter 限制在节点内，节点间只复制，是带宽有限时的工程化选择。

另外提醒一点：SHARD_GRAD_OP 常被误当作“省内存”的选项，但它省的是**通信**，不是**显存**——参数前向后常驻，峰值内存与 DDP 相当。

**八、FSDP1 与 FSDP2，两代设计的差异**

源码里同时躺着两套实现，值得说清：

| 维度 | FSDP1（FullyShardedDataParallel） | FSDP2（fully_shard） |
| --- | --- | --- |
| 切分粒度 | 模块内参数压平成 FlatParameter 再切 | 每个参数独立按 dim-0 切分 |
| 存储表示 | 自定义 FlatParameter | DTensor（可组合 TP/EP） |
| 使用方式 | 手动 wrap 或用 wrap（） 自动包装 | fully_shard（module） 一行，无需 wrap |
| 通信 | 整块 AllGather/ReduceScatter | 逐参数调度，更细粒度 |
| 状态 | 成熟稳定 | 新默认，继续演进 |

为什么会有两代实现？FSDP1 诞生于 PyTorch 还没有 DTensor 的时期，参数只能以自研的 FlatParameter 存储，一切切分与还原逻辑都要自己维护；而 FSDP2 建立在 DTensor 之上——DTensor 本身定义了”张量如何分布在一个 mesh 上”，FSDP 只需要声明 Shard（0） 切分，参数的存储、切分、组合全部交给 DTensor 框架管理，FSDPParam 因此可以做得比 FlatParameter 简单得多，还顺带解决了分片参数与张量并行参数在同一套框架下共存的问题。

FSDP2 的 FSDPParam 每个参数一条通信记录，配合 DTensor 之后，FSDP 可以与张量并行（TP）、序列并行组合使用，这也是新 API 的主要设计动机之一。对新项目，官方推荐直接使用 FSDP2 的 fully_shard API（torch.distributed.fsdp.fully_shard）；FSDP1 仍被广泛使用，主要用于兼容既有代码与生态。

前面讲的都是 FSDP 的默认行为。作为框架，FSDP 也留了几个关键扩展口子，让你可以介入“切分—收集—归约”这条主链路：

钩子拿到的是“完整、压平、未切分的梯度”（或者一个预分配好的分片梯度输出缓冲区），之后怎么做完全由你定义——**FSDP 的通信机制本身是插件化的**。两个细节值得注意：它必须在第一次前向之前注册，且只能注册一次；state 参数用于跨 step 维护状态（如梯度压缩中的误差反馈）。

FSDP2 把扩展点下沉到了每个参数：给张量挂上 fsdp_pre_all_gather 与 fsdp_post_all_gather 两个方法，FSDP 就会在 AllGather 之前调用前者处理本地分片、之后调用后者还原完整参数：

“用完即还”是 FSDP 的默认哲学，但有些操作确实需要完整参数在每张卡上同时出现——保存全量 checkpoint、跑一次全量评估。summon_full_params 就是这个“显式借齐”的入口：

**十、总结：借来即还的分布式哲学**

回到标题：一份参数为什么能分散在多张卡上？因为 FSDP 重新定义了参数的“驻留权”

1. **存储上**：参数、梯度、优化器状态各只存 1/N（切分）；
2. **计算上**：用到哪个模块，AllGather 临时借齐（前向/反向各一次）；
3. **梯度上**：ReduceScatter 一步完成“归约 + 切分”，梯度不落地全量；
4. **生命周期上**：用完即还，完整副本从不驻留。
