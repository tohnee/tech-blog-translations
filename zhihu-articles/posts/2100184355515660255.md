**本文主要讨论张量并行的本质、代价和优化方案。**

另外，当单卡支持模型训练或推理时，数据并行确实是首选，但随着使用设备数量的增加，其拓展效率受到通信开销的制约。数据并行在训练中每轮迭代结束后，必须发生通信（比如all-reduce)同步所有卡状态（梯度与优化器）。当单次迭代计算时间不能掩盖通信开销，数据并行的大规模扩展效率骤降。

当模型单卡无法支持存放模型状态，直接的思路是将模型参数也同时并行，这种策略一般称为张量并行(Tensor Prallel)。

由于模型中有大量矩阵计算，参数分布在不同卡间，矩阵的计算可能需要搜集其他卡参数才能得到正确计算结果，会相比数据通信带来更大的通信开销。

### 1. 张量并行的本质

Tensor Parallel的本质是：

1. 关心每个算子权重沿着哪个维度切。
2. 切完后中间激活用什么通信连接。

Transformer模型结构主要由MHA（multi-head attention)和MLP(multi-layer perceptron)组成。如果想以最小的通信开销完成模型推理，attention部分经常选择以head维度进行切分，Attention 天然就是一个”head 之间互不通信”的结构——每个 head 自己算自己的 Q·K、softmax、V。这正是 num_attention_heads 这个维度”天然独立”的含义。这样只需要在atten末尾进行一次（all-reduce)通信，同步不同卡间计算结果。

![](https://pic1.zhimg.com/v2-7153e1c8f4aee3b0843f098ba532fa24_r.jpg)

矩阵乘法的常见两种切法 对一个线性层 Y=XW ，其中 X 形状是 [b,hin] ，W 形状是 [hin,hout] ：

- 列切（Column Parallel）：把 W 按输出维度 hout 切成 [W1,W2,…,WTP] ，每卡持有 Wi∈[hin,hout/TP] 。每卡算 Yi=XWi ，得到输出切片。因为 X 是完整的（每卡都拿一份输入的副本），各卡的计算完全独立，不需要通信。
- 行切（Row Parallel）：把 W 按输入维度 hin 切成上下堆叠的 Wi∈[hin/TP,hout] 。这时每卡只拿到输入的一部分 Xi ，算的是部分和 Yi=XiWi ，而完整输出是各卡部分和之和：Y=∑iXiWi 。需要一次 All-Reduce（或 Reduce-Scatter）把部分和加起来。

列切独立、行切求和。TP 的全部设计就是在交替使用这两种切法，让通信恰好"抵消"。<br>MLP部分经常由2个连续矩阵组成producer和consumer关系，对于第一个矩阵(up projection)通常选择column wise切分（mk*kn矩阵的n维度），第二个矩阵(down projection) 通常选择row-wise 切分（k维度）。

![](https://pic3.zhimg.com/v2-a75596993254dafeb02cc0ce6fc3f83c_r.jpg)

### 2. TP切分的代价

![](https://pic3.zhimg.com/v2-c03f054a5c6b7d5eedc1fc536db18c4a_r.jpg)

看 图中 A 的前向2个rank的展示。Rank 0 和 Rank 1 各自独立算完 FC1、GeLU、FC2（列切/行切带来的自由区间），然后在红色 All-Reduce 处汇合。这个汇合点是硬依赖：下一个 LayerNorm 需要的是 *Y*=∑*iYi* 的完整结果，任何一张卡的计算都无法越过它先走一步。通信期间，两张卡的计算单元全部空转——这就是图上标注的"气泡"。<br>图中B：把行切的 FC2 沿 K 维（sharded 的中间维）分成两块，先算分块 1 的部分和，异步发起 AR1，同时继续算分块 2——AR1 的通信和分块 2 的计算重叠。图中暴露时间从 3.0 压到 1.4。但它利用计算掩盖通信不完全，原因是分块之间共享同一条输出累加链，最后一个分块的 AR 无论如何都在关键路径尾部；而且这只是把一个 AR 拆小了，总通信字节数没有变，只是把延迟摊进计算里。<br>图中 C 展示不同TP切分数量下造成的单卡吞吐量下降，主要原因在于：<br>一个 GEMM 有 *F* 次浮点运算，分给 TP 张卡，每张卡分到 *F*/*TP* 。<br> $$ \text{时间} = \frac{F/TP}{\text{每卡实际跑出来的速度}} $$

GPU 的实际速度取决于 GEMM 的形状，GEMM 越小，跑得越”不满速”。记 *η* = 实际利用率，时间就变成了：

$$ \dfrac{F/TP}{\eta \cdot P_{peak}} = \dfrac{T}{TP \cdot \eta} $$

GPU 跑 GEMM 不是一口算完，而是把它切成一堆 tile，一个 SM 一次处理一个 tile，像剧院一场一场翻台：

- 一张 GPU 有 132 个 SM = 剧院有 132 个座位，一场最多坐 132 个 tile；
- tile 总数 ≫ 座位数时，要翻很多场（wave），只有最后一场可能坐不满——损失摊到几十场里，忽略不计；
- tile 总数和座位数差不多、甚至更少时，整场演出都有空座，那些 SM 从头到尾在空转——你付了整场的时间，只用了一部分座位。

每张卡分到的工作量确实除以了 TP，TP=16 时每卡的 GEMM 只有原来的 1/16，但跑它的时候整个芯片只有 85% 在工作，所以时间不是 1/16。比如：

- TP=1：每卡 FC1 能切出 7168 个 tile，要翻 55 场，最后一场不满的损失摊到 55 场里，η=99%；
- TP=8：896 个 tile，翻 7 场，η=97%，还行；
- TP=16：只剩 448 个 tile，理论上 3.4 场就够，但 wave 只能取整——翻 4 场，第 4 场只坐了 132 个座位中的 44 个，整场 GPU 有 2⁄3 是空的，η 直接掉到 85%；
- TP=32：tile 更少，而且 N=448 不是 128 的整数倍，tile 边界还有 12.5% 的 padding 浪费，η 同样 85%。

### 2.1 激活只能“在某种程度上”切分

在线性层内部，很多中间激活天然是切开的。例如 Column Parallel Linear 的输出只在当前 rank 上保存一部分。

但到了某些位置，计算又需要完整激活，例如：

- 某些 Row Parallel Linear 的输入；
- 普通 TP 实现中，LayerNorm 前后的完整隐藏状态；
- 残差连接附近；

于是每张卡可能都要保存一份完整激活。TP 增大后，参数显存持续下降，但这部分激活显存却不下降，逐渐成为瓶颈。

可以粗略写成：

$$ M_{\text{act}}(t)\approx \frac{A_{\text{shardable}}}{t} +A_{\text{replicatedActivation}} $$

如果我们把sequence length也进行sharding（SP, Sequence Parallelism)的目标就是把第二项也尽量变成：

$$ M_{\text{act}}(t)\approx \frac{A_{\text{shardable}}+A_{\text{sequence}}}{t} +A_{\text{remaining}} $$

![](https://pica.zhimg.com/v2-3eeb9064f4caf482dfd1d0b0f2e23056_r.jpg)

由上图，当模型sequence长度变大，固定TP时，激活会显著增长，所以我们会选择切分序列维度。

![](https://pic1.zhimg.com/v2-5997e1fe50e5ff1ea7b0e186ca997ad0_r.jpg)

SP+TP的切法核心是，进入 TP 区域前 All-Gather，离开 TP 区域后 Reduce-Scatter，让两端的 Norm、Dropout 和残差始终只保存本地序列片段。 用 TP 切分计算量大的 Attention／MLP，用 SP 切分其余逐 token 操作，在降低每卡激活显存的同时，付出更频繁的集合通信开销。

![](https://pica.zhimg.com/v2-0e481fee1691ec61ed53d347ee6f8adc_r.jpg)

TP＋SP 的策略仍然有两个主要问题：

1. **并没有完全消除长序列在 TP 区域膨胀**

SP 只切两端的逐 token 区域。进入 Attention／MLP 前仍要 All-Gather：<br> $$ [b,s/t,h]→[b,s,h] $$ <br>因此 TP 区域依然可能存在：

- 完整序列的输入激活；
- 较大的 MLP 中间激活；
- Attention 的上下文计算和临时 buffer；
- 若实现不佳，显式 *S*×*S* 注意力矩阵还会带来 $O(S^2)$ 项。

所以 SP 不能替代 FlashAttention、Context Parallelism 或激活重计算。

2. **大模型跨节点 TP 会严重降速**

如果模型在单节点 `TP=8` 下仍放不下，就不得不：

- 增大 TP 并跨节点，承受明显的通信降速；
- 或结合 PP、DP、ZeRO／FSDP、激活重计算、Context Parallelism 等策略。接下来讲解Context Parallelism策略。

### 3. Context Parallelism

当模型有更长的sequence length，由上一节讨论可知，每张卡需要保存很大的activation，导致可能会超出单卡内存。前向传播时只保存少量关键激活，反向传播需要时再重新执行一次前向计算。它通常会带来约 30% 的额外计算开销，具体数值取决于模型结构和实现方式。更重要的是，我们仍然需要保存各个层边界的输入，也就是用于重启重算的 checkpoint。这些激活的大小会随着序列长度线性增长。当序列长度继续增加时，即使启用了完全重算，激活显存依然可能成为瓶颈。上下文并行（Context Parallelism，CP）正是用来解决这类问题。

上下文并行与序列并行一样，都是沿着序列维度切分输入。但二者的切分范围不同。在“张量并行＋序列并行”中，序列切分通常只发生在特定的序列并行区域；进入注意力或 MLP 的矩阵乘法前，往往还需要重新收集完整序列。上下文并行则把序列分片贯穿到整个模型：从输入 embedding 开始，经过每一层 Transformer，直到最终输出，各设备始终只保存自己负责的序列片段。

假设上下文并行度为 *P* ，完整序列长度为 *S* ，那么每个设备理想情况下只保存 *S*/*P* 个 token 对应的激活：

$$ X_r\in\mathbb{R}^{B\times S/P\times H} $$

![](https://picx.zhimg.com/v2-763b88d674aaf9806b2b74e924abfc81_r.jpg)

假设 CP degree 为 4，序列被切成四段：

$$ [x0,x1,x2,x3] $$

每个 CP rank 只保存并处理其中一段。对于 LayerNorm、MLP 等逐 token 运算，每个 rank 可以独立完成计算，不需要因为 CP 增加前向通信。

对于 LayerNorm、RMSNorm、MLP 和逐 token 的线性变换，每个 token 的计算都是独立的。一个设备只需要处理自己持有的 token，不需要知道其他设备上的序列内容。

因此，在注意力之外，上下文并行通常不需要额外的逐层集合通信。它也不同于张量并行：CP 没有切分这些算子的权重矩阵，因此不需要在每次矩阵乘法后同步结果。Attention 是例外：Q 是本地的，但 Attention 的计算不是本地的

### 3.1 注意力为什么必须跨设备交换数据

在自注意力中，每个 query 都需要访问其他 token 的 key 和 value。对于普通双向注意力，它可能需要访问完整序列；对于因果注意力，它至少需要访问自己之前的所有 token。

当序列被切分到不同设备后，一个设备上的本地 query 只凭本地 KV 无法得到正确结果。它必须获取其他序列分片的 KV 数据。

最直接的办法是先通过 all-gather 收集完整 KV，再在本地计算注意力。这种方式容易理解，但会带来两个问题：

1. 每个设备都要临时保存完整序列的 KV，削弱上下文并行节省显存的效果；
2. KV 集中传输可能形成较大的通信峰值，而且不容易与计算充分重叠。

因此，CP 的关键不是“怎么切序列”，而是：

> 如何在不把完整序列重新物化到每张 GPU 上的前提下，让每个 Query 看到它需要的 Key/Value。

### 3.2 Ring Attention

Ring Attention 提供了一种更适合分块执行的方式。Ring Attention 的基本思想可以概括为：

> 查询块固定不动，键值块在设备之间循环传递。

假设有 *P* 个设备，每个设备保存一个本地查询块 *Qr* ，以及最初对应的 *Kr*,*Vr* 。计算从本地 KV 块开始，随后每个设备不断接收下一个 KV 块，同时把自己当前持有的 KV 块发送给下一个设备。

![](https://pic1.zhimg.com/v2-62f340134cf125f9dfab2bb30b945726_r.jpg)

经过本地计算和后续的 $P−1 $ 轮交换，每个查询块都能访问完整序列中的所有 KV 块。

只要当前 KV 块的计算时间足够长，就可以把下一块 KV 的传输隐藏在计算之后。这样，Ring Attention 不需要一次性在某个设备上物化完整 KV，并且有机会重叠通信与计算。

不过，这里还有一个不能省略的问题：不同 KV 块得到的局部注意力结果不能直接相加。

Softmax 不是对每个 KV 块独立计算的。它的分母依赖当前 query 能访问的所有 key，而且为了数值稳定，还需要使用全局的行最大值。

因此，每处理一个新的 KV 块，设备都不能简单地计算一次局部 softmax，然后把结果累加到之前的输出上。正确做法是维护一组可以逐步合并的状态：

- 当前最大的注意力分数；
- 当前 softmax 的归一化项；
- 经过相应缩放的注意力输出累加器。

当新的 KV 块到来时，先更新最大值，再重新缩放之前的归一化项和输出累加器，最后合并当前块的贡献。这与 FlashAttention 使用的在线 softmax 思路一致。

所以，Ring Attention 并不只是“把 KV 放到环上传输”，而是三个机制的组合：

> 分块精确注意力、在线 softmax 合并，以及 KV 通信与块计算的重叠。

### 3.3 因果注意力还需要解决负载不均

普通双向注意力$full attention$：可以看到整个序列。

对于因果注意力，仅仅让每个设备获得相同数量的 token，并不代表它们的计算量相同，区别在于使用了不同的注意力掩码（mask）:

$$ \operatorname{Attention}(Q,K,V) = \operatorname{softmax} \left( \frac{QK^\mathsf{T}}{\sqrt{d}}+M \right)V $$

其中 *M* 是注意力掩码：

- 允许访问的位置加 0 ，不改变注意力分数；
- 禁止访问的位置加 −∞ ，经过 softmax 后权重接近 0 。

对于双向注意力，每个本地 *Qr* 都需要访问全部 KV 块，因此通常要完成整个环形交换过程。

对于因果注意力，不同 query 块需要的 KV 数量不同：

- 序列前部的 query 只需要较少的历史 KV；
- 序列后部的 query 需要访问更多历史 KV；
- 被因果掩码完全屏蔽的块计算可以跳过。

如果采用简单的连续切分，序列前部的 query 只能看到很短的历史，而序列后部的 query 需要关注大量历史 token。结果是：负责后部的设备计算量更大，负责前部的设备则可能提前空闲。

![](https://pic4.zhimg.com/v2-d9a83aa5cc6cf2505554493bda9c786f_r.jpg)

常见的解决方法是使用 zigzag 分片。直接把序列连续切成 *P* 份，每份虽然有相同数量的 token，但：

- 靠前的分片只需要访问较短的历史；
- 靠后的分片需要访问较长的历史；
- 最后一个分片的计算量通常最大。

因此，token 数均衡不等于注意力计算量均衡。

### 3.4 Zig-Zag 的核心：把靠前的行和靠后的行配对

![](https://pic1.zhimg.com/v2-1745536a019c06ecabf979cc44e6c120_r.jpg)

观察因果掩码，第 *i* 行和第 *N*+1−*i* 行的计算量之和为：

$$ i+(N+1−i)=N+1 $$

![](https://picx.zhimg.com/v2-fa90fb2cbe42360f9b448bde2fa7ca93_r.jpg)

综上：

- Zig-Zag：决定哪些 query 块和初始 KV 块放在哪台设备上，解决负载均衡；
- Ring Attention：决定 KV 块怎样在设备间移动，解决分片状态下的注意力计算与临时显存问题。

### 4. 讨论

TP 有一个隐含前提：参与 TP 的设备之间最好具有高速、低延迟的互联。

这是因为 TP 并不是在模型开始和结束时才通信，而是在 Transformer 层内部的计算过程中反复同步。每个设备都参与每一层的计算，因此层内集合通信发生得非常频繁。

在单节点内部，设备通常通过 NVLink 等高速互联连接，这种通信开销相对容易接受。但跨节点网络的带宽和延迟通常更差。如果简单地把 TP 组扩大到多个节点，设备可能频繁停下来等待通信，计算效率会明显下降。

于是问题变成：

> 如果模型经过节点内 TP 后仍然无法轻松放入一个节点，我们能不能避免让所有节点共同参与每一层内部的计算？

这就需要换一种模型切分方式。

这就是流水线并行（Pipeline Parallelism，PP）的基本思想：

> 把模型按层划分成多个阶段，每个阶段放在不同设备或节点上，阶段之间传递中间激活。

接下来讲解PP实践经验。
