## FSDP 通信：从单层 collective 到计算重叠

- **状态分片**：权重、梯度和优化器状态按 rank 分片，激活仍由各 rank 的本地计算图管理。
- **运行时通信**：计算前用 AllGather 临时收齐参数，反向后用 ReduceScatter 规约并切分梯度。
- **显存与速度**：reshard、prefetch、mixed precision 和 checkpointing 都在调整显存占用、通信量与重算成本。
- **执行调度**：`FSDP::pre-backward` 负责在 autograd 进入某层反向前准备参数，并为通信与计算重叠创造条件。

本文从状态分片、参数生命周期、前反向通信、计算重叠、autograd 调度和配置权衡六个角度介绍 FSDP2。文中的 8-way shard、28 个 Decoder Layer 独立 wrap 的训练 trace 用作贯穿案例，帮助把抽象机制对应到真实执行时间线。

### 1. 单层 FSDP 的完整生命周期

FSDP2 里要把四类状态分开看：**权重/参数**按 rank 分片保存，计算前通过 AllGather 临时恢复完整；**梯度**在本地反向中先形成完整参数梯度，再通过 ReduceScatter 完成跨 rank 求和并切回 shard；**激活**留在本 rank 的前向/反向链路里，不是 FSDP collective 的 payload；**优化器状态**跟随参数 shard 常驻本 rank，只在 optimizer step 消费本 rank 的 gradient shard。

![](https://pic3.zhimg.com/v2-b114aeeeb747672b91136ec432a2b9fa_r.jpg)

当 `reshard_after_forward=True` 时，典型顺序如下：

1. **Forward AllGather**：各 rank 交换参数 shard，在本地重建该层完整参数。
2. **Forward compute**：当前层用完整参数执行前向；结束后释放完整参数，回到分片状态。
3. **Pre-backward AllGather**：梯度流回该层前，再次收齐参数。
4. **Backward compute**：计算 input gradient 和完整参数梯度。
5. **ReduceScatter**：跨 rank 求和参数梯度，并让每张卡只留下自己负责的 gradient shard。

在默认重分片策略下，一个 FSDP unit 每轮通常经历 **前向 1 次 AllGather，反向 1 次 AllGather 和 1 次 ReduceScatter**。这三次 collective 对应参数从 shard 到 full、再从完整梯度回到 gradient shard 的生命周期；具体次数还会受到 wrap 粒度、reshard 策略和梯度同步设置影响。

### 2. 四类状态与 collective payload

FSDP2 的通信问题不能只说“模型状态被 shard 了”。权重、梯度、激活、优化器状态的归属和生命周期不同，只有前两类会进入本节讨论的前反向 collective。

| 状态类别 | 静态归属 | 前向/反向形态 | 是否是 collective payload | 理解重点 |
| --- | --- | --- | --- | --- |
| 权重/参数 | 每个 rank 持有 1/N shard | 计算前 AllGather 成完整参数，用完按策略 reshard | 是，AllGather 搬参数 shard | 完整参数只在计算窗口内临时存在，是否立即 reshard 由策略决定。 |
| 梯度 | 反向前通常没有持久梯度 | 本地算出完整参数梯度，再 ReduceScatter 成 gradient shard | 是，ReduceScatter 搬梯度分块并规约 | ReduceScatter 同时完成跨 rank 规约与梯度分片。 |
| 激活 | 本 rank 前向产生并保存，或由 checkpoint 重算 | 服务于本 rank 的 backward，随计算图释放 | 否，不由 FSDP AllGather/ReduceScatter 搬运 | FSDP 不负责跨 rank 分片激活；checkpointing 单独控制保存与重算。 |
| 优化器状态 | 跟随本 rank 负责的参数 shard | optimizer step 用本 rank 的 gradient shard 更新本地参数 shard | 否，不在前反向 collective 中传输 | 优化器只更新本 rank 负责的参数 shard，状态与该 shard 同位。 |

把四类状态拆开后，下面两条 collective 的 payload 才不容易混淆：

| Collective | 输入状态 | 网络 payload | 完成后的本地状态 |
| --- | --- | --- | --- |
| AllGather | 每卡持有 1/N 参数 shard | 各 rank 的参数 shard | 每卡临时持有完整参数 |
| ReduceScatter | 每卡算出完整参数梯度 | 参数梯度分块，边规约边散发 | 每卡保留 1/N gradient shard |

这张 collective 表只回答“网络上搬什么”：AllGather 补齐权重/参数，ReduceScatter 同步并切分参数梯度。activation 的保存/重算会改变显存峰值和反向耗时，optimizer state 的分片会改变常驻显存，但二者都不是前反向 AllGather/ReduceScatter 的 payload。

设 shard world size 为 N，单层完整参数占 P 字节。单 rank 每次 AllGather 或 ReduceScatter 的逻辑 payload 近似为 `(N-1)/N * P`。N=8 时，2 次 AllGather 加 1 次 ReduceScatter 约为 `3 * 7/8 * P = 2.625P`。这是逻辑数据量，不包含 NCCL ring 转发、协议和拓扑开销。

通信字节还受 dtype 影响：`param_dtype` 决定参数 AllGather 的字节数，`reduce_dtype` 决定 ReduceScatter 的字节数。mixed precision 省下的是网络字节和临时完整参数显存，不会改变 collective 的基本形态。

### 3. 从 wrap 结构推导通信次数

通信次数首先由 FSDP unit 数量和各 unit 的生命周期决定。以 28 个 Decoder Layer 独立 wrap、外加 1 个 root FSDP unit 的案例为例，每个物理 ProfilerStep 可以观察到：

| 事件 | 物理次数 | 解释 |
| --- | --- | --- |
| NCCL AllGather kernel | 57 | 28 层前向 + 28 层反向 + 1 个 root unit |
| NCCL ReduceScatter kernel | 29 | 28 层梯度同步 + 1 个 root unit |
| FSDP backward prefetch | 28 | 对应 28 个 Decoder Layer 的反向预取调度 |

这个案例也说明 profiler 里的 annotation 数量不等于物理通信次数：同一个 collective 可能同时留下 CPU 和 GPU 侧记录，因此 114 个 AllGather annotation 对应 57 个 NCCL kernel，58 个 ReduceScatter annotation 对应 29 个 NCCL kernel。理解 FSDP 的通信规模时，应结合 wrap 结构、生命周期和去重后的 collective ID，而不是只看事件名称的出现次数。

### 4. 通信如何与计算重叠

FSDP 通常把计算与 collective 放在不同 CUDA stream 上，但不同 stream 只提供并发条件，不保证自动重叠。collective 需要提前 enqueue，参数依赖也要允许通信 stream 在当前计算结束前开始工作。

### 4.1 前向：用当前层计算盖住下一层 AllGather

当前层在 compute stream 上执行 forward 时，下一层参数可以在通信 stream 上 AllGather。第一层前面没有计算窗口，首个 AllGather 天然暴露；后续层能遮住多少，取决于当前层计算时长、网络时长、CPU enqueue 速度和显存余量。

`enable_forward_prefetch=true` 只解决“提前发起”的问题。若 CPU 本身卡住、通信依赖没有满足、当前层太轻，或预取完整参数把显存顶满，重叠仍会变差。

### 4.2 反向：下一层 AllGather 必须排在当前层 ReduceScatter 前面

![](https://pica.zhimg.com/v2-2f2f37573ef2906e15b6f89fb1b880f6_r.jpg)

反向阶段同时存在下一层参数 AllGather 和当前层梯度 ReduceScatter。两类 collective 通常共用 NCCL process group，并在同一内部通信 stream 上按 enqueue 顺序执行，因此调度顺序会直接影响下一层是否等待参数。

理想顺序是：执行 layer i 的 backward compute 时，先 enqueue layer i-1 的参数 AllGather，再 enqueue layer i 的 ReduceScatter。这样 layer i-1 的参数更可能在其计算开始前准备好。

如果 ReduceScatter 先进入通信 stream，layer i-1 的 AllGather 就只能排在后面，而 layer i-1 的 backward 又依赖完整参数。结果是计算等待通信，原本可并行的两个 stream 出现串行区间。PyTorch FSDP Notes 指出，没有显式 backward prefetch 时，通信与计算的 overlap 可能为 0。[^1]

### 5. `FSDP::pre-backward` 的生命周期位置

`FSDP::pre-backward` 是 autograd 生命周期里的调度入口。它覆盖的 CPU 区间可能包含 hook 调度、状态切换、stream/event 等待和 collective enqueue，不能把整个区间都算成 NCCL 执行时间。

![](https://pic4.zhimg.com/v2-4cae86a08b11e8ac38cf8c251a0973ef_r.jpg)

典型触发链如下：

1. forward 返回后，FSDP 在 `requires_grad=True` 的输出 tensor 上注册 pre-backward hook。
2. autograd 首次把梯度传回该模块输出时，调用 `_pre_backward()`。
3. FSDP 将状态切到 `PRE_BACKWARD`，并注册 root backward final callback。
4. 当前 param group 执行 pre-backward unshard，也就是参数 AllGather。
5. 调度器按反向顺序或显式配置，预取下一待反向模块的参数。
6. 当前层参数就绪后，autograd 才继续执行该层 backward compute。

`_pre_backward()` 必须幂等。一个模块可能有多个输出，也可能被多条 autograd 路径触发；幂等保护避免重复 unshard。较新的 FSDP2 实现还用 `saved_tensors_hooks` 覆盖一种边界：loss 依赖模块保存的中间 tensor，而不是直接依赖模块输出时，访问 saved tensor 也能先触发参数准备。[^2]

整轮 backward 结束后，root final callback 统一补尾：复位 training state、清理 post-forward order，并等待或清理尚未完成的 ReduceScatter event。它负责整轮 backward 的收尾，不属于某一层的局部通信。

### 6. 配置如何改变显存、通信与重算

### 6.1 `reshard_after_forward=False`

前向后保留完整参数，反向前不再需要第二次 AllGather。单层从 3 次 collective 变成 2 次，但完整参数会跨过 forward/backward 间隔常驻显存。适合显存有余量、反向前 AllGather 明显暴露的场景。

### 6.2 梯度累积

FSDP2 可通过 `set_requires_gradient_sync(False)` 跳过 accumulation step 的梯度同步，相当于 FSDP1 的 `no_sync`。若同时使用 `set_reshard_after_backward(False)`，下一轮前向也可复用完整参数，进一步减少 AllGather；代价仍是显存。

### 6.3 HSDP / HYBRID_SHARD

HSDP 使用二维 device mesh。shard 维度内仍执行 AllGather 和 ReduceScatter，replicate 维度还可能追加 AllReduce。纯 FSDP 的“每层 2 AG + 1 RS”不能直接套到 HSDP，必须按 mesh placement 和 process group 分开统计。

### 6.4 Activation checkpointing

checkpoint 会在 backward 中重算 forward。checkpoint region 最好落在一个 FSDP unit 内，否则 recompute 与 unshard 的边界容易错位，可能增加参数驻留时间或重复通信。判断是否重复 AllGather，要看实际 NCCL kernel 和参数生命周期，不能只数 forward op。

### 7. 案例：28 层模型的一轮 FSDP2 执行

把前面的机制放进一个具体场景：模型有 28 个 Decoder Layer，每层独立成为一个 FSDP unit，外层还有 root unit；参数沿 8 张卡分片，启用 mixed precision、forward prefetch 和默认重分片，不使用 CPU offload。沿着一次训练迭代，可以看到下面这条完整链路。

1. **静态状态**：每个 rank 只保存各层 1⁄8 的参数 shard，以及与这些参数对应的 optimizer state；此时没有完整层参数常驻显存。
2. **前向逐层展开**：进入某个 Decoder Layer 前，8 个 rank 通过 AllGather 交换参数 shard，每个 rank 临时得到该层完整参数，然后执行本地 forward。
3. **前向完成后重分片**：该层 forward 结束，完整参数被释放，只保留原来的 1⁄8 shard；与此同时，forward prefetch 可以提前准备下一层参数，让通信与当前层计算重叠。
4. **反向从第 27 层开始**：梯度流回某层前，`FSDP::pre-backward` 触发该层参数 AllGather。参数就绪后，autograd 才计算 input gradient 和参数梯度。
5. **梯度规约并重新分片**：一层 backward 完成后，ReduceScatter 对完整参数梯度做跨 rank 求和，并让每个 rank 只留下自己负责的 1⁄8 gradient shard，供 optimizer step 使用。
6. **整轮事件数量闭合**：这个案例的一个物理 ProfilerStep 中有 57 个 AllGather kernel 和 29 个 ReduceScatter kernel，可由 28 层的前向与反向通信以及 root unit 解释。CPU/GPU 两侧 annotation 可能重复记录同一 collective，因此事件名称出现次数会比物理通信次数多一倍。

> **概念边界**：`FSDP::pre-backward` 是 autograd 调度区间，不是一颗 NCCL kernel。它可以包含 hook、状态切换、stream/event 等待和 collective enqueue；判断通信执行时间时，需要回到 GPU timeline 上的真实 NCCL kernel。

### 8. 从案例推广到其他 FSDP 配置

28 层、8-way shard 只是一个便于观察的实例，不是固定公式。FSDP 的基本机制始终相同：模型状态平时分片存放，计算某个 unit 时临时收齐参数，反向结束后再把梯度规约并切回 shard。改变模型层数会改变 unit 数量，改变 shard world size 会改变每个 rank 的持有比例，改变 wrap 边界则会同时改变 collective 次数、单次消息大小和完整参数的峰值驻留量。

理解一套 FSDP 配置，可以依次看五个问题：**状态分在哪里、unit 怎样划分、完整参数保留多久、下一份参数何时预取、梯度何时同步**。在这个基础上，mixed precision 改变通信与临时参数的字节数，activation checkpointing 用重算换激活显存，CPU offload 改变数据驻留位置，梯度累积改变同步频率，HSDP 则在 shard 维度之外增加 replicate 维度。评价效果时要同时看峰值显存、暴露通信、重算开销和 step time，这四项共同描述 FSDP 的实际成本。
