这是一场比较典型的底层 AI Infra / 算子岗位技术面：项目只是入口，后面很快会落到 CUDA 编程模型、GEMM 优化、性能分析方法和 Attention 算子理解上。

### 1. CUDA Graph：不只问“减少 launch overhead”

第一个技术问题是 CUDA Graph 的基本机制、创建方式和使用场景。

比较完整的回答至少要包括：先 capture 一段固定执行路径，再实例化并 replay；它主要减少 CPU 侧 launch 开销，适合 decode 这类 kernel 短、数量多、执行模式稳定的场景。

随后会追问约束：

- 执行拓扑和算子序列要相对固定；
- shape / batch 通常需要落在预先 capture 的范围内；
- 相关内存地址、生命周期和 stream 使用不能随意变化；
- capture 期间要避免破坏 capture 的 host-device 同步、动态分配等行为；
- 实际工程里还要考虑多条 graph、warmup、fallback 和正确性回归。

这里的教训是：不能把 CUDA Graph 和某个特定推理库的融合实现混为一谈。前者是 CUDA 的执行图机制，后者可能只是框架层的额外优化路径。

### 2. 小 M GEMM：项目题重点在定位和取舍

面试官让我展开一个小 M 场景下的 GEMM 优化。我的主线是：

1. 先用系统级 profiling 对不同 shape 做对比；
2. 发现小 M 时耗时没有随有效计算量明显下降；
3. 回看实现，确认默认 tile 对小 M 利用率很低；
4. 结合 dtype、确定性和数值一致性要求，选择不同实现路径；
5. 不满足条件时保留 fallback；
6. 用正确性和性能测试验证。

这类题面试官更看重的不是“我写了一个 kernel”，而是你能否说明：

- baseline 是什么；
- 什么 shape、dtype、硬件下出现问题；
- 瓶颈来自计算、访存还是 launch / 调度；
- 为什么某个常见手段在确定性要求下不能直接用；
- 优化收益能否落到端到端，而不是只看单 kernel。

### 3. 手写 GEMM 的链路与优化方向

随后被问到：如果手动实现 GEMM，完整的数据路径和优化思路是什么。

比较稳的回答框架应该是：

> 先根据 shape、dtype、GPU 架构和瓶颈做分解；再设计 CTA / warp / thread tile；让数据从 global memory 协同加载到 shared memory，完成复用后进入寄存器和 MMA 累加，最后处理 epilogue 并写回。优化时围绕访存、计算、并行度和同步开销逐层展开。<br>

可以继续展开：

- 全局内存合并访问与向量化加载；
- shared memory 布局、bank conflict 和数据复用；
- register tile、warp tile、CTA tile 的选择；
- copy-compute overlap、pipeline stage；
- Tensor Core / WGMMA / TMA 等硬件能力；
- epilogue fusion，减少中间结果回写；
- 小 shape、尾块和不同 dtype 的专门路径。

这部分我回答得不够聚焦，提到了很多关键词，但链路没有足够完整。后续应该把“数据怎么搬、谁来算、什么时候同步、哪个指标证明瓶颈”练成固定回答。

### 4. Profiling：Nsight Systems 和 Nsight Compute 的分工

面试中还问了常用 profiling 工具和判断瓶颈的指标。

我的理解是：

- Nsight Systems：看端到端时间线，包括 CPU launch、kernel gap、prefill / decode 占比、NCCL、通信与计算 overlap。
- Nsight Compute：锁定热点 kernel 后，再看单 kernel 的 memory / compute 限制、occupancy、warp stall、cache / DRAM 吞吐、指令和访存行为。

这个岗位不需要只会背指标名称，但要能讲出从全局到局部的定位顺序：

> 先找端到端最大开销和热点 kernel，再判断是计算受限还是访存受限，最后结合 stall、吞吐和并行度决定优化方向。<br>

### 5. 图优化、国产卡算子库与 Attention

后半程的问题覆盖了图优化和国产卡算子库：如何识别可融合的子图、融合后如何处理旧节点和无效节点、哪些情况应该直接调用高性能库、哪些 dtype 或特殊 shape 需要自己写 kernel。

Attention 部分从 MHA 的计算流程问到 FlashAttention 和 Softmax：

- Attention：QKT → scale / mask → softmax → 乘 V；
- FlashAttention 的核心是分块和 online softmax，尽量避免把巨大的中间矩阵反复写回 HBM；
- Softmax 需要关注 max-subtraction 的数值稳定性，以及 max / sum 两次 reduction 带来的访存和同步成本。

这一段很能区分“听过 FlashAttention”和“理解其 I/O 优化逻辑”。我在 Softmax 的数学表达和细节上答得不够干净，这是后续最需要补的一块。

### 6. 一个意外但很实际的问题：怎么防止 AI Coding 把优化做歪

面试官还问了 AI 辅助编码的使用方式，以及如何发现 AI 为了让指标好看而偷偷改变实现语义。

这个问题其实很工程化。我的做法是先建立最小复现、固定环境和 baseline，再要求保留代码改动说明、profiling 结果、正确性结果，并在提交前 review 数据路径和端到端行为。

如果一个“GPU 优化”把部分计算搬到 CPU，或者直接用不等价的替换绕开原逻辑，单看某个 kernel 的指标可能更漂亮，但没有任何业务价值。人仍然需要负责定义约束、验证语义、做最终取舍。

### 7. 这场面试暴露的问题

这次面试给我的反馈很明确：

- 项目定位和性能优化流程能够讲出主线；
- GEMM 手写优化不能只堆概念，需要形成完整数据流；
- FlashAttention、Softmax、CUDA Graph 约束要补到底层细节；
- profiling 要能从指标进一步落到一个真实 case，而不是只说“看 stall、看 occupancy”；
- 对做过较早项目的细节要提前复习，否则追问时容易出现“做过但忘了”的状态。

整体来说，这类岗位的项目经历只是获得面试机会的门票，真正决定表现的是你能否把项目经验映射到基础能力：GPU 执行模型、内存层级、算子数据流、性能瓶颈和正确性验证。
