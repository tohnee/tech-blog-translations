同样使用 8 张 GPU，TP8、TP4＋PP2、TP2＋PP4，哪种配置能缓存更多 token？加上 CP、EP、DP，容量又会怎样变化？

这个问题可以拆成两步：**每张卡还剩多少显存可以分给 KV；一个 token 在这张卡上需要多少缓存。**

$$ \text{KV 缓存容量（token）} \approx \frac{\text{可用于 KV 的显存预算（字节）}} {\text{每个 token 在本卡上的 KV 缓存成本（字节/token）}} $$

并行策略通过两条路径影响结果：减少权重、工作区等占用，扩大分子；拆分缓存层、上下文或存储副本，缩小分母。

下面以 GLM 5.3 的 MLA＋DSA 结构为例，沿着官方 [lmsysorg/sglang:v0.5.21](https://hub.docker.com/r/lmsysorg/sglang/tags?name=v0.5.21) 镜像的实现展开。Python 代码采用该版本的原文节选，每段链接定位到函数与行号；容量示例采用 scaled FP8 KV 布局。

### 一、先算分子：给 KV 留下了多少显存

GPU 显存通常分给模型权重、KV 缓存、激活、内核工作区、通信缓冲和运行时预留。

```text
可用 KV 显存
    = 显存预算
    − 本地模型权重
    − 其他常驻占用
    − 运行时预留
```

SGLang 在加载模型后测量空闲显存，此时权重占用已经体现在测量结果中。KVCacheConfigurator._profile_available_bytes() 先读取可用显存，再计算运行时预留和 KV 预算：

因此，**凡是改变本地权重、激活或工作区的并行策略，都在改变 KV 容量的分子。** TP、PP、EP 可以通过权重分片释放空间；注意力权重复制、通信缓冲和图捕获则会消耗空间。

### 1. 主 KV 还包含量化 scale 与 RoPE

```text
RoPE：64 × 2 B = 128 B

```

### 2. DSA 还要保存 index-K

DSA 使用 indexer 选择历史位置，index-K 也占用缓存。以 128 维 FP8 index 加一个 FP32 scale 为例：

```text
index-K：128 B + 4 B = 132 B / token / index 层
```

完整分母可以写成：

```text
每 token 成本
    = 主 KV 层数 × 主 KV 单层成本
    + index 层数 × index 单层成本
    + 其他随 token 增长的缓存
```

DSA 的 top-k 选择减少 attention 的访问与计算量，主 KV 仍保存完整历史。部分层可以复用 top-k 结果，index-K 的实际分配层数则由存储优化开关决定。

### 三、TP 与 PP：一个切矩阵，一个切层

MoE 的 TP 路径也会切分专家矩阵的中间维。增加 GPU 并扩大 TP，通常会减少本地权重，为 KV 腾出更多空间。

对普通 MLA，每个 attention TP rank 仍需访问这批请求的共享 latent 历史，因此按本地层数保存完整 latent KV。**普通 TP 的 MLA 容量收益主要来自权重分片释放的显存。**

MHA/GQA 的分母则与本地 KV head 数有关：在头数允许的范围内，TP 分担 KV head。MLA 的共享 latent 缓存具有另一种存储结构，容量公式使用本地层数和 latent 宽度。

因此，PP 同时影响分子和分母：本地保存的层权重减少，需要缓存 KV 的层数也减少。

固定总卡数时，提高 PP 通常会缩小每个 stage 的 TP。每张卡负责的层更少，而每层保存的权重分片更大，需要将两者一起计算。

以 8 张 GPU、78 层为例，假设路由专家权重均匀分配：

| 配置 | 每卡层数 | 每卡专家权重份额 | 每 token KV 成本 | 固定 B 时的理论容量 |
| --- | --- | --- | --- | --- |
| TP8＋PP1 | 78 | 总量约 1⁄8 | 约 61,464 B | 1 倍 |
| TP4＋PP2 | 39 | 1⁄2 层数 × 1⁄4 分片，约 1⁄8 | 约 30,732 B | 约 2 倍 |
| TP2＋PP4 | 19–20 | 平均约 1⁄4 层数 × 1⁄2 分片，约 1⁄8 | 最重 stage 约 15,760 B | 约 3.9 倍 |

表中固定分子，展示减少 KV 层数带来的理论变化。实际容量还要代入首尾组件、注意力权重复制、量化 scale/padding 和通信工作区。PP 的协同实例由容量最小的 rank 决定，代码会对各 rank 的容量取最小值：

### 四、Prefill CP：计算切分和存储切分分别看

Prefill CP 将序列位置的计算分给不同 rank，再通过 gather 和重排提供后续层所需状态。普通 MLA/DSA 池在这一过程中重建完整 latent 历史，分母仍按本地层数和完整缓存宽度计算。

CP 对分子的影响，则要看它与 attention TP 的关系。所分析实现的派生公式为：

官方源码节选：[derive_attention_widths · runtime_context.py · L73–L78](https://github.com/sgl-project/sglang/blob/e00930c5489053f26d86b179cee0d087f846acbb/python/sglang/srt/runtime_context.py#L73-L78)

```python
def derive_attention_widths(
    *, tp_size: int, attn_cp_size: int, dp_size: int, enable_dp_attention: bool
) -> tuple:
    """Return (attn_dp_size, attn_tp_size) from the configured widths."""
    attn_dp_size = dp_size if enable_dp_attention else 1
    return attn_dp_size, tp_size // attn_dp_size // attn_cp_size
```

例如，Attention DP=1 时：

```text
TP8＋CP1 → attention TP8
TP4＋CP4 → attention TP1
```

### 五、DCP：沿上下文位置分主 KV

v0.5.21 的通用 MLA DCP 将同一请求的历史位置分给不同 rank，各 rank 对本地分片计算部分 attention，再归并结果。以 DCP4 为例：

```text
rank 0：token 0、4、8、12……
rank 1：token 1、5、9、13……
rank 2：token 2、6、10、14……
rank 3：token 3、7、11、15……
```

因此，DCP 需要区分本地物理行数和整个组的逻辑 token 空间。适用的 target MLA 池中：

```text
逻辑 token 容量 = 本地物理行数 × DCP 组宽
```

官方源码节选：[KVCacheConfigurator.logical_token_capacity · mem_cache/kv_cache_configurator.py · L319–L328](https://github.com/sgl-project/sglang/blob/e00930c5489053f26d86b179cee0d087f846acbb/python/sglang/srt/mem_cache/kv_cache_configurator.py#L319-L328)

```python
def logical_token_capacity(self, *, max_total_num_tokens: int) -> int:
    """Request tokens a pool of `max_total_num_tokens` per-rank rows holds."""
    # SWA allocators never widen under DCP.
    if self.is_hybrid_swa:
        return max_total_num_tokens
    # Target rows widen into attn_dcp_size ids; draft sizes already carry
    # loc_space_scale.
    return (
        max_total_num_tokens * get_parallel().attn_dcp_size // self.loc_space_scale
    )
```

### 六、EP：改变专家权重的保存方式

EP 按专家分配权重，MoE TP 按专家矩阵的中间维分片。核心关系可以写成：

官方源码节选：[FusedMoE.init · layers/moe/fused_moe_triton/layer.py · L407–L408](<b>http</b>s://github.com/sgl-project/sglang/blob/e00930c5489053f26d86b179cee0d087f846acbb/python/sglang/srt/layers/moe/fused_moe_triton/layer.py#L407-L408)

```python

self.intermediate_size_per_partition = intermediate_size // self.moe_tp_size
```

因此，本地路由专家权重近似为：

```text
本地路由专家权重 ≈ 本 stage 路由专家权重 / (EP × MoE_TP)
```

在固定 TP 总组宽、MoE_DP=1 时，派生关系是：

```text
MoE_TP = TP / EP
EP × MoE_TP = TP
```

这时，TP8 的专家矩阵分片与 EP8 的专家分配，都会使每卡路由专家权重约占八分之一。两者在通信、专家布局、padding 和工作区上的差异，会进一步改变可用于 KV 的预算。

**EP 主要作用于分子。** 普通 MLA 的分母继续由缓存层数、latent 宽度和 index 成本决定。

### 七、DP 与 Attention DP：把显存用来承载更多独立请求

### 普通 DP：复制整个模型实例

普通 DP 在不同 GPU 集合上运行完整模型副本，每个副本内部可以继续 TP/PP。各副本处理不同请求，也拥有各自的 KV 池。

增加一套相同配置的副本，会增加独立池的合计容量。固定总卡数、增加副本数，则会缩小每副本的 TP/PP 资源，并增加部署中的权重重复量，需要重新计算分子。

### Attention DP：把重复 latent KV 换成不同请求的 KV

普通 MLA TP8 中，八个 attention rank 保存同一批请求的 latent 历史。Attention DP 将不同请求交给不同注意力组，FFN/MoE 继续使用自身的并行组。

v0.5.21 使用 –enable-dp-attention 配合 –dp-size 配置注意力数据并行，对应参数定义为：

官方源码节选：[Parallel · arg_groups/fields/parallel.py · L163–L169](https://github.com/sgl-project/sglang/blob/e00930c5489053f26d86b179cee0d087f846acbb/python/sglang/srt/arg_groups/fields/parallel.py#L163-L169)

```python

    Arg(
```

用一个固定分子的例子看最直观：

```text
假设 8 张卡，每张卡都有容纳 N token 的 KV 空间。

普通 TP8：
8 张卡共同服务同一批请求，唯一 token 容量约为 N。

Attention DP8、attention TP1：
形成 8 个独立请求池，每个约 N，合计约 8N。
```

单条请求仍由所属池的 N 约束。实际 attention TP 缩小时，注意力权重复制和工作区也会变化，各池的 N 应按新预算计算。

这里最有用的区分是：**单实例能容纳的上下文，以及整个部署能够同时承载的唯一请求 token。** Attention DP 通过请求分配改善后一个指标。

### 八、把所有策略放回同一个公式

**B 是每卡可分给 KV 的显存字节数，b 是每个逻辑 token 在本卡承担的缓存字节数，单池容量约为 B 除以 b。**下表每种策略只列一行，比较该策略并行度增大时的变化；具体固定条件写在对应行中。

**统一比较条件：**使用相同模型、权重与 KV 精度、单卡显存预算。表内先按其他运行时占用近似相等给出方向。通信缓冲、激活、Graph 和工作区变化时，用“节省的权重显存减去新增的其他占用”计算 B 的净变化：结果为正，B 增大；为负，B 减小；为零，B 相等。

**容量判断规则：**B 增大且 b 相等，容量增大；B 相等且 b 减小，容量增大。B 与 b 同时变化时，容量倍率为“B 的变化倍率除以 b 的变化倍率”。协同实例取各 rank 的最小容量；独立请求池的合计容量按各池求和。

| 策略 | 分子 B | 分母 b | KV token 容量 |
| --- | --- | --- | --- |
| TP | 增大。<br>固定 PP、CP 和 Attention DP，增加 GPU 来扩大 TP。可切分权重的每卡份额随 TP 增大而减小，释放的显存进入 B。 | 相等。<br>普通 MLA 每卡仍按本地层保存完整 latent KV；层数、latent 宽度、KV 精度和 index 布局保持相同。 | 增大。<br>b 相等时，容量增大比例与 B 相同。可切分权重越多，TP 扩大带来的显存收益越大。 |
| PP | 增大。<br>固定每个 stage 的 TP，增加 GPU 来扩大 PP。本地层数减少，层权重占用减小；首尾组件和分层均衡程度决定各 stage 的 B。 | 减小。<br>每卡保存的 KV 层数减少。均匀分层时，主 KV 成本近似与 PP 成反比，index 成本按本地分配层数计算。 | 增大。<br>B 增大、b 减小共同扩大容量。先计算各 stage 的 B 除以 b，再取其中最小容量。 |
| CP | 减小。<br>固定总 TP 组宽、PP 和 Attention DP。CP 增大使 attention TP 减小，注意力权重的每卡份额增大；权重复制量决定 B 的减小幅度。 | 普通池相等；启用 DSA 按层分片时减小。<br>普通池重建完整历史；层分片池的主 KV 层数由 L 减为 ceil(L/CP)+1，index 项按实际分配层数另计。 | 普通池减小。<br>DSA 层分片池中，b 的降幅大于 B 的降幅时容量增大，两者降幅相等时容量相等，B 的降幅更大时容量减小。 |
| DCP | 近似相等；启用 Q 投影复制时减小。<br>固定 TP、PP，扩大 DCP 组宽 c。Q 投影复制增加本卡权重占用，新增权重的字节数决定 B 的减小量。 | 减小。<br>target 主 KV 按位置分片，每逻辑 token 的这部分成本缩为原来的 1/c；Draft 等复制项的成本相等。因此总 b 减小，复制项越多，降幅越小。 | B 近似相等时增大。<br>全部缓存均可分片时，容量接近原来的 c 倍。启用 Q 复制后，b 的降幅大于 B 的降幅时增大，降幅相等时相等，反之减小。 |
| EP | 固定总 TP 组宽时近似相等；增加 GPU 且保持 MoE TP 时增大。<br>前者的 EP 与 MoE TP 乘积保持相同，路由专家权重的每卡份额相同；后者的每卡专家数减少。 | 相等。<br>普通 MLA 的缓存层数、latent 宽度、KV 精度和 index 分配保持相同。 | 固定总 TP 组宽时近似相等；增加 GPU 且保持 MoE TP 时增大。<br>dispatch/combine 缓冲、共享专家和冗余专家占用的变化，再计入 B。 |
| 普通 DP | 增加 GPU 来复制完整实例时相等；固定总卡数时减小。<br>前者每副本沿用相同 TP/PP；后者增加副本数 d 会缩小每副本 TP，使每卡权重份额增大。 | 相等。<br>保持 PP 和缓存布局，各副本每个 token 的 KV 层数和 latent 宽度相同。 | 增加 GPU 时：单池相等，合计增大。<br>固定总卡数时：单池减小；d×B 增大时合计增大，减小时合计减小，相等时合计相等。 |
| Attention DP | 减小。<br>固定总 TP 组宽、PP、CP 和 MoE DP，扩大 Attention DP。attention TP 减小，注意力权重的每卡份额增大；MoE 权重份额保持相同。 | 相等。<br>每个注意力组保存自己的请求，单个请求的每 token 存储结构保持相同。 | 单池减小。<br>设注意力组数为 D，D×B 增大时合计增大，减小时合计减小，相等时合计相等。若 B 近似相等，合计容量随 D 近似线性增大。 |
| PD 分离 | 扩容前后，原有各 rank 的 B 相等。<br>以 1P1D 扩成 2P1D 为例，新增一套相同 P，原有 P、D 各自的权重和显存预算保持相同。 | 扩容前后，各角色的 b 相等。<br>P、D 分别沿用原缓存布局；同一种角色的单池容量相等。 | P 侧合计增大，D 侧合计相等。<br>新增相同 P 后，P 侧池容量合计约翻倍。统计唯一历史量时，将传输阶段同一请求的缓存副本去重。 |

**GLM 5.3 的版本口径：**CP 行中的层分片沿用前文 v0.5.21 的 PD prefill、interleave、Mooncake 和 PP1 条件；DCP 行说明通用 target MLA 的位置分片机制，本文 GLM 5.3 的 v0.5.21 DSA 算例使用 DCP1。

**固定 8 卡的例子：**从 TP8＋PP1 换成 TP4＋PP2，主要分片权重的每卡份额近似相等，KV 层数从 78 变为 39，b 约减半。其他占用近似相同时，B 近似相等，容量约翻倍。这一结果来自本地 KV 层数减少。

这些并行组会复用 GPU。例如 TP4＋PP2＋CP4 使用 8 张卡，每个 stage 的 TP4 组同时承担 CP4；Attention DP 和 EP 也各有派生关系。计算资源规模时，先画出进程和组的对应关系，再代入容量公式。

Attention TP、MoE TP 与 DCP 的实际组宽统一在派生函数中计算：

```python

    "attn_dp_size": attn_dp_size,
    # `attn_dp_size` already accounts for disabled DP attention.

        tp_size=tp_size,
        attn_cp_size=attn_cp_size,
```

PD 部署也沿用这一方法：P 池按 prefill 角色计算，D 池按 decode 角色计算。1P1D 扩成 2P1D，会增加 P 侧计算资源与独立池；D 侧的容量由其自身预算和存储布局决定。HiCache 等主存层级则另行统计逻辑历史量、GPU 驻留量和传输成本。

实际选配置时，依次记录三个量即可：

1. **分子**：加载后的空闲显存、运行时预留和固定工作区。
2. **分母**：本地缓存层数、主 KV / index 布局，以及存储副本的归属。
3. **容量单位**：单卡物理池、协同组逻辑容量，或多个独立请求池的合计容量。

将这三项写清，再结合手工上限与分页对齐，就能解释大部分“并行度变了，KV 池为什么随之变化”的现象。
