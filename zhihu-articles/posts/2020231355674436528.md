## 一、训练主循环与前反向调用链

### 1.1 分布式环境初始化：initialize_megatron

**设计哲学与核心问题**

分布式训练框架的初始化要解决一个根本问题：在 N 张卡上，如何让每张卡知道自己在整个并行拓扑里的位置——它属于哪个 TP 组、哪个 PP 组、哪个 DP 组，以及和哪些卡通信？

Megatron 的答案是在训练开始前一次性切好所有并行维度的通信组，存入全局变量，后续所有模块直接通过 `mpu.get_xxx_group()` 查询，不需要在运行时动态协商。这个设计的好处是通信组的构建代价只付一次，查询是 O(1) 的全局变量读，不会在训练的热路径上引入任何额外开销。

对比 VERL 在 FSDP 后端集成 Ulysses 时"两套独立 Mesh、互不干涉"的设计，Megatron 的思路更集中——所有并行维度都在 `initialize_model_parallel` 这一个函数里统一切出来，拓扑关系在初始化时就已经完全确定。

**实现细节**

初始化的核心工作集中在 `finish_mpu_init → _initialize_distributed` 这条链路里：

```python
def finish_mpu_init():
    _initialize_distributed(get_embedding_ranks, get_position_embedding_ranks)
    _set_random_seed(args.seed, ...)
```

`_initialize_distributed` 完成两件事：调用 `torch.distributed.init_process_group` 初始化底层 NCCL 通信后端，然后调用核心函数 `mpu.initialize_model_parallel`：

```python
mpu.initialize_model_parallel(
    args.tensor_model_parallel_size,
    args.pipeline_model_parallel_size,
    context_parallel_size=args.context_parallel_size,
    expert_model_parallel_size=args.expert_model_parallel_size,
    order='tp-cp-ep-dp-pp',
    ...
)
```

`order='tp-cp-ep-dp-pp'` 决定了全局 rank 的排列方式——从内到外，TP 在最内层（要求最高带宽），CP 紧随其后，DP 在外层（跨节点 AllReduce 可接受更高延迟），PP 在最外层。rank 排列越靠内层，同组 rank 编号越连续，物理上越倾向于在同一 NVLink 域内，通信延迟越低。

![](https://pica.zhimg.com/v2-faed5965c4d69a55f48eee337c3f3b7a_r.jpg)
*【图示】rank 拓扑排列*

`initialize_model_parallel` 内部用 `RankGenerator` 的正交分组算法，根据各维度大小和 `order`，一次性切出所有通信组并存入全局变量，供后续 `mpu.get_context_parallel_group()` 等接口查询。

**本文只关注纯 DP 场景，`cp=tp=pp=1`，此时 DP 组覆盖全部 rank。**

每张卡还通过 `torch.cuda.set_device(args.local_rank)` 显式绑定对应 GPU。这是 Megatron 不依赖 `CUDA_VISIBLE_DEVICES` 而直接用 `local_rank` 管理设备的方式，比 FSDP 通过 `DeviceMesh` 抽象管理设备更底层、更显式，也更容易在多机多卡场景下精确控制卡间的亲和关系。

### 1.2 模型与优化器初始化：setup_model_and_optimizer

**设计哲学与核心问题**

分布式训练里模型和优化器的初始化要解决两个紧密耦合的问题：模型参数如何在卡间分布（由 DDP/FSDP wrapper 决定），以及优化器状态如何和参数分布保持一致（由分布式优化器决定）。

**Megatron 的设计选择是在初始化阶段统一建立这两者的绑定关系。**

具体来说，DDP wrapper 在初始化时通过 `_ParamAndGradBuffer` 完成 `grad_data` 和 `param_data` 两块 buffer 的分配，以及 bucket 的划分；分布式优化器在初始化时根据 `grad_data` 的分片范围确定自己负责哪些参数，同时建立与 `param_data` 的映射关系。

**两者共享同一个 `_ParamAndGradBuffer` 实例**——`grad_data` 是梯度通信的内存中枢，`param_data` 是参数通信的内存中枢，整个优化器状态的内存布局在初始化时完全确定，训练中不再有动态分配。

**实现细节**

`setup_model_and_optimizer` 分三步完成初始化：

第一步，构建模型并用 DDP wrapper 包裹：

```python
model = [DP(config=config, ddp_config=ddp_config, module=model_chunk, ...)
         for model_chunk_idx, model_chunk in enumerate(model)]
```

这里的 `DP` 根据配置可以是 Megatron 自己的 `DistributedDataParallel`、PyTorch 的 FSDP2，或自定义 FSDP。**纯 DP 场景下走 Megatron 自己的 DDP。**

第二步，构建优化器：

```python
optimizer = DistributedOptimizer(
    *optimizer_args,
    data_parallel_group=mpu.get_data_parallel_group(with_context_parallel=True),
    ...
)
```

注意这里传入的 `data_parallel_group` 用了 `with_context_parallel=True`。纯 DP 场景下 `cp=1`，这个参数没有实际影响；**但一旦开启 CP，这里传入的 group 就会变成 `dp×cp` 的扩展 DP 组**——CP 对优化器的影响正是从这个参数注入的，第二篇会重点分析。这个"提前预留的扩展点"是 Megatron 把 CP 原生编码进框架的体现之一。

这也是为什么要以 DP 视角为 CP 做铺垫的原因之一——**从本质上讲，DP 和 CP 都是数据维度的切分，一个切 Batch，一个切 Seq。**除了在激活值方面的显存节省之外，**两者同样都会影响分布式优化器的显存占用。**

![](https://pic2.zhimg.com/v2-8dbf54aad22b7175c869670cbcb4b5fb_r.jpg)
*【图示】DDP wrapper 与分布式优化器的初始化关系*

分布式优化器的初始化在这一步完成参数分片映射的建立：根据 `_ParamAndGradBuffer` 中 `grad_data` 的分片范围，确定当前 rank 负责哪些参数；为每个 bf16/fp16 参数分配对应的 fp32 主参数副本（`shard_main_param`），fp32 参数则直接切片视图，无需额外副本。Adam 的 m/v 状态也在这时预分配，**整个优化器状态的内存布局在初始化时完全确定，训练中不再有动态分配。**

第三步，加载 checkpoint（如有），从 checkpoint 恢复模型权重和优化器状态，或将 `args.iteration` 置为 0 从零开始训练。

### 1.3 训练流程：从 train_step 到梯度归约

**设计哲学与核心问题**

Megatron 的训练循环要解决的核心问题是：如何让多个 micro_batch 的前反向高效流水，同时保证梯度累积的正确性，以及梯度归约和参数更新的时序不出错。

设计上有两个关键取舍：

- 第一，梯度累积通过 `no_sync` 控制，前 N-1 个 micro_batch 不触发跨卡通信，梯度在本卡叠加**，最后一个 micro_batch 结束时统一触发**——这样通信只发生一次，避免了每个 micro_batch 都触发通信的开销；
- 第二，`finalize_model_grads` 把梯度归约的收尾工作（等待异步通信完成、LayerNorm AllReduce、梯度缩放）集中在一个函数里，职责边界清晰，便于在 PP 等复杂场景下扩展。

**实现细节**

初始化完成后进入训练循环，每个 step 的核心是 `train_step`：

```python
losses_reduced = forward_backward_func(
    forward_step_func=forward_step_func,
    data_iterator=data_iterator,
    model=model,
    num_microbatches=get_num_microbatches(),
    ...
)
optimizer.step()
opt_param_scheduler.step(...)
```

![](https://picx.zhimg.com/v2-9ca5e0d7957d4092c19fb4ef0ff45629_r.jpg)
*【图示】训练流程*

`forward_backward_func` 根据 PP 配置选择不同实现，无 PP 时走 `forward_backward_no_pipelining`：

```python
total_num_tokens = torch.zeros([], dtype=torch.int, device="cuda")
with no_sync_func():
    for i in range(num_microbatches - 1):
        output_tensor, num_tokens = forward_step(...)
        total_num_tokens += num_tokens
        backward_step(...)

# 最后一个 microbatch 在 no_sync 上下文外执行，触发梯度同步
output_tensor, num_tokens = forward_step(...)
total_num_tokens += num_tokens
backward_step(...)

finalize_model_grads([model], total_num_tokens if calculate_per_token_loss else None)
```

`no_sync` 块外的最后一个 micro_batch 反向传播时，bucket 梯度通信异步发起；`finalize_model_grads` 随后等待这些通信完成，并补充做 LayerNorm/embedding 等特定通信域的梯度同步。

**两者是"发起"和"等待+收尾"的关系，不是同一件事。**

框架层的 `forward_step` 调用用户定义的 `forward_step_func`，得到模型输出和 loss 函数，再调用 loss 函数计算 loss 值：

```python
output_tensor, loss_func = forward_step_func(data_iterator, model)

if parallel_state.is_pipeline_last_stage():
    outputs = loss_func(output_tensor)
    if len(outputs) == 3:
        output_tensor, num_tokens, loss_reduced = outputs
        if not config.calculate_per_token_loss:
            output_tensor /= num_tokens        # per-token 平均 loss
            output_tensor /= num_microbatches  # 梯度累积归一化
```

`loss_func` 返回三元组 `(loss_sum, num_tokens, metadata)`。此后的归一化行为取决于 `calculate_per_token_loss` 的配置：

`calculate_per_token_loss=False`（默认）时，框架层在这里做两步归一化：`loss_sum / num_tokens` 得到当前 micro_batch 的 per-token 平均 loss，再除以 `num_microbatches` 做梯度累积归一化。**反向传播的起始梯度量级由此确定，是后续梯度推导的源头。**

`calculate_per_token_loss=True` 时，这两步归一化**不在这里做**——`output_tensor` 保持 `loss_sum` 的原始量级直接进入反向传播，**归一化推迟到 `finalize_model_grads` 里用全局 token 数做精确缩放。**这种模式的目的是在各卡 token 数不均等时（比如开启 CP 后序列被切分）仍能得到正确的 per-token 平均梯度，简单除以 `num_tokens`（单卡局部值）会引入误差。

`backward_step` 以**归一化后的 loss 为起点触发反向。**非 PP 场景下上游梯度为 None，一定会走 `grad_scale_func`：

```python
if output_tensor_grad[0] is None and config.grad_scale_func is not None:
    output_tensor[0] = config.grad_scale_func(output_tensor[0])
    # config.grad_scale_func = optimizer.scale_loss = loss_scale × loss

torch.autograd.backward(output_tensor[0], grad_tensors=output_tensor_grad[0])
```

`grad_scale_func` 是 fp16/bf16 训练的 loss scaler，对 loss 再乘一个缩放系数防止 fp16 下溢。反向传播的实际起点是 `loss_scale × mean(token_loss) / num_microbatches`，初始梯度为 1，链式法则往下传。

![](https://pic3.zhimg.com/v2-88b5f6ef1cba598da089bd6aff144d44_r.jpg)
*【图示】默认场景loss归一化链路*

整个前反向链路的职责划分非常清晰：

- 用户 `forward_step_func` 负责模型前向和 loss 定义；
- 框架层 `forward_step` 负责 loss 归一化；
- `backward_step` 负责触发反向并应用 loss scaling；`finalize_model_grads` 负责梯度归约的收尾。

每个环节职责单一，**用户只需要关注 `forward_step_func` 和 `loss_func` 的实现**，其余由框架透明处理。这种"用户定义 what，框架负责 how"的分层设计，是 Megatron 可以在不修改用户代码的情况下支持 PP/CP 等复杂并行策略的基础。

### 小结

训练主循环的设计围绕一个核心原则：**职责单一，层次分明**。

初始化阶段，通信组、buffer 分配、优化器状态的内存布局全部在启动时一次性确定，训练热路径上没有任何动态协商或内存分配。`_ParamAndGradBuffer` 是这个设计的枢纽——它在初始化时同时服务于 DDP（划定 bucket、分配 `grad_data`）和分布式优化器（建立分片映射、分配 `param_data`），两者通过共享同一个实例在初始化时完成绑定，训练中各司其职。

训练循环阶段，`forward_backward_no_pipelining` 把多 micro_batch 的前反向、梯度累积、通信触发的逻辑封装在一起，用户看到的只是一个 `train_step` 调用。loss 的归一化行为由 `calculate_per_token_loss` 控制，两条路径（框架层归一化 vs 推迟到 `finalize_model_grads` 精确缩放）服务于不同的训练场景，但对上层用户完全透明。

这种"初始化时确定结构，训练时只执行"的设计，是 Megatron 能在不修改用户代码的前提下支持 PP/CP 等复杂并行策略的基础——**第二篇引入 CP 时，变化的只是通信组的构成和 `calculate_per_token_loss` 的归一化路径，训练循环本身的框架不需要任何改动。**

## 二、DDP：bucket 设计与梯度通信

分布式训练里梯度通信有两个相互叠加的矛盾：一是 kernel launch 的固定开销——每触发一次 NCCL 通信，CPU 侧有几十微秒的固定启动代价，如果参数很小，实际传输量可能比启动开销还少，大量时间都浪费在"发起通信"本身上；二是计算被通信阻塞——如果每个参数的梯度算完就同步等待 AllReduce 完成，GPU 在网络传输期间没有后续计算可做，只能空转，计算流水线被频繁打断。

Megatron DDP 用**两级打包**同时解决这两个问题。第一级，把所有参数的梯度打包进一块连续的 `grad_data` buffer，消除参数间的内存碎片，让通信操作直接在大块连续内存上执行——原来 1000 个参数触发 1000 次 launch，现在打包后可能只触发几十次，launch 固定开销被大幅摊薄。第二级，把 `grad_data` 按大小切成若干 bucket，反向传播中一旦某个 BucketGroup 内所有参数的梯度就绪，立即**异步**发起该组的通信，不等后续 bucket——`start_grad_sync` 把通信请求扔进 NCCL stream 后立刻返回，反向传播继续往前计算下一层的梯度，上一个 bucket 的通信在后台并行进行。这样计算和通信在时间轴上交错，GPU 不需要停下来等网络，流水线不再断开。

对比 PyTorch 原生 DDP 以参数为粒度注册 hook、按参数触发通信的方式，Megatron DDP 以 `grad_data` 的连续内存区间为操作单位，通信粒度更粗、带宽利用率更高，同时也为分布式优化器提供了以连续 buffer 为中枢的内存基础。

### 2.1 双 buffer 分配与两阶段初始化

**两块独立 buffer：param_data 与 grad_data**

**`_ParamAndGradBuffer` 是梯度和参数的双 buffer 管理类**——同时管理 `grad_data`（梯度）和 `param_data`（参数，仅分布式优化器模式下分配）两块连续内存，是 DDP 和分布式优化器共同依赖的内存基础设施。

`_ParamAndGradBuffer` 在初始化时分配两块独立的连续内存：

```python
# 只有启用分布式优化器时才分配 param_data
if self.ddp_config.use_distributed_optimizer:
    self.param_data = torch.zeros(self.numel, dtype=self.param_dtype, ...)

# grad_data 始终分配
self.grad_data = torch.zeros(self.numel, dtype=self.grad_dtype, ...)
```

`grad_data` 存放梯度，`grad_dtype` 可以是 fp32（`grad_reduce_in_fp32=True` 时）或参数本身的精度，始终分配；

**`param_data` 存放参数，只在分布式优化器模式下才分配**——此时参数本身也被"搬进"连续 buffer，all-gather 可以直接在 `param_data` 上原地执行，不需要额外拷贝。

两块 buffer 的元素数（`numel`）相同，但当 `grad_reduce_in_fp32=True` 时 `grad_dtype=fp32` 而 `param_dtype=bf16`，两者实际占用的字节数并不相等。此外，参数按 `(param_dtype, grad_dtype)` 的组合分组，不同组合各自分配独立的 buffer 对，并不是全模型共用唯一的一对。

**两阶段初始化：先算索引，再分配内存**

buffer 初始化分两遍扫描，避免逐参数追加导致的内存碎片：

**第一遍**：逆序遍历参数（近似反向传播顺序），只计算每个参数在 buffer 中的位置索引 `(start, end, bucket_id)`，记录进 `param_index_map`，算出 buffer 的总元素数 `self.numel`。这一遍不分配任何内存。

**第二遍**：`torch.zeros(self.numel)` 一次性分配好完整内存，再遍历参数，把 `param.data` 和 `param.main_grad` 分别绑定到 `param_data`、`grad_data` 中对应的视图切片：

```python
# param.data → param_data 的视图（分布式优化器模式下）
param.data = self._get(param.data.shape, param_start_index, buffer_type=BufferType.PARAM)

# param.main_grad → grad_data 的视图（始终）
param.main_grad = self._get(param.data.shape, param_start_index, buffer_type=BufferType.GRAD)
```

`param.main_grad` 是 `grad_data` 的视图，不是独立内存。反向传播时 hook 里 `param.main_grad.add_(param.grad.data)` 直接写进这块共享内存，通信操作直接作用在 `grad_data` 上，全程零拷贝。

### 2.2 bucket 划分与对齐 padding

DDP 做梯度通信的最小单位不是单个参数，而是 bucket。这个设计解决两个问题：

- 第一，单参数触发一次通信的 kernel launch 开销远超实际通信量，打包成大块才能让 NCCL 跑满带宽；
- 第二，反向传播是逐层计算的，如果等所有参数梯度都就绪再统一通信，靠近输入层的梯度会白白等待——按 bucket 分批、就绪一个通信一个，才能让通信隐藏在计算后面。

**逆序排列与切桶规则**

参数按逆序遍历（`params[::-1]`），近似反向传播的计算顺序，让靠近输出层的参数排在 buffer 前面，先就绪、先触发通信。切桶规则直接：累积元素数超过 `bucket_size` 就切出一个新 bucket，切桶发生在当前参数完整放入之后——

```python
param_end_index = param_start_index + this_numel
self.param_index_map[param] = (param_start_index, param_end_index, bucket_id)

if (param_end_index - bucket_start_index) >= bucket_size:
    _update_bucket_metadata(param_end_index)  # 以当前参数末尾为 bucket 终点
```

每个参数完整属于某一个 bucket，不会跨 bucket 分割。bucket 实际大小可能略超 `bucket_size`——这是有意接受的代价，均匀性让位于完整性。

`bucket_size` 的默认值在 `get_model` 中按需设置：若用户未通过 `--ddp-bucket-size` 或 `--ddp-num-buckets` 显式指定，则以 DP world size 为基准计算下限：

```python
if ddp_config.bucket_size is None:
    ddp_config.bucket_size = max(
        40000000, 1000000 * parallel_state.get_data_parallel_world_size()
    )
```

DP 规模越大，bucket 下限越高——卡越多，每次通信的参与方越多，消息越大才能跑满带宽，摊薄 kernel launch 的固定开销。进入 DDP `__init__` 后，有三种情况会将 `bucket_size` 覆盖为 None，退化为单桶：

- `overlap_grad_reduce=False` 时分桶失去意义（没有 overlap 就没有流水，一个大桶反而通信次数更少）；
- 非首 PP stage 时（`pipeline_model_parallel_rank > 0`）；
- 以及调用方显式传入 `disable_bucketing=True` 时。

前两种覆盖作用在 `ddp_config` 对象本身，对后续所有逻辑可见；第三种只影响 `self.bucket_size`，`ddp_config.bucket_size` 原值不变。

**对齐 padding：分布式优化器的隐性前提**

分布式优化器的 reduce-scatter 要求 buffer 能被 `dp_world_size` 整除——每张卡分到严格等大的分片，才能保证各卡负责的参数范围不重叠。但按参数边界自然切出来的 bucket，其大小是随机的，无法保证整除。解决方案是 padding：

- **参数起始地址**对齐到 64 elements（128 字节），满足 cuBLAS GEMM 的访存对齐需求；
- **bucket 结束地址**对齐到 `lcm(dp_size, 128)`，直接保证 bucket 大小被 `dp_size` 整除；开启 `pad_buckets_for_high_nccl_busbw` 时进一步对齐到 `lcm(dp_size, 128, 2^16)`，让 NCCL ring 算法中每个 rank 的消息大小对齐到 2^16，维持高总线带宽。

两层 padding 共同保证了 `self.numel % dp_world_size == 0`。代价是 buffer 里参数之间存在空洞，`numel_unpadded ≤ numel`，空洞不属于任何参数，是纯粹的对齐填充。非分布式优化器模式下无需 padding，`numel == numel_unpadded`。

`shared_embedding` 参数（PP 首尾 stage 共享的 embedding）会被强制分配到独立 bucket。原因在于 PP 两端各自维护一份 embedding，reduce-scatter 后两端的分片范围必须完全对应，才能在 embedding AllReduce 之前完成 DP 梯度归约；若混入其他参数，分片边界就对不上。

### 2.3 backward hook 与 BucketGroup 就绪机制

bucket 分好了，但通信触发的时机需要精确控制——太早（参数梯度还没算完）会通信错误数据，太晚（等所有参数都就绪）就失去了 overlap 的意义。Megatron 的答案是 backward hook + BucketGroup 就绪计数的组合。

**hook 的三件事**

DDP 初始化时为每个需要梯度的参数注册 backward post-hook，梯度计算完成后自动触发：

```python
def hook(*unused):
    if param.grad is not None and not param.grad_added_to_main_grad:
        param.main_grad.add_(param.grad.data)  # 1. 累加进 grad_data 视图
    param.grad = None                           # 2. 释放临时梯度内存
    if self.ddp_config.overlap_grad_reduce:
        self.param_to_bucket_group[param].register_grad_ready(param)  # 3. 标记就绪
```

`param.grad` 只是反向传播写入的临时中转，**hook 触发后立刻累加进 `param.main_grad`（`grad_data` 的视图）并置 None**——梯度的实际归宿始终是 `grad_data` 的连续内存，`param.grad` 的生命周期极短，这样设计的好处是显存峰值更低：临时梯度不需要和 `grad_data` 同时存在。

**BucketGroup 级就绪判断：为什么不是 bucket 级**

`register_grad_ready` 的就绪计数以 BucketGroup 为粒度，而不是单个 bucket：

```python
def register_grad_ready(self, param):
    if self.is_last_microbatch:
        self.params_with_grad.add(param)
        if len(self.params_with_grad) == len(self.params):  # 全组参数就绪
            self.start_grad_sync()
```

一个 BucketGroup 可以包含多个 bucket，**合并后用 `_coalescing_manager` 发起一次 NCCL 调用。**粒度选在 BucketGroup 而不是单 bucket，是为了进一步减少 NCCL 调用次数——多个小 bucket 合并后，通信启动开销再次摊薄。

**`is_last_microbatch` 控制梯度累积窗口**

梯度累积的 N 个 micro_batch 里，前 N-1 个不应该触发通信——梯度还没累积完，通信了也是错的。`no_sync()` 通过 `is_last_microbatch` 标志实现这个控制：

```python
@contextmanager
def no_sync(self):
    for bucket_group in self.bucket_groups + ...:
        bucket_group.is_last_microbatch = False
    try:
        yield
    finally:
        for bucket_group in ...:
            bucket_group.is_last_microbatch = True
```

`is_last_microbatch=False` 时 `register_grad_ready` 直接返回，不记录、不计数、不通信——梯度在 `main_grad` 里静默累积。最后一个 micro_batch 退出 `no_sync` 后标志恢复，hook 重新触发计数和通信。这个设计的关键在于：梯度累积的正确性由标志保证，hook 的注册逻辑本身不需要感知当前是第几个 micro_batch。

### 2.4 梯度通信：从缩放到归约

**`gradient_scaling_factor` 为什么在通信前缩放**

梯度通信的目标是对 dp 张卡的梯度求平均。朴素的做法是先 AllReduce 求和、再除以 dp——但这意味着通信完之后还要额外做一次全局乘法。Megatron 把除法前置：通信前对 `grad_data` 原地乘以 `1/dp`，然后做 SUM，数学上等价，但省掉了通信后的缩放操作：

```python
for bucket in self.buckets:
    if bucket.gradient_scaling_factor != 1.0:
        bucket.grad_data *= bucket.gradient_scaling_factor  # 通信前原地乘 1/dp

reduce_op = ReduceOp.SUM
```

`average_in_collective=True` 时改用 `ReduceOp.AVG`，`gradient_scaling_factor=1.0` 跳过预缩放，把除法下沉到 NCCL 内部完成。

两种方式数学等价，**但 `AVG` 模式不适用于 `calculate_per_token_loss=True` 的场景**——此时 token 数在各卡间不均等，简单除以 dp 是错的，必须在 `finalize_model_grads` 里用全局 token 数做精确缩放。

**AllReduce vs reduce-scatter：和分布式优化器的协作**

是否使用分布式优化器决定了梯度通信的操作类型：

```python
if self.ddp_config.use_distributed_optimizer:
    local_data_view = shard_buffer(bucket.grad_data, dp_size)[dp_rank]
    dist_reduce_scatter_func(local_data_view, bucket.grad_data, ...)
else:
    torch.distributed.all_reduce(bucket.grad_data, ...)
```

AllReduce 让每张卡持有完整梯度，配合完整的优化器状态使用；reduce-scatter 让每张卡只保留 `1/dp` 的梯度分片，其余部分就地丢弃——这不是浪费，而是和分布式优化器的分工：每张卡只更新自己那段参数，只需要那段的梯度，多余的梯度没有意义。

![](https://pic1.zhimg.com/v2-ac06ad969e4eb5d077bc4c2a344074ac_r.jpg)
*【图示】AllReduce vs reduce-scatter 数据流*

**`finish_grad_sync` 的三条路径**

```python
def finish_grad_sync(self):
    if not self.ddp_config.overlap_grad_reduce:
        self.start_grad_sync()      # 路径1：非 overlap，同步执行
        return
    if self.ddp_config.num_distributed_optimizer_instances > 1:
        torch.cuda.default_stream().wait_stream(self.communication_stream)  # 路径2：多实例独立流
        return
    self.grad_reduce_handle.wait()  # 路径3：标准异步，等句柄
```

- 非 overlap 模式下（路径1），`finish_grad_sync` 本身就是通信的发起点，`start_grad_sync` 在这里同步调用；
- overlap 模式下（路径3），通信已经在反向传播中由 `register_grad_ready` 异步发起，`finish_grad_sync` 只是等待句柄。

两条路径是同一条梯度归约链路的两种时序安排，`finalize_model_grads` 调用 `finish_grad_sync` 是这条链路的终点，保证后续优化器 `step()` 看到的梯度是完整且同步好的。

### 2.5 参数通信：all-gather 与 forward pre-hook 链式预取

reduce-scatter 之后，**每张卡的 `param_data` 里只有自己那段 1/dp 分片是经过优化器更新的最新值，其余段还是上一轮的旧参数。**前向传播开始之前，必须把各卡的分片拼回完整参数——这是 all-gather 的职责，与 reduce-scatter 构成一对互逆操作：

```python
def start_param_sync(self, force_sync=False):
    local_data_view = shard_buffer(bucket.param_data, dp_size)[dp_rank]
    dist_all_gather_func(bucket.param_data, local_data_view, ...)
```

`local_data_view` 是当前 rank 持有的那段分片，all-gather 把所有 rank 的分片原地拼回 `param_data`，前向传播就能看到完整的新参数。

**三档配置：从同步到深度 overlap**

all-gather 的执行时机由两个开关控制，对应三种行为：

默认不开任何开关时，all-gather 同步执行——`optimizer.step()` 完成后统一发起所有 bucket 的 all-gather，全部完成后前向才能开始，GPU 在等待期间空转。

`--overlap-param-gather`（对应 `ddp_config.overlap_param_gather=True`）开启链式预取。此时 DDP 为每个 submodule 注册 forward pre-hook，前向走到哪一层，那一层的参数才被等待，同时下一层的 all-gather 已经发出去了：

```python
self.use_forward_hook = (
    self.ddp_config.use_distributed_optimizer and self.ddp_config.overlap_param_gather
)
if self.use_forward_hook:
    self.enable_forward_pre_hook()
```

注意两个条件缺一不可——链式预取依赖 `param_data` 的分片结构，而 `param_data` 只在分布式优化器模式下才分配。

`--overlap-param-gather-with-optimizer-step` 是更激进的变体，让 all-gather 和 optimizer step 本身也 overlap——在 step 执行期间就开始搬运下一轮的参数。代价是必须放弃分桶，强制退化为单桶：

```text
disable_bucketing=(model_chunk_idx > 0) or args.overlap_param_gather_with_optimizer_step
```

单桶是因为此时 all-gather 的调度时机由 optimizer step 内部控制，bucket 级别的链式预取反而会产生调度冲突。

**链式预取的实现**

`finish_param_sync` 在等待当前 bucket 完成的同时触发下一个：

```python
def finish_param_sync(self, skip_next_bucket_dispatch=False):
    if not self.param_gather_dispatched:
        self.start_param_sync()          # 还没发起就现在发起
    self.param_gather_handle.wait()      # 等当前 bucket，前向才能继续
    if self.next_param_gather_bucket_group is not None:
        self.next_param_gather_bucket_group.start_param_sync()  # 链式触发下一个
```

`next_param_gather_bucket_group` 在初始化时按前向顺序建立单向链表。每次 `finish_param_sync` 等待当前 bucket 的同时触发下一个，形成滚动预取：前向计算和参数搬运始终保持一步之差，GPU 不需要为等参数而停下来。

这个设计和梯度通信 overlap 是完全对称的两侧：反向传播中 bucket 梯度就绪后异步发起 reduce-scatter，前向传播中 forward pre-hook 在用到参数之前异步发起 all-gather。两条流水方向相反，隐藏通信的逻辑一致。

*【图示】all-gather 链式预取*

### 小结

回顾整个 DDP 的设计，可以看到一条贯穿始终的主线：**让通信尽量隐藏在计算后面**。

为了做到这一点，Megatron DDP 在三个层面上做了连续性的安排。

- 内存上，`param_data` 和 `grad_data` 各自是一块大的连续 buffer，**通信操作直接作用在连续内存上**，不需要在运行时做任何拷贝或重排；
- 时序上，bucket 按反向传播的就绪顺序流水触发 reduce-scatter，forward pre-hook 按前向传播的执行顺序流水触发 all-gather，**两条流水各自隐藏在对应的计算阶段后面**；
- 分工上，reduce-scatter 和 all-gather 分别对应梯度归约和参数恢复两个方向，`grad_data` 和 `param_data` 是两条流水各自的内存中枢，互不干扰。

**分布式优化器是这个设计的关键使能者**：正是因为每张卡只更新 1/dp 的参数分片，reduce-scatter 才有意义，all-gather 才是必要的。去掉分布式优化器，两条流水退化为一次 AllReduce，链式预取和分片逻辑也随之消失。三档配置（同步 → `overlap_param_gather` → `overlap_param_gather_with_optimizer_step`）则是在"隐藏程度"和"实现复杂度"之间提供了不同的权衡点，按需选取。

## 三、分布式优化器：参数分片与完整更新流程

DDP 解决了梯度通信的效率问题，但显存问题还没有解决：Adam 的优化器状态（fp32 主参数 + m + v）是 bf16 参数体积的六倍，在纯 DP 场景下每张卡维护完全相同的副本，这是纯粹的冗余。**分布式优化器的思路是把这份冗余变成分工**——DDP 已经把梯度打包进连续的 `grad_data` buffer 并做了 reduce-scatter，每张卡手里正好是自己那段 1/dp 的有效梯度；既然梯度已经分好了，优化器状态也应该跟着分，每张卡只维护对应段的 fp32 主参数、m 和 v。reduce-scatter 天然契合这个分工，不需要任何额外的通信。

![](https://pic4.zhimg.com/v2-eec28d391c77d9cc4fa792c9d2eca22d_r.jpg)
*【图示】核心类图*

本章沿着这个思路展开：3.1 节看分片如何建立，3.2 节看两套参数如何维护，3.3 节把六个阶段串成完整的更新流程，3.4 节总结两块 buffer 各自的角色。

### 3.1 分片设计：以 grad buffer 为单位等分

分片在 `_build_model_gbuf_range` 里完成，逻辑极简：

```python
gbuf_size = bucket.grad_data.numel()
max_gbuf_range_size = gbuf_size // data_parallel_world_size  # 严格等分

for r in range(data_parallel_world_size):
    gbuf_world_start = r * max_gbuf_range_size
    gbuf_world_end   = gbuf_world_start + max_gbuf_range_size  # 无余数
    gbuf_world_range = Range(gbuf_world_start + bucket.offset,
                             gbuf_world_end   + bucket.offset)
    gbuf_world_all_ranges.append(gbuf_world_range)

gbuf_world_range = gbuf_world_all_ranges[data_parallel_rank]
```

`grad_data` 在 `_ParamAndGradBuffer` 分配时已通过 padding 保证 `numel % dp_world_size == 0`（见 2.2 节），因此每张卡拿到严格等大的 `gbuf_size // dp_world_size` 个元素，不存在尾部余数。切分以 buffer 字节为单位，与参数边界无关——**一个参数完全可能横跨两个 rank 的分片边界，前半段的梯度归 rank k 处理，后半段归 rank k+1 处理。**

**四个 range 的映射**

参数横跨分片边界带来一个问题：后续取梯度、写回参数时，如何精确定位"这个参数有哪些元素落在当前 rank 的分片里"？`_build_model_gbuf_param_range_map` 为每个落在当前 rank 分片内的参数建立四个 range 的映射，分别服务于不同的操作：

```text
param_range_map[param] = {
    "gbuf_world":           # 参数在整个 grad buffer 的全局坐标
    "gbuf_world_in_bucket": # 参数在所属 bucket 内的坐标（写回 param_data 时用）
    "gbuf_local":           # 参数在当前 rank 本地分片内的坐标（取梯度时用）
    "param":                # 参数张量自身的坐标（sub_param_range，写回参数值时用）
}
```

四个 range 描述同一段数据在不同坐标系下的位置，互相可以推导。不是所有参数都会出现在当前 rank 的映射表里——只有确实有元素落在当前 rank 分片内的参数才被记录（`param_local_end > param_local_start`），完全落在其他 rank 分片内的参数对当前 rank 不可见。

![](https://pic2.zhimg.com/v2-24b5e76a3d27a9c669f5d3a57805b2cd_r.jpg)
*【图示】四个 range 的坐标系关系*

如上图所示：

- 最上层是 `grad_data` 全局 buffer，参数 W 横跨 rank 0 / rank 1 的分片边界，W 前半段归 rank 0，W 后半段归 rank 1，**`gbuf_world` 标注 W 在整个 buffer 的完整全局区间；**
- 中间层是 rank 1 的视角，W 后半段落在本地分片起点，**`gbuf_local` 从 0 起标注，**`gb`**`uf_world_in_bucket` 在此基础上加上 `bucket.offset`**，起点右移；
- 最下层是参数张量 W 自身的完整视图，**`param`（`sub_param_range`）标注在 W 自身坐标系的靠右位置，对应 rank 1 负责的那段。**

四个 range 描述同一段数据，坐标系不同。

### 3.2 两套参数：model param 与 main param

bf16 训练时，每个参数在分布式优化器里实际存在两个分片对象，职责不同、内存独立性不同：

```python
# shard_model_param：model_param 的切片视图，共享底层内存
shard_model_param = model_param.detach().view(-1)[param_range.start : param_range.end]

# shard_main_param：独立 clone 升精度，fp32，独立占显存（仅 bf16/fp16 参数需要）
shard_main_param = shard_model_param.clone().float()
model_param.main_param = shard_main_param
```

`_build_model_and_main_param_groups` 按参数精度分两条路径处理，返回五类参数组：

**bf16/fp16 参数路径**：`shard_model_param` 是 `model_param` 的切片视图（bf16，共享内存），`shard_main_param` 是从视图 `.clone().float()` 出来的独立 fp32 副本。Adam 在 fp32 副本上更新，更新完通过 `_copy_main_params_to_model_params` cast 回 bf16 写入 `param_data`，多一次写回，也多占一份 fp32 显存——这是混合精度训练的必要代价。

**fp32 参数路径**：`shard_model_param` 直接切片（fp32，视图），Adam 在视图上原地更新，参数本身就是最新值，不需要写回步骤，也不额外占显存。

bf16/fp16 参数路径中每次循环迭代里，三个列表同步追加：

```python
model_float16_params_this_group.append(model_param)          # 完整 bf16 参数
shard_float16_params_this_group.append(shard_model_param)    # 对应的 bf16 切片视图
shard_fp32_from_float16_params_this_group.append(shard_main_param)  # 对应的 fp32 副本
```

三行同步追加保证了 `model_float16_groups`、`shard_float16_groups`、`shard_fp32_from_float16_groups` 三个列表的**索引严格对齐**——相同下标对应同一参数的完整 bf16 tensor、bf16 切片视图、fp32 副本三种形态。

后续 `_copy_model_grads_to_main_grads` 和 `_copy_main_params_to_model_params` 通过 `zip` 配对这些列表，能正确工作的前提正是这里建立的对齐关系。fp32 参数路径同理，`model_fp32_groups` 和 `shard_fp32_groups` 索引对齐，只是 fp32 参数不需要第三个副本。

五类参数组的完整对照：

| 参数组 | 精度 | 内存方式 | 进 Adam | 用途 |
| --- | --- | --- | --- | --- |
| model_float16_groups | bf16 | 完整参数引用 | 否 | 取 main_grad；与 shard 组 zip 对齐 |
| model_fp32_groups | fp32 | 完整参数引用 | 否 | 同上，fp32 参数对应组 |
| shard_float16_groups | bf16 | model_param 视图（切片） | 仅 precision_aware 模式 | 提供分片索引；precision_aware 模式下直接进 Adam |
| shard_fp32_groups | fp32 | model_param 视图（切片） | 是 | fp32 参数原地更新，无需写回 |
| shard_fp32_from_float16_groups | fp32 | 独立 clone（.clone().float()） | 是 | bf16 参数的 fp32 副本，更新后写回 param_data |

底层优化器的 `param_groups` 最终被替换为两类 fp32 分片的合并：

```python
group_range["orig_group"]["params"] = [
    *shard_fp32_params_this_group,               # fp32 参数直接切片，原地更新
    *shard_fp32_from_float16_params_this_group,  # bf16 参数 clone 出的 fp32 分片，需写回
]
self.optimizer.param_groups = [g["orig_group"] for g in self.opt_group_ranges]
```

这也解释了为什么 `_copy_main_params_to_model_params` 只处理 `shard_fp32_from_float16_groups` 和 `model_float16_groups` 的配对——**fp32 参数走视图原地更新，根本不需要写回，`shard_fp32_groups` 不在写回逻辑里。**

Adam 的 `step()` 直接在这些 fp32 分片上操作，天然只更新当前 rank 负责的部分，m/v 状态也只为这些分片分配。显存节省的量级：fp32 main param、m、v 三项各节省 `(1 - 1/dp)` 倍，dp=8 时优化器状态降至 1/8，dp=64 时降至 1/64，收益随 DP 规模线性增长。

### 3.3 完整更新流程：六个阶段

一次完整的参数更新横跨反向传播和 `optimizer.step()`，分六个阶段。前两个阶段在 DDP 层完成，后四个阶段在分布式优化器内部完成。

![](https://pica.zhimg.com/v2-d43d71246b8692e4aab63d547fea9858_r.jpg)
*【图示】六阶段时序图*

**阶段 1：reduce-scatter（反向传播中自动触发）**

反向传播中，每个参数的梯度计算完成后 hook 自动触发，把 `param.grad` 累加进 `param.main_grad`（`grad_data` 的视图）：

```python
if param.grad is not None and (
    not param.grad_added_to_main_grad or getattr(param, 'zero_out_wgrad', False)
):
    param.main_grad.add_(param.grad.data)
param.grad = None
```

`param.grad_added_to_main_grad` 标志防止重复累加——某些场景下梯度已在别处写入 `main_grad`，此时 hook 跳过累加。`param.grad = None` 在累加后立即执行，主动释放这块临时显存，不依赖 GC 回收。

**BucketGroup 内所有参数就绪后触发 `start_grad_sync`**，在 DP 通信组上执行 reduce-scatter。结束后每张卡的 `grad_data` 里只有自己负责的 1/dp 那段是有效的聚合梯度，其余段已分发给对应 rank。

**阶段 2：`finalize_model_grads`（梯度归约收尾）**

```python
for model_chunk in model:
    model_chunk.finish_grad_sync()
```

**`finish_grad_sync` 等待所有 bucket 的异步 reduce-scatter 完成。**随后处理 TP-SP 场景下 LayerNorm 梯度的额外 AllReduce 和 PP 首尾 stage 的 embedding 梯度 AllReduce；`calculate_per_token_loss=True` 时用全局 token 数做精确缩放。纯 DP 场景下后两项是空操作。

**阶段 3：`_copy_model_grads_to_main_grads`（梯度精度转换）**

reduce-scatter 结束后，`grad_data` 里当前 rank 那段有效梯度需要转精度才能给 Adam 用。这里用 `param_range_map["param"]`——参数自身被切了哪段——来定位：

```text
model_grad = model_param.main_grad                            # grad_data 的视图
shard_model_grad = model_grad.view(-1)[param_range.start : param_range.end]
shard_main_param.grad = shard_model_grad.float()             # bf16 → fp32
```

cast 到 fp32 写入 `shard_main_param.grad`，为 Adam 准备好梯度。随后父类 `MixedPrecisionOptimizer` 做 unscale（除以 loss_scale）和 inf/nan 检测，决定本轮是否跳过更新。

**阶段 4：`clip_grad_norm`（可选）**

在 fp32 梯度上做 grad clip。clip 的覆盖范围是当前 rank 负责的参数分片，但 clip 的阈值判断依赖全局梯度范数——各 rank 先分别计算本地分片的梯度范数，再通过 AllReduce 聚合得到全局范数，最后统一决定是否 clip 以及 clip 的系数。这保证了所有 rank 对同一轮梯度做出完全一致的 clip 决策，参数更新不会因分片而出现不一致。

**阶段 5：`step_with_ready_grads`（参数更新 + all-gather）**

```python
def step_with_ready_grads(self):
    update_successful = super().step_with_ready_grads()  # fp32 Adam 更新 shard_main_param

    if not self.ddp_config.overlap_param_gather:
        for model_chunk in self.model_chunks:
            model_chunk.start_param_sync()   # 同步 all-gather
    # overlap=True 时：不在这里发起，交给下一轮 forward pre-hook 链式触发
```

Adam 更新完 `shard_main_param` 后，`_copy_main_params_to_model_params` 把 fp32 分片写回 `param_data`：

```python
world_range = param_range_map["gbuf_world_in_bucket"]  # 参数在 bucket 内的全局位置
shard_model_param = model_param_buffer.view(-1)[world_range.start : world_range.end]
shard_model_param.data.copy_(shard_main_param)         # fp32 → bf16，写入 param_data
```

这里用 `gbuf_world_in_bucket` 而不是 `param` range——两者描述同一段数据，但坐标系不同：`param` range 是参数自身坐标系，**`gbuf_world_in_bucket` 是 bucket 内全局坐标系**，写回 `param_data` 需要后者来定位目标位置。写回完成后，all-gather 把各卡的 `param_data` 分片拼回完整参数，供下一轮前向使用。

`overlap_param_gather=True` 时 all-gather 不在这里发起，等下一轮 forward pre-hook 链式触发，与前向计算重叠；**`overlap_param_gather=False` 时同步执行，前向必须等 all-gather 全部完成才能开始。**

**阶段 6：`zero_grad`（下一轮准备）**

```python
total_groups = [
    self.model_float16_groups,
    self.model_fp32_groups,
    self.shard_float16_groups,
    self.shard_fp32_groups,
    self.shard_fp32_from_float16_groups,
]
for groups in total_groups:
    _zero_grad_group_helper(group, set_to_none, ...)
```

清零范围覆盖五类参数组，确保上一轮的梯度不会污染下一轮。`set_to_none=True`（默认）时直接将 `.grad` 置 None 而非填零，触发显存释放——`grad_data` 在下一轮反向传播写入前不需要保留，这个时机释放可以有效压低峰值显存。

### 3.4 两块 buffer 各自的角色

六个阶段里，`grad_data` 和 `param_data` 分工明确、时序互补，两块 buffer 从不混用：

`grad_data` 是**梯度流水**的中枢，生命周期严格限定在反向传播到阶段 3：反向写入梯度 → reduce-scatter 聚合 → `_copy_model_grads_to_main_grads` 取出转精度。阶段 3 结束后 `grad_data` 的使命完成，`zero_grad` 在下一轮反向开始前清零并释放 `.grad` 的显存，等待下一轮写入。

`param_data` 是**参数流水**的中枢，生命周期覆盖前向传播阶段：`_copy_main_params_to_model_params` 写入更新后的 bf16 分片 → all-gather 拼回完整参数 → 前向读取。`param_data` 只在分布式优化器模式下分配，是 all-gather 能原地操作、无需额外拷贝的基础——没有这块连续 buffer，all-gather 就必须为每个参数单独分配目标内存。

两条流水方向相反、时序衔接：`grad_data` 在反向传播中填满，阶段 3 取空；`param_data` 在阶段 5 写入，前向传播中读取。上一轮的参数流水结束，下一轮的梯度流水开始——一次完整的训练迭代正是由这两条首尾相接的流水构成。

### 小结

分布式优化器的设计思路可以用一句话概括：**把 DP 的冗余变成分工**。N 张卡各自维护完整的优化器状态是纯粹的冗余；把这份冗余拆开——每张卡只负责 1/dp 的参数更新，显存压力线性下降，通信结构也随之自然确定：reduce-scatter 把梯度分发到各自负责的 rank，all-gather 把更新后的参数收回来。

围绕这个核心，有三个设计细节值得记住：

**分片粒度**：以 `grad_data` 字节数等分，不关心参数边界。这和 DDP 切 bucket 时"以参数为最小单位"的策略相反——DDP 优先保证参数完整，分布式优化器优先保证每张卡负载严格均等。两种策略服务于不同目标，在同一个框架里共存而不矛盾。

**两套参数，两套内存**：`shard_model_param` 是 `model_param` 的切片视图，不占额外显存；`shard_main_param` 是独立 clone 的 fp32 tensor，Adam 的 m/v 状态挂在它上面，是真正占显存的那份。三个列表（`model_float16_groups`、`shard_float16_groups`、`shard_fp32_from_float16_groups`）在初始化时同步追加、索引严格对齐，是后续所有 copy 操作能正确配对的基础。

**两块 buffer，各司其职**：`grad_data` 全程服务于梯度归约（反向到阶段 3），`param_data` 全程服务于参数恢复（阶段 5 到前向），两者从不混用。去掉分布式优化器，`param_data` 不再分配，两条流水退化为一次 AllReduce，所有分片逻辑随之消失——这也说明分布式优化器是这套设计的真正使能者，而不只是一个显存优化的附加选项。

## 四、梯度量级基线

前三章分别走读了训练主循环、DDP 和分布式优化器的实现，每一章都有影响梯度量级的设计决策——loss 归一化在哪里做、`gradient_scaling_factor` 是多少、`finalize_model_grads` 是否追加缩放。这些决策散落在不同模块里，单独看每一处都合理，但梯度的最终量级是它们共同作用的结果。

本章把这条链路串起来做一次完整推导，得到纯 DP 场景下的梯度基线。这个基线的目的不是为了本文自身——而是为下一篇引入 CP 做精确的对照：CP 会改变通信组的范围、loss 归一化的分母、梯度缩放系数，有了基线才能看清楚每一处改动了什么、为什么改、代价是什么。

### 第一步：单个 microbatch 的反向起点

`forward_step` 对 loss 做两步归一化（见 1.3 节），`backward_step` 再乘 `loss_scale`，每个 microbatch 的反向起点是：

```python
backward_input = loss_scale × mean(token_loss) / num_microbatches
```

这是链式法则的起点，后续所有梯度都以此为基准往下传。

### 第二步：梯度累积——`/num_microbatches` 的真实作用

`forward_backward_no_pipelining` 串行执行 `num_microbatches` 个 microbatch，前 N-1 个在 `no_sync` 里只累加不通信，梯度在 `grad_data` 里逐步叠加：

```python
grad_accumulated = Σ_{mb=0}^{num_mb-1} [loss_scale × mean(token_loss_mb) / num_microbatches × ∂param]
                 = loss_scale / num_microbatches × Σ_{mb} mean(token_loss_mb) × ∂param
```

这里有一个容易忽视的细节：`/num_microbatches` 在**每个** microbatch 的反向起点上做，累加 `num_microbatches` 次后，`/num_microbatches` 和 `Σ_{mb}` 合并，等价于对所有 microbatch 取平均：

```python
grad_accumulated = loss_scale × mean_over_mb(mean(token_loss)) × ∂param
```

`num_microbatches` 在分子分母相消，**最终梯度量级里 `num_microbatches` 消掉了**。`/num_microbatches` 的作用不是改变最终量级，而是控制每步梯度累积的贡献比例——保证累加后的量级和单个 microbatch 的量级一致，不随梯度累积步数膨胀。

### 第三步：DDP 通信

`gradient_scaling_factor = 1/dp`，通信前对 `grad_accumulated` 原地预乘，再做 SUM over dp：

```python
grad_after_sync = loss_scale × mean_over_mb(mean(token_loss)) × ∂param
                × dp        ← SUM 把 dp 份梯度加在一起
                × (1/dp)    ← gradient_scaling_factor 通信前预缩放
               = loss_scale × mean_over_mb(mean(token_loss)) × ∂param
```

SUM 和预缩放互相抵消，梯度量级不变，但语义从"本卡梯度"变成了"dp 张卡的平均梯度"。不同 DP rank 持有不同样本的 microbatch，平均后每张卡的梯度包含了所有样本的信息，保证参数更新方向一致。

### 第四步：`finalize_model_grads`

`calculate_per_token_loss=False` 时，`num_tokens` 为 None，无额外缩放：

```python
grad_final = loss_scale × mean_over_mb(mean(token_loss)) × ∂param
```

各 microbatch 等长时 `mean_over_mb(mean(token_loss)) = mean(token_loss)`，进一步简化为：

```text
grad_final = loss_scale × mean(token_loss) × ∂param
```

### 基线与其含义

这就是无 CP 时的梯度基线。每个参数的梯度正比于所有 microbatch 的 per-token 平均 loss（等长时等于单个 microbatch 的 per-token 平均），乘以 `loss_scale`。不同 DP rank 的 microbatch 来自不同样本，DDP 通信把它们平均，最终每张卡持有相同的梯度，保证参数更新一致。

这个基线成立有两个隐含前提：各卡的 token 数相等（所以用局部 `num_tokens` 做归一化是准确的），以及 DP 通信组覆盖所有参与训练的卡（所以 `1/dp` 的平均是全局平均）。引入 CP 后，第二个前提会被打破——通信组的范围需要扩展到 `dp×cp`——这正是下一篇要重点分析的内容。

## 💡 全文小结

本文以纯 DP 视角走读了 Megatron 的训练主循环、DDP 和分布式优化器，这三个模块不是并列的，而是层层递进、共同服务于一次完整训练迭代的：

**训练主循环**定义了迭代的节奏和 loss 的归一化方式。`forward_backward_no_pipelining` 串行执行多个 micro_batch 的前反向，`no_sync` 控制梯度累积窗口，`finalize_model_grads` 做收尾。框架层 `forward_step` 在 loss 上做两步归一化（`/num_tokens`、`/num_microbatches`），`backward_step` 再乘 `loss_scale`，共同决定了每个 microbatch 的反向起点——`/num_microbatches` 控制每步梯度的贡献比例，累加后与 `×num_microbatches` 相消，最终梯度量级不含 `num_microbatches`。

**DDP** 在主循环确定的梯度量级基础上，解决梯度的高效通信问题。参数梯度打包进连续 `grad_data` buffer，按 BucketGroup 流水触发通信，与反向计算重叠。是否启用分布式优化器决定通信类型：AllReduce 让每张卡持有完整梯度，reduce-scatter 让每张卡只保留 `1/dp` 分片——后者是分布式优化器能工作的前提。

**分布式优化器**承接 reduce-scatter 的输出，把 DP 的冗余变成分工。以 `grad_data` 字节数等分，每张卡只维护 `1/dp` 的 fp32 主参数和 Adam 状态；更新完 cast 回 bf16 写入 `param_data`，all-gather 拼回完整参数。`grad_data` 和 `param_data` 两条流水方向相反、时序互补，首尾相接构成一次完整的训练迭代。

梯度基线是把三章链路串成公式的结果：

```python
grad_final = loss_scale × mean(token_loss) × ∂param
```

这个基线成立有一个隐含前提：DP 通信组覆盖所有参与训练的卡，`1/dp` 的平均是全局平均。引入 CP 后，同一条序列被切给 cp 张卡，这 cp 张卡处理的是同一个样本的不同片段，它们的梯度需要一起参与归约——DP 通信组必须扩展到 `dp×cp` 的联合组，`gradient_scaling_factor` 从 `1/dp` 变为 `1/(dp×cp)`，loss 归一化的分母也需要对应调整。这正是 1.2 节里 `with_context_parallel=True` 这个扩展点提前预留的原因。下一篇从这个基线出发，精确描述 CP 在每一处的改动是什么、为什么改、代价是什么。
