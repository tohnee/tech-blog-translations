# 第七篇：RAG 面试必问｜RAG、Memory 和 Knowledge Graph 在 Agent 系统中分别负责什么？

#github#开源项目#RAG#Agent开发#检索增强生成#求职#秋招#AI#LLM#vaultcoach 
 我会结合一个 **开源项目** Vault Coach 带你彻底搞懂 RAG，帮你从容应对 Agent 开发岗位的面试。欢迎关注本合集，后续还会有更多 Agent 开发相关的项目和理论！

当系统从 Chatbot 继续向 Agent 演进以后，经常会同时出现三个词：

```text
RAG
Memory
Knowledge Graph

```

很多项目最后把三者全部叫成：

> “知识库。”

但从系统设计角度，它们解决的是完全不同的问题。

Vault Coach 项目的后续功能恰好提供了一个非常好的案例。

## RAG：负责告诉 Agent 资料里写了什么

例如用户问：

> 我的笔记里怎么解释二维动态规划算法？

系统应该从：

```text
Markdown / PDF

```

中找到最相关的原文。

这属于：

> Document Retrieval。

RAG 强项是：

- • 找证据；
- • 找段落；
- • 找原文；
- • 回到来源。

## Memory：负责告诉 Agent 之前发生过什么

假设用户 **上周** 说：

> 我现在正在准备强化学习算法岗位面试。

今天用户说：

> 再帮我出五道题。

系统如果希望知道“五道什么题”，需要依赖历史信息。

这属于 Memory，而不是普通文档 RAG。

Vault Coach 的 Advanced RAG 设计包含 **可选长期记忆** ：

- • 从对话中提取较稳定的信息，在 **跨会话** 时重新注入 Context；
- • 当前版本也允许用户关闭这一能力。

所以可以简单记成：

```text
RAG
= external knowledge

Memory
= interaction history / durable user facts

```

两者不能完全互相替代。

## Knowledge Graph：告诉 Agent 知识之间是什么关系

再看一个问题：

> 学习 GRPO 之前，我应该先理解哪些概念？

单纯 Semantic Search 可能返回很多讲 GRPO 的文章。

但 正确的回答必须依赖的逻辑是：

```text
概念 A
↓ prerequisite_of （前置）
概念 B

```

这已经不是单纯“哪一段文字最相似”的问题。

而是：

> **Relationship Query。**

Vault Coach 当前已经可以从已索引 Section 中提取 **概念** （Concept）和 **关系** 候选，并要求用户审核之后再把关系视为已确认事实。

例如：

```text
TD Error
  ↓ prerequisite_of
Advantage Estimation
  ↓ related_to
PPO

```

## Graph 能不能替代 RAG？

不能简单这么理解。

**Knowledge Graph** 擅长：

```text
A 和 B 什么关系？
A 的前置知识有哪些？
从 A 到 D 有什么路径？

```

**RAG** 擅长：

```text
原文怎么解释 A？
A 的公式是什么？
哪篇笔记讨论过 A？

```

使用体验更好的系统反而会让知识图谱和 RAG 合作：

```text
Question
↓
Router / Agent
├─ Document RAG
├─ Memory
└─ Knowledge Graph
    ↓
Evidence Fusion
    ↓
   Answer

```

## 这时候 RAG 为什么成了 Agent 基础设施？

因为 Agent 本身并不应该记住所有知识。

它更像一个 **决策者** ：

> 我现在缺什么信息？

然后调用不同 Tool。

例如 Vault Coach 的业务里可以存在这样的流程：

```text
用户：帮我复习 DQN
↓
读取用户本地的 Learning State
↓
查询 Knowledge Graph
↓
发现 Target Network 是该用户的薄弱概念
↓
RAG 获取相关笔记
↓
生成一次范围明确的测试
↓
保存测试结果

```

当前 Vault Coach 已经分别具备带引用问答、限定范围考试、已审核概念图谱以及基于测试结果的掌握度追踪，这说明同一套 **知识基础设施** 已经可以服务多个上层学习任务，而不只是聊天。

## 什么是 Agentic RAG？

面试中这个词不要解释成：

> “用了 Agent 的 RAG。”

更准确地说：

**传统 RAG** 通常是一条固定 Pipeline：

```text
Query
→ Retrieve
→ Generate

```

**Agentic RAG** 则允许系统根据任务 **动态决定** ：

```text
要不要检索？
检索哪个数据源？
是否重写 Query？
结果够不够？
是否继续检索？
是否查询 Graph？
下一步执行什么 Tool？

```

也就是说：

> **Retrieval 从固定步骤变成 Agent 可以调度的能力。**

这也是为什么在今天讨论 Agent System Architecture 时，Retrieval 仍然非常重要。

## Agentic RAG 就一定更好吗？

也不是。

如果产品只是：

> 从 100 篇 FAQ 中回答一个简单问题。

加一个循环 Agent：

```text
Plan
→ Search
→ Reflect
→ Search
→ Reflect

```

很可能只会：

- • 更慢；
- • 更贵；
- • 更难 Debug。

Agentic RAG 真正适合的是：

- • 多知识源；
- • 多跳问题；
- • 任务类型不确定；
- • 需要决定是否检索；
- • 需要 Retrieval 后继续执行动作。

## 面试官问：什么时候考虑 GraphRAG？

可以回答：

> 当问题的核心从“找到相似文本”变成“理解实体之间的关系和多跳结构”时，再考虑 Knowledge Graph 或 Graph-enhanced Retrieval。

例如：

```text
A 和 B 为什么相关？
A 依赖哪些知识？
某技术经过哪些概念连接到另一个技术？

```

这类问题才真正体现 Graph 的价值。

但是不要因为 Knowledge Graph 听起来高级，就给普通 FAQ 系统强行上 Graph。

## 最后总结

RAG、Memory 和 Knowledge Graph 可以这样区分：

```text
RAG
→ 找文档证据

Memory
→ 保存跨时间上下文

Knowledge Graph
→ 表达概念关系

```

而 Agent 的作用是：

> **根据当前任务决定何时使用哪一种知识能力。**

所以真正值得掌握的是：

> **怎样把 Retrieval 设计成 Agent 可以可靠调用的知识基础设施。**

这也是下一阶段 RAG 工程能力真正有价值的地方。
