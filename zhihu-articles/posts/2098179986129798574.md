## 从算子到 AI 编译器：当 AI 开始写算子，这条链路上的人往哪走

编译器、算子库与 AI 生成，正在融合成一条多路径的 lowering 流水线；而人的位置，移到了上游和验收端。

一个训练好的模型要跑在 AI 芯片上，中间要经过一长串角色。很多人听过”编译器”“Runtime”“驱动”，但具体谁干什么、边界在哪，经常一团浆糊。再往下还有”算子开发工程师”和”AI 编译器开发工程师”，名字都带”开发”，到底有什么区别？手写算子是不是一定比编译器生成的好？如果编译器越来越强，手写还有没有活路？而当 AI 开始自己写 kernel，这条链路上的人，又被推向哪里？

### 一、先分清三层：编译器、Runtime、驱动

**编译器**负责”生成”。它把模型的计算图翻译、优化成芯片能执行的指令或算子序列。NVIDIA 的 `nvcc`、Google 的 XLA、华为的 MindCompiler、寒武纪的 MagicMind，以及 TVM、Triton、MLIR 这些通用框架，都属于这一层。在 AI 语境下，编译器处理的不再是普通代码而是神经网络的计算图，要做算子融合、内存规划、指令选择、代码生成。

**Runtime** 负责”管理”。程序跑起来之后，内存怎么分配、kernel 怎么启动、流和事件怎么调度、主机和设备之间怎么拷贝数据，都是 Runtime 的事。CUDA Runtime、libtpu、CANN Runtime、HIP Runtime 都是这一层。它是应用程序和驱动之间的桥梁，让开发者不用直接面对复杂的驱动 API。

**驱动**负责”操作硬件”。它通常跑在内核态，直接和芯片通信，处理中断、DMA、命令队列、寄存器操作，向上提供统一接口。没有驱动，操作系统根本认不出这块芯片。

**总之，编译器管生成，Runtime 管运行支撑，驱动管硬件访问。**

### 二、算子开发工程师站在哪

算子开发工程师站在**算子库 / Kernel 实现层**，夹在”框架调用算子”和”芯片执行”之间。

往上，PyTorch、TensorFlow、PaddlePaddle 会调用 Conv2D、MatMul、Softmax 这些算子；往下，这些算子最终要变成芯片上的 kernel，通过 Runtime 启动、驱动执行。算子开发工程师干的，就是**把这个算子本身写得又对又快**：定义算子接口，用 CUDA、HIP、Ascend C、BANG、OpenCL 甚至汇编和 intrinsics 写 kernel，做 tiling、向量化、流水线、shared memory 优化、寄存器分配、双缓冲、warp 调度，处理 FP16/BF16/FP8/INT8 各种精度和边界 shape，做自动调优，最后测正确性和性能。

归属因公司而异：NVIDIA 在 CUDA Libraries 团队做 cuDNN、cuBLAS、CUTLASS；华为在 CANN 做 Ascend C；寒武纪在 NeuWare/BANG；AMD 在 ROCm；互联网公司可能做框架自定义算子、推理引擎优化或 TVM/TensorRT 插件；编译器团队里也有人在做算子 lowering 和代码生成。

### 三、算子开发 vs AI 编译器开发

两个岗位常在同一条链路上协作，但核心产出不同。

**算子开发工程师**关心单个算子：这个 MatMul 的 tiling 怎么选？GELU 用查表、多项式还是近似？非对齐 shape 怎么走 fallback？shared memory bank conflict 怎么避免？occupancy 和带宽利用率如何？

**AI 编译器开发工程师**关心整个计算图：MatMul + Bias + GELU 能不能融合？是 lower 成三个算子调用，还是生成一个 fused kernel？中间结果放 shared memory 还是寄存器？要不要插 transpose？内存峰值多少？编译时间是否可接受？

| 维度 | 算子开发工程师 | AI 编译器开发工程师 |
| --- | --- | --- |
| 核心问题 | 这个算子怎么算得快、算得对 | 整个模型怎么变成高效算子序列 |
| 工作对象 | 单个算子 / kernel | 计算图、IR、调度方案 |
| 主要产出 | 算子接口、kernel、算子库、调优配置 | IR、Pass、lowering、代码生成后端 |
| 优化范围 | 局部：tiling、向量化、流水、访存 | 全局：融合、布局、常量折叠、内存复用 |
| 正确性重点 | 数值精度、边界 shape、溢出 | 语义保持、图变换正确性、端到端一致 |

边界不是绝对的：编译器后端也会生成 kernel，这时编译器工程师也在写”kernel 生成逻辑”；算子开发也会写模板和 autotune，和编译器的调度搜索很像。有些公司干脆把”算子开发”叫”AI 编译器后端”，看实际工作内容比看 title 可靠。

总之，**算子开发是单点爆破，把一个算子做到极致；AI 编译器是全局调度，把整个模型翻译好、融合好、编排好。** 二者是上下游协作关系。

### 四、两条落地路径：调算子库，还是生成 kernel

**路径 A：调用算子库。** 编译器把图 lower 成对 cuDNN、cuBLAS、CANN 算子库的调用。这些 kernel 是算子库团队预先写好、经过大量验证的通用实现。编译器主要做算子选择、参数配置、布局转换，融合能力有限，除非库本身提供 fused 算子。

**路径 B：直接生成 kernel。** 编译器根据当前模型的具体 shape、dtype、layout，现场生成专用 kernel。比如把 `MatMul + Bias + GELU` 生成一个 fused kernel，读 A、B，算 MatMul，加 Bias，算 GELU，写回，中间结果留在寄存器或 shared memory，减少中间写回和 kernel 启动。

可以理解成**用预制件组装**和**现场定制加工**。

| 维度 | 调用算子库 | 直接生成 kernel |
| --- | --- | --- |
| 优化粒度 | 通用，覆盖常见 shape / dtype / layout | 专用，可针对具体 shape 和融合模式特化 |
| 覆盖范围 | 受库支持范围限制 | 理论上可覆盖任意融合组合 |
| 性能 | 常见场景调优成熟，特殊 shape 可能不最优 | 特化后可能更快，依赖生成质量 |
| 编译时间与正确性风险 | 低 | 高，需要调度搜索，边界处理容易出 bug |
| 灵活性 | 低，库没有的算子/融合无法直接调用 | 高，可做融合、布局与动态 shape 特化 |

实际系统通常是混合的：XLA 能调库就调库，不合适的生成 kernel；TensorRT 优先用高度优化的内置 kernel 和插件；TVM/Triton 更偏代码生成；PyTorch eager 直接调算子库基本不走图编译器，而 TorchInductor 生成 Triton kernel 同时也会调库。

这里有个容易混淆的点：**算子库是核心资产，但编译器后端不一定用它。**”核心资产”是生态和商业层面的判断，cuDNN/cuBLAS 是大量框架和用户直接依赖的标准件，独立发布、独立演进，不隶属任何编译器后端；它不只做加速，还负责语义正确、精度处理、边界 shape、硬件能力封装和版本兼容。”不一定用它”是技术选择层面，编译器可以调库、生成 kernel 或混合。就像标准件库是工厂的核心资产，但某条产线可以选择自己加工。

### 五、手写一定比编译器生成的好吗

不一定。更准确地说：**在成熟高频算子和常见形状上，手写常常更好；在长尾、特殊融合、新硬件上，编译器生成可能更好或唯一可行。**

手写的优势来自几个地方：人有时间做极致调优，一个 MatMul kernel 可以调几个月，试遍 tiling、流水、寄存器分配、Tensor Core 布局；人能利用非常规硬件特性，特殊指令、异步拷贝、手工流水线；人能针对固定 shape/dtype 做特化，比如写死 `M=N=K=4096` 的 FP16 MatMul 最优参数；人能避开编译器的保守假设；还能手工做融合，把 Conv+Bias+ReLU 写成一个 kernel，减少中间写回。

编译器的优势在另一边：覆盖长尾，任意算子组合、shape、dtype 手写不可能全覆盖；自动发现图级别手写库没提供的融合机会；快速适配新硬件和新模型，改后端比组织人手重写算子库快；用编译时间换运行时性能，针对当前模型现场特化。

那为什么不全部手写，也不全交给编译器？因为**两边各有硬边界，而且是不同性质的边界**：

|  | 手写的边界 | 编译器的边界 |
| --- | --- | --- |
| 根本约束 | 组合爆炸：算子 × dtype × shape × layout × 硬件代际 | 调度空间和编译时间有限 |
| 成本 | 长尾算子投入产出比太低，硬件换代要跟着改 | 硬件建模不精确：流水线、bank 冲突、寄存器压力 |
| 响应速度 | 新算子、新融合模式要排期 | 非常规优化在 IR 里难以表达，验证成本高 |
| 其他 | 维护成本随框架升级、新精度格式持续增长 | 通用性与特化矛盾；有些库本身就是用户直调的标准接口 |

所以工业界的答案是**混合策略**：高频核心算子手写进库，长尾和特殊融合交给编译器生成，编译器也优先调库。手写赢在深度和特化，编译器赢在广度和自动化。

### 六、手写优势的具体例子

前面说手写更好的前提是：特定形状、固定公式、硬件细节可知。这个判断在具体场景里怎么兑现？

**FlashAttention：算法级融合。** 这不是编译器”漏掉”的普通融合，它的合法性来自一个数学恒等式——Softmax 对输入减去任意常数具有不变性：

$$ \operatorname{softmax}(z)_i = \dfrac{\exp(z_i-m)}{\sum_j \exp(z_j-m)} = \dfrac{\exp(z_i)}{\sum_j \exp(z_j)} $$ m 取任意常数都不改变结果；实现中取 running max，顺带解决数值溢出

编译器依赖的计算图依赖分析无法推导出这个代数恒等式，所以传统编译器在原理上就无法自动生成这种融合。正是这一点让分块计算成立：不必先拿到完整的 N×N 矩阵再归一化，而是逐块算出局部结果、用 running max 与 running sum 增量更新，最后只把输出写回。

![](https://pica.zhimg.com/v2-0863dfa5e758e8a32ec4f7fdf5c13546_r.jpg)

*图：标准 Attention 与 FlashAttention 的访存路径对比*

手写实现借此把 Attention 里巨大的 N×N 中间矩阵彻底消除，对 HBM 的访存从与 N² 成正比降为与 N 线性相关，长序列 Prefill 的注意力段实测有 2 到 4 倍收益。这种优化需要人洞察数学性质，再围绕它重新设计整个 kernel 的循环和分块结构。

**榨取特定硬件的非常规特性。** 在 H100 上手写 FlashAttention-2 时，可以直接调用 TMA（Tensor Memory Accelerator）和 WGMMA 这类 Hopper 特有的硬件单元。数据从 HBM 到 Tensor Core 要跨越好几级存储，每一级都有自己的带宽和陷阱，而手写 kernel 可以逐级接管这条通路：

![](https://pic4.zhimg.com/v2-ff2f948a9b501b0a1435650c122b1099_r.jpg)

*图：Hopper 上从 HBM 到 Tensor Core 的数据通路*

手工计算 shared memory 地址、显式使用 `ldmatrix`/`mma` PTX 指令、手动设计 swizzle 模式规避 bank 冲突，都是对这条通路的逐段接管。相比为上一代 Ampere 优化的版本，FLOPs/s 提升 20% 到 50%。编译器生成的代码在这些底层细节上往往不如人意。

**数值层面的算法魔术。** GELU 这类包含 `erf` 或 `tanh` 的复杂激活函数，定义本身就不便宜：

$$ \operatorname{GELU}(x) = x\cdot\Phi(x) = \dfrac{x}{2}\Bigl[\,1 + \operatorname{erf}\bigl(\tfrac{x}{\sqrt{2}}\bigr)\Bigr] $$

推理常用近似：$\operatorname{GELU}(x) \approx \dfrac{x}{2}\Bigl[\,1 + \tanh\bigl(\sqrt{\tfrac{2}{\pi}}\;(x + 0.044715x^{3})\bigr)\Bigr]$

推理场景对精度要求不极端时，手写可以连这个近似都不要，直接拟合一个 4 阶多项式：

$$ P_{4}(x) = a_{0} + a_{1}x + a_{2}x^{2} + a_{3}x^{3} + a_{4}x^{4} $$

Horner 形式：$P_{4}(x) = (((a_{4}x + a_{3})x + a_{2})x + a_{1})x + a_{0}$ 只有乘加、没有超越函数，向量单元可以满速流水

这条路线换来的是 3 到 5 倍性能提升。昇腾 CANN 的 `bessel_i1e` 优化是同一思路的另一面，追求的不是速度，而是精度：

$I_{1}(x) = \sum_{k=0}^{n} \frac{1}{k!\,(k+1)!}\left(\frac{x}{2}\right)^{2k+1} \qquad \substack{\text{项数 } 9 \to 13\\{最大误差 } 2.6\times10^{-6} \to 6.1\times10^{-10}} $

把泰勒级数从 9 项扩到 13 项、采用分阶段 Horner 形式来规避编译器处理深层嵌套的局限，最终最大误差降低约 4000 倍。这种对特定误差区间的精雕细琢，通用编译器不会去做。

三者共同说明：手写的优势在于人能跳出编译器的通用抽象框架，用领域知识、硬件知识和数值知识，在固定且关键的场景下做编译器无法自动完成的深度特化与融合。

### 七、这些非常规知识能教给编译器吗

可以转化，但不是”手写技巧变成编译器规则”这么简单。这些知识正通过多条路径被系统性”编译”进工具链，但有清晰边界。

**能转化的部分。** 硬件特性和底层指令正从”直觉”变成”显式接口”：Triton-TLE 提供 `TLE-Lite`、`TLE-Struct`、`TLE-Raw` 等分层，让开发者逐级向编译器提示数据布局和流水线意图，由编译器围绕这些提示自动优化 bank conflict 和寄存器复用；MLIR 能生成针对特定架构的汇编；Axon 这类系统通过程序合成，从语义规格自动生成目标指令并探索不同分块配置来最小化内存流量。

数值技巧也在从”手写拟合”走向”自动调优与合成”：TVM 的 Ansor 能在 6 小时内找到优于专家手写的配置，因为性能好的优化往往不直观；Axon 通过 SMT 求解器保证语义等价，自动发现人类没写过的代数变换，生成的 kernel 最高比手写快 1.35 倍。

调度与融合在从”手工模板”走向”自动推导”：Nautilus 能直接从数学描述出发，全自动推导出 FlashAttention-3 级别的高性能内核；FLASHLIGHT 能在 PyTorch 内自动为任意 Attention 变体生成融合 kernel，不需要静态模板。

**难转化的边界。** 数学洞察和算法级创新仍依赖人：Nautilus 能复现 FlashAttention 的结构，但”发明”这种融合本身仍靠人的领域洞察。不规则负载和未知硬件也是边界——Triton 的 GEMM 可以超过 cuBLAS，但在不规则访存面前会失灵，它的 N-Body 模拟比朴素 CUDA 慢 13.5 倍；手写 Triton kernel 要达到竞争力，仍需专家级逐 GPU 调优。把知识转化为编译器规则，高度依赖目标负载和硬件的已知性与规则性。

一句话：**编译器的进步，本质是把”可形式化、可搜索、可验证”的手写知识自动化。** 它把硬件细节、数值技巧和调度策略从个人经验沉淀为显式接口、自动调优空间和程序合成算法，但难以替代基于深层领域知识的算法创新，以及在不规则负载和未知硬件上依赖试错与直觉的探索。

### 八、AI 进来之后，边界怎么变

结合 AI 之后，改变的不是”手写还是生成”这个二元选择，而是**“什么能被自动化”的边界本身**。

**AI 作为算子生成器。** DRTriton 用强化学习训练 LLM 把 PyTorch 程序转成 Triton kernel，在 KernelBench Level 2 上，一个 7B 模型在 92% 的任务上超过 PyTorch。CudaForge 用”Coder + Judge”双 Agent 循环，结合 Nsight Compute 的硬件反馈迭代优化 CUDA kernel，达到平均 1.68 倍加速，单个 kernel 约 26.5 分钟、0.3 美元。CuBridge 更巧妙：它不从零生成，而是把专家写的 CUDA Attention kernel”举升”为中间表示，再根据用户给的 PyTorch 规格重构出适配的优化 kernel。这意味着 AI 正在把”手写算子”变成可复用、可迁移的知识资产，而不是每次从零开始。

**AI 作为编译器本身。** 一篇 2026 年的论文直接题为”AI as a Compiler”，让 LLM agent 把 Triton kernel 直接翻译成 PTX，完全跳过 Triton 自身的 lowering 流水线，在 Ada、Hopper、Blackwell 上性能是自动调优 Triton 的 0.83 到 3.34 倍。最大的收益恰恰来自 lowering 不会做的变换：把打包的二进制权重直接解码为 Tensor Core 操作数（3.34 倍），为每个线程分配完整的 softmax 行（FlashAttention 上 1.37 倍），复用重叠的卷积窗口（最高 2.23 倍）。过去说”非常规技巧难以转化成编译器规则”，AI 提供了一条绕过”规则化”的路径——不需要把技巧写成 pass，而是直接学会在给定输入下产出正确的低层代码。

**AI 辅助编译器优化。** 一个集成 LLVM/MLIR 的强化学习框架，把优化 pass 选择和参数调优建模为序列决策，比标准 `-O3` 性能提升最高 35%，且不增加编译时间。编译器不再是人写死的规则集，而是可以被训练的策略。

**对人意味着什么。** DeepSeek 一位资深算子工程师在 2026 年的反思很有代表性：AI 在一年内从”查文档、读代码、找 bug 的小助手”，变成能独立阅读 CUDA、PTX、SASS 并独立优化算子的工具。他的判断是：不至于失业，但必须转业——从亲手编写算子，转向做 Agent 的”机甲驾驶员”，依靠对硬件和上层需求的理解来调度 AI、拆解任务、评估结果并对最终系统负责。被 AI 接管的是具体操作：查指令、读汇编、逐条分析停顿。可迁移的是判断力：哪个瓶颈值得先动、延迟与吞吐怎么取舍、一个算子改动如何影响整条链路。边界正从”执行”移向”判断和定义问题”。

**AI 仍然没有消除的壁垒。** 数学洞察仍需人提供起点——CuBridge 有效的前提，是先有专家写的 CUDA kernel 可供”举升”。AI 生成本身也不稳定：当前 SOTA 代码 LLM 在生成高效 Triton 算子方面仍有显著差距，需要评估框架、验证器和搜索策略兜底。成本与延迟也是新的权衡维度——生成一个 kernel 要 26.5 分钟和 0.3 美元，小规模或一次性场景未必划算。AI 生成适合高频、稳定、可摊销的场景，而不是替代所有手写。

### 九、最终的图景

> **人从”写具体代码”转向”定义问题、提供起点、评估产出、对系统负责”；AI 承担中间那层曾经被认为”只能靠人试错”的探索和生成。编译器、算子库、AI 生成，三者正融合成一条多路径的 lowering 流水线，而人的位置在流水线的上游和验收端。**

![](https://picx.zhimg.com/v2-5294e2ede1f7665c390d684a07afa181_r.jpg)

*图：多路径 lowering 流水线，人在上游与验收端*

几条核心结论：

1. 算子开发做单点算子的极致优化，AI 编译器做全图的翻译、融合、调度和代码生成；二者是上下游协作，不是上下级。
2. 调用算子库是预制件组装，直接生成 kernel 是现场定制加工，实际系统混合使用；算子库是编译器可选的落地后端，不是它的子模块。
3. 手写不一定总更好，但在高频、固定形状、硬件细节可利用的场景下，人投入足够时间通常能调得更极致。
4. 不全手写是因为组合爆炸、长尾覆盖和响应速度；编译器不能全覆盖是因为调度空间、硬件建模精度和验证成本有边界。
5. 非常规知识可以部分转化为编译器知识（分层硬件接口、自动调优、程序合成、自动融合推导），但数学洞察、不规则负载、未知硬件仍是边界；AI 抬高并部分绕过了这个边界，但仍需人提供问题起点、评估标准和系统责任。
