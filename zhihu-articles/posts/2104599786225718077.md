**对于 Groq TSP这种以静态调度（Static Scheduling）为核心的架构，Cycle-Accurate Microarchitecture Model 不应该仅仅是一个性能评估工具，而应该成为编译器开发基础设施的一部分。**

[​TauLang: A Language and Compiler for Space-Time Programming on Statically Scheduled Accelerators](https://arxiv.org/abs/2611.06079?utm_source=chatgpt.com)，

既然架构假设是

> 移除芯片里的一切不确定性因素，没有随机延迟访问，一切都是确定性的，SRAM访问延迟是固定的，运算部件延迟是固定的，编译器就可以精准的知道每个cycle芯片上发生的一切，编译器精准的告诉每个硬件单元每个周期做什么

那么提供一个 Cycle 级 Accurate Model，对于架构快速迭代，编译器开发的重要性就被抬高了。

但是同样的这个地方有一个非常关键的问题，对于服务器专用的LLM加速芯片，可以做“deterministic“假设。对于异构芯片，这种假设就会变得愈发困难

这个地方实际就是 3 个问题：

- 对于未来面向 Agent Worload 异构 SoC，其中用于本地 LLM 计算的 XPU，Groq TSP 是否还有可借鉴价值
- Cycle Accurate Model，对于静态编译器开发和架构的快速迭代是否关键
- 面临算力扩展，模型将如何高效的 Tile 到多块 XPU 计算 Cluster/Core 上，以及如何高效的进行 Cross Compute Cluster 通信、同步

在探索如何将目标模型高效Tile到目标预算下的XPU上之前，还是应该先捋清楚

- 1. 应该如何进行架构仿真
- 2. 如何实现编译器和架构 Co-Design
- 3. 如何借助AI加速整个收敛流程

## 一、定义问题

问题可以进一步被定义为：

> **在 RTL 实现之前，构建一个与目标硬件微架构周期行为一致的可执行模型，让编译器能够在模型上完成指令调度、资源分配、功能验证和性能评估。**

**进一步可能需要细化成两个问题：**

1. 编译器能否通过模型获得传统 ISA 级模拟器无法提供的静态调度信息？
2. 能否利用这个模型，在 RTL 交付之前验证编译器生成的静态调度结果？

## 二、GEM5 够看么

传统 GEM5 主要模拟处理器的执行行为。即使使用 Timing CPU Model，它关注的仍然是：

- 指令什么时候进入执行阶段；
- 什么时候满足执行条件；
- 什么时候访问 Cache / Memory；
- 什么时候完成执行；
- 整体运行了多少周期。

它解决的是：**给定一段程序，模拟处理器执行它会发生什么。**

但是这个地方我们要去开发出一套能够高效地将某一代的模型映射到底层执行硬件的静态编译器，

我们可能会希望编译器提前决定：

- 每个 Cycle 哪个计算单元执行什么操作；
- 每个 SRAM Bank 在哪个 Cycle 读取或写入；
- 数据在 PE 之间如何流动；
- 不同计算单元如何避免资源冲突；
- 如何让数据搬运和计算形成流水重叠。

它需要解决的是：**给定硬件资源和时序约束，编译器应该生成什么样的执行计划。**

**GEM5 并不是完全适合 LLM Workload Architecture Model**

| 维度 | 传统 GEM5 使用方式 | 面向静态调度的模型 |
| --- | --- | --- |
| 核心目标 | 模拟程序执行 | 验证执行计划 |
| 调度方式 | 模拟硬件执行机制 | 模拟编译器生成的 Schedule |
| 时间模型 | 根据 CPU / Memory Model 推进 | 严格按 Cycle 推进 |
| 数据流 | 通过执行和访存行为体现 | 显式追踪数据流 |
| 资源冲突 | 由模拟的硬件机制处理 | 检查编译期是否已经消除冲突 |
| 输出 | IPC、Latency、Cache 等 | Schedule Correctness、Utilization、Latency |

## 三、Compiler-Oriented Cycle-Accurate Model

这个地方的意义在于我们虽然不期待 Groq TSP 级别的精准调度，但是能够实现不断地寻找在给定资源限制下，Dynamic Schedule和Static Schedule之间的平衡

本身LLM的Workload并不像CPU Workload那样天然的极难预测，以FFN层为例，他的计算是非常固定的，就算硬件上存在一些扰动，整体上他的执行是确定的

甚至不需要模拟器，通过目标算力预算、目标带宽预算、目标片上SRAM预算，我们就能够得出一些早期结论，应该怎么切，切出来的每一块大概在某个引擎执行多久

![](https://picx.zhimg.com/v2-25ada3f20b4e81d99cf7975310c743e1_r.jpg)
*某层计算*

整个结算图计算量和所需要消耗的DMA时间、计算时间实际是比较明确的

问题在于如何在任务层，通过静态调度，编排流水把各个引擎都充分利用起来（毕竟我们不是在设计一个串行引擎），整体上我们不需要把执行精确到每个cycle，比如GEMM + Mul阶段，

我们不需要知道非常精准的就是执行了N个Cycle。但是我们需要知道，根据当前的架构计算引擎定义的数据流，**执行 GEMM + Mul**，在理论时间窗口内：

- MAC阵列，忙碌多少拍
- Elementwise Fuse 能否完全消除对MAC阵列背压
- 整个执行过程
- AI计算引擎数据写回 L2 SRAM

这样编译器在编排别的引擎 和 GEMM fuse Mul 并行的时候，就能相对精确的知道，

- 计算结果大概在什么时间窗口准备好
- 整个计算过程在不同时间窗口，对L2 SRAM的访存压力。
- 后置算子是否不必完全等前置算子全部计算完，可以提前消费已经写回L2 SRAM部分结果
- 多引擎并行下 L2 SRAM 如何平衡各 DMA 之间的 Bank冲突

### 2.1 Architecture Model

- PE / MAC / SIMD / Vector Engine 的组织结构
- SRAM Bank 数量、端口、读写带宽
- 数据流网络拓扑、方向和路由规则
- 各运算单元的 Pipeline Latency / Initiation Interval
- 芯片间通信接口及延迟

### 2.2 Cycle-Accurate Execution Model

- 每个 Cycle 的指令发射与执行
- SRAM Read / Write 的时序行为
- 数据在 PE 之间的逐周期流动
- Pipeline Stall、Resource Conflict
- 数据依赖、Buffer Occupancy
- Chip-to-Chip Transfer

### 2.3 **Schedule Verification & Analysis**

- 静态调度合法性检查
- 数据依赖和时序约束检查
- SRAM Bank Conflict 检查
- Pipeline Hazard 检查
- 计算单元利用率
- SRAM 带宽利用率
- End-to-End Latency

## 四、TauLang Is Good

最早能追溯到的是 TSP 架构 Think Fast

**Think Fast: A Tensor Streaming Processor (TSP) for Accelerating Deep Learning Workloads，ISCA 2020。**

TSP 将调度复杂度推给编译器，编译器必须精确安排指令；同时，硬件的数据流具有确定性，编译器能够追踪架构状态。论文还描述了 NOP 对指令间隔的周期级控制，以及数据在不同 Functional Slice 之间逐周期流动的机制

**TauLang：一个非常新的相关研究**

[TauLang: A Language and Compiler for Space-Time Programming on Statically Scheduled Accelerators](https://arxiv.org/abs/2611.06079?utm_source=chatgpt.com)，

这篇论文的研究方向比较贴合我们现在面临的问题和实际需求：

- 面向 Groq TSP 一类静态调度加速器；
- 将时间作为编程模型中的非常重要的概念；
- 通过显式时间约束验证调度合法性；
- 联合优化 Tensor Placement 和 Cycle Scheduling；
- 在 TSP-like Cycle-Accurate Model 上进行性能评估。

**Space-Time Programming + Cycle-Accurate Modeling + Compiler Co-Design。**

## 结语：在确定性与灵活性之间寻找平衡

回到最初的问题，Groq TSP 的架构思想是否值得借鉴？

Groq 选择通过消除硬件执行过程中的不确定性，让编译器获得对整个芯片执行过程的精确控制。这是一种**非常极致的 Architecture-Compiler Co-Design。**

但对于未来面向 Agent Workload 的异构 SoC，情况可能会复杂得多。不同计算引擎之间存在不同的执行特征，片上资源需要动态共享，跨 Cluster 通信也会引入额外的时延和不确定性。我们很难要求所有执行过程都像 Groq TSP 一样完全确定。

不过，这并不意味着静态调度失去了价值。

LLM 中相当多的计算过程本身具有**很强的结构性和可预测性**。对于这些部分，我们完全可以通过 Architecture Model 提前推导计算时间、数据搬运时间、Buffer 占用和资源竞争，并利用 Cycle-Accurate Model 验证编译器生成的执行计划。对于确实存在动态行为的部分，再交给硬件调度机制处理。

**我更倾向于将未来的方向理解为：不是在 Static Scheduling 和 Dynamic Scheduling 之间二选一，而是寻找两者最合适的边界。**

而**Cycle-Accurate Microarchitecture Model**的意义，恰恰在于帮助我们找到这个边界。

它不应该只是 RTL 完成之后，用来估算性能的一个模拟工具，而应该成为 Architecture、Compiler 和 Hardware 三者之间的共同语言。

让架构设计可以更快地探索，让编译器可以更早地验证，让 RTL 实现之前的每一次设计决策，都尽可能有可执行的模型和数据作为依据。

**Architecture 不再只是等待 RTL 去验证的设计文档，Compiler 也不再只是等待 Hardware 去适配的代码生成工具。两者应该在一个可执行的微架构模型上，共同演进。**

这可能才是我们从 Groq TSP 的静态调度思想中，真正值得借鉴的东西。
