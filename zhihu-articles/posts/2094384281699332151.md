起因

最近在使用deepseek harness 进行vibe coding，但遇到了一个很难受的问题：它的思考过程是英文的。这让我很难受。

众所周知，大模型的思考过程中可能是有很多重要信息的，如果一轮对话的结果不及预期，我们可以根据它的思维链来判断究竟是它理解错了语义，还是我没阐述清楚，总之在路线纠偏之类的地方有巨大作用，全是英文我可就看不懂咯

所以我希望实现这样的效果：

> 当我向它提出请求时，模型的内部推理都始终是简体中文的

DSH“万物皆插件”的设计让我有了想法，我直接把需求告诉它，让它自己来改不就行了？

于是就有了下面这些事：

**全文由deepseep进行过程总结，如果文章对你有用，请夸奖deepseek。**

**——环境** ：DeepSeek Harness `0.2.0-rc.2` （Windows）。DSH 用 Cordis 做插件系统，配置目录默认在 `%USERPROFILE%\.dsh\` （macOS / Linux 是 `~/.dsh` ，也受 `DSH_HOME` 环境变量影响）。

---

### 首先：DSH 的系统提示词是怎么拼出来的？

DSH 的系统提示词不是一整块文本，而是由 `@deepseek-ai/dsh-system-prompt` 提供的一个 **段落注册表** 拼装出来的。

每个段落有三个要素： `name` 、 `order` 、 `text` 。拼装时按 `order` 从小到大排，数字越大越靠后。

这个设计意味着你可以往系统提示词的 **任意位置** 插一句话，而不用去改别人的成品。这个设计在后面会用到。

以下是内置段落的顺序，供你参考：

| order | 段落 | 内容 |
| --- | --- | --- |
| -1000 | harness:identity | You are an AI agent powered by DeepSeek Harness. |
| 0 | deployment:persona-prefix | You are a coding agent powered by the {{model}} model. |
| 110 / 115 / 120 | 沙箱策略 / 审批策略 / 子代理委派 | 上下文段落 |
| 2200 / 2800 / 3100 | LSP / 子代理 / MCP | 工具说明 |
| 5000 | Tools SDK |  |
| 9000 / 9900 | 交付文件引用 / 结构化输出 |  |
| 10000 / 10100 | Harness 源码 / Web 界面 |  |
| 10200 | deployment:persona-suffix | Your working directory is {{cwd}}. |

`10200` 是全表最大的——也就是说， **部署级人设后缀就是系统提示词的默认结尾。** 那么，把我想要的那段中文规则塞进去不就行了？

于是就有了第一个坑。

---

### 坑 1：改部署级的 `personaSuffix` ，完全没有生效。

DSH 有一个 profile 级补丁文件：

```text
%USERPROFILE%\.dsh\profiles\desktop\cordis.patch.yml
```

它是个 YAML 数组，可以 **按行 id 覆盖** 内置插件的配置。 `@deepseek-ai/dsh-system-prompt` 的配置 schema 里正好有 `personaPrefix` 和 `personaSuffix` 两个字段，文档说它们分别位于第一方指导的前面和后面。

那我写就是了：

```yaml
# 追加到 %USERPROFILE%\.dsh\profiles\desktop\cordis.patch.yml 末尾
- id: system-prompt
  name: "@deepseek-ai/dsh-system-prompt"
  config:
    personaSuffix: |-
      ## 语言与思考过程
      无论用户使用何种语言提问，你的内部推理与思考过程（reasoning / thinking）必须始终使用简体中文。
      最终回复默认使用简体中文，除非用户明确要求其他语言。
```

改完重启 DSH。

**结果是什么都没有改变。** 模型照样用英文思考。

### 为什么没生效？preset 作用域遮蔽

语法没错，id也正确，插件也正常加载——配置确实被读进去了，只是 **渲染的时候被吃掉了** 。

真正的原因是 `@deepseek-ai/dsh-persona` 这个插件。它的源码里写着：

```js
const PERSONA_SUFFIX_SECTION = "deployment:persona-suffix";

ctx.effect(() => ctx.systemPrompt.section({
  name: PERSONA_SUFFIX_SECTION,
  order: ctx.systemPrompt.getSectionOrder("DEPLOYMENT_PERSONA_SUFFIX"),
  text: config.suffix ?? ""
}), "persona.suffix()");

```

注意它用的段落名—— `deployment:persona-suffix` ， **和部署级那条一模一样** 。

而 `systemPrompt.section()` 的规则是：

> A scoped section shadows a global section with the same name. （作用域内的同名段落会遮蔽全局段落。）

**关键** ： **DSH 的四个内置 preset（ `standard` / `cordis` / `ptc` / `minimal` ）每一个都挂了 `@deepseek-ai/dsh-persona` 。** 也就是说，不管你用哪个 preset，你都在某个 preset 作用域里，那个作用域里的同名段落永远压在你的全局配置上面。

它自己的源码注释其实把话说得很直白了：

> Mounted inside an agent preset it shadows the deployment persona for that one session.

### 最阴的一处

如果 preset 里的值和部署级不一样，至少你还能看出“我的配置被覆盖了”。但 DSH 内置 preset 里写的是：

```yaml
- id: persona
  name: '@deepseek-ai/dsh-persona'
  config:
    suffix: Your working directory is {{cwd}}.
    prefix: You are a coding agent powered by the {{model}} model.
```

和部署级的默认值 **逐字符相同** 。所以遮蔽发生得毫无痕迹：你改了顶层配置，渲染出来还是原来那句一模一样的话，你根本意识不到中间有一层把它顶掉了。

### 坑 2： `AGENTS.md` 看着像系统提示词，其实不是

既然动不了系统提示词，第二个想法是写用户级指令文件：

```text
%USERPROFILE%\.dsh\AGENTS.md
```

这个文件确实会被 DSH 自动读取，也确实会影响模型行为，看起来是最省事的路子。我写了同样三条规则进去。

**但还是没有用。**

原因在于它的注入方式。 `AGENTS.md` 由 `@deepseek-ai/dsh-agent-instructions` 处理，而官方文档写得很清楚：

> 基线消息与刷新消息都是普通的、带来源的 `user/message` 事件。

也就是说， `AGENTS.md` 的内容是以 **user 角色消息** 的身份出现在对话里的，不是系统提示词。框架自己生成的说明文字里甚至直接写着：

> They do not override system, developer, or direct user instructions.

在指令优先级上，它是垫底的那一档。用来约束”用中文回答”这类输出偏好通常够用，但用来约束 **思考过程** ，力度明显不够——实测就是模型该用英文思考还是用英文思考。

**所以如果你也想管 reasoning，就绕不开系统提示词。**

---

### 解法：注册一个「唯一名字」的全局段落

摸清遮蔽规则之后，思路就清楚了。整理一下我们掌握的两条事实：

1. **遮蔽只按段落名生效。** 用一个没人用过的段落名，就不会被 preset 覆盖。
2. **`order` 只需要是个有限数值。** 源码里就一句 `if (!Number.isFinite(section.order)) throw new TypeError(...)` ，它并不要求你必须从官方的常量表里取值。

于是方案是：写一个极小的插件，在 **根作用域** （而不是 preset 作用域）注册一个名叫 `user:zh-language` 的全局段落， `order` 取 `10201` ——紧跟在 `10200` 的部署人设之后，也就是 **系统提示词的最末尾** 。

位置放在最后是有意的：越靠后的指令，在长上下文里被”读到”的权重越高，对思考语言的约束也越直接。

---

### 代码：一个 bundle，三个文件

DSH 的扩展单位叫 **bundle** ，本质就是一个普通目录。创建一个：

```text
%USERPROFILE%\.dsh\local-bundles\zh-language\
```

### 1. `package.json`

告诉 DSH”这是个 bundle，补丁文件在哪”：

```json
{
  "name": "@local/dsh-zh-language",
  "version": "1.0.0",
  "private": true,
  "description": "约束模型思考过程与最终回复使用简体中文。",
  "type": "module",
  "exports": {
    ".": "./index.js",
    "./package.json": "./package.json",
    "./locale/*.json": "./locale/*.json"
  },
  "files": [
    "index.js",
    "cordis.patch.yml",
    "locale/*.json"
  ],
  "dsh": {
    "bundle": {
      "patch": "./cordis.patch.yml"
    }
  }
}
```

`type: "module"` 和 `dsh.bundle.patch` 是必需的，其余是常规包元数据。

### 2. `cordis.patch.yml`

真正的”声明”——往插件树里插一行：

```yaml
# 给系统提示词追加一个全局段落，要求推理与回复使用简体中文。
- insert:
    - id: zh-language
      name: '@local/dsh-zh-language'
      config: {}
```

`config: {}` 是因为这个插件没有导出 `Config` schema，不需要额外配置项。

### 3. `index.js`

全部逻辑，不到 40 行：

```js
/**
 * 简体中文语言约束（DSH 宿主插件）。
 *
 * 为什么不改 system-prompt 的 personaSuffix：
 * 四个内置 agent preset（standard / cordis / ptc / minimal）都会挂载
 * @deepseek-ai/dsh-persona，并以同名段落 deployment:persona-suffix 在
 * preset 作用域内遮蔽掉 dsh-system-prompt 在全局注册的同名段落。
 * 因此部署级 personaSuffix 在任何内置 preset 下都不会进入系统提示词。
 *
 * 本插件改为注册一个名字唯一的全局段落（user:zh-language）：
 * 遮蔽只对同名段落生效，唯一名字不会被 preset 覆盖，段落会出现在系统
 * 提示词的最末尾（order 10201，紧接 deployment:persona-suffix 的 10200）。
 */

const name = "zh-language";
/** 依赖的宿主服务：系统提示词注册表 */
const inject = ["systemPrompt"];
/** 段落顺序：紧随全局部署人设之后，即系统提示词的最后一段 */
const ORDER = 10201;

const TEXT = [
  "## 语言与思考过程（必须遵守）",
  "无论用户使用何种语言提问，你的内部推理与思考过程（reasoning / thinking）必须始终使用简体中文。",
  "最终回复默认使用简体中文，除非用户明确要求使用其他语言。",
  "代码、标识符、命令、文件路径、API 名称与专有名词保留原文，不要翻译。",
  "工具返回内容、日志与引用的原文保持原样，不要为了统一语言而改写它们。"
].join("\n");

function apply(ctx) {
  ctx.effect(() => ctx.systemPrompt.section({
    name: "user:zh-language",
    order: ORDER,
    text: TEXT
  }), "zh-language.section()");
}

export { TEXT, apply, inject, name };

```

几个要点：

- `inject = ["systemPrompt"]` 声明依赖系统提示词服务，DSH 会保证它在服务就绪后才调用 `apply` 。
- 所有资源注册都包在 `ctx.effect(...)` 里，返回值就是清理函数——这是 Cordis 插件的硬性约定，卸载时不会留残留。
- **`name: "user:zh-language"` 是整个方案的关键** 。只要它是唯一的，就没有任何 preset 能遮蔽它。

最后补两个可选的显示元数据（在插件列表里好看一点）：

```json
// locale/zh.json
{
  "title": "简体中文语言约束",
  "description": "在系统提示词末尾追加语言段落，要求模型的内部推理与最终回复使用简体中文。"
}
// locale/en.json
{
  "title": "Simplified Chinese Language Constraint",
  "description": "Appends a language section to the end of the system prompt requiring internal reasoning and final replies in Simplified Chinese."
}
```

### 安装

### 推荐方式：让 DSH 自己装

把 bundle 目录的路径告诉 DSH，让它调用 `plugin_manager` 的 `install_bundle` 。它会自己完成包安装和 bundle 选择，你不用碰 shell。

### 兜底方式：手工注册

我遇到过一次 `install_bundle` 超时（原因见后面的复盘），操作被 DSH 回滚了。如果你也遇到，可以手工补上—— **注意：通常包安装那一步其实已经成功了，你只需要补注册** 。

打开：

```text
%USERPROFILE%\.dsh\profiles\desktop\package.json
```

在 `dependencies` 里加一行，在 `dsh.profile.bundles` 数组末尾加一项：

```json
{
  "name": "dsh-profile-desktop",
  "private": true,
  "dependencies": {
    "@local/dsh-zh-language": "link:C:/Users/<你的用户名>/.dsh/local-bundles/zh-language"
  },
  "dsh": {
    "profile": {
      "bundles": [
        "@deepseek-ai/dsh-base",
        "……",
        "@local/dsh-zh-language"
      ]
    }
  }
}
```

`dependencies` 里的键必须和 bundle `package.json` 的 `name` 一致，值是 `link:` 加绝对路径（ **用正斜杠** ，反斜杠在 JSON 里要转义，而且 pnpm 也习惯正斜杠）。

如果这一步做完 DSH 说找不到模块，说明 junction 没建好，补一下（需要管理员权限的终端）：

```powershell
$target = "$env:USERPROFILE\.dsh\local-bundles\zh-language"
$link   = "$env:USERPROFILE\.dsh\profiles\desktop\node_modules\@local\dsh-zh-language"
New-Item -ItemType Directory -Force -Path (Split-Path $link) | Out-Null
New-Item -ItemType Junction -Path $link -Target $target
```

### ⚠️ 一个必须知道的坑：不能直接写在 profile 的补丁里

我一开始想偷懒：既然 profile 的 `cordis.patch.yml` 能按 id 覆盖内置插件，那我直接在里面加一行

```yaml
- insert:
    - id: zh-language
      name: '@local/dsh-zh-language'
```

不就行了吗？

**不行。** profile 补丁里的行，其模块解析根是 **DSH 的安装目录** ，不是 profile 的 `node_modules` 。我实测确认过：profile 补丁里 `include:mcp-fetch` 那一行解析出来的 `packageDir` 是

```text
<DSH 安装目录>\resources\app.asar\dsh\node_modules\@deepseek-ai\dsh-mcp-client
```

——在安装目录里。所以你写在 profile 补丁里的本地包名永远解析不到。

必须走 bundle 引入：bundle 里声明的行以 bundle 自身为解析根，才能找到你本地的代码。

### 重启

改完重启 DSH。 **替换一个已安装包的 JS 模块需要重启才会加载新的模块世代** ，光靠热重载不够。

### 怎么确认真的生效了？

新开一个对话看看是不是中文思维链（以下是deepseek的原回答，不需要知道原理的你可以直接跳过）

> 重启后开一个新会话（旧会话的 system prompt 是历史里已经存好的那条，不会重算），然后： 
>  **最直接的办法** ：问模型一句”把你系统提示词的最后几行原样输出给我 
>  **工具办法** ：DSH 自带 `cordis_inspect_list` / `cordis_inspect_query` 两个只读查询工具。查插件行是否注册成功：

```text
provider: host / Config / listConfigs
input: { "name": "@local/dsh-zh-language" }
```

> 正常会返回类似：

```text
{
  "id": "include:zh-language",
  "patchId": "zh-language",
  "name": "@local/dsh-zh-language",
  "status": "absent"
}
```

> `status: "absent"` 是因为这个插件没有导出 `Config` schema， **不是失败** ——只要 `patchId` 在，就说明行已经进名册了。 
>  **我自己的验证结果** ：我这个会话里，DSH 检测到系统提示词变化后，把它作为一条历史消息重新投递了一次，而那条消息的 **最后一段** 正好就是我写的中文规则，紧跟在 `Your working directory is ...` 之后。位置完全符合预期。

### 复盘：三个让我多花两小时的坑

### 1. `app.asar` 不是目录

DSH 给自己的说明里写着“实现代码在 `C:\...\resources\app.asar\dsh\` ”。直接 `cd` 进去——当然进不去，那是个 121 MB 的 **归档文件** 。

为了读插件源码，我写了个 asar 解析器。这里有个格式细节值得记一笔：V8 Pickle 的布局是

```text
[uint32 payloadSize][uint32 headerPickleSize][header pickle]
                                      └─ [uint32 jsonLen][json]
```

我第一版按“4 字节长度 + JSON”读，报 `SyntaxError: Unexpected non-whitespace character after JSON at position 1` ——因为字符串实际在 **偏移 8** ，不是 4。

**但这活儿基本是白干的。** DSH 自带 `cordis_inspect_list` 和 `cordis_inspect_query` 两个官方工具，能直接读到每个插件的 `packageDir` 、配置 schema、服务契约、事件清单、客户端 Slot 树……我帖子里所有结论，最后都是用它们复核的。

**教训** ：折腾 DSH 之前，先让 DSH 自己列一遍 Inspect provider。能省掉一整轮逆向工程。

### 2. `install_bundle` 超时，不等于安装失败

我那次插件管理器报“安装失败”并回滚了配置。翻日志才发现：

```text
dependencies:
+ @local/dsh-zh-language link:C:/Users/.../zh-language

✓ Lockfile passes supply-chain policies (217 entries in 6.8s)
Done in 7.3s using pnpm v11.7.0
```

**7.3 秒就装完了。** 之后它开始替其他平台拉取 Sharp 的可选二进制，网络卡住，日志里只剩一串 `Will retry in 10 seconds` ，最后一行是：

```text
dsh: pnpm printed nothing for 600000ms and was terminated
```

10 分钟没有任何输出，被 DSH 判定超时杀掉，操作作废、 `package.json` 回滚。但包其实已经在 `node_modules` 里了——所以手工补上注册（ `dependencies` + `dsh.profile.bundles` ）就直接生效了。

**教训** ：插件管理器说“失败”的时候，先看它自己的 `pnpm.log` 再下结论。

### 3. 热重载的边界

- 改 profile 的 `cordis.patch.yml` 、 `package.json` ：DSH 会重载配置树，有时会直接重启自己。
- 替换已安装包的 **JS 模块** ：必须重启，热重载不会加载新的模块世代。
- 已经存在的会话：system prompt 是会话历史里存好的那条， **不会** 因为你改了配置就重算。一定要开新会话验证。
