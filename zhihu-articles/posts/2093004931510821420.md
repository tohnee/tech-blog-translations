## 关于 OxyGen 本身：具身场景下的实时性约束与调度空间

简单来说，OxyGen 关注这样一个问题：机器人在生活场景中的落地需要对话、记忆等语言输出能力，而在端侧处理这些任务又会与并发的动作推理互相竞争资源，导致机器人长时间卡顿；**基于**$\pi_{0.5}$**这类既支持动作输出、又支持语言输出的模型架构，如何利用好共享的视觉感知输入，通过合理的调度，同时提升动作和语言输出的速度（而不是互相竞争）？**

我们的做法是，对动作和语言推理的 KV Cache 做统一的管理：除了跨任务（动作 / 语言）的共享外，还可以把单个语言任务的解码请求划分到不同的推理轮次中，并与其他请求 batch 起来处理。其实方法本身比较直接（可以理解为 prefix reuse + continuous batching for 具身）。**这里关键的观察在于，具身场景对于动作和语言输出的实时性要求不同：**

- 流畅的动作执行，对于动作块（action chunk）的输出延时有极高的要求（e.g., 百毫秒级延时）。这使得在动作之间等待一个完整的语言请求完成，是不可接受的。
- 大多数情况下，语言输出的实时性要求并不高，只要一段时间内的吞吐达到要求即可。这为我们拆分语言解码请求，“插缝”到动作生成中提供了空间。拆分后，来自不同时刻的请求 batch 起来，进一步提供了加速空间。

具体的方法和实验，欢迎大家去看[论文](https://arxiv.org/abs/2603.14371)以及[代码](https://github.com/air-embodied-brain/OxyGen)（ $\pi_{0.5}$ 上至多 3.7 倍加速，也有更多 backbone 以及真机延时验证）。以下是一个 LIBERO 仿真中的例子：模型需要同时输出可供机械臂执行的动作，以及对应的文本形式的记忆（即“当前已经完成了什么”）。我们固定了仿真器中每次执行对应的耗时，来展示有 / 无上述 KV Cache 优化的端到端延时差异（25.1 → 18.7 s）。虽然方法本身不改模型，我们在这个 demo 中还是为语言部分训了一个 LoRA adapter。

## OxyGen 之外的探索空间：模型与场景的拓展

今天，基于这类 Mixture-of-Transformers (MoT) 架构的模型越来越多，无论是在具身领域的世界动作模型（WAM），还是更广泛领域中的各类多模态生成模型。其中比较有代表性的应该是 Cosmos 3 这类统一的 omnimodal 模型。而 OxyGen 本身的方法和实现还是更专注于 $\pi_{0.5}$ 这类 VLA 模型。**如何把类似的思路拓展到全模态的 MoT 模型上，实现更普遍意义下的多任务并行推理加速，会是很有意思的问题。**简单 brainstorm 一下：

- 不同模态输出之间如果存在依赖关系（不能够简单地拆分并独立调度），怎么解决？
- 当前输入能否对历史请求的输出产生影响，在每轮推理时持续更新，以保持时效性？
- 当并发足够高（并非端侧场景）时，KV Cache manager 本身是否会成为性能瓶颈？
- 如何和最近比较火的全双工大模型等方向结合？
- ……

## 从 Opus 到 Astra，一部 coding agent 进化史（💩）

OxyGen 这个工作几乎跨越了近一年 coding agent 膨胀的整个周期，repo 里也许堆了不同时代模型的💩（已经多次整理过，放心食用）。

去年夏天开始做时，还在 Chat 里和 Claude Sonnet 4 （maybe，记不清了）聊 idea，后来在 GitHub 学生免费的 Copilot 里用刚出的 Gemini 3 Pro 写代码。

到了今年 1~2 月份，在 Claude Code + Opus 4.6 加持下一路狂飙，刷新了我对 coding agent 的认知：原来我无需想清楚每个实现细节，只需要关注顶层设计和整个系统的输入输出。真正重要的是，监督模型设计严谨的测试和验证，拷打模型解释自己究竟做了什么，为什么这么做：就像一个真正的下属一样，自己不用改一行 code。

同时我也意识到 context 对于 agent 的重要性：把完整的 codebase 和 latex repo 放在一起，让模型自己基于代码和实验结果写 paper，或基于 paper 整理和修改代码。虽然模型经常会把 paper 写得如同实验报告一般（事无巨细，把代码翻译成文字），但在开始写作的初期，对于冷启动的加速是巨大的；在实验结果整理和作图中也是效率倍增。**但在问题的定义、技术贡献的提炼等涉及 story telling 的部分，还是非常需要人的思考。**

这篇工作最初在 3 月投到了 ECCV，分数不理想；在 5 月极限转投 NeurIPS 时，甚至在 Opus 4.8（这也是最后一个月使用 Claude，因为量大管饱的 GPT 5.5 马上来了）的一手操办下几天内完成了一个新设备上的环境搭建，并重跑了若干个实验。再到 8 月份 NeurIPS rebuttal 时就更不用说：GPT 5.6 Sol 一手包办所有新实验的代码实现，运行，结果整理和验证（出于对自己工作的严谨负责，人还是要拷打各种存疑的细节）。**最头疼的点在于调教不说人话的模型如何写作（希望下一代模型多说人话，少说鬼话）。**

再到最近的几天，刚刚驾驶 Astra 改完 camera ready。有时很难说 agent 让人变得轻松了还是更累了：为了跟上 agent 产出💩的速度，并且及时铲💩，可能要付出数倍于自己拉💩的精力（尤其是当你有很多 agent 在拉💩时）。

## 展望：未来的 System Research 做什么，如何做？

暴论：输入输出明确，目标产出明确的 system research 会变成 agent 几乎完全能够自己 handle 的 pure engineering（只不过，可能需要合适的工作流和 context，非常多的 token，和个别复杂 case 的人工提示），尤其是那些规模不大而易于验证的任务（例如单机上的算子优化）。

很遗憾的是，前 agent 时代的许多 system research 工作量恰恰是靠这部分内容撑起来的。未来 system research 的评价标准，应该要有一个大的变化。某种程度上也许也要变成故事会。你别笑，讲故事这方面，人类远胜于 AI。

目前这个阶段，我个人的判断和目标是：充分考虑上层的算法和应用，尽可能打通去做全栈的、端到端的优化，留出尽可能简单而直接的接口。这样的系统，能够产生最大的影响力。换言之，解决很多底层复杂的问题，可以获得技术上的征服感，但如果不能交付一个端到端的简单高效的解决方案，就大概率处于 nobody cares 的状态（惨痛的教训）。或者用老生常谈的话来说，不要拿着锤子找钉子，对系统研究尤其适用。

所以，今年也投了若干篇 AI conference paper，尝试朝着全栈的、端到端的最终目标前进。**相信算法、系统、硬件，在某个时刻将殊途同归：在 AI 越来越强大的今天以及未来，用技术栈定义自己是一种自我设限。**在这个尚且不算老登的年龄（卡着00的边哈哈），我还有更多可以学习、可以进步的空间和机会。反而最令人焦虑的，是什么样的问题真正重要，值得且应该由自己去解决。
