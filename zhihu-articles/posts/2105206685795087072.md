先说结论：编码智能体最容易出事的地方，往往不是代码写不出来，而是计划本身没人认真审过。它对着没打开过的文件写计划，写完自己审自己，改了计划外的文件，最后在没有任何运行记录的情况下宣布「测试全部通过」。

我写了一个开源的智能体 skill，叫 plan-on-trial（计划受审）。**它把一份实施计划当成案件来审：先写带证据的案卷，再由全新上下文的审查者质询，裁定通过后才动手，写完代码再拿真实的 git diff 和运行记录开庭判决。**

仓库有中英文版 SKILL.md 和说明、一个只用 Python 3 标准库和 git、不联网的辅助脚本 plantrial.py，以及空白模板和一套「部分退款」的完整示例，MIT 许可。

---

## 一、智能体的计划，通常败在哪几步

说明文档里列的几种情况，我自己用智能体写代码时基本都遇到过：

- 凭记忆写计划：引用的文件和 API 根本没打开看过
- 自己审自己：写完计划紧接着自审，结果自己同意自己
- 用「万一」把计划撑大：加了一堆谁也触发不了的防御
- 悄悄越界：多改了几个文件，动了没人批准的数据库迁移或锁文件
- 空口报喜：说测试全过，却拿不出一次真实运行记录

plan-on-trial 的每一步，都对着上面某一种情况设检查。

---

## 二、先称重：不是每个改动都要走全套

第一步是给改动分级，写在案卷顶部：

1. FEATHER（羽量）：一个问题、一次探查、一行修复。跑一次便宜的检查，两句话汇报，不写案卷
2. MIDDLE（中量）：1 到 3 个文件，不改契约，容易回滚。对话里写简短案卷，质询可选，开庭必做
3. HEAVY（重量）：数据库结构、公开 API、金额、认证、新依赖、多模块，或任何难以撤销的事。完整案卷、全新上下文质询、裁定，然后开庭

文档里有句话我很喜欢：对一个单行错别字修复强行走全套流程，本身就是一种失败。犹豫的时候，只有改错后撤销代价很高才选更重的一级。

## 三、案卷：把计划写成能被检验的东西

案卷有五个部分：

- 前提（K1、K2…）：计划依赖的代码事实，每条都要带证据，可以是「路径:行号」、一条命令及其输出，或者老实写 ASSUMED 并说明谁能确认
- 标准（C1、C2…）：带具体数值的可观察结果，比如「100.00 的发票退 30.00 后余额为 70.00」，每条都写清怎么验证、期望什么结果
- 步骤（S1、S2…）：精确到文件，并注明它交付哪几条标准
- 闸门（G1、G2…）：数据库结构、公开 API、新依赖这类需要人点头的事，没人签字前一直是 signed: no
- 不做的事：明确写下不做什么，日后挡住范围蔓延靠的就是它

写完用脚本检查，结果分三档：VAGUE（有结构性漏洞，比如标准没有验证方式、步骤没写文件）、THIN（能审但有软肋，比如有 ASSUMED 前提或「as needed」「robust」这类含糊措辞）、READY（可以进入质询）。检查完要停下来等人看，不要直接开始实现。

---

## 四、质询：换一个「没听过作者解释」的审查者

审查者不能是写计划的那个会话。新开对话、子智能体或者换个模型，只给它案卷和代码仓库，不给作者的对话记录。理由很直接：继承了作者推理过程的审查者，往往也继承了作者的盲点。

每条异议必须分级，这是我觉得最实用的设计，文档叫它「YAGNI 刹车」：

- SEEN（已见）：能指出出问题的代码，必须给「路径:行号」
- PLAUSIBLE（可信）：暂无证据，但有一条具体的触发路径，必须写出来
- SPECULATIVE（臆测）：「万一将来……」，没有触发路径，直接搁置，永远不加进计划

然后作者逐条修复或给出理由驳回，再用脚本出裁定：格式不合格是 MISTRIAL，有未关闭的 SEEN critical 或三条以上 critical/major 是 RETRY（重写计划，别打补丁），还有未关闭异议是 AMEND，全部处理完才是 CLEARED。只有 CLEARED 之后才开始写代码。

---

## 五、开庭：拿 diff 和运行记录说话

实现过程中，每跑一次某条标准的检查，就在 evidence.log 里按实际结果记一行，失败也要记；没跑过的命令绝不能写。

写完代码后开庭，脚本读取 git diff（相对 base、已暂存、未跟踪）和证据日志，报告这些问题：

- UNDELIVERED：某个计划步骤的文件一个都没改
- UNPLANNED：改了没有任何步骤列出的文件
- UNSIGNED：闸门没签字，但它覆盖的文件被改了
- UNGATED：改了锁文件、依赖清单、迁移、.env、CI、Dockerfile 这类高风险文件，却没有闸门覆盖
- UNPROVEN 和 FAILED：标准没有运行记录，或最后一次运行没通过

判决从差到好是 BROKEN、UNPROVEN、DRIFTED、HOLDS。三个子命令的退出码在 READY、CLEARED、HOLDS 时为 0，其他情况非 0，所以可以直接放进 pre-push 钩子或 CI。

## 六、一个「部分退款」的例子

仓库 examples 里有一个 HEAVY 级别的完整例子。我在本地用仓库自带的示例文件跑了前两步：

```text
$ python3 plantrial.py lint examples/refund.docket.md
ASSUMED     K3    unverified claim; check it or name who confirms it

VERDICT: THIN

$ python3 plantrial.py rule examples/refund.objections.md
FIXED       O1    [S1] SEEN critical
OPEN        O2    [K3] PLAUSIBLE major
PARKED      O3    [S3] no trigger path - not added to the plan
REJECTED    O4    [C3] SEEN minor
SUMMARY     -     open=1 parked=1 malformed=0

VERDICT: AMEND
```

意思是：K3 只是假设，所以案卷「单薄」；O1（支付通道重试时没带幂等键）已修复，O2 还没关闭，所以要「修改」；那条「将来可能要支持多原因退款」的臆测被搁置了。

说明文档里接着演示了开庭：发现两处计划外改动、一个没签字就被改的迁移闸门、一条从没跑过的标准，判为 BROKEN；让闸门签字、回滚顺手改的文件、补跑那条标准之后，再开庭判为 HOLDS。

## 七、怎么装、怎么用

克隆到智能体的技能目录就行，以 Claude Code 为例：

```text
git clone https://github.com/fangdididi/plan-on-trial ~/.claude/skills/plan-on-trial
```

Codex 放到 ~/.codex/skills/plan-on-trial，Cursor 放到项目里的 .cursor/skills/plan-on-trial。其他智能体让它读 SKILL.md，并把 plantrial.py 和 templates 放在同一目录。

装好后可以直接对智能体说：「用 plan-on-trial 做这个改动：增加部分退款」「先写案卷，停下来等我批准」「对照 main 开庭」。

最后两点提醒，也是文档里写明的：闸门只是智能体遵守的约定，不是安全边界，必须强制执行的事请用工具自带的权限设置；开庭只看文件名，看不懂代码含义，即便判了 HOLDS，也要亲自读一遍 diff。
