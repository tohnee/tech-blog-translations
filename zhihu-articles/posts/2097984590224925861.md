209M 参数，拿下三个时间序列预测基准的第一。

这是 Mistral AI 在 2026 年 10 月 15 日发布 Timestral 时给出的成绩：在 GIFT-Eval、TIME 和 fev-bench 的预训练、零样本模型比较中，Timestral-209M 均排名第一。

![](https://pic1.zhimg.com/v2-980725828b2a3293e170b0c35313a4ee_r.jpg)

对做预测任务的人来说，我们关注的是： **这样一个基础模型，能不能用自己的数据继续训练？**

例如，手里已经有一份按小时记录的设备指标，希望结合历史读数和日历信息，预测未来几天的变化。从一张表到一个可用的微调模型，中间还需要数据配置、训练、验证、回测和导出。

开源项目 **timestral-ft** 把这些步骤串成了一套工作流。它支持全参数和 LoRA 两种微调方式，既能通过命令行运行，也提供 Python API。下面从项目能力、上手过程和实验结果三个方面，看看它能做什么。

项目地址 [https://github.com/elarazju/timestral-ft](https://github.com/elarazju/timestral-ft)

## 1. Timestral 为什么值得关注？

时间序列基础模型将预训练的思路带入预测任务：先从大量序列中学习可迁移的规律，再面对新的数据进行预测。直接使用预训练权重、不在目标数据上更新参数，就是这里所说的零样本预测。

Timestral 提供 5M、28M、123M 和 209M 四个规模，支持多变量联合预测、历史协变量和未来已知协变量；每个时间点输出 21 个分位数，推理上下文最长可达 32,768 步，也支持 CPU 推理。

项目地址 [https://github.com/mistralai/timestral](https://github.com/mistralai/timestral)

这些能力对应着几个具体需求。

**多个目标可以一起预测。** 例如，一台设备的多个传感器指标可以作为联合预测目标，模型有机会利用变量之间的关系。

**预测可以使用额外信息。** 历史传感器读数属于过去已知的信息；小时、星期几，以及提前确定的排班，可以属于未来已知的信息。两类特征在预测时的可用范围不同，需要明确区分。

**输出可以表达不确定性。** 除了中位数预测，还可以查看较低和较高分位数之间的区间。对于容量规划、库存安排等任务，预测区间能为决策提供额外信息。

基础模型提供了起点，而具体业务数据中的周期、尺度和变量关系，仍然需要通过实际回测来检验。微调就是可以尝试的一条适配路径。

## 2. timestral-ft 提供了什么？

timestral-ft 是一个面向 Timestral 的独立社区微调工具包，它复用官方网络，并提供训练层、表格数据处理和模型产物管理。

整个使用过程可以概括为：

**CSV / Parquet / DataFrame → 配置目标与特征 → 微调 → 滚动回测 → 导出模型。**

训练方式有两种：

| 方式 | 更新哪些参数 | 在项目中的使用方式 |
| --- | --- | --- |
| 全参数微调 | 更新全部网络参数 | 训练时选择 full |
| LoRA 微调 | 冻结基础参数，训练注入注意力投影的低秩适配器 | 训练时选择 lora |

项目默认的 LoRA 设置为 rank=8、alpha=16。在仓库的 Timestral-5M 示例中，LoRA 需要训练 92,160 个参数，全参数微调则更新 5,208,960 个参数。前者约为后者的 1.77%。这里比较的是可训练参数量，实际内存和耗时还取决于输入长度、批量和设备。

工具同时提供验证集选优、早停、梯度累积、断点续训和预处理配置保存。这意味着，跑完一次训练后，可以继续评估、加载预测或导出权重。

## 3. 跑通第一个微调实验

初次使用可以从仓库自带的 ETTh1 示例开始。这个例子使用 Timestral-5M，根据过去 256 个时间步，预测未来 96 个时间步的 `OT` ，同时使用历史特征与日历特征。

以下命令沿用项目文档，适用于 macOS／Linux 的终端环境。

### 安装项目并准备数据

```text
git clone https://github.com/elarazju/timestral-ft.git
cd timestral-ft

python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -e .

python scripts/run_etth1.py --prepare-only

```

准备脚本会校验数据、按时间划分训练／验证／测试集，并生成示例使用的时间特征。首次加载模型时还需要下载预训练权重。

### 启动 LoRA 微调

```text
timestral-ft train \
  --config examples/etth1.yaml \
  --mode lora \
  --output runs/blog/lora

```

这个示例默认使用 CPU，最多运行 200 个优化步骤。它已经包含验证和检查点选择逻辑，因此不必先自行编写训练循环。

如果要比较全参数微调，使用相同配置、换一个输出目录即可：

```text
timestral-ft train \
  --config examples/etth1.yaml \
  --mode full \
  --output runs/blog/full

```

Apple Silicon 用户可以在命令后增加 `--device mps` 。

### 在测试集上回测

```text
timestral-ft evaluate \
  --model runs/blog/lora/model \
  --data data/etth1/test.parquet \
  --history data/etth1/history.parquet \
  --output runs/blog/lora/evaluation

```

这里会做滚动回测：在多个历史时间点发起预测，再与已经发生的真实值比较。输出包括预测文件、误差指标和元数据，便于进一步检查哪些时间段预测得好、哪些时间段出现偏差。

评估时既可以观察 MAE、MSE 等点预测误差，也可以查看分位数误差和 80% 区间覆盖率。训练损失下降只是过程信号，测试集上的表现才是判断本次适配是否有效的依据。

### 导出适配器与合并权重

```text
timestral-ft export \
  --model runs/blog/lora/model \
  --output runs/blog/adapter \
  --adapter-only

timestral-ft export \
  --model runs/blog/adapter \
  --output runs/blog/merged

```

独立适配器保留微调增量，并依赖对应的基础权重；合并导出则生成官方兼容格式。处理原始表格时，还应保留随模型保存的预处理配置，确保预测阶段对列和类别的处理与训练时一致。

## 4. 换成自己的数据，关键在于列的含义

示例跑通后，下一步是配置自己的数据。每行表示一个序列在一个时间点的观测，数据配置需要说明时间列、预测目标以及可用的额外特征。

ETTh1 示例中的配置如下：

```text
data:
  time_column: date
  target_columns: [OT]
  past_covariates: [HUFL]
  known_covariates: [hour_sin, hour_cos]
  categorical_known_covariates: [hour_category, weekday_category]
  frequency: h

```

`OT` 是要预测的目标； `HUFL` 只提供历史观测；小时和星期信息在预测未来时已经可以确定，因此作为未来已知协变量。

迁移到自己的任务时，可以依照下面的关系修改配置：

| 数据内容 | 配置字段 |
| --- | --- |
| 时间戳 | time_column |
| 门店、设备或其他序列标识 | id_column，单序列可省略 |
| 一个或多个预测目标 | target_columns |
| 只在历史区间可得的数值特征 | past_covariates |
| 预测未来时已经知道的数值特征 | known_covariates |
| 历史／未来已知分类特征 | 对应的 categorical_*_covariates |

例如，预测某台设备的未来负荷时，可以使用已经确定的生产计划；预测区间内尚未发生的实际传感器读数，则不能作为“未来已知”输入。

**配置特征时，应该以发起预测的那个时刻为准。** 某一列后来出现在完整数据表里，并不意味着当时就能获得它。

训练、验证和测试集也需要提前按时间划分。项目会限制窗口标签不跨越划分边界，分类词表仅从训练集建立；这些实现能帮助保持评估边界，但业务特征本身是否提前可得，仍需要使用者正确判断。

## 5. 微调之后，效果提升了多少？

项目公开记录中，一个比较直观的结果来自前面的 ETTh1 单目标协变量实验。

| 方式 | MAE ↓ | WQL ↓ | 80% 区间覆盖率 |
| --- | --- | --- | --- |
| 原模型 | 1.897857 | 0.275712 | 62.60% |
| 全参数微调 | 1.658971 | 0.238410 | 74.76% |
| LoRA 微调 | 1.657016 | 0.238540 | 73.75% |

在这一设置下，LoRA 的 MAE 相比原模型降低约 **12.7%**，与全参数微调接近；区间覆盖率也更接近名义上的 80%。结果来自 Timestral-5M、种子 42、最多 200 个优化步骤的实验，测试包含 30 个滚动起点。

这组数字对应的是仅预测 `OT` 、历史长度 256、预测长度和滑窗步长均为 96 的设置，MAE 使用原始单位。常见的 ETT 多变量基准涉及不同目标和标准化方式，两者不能直接混比。

项目还提供了多变量、多种子的结果。例如，在联合预测 ETTh1 全部 7 列、历史长度 96、预测长度 96 的设置下：

| 方式 | 标准化 MSE ↓ |
| --- | --- |
| 原模型 | 0.43385 |
| 全参数微调 | 0.41122 ± 0.00098 |
| LoRA 微调 | 0.41476 ± 0.00096 |

微调结果为三个种子的均值与样本标准差。这个设置下也观察到了改善，但标准差只描述不同种子的变化，不能直接当作统计显著性的证明。

## 6. 从一个数据集走向 97 项任务，结论更有意思

单个示例能够说明微调的可能性，更广泛的实验则展示了适用边界。

timestral-ft 分别对 Timestral-5M 和 Timestral-209M 完成了 GIFT-Eval 全部 97 项任务的适配与测试。两轮实验采用各自的训练配方，聚合结果如下：

| 实验 | CRPS 近似相对变化 ↓ | MASE 相对变化 ↓ |
| --- | --- | --- |
| Timestral-5M LoRA | +0.030% | +0.043% |
| Timestral-209M 选中 LoRA／回退方案 | +0.569% | +0.507% |

这里先将每项任务的指标除以同任务 Seasonal Naive 指标，再取几何均值，与原模型比较。正值表示误差上升。 **两轮配方都没有获得测试集的整体收益。** 其中，5M 的变化非常小；两轮均为单种子，无法据此判断差异是否稳定。

209M 实验尤其值得关注：验证集选中的检查点改善了验证指标，但收益没有迁移到测试集；97 个任务中，有 21 个最终依据验证结果回退到原模型。报告提出，反复在单一验证时间段选优可能是原因之一，但目前尚无因果对照证明。

具体业务是否值得微调，需要看目标数据上的结果。ETTh1 示例中的改善，不能直接转换成销量、流量或其他领域的收益承诺；GIFT-Eval 的聚合负结果，也不能证明所有任务上的微调都无效。
