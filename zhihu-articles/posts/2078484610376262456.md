# 提示词工程与 Agent 上下文

## 1. Prompt：AI 与人沟通的核心接口

**Prompt（提示词）** 本质上是人与 AI 沟通的自然语言接口。

从 ChatGPT 出现以后，人们开始越来越频繁地通过自然语言向模型下达指令，例如：

- “帮我生成一个游戏。”
- “帮我完成这份作业。”
- “解释一下 Assembly。”
- “生成文字、代码或者图片。”

AI 根据 Prompt 返回相应结果，因此 Prompt 成为了使用生成式 AI 时非常重要的一环。

### Prompt 带来的一个关键变化

早期人们可能把 Prompt 简单理解为：

> “我在聊天框里输入的那句话。”

但对于今天的 **Agent** 来说，这种理解已经过于狭窄。

**Prompt 并不只是 User Message，而是构成 Agent 上下文的大量信息。**

---

## 2. Prompt 的含义已经从“一句话”扩展到“整个上下文”

一个 Agent 在真正开始和用户对话之前，往往已经接收了大量内容。

可以粗略理解为：

$$
\text{Agent Context} = \text{System Prompt} + \text{Instructions} + \text{Files} + \text{Tools} + \text{Tool Results} + \text{User Messages} +\cdots
$$

因此，今天讨论 **Prompt Engineering（提示词工程）** 时，不能只考虑“怎么写一句更好的指令”，而应该考虑：

> **如何设计整个 Agent 能看到的上下文。**

---

## 3. System Prompt：Agent 在聊天前就已经收到的 Prompt

用户看到的聊天窗口并不是 Agent 获得的全部信息。

在用户发送第一条消息之前，Agent 通常就已经拥有一个 **System Prompt（系统提示词）** 。

System Prompt 可以规定 Agent 的基本行为，例如：

- 使用什么语言回答；
- 遵循什么规则；
- 扮演什么角色；
- 怎样使用工具；
- 怎样处理任务。

例如，可以在 System Prompt 中规定：

> 无论 User Message 使用什么语言，都使用中文回答。

于是即使用户用英文写 Prompt，Agent 仍然可以输出中文。

这说明：

**最终行为并不只取决于用户最后输入的那句话。**

---

## 4. Agent 的 Prompt 往往是一整套层次化配置

在实际的 Agent 系统中，System Prompt 之后还可能继续加载大量信息。

例如，一个 Agent 可能具有类似这样的结构：

```text
System Prompt
    ↓
Agent 配置
    ↓
AGENTS.md
    ↓
Skills
    ↓
其他说明文件
    ↓
用户消息
    ↓
工具调用
    ↓
工具调用结果
```

其中常见的内容包括：

### **AGENTS.md**

项目中可能存在专门给 Agent 阅读的说明文件，例如：

- 项目规则；
- 编码规范；
- 工作流程；
- 构建方式；
- 测试方式；
- 注意事项。

### **Skills**

Agent 还可能加载各种 **Skill（技能描述）** ，进一步告诉它：

- 遇到某类任务应该怎么做；
- 应该读取哪些文件；
- 应该使用哪些工具；
- 应该遵循怎样的处理流程。

而 Skill 自己甚至可能要求 Agent **继续读取其他文件** 。

因此，Prompt 的实际组成很容易不断扩张。

---

## 5. Tool Call 也是上下文的一部分

Agent 不只是接收静态的 Prompt。

当 Agent 使用工具时：

$$
\text{Tool Call} \rightarrow \text{Tool Result} \rightarrow \text{加入上下文}
$$

例如 Agent：

1. 调用搜索工具；
2. 得到搜索结果；
3. 将结果放入自己的上下文；
4. 再根据新的上下文继续推理。

因此， **工具调用以及工具返回结果本身也属于 Agent 上下文的一部分。**

随着任务不断推进，上下文会持续增加。

---

## 6. Agent 使用的是线性增长的上下文

可以把 Agent 的上下文想象成一条不断增长的记录：

```text
System Prompt
    ↓
初始配置
    ↓
文件内容
    ↓
第一次 Tool Call
    ↓
Tool Result
    ↓
第二次 Tool Call
    ↓
Tool Result
    ↓
User Message
    ↓
Agent Response
    ↓
……
```

所以，当用户最终说：

> “帮我做一个游戏。”

此时 Agent 所看到的并不是单独这一句话。

它实际上看到的是：

> **前面已经积累的大量上下文 + 当前 User Message。**

这也是现代 Agent 能够处理复杂任务的重要原因之一。

---

## 7. 为什么现代 Agent 的能力如此强

现代 Agent 一个非常重要的能力，是：

**它可以在非常长的上下文中同时看到大量背景信息。**

因此，我们可以提前把大量知识和规则放入上下文，让 Agent 在执行任务时直接使用。

例如：

```text
System Prompt
    ↓
定义角色和行为
    ↓
项目规则
    ↓
Skills
    ↓
项目文档
    ↓
代码
    ↓
工具结果
    ↓
用户任务
```

用户最后只需要给出相对简单的指令，Agent 就能够结合之前提供的大量信息完成复杂任务。

这与传统程序非常不同：

> **传统程序主要依赖显式代码控制行为；Agent 则可以通过自然语言上下文向模型注入大量行为规则和背景知识。**

---

## 8. “优化 Prompt”真正优化的是什么

因此，当我们说 **Prompt Engineering** 或者“优化提示词”时，不能只理解成：

> 把一句指令写得更加清楚。

更准确的理解是：

> **优化 Agent 所接收的整个上下文，使模型能够获得正确的信息、遵循正确的规则，并以预期方式完成任务。**

也就是说，需要关注的不只是：

**“我应该怎么告诉 AI 做这件事？”**

还包括：

**“AI 在做这件事之前，究竟已经看到了什么？”**

这意味着现代 Prompt Engineering 已经逐渐从单纯的 **指令编写** ，扩展到了 **Context Engineering（上下文工程）** 。

## Context Engineering：从 Prompt Engineering 到上下文工程

### 1. Prompt Engineering 的真正含义是 Context Engineering

当我们今天说 **Prompt Engineering（提示词工程）** 时，更准确的说法其实是 **Context Engineering（上下文工程）** 。

因为影响模型行为的并不只是用户最后输入的一条 Prompt，而是：

> **模型在生成每一个 Token 时能够看到的整个 Context。**

因此，工程上的核心问题逐渐从：

**“怎么写好一句 Prompt？”**

变成：

**“怎么设计、组织和维护模型能够看到的整个上下文？”**

---

### 2. 从 Next Token Prediction 理解 Agent

模型的基本机制仍然可以理解为 **Next Token Prediction（下一个 Token 预测）** 。

模型每一步都根据当前上下文预测下一个 Token：

$$
P(x_{t+1}\mid x_1,x_2,\ldots,x_t)
$$

而这个 Token 不一定只是普通文字，它可能对应：

- 输出一个字符；
- 输出一段代码；
- 继续解释；
- **调用工具** ；
- 继续推进任务。

因此，Agent 的执行过程可以看成不断进行：

$$
\text{Context} \rightarrow \text{Next Token} \rightarrow \text{新的 Context} \rightarrow \text{Next Token} \rightarrow \cdots
$$

也就是说， **Agent 是通过连续的 Token 生成不断推进任务执行的。**

---

### 3. 长上下文让模型开始真正具备持续遵循指令的能力

随着模型和后训练技术的发展，模型的 **Instruction Following（指令遵循）** 能力显著增强。

一个重要变化是：

> **即使上下文非常长，模型仍然可以在上下文后部继续遵循很早之前给出的指令。**

这使得现代 Agent 可以把大量规则、文档、工具结果和历史对话放在同一个 Context 中，并在很长的任务过程中持续使用这些信息。

因此， **长上下文 + 强指令遵循** 是现代 Agent 能够处理复杂长期任务的重要基础。

---

### 4. “喵”实验：观察上下文是否仍然有效

一个很直观的工程实践是：

在最开始的 Prompt 中加入一个简单规则：

> **每说一句话，都在结尾加“喵”。**

然后和 Agent 长时间工作。

如果过了很久之后，Agent 突然不再加“喵”，这就可以作为一个非常直观的信号：

**模型可能已经无法继续完整遵循早期上下文中的指令。**

背后的原因可能包括：

- **Context Truncation（上下文截断）** ；
- **Context Compression（上下文压缩）** ；
- 上下文管理机制发生变化；
- 模型对早期信息的有效利用能力下降。

因此，“喵”并不是重点，重点在于它可以作为一种简单的 **Context Health Check（上下文状态检查）** 。

可以把它理解为一个非常粗糙但实用的指标：

$$
\text{Old Instruction Still Followed} \Rightarrow \text{Context 可能仍然完整有效}
$$

反过来：

$$
\text{Old Instruction Lost} \Rightarrow \text{Context 可能发生截断、压缩或有效性下降}
$$

---

### 5. 上下文工程来自真实工程实践

这些问题并不是单纯的理论讨论，而是在实际使用 Agent 的过程中不断出现的：

- Prompt 越来越长；
- 工具调用越来越多；
- 历史信息不断累积；
- Context 可能被截断或压缩；
- 模型可能逐渐遗忘较早的要求；
- Agent 需要重新整理上下文。

所以，工程师逐渐发展出各种 **Context Engineering** 方法。

核心目标就是：

> **让 Agent 在长时间工作过程中，始终能够获得完成任务所需要的关键信息。**

---

### 6. AI 最大的价值之一：把“立即尝试”变得非常便宜

课程中强调的另一个重要观点是：

**遇到任何有一点麻烦的事情，都应该立即尝试使用 AI。**

原因不只是 AI 能回答问题，而是 AI 大幅降低了 **尝试和提问的成本** 。

#### 传统学习中的问题

向身边的人请教时，可能存在很多额外成本：

- 对方可能正在忙；
- 需要组织问题；
- 担心自己的问题太基础；
- 担心暴露自己“不懂”；
- 对方可能不愿意反复解释。

因此，人有时候会因为“问问题的成本太高”而选择自己硬想。

#### AI 带来的变化

AI 可以作为一个非常耐心的老师：

- 可以反复提问；
- 可以不断追问细节；
- 可以让它换一种说法；
- 可以要求进一步解释；
- 可以从非常基础的问题开始。

所以：

> **AI 降低的不只是获得答案的成本，更降低了“开始学习和尝试”的成本。**

---

### 7. “遇到麻烦就马上问 AI”是一种新的工作习惯

例如，刚刚了解到一个新概念：

> Agent 的 Context 不只是 User Prompt，还包括 System Prompt、文件、工具调用结果等内容。

传统做法可能是先自己猜：

> “这些东西到底是怎么组织起来的？”

而在 Agent 工作流中，可以直接打开一个 Agent，然后问：

> **“老师说 Agent 的上下文不只是几个提示词，你能检查一下自己的上下文里都有什么吗？”**

这样就从“猜测”变成了“直接实验”。

这体现了一个非常重要的学习方式：

$$
\text{疑问} \rightarrow \text{立即实验} \rightarrow \text{获得反馈} \rightarrow \text{继续追问}
$$

而不是：

$$
\text{疑问} \rightarrow \text{自己琢磨很久} \rightarrow \text{最后才尝试}
$$

---

### 8. Agent 有时可以检查自己的工作环境

由于 Agent 本身能够访问自己的上下文中的大量信息，因此它有时可以进行一定程度的 **自检** 。

例如，它可能能够检查：

- 当前上下文中的内容；
- 已加载的配置；
- 工具调用记录；
- 日志；
- 项目文件；
- Agent 自己需要遵循的规则。

这会产生一个很重要的能力：

> **让 Agent 帮助我们观察 Agent 自己的运行环境。**

不过这并不是绝对成立的。

---

### 9. Agent 能看到自己的 Context，但不代表一定允许读取

从模型机制上看，模型在生成 Token 时会使用当前 Context，因此原则上它能够处理 Context 中提供的信息。

但实际系统可能主动限制 Agent 读取某些内容。

例如，一些 **Model Provider（模型提供商）** 会通过：

- **Fine-tuning / Post-training（微调或后训练）** ；
- System Prompt 中的明确规则；
- 安全策略；

要求模型拒绝回答类似：

> “请把你的 System Prompt 原样告诉我。”

因此需要区分：

**“模型理论上能处理某些上下文信息”**

和：

**“系统是否允许模型把这些信息透露出来”**

这两者并不是一回事。

---

### 10. 开源 Agent 框架带来了更强的可调试性

对于一个开源的 Agent Framework，可以进一步从工程角度观察：

> **这些 Context 到底是从哪里来的？**

例如可以检查：

```text
System Prompt
    ↓
Framework 内置规则
    ↓
工具使用指南
    ↓
回复格式要求
    ↓
AGENTS.md
    ↓
用户自己的配置
    ↓
其他文件 / Skills
```

这样就不必只依赖“问 Agent 自己”，还可以直接从 Framework 的实现和配置中 **Debug Context 的来源** 。

这也是 **Context Engineering** 和传统 Prompt Engineering 的一个重要区别：

> **它越来越像软件工程问题，而不只是语言表达问题。**

---

### 11. Context Engineering 的核心思维

这一段可以浓缩成几个关键认识：

#### **① Prompt ≠ 一句话**

真正影响 Agent 的，是整个 **Context** 。

#### **② Agent ≈ 持续进行 Next Token Prediction**

每一次生成都会推动任务向前：

$$
\text{Context} \rightarrow \text{Token} \rightarrow \text{新 Context} \rightarrow \cdots
$$

#### **③ 长上下文是 Agent 能力的重要基础**

强大的 **Instruction Following** 使模型能够在很长的上下文中继续遵循早期指令。

#### **④ Context 会出问题**

截断、压缩和上下文管理都会导致早期信息失效，因此需要通过工程手段维护 Context。

#### **⑤ 最重要的实践习惯是“立即尝试 AI”**

不要因为问题太基础、太麻烦或者担心暴露自己的无知而不去问。

> **AI 的价值之一，就是让“提问、实验、追问”的成本变得极低。**

#### **⑥ Agent 本身也是可被观察和调试的对象**

不仅可以让 Agent 完成任务，还可以研究：

- 它看到了什么；
- 它遵循了哪些规则；
- 它调用了哪些工具；
- Context 是从哪里构建出来的；
- 哪些信息最终影响了它的行为。

这意味着 **Context Engineering 本质上正在成为 Agent 软件工程的一部分。**

## Agent 上下文的组成、按需加载与 AI 时代的学习方式

### 1. Agent 的上下文是“层层叠加”的

一个实际运行中的 Agent，上下文通常不是单一来源，而是由多层信息逐步组成。

以课程演示环境为例，可能包括：

```text
全局上下文
    ↓
项目级指令
    ↓
目录级 AGENTS.md
    ↓
Skills 索引
    ↓
具体 Skill
    ↓
Tools 定义
    ↓
历史信息
    ↓
环境信息
    ↓
User Message
```

这些信息共同决定 Agent 在当前任务中的行为。

#### 全局上下文

可以在全局层面规定一些通用行为，例如：

- **使用中文回答**
- 回复末尾必须包含 **Recap（回顾）**

这些规则不需要用户每次重复说明，而是作为更高层级的上下文长期存在。

#### 项目级 / 目录级指令

项目中还可以通过 `AGENTS.md` 等文件加入更具体的规则。

而且这种配置还可以继续向目录内部延伸：

```text
项目/
├── AGENTS.md
└── 某个子目录/
    └── AGENTS.md
```

因此，Agent 所遵循的规则可能形成一个 **层级结构** ：

$$
\text{Global Rules} \rightarrow \text{Project Rules} \rightarrow \text{Directory Rules} \rightarrow \text{Task-specific Rules}
$$

越靠近当前任务的规则，通常越具体。

---

### 2. Skills：Agent 的能力可以按需加载

Agent 通常还会拥有一个 **Skills（技能）** 索引。

Skill 可以理解为：

> **告诉 Agent “遇到某类任务时应该怎样完成它”的可复用能力模块。**

例如课程演示中存在一个 `make_slide` Skill，它用于处理幻灯片渲染，让用户能够通过 `F5` 播放或查看生成的幻灯片效果。

但一个关键点是：

**Agent 并不会在每一轮开始时把所有 Skill 的完整内容全部塞进 Context。**

---

### 3. Skill 采用“索引 + 按需加载”的机制

在通常情况下，Agent 只需要先看到 Skill 的一些元信息，例如：

- **名称**
- **Description（简要描述）**
- 其他 **Metadata（元数据）**

例如可以抽象成：

```text
Skills Index

make_slide
  description: 渲染和播放幻灯片
```

Agent 先通过这些信息判断：

> 当前任务是否与 `make_slide` 有关？

如果没有关系，就没有必要读取完整 Skill。

只有任务匹配时，才进一步加载完整的 `SKILL.md` 。

可以表示为：

$$
\text{Skill Index} \rightarrow \text{Task Matching} \rightarrow \text{Load Full Skill}
$$

这就是 **On-demand Loading（按需加载）** 。

---

### 4. 为什么 Skill 不应该全部常驻 Context

一个 Skill 可能写得非常长。

如果把所有 Skill 的完整内容全部提前加载，会导致：

- Context 迅速膨胀；
- 占用更多 Token；
- 增加模型处理负担；
- 无关信息干扰当前任务。

因此，更合理的方式是：

> **平时只保留“这个 Skill 是干什么的”的索引信息，真正需要时才读取完整内容。**

甚至在某一轮任务结束后，已经加载的 Skill 内容还可能被从当前 Context 中移除。

所以它更像：

```text
Skill Index
    ↓
发现需要 make_slide
    ↓
加载 make_slide.md
    ↓
执行任务
    ↓
本轮结束后不再长期保留完整内容
```

这说明 **Context Engineering** 不只是“往上下文里添加东西”，同样包括：

**什么时候加载、加载多少、什么时候移除。**

---

### 5. Tool Definition 也会进入 Context

除了 Prompt、文件和 Skills， **Tool Definition（工具定义）** 同样可能以文本形式出现在模型的 Context 中。

模型需要知道：

- 工具有哪些；
- 工具叫什么；
- 参数是什么；
- 应该怎样调用。

因此从模型视角看，工具并不是一个完全隐藏在外部的黑盒。

它可以近似理解为：

$$
\text{Tool Definition} \rightarrow \text{进入 Context} \rightarrow \text{模型根据定义生成 Tool Call}
$$

所以：

> **工具系统本身也是 Context Engineering 的组成部分。**

---

### 6. 历史信息与环境信息也是 Context 的组成部分

除此之外，Agent 上下文中还可能存在：

- **对话历史**
- 之前的工具调用结果
- 绘图或其他操作历史
- 当前工作环境信息
- **Environment Variables（环境变量）**

甚至每一次 Agent 执行时，系统都可能注入一些当前环境信息，例如：

- 当前使用的模型；
- 当前时间；
- 当前运行环境；
- 其他与执行有关的信息。

因此，一个完整的 Context 可以进一步抽象成：

$$
C = C_{\text{system}} + C_{\text{project}} + C_{\text{skills}} + C_{\text{tools}} + C_{\text{history}} + C_{\text{environment}} + C_{\text{user}}
$$

这也是为什么真正的 Prompt Engineering 最终会演化成 **Context Engineering** ：

> **工程师要管理的是所有进入模型上下文的信息，而不只是用户输入框里的那一句话。**

## AI 时代的学习方式

### 7. 第一种方式：把 AI 当老师，不断追问

学习一个陌生概念时，可以首先把 AI 当成老师。

基本过程是：

$$
\text{遇到疑问} \rightarrow \text{询问 AI} \rightarrow \text{不懂就继续追问} \rightarrow \text{直到理解}
$$

AI 的一个巨大优势在于：

**提问成本非常低。**

它不会因为问题过于基础而嫌弃你，也不会因为你反复追问同一个概念而不耐烦。

这使得学习过程可以变成一种非常低成本的 **交互式教学** 。

---

### 8. 第二种方式：把 AI 当学生，反过来讲给它听

理解一个概念之后，可以采用 **Feynman Technique（费曼学习法）** 。

核心思想是：

> **如果你真的理解一个知识，就应该能够把它解释给一个什么都不知道的人。**

传统情况下，这种方法存在一个实际问题：

你需要找一个真实的人充当“学生”。

例如找室友听你解释，但对方可能：

- 对这个主题没有兴趣；
- 已经知道相关知识；
- 不想花时间听；
- 不愿意不断配合你练习。

AI 则非常适合作为这个“学生”。

---

### 9. AI + 费曼学习法：正向学习 + 反向验证

完整流程可以设计成两遍：

#### 第一遍：AI 当老师

```text
    ↓

    ↓
你继续追问
    ↓
直到自己认为理解了
```

#### 第二遍：AI 当学生

然后角色反过来：

```text
AI 假装什么都不知道
        ↑
      你来讲
        ↓
AI 检查你的解释
        ↓
指出逻辑错误、遗漏和不清楚的地方
```

也就是：

$$
\text{AI 教你} \rightarrow \text{你教 AI} \rightarrow \text{AI 纠正你}
$$

这种“正着学一遍、反着讲一遍”的方式，可以显著暴露理解中的漏洞。

尤其是以下问题很容易被发现：

- **概念是否真的理解**
- **推理链条是否完整**
- **是否存在逻辑跳跃**
- **是否遗漏关键条件**
- **是否只是记住了术语，却不会解释**

---

### 10. AI 降低了费曼学习法的实践成本

传统费曼学习法最大的成本之一，是需要一个愿意配合的听众。

AI 则几乎可以随时充当这个听众。

因此：

> **AI 不只是知识来源，也可以成为学习过程中的陪练、提问者和审稿人。**

一个完整的 AI 学习循环可以变成：

$$
\boxed{ \text{AI 教你} \rightarrow \text{你追问} \rightarrow \text{你理解} \rightarrow \text{你向 AI 讲解} \rightarrow \text{AI 找漏洞} \rightarrow \text{重新理解} }
$$

这实际上把 **Feynman Technique** 和 **AI Tutor（AI 教师）** 结合起来了。

---

### 11. AI Native 学习者的优势：反馈循环变得极短

传统学习往往是：

$$
\text{遇到问题} \rightarrow \text{寻找资料} \rightarrow \text{理解} \rightarrow \text{验证}
$$

而 AI 可以把这个过程压缩成：

$$

因此，真正重要的变化并不仅仅是：

> “AI 知识很多。”

更重要的是：

> **AI 把学习中的反馈循环变得非常短。**

这使学习者可以更加频繁地：

**提问 → 实验 → 验证 → 修正 → 再提问。**

这正是 **AI Native（AI 原生）学习方式** 的重要特征之一。

## Agent 安全机制、风险判断与 AI 辅助理解复杂软件

### 1. Agent 的自动执行与安全确认存在权衡

Agent 在执行操作时，需要在 **自动化程度** 和 **安全性** 之间做平衡。

例如某些 Agent 在默认配置下可能处于类似 **YOLO Mode** 的模式，即：

> **几乎所有操作都直接执行，而不是每次都向用户确认。**

这样做的优点是自动化程度很高，但风险也非常明显。

如果用户给出的 Prompt 不够严谨，Agent 可能执行危险操作，例如：

- 删除文件；
- 修改大量代码；
- 执行危险命令；
- 破坏当前工作环境。

极端情况下，一个错误的 Prompt 甚至可能导致整个工作环境被破坏。

因此：

$$
\text{更高自动化} \leftrightarrow \text{更高潜在风险}
$$

这是 Agent 工程中一个非常基本的设计权衡。

---

### 2. Sandbox：通过隔离环境降低风险

一种常见的解决方法是让 Agent 在 **Sandbox（沙箱）** 中运行。

沙箱的核心思想是：

> **让 Agent 的操作权限受到限制，即使它执行了错误或危险的操作，也尽量不要影响真实环境。**

例如：

```text
真实环境
    ↑
    │ 尽量隔离
    ↓
Sandbox
    ↓
Agent 在受限环境中执行
```

这样可以提高安全性，但会产生新的问题：

**Agent 可能需要访问沙箱之外的资源。**

---

### 3. 沙箱会导致 Agent 的执行流程出现“先失败、再升级权限”

在实际使用中，Agent 可能出现这样的行为：

```text
尝试执行操作
      ↓
操作失败
      ↓
发现当前处于 Sandbox
      ↓
判断“这个操作需要更高权限”
      ↓
尝试在 Sandbox 外执行
      ↓
发现操作存在风险
      ↓
请求用户确认
```

因此，Agent 有时并不是一开始就知道：

> “这个操作一定需要用户授权。”

而可能是：

> **先尝试 → 根据失败结果理解环境 → 调整方案 → 必要时请求权限。**

这也是 Agent 工作流中一个很有代表性的细节。

---

### 4. 真正影响 Agent 体验的，往往是这些“小细节”

从用户角度看，最理想的 Agent 工作方式通常是：

```text
准备多个任务
    ↓
全部启动 Agent
    ↓
自己去吃饭 / 做其他事情
    ↓
回来时任务已经完成
```

但如果 Agent：

```text
执行一分钟
    ↓
遇到一个需要确认的操作
    ↓
停下来等待用户
```

那么自动化的价值就大幅降低了。

因此，一个 Agent 即使核心能力很强， **权限管理、确认策略、任务调度等细节同样会直接影响实际生产力。**

可以粗略理解为：

$$
\text{Agent 实际生产力} \neq \text{模型能力}
$$

而更接近：

$$
\text{Agent 实际生产力} = \text{模型能力} + \text{工具能力} + \text{自动化程度} + \text{权限策略} + \text{工作流设计}
$$

---

### 5. 风险判断（Risk Assessment）本身就是一个复杂问题

Agent 不一定会对所有命令都要求用户确认。

有些操作会被判断为低风险，从而直接执行。

例如某些查看目录的命令，Agent 可能认为：

> “这个操作只是查看信息，直接执行应该没问题。”

于是无需询问用户。

而对于删除、修改系统状态等更危险的操作，则可能要求确认。

因此背后通常存在一个 **Risk Assessment（风险评估）** 机制：

$$
\text{Command} \rightarrow \text{Risk Assessment} \rightarrow \begin{cases} \text{Allow} \\ \text{Ask User} \\ \text{Deny} \end{cases}
$$

---

### 6. 风险判断并没有想象中那么简单

一个非常值得注意的问题是：

> **如何判断一个命令究竟是否安全？**

看起来可以直接分析命令字符串，但实际上存在一个重要陷阱：

**命令的真正语义取决于具体运行环境。**

例如某个命令在标准 Linux 环境下可能是一个普通的安全操作，但用户完全可以修改命令解释方式。

比如：

```text
ls
```

理论上大家知道它通常表示查看目录内容。

但如果用户在当前环境中把它重新映射成了其他程序，那么：

```text
ls
```

实际执行的就不一定还是原来的语义。

因此：

> **“命令字符串看起来安全”并不等于“实际执行一定安全”。**

---

### 7. Risk Assessment 可以有多种实现方式

面对一个命令时，到底应该如何判断风险，可能存在多种方案：

#### 方案一：规则分析

通过人工编写规则判断：

```text
ls      → 低风险
rm      → 高风险
sudo    → 高风险
```

优点是简单、可预测。

但缺点是：

**很难覆盖复杂环境下所有命令语义。**

#### 方案二：代码分析

直接分析命令执行逻辑和当前环境，判断真正会调用什么。

这样更加准确，但实现成本更高。

#### 方案三：让大模型参与风险评级

把命令及其上下文交给模型，让模型判断：

> “这个操作危险吗？”

这更灵活，但模型自身也可能判断错误。

因此，实际系统可能采用多种方法组合，而具体实现需要直接查看代码才能确定。

## AI 辅助阅读和理解复杂软件

### 8. 遇到不理解的系统，不需要先把整个系统吃透

传统的软件工程学习经常会遇到一个非常高的门槛。

例如学习 **Linux Kernel** ：

1. 下载源码；
2. 搞清楚依赖；
3. 搞清楚编译方式；
4. 配置环境；
5. 成功构建；
6. 之后才能真正开始研究代码。

即使具备一定 Linux 使用经验，这个过程也可能已经足以让人放弃。

因此传统软件工程学习常常存在：

> **理解系统之前，先要付出很高的环境和认知成本。**

---

### 9. AI 正在降低复杂软件系统的“入门摩擦”

现在面对一个复杂软件系统，可以采用完全不同的方式。

例如：

> 下载一个复杂 Agent 的源码。

以前可能需要自己：

- 阅读项目结构；
- 搜索文档；
- 理解构建系统；
- 找入口；
- 猜测模块之间的关系。

现在则可以直接：

> **让 Agent 帮自己阅读这个软件。**

比如直接问：

> “这个系统在什么时候做风险判断？”

然后让 Agent：

```text
搜索代码
    ↓
定位相关模块
    ↓
读取实现
    ↓
分析调用关系
    ↓
解释设计
```

这使“研究一个复杂软件系统”的成本显著降低。

---

### 10. Agent 可以直接成为代码阅读助手

当用户问一个具体的软件工程问题时，Agent 可以主动使用各种工具。

例如：

```text
User Question
      ↓
Agent
      ├── 搜索代码
      ├── 阅读文件
      ├── 查找符号
      ├── 分析调用关系
      ├── 查看配置
      └── 查询日志
      ↓
综合分析
      ↓
回答问题
```

因此， **AI 不只是回答“知识问题”，还可以直接参与软件逆向理解和代码考察。**

---

### 11. LSP 让 Agent 获得类似 IDE 的代码导航能力

如果 Agent 能够使用 **LSP（Language Server Protocol，语言服务器协议）** 等工具，那么它甚至可以获得类似 IDE 的代码导航能力。

例如开发者平时在 IDE 中会：

- 跳转到定义；
- 查找引用；
- 查看符号；
- 查看类型；
- 查看调用关系。

Agent 也可以通过类似工具完成这些操作。

因此：

> **AI Agent + LSP，本质上是在给模型提供“机器可操作的 IDE 能力”。**

最终形成：

$$
\text{自然语言问题} \rightarrow \text{代码搜索} \rightarrow \text{符号导航} \rightarrow \text{源码阅读} \rightarrow \text{理解系统}
$$

这也是现代 AI 辅助软件工程与过去最大的区别之一：

> **面对一个复杂系统时，不再需要先凭自己承受完整的理解成本，而可以让 AI 直接进入系统内部，与代码、工具和运行环境一起工作。**

## IDE 配置、Agent 风险评估与软件工程上下文

### 1. 正确配置 IDE 是软件工程实践的一部分

在学习操作系统、计算机系统等课程时，经常会出现一种情况：

> **代码虽然能够编译、程序也能够运行，但 IDE 中始终存在大量红线。**

这种情况并不一定会阻止程序完成，因为课程提供的受控构建环境可能已经配置好了真正的编译参数。

但从软件工程实践来看：

**“能编译”不等于“开发环境配置正确”。**

例如 VS Code 需要正确配置：

- **Include Path**
- 编译器路径
- 编译参数
- 相关项目配置

如果这些配置正确，IDE 才能真正理解代码。

---

### 2. 正确的代码配置会解锁 IDE 的高级能力

一旦 IDE 获得正确的项目和编译配置，就不仅仅是“红线消失”。

它可以进一步提供大量基于代码语义的功能，例如：

- **Go to Definition** ：跳转到定义；
- **Find References** ：查找引用；
- **Rename Symbol** ：重命名符号；
- 自动补全；
- 类型分析；
- 跨文件重构。

例如使用 **Rename Symbol** ，可以一次性修改一个变量、类型或函数在整个项目中的相关引用，而不需要手动搜索替换。

这些能力在大模型出现之前就已经存在，因此：

> **AI 并没有创造 IDE 的代码理解能力，而是在已有的程序分析基础上进一步提高了自动化程度。**

## Agent 的风险评估机制

### 3. Agent 的安全控制通常不是“每条命令都问用户”

Agent 在执行命令时，可能存在多层风险控制。

一个简化后的流程可以理解为：

$$
\text{Command} \rightarrow \text{Static Classification} \rightarrow \text{Risk Assessment} \rightarrow \text{Permission Decision}
$$

也就是说，Agent 往往不是简单地：

> “看到命令 → 直接问用户。”

而是会先进行一定程度的分类和判断。

---

### 4. 第一层：静态规则进行快速分流

其中一种机制是 **静态分流（Static Routing）** 。

例如：

- **Sandbox 内的低风险命令** → 直接执行；
- 命中 **Allowlist / Whitelist（允许列表）** → 直接放行；
- 其他命令 → 进入进一步的风险评估。

例如某些简单的目录查看命令可能被认为是低风险操作，因此不需要审批。

可以抽象为：

$$
\text{命令} \rightarrow \begin{cases} \text{Allowlist 命中} &\Rightarrow \text{直接执行}\\ \text{否则} &\Rightarrow \text{进一步风险分析} \end{cases}
$$

这样可以避免每个简单操作都打断用户。

---

### 5. Allowlist 的意义：低风险操作直接通过

系统可以维护一套预先定义的安全命令集合。

例如：

```text
命令
 ↓
Parser
 ↓
检查是否属于 Allowlist
 ├── 是 → 直接执行
 └── 否 → 风险评估
```

这样做的好处是：

**对于确定安全的操作，不需要调用额外的判断机制，更不需要频繁请求用户确认。**

这同时改善了：

- 执行速度；
- 用户体验；
- 自动化程度。

---

### 6. 第二层：让大模型进行风险评级

如果一个命令没有命中静态允许规则，就可能进入更复杂的风险判断流程。

这里又可以使用 **Prompt Engineering** 。

系统可以在原有 Context 中动态注入一小段额外 Prompt，要求模型判断：

> **这个操作的安全风险是什么？**

所以整个机制可能类似：

$$
\text{Command} \rightarrow \text{静态规则} \rightarrow \text{Prompt 注入} \rightarrow \text{LLM Risk Assessment} \rightarrow \text{执行 / 审批 / 拒绝}
$$

这里非常值得注意的一点是：

**“给模型增加一条规则”本身就是 Prompt Engineering。**

换句话说，Prompt Engineering 不只是用户写 Prompt，也包括 Agent 系统内部动态构造的 Prompt。

---

## 通过修改 Prompt 验证系统行为

### 7. 不要盲目相信模型给出的风险判断

即使系统使用大模型做风险评估，也不能默认：

> “模型说安全，所以一定安全。”

模型的判断本身就是一种 **Evidence（证据）** ，而不是绝对真理。

因此应该区分：

- **可信度较高的确定性规则**
- **模型产生的判断**
- **尚未验证的推测**

其中模型输出尤其应该被看作 **Untrusted Evidence（不完全可信的证据）** 。

---

### 8. 一个很有价值的实验：修改风险评估 Prompt

如果不确定某个风险评估机制是否真的按照预期工作，可以直接做实验。

例如修改负责风险判断的 Prompt：

```text
原 Prompt
    ↓
改变其中的判断条件
    ↓
再次执行相同类型的命令
    ↓
观察行为是否变化
```

可以设计反事实实验：

> 原本应该拒绝的操作，修改 Prompt 后尝试让它通过。

或者：

> 原本允许的操作，修改 Prompt 后尝试让它拒绝。

如果修改 Prompt 后行为确实发生对应变化，那么就获得了一项有价值的 **实验性证据** ：

$$
\text{Prompt 改变} \rightarrow \text{Behavior 改变} \Rightarrow \text{Prompt 对行为具有实际影响}
$$

这比单纯阅读一段说明或者相信模型自己的解释更加可靠。

---

### 9. 代码分析 + 实验验证比单纯相信解释更可靠

对于 Agent 系统，理解一个机制时，可以采用两条路线：

#### 静态路线

直接阅读源代码：

```text
源码
 ↓
Parser
 ↓
Risk Classification
 ↓
Prompt Construction
 ↓
Model Call
 ↓
Permission Decision
```

#### 动态路线

实际修改配置或 Prompt，然后观察行为：

```text
修改条件
 ↓
运行 Agent
 ↓
记录结果
 ↓
对比行为变化
```

两者结合起来：

$$
\boxed{ \text{Code Inspection} + \text{Behavioral Experiment} }
$$

通常比单纯询问 Agent：

> “你是怎么实现的？”

更加可靠。

---

## 软件工程任务中的 Context

### 10. 从 Intent 到 Implementation，中间存在大量层次

软件工程本身就是一个不断把抽象目标细化成具体实现的过程。

例如一开始可能只有一个 **Intent（意图）** ：

> “我要做一个面向大众的大型应用。”

然后逐步细化为：

$$
\text{Intent} \rightarrow \text{Expectations} \rightarrow \text{Architecture} \rightarrow \text{Language / Technology} \rightarrow \text{Implementation}
$$

也就是说：

#### **Intent**

我真正想做什么？

#### **Expected Behavior**

系统应该具有什么能力、达到什么效果？

#### **Architecture**

系统整体应该怎样组织？

#### **Technology Choice**

选择什么语言、框架和技术？

#### **Implementation**

最终具体写哪些代码？

---

### 11. Agent 接手软件工程任务时，需要看到这条链条中的部分信息

当我们让模型完成软件工程任务时，不可能只给它一句：

> “把这个功能做出来。”

真正能够让 Agent 正确工作的，是把任务过程中需要的背景信息逐步放入 Context。

例如：

```text
项目目标
   ↓
功能要求
   ↓
架构约束
   ↓
技术选择
   ↓
编码规范
   ↓
已有代码
   ↓
当前问题
   ↓
实现任务
```

因此：

> **Agent 的 Context 实际上承载了软件工程过程中原本由人类开发者记在脑中、文档里和代码里的大量信息。**

---

### 12. Context Engineering 本质上也是软件工程过程的“信息组织”

前面的讨论可以进一步统一起来。

无论是：

- 全局 System Prompt；
- `AGENTS.md` ；
- Skills；
- Tool Definition；
- Tool Result；
- 环境变量；
- 风险评估 Prompt；
- 项目代码；
- 用户任务；

它们最终都在回答同一个问题：

> **在 Agent 执行当前任务时，究竟应该让它知道什么？**

所以 **Context Engineering** 可以理解为：

$$
\boxed{ \text{把完成任务所需的信息} \rightarrow \text{以合适的形式} \rightarrow \text{在合适的时间} \rightarrow \text{提供给模型} }
$$

这已经不只是“写一句好 Prompt”，而是在设计一个完整的 **AI 软件工程工作环境** 。

## 上下文设计的核心：缩小 Intent 与可验证 Specification 之间的 Gap

### 1. 理解复杂 Agent 时，要区分“设计原则、Spec 与实现”

阅读一个成熟软件系统时，通常不能只看最终代码。

以 Agent 的安全策略为例，一个完整的设计往往可以拆成三层：

```text
Design / Rationale
    ↓
Spec
    ↓
Implementation
```

#### **Design / Rationale：为什么这样设计**

首先解释：

- 为什么需要这套安全策略；
- 希望解决什么问题；
- 整体设计目标是什么；
- 为什么采用这种方案。

#### **Spec：具体应该怎么工作**

然后通过 **Specification（规格说明）** 把设计具体化，例如：

- 哪些命令允许直接执行；
- 哪些命令需要审批；
- 哪些情况应该拒绝；
- 风险判断应该发生在哪一层。

#### **Implementation：代码到底怎么实现**

最后看真实代码：

- 规则在哪里实现；
- 使用了什么 Parser；
- 如何调用模型；
- 如何做权限判断；
- 最终怎样执行命令。

因此，理解一个系统时，可以让这三层相互验证：

$$
\text{Design} \leftrightarrow \text{Spec} \leftrightarrow \text{Implementation}
$$

这比单独阅读代码更容易判断：

> **“系统为什么这么做，以及它是否真的按照设计实现了。”**

---

## 设计 Agent Context 时最重要的原则

### 2. 核心问题：缩小 Intent 到实现之间的 Gap

当我们让模型完成软件工程任务时，最重要的问题之一是：

> **模型到底知道我们真正想要什么？**

可以把这个问题表示成：

$$
\text{Intent} \rightarrow \text{Specification} \rightarrow \text{Implementation}
$$

其中最容易出问题的是 **Intent 与最终实现之间的 Gap** 。

如果只告诉模型一个非常模糊的 Intent，那么中间存在大量没有明确说明的约束。

---

### 3. 模糊 Intent 很容易导致“漂移”

例如告诉模型：

> “给我生成一个 CSGO。”

模型当然可能真的生成一个“类似 CSGO 的游戏”。

但问题在于：

**什么叫 CSGO？**

用户脑子里的 CSGO 可能包含：

- 特定玩法；
- 特定地图；
- 特定美术资源；
- 特定武器；
- 特定物理效果；
- 特定操作方式；
- 特定 UI；
- 特定视觉风格。

但这些东西如果没有写进上下文，模型并不知道。

于是会出现：

$$
\text{你的 Intent} \neq \text{模型理解的 Intent}
$$

最终得到的结果可能“看起来很厉害”，却不是你真正想要的东西。

这种现象可以称为 **Drift（目标漂移）** ：

> **模型仍然在努力完成任务，但它逐渐偏离了用户真正想要的目标。**

---

### 4. 模型能力越强，也不能自动补全你脑中的隐含约束

即使假设模型能力无限大，也存在一个根本问题：

> **模型无法凭空知道你没有表达出来的要求。**

例如：

> “给我做一个 CSGO。”

模型可能生成：

- FPS；
- 枪械；
- 敌人；
- 地图；
- 碰撞；
- UI；
- 后视镜或其他视觉效果。

这些都可能非常优秀。

但你真正想要的可能是：

> **“使用真实 CSGO 地图和美术资产，实现一个尽可能接近原游戏的版本。”**

如果这个约束没有告诉模型，它没有理由自动推断出来。

因此：

$$
\text{模型能力} \neq \text{用户脑中的隐含需求}
$$

---

## 让模型从 Intent 走向可验证的 Specification

### 5. 解决 Drift 的方法：尽可能把系统设计和 Spec 提供给模型

如果只给模型一个模糊目标：

```text
Intent
“做一个 CSGO”
```

模型需要自己补全大量细节：

```text
Intent
   ↓
模型自行猜测
   ↓
Architecture
   ↓
Implementation
```

猜测越多，漂移风险越大。

更好的方式是：

```text
Intent
   ↓
明确的 System Design
   ↓
完整 Specification
   ↓
Implementation
```

这样模型拥有更加明确的约束。

---

### 6. 一个好的 Spec 应该让结果“可验证”

例如明确规定：

> **必须使用 C++ 实现。**

那么模型最后如果交付 Java 代码，你一眼就能判断：

$$
\text{Spec: C++} \neq \text{Result: Java}
$$

因此这个结果显然是不合格的。

这说明一个非常重要的原则：

> **好的上下文应该尽可能包含能够直接判断“对不对”的约束。**

---

## Machine-Verifiable：让 Agent 自己不断验证

### 7. 能机器验证的任务，特别适合交给 Agent 反复执行

最理想的情况是：

> **任务是否完成，可以由机器自动判断。**

例如存在一个测试脚本：

```text
Agent 修改代码
      ↓
运行测试
      ↓
PASS / FAIL
      ↓
Agent 根据结果继续修改
      ↓
再次测试
      ↓
……
```

于是：

$$
\text{Implementation} \rightarrow \text{Verification} \rightarrow \text{Correction} \rightarrow \text{Verification} \rightarrow \cdots
$$

只要还有失败，Agent 就可以继续迭代。

---

### 8. 可验证性越强，Agent 越可以“不知疲倦”地迭代

如果任务有一个非常明确的验收标准，即使问题非常困难，Agent 仍然可以不断尝试。

例如：

$$
\text{Goal} = \text{Test Suite 全部通过}
$$

那么 Agent 不需要自己猜：

> “我觉得应该差不多了。”

而可以直接以测试结果为反馈：

- 失败 → 修复；
- 再失败 → 继续分析；
- 继续失败 → 更换方案；
- 需要工具 → 安装工具；
- 缺少资料 → 搜索资料；
- 再次验证。

这使 Agent 形成一个持续的 **Feedback Loop（反馈循环）** ：

$$
\boxed{ \text{Implement} \rightarrow \text{Test} \rightarrow \text{Observe} \rightarrow \text{Fix} \rightarrow \text{Test} \rightarrow \cdots }
$$

---

### 9. 即使任务非常困难，明确的目标也可以驱动长时间搜索

课程中提到了一个极端例子：

在某些 **CTF（Capture The Flag）** 场景中，可以给 Agent 一个非常困难、甚至看起来“不可能完成”的任务。

如果目标定义得足够明确，而且存在客观的成功判定，那么 Agent 可以进行大量轮次的尝试：

```text
明确目标
   ↓
尝试
   ↓
失败
   ↓
分析失败原因
   ↓
搜索资料 / 阅读代码 / 使用工具
   ↓
再次尝试
   ↓
……
```

这里最重要的并不是某一个具体漏洞，而是：

> **只要成功条件足够明确，Agent 就能够围绕同一个目标持续优化，而不需要每轮都重新猜测“到底什么算完成”。**

---

## 为什么“一句话生成一个游戏”仍然会失败

### 10. 模型生成的结果再优秀，也可能不是你想要的结果

现在的大模型已经可以根据非常简单的一句话生成复杂程序。

例如直接要求：

> “生成一个 CSGO。”

模型可能做出非常惊艳的结果：

- 物理效果完整；
- 碰撞正常；
- 游戏逻辑完整；
- 甚至有类似后视镜等细节；
- 整体视觉效果非常逼真。

但是：

**它依然可能不是你想要的 CSGO。**

因为“技术质量高”和“目标匹配度高”是两个不同的问题。

可以表示成：

$$
\text{Quality} \neq \text{Specification Compliance}
$$

一个实现可以：

> **做得非常好，但做错了东西。**

---

### 11. 模型无法自动补全你脑海中的隐含需求

例如你真正想做的是：

> 在真实地图中驾驶车辆。

如果只说：

> “做一个赛车游戏。”

模型可能创造一个全新的虚构地图。

但如果明确告诉它：

> “使用真实地图和现有美术资产。”

它就可以进一步寻找对应资源。

甚至如果要求是在：

> **南京大学仙林校区中驾驶。**

那么这个目标已经足够具体，模型就可以进一步考虑获取真实地理数据，例如使用 **OpenStreetMap** 等开放地图数据源。

因此：

$$
\text{约束越明确} \Rightarrow \text{模型需要自行猜测的部分越少} \Rightarrow \text{Drift 越小}
$$

---

## 12. 上下文设计的核心原则

这一段可以浓缩成一个非常重要的链条：

```text
模糊 Intent
    ↓
大量隐含约束
    ↓
模型自行猜测
    ↓
实现发生 Drift
```

而更好的方式是：

```text
明确 Intent
    ↓
System Design
    ↓
Specification
    ↓
Machine-verifiable Criteria
    ↓
Implementation
    ↓
Automatic Verification
    ↓
持续修正
```

最终可以总结为：

#### **原则一：减少模型猜测**

**能明确写出来的约束，不要留在自己的脑子里。**

#### **原则二：让目标尽可能可验证**

尤其是能够通过测试脚本、编译结果、静态检查等机器手段验证的目标。

#### **原则三：把 Design、Spec、Implementation 相互印证**

不要只看“代码能不能跑”，还要检查：

$$
\text{代码实现} \stackrel{?}{=} \text{Spec} \stackrel{?}{=} \text{设计目标}
$$

#### **原则四：把 Agent 看成一个可以反复迭代的执行者**

只要反馈信号明确：

$$
\text{失败} \rightarrow \text{修复} \rightarrow \text{再验证}
$$

Agent 就可以进行非常多轮的自动尝试。

#### **最核心的一句话**

> **好的 Context，不是把更多文字塞给模型，而是把原本存在于人脑中的关键约束转化成模型能够看到、理解并验证的 Specification。**

## 明确约束、最小引导与 AI 生成结果的“AI 味”

### 1. 越具体的资源约束，模型越能还原真实目标

在生成一个复杂系统时，模型并不一定需要“从零创造所有东西”。

例如，如果目标是：

> 在南京大学仙林校区中驾驶。

那么除了告诉模型“做一个赛车游戏”，还可以进一步告诉它：

- **使用仙林校区真实地图数据**
- 地图文件是什么格式；
- 使用哪些公开可用的美术资产；
- 哪些资产用于道路、建筑、树木、车辆等。

如果这些信息足够具体，模型就可以：

$$
\text{真实地图数据} + \text{美术资产} + \text{系统逻辑} \rightarrow \text{重新建模目标世界}
$$

也就是说， **模型并不一定需要自己发明世界，它也可以根据已有资源重建世界。**

---

### 2. 不提供资源约束，模型很容易默认“从零生成”

如果用户只说：

> “帮我做一个城市赛车游戏。”

模型可能默认：

> “所有地图、城市、树木、车辆等内容都由我自己生成。”

于是它会走向一种 **Self-contained（自包含、从零构建）** 的方案。

但用户实际可能想的是：

> **复用已有地图和公开资产，只补足必要的程序逻辑。**

因此，不明确资源来源，也是一种 **隐含约束缺失** 。

可以理解为：

$$
\text{未说明资源来源} \rightarrow \text{模型自行假设} \rightarrow \text{方案偏移}
$$

---

## 如何写一个好的 Agent 上下文

### 3. 一个好的 Prompt 至少要把三个问题说清楚

课程中给出的核心思路可以概括成：

#### **① 我要什么**

即 **Goal / Intent** 。

例如：

> 我要一个在真实校园地图中驾驶的赛车游戏。

#### **② 用什么实现**

即技术和资源约束：

- 使用什么语言；
- 使用什么框架；
- 使用什么地图数据；
- 使用什么美术资源；
- 哪些现有组件必须复用。

#### **③ 怎样才算正确**

即 **Acceptance Criteria（验收标准）** ：

- 功能是否完成；
- 指定资源是否正确使用；
- 是否通过测试；
- 是否符合架构和技术约束。

因此可以抽象成：

$$
\boxed{ \text{Goal} + \text{Constraints} + \text{Acceptance Criteria} }
$$

这比单纯告诉模型：

> “帮我做一个 XX。”

明确得多。

---

### 4. 真正高级的 Context Engineering：用最小信息提供最大约束

这里还有一个非常重要的思路：

> **并不是给模型的 Prompt 越长越好。**

模型本身已经拥有非常强的通用能力，因此很多实现细节并不需要人类逐条教它。

真正需要人工提供的是：

**那些模型无法从上下文中自行推断出来的关键约束。**

可以把它理解成：

$$
\text{人类负责约束方向} + \text{模型负责大量具体实现}
$$

而不是：

$$
\text{人类负责描述每一个实现步骤}
$$

因此，优秀的上下文设计追求的是：

> **用尽可能少的信息，让模型准确理解你真正的目标。**

---

### 5. 人类的角色从“执行者”逐渐转向“约束设计者”

对于能力足够强的模型，可以把它想象成一个：

> **知识面极广、解决问题能力非常强的博士级工程师。**

那么人类真正需要做的，往往不是告诉它：

> “第一步打开这个文件，第二步写这个函数，第三步再做这个……”

而是告诉它：

- 最终目标是什么；
- 哪些事情不能做；
- 哪些资源必须使用；
- 什么样的结果才算正确。

然后让模型自行规划和执行。

因此，人类的核心工作越来越接近：

$$
\text{定义问题} + \text{定义约束} + \text{定义验收标准}
$$

而具体实现则更多交给 Agent。

---

## Agent 的完成状态

### 6. 在约束充分的情况下，Agent 的结果通常有两种

如果目标定义得足够清楚，Agent 的工作状态可以简单理解为：

```text
明确目标
   ↓
Agent 持续尝试
   ↓
┌───────────────┐
│               │
完成            无法完成
│               │
↓               ↓
验收通过      重新规划
```

也就是说，它要么：

**完成任务。**

要么经过多轮尝试以后发现：

> **当前方案无法继续，需要重新规划。**

理想情况下，不应该是 Agent 因为不知道你的真实需求而随意结束，而应该是：

> **目标明确 → 持续执行 → 根据反馈调整。**

---

## AI 生成页面的一个典型问题：技术正确但审美偏移

### 7. “现代风格”并不等于你真正想要的风格

另一个非常典型的例子是让 AI 生成个人主页。

例如给模型一个非常简短的 Prompt：

> “生成一个现代风格的个人主页。”

模型可能生成一个：

- UI 很精致；
- 动画很流畅；
- 滚动效果很好；
- 浮动效果很好；
- 视觉效果专业；

的页面。

从技术和视觉完成度来看，它可能非常优秀。

但用户依然可能觉得：

> **“这个页面 AI 味很重。”**

问题就在于：

**“现代风格”并没有精确定义你想要的视觉语言。**

---

### 8. AI 很难凭一句“不要 AI 味”恢复具体设计意图

进一步告诉模型：

> “不要那么 AI。”

看起来是在增加约束，但实际上这个约束依旧很模糊。

因为：

**“AI 味”本身不是一个明确的 Specification。**

模型需要自行猜：

- 什么叫 AI 味？
- 是颜色问题？
- 是动画太多？
- 是布局太规整？
- 是字体太统一？
- 是视觉元素太模板化？
- 是文案太像 AI？

因此：

$$
\text{“不要 AI 味”} \neq \text{明确的设计规范}
$$

这与前面的软件工程问题其实完全一致：

> **抽象目标如果没有进一步转化为可观察的约束，模型依旧需要自行补全。**

---

## 真实设计中的“隐性细节”

### 9. 人类设计往往存在大量难以用一句 Prompt 表达的细节

一个真正由人设计出来的主页，可能看起来只是：

> “一个干净的终端风格主页。”

但背后可能存在大量具体处理：

- 真实终端式的交互；
- 支持 **Pipeline / Pipe（管道式操作）** ；
- 字体并非严格规整；
- 特意保留某些“不完美”；
- 特定的排版节奏；
- 轻微的视觉噪声；
- 某些细节经过人工后处理。

这些东西可能根本不会出现在最初的 Intent 里，却深刻影响最终观感。

这就是典型的：

$$
\text{显式需求} + \text{大量隐含设计决策} \rightarrow \text{最终作品}
$$

---

### 10. “不完美”有时反而是设计的一部分

案例中，真正的终端界面中的文字并不是完全工整的。

甚至进行了很小的 **Post-processing（后处理）** ，让字体保留一些微妙的不完美。

这种细节很难通过：

> “生成一个现代终端风格的网站。”

自动得到。

因为对模型而言：

> **规整、平滑、精致往往是更明显、更容易学习到的“高质量模式”。**

而人类设计者有时反而会主动加入：

**不规则、瑕疵、克制、非模板化的细节。**

这也是为什么：

> **AI 可以很容易生成“看起来很专业”的东西，却未必能自动生成“具有特定个人设计语言”的东西。**

---

## 11. 本段核心方法论

可以将这一段统一成下面这套方法：

```text
模糊 Intent
    ↓
明确 Goal
    ↓
补充关键资源约束
    ↓
补充技术约束
    ↓
定义正确标准
    ↓
交给 Agent 自主实现
    ↓
自动验证 / 人工验收
```

其中最重要的不是：

> **“告诉模型每一步怎么做。”**

而是：

> **“把模型无法凭空知道的关键约束告诉它。”**

因此，Context Engineering 的理想状态可以概括为：

$$
\boxed{ \text{最少的人工引导} + \text{最明确的关键约束} + \text{可验证的成功标准} \rightarrow \text{最大化 Agent 自主执行能力} }
$$

最终，人类越来越重要的能力不是“比模型更会实现”，而是：

> **知道哪些信息必须告诉模型，哪些事情可以放心交给模型自己决定。**

## 设计约束、审美多样性与生成式软件工程

### 1. 后处理可以显著改变 AI 生成内容的观感

一个页面即使完全由 AI 生成，也不意味着最终一定会呈现出明显的“AI 味”。

例如，可以在 **Excalidraw / 终端式渲染** 完成后增加一层 **Post-processing（后处理）** ，人为加入一些细微的不完美：

- 模拟真实打字机打字的效果；
- 让文字不那么工整；
- 保留轻微的随机性；
- 调整渲染后的细节。

这样最终效果会更加接近真实人工制作的界面。

这里有一个重要现象：

> **“看起来不像 AI”不一定意味着人类亲自写了代码。**

完全可以是：

$$
\text{AI 生成} + \text{人工设计约束} + \text{后处理} \rightarrow \text{更具个性的最终作品}
$$

因此，关键不在于“有没有 AI 参与”，而在于：

**最终结果是否受到明确的设计意图控制。**

---

### 2. “AI 味”往往来自缺乏具体约束

如果只给 Agent：

> “做一个现代风格的主页。”

模型就会根据自己最熟悉、最常见的模式生成结果。

但如果进一步明确：

- **终端是什么风格**
- 背景是什么；
- 前景是什么；
- 字体如何渲染；
- 渲染完成以后如何做后处理；
- 页面应该采用什么样式；
- 排版应该如何组织；
- 哪些视觉元素应该避免。

那么模型的自由空间就会明显缩小。

可以把它理解为：

$$
\text{Model Output} = \text{Model Capability} + \text{Constraint}
$$

其中：

$$
\text{Constraint 越弱} \Rightarrow \text{可发散空间越大}
$$

而：

$$
\text{Constraint 越明确} \Rightarrow \text{结果越接近目标}
$$

因此：

> **“去掉 AI 味”真正有效的方法，不是告诉模型“不要有 AI 味”，而是把你真正喜欢的视觉特征拆成具体、可执行的设计约束。**

---

## 人类设计能力仍然非常重要

### 3. 要控制 Agent，首先必须知道自己想要什么

这意味着生成式软件工程并不意味着：

> “以后不用学习设计了，因为 AI 会帮我设计。”

恰恰相反。

如果希望让 AI 稳定地产生自己真正喜欢的作品，就必须具备足够的 **审美和设计判断能力** 。

例如需要了解：

- 前端设计；
- UI / UX；
- 排版；
- 间距；
- 字体；
- 色彩；
- 动画；
- 交互；
- 页面结构。

原因很简单：

> **如果你无法判断“好在哪里”，就很难把这种好转化成 AI 能理解的约束。**

---

### 4. 阅读优秀作品，是建立“审美词汇表”的过程

除了学习设计知识，还应该主动观察优秀作品。

例如看到一个网页时，不只是觉得：

> “这个网页很好看。”

而应该进一步追问：

> **“它为什么好看？”**

可能答案是：

- 两个按钮之间用了非常规的间距；
- 某个元素的位置非常特别；
- 排版比例与常见网站不同；
- 字体选择很有个性；
- 某个交互动画非常克制；
- 某种不规则设计打破了模板感。

也就是说，要把：

$$
\text{“我觉得很好看”}
$$

逐步转化成：

$$
\text{可描述的设计特征}
$$

最终形成自己的 **审美词汇表** 。

---

### 5. “漫无目的探索”在 AI 时代反而更加重要

学习和设计并不总是需要一个明确任务。

也可以：

- 浏览优秀网站；
- 观察不同作品；
- 记录喜欢的设计；
- 比较不同人的风格；
- 探索不同领域。

这种探索可能没有直接产出，却会积累：

**经验 → 判断力 → 偏好 → 更明确的需求。**

因此：

> **接触足够多样的作品，本身就是建立设计能力的一部分。**

---

## AI 生成的同质化风险

### 6. 一个值得警惕的问题：AI 可能让数字内容越来越相似

如果所有人都使用类似的模型，并且都不给模型额外约束，那么模型很可能反复生成自己最熟悉、最常见的模式。

于是会出现：

$$
\text{相同模型} + \text{相似 Prompt} \rightarrow \text{相似结果}
$$

例如：

- 类似的页面布局；
- 类似的配色；
- 类似的动画；
- 类似的插画；
- 类似的人物脸型；
- 类似的宣传图。

久而久之，内容就容易出现 **同质化** 。

---

### 7. “AI 味”本质上是一种统计意义上的趋同

模型会倾向于向自己最熟悉的模式靠拢。

当用户只提供：

> “现代风格。”

模型需要从大量可能性中选择一个最合理的区域。

于是容易：

$$
\text{模糊需求} \rightarrow \text{模型默认风格} \rightarrow \text{大量相似输出}
$$

因此，“AI 味”往往不是某个具体视觉元素，而是：

> **模型在缺乏个性化约束时，向高概率、常见模式收敛所产生的整体感觉。**

---

## 多样性是培养个人判断力的重要来源

### 8. 为什么需要接触不同的人、老师和风格

课程中进一步把这个问题扩展到了教育。

之所以需要：

- 不同老师；
- 不同课程；
- 不同同学；
- 不同观点；
- 不同作品；

一个重要原因就是：

> **多样性能够帮助人建立自己的判断标准。**

如果你只接触一种风格，很可能会把：

> “别人默认认为好的东西”

误认为：

> “自己真正喜欢的东西”。

而当你接触足够多样的作品之后，就会逐渐知道：

- 哪些东西自己喜欢；
- 哪些东西自己不喜欢；
- 喜欢的原因是什么；
- 不喜欢的原因是什么。

最终才能把个人偏好进一步表达成明确要求。

---

### 9. 多样性最终会转化成更强的 Prompt 能力

整个过程可以表示为：

$$
\text{接触更多样的作品} \rightarrow \text{形成比较} \rightarrow \text{建立审美判断} \rightarrow \text{明确个人偏好} \rightarrow \text{形成具体约束} \rightarrow \text{更精准地控制 AI}
$$

因此：

> **Prompt Engineering 的上限，在很大程度上受到提问者自身判断力的限制。**

不是模型不会做，而是用户是否知道：

> **自己到底想让它做成什么样。**

---

## 技术能力越扎实，AI 越能成为讨论对象

### 10. AI 时代最重要的能力正在发生变化

如果一个人已经能够：

- 理解技术选型；
- 判断不同技术方案的优缺点；
- 理解架构设计；
- 明确性能、维护性和复杂度之间的权衡；

那么很多具体技术实现其实已经可以交给 AI。

这时候，可以直接把 AI 当成一个技术讨论对象：

> “我现在有两个技术方案，哪个更合适？”

而不是要求 AI：

> “替我从零决定一切。”

---

### 11. 技术选型可以使用“AI + 费曼学习法”

这一过程与前面提到的 **Feynman Technique（费曼学习法）** 是一致的。

例如：

```text
我提出两个技术方案
       ↓
让 AI 分析各自优缺点
       ↓
我自己判断
       ↓
向 AI 解释我的选择
       ↓
让 AI 反驳我的理由
       ↓
发现自己的逻辑漏洞
       ↓
重新评估
```

最终形成的不是：

> **“AI 替我做决定。”**

而是：

> **“AI 帮助我把自己的判断变得更加清晰、完整、可验证。”**

---

## 12. 本段核心逻辑

```text
生成结果
   ↓
发现 AI 味
   ↓
分析“为什么不像我想要的”
   ↓
把审美拆成具体设计约束
   ↓
让 Agent 按约束生成
   ↓
必要时进行后处理
   ↓
得到更符合个人意图的结果
```

而更深层的一条链是：

$$
\boxed{ \text{知识} \rightarrow \text{观察} \rightarrow \text{比较} \rightarrow \text{判断} \rightarrow \text{明确意图} \rightarrow \text{设计约束} \rightarrow \text{控制 AI} }
$$

**生成式软件工程真正需要学习的，不只是“怎样让 AI 写代码”，而是怎样形成自己的判断，并把这种判断转换成 AI 能够执行和验证的约束。**

## 上下文工程、指令遵循与模型的“纸笔”记忆

### 1. 技术选型本身就是可以交给 AI 讨论的问题

例如要设计一个 **教务系统** ，后台可能有多种技术选择：

- **Python**
- **Java**
- **TypeScript**

真正的问题并不是：

> “AI 告诉我应该选哪个？”

而是：

> **“基于这个系统的实际约束，这几个方案分别有什么优缺点？”**

例如可以进一步考虑：

- 未来是否需要上云；
- 云环境对不同技术栈的支持情况；
- 部署和运维成本；
- 性能与扩展能力；
- 团队学习和维护成本；
- 生态与第三方库；
- 长期演进是否方便。

因此可以让 AI 充当一个 **技术讨论者 / 挑战者** ：

> **“我准备采用方案 A，请你挑战这个选择，找出它可能存在的问题。”**

这种方式与前面的费曼学习法是一致的： 不是简单让 AI 替自己做决定，而是让 AI **反驳、质疑和补充自己的判断** 。

---

## 让模型更好地遵循指令

### 2. 理解模型为什么“听话”，才能更好地写 Prompt

要想设计更有效的 Prompt，需要先理解：

> **模型到底是怎样遵循指令的？**

模型本质上仍然可以理解为一个 **概率分布模型** 。

给定当前 Context，它预测下一个 Token：

$$
P(x_{t+1}\mid x_1,x_2,\ldots,x_t)
$$

因此从最底层来看：

> **模型并没有一个独立于生成过程之外的“执行指令模块”；它仍然是在根据上下文不断预测下一个 Token。**

所以，“遵循指令”最终也会体现在：

**当前 Context 改变了哪些 Token 更可能被生成。**

---

### 3. 一个 Token 的生成，本质上是一次有限的计算

即使模型参数规模非常巨大，例如达到 **Trillion-scale（万亿级）** ，也不能简单理解为：

> 每生成一个 Token，都把整个模型所有参数完整计算一遍。

实际推理过程中，每一步只会执行与当前 Token 生成相关的那部分计算。

尤其对于使用 **Mixture of Experts（MoE，专家混合）** 的模型，可以理解为：

$$
\text{Huge Model} \rightarrow \text{部分参数 / 专家被激活} \rightarrow \text{生成一个 Token}
$$

因此：

> **模型总体规模可以非常大，但单次 Token Prediction 的实际计算仍然是有限的。**

这为后面的一个类比提供了基础：

**模型本身很强，不代表单步推理拥有无限计算。**

---

## 有限状态机、图灵机与“外部记忆”

### 4. 有限状态机：计算能力受到有限状态限制

大家在数字电路等课程中接触过 **Finite State Machine（有限状态机，FSM）** 。

例如一个简单计数器：

```text
000
 ↓
001
 ↓
010
 ↓
011
 ↓
……
 ↓
返回某个状态
```

它只能处在有限数量的状态中。

因此可以把 FSM 理解为：

$$
\text{有限状态} + \text{状态转移规则}
$$

---

### 5. 图灵机的关键优势：拥有外部可读写存储空间

**Turing Machine（图灵机）** 与有限状态机的一个经典区别，是它拥有一条可以不断扩展的 **Tape（纸带）** 。

这个纸带可以充当记忆：

```text
有限状态控制器
      +
可读写的无限纸带
      ↓
更强的计算能力
```

因此：

> **有限控制 + 外部存储，可以产生远强于纯有限状态系统的计算能力。**

这也是理论计算机科学中非常重要的思想。

---

## 人脑、模型与“纸和笔”

### 6. “人脑是有限状态机”只是一个帮助理解的类比

课程使用了一个很有启发性的类比：

> **如果只考虑人脑当前正在进行的计算，人可以近似看作一个有限状态系统。**

因为：

- 神经元数量是有限的；
- 当前可参与计算的内部状态是有限的；
- 每一次具体思考所能处理的信息和计算量也是有限的。

因此：

$$
\text{人脑本身} \approx \text{有限状态计算系统}
$$

这当然不是对人脑真正神经计算机制的严格形式化，而是为了说明一个更重要的概念：

> **外部记忆可以极大增强一个有限计算系统的实际能力。**

---

### 7. “Paper and Pencil”让有限计算系统获得更强能力

有一个经典的说法：

> **人是有限状态自动机，但当人拥有 Paper and Pencil（纸和笔）时，就获得了类似图灵机的计算能力。**

这里真正想强调的不是严格的生物学或计算理论等价，而是：

**记录本身就是计算能力的扩展。**

例如面对一个复杂问题：

```text
只在脑中思考
    ↓
前面的信息不断丢失
    ↓
容易忘记
```

而如果把思考过程写下来：

```text
思考
 ↓
记录
 ↓
继续思考
 ↓
回看记录
 ↓
继续推导
 ↓
积累越来越多的信息
```

那么就形成了一个外部记忆系统。

因此学习上的关键实践是：

> **一边思考，一边把重要信息记录下来。**

随着时间积累，记录会越来越多，知识和思考成果也就越来越容易复用。

---

## Chain of Thought：模型自己的“纸和笔”

### 8. Chain of Thought 可以理解为给模型增加了一块外部工作区

现代的 **Chain of Thought（思维链）** 模型，可以从这个角度理解：

> **模型把自己的 Context 当成了“纸和笔”。**

也就是：

$$
\text{当前思考结果} \rightarrow \text{写入 Context} \rightarrow \text{继续读取} \rightarrow \text{继续思考}
$$

这样模型就不再完全依赖单次瞬间计算，而能够把中间结果保留下来，再利用这些结果继续向后推理。

这与人类：

> **想一步 → 写下来 → 再看前面的结果 → 继续想**

非常相似。

---

### 9. Context 本身就是模型的“工作记忆”

从这个角度看：

$$
\boxed{ \text{Model Computation} + \text{Context as Memory} }
$$

才形成了今天强大的 Agent 推理能力。

Context 中可以保存：

- 问题；
- 已知条件；
- 中间推理结果；
- 工具调用结果；
- 计划；
- 环境信息；
- 历史对话。

模型每次预测下一个 Token 时，都可以再次读取这些内容。

因此：

> **Context 不只是输入，它同时承担了“工作记忆”的角色。**

---

## Append-only Context 的局限

### 10. 模型的“纸和笔”存在一个重要缺陷：只能不断向后写

这里还有一个非常重要的区别。

普通纸笔可以：

- 修改；
- 擦除；
- 重写；
- 在任意位置增删内容。

但模型的 Context 在很多情况下更接近：

**Append-only（只追加、不修改历史）** 。

即：

```text
A
 ↓
A + B
 ↓
A + B + C
 ↓
A + B + C + D
 ↓
……
```

它主要是在末尾不断追加新的内容，而不是直接把前面的 Token 擦掉重写。

---

### 11. 只能追加，会带来上下文管理问题

随着任务持续执行：

$$
|Context| \uparrow
$$

上下文长度不断增加。

于是可能出现：

- Context 越来越长；
- 旧信息与新信息混在一起；
- 需要更强的注意力机制才能找到关键信息；
- 最终可能需要压缩或截断。

因此，后续的 **Context Engineering** 问题就自然产生了：

> **既然 Context 是 Agent 的“纸和笔”，那么如何让这块纸长期保持有用？**

这会进一步涉及：

**信息记录、摘要、压缩、清理、重新组织以及上下文生命周期管理。**

---

### 12. 本段核心逻辑

整个理论链条可以浓缩为：

```text
Next Token Prediction
        ↓
每次推理都是有限计算
        ↓
单步计算能力有限
        ↓
需要记忆中间结果
        ↓
Context 成为“纸和笔”
        ↓
模型可以不断把结果写回 Context
        ↓
形成更长的推理过程
        ↓
Agent 获得更强的复杂任务能力
```

而它与前面的 Context Engineering 又自然连接起来：

$$
\boxed{ \text{模型能力} \approx \text{单步计算} + \text{Context 提供的外部工作记忆} }
$$

因此， **Prompt / Context 不只是“告诉模型做什么”，还在某种程度上决定了模型能够记住什么、继续利用什么，以及能够把复杂思考推进多远。**

## 从 Next Token Prediction 到 Test-Time Scaling

### 1. 模型已经学会利用 Context 进行多步推理

前面的核心观点是：模型并不是每次都“一步直接得到答案”。

对于简单问题，例如：

> `1 + 1 = ?`

模型可以直接通过 **Next Token Prediction** 输出：

> `2`

因为这个问题非常简单，不需要复杂的中间推理。

但面对困难问题时，模型可以采用不同的策略：

```text
问题较难
   ↓
先分析问题
   ↓
提出一个可能的解法
   ↓
把中间思考写入 Context
   ↓
检查这个解法是否正确
   ↓
发现问题
   ↓
修改 / 重新推导
   ↓
再次验证
   ↓
得到更可靠的答案
```

因此，模型逐渐表现出一种类似人类解题的模式：

> **“这个问题比较难，我不能马上回答，需要先想一想。”**

---

### 2. Chain of Thought：把中间思考过程写进 Context

这种能力可以通过 **Chain of Thought（思维链）** 来理解。

关键思想是：

> **先产生中间步骤，再利用这些中间步骤继续计算。**

模型不必：

$$
\text{Question} \rightarrow \text{Answer}
$$

而可以变成：

$$
\text{Question} \rightarrow \text{Intermediate Reasoning} \rightarrow \text{Candidate Answer} \rightarrow \text{Verification} \rightarrow \text{Final Answer}
$$

这里的中间 Token 不只是“多说了一些话”，而是在一定程度上充当了模型的 **外部工作记忆和中间计算空间** 。

---

### 3. “先写出解，再检查解”是关键能力

面对复杂任务时，模型可以先构造一个候选答案。

但它并不一定相信自己的第一次尝试。

因此会形成：

$$
\text{生成候选解} \rightarrow \text{检查} \rightarrow \begin{cases} \text{正确} & \rightarrow \text{继续}\\ \text{错误} & \rightarrow \text{修改} \end{cases}
$$

如果某条路线长时间无法得到正确结果，还可能：

$$
\text{当前方案失败} \rightarrow \text{换一种思路} \rightarrow \text{重新推导}
$$

这就是现代推理模型的重要变化：

> **模型不再要求自己必须“一步答对”，而可以通过增加推理计算量逐渐逼近目标。**

---

## 从“必须回答”到“努力答对”

### 4. 早期模型存在“无论如何都要回答”的倾向

早期 ChatGPT 类模型在没有较强 **Reasoning / Chain of Thought** 能力时，一个明显问题是：

> **即使不知道答案，也倾向于给出一个回答。**

这是因为训练过程中的反馈机制会产生一个简单的激励：

- 不回答 → 很可能直接被判定为不好；
- 随便回答 → 有概率答对；
- 答对 → 获得高分；
- 答错 → 获得低分。

因此从优化角度看：

$$
\text{“始终给出答案”}
$$

有时比：

$$
\text{“承认自己不知道”}
$$

更有利于获得奖励。

这也是模型容易产生 **Hallucination（幻觉）** 的一个重要背景：

> **模型存在“即使不确定也要生成某种答案”的压力。**

---

### 5. 强化学习改变了模型对“错误”的态度

随着 **Reinforcement Learning（强化学习）** 等训练方法的发展，模型越来越能够意识到：

> **答错的代价可能远高于多花一些 Token 去思考。**

于是它开始倾向于：

$$
\text{更多计算} \rightarrow \text{更充分验证} \rightarrow \text{降低错误率}
$$

也就是从：

> **“必须回答。”**

逐渐转向：

> **“必须尽量找到正确答案。”**

这是一种非常重要的行为变化。

---

## Test-Time Scaling：用更多推理计算换取更高成功率

### 6. Test-Time Scaling 的核心思想

这种在推理阶段增加计算量来提升结果质量的方式，可以称为：

**Test-Time Scaling（测试时扩展 / 推理时扩展）** 。

核心关系可以概括为：

$$
\text{更多 Test-Time Compute} \Rightarrow \text{更多思考 / 尝试 / 验证} \Rightarrow \text{更高成功概率}
$$

因此，模型能力不再只由：

> **“训练时模型有多大”**

决定。

还与：

> **“真正解决这个问题时，愿意花多少计算量”**

有关。

---

### 7. 推理模型越来越像“不断试错逼近目标”

一个复杂问题可以被看成优化过程：

$$
x_0 \rightarrow x_1 \rightarrow x_2 \rightarrow \cdots \rightarrow x^*
$$

其中：

- $x_0$：最初的尝试；
- $x_i$：不断修正后的中间结果；
- $x^*$：最终满足目标的解。

因此：

> **推理模型的强大之处，不仅在于一次生成得多好，还在于它愿意利用更多 Token 进行尝试、验证和修正。**

这与 Agent 中的：

$$
\text{尝试} \rightarrow \text{观察} \rightarrow \text{修正} \rightarrow \text{再次尝试}
$$

实际上是同一种基本思想。

---

## 用“故意刁钻的任务”观察模型如何推理

### 8. 复杂约束任务特别适合观察模型的推理行为

课程给出的实验非常有代表性：设计一个对人类来说很奇怪、甚至接近 **Nonsense（无意义约束）** 的任务。

例如同时要求模型：

- 用中文写作；
- 写一首 **押韵的藏头诗** ；
- 内容与动物有关；
- 指定 **8 个字** ；
- 这 8 个字必须按照指定顺序分别出现在 8 句中；
- 任务本身没有实际意义，只是为了测试模型能否同时遵守多重约束。

这种任务对人而言非常不自然。

但模型会把它当成一个真正需要解决的约束问题。

---

### 9. 模型会把复杂任务拆成多个子问题

面对这个任务，模型不会简单地“一次性输出”。

它可能先思考：

> **首先需要确定韵脚。**

因为如果直接往下写，后面的句子可能无法满足押韵要求。

于是形成类似：

```text
多重约束
   ↓
分析约束之间的关系
   ↓
选择一个韵脚方案
   ↓
尝试生成
   ↓
检查是否满足要求
   ↓
不满足 → 修改
   ↓
仍然困难 → 更换方案
   ↓
继续验证
```

这里体现出了非常典型的：

**Constraint Solving（约束求解）** 。

---

### 10. 模型甚至可以通过“换方案”重新搜索

如果当前韵脚方案不好，模型可能会意识到：

> 当前路线继续下去很困难。

然后重新选择另一套方案：

$$
\text{方案 A} \rightarrow \text{发现冲突} \rightarrow \text{方案 B} \rightarrow \text{继续尝试}
$$

这说明模型并不只是线性生成文字，还可能进行：

- 候选方案生成；
- 局部验证；
- 失败回退；
- 重新规划。

这与程序中的 **Backtracking（回溯）** 有一定相似性。

---

## “核磁共振”式地观察模型的推理

### 11. 特殊测试任务可以暴露模型的推理偏好

课程中用了一个很形象的类比：

> **通过这种特殊任务，可以像把模型“大脑拿出来做核磁共振”一样，观察它是怎样解决问题的。**

当然，这不是字面意义上的观察模型内部神经活动，而是指：

**通过设计有针对性的任务，观察模型外显的推理行为。**

例如可以观察：

- 它先处理哪个约束；
- 它优先考虑押韵还是内容；
- 它什么时候进行验证；
- 失败后会不会换方案；
- 会不会重新开始；
- 如何处理多个互相冲突的条件。

因此，精心设计测试题本身就是一种很好的 **模型研究方法** 。

---

## 12. 这里的一个重要转变：从“生成”到“搜索”

传统的文本生成可以简单理解成：

$$
\text{Context} \rightarrow \text{Next Token} \rightarrow \text{Next Token} \rightarrow \cdots
$$

而推理模型越来越像：

$$
\text{Problem} \rightarrow \text{Candidate} \rightarrow \text{Evaluate} \rightarrow \text{Revise} \rightarrow \text{Candidate} \rightarrow \cdots
$$

因此可以把它看作：

> **从单纯的序列生成，逐渐加入了搜索、验证和迭代。**

这也是 **Test-Time Scaling** 为什么重要的原因：

**增加 Token 不只是让模型“说得更多”，而可能让它获得更多真正用于解决问题的计算步骤。**

---

## 13. 本段核心逻辑

```text
模型本质
    ↓
Next Token Prediction
    ↓
单次推理计算有限
    ↓
复杂问题无法立即得到正确答案
    ↓
把中间结果写入 Context
    ↓
继续利用这些结果推理
    ↓
进行验证
    ↓
发现错误就修改
    ↓
必要时换一条路线
    ↓
不断逼近正确答案
```

最终可以浓缩为：

$$
\boxed{ \text{更多推理 Token} \rightarrow \text{更多计算} \rightarrow \text{更多尝试与验证} \rightarrow \text{更高的任务成功率} }
$$

而这正是 **Test-Time Scaling** 的核心思想：

> **模型的能力不只来自“它训练了多少”，也来自“它在真正解决一个问题时，愿意花多少计算量去想”。**

## Ver验器驱动的 Prompt Engineering：从复杂约束到可验证反馈

### 1. 模型可以通过进一步收束 Spec，降低“AI 味”

在前面的藏头诗实验中，即使模型已经能够很好地执行复杂指令，生成结果仍然可能带有明显的默认风格。

通过继续增加一些 **Prompt 约束** ，例如对内容形式、问题结构等进行进一步限定，可以让输出逐渐向目标收束。

但这里仍然存在一个重要事实：

> **模型执行指令的能力很强，不意味着它天然知道什么结果才是“你真正满意的结果”。**

因此，继续增加约束的价值主要在于：

$$
\text{更多明确约束} \rightarrow \text{更小的搜索空间} \rightarrow \text{更少的结果漂移}
$$

---

## 2. 为什么训练数据里没有见过题目，模型仍然能做

课程中特意设计了一些几乎不可能出现在训练集中的任务，例如：

- 特殊的藏头诗；
- 多重韵脚约束；
- 指定日期字符；
- 18 字句子；
- 要求全部使用相同偏旁 / 部首。

这类任务的重要意义在于：

> **模型不需要“记住答案”，也可以依靠训练形成的通用推理能力解决新问题。**

也就是说：

$$
\text{Training Data} \neq \text{Exact Problem}
$$

但依然可能：

$$
\text{Learned Reasoning Ability} \rightarrow \text{Solve Novel Problem}
$$

---

### 3. 强化训练中的“可反馈任务”非常重要

课程认为，这类模型的训练数据中，大量任务可能属于具有明确反馈信号的领域，例如：

- **代码**
- **数学题**
- 其他可以自动判断对错的任务。

这些任务有一个非常重要的特点：

> **结果容易验证。**

例如：

#### 编程

```text
代码
 ↓
编译
 ↓
测试
 ↓
PASS / FAIL
```

#### 数学

```text
解答
 ↓
计算 / 验证
 ↓
正确 / 错误
```

因此模型可以通过强化学习不断强化：

$$
\text{尝试} \rightarrow \text{反馈} \rightarrow \text{修正}
$$

这种训练最终可能迁移到训练数据之外的奇怪问题上。

---

## 4. 复杂语言约束也可以被当作约束求解问题

例如要求：

> **写一个 18 字的一句话，并且所有字都使用相同的偏旁或部首。**

对人类来说，这也是非常困难的题目。

但文本模型可以通过 **Chain of Thought** 逐步求解：

```text
题目
 ↓
分析约束
 ↓
选择一个容易扩展的偏旁
 ↓
例如选择“氵”
 ↓
列举符合条件的字
 ↓
尝试构造句子
 ↓
检查每个字
 ↓
发现问题
 ↓
修改
 ↓
重新检查
```

例如模型可能首先发现：

> **“三点水”比较容易找到大量候选字。**

然后围绕这一约束不断构造文本。

这说明：

> **模型并不是因为“见过这道题”才会做，而是把它转换成了一个可以逐步搜索和验证的约束问题。**

---

## 5. 文本模型甚至可以处理自己并不擅长的结构性约束

一个值得注意的现象是：

**纯文本模型对空间结构和视觉信息的直接感知能力通常并不如视觉模型。**

但即使如此，它仍然能够通过语言形式表达和推理，把复杂的“字符结构约束”转化成可处理的问题。

例如：

$$
\text{偏旁约束} + \text{字数约束} + \text{语义约束} \rightarrow \text{候选文本搜索}
$$

所以它并不是直接“看到”字符的空间结构，而是在语言表示空间中进行推理和筛选。

---

## 6. 人类在某些任务上仍然具有明显优势

不过，这并不意味着模型在所有创造性任务上都已经超过人类。

对于这种特殊文字游戏，人类往往还具有很强的：

- 语言直觉；
- 文化知识；
- 谐音联想；
- 创造力；
- 群体智慧；
- 对“什么更有趣”的判断。

尤其是经典文字游戏和文学作品中，人类经过长期文化积累形成了非常强的语言审美。

因此：

$$
\text{AI 的约束求解能力} \neq \text{人类的语言创造力}
$$

两者各有优势。

---

## Verifier：Prompt Engineering 中最关键的概念

### 7. 好 Prompt 最重要的不是“描述得多”，而是“结果是否可验证”

这一段最重要的关键词是：

**Verifier（验证器）** 。

核心思想是：

> **如果你能够给模型一个明确的 Verifier，那么模型就能围绕这个反馈信号不断改进。**

可以抽象成：

$$
\boxed{ \text{Task} + \text{Verifier} + \text{Agent} \rightarrow \text{Iterative Improvement} }
$$

例如：

```text
Agent 输出
    ↓
Verifier 检查
    ↓
失败原因
    ↓
Agent 修改
    ↓
Verifier 再检查
    ↓
……
    ↓
通过
```

---

### 8. Verifier 的价值：把“好不好”变成反馈信号

假设任务有明确的验证器：

```text
compile
test
lint
assert
expected output
```

那么 Agent 不需要完全依赖自己的主观判断。

它只需要不断优化：

$$
V(x) \rightarrow 1
$$

其中：

- $x$：当前候选解；
- $V(x)$：验证器对候选解的判定；
- $1$：满足要求。

于是任务就变成：

> **不断修改候选解，直到 Verifier 通过。**

---

## 9. 为什么代码任务特别适合 Agent

编程任务天然拥有非常强的 Verifier。

例如：

$$
\text{代码} \rightarrow \text{Build} \rightarrow \text{Tests} \rightarrow \text{结果}
$$

因此 Agent 可以：

- 写代码；
- 编译；
- 看错误；
- 修代码；
- 再编译；
- 再运行测试；
- 继续修正。

这使代码 Agent 特别适合执行大量自动化迭代。

---

## 10. 教学任务反而更难建立 Verifier

与编程相比， **教学任务** 的 Verifier 很难设计。

例如：

> “把这个知识讲得很好。”

这个目标缺乏明确判定标准。

“好”可能同时包括：

- 是否准确；
- 是否易懂；
- 是否有条理；
- 是否适合当前听众；
- 是否足够深入；
- 是否有趣；
- 是否避免 AI 味；
- 是否符合个人偏好。

因此它实际上是一个 **多维目标** ：

$$
Q = f( \text{Accuracy}, \text{Clarity}, \text{Depth}, \text{Style}, \text{Audience Fit}, \ldots )
$$

但这些指标很难被一个简单的程序精确测量。

---

### 11. “好”如果无法验证，Agent 就很难持续优化

这也是为什么某些任务非常适合自动化，而另一些任务很难。

#### 容易自动迭代

```text
编译是否成功？
测试是否通过？
输出是否匹配？
格式是否正确？
```

这些都有比较明确的答案。

#### 难以自动迭代

```text
这个网页好不好？
这个简历有没有 AI 味？
这个教学方式是否自然？
这个设计是否有品位？
```

这些问题往往没有唯一标准答案。

因此：

$$
\text{明确 Verifier} \Rightarrow \text{高效自动迭代}
$$

而：

$$
\text{模糊评价标准} \Rightarrow \text{Agent 优化困难}
$$

---

## 12. Verifier 决定了 Agent 能走多远

如果模型已经足够强，那么瓶颈可能逐渐从：

> **“模型会不会做？”**

转向：

> **“我能不能告诉它什么叫做对？”**

这就是本段最核心的变化。

可以概括成：

$$
\boxed{ \text{强模型} + \text{明确 Spec} + \text{强 Verifier} \rightarrow \text{极强 Agent} }
$$

其中：

- **Spec** 决定“目标是什么”；
- **Verifier** 决定“怎样算完成”；
- **模型** 负责寻找实现路径。

---

## 13. 当 Verifier 越强，Agent 越接近“自动搜索器”

最终可以形成这样的闭环：

```text
明确 Spec
    ↓
生成候选解
    ↓
Verifier
    ↓
通过？ ───── 是 ───→ 完成
  │
  否
  ↓
分析失败原因
  ↓
修改 / 重规划
  ↓
再次验证
  ↓
……
```

因此，一个真正适合 Agent 的任务，不只是：

> **“我要什么。”**

还应该尽量明确：

> **“你怎样证明自己已经做到了。”**

---

## 14. 本段最重要的原则

#### **原则一：Spec 决定目标，Verifier 决定成功**

$$
\text{Spec} \rightarrow \text{定义目标}
$$

$$
\text{Verifier} \rightarrow \text{定义成功}
$$

#### **原则二：尽可能把“主观判断”转化为“可检查条件”**

例如不要只说：

> “代码写得好一点。”

而应该尽量转换成：

- 编译必须通过；
- 单元测试必须通过；
- 性能不超过某阈值；
- 接口必须符合指定设计；
- 静态检查不能出现特定问题。

#### **原则三：强模型 + 强反馈，比单纯扩大 Prompt 更重要**

一个非常重要的关系是：

$$
\boxed{ \text{明确目标} + \text{可验证反馈} > \text{单纯增加 Prompt 长度} }
$$

因为模型本身已经具备非常强的通用能力。

真正限制 Agent 的，经常不是：

> **“它不会做。”**

而是：

> **“我们没有告诉它什么叫做做对了。”**

#### **核心结论**

> **生成式软件工程的关键，不只是把 Intent 说清楚，更要把 Intent 转化成模型能够持续优化、机器能够检查的 Specification + Verifier。**

## Verifier 的边界、AI 协作与 Attention 对指令的选择性关注

### 1. 不是所有任务都能建立可靠的 Verifier

前面提到，强 **Verifier（验证器）** 能让 Agent 持续迭代，但并不是所有任务都存在一个清晰的 Verifier。

例如：

- 数学题：通常可以判断答案对错；
- 编程：可以编译、运行测试；
- 代码格式：可以静态检查；
- 音频 / TTS 效果：可能涉及自然度、情感、节奏等复杂评价；
- 教学效果：很难用一个明确指标定义“好不好”。

因此：

$$
\text{任务越客观} \Rightarrow \text{Verifier 越容易建立}
$$

而：

$$
\text{任务越主观} \Rightarrow \text{Verifier 越难建立}
$$

---

## 2. 教学是典型的“难以验证”任务

例如一个老师讲课时，并不只是把事实讲出来。

一堂好的课通常还需要考虑：

- **节奏**
- **情绪起伏**
- **信息密度**
- **学生当前的理解程度**
- **什么时候应该重复**
- **什么时候应该制造惊喜**
- **什么时候应该停下来让学生思考**

例如：

```text
先讲已知知识
      ↓
学生开始觉得“这些我知道”
      ↓
突然加入一个意料之外的实验
      ↓
产生 Surprise
      ↓
重新集中注意力
      ↓
继续讲解
```

这种设计不是简单的“信息传递”，而是一种 **课堂体验设计** 。

---

### 3. “Surprise” 是课堂设计的重要手段

课程中的例子是：

先解释 Agent Context 的基本组成。

这些内容对于学生来说可能已经比较熟悉，因此单纯继续讲理论容易让注意力下降。

于是突然让 Agent：

> **自己检查当前的 Context。**

这样就产生一个效果：

> **意料之外，但又符合前面理论推导。**

也就是：

$$
\text{Unexpected} + \text{Reasonable} \rightarrow \text{Surprise}
$$

这种设计可以提升课堂的参与感。

---

## 4. 人类教师和 AI 的差异：体验本身难以形式化

教师不仅仅是在传递知识，还需要理解：

> **“坐在下面的人现在是什么感觉？”**

例如教师可以根据现场反馈判断：

- 学生是不是已经听懂了；
- 是否开始走神；
- 哪个地方需要停下来；
- 哪个地方可以加快；
- 什么地方适合开一个玩笑；
- 什么地方需要制造一个惊喜。

这依赖于大量的：

**Human Experience（人类经验） + Empathy（共情） + Situational Judgment（情境判断）。**

而这些东西很难转化成一个简单的函数：

$$
\text{Lecture Quality} = f(\ldots)
$$

因为“好课”的标准本身就是多维且高度情境化的。

---

## 5. 没有明确 Verifier 的任务，更适合人机协作

因此，目前可以形成一个非常实用的分工：

#### AI 更擅长

具有明确反馈的问题，例如：

- 数学；
- 编程；
- 自动化测试；
- 结构化分析；
- 可以不断执行和验证的工程任务。

#### 人类更重要

缺乏明确客观标准的问题，例如：

- 审美；
- 教学体验；
- 情绪控制；
- 叙事节奏；
- 价值判断；
- 复杂的主观评价。

因此，最理想的方式不是：

> **“AI 替代人。”**

而是：

$$
\boxed{ \text{AI 负责高强度执行与搜索} + \text{人类负责目标、品位与判断} }
$$

---

## 6. AI 可以成为能力放大器

当模型在某类任务上已经远超大多数人的执行能力时，人类更应该把它当成：

**Capability Amplifier（能力放大器）** 。

也就是说：

$$
\text{Human Capability} \times \text{AI Capability} \rightarrow \text{更强的整体能力}
$$

例如一个人已经知道：

- 想解决什么问题；
- 技术方案有哪些；
- 什么结果才是好的；
- 如何判断结果是否符合要求；

那么 AI 就可以承担大量：

- 搜索；
- 编码；
- 实验；
- 修改；
- 重复验证；
- 信息整理。

人类则主要负责：

**方向和判断。**

---

## Attention：模型如何在巨大 Context 中找到有用的信息

### 7. Self-Attention 是模型处理 Context 的关键机制

前面说模型可以看到非常长的 Context，但还有一个问题：

> **当 Context 中有成千上万甚至更多 Token 时，模型怎么知道现在应该关注哪一部分？**

这里就涉及 **Self-Attention（自注意力机制）** 。

在 Transformer 中，每生成一个 Token，模型会根据当前任务，对过去的不同 Token 分配不同程度的关注。

可以粗略理解为：

$$
\text{Context} \rightarrow \text{不同 Token 的相关性计算} \rightarrow \text{当前最重要的信息} \rightarrow \text{预测下一个 Token}
$$

---

### 8. 同一个 Context 中，不同信息的重要程度并不相同

例如 Context 中同时存在：

```text
System Prompt：
“请使用中文回答。”

AGENTS.md：
项目编码规范……

User：
“帮我实现一个极品飞车。”

当前正在写：
C++ 代码……
```

当 Agent 正在写代码时：

**“帮我实现一个极品飞车”** 和当前已经生成的代码，会成为非常重要的信息。

而：

**“请使用中文回答”**

虽然仍然存在于 Context 中，但对当前这个具体 Token 的生成来说，相关性可能较低。

所以不能简单地认为：

> **所有 Context 内容在每一步都具有相同权重。**

更准确地说：

> **模型会根据当前生成任务，动态选择哪些历史信息更值得关注。**

---

## 9. Attention 可以把高维 Context 中有用的结构“捞出来”

整个 Context 从宏观上看非常复杂。

可以把它理解成：

$$
\text{大量文本} \rightarrow \text{高维信息表示}
$$

但其中通常隐藏着某些与当前任务高度相关的结构。

例如在“实现赛车游戏”的这个时刻，模型需要重点关注：

- 游戏需求；
- 当前代码；
- API；
- 相关技术约束。

而不是：

- 很久以前已经完成的闲聊；
- 与当前实现无关的说明。

**Attention** 的作用之一，就是从大量上下文表示中提取与当前预测最相关的信息。

可以形象地理解为：

> **Context 是一个巨大的信息空间，而 Attention 在里面不断寻找当前最值得关注的部分。**

---

## 10. Chain of Thought 的每一个 Token 都会重新选择“该看什么”

这也解释了为什么 **Chain of Thought** 可以逐步推进。

每生成一个新的推理 Token，模型都会再次根据整个可见 Context 判断：

> **“为了生成下一个 Token，我现在最应该关注前面的什么？”**

于是：

$$
\text{第 }t\text{ 个 Token} \rightarrow \text{重新计算注意力} \rightarrow \text{生成第 }t+1\text{ 个 Token}
$$

然后不断重复。

所以模型并不是：

> “读完 Context 一遍以后就固定理解了。”

而是：

> **每一步生成时，都在重新决定哪些信息对下一步最重要。**

---

## 11. 人类思考也存在类似的“注意力切换”

课程用数学题举了一个直观类比。

例如你在做一个复杂的数学题：

```text
看到问题
   ↓
集中注意力分析公式
   ↓
化简表达式
   ↓
得到中间结果
   ↓
重新审视整个问题
   ↓
进入下一步
```

在化简公式的时候，你的大部分注意力都会集中在：

**当前公式和相关条件。**

而当这一阶段完成后，你可能会暂时“喘口气”，重新看整个问题，然后进入下一阶段。

所以可以粗略类比为：

$$
\text{人类注意力切换} \approx \text{模型 Attention 动态选择}
$$

虽然两者在机制上完全不同，但这个类比有助于理解：

> **复杂思考并不是始终平均地关注所有信息，而是在不同阶段选择当前最重要的部分。**

---

## 12. 当前任务会改变 Context 中“什么最重要”

因此，同一份 Context 在不同时间点，Attention 的关注重点可能完全不同。

例如：

#### 写代码阶段

```text
需求
+
当前代码
+
API
+
错误信息
```

#### Debug 阶段

```text
错误日志
+
调用栈
+
相关代码
+
最近修改
```

#### 总结阶段

```text
任务目标
+
最终实现
+
关键结果
+
验证结果
```

**Context 没变，不代表信息的重要性没变。**

这也是为什么 Prompt / Context 的组织方式非常重要：

> **好的上下文不仅要“包含信息”，还要让模型容易在当前任务中找到相关信息。**

---

## 13. 本段核心逻辑

```text
复杂任务
   ↓
不是所有事情都能建立 Verifier
   ↓
客观任务 → AI 更适合持续优化
主观任务 → 需要人类判断
   ↓
人类定义目标和品位
   +
AI 承担大量执行
   ↓
AI 成为能力放大器

大量 Context
   ↓
Self-Attention
   ↓
动态选择当前最相关的信息
   ↓
生成下一个 Token
   ↓
重新选择
   ↓
……
```

最重要的两个结论是：

$$
\boxed{ \text{Verifier 决定 AI 能否高效自我迭代} }
$$

以及：

$$
\boxed{ \text{Attention 决定模型如何在庞大 Context 中找到当前有用的信息} }
$$

因此， **Context Engineering 的目标不仅是“把信息放进去”，还包括让正确的信息在正确的任务阶段得到足够的关注。**

## Attention 动态分配、指令遵循与 Verifier 驱动的模型行为

### 1. 模型会随着任务阶段变化而改变注意力重点

在一个复杂任务中，模型并不是从头到尾都以同样的方式关注 Context。

例如：

```text
阶段 1：编写代码
    ↓
关注当前代码、API、用户需求

阶段 2：代码完成
    ↓
关注还有哪些要求没有完成

阶段 3：总结 / 收尾
    ↓
关注用户的语言要求、输出格式、遗漏任务
```

因此，同一个 Context 在不同阶段，模型的 **Attention（注意力）** 分布会发生变化。

可以理解为：

$$
\text{Task Stage} \rightarrow \text{Attention Pattern 改变} \rightarrow \text{当前最相关的信息被重新突出}
$$

---

### 2. 指令遵循的关键：在正确的时候注意到正确的信息

模型训练最终希望形成一种行为模式：

> **在当前任务阶段，能够关注到真正重要的指令。**

例如最开始用户要求：

> 用中文回答。

随后又要求：

> 实现一个游戏。

模型正在写代码时，主要关注：

- 游戏需求；
- 当前代码；
- API；
- 技术约束。

而当代码完成、准备输出总结时：

- **“用中文回答”**
- **“还要完成另外一个任务”**

这些要求的重要性又会上升。

因此，完整的指令遵循并不是：

$$
\text{永远平均关注所有要求}
$$

而是：

$$
\boxed{ \text{不同阶段} \rightarrow \text{关注不同要求} \rightarrow \text{最终逐步满足整个 Context 中的约束} }
$$

---

## 3. 模型可以发现“刚才自己做错了”

这带来一个非常重要的能力：

**模型当前生成的内容，本身也会成为后续 Context 的一部分。**

例如：

```text
过去的要求：
“必须满足 A”

当前生成：
“我刚才生成了 B”

下一阶段重新推理：
Attention 同时看到 A 和 B

↓
发现：
B 不满足 A

↓
修正 B
```

因此模型可以形成：

$$
\text{生成} \rightarrow \text{看到自己的结果} \rightarrow \text{与历史要求比较} \rightarrow \text{发现错误} \rightarrow \text{修正}
$$

这正是前面复杂藏头诗等任务中反复出现的行为。

---

### 4. “停下来喘口气”对应重新检查任务约束

在连续生成过程中，模型可能暂时高度关注当前局部问题。

例如正在写某一句诗时，它可能主要考虑：

> **下一句怎样押韵。**

此时另一个较早的约束可能暂时没有成为最主要的注意对象。

但当一个阶段完成后，模型继续向后生成，就可能重新看到：

- 当前已经生成的结果；
- 更早的任务约束；
- 其他尚未满足的条件。

于是产生类似：

> “等等，我刚才那个结果不符合要求。”

然后重新修改。

因此可以把复杂生成理解成：

$$
\text{局部求解} \rightarrow \text{重新审视全局约束} \rightarrow \text{发现冲突} \rightarrow \text{局部修正}
$$

这是一种非常重要的 **局部搜索 + 全局约束检查** 模式。

---

## 5. 超长 Context 仍然可能保持一定程度的指令遵循

即使 Context 非常长，模型仍然可以在一定程度上维持早期要求。

这也是现代长上下文模型令人惊讶的地方：

> **上下文长度增长以后，并没有简单地变成“后面的信息全部取代前面的信息”。**

模型仍然可以通过 Attention 从历史信息中找到相关内容。

但这并不意味着：

> **Context 越长越好。**

实际上，更多的指令也意味着更多的信息在竞争 Attention。

---

## 6. Context 是一种有限的“注意力资源”

可以把模型的 Attention 理解为一种有限资源。

当 Context 中只有少量要求时：

```text
要求 A
要求 B
要求 C
```

模型比较容易集中注意力。

但如果增加大量要求：

```text
要求 A
要求 B
要求 C
要求 D
要求 E
……
要求 Z
```

它就需要在更多信息之间分配注意力。

因此：

$$
\boxed{ \text{更多 Context} \not\Rightarrow \text{更容易完成任务} }
$$

甚至可能出现：

$$
\text{Context 增长} \rightarrow \text{Attention 竞争加剧} \rightarrow \text{某些约束被忽视}
$$

所以 **Context Engineering** 的目标不是无脑增加信息，而是让重要信息在需要的时候更容易被模型关注。

---

## 从早期 Prompt Engineering 到现代模型

### 7. 早期模型为什么需要非常长的“角色 Prompt”

早期模型的 **Instruction Following** 能力相对较弱。

因此当时网上大量存在这种 Prompt：

```text
You are an expert...
You are a senior engineer...
You are a professional...
You have 20 years of experience...
...
```

这类 Prompt 往往非常长。

其一个实际作用可以理解为：

> **通过重复和强化某种角色描述，提高模型在生成时对这些信息的关注程度。**

也就是说，它在一定程度上是在“诱导”模型的 Attention：

$$
\text{反复强调角色} \rightarrow \text{角色相关 Token 更突出} \rightarrow \text{模型更倾向于表现出对应角色}
$$

因此早期所谓的 **Prompt Engineering Hack** ，很多时候实际上是在弥补模型指令遵循能力不足。

---

## 8. 现代模型逐渐不再需要这种“魔法咒语”

随着 **Post-training / Reinforcement Learning（后训练 / 强化学习）** 的发展，模型逐渐学会：

> **哪些信息是应该认真遵循的指令。**

因此现代模型通常不再需要：

- “你是一位世界顶级专家”；
- “你是全宇宙最优秀的程序员”；
- 大量重复角色设定；
- 各种格式复杂的 Prompt 魔法。

更有效的方式变成：

> **直接把真正重要的 Specification 和 Verifier 写清楚。**

也就是：

```text
不要：
“你是世界顶级专家，请认真认真认真……”

而是：
“必须满足 A、B、C。
验证标准是 D。”
```

核心变化是：

$$
\text{Prompt Hack} \rightarrow \text{明确 Specification} + \text{明确 Verifier}
$$

---

## 9. 强化学习让模型形成“必须完成 Verifier”的倾向

如果模型在训练过程中反复受到这样的反馈：

```text
满足指令 + 通过验证
    → Reward 高

违反指令 / 验证失败
    → Reward 低
```

那么模型就会逐渐学到：

> **看到 Verifier，就应该想办法让它通过。**

因此现在的模型更像一个非常执着的“做题家”。

可以抽象成：

$$
\text{Verifier} \rightarrow \text{约束} \rightarrow \text{模型持续优化}
$$

这也是为什么现代模型面对明确的任务要求时，往往会主动进行检查和修正。

---

## 前端案例：一个简单指令也会被严格执行

### 10. 明确的指令很容易成为模型持续关注的约束

例如前端任务中明确要求：

> **背景必须是白色，不要半透明效果。**

这其实是一个非常简单的 **Verifier-friendly Constraint（容易验证的约束）** 。

模型可以检查：

```text
Background
    ↓
White?
    ↓
Yes

Transparency?
    ↓
No
```

因此模型通常会很好地遵循它。

---

### 11. 甚至可以把验证机制进一步外置

如果 Prompt 规定：

> **每完成一个设计都必须截图，再使用视觉模型检查。**

那么 Agent 甚至可以形成：

```text
写代码
   ↓
运行
   ↓
截图
   ↓
视觉模型检查
   ↓
是否白色背景？
是否存在透明效果？
   ↓
失败 → 修改
   ↓
重新截图
   ↓
再次验证
```

这就是一个更加完整的 **Verifier Loop（验证循环）** 。

其核心仍然是：

$$
\text{Generate} \rightarrow \text{Verify} \rightarrow \text{Fix} \rightarrow \text{Verify} \rightarrow \cdots
$$

---

## 12. “白色背景，不要半透明”为什么值得注意

模型甚至可能在代码中留下类似：

```text
 // White background, no transparency.
```

这不是因为模型真的需要这个注释来让程序运行，而是一个很典型的现象：

**模型已经把自然语言约束映射成了实现层面的明确要求。**

即：

$$
\text{自然语言约束} \rightarrow \text{实现选择} \rightarrow \text{代码 / 结果}
$$

这说明现代模型在面对明确约束时，已经能够把高层要求持续带入具体实现。

---

## 13. 本段核心逻辑

```text
复杂 Context
    ↓
不同阶段需要不同信息
    ↓
Attention 动态选择重点
    ↓
模型生成当前结果
    ↓
当前结果也进入 Context
    ↓
重新关注历史要求
    ↓
发现不满足约束
    ↓
修正
    ↓
继续推进
```

而模型能力的发展趋势可以概括成：

$$
\boxed{ \text{早期：需要 Prompt Hack} \rightarrow \text{现代：理解明确 Spec} \rightarrow \text{进一步：主动关注 Verifier 并持续修正} }
$$

最终最重要的工程原则是：

> **不要依赖“你是专家”“请认真思考”之类的 Prompt 魔法；把真正重要的约束写清楚，并尽可能提供明确的 Verifier。模型越强，人类越应该负责定义“什么是对的”，而不是反复教模型“怎么像一个专家说话”。**

## 强化学习的局限、上下文污染与高质量资料的阅读方法

### 1. 强指令遵循并不等于真正理解“人类想要什么”

现代模型经过 **Reinforcement Learning（强化学习）** 和后训练之后，已经非常重视：

- 遵守指令；
- 满足 Specification；
- 通过 Verifier；
- 完成用户要求。

但这里仍然存在一个问题：

> **模型可能非常擅长“把题做对”，却不一定擅长理解“人为什么希望它这样做”。**

例如一个老师在课堂上除了传递正确知识，还要考虑：

- 学生是否听懂；
- 节奏是否舒服；
- 哪里应该停下来；
- 哪里需要惊喜；
- 什么样的表达更像“人说的话”。

这些属于 **Empathy（共情）** 和情境判断，当前后训练在这方面可能仍然相对不足。

因此有时会出现：

> **模型严格执行了要求，但表达方式“不像人说的话”。**

这可以理解为：

$$
\text{Instruction Following} \neq \text{Human Intent Understanding}
$$

---

## 2. “更听话”本身也会带来 Trade-off

模型越来越听话，并不意味着所有方面都同时变好。

例如为了避免模型输出不符合项目要求的内容，可以在 `AGENTS.md` 中加入：

```text
注释应该怎么写
代码应该怎么组织
命名应该遵循什么规则
……
```

也可以把这些规则写进某个 **Skill** 。

这样模型确实更容易遵循规范。

但是问题在于：

> **这些规则本身也会占用 Context。**

因此形成一个典型的 **Trade-off（权衡）** ：

$$
\text{更多规则} \Rightarrow \text{更强约束}
$$

但同时：

$$
\text{更多规则} \Rightarrow \text{更大的 Context} \Rightarrow \text{更多 Attention 竞争}
$$

所以不能简单地认为：

> **规则越多越好。**

---

### 3. Context Pollution：上下文污染

如果把越来越多规则、Skills、说明文档都加入上下文，就可能出现：

**Context Pollution（上下文污染）** 。

也就是说：

> **为了让 Agent 更可靠，我们不断向 Context 添加信息，结果反而让真正重要的信息更难被关注。**

因此存在一个非常实际的工程问题：

$$
\boxed{ \text{约束越多} \leftrightarrow \text{Context 越重} }
$$

好的 Context Engineering 必须同时解决：

**“该加什么”** 和 **“什么不该加”** 。

---

## 4. 网上现成的 Skill 并不是拿来即用

现在网上存在大量现成的 Agent Skills。

看起来很诱人：

> “既然别人已经写好了，我直接拿过来不就行了吗？”

实际使用时往往会经历：

```text
第一次使用
    ↓
明显改善
    ↓
第二次使用
    ↓
发现仍然不够好
    ↓
继续修改 Skill
    ↓
再加规则
    ↓
再修
    ↓
……
```

最后容易进入一种：

> **不断打补丁、不断加规则，却越来越不知道问题根源在哪里。**

也就是所谓的“泥潭”。

---

### 5. 进入“规则泥潭”后，应该回到底层模型机制

遇到这种情况，课程给出的建议不是继续无止境地堆规则，而是：

> **重新回到模型本身是怎么工作的。**

尤其重新考虑：

- **Next Token Prediction**
- **Self-Attention**
- Context 是如何组成的；
- 模型当前可能关注什么；
- 哪些信息可能抢占 Attention；
- 某条规则为什么没有生效。

然后进行一种：

**不严格的可解释性分析（Informal Interpretability）**

即尝试猜测：

> **“模型刚才这样做，是因为它注意到了什么？”**

例如：

```text
输入 Context
    ↓
模型产生行为 A
    ↓
观察行为
    ↓
推测它可能关注了 B
    ↓
修改 Prompt / Context
    ↓
再次观察
```

这并不是严格证明模型内部发生了什么，而是一种 **基于行为的工程推断** 。

---

## 论文阅读：为什么“直接丢给模型总结”存在问题

### 6. 一个看似合理的方法：把 PDF 直接交给 Agent

例如：

> “这是 `paper.pdf` ，帮我总结一下。”

这是非常自然的操作。

但根据前面关于 **Self-Attention** 的分析，它存在一个容易忽视的问题：

> **一篇写得越完整、逻辑越自洽的论文，反而越容易让模型完全接受作者自己的叙事。**

---

### 7. 论文是一条高度自洽的逻辑链

一篇已经经过多轮修改的论文通常会形成：

$$
A \rightarrow B \rightarrow C \rightarrow D \rightarrow E
$$

作者已经把：

- 问题；
- 假设；
- 方法；
- 实验；
- 结论；

组织成了完整的因果链。

因此模型读到它时，很容易产生：

> **“A 导致 B，B 导致 C，C 又支持 D，所以这个论证整体是成立的。”**

这会让模型非常自然地沿着作者的逻辑继续推理。

---

## 8. 这会产生“逻辑污染”：模型容易继承作者的立场

这里的核心并不是说论文一定存在错误，而是：

> **模型做摘要时，天然倾向于复述文档作者已经建立好的逻辑框架。**

于是：

$$
\text{论文作者的观点} \rightarrow \text{模型读取} \rightarrow \text{模型内化其逻辑结构} \rightarrow \text{总结作者的观点}
$$

最终你看到的“总结”往往并不是独立判断，而是：

> **作者观点的高质量压缩版。**

因此，“总结得非常准确”甚至可能意味着：

> **模型把作者的论证完整地接受下来了。**

---

## 9. 这不只是论文的问题

这个问题可以推广到几乎所有结构完整的资料：

- **论文**
- 教科书章节；
- 项目文档；
- 技术设计文档；
- 教程；
- 研究报告。

例如学习计算机系统基础中的 **Linking and Loading（链接与加载）** 。

如果直接把一章教材丢给模型：

> “帮我总结这一章。”

模型很容易沿着教材自己的知识组织方式进行压缩。

如果教材中存在某个：

- 隐含假设；
- 有争议的观点；
- 特定教学取舍；
- 不够完整的解释；

模型很可能也会一起继承。

因此：

$$
\text{Summary} \neq \text{Independent Understanding}
$$

它更接近：

$$
\text{Summary} \approx \text{Source Author's Structure + Model's Compression}
$$

---

## 10. 真正需要警惕的是“逻辑自洽带来的说服力”

Self-Attention 的角度下，一个逻辑高度连贯的文档具有一个特殊优势：

> **前面的内容不断为后面的内容提供上下文支持。**

于是形成：

$$
A \rightarrow B \rightarrow C \rightarrow D \rightarrow E
$$

每一步都能引用前一步。

模型看到这种结构后，会很容易沿着已有逻辑继续生成。

因此：

> **“逻辑写得很完整”会增强模型对该逻辑框架的吸收，而不自动意味着该逻辑本身正确。**

这正是阅读资料时需要特别注意的地方。

---

## 11. 更合理的阅读思路：区分“复述”与“审查”

如果目标只是：

> **“作者说了什么？”**

那么直接总结当然很有效。

但如果目标是：

> **“这个东西到底对不对？”**

那么仅仅总结是不够的。

应该进一步引入：

```text
原文
 ↓
总结作者观点
 ↓
提取关键假设
 ↓
拆解论证链
 ↓
寻找证据
 ↓
寻找反例 / 漏洞
 ↓
独立判断
```

也就是说，要把：

**“理解作者”**

和：

**“接受作者”**

分开。

---

## 12. 本段对 Context Engineering 的进一步启发

这一段其实把前面的几个主题连了起来：

#### **① Rule 越多，不一定越好**

因为：

$$
\text{更多规则} \rightarrow \text{更强约束} + \text{更多 Context Competition}
$$

#### **② Skill 不能无限堆叠**

遇到问题时，应该理解：

> **为什么现有 Context 没有效果？**

而不是继续不断追加规则。

#### **③ Attention 决定哪些信息最终影响行为**

模型并不是平均使用所有 Context，而是在不同阶段关注不同部分。

#### **④ 文档本身也会“塑造”模型的判断**

一份逻辑严密的文档会通过其上下文结构强烈影响模型后续推理。

因此：

$$
\text{输入什么} \rightarrow \text{模型更容易关注什么} \rightarrow \text{模型更容易得出什么}
$$

---

## 13. 本段最核心的工程原则

可以浓缩成三个问题：

#### **问题一：我为什么要加入这条规则？**

不是：

> “别人都这么写。”

而是：

> **“这条规则具体解决什么问题？”**

#### **问题二：这条规则带来了多少 Context 成本？**

需要考虑：

$$
\text{Benefit} \stackrel{?}{>} \text{Context Cost}
$$

#### **问题三：模型是在“理解”，还是在“复述”？**

尤其阅读论文、教材、设计文档时，要区分：

$$
\text{作者观点} \neq \text{客观事实}
$$

最终可以归纳为：

> **强模型并不意味着可以无脑增加上下文。好的 Context Engineering 是在“提供足够约束”和“避免注意力污染”之间寻找平衡；而阅读高质量资料时，还要警惕模型过于顺滑地继承原文的逻辑与观点。**

## 抵抗上下文污染：Grounding、立场对齐与个人知识边界

### 1. 直接让 AI 总结论文，得到的往往是“作者观点的复述”

如果把一篇论文直接交给 AI，并要求：

> “帮我总结这篇论文。”

那么最终结果通常会高度贴近论文原文的逻辑。

因为论文本身已经建立了完整的论证链：

$$
A \rightarrow B \rightarrow C \rightarrow D
$$

模型在阅读过程中会不断利用前面的内容理解后面的内容，于是很容易沿着作者已经建立好的逻辑继续生成。

因此：

$$
\text{AI Summary} \approx \text{作者观点的压缩版}
$$

这对于“了解作者说了什么”很有用，但对于：

> **“我应该如何评价这个工作？”**

就明显不够了。

---

## 2. AI 容易表现出“墙头草”特征

模型还有一个很明显的问题：

> **你说它好，它容易跟着你说好；你说它不好，它也容易跟着你说不好。**

例如：

```text
你：这篇论文很好
        ↓
AI：确实很好，它有很多贡献

你：我觉得它其实不怎么样
        ↓
AI：确实存在很多问题
```

于是会出现一种：

$$
\text{观点 A} \rightarrow \text{AI 支持 A}
$$

再变成：

$$
\text{观点 B} \rightarrow \text{AI 支持 B}
$$

的问题。

这意味着：

**AI 的“同意”并不等于独立判断。**

---

### 3. 不断追问 AI，可能陷入“细枝末节循环”

即使你明确要求：

> “不要盲目相信作者，认真评价研究贡献。”

AI 也可能不断提出一些边缘问题：

- 某个实验能不能再加一点；
- 某个测试是否可以再补；
- 某个实现细节是否还能优化；
- 某个结果是否可以进一步验证。

这些意见本身可能并非错误，但容易出现一种现象：

> **AI 在不重要的地方不断发力，却没有真正回答核心研究问题。**

原因之一是：

**这些细节比较容易识别和评论，而“这项工作究竟解决了什么重要问题”更难判断。**

因此需要把分析重新拉回到更高层次。

---

## 4. 需要用 Cross-validation 防止单一 AI 判断失真

对于真正重要的研究判断，不能完全依赖一次 AI 输出。

尤其是：

- 论文评价；
- 研究贡献判断；
- 项目技术选型；
- 复杂系统分析。

更可靠的方法是做 **Cross-validation（交叉验证）** ：

$$
\text{AI Analysis} + \text{Independent Evidence} \rightarrow \text{更可靠的判断}
$$

例如：

- 查原论文；
- 查相关工作；
- 看代码；
- 看实验；
- 使用不同模型；
- 自己验证关键结论。

核心原则是：

> **把模型输出当作证据，而不是直接当作事实。**

---

## 5. 抵抗 Context Pollution 的关键：让 AI 与“我”站到同一个立场

这里提出了一个非常重要的个人实践：

如果研究对象是一篇论文，不希望 AI 单纯站在论文作者的角度理解它。

真正希望的是：

> **AI 和自己对齐，然后站在自己的知识背景和问题意识上理解这篇论文。**

可以抽象成：

$$
\boxed{ \text{Paper} + \text{My Knowledge / Position} \rightarrow \text{Aligned Understanding} }
$$

而不是：

$$
\text{Paper} \rightarrow \text{AI 直接接受作者叙事}
$$

---

## 6. Grounding：先把 AI 拉回人类已有知识边界

实现这种对齐的一个核心方法是 **Grounding（知识锚定 / 基于已知事实建立共同基础）** 。

分析论文时，不要一上来问：

> “这篇论文有什么贡献？”

而可以先要求 AI：

#### 第一步：确定人类已经知道什么

> **在人类已有知识边界内，这个问题之前已经解决到了什么程度？**

也就是：

$$
\text{Human Knowledge} \rightarrow \text{Existing Solutions} \rightarrow \text{Current State of Art}
$$

#### 第二步：明确已有工作的边界

需要找到：

- 已经解决的问题；
- 已经存在的方法；
- 已知的局限；
- 当前技术水平。

#### 第三步：再看这篇论文新增了什么

最终：

$$
\text{本领域已有成果} \rightarrow \text{已有边界} \rightarrow \text{论文新增的 Increment}
$$

这样才能真正判断：

> **这篇论文究竟贡献了什么。**

---

## 7. “先建立共同事实，再讨论观点”

这种方法的核心不是要求 AI：

> “站在我这一边。”

而是：

> **先让我们双方建立一个尽可能客观的共同知识基础。**

即：

```text
已有知识
   ↓
相关工作
   ↓
已经解决的问题
   ↓
尚未解决的问题
   ↓
论文试图解决什么
   ↓
论文到底增加了什么
```

这一步相当于把 AI 从：

> **“作者的叙事框架”**

拉回到：

> **“人类已有知识 + 当前问题的真实边界”。**

这是抵抗上下文污染最重要的手段之一。

---

## 8. 对学生来说，还需要加入“我的知识边界”

对于研究生或学生，更复杂的问题在于：

> **AI 并不知道你已经学到了什么。**

例如学习“链接和加载”时：

如果 AI 假设你已经学过 ELF、ABI、动态链接器等内容，它可能直接从高级概念开始解释。

但如果实际上你只学过：

- C；
- 汇编；
- 编译；
- 基础操作系统；

那么解释方式就会完全不同。

因此，学生应该主动告诉 AI：

> **“我的知识边界在哪里？”**

---

## 9. 可以把个人知识状态维护成长期 Memory / `AGENTS.md`

一个很有实践价值的方法是维护一个类似个人知识数据库的东西。

例如：

```text
My Knowledge State

已经掌握：
- C
- 基础数据结构
- 操作系统基础

正在学习：
- 编译与链接
- 程序加载
- ELF

尚未学习：
- 高级动态链接机制
- 某些 ABI 细节
```

可以放在：

- **Memory**
- `AGENTS.md`
- 个人知识库；
- 其他持久化 Context。

这样 Agent 每次都可以基于你的真实知识水平进行工作。

---

## 10. 个性化 Context 的本质：让 AI 对齐“我的认知状态”

完整流程可以变成：

$$
\text{我的知识水平} \rightarrow \text{AI 获得 Context} \rightarrow \text{基于我的基础解释} \rightarrow \text{我继续追问}
$$

而不是：

$$
\text{AI 假设我的水平} \rightarrow \text{直接输出}
$$

这会显著减少两个常见问题：

#### **问题一：解释太简单**

你已经会了，但 AI 还在重复基础知识。

#### **问题二：解释跨度太大**

AI 直接跳到你尚未学习的概念。

因此：

> **个人 Context 实际上是在告诉 AI：“你应该从哪里开始教我。”**

---

## 11. 让 AI 对知识体系进行“Refresh”

建立个人知识边界之后，还可以要求 AI：

> **基于我已经学过的知识，把当前问题重新 Refresh（复习 / 重建）一遍。**

例如：

```text
我的已有知识
      ↓
当前要学习的主题
      ↓
连接两者之间的知识缺口
      ↓
重新构建解释
      ↓
从我能理解的位置继续
```

这比单纯：

> “解释一下这个概念。”

更加个性化。

---

## 12. Grounding 不只是论文阅读，也适用于学习和项目分析

这个方法可以广泛应用于：

- **论文阅读**
- 教科书学习；
- 开源项目分析；
- 技术方案评审；
- 软件工程设计；
- 新领域入门。

统一的逻辑都是：

$$
\boxed{ \text{已有知识} \rightarrow \text{已知解决方案} \rightarrow \text{问题边界} \rightarrow \text{新的工作} }
$$

这样可以避免直接被某一个文档自己的叙事框架带走。

---

## 13. 本段最重要的认识：Context 不只是“让 AI 知道更多”

前面一直在强调增加 Context，但这里进一步发现：

> **Context 还决定了 AI 是站在哪个视角上理解问题。**

同一篇论文：

#### 直接输入

$$
\text{Paper} \rightarrow \text{AI Summary}
$$

结果容易变成：

> **作者怎么说，AI 就怎么总结。**

#### 加入 Grounding

$$
\text{Existing Knowledge} + \text{My Knowledge State} + \text{Paper}
$$

结果更容易变成：

> **基于已有知识，判断论文究竟解决了什么新的问题。**

因此：

$$
\boxed{ \text{Context Engineering} = \text{信息管理} + \text{视角管理} + \text{知识边界管理} }
$$

---

## 14. 本段核心工作流

```text
                 分析一个对象
                     │
                     ↓
            不直接相信原文叙事
                     │
                     ↓
          建立人类已有知识边界
                     │
                     ↓
              梳理相关工作
                     │
                     ↓
           确定已解决 / 未解决问题
                     │
                     ↓
             明确当前工作的增量
                     │
                     ↓
        再评价它的真正贡献与价值
```

而对于个人学习：

```text
维护自己的知识状态
        ↓
告诉 AI “我已经知道什么”
        ↓
告诉 AI “我还不知道什么”
        ↓
让 AI 基于我的知识边界解释
        ↓
持续更新个人 Context
```

最终可以概括为：

> **抵抗 AI 上下文污染的关键，不是简单减少上下文，而是建立正确的 Grounding：先对齐人类已有知识、相关工作的边界以及自己的知识水平，再让 AI 理解新的对象。这样 AI 才更可能成为你的分析助手，而不是某篇文档作者观点的复述器。**

## Grounding 后的单步推理、知识增量与逻辑链验证

### 1. 从已有知识出发，先建立 AI 与自己的共同起点

理解一个新概念时，不应该直接从陌生对象开始，而应该先回到自己已经掌握的知识。

例如学习 **Linking（链接）** 时，可以先从一个非常熟悉的事实出发：

```text
C++ 源代码
    ↓
编译
    ↓
可执行文件
    ↓
.exe
```

然后提出：

> **“既然源代码已经可以变成 `.exe` ，为什么还需要单独讨论 Linking？”**

这就把新问题放在已有知识体系上。

核心过程是：

$$
\text{已有知识} \rightarrow \text{找到知识缺口} \rightarrow \text{提出下一步问题}
$$

这种方式可以帮助 AI 和用户建立一个 **共同的知识起点** 。

---

### 2. Context Engineering 的目标之一，是让 AI 与用户“对齐”

例如阅读软件可视化相关论文时，与其直接问：

> “这篇论文解决了什么问题？”

不如先明确：

- 目前这个领域已经知道什么；
- 已有方法为什么存在；
- 当前方法有哪些现实痛点；
- 这些方法为什么还不能很好地实际使用；
- 论文究竟往前推进了一步什么。

这样 AI 就不会只是：

> **站在作者的立场复述论文。**

而是逐渐和用户建立：

$$
\text{共同知识基础} \rightarrow \text{共同问题定义} \rightarrow \text{共同判断标准}
$$

这就是前面所说的 **Grounding（知识锚定）** 。

---

## 3. Grounding 能显著提高 AI 与人的协作对齐程度

不同模型在长文档理解上的能力不同。

能力较强的模型能够自行整理大量相关知识，因此直接阅读论文也可能已经做得不错。

但即使如此，加入合适的 **Context Engineering** 仍然能够进一步提高协作质量。

核心差异是：

#### 没有 Grounding

$$
\text{Paper} \rightarrow \text{AI 自己理解} \rightarrow \text{AI 自己得出结论}
$$

#### 有 Grounding

$$
\text{我的知识} + \text{人类已有知识} + \text{Paper} \rightarrow \text{共同理解} \rightarrow \text{下一步推理}
$$

于是 AI 不再只是“自己说自己的”，而是更容易：

> **站在和用户共同建立的知识基础上继续往下推。**

---

## 4. 最适合 AI 的任务，是“向前推一步”

建立好 Grounding 以后，不需要一次要求 AI 解决整个问题。

更好的方式是：

> **让 AI 只做一步推理。**

也就是：

$$
I_0 \rightarrow I_1 \rightarrow I_2 \rightarrow I_3 \rightarrow \cdots
$$

其中：

- $I_0$：已知事实；
- $I_1$：下一步合理推论；
- $I_2$：基于前一步继续推导。

这非常符合模型的基本工作方式：

$$
\text{Context} \rightarrow \text{Next Token} \rightarrow \text{新 Context} \rightarrow \text{下一步}
$$

因此：

> **“从已有事实往前推一步”恰好是现代推理模型最擅长的事情之一。**

---

## 5. 为什么“一步推理”特别重要：它容易验证

推理最重要的问题不是：

> “模型能不能想得很复杂？”

而是：

> **“这一步推得对不对？”**

如果可以判断：

$$
I_n \rightarrow I_{n+1}
$$

是否合理，那么就可以建立反馈。

这与编程中的：

$$
\text{Code} \rightarrow \text{Test} \rightarrow \text{PASS / FAIL}
$$

类似。

虽然论文分析中的 Verifier 往往没有编程测试那么严格，但仍然可以使用：

- 已有知识；
- 相关工作；
- 逻辑一致性；
- 实验证据；

来判断这一步推理是否合理。

因此：

$$
\boxed{ \text{Good Reasoning} = \text{基于事实} + \text{向前推一步} + \text{检查合理性} }
$$

---

## 6. AI 的“批评能力”建立在已有知识和逻辑链上

例如让 AI 评价一篇已经发表的论文。

真正有价值的问题不是：

> “实验还能不能多做几个？”

而是：

> **“这个工作从已有知识出发，逻辑上是否真正成立？”**

如果已经知道：

$$
A \rightarrow B
$$

论文声称：

$$
B \rightarrow C
$$

那么就应该检查：

> **A → B → C 这条链是否真的成立？**

如果某一步逻辑断开，那么即使：

- 实验做得很漂亮；
- 代码能运行；
- 指标有所提升；

整个研究故事仍然可能不成立。

---

## 7. 人类审稿与 AI 审稿的一个重要差异

一篇论文可能已经被正式接受，意味着人类审稿人认为它：

- 有一定新颖性；
- 逻辑基本成立；
- 对人类知识产生了有效增量。

但这不代表论文中的每个实验都已经做到极致。

课程中的审稿标准更倾向于：

> **优先检查研究逻辑是否成立，而不是因为实验还可以多做一些就拒稿。**

也就是说，更重要的是：

$$
\text{新问题} + \text{有效方法} + \text{合理结论}
$$

而不是：

$$
\text{实验数量尽可能多}
$$

---

## 8. 真正严重的问题：逻辑链条断裂

例如某篇论文的结构是：

```text
整体问题 A
   ↓
A1 + A2
   ↓
A2 是目前研究不足的部分
   ↓
提出 A2'
   ↓
A2' 的性能提升
```

乍看之下，这是非常标准的研究路线。

问题在于：

> **A2 可能只占整个 A 的极小部分。**

假设：

$$
A_1 \approx 99\%
$$

而：

$$
A_2 \approx 1\%
$$

论文可能证明：

$$
A_2' > A_2
$$

甚至实验完全正确。

但是整个论文想表达的：

> **“我们显著改善了问题 A。”**

可能就并不成立。

---

## 9. 局部优化正确，不代表整体目标成立

这是一个非常重要的研究判断原则：

$$
\boxed{ \text{局部改进} \neq \text{整体问题被有效解决} }
$$

例如总体性能：

$$
P = P_1 + P_2
$$

其中：

$$
P_1 = 99\%, \qquad P_2 = 1\%
$$

如果论文把 $P_2$ 优化了很多，即：

$$
P_2 \rightarrow P_2'
$$

但 $P_1$ 几乎没有变化，那么整体效果：

$$
P' = P_1 + P_2'
$$

可能仍然非常有限。

因此不能因为：

> **“A2 确实被优化了。”**

就进一步推出：

> **“整个 A 问题因此得到了重要改善。”**

中间缺少一层关键论证。

---

## 10. 研究贡献必须和问题的重要性建立联系

一个合理的研究故事应该是：

$$
\text{重要问题} \rightarrow \text{关键瓶颈} \rightarrow \text{有效方法} \rightarrow \text{整体收益}
$$

如果变成：

$$
\text{重要问题} \rightarrow \text{找到很小的子问题} \rightarrow \text{把子问题优化得很好}
$$

那么还需要回答：

> **这个子问题对整体问题到底有多重要？**

否则就容易出现：

**局部优化很正确，但研究贡献不成立。**

---

## 11. 这也是“站在人类知识边界上”评审的意义

如果站在论文作者的视角，可能会觉得：

> “我确实提出了一个新方法，而且实验也证明它有效。”

但站在人类已有知识的角度，更重要的问题是：

- 以前已经知道什么？
- 这个问题到底还剩多少没有解决？
- 新方法解决的是核心瓶颈还是边缘问题？
- 这个改进能改变整体结论吗？
- 这项工作给人类增加了什么新的知识？

因此研究评价可以进一步抽象成：

$$
\boxed{ \text{Contribution} = \text{New Knowledge} + \text{Problem Relevance} + \text{Logical Validity} }
$$

---

## 12. Context Engineering 的最终目标：让 AI 沿着你的知识边界推理

综合这一段，可以形成一个完整工作流：

```text
我的已有知识
      ↓
建立共同知识基础
      ↓
明确已有工作
      ↓
找到问题缺口
      ↓
明确论文声称解决什么
      ↓
只向前推一步
      ↓
检查这一步是否合理
      ↓
继续下一步
      ↓
最终评价整体贡献
```

这个过程与直接：

> “给我总结一下这篇论文。”

有本质区别。

前者是：

> **让 AI 和你站在同一个知识起点，一步一步共同推理。**

后者则更容易变成：

> **让 AI 独立复述作者已经写好的逻辑。**

---

## 13. 本段核心结论

#### **① 先 Grounding，再 Reasoning**

$$
\text{Grounding} \rightarrow \text{Reasoning}
$$

没有共同知识基础，后面的推理很容易偏离用户真正想解决的问题。

#### **② 一次只推进一步**

$$
I_n \rightarrow I_{n+1}
$$

每一步都尽可能检查，而不是要求模型直接跳到最终结论。

#### **③ Verifier 是推理质量的关键**

即使没有严格程序测试，也应该尽可能利用：

- 已有知识；
- 相关工作；
- 实验证据；
- 逻辑一致性；

来验证每一步。

#### **④ 评价研究时优先检查“逻辑链”**

不能因为：

> **局部实验正确**

就推出：

> **整体研究贡献成立。**

必须确认：

$$
\boxed{ \text{Problem} \rightarrow \text{Method} \rightarrow \text{Result} \rightarrow \text{Contribution} }
$$

这条链条完整且合理。

#### **最核心的一句话**

> **高质量的 AI 协作不是让模型直接给出一个漂亮的结论，而是先与 AI 对齐知识和问题边界，再让它基于已知事实一步一步向前推，并持续检查每一步是否真的成立。**

## 研究贡献、AI Slop 与学术知识体系的变化

### 1. 评审不能只看局部优化是否成立

前面的例子中，论文针对整体问题 $A$，将其拆分成：

$$
A = A_1 + A_2
$$

假设：

$$
A_1 \approx 99\%, \qquad A_2 \approx 1\%
$$

作者在 $A_2$ 上提出了改进 $A_2'$，并且证明：

$$
A_2' > A_2
$$

那么至少可以说明：

> **作者确实把 $A_2$ 做得更好了。**

但真正的问题是：

> **为什么要优化 $A_2$，而不是整体问题中占绝大部分的 $A_1$？**

如果 $A_2$ 对整个系统的影响只有约 $1%$，那么即使把它优化得非常漂亮，对整体效果的贡献仍然可能非常有限。

因此：

$$
\boxed{ \text{局部改进成立} \neq \text{整体研究价值成立} }
$$

---

### 2. 需要区分“技术正确”和“研究重要”

论文可能完全不存在技术错误：

- 方法确实有效；
- 实验确实正确；
- 数据确实支持结论；
- 代码也确实可以复现。

但仍然可以追问：

> **这个结果为什么值得成为一篇独立论文？**

也就是从：

$$
\text{Is it correct?}
$$

进一步追问：

$$
\text{Is it important?}
$$

再进一步：

$$
\text{Does it contribute meaningful new knowledge?}
$$

因此研究评价至少包含三个不同层次：

$$
\boxed{ \text{Correctness} \rightarrow \text{Significance} \rightarrow \text{Knowledge Contribution} }
$$

---

## 3. 学生论文中很容易出现“局部问题被放大”的情况

如果作者是学生，研究路线可能来源于导师已经确定的大方向 $A$。

导师或课题组长期研究 $A$，学生被安排研究其中的 $A_2$，或者自行选择了 $A_2$。

于是可能出现：

```text
导师长期研究 A
      ↓
学生负责 A2
      ↓
发现可以把 A1 中的一些技术搬到 A2
      ↓
A2 得到一定改善
      ↓
形成一篇论文
```

这在工程和研究上并不一定是错的。

但需要进一步追问：

> **这个局部增量对于整个 A 究竟意味着什么？**

如果只是：

> “我把已有技术 XYZ 从 A1 搬到了 A2，并且 A2 稍微好了些。”

那么真正的中心问题依然存在：

> **为什么这个增量值得单独发表和阅读？**

---

## 4. Review 的中心问题应该是“为什么值得做”

因此，比“实验还能不能再多做一点”更重要的问题是：

> **为什么这个问题值得研究？**

也就是说，审稿时应该建立这样一条逻辑：

$$
\text{重要问题} \rightarrow \text{关键缺口} \rightarrow \text{新方法} \rightarrow \text{有意义的收益}
$$

而不是：

$$
\text{存在一个小问题} \rightarrow \text{我们解决了它} \rightarrow \text{所以值得发表}
$$

后者缺少了一个关键环节：

**这个问题和整体研究领域的重要性是什么？**

---

## 5. AI Slop 可能改变学术发表与评审体系

课程进一步提出了一个非常激进的判断：

> **随着 AI 大量参与论文写作和论文评审，传统学术发表体系可能面临严重冲击。**

这里说的 **AI Slop** 可以理解为：

> **大量由 AI 快速生成、形式上完整，但实际价值有限、彼此高度同质化的内容。**

问题可能形成一个闭环：

```text
AI 写论文
    ↓
大量论文产生
    ↓
AI 审论文
    ↓
AI 总结论文
    ↓
人越来越少直接阅读
    ↓
论文数量继续增加
    ↓
进一步依赖 AI
```

最终可能出现：

$$
\boxed{ \text{AI 生成} \rightarrow \text{AI 评审} \rightarrow \text{AI 阅读} \rightarrow \text{AI 生成} }
$$

形成一个高度自动化、但缺乏真正人类判断的循环。

---

## 6. Context Pollution 会影响 AI 审稿

前面讨论论文阅读时已经指出：

> **论文自身的逻辑结构会成为非常强的 Context。**

因此，如果让 AI 直接读论文并评价，它很容易沿着作者的故事走。

例如：

```text
作者：
A 很重要
 ↓
A1 + A2
 ↓
A2 尚未解决
 ↓
提出 A2'
 ↓
实验成功
```

AI 很容易得到：

> “这个方法有效，实验充分，因此论文贡献成立。”

但真正的问题可能是：

> **“A2 本身只占整体问题的 1%，为什么研究它能够构成重要贡献？”**

这一步需要从作者的叙事中跳出来，重新放回整个知识体系中判断。

---

## 7. AI 审稿很容易验证“逻辑正确”，却忽略“是否值得阅读”

模型可能很擅长检查：

- Claim 是否被实验支持；
- 方法是否描述清楚；
- 实验是否完整；
- 逻辑有没有明显漏洞；
- 结论是否和结果一致。

但这并不自动等于：

> **这是一篇值得研究者花一个小时阅读的论文。**

也就是说：

$$
\text{Paper is Valid} \neq \text{Paper is Valuable}
$$

甚至可以进一步区分：

$$
\text{Validity} \neq \text{Significance} \neq \text{Reader Value}
$$

---

## 8. “值得发表”和“值得大家阅读”并不是完全相同的问题

课程提出了一个很值得注意的区分。

假设一篇论文：

- 技术上没有错误；
- 实验也成立；
- 方法确实带来增量。

那么它可能 **可以发表** 。

但进一步的问题是：

> **是不是值得大量研究人员投入时间阅读？**

例如一个研究生看到：

> “某顶级会议发表了一篇新论文。”

于是决定投入一个小时认真阅读。

结果发现：

> **论文只是对整体问题中很小的一部分做了一次边缘优化。**

那么这一个小时的阅读时间可能产生很低的知识收益。

因此未来的学术体系可能需要更关注：

$$
\boxed{ \text{Publication} \neq \text{Attention Worthiness} }
$$

也就是说：

> **发表资格与大众阅读价值可能需要成为两个不同的评价维度。**

---

## AI 时代的学习方式

### 9. 学习的本质：不断扩大自己的“世界模型”

课程随后把讨论从论文评审转回到了学习。

学习可以理解为：

> **不断增加自己对世界的理解。**

也就是：

$$
\text{Knowledge}_{t+1} = \text{Knowledge}_{t} + \text{New Understanding}
$$

因此，学习不是简单地“记住更多内容”，而是不断扩大：

- 自己知道什么；
- 自己理解什么；
- 自己能够解释什么；
- 自己能够判断什么。

---

### 10. 学习需要持续与“过去的自己”对齐

一个很有意思的观点是：

> **学习不是不断重新从零开始，而是在和过去的自己建立连接。**

当你学习新知识时，需要不断问：

- 这和我以前知道的什么有关？
- 它解决了我以前哪个问题？
- 它修改了我之前的哪种理解？
- 它与过去的知识体系怎样连接？

可以表示为：

$$
\text{New Knowledge} \leftrightarrow \text{Existing Knowledge}
$$

这与前面给 AI 做 **Grounding** 的方法其实非常相似。

---

## 11. 优秀资料的价值，在于改变已有知识结构

当遇到一篇非常优秀的论文、几十年前的经典文章，甚至完全不同领域的一篇博客时，真正有价值的并不是：

> “我读完了这篇东西。”

而是：

> **“它有没有改变我原来的思考方式？”**

例如一篇文章可能让你意识到：

> 原来我以前理解这个问题的方式存在一个隐藏假设。

或者：

> 原来两个看似无关的问题，本质上可以用同一个框架解释。

这种知识才真正进入你的长期认知结构。

因此：

$$
\text{高质量学习} \neq \text{信息数量增加}
$$

更接近：

$$
\boxed{ \text{高质量学习} = \text{知识增加} + \text{认知结构更新} }
$$

---

## 12. 本段与 Context Engineering 的最终连接

前面的内容可以统一起来：

```text
已有知识
    ↓
明确知识边界
    ↓
建立 Grounding
    ↓
阅读新的论文 / 项目 / 教材
    ↓
不要直接接受原作者的故事
    ↓
寻找相关工作与人类知识边界
    ↓
判断真正的新知识
    ↓
更新自己的知识体系
```

与此同时，AI 也应该被放在这个框架里：

```text
不是：
Paper → AI Summary → 接受结论

而是：
已有知识
    ↓
Grounding
    ↓
Paper
    ↓
AI 帮助分析
    ↓
验证逻辑
    ↓
判断贡献
    ↓
更新知识
```

---

## 13. 本段最核心的几个判断

#### **① 局部有效，不代表整体重要**

$$
\text{A2 优化成功} \not\Rightarrow \text{A 得到重要改善}
$$

必须进一步证明 A2 对整体 A 的重要性。

#### **② 论文评价不能只检查“对不对”**

还应该检查：

$$
\boxed{ \text{Correct?} \rightarrow \text{Important?} \rightarrow \text{New?} \rightarrow \text{Worth Reading?} }
$$

#### **③ AI 审稿最大的危险之一，是被论文自己的 Context 带着走**

模型可能非常准确地验证作者的逻辑，却没有跳出来判断：

> **作者为什么认为这个问题值得研究？**

#### **④ 真正有价值的学习，是更新自己的知识结构**

不是简单增加：

$$
\text{Information}
$$

而是形成：

$$
\boxed{ \text{Information} \rightarrow \text{Understanding} \rightarrow \text{Judgment} \rightarrow \text{World Model Update} }
$$

#### **⑤ 人类仍然需要负责“价值判断”**

AI 可以非常强地完成：

- 总结；
- 推理；
- 查找；
- 验证；
- 比较。

但对于：

> **“这件事究竟重要不重要？”**

尤其是涉及研究价值、审美、教学价值和长期知识积累的问题，人类的判断仍然非常关键。

## 从知识边界扩张到 Long-Horizon Task

### 1. 学习的第一步：意识到自己的知识盲区

学习新知识时，一个非常重要的问题是：

> **“我现在不知道什么？这些东西依赖哪些前置知识？”**

如果连自己的盲区都不知道，就很难主动寻找需要补充的内容。

因此，知识积累的第一步不是无限搜资料，而是逐渐形成：

- **已经知道的 Facts**
- **已经掌握的 Concepts**
- **还不知道的知识**
- **当前知识的边界**

可以理解为：

$$
\text{Known} \rightarrow \text{Unknown} \rightarrow \text{寻找连接} \rightarrow \text{扩展 Knowledge Boundary}
$$

---

## 2. 知识不是孤立 Facts，而是一张不断扩张的网络

例如学习生物学时，一个看似孤立的事实可能是：

> **线粒体 DNA 具有母系遗传特征。**

这个事实本身只是知识网络中的一个节点。

但当你进一步知道：

- 线粒体 DNA 可以发生突变；
- 可以比较不同人的线粒体 DNA；
- 可以根据遗传差异推断亲缘关系；
- 可以进一步追溯共同祖先；

那么原来的 Fact 就开始和更多知识建立连接。

于是：

$$
\text{一个 Fact} \rightarrow \text{多个 Concepts} \rightarrow \text{新的推论} \rightarrow \text{更多 Facts}
$$

知识边界就不断向外增长。

---

### 3. 学习的真正积累，是不断增加“连接”

因此，知识增长不仅是：

$$
\text{Fact}_1,\text{Fact}_2,\text{Fact}_3,\ldots
$$

更重要的是：

$$
\text{Fact}_1 \leftrightarrow \text{Fact}_2 \leftrightarrow \text{Concept} \leftrightarrow \text{Reasoning}
$$

也就是说：

> **真正有价值的学习，是让已有知识之间建立新的连接。**

很多时候，你并没有学到大量全新的事实，但某一本书、某篇论文可能让你突然发现：

> “原来以前知道的这些东西可以这样联系起来。”

这同样是一种非常大的认知进步。

---

## 4. AI 可以显著加速知识边界的扩张

在 AI 的帮助下，可以更快速地：

- 询问陌生概念；
- 找前置知识；
- 追问细节；
- 建立概念之间的联系；
- 验证自己的理解；
- 从一个知识点继续向外探索。

因此：

$$
\boxed{ \text{AI} \rightarrow \text{降低探索成本} \rightarrow \text{更快扩展知识边界} }
$$

但这里有一个重要前提：

> **AI 不能替代真正的学习实践。**

---

## 5. 只有真正“读不懂”，才能发现自己的知识边界

单纯听老师讲：

> “学习非常重要”“要和 AI 协作”“要扩展知识边界。”

很容易感觉：

> “这个道理我懂了。”

但真正开始阅读一篇论文、一个项目或者一章教材时，才会发现：

- 有的术语完全不知道；
- 有的推导接不上；
- 有的前置知识缺失；
- AI 解释了很多遍仍然不懂。

这种 **失败本身就是学习反馈** 。

因此：

> **实践中的“不懂”，比听懂一个学习方法更有价值。**

可以表示为：

$$
\text{尝试学习} \rightarrow \text{失败} \rightarrow \text{发现知识缺口} \rightarrow \text{补足}
$$

---

## 6. 不要害怕反复纠正 AI

在实际使用 AI 时，AI 的解释也可能存在问题。

例如用户可能直接告诉 AI：

> **“说人话。”**

意思不是让 AI 变得随意，而是希望它：

- 不要堆砌术语；
- 不要一次跳太多层；
- 不要假设用户已经懂了所有前置知识；
- 把解释调整到用户真正能理解的程度。

这通常需要多轮对话：

```text
AI 第一次解释
    ↓
仍然不懂
    ↓
用户纠正
    ↓
AI 换一种解释
    ↓
建立共识
    ↓
继续推理
```

因此，高质量 AI 学习不是：

> **问一次 → 得到答案 → 结束。**

而是：

> **通过多轮对话不断让 AI 和自己的认知状态对齐。**

---

## 7. “共识 → 推理”是高质量 AI 学习的重要流程

前面的内容可以进一步整理为：

$$
\boxed{ \text{Consensus} \rightarrow \text{Reasoning} }
$$

其中：

#### **Consensus：先建立共同基础**

明确：

- 我已经知道什么；
- 我不知道什么；
- 相关概念是什么意思；
- 当前问题究竟是什么。

#### **Reasoning：再向前推进**

在共同基础上：

$$
I_0 \rightarrow I_1 \rightarrow I_2 \rightarrow \cdots
$$

一步一步扩展理解。

这样能够明显减少 AI 和用户之间的认知错位。

---

## 8. 从“遵循指令”到“扩展认知”，Verifier 的含义也发生变化

前面的藏头诗属于一种很短的任务：

> **Instruction + Verifier → 完成任务**

例如：

$$
\text{字数正确} + \text{韵脚正确} + \text{指定字出现}
$$

这些约束比较明确。

但学习和知识理解中的 Verifier 可能完全不同。

这里的验证标准可以变成：

> **“AI 是否真的按照我的知识水平，把这个问题重新构建成我能理解的逻辑？”**

也就是说：

$$
\text{Verifier} = \text{是否推动了我的理解}
$$

这是一个更加主观、更加难自动化的 Verifier。

---

## 9. 高质量学习的验证标准：是否改变了你的认知结构

如果读完一本书、论文或教材后，只记住几个事实：

$$
F_1,F_2,F_3
$$

那么收益有限。

但如果出现：

$$
\text{旧知识} \xrightarrow{\text{新的理解}} \text{重新连接}
$$

让整个知识体系重新组织，那么学习的价值就大得多。

例如原来：

```text
A   B   C
```

彼此独立。

学习之后：

```text
      A
     / \
    B---C
```

原有 Facts 没变，但关系发生了改变。

这就是所谓：

> **“三观尽毁”式学习。**

不是以前知道的事实全部错误，而是：

> **以前的 Facts 被重新组合成了一套完全不同的理解框架。**

---

## 10. 长期学习可以看成不断进行“知识重构”

因此，一个人的学习过程可以理解为：

$$
\text{Facts} \rightarrow \text{Connections} \rightarrow \text{Mental Model} \rightarrow \text{New Facts} \rightarrow \text{重新连接} \rightarrow \text{更新 Mental Model}
$$

这个过程会不断重复。

所以：

> **学习不是简单地往脑子里堆知识，而是不断重构知识之间的关系。**

---

## 11. 把失败经验“蒸馏”为自己的 Skill

课程还提出了一个非常实用的思路：

> **失败本身可以被沉淀成 Skill。**

例如第一次遇到问题：

```text
失败
 ↓
发现原因
 ↓
总结经验
 ↓
形成规则
 ↓
下一次自动使用
```

经过多次迭代：

$$
\text{失败经验} \rightarrow \text{经验总结} \rightarrow \text{规则} \rightarrow \text{Skill}
$$

这就是 **Skill Distillation（技能蒸馏）** 。

本质上是把：

> **“我以前遇到过这个问题，下次应该怎么做。”**

变成一个可复用的知识模块。

---

## 12. Skill Distillation 的最终目标

理想情况下，你不应该每次从头踩同一个坑。

而应该：

```text
第一次：
问题 → 失败 → 分析

第二次：
问题 → 应用经验 → 改进

第三次：
问题 → Skill 自动指导 → 成功概率提高

……

最终：
形成稳定的个人方法论
```

所以一个人的能力也可以不断被“工程化”：

$$
\boxed{ \text{Experience} \rightarrow \text{Reflection} \rightarrow \text{Rule} \rightarrow \text{Skill} }
$$

---

## 进入 Long-Horizon Task

### 13. 短任务与 Long-Horizon Task 的区别

前面讲的很多任务，例如：

- 写一首满足多个约束的诗；
- 完成一道题；
- 编译代码；
- 通过一个测试；

虽然可能很复杂，但仍然属于相对短程、目标明确的任务。

而真正的 **Long-Horizon Task（长程任务）** 有明显不同。

例如完整完成一个大型软件工程任务，需要：

$$
\text{需求} \rightarrow \text{设计} \rightarrow \text{实现} \rightarrow \text{调试} \rightarrow \text{测试} \rightarrow \text{修改} \rightarrow \text{再次测试} \rightarrow \cdots
$$

它可能跨越：

- 很多步骤；
- 很长时间；
- 很多上下文；
- 多次工具调用；
- 多轮失败与恢复。

因此：

> **长程任务的核心问题，不再只是“模型能不能正确执行一步”，而是“模型能不能在很长的执行链中持续保持正确方向”。**

---

## 14. 前面讨论的 Context Engineering 会在 Long-Horizon Task 中真正变得重要

短任务中，Context 可能只需要：

```text
User Request
+
几个约束
+
Verifier
```

而长程任务需要维护：

```text
长期目标
   ↓
当前计划
   ↓
已完成工作
   ↓
当前状态
   ↓
失败记录
   ↓
工具结果
   ↓
下一步目标
   ↓
Verifier
```

于是之前讨论的所有问题都会再次出现：

- Context 如何增长；
- 哪些信息应该保留；
- 哪些信息应该压缩；
- 如何防止上下文污染；
- 如何保持长期目标；
- 如何持续验证；
- 如何从失败中恢复。

这也意味着：

$$
\boxed{ \text{Context Engineering} \rightarrow \text{Long-Horizon Agent Engineering} }
$$

---

## 15. 本段核心逻辑

```text
发现自己的知识盲区
       ↓
通过 AI 快速探索
       ↓
在真实阅读 / 实践中失败
       ↓
发现新的知识缺口
       ↓
建立共识
       ↓
一步一步推理
       ↓
重新组织已有知识
       ↓
把成功经验沉淀为 Skill
       ↓
进入更复杂的 Long-Horizon Task
```

最核心的认识可以概括为：

$$
\boxed{ \text{学习} = \text{扩展知识边界} + \text{重新连接已有知识} + \text{从失败中蒸馏方法} }
$$

而当任务从短程走向 **Long-Horizon** 后，人类最需要掌握的就进一步变成：

$$
\boxed{ \text{明确目标} + \text{维护 Context} + \text{持续验证} + \text{从失败恢复} + \text{积累可复用 Skill} }
$$

## Long-Horizon Task、软件复杂度与 AI 阅读大型代码库的优势

### 1. Long-Horizon Task 的本质：从不完整信息出发

真正的 **Long-Horizon Task（长程任务）** 和前面“给定明确 Spec、不断通过 Verifier”的任务不同。

它通常具有：

- 一个相对明确的 **Intent（意图）** ；
- 但具体 **Specification（规格）** 尚未完全确定；
- **Implementation（实现方案）** 也存在大量未知；
- 最终却要求交付一个高质量的实现。

可以表示为：

$$
\text{Initial State} \rightarrow \text{Intent} \rightarrow \text{未知的 Spec} \rightarrow \text{未知的 Implementation} \rightarrow \text{High-quality Result}
$$

因此，Long-Horizon 的难点不只是“任务很长”，更重要的是：

> **任务在执行过程中还会逐渐明确。**

---

## 2. 不应该让 Agent 一开始就把整个未来规划完

由于模型本质上通过 **Self-Attention + Next Token Prediction** 不断向前生成，同时训练过程又非常强调“尽快满足任务要求”，模型容易产生一种倾向：

> **赶紧做出一个看起来满足要求的结果，然后结束任务。**

因此如果一开始就要求：

> “帮我从零规划完整产品，考虑所有未来需求，然后再开始实现。”

可能反而不理想。

因为过度规划会带来：

- 大量推理 Token；
- Context 快速膨胀；
- 计划本身可能发生错误；
- 后续实现空间被过早锁死；
- 最终甚至还没开始做就已经消耗了大量上下文。

因此当前阶段更适合让 Agent：

> **先完成一个边界清晰、可以验证的阶段性目标。**

例如课程作业：

> “先把 PA2 做完。”

这类任务恰好处于：

$$
\text{目标明确} + \text{范围明确} + \text{有验证手段}
$$

所以非常适合当前 Agent。

---

## 3. One-shot 生成已经非常强，但“持续维护”是另一回事

现在从零生成一个小型产品，往往已经非常容易。

例如只用一句：

> “帮我做一个极品飞车。”

模型就可能直接生成一个可以运行的 **Proof of Concept（概念验证，PoC）** 。

类似地：

- 个人主页；
- 小型工具；
- 简单游戏；
- 小型 Web App；

都可以快速得到一个第一版。

所以：

$$
\boxed{ \text{从 0 到 1} \quad \text{往往已经很容易} }
$$

真正困难的反而是：

$$
\boxed{ \text{从 1 到 N} }
$$

也就是后续不断：

- 加功能；
- 修改需求；
- 重构；
- 修 Bug；
- 维护旧逻辑；
- 保持系统结构；
- 保证新增代码和已有代码一致。

---

## 4. 软件维护过程中，AI 可能出现“翻车点”

一个非常典型的现象是：

```text
初始版本
   ↓
加一个功能
   ↓
再加一个功能
   ↓
再加一个功能
   ↓
……
   ↓
某个时间点开始明显翻车
```

随着项目不断修改， **Complexity（复杂度）** 会逐渐增长。

可以粗略表示为：

$$
C_0 < C_1 < C_2 < \cdots
$$

当复杂度达到某个阶段以后，Agent 可能开始：

- 修改错误的地方；
- 重复实现已有功能；
- 破坏旧接口；
- 产生越来越多补丁；
- 很难维持整体架构。

这和经典软件工程问题高度一致。

---

## 5. 软件复杂度并不是 AI 时代才出现的问题

课程引用 **The Mythical Man-Month（人月神话）** 所讨论的经典观点：

> **大型软件系统最困难的问题之一，就是随着系统增长而不断出现的复杂度。**

软件不是简单地：

$$
\text{Feature}_1 + \text{Feature}_2 + \text{Feature}_3
$$

而是会产生大量：

- 模块之间的依赖；
- 接口关系；
- 历史兼容性；
- 特殊情况；
- 隐含约束。

因此：

$$
\text{System Complexity} \gg \text{Feature Count}
$$

这也是为什么“小项目很好生成”与“大项目难维护”可以同时成立。

---

## 6. 一个有趣的悖论：AI 在大型复杂系统里反而可能表现更好

这里出现了一个非常反直觉的观察：

> **小项目从零生成很容易，但大型成熟软件系统反而可能更适合 AI 进行局部修改。**

例如 **Linux Kernel** 。

现代 Linux Kernel 的代码规模极其庞大，长期演化之后，一个功能往往会跨越很多层抽象。

人类阅读一个简单问题，例如：

> “文件是怎么打开的？”

可能会遇到：

```text
open()
 ↓
函数调用
 ↓
另一个函数
 ↓
继续跳转
 ↓
……
 ↓
第十层调用
 ↓
最终某个简单操作
```

对于不了解该 **Subsystem（子系统）** 的人来说，这种代码阅读体验非常痛苦。

---

## 7. 大型成熟系统的复杂度，却可能同时包含大量“经验”

大型系统虽然复杂，但它的代码不是随机复杂，而是：

> **经过多年大量人类工程实践、修复、重构和维护之后形成的。**

因此高质量成熟代码中往往已经积累了：

- 经过验证的设计；
- 稳定的接口；
- 大量代码模式；
- 已解决的边界情况；
- 一致的工程习惯。

于是会产生一个非常重要的现象：

$$
\text{代码复杂} \neq \text{代码毫无结构}
$$

反而可能是：

$$
\text{高复杂度} + \text{高结构性}
$$

这恰恰给 AI 提供了大量可以学习的模式。

---

## 8. 高质量代码对 AI 来说可以成为“示例数据库”

假设你要在 Linux Kernel 中实现一个新的功能。

这个功能很可能不是世界上第一次出现。

Kernel 中可能已经有：

```text
实现 A
实现 B
实现 C
```

三个类似功能。

那么 Agent 可以通过搜索和 Attention 找到它们：

$$
\text{新需求} \rightarrow \text{搜索类似实现} \rightarrow \text{比较已有模式} \rightarrow \text{组合已有经验} \rightarrow \text{实现新功能}
$$

对人类来说，这可能需要非常大量的：

- 搜索；
- 阅读；
- 记忆；
- 对比；
- 心智建模。

而 Agent 可以同时加载几十个甚至更多相关文件，然后寻找其中共同的结构。

---

## 9. Self-Attention 在大型代码库中体现出特别强的优势

例如同一个子系统里，多个代码位置都采用：

```text
获取资源
 ↓
检查状态
 ↓
加锁
 ↓
执行操作
 ↓
释放锁
```

人类如果刚接触这个 Subsystem，需要自己总结：

> “原来这个模块都是这么做的。”

而模型可以在读取多个文件之后，通过 Attention 发现这种重复模式。

可以抽象成：

$$
\text{File}_1 + \text{File}_2 + \text{File}_3 +\cdots \rightarrow \text{Shared Pattern}
$$

然后：

$$
\text{Shared Pattern} \rightarrow \text{New Implementation}
$$

这就是为什么：

> **面对一个已有大量高质量实现的大型代码库，AI 有时反而比人更容易快速找到“应该照着谁做”。**

---

## 10. 最难的细节可以被“已有代码模式”直接托管

尤其在大型系统里，人类最头疼的往往不是语法，而是大量隐含规则。

例如：

- 应该调用哪个 Helper；
- 应该先加哪个锁；
- 锁的顺序是什么；
- 哪个接口需要特殊处理；
- 错误应该在哪一层传播；
- 哪些状态必须提前检查。

如果对整个 Subsystem 不熟悉，人类很难靠一次阅读建立完整心智模型。

但 Agent 可以：

```text
加载多个相关文件
      ↓
寻找相同代码结构
      ↓
发现共同模式
      ↓
推断隐含约束
      ↓
模仿已有实现
```

因此：

> **成熟代码库本身就包含了大量“隐式 Specification”。**

这些 Spec 不一定写在文档里，但已经被大量现有代码体现出来。

---

## 11. 这与前面的“论文上下文污染”恰好形成反差

前面讨论论文时：

$$
\text{逻辑高度自洽的文档} \rightarrow \text{强烈影响 Attention} \rightarrow \text{模型容易接受作者叙事}
$$

而在高质量代码库中：

$$
\text{大量经过验证的代码模式} \rightarrow \text{重复结构} \rightarrow \text{模型容易发现稳定模式}
$$

因此两种 Context 的效果可能完全不同：

| Context 类型 | 可能产生的效果 |
| --- | --- |
| 自洽的论文 | 容易让模型顺着作者的逻辑走 |
| 高质量成熟代码 | 容易让模型找到已有工程模式 |

关键区别在于：

> **代码中的大量重复实现本身就是可观察、可模仿的工程证据。**

---

## 12. 从大型代码库中“学习”已有工程规律

因此，修改大型系统时，一个非常有效的 Agent 工作方式是：

```text
明确局部需求
      ↓
定位相关 Subsystem
      ↓
搜索类似功能
      ↓
读取多个已有实现
      ↓
提取共同模式
      ↓
识别隐含约束
      ↓
按照既有模式实现
      ↓
运行验证
```

也就是说：

> **不要让 Agent 凭空设计一个新方案，而应尽可能让它从代码库中寻找“已经被人类证明过的方案”。**

这实际上是在利用：

$$
\boxed{ \text{Existing Code} = \text{Accumulated Engineering Experience} }
$$

---

## 13. Long-Horizon Task 的关键矛盾

这一段可以归纳为一个很重要的矛盾：

$$
\boxed{ \text{从零创造} \rightarrow \text{AI 很强} }
$$

但：

$$
\boxed{ \text{长期维护} \rightarrow \text{复杂度快速增长} }
$$

然而对于成熟大型系统：

$$
\boxed{ \text{系统很复杂} + \text{已有大量高质量模式} \rightarrow \text{AI 反而可能很擅长局部修改} }
$$

所以真正困难的并不单纯是：

> **代码量大。**

而是：

> **上下文中是否存在足够清晰、稳定、可复用的结构。**

---

## 14. 本段核心结论

#### **① Long-Horizon 的真正难点是“未知”**

不是单纯步骤多，而是：

$$
\text{Intent 已知} ,\quad \text{Spec / Implementation 部分未知}
$$

需要在执行过程中不断明确问题。

#### **② 当前更适合让 Agent 处理明确的阶段性目标**

例如：

> **先完成 PA2。**

而不是一开始就要求它规划整个未来。

#### **③ 从 0 到 1 已经非常容易，从 1 到 N 更难**

$$
\text{Generation} < \text{Long-term Maintenance}
$$

持续修改会让软件复杂度快速增长。

#### **④ 大型成熟代码库反而可能成为 AI 的优势场**

因为高质量代码中已经包含：

- 已验证的实现；
- 重复模式；
- 隐含约束；
- 工程经验。

#### **⑤ Self-Attention 可以帮助 Agent 从大量代码中提取共同模式**

$$
\text{多个已有实现} \rightarrow \text{共同 Pattern} \rightarrow \text{新实现}
$$

#### **⑥ 成熟代码库本身就是一种隐式 Specification**

这是一条非常重要的认识：

> **文档没有写出来的规则，往往已经被大量高质量代码“写”出来了。**

因此，Agent 不一定需要先完全理解整个 Linux Kernel，才能实现一个局部功能；它可以通过阅读多个相似实现，直接学习这个 Subsystem 已经形成的工程习惯。

**最终的核心原则是：**

> **Long-Horizon Task 中，不要强迫 AI 一次性猜完整个未来；在大型成熟系统中，则尽量让 AI 从已有代码中寻找已经验证过的模式，让代码库本身承担一部分 Specification 的作用。**

## 大型成熟软件中的 AI 优势与“优秀设计经验注入”研究方向

### 1. AI 在大型复杂系统与小型项目中的表现存在反差

前面观察到一个非常有意思的现象：

> **AI 做复杂的大型软件维护，有时反而比从零做一个小项目更稳定。**

例如修改 **Linux Kernel** 或 **Android Runtime（ART）** 中的 **JIT Compiler（即时编译器）** ，对人类开发者来说可能极其困难。

这类系统具有：

- 巨大的代码规模；
- 很多历史兼容性；
- 复杂的调用关系；
- 大量隐含约束；
- 深厚的领域知识要求。

对于人类来说，深入修改一个成熟 JIT 编译器甚至可能成为一个非常高的学习门槛。

而 AI 面对这种情况却可能表现得非常好。

---

### 2. 为什么成熟的大型系统反而适合 AI

关键原因仍然是：

> **成熟系统中的复杂性并不是随机的，而是存在大量稳定的工程模式。**

例如 AI 在修改一个复杂 Subsystem 时，可以同时看到：

- 多个相似实现；
- 相关 Helper；
- 锁的使用方式；
- 错误处理方式；
- 生命周期管理；
- 调用顺序。

于是它可以通过 Attention 找到：

> **“这个系统通常就是这么做的。”**

这相当于直接利用了多年工程实践留下来的经验。

因此可以形成：

$$
\text{成熟代码} \rightarrow \text{大量重复模式} \rightarrow \text{隐含 Specification} \rightarrow \text{AI 模仿} \rightarrow \text{较高质量实现}
$$

---

## 3. AI 做“小型项目”反而可能更容易 Drift

如果让 AI 从零生成一个小游戏、个人主页等小型项目，它虽然可以迅速给出一个能运行的版本，但后续不断增加需求时容易出现：

- 架构逐渐失控；
- 重复造轮子；
- 局部修补越来越多；
- 代码复杂度持续上升；
- 最终难以长期维护。

因为从零开始时，Context 中缺少：

> **大量已经被证明有效的工程设计模式。**

所以：

$$
\text{空白项目} \rightarrow \text{模型自行设计} \rightarrow \text{大量自由度} \rightarrow \text{更高 Drift 风险}
$$

而成熟代码库则恰恰相反：

$$
\text{已有大量模式} \rightarrow \text{设计空间受到约束} \rightarrow \text{模型更容易沿用正确模式}
$$

---

## 4. 一个可能重要的研究方向：把人类优秀工程经验提取出来

课程中提出了一个非常有意思的 **Research Idea（研究方向）** ：

> **能不能系统性地收集人类历史上最优秀的软件项目，把其中的设计经验提取出来，再提供给 AI？**

例如：

- 每个领域选取最优秀的 10～20 个项目；
- 分析它们的架构；
- 提炼共同设计原则；
- 提取成功的工程模式；
- 把这些经验压缩成 AI 可以利用的知识。

可以抽象为：

$$
\text{优秀软件项目} \rightarrow \text{代码分析} \rightarrow \text{设计经验提取} \rightarrow \text{Design Patterns / Principles}
$$

---

## 5. 这与《A Philosophy of Software Design》的思路相似

这个思路与 **A Philosophy of Software Design** 类似。

这类书做的事情，本质上就是：

> **从大量软件工程实践中提炼出更一般性的设计原则。**

例如：

- 什么情况下应该封装；
- 什么情况下不应该过度抽象；
- 模块应该如何组织；
- 继承和组合应该怎样选择；
- 接口应该如何设计；
- 如何控制复杂度。

也就是说：

$$
\text{大量具体项目} \rightarrow \text{经验} \rightarrow \text{抽象原则}
$$

如果能够把这个过程自动化，就有可能构建一种：

> **“高质量软件工程经验数据库”。**

---

## 6. 不一定要把整个优秀项目塞进 Context

一个直接的方法是：

> 把一个优秀代码库完整放进 Context，再把自己的需求放进去。

例如：

```text
优秀项目代码
      ↓
你的需求
      ↓
Agent
      ↓
参考优秀项目实现
```

理论上，这可能有效。

因为 Attention 可能在生成代码时发现：

> “这个优秀项目里已经有类似功能，而且它采用了某种成熟结构。”

于是模型就可能模仿这种结构。

---

### 7. 但完整代码直接塞进 Context 也会造成污染

问题在于：

**优秀项目本身也会占据大量 Context。**

因此：

$$
\text{参考代码越多} \rightarrow \text{Context 越大} \rightarrow \text{Attention 竞争越严重}
$$

而且代码库中必然存在：

- 与当前任务无关的代码；
- 特定项目的历史包袱；
- 项目专属约束；
- 不适合当前任务的设计。

所以“直接把整个优秀项目塞进去”并不是理想方案。

---

## 8. 更好的方向：把优秀项目“蒸馏”为设计知识

因此，一个更加理想的方案可能是：

$$
\text{优秀代码库} \rightarrow \text{分析} \rightarrow \text{提取设计模式} \rightarrow \text{压缩成文档}
$$

而不是：

$$
\text{优秀代码库} \rightarrow \text{完整塞入 Context}
$$

最终得到的可能是类似：

```text
模块设计原则
接口设计原则
错误处理模式
并发模型
资源生命周期
常见反模式
适用场景
……
```

这和《A Philosophy of Software Design》做的事情非常相似：

> **把大量具体工程实践压缩成少量通用原则。**

---

## 9. “好的经验”也可以作为 Context 中的先验

一种更激进的方法是：

```text
优秀项目的设计经验
        ↓
加入 Context
        ↓
当前需求
        ↓
Agent
        ↓
结合经验寻找实现
```

这里的关键思想是：

> **先给模型一个“好的工程先验”，再让它解决具体问题。**

例如：

```text
Design Knowledge
    ↓
“这个系统倾向于松耦合”
“这里应该避免继承”
“这个模块应该隐藏实现细节”
……
    ↓
Current Requirement
    ↓
Implementation
```

这样可以减少 Agent 在完全空白的情况下自行设计的自由度。

---

## 10. 不同优秀设计之间可能互相冲突

但这条路线存在一个非常大的困难：

> **不存在一个适用于所有软件的唯一“最佳架构”。**

例如两种都很优秀的设计：

#### 设计 A：松耦合消息系统

```text
Module A
   ↓
Message
   ↓
Module B
```

模块之间通过消息交互，彼此高度解耦。

#### 设计 B：统一 Gateway

```text
Module A
   ↓
Unified Gateway
   ↓
查表 / 路由
   ↓
Module B
```

所有调用都集中到一个统一入口。

两者都可能是优秀设计，但它们的思想明显不同。

因此：

$$
\text{Design A} \neq \text{Design B}
$$

而且不能简单地把二者同时作为“必须遵循的原则”。

---

## 11. 不同 Design Pattern 之间可能产生冲突

于是问题变成：

> **如果 Context 中同时放入多个优秀项目，它们的设计原则互相冲突怎么办？**

例如：

```text
项目 A：强封装
项目 B：开放组合
项目 C：事件驱动
项目 D：统一 Gateway
```

如果全部告诉 Agent：

> “这些都是优秀实践，请参考。”

那么模型可能出现：

- 不知道应该选哪个；
- 混合出一个奇怪的架构；
- 在不同部分随机采用不同原则；
- 失去整体一致性。

所以：

$$
\text{更多优秀经验} \not\Rightarrow \text{更好的结果}
$$

---

## 12. 一个更进一步的想法：让 AI 自己进行设计空间搜索

因此课程提出了一个可能更有意思的方向：

> **不要告诉 AI “唯一正确的设计是什么”，而是给它多个优秀项目，让它通过多轮推理逐渐收敛。**

流程可以是：

```text
优秀项目 A
        +
优秀项目 B
        +
优秀项目 C
        ↓
提取各自设计原则
        ↓
比较差异
        ↓
结合当前需求
        ↓
尝试架构方案 1
        ↓
评估
        ↓
修改
        ↓
架构方案 2
        ↓
继续验证
        ↓
最终收敛
```

即：

$$
\boxed{ \text{Multiple Good Designs} \rightarrow \text{Comparison} \rightarrow \text{Adaptation} \rightarrow \text{Iteration} \rightarrow \text{Good Structure} }
$$

这比简单复制某一个项目更加灵活。

---

## 13. “参考多个优秀项目”更像一种设计搜索

可以把它看成一个 **Design Space Search（设计空间搜索）** ：

$$
D_1,D_2,\ldots,D_n \rightarrow \text{Candidate Designs} \rightarrow \text{Evaluation} \rightarrow D^*
$$

其中：

- $D_i$：已有优秀项目中的设计；
- $D^*$：针对当前需求选择出的更合适设计。

这与机器学习中的搜索、优化思想很接近。

关键不再是：

> **“哪个项目最好？”**

而是：

> **“哪个项目中的哪些设计原则最适合当前问题？”**

---

## 14. 这种方法的核心挑战：如何自动判断“好设计”

最终仍然会回到前面反复出现的 **Verifier** 问题。

你可以非常容易判断：

> “代码能不能编译？”

但很难判断：

> “这个架构是不是一个好的长期可维护架构？”

因此，要真正实现这种研究方向，还需要建立更加复杂的 **Design Verifier（设计验证器）** ，例如综合考虑：

- 可维护性；
- 模块耦合；
- 扩展成本；
- 性能；
- 可测试性；
- 代码复杂度；
- 一致性。

最终可能形成：

$$
\text{Candidate Architecture} \rightarrow \text{Design Evaluation} \rightarrow \text{Feedback} \rightarrow \text{Revision}
$$

这也是它真正困难的地方。

---

## 15. 为什么这个方向可能延缓 AI Slop

前面讨论过，AI 从零生成代码容易趋向自己的默认风格。

如果能够提供大量经过人类长期实践验证的设计经验，那么：

$$
\text{Default AI Design} \rightarrow \text{Human Engineering Patterns}
$$

模型就不必每次都从自己的默认分布开始。

更理想的状态是：

$$
\boxed{ \text{AI 能力} + \text{人类优秀工程经验} + \text{当前项目约束} }
$$

从而更大概率生成：

> **不仅能够运行，而且能够长期维护的软件。**

---

## 16. 本段核心逻辑

```text
AI 从零生成小项目
        ↓
短期效果很好
        ↓
长期维护容易 Drift

而大型成熟代码库
        ↓
包含大量经过验证的工程模式
        ↓
AI 更容易找到正确做法
        ↓
局部维护反而表现很好
```

由此产生一个研究方向：

```text
大量优秀软件项目
        ↓
提取设计经验
        ↓
压缩成 Principles / Patterns
        ↓
作为 Context 提供给 Agent
        ↓
多个优秀设计之间进行比较
        ↓
结合当前需求进行多轮搜索
        ↓
收敛到适合当前系统的架构
        ↓
生成更加可维护的代码
```

最终可以概括为：

$$
\boxed{ \text{把人类长期积累的软件工程经验} \rightarrow \text{蒸馏成 AI 可使用的设计知识} \rightarrow \text{让 AI 不再从默认风格出发，而是在优秀实践空间中搜索} }
$$

**核心问题已经从“怎么让 AI 会写代码”，进一步变成了“怎么把人类几十年积累的软件设计智慧注入 AI，并让它根据具体问题选择和组合这些经验”。**

## 上下文意识、Verifier 设计与 AI 引导边界

### 1. 当前 AI 还没有“理解一切”的超能力

前面讨论的很多方法，最终都建立在一个现实前提上：

> **今天的 AI 还没有强大到可以自动理解所有上下文、所有设计意图和所有软件工程问题。**

因此，人类仍然需要知道：

- Context 中有哪些信息；
- 每条信息的作用是什么；
- 不同信息之间是否冲突；
- 哪些信息会影响模型行为；
- 怎样让模型始终关注关键约束。

也就是说：

$$
\boxed{ \text{AI 很强} \neq \text{AI 可以替你决定一切} }
$$

---

## 2. AI 时代并不是“不需要学习”，而是“学习方式发生变化”

要真正控制 AI，首先仍然需要具备基础概念。

例如至少需要理解：

- **Processor（处理器）**
- **Operating System（操作系统）**
- **Compiler（编译器）**
- **Database（数据库）**
- 软件架构；
- 软件设计。

这些领域中本身就包含大量经过长期实践积累的 **设计智慧** 。

因此：

> **AI 并没有让专业知识变得无关紧要，反而让“拥有概念”变得更加重要。**

原因是：

$$
\text{缺少基础概念} \rightarrow \text{无法判断 AI 的方案是否合理}
$$

而：

$$
\text{掌握基础概念} \rightarrow \text{可以与 AI 讨论设计} \rightarrow \text{可以约束 AI} \rightarrow \text{可以验证 AI}
$$

---

## 3. 学习方式会改变，但知识本身不会消失

未来更高效的学习方式可能变成：

```text
传统学习：
教材 → 理解 → 练习

AI 时代：
概念学习
   ↓
AI 辅助解释
   ↓
立即实验
   ↓
不断追问
   ↓
验证
   ↓
形成自己的理解
```

因此变化主要发生在：

> **如何获得知识、如何练习、如何反馈。**

而不是：

> **“不用学处理器、OS、编译器了。”**

恰恰相反，这些基础知识会决定一个人能否真正驾驭 AI。

---

## 4. 生成式软件工程需要的核心能力是一整套“工程闭环”

课程认为，这门课真正要教的并不只是 Prompt 写法，而是一整套软件工程方法：

$$
\boxed{ \text{Define} \rightarrow \text{Instruct} \rightarrow \text{Monitor} \rightarrow \text{Verify} \rightarrow \text{Correct} }
$$

具体来说：

#### **① 给出正确指令**

告诉 AI：

- 要做什么；
- 为什么做；
- 有哪些约束；
- 什么不能做。

#### **② 监控 Agent**

观察：

- 它正在做什么；
- 它为什么这么做；
- 有没有偏离目标；
- 上下文中是否出现了错误方向。

#### **③ 提供好的 Verifier**

让 Agent 知道：

> **什么结果才算正确。**

#### **④ 失败后纠偏**

如果方向不对：

$$
\text{Observe} \rightarrow \text{Identify Deviation} \rightarrow \text{Correct Context}
$$

所以，生成式软件工程实际上更接近：

> **用软件工程的方法管理 AI，而不是单纯写 Prompt。**

---

## 5. “好的 Verifier”本身就是一个需要设计的问题

前面只是说：

> **“给模型一个 Verifier。”**

但真正困难的是：

> **什么才算一个好的 Verifier？**

例如代码测试：

```text
测试通过
→ 明确成功
```

非常容易。

但对于研究、设计、教学等任务：

```text
是不是一个好研究？
是不是好的架构？
是不是好的教学？
是不是好的设计？
```

这些标准往往没有天然的机器判定器。

因此：

$$
\text{设计 Verifier} \approx \text{定义“什么叫正确”}
$$

它本身就是一个非常重要的软件工程问题。

---

## 6. 人类最重要的工作：把 AI 引导到正确的位置

虽然模型很强，但它并不知道：

> **你脑子里真正的目标是什么。**

所以仍然需要进行 **Guidance（引导）** 。

理想状态不是：

> “告诉 AI 每一步怎么写。”

而是：

> **“给它足够少、但足够关键的方向信息，让它自己完成后面的工作。”**

可以理解成：

$$
\text{Human} \rightarrow \text{Direction + Constraints}
$$

$$
\text{AI} \rightarrow \text{Execution + Exploration}
$$

这与传统工程团队也存在一个很有意思的对比。

---

## 7. AI 与传统工程团队的一个重要区别

传统大型项目中，如果需要完成复杂任务，通常需要：

- 招很多人；
- 分配职责；
- 开设计会议；
- 建立团队共识；
- 不断同步；
- 处理沟通成本。

这会形成巨大的 **Coordination Cost（协调成本）** 。

而使用足够强的 Agent 时，可以在一定程度上变成：

$$
\text{Human Goal} + \text{Concise Context} \rightarrow \text{AI Execution}
$$

因此：

> **模型越聪明，人类越应该关注“把正确方向告诉它”，而不是亲自描述每一个实现细节。**

---

## 8. 一个新的研究问题：能不能把人类工程经验直接注入 AI

前面提出的“优秀项目经验提炼”在这里得到进一步延伸。

可以设想：

```text
优秀项目
   ↓
提取设计经验
   ↓
形成通用原则
   ↓
提供给 AI
   ↓
AI 根据当前需求选择
```

这样 AI 不必完全从自己的默认分布出发，而可以站在：

> **人类几十年积累的软件工程经验之上继续搜索。**

这可能成为未来 **Context Engineering** 的一个重要研究方向。

---

## 研究案例：符号执行引擎优化

### 9. 一个适合学生研究的任务：优化符号执行引擎

课程举了一个具体研究项目作为反例。

项目大致目标是：

> **优化一个符号执行引擎的执行效率。**

不需要深入理解 **Symbolic Execution（符号执行）** 的具体算法，只需要把它看作：

> 一个可以自动分析程序、检查程序行为，甚至帮助验证程序正确性的系统。

当前系统：

$$
\text{正确} \quad但\quad \text{执行效率较低}
$$

于是提出一个合理的研究问题：

> **是否可以通过某种优化方法，让它运行得更快？**

这是一个非常典型的：

**Incremental Research（增量式研究）** 。

---

## 10. Incremental Research 本身是合理的学生研究模式

学生研究通常并不要求：

> “从零创造一个全新的计算领域。”

更常见的是：

```text
已有系统
   ↓
发现一个具体瓶颈
   ↓
提出一个改进方法
   ↓
验证方法有效
   ↓
形成新的研究贡献
```

因此：

> **只要问题具体、方法合理、实验可行，这类研究方向完全可以成为学生项目。**

---

## 11. 但案例中的 Agent 很快遇到了 Long-Horizon 的真正困难

研究者提出初始 Idea 后：

> “这个优化方向应该是可行的。”

人类觉得有道理。

AI 也觉得有道理。

于是让 GPT-5.6 之类的模型开始执行。

然后出现了一个关键问题：

> **AI 持续产生大量 Token 和反馈，但研究者无法判断这些反馈究竟是否正确。**

即：

```text
AI
 ↓
给出分析
 ↓
研究者不知道对不对
 ↓
AI 继续
 ↓
又给出新结论
 ↓
仍然不知道对不对
 ↓
……
```

这就是 Long-Horizon Research 中非常危险的情况：

$$
\boxed{ \text{Agent 能运行很久} \neq \text{Agent 一直在正确方向上运行} }
$$

---

## 12. “不知道 AI 为什么错”会让反馈循环失效

如果 Agent 给出一个 Negative Result：

> “这个优化方向不行。”

问题就变成：

> **为什么不行？**

如果人类无法判断它的依据是否正确，就无法有效纠正。

于是：

$$
\text{AI Negative} \rightarrow \text{Human 无法验证} \rightarrow \text{无法提供有效反馈}
$$

这样整个反馈循环就会断掉。

这说明：

> **Long-Horizon Task 最大的问题之一，不是模型愿不愿意继续做，而是人类还能不能判断它是不是在正确做。**

---

## 13. 真正的失败发生在“引导错了一步”

这个案例中，问题并不是：

> **AI 完全不会做。**

而是：

> **Context 中的一条要求把它引向了错误方向。**

研究者心中的真正目标是：

> **证明这个研究方向对整个问题有意义。**

但 Context 中存在一个更局部的要求：

> **“证明方法 A 是有效的。”**

模型看到后，开始强烈优化这个局部目标。

于是发生：

$$
\text{Big Picture} \rightarrow \boxed{\text{局部目标}} \rightarrow \text{不断证明局部有效}
$$

最终忽略了：

> **“这个局部改进对于整个研究问题到底有什么意义？”**

---

## 14. Reward Hacking：模型可能把“局部指标”当成真正目标

这种现象可以联系到 **Reward Hacking（奖励投机 / 奖励黑客）** 。

核心问题是：

> **模型优化的是“可被当前评价机制奖励的目标”，而不一定是人类真正想要的目标。**

例如：

```text
Human Goal：
证明整个研究方向有价值

Context 中显式目标：
证明方法 A 有效

AI：
“那我就不断证明 A 有效。”
```

如果 Verifier 只检查：

$$
\text{Is A Effective?}
$$

那么模型就会极力优化这一点。

但真正需要的是：

$$
\text{Is A Effective?} + \text{Does A Matter?} + \text{Does It Advance the Overall Problem?}
$$

因此：

> **局部 Verifier 正确，不代表整体目标正确。**

---

## 15. Research Agent 特别需要防止“局部最优”

软件工程任务中，可以较容易定义：

> “测试全部通过。”

但研究任务往往需要多层目标：

$$
\text{Local Correctness} \rightarrow \text{Global Relevance} \rightarrow \text{Research Significance}
$$

如果只给模型一个局部目标：

$$
\text{Optimize A}
$$

模型很可能真的把 A 做得越来越好。

但它可能完全没有回答：

> **“为什么要优化 A？”**

这正是这个案例中 AI 最重要的失败点。

---

## 16. 本段核心工作流与原则

```text
人类已有知识
      ↓
明确研究 / 工程目标
      ↓
识别 Big Picture
      ↓
拆出局部可验证任务
      ↓
给 Agent 明确 Context
      ↓
持续执行
      ↓
持续 Verify
      ↓
不断检查局部结果是否仍然服务于整体目标
```

最重要的原则是：

$$
\boxed{ \text{Local Verifier} \neq \text{Global Goal} }
$$

因此在 Long-Horizon Task 中，除了问：

> **“这一步做对了吗？”**

还必须不断问：

> **“这一步为什么值得做？它还在服务最初的目标吗？”**

最终可以概括为：

> **生成式软件工程真正的核心，不是让 AI 替你思考所有事情，而是让你能够定义正确的方向、维护正确的 Context、设计合适的 Verifier，并持续检查 Agent 是否仍然在解决真正的问题。**

## Research Failure、AI 协作分工与高价值人工时间

### 1. “证明 Idea 有用”本身可能成为错误目标

前面的研究案例中，Agent 因为 Context 中有一句：

> **“我要证明这个 Idea 是有用的。”**

于是开始围绕这个目标不断优化。

它做了大量：

- 小型 Benchmark；
- 微小实验；
- 正面结论；
- 负面结论；
- 局部性能比较。

表面上看，它一直在“做研究”。

但真正的问题是：

> **这些实验并不能回答这个研究问题在真实场景中是否有价值。**

于是形成了典型的目标偏移：

$$
\text{Research Goal} \rightarrow \text{证明 Idea 有效} \rightarrow \text{构造容易证明的 Benchmark} \rightarrow \text{得到局部正面结果}
$$

而原本真正应该回答的是：

$$
\text{这个 Idea 是否解决真实问题？}
$$

---

## 2. 研究中的典型错误：Benchmark 被反过来“迎合方法”

这是一个很重要的方法论问题。

正常流程应该是：

$$
\text{真实问题} \rightarrow \text{真实场景} \rightarrow \text{合适 Benchmark} \rightarrow \text{测试方法}
$$

而案例中的流程变成：

$$
\text{已有 Idea} \rightarrow \text{寻找容易验证的 Benchmark} \rightarrow \text{证明 Idea 有效果}
$$

这会产生一种危险：

> **不是让方法接受问题的检验，而是在寻找能够支持方法的问题。**

因此，即使实验结果为正，也未必意味着研究结论成立。

---

## 3. 更合理的研究方法：从真实工具与 State of the Art 出发

纠正之后，采用的是另一种思路：

> **先使用真实工具和 State of the Art（当前最先进的方法）作为基线。**

然后选择真正困难的 Benchmark。

即使：

$$
\text{Benchmark Runtime} > \text{Time Limit}
$$

最终得到的是 **Timeout** ，也不应该简单认为：

> “实验失败了，所以没有价值。”

恰恰相反，Timeout 过程中产生的：

- 搜索路径；
- 探索状态；
- 程序结构；
- 分支行为；
- 搜索空间特征；

都可能包含非常有价值的信息。

---

### 4. Timeout 也可以是重要的研究证据

对于符号执行等搜索型系统：

```text
程序
 ↓
探索状态
 ↓
搜索路径
 ↓
搜索空间越来越大
 ↓
Timeout
```

虽然最终没有得到：

> “成功验证。”

但它可能揭示：

> **现有方法在哪些程序结构上表现特别差。**

因此：

$$
\text{Timeout} \neq \text{无结果}
$$

而可能是：

$$
\boxed{ \text{Timeout} \rightarrow \text{暴露现有方法的结构性瓶颈} }
$$

这反而可以成为后续研究的重要依据。

---

## 5. 从失败中提取研究价值

好的研究并不要求每一次实验都得到正面结果。

更重要的是：

> **失败是否帮助我们理解了问题。**

例如：

$$
\text{State of Art} \rightarrow \text{困难 Benchmark} \rightarrow \text{Timeout} \rightarrow \text{观察搜索路径} \rightarrow \text{发现瓶颈} \rightarrow \text{提出新问题}
$$

因此：

**Research Failure（研究失败）本身也可能产生 Knowledge Contribution（知识贡献）。**

关键在于：

> **失败是否揭示了新的事实、边界或机制。**

---

## 6. 为什么这个案例说明“人今天仍然非常有用”

这个案例的关键不是：

> “AI 太弱，所以 AI 没用。”

而是：

> **AI 很擅长执行明确目标，但人类仍然需要判断“这个目标到底对不对”。**

Agent 可以：

- 写代码；
- 跑 Benchmark；
- 分析结果；
- 修改实现；
- 重复实验。

但它不一定能够自动发现：

> **“我们其实把研究问题定义错了。”**

因此：

$$
\boxed{ \text{AI 擅长执行} \quad \text{人类负责方向} }
$$

尤其是在 **Open-ended Question（开放问题）** 中，这种差异非常明显。

---

## 7. 领域知识决定你能否给 AI 正确方向

如果缺乏：

- 操作系统；
- 编译器；
- 数据库；
- 算法；
- 软件工程；

等基础知识，那么你很难判断：

> AI 当前做的事情到底有没有意义。

因此：

$$
\text{Domain Knowledge} \rightarrow \text{提出正确问题} \rightarrow \text{设计正确约束} \rightarrow \text{识别错误方向}
$$

这再次说明：

> **AI 时代不是“不需要学习专业知识”，而是专业知识越来越多地用于“指导和审查 AI”。**

---

## AI 协作中的时间分配

### 8. 直接盯着 Agent，可以更快完成某些任务

实际使用 Codex 一类 Agent 时，可以采用两种模式。

#### 模式 A：主动监督

```text
Agent 执行
 ↓
人观察
 ↓
发现偏离
 ↓
立即纠正
 ↓
Agent 继续
```

对于比较明确的工程任务，这通常可以快速避免走错路。

例如：

> “实现某个交互系统功能。”

如果发现 Agent 使用了错误的架构，可以马上把自己的领域知识注入进去。

---

### 9. 放手让 Agent 长时间运行，也可能最终完成

另一种策略是：

```text
提交任务
 ↓
Agent 自己跑
 ↓
失败
 ↓
自己修
 ↓
继续尝试
 ↓
最终完成
```

只要任务足够明确，Agent 有时即使走了很多弯路，最后也能完成。

于是出现一个非常实际的 **Trade-off（权衡）** ：

$$
\boxed{ \text{人工监督成本} \leftrightarrow \text{Agent 额外 Token / 时间成本} }
$$

---

## 10. 人类的时间和 AI 的 Token 都是资源

这里有一个非常重要的资源分配问题。

人的资源是：

- 注意力；
- 时间；
- 精力；
- 判断能力。

AI 的资源则更接近：

- Token；
- 推理计算；
- 工具调用；
- 执行时间。

因此：

$$
\text{Human Time} \quad\leftrightarrow\quad \text{AI Compute}
$$

不是所有任务都值得人类全程盯着。

---

### 11. 一个实用原则：把人的时间留给 AI 不擅长的部分

如果你已经知道：

> **“这件事情应该怎么做。”**

并且：

> **“AI 基本可以把它正确做出来。”**

那么更合理的策略是：

> **把任务交给 AI，自己去做更高价值的事情。**

例如：

```text
你知道怎么做
      ↓
AI 可以可靠执行
      ↓
放手
      ↓
最后验收
```

而如果：

> **你自己都不知道方向是否正确。**

那么就应该投入更多时间：

```text
AI 给出方案
      ↓
你审查
      ↓
发现方向问题
      ↓
重新定义目标
      ↓
再让 AI 执行
```

---

## 12. “纠正 AI”会带来一种特殊的心理奖励

课程提出了一个很有意思的人类心理观察。

当你纠正 AI 时，会产生一种：

> **“虽然 AI 很厉害，但我还是有用的。”**

这种感觉本身很有满足感，甚至会带来类似 **Dopamine（多巴胺）反馈** 。

于是容易形成：

```text
Agent 犯错
 ↓
我发现问题
 ↓
我纠正它
 ↓
Agent 改对
 ↓
我获得“我比 AI 强”的心理满足
```

但这未必代表：

> **这种行为是最高价值的时间使用方式。**

---

## 13. 不要为了证明“我还有用”而过度监督 AI

另一种极端则是：

```text
YOLO Mode
 ↓
Agent 自己跑
 ↓
你去做别的事
 ↓
回来验收
```

如果 Agent 已经可以稳定完成任务，那么：

> **盯着它的每一步，并不会产生额外价值。**

所以人类应该避免把：

> **“监督 AI”**

本身变成一种新的“假努力”。

真正应该问的是：

> **我的参与能不能显著改善最终结果？**

如果不能，就应该减少参与。

---

## 14. AI 时代的“有效努力”会变得更加重要

传统软件工程里已经强调：

> **不要假努力，要做有效努力。**

AI 时代这一点会更加明显。

因为一个人一天能投入的时间依然有限，而 AI 可以替你执行大量机械工作。

因此真正稀缺的是：

$$
\text{Human Judgment}
$$

而不是：

$$
\text{Typing / Repetition}
$$

如果你的同龄人把时间全部投入到：

- 学习新知识；
- 建立判断力；
- 研究问题；
- 理解系统；

而你却把大量时间花在：

- 盯 Agent；
- 反复改一些 AI 能自己解决的问题；
- 追求“我必须亲自做”；

那么差距可能会被进一步放大。

---

## 长 Context 下的指令遵循

### 15. Context 越长，Instruction Following 往往会下降

课程最后再次回到 Context Engineering。

随着：

$$
|\text{Context}| \uparrow
$$

模型的指令遵循能力可能出现一定程度的下降。

尤其是：

> **位于 Context 中间位置的指令，更容易被忽略。**

可以粗略理解为：

```text
Context 开头
   ↓
指令
   ↓
大量内容
   ↓
中间指令 ← 更容易被忽视
   ↓
大量内容
   ↓
最后指令 ← 往往更容易被遵循
```

因此，Context 中信息的位置本身也可能影响模型行为。

---

### 16. 但即使存在长 Context 问题，Agent 仍然非常有用

一个重要的观察是：

> **虽然早期 / 中间指令的遵循能力可能下降，但模型对于当前最后给出的任务往往仍然具有很强的执行能力。**

所以实际工程中：

> **把当前最重要、最具体的工作要求放在靠近任务执行的位置，通常更容易得到稳定结果。**

这与前面“让 Agent 每阶段只处理一个明确目标”的思路是一致的。

---

## 17. 本段核心原则

#### **① 不要让局部 Verifier 定义整个研究目标**

$$
\text{证明 A 有用} \not\Rightarrow \text{A 对整个问题有意义}
$$

必须始终回到 **Big Picture（整体问题）** 。

#### **② 真实 Benchmark 比容易成功的 Benchmark 更有价值**

哪怕：

$$
\text{Benchmark} \rightarrow \text{Timeout}
$$

只要能揭示现有方法的瓶颈，它仍然可能是重要结果。

#### **③ 把领域知识注入 AI，而不是把所有判断交给 AI**

$$
\text{Human} \rightarrow \text{Problem Definition + Direction}
$$

$$
\text{AI} \rightarrow \text{Execution + Search + Iteration}
$$

#### **④ 人工监督和 AI 自主运行之间存在资源权衡**

$$
\text{Human Attention} \leftrightarrow \text{AI Compute}
$$

应该把人的精力投入到 **只有人才能高价值完成的事情** 上。

#### **⑤ 避免把“纠正 AI”变成假努力**

判断标准不是：

> “我有没有参与？”

而是：

> **“我的参与是否显著提高了最终结果？”**

#### **⑥ 长 Context 需要关注指令位置**

$$
\text{Context 越长} \rightarrow \text{指令竞争越强}
$$

尤其要警惕中间位置的重要指令被忽略。

---

### 18. 最核心的一条工作哲学

可以把整段内容压缩成：

$$
\boxed{ \text{人类负责决定“做什么、为什么做、什么算重要”} }
$$

$$
\boxed{ \text{AI 负责在明确方向下“怎么做、怎么试、怎么改、怎么跑”} }
$$

真正高效的 AI 协作，不是：

> **让人和 AI 一起做所有事情。**

而是：

> **把人的有限时间投入到方向、判断、知识和价值选择，把可以验证、可以重复、可以自动迭代的工作尽可能交给 AI。**

## Long-Horizon 搜索、算力换智力与群体智能

### 1. 当前模型最擅长的是“短窗口、明确任务”

长 Context 下，虽然早期或中间位置的指令可能更容易被忽略，但如果最后一个窗口给出了一个 **明确、具体、可执行的任务** ，模型通常仍然能够很好地完成。

例如：

> “帮我把这个 Bug 修掉。”

这种任务具有：

- 明确目标；
- 明确输入；
- 相对有限的搜索空间；
- 通常可以通过测试或运行结果验证。

因此：

$$
\boxed{ \text{短窗口} + \text{明确任务} + \text{Verifier} \rightarrow \text{Agent 很擅长} }
$$

这也是为什么目前的 Agent 仍然非常值得使用。

---

## 2. 真正困难的是“不确定的探索问题”

但如果任务变成：

> **“帮我考虑几种方案，哪个最好？”**

性质就发生了变化。

这不再只是：

$$
\text{已知问题} \rightarrow \text{寻找可验证解}
$$

而变成：

$$
\text{不确定空间} \rightarrow \text{探索} \rightarrow \text{比较多个可能方向} \rightarrow \text{选择最优方案}
$$

这里缺少一个简单明确的 Verifier。

因此，当前模型更容易出现：

> **给出一个“还不错”的方案，而不是经过充分搜索后真正最好的方案。**

---

## 3. 为什么模型倾向于给出“能完成”的方案

模型经过后训练和强化学习后，一个很强的行为倾向是：

> **尽可能完成用户交给它的任务。**

可以粗略理解为：

$$
\text{完成任务} \rightarrow \text{Reward}
$$

因此如果用户要求：

> “请给我一个解决方案。”

模型更容易倾向于：

$$
\text{找到一个可行解}
$$

而不是：

$$
\text{搜索整个方案空间} \rightarrow \text{证明它是最优解}
$$

后者通常需要大量额外计算。

于是出现：

> **模型更像是在考试快交卷时，尽快写出一个有希望得分的答案。**

---

## 4. P 与 NP：为什么“验证容易，寻找困难”

这个现象可以用经典的 **P vs NP** 直觉帮助理解。

在很多问题中：

$$
\text{给定一个候选解} \rightarrow \text{验证它}
$$

可能比较容易。

但：

$$
\text{从巨大搜索空间中} \rightarrow \text{找到一个满足条件的解}
$$

可能非常困难。

例如 **Hamiltonian Path（哈密顿路径）** ：

给你一条具体路径，检查它是不是哈密顿路径相对容易。

但：

> **从一个大型图中找到一条满足要求的哈密顿路径**

则可能需要巨大的搜索量。

因此：

$$
\boxed{ \text{Verification Easy} \neq \text{Search Easy} }
$$

这也是 Agent 面对开放问题时的根本困难之一。

---

## 5. 对开放问题，模型必须在有限计算预算内做搜索

如果：

$$
\text{Search Space} \gg \text{Available Compute}
$$

那么模型不可能真正穷举所有可能性。

它只能：

- 选择一些可能方向；
- 利用自己的训练经验；
- 进行有限搜索；
- 给出一个看起来合理的结果。

因此最终结果实际上是：

$$
\text{Model Prior} + \text{Limited Search} \rightarrow \text{Candidate Solution}
$$

这意味着：

> **模型给出的“最好方案”，很多时候更准确地说是“在有限计算和已有偏见下找到的一个较优方案”。**

---

## 6. 算力换智力：扩大搜索空间

如果希望提高结果质量，一个直接的方法就是：

> **增加推理时的计算量。**

即：

$$
\boxed{ \text{More Compute} \rightarrow \text{More Search} \rightarrow \text{More Candidates} \rightarrow \text{Better Result} }
$$

这可以称为：

**Compute for Intelligence（用算力换智力）** 。

具体可以从：

```text
一次尝试
```

变成：

```text
方案 1
方案 2
方案 3
……
方案 N
```

然后：

$$
\text{Candidates} \rightarrow \text{Evaluate} \rightarrow \text{Select}
$$

这样得到更好答案的概率会更高。

---

## 7. 举例：AI 起名为什么容易同质化

例如让 AI 给一个产品起名字。

模型可能给出一个：

> 很自然、很专业、很像优秀品牌的名字。

但问题是：

> **很多人都在使用相似的模型。**

于是不同用户可能得到：

- 相似的词；
- 相似的音节；
- 相似的文化来源；
- 相似的命名风格。

这就产生了：

**AI 同质化。**

也就是说：

$$
\text{同一个模型} + \text{相似 Prompt} \rightarrow \text{相似结果}
$$

所以“AI 觉得好”并不等于：

> **“这个名字对我来说足够独特。”**

---

## 8. 系统性调研可以克服模型默认偏见

如果真的需要一个高质量、独特的名字，更好的方法不是：

> “再问模型一次。”

而是建立一个系统性的搜索流程。

例如：

```text
候选音节 / 词根
      ↓
枚举大量候选
      ↓
筛掉不喜欢的音
      ↓
得到候选集合
      ↓
Subagent 逐个检查
      ↓
检查语义、文化、来源、重复度
      ↓
人工筛选
```

这与科研中的 **Literature Review（文献调研）** 很类似：

$$
\text{先穷尽相关空间} \rightarrow \text{再比较} \rightarrow \text{最后选择}
$$

而不是：

$$
\text{随机问 AI 一次} \rightarrow \text{直接接受结果}
$$

---

## 9. “算力换智力”的关键：把大问题切成许多小问题

开放问题的困难来自：

$$
\text{Search Space 很大}
$$

一个有效的方法是进行 **Decomposition（问题分解）** 。

例如：

```text
开放问题
   ↓
拆成很多候选方向
   ↓
每个方向变成一个明确的小任务
   ↓
分别验证
   ↓
综合结果
```

这样每个子问题就可以重新拥有：

- 更明确的 Spec；
- 更明确的 Verifier；
- 更有限的搜索空间。

于是：

$$
\text{Open Problem} \rightarrow \text{Many Verifiable Subproblems}
$$

这会显著提高 Agent 的有效搜索能力。

---

## 10. Subagent 是扩大搜索预算的一种方式

例如一个名字生成任务，可以让多个 Subagent 分别负责：

```text
Agent A：寻找英文候选
Agent B：寻找古典来源
Agent C：检查读音
Agent D：检查语义
Agent E：检查重复 / 冲突
```

然后再让一个更高层 Agent：

$$
\text{Candidate Results} \rightarrow \text{Comparison} \rightarrow \text{Final Selection}
$$

这样相当于把：

$$
\text{一个有限搜索过程}
$$

扩展成：

$$
\text{多个并行搜索过程}
$$

从而提高总体计算预算。

---

## 11. 但代价是 Token 和 Compute 会迅速增加

“算力换智力”不是免费的。

如果：

$$
N_{\text{candidate}} \uparrow
$$

那么：

$$
\text{Token Cost} \uparrow
$$

同时：

$$
\text{Latency} \uparrow
$$

因此仍然存在一个 Trade-off：

$$
\boxed{ \text{Search Quality} \leftrightarrow \text{Compute Cost} }
$$

对于值得投入的任务，可以花更多算力。

对于普通任务，则没有必要进行如此昂贵的穷举。

---

## 人类为什么仍然具有不可替代的群体优势

### 12. 人类最大的优势之一，是巨大的“世界样本空间”

课程进一步提出一个非常有意思的视角：

> **世界很大，而单个人很小。**

每个人接触到的东西都有限。

但每个人都有不同的：

- 城市；
- 教育背景；
- 家庭环境；
- 生活经历；
- 朋友圈；
- 兴趣；
- 专业；
- 文化背景。

因此每个人都带有自己的 **Bias（偏置）** 。

---

### 13. Bias 不完全是缺点，它也是创造多样性的来源

假设所有人都接受完全一样的数据：

$$
\text{Same Data} \rightarrow \text{Same Prior} \rightarrow \text{Same Output}
$$

那么整个群体会变得非常同质化。

而现实世界中：

$$
\text{不同人的经历} \rightarrow \text{不同 Bias} \rightarrow \text{不同判断} \rightarrow \text{不同探索方向}
$$

因此，人的“偏见”在一定程度上也是：

> **产生多样性的重要来源。**

---

## 14. 群体智慧来自不同个体的有限认知

一个非常重要的观点是：

> **单个人的认知有限，但很多具有不同背景的人组合起来，可以形成远超个人的群体智慧。**

可以表示为：

$$
\boxed{ \text{Many Different Human Priors} \rightarrow \text{Diverse Search} \rightarrow \text{Collective Intelligence} }
$$

也就是说：

> 人类并不需要每个人都知道整个世界，只需要不同的人分别探索不同区域，然后通过社会协作把这些知识组合起来。

---

## 15. AI 可能带来的新问题：算力的不平等

如果未来：

$$
\text{AI Compute} \rightarrow \text{Search Capability} \rightarrow \text{Effective Intelligence}
$$

那么一个非常值得思考的问题就出现了：

> **如果少数人能够获得远超其他人的 AI 计算资源，会发生什么？**

假设：

$$
\text{Intelligence} \propto \text{Available Compute}
$$

那么拥有无限计算资源的一方，就可能不断：

- 生成更多候选；
- 进行更多验证；
- 探索更多方案；
- 运行更多 Agent；
- 获得更快的反馈。

这可能形成巨大的能力差距。

---

## 16. “墙内”和“墙外”的极端设想

课程用了一个非常极端的思想实验：

```text
             计算资源
                ↓
       ┌─────────────────┐
       │  高算力 / 高 AI   │
       │      人群        │
       └─────────────────┘
                │
                │ 巨大能力差距
                ↓
       ┌─────────────────┐
       │  普通算力 / 普通人 │
       └─────────────────┘
```

如果 AI 的有效智能可以随着计算资源不断增长，那么获得无限计算的一方可能形成：

> **一个能力越来越高的“墙内世界”。**

而墙外的人由于计算资源不足，无法追上墙内的知识和决策速度。

极端情况下：

$$
\text{Compute Gap} \rightarrow \text{Intelligence Gap} \rightarrow \text{Power Gap}
$$

最终产生一种非常不平等的结构。

---

## 17. 为什么这是 AI 时代值得提前思考的问题

这个思想实验真正重要的地方不在于“墙”的字面含义，而在于：

> **如果智能越来越能够被计算资源放大，那么“谁拥有多少计算资源”可能成为一种新的核心社会资源。**

过去：

$$
\text{Knowledge} \approx \text{人的学习能力}
$$

未来可能逐渐变成：

$$
\text{Effective Intelligence} \approx f( \text{Model}, \text{Compute}, \text{Data}, \text{Search} )
$$

因此 AI 带来的问题不仅是：

> **“模型能不能变得更聪明？”**

还包括：

> **“谁能够获得这种更强的智能，以及这种差距会不会不断扩大？”**

---

## 18. 本段核心逻辑

```text
明确任务 + Verifier
        ↓
AI 非常擅长
        ↓
如果问题变成开放探索
        ↓
搜索空间巨大
        ↓
单次 Next Token Prediction 不够
        ↓
需要增加 Test-Time Compute
        ↓
把大问题拆成多个小问题
        ↓
并行搜索 + 多轮验证
        ↓
算力换智力
```

与此同时：

```text
人类
 ↓
每个人拥有不同经历和 Bias
 ↓
产生不同探索方向
 ↓
组合形成群体智慧
```

于是出现一个未来问题：

$$
\boxed{ \text{如果算力可以持续转化为智能} }
$$

那么：

$$
\boxed{ \text{Compute Inequality} \rightarrow \text{Intelligence Inequality} }
$$

这可能成为 AI 时代非常重要的社会问题。

---

### 19. 最核心的几个结论

#### **① 当前 Agent 最强的是“可验证的任务”**

$$
\text{明确目标} + \text{Verifier} \rightarrow \text{高成功率}
$$

#### **② 真正的 Long-Horizon Open Problem 难在“搜索”**

$$
\text{找到一个解} \neq \text{找到最好解}
$$

#### **③ 可以通过算力换智力**

$$
\text{More Compute} \rightarrow \text{More Search} \rightarrow \text{Better Solution}
$$

但代价是：

$$
\text{Token / Time / Cost} \uparrow
$$

#### **④ 把开放问题拆成很多可验证的小问题，是提升 AI 能力的关键方法**

$$
\boxed{ \text{Open Problem} \rightarrow \text{Decomposition} \rightarrow \text{Verifiable Subproblems} \rightarrow \text{Parallel Search} }
$$

#### **⑤ 人类的多样性本身是一种智能资源**

不同人的经历和 Bias：

$$
\text{Diversity} \rightarrow \text{Different Priors} \rightarrow \text{Collective Intelligence}
$$

#### **⑥ AI 时代值得警惕“计算资源 → 智力”的不平等**

如果这种关系不断增强：

$$
\boxed{ \text{Compute} \rightarrow \text{Intelligence} \rightarrow \text{Capability} }
$$

那么谁拥有计算资源、谁能获得更强的 Agent，可能逐渐成为决定能力差距的关键因素。
