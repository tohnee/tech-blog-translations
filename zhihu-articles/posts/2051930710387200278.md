### 问题 1：TorchMemorySaver vs expandable_segments 冲突

### 现象

```text
RuntimeError: TorchMemorySaver is disabled for the current process
              because expandable_segments is not supported yet.
```

8 个 sglang TP scheduler 全部初始化失败，job FAILED。

### 根因

`runtime_env.yaml` 设置：

```text
PYTORCH_CUDA_ALLOC_CONF: "max_split_size_mb:1024,expandable_segments:True"
```

而 `--colocate --offload` 模式下 sglang 用 `TorchMemorySaver` 在不用 GPU 时 sleep 推理权重到 CPU。`TorchMemorySaver._sanity_checks()` 在初始化时检测到环境变量含 `expandable_segments:True` 就直接 raise：

```python3
# torch_memory_saver/entrypoint.py:197
def _sanity_checks():
    if "expandable_segments:True" in os.environ.get("PYTORCH_CUDA_ALLOC_CONF", ""):
        raise RuntimeError(
            "TorchMemorySaver is disabled for the current process because "
            "expandable_segments is not supported yet."
        )
```

### 修复

`runtime_env.yaml`:

```text
# 删掉 expandable_segments:True
PYTORCH_CUDA_ALLOC_CONF: "max_split_size_mb:1024"
```

### 教训

- TorchMemorySaver 用 cuda virtual memory 自己管理虚拟地址映射，跟 PyTorch 的 expandable_segments 互斥
- 任何用 `enable_memory_saver=True`（colocate 模式必开）的进程都不能用 `expandable_segments:True`
- 后期 megatron 训练 OOM 时 PyTorch 会建议 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` 解决碎片，但**只要还在 colocate 模式就不能加**

### 问题 2：filter_long_prompt 单线程慢（误判 hang）

### 现象

启动后 10 分钟没有日志输出，看起来 hang 住。py-spy 显示主线程在：

```text
Thread 40883 (active+gil): "MainThread"
    filter_long_prompt (slime/utils/data.py:103)
    __init__ (slime/utils/data.py:267)
    __init__ (slime/rollout/data_source.py:71)
    __init__ (slime/ray/rollout.py:390)
```

### 根因

不是 hang，而是 **slime 在加载完 prompt 数据后，单线程用 tokenizer 逐条编码所有 prompt 来过滤超长样本**：

```text
# slime/utils/data.py:103
input_ids_list = tokenizer(prompts, add_special_tokens=False)["input_ids"]
```

20 万行 prompt × 平均几千 token，`HuggingFaceTokenizer` 单线程跑了大概 **8 分钟**。最后输出：

```text
[2026-06-19 23:23:57] data.py:125 - Filtered 60067 samples longer than max_length=11000.
```

### 教训

- 启动慢不一定是 hang，先用 `py-spy dump` 看主线程栈，区分死锁 vs 单线程慢循环
- 这个 8 分钟会在每次启动重复，可考虑离线预过滤数据集
- 标志：CPU 100% 但 GPU 0%，stack 在 python 用户代码 = 在跑 python 慢循环

### 问题 3：FlashInfer AllReduce Fusion 在 sm100 上 rendezvous 死锁

### 现象

8 个 sglang scheduler 在 GPU 已加载完权重 + KV cache 后，CPU 90% 但 GPU 0%，**11 分钟无日志**。py-spy 栈：

```text
Thread 87266 (active+gil): "MainThread"
    rendezvous (torch/distributed/_symmetric_memory/__init__.py:1991)
    _alloc_symm_buffer_bytes (flashinfer/comm/torch_symmetric_memory.py:71)
    trtllm_create_ipc_workspace_for_all_reduce_fusion (flashinfer/comm/trtllm_ar.py:658)
    create_allreduce_fusion_workspace (flashinfer/comm/allreduce.py:413)
    flashinfer_allreduce_residual_rmsnorm (flashinfer_comm_fusion.py:672)
    forward (qwen3_5.py:652)
    _flashinfer_autotune (model_runner.py:2672)
```

### 根因

sglang 在 sm100 (B200) 上**自动启用 `enable_flashinfer_allreduce_fusion=True`**，触发 `flashinfer.comm.trtllm_ar.trtllm_create_ipc_workspace_for_all_reduce_fusion`，这个函数内部调用 `torch._C._distributed_c10d._SymmetricMemory.rendezvous()` 进行跨进程 IPC handle 握手。

在 colocate 容器环境下，CUDA IPC namespace 可能不对，握手永远不会完成。

日志佐证：

```text
[2026-06-19 23:24:30] Auto-enabling FlashInfer AllReduce Fusion on SM90/SM10X
                      for Qwen3_5MoeForConditionalGeneration
```

### 修复

```text
# SGLANG_ARGS:
--sglang-enforce-disable-flashinfer-allreduce-fusion
```

加上后日志显示：

```text
FlashInfer allreduce fusion is forcibly disabled via
--enforce-disable-flashinfer-allreduce-fusion.
```

随后 autotune 3 秒就过了。

### 教训

- sglang 在 B200 上自动启用的 fusion 不一定都能 work，特别是涉及 IPC 的
- py-spy 栈显示 `rendezvous` + CPU 100% + GPU 0% = IPC 握手死锁
- `enable_torch_symm_mem=False` 这个开关名误导，不影响 flashinfer 内部的 symm_mem 调用

### 问题 4：Custom AllReduce v2 + CUDA Graph capture 失败

### 现象

修了问题 3 后，下一次启动到 cuda graph capture 阶段：

```text
Capturing batches (bs=1 avail_mem=49.28 GB): 100%|██████████| 35/35 [00:14<00:00]
[TP3] Scheduler hit an exception: Traceback (most recent call last):
  ...
  File "cuda_graph_runner.py", line 626, in __init__
    self.capture()
  File "parallel_state.py", line 533, in graph_capture
    with self.device_module.stream(stream), maybe_ca_context:
  File "custom_all_reduce_v2.py", line 102, in capture
    pairs = self.obj.share_graph_inputs()
tvm.error.InternalError: Runtime check failed at
  /sgl-workspace/sglang/python/sglang/jit_kernel/include/sgl_kernel/distributed/custom_all_reduce.cuh:37:
  CUDA error: invalid argument
```

### 根因

35 个 batch sizes 的 cuda graph **都 capture 完了**，但在退出 graph capture context manager 时，`custom_all_reduce_v2.share_graph_inputs()` 要把 IPC handle 注册给所有 graph buffer，这一步失败 — 跟问题 3 同源（CUDA IPC 在环境下不工作）。

### 修复

```text
# SGLANG_ARGS:
--sglang-disable-custom-all-reduce
```

让 sglang 走标准 NCCL allreduce 路径，不用 sgl-kernel 自家的 IPC 实现。

### 教训

- sglang 在 B200 上有两条 IPC allreduce 路径：flashinfer fusion 和 sgl-kernel custom_all_reduce_v2
- 容器 IPC 有问题时**两条都要关**
- 性能成本：~3% 推理 throughput

### 问题 5：MoE 权重 layout 不匹配（64 vs 2048）

### 现象

修了问题 3+4 后，sglang 启动成功，开始训练。**第一个 RL step 的 update_weights** 阶段：

```text
RuntimeError: The size of tensor a (64) must match the size of tensor b (2048)
              at non-singleton dimension 2
File "sglang/srt/layers/moe/fused_moe_triton/layer.py:490" _load_w13
    expert_data.copy_(loaded_weight)
```

### 根因

sglang 在 sm100 上**自动选择 `moe_runner_backend=flashinfer_trtllm`** 作为 MoE backend：

```text
[Use flashinfer_trtllm as MoE runner backend on sm100 for Qwen3_5MoeForConditionalGeneration]
```

flashinfer_trtllm MoE backend 期望的 expert weight layout 是”每个 expert 独立的 64 列”，而 Megatron 端 `update_weights_from_tensor` 传过来的是”32 个 local experts 拍平成 2048 列”（`64 × 32 = 2048`，对应 `EP=8` 时每 rank 32 个 expert）。

### 修复

```text
# SGLANG_ARGS:
--sglang-moe-runner-backend triton
```

强制 sglang 用 triton MoE backend，跟 Megatron 传过来的 layout 兼容。

### 教训

- sglang 在 sm100 上自动选 flashinfer_trtllm，但跟 slime/Megatron 的 weight transfer 路径不兼容
- standalone 测试 sglang 加载 hf_checkpoint 不会触发这个问题（只有 train→sglang weight sync 才会）
- 性能成本：MoE GEMM 慢 ~10%，但稳定

### 问题 6：训练阶段 OOM 之 train_memory_margin 过大

### 现象

训练侧 actor train 阶段持续 OOM 重试：

```text
[torch_memory_saver.cpp] TorchMemorySaver::malloc return OOM
  since memory_margin_bytes=4294967296 (alloc)size=524288000 free_bytes=4420337664
  [repeated 126x across cluster]
```

最终 RayTaskError(OutOfMemoryError)。

### 根因

`--train-memory-margin-bytes 4294967296`（4GB） + 同时关掉 recompute + 开 vp=4 三个改动叠加。`memory_margin` 是 TorchMemorySaver 给 sglang sleep/resume 预留的”安全边界”，调到 4GB 后训练侧实际可用显存少了 4GB，加上其他改动让 activation 涨了，OOM。

### 修复

```text
# 改回默认 1GB
--train-memory-margin-bytes 1073741824
```

### 教训

- `train-memory-margin-bytes` 用来给 sglang resume 预留显存避免冲突；调大 = 训练侧可用显存减少
- B200 显存大但不是无限，多个改动叠加要谨慎
- **每次只改一个变量**，OOM 才能定位是哪个改动导致的

### 问题 7：训练阶段 OOM 之 cross-entropy fp32 临时张量

### 现象

```text
torch.OutOfMemoryError: CUDA out of memory. Tried to allocate 15.16 GiB.
GPU 0 has 178.35 GiB total of which 12.53 GiB is free.

栈：transformer/module.py:406 float_conversion
    val = val.float()    ← bf16 → fp32 升精度
```

### 根因

```text
--accumulate-allreduce-grads-in-fp32   # ← 触发
--attention-softmax-in-fp32
cross_entropy_loss_fusion=False        # ← 默认关，是 OOM 主因
```

LM head logits shape：`[microbatch_tokens, vocab/TP] = [N, 124160]`

- bf16 logits = N × 124160 × 2 bytes
- 升 fp32 翻倍 = N × 124160 × 4 bytes
- 加上 softmax + log_softmax 中间张量，峰值 ~30-40 GB

unfused cross-entropy 会**实例化**完整的 fp32 logits + softmax + log_softmax 中间张量。

### 修复

```text
# MISC_ARGS:
--cross-entropy-loss-fusion
--cross-entropy-fusion-impl te
```

TE 实现的 fused cross-entropy 把 logits → softmax → log → loss 合成单 kernel，**不实例化中间张量**，那 15 GB 直接消失。

### 教训

- 大 vocab (>100k) 模型在 PP stage 1 / forward 末尾的 logits buffer 是显存大头
- `--accumulate-allreduce-grads-in-fp32 + --attention-softmax-in-fp32` 单独不会 OOM，但会让 caller 在 backward 路径上做 bf16→fp32 升级，跟 unfused CE 叠加触发 OOM
- 任何 vocab > 50000 的模型都应默认开 `--cross-entropy-loss-fusion`

### 问题 8：节点 1 vs 节点 2 显存严重不均衡

### 现象

成功跑起来后观察：

```text
Node 1 (PP stage 0, layers 0-19):    107362 MiB / 183359 MiB
Node 2 (PP stage 1, layers 20-39):   157362 MiB / 183359 MiB  ← 86% 满，余量小
```

### 根因（叠加 3 个因素）

1. **PP stage 1 持有更多组件**：embedding + LM head + loss
2. **1F1B schedule stage 1 持有更多 in-flight microbatch activation**
3. **EP 路由不均衡**：256 expert / EP=8 没开 aux loss → 少数热门 expert 把某些 rank 推高

### 修复

```text
# PERF_ARGS:
--account-for-loss-in-pipeline-split        # PP 自动重平衡，让 stage 1 少装一层
--account-for-embedding-in-pipeline-split

# MISC_ARGS:
--moe-aux-loss-coeff 0.001                  # 轻微的 expert 负载均衡损失
```

预期 Node 2 显存从 157 GB → ~135-145 GB。

### 教训

- 对 35B-A3B 这种 vocab 大 + MoE 多 expert 的模型，PP 必须开 `--account-for-*-in-pipeline-split` 才能均衡
- aux_loss_coeff=0.001 对 reward 影响小但对显存均衡贡献大
- 如果自动重平衡不够，用手动 `--decoder-last-pipeline-num-layers 18` 进一步减少 stage 1 的 layer 数

### 问题 9：overlap-grad-reduce 与 slime no_sync_func 冲突

### 现象

```text
AssertionError: When overlap_grad_reduce is True,
                config.no_sync_func must be None;
                a custom no_sync_func is not supported when overlapping grad-reduce

位置：slime/backends/megatron_utils/model.py:660
```

### 根因

slime 在训练时给 megatron config 设了 `no_sync_func`（用于跳过 DDP grad sync 的某些 microbatch），跟 megatron 的 `--overlap-grad-reduce` 冲突，slime 自己显式 raise。

### 修复

```text
# PERF_ARGS:
#--overlap-grad-reduce         # 注释掉
--overlap-param-gather         # 这个 OK 保留
```

`overlap-param-gather` 走的是 forward 前的参数 all-gather，不依赖 no_sync_func，所以 OK。

### 教训

- 框架集成层经常有这种”互斥但 megatron 文档不写”的约束
- 加 megatron 优化选项时要先 grep 一下 slime 源码看有没有 explicit assert

### 问题 10：Mamba radix cache ping-pong donate illegal memory access

### 现象

`partial-rollout` 模式下，跑了 2-3 个 rollout 后崩：

```text
File "mamba_radix_cache.py:654" cache_unfinished_req
  → mamba_value_donated = self.req_to_token_pool.donate_mamba_ping_pong_slot(...)
File "memory_pool.py:697" donate_mamba_ping_pong_slot
  → assert mamba_value_donated.item() != -1
torch.AcceleratorError: CUDA error: an illegal memory access was encountered
```

8 个 TP rank 集体崩溃。后续 `flush_cache` HTTP 请求 timeout，连锁导致 `RolloutManager.offload()` 失败。

### 根因

Qwen3.5-A3B 是 hybrid mamba/linear-attention 模型，sglang 用 mamba ping-pong slot（双 buffer 轮换）来支持 overlap schedule。`partial-rollout` 让请求在中途被 pause/resume，触发 `cache_unfinished_req → donate_mamba_ping_pong_slot` 路径。

`mamba_ping_pong_track_buffer_size = 2 if enable_overlap_schedule else 1`

在 sglang 0.6.12 的 V2 spec + extra_buffer + EAGLE + partial-rollout 组合下，这条路径有 race condition。slot 还没初始化就被读，导致 `mamba_value_donated.item() == -1`，进而触发 CUDA illegal memory access。

### 尝试过的失败修复

| 尝试 | 结果 |
| --- | --- |
| SGLANG_ENABLE_SPEC_V2=1 | 无效（默认就是 True） |
| --mamba-scheduler-strategy no_buffer | 拒绝：”no_buffer + radix cache + speculative decoding 不兼容” |
| --mamba-scheduler-strategy extra_buffer + --disable-radix-cache | 拒绝：”extra_buffer 不能和 disable-radix-cache 一起用” |

### 最终修复

sglang 给出的官方推荐组合：

```text
--sglang-disable-radix-cache
--sglang-mamba-scheduler-strategy no_buffer
```

代价：失去 prefix cache hit（之前 ~49%），rollout 慢约 15%。

### 教训

- sglang 0.6.12 在 Qwen3.5 hybrid mamba 上的 partial-rollout 路径有已知 bug
- 错误信息里的”修复建议”有时候会误导（说”用 V2 + extra_buffer”但其实就是 bug 本身）
- 兼容性矩阵：`speculative + radix_cache` 必须 `extra_buffer`，`disable_radix_cache` 必须 `no_buffer`，两组组合二选一

### 问题 11：sglang overlap schedule 异步 CUDA 错误

### 现象

修了问题 10 后还崩，崩点变了：

```text
File "scheduler.py:3021" run_batch
  → future_map.resolve_seq_lens_cpu(batch)
  File "overlap_utils.py:232" resolve_seq_lens_cpu
  → fwd_prepare_d2h_stream.synchronize()
torch.AcceleratorError: CUDA error: an illegal memory access was encountered

提示：CUDA kernel errors might be asynchronously reported at some other API call
```

### 根因

CUDA 错误是异步报告的：真正出错的 kernel 可能是几百毫秒前 launch 的，但要等到下一次 stream synchronize 才被发现。这次崩点是 `synchronize()`（overlap schedule 的 D2H 流同步）。

也就是 **EAGLE + overlap schedule + Qwen3.5 hybrid mamba** 组合中某个 kernel 触发了 illegal memory access。

### 修复尝试

```text
--sglang-disable-overlap-schedule
```

让 sglang 用 `event_loop_normal` 而不是 `event_loop_overlap`。

### 后续

仍然崩，问题真凶是 EAGLE（见问题 12）。但即使关掉 overlap schedule 也是必要的，因为 EAGLE 关掉后再开 overlap 可能也会出别的问题。

### 教训

- CUDA 异步错误调试很难，stack trace 经常指向无关位置
- `CUDA_LAUNCH_BLOCKING=1` 能定位真凶但会让训练慢 30-50%
- 在调试期可以暂时关 overlap schedule，性能换可见性

### 问题 12：EAGLE draft cuda graph replay illegal memory access

### 现象

关 overlap schedule 后崩点变成：

```text
File "scheduler.py:3095" run_batch
  → self.model_worker.forward_batch_generation(batch)
File "eagle_worker_v2.py:425" draft
  → self.cuda_graph_runner.replay(forward_batch)
File "eagle_draft_cuda_graph_runner.py:255" _replay
  → self.graphs[self.bs].replay()
torch.AcceleratorError: CUDA error: an illegal memory access was encountered
```

明确崩在 EAGLE draft model 的 cuda graph replay。

### 关键观察

```text
rollout/spec_accept_rate: 0.0    ← EAGLE 接受率是 0%！
rollout/spec_accept_length: 2.25 ← draft 跑了 2.25 步但全部被拒绝
```

**EAGLE 在这环境上完全没有加速效果，反而每次还要跑 2.25 个 draft step 浪费算力**。

### 根因

EAGLE + sglang 0.6.12 + Qwen3.5 hybrid mamba + trtllm_mha attention backend 的组合：

- spec_accept_rate=0% 说明 draft model 的 logits distribution 跟 target model 完全对不上（可能是 MTP 权重加载问题或 attention backend 不兼容）
- draft cuda graph 在 partial-rollout 触发的某些 batch_size 下 replay 出错

### 修复

```text
# SGLANG_ARGS - 注释掉所有 EAGLE 参数
#--sglang-speculative-algorithm EAGLE
#--sglang-speculative-num-steps 2
#--sglang-speculative-eagle-topk 1
#--sglang-speculative-num-draft-tokens 3
```

性能成本：本来就没加速，关掉反而省去 EAGLE 自身 overhead，**速度可能略快**。

### 教训

- 检查 `rollout/spec_accept_rate` 是验证 EAGLE 是否生效的关键指标
- spec_accept_rate=0 + 仍然崩 = 这个版本的 EAGLE 在模型/环境上不可用
- MTP/EAGLE 是性能优化，不是必需功能，崩了直接关掉

### 问题 13：actor train 阶段 entropy 计算 OOM (最终 OOM)

### 现象

终于跑通后，actor train 阶段在第一个 train step 崩：

```text
File "slime/utils/ppo_utils.py:173" forward
    normalized_vocab_parallel_logits = vocab_parallel_logits - logits_max
                                       ~~~~~~~~~~~~~~~~~~~~~~^~~~~~~~~~~~
torch.OutOfMemoryError: CUDA out of memory. Tried to allocate 19.78 GiB.
GPU 1 has 178.35 GiB total, 5.98 GiB free, allocated 157.06 GiB.
```

### 根因

slime 计算 entropy 的路径：

```text
# slime/utils/ppo_utils.py:165 _VocabParallelEntropy.forward
logits_max = vocab_parallel_logits.max(dim=-1, keepdim=True).values
normalized_vocab_parallel_logits = vocab_parallel_logits - logits_max  # ← 这里 alloc 19.78GB
```

`vocab_parallel_logits` shape `[T, V/TP] = [40k, 124160]`，bf16 ~10 GB， “减法”会创建一个**完全相同大小的新张量**，又是 ~10 GB； fp32 路径下 ~20 GB。

加上 sglang sleep 后还占的 5 GB + 训练 145 GB + 碎片 7 GB，差一点就够。

### 修复方案分析

研究 slime 源码发现：**slime 已经实现了 chunk 机制 + with_entropy 开关**：

```text
# slime/utils/ppo_utils.py:649
def calculate_log_probs_and_entropy(logits, tokens, tp_group,
                                     with_entropy=False, chunk_size=-1):
    if chunk_size > 0:
        num_chunks = (logits.size(0) - 1) // chunk_size + 1
        logits_chunks = logits.chunk(num_chunks, dim=0)
        # 沿 seq 维度切 chunk 循环算
```

但默认 `chunk_size=-1`（不启用），且 `policy_loss_function` 强制传 `with_entropy=True`。

### 修复（方案 P0：零代码改动）

```text
# MISC_ARGS:
--log-probs-chunk-size 1024
```

效果：`[40k, 124160]` → 切成 40 个 `[1024, 124160]`chunk 循环算，单次 alloc 从 19.78 GB → ~250 MB，**OOM 直接消失**。

### 修复（方案 P1：跳过 entropy）

```text
# slime/backends/megatron_utils/loss.py:843 改：
with_entropy=(args.entropy_coef > 0),    # entropy_coef=0 → 跳过整个 entropy 路径
```

收益：actor train 阶段 +10-15% 速度（少一遍 entropy backward）。需要小改 ~30 行代码。

### 教训

- 大 vocab 模型的 logits 临时张量是 OOM 重灾区
- 检查框架是否已经实现 chunked loss / log_probs，往往一个 CLI 参数就解决
- `entropy_coef=0` 时 entropy 只为 logging，可以省略

### 关键经验总结

### 调试方法论

1. **py-spy 是利器**：CPU 高 GPU 0% 时，`py-spy dump --pid <PID>` 能区分死锁 vs 慢循环 vs IPC 握手卡
2. **CUDA 异步错误**：stack trace 经常误导，必要时用 `CUDA_LAUNCH_BLOCKING=1` 同步执行（性能 -30%）
3. **每次只改一个变量**：多个改动叠加导致 OOM 时无法定位
4. **看错误信息但不要全信**：sglang 的”建议修复”有时是 bug 本身（例：问题 10）

### sglang 在 B200 上的特殊问题

sglang 在 sm100 (B200) 上有多个**自动启用**的优化路径，但容器/colocate 环境下经常出问题：

| 自动启用 | 触发的问题 | 必须的关闭参数 |
| --- | --- | --- |
| enable_flashinfer_allreduce_fusion=True | rendezvous 死锁 | --enforce-disable-flashinfer-allreduce-fusion |
| custom_all_reduce_v2 (sgl-kernel) | cuda graph capture invalid argument | --disable-custom-all-reduce |
| moe_runner_backend=flashinfer_trtllm | weight layout 不匹配 | --moe-runner-backend triton |
| EAGLE in 0.6.12 | spec_accept=0 + draft cuda graph 崩 | 注释所有 --speculative-* |
| overlap schedule | 异步 CUDA error | --disable-overlap-schedule |
| mamba radix cache + partial-rollout | ping-pong donate illegal memory access | --disable-radix-cache --mamba-scheduler-strategy no_buffer |

### 显存优化优先级（B200 / hybrid mamba MoE）

1. **必开**：`--cross-entropy-loss-fusion`（大 vocab 模型）、`--account-for-*-in-pipeline-split`（PP 重平衡）
2. **OOM 时第一步**：降 `--max-tokens-per-gpu`、回到 `--recompute-granularity full`
3. **OOM 时第二步**：开 `--log-probs-chunk-size 1024` 应对 entropy/log_probs 张量大
4. **OOM 时第三步**：降 `--global-batch-size`、降 `--rollout-batch-size`
5. **不要轻易开**：`--num-layers-per-virtual-pipeline-stage`（stage 0 5x activation）

### 框架集成约束

- slime 的 `no_sync_func` 与 megatron 的 `--overlap-grad-reduce` 互斥
- slime 已经有 `--log-probs-chunk-size`、`with_entropy` 开关，但默认未启用
- megatron 的 `--account-for-*-in-pipeline-split` 在改 PP 切分时可能跟旧 checkpoint 不兼容

### 常见性能成本估算

| 修复 | 性能成本 |
| --- | --- |
| enforce-disable-flashinfer-allreduce-fusion | -5% sglang throughput |
| disable-custom-all-reduce | -3% sglang throughput |
| moe-runner-backend triton（vs flashinfer_trtllm） | -10% MoE GEMM 速度 |
| disable-radix-cache | -15% rollout（失去 prefix hit） |
| disable-overlap-schedule | -15-25% rollout |
| 关闭 EAGLE | 0%（本来就没加速） |
| recompute-granularity full（vs selective） | -30% actor train |
| log-probs-chunk-size 1024 | -5-8% log_probs 阶段 |

**累计：rollout 阶段约慢 30-50%，actor train 阶段约慢 30%**。这是 B200 + colocate + Qwen3.5 hybrid mamba 在 sglang 0.6.12 下为换稳定性付出的代价。
