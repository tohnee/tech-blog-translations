### 1. 从零预训练305M大模型：单卡跑通实战，显存爆炸、Activation解析与30倍提速全记录

> 作者：QZero ｜ 赞同：14 ｜ 原文链接：[https://zhuanlan.zhihu.com/p/2033969214759883103](https://zhuanlan.zhihu.com/p/2033969214759883103) ｜ 全文来源：知乎搜索摘要（未获取全文镜像）

### 系列背景

本系列文章记录作者从零开始预训练一个 305M”大”语言模型的全过程。上篇介绍训练前的 setup：模型架构、数据集、训练时的显存问题（计算 Activation、Gradient Checkpoint）、数据预处理，以及 `torch.compile` 带来的 30 倍提速；下篇着重介绍训练细节：排查 Loss 平台期、分布式训练、推理时的 KV Cache 等。

作者基于斯坦福 CS336（Language Modeling from Scratch）课程的 Assignment 1 完成实验。该课程涵盖大模型领域较为前沿的内容，从最基础的模型架构、Triton 算子，到更进阶的分布式训练、RLHF 等。Assignment 1 提供了大量中间测试用例，可以确保底层模块实现没问题，大大减少翻车时的错误排查成本（代码仓库：[https://github.com/stanford-cs336/assignment1-basics/tree/main）。](https://github.com/stanford-cs336/assignment1-basics/tree/main%EF%BC%89%E3%80%82)

### 实验结果

- 模型参数量：305M，单张 RTX 5090 训练约 **43 小时**
- 训练数据量：**4.5B token**，最终 valid loss 为 **3.086**
- 模型能够比较流畅地输出文本，并表现出了一定的知识储备

### 显存爆炸：远超想象的显存占用

作者最初的想法：300M 的模型参数，全用 fp32 也才 1.2GB，而 5090 有 32GB 显存，”优势在我”。但用 **context length=1024、batch size=16** 上手跑了一次之后，一轮参数更新还没跑完就 `CUDA out of memory` 了。

这个现象的根源在于：训练时的显存占用远不止模型参数本身，激活值（Activation）随 batch size、序列长度、模型深度增长，是训练显存的大头。文章随后详细推算了训练所需显存量（计算 Activation 的方法与 Gradient Checkpoint 的取舍），这也是本篇的核心内容之一。

### 实战启示

- 估算显存时**不能只算参数**：参数只是显存账单里最小的一栏，激活值与优化器状态才是压垮单卡的主因。
- CS336 风格的”先写测试用例再跑模型”能显著降低底层实现错误（如 tokenizer、attention 模块）的排查成本。
- `torch.compile` 在该实验中带来 30 倍提速，是小规模训练不可忽视的免费优化。

### 2. 从零预训练 305M 大模型（二）：Loss 平台期排查、Chinchilla 法则、Gradient Accumulation 与 DDP/FSDP 分布式训练实战

> 作者：QZero ｜ 赞同：10 ｜ 原文链接：[https://zhuanlan.zhihu.com/p/2034310849083487078](https://zhuanlan.zhihu.com/p/2034310849083487078) ｜ 全文来源：知乎搜索摘要（未获取全文镜像）

### 本篇定位

本系列中篇，主要介绍 Loss 平台期踩坑经历、Chinchilla 经验法则、Gradient Accumulation 技巧，以及分布式并行训练相关内容；下篇聚焦训练后的推理阶段（自回归推理采样、KV Cache、后训练指令微调）。

### Loss 平台期排查

训练开始后，前期 loss 下降很快，约 200 个 step 就从 10 下降到 5。

> 顺带一提，初始 loss 约等于 ln(vocab_size)：初始阶段可认为模型选中 vocab 里任意一个词的概率均等，为 1/vocab_size，因此交叉熵为 -ln(1/vocab_size) = ln(vocab_size)。

训练一段时间后，loss 卡在 **3.9 左右几乎不动**，用 checkpoint 做自回归推理也经常陷入复读。

**排查参数梯度**：作者把每个参数的梯度打印出来检查，发现有几个**严格等于 0 的梯度**——梯度可以是很小的浮点数，但严格为 0 很反常。进一步用 `named_parameters()` 同时打印参数名和梯度，发现为 0 的梯度都是 **SwiGLU 这个 FFN 层的参数**，信号明确：就是 SwiGLU 模块出问题了。

### 踩坑 1：用全 0 初始化 SwiGLU

奇怪的是，这个模块通过了 CS336 提供的测试用例（使用官方权重得到了相同结果）。最终定位到是 **SwiGLU 的权重初始化出错**：作者为了省事，直接用 `torch.zeros` 初始化了 SwiGLU 的所有权重：

```python
self.W1 = nn.Parameter(torch.zeros((self.d_ff, self.d_model)))
self.W2 = nn.Parameter(torch.zeros((self.d_model, self.d_ff)))
self.W3 = nn.Parameter(torch.zeros((self.d_ff, self.d_model)))
```

全 0 初始化导致 SwiGLU 各参数梯度恒为 0，参数永远不更新，loss 因此卡在平台期。教训：FFN 的门控/投影矩阵必须按一定方差随机初始化（而非全 0）。

### 实战启示

- loss 数值本身携带信息：初始 loss 应接近 ln(vocab_size)，据此可快速验证训练是否正常启动。
- loss 长期不动时，先按参数逐个检查梯度（严格为 0 的梯度几乎必然指向初始化或计算图断连问题）。
- 显存不够时用 Gradient Accumulation 模拟大 batch（本篇另一主题），并进一步走向 DDP/FSDP 分布式训练。

### 305M 小模型的自回归生成实况（开源后实测样例）

**样例一（续写任务）**

- Prompt： > If you believe that the course staff made an objective error in grading, you may submit a regrade request within 3 days after the grades are released.
- Generated： > If you believe that the course staff made an objective error in grading, you may submit a regrade request within 3 days after the grades are released. These regrands will then be assigned to the Divisional Board, and the Divisional board will manage the school through that regrip. This process will take approximately one year from inception to completion.

模型能接住句式与主题，但语义已开始漂移（自造词 regrands / regrip）。

**样例二（问答任务）**

- Prompt：The capital of the United States is
- Generated：The capital of the United States is цильсь прод（输出乱码）

作者分析：**这种现象应该和数据关系很大**，因为预训练语料里很少有这种直接的问答形式文本——没有经过指令微调的 base model 天然不会”答题”。

### 一些感悟：对大模型的祛魅

- 即使是目前最强大的模型，在面对训练数据里没出现过的事物时也会”宕机”，就像小模型面对一个简单的复读任务那般。
- 现在的大模型本质上仍然是一个**记住了训练数据概率分布的静态模型**。训练数据几乎就是当今互联网上的所有数据（有些模型还会用 OCR 扫描纸质书籍），因此大模型能上知天文下知地理；但对于那些无法被文字记录的”灵感”，大模型无法理解——这是人类和硅基生命之间难以跨越的鸿沟。
- 一个精彩的类比：大模型也许能够求解相对论场方程，但永远无法**提出**相对论——因为在 1905 年以前的海量文本中，以太仍是主流假说，按大模型的算法只会人云亦云地朝”以太风”的方向解释迈克尔逊-莫雷实验，能采样到”光速不变”这种离经叛道结果的概率微乎其微。

### 实战启示

- 预训练模型的生成质量高度依赖数据分布：续写风格任务表现尚可，直接问答则容易输出乱码，需指令微调（SFT）补齐。
- KV Cache、自回归采样与指令微调是该篇的工程主线（摘要未覆盖实现细节，可结合原文与开源代码学习）。

### 4. LLM Training Lab 08：目标模型放不进显存时，哪些优化真的值得用？

> 作者：鬼马行天Mark ｜ 赞同：0 ｜ 原文链接：[https://zhuanlan.zhihu.com/p/2084317039116789437](https://zhuanlan.zhihu.com/p/2084317039116789437) ｜ 全文来源：知乎搜索摘要（未获取全文镜像）

### 实验设定（系列第 08/38 篇，全部数据为真实运行 REAL）

- 环境：WSL2 Ubuntu 24.04 + PyTorch 2.14.0+cu130 + transformers 5.17.0
- 硬件：NVIDIA RTX 3070 **8 GB**（实测可用约 **6.78 GB**）
- 前置：06 篇统一训练接口、07 篇”四口径显存探针”与阶段打点
- 红线 bench 六组合、OOM 时间线与 parity 五组合均在 RTX 3070 上实测

### 核心术语与结论表

| 术语 | 含义 | 为什么需要 |
| --- | --- | --- |
| OOM | 分配请求得不到满足时 CUDA 抛出的错误，训练进程直接崩溃 | 本篇要救的就是它；07 篇已教区分容量与碎片 |
| 显存红线（set_per_process_memory_fraction） | 给进程画一条显存上限，超出即触发真实 OOM | WSL2 只慢不崩，红线把 8GB 卡模拟成更小的卡，让 OOM 在受控条件下复现 |
| gradient accumulation（梯度累积） | 把大 batch 拆成多次小前向，梯度逐次累加后执行一次参数更新 | 第 2 章”最便宜的交换”：激活只来自一个 micro_batch |
| micro_batch 与 effective batch | micro_batch 是单次前向的真实 batch；effective batch = micro_batch × 累积步数 | 说清 accum 省显存但不改等效 batch |
| activation checkpointing（激活检查点） | 反向时重新执行一次前向，层间激活不常驻 | 第 3 章主角：用重算换激活 |
| 混合精度 AMP | fp16 存激活与执行矩阵乘，fp32 保留主权重 | 省激活还提速，但碰不到优化器状态 |
| GradScaler | 放大 loss 防 fp16 梯度下溢，step 前 unscale 再更新 | 解释 AMP 的数值代价与 06 篇的 unscale 顺序坑 |
| fp16 优化器状态（lowstate） | AdamW 的 m 与 v 以 fp16 存储，状态字节减半 | 第 4 章省显存最多、但实测出现 NaN 的一项 |
| CPU offload | 优化器状态搬到主机内存，step 时经 PCIe 传回 GPU | 第 4 章”用总线换容量”的最后一笔交换 |
| PCIe 带宽 | GPU 与主机内存之间的传输通道 | offload 的代价来源，解释吞吐为什么跌 |
| zero_grad(set_to_none=True) | 释放梯度张量而非填零 | “三件小事”之一，几乎免费的交换 |

### 显存优化的”交换”框架（按代价从低到高）

1. **几乎免费**：`set_to_none=True` 等三件小事；
2. **最便宜的交换——梯度累积**：激活显存只与 micro_batch 挂钩，等效 batch 靠累积步数凑，对数学结果几乎无影响；
3. **用计算换显存——激活检查点**：反向时重算前向，层间激活不常驻，代价是约多一次前向的算力；
4. **省激活还提速——AMP 混合精度**：fp16 存激活/做矩阵乘、fp32 保主权重，但优化器状态纹丝不动，且引入 GradScaler 的数值管理；
5. **省显存最多但危险——fp16 优化器状态**：AdamW 的 m/v 字节减半，实测出现 NaN（数值稳定性风险）；
6. **最后一笔交换——CPU offload**：优化器状态搬去主机内存，容量换带宽，吞吐经 PCIe 跌落。

**总体结论方向**：先做免费的，再做数学上等价的（梯度累积），再权衡计算换显存（检查点）与精度换显存（AMP/lowstate），offload 是吞吐代价最大的最后手段。

### 5. LLM训练的「显存账单」：从OOM到分布式，一篇讲清面试官想听的所有硬核细节

> 作者：Regulus ｜ 赞同：4 ｜ 原文链接：[https://zhuanlan.zhihu.com/p/2034986154831910428](https://zhuanlan.zhihu.com/p/2034986154831910428) ｜ 全文来源：知乎搜索摘要（未获取全文镜像）

### 核心公式：训练显存账单

```text
显存占用 = 参数(P) + 梯度(P) + 优化器状态(× 取决于用Adam还是SGD) + 激活值(× batch)
         = 2P + 2P + 8P(Adam) + Activation
         = 12P + Activation
```

即混合精度训练下，参数 2 字节/个 + 梯度 2 字节/个 + Adam 优化器状态 8 字节/个（FP32 的参数副本、动量、方差等），合计 **12 字节/参数**，再叠加与 batch size 成正比的激活值。

### 解决方案菜单

- 装不下**参数 + 优化器** → MP（模型并行）或 PP（流水线并行）
- 装不下**激活值** → 减小 batch size 或梯度累积
- 单卡全装不下 → 3D 并行（DP + MP + PP）
- **推理太慢** → KV Cache + 量化

### 面试追问专栏（原文四问四答）

**Q1：Adam 需要 8P 的优化器状态，那 AdamW 呢？区别是什么？显存有什么变化？**

> AdamW 把 weight decay 从梯度里拆出来直接加到权重上（解耦式衰减），显存占用跟 Adam 一样（都是 8P），但收敛更好。

**Q2：FP16 训练时，梯度下溢的典型表现是什么？”Loss 直接变成 NaN”和”Loss 一直不变”分别说明什么？**

> NaN 通常是梯度爆炸（Loss Scaling 不够大或没用好）；Loss 卡住不动可能是梯度下溢全变 0 了（Loss Scaling 太大或架构问题）。能区分这两者，说明你 debug 过真实训练。

**Q3：数据并行 DP 和分布式数据并行 DDP 有什么本质区别？为什么现在没人用 DP 了？**

> DP 是单机多卡，用一台机器上的一个主进程做梯度汇总，通信走机器内部；DDP 是多机多卡，每个进程独立，用 AllReduce 同步梯度。DP 有单点瓶颈 + Python GIL 限制，DDP 是现在的标配。

**Q4：KV Cache 在长序列推理中会遇到什么问题？有什么解决思路？**

> 序列极长时（比如 128K tokens），KV Cache 显存占用会超过模型本身。解决方案：Multi-Query Attention (MQA) / Grouped-Query Attention (GQA) 减少 KV 头数；KV Cache 量化（INT8/INT4）；或滑动窗口注意力（sliding window）。

### 6. 大模型显存优化之task1：硬件与显存账本

> 作者：哒哒 ｜ 赞同：4 ｜ 原文链接：[https://zhuanlan.zhihu.com/p/2083492155214000917](https://zhuanlan.zhihu.com/p/2083492155214000917) ｜ 全文来源：知乎搜索摘要（未获取全文镜像）

### 训练状态字节数：16 字节/参数（教学假设）

以 7B 模型（70 亿参数）为例：计算用权重占 **7 × 2 = 14 GB**（bf16），完整训练状态占 **7 × 16 = 112 GB**，后者仍未包含激活等开销。这里统一采用十进制 GB（10⁹ 字节）。

**注意：16 不是通用常数。** 例如其他条件不变、梯度改为 FP32，计算就变成 **2+4+4+8=18 字节/参数**。必须先确认参数、梯度和优化器的实际精度（典型拆分：参数 bf16 2B + 梯度 bf16 2B + FP32 主权重 4B + FP32 动量 4B + FP32 方差 4B = 16B）。

### ZeRO：把重复保存的训练状态分给多张卡

- 普通 DDP：每张卡处理不同的数据，但各自保存完整的参数、梯度和优化器状态；
- ZeRO：不再让每张卡都保存全部训练状态，而是将指定状态切成多份，各卡分别保存。

设 N 为参与 ZeRO 分片的 GPU 数量，沿用 16 字节假设，理想单卡占用如下（只算训练状态，不是完整训练峰值；分片对象与 DeepSpeed 官方定义一致）：

| 策略 | 分片保存哪些状态 | 单卡训练状态显存（字节） | 7B 模型、8 张卡 |
| --- | --- | --- | --- |
| DDP / ZeRO-0 | 不分片 | 16P | 112 GB |
| ZeRO-1 | 优化器相关状态 | P(4+12/N) | 38.5 GB |
| ZeRO-2 | 再加上梯度 | P(2+14/N) | 26.25 GB |
| ZeRO-3 | 再加上参数 | 16P/N | 14 GB |

**记忆口诀：一切优化器，二加梯度，三加参数。**

以 ZeRO-2 为例，计算过程：

```text
14（完整参数）+ 14/8（梯度分片）+ 84/8（优化器相关状态分片）= 26.25 GB/卡
```

### 根据显存容量反推模型规模

先扣除预留空间，再除以每个参数在单卡上的占用：

```text
可容纳参数量（十亿）≈ 单卡容量(GB) × (1 - 预留比例) / 单卡每参数字节数
```

例如：8 张卡、每卡 80GB、预留 20%，单卡训练状态预算 = 80 × 0.8 = 64 GB。

- DDP（16B/参数）：64 / 16 = **4B 参数**
- ZeRO-3（16/8 = 2B/参数）：64 / 2 = **32B 参数**

### 7. GPU通识课（3）：单卡显存优化

> 作者：紫老头 ｜ 赞同：1 ｜ 原文链接：[https://zhuanlan.zhihu.com/p/2076070720422016190](https://zhuanlan.zhihu.com/p/2076070720422016190) ｜ 全文来源：知乎搜索摘要（未获取全文镜像）

### 通信相关的显存开销

- 多卡并行（Tensor Parallel / Pipeline Parallel / Expert Parallel）时卡间需要频繁通信，对应的 **AllReduce / AllGather / All-to-All 都需要 NCCL Buffer**，这部分同样占用显存；
- **MoE 场景尤其明显**：此时通信 Buffer 可能显著增大。

### Allocator Cache：reserved ≠ allocated

与训练一样，需要区分两个指标：reserved（分配器保留）与 allocated（实际分配），两者往往不相等。例如多出的 5GB 只是 PyTorch CUDA allocator 缓存起来准备复用的显存——**reserved − allocated 不能理解为”模型真的用了这么多显存”**。

### 总结公式

完整版（推理）：

```text
推理显存 ≈ 模型权重 + KV Cache + 运行时开销
```

其中两个主导项的行为完全不同：

| 组成 | 主要决定因素 | 特性 |
| --- | --- | --- |
| 模型权重 | 参数量 × 参数精度 | 相对固定 |
| KV Cache | Batch × Sequence Length | 动态增长 |

### 训练 vs 推理显存对照表

| 显存组成 | 训练 | 推理 |
| --- | --- | --- |
| 模型参数 | ✓ | ✓ |
| Gradient | ✓ | ✗ |
| Optimizer State | ✓ | ✗ |
| Activation | 大量保存 | 临时 |
| KV Cache | 通常不是主要矛盾 | 核心显存之一 |
| Workspace | ✓ | ✓ |
| Communication Buffer | ✓ | 多卡时 ✓ |
| Allocator Cache | ✓ | ✓ |

**一句话总结：训练显存主要是 Parameter + Gradient + Optimizer + Activation；推理显存主要是 Weight + KV Cache。**

对 LLM 推理还可按阶段拆分：Decode 阶段随着 token 逐个生成，KV Cache 持续增长。因此在长上下文、高并发场景下，KV Cache 往往成为推理显存的主要瓶颈——这也正是 **PagedAttention、KV Cache 量化、KV Cache 卸载**等技术的出发点。

### 显存复用的通用手段：时间维度上的轮流使用

显存复用的核心思想只有一句：**让同一块物理显存在时间维度上被多份数据轮流使用。**

所有具体手段都可归入”拿别的资源去换显存”框架，按换出去的是什么划分，共六类：

1. 不付代价的复用（框架层面，如 allocator 自动复用、inplace/reuse）
2. 拿计算换（激活重计算/检查点）
3. 拿带宽换（offload，跨 PCIe/NVMe 搬运）
4. 拿精度换（量化、低精度优化器状态）
5. 拿可训练参数换（PEFT：只训部分参数，省梯度与优化器状态）
6. 调度层面的复用（分页、分块、按需加载）

### 8. 大模型训练中的并行加速与显存优化

> 作者：智能计算系统手记 ｜ 赞同：2 ｜ 原文链接：[https://zhuanlan.zhihu.com/p/2045681342650885222](https://zhuanlan.zhihu.com/p/2045681342650885222) ｜ 全文来源：知乎搜索摘要（未获取全文镜像）

### 两堵墙

训练大模型时，最先撞上的墙通常有两堵：一堵叫**算力墙**（模型太大、训练太慢），另一堵叫**显存墙**（参数、梯度、优化器状态、激活加起来，单卡根本放不下）。Megatron 并行和 FSDP2 并行都是为了解决这些墙，但出发点不一样：

- **Megatron 更像把模型计算拆开**，让多张 GPU 一起算；
- **FSDP2 更像把模型状态切片存起来**，让每张 GPU 少背一点包袱。

### 共同点：并行训练本质都在”分”

理解并行训练，先分清三件事：**样本、计算、状态**。

- **数据并行 DP 是”分样本”**：GPU0 处理一批样本，GPU1 处理另一批。问题是每张卡通常都要放一份完整模型状态，显存并没有根本省下来。
- **Megatron 主要是”分计算”**：把 Transformer 的层、张量、序列维度拆到多张卡上。比如一个 MLP 里巨大的矩阵乘法，单卡算不动，就把权重矩阵按列或按行切开，让多卡共同完成。
- **FSDP2 主要是”分状态”**：把参数、梯度、优化器状态切成 N 份，平时每张卡只保留其中一份；真正计算某一层时，再临时 all-gather 出完整参数，用完后重新切回分片。

**一句话：Megatron 解决”怎么算更大、更快”，FSDP2 解决”怎么把模型装进显存”。**

### Megatron 体系：TP、PP、SP

- **TP（张量并行）**：切的是同一层内部的张量。以 Linear 层为例，权重矩阵可以按列切，也可以按行切，每张 GPU 只负责一部分矩阵乘法，最后通过 all-gather 或 all-reduce 把结果拼起来。好处是即使单层非常大也可以训练；代价是**通信非常敏感**，尤其适合放在 NVLink、NVSwitch 这类高速互联的 GPU 之间。
- **PP（流水线并行）**：切的是模型层。比如 48 层 Transformer，可以把 1-12 层放 GPU0，13-24 层放 GPU1，依次往后。为避免前面的卡算完就闲着，训练会把 batch 拆成多个 micro-batch，像工厂流水线一样持续推进。难点在于**“气泡”**：流水线填充和排空阶段会有 GPU 空转，所以 micro-batch 数、层划分、调度策略都很关键。
- **SP（序列并行）**：常与 TP 配合，把序列维上的激活也拆开，进一步节省激活显存。

Megatron 的核心不是”少存几份优化器状态”，而是把计算图切细，把大算子、大层、大模型摊到多卡上。

### 9. 大模型训练的硬件基础：GPU内存层级、分块与并行策略

> 作者：deephub ｜ 赞同：8 ｜ 原文链接：[https://zhuanlan.zhihu.com/p/2012990742671413754](https://zhuanlan.zhihu.com/p/2012990742671413754) ｜ 全文来源：全网镜像 [https://developer.aliyun.com/article/1714829](https://developer.aliyun.com/article/1714829) （阿里云开发者社区，正文按镜像抓取整理）

### 引子

AI 和 LLM 的进步通常归因于三方面：模型、数据、计算。Llama 3 最大的模型超过 4000 亿参数，在 16000 块 GPU 上训练了数周乃至数月——优化计算意味着在更低的成本下训练更大的模型。本文介绍 GPU 的核心特性，并据此讨论如何设计更快的算法（技巧源自斯坦福 CS336 课程）。

### GPU 与 CPU 的区别

- CPU 优化**单任务延迟**，GPU 优化**吞吐量**：CPU 像一个能力极强的工人，GPU 像一群普通工人同时干活。LLM 训练这种大规模并行处理场景下 GPU 天然占优。
- 工厂类比：GPU 是一个庞大的工厂城镇——多个”工厂集群”（SM，流式多处理器），每个集群包含多个工厂（SP，流式处理器）和一个小仓库（共享内存）；城镇里还有一个全局仓库（DRAM），离各集群更远但容量大得多。**集群内的小仓库访问速度远快于全局仓库，代价是容量小得多。**
- 关键数据：过去 20 年间，硬件浮点运算能力提升了 **60000 倍**，DRAM 带宽只提升了 **100 倍**，互连带宽更是只有 **30 倍**。**过去的瓶颈在计算，现在的瓶颈在内存带宽。** 既然数据搬运才是真正的瓶颈，减少搬运次数和搬运量就是让 GPU 跑得更快的关键。

### 技巧 1：低精度计算

精度越高，存储一个数字所需字节越多（9.327595 比 9.33 占空间大）。用 fp16 代替 fp32 意味着搬运的”货物”更少。但并非训练所有阶段都需要低精度，只需在**数据搬运阶段**降到 fp16：输入以 fp16 传入，矩阵乘法在 32 位精度下完成（计算并非瓶颈，高精度还可防止舍入误差累积），输出再降回 fp16 用于传输。工厂类比：道路拥堵，所以进出工厂的箱子越小越好；工厂内部空间充裕，在大空间中完成加工后再打包成小箱子运出。

### 技巧 2：算子融合

如果每完成一步操作就把半成品送回仓库再取回来做下一步，来回搬运次数非常多。算子融合把多步操作在工厂内一次性完成，省去中间产品的反复搬运。实现方式两种：手写低级代码控制融合细节，或直接用 `torch.compile` 自动完成优化。

### 技巧 3：重计算

前向的中间结果有两种存法：选项 1 把中间结果送回仓库保管（省重算但搬运量大）；选项 2 不保存中间结果、需要时重新计算（搬运量小但额外耗算力）。这是内存与计算的权衡。既然瓶颈在”道路拥堵”（带宽）而非车间产能（算力），**重计算是更合理的选择：重新加工成本低，但从仓库搬运的成本可能高出几个数量级。用算力换内存带宽，划算。**

### 技巧 4：内存合并访问

DRAM 以”突发模式”读取，每次返回一段连续字节——像仓库按板条箱整箱发货。当所有线程的访问地址落在同一个突发段内时，只需一次 DRAM 请求，称为**完全合并访问**；数据散落在多个箱子中，搬运成本成倍增加。一个直接推论：**把维度（比如词汇表大小）对齐到 64 的倍数会带来可观的速度提升**——因为分块操作需要沿突发段边界读取数据，分块边界与突发段不对齐时读取次数会急剧增加。

### 技巧 5：分块

把大矩阵切成小块，加载到共享内存中，避免反复访问全局内存。以两个 4×4 矩阵 A、B 相乘得 C 为例：直接算 C 的每个元素要多次跨行/跨列访问全局内存；分块做法是将 A、B 各切成四块，小块整块加载进共享内存，先加载一组块算部分和，再加载下一组块继续累加。**总计算量不变，但每一步都在共享内存中完成**，节省的时间相当可观。

### FlashAttention：在线 softmax

先回顾注意力：权重矩阵把隐藏向量投影为 Q、K、V；Q×Kᵀ 得到原始注意力分数；做 softmax 归一化；再与 V 加权求和。

数值稳定性：取指数之前先减去最大值——e¹² 已经是 162,755，超出 fp16 的上限 65,504，直接计算会溢出；减去最大值不改变 softmax 结果但规避溢出。

问题：Q×K 产生 N×N 矩阵（N 为序列长度），上下文窗口很大时这个矩阵无法整个放入共享内存。解法是沿 N 维度分块——如上下文窗口 1028、按 64 切块，逐块载入共享内存。

棘手之处在 softmax 与加权求和：计算 softmax 通常需要整行数据做归一化，访问整行意味着回全局内存。**FlashAttention 的突破在于”在线 softmax”——softmax 计算和 V 加权求和可以在块内一次性完成，无需看到全行数据。关键条件是最终操作是加权求和，这给了逐块修正的数学余地。**

逐块流程示例（六个原始分数分三块，每块 2 个元素）：

1. 处理第一块：基于本块的两个分数计算加权指数和，**不急着归一化**——记录归一化分母的累积值，最后一步统一归一化（后续块会改变总和，先归一化还得再修正）；
2. 处理第二块：传递三个量——当前块最大值、累积加权和、累积归一化分母，使结果与一次性看到全部四个值一致（四个值的全局最大值是 12，此时若终止，A₍₁₊₂₎ 除以分母 1.3098 即为最终结果）;
3. 处理第三块（边界情况）：新块出现更大的最大值（12 → 13），需修正之前的计算——将旧的累积加权和 A₍₁₊₂₎ 与归一化分母整体乘以 e^(-1)（即 e^(12-13)），补偿最大值变化，无需逐个回去修正每个指数值；
4. 最后用累积分子 A₍₁₊₂₊₃₎ 除以更新后的分母 1.4955 得到结果。

整个过程从未回访之前的块：只要跟踪最大值和归一化分母，就能逐块完成 softmax，且全部在共享内存中进行。**FlashAttention 原始论文显示，在 GPT-2 上注意力计算的耗时减少了数倍。** 处理大规模模型时，内存放置策略（尽量在共享内存中完成计算）对整体性能的影响远超想象。

### 并行计算：从单卡到 16K 卡

单 GPU 装不下现代大型 LLM（Llama 3 用了 16K 块 GPU），核心问题变成：如何把训练计算分配到多台机器上，再把结果汇总。先回顾训练流程：以一个 2 层神经网络、batch size 16、Adam 优化器（为每个参数维护一阶矩和二阶矩）为例。

**数据并行**

- 有效 batch size 16、每卡只装得下 4 个样本时，单卡需要梯度累积（跑 4 轮前向累积梯度再更新）；
- 数据并行做法：16 个样本分给 4 块 GPU，每块拿 4 个样本并行前向；
- 聚合梯度的聪明做法：各卡算各自 4 个样本的梯度再求和（比汇集激活值算平均 loss 再求梯度搬运量更小，数学上完全等价）；梯度求和后传回各机器分别更新本地模型。这个操作叫 **all-reduce**：每台机器贡献梯度，合并后每台都拿到结果（实际实现通常是环形传递，并非图中的”聚合器”）；
- 效率问题：每块 GPU 都在做完整模型更新，要维护所有参数的 Adam 状态（状态量是参数量的两倍），等于每卡复制了完整的模型参数、梯度、主权重与优化器状态——对大模型，内存成为硬瓶颈。

**ZeRO（Zero Redundancy Optimizer）**：一组内存优化技术，在保持数据并行的前提下大幅减少每卡内存占用。

**ZeRO Stage 1（优化器状态分片）**

- 核心思想：让每块 GPU 只负责更新一部分参数（如每层参数分四份，GPU1 负责 Part 1……）；
- 流程：数据仍拆到四卡，每卡算**完整**梯度（到这里还是标准数据并行）；梯度汇总后不再发回所有人，而是按参数分片发送——每卡只收到自己负责那部分参数的梯度，术语叫 **reduce-scatter**（每人只拿到合并结果的一个切片）；
- 各卡只更新自己负责的参数，也只保留该部分优化器状态；更新完成后各卡把自己的参数切片分享出去拼接成完整模型，术语叫 **all-gather**（每人贡献一个切片，每人拿到完整拼接结果）；
- 两阶段概括：第一阶段按数据维度拆分，各卡算全参数梯度再汇总；第二阶段按参数维度拆分，各卡只更新自己的参数切片，最后拼接出完整模型；
- 效果：每卡只保留一小部分优化器状态，内存节省可观；**reduce-scatter 加 all-gather 的总通信量与朴素数据并行的 all-reduce 等价，没有额外开销**。

**ZeRO Stage 2（梯度也分片）**

不仅优化器状态分片，梯度本身也要分片。关键在于反向传播是逐层进行的：**每一层的梯度算完后，立刻将不属于自己管辖的部分发送给对应 GPU 并丢弃**，任何时刻都不需要存储全部层的完整梯度。
