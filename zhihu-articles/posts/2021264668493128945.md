如果前面说的是 PagedAttention 的核心思想，那这一节要讲的就是它在系统里究竟是怎么落地的。很多人第一次看 vLLM 或类似系统时，会觉得它的设计很复杂：一边有 scheduler 在调度请求，一边有 block manager 在管显存，一边又有 block table 在做映射，最后 attention kernel 还要按这个映射去读 KV。实际上，把它串起来看，整条链路非常清楚：

> scheduler 先决定这一轮谁能进 batch，block manager 再为这些序列分配或复用 physical blocks，接着 block table 把“逻辑上的序列”翻译成“物理上的 KV 位置”，worker 拿到这些映射后运行 paged attention kernel 去读取 K/V；如果多个序列共享同一段前缀，而其中某个序列又要继续往后写，就触发 copy-on-write。

换句话说，PagedAttention 并不是某一个 CUDA kernel 单独完成的优化，而是一整套“调度 + 内存管理 + 地址映射 + kernel 执行”的协同机制。只有把这几个部件放在一起，才能真正理解为什么它能同时做到高吞吐和高内存利用率。<br>**1. Block table 是怎么工作的**

![](https://picx.zhimg.com/v2-a9c87432455ab8a85efeb87cc9a8abb1_r.jpg)

可以把 block table 直接理解成 **KV Cache 的页表**。vLLM 先把每个请求的 KV cache 切成固定大小的 **logical blocks**，再把这些逻辑块映射到 GPU 上实际分配的 **physical blocks**。论文里明确写到：每个 block table entry 记录“这个逻辑块对应哪个物理块”，以及“这个块里已经填了多少 token slot”。正因为逻辑块和物理块被分开，序列才能按需增长，不必一开始就为最大长度预留一整块连续显存。图 6 里那个例子就是：logical block 0、1、2 可以分别映射到完全不连续的 physical block 7、1、3。

运行时的流程是这样的：每一轮 decode，scheduler 先选出本轮要推进的 sequence，把需要的新 block 分配好，然后把 **输入 token IDs + block tables** 一起发给 GPU workers。worker 在 attention 层里并不是“顺着一大块连续 KV”去读，而是根据 block table 先找到每个 logical block 对应的 physical block，再去取 K/V。新生成 token 的 K/V 也会被写回当前 logical block 对应的 physical block；如果最后一个 logical block 已满，就再分配一个新的 physical block，并把 block table 更新一行。换句话说，attention kernel 看到的是“这轮该读哪些 physical block”，而不是“这条序列在显存里连续放在哪里”。 <br>

从最新设计看，vLLM 后续还专门优化了 block table 的下发方式：在 Model Runner V2 里，大张的 block table 不再每步都整张从 CPU 拷到 GPU，而是保留一份 GPU base tensor，只把 CPU 侧的 diff 打包后传过去，再用一个 kernel 把这些 diff 应用到 GPU 上。这是为了把 block table 本身的控制面开销压下去。 <br>

## **2. Copy-on-write 是怎么工作的**

![](https://pic1.zhimg.com/v2-e19b7f8498b3809a5d7b4a2499ba7e4a_r.jpg)

copy-on-write 的前提是 **多个逻辑序列可以共享同一个 physical block**。这在 parallel sampling、beam search、shared prefix 这些场景里非常常见：前缀完全一样，就没有必要把前缀的 KV 重复存多份。论文里说得很直接，vLLM 为每个 physical block 维护引用计数；当前缀被多个样本或多个 beam 共享时，这些 block 的 refcount 会大于 1。

![](https://pic4.zhimg.com/v2-706c4572c1ad8bf8cd2e61b215827423_r.jpg)

真正需要 copy-on-write 的时刻，是“某个共享 block 现在要被继续写入，但它已经被不止一个序列共享”。这时系统不能直接在原 block 上追加，因为会污染别的序列的历史。当前实现里有一个 CopyOnWriteTracker，它会先检查这个 block 是否 appendable；如果 refcount 大于 1，就给当前序列分一个新的 physical block，把旧 block 内容拷过去，记录一条 src_block_id -> dst_block_id 的映射，然后把当前序列的 block table 指向新 block。后面这个序列就在新 block 上继续写，别的序列还留在旧 block 上。 <br>

这个机制的好处是：**只在真正发生分叉时才复制，而且通常只复制最后那个正在被写的 block**。论文在 parallel sampling 和 beam search 的例子里都强调了这一点：大部分前缀 block 可以长期共享，只有“新 token 落在旧共享 block 内”时才触发 copy-on-write，所以复制代价通常就是一个 block，而不是整条历史序列。 <br>

## **3. Scheduler 是怎么工作的**<br>

vLLM 的 scheduler 是 **centralized scheduler**。论文里的描述是：它统一协调 distributed GPU workers，并在每个 decoding step 决定这轮哪些 sequence 要继续跑、哪些要分配 block、哪些需要被换出或恢复。worker 不负责做内存管理决策，只负责按照 scheduler 发下来的控制信息执行模型。

调度粒度不是“整请求跑完再切换”，而是 **iteration-level scheduling**。也就是每生成一轮 token，系统就可以重新组 batch：完成的请求移走，新的请求加进来，正在运行的请求继续保留。论文把这种方式和传统 request-level batching 区分得很清楚；而当前 vLLM 的 engine 文档也明确写了，LLMEngine 利用 iteration-level scheduling 和高效内存管理来最大化吞吐。 <br>

就当前代码结构来说，scheduler 至少会显式区分 WAITING、RUNNING、SWAPPED 这些状态，并分别有调度 waiting/prefill 队列和 swapped 队列的逻辑。_schedule_prefills 会在 token budget 允许时从 waiting 队列取请求， _schedule_swapped 会在 budget 允许且能 swap-in 的情况下把 swapped request 拉回 batch。代码里还能看到它会受一个 SchedulingBudget 约束：要同时满足 batched token 数和 sequence 数预算。

当显存或预算不够时，就进入 preemption。论文里写得很明确：vLLM 默认按 FCFS 保证公平性，早到的优先，晚到的先被抢占；而且它不是随便逐块淘汰，而是采用 **all-or-nothing eviction**，即一个 sequence 的 block 要么全留、要么全赶走。对于 beam search 这种一个 request 内多条序列共享 block 的情况，它们会作为一个 sequence group 一起被 preempt / reschedule，因为这些序列之间有共享关系，不能单独拆。 <br>

被抢占之后有两种恢复方式。第一种是 **swap**：把 block 从 GPU 挪到 CPU RAM，需要时再换回来；第二种是 **recompute**：以后重新跑 prompt/prefill 把 KV 再算一遍。论文把这两种方式都写进了设计里；当前 scheduler 代码也能看到它在 swap-in 时会维护 blocks_to_swap_in 和 blocks_to_copy，并且在需要时会从 running queue 里挑 victim 做 _preempt。 <br>

## **4.** **paged_attention_v1和** **paged_attention_v2的区别**

最核心的区别其实就一句话：

**V1 是单阶段、整段上下文一次算完；V2 是先分 partition 分段算，再做一次 reduce 合并。**

paged_attention_v1 的接口只需要 out + query + key/value cache + block_tables + seq_lens 这些主输入。它的 launcher 里，grid 形状是 (num_heads, num_seqs, 1)，也就是每个 head、每条 sequence 只起一个 thread block；同时它给 softmax logits 申请的 shared memory 大小直接跟 **padded_max_seq_len** 成正比。直觉上这意味着：上下文越长，单个 thread block 需要的 shared memory 越大。

![](https://pic4.zhimg.com/v2-f6c96fb5bb8a52d9f2203c1e113e945d_r.jpg)

paged_attention_v2 则不一样。它除了最终输出 out 以外，还要额外传入 exp_sums、max_logits、tmp_out 三个中间缓冲。它的第一阶段 kernel 的 grid 是 (num_heads, num_seqs, max_num_partitions)，也就是把一条长上下文切成多个 partition 并行处理；第二阶段再用一个 paged_attention_v2_reduce_kernel 把各个 partition 的局部结果合并成最终输出。代码里能看到它会先保存每个 partition 的 max_logits 和 exp_sums，reduce 时再用全局最大 logit 做重标定，把各 partition 的 softmax 结果正确合并。

这样设计的直接后果是：V2 的单个 thread block 不需要再为“整条长上下文”准备那么大的 shared memory，因为它只处理一个 partition。当前 Python 侧把 _PARTITION_SIZE 设成 512；源码注释里也明确写了，对于 **超过 8192 的 context length**，会倾向使用 V2，以避免 shared memory shortage。代价则是它必须多写几块中间 buffer，再做一次 reduce，所以在不需要 partition 的情况下会多一层开销。 <br>

所以可以把两者理解成：

- **V1**：路径短、额外开销少，适合上下文不长，或者虽然上下文不算短，但当前 num_seqs * num_heads 已经很多、GPU 并行度足够的情况。
- **V2**：更适合长上下文，因为它把上下文分片后再归约，避免单 kernel shared memory 撑爆，但会多出 tmp_out / exp_sums / max_logits 和 reduce 的成本。这个判断不是我在猜，vLLM Python 侧确实有一段启发式：当 max_seq_len <= 8192 且“只有一个 partition”或者“num_seqs * num_heads > 512”时优先选 V1；否则更倾向选 V2。 <br>

再说得更直白一点：

**V1 更像“单次整段做完”，V2 更像“分块做局部 softmax，再把局部结果正规化合并”。** 两者的目标结果是一致的，差别主要在并行拆分方式、shared memory 压力和中间归约开销。这个从它们共享同一个底层 paged_attention_kernel、只是 V2 多了一层 partition + reduce 的实现结构就能看出来。 <br>

![](https://pic1.zhimg.com/v2-f058acf758d2cd3dc9299be81d1974fa_r.jpg)

**5. Scheduler 先决定这一轮谁进入 batch**

在线推理系统最大的现实问题之一，就是所有请求都不整齐。有人刚进来，还在做 prompt prefill；有人已经进入 decode 阶段，正在一 token 一 token 往后生成；还有人这一轮可能已经结束，不再需要继续占用计算资源。如果系统还像传统 batch 那样，把“一个请求从头跑到尾”当作最小调度单位，那么很快就会出现两个问题：短请求被长请求拖住，新请求又迟迟进不来，GPU 虽然在跑，但调度效率非常低。

所以现代 LLM serving 更常见的做法，不是 request-level batching，而是 **iteration-level scheduling**。也就是说，scheduler 并不是一次性决定“这几个请求一起跑完整个生成过程”，而是每一轮 decode 都重新看一遍：哪些请求下一步还需要一个 token，哪些请求这一轮已经结束，哪些新请求现在可以塞进来。于是 batch 的边界不再是“请求”，而变成了“这一轮参与生成的 token 集合”。

这一步看起来只是调度层的小变化，但它非常关键。因为 GPU 的吞吐能不能高，很大程度上取决于每一轮都能不能拼出一个足够饱满的 batch。scheduler 做的事，本质上就是在各种约束下，尽可能把这一轮能推进的序列塞进去。这里的约束不只是算力预算，还包括显存预算，尤其是 KV Cache 还能不能继续装下这些活动序列。

**重点：scheduler 管的不是“谁有资格用模型”，而是“这一轮哪些序列值得被推进，以及推进它们还需要多少 KV 资源”。**

### **6.2 第二步：Block Manager 按需分配或复用 physical blocks**

当 scheduler 决定了这一轮有哪些 sequence 要进入 batch，下一步就不是马上算 attention，而是先检查这些序列的 KV Cache 还能不能继续往后长。如果某条序列当前最后一个 block 还没满，那很好，新的 token 对应的 K/V 直接写到这个 block 的下一格里就行；但如果这个 block 已经写满了，就必须再拿一个新的 physical block 出来接着写。

这就是 block manager 的职责。它不再像传统系统那样“给每个请求准备一整片大连续空间”，而是维护一个 **固定大小 physical blocks 的池子**。谁需要扩容，就从池子里拿一个 block；谁结束了，就把 block 还回来。因为所有 block 大小一致，所以分配和回收都非常直接，也不会出现传统那种“剩下一堆不规则空洞”的问题。

更重要的是，block manager 不只是负责“分配新块”，它还负责“复用旧块”。如果两个序列的历史前缀完全一致，比如 parallel sampling 的多个 sample，或者 beam search 里刚分叉之前的多个 beam，那么它们并不需要各自拿一份独立 block。block manager 可以让它们共同指向同一个 physical block，同时给这个 block 维护一个引用计数。只要内容还没分叉，共享就是安全的；只有在某个序列真的要写入不同内容时，才需要复制。

这一步的本质，是把 KV Cache 从“请求私有的一整坨内存”变成“系统统一管理的一组小页框”。从这里开始，KV 的管理方式就已经非常像操作系统里的物理页分配了。

**重点：block manager 真正管理的不是“请求”，而是“一组可以被分配、回收、共享、复用的固定大小显存块”。**

### **6.3 第三步：Block Table 把逻辑连续的序列翻译成物理离散的 KV 地址**

有了 scheduler 选出来的序列，也有了 block manager 分配好的 physical blocks，接下来还差一个关键问题：attention kernel 怎么知道这些离散的 blocks 属于哪条序列、以及应该按什么顺序去读？

这就轮到 **block table** 登场了。

可以把 block table 直接理解成 KV Cache 的“页表”。对于每一条活动序列，系统维护一张映射表，记录这条序列在逻辑上第 0 个 block、第 1 个 block、第 2 个 block……分别对应 GPU 上哪个 physical block。逻辑上它是一条连续增长的序列，物理上却可能散落在显存不同位置。正是这张表，把“逻辑连续”和“物理离散”连接了起来。

这件事非常重要，因为 attention 在数学上需要的是一段按 token 顺序排列的历史 K/V，而不关心它们在显存里是不是连续存的。也就是说，只要 block table 能告诉 kernel：这条序列前 512 个 token 在 block A，接下来的 512 个 token 在 block F，再后面一段在 block C，那么 kernel 就仍然能按正确顺序把它们读出来。对模型来说，这依然是一段连续的上下文；对系统来说，却不需要再为这段上下文保留一整片连续物理空间。

很多人第一次看到这里会突然意识到：PagedAttention 真正厉害的点，不是“块状存储”本身，而是 **通过 block table，把序列的逻辑结构和物理布局解耦了**。序列依然从左到右连续增长，但底层内存完全可以灵活摆放。

**重点：block table 是整套机制的桥梁。没有它，分页只是一堆离散块；有了它，离散块才能在逻辑上重新拼成一条连续序列。**

### **6.4 第四步：Worker 拿到 Block Table，Paged Attention Kernel 按映射去读 KV**

前面三步做的，其实都还是“准备工作”。真正进入 GPU 计算时，worker 会拿到这一轮要处理的 query、对应序列的长度信息，以及最关键的 block tables。然后 PagedAttention kernel 不再假设某条序列的 K/V 在显存里是一整段连续数组，而是根据 block table 一段一段地去找。

从执行角度看，当前 token 的 query 还是像普通 attention 一样参与计算，区别只在于历史 K/V 的读取方式。以前的实现可能是“给我一个起始地址，我顺着读完历史上下文”；现在变成“先看逻辑 block 0 对应哪个 physical block，读完它；再看逻辑 block 1 对应哪个 physical block，继续读；一直到覆盖当前序列的全部历史 token 为止”。从 kernel 的视角，这更像是一种带映射关系的 gather 读取，而不是单纯的线性扫描。

这也是为什么 paged attention kernel 必须和 block table 紧密配合。因为它不是简单在一个连续 buffer 上做 attention，而是在“分页化的 KV Cache”上做 attention。它既要保证读到的是正确的历史 token，又要尽量保持内存访问高效，比如尽可能让 warp 在读取 block 时仍然具有比较好的访问模式。也就是说，分页机制虽然解决了内存管理问题，但它也把一部分复杂度转移给了 kernel：kernel 需要理解这种分页布局，才能把它跑快。

从模型输出的角度看，这一切都不应该有任何差别。attention 的结果必须和“把全部历史 KV 连续存起来再去读”的结果一致。不同之处只在于系统不再为这个“看起来连续”的历史付出巨大的碎片和浪费成本。

**重点：PagedAttention kernel 的任务不是改变 attention 本身，而是在“物理不连续”的 KV 布局上，仍然正确且高效地完成 attention 读取。**

### **6.5 第五步：如果共享前缀要继续写，就触发 Copy-on-Write**

前面提到，多个序列是可以共享同一个 physical block 的。这个设计非常省内存，但它天然会引出一个问题：如果两条序列原本共享前缀，现在其中一条要继续写新 token，而另一条不写，或者两条从这里开始分叉了，那还能继续共用同一个 block 吗？

答案是不能直接写，否则就会把别的序列的历史也改掉。

这时就需要 **copy-on-write**。它的思路和操作系统里完全一样：只要大家读的是同一份历史，那就继续共享，不做复制；一旦某个共享 block 要被某条序列“写坏”，系统才在这一刻真正复制出一份新的 physical block，然后把当前这条序列的 block table 改成指向新块，后续写入也只发生在新块里。其他还没分叉的序列，仍然保留对旧 block 的引用。

这个机制特别适合 beam search 和 parallel sampling。因为这些场景的特点就是：前半段大量内容都相同，只有后面某一步才开始分支。如果系统从一开始就为每个 beam 或 sample 准备一整套独立 KV Cache，显存会被快速吃光。而 copy-on-write 让系统可以非常节制地复制：不分叉就不复制，真正分叉时也通常只需要处理最后那个正在被写的 block，而不是整条历史全部重拷。

所以，从工程上看，copy-on-write 不是一个“锦上添花”的优化，而是 block sharing 能成立的前提。没有它，你只能在“共享但不可写”和“可写但不共享”之间二选一；有了它，系统才能兼得前缀共享的高利用率，以及后续分叉时的正确性。

**重点：copy-on-write 让“共享历史”与“独立生成”两件事同时成立。**

### **6.6 把整条链路串起来看：一次 decode 为什么会高效**

现在把整个流程再顺一遍，就会非常清楚。

每一轮 decode 开始时，scheduler 先根据当前系统状态决定这一轮哪些序列应该进入 batch。然后 block manager 检查这些序列现有的 KV block 是否足够，不够就分配新的 physical blocks；如果多个序列共享前缀，就尽量让它们继续共享已有 blocks。接着系统把每条序列的 block table 整理好，下发给对应的 worker。worker 运行 paged attention kernel 时，不再依赖连续 KV 缓冲区，而是根据 block table 去读取这条序列真正对应的 physical K/V blocks。最后，如果某些共享 block 在这一轮需要被继续写入并产生分叉，就由 copy-on-write 机制复制必要的块、更新 block table，并继续推进后续生成。

这整条链路的意义在于，它让系统不再被“必须给每个请求一整段连续 KV Cache”这个前提绑死。请求可以动态加入、动态退出；KV 可以按 block 增长、按 block 回收；相同前缀可以共享，不同后缀再分裂。对上层模型来说，它看到的依然是正常的自回归 attention；但对底层系统来说，整个内存管理方式已经从“粗放分配”变成了“页式调度”。

这也是为什么 PagedAttention 真正解决的，不只是一个 kernel 问题，而是一个系统资源组织问题。它让 KV Cache 终于可以像成熟操作系统里的内存一样，被分页、映射、共享、复制和回收。只要这一层做对了，后面的吞吐、并发和成本，才有被真正拉起来的可能。
