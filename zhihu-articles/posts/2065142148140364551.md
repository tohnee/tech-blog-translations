大模型训练难，难在它本质上是一场显存、算力、通信的三线作战：参数一张卡放不下，就要把模型切到成百上千张卡上；切开了，每张卡在算之前还得先跟别的卡把参数要齐、算完之后把梯度归约回去——于是规模化之后，训练的瓶颈往往不在"算"，而在"通"。尤其当集群进入超节点时代，节点内是数百上千卡的高带宽互联、节点间回到普通网络，两级网络差着一个数量级，**通信该怎么组织，直接决定了这套昂贵硬件能跑出几成利用率**。 所以"如何优化大模型训练"这个问题，答案里很大一块是并行策略的设计：让每一次集合通信都不浪费一趟数据搬运，让通信的等待永远不落在计算的关键路径上。

本文介绍 hyper_parallel 中 fully_shard(FSDP2/HSDP) 实现的两个核心设计：**逐参数零拷贝下发路径**与**HSDP 反向下发时序优化**，并与 PyTorch 官方 FSDP2(torch.distributed.fsdp.fully_shard)对比。

### 0. hyper_parallel 是什么

**hyper_parallel(HyperParallel)** 是一个面向超节点的昇腾亲和分布式并行加速库，核心思想是**模型与系统优化解耦**：用户以声明式的方式描述并行策略(HSDP/TP/CP/EP)，并行、重计算、offload 等系统优化由框架隐式注入。本文的主角 fully_shard 就是其数据并行的主力实现。

> 仓库地址：[https://atomgit.com/mindspore/hyper-parallel](https://atomgit.com/mindspore/hyper-parallel)

### 1. 背景：FSDP2 通信的两个关键问题

FSDP(Fully Sharded Data Parallel)的思想大家都很熟悉：把模型参数切分到所有数据并行 rank 上，前向时通过 **all-gather(AG)** 临时收全参数、算完即释放；反向时通过 **reduce-scatter(RS)** 把全量梯度归约并切分回各 rank。HSDP(Hybrid Shard DP)在此基础上加一维”副本”：参数在副本组内分片、组间复制，梯度先做组内 RS，再做一次**跨副本组的 all-reduce(AR)**。一个典型的映射是：**分片维 = 超节点内，副本维 = 跨超节点**。

这里的”超节点”不是抽象概念。以昇腾为例，CloudMatrix 384 通过灵衢(UB)总线把 384 颗昇腾 910C 全对等互联，跨机柜带宽衰减小于 3%；最新的 Atlas 950 SuperPoD 进一步用灵衢 2.0 把 8192 颗昇腾 950DT 连成无收敛全互联。”超节点内”因此是一个带宽接近节点内、规模数百至数千卡的高带宽域，而”跨超节点”回到普通数据中心网络(RoCE 等)——两级网络的带宽和时延相差一个数量级以上，这是一切设计的前提。

思想不复杂，但要跑得快，有两个问题绕不开：

1. **通信怎么下发？** 是把一层的所有参数打包成一个融合 buffer 发一次集合通信，还是逐参数各发各的？融合要付出打包/拆包的数据搬运代价，逐参数要付出更多的通信次数。
2. **通信什么时候下发、什么时候等待？** RS/AR 与反向计算如何排布，才能既不阻塞计算、又不撑爆显存？

PyTorch 官方 FSDP2 对这两个问题给出的答案是面向通用以太网/RoCE 集群的；hyper_parallel 则针对超节点的两级网络给出了另一套答案。先看整体流程，再分别展开。

### 2. 整体流程：一次迭代里 fully_shard 在做什么

![](https://pic4.zhimg.com/v2-e6b22a3cde4f8845f818b41b73fc546f_r.jpg)

hyper_parallel 的 fully_shard 与 PyTorch FSDP2 的骨架一致：每个被管理的 module 注册 forward pre-hook / forward hook / backward hook。

- **前向**:pre-hook 中对本层参数做 unshard(all-gather 收全)，同时**预取(prefetch)下一层**的 all-gather，让通信与当前层计算重叠；post-hook 中 reshard，立刻释放全量参数，显存峰值只比”单卡分片”高出一到两层。
- **反向**:backward pre-hook 重新 unshard 参数；autograd 算出本层梯度后，post_backward 负责梯度通信的调度——这是全文第二个重点，第四节展开。
- **收尾**:root module 的 backward hook 在反向结束时统一等待所有未完成的 all-reduce，并把梯度一次性写回各参数的 `.grad`。

流程骨架一致，差异就在”通信怎么下发”和”反向里通信怎么排”这两处。

### 3. 核心设计一：逐参数零拷贝下发路径

### 3.1 torch FSDP2：只有融合下发一条路

官方 FSDP2 的通信粒度是”一个 FSDP 单元一次集合通信”。每层 all-gather 前，要先用 `torch._foreach_copy_` 把该层所有参数的 shard **拷进(copyin)**一块融合输入 buffer;all-gather 完成后，再把融合输出 buffer **拆拷(copyout)**回每个参数自己的存储。反向的 reduce-scatter 同理有一次 copyin。

也就是说，每一次集合通信的前后都各多了一遍完整的显存读写。这些拷贝 kernel 排在计算流上，挤占的是本应用来跑 matmul 的显存带宽，且这笔开销随层数与迭代次数线性放大。

### 3.2 hyper_parallel：逐参数下发，通信路径零拷贝

hyper_parallel 的默认路径(comm_fusion 关闭)是**逐参数下发**:

- all-gather 的**输入直接就是参数自己的 shard 数据**，不需要 copyin;
- all-gather 的**输出直接写进该参数专属的持久 buffer**，全量参数只是这块 buffer 上的一个视图，不需要 copyout;
- 反向 reduce-scatter 同样：梯度直接作为 RS 输入，输出直写目标 buffer。

![](https://pic1.zhimg.com/v2-960d804bb06438c9f4e7edf6ed0f8d5a_r.jpg)

两边通信总量完全一样，省掉的是通信前后的全部数据搬运。

### 3.3 超节点内，逐参数下发的代价可以忽略

对逐参数路径最常见的质疑是：”小消息、多次数，通信效率不会掉吗？”

这个质疑在跨节点网络上成立——小消息打不满带宽、launch 开销占比高，所以传统实现要靠融合攒大包。在超节点内，逐参数下发的效率并非完全没有损失，但损失足够小，而且**能够被计算完全掩盖**：一方面超节点内链路带宽高、时延低，单参数级别的消息已经足够大，逐参数与融合下发的带宽差距很小；另一方面，all-gather 本来就通过 prefetch 隐藏在计算背后，reduce-scatter 也通过异步下发与反向计算重叠——通信不暴露在关键路径上，这点损失就不会体现到端到端耗时里。此时再去追求融合，省下的 launch 开销看不见，copyin/copyout 白烧的显存带宽却是实打实的。**在超节点内，零拷贝的逐参数下发就是更优解。**

### 3.4 HSDP 的两级策略：跨超节点融合 AR，而且融合也零拷贝

HSDP 还有第二级通信：跨超节点的 all-reduce。跨超节点走的是普通数据中心网络，带宽稀缺、时延高——这里融合是对的。hyper_parallel 的策略是**按拓扑分级**:

- **超节点内**(分片维):all-gather / reduce-scatter 逐参数下发，零拷贝；
- **跨超节点**(副本维):all-reduce 融合下发，一层的参数梯度合并成一次跨节点集合通信。

关键在于，这个融合 AR 本身也不需要 copyin/copyout。实现上依靠 `AllReduceParamGroup` 维护的一块 **512 字节对齐的连续融合 buffer**:

1. 反向时逐参数下发的 reduce-scatter,**输出直接写进融合 buffer 中各参数的视图**(buffer 提前置零，padding 区域不影响 SUM 语义)——AR 的输入天然就是拼好的大包，零 copyin;
2. 对整个融合 buffer 只发一次跨超节点 all-reduce;
3. AR 完成后，各参数直接从自己的 buffer 视图读出梯度写回 `.grad`——零 copyout。

![](https://pic2.zhimg.com/v2-e95224d65ff4087af65ee6622ecd4839_r.jpg)

一句话总结：**超节点内用零拷贝换带宽，跨超节点用融合换次数，靠”RS 输出直写 buffer 视图”让两者不再矛盾。**

### 4. 核心设计二：HSDP 反向下发时序优化，all-reduce 零阻塞

### 4.1 torch FSDP2 的时序：同层 RS/AR 背靠背

官方 FSDP2 在 HSDP 模式下，每层的 post_backward 里把 RS 和 AR **背靠背链式下发**:AR 流等待本层 RS 流完成即启动，靠多条 stream + event 做跨流同步。每层的 AR event 由该层状态自行保管，在该层下一轮 post_backward、buffer 复用等位置回查等待。

这套机制能工作，但有两个结构性弱点：

- **AR 的启动被锁死在本层 RS 完成之后**，同层链式依赖，跨层之间没有流水；
- **AR event 的生命周期管理复杂**，每层都要带着自己的 event 状态跨迭代传递，任何需要触碰梯度或复用 buffer 的地方都要回查等待。

### 4.2 hyper_parallel：post_backward 四步流水

hyper_parallel 把梯度通信的调度显式组织成一条**跨层软件流水**。每一层的 post_backward 固定做四件事:

1. **wait 上一层的 RS**——此时当前层的反向计算已经跑完，上一层的 RS 已与这段计算重叠完毕，wait 几乎不花时间；
2. **结算无需 AR 的参数**(纯 FSDP 参数或单副本参数)的梯度；
3. **下发当前层的 RS**——逐参数下发，输出直写本层 `AllReduceParamGroup` 融合 buffer 的视图(零拷贝，见 3.4);
4. **异步下发上一层的融合 AR**——上一层 RS 已在第 1 步确认完成，AR 即刻启程，handle 挂入全局 pending 队列，**不等待**。

由此形成两级重叠:

- 层 N 的 RS ↔ 层 N-1 的反向计算；
- 层 N 的 AR ↔ 层 N-1 及其后续各层的反向计算。

注意第 3、4 步的顺序：**先发当前层的 RS，再发上一层的 AR**，而不是 wait 完上一层 RS 就立刻发它的 AR。这个顺序是按”死线”排的优先级：本层 RS 的死线是下一层 post_backward 的第 1 步（窗口只有一层反向计算），而上层 AR 的死线是 root hook（窗口是整个剩余反向）。通信的执行资源是共享的，若让慢 AR 先占住资源，快 RS 的完成时间被推迟，下一层第 1 步的 wait 就从”近似零开销”变成真阻塞，并逐层传导；反过来先发 RS,AR 只晚上路一个超节点内 RS 的时长，对它宽裕的死线毫无影响。快通信先行、慢通信吃余量，这是这条流水每层都不堵的关键。

### 4.3 root hook 统一结算：反向全程对 AR 零阻塞

整条反向链路里，**没有任何一处等待 AR**:host 侧只负责下发，AR 的 handle 逐层挂到全局 pending 队列。直到 root module 的 backward hook——整个反向计算已经全部结束——才统一做两件事:

1. wait 所有 pending 的融合 all-reduce;
2. 把各参数的最终梯度一次性写回 `.grad`。

![](https://pica.zhimg.com/v2-108a49c009c679110ac71ee211682cd8_r.jpg)

AR 的等待点从”每层各自维护 event、多处回查”收敛为”root 一处统一等待”：反向期间梯度通信对计算完全不可见，all-reduce 实现真正意义上的零阻塞。

### 4.4 与 TP/CP/EP 通信域共存：消除”快通信等慢通信”的倒挂

先澄清一个前提：反向阶段的 RS 依赖本层梯度的计算结果(梯度由计算流产出)，这是数据依赖，无法也不需要消除；真正与计算流无数据依赖的是前向的 all-gather，但 AG 是前向通信。所以问题不在于”HSDP 通信能否脱离计算流”，而在于**它的等待点落在哪里，会不会把计算流上的其他通信拖下水**。

实际训练是多维混合并行：TP 的 all-gather/reduce-scatter、EP 的 all-to-all、CP 的 ring 通信都同步排在计算流上、穿插在每层反向计算之间，而且几乎都是超节点内的快通信；HSDP 的跨超节点 AR 是全场最慢的通信。一旦反向中存在”等待 AR”的同步点——无论 host 阻塞式等待，还是把 AR event 挂到计算流上回查——排在其后的 TP/CP/EP 集合通信全部被迫排队：快通信等慢通信，跨节点的长耗时被逐层放大。

四步流水从三个位置拆掉这种耦合：

1. **RS 的等待点后置一层**。wait 上一层 RS 时，它已与当前层整段反向计算(含其中的 TP/CP/EP 通信)重叠完成，近似零开销。若在本层 post_backward 同步等待，host 停在原地，后续反向 kernel(包括 TP/CP/EP 集合通信)的下发全被推迟——RS 本是超节点内的快通信，却成了反向的堵点；
2. **AR 只下发、不等待**。AR 的下发只依赖本层 RS 完成(通信流内部依赖)，与计算流上 TP/CP/EP 的排队深度无关，总能尽早启程，把跨节点慢通信的耗时摊进整个反向窗口；反过来，计算流上不存在任何等待 AR 的同步点，快通信永远不会排在慢通信身后；
3. **唯一的 AR 等待在 root hook**。此刻反向(含全部 TP/CP/EP 通信)已结束，等待一次付清，没有任何后续算子会被它阻塞。

对比来看，torch FSDP2 每层各自保管 AR event，在 buffer 复用、下一轮 post_backward、迭代状态重置等多处回查——标准路径下可以工作，但在梯度累积、chunked loss、部分层未参与反向等非标准路径下，慢通信依赖容易从某个回查点泄漏进反向关键路径。hyper_parallel 的”只下发 + root 一处 wait”结构更简单，也从机制上保证了反向期间计算流对跨超节点 AR 零依赖。超节点内外一个数量级以上的带宽/时延差，决定了慢通信必须被彻底隔离出反向关键路径。

### 5. 总结

| 维度 | PyTorch 官方 FSDP2 | hyper_parallel fully_shard |
| --- | --- | --- |
| 通信下发粒度 | 只有融合下发(每单元一次集合通信) | 逐参数下发(默认)+ 可选融合下发 |
| copyin/copyout | 每次 AG/RS 前后各一遍显存读写 | 逐参数路径零拷贝 |
| 拓扑感知 | 无差别对待各级网络 | 超节点内逐参数、跨超节点融合 AR |
| 跨副本 AR 的融合代价 | AR 直接打在 RS 输出上(零拷贝) | RS 输出直写对齐 buffer 视图，融合且零拷贝 |
| RS/AR 时序 | 同层背靠背链式下发，event 逐层维护 | post_backward 四步跨层流水 |
| AR 等待点 | 分散在各层 event 回查 | root hook 统一 wait + 统一写回，反向零阻塞 |
| 与 TP/CP/EP 共存 | AR event 逐层保管、多处回查，非标准路径下慢通信依赖易泄漏进关键路径 | AR 只下发、root 一处 wait，慢通信彻底隔离出反向关键路径 |

两项设计贯彻的是同一个思路：**把通信的数据搬运成本和时序耦合成本都压到零**——前者靠逐参数零拷贝下发和 buffer 视图融合，后者靠跨层流水与 root 统一结算。

### 6. 落地进展与开源计划

- **MindFormers**:hyper_parallel 已在 MindFormers 落地多维混合并行(含本文介绍的 fully_shard)，支撑实际的大模型训练业务；
- **Pangu**：已完成对 Pangu 基于 Megatron 训练框架的训练流程的适配，支持 TP/EP/CP；在超节点下可替代流水线并行(PP)，以更简单的并行配置支撑万亿规模模型训练。适配代码将随 Pangu 训练仓一起开源；
- **torch 生态(开发中)**：基于 torch、完整兼容 HuggingFace 生态的类 Titan 声明式编程套件，性能对标 Megatron。

欢迎持续关注 hyper_parallel 仓库与 Pangu 训练仓的开源进展。
