这篇文章主要介绍通用的单卡显存优化方法。

## 1. PyTorch的显存管理机制

显存的分配和内存的分配极为类似。为了方便Porch频繁访问显存，PyTorch引入了显存池机制。简单来说，每次PyTorch不会只申请刚好和请求对应的显存大小，而是一次性申请一个更大块的显存空间，多出来的作为缓存。

**PyTorch 显存池（CUDA Caching Allocator）**

> PyTorch 不会在每次创建/销毁 Tensor 时都向 CUDA 驱动申请或归还显存，而是自己维护一个显存池，尽量复用已经申请到手的显存。

理解了这一点，就能解释一个非常常见的困惑：**为什么 `nvidia-smi` 显示占用很高，`torch.cuda.memory_allocated()` 却小得多。**

### **1. 为什么需要显存池**

考虑这样一段反复申请、释放的代码：

```python3
x = torch.randn(1024, 1024, device="cuda")   # 4 MB (float32)
del x

x = torch.randn(1024, 1024, device="cuda")
del x
```

如果每一次都老老实实走驱动：

```text
PyTorch → CUDA Driver → cudaMalloc
PyTorch → CUDA Driver → cudaFree
```

问题在于 `cudaMalloc` / `cudaFree` 都是**同步且昂贵**的操作：它们会打断 CUDA stream，代价远高于一次 kernel launch。训练循环里每步成千上万次分配，开销完全不可接受。

于是 PyTorch 的做法变成：

![](https://pic2.zhimg.com/v2-27bc35181423da015eb5366f41c24691_r.jpg)

这就是 **Caching Allocator**：用「不归还」换取「后续分配几乎零成本」。

### **2. 两个必须分清的指标**

```python3
torch.cuda.memory_allocated()
torch.cuda.memory_reserved()
```

allocated —— 真正被 Tensor 占用的显存

即当前所有活着的 Tensor 占用的字节数（每次分配会向上对齐到 512 B，所以会略大于理论张量大小）。

```python3
Tensor A：10 GB
Tensor B：20 GB
→ memory_allocated() ≈ 30 GB
```

reserved —— PyTorch 从驱动手里拿过来的总量

即显存池的总规模，其中一部分正在被使用，一部分是缓存着的空闲显存。

```text
GPU
│
├── PyTorch Reserved：50 GB
│     ├── Tensor 正在使用：30 GB   ← allocated
│     └── 池内空闲（cached）：20 GB
│
└── PyTorch 之外：30 GB
```

所以恒有：

```text
reserved ≥ allocated
```

两者的差值 = 缓存起来备用的空闲显存，**不是泄漏**。

### **3. 为什么 `nvidia-smi` 和 allocated 对不上**

典型场景：

```python3
torch.cuda.memory_allocated()   # 20 GB
torch.cuda.memory_reserved()    # 50 GB
```

而 `nvidia-smi` 显示：

```text
GPU Memory Usage: 52 GB
```

拆开看就很清楚：

```python3
nvidia-smi 看到的 52 GB
│
├── PyTorch reserved：50 GB
│     ├── allocated：20 GB
│     └── cached/free：30 GB   ← 仍归 PyTorch 池管理，可被后续 Tensor 直接复用
│
└── 其他开销：约 2 GB
      ├── CUDA context（几百 MB ~ 1 GB+）
      ├── cuBLAS / cuDNN workspace
      └── NCCL 通信 buffer 等
```

结论：

- **`nvidia-smi` ≥ reserved ≥ allocated** 是正常现象；
- 驱动只知道「这块显存被进程要走了」，看不到 PyTorch 池内部是空闲还是在用；
- 想把池内空闲部分真正还给驱动，需要显式调用 `torch.cuda.empty_cache()`（注意：它只能归还**完全空闲的整段**，且会让下一轮分配重新变慢，不建议在训练循环里频繁调用）。

### **4. 池内部结构：Segment 与 Block**

显存池并不是一整块 80 GB 的大数组，而是分层管理的：

- **Segment**：一次 `cudaMalloc` 拿到的连续显存段；
- **Block**：在 segment 内部切分出来的小块，才是真正分给 Tensor 的单位。

```python3
PyTorch Caching Allocator

Segment #1（连续 1 GB）
├── Block 1：256 MB   allocated
├── Block 2：512 MB   free
└── Block 3：256 MB   allocated

Segment #2（连续 20 MB）
├── Block 1：  8 MB   allocated
└── Block 2： 12 MB   free
```

PyTorch 还把池分成两套：小于等于 1 MB 的分配走 **small pool**，更大的走 **large pool**，避免小张量把大段显存搅碎。

一次分配的流程大致是：

```text
申请 500 MB
      ↓
在池中找一个 ≥ 500 MB 的连续空闲 block
      ↓
找到 512 MB 的那块
      ↓
切一块给你（剩余部分继续留在池中）
      ↓
全程不打扰 CUDA Driver
```

只有在池里确实找不到合适 block 时，才会向驱动申请新的 segment。

### **5. 碎片：free 很多 ≠ 能分配得出来**

假设池里现在的空闲块是这样：

```text
free blocks（分散在不同位置）：
100 MB
100 MB
100 MB
100 MB
100 MB
------------
合计 500 MB free
```

此时你申请 **400 MB**：

```text
总空闲 500 MB ✓
但没有任何一个连续的 400 MB block ✗
```

分配失败 —— 这就是**显存碎片（fragmentation）**。

它是训练中「明明还剩不少显存却报 OOM」的最常见原因之一。PyTorch 的 OOM 报错信息里通常会同时打印 reserved、allocated 和 free，一旦发现 `reserved - allocated` 很大却仍然 OOM，基本可以断定是碎片问题。

值得一提的是，在真正抛出 OOM 之前，PyTorch 会先自动释放所有**完全空闲的 segment** 再重试一次；如果剩下的空闲块都夹在正在使用的 block 之间，无法整段归还，就只能失败。

### **6. Allocator 如何对抗碎片**

**Split（切分）**

一个 1 GB 的空闲 block，只需要 300 MB 时：

```text
[1 GB free]
      ↓
[300 MB allocated][700 MB free]
```

避免为小请求浪费整块大显存。

**Merge / Coalesce（合并）**

同一 segment 内相邻的空闲 block 会被合并：

```text
[300 MB free][700 MB free]
            ↓
        [1 GB free]
```

**注意：合并只能发生在同一个 segment 内部。** 不同 `cudaMalloc` 拿到的段之间即使地址相邻也不会合并 —— 这正是碎片无法被彻底消除的根本原因。

**可以手动调整的开关**

通过环境变量 `PYTORCH_CUDA_ALLOC_CONF` 配置：

| 选项 | 作用 |
| --- | --- |
| expandable_segments:True | 用虚拟地址映射让 segment 可按需增长，从机制上大幅缓解碎片，是目前最推荐的第一手段 |
| max_split_size_mb:<N> | 禁止把大于 N MB 的 block 切分，保护大块显存不被小请求打碎 |
| garbage_collection_threshold:<比例> | 池占用超过阈值时主动回收空闲 block |

例如：

```text
PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True python train.py
```

### **7. 排查工具速查**

| 目的 | 方法 |
| --- | --- |
| 当前张量占用 | torch.cuda.memory_allocated() |
| 池的总规模 | torch.cuda.memory_reserved() |
| 历史峰值 | torch.cuda.max_memory_allocated() / max_memory_reserved() |
| 完整统计 | torch.cuda.memory_stats() / memory_summary() |
| 逐次分配的调用栈 | torch.cuda.memory._record_memory_history() + _dump_snapshot()，导出后用 [http://pytorch.org/memory_viz](http://pytorch.org/memory_viz) 可视化 |
| 归还空闲显存给驱动 | torch.cuda.empty_cache()（仅在需要给其他进程腾地方时使用） |

### **小结**

1. PyTorch 用显存池缓存显存，避开昂贵的 `cudaMalloc` / `cudaFree`；
2. `allocated` 是张量实际占用，`reserved` 是池的总量，`nvidia-smi` 还要再加上 CUDA context 等开销；
3. 三者层层递增，属于正常现象，不是内存泄漏；
4. 池内以 segment / block 组织，靠 split 与 merge 复用显存；
5. 跨 segment 无法合并 ⇒ 碎片不可避免 ⇒ 「有空闲却 OOM」；
6. 遇到碎片型 OOM，优先尝试 `expandable_segments:True`，再考虑 `max_split_size_mb`。

## 2. 训练显存都花在哪儿了

先看全景（在你原有分类基础上补了 CUDA Context 一项——它经常被忽略，但每个进程都要交这份”入场费”）：

```python3
训练显存
│
├── 0. CUDA Context / 驱动开销
│   └── 每进程 0.3 ~ 1 GB+，进程一起来就存在，省不掉
│
├── 1. 模型状态（Model States）
│   ├── Parameters        参数
│   ├── Gradients         梯度
│   └── Buffers           BatchNorm running stats、RoPE cache、mask 等
│
├── 2. 优化器状态（Optimizer States）
│   ├── Momentum / m
│   ├── Variance / v
│   └── FP32 Master Weights（混合精度）
│
├── 3. Activation
│   └── Forward 为 Backward 保存的中间结果
│
├── 4. 临时工作空间（Temporary / Workspace）
│   ├── GEMM / cuBLAS workspace
│   ├── Attention workspace
│   ├── cuDNN workspace
│   └── 算子内部临时 Tensor
│
├── 5. 通信 Buffer
│   ├── NCCL 内部 buffer
│   ├── DDP gradient bucket
│   └── FSDP/ZeRO 的 AllGather / ReduceScatter buffer
│
└── 6. Allocator 保留的 Cached Memory
    └── PyTorch 显存池中暂时空闲、但未归还驱动的部分
```

这六类里，**真正需要你动手优化的只有 1、2、3**，其余更多是”知道它存在、别把它算成泄漏”。

### 一个更有用的切法：静态 vs 动态

按”随什么增长”重新分组，比按来源分组更贴近调参时的直觉：

| 类别 | 随什么增长 | 与 batch/seq 相关？ |
| --- | --- | --- |
| 参数 / 梯度 / 优化器状态 | 模型规模 | 无关 |
| Activation | batch × seq × 层数 | 线性甚至更快 |
| Workspace | 单个算子的规模 | 相关，但量小 |
| 通信 Buffer | 并行策略与桶大小 | 基本无关 |
| CUDA Context | 固定 | 无关 |

所以调 batch size 时上下浮动的几乎全是 Activation；而”模型刚 `.cuda()` 完就占了一大半”说的是模型状态。这两类的优化手段完全不同，先分清是哪一类再动手。

### 1 + 2. 模型状态与优化器状态：算得清的那部分

这两块可以精确到”每个参数几字节”。以最主流的 **bf16 混合精度 + Adam** 为例：

```text
每个参数：

bf16 参数        2 B
bf16 梯度        2 B
fp32 master      4 B  ┐
fp32 momentum    4 B  ├── 优化器状态，共 12 B
fp32 variance    4 B  ┘
─────────────────────
合计            16 B / param
```

代入模型规模：

```text
7B  模型 → 约 112 GB
13B 模型 → 约 208 GB
70B 模型 → 约 1.1 TB
```

一张 80 GB 的卡连 7B 的全参微调都放不下——**这就是 ZeRO / FSDP 存在的全部理由**：把这 16 B/param 沿数据并行维度切开。

几个常见变体：

| 配置 | 每参数字节 |
| --- | --- |
| bf16 + Adam（上表） | 16 B |
| bf16 + 8-bit Adam | 10 B |
| bf16 + SGD momentum | 8 B |
| 纯 fp32 + Adam | 16 B（但 activation 翻倍） |
| LoRA（base 冻结） | 2 B + 极小的可训练部分 |

Buffers 通常可以忽略（BN 的 running stats 只有 channel 量级），但有两个例外值得留意：因果 mask 若被物化成 `[b, 1, s, s]`，长序列下大得吓人；推理时的 KV cache 也归在这一类，且会随生成长度持续增长。

### 3. Activation：唯一由你实时掌控的大头

Forward 过程中，凡是 Backward 还要用到的中间结果都得留着。比如 `y = x @ W`，求 `dW` 需要 `x`，所以 `x` 在整个 forward 期间不能释放。层数越深，攒的越多。

Transformer 单层的激活量有个常用估算（bf16、无重计算）：

```text
per_layer ≈ s · b · h · (34 + 5 · a · s / h)   字节

s: 序列长度   b: micro-batch   h: hidden   a: 注意力头数
```

括号里的第二项带着 `s²`——**序列长度翻倍，注意力那部分激活翻四倍**。这也是长上下文训练最先炸显存的地方（用了 FlashAttention 后这一项基本消失，因为它不再物化 `s × s` 的注意力矩阵）。

主要手段：

- **梯度检查点（gradient checkpointing）**：只存每层入口，backward 时重算。显存从 `O(L)` 降到约 `O(√L)`，代价是多约 30% 的前向计算。性价比最高的一招。
- **减小 micro-batch，靠梯度累积补回等效 batch**：最直接，不改模型。
- **FlashAttention**：消掉 `s²` 项。
- **序列并行 / 张量并行**：把激活沿 seq 或 hidden 维度切开。

峰值出现的时机也值得记一下：**通常在 forward 结束、backward 刚开始的瞬间**，此时激活攒到最满、梯度开始逐个分配。此外 optimizer step 也常有一个尖峰（fused optimizer 会好很多）。所以 OOM 报在哪一行，往往不代表那行本身有问题。

### 4. Workspace：量不大，但会制造碎片

cuBLAS 为某些 GEMM 形状申请的暂存区、cuDNN 卷积算法的工作区、算子内部的临时张量，单个通常在几 MB 到几百 MB。

两点实际影响：

- cuDNN 的 `benchmark=True` 会在首次运行时试跑多种算法，**试跑期间的显存峰值可能明显高于稳态**——不少”第一个 step 就 OOM，后面反而没事”是这个原因；
- 这类 buffer 生命周期短、大小不规整，是显存碎片的常见来源之一。

### 5. 通信 Buffer：分布式下容易被漏算的一块

- **NCCL 内部 buffer**：每个通信 channel 一份，由 `NCCL_BUFFSIZE` 控制，通常几十到几百 MB 量级；
- **DDP gradient bucket**：DDP 会把梯度打包成桶再 AllReduce，`bucket_cap_mb` 默认 25 MB，这是**额外的一份拷贝**；
- **FSDP / ZeRO-3**：计算某层前要 AllGather 出完整参数，开了 prefetch 时同时驻留的可能是两层的完整参数。这部分是实打实的显存开销，估算模型状态时经常被忘掉。

单卡调通、一上多卡就 OOM，八成出在这里。

### 6. Allocator Cached Memory

这一项不是”消耗”，而是 PyTorch 显存池里已从驱动拿到、暂时没被张量占用的部分，可被后续分配直接复用（详见《PyTorch 显存池》一文）。判断标准：

```text
memory_reserved() - memory_allocated()   ← 这就是第 6 项
```

差值大且伴随 OOM，说明是碎片问题而非真的不够用，优先试 `expandable_segments:True`。

### 对症下药速查

| 症状 | 大概率是哪一类 | 先试什么 |
| --- | --- | --- |
| 模型加载完就占满 | 1 + 2 | ZeRO / FSDP、LoRA、8-bit optimizer |
| batch 加一点就炸 | 3 | 梯度检查点、减小 micro-batch |
| 长序列时炸 | 3（s² 项） | FlashAttention、序列并行 |
| 第一个 step 炸，之后正常 | 4 | 关掉 cudnn.benchmark |
| 单卡好好的，多卡就炸 | 5 | 调小 bucket_cap_mb、关 FSDP prefetch |
| reserved 远大于 allocated 却 OOM | 6 | expandable_segments:True |

### 一句话总结

显存 = **固定成本**（context + 模型状态 + 优化器状态）+ **可调成本**（activation）+ **零碎开销**（workspace + 通信 buffer）+ **看起来占了其实没占**（allocator cache）。

先用 `torch.cuda.memory_summary()` 或 memory snapshot 看清楚自己卡在哪一层，再选手段——不然很容易在错误的地方使劲。

## 3. 推理过程中的显存占用

### 1、全景图

先建立整体认知，推理时 GPU 显存被以下几类内容占据：

```text
推理显存
│
├── 0. CUDA Context / Runtime 开销
│   └── CUDA Context、CUDA Runtime、cuBLAS / cuDNN 等
│
├── 1. 模型状态（Model States）
│   ├── Parameters   模型权重
│   └── Buffers      RoPE 表、LayerNorm 参数、mask 等
│
├── 2. KV Cache
│   ├── K Cache
│   └── V Cache
│
├── 3. Activation / 临时 Tensor
│   ├── 输入 embedding
│   ├── Attention 中间结果
│   ├── FFN 中间结果
│   └── logits 等
│
├── 4. Workspace / Temporary Buffer
│   ├── GEMM workspace
│   ├── FlashAttention workspace
│   └── 各类算子临时空间
│
├── 5. 通信 Buffer（多卡推理）
│   ├── NCCL Buffer
│   ├── AllReduce
│   └── AllGather / All-to-All
│
└── 6. Allocator Cached Memory
    └── PyTorch / CUDA 显存池中暂时空闲的显存
```

对大模型推理而言，真正需要重点关注的只有两项：

> **① 模型权重 + ② KV Cache**

其余各项通常只是相对较小的运行时开销。

### 2、模型权重：最基本的固定成本

模型一旦加载到 GPU，这部分显存就被占住了。

以 **3B 模型**为例：

| 精度 | 每参数字节数 | 权重显存 |
| --- | --- | --- |
| FP32 | 4 B | ≈ 12 GB |
| BF16 / FP16 | 2 B | ≈ 6 GB |
| INT8 | 1 B | ≈ 3 GB |
| INT4 | 0.5 B | ≈ 1.5 GB |

结论很直接：

```text
模型越大 / 精度越高
        ↓
   权重显存越大
```

而且它与 batch size、sequence length **基本没有直接关系**：

```text
3B BF16

batch = 1   → ≈ 6 GB
batch = 8   → ≈ 6 GB
batch = 32  → ≈ 6 GB
```

权重不会因为 batch 增大而复制多份。

### 3、KV Cache：LLM 推理最关键的动态显存

这是训练与推理最重要的区别之一。

生成式 Transformer 在 **Decode 阶段**，每生成一个 token，都需要用到之前所有 token 的 Key / Value。如果每步都重新计算，计算量会随序列长度平方级膨胀。

因此把已经算过的 K、V 缓存下来：

```text
KV Cache
│
├── Layer 1
│    ├── K
│    └── V
│
├── Layer 2
│    ├── K
│    └── V
│
...
└── Layer L
     ├── K
     └── V
```

### 3.1 粗略估算公式

对于标准 Multi-Head Attention（MHA）：

```text
KV Cache ≈ 2 × Layers × Batch × SeqLen × HiddenSize × bytes
```

| 符号 | 含义 |
| --- | --- |
| 2 | K + V 两份 |
| Layers | Transformer 层数 |
| Batch | 同时服务的请求数 |
| SeqLen | 当前上下文长度（prompt + 已生成 token） |
| HiddenSize | 隐藏维度 |
| bytes | FP16 / BF16 通常为 2 |

> **补充：GQA / MQA 的修正**<br> 现代模型大多使用 GQA / MQA，KV 头数少于 Q 头数，公式中的 `HiddenSize` 应替换为 `num_kv_heads × head_dim`。例如 32 个 Q 头、8 个 KV 头时，KV Cache 直接降到 MHA 的 1/4， 这正是 GQA 被广泛采用的核心原因之一。

### 3.2 一个直观的例子

以一个 32 层、hidden = 4096 的模型为例（FP16）：

- **MHA**：每 token 每层 `2 × 4096 × 2 B = 16 KB`，32 层即 **512 KB/token** → 8K 上下文、batch = 1 约需 **4 GB**
- **GQA（8 KV 头，head_dim = 128）**：每 token 仅 **128 KB** → 8K 上下文、batch = 1 约需 **1 GB**

### 3.3 关键特性

**KV Cache 随 batch 和 sequence length 线性增长。**

这也解释了推理中最常见的一类现象：

```text
模型权重还能放下
        ↓
   但上下文一长
        ↓
       OOM
```

### 4、Activation：推理也有，但与训练完全不同

推理当然也会产生 activation：

```text
Input → Embedding → Attention → FFN → ... → Logits
```

关键区别在于**是否需要为 backward 保留**。

**训练：**

```text
Forward
   ↓
保存大量 Activation
   ↓
Backward
   ↓
计算 Gradient
```

**推理：**

```text
Forward
   ↓
Activation
   ↓
用完即释放
   ↓
下一层
```

所以推理的 activation 是**临时性**的，不会像训练那样随层数累积。

> 因此在大模型推理中，**KV Cache 远比普通 activation 更值得关注**。

一个例外是 **Prefill 阶段**：长 prompt 一次性进入模型，中间激活和 logits 可能形成明显的显存尖峰。

### 5、Workspace / Temporary Buffer

某些算子在执行时需要临时工作空间，例如：

- GEMM（cuBLAS）
- FlashAttention
- TensorRT / 自定义 CUDA Kernel

特点是：

```text
生命周期短
      ↓
用完释放 / 复用
```

一般不是显存大头，但可能导致：

- 显存**峰值**抬高
- 显存**碎片**
- 某些特殊 shape 下显存突然增加

### 6、多卡推理的通信显存

当模型使用以下并行策略时：

- Tensor Parallel
- Pipeline Parallel
- Expert Parallel

卡间需要频繁通信：

```text
GPU0 ←→ GPU1 ←→ GPU2 ...
```

对应的 `AllReduce` / `AllGather` / `All-to-All` 都需要 NCCL Buffer，这部分同样占用显存。

**MoE 尤其明显：**

```text
Expert Parallel
      ↓
   All-to-All
      ↓
Token 在 GPU 之间交换
```

此时通信 Buffer 可能显著增大。

### 7、Allocator Cache

与训练一样，需要区分两个指标：

```text
torch.cuda.memory_allocated()   # 实际分配给张量的显存
torch.cuda.memory_reserved()    # PyTorch 向 CUDA 申请的总显存
```

两者往往不相等：

```text
Reserved  = 20 GB
Allocated = 15 GB
──────────────────
差值        5 GB
```

这 5 GB 只是 PyTorch CUDA allocator **缓存起来准备复用**的显存。

> 所以 `reserved − allocated` **不能**理解为“模型真的用了这么多显存”。

### 8、总结公式

完整版：

```text
Inference Memory
≈ Model Weights
+ KV Cache
+ Activation / Temporary
+ Runtime / Communication
+ Allocator Cache
```

面试记忆版：

> **推理显存 ≈ 模型权重 + KV Cache + 运行时开销**

其中两个主导项的行为完全不同：

| 组成 | 主要决定因素 | 特性 |
| --- | --- | --- |
| 模型权重 | 参数量 × 参数精度 | 相对固定 |
| KV Cache | Batch × Sequence Length | 动态增长 |

### 9、训练 vs 推理

| 显存组成 | 训练 | 推理 |
| --- | --- | --- |
| 模型参数 | ✓ | ✓ |
| Gradient | ✓ | ✗ |
| Optimizer State | ✓ | ✗ |
| Activation | 大量保存 | 临时 |
| KV Cache | 通常不是主要矛盾 | 核心显存之一 |
| Workspace | ✓ | ✓ |
| Communication Buffer | ✓ | 多卡时 ✓ |
| Allocator Cache | ✓ | ✓ |

一句话总结：

> **训练显存主要是 Parameter + Gradient + Optimizer + Activation； 推理显存主要是 Weight + KV Cache。**

对 LLM 推理，还可以进一步按阶段拆分：

```text
Prefill：Weight + Activation + KV Cache
Decode： Weight + KV Cache + 少量 Activation / Temporary
```

Decode 阶段随着 token 逐个生成，KV Cache 持续增长。因此在**长上下文、高并发**场景下，KV Cache 往往成为推理显存的主要瓶颈——这也正是 PagedAttention、KV Cache 量化、KV Cache 卸载等技术的出发点。

## 4. 显存复用的通用手段

### 4.1 总纲：时间维度上的轮流使用

显存复用的核心思想只有一句：

> **让同一块物理显存在时间维度上被多份数据轮流使用。**

所有具体手段都可以归入”拿别的资源去换显存”这一框架。按**换出去的是什么**来划分，可分为六类：不付代价的复用、拿计算换、拿带宽换、拿精度换、拿可训练参数换，以及调度层面的复用。本章依次展开，并在 4.7 节给出统一的权衡表。

### 4.2 不付代价的复用（框架层面）

这一类是纯粹的浪费消除，不牺牲任何东西，因此应当最先做。

### 4.2.1 原地操作（in-place）

`relu_()`、`add_()`、`x += y` 等操作复用输入张量的存储，省掉输出张量的分配。

需要注意的是，只有当该输入在 backward 中不再需要时，原地操作才是安全的。PyTorch 的 autograd 会对不安全的情形自动报错拦截，不必担心静默出错。

### 4.2.2 算子融合

把 `LayerNorm → Linear → GELU` 融合成一个 kernel，中间张量根本不落显存。这是 torch.compile、TensorRT、Triton 的主要收益之一，显存与速度同时受益。

### 4.2.3 静态图的内存规划

编译器对张量做生命周期（liveness）分析，把生命周期不重叠的张量分配到同一块地址上。XLA 的 buffer assignment、TensorRT 的 memory pool 都基于这一原理，其本质是一个图着色问题。

这也是静态图框架的显存占用通常低于 eager 模式的原因。

### 4.2.4 分配器层面的复用

即第一章讨论的 split / merge 机制，以及 `expandable_segments:True`。

### 4.2.5 消除意外持有

最典型的错误是 `total_loss += loss`——它会把整张计算图挂住无法释放，正确写法是 `total_loss += loss.item()`。另一个常见疏漏是推理时忘记 `torch.inference_mode()`。

这类问题不属于”优化”，而属于”修 bug”，但在实践中出现频率很高。

### 4.3 拿计算换显存（Recompute）

**梯度检查点（gradient checkpointing）**——只保存每层入口，backward 时重算中间结果。激活显存从 $O(L)$ 降至约 $O(\sqrt{L})$，代价是约 30% 的额外前向计算。

**选择性重算（selective recompute）**——Megatron 的做法：只重算 attention 中那些”显存占用大但计算便宜”的部分（softmax、dropout 的中间结果），保留 GEMM 的输出。显存收益接近全量重算，而计算代价只有百分之几，性价比明显更优。

**FlashAttention**——不物化 $s \times s$ 的注意力矩阵，转而在线重算 softmax。就机制而言，它本质上也属于这一类。

### 4.4 拿带宽换显存（Offload）

思路是把暂时不用的数据挪到 CPU 内存甚至 NVMe，需要时再搬回来。按外放对象分为三种：

- **优化器状态 offload**（ZeRO-Offload）——optimizer state 每个 step 只用一次，最适合外放；
- **参数 offload**（ZeRO-Infinity）；
- **激活 offload**——forward 时搬出，backward 前预取回来。

**这类方案的成败点在于通信与计算的重叠。** 若 prefetch 做得不好，PCIe 带宽会直接成为瓶颈，训练速度可能下降一半以上。

### 4.5 拿精度换显存（Quantization）

**表 4.1 各类对象的量化手段与收益**

| 对象 | 手段 | 收益 |
| --- | --- | --- |
| 权重 | BF16 → INT8 / INT4 | 2× ~ 4× |
| 优化器状态 | 8-bit Adam | 12 B → 6 B/param |
| 激活 | FP8 | 2× |
| KV Cache | FP8 / INT8 / INT4 | 2× ~ 4× |
| 梯度 | 通信前压缩 | 主要节省通信 |

在推理场景下，**KV Cache 量化的性价比通常最高**，因为它同时缓解显存容量与访存带宽两个瓶颈。

### 4.6 拿可训练参数换显存（PEFT）

**LoRA / QLoRA**——base 模型冻结，梯度与优化器状态只对少量新增参数存在。式 (2.1) 中那 16 B/param 由此塌缩为 2 B/param 加上极小的可训练部分。

当全参微调放不下时，这是最有效的一招。

### 4.7 调度层面的复用

这一类在推理侧尤为重要。

**micro-batch + 梯度累积**——最朴素也最直接的手段，等效 batch size 保持不变。

**PagedAttention**——把 KV Cache 切成固定大小的 page，按需分配、非连续存放。它解决的正是第 1.5 节所述的碎片问题，可将 KV Cache 的利用率从常见的 20%~40% 提升到 90% 以上。

**Prefix Caching / Radix Attention**——多个请求共享相同前缀（system prompt、few-shot 示例）的 KV，实现跨请求复用。

**Continuous Batching**——请求一结束立刻释放其 KV 并填入新请求，而非等待整个 batch 跑完。

### 4.8 权衡总览

**表 4.2 各类手段的代价与收益对比**

| 手段 | 换出去的是 | 典型收益 | 典型代价 |
| --- | --- | --- | --- |
| 融合 / 内存规划 / in-place | 无 | 10%~30% | 几乎为零 |
| 梯度检查点 | 算力 | 激活降至 O(\sqrt{L}) | +30% 前向 |
| 选择性重算 | 算力 | 接近全量重算 | +2%~5% |
| Offload | PCIe 带宽 | 可省下全部优化器状态 | 重叠不好则严重掉速 |
| 量化 | 数值精度 | 2× ~ 4× | 精度损失，需评测 |
| LoRA | 可训练容量 | 16 B → 2 B/param | 表达能力受限 |
| PagedAttention | 无（换实现复杂度） | KV 利用率提升至 90%+ | 需要专门的推理引擎 |
