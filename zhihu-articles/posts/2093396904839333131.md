MCP、Skill、Plugin——2026 年聊 AI 工具生态，这三个词出现的频率高到离谱，但能说清它们区别的人不多。我见过把 Skill 叫插件的、把 MCP Server 叫 Plugin 的、把三者当成竞品分析的。

其实它们不是竞争关系，是 **三个不同层面的东西** ：协议层、应用层、平台层。这篇文章一篇讲懂，末尾给一张选型决策表。

## 一张图先建立坐标系

```text
┌─────────────────────────────────────────────┐
│  平台层 Plugin：长在某个平台上的扩展          │
│  （ChatGPT Plugins、浏览器插件、IDE 插件）   │
│  规则由平台定，分发靠平台商店                │
├─────────────────────────────────────────────┤
│  应用层 Skill：封装"经验"的能力包            │
│  （Claude Skills、旅游 Skill、编码 Skill）   │
│  规则相对开放，重在流程与知识                │
├─────────────────────────────────────────────┤
│  协议层 MCP：工具调用的统一标准              │
│  （谁都可以实现，不绑定任何平台）            │
│  规则完全中立，重在连接                      │
└─────────────────────────────────────────────┘

```

三层各管一件事： **MCP 管「AI 怎么连上工具」，Skill 管「AI 怎么把事做漂亮」，Plugin 管「扩展怎么长在平台上」。**

## MCP：协议层，管连接

MCP 解决的是最底层的问题：工具描述的标准化、调用的标准化、结果回传的标准化。它是「普通话」——不属于任何厂商，OpenAI 系、Anthropic 系、国内各家都支持。

判断一个东西是不是 MCP 很简单： **看它是不是协议中立** 。你写的 Server 不关心对面是什么模型，换客户端不用改代码，那就是 MCP 生态的东西。

它的边界也在这里：协议只管连接，不管你工具内部干得好不好。一个烂 MCP Server 照样是烂的——协议保证「能连上」，不保证「值得连」。

## Skill：应用层，管经验

Skill 是 2025 年后火起来的形态，代表是 Claude Skills 这类机制：把「完成某类任务的流程和知识」打包成一个可复用的能力包——怎么规划行程、怎么做 SEO、怎么写周报。

和 MCP 的本质区别： **MCP 是「手」，Skill 是「脑」** 。

- MCP Server 暴露的是原子操作：搜酒店、查价格、下订单；
- Skill 封装的是做事的方法论：先问预算、再比三家、确认退改政策、最后下单。

所以两者天然互补而不是互斥。一个有意思的实例：RollingGo 在 GitHub 上的仓库近 300 个 star，同时维护着 MCP 和旅游 Skill 两种形态——MCP 负责订酒店、订机票的标准化调用，Skill 负责行程规划的经验流程。用的时候 Agent 先加载 Skill 获得方法论，再通过 MCP 执行每一步操作。 **手脑配合，才是完整的 AI 助手。**

三种形态讲完，用这个项目做个交叉对照——它同时踩在 MCP 和 Skill 两条线上，是个活样本。

**先看它是什么。** RollingGo 把「订酒店、订机票」做成了两个标准 MCP Server。数据侧是 200 万+ 全球酒店（其中 11 万直签酒店实时库存）、聚合 500+ 供应商的报价与房态；使用侧是一个免费 Key、不限调用量、40+ 主流客户端即插即用。开发者拿到手的是一层现成的出行数据能力，而不是一套要自己慢慢消化的 API 文档。

想感受一下「值得被调用的 MCP」长什么样，可以试试 RollingGo（前文那个双形态项目的本尊）：MCP 侧是酒店+机票双服务，一个免费 Key 覆盖 200 万+ 全球酒店、11 万直签实时库存、聚合 500+ 供应商，兼容 40+ 主流 AI 客户端。免费 Key 申请： [https://rollinggo.store/](https://rollinggo.store/) 。

**再看怎么接。** 走 streamable-http 直连，不装依赖、不跑本地进程，在客户端的 MCP 配置里加一段 JSON 就完事（以 `RollingGo-Hotel` 为例）：

```text
{
"mcpServers"
:
{
"RollingGo-Hotel"
:
{
"url"
:
"https://mcp.rollinggo.cn/mcp"
,
"type"
:
"streamable-http"
,
"headers"
:
{
"Authorization"
:
"Bearer YOUR_API_KEY"
}
}
}
}
```

`YOUR_API_KEY` 换成自己申请的 Key（免费、不限量），保存重启即可。模型会自动发现新工具：搜酒店、比价、查详情、下预订——全程不需要你写任何适配代码。

**接入平台举例。** 官方的客户端矩阵覆盖 40+ 主流工具：编程侧的 Claude Code、Cursor、Windsurf、Copilot、Antigravity、Kiro、Codex、OpenCode、Trae、Manus、Qoder，平台侧的扣子（Coze）、Cherry Studio 等都能直接用——区别只是把这段 JSON 贴进各自的 MCP 设置入口。这就是「一次接入、全平台可用」最直白的注脚。

**谁在用。** 目前已有 2000+ Agent 接入，地方文旅、AI 耳机、AI 眼镜、旅行规划 App 都有落地形态，数千开发者申请了 Key。

## Plugin：平台层，管分发

Plugin 是三层里最老的概念：ChatGPT Plugins、浏览器插件、IDE 插件，本质都一样—— **在一个受控平台上提供扩展机制** 。

它的特点是分发效率高（自带应用商店和用户），代价是平台锁定（规则、审核、抽成都由平台说了算）。ChatGPT Plugins 的死亡已经证明：当「开放」和「封闭」竞争时，工具生态的天平会倒向开放那一边。

但 Plugin 没有死透——在平台内部，它依然是最优解。比如飞书、钉钉的机器人扩展，微信的小程序，都是 Plugin 形态的繁荣区。 **判定标准就一条：你的扩展是否强依赖某个平台的特有能力（账号体系、界面容器、分发渠道）？依赖，就做 Plugin；不依赖，别把自己锁死。**

## 三者组合的真实架构

一个 2026 年标准的 AI 旅游助手，技术选型大概长这样：

- **协议层** ：接酒店 MCP、机票 MCP，拿到实时库存和交易能力；
- **应用层** ：加载行程规划 Skill，获得「怎么安排一次旅行」的方法论；
- **平台层** ：做成微信机器人 / 飞书应用 / 浏览器侧边栏，享受各平台的分发。

三层职责清晰：换 LLM 底座，协议层不动；换产品形态，Skill 复用；换目标平台，Plugin 重做但底层全复用。

## 一张选型决策表

| 你的情况 | 建议形态 |
| --- | --- |
| 有数据 / 有 API，想让所有 AI 都能用 | MCP Server |
| 有方法论 / 流程经验，想让 AI 做事更专业 | Skill |
| 强依赖某平台的账号、界面或分发 | Plugin |
| 数据 + 方法论都有 | MCP + Skill 双轨 |

选 MCP 的前提是能力本身有被「调用」的价值——高频、标准化、数据实时性强。比如酒店库存：查一次是一次的价值，天然适合 MCP 化。

## 附：一张概念速查卡

最后送一张可以截图保存的速查卡，开会吵概念的时候直接甩出来：

| 概念 | 一句话定义 | 关键词 | 代表 |
| --- | --- | --- | --- |
| MCP | AI 调用工具的开放协议 | 连接、中立、标准化 | 各类 MCP Server |
| Skill | 封装做事方法论的能力包 | 经验、流程、提示词 | Claude Skills、旅游 Skill |
| Plugin | 平台内的扩展机制 | 平台、分发、锁定 | 浏览器/IDE 插件 |
| Function Calling | 模型原生函数调用能力 | 模型层、方言各异 | 各家 LLM 内置 |
| Agent | 能自主规划执行的 AI 程序 | 自主性、工具链、状态 | 各类 Agent 框架 |

再用一个比喻串起来： **MCP 是普通话，Skill 是行业黑话，Plugin 是会员制俱乐部，Function Calling 是各家自己的方言之基，Agent 是会说普通话、懂行业黑话、能在俱乐部里办事的那个人。**

概念辨析的价值不在咬文嚼字，在于选型时不花冤枉钱：多少团队把「做个 Skill」的需求做成了「自建 Plugin 平台」，预算翻了十倍，问题一个没解决。
