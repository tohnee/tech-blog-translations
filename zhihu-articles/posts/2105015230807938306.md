上期我们引入了数据并行，增加了模型副本，但每张卡仍需容纳完整的 weight、梯度和 optimizer 状态，模型规模受单卡 HBM 容量限制。这次我们给 [Meowgatron-LM](https://github.com/KurodaKanbei/Meowgatron-LM) 加入流水线并行（Pipeline Parallelism），沿层分摊模型状态，代价是 stage 之间传递激活与梯度的通信开销，以及等待上下游计算的时间。

## 模型配置与流水线划分

我们的实验模型也改为更规整的尺寸，从 20 层改为 16 层，attention head 从 20 个改为 32 个：

```yaml
model:
  num_layers: 16
  num_heads: 32

distributed:
  pipeline_layout: [4, 4, 4, 4]
```

`pipeline_layout` 指定各 pp stage 的 Transformer block的数量。embedding 留在首段，final norm、LM head 和 loss 留在末段；首尾的负担明显更重，`[3, 5, 5, 3]`也是可以考虑的分段方案。

这样八张卡组成 PP4 × DP2，相同 pp stage 的副本组成 DP 组，只规约本段的梯度。

### 激活怎样跨卡传递

stage 在两个完整的 Transformer block 之间切分：前一 stage 完成最后的残差相加后，将输出送到后一 stage 的 RMSNorm。反向计算则传递后一 block 的输入梯度 `dX`，作为前一 block 的 `dY`。工程上，我们将需要共同推进的前向/反向传递用`batch_isend_irecv` 成组提交。

![](https://pic4.zhimg.com/v2-7bdf08b3b6feb198c79d7b56829afde5_r.jpg)

这里有一个小巧思，两个block之间的hidden state和他对应的梯度，是这个前反向有向图上的最小割，在这里把模型切开，可以最小化pp stage之间的通信量，使残差支路留在各自 stage 内，跨界只需传递 hidden state 和对应梯度。本次训练配置，边界张量为 fp32 的 `[8, 512, 1280]`，每个 microbatch 的前向激活和反向梯度各占 20 MiB。

H800 上，ProcessGroupNCCL 将这些操作转成同一 group 内的 `ncclSend/ncclRecv`，提交到 CUDA 通信流。[^1] 950DT 上，torch_npu 的 ProcessGroupHCCL 将它们合并为 `HcclBatchSendRecv`，传入device tensor 的地址。[^2]send前，通信流等待计算结果就绪；使用接收数据前，计算流等待recv完成。两条流通过 device event 建立依赖。

## 流水线调度

stage 做完前向，还要等下游传回梯度，才能反向并释放激活。如果使用串行调度，每次只让一个 microbatch 走完整条流水线，那么大部分卡都会在等待，引发计算资源的浪费。

![](https://pic4.zhimg.com/v2-495244b66e50d42148f14f8fbd0c4f3b_r.jpg)

### GPipe：先完成所有前向，再做反向[^3]

GPipe 将一次更新分为前向、反向两个阶段。 前向阶段连续送入所有 microbatch，各 stage 保留激活；全部前向完成后，再逐个反向并释放。

### 1F1B：交替前向与反向[^4]

我们采用 1F1B（one forward, one backward），各 stage 依次经历三个阶段：

- **预热**：只做前向，逐步填充流水线。
- **稳态**：交替执行一次前向和一次反向，及时释放激活。
- **排空**：停止前向，完成剩余反向。

![](https://pica.zhimg.com/v2-64effc10528183abf50c2112cf7c3202_r.jpg)
*图中两种调度的总时长相同；1F1B 更早完成反向，将各段保留的激活份数从 8 份降为 4、3、2、1 份。*

设流水线有 $P$ 段，每次更新包含 $m$ 个 microbatch。第 $i$ 段同时保留的 microbatch 激活份数最多为：

$$ n_i=\min(m,\;P-i) $$

值得注意的是，流水线填充和排空时仍有气泡。在各段耗时相同时，P 段、m 个 microbatch 的气泡占整次更新约 `(P−1)/(m+P−1)`。减小 MBS 可以摊薄气泡占比，却也可能降低单个microbatch的计算效率。

## 重算配置

1F1B 减少同时保留的 microbatch，但每份激活仍包含反向所需的中间结果，例如 Linear 的输入和 softmax 概率。我们引入重算机制：只保留区域入口，在反向需要时重建内部激活，以额外计算换取显存。[^5]

我们使用 PyTorch 原生的 non-reentrant checkpoint。[^6]autograd 保留重算区域的入口 tensor，前向时不再为反向长期保存区域内部的中间 tensor；反向需要这些值时，从保留的入口重新执行前向，重建后用于求梯度。我们提供两种重算的选择模式：

`full` 将整个 Transformer block 包起来，保留它的输入 `hidden`：

```python
checkpoint(
    self._forward, hidden,
    use_reentrant=False, preserve_rng_state=False,
)
```

`selective` 则按模块缩小范围，可以在 YAML 中组合选择：

```yaml
training:
  recompute: selective
  recompute_modules: [attention, norm, mlp_act]
```

![](https://picx.zhimg.com/v2-0f32794e4dc7cf8f8688a9774f0250c7_r.jpg)

重算范围还要包括后续使用并保存这些激活的算子。例如只给 GELU 加 checkpoint，后面的 down 仍会为计算 dW 留住 GELU 输出，因此我们将 GELU 和 down 一起包起来。反向重建出 GELU 输出后，checkpoint 的 early-stop 就会停止重放，不再执行 down GEMM。

选择哪些区域，取决于保存与重建成本的trade off。`norm` 和 `mlp_act` 不增加 GEMM；`attention` 补做 QK、softmax，省下随序列长度平方增长的P矩阵。`mlp` 进一步省去 up 的输出，代价是多做一次 up GEMM；`full` 保留 block 输入，节省更多内部激活，也要重放更多矩阵乘。

### Checkpoint 跟着模型切分

PP 下没有单个 rank 持有完整模型，checkpoint 因而按 stage 分片，每段由一个 DP 副本负责保存。

![](https://pic3.zhimg.com/v2-4fdaf82329ede09455feba581ac9908c_r.jpg)

保存发生在完整更新结束、流水线排空之后，各 stage 写完本步分片后，再统一更新checkpoint的latest标识；恢复时按同一个步数加载本 stage 状态和对应的 DP 数据游标。

## 代码与配置

```text
Meowgatron-LM/
├── configs/meow.yaml   # 改动：模型、PP 与重算配置
├── core/
│   ├── pipeline.py     # 新增：按 layout 分段、1F1B 与首尾梯度合并
│   ├── model.py        # 改动：block、norm 与 MLP 重算边界
│   ├── attention.py    # 改动：attention core 重算
│   ├── mlp.py          # 改动：MLP 激活重算
│   ├── distributed.py  # 改动：划分 PP 与 DP 通信组
│   ├── checkpoint.py   # 改动：按 stage 保存、恢复整套分片
│   └── training.py     # 改动：接入流水线调度
└── examples/meow.py    # 改动：接入 PP 配置与模型装配
```

控制流程上，`training.py` 将一批 microbatch 交给 `pipeline.py` 调度，待反向和梯度同步完成后再更新 weight。重算嵌入现有模型组件的前向计算，`checkpoint.py` 则负责各 stage 分片的保存与加载。

## 训练与恢复验证

H800 与 950DT 分别完成了重算对照：单个 Transformer block 的四类单选、组合与 `full`，在不同重算组合下全部前向输出和梯度均与不重算时一致。完整模型采用 PP4 × DP2，`attention`、`norm`、`mlp` 单选及两种组合连续训练 50 步，各配置的逐步 loss、weight 和 optimizer 状态在同一硬件下完全一致。

断点续训采用 `attention + norm + mlp`，比较连续 100 步与 50＋50 步。两端各自的 50 个恢复 loss 点与完整 checkpoint 状态均逐位一致。不均分布局 `[3, 5, 5, 3]` 的 10 步与 5＋5 步对照也一致。

长跑对照我们采用 PP4 × DP2、`attention` 重算，两端跑完 FineWeb-Edu 10BT，共 9.954B token。最后 2,000 步的平均 loss，H800 为 2.93833，950DT 为 2.93990，950DT 平均高 0.00157。

![](https://pic4.zhimg.com/v2-0714d1855cad9bbc6fb49eb06e265b6b_r.jpg)

## 小结

本次更新我们把完整模型拆成独立的流水线分段，用 1F1B 减少激活等待反向的时间，再用 selective 重算减少需要保留的中间结果。在两种硬件上通过了断点续训/重算配置验证，并完成10B的训练。
