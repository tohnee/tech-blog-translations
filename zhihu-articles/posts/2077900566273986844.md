## RDMA 为什么需要无损网络？从丢一个包到整个 AI 集群变慢

在智算网络、AI 数据中心和高性能计算场景中，经常会听到一句话：

> **RDMA 要求网络无损。**

这句话从工程实践角度没有太大问题，但从技术原理上并不完全准确。

更严谨的说法应该是：

> **RDMA 本身并不要求底层网络绝对无损，但传统 RoCE 的丢包恢复机制效率较低，一旦发生丢包，可能造成严重的重传、吞吐下降和尾时延增加。因此，为了发挥 RDMA 的低时延、高吞吐优势，传统 RoCE 网络通常通过 PFC、ECN 和拥塞控制构建近似无损网络。**

而且近年来技术方向正在发生变化：

```text
传统 RDMA
Lossless Network
      ↓
PFC + ECN
      ↓
尽量不允许丢包

          ↓ 演进

现代 RDMA
Loss-Tolerant Network
      ↓
Selective Retransmission
+ Fast Recovery
+ Advanced CC
      ↓
允许少量丢包，但快速恢复

```

理解这个变化，首先需要回答一个问题：

**为什么一个看起来微不足道的 Packet Loss，会对 RDMA 造成如此大的影响？**

---

## 1. RDMA 到底解决了什么问题？

RDMA，全称 Remote Direct Memory Access。

它的核心目标，是让一台服务器直接访问另外一台服务器的内存，同时尽可能绕过：

- CPU；
- Kernel；
- TCP/IP Software Stack；
- Memory Copy。

![](https://pic2.zhimg.com/v2-825ca437d40d5c5df39ac80d460a4da9_1440w.jpg)

传统 TCP 数据传输路径大致是：

```text
Application
    ↓
Socket
    ↓
Kernel
    ↓
TCP/IP Stack
    ↓
NIC
    ↓
Network

```

数据到达对端之后，又需要经历相反的路径。

而 RDMA：

```text
Application Memory
       ↓
      RNIC
       │
       │  RDMA Network
       ↓
      RNIC
       ↓
Remote Application Memory

```

其核心能力包括：

- Kernel Bypass；
- Zero Copy；
- RNIC Offload；
- Direct Memory Access。

因此 RDMA 可以同时获得：

![](https://pic2.zhimg.com/v2-3cc07675a939f4f2ce71fc9988417b69_1440w.jpg)

![](https://picx.zhimg.com/v2-a8702d24850d8cee49b52571d82f4601_1440w.jpg)

以及：

![](https://picx.zhimg.com/v2-18eeb1e005d05fa95011b376cc638a17_1440w.jpg)

这也是为什么 RDMA 被广泛应用于：

- AI 大模型训练；
- HPC；
- 分布式存储；
- 分布式数据库；
- 高性能云计算。

但 RDMA 为了追求极致性能，也付出了一个代价：

> **Transport 被大幅简化，很多传统 TCP 中复杂的可靠性处理被下沉到 RNIC。**

这使得传统 RoCE 对 Packet Loss 特别敏感。

---

## 2. 先纠正一个概念：不是所有 RDMA 都要求无损

RDMA 是一个比较大的概念。

常见实现包括：

```text
                    RDMA
                      │
       ┌──────────────┼─────────────┐
       │              │             │
 InfiniBand         RoCE          iWARP
       │              │             │
InfiniBand网络     Ethernet        TCP/IP

```

其中：

### InfiniBand

原生使用 Credit-Based Flow Control，网络天然倾向于避免 Buffer Overflow 和 Packet Drop。

### RoCE

RDMA over Converged Ethernet。

RoCE 尤其是 RoCEv2，直接运行在 Ethernet/IP 网络之上。

Ethernet 本身是：

> **Lossy Network**

交换机 Buffer 满了以后，可以直接 Drop Packet。

因此：

```text
RoCE
  +
Lossy Ethernet

```

就产生了一个非常重要的问题：

**Packet Loss 怎么办？**

### iWARP

iWARP 建立在 TCP 之上。

TCP 本身具有成熟的可靠传输、重传和拥塞控制机制，所以 iWARP 并不要求 Ethernet 必须是 Lossless。

因此严格来讲：

> **“RDMA 必须无损”并不准确。**

真正的问题应该是：

> **为什么传统 RoCE 长期依赖 Lossless Ethernet？**

---

## 3. 根本原因：传统 RoCE 的丢包恢复效率太低

这是理解整个问题最关键的一点。

早期 RDMA Transport 的设计背景是 InfiniBand。

InfiniBand 网络通过 Credit-Based Flow Control，本身就很少发生 Packet Drop。

所以最初设计 RDMA Transport 时，一个合理的假设就是：

> **Packet Loss 是非常罕见的异常事件。**

后来 RoCE 把 RDMA Transport 搬到了 Ethernet。

问题来了。

Ethernet 天生允许：

```text
Queue Full
    ↓
Packet Drop

```

于是原本针对“极少丢包环境”设计的可靠传输机制，被放到了一个可能产生丢包的 Ethernet 网络里。

这就是传统 RoCE 强依赖 Lossless Network 的历史原因之一。

SIGCOMM 2018 的经典论文 **IRN: Revisiting Network Support for RDMA** 对这个问题进行了非常系统的研究。

---

## 4. 丢一个 Packet，为什么会产生多个 Packet 重传？

传统 RoCE Reliable Connection 使用的经典恢复方式可以近似理解为：

> **Go-Back-N，简称 GBN。**

假设 Sender 发送：

```text
Packet:

1 → 2 → 3 → 4 → 5 → 6 → 7

```

结果 Packet 3 丢了：

```text
1 → 2 → X → 4 → 5 → 6 → 7
        ↑
       Loss

```

接收端期望收到：

```text
PSN = 3

```

却收到了：

```text
PSN = 4

```

发现 Sequence Gap。

传统 RoCE 的处理并不像现代 TCP SACK 那样简单地缓存所有乱序数据，然后只补 Packet 3。

而可能出现：

```text
Packet 3 Loss
      ↓
Receiver 发现 PSN Gap
      ↓
后续 Out-of-Order Packet 无法正常利用
      ↓
NAK
      ↓
Sender Go-Back-N
      ↓
3 / 4 / 5 / 6 / 7 ...
重新发送

```

于是：

![](https://pic2.zhimg.com/v2-9457457d7c8c60cc4beefbb1f46dd3b9_1440w.jpg)

并不等于：

![](https://pic2.zhimg.com/v2-be6afbea5e84e199324c263507504915_1440w.jpg)

而可能变成：

![](https://pic3.zhimg.com/v2-496f18171e2ebcb7577f9d3af5fb33ae_1440w.jpg)

这就是所谓：

> **Retransmission Amplification，重传放大。**

因此 RDMA 真正害怕的，并不是“丢掉了那几个 KB 数据”。

而是：

> **一个 Packet Loss 可能触发远大于这个 Packet 本身的数据重传和传输停顿。**

## 5. 数据到底有多夸张？0.001% Loss 就可能产生巨大影响

一个非常有代表性的实验来自 IEEE/ACM IWQoS 2024 的论文：

**LoWAR: Enhancing RDMA over Lossy WANs with Transparent Error Correction**

研究人员直接使用 Mellanox ConnectX-5 RNIC 测试 Commercial RoCE。

实验环境：

| 参数 | 配置 |
| --- | --- |
| RNIC | Mellanox ConnectX-5 |
| Bandwidth | 10 Gbps |
| RTT | 40 ms |
| Protocol | RoCE |
| Loss | 人工注入 |

无丢包时：

![](https://pica.zhimg.com/v2-a5b06081dc9e5506f8eeae2d74a58f00_1440w.jpg)

也就是说 10G 链路基本跑满。

但是当 Packet Loss 只有：

![](https://pica.zhimg.com/v2-117b2abb02fd32efe6e92f0dba4445de_1440w.jpg)

Goodput 降到了：

![](https://pic2.zhimg.com/v2-f4a98fc2eecbb3ff7280329c015093d3_1440w.jpg)

性能下降：

![](https://pica.zhimg.com/v2-1f422ea52838c59c7f0190f24f14fe76_1440w.jpg)

![](https://pic3.zhimg.com/v2-9e136885b1df91bcce60e09c9e3c1da8_1440w.jpg)

也就是说：

> **仅 0.001% Packet Loss，就使实验中的 RoCE Goodput 从 9.21 Gbps 降到 2.92 Gbps，下降约 68%。**

而当 Loss Rate 超过：

![](https://pic1.zhimg.com/v2-8e87a64f4b0c300f2fe23c3b7c02a804_1440w.jpg)

Goodput 已经：

![](https://pic1.zhimg.com/v2-f97cd3b7a8093b830802fba4e117ca34_1440w.jpg)

论文明确将这种剧烈下降归因于 Commercial RoCE 的 GBN Recovery，以及高 RTT 下巨大的带宽浪费。

需要注意的是，这是 **40 ms RTT 的 Lossy WAN 实验**，不能直接等同于微秒级 RTT 的数据中心 RoCE；但它非常直观地说明了：

> **Loss Rate 本身很低，并不意味着 RDMA 性能损失也很低。**

## 6. 为什么 0.001% Loss 都可能这么严重？

0.001% 看起来几乎可以忽略：

![](https://pica.zhimg.com/v2-84d1e7600c1053f5a340ecd7c840a07e_1440w.jpg)

即平均约：

![](https://pica.zhimg.com/v2-1debd583718fcfc94981e5fc9afbf7be_1440w.jpg)

才丢一个。

如果一个 Packet 大约 4 KB：

![](https://pic2.zhimg.com/v2-9fa192cfe3dc557eb41d932397deeddd_1440w.jpg)

大约传输数百 MB 数据才发生一次丢包。

问题在于：

```text
Loss Rate = 0.001%

```

并不意味着：

```text
Performance Loss = 0.001%

```

因为真正发生的是：

```text
Packet Loss
    ↓
Sequence Gap
    ↓
NAK / Timeout
    ↓
Go-Back-N
    ↓
大量已经发送的数据重新传输
    ↓
Bandwidth Waste
    ↓
Goodput ↓

```

所以：

![](https://picx.zhimg.com/v2-c9bccec75268fd34f00d5cd172a494e1_1440w.jpg)

与：

![](https://pic1.zhimg.com/v2-5c4d253fae949718d0436c6a4c0d993e_1440w.jpg)

不是线性关系。

在某些情况下可能出现：

![](https://pic1.zhimg.com/v2-ff6ecfc0387bc145775b7034fe00a9e6_1440w.jpg)

却导致：

![](https://pica.zhimg.com/v2-30b932172523e4f4d2df89f1578a07c8_1440w.jpg)

这也是为什么评价 RDMA 网络不能只说：

> “我的丢包率只有万分之一甚至十万分之一。”

真正应该关注的是：

![](https://picx.zhimg.com/v2-3c2b5a397d297a419aa4d5a4af22a2a5_1440w.jpg)

## 7. 链路速度越高，丢包恢复的机会成本越大

现在再考虑一个智算网络非常重要的因素：

**400G / 800G 网络非常快。**

400 Gbps：

![](https://pic3.zhimg.com/v2-3c0a28ae6fed5a1323b4d62ec50648c8_1440w.jpg)

如果一次 Loss Recovery 让数据流停顿：

![](https://pic2.zhimg.com/v2-f21ed677e09deecca8a0f4bdde1f0ff7_1440w.jpg)

理论上这 100 μs 本来可以发送：

![](https://pic4.zhimg.com/v2-ae96d17caa800b013d47d39b2cc51cff_1440w.jpg)

即：

![](https://pica.zhimg.com/v2-fe78c3ff8590c046a4fdf4fb884c4498_1440w.jpg)

数据。

对于 800G：

![](https://pic2.zhimg.com/v2-e2ca031841b058e6da9b8a5af36142cf_1440w.jpg)

100 μs 对应：

![](https://pic1.zhimg.com/v2-3554d68fe48b67a871e8fc69db703c2a_1440w.jpg)

也就是说：

| 网络 | 100 μs 对应传输能力 |
| --- | --- |
| 100G | 1.25 MB |
| 200G | 2.5 MB |
| 400G | 5 MB |
| 800G | 10 MB |

注意：

这并不是说“丢一个包一定损失这么多数据”，而是在说明一个更加重要的概念：

> **链路速度越高，一次 Recovery Stall 所损失的传输机会越大。**

因此到了 400G、800G 甚至未来 1.6T 网络：

> **Recovery Latency 本身就成为非常昂贵的成本。**

## 8. RTT 越大，GBN 的代价也越大

还可以进一步理解为什么 WAN 场景下 RoCE 对 Loss 特别敏感。

一个连接在一个 RTT 内可以发送的数据量主要由：

![](https://pica.zhimg.com/v2-99831a67a610200ac2798ee1cfde9002_1440w.jpg)

决定。

假设：

![](https://pic2.zhimg.com/v2-81f62552d4319285076958bc5d8fc76f_1440w.jpg)

![](https://picx.zhimg.com/v2-fabd66b1d4ddec1e0ef8defb02246a2d_1440w.jpg)

那么：

![](https://pic3.zhimg.com/v2-113b5d018439894346abe7b82d857d0a_1440w.jpg)

约：

![](https://pic1.zhimg.com/v2-fb9ab130a2a671e86a7b96a05e2082e0_1440w.jpg)

意味着在收到反馈以前，网络中可能已经存在大量 In-Flight Data。

如果前面的某个 Packet 丢失：

但 N+1、N+2、N+3……
已经继续发送
     ↓
GBN Recovery
     ↓
大量 In-Flight Data 被浪费

因此：

![](https://picx.zhimg.com/v2-1d0e1a50476af94b1d073169d5a98c03_1440w.jpg)

## 9. 既然 RoCE 怕丢包，那就让 Ethernet 不丢包

于是工程界采用了一个非常直接的思路：

```text
RoCE怕Drop
    ↓
那就阻止交换机Drop

```

这就是：

## PFC

Priority-based Flow Control。

普通 Ethernet：

```text
Traffic
   ↓
Switch Buffer
   ↓
Buffer Full
   ↓
DROP

```

部署 PFC 以后：

```text
Traffic
   ↓
Switch Queue不断增长
   ↓
达到PFC Threshold
   ↓
发送PFC Pause Frame
   ↓
上游设备暂停该Priority发送
   ↓
Queue得到释放
   ↓
避免Buffer Overflow
   ↓
避免Packet Drop

```

于是：

![](https://pic3.zhimg.com/v2-ae50888698f6449f019a8f8778666044_1440w.jpg)

Microsoft 在 SIGCOMM 2015 的经典 DCQCN 论文中就明确指出，RoCEv2 依赖 PFC 构建 Drop-Free Network。

这也是为什么传统数据中心 RDMA 网络经常采用：

```text
RoCEv2
   +
PFC
   +
ECN
   +
DCQCN

```

形成近似：

> **Lossless Ethernet**

的网络环境。

## 10. PFC 和 ECN，其实解决的是两个不同问题

这是一个非常容易混淆的地方。

很多时候会看到：

```text
PFC + ECN

```

但两者目的不一样。

## PFC：最后一道防线

PFC 解决：

> **已经快要丢包了怎么办？**

```text
Queue
 ↓
越来越深
 ↓
达到PFC Threshold
 ↓
PAUSE
 ↓
防止Drop

```

因此 PFC 是：

> **Loss Prevention**

---

## ECN：提前控制拥塞

ECN 解决的是：

> **为什么不在 Queue 堆满之前让 Sender 减速？**

```text
Queue增长
    ↓
ECN Threshold
    ↓
Switch Mark ECN
    ↓
Receiver反馈
    ↓
Sender降低Rate
    ↓
Queue下降

```

因此：

![](https://pic4.zhimg.com/v2-4064006d1f19f0bc0d0698bd3dde808f_1440w.jpg)

结合 DCQCN：

```text
ECN
 ↓
DCQCN
 ↓
Rate Control
 ↓
Prevent Queue Build-up

```

理想情况下：

> **ECN + Congestion Control 应该尽可能早地控制拥塞，让 PFC 根本没有机会触发。**

---

## 11. 为什么不能只靠 PFC？

如果 PFC 可以做到 Lossless，那是不是打开 PFC 就行了？

不是。

因为 PFC 本身也存在非常严重的问题。

Microsoft 的实际 RoCEv2 大规模部署经验已经观察到：

- PFC Deadlock；
- PFC Pause Storm；
- Head-of-Line Blocking；
- Fairness 问题；
- Congestion Spreading。

Microsoft 甚至在生产环境中经历过 PFC-induced Deadlock。

假设：

```text
Server A
   ↓
Switch A
   ↓
Switch B拥塞

```

Switch B：

```text
发送PFC Pause
      ↓
Switch A停止发送

```

但 Switch A 自己又开始积压：

```text
Switch A Buffer ↑
       ↓
向更上游发送PFC
       ↓
Pause继续传播

```

最后形成：

```text
Congestion
    ↓
PFC
    ↓
Upstream Pause
    ↓
More Queue
    ↓
More PFC
    ↓
Congestion Spreading

```

这就是为什么现代 RDMA 网络真正的目标并不是：

> **让 PFC 大量工作。**

而应该是：

> **网络正常运行时几乎不触发 PFC，PFC 只作为最后一道保护机制。**

---

## 12. 所以真正优秀的“无损 RDMA 网络”是什么样？

传统理解：

```text
Lossless
=
PFC不让它丢包

```

实际上更加先进的设计应该是：

```text
            Traffic
               ↓
       Intelligent Routing
               ↓
       Load Balancing
               ↓
            ECN
               ↓
    Congestion Control
               ↓
      Queue保持较低水平
               ↓
      PFC很少甚至不触发
               ↓
          No Packet Loss

```

所以真正理想的 Lossless Network：

> **不是拥塞之后靠 PFC 强行暂停，而是尽量不要让网络进入需要 PFC 的状态。**

## 13. AI 集群为什么比普通业务更怕 RDMA Loss？

到了 AI 大模型训练，这个问题又会被进一步放大。

假设有：

![](https://pica.zhimg.com/v2-998571371234ca534833b92086812274_1440w.jpg)

执行一次 ReduceScatter：

```text
GPU 0
GPU 1
GPU 2
...
GPU 314
...
GPU 2047

```

其中 Rank 314 所在路径发生 Packet Loss：

```text
Packet Loss
    ↓
RDMA Retransmission
    ↓
Rank 314通信变慢

```

如果这是一次同步 Collective：

```text
Rank 314变慢
      ↓
Collective无法完成
      ↓
其他Rank等待
      ↓
2048 GPU同步等待

```

所以 Loss 的影响出现了第二层放大：

```text
第一层

Packet Loss
    ↓
RDMA Recovery
    ↓
Flow Completion Time ↑

第二层

Flow Completion Time ↑
    ↓
Rank成为Straggler
    ↓
Collective Time ↑
    ↓
Step Time ↑
    ↓
GPU Idle Time ↑
    ↓
MFU ↓

```

最终：

![](https://pica.zhimg.com/v2-fbec095c7024ed998f934fbf4f20949c_1440w.jpg)

因此：

> **AI 网络里的一个 Packet Loss，其业务影响可能远远超过这个 Packet 本身。**

它最终浪费的不是几 KB 网络数据，而可能是：

> **数百、数千块 GPU 的等待时间。**

---

## 14. 最新研究正在挑战：“RDMA 一定要无损吗？”

答案越来越明确：

> **不一定。**

SIGCOMM 2018 的 IRN 已经开始系统挑战“RDMA 必须依赖 PFC”的传统观点。

IRN 的核心思想包括：

- Selective Retransmission；
- Better Loss Recovery；
- BDP-based Flow Control；
- 不再强依赖 PFC。

其意义在于：

> **如果 RNIC 能够高效恢复 Packet Loss，那么底层网络就不一定必须通过 PFC 实现严格 Lossless。**

这实际上重新定义了问题。

以前：

```text
RNIC不擅长处理Loss
       ↓
Network不能Loss
       ↓
PFC

```

新的方向：

```text
RNIC可以快速处理Loss
       ↓
Network允许少量Loss
       ↓
Selective Retransmission
       ↓
不再强依赖PFC

```

## 15. 2025 年 SIGCOMM：Lossy RDMA 已经成为重要研究方向

SIGCOMM 2025 的论文：

**Revisiting RDMA Reliability for Lossy Fabrics**

进一步提出了 DCP。

论文的出发点非常明确：

## 18. 最终结论：为什么 RDMA 需要无损网络？

现在可以重新回答最开始的问题。

传统答案：

> **因为 RDMA 不能丢包。**

这个答案不够准确。

真正的答案是：

> **传统 RoCE 的可靠传输机制是在低丢包环境下设计的，其 Go-Back-N 等恢复机制面对 Packet Loss 时效率较低。一个 Packet Loss 可能触发大量冗余重传、等待 NAK/RTO、Goodput 下降和 Tail Latency 增加。因此，为了保证 RDMA 的低时延和高吞吐，传统 RoCE 网络长期通过 PFC、ECN 和拥塞控制构建近似无损 Ethernet。**

可以进一步压缩成一条完整的逻辑链：

```text
RDMA追求极低时延和极高吞吐
              ↓
Traditional RoCE Loss Recovery较弱
              ↓
Packet Loss
              ↓
Go-Back-N / Timeout
              ↓
Retransmission Amplification
              ↓
Goodput ↓ / Tail Latency ↑
              ↓
Collective出现Straggler
              ↓
Step Time ↑
              ↓
GPU等待
              ↓
MFU ↓

```

因此：

![](https://picx.zhimg.com/v2-8946422d8feba0a6f3664aabff6aa6b1_1440w.jpg)

这就是所谓：

## Lossless Ethernet

但下一代 RDMA 网络的目标已经开始变化：

![](https://pic3.zhimg.com/v2-ef4a80ce0a50430cf1ce2a834b9d1264_1440w.jpg)

未来更理想的设计很可能不是：

> **“绝对不能丢一个包。”**

而是：

> **“正常情况下尽量不丢包；即使发生丢包，也能够快速、精准、低成本地恢复。”**

这可能才是 400G、800G 以及大规模 AI Fabric 中 RDMA 网络更长期的技术方向。

## 一句话总结

> **RDMA 并不是“不能丢包”，而是传统 RoCE“丢不起包”：低效的 Loss Recovery 会把极少量 Packet Loss 放大成大量重传、尾时延和吞吐损失；在 AI 集群中，这种影响还会通过 Straggler 和 Collective 同步进一步放大。因此传统 RoCE 长期依赖无损网络，而下一代 RDMA 的方向则是让网络从“不能丢”走向“丢了也能快速恢复”。**
