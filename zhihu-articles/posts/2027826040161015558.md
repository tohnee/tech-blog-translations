很多人谈 Triton、CuTe，只会说两件事：写 kernel 更方便，性能也不错。这两个判断都没错，但都还停留在表面。更深一层的问题是：在高层图语言和底层 ISA 之间，GPU 时代长期缺了一层真正适合表达 tile、layout、fragment、pipeline 和 memory movement 的语言，而这些 DSL 正在补上这层空白。

**先说结论**

- Triton、CuTe 的真正意义，不只是开发效率，而是系统位置。
- 它们承载的是介于图语义和硬件 ISA 之间的“中观执行结构”。
- 一旦这层语言成立，compiler、autotuning、团队协作和知识沉淀方式都会改变。

前面几篇我们已经把几条线逐渐拧到一起了。

Linux kernel 的经典抽象依然重要，但 AI 时代的系统中心正在迁移。<br>GPU 不再只是普通设备，而是主执行域。<br>runtime 暴露的是新的执行原语。<br>compiler 不再只是工具，而在定义执行结构。<br>`fusion`、`tiling`、`layout` 这些词，开始承担资源管理职责。<br>FlashAttention 这样的工作，则把这种变化以最浓缩的方式暴露出来。

顺着这个逻辑，下一步自然就会问：如果 AI 程序越来越依赖 tile、pipeline、layout、memory movement 这些结构，那我们到底该用什么语言来表达它们？

这正是 Triton、CuTe 这类 DSL 真正重要的地方。

很多人谈它们，只会说两类评价：

- 写 kernel 更方便
- 性能不错，接近手写 CUDA

这些评价都不算错，但还停留在表层。更深一层的意义在于：它们正在重新发明 GPU 时代的中间语言。

不是高层图语言，也不是底层 ISA，而是介于两者之间、专门用来承载 tile、layout、fragment、pipeline、memory movement 等核心约束的一层新表达。

这一篇最容易被误读的地方，就在于很多人会把 DSL 看成“更方便写 kernel 的工具”，或者“换一种语法写底层实现”。但如果把高层图编译、compiler lowering 和 Triton/CuTe 这类体系放在同一条链上看，会很清楚：它们最重要的不是语法，而是系统位置。

### 一、为什么传统高层语言和底层 CUDA/C++ 之间会出现一个巨大的表达断层

先看问题是怎么来的。

在高层框架或图编译器眼里，程序往往还是：

- matmul
- attention
- normalization
- elementwise
- reduce

这些对象表达的是“计算语义”。它们很好地描述了要做什么，但对如何在 GPU 的层次结构上完成这件事，通常描述得很粗。

而在底层 CUDA/C++ 或更低层表示里，你面对的则是：

- thread block
- warp
- lane
- register
- shared memory
- barrier
- cp.async
- mma/tensor core 指令级模式

这些对象表达的是“机器细节”。它们足够强，但距离高层语义又太近地贴住了硬件，导致可组合性、可迁移性和抽象稳定性都受限。

问题就出在中间。

真正决定 AI kernel 能否做好的那层结构，并不完全等于高层算子语义，也不等于底层机器指令，而是：

- tile 怎么切
- 数据 fragment 如何分配给并行单元
- layout 如何和 tile 匹配
- load/compute/store 怎样 pipeline
- 哪些 memory movement 应该显式化
- 哪些同步边界应该保留

这层结构如果没有合适语言承载，就会出现两个问题：

- 高层 compiler 很难稳定表达这些关键约束
- 底层 kernel author 只能不断在 CUDA/C++ 模板和手工技巧里重复发明轮子

Triton、CuTe 等 DSL 的出现，本质上就是在填补这个断层。

### 二、什么叫“GPU 时代的中间语言”

我这里说的“中间语言”，不是传统 compiler 理论里狭义的 IR，而是更宽泛的系统位置。

它位于：

- 高层图/算子语义之下
- 底层 ISA/硬件细节之上

它要解决的问题不是表达整个程序，也不是表达最终每条机器指令，而是表达“如何把一个高层 tensor program 组织成符合 GPU 层次结构的执行形态”。

所以这种语言天然要擅长表达：

- tile
- block/warp/thread 映射
- fragment
- layout
- pipeline
- vectorized access
- async copy
- software-managed memory hierarchy

如果没有这层语言，AI 编译栈会一直卡在一个尴尬位置：高层太抽象，看不见关键约束；底层太具体，难以形成稳定系统接口。

这也是为什么我不把 Triton、CuTe 这类东西简单叫“kernel 开发工具”。它们更像是在给整个系统栈补一层长期缺失的表示。

### 三、Triton 真正改变了什么：把大量关键约束抬升到可编程层

先说 Triton。

Triton 之所以引起广泛关注，不只是因为它让很多人不必直接写 CUDA，就能写出性能不错的 kernel。更根本的地方在于，它把大量原本埋在底层实现里的关键约束，抬升成了可编程对象。

在 Triton 风格里，你会直接面对：

- program id 与块级映射
- block pointer 或 block-level tensor view
- tile 级 load/store
- mask
- vectorized operation
- 某种程度上显式的数据流

你不是在描述“这段数学式子等价于什么算子”，而是在描述“这段 tile 应该如何被线程块/程序实例取到、变换、计算和写回”。

这件事为什么重要？

因为它意味着开发者和编译器之间有了一个更准确的共同语言。以前很多关键信息要么被高层语义吃掉了，要么只能在极底层通过经验和模板硬编码；现在至少有机会在中间层把它表达出来。

从系统角度看，这意味着更多关键约束可以被组合、分析、复用和自动化，而不是永远停留在少数高手的手工技巧里。

Triton 真正有意思的地方，不在于“大家都能更快写一个 kernel”，而在于它让很多原来只能隐含在经验里的结构，第一次比较自然地进入了可编程层。这种变化对 compiler、autotuning、团队协作的意义，比对单个开发者的 convenience 更大。

### 四、CuTe 真正重要的，不只是模板技巧，而是对 tile/layout/fragment 的显式建模

再说 CuTe。

很多人第一次接触 CuTe，最直观的感受可能是：模板很多、抽象很硬核、上手门槛不低。这个印象一点没错。但如果只把它看成“写 CUTLASS kernel 的底层模板体系”，仍然低估了它。

CuTe 真正有价值的地方，在于它对几个最核心对象做了非常显式的建模：

- tile
- layout
- shape
- stride
- fragment
- tiled copy
- tiled MMA

这些对象看起来像库设计细节，但在系统视角里，它们其实是在把 GPU 程序最本质的中观结构语言化。

为什么这件事重要？

因为很多高性能 GPU kernel 的本质难点，并不在最底层指令，而在中观结构：

- 一个 tile 如何映射到线程层次
- 一个 layout 如何变成访问模式
- 一个 fragment 如何在 register 中被组织
- copy 和 compute 如何围绕 tile 形成流水

CuTe 的价值就在于，它努力让这些结构本身成为可组合、可推理的对象，而不只是隐含在一大堆 ad hoc 代码里。

所以从我的角度看，CuTe 的系统意义并不只是“方便写 GEMM”，而是它在尝试为 GPU 时代那些最关键但长期缺乏稳定表达的结构，建立一套可复用语言。

如果说 Triton 更像把很多关键结构抬到更广泛可编程的层次，那么 CuTe 给我的感觉更像是在把这些结构本身做成严肃的对象系统。也正因为如此，我不太愿意把两者简单归成“两个 kernel DSL”。它们确实都属于中间语言的一部分，但承载知识的方式和面向的工程边界并不完全一样。

### 五、为什么说它们不是“语法糖”，而是对系统边界的重新划分

把 DSL 叫做语法糖，是我最不认同的一种说法。

语法糖的前提是：底层概念已经稳定，只是表达方式更顺手。可 Triton、CuTe 这些东西的问题恰恰在于，底层长期缺的不是“更顺手表达”，而是“中间结构本身没有被稳定表达”。

举个简单例子。

如果一个系统里，tile、layout、pipeline 和 fragment 只是隐藏在底层内核作者脑中的隐式设计，那 compiler 很难理解它们，runtime 也很难对接它们，团队也很难在其上形成稳定协作。而一旦 DSL 把这些结构抬升出来，它们就变成了：

- 可分析对象
- 可变换对象
- 可组合对象
- 可复用对象

这就是系统边界的变化。

以前很多信息卡在“高层看不见、底层不稳定”的黑箱里；现在 DSL 把黑箱掀开了一部分。它当然还不是完整答案，但已经明显改变了系统如何组织知识和约束。

### 六、它们和 MLIR、图编译器的关系：不是替代，而是承接

讨论 DSL 时，一个常见误区是把它和 MLIR、图编译器放成竞争关系，仿佛只能有一个“正确层次”。

更准确的关系是承接。

图编译器擅长做什么？

- 高层边界重画
- 算子级融合
- shape propagation
- 更大范围的图级等价变换

MLIR 一类多层 IR 擅长做什么？

- 在不同抽象层承载语义
- 让跨层约束能够被逐步 lower
- 组织 passes 和 dialect 之间的转换

而 Triton、CuTe 这类 DSL 擅长做什么？

- 把最终对性能最敏感的 tile/layout/pipeline 结构显式化
- 在接近硬件但尚未完全坠入底层指令的地方建立稳定表示

也就是说，它们不是互相替代，而是在不同层次共同构成一条表达链。

高层决定“做什么”和“大边界怎么切”；<br>中间 DSL 决定“如何把这段工作组织成机器友好的结构”；<br>更低层 codegen 再决定“最终怎么落到具体硬件”。

一旦这样看，DSL 的系统位置就非常清楚了。

### 七、为什么 GPU 时代尤其需要这种中间语言

如果在 CPU 世界，很多时候普通编译器 IR 加自动优化就能覆盖大部分情况，为什么 GPU 世界会尤其需要这种中间语言？

这里大概有几个原因。

第一，GPU 的层次结构太“显式”。<br>register、shared memory、warp、block、tensor core、copy engine，这些东西的性能差异巨大，而且很难完全被黑箱自动优化稳稳吃透。

第二，AI 工作负载太结构化。<br>大量热点都围绕 matmul、attention、norm、dequantize、gather/scatter、collective 邻接区展开。这种结构化热点恰恰适合由更中观的语言去承载。

第三，硬件变化快，但共性约束也很强。<br>不同代 GPU 细节不同，但 tile、layout、pipeline、memory movement 这些概念具有强共性。中间语言可以在“不过度贴死硬件”和“不过度抽象丢失关键约束”之间找到平衡。

第四，系统栈越来越厚。<br>没有稳定中间表示，compiler、kernel author、runtime、serving system 很难有效协同。

这四点叠加，决定了 GPU 时代尤其需要一层专门表达执行结构的语言。

### 八、DSL 为什么会反过来影响系统抽象，而不只是优化效率

很多人会说，语言再重要，不也还是实现工具吗？为什么要把它抬到系统抽象的高度？

因为语言决定你能稳定表达什么，而能稳定表达什么，最终就会影响系统把什么当一等对象。

如果你的语言只能稳定表达高层算子，而无法表达 tile、fragment、pipeline，那么这些东西就只能作为底层技巧存在，很难形成系统抽象。

反过来，如果你的语言已经能稳定表达：

- block-level tensor view
- tiled copy
- tiled MMA
- layout transform
- software pipeline

那么这些对象就会逐渐从“专家技巧”变成“系统可操作对象”。

一旦对象变得可操作，compiler 会分析它，runtime 会围绕它做契约，团队会围绕它分工，文档和知识也会围绕它固化。长期来看，这就是抽象形成的过程。

所以，DSL 的出现并不只是优化开发效率，而是在推动系统一等对象的显式化。

### 九、为什么说它们像新时代的“汇编之上、图之下”

如果一定要用一句形象但尽量不失真的话来定义 Triton、CuTe 这一层，可以说：

它们像新时代的“汇编之上、图之下”。

为什么这样说？

- 它们比高层图语义更靠近执行结构
- 但又没有掉到最终机器指令那一层
- 它们既保留了足够多的机器约束信息
- 又保留了足够多的结构信息，便于编排和推理

这非常像一种新的中间语言层，而不是普通库 API。

这层如果成熟起来，会对整个 AI 软件栈产生长期影响。因为未来很多最核心的高性能路径，很可能都要在这层找到自己的稳定表达，而不是永远在高层和底层之间跳来跳去。

### 十、它们的边界与局限：为什么还不能简单宣布“以后都用 DSL 写”

把 Triton、CuTe 抬得太高也不对。它们有非常明显的边界。

第一，不是所有工作负载都值得下沉到这一层。<br>很多算子和图级变换更适合停留在高层 compiler 或 library 组合层。

第二，这层表达力越强，复杂度也越高。<br>尤其在 CuTe 一类体系里，抽象本身就有不小门槛。系统要想普遍受益，还需要更好的工程化、模板化和工具支持。

第三，它们仍然要依赖更高层提供结构信息。<br>如果图级边界切错了、layout 从高层就定坏了、runtime 对真实 workload 统计一无所知，再好的 DSL 也只能在坏现实上做局部最优。

所以正确的理解方式不是“以后大家都直接写 DSL”，而是：

DSL 为最关键的中间结构提供承载层，和高层 compiler、低层 codegen、runtime 共同构成系统。

### 十一、这对 AI OS 讨论意味着什么

到了这里，我们可以把它和前面“AI OS”这个主线重新接上。

如果未来真的会形成某种 `Compute OS`，那它一定不只是驱动和 runtime，也不只是若干 kernel 库。它还需要一套能稳定表达核心执行结构的中间语言层。

为什么？因为系统不只要“能跑”，还要：

- 可分析
- 可变换
- 可迁移
- 可与上层契约对接
- 可随着硬件演进而延续核心抽象

而这些要求，恰恰是中间语言层最擅长承担的。

所以从系统角度看，Triton、CuTe 这类 DSL 的意义，远超“方便写 kernel”。它们在帮助未来的 AI 系统栈寻找自己的稳定中观表达。

### 十二、为什么 DSL 也会改变团队边界与知识沉淀方式

这件事还有一个很实际但经常被忽视的后果：一旦中间语言层稳定下来，团队边界和知识沉淀方式都会跟着变。

在没有这层语言时，很多高性能经验只能以几种不太理想的形式存在：

- 少数专家脑中的隐性知识
- 某些特定 kernel 文件里的模板技巧
- benchmark 驱动的经验公式

这种知识形态很难扩散，也很难成为系统能力。因为高层 compiler 看不懂，runtime 无法对接，其他团队也只能“会用不会改”。

而一旦 tile、layout、fragment、pipeline 等结构拥有相对稳定的 DSL 表达，它们就会逐渐变成：

- 可文档化的结构知识
- 可复用的代码模板
- 可分析和可测试的中间对象
- 可被不同团队共同讨论的系统接口

这会直接改变工程协作。compiler 团队不再只是“产出 lower 结果”，kernel 团队也不再只是“写底层魔法代码”，两者之间会开始围绕中间语言形成真正的契约。

### 十三、自动生成与专家手工之间，DSL 很可能会成为最稳的桥

另一个值得提前判断的方向，是自动生成。

未来几年，无论是 auto-scheduler、program synthesis，还是更广义的 AI-assisted kernel generation，大概率都会越来越多。但这并不意味着专家写 kernel 会立刻消失。更现实的图景是：自动生成和专家手工之间，需要一层稳定的中间承载物。

为什么？

因为自动生成如果直接生成极底层实现，很难保证可控性、可解释性和长期维护；如果只停在太高层，又抓不住关键约束。而 DSL 恰好处在一个很好的中间位置：

- 足够接近硬件约束
- 但又保留结构性
- 可被分析
- 可被重写
- 可被专家 review

所以从长远看，Triton、CuTe 这类 DSL 也许不仅是今天的开发工具，更可能是未来自动生成系统和人工专家共同工作的接口层。

### 十四、结语：它们不是写 kernel 的小工具，而是新执行时代的语言雏形

这篇文章想落在一个很明确的判断上：

Triton、CuTe 这类 DSL 真正改变的，不只是 kernel 开发效率，而是它们开始把 GPU 时代最关键的执行结构显式化、语言化、系统化。

它们表达的不是完整应用，也不是最终机器指令，而是介于图与硬件之间那层最关键但长期缺位的结构：

- tile
- layout
- fragment
- pipeline
- memory movement
- block/warp/thread mapping

一旦这层结构拥有自己的语言，系统栈就会跟着变化。compiler 会更像系统组件，runtime 会更容易形成稳定契约，kernel 优化也不再只能靠少数专家在底层手工硬扛。

所以，在我看来，它们不是“方便写 kernel 的小工具”，而是 GPU 时代新中间语言的雏形。

### 附：中间语言一旦成立，会反过来影响生态、教育和人才结构

还有一个长远影响，经常在纯技术讨论里被忽略：一层稳定的中间语言一旦成立，它会反过来影响整个生态的人才结构。

为什么 CUDA 时代会逐渐形成一套相对稳定的工程训练路径？就是因为大家对 block、warp、shared memory、coalescing 这些对象逐渐有了共同语言。类似地，如果 Triton、CuTe 或其他未来 DSL 真正沉淀下来，它们不仅会改变代码怎么写，还会改变：

- 新人如何学习 GPU 系统
- 团队如何分层协作
- 开源生态如何共享可复用模式
- 自动生成系统如何和专家经验结合

从这个角度看，中间语言不是“方便写代码”的局部工具，而是整个系统知识开始被标准化的前奏。

而一旦知识开始标准化，系统创新的速度反而会更快。因为大家终于不必每次都从高层黑箱和底层手工技巧之间反复跳跃，而能在同一层语言上累积经验。

从长期看，这种标准化本身就是系统能力的一部分。

它越早形成，未来 GPU 软件栈的演进成本就越低，生态也越容易形成真正可复用的公共积木。

而一旦公共积木足够丰富，很多今天必须由顶尖专家手工完成的工作，未来才有可能逐步沉淀为“系统默认能力”。
