> 42 天、2693 条 commit。SGLang 这个月不只是在支持更多模型，它正在重写缓存寻址、PD 调度和投机解码的组合边界。

过去一个月，SGLang 的发布摘要看起来仍是一份典型的推理框架成绩单：新模型、NVFP4、AMD 适配、更高的 decode 吞吐。

但 README 和 benchmark 只能回答“结果是什么”。决定这些结果能否复现、能否组合、能否进入生产的，是 PR 里的机制：缓存地址怎样翻译，PD 切角色时哪些状态要重建，投机解码被拒绝以后状态怎样回滚，模型加载如何绕开串行 I/O。

这篇文章按 42 天的代码变更做月度复盘。每个主题都会回答三件事：原来卡在哪里，PR 引入了什么机制，结果付出了什么代价。

### 缓存：系统开始管理“地址与生命周期”

这个月缓存和 Diffusion 一起位于 Release 条目的第一梯队，但缓存的关键变化不在“多存一些 KV”，而在 SGLang 开始把多种模型状态统一到一套寻址和回收机制里。

现代模型里的缓存已经不只是普通 K/V。MLA 使用压缩 latent cache，SWA 有窗口边界，Mamba/GDN/KDA 有 recurrent state，MTP/EAGLE 还有 draft state。它们可能分别存在 GPU、主机内存和远端存储中。缓存命中以后，如果状态没有一起恢复，结果仍然可能出错。

| 代表性PR | 具体改动 | 结果 |
| --- | --- | --- |
| #39627 | Rust TreeCore 默认化；Full、SWA、Mamba 共享树、锁与回收接口；不支持配置集中回退 Python | CPU 侧树操作统一；531 个 CPU 测试、43 个子测试通过，36 个 Python/Rust write-back 场景一致 |
| #42399 | 新增 SeaweedFSStore：以 KV page 为对象，page buffer 直读直写，key 按模型和 rank 隔离 | 长前缀 L3 TTFT 降低 3.5×—4.7×；小模型约 25K token 以下仍可能重算更快 |
| #37628 / #40491 / #40492 | Draft KV 嵌入 target slot；一个 slot 同时寻址 target/draft，读写经过 virtual/physical ID 翻译 | 支持 EAGLE/EAGLE3/DFlash/DSpark 融合路径；Kimi-Linear 一组配置显存 127.8→90.8 GiB/rank |
| #43868 / #43870 | 预取、staging、H2D、prefix insert 与 receipt release 拆成 pipeline operation；新增 block-group 命中 | 支持 side-pool 整组命中与 caller-owned 目标行；FULL 淘汰可持续走到分配目标 |
| #41769 | DSA transfer 先对齐 PP 层 span，再跳过未读取的零长度 index-K entry | GLM-5.2 Prefill KV 容量 +11.6%、Decode +13.7%；该测试吞吐基本不变 |

Rust TreeCore 不是一次“把 Python 换成 Rust”的重写。它把插入、分裂、淘汰、HiCache 回写和锁 receipt 都收敛到统一接口，连 T-LRU 的整数/浮点比较顺序都要与 Python 对齐。这样做的原因很实际：模型并行度上来以后，CPU 侧的锁竞争和树操作会先于 GPU 成为瓶颈。

SeaweedFS 的实现也说明 L3 缓存的难点在对象语义。每个 KV page 是一个对象，page-first 布局下多个 host buffer 被连续写入同一对象；对象大小不匹配就直接视为 miss，避免错误覆盖；MLA rank 共享相同 KV，所以共用 key，MHA rank 则必须按 TP/CP 分开。它不只是把文件传到 S3，也在定义缓存页、rank 命名空间和兼容接口。

最值得关注的是 fused draft KV。此前 draft 有自己的池和第二套地址空间；新机制把 draft 的 K/V 行放到 target slot entry 后面，使一次分配、一次释放、一次整页搬迁同时带走 target 与 draft。虚拟 ID 保证请求在 compaction 后仍指向正确逻辑 slot，物理 ID 则供 attention kernel 当前寻址，二者由 translator 在读写门口转换。

这套设计并不等于所有投机算法都能直接受益。fused 区域目前要求 draft 使用稠密、全注意力 K/V；不等宽 K/V、draft 自己的 SWA/recurrent 层、不同 KV dtype、DCP 和部分 host-pool 模式仍会退回独立池或被启动检查拒绝。

性能上也有清晰边界。SeaweedFS 的零拷贝路径把 1.6K、6.6K、13.2K token 的 L3 TTFT 从通用路径的 4.85、16.4、31.9 秒降到 1.41、3.81、6.83 秒。在同一块 A10 上使用同一个 Qwen3-4B 和相同 page size 做对照时，小于约 25K token 的请求直接重算仍可能比从 L3 加载更快。缓存是否值得读，取决于前缀长度、存储带宽和 Prefill 成本。

`#41769` 还给出一项很干净的容量收益：GLM-5.2 的 78 个 DSA 层里，21 层是 top-k producer，57 层只共享索引、不读取自己的 index-K。允许 HiCache/PD 跳过这些零长度 entry 后，Prefill 的 KV 容量提高 11.6%，Decode 提高 13.7%。这组实验中吞吐没有明显变化，因为 KV 容量并不是当时负载的约束；容量优化只有在缓存压力真实存在时才会转成吞吐。

代码索引：[#39627](https://github.com/sgl-project/sglang/pull/39627)、[#42399](https://github.com/sgl-project/sglang/pull/42399)、[#37628](https://github.com/sgl-project/sglang/pull/37628)、[#40491](https://github.com/sgl-project/sglang/pull/40491)、[#40492](https://github.com/sgl-project/sglang/pull/40492)、[#43868](https://github.com/sgl-project/sglang/pull/43868)、[#43870](https://github.com/sgl-project/sglang/pull/43870)、[#41769](https://github.com/sgl-project/sglang/pull/41769)。落点包括 `unified_tree_core.rs`、`seaweedfs_store.py`、`fused_draft.py`、`kv_index_translator.py`、`unified_radix_cache.py` 与 DSA transfer 路径。SeaweedFS 数据来自单张 A10、Qwen3-4B、page size 64 的冷/热前缀测试。

### PD：从部署拓扑变成状态控制面

PD 分离把 Prefill 和 Decode 放到不同 worker，但固定角色很难适应波动的输入/输出比例。这个月的几项 PD 工作，开始分别处理资源弹性、准入时机和异构并行。

| 代表性PR | 具体改动 | 结果 |
| --- | --- | --- |
| #28403 | 保留角色无关 KV pool；只重建 bootstrap、sender/receiver、socket、RDMA 注册等角色结构；排空后重派 event loop | 支持运行中 P↔D 切换；100 次往返切换无失败，权重/KV/thread 资源保持平稳 |
| #40703 | 新增 prefill_complete 准入策略；最终 Prefill 结果就绪后发送带 nonce/ownership 的 readiness | Decode KV 压力场景吞吐 +26.8%、p95 TTFT −48.9%；p99 ITL +92.77%，保持 opt-in |
| #40909 | 按 token 和 KV-head ownership 切分 SWA state；NIXL/Mooncake 各自完成传输 | TP1↔TP4 双向请求通过；PP>1 或不兼容布局仍拒绝，未宣称跨 TP 数值完全等价 |

#28403 的关键前提是 Prefill 和 Decode 共用同一种 KV 池，因此切角色不需要重分配 KV 或碰模型权重。实现只替换 role-specific 数据面结构；如果重建失败，实例直接进入 unhealthy，而不是假装原地回滚。角色翻转还必须等实例完全 idle，因为运行中的 Decode 请求可能仍持有上游 Prefill 写入的 KV。自动按负载触发的 flip 策略不在这个 PR 内，当前仍由 operator/router 控制。

#40703 改的是时机，不是分配速度。它把 Decode 目的 KV 的预留从“Preflight 时”推迟到“最终 Prefill 结果被接受后”。在 GLM-5.2 NVFP4、Decode KV 受压的混合长短请求测试里，吞吐提高 26.8%，p95 TTFT 降低 48.9%；但 p99 ITL 上升 92.77%，因为 KV 在源端停留更久，chunked prefill 与传输的重叠也减少了。这个策略因此保持 opt-in，而不是改成默认。

#40909 则说明“PD 支持不同拓扑”不是只改传输接口。hybrid SWA 的窗口状态必须按 token 与 KV head 重新切片，并保证目标 rank 的窗口字节与外围 sentinel 完全正确。当前仅支持 PP1，并继续拒绝不兼容的 buffer layout。

三项工作合起来，PD 从“启动时选 Prefill 或 Decode”变成了一个涉及准入、状态、通信和故障边界的控制面。它的难点已经不在 KV 传得多快，而在何时切、何时分配、失败后由谁恢复。

代码索引：[#28403](https://github.com/sgl-project/sglang/pull/28403)、[#40703](https://github.com/sgl-project/sglang/pull/40703)、[#40909](https://github.com/sgl-project/sglang/pull/40909)。主要落点为 `disaggregation/role_switch.py`、`disaggregation/common/bootstrap.py` 与 `disaggregation/common/conn.py`。性能数字来自各 PR 的指定模型、GPU、并发与 KV 压力配置。

### Layer boundary：把并行语义从模型代码里抽出来

这个月还有一组不太出现在性能 headline 里的重构。[#41547](https://github.com/sgl-project/sglang/pull/41547) 到 [#41557](https://github.com/sgl-project/sglang/pull/41557) 收拢了 residual、attention/FFN 边界、reduce fusion 和 CP adapter；随后多个 PR 把一批 decoder 改成从 stage boundary 构建，其中 [#41779](https://github.com/sgl-project/sglang/pull/41779) 一次迁入 7 个模型。

过去这些 decoder 往往自己把 residual 穿过每一层，再手动把两个 tensor 交给下一个 PP rank。attention projection 的一次 all-reduce 与 FFN 输入融合、DP attention gather、aux hidden-state capture 和最后 norm 也因此散在各模型里。边界重构后，模型通过 `residual_batch` 的 start/from_pp/to_pp/final_norm 进入和离开阶段，attention 输出可以把 TP sum 留给 FFN 输入，MLP 明确完成自己的 reduction。

这组 PR 没有宣称性能提升，却在解决更长期的问题：模型数持续增长后，每接一个 decoder 都重新实现并行通信，迟早会出现重复 reduce、错误的 PP handoff 或遗漏 aux state。PR 验证里甚至修掉了 EXAONE 4.0 在 PP2 下原本无法启动的问题。它的价值是把“模型能跑”和“模型能在所有并行组合下正确跑”拆成两个清楚层次。

### 投机解码：正确性已经成为性能的一部分

投机解码的表面指标是接受长度和 tok/s，代码里的复杂性来自 draft、target、KV 和 recurrent state 在每一步如何对齐。

| 代表性PR | 具体改动 | 结果 |
| --- | --- | --- |
| #37771 | 多步 gather/commit swap 接入 HiSparse；一次处理多步 miss、scratch 与 accepted-token commit | 端到端支持 EAGLE/MTP + HiSparse；GSM8K 97.50% 对 96.00%，GPQA-Diamond 90.91% 对 91.92% |
| #43735 | target KV 按位置 stripe；index-K 复制；每 rank 局部 top-k 后合并 LSE；MTP pool 按 DCP 复制 | GLM-5.3：DCP2+MTP 1041→1876 gen tok/s，DCP8+MTP 838→1784 |
| #43029 | 用 committed length 重算 verifier 窗口，处理 grammar-retained token 与非 draft token 边界 | 修复错误 Mamba state 恢复；新增 165 行边界测试，覆盖跨 interval 场景 |

这三项分别解决生命周期、并行和边界。HiSparse 的变化不是多加一个判断，而是把 speculative verify 前的 scratch、多步 page-map、accept 后的 cache commit、host backup 和请求清理放进同一条生命周期；DCP + MTP 则要保证每个 rank 只做局部 top-k，却仍能通过 LSE merge 得到全局 attention 结果。

计算结果也没有被故意藏起来：#43735 在 8×B300、GLM-5.3 上，DCP2 + MTP 从 1041 提升到 1876 gen tok/s，DCP8 + MTP 从 838 提升到 1784；但 AIME26 pass@1 因采样和截断存在波动，不能只看吞吐。PR 同时明确 HiCache、PD、tree drafting 等组合仍会拒绝启动。

#43029 更值得单独看。投机 token 被拒绝只是表面，难点在 grammar 截断、非 draft token 和 committed length 三者共同决定 verifier 窗口。原逻辑在跨 interval 边界时可能把仍处于同一 track 的请求误判成跨页。修复后只改了一小段分支，却用 165 行测试锁定不同 retained/非 retained 路径。

这说明一个成熟推理框架的评价标准正在变化：支持哪些投机算法只是功能表，能不能解释状态提交、回滚和组合拒绝理由，才决定它能否被生产使用。

代码索引：[#37771](https://github.com/sgl-project/sglang/pull/37771)、[#43735](https://github.com/sgl-project/sglang/pull/43735)、[#43029](https://github.com/sgl-project/sglang/pull/43029)。主要落点为 `managers/hisparse_coordinator.py`、`layers/attention/dsa/dsa_dcp.py` 与 `scheduler_components/batch_result_processor.py`。投机倍率依赖模型、draft、并行、batch 与上下文条件，不可互相相乘。

### 算力利用：专用 kernel、调度与 Graph

本月最醒目的提升来自四个不同的模型路径。它们说明 SGLang 不再追求一套通用 kernel 打天下，而是在统一接口下给热点组合建立专用 fast path。

| 代表性PR | 具体改动 | 结果 |
| --- | --- | --- |
| #41251 | DeepSeek-V4.1 Hopper 调 group32 GEMM、复用精确 BF16 权重展开、用 live paged indexer length、融合 mask/sort/slot map | 8×H200 每 GPU 输出吞吐 2.1×—2.3× |
| #42175 | Qwen3.8-Flash-Next 重叠 HC gate 与 block 计算、融合 norm、延迟 MoE finalize、改用更小 GDN value tile | 4×B200、C1 下 242.4→271.0 tok/s，decode graph kernel 数 1432→1241 |
| #42489 | GLM-5.3-Flash DFlash 复用 CPU seq_len、一次构建 pooled page table、调 KDA recurrence 与 gated norm launch | 8×B300 decode 1091.9→1199.7 tok/s |
| #41886 | MiMo 在 SM100/SM103 默认切到 FA4，保留显式 backend override | DFlash decode 1.85×，普通 decode +9%，TTFT −34.8% |

这些 PR 的深度差异很大。#41886 只增加了五行默认选择，却让 MiMo 避开不合适的 Triton fallback；#42175 则深入层边界，把 HC、shared gate、MoE finalize 和 GDN tile 重新编排。性能提升来自不同层级，不能用一个“kernel 优化”概括。

硬件边界也在继续扩张。除了 AMD MI350/MI355 和 Intel 发布镜像，本月还补上了 Apple Silicon 的标准 PyTorch 后端（[#36780](https://github.com/sgl-project/sglang/pull/36780)），与已有 MLX 路径并存。它未必能立刻服务大模型集群，但说明同一 serving API 正在向桌面和异构设备延伸。

代价也必须写出来。#41251 的 Hopper derived cache 让模型加载内存从 72.71 增至 75.43 GB/GPU，`max_total_num_tokens` 从 16,012,800 降到 14,223,104，约少 11.2%；在线更新权重时还要关闭这些 derived cache。#42175 的 MoE specialization 也只在 hidden 2560、512 experts/top-10、BF16、SM10、TP4/EP1 且没有 LoRA、投机和双 batch overlap 时启用。

所谓“快 2.3 倍”从来不是免费午餐。SGLang 的选择是让收益明确的配置继续加速，同时用 dispatch guard 把不支持组合挡在专用路径之外。

补充：四组结果使用的模型、GPU 数量和并行配置不同，不能横向相加。准确率与吞吐数据见对应 PR。

### MoE 与 MLP：专用融合继续下沉

Blackwell 上的 MLP 也新增了专用 fast path。[#41887](https://github.com/sgl-project/sglang/pull/41887) 用 CuTe DSL 把 `input @ gate_weight`、`input @ up_weight` 和 `SiLU(gate) * up` 融进同一个 dual-GEMM kernel；B200 FP8、Qwen2-7B 的测试中，输出吞吐均值提高 8.96%。

MegaMoE 则补上了启动期 autotune（[#43789](https://github.com/sgl-project/sglang/pull/43789)）。它在 CUDA Graph capture 之前准备 decode/prefill capacity profile，用同步后的 DP token 数在 EP rank 间选择同一 workspace，并缓存 native tactic。这样不会让首个真实 batch 承担 tuning 抖动，也避免每层再分配私有 workspace。

代码索引：[#41887](https://github.com/sgl-project/sglang/pull/41887)、[#43789](https://github.com/sgl-project/sglang/pull/43789)。MoE 和 MLP 的收益依赖 GPU 架构、精度与 batch shape。

### 调度器：重点从排序转向不让流水线停住

调度改动不碰模型前向，却直接决定 GPU 能否持续有活干。

[#40024](https://github.com/sgl-project/sglang/pull/40024) 增加 shortest-prefill-first：按剩余 uncached token 选择请求，并为较短等待请求保留后续 chunk 预算，避免一个长请求长期占住 Prefill 进度。

更关键的是 [#42035](https://github.com/sgl-project/sglang/pull/42035)。PD Prefill 的 overlap loop 原先在 `copy_done.synchronize()` 等结果，期间不再接收新请求；长 Prefill 会把 intake 变成 stop-and-go。新实现把同步等待改成 non-blocking query，并在 TP CPU group 上做一次 `MIN`，让所有 rank 对“最老 batch 是否完成”达成一致。这样结果 pending 时还能继续 ingest 并准备第二个 batch。

同月还修正了两条会丢请求或打崩服务的路径：[#43290](https://github.com/sgl-project/sglang/pull/43290) 在 mixed-chunk 混入 running decode 前先检查 KV 是否装得下，不足时让 decode 延后一步；[#43298](https://github.com/sgl-project/sglang/pull/43298) 在 admission 预占了低优先级请求却最终没有接纳任何请求时，把 preempted requests 重新入队。后者的端到端测试中，原实现每轮最多丢 1⁄6 请求，新实现 36⁄36 全部返回。

代码索引：[#40024](https://github.com/sgl-project/sglang/pull/40024)、[#42035](https://github.com/sgl-project/sglang/pull/42035)、[#43290](https://github.com/sgl-project/sglang/pull/43290)、[#43298](https://github.com/sgl-project/sglang/pull/43298)。PD continuous polling 目前由环境变量开启，并限制在非投机、attention DP=CP=1 的路径。

### CUDA Graph：从 decode 快路径扩展到 prefill 与 mixed chunk

CUDA Graph 一直是 decode 的常规优化，但这个月开始覆盖更复杂的 prefill 路径。

DeepSeek-V4 的 C4 indexer 原先按模型最大位置 1,048,576 填充 `[N, context]` logits；当 prefill graph 捕获到 16K batch 时，单是这块 workspace 就很大。新参数 `--cuda-graph-prefill-max-context` 允许按实际部署上下文裁剪 padding，超出范围的请求回退 eager。结果是捕获内存从 43 GB 降到 18 GB（−58%），端到端延迟约降低 10%。

同时，GLM-5.3-Flash 的 KDA extend 开始进入 breakable prefill graph，并被设为默认；Full prefill graph 也能接受 mixed chunk，在不放弃 decode 进度的前提下交错处理新 Prefill。

这条线的关键不是“graph 更多了”，而是 fallback 设计：形状未捕获、上下文超过预算或混合并行无法捕获时，请求要能干净回退 eager。Graph 覆盖越广，启动时间、捕获内存和 bucket 管理越重要。

代码索引：[#36534](https://github.com/sgl-project/sglang/pull/36534)、[#42845](https://github.com/sgl-project/sglang/pull/42845)、[#43461](https://github.com/sgl-project/sglang/pull/43461)。

### NVFP4：容量收益最大，但 Prefill 不一定更快

NVFP4 是这个月最容易误读的一组数字。

#36340 为 SM100/SM103 增加了原生 packed NVFP4 KV。K/V 保持 slot-major，GenMHA 通过 strided HND view 直接读取；K scale 按 token 线性排列，V scale 使用 GenMHA 的四 token interleave。decode 可在 attention kernel 内完成反量化，避免单独的整块 dequantize 读写。

在 Qwen3.5-35B-A3B、GB300、1M 上下文测试里，NVFP4 KV 每 token 的 MHA KV bytes 比 FP8 少 43.75%，理论容量为 1.778×。但 native FP4 的 Prefill 是 14.84 秒，FP8 是 13.36 秒，约慢 10%；非 MTP decode 只快 4.2%，MTP decode 反而慢 8.2%。对应的 q_len=1 attention kernel 虽然快 1.355×，整段 decode 只留下 4.2%——这再次说明 kernel 与链路收益不能混为一谈。

另一篇官方博客测试 Qwen3.8-27B + RTX PRO 6000，结果又不同：等并发 decode 吞吐提高 26%—30%；利用容量提高并发后，32K/160K/1M 的峰值吞吐提高 37.37%/57.75%/78.46%。但 Prefill TTFT 在等并发下略差 0.20%—0.40%，SWE-bench Verified 也从 FP8 的 77.80% 降到 76.20%。

两组结果并不矛盾，只是模型、GPU、并行和执行路径不同。它们共同说明：NVFP4 KV 最直接的收益是字节数和容量，不是所有阶段都变快。是否启用，要看上下文长度、并发、Prefill 成本和质量容忍度。

补充：NVFP4 KV 当前仍被官方标为实验性能力；两组 benchmark 不是同一实验，不能合并成单一加速倍率。官方博客中的 1M 上下文为性能测试覆盖，Qwen3.8-27B 原生上限为 262,144 tokens。

### Vera Rubin 的提醒：20% kernel 不等于 20% 服务

官方 Vera Rubin 博客提供了一个衡量端到端收益的例子。同一个 Kimi K3 服务里，MLA 加深 pipeline 后于 batch 16、128K 上下文下快 16%；split-KV reduction 改加载顺序后，batch 1 的 full FP8 MLA 快 20%。

可是 split-KV 从 32 路增加到 64 路，端到端只提升 1.9%。另一边，MoE finalize、shared expert、all-reduce 和 RMSNorm 合成一个 collective kernel，每个 decode step 少 276 次 launch，端到端提升 5.9%。

这组对比说明，推理框架越成熟，越需要区分 microbenchmark 与请求级收益。局部热点只占整条 trace 的一部分，减少固定 launch 开销有时比继续优化一次 GEMM 更值钱。

资料：[SGLang and Miles on NVIDIA Vera Rubin](https://lmsys.org/blog/2026-10-09-vera-rubin/)。

### 服务边界：加载、路由与 API 不再是外围

这个月还有一批改动不发生在 GPU 前向里，却直接影响线上吞吐和首字延迟。

| 代表性PR | 具体改动 | 结果 |
| --- | --- | --- |
| #40453 | InstantTensor loader：safe_open 流式迭代、接入 process group、支持 I/O 参数调优 | 50 GB/s 存储下 Qwen3-30B 57.4→1.77 秒，DeepSeek-R1 160→15.3 秒 |
| #41766 | protobuf 直接映射到共享 FrontendHandle；事件流反向转换成 protobuf | Rust 原生 Text/Generate gRPC 可用，流式、取消和错误码语义保留 |
| #38965 | multi-position pooling；候选一次 Prefill，每个 anchor 读取分类 head | Qwen3-8B、16 候选的 MIS p95 20.6 ms，Generate 54.1 ms，SIS 53.1 ms |
| #39108 | Cache-aware tree 为每个 worker 维护 GPU/Host/DISK/EXTERNAL tier bitset | device 淘汰不再抹掉 host 归属，修复前缀短暂不可路由问题 |
| #41974 | 按 sticky key、最深 prefix、最少在途请求选 DP rank，并透传专用 header | Router 可稳定落到有缓存的 rank；客户端伪造 header 会被剥离 |
| #42316 | /v1/messages 入口转内部 chat request，回复与 SSE 转 Anthropic 格式 | Anthropic SDK、Claude Code 可直接接入，支持图片、工具、thinking 与流式 |

InstantTensor 的收益高度依赖存储。50 GB/s 存储下，Qwen3-30B-A3B 加载从 57.4 秒降到 1.77 秒，DeepSeek-R1 从 160 秒降到 15.3 秒；换到 tmpfs，DeepSeek-R1 只剩 1.87×，因为加载已不完全受磁盘限制。这说明优化的是 I/O 流水线和并行读取，不是“所有机器都能快十倍”。

Rust gRPC PR 也没有另造前端。它把 protobuf 直接转换成已有的 `FrontendRequest`，把 `FrontendEvent` 流映射回 protobuf，并保留 cancellation、增量/累计输出和错误码语义。明确返回 `UNIMPLEMENTED` 比静默忽略字段更适合生产。

Score API 的关键机制是 pooling position。候选集合被放进一个 prompt，每个候选后放 extraction token；`pool_at_positions()` 在一次前向中池化多个位置。MIS 再把多个候选组成 block-diagonal attention，共享 query prefix。调度器还会按 pooling mode 拆分 Prefill batch，避免 setwise 与 pointwise 混批改变接口结果。

官方 16 候选测试里，Qwen3-8B 的 MIS p95 为 20.6 ms，Generate 为 54.1 ms，SIS 为 53.1 ms。但 setwise 要求关闭 radix cache 和 chunked prefill，低负载下也未必最快。它适合候选择优和 Agent 决策，不是生成接口的通用替代。

模型支持也继续向生成之外扩张。本月新增的 Clef / Clef Flash、PPLX-Decider v1/v1.1 和 EmbeddingGemma 2，分别覆盖决策、排序与 embedding 工作负载。SGLang 的 API 面因此不再只围绕 chat completion 展开。

Router 的 #39108 则揭示了层次化缓存下更隐蔽的错误。engine 已经会在 device 副本被淘汰时发布 tier-tagged KV event，但 in-process radix tree 把任何 `BlockRemoved` 都理解为整个前缀消失。结果设备缓存周转一次，host 里仍可快速回读的前缀就全部“不可路由”，实测仅剩约 2.4% 的 host-hit。新树为每个 worker 维护四层 tier bitset，device eviction 不再抹掉 host/L3 归属。

#41974 又把手伸到 worker 内部：如果 DP rank 各自拥有 KV，而 Router 只在 worker 级选路，同一会话的下一轮可能落到另一个没有缓存的 rank。新路径按 sticky session key、最深 prefix、最少在途请求依次选 rank，并覆盖客户端伪造的 rank header。

面向 RL 的权重更新也发生了结构性变化。[#40777](https://github.com/sgl-project/sglang/pull/40777) 增加 `begin_weight_update` / `end_weight_update` 会话：开始时把已经被 Marlin、MXFP8、NVFP4 等 postprocess 改写的 packed weights 恢复成可加载布局，结束时统一重新做 kernel layout；一个 refit 跨多个 bucket，只 finalize 一次。target 与 draft 的 runner 也被统一枚举，EAGLE、MTP、DFlash、DSpark 等投机 worker 不再各走一套更新逻辑。

这不是普通的 API 整理。训练侧更新权重时，如果只调用 `load_weights` 而漏掉 `postprocess_weights`，参数形状可能能加载，kernel 读到的布局却已经错了。PR 同时明确 W4A16 Triton MoE 等格式暂时不能安全 refit。能更新权重，不等于量化后的 kernel layout 也被正确恢复。

API 侧的安全边界也在收紧。Responses 的数据保存在本月改为默认关闭，PD 部署直接禁止开启，`previous_response_id`、background 和 PD 内建工具在准入阶段返回错误，避免 Prefill 与 Decode 对状态存储的假设不一致。这个改动不提升吞吐，却消除了无界内存泄漏，以及 Decode 可能一直等不到对应 KV 的故障路径。

可观测性也在从“机器指标”下沉到“请求因果”。这个月新增 request-level TPOT histogram，让非 streaming 和 streaming 请求都能按请求统计输出间隔；HiCache 的 `storage_prefetch_wait` 与 `storage_staging_wait` 直接进入请求 meta info；DP attention 则导出每 rank 的 token imbalance、idle step 和 sync wait。以后分析一次慢请求，可以区分是在等存储、等最慢 rank，还是单纯生成慢。

API 还增加了可选的 Aaronson-Gumbel 文本水印。它不额外生成 token，检测只看 token ID 与密钥；实现覆盖普通 decode、EAGLE/NEXTN 和混合 watermarked batch，并对 DFLASH、PD、beam search 等不支持组合 fail-closed。代价也公开了：有限 top-k 基本在噪声内，unlimited top-k 会损失 2.8%—7.2% 单流吞吐，MTP TPOT 约增加 9.2%。这类功能说明 serving runtime 开始承担模型之外的治理责任。

代码索引：[#40453](https://github.com/sgl-project/sglang/pull/40453)、[#41766](https://github.com/sgl-project/sglang/pull/41766)、[#38965](https://github.com/sgl-project/sglang/pull/38965)、[#39108](https://github.com/sgl-project/sglang/pull/39108)、[#41974](https://github.com/sgl-project/sglang/pull/41974)、[#42316](https://github.com/sgl-project/sglang/pull/42316)、[#40777](https://github.com/sgl-project/sglang/pull/40777)、[#40275](https://github.com/sgl-project/sglang/pull/40275)、[#43946](https://github.com/sgl-project/sglang/pull/43946)、[#42755](https://github.com/sgl-project/sglang/pull/42755)、[#37577](https://github.com/sgl-project/sglang/pull/37577)。InstantTensor 数据来自 50 GB/s 存储与指定 GPU。

### Diffusion：ComfyUI 支持是一层翻译，不是包装脚本

本月 SGLang-Diffusion 有 210 个 Release 条目。新增模型之外，更值得看的是 ComfyUI integrated mode 如何处理 checkpoint 与执行语义。

#43504 让 MiniMax-H3、FastH3 和 VDN-H3 在 ComfyUI 中运行。代码修正了 audio velocity 被重复缩放、denoise mask 与 carried-audio transform 顺序不一致；FastH3 必须读取原生 runtime 目录与训练好的 sigma grid，不能把 8-step 蒸馏模型当普通 H3；VSA/cube/VDN hybrid 的 sparse attention 还需要按 step 生成对应 metadata。

#43581 则把 Qwen-Image 2.1 的 ComfyUI row-fused `img_mlp.gate_up` 拆成 gate/proj，应用 `comfy_quant` marker；reference edit 时在 image slot 插入占位 token、处理 ComfyUI 与原生 latent grid 的半 token 偏移，并在显存允许时为同一 condition 缓存 prefix K/V。没有这些转换，接口能加载文件，生成结果也不一定正确。

社区 LoRA 兼容则暴露了同类问题。[#42174](https://github.com/sgl-project/sglang/pull/42174) 发现热门 Qwen-Image 2.1 LoRA 中，fused `gate_up` 参数会被静默丢弃，实际只覆盖 160⁄224 个 block layer；修复后多个热门 LoRA 恢复到 224⁄232 的完整覆盖。diffusers 将 `lora_alpha` 存在 metadata 中，此前退化成 rank 默认值，Pruna 因此只以一半强度运行；修复后可逐像素复现显式 alpha=128 的结果。

GGUF 也不是统一转换器就能解决。[#39523](https://github.com/sgl-project/sglang/pull/39523) 针对 H3 text encoder 的 folded patch embedding，把 ComfyUI 的 `(3456,2,16,16)` 恢复成原生 Conv3D 期望的 `(1152,3,2,16,16)`。在公开 GGUF 与原 BF16 checkpoint 上，FP32/BF16 Conv3D 输出都做到 `max_abs=0`。

最终数据包含质量与延迟两条线。Qwen-Image 2.1 BF16/INT8 在 1024² 下与 stock ComfyUI 的 latent cosine 分别为 0.997⁄0.998；MiniMax-H3 为 0.982。性能侧，MiniMax-H3 去掉一次 4.2 GiB 全视频 copy，VAE 后处理快约 21%；Wan2.2 TI2V 5B 单 B200 请求从 6.27 秒降到 5.83 秒。

这说明 Diffusion 的“支持新模型”是一段很长的翻译链：checkpoint 命名、张量布局、采样网格、mask 顺序、attention metadata 和 cache 生命周期都要与原生实现对齐。SGLang 复用 LLM 侧的量化、图捕获、offload 和并行能力，但不能跳过模型语义本身的适配。

月底两篇 Day-0 博客也说明这种适配正在前置。Nemotron 3.5 Super VL 是 120B-A12B 的混合 Mamba-Transformer 多模态模型；Muse Spark Open 是 816B 参数、约 42B 激活、支持 1M 上下文的多模态 MoE。后者在 4×GB300、TP4/EP4 上加入 sequence parallel 与 NVFP4 MegaMoE 后，p90 TTFT 比普通 TP4 低 28.3%—41.9%。收益来自 activation、routing、all-to-all 和 expert output 的重新分摊，而不是单个 attention 加速。

代码索引：[#43504](https://github.com/sgl-project/sglang/pull/43504)、[#43581](https://github.com/sgl-project/sglang/pull/43581)、[#42174](https://github.com/sgl-project/sglang/pull/42174)、[#39523](https://github.com/sgl-project/sglang/pull/39523)。主要落点为 `executors/minimax_h3.py`、`executors/qwen_image21.py`、Qwen-Image LoRA adapter 与 GGUF patch embedding loader。Cosine 数据来自固定 seed、指定分辨率与步数的端到端对比。

### 回顾：三条主线

第一条是**统一寻址**。KV、SWA、Mamba state 和 draft KV 不再各自维护一套 ID 空间。target slot、virtual id、physical id 和 translator 正在成为公共基础设施。

第二条是**状态协议**。PD 切换、Prefill-complete 准入、HiSparse 多步 swap、DCP + MTP 和投机回滚都需要明确谁拥有状态、何时提交、失败后回到哪里。性能优化只有状态正确时才成立。

第三条是**性能策略化**。DeepSeek、Qwen、GLM、MiMo 各自需要不同 kernel、量化布局和并行 guard；PD 的 Prefill-complete 策略改善 p95，却恶化 p99；NVFP4 KV 增加容量，却可能拖慢 Prefill。越来越多的收益取决于 workload，已经没有一个全局默认值适合所有部署。cookbook 因此正在从说明文档变成策略配置。

如果沿着这三条线继续走，下一阶段的竞争会落在上下文对象化、组合测试、缓存感知路由和任务级 SLO。单卡 tokens/s 仍会增长，却越来越难解释整条服务链路的效率。

### 给使用者的判断

单模型、短文本、稳定流量，优先关注加载、attention backend 和目标模型的专用 kernel。动态 PD、复杂 L3 缓存未必马上带来收益，反而增加配置和故障面。

长上下文、多轮 Agent、MoE 或 PD 集群，则应重点评估 fused draft KV、HiCache 分层、动态 PD 和 DCP + MTP。上线前至少要覆盖：

- PD × 量化 × 投机解码 × 结构化输出；
- HiCache × Mamba/线性注意力 × 长对话恢复；
- Router 缓存亲和 × 多实例扩缩容；
- Diffusion × LoRA/GGUF × offload。

验收不要只看吞吐。p50/p95/p99 TTFT、TPOT、p99 ITL、任务准确率、缓存命中率、冷启动和恢复时间都应记录。尤其要验证状态回滚和缓存迁移，因为这类问题往往不会崩溃，只会让结果悄悄偏离。

升级检查：月末版本要求 Python 3.11+；`--enable-dp-attention` 已改用 `--attn-dp-size`；disaggregation decode host receive threshold 的 0/1 语义发生翻转；`ChunkCache` 与 `tc_piecewise` 被移除。上线前应先核对启动参数和部署镜像。

### 展望：下一阶段会竞争什么

**第一，KV cache 会成为可寻址、可迁移的上下文资源。** 当前 unified pool 已经在分离 virtual/physical ID，fused draft 又让 target 与 draft 共用 slot。下一步自然会走向跨实例缓存归属、compaction 后继续复用，以及 L3、Router 和调度器共同决定上下文放在哪里。真正的难点不是存得下，而是迁移后还能正确读。

**第二，状态正确性会成为功能发布的硬门槛。** 这个月已经有投机、Mamba、结构化输出的组合 bug，也出现了 PD、HiSparse、DCP、HiCache 大量互相拒绝的配置。下一阶段需要的不只是更多兼容开关，而是可视化的能力矩阵、明确的 ownership、跨 batch 一致性测试和自动回退。

**第三，默认性能会继续让位于 workload-aware policy。** shortest-prefill-first 改变调度顺序，Prefill-complete 改变 KV 准入时机，tier-aware Router 调整缓存亲和，NVFP4 改变容量与 Prefill 的平衡。这些策略不存在统一最优值。未来更可能看到 SGLang 根据模型、SLO、缓存层级和硬件自动选择 policy，cookbook 也会变成可执行的策略配置。

**第四，评估指标会从 token 速度转向任务成本。** Decision API、Agent 负载和新增的请求级遥测都在推动这个变化。完成一次任务需要多少时间、消耗多少 token、命中多少缓存、调用工具错多少次，会比单卡 tok/s 更能解释系统价值。

接下来一个月，我会重点看三件事：unified memory 是否继续跨实例；Router 是否把 GPU/Host/L3 的 tier 信号真正转成选路策略；新增的 TPOT、存储等待和 DP imbalance 指标能否闭环到自动调度。如果这三条同时推进，SGLang 的竞争对象就不再只是推理引擎，而是 Agent 时代的内存、缓存和调度基础设施。

放到更长周期看，模型权重和硬件代数都会快速变化，真正可复用的会是上下文的身份与迁移协议、缓存和实例的归属关系、状态提交与回滚语义，以及把 SLO 转成调度策略的能力。SGLang 这个月的工作是否成功，不应只看下一次 benchmark 高出多少，而要看它能否让不同模型、并行方式和加速器在同一套控制面上可靠组合。那一天，“推理框架”这个词本身也会显得过窄。
