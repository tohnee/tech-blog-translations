## 0x01. 写在前面

好久不见~

这段时间没有更新知乎，是因为最近的工作比较忙，带着团队里的同学们一起打通了coding agent的整个优化链路，踩了非常多的坑。不过这些坑都是各种和工程相关的，涉及到流水线/网络/服务部署之类各种方面的bug，比较琐碎且缺少普适性，很难沉淀出对大家有指导意义的文章。

之后只要有时间，还是会继续做大模型的知识整理的。这篇文章应该是LLM Agent系列的倒数第二篇：MCP（Model Context Protocol，模型上下文协议）。

因为这个系列的下一篇会是 **Skills** ，即使现在MCP使用已然不多，但为了整个发展进程的完整性，MCP作为此前一个非常重要的发展阶段，我们必须要先了解MCP。

本文不会深入 MCP 的实现细节，而是完全从应用视角出发，讲清楚它到底解决了什么问题、怎么用、又为什么会被质疑。最后，我会重点分析 MCP 的局限性，并解释为什么会出现 “MCP is dead. Long live the CLI” 这样的论点，以及在 CLI + Skills 的时代，我们为什么在某些场景下仍然需要 MCP。

## 0x02. 什么是 MCP

> "把一条巴别鱼塞进耳朵，你就能立刻听懂任何物体以任何语言形式向你表述的意思。" ——《银河系搭车客指南》，道格拉斯 · 亚当斯

MCP（Model Context Protocol，模型上下文协议） 起源于Anthropic发布的文章 [Introducing the Model Context Protocol](https://www.anthropic.com/news/model-context-protocol) 。这篇官方文章用了一个非常直观的比喻：

“MCP 就是 AI 应用的 USB-C 接口。正如 USB-C 让不同设备能通过 **同一种接口** 连接，MCP 让不同 AI 应用能 **通过同一种协议连接各种工具和数据** 。”

> Think of MCP like a USB-C port for AI applications. Just as USB-C provides a standardized way to connect electronic devices, MCP provides a standardized way to connect AI applications to external systems.

![](https://pica.zhimg.com/v2-063996debfb44abe1dbbb2b22b87e958_r.jpg)
*MCP的核心在于接口的“统一化”、“标准化”，就像一个万能转接头一样*

**MCP 不是让 AI 能调用工具的技术。** 自动调用工具的方式叫做tool call/function call，这个早就存在了，各种 Agent 框架都能做。所以 MCP 不是让 AI 能调用工具，而是 **让工具能在不同 AI 应用之间即插即用** 。

按照官方的文档做一个类比，那就是每个手机早就能充电了，MCP 不是发明了充电，而是统一了充电口。

**（2）MCP和tool call有什么区别呢？**

很多人会把 MCP 和 Function Call 搞混，觉得它们是竞争关系。但其实不然。实际上它们是合作关系，各负责任务的一半。

当 AI 要使用外部工具时，整个过程分为两个阶段：

- 阶段1: 模型决定要调什么工具、传什么参数（Function Call）
- 阶段2: 实际去找到工具、执行工具、拿回结果（MCP）

假如用户的问题是："苹果公司现在股价多少？"，那么模型会把这句自然语言翻译成一条结构化的指令：

```text
"调用 `get_current_stock_price` 这个函数，参数是 `company=Apple Inc., format=USD`"
```

但Function Call 有一个核心问题：平台绑定。也就是说 **每家 AI 厂商输出这条指令的格式都不一样** 。

比如OpenAI 的格式是这样的：

```text
{
  "tool_calls": [{
    "name": "get_current_stock_price",
    "arguments": "{\"company\": \"Apple Inc.\", \"format\": \"USD\"}"
  }]
}
```

Anthropic 的格式是这样的：

```text
{
  "type": "tool_use",
  "name": "get_current_stock_price",
  "input": {"company": "Apple Inc.", "format": "USD"}
}
```

Gemini 的格式又是这样的：

```text
{
  "functionCall": {
    "name": "get_current_stock_price",
    "args": {"company": "Apple Inc.", "format": "USD"}
  }
}
```

虽然查询股价这个核心的函数get_current_stock_price的实现逻辑是一样的，但是怎么把它接到 AI 上呢？这部分每个平台的格式完全不同。比如，如果我们想把它接到OpenAI上，就得按 OpenAI 的格式描述工具，之后再按照OpenAI 的格式解析 tool_call、按 OpenAI 的格式把结果传回去。假如我们想在Claude Code中使用，就又得按Anthropic格式再配一遍。

为了解决这个问题，MCP定义了一套 **统一的格式** ：

```text
{
  "jsonrpc": "2.0",
  "method": "tools/call",
  "params": {
    "name": "get_current_stock_price",
    "arguments": {"company": "Apple Inc.", "format": "USD"}
  }
}
```

不管前面是 OpenAI、Claude 还是 Gemini 发出的指令，Host 应用（比如Claude Desktop、VS Code）会把各家不同的格式统一转换成 MCP的这个统一标准化格式，然后发给 MCP Server 执行，MCP Server只认 MCP 格式。也就是将数据连接到模型的这个环节更加统一化了。

模型并会不直接生成 MCP 格式，它们只会说自家的"方言"（比如OpenAI 有 OpenAI 的格式，Claude 有 Anthropic的格式），是 Host 应用在中间当翻译官，把各家方言统一翻译成 MCP 格式。这层翻译对我们普通开发者来说完全不可见，不管是写 MCP Server 的人还是用工具的人，都不需要关心它。只有做 Claude Desktop、Cursor 这种 Host 应用的开发团队需要处理翻译逻辑。

下面流程的示例：

```text
用户问题: "北京今天天气怎么样？"
        ↓
模型（Phase 1 - Function Call）:
  "我要调用 maps_weather(city='北京')"
   输出的是每个框架独有的格式，比如Claude会输出：{"type": "tool_use", "name": "maps_weather", "input": {"city": "北京"}}
        ↓
Host 应用（Claude Desktop / Cursor / ChatGPT）:
   把模型特有的格式翻译成 MCP 标准格式：{"jsonrpc": "2.0", "method": "tools/call", \
        "params": {"name": "maps_weather", "arguments": {"city": "北京"}}}
        ↓
MCP Server（Phase 2 - 标准化执行）:
    收到 MCP 格式请求后便调用函数体，其中调用高德天气 API，返回结果
        ↓
Host 应用:
     把结果翻译回模型能理解的格式，传给模型
        ↓
模型:
     "北京今天晴，气温 28°C，适合出行。"
```

所以总结来说， Function Call 是模型的能力，模型能够理解自然语言并决定调什么工具；而MCP 是一个统一的标准，设计了工具怎么被调用、返回结果。

**（3）基本概念：Host，Client，与MCP Server**

MCP 的架构有三个角色： **Host、Client、Server** 。其实作为普通用户，我们只需要关心 MCP Server，Host 和 Client 都是现成的。但理解它们的关系有助于我们理解整个系统怎么运转。

- **Host** 就是你直接使用的 AI 应用，比如Claude Desktop、VS Code、ChatGPT Desktop。
- **MCP Server** 是提供具体能力的小程序，就是我们在后面会介绍的 `.py` 或 `.js` 文件，它包装了某个具体的功能（比如查询高德地图、查询数据库）。现在的社区开源了 2500+ 个 MCP Server，就指的是这些小程序。当然，你也可以自己写一些MCP Server。
- **Client** 是Host 内部的连接组件（这是最容易困惑的一个概念）。Client是Host 内部的一段代码，负责跟对应的Server通信。每连一个 Server，Host就创建一个 Client 对象来维护这个连接。如果你配了 3 个 MCP Server（高德、GitHub、数据库），Host 内部就会有 3 个 Client，分别跟 3 个 Server 一对一通信。但其实你完全不需要关心 Client，它是 Host 自动创建和管理的，你既看不到它，也不需要配置它。

![](https://pic4.zhimg.com/v2-7d6a10e0ec6d8fafff5173caadd5e7af_r.jpg)
*这种架构设计使得AI框架可以在不同场景下灵活调用各种工具和数据源，而开发者只需专注于开发对应的 MCP Server，无需关心 Host 和 Client 的实现细节。*

**（4）MCP如何实现？模型怎么知道该调用哪个MCP？**

Host 会在 system prompt 中塞入所有可用工具的描述。我们拿一个真实的开源项目 [https://github.com/sugarforever/amap-mcp-server](https://github.com/sugarforever/amap-mcp-server) 举例来看整个过程。这是一个高德的MCP Server，它的源码节选如下：

```text
from mcp.server.fastmcp import FastMCP
mcp = FastMCP("amap-maps")

@mcp.tool()
def maps_geo(address: str, city: Optional[str] = None) -> Dict[str, Any]:
    """将详细的结构化地址转换为经纬度坐标。支持对地标性名胜景区、建筑物名称解析为经纬度坐>标"""
    # ... 调用高德 API 的代码 ...

@mcp.tool()
def maps_weather(city: str) -> Dict[str, Any]:
    """根据城市名称或者标准adcode查询指定城市的天气"""
    # ... 调用高德 API 的代码 ...

@mcp.tool()
def maps_bicycling_by_address(origin_address: str, destination_address: str, ...) -> Dict[str, Any]:
    """Plans a bicycle route between two locations using addresses."""
    # ... 调用高德 API 的代码 ...
```
```

**那些 docstring就是未来模型会看到的工具描述。**

当 Claude Desktop/Claude Code 启动这个 Server 后，相关信息会被整合起来发给大模型，大致相当于在 system prompt 中塞入了类似下面这样的工具描述：

```text
你有以下工具可以使用：

工具: maps_geo
描述: 将详细的结构化地址转换为经纬度坐标。支持对地标性名胜景区、建筑物名称解析为经纬度坐标
参数:
  - address (string, required): 地址
  - city (string, optional): 城市

工具: maps_weather
描述: 根据城市名称或者标准adcode查询指定城市的天气
参数:
  - city (string, required): 城市名称

工具: maps_bicycling_by_address
描述: Plans a bicycle route between two locations using addresses.
参数:
  - origin_address (string, required): Starting point address
  - destination_address (string, required): Ending point address
  ...

如果需要用工具，输出对应的 tool_use 格式。如果不需要，直接回答。
```

所以当用户问"北京今天天气怎么样"时，Claude 看到 maps_weather 的描述是"查询指定城市的天气"，就会选择调用它。

**这意味着，工具的描述（docstring）写得好不好，直接影响模型能不能正确地选择工具** 。

## 0x03. 如何使用MCP工具

**（1）如何使用现有的 MCP Server？**

不管 Server 做什么，接入方式都是同一个套路，即编辑 `claude_desktop_config.json` ：

```text
{
  "mcpServers": {
    "amap": {
      "command": "uv",
      "args": ["--directory", "/path/to/amap_project", "run", "amap_server.py"],
      "env": { "AMAP_KEY": "xxx" }
    },
    "database": {
      "command": "uv",
      "args": ["--directory", "/path/to/db_project", "run", "db_server.py"]
    },
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": { "GITHUB_PERSONAL_ACCESS_TOKEN": "xxx" }
    },
"web_reader": {
      "command": "python",
      "args": ["/path/to/web_reader.py"]
    }
  }
}
```

这个配置文件告诉AI应用怎么启动每个 MCP Server，这个格式可能看起来有些奇怪。下面举两个例子：

```json
 "amap": {
    "command": "uv",                                          // 用 uv 这个 Python 包管理器来运行
    "args": ["--directory", "/path/to/amap_project",          // 进入项目目录
             "run", "amap_server.py"],                        // 运行 amap_server.py
    "env": { "AMAP_KEY": "xxx" }                              // 把高德 API 密钥作为环境变量传进去
  }
```

就等价于在终端执行： `cd /path/to/amap_project && AMAP_KEY=xxx uv run amap_server.py`

> uv是一个用 Rust 编写的超快速 (100x) Python 包管理器和环境管理工具，定位为 pip 和 venv 的替代品。

而形如这样的配置：

```json
"github": {
    "command": "npx",                                         // 用 npx（Node.js 的包运行工具）
    "args": ["-y", "@modelcontextprotocol/server-github"],    // 自动下载并运行官方 GitHub Server
    "env": { "GITHUB_PERSONAL_ACCESS_TOKEN": "xxx" }          // GitHub 个人访问令牌
  }
```

npx -y 会自动从 npm 下载别人写好的 `@modelcontextprotocol/server-github` 包并运行。

目前社区已有 2500+ 个 MCP Server，覆盖你能想到的几乎所有领域：

- 官方 Server 列表 [https://github.com/modelcontextprotocol/servers](https://github.com/modelcontextprotocol/servers)
- 社区精选列表 [https://github.com/punkpeye/awesome-mcp-servers](https://github.com/punkpeye/awesome-mcp-servers)
- MCP Server 市场 [https://mcpservers.org](https://mcpservers.org/)

MCP也获得了主流 AI 厂商的支持，比如Anthropic的Claude Desktop、Claude Code、 Claude.ai ；OpenAI的ChatGPT Desktop、Agents SDK。

**（2）如何开发一个MCP Server**

开发一个 MCP Server，只需要把你的 Python/TypeScript 函数用 MCP SDK 包装起来。只要你能写一个函数完成这件事，那么它就能变成 MCP Server。

就像下面这样：

```python
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("我的工具名")

@mcp.tool()
def my_function(param1: str, param2: int) -> str:
    """这里的 docstring 会自动变成工具描述，AI 靠它来理解这个工具能干什么。"""
    # 你的业务逻辑
    return "结果"

if __name__ == "__main__":
    mcp.run()
```

就是这么简单。@mcp.tool() 装饰器会把把函数注册为 MCP 工具，

- 函数名自动变成工具名；
- docstring 自动变成工具描述；
- 参数的类型注解自动变成参数 schema
- 返回值自动作为工具执行结果传回给模型

## 0x04. 把整个流程串起来

为了能够更好地了解整个过程，我们以一个简单的case为例，看一下整个流程是如何工作的。

用户在 Claude Desktop 中问：【帮我搜一下上海有什么好吃的火锅店】，而且用户配置了【高德地图 MCP Server】。

- **step1: 启动阶段（用户打开 Claude Desktop 时）**

Claude Desktop 读取 config.json，并发现配置了 "amap" server，于是启动子进程: uv run amap_server.py

Client和Server 握手，Server告诉它：“我有 search_place, get_driving_route, geocode 三个工具"，于是Client记住了这些工具的名字和描述。

- **step2: 用户输入问题：** "帮我搜一下上海有什么好吃的火锅店“
- **step3：Host构造请求发给模型**

Claude Desktop 把以下内容打包发给 Claude API:

```text
System: 你有以下工具可用: 
    工具: search_place
    描述: Search for places like restaurants, hotels, attractions using Amap (高德地图). 
    Use this when the user asks 'where is ...', 'find ... near me', or wants location info.
    参数: 
       - keyword (string, required): What to search
       - city (string, optional): City name, default '北京'

    工具: get_driving_route
    描述: Get driving directions between two locations......
    
    工具: geocode
    描述: Convert a text address to coordinates......

User: "帮我搜一下上海有什么好吃的火锅店" 
```

- **step4. Claude 模型做出判断**

Claude 读懂了工具描述 + 用户问题，判断应该用 `search_place` 工具。于是输出了结构化的 Anthropic tool call 格式:

```json
{
    "type": "tool_use",
    "id": "toolu_01A09q90qw90lq917835lq9",
    "name": "search_place",
    "input": {
      "keyword": "火锅",
      "city": "上海"
    }
  }
```

- **step5: Host 做协议转换，Client 执行工具调用**

Claude Desktop 收到 tool call之后，翻译成 MCP 格式发给 amap server：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "search_place",
    "arguments": {"keyword": "火锅", "city": "上海"}
  }
}
```

于是， `amap_server.py` 中的 `search_place()` 函数被执行，其内部调用了高德 API，并最终返回结果：

```text
"在上海搜索'火锅'的结果:
 - 海底捞火锅(南京东路店) | 地址: 黄浦区南京东路... | 电话: 021-xxxx
 - 小龙坎火锅(徐家汇店) | 地址: 徐汇区... | 电话: 021-xxxx
 - 巴奴毛肚火锅(静安店) | 地址: 静安区... | 电话: 021-xxxx
 - 凑凑火锅(环球港店) | 地址: 普陀区... | 电话: 021-xxxx
 - 哥老官火锅(人民广场店) | 地址: 黄浦区... | 电话: 021-xxxx"
```

这个结果被作为 tool_result 发送回 Claude API

- **step6: Claude 生成最终回复**

Claude 收到工具返回的原始数据，结合用户问题生成自然语言回复

## 0x03. "MCP is dead. Long live the CLI"

今年2月，开发者 Eric Holmes 发了一篇 [MCP is dead. Long live the CLI](https://ejholmes.github.io/2026/02/28/mcp-is-dead-long-live-the-cli.html) 引发了热烈的讨论；两周后，Perplexity CTO *Denis Yarats* 宣布 Perplexity 内部正在弃用 MCP，回归CLI，理由是 MCP 工具定义占掉了 72%的上下文窗口 ( [https://milvus.io/blog/is-mcp-dead-cli-and-skills-for-ai-agents.md](https://milvus.io/blog/is-mcp-dead-cli-and-skills-for-ai-agents.md) )；同一天，Garry Tan 在 X 上发了那条著名的推文——"MCP sucks honestly"( [https://x.com/garrytan/status/2031910564344262988](https://x.com/garrytan/status/2031910564344262988) )

所以在本节，我们会通过两个角度来介绍MCP具有的问题。

**（1）问题1. MCP的token消耗过大**

**(a) 工具定义token占用**

Quandri 做过一组真实的测量 ( [https://medium.com/@joe.njenga/claude-code-just-cut-mcp-context-bloat-by-46-9-51k-tokens-down-to-8-5k-with-new-tool-search-ddf9e905f734](https://medium.com/@joe.njenga/claude-code-just-cut-mcp-context-bloat-by-46-9-51k-tokens-down-to-8-5k-with-new-tool-search-ddf9e905f734) )：同时连接四个 MCP Server，光是加载工具定义schema 就吃掉了 21000 tokens，占了Claude Code 200K上下文的 10.5%。

比如说，GitHub MCP Server 有 43 个工具，但是我们查一个 PR 只需要get_pull_request这一个。可是每次调用的时候，另外 42个的完整参数定义也会一起发送。相比之下，CLI 只需要一个 Bash 工具定义，不管你要调 git、docker 还是curl，schema 都是同一个。

我们在之前在介绍agent的上下文管理的时候介绍过所谓的"context rot"现象，即当模型面对的上下文变得非常长时，模型会遇到效果的下降。所以，随着工具数量增加，模型的工具选择准确率可能反而会降低。

**(b) 工具返回堆积**

LLM的对话历史是一个不断增长的消息列表，每一轮的 tool_result 永远留在对话历史里，后续每次 API 调用都要带上。MCP返回的是原始 API JSON，包括嵌套对象、元数据字段、分页信息，这个的长度是很长的：

```text
  [system prompt + 工具定义]
  [user: 帮我查PR 123]
  [assistant: 调用 get_pull_request]
  [tool_result: {完整JSON响应, ~800 tokens}]     ← 留在历史里
  [assistant: PR 123 是关于...]
  [user: 再查一下它的 diff]
  [assistant: 调用 get_pull_request_diff]
  [tool_result: {完整diff JSON, ~2000 tokens}]   ← 也留在历史里
  [assistant: diff 显示...]
```

就像滚雪球似的，10 轮对话下来，MCP 的历史消息可能累积了上万 tokens 的 JSON；CLI 则可能只有几百tokens 的命令行输出。

**(c) 缺乏上下文管理**

之前我们在介绍agent上下文管理的时候，介绍过很多降低上下文占用的方式。戳这里复习：

[万字长文解析Agent框架中的上下文管理策略](https://zhuanlan.zhihu.com/p/2012088406826562496)

其中有一个重要的方式就是上下文卸载与检索（Context Offload & Retrieval），即将信息转移到文件系统中。因为上下文窗口是有限的，所以我们不能将所有信息都塞进 Agent 的短期记忆（上下文窗口）中，而应将其“卸载”到外部存储，并在需要时精确检索。

这是因为文件系统天然具有无限容量、持久化、可随机访问的特性，Agent 可以像人类一样通过路径、文件名、时间戳等元数据来组织信息。最关键的是，这样的压缩策略是 **可逆的** 。例如：

- 当 Agent 访问一个网页时，只要保留 URL，就可以将网页内容从上下文中移除。后续需要时，Agent 可以重新请求该 URL。
- 当处理文档时，只要保留文件路径，就可以省略文档内容，需要时再用 `cat` 或 `tail` 读取。
- 在日志中，完整的输出content可以被移除，只保留一个path路径。

这种“可逆压缩”确保上下文长度缩减的同时，信息并未真正丢失——它们只是被卸载到文件系统中了，随时可以重新加载进来。

**相比之下，MCP就没有这么好的特性了。** 还是以 Agent 访问网页为例，不管你需不需要看页面的全部状态，请求之后它都会把这整个网页都塞进对话历史。接下来每一轮 API调用，这条消息都会被重新发送。假如说我们后续又对这个网页做了一些修改，之后又去请求，反复N次；这样，N步操作之后，对话历史里堆着N份完整快照，每份都有上千 tokens，共计就是可能上万token的页面状态。而且这N份之间可能 90% 内容相同（页面只是多了个弹窗或换了个表单值），造成了很大的浪费。

**（2）CLI更加贴近LLM的训练语料分布**

> "CLIs are the de-facto MCPs for agents"

我们在训练LLM的训练时，其训练语料包含了海量代码文本比如Stack Overflow、GitHub repo、终端交互记录等等。而CLI的书写方式恰恰贴近这些自然的代码语料，这就好比LLM在用 **“母语”** 与我们沟通。当 Agent 需要执行一个 CLI 命令时，它在做一件训练数据里见过无数次的事。命令格式是熟悉的，输出格式是熟悉的，错误信息的含义也是熟悉的。相比于结构化的各种工具调用，模型更擅长的是直接输出CLI代码。

### 0x04. MCP已死...了吗？

对于那些已经拥有成熟 CLI 的开发者工具（如 git、docker、kubectl），直接调用命令行对模型而言更贴近预训练语料的分布，输出也更具可读性，对个人开发者非常友好。因此，不难理解为什么那些认为“MCP 已死”的人几乎都是 coding agent 的深度用户，在他们看来，MCP 增加了不必要的协议层和 token 开销，却没有带来收益。

但是，企业的痛点和个人开发者完全不同。在一些复杂的应用场景下，直接使用CLI会带来安全与治理的严重问题。比如，MCP 支持 OAuth 2.1 和细粒度的工具/Agent 权限划分，而不是让 Agent 直接拿着用户的全量凭证；MCP 可以提供集中的工具调用日志、网关控制和策略执行，直接调用则几乎无标准审计。而且在复杂的系统场景下，这些系统的 API各有各的认证流程、各有各的数据模型、各有各的分页方式。 这种场景下 MCP 的价值就出来了，它把这些异构系统的差异封装在一套统一的协议之下，让 Agent 可以用标准化的方式使用能力。

**此外，MCP 自己也在进化。** 比如Claude Code就引入了 Tool Search 机制( [https://www.anthropic.com/engineering/advanced-tool-use](https://www.anthropic.com/engineering/advanced-tool-use) )，MCP 工具 schema不再在会话开始时全量加载，而是按需发现、按需加载，token 开销降低了 85%-95%。

因此，MCP 在 2026 年并没有死，只是从炒作顶峰进入了“幻灭期”，而这恰恰是企业级使用真正开始的阶段。
