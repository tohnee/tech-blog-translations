PyTorch框架当前通信算子的输入输出Tensors的生命周期远远长于理论上最小的生命周期，从而造成训练/推理过程**峰值显存占用明显增加**！具体表现可参考如下链接。

[CUDA allocation lifetime for inputs to distributed.all_reduce](https://discuss.pytorch.org/t/cuda-allocation-lifetime-for-inputs-to-distributed-all-reduce/191573/4)

## 一、当前通信操作Record Streams的问题

当前PyTorch框架的NCCL通信操作通过Record Streams保证数据安全，会明显延长参与通信的Tensors的生命周期，接下来具体走读一下完整流程。

```text
// Both `inputs' and `outputs' are created on a worker stream and used in
// different ncclStreams.  Hence, both must record the ncclStream to
// prevent being freed before the collective finishes.
CUDACachingAllocator::recordStream(inputs[i].storage().data_ptr(), ncclStream);
```

RecordStream操作会将Tensor Storage的block同stream关联起来，stream_uses记录当前block被哪些streams使用。

```text
void recordStream(const DataPtr& ptr, cuda::CUDAStream stream) override {
    ...

    Block* block = get_allocated_block(ptr.get());
    // block must not be null reaching here
    TORCH_INTERNAL_ASSERT(block != nullptr, "No allocated block can be found");
    device_allocator[block->device]->recordStream(block, stream);
}
void recordStream(Block* block, cuda::CUDAStream stream) {
    std::lock_guard<std::recursive_mutex> lock(mutex);
    if (stream.stream() == block->stream) {
      // ignore uses on the allocation stream, since those don't require any
      // special synchronization
      return;
    }
    block->stream_uses.insert(stream);
}
```

既然已经record streams，那接下来Tensor析构释放对应block的时候，如果发现当前block被多个streams使用，那就下发Event到对应的Streams，即调用insert_events函数插入events，对应的block并不会真正释放。

```text
void free(Block* block) {
    ...

    if (!block->stream_uses.empty()) {
      if (C10_UNLIKELY(captures_underway)) {
        ...
      } else {
        insert_events(block);
      }
    } else {
      free_block(block, context);
    }
}
```

接下来可以看到不同的streams会插入对应的cuda events，如果对应stream执行到events节点，那就标识当前block是可以释放的了，这样可以保证Tensor释放绝对安全，因为当前时间点之前的stream task全部执行完。

**问题：当前时间点已经滞后，这段时间可能下发了其他的task，明显延长了block的生命周期。如果当前/其他stream继续下发kernel task，就算当前nccl task结束（仍然需要对应events节点完成才能标记available），也不能跨stream共享当前block。**

```text
void insert_events(Block* block) {
    ...

    stream_set streams(std::move(block->stream_uses));
    AT_ASSERT(block->stream_uses.empty());
    for (auto& stream : streams) {
      C10_CUDA_CHECK(c10::cuda::SetDevice(stream.device_index()));

      EventPool::Event event =
          create_event_internal(static_cast<int>(stream.device_index()));
      C10_CUDA_CHECK(cudaEventRecord(*event, stream.stream()));

      block->event_count++;
      cuda_events[stream].emplace_back(std::move(event), block);
    }

    C10_CUDA_CHECK(c10::cuda::MaybeSetDevice(prev_device));
}
```

然后就是每次free block时轮询所有的events了，其中每个stream对应一个events list，防止其中某些stream存在long-running operations，进一步阻止Tensor block释放。每个events list按顺序轮询。

```text
void process_events(const std::shared_ptr<GatheredContext>& context) {
    insert_events_deferred_until_no_capture();

    // Process outstanding cudaEvents. Events that are completed are
    // removed from the queue, and the 'event_count' for the
    // corresponding allocation is decremented. We maintain a separate
    // list of events per stream to avoid head-of-line delays if one
    // or more streams has long-running operations.

    // Iterate over different streams.
    for (auto it = cuda_events.begin(); it != cuda_events.end();) {
      // Iterate over this stream's (event, block) pairs.
      while (!it->second.empty()) {
        auto& e = it->second.front();
        EventPool::Event event = std::move(e.first);
        Block* block = e.second;

        cudaError_t err = C10_CUDA_ERROR_HANDLED(cudaEventQuery(*event));
        if (err == cudaErrorNotReady) {
          // ignore and clear the error if not ready
          (void)cudaGetLastError();
          // Return the ownership of the Event (unique ptr)
          e.first = std::move(event);
          break;
        } else if (err != cudaSuccess) {
          C10_CUDA_CHECK(err);
        }

        block->event_count--;
        if (block->event_count == 0) {
          free_block(block, context);
        }
        it->second.pop_front();
      }

      if (it->second.empty()) {
        it = cuda_events.erase(it);
      } else {
        it++;
      }
    }
}
```

直到该block的所有events全部执行完成，这时候就能够满足该block的释放条件，才能够将对应的block释放回内存池，方便下一次复用。**显然已经晚了，黄花菜都凉了……**

```text
auto allocatable = [](Block* b) {
      return b && !b->allocated && b->event_count == 0 && b->stream_uses.empty();
};
```

## 二、Avoid Record Streams优化策略

很明显采用Record Streams并不是完美匹配Tensor的生命周期，前面标识的几个地方明显延长了Tensor对应block的生命周期，造成内存释放严重滞后，内存复用效果差，峰值内存占用高。<br>Avoid Record Streams采用了另外一种思路来完美匹配Tensor的生命周期，即当前nccl stream完成的时候即释放对应的Tensor block。<br>通过一个list来保存当前nccl通信操作对应的Tensors的引用，直到user-facing stream(s) are synced with the nccl work stream(s)。可以理解为在对应的计算stream显示或隐式调用wait函数，即保证当前nccl task完成。

```text
// Stores references to participating non-output tensors (ie inputs,
// flattened intermediates).
// We'll clear this list in synchronizeStreams, just after user-facing
// stream(s) are synced with the nccl work stream(s).
// By keeping these refs (as well as outputs_) alive until after the
// collective's work rejoins the user-facing streams, we achieve
// caching allocator safety without any recordStream calls.
// For in-place collectives, some refs stashed here may alias outputs_,
// but that doesn't do any harm.
std::shared_ptr<std::vector<at::Tensor>> stashed_for_allocator_safety_;
```

WorkNCCL::wait() or WorkNCCL::synchronize()操作都会执行到当前函数，使得当前nccl task的end events阻塞对应的计算stream，直到nccl task完成。其中每一个通信操作对应一个WorkNCCL实例。

```text
void ProcessGroupNCCL::WorkNCCL::synchronizeStreams() {
  for (const auto i : c10::irange(devices_.size())) {
    auto currentStream = at::cuda::getCurrentCUDAStream(devices_[i].index());
    // Block the current stream on the NCCL stream
    (*ncclEndEvents_)[i].block(currentStream);
  }

  if (avoidRecordStreams_) {
    stashed_for_allocator_safety_->clear();
  }
}
```

**上述操作通过环境变量TORCH_NCCL_AVOID_RECORD_STREAMS即可开启。**

## 三、终极优化方案设计

**首先感谢华为海思PyTorch总架构师的方案指导！！！**

[公瑾](https://www.zhihu.com/people/zhou-gong-jin-38-39)

对于我们常见的通信操作用法，对于同步通信我们就不再讨论了，所见即所得。通常在考虑计算/通信并行的时候会采用异步通信，这个也是目前LLM训练框架使用最多的姿势。

```text
comm_handle = torch.distributed.all_reduce(data, group=xxx, async_op=True)
...  # 省略若干代码
comm_handle.wait()
```

考虑两种情况：

1. **如果通信在wait之前完成，即在overlap的计算流程中已经完成了通信**
2. **如果计算较快，wait的时候通信还没有完成，即wait需要阻塞一会**

如果完全采用Avoid Record Streams优化策略，那么对于第一种情况，并不会提前释放对应参与通信的Tensors，因为所有的引用都需要在synchronize/wait的时候清空，这个时候Tensors的生命周期就不太合理，**优化还是不到位！！！**。

如果完全采用record streams方案，那么虽然对于第一种情况会提前运行完所有的record events节点，完成Tensors释放。但是对于大部分情况还是如同第一章节分析的那样拉胯。

**既然上述方案都不行，那么终极方案该怎么设计呢？接下来我简单的描述一下。**

一言以蔽之，record streams和stash reference同时存在，哪个先完成就哪个生效。如果是record streams生效很简单，那就是所有插入的events节点执行完成，内存池轮询即可，但是对于input/output Tensors的引用需要采用weak ptr，不然还是无法释放；如果是运行到wait/synchronize，那就是stash reference生效，我们需要主动清空Tensors block对应的streams和events，保证内存的及时释放。最后，简单放一下erase Stream示例实现。

```text
void eraseStream(Block* block, Stream stream) {
    std::lock_guard<std::recursive_mutex> lock(mutex);
    block->stream_uses.erase(stream);

    // free block, lazy destory block related events
    for (auto it = events.begin(); it != events.end();) {
      if (block != (*it).second) {
        it++;
        continue;
      }
      Event event = (*it).first;
      LazyDestroy(event);
      events.erase(it);
      block->event_count--;
      if (block->event_count == 0) {
        free_block(block);
        break;
      }      
    }
}
```
