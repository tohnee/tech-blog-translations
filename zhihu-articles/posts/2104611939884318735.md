今天的问题（面试题）：7B 模型开了投机解码，单请求延迟从 40ms/token 降到 15ms/token。但线上 QPS 一上来，集群吞吐反而比不开时低 15%，P99 变差。为什么？

一句话回答：投机解码赚的是闲置算力，只在解码受显存带宽限制时成立；batch 一大，解码转成算力受限，多验证的 token 就成了纯开销。

它赚的是什么

自回归解码每步只出 1 个 token，却要读一遍全部权重：7B BF16 约 14GB，3TB/s 带宽读一次约 4.7ms，这期间算力几乎闲置。投机解码用闲置算力换显存流量——草稿模型猜 γ 个 token，目标模型一次前向并行验证 γ+1 个，拒绝采样保证输出分布不变。

收益只有一条公式：speedup = Ω × T_T / (γ·T_D + T_V(γ))，Ω = (1−α^(γ+1))/(1−α)。分子被接受率封顶，分母由验证成本决定。

为什么 batch 一大就失效

关键在 T_V(γ) 随 batch 的增长。设单序列 KV 读取 k、每 token 算力 c、权重读取 t_w，验证从带宽受限翻成算力受限的临界 batch 是 B* ≈ t_w / ((γ+1)·c − k)。以 27B 稠密模型、H100、2k 上下文估算：γ=3 时 B*≈85，γ=7 时只有 30。越线之后，多验证一个 token 不再免费。

更糟的是 Ω 随 γ 饱和：接受率沿位置衰减，第一位 94% 不代表第七位还有 94%。分子封顶、分母线性涨，加速比必然塌陷。Agent Spec 实测：agent 场景 batch 超 32 后，投机解码慢于自回归。

三种常见错误回答

· "草稿模型算力成瓶颈。" 只对一半：它只占 4% 参数，真正瓶颈是目标模型的验证阶段。

· "接受率降低了。" 接受率与 batch 基本无关，取决于草稿模型匹配度、任务类型和位置衰减。

· "调小 γ 就行。" 方向对，但 γ 要按并发调，写死 num_speculative_tokens 是错配。

好回答的四层

· 机制：讲清 memory-bound 到 compute-bound 的翻转，给出 B* 的直觉。

· 公式：三因子拆开，指出验证成本比随 batch 恶化。

· 数据：1–32 并发 3.3 倍、128 并发 1.5 倍、256 并发 1.16 倍，曲线是塌的不是断的。

· 工程：按 p95 并发选 γ 让 B* 高于峰值；高低并发分流或动态缩 γ；用 vllm bench serve 并发扫描，读 vllm:spec_decode 按位置算条件接受率。

加分反问

追问"长上下文呢"，答"不一样"：序列够长时 KV 读取随 batch 线性涨，验证重回带宽受限，收益反随 batch 上升。MagicDec 据此翻案：LLaMA-3.1-8B 在 batch 32–256 仍有 1.84 倍。判据是是否越过 S_inflection，由硬件 FLOPS/带宽比与 GQA 结构决定。
