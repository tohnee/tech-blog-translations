随着模型的演进，KV cache从去年的GQA/MLA，发展到今年的滑窗、稀疏/压缩等多种类型。本文以**DeepSeek V4.1-Flash**为基础，分析其KV cache结构、各类KV cache的特征与体积算法，以及考虑如何构建prefix cache。

## 1 模型整体结构

在分析模型的KV cache之前，先了解一下模型的基本结构，知道哪些层有KV cache，以及存些什么内容。V4.1-Flash采用栈式Transformer结构，通过`compress_ratios`和`kv_source_layers`将层划分为滑窗、压缩稀疏、YoCo consumer三类，再外挂Engram与DFlash。 主干40层，另有3层DFlash（`n_mtp_layers=3`）。 3D结构[^1]：

![](https://pic3.zhimg.com/v2-c1682f31aaba16825d95bcee5993bac8_r.jpg)
*​https://calvinxky.github.io/InfraTech/3d_models/*

关键配置：

| 项 | 值 |
| --- | --- |
| n_layers | 40 |
| compress_ratios | L0–1为0；L2–19为2；L20–39为1；DFlash侧为0 |
| kv_source_layers | 2, 8, 14, 20 |
| index_source_layers | 2, 8, 14, 20, 24, 28, 32, 36 |
| window_size / sliding_window | 128 |
| n_prefill_layer | 第一个ratio==1的层，即20 |
| head_dim / rope_head_dim | 512 / 64，故kv_lora_rank=448 |

注：

- `compress_ratio > 0`并不等同于本层自行压缩KV；只有`kv_source_layers`写入压缩cache，其余层读取同一份。
- Prefill整段prompt时，前半截（encoder）要算全；后半截consumer层不必对整段prompt的每个位置都算一遍，只保留/只算末尾一小段就够。举例，设prompt长度`L=4096`，开启截断后保留末尾约`KEEP=140` ，Consumer侧只处理末尾 3956..4095 这一截（约140个token）。
- prefill的截断配置：DEEPINFER_YOCO_PREFILL_TRUNCATION_MODE（mask / compact），保留末尾约140 token。`mask`模式：query还在，但SWA可见域被收窄到末尾矩形；`compact`模式：直接把截断区的query拿掉，consumer少算那些位置。

## 2 层类型与KV cache关系

### 2.1 分类

按compress_ratio划分的三类注意力层：

| 类型 | 层号 | 特征 |
| --- | --- | --- |
| 纯滑窗; | L0–L1，以及DFlash层 | 只维护window_kv_cache；无compress_kv_cache |
| 压缩稀疏（Encoder侧） | L2–L19 | 滑窗 + 压缩轴上的全局稀疏注意力； |
| YoCo consumer; | L20–L39 | 从n_prefill_layer=20起；主KV多共享/投影；Prefill可截断；consumer SWA默认不存盘 |

### 2.2 KV源层与Indexer源层

KV cache的生产者（不考虑SWA）：

```text
kv_source_layers:    2, 8, 14, 20
index_source_layers: 2, 8, 14, 20, 24, 28, 32, 36
```

层间通过`SharedAttentionRuntime`传递：

- 源层写入`compress_kv`、`index_k`、`topk_idxs`
- 后续非源层直接读取这些槽位
- 按层号顺序执行，消费者读到的是上一个源刚发布的内容

**举例：第3层**

- `compress_ratio=2`，但并非kv/index源
- 压缩主KV读取第2层写好的`compress_kv`
- topk下标读取第2层发布的`topk_idxs`
- 本层仍有自己的`window_kv_cache`

```text
L2（源）写 compress_kv_cache + indexer
L3（非源）读 shared_attn.compress_kv / topk_idxs
L3 同时写自己的 window_kv_cache
L3 用本层Q对 [本层SWA | L2压缩KV] 做 sparse_attn
```

L4–L7同样挂在L2上；到L8再开一份新的压缩主KV，依此类推。

相关代码可以参考[^3]：[inference/model.py](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash/tree/main/inference)

**举例：24层**

再看L24，这是另一类典型层：在`index_source_layers`里，但不在`kv_source_layers`里。将这种层称为**Reindex层**（24/28/32/36同型）。

L24的配置：

- `compress_ratios[24] = 1`，已进入YoCo consumer半区（`n_prefill_layer=20`）
- `is_index_source = True`：本层会运行Indexer，重新计算topk
- `is_kv_source = False`：**不写本层的**`compress_kv_cache`
- Indexer中`owns_k = (layer_id in kv_source_layers)`，L24为False。 表示直接读取共享槽里已有的index K

L24的数据来源概括为：

```text
压缩主KV（compress_kv）  ← 读 L20（最近的kv_source）
Indexer 的 K（index_k）   ← 也读 L20 发布的那份（owns_k=False）
topk 下标                  ← 本层自己算一遍（is_index_source=True）
本层 SWA                   ← 本层自己的 window_kv_cache
候选块约束（若开启）       ← L20 是 candidate_source_layer，L24 在其候选块内重打分
```

对应逻辑对比：

```text
L20（既是kv源，也是index源，还是candidate源）
  写 compress_kv_cache
  写 index_k，并发布 candidates

L24（仅index源 / Reindex）
  不压缩、不写主KV
  用本层Q与weights，对 L20 的 index_k 重新打分
  可先被 L20 的 candidate blocks 收窄，再取本层 top-512
  发布新的 shared_attn.topk_idxs 给后面的非index源层用
  注意力读的压缩KV仍是 L20 那份 compress_kv
```

因此L24需要自己算一次index（即对本层query重新打分并选出topk），但压缩主KV从L20取。Indexer用来打分的K向量也来自L20。

和L3对比：

|  | L3 | L24 |
| --- | --- | --- |
| 是否kv源 | 否 | 否 |
| 是否index源 | 否 | 是 |
| 压缩主KV | 读L2 | 读L20 |
| topk谁算 | 直接复用L2的topk_idxs | 本层重算并发布 |
| 所在半区 | Encoder，ratio=2 | Consumer，ratio=1 |

**其它结构**

在模型中还有其它结构，但不涉及KV cache，如下：

- Engram：在L1、L14将n-gram检索结果注入残差。
- DFlash：读取L37–L39特征，生成最多若干draft token，并附带confidence；服务于投机解码。
- Hyper-Connection（HC）：残差流多副本混合，影响隐状态布局。

## 3 KV Cache类型

**内容分类：**

| 名称 | 代码里常见字段 | 特征 |
| --- | --- | --- |
| 滑窗KV | window_kv_cache / swa_cache | 定长窗口（128+回退余量）；每层可自有；随生成滑动 |
| 压缩主KV | compress_kv_cache / ca_cache | 仅kv源层写入；长度≈seq_len/compress_ratio；分页、可远端存 |
| Indexer K | index_k / ica_cache | 压缩轴上与主KV对齐；用于挑选top-k；可层间共享 |
| 压缩边界状态 | kv_state/score_state 或 ca_state/ica_state | 很短的ring；服务于”正在压缩、尚未收成完整entry”的边界；不存入3FS |

*原图：https://github.com/CalvinXKY/InfraTech/blob/main/models/deepseek_v4/deepseek_v4_architecture.jpg*

![](https://pic2.zhimg.com/v2-26e1ff263f6632aff7930371269a3357_r.jpg)

在**DeepInfer**[^4]中，KV cache的存放位置：

| 内容 | 介质 | 管理者 |
| --- | --- | --- |
| Block KV + state | 推理GPU显存 | Prefill/Decode实例 |
| SWA（保留部分） | 产出机本机内存 | 实例 + Entrypoint目录；跨机经400G VLAN回拉 |
| 分页Block KV（主KV+indexer） | 独立3FS集群 | kvcache-store |

设计上分开的原因：Block KV需要长大、共享、长留，适合进共享存储，这样任意Prefill都能命中任意前缀，路由不必绑定前缀亲和；SWA只需接缝附近一份定长窗口，留在本机。

**State槽物理布局**

单条序列一个`StateBlock`，从低地址到高地址：

```text
[stored region: 需落盘的SWA，V4.1约前20层]
[dropped region: YoCo consumer SWA | compression state]
```

跨请求to-disk只取stored区（`state_size_to_disk`）。consumer SWA与compression state靠重算或短生命周期拷贝，不进3FS主前缀。

## 4 KV cache的大小与增长

### 4.1 计算方式

以下按Flash配置与DeepInfer布局公式。

**每token占用大小：**

| 内容 | 公式口径 | Flash量级 |
| --- | --- | --- |
| 压缩主KV | FP4，每16通道一个E4M3 scale；向量维512 | 288 B / compressed-token |
| SWA | MXFP8：512B data + 16B scale | 528 B / window-token |
| Indexer K | index_head_dim=128：dim/2 + dim/32 | 68 B / compressed-token |

注意：在模型描述中“全局KV footprint约890 B/token”，是共享源层+压缩+低精度后的整模估算。

**单层计算：**

设当前序列逻辑长度为`L`（prompt+已生成），窗口推理槽为`W`（常见约`128 + backtrack`，示例134）。

纯SWA层（ratio=0）：

```text
swa_bytes ≈ W × 528
无分页主KV
```

KV源层（如L2，ratio=2）：

```text
compressed_len = floor(L / 2)          # 或引擎按块对齐后的等价长度
main_kv_bytes  ≈ compressed_len × 288
index_k_bytes  ≈ compressed_len × 68   # 若本层拥有indexer K
swa_bytes      ≈ W × 528               # 若该层启用SWA
```

非源压缩层（如L3）：

```text
不新增 main_kv / index_k 容量（读取共享源）
仍可能有本层 swa_bytes ≈ W × 528
```

**跨请求存3FS的SWA总量：**

```text
state_size_to_disk
  = 20 层 × 134 token × 528 B
  = 1,415,040 B
  ≈ 1.35 MB / 序列
```

只含前20层stored SWA；consumer SWA与compression state不计入。

**压缩状态:**

DeepInfer中`ratio>1`需要compression state；ring长度约为：

```text
ring = compress_ratio + max(0, MAX_BACKTRACKING_TOKENS - 1)
bytes = ring × 2 × dim × sizeof(fp32)
```

这是短ring，量级远小于分页主KV，且留在dropped区。

### 4.2 Prefill / Decode时KV变化

分析单次请求在GPU上的增长。

**Prefill:**

- step 1：prompt（可chunk）从Embedding进入整栈。
- step 2：L0–L1写各自SWA窗口。
- step 3：遇到kv源层（2/8/14/20）时，Compressor按`compress_ratio`把连续token收成latent，写入该层`compress_kv_cache`，并发布到`shared_attn`。
- step 4：同为index源的层跑Indexer，发布`topk_idxs`（及可能的`index_k`）。
- step 5：非源层读取共享压缩KV与topk，再结合本层SWA做注意力。
- step 6：进入L20后的consumer；Prefill侧可对consumer做截断或末尾短重放；decoder侧block KV在CED叙述中可由encoder末层hidden投影，不必再为整段prompt堆一份同等长度的独立前缀盘。

**Decode:**

- step 1：只输入新生成的token（投机时可多个draft）。
- step 2：隐状态仍穿过L0..L39；不重喂整段prompt。
- step 3：各层为新位置追加/滑动KV：源层向压缩cache尾部追加compressed entry；SWA写入ring下一格并滑出最旧token。
- step 4：采样下一个token，重复。
- 逻辑长度：`L = P + 已生成`。物理上Block KV随`L`增长，SWA占用近似恒定。

## 5 Prefix Cache构建

生产环境中prefix cache的构建链路可以概括为：

- 推理阶段数据驻留在GPU；
- 在128 token粒度触发CPU offload与远端持久化；
- Entrypoint基于哈希链做前缀匹配；命中后异步回填，并与计算重叠完成HBM换入。

**写入时机与写入内容**

![](https://picx.zhimg.com/v2-8df37cee14611eb495e4828500dd3b65_r.jpg)

推理过程中，Prefill与Decode都在GPU上维护paged KV。Decode侧通常不会因显存不足触发KV cache offload，但为提高后续前缀命中率，Decode新生成的Block KV仍会写入远端存储。

SWA按128 token对齐做CPU offload，保留在产出该请求的节点主机内存中：

- Prefill：仅在最后一个chunk写入；附着点先在序列末尾预留1个token，再向下对齐到128；若不足一个完整128单元，则不存SWA。
- Decode：在设备侧维护replica缓冲，每当序列长度超过128，拷贝当前窗口；请求结束时取最近一次完整快照，附着点再次对齐到128。

Block KV（主KV与indexer）写入独立的3FS集群，由kvcache-store管理，供任意Prefill节点按前缀复用。因此路由层无需绑定前缀亲和，任意节点均可命中任意前缀。

**命中策略**

有效命中长度只能落在128对齐点上。在YoCo约束下，长度为`L`的输入最多约可命中`L−134`。

- step 1：Entrypoint作为CHECK角色访问kvcache-store，仅基于元数据做哈希链前缀匹配，得到Block KV命中长度`L1`（128的整数倍）。该步发生在路由之前，无法与后续计算重叠。
- step 2：检查`[L1−128, L1]`区间内是否存在可用的SWA快照。
- step 3：若存在，有效命中取`L1`；若不存在，有效接缝回退到`L1−128`，或对命中前缀末尾128个token做SWA有界重放。重放仅重建SWA，Block KV继续复用，不覆盖。
- step 4：未命中后缀继续Prefill；已命中前缀对应的分页块从远端回填到本机。

**回填与换入**

- step 1：完成上述Matching阶段，确定命中前缀。
- step 2：Fetching阶段由独立进程执行，将3FS中的Block KV读入主机共享内存。
- step 3：Swap-in阶段在引擎进程内以独立线程进行，将共享内存中的分页块迁入HBM，并尽量与前向计算流水线重叠。细粒度块传输采用GDR/RDMA，以提高PCIe利用率并降低对SM的占用。

若SWA不在本机，Entrypoint先查内存目录定位持有节点，再经VLAN通道拉取。

**TTL与回收**

kvcache-store本身不做应用层过期控制，容量回收由3FS GC完成，按LRU周期性淘汰最久未用的 KV。

公开材料给出的量级约为100 PiB SSD；agent流量TTL（Time To Live）约3天，chatbot流量TTL约7天。SWA只保留在主机内存中，生命周期更短，因此会出现Block KV仍在但SWA已失效的情况；此时依赖有界重放恢复窗口状态。

## 小结

V4.1-Flash用滑窗层、压缩稀疏层、YoCo consumer三段组织注意力；全局压缩主KV只由少数`kv_source_layers`写入，其他层通过共享槽读取，本层通常仍保留SWA。体积上，压缩主KV按compressed-token计（约288B），SWA按窗口token计（528B），Indexer K按压缩轴计（约68B）。

Prefix cache的主体是3FS上的分页Block KV，SWA以128对齐快照留在产出机；命中先定Block KV的`L1`，再配SWA或短重放补窗口，拉取与换入同计算重叠。

大致特点概括：

1. 结构上是栈式分层+共享源KV，并非每层一份完整历史。
2. 存储上Block KV进共享盘、SWA进本机、compression state不进行offload保存。
3. 远端prefix cache形成闭环：按128对齐将数据CPU offload并持久化到3FS，经Entrypoint哈希链做前缀匹配，命中后异步回填并与计算重叠完成HBM换入；未命中或SWA失效时，再以有界重放补齐窗口状态。
