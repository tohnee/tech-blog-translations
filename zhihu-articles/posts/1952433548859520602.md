**KV-Cache是一种优化技术，用于 Transformer 模型的自注意力层，以提高计算效率。**

简而言之，KV 缓存存储中间键 (K) 和值 (V) 计算结果，以便在推理期间重用，从而显著提升文本生成速度。KV 缓存的缺点是它增加了代码的复杂性，增加了内存需求，并且无法在训练期间使用。然而，在生产环境中使用 LLM 时，推理速度的提升通常值得牺牲代码复杂性和内存。

本文主要介绍什么是KV Cache、KV Cache的实现以及优化。

## ⭕️**什么是KV缓存？**

假设LLM正在生成一些文本。具体来说，假设LLM收到以下提示：“Time”。我们知道，LLM每次生成一个单词（或token），下图展示了根据提示生成连续两个单词的示意图：

![](https://pic2.zhimg.com/v2-69a9e4386d1671d4d9806a7cb464a1e5_r.jpg)
*图1：该图展示了LLM如何逐个token地生成文本。从提示符“Time”开始，模型生成下一个token“flies”。下一步，对完整序列“Time flies”进行重新处理，生成token“fast”。*

需要注意的是生成的LLM文本输出中存在一些冗余，如下图所示：

![](https://pic3.zhimg.com/v2-b9a9c379377b9b75ffa4225278d671cc_r.jpg)
*图2：该图突出显示了LLM在每个生成步骤中必须重新处理的重复上下文（“Time flies”）。由于LLM不缓存中间的键/值状态，因此每次生成新的 token（例如，“fast”）时，它都会重新编码整个序列。*

在实现LLM文本生成函数时，我们通常只使用每个步骤中最后生成的token。然而，上面的可视化图从概念层面凸显了其中一个主要的低效之处。如果我们深入研究注意力机制本身，这种低效（或冗余）就变得更加清晰。

下图展示了LLM核心注意力机制计算的部分示意图。这里，输入标记（“Time” 和“flies”）被编码为三维向量（实际上，这些向量要大得多，但这会使它们难以放入一个小图中）。矩阵W是注意力机制的权重矩阵，用于将这些输入转换为键、值和查询向量。

下图展示了底层注意力分数计算的摘录，其中突出显示了键和值向量：

![](https://pic1.zhimg.com/v2-4c37e6281d3135d946592921f7ba1370_r.jpg)
*图3：该图展示了LLM在注意力计算过程中如何从token嵌入中导出键（k）和值（v）向量。每个输入 token（例如，“Time”和“flies”）都使用学习到的矩阵W_k和W_v进行投影，以获得其对应的键和值向量。*

如前所述，LLM每次生成一个单词（或token）。假设LLM生成了单词“fast”，那么下一轮的提示就变成了“Time flies fast”。如下图所示：

![](https://pic4.zhimg.com/v2-7b41733c11a5af15fb43ba6427001ef9_r.jpg)
*图4：该图展示了LLM在每个生成步骤中如何重新计算先前出现的token（“Time” 和 “flies”）的键值向量。当生成第三个token（“fast”）时，模型会重新计算相同的值k(1)/v(1)向量k(2)/v(2)，而不是重用它们。这种重复计算凸显了在自回归解码过程中不使用键值缓存的低效率。*

我们可以看到，通过比较前两张图，前两个标记的键和值向量完全相同，并且在每个下一个标记文本生成轮次中重新计算它们会很浪费。

而KV Cache的思想就是实现一种缓存机制，存储以前生成的键和值向量以供重用，有效避免这些不必要的重新计算。

## ⭕️**LLM 如何生成文本（有和没有 KV Cache）**

上一节我们了解了基本概念，下面我们再来详细了解一下，然后看具体的代码实现。

假设我们有一个没有KV Cache的“Time flies fast”的文本生成流程，可以这样理解：

![](https://pic2.zhimg.com/v2-c4c3e609d888827a0d0b5213d4015f49_r.jpg)

注意冗余：标记“Time”和“flies”在每个新的生成步骤中都会重新计算。KV Cache通过存储和重用先前计算的键和值向量来解决这种低效率问题：

1. 最初，模型计算并缓存输入标记的键和值向量。
2. 对于生成的每个新标记，模型仅计算该特定标记的键和值向量。
3. 从缓存中检索先前计算的向量以避免冗余计算。

下表总结了计算和缓存步骤和状态：

![](https://pica.zhimg.com/v2-6aa114647e5fee17dee8b5096ad33ec2_r.jpg)

这样做的好处是，"Time"计算一次，重复使用两次；"flies"计算一次，重复使用一次。（为了简单起见，我们举了一个简短的文本示例，但直观地可以看出，文本越长，我们就越能重复使用已经计算过的键和值，从而提高生成速度。）

下图并排展示了有和没有 KV Cache的生成步骤 3。

![](https://picx.zhimg.com/v2-66f6bf2545e39bc70e3316ebf208c44d_r.jpg)
*图5：比较使用和不使用KV Cache的文本生成。在顶图（不使用缓存）中，每个 token 步骤都会重新计算键和值向量，这会导致冗余操作。在底图（使用缓存）中，先前计算的键和值会从键值缓存中检索，以避免重新计算，从而加快生成速度。*

因此，如果我们想在代码中实现KV Cache，我们只需要像往常一样计算键和值，然后存储它们，以便在下一轮中检索它们。下一节将通过一个具体的代码示例来说明这一点。

### **1. 注册缓存缓冲区**

在构造函数中MultiHeadAttention，添加了两个非持久性缓冲区cache_k和cache_v，它们将保存跨步骤的连接键和值：

```python
self.register_buffer("cache_k", None, persistent=False) 
self.register_buffer("cache_v", None, persistent=False)
```

### **2. 带use_cache的Forward**

接下来，扩展forward该类的方法MultiHeadAttention来接受一个use_cache参数：

```python
def forward(self, x, use_cache=False):
    b, num_tokens, d_in = x.shape
​
    keys_new = self.W_key(x)  # Shape: (b, num_tokens, d_out)
    values_new = self.W_value(x)
    queries = self.W_query(x)
    #...
​
    if use_cache:
        if self.cache_k is None:
            self.cache_k, self.cache_v = keys_new, values_new
        else:
            self.cache_k = torch.cat([self.cache_k, keys_new], dim=1)
            self.cache_v = torch.cat([self.cache_v, values_new], dim=1)
        keys, values = self.cache_k, self.cache_v
    else:
        keys, values = keys_new, values_new
```

这里对键和值的存储和检索实现了KV Cache的核心思想。

**储存**

具体来说，在通过 if self.cache_k is None: ...初始化缓存后，我们分别通过self.cache_k = torch.cat(...)和self.cache_v = torch.cat(...)将新生成的键和值添加到缓存中。

**检索**

然后，keys, values = self.cache_k, self.cache_v从缓存中检索存储的值和键。

这就是键值缓存的核心存储和检索机制。接下来的第 3 节和第 4 节将讨论一些次要的实现细节。

### **3.清除缓存**

生成文本时，我们必须记住在两次单独的文本生成调用之间重置键和值缓冲区。否则，新提示的查询将关注前一个序列遗留的过时键，这会导致模型依赖不相关的上下文并产生不连贯的输出。为了防止这种情况，我们向类MultiHeadAttention中添加了一个方法reset_kv_cache，以便在以后的文本生成调用之间使用：

```python
def reset_cache(self):
    self.cache_k, self.cache_v = None, None
```

### **4.在完整模型中传播use_cache**

类MultiHeadAttention的变更完成后，我们现在来修改GPTModel。首先，我们为 Instructor 添加一个 token 索引的位置跟踪：

```python
self.current_pos = 0
```

这是一个简单的计数器，它记住模型在增量生成会话期间已经缓存了多少个令牌。

然后，我们用显式循环替换单行块调用，遍历use_cache每个转换器块：

```python
def forward(self, in_idx, use_cache=False):
    # ...
 
    if use_cache:
        pos_ids = torch.arange(
            self.current_pos, self.current_pos + seq_len,            
            device=in_idx.device, dtype=torch.long
        )
        self.current_pos += seq_len
    else:
        pos_ids = torch.arange(
            0, seq_len, device=in_idx.device, dtype=torch.long
        )
    
    pos_embeds = self.pos_emb(pos_ids).unsqueeze(0)
    x = tok_embeds + pos_embeds
    # ...
    for blk in self.trf_blocks:
        x = blk(x, use_cache=use_cache)
```

上面代码设置use_cache=True的情况是，我们从self.current_pos开始，并计算seq_len步骤数。然后，增加计数器，以便下一个解码调用从我们上次中断的地方继续。

进行self.current_pos跟踪的原因是，新的查询必须直接排列在已存储的键和值之后。如果不使用计数器，每个新步骤都会再次从位置 0 开始，因此模型会将新的标记视为与之前的标记重叠。（或者，我们也可以通过offset = block.att.cache_k.shape[1]来跟踪。）

上述更改还需要对TransformerBlock类进行小修改以接受该use_cache参数：

```python
def forward(self, x, use_cache=False):
    # ...
    self.att(x, use_cache=use_cache)
```

最后，为了方便起见，我们添加了一个模型级重置来GPTModel一次性清除所有块缓存：

```python
def reset_kv_cache(self):
    for blk in self.trf_blocks:
        blk.att.reset_cache()
    self.current_pos = 0
```

### **5. 在生成中使用缓存**

通过对GPTModel，TransformerBlock和MultiHeadAttention的修改，最后，我们在一个简单的文本生成函数中使用 KV Cache的方法如下：

```python
def generate_text_simple_cached(
        model, idx, max_new_tokens, use_cache=True
    ):
    model.eval()
​
    ctx_len = model.pos_emb.num_embeddings  # max sup. len., e.g. 1024
    if use_cache:
        # Init cache with full prompt
        model.reset_kv_cache()
        with torch.no_grad():
            logits = model(idx[:, -ctx_len:], use_cache=True)
​
        for _ in range(max_new_tokens):
            # a) pick the token with the highest log-probability 
            next_idx = logits[:, -1].argmax(dim=-1, keepdim=True)
            # b) append it to the running sequence
            idx = torch.cat([idx, next_idx], dim=1)
            # c) feed model only the new token
            with torch.no_grad():
                logits = model(next_idx, use_cache=True)
    else:
        for _ in range(max_new_tokens):
            with torch.no_grad():
                logits = model(idx[:, -ctx_len:], use_cache=False)
            next_idx = logits[:, -1].argmax(dim=-1, keepdim=True)
            idx = torch.cat([idx, next_idx], dim=1)
​
    return idx
```

请注意，我们仅通过 c) logits = model(next_idx, use_cache=True)向模型提供新令牌。如果没有缓存，我们将整个输入logits = model(idx[:, -ctx_len:], use_cache=False)提供给模型，因为它没有存储可重用的键和值。

## ⭕️**KV Cache的优点和缺点**

随着序列长度的增加，KV 缓存的优点和缺点在以下方面变得更加明显：

- [**好**]计算效率提升：如果没有缓存，第t步的注意力机制必须将新查询与之前的t 个键进行比较，因此累积工作量呈二次方增长，即 O(n²)。有了缓存，每个键和值只需计算一次即可重复使用，从而将每步总复杂度降低到线性 O(n)。
- [**不好**]内存使用量呈线性增长：每个新 token 都会附加到 KV 缓存中。对于长序列和较大的 LLM，累积的 KV 缓存会越来越大，这可能会消耗大量甚至过大的（GPU）内存。作为一种解决方法，我们可以截断 KV 缓存，但这会增加更多的复杂性（但同样，在部署 LLM 时，这样做可能是值得的）。

## ⭕️**优化KV Cache实现**

虽然上面的 KV 缓存的概念实现有助于清晰理解，并且主要是为了代码可读性和教育目的，但在实际场景中部署它（特别是更大的模型和更长的序列长度）需要更仔细的优化。

### **扩展缓存时的常见陷阱**

- **内存碎片和重复分配**：如前所示，通过连续连接张量torch.cat会导致性能瓶颈，因为频繁的内存分配和重新分配。
- **内存使用量线性增长**：如果没有适当的处理，KV 缓存大小对于非常长的序列来说变得不切实际。

### **技巧 1：预分配内存**

我们可以根据预期的最大序列长度预先分配一个足够大的张量，而不是重复连接张量。这可以确保内存使用的一致性并减少开销。伪代码如下所示：

```python
# Example pre-allocation for keys and values
max_seq_len = 1024  # maximum expected sequence length
cache_k = torch.zeros(
    (batch_size, num_heads, max_seq_len, head_dim), device=device
)
cache_v = torch.zeros(
    (batch_size, num_heads, max_seq_len, head_dim), device=device
)
```

在推理过程中，我们可以简单地写入这些预分配的张量的切片。

### **技巧 2：通过滑动窗口截断缓存**

为了避免耗尽 GPU 内存，我们可以实现一个带有动态截断的滑动窗口方法。通过滑动窗口，我们只维护window_size缓存中的最后一个标记：

```python
# Sliding window cache implementation
window_size = 512
cache_k = cache_k[:, :, -window_size:, :]
cache_v = cache_v[:, :, -window_size:, :]
```

## ⭕️**结论**

尽管缓存带来了额外的复杂性和内存考虑，但效率的显著提高通常超过这些权衡，特别是在生产环境中。

本文代码优先考虑代码的清晰度和可读性而不是效率，但实际实现通常需要深思熟虑的优化，例如预分配内存或应用滑动窗口缓存来有效管理内存增长。
