2025年12月9日，Anthropic 宣布将 Model Context Protocol（MCP）捐赠给 Linux 基金会旗下新成立的 Agentic AI Foundation（AAIF）。这个由 Anthropic、Block 和 OpenAI 联合创立，并获得 Google、Microsoft、AWS、Cloudflare 和 Bloomberg 支持的基金会，承载着让 AI Agent 技术透明化、协作化和为公众利益服务的使命。

表面上看，这是一个值得庆祝的里程碑。MCP 推出仅一年，就已经拥有超过 10,000 个活跃的公开服务器，被 ChatGPT、Cursor、Gemini、Microsoft Copilot、Visual Studio Code 等主流 AI 产品采用，SDK 月下载量超过 9700 万次。但在开源社区的另一端，开发者们却对 MCP 充满了抱怨和质疑。

![](https://pic1.zhimg.com/v2-1a1c55963aef8b11f20fa7bab4922314_r.jpg)
*小红书上吐槽 MCP 的用户*

这种反差让人不禁想问：一个被大厂力推、看似前景光明的协议，为什么会遭到如此多的吐槽？开发者到底在吐槽什么？

## 一、技术实现的复杂性困境

### 1. 过度设计的传输机制

MCP 最被诟病的就是它的传输设计。从最初的本地 STDIO 模式，到后来演变为依赖 HTTP+SSE（Server-Sent Events）的双通道传输，MCP 引入了多条持久连接。

开发者直言不讳地指出："MCP 的 HTTP+SSE 传输模式非常繁琐，需要维护双向的长连接，对比于 WebSocket 方案显得过于复杂。" 更尖锐的评论则认为，这种设计"基本上是在 SSE 上实现 WebSocket"——既然如此，为什么不直接用 WebSocket？

这种过度设计带来的直接后果是实现难度和维护成本的双重提升。对于习惯了 RESTful API 或 WebSocket 的开发者来说，MCP 的学习曲线陡峭得有些不合理。

好的设计总是简单的设计，从我们自己的开发经验来说，开发 MCP 协议的接口总归是要花时间去理解一个新协议，相比 RESTful 等的确有些繁杂。

### 2. 文档质量不足

更糟糕的是，MCP 的官方文档质量被普遍批评为"非常糟糕"。开发者反映："规范忽略了重要方面，也没有给出完整的对话示例。"

这意味着开发者常常需要自行逆向工程来摸清协议细节。对于一个号称要成为 AI 领域"通用标准"的协议来说，这样的文档水平显然是不合格的。学习成本的居高不下，直接劝退了大量潜在的采用者。

### 3. 缺乏灵活性的固定接口

MCP 目前仅支持基于 JSON-RPC 的固定接口，没有分级授权或风险控制机制。更令人担忧的是，MCP 协议本身对工具的权限风险没有任何概念，对本地执行的工具也采取默认信任的态度。

这种"一刀切"的设计在功能上显得相对单一。部分开发者批评 MCP 并没有本质创新，"只是把已有的函数调用封装在另一层协议里"，并未有效避免重复造轮子。

## 二、Agent 集成的现实困境

### 1. 工具定义的混乱状态

由于 MCP 生态尚处于早期，许多 MCP 服务器仓促上线，导致工具名称、输入输出描述等元信息不完整或不精确。

实际使用中，开发者发现 AI 常常因为工具说明不清而调用错误的方法，返回无效结果。比如，某些服务器未正确描述货币字段或参数，在调用发票工具时就会产生金额错误。这种基础性问题的大量存在，严重影响了实际生产环境的可靠性。

### 2. 维护困境与可靠性问题

第三方 MCP 服务器普遍维护不足。开发者抱怨："服务器虽然已经发布，但很少更新修复漏洞，文档错误迟迟没人改。"

这种状况导致使用过程中频频碰到 BUG 或兼容性问题，开发者需要自行排查和适配。对于希望在生产环境中稳定使用的团队来说，这样的生态质量是难以接受的。

### 3. 集成测试的指数级成本

为了让 Agent 能稳定调用多种工具，开发者需要对每个 MCP 服务做大量测试，包括沙箱数据准备、多场景验证以及性能评估等。更麻烦的是，这种测试成本随着服务数量呈指数增长。

当你的系统需要集成 10 个、20 个甚至更多 MCP 服务时，测试和维护的负担会变得极其沉重。

### 4. 安全隐患与权限管理缺失

MCP 赋予了 Agent 访问外部系统的强大能力，但缺乏内建的权限管理机制。一旦服务端密钥或配置不当，敏感数据（如 API 密钥、个人信息）可能被误泄露。

更严重的是，MCP 本身对权限检查没有要求，不同客户端实现间缺乏一致性，使开发者在授权流程上感到头疼。在企业级应用中，这样的安全短板是致命的。

## 三、架构设计的性能瓶颈

### 1. 上下文膨胀的恶性循环

对于非开发者用户，MCP 最直观的不足是导致上下文窗口膨胀，比如 ClaudeCode 中，什么还没开始干，多引入几个MCP 工具就已经占用了 10-20% 的窗口。

这是因为 MCP 要求在 LLM 的对话上下文中列出可用工具的所有信息。这导致：工具越多，上下文占用越大。加载大量工具定义会导致 LLM 上下文窗口膨胀，占用大量 token，模型反应变慢，甚至开始忘记或混淆细节。

并且，当工具和数据过多时，AI 可能出现两种极端表现：要么"忽略本应使用的工具"，要么"多调用不相关的工具"。这影响了系统的效率与稳定性，形成了一个恶性循环——你越想让系统功能丰富，系统就越可能失控。

### 2. 有状态会话的资源陷阱

为支持多次交互，MCP 采用了有状态会话模式。这要求服务器必须维持每个客户端的会话状态，处理心跳、断开等事件。MCP 的设计从无状态调用变为有状态会话，这破坏了典型 Web API 的无状态特性，需要开发者手动管理连接和会话生命周期。持久连接让系统变得更易出错。这种设计在互联网架构演进的大趋势中，显得有些"逆潮流"。

### 3. 功能范围的局限性

MCP 1.0 主要面向单个 Agent 与工具的上下文交互，并不擅长 Agent 之间的复杂协调。一些观点将其比作"USB-1"——只解决了最基本的问题，未来需要新协议来处理 Agent 间的接力或共享记忆。

## 四、开发者的替代方案选择

面对这些问题，开发者们找到了多种替代方案。

### 1. 原生函数调用（Function Calling）

对于只使用单一 LLM 服务商的应用，直接使用其原生的函数调用接口更为简单直观。函数调用通常比引入 MCP 更容易实现，对每种服务只需要在客户端配置即可。这种方案虽然缺乏通用性，但在特定场景下更简单高效和可控。

### 2. AI Agent 框架的抽象层

LangChain、AutoGen 等 AI Agent 框架已经封装了工具发现和调用逻辑。开发者指出："这些抽象层比直接使用 MCP 更易于使用，我预期它们将继续存在。在这些框架背后再接入 MCP 即可，不用每个开发者都从头实现 MCP。"

### 3. Anthropic Skills 的崛起

最近 Anthropic 推出的 Skills 机制，更是对 MCP 地位形成了直接挑战。

开发者讨论中有这样的观点："MCP 是管道，而 Skill 是一个具备执行能力的终端应用。" Skills 可以在 Claude Code、Claude.ai 网页端和 API 调用三个终端上直接使用，已经被原生植入了整个 Claude 生态。

更关键的是，Skills 提供了更强的掌控感。一位开发者坦言："很多第三方的 MCP 服务，你并不知道它背后具体做了什么，对其信任度不高。而 Skill 是我们自己搜集资源、编写脚本、自由组合的，掌控感更强。"

有开发者直言："我个人非常期待 Skills 能替换掉 MCP，因为我一点都不喜欢 MCP。" 在他们看来，Skill 更加易用，可复用性也更高，而 MCP 消耗的资源太大了。

### 4. 直接调用 API 的务实选择

除了正式协议和框架，团队也常采用更轻量的方案，如直接通过 HTTP API 调用工具、将文件内容注入 Prompt 或使用检索式方法（RAG）为模型提供上下文。

这些方案虽然不够通用，却因简单高效而被不少开发者采用，尤其在原型和小规模项目中更为常见。“直接导出一份 OpenAPI (Swagger) 文档，AI 一下就能读懂，并不需要 MCP 再来封装一层。"

### 5. CLI 调用

2026 年出现了一种新趋势：逐渐有一些软件和 Agent 不再通过网络接口去访问其他应用的数据，而是通过 Bash 工具，利用 CLI 进行交互。

一些软件开始提供命令行工具，一些 Agent 也在重度使用 Bash 这个通用工具。通过这种方式，Agent 能高效获取工具内部的能力和数据。这种模式其实和 MCP 协议中的标准输入输出协议（stdio）非常相似。

值得注意的标志性事件是笔记软件 Obsidian 近期推出了Obsidian CLI，软件开发者不仅仅为人类开发图形界面，也开始专门为 AI 开发更易用的 CLI 交互界面。这种交互方式对 Agent 的开发者来说非常简单。他只需要给 Agent 配备bash 工具这一个工具，再做好权限管理和沙箱等工作后，就拥有了去调用整个计算机上许多软件的能力。

> 我们自己开发的一款个人全文检索和知识库产品 [LinklyAI](https://linkly.ai/) ，在研究如何方便Agent接入时，发现Skills + CLI的组合相比MCP接入有太多优势。如果你想寻找一款免费的适合个人在本地建立知识库的产品，可以试试 [LinklyAI](https://linkly.ai/) 。

## 五、捐赠背后的深层思考

Anthropic 将 MCP 捐赠给 Linux 基金会，官方解释是为了"确保 MCP 保持开源、社区驱动和供应商中立"。但从另一个角度看，这也可能反映了一些现实困境。

### 1. 商业化的两难

作为一个企业主导的协议，MCP 面临着商业利益与开放标准之间的天然矛盾。捐赠给中立的基金会，或许是为了消除其他厂商的戒心，推动更广泛的采用。

但问题在于，如果 MCP 真的如官方所说那样成功，为什么需要这么快就"交出去"？Anthropic 这家公司历来对开源并不热衷，似乎他们更加专注在其商业目标上。这不禁让人怀疑，Anthropic 是否在内部也发现了一些难以克服的问题和不足。

### 2. 生态建设的困局

尽管数据看起来漂亮（10,000+ 服务器，9700 万 SDK 下载），但从开发者反馈来看，MCP 生态的质量堪忧。大量服务器缺乏维护，文档质量低下，集成体验糟糕。

这种"虚胖"的生态，很可能源于早期的激进推广策略。当 Anthropic 试图通过 Claude 产品强行推动 MCP 时，确实带来了数量上的增长，但质量和体验却没有跟上。

### 3. 标准化的困境

MCP 试图成为 AI 领域的"通用标准"，但现实是，真正的标准往往是自然演化而来的，而非由单一公司设计和推动。

HTTP 之所以成功，是因为它解决了一个真实的、普遍的痛点，并且足够简单、足够开放。相比之下，MCP 显得过于复杂，功能定位也不够清晰——它到底是想解决工具调用的问题，还是想解决上下文管理的问题？到底是面向开发者呢，还是作为一种扩展能力提供给普通用户的？

这种模糊性让人感到困惑。

## 六、未来的展望：MCP 会走向何方？

### 1. 短期内：与 Skills 的共存与竞争

从目前的讨论来看，MCP 和 Skills 更像是互补而非替代关系。正如开发者所说：

大厂或拥有成熟 API 体系的厂商，会倾向于将自身能力封装成 MCP，作为一种特殊“产品”提供给市场。而有研发能力的开发者或团队，则更倾向于使用更可控灵活的方式来满足自己高度个性化的需求。

但这种"共存"可能并不稳定。如果 Skills 在易用性和灵活性上持续优于 MCP，开发者会用脚投票。

我们作为一个应用开发者，会希望通过 MCP，让我们的用户能在其他 AI 应用中使用我们的产品能力。但我们再开发自己产品时，则更希望通过 function call 直接调用 HTTP 等通用协议的接口，而不是复杂的 MCP。

### 2. 中期内：协议的演化与分化

MCP 1.0 被开发者比作"USB-1"，意味着它只是一个开始。未来可能会出现 MCP 2.0、3.0，或者完全不同的协议来解决 Agent 间协作、权限管理、性能优化等问题。

Linux 基金会的中立治理可能会带来更开放的演化路径，但也可能因为缺乏强有力的商业驱动而放慢创新速度。

### 3. 长期内：回归本质的思考

或许我们需要重新思考：AI 应用真的需要一个"通用协议"吗？

在互联网和移动互联网时代，我们并没有为网站和 App 之间的通信制定一个强制性的协议标准。每个 App 根据自己的需求选择合适的技术方案——REST、GraphQL、gRPC 等等都在各自的场景下发挥作用。

AI 应用因为具备自主性，使用外部工具和能力具有不可控性，需要一种方便 LLM 发现和调用的方法。这个需求我认为是明确的，至于是不是 MCP 协议，尚未可知，但交给一个中立的基金会来维护，总归是一件促进发展的好事。

## 结语

开发者对 MCP 的吐槽，不仅仅是对一个具体协议的批评，更是对整个 AI 技术栈如何走向成熟的一次思考。Anthropic 将 MCP 捐赠给 Linux 基金会，或许是一个新的开始，但能否真正解决这些根本性的问题，还需要时间来检验。伟大的创新是无法被计划。

对于开发者来说，保持开放的心态和务实的选择或许是最明智的策略。不要被任何"通用标准"的宣传所迷惑，而是根据实际需求选择最合适的技术方案。毕竟，工具的价值在于它能解决问题，而不在于它有多么"标准"。
