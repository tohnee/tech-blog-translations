## 概述

现在scale up在带宽、延迟、内存语义与统一寻址、单跳交换机下的扁平化的拓扑追求、基础可靠性（多种FEC、LLR、端到端重传）、流控（CBFC、PFC）、基于以太网路线这些功能上达成了较一致的统一。

在超节点卡数上也由于是否引入光、机柜的工程问题、交换机的跳数、的限制下也基本达成一致。

在在网计算、2跳拓扑和2跳以上的超节点卡数、MOE流量的处理、负载均衡、lane degrade、光模块的引入、header压缩、小包merge、故障处理（单 Lane 故障、链路闪断 / 误码、单个光模块故障、端到端路径故障）、等方面还在百花齐放。

## 业务流量与协议的映射

如果将各种复杂业务流量拆解到scaleup协议的映射上对应：incast、小包高频、进关键路径同步耦合、随规模放大卡数增加导致流量增加等场景。

MoE all2all 的结构是：**稀疏扇出（每 token 只去 K 个专家，而非全部）+ 多打一（N 个源同时写同一目的）+ 小包高频（单轮 7KB、58 轮）+ 与计算强同步（落在 TPOT 关键路径）+ 流量随规模线性放大**。

几乎是全集。

## 华为在MOE流量处理

而华为在MOE流量处理方面，不是靠交换机聚合，也不是靠集合通信硬件卸载完成的，主要是体现在三个点上，

1. 统一全局地址空间（UGAS）：所有 NPU 的 HBM 编进同一个地址域，跨 NPU 直接 load/store。
2. 512B 原子性：Ascend NPU 在超节点与 NoC 域内支持 512 字节的原子 load/store，且 UB Fabric 保证这种写对远端是单一事务（要么整块可见、要么不可见），并串行化其后的读【UBEP】。这是后面 “数据即标志” 能成立的物理前提。
3. 事务层的 Atomic 事务：规范里明确有 9 种子类型（compare_swap / swap / load / store / fetch_add / fetch_sub / fetch_and / fetch_or / fetch_xor），单包、保证原子性且只执行一次【UB 规范 2.1.0 §7.4.2.3】。Combine 阶段多个专家向同一个 token 归还结果时，正是用 atomic_add 把 “又到了一路” 累加进标志位。

华为主导的白皮书给出的是工程口径：<br>DeepSeek V3 每 token 要走 58 层 MoE、58 轮 Dispatch + Combine，单轮最小粒度只有 7KB，通信量随 batch 线性的长到百 MB 级；<br>而要在 TPOT 10ms 以内做大批量，单次 Dispatch 与 Combine 都必须压到 10µs 以下。

### 1、统一全局地址空间（UGAS）

UBEP 论文原文叫 Unified Global Address Space (UGAS)，规范里对应的是另一套说法：**UBAS（UB Address Space）** 加 **内存段（Memory Segment）** 机制。

![](https://pic4.zhimg.com/v2-b5889e09b01521c803dbbdc29f8bda53_r.jpg)

### 2、512B 原子性解决了什么问题？

解决的不是 “少发一次通信”，而是去掉 payload 与 flag 之间的内存序栅栏。这一点论文讲得很直接：在内存语义下，payload 和 flag 是两次独立的 store，两者的可见顺序没有保证，所以必须插入显式 memory barrier 来强制 “先数据、后标志” 的可见次序，而这个 barrier 会让硬件流水线停顿。

所以传统方案真正的问题在于：

| 层次 | 问题 |
| --- | --- |
| 正确性 | 接收端可能看到 flag 已到、数据尚未落地 → 必须有 fence 兜住 |
| 性能 | fence 是流水线停顿，而且它天然是 “全体对齐” 的（对应上一轮讲的那两道 SyncAll） |
| 结构 | flag 是独立的一次写、一次 RTT、一个独立阶段 |

根因一句话：**最终布局的起始偏移是 “全局前缀和”，而前缀和天生要等所有人**

FFN 要的是每个专家一段连续紧凑的 `[n_e, 7168]`，而这个 `n_e` 每轮都在变（路由是动态的）。紧凑排列的起点 = 前面所有同类 token 的数量之和 —— 这是一个 **sum over all sources** 的全局归约，最后一个元素必须等全部数据到齐才能算出来。论文原文把这个动作点名了：`CalCumSum`，算完才敢做 `Token-Reordering`【UBEP §2.3 / Fig.3a】。

只要偏移依赖全局求和，中间就必须有一道全局栅栏。BSP 不是设计者的偏好，是这道依赖逼出来的。

![](https://pic3.zhimg.com/v2-23688ddb484937b9507c47888d3a830e_r.jpg)

TFF 用**原子性**把这三层一起消掉：一个 512B 块是一次原子写，**数据与标志要么全到、要么全没到**。既然不可分割，“顺序” 这个问题就不存在了 —— 也就不需要 fence。

![](https://pic1.zhimg.com/v2-7aa1cfc04531d6609d98f581bfb6cc78_r.jpg)

它恢复的是 token 级流水，这才是关键收益

BSP（**Bulk Synchronous Parallel**） 的痛点是 “等整批”。TFF 之后，一个 7.5KB 的 token 被切成 16 个 512B 块，**每块落地即可被消费**—— 前缀和不用等人、数据处理不用等标志，接收端可以按块推进。

![](https://pic3.zhimg.com/v2-ad01ccced61a872c96b75204a834a75c_r.jpg)

用不同的方式回答 “那 32B 该不该花”

| 变体 | 做法 | 有效带宽 | 换到了什么 | 代价 |
| --- | --- | --- | --- | --- |
| TFF | 32B 标志 + 480B 载荷，同块原子写 | 93.75% | barrier-free + token 级流水 | 6.25% 带宽；且需先把 token 从 HBM 搬到本地内存嵌标志 |
| DC | 512B 全是载荷，前 32B 当验证标记；发送完成后额外发一个累积校验和包 | ~100% | 带宽不受损 | 必须等整个 batch 的校验和 → token 级流水被毁 |
| SP | 收端预置哨兵值，发端发原始载荷；收端看指定字节是否 ≠ 哨兵 | 理论 100% | 标志生成与验证全移到收端，且不占载荷 | 要主动重置接收 buffer；数据恰好等于哨兵 → 同步死锁 |

取舍的实质很清楚：**DC 选了 “零开销”，代价是退回批级；TFF 选了 “细粒度流水”，代价是 6.25%；SP 想两个都要，但把风险转成了正确性问题。**

注意 SP 的那个风险论文是明说的：即使 32B（256 bit）哨兵把碰撞概率压到极小，只要发生一次就是死锁，所以工程上要么预留 “不可能产生的编码”，要么就得接受这个尾部风险。

两处不能忽略的隐含成本

**第一，TFF 多了一次本地搬运。** 论文原文说它 “necessitates the movement of token data from the HBM to the local memory”—— 因为要在本地把 flag 和数据拼成 512B 块，再原子写出去。这次搬运是 Intra-NPU 级（218ns），比网络往返便宜得多，但它确实存在，不是零成本。

**第二，DC 的 “省带宽” 是有条件的。** 它把 32B 标记复用为数据本身的一部分，省下的正是 TFF 那 6.25%；但校验和是 batch 级的，所以它换回的是 “一个 batch 一次确认”。**在 MoE decode 这种 TPOT 卡在 10ms、单轮要 <10µs 的场景里，这个批级等待是不可接受的**—— 这就是为什么论文最终主推 TFF 而不是 DC。

### 3、事务层的 Atomic 事务

![](https://pica.zhimg.com/v2-4b7821b2e38783091b56b8a60734916e_r.jpg)

![](https://pic2.zhimg.com/v2-8a5815449bde268e3433189042e4bedd_r.jpg)

Atomic 支持 ROI、ROT、ROL（不支持不可靠模式）：

| 模式 | 全称 | 保序责任方 | 应答方式 |
| --- | --- | --- | --- |
| ROI | Reliable and Ordered by Initiator | 发起方自己保序 | 事务层生成独立 TAACK |
| ROT | Reliable and Ordered by Target | 目标方保序 | 事务层生成独立 TAACK |
| ROL | Reliable and Ordered by Lower layer | 传输层保序，PSN 承担事务保序 | 由传输层应答捎带，不生成独立包 |

ROL 这条差异值得记：它 “不生成独立的事务层应答包，而由传输层应答承载事务层应答”，代价是传输层应答必须**等事务层的执行结果**才能回。省一个包，换一段等待。

它解决了什么：把 “等齐 K 份” 从栅栏变成一次原子返回

这才是核心。Combine 阶段有个绕不过的语义：**同一个 token 有 K 个专家各算一份，必须等 K 份都到齐才能加权求和**。

![](https://pic1.zhimg.com/v2-6e903257cd1d3d968f09f8fd540a1a78_r.jpg)

fetch_add 的关键在返回值。如果只做 store(cnt, cnt+1)，读回来的值可能是别人写的，分不清谁是最后；fetch_add 把 “读旧值 + 写新值” 做成单一不可分操作，于是 8 个并发调用拿到的返回值必然不重不漏。这个性质叫 “最后一个到达者（last-arrival）” 模式，是免栅栏同步的标准零件。

规范自己写明了这个用途：0x19 就是 “写数据 + 原子加” 的融合原语

这一条比上面的推论更明确。规范 §7.4.2.1.6 定义了 Write_with_atomic_store_add（TAOpcode 0x19），描述里直接写了应用场景：

" 该事务可应用于两种典型场景：

1. 多端口多路径下，以多包方式乱序并发传递大事务数据，统计已完成传输的数据数量，进行通信判断。一种可选的使用方式为，通过查询统计计数是否达到预期，判断是否已经收齐所有的数据，可以节省单独的通知报文。
2. 多端口多路径下，以多包方式乱序并发传递大事务数据，统计已完成通信的任务数量，进行任务调度。"

这段几乎就是 MoE Combine 的说明：多源并发、多包乱序、统计收齐、省掉单独通知。机制上它是：

- MAETAH.Address = 数据写入地址（超 MTU 时逐包递推）
- NTFETAH.Address = 统计计数的独立地址
- NTFETAH.Notify_Data = 要原子累加的增量（“该值由 Initiator 指定，协议不做规定”）
- 目标侧：数据写入 → 无异常后把 Notify_Data 原子累加到统计地址

还有一个更省的变体 0x1A Write_with_remote_sync：不指定独立统计地址（改用 MAETAH 地址的相对偏移），也不用 Notify_Data 字段，直接拿该包的数据写入长度当增量。所以 “每写 7.5KB 就自动 +7500” 这件事，连额外字段都不用带。

这三个原语放在一起看，分工很清楚：

| 原语 | 原子粒度 | 干什么 | 谁用 |
| --- | --- | --- | --- |
| 0x19 / 0x1A | 字级（计数器） | 写数据的同时自动累加计数 | 多源汇聚，省通知包 |
| 0xB fetch_add | 字级（计数器） | 单纯把计数 +1 并拿回序号 | 需要知道 “我是第几个” 的场合 |
| 512B 原子 store | 块级（512B） | 整块数据 + 内嵌 flag 一起可见 | Data-as-Flag |

**“数据即标志” 和 “原子计数器” 是两种不同粒度的原子性，不能混为一谈**：前者靠 “整块要么全可见”，后者靠 “读改写不可分”。TFF 用前者（把 flag 塞进 512B block 的前 32B），Combine 的计数用后者。
