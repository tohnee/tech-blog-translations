> 分布式训练「变慢」或「卡住」是两类完全不同的问题，处置也不同。用 barrier 把一次迭代拆成三段计时，能把「计算慢拖累通信」和「通信本身慢」分开——这套方法在 Megatron-LM 里对应哪些内置参数、数字会怎么骗人、死锁时框架工具全部失效只剩 PyTorch 侧哪四层，是这篇的重点。

### 1. 先把「慢」和「死锁」劈开

所有通信问题先按一条界劈成两半：

**慢**——所有 rank 执行的是同一套 collective 序列，最终都会返回。它是定量问题：数值偏大，改配置、改并行度、改消息尺寸能量化改善。

**死锁**——各 rank 执行的 collective 序列本身不一致（次数、顺序、process group 或形状任一项分歧）。它是定性问题：永不返回，任何计时都打印不出来，只能靠超时暴露。

两类问题**不能用同一套工具诊断**。Megatron 的 timer 和 StragglerDetector 只对「慢」有效；死锁时它们一个数都打不出，只剩 PyTorch 侧的 watchdog 和 Flight Recorder。

先判断是哪一类：有没有 iteration 日志在往前走？有就是慢，没有就是死锁。

### 2. Megatron 里的三段计时

集合通信有个隐含语义：**它顺带是一次同步**。最快的 rank 进入 all-reduce 后，必须等最慢的 rank 也进来，数据才能开始流动。所以给 all-reduce 直接计时，量到的是两样东西之和：

```text
all_reduce 耗时 = 等最慢的 rank 到达 + 真正传数据
```

而这两者对应两类完全不同的问题。混在一个数里，等于没诊断。

### 2.1 三段计时的原理

做法是在 collective 之前主动插一次 barrier，让 barrier 把「等对端」这部分吸收掉：

```text
t0 = perf_counter()
...本地计算（forward / backward）...        # 第 1 段
t1 = perf_counter()
dist.barrier(); torch.cuda.synchronize()   # 第 2 段：吸收 skew
t2 = perf_counter()
dist.all_reduce(g); torch.cuda.synchronize()  # 第 3 段
t3 = perf_counter()
```

三段各自衡量什么：

| 列 | 衡量的是 | 谁的锅 |
| --- | --- | --- |
| compute | 发起 collective 前的本地耗时 | 自己 |
| skew_wait | 等所有 rank 到齐的时间 | 别人 |
| comm | 已在同一起跑线后 collective 的耗时 | 网络/拓扑 |

判据是 `max(compute) - min(compute)` 与 `comm` 均值比大小：前者大 → 某个 rank 计算慢；后者大 → 通信本身慢。

**必须横向比所有 rank**。`compute` 证据在慢的那个 rank 手里，而 rank0 通常是被拖累的一方。

### 2.2 在 Megatron 里的对应

Megatron 里就有三段计时的对应物，只是名字不同、分散在不同的 timer level 上：

| 手写 demo | Megatron timer | 打开方式 |
| --- | --- | --- |
| compute | forward-compute / backward-compute | --timing-log-level 2 |
| comm | all-grads-sync / embedding-grads-all-reduce / layernorm-grads-all-reduce | --timing-log-level 1 起 |
| skew_wait | 没有独立列 —— 被 timer 自带的 barrier 吸收了 | 见下节 |

这些名字不是用户起的，是 Megatron 在源码里硬编码埋的计时点——在训练循环的关键位置各放一对 `timers('xxx').start()/.stop()`。按训练先后顺序如下（括号是该 timer 需要的最低 log level）：

| timer（level） | 埋在训练循环的哪段 | 备注 |
| --- | --- | --- |
| batch-generator (2) | 取一个 batch |  |
| forward-backward (1) | 前向+反向整段（套着下面几项） | level 1 粗粒度总时长 |
| ↳ forward-compute (2) | 前向计算 |  |
| ↳ backward-compute (2) | 反向计算 |  |
| ↳ forward-send/recv、backward-send/recv (2) | PP 各 stage 间 P2P 通信 | PP>1 才有 |
| embedding-grads-all-reduce (1) | 梯度 finalize：embedding 梯度 | PP 下首尾 stage 各算一份 |
| all-grads-sync (1) | 梯度 finalize：DP 主梯度 all-reduce |  |
| layernorm-grads-all-reduce (1) | 梯度 finalize：非 TP 模块梯度 | sequence parallel 才有 |
| optimizer (1) | optimizer step 整段（套着下面几项） | level 1 粗粒度总时长 |
| ↳ optimizer-copy-to-main-grad (1) | 梯度拷到 main param |  |
| ↳ optimizer-clip-main-grad (1) | 梯度裁剪 |  |
| ↳ optimizer-inner-step (1) | 真正的 optimizer.step() |  |
| ↳ optimizer-copy-main-to-model-params (1) | 更新拷回 model param |  |

另有 `optimizer-unscale-and-check-inf`（fp16 AMP 才走，bf16 没有 grad_scaler 故跳过）、`params-all-gather`（分布式优化器才走）等条件性埋点，demo 配置下不出现。`--timing-log-level` 决定哪些埋点真计时，低于设定级别的会被换成 `DummyTimer`（空操作），所以 level 0 一个数都没有。

`skew_wait` 没有对应列，因为 Megatron 把它「消化」掉了而不是「量化」出来——timer 自带的 barrier 会先等所有 rank 到齐，但这个等待时间没有单独打印，而是直接扔掉。这是理解后面所有现象的关键。

### 2.3 timer 的两个旋钮：level 和 option

Megatron 的 timer 有两个独立开关，名字很像但各管一件事：

| 参数 | 管什么 | 取值 |
| --- | --- | --- |
| --timing-log-level | 记多细——决定哪些分段真正计时 | 0 / 1 / 2 |
| --timing-log-option | 怎么聚合——决定多个 rank 的数怎么汇总打出来 | minmax / max / all |

`--timing-log-level` 三档：

- `0`：只打 iteration 汇总
- `1`：打粗粒度分段（`forward-backward` / `all-grads-sync` / `optimizer`）
- `2`：把 forward/backward 拆成 compute 与各类 grads-sync

排障基本都要 `level 2`，否则分不出「计算慢」和「通信慢」。

`--timing-log-option` 默认的 `minmax` 则是排障时最容易栽的坑——下一节展开。

### 2.4 `minmax` vs `all`：一个丢 rank 号，一个不丢

`--timing-log-option` 决定聚合方式，而聚合方式直接决定能不能定位到人：

```text
minmax:  forward-compute ...............................: (17.67, 616.81)
all:     forward-compute:
              rank  0: 17.67
              rank  1: 616.81
```

`minmax` 只做 `min()` / `max()`，**rank 号在聚合里就丢了**。它能喊出「有 rank 慢」（17.67 对 616.81，差 35 倍），但喊不出是谁。`all` 走 `all_gather_into_tensor`，每个 rank 一行原样打出来。

排障时**第一件事就是加 `--timing-log-option all`**，否则只能知道有人慢，不知道是谁。

> **易错点**：`minmax` 的 `(17.67, 616.81)` 说明有人慢 35 倍，但 rank 号被聚合丢掉了。要定位必须换 `all`。

### 2.5 level-1 timer 的 barrier：它就是 `skew_wait` 的去处

Megatron 的 `Timer.start()` 支持 `barrier=True`，此时它会先 `torch.distributed.barrier()` 再 `torch.cuda.synchronize()`，然后才开始计时。`config.barrier_with_L1_time` **默认为 True**，所以 level-1 的几个 timer 天生带 barrier。

这和手写 demo 里「在 collective 前插一次 barrier 把 skew 剥出来」是同一个手法，只是 Megatron 把 barrier 的耗时直接扔掉了，没有单独打成一列。

代价与收益都很明确：

- 收益：`all-grads-sync` 量到的是**净通信耗时**，不含「等最慢 rank」
- 代价：level-1 看不出是谁慢，因为差异被 barrier 抹平了。要点名得上 level 2

### 2.6 关掉 barrier 之后数字会怎么骗人

`--no-barrier-with-level-1-timing` 可以关掉它。实测注入 rank1 每次 forward 额外 sleep 0.3s：

**barrier 开（默认），643.6 ms/iter：**

```text
forward-backward   rank0 636.98 / rank1 636.91
all-grads-sync     rank0   0.95 / rank1   1.01
optimizer          rank0   4.81 / rank1   4.81
```

**barrier 关，640.9 ms/iter：**

```text
forward-backward   rank0 634.23 / rank1 634.04
all-grads-sync     rank0 600.46 / rank1   0.85    ← 虚高在快 rank 手里
```

两点值得记住。第一，虚高出现在 `all-grads-sync` 而不是 `forward-backward`，因为前者嵌套在后者内部，外层 timer 开始时 skew 还不存在。第二，**600ms 出现在 rank0 这个快 rank 上，慢的 rank1 反而干净 0.85ms** —— 照这个数去读会得出「DP 梯度同步慢，该调 NCCL」，方向完全反了。证据在快 rank 手里、结论要往慢 rank 上找，这是排障时最容易栽的地方。

> **易错点**：关 barrier 后虚高落在 `all-grads-sync`（嵌套在内层），且出现在快 rank 手里，慢 rank 反而干净。读数前先想清这个数是在 barrier 之内还是之外。

### 3. StragglerDetector：timer 给不了的三样东西

`--log-straggler` 打开 `StragglerDetector`，它输出的不是分段耗时，而是一行摘要。注入 rank1 每次 forward 额外 sleep 0.3s，稳态（iteration 12）那行长这样（为可读性折行）：

```text
MxRtt/Rnk: 614.85ms/1 | MnRtt/Rnk: 16.34ms/0
MnUtl/Rnk: 4.00%/1   | MxUtl/Rnk: 100.00%/0
MnClk/Rnk: 1155MHz/1 | MxClk/Rnk: 1410MHz/0
MnDRtt/Rnk: 0.79ms/1 | MxDRtt/Rnk: 0.95ms/0
MnEtpt/Rnk: 0.12TF/1 | MxEtpt/Rnk: 4.47TF/0
```

每个指标分 `Mn`（min）和 `Mx`（max）两档，`/Rnk` 是对应 rank 号。比 timer 多出来的几样：

| 指标 | 含义 | 排障价值 |
| --- | --- | --- |
| MxRtt/Rnk | 最慢 round-trip 时间及其 rank 号 | 直接点名，不用切 all 档自己扫 |
| MnDRtt/MxDRtt | 单独量 get_batch 耗时 | 把「数据加载慢」和「计算慢」分开 |
| MnEtpt/Rnk | 有效算力（TFLOP/s） | 慢是「活干得多」还是「机器不行」 |
| Mn/Mx Utl/Clk/Pwr/Tmp | 利用率/时钟/功耗/温度 | 把慢归因到硬件降频 |

拿上面那行读一遍，三件套的价值就出来：`MxRtt/Rnk: 614.85ms/1` 直接点名 rank1（rank0 只要 16ms）；`MnDRtt/MxDRtt` 只有 ~1ms，说明慢不在数据加载、在计算侧；`MnUtl 4%`、`MnClk 1155MHz`、`MnEtpt 0.12TF` 全指向 rank1。

> **易错点**：慢 rank 在不同指标上落在不同档——round-trip 看 `Mx`（最慢），但 util/clock/算力看 `Mn`（最低），因为它在 sleep、GPU 空闲导致利用率与时钟一起掉。读数时分清方向。另外 sleep 注入会触发 DVFS 降频，让慢 rank 看着像「机器降频」，但真·计算慢（kernel 本身慢）时 util 是高的——util 低反而说明它在「发呆」而非「拼命算」。`MnEtpt` 区分「活多」vs「机器慢」、`MnDRtt` 把数据加载分出来，这两样在纯 timer 里是混在一起的。

### 4. 死锁：Megatron 的工具全部失效

死锁意味着 iteration 永不结束，所以 **Megatron 的 timer 和 StragglerDetector 一个数都打不出来**（它们的输出都在 iteration 结束后才打印）。死锁的本质先看清，剩下 PyTorch 侧的四层工具再按开销从低到高排。

NCCL 的 collective 是按 **入队顺序配对** 的——所有 rank 进入 NCCL 调度的那一刻，队列里第 N 个 collective 就被配成一组，它**不校验** OpType、形状、process group。所以各 rank 的 collective 序列只要在下面四个维度有任一不一致，就会配错对、导致死锁：

| 维度 | 不一致形态 |
| --- | --- |
| 次数 | 某 rank 多发或少发一次（此后全体错位） |
| 顺序 | 两个 collective 在不同 rank 上交叉（如 rank1 先 all-reduce 后 all-gather，rank0 反过来） |
| OpType | 同一个位置，rank1 是 all-reduce，rank0 是 all-gather |
| 形状 / PG | 同是 all-reduce，但张量形状或 process group 不同 |

「同 SeqNum 不同 OpType」会死锁，但它只是四种情况之一。真正的判据是：**各 rank 的 collective 序列（次数、顺序、OpType、形状）完全一致，才不死锁**。下面四层工具就是用来抓这种不一致的。

| 工具 | 开销 | 何时失败 | 给什么 | 能否常开 |
| --- | --- | --- | --- | --- |
| 裸 watchdog | 0 | 等满 timeout | SeqNum / OpType / last enqueued-completed | 天生就在 |
| TORCH_NCCL_DESYNC_DEBUG=1 | ≈0 | 等满 timeout | 结构化的「谁没来参加第几个」报告 | 可以 |
| Flight Recorder | 环形缓冲，≈0 | 等满 timeout | 错配双方 + input_sizes + state + 调用栈 | 可以 |
| TORCH_DISTRIBUTED_DEBUG=DETAIL | +8% | 0 秒 fail fast | 双方完整指纹 + Python traceback | 不行 |

关键分野是**能不能常开**。前三个开销可忽略，可以挂生产训练，死锁第一次发生就抓到；DETAIL 有持续开销，只能等问题出现后重跑一次。

大规模训练里「复现一次」的成本极高，所以 FR 常开的价值远大于它在单次排障上信息量略少这件事。

### 4.1 裸 watchdog：只给半个答案

rank1 在第一次 forward 多发一次没有对端的 `all_reduce`，此后全体错位一格。1 分钟超时后：

```text
[rank1] Watchdog caught collective operation timeout:
  WorkNCCL(SeqNum=26, OpType=ALLREDUCE, NumelIn=1024, Timeout(ms)=60000)
  ran for 60097 milliseconds before timing out.
[rank1] failure detected by watchdog at work sequence id: 26
        PG status: last enqueued work: 26, last completed work: 25
[rank0] Received a dump signal from rank 1 ...
        Last enqueued NCCL work: 26, last completed NCCL work: 26
[rank1] Stack trace of the failed collective not found,
        potentially because FlightRecorder is disabled.
```

注意最后一行 —— torch 自己在提示你该开 Flight Recorder。

这里有个对手写 demo 结论的重要修正。手写 demo 给的判据是「同一个 `SeqNum` 上各 rank 报的 `OpType` 不一致」。**这条判据在裸 watchdog 日志上经常不成立** —— 本例里错位的双方一个是注入的 `all_reduce`（`[[1024]]`），另一个是 Megatron 内部的 `all_reduce_barrier`（`[[1]]`），两者 `OpType` 都是 `ALLREDUCE`。NCCL 按入队顺序配对，既不看 op 类型也不看形状，所以尺寸不同的两个 op 照样被配成一对，小的那边完成、大的那边永远等。

> **易错点**：裸 watchdog 里真正能用的判据是 `last enqueued` 与 `last completed` 的不对称（卡住的 rank 是 26/25，对端是 26/26）。「同 OpType 仍死锁」时，形状差异要靠 FR 的 `input_sizes` 才看得见。

### 4.2 `TORCH_NCCL_DESYNC_DEBUG=1`：几乎白捡的一段报告

它在 watchdog 超时的那一刻从 TCPStore 里把各 rank 的状态拉出来，拼成一段人能直接读的报告：

```text
- [1] Timeout at collective: ALLREDUCE, #26
 - To our best knowledge, the lagging/dead/mismatched ranks that caused the desync are:
   - [1] joined but didn't finish collective #26 (count from 1)
     [0] finished collective #26, but didn't join collective #27 (count from 1)
 - Snapshot of ranks' latest states:
   #26 started ranks:
   #26 finished ranks:
```

两行结论直接可读：rank1 进了 #26 但没做完，rank0 做完 #26 之后就没再来参加 #27 —— 这正是「rank1 多发一次、此后全体错位一格」的形状。

注意后面那两行 `started/finished ranks` 在本例里是空的。顺序错位（`all_reduce` ↔ `all_gather`）的场景下它们才会并列打出双方的 OpType：

```text
#4 started ranks:  [1] started ALLREDUCE
                      [0] started ALLGATHER
```

### 4.3 Flight Recorder：能常开，且 Megatron 是集成了的

Flight Recorder 是 PyTorch 内置的「飞行记录器」，名字直接类比飞机黑匣子——**平时一直在录，出事（超时）才落盘**。每个进程内开一个固定大小的环形缓冲（ring buffer），每个 collective 入队时记一条：SeqNum、OpType、`input_sizes`/`output_sizes`、所属 process group、`state`（`scheduled` 还是 `completed`），开了 stack trace 选项再附调用栈。环形缓冲只记元数据、不记 tensor 字节，大小固定（满了覆盖最老的），所以开销近乎 0、可以常开。

死锁触发 watchdog 超时那一刻，每个 rank 把自己这段缓冲 dump 成一个 pickle 文件（`_dump_0`、`_dump_1`……）。事后用 `torchfrtrace` 把各 rank 的记录按 SeqNum 摆到一起——「配错对」就是同 SeqNum 下两个 rank 的记录对不上（`input_sizes` 不同，或一个 `completed` 一个 `scheduled`）。

Megatron **有**一整套 `--flight-recorder-*` 参数，会在 `init_process_group` **之前**把值写进 `TORCH_FR_*` env：

| Megatron 参数 | 对应 env | 默认 |
| --- | --- | --- |
| --flight-recorder-dump-path | TORCH_FR_DUMP_TEMP_FILE | None（不开） |
| --flight-recorder-trace-buffer-size | TORCH_FR_BUFFER_SIZE | 2000 |
| --no-flight-recorder-dump-on-timeout | TORCH_NCCL_DUMP_ON_TIMEOUT | 开 |
| --flight-recorder-include-stack-trace | TORCH_INCLUDE_STACK_TRACE | 关 |

**为什么必须由框架代劳**：这些 env 只在建通信器时读一次，在训练脚本里 `os.environ[...] = ...` 已经太晚。

> **易错点**：FR 和 NCCL 的 env 都只在 `init_process_group` 时读一次，训练脚本里设已经晚了。排障参数要在启动命令里设。

dump 路径给目录时，Megatron 会自动追加 `_dump_` 前缀。解析用 torch 自带的 CLI：

```text
torchfrtrace /tmp/mlm_fr --prefix "_dump_"
```

输出：

```text
Collective sequence number: 26 has errors
internal record id: 30
group info: 0:default_pg
collective: nccl:all_reduce
input sizes: [[1024]]      output sizes: [[1024]]
world size: 2              expected ranks: {0, 1}
collective state: scheduled
error msg: Culprit rank 0; Error type: COLLECTIVE_TYPE_MISMATCH,
           Expected collective type: 'all_reduce' does not match
           found collective type: 'all_reduce_barrier'
collective stack trace:
  all_reduce at torch/distributed/distributed_c10d.py:3007
  ... hook at slow_rank.py:92 → forward at slow_rank.py:46
  → forward_step at pretrain_gpt.py:348 → schedules.py:509
```

一次给全了 watchdog 给不了的东西：错配双方的名字、`COLLECTIVE_TYPE_MISMATCH` 的定性、`state: scheduled` 说明它排上了但没跑完、以及精确到注入那一行的调用栈。

三个读 dump 时的实用细节：

- 扫 `state` 字段，找唯一不是 `completed` 的那条就是卡住的 op
- `pg_status` 的 `last_enqueued` ≠ `last_completed` 的那个 rank 就是卡住的 rank
- process group 的数字 id 在不同 rank 上可能不同，跨 rank 对齐要按 `desc` 而不是 id

### 4.4 `TORCH_DISTRIBUTED_DEBUG=DETAIL`：不等超时，0 秒抛错

DETAIL 会把 NCCL PG 包一层 `_ProcessGroupWrapper`，另起一个 Gloo helper PG，每次 collective 前先交换指纹：

```text
CollectiveFingerPrint(SequenceNumber=25, OpType=ALLREDUCE, TensorShape=[1024],
                      TensorDtypes=Float, TensorDeviceTypes=...)
```

对不上就立刻抛 Python `RuntimeError`：

```text
RuntimeError: Detected mismatch between collectives on ranks.
  Rank 1 is running collective: CollectiveFingerPrint(SequenceNumber=25,
      OpType=ALLREDUCE, TensorShape=[1024], ...)
  but Rank 0 is running collective: CollectiveFingerPrint(SequenceNumber=0, OpType=REDUCE)
  Collectives differ in the following aspects:
      Sequence number: 25 vs 0    Op type: ALLREDUCE vs REDUCE
      Tensor shapes: 1024 vs
  File "slow_rank.py", line 92, in hook → dist.all_reduce(torch.ones(1024, ...))
```

三点和其他三层不同：

- **逐项列出「差在哪几项」**，不用自己比两串指纹
- Python traceback 直接落在注入那一行
- 进程正常退出 —— 唯一不需要外层 `timeout` + `pkill` 兜底的死锁模式（前三层超时后会留 100% CPU 空转的 rank，见第 5 节）

代价是每个 collective 多一次 Gloo 往返，有约 +8% 的持续开销，所以只能用于「重跑复现」，不能常开——生产能常开的是 FR（见第 4 节开头工具表）。

两个容易踩的点：

- 依赖 Gloo。没编 Gloo 的话它只打一条 info 日志然后静默失效
- 取值只有 `OFF` / `INFO` / `DETAIL`，和 `NCCL_DEBUG` 那套是两个变量

> **易错点**：没编 Gloo 时 DETAIL 会**静默失效**——只打一条 info 日志就跳过包装，你以为开了指纹校验其实没开。另外它只有 `OFF`/`INFO`/`DETAIL` 三档，和 `NCCL_DEBUG`（`VERSION`/`WARN`/`INFO`/`TRACE`）是两个变量，别混。

### 5. 排障流程

串流程之前，先把这些工具按来源归个位——哪些是 Megatron 提供的、哪些落在 PyTorch 侧：

| 能力 | 来源 | 打开方式 |
| --- | --- | --- |
| Timer（三段计时） | Megatron 独有 | --timing-log-level / --timing-log-option |
| StragglerDetector | Megatron 独有 | --log-straggler |
| gpu_sniff_test | Megatron 独有 | 独立脚本 |
| Flight Recorder | PyTorch 底座，Megatron 封装了 CLI | Megatron --flight-recorder-*（替你设 TORCH_FR_*） |
| distributed timeout | PyTorch 底座，Megatron 封装 | --distributed-timeout-minutes |
| 裸 watchdog | PyTorch/NCCL 内置 | 天生就在 |
| TORCH_NCCL_DESYNC_DEBUG=1 | PyTorch，Megatron 未封装 | 自己设 env |
| TORCH_DISTRIBUTED_DEBUG=DETAIL | PyTorch，Megatron 未封装 | 自己设 env |

三类各有成因。**Megatron 独有**的（Timer / Straggler / gpu_sniff）是训练循环级能力——要懂「forward/backward 分段」「一次 iteration」，而 PyTorch 是通信库、不懂训练语义，这块它根本没有。**PyTorch 底座 + Megatron 封装**的典型是 Flight Recorder：`TORCH_FR_*` 是 PyTorch 的 env，但必须在 `init_process_group` 之前设，Megatron 的启动流程正好控制那个时机，于是给了 `--flight-recorder-*` 替你设。**只有 PyTorch、Megatron 没覆盖**的是 `DESYNC_DEBUG` 和 `DETAIL`——排障时临时加的诊断 env，Megatron 没给持久 CLI 入口。

一个实操后果：死锁排障里能复现那条路（`DETAIL`）Megatron 没封装，必须自己设 env，别以为「全用 Megatron 参数就行」而漏掉它。

把上面的工具串成一条流程：

1. **先确认是慢还是死锁** —— 有没有 iteration 日志在往前走
2. 慢：`--timing-log-level 2 --timing-log-option all`，看 `forward-compute` 的 rank 间离散度 vs `all-grads-sync` 的绝对值
3. 确认是计算慢之后，`--log-straggler` 看 `MxRtt/Rnk` 点名，`MnDRtt/MxDRtt` 区分数据加载
4. 怀疑是机器而不是代码，`gpu_sniff_test` 脱离训练体检
5. 死锁：先把 `--distributed-timeout-minutes` 调小让它快速失败。然后按「能不能复现」分两条路：

- **能复现** → 重跑一次 `TORCH_DISTRIBUTED_DEBUG=DETAIL`，0 秒失败、traceback 落业务代码
- **不能复现** → 靠常开的 `TORCH_NCCL_DESYNC_DEBUG=1` + Flight Recorder，死锁第一次发生就有 dump

两个贯穿全程的纪律：**排障参数要在启动命令里设**（timer 的 barrier、FR 的 env 都只在初始化时生效一次），以及**读数前先想清楚这个数是在 barrier 之内还是之外**。

收尾还有个坑：前三个死锁工具（watchdog / DESYNC_DEBUG / FR）超时后进程不一定自己干净退出。watchdog 报错后要走一段 abort 清理（communicator 析构、shutdown 同步），这些步骤要 rank 间配合，而死锁状态下配合又凑不齐，部分 rank 就卡在清理的自旋等待里——进程不退出、占满一个 CPU 核、显存不释放，torchrun 也收敛不了。所以外层必须套 `timeout` 卡总时长 + `pkill -9` 强杀残留，否则留下一批占着显存的僵尸进程。`DETAIL` 反而不需要这层保护——它抛的是普通 Python 异常，进程正常退出。
