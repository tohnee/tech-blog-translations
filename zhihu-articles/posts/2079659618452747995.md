**SGLang CUDA Graph 高级用法拆解：Breakable CUDA Graph 如何让推理引擎摆脱编译器依赖**

**开篇导读**

**背景**：CUDA Graph 是消除 GPU kernel launch 开销的标准手段——把一串 GPU 操作录制成图，回放时只需一次 launch。但在真实推理引擎里用起来远没有这么简单：prefill 的输入长度和请求数同时变化、自定义 Triton/CUDA 内核不配合编译器、torch.compile 一次要跑 90 秒。SGLang 团队 2026 年 8 月 17 日发的这篇博客，系统讲了他们怎么把 CUDA Graph 做进推理引擎的每一条执行路径。

**为什么值得读**：

- Breakable CUDA Graph（BCG）是 SGLang 原创的技术，2026 年 2 月首次开源，现在已是 SGLang prefill 的默认策略——它用一个装饰器就替代了 torch.compile 的整套分段编译，思路值得抄走。
- 三种捕获策略（Full / BCG / TC piecewise）同台对比，讲清各自的启动开销、兼容性边界和性能差异，不是只夸自家方案。
- Full CUDA Graph for Prefill 的 padding 技巧和内存管理（捕获到 chunked_prefill_size 消除激活峰值）有直接的工程参考价值。

**原文来源**：SGLang Team，《Advanced CUDA Graph Techniques in SGLang》，2026-08-17，[https://lmsys.org/blog/2026-08-17-advanced-cuda-graph](https://lmsys.org/blog/2026-08-17-advanced-cuda-graph) 。BCG 独立库：[https://github.com/meta-pytorch/breakable-cuda-graphs](https://github.com/meta-pytorch/breakable-cuda-graphs) 。

**TL;DR**

- **BCG 是 SGLang 原创**：2026 年 2 月首次实现（#19102），4 月扩展到 prefill（#22218），用 @eager_on_graph 标记不兼容操作，捕获时自动在图段之间插入 eager 断点，不需要编译器。
- **比 torch.compile 方案全面领先**：构建图快 3.8–5.2 倍（无编译阶段），replay 时还快 17%，代码量只有 1/4（521 vs 1771 行），且对自定义内核和新功能的兼容性好得多。
- **Full CUDA Graph for Prefill**：通过 token bucket + request slot 双重 padding，把动态 prefill 变静态，prefill 延迟比 eager 快 1.93 倍（BCG 是 1.70 倍），目前实验性支持 FA4 和 FlashInfer。
- **内存管理精细**：共享内存池 + 弱引用 + 共享输出缓冲，42 个捕获形状 × 78 层 MoE 只增 2.4 GB 图内存；捕获到 chunked_prefill_size 可把激活峰值从 1.55 GB 压到 0.35 GB。
- **BCG 已独立成库**：meta-pytorch/breakable-cuda-graphs，可在其他推理引擎、训练循环或研究原型中直接使用，不绑定 SGLang。

**一、背景：为什么 CUDA Graph 在推理引擎里不好用**

一次推理解码步不是一个 kernel，而是几百个小算子的序列——matmul、attention、MoE routing、layer norm、activation……每个算子都要 CPU 端发起一次 launch。在 batch-1 或小 batch 场景下，这些 launch 开销加起来可能占到单步延迟的 20%–40%。CUDA Graph 的思路很直接：把这串 GPU 操作录制下来，回放时只发一次 launch，开销从 O(n) 降到 O(1)。

但真正做进推理引擎时，三个问题让事情变复杂：

- **形状动态**：decode 每步 batch size 变化，prefill 的输入长度和请求数同时变化，而捕获的图要求形状固定。
- **算子不兼容**：自定义 Triton/CUDA 内核、运行时依赖的 attention metadata 准备、MoE all-to-all 通信，这些操作不能直接被 CUDA Graph 捕获。
- **编译慢**：用 torch.compile 做分段捕获时，编译本身占了图构建时间的 78%–86%，235B MoE 上要 90 秒，GLM-5.2 上要 158 秒。

这篇博客围绕这三个问题，重构了 SGLang 的整套 CUDA Graph 支持，并提出了 Breakable CUDA Graph 这个原创方案。

**二、Runner/Backend 分离：三种捕获策略的统一架构**

重构之前，decode、prefill、投机解码各有各的 CUDA Graph 实现，捕获形状管理、静态缓冲、回放逻辑大量重复。SGLang 把它拆成两层：

- **Runner（执行路径层）**：管理特定执行路径的捕获/回放状态——捕获哪些形状、静态输入缓冲、attention metadata、把 live batch padding 到捕获形状。decode、prefill、EAGLE draft、MTP draft 各有各的 runner。
- **Backend（捕获策略层）**：决定一次 forward 怎么变成可回放的图。有三种：

**Full CUDA Graph**：每个形状捕获一个完整的 torch.cuda.CUDAGraph，没有 eager 区域，回放时 launch 次数最少。decode 天然适合（每请求一个 token，形状变量只有 batch size），prefill 较难。

**Breakable CUDA Graph（BCG）**：捕获图安全区域，允许标记的操作在图段之间以 eager 模式运行。用 @eager_on_graph 装饰不兼容的函数，捕获到它时自动结束当前图段、eager 执行、然后开启新图段。

**TC piecewise**：用 torch.compile 先 trace 整个 forward，在注册的分割点切开，每段单独编译捕获。这是 SGLang 最早的分段方案，现在主要在 BCG 未验证的平台上兜底。

![](https://pica.zhimg.com/v2-3d8c1a473cb3c5803237c46dff4899fe_r.jpg)

图1：Runner/Backend 分离架构。Runner 负责执行路径的状态管理，Backend 决定捕获策略（Full / BCG / TC piecewise），每条执行路径可独立选择。<br>

这样拆分后，每条执行路径（decode/prefill/spec decoding）可以独立选捕获策略，而捕获基础设施（形状管理、静态缓冲、回放）只写一遍。

**三、Breakable CUDA Graph：无编译器的分段捕获**

BCG 是这篇博客的重点，也是 SGLang 原创的技术。它要解决的问题是：CUDA Graph 要求捕获区域完全图兼容，但真实推理 forward 里总有一些操作不能被捕获（比如依赖运行时序列长度的 attention backend）。传统做法是遇到不兼容就放弃整个 forward 的图捕获，BCG 的做法是——在不兼容的地方打断，前后继续捕获。

**3.1 设计机制：一个装饰器搞定分段**

开发者用 @eager_on_graph 标记不兼容的函数。捕获过程中执行到这个函数时：

1. 当前图段自动结束（cudaGraphEndCapture）
2. 标记函数以 eager 模式正常执行
3. 函数返回的 tensor 被保留为持久边界缓冲（device 地址固定）
4. 开启新图段，后续操作继续捕获

回放时，图段和 eager 函数按捕获时的顺序交替执行。每次 eager 函数返回新 tensor，BCG 把它 copy 进之前保留的边界缓冲——下一段图读取的地址和捕获时一致，值却是最新的。BCG 从不 trace eager 区域内部，它只需要那个函数能正确执行。

和 torch.compile 方案的关键区别：TC piecewise 先让编译器理解整个 forward 再切图，BCG 是在捕获过程中直接放断点。前者需要编译器能 trace 每个算子，后者不需要。

**3.2 为什么比 torch.compile 好**

**启动快。**torch.compile 的编译占了图构建时间的 78%–86%，235B MoE 要 90 秒、GLM-5.2 要 158 秒。BCG 完全去掉编译阶段，一次捕获就完成。42 个捕获形状下，BCG 构建 prefill 图比 TC piecewise 快 3.8–5.2 倍。

![](https://picx.zhimg.com/v2-0d09c40b363c66b993ac2e687601259f_r.jpg)

图2：Prefill CUDA Graph 构建时间对比（42 个捕获形状，TP4 on 4×GB300）。BCG 无编译阶段，构建速度显著快于 TC piecewise。<br>

**兼容性广。**SGLang 大量使用自定义 CUDA/Triton/JIT 内核，让 torch.compile 识别它们需要通过 torch.library 注册并提供 fake 实现，这在整个内核栈里撒了大量编译器脚手架。更麻烦的是，编译器限制了图边界能放在哪——跨越边界的输入输出必须是编译器能表示的类型。BCG 在 eager 断点处没有这个限制：图系统不需要理解标记函数的内部实现，边界可以跟着服务逻辑走，而不是被编译器 tracing 要求牵着走。

**可调试。**捕获的 CUDA Graph 回放时是黑盒，Python 不执行，print/assert/单步都不好使。BCG 天然保留了 eager 区域，正常 Python 在每次回放时仍会执行。SGLang 还提供 --debug-cuda-graph，把整个 forward 包在一个 eager 断点里——模型完全 eager 执行，但仍走 CUDA Graph runner 的静态缓冲、回放路径和 metadata 准备。如果问题还在，说明在模型或 runner 路径；如果消失了，捕获本身就是嫌疑。

**3.3 BCG 在 Diffusion 中的应用**

BCG 不只用于 LLM。SGLang 的扩散模型栈也采用了 BCG：去噪过程反复执行同一个 DiT forward，里面大量小算子是 launch-bound 的，CUDA Graph 收益大。BCG 捕获稳定计算区域，动态 attention 和运行时 metadata 准备保持 eager，不需要 torch.compile 理解整个 DiT forward。

效果显著：Qwen-Image 512×512 在单张 B200 上，端到端延迟从 6.48 秒降到 2.45 秒；Z-Image 从 1.231 秒降到 0.662 秒。

![](https://pic4.zhimg.com/v2-1d5f623c5db2fdadcbdffc4fbfdc7f0b_r.jpg)

图3：BCG 在 Diffusion 模型上的端到端延迟对比（warmup 后，相同 workload 和 seed）。Qwen-Image 提速 2.6 倍，Z-Image 提速 1.9 倍。<br>

注意 BCG 消除的是 launch 开销，不是模型 FLOPs。它的优势在 launch gap 占执行时间比例较大时最明显——计算密集的大 kernel 不会因为 BCG 变快。

**四、Full CUDA Graph for Prefill：把动态 prefill 变静态**

Decode 用 Full CUDA Graph 很自然——每请求一个 token，形状变量只有 batch size，用一组 bucket 覆盖就行。Prefill 难在两个维度同时变化：总 token 数和请求数。SGLang 最近找到了让 prefill 足够静态的方法。

**4.1 双重 padding：token bucket + request slot**

**Token 维度**：用 token bucket，live batch padding 到最近的捕获 token 数，和 decode padding batch size 一个思路。

**Request 维度**：每个捕获图预留固定数量的 request slot。实际请求占前面的 slot，未使用的 slot 被写成零长度哨兵（zero-length sentinel）——序列长度和 extend 长度都是零，offset 放在真实 token 之后。如果请求数超过 slot 数，回退到 eager。

![](https://pic1.zhimg.com/v2-661a4850ba67ef4fb1ece3492383b2f2_r.jpg)

图4：Full Prefill 捕获的 padding 机制。token padding 到捕获 bucket，未使用的 request slot 填零长度哨兵。<br>

每次回放都要重写哨兵 metadata，因为捕获的图仍会读取整个请求表。attention metadata 也要在回放前为 padding 后的 batch 重建。这就是为什么 full prefill capture 目前只支持 FlashAttention（FA4）和 FlashInfer——只有这两个 backend 支持这种 extend-mode metadata 准备方式。

**4.2 两种 padding 的代价不对称**

**Token padding 贵**：padding 的 token 是真实计算——它们变成 batch 里的真实行，跟着 GEMM 一起算。虽然 SGLang 单独记录真实 token 数，让 MoE routing、attention、linear-attention 内核跳过大部分 padding 区域，但 dense 计算仍要为这些额外行付费。

**Request slot padding 便宜**：FlashAttention 的变长调度器按每个序列的实际长度分配计算，零长度请求基本不贡献 attention 工作量，主要增加一点 metadata 和调度开销。

两种 padding 代价不同，选型时要注意：token 数是 expensive dimension，request slot 是 cheap dimension。Full prefill capture 目前还是实验性功能，需要显式开启，引擎会警告并建议生产环境用 BCG 或 TC piecewise。

**五、性能与内存：关键数据**

**5.1 Prefill 性能**

在 gpt-oss-120b（TP4, 4×GB300）上，单请求、固定输入长度、decode 图全部禁用，四种路径同台对比：

- Full capture：比 eager 快 **1.93 倍**
- BCG：比 eager 快 **1.70 倍**
- TC piecewise：比 eager 快 **1.45 倍**

BCG 在 replay 时也比 TC piecewise 快 17%——差距来自 TC piecewise 每次回放都要回调 compiled callable，付 Torch Dynamo 的 guard check 和 dispatch 开销，而 BCG 直接回放录制的图段。

在 GLM-5.2 上只有 BCG 能捕获（TC piecewise trace 不了 forward，full capture 没有稀疏注意力路径），BCG 比 eager 快 1.60 倍。所有曲线在 32 倍 prompt 长度范围内都是平的——这是 launch 开销主导的典型特征，不是计算。

![](https://pica.zhimg.com/v2-84079ed85e6e14ce1b8a2d2ba1b9f244_r.jpg)

图5：Prefill-only 延迟对比（gpt-oss-120b, TP4 on 4×GB300）。Full 1.93×、BCG 1.70×、TC piecewise 1.45×（vs eager）。曲线平坦说明瓶颈是 launch 开销而非计算。<br>

**5.2 内存管理**

分段捕获容易让图内存翻倍——每个形状有多个图段，每段的中间结果都要保留到回放。BCG 通过三种复用避免膨胀：

1. **跨段共享内存池**：同一形状的所有段用同一个 CUDA Graph pool，中间存储可复用而非每段单独钉住。
2. **eager 断点处的弱引用**：传入断点的 tensor 在图池已拥有其存储时用弱引用持有，避免不必要的 Python 引用延长 tensor 生命周期（这个技巧来自 vLLM #9724）。
3. **跨捕获尺寸共享输出缓冲**：所有捕获尺寸共享一个最大尺寸的输出缓冲，按形状切需要的行，而不是每个形状分配一个。

效果：42 个捕获形状 × 78 层 MoE，在 GLM-5.2 上只增加 2.4 GB 图内存。

更关键的是**捕获天花板**。图内存是常驻的（捕获时分配，服务生命周期内保留），eager 激活是瞬时的（每次 prefill 分配工作内存，最大 prefill 决定峰值）。如果捕获 ladder 的天花板低于 chunked_prefill_size，最大的 prefill 仍回退 eager，激活峰值不变——同时服务器还白付了所有常驻图内存。

只有捕获到 chunked_prefill_size，最大的 prefill 才回放图，激活峰值才会塌缩：gpt-oss-120b 上从 0.56 GB 降到 0.001 GB，GLM-5.2 上从 1.55 GB 降到 0.35 GB（稀疏注意力 indexer 仍在断点处 eager 运行）。总内存反而比无图基线低 0.51–1.10 GB。

![](https://pica.zhimg.com/v2-6b52d959ecec0864f7494bced6055534_r.jpg)

图6：Prefill 内存对比（在 chunked-prefill size 处执行一次 prefill 后测量）。捕获天花板达到 chunk size 时激活峰值塌缩，总内存低于无图基线。<br>

**六、BCG 独立成库**

BCG 的可断点捕获机制不绑定 SGLang。SGLang 团队和 Meta PyTorch 团队合作，把它提取成了独立库 meta-pytorch/breakable-cuda-graphs，提供 PyTorch 风格的 API：

- breakable_graph(...) 上下文管理器，类似 torch.cuda.graph
- @no_graph 装饰器，标记在图段之间 eager 执行的函数
- CUDAGraphSequence，按顺序回放捕获的图段和 eager 区域

如果上下文里没有 eager 断点，整个块会被捕获成单个图段——标准 CUDA Graph 模式是它的平凡情况。其他推理引擎、训练循环或研究原型都可以直接用这个库，不需要接入 SGLang 的 runner 栈。
