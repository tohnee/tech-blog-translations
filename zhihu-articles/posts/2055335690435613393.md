前几天，阶跃发布了JetSpec（[https://arxiv.org/html/2606.18394v2](https://arxiv.org/html/2606.18394v2)），DeepSeek发布了新的投机解码算法DSpark（[https://github.com/deepseek-ai/DeepSpec/blob/main/DSpark_paper.pdf](https://github.com/deepseek-ai/DeepSpec/blob/main/DSpark_paper.pdf)），接着[投机解码（一）：让大模型“少算几步”：从经典 Draft-Verify 到 DeepSeek MTP](https://zhuanlan.zhihu.com/p/2049921024117027828)，继续梳理一下二者在投机解码上的改进。

投机解码的基本思路，是让一个更便宜的 draft model 先往前猜一段，再让 target model 一次性验证这段猜测。只要验证规则设计正确，最终输出分布仍然和原始大模型逐 token 生成完全一致，用户看到的是“同一个模型的回答”，只是生成过程少走了很多步。

但真正难的地方不在“猜”，而在“猜得值不值得验”。

最近两个工作很有意思：阶跃星辰的 **JetSpec** 和 DeepSeek 的 **DSpark**。它们都不是简单地说“我一次多猜几个 token”，而是开始认真处理投机解码里的两个老问题：

1. 草稿生成得太慢，抵消加速收益；
2. 草稿生成得太粗，后半段 token 大量被拒，浪费验证算力。

这篇主要讲 DSpark，顺带把它和 JetSpec 的思路放在一起看。

## 一、投机解码的账本

先回顾一下投机解码的账本。

假设 target model 原本每一步只能生成 1 个 token。现在 draft model 先生成一串候选 token，例如 8 个，然后 target model 一次 forward 验证这 8 个。如果前 5 个都被接受，第 6 个被拒，那么这一步实际就前进了 5 个 token。

于是速度提升为 $C_{\text{per-token}}=\frac{C_{\text{draft}}+C_{\text{verify}}}{\mathbb{E}[A]}$ ，取决于3个量

- $C_{\text{draft}}$ 生成草稿的成本；
- $C_{\text{verify}}$ 验证草稿的成本；
- $\mathbb{E}[A]$ 平均每轮能接受多少 token。

换句话说，不是草稿越长越好。长草稿如果大部分都被拒，反而会浪费 target model 的 batch capacity。尤其在线上服务里，高并发请求共享 GPU batch，大量低质量草稿 token 被送去验证，会挤占别的请求。

早期方案大致有两类。

第一类是 **autoregressive drafter**，比如 EAGLE 系列、MTP 风格方案。它们逐 token 生成草稿，后一个 token 可以依赖前一个 token，因此草稿质量较高，接受率不错。但缺点也很明显：草稿本身还是串行的，候选块越长，draft latency 越高。

第二类是 **parallel drafter**，例如 DFlash 一类方案。它希望一次 forward 直接生成多个未来位置的 token。这样草稿生成很快，块长可以拉大。但问题是，不同位置之间缺少块内依赖。第 1 个 token 看起来合理，第 2 个 token 单独看也合理，拼在一起可能就不合理。越往后，错误会累积，接受率快速衰减。例如Of + course 或者No + problem都是合理的，但是Of + problem就不合理了。

所以投机解码走到这里，矛盾变成了：

> 我们既想要并行草稿的速度，又想要自回归草稿的条件依赖。

DSpark 和 JetSpec 都是在解决这个矛盾，只是切入点不同。

## 二、DSpark

DSpark 的论文有两个关键词：

- **Semi-Autoregressive Generation**：半自回归生成；
- **Confidence-Scheduled Verification**：基于置信度调度的验证。

---

### 优化 $C_{\text{draft}}$ ：半自回归优化，不是重新串行生成

先看第一个 **半自回归，**可以粗略理解成两步：

1. 并行 backbone 一次性给出多个未来位置的基础 hidden states / logits；
2. 一个轻量 sequential head 从左到右扫一遍，为每个位置注入块内前缀信息。

这就是“半自回归”的含义：主体计算是并行的，只有很轻的输出修正是顺序的。

它和纯自回归 draft model 的区别在于，DSpark 并不是每生成一个 token 都重新跑一遍完整 draft network。串行部分只是一个很薄的 head，用来补充 token 之间的局部转移关系。

论文里提到两种 head：

- **Markov head**：主要依赖前一个 token，建模相邻 token 的转移关系；
- **RNN head**：维护循环状态，累积更长的块内历史。

从工程角度看，Markov head 更轻、更好部署，所以 DSpark 默认采用 Markov head。RNN head 表达力更强，但收益和复杂度之间未必划算。

---

### 优化 $C_{\text{verify}}$ ：过target model之前过滤一遍

第二个重点是 **confidence-scheduled verification**。

传统投机解码通常会固定验证一个长度，例如每轮都验证 8 个或 16 个 draft token。但这在线上服务里并不总是最优。

原因很简单：每个位置的通过概率不同。

一般来说，草稿块越往后，接受概率越低。前几个 token 值得验，后几个 token 可能大概率会被拒。系统空闲时，多验几个也无妨；系统繁忙时，把宝贵 batch capacity 花在低通过率 token 上，就会拖垮整体吞吐。

DSpark 因此给每个 draft token 预测一个置信度，可以理解为：

> 在前面 token 都被接受的条件下，当前位置 token 继续被接受的概率是多少。

然后调度器根据这些置信度，以及**当前服务负载和硬件状态**，动态决定每个请求到底送多少个 token 去 target model 验证。（**笔者在这里对Deepseek的务实精神叹服，这里软硬结合的方式是普通大模型算法工程师所忽视的**）

这一步很关键。因为 DSpark 不只是一个模型结构改进，也是一个 serving 策略改进。

在低负载场景下，系统可以更激进，多验证一些 token，追求单用户低延迟；在高负载场景下，系统可以更保守，只验证最有希望通过的前缀，避免无效 token 占用 batch。

论文还提到，原始 confidence head 容易过度自信，因此需要做后验校准，例如顺序温度缩放。这个细节很工程，但很重要。因为调度器依赖置信度的绝对值，如果概率整体偏高，就会误判吞吐收益，导致验证过长。

---

### 和 DeepSeek MTP 的关系：从单 token 推测到块级推测

DeepSeek 之前在 V3 里已经用过 MTP，也就是 multi-token prediction。MTP 本身可以用于训练，也可以用于推理时的投机解码。

DSpark 相当于在 MTP 思路上继续往前走：

- 不只预测一个未来 token，而是构造一段候选块；
- 不用完整自回归方式生成这段候选，而是用并行 backbone 降低 draft cost；
- 不盲目验证整段候选，而是用 confidence scheduler 决定验证前缀长度。

所以 DSpark 的进步不只是“draft model 更强”，而是把投机解码拆成了一个更完整的系统问题：

> 草稿怎么生成，草稿多长合适，哪些草稿值得验证，服务负载变化时如何调整。

论文和公开报道里提到，在同等系统吞吐规模下，DSpark 让 DeepSeek-V4-Flash 的单用户生成速度提升约 60%-85%，V4-Pro 提升约 57%-78%。这些数字的意义在于，它不是只在离线 benchmark 上测一个漂亮接受率，而是已经进入真实服务流量验证。
