## 0. 引言

前两篇解决了两个问题：参数和梯度分别存在哪里（第一篇），以及它们在前向/反向过程中如何被管理（第二篇）。本篇聚焦最后一个环节：**梯度从 `averaged_gradients` 出发，如何经过反缩放、裁剪、Adam 更新，最终写回 BF16 权重分片**。

`step()` 的核心设计思想只有一句话：**逐 sub_group 串行推进**。每次只把一个 sub_group 的梯度转成 FP32、执行 Adam、再释放，峰值额外显存始终只有一个 sub_group 的 FP32 梯度，而不是所有参数梯度的总和。

## 1. `step()` 整体结构

先给出全局地图，再逐节深入。

![](https://pic3.zhimg.com/v2-eab8c8a4a3c1f665c37f6b04a8a6bdb0_r.jpg)

```text
def step(self, closure=None):
    self._pre_step()                          # 状态重置、计时器初始化
    self._partition_all_parameters()          # 兜底：强制释放所有残留完整参数

    if self._overflow_check_and_loss_scale_update():
        return                                # 梯度溢出：跳过本次更新，loss_scale 下调

    norm_groups = self._get_norm_groups()
    scaled_global_grad_norm = torch.linalg.vector_norm(torch.stack(norm_groups))

    for sub_group_id in range(len(self.fp16_groups)):
        self._prepare_sub_group(sub_group_id)           # BF16 梯度 → FP32
        self.unscale_and_clip_grads(sub_group_id, scaled_global_grad_norm)
        self._optimizer_step(sub_group_id)              # Adam in-place 更新
        self._reassign_or_swap_out_partitioned_parameters(sub_group_id)  # FP32 → BF16
        self._release_sub_group(sub_group_id)           # 释放 FP32 梯度

    self._post_step()
```

整个 `step()` 可以分为四个阶段：

| 阶段 | 函数 | 核心动作 |
| --- | --- | --- |
| 前处理 | _partition_all_parameters | 兜底释放残留完整参数，确保显存回到静态格局 |
| 全局范数 | _get_norm_groups | BF16 梯度 → AllReduce → scaled_global_grad_norm |
| 逐 sub_group | 五步循环 | BF16→FP32 → unscale+clip → Adam → FP32→BF16 → 释放 |
| 后处理 | _post_step + 监控 | 计时统计、显存压力监控 |

---

## 2. 前处理：为什么需要兜底释放

`step()` 开头调用 `_partition_all_parameters`，强制把所有还处于完整形态的参数归还为分片形态。

正常情况下，反向传播结束后 Post-Backward Hook 会释放每层的完整参数，显存已回到静态格局。但有一种情况会漏掉：**某个模块的所有输入 tensor 都是 `requires_grad=False`**，这时 `PostBackwardFunctionModule` 根本不会进入计算图，自然也不会触发，完整参数就会一直残留在显存里。

`release_and_reset_all` 内部处理三种状态的参数：

```text
for param in iter_params(module, recurse=True):
    if param in self.__inflight_param_registry:
        self.__inflight_param_registry.pop(param).wait()  # INFLIGHT：等待通信完成
    param.ds_active_sub_modules.clear()                   # 强制清空活跃子模块引用
    self.__release_param(param)                           # → partition()，NOT_AVAILABLE
```

执行完毕后，第二轮遍历全量断言所有参数都是 `NOT_AVAILABLE`，否则直接抛异常——这是一道硬性防线，确保进入逐 sub_group 循环时显存格局是干净的。

## 3. 全局梯度范数：三个设计决策

范数计算发生在逐 sub_group 循环之前，`get_grad_norm_direct` 的核心逻辑是：

```text
# 每个 rank 计算自己持有的梯度分片的 L2 范数平方
for g, p in zip(gradients, params):
    if is_model_parallel_parameter(p) or (self.model_parallel_rank == 0):
        grad_norms.append(g.to(device).double().norm(2))  # 临时转 double

total_norm_cuda = torch.sum(torch.pow(torch.stack(grad_norms), 2))

# AllReduce 求全局平方和，开根号得全局 L2 范数
dist.all_reduce(total_norm_cuda, op=dist.ReduceOp.SUM, group=self.dp_process_group)
total_norm = total_norm_cuda ** 0.5

# inf/nan 时返回哨兵值 -1.0，由溢出检查识别
inf_or_nan = total_norm.isnan().logical_or(total_norm.isinf())
return torch.where(inf_or_nan, torch.tensor(-1.0), total_norm)
```

这里有三个值得注意的设计决策：

**决策一：范数在 BF16 梯度上计算，临时转 double**

此时 `averaged_gradients[i]` 还是 `grad_partitions_flat_buffer` 的 BF16 视图，FP32 转换尚未发生。临时 `.double()` 是为了防止 BF16 精度下梯度平方累加的误差积累——BF16 只有 7 位尾数，大量小数平方相加很容易溢出或下溢。`double()` 只是临时的，不产生持久的 FP64 tensor。

**决策二：范数必须在 sub_group 循环之前完成**

梯度裁剪需要**全局**范数。如果在循环内部每个 sub_group 各自计算局部范数来裁剪，梯度各分量被不同比例缩小，方向发生偏转，训练会出现不稳定甚至发散。先做一次全局 AllReduce 拿到统一的 `scaled_global_grad_norm`，循环内所有 sub_group 用同一个裁剪系数，梯度向量才能被**等比例缩小**，方向不变。

**决策三：`norm_groups` 的两层聚合**

`_get_norm_groups` 返回的是每个 param_group 的全局范数列表，外层 `torch.linalg.vector_norm(torch.stack(norm_groups))` 再把多个 param_group 的范数合并为一个标量 `scaled_global_grad_norm`，这才是 `unscale_and_clip_grads` 的入参。

## 4. 单个 sub_group 的完整生命周期

以主路径（`offload_optimizer=False`，参数常驻 GPU）为例，一个 sub_group 从准备到释放经历五步，数据在各张量之间流动：

![](https://picx.zhimg.com/v2-ffafcef057228c3052a566d7c69c9623_r.jpg)

### 4.1 BF16 → FP32：`_prepare_fp32_grad_for_sub_group`

```text
# averaged_gradients[i] 是 grad_partitions_flat_buffer 的视图列表（BF16）
# flatten 拼接为一维 tensor，to(fp32) 完成类型转换
# ★ 整个训练链路唯一一次 BF16 → FP32 类型转换
single_grad_partition = self.flatten(self.averaged_gradients[sub_group_id]).to(
    self.fp32_partitioned_groups_flat[sub_group_id].dtype
)
self.fp32_partitioned_groups_flat[sub_group_id].grad = single_grad_partition

# 释放 BF16 视图引用，grad_partitions_flat_buffer 对应区段可被下一轮复用
self.averaged_gradients[sub_group_id] = None
```

这一步完成后，显存里新增了一块 FP32 梯度（约 `sub_group_size × 4 bytes`），同时 BF16 引用被释放。这是整个 sub_group 生命周期中**唯一的新显存分配**。

### 4.2 反缩放 + 梯度裁剪：`unscale_and_clip_grads`

混合精度训练中，反向传播产生的梯度是被 `loss_scale` 放大过的（`g_scaled = g_real × loss_scale`），使用前必须还原。如果同时需要梯度裁剪，两步可以合并为一次 `mul_`：

```text
combined_scale = self.loss_scale
if self.clip_grad > 0.:
    # real_norm = total_norm / loss_scale（还原真实梯度范数）
    # clip = real_norm / clip_grad，大于 1 时才需要裁剪
    clip = ((total_norm / self.loss_scale) + 1e-6) / self.clip_grad
    clip = torch.clamp(clip, min=1.0)
    combined_scale = clip * self.loss_scale

# 反缩放 + 裁剪合并为一次 in-place 乘法，无新分配
self.fp32_partitioned_groups_flat[sub_group_id].grad.mul_(1. / combined_scale)
```

`combined_scale` 的数学等价性：

```text
有裁剪时（real_norm > clip_grad）：
  result = g_scaled / (clip × loss_scale)
         = g_real / clip
         = g_real × (clip_grad / real_norm)   ← 标准梯度裁剪公式 ✓
```

`1e-6` 的作用是防止 `total_norm` 极小时浮点除法下溢，避免 `combined_scale` 变成 0 导致 `1/combined_scale` 为 inf。

### 4.3 Adam 更新：`_optimizer_step`

```text
param_group_id = self.sub_group_to_group_id[sub_group_id]
fp32_param = self.fp32_partitioned_groups_flat[sub_group_id]

# 动态填充：step() 瞬间填入，执行完立刻清空
self.optimizer.param_groups[param_group_id]['params'] = [fp32_param]
self.optimizer.step()   # exp_avg、exp_avg_sq、fp32_param 全部 in-place 更新
self.optimizer.param_groups[param_group_id]['params'] = []
```

`param_groups` 平时为空，是为了避免 PyTorch 优化器持有所有 sub_group 的参数引用，造成显存无法释放。动态填充保证每个 sub_group 的 FP32 权重只在更新瞬间被引用，其余时间引用计数为 0，可以精确控制显存生命周期。

优化器状态（`exp_avg`、`exp_avg_sq`）通过 `self.state[fp32_param]` 以对象 id 为 key 查找，`fp32_param` 的 Python 对象在整个训练中不变，动态填充/清空 `param_groups` 不会影响状态查找，不存在状态丢失的问题。

`sub_group_to_group_id` 映射保证多个 sub_group 共享同一个 param_group 的超参（lr、weight_decay 等）——一个大的 param_group 被 `sub_group_size` 切成多片后，各片使用相同的优化超参。

### 4.4 FP32 → BF16 + 视图重建：`_reassign_or_swap_out_partitioned_parameters`

```text
# FP32 → BF16，in-place copy_，无额外显存分配
self.fp16_partitioned_groups_flat[sub_group_id].data.copy_(
    self.fp32_partitioned_groups_flat[sub_group_id].data
)
# 重建 ds_tensor 视图
self._unflatten_partitioned_parameters(sub_group_id)
```

`_unflatten_partitioned_parameters` 是这一步容易被忽视的关键操作。`copy_` 把更新后的 FP32 数值写入了 `fp16_partitioned_groups_flat`，但各参数的 `ds_tensor` 还指向旧地址。`_unflatten_partitioned_parameters` 把 flat buffer 按各参数的 `partition_numel` 重新切片，赋回 `ds_tensor.data`，让视图关系重新成立：

```text
fp32_partitioned_groups_flat[i]
  ↓  .data.copy_()（FP32 → BF16）
fp16_partitioned_groups_flat[i]（连续 flat buffer，数值已更新）
  ↓  _unflatten_partitioned_parameters
param.ds_tensor.data = fp16_flat.narrow(offset, numel)（视图重建）
  ↓  下一轮 AllGather
all_gather_coalesced 读取 ds_tensor → 聚合完整参数（读到的是新参数 ✓）
```

💡 如果跳过 `_unflatten_partitioned_parameters`，`ds_tensor` 仍指向旧地址，下一轮 AllGather 聚合的是更新前的旧参数。训练照常运行，没有任何报错，但参数实际上从未被更新——这是一个极其隐蔽的正确性 bug。

### 4.5 释放 FP32 梯度：`_release_sub_group`

```text
# 主路径只有一行
self.fp32_partitioned_groups_flat[sub_group_id].grad = None
```

`.grad = None` 释放了 4.1 步里 `flatten().to(fp32)` 分配的那块 FP32 梯度显存。FP32 主权重本身（`fp32_partitioned_groups_flat[sub_group_id]`）不动，全程驻留 GPU。

## 6. 显存压力监控

`step()` 结尾有一个容易忽视但实际很有用的监控点：

```text
alloc_retries = get_accelerator().memory_stats().get("num_alloc_retries", 0)
if alloc_retries > self.n_caching_allocator_flushes:
    logger.warning("pytorch allocator cache flushes detected ...")
    self.n_caching_allocator_flushes = alloc_retries
```

`num_alloc_retries` 是 PyTorch CUDA 内存分配器的内部计数器，记录显存分配失败后触发缓存 flush 并重试的次数。这个数值增长意味着显存碎片化严重，分配器不得不清空缓存重新整理，会显著拖慢训练吞吐。

训练日志里频繁出现这条 warning 时，通常有两个方向可以调：`sub_group_size` 设置过大（峰值显存过高），或者激活值没有及时释放（建议搭配 gradient checkpointing）。

## 7. 调优参数速查

三篇内容涉及的核心调优参数汇总：

| 外部配置 | 默认值 | 控制的 tradeoff | 调大的效果 |
| --- | --- | --- | --- |
| sub_group_size | 1e9 | step() 峰值显存 vs IO 次数 | 峰值显存↑，IO 调用次数↓ |
| reduce_bucket_size | 5e8 | 梯度通信效率 vs 峰值显存 | AllReduce 效率↑，bucket 峰值显存↑ |
| prefetch_bucket_size | 5e7 | 单次预取量 vs 启动延迟 | 通信批次↓，单次启动延迟↑ |
| max_live_parameters | 1e9 | 预取激进度 vs 峰值显存 | 预取更激进，峰值显存↑ |
| max_reuse_distance | 1e9 | 共享参数保留时间 vs 显存 | 共享参数更可能被保留，显存↑ |
| param_persistence_threshold | 1e5 | 小参数通信开销 vs 常驻显存 | 更多小参数常驻显存，通信次数↓ |

**实际调优顺序建议**：先调 `sub_group_size`（控制 step 峰值），再调 `reduce_bucket_size`（控制反向峰值），最后调 `prefetch_bucket_size` 和 `max_live_parameters`（控制前向通信效率）。`param_persistence_threshold` 仅在有大量小参数层（如 LayerNorm、bias）时值得关注。

## 8. 三篇总结

至此，ZeRO-3 从初始化到参数更新的完整机制走读完毕。

| 阶段 | 关键操作 | 通信原语 | 显存变化 |
| --- | --- | --- | --- |
| 初始化 | partition()：分片存入 ds_tensor | Broadcast（对齐初始值） | 建立静态 1/N 分片格局 |
| 初始化 | defragment：ds_tensor → fp16_partitioned_groups_flat | 无 | 碎片化 → 连续大块 |
| 初始化 | clone().float()：BF16 → fp32_partitioned_groups_flat | 无 | FP32 主权重就位 |
| 初始化 | grad_partitions_flat_buffer 一次性 malloc | 无 | 梯度 buffer 就位 |
| 前向（每层） | AllGather → 计算 → partition() | AllGather（Trace 预取隐藏） | 峰值 ≈ 静态 + 1~2 层完整权重 |
| 反向（每层） | AllGather → 梯度计算 → partition() | AllGather | 同上 + grad bucket |
| 反向（梯度归约） | 入桶 → AllReduce/ReduceScatter → copy_ 写入 flat buffer | AllReduce / ReduceScatter | grad bucket 清空，梯度分片落地 |
| step 前处理 | 兜底释放残留完整参数 | 无 | 显存回到静态格局 |
| step 范数计算 | BF16 梯度 → local norm → AllReduce | AllReduce（一次） | 无新分配 |
| step 逐 sub_group | BF16→FP32 → unscale+clip → Adam → FP32→BF16 → 释放 | 无 | 峰值额外 = 1 sub_group FP32 梯度 |

ZeRO-3 的本质是一个彻底的 tradeoff：**用通信换显存，用复杂的 Hook 系统换对用户代码的零侵入**。每个 rank 长期只持有 1/N 的参数、梯度和优化器状态，仅在计算发生的瞬间临时聚合完整参数，用完立刻归还。代价是每次 forward/backward 都引入额外的 AllGather，以及 step 前的一次梯度范数 AllReduce。

理解了这套机制之后，CPU/NVMe offload、gradient checkpointing 与 ZeRO-3 的交互，以及 Swift 框架在 RLHF 场景下的多模型显存管理，都会有更清晰的脉络。
