看完这篇文章，你会知道：KV Cache 到底缓存了什么、公式里每个因子从哪来、怎么用一个数字心算显存、以及为什么这个数字直接决定了你的 vLLM 能开多大并发。

### 一、KV Cache 缓存的到底是什么

先破除一个常见误解:KV Cache **不是**缓存注意力的输出结果,也**不是**缓存整个 hidden state。***它缓存的,是每一层里历史 token 的 K 向量和 V 向量。***

为什么是 K 和 V,不包括 Q?回到注意力的计算式。生成第 t 个 token 时:

```text
attn = softmax(q_t · K^T / √d) · V
```

这里 `q_t` 只有当前这一个 token 的查询向量,而 `K`、`V` 需要包含**前面所有 token** 的。

关键在于因果掩码(causal mask)保证了:第 i 个 token 的 `k_i`、`v_i` 只依赖它自己位置上的输入,后续生成的 token 不会回头改变它们。既然算过一次就永远不变,那就存下来,下一步直接拼接复用,把每步 O(t) 的重复计算变成 O(1)。

而 `q_t` 是用完即弃的。它只参与当前这一步的打分,下一步会有新的 `q_{t+1}`,历史 query 再也用不到。

所以缓存里存的是两份,不是三份:

```text
第 l 层的 KV Cache:
  K = [k_1, k_2, ..., k_t]
  V = [v_1, v_2, ..., v_t]
```

生成第 t+1 个 token 时,只需要算 `q_{t+1}, k_{t+1}, v_{t+1}`,然后拼上去:

```text
K_cache = [k_1 ... k_t, k_{t+1}]
V_cache = [v_1 ... v_t, v_{t+1}]
```

历史 token 的 K/V 一次都不用重算。这就是 KV Cache 的全部作用。

### 二、公式:六个因子各自从哪来

完整的公式长这样:

```text
元素个数 = B × S × L × 2 × H_kv × d_head
字节数   = 元素个数 × 每元素字节数
```

六个因子,一个个拆。

### 2 —— K 和 V

上面已经讲了,只有这两个需要存。

### H_kv × d_head —— 每个 token 在一层里占多大

每个注意力头都独立维护自己的一套 K/V。单个头里,一个 token 的 key 是长度 `d_head` 的向量,value 也是 `d_head`。所以:

```text
一个 token、一层、一个 KV 头 = 2 × d_head
一个 token、一层、全部 KV 头 = 2 × H_kv × d_head
```

实际张量形状是每层两个 `[B, H_kv, S, d_head]`,把 B 和 S 抽掉就剩这个。

**这里有个坑**:MHA 下 `H_kv × d_head` 恰好等于 `hidden_size`,所以很多人记成「每 token 每层 2 倍隐藏维」。但 GQA 一来这个等式就断了 —— 后面单独讲。

### L —— 为什么要乘层数

注意力是每层各算各的」到底什么意思?

意思是**每一层都有自己独立的一套 `W_Q / W_K / W_V`**。第 1 层的 W_K 和第 2 层的 W_K 是两个完全不同的矩阵,训练时各学各的。

流程是这样的:token embedding 进入第 1 层,第 1 层用它自己的 W_K、W_V 算出一组 K/V,做完注意力和 FFN 后输出一组新的隐状态;这组新隐状态成为第 2 层的输入,第 2 层用它自己的 W_K、W_V **重新算一遍** K/V。

关键在于:第 2 层的输入已经不是原始 embedding 了,而是被第 1 层加工过的向量。所以哪怕两层的权重碰巧一模一样,算出的 K/V 也不同。层与层之间没有任何复用的可能。

一个 32 层的模型,推理时是这样跑的:

```text
新 token
   ↓
第 1 层:算 Q1/K1/V1 → 读 KV Cache_1 → 注意力 → 把 K1/V1 追加进 Cache_1
   ↓
第 2 层:算 Q2/K2/V2 → 读 KV Cache_2 → 注意力 → 把 K2/V2 追加进 Cache_2
   ↓
  ...
   ↓
第 32 层:算 Q32/K32/V32 → 读 KV Cache_32 → 注意力 → 追加
   ↓
输出 logits
```

一次生成一个 token,本质上就是这个 token 依次穿过所有层,每一层读取**自己那份**缓存,再把新的 K/V 加进去。

所以:**注意力是每层各算各的,KV Cache 也是每层各存各的**。32 层就是 32 份互不相干的缓存,直接乘。

反过来想:如果 K/V 真能全层共享,`L` 就不该出现在公式里,缓存大小会和模型深度无关。显然不是这样 —— 深度是直接乘进显存的。

### B × S —— 为什么是纯线性

每个 token 在缓存里占一个固定大小的槽位,序列之间互不干扰。第 1000 个 token 和第 1 个 token 占的空间一模一样,不会因为位置靠后就变大。

所以对 batch 和序列长度都是严格线性。这也是长上下文难做的根本原因:参数量是**固定成本**,KV Cache 是随 `B × S` 增长的**变动成本**。

### 每元素字节数

FP16/BF16 是 2,FP32 是 4,FP8/INT8 是 1。注意 **KV Cache 的 dtype 可以和权重 dtype 不同** —— FP8 KV 量化是很常见的省显存手段,vLLM 里对应 `--kv-cache-dtype fp8`,能直接把这块显存砍半。

### 三、代码实现

把上面的推导写成函数:

```text
def estimate_kv_cache_size(model_config: dict, batch_size: int, seq_len: int) -> dict:
    """
    估算 Transformer 推理时 KV Cache 的显存占用。

    elements = B × S × L × 2 × H_kv × d_head   (这个 2 是 K 和 V)
    """
    num_layers = model_config['num_layers']
    num_heads = model_config['num_attention_heads']
    num_kv_heads = model_config.get('num_kv_heads', num_heads)  # 缺省即 MHA
    head_dim = model_config['hidden_size'] // num_heads         # 由 query 头数推出
    dtype_bytes = model_config['dtype_bytes']

    # 一个 token、一层、全部 KV 头
    per_token_per_layer = 2 * num_kv_heads * head_dim

    elements = batch_size * seq_len * num_layers * per_token_per_layer
    total_bytes = elements * dtype_bytes

    return {
        'kv_cache_elements': elements,
        'kv_cache_size_bytes': total_bytes,
        'kv_cache_size_mb': round(total_bytes / 1024**2, 4),
        'per_layer_size_mb': round(total_bytes / num_layers / 1024**2, 4),
        'per_token_size_kb': round(
            num_layers * per_token_per_layer * dtype_bytes / 1024, 4
        ),
    }
```

几个实现细节值得说明。

**`head_dim` 必须用 query 头数去除**,不能用 KV 头数。GQA 里 KV 头是被「复制」去匹配 query 头的,单头维度由 query 侧定义。如果误写成 `hidden_size // num_kv_heads`,GQA 省下的显存会被这个错误的除法悄悄抵消掉,算出来和 MHA 一样。

**`//` 和 `/` 的区别是有意的**。`head_dim` 用地板除保证是 int,后面参与元素个数计算;而 MB/KB 换算用真除法 `/`,它在 Python 3 里永远返回 float,所以能得到 `18.0` 而不是 `18`。

**`per_token_size_kb` 故意不乘 batch 和 seq_len**。它是「一个序列里多加一个 token 的边际成本」,这个数字才是估算上下文能撑多长时的核心。而 `per_layer_size_mb` 保留 batch,因为它是实际分配的一个切片。

**`round(x, 4)` 用的是银行家舍入**(round half to even),`round(2.5)` 得 2 不是 3。这里因为字节数基本都是 2 的幂的倍数,除以 1024 后往往能精确表示,第 4 位小数没有歧义,所以不用担心。

验证一下 GPT-2 small(12 层 / 12 头 / hidden 768 / FP16),batch 1、512 token:

```text
{'kv_cache_elements': 9437184, 'kv_cache_size_bytes': 18874368,
 'kv_cache_size_mb': 18.0, 'per_layer_size_mb': 1.5, 'per_token_size_kb': 36.0}
```

### 四、记住一个数字:512 KiB

真正实用的不是公式,是一个能心算的锚点。

拿 Llama-2-7B 的形状:**32 层,32 个 KV 头,head_dim 128,FP16**。

```text
每 token 每层 = 2 × 32 × 128 × 2 bytes = 16 KiB
每 token 全部 = 16 KiB × 32 层        = 512 KiB
```

**每个 token 半兆显存。** 记住这一个数,后面全是心算:

| 场景 | KV Cache |
| --- | --- |
| 单条 2048 token | 1 GiB |
| 单条 4096 token | 2 GiB |
| batch 32 × 2048 | 32 GiB |
| 单条 128k 上下文 | 64 GiB |

回到开头那个面试题:7B 权重 FP16 占 13.5 GiB,看着 80G 显存绰绰有余。但 batch 开到 32、上下文 2048,KV Cache 就是 32 GiB —— 已经是权重的两倍多了。想跑 128k 上下文?单条序列 64 GiB,一条都够呛。

这就是为什么「显存够不够」这个问题,答案几乎从不取决于权重。

### 五、GQA / MQA:唯一能改变这个数字的架构手段

上面 512 KiB 是 MHA 的代价。GQA(Grouped-Query Attention)的想法很简单:**多个 query 头共享同一份 K/V**。

Llama-3-8B 的配置是 32 个 query 头、8 个 KV 头(4:1)。查询侧的表达力完全不变,但缓存只需要存 8 组:

```text
每 token 每层 = 2 × 8 × 128 × 2 = 4 KiB
每 token 全部 = 4 KiB × 32 = 128 KiB
```

**直接降到 1/4。** 同样的显存能装四倍的 token,或者四倍的并发。

MQA 是极端情况,`H_kv = 1`,压缩比等于 query 头数。省得更狠,但质量损失明显,所以现在主流是折中的 GQA。

压缩比就是 `H_q / H_kv`,一眼可算。这也是为什么代码里 `num_kv_heads` 缺省要 fallback 到 `num_attention_heads` —— 老模型的 config 里没这个字段,默认就是 MHA。

大模型上效果更夸张。Llama-3-70B 是 80 层、64 query 头、8 KV 头、head_dim 128:

```text
每 token = 2 × 8 × 128 × 2 × 80 层 = 320 KiB
```

batch 8 × 8192 token = 20 GiB。如果没有 GQA,同样配置是 **160 GiB** —— 单卡直接放弃。

### 六、从这个数字到 PagedAttention

理解了「KV Cache 是按 token 线性增长的」,才能理解 vLLM 在解决什么问题。

**vLLM 之前的做法**:给每个序列预留一整块**连续显存**,按 `max_seq_len` 分配。一条实际只生成了 100 个 token 的请求,如果 `max_seq_len=4096`,照样占着 2 GiB。三种浪费同时发生:

- **内部碎片**:预留了但没用到的部分,往往是大头
- **外部碎片**:连续块之间的空隙装不下新序列
- **无法共享**:同一个 system prompt 被 10 个请求复用,K/V 却存了 10 份

**PagedAttention 借了操作系统虚拟内存的思路**:把缓存切成固定大小的 **block**,每个 block 存 `block_size` 个 token。用 Llama-2-7B 的数字,`block_size=16` 时一个 block 是:

```text
16 tokens × 16 KiB/层 × 32 层 = 8 MiB
```

序列不再需要连续显存,只需要一张 **block table** 记录「我的第 3 段 K/V 在物理块 #729」。浪费被压到每条序列最多不到一个 block(平均半个,约 4 MiB),对比原来动辄 1–2 GiB 的预留,显存利用率从 20–40% 提到 96% 以上。

顺带解锁两件事:

- **前缀共享**:多个请求共享同一段 prefix 时,直接指向同一批物理块,写入时才 copy-on-write
- **并行采样**:一个 prompt 出 n 个候选,prompt 部分只存一份

**vLLM 启动时打印的 `# GPU blocks: xxxx` 就是这么算出来的**:

```text
可用显存  = 总显存 × gpu_memory_utilization − 权重 − 激活峰值
num_blocks = 可用显存 / (block_size × 每token每层字节 × 层数)
```

80GB A100 跑 7B,`utilization=0.9` 大约剩 58 GiB,除以 8 MiB 得到约 7400 个块,即能同时缓存约 **11.8 万个 token** —— 折合 2048 上下文下的 58 条并发。

如果你把 `--max-num-seqs` 调到超过这个数,调度器不会变快,只会排队或者触发抢占(把某些序列的块换出到内存再换回来),吞吐反而下降。

所以这个手算结果,本质上就是**你这台机器的并发上限**。调参之前先算一遍,比盲试有效得多。

### 七、公式什么时候会失效

前面的公式覆盖绝大多数主流模型,但有几种情况需要修正,列出来避免踩坑。

**滑动窗口注意力(SWA)。** Mistral、Gemma 这类模型每层只保留最近 W 个 token,`S` 要换成 `min(S, W)`。一个 128k 上下文配 4k 窗口,缓存只按 4k 算。更麻烦的是有些模型是混合的(部分层全局、部分层滑窗),得逐层算。

**MLA(DeepSeek-V2/V3)。** 缓存的不是 per-head 的 K/V,而是一个压缩后的低秩隐向量,解码时再投影回来。公式完全不同,压缩比可以到几十倍。用上面的函数去估 DeepSeek 会严重高估。

**跨层共享(CLA / YOCO)。** 前面说「层与层之间没有复用的可能」,那是指标准架构。CLA 让相邻几层共享同一份 K/V,YOCO 只在一层算 K/V 供后面所有层复用 —— 这些方法的目标正是把公式里的 `L` 换成一个更小的数。

**分页的 block padding。** vLLM 会把每条序列向上取整到 block 边界,实际占用比理论值多几个百分点。估容量时留点余量。

**别忘了还有别的东西在吃显存。** 激活峰值、CUDA graph、NCCL buffer、框架自身开销,都在 `gpu_memory_utilization` 那 10% 里。所以 vLLM 默认留 0.9 而不是 0.95。

### 最后

整篇文章其实就围绕一行公式:

```text
B × S × L × 2 × H_kv × d_head × dtype_bytes
```

但真正有用的是三件事:

1. **知道每个因子从哪来**,这样看到新架构(GQA、SWA、MLA)时能立刻判断哪个因子被改了
2. **记住一个锚点数字**,比如 7B MHA 的「每 token 512 KiB」、8B GQA 的「128 KiB」,现场心算
3. **知道这个数字通向哪里** —— 它就是 PagedAttention 的 block 大小、就是 vLLM 的 `# GPU blocks`、就是你的并发上限

部署时先花两分钟把这笔账算清楚,能省掉后面两小时的 OOM 调参。
