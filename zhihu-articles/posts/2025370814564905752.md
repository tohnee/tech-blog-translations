AI Agent长周期运行会带来的“上下文爆炸”问题，因此需要对上下文做工程化的管理，本文将聚焦于上下文工程中的第一大策略：上下文筛选。

## 上下文筛选的目标

根据多项针对AI Agent执行长轨迹任务（如SWE-bench测试集）的实证研究，在Context中，Token的消耗比例呈现出极度不均衡的分布。

[The Complexity Trap: Simple Observation Masking Is as Efficient as LLM Summarization for Agent Context Management](https://arxiv.org/abs/2508.21433) 这篇论文中的统计表明，在未经过优化的“原生Agent（Raw Agent）”中，Observation（观察，即工具返回的结果与环境反馈）约占 83.9%：

![](https://pic2.zhimg.com/v2-2890855ad5cabc4c7de6164fd74b09fb_r.jpg)

另一项研究 [SWE-Pruner: Self-Adaptive Context Pruning for Coding Agents](https://arxiv.org/abs/2601.16746) 也有类似的结论，在编程Agent的各项操作中，“读取信息（Read）”操作占到了所有Token开销的 76.1%：

![](https://pic4.zhimg.com/v2-600b40e31b5c1b696cf343ab6c1b8239_r.jpg)

这就给我们指明了明确的优化方向：上下文筛选的首要目标，就是对庞大的“Observation（外部输入/工具输出）”进行精准过滤，同时避免在初始的 System Prompt 中硬塞入过多的冗余背景和全量工具定义。

## RAG (Retrieval-Augmented Generation)

当前工业界最成熟、最广为人知的上下文筛选技术就是 RAG（检索增强生成）。

### RAG的一般流程

RAG的核心逻辑并不复杂，一句话可以概括为： **“先检索再生成”** 。当用户提出需求时，系统不会直接让大模型直接去生憋答案，而是先将用户的Query转化为检索指令，去外部资料库中捞取相关信息，然后将这些信息拼接成一段精简的Context喂给大模型。

“Retrieval-Augmented Generation”（简称 RAG）这个命名最早是在 2020年 的一篇经典论文中 [Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks](https://arxiv.org/abs/2005.11401) 正式提出来的，论文中提出：在解决知识密集型的问答任务上，需要结合两种记忆：

- 参数化记忆（Parametric memory）：利用预训练的生成式语言模型（论文中使用的是 BART 模型）将知识存储在模型权重中
- 非参数化记忆（Non-parametric memory）：利用外部知识库（论文中将维基百科转化为密集向量索引，通过 DPR - Dense Passage Retriever 进行检索）

![](https://picx.zhimg.com/v2-76aac7dce473146ec80f44a650a18311_r.jpg)

这篇论文证明了将检索模型和生成模型结合后，能够让模型在无需重新训练底层参数的情况下，直接获取最新知识，在开放域问答（Open-domain QA）等“知识密集型”任务上达到了当时的SOTA水平，同时大幅降低了模型凭空捏造事实（幻觉）的概率。

值得一提的是，因为“RAG”这个词在英语中原本是“破布、碎布”的意思，并不是一个很优雅的缩写。论文的第一作者 Patrick Lewis 后来在一次会议演讲时曾半开玩笑地透露过遗憾：“如果早知道这项技术后来会被采用得这么广泛，我们当初一定会给它起一个更好听的名字。” 但无论如何，这个名字和它代表的架构已经成为了当今大模型时代最为核心和普及的技术之一。

> “We would have chosen a better name had we anticipated its widespread adoption,” he stated during a conference in Singapore while presenting his ideas at a regional database developers conference. ‘We always intended a more appealing name, but when it came time to write the paper, nothing better came to mind.’ he further stated.

### 基于向量检索的RAG

基于向量的检索是RAG最常见的形式。它擅长处理语义相关性的匹配。

### 基于关键词检索的RAG

尽管向量检索在“模糊语义”上表现优异，但在某些极其强调精准匹配的场景下，基于关键词的词法检索（如BM25、Grep）却更加高效和可靠，Coding Agent就是这样一个场景。

Coding Agent最常做的就是代码检索，代码检索与知识库检索的最大差异是：代码天然存在可精确匹配的符号、字符串与结构（import 路径、函数名、错误栈、配置 key）。因此很多代码 Agent 并不总是需要向量库；相反，“先用关键词/模式检索锁定范围，再 Read 精读”往往更稳。

Claude Code 提供了内置工具 Glob（按模式找文件）与 Grep（在文件内容中搜索模式），并把这些工具名用于权限规则、子代理工具列表等配置；这本质上就是一套“关键词检索→候选文件→读取证据→生成/修改”的检索增强工作流。

### 万物皆可RAG：Tool RAG与Memory RAG

RAG的理念不仅可以用来搜文档/代码，在Agent的设计中，“万物皆可RAG”。

**挑选工具（Tool RAG）**

随着Agent能力的扩展，它可能掌握成百上千个工具（航班API、酒店API、天气API、打车API、翻译API等）。如果把这些工具的Description全部塞进System Prompt，可能仅工具列表就会吃掉一万个Token。Tool RAG的解法是，Agent在规划出“我要去订餐厅”后，利用检索系统去“工具库”里查询“餐厅预订”，此时只有 Restaurant_Booking_API 的Schema会被注入到当前的Context中。

**挑选记忆（Memory RAG）**

用户和Agent可能相伴了几个月，积累了海量的Dialogue History。如果把“Agent一生的经历”全部放入上下文，大模型必定会崩溃。Memory RAG的解法是，当开始规划本次杭州行时，Agent触发检索，从长期记忆库中捞出：“用户对海鲜过敏”、“上次去成都时，用户抱怨每天早上8点起太累了”。仅将这几条记忆放入本次的Context。

当然，无论是Tool RAG还是Memory RAG，也都有关键词检索和向量检索两种可选的实现方案。

## 渐进式的按需加载（progressive Disclosure）

### 为什么要引入渐进式的按需加载？

RAG用到的文本转向量模型，通常是一个小参数量的模型，这意味着，大模型的能力的提升无法直接提升检索这一步的效果，而小模型由于参数量的限制，检索能力的上限非常有限。

为了解决上述问题，业界提出了渐进式的按需加载来做上下文筛选。渐进式按需加载采用了一种“分层过滤”的哲学：把上下文拆成层级，只在必要时加载更重的内容。这种分层机制确保了 Agent 始终维持在最低的“认知负荷”状态，同时具备按需获取无限知识的能力。

### MCP Zero：按需发现并动态加载工具

MCP-Zero就是这一理念的研究成果，它把这个思想应用在MCP工具选择问题上。

以GitHub的MCP工具集为例，所有GitHub相关工具加起来超过4600个Tokens。过去我们习惯把所有可用的工具Schema（如JSON格式的API描述）全部塞进Prompt里，导致Token爆炸且容易产生幻觉。

RAG的做法，则容易带来工具选择不准确，尤其是在多轮对话的场景下，原始的单句用户query表达未必完整准确。

而MCP-Zero的做法是，当Agent遇到模糊需求时，它会输出类似 “I need a tool to manage code repositories”。此时系统调用一个极轻量的Search Engine，向Agent返回相关工具的简要描述（Description）。Agent读了描述后，觉得自己确实需要，才会去发起真正的“加载（Load）”动作，将那几千个Token的详细使用说明和API格式拉入当前的Context。这就是按需加载。如果觉得这个工具不需要，则重新请求。MCP Zero的做法可以概括为： **Agent 分析任务 -> 发现能力缺失 -> 发起工具请求 -> 系统检索工具并返回 -> Agent 评估工具是否好用，不好用则重新请求**

![](https://pic1.zhimg.com/v2-d19eac4b43433d20a93ea60fae87f0ec_r.jpg)

MCP-Zero相对RAG的改进已经比较全面了，但是后来并没有像Skills的做法那么流行。

### Skill.md: 渐进式按需加载的行业规范

Skill.md 在2025年底由Anthropic、Vercel等共同推动，迅速成为面向开发者的标准。它将Agent视为一个“新入职的员工”，需要一份“操作手册”。它是一个纯文本/Markdown驱动的标准，存放在项目本地（例如 .claude/skills/SKILL.md）

一个标准的Skill文件通常不仅是一串代码，而是一份“人类和AI都能读懂的说明书”，包含三层架构规范：

1. YAML Frontmatter（元数据层）：技能名称和简要描述。常驻大模型上下文。负责告诉模型“我是谁”和“什么时候该用我”。
2. Markdown 核心指令层：仅在技能被触发时加载进上下文。通常包含标准化、可追踪的 Workflow 清单。
3. 外部资源层（可选）：配套的 scripts/assets/reference，仅靠工具按需读取。

以“杭州3日家庭游”为例的Skill.md示例，假设系统中存在一个 Book_Restaurant.md 的技能文件：

```text
---
name: book-restaurant
description: 用于预订热门餐厅。当用户在规划旅行并明确提到需要安排餐饮、预订餐厅，或者提到“吃饭”、“聚餐”、“美食”等相关需求时，必须无条件触发此技能进行处理。
---

# 餐厅预订执行指南

本技能旨在帮助你遵循标准且安全的流程，为用户预订杭州本地的优质餐厅，特别是针对家庭游/亲子游场景。

## Prerequisites (前置条件)
在执行预订工作流之前，你**必须**确保已从 Memory 或目前的对话历史（Dialogue History）中获取了以下关键信息。如果信息缺失，请主动向用户提问补齐，不要自行捏造：
1. **用餐人数 (Party size)**: 需要具体数字，并特别注意是否包含儿童或老人。
2. **饮食禁忌 (Dietary restrictions)**: 必须严格确认是否有过敏史（如海鲜过敏、坚果过敏、忌口等）。
3. **用餐时间 (Time)**: 确认是午餐、晚餐还是具体的到店时间段。

## Workflow (工作流)
为了保证任务的准确执行，请复制以下 Checklist 并在你输出的回复中通过勾选来追踪你的进度：

预订进度追踪：
- [ ] Step 1: 确认所有前置条件 (Prerequisites) 已集齐。
- [ ] Step 2: 搜索高分餐厅 (调用 Search_Restaurant 查找评分 > 4.5 的餐厅)。
- [ ] Step 3: 饮食禁忌排查 (严格对比餐厅特色与用户的 Dietary restrictions)。
- [ ] Step 4: 执行预订 (调用 Confirm_Booking_API 提交订单)。
- [ ] Step 5: 向用户输出最终的确认信息与预订凭证。

......
```

那么，基于上面的Skill.md，Agent如何基于Skills实现渐进式按需加载呢？

- 第一层（目录浏览）：Agent的初始Context里，只有极其精简的技能目录清单。也就是启动时system prompt中只加载每个 skill 的 name/description（很省 token）。它看到有一条叫 Book_Restaurant，知道可以用来订饭，但是具体如何预订，Agent此时是不知道的。
- 第二层（阅读说明书）：当任务与 description 匹配到某个 skill，再加载完整 SKILL.md body（工作流细节、注意事项）。例如，Agent决定订饭，于是它触发一个 Read(Book_Restaurant.md) 的动作。此时，这篇Skill.md的内容才被加载进Context。
- 第三层（动作执行）：Agent按 SKILL.md 的指令去最终调用工具并交付最终的产物。在这个过程中，可能需要阅读更多的信息，如scripts/assets/reference等。

![](https://pica.zhimg.com/v2-11188f9c9cdb1d14466318fa8180700c_r.jpg)

这种按需披露的方式，使得 Agent 的有效 Context 始终集中在当前的执行逻辑上，彻底告别了“信息轰炸” 。

## 总结

本文聚焦AI Agent上下文工程的核心策略： **上下文筛选** 。为解决Agent在长周期任务中高达80%的“观察/读取”Token开销，文章探讨了两大解决方案：

1. **RAG机制** ：包含向量与关键词检索，并泛化至Tool/Memory RAG，基于相似度将被动匹配的信息注入上下文。
2. **渐进式按需加载** ：以MCP-Zero和Skill.md为代表，化被动为主动。Agent通过“先看精简目录，确有需要再加载详细工作流”的分层模式获取知识。

从被动RAG到主动分层加载，上下文筛选有效降低了Agent的认知负荷与Token成本，是破解“上下文爆炸”的关键利器。
