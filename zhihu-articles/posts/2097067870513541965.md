### 一、MCP 是什么？

### 1.1 定义

MCP（Model Context Protocol，模型上下文协议） 是由 Anthropic 于 2024 年 11 月推出的开放协议，用于标准化 AI 模型与外部工具、数据源之间的通信方式。

简单来说，MCP 就是 AI 世界的"USB 接口标准"——让不同的 AI 客户端（Claude Desktop、Cursor、Cline 等）能以统一的方式连接各种外部工具和数据。

### 1.2 核心架构

MCP 采用 客户端-服务器架构，涉及三个核心角色：

```text
┌─────────────────────────────────────────────────────────┐
│  Host（宿主/客户端）                                       │
│  比如 Claude Desktop、Cursor、Cline、Qoder 等              │
│                                                          │
│  ┌───────────────┐                    ┌────────────────┐ │
│  │  MCP Client   │ ◄── 通信管道 ────►  │  MCP Server    │ │
│  │  (内置在Host中)│  (stdio/http/sse)   │  (独立进程)     │ │
│  └───────────────┘                    └───────┬────────┘ │
│                                               │          │
│                                    访问外部资源 ▼          │
│                                    ┌──────────────────┐  │
│                                    │ 文件系统/数据库/   │  │
│                                    │ GitHub/浏览器等   │  │
│                                    └──────────────────┘ │
└─────────────────────────────────────────────────────────┘
```

### 1.3 三大核心能力

| 能力 | 说明 | 举例 |
| --- | --- | --- |
| Tools（工具） | 让 AI 能执行操作 | 读写文件、查询数据库、发送消息 |
| Resources（资源） | 让 AI 能读取数据 | 文件内容、数据库记录、API 响应 |
| Prompts（提示） | 预定义的交互模板 | 代码审查模板、报告生成模板 |

### 1.4 为什么需要 MCP？

没有 MCP 之前：

▪︎ 每个 AI 客户端都要自己实现对接各种工具

▪︎ 工具方也要为每个客户端写适配代码

▪︎ N 个客户端 × M 个工具 = N×M 种适配

有了 MCP 之后：

▪︎ 工具方只需实现一次 MCP Server

▪︎ 任何支持 MCP 的客户端都能直接用

▪︎ N 个客户端 + M 个工具 = N+M 次开发

### 二、MCP 的通信方式

MCP 支持三种通信传输方式：stdio、SSE（已弃用）和 Streamable HTTP（推荐）。

> 重要提示： SSE 已于 2025 年 3 月被官方标记为 deprecated（已弃用），新项目应使用 Streamable HTTP 替代。很多网上老教程还在教 SSE，请注意甄别。

### 2.1 三种方式现状总览

| 方式 | 状态 | 适用场景 | 配置关键字段 |
| --- | --- | --- | --- |
| stdio | 推荐 | 本地工具，Host 以子进程方式启动 Server | command + args |
| Streamable HTTP | 推荐（远程） | 远程生产环境，Server 作为 HTTPS 服务 | type: "http" + url |
| SSE | 已弃用 | 仅用于兼容历史 Server，新部署不应使用 | type: "sse" + url |

### 2.2 stdio（标准输入/输出）

最常用的本地通信方式，适合本地服务器。

```text
┌─────────────────┐         stdin (写入)         ┌─────────────────┐
│   MCP Client    │ ────────────────────────────► │   MCP Server    │
│  (AI 客户端)     │                               │   (本地子进程)   │
│                 │ ◄──────────────────────────── │                 │
└─────────────────┘         stdout (读取)         └─────────────────┘
```

工作流程：

▪︎ AI 客户端启动 MCP Server 作为本地子进程

▪︎ Client 通过 stdin（标准输入）向 Server 发送 JSON-RPC 请求

▪︎ Server 处理后通过 stdout（标准输出）返回结果

▪︎ 整个过程在本机完成，不经过网络

配置示例：

```text
{
  "mcpServers": {
    "filesystem": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/Users/dongmx/Documents"]
    }
  }
}
```

特点：

| 优点 | 缺点 |
| --- | --- |
| 简单，不需要网络配置 | 只能本地运行 |
| 安全，数据不出本机 | 每个客户端启动独立的 Server 进程 |
| 延迟低，直接进程间通信 | 不支持多客户端共享同一个 Server |
| 配置简单，只需 command + args | 不适合远程/分布式场景 |

> 注意： 如果不写 "type": "stdio"，大多数客户端会默认当作 stdio 处理。

### 2.3 Streamable HTTP（推荐远程方式）

2025 年 3 月标准化的远程通信方式，替代已弃用的 SSE。

```text
┌─────────────────┐      HTTP POST (请求)       ┌─────────────────┐
│   MCP Client    │ ───────────────────────────► │   MCP Server    │
│  (AI 客户端)     │                              │  (远程服务器)      │
│                 │ ◄─────────────────────────── │                 │
└─────────────────┘   HTTP 响应 (可选 SSE 流式)    └─────────────────┘
        │                                               │
        └─────────── 通过网络连接，Server 可部署在远端 ──────────┘
```

工作流程：

▪︎ AI 客户端通过 HTTP POST 向远程 MCP Server 发送 JSON-RPC 请求

▪︎ Server 处理后，通过 HTTP 响应返回结果（可选 SSE 流式推送）

▪︎ 支持双向流式通信，连接管理和鉴权更规范

▪︎ 与企业级反向代理（Nginx/Envoy）兼容

为什么推荐 Streamable HTTP 而不是 SSE：

▪︎ 支持双向流式通信（SSE 只能服务器→客户端单向推送）

▪︎ 断连恢复能力强（SSE 没有标准化的断点续传）

▪︎ 只需一个端点 /mcp（SSE 需要两个端点 /sse + /message）

▪︎ 与企业级基础设施兼容性更好

配置示例：

```text
{
  "mcpServers": {
    "github-remote": {
      "type": "http",
      "url": "https://mcp.github.com/mcp",
      "headers": {
        "Authorization": "Bearer your-token"
      }
    },
    "grafana": {
      "type": "http",
      "url": "http://localhost:8080/mcp",
      "headers": {
        "Authorization": "Bearer your-grafana-key"
      }
    },
    "moka": {
      "type": "http",
      "url": "https://your-domain.com/mcp",
      "headers": {
        "X-API-Key": "your-api-key"
      }
    }
  }
}
```

特点：

| 优点 | 缺点 |
| --- | --- |
| 支持远程部署，多客户端共享 | 需要网络，有延迟 |
| 双向流式通信，断连恢复强 | 需要搭建和维护服务器 |
| 企业级兼容，安全性好 | 配置相对复杂，需要处理认证 |
| 单一端点，架构简洁 | 需要防火墙开放对应端口 |

### 2.4 SSE（已弃用，仅兼容旧项目）

早期 MCP 使用的远程通信方式，2025 年 3 月起官方标记为 deprecated。

```text
┌─────────────────┐         HTTP POST          ┌─────────────────┐
│   MCP Client    │ ───────────────────────────► │   MCP Server    │
│  (AI 客户端)     │         (发送请求)           │  (远程服务器)     │
│                 │                              │                 │
│                 │ ◄─────────────────────────── │                 │
└─────────────────┘    SSE 长连接 (持续推送)      └─────────────────┘
```

为什么被弃用：

▪︎ 单向通信：SSE 只能服务器→客户端流式推送，客户端→服务器要走额外的 POST 到 /message 端点

▪︎ 断连恢复弱：没有标准化的断点续传，长任务场景下网络抖动会导致整个会话丢失

▪︎ 需要两个端点：/sse（建立 SSE 流）+ /message（发送请求），架构复杂

▪︎ TypeScript SDK 已移除 SSE server 支持

旧配置示例（仅供兼容参考，新项目不要用）：

```text
{
  "mcpServers": {
    "legacy-sse-server": {
      "type": "sse",
      "url": "https://mcp.example.com/sse",
      "headers": {
        "Authorization": "Bearer your-token"
      }
    }
  }
}
```

从 SSE 迁移到 Streamable HTTP：

```text
# 旧方式（SSE）
claude mcp add --transport sse my-server https://mcp.example.com/sse

# 新方式（Streamable HTTP）
claude mcp add --transport http my-server https://mcp.example.com/mcp
```

大多数 MCP Server 提供方已经同时支持 HTTP 和 SSE，通常只是 URL 路径不同。检查你的 MCP Server 文档，找到 HTTP endpoint 替换即可。

### 2.5 三种方式对比总结

| 对比项 | stdio | Streamable HTTP | SSE（已弃用） |
| --- | --- | --- | --- |
| 运行位置 | 本地子进程 | 远程服务器 | 远程服务器 |
| 通信方式 | stdin/stdout 管道 | HTTP POST + 可选 SSE 流式 | HTTP + SSE 单向推送 |
| 是否需要网络 | 不需要 | 需要 | 需要 |
| 多客户端共享 | 不支持 | 支持 | 支持 |
| 双向流式 | 不适用 | 支持 | 不支持（单向） |
| 断连恢复 | 不适用 | 强 | 弱 |
| 端点数量 | 不适用 | 1 个（/mcp） | 2 个（/sse + /message） |
| 配置复杂度 | 简单 | 中等 | 中等 |
| 适用场景 | 本地开发、个人使用 | 远程生产、团队共享、云端部署 | 仅兼容旧项目 |
| 推荐程度 | 推荐（本地） | 推荐（远程） | 不推荐 |

### 2.6 选型决策

```text
需要远程访问？
├── 是 → 用 Streamable HTTP（type: "http"）
└── 否 → 用 stdio（type: "stdio" 或省略）

兼容旧项目？
└── 是 → 暂时用 SSE（type: "sse"），但计划迁移到 Streamable HTTP
```

一句话总结：本地用 stdio，远程用 Streamable HTTP，别碰 SSE。

### 三、MCP Client（AI 客户端）配置步骤（快速上手指南）

本节介绍两大类主流客户端的配置方法：Cline 插件（VS Code/IDEA）和 DeepSeek Harness。

### 3.1 快速上手指南

### 3.1.1 环境准备

MCP 服务器分为 Node.js 和 Python 两种语言实现，根据你的需求选择准备对应的环境。

方式一：Node.js 环境准备

适用于运行 Node.js 版本的 MCP 服务器（如 filesystem、memory、github 等）。

```text
# 1. 检查 Node.js 版本（建议 18+）
node -v
# 如果未安装或版本过低，从官网下载：https://nodejs.org/

# 2. 检查 npm 和 npx
npm -v
npx --version
# npm 和 npx 随 Node.js 一起安装，通常无需单独安装

# 3. 测试运行（可选）
npx -y @modelcontextprotocol/server-filesystem ~/Documents
# 看到 "Server running on stdio" 或终端进入等待状态即成功
# 按 Ctrl+C 退出
```

方式二：Python 环境准备

适用于运行 Python 版本的 MCP 服务器（如 time、fetch、git 等）。

```text
# 1. 检查 Python 版本（建议 3.10+）
python3 --version
# 如果未安装或版本过低，从官网下载：https://www.python.org/

# 2. 检查 pip（Python 包管理器）
pip3 --version
# 如果未安装，参考：https://pip.pypa.io/en/stable/installation/

# 3. 安装 uv（推荐的 Python 包管理工具）
# uv 比 pip 更快，且提供 uvx 命令类似 npx
curl -LsSf https://astral.sh/uv/install.sh | sh

# 4. 检查 uv 和 uvx
uv --version
uvx --version

# 5. 测试运行（可选）
uvx mcp-server-time --help
# 看到帮助信息即成功
```

环境选择建议：

| 场景 | 推荐环境 | 说明 |
| --- | --- | --- |
| 使用官方 filesystem、memory、github 等服务器 | Node.js | 这些服务器官方实现为 Node.js 版本 |
| 使用 time、fetch、git 等服务器 | Python | 这些服务器官方实现为 Python 版本 |
| 自己开发 MCP 服务器 | 两者皆可 | Node.js 用官方 TypeScript SDK，Python 用官方 Python SDK 或 FastMCP |
| 同时使用多种服务器 | 两者都安装 | 可以同时准备两种环境 |

> 提示： 如果你不确定需要哪种环境，建议两种都安装，这样可以运行所有官方 MCP 服务器。

### 3.1.2 五分钟体验第一个 MCP 服务器

```text
# 直接运行 filesystem 服务器
npx -y @modelcontextprotocol/server-filesystem ~/Documents
```

看到 Server running on stdio 或终端进入等待状态，就说明成功了。按 Ctrl+C 退出。

### 3.1.3 配置到你的 AI 客户端

不同客户端的配置文件位置：

| 客户端 | 配置文件路径 |
| --- | --- |
| Claude Desktop (macOS) | ~/Library/Application Support/Claude/claude_desktop_config.json |
| Claude Code | 项目根目录 .mcp.json，或全局 ~/.claude.json |
| Cursor | 项目根目录 .cursor/mcp.json，或全局设置 |
| Cline (VS Code) | VS Code 设置面板里配置 |
| Cherry Studio | 应用内 MCP 管理界面 |

写入配置：

```text
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/Users/dongmx/Documents"]
    },
    "time": {
      "command": "uvx",
      "args": ["mcp-server-time"]
    },
    "memory": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-memory"]
    }
  }
}
```

重启客户端，然后在对话中测试：

▪︎ "列出 ~/Documents 下的文件" → 验证 filesystem

▪︎ "现在几点了" → 验证 time

▪︎ "记住我喜欢用 TypeScript" → 验证 memory

### 3.2 Cline 插件（VS Code / IDEA）

Cline 是一个流行的 AI 编程助手插件，支持 VS Code 和 JetBrains IDEA，内置 MCP 客户端功能。

### 3.2.1 安装 Cline 插件

VS Code：

▪︎ 打开 VS Code

▪︎ 按 Ctrl+Shift+X（或 Cmd+Shift+X）打开扩展面板

▪︎ 搜索 "Cline"

▪︎ 点击 "Install" 安装

JetBrains IDEA：

▪︎ 打开 IDEA，进入 Settings/Preferences

▪︎ 选择 Plugins → Marketplace

▪︎ 搜索 "Cline"

▪︎ 点击 "Install" 安装，重启 IDE

### 3.2.2 配置 MCP 服务器

方式一：通过 GUI 配置（推荐）

▪︎ 打开 Cline 侧边栏面板

▪︎ 点击设置图标（齿轮）或进入 MCP Servers 页面

▪︎ 点击 "Add Server" 或 "Configure MCP Servers"

▪︎ 选择配置方式：

▪︎ stdio 方式：填写 Command、Args、Env

▪︎ HTTP/SSE 方式：填写 URL 和 Headers

方式二：通过配置文件

Cline 的配置文件位置：

| 操作系统 | 配置文件路径 |
| --- | --- |
| macOS | ~/Library/Application Support/Code/User/globalStorage/saoudrizwan.claude-dev/settings/cline_mcp_settings.json |
| Windows | %APPDATA%\\Code\\User\\globalStorage\\saoudrizwan.claude-dev\\settings\\cline_mcp_settings.json |
| Linux | ~/.config/Code/User/globalStorage/saoudrizwan.claude-dev/settings/cline_mcp_settings.json |

stdio 配置示例：

```text
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/Users/dongmx/Documents"],
      "env": {}
    },
    "memory": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-memory"]
    },
    "time": {
      "command": "uvx",
      "args": ["mcp-server-time"]
    }
  }
}
```

HTTP 远程配置示例：

```text
{
  "mcpServers": {
    "remote-server": {
      "url": "http://localhost:8000/mcp",
      "headers": {
        "Authorization": "Bearer your-token"
      }
    }
  }
}
```

### 3.2.3 验证配置

▪︎ 保存配置文件后，重启 Cline 或点击 "Reload Servers"

▪︎ 在 Cline 面板中查看 "MCP Servers" 列表

▪︎ 确认服务器状态为 "Connected" 或绿色指示灯

▪︎ 测试工具调用：在对话中输入 "列出当前目录下的文件" 验证 filesystem 服务器

### 3.3 DeepSeek Harness 桌面版

DeepSeek Harness 桌面版是 DeepSeek 官方提供的 MCP 客户端桌面应用，支持通过图形界面和配置文件两种方式管理 MCP 服务器。

### 3.3.1 安装 DeepSeek Harness 桌面版

前往 DeepSeek 官网 下载桌面版安装包：

| 操作系统 | 安装包格式 |
| --- | --- |
| macOS | .dmg |
| Windows | .exe 安装程序 |
| Linux | .AppImage / .deb |

安装后启动应用，首次运行会自动创建配置文件。

验证安装：在应用"关于"页面查看版本号。

### 3.3.2 内置插件管理

DeepSeek Harness 桌面版内置了部分 MCP 插件，可在"设置 → 内置插件"页面中查看。

查看内置插件：

▪︎ 打开 DeepSeek Harness 桌面版

▪︎ 进入"设置 → 内置插件"页面

▪︎ 在插件列表中可查看当前可用的内置插件（如 filesystem、fetch 等）

▪︎ 点击插件名称可查看该插件提供的工具列表和说明

> 说明：内置插件默认随应用提供，具体启用/禁用方式取决于应用版本。如需精确控制 MCP 服务器的启用状态，推荐通过配置文件方式管理（见 3.3.4）。

### 3.3.3 配置文件位置

DeepSeek Harness 桌面版（v0.2.1-rc.2）的配置文件通过应用内打开：

▪︎ 打开 DeepSeek Harness 桌面版

▪︎ 进入"设置"页面

▪︎ 点击左上角 "打开配置文件" 按钮

▪︎ 系统会自动打开配置文件所在目录

主要配置文件：

| 文件 | 用途 | 路径 |
| --- | --- | --- |
| config.json | 应用主配置（模型、代理等） | 通过"打开配置文件"按钮打开 |
| cordis.patch.yml | MCP 服务器配置 | ~/.dsh/profiles//cordis.patch.yml |

> 说明： 为当前使用的配置文件名（默认为 default），完整路径示例：~/.dsh/profiles/default/cordis.patch.yml

### 3.3.4 通过配置文件添加 MCP 服务器

如需添加内置插件列表之外的 MCP 服务器（如自定义服务器、第三方远程服务器），直接编辑 cordis.patch.yml 文件即可，无需额外安装插件。

操作步骤：

▪︎ 打开文件：~/.dsh/profiles/default/cordis.patch.yml

▪︎ 按以下格式添加配置（YAML 列表格式）：

```text
- insert:
# 示例：配置默认模型
- id: agent-default-model
  name: "@deepseek-ai/dsh-agent-default-model"
  config:
    provider: deepseek-account
    model: deepseek-flash
```

### 四、MCP Server 部署方式

### 4.1 服务器类型区分

MCP 官方仓库中的服务器分为两种语言实现，所有 7 个服务器都自带 Dockerfile，支持容器化部署：

| 语言 | 服务器 | 包管理器 | 运行工具 | Dockerfile |
| --- | --- | --- | --- | --- |
| Node.js | filesystem, memory, sequentialthinking, everything | npm | npx / node | 有 |
| Python | time, fetch, git | PyPI | uvx / pip | 有 |

部署方式按通信协议分为两大类：

▪︎ 本地 stdio 部署：服务器作为客户端子进程运行

▪︎ 远程 HTTP 部署：服务器作为独立网络服务运行


步骤 4：编写服务器代码

创建 server.py 文件：

```text
from fastmcp import FastMCP
from datetime import datetime

# 创建 MCP 服务器实例
mcp = FastMCP("my-remote-server")

# 注册工具 1：获取服务器时间
@mcp.tool()
def get_server_time() -> str:
    """获取服务器当前时间"""
    return datetime.now().strftime("%Y-%m-%d %H:%M:%S")

# 注册工具 2：简单的计算器
@mcp.tool()
def calculate(a: int, b: int, operation: str) -> str:
    """执行简单的数学运算

    Args:
        a: 第一个数字
        b: 第二个数字
        operation: 运算类型（add/subtract/multiply/divide）
    """
    if operation == "add":
        return str(a + b)
    elif operation == "subtract":
        return str(a - b)
    elif operation == "multiply":
        return str(a * b)
    elif operation == "divide":
        if b == 0:
            return "错误：除数不能为 0"
        return str(a / b)
    else:
        return "错误：不支持的运算类型"

# 启动服务器（使用 Streamable HTTP 传输方式）
if __name__ == "__main__":
    # 默认监听 http://0.0.0.0:8000/mcp
    mcp.run(transport="streamable-http", host="0.0.0.0", port=8000)
```

```text
const server = new McpServer({

  version: "1.0.0"

  transport.handleRequest(req, res);
```

Nginx 配置示例：

```text
server {
    listen 443 ssl;
    server_name mcp.yourdomain.com;

    ssl_certificate /path/to/cert.pem;
    ssl_certificate_key /path/to/key.pem;

    location /mcp {
        proxy_pass http://localhost:8000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # 支持长连接
        proxy_set_header Connection '';
        proxy_buffering off;
        proxy_cache off;
    }
}
```

```text
    stdin_open: true
    volumes:
      - /Users/dongmx/Documents:/workspace

  mcp-time:
    build:
      context: .
```

### 4.6 所有部署方式对比总结

▪︎ 部署方式：npx　｜　通信协议：stdio　｜　语言：Node.js　｜　优点：不用安装，自动下载　｜　缺点：首次启动慢，依赖网络　｜　适合场景：快速体验　｜　复杂度：低

▪︎ 部署方式：node 本地构建　｜　通信协议：stdio　｜　语言：Node.js　｜　优点：离线可用，能改源码　｜　缺点：需先 clone + build　｜　适合场景：开发调试　｜　复杂度：中

▪︎ 部署方式：npm -g 全局安装　｜　通信协议：stdio　｜　语言：Node.js　｜　优点：启动快，命令简洁　｜　缺点：需手动全局安装　｜　适合场景：日常使用　｜　复杂度：低

▪︎ 部署方式：uvx　｜　通信协议：stdio　｜　语言：Python　｜　优点：不用安装，自动管理　｜　缺点：每次启动稍慢　｜　适合场景：快速体验　｜　复杂度：低

▪︎ 部署方式：pip install　｜　通信协议：stdio　｜　语言：Python　｜　优点：启动快，命令简洁　｜　缺点：需手动更新版本　｜　适合场景：日常使用　｜　复杂度：低

▪︎ 部署方式：uv pip install　｜　通信协议：stdio　｜　语言：Python　｜　优点：比 pip 快，环境隔离好　｜　缺点：多装一个 uv　｜　适合场景：注重环境隔离　｜　复杂度：低

▪︎ 部署方式：本地源码　｜　通信协议：stdio　｜　语言：两者　｜　优点：能改代码、离线可用　｜　缺点：路径长，依赖本地仓库　｜　适合场景：开发调试　｜　复杂度：中

▪︎ 部署方式：FastMCP　｜　通信协议：HTTP　｜　语言：Python　｜　优点：最简单，几行代码　｜　缺点：需自己写服务器代码　｜　适合场景：快速搭建远程服务　｜　复杂度：低

▪︎ 部署方式：TypeScript SDK　｜　通信协议：HTTP　｜　语言：Node.js　｜　优点：生态丰富，类型安全　｜　缺点：代码量较多　｜　适合场景：Node.js 项目　｜　复杂度：中

▪︎ 部署方式：Docker + FastMCP　｜　通信协议：HTTP　｜　语言：Python　｜　优点：环境隔离，易部署　｜　缺点：需学 Docker　｜　适合场景：生产推荐　｜　复杂度：中

▪︎ 部署方式：Nginx 反向代理　｜　通信协议：HTTP　｜　语言：两者　｜　优点：HTTPS、负载均衡　｜　缺点：配置复杂　｜　适合场景：企业级　｜　复杂度：高

▪︎ 部署方式：云平台托管　｜　通信协议：HTTP　｜　语言：两者　｜　优点：免运维，自动扩缩　｜　缺点：有成本　｜　适合场景：快速上线　｜　复杂度：中

▪︎ 部署方式：Docker 单容器　｜　通信协议：stdio　｜　语言：两者　｜　优点：环境隔离，安全　｜　缺点：启动稍慢　｜　适合场景：团队共享　｜　复杂度：中

▪︎ 部署方式：Docker Compose　｜　通信协议：stdio　｜　语言：两者　｜　优点：多服务编排　｜　缺点：需写 compose 文件　｜　适合场景：多服务协同　｜　复杂度：中高

▪︎ 部署方式：Kubernetes　｜　通信协议：两者　｜　语言：两者　｜　优点：高可用，自动扩缩容　｜　缺点：复杂度高　｜　适合场景：企业级大规模　｜　复杂度：高

选型建议：

| 场景 | 推荐方案 |
| --- | --- |

### 5.10 实用工具：Supergateway（把本地 stdio 服务器变成远程 SSE 服务）

如果你想把本地的 stdio 服务器暴露成远程 HTTP 服务（比如团队共享），可以用 Supergateway。注意：当前版本的 Supergateway 只支持 SSE 传输方式，不支持 Streamable HTTP。

启动 SSE 服务：

```text
# 安装
npm install -g supergateway

# 把 filesystem 服务器转成 SSE 服务
supergateway --stdio "npx -y @modelcontextprotocol/server-filesystem /Users/dongmx/Documents" \\
  --port 3444 \\
  --baseUrl http://localhost:3444
```

启动后会看到：

```text
[supergateway]   - outputTransport: sse
[supergateway]   - port: 3444
[supergateway]   - ssePath: /sse
[supergateway]   - messagePath: /message
[supergateway] SSE endpoint: http://localhost:3444/sse
[supergateway] POST messages: http://localhost:3444/message
```

客户端配置：

```text
{
  "mcpServers": {
    "remote-filesystem": {
      "type": "sse",
      "url": "http://192.168.1.100:3444/sse"
    }
  }
}
```

说明：

▪︎ Supergateway 是一个桥接工具，把 stdio 协议转成 SSE 协议

▪︎ SSE 是 2025 年 3 月前的旧标准，但目前仍被广泛支持

▪︎ 如果你需要 Streamable HTTP（新标准），可以直接用 FastMCP 等框架自己搭建（见 4.3.1 节）

### 7.4 开发远程 MCP 服务器（远程部署）

将 MCP 服务器部署为远程 HTTP 服务，适合团队共享和生产环境。

### 7.4.1 使用 FastMCP 开发远程服务器（Python）

步骤 1：安装依赖

```text
pip install fastmcp uvicorn
```

步骤 2：编写服务器代码

创建 server.py：

```text
from fastmcp import FastMCP
from datetime import datetime

# 创建 MCP 服务器
mcp = FastMCP("my-remote-server")

# 注册工具
@mcp.tool()
def get_server_time() -> str:
    """获取服务器当前时间"""
    return datetime.now().strftime("%Y-%m-%d %H:%M:%S")

@mcp.tool()
def calculate(a: int, b: int, operation: str = "add") -> str:
    """执行数学计算"""
    if operation == "add":
        result = a + b
    elif operation == "multiply":
        result = a * b
    else:
        return f"不支持的操作: {operation}"

    return f"{a} {operation} {b} = {result}"

# 注册资源
@mcp.resource("config://app-name")
def get_app_name() -> str:
    """获取应用名称"""
    return "My Remote MCP Server"

# 启动为 Streamable HTTP 服务
if __name__ == "__main__":
    mcp.run(transport="streamable-http", host="0.0.0.0", port=8000)
```

步骤 3：运行服务器

```text
python server.py
```

服务器将在 [http://0.0.0.0:8000/mcp](http://0.0.0.0:8000/mcp) 启动。

```text

  "mcpServers": {
```

### 7.4.2 使用 TypeScript SDK 开发远程服务器

步骤 1：初始化项目

```text
mkdir my-mcp-server && cd my-mcp-server
npm init -y
npm install @modelcontextprotocol/sdk express cors
npm install -D @types/express @types/cors typescript
```

步骤 2：编写服务器代码

创建 src/server.ts：

```text
import express from 'express';
import cors from 'cors';
import { McpServer } from '@modelcontextprotocol/sdk/server/mcp.js';
import { StreamableHTTPServerTransport } from '@modelcontextprotocol/sdk/server/streamableHttp.js';
import { z } from 'zod';

const app = express();
app.use(cors());
app.use(express.json());

// 创建 MCP 服务器
const server = new McpServer({
  name: 'my-remote-server',
  version: '1.0.0'
});

// 注册工具
server.tool(
  'get_time',
  '获取当前时间',
  {},
  async () => ({
    content: [{ type: 'text', text: new Date().toISOString() }]
  })
);

// 创建传输层
const transport = new StreamableHTTPServerTransport({
  sessionIdGenerator: () => crypto.randomUUID()
});

// 连接服务器和传输层
await server.connect(transport);

// 设置 MCP 端点
app.post('/mcp', async (req, res) => {
  await transport.handleRequest(req, res);
});

app.get('/mcp', async (req, res) => {
  await transport.handleRequest(req, res);
});

// 启动服务器
const PORT = process.env.PORT || 8000;
app.listen(PORT, () => {
  console.log(`MCP Server running on http://0.0.0.0:${PORT}/mcp`);
});
```

步骤 3：编译和运行

```text
npx tsc
node dist/server.js
```

### 7.6 架构设计原则

### 7.6.1 MCP 使用注意事项

▪︎ Token 消耗：每次 MCP 工具调用都会消耗 AI 模型的 token，复杂工具可能消耗大量 token

▪︎ 上下文占用：MCP 工具的输入输出会占用对话上下文，影响模型的长期记忆能力

▪︎ 优先级原则：

▪︎ 能用 Skill 完成的任务，优先使用 Skill（Skill 不消耗额外 token，不占用上下文）

▪︎ 非必要不使用 MCP 调用（简单任务直接用 AI 模型内置能力）

▪︎ 必须使用 MCP 时，选择最简洁的工具（减少 token 消耗和上下文占用）

### 7.6.2 设计原则速查表

| 原则 | 要点 |
| --- | --- |
| 工具设计 | 单一职责、参数和输出精简、描述清晰，帮助 AI 正确调用 |
| 安全性 | 输入验证、权限控制、敏感数据脱敏、速率限制、审计日志 |
| 错误处理 | 返回友好错误信息、设置超时、临时错误指数退避重试 |
| 性能优化 | 缓存高频查询、支持批量操作、耗时操作异步处理、连接池复用 |
| 可测试性 | 完善的单元测试、Mock 支持、Inspector 集成调试 |
| 版本管理 | 语义化版本（SemVer）、向后兼容、清晰弃用策略 |
| 监控运维 | 健康检查端点、调用指标收集（延迟/错误率）、告警机制 |
| 幂等性 | 查询天然幂等、写操作支持安全重试、使用请求 ID 防重复 |
| 多租户隔离 | 数据/资源/配置三层隔离 |

### 7.6.3 Token 节省优化方案

实测以下四项配置优化可降低 60% 以上 的 token 消耗：

| 优化项 | 作用 | 操作步骤 |
| --- | --- | --- |
| 关闭激进上下文压缩 | 避免模型为压缩上下文丢弃关键信息，减少重复请求 | 设置 → 高级 → 上下文压缩 → 选择"关闭"或"保守模式" |
| 限制工具预加载 | 仅加载当前会话需要的 MCP 工具，减少系统提示词膨胀 | 设置 → 内置插件 → 关闭不常用的 MCP 插件开关 |
| 启用滑动窗口 | 限制对话历史长度，避免长对话累积消耗大量 token | 设置 → 高级 → 上下文窗口 → 启用"滑动窗口"并设置保留轮数（建议 5-10 轮） |
| 调低最大输出 Token | 限制单次回复长度，避免生成冗余内容 | 设置 → 模型参数 → 最大输出 Token → 调整为 1024-2048 |

补充建议：

▪︎ 单次会话专注一个任务，完成后开启新会话，避免上下文无限膨胀

▪︎ 优先使用 Skill 而非 MCP 工具处理简单任务（Skill 不消耗额外 token）

▪︎ 工具描述（description）尽量精简，写得啰嗦会直接增加每次调用的 token 成本
