## 01. 推理引擎快，不是因为模型突然变小了

把一个 7B 模型用 `transformers.generate()` 跑起来，再把同一个模型放进 vLLM、TGI 或其他推理引擎里，第一反应往往是：为什么吞吐差这么多？权重没变，GPU 没变，输入输出也差不多，难道推理引擎只是把 CUDA kernel 写得更狠吗？

kernel 优化当然重要，但这不是 LLM 推理服务最容易被低估的部分。在线推理和单机脚本的关键差别在于：线上不是一个请求独占 GPU，而是一堆长度不同、到达时间不同、输出长度不同的请求同时挤进同一块显卡。单请求脚本关心的是“这条 prompt 能不能生成答案”；推理引擎关心的是“在不 OOM、不让用户等太久的前提下，如何让 GPU 每一轮都尽量有有效工作可做”。

LLM 推理瓶颈不只是原始算力，更是内存管理和调度。尤其是 KV cache，它既随上下文长度增长，又随并发请求数放大，还因为请求长度差异产生碎片。vLLM 的 PagedAttention 之所以有代表性，不是因为它把 Transformer 数学公式改掉了，而是因为它把 KV cache 当成类似操作系统虚拟内存的问题来管理：逻辑序列保持连续，物理显存按 block 分配和回收。

理解推理引擎，不能只盯着模型文件大小和单次 forward latency。推理服务的真实瓶颈通常藏在四个地方：prefill 和 decode 的资源画像不同；KV cache 随序列长度和 batch 放大；静态 batch 让 GPU 等最慢请求；缺少 prefix 复用会让大量相同 system prompt 反复计算。搞清楚这些，才知道为什么“同样模型，同样卡”，服务吞吐可以差出一个数量级。

## 02. 一个请求其实分成 prefill 和 decode 两种工作负载

LLM 是自回归生成模型。输入 prompt 后，模型先处理已有 token，得到每一层 attention 需要的中间状态；之后每生成一个新 token，就把这个新 token 接回上下文，再预测下一个 token。服务实现里通常把这件事拆成两个阶段：prefill 和 decode。

![](https://pica.zhimg.com/v2-7cacf4179b2c9cfe1595b09a62c3e416_r.jpg)
*Prefill 和 Decode 的内存访问模式：输入 prompt 经 prefill 写入 KV cache，decode 阶段逐 token 读取历史 KV 并流式输出*

Prefill 阶段处理的是完整 prompt。假设用户输入 3000 个 token，prefill 会把这 3000 个 token 一次性喂给模型，做一轮完整前向传播，计算出 logits，同时为每一层写入 key/value cache。这个阶段矩阵较大，batch 和序列长度足够时更容易把 GPU 的 Tensor Core 喂饱，所以它更接近 compute bound。prompt 越长，首 token 之前需要做的工作越多，TTFT 就越容易变长。

Decode 阶段完全不同。每一步只生成一个新 token。每一步都要读已有上下文对应的 KV cache，和当前 token 的 query 做 attention，再输出下一个 token。这里的矩阵往往小得多，反复读取历史 KV cache 的成本变得突出。输出越长，decode 步数越多；并发越高，所有请求的 KV cache 工作集越大；显存带宽、cache locality 和调度策略就会变成核心问题。

这也是为什么延迟指标要拆开：TTFT 主要受排队、prefill、模型加载状态和首轮调度影响；TPOT 主要受 decode 每步耗时、batch 形态、KV cache 管理和采样逻辑影响。把两者混成一个“平均响应时间”，很容易做错优化。比如把 batch size 调大，可能让 tokens/s 上升，但首 token 前的排队变长；把 max model length 开得很大，模型能力变强了，但 KV cache 预算被长上下文吃掉，短请求也跟着排队。

一个常见误区是把推理理解成普通 Web handler：请求进来，函数执行，结果返回。LLM 推理服务更像一条持续运行的 GPU 流水线。prefill 请求、decode 请求、等待队列、KV cache 分配、streaming 返回都在同一个调度器里交错发生。单请求快，不代表并发下快；平均 token 快，不代表首 token 快。

## 03. KV cache 是推理显存里最动态的那部分

模型权重是固定开销。7B 参数用 fp16/bf16 加载，大约 14GB；量化后可以更小；张量并行后可以分散到多张卡。KV cache 则不同，它随请求数、上下文长度、输出长度一起变化，而且变化发生在服务运行时。

KV cache 存的是每一层 attention 里历史 token 的 key 和 value。没有 cache 时，每生成一个 token 都要重新计算之前所有 token 的 K/V，代价不可接受。有了 cache 后，历史 K/V 只算一次，decode 时直接读取。缓存换来了计算节省，但把压力转到了显存容量和显存带宽。

粗略估算公式可以写成：

`KV cache bytes ≈ token 数 × 层数 × KV head 数 × head_dim × 2(K+V) × bytes_per_element`

以 Llama-2-7B 这类 32 层、32 个 KV head、head_dim 128、fp16 的模型为例，一个 4096 token 序列的 KV cache 大约是：

`4096 × 32 × 32 × 128 × 2 × 2 bytes ≈ 2GB`

这个数不应该被当成所有模型的固定值。采用 grouped-query attention 的模型，KV head 数会小很多；使用 fp8 KV cache 或其他压缩方式，也会改变结果。但它足够给出数量级直觉：在线服务不是“权重能装下就完事”，长上下文并发会把 KV cache 变成主要显存消费者。

假设一张 80GB GPU 上加载了 14GB 权重，框架和临时 buffer 再占一部分，剩下显存用于 KV cache。若每个长请求都接近 2GB KV cache，那么几十个长请求就可能把显存吃满。更麻烦的是，真实请求不会整齐地都是 4096 token：有人输入 200 token，有人输入 4000 token；有人输出 20 token，有人输出 2000 token。显存压力不只是总量，还包括分配和释放是否足够细。

这解释了一个线上常见现象：GPU 利用率看起来不高，服务却开始排队甚至 OOM。原因可能不是算力不足，而是 KV cache 预算被碎片、预留和长请求占住，调度器不能再安全接纳新请求。此时继续盲目提高并发，只会让 tail latency 更差。

## 04. 朴素 `generate()` 的假设不适合在线服务

Hugging Face Transformers 的 `generate()` 是非常好的模型使用入口，适合本地实验、离线脚本、功能验证和小规模批处理。它把模型加载、tokenizer、采样策略、KV cache 等封装得足够清楚，便于快速理解生成流程。但它的默认心智模型更接近“一个进程控制一批请求”，不是“多租户在线推理服务”。

在线服务会遇到几个 `generate()` 脚本不必处理的问题。第一，请求连续到达，不会天然凑成长度相近的一批。第二，每个请求输出何时结束不可提前精确知道，`eos_token`、max_tokens、stop words、采样随机性都会影响长度。第三，GPU 显存要同时容纳不同请求的 KV cache，并在请求结束后快速回收。第四，用户希望 streaming 输出，服务端不能等整批都生成完才返回。

如果用普通 batch 思路处理这些请求，容易出现两个浪费。计算浪费来自 padding：短 prompt 要补到长 prompt 的长度，短输出要陪长输出一起占槽。显存浪费来自预留：为了避免生成过程中 KV cache 不够，系统可能按最大长度提前留空间；短请求没用完的部分仍然被占住。两种浪费叠加后，吞吐和并发都会受影响。

推理引擎做的事情，就是把这些在线服务问题显式化。它维护等待队列，决定哪些请求进入 prefill；维护活跃 decode 集合，决定每轮 iteration 里谁继续生成；维护 KV cache 分配器，决定每个请求的 cache 放在哪里；维护 token budget，避免单个长请求把所有显存吃完。模型前向只是其中一环。

这也是为什么 benchmark 要看清楚条件。单条短 prompt 的 latency，不能代表服务并发吞吐；固定输入输出长度的离线压测，也不能代表真实用户混合流量；只有把 prompt 长度分布、输出长度分布、并发到达模式、streaming 指标和显存水位放在一起，才能判断引擎是否真的适合你的场景。

## 05. 朴素 KV cache 分配会把显存切碎

KV cache 最直观的做法，是给每个请求分配一段连续显存。请求最大长度是多少，就按这个上限规划空间。这个思路容易理解，也符合连续数组的直觉：一段序列放在一段连续内存里，索引简单，管理也简单。

问题在于，在线推理的请求长度高度不均匀。若按最大上下文长度预留，大量短请求会留下空洞；若按当前长度逐步扩容，又需要找到足够连续的空间，并处理扩容失败、搬迁和碎片。随着请求不断进入和结束，显存里会出现许多小块空闲空间，总空闲量看似够，但不一定有合适的连续区域接纳新请求。

![](https://pic3.zhimg.com/v2-767c5dc4c46d2754265d0134f66d2860_r.jpg)
*朴素 KV cache 与 PagedAttention 对比：静态连续预留导致显存碎片，PagedAttention 通过物理块池和 block table 提高 KV cache 利用率*

vLLM 论文和官方介绍里反复强调的一个点，就是传统 KV cache 管理会造成大量浪费。这个浪费不一定表现成“显存里有一块明显空着的大区域”，更常见的是被不同请求的预留空间、未用完空间和释放后的碎片分散掉。结果是：GPU 还有计算能力，服务却无法接纳更多序列。

从工程后果看，碎片化会带来三件事。第一，吞吐下降，因为同一时间能放进 active set 的请求变少。第二，tail latency 变差，因为新请求要等 cache 空间释放。第三，调参变脆弱，因为 `max_model_len`、并发上限、输出长度限制之间互相影响，稍微放宽一个配置就可能触发 OOM。

一个常见问题是：把显存水位调低一点，不就安全了吗？确实更安全，但成本是可服务并发下降。真正的问题不是留多少安全边际，而是分配粒度太粗。就像操作系统如果要求每个进程必须拿到一整段连续物理内存，内存利用率会很差；分页机制的价值就在于把逻辑连续和物理连续解耦。

## 06. PagedAttention 把 KV cache 变成分页管理问题

PagedAttention 的核心思想可以用一句话概括：请求看到的是连续 token 序列，但底层 KV cache 可以存放在不连续的物理块里。每个请求维护一个 block table，表里记录逻辑块到物理块的映射。attention 需要读取某个 token 范围的 K/V 时，通过映射找到对应物理 block。

![](https://pic1.zhimg.com/v2-248c04e46fcc3e275b482bddc2be4006_r.jpg)
*PagedAttention Block Table 示意：逻辑序列切成逻辑块，经 block table 映射到不连续物理 KV cache block，并由块池管理分配释放和复用*

这个设计有几个直接收益。第一，物理显存按 block 分配，请求增长时只需要追加新的 block，不需要提前拿到最大长度空间。第二，请求结束后可以按 block 回收，减少长短请求混合造成的空洞。第三，不同请求共享前缀时，前缀对应的物理 block 可以复用，减少重复计算和重复存储。第四，调度器可以更精确地根据剩余 block 数决定是否接纳新请求。

PagedAttention 借鉴的是虚拟内存的心智模型，但它不是把 CPU 页表直接搬到 GPU 上。LLM attention 有自己的访问模式、kernel 约束和并行组织方式。工程难点在于：既要让 block 管理足够细，减少浪费；又不能让查表和非连续访问把 attention kernel 拖慢。vLLM 的贡献正是在这个平衡点上做了系统设计。

理解 PagedAttention 时，不必先陷入所有 kernel 细节。先抓住数据结构层面的变化：过去 KV cache 是“每个请求一段大连续数组”，现在变成“每个请求一个逻辑地址空间，底层由块池提供物理页”。这个变化让推理引擎有能力把显存当成共享资源管理，而不是被每个请求的最大长度预留绑住。

这也解释了为什么 PagedAttention 对高并发服务更有价值。单请求本地生成时，碎片化不明显；并发请求越多，长度分布越不均匀，块级管理的收益越明显。若一个服务只有固定长度、离线批量、没有 streaming 的任务，PagedAttention 的相对收益可能没有在线混合流量那么夸张。性能结论必须和负载形态一起看。

## 07. Continuous batching 解决的是 GPU 空槽问题

KV cache 管理解决了“能不能放下更多请求”。调度解决的是“这些请求如何一起跑”。传统静态 batch 的做法，是凑齐一批请求后一起执行，等这批请求都完成，再处理下一批。对普通深度学习推理，这种方式常常够用；对自回归 LLM，它会留下大量空槽。

原因很简单：同一批请求的输出长度不同。某个请求 20 个 token 就结束，另一个请求要生成 800 个 token。静态 batch 中，短请求结束后，它占过的槽位不能立刻让新请求进入；长请求继续 decode，GPU 每一轮实际活跃请求数下降。越到后面，batch 越稀疏，GPU 越容易空转。

![](https://picx.zhimg.com/v2-da004ff02fc97e572de41b51aa3c4d51_r.jpg)
*Continuous batching 调度时序：静态 batch 中短请求结束后留下空槽，continuous batching 在每个 decode iteration 之间插入新请求并移除完成请求*

Continuous batching，也常被称为 iteration-level scheduling，把调度粒度从“整批请求”缩小到“每个 decode iteration”。每一轮生成之后，调度器检查哪些请求完成，释放它们的 KV cache；再检查等待队列里哪些请求可以进入，给它们分配 cache 并加入下一轮。这样 batch 不必同生共死，活跃集合可以滚动更新。

这个设计对吞吐有明显帮助，因为 GPU 更长时间保持忙碌。但它也引入新的取舍。新请求进入 active set 需要 prefill，而 prefill 和 decode 的资源画像不同；若 prefill 太多，可能影响已经在 streaming 的请求 TPOT；若只照顾 decode，等待队列里的新请求 TTFT 会变差。调度器必须在首 token 延迟、每 token 延迟、吞吐和显存预算之间做权衡。

所以 continuous batching 不是简单的“开了就更快”。它需要配合准入控制、token budget、最大并发、抢占策略和 KV cache 管理一起看。优秀的推理引擎不会只追求 batch 越大越好，而是让 batch 在每一轮里尽量有效：既不让 GPU 空着，也不让长请求把短请求长期挡在门外。

## 08. Prefix caching 让相同前缀不再反复计算

很多 LLM 应用的 prompt 有大量重复前缀。比如所有请求都带同一段 system prompt；RAG 服务里，多个用户问题可能召回同一份文档片段；代码助手会带相似的仓库上下文；客服机器人会带固定的角色、规则和输出格式。若每个请求都从头 prefill，这些重复前缀会反复消耗算力和显存带宽。

Prefix caching 的目标是复用已有前缀对应的 KV cache。若新请求的前 N 个 token 与缓存中的前缀一致，推理引擎可以复用这一段 KV cache，只对后续新增 token 做计算。vLLM 文档里的 automatic prefix caching 就是这类能力的代表；SGLang 里常被讨论的 RadixAttention，也强调通过前缀树结构复用 prompt 前缀。

Prefix caching 的收益高度依赖流量形态。系统 prompt 固定、模板稳定、重复文档多、请求前缀命中率高时，它能明显降低 TTFT 和 prefill 计算。若每个请求前缀都完全不同，或者 prompt 里塞了大量时间戳、随机 ID、用户特定字段，命中率就会下降。很多团队发现 prefix caching 效果一般，不是技术失效，而是 prompt 模板把可复用前缀打碎了。

这给应用侧一个很实用的提醒：prompt 模板也是性能接口。把动态字段尽量放在后面，把稳定 system prompt、工具说明、格式约束放在前面，可以提高前缀复用机会。RAG 场景里，若文档排序不稳定、chunk 拼接顺序随机，prefix cache 也很难命中。推理优化有时不只在引擎参数里，也在上游 prompt 组织方式里。

Prefix caching 还要注意一致性边界。缓存复用要求 token 序列完全一致，不是文本语义相似就行；tokenizer 版本、空格、换行、模板字段顺序都会影响命中。若模型、tokenizer 或 adapter 版本变了，旧 KV cache 不能跨版本使用。推理引擎可以管理这些细节，但应用侧要理解缓存不是魔法，它只复用严格相同的计算前缀。

## 09. 调度器真正管理的是四种预算

推理引擎调度器看起来是在管理请求队列，实际是在管理四种预算。

第一是显存预算。权重、KV cache、临时 buffer、CUDA graph 或 runtime buffer 都要占显存。`gpu_memory_utilization` 这类参数调的是可用水位，不是越高越好。水位高，KV cache 容量更大，能接纳更多请求；水位太高，临时峰值和碎片波动就可能触发 OOM。

第二是 token 预算。一个 batch 里能处理多少 token，不只由请求数决定，还由 prompt 长度、输出长度和 prefill/decode 混合决定。长 prompt 的 prefill 会瞬间消耗大量计算；长输出的 decode 会长期占据 KV cache。调度器需要避免少数超长请求让所有短请求排队。

第三是延迟预算。实时对话希望首 token 快、输出稳定；离线摘要可以接受排队但希望 tokens/s 高；代码补全对 TTFT 更敏感，宁愿牺牲一部分吞吐。没有 SLO 的调度器只能按通用策略工作，有 SLO 的平台才能做场景化队列、优先级和限流。

第四是公平预算。多租户服务里，某个用户提交一批超长请求，可能占满 KV cache 和 decode 槽。若没有 per-tenant quota、max_tokens 限制、队列隔离和抢占策略，推理服务会出现“没有报错但大部分用户变慢”的软故障。公平性不是业务层才关心的事，它会直接影响 GPU 调度效率。

这些预算互相牵制。提高 `max_num_seqs` 可能增加吞吐，也可能让每个请求排队更久；提高 `max_model_len` 扩展了能力，也会抬高最坏情况下的 KV cache 需求；增加 tensor parallel 可以让大模型装进多卡，却引入跨卡通信；prefix caching 能降低 prefill，但命中率低时收益有限。调参前先画清楚预算，调参后再看指标，不要凭感觉把参数拉大。

## 10. “vLLM 快一个数量级”要放在正确上下文里理解

很多文章会说 vLLM 比普通 Hugging Face 推理快一个数量级。这个说法在特定负载下有依据，但不能被理解成“任何单请求 latency 都快十倍”。vLLM 的优势主要来自服务场景：PagedAttention 提高 KV cache 利用率，continuous batching 提高 GPU 活跃度，prefix caching 在重复前缀场景下降低 prefill，OpenAI-compatible serving 让它更容易接入真实服务流量。

若你只测一条短 prompt、输出也很短，瓶颈可能是 Python 调用、tokenizer、网络、采样或一次 kernel launch；推理引擎的调度能力没有充分发挥。若你测的是大量并发、长短混合、streaming 输出，传统脚本式 generate 很快暴露队列和显存管理问题，此时推理引擎收益会明显得多。

还有一些情况，vLLM 不是唯一答案。NVIDIA TensorRT-LLM 在特定模型、特定硬件、编译优化和量化路径下可能更适合追求极致性能；TGI 对 Hugging Face 生态集成较顺手；SGLang 在结构化输出、程序化调用和某些 agentic workload 中有自己的设计重点。选择引擎时，不要只问“谁最快”，要问“我的 SLO、模型、硬件、团队维护能力和流量形态是什么”。

推理引擎也不能替代上游治理。prompt 过长、RAG 塞入无关文档、用户 max_tokens 无限制、请求没有租户隔离、评估不看 tail latency，再好的引擎都会被拖垮。引擎负责把 GPU 资源高效调度起来，应用和平台要负责把请求形态控制在可服务范围内。

## 11. 从本地脚本走向推理服务的练习路径

可以用一个小练习建立完整直觉：同一个 7B 或 8B 模型，先用 Transformers 本地 `generate()` 跑单请求，再用 vLLM OpenAI-compatible server 跑并发请求。不要一开始追求极限压测，先记录四类指标：TTFT、TPOT、tokens/s、显存水位。

第一组实验固定 prompt 长度，改变并发数。观察 tokens/s 如何上升，TTFT 如何变化，显存水位如何增长。第二组实验固定并发，改变 prompt 长度。观察 prefill 对首 token 的影响。第三组实验固定 prompt，改变 max_tokens。观察 decode 步数和 KV cache 占用如何影响 TPOT。第四组实验加入相同 system prompt，观察 prefix caching 开启前后的差异。

练习时要保守记录环境：GPU 型号、显存、模型版本、tokenizer、精度、引擎版本、主要参数、输入长度分布、输出长度分布。没有这些元数据，结果很难复盘。不要把某次单机压测结果直接写成普遍结论。推理性能是模型、硬件、引擎、参数和流量共同作用的结果。

排查顺序也可以固定下来。首 token 慢，先看队列、prefill 长度、prefix cache 命中和模型是否冷启动；每 token 慢，先看 decode batch、KV cache 水位、采样逻辑和跨卡通信；吞吐低但显存满，优先怀疑 KV cache 预算、max_model_len、长请求和碎片；错误率高，先看 OOM、上下文超限和模型加载日志。

推理服务优化，不是把所有参数调到最大，而是把系统约束写清楚：最多支持多长上下文，默认输出多少 token，单租户并发限制是多少，TTFT 和 TPOT 的 SLO 是什么，超过预算时排队、降级还是拒绝。推理引擎给了你更好的资源管理工具，但工程判断仍然要由人来做。
