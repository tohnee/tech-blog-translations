一篇 Inference 论文的加速比，至少依赖：

1. 模型与版本。
2. GPU/NPU 型号和数量。
3. 精度与量化格式。
4. runtime/engine 版本。
5. 输入长度分布。
6. 输出长度分布。
7. 并发和 batch 上限。
8. 基线配置与 SLO。

![](https://pic3.zhimg.com/v2-d817acdf7560d7e861b4c6e64e0fd7a2_r.jpg)

少了任何一项，数字都可能无法迁移。离线最大 batch 的吞吐高，不代表在线聊天体验好；单请求 batch 1 的最优 kernel，也不代表高并发服务最优。

指标还要成对看：平均 TTFT 与 P99 TTFT，TPOT 与 P99 TPOT，吞吐与 goodput，峰值显存与稳态显存，性能与任务质量。

TideKV 强调 Prefill 构造峰值，ZipFusion 强调 Attention 读取路径，Apple 研究强调硬件和 runtime 差异，PackServe 把 TPOT SLO 与 GPU-hours 放在一起，BLIS 则说明模拟适合缩候选空间但不能替代真实压测。

我写论文拆解时会把数字分成“论文报告值、换算值、本机验证值”。没有复现，就不写“已验证”。不同 batch、上下文和硬件的结果，也不直接相加。

一张好的基准表，作用不是制造冠军，而是明确告诉读者：这个收益在什么条件下成立，换环境后要重新测什么。

可以用三个具体误读检验自己有没有看懂：

1. 看到 TideKV 把构造期临时内存降低 83.89%，就写成“所有长上下文显存节省 83.89%”。论文测的是 A100 64K、batch 1 下的构造峰值，不是稳态缓存总量，也不是所有硬件。
2. 看到 Apple 上 KV 裁剪最快，就把它迁到 RTX 4090。实测在那里只有约 0.98 倍，技术方向相同，收益消失。
3. 看到 BLIS 的 6.7% 中位误差，就说模拟可以替代集群。论文的限制页明确列出拓扑、争用、PD 分离和专家并行等未覆盖部分。

一份可信结果最好同时带三层标签：

| 标签 | 含义 |
| --- | --- |
| 论文报告值 | 作者在明确条件下测到 |
| 换算值 | 公式推导，假设要写清 |
| 本机验证值 | 在目标硬件和脚本上实际跑过 |

没有 GPU 实测时，不能把换算值写成“已验证”。本系列的工具也只做结构验算。

最实用的复核顺序是：

1. 主结果能否回查到具体实验。
2. 基线是否同模型、同硬件、同精度。
3. batch、上下文和输出长度是否对齐。
4. 平均指标旁是否有 P99。
5. 显存峰值和稳态是否分开。
6. 性能旁边是否有质量。
7. 模拟、论文和本机数据有没有混写。

很多“推理加速”争论，不是技术不存在，而是两边比较的根本不是同一种服务。

我最后只保留一张最小复核卡：

```text
模型一致？
硬件一致？
精度一致？
输入/输出长度一致？
并发与 batch 一致？
基线是否有同等缓存？
是否同时报了平均和 P99？
质量是否仍然可用？
```

只要有一项答不上来，“加速几倍”就还不能进入工程决策。

论文里的最高值用于吸引注意，工程表里的 Pareto 前沿才用于选型。两者不要混。

如果表格里同时出现两篇论文，我还会检查它们的“快”是不是同一指标。Prefill 吞吐、Decode 吞吐、TTFT、TPOT、GPU-hours 和 goodput 不能互相替代。只有业务指标对齐后，技术指标才有比较意义。
