本文描述 **社区 sgl-project/sglang main 分支** 的 PD（prefill/decode）分离实现（2026-06-13）。

核心思路：**decode 先预分配 KV slots 并把目标地址告诉 prefill；prefill 作为单边 RDMA 写方主动搬运；首 token 以「值」随 KV 过去；decode 跳过 prefill 前向直接进解码循环。**

## 为什么要做 PD 分离

LLM 推理两个阶段的特性完全相反：**prefill**（处理 prompt）是计算密集型、一次处理整段 prompt、吃满算力；**decode**（逐 token 生成）是访存密集型、每步只算一个 token、吃满显存带宽但算力空闲。

**混部（P、D 跑在同一实例）时这两个阶段会互相拖累，是个双输局面**——因为同一实例每步只能跑一个 batch，且 P/D 共用同一块显存：

- **prefill 抢算力 → 拖高 decode 的 TPOT（每 token 延迟）**：prefill 的计算量由 prompt 的 token 总数决定，哪怕只有一个请求，只要 prompt 长（如 2000 token），这一步就要一次算完这 2000 个位置的注意力，耗时可能是 decode step 的几倍到几十倍（decode 每步只算 1 个新 token）。GPU 同一时刻只能跑一个 batch，调度器一旦插进来这么一个重 prefill，**正在解码的请求只能干等它算完**，下一个 token 迟迟吐不出来——用户感受就是吐字卡顿。
- **decode 占显存 → 拖高新请求的 TTFT（首 token 延迟）**：decode 请求从开始生成到结束，KV cache 一直挂在显存里，可能持续上千 token、占用很久；并发 decode 越多，被钉住的显存越多。而新请求要做 prefill 得先为整段 prompt 申请 KV 空间，**显存被解码请求占满时，新请求即使在排队也分不到空间进不来**。

你想保 decode 流畅就得少插 prefill，新请求就饿死；想多放 prefill，decode 就卡——单实例里这两个目标天然打架，没法同时调到最优。

PD 分离把它们拆到不同实例：prefill 实例只跑 prefill、用满算力，没有 decode 被它拖；decode 实例只跑 decode、显存只服务解码请求，不跟新请求抢入场显存。两边各按自己的特性独立扩缩容、独立优化 batch 策略，再通过 RDMA 把 prefill 算好的 KV cache 高速搬到 decode。

### 一次请求的全景（按时间顺序）

1. Router 选一对 (P, D) 实例，生成 bootstrap_room，把同一请求并发发给两侧。
2. D 侧建 receiver、向 P 的 bootstrap server 握手，拿到空闲显存后**预分配 KV 页**、把”写到哪些页”经 ZMQ 告诉 P。
3. P 侧建 sender、握手完成后跑 prefill 前向算出 prompt 的 KV 和第一个输出 token，发起 **RDMA 单边写**把 KV 直接写进 D 预分配的页，首 token 以”值”经 aux buffer 一起带过去。
4. D 侧轮询到传输完成（KVPoll.Success），读出首 token，**跳过 prefill 前向**直接进入自回归解码循环。

## 一、请求入口：Router（图顶紫框）

Router（sgl-router，Rust 实现，位于独立的 sgl-router 仓库、不在本仓库内）是整个 PD 分离的请求编排者。它在一个请求进来时做四件事（下面的函数名为 sgl-router 中的逻辑职责，具体命名以该仓库为准）：

1. **选 PD 对**：select_pd_pair 按负载/策略从注册的 prefill 池和 decode 池里各挑一个实例，组成本次请求的 (P, D) 对。
2. **生成全局唯一的 bootstrap_room**：generate_room_id 产生一个 64 位整数 room。这个 room 是贯穿整条链路的”请求指纹”——它既要在 P 侧配对出唯一的 KVSender、在 D 侧配对出唯一的 KVReceiver，又要在后续所有 ZMQ 信令、RDMA 元数据校验里充当请求标识。
3. **注入 bootstrap 信息**：inject_bootstrap_into_value 把 bootstrap_host / bootstrap_port / bootstrap_room 三个字段塞进请求体（host/port 取自上一步选中的 prefill 实例）。
4. **并发双发**：用 tokio::join! 把**同一个请求同时发往 P 和 D 两侧**，不是先 P 后 D 的串行，而是并发——这样 D 侧可以尽早开始握手和预分配，与 P 侧的 prefill 前向重叠。

两侧拿到请求后用途不同：

- **P 侧**只真正使用 room（bootstrap server 的监听端口用它自己配置的 disaggregation_bootstrap_port，不依赖请求里的 port）。
- **D 侧**用 host+port 主动拨号去连 prefill 的 bootstrap server，完成 rank 发现与握手。

当 prefill 开了 DP（data parallel，dp_size > 1）时，请求落到哪个 prefill DP rank 有两种路由方式（common/conn.py 的 KVSender.init）：默认由 router 显式指定 dp_rank（_register_prefill_dp_rank 去 bootstrap server 查询/注册）；只有把 load_balance_method 设为 “follow_bootstrap_room” 时，才用 `bootstrap_room % server_args.dp_size` 取模决定。后一种方式下 room 同时承担了 DP 路由，保证 P、D 两侧对同一请求算出同一个 DP rank、连到同一份 KV（若实际派发的 dp_rank 与取模结果冲突，默认报错，除非置 SGLANG_DISAGGREGATION_FORCE_QUERY_PREFILL_DP_RANK=1）。

## 二、KVPoll 状态机（底部状态条）

KVPoll 是一个请求在 PD 链路里的生命周期状态，定义在 base/conn.py 的 KVPoll 类，**五个状态用整数值排序**，这个排序是后续 MIN 规约的关键：

| 值 | 状态 | 含义 |
| --- | --- | --- |
| 0 | Failed | 握手超时、传输失败、节点故障——终态，触发 abort + 清理 |
| 1 | Bootstrapping | 刚建好 sender/receiver，正在握手发现 rank、交换内存基址 |
| 2 | WaitingForInput | 握手完成，等待对端发起/完成数据搬运 |
| 3 | Transferring | 数据搬运或某个前置依赖（元数据/staging/HiCache）正在进行中 |
| 4 | Success | 一切就绪，可以提交、进入下一阶段 |

### 2.1 为什么要跨 TP rank 取 MIN 规约

一个请求在 TP（tensor parallel）下被切到多个 rank，每个 rank 各自有一份 KV 分片、各自 poll 出一个状态。调度器**必须等所有 rank 都就绪才能推进**，否则某个 rank 抢跑会导致队列状态分叉、最终 hang 或读到半成品 KV。

实现上用 dist.all_reduce(op=MIN)（poll_and_all_reduce，utils.py）：因为状态值是按”就绪程度”递增编号的，取 MIN 等价于”以最落后的 rank 为准”——只要有一个 rank 还在 Transferring(3)，全体规约结果就是 3，没人能提交；只有所有 rank 都到 Success(4)，MIN 才是 4。这就是为什么状态值的数值顺序不能乱排。

> prefill 侧用的是 poll_and_all_reduce_attn_cp_tp_group（prefill.py），先在 attn-tp 组内规约、再在 attn-cp 组内规约，覆盖 TP×CP 两个维度。

### 2.2 Transferring 是「读到」的，不是「写入」的

**Transferring 不是 decode 调度器自己写的状态，而是它在轮询 Transfer 队列时「读到」的一个中间态**。decode.py 的 pop_transferred 在 poll 分支里把 {Bootstrapping, WaitingForInput, Transferring} 三个统统当「继续等」(`pass`)，只有读到 Success 才调 _commit_transfer_to_req 提交、读到 Failed 才走 abort 清理。

请求从 WaitingForInput 变成 Transferring 有**两类来源，机制完全不同**：

**① 主动推进（传输真正开始时置位，仅 nixl / mori）**——这是「正向」的 WaitingForInput → Transferring。prefill 侧后台 transfer_worker 从 FastQueue 取出一个 chunk、确认该 room 没失败后，**在发起 RDMA 写之前**就立刻调 update_status(room, Transferring)（nixl/conn.py；mori/conn.py），把这个 room 的共享状态翻到 Transferring；decode 侧的 KVReceiver.poll() 通过 check_status(bootstrap_room) 读到共享状态，于是 poll 返回 Transferring——含义是”对端已经开搬了，正在写我的显存”。

> **mooncake 主路径不走这一步**：mooncake 后端的 transfer_worker 在搬运过程中**不**显式置 Transferring（见 §三的 transfer_worker 分析），正常情况下 decode 侧观测到的是 WaitingForInput 直接跳到 Success。所以纯 mooncake、无任何门控时，Transferring 几乎不出现。

**② Success → Transferring 降级（底层 poll 已 Success，但还不能提交）**——这一类是”明明传完了，却被强行压回 Transferring”。降级动作发生在 MIN all-reduce **之前**（_apply_metadata_gate 在 poll_and_all_reduce 内部、规约前调用，utils.py），所以任一 rank 没就绪，MIN 规约就让全体继续等：

- **元数据门（最通用、后端无关，mooncake 也走）**：KV 本身传完了（poll=Success），但首 token 的元数据还没落地——具体判据是 decode 侧 metadata_buffers.bootstrap_room[metadata_buffer_index, 0] 仍然是 0（prefill 在 RDMA 写 aux 时会把真实 room 写进这个格子，见 §五的 set_buf）。room 还是 0 说明 aux 那一笔 RDMA 还没到，于是 _apply_metadata_gate 把该请求的 poll 从 Success 降级成 Transferring。这一步在公共 poll 路径里，**所有后端都会经过**。
- **staging 门**：开了 staging buffer 时（require_staging），即使底层 poll=Success，只要 staging_handler.is_done() 还是 False（decode 侧的 scatter 还没把数据从 staging 区铺到 KV 池），就降级 Transferring（poll_and_all_reduce_with_staging，utils.py）。
- **decode HiCache 门控 receiver**：开了 decode 端 HiCache 时，真正的 receiver 被 HiCacheRestoreGatedKVReceiver 包了一层；即使 KV 传输 Success，只要本地前缀恢复状态还是 PENDING（L2/L3 → L1 的回灌没做完），poll 就返回 Transferring（decode_hicache_mixin.py）。

> 所以 **Transferring 表示「数据搬运或某个前置依赖（元数据落地 / staging scatter / HiCache 恢复）正在进行中」**，是给调度器的”还不能提交”信号：要等 KV、首 token 元数据、staging 散射、HiCache 回灌全部齐活，请求才升到 Success 进入预构建批。即便 mooncake 后端自身从不置 Transferring，元数据门 / staging 门也会让 mooncake 部署短暂出现这个状态。

## 三、Prefill 侧（图左红泳道）：3 队列骨架 + staging 快路径

### 3.1 三个队列构成的骨架

prefill 侧把一个请求的生命周期拆成三段，每段对应一个队列（prefill.py 文件头的 docstring 就是这个设计）：

1. **PrefillBootstrapQueue**（prefill.py 的 PrefillBootstrapQueue 类）——存”正在握手”的请求。建好 KVSender 后请求先进这里，等 decode 侧把目标页索引发过来、握手完成。
2. **scheduler 通用 waiting_queue**——握手完成的请求进入调度器的通用等待队列，和非 PD 请求共用同一个 PrefillAdder 出队逻辑、参与正常的 batch 组装。这一步**没有 PD 专属队列**，复用主调度器。
3. **disagg_prefill_inflight_queue**——前向算完、已经发起 KV 搬运、正在等搬运完成（”在飞”）的请求。

事件循环有两个版本：event_loop_normal_disagg_prefill 和 event_loop_overlap_disagg_prefill（prefill.py），区别是后者把 GPU 前向与上一批的结果处理重叠（overlap scheduling）。两个循环每轮都做：收请求 → pop_bootstrapped 把握手完的灌进 waiting_queue → 跑一批前向 → process_disagg_prefill_inflight_queue 轮询在飞队列。

### 3.2 两个后台线程（图中黄框）

主事件循环只管”出队/入队/前向”，真正的网络握手和 RDMA 由两个常驻后台线程承担（mooncake 后端在 start_prefill_thread 里起）：

**① bootstrap_thread**（mooncake/conn.py 的 start_prefill_thread 内）——一个 ZMQ recv 循环，是 prefill 的”信令总机”。它在 server_socket 上收 decode 发来的多种消息，按第一帧的内容分派：

- room == “None”：decode 第一次建 receiver 时发来的**内存基址注册**（KVArgsRegisterInfo），记进 decode_kv_args_table，告诉 prefill”我这边的 KV 池长什么样”。
- room == 普通数字：decode 为某个请求发来的**目标页索引**（TransferInfo）。关键逻辑在这里——它把这条 info 存进 transfer_infos[room]，然后判断 `len(self.transfer_infos[room]) == required_dst_info_num`：**只有当所有需要的 decode rank 都把目标索引发齐了**，才调 update_status(room, WaitingForInput)，把这个 room 从 Bootstrapping 翻到 WaitingForInput。这正是 P1 建的 sender 能被 P2 观测到”握手完成”的时刻。
- room == “WATERMARK” / “STAGING_RSP”：staging 模式的水位/分配回执（见后文 staging）。
- room == “ABORT”：decode 侧主动中止通知，把对应 room 置 Failed 并回 ACK。

**② transfer_worker（×N）**——真正发起 RDMA 写 + 回传状态的工作线程池。它不是单线程：构造时建了 N 个 FastQueue + 配套的 N 个 ThreadPoolExecutor（mooncake/conn.py 的 MooncakeKVManager.**init**，self.transfer_queues）。请求按 session 端口哈希分片到某个 queue（add_transfer_request 里 `shard_idx = session_port_sum % len(self.transfer_queues)`），实现多线程并发搬运、互不阻塞。每个 worker（transfer_worker，mooncake/conn.py）循环 `queue.get()` 取出一个 TransferKVChunk，先检查 room 没失败，再对该 room 下的每个目标 rank 发起 RDMA 写，最后经 ZMQ 把 (room, status, prefill_rank) 回传给 decode（sync_status_to_decode_endpoint）。

> 这里的 mooncake transfer_worker 搬运过程中**不**显式置 Transferring——这正是 §二讲的”mooncake 主路径直接 WaitingForInput → Success”，与 nixl/mori 搬运前先置 Transferring 的区别由来。

### 3.3 主步骤 P1–P5（图左红框）

- **P1 create_sender**（prefill.py 的 create_sender）：为请求建一个 KVSender，bootstrap_addr 拼成 `{bootstrap_host}:{bootstrap_port}`。同时 _process_req 强制把 `max_new_tokens = 1`（prefill.py）——**prefill 只需要算出第一个输出 token，绝不在 prefill 侧做自回归解码**。建完 sender 请求进 BootstrapQueue，状态 Bootstrapping。
- **P2 pop_bootstrapped**（prefill.py 的 pop_bootstrapped）：每轮轮询 BootstrapQueue 里所有 sender 的 poll。当 bootstrap_thread 已经把某 room 翻到 WaitingForInput，这里就读到 WaitingForInput，于是调 finalize_bootstrap（prefill.py）：先 ensure_metadata_buffer 分配 metadata 索引（没空闲就这轮跳过、下轮再试），再按 `num_kv_indices - decode_prefix_len` 算出要传的页数（decode_prefix_len 是 decode HiCache 命中后告诉 prefill “可以少传的前缀长度”，见 §四），最后 sender.init 把页数和 metadata 索引登记好。完成后请求挪进通用 waiting_queue。
- **P3/P4 前向 + 发 KV**（process_batch_result_disagg_prefill，prefill.py）：请求从 waiting_queue 被组进 batch 跑前向，算出 prompt 的 KV 和第一个输出 token，把 token 追加进 output_ids，再调 send_kv_chunk(last_chunk=True) 发起搬运（搬运链路详见 §六，首 token 如何随 aux 过去见 §五）。然后请求进 inflight_queue。
- **P5 轮询在飞队列**（process_disagg_prefill_inflight_queue，prefill.py）：每轮 poll inflight_queue。读到 Success 就 release_kv_cache 解锁 radix tree、把请求标记完成并流式返回客户端；读到 Failed 就 abort + 累加 num_transfer_failed_reqs_total；读到 WaitingForInput/Transferring 则留在队列继续等。

> 术语澄清：这里的 **staging 指”暂存中转区”**（如同物流的集结区、ETL 的暂存表），不是部署语境里”上线前测试环境”那个 staging。它是 GPU/RDMA 编程的标准术语——数据先 gather 到一块连续缓冲暂存，再一次性搬走。代码里类名 StagingBuffer/StagingAllocator、env SGLANG_DISAGG_STAGING_BUFFER 都用这个词。

**staging buffer 快路径（异构 attn-TP 优化；为保持图简洁，SVG 只画对称 attn-TP 直写，staging 仅在此文字说明）**。transfer_worker 分三条路径派发（conn.py）：

1. send_kvcache（全池，MLA 或对称 attn-TP，conn.py）；
2. **_do_staging_transfer**（异构 attn-TP + 开启 staging，conn.py）；
3. 逐 slice send_kvcache_slice（conn.py）。

> 三者**互斥**（transfer_worker 的 if/elif，conn.py，一个 chunk 只走一条）：路径 1 send_kvcache 就是图中的「**RDMA 单边写**」——**MLA 或对称 attn-TP** 时 KV 布局匹配，直接 RDMA 写进 decode 的 KV 池页（无需 scatter）；路径 2 staging、路径 3 逐 slice 都只在 **异构 attn-TP** 时用，**staging 是逐 slice 的优化替代**（聚合小写）。所以「RDMA 单边写」与 staging 是**二选一**，不是先后/并行。无论走哪条，末块都照常 send_aux 把首 token 写进 aux 池（与 KV 路径无关）。

**为什么对称 attn-TP 只要 O(layers) 笔（直写）。** 两侧 attn_tp_size 相同时，每个 rank 持有的 head 集合一一对应，decode 侧某层的内存布局和 prefill 侧**完全一样**——一整层是连续的一大块，可以原样照搬。send_kvcache（conn.py）对**每一层**调一次 batch_transfer_sync，一笔就把”这一层、这些页”整块写过去（同一层里多个 token 的页地址打包进同一次 batch 调用）。所以笔数 ≈ 层数 ×（K、V）= **O(layers)**，与 token 数无关。这就是图中的「RDMA 单边写」。

**为什么异构 attn-TP 退化成 O(tokens × layers) 个小 RDMA（逐 slice）。** 两侧 attn_tp_size 不同时，每个 rank 持有的 head 集合就对不上，head 切片在两侧布局错位，没法整层照搬。分两种方向看（都以共 8 个 KV head H0~H7、同一层 layer 0 为例）：

**方向一：prefill TP=4 → decode TP=2（多合一）**——一个 decode rank 要的 head 在 prefill 侧**跨多个 rank**，得从多个 prefill rank 各拿一小段拼起来：

**方向二：prefill TP=2 → decode TP=4（一拆多）**——一个 prefill rank 持有的 head 要**拆成多份**发给多个 decode rank：

![](https://pic2.zhimg.com/v2-d07a3d29a22acd174c799846fc25e3e7_r.jpg)
*图4*

两种方向本质一样：传输的最小单元都是”**某层、某 token 槽位里的一小段 head 切片**“，源/目标地址对不上。send_kvcache_slice（conn.py）只能**给每个 token 的每个页槽位**单独算源/目标地址（process_layer_tp_aware 里 total_slices = token 数 × page 内槽位数），再对**每一层**各跑一遍。于是传输描述符 ≈ **token 数 × 层数**——每个 token 在每层都得描述一个小切片的搬运。”小 RDMA”就是这种粒度极细、数量爆炸的切片搬运，网卡被海量小请求拖慢、TTFT 升高（send_kvcache_slice 的 docstring 也明说会增大长序列的 TTFT）。

> **切片粒度澄清（图按 head 画，代码按 token 切）**：上图把每个 head 单独画成方块便于看清”哪些 head 对应哪个 decode rank”，但**实际传输并不按单个 head 拆**。send_kvcache_slice 里 `num_heads_to_send = src_heads_per_rank`、`heads_bytes_per_token_to_send = num_heads_to_send × bytes_per_head_slice_to_send`（conn.py），即**把该 prefill rank 持有的整组 head 打包成一个切片**——所以更准确的说法是「**每 token 一个切片**」，而非每 head 一个切片。以方向一 P-rank0（持 H0、H1）为例：token0 的 H0、H1 连续成**同一个描述符**，token1 的 H0、H1 是**另一个描述符**；同一层、同一份（K 或 V）下，这些描述符（total_slices = token 数 × page 内槽位数）会被打进**同一次 batch_transfer_sync 批量调用**一起提交——是”一起提交的多个独立描述符”，而非”合并成一笔连续拷贝”（token 槽位可不连续，故不能合并）。

**staging 的优化：gather 成连续块，再用少量大 RDMA 搬。** 既然小 RDMA 多的根源是”布局对不齐、切片散落”，那就**先在 GPU 本地把散落的切片聚合成连续内存**，再整块搬。staging 把搬运改成**分 chunk** 进行（_do_staging_transfer，conn.py，每次一个 chunk）：

![](https://pic2.zhimg.com/v2-f5dc123f9ec9aaa5f5f221924a3ff17b_r.jpg)

- **gather（prefill）**：Triton 融合 kernel gather_all_layers_to_staging（staging_buffer.py）把该 chunk **各层**散落的 head 切片聚合进 prefill 的连续 staging 区，send_kvcache_staged（conn.py）一次 _transfer_data RDMA 写到 **decode 的 staging 缓冲区**（**不是直接写 KV 池**）；非末块发 CHUNK_READY 通知（_send_chunk_ready，conn.py）。
- **scatter（decode，由 decode_thread 触发）**：decode_thread 收 CHUNK_READY（末块则在收齐 Success 时）→ handle_chunk_arrived / submit_chunk_scatter（staging_handler.py）→ scatter_staging_to_kv（Triton，staging_buffer.py）把 **decode staging 区 → KV 池**（按 req_to_token 槽位写 k/v_buffers，staging_handler.py），跑在独立 scatter_stream 上；**主线程** advance_scatter（staging_handler.py）检查 scatter 完成、释放 staging 分配并回传水位给 prefill（让其复用 staging 区）。

“大 RDMA”就是指 gather 之后**连续的一大块、一笔搬走**（每 chunk 一轮 gather + 一次大搬，不再逐 token）；笔数从”token × layer 笔小的”降到”每 chunk 若干笔大的”，趋近 O(layers) 甚至 O(1)（staging_buffer.py 顶部注释）。代价是 gather（prefill 侧）和 scatter（decode 侧 staging 区 → KV 池）两次 GPU 本地拷贝（Triton），由 decode_thread 触发、主线程收尾——**用两次本地拷贝换网络请求数的大幅下降**，与对称直写的”零本地拷贝”路径不同。

三条路径对比：

| 路径 | 适用 | RDMA 笔数 | 本地拷贝 |
| --- | --- | --- | --- |
| send_kvcache（直写，图中「RDMA 单边写」） | MLA 或对称 attn-TP | O(layers)，整层整块 | 无 |
| send_kvcache_slice（逐 slice） | 异构 attn-TP，未开 staging | O(tokens × layers) 小笔 | 无 |
| _do_staging_transfer（staging） | 异构 attn-TP，开 staging | 每 chunk 若干大笔（趋近 O(layers)） | gather + scatter 两次 Triton 拷贝 |

> **本质**：异构布局对不齐 → 要么忍受海量小 RDMA（逐 slice），要么先在本地 gather 成连续块、用少量大 RDMA 搬（staging）——用两次 GPU 本地拷贝换取网络请求数的大幅下降。

- 默认**关**：env SGLANG_DISAGG_STAGING_BUFFER（environ.py），buffer 大小 SGLANG_DISAGG_STAGING_BUFFER_SIZE_MB=64；**仅非 MLA**（MLA 下设置会报错，prefill.py）；目前接在 mooncake 后端。
- 配套：控制协议 STAGING_REQ/RSP + 水位（staging_handler.py），decode 端 StagingAllocator 环形缓冲，前向前预取钩子 maybe_prefetch_staging_for_batch（prefill.py，在 prefill GPU 前向期间让 decode 提前分配 staging）。

**prefill 侧超时**：只有 bootstrap 一处超时——SGLANG_DISAGGREGATION_BOOTSTRAP_TIMEOUT（environ.py，默认 **300s**，存在 common/conn.py）。sender 的 poll 在 Bootstrapping 状态下调 _check_bootstrap_timeout（common/conn.py）强制：等 decode 握手超过 300s 还没翻到 WaitingForInput，就置 Failed。**prefill 侧没有 inflight 独立超时**——KV 已经开始搬运后不再单独计时（搬运失败靠后端自身的 session 检测和 decode 侧 heartbeat 兜底）。

> 可观测性（prefill 侧 Prometheus 指标，定义在 observability/metrics_collector.py、经 scheduler_components/metrics_reporter.py 填充）：num_prefill_prealloc_queue_reqs（gauge，名为 prealloc 实为 Bootstrap 队列深度）、num_prefill_inflight_queue_reqs（gauge，在飞队列深度）；P2 bootstrap 失败累加 num_bootstrap_failed_reqs_total，P5 传输失败累加 num_transfer_failed_reqs_total（均为 counter）。

**prefill 的 HiCache（通用，非 disagg 专属）**：prefill **没有**像 decode 那样的 disagg 专属 HiCache（无 decode_hicache_mixin 的对应物、无 disaggregation_prefill_enable_radix_cache 开关、无 prefill×HiCache 调度钩子）。但它把算出的 KV 写进**通用** self.tree_cache（maybe_cache_unfinished_req，prefill.py；P5 release_kv_cache 解锁）——开 enable_hierarchical_cache 时这个 tree_cache 就是 **L1/L2/L3 分层 HiCache**，开 hicache_storage_backend（→ enable_hicache_storage）时还参与 **L3 存储层释放**（prefill.py）。它走的是**标准调度器的前缀缓存/复用**（目的为避免重算 prompt 前缀），不是 disagg 为 prefill 单独加的机制——这是与 decode 侧 disagg 专属 HiCache 的关键区别（HiCache 概念与 decode HiCache 见 §四）。

## 四、Decode 侧（图右蓝泳道）：decode_thread 收完成回传 + HiCache 本地前缀复用

### 4.1 三个队列构成的骨架

和 prefill 对称，decode 侧也是三段队列（decode.py 文件头 docstring）：

1. **DecodePreallocQueue**（decode.py，是 DecodeHiCachePreallocMixin 的子类）——存”已建 receiver、握手中或等显存预分配”的请求。这一段是 decode 的核心：它要在有空闲 KV 显存时，**先把目标页索引分配好并告诉 prefill**，prefill 才能开始 RDMA 写。
2. **DecodeTransferQueue**（decode.py，是 DecodeHiCacheTransferMixin 的子类）——存”页索引已发出、正在等 prefill 把 KV 写过来”的请求。
3. **通用 waiting_queue → 预构建批 → running_batch**——传输完成的请求进通用等待队列，再经 get_new_prebuilt_batch 组成”预构建批”（跳过 prefill 前向），最后并入 running_batch（get_next_disagg_decode_batch_to_run）跑自回归解码。

> 为什么 decode 要有专门的 DecodeReqToTokenPool（decode.py）：普通 ReqToTokenPool 下 #预分配 + #传输中 + #运行 共享 max_running_requests 配额；而 decode 分离希望**用空闲显存尽量多地预分配请求来喂饱 prefill**，所以把预分配/传输中的配额单独拆出来（pre_alloc_size），让 #running 单独受 max_running_requests 限制，避免预分配请求挤占解码并发。

### 4.2 完成通知机制：decode_thread 累计 per-rank 回传

decode 侧也有常驻后台线程（start_decode_thread，mooncake/conn.py）。它和 prefill 的 bootstrap_thread 一样是个 ZMQ 多路复用接收线程，按消息头分派：

- **(room, status, prefill_rank) 三元组**——这是核心的完成回传。P 的 transfer_worker 每写完一个目标 rank 的 KV，就经 ZMQ sync_status_to_decode_endpoint 把 (room, status, prefill_rank) 发过来。decode_thread 收到 status==Success 时，把这个 prefill_rank 记进 prefill_response_tracker[room]；**只有当累计到的 rank 数 == required_prefill_response_num_table[room]**（即所有应答的 prefill rank 都到齐），才调 update_status(room, Success)。这种”按 rank 累计齐才算成功”的设计，是为了正确处理 prefill 侧 TP/PP 切分——KV 是分片传的，少一片都不能算完成。
- **AUX_DATA**（_handle_aux_data）——首 token 等元数据的旁路传输消息。
- **CHUNK_READY / STAGING_REQ / WATERMARK**——staging 模式的控制消息（见 §三 staging）。
- **ABORT_ACK**——prefill 对 decode 中止通知的确认。

decode_thread 置好 Success 后，调度器主线程的 pop_transferred 再用 poll_and_all_reduce 跨 TP rank 规约读到这个状态（decode.py），才真正提交。**注意分工**：后台线程负责把网络回传”翻译”成共享状态，主线程负责”读状态 + 推进队列”，两者通过 request_status 共享字典解耦。

### 4.3 另外两个机制

- **decode 等 RDMA 超时**：receiver 的 poll 在 WaitingForInput 状态下调 _check_waiting_timeout（common/conn.py）强制——发出页索引后等 prefill 把 KV 写过来，超过 SGLANG_DISAGGREGATION_WAITING_TIMEOUT（environ.py，默认 **300s**）还没完成就置 Failed。这是和 prefill bootstrap 超时对称的另一处超时（全链路只有这两处）。
- **heartbeat_checker**（_start_heartbeat_checker_thread，common/conn.py，由 start_decode_thread 末尾触发）：decode 周期性 GET prefill 的 /health（默认 5s），连续失败 max_failures 次就认定 prefill 节点死了，调 _handle_node_failure 把挂在该节点上的所有在飞 room 直接置 Failed——这样 decode 不用干等上面那个 300s 超时就能快速失败、释放资源。
- **retracted_queue + resume_retracted_reqs**：显存压力下被回收（retract）的请求暂存在这里，等显存松动再恢复（process_decode_queue，decode.py）。

> 可观测性（decode 侧 Prometheus 指标）：num_decode_prealloc_queue_reqs、num_decode_transfer_queue_reqs（gauge，两个队列深度）；握手/传输失败分别累加 num_bootstrap_failed_reqs_total、num_transfer_failed_reqs_total（counter，与 prefill 侧同名、各自递增）；另有 pending_prealloc_token_usage（gauge）。HiCache 复用量折算进 req 的 cached*tokens*{device,host,storage}（decode.py），开分层缓存时还有 sglang:hicache_host_used_tokens / hicache_host_total_tokens。

### 4.4 主步骤 D1–D5（图右蓝框）

- **D1 建 KVReceiver**：构造时状态置 Bootstrapping（common/conn.py），向 prefill 的 bootstrap server 发起 init 握手；握手拿到 prefill rank 拓扑后翻 WaitingForInput。同时把自己的 KV 池基址注册给 prefill（room==“None” 的那笔 ZMQ）。
- **D2 预分配 + 发页索引**（pop_preallocated → _pre_alloc，decode.py）：当有空闲显存时，_pre_alloc 在 req_to_token_pool 里给请求分配 KV 页（多页可不连续）和一个 metadata 槽位，然后 kv_receiver.send_metadata(page_indices, aux_index, state_indices, decode_prefix_len=…) 经 ZMQ 把”请把 KV 写到这些页”告诉 prefill。其中 decode_prefix_len 在开了 decode HiCache 时会携带本地命中的前缀长度让 prefill 少传（详见下文 decode HiCache 节）。
- **D3 轮询传输完成**（pop_transferred → Success，decode.py）：读到 Success 后调 _commit_transfer_to_req（decode.py）从 metadata buffer 读出首 token、logprobs、hidden states 等，**并校验 bootstrap_room**——读出来的 room 必须等于本请求的 room，否则说明 metadata 槽位串了（缓冲区索引碰撞），直接 abort，防止读到别人的 token。校验通过则 output_ids.append 首 token，请求进通用 waiting_queue。
- **D4 构建预构建批**（get_new_prebuilt_batch，decode.py）：把请求标记成 PREBUILT、**跳过 prefill 前向**（prompt 的 KV 已经从 prefill 传过来了，不用重算）。
- **D5 自回归解码**：并入 running_batch（get_next_disagg_decode_batch_to_run，decode.py）跑正常的逐 token 解码循环。

### 4.5 HiCache 是什么（分层 KV 缓存）

HiCache = **Hierarchical KV Cache，分层 KV 缓存**：把 radix 前缀缓存（RadixCache）从「只在 GPU」扩展成跨三级存储下沉/回灌的 KV 复用体系，核心类 HiRadixCache(RadixCache)（mem_cache/hiradix_cache.py）。

**为什么**：GPU 显存小 → 前缀缓存装不下多少 → 共享前缀命中率低、得重算 prompt。HiCache 把 L1 淘汰的 KV 往下沉到容量大得多的 host 内存、再到存储；命中时回灌上来，避免重算（PD 分离里还能避免重传）。

**三级（device → host → storage）**：

| 级 | 介质 | 实现 |
| --- | --- | --- |
| L1 | GPU 显存 | 设备 KV 池 + radix 树（即普通前缀缓存） |
| L2 | host 内存（CPU RAM） | HostKVCache / MHATokenToKVPoolHost（mem_cache/memory_pool_host.py），L1↔L2 走 DMA |
| L3 | 外部存储（文件 / nixl / mooncake / 3fs…） | mem_cache/hicache_storage.py、mem_cache/storage/…，由 hicache_storage_backend 选 |

**开关**：–enable-hierarchical-cache 开 L1+L2（把 tree_cache 换成 HiRadixCache）；再配 –hicache-storage-backend 才有 L3（enable_storage = hicache_storage_backend is not None，hiradix_cache.py）。**机制**：write-through/back 往下沉、prefetch + load-back 往上回灌，由 controller 管异步 DMA。

**在 PD 分离里出现两处**：① **prefill**（§三）用通用 tree_cache，开 hierarchical 即 HiCache，目的省**重算** prompt 前缀（非 disagg 专属）；② **decode HiCache**（下文，disagg 专属）让 decode 侧自己维护分层前缀缓存，共享前缀**本地回灌**而非让 prefill 经 RDMA **重传**，省带宽。

### 4.6 decode HiCache 本地前缀复用（仅文字说明，图中未画）

decode_hicache_mixin.py（311 行）。**门控**：enable_decode_hicache = disaggregation_decode_enable_radix_cache AND enable_hierarchical_cache（scheduler.py）。

**做什么**：decode 端跨 L1（device radix）/ L2（host）/ L3（storage）做**本地前缀复用**——共享前缀**本地恢复**而不是从 prefill 重传。

- 入队时 _match_prefix_and_lock → _build_decode_prefix_match 匹配本地前缀（含 L3 命中长度查询）（decode.py，mixin ）。
- _pre_alloc **只分配 L1 缺口**，[prefix_len, total_prefix_len) 由 HiCache 回灌；把更大的 total_prefix_len（decode_prefix_len）告诉 prefill，**让 prefill 跳过本地已缓存的前缀**，少传 KV（decode.py）。
- L3 命中走后台预取 _start_hicache_prefetch（mixin ）。
- 本地恢复是一个 **HiCacheRestoreResult（PENDING/READY/FAILED）三相状态机**（mixin ）：A 推进在飞 L2→L1 DMA、B 入队新的 init_load_back、C 启动合并 DMA。
- **与传输的耦合**：恢复 PENDING 时 HiCacheRestoreGatedKVReceiver 会把 Success 降级为 Transferring（机制见 §二的”decode HiCache 门控 receiver”）；READY 后提交时 _commit_hicache_local_restore_to_req 把恢复的 KV 索引写回 req_to_token_pool、扩展 prefix_indices。FAILED 则中止 + 清理预取资源。
- 关键类：DecodePrefixMatch、HiCacheRestoreResult、DecodeHiCachePreallocMixin、DecodeHiCacheTransferMixin、HiCacheRestoreGatedKVReceiver。

## 五、内存池 / staging buffer（图中绿色块）

PD 分离里 decode 侧有两块预先注册到网卡（RDMA 可直写）的内存，都在启动时一次性分配，请求级别只是”分配槽位”而非”新建”：

- **KV 池**（设备 KV 池，分页）：存所有请求的 KV cache，按 page 组织。D2 的 _pre_alloc 为本请求分配若干页（页可连续也可不连续），把页索引经 ZMQ 发给 prefill，prefill 用 RDMA 单边写直接把 KV 写进这些页。
- **Aux 池**（MetadataBuffers，utils.py 的 MetadataBuffers 类）：存每请求的”首 token 元数据”。它不是按请求新建，而是一个定长池（ReqToMetadataIdxAllocator 管空闲槽位），每请求分到**一个固定槽位**。槽位里装一组定长张量：output_ids（首 token id）、output_token_logprobs、output_top_logprobs、output_hidden_states（spec decode 用）、cached_tokens（前缀缓存命中数），以及关键的 **bootstrap_room**——这个字段是元数据门和上下文校验的依据（见 §二、§四 D3）。注意 set_buf 里有个细节：单笔 RDMA 最小 64 字节，所以小字段（如 output_ids）都 pad 到 16 个元素的行。bootstrap_room 写在 [idx, 0]，decode 侧靠”它是否非 0”判断 aux 这笔 RDMA 到没到。
- **staging buffer**（**图中未画**——仅文字说明）：见 §三——异构 attn-TP 时的 KV 搬运聚合区，prefill 端 StagingBuffer（定长 gather 区）、decode 端 StagingAllocator（带 overcommit/水位的环形缓冲），staging_buffer.py。

### 5.1 首 token 交接与 KV 计算边界

关键边界：**prompt 的 KV 在 P 算、第一个输出 token（记 t₀）的 KV 在 D 算；全局每个 token 的 KV 只算一次，无重复计算。**（”第一个 token”指 prefill 采样出的输出 token，不是 prompt 首 token。）

- **P 传的 KV 只到 prompt 末尾。** send_kv_chunk（prefill.py）的 end_idx = min(req.fill_len, len(origin_input_ids))（再按 page_size 对齐 ），上界卡在 prompt 长度；起点 start_send_idx在开 decode HiCache（§四）时可 >0，少传 decode 本地已缓存的前缀。t₀ 的 KV 此刻不存在——prefill max_new_tokens=1（prefill.py），只对 prompt 跑一次前向、采样出 t₀，不把 t₀ 当输入再前向。
- **t₀ 以「值」交接，不是 KV。** set_buf 把 req.output_ids[0]（token id）连同 logprob/hidden 写进 aux buffer（utils.py），随 KV 一起 RDMA；D 端 _commit_transfer_to_req 用 get_buf 读出后 output_ids.append(…)（decode.py），**不重新采样**。
- **t₀ 的 KV 由 D 在首个前向里补算。** prepare_for_prebuilt（decode_schedule_batch_mixin.py；forward_mode = ForwardMode.PREBUILT；改编自 prepare_for_extend）把收到的 prompt KV 当作已就绪的 prefix_indices（**prompt 不重算**——”跳过 prefill 前向”指此），以剩余 token（含 t₀）为输入跑一次 PREBUILT 前向，算出 t₀ 的 KV 并采样出 t₁，随后转入正常 decode。

> **图文对应**：图中 P3「算 KV + 首 token」产出 t₀ → P4 写 aux + 红色「RDMA 单边写」把 KV 与 aux 送达 decode → D3「读首 token」取出 t₀。D4「跳过 prefill 前向」专指**不重算 prompt**；D 仍在并入 D5 前跑一次 PREBUILT 前向补算 t₀ 的 KV（这一步图中归入 D4→D5 段，未单独画框）。

## 六、KV 搬运 + RDMA 引擎

**搬运链路**（从主线程发起到后台真正写网卡）：

1. process_batch_result_disagg_prefill 调 send_kv_chunk（prefill.py）——计算本次要传的页索引区间 [start_send_idx, end_idx)，last_chunk 时顺带 set_buf 写 aux。
2. send_kv_chunk 调 sender.send()——把页索引交给 KVSender。
3. sender.send 内部调 add_transfer_request（mooncake/conn.py）——把请求按 session 端口哈希分片，put 进某个 FastQueue。这一步是**异步入队**，主线程不等搬运、立即返回继续跑下一批前向。
4. 后台 transfer_worker 从 FastQueue 取出 chunk，三路派发（§三的 send_kvcache / _do_staging_transfer / send_kvcache_slice 三选一）真正发起 RDMA 写。

这个”主线程入队、后台线程搬运”的分离，是 prefill 能不被网络 IO 阻塞、持续打满 GPU 的关键。

**RDMA 引擎**：底层是一个**全局单例** get_mooncake_transfer_engine()（distributed/parallel_state.py 返回 MooncakeTransferEngine，定义在 distributed/device_communicators/mooncake_transfer_engine.py），整个进程内所有 transfer_worker 共用这一个引擎。conn.py 取用它，底层批量写走 MooncakeTransferEngine.batch_transfer_sync（一次提交多笔 RDMA 写、批量同步等完成）。mooncake/utils.py 现在只剩 custom-mem-pool 辅助逻辑。

> 可观测性（搬运相关 Prometheus 指标，histogram）：kv_transfer_speed_gb_s（搬运带宽）、kv_transfer_latency_ms（搬运耗时）、kv_transfer_bootstrap_ms（握手耗时）、kv_transfer_alloc_ms（等显存分配耗时）、kv_transfer_total_mb（单请求搬运量）；另有 num_prefill_retries_total（counter，乐观 prefill 重试次数）。这些由 prefill 侧 P5 完成时统计、上报。

## 七、传输后端

TransferBackend = **mooncake / mori / nixl / ascend / fake**（utils.py 的 TransferBackend 枚举），由 get_kv_class(backend, KVClassType.…) 在运行时按字符串选出对应的 {KVManager, KVSender, KVReceiver, BootstrapServer} 四件套（utils.py）。除 fake 外，其余四个都继承自共享的 Common{KVManager,KVSender,KVReceiver,BootstrapServer}（common/conn.py）——也就是说**握手、bootstrap server、room 配对、状态机这套骨架是公用的，各后端只是替换底层”怎么把字节搬过去”的传输引擎**。前几章讲的流程（队列、bootstrap_thread、transfer_worker、decode_thread）以 mooncake 为样板，对其他后端同样成立。

### 7.1 mooncake（默认，NVIDIA 主路径）

本文前几章的样板后端。基于 Mooncake 的 RDMA 传输引擎，进程内全局单例 MooncakeTransferEngine（distributed/device_communicators/mooncake_transfer_engine.py），底层批量写走 batch_transfer_sync（见 §六）。功能最全：transfer_worker 的三路派发、staging 快路径、custom mem pool、heartbeat 等都首先在它上面落地。生产部署的首选。

### 7.2 mori（AMD / ROCm）

面向 AMD GPU 的 RDMA 后端（mori/conn.py），基于 [http://mori.io](http://mori.io) 的 IOEngine。从 [http://mori.io](http://mori.io) 导入 IOEngine / RdmaBackendConfig / PollCqMode 等，可配置 QP（queue pair）数量、CQ 轮询模式，并支持把 aux（首 token 元数据）也走 RDMA 传。它和 nixl 一样属于”搬运前先置 Transferring”的后端（见 §二①）——decode 侧能观测到显式的 Transferring 中间态。是 ROCm 平台上 mooncake 的对位实现。

### 7.3 nixl（NVIDIA NIXL 通用传输库）

基于 NVIDIA NIXL 库的后端（nixl/conn.py），通过 nixl_agent 管理传输。传输子后端可配——env SGLANG_DISAGGREGATION_NIXL_BACKEND 选 “UCX”（默认，基于 UCX 通信框架）等，SGLANG_DISAGGREGATION_NIXL_BACKEND_PARAMS 传 JSON 形式的后端参数。NIXL 把”注册内存描述符（reg_descs）+ 创建传输（create_xfer）”抽象成统一 API，适合想复用 UCX 生态、或在非 Mooncake 环境里跑 PD 的场景。同样是”搬运前置 Transferring”的后端。

### 7.4 ascend（华为昇腾 NPU）

面向昇腾 NPU 的后端（ascend/conn.py）。它**直接复用 mooncake 的四件套类**（AscendKVManager 继承 MooncakeKVManager 等），只替换底层引擎为 AscendTransferEngine（ascend/transfer_engine.py，又继承自 MooncakeTransferEngine）——引擎内部用华为的 memfabric_hybrid 的 TransferEngine，靠环境变量 ASCEND_MF_STORE_URL 指定中心化存储地址。也就是说 ascend = mooncake 的调度/协议骨架 + 昇腾专属传输引擎。注意它的 metadata buffer 因 NPU 限制放在 NPU 上、bootstrap_room 用 int64（见 utils.py 的 MetadataBuffers 对 is_npu 的分支）。

### 7.5 fake（健康检查 / Warmup 旁路，图中未画）

唯一**不继承 Common、直接实现 Base 接口**的后端（fake/conn.py），是个纯桩：send() 只把 has_sent 置 True、不做任何 RDMA，poll() 在 send 之后立即返回 Success。它不用于真实推理,只在健康检查和 warmup 时被自动选中（_is_fake_transfer，utils.py），目的是让 P、D 各自跑一个 dummy 请求自检、完全跳过真实 KV 传输（详见下面的 FAKE 旁路）。

图为正常 KV 传输路径；本节的健康检查/warmup **完全旁路真实 KV 传输**。/health 与 /health_generate 共用处理函数 health_generate（两个装饰器叠在同一函数，http_server.py）。PD 分离下 P、D 各跑一个 dummy 请求自检，无任何 P→D 搬运：

- **Router 不配对两侧**：各发独立 GET /health_generate 给 P 和 D，不注入 bootstrap_room/host。
- **dummy 请求打 FAKE 哨兵**：服务端构造 dummy 请求，disagg 下强制 gri.bootstrap_host = FAKE_BOOTSTRAP_HOST（”2.2.2.2”，utils.py）、bootstrap_room = 0（http_server.py）。
- **两侧据此切 FAKE 后端**：prefill 检测 bootstrap_host == FAKE_BOOTSTRAP_HOST（prefill.py）、decode 经 _is_fake_transfer（utils.py，decode.py）选 TransferBackend.FAKE。FAKE（fake/conn.py）是纯桩：send() 只置 has_sent=True、无 RDMA，poll() send 后立即 Success。
- **忙时直接丢弃**：实例非完全空闲时健康检查请求被跳过、视为健康（scheduler.py，is_health_check_generate_req(…) and not is_fully_idle(for_health_check=True)），FAKE 路径只在空闲时执行。
- 同套机制也用于 **warmup**（warmup.py）。注意 bootstrap server 自身另有轻量 /health（common/conn.py，_handle_health_check），仅供 §四 heartbeat 探活、不涉及传输。
