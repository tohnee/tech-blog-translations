故事是这样的，有一朋友对 TraceWeave 提了一个 issue：

人打开 Verdi，trace 到对应逻辑后，会把相关信号一股脑地拉进波形窗口一起看；而 TraceWeave，却经常是一个个找层次路径，再传入某个时刻获取点值。

一个像在看网，一个沿着点走，从这个角度看，TraceWeave 效率确实不高。

唉，听上去挺有道理的，而我是一个非常听劝的人，因为我知道这一坨屎山代码是如何堆起来的。

*TraceWeave 是我做的芯片仿真调试 MCP Server，通过 MCP（模型上下文协议），让 Claude Code、Codex 调用工具查日志、读 RTL 源码、找层次和连接关系，再从波形里取证。*

*项目在这里： [http://github.com/gokeshenzhen/TraceWeave](http://github.com/gokeshenzhen/TraceWeave)*

但我有一点点不安，因为几个月前，我已经给 TraceWeave 加过一个直方图功能，对，就是直方图。

当时我在做算法模块的根因分析，也就是 RCA，思路来自侧信道：密码算法的实现如果处理不好，功耗、执行时间这些旁路信息，都可能泄露内部行为。

如果把多组数据的分布用直方图的形式整理出来，是不是更容易看见规律，更快找到算法设计里的 bug？

这也挺有道理，我就跟 Claude Code 许个愿，让它做进去了。

是的，这个功能还在 TraceWeave 里面大家可以去翻一下代码，

只是我把它关了，为什么关掉，

当时做完后我没记错是做了一些测试结果并没有想象中那么好。

在遥测统计里，Claude Code 压根就不用这个工具，照样能沿着别的路线做根因分析。

我后来跟 CC 聊过这件事， 

没错，那会儿我的 CC 账号还没被封，

按我的记忆，它的答复大意是：直方图对人比较直观，但在已有上下文里，AI 可能直接从数值和关系中分析，不一定需要这个工具。

带着这个不确定性以及不安我还是想试试 

这个网状 debug 其实概念上非常类似于形式验证的影响锥 COI(cone of influence)，搞好了，那 TraceWeave 效率也能高一点也是很值得。

但我没想到为了这个功能国庆假期一大半时间我都出不了门，

![](https://pic1.zhimg.com/v2-30af168e8f56d780db0022d7d10b6d66_r.jpg)

Codex 跑的那几天，我经常性盯着屏幕，像是要把屏幕吃进去，偶尔拿起旁边的手机翻翻，哈哈傻笑，有时又看看电子书，打个哈欠，趴在桌上睡一会儿，再站起来伸个懒腰，拉一下单杠。

实现倒没拖沓，评测真的要了额度的老命。

幸好 10 月 2 号赶上了 Reset God 的一波重置，不然我这 5x 的额度，扛不住这么折腾。

![](https://picx.zhimg.com/v2-cc533ffc724b75dcba81e537e627cb17_r.jpg)

我原本只想看多给几根信号能不能少查几次，然后摁一下回车，"啪"，debug 效率上去，皆大欢喜。

但真跑起来，问题却复杂得多。

AI 是一个黑盒，得逐项核对，

模型拿到候选不等于用过，用过也不等于省时，

什么叫收益，一次实验数据足够吗，没有这个功能的 session 跟使用这个功能的 session 取证路线是一样吗，要是使用了这个功能的 session 效率更慢呢，可以断定这个功能无效吗。

我把路铺好，它未必走

原来的 `explain_signal_driver` 工具主要帮你找到驱动逻辑和源码位置。

这次加了一个可选的局部依赖包：把往上一跳的数据、控制、时钟、复位候选一起列出来，标明角色，并尽量对应到波形里的完整路径和具体位选。

哪些地方还没查全，也一起带回来。

比如查UART的 tx_q，就能顺带拿到tx_d、时钟、tick_baud_q等候选。

接着交给波形工具，比较时钟沿前后：数据准备好了没有，更新条件有没有成立。

原先得自己到处找的几根线，现在工具帮你先整理出来。听上去，应该能少绕一些路。

![](https://pic3.zhimg.com/v2-80e4d478eb7097379f7d2d55e59f81d4_r.jpg)

我先让模型自己决定用不用。五类任务，每类三组配对，合计30次独立运行。增强组的15次里，只有6次用了，请求了依赖包。

这一批，用依赖包的增强组整任务总token 多了1.9%。

耗时中位数从350.5秒到了368.5秒，多了5.1%。

严格预算内完成任务的次数，原组是11/15，增强组是9/15。

没有过预先定好的验收门槛，

我预设的门槛是至少得有 10% 的收益，不管是 token 还是耗时。

| 指标 | 原组 | 可选增强组 |
| --- | --- | --- |
| 整批总 token | 12,277,454 | 12,509,638 |
| 任务耗时中位数 | 350.5 秒 | 368.5 秒 |
| 严格预算内成功 | 11/15 | 9/15 |

token 是模型输入输出的文本计量单位，这里统计整段任务的各轮累计用量：

总 token 多了 1.9%，耗时中位数多了 5.1%，

完整工作流没过预先约定的验收。

我又固定 Source Graph，也就是解析 RTL 局部逻辑关系的后端，

选出 UART、DMA 的用例、DES 加密模块这三个局部任务，

强制一组关闭依赖、另一组开启。

每类三组配对，共 18 次，双方都在严格预算内完成任务.

| 局部任务 | 开启后 token 中位数变化 | 耗时中位数变化 |
| --- | --- | --- |
| UART | −18.1% | −3.5% |
| DMA | −4.3% | +1.8% |
| DES | +28.2% | +9.6% |

同一个功能，落到不同任务上，方向都能变：整批总 token 少了约 7%，总体任务耗时中位数只少了约 1.2%。

并没有观察到增强组补齐缺失证据的质量收益。

这份实现的最终归属是合入了主分支，在没有更多有利实验数据下我不敢默认打开，也不声称这个功能能提升多少效率，而是提供了一个参数给到 AI 自主选择。

非常偷懒的处理，但实在扛不住了，不管是我，还是 5x 的额度。

在对 explain_signal_driver增强实现的时候，还发现一个附带需求，

### MCP 回执字数太多，压缩有无显著收益

就是 explain_signal_driver返回 token 太多，加一个 compact 选项，

理由是很朴素：相同事实用紧凑格式装，少一些 JSON 排版空白，模型就少看一些文本。听上去，应该比“请它换一条路线”容易兑现。

这也是一个坑。

先查字节，三个任务各自固定的 driver 回执集合，

字节数分别少了 23.7%、25.5%、31.1%，下降比例的中位数为 25.5%，可以粗略说“少了约四分之一”。

但少掉的是这些回执的字节，不能换成“整个任务上下文少了四分之一”，也不能直接说“单条回执 token 省了 25%”。

接着跑完整任务：full 和 compact 各 9 次，共 18 次，固定 Source Graph，模型配置、提示和预算一致，每次新上下文、新 MCP 进程。

最终，整批总 token 从 **4,232,075** 降到 **3,936,330** ，少了约 **7%** ；

任务耗时中位数却从 **304.6 秒** 变成 **331.5 秒** ，多了约 **8.8%** 。

给回执减掉了一部分字，时间那一栏反而多了 26.9 秒。

| 局部任务 | compact 的 token 中位数变化 | 耗时中位数变化 |
| --- | --- | --- |
| UART | +13.0% | +10.9% |
| DMA | −16.9% | +11.1% |
| DES | −3.6% | −18.5% |

UART 两项都涨，

DMA省了 token 却等得更久，

DES 的 token 只少一点，时间倒是明显下降。

效果并不明显，甚至在某些场景还变差了

这批为什么更慢，我还不能全归因于紧凑格式，因为服务负载、缓存和路线波动没有完全拆开；工程上这份原型依然没合进主分支，留在本地研究分支里。 *这里需要说明一下，后续我实现并合入了另一版的回执，方案跟这个完全不一样，效果也还还行，这里卖个关子，大家感兴趣可以去翻代码 :）*

到这里，其实有一个问题很自然浮出来，就是

### AI 本身是否存在波动

如果不改功能、不换格式，只把同一道题原样再做几次，结果能差多少？

于是，我又在同一个 UART 局部问题独立跑了六次，

提示和 `Astra / max` 配置一致，每次新上下文、新 MCP 进程，不喂答案，全部使用 full。

这一批登记的有效样本就是六次。

| 运行 | 总 token | 完成耗时 |
| --- | --- | --- |
| R01 | 501,077 | 230.3 秒 |
| R02 | 346,791 | 234.4 秒 |
| R03 | 316,624 | 267.2 秒 |
| R04 | 367,503 | 246.0 秒 |
| R05 | 378,756 | 250.5 秒 |
| R06 | 305,490 | 230.8 秒 |

token 最少 305,490，最多 501,077，中位数 357,147，极差 **195,587** 除以中位数，就是 **54.8%** ； 

如果换成“最高比最低多多少”，则是约 64.0% ！

同一道题，同一套工具，交付要求都满足，token 能差出近20万。

耗时最短 230.3 秒、最长 267.2 秒、中位数 240.2 秒，

同样按“极差除以中位数”算，波动为 **15.4%。**

偏偏用了 50.1 万 token 的 R01 最快，230.3 秒；

用了 31.7 万 token 的 R03 最慢，267.2 秒，

只看 token 那列猜谁先结束，你大概会猜错。

这份用量是各轮输入与输出的累计，包含缓存命中的输入和重复送入的上下文；

缓存输入已包含在输入里，推理输出已包含在输出里，都不能重复加，所以 50 万 token 既不是最后写了 50 万字，也不能直接当实际费用。

六次的使用MCP 工具次数从 8 到 11，取证次序和查询组合也变了，多走几轮，上下文可能又跟着送进去； 

但四次同为 8 轮的运行，总 token 仍从 305,490 到 378,756，连轮数也解释不了全部差异。

我能回看它先查了哪根线、后读了哪段源码，却不能只凭这些记录，事先算出它会走多长。

时间考量在这六次里比 token 稳一些。

### AI 在芯片领域依然是个黑盒

Claude Code 负责人 Boris Cherny 的核心设计理念就是给 AI 提供必要的工具，并不设过多限制，让它能够自主观察、执行和验证。

因为 AI 就是一个巨大的黑盒。 

我说的黑盒，是大模型接进芯片调试后这种具体的不可预期：

回执能读、路线能回看、局部结论能复核，可光看接口多了什么、输出少了多少，还不能稳定预测 AI 会怎样走完任务。

如果一个人拍着胸脯说采用什么方式能省多少 token，

或者这个工具比较省 token，

要是不提供大量的场景评测数据支撑，我们权当广告来看。

时间是一个比较可靠的指标。 

是黑盒也是机会

在 Coding Agent 快速演进的阶段，我觉得这是国产 EDA 的机会：

原型越来越容易做，竞争会更多落到真实项目、工具接口和验收能力上；

老牌公司既有架构和工作方式却未必适合新的模型。 

在某种程度上模型用到 Opus5.5，Astra 级别，AI 就像一个许愿池。做出原型的门槛正在降低，那差别在哪里。

差别来自于如何在更多的实际项目摸爬滚打，如何在看清大模型能力之后对产品增删查改，如何跟着大模型演进的历程，随时调整自己步伐。

最后，

很多人包括我每天花在跟 AI 聊天的时间多过跟真人，在国庆假期多次拒绝出门，对朋友圈的假期旅行嗤之以鼻之后，我发现这几天我收获的只有自我怀疑。

连接人与人之间的真实生活，大量的真实经历是机器很难替代的，不然我们无法保持自我的一部分，变成 AI 在现实的智能代理。
