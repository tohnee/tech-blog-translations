## 为什么用tensorrt模型部署时，有的用Protobuf解析ONNX，有的用onnxparser解析ONNX

关于protobuf的介绍：[Protobuf | 爱编程的大丙](https://subingwen.cn/cpp/protobuf/)

ONNX是一种开放格式，用Protobuf（.proto）定义。Protobuf是Google的数据序列化工具，所以ONNX文件本质上是按照特定结构序列化的二进制文件。TensorRT需要一个解析器来读取ONNX模型并将其转换为TensorRT的内部表示，这样才能进行优化和部署。

ONNX 确实可通过 Protobuf 结构读写；但 **Protobuf 只能读/改模型结构**，不能自动把模型变成 TensorRT engine。TensorRT 的 `OnnxParser` 才是把 ONNX 解析进 TensorRT network 的工具。官方 TensorRT 文档也明确说 `OnnxParser` 用于把 ONNX 模型解析到 TensorRT network definition。

## 动态图和静态图的概念

[(47 条消息) 动态图、静态图 - 知乎](https://zhuanlan.zhihu.com/p/2046987707662989156)

PyTorch动态图 ， ONNX静态图

> **动态图：边运行边建图。**<br>**静态图：先把图建好，再运行。**

**计算图结构**：一个**有向无环图**，其中节点代表运算符（如卷积、矩阵乘法），边代表数据（张量）的流动

**需要注意的是，ONNX 的静态图**说的是计算流程固定，**并非意味着所有维度都必须固定不变。**它支持通过**符号维度**来表示动态大小。例如，你可以在导出模型时指定输入的批次维度（通常为第0维）或图像空间维度（如高度、宽度）是动态的，用符号（如 `batch_size`, `height`, `width`）来代替具体数字。这样，在推理时就可以接受这些维度在一定范围内变化的输入数据。

**动态图是什么？**

**动态图**就是：程序运行到哪一步，计算图就临时构建到哪一步。典型代表：**PyTorch 默认模式**。

例如：

```text
import torch

x = torch.tensor(2.0, requires_grad=True)
w = torch.tensor(3.0, requires_grad=True)
b = torch.tensor(1.0, requires_grad=True)

y = x * w + b
loss = y ** 2

loss.backward()
```

当程序执行到：

```text
y = x * w + b
```

PyTorch 才知道这里发生了乘法和加法，于是把它们记录进计算图。

执行到：

```text
loss = y ** 2
```

它又继续把平方操作记录进去。

最后执行：

```text
loss.backward()
```

PyTorch 根据刚刚临时构建出来的计算图，自动反向传播。

**动态图的特点，**最大特点是：

```text
代码怎么写，图就怎么建。
每次运行，图都可以不一样。
```

比如你可以写 if 判断：

```text
if x.sum() > 0:
    y = x * 2
else:
    y = x - 2
```

如果这次 `x.sum() > 0`，图里就是乘法。

```text
x ── ×2 ── y
```

如果下次 `x.sum() <= 0`，图里就是减法。

```text
x ── -2 ── y
```

也就是说，**动态图可以根据数据内容改变计算流程**。这对调试非常友好，因为它就像普通 Python 程序一样，哪里出错就能直接打印、断点、检查变量。

**静态图是什么？**

静态图就是：先把整个计算流程定义好，形成一张固定的图，然后再往里面喂数据运行。

典型代表：

```text
TensorFlow 1.x
ONNX
TensorRT engine
一些部署推理框架
```

静态图更像是先设计一条生产流水线：

```text
输入 → 卷积 → BN → ReLU → 卷积 → 输出
```

这条流程先固定下来。之后你不断把图片放进去，它都按照这条固定流程执行。

## 为什么对于一张640x640图片来说，YOLOv5预测框的总数量是**25200**(针对COCO数据集80类别而言)，每个预测框的维度是**85**

YOLOv5可能有三个不同的检测头，分别对应不同的特征图尺寸。比如，假设特征图的尺寸分别是80x80、40x40和20x20，这是因为输入图片是640x640，下采样倍数分别为8、16、32，这样得到不同大小的网格。每个网格单元预测的锚框数量通常是3个，所以总预测框数量应该是这三个特征图网格数乘以每个网格的锚框数，再乘以每个锚框对应的类别和坐标信息。

具体来说，80x80的特征图网格数量是80 * 80=6400，每个网格3个锚框，所以6400 * 3=19200。同样，40x40的特征图是40 * 40=1600，1600 * 3=4800。20x20的特征图是20 * 20=400，400 * 3=1200。将这三个数加起来，19200+4800+1200=25200。所以总共有25200个预测框。

## __global__核函数和__device__设备函数都是在device上执行，有什么区别

`__global__`函数是核函数，也就是从主机调用，在设备上执行的，而`__device__`函数是设备函数，只能在设备上调用，通常用于辅助核函数。

`__global__`和`__device__`函数**无法直接访问 CPU 的 Pageable/Page-Locked Memory**，必须通过`cudaMemcpy`在 Host 和 Device 内存间传输数据。

## 详细介绍一下在warp_affine_bilinear_kernel核函数中每个像素的通道和thread是怎么对应的

在核函数中，每个线程通过其 **全局索引** 确定负责的目标像素位置 `(dx, dy)`：

```text
int dx = blockDim.x * blockIdx.x + threadIdx.x; // 列坐标（水平方向）
int dy = blockDim.y * blockIdx.y + threadIdx.y; // 行坐标（垂直方向）
```

- **`dx`**：目标图像的列索引（对应图像宽度方向）。
- **`dy`**：目标图像的行索引（对应图像高度方向）。
- **每个线程唯一对应一个像素**：若图像尺寸为 `W×H`，则需启动 `W×H` 个线程。

每个线程负责处理 **同一像素的所有通道**（如 RGB 三通道）：

```text
// 目标像素内存地址计算（假设通道顺序为 RGB）
uint8_t* pdst = dst + dy * dst_line_size + dx * 3; // 3 表示 3 个通道

// 写入三通道值
pdst[0] = c0; // Red 通道
pdst[1] = c1; // Green 通道
pdst[2] = c2; // Blue 通道
```

## warp_affine_bilinear_kernel函数里的 pdst 不是函数执行结束之后就销毁了吗？有啥用

实际上，pdst指向的是通过参数传入的dst指针（uint8_t* pdst = dst + dy * dst_line_size + dx * 3;），而dst应该是在主机端分配的设备内存。因此，pdst实际上是在操作设备内存中的位置，即使函数结束，数据仍然保留在设备内存中。

虽然pdst本身是一个局部指针变量，存储在线程的栈上，但它的值指向的是设备内存中的地址。写入操作是通过指针直接修改设备内存中的数据，所以即使pdst变量被销毁，数据仍然保留在设备内存中。用户可能对局部变量的生命周期有误解，认为局部变量销毁后数据就不见了。但实际上，**这里的关键在于指针指向的内存位置，而不是指针变量本身。**CUDA核函数中的每个线程都会独立执行，每个线程的pdst指向不同的内存位置，写入操作是直接对设备内存的修改，这些修改在函数结束后依然有效。

另外，需要强调CUDA的内存管理机制。主机端通过cudaMalloc分配的设备内存，在核函数执行完成后依然存在，直到显式释放。因此，通过pdst写入的数据会一直保留在设备内存中，直到被主机端释放或覆盖。

## FP32和int8分别用什么关键字表示

FP32 和 int8 通常使用以下关键字来表示：

- **FP32**：通常使用**`float`**关键字来表示单精度浮点数，即 FP32 类型。例如，`float num = 3.14f;`声明了一个 FP32 类型的变量`num`。**FP32（单精度浮点数）**：占用 **4 个字节（Byte）的内存**。因为 1 字节等于 8 位（bit），所以 FP32 **总共占用 32 位**的存储空间。在这种表示方法中：<br>通常会用**1 位**来表示符号位（正或负），<br>**8 位**表示指数部分【采用移码（也称为偏移二进制）表示法，偏移量为 127，意味着实际存储的指数值是真实指数值加上 127】，<br>剩下的 **23 位**表示尾数部分【IEEE 754 标准采用隐含位技术，即对于规格化的浮点数（指数位不全为 0），默认尾数的最高位为 1（这个 1 不存储在尾数部分），只存储后面的 23 位小数部分。例如，假设尾数部分存储的二进制值为`101000...0`（共 23 位），由于隐含最高位 1，实际表示的二进制小数就是`1.101000...0`】

- **int8**：可以使用**`int8_t`**来表示 8 位有符号整数，它在`<stdint.h>`头文件中定义。例如，`int8_t num = -12;`声明了一个 int8 类型的变量`num`。无符号的 8 位整数则可以使用`uint8_t`表示。**INT8（8 位整数）**：占用 **1 个字节的内存，即 8 位**。它只能表示整数，所能表示的数值范围是 - 128 到 127（包括 - 128 和 127），或者 0 到 255（无符号整数的情况）

## 为什么线程块大小要设置成32的整数倍

在NVIDIA GPU中，**线程束**大小固定为32线程。若**线程块**大小不是 32 的整数倍，最后一个线程束会包含空闲线程（称为 ​不完全线程束），导致资源浪费。

## 训练时的batch size和warp size有对应关系吗？

现代深度学习框架（如PyTorch、TensorFlow）在底层自动处理GPU资源分配和线程调度。开发者仅需设置batch size等高层参数，无需干预warp级别的操作‌。例如，框架会根据硬件特性自动优化内存对齐或并行计算模式，使得batch size的选择无需与warp size对齐‌

### **为什么batchsize设为2的倍数**

很多时候会选 **2 的幂** 或 **8/16/32/64 的倍数**，是为了让矩阵维度更适合 Tensor Core、tiling、内存访问和库优化。但现代 cuBLAS/cuDNN 即使维度不对齐也常常能运行，只是某些情况下效率差一点。NVIDIA 文档说 FP16 通常 multiples of 8 更高效，INT8 常见 multiples of 16，A100 等架构还有更大的推荐对齐粒度。
