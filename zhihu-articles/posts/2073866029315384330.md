如果你训练完一个模型准备上线，大概率会听到有人说一句：「用 TensorRT 跑一下，能快好几倍。」

然后你照做了，模型确实快了，但心里始终有个疑问：**同样一张卡、同样一个模型、同样的输入，凭什么换个框架就能快几倍？算力又没变。**

这篇文章就来回答这个问题。不需要你写过 CUDA，但读完你会知道 GPU 推理的性能到底卡在哪、以及一个推理引擎能在哪些地方动手脚。

### 一、先建立一个直觉：解释执行 vs 提前编译

先讲个不那么严谨但很好用的类比。

**PyTorch 平时的运行方式，像 Python 解释器。** 你写一行 `y = linear(x)`，它就去调一个 GPU 函数算一下，算完等着你的下一行代码。它**不知道你下一行要干什么**——因为你随时可能写个 `if`，可能打印一下中间结果,可能直接改主意。这种模式叫 eager execution（即时执行），它的最大优点是灵活、好调试，这也是 PyTorch 当年打败 TensorFlow 1.x 的核心原因。

**TensorRT 像一个 C 编译器。** 你把整个模型交给它，它说：「行，你先别急着跑。让我把整个程序看一遍。」然后它花几分钟甚至几十分钟做分析、重排、优化，最后吐出一个叫 **engine** 的二进制文件。这个 engine 里所有决策都已经固化好了，之后每次推理就是照着执行，不用再想。

一句话概括 TensorRT 的哲学：

> **Build once, execute many times.**（编译一次，执行无数次。）

它做的所有事情，本质上都是**把运行时的决策提前到编译期**。因为部署场景下模型是固定的、要跑几百万次，那么花十分钟做一次深度优化，显然非常划算。

> 如果你做分布式与并行计算，你会里面发现几乎所有大模型推理框架都是用了分布式与并行计算的技术。这里的TensorRT和Spark里的lazy technique，以及DAG优化非常类似。 --紫老头

而它具体优化了什么，可以拆成五层。

### 二、第一层：看到全局，才能优化全局

假设有个再普通不过的结构：

```text
输入 X → Linear → 加 Bias → GELU → 输出
```

PyTorch eager 模式下，执行流程是这样的：

```text
Linear
  ↓  产生一个中间结果，写进显存
Bias
  ↓  产生一个中间结果，写进显存
GELU
  ↓  最终结果
```

每一步都是独立的一次 GPU 调用。不是 PyTorch 笨，而是它**在执行 Linear 的那一刻，确实不知道下一步是什么**。

TensorRT 拿到的是整张计算图，于是它可以做一堆全局层面的事：

- **常量折叠**：编译期就能算出来的部分，直接算好存起来，运行时不用再算
- **消除无用节点**：训练时留下的 dropout、identity、没被用到的分支，直接删掉
- **BN 折叠**：把 BatchNorm 的缩放和偏移直接吸收进前面卷积的权重里——推理时 BN 的参数是固定的，完全可以合并，等于白赚一个算子
- **算子融合**：把上面那三步合并成一个

前三个都好理解。第四个「融合」是重头戏，也是最容易被误解的地方。

### 三、第二层：算子融合，省的不是函数调用

很多人以为融合的好处是「少了几次函数调用开销」。这个理解不能说错，但抓错了重点。

真正的原因，要从 GPU 的存储结构说起。

### GPU 真正的瓶颈往往不是算力

GPU 上的数据有几个存放位置，速度差异极大：

| 位置 | 大致带宽 | 大致延迟 | 类比 |
| --- | --- | --- | --- |
| 寄存器 Register | 10 TB/s 以上 | ~1 个时钟周期 | 手里拿着 |
| 共享内存 / L1 | 数 TB/s | 几十个周期 | 桌上放着 |
| L2 缓存 | 数 TB/s | 上百个周期 | 抽屉里 |
| 显存 HBM | 数百 GB/s ~ 数 TB/s | 数百个周期 | 楼下仓库 |

差了一到两个数量级。**计算单元本身很快，慢的是把数据从显存搬过来这件事。**

现在回头看没有融合的情况：

```text
Kernel 1：算 Linear
    ↓  把中间结果 Y 写回显存      ← 跑一趟仓库
Kernel 2：算 GELU
    ↓  再从显存把 Y 读回来        ← 又跑一趟仓库
    ↓  写出最终结果 Z
```

融合之后：

```text
一个 Kernel：
   算 Linear
     ↓  Y 就待在寄存器里，根本没离开芯片
   算 GELU
     ↓  写出 Z
```

**中间结果压根没出过芯片。** 这才是融合的核心收益。

### 为什么 element-wise 算子尤其需要融合

像 GELU、加法、LayerNorm 这类逐元素操作，有个共同特点：搬一个数进来，只做几次浮点运算，就得搬回去。

衡量这件事的指标叫 **算术强度（arithmetic intensity （AI） ）**，也就是「每读写一个字节，能做多少次计算」。这类算子的算术强度极低,意味着它们的耗时几乎完全由访存决定,跟 GPU 标称的算力峰值毫无关系。这种情况叫 **memory bound（访存受限）**。

所以融合的本质是：**把一堆访存受限的小算子，塞进一个计算受限的大算子里，让它们的访存成本被摊销掉。**

打个比方:你要去楼下仓库取货,取一件是跑一趟,取五件也是跑一趟。融合就是把五次单独的往返,合并成一次。

至于省下的那几微秒 kernel 启动开销,是顺带的赠品。

### 四、第三层：为同一个运算，挑最合适的实现

这一层是很多人完全没意识到的。

对于矩阵乘法 `C = A × B`，实现方式不是唯一的，而是有几十上百种：矩阵按多大的块切分、每个线程块负责多少、要不要沿 K 维拆分并行、流水线开几级、用不用 Tensor Core、数据按什么顺序摆放……

**关键在于，哪种实现最快是「看情况」的：**

- 矩阵又高又瘦，和又矮又胖，最优实现不一样
- batch = 1 和 batch = 128，不一样
- FP16、INT8、FP8，不一样
- 同样是 FP16，在 Ampere 架构和 Hopper 架构上，还是不一样

PyTorch 在运行时只能靠一些启发式规则,去 cuBLAS/cuDNN 这些库里挑一个「大概率不错」的实现——它总不能在你每次前向传播的时候，现场把几十种方案都测一遍。

TensorRT 可以，因为它在编译期，有的是时间。它会针对**你这张卡、这个 shape、这个精度**，把候选实现真的跑一遍计时,选出最快的固化进 engine。这个过程叫 **tactic selection**，本质上是一次小规模的自动调优（autotuning）。

这也解释了两个大家常遇到的现象：

1. **为什么 build engine 那么慢？** 因为它真的在跑 benchmark。
2. **为什么 engine 不能拷到另一台机器上直接用？** 因为选出来的最优方案是绑定特定 GPU 架构的，换卡（甚至换 TensorRT 版本）就必须重新编译。

### 五、第四层：降低精度，省的是算力还是带宽？

这可能是普通用户感知最强的一层——「量化」。

精度链条大致是：

```text
FP32 → FP16 / BF16 → FP8 → INT8 → INT4
```

降精度带来三个收益，而且**它们的重要性在不同场景下完全不同**。

### ① 算得更快

现代 NVIDIA GPU 有专门的 **Tensor Core**，对低精度有独立的硬件通路。精度每降一档，峰值算力大致翻一倍。

### ② 存得更少

单个参数占用的字节：

```text
FP32 = 4 字节    FP16/BF16 = 2 字节    FP8/INT8 = 1 字节    INT4 = 0.5 字节
```

一个 70 亿参数的模型，光权重就是：

```text
FP16 ≈ 14 GB      INT8 ≈ 7 GB      INT4 ≈ 3.5 GB
```

对消费级显卡和端侧设备来说，这一栏决定的往往不是「跑多快」，而是**「能不能跑起来」**。

### ③ 搬得更少 —— 这一点对大模型最关键

这里值得单独展开，因为它解释了大模型推理最反直觉的一个现象。

大语言模型生成文字是**一个 token 一个 token 挤出来的**。而每挤出一个 token，都必须把**整个模型的权重**从显存完整读一遍——但实际参与的计算量，只相当于一次极小的矩阵向量乘法。

也就是说：**搬了 14 GB 的数据，只为了做一点点计算。**

这是极致的访存受限。结论就是：

> 大模型生成阶段的速度，基本上约等于 **显存带宽 ÷ 模型大小**。

所以把权重从 FP16 量化到 INT8，理论上生成速度直接接近翻倍——**这里省下的根本不是算力，而是带宽。**

顺带一提，大模型推理其实分两个阶段，瓶颈完全相反：

- **Prefill（处理你的输入提示词）**：所有 token 一起算，计算密集，是 **compute bound**
- **Decode（逐字生成回复）**：一次一个 token，访存密集，是 **memory bound**

理解了这一点，你就明白为什么「首字出现要等一会儿，但之后就哗哗地出」——这是两个不同的性能问题。

### 六、第五层：显存规划，静态图的隐藏福利

推理不只要算得快，还得别在显存分配上浪费。

因为整张图是静态的、每个中间结果的生命周期是可以提前算出来的，TensorRT 就能做**显存复用**：

```text
Layer 1 → 产生张量 A
Layer 2 → 产生张量 B      ← 此时 A 已经没人需要了
Layer 3 → 产生张量 C      ← 直接用 A 腾出来的那块显存
```

这跟编译器做寄存器分配是同一个思路：不是给每个变量都分一块地，而是算出一个全局最小的「工作区」，让大家轮流用。

PyTorch 也有自己的显存缓存分配器，做的事情类似,但它是**运行时**的动态分配——看不到未来，只能靠缓存池去逼近，做不到全局最优。

### 八、那 PyTorch 就不能编译吗？—— 关于 torch.compile

必须澄清一个过时的认知：**现在的 PyTorch 早就不只有 eager 模式了。**

PyTorch 2.x 有一整套编译栈：

```text
torch.compile
   ↓
TorchDynamo      —— 把 Python 代码里的计算图抓出来
   ↓
TorchInductor    —— 做图优化、生成 kernel
   ↓
Triton / CUDA
```

它同样能做图捕获、算子融合、代码生成和自动调优。方法论上，和 TensorRT 是**收敛的**。

那区别在哪？在**定位和包袱**：

- `torch.compile` 要兼顾训练和推理，要保留 Python 的语义，遇到搞不定的代码还得能优雅地退回 eager 模式继续跑。这些约束决定了它的优化必须相对保守。
- TensorRT 只服务于「NVIDIA GPU 上的固定模型推理」这一件事。没有包袱，就可以做更激进的融合、更彻底的方案搜索、更深的硬件专用优化。代价是灵活性和通用性。

顺带提一句 **Torch-TensorRT**，它是把两条路缝在一起：TensorRT 能吃下的子图交给 TensorRT，剩下的落回 PyTorch。这个产品的存在本身就说明——业界的判断是「各有边界」，而不是谁取代谁。

### 九、TensorRT 什么时候反而不划算？

科普文章如果只讲好处就成广告了。TensorRT 有明确的适用边界：

- **模型动态性太强。** 控制流复杂、输入 shape 频繁变化。动态 shape 只能按你给定的范围做折中优化，拿不到最优解。
- **有很多不支持的自定义算子。** 图会被切成一堆碎片，每个边界都要来回拷贝数据，融合收益全被吃光,搞不好比不优化还慢。
- **模型本身很小。** 本来就没多少 kernel 启动和访存可省，优化空间有限。
- **量化没做好。** 强行 INT8 但校准不到位，为了保精度到处插回高精度节点，最后既不准也不快。
- **工程成本被低估。** 编译一次可能几十分钟；engine 绑定 GPU 架构和 TensorRT 版本，换卡换版本就得重来。如果你要支持十几种机型，这个负担是实打实的。

所以：**快速迭代的实验阶段别碰它；模型结构稳定、要长期跑、对延迟和吞吐有硬指标的生产环境，它才真正发光。**

### 十、大模型时代：TensorRT-LLM 又叠了什么

传统 TensorRT 那套（静态图 + 固定 shape）在大模型上会撞墙：序列长度可变、KV Cache 不断长大、每个用户的生成长度还都不一样。

所以 NVIDIA 单独做了 **TensorRT-LLM**，在前面五层之上又加了针对性优化：

- **专用 Attention Kernel**：把 FlashAttention 那类实现集成进来，避免巨大的注意力矩阵落到显存
- **Paged KV Cache**：像操作系统管理内存分页一样管理 KV Cache，消除碎片，同样显存下能塞下更多并发请求
- **In-flight Batching**：某个用户生成完了就立刻放新请求进来，不用等整批人对齐。**这一项对吞吐的提升，往往比所有 kernel 层优化加起来还大**
- **FP8 / INT4 量化**：直击生成阶段的带宽瓶颈
- **多卡并行**：张量并行、流水线并行及其通信优化

值得注意的是，这些优化的重心已经从「单次计算更快」转向了「**调度和显存管理更聪明**」——这也是 vLLM、SGLang 这些引擎在做的事。

### 十一、总结：一句话和一个框架

如果只记一句话：

> **TensorRT 的加速，本质上是在减少三件事——计算量、kernel 启动次数、显存访问量，同时提高 Tensor Core 的利用率。而它之所以能做到，是因为它把决策从运行时提前到了编译期。**

前面五层（图优化 / 算子融合 / kernel 选择 / 低精度 / 显存规划），都是这句话的注脚。

而这个框架的价值在于，它**不只适用于 TensorRT**。你去看 ONNX Runtime、TVM、vLLM、llama.cpp、MNN、NCNN——不管名字多不一样，翻来覆去做的也就是这几件事。

下次再看到某个新推理引擎宣称「快 N 倍」，你可以直接问：**它省的是计算，是启动开销，还是访存？**

**真正的瓶颈取决于模型和场景：有时候是计算，有时候是 kernel launch，有时候是显存带宽，有时候是通信，有时候甚至是调度。优秀的推理引擎做的事情，就是尽可能准确地找到瓶颈，然后针对瓶颈优化。**
