01｜生成结果正确，专家 ID 为什么会错？

![](https://pic2.zhimg.com/v2-e7acb0750681129a890855336bf69733_r.jpg)

TBO 的核心思路是把一个 batch 切分为两个 microbatch，通过交错执行实现计算与通信重叠。

问题出现在 `return_routed_experts` 这条数据捕获路径上。

实际测试中，TBO-on 与 TBO-off 生成的 Token 完全一致，但捕获的 routed-expert ID 存在大量差异。

这说明需要重点检查的不是模型生成过程，而是**专家 ID 的捕获、存储和回读逻辑**。

## 02｜第一个 Bug：两个 Microbatch 的数据互相覆盖

![](https://pica.zhimg.com/v2-6082d1ae1363e0bf91f5fc4c27e9d276_r.jpg)

进一步追踪发现，两个 microbatch 共用同一块设备缓冲区。

原来的捕获逻辑没有考虑当前 microbatch 在完整 batch 中的位置，两个 microbatch 都从缓冲区第 0 行开始写入。

结果就是：后一次写入覆盖前一次的数据，而缓冲区后面的部分还可能保留零值或旧数据。

最终按照原始 batch 顺序回读时，自然得不到正确的专家 ID。

## 03｜修复思路：按照原始 Batch 的行区间写回

![](https://pic1.zhimg.com/v2-4e8f189538eb701f638463ee879d0650_r.jpg)

解决方法并不复杂：让每个 microbatch 明确自己对应原始 batch 中的哪几行。

通过 `tbo_parent_token_range`，捕获器可以获得当前 microbatch 的行区间，只更新这部分数据。

例如新增单测中的两个区间：

- 第一个 microbatch：`[0, 1)`
- 第二个 microbatch：`[1, 4)`

两次写回后，缓冲区对应内容为 `[1, 2, 2, 2]`。

这样就避免了不同 microbatch 之间的写入覆盖。

## 04｜如何把行区间传递到捕获器？

![](https://pic1.zhimg.com/v2-daf0cf4a4ab983482d723c3e6de82da0_r.jpg)

修复的另一个关键点，是让捕获器拿到正确的执行上下文。

相关信息沿着以下路径传递：

**ForwardBatch → _StageExecutor → ForwardContext → RoutedExpertsCapturer**

`ForwardBatch` 保存当前 microbatch 的行区间信息，`_StageExecutor` 将其传入对应的 `ForwardContext`。

执行 MoE 时，捕获器通过当前上下文获取行区间，再决定数据应该写入的位置。

这种实现不需要改动 MoE 的专家选择算法，同时保持了非 TBO 路径的原有行为。

## 05｜这次 PR 实际修改了哪些模块？

![](https://pic3.zhimg.com/v2-186e71dd454f65f0f0c086a947a65c36_r.jpg)

整个 PR 涉及六个文件，主要分为三部分：

**执行上下文：** 在 `ForwardBatch`、`ForwardContext` 和 `_StageExecutor` 相关实现中传递 microbatch 的布局信息。

**捕获逻辑：** 修改 `routed_experts.py`，让捕获数据按照正确的源位置和目标位置写入。

**DeepSeek-V4 适配：** 补充非 EP DP 场景下的 Parent DP offset 计算。

此外，还扩展了原有的 routed-expert 单元测试，覆盖不同的 batch 切分和 DP 数据布局。

## 06｜第二个 Bug：DeepSeek-V4 的 DP 数据布局错位

![](https://pica.zhimg.com/v2-e87f04d25302e191d2325b577a53e5d2_r.jpg)

修复第一个问题后，还需要处理 DeepSeek-V4 非 EP DP TBO 下的另一种情况。

这里的 MoE 捕获数据包含跨 DP rank 汇集的行，并可能带有 padding。

但是，Parent Batch 回读数据时，使用的是自身的 DP 行布局。

**Child Gathered Layout 与 Parent Layout 并不相同。**

因此，即使已经知道 microbatch 在 Parent 中的行区间，也不能直接假设读取数据的位置和写入位置完全一致。

## 07｜分别定位 Source 和 Target

![](https://pic4.zhimg.com/v2-7e827a84769f800db217a1db78b04773_r.jpg)

第二个问题的关键是区分两个偏移：

**Source：** 当前 DP rank 的有效数据在 Child Gathered Layout 中从哪里开始。

**Target：** 当前 DP rank 在 Parent Layout 中的起始偏移。

具体实现中，Source 根据 Child 汇集后的各 rank 数据长度计算，Target 则根据 Parent 的 DP 数据长度确定。

最终再结合 microbatch 的行区间，将正确的专家 ID 写入对应区域。

本质上，这是一次**不同数据布局之间的索引对齐修复**。

## 08｜如何验证两个问题都得到解决？

![](https://pic4.zhimg.com/v2-253b5b55c69c845d840b65d0a69965bb_r.jpg)

针对这次修改，补充了三类单元测试：

**第一类：** 验证两个 microbatch 按照各自的 Parent 行区间写回，不发生覆盖。

**第二类：** 验证执行上下文能够正确传递行区间和 DP offset。

**第三类：** 覆盖非 EP DP 下不同 rank 负载、空 rank 和不均匀 batch 切分等情况，检查最终回读的专家 ID 是否正确。

测试重点不只是写入成功，而是确保**写入位置与后续回读的数据布局一致**。

## 09｜DeepEP 实际模型验证

![](https://picx.zhimg.com/v2-65e2500fabe15cc6ad7580aa96756105_r.jpg)

使用 Qwen3-30B-A3B FP8，在 DeepEP 场景下对比 TBO-on 与 TBO-off，每个请求生成 48 个 Token。

下表统计专家 ID 与 TBO-off 不一致的请求数量：

| DP Rank 负载 | 修复前 | 修复后 |
| --- | --- | --- |
| [32,32] | 64/64 | 0/64 |
| [3,29] | 32/32 | 16/32 |
| [1,31] | 32/32 | 1/32 |
| [0,32] | 32/32 | 0/32 |
| [8,8] | 16/16 | 0/16 |

可以看到，在多个负载组合下，错误的捕获结果得到明显改善。

部分不均匀负载仍然存在专家 ID 差异，可能与 batch shape 引起的数值敏感性有关。

整个实验中，**生成 Token 的差异始终为 0**。

## 10｜总结：两个 Bug，一条完整的数据捕获链路

![](https://pica.zhimg.com/v2-e4bf71c3b8d31604a14bab2d05070a6e_r.jpg)

这次 PR 解决了两个不同层次的问题：

**① TBO Microbatch 写入覆盖**

通过 Parent 行区间，将不同 microbatch 捕获的专家 ID 写到正确位置。

**② DeepSeek-V4 非 EP DP 数据错位**

通过分别计算 Source 和 Target，对齐 Child Gathered Layout 与 Parent Layout。

在 DeepSeek-V4 架构的非 EP DP 验证中，使用 8 层模型和 seeded dummy weights，不一致的路由数据行数从 **89,123 降到 0**，全零行数从 **62,918 降到 0**。

这次排查让我印象比较深的是：

**大模型推理系统中的正确性问题，不一定出在算子或模型计算本身，也可能出在异步执行、数据布局转换与状态捕获之间。**
