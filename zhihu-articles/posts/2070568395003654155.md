## 1 性能对比总表

### 1.1 7 个典型算子的实测数据

我们在 A100 80GB SXM 和 H100 80GB SXM5 上对 7 个典型算子做了横向对比，每个算子用 4-5 种实现方式跑同样的输入，结果如下：

| --- | --- | --- | --- | --- | --- | --- |
| vector_add (2²⁴) | 0.19 ms | 0.18 ms | - | - | 0.22 ms | +5.6% |
| softmax (4096×4096) | 0.42 ms | 0.45 ms | 0.38 ms | - | 0.65 ms | +10.5% |
| layernorm (4096×1024) | 0.15 ms | 0.16 ms | 0.13 ms | - | 0.20 ms | +15.4% |
| matmul (4096×4096) | 1.95 ms | 2.10 ms | 1.85 ms | - | 2.30 ms | +5.4% |

### 1.2 数据解读

**规律 1：Triton 在 pointwise / reduction 类算子上接近最优**

| 算子类型 | Triton vs 最优差距 | 原因 |
| --- | --- | --- |
| vector_add | +5-11% | 带宽 bound，Triton 自动向量化已接近极限 |
| reduction | +6-7% | Triton warp shuffle + shared mem 归约与手写几乎一致 |
| RMSNorm | Triton 略快 | Inductor 自动 fusion 比 CUDA 手写更激进 |
| layernorm | +14-15% | cuDNN 用了特殊 PTX 指令，Triton 难以匹配 |

**规律 2：cuBLAS/cuDNN 在标准 GEMM 上仍有 5-15% 优势**

cuBLAS 优势来自：

1. NVIDIA 内部架构 insight（如 A100 SM 内部数据通路）
2. 更激进的 SW pipeline（4-stage，Triton 默认 2-stage）
3. 特殊 PTX 指令（如 `ldmatrix`、`cp.async`、`mbarrier`）
4. 针对每代 GPU 单独调优的 micro-kernel 库

**规律 3：Flash Attention 类融合算子差距最大（25-30%）**

Triton FA2 vs FA2 官方稳定差 25%，原因：

1. FA2 官方用 Hopper 的 WGMMA 指令（async matmul），Triton 2.x 还未完整支持
2. FA2 官方有手写的 warp specialization（producer/consumer warp）
3. FA2 官方针对每个 (B, H, N, d) 组合预 tuning

### 1.3 Triton 何时接近 cuBLAS

| 条件 | Triton 表现 | 例子 |
| --- | --- | --- |
| 计算密度低（pointwise） | 接近最优 | vector_add、RMSNorm |
| 自动 tiling 足够 | 接近最优 | matmul 大 K（K>>M, N） |
| 标准 reduction | 接近最优 | sum、max、mean |
| 融合 pointwise + reduction | 接近最优 | softmax、layer norm |

### 1.4 Triton 何时有差距

| 条件 | Triton 差距 | 例子 |
| --- | --- | --- |
| 需要特殊 PTX 指令 | 5-15% | 大 matmul（cuBLAS 用 ldmatrix） |
| 需要 warp specialization | 15-25% | Flash Attention（producer/consumer warp） |
| 需要软件流水线深度 ≥4 | 5-15% | memory-bound 大循环 |
| 跨 SM 协作 | 较大 | grid.sync、persistent kernel |

### 1.5 性能差距的根因分析

**1. Tensor Core 指令覆盖差异**

cuBLAS 用 `mma.sync` / `wgmma.mma_async` 直接控制 Tensor Core，而 Triton 通过 `tl.dot` 间接调用。Triton 2.x 的 `tl.dot` 在 A100 上覆盖 m16n8k16（FP16），但在 H100 的 WGMMA（async）支持上仍不完整，导致 H100 上差距更大。

| 指令 | cuBLAS 使用 | Triton 2.x 支持 | Triton 3.0+ 规划 |
| --- | --- | --- | --- |
| mma.m16n8k16 (A100 FP16) | ✅ | ✅ | ✅ |
| mma.m16n8k8 (INT8) | ✅ | ⚠️ 部分 | ✅ |
| wgmma.mma_async (Hopper) | ✅ | ⚠️ 部分 | ✅ 完整 |
| wgmma.fence / wgmma.commit_group | ✅ | ❌ | ✅ |
| Blackwell tcgen05.mma | ✅ | ❌ | ⚠️ 规划中 |

**2. Warp Specialization 缺失**

Flash Attention 官方实现用 producer/consumer warp 模式：producer warp 专职加载 K/V 到 shared memory，consumer warp 专职计算，两组通过 mbarrier 同步。Triton 2.x 不直接暴露 warp specialization，编译器自动生成的 schedule 不如手写激进，导致 Flash Attention 差距 25%。

**3. 内存布局优化差异**

cuBLAS 在 matmul 时会根据矩阵 shape 自动选择 K-major / N-major layout，并通过 `ldmatrix` 指令高效加载。Triton 的 `tl.dot` 默认 layout 选择较为保守，对非标准 shape 的优化不足。

## 2 开发效率对比

### 2.1 代码行数对比

| 算子 | Triton 代码行数 | CUDA 代码行数 | 倍数 | 备注 |
| --- | --- | --- | --- | --- |
| vector_add | 20 | 80 | 4.0x | CUDA 含 malloc/copy/check 样板 |
| softmax | 40 | 150 | 3.75x | CUDA 含 shared mem 协同加载 |
| layernorm | 35 | 130 | 3.7x | CUDA 含 warp reduce 模板 |
| RMSNorm | 30 | 100 | 3.3x | CUDA 含 FP16/FP32 转换 |
| matmul (2D tile) | 80 | 250 | 3.1x | CUDA 含 shared mem + sync |
| matmul (Tiled + TC) | 120 | 400 | 3.3x | CUDA 含 WMMA/mma 指令 |
| Flash Attention v2 (前向) | 130 | 350 | 2.7x | CUDA 含 online softmax + TC |
| Flash Attention v2 (前向+反向) | 250 | 700 | 2.8x | CUDA 反向更复杂 |
| GQA + Sliding Window | 180 | 500 | 2.8x | CUDA 需重写索引 |

**统计**：Triton 平均代码量 ≈ CUDA 的 1/3，复杂算子（如 FA2）的差距反而较小（因为复杂度主要在算法逻辑而非样板代码）。

### 2.2 开发时间对比

| 算子 | Triton 开发时间 | CUDA 开发时间 | 倍数 |
| --- | --- | --- | --- |
| vector_add | 30 分钟 | 2 小时 | 4x |
| softmax | 1 小时 | 1 天 | 8x |
| layernorm | 1 小时 | 6 小时 | 6x |
| matmul (2D tile) | 3 小时 | 3 天 | 8x |
| matmul (Tiled + TC) | 1 天 | 1 周 | 7x |
| Flash Attention v2 | 1-2 天 | 1-2 周 | 7-10x |
| GQA + Sliding Window | 1 天 | 1 周 | 5-7x |

**统计**：Triton 平均开发效率 ≈ CUDA 的 5-10x，主要省时在：

1. 不写 shared mem 协同加载代码
2. 不写 `__syncthreads` / `__syncwarp`
3. 不写 warp shuffle 模板
4. autotune 自动找配置（vs 手写 benchmark 脚本）
5. JIT 编译无需 nvcc 调试

### 2.3 调试难度对比

| 维度 | CUDA 调试 | Triton 调试 |
| --- | --- | --- |
| 错误信息 | nvcc 编译错误晦涩（template 报错） | Python traceback，较友好 |
| 数值错误 | cuda-gdb / cuda-memcheck / NCU | Python print / NCU |
| 性能调试 | NCU + SASS 分析 | NCU + Triton IR dump |
| 内存越界 | segfault 或静默错误 | mask 缺失会读到垃圾值，但不 segfault |
| 死锁 | kernel 卡死需重启进程 | kernel 卡死需重启进程 |
| 边界条件 | 手写 if (i < n) | mask = offs < n 一行 |

### 2.5 工程实践对比

**1. 项目结构对比**

CUDA 项目典型结构：

```text
my_cuda_project/
├── CMakeLists.txt          # 构建配置
├── src/
│   ├── kernel.cu           # kernel 实现
│   ├── kernel_wrapper.cpp  # pybind11 / cffi wrapper
│   └── host.cpp            # host 代码
├── include/
│   └── kernel.h
├── tests/
│   └── test_kernel.cu
├── benchmarks/
│   └── bench_kernel.cu
└── setup.py                # 安装脚本
```

Triton 项目典型结构：

```text
my_triton_project/
├── kernel.py               # kernel + wrapper（一份文件）
├── test_kernel.py          # 测试
└── bench_kernel.py         # benchmark
```

**2. 部署对比**

| 步骤 | CUDA | Triton |
| --- | --- | --- |
| 编译 | nvcc -o ... 或 pip install . | 无（JIT） |
| 部署 | 拷贝 .so + 设置 LD_LIBRARY_PATH | 拷贝 .py |
| 首次运行 | 无开销 | JIT 编译 1-3 秒 |
| 跨 GPU 架构 | 需重新编译或包含多 PTX | 自动 JIT |
| 依赖 | CUDA toolkit + driver | 仅 driver + Python |

**3. 版本管理对比**

CUDA 项目版本升级风险：

- CUDA 11 → 12 可能有 ABI break
- PyTorch 版本变化影响 pybind11
- GPU 架构升级需重新编译

Triton 项目版本升级风险：

- Triton 自身版本变化较少 break API
- Python 3.x → 3.y 通常无影响
- GPU 架构升级自动适配

### 3.2 Triton-on-HIP 实践

AMD 通过 ROCm 6.0+ 官方支持 Triton-on-HIP，同一份 Triton 代码可以在 NVIDIA 和 AMD GPU 上运行：

```text
# 同一份 Triton softmax 代码
@triton.jit
def softmax_kernel(...):
    ...

# NVIDIA GPU
x_nvidia = torch.randn(4096, 4096, device='cuda')
softmax(x_nvidia)  # 走 NVIDIA PTX 后端

# AMD GPU（需要 ROCm 6.0+）
x_amd = torch.randn(4096, 4096, device='cuda')  # PyTorch 在 ROCm 上也用 'cuda'
softmax(x_amd)  # 走 AMD GCN/CDNA 后端
```

**实测性能对比（MI300X vs H100，softmax 4096×4096, FP16）**：

| 实现 | H100 | MI300X | 差距 |
| --- | --- | --- | --- |
| Triton | 0.22 ms | 0.28 ms | MI300X 慢 27% |
| 厂商官方库 | 0.19 ms (cuDNN) | 0.24 ms (rocDNN) | MI300X 慢 26% |

**结论**：Triton 在 MI300X 上的性能约为 H100 的 73-80%，与厂商官方库的相对差距一致，证明 Triton-on-HIP 已基本成熟。

### 3.3 实际案例：Meta Llama 3 训练栈

Meta 在 Llama 3 训练中混合使用 NVIDIA H100 和 AMD MI300X 集群，其训练栈的关键选择：

| 模块 | 选择 | 原因 |
| --- | --- | --- |
| Attention | Triton FA2 | 一份代码同时跑 H100/MI300X |

### 4.3 何时用 Triton

✅ **推荐用 Triton 的场景**：

1. **算子迭代快**：LLM 自定义算子（RMSNorm 变体、新型 attention），可能每两周改一次
2. **团队 CUDA 经验有限**：Python 入门门槛低于 C++/PTX
3. **跨厂商部署**：NVIDIA + AMD 混合集群
4. **性能要求 95% 即可**：教学、研究、原型、中等规模训练
5. **融合算子多**：Inductor 自动 fusion + Triton 手写 fused kernel
6. **快速验证想法**：JIT 编译，无需 nvcc 链接

### 4.4 何时用 CUDA

✅ **推荐用 CUDA 的场景**：

1. **极致性能场景**：H100 SXM 万卡训练，5% 性能等于 5% 训练成本
2. **已有成熟 CUDA 代码库**：迁移成本不值得
3. **需要 CUDA Graph / Stream 底层控制**：Triton 不暴露这些
4. **需要特殊 PTX 指令**：`ldmatrix`、`cp.async`、`mbarrier` 等
5. **需要 warp specialization**：Flash Attention 类 producer/consumer 模式
6. **嵌入式 / 边缘设备**：Triton 后端支持有限
7. **非 NVIDIA/AMD 厂商**：寒武纪 / 昇腾等需厂商自己适配

### 4.5 混合使用策略

实际工程中往往是混合使用：

```text
# 典型的混合栈（伪代码）
class LLMModel(nn.Module):
    def __init__(self):
        # 标准算子用官方库
        self.qkv_proj = nn.Linear(d, 3*d)  # 内部用 cuBLAS
        # 自定义算子用 Triton
        self.attn = TritonFlashAttention(...)  # Triton
        self.norm = TritonRMSNorm(...)         # Triton
        # 通信用 NCCL
        # ...

    def forward(self, x):
        # 用 torch.compile 把 pointwise 融合
        x = torch.compile(self.norm)(x)
        # Flash Attention 直接调 Triton kernel
        attn_out = self.attn(x)
        # matmul 走 cuBLAS
        out = self.qkv_proj(attn_out)
        return out
```

**混合策略原则**：

1. **标准 GEMM/Conv**：用 cuBLAS/cuDNN（厂商最优）
2. **Pointwise / Reduction 融合**：用 torch.compile + Inductor 自动生成 Triton
3. **复杂融合算子**：手写 Triton kernel（如 Flash Attention 变体）
4. **极致性能算子**：CUDA + CUTLASS（如 H100 上的大 GEMM）
5. **通信**：用 NCCL/RCCL，不要自己写

### 4.6 真实项目选型案例

**案例 1：vLLM 推理框架**

vLLM 是当前最流行的 LLM 推理框架之一，其算子栈选型：

| 模块 | 实现 | 选型理由 |
| --- | --- | --- |
| PagedAttention | Triton | 需要自定义 block 级 KV cache 访问，Triton 灵活 |
| RMSNorm | Triton | 算子简单，Triton 融合 + epilogue |
| RoPE | Triton | 多种变体（旋转/部分旋转），Triton 易扩展 |
| Silu + Mul (SwiGLU) | torch.compile | Inductor 自动融合 |
| GEMM | cuBLAS | 标准 GEMM，cuBLAS 最优 |
| Sampling | Triton | 自定义 top-p / top-k 逻辑 |
| 通信 | NCCL / custom | 自定义 all-reduce 优化 |

**案例 2：DeepSpeed 训练框架**

| 模块 | 实现 | 选型理由 |
| --- | --- | --- |
| Flash Attention | FA2 官方 | 训练性能优先 |
| RMSNorm | Triton | 融合 norm + epilogue |
| Optimizer (fused Adam) | Triton | 融合多 op，减少 launch |
| ZeRO 通信 | NCCL | 标准库 |
| Gradient clipping | torch.compile | 简单 fusion |

**案例 3：单兵研究员/小团队**

如果是单人或小团队做 LLM 研究，推荐极简栈：

- 全部用 `torch.compile(model, mode='max-autotune')`
- 标准 attention 用 `F.scaled_dot_product_attention`
- 自定义算子用 Triton
- 不碰 CUDA C++

这个栈在 A100/H100 上能达到 cuBLAS + 手写 kernel 训练性能的 90-95%，但开发效率高 5x。

## 5 编译与代码生成深度对比

### 5.1 编译流程总览对比

CUDA 是 AOT（Ahead-Of-Time）编译，Triton 是 JIT（Just-In-Time）编译。这不仅是技术差异，更影响开发节奏、部署形态和调试方式。

| 维度 | CUDA | Triton |
| --- | --- | --- |
| 编译时机 | 构建期（nvcc） | 运行期（首次调用） |
| 输入 | .cu / .cpp | Python 函数（@triton.jit） |
| 中间表示 | PTX → SASS | TTIR → TTGIR → LLVMIR → PTX → SASS |
| 产物 | .so / .cubin | 缓存 .cubin（~/.triton/cache） |
| 跨架构 | 需指定 gencode 或多 PTX 嵌入 | 运行时自动选 PTX |
| 编译错误暴露 | 构建期 | 运行期（首次调用） |

![](https://pica.zhimg.com/v2-b83cc22a599ae381cfd64e122b84f9c0_r.jpg)

### 5.2 IR 层级与可观测性

Triton 的最大工程优势之一是 IR 全程可观测。CUDA 的 PTX 可读但 SASS 闭源，Triton 的每一层 IR 都能 dump 出来，便于定位”是高层抽象的问题还是后端 lowering 的问题”。

| IR 层级 | CUDA 对应 | Triton 对应 | 可读性 | 获取方式 |
| --- | --- | --- | --- | --- |
| 高层 DSL | CUDA C++ | TTIR | ⭐⭐⭐⭐ Python 风格 | kernel.asm['ttir'] |
| GPU tile IR | - | TTGIR | ⭐⭐⭐ 含 block/warp 信息 | kernel.asm['ttgir'] |
| LLVM IR | - | LLVMIR | ⭐⭐ 较底层 | kernel.asm['llir'] |
| 汇编 | PTX | PTX | ⭐⭐ 统一格式 | kernel.asm['ptx'] |
| 机器码 | SASS | SASS | ⭐ 不可读 | cuobjdump -sass |

**实测：dump 一个 softmax kernel 的各层 IR**

```text
@triton.jit
def softmax_kernel(x_ptr, out_ptr, n_cols, BLOCK: tl.constexpr):
    row = tl.program_id(0)
    offs = tl.arange(0, BLOCK)
    mask = offs < n_cols
    x = tl.load(x_ptr + row * n_cols + offs, mask=mask, other=-float('inf'))
    x = x - tl.max(x, axis=0)
    num = tl.exp(x)
    den = tl.sum(num, axis=0)
    out = num / den
    tl.store(out_ptr + row * n_cols + offs, out, mask=mask)

# 触发编译
softmax_kernel[(4096,)](x, out, 4096, BLOCK=1024)

# 各层 IR
print(softmax_kernel.asm['ttir'])   # 最接近源码
print(softmax_kernel.asm['ttgir'])  # 含 num_warps / shared mem 分配
print(softmax_kernel.asm['ptx'])    # 最终汇编
```

TTIR 片段（已简化）：

```text
%row = tl.program_id(0) : i32
%offs = tl.arange(0, 1024) : tensor<1024xi32>
%mask = %offs < 4096 : tensor<1024xi1>
%x = tl.load %x_ptr, %mask, -inf : tensor<1024xf32>
%m = tl.max %x, axis=0 : f32
%x_sub = %x - %m : tensor<1024xf32>
...
```

TTGIR 片段（可见 block 级 lowering，已分配 shared memory 用于跨 warp 归约）：

```text
%x = tt.load %ptr, %mask, %other : tensor<1024xf32>
%m = tt.reduce %x {axis=0, kind=max} : f32
%x_sub = tt.sub %x, %m : tensor<1024xf32>
...
```

**对比 CUDA**：CUDA C++ 经过 nvcc 后只能看到 PTX，中间的 AST、优化 pass 不可观测，定位”为什么编译器没做某个优化”几乎只能靠经验猜。

### 5.3 编译器优化能力对比

| 优化项 | CUDA (nvcc) | Triton | 说明 |
| --- | --- | --- | --- |
| 自动 tiling | ❌ 手写 | ✅ tl.dot 自动 | Triton 核心优势 |
| 自动向量化 | ⚠️ 部分 | ✅ 完整 | tl.load 自动 coalesced |
| shared memory 分配 | ❌ 手写 __shared__ | ✅ 编译器推断 | 含跨 warp 归约临时区 |
| warp shuffle lowering | ❌ 手写 | ✅ 自动 | reduction 自动用 shuffle |
| 软件流水线 | ⚠️ 手写 cp.async | ✅ num_stages | Triton 自动插 pipeline |
| mask 向量化 | ❌ 手写 if | ✅ mask= 参数 | 自动处理非整除 |
| 常量折叠 / 死代码消除 | ✅ | ✅ | LLVM pass |
| 循环展开 | ✅ #pragma | ✅ tl.constexpr | 编译期展开 |
| 跨 kernel fusion | ❌ | ⚠️ Inductor 层 | torch.compile 才有 |
| Tensor Core 映射 | ❌ 手写 mma | ✅ tl.dot 自动 | Triton 隐藏 TC 细节 |

**关键差异**：Triton 把”如何用硬件”交给编译器，CUDA 把”如何用硬件”交给程序员。前者开发快但调优空间小，后者开发慢但能压榨最后 5%。

### 5.4 编译时间与缓存

JIT 是 Triton 的双刃剑：开发时无需 nvcc 链接，但首次运行有编译开销。

**实测：首次编译耗时（A100，冷缓存）**

| 算子 | Triton 首次编译 | CUDA 构建（含 nvcc） | 说明 |
| --- | --- | --- | --- |
| vector_add | 0.8 s | 8 s | CUDA 含 nvcc 启动 + 链接 |
| softmax | 1.2 s | 12 s | - |
| matmul (tiled) | 1.5 s | 18 s | - |
| Flash Attention v2 | 3.5 s | 35 s | Triton 含 autotune 20 配置 |
| autotune matmul (20 配置) | 25 s | - | CUDA 无 autotune |

**Triton 缓存机制**：

```text
~/.triton/cache/
├── <hash>/
│   ├── kernel.cubin        # 编译产物
│   ├── kernel.ptx
│   ├── kernel.json         # 配置元数据
│   └── lock                # 并发锁
└── ...
```

缓存 key 由 kernel 源码 hash + constexpr 参数 + autotune 配置 + GPU 架构构成。同一 kernel + 同一 shape 二次运行直接命中缓存，开销 < 1ms。

**生产环境坑点**：

1. **容器镜像未挂载缓存卷**：每次重启容器都重编译，首次推理延迟飙升
2. **autotune 配置过多**：20+ 配置首次编译可达分钟级，需预热
3. **多 GPU 架构混合集群**：A100/H100 各一份缓存，key 不通用
4. **分布式训练 rank 0 编译**：若未广播缓存，rank 1-N 各编译一次

**CUDA 的对应优势**：构建期一次性编译，运行时零开销，适合启动延迟敏感的推理服务。

### 5.5 编译产物的可移植性

| 维度 | CUDA | Triton |
| --- | --- | --- |
| 跨架构（同厂商） | 需 embed 多份 PTX 或重编译 | 运行时自动选 PTX |
| 跨厂商（NVIDIA→AMD） | 需重写为 HIP | 同源码走 HIP 后端 |
| 二进制分发 | .so 可直接拷贝 | 需带 .py 或预编译缓存 |
| 版本兼容 | CUDA 11→12 可能 ABI break | Triton 版本间 API 稳定 |

**实践建议**：

- 离线推理服务：用 CUDA（启动延迟低）
- 在线训练 / 研究：用 Triton（迭代快，缓存命中后无开销）
- 跨厂商部署：用 Triton（一份源码两份效益）

### 6.1 调试工具栈总览

| 工具类型 | CUDA | Triton | 说明 |
| --- | --- | --- | --- |
| 编译错误 | nvcc 报错 | Python traceback | Triton 更友好 |
| 数值调试 | cuda-gdb / printf | Python print | Triton 可直接 print tile |
| 内存越界 | cuda-memcheck / compute sanitizer | mask 缺失读垃圾值 | Triton 不 segfault 但结果错 |
| 性能分析 | NCU / Nsight Systems | NCU / Nsight Systems | 工具相同，解读视角不同 |
| IR 分析 | PTX（SASS 闭源） | TTIR / TTGIR / PTX | Triton 全链路可观测 |
| 死锁 | cuda-gdb | 重启进程 | 两者都难调 |
| Warp divergence | NCU + 手算 | NCU + tl.where 检查 | - |

**关键差异**：CUDA 的调试工具更底层（cuda-gdb 可单步到 SASS），Triton 的调试更高层（Python print 可直接看 tile 值）。

### 6.2 Nsight Compute 使用对比

NCU（Nsight Compute）对 CUDA 和 Triton kernel 同样适用，但解读重点不同。

**CUDA kernel 的 NCU 关注点**：

1. `smsp__inst_executed.sum` → warp 发射效率
2. `l1tex__t_sectors_pipe_lsu_mem_global_op_ld.sum` → 全局访存效率
3. `sm__warps_active.avg.pct_of_peak_sustained_active` → warp 占用率
4. 手写 shared mem bank conflict → `l1tex__data_bank_conflicts_pipe_lsu_mem_shared.sum`

**Triton kernel 的 NCU 关注点**：

1. 同样的 warp / 访存指标
2. 但更要对照 TTGIR 看”编译器是否按预期分配 shared mem”
3. Triton 自动生成的 pipeline 是否生效（看 `stall` 原因）
4. `tl.dot` 是否真的命中 Tensor Core（看 `smsp__pipe_tensor_op_hmma_cycles_active`）

**实测：同一个 matmul 的 NCU 输出对比**

| 指标 | CUDA 手写 | Triton | 差距 | 原因 |
| --- | --- | --- | --- | --- |
| 占用率 (occupancy) | 75% | 50% | Triton 低 | Triton 默认 num_warps=4，shared mem 用得多 |
| Tensor Core 利用率 | 82% | 68% | Triton 低 14pt | Triton tl.dot 的 tile 形状不够优 |
| L2 cache hit rate | 71% | 65% | Triton 低 6pt | Triton 未加 eviction_policy hint |
| shared mem bank conflict | 0 | 3% | Triton 有 | 编译器 layout 选择保守 |
| stall (long scoreboard) | 12% | 28% | Triton 高 | Triton pipeline 深度浅 |

**结论**：NCU 指标本身通用，但 Triton 的低占用率 / 高 stall 往往源于编译器保守选择，需要回看 TTGIR 才能定位”哪个 tile 决策导致”。

### 6.3 性能瓶颈定位方法论

![](https://picx.zhimg.com/v2-00ee68b84cbb747ebe56fb774453bafb_r.jpg)

**CUDA 与 Triton 的定位路径差异**：

| 瓶颈类型 | CUDA 定位 | Triton 定位 |
| --- | --- | --- |
| 计算不足 | 看 SASS mma 指令密度 | 看 TTGIR 的 tt.dot tile 形状 |
| 访存不足 | 看 shared mem 手写代码 | 看 TTGIR 的 tt.alloc 大小 |
| Pipeline 浅 | 手写 cp.async 深度 | 调 num_stages 参数 |
| Bank conflict | 手算 shared mem 索引 | 看 TTGIR 的 layout（较难） |
| Warp 占用低 | 算 register / shared mem 上限 | 调 num_warps 或拆 BLOCK |

### 6.4 数值正确性验证

GPU 数值错误最难调，因为可能不 segfault，只是结果悄悄错。

| 验证手段 | CUDA | Triton | 说明 |
| --- | --- | --- | --- |
| 单元测试 | GoogleTest + CUDA | pytest + torch.allclose | 两者都需写非整除 shape |
| 数值精度 | 与 CPU 参考实现比 | 与 PyTorch eager 比 | Triton 有现成参考 |
| 边界 shape | 手写 n=1, n=1023 | mask = offs < n 自动 | Triton 省心 |
| FP16 / BF16 舍入 | 手动控制 accumulation | tl.dot 默认 FP32 accumulate | Triton 自动 |
| 反向传播梯度 | 手写 grad kernel | torch.autograd 自动 | Triton 集成更好 |
| 数值回归 | 自建 baseline | torch.testing | - |

**Triton 的隐藏坑**：

1. **mask 缺失**：`tl.load` 不加 mask 会读越界，但不报错，结果含垃圾值
2. **reduction 维度错**：`tl.sum(x, axis=1)` vs `axis=0` 容易写反
3. **BLOCK 非整除**：BLOCK=128 处理 n=4096 没问题，n=4000 会读 96 个垃圾值（除非加 mask）
4. **dtype 隐式转换**：`tl.dot` 的 FP16 输入会自动转 FP32 accumulate，但中间 `tl.exp` 可能溢出

**CUDA 的对应坑**：

1. **race condition**：`__syncthreads()` 缺失导致读后写冲突，结果不稳定
2. **bank conflict**：shared mem 索引错位，性能掉但不报错
3. **warp divergence**：`if (i < n)` 在 warp 内部分歧，性能掉 2x
4. **out-of-bound**：越界访问可能 segfault 也可能静默错

### 6.5 实战：同一个 bug 的两种排查路径

**场景**：softmax kernel 在 n_cols=4000 时输出含 NaN，n_cols=4096 时正常。

**CUDA 排查路径**（约 4 小时）：

1. cuda-gdb 跑 n_cols=4000，断点看 shared mem → 发现最后一组线程读到 -inf
2. 检查 `if (i < n_cols)` 边界 → 发现 boundary tile 没初始化
3. 加 `if (i < n_cols) val = x[i]; else val = -inf;` → 修复

**Triton 排查路径**（约 30 分钟）：

1. Python print 最后一个 tile 的值 → 直接看到垃圾值
2. 检查 `tl.load` → 发现 `mask = offs < n_cols` 已加，但 `other=-inf` 没加
3. 加 `other=-float('inf')` → 修复

```text
# Bug 版本：other 默认 0，exp(0)=1 导致 sum 偏大
x = tl.load(x_ptr + offs, mask=mask)

# 修复版本：exp(-inf)=0，不影响归一化
x = tl.load(x_ptr + offs, mask=mask, other=-float('inf'))
```

**效率差异根因**：

1. Triton 可直接 print tile 值，CUDA 需 cuda-gdb 单步
2. Triton 的 mask + other 语义把边界条件集中在一行，CUDA 散落在多个 if
3. Triton 的 Python traceback 直接指到出错行，CUDA 的 segfault 栈可能不完整

**反向案例：性能 bug**

**场景**：matmul kernel 比 cuBLAS 慢 30%，找不到原因。

**CUDA 排查**：看 SASS → 发现 mma 指令密度低 → 改 shared mem layout → 修复（2 天）

**Triton 排查**：看 TTGIR → 发现 `tt.dot` 的 tile 是 32x32x16 → autotune 搜索更大 tile → 修复（半天）

但 Triton 也有排查不动的场景：编译器选择了保守的 shared mem layout，TTGIR 看不出问题，但 NCU 显示 bank conflict 3%。此时只能调 BLOCK 形状碰运气，而 CUDA 可直接改索引算式。

**结论**：

- 数值 bug：Triton 排查快 5-10x（Python print + 集中 mask）
- 性能 bug：两者都需 NCU，但 CUDA 的可干预空间更大，Triton 受限于编译器
- 极端性能：CUDA 优于 Triton，因为能控制到 SASS 级

### 9.3 给读者的最后建议

1. **先建立硬件直觉再学抽象**：直接学 Triton 会出现”知道怎么写但不知道为什么这样写”的问题，建议先读 CUDA ch1-3
2. **多写多测少看文档**：每个算子都自己实现一遍，对照 NCU 输出找性能瓶颈
3. **关注编译产物**：用 `kernel.asm['ttir']` / `TORCHINDUCTOR_DEBUG=1` 看 Triton/Inductor 生成的代码，理解编译器做了什么
4. **跟社区**：Triton 迭代快，关注 OpenAI Triton GitHub、PyTorch dev-discuss、triDAO Lab
5. **不要追求完美**：99% 场景下 Triton 已经够用，别为了 5% 性能损失重写为 CUDA
