> “提示词和代码一样，会积累技术债。”<br> “更聪明的模型配合更低的思考力度，往往比弱模型死磕高思考力度更便宜，且效果更好。”<br> “设计长周期 Agent 的核心原则，是把大脑和双手彻底解耦。”

大多数开发团队以为自己正在使用最前沿的大模型，但实际上，他们的应用远远没有触及模型能力的帕累托前沿（Pareto frontier）。在成本与质量的二维坐标系里，绝大多数系统都缩在曲线内部。原因不在于模型不够强，而在于工程配置上的滞后与惯性。

在 AI Engineer 峰会的技术分享中，Anthropic 技术团队成员 Lance Martin 拆解了他们的工程方法论。Lance 没有谈论宏大的模型架构演进，而是直接指出了当前 AI 应用开发中最普遍的病灶：开发者用两年前的提示词习惯去束缚今天的顶级模型，忽视基础的缓存经济学，在缺乏严谨评估集的情况下盲目调优，结果多花了冤枉钱，还把模型的智商拉低了。

大模型应用开发的重心，已经从早期的“手工提示词”，全面转向“清理历史负债、构建可攀爬的评估体系（Evals）以及设计高可靠性的运行时架构（Harness）”。对于真正在生产环境中落地 AI 的工程团队而言，理解并执行这套标准，是目前性价比最高的技术升级路径。

### 提示词里的技术债：你的经验正在拖累模型

过去两年里，行业里流传着大量所谓的提示词工程秘籍。开发者习惯在系统提示词里塞满各种指令，比如要求模型“一步步思考（think step by step）”，加上“请仔细复核你的工作”之类的验证，或者写上“请保持最大限度的严谨与周全”，甚至专门开辟一块草稿区手把手教模型怎么打草稿。

Lance 指出，这些做法放到今天的前沿模型（如 Claude Opus 最新系列）身上，已经全部沦为反模式（anti-patterns）。

新一代前沿模型在底层训练阶段就已经内化了极强的推理规划与自我验证能力，模型自己非常清楚什么时候该深入思考、什么时候该直接输出。强行在提示词里保留旧时代的“思考助推器”，最直接的后果就是诱发模型过度消耗 Token，导致推理延迟增加、API 账单膨胀。

更隐蔽的危害在于指令冲突。早期的模型指令遵循能力较弱，当一段冗长的历史提示词里出现前后矛盾的两条规则时，旧模型往往会糊里糊涂地忽略其中一条，系统勉强还能运转。但今天的前沿模型对指令极其敏感，面对相互矛盾的规则，模型会陷入逻辑纠结，直接导致输出质量下降。

那些曾经用来给弱模型兜底的拐杖，如今变成了绊倒强模型的绳索。

在一个包含 50 个客服工单的合成基准测试中，Lance 模拟了从旧版 Opus 迁移到新版 Opus 的过程。如果直接带着包含上述反模式的旧提示词迁移，虽然也能享受到一点新模型带来的性能提升和成本下降，但收益非常有限。一旦对提示词进行彻底审计，剔除多余的验证仪式和矛盾规则，系统的性能会再次出现显著跃升，同时 Token 消耗大幅回落。

为了降低清理门槛，Anthropic 直接在 Claude Code 中内置了 `checkup prompt-audit` 和 `claude api prompt-audit` 两个命令。前者用于检查开发者本地的 Claude Code 配置与技能（Skills），后者专门扫描调用 API 的业务代码库。工具会自动识别工作目录中的提示词反模式，结合目标模型的特性给出清理建议。

把提示词当成代码一样定期重构、偿还技术债，是释放新模型潜力的第一步。

### 提示词缓存与严格前缀匹配：白捡 72% 的成本降幅

如果说清理提示词能同时优化质量与成本，那么正确使用提示词缓存（Prompt Cache），就是在不损失模型性能的前提下白捡利润。

多轮对话和 Agent 应用有一个显著的运行特征：每一轮交互只新增极少量的信息（比如一次工具调用的返回结果），而绝大部分上下文在每一轮都在重复发送。提示词缓存的计费标准大约只有基础输入 Token 的十分之一，同时还能大幅降低首字延迟。在 Claude Code 团队内部，提示词缓存命中率（hit rate）是一个必须盯死的核心经济指标。

道理谁都懂，但很多工程团队在实际落地时却频繁踩坑。Lance 带着平台团队用诊断工具扫描了内部一批采用默认框架的基准测试任务，结果发现，仅仅通过重组提示词结构以修复缓存失效问题，就能在不改变任何模型表现的前提下，把运行成本最高砍掉 72%。

为什么缓存这么容易失效？核心机制在于提示词缓存采用的是“严格前缀匹配”。哪怕前缀里只变动了一个字节——比如某个动态生成的时间戳被不小心塞进了系统指令，或者工具列表的排列顺序发生了轻微变化——整段缓存就会失效，系统被迫按全价重新计算所有上下文。

这就要求工程师在组织上下文架构时，必须严格按照数据的生命周期进行分层排列：最顶层放置跨所有会话全局共享的系统指令（System Instructions）与工具定义；第二层放置项目级别的静态上下文（如 `CLAUDE.md` 和项目记忆）；第三层是单次会话的状态信息；最末尾才是每一轮递增的动态消息。通过 Claude Code 中的 API 诊断命令，开发者可以直接定位代码库里破坏前缀匹配的隐患，把这笔原本不该花的钱省下来。

### 评估集设计与自动爬山：把调优交还给模型

当基础的提示词清理和缓存配置完成后，要想进一步压榨业务表现，就必须引入评估（Evals）与自动爬山（Hill Climbing）机制。

现在的前沿模型具备极强的自我纠错与迭代能力。只要给模型提供一个结构良好的评估集和明确的反馈信号，模型完全可以在没有人类干预的情况下，自动修改系统配置、反复运行测试，像爬山一样一步步把业务指标推向高点。

但这里有一个致命的前提：你提供的评估集必须是真正“可攀爬的”。Lance 在一线观察到大量失败的自动优化案例，模型烧掉了海量 Token 却卡在原地动弹不得，复盘下来发现根本不是模型能力见顶，而是评估集本身不够好。

一个合格的评估集必须满足四个基本特征：模型档次越高（从 Haiku 到 Sonnet 再到 Opus），得分应当随之上升；给模型分配的思考 Token 越多，得分应当提升；在最强模型上依然留有提升空间（未饱和），且不能充斥根本无解的歧义题目；多次重复运行的方差必须足够低。

很多团队看着自己 80% 的评估准确率，以为还有 20% 的优化空间，殊不知剩下那 20% 全是指令模糊、连人类专家都无法达成共识的坏样本，或者是评分器本身的逻辑漏洞。

在涉及开放式文本生成的场景中，如何设计评分器尤为关键。Lance 给出了极其克制的实操建议：优先使用确定性的启发式规则检查；如果必须引入大模型充当裁判（LLM-as-Judge），绝对不要让模型在 0 到 10 或者 0 到 5 的任意刻度上打分，这种模糊刻度会产生极大的噪声。最稳妥的做法是拆解成多个清晰的二分类问题（好或坏、通过或不通过），或者采用成对比较（Pairwise Comparison，即对比 A 和 B 哪个更好，再汇总计算 Elo 分数）。

同时，必须用不同尺寸的模型对同一套评分标准进行交叉验证，如果连不同模型按照同一套标准打出的分数都大相径庭，说明评分规则本身就不合格。

此外，抽样构建评估集时还要警惕“对抗性抽样”陷阱。大模型的智力分布是参差不齐的（jagged intelligence）。如果开发者专门挑出 Sonnet 做错的题目组成评估集，等升级到 Opus 时可能会发现这些题瞬间被全部秒杀，导致评估集失去区分度。健康的评估样本应当源于业务的第一性原理和真实生产日志，而不是围绕某一代特定模型的短板去局部挖坑。

有了扎实的评估集，就可以启动 Claude Code 中的 `build-eval` 和 `hill-climb` 技能。为了防止自动爬山过程中最常见的“过拟合”——比如模型为了迎合评估集里的某道特殊题目，偷偷在提示词里写死特定短语或强行挂载生产环境根本用不到的 OCR 工具——该工具引入了经典机器学习中的训练集/测试集切分（Train/Test Split）机制。

模型在反思错误、修改提示词或技能文本时，只能看到训练集的表现；系统在后台同步监测测试集得分。一旦出现训练集高歌猛进、测试集纹丝不动的情况，过拟合警报就会拉响。

至于自动爬山修改的目标对象，Lance 建议优先从提示词和技能文档这类纯文本表面入手。文本与模型行为高度耦合，修改粒度可控；相比之下，直接让模型去修改底层的 Agent 框架代码，每一轮产生的代码差异过大，极易引入难以归因的系统混乱。

### 反直觉的成本工程：用最聪明的模型，出最少的力

在自动爬山的应用中，Lance 展示了一个真实案例：利用爬山算法专门针对“降本”进行寻优，最终在性能显著提升的前提下，把运行成本硬生生砍掉了 90%。

这个案例揭示了：**在许多复杂任务上，“高阶模型 + 低思考力度（low effort）”的组合，往往比“中低阶模型 + 高思考力度（high effort）”好用。**

很多开发团队为了省钱，习惯选用单价便宜的小模型，然后把思考力度（effort）拉满，指望靠“大力出奇迹”来弥补智商差距；或者在使用旗舰模型时，不假思索地默认开启最高思考力度。实际上，`effort` 参数控制着模型在解决问题时投入的思考深度与验证篇幅。一个基础智商极高的模型（如最新一代 Opus），在低思考力度下往往能一眼看穿问题本质，用极少的 Token 干净利落地给出正确答案；而单价便宜的模型在高思考力度下，会陷入冗长的反复试探与自我怀疑，消耗掉天文数字般的推理 Token，最后算总账反而更贵，效果还差一截。

在那个砍掉 90% 成本的客服基准测试中，爬山器从高思考力度的旧版 Opus 出发，给定“性能不低于基线、尽可能压低成本”的目标。算法自动搜索模型与思考力度的组合空间，先切到低思考力度的新一代模型拿下第一波降本增效，接着继续下探成本更低的模型档位，并在性能出现轻微滑坡时自动微调提示词把准确率救了回来。即便面对一个准确率已经饱和的评估集，工程团队依然可以用这套固定性能、单向压榨成本的爬山策略，把系统的经济账算到极致。

### 当 Agent 运行数天：大脑与双手必须解耦

视线拉远一点，根据评估机构 METR 的追踪曲线，大模型能够独立完成的任务时长正在经历指数级跨越。早期的 Claude Opus 3 只能维持大约 4 分钟的自主工作，那时的产品形态只能局限于代码补全或简单问答；到了 2025 年，模型能胜任一两个小时的人类等效工作，催生了 Claude Code 的普及；而现在，行业正在进入模型连续自主工作数天甚至更长时间的新阶段。

当一个 Agent 需要连续跑上两天两夜，底层运行框架（Harness）的设计逻辑就彻底变了。如果跑到大半夜代码沙箱崩溃了，或者进程意外中断导致上下文丢失，前期的计算投入就会全部打水漂；同时，让一个脱离人类视线连续运转几十个小时的程序直接持有生产环境的 API 密钥，在安全上也是不可接受的。

这正是 Anthropic 推出 Claude Managed Agents 背后的工程动机，其核心架构原则只有一句话：**将大脑与双手解耦（separating the brain from the hands）。**

在这套架构中，负责推理调度的 Agent 框架（大脑）、负责写代码和执行动作的沙箱环境（双手），以及记录全量状态的会话日志，被拆分成完全独立的组件。会话日志是一个只追加的独立持久化对象，借鉴了递归语言模型（RLM）将上下文对象独立于模型之外的思想。传统的长对话一旦执行上下文压缩，被压缩掉的历史细节就永久丢失了；而在解耦架构下，完整的会话日志始终独立存留，大脑可以通过工具随时按需回溯查询任何历史片段。无论是沙箱挂了还是推理框架崩了，编排器都能瞬间拉起新的实例，直接从会话日志中无损恢复状态。

在安全性上，系统引入了密码保险箱（Vaults）机制。Agent 在执行任务时只能引用密钥的句柄来完成外部调用，永远无法在明文层面直接读取密钥内容，从根源上杜绝了长周期自主运行带来的凭证泄露风险。

### 工程师的角色重塑：从拧螺丝到定义目标

把 Lance 分享的这五个模块拼合在一起，一幅现代 AI 工程团队的日常工作图景就非常清晰了：白天，工程师把精力花在清理提示词负债、优化缓存结构，以及结合真实业务数据打磨高质量的评估集；到了傍晚，把优化目标交给运行在安全解耦架构上的长周期 Agent，让它围着评估集跑一整晚的自动爬山；第二天早上来上班时，直接收获一个准确率更高、成本更低的新版配置。

在这个人机协作的新闭环里，繁琐的试错、日志初筛、甚至评估运行器的代码编写，都可以交由 Claude 辅助完成。但这绝不意味着人类工程师变得多余。恰恰相反，人类的审美、直觉与业务品味变得前所未有的重要。模型很擅长顺着给定的指标往上爬，但究竟什么指标真正代表用户的满意度？哪些边缘案例反映了核心业务逻辑的缺陷？测试集与真实生产分布之间是否存在偏差？这些顶层的目标定义与价值判断，模型无法代劳。

停止在陈旧的提示词里反复雕花，把工程重心转移到评估体系建设与上下文基础设施上来。解开套在前沿模型身上的旧手铐，技术的红利才能真正转化为业务账面上的质量优势与成本壁垒。
