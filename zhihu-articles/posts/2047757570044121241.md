### 先说个真事

去年我在双卡4090上部署**Qwen3-30B-A3B**（MoE架构，仅3B激活），FP8量化，TP=2。启动半小时，OOM。

日志里有一行我之前从没注意过的东西：`CUDA graph capture failed, falling back to eager mode`。

什么意思？我不知道。但加了`enforce_eager=True`之后确实不OOM了。

代价是吞吐从417 tok/s掉到280 tok/s，掉了三分之一。

我花了三天把这行日志从头追到尾。从`gpu_model_runner.py`追到`EngineCore`，追到`Scheduler`，追到`BlockManager`。最后搞明白了：MoE模型专家数量太多，CUDA Graph捕获时显存峰值比正常运行高出好几个GB，直接撑爆。

真正的解法不是禁用CUDA Graph——那是用性能换稳定。把`max_num_seqs`从128改成64，Graph捕获时的batch size上限降下来，峰值显存就够了，Graph正常捕获，吞吐也回来了。

**这三天让我想明白一件事：生产环境跑推理，不看源码就是蒙着眼开高速。**

### vLLM现在什么地位

GitHub 81.7k star，月增长稳定。推理赛道最活跃的开源项目。

对比一下就清楚定位了：

| 框架 | 特点 | 适用场景 |
| --- | --- | --- |
| TensorRT-LLM | NVIDIA亲儿子，性能顶尖 | 硬件固定、不改代码 |
| TGI | HuggingFace出品，简单 | 快速原型、轻量部署 |
| SGLang | 学术味重，新特性多 | 研究实验 |
| llama.cpp/Ollama | 本地轻量，消费级显卡 | 个人用户 |
| vLLM | 功能全、更新快、扛得住 | 企业生产 |

vLLM能在企业级部署里成为事实标准，核心就一点：**能扛事**。

100+模型开箱即用，HuggingFace上新模型，vLLM大概率隔天就支持。四种量化方案（GPTQ/AWQ/FP8/Marlin）全齐。OpenAI兼容API，改一行`base_url`就能接。

我用它跑了半年生产环境。GPU故障三次，断电两次，NCCL版本打架若干次。vLLM都扛住了。

不是我选的vLLM，是项目需要快速上线，试了一圈发现只有它能**在不折腾的前提下跑起来**。后来读源码，才发现设计得确实扎实。

### 为什么要熟读源码，而不是会用就行

### 调参不靠猜

`gpu_memory_utilization`默认0.9。我寻思显存紧张，改成0.95。两天后又OOM。

为什么？源码里写得清楚：这0.1的余量是给CUDA Graph和临时tensor留的。公式大概是：

```text
KV Cache = (总显存 × utilization - 模型权重) / block_size
```

utilization拉到0.95，Graph空间不够，捕获失败，回退eager模式，性能反而更差。

**调参靠猜，迟早翻车。每个参数背后都是一段代码逻辑。**

### 排障快十倍

推理服务出问题就几类：OOM、推理慢、结果不对、卡死。

每种情况在源码里都有对应的处理路径和日志。你知道这些逻辑在哪个文件哪个函数，排障速度就是别人的十倍。凌晨两点告警，十倍速度意味着能不能回去接着睡。

### 最重要的是：建立心智模型

vLLM的核心设计——PagedAttention管理KV Cache，Scheduler做请求调度，Continuous Batching提高利用率，Tensor Parallelism切权重——你以为只有vLLM这么干？

TGI这么干，TensorRT-LLM这么干，SGLang这么干，国内的MindIE也这么干。

大家都在解决同样的问题：显存不够、GPU不能闲、延迟和吞吐要平衡。方案大同小异。

**吃透vLLM，脑子里就有了一张推理引擎的通用地图。** KV Cache管理有几种方案、调度策略怎么设计、量化权重怎么加载、分布式通信怎么做算子切分——这些不是vLLM特有的，是领域通用知识。

然后有一天，客户说”我们用国产芯片，要用某某国产推理框架”。你慌不慌？

不慌。新框架名字没听过，但架构一眼就能看明白：哦这个是PagedAttention变种，那个是Continuous Batching调度策略，权重加载大同小异，通信换个库而已。核心设计都见过。

我之前从vLLM切到另一个框架，从读文档到跑通生产环境，两天。不是因为我聪明，是vLLM源码已经帮我建立了心智模型。**换框架就是换层壳，里面的东西你见过。**

面试的时候也一样。你说读过vLLM源码，能讲清楚PagedAttention怎么实现、Scheduler调度策略是什么——跟只会调参数的人，完全两个段位。

**技术资本不是会用某个框架，是理解架构后任何框架上手都快。话语权不是靠说，是你真的懂，问什么都接得住。**

### 环境准备

### 前置要求

- Python = 3.11
- CUDA = 13.1
- Git
- gcc/g++（编译CUDA扩展需要）

### 一步步来

**第1步：装系统依赖（openEuler 22.03 SP4）**

```text
yum install -y gcc gcc-c++ make
```

Ubuntu用户换成 `apt install -y gcc g++ make`。

**第2步：Clone源码，锁定版本**

```text
git clone https://github.com/vllm-project/vllm.git
cd vllm
git fetch --tags
git checkout v0.21.0
```

国内GitHub慢的话用Gitee镜像：

```text
git clone https://gitee.com/mirrors/vllm/
```

**第3步：创建虚拟环境**

```text
/usr/local/python311/bin/python3.11 -m venv /opt/vllm/venv
source /opt/vllm/venv/bin/activate
pip install --upgrade pip
```

**第4步：安装vLLM**

```text
pip install -e . -v -i https://pypi.tuna.tsinghua.edu.cn/simple --default-timeout=300
```

国内服务器用清华镜像，加长超时。如果清华源也超时，换成阿里镜像 `https://mirrors.aliyun.com/pypi/simple/`。

**编译时卡住？** 编译CUDA扩展需要从GitHub下载cutlass库，国内可能连不上。手动下载：

```text
# 从Gitee镜像下载cutlass
rm -rf /opt/vllm/.deps/cutlass-src
git clone https://gitee.com/git_mirror/cutlass /opt/vllm/.deps/cutlass-src

# 清掉之前失败的编译缓存
rm -rf /opt/vllm/.deps/cutlass-subbuild /opt/vllm/.deps/cutlass-populate-prefix /opt/vllm/build

# 用本地cutlass源重新安装
FETCHCONTENT_SOURCE_DIR_CUTLASS=/opt/vllm/.deps/cutlass-src pip install -e . -v -i https://pypi.tuna.tsinghua.edu.cn/simple --default-timeout=300
```

**第5步：验证**

```text
python -c "import vllm; print(vllm.__file__)"
# 应输出 /opt/vllm/vllm/__init__.py
```

> 图：安装成功截图，显示 `vllm-0.21.0+cu131` 已安装，虚拟环境激活正常

输出这个路径就说明加载的是你本地源码，改代码直接生效。

### 核心目录

记住这几个就够了：

```text
vllm/
├── entrypoints/       # API入口，HTTP服务器
├── v1/                # V1引擎（调度+执行）
├── model_executor/    # 模型执行、加载、量化
├── distributed/       # 分布式，TP/PP通信
├── attention/         # Attention后端
└── csrc/              # C++和CUDA kernel
```

最大单文件是`gpu_model_runner.py`，七千多行。整个项目约16万行Python。

但读源码不一定要装。VSCode装Python插件，能跳转定义、搜索引用就够了。我很多时候直接在GitHub网页看，搜索框比什么都好使。

### 版本说明

专栏基于**V1架构**。V1在2024年底成为默认引擎。

怎么判断你用的是V0还是V1？看启动日志，出现`EngineCore`和`MultiprocExecutor`就是V1。V0和V1的区别第12篇详细讲。

### 我的环境

服务器，openEuler 22.03，海光C86-3G 7390（32核，314GB内存）。双卡RTX 4090定制48GB，PCIe互连，无NVLink。

主力模型现已升级到**Qwen3.6-35B-A3B**（MoE+GDN混合架构，Agent编码能力超Qwen3.5-397B）。之前用的是Qwen3-30B-A3B，去年部署它时遇到的那些坑都在上面了。

生产环境：FP8量化，TP=2，64并发，**417 tok/s**。 开发调试：AWQ 4-bit单卡，32并发，210 tok/s。

海光CPU跑推理没问题，tokenize和采样都是CPU活，32核绰绰有余。并发上100的话tokenize可能成为瓶颈，后面讲调度时会细说。

踩过的坑除了前面说的`enforce_eager`，还有NCCL版本兼容性（CUDA 12.1和PyTorch 12.4打架，排查一整天）。GPU故障自动恢复倒是挺靠谱，vLLM的health check机制救了好几次。

第16篇量化实战全是踩坑记录，可以期待。
