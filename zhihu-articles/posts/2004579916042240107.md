## 1.前言

端侧npu推理跑llm和云端推理npu跑llm的一个主要区别点我理解是因为端侧的计算batch=1，没有并行输入的多个序列，所以端侧的llm模型不光token重要，时延也重要。如果我们不考虑访存瓶颈，假设端侧和云端针对一个相同size的模型都是100token/s，但是云端的batch是32，总输出token云端就是端侧的32倍，端侧你的输入是当前时间的图像和语音数据，你需要尽快的算完。所以我发现云端的npu都没有L1 L2，端侧的npu有L1 L2.

**所以核心差异：延迟敏感 vs 吞吐敏感**

| 维度 | 端侧NPU (Edge) | 云端NPU (Cloud) |
| --- | --- | --- |
| 优化目标 | 首Token延迟 + 每Token延迟 | 总吞吐 (Tokens/s) |
| Batch Size | =1 (单用户实时交互) | =32/64/128 (多用户并发) |
| 性能指标 | Time-to-first-token (TTFT) < 100ms | 总吞吐 = Batch × Token/s |
| 缓存层级 | L1/L2 Cache 至关重要 | 大容量HBM + 计算并行掩盖延迟 |

## 2.展开

### 2.1 为什么端侧必须有L1/L2？

1. **KV-Cache的局部性利用**

- LLM推理中，**90%以上的访存是KV-Cache的反复读取**（Attention计算）
- Batch=1时，每次只处理1个token，KV-Cache的访问模式是**高度顺序且局部**的
- **L2 Cache**可以缓存当前层的KV-Cache，避免每次去DDR/HBM取数
- 如果没有L2，每个token都要从主存读一遍KV-Cache → **内存墙直接压死**

2. **延迟掩盖失效**

- 云端靠**大Batch**实现"计算-访存"并行掩盖：当Batch=32时，计算一个token的时间可以掩盖读下一个batch数据的延迟
- 端侧Batch=1，**没有并行度可以掩盖延迟**，必须靠**Cache层级**减少访存延迟

3. **权重驻留策略**

- 端侧模型通常**量化到INT4/INT8**（7B模型约3.5-7GB），可以分层加载
- L2可以驻留当前层的权重，实现**层内计算零DDR访问**

### **2.2**云端为何可以"无L1/L2"？

这里的"无"是相对概念，实际是**架构权衡不同**：

```text
云端NPU（如NVIDIA H100）：
- 超大HBM带宽（3TB/s+）+ 高并行计算单元
- 通过Tensor Core的矩阵计算 + 大Batch来饱和算力
- Cache层级被"展平"进HBM控制器和Shared Memory，不强调传统L1/L2概念

端侧NPU（如Apple NPU、高通Hexagon、联发科APU）：
- DDR带宽有限（通常<100GB/s）
- 必须通过L1（~MB级）→ L2（~MB-十MB级）→ DDR的层级，逐级过滤访存
```

NPU 没有 L1/L2 Cache 作为缓冲，**tiling 过小会导致 DMA 启动开销主导，带宽利用率暴跌，计算单元空转**。

**NPU 的核心优化原则就是"避免小数据块计算"，也要避免batch过小。算子融合、**强制 batch 聚合也要用上。

1）下面给一个例子：

矩阵乘法 C = A × B

矩阵尺寸：M=4096, N=4096, K=4096 HBM 带宽：1.2 TB/s（NPU 典型值） 不同 tiling 策略：

| Tiling 块大小 | 计算量 | DMA 次数 | DMA 数据量 | DMA 时间 | 计算时间 | 瓶颈 |
| --- | --- | --- | --- | --- | --- | --- |
| 大 tile (512×512) | 137 GFLOPs | 64 次 | 512 MB | 0.43 ms | 0.5 ms | 计算 |
| 中 tile (128×128) | 137 GFLOPs | 1024 次 | 512 MB | 0.43 ms | 0.5 ms | 计算 |
| 小 tile (32×32) | 137 GFLOPs | 16384 次 | 512 MB | 0.43 ms | 0.5 ms | DMA 开销 |
| 极小 tile (8×8) | 137 GFLOPs | 262144 次 | 512 MB | 0.43 ms | 0.03 ms | 严重 DMA 瓶颈 |

**2）gpu为啥增大batch能立马增加吞吐**

**增加 batch 能提升吞吐的核心原因是：隐藏计算延迟、提高硬件利用率，而非 DMA 带宽不足（当然你如果增加batch到了dma搬运的上限再增加就没用了）**。

单 batch（batch=1）的问题：内存延迟暴露<br>

```text
时间轴 →
┌─────────┬─────────┬─────────┬─────────┬─────────┐
│ 加载 W  │ 等待    │ 计算    │ 等待    │ 存储    │
│ (DMA)   │ (空闲)  │ (GPU)   │ (空闲)  │ (DMA)   │
└─────────┴─────────┴─────────┴─────────┴─────────┘
     ↑        ↑        ↑        ↑        ↑
   3.35TB/s  计算单元  100%    内存延迟   3.35TB/s
            利用率低   峰值     暴露

问题：计算单元频繁等待数据，利用率可能 < 30%
```

大 batch（batch=32/64）：计算与通信重叠

```text
时间轴 →
┌─────────────────────────────────────────────────┐
│  加载 W (DMA)  │  计算 Batch 0-31  │  存储结果  │
│                │  (GPU 全速运行)   │  (DMA)    │
├─────────────────────────────────────────────────┤
│  权重复用 32 次  │  矩阵乘法充分利用 Tensor Core │
│  (摊销加载成本)  │  (计算密度最大化)              │
└─────────────────────────────────────────────────┘

效果：计算单元利用率 → 80-95%，吞吐提升 3-5x。或者像vllm那样多个batch交替搬运来隐藏流水也行。
```

**DMA 带宽 vs 实际需求**

| 硬件 | DMA (HBM) 带宽 | 单 batch 峰值需求 | 利用率 |
| --- | --- | --- | --- |
| H100 | 3.35 TB/s | ~100-200 GB/s | < 10% |
| A100 | 2.0 TB/s | ~80-150 GB/s | < 10% |
| 4090 | 1.0 TB/s | ~50-100 GB/s | < 10% |

DMA 带宽**严重过剩**，瓶颈在别处。真正的瓶颈：内存延迟 + 计算单元闲置

```text
┌─────────────────────────────────────────┐
│           内存层次延迟（典型值）          │
├─────────────────────────────────────────┤
│  L1 Cache (SRAM):        ~1  cycle     │
│  L2 Cache:              ~10-20 cycles   │
│  HBM (显存):           ~100-500 cycles  │
│  系统内存 (CPU):     ~1000-5000 cycles  │
├─────────────────────────────────────────┤
│  问题：数据从 HBM 到 SM（流式多处理器） │
│        的延迟导致计算单元空闲            │
└─────────────────────────────────────────┘
```

### 2.3 例子

假设7B模型，FP16，上下文长度4K：

```text
KV-Cache = 2 (K+V) × num_layers × hidden_size × seq_len × batch × sizeof(dtype)
```

| 指标 | 端侧 (Batch=1) | 云端 (Batch=32) |
| --- | --- | --- |
| KV-Cache大小 | ≈ 1G | 1G × 32 = 32GB |
| 每Token需读KV-Cache | 112MB (全量) | 3.5GB |
| 有效带宽需求@100tok/s | 11.2GB/s | 350GB/s |
| 实际策略 | L2缓存当前层KV-Cache，DDR读权重 | HBM直接吞吐，Cache不关键 |

## 3.总结

**更深层的架构启示**

我的这个思考其实揭示了**计算机体系结构的经典权衡**：**"当并行度不足时，必须通过存储层级优化来掩盖延迟；当并行度充足时，可以通过吞吐量优化来摊平延迟。"**

端侧NPU的设计哲学更接近**CPU的Cache层级**（低延迟导向），而云端NPU更接近**GPU的流式处理**（高吞吐导向）。

这也是为什么端侧NPU都会强调**大容量On-Chip SRAM**（几十MB级），而云端芯片强调**HBM容量和带宽**。

端侧LLM优化非常关键——**在Batch=1的约束下，访存延迟是头号敌人，Cache层级是核心武器。**
