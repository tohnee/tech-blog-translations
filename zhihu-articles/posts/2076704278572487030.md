我之前对 SGLang 的调度和并发一直理解得比较模糊，再加上如 PP 的一些并行策略就更懵逼了。

为了理清这些概念，我结合当前 SGLang 源码、[《从 KV Cache 到 Zero Overhead Scheduling，一文读懂 SGLang 的调度巧思》](https://zhuanlan.zhihu.com/p/1992587332189197731)以及 SGLang 官方文档，并借助 AI 进行资料整理和源码交叉核对，形成了这篇文章。本文从一条请求的生命周期出发，逐步解释客户端并发、服务端队列、Continuous Batching、Chunked Prefill、Decode batch 和 PP microbatch 之间的关系。

### 1. 先给结论

它们不是同一个东西。

SGLang 中至少有五种容易被统称为“并发”的量：

| 层级 | 典型参数或状态 | 真正含义 |
| --- | --- | --- |
| 客户端在途并发 | --max-concurrency C | 同时已经发出、尚未收到完整响应的 HTTP 请求数上限 |
| 服务端等待队列 | waiting_queue | 已到达 Scheduler，但尚未被本轮计算接纳的请求 |
| 服务端活跃请求上限 | --max-running-requests | Scheduler 和请求状态池允许同时维护的活跃序列上限 |
| 单次模型执行 batch | ScheduleBatch | 当前 engine step 真正交给模型 forward 的请求及 token 集合 |
| PP microbatch | --pp-max-micro-batch-size | Pipeline Parallelism 中，一条流水线 microbatch lane 最多容纳的请求数 |

最重要的理解方式是：

> 客户端并发描述“外面有多少请求正在等结果”；服务端调度描述“这一轮选择哪些请求、每条请求处理多少 token”。

因此，`C=8` 并不意味着每次 GPU forward 都是 8 条请求，也不意味着 Decode CUDA Graph 的 batch size 永远是 8。

### 2. 一条请求经历什么

一条生成请求的大致生命周期如下：

```text
客户端等待并发槽位
        ↓
开始 HTTP POST                         ← Benchmark TTFT 起点
        ↓
HTTP 接收、Tokenizer、请求封装
        ↓
Scheduler waiting_queue
        ↓
Prefill admission / KV Cache 分配
        ↓
一个或多个 Chunked Prefill step
        ↓
采样出第一个 token
        ↓
第一个有效输出返回客户端                ← Benchmark TTFT 终点
        ↓
进入 running decode batch
        ↓
每个 Decode step 生成一个 token
        ↓
EOS、stop condition 或 max_new_tokens
```

### 2.1 TTFT 包含什么

SGLang serving benchmark 在真正执行 HTTP POST 前记录起始时间，在收到第一个非空生成文本时计算 TTFT。因此：

```text
TTFT = HTTP/Tokenizer
     + 服务端排队
     + Scheduler 等待
     + Prefix Cache 查询
     + Prefill（包括所有 chunk）
     + 第一个 token 的采样和返回
```

TTFT **不包含**请求在客户端等待 `max_concurrency` semaphore 的时间。某条请求只有拿到客户端并发槽位、真正开始发送后，才开始计时。

对应源码：

- 客户端并发 semaphore：`python/sglang/benchmark/serving.py:1380`
- HTTP 请求前记录 `st`：`python/sglang/benchmark/serving.py:699`
- 第一个有效输出计算 TTFT：`python/sglang/benchmark/serving.py:748`

### 2.2 TPOT 与 ITL 看什么

请求产生首 token 后进入 Decode。普通自回归 Decode 每个 engine step 为每条活跃请求生成一个 token。

- **TPOT**：除首 token 外，平均生成一个输出 token 所需时间。
- **ITL**：客户端观察到的相邻 token 到达间隔。
- **E2E latency**：从发出 HTTP 请求到完整响应结束。

长输出场景中，Decode 排队、Prefill 插入、Scheduler 抖动和网络流式返回都会反映到 ITL；TPOT 更偏向请求自身的平均 Decode 速度。

### 3. Benchmark 的 `C=8` 到底是什么

以一组 serving benchmark 为例：

```bash
--num-prompts 40
--max-concurrency 8
--request-rate 10000
```

Benchmark 通过 `asyncio.Semaphore(8)` 限制完整 HTTP 请求生命周期，所以行为近似为：

```text
t0：请求 1~8 几乎同时开始
t1：请求 3 完成，请求 9 获得客户端槽位并开始
t2：请求 1 完成，请求 10 开始
...
直到 40 条全部完成
```

因此：

- 总请求数是 40；
- 任意时刻最多 8 条 HTTP 请求在途；
- 第 9 条在客户端等待 semaphore 的时间不计入它自己的 TTFT；
- 一旦第 9 条开始 POST，它在服务端的排队时间就计入 TTFT。

`request-rate=10000` 让请求在有并发槽位时几乎立即发出。它并不会突破 `max-concurrency=8`。

**注意，在 PD 分离的场景下， serving benchmark 看的是D 节点完成整个请求，不是 P 节点完成 Prefill 就打入下一条请求。**

### 4. `max_running_requests` 管什么

`--max-running-requests` 是服务端容量上限，不是压测流量，也不是固定 batch size。

### 4.1 客户端并发小于服务上限

```text
C = 8
max_running_requests = 128
```

客户端最多只提供 8 条在途请求，服务端不会凭空生成另外 120 条请求。实际活跃数仍不超过 8。

### 4.2 客户端并发大于服务上限

```text
C = 128
max_running_requests = 32
```

最多约 32 条请求能够占用服务端活跃槽位；其他已到达请求留在等待队列。等待队列中的时间属于用户可见延迟，因此计入 TTFT。

### 4.3 有请求槽位不代表一定有 KV 空间

真正的 admission 同时受以下条件约束：

- 请求槽位；
- KV Cache 可用 token 数；
- `max_prefill_tokens`；
- chunk token budget；
- 对 Kimi-K3 这类混合模型，还可能受 Mamba state cache 限制；
- PP microbatch 当前剩余位置。

所以即使 `max_running_requests=128`，服务也可能因为 KV Cache 或 Mamba state 不足，只接纳更少请求，甚至 retract 部分 Decode 请求。

当不显式传入时，SGLang 会结合内存池自动解析有效值。应以启动日志中的：

```text
max_running_requests=...
max_running_requests is capped to ... by the mamba state cache
```

为准，而不是只看启动命令。

对应源码：

- 参数定义：`python/sglang/srt/server_args.py:779`
- Scheduler 读取最终容量：`python/sglang/srt/managers/scheduler.py:1029`
- 请求槽位检查：`python/sglang/srt/managers/scheduler.py:3177`

### 5. 请求在 Scheduler 里如何流转

从请求状态看，Scheduler 会在 `waiting_queue`、`new_batch`、`last_batch`、`running_batch` 和 `cur_batch` 之间推进请求。这个视角可以直接区分“请求已经到达”和“请求正在 GPU 上执行”。

### 5.1 `waiting_queue`

保存尚未完成 Prefill、等待被接纳的请求，以及因 KV 空间不足从 Decode 阶段 retract 回来的请求。它不是“所有 active requests”的总表：已经进入 Decode 的请求位于 `running_batch`，正在分块 Prefill 的请求还可能由 `chunked_req` 单独跟踪。

新请求会按 `schedule_policy` 排序，再由 `PrefillAdder` 根据请求槽位、KV Cache、Prefill token 和 chunk budget 选择一部分组成 Prefill batch。

### 5.2 `new_batch` / Prefill batch

这是当前轮准备执行 `EXTEND` forward 的请求集合。它既可能是新请求的完整 Prefill，也可能只包含长请求的一段 chunk。

普通新请求的主要轨迹是：

```text
waiting_queue
    ↓ admission
new_batch（本轮 Prefill）
    ↓ 本轮执行结束
last_batch（下一轮开始时处理结果）
    ↓ 完成全部 Prefill
running_batch（后续 Decode）
```

### 5.3 `chunked_req`

长请求没有完成全部 Prefill 时，不能提前进入 Decode。当前实现用 `self.chunked_req` 保存这个正在分块推进的**请求对象**，而不是简单的布尔标志。

它处于一个特殊中间状态：

- 已从普通等待队列取出；
- 当前 chunk 执行完后，KV 会被暂存；
- 仍未进入传统 Decode `running_batch`；
- 后续调度继续处理剩余 chunk；
- 只有最后一个 chunk 完成后才生成首 token 并转入 Decode。

### 5.4 `running_batch`

保存已经完成 Prefill、仍需继续生成 token 的请求。每个普通 Decode step 会先过滤已完成请求、检查下一 token 的 KV 空间，再准备 Decode forward。

如果 KV Cache 不足，`retract_decode()` 会撤回部分请求，释放其资源并送回等待队列。此时客户端连接仍可能在等待，但请求不再属于当前 Decode batch。

### 5.5 `cur_batch` / `batch_to_run`

这是当前 engine step 真正交给模型执行的 `ScheduleBatch`：

```text
有可运行 Prefill：cur_batch = Prefill batch
没有 Prefill：    cur_batch = 更新后的 running Decode batch
都没有：          当前 engine step 空闲
```

因此，同一时刻可以同时存在：

```text
客户端 8 条 HTTP 在途
waiting_queue 中 3 条
chunked_req 1 条
running_batch 中 4 条
cur_batch 本轮只执行其中某个 Prefill chunk
```

这些数量都合理，并不矛盾。

### 5.6 “Batch”也有不同抽象层

从 CPU 调度到 GPU 执行，batch 还会经过不同的数据结构：

| 数据结构 | 所在层次 | 主要内容 |
| --- | --- | --- |
| ScheduleBatch | CPU Scheduler | 请求对象、KV 分配、前缀、调度模式 |
| ModelWorkerBatch | Worker 接口 | 模型 forward 所需的批次张量和缓存索引 |
| ForwardBatch | GPU ModelRunner | input_ids、位置、序列长度等底层 tensor |
| GenerationBatchResult | GPU→Scheduler 结果 | token、logits 元信息、同步事件和 Future 索引 |

这进一步说明：HTTP concurrency 是请求级概念，而 kernel 看到的是经过调度、缓存命中和 token 切块后形成的 tensor shape。

### 6. Continuous Batching 不是“固定一批一起跑完”

传统静态 batching 会固定一批请求，等最慢请求结束后才接收下一批。Continuous Batching 则在每个调度循环重新形成执行 batch：

```text
Step 0：A B C D
Step 1：A B   D    （C 完成）
Step 2：A B E D    （E 新加入）
Step 3：  B E D F  （A 完成，F 新加入）
```

SGLang 的正常 Scheduler loop 每轮执行：

```python
接收新请求
→ 更新 waiting_queue
→ get_next_batch_to_run()
→ run_batch()
→ 处理结果和完成请求
```

对应源码：`python/sglang/srt/managers/scheduler.py:1719`。

这里的 batch 是**一次 engine step 的工作集合**，不是 HTTP 层的一组固定请求。请求可以在不同时间加入和离开。

### 6.1 Normal Scheduler

Normal Scheduler 的一个 step 可以抽象为：

```text
Pre Schedule（CPU）
→ Model Forward（GPU）
→ Sample（GPU）
→ Post Schedule（CPU）
→ 下一 step
```

CPU 需要等待 GPU 采样出的 token，完成 EOS/长度检查、流式输出和状态更新后，才能准备下一轮。Decode 单步较短时，Python 和同步开销容易变成 GPU 时间线中的空洞。

### 6.2 Zero Overhead / Overlap Scheduling

Zero Overhead Scheduling 的核心是**把 CPU 调度与相邻 GPU step 重叠**。它隐藏调度开销，但不扩大并发容量，也不改变 Prefill/Decode admission 规则。

SGLang 通过 `FutureMap` 预留 GPU 槽位，让 CPU 在尚未读取真实 token ID 时，先用“未来结果所在位置”构造下一批输入。GPU stream 保证上一批 Sample 先写入真实 token，下一批再解析这个 future。

时间线由串行的：

```text
CPU Schedule N → GPU Compute N → CPU Post N → CPU Schedule N+1 → GPU Compute N+1
```

变成近似：

```text
GPU Compute/Sample N+1
        ∥
CPU Post N + Pre Schedule N+1
```

它优化的是 **Scheduler overhead**：同样的请求、同样的 KV 限制、同样的 token batch，CPU 工作被隐藏在 GPU 计算后面。

当前源码分别使用 `event_loop_normal()` 和 `event_loop_overlap()`。Pipeline Parallelism 路径要求启用 `disable_overlap_schedule`，因此 PP 的性能变化主要来自模型分层、stage 通信、microbatch 和 pipeline bubble，而不是 Zero Overhead Scheduling。

### 7. KV Cache 为什么会决定并发

并发请求的 KV 状态可以分成三层理解：

| 层次 | 作用 | 和并发的关系 |
| --- | --- | --- |
| RadixCache | 决定哪些前缀可以共享 | 命中越多，需要新计算和新分配的 KV 越少 |
| ReqToTokenPool | 记录每个请求每个 token 对应的物理 slot | 行数对应请求状态槽位，受 max_running_requests 影响 |
| TokenToKVPool | 真正保存 K/V tensor | token 容量决定活跃请求能保留多少上下文和输出 |

Paged Attention 和 Radix Cache 不是替代关系：

- Paged Attention 解决逻辑连续 KV 到离散物理页的寻址和碎片问题；
- Radix Cache 决定哪些请求能复用已有前缀 KV。

这也解释了为什么“还能容纳 128 个 request slot”不等于“还能容纳 128 条 128K 请求”。前者是请求元数据容量，后者还需要巨大的 token KV 容量。

Radix Cache 只有在相应 KV 计算完成后才能安全插入或更新；否则另一个并发请求可能命中尚未写完的前缀。Prefix Cache 因而同时影响 admission、Prefill 工作量和并发容量。

### 8. Prefill 是按 token 调度的

Prefill 阶段一次可以处理很多 token；不同请求长度也可能不同。因此 Prefill 的核心预算不是只有“几条请求”，还包括“总共多少 input token”。

关键参数：

| 参数 | 含义 |
| --- | --- |
| chunked_prefill_size | 单个长请求一次最多推进多少 Prefill token |
| max_prefill_tokens | 当前 Prefill batch 合计最多接收多少 input token |
| prefill_max_requests | 当前 Prefill batch 最多包含多少条请求；默认不单独限制 |

以 Kimi-K3 的一组 Prefill 测试为例：

```text
ISL = 16K
chunked_prefill_size = 8K
max_prefill_tokens = 16K
C = 8
```

一条请求通常要经过两个约 8K 的 Prefill chunk。客户端虽然有 8 条请求在途，但一次 Prefill forward 的 token 预算只有约 16K，无法一次完成 8×16K 输入。

从预算上看，一次执行最多容纳约两个 8K chunk；实际组合由 Scheduler、KV 空间、页面对齐和 PP lane 状态决定。

这解释了为什么：

```text
客户端并发 = 8
服务端活跃请求可能 = 8
某次 Prefill forward 的请求数仍可能远小于 8
```

Prefill admission 由 `PrefillAdder` 同时核算请求槽位、KV token、input-token budget 和 chunk budget。对应入口：`python/sglang/srt/managers/scheduler.py:3282`。

### 9. 考虑 Decode 后会发生什么

假设测试改为：

```text
ISL = 16K
OSL = 1K
C = 8
```

### 9.1 Prefill 完成后的 Decode batch

某条请求完成全部 Prefill 并生成首 token 后，会进入 running Decode batch。普通 Decode step 中，每条请求贡献一个 token：

```text
Decode batch size = 当前参与本 step 的活跃 Decode 请求数
Decode token 数   ≈ Decode batch size
```

如果 8 条请求都进入 Decode，那么一次普通 Decode forward 大约处理 8 个新 token，而不是处理 8×1K 个 token。1K 输出需要执行约 1K 轮自回归 step。

### 9.2 Continuous Batching 对长 Decode 的作用

请求输出长度不同，完成时间也不同：

```text
Step 100：A B C D E F G H
Step 101：A B C D E F G H
Step 102：A B C D E F   H   （G 遇到 EOS）
Step 103：A B C D E F I H   （新请求 I 加入）
```

因此 Decode batch size 是动态的。`C=8` 只给它一个外部上限，不保证每一步恰好为 8。

### 9.3 新 Prefill 与已有 Decode 的竞争

单实例同时处理 Prefill 和 Decode 时，两类工作共享 GPU。当前 Scheduler 的主决策顺序是：

```text
尝试形成新的 Prefill batch
→ 如果有 Prefill 可运行，先运行 Prefill
→ 否则更新并运行 running Decode batch
```

对应源码：`python/sglang/srt/managers/scheduler.py:3040`。

这意味着持续到达的长 Prefill 可能推迟 Decode，表现为 TPOT/ITL 上升。Chunked Prefill 把一个很长的阻塞切成较短的执行单元，但“切块”本身不自动保证 Decode 一定能在每两个 chunk 之间执行。

如果启用了 mixed chunked prefill，SGLang 可以把已有 Decode 请求以每条 1 token 的形式混入 Prefill `EXTEND` batch；未启用时，Prefill 和 Decode 通常仍是不同的 forward batch。

因此选择 chunk 大小是在做权衡：

| Chunk | Prefill/TTFT | Decode 干扰 | 调度/通信次数 |
| --- | --- | --- | --- |
| 较大 | 单请求 Prefill 通常更快 | 单次阻塞 Decode 更久 | 更少 |
| 较小 | 单次 chunk 更短 | 更容易控制单次停顿 | 更多，可能降低 Prefill 吞吐 |

### 10. PP microbatch 到底是什么

Pipeline Parallelism 将模型层切成多个 stage。例如 PP4：

```text
Stage 0：模型前 1/4 层
Stage 1：模型第 2/4 层
Stage 2：模型第 3/4 层
Stage 3：模型后 1/4 层
```

一个大 batch 如果只作为一份工作依次穿过四个 stage，会产生大量空闲：

```text
时隙 0：Stage0 跑 A
时隙 1：Stage1 跑 A，Stage0 空闲
时隙 2：Stage2 跑 A，其余大多空闲
时隙 3：Stage3 跑 A
```

PP 会维护多条 microbatch lane，让不同 stage 同时处理不同 microbatch：

```text
时隙0  时隙1  时隙2  时隙3  时隙4  时隙5  时隙6
Stage 0      A      B      C      D
Stage 1             A      B      C      D
Stage 2                    A      B      C      D
Stage 3                           A      B      C      D
```

这里 A/B/C/D 是不同的 microbatch。它们不是四个模型副本，而是同一模型流水线中不同的在途工作集合。

### 10.1 `pp_max_micro_batch_size` 限制什么

它限制的是**每条 PP microbatch lane 中最多维护多少条请求**，不是 microbatch 的数量，也不是 token 数。

SGLang 当前 PP loop 的 lane 数为：

```python
pp_loop_size = pp_size + pp_async_batch_depth
```

对应源码：`python/sglang/srt/managers/scheduler_pp_mixin.py:561`。

每条 lane 有自己的：

```text
running_mbs[mb_id]
last_mbs[mb_id]
mbs[mb_id]
```

各 stage 按相同顺序推进这些 lane。对应 PP 主循环：`python/sglang/srt/managers/scheduler_pp_mixin.py:61`。

### 10.2 Prefill microbatch 和 Decode microbatch

同一条 PP lane 在不同阶段可以承载不同类型的工作：

- Prefill 时：里面的请求各自贡献一段输入 token，工作量受 chunk 和 `max_prefill_tokens` 控制；
- Decode 时：里面每条活跃请求通常贡献一个新 token；
- Chunked Prefill 请求可以跨多个 PP microbatch 周期继续推进。

所以“microbatch size=2”只表示这条 lane 最多有两条请求，不代表 Prefill token 数固定为 2，也不代表只执行两次 forward。

### 10.3 默认值为什么和 `max_running_requests` 有关

没有显式设置时，SGLang 使用：

```python
pp_max_micro_batch_size = max(max_running_requests // pp_size, 1)
```

对应源码：`python/sglang/srt/managers/scheduler.py:1056`。

直观上，它尝试把服务端活跃请求容量分散到多条 PP lane：

```text
max_running_requests = 8, PP4
→ 每条 lane 默认上限约 2
→ 4 条 lane 理论合计约 8 条请求
```

### 10.4 microbatch 不是越大越好，也不是越小越好

较小 microbatch：

- 容易形成更多独立在途 microbatch，填充流水线；
- 单次算子 shape 更小，GPU/MoE 计算效率可能下降；
- stage 间发送和调度次数可能增加。

较大 microbatch：

- 单次 GEMM/MoE 更容易获得较好效率；
- 如果所有请求集中进少量 microbatch，其他 stage 可能等不到独立工作，pipeline bubble 增加；
- 单次 Prefill 可能更重，尾延迟更高。

因此，不能把“microbatch=1”直接等同于“更大的 pipeline bubble”。真正需要观察的是：

```text
同时有多少条 PP lane 在途
× 每条 lane 的请求数/token 数
× 各 stage 的执行时间是否均衡
```

例如显式设置 `--pp-max-micro-batch-size 1` 时，PP4 常规只有约四条 lane，每条最多一条请求。客户端即使 `C=8`，也可能只有约四条请求处于这组 PP running lanes，其余请求继续排队；但这四条小 batch 也可能更容易填满四个 stage。最终结果取决于小 batch 的计算效率损失与 pipeline bubble 收益，需要通过实验确定。

---

### 11. CUDA Graph batch size 不是并发上限

例如：

```bash
--cuda-graph-max-bs-decode 16
```

它表示预捕获的 Decode CUDA Graph 最大 batch shape，作用是减少 Decode kernel launch 开销。

它不限制：

- 客户端最多发多少请求；
- Scheduler 最多维护多少请求；
- waiting queue 长度。

如果某轮 Decode batch 超过已捕获范围，框架可能选择 eager 路径、其他 graph shape，或者依据当前实现做 padding/fallback。这会影响性能，但不是 HTTP 层的拒绝或并发限制。

### 12. 用两个实验解释

### 12.1 `16K → 1, C=8`

这是 Prefill 主导实验：

```text
40 条总请求
最多 8 条 HTTP 在途
每条 16K 输入拆成约两个 8K chunk
每个 Prefill batch 总预算约 16K token
首 token 返回后请求立即结束
```

由于 OSL=1，几乎没有稳定的 Decode running batch。它主要测：

- waiting queue；
- Prefill admission；
- Chunked Prefill；
- TP/EP/PP 通信与计算；
- 首 token 返回。

此时 TTFT 接近完整请求时延，TPOT 没有代表性。

### 12.2 `16K → 1K, C=8`

这是 Prefill + 长 Decode 混合实验：

```text
请求完成 Prefill 后长期留在 running batch
每轮 Decode 每条请求生成约一个 token
完成或 EOS 的请求离开
Benchmark 随即补入新请求
新请求 Prefill 与旧请求 Decode 竞争 GPU
```

它同时测：

- TTFT：新请求入场和 Prefill 成本；
- TPOT/ITL：Decode batch 效率及被 Prefill 打断的程度；
- throughput：持续 batching 能否保持 GPU 饱和；
- KV 容量：长 Decode 请求会长期占用 KV Cache。

这也是为什么同一个 `C=8`，在 OSL=1 和 OSL=1K 下代表的系统压力完全不同。
