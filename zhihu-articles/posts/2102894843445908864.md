大家好，我是曲星宇，武汉大学计算机学院弘毅班大三本科生。我主要关注 Systems for ML，尤其是大模型推理服务中的计算、缓存与资源调度。

最近，我们在 arXiv 更新了 CacheBridge 的完整版论文，想借这篇blog跟大家分享一下。

**CacheBridge 是首个通过跨模型 KV 迁移来加速异构多模型推理服务的系统。**先放几个核心结果：

- 在 τ-bench Agent 在线服务中，请求速率为 1–24 QPS 时，平均 TTFT 降低 30%–98%，任务成功率与 re-prefill 相当
- 32K 历史的模型交接，TTFT 降到 re-prefill 的约 1/6，单机和双机跨节点部署都能达到
- 映射器存储只有 Closed-Form Mapper 的 1/8–1/12
- 覆盖三个模型家族的五组模型对，在对话与推理、RAG 任务上的平均质量保持率分别为 97.94% 和 102.94%

论文：[CacheBridge: Efficient Cross-Model KV Transfer for Multi-Model LLM Serving](https://arxiv.org/abs/2609.00891)

下面完整介绍这项工作：多模型协作为什么需要跨模型 KV 复用，以及我们如何让它在在线服务中真正变快。

## 一、模型交接时的重复计算

多模型系统用不同成本、不同能力的模型协作完成任务。路由器按请求选择模型，级联系统在不同阶段切换模型，Agent 工作流让不同模型分别负责规划、执行和结果处理。

一个典型的例子是零售客服 Agent。小模型先和用户沟通需求、调用工具查询订单。遇到更难的问题时，再把整段对话交给大模型继续处理。这时跨模型的KV-Cache就需要重新计算。

CacheBridge 要回答的关键问题是：**源模型已经完成的上下文计算，能否随任务一起跨模型复用？并且在真实在线的环境下获得效率优势？**

## 二、为什么已有的跨模型 KV 迁移还不够快

KV cache 保存了模型处理历史 token 时各层计算出的 key 和 value。它与模型高度绑定：层数、KV head 数、head 维度和内部表示一旦不同，一个模型的 KV 就无法直接给另一个模型使用。

已有工作提出了跨模型 KV 迁移，用源模型的 KV 重建目标模型的 KV。代表性方法包括线性 Closed-Form Mapper（CFM）、加入 MLP 的 CFM+MLP，以及结合目标端历史重放的 Mixture-of-Translators（MoT）。

我们把这些方法放进真实的 SGLang 服务中，测量完整的交接延迟。实验使用 Qwen3 14B→32B，两个模型各自独占 4 张 H800。

结果是：从 256 到 8K 的所有历史长度上，三种方法都比 re-prefill 慢。在 8K 历史下，CFM、CFM+MLP 和 MoT 的 TTFT 分别约为 re-prefill 的 2.8 倍、3.2 倍和 11 倍。

拆开交接路径，可以看到四类开销：

- 映射计算随历史长度增长，加入 MLP 后在 8K 下增加约 6 倍
- MoT 的映射器很轻，但它在目标端重放历史，重放时间从 512 token 时的约 0.1 s 增长到 8K 时的 1.8 s，又把 prefill 计算带了回来
- 每个目标 rank 实际接收约 24 GiB 数据，是映射真正读取量的 13–36 倍。CFM 在 8K 下约 69% 的 TTFT 花在等待其他 rank 的接收与确认上
- 安装阶段要为整段历史保留中间缓冲，和正常推理争抢显存，也限制了并发迁移数量

![](https://pic4.zhimg.com/v2-b15772dcc56944f74f05aa011681c59f_r.jpg)

还有两个发现直接影响了我们的设计。

第一，映射器读得越多，任务质量并不会越高。CFM 让目标模型的每个 KV head 读取所选源层的全部 KV heads。在 HellaSwag 上，只读 1 个源 head 时准确率为 75.00%，读 2 个时为 79.69%，读全部 8 个时反而降到 78.13%。可是映射器存储从 512 MiB 增加到 4,096 MiB，重建计算也成倍增长。

![](https://pic3.zhimg.com/v2-50bd3c0d999b791e7781892191635a2c_r.jpg)

第二，KV 拟合得准，目标模型不一定用得好。在长文档问答 HotpotQA-E 上，即使读取全部 source heads，CFM 也只保留了 re-prefill 得分的 60.6%。原因在于目标模型通过 attention 读取历史，而这项任务上的 attention 读出误差明显更高。

![](https://pic1.zhimg.com/v2-06e21e8946c275bb5af3d59e6bd1f40a_r.jpg)

因此，CacheBridge 优化的不是某一个算子，而是从映射器到在线调度的整条交接路径。

## 三、CacheBridge 的系统设计

CacheBridge 冻结源模型和目标模型的参数，在两者之间放一个离线拟合、校准好的轻量映射器。在线阶段的流程是：

源模型历史 KV → 在源 GPU 上重建目标模型 KV → 分块传输并直接安装到目标引擎 → 目标模型继续处理请求

整个设计由四部分组成。

**1. 紧凑 head assignment：让映射器变小，也让数据依赖变局部**

对于目标模型的每个 KV head，CacheBridge 在每个选中的源层里只读取一个对应的源 KV head，再通过仿射映射完成重建。

在 Qwen3 14B→32B 上，这让映射器存储从 4,096 MiB 降到 512 MiB，在线计算量也按相同比例下降。

更重要的是，它改变了数据依赖。在张量并行下，head 划分与 rank 一一对齐。重建目标 rank r 所需的全部输入，都已经在源 rank r 的显存里。如果改用全 head 映射，每个源 rank 都要先从其他 GPU 收集四分之三的源 KV。

映射器结构就这样直接决定了 GPU 数据局部性。

![](https://pica.zhimg.com/v2-dbec4f0acdae9196b8285ab21c1bb150_r.jpg)

**2. Attention-readout calibration：让映射器对齐模型实际读取的信息**

目标模型通过 attention 读取历史。所以，让重建 KV 在坐标上接近原生 KV 还不够，还要让 attention 读出的结果接近原生 KV 的读出结果。

CacheBridge 固定 key maps 和 head assignment，只校准 value maps。由于 key 固定，attention 权重不随校准改变，value map 的修正量与读出变化成线性关系。每层每个 KV head 的修正可以通过一个带约束的最小二乘求解。

校准按目标模型的层顺序进行，前面层的修正会影响后面层的校准。最终修正直接折叠进 value map 的系数，在线阶段仍然使用同一个紧凑映射器，没有增加任何计算。

在五组模型对、十项任务构成的 50 个设置中，校准改善了其中 45 个，平均质量保持率从 72.26% 提升到 99.94%。

![](https://picx.zhimg.com/v2-a2fffb3c94bd93547d906b69f7412797_r.jpg)

**3. 源端重建与流水线交付：只搬运必要的数据**

CacheBridge 把重建放在源 GPU 上。源模型的历史 KV 本来就驻留在那里，可以直接读取。跨模型传输的只剩目标模型本来就要保存的 KV，目标端的算力继续服务已有请求。

配合 head assignment，源 rank r 恰好产出目标 rank r 需要的 KV。各 rank 对并行传输，就绪和确认信号只在本对 rank 内传递，任何数据块都不需要等待其他 rank。在 8K 历史下，每个目标 rank 只接收约 0.5 GiB，比原有路径少约 48 倍。

历史 KV 被切成 2,048 token 的块。每个块直接写入目标引擎已分配好的分页 KV 存储，不再保留整段历史的中间副本。源端通过双缓冲，在目标端读取当前块的同时重建下一个块，让重建、传输和安装重叠执行。临时显存只与块大小和已准入的迁移数量有关。

**4. 在线服务策略：根据负载和资源选择路径**

历史较短时，re-prefill 本身就很快。历史变长后，迁移的优势才显现。在 Qwen3 14B→32B 上，两者的交叉点约为 2K token。CacheBridge 根据离线测得的交叉点为每个请求选择更快的路径。

每个迁移请求使用独立的缓冲区集合，多个迁移可以并发推进。系统按剩余显存计算可并发的迁移数量；没有空闲缓冲区时，请求回退到 re-prefill。缓冲池会随服务需求增长，在显存紧张或空闲时回收。

系统基于 SGLang 实现，调度器只修改了约 50 行，原生 attention 和解码保持不变。在跨节点部署中，源端和目标端各占一台 8 卡 H800 服务器，对应的 GPU rank 通过 NCCL 点对点通信和 GPUDirect RDMA 直接写入目标 GPU 的 KV 页，KV 数据不经过主机内存中转。

![](https://pic1.zhimg.com/v2-d4209d76e7ee5fc74a6e69bd5364b1a4_r.jpg)

## 四、实验结果

效率实验使用 Qwen3 14B→32B，质量实验覆盖 Qwen3、Llama 3.1 和 Ministral 3 三个家族的五组模型对。质量保持率指相对 re-prefill 保留的任务得分比例，超过 100% 表示得分高于 re-prefill。

| 评测内容 | 主要结果 |
| --- | --- |
| τ-bench Agent 服务 | 1–24 QPS 下平均 TTFT 降低 30%–98%，P99 降低 29%–97%；任务成功率 26.1%，re-prefill 为 26.7% |
| 吞吐与有效吞吐 | 吞吐 6.18 vs 3.18 req/s；5 QPS 下满足延迟目标的有效吞吐从 0.025 提升到 4.369 req/s |
| 长上下文与并发交接 | 并发 1–16、4K–32K 历史下平均 TTFT 降低 35%–84%，32K 下约快 6 倍 |
| 双机跨节点（TP8） | 4K–32K 历史在所有并发度下均优于 re-prefill；32K、并发 16 时 TTFT 比约为 0.167 |
| 映射器存储 | 320–1,601 MiB，约为 CFM 的 1/8–1/12、CFM+MLP 的 1/68–1/105 |
| 任务质量 | 在 50 个单轮设置中，38 个持平或超过最强迁移基线；平均保持率为 97.94%（对话与推理）和 102.94%（RAG） |

在线服务的收益不只来自单次交接变快。一次长历史的 re-prefill 会占用目标模型的算力，延后其他请求。交接变快后，请求更早进入后续推理，排队也随之缓解。这正是平均 TTFT 和尾延迟一起大幅下降、有效吞吐成倍提升的原因。

![](https://pic2.zhimg.com/v2-88b2cccb773af230fffcc8ba44d53fb9_r.jpg)

![](https://pic1.zhimg.com/v2-abb988a7c4196d6bd0d4e98ffc0a9d82_r.jpg)

消融实验中，每项只改动一个组件：

- 紧凑映射器：换成 CFM 映射器、其他系统优化保持不变时，TTFT 最多增加 65%
- 直接安装：在 32K 历史下，目标端新增的峰值显存降低 99.6%
- 流水线重叠：平均 TTFT 降低 12%–35%
- 路径调度：在混合长度负载上，平均 TTFT 降低 20%–63%
- 请求并发：平均 TTFT 降低 24%–49%
- 动态缓冲分配：平均 TTFT 降低 21%，缓冲池平均驻留显存降低 22%

## 五、新的 workload，新的计算模式

在我看来，CacheBridge 的意义不只是让一次交接变快。它把多模型协作中的模型交接，确立为推理服务需要专门优化的一类 workload。

在单模型服务里，KV cache 是模型自己的历史状态：算一次，存起来，后面反复读取。多模型协作带来了一种不同的计算模式。任务每切换一次模型，历史状态都要从一个模型的表示空间转换到另一个模型的表示空间。这次转换发生在首 token 的关键路径上，计算量随历史长度增长，还要和正常推理共用同一批 GPU 的算力、显存和互联带宽。

围绕这种新的计算模式，CacheBridge 做了三件事。

第一，刻画这类 workload 的真实服务开销。我们首次在完整的在线服务路径上测量跨模型 KV 迁移，把交接延迟拆成映射计算、数据搬运、跨 rank 等待、历史重放和缓存安装。结果表明，能否加速取决于整条路径的成本，而不只是映射算法本身。跨模型 KV 复用由此从一个表示映射问题，变成了一个系统问题。

第二，把跨模型状态转换设计成适合系统执行的计算。映射器读取哪些 head，决定了重建要访问哪些 GPU。用 attention 读出来校准映射器，修正量直接折叠进原有系数，在线阶段不增加计算。这样，跨模型 KV 重建就成为一种 head 局部、按块切分、放在源端执行的计算。它能与张量并行对齐，能与传输和安装流水线重叠，临时显存也有明确上界。

第三，让模型交接成为服务系统可以调度的对象。re-prefill 和 KV 迁移是同一次交接的两条执行路径，在不同的历史长度和负载下各有优势。CacheBridge 按历史长度选择路径，按可用显存准入迁移，按服务需求伸缩缓冲区，把交接和正常推理放在同一个资源视角下统一管理。

这三件事合起来，构成了一套处理多模型协作 workload 的完整方法：**先测量真实开销，再设计计算形态，最后做在线调度。**

**这类 workload 还打开了更大的设计空间。当模型选择同时决定对话状态能否复用时，路由不只是挑一个能力合适的模型，也在决定哪些计算可以被继承。缓存保留也不只服务当前模型，还要服务将来可能接手的模型。模型路由、缓存保留和交接调度因此可以放在完整的多轮工作流里联合优化，在质量、延迟和显存之间取得更好的平衡。**

这也是我想持续投入 Systems for ML 的原因。**新的模型使用方式会不断带来新的 workload 和计算模式。我希望从模型运行时的数据和状态出发，找出哪些计算可以复用、哪些数据移动可以省掉，再把这些机会做成真正能跑起来的服务系统。CacheBridge 是我们在多模型协作方向上迈出的第一步。也是我作为junior researcher迈出的关键一步。**
