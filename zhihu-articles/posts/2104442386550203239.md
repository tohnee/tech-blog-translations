如果你写过 Tensor Core 或 NPU 的 kernel，一定遇到过这类 bug：算术完全正确，结果却错了——因为你把 fragment 放错了 lane，或者 VTCM 里的 tile 少交错了一层。这种"指令看得见的布局"不在指令的算术语义里，却是操作数合法性的前提。

今天解读的论文 **Retargetable Compilation for Tensor Kernels via a Unified Layout Abstraction**（arXiv:2611.13741，北京大学 + Infinigence-AI）给出了一个编译器侧的答案：**Arknife**。它把布局从"程序里要写死的东西"变成"编译器要解的未知数"——用一套与 ISA 无关的约束式布局代数，让同一个张量程序在 x86 CPU、Qualcomm Hexagon NPU、NVIDIA A100 上都能生成合法且少搬数据的 kernel。

## 一、结论先行

- **x86 CPU**（双路 Xeon Gold 6348，AVX-512 VNNI）：9 个 workload 几何平均比 oneDNN 3.7.1 快 **2.17×**（矩阵类 1.91×、标量类 2.55×）；比重定向编译器 MISAAL 和 Hydride 快 **5.08× / 5.13×**。
- **Hexagon NPU**（Snapdragon SM8650，QNN 2.28）：9 个 workload 比 MISAAL / Hydride 快 **4.53× / 4.58×**；11 个算子几何平均比厂商库 QNN 快 **3.78×**（Transpose 5.96×，Int8 GEMM 打平 1.08×）。
- **A100**：FP16 多头注意力几何平均比未融合的 PyTorch eager 快 **5.04×**，同基线下的 Triton 4.56×、FlashAttention 4.83×、TileLang 3.53×；TF32 GEMM 达到 cuBLAS 的 **97%**（比 Triton 快 2.20×、比 TileLang 快 1.16×），而 kernel 手写代码只有 **68 行**（对比 117–650 行）。
- 换后端不动代数和求解器，只需要写"硬件描述（几十行）+ 每条指令的布局需求（不到 10 行）"。

## 二、问题：指令的"布局契约"

### 2.1 同一块 tile，三种摆法

论文开篇给了一个非常具体的例子：同样一个逻辑上的 GEMM A tile，三个后端要求的物理摆放完全不同。

- **x86 VNNI**：把 K 方向相邻的 4 个字节打进一个 32 位 lane，一条 vpdpbusd 累加 4 个乘积。
- **Hexagon HMX**：tile 在 VTCM 里按"行对交错"摆放，指令要求的顺序（从内到外）是"每对里的两行 → 一个块的 32 列 → 16 个行对 → 下一个 reduction 轴块"。这个顺序混了两个轴的因子，**行主序/列主序这种整轴置换根本表达不了**。
- **A100 MMA**：ldmatrix 把元素摊到 lane 与寄存器上，warp 内每个线程持有 fragment 的特定位置。

![](https://picx.zhimg.com/v2-cc142181f791ca590af1b106d843ce75_1440w.jpg)

图 1：(a) x86 CPU 的 VNNI 打包；(b) Hexagon NPU 的 HMX lane 布局（VTCM 中行成对交错）；(c) A100 GPU 的 MMA fragment（ldmatrix 把元素分配到 lane 与寄存器）；(d) 用完整因子形式写出 HMX 对两个连续 32×32 FP16 块的需求：行按 m = 32 = (m0:2, m1:16) 分解、列按 k = K = (k0:32, k1:K/32) 分解，最终顺序是 (k0, k1, m0, m1)。

关键点：**布局错了不是变慢，是结果错**。HMX 的 tile buffer 填充就按这个顺序来，任何其他排列都是非法操作数。

### 2.2 转换指令本身很贵

论文把"以改变布局为目的的指令"叫 repair（修复指令）。Hexagon 的 ISA 为这件事专门提供了十几种原语：寄存器转置（vshuff、vdeal）、位宽转换（vpack、vunpack）、寄存器重塑（vcombine、vsplat、valign）。

这里有一个非常有说服力的数字：在 VTCM 与寄存器之间做一次"行对交错 → 行主序"的置换，**没有价格相当的专用原语**，退化成字节粒度的标量搬移时是 **70–504 个周期/128 字节**，而寄存器内的通用置换只要 **3.5 个周期**（hexagon-sim，v66，HVX-128B，单线程；issue-bound 依赖链）。

也就是说，"布局没选好"的代价可能差两个数量级——这正是"全局选布局"而不是"局部打补丁"的经济学基础。

## 三、现有三条路线，各缺一块

| 路线 | 代表 | 谁声明布局 | 冲突修补的范围 | 代数形态 |
| --- | --- | --- | --- | --- |
| 布局引导的张量 DSL / 调度 | TensorIR、TIRx | 程序员在 schedule / 类型里写 | – | 布局是输入 |
| 综合式 kernel 生成 | Hydride、MISAAL | 编译器决定 | 局部（每个 rewrite 各自打补丁） | 布局是输入 |
| 构造式布局代数 | CuTe、Linear Layouts | 编译器/库 | 依赖 GPU 专有 ISA 原语 | 给定布局 → 推导转换 |
| Arknife | 本文 | 编译器（从指令描述读需求） | 全局（整个计算图） | 给定需求 → 解出布局 |

三类方案的具体问题：

- **DSL 路线**把布局写进程序。单目标上只是啰嗦，跨后端就成了重活：每个目标的层次结构和指令约束都不同，得重新推导一遍布局；而且布局选错会以**错误结果**的形式暴露，不是性能下降。
- **综合式路线**把布局决策收进编译器，但冲突修补是**局部**的：Hydride 一次只看表达式的一个小窗口，即使隔壁窗口换个布局就能免掉这次转换，它也看不见。论文量了这个代价：在 x86 的两个融合图上，Hydride 执行的布局处理指令是 Arknife 的 **17.1×** 和 **51.4×**；在 Hexagon 量化 Add 上是 **85.8×**。
- **构造式代数**（CuTe / Linear Layouts）很强，但它假设"布局已知"，只回答"给定两个布局，转换怎么写"。它成立的前提是布局改变的手段少、固定在 ISA 里、价格差不多——GPU block 内一次 shared memory 往返就能以有界代价把任意布局变成任意布局。可重定向编译器没有这个常数：VTCM→寄存器这条边界上就没有便宜原语。

![](https://pic2.zhimg.com/v2-442b96ef05f72a79563147ee98c350e9_1440w.jpg)

图 2：现有系统的布局处理方式与 Arknife 的对比。(a) 布局引导的张量 DSL：程序员显式写出 `L=Layout(vtcm, order)` 这类布局；(b) 综合式 kernel 生成：转换在局部 rewrite 窗口内解决；(c) 构造式布局代数：已知布局两两复合得到转换；(d) Arknife：程序里不写布局，需求由指令声明、冲突用目标提供的 repair 显式化、最后在整图范围求解并消掉冗余转换。虚线框标出"冲突修补的作用域"——只有 (d) 覆盖整图。

## 四、核心抽象：把布局当未知数

### 4.1 目标模型与硬件坐标空间

Arknife 把目标抽象成一个四元组 T = (L, M, I, R)：并行层次集合 L、存储空间集合 M、指令模板集合 I、以及其中作为 repair 的子集 R。

每个并行层次 l（有 n_l 个单元）贡献一条并行坐标轴，每个存储空间 m 贡献一个"每单元局部地址空间"，它们的笛卡尔积就是**硬件坐标空间 H**。一个硬件位置就是这个空间里的一个点：它同时说明"在哪个 lane/warp/核上"和"在哪个存储空间的哪个偏移"。

### 4.2 布局 = 从逻辑轴因子到 H 的单射

- **张量布局** F_T(t)：把张量的每个逻辑元素映射到 H 中的一个位置，要求单射（不同元素不能撞到同一位置）。
- **操作数需求** F_B(b) = (π_b, g_b)：π_b 把硬件位置投影到"这条指令关心的那几个坐标分量"，g_b 规定这些分量应该取什么值。**未被约束的分量说明这条指令不关心**——这是整个抽象能做"部分约束"的关键。
- **合法性**：一个摆放 F 满足需求，当且仅当 π_b∘F = g_b。

举个论文里的例子：两路交错（偶数元素在向量 0、奇数在向量 1）。把硬件位置写成 (q, p, v)（向量对、对内的哪个向量、元素位置），需求就是 π_b(q,p,v) = (p, v)、g_b(k) = (k mod 2, ⌊k/2⌋)：元素 k 必须落在"第 k mod 2 个向量的第 ⌊k/2⌋ 个位置"，而分到哪一对 q 不关心。

### 4.3 因子化：让求解不随张量尺寸爆炸

按坐标点做搜索是指数级的。Arknife 的做法是把每个逻辑轴拆成若干因子的有序乘积（例如 m = m0 × m1，K = k0 × k1），布局变成"因子到硬件因子的单射映射"，需求变成"因子到硬件因子的**部分**映射"。这样既能表达 HMX 那种"跨轴交错"的顺序（整轴置换做不到），又让约束可按因子分离，规模只与图的约束数量有关。

### 4.4 关键定理：把"存在布局"变成"约束可满足"

对一个张量的所有使用（生产者 + 消费者），每个使用贡献一份需求。把它们映射回张量因子再取并集，得到**最小约束 C_t**。论文证明（Prop. 4.7）：一个布局满足该张量的全部使用，当且仅当 C_t ⊆ Λ_T(t)。

这条性质带来三个工程上极其重要的后果：

- **顺序无关**：C_t 是并集，与遍历顺序无关，所以可以做增量检查；
- **单调**（Prop. 4.8）：使用集合变大，约束只会变强；反过来说，任何满足大集合的布局也满足子集——所以指令选择时可以**可靠地剪枝**，不必回到最后才发现不可行；
- **局部性**：repair 的可行性只在两个张量（repair 的输入与输出）上检查（Def. 4.9），是一个"两轴模型"的小问题，而不是整图问题。

![](https://pic1.zhimg.com/v2-508b64c2e6203821d8187b2a6a903540_1440w.jpg)

图 5：(a) 冲突。张量 t 的布局 Λ_T(t) 把因子 a2 放到寄存器轴上、a0/a1 放到 lane 轴上，而下游指令 b 要求 a0 在寄存器轴、a1/a2 在 lane 轴——操作数视图 V = Λ_T ∘ φ 不包含需求 Λ_B，直接绑定非法。(b) 修复。插入一条 vshuff（Q6_Ww_vmpy_VhVh，i16×i16→i32）后，中间张量 t' 与结果张量 t 各自只需要满足一侧的需求，两个边界同时变得合法，而张量的逻辑值语义不变。

## 五、编译流程：五步

![](https://picx.zhimg.com/v2-f0ecb03a0778b338e9e784ebaacd2fa7_1440w.jpg)

图 3：编译流程。输入是张量程序（只写逻辑计算，不写布局）+ 目标描述（并行层次、存储空间、指令模板及其操作数布局需求）。依次是：指令绑定（§5.1）→ 布局 repair 插入与可行性检查（§5.2，repair 家族包括 data move / transpose / reduce / broadcast）→ 基于 e-graph 的冗余 repair 消除（§5.3）→ 全局布局求解（§5.4）→ 保布局的代码生成（§5.5）。三个后端（x86 CPU / Hexagon NPU / NVIDIA GPU）共用同一条流水线。

- **指令绑定**：对每个算子枚举算术等价的候选指令（Semantics(ι) ⊨ o），按拓扑序访问，用"寄存器足迹小 + 与已绑定邻居兼容"的启发式排序，逐个检查候选与累积约束是否可满足，不可行就回溯。因为单调性，剪枝是 sound 的。
- **repair 插入**：边界上需求冲突时，插入"最低代价且可行"的目标 repair 实例（r★ = argmin Cost(r) s.t. Feasible(...)）。这些 repair 是**临时的**——下一步可能把它们搬走、合并或消掉。Hexagon 里三个 permutation repair 就是这样被插进来的。
- **e-graph 优化**：用饱和 + 代价提取消掉冗余转换。四条通用规则：Commute（把置换穿过逐元素算子）、Fusion（两个置换复合成一个）、Identity（恒等置换删除）、Hoist（把置换提升过 broadcast）。后端还可以加自己的规则。所有重写都必须保持张量值语义、边界轴映射和内部可行性。
- **全局布局求解**：把兼容性问题编码成**二元整数规划**。变量 x(a,p) 表示"指令局部轴 a 映射到程序根因子 p"；指令内部的约束保证 φ 是合法嵌入，跨使用的约束编码 C_t ⊆ Λ_T(t)；硬约束保合法，软偏好（连续映射、后缀对齐、跨使用复用同一映射）在合法解里挑最好的。求解器是 SCIP（PySCIPOpt 6.0.0）。
- **保布局 lowering 与 codegen**：空间切分（再解一个 ILP 定 tile 尺寸，受每单元容量硬约束）、时间循环补全（把还没被任何循环覆盖的轴包进 TemporalOp，不改 φ）、内存规划（按生命周期复用，把临时量放进声明区域里第一个够大的空块）、代码发射（遍历精化后的图，用每个指令的 codegen 回调 + 解出的布局属性生成代码）。repair 节点的发射与计算指令完全一致。

![](https://pic4.zhimg.com/v2-e00a26ed73556e6bbcbe88105842582d_1440w.jpg)

图 6：Hexagon 量化加法的案例。(a) 输入程序只声明"寄存器张量 + 自由逻辑轴 n"，不指定任何指令级轴映射；(b) 编译结果：Scale/Add/Requantize 分别绑定 vmpy / vadd / vround，初始绑定插入三个 permutation repair 来对齐 vmpy 输出与 vround 的输入组织；e-graph 用 Commute 把两个匹配的置换推过逐元素加法，再用 Fusion + Identity 与前一个 vround 的逆置换抵消——**三个 repair 全被消掉**，vadd 直接沿用 vmpy 与 vround 共享的交错表示；最后求解器把 n 分解为 n = no × nv × ni，把 vmpy/vround 的"向量角色 + 两路交错角色"分别落到 nv 与 ni 上，而 vadd 不声明交错角色，ni 就落在它的 tile 之外。

这个案例很能说明"全局"和"局部"的差别：局部修补会留下三条置换指令（每条都是真金白银的向量指令），全局求解 + e-graph 之后一条都不剩。

## 六、重定向到底有多贵

- 硬件描述（并行层次、存储空间、容量、通信通道）：**几十行**。
- 指令描述（操作数语义、布局属性、资源影响、代码发射回调）：每条 **不到 10 行**。
- 所有 kernel 共享这些描述，与具体 kernel 的调度决策无关。

换句话说，加一个新后端的工作量从"重写一套布局推理"降到"填表"。这是这篇论文在方法论上最想主张的一点：**把"需求"而不是"布局"作为接口，代数才能跨 ISA 复用。**

### 7.3 布局处理指令数：差距在哪

| 设置 | Arknife 布局指令 | Hydride 布局指令 | 减少倍数 | Hydride 标量化比例 |
| --- | --- | --- | --- | --- |
| x86 量化 MM+B+ReLU | 546K（占动态指令 18.3%） | 9.33M（37.0%） | 17.1× | 91.3% |
| x86 + 第二个 MM | 1.13M（16.5%） | 58.1M（43.8%） | 51.4× | 74.2% |
| Hexagon 量化 Add | 99.3K（27.4%） | 8.52M（90.7%） | 85.8× | 73.8% |
| Hexagon 量化 Mul | 100K（26.9%） | 7.22M（93.6%） | 71.9× | 80.7% |

读法：Hydride 的布局处理里 74–91% 是**标量化**的（vpinsrw 逐元素插入、字节粒度搬移、标量移位）；Arknife 的布局指令**全部是整向量操作**（标量化比例 0%）。Hexagon 上 Hydride 的布局指令甚至占到全部动态指令的 90%+——基本上就是在搬数据，不在算数。

e-graph 的消融也很诚实：在 x86 上关掉它**没有变化**（GCC -O2 已经把这些寄存器拷贝和 pack/unpack 往返消掉了）；在 Hexagon 上它把布局处理再降 2.18×（Add）和 1.45×（Mul），因为要吸收"加宽乘法"（vmpy、vmpye/vmpyoacc）天然产生的交错，并把单边置换提升过 lane-wise 算子与逆置换抵消。

### 7.4 编译开销

| 后端 | workload | axis-map 总时间 | 其中 ILP 求解 |
| --- | --- | --- | --- |
| x86 | MatMul（256³） | 177.3 ms | 19.6 ms |
| x86 | MatMul+B+ReLU | 340.6 ms | 34.9 ms |
| Hexagon | HMX GEMM（1024³） | 228.5 ms | 44.7 ms |
| Hexagon | GQA Decode（4096，d=4096） | 1862.1 ms | 296.1 ms |
| Hexagon | Transpose（1024×1024） | 56.1 ms | 6.5 ms |

- SCIP 只占 axis-map 时间的 10–20%，大头是约束构造与结果应用。
- 规模敏感性：x86 MatMul 从 256³ 扫到 1024³，ILP 中位时间稳定在 **15.9–19.1 ms**；GQA Decode 序列从 1024 到 8192，稳定在 **273.2–291.7 ms**。原因是二元轴表示下"维度翻倍只多一个根片段"，求解时间对**图的约束数**比对张量尺寸更敏感。

## 八、批判性评估

- **基线选择决定了数字的观感**。对 oneDNN 的 2.17× 有很大一部分来自小 shape 上 oneDNN 的每调用开销，以及融合边界上的收益；论文自己也说最大 shape 收敛到持平。对 cuBLAS 只有 97%（这是合理且诚实的结果，说明在成熟后端上 Arknife 是"够用"而不是"更强"）。
- **Hexagon 端到端并不是全面胜出**。Qwen3-0.6B 单步 decode 在序列 1024 时只有 **0.87×**（输给 QNN），到 8192 才 2.77×。原因是短上下文时执行以投影为主（带宽受限、对布局不敏感），而 Arknife 没做自动权重预处理、权重常驻和 megakernel 融合——论文把这些明确列为 future work。这是一个"per-operator 赢、端到端未必赢"的典型案例。
- **规模偏小**。9 个 workload、11 个 QNN 算子、8 个 MHA 配置；除 0.6B decode 单步外没有 LLM 端到端。整网（几十层、上百个算子）的编译时间和求解质量没有被验证——目前最大测到的 axis-map 是 1.86s，如果按图规模线性增长，整网编译会到分钟级。
- **e-graph 的收益高度依赖后端**。x86 上完全无效（被 GCC 顺手做掉了），说明这套优化不是普适的"必赚项"，而是针对"ISA 会天然产生交错"的目标（如 Hexagon 的加宽乘法）。
- **没有开源**。论文没有 artifact 链接，PySCIPOpt + SCIP 是外部依赖，但三个后端的指令描述、codegen 回调、pass 实现都得自己重写。复现门槛不低。
- **模型边界**：只处理规则的矩形域（ragged 域和数据相关的访问关系被明确排除在外），只覆盖"指令可见布局"，像 shared memory 的 XOR swizzle 这类不改变指令边界视图的优化留给后端在求解之后做——这是合理的分工，但也意味着它不解决 bank conflict 这类问题。
- **ILP 的软偏好是启发式的**。连续映射、后缀对齐、跨使用复用这三项偏好如何加权、权重对性能多敏感，论文没有给消融。实际部署时这可能是需要调的旋钮。

## 九、对工程实践的启示

- **把布局需求写成"接口"，而不是把布局写进程序**。这是全文最可迁移的思想：只要每个指令能声明"我关心哪几个坐标分量、它们该取什么值"，剩下的就可以交给求解器。哪怕你不写编译器，团队内部的 kernel 模板库也可以这样组织——先定义每个 intrinsic 的操作数契约，再让代码生成去满足它。
- **先看消费指令要什么视图，再谈融合**。论文里 25.35× 的那个 MM+B+R+MM 案例，收益全部来自"让第二个 MatMul 直接吃第一个 MatMul 累加器的布局"。融合的收益上限往往不在计算，而在边界上的重排。
- **标量化是布局失败的信号**。如果你在自己的生成代码里看到 vpinsrw 一条条插、或者字节粒度的 load/store，那基本就是布局没解对。论文里 Hydride 91% 的布局指令是标量化的，这个比例值得当成一个诊断指标。
- **重定向的成本可以量化**：几十行硬件描述 + 每条指令不到 10 行，这是"支持一个新 NPU"的现实预算。评估一个编译器框架是否真的可重定向，看的就是这个数字。
- **对编译器作者**：约束的单调性（加一个使用只会让约束更强）是一个非常强的工程性质——它让"边绑定边剪枝"变得 sound，而不用等全局求解失败再回溯。这个技巧可以独立于布局问题复用。

一句话总结：Arknife 把"布局"从程序员的手艺变成了编译器的约束求解问题——它没有发明新的指令或新的硬件，但让同一份张量程序在三种完全不同的 ISA 上都能生成"合法且不浪费在搬数据上"的 kernel。在 NPU 百花齐放的当下，这种"把 ISA 差异关进描述文件"的思路，比某个具体 kernel 快几倍更值得关注。
