## 写在前面

我的自博弈农场在推理侧有一张 TensorRT 合成图：一串小核串成一条链，每批处理 256 行对局状态，引擎纯批时 2.03 ms。这堵墙的成因很朴素——每个核都太小，核与核之间的发射、同步、显存往返把时间吃光，张量核心再快也轮不到它发力。等价变换的路子试过、判过死，剩下的选项只有融合和手写。

9 月 30 日深夜，我决定把这张图里最重的两段（状态机更新、读出打分）重写成手写 CUDA 核。工具选了 DeepJIT——DeepSeek 9 月初刚开源的 header-only C++20 JIT 运行时（GitHub 搜 deepseek-ai/DeepJIT，MIT，版权头就一行 "Copyright (c) 2026 DeepSeek"），把"内核源码字符串 → nvcc → cubin → 驱动加载发射"整条链包成两个函数调用。我拿到的是它 9 月底刚迁到 PyTorch stable ABI 的版本——标准的尝鲜场景：新工具，真活，一个通宵。从深夜起步到双引擎组全部换装、生产路径零 TRT 核执行：引擎纯批时 2.03 → 1.49 ms，腿级端到端吞吐 92.4k → 约 114–116k 行/s（验收判决 1.23×，按较慢一跑计），池引擎组再 +14%。

这篇手记记录整个过程：DeepJIT 怎么用、坑踩在哪里、每个数字多少，以及我对"运行时编译内核"这件事的最终感受。正文里还穿插了今天补做的两组验证实验（DeepJIT 三段式与发射开销、合并访存缩小复现）——后者把当晚最大的一步优化（合并访存，1.93→0.496 ms）在玩具尺度复现了，结论成立。

## 一、DeepJIT 是个什么东西

DeepSeek 在仓库 README 里给自己的定位（deepseek-ai/DeepJIT）：面向 NVIDIA CUDA GPU 和华为昇腾 NPU 的轻量 header-only C++20 JIT 运行时，给 C++/Python 扩展作者提供统一接口：运行时编译内核源码、缓存产物、加载到设备、按后端选项发射。

对我真正有用的，是它的三层缓存：

1. **进程内内存缓存**：同一个源码字符串第二次 `compile()`，直接返回已加载的内核指针（今天实测 11 µs）；
2. **磁盘缓存**：编译产物以原子方式发布到缓存目录（`.committed` 标记 + kernel.cu + kernel.cubin + meta.json 四件），跨进程、跨用户、甚至跨节点共享——重启进程后 0.28 ms 拿回此前编好的核（实测为同日第二个进程）；
3. **nvcc 现编**：缓存全未命中才真正调用 nvcc。

缓存键不糊弄：源码内容、被追踪的头文件树、nvcc 版本输出、全部编译选项的哈希一起进摘要。改了任何一环，自动重编。

还有一个结构性优点：它走的是完整 nvcc，不是 NVRTC。C++20 语义、模板、标准库头文件都能用，`--gpu-architecture` 按设备自动探测。对想写"正经"设备代码而不是拼接 PTX 片段的人，这条路踏实得多。

今天实测的三段式耗时（RTX 3060 Laptop，saxpy 核，N=2²⁰）：

| 获取方式 | saxpy 核 | 两个 96×96 矩阵向量积核 |
| --- | --- | --- |
| 冷编译（nvcc 现编+落盘+加载） | 648.50 ms | 428.76 / 434.32 ms |
| 磁盘缓存热启（第二个进程） | 0.28 ms | 0.14 / 0.09 ms |
| 进程内内存缓存（同进程再取） | 0.005–0.011 ms（两轮） | — |

![](https://pic2.zhimg.com/v2-199d2e4ae87e5f9b9660d8a2a8dbabbf_r.jpg)

冷编译的 648.5 ms 里，用 DeepJIT 缓存条目 meta.json 里记录的原命令单独跑 nvcc 只要 410 ms（五次实测 0.40–0.41 s，且产物 cubin 3368 字节与 DeepJIT 的产物同大小），剩下的约 240 ms 是 JIT 的包装开销（临时目录、落盘校验、模块加载）。也就是说 JIT 不是魔法，它就是帮你拼命令、管缓存、做校验——但这份"帮你"值钱的地方在迭代期，后面细说。

发射路径的开销也量了一下：同一颗 saxpy cubin，DeepJIT 的 `launch()` 走 20000 次连发（1×32 线程小网格、只测入队不含同步），两轮实测 1909–1995 ns/次；绕过它直接用驱动 API `cuLaunchKernel` 发同一份 cubin，1757–1758 ns/次。差距约 150–240 ns（约 9–13%）。这个数字后来影响了我们的生产决策，见第四节。

最后一个观察，关于 DeepSeek 为什么造它：DeepJIT 同时带 CUDA 和昇腾两个后端，同一套 compile/launch 接口换个模板参数就切芯片；同一波开源的还有 TopK 算子内核 DeepSelect、对话模板适配层 deepseek-recipe。连起来看方向很清楚——做权重之外的推理软件栈，而且顺手给昇腾生态铺路。对使用者是好消息：这类大厂自用工具外溢出来的项目，接口贴着真实负载长；但毛边也真实——第三节和第四节那些坑就是证明。

## 二、环境配方与三个坑

实录环境（2026-09-30 深夜，与今天实测同一台机器）：

| 项 | 值 |
| --- | --- |
| 硬件 | ASUS TUF A15（FA506QM），RTX 3060 Laptop 6GB（sm_86，30 SM，L2 3MB） |
| 系统 | Ubuntu 26.04（glibc 2.43） |
| 编译器 | nvcc 13.1（apt 源 cuda-nvcc-13-1 13.1.115 + cuda-cudart-dev-13-1 13.1.80） |
| PyTorch | 2.14.0+cu130（venv 内，仅头文件与链接用） |
| DeepJIT | commit 3732a3b（2026-09-30） |
| 驱动 | 580 系起步；今天实测时为 595.91.07 |

环境配方有三个坑，全部实物核验过（今天逐项复查：dpkg 包在位、补丁文件在位）：

1. **nvcc 本体不在 pip 包里**。apt 装 NVIDIA 源的 `cuda-nvcc-13-1` + `cuda-cudart-dev-13-1` 才有 nvcc 驱动本体；pip 的 nvidia-cuda-nvcc 包只含 ptxas/nvvm，别踩。
2. **glibc 2.43 与 CUDA 13.1 的 noexcept 冲突**。Ubuntu 26.04 的 mathcalls.h 给 rsqrt 声明了 `noexcept(true)`，与 CUDA 头里的声明冲突，EDG 前端直接报 exception specification incompatible——而且 `--compiler-options`、`-D` 都进不了前端，绕不过去。修法是给 CUDA 头打两行补丁（`crt/math_functions.h` 的 rsqrt/rsqrtf 声明加 noexcept）。今天复查时补丁和备份（`.bak_glibc_compat`）都还在原位，注释就写着 `// glibc-compat`。
3. **纯 C++ 也要 torch 头**。用 `-DDJ_DISABLE_GIL=1` 可以免掉 pybind，但 backend 头文件无条件包含 torch 的 stable ABI 工具头，所以宿主程序仍需 torch 的 include 路径和 libtorch 链接。这是上游可改进点。

宿主侧编译命令的要点（g++）：`-std=c++20 -DDJ_DISABLE_GIL=1`，include 加 DeepJIT、CUDA、torch（含 torch/csrc/api/include）三处，链接 `cudart、cuda、dw、torch、torch_cpu、torch_cuda、c10、c10_cuda`。跑之前设 `CUDA_HOME` 指向 toolkit 根目录。

## 三、实录一夜（一）：K1 状态机核

K1 是状态机更新核。功能一句话：读入一批事件，做事件编码、k/v 投影（ELU+1 激活）、L2 归一化，然后对 8 个事件逐个扫描更新一张 96×96 的状态矩阵 M 和两个移位环（Kr/Vr），外加长度/复位统计。

**先立对拍门**。oracle 用现役 TRT 引擎（同权重），五个输出全对到 fp16 噪声级（相对误差 ≤8e-3，vlen 逐位一致）。这一步花了耐心但救了命——后面所有的优化都是在"逐位/噪声级不退化"的门内做的。

**优化阶梯**（256 行/批，GPU 锁内实测，2026-09-30 开发日志）：

| 阶段 | 手段 | 单批耗时 |
| --- | --- | --- |
| 初版 | 96 线程 | 2.07 ms |
| ① | 环移位改一次性全局定位，去掉 49KB 环形 smem | 2.06 ms（环不是瓶颈） |
| ② | 96 → 768 线程（8 事件×96 维并行展开） | 1.93 ms |
| ③ | 权重主机侧预转置 + 核内合并访存 | 0.496 ms（真凶） |
| ④ | warp 归约替 768 次 atomicAdd + #pragma unroll 8 | 0.312 ms（累计 6.6×） |

③一步把 1.93 ms 砍到 0.496 ms（对上一步 3.9×，较初版累计 4.2×），机制在第六节用玩具实验单独复现了。原实现里同 warp 的 32 个 lane 读权重 `[d][j]` 排布，相邻 lane 地址差 96 个 float（384 字节），完全不合并；权重在主机侧先转置、核内改读 `[j][d]`，相邻 lane 地址连续，一次访存指令 128 字节拿满。数学一行没变。

④顺带暴露了一个**潜伏竞态**：P4 阶段归一化写完共享内存、P5 跨事件组读，中间没同步——此前一直靠 warp 时序侥幸不炸，unroll 改变时序后只在"恰好 4 个激活事件"的行爆发。修法是归一化后补 `__syncthreads`。教训记一句：竞态靠时序掩盖不等于不存在，任何改变时序的优化都是开盲盒。

## 四、实录一夜（二）：K23 读出打分核

K23 更重：读出新状态、对每行 128 个候选打分，输出 logits。这一段踩的坑是全篇最密集的，挑有普适性的说。

**第一个坑是 DeepJIT 本身的**：这颗核用了大块动态共享内存，DeepJIT 的发射路径对它设属性时报错 700；同一份 cubin 用裸驱动 API 发射全通。绕法从这一刻定型：**nvcc 直编 cubin + `cuLaunchKernel` 直发**。后来 K1 的生产接入也沿用了这个姿势——DeepJIT 的编译和缓存管开发期，发射走裸驱动。前面量的那 150–240 ns 差距本身不大，压垮决策的是"发射路径有未解 bug"这一条：生产路径要的是最短可信链。

**三个真 bug 叠罗汉**：共享内存偏移公式少算了一个数组（6 个数组装成 5 个）；`__syncthreads()` 写在 `if` 分支内（发散屏障，未定义行为）；宿主侧一段赋值顺序错了导致权重指针为空。单独看每个都低级，叠在 700 报错的烟雾里，排了一阵子。

**bisect 被"假崩"污染**：二分定位时，早退的分支也报同样的非法访问，切换次数完全失真。真因有两个：调试遗留的 smem=0 发射，以及 nvcc 静默失败后程序拿着旧 cubin 在跑——编译日志里有错误但没人看。教训后来固化进了构建脚本：`system()` 类编译必须检查返回值和日志，cubin 时间戳必须对过源文件，失败就响亮地死，绝不复用旧产物。

**randn 会把数值验证带进沟里**。K23 最初对拍时 logits 出现 max=inf、p99≈700，怎么看都是数值 bug。换成真实量级的输入（各面取值∈[0,1]、状态 N(0,0.15)）后，与 TRT 的对拍回到正常水位——三方对拍（numpy-手写核、numpy-TRT）偏差同量级，佐证这是病态随机输入在 FiLM 放大链上的伪影，不是核的错。这条教训值一节标题：**对拍数据必须用真实量级**。

**优化阶梯**（同口径，开发日志）：4.557 → 3.47（拆成 K23a 读出 + K23b 打分两核）→ 1.40（K23a 重写 + K23b 寄存器分块：权重一次加载喂 8–16 个 FMA）→ 0.94（掩码打包：掩码外候选直写 -1e4，免掉分支）→ 0.881 ms 定版（分块宽度调优，smem 43KB→每 SM 3 块）。累计 5.2×。

![](https://pic4.zhimg.com/v2-b7eb3e49b661edbfb744f33ed17c7df7_r.jpg)

这一段还有四条一句话血泪，全部有事故现场：v2 重写引爆了基线遗传的跨 warp 原地读写竞态（又是一次"改时序开盲盒"）；float64 的 numpy 参考实现与量化路径的 TRT 在放大链上差 60–150 绝对值，拿它当中间量真值会把好核全员判死——**唯一可信的门是对 TRT 文件直接对拍**；插桩三连坑（dump 步长混用、dump 插在写相之前、补丁误删一个 `__syncthreads`——补丁后必数 sync 数）；warp softmax 里每 lane 必须持互斥元素（四个 lane 各算同样的 4 个 exp，归约出来的和大了 4 倍）。

**half2 判决**值得单独一段。把 K23 的候选打分段做 half 化时试了三种方案（half 权重+half 累加 / half 乘+fp32 累加 / fp32 主权重即时转 half2），数值全部失败（argmax 一致率 2%、logits 差 176 级），且三种方案的误差几乎逐位相同——说明不是累加精度问题、不是主权重量化问题，而是 SIMT 的 `__hmul2` 乘积本身舍到 fp16。对照组是 TRT：tensor core 的 fp16×fp16 乘积精确落到 fp32 累加，天生多这一位精度，而这条链上的 FiLM 放大把微小舍入放大了约 60 倍。定谳：**SIMT 路线的 half2 数值过不了门；真正的 half 红利只能走 mma（fp16 输入 / fp32 累加语义）**。已回滚 fp32 版本（4.55 ms 全绿）。

## 五、落地与验收：1.23× 是怎么构成的

落地分三步，每步全量验收（4k 手同 seed 的世界偏移、确定性、回归门、吞吐）：

| 路径 | 构成 | 腿级吞吐（16384 手/腿） | 世界偏移 vs 现役 |
| --- | --- | --- | --- |
| 现役 | TRT 合成图 | 92.4–92.9k 行/s | — |
| 混血 | K1 核 + TRT 纯头 | 110.5k 行/s（vs 同场现役 1.19×） | 翻转 1.56–2.08% |
| 全自定义 | K1+K23a+K23b，零 TRT 核执行 | ~114–116k 行/s（vs 同场现役 1.23–1.26×） | 翻转 0.0732%（3/4096） |
| 池引擎组换装 | 双组同构核链 | 3625 手/s（基线 3178 手/s，+14%） | 翻转 0.0977% |

（混血与全自定义分属同晚两次验收，各自与同场现役腿对照——两次基线 92.9k / 92.4k 行/s，相差 0.5%；池组一行的单位是手/s。）

正确性口径：单元链对拍 argmax 一致率 99.22%，状态 M 的 p99 相对误差 8.7e-3，logits 掩码内相对误差中位 5.4e-3（这是与 fp16-TRT 对拍的固有水位）；全部日期 2026-09-30，GPU 锁内实测。全自定义路径的世界偏移反而比混血低一个量级——差异指向读出打分段：混血里它跑 fp16 的 TRT 头，全自定义换成了 fp32 手写核。这是个意外之喜。

一个必须诚实交代的数字：**为什么不是 1.5×**。引擎纯批时 2.03 → 1.49 ms，只省 0.54 ms；而在线服务的整批周期里引擎只占约 55%（gather/scatter、主机-设备传输、调度、跨流等待占其余）。飞行窗 GPU 串行时间 8.15 → 5.97 → 3.69 ms（−55%）证明引擎侧确实在省，但墙已转移到管线。这是本次工程最大的认知收获：**动手之前先确认墙在哪，拆完之后确认墙挪到了哪**。原定"候选打分段 ~0.3ms"的目标也没有达成（定版 0.881ms，瓶颈是约 188MB/批的 L2 权重流量墙，FMA 理论地板只有 ~0.13ms）——mma 化是遗留的接续点，而 half2 判决表明激活量化是那条路上最大的风险。

## 六、今天的复现实验（2026-10-02）

日志数字是当晚的。为了检验机制本身（也为了这篇手记的数字纪律），今天在同一台笔记本、空闲 GPU 上补了两组实验（环境见第二节；驱动 595.91.07）。

**实验 A：三段式与发射开销**——见第一节的表和图。三个值得留意的点：冷编译 648 ms 中 nvcc 本体占 410 ms（meta.json 原命令单独计时），JIT 包装开销约 240 ms；磁盘缓存热启 0.28 ms——源码没改的重启进程几乎免费，真改了源码，缓存键变化会触发一次完整冷编（648 ms 那档）；DeepJIT 发射路径比裸驱动贵约 9–13%，开发期无感，生产期有理由绕开。

**实验 B：合并访存缩小复现**。把 K1 那步 3.9× 的真凶做成最小玩具：1024 个块，每块一个线程块算一行 96 维矩阵向量积，权重池 128 个 96×96 矩阵（4.7MB，大于 L2 的 3MB，强制每批从显存流过）。两个核的数学完全相同（fp32、同求和顺序），唯一区别是权重排布与访存下标——两个核都以源码字符串喂给 DeepJIT 现场编译（冷编约 430 ms/个，即第一节的表），发射走 `jit->launch`，整个实验从头到尾跑在 DeepJIT 上：

```cuda
// 核 U：原排布 W[d][j] —— 同 warp 相邻 lane 地址差 96 float，完全不合并
float acc = 0.f;
for (int j = 0; j < D; j++) acc += wg[d * D + j] * xb[j];

// 核 T：预转置 W[j][d] —— 同 warp 相邻 lane 地址连续，128B 拿满
float acc = 0.f;
for (int j = 0; j < D; j++) acc += wg[j * D + d] * xb[j];
```

结果（cudaEvent 计时，200 连发均值，预热 30 次，两轮复测偏差 <0.3%）：

| 核 | 单次耗时 | 等效带宽 | 正确性 |
| --- | --- | --- | --- |
| U（原排布） | 238.2 µs | 21.5 GB/s | 对拍 CPU 参考零超差（容差 1e-3 相对） |
| T（预转置） | 70.5 µs | 72.5 GB/s | 与 U 逐位一致（maxdiff=0） |

![](https://pic3.zhimg.com/v2-22708f3c5bac06b01045f6d08d9c0530_r.jpg)

3.38×（第二轮 3.37×），与当晚 K1 实战中合并访存一步的账（1.93→0.496 ms，对上一步 3.9×）同机制、同量级。两核输出逐位一致说明测到的纯粹是访存排布的账，不是数学的账。

## 七、使用感受

**先说尝鲜结论**：值得上手，但把它当脚手架，别当顶梁柱。开源不到一个月，毛边真实存在（动态 smem 发射报 700 未解、纯 C++ 宿主被迫带上 torch 头），可甜点区——源码字符串即内核、三层缓存、结构化编译选项——没有一样是花架子。而且新工具只有放进真负载里跑一晚才知道深浅：700 报错、glibc 补丁、torch 头强依赖，这些毛边读十遍 README 也撞不到。

**甜点区**：改动-编译-验证回路。改一行源码字符串，几百毫秒后新核在跑；四行 API；磁盘缓存让第二天重启进程几乎免费。对"内核还在频繁变形"的阶段，这个体验碾压"改 .cu → 手动 nvcc → 改加载路径 → 重跑"的循环。缓存键把编译选项、nvcc 版本、源码哈希全算进去，"我改的到底是哪个版本的核"这种事故被机制性消灭了。

**不甜点区**：动态 smem 超限的核在发射路径上报 700（未解，绕道裸驱动）；纯 C++ 宿主也被迫带上 torch 头和链接；单次冷编译 ~650 ms，对"每进程编一次"无感，但如果想玩"每帧生成内核"就要心里有数。

**JIT 是脚手架，不是终态**。最终的生产路径是 nvcc 预编 cubin + 裸驱动直发，DeepJIT 的发射路径和缓存全部退场——但它承担的"把核在几小时内写对"的迭代过程不可替代。定版核源就是从测试用的源码字符串里逐字抽出来的，开发模式一直保留到了今天。

**给同类场景的三条建议**（也送给自己训小模型、自己折腾部署的读者）：第一，先量化墙——本例引擎纯批时只省 0.54ms 而端到端拿到 1.23× 的验收判决，这组数字的差距本身就是"墙在哪"的答案；第二，写核先建对拍门，oracle、真实量级输入、逐位/噪声级判据，三样齐了再动手，数字不过门一切免谈；第三，优化顺序按性价比来：访存排布（今天 3.38× 的玩具就是证据）→ 线程组织与 warp 归约 → 最后才考虑 mma/张量核心。

## 八、局限

- 单机单卡（RTX 3060 Laptop 6GB），无多卡、无多机结论；性能数字均为该卡锁内实测，换卡需重测。
- DeepJIT 迭代很快，本文全部结论基于我拿到的 commit 3732a3b（9 月底的 PyTorch stable ABI 迁移版），API 与行为可能随后续版本变化——尝鲜文的半衰期本来就这么短。
- 第六节的复现是玩具缩小版：3.38× 验证的是机制，与实战中的 3.9× 不能直接比（工作集、占用率、smem 压力都不同）。
- K23 原定目标未达（候选打分段 ~0.3ms vs 定版 0.881ms），mma 化路线未开工，half2 判决提示激活量化是主要风险。
- 第三节至第五节的开发日志数字引自 2026-09-30 当晚的实测记录，本文未重放原始实验；验收明细以该记录为准。

## 附录 C：合并访存复现的两个核（完整源码）

两个核以源码字符串形式存在宿主程序里，喂给 DeepJIT 现场编译（冷编约 430 ms/个，缓存命中后约 0.1 ms）：

```cpp
auto k_u = jit->compile("matvec_u", SRC_MATVEC_U);   // 核 U 源码字符串 → cubin → 加载
auto k_t = jit->compile("matvec_t", SRC_MATVEC_T);   // 同一进程内第二个变体，另付一次编译
jit->launch(k_u, { .grid_dim = dim3(1024), .block_dim = dim3(96) }, d_wu, d_x, d_yu);
jit->launch(k_t, { .grid_dim = dim3(1024), .block_dim = dim3(96) }, d_wt, d_x, d_yt);

```

核源本体（即上面 SRC_MATVEC_U / SRC_MATVEC_T 字符串的内容）：

```cuda
#define D 96
#define NW 128
extern "C" __global__ void matvec_u(          // 原排布：W[g][d][j]
        const float* __restrict__ W, const float* __restrict__ x, float* __restrict__ y) {
    const int b = blockIdx.x, d = threadIdx.x;
    const float* wg = W + (long)(b % NW) * D * D;
    const float* xb = x + (long)b * D;
    float acc = 0.f;
    for (int j = 0; j < D; j++) acc += wg[d * D + j] * xb[j];   // lane 跨度 = D
    y[(long)b * D + d] = acc;
}
extern "C" __global__ void matvec_t(          // 预转置：WT[g][j][d]
        const float* __restrict__ W, const float* __restrict__ x, float* __restrict__ y) {
    const int b = blockIdx.x, d = threadIdx.x;
    const float* wg = W + (long)(b % NW) * D * D;
    const float* xb = x + (long)b * D;
    float acc = 0.f;
    for (int j = 0; j < D; j++) acc += wg[j * D + d] * xb[j];   // lane 连续
    y[(long)b * D + d] = acc;
}
```

（两个核逐位一致的前提：fp32、同求和顺序、同一编译选项。逐位一致才能把耗时差全部记在访存排布头上。）
