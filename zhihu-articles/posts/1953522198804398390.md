## 1.tensor 计算硬件单元常见的三种接口

计算图接口+向量计算接口+指令集合接口。

目前大部分npu都支持计算图接口，如果不支持它就卖不了。指令集接口因为容易暴露秘密几乎不支持，nvidia也只支持暴露了ptx指令集。所以我们讨论的重点就变为了如何支持向量计算接口，支持类似cuda这种向量计算的接口就意味着可以自定义算子，才能让今年发布的npu支持未来才会有的模型算子，而不是等厂家适配了后，npu才能支持对应的算子。

下面我们简单讨论一下这两种方式的成本和代价。因为我能力相关，个别错误辛苦指正。

## 2.成本和代价

### 2.1 triton这种python first的dsl

<br>1）编译器后端：Triton → NPU<br>

| 任务 | 交付物 | 关键动作 & 坑 |
| --- | --- | --- |
| Fork Triton 官方仓库，建立 triton-npu 分支 | GitHub 私有库，CI 能编过 | LLVM 的仓库很重要，也要看自己npu的编译器。openai triton 的nvidia backend就是用llvm的ptx ir生成的代码。 |
| 新增 npu Target 到 triton/lib/Target/ | NPUTargetInfo.cpp NPUAsmPrinter.cpp | 参考 AMDGPU 目录，先把 ModuleOp 降到你们已有的 mlir → NPU 通路；先只支持 FP16 GEMM，别的 op fallback 到 CPU。 |
| 实现 TritonGPUToNPU Pass | triton-gpu-to-npu-pass.cpp | 把 Triton 的 blocked -> shared -> dot_op（把 tile 再劈一次，变成 MMA 指令能直接吃下去的“寄存器片”） 三步 layout 降到你们片上 SRAM 的 tile 原语；shared memory 容量更具真实设置 tile 块。 |
| 二进制格式 & 驱动接口 | .nbin 文件格式、libnpu_compiler.so | 参照 cudaFatBinary 在 .nbin 里放多种 arch=mp_10/20/30 镜像；驱动只需实现 ioctl(NPU_IOC_LOAD_BIN) 即可。 |

<br><br><br>2. 运行时：让 kernel 能在 NPU 上启动<br>

| 任务 | 交付物 | 关键动作 & 坑 |
| --- | --- | --- |
| 写 libnpu_runtime.so | npLaunchKernel / npStreamCreate 等 30 个 API | 先做到 同步执行（省去 event、callback），把 dim3 grid, block 翻译成你们硬件的 task_id + tile_id；threadIdx.x 用硬件 local_id 直接映射，不要搞复杂调度。<br>最终版本要决定应用层的thread 号是如何对应驱动的job。 |
| PyTorch 插件 torch.npu | torch_npu.cpp | 把 Triton 生成的 *.nbin 用 PYBIND11_MODULE 包成 autograd.Function；保证 DLPack 零拷贝，否则 ViT 的 224×224 图像吞吐直接掉 30 %，都不要考虑llm。 |

### 2.2 实现一套cuda类似的接口

你得定义一门新的语言（类比cuda）+新的编译器（类比nvcc）+新的算子库(对比cublas 、cutlass cudnn 等)。

1）语言层：定义NPU C++扩展，对比cuda。

- 新增关键字/属性，例如`__npu__` `__global_npu__` `__shared_npu__` `<<<grid, block>>>` 语法。
- 提供头文件 `<npu_runtime.h>` 等价于 `<cuda_runtime.h>`，把`npMalloc / npMemcpy / npLaunchKernel` 等 API 对齐 CUDA。
- **实现方式**：基于 Clang 做 fork，把新关键字转成低层内置或内联汇编。<br>

2）编译器：把NVCC造出来

**.npu → （device pass）→ PTX 等价物 → 汇编器 → cubin 等价物 → （host pass）→ 改写 <<<>>> → 与 fatbinary 链接 → .so/.bin**

- 前端：Clang 插件搞定 C++ 扩展解析。
- 中端：LLVM IR → 你们自己的 NPU IR。
- 后端：– PTX 等价物：文本化可移植 IR（假如叫 `.nir`），内含 `arch=compute_70` 同款 capability 字段；– 汇编器：把 `.nir` 汇编成 `.nbin`（真正的微码）；– fatbinary：把多版本 `.nbin` 和 `.nir` 压进一个 fatbin，供运行时 JIT 选用。
- 主机端：把 <<<>>> 语法换成 `__npLaunchKernel(fatbinEntry, dim3, dim3, args…)`。

3）驱动与运行时：把CUDA driver/runtime造出来

- **用户态 runtime**（libnpu_runtime.so）– `npSetDevice / npMemcpyAsync / npStreamSynchronize` 全级对等；– 把 fatbin 解析、代码段加载、参数打包、队列下发全部包办。
- **内核态驱动**– 提供 `/dev/npu0` 字符设备，实现 `ioctl`：分配片上 SRAM、下发 kernel 描述符、做 DMA 映射。– 支持多进程、多 stream、地址空间隔离、错误回收。
- **JIT 编译器**（可选）若现场只装了 `.nir` 没装 `.nbin`，则由驱动调用 `libnpu_compiler.so` 即时汇编。

4）调试与 profiling：把cuda-gdb / nsight造出来

- 在 `.nir` 里嵌入 dwarf 行号，kernel 侧支持 printf、assert、单步、断点。
- 提供 `npu-gdb` 前端，让 gdb 能识别 `__global_npu__` 函数符号。
- 提供 `npuprof` CLI，能导出 chrome tracing 格式的 kernel 时间线。对比nsys、ncu。<br>

5）库与生态：把cuBLAS / cuDNN造出来

- 先给线性代数、卷积、attention 写 20 个高频 kernel，做到`npublasSgemm`、`npudnnConvolutionForward` API 级兼容。
- 用 template pack 的方式，让 PyTorch `torch.backends.npu` 只需改 10 行即可 `torch.cuda` 无缝替换。
- cuSPARSE 、cuFFT 、cuRAND等lib也要实现。<br>

6）打包交付

产出类似：

```text
/usr/local/npu-sdk/
├── bin/npucc                 # 编译器驱动
├── include/npu_runtime.h     # 运行时 C 头
├── lib64/libnpu_runtime.so   # 运行时
├── lib64/libnpublas.so       # 高性能库
└── tools/npu-gdb             # 调试器
```

## 3.结论

1）PyTorch 官宣：告别 CUDA，GPU 推理迎来 Triton 加速新时代，最新的pytorch2 一半以上都是用triton来实现的算子了。尤其是flash attention mla等复杂算子。<br>2）nvidia基于cutlass演化来的cute，已经支持了python的dsl。 CuTile DSL好像也要马上发布了。<br>3）基于triton这种python first的方案，可以直接使用pytorch的资源，也不需要额外定义前端的dsl语言，并规训用户。

4）基于triton的方式不用开发前端语言了，只需要开发backend的算子优化和codegen+runtime适配。不用自己实现庞大的算子库了。也不要花费巨大维护类似nvcc这套编译器。

5）因为经过triton编译后的已经是指令了，所以不存在效率问题。并且针对比如自动驾驶代码全是c++的场景，可以生成c++算子代码，或者直接生成lib，然后使用runtime的plugin的方式插入来调用。

6)详细对比

| 维度 | NPU 自己实现 CUDA 接口（含 npucc + 驱动 + cuBLAS 等价物） | NPU 借助 Triton（fork triton-lang，加 own backend） |
| --- | --- | --- |
| 目标 | 让存量 CUDA 代码 零改动 重新编译即可跑。或者处于宣传技术牛逼的角度。 | 让新写 Python DSL 能一键编译到 NPU； |
| 接口形态 | 源码级兼容：.cu、<cuda_runtime.h>、<<<>>>、__global__ 全部保留 | 新 DSL：Python 装饰器 @triton.jit，tl.load/tl.store 编程模型 |
| 开发量 | 巨大——语言前端、驱动、runtime、JIT、math 库、调试器、profiling 全栈自研； | 中等——复用 Triton 前端 + 优化 Pass，只写后端 CodeGen 与 runtime； |
| 性能上限 | 理论上 =CUDA（同算法同硬件频率）；实际首版只能到 60–70 %，持续优化 3 年可逼近 90 % | 实测 *76–82 % CUDA（H100/A100 上 LLM 推理）；GEMM 慢 1.2–1.4×，Flash-Attn 慢 1.6×，仍有追赶空间 |
| 硬件细节暴露 | 全暴露——shared-memory 大小、bank 宽度、warp 宽度、tensor-core 指令都得在头文件/PTX 里可见，NPU 必须 1∶1 模仿 | 隐藏——Triton 用 tile/block 抽象，编译器自动分片、排流水，NPU 只需实现 “tile 计算 + SRAM 搬运” 原语即可 |
| 生态借力 | 生态为0 →全部自己拉社区；PyTorch 侧要写 torch.backends.npu 插件，TF/Jax 同理 | 直接继承 Triton 已有生态：PyTorch torch.compile、vLLM、HF Transformers、 |
| 跨平台能力 | 无——二进制、驱动、PTX 都是 NPU 私有，换另一家 NPU 要重新实现 | 天然跨平台——同一套 @triton.jit Python kernel 可在 NVIDIA/AMD/Intel/自家 NPU 上各走各 backend。 |
| 维护成本 | 高——CUDA 每升大版本（如 12→13）就得同步改语法、指令、库；长期养一个 “NVCC 平行世界” 团队 | 低——Triton 上游迭代只需定期 rebase，后端接口稳定；focus 在性能 Pass 即可 |
| 长期演进 | 只能 跟随 NVIDIA 节奏；CUDA 新特性（如 FP8、Blackwell 新指令）出现即落后至少 1 年 | 可 共同制定 上游路线；Triton 社区已把 FlexAttention、Split-K GEMM 等贡献合并，NPU 后端自动受益 |
| 典型落地时间 | 3–4 年才能对外宣称 “CUDA 兼容” 且可商用 | 1–1.5 年即可 “Llama-7B/ViT-Base 端到端跑通”，2 年达到生产 SLO |
