# eval() 执行模型输出：国产推理服务 Xinference 工具调用解析 RCE（CVE-2026-61539，CVSS 10.0）

## TL;DR

AI 推理服务 Xinference（Xorbits，GitHub 9.5k★）的 Llama3 工具调用解析器用 `eval(model_output, {}, {})` 直接执行「模型生成的文本」——而模型输出可被攻击者用一条精心构造的 chat 请求诱导。默认部署无鉴权，远程攻击者发一条 `/v1/chat/completions` 请求即可让服务器执行任意命令。**CVSS 10.0，Critical，2026-08-21 才进入 GitHub Advisory Database，中文社区零覆盖。** 修复方式是把 `eval()` 换成 `json.loads()` + `ast.literal_eval()`。

核心链条：**攻击者控制 prompt → 模型输出变成 Python 表达式 → 服务端 eval() 执行 → RCE**。

## 二、攻击链拆解：一条请求怎么变成一台服务器的沦陷

### 2.1 第一步：诱导模型输出恶意表达式

Xinference 提供 OpenAI 兼容的 `/v1/chat/completions` 接口。当请求里带 `tools` 字段（工具调用），Transformers 后端在推理完成后会进入工具调用解析流程。

问题在于：**工具调用的「参数」本质是模型生成的自由文本**。模型不是结构化输出引擎——它只是按概率生成下一个 token。攻击者把恶意指令写进 user prompt，就能诱导模型在 tool call 的 parameters 位置输出类似这样的内容：

模型输出类似 `{"name": "get_weather", "parameters": "<任意表达式>"}`——parameters 可以是任意字符串，包括恶意表达式（具体形态见官方 advisory PoC）。

正常情况模型会输出 `{"name": "get_weather", "parameters": {"city": "北京"}}` 这样的字典。但 prompt 注入可以让它输出任何 Python 表达式。

### 2.2 第二步：解析器把模型输出喂给 eval()

带 tools 的请求处理链路：`restful_api.py` → Transformers 后端 `core.py` 的 `handle_chat_result_non_streaming()` → 检测到 `tools` 字段后调用 `_post_process_completion()` → 进入 Llama3 工具解析器。

漏洞代码在 `xinference/model/llm/tool_parsers/llama3_tool_parser.py`：

```text
def extract_tool_calls(self, model_output: str):
    try:
        data = eval(model_output, {}, {})   # ← 漏洞行：执行模型输出的文本
        return [(None, data["name"], data["parameters"])]
    except Exception:
        return [(model_output, None, None)]

```

同一份漏洞还存在于 `xinference/model/llm/utils.py` 的 `_eval_llama3_chat_arguments()`（非流式 chat 的 tool call 处理路径）：

```text
@classmethod
def _eval_llama3_chat_arguments(cls, c):
    text = c["choices"][0]["text"]
    try:
        data = eval(text, {}, {})           # ← 漏洞行
        return [(None, data["name"], data["parameters"])]
    except Exception:
        return [(text, None, None)]

```

开发者的本意：模型输出的 tool call 是一个「长得像 Python 字典的字符串」，用 `eval()` 把它变成真正的 dict，然后取 `name` 和 `parameters`。

但 `eval("<含命令执行的表达式>", {}, {})` 不会报错——它会真的执行。

### 2.3 第三步：为什么 `eval(x, {}, {})` 不是沙箱

很多开发者以为传 `{}, {}` 作为 globals/locals 就能隔离内建函数。这是经典误解。

`eval()` 的文档写得明白：**即使你传了空的 globals 字典，Python 也会自动注入 `__builtins__`**。所以 `__import__`、`open`、`exec`、`getattr` 这些全能函数照样可用：

### 2.4 第四步：未认证 RCE

GHSA 原文确认：**测试的默认部署没有启用鉴权**。也就是说攻击者不需要任何账号密码，直接向暴露的 `/v1/chat/completions` 发请求即可。命令在 Xinference 服务进程的权限上下文中执行——生产环境通常就是部署机 root/systemd 用户，可以读敏感文件、下载挖矿木马、横向移动。

CVSS 评 10.0 不是夸张：AV:N（远程可达）+ PR:N（无需权限）+ C:H/I:H/A:H（完全失陷）。

## 三、官方修复：eval → json.loads + ast.literal_eval

修复 PR #4786（commit 1b3d220）把两个漏洞点都改了。修复后 `llama3_tool_parser.py` 的 `extract_tool_calls()`：

```text
def extract_tool_calls(self, model_output: str):
    try:
        # 先试 JSON（LLM 最常见的输出格式）
        data = json.loads(model_output)
    except (json.JSONDecodeError, TypeError):
        try:
            # 再退回 ast.literal_eval，兼容 Python 字面量格式
            # （如 True/False/None 而非 true/false/null）
            # 与 eval() 不同，ast.literal_eval 只允许字面量结构，
            # 无法执行任意代码。
            data = ast.literal_eval(model_output)
        except (ValueError, SyntaxError):
            return [(model_output, None, None)]
    try:
        return [(None, data["name"], data["parameters"])]
    except (KeyError, TypeError):
        return [(model_output, None, None)]

```

关键点： 1. **`json.loads()` 优先**——纯数据解析，永远不执行代码，模型输出 `{"name": ..., "parameters": {...}}` 直接正常解析； 2. **`ast.literal_eval()` 兜底**——它只接受字符串/数字/元组/列表/字典/布尔/None 字面量，遇到 `__import__(...)`、函数调用、属性访问直接抛 `ValueError`，从语法树层面拒绝代码执行； 3. **`except Exception` 收窄为 `except (KeyError, TypeError)` / `(ValueError, SyntaxError)`**——不再吞掉所有异常掩盖问题。

`utils.py` 的 `_eval_llama3_chat_arguments()` 同样替换。

回归测试新增 25 个用例，其中安全用例覆盖：

- 恶意 payload | 修复后行为
- 命令执行载荷（见 PR #4786） | 拒绝，按原文返回不执行
- 对象内省逃逸载荷（见 PR #4786） | 拒绝，按原文返回不执行
- exec('import os') | 拒绝，按原文返回不执行
- 正常 JSON tool call | 正常解析 ✅
- Python 字面量格式{'name': 'toggle', ...} | 正常解析 ✅

### 修复 PR 的另一个亮点：全库审计

PR #4786 还审计了其余 7 个工具解析器（qwen/deepseek_v3/deepseek_v3_1/deepseek_r1/glm4/minimax 等）——**它们本来就都用 `json.loads()`，只有 Llama3 解析器用了 `eval()`**。这提示一个规律：同仓库不同后端的「同一功能」，代码质量可能天差地别——审查工具调用解析安全时，不能因为「其他解析器安全」就跳过某个特定后端。

## 四、本地快速验证：10 秒看清 eval 与 ast.literal_eval 的差距

不需要部署 Xinference 也能理解漏洞本质——在本地 Python 里直接跑下面这段（与漏洞代码等价的提取逻辑）：

```text
# 模拟 Xinference 漏洞版解析器（CVE-2026-61539）
def extract_vulnerable(model_output: str):
    """漏洞版：eval 执行模型输出"""
    try:
        data = eval(model_output, {}, {})          # 与漏洞源码一致
        return (data.get("name"), data.get("parameters"))
    except Exception:
        return (model_output, None)

# 模拟修复版解析器（PR #4786 后的逻辑）
import json, ast
def extract_fixed(model_output: str):
    """修复版：json.loads 优先 + ast.literal_eval 兜底"""
    try:
        data = json.loads(model_output)
    except (json.JSONDecodeError, TypeError):
        try:
            data = ast.literal_eval(model_output)
        except (ValueError, SyntaxError):
            return (model_output, None)
    return (data.get("name"), data.get("parameters"))

# —— 测试 1：正常 tool call ——
normal = '{"name": "get_weather", "parameters": {"city": "Beijing"}}'
print("正常请求  漏洞版:", extract_vulnerable(normal))
print("正常请求  修复版:", extract_fixed(normal))

# —— 测试 2：恶意 payload（攻击者诱导模型输出的表达式）——
evil = "<命令执行载荷，结构见官方回归测试>"  # import os 后调用 system
print("\n恶意请求  漏洞版:", extract_vulnerable(evil))  # ← 会真的打印 PWNED
print("恶意请求  修复版:", extract_fixed(evil))        # ← 安全，按原文返回

# —— 测试 3：对象内省逃逸（即使禁 __builtins__ 也危险）——
evil2 = "<对象内省逃逸载荷>"  # 遍历类层级
print("\n内省逃逸  漏洞版:", type(extract_vulnerable(evil2)))  # ← 返回类列表，泄露对象图
print("内省逃逸  修复版:", extract_fixed(evil2))              # ← 拒绝

```

预期输出对照：

- 测试 | 漏洞版 eval | 修复版 json.loads+literal_eval
- 正常 tool call | ✅ 解析成功 | ✅ 解析成功（功能不降级）
- 命令执行载荷（结构见官方回归测试） | ❌执行命令（打印 PWNED） | ✅ 安全返回原文
- 对象内省逃逸载荷（见 PR #4786） | ❌ 返回全类列表（逃逸前置） | ✅ 抛 ValueError 被捕获

这个实验同时验证了两件事：**修复不破坏正常功能，且恶意输入被彻底拒绝**——官方 25 个回归测试覆盖的正是这三类。

## 六、这类漏洞的家族谱：模型输出永远不可信

CVE-2026-61539 不是孤例，它属于一个正在快速扩大的漏洞家族——**服务端把模型输出当代码/命令执行**：

- 漏洞/事件 | 本质 | 教训
- Xinference CVE-2026-61539（本文） | eval() 执行模型 tool call 输出 | 工具调用参数解析用 json.loads
- Semantic Kernel eval 绕过（2026-08 双 CVE，本专栏 #09） | prompt 注入 + eval 沙箱逃逸 | eval 沙箱不存在，禁止 eval
- 各类「LLM 生成 SQL/代码后直接执行」事故 | 模型输出当可信指令 | 输出校验 + 最小权限 + 人类审批
- 提示词注入 → 工具调用越权（本专栏 #08） | 模型被诱导调用危险工具 | 工具侧 ACL，不信任模型意图

**共同根因一句话：LLM 的输出是「概率生成的文本」，不是「可信任的结构化数据」。** 所有把它当代码、当 SQL、当 shell 命令、当可信工具参数的地方，都必须做数据级净化（parse），而不是执行级处理（eval）。

## 七、常见误区 FAQ

**Q1：`eval(x, {}, {})` 传了空字典不是就安全了吗？** A：不是。Python 的 eval 在 globals 没显式给 `__builtins__` 时会自动注入完整内建模块。内建导入函数能拿到，等于整个标准库都可用。要挡代码执行唯一可靠方式是根本不用 eval——用 `ast.literal_eval()` 或 `json.loads()`。

**Q2：`ast.literal_eval()` 绝对安全吗？** A：对「防代码执行」这个目标，`ast.literal_eval()` 是安全的——它只解析字面量节点，函数调用/属性访问在 AST 层就被拒绝。但它不是 JSON 解析器：它接受 Python 单引号字符串、True/False/None（而非 true/false/null），还可能解析出超大对象消耗内存。所以生产首选 `json.loads()`，`literal_eval` 只做兼容兜底（官方修复正是这个顺序）。

**Q3：只有 Llama3 模型受影响吗？** A：是。漏洞在「Llama3 tool parser」里，只有用 Transformers 后端加载 Llama3 系模型并开启工具调用才会走到 eval 路径。但其他模型的解析器如果后续被改成 eval 同样会中招——查版本比查模型更可靠。

**Q4：我不用工具调用功能，受影响吗？** A：请求里不带 `tools` 字段就不会走进 tool parser。但如果服务无鉴权暴露公网，攻击者随时可以带 `tools` 字段打——**功能不用不等于漏洞不存在**。修复版本 2.7.0 出来就升，别赌没人打。

**Q5：发现者里有腾讯玄武实验室，国产项目被国产安全团队挖洞说明什么？** A：说明 AI 基础设施安全审计在国内已经进入实战阶段——玄武 + Atuin 自动化引擎的组合意味着这类「模型输出 → eval」漏洞会被成规模地自动化发现。国产推理服务用户（Xinference/其他）应该把「升级到最新版」当作常规安全操作，而不是等出了事再补。

## 八、写在最后

CVE-2026-61539 是一次教科书级的「一行代码毁掉一个服务」：开发者的意图只是把模型输出的字典字符串转成 Python 对象，手一滑用了 `eval()`，CVSS 直接拉满 10.0。

三个必须记住的认知：

1. **模型输出不可信，尤其在工具调用场景**——tool call 的参数是自由文本，解析它只能用数据解析器（json.loads / ast.literal_eval），任何 `eval/exec` 都是 RCE；
2. **`eval(x, {}, {})` 不是沙箱**——`__builtins__` 自动注入 + 对象内省逃逸，传空字典只是心理安慰；
3. **默认无鉴权的推理服务是公网上的裸奔靶子**——Xinference 只是第一个被公开的，任何暴露 `/v1/chat/completions` 的服务都该自查：鉴权开了吗？版本最新吗？代码里有 eval 吗？

**排查顺序永远先查版本，再查鉴权，最后查代码里的 eval。**
