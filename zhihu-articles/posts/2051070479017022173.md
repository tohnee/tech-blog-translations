最近需要评估一个目标检测模型在服务器上的实际推理吞吐，于是写了一套完整的 TensorRT 压测工具，对同一个模型分别测试了 **FP32 / FP16 / INT8** 三种精度在不同 Batch Size 下的表现。结论有些出乎意料——同一张卡、同一个模型，最优配置和最差配置的吞吐相差 **4.6 倍**。

### 测试环境

| 项目 | 配置 |
| --- | --- |
| GPU | 双卡T4服务器（本文为单卡结果） |
| CUDA | 11.8 |
| TensorRT | 8.6.1 |
| Python | 3.10 |
| 模型输入 | [B, 3, 544, 960] float32 |
| 模型输出 | [B, 6, 10710] 检测候选框 |

**精度说明：**

- **FP32**：原始精度，CUDA Core 运算
- **FP16**：TensorRT 半精度，启用 Tensor Core
- **INT8**：TensorRT INT8 量化，本次使用随机数据校准（仅测速，不代表精度表现）

---

### 测试流程

```text
ONNX（各 Batch 静态导出）
       │
       ▼
TRT 编译 Engine ── fp32 / fp16 / int8 各一套
       │
       ▼
单线程压测（Batch=1/2/4/8/16/32，各 15s）
       │
       ▼
多线程并发压测（线程数=1/2/4/8/16，各 15s）
       │
       ▼
GPU 监控采样（每 500ms 记录利用率 + 显存）
       │
       ▼
汇总对比表
```

双卡并行策略：FP32 跑在 GPU0，FP16 同时跑在 GPU1，FP32 结束后 GPU0 立即接 INT8，总测试时间缩短约 1/3。

### 深入分析

### FP32 完全饱和，加大 Batch 没有意义

FP32 在 Batch=1 时 GPU 利用率就已达到 **88%**，此后将 Batch 从 1 涨到 32，吞吐仅从 89.9 提升到 92.4 img/s，增幅不足 **3%**，但延迟却从 11ms 涨到 346ms，整整 **31 倍**。

原因是 FP32 在 CUDA Core 上运算，该模型的算力需求已经把 SM 打满，增大 Batch 只是让更多任务在队列里等待，不产生实际并行收益。

> **结论：FP32 无论 Batch 多大都只有约 95 img/s，不适合追求吞吐的部署场景。**

---

### FP16 利用率偏低是正常现象，甜点在 Batch=16

FP16 全程 GPU 利用率稳定在 **70~73%**，看起来”没跑满”，但吞吐却是 FP32 的 2.5~2.9 倍。

这个矛盾并不奇怪：FP16 使用 Tensor Core 运算，而 NVML 统计的 `gpu_util` 指的是 **CUDA Core 占用率**，Tensor Core 饱和时 CUDA Core 可以是空闲的，因此监控数字偏低是正常现象，实际 Tensor Core 已经在全速工作。

Batch 从 1 增加到 16，吞吐从 220 → 270 img/s，提升了 **22%**，收益来自摊薄 H2D/D2H 数据搬运的固定开销。Batch=32 时小幅回落，内存带宽开始成为限制。

---

### INT8 全场最强，但 Batch=4 出现了一个异常峰

![](https://pica.zhimg.com/v2-33b6f8dfea2b308b0cfd962490a7c252_r.jpg)

INT8 在 Batch=4 时跑出了 **439.3 img/s**，是 FP32 同配置的 **4.6 倍**，也是全场最高。

然而 Batch=8 时吞吐直接跌到 349 img/s，GPU 利用率从 85% 掉到 59%，幅度明显。这不是测量误差，而是 **TensorRT 在 Batch=8 时为该模型选择了不同的 INT8 GEMM kernel**，该 kernel 对 `[8, 3, 544, 960]` 这个 shape 的 tiling 方式效率更低。这是 TRT 自动 kernel 选择机制的已知行为，与 GPU 型号、TRT 版本和具体模型结构都有关系。

Batch=8 之后吞吐稳定在 349~361 img/s，GPU 利用率稳定在 59%，瓶颈已从计算转移到**显存带宽**——INT8 权重体积更小，数据搬运速度反而成了上限。

> **结论：INT8 Batch=4 是全场最优，追求低延迟则选 INT8 Batch=1（3.6ms）。生产使用 INT8 需要真实数据集校准。**

---

### 多线程并发无法提升吞吐

![](https://picx.zhimg.com/v2-8723df6d72be9b0f3e667cb893fa07e7_r.jpg)

以 FP16 Batch=32 为例，增加并发线程数：

| 线程数 | 吞吐 (img/s) | P99 延迟 (ms) | GPU 利用率 |
| --- | --- | --- | --- |
| 1 | 307 | 125 | 84% |
| 2 | 307 | 323 | 83% |
| 4 | 305 | 573 | 84% |
| 8 | 305 | 1203 | 87% |

吞吐从 1 线程到 8 线程几乎没有变化，P99 延迟却翻了近 **10 倍**。原因是单线程已接近 GPU 饱和，多线程只是把请求堆在调度队列里轮流执行，并不产生真正的 GPU 并行。

### 最终推荐

![](https://pica.zhimg.com/v2-1217af5cc89006f0225fd41aa936593e_r.jpg)

| 场景 | 推荐配置 | 吞吐 | P50 延迟 | 显存 |
| --- | --- | --- | --- | --- |
| 最高吞吐（精度要求宽松） | INT8 Batch=4 | 439 img/s | 9 ms | 644 MB |
| 生产高吞吐 | FP16 Batch=16 | 270 img/s | 59 ms | 1030 MB |
| 低延迟实时 | INT8 Batch=1 | 276 img/s | 3.6 ms | 592 MB |
| 低延迟保精度 | FP16 Batch=1 | 220 img/s | 4.5 ms | 606 MB |
| 不推荐 | FP32 任意 Batch | ~95 img/s | 高 | 高 |
