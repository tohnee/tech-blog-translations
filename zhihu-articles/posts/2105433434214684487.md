RISC-V AI CPU 为 AI 计算提供了向量和矩阵扩展，而这些硬件能力能否在模型中发挥作用，很大程度上取决于算子的实现。对算子开发者来说，需要处理的既有不断变化的量化格式、数据准备和累加方式，也有不同芯片的向量宽度、寄存器容量与指令约束。两类变化交织在一起，增加了算子开发与维护的工作量。

Weft 为这类 CPU 算子提供了一种可组合的编程模型。它让程序描述数据如何解释、计算如何组织，以及哪些结果需要共享或延续，再由编译器根据目标 CPU 安排具体的存储、布局和指令。

基于这一模型，Triton 和 TileLang 分别扩展为 Triton–Weft 与 TileLang–Weft，使开发者可以在两种语言中使用 Weft 的抽象，编写面向 RISC-V AI CPU 的算子。两个前端共用 CPU 编译核心与运行时，已完成多平台算子测试；Triton–Weft 进一步接入 llama.cpp，检验算子在完整模型推理中的效果。

**一、Weft：面向 CPU 的算子编程模型**

CPU 算子的性能，除了取决于执行什么运算，还取决于这些运算怎样配合。以低比特线性层为例，权重需要解码，激活可能需要预处理，计算结果需要跨输入块持续累加。同一份准备结果能被多少计算复用、累加状态保留到什么时候，都会影响最终的执行效率。

Weft 将这些组织选择分别表达为字段解释、算术形式、准备范围和状态生命周期。程序可以明确描述“一份数据由哪些计算共享”“一个结果怎样连续更新”，而不必在同一处固定它们对应的寄存器与缓冲区。

![](https://pica.zhimg.com/v2-fd9e2dd6acbee17ce912f1ff59b30322_r.jpg)

*图 1 Weft 编程模型与 CPU 算子组织。程序表达字段、算术、共享准备与状态之间的关系，编译器面向目标 CPU 实现存储、布局和指令。*

如图 1 所示，算子的组织方式与底层实现之间有了明确分工。开发者可以围绕量化格式和计算方法扩展算子，编译器则处理这些逻辑在具体硬件上的实现。已有的准备与计算逻辑也因此可以被后续格式复用，减少重复组织整个算子的工作。

**二、扩展 Triton 与 TileLang，共用 CPU 编译框架**

编程模型需要与实际的开发工具连接。围绕 Weft 的前端扩展形成了 [Triton–Weft](https://gitee.com/dongshan-community/triton-weft) 和 [TileLang–Weft](https://gitee.com/dongshan-community/tilelang-weft)：前者保留 Triton 的张量操作与 JIT 工作方式，后者保留 TileLang 的 tensor、tile 操作、循环、宏和调优接口，并分别加入 Weft 的 CPU 编程抽象。

两个前端在共享的 Weft 中间表示中汇合。算子组织信息在这一层保留下来，再由后端根据目标平台生成原生 CPU 算子。图 2 展示了整体框架。

![](https://pic4.zhimg.com/v2-8694dea25f32ac6da800027e33f28af7_r.jpg)

*图 2 Triton–Weft 与 TileLang–Weft 的共享编译框架。两个语言前端接入同一套 Weft 编译核心，连接 RISC-V、x86 后端与原生运行时。*

在 RISC-V 侧，当前实现覆盖 SG2044、K1 和 K3 等平台，适配不同的向量宽度，以及 K1 的 IME、K3 的 IME2 矩阵扩展；x86 侧也提供了相应后端。CPU 的布局、指令和资源处理集中在共享编译核心中，两种前端可以复用这些能力。

这一实现还包含从编译到调用的执行路径：生成的算子既能通过 Python 的 JIT 调用执行，也能通过原生 C 接口嵌入 C/C++ 程序。仓库提供了导出、原生调用和 GGML 部署示例，使前端扩展能够继续接入实际的推理软件。

**三、实际运行：算子性能与模型推理**

**算子性能**

算子层面的评测覆盖 SG2044、K1、K3 和 Xeon 8470Q 四个平台，包含低比特计算、格式转换、矩阵运算、归一化等任务。Triton–Weft 的测试共包含 553 个“算子—平台”用例，其中 543 项有匹配的参考库耗时，476 项快于参考实现。

图 3 给出了代表性算子的结果和全部匹配用例的性能分布。相对各自的参考实现，Triton–Weft 在 SG2044、K1 和 K3 上的加速比几何平均分别为 **1.60×、1.54× 和 1.83×**，在 x86 上为 **1.32×**。

![](https://picx.zhimg.com/v2-cdae80e8eab60c316c69fe63cb9f3aa9_r.jpg)

*图 3 Triton–Weft 的算子性能。(a) 代表性算子的加速比；(b) 全部 543 项匹配比较的累积分布。加速比大于 1× 表示快于参考实现，GM 表示几何平均。*

这组结果采用单线程原生算子调用计时，不包含 JIT 编译和 Python 分发开销。参考实现以 GGML 为主，并包含 oneDNN 对照。完整用例、计时范围和结果可在[算子评测数据](https://gitee.com/dongshan-community/triton-weft-bench/tree/main/docs/paper)中查阅。

TileLang–Weft 也完成了四个平台的 553 项源码 JIT 与数值检查。在 543 项有外部参考的比较中，468 项快于参考实现；与对应 Triton 实现使用同一批输入交替测量时，全部 553 项的 TileLang 原生耗时均不超过 Triton 耗时的 1.03 倍。这组逐项测试验证了两个前端共用 CPU 编译核心后的执行效果，结果见 [TileLang–Weft Bench](https://gitee.com/dongshan-community/tilelang-weft-bench)。

**模型推理**

应用层面的评测将 Triton–Weft 生成的算子接入 llama.cpp，覆盖 Llama 2、DeepSeek 和 Qwen 2.5 等模型，在 RISC-V 与 x86 上测试输入处理（prefill）和逐 token 生成（decode）两个阶段，结果如图 4 所示。

![](https://picx.zhimg.com/v2-756260d511b5350d00039950addb9afb_r.jpg)

*图 4 Triton–Weft 接入 llama.cpp 后的推理性能。蓝色柱表示 prefill，灰色斜线柱表示 decode；K3 分别列出以 CPU 向量实现和厂商 IME2 实现为参考的结果。*

在 8 组模型—平台部署中，prefill 的加速比几何平均为 **1.27×**，decode 为 **1.14×**；汇总时，K3 采用厂商 IME2 实现作为参考。例如，K1 上 Llama 2 7B 的 prefill 达到 1.43×；K3 上 DeepSeek 8B 相对 IME2 参考实现的 decode 达到 1.36×。

这部分测试采用多线程完整推理阶段计时，包含框架调度和相关准备工作，展示了算子接入模型后的实际收益。不同模型、阶段和平台的收益幅度有所差异，具体配置与结果见[应用评测数据](https://gitee.com/dongshan-community/triton-weft-bench/blob/main/docs/paper/applications.csv)。
