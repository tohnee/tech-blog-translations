## 一、引子：同一场显存危机，两套解法

2023 年是 LLM 推理引擎的"分水岭之年"。这一年，两个系统几乎同时登场，各自解决了一个让所有人头疼的问题：

- **vLLM** 在 SOSP 2023 发表了 **PagedAttention**，把操作系统的虚拟内存分页思想搬进了 KV Cache，解决了**显存碎片化**；
- **SGLang** 随后在 NeurIPS 2024 发表了 **RadixAttention**，用一棵基数树缓存所有请求的 KV Cache，解决了**前缀重复计算**。

很多人把这两项技术当成"同类竞品"，问"该用哪个"。但如果你仔细读过两篇论文就会发现：**它们解决的根本不是同一个问题**——一个是物理内存怎么放（空间维度），一个是历史算力怎么复用（时间维度）。今天这篇文章，我们就来把这两项技术彻底拆开、对比、融合，并用一个迷你模拟器验证它们各自的价值。

一句话预告结论：**PagedAttention 管"显存怎么放"，RadixAttention 管"前缀怎么复用"。现代推理引擎（vLLM、SGLang）最终都同时装上了这两样东西。**

## 二、背景：KV Cache 的三大特性

要理解这两项技术，先要理解它们共同的战场——KV Cache。

Transformer 自回归解码时，每个 token 都要和之前所有 token 的 Key/Value 向量做注意力计算。为了不重复计算，引擎把这些 K/V 张量缓存在显存里，这就是 KV Cache。它有三个致命特性：

**特性一：巨大。** 以 OPT-13B 为例，单个 token 的 KV Cache 需要 800KB 显存（2 份 K/V × 5120 隐藏维度 × 40 层 × FP16 2 字节）。一个 2048 token 的序列，KV Cache 高达 **1.6GB**。论文实测在 A100 40GB 上跑 13B 模型，模型权重占约 65%，KV Cache 占约 **30%**，剩余才是激活值等临时数据。换句话说，**决定你能同时跑多少个请求的，不是算力，而是 KV Cache 显存**。

**特性二：动态增长。** 解码是逐 token 进行的，KV Cache 每步追加一块，最终长度在请求完成前**不可预知**。这给内存分配出了个大难题。

**特性三：前缀可复用。** 这是最容易被忽视的一点：**同一个 token 序列在不同请求里，其 KV Cache 完全一样**。因为 KV Cache 只依赖于它之前的所有 token。这意味着——如果两个请求共享一段前缀，这段前缀的 KV 根本不需要算第二遍。

三大特性，催生了两大问题：**显存碎片化（特性一+二）**和**前缀重复计算（特性三）**。PagedAttention 和 RadixAttention 各领一道。

## 三、问题一：显存碎片化，传统系统只能用到两成

在 PagedAttention 之前，主流 serving 系统（FasterTransformer、Orca 等）怎么管理 KV Cache？

答案是**连续预分配**：每个请求到达时，按"最大可能序列长度"（比如 2048 token）一次性预留一块连续显存。由于深度学习框架要求张量连续存储，这是最自然的做法。但 KV Cache 的"动态增长 + 长度未知"特性，让这种方案产生了**三种纯浪费**：

- **预留浪费**：为未来 token 预留的空间，在请求整个生命周期内其他请求都不能用；
- **内部碎片**：请求实际只生成了 100 token，却占着 2048 token 的坑；
- **外部碎片**：不同请求预留不同大小，内存分配器（buddy allocator 等）对不齐产生的空洞。

论文实测结果触目惊心：传统系统里，**KV Cache 显存的实际利用率只有 20.4% ~ 38.2%**——近三分之二的显存被浪费了。这意味着同样一块 GPU，本可以多塞 2-4 倍的请求。

有人会说：那预分配小一点不就行了？不行——**你不知道输出有多长**。预分配短了，长输出请求会直接失败；预分配长了，就是浪费。这是个无解的两难。

vLLM 的解法是：**干脆不连续了**。

## 四、PagedAttention：把虚拟内存搬进 KV Cache

### 4.1 核心思想：逻辑块与物理块

PagedAttention 的灵感直接来自操作系统的虚拟内存：OS 把进程的地址空间切成固定大小的页，逻辑连续的页可以映射到物理上不连续的内存，按需分配、缺页再补。

![](https://pica.zhimg.com/v2-81dd249b2134ee00b168838cd31ae100_r.jpg)

PagedAttention 如法炮制：

- **KV Block**：把 KV Cache 切成固定大小的块（如 16 token 一个块）；
- **逻辑块**：每个序列的逻辑 KV 块，按 token 顺序排列（逻辑连续）；
- **物理块**：GPU 显存里的实际存储单元，可以任意不连续；
- **块表（Block Table）**：每个请求一张映射表，记录"逻辑块 N → 物理块 M，已填充 X 个位置"。

注意力计算时，kernel 按块表逐个取物理块做 block-wise attention，物理上分散完全无所谓。

这一招直接消灭了前两种碎片：**按需分配**让"预留浪费"消失（用到哪分配到哪）；**固定块大小**让"外部碎片"消失（所有块一样大）；唯一剩下的浪费是**最后一个块没填满的空槽**，最多 16 token，利用率直接拉到 ~99%。

### 4.2 块级共享：Parallel Sampling 与 Beam Search

分页带来的第二个红利是**共享**。物理块可以被多个序列同时映射——只要它们的逻辑块内容相同。

![](https://pic1.zhimg.com/v2-7e492d9f58786092870be7f20ff8a76e_r.jpg)

**Parallel Sampling**（一个 prompt 采样 N 个输出）是最典型的场景：N 个采样分支共享整个 prompt 的物理块（引用计数 = N）。当某个分支要往"共享的最后一个块"写入新 token 时，触发 **Copy-on-Write**：复制一块给自己，再写。共享的代价从"整个 prompt 的显存"变成"每分支一块的复制"。

**Beam Search** 更精彩：beam 候选之间不仅共享 prompt，还能共享生成过程中的中间块——共享树随剪枝动态变化，像 OS 里 fork 出来的进程树。refcount 归零的物理块立即释放。论文实测：parallel sampling 节省 6.1% ~ 30.5%，beam search 节省 **37.6% ~ 66.3%**（prompt 越长、beam 越宽，省得越多）。

### 4.3 内存耗尽怎么办：抢占、交换与重算

显存是硬约束，请求多了总会耗尽。vLLM 的处理是**序列级抢占**（all-or-nothing）：被抢占序列的所有块要么全驱逐、要么全保留。恢复方式有两种：

- **交换（Swap）**：把被抢占序列的 KV 块拷到 CPU 内存（类比 OS 的 swap），腾出显存后换回；
- **重算（Recompute）**：等被抢占序列重新调度时，把已生成 token 拼进 prompt 一次性重新 prefill（因为 KV 计算是确定性的，重算结果完全一致）。

FCFS 调度保证公平不饿死。这套机制让 vLLM 在**任何流量下都不会 OOM**——这一点对生产系统至关重要。

**PagedAttention 小结**：它解决的是"**空间**"问题——让同样一块 GPU 装下更多请求。vLLM 论文实测吞吐比 FasterTransformer/Orca 高 **2-4 倍**，且序列越长、模型越大、解码算法越复杂，优势越明显。

但注意：**PagedAttention 自己并不做跨请求的缓存复用**。共享前缀？vLLM 论文里也有，但那是"服务方手动预留物理块"的预定义前缀，需要人工介入。真正的自动复用，是 RadixAttention 的事。

## 五、问题二：前缀重复计算，算力被白白烧掉

2023 年的另一个趋势是 **multi-call LLM 程序**：agent 控制、RAG 检索、few-shot 评测、JSON 结构化输出、多轮对话……一个程序里要发起**多次**生成调用，且这些调用之间**大量共享前缀**：

- **多轮对话**：第 N 轮请求 = 系统提示词 + 全部历史 + 新问题，其中 90%+ 的 token 和前一轮一模一样；
- **few-shot / 系统提示词**：所有请求共享同一段长指令；
- **agent 多路径 / Tree-of-Thought**：多个分支共享同一个思考前缀；
- **RAG**：长文档被不同问题反复查询。

传统 serving 系统怎么处理？**每次调用都从零开始 prefill**。同一个 2000 token 的系统提示词，1000 个请求就白算 200 万 token 的注意力。vLLM 论文自己也承认：多轮对话场景为了不占显存，**故意不存跨轮 KV**——因为"存了会挤占其他请求的空间"。

这就是 RadixAttention 的切入点：既然 KV Cache 是确定性的，**为什么算过一遍的结果要扔掉？**

## 六、RadixAttention：用基数树索引历史

### 6.1 核心思想：树形缓存，自动复用

SGLang 的答案是一棵**基数树（Radix Tree）**：

- **Key** = token 序列（节点存变长 token 段，天然前缀压缩）；
- **Value** = 该段对应的 KV Cache 张量（存在非连续分页池里，页大小 = 1 token）；
- 请求完成后 KV **不丢弃**，插入树中；
- 新请求到达，**match_prefix** 沿树逐段匹配最长共享前缀，命中的 KV 直接复用，**只 prefill 剩余部分**。

![](https://pica.zhimg.com/v2-fe1bb2ca44ebc421a17ea9ff0f7e025a_r.jpg)

与普通 trie 不同，radix tree 的边可以携带**变长**的 token 段（"The cat" 是一个节点而不是 7 个），这让树的维护开销极低——论文实测：128 个请求的树操作只要 0.07 秒（对比前向 17.6 秒），零命中场景下树维护开销仅 **0.5%**。

### 6.2 三个核心操作：匹配、分裂、插入

- **match_prefix**：从根开始逐段比较。若一段只命中一半（新请求是 "The cat sat" 而树里是 "The cat"），就 **分裂节点**——"The cat" 留在原地，"sat" 成为子节点；
- **insert**：请求完成后，把未命中部分作为新节点挂到树里；
- **evict**：显存不够时 **LRU 驱逐叶子节点**——只删叶子（内部节点可能被其他请求共享），且 **lock_ref=0** 的节点才可驱逐（正在运行的 batch 引用的节点被锁住），驱逐后父节点可能变成新叶子，递归评估。

### 6.3 Cache-Aware 调度：让命中率最大化

光有树还不够——**调度策略决定命中率**。如果按 FCFS 乱序调度，请求在树的不同子树间来回切换，缓存刚建好就被挤掉（缓存抖动）。SGLang 的做法是 **cache-aware scheduling**：每个请求到达先 match_prefix，然后**按命中前缀长度排序**，命中长的优先进 batch。同类前缀的请求聚在一起，batch 内部共享计算。

![](https://pic1.zhimg.com/v2-8277af3149bbb2545612dcd274c71748_r.jpg)

论文消融实验证实：LMP（Longest Matching Prefix）策略显著优于 Random 和 FCFS；SGLang 生产版本里，cache-aware router 把前缀命中率从 20% 拉到 75%，吞吐从 82.7K 提到 158.6K token/s。

### 6.4 extend kernel：没有它就不成立

复用 KV 需要新的 CUDA kernel：标准的 prefill kernel 假设 query/key 长度相等，decode kernel 假设 query 长度=1，都处理不了"一部分 KV 来自缓存、一部分是新算的"场景。SGLang 为此写了 **extend kernel**：能同时从**连续 buffer**（新算的）和**非连续分页池**（缓存的）读取 KV，融合计算，**零拷贝开销**。消融实验里关掉 extend kernel，长上下文任务性能明显劣化。

**RadixAttention 小结**：它解决的是"**时间**"问题——让算过一遍的 KV 能被反复利用。SGLang 论文在多类 multi-call 任务（agent 控制、逻辑推理、JSON 解码、RAG、多轮对话）上实测最高 **6.4 倍**吞吐提升。

## 七、殊途同归：现代引擎的两层架构

到这里，两项技术的关系应该很清楚了：**它们正交，且互相需要**。

RadixAttention 的 KV 存哪里？——**非连续分页池**（论文明说"compatible with existing techniques like continuous batching and paged attention"）。也就是说，RadixAttention 建立在分页内存管理之上，树的 value 就是分页池里的物理块索引。**没有分页池，前缀树复用就无从谈起**。

反过来，vLLM 后来也补上了自动前缀复用：**Automatic Prefix Caching（APC）**。vLLM 的 AP C 实现是 hash-based：每个 KV 块计算 `hash(父块哈希 + 块内 token + 额外哈希)`，块哈希相同即可复用。v0.11 起默认 sha256 消除冲突风险，支持 cache_salt 做多租户隔离，只缓存完整块。官方文档甚至直言这个思路来自 SGLang 等框架。

所以今天的生产引擎是这样的：

- **vLLM** = PagedAttention 分页 + APC 哈希前缀缓存；
- **SGLang** = 分页内存池 + RadixAttention 前缀树 + cache-aware 调度。

两者实现路径不同（哈希块表 vs 变长段树），但**殊途同归**：分页解决空间，前缀缓存解决时间，缺一不可。

## 九、代码验证：V1-V4 迷你模拟器

理论说得再多，不如跑起来看数字。我写了一个四阶段的迷你模拟器（纯 Python，无 GPU 依赖，代码在 `~/.hermes/output/radix-vs-paged/code/`），每一步对应论文里的一个核心机制，全部实际运行验证。

### V1：碎片化模拟——分页 vs 连续预分配

模拟 32 个长短不一的请求（prompt 100-800 token，输出 20-800 token，最大序列 2048），对比两种分配策略：

```text
策略                    预留空间        实际使用       利用率
------------------------------------------------
A 连续预分配           65,536      26,260     40.1%
B 分页按需            26,448      26,260     99.3%
------------------------------------------------
结论: 连续预分配利用率 40.1%  (论文实测传统系统仅 20.4%-38.2%)
      分页按需利用率 99.3%, 碎片从 '整个预留区间' 缩小到 '最后一个块'
      同等显存下分页可容纳的请求数约为连续方案的 2.5x
```

### V2：块表 + Copy-on-Write 模拟

模拟 parallel sampling（4 路采样共享 512-token prompt）和 beam search（beam=4，8 步扩展）：

```text
  无共享方案所需块数: 192
  分页共享实际分配块数: 100
  节省: 92 块 = 47.9%  (提示词部分 67% 被 4 路共享)

  朴素实现(每候选独立存全部块)约需: 384 块
```


### V4：双引擎对比——分页 vs 分页 + RadixAttention

同一份混合请求流（8 few-shot 共享系统提示词 + 6 多轮对话 + 8 独立请求，共 5965 token 输入），跑两个引擎：

```text
指标                               引擎A (仅分页)      引擎B (+Radix)
------------------------------------------------------------
prefill token 总量                 5,965             2,020
前缀命中 token                               -             3,945
KV 峰值占用                          2,820             3,000
所需 batch 数                               3                 3
batch 大小序列                             [6, 7, 9]        [9, 11, 2]
------------------------------------------------------------
结论:
  1. prefill 计算量: B 比 A 少 2.95x (命中 66% 的输入 token)
  2. B 的 KV 峰值 3000 = 容量上限: 命中部分从树里读,
     不重复计算也不重复占运行显存
  3. 引擎 A 的 '分页' 解决碎片化; 引擎 B 叠加的 'radix tree'
     解决重复 prefill —— 两者叠加 = 现代推理引擎的标准配置
```

注意 V4 里的一个细节：引擎 B 的 KV 峰值 3000 = 容量上限，说明**缓存是要付显存代价的**——这正是 RadixAttention 用 LRU 驱逐控制缓存大小的原因。但用 3000 token 的显存缓存，换来了 2.95 倍的 prefill 算力节省，这笔账非常划算。

## 十、总结与学习路径

**一句话总结**：PagedAttention 和 RadixAttention 不是竞品，而是 LLM 推理引擎的两层地基——PagedAttention 用分页消灭显存碎片（空间维度），RadixAttention 用基数树消灭重复计算（时间维度）。今天的 vLLM 和 SGLang 都把两者装进了同一个引擎。

**它们各自适合谁？**

- 如果只有**单次调用、请求彼此独立**（简单 chat 服务、批量打分）——PagedAttention 的分页已足够，RadixAttention 收益有限；
- 如果是**multi-call 场景**（agent、RAG、多轮对话、few-shot 评测、JSON 结构化输出）——前缀缓存是决定吞吐的关键，RadixAttention（或 vLLM 的 APC）必须有。

**动手学习路径**：

- **论文**：先读 PagedAttention（arXiv:2309.06180，SOSP'23），重点 §3 的碎片化分析和 §4 的块表机制；再读 SGLang（arXiv:2312.07104，NeurIPS'24），重点 §5 的 RadixAttention 和 Algorithm 1 的 cache-aware 调度；
- **源码**：vLLM 的 `block_manager` 与 `prefix_caching`；SGLang 的 `python/sglang/srt/mem_cache/radix_cache.py`（600 行左右，核心是 match_prefix / insert / evict 三个方法）；
- **复现**：用本文的 V1-V4 模拟器（纯 Python）把碎片化、COW、前缀树、双引擎对比各跑一遍，改改参数看数字怎么变；
- **生产验证**：用 `vllm serve --enable-prefix-caching` 和 `python -m sglang.launch_server` 各起一个服务，用长文档问答和多轮对话的 trace 打流量，对比 prefill 耗时和首 token 延迟。
