### 1 Paged KV Cache

Paged KV Cache 这种 KV 管理模式能够更高效的利用 GPU 显存资源，减少外部碎片。参考 vllm 的实现原理，对于单一的文本模态模型，例如 Qwen3，会将 prompt 切分为多个 chunk (例如 16 tokens)，每个 chunk 所需显存大小都是固定的，大小为 $layers\_num \times chunk\_size \times kv\_size\_per\_token$。推理系统事先根据一块 chunk 的大小将 GPU Memory 一整块切分为多个 连续的 page，之后按需将 page 分给序列长度确定的 prefill 阶段和序列长度增长的 decode 阶段。整体思路类似于 OS 的内存分页，参考论文 [PagedAttention](https://arxiv.org/abs/2309.06180)。

![](https://pic2.zhimg.com/v2-cd58347f8987facffd6afdb4d26723c1_r.jpg)
*图1 KV Cache 示意图*

如图一，模型有很多个注意力层，**在处理一条序列时**，每一层都会产生 KV Cache，并且每一层的 KV Cache 大小都一样。GPU Memory 会按照 page 的大小切分为很多个小块，按 Attention Layer 平均分这些 page。在管理 KV Cache 时，由于每一层的行为都一样，只需要根据 pages 的总数 $q$ 来维护 pages 的空闲队列，占用队列等。对于 $Page (i, j)$，只需要管理表示实际块位置的 $j$ 坐标即可，$i$ 所代表的层的行为都一致。

### 2 单文本模态下的 prefix cache

在有了显存分页管理之后，那么请求到来时如何判断当前请求的 KV Cache 已经计算过？已知 LLM 是关于输入的函数，即模型的内部隐藏状态（包括 KV Cache）都是是输入 token 序列的函数，在不考虑数值精度的影响，相同的输入 token 序列计算出来的模型隐藏状态 tensor 一定一样。假定有两条 token 序列 $seq_i$ 和 $seq_{j}$，状态如公式 (1)

$$ state_{i} = f(seq_{i}), \ \ \ state_{j} = f(seq_{j}) \tag{1} $$

假如前 $t$ 个 token 都相同，即

$$ state_{i}^{(0...t)} = f(seq_{i}^{(0...t)}), \ \ \ state_{j}^{(0...t)} = f(seq_{j}^{(0...t)}), \ \ \ seq_{i}^{(0...t)} = seq_{j}^{(0...t)} \\ \Rightarrow state_{i}^{(0...t)} = state_{j}^{(0...t)} \tag{2} $$

因此，只要两条 $seq$ 有相同前缀，就可以复用另一条 $seq$ 前缀对应的那一部分 KV Cache。

但是在 Paged KV Cache 的设计下，token 序列是按照 chunk 切分的，也就是相同的前缀会被切分为多个块。在上一条序列 $seq_{i}$ 在处理完成之后，它的 KV Cache 会按照 chunk 切分保存在 page 上。下一条序列 $seq_{j}$ 到来之后，需要对 $seq_{j}$ 和 $seq_{i}$ 进行字符串匹配。但是对于一个大型的模型服务系统，会有难以估量的模型请求，$seq_{j}$ 将要和所有的序列计算最长前缀，这是一个巨大的 CPU 侧开销，因此采用字符串前缀匹配的方式不可行。

每一个 chunk 都会唯一对应一个 $Page(i,j)^{i=0...n}$，可以使用哈希将这部分 chunk 的 token ids 映射到一个唯一的 hash id，通过这个 hash id 来判断当前 chunk 的 KV Cache 是否可复用。在处理新请求 $seq_{j}$ 时，只需要计算 $seq_{j}$ 每个 chunk 的 hash id，然后在 page 池中匹配。这里有一个可能忽略的点，$state$ 是前缀的函数，但是位于中间的 chunk 确实了前缀信息，所以在计算 hash id 时，采用一种**链式方法**，在 chunk 的 hash 算法的输入中即要有当前 chunk 的 token id 序列还要有前一个 chunk 的 hash id，如图 2。

### 3 多模态下的 KV Cache 问题

- 多模态的 token id

在多模态场景下，模型的输入是文字和图片（简化讨论，多模态还有视频和音频等等），图片是没有 token id 的，而经过 chat template 处理之后的 token_ids，会使用 special token，例如 `<|image_pad|>` 的 token id 作为占位 token 去替代原本图片没有的 token 序列 。所以会出现如下这种情况

```text
chunk1: [13, 14, 15, 24572, 16, 24572, 24572]
chunk2: [24572, 24572, 24572, 24572, 24572, 24572, 24572]
chunk3: [24572, 24572, 24572, 29, 31, 32, 32]
```

- 多模态输入处理流程

*图3 多模态 embeddings*

既然多模态输入没有 token id，就不能使用 nn.embedding 模块获得多模态部分的 embeddings。如图三，多模态模型具备 Vision Tower，多模态输入先要通过 Vision Tower 处理得到 vision embeddings，vision embeddings 通过 scatter 操作将拷贝到 token embeddings 预留出来的位置，最后按照传统文本模型做前向推理。

- 多模态推理分析

从图三可以看到，多模态过程多了视觉塔处理的输出 vision embeddings，并且这部分的计算量是远比 nn.embedding 的 token 映射大得多，vision embeddings 还是独立计算的，没有前缀要求，所以 **vision embeddings 有缓存价值，是否缓存这部分 tensor 在系统设计时是一个不可忽略的 trade off**。同时 vision embeddings 的位置也会产生 KV Cache，这部分 KV Cache 和文本 token 的 KV Cache 处于同一个缓存级别，和原来的单一文本模态的缓存设计是兼容的。

但是由于 image 占位 token 的原因，通过图片可以确定它需要多少占位 token（如图四），但是仅通过占位 token 不能确定到底是哪一张图片，所以 chunk 的识别策略需要改进。

### 4 多模态缓存命中

原本的单一文本模态给每个 chunk 标识一个唯一的 hash id，同理，加了图片模态后，就需要将图片信息带到 hash id 里面，让含有占位 id 的 chunk 在计算 hash id 时包含图片信息。

### 4.1 分析多模态 chunk 的 hash

- 唯一确定一张图片

对于一张 RGB 图，如果任何一个像素的值发生变化，这就是另一张图，像素值和图片的字节化序列是一一对应的，通过对图片的字节流应用 hash 就能得到图片的唯一 ID，类似如下代码。

```python
import hashlib
from pathlib import Path

LEN = 8  # 长度用 8 字节小端

def _put(h, chunk: bytes) -> None:
    h.update(len(chunk).to_bytes(LEN, "little"))
    h.update(chunk)

def _raw(value) -> bytes:
    return value if isinstance(value, bytes) else str(value).encode("utf-8")

def image_hash(image: bytes, **params) -> str:
    h = hashlib.sha256()
    fields = {"image": image, **params}

    for name in sorted(fields):      # 排序 → 与书写顺序无关
        _put(h, name.encode())       # 字段名
        _put(h, _raw(fields[name]))  # 字段值

    return h.hexdigest()

if __name__ == "__main__":
    path = Path(__file__).with_name("test.png")
    raw = path.read_bytes()
    base = image_hash(raw, max_pixels=1024)
```

- 唯一确定一个 chunk（或者 KV Page）

现在考虑在 chunk 的 token id 相同的情况下，图片的哪些行为会影响到 chunk 的 hash 值。由于 chunk 是前缀匹配，如果前面的 chunk 就匹配不上，那么当前 chunk 肯定也不匹配，没有讨论意义，所以在讨论当前 chunk 时，假设之前的 chunk 都能匹配。

a. chunk 内部没有 image 占位 token. 因为没有占位 token，所以这个 chunk 的 hash 不需要加入图片信息

b. chunk 内部全部都是 image 占位 token. 此时，仅通过 chunk 的 token ids 不能唯一确定当前 chunk，需要把图片信息加入到 hash 里面。

c. chunk 内部既有既有文本 token 和占位 token. 还是需要通过 chunk 内部的 token hash 和图片信息一起计算最终 hash，如图五。

![](https://picx.zhimg.com/v2-10cc880e2f568ac3c068e425d218624f_r.jpg)
*图5 含有 image pad 的示意图*

d. chunk 内部有多个图片的占位块. 此时，图片的占位块之间还有相对位置顺序，如图六，这种情况下，计算 hash 需要考虑图片的位置顺序。

![](https://pica.zhimg.com/v2-1e099f0e639665f167063a03a935c068_r.jpg)
*图6 含有多个 image pad 的示意图*

> 综上，要唯一确定一个 chunk，不仅需要考虑当前 chunk 的内容，还要考虑图片信息及其相对位置。

### 4.2 命中算法具体实现

这里介绍 vLLM 和 SGLang 的实现，具备代表性。

- vLLM 的实现

vLLM 先计算图片的 hash 值，并且会计算这个图片的占位符的起始地址相对于当前 chunk 的位置，得到一个 mm 元组列表 $[(image\_hash_{0}, offset_{0}), (image\_hash_{1}, offset_{1}), ...]$，这个 mm 元组列表根据模版化的图片占位块的顺序排列。之后将前缀 hash ，本块 ids，mm 一起字节化计算 hash。

```python
def hash_block_tokens(hash_function, parent_block_hash, curr_block_token_ids, extra_keys=None):
    if not parent_block_hash:
        parent_block_hash = NONE_HASH

    curr_block_token_ids_tuple = tuple(curr_block_token_ids)
    return BlockHash(
        sha256((parent_block_hash, curr_block_token_ids_tuple, extra_keys))
    )
    
def sha256(input):
    return hashlib.sha256(pickle.dumps(input, protocol=5)).digest()
```

- SGLang 的实现

SGLang 的实现更巧妙简单，SGLang 将图片 hash 通过移位等操作，将图片 hash 前 8 字节压缩到了 token id 一样的整数大小，使用这个压缩后的整数替换 tokenizer 之后的 token id list 中的占位 token，从而可以使用文本模态的那一套 hash 算法。
