### 开篇：为什么”跑通一次”不算交付

一个模型在笔记本上跑出 92 分，离上线通常还差八件事：

```text
跑通一次 ≠ 能交付
    │
    ▼
数据换了怎么办？         → ① 数据版本管理
特征线上不一致怎么办？    → ② 特征工程
谁在什么时候重跑？       → ③ 训练编排
参数哪组最好？           → ④ 实验追踪
谁批准上线？             → ⑤ 模型注册
怎么发、怎么回滚？       → ⑥ 部署
怎么知道坏了？           → ⑦ 监控
效果掉了要不要重训？     → ⑧ 自动重训
```

**开篇一句话**：**MLOps 不是工具清单，而是把”人肉流程”变成”可重复、可追溯、可回滚”的工程纪律。**

> **与 2.x 的边界**：2.4 管”一个模型的生老病死”，3.1 管”**这条流水线怎么自动转起来**“——注册表是节点，流水线是把节点串起来的轨道。

---

### 一、先建立整体认知：流水线的六个阶段

```text
┌──────────────────────────────────────────────────────────────────┐
│  数据 → 特征 → 训练 → 注册 → 部署 → 监控                         │
│   ↑                                              │              │
│   └──────────── ⑧ 自动重训 ← ⑦ 监控发现漂移 ←───┘              │
└──────────────────────────────────────────────────────────────────┘
       ①        ②      ③④      ⑤      ⑥      ⑦
```

**关键认知**：这是一条**闭环**，不是一条直线。监控发现问题，触发重训，回到起点——**“闭环”才是 MLOps 与一次性脚本的根本区别**。

### 二、① 数据版本管理：数据变了，谁知道？

**核心问题**：代码有 Git，数据没有——**数据是模型的第一成因，却最常被忽视**。

### 1.1 这里的”数据”具体指什么

大模型流水线里的”数据”不是一份 Excel，而是**五类资产的集合**：

| 类型 | 具体是什么 | 要不要版本化 |
| --- | --- | --- |
| 训练 / 微调数据 | SFT 问答对、偏好排序对、领域语料 | ✅ 必须 |
| 评测数据集 | 黄金测试集、对抗样本集、回归集 | ✅ 必须 |
| 输出数据（最常被忽略） | Teacher 蒸馏生成的答案、历史对话日志 | ✅ 必须 |
| 配置与元数据 | 超参、数据清单、Prompt 模板、模型卡 | ✅ 必须 |
| 生成物 | 模型权重文件本身 | ⚠️ 只存指针，不存副本 |

> **关键判断**：**要版本化的是”指向权重的指针 + 哈希”，不是权重本身**。一个 7B 模型约 14 GB，存十份就是 140 GB，纯属浪费——这和 2.2 算的那笔显存账是同一逻辑。

### 1.2 为什么数据必须版本化

| 没有版本管理 | 有版本管理 |
| --- | --- |
| “上周还能跑，这周不行了”查不出原因 | 能定位到哪天、哪批数据变了 |
| 无法复现历史实验 | 任何历史结果都能重跑 |
| 数据被覆盖，无法回退 | 哈希寻址，天然不可变 |

### 1.3 LakeFS、Git-LFS、对象存储分别是什么

三者**不是替代品，而是分工协作的一层栈**——很多团队踩坑是因为拿其中一个去干另外两个的活：

```text
对象存储（S3 / COS / OSS / MinIO）
    ↑ 真正存放几百 GB 的文件
Git-LFS
    ↑ 把大文件换成 2KB 的指针，仓库不再膨胀
Git
    ↑ 管代码 + 指针的提交历史
LakeFS
    ↑ 在对象存储之上加"分支 / 合并 / 回滚"，把硬盘柜变成 Git
```

**对象存储：硬盘柜** 本质是”按量付费的无限硬盘”，只管存文件和算账单，**不知道”哪个版本”**。它能告诉你文件在，但回答不了”这批数据改了哪三行”。适合存权重、原始语料、日志等胖文件。

**Git-LFS（Large File Storage）：胖子的指针** Git 天生不擅长大文件——往仓库里塞几个 2 GB 文件，克隆就会卡死。Git-LFS 的解法是：**仓库里只留一个 2 KB 的指针文件，真正的内容存在 LFS 服务器，checkout 时才按需拉取**。你照常用 `git clone`、`git checkout`，体感不变。

**LakeFS：给对象存储装上 Git 的脑子** 它在对象存储之上实现一个**兼容 S3 协议的分支管理层**，提供 branch / merge / diff / revert / commit。核心价值是三点：

- **分支隔离**：数据团队和算法团队可以各自开分支改同一批语料，互不影响，改完合并
- **可回滚**：一次 merge 就是一个版本，`revert` 即可回到上周的数据状态
- **能 diff**：可以回答”这次上线相对上次，删了 127 条、改了 43 条、新增 2100 条”

**怎么配合（这是最常见的落地组合）**：

- 权重、原始语料、Teacher 输出 → **对象存储**
- 对象存储里文件的”哪个版本”这一层 → **LakeFS**
- 小配置文件、Prompt 模板、数据清单 → **Git-LFS**（或直接进 Git）
- 代码、指针、提交历史 → **Git**

**选型建议**：小团队用 **对象存储 + Git-LFS**，零运维、够用；数据规模上 TB 级或多团队并行改同一份数据 → 上 LakeFS。

### 1.4 数据版本化的三个落地动作

1. **每个数据集给一个哈希 ID**，在数据卡上写明，训练脚本引用 ID 而非路径
2. **数据变更要走 PR**：谁改的、为什么改、影响哪些模型，必须留痕
3. **保留”黄金数据集”**：一个永远不删、用于回归对比的基准集

### 1.5 数据质量门禁：坏数据进流水线，出来的是坏模型

版本化只解决”能不能回退”，不解决”数据对不对”。提交数据时要自动过四道检查：

| 检查项 | 查什么 | 不通过的典型信号 |
| --- | --- | --- |
| 格式校验 | 字段缺失、JSON 是否可解析、问答是否成对 | 空答案、截断的 JSON |
| 去重 | 与训练集、评测集的重复率 | 评测集里出现训练样本 → 分数虚高 |
| 敏感信息检测 | 手机号、身份证、密钥、内部 IP | 训练完的模型能背出员工手机号 |
| 领域覆盖度 | 各业务场景的样例数分布 | 90% 是 A 场景，B 场景只有 3 条 |

> **承接 2.3**：去重和领域覆盖度直接决定评测分数可不可信——数据漏了，评测再严谨也是假精准。

### 1.6 数据集拆分规范：三份必须物理隔离

```text
全部数据
  ├─ 训练集（Dev）     80%  用来训练，可以反复改
  ├─ 评测集            10%  决定能不能上线，任何人不得改
  └─ 线上回流集        10%  真实用户反馈，只追加不修改
```

**铁律：三份必须物理隔离，不能靠”约定”分开。** 评测集一旦被拿去训练，2.3 里的所有分数立刻失去意义。

> **反直觉结论**：**数据版本管理比代码版本管理更重要**——代码回滚秒级，数据回滚可能意味着重新采集标注。

### 三、② 特征工程：线上线下一致吗？

**核心问题**：训练时算出来的特征，线上推理时能不能算出**一模一样**的值？

### 2.1 大模型时代，特征工程变了吗？

> **没有消失，只是换了形态。**

| 传统 ML | 大模型时代 |
| --- | --- |
| 人工构造数值特征 | 构造上下文（RAG 检索质量、Prompt 模板、工具定义） |
| 特征筛选 | 检索片段筛选、上下文裁剪 |
| 特征存储 | 知识库版本管理 |

### 2.2 训练-服务偏差（Training-Serving Skew）

这是特征工程在大模型场景下的**头号杀手**：

```text
训练时：系统提示 + 检索到的 3 条片段 + 用户问题   → 模型学会"依赖这 3 条"
服务时：检索到 5 条，或 0 条                     → 模型行为漂移
```

**对策**：

1. 特征（上下文）构建逻辑**只写一份**，训练和服务共用同一套代码
2. 服务时记录”实际喂给了模型什么”，与训练分布对比
3. 对 RAG 场景，**把检索命中率、片段数、相似度分位数纳入监控**

### 四、③ 训练编排：谁在什么时候跑？

**核心问题**：训练任务不该靠人手动触发——**谁、在什么条件下、用哪份数据、跑多久，都要可编程**。

### 3.1 三种编排方式

| 方式 | 适用 | 特点 |
| --- | --- | --- |
| 定时任务（Cron / Airflow） | 规则明确、周期固定 | 简单可靠 |
| 事件触发（数据更新 / 漂移超标） | 响应式 | 与 ⑧ 自动重训衔接 |
| 手动审批 + 自动化执行 | 生产环境 | 人审机器跑，兼顾安全与效率 |

### 3.2 一个训练任务必须声明哪些要素

一次训练任务至少要把下面几项写全，缺任何一项都是”不可复现”的起点：

| 要素 | 说明 |
| --- | --- |
| 任务名 | 含模型、场景、版本，如 qwen7b-customer-service-lora-v1.4 |
| 触发条件 | 数据版本变更 / 定时 / 手动审批 |
| 数据版本 | 引用哈希 ID，绝不写路径 |
| 基座模型 | 精确到版本号，不写”最新版” |
| 训练方法 | 全参微调或 LoRA（回扣 2.4 第四、五节） |
| 超参 | 学习率、LoRA r、训练轮数、batch size |
| 资源 | 几张卡、什么型号，决定成本（回扣 2.2） |
| 通知人 | 跑完、失败、超时报给谁 |

> **关键纪律**：**训练脚本、数据版本、超参、环境，全部进版本库**——任何一项靠”口头约定”，就是不可复现的起点。

### 五、④ 实验追踪：哪组参数最好？（本章重点）

**核心问题**：跑了 20 组参数，两周后还能说清哪组最好吗？

> **没有实验追踪的微调 = 玄学。** 这是 90% 团队的真实状态。

### 4.1 实验追踪记什么

```text
一次实验 = 代码版本 + 数据版本 + 超参 + 环境 + 指标 + 产出物
```

| 类别 | 具体内容 |
| --- | --- |
| 代码 | Git commit hash |
| 数据 | 数据集哈希 ID |
| 超参 | 学习率、batch size、LoRA r、训练轮数 |
| 环境 | 框架版本、CUDA / CANN、驱动 |
| 指标 | loss、评测分数、显存占用、耗时 |
| 产出物 | 模型权重、日志、评测报告 |

### 4.2 两大主流工具

| 工具 | 定位 | 适合 |
| --- | --- | --- |
| MLflow | 开源、轻量、自托管 | 中小团队、私有化部署 |
| Weights & Biases (W&B) | 商业、可视化强、协作好 | 团队协作、需要精细对比 |

### 4.3 最小可用工作流（以 MLflow 为例）

一次完整的追踪只需三步：

1. **启动追踪服务**：部署一个 MLflow Server（或 W&B 项目），拿到一个可访问的地址
2. **训练脚本里记四件事**：`log_param` 记超参（学习率、LoRA r）、`log_metric` 记指标（eval_score、loss）、`log_artifact` 保存权重与评测报告、`set_tag` 写清这次改了什么
3. **在界面上对比**：按实验名筛选、并排叠出多条曲线、点进某次实验看全部上下文

> **落地建议**：**先跑通”记录 + 对比”两件事**，别一上来就搞自动化调参——能说清”哪组最好”，就已经超过大多数团队。

### 4.4 三个必做动作

1. **每次实验必须命名**——`lora-r16-lr2e4-data-v3.2`，别用 `run_27`
2. **对比要并排**——好的追踪工具能叠出 20 条曲线的对比图，别用肉眼翻日志
3. **留下”为什么”**——在实验备注里写清这次改了什么、预期什么效果

> **落地建议**：**先跑通”记录 + 对比”两件事**，别一上来就搞自动化调参——能说清”哪组最好”，就已经超过大多数团队。

### 六、⑤ 模型注册：谁批准上线？

**核心问题**：实验里分数最高的模型，凭什么能上生产？

### 5.1 三阶段门禁

```text
实验模型 ──→ 候选模型 ──→ 生产模型
 (Staging)    (Candidate)   (Production)
   自动          人工评测       灰度验证
```

| 阶段 | 准入条件 | 谁负责 |
| --- | --- | --- |
| 实验 | 跑完、指标已记录 | 算法工程师 |
| 候选 | 通过 2.3 的评测体系 + 安全扫描 | 算法负责人 |
| 生产 | 灰度验证通过 + Owner 签字 | 业务 + 技术双签 |

### 5.2 与 2.4 的衔接

> 2.4 的”模型注册表”是**数据模型**（记什么）；本节”模型注册”是**流程**（怎么流转）。 实现上：注册表是 MLflow Model Registry / 自研系统，流转规则写在流水线里。

### 5.3 版本号纪律

沿用 2.4 的 SemVer 规则：

- **主版本**：架构/基座变更（破坏性）
- **次版本**：能力增强（新增技能）
- **修订号**：修复（数据/超参微调）

> **关键纪律**：**没有评测报告，不许进”候选”；没有灰度结果，不许进”生产”。**

### 七、⑥ 部署：怎么发、怎么回滚？

**核心问题**：模型怎么从”候选”变成”用户能用”，且出问题能秒级退回？

### 6.1 四步灰度（回扣 2.4 第十节）

```text
影子流量 → 内部白名单 → A/B 对照 → 全量
  1%        5%           10-20%      100%
```

### 6.2 回滚决策树（回扣 2.4 第十一节）

```text
监控告警 → 是模型问题？
  ├─ 是 → 路由切回上一版本（秒级）
  └─ 否 → 是数据/提示词问题？
       ├─ 是 → 回滚配置/提示词
       └─ 否 → 扩容或排查服务
```

### 6.3 部署必须自动化

一次部署要把四件事写死在流水线里，而不是靠人盯着：

| 要素 | 说明 |
| --- | --- |
| 发布策略 | 金丝雀（canary），按 1% → 5% → 20% → 100% 递进 |
| 每步自动检查 | P95 时延、错误率、评测通过率三项同时达标才放行 |
| 自动回滚 | 任一项不达标立即退回上一版本，不等人工判断 |
| 记录产物 | 这次发布对应哪个模型版本、哪份配置，必须留痕 |

> **关键纪律**：**回滚方案必须在部署前写好，而不是出问题后再想。**

### 八、⑦ 监控：怎么知道坏了？

**核心问题**：模型不会报错，只会”悄悄变差”——**监控是 MLOps 闭环的眼睛**。

### 7.1 四层监控

| 层级 | 监控什么 | 典型指标 | 发现什么 |
| --- | --- | --- | --- |
| ① 服务层 | 服务是否活着 | QPS、P95/P99 时延、错误率、GPU 利用率 | 容量问题 |
| ② 模型层 | 模型是否变差 | 置信度分布、拒答率、幻觉率、输出长度 | 模型退化 |
| ③ 数据层 | 输入是否漂移 | 输入长度分布、topic 分布、缺失率 | 数据漂移 |
| ④ 业务层 | 用户是否满意 | 转化率、人工介入率、投诉率 | 业务影响 |

### 7.2 三个必看指标

1. **P95 / P99 时延**（回扣 2.2）——均值掩盖长尾，用户感知的是最慢的那 5%
2. **幻觉率 / 拒答率**（回扣 2.3）——模型层核心健康度
3. **人工介入率**——业务层最终裁判

### 7.3 告警设计三原则

1. **告警要能行动**——”P99 超 3s”能触发扩容，”CPU 用了 60%“只是噪音
2. **分级告警**——P0（业务受损，立即）／P1（指标异常，当日）／P2（趋势变化，周会）
3. **告警要有人认领**——未处理的告警 = 没有告警

> **反直觉结论**：**最危险的模型不是报错那个，是”不报错但悄悄变差”那个**——所以它必须被监控，而不是靠人工抽查。

### 九、⑧ 自动重训：什么时候该重训？

**核心问题**：效果掉了，是修 bug 还是重训？谁来决定？

### 8.1 三种触发条件

| 触发 | 信号 | 动作 |
| --- | --- | --- |
| 数据漂移 | 输入分布显著变化 | 评估是否需要重训 |
| 效果衰减 | 线上指标连续下滑 | 启动重训流水线 |
| 周期重训 | 固定周期（如月度） | 预防性重训 + 对比 |

### 8.2 自动重训不等于全自动

```text
监控发现异常
   ↓
① 自动评估（跑评测集，对比当前 vs 候选）
   ↓
② 评估通过？──否──→ 人工介入，排查原因
   ↓ 是
③ 自动注册为候选
   ↓
④ 灰度验证（1% → 5% → 全量）
   ↓
⑤ 新模型优于旧模型？──否──→ 回滚，不发版
   ↓ 是
⑥ 切换生产，旧模型保留 7 天
```

> **关键纪律**：**自动重训必须有人审（评估门禁）**，否则会把”变差”自动发布出去——那不是自动化，是自动化灾难。

### 8.3 一个判断口诀

> **效果掉了先查三件事：数据变了吗？提示词改了吗？上游模型换了吗？** 三件都没变才考虑重训——**重训是最后手段，不是第一反应**。

### 十、横切关注点：贯穿全流程的四件事

### 10.1 可复现性（Reproducibility）

> **这是 MLOps 的终极目标：任何人，在任何机器，用同一份声明，能跑出同一个结果。**

三个必备：

- 代码版本 + 数据版本 + 环境版本，三者锁定
- 随机种子固定（能固定的地方都固定）
- 产出物（权重、日志、报告）全部归档

### 10.2 可观测性（Observability）

不只监控”是否活着”，还要能回答：

- 这次推理用了哪个模型、哪个版本？
- 输入来自哪个用户、哪个场景？
- 输出被人工修改了吗？为什么？

### 10.3 成本追踪（Cost Tracking）

回扣 2.2 的成本账：

- 每次训练花多少卡时 → 谁在烧钱
- 每个模型上线后花多少 Token → 值不值
- 重训频率 → 是否该优化数据而非频繁重训

### 10.4 安全与合规

- 训练数据是否含敏感信息
- 模型输出是否需过滤
- 模型权重访问权限（回扣 2.5 权限体系）
- 审计日志留存

---

### 十一、落地路线图：别追求”大一统”

```text
第 1 步（1–2 周）  ✅ 数据版本化 + 实验追踪      → 先"能复现、能对比"
第 2 步（2–4 周）  ✅ 模型注册 + 评测门禁        → 再"能管住准入"
第 3 步（1–2 月）  ✅ 自动化部署 + 灰度/回滚     → 然后"能稳定发"
第 4 步（持续）    ⚙️ 监控 + 自动重训            → 最后"能自循环"
```

> **三条务实建议**：<br>

1. **从”最痛的点”开始**——跑 20 组实验说不清哪组好？先做实验追踪
2. **工具服务于流程，别被工具绑架**——MLflow 不是目的，可复现才是
3. **每步都要有”退出条件”**——做到什么程度算完成，提前定义

---

### 十二、决策速查表

| 情况 | 该做 | 不该做 |
| --- | --- | --- |
| 刚起步，1–3 个模型 | 数据版本 + 实验追踪两件套 | 一上来就建完整平台 |
| 频繁微调，参数混乱 | 强制实验追踪 + 命名规范 | 靠记忆和群聊记录 |
| 效果莫名其妙变差 | 查数据/提示词/上游，再考虑重训 | 立即重训 |
| 要上生产 | 评测门禁 + 灰度 + 回滚方案 | 直接全量 |
| 监控告警太多 | 按”能否行动”分级精简 | 全量告警 |
| 自动重训 | 评估门禁 + 灰度验证 | 全自动无人工审核 |

### 小结：MLOps 的终局

**一句话收束**：**MLOps 的目标不是”工具多”，而是”稳定复现”**——同一个声明，跑一万次，结果一致；出了问题，能定位、能回滚、能改进。

**三个层次的成熟度：**

| 层次 | 特征 | 标志 |
| --- | --- | --- |
| L1 手工 | 脚本 + 人肉记录 | “上周那个结果怎么来的？” |
| L2 可追溯 | 数据/实验/模型全版本化 | “任何结果都能复现” |
| L3 自动化 | 门禁 + 灰度 + 监控 + 重训闭环 | “问题自动发现、自动修复” |

**与 2.x 的呼应（本篇落点）：**

| 3.1 环节 | 回扣 |
| --- | --- |
| ⑥ 部署承接 2.1 网关 | 2.1 网关五平面 |
| 算力调度与成本追踪 | 2.2 利用率算账 |
| ⑤ 注册门禁 + 评测 | 2.3 评测体系 |
| ⑤ 注册 / 血缘 / 灰度 / 回滚 | 2.4 模型全生命周期 |
| ⑦ 监控指标 + 成本 | 2.5 多模型管理 |
| ② 特征工程（上下文版） | 1.3 Prompt 与上下文工程 |

> **3.x 开篇定位句**： 2.x 解决”**单点能力**“，3.x 解决”**把这些能力串成一条能自动跑、能稳定复现、能持续迭代的流水线**“。 3.1 是这条流水线的**总纲**，后续 3.x 各篇会把它拆开讲透。
