**超节点下 RDMA NIC 的数据通路详解**

GPUDirect RDMA · C2C · Data Direct · WQE/CQE · Rail Fabric

技术详解 · 2026-11-08

| 核心结论：超节点里 RDMA NIC 只承担 Scale-out。柜内 GPU↔GPU 走 NVLink / PCIe<br> P2P，不经过 NIC。NIC 数据通路的本质是：HCA 的 DMA 引擎把 GPU HBM 当成一块可 DMA 的内存，经 PCIe 或 C2C 读写，再封装成<br> IB/RoCE 包出柜。CPU 只做控制面（建 QP、注册 MR、写 WQE、敲门铃）；数据面字节流不应进 Host DRAM。超节点代际差异不在<br> Verbs 语义，而在 NIC 挂到哪棵 PCIe 树上：经典 BAR P2P、GB200 的 C2C 绕行、CX8 Data Direct 双树。 |
| --- |

## 1. NIC 在超节点里站在哪一层

NVL72 / PCIe Switch 超节点同时存在三张网。把 NIC 数据通路和 NVLink 数据通路混为一谈，是最常见的分析错误。

| 网络 | 范围 | 物理载体 | NIC 是否参与数据面 |
| --- | --- | --- | --- |
| Scale-up / NVLink | 超节点内部 GPU↔GPU | NVSwitch 铜背板或 PCIe Switch<br> P2P | 否 |
| Compute East/West | 超节点之间 GPU↔GPU | 每 GPU 一张 SuperNIC + IB/RoCE<br> leaf-spine | 是，主数据通路 |
| Storage/Mgmt North/South | 存储、置备、带内管理 | BlueField DPU / 独立存储网 | 是，但走存储 NIC，不与计算网混流 |

标准 GB200 NVL72：18 个 compute tray × 4 GPU，柜内 72 GPU 一张 NVLink 域；每 GPU 1:1 配 ConnectX-7 400G，整柜东向约 28.8 Tb/s。GB300 NVL72 换成 ConnectX-8 800G，整柜东向约 57.6 Tb/s。NVLink 随柜出厂，不进 BOM；要买交换机和光模块的是后两张网。

**超节点三张网与 NIC 位置**

| ┌──────────────<br> 一个超节点 / NVL72 或 PCIe Switch 域<br> ──────────────┐<br> │ GPU0 <br> GPU1 GPU2 GPU3 ... GPU71 │<br> │ │ <br> │ │ │ NVLink / NVSwitch / PCIe P2P │<br> │ NIC0 <br> NIC1 NIC2 NIC3 ... <br> （1:1 SuperNIC，计算东向） │<br> │ DPU（存储/管理北向） │<br> └────┼─────┼─────┼─────┼──────────────────────────────────────────┘<br> │ <br> │ │ │ <br> rail-optimized leaf<br> └─────┴─────┴─────┴──► IB / RoCE<br> Scale-out ──► 其他超节点 |
| --- |

## 2. 三种 NIC 挂接拓扑，决定整条数据通路

Verbs 语义（QP、WQE、RDMA WRITE、rkey）在三代超节点上几乎一样。真正改变数据通路的是：NIC DMA 发出的 PCIe TLP 下一跳落到哪里。

## 2.1 路径 S：PCIe Switch / 经典 HGX BAR P2P

x86 HGX、以及基于 PCIe Switch 的开放超节点都属于这一类。GPU 与 NIC 挂在同一 PCIe Switch 或同一 Root Complex 下。NIC 把 GPU BAR1 窗口当成普通 MMIO 目标，发 Memory Read/Write TLP。CPU 不在数据面。

**路径 S：同 Switch P2P，最优 GPUDirect RDMA**

| GPU HBM<br> ← BAR1 翻译 ← GPU PCIe EP<br> ↑ PCIe P2P TLP（不进<br> Root Complex 最佳）<br> NIC HCA DMA<br> ↑ 门铃<br> / WQE 在 Host 或 GPU<br> CPU 只做控制面 |
| --- |

· 只有 PCIe Switch 在路上：最优，P2P 读带宽接近链路标称。

· 经过单个 CPU Root Port：能工作，部分 x86 上 P2P Read 会被严重限速。

· 穿过 QPI/UPI/HT 到另一 socket：可能极慢或不可靠。NCCL 此时可能改走 GPU–NIC–NIC–GPU。

· 前提：ACS 不把 P2P 重定向回 Root Complex；IOMMU 为 passthrough 或允许 P2P；BAR 窗口覆盖已注册 HBM。

## 2.2 路径 C：GB200 标准托盘，NIC 挂在 Grace 的 PCIe 上

标准 GB200 compute tray 是 2×Grace + 4×Blackwell。GPU 经 NVLink-C2C 连到 Grace，CX7 经 PCIe 连到 Grace，没有 GPU–NIC 直连 PCIe。NIC DMA 看到的是可路由到 GPU HBM 的 I/O 地址；物理上字节要过 Grace 一致性结构再上 C2C。这不是 Host DRAM bounce，CPU 核不搬数据，但数据面确实经过 CPU 芯片的互连。

**路径 C：C2C 一致内存上的 GPUDirect RDMA**

| GPU<br> HBM ←→ <br> NVLink-C2C（单向约 450 GB/s） ←→ Grace<br> <br> ↑ PCIe Gen5 x16 ~ 64 GB/s 理论<br> <br> CX7 400G ~ 50 GB/s 线速<br> NCCL 侧：NCCL_NET_GDR_C2C，PATH_C2C。CX7<br> 只看见 RDMA MR，backing 是<br> GPU HBM。 |
| --- |

带宽账：单 NUMA 上 NIC:Grace:Blackwell = 2:1:2。CX7 400G 实际约 46 GB/s，远小于 C2C 的 450 GB/s，所以单卡 RDMA 通常喂不满 C2C。真正的压力是：两张 GPU 共享一颗 Grace 的 PCIe 根，控制面、一致性探测和多 NIC 并发会抢同一颗 CPU 的 I/O 出口。公开讨论里把这称为 GB200 scale-out 的 host-path 约束。部分超大规模用户用 1:1 Grace–GPU 或外置 PCIe Switch 来绕开。

## 2.3 路径 D：CX8 Data Direct / Direct NIC 双 PCIe 树

GB300 NVL72 以及部分带 CX8 的 Grace Blackwell 平台引入 Data Direct。Grace 不支持 PCIe ATS，经典 ATS+IOMMU 直通做不到。CX8 因此拆成两棵虚拟 PCIe 树：

**路径 D：控制面走 CPU，数据面直连 GPU**

| 树 1 控制面 NET-PF <br> ──PCIe──► Grace Root Port<br> QP 状态、EQ、大部分门铃、驱动枚举、以太网管理面<br> <br> 树 2 数据面 Data Direct PF ──PCIe Gen6 x16──► GPU PF<br> HCA DMA 读写<br> GPU HBM，绕开 Grace，满 800 Gb/s |
| --- |

NCCL 2.27 的 Direct NIC 就是为这条路径准备的。Grace 自身只到 PCIe Gen5（约 400 Gb/s），若 RDMA 仍走路径 C，800G 网卡会被 CPU PCIe 卡死。Data Direct 把数据面放到 GPU–NIC 的 Gen6 x16 上，GDR 才能跑满 800G。软件要求大致为：GB200 用 r570+/CUDA 12.8+，GB300 用 r580+/CUDA 13.0+，DOCA-OFED 3.2+ 与对应 CX8 固件，并需要带 Data Direct 补丁的内核（公开材料指向 6.17-nvidia）。

| 比较项 | 路径 S PCIe P2P | 路径 C GB200 C2C | 路径 D CX8 Data Direct |
| --- | --- | --- | --- |
| NIC 挂接 | 与 GPU 同 Switch / 同 RC | 挂在 Grace PCIe | 数据 PF 挂 GPU，控制 PF 挂 Grace |
| 数据面是否过 CPU 芯片 | 否（理想情况） | 是，过 C2C/一致性结构 | 否 |
| 地址模型 | GPU BAR1 + peer_mem/dma-buf | C2C 一致地址 / MR IOVA | Data Direct DMA + dma-buf |
| 典型线速 | PCIe Gen5 x16 或网卡瓶颈 | 400G，受 Grace PCIe 约束 | 800G，Gen6 x16 |
| ATS 依赖 | 通常不强制 | 靠 C2C 一致性 | Grace 无 ATS，用 Data Direct 替代 |
| 代表平台 | HGX、PCIe Switch 超节点 | 标准 GB200 NVL72 | GB300 NVL72 / CX8 DirectNIC |

## 3. 控制面与数据面必须拆开

任何一条超节点 RDMA 通路都可以画成上下两层。混在一起会误判“CPU 参与了拷贝”。

| 层 | 谁执行 | 做什么 | 不做什么 |
| --- | --- | --- | --- |
| 控制面 | CPU proxy / 驱动 / 可选 GPU<br> kernel | 建 QP、交换 GID/QPN、注册 MR、写 WQE、敲门铃、轮询<br> CQE | 不搬 payload 字节 |
| 数据面 | NIC HCA DMA + 对端 HCA DMA | 按 WQE 里的 lkey/rkey/addr/length<br> 对 GPU HBM 做 PCIe DMA，再封装 IB/RoCE | 不解释 CUDA VA，不走 NVLink |

NCCL 默认仍是 CPU proxy：GPU kernel 把 chunk 写进已注册的 GPU FIFO（GDR）或 Host FIFO（无 GDR），proxy 线程 ibv_post_send。GDAKI / IBGDA / DOCA GPUNetIO 把 WQE 准备和门铃下放到 GPU SM，控制面也离开 CPU 热路径，但数据面仍然是同一套 HCA DMA。

## 4. 地址翻译链：从 CUDA 指针到网线上的包

NIC 从来不理解 CUDA VA。它只认自己页表里的 IOVA，以及 WQE 里的 lkey/rkey。超节点 GDR 的准备工作就是把 GPU 页变成 NIC 能 DMA 的 MR。

**GDR 地址翻译全链**

| 应用 CUDA VA<br> │ <br> cudaMalloc / cuMemCreate<br> GPU GMMU<br> PTE（Aperture = VID / SYS / PEER）<br> │ <br> pin + export<br> nvidia-peermem 或 dma-buf（cuMemGetHandleForAddressRange）<br> │ <br> ibv_reg_mr / ibv_reg_dmabuf_mr<br> HCA MTT<br> / MPT → lkey / rkey，IOVA 或<br> BAR 总线地址<br> │ <br> WQE：laddr + lkey + raddr + rkey + length<br> + opcode<br> HCA DMA 发<br> PCIe TLP<br> │ 路径<br> S：P2P 到 GPU BAR1 → BAR 翻译<br> → HBM<br> │ 路径<br> C：Grace IOMMU/一致性 → C2C → GPU HBM<br> │ 路径<br> D：Data Direct PF → GPU PF → HBM<br> HCA 封装<br> BTH + payload → IB/RoCE 出柜 |
| --- |

### 4.1 注册两种后端

· 传统 nvidia-peermem：IB 核心的 peer memory client。GPU KMD 提供 nvidia_p2p_get_pages，返回 GPU 页的总线地址列表，NIC 驱动编进 MR。依赖 MLNX_OFED/DOCA-OFED 的 peer_mem。

· 现代 dma-buf：CUDA 11.7+、内核 5.12+、Open GPU kernel module。NCCL 在三者都支持时默认走 dma-buf，不再强绑 nvidia-peermem。推荐路径。

· 注册很贵，NCCL 用 MR cache 缓存已注册区域，避免每次 isend 都 ibv_reg_mr。

### 4.2 BAR、IOMMU、ACS 三个开关

· BAR1 是 CPU/NIC 看 GPU HBM 的窗口，不一定覆盖全部显存。窗口不够时只能注册一部分，或退回 bounce。

· IOMMU 开着且 ACS Redirect 打开时，P2P TLP 会被拐回 Root Complex，GDR 从“直通”变成“绕 CPU”，带宽和延迟都会掉。

· 生产超节点通常：计算网卡与对应 GPU 放进同一 IOMMU group，ACS P2P Request Redirect 关闭，或 IOMMU passthrough。

· 路径 D 不用 ATS，因为 Grace 没有 ATS；靠 CX8 Data Direct 功能代替“翻译后的 P2P”。

## 5. 发送通路：本卡 GPU HBM 如何变成网上的 RDMA WRITE

以 NCCL IB 插件、GDR 开启、opcode = RDMA_WRITE 为例，超节点 rank 把一块已就绪的 GPU 缓冲推到对端超节点。

### 5.1 准备阶段（一次，不在热路径）

· 每对 rank 建两条 RC QP：前向 QP 走大数据；反向 QP 只传 CTS（对端缓冲地址、rkey、tag）。

· GPU FIFO / send buffer 注册成 MR，得到 lkey；对端 recv buffer 的 rkey 经 CTS 拿到。

· rail-optimized 组网时，本 GPU 的 SuperNIC 接到固定 leaf；同 rail 对端只过一跳 leaf。

### 5.2 热路径逐步

**发送热路径**

| 1. 本卡<br> kernel / CE 把要发送的 chunk 写入已注册 GPU buffer，并保证对<br> PCIe 可见<br> （store → fence / cuda<br> stream 同步。GDR 只在 kernel 边界提供一致性）<br> 2. CPU<br> proxy（或 GPU SM 在 GDAKI 下）填写<br> WQE：<br> opcode = RDMA_WRITE<br> local <br> = {ioaddr, lkey, length}<br> remote = {raddr, rkey}<br> 3. 门铃：写<br> NIC MMIO doorbell（BAR0）<br> 路径 S/C：CPU<br> 写 NET-PF BAR<br> 路径 D：控制面仍常走<br> NET-PF；Data Direct PF 负责随后的 payload DMA<br> GDAKI：GPU 映射门铃，SM<br> 直接写；映不上则 CPU proxy 代敲<br> 4. HCA 取<br> WQE，按 lkey 查 MTT，对<br> GPU 发 PCIe Memory Read TLP<br> 5. GPU 完成<br> Completion 带回数据；HCA 切成 MTU（如<br> 4 KB）加上 BTH/ETH/IP/UDP<br> 6. 经<br> SuperNIC SerDes → leaf →（跨 SU 再过<br> spine）→ 对端 SuperNIC<br> 7. 最后常跟一条<br> RDMA_WRITE_WITH_IMM，用 immediate 做完成通知 |
| --- |

关键点：第 4 步才是“从 GPU 用 DMA copy”。搬运者是 NIC，不是 GPU Copy Engine。GPU CE 只在路径 B（无 GDR、必须 staging）或柜内 Scale-up 时出现。

### 5.3 线上包长什么样

InfiniBand 是 BTH + payload；RoCE v2 是 Ethernet + IPv4/IPv6 + UDP(4791) + BTH + payload。超节点计算网几乎全是 RC 可靠连接，丢失由 HCA 重传，不走 TCP。Spectrum-X / Quantum 上常用自适应路由；NCCL 对大消息会把数据与 WITH_IMM 完成通知拆开，避免自适应乱序打乱完成语义。

## 6. 接收通路：对端 RDMA WRITE 如何进入本卡 HBM

**接收热路径**

| 1. 本卡事先<br> post recv / 把 rkey 经 CTS 交给对端<br> 2. 对端<br> HCA 发来 RDMA WRITE 包，本卡 HCA 按<br> BTH.deth / rkey / vaddr 查 MPT<br> 3. HCA<br> DMA 对 GPU 发 PCIe Memory Write TLP（Posted<br> Write）<br> 路径 S：P2P<br> 进 GPU BAR1 → 写 HBM<br> 路径 C：Grace<br> 一致性结构 → C2C → GPU HBM<br> 路径 D：Data<br> Direct PF → GPU PF → HBM<br> 4. 全部包到齐后，HCA<br> 写 CQE；若带 IMM，CQE<br> 带 immediate<br> 5. Flush：Posted<br> Write 完成不等于 GPU cache/HBM 对 SM 可见 |
| --- |

### 6.1 为什么必须 flush

PCIe Memory Write 是 Posted。HCA 认为 DMA 完成、CQE 已经写好时，最后几拍 TLP 仍可能停在 GPU 入站缓冲、Switch、或 C2C 上。若 GPU kernel 此时读 recv buffer，会看到新旧数据混合。这和“GPU DMA 到 Host HBM 数据不完整”是同一类完成语义问题，只是发起者换成了 NIC。

· NCCL：专用 flush QP 连到自己，发一条 dummy RDMA_READ。读不进网络，但 verbs 层会等先前 Posted Write 的 PCIe 完成。

· 应用：cuFlushGPUDirectRDMAWrites。若设备属性 GPU_DIRECT_RDMA_WRITES_ORDERING 已经覆盖目标 scope，调用是空操作。

· 多路径平台（PCIe 与 C2C 同时存在）时，CUDA 可能把 ordering 报成 ALL_DEVICES 且 flush 为空操作；混用两条入站路径时，顺序要由应用自己保证。

## 7. 谁敲门铃：CPU proxy 与 GPU-initiated RDMA

| 模式 | WQE 谁写 | 门铃谁敲 | CQ 谁轮询 | 超节点上的位置 |
| --- | --- | --- | --- | --- |
| NCCL CPU proxy | CPU | CPU 写 NIC BAR | CPU ibv_poll_cq | 训练集合通信默认 |
| GDAKI 完整 | GPU SM 写 GPU 上的 SQ | GPU 映射门铃直接写 | GPU 轮询 GPU 上的 CQ | 推理 KV、NVSHMEM put、NCCL GIN |
| GDAKI fallback | GPU SM | CPU 线程代敲 | GPU 轮询 CQ | 门铃无法映射到 GPU 时 |
| IBGDA / NVSHMEM | GPU | GPU 或 proxy | device-side wait | 对称堆、小消息热点 |

门铃映射失败的典型原因：PeerMappingOverride 未开、gdrdrv 不在、NIC BAR 不允许 GPU P2P。此时数据面仍是 GDR（payload 仍 NIC↔GPU），只是控制面门铃回到 CPU。分析超节点延迟时要把“数据 DMA 延迟”和“门铃往返延迟”分开。

## 8. Rail 组网如何塑造 NIC 数据面

超节点 Scale-out 不是“72 张网卡随便接 leaf”。它是 rail-optimized fat-tree：同一 rail 编号的 GPU（各 tray 的 GPU0、GPU1、…）接到同一组 leaf。同 rail 通信一跳；跨 rail 才上 spine。

**Rail 与 SuperNIC 的绑定**

| Tray0<br> GPU0-NIC ──┐<br> Tray1<br> GPU0-NIC ──┼── Leaf rail0 ── Spine ── 其他 SU<br> Tray2<br> GPU0-NIC ──┘<br> Tray0<br> GPU1-NIC ──┐<br> Tray1<br> GPU1-NIC ──┼── Leaf rail1<br> ...<br> 柜内同 rail 的跨超节点流量：NIC DMA → 一跳<br> leaf → 对端 NIC DMA<br> 跨 rail：NIC DMA → leaf → spine →<br> leaf → 对端 NIC |
| --- |

· 1:1 GPU–NIC 保证每张 GPU 有独立 DMA 引擎和独立 400G/800G 出口，避免多 GPU 抢一张网卡的 SQ/CQ。

· NCCL 默认每对远端 GPU×NIC 开 2 个逻辑 channel（NCHANNELS_PER_NET_PEER），轮转 QP，提高 ECMP 熵、增大每 QP chunk。

· Dual-plane：CX8 800G 拆成 2×400G 进两张独立 fabric。GPU 只看见一张 SuperNIC；平面间负载和故障切换在 NIC 硬件或 NCCL swplb/hwplb 完成。

· SHARP：部分 Reduce/AllGather/ReduceScatter 在 IB/Ethernet 交换机内归约。NIC 数据通路从“写对端 HBM”变成“写交换机归约上下文，再收回一份结果”。

## 9. 退化通路：NIC 碰不到 GPU 时发生什么

GDR 失败并不等于通信失败。NCCL 会把 FIFO 改放到 Host pinned，数据面变成两段 DMA。

**路径 B：Host staging**

| 发送：GPU HBM ──GPU CE 或 SM copy──► Host pinned<br> FIFO ──NIC DMA──► 网络<br> 接收：网络 ──NIC DMA──► Host pinned FIFO ──GPU CE /<br> kernel copy──► GPU HBM |
| --- |

| 触发条件 | 后果 |
| --- | --- |
| GPU 与 NIC 不在可 P2P 的 PCIe 域；ACS/IOMMU<br> 拐走 TLP | 退回 Host FIFO，PCIe 被拷两次，CPU<br> DRAM 成为瓶颈 |
| BAR 窗口不够或 peer_mem/dma-buf 不可用 | 只能注册部分缓冲，或整段 staging |
| NCCL LL 小消息协议 | 故意把 FIFO 放 Host，方便 CPU 轮询<br> flag；牺牲带宽换延迟 |
| 机密计算 / 不可导出 HBM | GPU DMA 到加密 bounce，NIC 只<br> DMA bounce |
| UVM 页还在 Host 或未 pin | 先 migration / CE copy 进 HBM，再注册 |

## 10. 一跳的延迟与带宽预算

| 环节 | 量级（数量级） | 说明 |
| --- | --- | --- |
| GPU store 对 PCIe 可见 | 百 ns～数 µs | 取决于 fence、L2 flush、C2C 一致性 |
| 门铃 + HCA 取 WQE | 亚 µs～数 µs | GDAKI 去掉 CPU 唤醒时可压到较低 |
| HCA DMA 读本地 GPU | 受 PCIe/C2C 往返 | 路径 S/D 短；路径 C 多一跳 C2C |
| 400G/800G 序列化 1 MB | 约 20 µs / 10 µs | 纯线速，不含交换机排队 |
| rail 一跳 leaf | 亚 µs～数 µs | 同 rail 最短 |
| 跨 SU spine | 再加一跳 | 大集群常见 |
| 对端 Posted Write + flush | 数 µs | 漏 flush 会表现为静默数据错误 |

所以超节点 NIC 通路的主要矛盾不是“RDMA 协议太慢”，而是：(1) 本端 GPU–NIC 物理跳数（S/C/D 三选一）；(2) 是否 1:1 以及 rail 是否对齐；(3) 完成可见性；(4) 小消息门铃开销。柜内 NVLink 单向数百 GB/s，单卡 NIC 只有约 50 或 100 GB/s。分层 AllReduce 先在柜内收薄再出 NIC，就是在保护这条更窄的数据通路。

## 11. 与柜内 DMA_COPY 如何衔接

**分层集合通信中的 NIC 切面**

| 超节点内（不进 NIC）：<br> TMA / Copy Engine / CFT ──CGBR──► P2P/NVLink ──► 邻卡<br> HBM<br> 可选 Switch Reduce，只向发起卡返回一份结果<br> <br> 超节点边界（进 NIC）：<br> 局部结果仍在 GPU HBM<br> → 注册 MR<br> → HCA DMA（路径 S / C / D）<br> → IB/RoCE<br> → 对端 HCA DMA 进<br> GPU<br> → flush<br> → 对端柜内再 DMA_COPY / multicast 展开 |
| --- |

NIC 数据通路的输入永远是“已经在某张 GPU HBM 上的一块注册内存”，不是 NVLink packet，也不是 CUDA VA。柜内 DMA_COPY 的工作是把 72 卡的数据收成 NIC 灌得动的尺寸；NIC 的工作是把它完整、有序、可见地送到另一超节点的对应 GPU。

## 12. 故障点与可见性（数据通路 RAS）

| 段落 | 典型故障 | 软件能看到什么 |
| --- | --- | --- |
| GPU 出站 / BAR 翻译 | BAR 窗口失效、P2P mapping 收回、poison<br> TLP | XID、nvidia_p2p invalidation<br> callback、dma-buf 撤销 |
| PCIe / C2C / Data Direct | ACS 重定向、链路降速、Completion<br> Timeout | AER、dmesg、NCCL NET 错误 |
| HCA SQ/CQ/MR | rkey 无效、QP 进 ERR、门铃丢失 | CQE syndrome；GDAKI 生产路径常常只报<br> REQ_ERR |
| 线缆 / leaf / spine | PFC 风暴、ECMP 极化、plane 失效 | 交换机遥测；dual-plane 切到剩余平面 |
| 对端入站 Posted Write | 写完成但 GPU 未见、poison 写入 HBM | 缺 flush 表现为计算错误；poison 应阻断提交 |

GPU DMA descriptor 上的 RAS tag 覆盖不了 NIC 发起的 DMA。peer_mem / GDS 必须用跨设备 request/incident ID，把 HCA CQE、PCIe AER 和 GPU 入站 poison 关联成一次事件。

## 13. 分析清单：面对一块超节点 NIC 时怎么看通路

· 先问挂接：lspci 树上 NIC 和 GPU 是同 Switch（S）、挂 Grace（C）、还是有 Data Direct PF（D）？

· 再问映射：NCCL 日志里是 dma-buf 还是 peermem？MR cache 是否命中？

· 再问 ACS/IOMMU：P2P 是否被 Redirect？路径 C 是否 PATH_C2C？

· 再问控制面：proxy 还是 GDAKI？门铃是否真的 GPU 直写？

· 再问 rail：该 GPU 的 SuperNIC 进哪条 leaf、哪个 plane？对端是否同 rail？

· 最后问完成：收包后有没有 loopback RDMA_READ 或 cuFlushGPUDirectRDMAWrites？

| 一句话：超节点 RDMA NIC 的数据通路是“HCA DMA ↔ GPU HBM ↔ IB/RoCE”，不是“GPU<br> Copy Engine ↔ 网卡驱动 ↔ TCP”。代际演进是把这条 DMA 从“过 CPU 根”挪到“过 Switch P2P”，再挪到“CX8<br> Data Direct 直连 GPU”。柜内 NVLink 负责把数据收薄；NIC 负责把剩下的那一份完整送出柜。 |
