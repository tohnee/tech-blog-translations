### 1. 一句话总览

**MLOps** 让”训练出来的模型”在生产中稳定运行；**LLMOps** 让”调用大模型的应用程序”在生产中可控、可观测；**AgentOps** 让”自主调用工具的智能体”在生产中安全、可追溯。三者属于同一工程血脉的三个层级。

| 范式 | 管理对象 | 核心问题 | 出现时间 | 典型栈 |
| --- | --- | --- | --- | --- |
| MLOps | 自训练 ML 模型 | 模型漂移、训练-服务偏差、复现性 | 2015–2018 | MLflow + TFX + KServe |
| LLMOps | 基于 LLM 的应用 | 提示词管理、幻觉、成本与延迟 | 2023 | Langfuse + LiteLLM + Vector DB |
| AgentOps | 自主工具调用智能体 | 多步推理、动作安全、行为审计 | 2024 | LangSmith + AgentOps + MCP |

### 1.1 一张图看清”每个 Ops 到底在管什么”

| 运维对象 | 输入 | 产出 | 失败后果 |
| --- | --- | --- | --- |
| ML 模型 | 训练数据 | 预测概率 | 漂移导致线上 AUC 跌 5% |
| LLM 应用 | 用户问题 + Prompt + 上下文 | 生成文本 | 幻觉、PII 泄漏、月账单爆 |
| Agent | 用户目标 | 动作序列 + 副作用 | 误删数据库、API 越权调用 |

### 1.2 为什么需要三套不同的 Ops？

“被管理对象的不可逆性”逐级放大：

- **预测错误**：可记录、不可改写外部世界 → 影响范围有限
- **生成错误**：会”说出来” → 触及合规、品牌、用户信任
- **动作错误**：会”动手” → 真实修改数据库、发邮件、转账

**结论**：越往 AgentOps 走，对可观测性、可控性、可回滚性的要求越高，这也是为什么 AgentOps 2024 年才”必须”出现。

### 3. MLOps：机器学习运维

### 3.1 起源与驱动力

- **2015 年**：Google 团队在 NeurIPS 发表《Hidden Technical Debt in Machine Learning Systems》（Sculley 等），首次系统提出 ML 系统会累积大量”看不见的技术债”——边界侵蚀、纠缠、隐藏反馈循环、未声明的消费者、数据依赖、配置问题、外部世界变化等 [3]。
- **驱动力**：随着 ML 从实验环境走向生产，团队发现模型上线的维护成本远高于构建成本。
- **关键转折**：Google 在 2020 年正式发布 MLOps 白皮书《Practitioners Guide to MLOps》，将其定义为”ML 工程文化与实践，目标是统一 ML 系统开发（Dev）与运行（Ops）” [1][2]。

### 3.2 理论框架

根据 Kreuzberger、Kühl、Hirschl 在 IEEE Access 发表的综述论文（2023），MLOps 是 **机器学习 × 软件工程/DevOps × 数据工程** 三者的交叉，遵循九大原则 [4]。**下面每条原则都给出”具体如何实现 + 代码骨架”**：

![](https://picx.zhimg.com/v2-424f9bf34813482e1d3b5997fe8c805d_r.jpg)
*MLOps 九大原则*

> 每条原则解决一个具体问题——CI/CD 让变更可追溯，CT 让模型不过时，监控让漂移可见，反馈闭环让模型能持续进化。

### 3.2.1 九大原则逐条落地

### 原则 1 — CI/CD 自动化

**解决问题**：训练脚本、模型文件、配置变更无版本、无回归、无审批。

**具体实现**：

- **代码 CI**：GitHub Actions / GitLab CI 在 PR 触发单元测试、训练 dry-run、模型 schema 校验
- **模型 CD**：用 **KServe / Seldon Core / BentoML** 把模型文件打包成独立推理服务
- **流水线 CD**：用 **Kubeflow Pipelines / Argo Workflows** 把”数据→训练→评估→部署”封装为 DAG

```yaml
# GitHub Actions 示例：训练 → 注册 → 部署
name: train-and-deploy
on: { push: { branches: [main] } }
jobs:
  train:
    runs-on: gpu-runner
    steps:
      - uses: actions/checkout@v4
      - run: python -m pytest tests/  # 单元测试
      - run: python train.py --config prod.yaml
      - run: mlflow models register -n fraud-detector -m runs:/${{ github.run_id }}/model
      - run: |
          # 部署到 staging
          kubectl apply -f deploy/kserve-fraud.yaml
```

### 原则 2 — 工作流编排

**解决问题**：训练步骤散落在多个 Notebook / 脚本里，无法编排、无法重试、无法可视化。

**具体实现**：

- **Airflow**：通用任务编排，适合 ETL 特征工程
- **Kubeflow Pipelines (KFP)**：ML 专用，DAG 节点是容器化步骤
- **Metaflow / Flyte**：Netflix / Lyft 出品，Python 优先，AWS/GCP 集成深
- **Dagster**：资产（asset）为中心，适合数据 + 模型双流水线

```python
# KFP 示例
@dsl.pipeline(name="fraud-training")
def fraud_pipeline():
    data = load_data_op()                    # 节点 1: 加载数据
    features = feature_eng_op(data)          # 节点 2: 特征工程
    train = train_op(features)               # 节点 3: 训练
    eval = eval_op(train)                    # 节点 4: 评估
    with dsl.Condition(eval.outputs.auc > 0.85):
        deploy_op(train)                     # 节点 5: 仅当 AUC 达标才部署
```

### 原则 3 — 可复现性

**解决问题**：同一份代码 6 个月后跑不出相同结果，事故复盘无法对齐。

**具体实现**：

- **环境层**：Docker + `pip freeze` / Poetry 锁文件
- **数据层**：DVC 用指针管理 S3 上的大数据集
- **代码层**：Git commit hash + 训练 commit 双绑定
- **运行时**：容器内固定随机种子，记录 `numpy/torch` 版本

```python
import mlflow, random, numpy as np
mlflow.log_params({"git_sha": subprocess.check_output(["git","rev-parse","HEAD"]).decode()})
random.seed(42); np.random.seed(42); torch.manual_seed(42)
mlflow.log_artifact("requirements.lock")
```

### 原则 4 — 代码/数据/模型版本化

**解决问题**：数据换了结果变了、模型换了指标跌了、谁也说不清为什么。

**具体实现**：

- **DVC**：`dvc add data/train.csv` → 数据走 Git 指针 + S3 真实数据
- **Git-LFS**：模型权重 ≤ 几 GB 时
- **MLflow Model Registry**：`fraud-detector@v3` `Staging` → `Production` 状态机

```bash
dvc add data/train.csv            # 数据版本化
dvc add models/fraud.pkl          # 模型版本化
git add . && git commit -m "v2.3 add 2024Q3 data"
mlflow models register -n fraud -m runs:/abc/model --stage Staging
```

### 原则 5 — 跨角色协作

**解决问题**：数据科学家、ML 工程师、DevOps、业务方各说各话。

**具体实现**：

- **角色 RACI**：谁负责训练、谁负责部署、谁负责回滚
- **共享实验平台**：MLflow Tracking / Weights & Biases 团队空间
- **统一术语**：Feature Store 统一”特征定义”，所有人引用同一个名字

| 角色 | 职责 | 工具 |
| --- | --- | --- |
| 数据科学家 | 探索、训练、注册模型 | Jupyter + MLflow |
| ML 工程师 | 特征工程、流水线、部署 | KFP + KServe |
| DevOps | 基础设施、监控、告警 | K8s + Prometheus |
| 业务方 | 标注、反馈、验收 | Label Studio + A/B 平台 |

### 原则 6 — 持续训练 (CT)

**解决问题**：模型上线后随时间漂移，但没人主动重训。

**具体实现**：

- **触发条件**：定时（每日）、数据量阈值（新增 1 万条）、性能触发（AUC 跌 2%）
- **工具**：Airflow `@hourly` + KFP；Vertex AI / SageMaker 内置 CT
- **关键决策**：**影子部署**新模型，对比流量后再切

```python
# Airflow DAG 定时触发
@dag(schedule="@daily", start_date=datetime(2024, 1, 1))
def ct_dag():
    new_data = check_data_drift()           # 监控数据
    model = train(new_data)                 # 训练
    auc = eval(model, holdout)              # 评估
    deploy(model) if auc > baseline else alert("AUC below baseline")
```

### 原则 7 — 元数据跟踪与日志

**解决问题**：训练时改了哪个超参导致 AUC 提升？不知道。

**具体实现**：

- **MLflow Tracking**：`log_params / log_metrics / log_artifact`
- **Weights & Biases**：可视化 + 超参搜索 + 报告分享
- **关键字段**：超参、metrics、代码 SHA、数据 SHA、环境、耗时

```python
with mlflow.start_run():
    mlflow.log_params({"lr": 1e-3, "batch": 64, "epochs": 10})
    mlflow.log_metric("auc", 0.91, step=epoch)
    mlflow.sklearn.log_model(model, "model")
```

### 原则 8 — 持续监控

**解决问题**：模型上线后没人看，漂移了 3 个月才发现。

**具体实现**：

- **Evidently AI / whylogs**：开源漂移检测
- **Arize / Fiddler**：商业 ML 可观测平台
- **监控信号**：输入分布（PSI、KS 检验）、输出分布、性能、AUC

| 信号 | 监控工具 | 告警阈值 |
| --- | --- | --- |
| 数据漂移 (PSI) | Evidently | PSI > 0.2 |
| 概念漂移 (AUC 跌) | 自定义评估任务 | AUC 跌 > 2% |
| 服务 P99 延迟 | Prometheus | > 200ms |
| 预测分布 | KServe 自带 | 偏离训练分布 |

### 原则 9 — 反馈闭环

**解决问题**：线上表现与训练表现脱节，模型越用越差。

**具体实现**：

- **隐式反馈**：用户点击 / 转化 / 跳过
- **显式反馈**：人工标注、人工审核队列
- **闭环**：反馈数据 → 重新标注 → 进入下一轮训练

```text
[线上预测] → 收集用户行为 / 人工反馈
    ↓
[反馈存储] → Feature Store / 标注平台
    ↓
[触发 CT] → 用新数据 + 旧数据混合训练
    ↓
[新模型上线] → 影子评估 → 全量切换
```

### 4. LLMOps：大语言模型运维

### 4.1 起源与驱动力

- **2023 年**：随着 ChatGPT、Claude、Gemini、Llama 等大模型爆发，企业开始大规模把 LLM 集成进产品，MLOps 在”调用的不是自己训练的模型”这一场景下明显不足 [6][7][8]。
- **驱动力**：模型由外部 API 提供（OpenAI、Anthropic）、需要提示词（prompt）工程、RAG（检索增强）、成本与延迟管理、合规与安全。
- **2025 年**：阿里云联合中国信通院发布《面向 LLM 应用的可观测性能力要求》标准，进一步规范化 LLM 应用运维 [9]。

### 4.2 LLMOps 与 MLOps 的关键差异

| 维度 | MLOps | LLMOps |
| --- | --- | --- |
| 模型来源 | 主要自训练 | 主要调用基础模型 + 微调 |
| 核心”代码” | Python 模型脚本 | Prompt + 上下文 + 检索片段 |
| 评估方式 | 准确率、AUC 等指标 | 语义相似、LLM-as-Judge、人工评审 |
| 主要风险 | 模型漂移、数据漂移 | 幻觉、提示注入、成本爆炸 |
| 监控信号 | 预测概率分布、特征分布 | Token 用量、延迟、毒性、相关性 |
| 部署单元 | 模型文件 + 服务容器 | Prompt 模板 + 检索索引 + LLM 调用链 |

> **核心差异**：LLMOps 把”模型的内部参数”变成”应用的外部资产”，运维重心从”训练”前移到”提示、调优、检索、评估、护栏”。

### 4.2.1 三个”被管理资产”的具体形态

| 资产 | MLOps 长什么样 | LLMOps 长什么样 | 怎么版本化 |
| --- | --- | --- | --- |
| 代码 | model.py | prompt_v3.md + chain.py | Git + Prompt Registry |
| 数据 | train.parquet (GB 级) | gold_set.jsonl (千行) + vector_index/ | DVC + Langfuse dataset |
| 模型 | model.pkl (100MB) | 外部 API endpoint | Model Registry + Provider lock-in |

### 4.4 RAG：从 Naive → Advanced → Modular

RAG 是 LLMOps 中最核心的应用模式之一。Gao 等人（2023）将 RAG 演进分为三个阶段 [12]，Shao 等人（2024）进一步提出 Modular RAG [13]：

![](https://pic3.zhimg.com/v2-2ce2b2b53b79a0e2b250e2ec5f42301e_r.jpg)
*RAG 三范式演进*

Modular RAG 把 RAG 系统视作”乐高式”计算图，对应了 AgentOps 中”工具与编排”的思想。

### 4.4.1 Naive RAG：30 行能跑通

```python
# 最朴素的 RAG — 仅作教学，生产请用 Advanced / Modular
from langchain.embeddings import OpenAIEmbeddings
from langchain.vectorstores import FAISS
from langchain.chat_models import ChatOpenAI
from langchain.chains import RetrievalQA

# 1) 索引
docs = loader.load()
vectorstore = FAISS.from_documents(docs, OpenAIEmbeddings())

# 2) 检索 + 生成
qa = RetrievalQA.from_chain_type(
    llm=ChatOpenAI(model="gpt-4o"),
    retriever=vectorstore.as_retriever(k=4)
)
print(qa.run("什么是 MLOps?"))
```

**Naive RAG 的三大典型问题**：

1. 召回不准（用户问”A”召回到”B”相关文档）
2. 上下文窗口撑爆（top-K=20 太长）
3. 答案”看似相关但其实是编的”（无 grounding 校验）

### 4.4.2 Advanced RAG：在 Naive 之前 / 之后插入”优化模块”

| 优化阶段 | 技术 | 作用 |
| --- | --- | --- |
| Pre-Retrieval | 查询重写 (HyDE / Multi-Query) | 把模糊问句改成精确检索句 |
| Pre-Retrieval | Query Decomposition | 把复杂问题拆成多个子问题 |
| Retrieval | Hybrid (BM25 + 向量) | 兼顾关键词 + 语义 |
| Retrieval | Metadata Filter | 按时间 / 部门 / 标签过滤 |
| Post-Retrieval | Re-ranking (Cohere / bge-reranker) | 用更贵的模型重排 top-100→top-5 |
| Post-Retrieval | Context Compression | 用 LLM 提取关键句，去掉冗余 |
| Generation | Citations / Source | 强制要求 LLM 引用来源段落 |

```python
# Advanced RAG 伪代码（典型生产形态）
def advanced_rag(query):
    # 1. 查询重写
    rewritten = llm(f"把以下问题改写为 3 个不同角度的检索句: {query}")
    sub_queries = rewritten.split("\n")

    # 2. 多路召回 + 混合检索
    docs = []
    for q in sub_queries:
        vector_hits = faiss.search(q, k=20)
        bm25_hits = bm25.search(q, k=20)
        docs += hybrid_fuse(vector_hits, bm25_hits)

    # 3. Re-rank
    docs = cohere_rerank(query, docs, top_n=5)

    # 4. 上下文压缩
    context = llm_compress(query, docs, max_tokens=2000)

    # 5. 生成 (带引用)
    return llm(PROMPT_WITH_CITATIONS.format(q=query, ctx=context))
```

### 4.4.3 Modular RAG：把 RAG 当成”乐高”

Modular RAG（arXiv:2407.21059）把 RAG 拆成可任意组合的算子 [13]：

| 模块 | 作用 | 典型实现 |
| --- | --- | --- |
| Indexing | 把文档切成 chunk、嵌入 | LlamaIndex, LangChain loaders |
| Pre-Retrieval | 查询变换 | HyDE, Multi-Query, Step-Back |
| Retrieval | 向量 / 关键词 / SQL / API | FAISS, BM25, Elastic, Text2SQL |
| Post-Retrieval | 过滤、重排、压缩 | Cohere Rerank, LLMFilter |
| Generation | Prompt 模板 + LLM | Promptfoo, Guidance |
| Orchestration | 路由、调度、融合 | LangGraph, LlamaIndex Workflows |

```python
# LangGraph Modular RAG 示例
from langgraph.graph import StateGraph
class RAGState(TypedDict):
    query: str; docs: list; answer: str
graph = StateGraph(RAGState)
graph.add_node("rewrite", rewrite_query)
graph.add_node("retrieve", hybrid_retrieve)
graph.add_node("rerank", cohere_rerank)
graph.add_node("generate", llm_generate)
graph.add_conditional_edges("rewrite", should_decompose, {"yes": "decompose", "no": "retrieve"})
app = graph.compile()
```

### 4.4.4 RAG 评估：怎么知道”回答好不好”

| 指标 | 含义 | 工具 |
| --- | --- | --- |
| Context Precision | 检索到的文档里相关比例 | RAGAS, TruLens |
| Context Recall | 应当被检索到的文档里召回了多少 | RAGAS |
| Faithfulness | 答案是否忠于检索内容（无幻觉） | RAGAS, DeepEval |
| Answer Relevancy | 答案是否回答了用户问题 | RAGAS |
| Answer Correctness | 答案与标准答案的语义相似度 | RAGAS |

```python
# RAGAS 评估示例
from ragas import evaluate
from ragas.metrics import faithfulness, answer_relevancy, context_precision

result = evaluate(
    dataset,                # 含 question/answer/contexts/ground_truth
    metrics=[faithfulness, answer_relevancy, context_precision]
)
print(result)  # {'faithfulness': 0.92, 'answer_relevancy': 0.88, 'context_precision': 0.81}
```

### 5.2.1 Reflection — 让 LLM 自己给自己批改

```python
# 经典 self-refine 模式
def generate_with_reflection(prompt, n_iter=3):
    answer = llm(prompt)
    for i in range(n_iter):
        critique = llm(f"请严格评价以下回答，给出改进意见:\n{answer}")
        answer = llm(f"根据意见改进:\n意见: {critique}\n原答案: {answer}")
    return answer
```

**生产实践**：

- 用 **Reflexion** 框架：把自我批评存入”记忆”，避免下次重蹈覆辙
- 配合 **Constitutional AI**（Anthropic）：让批评基于”宪法原则”
- **局限**：反思可能陷入”自我循环”，必须设最大迭代次数

### 5.2.4 Multi-Agent — 角色分工 + 消息总线

```python
    role="高级研究员",
    goal="查找并整理关于 MLOps 的最新资料",
    backstory="你是资深 AI 工程师，10 年 MLOps 经验",
    tools=[search_tool, arxiv_tool]

writer = Agent(
    role="技术作家",
    goal="把研究材料写成结构清晰的技术文章",
    backstory="你擅长把复杂概念讲清楚",
    tools=[]
)

task2 = Task(description="基于研究结果写一篇 1500 字文章", agent=writer)
```

**生产注意**：

- **消息总线**：用 LangGraph / Temporal 让 Agent 协作可视化
- **角色不要超过 5 个**：超过之后协调成本指数上升
- **“老板” Agent**：永远设一个规划者来裁决冲突

### 6. 三者关系：同源、层进、融合

### 6.1 同心圆模型

业界（包括 fmind AgentOps Open Course、Databricks Big Book of AgentOps）普遍认为三者是”同心圆”关系 [20][21]：

![](https://pic3.zhimg.com/v2-f630db7d6bcd0a84890b5555befc7478_r.jpg)
*MLOps/LLMOps/AgentOps 同心圆*

> **核心论断**：外圈继承内圈的全部能力，再叠加新一层”被管理对象”引入的新关注点。MLOps → 管理”预测”，LLMOps → 管理”生成”，AgentOps → 管理”动作”。

### 6.2 核心维度对比表

| 维度 | MLOps | LLMOps | AgentOps |
| --- | --- | --- | --- |
| 管理对象 | ML 模型 | LLM 应用 | 自主智能体 |
| 典型输出 | 预测 / 打分 | 生成文本 | 完成任务的动作序列 |
| 核心组件 | 数据、模型、流水线 | Prompt、模型、RAG | Agent、工具、记忆 |
| 关键监控 | 准确率、数据漂移 | 质量、延迟、Token 成本 | Trace、工具调用、决策路径 |
| 主要风险 | 模型退化 | 幻觉、成本失控 | 错误/不安全动作 |
| 评估方式 | 指标 vs 标签 | 响应质量 | 端到端任务成功率 |
| 典型工具 | MLflow、TFX、SageMaker | Langfuse、PromptLayer、Helicone | LangSmith、AgentOps、Arize |
| 成熟度 | 高 | 成长中 | 早期 [22] |

### 6.3 典型应用栈组合

![](https://pic2.zhimg.com/v2-934a6988fab8ed98fb0f7242cb6d94a7_r.jpg)
*典型应用栈组合*

> 实际生产中，一个智能体应用往往**同时**用到三者：传统 ML 模型做风险打分、LLM 做推理与生成、Agent 编排工具调用与多步决策。

### 6.3.1 一个真实的业务场景：**银行客服 RAG 智能体**

**业务目标**：客户问”我这张信用卡为什么被拒了？”智能体要走完：

1. 用传统 ML 模型预测”拒卡原因”（多分类，95% 准确率）
2. 用 LLM 把预测结果 + 客户画像生成”自然语言解释”
3. 用 Agent 决定：要不要调用”调额工具”“重审工具”“人工坐席”

| 阶段 | 用到 | 谁负责 |
| --- | --- | --- |
| 风险打分 | XGBoost 模型（自训练） | MLOps 管模型版本、漂移、CT |
| 生成解释 | GPT-4o + RAG（监管文档） | LLMOps 管 Prompt、Token 成本、幻觉 |
| 工具调用 | 调额 API / 重审 API / 坐席路由 | AgentOps 管 Trace、Guardrail、HITL |

**完整 trace 一次**（简化）：

```text
[Trace] 客户问"为什么拒卡"
 ├─ [Agent Span] 总耗时 8.2s
 │   ├─ [Plan Span] 决策：先评分 → 查文档 → 调工具
 │   ├─ [Task] 风险评分
 │   │   └─ [ML Model Span] XGBoost v2.3 → 拒卡原因=高负债率
 │   ├─ [Task] 检索监管文档
 │   │   ├─ [RAG Retrieval] top-5 文档
 │   │   └─ [LLM Span] GPT-4o → "根据您近6个月负债..."
 │   ├─ [Task] 决定下一步
 │   │   └─ [LLM Tool Use] 选择调"调额工具"
 │   ├─ [Task] 执行调额
 │   │   └─ [Tool Span] 调额 API 成功
 │   └─ [Evaluation] 用户点击"问题解决"
 └─ [Guardrail] 检查 PII、毒性、幻觉 → 全部通过
```

**这套系统的”统一可观测” 5 大仪表盘**：

1. **ML 仪表盘**：模型版本、AUC、漂移指标
2. **LLM 仪表盘**：Token 用量、延迟、幻觉率、相关性
3. **Agent 仪表盘**：成功率、平均步数、人工接管率
4. **成本仪表盘**：每会话成本、模型路由节省金额
5. **安全仪表盘**：PII 拦截、越权尝试、注入攻击

### 6.3.2 三个 Ops 的”职责边界”实战约定

| 触发的事件 | MLOps 负责 | LLMOps 负责 | AgentOps 负责 |
| --- | --- | --- | --- |
| AUC 跌 3% | ✅ 触发 CT、告警 | - | - |
| Token 月支出超预算 | - | ✅ 切到小模型、限流 | - |
| 工具调用失败率 > 5% | - | - | ✅ 熔断、切换路径 |
| PII 出现在回答里 | - | ✅ 拦截 + 告警 | ✅ 强制走人工 |
| Agent 步数 > 10 步 | - | - | ✅ 强制停止 + 人工接管 |

### 6.3.3 一句话总结三者关系

> **同源**（都源自 DevOps 的 CI/CD 思想）→ **层进**（被管理对象从预测 → 生成 → 动作）→ **融合**（一个复杂应用往往三者并存）。**MLOps 是底座，LLMOps 是能力放大器，AgentOps 是安全边界**。

```text
├─ < 1000 → 自托管开源（Langfuse + LiteLLM + vLLM）
├─ 1000-100k → 商业 SaaS（LangSmith / Arize）
└─ > 100k → 自研平台（阿里云 ARMS / Datadog LLM Obs）

你的应用核心是?
├─ RAG 为主 → LlamaIndex + RAGAS + Qdrant
├─ Agent 为主 → LangGraph + LangSmith + MCP
└─ 多 Agent → AutoGen / CrewAI + Arize

你是否在金融/医疗/政企?
├─ 是 → 必须自托管 + 国密算法 + 审计日志
└─ 否 → 可用 SaaS，但 PII 要脱敏
```

### 8. 风险与挑战

| 风险 | MLOps | LLMOps | AgentOps |
| --- | --- | --- | --- |
| 技术债 | 数据/配置债、纠缠 | Prompt 债、检索债 | 工具债、记忆债、权限债 |
| 非确定性 | 训练随机性 | 采样温度、模型升级 | 多步决策、并发冲突 |
| 可观测性 | 特征/预测分布 | Token、内容质量 | 决策路径、工具副作用 |
| 安全合规 | 模型公平性 | 提示注入、隐私泄漏 | 越权操作、级联失败 |
| 成本 | 算力 | API 计费、上下文长度 | 工具调用、长链推理 |
| 责任分散 | 模型 vs 服务 | 多家模型 API | 多 Agent、第三方工具 |

### 9. 未来趋势

1. **统一可观测协议**：OpenTelemetry GenAI 语义正成为跨 MLOps/LLMOps/AgentOps 的事实标准（阿里云 ARMS、Dify、Datadog 等均已支持）[10][14]。
2. **护栏即基础设施（Guardrails-as-a-Service）**：Arize、AgentOps、LangSmith 等纷纷内置护栏，对应 EU AI Act 等监管要求 [22]。
3. **LLM-as-Judge 标准化**：评估走向”模型评估模型”，配合人类反馈形成 RLHF/RLAIF 闭环。
4. **智能体即数字员工**：Databricks 提出 Agent Bricks——把”智能体构建、调优、部署”做成托管服务 [21]。
5. **从单体到编排**：未来 AgentOps 关注的不只是”单个智能体的可观测”，而是”多智能体协作系统的可观测与治理”。
6. **MLOps 思想反向影响 AgentOps**：CT（持续训练）的思想被映射为 Agent 的”持续评估 + 持续再训练”。

### 9.1 三大技术衍生方向

### 衍生方向 1 — Edge MLOps / 端侧智能体

**为什么出现**：

- 隐私要求高的场景（医疗、政企）不允许数据上云
- 实时性要求（自动驾驶、机器人）必须端侧推理
- 成本压力（千万级 IoT 设备）

**技术栈**：

- 端侧推理引擎：llama.cpp / TensorRT-LLM / MNN / ONNX Runtime
- 端侧 Agent：Apple Foundation Models（iOS 18）、Android AICore
- 端云协同：端侧做意图识别，云侧做大模型推理

**挑战**：

- 模型压缩（量化、剪枝、蒸馏）必须自动化
- OTA 更新要保证原子性
- 端侧硬件碎片化严重

### 衍生方向 2 — RAG Ops / EvalOps / Context Engineering

**为什么出现**：

- LLM 应用 80% 是 RAG，但 RAG 质量难量化
- 上下文窗口有限，Context Engineering 成为新学问
- 评估从”指标式”走向”LLM-as-Judge + 人类反馈”

**技术栈**：

- 评估：RAGAS、DeepEval、TruLens、Promptfoo
- Context Engineering：Anthropic 2024 年提出，强调”用最少 token 拿到最好结果”
- 高级模式：GraphRAG（Microsoft）、Agentic RAG、Self-RAG

**代表论文**：

- GraphRAG (arXiv:2404.16130) — 微软 2024，把知识图谱引入 RAG
- Self-RAG (arXiv:2310.11511) — 自反思检索
- CRAG (arXiv:2401.15884) — 修正型 RAG

### 衍生方向 3 — 协议标准化（MCP / A2A / ANP）

**为什么出现**：

- 工具接入方式碎片化（Function Calling、LangChain Tools、LlamaIndex Tools…）
- 多智能体无法跨框架协作
- 需要类似”USB-C”一样的统一接口

**核心协议**：

- **MCP (Model Context Protocol)** — Anthropic 2024-11 开源，标准化”LLM ↔ 工具”接口
- **A2A (Agent-to-Agent)** — Google 2025-04 提出，智能体之间消息协议
- **ANP (Agent Network Protocol)** — 中国社区 2025 提出，去中心化智能体网络

**生产建议**：

- 2025 年起，新项目**直接基于 MCP** 实现工具接入
- 多 Agent 项目关注 A2A 进展，但短期内 LangGraph 仍是工程首选
- 跨企业协作场景关注 ANP

### 9.2 6 大未来趋势详细解读

| 趋势 | 时间窗 | 影响力 | 关注指标 |
| --- | --- | --- | --- |
| 统一可观测协议 | 2024-2026 | 高 | OpenTelemetry GenAI 兼容性 |

**附录 A：术语速查（Glossary）**

| 术语 | 解释 |
| --- | --- |
| DevOps | Development + Operations 的融合实践，核心是 CI/CD 与自动化 |
| MLOps | 把 DevOps 思想扩展到机器学习全生命周期 |
| LLMOps | 在 MLOps 基础上管理 LLM 应用，重点在 Prompt、RAG、Token 成本、幻觉 |
| AgentOps | 在 LLMOps 基础上管理自主智能体，重点在 Trace、工具、Guardrail、HITL |
| CT | Continuous Training，持续训练 |
| CI/CD | Continuous Integration / Continuous Delivery |
| RAG | Retrieval-Augmented Generation，检索增强生成 |
| HITL | Human-in-the-Loop，人在环 |
| Drift | 数据漂移或概念漂移，指输入/目标分布随时间变化 |
| Guardrail | 护栏，约束智能体或 LLM 行为的规则 |
| Span / Trace | OpenTelemetry 的追踪原语，Span 是单个操作，Trace 是完整调用链 |

### **一句话总结衍生**：每个 Ops 都在”被管理对象不可逆性增加”的过程中，分化出更细的子领域。
