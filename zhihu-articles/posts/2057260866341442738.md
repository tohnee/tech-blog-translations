### 1 为什么需要 layout

[04 · TTIR 篇](https://zhuanlan.zhihu.com/p/2053996516017181821) 留下了一个明确的边界：TTIR 是**block 级**的——一个 `tt.load` 描述”整个 block 要从 global memory 读一整块数据”，但**这块数据在 GPU 上到底由哪些 thread 各自持有哪几个元素，TTIR 一字未提**。这正是它”离 Python 近、离硬件远”的体现。

硬件的现实是 thread 级的：一个 block 由若干 warp、每个 warp 32 个 thread 组成，每个 thread 只有自己私有的那一小撮寄存器。你在 TTIR 里写的 block 级操作（读一整块、算一整块），落到硬件上必须被**拆给这些 thread**——数据从 global memory 经 shared memory 进到寄存器后，就分散在各个 thread 手里，每个 thread 各持有一部分、各算一部分。

问题在于：同样一块数据（比如一个 128×256 的 tile），”哪个 thread 持有哪几个元素”**有成百上千种合法的分法**，而这些分法直接决定了能不能用上 tensor core、访存会不会 coalesce、shared memory 会不会 bank conflict。

**Layout（布局）/ encoding 就是回答”这块数据怎么分布到 warp/thread/寄存器/shared memory 上”的那份说明。** 把它从 TTIR 的 block 级抽象”落”到 thread 级，就是本篇的主线——这一跳由 `convert_to_ttgpuir` 这个 pass 完成：

![](https://pic4.zhimg.com/v2-72d6adff6d2d800116b0626d3670d26f_r.jpg)
*图1：TTIR 到 TTGIR 的本质差别，就是 tensor type 上多了一层 encoding*

一句话：**TTIR 的 tensor 只有”形状 + 元素类型”，TTGIR 的 tensor 还多了”encoding”。** layout 不改变数据本身，只改变”数据怎么摆放”——而摆得好不好，是 Triton 性能的灵魂。

### 2 encoding 到底是什么：拆一个真实的 blocked

encoding 是挂在一个 tensor type 上的**属性（Attribute）**。在 IR 文本里它紧跟在元素类型后面，前面带 `#`。先看贯穿全系列的 matmul 在 `cuda:80`（Ampere）上编译出来的真实 TTGIR 开头（见同目录缓存 `matmul_kernel.ttgir`）：

```text
#blocked  = #ttg.blocked<{sizePerThread = [1, 8], threadsPerWarp = [1, 32], warpsPerCTA = [8, 1], order = [1, 0]}>
#blocked1 = #ttg.blocked<{sizePerThread = [1, 8], threadsPerWarp = [4, 8],  warpsPerCTA = [8, 1], order = [1, 0]}>
```

这两行声明了两个 layout，之后函数体里凡是 `#blocked` / `#blocked1` 标注的 tensor，都用这份排布。`#ttg.blocked<...>` 是最常见的一种 encoding，叫 **BlockedEncoding**，它用四个元组完整描述了一块二维 tensor 怎么切给 warp / thread：

| 字段 | 含义 | #blocked 的值（以 64×256 的 tile 为例） |
| --- | --- | --- |
| sizePerThread | 每个 thread 在各维上持有几个元素 | [1, 8]：dim0 持 1 个、dim1 持 8 个（共 8 个/线程） |
| threadsPerWarp | 一个 warp 内 32 个 thread 怎么铺在各维 | [1, 32]：32 个 thread 全沿 dim1 排 |
| warpsPerCTA | 一个 block 内各 warp 怎么铺在各维 | [8, 1]：8 个 warp 全沿 dim0 排 |
| order | 各维的遍历优先级（最快变化维在前） | [1, 0]：dim1 最快变化（contiguous） |

把这四个元组”乘”起来，就得到了”logical 坐标 → （warp、thread、寄存器）”的完整映射。以 `#blocked` 为例：每个 warp 沿 dim1 有 32 个 thread、每个 thread 沿 dim1 取 8 个连续元素，所以**一个 warp 一次覆盖 dim1 上 32×8 = 256 个连续元素**——正好等于 `BLOCK_SIZE_N = 256`。这正是 `#blocked` 常用于 load/store 的原因：需要连续访问一整段元素时（比如加载某个矩阵 tile 或写回结果），这种布局让连续的 256 个元素被整齐地分给一个 warp 的 32 个 thread，访存完全 coalesce。

![](https://pica.zhimg.com/v2-af24bd5af08df202154f933a163c1ef4_r.jpg)
*图2：encoding 就是把”块内逻辑坐标”拆成（warp、thread、寄存器）三层物理坐标的映射规则*

**核心记忆点：** encoding 不改变 tensor 的形状和元素类型，它是一份额外的”摆放说明书”。同一个 `tensor<64x256xf16>`，挂 `#blocked` 和挂 `#mma` 是两块**逻辑相同、物理摆放完全不同**的数据——pass 的工作就是为每个 tensor 挑一份合适的说明书，并在摆放不一致时插入”翻译”。

> 这套 encoding 系统仍在演进中。本篇讲的 `Blocked/DotOperand/NvidiaMma` 等是当前主线；Triton 正在用 **LinearLayout**（见 §6）把它们统一成一个数学表示，部分转换逻辑已迁移过去，后续版本会继续变化。

### 3 matmul 用到的几种 encoding

Triton 的 encoding 分**两大类**：一类是**分布式布局**（数据在寄存器里，分布在各 thread 上），另一类是**共享布局**（数据在 shared memory 里）。完整有十几种，本节只讲 matmul 实际用到的这 5 种（4 种分布式 + 1 种共享）。打开真实 matmul 的 TTGIR 你就会撞见它们，各有分工：

![](https://pic2.zhimg.com/v2-b09e3034f2f6583697bd0e5890b86d2b_r.jpg)
*图3：matmul 用到的五种 encoding*

逐一拆解（每个都给真实 matmul 里的实例）：

### 3.1 Blocked —— 通用的”好搬运”布局

就是 §2 拆的那个。它的设计目标是**让 load/store coalesce**——相邻 thread 访问相邻地址。matmul 里所有指针张量、累加器之外的大部分中间 tensor 都用 Blocked。源码定义：[TritonGPUAttrDefs.td:738](https://github.com/triton-lang/triton/blob/0a0a6e5a3d5e3e3683683dd920ceef459798c99b/include/triton/Dialect/TritonGPU/IR/TritonGPUAttrDefs.td#L738)。

### 3.2 DotOperand —— 喂给 tensor core 的输入布局

```text
#ttg.dot_op<{opIdx = 0, parent = #mma, kWidth = 2}>   // A 的布局
#ttg.dot_op<{opIdx = 1, parent = #mma, kWidth = 2}>   // B 的布局
```

`tt.dot` 的两个 operand **必须**是 DotOperand layout。它有三个参数：

- `opIdx`：这个 operand 是 dot 的第几个输入（A 是 0，B 是 1）——A 和 B 在 tensor core 里的摆放规则不同，所以要区分。
- `parent`：它配套的”结果布局”是谁（这里是 `#mma`）——operand 的摆放要和结果的摆放对得上。
- `kWidth`：一个 thread 沿 K 维连续持有几个元素。f16 是 16 bit，tensor core 一次喂 32 bit，所以 `kWidth = 32/16 = 2`。

设计意图一句话：**tensor core 指令对 operand 的摆放有硬性要求，DotOperand 就是把通用 Blocked 数据”摆成 mma 想要的样子”的那层布局。** 源码定义：[TritonGPUAttrDefs.td:1431](https://github.com/triton-lang/triton/blob/0a0a6e5a3d5e3e3683683dd920ceef459798c99b/include/triton/Dialect/TritonGPU/IR/TritonGPUAttrDefs.td#L1431)。

### 3.3 NvidiaMma —— tensor core 的输出布局

```text
#mma = #ttg.nvidia_mma<{versionMajor = 2, versionMinor = 0, warpsPerCTA = [2, 4], instrShape = [16, 8]}>
```

matmul 的累加器 `accumulator` 就是这个 layout：`tensor<128x256xf32, #mma>`。`versionMajor = 2` 表示 Ampere/Turing 的第二代 tensor core（对应 `mma.sync` 指令），`instrShape = [16, 8]` 是一条 mma 指令算的小块大小，`warpsPerCTA = [2, 4]` 把 8 个 warp 铺成 2×4。**这是 `accelerate_matmul` pass 把 `tt.dot` 的结果从通用 Blocked 改写来的**——细节留到下一篇（06 · 优化篇 A），这里只要记住：mma 结果天然就是这个摆放。源码定义：[TritonGPUAttrDefs.td:1272](https://github.com/triton-lang/triton/blob/0a0a6e5a3d5e3e3683683dd920ceef459798c99b/include/triton/Dialect/TritonGPU/IR/TritonGPUAttrDefs.td#L1272)。

### 3.4 SwizzledShared —— shared memory 里避 bank conflict 的重排

```text
#shared = #ttg.swizzled_shared<{vec = 8, perPhase = 1, maxPhase = 8, order = [1, 0]}>
```

数据进 shared memory 后，`local_load` 把它读进寄存器喂给 mma。shared memory 有 32 个 bank，连续 32 个元素分属不同 bank——如果某些访问模式让多个 thread 撞同一 bank，就会**串行化（bank conflict）**。SwizzledShared 通过对地址做 xor 重排（swizzle），让”看似会撞 bank 的访问”散开到不同 bank。`vec / perPhase / maxPhase` 三个参数控制重排模式（`.td` 里有详细的 xor 示意）。它只出现在 `ttg.memdesc` 类型上——shared memory 的”句柄”，和分布在寄存器的 tensor 是两个世界。源码定义：[TritonGPUAttrDefs.td:10](https://github.com/triton-lang/triton/blob/0a0a6e5a3d5e3e3683683dd920ceef459798c99b/include/triton/Dialect/TritonGPU/IR/TritonGPUAttrDefs.td#L10)。

### 3.5 Slice —— expand_dims 的逆布局

```text
tensor<128xi32, #ttg.slice<{dim = 1, parent = #blocked1}>>
```

matmul 里 `offs_am` 是 1D 的，但它是某个 2D `#blocked1` tensor 在 `dim=1` 上”压扁”得到的——Slice 就是描述这种”从父布局挤掉某一维”的派生布局，参数 `dim` 指定挤哪一维、`parent` 指定父布局。它主要服务于 `expand_dims` / `broadcast` 的逆运算，是布局推导里的一块”胶水”。源码定义：[TritonGPUAttrDefs.td:1381](https://github.com/triton-lang/triton/blob/0a0a6e5a3d5e3e3683683dd920ceef459798c99b/include/triton/Dialect/TritonGPU/IR/TritonGPUAttrDefs.td#L1381)。

> 小结一张表，把五种 encoding 按”住在哪里 / 服务于谁”归位：

| encoding | 物理位置 | 服务对象 | matmul 实例 |
| --- | --- | --- | --- |
| Blocked | 寄存器（分布在 thread） | 通用访存、coalesce | 指针张量、中间结果 |
| DotOperand | 寄存器 | tt.dot 的 operand | a_109 / b_111（local_load 的结果） |
| NvidiaMma | 寄存器 | tt.dot 的结果 | 累加器 accumulator |
| SwizzledShared | shared memory | async_copy 落地、避 bank conflict | ttg.memdesc<...,#shared,#smem> |
| Slice | 寄存器 | expand_dims/broadcast 的逆 | 1D 的 offs_* |

### 4 convert_to_ttgpuir：layout 是怎么被分配的

前面三节讲的是”layout 是什么、有哪些”。本节回答最关键的问题：**这堆 encoding 是怎么被挂上去的？** 答案全在 `convert_to_ttgpuir` 这个 pass 里。它用的是 [03 · MLIR 速成篇](https://zhuanlan.zhihu.com/p/2052444385267257385) 讲过的 Conversion 框架——三件套：`TypeConverter` + `ConversionTarget` + 一堆 `OpConversionPattern`。

![](https://pic2.zhimg.com/v2-2582bbe9e5210ddde19ac064c6d077e3_r.jpg)
*图4：convert_to_ttgpuir 复用 MLIR 的 Conversion 框架，三件套各司其职*

### 4.1 默认分配：TypeConverter 给每个 tensor 发一个 Blocked

Conversion 框架的核心是：**当 pattern 改写一个 op 时，它的 operands / results 类型会被 TypeConverter 自动”转换”。** Triton 的 `TritonGPUTypeConverter` 对”没有 encoding 的 tensor”做的事情非常朴素——给它发一个默认 Blocked：

源码：[TritonGPUConversion.cpp:28-38](https://github.com/triton-lang/triton/blob/0a0a6e5a3d5e3e3683683dd920ceef459798c99b/lib/Conversion/TritonToTritonGPU/TritonGPUConversion.cpp#L28-L38)

```text
addConversion([this](RankedTensorType tensorType) -> RankedTensorType {
    if (tensorType.getEncoding())
      return tensorType;                       // 已经有 layout，不动
    ArrayRef<int64_t> shape = tensorType.getShape();
    triton::gpu::BlockedEncodingAttr encoding =
        getDefaultBlockedEncoding(this->context, shape, this->numWarps,
                                  this->threadsPerWarp, this->numCTAs);
    return tensorType.cloneWithEncoding(encoding);   // 挂上默认 Blocked
});
```

**要解决什么问题：** TTIR 里成百上千的 tensor 都没 layout，需要一个兜底策略统一分配。**机制：** 凡是没 encoding 的 tensor，一律调 `getDefaultBlockedEncoding` 发一个 Blocked。那默认 Blocked 长什么样？

源码：[Dialect.cpp:682-695](https://github.com/triton-lang/triton/blob/0a0a6e5a3d5e3e3683683dd920ceef459798c99b/lib/Dialect/TritonGPU/IR/Dialect.cpp#L682-L695)

```text
// 1 element per thread
// order = reverse(arange(rank))
BlockedEncodingAttr getDefaultBlockedEncoding(..., ArrayRef<int64_t> shape,
                                              int numWarps, ...) {
  int rank = shape.size();
  SmallVector<unsigned> order(rank);
  std::iota(order.begin(), order.end(), 0);
  std::reverse(order.begin(), order.end());        // 二维 → order = [1, 0]
  SmallVector<unsigned> sizePerThread(rank, 1);    // 每维每线程 1 个
  return BlockedEncodingAttr::get(context, shape, sizePerThread, order,
                                  numWarps, threadsPerWarp, numCTAs);
}
```

**设计取舍：** 默认值是**保守的**——`sizePerThread` 全 1（每个线程每维只拿 1 个元素）、`order` 取反序（最后一维最快变化，对 row-major 数据天然 coalesce）。这是个”安全但平庸”的起点：它保证正确，但不追求性能。注意 §2 真实 dump 里的 `#blocked` 是 `sizePerThread = [1, 8]`——**那不是 convert_to_ttgpuir 的默认值**，而是后续 `coalesce` pass（依赖 AxisInfo 连续性分析）把连续维从 1 放大到 8、做成向量化加载的结果。`sizePerThread = [1,1]` 才是 convert_to_ttgpuir 刚挂上去时的样子。

**一句话：convert_to_ttgpuir 先把所有 tensor 一刀切地发成”保守 Blocked”，性能上的精雕细琢留给后面的 pass。** 这一刀切保证了”每个 tensor 都有 layout”这个不变量——TTGIR 里不会再出现没 encoding 的 tensor。

### 4.2 tt.dot 的特殊待遇：operand 必须是 dot_op

并非所有 op 都满足于”默认 Blocked”。`tt.dot` 就有一条硬性合法性约束——它的两个 operand **必须**是 DotOperand layout，否则这个 dot 在 TTGIR 里就是”非法”的、必须被改写。

合法性规则就一行，源码：[TritonGPUConversion.cpp:81-90](https://github.com/triton-lang/triton/blob/0a0a6e5a3d5e3e3683683dd920ceef459798c99b/lib/Conversion/TritonToTritonGPU/TritonGPUConversion.cpp#L81-L90)

```text
addDynamicallyLegalOp<triton::DotOp>([](triton::DotOp dotOp) -> bool {
    auto aEnc = cast<RankedTensorType>(dotOp.getA().getType()).getEncoding();
    auto bEnc = cast<RankedTensorType>(dotOp.getB().getType()).getEncoding();
    return aEnc && isa<DotOperandEncodingAttr>(aEnc) &&
           bEnc && isa<DotOperandEncodingAttr>(bEnc);   // 两个 operand 都是 dot_op 才合法
});
```

Conversion 框架看到 dot 不合法，就去 pattern 列表里找能处理它的工人——找到的是 `TritonDotPattern`。它干两件事：

源码：[TritonToTritonGPUPass.cpp:223-253](https://github.com/triton-lang/triton/blob/0a0a6e5a3d5e3e3683683dd920ceef459798c99b/lib/Conversion/TritonToTritonGPU/TritonToTritonGPUPass.cpp#L223-L253)

```text
// 1) 给 dot 的结果分配一个 Blocked（sizePerThread 按元素总数缩放）
Attribute dEncoding = BlockedEncodingAttr::get(
    getContext(), origShape, retSizePerThread, retOrder, numWarps, ...);
RankedTensorType retType = origType.cloneWithEncoding(dEncoding);

// 2) operand 不是 dot_op 的，分配 dot_op 并插一个 convert_layout 翻译过去
if (!isa<DotOperandEncodingAttr>(aEncoding)) {
  Attribute enc = DotOperandEncodingAttr::get(getContext(), 0, dEncoding, aEltType);
  a = ConvertLayoutOp::create(rewriter, a.getLoc(),
                              aType.cloneWithEncoding(enc), a);
}
// ... 对 b 同理（opIdx = 1）
```

**要解决什么问题：** tensor core 指令对 operand 摆放有硬要求，所以 dot 的 operand 不能用通用 Blocked。**机制：** pattern 给 operand 重新分配一个 `DotOperandEncodingAttr`（带 `opIdx` 区分 A/B、`parent` 指向 dot 的结果布局），并在 operand 原值和新布局之间插一个 `convert_layout` op 做翻译。**设计取舍：** 注意此时 dot 的**结果**分配的还是 Blocked（不是 mma）——convert_to_ttgpuir 只管”operand 必须是 dot_op”这条合法性，把 dot 的结果精修成 `NvidiaMma` 是后面 `accelerate_matmul` 的事（§5 会跟踪）。这种”先满足合法性、再精修性能”的分层，是 Triton 编译管线反复出现的节奏。

### 4.3 convert_layout：layout 不匹配时的”适配器”

4.2 里反复出现的 `convert_layout` 是整个 layout 体系的关键 op。它的语义很简单：**把一个 tensor 从一种 layout 搬到另一种 layout**，逻辑数据不变、物理摆放变了。它在 IR 里长这样（matmul 写回 C 之前的那一步）：

```text
%7 = ttg.convert_layout %c : tensor<128x256xf16, #mma> -> tensor<128x256xf16, #blocked>
tt.store %c_ptrs_86, %7, %c_mask_92 : tensor<128x256x!tt.ptr<f16>, #blocked>
```

`%c` 是 dot 出来的结果，挂在 `#mma` 布局上；但 `tt.store` 要把它写回 global memory，store 的指针是 `#blocked` 布局（coalesce 友好）。两套摆放不一致，于是在中间插一个 `convert_layout` 把 `#mma → #blocked` 翻译过去。

**为什么需要它？** layout 体系的本质矛盾是：**不同 op 偏好不同的布局**（dot 喜欢 mma/dot_op，store 喜欢 blocked），而 IR 是一条数据流链，前一个 op 的输出布局往往不是后一个 op 想要的。convert_layout 就是这条链上的”变压器”。

**设计取舍：** convert_layout 是有代价的——**若重排需要跨 warp**（数据要从一个 warp 倒到另一个），就得经过 shared memory 搬一道（寄存器→shared→寄存器）；只有局限在 warp 内的重排，才能用更便宜的 shuffle 指令躲开 shared memory。所以后续有一大批 pass（`remove_layout_conversions`、`coalesce` 等）专门**贪心地消除它**：要么把相邻 op 的 layout 谈拢、避免插入；要么把零散的 convert_layout 合并掉。一篇好的 layout 优化，目标之一就是让数据流上 convert_layout 越少越好。

### 4.4 把它跑起来：runOnOperation

三件套在 pass 的 `runOnOperation()` 里组装并启动，结构和 [03 · MLIR 速成篇](https://zhuanlan.zhihu.com/p/2052444385267257385)§2.9 讲的 conversion 框架完全一致：

源码：[TritonToTritonGPUPass.cpp:728-764](https://github.com/triton-lang/triton/blob/0a0a6e5a3d5e3e3683683dd920ceef459798c99b/lib/Conversion/TritonToTritonGPU/TritonToTritonGPUPass.cpp#L728-L764)

```text
void runOnOperation() override {
    MLIRContext *context = &getContext();
    ModuleOp mod = getOperation();
    TritonGPUTypeConverter typeConverter(context, numWarps, threadsPerWarp,
                                         numCTAs, enableSourceRemat);   // TypeConverter：默认 Blocked
    TritonGPUConversionTarget target(*context, typeConverter);          // 合法性：dot operand 必须 dot_op
    RewritePatternSet patterns(context);
    populateArithPatternsAndLegality(typeConverter, patterns, target);
    populateMathPatternsAndLegality(typeConverter, patterns, target);
    populateTritonPatterns(typeConverter, patterns, numCTAs);            // patterns：含 DotPattern
    populateSCFPatterns(typeConverter, patterns);
    populateCFPatterns(typeConverter, patterns);
    // 把 num_warps / target 等元数据写进 module
    mod->setAttr(AttrNumWarpsName, ...);
    mod->setAttr(AttrTargetName, ...);                                  // cuda:80
    applyPartialConversion(mod, target, std::move(patterns));           // 启动调度
}
```

值得一说的是绝大多数 op（`arith.addi`、`tt.load`、`tt.expand_dims`、`scf.for` …）走的都是 `GenericOpPattern`——它什么也不做，只是”用 TypeConverter 把结果的 tensor type 转一下（即挂上默认 Blocked），原样重建同名 op”。也就是说，**对这些 op，layout 分配完全由 TypeConverter 兜底**，没有特殊逻辑。真正有特殊逻辑的只有 `tt.dot`（DotPattern）、`tt.expand_dims`、`tt.cat` 等少数几个——它们的输出 layout 需要从输入 layout 派生，不能简单发默认值。

### 5 layout 在管线里怎么演化：跟一次 matmul

现在把视角拉远。convert_to_ttgpuir 只是 `make_ttgir` 这一大段（[compiler.py:261-336](https://github.com/triton-lang/triton/blob/0a0a6e5a3d5e3e3683683dd920ceef459798c99b/third_party/nvidia/backend/compiler.py#L261-L336)）里的**第一个** pass。你看到的真实 `matmul_kernel.ttgir` 是**整段跑完**的最终产物，所以里面的 encoding 已经被后面好几个 pass 精修过了。本节跟一遍 matmul 的 layout 演化，把”哪些是 convert_to_ttgpuir 给的、哪些是后加工的”分清楚：

![](https://picx.zhimg.com/v2-4a694414ace39642fc01a8c7e6268e73_r.jpg)
*图6：matmul 的 layout 完整流程*

逐步对照真实 dump：

1. **convert_to_ttgpuir（起点）**：所有 tensor 挂默认 Blocked（`sizePerThread=[1,1]`、`order=[1,0]`）；`tt.dot` 的 A、B operand 挂上 `dot_op`（parent 当时还是 Blocked），中间插 `convert_layout`。dot 结果还是 Blocked。
2. **coalesce**：依据 [AxisInfo](https://github.com/triton-lang/triton/blob/0a0a6e5a3d5e3e3683683dd920ceef459798c99b/lib/Analysis/AxisInfo.cpp) 的连续性分析，把连续维的 `sizePerThread` 从 1 放大到 8——这就是真实 dump 里 `#blocked` / `#blocked1` 的 `[1, 8]` 来源。放大后每个 thread 一次拿 8 个连续元素，访存向量化。
3. **accelerate_matmul**：把 `tt.dot` 的结果 layout 从 Blocked 改写成 `NvidiaMma`（`#mma`），dot operand 的 `parent` 也随之指向新的 `#mma`——这就是真实 dump 里 `#ttg.dot_op<{opIdx=0, parent=#mma, kWidth=2}>` 的样子。这一步是 matmul 用上 tensor core 的关键。
4. **pipeline（软件流水线）**：在 dot 循环里插入 `ttg.async_copy_global_to_local`，让数据先落到 shared memory（`#shared` swizzled_shared 布局的 `memdesc`），再 `ttg.local_load` 读进寄存器的 `dot_op` 布局喂给 mma。这一步引入了”shared memory 布局”这个新世界——dump 里 `memdesc<2x128x64xf16, #shared, #smem>` 前导那个 `2` 就是流水线准备的多份缓冲（让”加载下一块”和”计算当前块”重叠），缓冲份数由 `num_stages` 等参数决定。

**这条演化线回答了一个容易困惑的问题**：为什么 convert_to_ttgpuir 给 dot 结果的是 Blocked，但真实 dump 里看到的是 mma？因为中间隔着一个 `accelerate_matmul`。layout 的最终形态是整条 pass 链协作的结果，convert_to_ttgpuir 只负责”先让每个 tensor 有个合法的 layout 起点”。

> accelerate_matmul、coalesce、pipeline 各自的内部机制都是大题目，本篇只点到”它们改了哪些 layout”。逐一深挖是下一篇（06 · 优化篇 A）和后续软件流水线篇的事。

### 6 LinearLayout：用线性代数统一所有布局

最后讲一个”幕后的统一抽象”。前面看到的 Blocked/DotOperand/Mma，每一种 encoding 都自带一套”如何转成 LinearLayout、如何互相转换”的逻辑——这套”各写一套”的做法在 Triton 早期就是这样，结果是**布局转换逻辑分散、易错、难组合**。

**LinearLayout** 用一个统一的数学对象来替代它们：一个整数线性映射，把 logical 坐标 `(dim0, dim1, …)` 映射到物理坐标 `(register, lane, warp, block)`。在 IR 文本里它长这样（输入维 `register/lane/warp/block`，每个 basis 是一个输出向量）：

```text
#ttg.linear<{register = [[0, 1], [8, 0], [0, 8], [64, 0]],
             lane = [[0, 2], [0, 4], [1, 0], [2, 0], [4, 0]],
             warp = [[16, 0], [32, 0]], block = []}>
```

**为什么引入它：** 把”layout”从”一堆各自为政的属性”统一成”一个线性映射”后，`convert_layout` 变成了一个纯粹的线性代数运算（矩阵复合），布局传播、合法性判断都有了统一的数学基础，不再需要为每对 encoding 单独写转换代码。源码定义见 [LinearEncodingAttr](https://github.com/triton-lang/triton/blob/0a0a6e5a3d5e3e3683683dd920ceef459798c99b/include/triton/Dialect/TritonGPU/IR/TritonGPUAttrDefs.td#L665)，转换逻辑大量集中在 `lib/Dialect/TritonGPU/IR/LinearLayoutConversions.cpp`。

**本篇的定位：** 你会在很多 pass 源码里看到 `toLinearLayout()`、`LinearLayout` 的身影（比如 §4.2 的 `TritonExpandDimsPattern` 就在用它做布局推导）——它是越来越多布局运算的底层实现。但**理解 Blocked/DotOperand/Mma 的语义**（本篇 §3 的内容）依然是读 layout 相关代码的第一道关，因为 IR 文本里挂的还是这些具名 encoding，LinearLayout目前更多藏在”它们怎么互相转换”的实现里。

### 小结

Layout 是 Triton 的灵魂，它回答”一块 tensor 数据在 GPU 上怎么分布到 warp / thread / 寄存器 / shared memory”。本篇的三条主线：

1. **encoding 是 tensor type 上的属性**——它不改变数据，只给数据一份”摆放说明书”。TTIR 的 tensor 没 layout（block 级），TTGIR 的 tensor 有 layout（thread 级），这一跳由 `convert_to_ttgpuir` 完成。
2. **matmul 用到五种 encoding**：Blocked（通用、coalesce 友好）、DotOperand（喂 mma 的输入）、NvidiaMma（mma 的输出）、SwizzledShared（shared memory 里避 bank conflict）、Slice（expand_dims 的逆）。它们各有分工，按”住寄存器还是住 shared memory”分两大类。
3. **layout 由 Conversion 框架分配**：`convert_to_ttgpuir` 用 TypeConverter 给所有 tensor 发”保守默认 Blocked”，再用合法性约束 + DotPattern 让 `tt.dot` 的 operand 走 dot_op；layout 不匹配时靠 `convert_layout` 这个”变压器”翻译。最终的 layout 形态是 convert_to_ttgpuir 之后多个 pass（coalesce、accelerate_matmul、pipeline）依次精修的结果。

读懂本篇后，打开任意一份 TTGIR，你应该能认出每个 tensor 挂的是哪种 encoding、它为什么挂这个、以及它和相邻 op 的布局怎么接上。这就是进入后续优化 pass（accelerate_matmul 怎么挑 mma 布局、pipeline 怎么安排 shared memory）的门票。

### 自测题

**1. 打开真实 matmul 的 TTGIR，`#blocked` 的 `sizePerThread = [1, 8]`。这个 `8` 是 `convert_to_ttgpuir` 挂上去的吗？如果不是，是谁、依据什么改的？**

不是。`convert_to_ttgpuir` 的默认值是 `getDefaultBlockedEncoding` 给的 `sizePerThread = [1, 1]`（每维每线程 1 个元素）。`8` 是后续 `coalesce` pass 依据 `AxisInfo` 的连续性分析，把连续维放大得到的——目的是让每个 thread 一次取 8 个连续元素、走向量化访存。

**2. 为什么 `tt.dot` 的两个 operand 必须是 `DotOperandEncodingAttr`？convert_to_ttgpuir 是怎么保证这一点的？**

因为 tensor core 指令对 operand 的物理摆放有硬性要求，通用 Blocked 布局不满足。`convert_to_ttgpuir` 在 `ConversionTarget` 里给 `tt.dot` 加了一条合法性规则（[TritonGPUConversion.cpp:81-90](https://github.com/triton-lang/triton/blob/0a0a6e5a3d5e3e3683683dd920ceef459798c99b/lib/Conversion/TritonToTritonGPU/TritonGPUConversion.cpp#L81-L90)）：两个 operand 必须都是 `dot_op` 才算合法。Conversion 框架发现 dot 非法，就用 `TritonDotPattern` 把 operand 重新分配成 `dot_op`，并在原值和新布局之间插一个 `convert_layout` 做翻译。

**3. matmul 写回 C 时有一句 `ttg.convert_layout %c : #mma -> #blocked`，紧接 `tt.store`。为什么需要这个 convert？如果删掉会怎样？**

`%c` 是 `tt.dot` 的结果，挂在 `NvidiaMma`（`#mma`）布局上——这是 tensor core 输出的摆放。而 `tt.store` 写回 global memory 时，指针是 `#blocked` 布局（coalesce 友好，相邻 thread 写相邻地址）。两套物理摆放不一致，所以必须用 `convert_layout` 把数据从 mma 摆放重排成 blocked 摆放。删掉的话，store 会按 mma 布局去写，相邻 thread 写的地址不再连续，访存不再 coalesce，性能会显著下降（语义上数据仍正确，因为 layout 只影响摆放不影响逻辑值，但编译器不会允许这种低效写法存在——convert_layout 正是显式表达这步重排）。
