RAG 分块（chunking）策略对比：五个分块器在相同文档、检索器（retriever）和 120 词上下文（context）预算下的完整证据召回率（complete-evidence recall）。

![](https://pica.zhimg.com/v2-4098a4cfe685759c0706e3a02d737558_r.jpg)

**QESChunker** (arXiv 2610.36557, Oct 27) 将分块视为有监督优化（supervised optimisation）。给定问题-证据（question–evidence，QE）对（无论人工编写还是 LLM 生成），它会挑选能够最大化最终可检索证据量的文本块边界。在不允许重叠（overlap）的情况下，目标函数在各个文本块上分解，**动态规划（dynamic programming）可以在多项式时间内找到精确最优解**。在允许重叠的情况下，目标函数是单调次模的（monotone submodular）。此时精确优化是 NP-hard 的，但贪心选择（greedy selection）具有 (1 - 1/\\sqrt{e}) 的近似保证。

**StrucChunk** (arXiv 2610.26313, Oct 19) 使用作者已经写好的结构。它将文档视为条款（provisions）组成的图，从不跨子句边界切分，**在生成 Embedding 之前**解析交叉引用（“见第 4.2 节”），并通过倒数排序融合（Reciprocal Rank Fusion）将 BM25 与稠密检索（dense retrieval）融合。在 LegalBench-RAG 上，Char-Recall@8 从 23.59% 提升到 48.18%。在一个语料库（corpus）上，Recall@5 从 0.557 上升到 0.804，作者将其中 88% 的增益归因于分块本身。

**SpectRAG** (arXiv 2610.36991, Oct 27) 不再将文本块视为相互独立的。它在文本块之上构建加权图（包含邻接关系、章节层级、共享实体、引用），通过混合搜索（hybrid search）生成种子节点，传播相关性，并在**固定的 Token 预算**下组装上下文。其目标是构建一个相关、多样、连通且充足的上下文。

**The Bottleneck Is Retrieval, Not Reading** (arXiv 2610.26951, Oct 18) 提供了诊断。在十个前沿模型和三个开源权重（open-weight）模型中，检索能够可靠地找出一部分相关文本块，但找不出多事实问题所需的*所有*文本块。分块还会剥离文档级上下文，而这些上下文原本用于解析段落之间的引用关系。

九月份的三篇论文构建了其余的背景框架：

- **Pre-retrieval Query Clustering for Adaptive Top-k** (arXiv 2609.13489) 为每个查询聚类（query cluster）选择检索深度，报告在简单聚类上 F1 提升了 36% 以上，同时 Token 减少了 14%。上下文大小是一个随查询变化的变量。
- **Parser, Chunking, and Embedding Interactions** (arXiv 2609.31660) 运行了一项包含 54 种配置的全因子研究（factorial study），发现解析器（parser）和分块器的选择存在交互作用，没有任何单一检索器能在所有场景下获胜。
- **Re-ranking and Late Interaction Drive Retrieval Quality** (arXiv 2609.38473) 在约 464,000 篇论文上比较了六个 Pipeline，发现最大的质量提升点出现在第一阶段检索之后。主演示程序中已经为此配备了一个交叉编码器重排序器（cross-encoder reranker）。

### 测试平台

语料库是一本虚构的天文台手册，特意写得像一份政策文档：

![](https://pic3.zhimg.com/v2-f872db571fa49ce9ade22b8c050ba7b2_r.jpg)

每个 QE 对将问题和精确的证据句子存储为字符串。实验平台使用针对单元起始偏移量的二分查找（binary search），将每个证据字符串映射到一个字符跨度（character span）及其覆盖的文本单元范围：

```text
 const unitAt = pos => {  
   let lo = 0, hi = units.length - 1  
   while (lo < hi) { const m = (lo + hi + 1) >> 1; if (units[m].start <= pos) lo = m; else hi = m - 1 }  
   return lo  
 }
```

解析器在后跟空白字符的 `.`、`!` 或 `?` 处切分句子，因此 "1.2-metre" 和 "Section 1.3" 保持完整。条款是指第 3 级或更深层级的任何标题，或任何编号为 `x.y` 的标题，加上其下的句子。每个条款记录其标题路径，例如 `1 Definitions › 1.3 Red-light zone`。

**所有策略的固定条件：** 文本块长度限制 L = 450 个字符，上下文预算 B = 120 个词，相同的 BM25（k_1 = 1.2，b = 0.75，停用词移除（stop-word removal），以及一个轻量级后缀词干提取器（stemmer），用于从长于四个字符的 Token 中剥离 -s、-es、-ed 和 -ing），以及相同的上下文组装器（context assembler）。

### 五个分块器

### 1、固定窗口（Fixed window）

N 个字符，带有 50 个字符的重叠，步长为 `L − 50`。这是教程中的默认设置。它会在词中间和句子中间切分。

### 2、句子窗口（Sentence window）

主演示程序使用的精确算法（`ragEngine.js` 中的 `chunkDocument()`）。它将完整的句子打包，直到达到 L 个字符。当一个文本块结束时，它会从末尾回溯完整的句子，直到用完 50 个字符的重叠预算，并用这些句子开始下一个文本块。

### 3、结构感知（Structure-aware，StrucChunk 风格）

每个条款一个文本块。文本块从不跨越条款边界，长于 L 的条款会在句子边界处切分。每个文本块获取其标题路径作为前缀，并且在建立索引时，通过追加最多 320 个被引用条款的字符，解析其中的每一个 “Section x.y” 引用：

```text
 for (const m of C.slice(start, end).matchAll(/Section (\\d+(?:\\.\\d+)+)/g)) {  
   const ti = byId.get(m[1])  
   if (ti === undefined || ti === pi || seen.has(ti)) continue  
   seen.add(ti)  
   refs.push({ id: m[1], prov: ti, text: bodyText(provisions[ti], refChars) })  
 }
```

建立索引后的文本块如下所示：

```text
 [2 Access and Arrival › 2.1 Gate hours]  
 The lower gate opens at 17:00. It closes to arriving vehicles 30 minutes  
 before the start of the dark window defined in Section 1.1. ...  
 ↳ Section 1.1 Dark window: A dark window is any period of at least 90  
 minutes between the end of astronomical twilight and moonrise. ...
```

现在，规则及其所依赖的定义成为了一个可检索单元。

### 4、QESChunker，精确动态规划

将文档视为由 n 个文本单元组成的序列。分割（segmentation）将其切分为连续的文本块，每个文本块最多 L 个字符。覆盖单元 j..i-1 的文本块的效用（utility）为：

```text
 u(j, i) = Σ_{e ∈ spans}     1[ e ⊆ [j, i) ]  
         + Σ_{q ∈ multi-ev}  1[ ∀ e ∈ E(q) : e ⊆ [j, i) ]  
         − μ                                   (μ = 0.05, a small per-chunk cost)
```

第一项奖励保持完整的证据句子。第二项奖励将多事实问题的所有证据保持在一起。目标函数是所有文本块的求和，因此最优解满足一个简单的递推关系：

```text
 best[0] = 0  
best[i] = max_{j < i, span(j, i) ≤ L}  best[j] + u(j, i)  
for (let i = 1; i <= n; i++) {  
  for (let j = i - 1; j >= 0; j--) {  
    const span = U[i - 1].end - U[j].start  
    if (span > L && j < i - 1) break  
    const v = best[j] + util(j, i)  
    if (v > best[i]) { best[i] = v; arg[i] = j }  
  }  
 }
```

内部循环在窗口超过 L 时立即停止，因此开销为 O(n \\cdot w \\cdot \\vert{}QE\\vert{})，其中 w 是每个窗口的最大单元数。在这篇文档上，最优解的目标函数值为 13.35，并且每个训练证据片段都保持完整。

### 5、QESChunker，重叠贪心（overlapping greedy）

在允许重叠的情况下，实验平台在文档长度 1.35\\times 的总索引预算下，挑选一组可能重叠的窗口。覆盖函数计算新覆盖的证据片段、新完成的多事实问题，以及每个新覆盖单元 \\alpha = 0.02 的权重，以便对整个文档建立索引。该函数是单调次模的，因此实验平台运行成本效益贪心算法（cost-benefit greedy）：

```text
 while (true) {  
  let bestC = null, bestR = 0  
  for (const c of cands) {  
    if (spent + c.cost > budget) continue  
    const g = gain(c)           // 给定已选内容下的边际覆盖增益  
    if (g <= 0) continue  
    const r = g / c.cost        // 每字符收益  
    if (r > bestR) { bestR = r; bestC = c }  
  }  
  if (!bestC) break  
  chosen.push(bestC); spent += bestC.cost  
  // 标记被 bestC 覆盖的片段、问题和单元  
 }
```

这里要说明的是：如果没有窗口大小的下限，成本效益贪心算法会坍缩成单句文本块，因为单个证据句子具有最高的每字符收益。因此，排除了短于 0.5 \\cdot L 的候选项。预算用尽时仍未覆盖的单元会打包到间隙文本块（gap chunks）中，以保持可搜索性。

### 两种检索模式

### 扁平 Top-k（Flat top-k）

按 BM25 对文本块进行排序，然后按排序顺序填充词数预算。组装器会跳过任何会超出预算的文本块，以及任何新 Token 比例低于 30% 的文本块（这是一个近似重复过滤器，对重叠分块器很重要）：

```text
 for (const i of order) {  
  const c = chunks[i]  
  if (used + c.words > budget) continue  
  const t = toks(c.text)  
  const novel = t.filter(x => !seen.has(x)).length / Math.max(1, t.length)  
  if (picked.length && novel < 0.3) continue  
  picked.push(i); used += c.words  
  t.forEach(x => seen.add(x))  
 }
```

注意这里使用的是 `continue` 而不是 `break`：一个放不下的大文本块会让位给一个较小、排名较低的文本块来占用空间。这个细节解释了下文的一个结果。

### 文本块图（Chunk graph，SpectRAG-lite）

在文本块之上构建一个包含四种边类型的无向加权图：

![](https://pic3.zhimg.com/v2-4b491c1a72974115a71796385fc8e166_r.jpg)

然后从前 3 个 BM25 种子节点运行个性化 PageRank（personalised PageRank），重启向量（restart vector）按 BM25 分数加权，重启概率为 0.5，迭代 25 次：

```text
 p₀[i]   = s[i] / Σ_seed s          for the 3 seeds, 0 elsewhere  
 p ← 0.5 · p₀ + 0.5 · Wᵀ D⁻¹ p      (25 iterations)  
 score[i] = 0.6 · s[i]/max(s) + 0.4 · p[i]/max(p)
```

最终排名将归一化的 BM25 与归一化的 PageRank 权重（mass）混合，并通过相同的预算组装器。两种模式之间唯一改变的是提供文本块的顺序。

### 结果 1：部分召回率虚高

![](https://picx.zhimg.com/v2-be123dad28891ac38007cbab5a44272b_r.jpg)

留出集（held-out）问题，L = 450，B = 120 词：

![](https://pic3.zhimg.com/v2-2ffd5a5cbac7f7b9c28ddccb989aad74_r.jpg)

每种策略都能为 69–92% 的问题找到*一些内容*。默认分块器组装出*完整*答案的比例不到四分之一。如果按部分命中来评估 Pipeline，它看起来会很健康，但实际上四分之三的多事实回答都建立在不完整的证据之上。

“平均上下文词数（avg context words）”列展示了第二个效应。窗口分块器在 120 词的预算中留下了 30–48 词未使用，因为下一个排名的 60–70 词窗口放不下了。小文本块能更高效地填满预算。

### 结果 2：上下文稀缺时，结构化方法获胜

条款大小的文本块平均为 285 个字符，而窗口分块器约为 400 个字符。在 120 词的限制下，可以放入两到三个条款，但只能放入一个大窗口。答案分布在两个地方时，两个小而精确的片段胜过一个碰巧包含一半答案的大片段。

预算扫描（budget sweep，留出集、扁平检索、L = 450）使这种权衡变得直观可见：

![](https://pic2.zhimg.com/v2-2421331d1272c3a745375b8491739673_r.jpg)

![](https://pic3.zhimg.com/v2-44e5680e9c0659b8b8f8debe870146de_r.jpg)

在 40 词时，结构感知是唯一超过 10% 的策略。到 300 词时，大窗口分块器追了上来，到 400 词时超过了它，而结构感知策略在 77% 处趋于平稳。在预算充裕的情况下，几乎任何分块器最终都能把证据拉进来，因为发送了文档的很大一部分。**最佳分块器取决于预算，而正确的预算取决于查询**，这正是自适应 Top-k（adaptive top-k）论文从另一个方向提出的论点。结构感知策略在 77% 处的平台期并非分块失败，它剩余的未命中属于检索失败（见结果 5）。

### 文本块大小扫描（Chunk-size sweep）

固定 B = 120 并改变 L，从另一侧展示了相同的机制：

![](https://picx.zhimg.com/v2-4c012b64d0a8ef6422bbab7ac36df3c7_r.jpg)

这里有2点需要说明：

1. **结构感知策略稳定在 62–69%。** 几乎每个条款都短于 450 个字符，因此 L 几乎不改变其文本块。它的粒度来自文档，而非超参数（hyperparameter）。
2. **在** L = 800 **时，固定窗口和句子窗口得分为 0%。** 一个 800 字符的窗口大约是 130 个词，大于 120 词的预算，因此组装器连一个文本块都放不下。不同的人分别调整文本块大小和上下文预算时，就会出现这种失败。

在 L = 250 时，每个分块器都变得更好，差距也在缩小。较小的文本块表现得更像条款。代价是索引更大且对于任何需要周围上下文的阅读器来说碎片更多。

### 结果 3：可证明最优的分块器排在最后

QESChunker 的精确 DP 对于其目标函数是最优的。但它在留出集问题上仍仅获得 **15%**，在**用于训练它的 12 个问题上获得 58%**，低于普通固定窗口的 75%。

![](https://pic3.zhimg.com/v2-cbe88789349052a07a833b738f67a4c2_r.jpg)

![](https://pic1.zhimg.com/v2-8b3bc98c2e5660d5a9c3de43faf0c3d2_r.jpg)

边界图展示了其中的机制。效用函数奖励完全位于文本块内部的证据句子，而对它们周围的文本只字未提。保持一条规则完整的最廉价方法是在它*紧前面*切分。在手册中，规则紧前面的那一行是它的标题 `### 5.2 Emergency kit`。标题最终落在了前一个文本块的末尾，而规则开启了下一个文本块。证据完整性：100%。但是关于 "emergency kit" 的关键词查询现在匹配的是包含孤立标题的文本块，而非包含规则的文本块。因此 DP 中有 0% 的文本块以标题开头。

**消融实验（Ablation）：标题路径前缀能挽救它吗？** 实验平台可以为来自每个分块器的每个文本块加上它所触及的每个条款的标题路径前缀（即 “contextual headers” 开关）。留出集、扁平检索下的结果如下：

![](https://pic3.zhimg.com/v2-2502fa661a42cca3592b16ad92fcf0a4_r.jpg)

这并不能挽救 DP。前缀告诉 BM25 一个文本块属于哪个条款，但包含孤立标题的文本块在其前缀中也获得了该条款的名称，因此两个文本块仍然在争夺同一个查询。前缀还会在每个文本块上消耗预算词数。只有窗口已经倾向于从标题开始的重叠变体从中受益。

QESChunker 使用固定的**混合**检索器进行评估，而稠密 Embedding 对标题落点位置的敏感度要低得多。这对于任何移植该思想的人来说是一个教训：**优化目标必须对实际运行的检索器进行建模**。完整的证据和可查找的证据是不同的目标，而分块器只优化写下来的那个目标。一个实用的修复方法是在 u(j, i) 中添加一项，用于评估训练问题在实际检索器下是否能检索到该文本块，或者禁止在标题及其第一句话之间切分。

重叠允许贪心过程选择既从标题开始*又*覆盖证据的窗口。它在未被告知文档具有结构的情况下，在留出集上达到了 46%，在训练问题上达到了 83%。在没有清晰标题的文档（转录文本、电子邮件往来、扫描的 PDF）上，这是我会选择的版本。训练集与留出集之间的差距（83% 对 46%）是对每个有监督分块器的警示：索引是围绕预先想到的那些问题来塑造的。

### 结果 4：定义作为中心节点（hubs）时，文本块图能提供帮助

切换到图检索将结构感知分块从 62% 提升到了 **69%**，而对其他分块器几乎没有改变。

![](https://pic1.zhimg.com/v2-cad4627fc4aeb8b3d70ab18ff4c7c7ac_r.jpg)

有一个问题展示了这种增益的来源：

![](https://picx.zhimg.com/v2-f524d576bade20e1937522a7a86ca02b_r.jpg)

*“圆顶地板上允许使用闪光灯拍照吗？（Is flash photography allowed on the dome floor?）”* 需要两个事实：相机规则（§4.3，红光区内任何地方都禁止使用闪光灯）和定义（§1.3，红光区*覆盖圆顶地板*）。扁平 BM25 将定义排在第三位。由于它有 52 个词，在前两次挑选之后就放不下了，因此组装器的 `continue` 让一个关于望远镜的较短但无用的文本块占用了空间。

在图模式下，§1.3 定义文本块是一个**中心节点**：另外两个条款交叉引用了它，并且它与更多条款共享词汇。PageRank 权重从种子节点流入其中，其混合分数超过了望远镜文本块，从而使答案变得完整。

![](https://pic4.zhimg.com/v2-8037816f0bc6745af809d34de5e48d29_r.jpg)

**消融实验：关闭交叉引用解析。** 结构感知图模式从 69% 跌回 62%，与扁平检索相同。图的增益来自 `xref` 边，这是文档提供的最可信的边。

**在窗口分块器上，图没有帮助，有时甚至有害。** 句子窗口从 23% 下降到 15%。在混合了多个主题的大窗口之间，词汇边（lexical edges）主要将相关性传播给已找到内容的邻居。由于最终分数的 40% 来自 PageRank，邻居节点的排名可能会超过正确的 BM25 挑选项，并取代它在预算中的位置。SpectRAG 自己的摘要中也指出了早期精确率（early precision）和领域依赖性方面的权衡，这个玩具实验复现了这一点。

### 结果 5：它们都没能解决的问题

![](https://pic4.zhimg.com/v2-6ec9f1e04706af848a1138c28c49d4fd_r.jpg)

*“我 8 岁的孩子要来。露台上适用什么规则？（My 8-year-old is coming. What rule applies on the terrace?）”* 每种策略都漏掉了这两个证据句子。规则写的是 “10 岁以下儿童（children under 10）”，而问题写的是 “8 岁（8-year-old）”。经过分词（tokenisation）后，问题变成了 `[8-year-old, com, rule, appli, terrace]`，而规则句子完全不包含这些 Token。结构感知分块走完了一部分路：解析后的 §1.3 引用将 "terrace" 带入了儿童规则所在的文本块，使其获得了 1.18 分而非 0 分。但是 "terrace" 也出现在其他几个条款中，并且它们的排名高于该文本块。没有任何分块策略能弥合 "8-year-old" 和 "under 10" 之间的鸿沟。这需要稠密或混合检索器、查询重写（query rewriting），或者能够理解问题的重排序器（reranker）。

因此，该实验平台旨在补充主 Pipeline，而非将其替代。主 Pipeline 拥有 MiniLM Embedding、混合融合（hybrid fusion）和交叉编码器重排序器。**分块决定了什么*可以被*检索。检索器决定了什么*实际被*检索。** 本月的论文主要讨论的是这句话的前半部分。

### 实际应该怎么做

1. **测量完整证据召回率，而非命中率。** 为语料库编写 20 个多事实问题，标记证据句子，并追踪*所有*证据句子同时进入上下文的频率。将其与部分召回率一起报告。两者之间的差距就是需要关注的数字。
2. **如果文档有结构，就按结构分块。** 在标题和编号子句处切分，加上标题路径前缀，并在建立索引时解析显式的交叉引用。这种方法具有确定性、成本低且可解释，在本文的实验中它是最大的单一制胜点。
3. **如果文档没有结构，使用带重叠的有监督分块器。** 用 LLM 生成 QE 对，针对它们优化边界，在*不同的*问题上进行评估，并将实际使用的检索器放入目标函数中，或者至少禁止在标题及其第一行之间切分。
4. **一起调整文本块大小和上下文预算。** 针对每个文本块大小，绘制完整召回率随预算变化的曲线。如果一个文本块可能超过预算，它就永远无法被检索到。如果曲线发生交叉，那么“最佳分块器”就取决于发送多少上下文，而这应该随查询而变化。
5. **仅在边可信的情况下添加文本块图。** 交叉引用、文献引用和章节层级是好的边。大文本块之间的词汇相似度通常不是。
