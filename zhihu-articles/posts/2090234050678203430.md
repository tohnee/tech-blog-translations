> 系列第三篇・Conclave 重构手记 [承接上文](https://zhuanlan.zhihu.com/p/2090233130804429064) ：当一套自研的议会制多 Agent 系统跑通核心流程之后，架构演进的下一个路口，永远是「自研到底」与「拥抱通用框架」的博弈。

做过 Agent 编排系统的开发者，大概都会遇到同一个灵魂拷问： 当自研的工作流管线从 3 个阶段涨到 6 个阶段，从简单串行变成 DAG 并行、回退循环、动态路由，维护成本指数级上升的时候，到底该不该放弃自研，迁移到 LangGraph 这类通用图编排框架？

一边是社区成熟的状态机、检查点、并行调度、可视化工具，能一次性清掉大量技术债； 一边是自己打磨的质量门禁、上下文治理、证据链机制，这些领域核心能力一旦套进通用框架，很容易被抽象层 “磨平”，最终丢掉产品最核心的竞争力。

最近我们围绕 Conclave 编排层重构，拉了三个立场完全对立的视角做了一次完整的三方研讨。没有谁说服谁，最终的答案也不是简单的 “迁” 或 “不迁”，而是走出了第三条路 —— **混合架构** 。

### 一、三个阵营：一场关于架构本质的对峙

讨论的起点很明确：当前自研的六阶段议会管线已经跑通全流程，但组件耦合、调试困难、扩展成本高的问题开始显现；与此同时 LangGraph 为代表的图编排框架日渐成熟，同时免费长上下文大模型也带来了新的变量。

围绕这个现状，三种典型的工程立场完整呈现了出来。

### 迁移派：通用框架才是答案，技术债该清了

支持全面迁移的一方，核心论点非常清晰： 自研编排的 Runner 主循环已经承担了状态管理、调度、路由、检查点、错误处理五重职责，复杂度已经触及手写框架的天花板。这些 DAG 调度、状态持久化、动态路由的能力，本质上都是分布式系统的通用问题，不是多智能体决策的核心竞争力。

用 LangGraph 的声明式状态机重新表达六阶段管线，只需要几十行代码就能定义清楚拓扑；质量门禁从嵌套的 if-else 变成独立的条件边函数；检查点持久化、增量快照、时间旅行这些调试能力，社区已经做了成熟的方案。

一句话总结： **领域知识留下，编排基础设施这种重复造轮子的事，交给通用框架。**

### 坚守派：领域核心不能丢，框架解决不了本质问题

坚持自研的一方，则精准命中了迁移派的盲区： 通用框架的核心抽象是 “泛型状态 + 条件边”，它不区分 “普通的条件分支” 和 “不可绕过的质量门禁”。在框架里，所有节点都是平级的，所有边都是可选的 —— 但对于一套以 “证据诚实、决策可追溯” 为核心价值的系统来说，有些门禁是强制性的，是不能被绕过的。

更关键的是，自研的上下文分层治理、阶段白名单保护、证据校验机制，这些是经过大量场景打磨出来的领域核心资产。迁移到通用框架，等于把这些核心逻辑打散塞进各个节点里，看似换了框架，实则耦合问题只是换了个地方存在，根本没有解决。

一句话总结： **迁移不是重构，是重写核心资产。框架解决不了耦合，只是把耦合换了个形状。**

### 混合派：不是二选一，是分层负责

第三种思路跳出了 “非迁即守” 的二元对立： 为什么要整个系统全部迁移，或者全部死守？编排基础设施和领域决策逻辑，本来就是两个层面的东西。

- 图拓扑、路由、检查点、并行执行，这些是 **非差异化的基础设施** ，谁做都一样，通用框架做得更好，就用框架的；
- 质量门禁、上下文治理、证据校验、阶段白名单，这些是 **差异化的领域核心** ，是产品的竞争力，必须自研，牢牢握在自己手里。

中间用一层薄适配器衔接：每个 LangGraph 节点本质上是一个适配器，负责输入输出校验、日志埋点、指标采集，然后调用自研的领域服务。领域服务对上层框架完全无感知，可以独立测试、独立迭代。

一句话总结： **框架管流程怎么走，自研管决策怎么做，DTO 管数据怎么传。三者各司其职。**

### 二、六个维度：真正的差距在细节

三方的对峙没有停留在理念层面，我们沿着六个核心维度拆解下去，才发现很多看似的共识，在细节处全是分歧；而很多看似对立的立场，底层其实有共同的认知。

### 1. 编排层：谁是主人，谁是工具

这是最核心的战场。 迁移派认为编排层就应该完全交给状态图，所有业务语义都用节点和边来表达； 坚守派认为编排层必须有强制力，质量门禁是高于流程的存在，不能和普通分支平级； 最终混合派的方案胜出： **LangGraph 承载图拓扑，但不承载业务规则。** 所有强制性的质量门禁、阶段约束，都下沉到节点内部的领域服务层，由适配器层触发，而不是由框架的条件边决定。框架只负责 “到哪个节点”，节点内部负责 “能不能过”。 这样既用上了框架的路由和检查点能力，又保住了门禁的强制性 —— 框架层面永远无法绕过节点内部的校验。

### 2. 组件拆分：边界比拆分本身更重要

三方在 “要拆分” 上达成了完全共识，但拆分的逻辑完全不同。 迁移派是按框架的节点拆，每个节点一个模块； 坚守派是按业务领域拆，编排逻辑和业务逻辑绑定； 而我们最终认可的拆分原则是： **按依赖方向拆，所有跨层调用都走 DTO 契约。** RAG 检索从阶段逻辑里抽出来，变成独立的检索服务，编排层只消费检索结果 DTO； 工具调用从 Agent 逻辑里抽出来，做成统一的工具适配层，所有调用走请求 / 响应 DTO； 评分判定逻辑从调度路径里抽出来，做成可插拔的评分器接口，编排层只调用判定结果。 拆分的目的不是为了迎合框架，而是为了解耦。只要边界清晰，上层用不用框架、用什么框架，都不会伤到核心逻辑。

### 3. 数据契约：“约定式校验” 是最大的坑

这一点是本次研讨最有价值的结论之一。 自研管线时代，我们有阶段间的输入输出契约，但本质上是 “约定式” 的 —— 开发者记得加校验就加，忘了加，脏数据也能流向下一阶段。 迁移派的方案是把 DTO 直接写进 State 里，靠框架类型检查兜底；但问题在于，框架的类型检查是编译时的，LLM 输出的结构化数据是运行时的，脏数据依然能进来。 最终我们采用了 **“DTO 膜” 方案** ： 在每个节点的入口和出口，都加一层强制校验。入口 InputDTO 校验，出口 OutputDTO 校验，像一层半透膜，只允许合法数据通过。LLM 输出统一走 “JSON 解析→DTO 校验→通过则合并→失败则重试修正” 的路径，完全不依赖开发者自觉。 这层薄薄的校验膜，解决了多 Agent 系统里最头疼的问题：数据一致性。

### 4. 免费大模型：定位错了就是灾难

免费长上下文大模型的出现，是这次重构的新变量。但三方都同意一个原则： **免费模型不能碰核心决策。** 它的定位被严格限定在三层：

- 最上层：路由分类、议题澄清这类轻量判定，快路径直接返回；
- 中间层：工具调用预校验、长文本信息抽取、证据初步聚合；
- 最底层：格式校验、结构化输出兜底、错误重试。 核心的八维质量评分、最终仲裁裁决、强证据判定，必须由主模型完成。免费模型只做 “可错可重试” 的工作，绝对不进入需要可追溯的强判定环节。 毕竟，免费的东西，永远是最贵的。

### 5. 可观测性：两种追踪，一套都不能少

调试难是触发这次重构的直接原因，但讨论后我们发现：框架解决不了所有调试问题。 通用框架的检查点机制，擅长回答 “哪个节点、状态变了什么”，是结构化的追踪； 而自研的日志总线、事件链路，擅长回答 “为什么会变成这样、决策依据是什么”，是语义化的追踪。 两者不是替代关系，是互补关系。 最终的方案是用 checkpoint_id 把两套追踪关联起来：先通过框架的可视化图定位到哪个节点出了问题，再通过节点关联的语义日志，定位到具体的决策过程和证据依据。 一个定位问题，一个解释问题。缺一不可。

### 6. 技术债：哪些是资产，哪些是真的债

重构最容易犯的错，就是把孩子和洗澡水一起倒掉。 这次讨论我们明确划清了一条线：

- **必须保留的资产** ：RAG 全栈能力、沙箱隔离体系、自研工程化框架、八维质量评分标准、已有的架构决策约束。这些是核心竞争力，换什么框架都不能丢。
- **必须清理的技术债** ：RAG 与阶段逻辑渗透、工具调用与 Agent 执行混杂、判定逻辑内联、接口层不规范、阶段间硬编码。这些是耦合的根源，必须拆。 很多人分不清 “自研的核心能力” 和 “自研的技术债”。 判断标准很简单： **能带来差异化价值的，是资产；只是重复实现通用功能的，是债。**

### 三、最终方案：混合架构与渐进式迁移

综合三方的论证，我们最终选择了混合架构方案，以及一条 12 周的渐进式迁移路线。

### 四层混合架构模型

整个系统从下到上分成四层，职责边界清晰：

1. **基础设施层** ：RAG、沙箱、LLM、缓存，原样保留，通过服务接口向上提供能力；
2. **领域核心层** ：质量门禁、上下文治理、证据校验、评分器，全部提取为独立服务，是整个系统的核心；
3. **节点适配层** ：每个节点都是一个薄适配器，负责 DTO 校验、日志、指标、调用领域服务，是框架和核心之间的防腐层；
4. **编排拓扑层** ：用 LangGraph StateGraph 定义六阶段拓扑、条件路由、检查点、并行执行，只负责流程调度。

这就是我们说的 “节点即适配器” 模式。框架永远碰不到核心逻辑，核心逻辑也不需要知道上层用的是什么框架。哪天想换框架了，只需要重写适配层，领域服务一行都不用动。

### 灰度迁移：可进可退，才叫工程

重构最大的风险，从来不是方案本身，而是一刀切切换。 我们把迁移拆成了四个阶段，每个阶段都有独立的灰度开关和回滚能力：

- **Phase 0：契约定义** ：先不动代码，只定义所有模块边界的 DTO 契约。纯增量，零风险。
- **Phase 1：服务提取** ：把质量门禁、上下文治理这些核心逻辑从管线里抽成独立服务，旧管线通过 DTO 调用。可随时切回直连。
- **Phase 2：框架引入** ：接入状态图框架，先迁移最简单的澄清阶段，小流量灰度验证。出问题一键切回旧管线。
- **Phase 3：逐阶段迁移** ：每周迁移一个阶段，每个阶段独立灰度、独立回滚。
- **Phase 4：全量切流** ：所有阶段迁移完成，全量切流，清理旧代码，更新架构决策。

回滚的边界永远是稳定的 DTO 契约。只要契约不动，任何一步都能退回去。 这才是工程级重构该有的样子：不是毕其功于一役，而是步步为营，可进可退。

### 四、最后：架构的本质是取舍

写到最后，其实想聊点技术之外的东西。 很多人做架构，喜欢追新，喜欢 “最先进的方案”。听说 LangGraph 火，就想全量迁过去；听说新框架好用，就想全部重写。 也有很多人喜欢死守，觉得自研的什么都好，通用框架都是垃圾，重复造轮子也在所不惜。

但真正的工程实践，从来都不是选 “最好的”，而是选 “最合适的”。 通用框架有通用框架的优势：社区验证、生态完善、文档齐全，解决的是 80% 的通用问题； 自研核心有自研核心的价值：贴合业务、控制力强、差异化竞争，解决的是 20% 的核心问题。

好的架构，不是一边倒，而是找到那条分界线。 把通用的东西交给通用框架，把核心的东西攥在自己手里。中间用清晰的契约和适配层隔开，既能享受生态的红利，又不会丢掉自己的立身之本。

对于 Conclave 来说，这次重构也不是终点。 它只是为下一步 —— 记忆系统的落地、自进化能力的实现，打下一个更稳固的架构底座。毕竟，当一套系统要从 “任务驱动的议会” 走向 “有记忆、会成长的智能体”，架构的弹性，决定了它最终能走多远。

历史的车轮滚滚向前，技术的演进永不停歇。我们能做的，就是在每一个路口，都做出当下最清醒的选择。
