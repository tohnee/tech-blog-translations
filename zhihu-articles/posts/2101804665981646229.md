## 一、它解决什么问题

用 Claude Code 写代码的人都遇到过：开三个终端跑三个 agent，然后——

- 两个 agent 改同一个文件，互相覆盖
- 没人记得「谁在干什么」，问一圈才发现两件事是同一件事
- agent 说「做完了」，你一问，其实没跑验证
- 会话一断（压缩/重启），上下文全丢，接手的人从零开始

**cc-team 是一套多智能体协作的「台账+调度」框架**：把人类团队的站会、任务卡、代码评审、合并流程，做成 agent 之间可执行的协议。一个 PM 会话派卡，若干 worker 会话领卡干活，全部状态落文件——不是聊天记录，是台账。

## 二、核心机制

| 机制 | 干什么 | 对应人类团队里的什么 |
| --- | --- | --- |
| 任务卡台账（cards DAG） | 每张卡有状态机：立卡→认领→交卷→验收→合并，卡间依赖成图 | 看板/任务系统 |
| 唯一认领（claim） | 一张卡同时只有一个 worker，认领写进台账原子字段 | 站会口头认领，但机器强制 |
| worktree 多道并行 | 每个 worker 在独立 git worktree 写代码，互不踩文件 | 一人一分支 |
| 验收判据先行 | 立卡时必须写「操作/输入/预期输出」三要素，判据跑不通不准开卡 | DoD（Definition of Done） |
| 会话退出钩子 | worker 会话结束自动跑验收命令，绿了才进合并火车 | CI 门禁 |
| 合并火车 | 多张绿卡按序合入主干，冲突计数上报 | 合并队列 |
| 保险丝/看门 | 心跳超阈自动报警、STOPLOSS 连拒即停 | on-call 告警 |

## 三、上手体验

裸跑 `cc` 进六步向导：**探测 → 问需 → 出方案书 → 你回「确认」→ 批量立卡 → 起工位+实时播报**。之后你只需要看播报：立卡、认领、并行编码、验收、合并，每个关键节点推一条消息。

## 四、我们踩过的坑（这套机制的由来）

这套东西不是设计出来的，是被真实事故逼出来的：

- **静默假完成**：worker 报告「已完成」但从未跑验证 → 于是有了「判据先行 + 退出钩子强制跑」
- **重复认领**：启动器失联窗口里一张卡被换手上 18 次 → 于是有了 claim 原子计数 + 高换手亮色告警
- **会话记忆当台账**：PM 靠聊天记录记排队任务，上下文一压缩全忘 → 于是「任何待办必须先落文件，会话文本是易失存储」
- **报警无人认领**：报警发了 23 小时没人看 → 于是分级升级：30 分钟叫值班，60 分钟直达业主信箱

README 里把这些写成了「四痛点」章节，每一条都有对应的机制回收。

## 五、FAQ

**Q：和 LangGraph / CrewAI 这类多agent框架什么区别？**

A：它们管「单次工作流编排」；cc-team 管「常驻团队」——卡台账跨会话续存、断点恢复、验收合并、异常升级。我们内部评审过 LangGraph 作底层运行时（checkpoint 解决状态续存），但任务卡语义、认领纪律、合并火车是我们的协议层。

**Q：只能配 Claude Code 吗？**

A：协议是文本台账+git，任何能读写文件、跑命令的 agent 运行时都能接；我们实测基座是 Claude Code 无头模式（`-p` 工人：只读记忆、点名才写，配显式学习闭环补自动攒经验的缺口）。

**Q：生产可用吗？**

A：这套框架在本机跑了多周、管过几十张真实卡（本文三篇 CSDN/知乎文章就是它的产物链）。但它是「我们团队的形状」，通用化文档还在补，issue 欢迎。

## 六、诚实的局限

- 重度依赖 git worktree + 本地 CLI，非 Windows/WSL 混合环境需自适配
- 验收判据质量决定整套机制上限——垃圾进垃圾出
- 单人小团队（≤2 个 agent）用它有点重

如果你觉得「AI 员工管起来比管人还累」，这套台账协议值得抄。仓库点个 Star，坑清单都在 README 和 docs 里。
