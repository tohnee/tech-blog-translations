> 上一篇《B200 单卡跑 Qwen3-8B》得出一个推论：高并发时，decode 的瓶颈从读权重变成了读 KV Cache。如果这个推论成立，把 KV Cache 从 BF16 换成 FP8 就应该带来明显提速。这篇先写下预测，再做实验验证。结果是：方向对了，幅度只有预测的一半；中途还冒出一个异常，我第一次给出的解释被实验推翻了；最后又顺带发现，常用的固定长度压测会高估真实性能。<br>

![](https://pic4.zhimg.com/v2-d8eeb104b0646b9410cd7030d66fa191_r.jpg)

- **吞吐**：并发越高，FP8 KV Cache 的收益越大。并发 256 时 **+35%**，BF16 在这个并发下吞吐已经开始下降，FP8 还在上升。低并发（1–4）时反而 **慢约 5%**。
- **容量**：KV Cache 容量从 105.8 万 token 翻倍到 211.5 万 token。
- **预测偏差**：TPOT 的改善只有预测的一半左右。原因是 FP8 模式下 attention kernel 读取 KV Cache 的有效带宽只有约 2.8 TB/s，而 BF16 约 4 TB/s。省下的字节，有一部分被量化和反量化的开销吃掉了。
- **一个虚惊**：固定长度压测中，FP8 的 P99 TTFT 更差。原因不是 kernel，而是请求整批同步到达，换成长度随机的负载后差距消失。
- **精度**：GSM8K 全部 1,319 题，两者准确率都是 87.6%。逐题配对比较，McNemar 检验 p = 1.0，没有观察到差异。
- **附带发现**：同样是 BF16 并发 64，换成长度随机的负载后，吞吐下降 17%，P99 TTFT 几乎翻倍。**用固定长度压测做容量规划会偏乐观。**

## 1. 实验设计

| 项目 | 配置 |
| --- | --- |
| 硬件 | B200 × 2（BF16 服务在 GPU 0，FP8 服务在 GPU 1，同一台机器） |
| 软件 | vLLM 0.30.0，Qwen3-8B（BF16 权重） |
| 唯一变量 | --kv-cache-dtype fp8 |
| 负载 | random 数据集，输入 1024 / 输出 256，并发 1–256 |
| 重复 | 每组 3 次，取中位数；压测依次执行，不同时跑 |

## 2. 先写下预测

上一篇的模型是：**TPOT ≈ 每步读取的字节数 ÷ 有效带宽（约 4 TB/s）**。FP8 把每个 token 的 KV 从 144KB 降到 72KB，每个请求的 KV Cache 从约 0.17GB 降到约 0.085GB。

| 并发 | BF16 实测 TPOT | FP8 每步读取量 | FP8 预测 TPOT |
| --- | --- | --- | --- |
| 1–16 | 3.9–4.4 ms | 基本不变 | 基本不变 |
| 64 | 6.7 ms | 16.4 + 5.4 = 21.8 GB | 5.0–5.5 ms |
| 128 | 9.7 ms | 16.4 + 10.9 = 27.3 GB | 6.5–7.5 ms |
| 256 | 16.8 ms | 16.4 + 21.8 = 38.2 GB | 10–11 ms |

## 3. 实测结果（每组 3 次中位数）

| 并发 | BF16 吞吐 | FP8 吞吐 | 变化 | BF16 TPOT | FP8 TPOT | FP8 预测 TPOT |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 251 | 236 | −6% | 3.9 | 4.1 | 不变 |
| 4 | 949 | 902 | −5% | 3.9 | 4.1 | 不变 |
| 16 | 3,293 | 3,291 | 0% | 4.4 | 4.4 | 不变 |
| 32 | 5,656 | 5,820 | +3% | 5.0 | 4.8 | — |
| 64 | 8,520 | 9,142 | +7% | 6.7 | 6.1 | 5.0–5.5 |
| 128 | 11,457 | 12,666 | +11% | 9.7 | 8.3 | 6.5–7.5 |
| 256 | 11,003 | 14,844 | +35% | 16.8 | 14.0 | 10–11 |

吞吐单位为 tok/s，TPOT 单位为 ms。

**方向对了**：收益随并发单调增大，符合"高并发时读 KV Cache 是瓶颈"的推论。**幅度不对**：TPOT 的实测改善大约只有预测的一半。

## 4. 预测错在哪

看"每多加 1 个请求，TPOT 增加多少"（用并发 16 到 256 这一段估算）：

|  | BF16 | FP8 |
| --- | --- | --- |
| 每个请求带来的 TPOT 增量 | 0.052 ms | 0.040 ms |
| 其中读 KV Cache 的理论耗时（按 4 TB/s 计算） | 0.043 ms | 0.021 ms |

- **BF16 的模型基本成立**：每个请求带来的增量里，约 80% 可以用读 KV Cache 解释。
- **FP8 的读取量减半了，增量却只减少了 23%**。假设剩下那部分开销两边相同，可以反推出 FP8 模式下 attention 读取 KV Cache 的有效带宽只有约 **2.8 TB/s**。

日志给出了线索。开启 FP8 KV Cache 后，FlashInfer 打印的是：

```text
BF16: prefill=torch.bfloat16,      decode=torch.bfloat16,      kv_cache_dtype=torch.bfloat16
FP8:  prefill=torch.float8_e4m3fn, decode=torch.float8_e4m3fn, kv_cache_dtype=torch.float8_e4m3fn
```

**不只是 KV Cache 用 FP8 存储，Query 也被量化成了 FP8，整个 attention 都在 FP8 下计算。** 每一步都要额外做量化和反量化，这能解释两件事：低并发时 FP8 反而慢约 5%，以及高并发时有效带宽偏低。

一个参数背后，换的是一整条 kernel 路径。这也说明 attention kernel 还有优化空间：省下的字节还没有全部变成速度。

## 5. 一个异常，和一次被推翻的推测

固定长度压测里，FP8 的 P99 TTFT 在并发 64 和 128 时明显更差：

| 并发 | BF16 三次 P99 TTFT | FP8 三次 P99 TTFT |
| --- | --- | --- |
| 64 | 457 / 417 / 589 ms | 628 / 594 / 753 ms |
| 128 | 819 / 606 / 1,086 ms | 1,448 / 1,353 / 1,226 ms |

并发 128 时两组数字没有重叠，不是测量误差。

**第一个推测（错了）**：BF16 日志里有 `Using TRTLLM prefill attention (auto-detected)`，FP8 日志里没有。于是我推测 FP8 模式下 prefill 退回了更慢的 kernel。

**验证**：把输出长度设成 1，只测 prefill：

|  | BF16 | FP8 |
| --- | --- | --- |
| prefill 吞吐 | 84,872 tok/s | 84,022 tok/s |
| 平均 TTFT | 747 ms | 755 ms |

prefill 速度两边一样，推测被推翻。**日志里少了一行，不等于性能有差别。**

**第二个推测（成立）**：`vllm bench serve` 的 random 负载里，每个请求的输出长度完全相同，所以同一批请求几乎同时结束，压测工具会立刻一次补上一整批新请求。64 个请求同时做 prefill，共约 6.5 万 token，而每一步最多处理 16,384 个 token，排在最后的请求就要多等几轮。FP8 的 decode 更快，批次同步可能更整齐，尾部等待也就更明显。

**验证**：加上 `--random-range-ratio 0.5`，让输入和输出长度在 50%–150% 之间随机变化：

| 长度随机 | BF16 | FP8 |
| --- | --- | --- |
| c=64 P99 TTFT | 859 ms | 870 ms |
| c=128 P99 TTFT | 1,660 ms | 1,638 ms |
| c=64 吞吐 | 7,108 | 7,443（+5%） |
| c=128 吞吐 | 9,242 | 9,925（+7%） |

TTFT 的差距消失了，FP8 在吞吐上的优势仍在。**结论：这是固定长度负载造成的现象，不是 FP8 本身的问题。**

## 6. 附带发现：固定长度压测会高估性能

同样是 BF16、并发 64：

| 负载 | 吞吐 | P99 TTFT |
| --- | --- | --- |
| 固定长度 | 8,520 tok/s | 457 ms |
| 长度随机 | 7,108 tok/s（−17%） | 859 ms（×1.9） |

真实流量里，请求随时进出，prefill 会持续插进 decode 的批次里，互相干扰比整批同步时更严重。**做容量规划时，应该使用接近真实分布的负载，最好直接回放线上请求的长度分布。** 上一篇里"单卡并发 64–96"的建议，在长度随机的负载下需要下调。

## 7. 精度

FP8 模式下连 Query 都被量化了，精度必须验证。

- **先测了前 500 题**：BF16 91.0%，FP8 89.2%，差 1.8 个百分点。但两边的标准误差各有约 ±1.3 个百分点，这个差距只相当于约 1 个标准差，不能下结论。
- **再测全部 1,319 题，并逐题配对比较**：

|  | 结果 |
| --- | --- |
| BF16 准确率 | 87.6% |
| FP8 准确率 | 87.6% |
| 只有 BF16 做对的题 | 33 |
| 只有 FP8 做对的题 | 33 |
| McNemar 精确检验 | p = 1.000 |

**在 GSM8K 上没有观察到精度差异。** 前 500 题里的差距只是抽样波动。这也说明，只看小样本的平均分很容易得出错误结论，配对比较更可靠。

（GSM8K 只是一个数学推理测试集。对长上下文、代码等任务，上线前还应该用业务相关的评测集再验证。）

## 8. 给运维的结论

| 场景 | 建议 |
| --- | --- |
| 高并发、追求吞吐（批处理、离线任务） | 开启 FP8 KV Cache：吞吐最多 +35%，KV Cache 容量翻倍 |
| 低并发、对延迟敏感 | 保持 BF16：FP8 在这种情况下慢约 5% |
| 长上下文 | 优先考虑 FP8：容量翻倍，意味着同样的显存能容纳两倍的上下文 |
| 所有场景 | 用接近真实分布的负载做压测；上线前用业务评测集验证精度 |

## 9. 复现

```bash
# BF16 服务（GPU 0）与 FP8 服务（GPU 1）
CUDA_VISIBLE_DEVICES=0 vllm serve Qwen/Qwen3-8B --port 8000
CUDA_VISIBLE_DEVICES=1 vllm serve Qwen/Qwen3-8B --port 8001 --kv-cache-dtype fp8

# 确认配置真的生效（不要只相信启动命令）
curl -s localhost:8001/metrics | grep -o 'cache_dtype="[^"]*"'

# 并发扫描（每组 3 次）
./sweep.sh 8000 bf16 3 && ./sweep.sh 8001 fp8 3

# 只测 prefill
vllm bench serve --model Qwen/Qwen3-8B --port 8001 --dataset-name random \
  --random-input-len 4096 --random-output-len 1 --num-prompts 200 --max-concurrency 16

# 长度随机的负载
vllm bench serve ... --random-range-ratio 0.5

# 精度：全量 GSM8K + 逐题配对
lm_eval --model local-completions --tasks gsm8k --log_samples --output_path ./eval_8001 \
  --model_args model=Qwen/Qwen3-8B,base_url=http://localhost:8001/v1/completions,num_concurrent=64,tokenized_requests=False
python paired.py
```

## 10. 这次学到的

1. **先写预测，再做实验。** 没有预测，就不会发现"只达到一半"这个最有价值的信息。
2. **确认配置真的生效。** 实验中途，我一度找不到 FP8 服务的日志，最后是通过进程参数和 `/metrics` 接口确认的。
3. **日志线索只是线索。** 看起来最合理的解释，一个实验就推翻了。
4. **压测负载的形状会改变结论。** 固定长度的负载既会高估性能，也会制造出不存在的问题。
