最近在研究 Megatron 的 Context Parallel，发现开启 CP 和不开启 CP 时 loss / grad norm 对不齐，于是深挖了一下，发现了他实现的一些问题。

影响范围：当开启 --calculate-per-token-loss 开关时，梯度会被放大 CP 倍，影响了训练的稳定性。

（如果不知道什么是 CP，可以先拉到本文结尾补充背景知识）

## 万恶之源

![](https://pic1.zhimg.com/v2-3b083d301fb3f018cd9a51465223e90a_r.jpg)
*万恶之源*

一切的一切要从这个诡异的 [* CP](https://github.com/NVIDIA/Megatron-LM/blob/77537b98da08c4100a611f36af349f6651777a8a/pretrain_gpt.py#L213) 说起。在 Megatron 的[早期版本](https://github.com/NVIDIA/Megatron-LM/blob/2360d732a399dd818d40cbe32828f65b260dee11/pretrain_gpt.py#L71)中，loss_func 的第一个返回值是一个干干净净的 loss，非常好理解。然而，自从 Megatron 支持 CP 后，这里就多一个 * CP，看起来有些难以理解。那为什么他要这么做呢？经过一顿代码阅读，最后发现其实和**分布式数据并行（Distributed Data Parallel, DDP）**有很大的关系。

## Megatron 的 DDP

DDP 通常由以下操作组成：

1. **数据分割**：将一个 batch 的数据分割成若干份，分配到不同的 GPU 上。

2. **模型复制**：每个 GPU 上都有一个完整的模型副本，这些副本初始时具有相同的参数。

3. **梯度计算**：每个 GPU 使用分割后的 micro-batch 进行前向传播、loss计算和反向传播，计算出梯度。

4. **梯度聚合**：包括梯度累加和梯度同步。梯度累加指的是在单个节点上，多个 micro batch 的梯度累加。梯度同步指的是所有节点梯度的全局平均，这种梯度聚合可以通过集合通信（如all-reduce）实现。

5. **参数更新**：聚合后的梯度用于更新模型参数，然后这些更新的模型参数会同步到所有节点。

举个例子，Global batchsize = 16 (一次梯度更新计算 16 个样本）, Micro batchsize = 1（一次前向后向计算 1 个样本），8 卡训练，不考虑其他并行方式（TP=1, PP=1, CP=1)，DP=8, 模型被复制成8份，每张卡上都有一个模型，数据也被切分为 8 份，每张卡上有 1 条数据。如下图所示。

![](https://pic1.zhimg.com/v2-c96ab18a732682b1e55b34ab4f46b83e_r.jpg)
*DDP*

然后一次 forward-backward 计算，每张卡就积累了各自数据产生的梯度。

**梯度累加**：由于一次只计算了 8 条样本，还需要一次额外的 forward-backward 才能得到 16 条样本的梯度，这个过程称为梯度累加。两次 forward-backward 后，每张卡上的梯度为 2 份，所以需要[进行缩放](https://github.com/NVIDIA/Megatron-LM/blob/baf94af3c667248865f23df73b9fb8e2395e6fd0/megatron/core/pipeline_parallel/schedules.py#L278)（**除以 2**） 。

**梯度同步**：经过梯度累加并缩放，每张卡得到了 1 条数据产生的梯度，然后通过 [all-reduce / reduce-scatter](https://github.com/NVIDIA/Megatron-LM/blob/b5d90de8e7c7fae5f35be89d665f237970540bed/megatron/core/distributed/param_and_grad_buffer.py#L347) 通信一次获得所有数据的梯度。因为 reduce 使用了[求和运算](https://github.com/NVIDIA/Megatron-LM/blob/b5d90de8e7c7fae5f35be89d665f237970540bed/megatron/core/distributed/param_and_grad_buffer.py#L304)，所以需要[进行缩放](https://github.com/NVIDIA/Megatron-LM/blob/b5d90de8e7c7fae5f35be89d665f237970540bed/megatron/core/distributed/distributed_data_parallel.py#L242)（**除以 8）**得到平均每条数据的梯度。

这里可以看出，为了求得平均每条数据的梯度，优化器更新前要对梯度做两次缩放。第一次缩放的因子为「**梯度累加数**」，第二次缩放为「**DP数**」。

引入 CP 后，其他参数和刚才一样，当 CP=2 时，DP=4，模型依旧被复制为 8 份，因为 CP 其实也是在切数据，可以理解为一种另类的数据并行。数据被竖着切成 2 份，横着切成 4 份。所以这时每张卡会得到「半条」数据，如下图所示。

![](https://pic4.zhimg.com/v2-b5b0fdd9803228f1b2de3f361b717745_r.jpg)
*+CP*

所以，一次 forward-backward 后，每张卡就积累了**半条数据**产生的梯度。

**梯度累加**：这时总共仅完成了 4 个样本。为了得到 16 个样本的梯度，总共需要做 4 次 forward-backward，即梯度累加数 = 16/4 = 4 。因为进行了梯度累加，所以梯度要**除以 4**。

**梯度同步**：通过梯度累加然后平均，每张卡得到「半条数据」的梯度。经过一次 reduce-scatter 通信后每张卡可以得到 4 条「整条数据」的梯度，这时应该**除以 DP size = 4**，得到平均每个「整条数据」的梯度。

然而，[Megatron 的 DDP 梯度同步的缩放因子](https://github.com/NVIDIA/Megatron-LM/blob/b5d90de8e7c7fae5f35be89d665f237970540bed/megatron/core/distributed/distributed_data_parallel.py#L238C5-L243C12)为**DP*CP = 8**，额外缩小了 CP 倍，最终每张卡得到了 1 / CP 个「整条数据」的梯度。所以就出现了本文开头的 loss * CP，属于是拆东墙补西墙了。

![](https://picx.zhimg.com/v2-fa4541b74d17c12077c039cf35cda8b5_1440w.jpg)
*编程的第一法则：如果代码以某种形式运行起来了，就不要再碰了。*

## --calculate-per-token-loss

之前写过一篇文章，介绍了 SFT 容易出现的问题：[Ethan Yan：SFT loss 计算的那些坑（多轮合并/packing）](https://zhuanlan.zhihu.com/p/721652210)，其中提到了 loss 的三次平均。为了避免框架在 DP 和梯度累加上平均，需要开启 --calculate-per-token-loss。

如果没有开启，默认梯度会[先缩放「梯度累加」倍](https://github.com/NVIDIA/Megatron-LM/blob/baf94af3c667248865f23df73b9fb8e2395e6fd0/megatron/core/pipeline_parallel/schedules.py#L278)，[再缩放「DP*CP」倍](https://github.com/NVIDIA/Megatron-LM/blob/b5d90de8e7c7fae5f35be89d665f237970540bed/megatron/core/distributed/distributed_data_parallel.py#L242)。开启后，这些缩放[不会生效](https://github.com/NVIDIA/Megatron-LM/blob/b5d90de8e7c7fae5f35be89d665f237970540bed/megatron/core/distributed/distributed_data_parallel.py#L229)，转为[最后在「token_num」上缩放](https://github.com/NVIDIA/Megatron-LM/blob/b5d90de8e7c7fae5f35be89d665f237970540bed/megatron/core/distributed/finalize_model_grads.py#L314)，并且没有额外缩放 CP 倍的问题。

由于之前的「拆东墙补西墙」并没有考虑到这个开关，所以无论是否开启，都会 loss * CP，最后导致开启时 loss 被放大 CP 倍，梯度也被放大 CP 倍。

解决这个 bug 也很简单，当开启 --calculate-per-token-loss 开关后，删除 * CP。

至此，这个 bug 的起因，经过和结尾就介绍完了。

## one more thing

在 loss_func 中还有一段令我费解的代码

![](https://pic4.zhimg.com/v2-c37c7e0ae7e3f299da7c2382fcaf214b_r.jpg)

由于集合通信是不可导的，all-reduce 通信只会在前向传播中进行，并不会改变反向传播的计算图。loss 作为计算图中的叶结点，前向传播的终点，最后在 CP 维度 all-reduce 对梯度没有任何影响，所以这里对于反向传播来说相当于是一个空操作。

不过，他的 loss 其实还包括一个 “total_tokens”，这个通信其实是必要的，因为最终缩放使用的 num_tokens 只[在 DP 维度求和](https://github.com/NVIDIA/Megatron-LM/blob/b5d90de8e7c7fae5f35be89d665f237970540bed/megatron/core/distributed/finalize_model_grads.py#L311)，并没有考虑 CP 维度。

所以，最好在 reporting_loss / num_tokens 的 all-reduce 中，加上 with_context_parallel=True，这样就可以把两次通信合并了。和作者反馈，作者表示并不想改了，因为过了这么长时间已经有很多人在中间加了其他校验 loss 相关的代码，如果改了可能会有问题。

## 吸取教训

其实这种问题在团队合作中会经常出现，我们每个人可能都会遇到。从这次经历中我们可以学习到两件事：

1. 高内聚，低耦合。来自软件工程的经典概念，模块独立非常重要，不要写「拆东墙补西墙」的代码。

2. 加强沟通。后来在 github 的 issue 区从 CP 的开发者口中了解到 “--calculate-per-token-loss” 是在 CP 实现后引入的，CP 的作者甚至不知道这个特性的存在。

经过和 Nvidia 开发者的友好讨论，他们承诺未来会修复这个 bug，本文也将会同步更新进展。

## 补充一些背景知识

Q：什么是 CP？

CP 是 Megatron 第六种并行方式（前五种为TP、PP、DP、SP、EP），为了支持超长上下文训练。思路和 Ring Attention 类似。

Q：为什么要开 CP？

在训练长文本时，激活值会占用大量显存。开启 CP 是降低激活值显存占用的一个比较好的方式。和之前的序列并行（SP）不同，SP 只在 Dropout, Layernorm 等 token 之间互相独立的模块上切分激活值，CP 可以切分所有模块的激活值，包括 Attention。可以理解为 CP 用额外的通信换来了更低的激活值。

Q：CP 和其他并行方式是怎么搭配的？

TP*CP*DP*PP = 总GPU数。

Megatron 会按照 TP-CP-DP-PP 的优先级将不同卡分配到不同的 rank 上。如果 DP是把数据横向切开，CP 则是把数据从竖向切开，所以在原来 TP-DP-PP 基础上，将 “DP” 变成了 “CP-DP“。最后按照通信量排序，通信量越大越靠前。
