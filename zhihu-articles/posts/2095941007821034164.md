Deepseek官方发布了一篇《DeepSeek V4.1 Flash 大规模推理部署实践》。

[DeepSeek V4.1 Flash 大规模推理部署实践](https://zhuanlan.zhihu.com/p/2095560295930508953)

十分离谱，不仅是技术细节，就算是收入也给你公布了。

> 目前单一集群的服务吞吐是 155 万亿 Tokens/天，整体收入是每卡每小时 38 美金（按谷价）。

分享一些有趣的细节。

1.

目前单一集群的服务吞吐是 155 万亿 Tokens/天，这个数据什么概念，谷歌的劈柴哥在今年 I/O 上说，Google 全线一个月处理 3.2 千万亿 token，折下来一天 107 万亿。

DeepSeek 一个集群，一天 155 万亿。

DeepSeek 那个数里 96% 是缓存命中，Google 那边怎么算的没人知道，也没公布但量级上，一家公司的单个集群，和另一家顶级算力的公司的全部产品线来到了一个水平线上了。

MD，离谱。

2.

96% 的 token 没有进 GPU，命中缓存不用算。

大模型服务分两步，prefill 负责读：把你的几万字从头过一遍，算出每个词的内部状态，存成 KVCache。decode 负责写：一个字一个字往外蹦。

prefill 的麻烦在于跟输入长度成正比。你贴七万字进去，它就得老老实实算七万个 token 的注意力。

一轮都重算？77,000 除以每秒 6 万，首字要等 1.28 秒。

缓存改变的就是这件事。这段前缀算过，就把 KVCache 从硬盘搬回显存，跳过计算。

TTFT 的账立刻变了：77,000 里 96% 命中，只剩 3,080 个 token 要真算，51 毫秒。

营收中还有一个细节，那张 prefill 卡一小时过 54 亿 token，96% 的命中贡献 15.5 美元，4% 的未命中贡献 32.4 美元，96% 的 token 挣三成收入，4% 的 token 挣七成收入。

3.

V4.1 Flash，全局 KVCache 压到每 token 890 字节，大约是 V4 Flash 的四分之一。

怎么压到 890 的？文章只给了几个词：CSA2 里的跨层 KVCache 复用、FP4 KV 缓存、20 层 SWA。技术报告给的解释是，多层共用一份 KV，各层各算自己的 query，加上每个 K/V 元素只用 4 位存。

然后就不用内存了，Block KVCache 落在一个独立的 3FS 集群上，100 PiB 的 SSD。

100 PiB 装得下 126 万亿 token 的 KV，等于他们自己 0.8 天的 token 处理量。

这个数据量怎么样一个级别呢？峰值聚合读带宽 10 TiB/s，写 850 GiB/s。10 TiB/s 换成 token，是每秒 123 亿 token 的 KV。

集群的算力是每秒 17.9 亿 token，也就是存储能够喂的，要比算力能吃的多7倍。

这省钱省的。

4.

再说缓存。

Block KVCache，留 3 天，agent 流量的 TTL 3 天，chatbot 流量 7 天；

SWA KVCache，3 分钟；

TTL 约 180 秒。

没有工程化实践的经验，这个数据得不出来。

5.

传统模型的参数量是固定的。不管你喂进去还是吐出来，每一步走同样多的参数。

V4.1 Flash 把它拆开了：prefill 阶段激活 8B，decode 阶段激活 16B。

差一倍。

这个模型读你话，比写的话便宜一半。

更适合agent。平均输入 77,000，回你几百个字。翻译一下，就是把贵的参数放到用得少的那一侧。

6.

prefill 用常见的 8 卡机，decode 用常见的 64 到 128 卡超节点。

一个 8，一个 128。差 16 倍。

为什么能这么极端？因为两个阶段的瓶颈根本不同。

prefill 是算力活，所以 EP2 到 8 就够，通信越少越好。

decode 是显存带宽活。每吐一个 token，要把激活的权重从显存里读一遍。卡越多，每张卡上的专家越少，读的量越小。

7.

还有一部分代码目前没有开源——

> KVCache 管理与负载均衡组件因与内部基础设施耦合较深，相关代码目前尚未完整开源。

开源的部分列一下：FlashMLA、DeepGEMM、DeepEP、TileKernels 这些算子，推测解码、SWA 重放、异步调度、结构化输出、批次不变性、确定性采样。Apache 2.0。

不开源的：缓存系统，和四个负载均衡器。

8.

说的是训练怎么便宜。
