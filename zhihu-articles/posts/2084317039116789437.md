## 术语表

| 术语 | 含义 | 为什么本篇需要 |
| --- | --- | --- |
| OOM（Out of Memory，显存溢出） | 分配请求得不到满足时 CUDA 抛出的错误，训练进程直接崩溃 | 本篇要救的就是它，07 篇已教会区分容量与碎片 |
| 显存红线（set_per_process_memory_fraction） | 给进程画一条显存上限，超出即触发真实 OOM | WSL2 只慢不崩，红线把 8 GB 卡模拟成更小的卡，让 OOM 在受控条件下复现 |
| gradient accumulation（梯度累积） | 把大 batch 拆成多次小前向，梯度逐次累加后执行一次参数更新 | 第 2 章最便宜的交换：激活只来自一个 micro_batch |
| micro_batch 与 effective batch | micro_batch 是单次前向的真实 batch；effective batch 是 micro_batch 乘累积步数 | 说清 accum 省显存但不改等效 batch |
| activation checkpointing（激活检查点） | 反向时重新执行一次前向，层间激活不常驻 | 第 3 章主角，用重算换激活 |
| 混合精度 AMP | fp16 存激活与执行矩阵乘，fp32 保留主权重 | 省激活还提速，但碰不到优化器状态 |
| GradScaler | 放大 loss 防 fp16 梯度下溢，step 前 unscale 再更新 | 解释 amp 的数值代价与 06 篇的 unscale 顺序坑 |
| fp16 优化器状态（lowstate） | AdamW 的 m 与 v 以 fp16 存储，状态字节减半 | 第 4 章省显存最多但实测 NaN 的一项 |
| CPU offload | 优化器状态搬到主机内存，step 时经 PCIe 传回 GPU | 第 4 章用总线换容量的最后一笔交换 |
| PCIe 带宽 | GPU 与主机内存之间的传输通道 | offload 的代价来源，解释吞吐为什么跌 |
| set_to_none | zero_grad(set_to_none=True) 释放梯度张量而非填零 | 三件小事之一，几乎免费的交换 |

## 1. OOM 现场：它到底崩在哪一步

### 1.1 目标配置与红线

本篇的目标配置是：hidden 768 / layers 12 / heads 12 / seq 256 / batch 8 / fp32，即 04 篇的 100M 档（89.59M 参数）。这个量级在显存充裕的机器上没问题，但放到受限环境下就会触发 OOM。

为什么要设红线？07 篇已经实证：WSL2 的 DXG 内核驱动会把超额显存请求悄悄溢出到主机内存，导致大配置“只慢不崩”，无法直接复现显存不足的故障。这里说的 DXG 是 Windows 的 GPU 内核驱动，WSL2 里的 CUDA 请求都经它转发给真实显卡。`torch.cuda.set_per_process_memory_fraction` 给当前进程画一条硬上限，超出这条线就触发真实的 `CUDA out of memory`。本篇统一使用 `--mem-fraction 0.35`，对应 8 GB 卡上约 2.80 GiB 的可用上限，等价于模拟一张约 3 GB 的显卡。裸金属（不经虚拟化、直接装 Linux 的物理机）不需要这个参数，显存不足时系统本身就会报错。

用红线基线跑目标配置：

```text
python -m exp_opt.opt_bench --mode bench --opts baseline \
  --hidden 768 --layers 12 --heads 12 --seq 256 --batch 8 \
  --steps 50 --mem-fraction 0.35
```

**原始输出**（bench 模式把结果写成 JSON，摘录关键字段）：

```text
{
  "opts": [],
  "steps": 1,
  "peak_mb": 2610.7,
  "reserved_mb": 2864.0,
  "final_loss": null,
  "oom": "CUDA out of memory. Tried to allocate 16.00 MiB. GPU 0 has a total
          capacity of 8.00 GiB of which 4.09 GiB is free. 2.80 GiB allowed; ..."
}
```

steps 字段是 1，意思是循环走到第 2 轮（step 下标 1）就抛了 OOM，50 步只活了一步多。peak 2610.7 MB，reserved 2864.0 MB 已顶到 2.80 GiB 红线。

**预测：** 崩在第一步并不意味着崩在第一次前向。07 篇告诉我们，AdamW 的状态在第一次 `optimizer.step()` 时才真正分配（惰性初始化）。如果第一次前向本身就顶破红线，那崩溃发生在 `forward_0`；如果第一次前向撑过去了，崩溃可能在 `step_0` 状态物化之后的第二次前向。我们需要更细粒度的时间线来确认。

### 1.2 时间线证据：崩在第二次前向

切换到 oom 模式，它在每个关键阶段插入打点并写出 `oom_redline.json`：

```text
python -m exp_opt.opt_bench --mode oom \
  --hidden 768 --layers 12 --heads 12 --seq 256 --batch 8 \
  --mem-fraction 0.35
```

**原始输出**：oom 模式把结果写成 oom_redline.json，其中的 timeline 字段是下面六段打点，每段三个读数依次是 allocated、reserved、peak，单位 MB。

```text
model_loaded    343.6   / 380.0   / 343.6
optimizer_init  343.6   / 380.0   / 343.6
forward_0       1906.2  / 2064.0  / 1953.2
backward_0      708.6   / 2112.0  / 2000.2
step_0          1401.4  / 2112.0  / 2000.2
（forward_1 没有打点记录：崩溃发生在它内部）
```

同文件里的 oom 字段给出崩溃消息，oom_stage 字段记为“step_0 之后”。

**观察：**

`optimizer_init` 阶段 allocated 没有任何变化，仍停在 343.6 MB。07 篇已经讲过的惰性初始化行为，AdamW 在构造时只登记参数引用，不分配 m/v 张量。

`forward_0` 把 allocated 从 343.6 推到 1906.2（涨幅 1562.6 MB），这是一次前向产生的激活与临时张量。`backward_0` 结束后激活被释放，allocated 降回 708.6，但 reserved 维持在 2112，那是 PyTorch 的缓存池，不会立即归还给 CUDA。

`step_0` 是关键：allocated 从 708.6 跳到 1401.4，增加了 692.8 MB。这就是 AdamW 惰性状态物化的那一刻，m 和 v 张量在第一次 `step` 时被分配出来。此后 GPU 上常驻着权重（343.6 MB）、梯度（343.6 MB）与完整的 m/v 状态（约 687 MB，两倍参数量乘 4 字节），三项合计约 1374 MB，加上约 27 MB 的临时张量，就是 1401.4 MB 这个后续每一步的显存基底。

`forward_1` 试图在这个 1401 MB 的基底上再叠加一次激活（约 1562 MB），两者之和超过 2.80 GiB 红线，随即崩溃。

**解释：** 崩溃点不是"模型太大"，而是"状态物化之后，第二次前向的激活叠上去顶破了红线"。这和 07 篇时间线里 `step_0` 出现的 peak 尖峰是同一件事，本篇把它推进到了实际崩溃的场景。

### 1.3 读 OOM 消息：48 MiB 是最后一根稻草

崩溃时 PyTorch 打出的完整消息是：

```text
CUDA out of memory. Tried to allocate 48.00 MiB.
GPU 0 has a total capacity of 8.00 GiB of which 4.13 GiB is free.
2.80 GiB allowed;
Of the allocated memory 2.50 GiB is allocated by PyTorch,
and 259.79 MiB is reserved by PyTorch but unallocated.
```

这条消息的信息量比看起来大得多。`allocated 2.50 GiB` 加上 `reserved but unallocated 259.79 MiB`，合计约 2.76 GiB，已经非常逼近 2.80 GiB 的红线。失败的那笔分配只有 48 MiB，它是压垮那一刻的最后一笔，不是问题的根本。

memory snapshot 是崩溃回退之后抓的，它记录的是异常展开、前向中间张量释放之后的池子状态，不能当作崩溃瞬间的证据。它在这里的作用是补一个旁证：largest_inactive_block 48.0 MB，意思是池子里最大的连续空闲块只有 48 MB，而失败的那笔请求恰好是 48 MiB，连最大的空洞都填不进去，分配器只能走 CUDA 新分配路径，而新分配路径被红线截断。真正可靠的证据是上面两条：OOM 消息里的 allocated 与 reserved 已贴住红线，以及时间线里 step_0 之后基底抬高、forward_1 叠加崩溃。

**结论：** 要救这个配置，不能只减少某一处的峰值，而要把"状态物化之后 + 第二次前向激活叠加"这个最高叠加时刻的总量压到 2.80 GiB 以下。下一章从代价最小的交换方式开始逐步尝试。

## 2. 先动便宜的：不改计算图的三件小事

### 2.1 setnone 与 accum 各自换到什么

在动计算图（activation checkpointing）或数值精度（AMP、lowstate）之前，有三件不改模型结构的小事可以先做，调试风险很低：

**set_to_none** 解决的是梯度张量的占用。默认的 `zero_grad()` 只把梯度数据填零，张量本身仍然存在于显存。`zero_grad(set_to_none=True)` 直接把梯度张量的引用置为 `None`，PyTorch 可以立即回收这块内存。代价是下一次反向时需要重新分配梯度张量，但分配开销通常可忽略。

**gradient accumulation** 解决的是激活峰值问题。batch 8 的前向一次性产生 8 条序列的激活；如果拆成 accum=4、micro_batch=2，每次前向只产生 2 条序列的激活，激活峰值直接按比例缩小。梯度在四次小前向里累加，最后一步统一 `optimizer.step()`，等效 batch 仍然是 8，这就是用时间换显存。代价是相同步数下需要 4 倍的前向和反向调用，总计算量不变但总时间增加。opt_bench.py 里的内层循环长这样：

```python
opt.zero_grad(set_to_none=set_none)
            for _ in range(accum):
                with torch.autocast(device_type="cuda", dtype=torch.float16,
                                    enabled=use_amp):
                    loss = contract_loss(model(x), y) / accum
                if scaler is not None:
                    scaler.scale(loss).backward()
                else:
                    loss.backward()
```

loss 除以 accum 是为了让累加后的梯度等于完整 batch 的平均梯度，而不是它的 4 倍。04 篇踩过这个坑：漏掉除法时 loss 记账会错一个倍数，而且只在 accum 大于 1 时暴露。

**AMP（混合精度）** 单独能做到什么？预测：AMP 把激活与矩阵乘的中间张量从 fp32 换成 fp16，理论上激活峰值减半。但优化器状态（m/v）仍然是 fp32，这部分不受 AMP 影响。用 AMP 还有一条口径纪律：反向得到的是放大过的梯度，必须先 unscale 再裁剪、再 step，06 篇记录过先 clip 后 unscale 让 grad_norm 读成放大值的坑。上面的循环里 scaler.scale 包住 backward，裁剪与更新都在 unscale 之后，这条纪律在 opt_bench.py 里已经内置。

### 2.2 amp 单独为什么不够，peak 为什么反而更高

跑 amp 单独的红线 bench：

```text
python -m exp_opt.opt_bench --mode bench --opts amp \
  --hidden 768 --layers 12 --heads 12 --seq 256 --batch 8 \
  --steps 50 --mem-fraction 0.35
```

**原始输出**：

```text
{
  "opts": ["amp"],
  "steps": 2,
  "peak_mb": 2768.6,
  "reserved_mb": 2864.0,
  "final_loss": null,
  "oom": "CUDA out of memory. Tried to allocate 48.00 MiB. ..."
}
```

两个反直觉的结果同时出现：第一，amp 单独仍然 OOM；第二，它的 peak 2768.6 MB 比 baseline 的 2610.7 MB 还要高。

**解释：**

为什么仍然 OOM？AMP 确实把 fp16 激活换成了更小的张量，但 `step_0` 物化的 m/v 状态依然是 fp32，加上 AMP 本身需要同时维护 fp16 工作副本和 fp32 主权重，主权重占用并未减少。amp 并没有触碰优化器状态这个大头。

为什么 peak 反而更高？peak 记录的是 allocated 的历史最大值，它是某个叠加时刻的快照，不是某个组件的稳态大小。baseline 在 step_0 之后的 forward_1 就崩溃了，peak 停留在那个时刻；amp 让进程多活了一步，峰值记录到了更晚的、叠加更充分的时刻。两个 peak 对应的时间点不同，不能直接比较“amp 省没省显存”。要比较省没省，得让两个配置都活着跑完同样的步数，再比峰值，这正是第 5 章 parity 的做法。

### 2.3 三件一起上：跑通了，代价是吞吐

把 gradient accumulation、AMP 和 set_to_none 三件事合在一起跑：

```text
python -m exp_opt.opt_bench --mode bench --opts accum,amp,setnone \
  --hidden 768 --layers 12 --heads 12 --seq 256 --batch 8 \
  --steps 50 --mem-fraction 0.35
```

**原始输出**：

```text
{
  "opts": ["accum", "amp", "setnone"],
  "steps": 50,
  "peak_mb": 1870.2,
  "reserved_mb": 2000.0,
  "final_loss": 8.8085,
  "oom": null
}
```

50 步全部跑完，peak 1870.2 MB，低于 2.80 GiB 红线，首次跑通。final_loss 8.8085 是在随机数据上的绝对值，其意义在于与后续组合横向比较；各组合的吞吐和收敛对照放到第 5 章 parity 统一汇报。

三件事的合力：accum 把每次前向的激活从 batch 8 降到 micro_batch 2，AMP 把 fp16 激活大小减半，setnone 在每步梯度归零时释放梯度张量。三者叠加才让叠加峰值降到红线以下，缺任何一件都不够。

**下一问：** 已经跑通，能不能在不增加累积步数的前提下继续降峰值？

## 3. 动计算图：activation checkpointing

### 3.1 用重算换激活

activation checkpointing 的思路是：前向时不保留层间激活，反向时重新跑一次前向来临时恢复它们。激活不需要在前向结束后常驻显存，峰值由"单层最大激活"而非"全部层激活之和"决定。

`opt_bench.py` 里的实现是把每个 Transformer block 包进 `CkptBlock`：

```python
class CkptBlock(nn.Module):
    """把单个 Transformer block 包成 activation checkpointing 单元。"""

    def __init__(self, block: nn.Module):
        super().__init__()
        self.block = block

    def forward(self, *args, **kwargs):
        if self.training:
            return torch_checkpoint(self.block, *args,
                                    use_reentrant=False, **kwargs)
        return self.block(*args, **kwargs)
```

`torch_checkpoint` 是 `torch.utils.checkpoint.checkpoint` 的别名，`use_reentrant=False` 是新版 PyTorch 推荐的调用方式，避免了旧实现中需要手动处理输入 requires_grad 的约束。推理时（`self.training` 为 False）跳过 checkpoint，不引入额外开销。

跑 amp,ckpt 组合的红线 bench：

```text
python -m exp_opt.opt_bench --mode bench --opts amp,ckpt \
  --hidden 768 --layers 12 --heads 12 --seq 256 --batch 8 \
  --steps 50 --mem-fraction 0.35
```

**原始输出**：

```text
{
  "opts": ["amp", "ckpt"],
  "steps": 50,
  "peak_mb": 1801.3,
  "reserved_mb": 2046.0,
  "final_loss": 8.8015,
  "oom": null
}
```

peak 1801.3 MB，比 accum,amp,setnone 的 1870.2 MB 又低了 68.9 MB，且吞吐 11723 tok/s 比 8901 高出不少。

### 3.2 反直觉：加了重算为什么更快

在 parity 实验（第 5 章详细汇报）里，amp,ckpt 对 baseline 的吞吐对比是 77066 对 54244 tok/s，比 baseline 快了约 42%。加了一次重算不仅没有让速度变慢，反而显著提升，原因在两个独立的机制：

**AMP 的 Tensor Core 提速。** Tensor Core 是 NVIDIA GPU 上专门做矩阵乘的硬件单元，fp16 矩阵乘在它上面的吞吐约为 fp32 通用单元的 2 到 4 倍，这是 AMP 最核心的收益。baseline 全程 fp32，跑的是慢路径；amp,ckpt 走 fp16 矩阵乘，绝对速度已经大幅提升。

**ckpt 的重算开销被 AMP 收益覆盖。** activation checkpointing 把每个 block 的前向跑了两次（原始前向一次 + 反向前的重算一次），理论上慢一倍。但这两次重算都在 AMP 的 fp16 路径下执行，速度快；同时激活内存减少后，内存带宽压力下降，内存 bound 的操作也变快。两者叠加，重算的代价在本机硬件上被彻底吃掉，换到的是净收益。

parity 里 peak 的对比更清晰：amp,ckpt 是 512.3 MB，baseline 是 1265.7 MB，降低了 59.5%，而吞吐还高 42%。显存与速度同时改善，六个组合里没有第二个做到这一点。

**结论：** 在有 Tensor Core 的 GPU 上，amp,ckpt 的组合通常是"先试这个"的默认选择，它在不引入任何收敛风险的前提下同时提升速度和降低显存。

## 4. 动数值口径与总线：最贵的两笔交换

![](https://pica.zhimg.com/v2-8635690147b2569dd0a274fe8ef8ab80_r.jpg)
*六种资源交换：每项优化付出什么、换到什么*

上图总结了本篇六种交换的资源流向：set_to_none 在每步释放梯度张量；gradient accumulation 用时间（多次前反向）换激活峰值；AMP 用 fp16 精度换速度与激活大小；activation checkpointing 用计算（重算）换激活常驻；lowstate 用数值稳定性换优化器状态字节；CPU offload 用 PCIe 带宽换 GPU 容量。前三者代价低，后三者代价高，这是决策的顺序。

### 4.1 lowstate：省一半状态，代价是 NaN

AdamW 为每个参数维护两个状态张量：一阶动量 m 和二阶动量 v，默认均为 fp32，合计状态大小是参数量的两倍字节再乘二。红线目标配置有 89.59M 参数，fp32 的 m/v 合计约 693 MB（第 1.2 节 step_0 的实测增量），换成 fp16 存储就减半到约 346 MB。

跑 amp,ckpt,lowstate 红线 bench：

```text
python -m exp_opt.opt_bench --mode bench --opts amp,ckpt,lowstate \
  --hidden 768 --layers 12 --heads 12 --seq 256 --batch 8 \
  --steps 50 --mem-fraction 0.35
```

**原始输出**：

```text
{
  "opts": ["amp", "ckpt", "lowstate"],
  "steps": 50,
  "peak_mb": 1473.1,
  "reserved_mb": 1542.0,
  "final_loss": NaN,
  "oom": null
}
```

peak 1473.1 MB 是本篇红线 bench 六组合里最低的一个，比 amp,ckpt 的 1801.3 MB 低了 328.2 MB，与“状态减半约 346 MB”的预期同量级。但 final_loss 是 NaN，训练实际上已经发散。

**为什么会 NaN？** AdamW 更新时需要计算 v（梯度平方的指数移动平均）的平方根倒数。fp16 能表示的最小正规格化数约为 6×10⁻⁵，加上非规格化数也只能到约 6×10⁻⁸；梯度在某些层的绝对值本就很小，平方之后更小，低于这个下限就直接下溢到零。v 变成零后倒数变成无穷，参数更新出现 inf 或 nan，然后 nan 在矩阵乘中传播，最终 loss 变成 NaN。

parity 里也重现了同样的结果：val 是 NaN，训练完全无效。

**诚实记录：** lowstate 是本篇六组合里显存节省最多的单项操作，但也是唯一一个在本实验设置下毁掉训练的选项。它不是绝对不可用，工程上可以给它配一份 fp32 的主状态副本或更保守的缩放策略，但在没有这些额外处理的情况下，本篇的实测结论是不要单独启用。

### 4.2 offload：状态清零，总线成为新瓶颈

CPU offload 的原理是：把优化器状态（m 和 v 张量）从 GPU 显存搬到主机内存（DRAM）。GPU 上只保留模型权重和前向、反向所需的张量。每次 `optimizer.step()` 时，把需要更新的状态张量经 PCIe 传回 GPU，完成参数更新，再把状态张量搬回主机内存。

要看清这笔交换单独值不值，做单变量隔离：在 amp,ckpt 的基础上只加 offload，其余都不动。parity 的隔离运行给出：

| 组合 | 时间（s） | tok/s | peak(MB) | val loss |
| --- | --- | --- | --- | --- |
| amp,ckpt | 12.74 | 64312 | 507.4 | 5.3229 |
| amp,ckpt,offload | 21.74 | 37690 | 431.2 | 5.3229 |

parity 的配置是 12.93M 参数，fp32 的 m/v 合计约 103 MB，offload 实测省下 76.2 MB 峰值，与这个量级吻合（差额是搬运动作本身的临时缓冲）。代价是时间从 12.74 秒涨到 21.74 秒，每步多出约 45 毫秒，吞吐掉到原来的约六成。

**为什么每步多出 45 毫秒？** 每步要把约 103 MB 的状态搬两次（CPU 到 GPU、GPU 到 CPU），合计约 207 MB。按 PCIe 3.0 x16 约 16 GB/s 的带宽算，纯传输只要约 13 毫秒；实测多出的 45 毫秒里，剩下的是逐张量小拷贝的启动开销，优化器状态按参数张量分散存放，每一次拷贝都要单独发起。模型越大，状态越大，这两项开销都线性增长，PCIe 很快成为每步的固定等待。

**换到的峰值收益是 76.2 MB，付出的代价是每步多出 45 毫秒。** 这个交换在以下两种场景里合理：一是显存极端不足，其他所有手段都用完了还不够；二是训练时间没有约束，纯以跑通为目标。第 5 章的全家桶组合（peak 332.0 MB、18196 tok/s）里还叠着 accum 与 lowstate，那里的吞吐数字不能单独归因给 offload，隔离运行才是 offload 自己的账。

### 4.3 两者互斥与使用顺序

lowstate 和 offload 同时存在时，offload 优先于 lowstate：offload 把优化器状态搬到 CPU 上的 fp32，m 和 v 张量在主机内存里仍然是 fp32，lowstate 的 fp16 精度不再生效。等效结果是状态以 fp32 保存在 CPU，NaN 风险消失。

parity 全家桶 `amp,ckpt,lowstate,offload,accum,setnone` 的 val 5.3228 正常，验证了这个优先级规则：有 offload 时 lowstate 被覆盖，fp32 状态保住了数值稳定性。

**结论：** lowstate 和 offload 这两项排在决策表的最后，不是首选手段。只有前三步（set_to_none + accum + AMP + ckpt）不足以解决问题时，才考虑它们，且 offload 优先于 lowstate。

## 5. 交付：决策表与 parity

### 5.1 决策表：OOM 时先改哪一项

![](https://picx.zhimg.com/v2-eb7aaf81b2d20ffcc2c2e4e4ab0d761b_r.jpg)
*显存优化决策表：OOM 时先改哪一项*

决策表按“先低代价后高代价”四步走，与上图一一对应：

**第一步：不动计算图的三件小事。** set_to_none 加 gradient accumulation 加降 micro_batch。梯度累积把大 batch 拆成多次小前向，激活按 micro_batch 缩小，等效 batch 与收敛行为不变，只花时间。实测 peak 从 1265.7 降到 436.6 MB，吞吐从 54244 降到 41742 tok/s。跑完后用 07 篇的阶段探针重测 peak，如果已进安全线就停。

**第二步：混合精度加激活检查点。** amp 加 ckpt。AMP 把激活与临时张量减半还提速，ckpt 用反向重算换层间激活。本篇实测两者叠加后吞吐反而高于 baseline（77066 对 54244 tok/s），peak 512.3 对 1265.7 MB。在有 Tensor Core 的 GPU 上，这一步通常不降速。跑完后再次复测 peak。

**第三步：谨慎动数值口径。** lowstate 把优化器状态换 fp16，状态字节减半，但小梯度的平方在 fp16 下会下溢。本篇 parity 实测 val 直接 NaN。用之前必须验证自己的任务与学习率，默认不启用。

**第四步：最后才动总线。** offload 把优化器状态搬 CPU，GPU 上状态清零，但每步都要走 PCIe 来回搬运。隔离实测每步多出约 45 毫秒，吞吐掉到约六成；全家桶组合里吞吐只有 18196 tok/s。只有前三步都不够时才值得。

每一步之后都用 07 篇的探针重测 peak，而不是凭感觉估算；确认峰值降到安全范围内再决定是否继续下一步，避免不必要的代价堆叠。

如果时间有限，最小复现路径是只跑 baseline 与 accum,amp,setnone 两组红线 bench（各约 15 秒），其余组合直接读 results/Season1/08/ 下的 REAL 结果文件。

### 5.2 parity：优化换的是资源，不是收敛

parity 实验使用真实语料 corpus_large（char 分词），hidden 384 / layers 6 / heads 6 / seq 256 / batch 16 / 200 步，五个组合消费完全相同的数据和验证集，结果如下：

先交代数据怎么造的。bench 模式每一步现生成随机 token，而且 accum 会改变 micro_batch，随机序列随之不同，两个组合的 final_loss 因此不可比。parity 换了一条路：先从四大名著语料里按固定种子切出一批训练窗口和八个验证窗口，所有组合消费同一批窗口，loss 的差异才能归因于优化手段本身。用真实语料而不是随机 token 还有一个原因：随机数据下所有组合的 loss 都平在 ln(vocab) 附近不下降，“优化不改变收敛”这句话就没有着落。

```text
python -m exp_opt.opt_bench --mode parity \
  --configs "baseline;accum,amp,setnone;amp,ckpt;amp,ckpt,lowstate;amp,ckpt,lowstate,offload,accum,setnone" \
  --hidden 384 --layers 6 --heads 6 --seq 256 --batch 16 --steps 200
```

**parity 五组合结果表：**

| 组合 | 时间（s） | tok/s | peak(MB) | val loss |
| --- | --- | --- | --- | --- |
| baseline | 15.10 | 54244 | 1265.7 | 5.3237 |
| accum,amp,setnone | 19.63 | 41742 | 436.6 | 5.3228 |
| amp,ckpt | 10.63 | 77066 | 512.3 | 5.3229 |
| amp,ckpt,lowstate | 10.14 | 80778 | 458.3 | NaN |
| amp,ckpt,lowstate,offload,accum,setnone | 45.02 | 18196 | 332.0 | 5.3228 |

**观察：** 能训通的四个组合（baseline、accum,amp,setnone、amp,ckpt、offload 全家桶），val loss 分别是 5.3237、5.3228、5.3229、5.3228，最大差值 0.0009，小于 0.001。在同数据同预算（200 步 × 相同 token 数）的条件下，这点差异低于正常的随机扰动范围，可以认为优化手段本身没有引入收敛差异。

**解释：** 这个结论的前提是"同数据同预算"。accum 把 effective batch 保持与 baseline 一致；AMP 用 fp32 主权重保住参数精度；ckpt 只影响显存布局，不影响梯度值。只要这三个条件成立，val loss 理论上应当对齐，实测数据验证了这一点。

**amp,ckpt 吞吐比 baseline 高 42% 的直接原因** 前文已解释：fp16 Tensor Core 的矩阵乘速度。这不是理论推断，而是在 200 步 parity 实验里实测的 77066 对 54244。

**offload 全家桶** 把时间从 15.10 秒拉到 45.02 秒（约 3 倍），peak 从 1265.7 降到 332.0（降低了 73.8%），val 5.3228 与 baseline 的 5.3237 对齐。这 3 倍里叠着 accum 与 offload 两份时间代价：accum 单独在第二个组合里已经把时间从 15.10 拉到 19.63 秒，offload 自己的那份在第 4.2 节的隔离运行里（每步约 45 毫秒）。这笔交换在收敛上没有代价，代价全在时间上。

**唯一例外** 是 lowstate，val NaN，训练完全无效。fp16 优化器状态下溢不是偶发的数值噪声，而是系统性的失败模式，在本实验规模下可稳定复现。

**可验证性：** 上述五组合的 peak 数值和 val loss 可通过重跑 parity 命令在相同环境中复现；oom 模式输出的 `oom_redline.json` 包含六段打点的完整时间线和 OOM 消息；red line bench 六组合的峰值均在 `results/Season1/08/` 下保存了 REAL 结果文件，供时间不足时直接读取。

### 5.3 边界与下一篇

本文讨论的全部是**单卡完整训练（full fine-tuning）的显存交换策略**。三个明确的边界：

LoRA 及其他参数高效微调方法（PEFT）留给 24 篇。LoRA 从根本上改变了"哪些参数需要梯度"这个前提，它不是本篇讨论的显存优化，而是一种不同的训练范式。

FlashAttention 留给 09 篇。FlashAttention 通过改写注意力的 IO 模式，在不改变数学结果的前提下大幅降低激活内存，并且在长序列上比标准注意力快得多。09 篇会专门拆解它的机制与适用边界。

数据加载与 CUDA Kernel 的综合调优留给 10 篇。

09 篇的核心问题是：显存优化做完之后，为什么 attention 本身还是慢？峰值下来了，但计算与内存访问的比例（算术强度）并不会因为显存占用减少而改变，这才是 attention 计算效率的根本限制。
