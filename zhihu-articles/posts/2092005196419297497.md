## 第一部分：基础

### 第 1 章：Blackwell B200 Attention 基础实现

**本章路线图**

我们首先学习每个 CTA 做哪些工作，以及这些工作如何分配给 B200 上的不同 CTA，见“工作并行化”小节。然后可选地绕道初学者入门，介绍逻辑表示与物理表示、指针和分块矩阵乘法。接着放大观察 B200 Attention 内核，讨论每个 CTA 内部发生的事情。后文会用图示更详细地解释这一切。这里先给出整体地图，随后我会提供与图示直接对应的代码链接。

**Attention 基础内核**

先来理解第一个内核。后续内核大多沿用本章引入的数学和 `tcgen05` 概念，所以本章会讲清贯穿全文的基础。这也是第一章比后续章节更长的原因。第一个内核是起点，能给出正确的数值结果，但效率远不及后续内核。它本身已经不简单，并使用了不少 Blackwell 特有功能，下面会逐步介绍。

**主要瓶颈**

Attention 基本上就是两次矩阵乘法，中间夹着一次 Softmax。Softmax 的 FLOPs 少得多，但它运行在 ALU 和 MUFU 单元上，而不是 Tensor Core 上。在 Blackwell B200 上，Tensor Core 吞吐量大致翻倍，指数运算单元却基本没变；FA4 论文称之为“不对称的硬件扩展”。因此，在我们的 tile 尺寸下，Softmax 消耗的周期数与算力很强的 MMA 差不多，成为该内核的主要瓶颈。多数优化从两方面着手：降低 Softmax 工作的代价，以及让它与矩阵乘法重叠，也就是把它隐藏在 MMA 执行期间。

**工作并行化**

在讨论 B200 特有细节之前，先看工作如何划分。

![](https://pic4.zhimg.com/v2-7b57cbf5f298e08043d773b2ef96340b_r.jpg)

可以把 `Q`、`K`、`V` 和输出张量都看成具有相同的形状：B、`num_heads`、`seq_len`、`head_dim`。我们将张量划分成 tile，使之能放入速度快但容量小的片上存储。如上图所示，tile 尺寸为 `[128, 128]`。

![](https://pic4.zhimg.com/v2-bde9ceda92995a4dcc962e16adc9a197_r.jpg)

有多少个 `O`（输出）tile，就调度多少个 CTA；每个 CTA 生成一个 `O` tile。所有 CTA 合起来生成完整输出张量的全部 tile。CTA 并行执行，见紫色箭头。

每个 CTA 内部的 `K`/`V` 循环工作则是顺序执行的，见橙色箭头。放大观察一个 CTA：为了生成自己的 `O` tile，CTA 只加载一次对应的 `Q` tile，然后遍历所有 `K`/`V` tile 对。每轮计算 `S_tile = Q_tile @ K_tile.T`，再执行在线 Softmax 得到 `P_tile`，并把 `P_tile @ V_tile` 累加到该 CTA 私有的 `O` tile 缓冲区中。这个私有 `O` tile 是运行中的累加器，在每轮 `K`/`V` 循环中更新。最后一轮结束后，CTA 对 `O` 累加器做归一化，并将完成的输出 tile 写入全局内存。

如果现在还有不理解的地方，不用担心，下面会详细解释每一步。这种划分基本类似于分块矩阵乘法：不同 CTA 生成不同输出 tile，而一个输出 tile 对应的循环留在其 CTA 内部。但与矩阵乘法不同，Attention 还需要在整个 `K`/`V` 循环中维护在线 Softmax 状态。

高层流程的伪代码如下：

```text
# purple arrow: independent work items mapped across CTAs
parallel_for batch, head, q_tile:

    # one CTA starts here
    Q = load_q_tile(batch, head, q_tile)

    # orange arrow: sequential loop inside this CTA
    for K, V in kv_tiles(batch, head):

        # Section A: Q @ K.T -> S
        S = Q @ K.T

        # Section B: S -> P, update rowmax/rowsum, and correct old O
        P, softmax_state, O = online_softmax_update(
            S, softmax_state, O
        )

        # Section C: add the current P @ V contribution
        O += P @ V

    # final normalization of this single O tile
    output[batch, head, q_tile] = O / softmax_state.rowsum
```

遍历 `Q` tile 的外层循环成为 CUDA grid；遍历 KV tile 的内层循环则留在每个 CTA 内部。上述伪代码标出的部分与第一个 B200 内核的代码直接对应，本章会详细讨论：

- A 部分）`Scores = Query @ Key.T`：使用 micro-tile 执行 `tcgen05`，采用 `K`-major 布局。
- B 部分）`Scores -> Probabilities`：从 TMEM 读取。
- C 部分）`O += Probabilities @ Values`：使用 micro-tile 执行 `tcgen05`，采用 MN-major 布局。

阅读第 1 章时请始终记住这个整体图景；接下来会逐步放大，说明内核如何实现上述伪代码的每一步。

**初学者入门，可选阅读**

本节可选。如果你已经熟悉分块矩阵乘法、内存布局、数据逻辑视图与物理视图的区别，以及如何用指针对内存进行索引，可以跳过。

**与分块矩阵乘法的相似之处：**

先建立一个后面会用到的基本直觉：分块矩阵乘法。

![](https://picx.zhimg.com/v2-bd7b9d1347d1670cbc9c59ded13ef23d_r.jpg)

普通分块矩阵乘法将两个操作数矩阵都拆成 tile，使较小的 tile 能装进高速但容量有限的片上存储，从而可以直接在片上多次复用每次加载的数据。每一轮沿归约维推进，图中为 `K` 维，将匹配的 A、B tile 相乘，再把部分结果累加到同一个 C tile。处理完所有 `K` tile 后，将这些部分结果相加，在数学上等价于不拆分 `K` 维的完整矩阵乘法。Attention 的形式与之相似，但并不完全相同：

- 一般的分块矩阵乘法固定一个 C tile，沿其归约维遍历。
- Attention 固定一个 `Q` tile，沿 `K`/`V` 的序列维遍历。

**引入布局：**

现在，全局内存中存放着我们的数据 tile。假设要将一个 A tile 和一个 B tile 相乘。我们不想用软件手动遍历各元素，再用标量指令计算点积，因为那会非常慢。我们希望使用 Tensor Core，而在 Blackwell 上使用 Tensor Core，需要采用 `tcgen05.mma` 指令族。上图中的 `tile_a` 和 `tile_b` 看起来是二维矩阵，但它们只是已存数据的逻辑视图，实际内存是一维的。

![](https://pic3.zhimg.com/v2-44c6c98045e8cec2bf6e2f8de9853366_r.jpg)

因此，数据在物理内存中总是按照某种方式“排布”的。假设 GMEM 中的 A 操作数采用行主序。那么，各行在一维内存中依次连续存放，如上图所示。要在这段线性内存中找到某个 `[row, col]` 元素，需要从基指针出发，利用 stride 计算偏移量。例如有一个很小的 `[2,2]` 矩阵，我们想取得 `my_matrix[1,1]`。

![](https://pica.zhimg.com/v2-b8523e4461fd3681cd268d39581f4e16_r.jpg)

这些二维 tile 总会以某种方式放入物理内存。布局就是把 `[row, col]` 这样的逻辑坐标映射到物理内存地址的规则；行主序就是一种布局。但我们想调用的 `tcgen05.mma(tile_A, tile_B)` 不能使用这种简单的行主序物理布局。它只支持少数几种非常特定的布局，不只是普通行主序或列主序。MMA 具体要求哪些布局，暂时还不重要，后面会讲。

`tcgen05` 要求数据按特定布局组织，也就是按特定方式存放在内存中。此外，它不支持直接使用 GMEM 操作数，因为 GMEM 带宽太低，操作数必须先写入高速片上存储。本节要记住：我们需要在 SMEM 中，把 A、B 操作数排布成 `tcgen05` 支持的某一种布局。

**离开入门小节，回到主线：**

如前两幅图和伪代码所示，每个 CTA 内的 `Q` 保持不变，每轮 `K`/`V` 循环计算：

- A）`Q @ K.T -> S`
- B）`S -> P`
- C）`P @ V -> O`

这就是沿 `SEQ_LEN` 遍历的 KV 循环每轮执行的三项主要计算。下面放大观察一轮循环，逐一讲解这三步。

**A）`Q`@`K`.T：解释 `K`-major**

一轮 `K`/`V` 循环内部：三步中的第 1 步。执行 QK 前，`Q` 和当前 `K` tile 必须已经在 SMEM 中。`Q` 由 CTA 加载一次，每轮 `K`/`V` 循环则加载新的 `K` tile。`Q`、`K` 使用相同布局，所以下面只画 `Q` 的复制过程，省略 `K`。

![](https://pica.zhimg.com/v2-57493eb479f726b82dbe1b6115da8de4_r.jpg)

注意：QK 矩阵乘法的图和代码片段采用常规矩阵乘法维度名称：`Q`[M,`K`] @ `K`[N,`K`].T = `S`[M,N]。这是局部矩阵乘法的轴名，不是内核输入全局张量的轴名。前面说过，Blackwell 的 Tensor Core 通过 `tcgen05` 指令族使用。`tcgen05.mma` 要求操作数按特定布局组织，不能随意把 tile 从全局内存复制到共享内存后就执行 MMA。因此，我们必须将数据排布成 MMA 支持的布局之一。

那么，具体应如何在 SMEM 中排布数据，才能让 MMA 使用？为简单起见，只说明 `Q` tile 从 GMEM 到 SMEM 的复制过程，`K` tile 同样独立执行此过程。在逻辑上，我们将 `Q` tile 纵向切成若干条带，图中示意为 4 条，再用 TMA 逐条从 GMEM 复制到 SMEM，见上图[2]。为什么要这样切分 tile，而不是一次复制整个 tile？这是个好问题，先记在心里。我不想一次引入太多东西，等真正需要时再回来解释。现在只需记住，我们按条带复制。

复制完所有条带后，从 GMEM 到 SMEM 似乎没发生变化：图上仍是同一个逻辑 `[BLOCK_M, BLOCK_K]` 矩阵，只是现在位于 SMEM。但物理表示实际上变了，见上图绿色的“Physical view”标注。SMEM 中的结果不再是 GMEM 原有的行主序，而是先存一个条带的所有行，再存另一个条带的所有行，依此类推。

每个条带内部采用行主序，但整个 SMEM 中 `[BLOCK_M, BLOCK_K]` 的布局并非简单的行主序或列主序，而是 `tcgen05.mma` 支持的所谓“规范布局”（canonical layout）之一。记住这个术语，后面会经常遇到。

![](https://pic4.zhimg.com/v2-01868fd32530b0c00265f3fbdbf47c0d_r.jpg)

上图用另一种方式展示同一个 `Q` tile 在 GMEM 与 SMEM 中的物理表示差异。粉色箭头表示元素的物理顺序。GMEM 采用普通行主序；SMEM 则采用 `tcgen05` 能解释的规范布局。图中具体是 `K`-major、无 swizzle 的布局，稍后再讲。`K`-major 中的“`K`”不是 Key 张量，而是常规矩阵乘法命名中的归约维。在这里，它沿逻辑 tile 的水平方向延伸。上面的每条纵向条带只覆盖 `K` 维的一小部分。

暂时可以忽略这些细节，为简单起见，把它当成 `tcgen05` 唯一支持的布局。我不想一次引入太多概念，其他布局会在需要时讨论。这里主要强调：使用 TMA 复制纵向条带，改变了数据的物理组织方式。为什么物理布局必须这样，而不是其他任意方式？这看起来确实不直观，但我认为除了“NVIDIA 文档规定这是 `tcgen05` 支持的规范布局之一”以外，并没有更深的直觉解释。有些事情最终就是硬件契约，我们必须以它为准。

下面是稍作简化的复制代码。每轮由 `src_col` 选择 `Q` 接下来的 8 列，`dst_smem` 则选择所复制条带在 SMEM 中的存放位置。`Q_tmap` 保存 TMA 读取 `Q` 所需的元数据：全局内存地址、dtype、维度、stride 和复制形状。这里的形状是 `BLOCK_M` 行、8 列的 BF16 数据。TMA 结合这些元数据、源坐标和 SMEM 目标指针，复制选定条带。

注意源和目标的指定方式不同。对 `Q`，我们给 TMA 行列坐标，由 `Q_tmap` 描述坐标如何映射到全局内存；对 SMEM，则直接给字节地址。因此 `src_col` 的单位是列，而目标偏移量的单位是字节。

```text
int SLICE_COLS = 8;
int SLICE_BYTES = (BLOCK_M * SLICE_COLS) * 2;  // each BF16 value is 2 bytes

// one thread issues all copies in this loop
for (int slice = 0; slice < BLOCK_K / SLICE_COLS; ++slice) {
    // move right to the next source slice
    int src_col = slice * SLICE_COLS;               // column idx

    // Q_smem is starting byte address in SMEM,
    // place next slice after the previous one in SMEM
    int dst_smem = Q_smem + slice * SLICE_BYTES;    // byte address

    // TMA copy
    tma::copy_2d_gmem_to_smem(
        dst_smem,            // destination byte address in SMEM
        &Q_tmap,             // Q's metadata (address, dtype, dims, strides, and copy size)
        src_col,            // starting source column (advances by 8 each iter)
        q_row0,              // this Q tile's first global row (stays fixed)
        mbar_addr            // barrier to track copy completion
    );
}
```

这里没有遍历行的软件循环，每次 TMA 调用复制完整的 (`BLOCK_M`, 8) 条带。我们将 SMEM 目标地址增加 `SLICE_BYTES`，使新条带紧跟前一个条带。所以物理内存中先是条带 0 的所有行，再是条带 1 的所有行，依此类推，如上图所示。这里 `BLOCK_K = 128`，因此循环发起 16 次复制。简化图只画了 4 条。屏障设置和等待完成的代码在此省略。以上讲完 TMA 部分：把数据从 GMEM 复制到 SMEM。现在讨论 MMA 部分：如何对已经准备好的 SMEM 数据真正执行 MMA。

TMA 只是复制机制，并不知道后面要调用什么 `tcgen05.MMA`。另一方面，`tcgen05.MMA` 只知道如何解释少量特定布局，并不知道待读取的数据最初如何进入 SMEM。因此可以把它们看成前面讲过的加载部分与下面要讲的 MMA 部分。这两个步骤彼此独立、互不知情，确保它们采用一致布局是我们的责任。

![](https://pic4.zhimg.com/v2-53bc04149d848a33e58a8098da6ab3cf_r.jpg)

图示简化说明：为方便阅读，图中使用 `BLOCK_K` = `HEAD_DIM` = 32 个 BF16 元素，即 64B。下面的文字和代码使用 `BLOCK_K` = `HEAD_DIM` = 128，即 256B。原理完全相同，只是实际代码的条带数量是图中的 4 倍。

回顾一下：之前沿 `K` 维以 16B 宽的条带，将 `Q_tile` 和 `K_tile` 分别复制到 SMEM。现在需要将形状为 `(block_m, block_k)` 的 `Q` tile 与 `(block_n, block_k).T` 的 `K` tile 相乘。先只看 `Q`，也就是 `tcgen05.mma` 的第一个输入，暂时省略第二个输入 `K`。

我们的 tile 在 `K` 维有 `BLOCK_K = 128` 个元素；BF16 下即 256 字节。但一条 `tcgen05.mma` 在 `K` 维只消耗 `MMA_K` = 16 个 BF16 元素，即 32B[^3]。`MMA_K` 小于 tile 的 `K` 宽度，因此需要一个 for 循环，以 32 字节为步长遍历 `Q`、`K` tile 的 `BLOCK_K` 维；图中黄色表示对 SMEM 数据进行的软件循环。

`Q` 的每条条带在 `K` 维宽 16B，而一条 `tcgen05.mma` 消耗 32B。因此，相邻两条 `Q` 条带组成一个 `Q` micro-tile。上图每对同色条带就是一个 micro-tile。

这里的 micro-tile 指 `tcgen05` 直接消耗的 `BLOCK_M = 128`、`MMA_K = 16` 数据块。micro-step 指一次 `tcgen05.mma` 调用，它消耗一个 `Q` micro-tile 和对应的 `K` micro-tile。由于 `BLOCK_K = 128`、`MMA_K` = 16，`128 / 16 = 8` 个 micro-step 即可覆盖整个归约 `K` 维。简化图画出了其中两个 micro-step。

![](https://pic3.zhimg.com/v2-b353225cf04fddcfed34e41058323e1c_r.jpg)

为了更直观，我也画出了 `K_tile`。`K` 同样独立切成 16B 宽的条带并由 TMA 复制，每两个条带视作一个 micro-tile。因为与前面 `Q` 的过程相同，所以图中省略了复制 `K_tile` 的过程。将 `Q_tile` 与 `K_tile` 相乘，基本上就是将对应 micro-tile 相乘，见上图红框：

- 第 1 个 `Q` micro-tile @ 第 1 个 `K` micro-tile .T
- 第 2 个 `Q` micro-tile @ 第 2 个 `K` micro-tile .T

图中的 `output_accum` 就是分数 tile `S`。在 Blackwell 上，`tcgen05.mma` 将输出累加到 Tensor Memory（TMEM）；这是独立于 SMEM 和寄存器的专用片上存储。更早的 GPU 则将 Tensor Core 累加器放在寄存器中。所有 QK micro-step 都累加到 TMEM 中同一个 `S` tile。现在只需记住 MMA 输出位于 TMEM；到 B 部分 Softmax 需要读取 `S` 时，再解释 TMEM 的分配和访问。

我们将上面逐条展开的 MMA 调用改成一个循环，以 `MMA_K` = 16 的 micro-step 遍历 `Q_tile`、`K_tile` 的 `BLOCK_K` 维。伪代码如下：

![](https://pic3.zhimg.com/v2-4616154043d0f8de1ffffc76e0c5d224_r.jpg)

下面是实际内核中稍作简化的“黄色”循环，由一个线程执行：

```text
// tcgen05 mma_k width along K-dim
int MMA_K_BYTES = 32; // in bytes
int MMA_K = 16; // in BF16 values

// for now, think of each K-major SMEM "descriptor" as a
// pointer-like value selecting current micro-tile
// (it also contains some layout metadata, covered later)
uint64_t q_desc = noswizzle::desc_kmajor(Q_smem, BLOCK_M);
uint64_t k_desc = noswizzle::desc_kmajor(K_smem, BLOCK_N);

// offsets to advance the descriptors to next Q and K micro-tiles
// (minor detail, divide by 16 because descriptor addresses are encoded in 16B units)
uint64_t q_desc_step = (BLOCK_M * MMA_K_BYTES) / 16;
uint64_t k_desc_step = (BLOCK_N * MMA_K_BYTES) / 16;

// BLOCK_K = 128, MMA_K = 16, so 8 micro-steps
for (int k = 0; k < BLOCK_K / MMA_K; ++k) {

    // one micro-step
    tcgen05::mma_f16(
        taddr_s, q_desc, k_desc,
        /*MMA shape and dtypes=*/i_desc_qk,
        /*enable_input_d=*/(k == 0 ? 0 : 1));

    // advance descriptors to the next pair of micro-tiles
    q_desc += q_desc_step;
    k_desc += k_desc_step;
}

// make mbarrier track completion of all 8 micro-steps
tcgen05::commit_arrive(mbar_addr);
// the wait and required synchronization are omitted here
```

每轮对下一个 `MMA_K` = 16 的数据块调用 `tcgen05.mma`，并累加到同一个 `S` tile。第一个 MMA micro-step 初始化 `S`，余下 7 个 micro-step 继续累加。遍历所有 micro-tile 并等待完成后，`S_tile` 就包含 `Q_tile` @ `K_tile.T` 的结果。

无需显式转置 `K_tile`。`Q`、`K` 均使用 `K`-major 布局。MMA 的 A 操作数直接读取 `Q`[m,k]；对于 B 操作数，`tcgen05.mma` 将已存 `K` tile 解释成 `Q` @ `K`.T 所需的 [k,n] 操作数。`K`-major 本身不意味着“转置这个操作数”：A、B 是不同的 MMA 操作数槽位，逻辑形状分别为 `[M,K]` 和 `[K,N]`，所以 MMA 对它们的解释不同。

现在已经看过 QK micro-step 循环的代码。此前我们把 `q_desc` 和 `k_desc` 看作选择当前 micro-tile 的类指针值。下面展开这些描述符还包含哪些布局信息，以及 MMA 如何用它们定位 micro-tile 内部的数据。

![](https://pic4.zhimg.com/v2-d08d4559162c75e8d8466a366d2115c5_r.jpg)

这里其实还有更细的一层粒度。放大观察一个 `Q` micro-tile，即 `BLOCK_M = 128`、`MMA_K = 16`；相同逻辑也适用于 `K` micro-tile。micro-tile 本身由更底层的单元构成，称为 atom。CUDA 文档也称它们为“swizzle atom”。注意我们此时并未进行 swizzle；即使 swizzle 模式是 None，NVIDIA 仍将“swizzle layout atom”作为总称，见[表 53](https://docs.nvidia.com/cuda/archive/13.0.0/parallel-thread-execution/#tcgen05-smem-swizzle-mode)。

atom 的大小取决于采用的规范布局。在这里，即 `K`-major 无 swizzle 布局下，atom 的尺寸为 (8, 8)[^4]。暂时仍可忽略布局细节，假定这是 `tcgen05.mma` 唯一支持的布局。从上到下总结，见上图图例：一个 micro-tile 由两条条带组成，每条条带又由 atom 组成。我们需要理解 atom 在 SMEM 中的排布，但它们不是可以单独编程的 MMA 单元。发起 MMA 时，操作粒度仍是 micro-tile，而非单个 atom。

现在可以回答前面的问题：为什么要用 TMA 按 8 个元素宽的纵向条带复制 `Q`、`K`，而不是一次复制整个 tile？之前的条带宽度不是随意选择的，而是恰好一个 atom 的宽度。对 `Q` 而言，每条 `(128,8)` 条带是一叠纵向排列的 `(8,8)` atom。我们将 tile 切成这些条带，每次用 TMA 复制完整一叠，并在 SMEM 中将各叠依次存放。这就形成 `tcgen05.mma` 支持的 `K`-major atom 物理顺序。

![](https://pic1.zhimg.com/v2-1f1a60d8c55e47efd7ef30f0e075f580_r.jpg)

记住，前面说过，“黄色”循环每轮都向 `tcgen05.mma` 提供两个数据 micro-tile：一个 `Q` micro-tile 和一个 `K` micro-tile。对于单个 micro-tile，无需给 MMA 提供其中所有 atom 的地址，只需提供第一个 atom 的基指针，见上图高亮部分。

随着黄色循环推进，基指针从一个 micro-tile 移向下一个 micro-tile。第一轮指向青色 atom，即 micro-tile 0 的起点；第二轮指向紫色 atom，即 micro-tile 1 的起点；如此沿 `K` 维推进。`K` 操作数描述符也做同样的事。但基地址只指向第一个 atom，因此直觉上，除了基地址以外，MMA 还必须知道如何从当前 micro-tile 的第一个 atom 走到同一 micro-tile 中的其他 atom。

![](https://pic2.zhimg.com/v2-4b726096e96978ae56ac3c7f72a299a1_r.jpg)

为此引入 SBO 和 LBO，见上图。它们不会增加软件循环次数，而是描述同一 micro-tile 中其他 atom 相对基指针的位置。SBO 告诉 MMA 如何到达同一条带的下一个 atom；LBO 告诉 MMA 如何到达下一条带中索引相同的 atom。对当前讨论的 `K`-major 无 swizzle SMEM 布局，每个 atom，以及每条纵向条带，宽度都是 8 个 BF16 元素，即 16B，因此：

```text
SBO = 8 rows * 16B per row = 128B   // step over one atom
LBO = BLOCK_M rows * 16B per row = 2048B    // step over one complete slice of atoms
```

这里 LBO 就是 `Q` 复制循环中的 `SLICE_BYTES`，也就是 SMEM 中相邻纵向条带的偏移。一个 `Q` micro-tile 包含两条条带，因此循环将描述符基地址增加 `2 * SLICE_BYTES` 字节，便可到达下一个 micro-tile。描述符地址以 16 字节为单位编码，所以除以 16 后，就得到上面代码使用的 `q_desc_step`。合起来看，软件循环把基指针从一个 micro-tile 移到下一个，而 SBO、LBO 描述当前 micro-tile 内部其他 atom 的偏移。

**B）在线 Softmax：解释 `S -> P`**

一轮 `K`/`V` 循环内部：三步中的第 2 步。现在已讲完第一次矩阵乘法 `Q`@`K`.T，接下来进入内核的在线 Softmax 部分，即 `S -> P`。在线 Softmax 的数学是标准内容，并非 B200 特有，已有很多讲解，所以这里不重新推导。我只概述所需状态更新，然后重点介绍 B200 内核如何实现。

![](https://pic1.zhimg.com/v2-6194da1a6acdc118619d2346df233c54_r.jpg)

A 部分已简要见过 TMEM：`Q` @ `K`.T 的各个 micro-step 在那里累加出 `S`。现在放大观察 TMEM 本身，看看在线 Softmax 如何读取 `S` 并转换成 `P`。TMEM 的结构为 128 行、512 列，且必须显式分配。`K`/`V` 循环前，内核 1 为 `S` 分配 128 列，为 `O` 再分配 128 列。分配以列为单位，每列包含 128 个元素，因此分配 128 列就得到 [128,128] 的 FP32 TMEM 存储块。

`S` 保存当前 `K`/`V` tile 的分数，每轮 `K`/`V` 循环都会覆盖。`O` 是运行中的输出累加器，后面 C 部分的 `P`@`V` 每轮向其中累加。`tcgen05.alloc` 将所分配区域的 TMEM 基地址写入共享内存槽 `tmem_addr`，再将该分配区域划分成 `S`、`O` 两个地址：

```text
int TMEM_S_COLS = 128;
int TMEM_O_COLS = 128;

__shared__ int tmem_addr[1];

// simplified PTX notation
// warp selection and synchronization omitted.
tcgen05.alloc(tmem_addr, TMEM_S_COLS + TMEM_O_COLS);

// first 128 columns for S, next 128 for O.
int taddr_s = tmem_addr[0];
int taddr_o = taddr_s + TMEM_S_COLS;
```

把之前的这层抽象展开：

```text
# Section B: S -> P, update rowmax/rowsum, and correct old O
P, softmax_state, O = online_softmax_update(
    S, softmax_state, O
)
```

一轮 `K`/`V` 迭代中的状态变化如下，先看伪代码：

```text
// Section A, covered earlier
// S = Q @ K.T;

// Section B:

tile_rowmax = row_max(S);
// new basis
new_rowmax  = max(running_rowmax, tile_rowmax);

// rescale old state to the new basis
rescale     = exp(running_rowmax - new_rowmax);
running_rowsum *= rescale;
O              *= rescale;

// produce P and update denom
P               = exp(S - new_rowmax);
running_rowsum  += row_sum(P);
running_rowmax   = new_rowmax;

// Section C, covered later:
// O += P @ V;
// after complete K/V loop:
// output = O / running_rowsum;
```

这是通用在线 Softmax 更新，并非 B200 特有，因此不再多讲。主要问题是如何把它映射成 B200 内核。上述伪代码有许多个状态更新，但内核中整个在线 Softmax 工作主要围绕三次 TMEM 遍历组织，其他状态更新大多融合进这三次遍历中。因此，可以把它理解为“对 TMEM 中的数据 tile 做三次遍历”。

三次遍历可分为：

- 两次遍历 `S` tile，共同用于生成 `P`。
- 一次遍历 `O` tile，用于对 `O` 重缩放。

源码中的 `O` 重缩放位于两次 `S` 遍历之间。但由于两次 `S` 遍历的方式相同，我会把它们放在一起解释，再回来讲 `O` 重缩放。下面依次说明，随后对照代码。

**i）生成 `P`**

先讲两次 `S` 遍历如何将 `S` 转成未归一化的 `P`[5]；之后 `P` 会用于 `P`@`V` 矩阵乘法。为此，内核 1 对 TMEM 中 `S` 的每一行遍历两次：

- 第一次计算各行最大值，为第二步提供数值稳定性。
- 第二次减去行最大值并取指数，即 `exp(S - new_rowmax)`，生成未归一化 `P`。

在取指数前，先计算 `S` 每行最大值并从该行各元素减去它，称为 max trick，是 Softmax 实现常用的数值稳定技巧。`S` 中可能有很大的正分数，直接取指数可能溢出。减去行最大值，使 `exp` 输入都变成零或负数，在不改变 Softmax 结果的同时避免溢出。因此，不先减去 `rowmax` 就直接算 `exp(S)`，通常不具备数值稳定性。

之所以要做两次遍历，是因为实现没有把所有 `S` 保留在寄存器中。第一次按块从 TMEM 加载 `S`、更新逐行最大值，然后复用同一组寄存器加载下一块。完成第一次完整遍历时，早先读取的数据已不在寄存器中。为了生成 `P`，必须第二次从 TMEM 读取 `S`，减去更新后的行最大值，再取指数。

**第一次 `S` 遍历：计算 `rowmax`**

先看第一次遍历如何扫描 `S` 并计算逐行最大值，先看图，再看代码。

![](https://pic3.zhimg.com/v2-695bd66eea35c1bd541e791a74c7c12a_r.jpg)

只有 `tcgen05` 指令族能访问 TMEM，普通 load/store 不行。计算逐行最大值前，必须先加载 TMEM 中的数据，因此这里用 `tcgen05.ld`（ld 表示 load）将数据从 TMEM 加载到寄存器。从左到右读这幅图。我们分三个层次追踪 TMEM 遍历：整个 CTA、一个 warp、以及该 warp 中的一个线程。TMEM 中的 `S` tile 为 128 行、128 列。

从 CTA 角度看，4 个 warp 分摊 `S` 的 128 行，每个 warp 负责一个 `(32,128)` 的行块。因此内核 1 使用 4 个 warp，以 32 行为单位覆盖并并行处理全部 128 行。但每个 warp 不会一次读完整个 `(32,128)` 块。那会导致寄存器溢出：寄存器不足以容纳四个这样的块，编译器就会把部分数据写入极慢的全局内存。为避免这一点，4 个 warp 各自以更小的 `(32,8)` 步长遍历自己的 `(32,128)` 块[6]。因此需要一个遍历 TMEM 列的 for 循环。

放大到单个 warp：每轮使用 `tcgen05.ld` 从 TMEM 加载 32 行、8 列的数据块。32 个线程共同参与一条加载指令，`tcgen05.ld` 是 warp 集体操作。它将加载的 32 行分配给 32 个线程，每线程一行。因此，每线程收到自己那一行的 8 个 FP32 值，32 个线程合起来持有完整 `(32,8)` 块。从一个线程角度看，每轮始终跟踪同一行，一次收到 8 个值；它遍历这 8 个值，保留目前见过的最大值。

换句话说，加载是 warp 集体操作，而行计算是线程局部操作。每线程分批看到该行全部 128 个分数，每批 8 个，因此可在第一次 `S` 遍历中独立求出行最大值。这就是每个线程能在寄存器中维护自己的 `tile_rowmax` 标量的原因。每个线程在整个 `K`/`V` 循环中始终处理同一查询行。`rowmax` 和 `rowsum` 跨迭代保留，而 `tile_rowmax`、`tile_rowsum` 则对每个 tile 重新计算。

因此，4 个 warp 合起来每轮处理 `S` 的一个 `(128,8)` 块，再向右移动 8 列重复。经过 128 / 8 = 16 轮，4 个 warp 遍历 `S` 全部 128 列。循环结束时，每个线程都持有某一 TMEM 行的最大值。

代码调用 `tcgen05::ld_32x32b_x8` 辅助函数：.32x32b 表示加载 32 行 TMEM，每行一个 32 bit 值；.x8 表示在 8 列上重复该形状，并且仍是一条 `tcgen05.ld` 指令。于是每线程把 8 个 32 bit 行元素放入自己的 8 个寄存器。这就是图中的 `(32,8)` 块。下面是第一次 `S` 遍历的代码。每线程维护自己的 `tile_rowmax`，在经过各数据块时更新。

```text
float tile_rowmax = -FLT_MAX;

for (int score_n8 = 0; score_n8 < BLOCK_N / 8; ++score_n8) {
    // 8 FP32 temporaries per lane
    float s8[8];

    int addr = ... // covered below
    tcgen05::ld_32x32b_x8(addr, s8);

    for (int i = 0; i < 8; ++i) {
        tile_rowmax = fmaxf(tile_rowmax, s8[i]);
    }

}
```

那么，我们如何告诉这条指令要读取哪个数据块？`S` tile 的 `[BLOCK_M, BLOCK_N] = [128,128]` 分别对应 TMEM 的行和列。如前所示，4 个 warp 分别覆盖不同的 32 行区域，而每个 warp 的循环沿列推进。TMEM 地址是一个包含两个坐标的 32 bit 值，而不是普通字节地址：

```text
[ upper 16 bits: row ][ lower 16 bits: column ]
```

PTX 将 TMEM 的行称为“lane”。对于当前加载方式，这两个坐标指定整个 warp 数据块的起始行和列，而不是分别给每个线程指定行列。

地址构造如下：

```text
// first row of this warp's region:
// 0, 32, 64, or 96, depending on the warp_id
int row_base = warp_id * 32;
// bitshift to the upper 16 bits
int trow = row_base << 16;

// inside the loop over S columns
int taddr =
    trow                // starting row, encoded in the upper bits
    + taddr_s           // starting column of S
    + score_n8 * 8;     // current chunk's column offset within S
```

`<< 16` 将 `row_base` 移到高 16 位，低半部分为零。列号数值很小，自然位于低 16 位，高半部分为零，无需移位。下面每对括号表示 16 位：

```text
row_base << 16:  [row_base][  0   ]
column:          [   0    ][column]
sum:             [row_base][column]

(here, column = taddr_s + score_n8 * 8)
```

两个字段不重叠，因此用普通加法即可把行列组合成一个 TMEM 地址。注意，32 个线程传入相同的 `taddr`。对于这个加载形状，硬件利用线程的 lane ID，将 `row_base + lane_id` 行的数据分配给它。我们不自己把 `lane_id` 加到地址中，这与 `ld.global` 的普通逐线程寻址不同。例如 `row_base` = 32 时：

- lane 0 收到第 32 行的数据。
- lane 1 收到第 33 行的数据。
- ……
- lane 31 收到第 63 行的数据。

这就是 warp 集体加载的含义：同一 warp 的 32 个线程共同参与同一条加载指令。这里它们使用相同 `taddr`，但每个线程收到自己那一行的 8 个值。循环推进时，`trow` 不变，而列偏移量每次增加 8。

**第二次 `S` 遍历之前：更新累计 `rowmax`**

得到当前 `S` tile 的逐行最大值后，需要按在线 Softmax 定义更新累计 `rowmax`、`rowsum`。第一次遍历得到 `tile_rowmax`，即当前 `S` tile 中该行的最大值；第二次遍历使用的却是包含先前 `K`/`V` tile 在内的累计最大值。因此，第二次遍历前，要将 `tile_rowmax` 与旧 `rowmax` 合并，并对旧 `rowsum` 重缩放。这些都是寄存器中的逐线程标量更新，不是再遍历一遍 `S`。

取两个最大值中的较大者，并计算重缩放因子：

```text
float new_rowmax = fmaxf(rowmax, tile_rowmax);
float rescale = __expf(rowmax - new_rowmax);

rowmax = new_rowmax;
rowsum *= rescale;
```

如果当前 tile 提高了累计 `rowmax`，那么旧 `rowsum` 是按之前的最大值计算的，必须乘以 `rescale`，才能让早先贡献与更新后的最大值一致。第二次 `S` 遍历会使用更新后的 `rowmax` 生成 `P`。同一个 `rescale` 也必须施加到旧 `O` 上，稍后在 ii 小节说明。

**第二次 `S` 遍历：生成 `P` 并更新 `rowsum`**

现在有了更新后的累计行最大值，再遍历一次 `S`。分块重读 `S`，从分数中减去这些 `rowmax`，再安全地取指数，生成未归一化 `P`。TMEM 遍历方式与第一次相同，因此不另画遍历图。变化在于每线程对加载的 8 个值做什么：减去更新后的累计 `rowmax`、取指数、将结果加入该行的和，并将 `P` 写入 SMEM。仔细看看第二次遍历如何把 `P` 写入 SMEM。

![](https://pic2.zhimg.com/v2-f2974b232fdc6f4fb001508e91b9a0c9_r.jpg)

每读一块 `S`，就生成对应的一块 `P`，并写成 `K`-major SMEM 布局。这是后面 `P`@`V` MMA 所要求的布局。第二次 `S` 遍历每轮产生 8 列 `P`。相邻两块组成一个 16 列的 `P` micro-tile，由后续 PV MMA micro-step 消耗。TMEM 中的 `S` 本身不变。`P` 存入之前存 `K` 的同一个 SMEM 缓冲区。QK 结束后 `K` 已无后续用途，因此可以安全复用其空间存 `P`。

下面是第二次 `S` 遍历的代码，从 TMEM 读 `S`，并向 SMEM 写 `P`。

```text
int row = row_base + lane_id;
float tile_rowsum = 0.0f;

for (int score_n8 = 0; score_n8 < BLOCK_N / 8; ++score_n8) {
    float s8[8];

    int addr = ...; // same TMEM address calculation as the first pass
    tcgen05::ld_32x32b_x8(addr, s8);

    for (int i = 0; i < 8; ++i) {
        float p = __expf(s8[i] - rowmax);
        tile_rowsum += p;

        // write P into K-major SMEM
        int col = score_n8 * 8 + i;
        int p_idx = idx_kmajor_w8(BLOCK_M, row, col);
        P_smem_ptr[p_idx] = __float2bfloat16_rn(p);
    }
}

rowsum += tile_rowsum;
```

**将 `P` 写入 SMEM**

`idx_kmajor_w8` 计算每个 `P` 元素在熟悉的 `K`-major SMEM 布局中的位置，供后续 PV 矩阵乘法使用；该布局已在 A 部分介绍。辅助函数的具体实现并不重要，可以略过。这里需要 row 变量，因为这些是普通的逐线程 SMEM store，与 warp 集体 TMEM load 不同。

**ii）对 `O` 重缩放**

回到 `O` 重缩放。源码中，它位于两次 `S` 遍历之间。前面已算出新的最大值基准，但旧 `O` tile 仍处于旧基准下。因此，执行 `O += P @ V` 前必须重缩放 `O`。在在线 Softmax 中，在旧 `O` 转换到当前最大值基准之前，通常不能安全地向 `O` 累加 PV。之前将当前 `S` tile 纳入了累计 `rowmax`。`rowmax` 的改变会改变未归一化 `P` 的尺度，也就影响累加到 `O` 中的 `P`@`V` 贡献。因此，在加入当前 `P`@`V` 贡献前，必须重缩放旧 `O`，让早先贡献与新的 `rowmax` 对齐。

这是标准在线 Softmax 公式；这里唯一不同的是把它映射到 Blackwell B200 硬件。如前所述，`rowsum` 和 `rowmax` 是逐线程标量。`O` 不同，它是存于 TMEM 的完整 [`BLOCK_M`, `HEAD_DIM`] 部分累加 tile。因此，重缩放这些值需要读取 TMEM 中保存 `O` 的列，用刚从新旧 `rowmax` 算出的 `rescale` 乘它们，再写回 TMEM。必须写回，因为 `O` 仍是中间累加结果，并非最终输出；后续 PV 要继续在更新后的基准下累加。

每线程对自己 `O` 行的全部值使用同一个 `rescale`。第一次 `K`/`V` 迭代跳过此遍历，因为还没有旧 `O`；第一个 PV micro-step 会初始化 `O`。

```text
float o8[8];

for (int out_n8 = 0; out_n8 < HEAD_DIM / 8; ++out_n8) {

    // same TMEM address calculation as before, now for O
    int taddr =
        trow                // starting row, encoded in the upper bits
        + taddr_o           // starting column of O
        + out_n8 * 8;       // current chunk's column offset within O
    tcgen05::ld_32x32b_x8(taddr, o8);

    for (int i = 0; i < 8; ++i) {
        o8[i] *= rescale;
    }

    tcgen05::st_32x32b_x8(taddr, o8);
}
```

这里使用与 `S` 遍历相同的 4 个 warp、行归属和 8 列分块。新内容是：在寄存器里完成重缩放后，用 `tcgen05.st` 将修正后的 `O` 写回 TMEM。此处省略 store 完成等待和同步。完整内核确保 `O` 的写入在 PV 使用累加器之前完成。现在 `P` 已在 SMEM 中准备好，`O` 也已在 TMEM 中重缩放，C 部分便可把 `P` @ `V` 加入 `O`。

**C）`P`@`V`：解释 MN-major**

一轮 `K`/`V` 循环内部：三步中的第 3 步。前面介绍了如何生成 `P` tile，现在要将它与 `V` tile 相乘。与 `Q`、`K`、`P` 都使用 `K`-major SMEM 布局不同，`V` 使用另一种 SMEM 布局。这就是接下来的主题。在内核 1 中，`P_tile` 由 Softmax 直接生成到 SMEM，因此下面的全局内存视图不画 `P`。实际内核在 QK 之前随 `K` 一起加载 `V`。这里才讲 `V` 的复制，是为了把它的 SMEM 布局与消费它的 PV 矩阵乘法放在一起讨论。

![](https://pic4.zhimg.com/v2-15cdb991661baf8351517b7b9216487b_r.jpg)

注意：矩阵乘法图和代码片段以矩阵乘法为中心命名维度；实际内核源码则保留固定的 Attention tile 维度名。下面 PV 图采用常规矩阵乘法维度名：`P`[M,`K`] @ `V[K,N]` = `O`[M,N]。先退一步解释为什么把轴叫作 M、N、`K`。我对每次矩阵乘法分别使用常规 M/N/`K` 命名，因为这样单独观察每次乘法时，输入形状更容易理解。因此，这些是面向矩阵乘法的局部名称，不是全局张量 `Q`、`K`、`P`、`V` 固有的属性。

同一个源维度在 QK、PV 中可以有不同的局部名称。`K` 维总指当前矩阵乘法的归约维：QK 中是特征维，PV 中则是 `K`/`V` tile 的行维。现在回到 PV 矩阵乘法。`Q`、`K`、`V` 最初采用相同的全局内存布局，但内核根据各自 MMA 的消费方式，把它们放成不同的 SMEM 布局。为什么 `Q`、`K`、`P` tile 使用 `K`-major，而 `V` tile 要用下面介绍的另一种布局？因为 QK 需要把 `K` 看成转置后的矩阵；PV 的内部维度本来就匹配，`V` 无需转置。具体来说：

```text
QK: Q[M,K] @ K[N,K].T
PV: P[M,K] @ V[K,N]
```

QK 中，`K` 按 `[N,K]` 存储，MMA 却将 B 操作数视为逻辑 `[K,N]`。因此 `K` 使用 `K`-major，使 MMA 能把已存 `K` tile 解释成逻辑转置操作数，而无需先构造另一份转置 `K` tile。PV 中，`V` 已经是 MMA B 操作数所需的 `[K,N]` 方向，所以使用 MN-major，让 MMA 直接消费 `V`，而无需先转置 `V` tile。`P` 是 `[M,K]` 的 A 操作数，仍使用 `K`-major。

换句话说，对这些图使用的存储视图，我的速记方式是：

- `K`-major：归约 `K` 在右侧，如 `Q`[M,`K`]、`K`[N,`K`]、`P`[M,`K`]。
- MN-major 的 B 操作数：归约 `K` 在左侧，如 `V[K,N]`。

这只是我阅读这些操作数视图的速记方式，不是 `K`-major、MN-major 布局的正式定义。

![](https://picx.zhimg.com/v2-dbc0cf19d1a4a0a32d15597af3e8cde9_r.jpg)

它们是同一次 PV MMA 的两个操作数。`tcgen05.mma` 允许独立选择 A、B 的 major mode，因此 `P` 可以是 `K`-major，`V` 可以是 MN-major。左侧 `P` 使用与 A 部分 `Q` 相同的 `K`-major atom 顺序。数字表示递增的 SMEM 地址。两种布局都采用 `(8,8)` atom，区别在于哪些 atom 紧挨着存放，这决定每次 TMA 调用复制多少数据。

记住，对 `Q`，一次 TMA 调用复制整条纵向条带，并按正确顺序放置其中的 atom。`V` 的 SMEM 布局和 atom 顺序不同，因此需要重新考虑每次 TMA 调用应复制多少数据。为什么不和 `Q` 一样，按更大的条带复制 `V`？`Q` 的同一纵向条带中，各 atom 在 SMEM 中连续存放，因此一次 TMA 可复制整个条带。

看图中 `V` 的 atom 顺序：先沿第一个 8 行横带依次存放 atom，再向下移到下一个横带。因此，同一纵向条带的 atom 在 SMEM 中被其他 atom 隔开；一次 TMA 复制整条纵向条带，会把 atom 放错位置。那为什么不复制整个横带？我们使用的简单、无 swizzle 二维 TMA 复制会逐行存储矩形，得到普通行主序：一整行元素，接着下一整行。但目标布局要求先放完一个 `(8,8)` atom 的 8 行，再放下一个 atom。

所以我们一次复制一个 atom，显式选择每个 atom 在 SMEM 中的落点。下面是稍作简化的 `V` 复制循环。与 `Q` 不同，每次 TMA 复制一个 `(8,8)` BF16 atom，而非覆盖整个高度的纵向条带。`V_tmap` 与之前 `Q_tmap` 包含同类元数据，即全局地址、dtype、维度、stride，但复制形状现在是 8 行、8 列。`kv_row0` 是当前 `V` tile 的首个全局行。按图中命名，该 `V` tile 为 `BLOCK_K` 行、`BLOCK_N` 列。

```text
int ATOM_BYTES = (8 * 8) * 2;          // one 8x8 BF16 atom
int STRIPE_BYTES = (8 * BLOCK_N) * 2;  // one full 8-row stripe

// one thread issues all these TMA copies;
// barrier setup and completion wait omitted

// move down V, 8 rows at a time
for (int row8 = 0; row8 < BLOCK_K / 8; ++row8) {

    // copy one (8,8) atom per iteration, moving from left to right
    for (int col8 = 0; col8 < BLOCK_N / 8; ++col8) {

        // starting row and column of this (8,8) atom in global V;
        // element coordinates, not byte offsets
        int src_row = kv_row0 + row8 * 8;
        int src_col = col8 * 8;

        // V_smem is the starting byte address in SMEM
        int dst_smem = V_smem
                     + row8 * STRIPE_BYTES
                     + col8 * ATOM_BYTES;

        tma::copy_2d_gmem_to_smem(
            dst_smem, &V_tmap, src_col, src_row, mbar_addr);
    }
}
```

内层循环把完整 atom 在 SMEM 中相邻存放；外层循环向下移到下一个 8 行横带，再重复。这些偏移构造出上图所示的 MN-major 物理布局。对于 (128,128) 的 `V` tile，循环发起纵向 16 次、横向 16 次，共 256 次复制。我们并不遍历单个元素，每次调用会复制 `(8,8)` atom 的全部 64 个值。现在知道了 PV 两个操作数如何在 SMEM 中准备好：`P` 由前面 B 部分的 Softmax 生成，`V` 则按刚介绍的过程单独复制。下面看 MMA 如何消费它们。

![](https://pic1.zhimg.com/v2-d8c370161abc23fe1d5cb93ce6ffd110_r.jpg)

基本思想与 A 部分 QK 相同：图中的归约维 `BLOCK_K` 有 128 个 BF16 元素，而一次 `tcgen05.mma` 只消耗 `MMA_K` = 16 个。因此 PV 分成 `128 / 16 = 8` 个 MMA micro-step。为简单起见，图中只画 2 个。在这个 `V` 视图中，归约 `K` 是纵向的，所以一个 micro-step 消耗相邻两条 8 行横带。每个 micro-step 沿 `BLOCK_K` 消耗 16 个 BF16 元素，每个 BF16 占 2 字节，所以就是图中的 32 字节。

PV 循环结构与 QK 相同。`P` 使用 `K`-major 描述符，不同的是 `V` 使用 MN-major 描述符。指令描述符 `i_desc_pv` 指定 MMA 形状、数据类型和这些操作数模式。每个 PV micro-step 消费 `P` 的 16 列和 `V` 中对应的 16 行，并向同一 `O` tile 贡献结果。

```text
// P uses SMEM storage previously used by K
int P_smem = K_smem;

uint64_t p_desc = noswizzle::desc_kmajor(P_smem, BLOCK_M);
uint64_t v_desc = noswizzle::desc_mnmajor(V_smem, BLOCK_N);

// MMA_K = 16 BF16 values; MMA_K_BYTES = 32.
// descriptor addresses are encoded in 16-byte units
uint64_t p_desc_step = (BLOCK_M * MMA_K_BYTES) / 16;
uint64_t v_desc_step = (BLOCK_N * MMA_K_BYTES) / 16;

// one thread issues all MMA micro-steps
for (int k = 0; k < BLOCK_K / MMA_K; ++k) {

    // initialize O only on very first PV microstep,
    // every later microstep accumulates into existing O.
    // (kv_tile is zero-based index of the current K/V tile).
    int enable_input_d = (kv_tile == 0 && k == 0) ? 0 : 1;

    tcgen05::mma_f16(
        taddr_o, p_desc, v_desc, i_desc_pv, enable_input_d);

    p_desc += p_desc_step;  // next 16 columns of P
    v_desc += v_desc_step;  // next 16 rows of V
}

// track completion of all 128/16=8 PV microsteps
tcgen05::commit_arrive(mbar_addr);
```

与 QK 的一个区别是初始化条件。QK 每轮 `K`/`V` 迭代都创建新的 `S` tile；`O` 则必须保留先前 `K`/`V` tile 的贡献，它们已在 B 部分重缩放。因此，仅第一轮 `K`/`V` 迭代的第一个 micro-step 初始化 `O`，后续全部累加。第一轮还跳过 `O` 重缩放，因为尚无旧 `O`。循环将两个描述符推进到下一对 micro-tile。现在放大 `V` 描述符：基地址指向哪里，MMA 如何定位同一 micro-tile 的其他 atom？

![](https://pic1.zhimg.com/v2-f1cf210ea3436963083d5072f07c3c3c_r.jpg)

每个 PV micro-step 中，`V` 操作数描述符的基地址指向该 16 行块中的第一个 `(8,8)` `V` atom。micro-step 0 的 `V` 基地址是绿色高亮 atom。 micro-tile 循环随后把描述符移到下一个 16 行块， micro-step 1 的基地址就变成紫色高亮 atom。下图展示 LBO、SBO 如何从描述符基地址覆盖同一 micro-tile 中的其余 atom。

![](https://pic1.zhimg.com/v2-de41ccff9892aef89b6ab99b7da89b1a_r.jpg)

每个 PV micro-step 的描述符基地址，都指向第一条 8 行 `V` 横带的首个 atom。LBO 到达第二条 8 行横带中的对应 atom；SBO 则沿 N 维跨越宽度为 8 列的各个 atom。这些与 `V` 复制循环中的偏移完全相同。对于 128 列的 `V` tile：

```text
SBO = ATOM_BYTES   = 8 * 8 * 2       = 128 bytes
LBO = STRIPE_BYTES = 8 * BLOCK_N * 2 = 2048 bytes
```

因此，复制循环与 MMA 描述符对 atom 的位置达成一致：TMA 按这些偏移放置，MMA 用相同偏移找到它们。给定起始地址、两个偏移和 MMA 形状，一次 `tcgen05.mma` 就覆盖完整的 16 行 `V` micro-tile。

随后循环将 `P` 描述符移到下一个 16 列，将 `V` 描述符移到匹配的下一个 16 行。`V` 的下一 micro-tile 位于下方 16 行，即向下跨两条 8 行横带，所以基地址增加 2 * `STRIPE_BYTES` = 4096 字节。描述符地址以 16 字节为单位编码，除以 16 就得到上面代码中的 `v_desc_step`。

**拉回整体视角：一轮 `K`/`V` 迭代**

第 1 章 A、B、C 部分放大观察了一轮 `K`/`V` 循环内的各个步骤。现在回到完整一轮 KV 迭代的层面。上面的图省略了一件事：同步。TMA 加载和 `tcgen05.mma` 都是异步的。但内核 1 在每个主要交接点立刻等待：加载当前 `K`/`V` tile 后等待，运行 QK 后等待，完成行处理，再运行 PV 并等待。只有 PV 结束后才开始加载下一个 `K`/`V` tile。

因此，这个基础实现仍逐阶段串行运行。只有一个 `K`/`V` tile 处于存活状态，`K`/`V` 加载、QK、行处理和 PV 之间尚无有效重叠。后续内核才开始让这些阶段重叠。源码使用 `mbarrier` 判断异步 TMA、MMA 是否完成。`__syncthreads()` 只等待 CTA 所有线程到达同一点，并不会等待异步 TMA 或 MMA 完成。

收尾：整个 `K`/`V` 循环结束后，仍由同样的 4 个 warp 每次读 8 列 TMEM 中的 `O`。每线程将自己行的值除以最终 `rowsum`，转成 BF16，写入全局内存。与前面的 `O` 重缩放遍历不同，这里写的是最终输出，目标是全局内存，而不是 TMEM。

### 第 2 章：将 P 从 SMEM 移到 TMEM

内核 1 的第二次 Softmax 遍历从 TMEM 读 `S`，转换成未归一化概率 `P`，再将 `P` 写入原先存 `K` 的 SMEM 缓冲区。QK 后 `K` 已不再使用，因此可以安全复用。内核 2 改变 `P` 的存放位置：不再把 `P` 片段写入 SMEM，而是写回 TMEM。这是本章的主要变化。

这一改动不会减少 SMEM 使用量，但为后续优化做准备。内核 1 把 `P` 放入 `K` 不再使用的 SMEM 槽，耦合了两者生命周期：QK 后不再需要 `K`，但它的槽要一直由 `P` 占用到 PV 消费完，这并不理想。可以给 `P` 单独分配 SMEM，但后续优化几乎需要整个 SM 的 SMEM 预算。因此，内核将 `P` 移到 TMEM，在不增加 SMEM 分配的前提下解耦生命周期，后面会据此继续优化。

分配的 SMEM 不会减少，因为内核仍需要 `Q`、`K`、`V` 的存储空间。

![](https://pic3.zhimg.com/v2-778c94c7275c69f819cef25e1afb09ba_r.jpg)

进一步地，我们直接把 `P` 写进原来存 `S` 的区域，无需额外分配 TMEM。因为第二次 TMEM 遍历已经消费掉的 `S` 元素可以安全覆盖。因此，在内核 2 中，同一个 TMEM 槽的含义随时间变化：

- QK 后：槽内是 FP32 的 `S`。
- Softmax 第二遍：已消费的 `S` 块被打包的 BF16 `P` 覆盖。
- PV：将该槽作为 `P` 消费。

这确实耦合了 `S`、`P` 生命周期，但后面会看到，它不像 `P`、`K` 耦合那样棘手[7]。TMEM 以 32 bit 存储单元组织，而 `P` 是 BF16，因此两个 `P` 值可以打包进一个 TMEM 单元。`S` 是 FP32，一个分数占一个 b32 单元。所以 `P` 所需的 TMEM 列数是 `S` 的一半。

图中不同颜色箭头表示一次逻辑上处理 16 个分数的步骤。代码用两次 `tcgen05.ld.x8` 加载（橙色箭头），随后一次 `tcgen05.st.x8` 写入（绿色箭头）来实现。内核 1 按宽 8 的块处理 `P`；内核 2 每轮把两块合并，每行加载 16 个 FP32 `S`，生成 16 个 BF16 `P`。按宽 16 分组并非本质要求[8]。

回忆内核 1，生成 `P` 时按块遍历 TMEM，本章非常类似。新变化是把结果 `P` 块存入 TMEM：16 个 `P` 值打包进 8 个 b32 单元。因此 `S` 读指针前进 16 列，`P` 写指针只前进 8 列。每次 `P` 写入始终落在读指针之后，只覆盖第二次遍历已经消费的分数，因而不会破坏尚未读取的 `S`，图中也展示了这一点[9]。

`S` 占 128 个 TMEM 列，每次读取 16 列，共需 `128 / 16 = 8` 轮。结束后，低 64 个 b32 列包含完整的 128 列 BF16 `P` tile。`P` 只覆盖 `S` 缓冲区的一半，另一半保留不会再读的过期 `S` 值。下一轮 KV 循环的 QK 会用 `S`(i+1) 完整覆盖整个 `S`/`P` 槽。

![](https://pic4.zhimg.com/v2-4cdcf62f173f250566cfe7da7cc627ff_r.jpg)

PV 矩阵乘法不变：`P[BLOCK_M, BLOCK_K] @ V[BLOCK_K, BLOCK_N] -> O[BLOCK_M, BLOCK_N]`。只改变了 A 操作数 `P` 的来源。内核 1 的 `P`、`V` 都从 SMEM 消费；内核 2 的 `P` 从 TMEM，`V` 从 SMEM 消费。内核 1 的 `P` 需要 `K`-major SMEM 布局和 SMEM 描述符。内核 2 直接用 TMEM 地址标识 `P`，不再为 `P` 使用 SMEM 描述符。

`K`-major、MN-major 是 SMEM 布局，不用于 TMEM 操作数。`V` 仍是 MN-major 的 SMEM B 操作数。到这里已讲完 `P` 如何生成并写入 TMEM，而非第 1 章的 SMEM。现在再讨论 `P`@`V`，只是其中一个操作数 `P` 来自 TMEM。

![](https://picx.zhimg.com/v2-86f10162c2a6e12a4872760141dc4b2f_r.jpg)

记住，所有 MMA 图中的维度都采用常规局部矩阵乘法记号：A[M,`K`] @ B[`K`,N] = C[M,N]。PV 沿 `BLOCK_K = 128` 归约。与第 1 章一样，每次 MMA 消费匹配的 `MMA_K` = 16 micro-tile：`P[:, 16k : 16(k+1)] @ V[16k : 16(k+1), :]`。8 次调用覆盖完整的 `BLOCK_K = 128`。为避免图面拥挤，只画前两次。

![](https://pic4.zhimg.com/v2-667da93bead17c1d41f283f1a6adcba5_r.jpg)

循环沿用内核 1 的逻辑 `MMA_K` = 16 micro-tile 顺序，但通过 TMEM 地址选择 `P`，而不是推进 SMEM 描述符。`taddr_p + k * 8` 指向下一个 128x16 `P` micro-tile 的起点；每行的 16 个 BF16 值占 8 个 b32 列。`V` 描述符推进到匹配的 16 行，每次结果都累加到同一 `O` tile。`P` 现在由 `tcgen05.st` 产生，因此行线程在 PV 开始前必须等待这些 TMEM store，并执行 fence。这只是数据发布机制的小改动。

所以内核 2 不改变 Softmax 数学、PV 归约顺序和高层调度。唯一语义变化是：QK 在 TMEM 生成 `S`，Softmax 将该存储区域变为 `P`，PV 直接从 TMEM 消费 `P`。

### 第 3 章：Swizzling

前面已根据各源 tile 被 MMA 消费的方式，选择 `Q`/`K` 为 `K`-major、`V` 为 MN-major，见第 1 章。内核 3 保持调度和 major mode 不变，只分别改变各 tile 的 swizzle 模式：SMEM 中 `Q`/`K`/`V` 从无 swizzle 改为 SW128，以减少 bank conflict。`P` 留在 TMEM，因此不做 swizzle。

已有很多资料解释 swizzle 的动机，这里不重复，因为目标是理解 B200 相关概念。只需知道，swizzle 在每个 atom 内置换 SMEM 地址，使 Tensor Core 访问更好地分散到各 SMEM bank，避免 bank conflict。下面讲 B200 特有细节，而非通用 swizzle 教程。

Major mode 与 swizzle 是两回事，第 1 章已讨论。Major mode 指明每个 16B 元素内部紧密排列的是哪个矩阵乘法维度：`K`-major 为 `K`，MN-major 为 M/N；swizzle 则在该布局固定大小的 atom 内加入地址置换。因此先根据操作数角色选择 major mode，再决定使用 SW128，所需 atom 形状便由下面的 `tcgen05` 布局表确定。

辅助函数大致如下：

```text
float software_exp2_scalar(float x) {
    // polynomial coefficients
    float C3 = 0.077f;
    float C2 = 0.227f;
    float C1 = 0.695f;

    // input is in base-2 units, and we want to compute 2**x,
    // if x is below -127, that means 2**x will be extremely small,
    // so small that we don't care (FTZ like)
    x = fmaxf(x, -127.0f);

    int int_part = floor(x);
    float frac_part = x - int_part;

    // approximate 2^frac_part using three chained FMAs;
    // as an optimization, feed each result into the next FMA,
    // avoiding separate frac_part^2 and frac_part^3 computations
    float frac_exp2 = C3;
    frac_exp2 = fma(frac_exp2, frac_part, C2);
    frac_exp2 = fma(frac_exp2, frac_part, C1);
    frac_exp2 = fma(frac_exp2, frac_part, 1.0f);

    // expose the bits of our approximate 2^frac_part
    int frac_exp2_bits = __float_as_int(frac_exp2);

    // FP32 has 23 fraction bits, so 1 << 23 is one exponent step
    int exponent_adjustment = int_part * (1 << 23);

    // combine approximate 2^frac_part with 2^int_part
    int result_bits = frac_exp2_bits + exponent_adjustment;
    return __int_as_float(result_bits);
}<p><br></p><p>算法改编自 FA4 的 <code>ex2_emulation_2</code>。这里为便于理解，简化为每次处理一个值；<a href="https://github.com/IaroslavElistratov/b200-attention/blob/master/kernels/approximations.cuh">实际辅助函数</a>用打包的 <code>f32x2</code> 指令，对两个值同时执行相同算法。 第 8 章的硬件 <code>exp2</code> 和本章的软件 <code>exp</code> 两条路径都是近似计算。这项优化只改变选定 <code>P</code> 值的计算方式，并不减少 <code>exp</code> 次数。</p>
```

### 第 10 章：寄存器缓存

![](https://pic1.zhimg.com/v2-a408acb7d97b6b6d6d3ea563db6bd642_r.jpg)

前面每个 `Q` stage 都遍历并读取 TMEM 中的 `S` 两次，见第 1 章。第一次计算 `rowmax`，为第二步提供数值稳定性；第二次减去 `rowmax`，再取指数。必须先算出 `rowmax` 才能相减，因此需要两次遍历相同 `S`。下一项优化是在寄存器中保留部分 `S`，减少第二遍的 TMEM 重读。

![](https://picx.zhimg.com/v2-c747e78a9cc50827ea8a2b16c55e1659_r.jpg)

为了缩短寄存器生命周期，我们：

- （a）第一次 TMEM 遍历缓存最近读到的 `S`。由于从低列向高列读取，最近读到的是高 96 列。
- （b）将 `P` 生成遍历，也就是原来的第二次 TMEM 遍历，改为从高列向低列推进，让最近缓存的值先被消费。

![](https://pic4.zhimg.com/v2-7b50350f6a834b3f1ef2f89620417c9d_r.jpg)

从第 2 章起，此前一直把 `P` 放在 TMEM `S` 区域的低半部分。本章只缓存高 96 列，总共 128 列中的低 32 列之后还要重读。因此，不能再把高 96 列 `P` 写入低端 `S`，否则会在重读前破坏低 32 列 `S`。从第 10 章起，我们将 `P` 存入 `S` 的高半部分。

![](https://pic4.zhimg.com/v2-e9dfa7d2959ff54b799afbf852a132cf_r.jpg)

还有一点：重读的低 32 列 `S` 只用于生成 1/4 的 `P`，其他 3/4 由寄存器缓存的 `S` 生成。因此，第二次 `S` 遍历仍存在，但每行只从 TMEM 重读 128 个分数中的 32 个，去掉了 3/4 的重复读取。

### 第 11 章：跳过 O 重缩放

本章没有特别适合画图的内容，因此看一点伪代码。下一章继续图解。普通 Softmax 能看到整行，只需一次找到最终 `rowmax`，减去它，再取指数。在线 Softmax 每次处理一个 `K`/`V` tile，无法预先知道最终 `rowmax`。逐 tile 才逐渐看到整行，后面的 tile 可能出现更大最大值。因此，与普通整行 Softmax 不同，在线 Softmax 必须决定：

- 每遇到一个更大最大值，都立刻切换过去吗？
- 还是可以继续使用旧 `rowmax`？

前面各内核一旦发现更大最大值，就立刻采用：

```text
new_rowmax = max(old_rowmax, tile_rowmax)
```

然后将全部旧状态改写到新基准下：

```text
old O      *= rescale
old rowsum *= rescale
```

更新 `rowsum` 很便宜，但重缩放 `O` 需要再完整遍历 TMEM 中每行 128 个值。内核 10 每轮 KV 循环都执行 `O` 遍历，即便 scale 为 1。也就是说，最大值不变、`rescale == 1` 时，仍加载 128 个 `O` 值，乘以 1，再写回。这在数值上安全，却过于保守。内核 11 中，如果新 tile 最大值只比保留的 `rowmax` 略高，就继续使用旧 `rowmax`，不对 `O`、`rowsum` 做基准变换。只有差距足够大，才切换到新 `rowmax`，并把旧 `O`、`rowsum` 重缩放到新基准。

**跳过重缩放不会抹掉信息**

这一点我起初也没立即想明白[18]。用一个小例子看看跳过 `O` 重缩放会发生什么，确认它不会导致信息丢失。假设决定为某个 tile 跳过 `O` 重缩放，具体阈值稍后讨论。暂设当前 tile 最大值比旧 `rowmax` 高 7.78。我们仍相对于旧 `rowmax` 计算 `P`：

```text
P = exp2(scaled_S - kept_rowmax)
```

因此，新的最大值产生：

```text
exp2(7.78) ~= 219
```

尽管跳过 `O` 重缩放，新最大值并未被抹掉，信息也未丢失。因为仍用旧 `rowmax` 计算 `P`，较大分数变成了约 219 倍的未归一化 `P`。这份差异就保存在更大的 `P` 中。更好的是，与选择重缩放的情况相比，整个内核最终结果完全不变。因为较大的 `P` 同时进入 Softmax 的两部分：分子 `O` 和分母 `rowsum`。相同的 `P` 值进入 Attention 的两部分：

```text
O      += P @ V
rowsum += sum(P)
```

所以，对于前面 219 的例子：

```text
O      += 219 * V_new
rowsum += 219
```

整个 `K`/`V` 循环后：

```text
output = O / rowsum
```

新分数在 `O` 和 `rowsum` 中仍被视为约 219 倍大。最终除法没有抹掉这个相对差异，只是消去 `O`、`rowsum` 共有的尺度。

**那为什么还要切换基准？**

如果最终 `O / rowsum` 能处理共同尺度，似乎可以永远保留最初 `rowmax`。数学上，只要所有中间值不溢出，确实可以。例如旧 `rowmax` 已远落后于新值时：

```text
gap = 20
largest P = exp2(20) = 1,048,576
```

最终答案在数学上仍等价，但 `P`、`rowsum`、`O` 的中间值会变得很大。如果溢出，最后除以 `rowsum` 的归一化显然不能撤销溢出。

**逐行决策如何映射到 warp 级 TMEM `O` 遍历**

是否切换基准由每行独立决定，但 TMEM `O` 的加载与存储是 warp 集体操作。因此实际实现如下：

```text
// convert the current tile's raw rowmax into base-2 exponent units
tile_rowmax *= softmax_scale_log2;

// kept_rowmax is already stored in the same units
float candidate_rowmax = max(kept_rowmax, tile_rowmax);
float rowmax_gap = candidate_rowmax - kept_rowmax;
bool row_needs_rebase = rowmax_gap >= REBASE_THRESH_LOG2;

float rescale = 1.0f;

// 1) if needed, rescale this row's state and start using the new rowmax
if (row_needs_rebase) {
    // this factor will be applied to both rowsum and O
    rescale = fast_exp2(kept_rowmax - candidate_rowmax);

    // move this row's scalar accumulator into new rowmax basis
    rowsum *= rescale;

    // use new rowmax when producing this P tile and future P tiles
    kept_rowmax = candidate_rowmax;
}

// 2) apply same rescale factor to O
//
// TMEM loads/stores are warp-collective. If any row needs rescaling,
// entire warp must process its 32x128 O slab.
// Rows that don't rebase still participate but with rescale 1
if (__any_sync(FULL_WARP_MASK, row_needs_rebase)) {
    float o8[8];

    // same O traversal used in earlier kernels
    for (int col = 0; col < HEAD_DIM; col += 8) {
        int taddr = taddr_o_stage + trow + col;

        tcgen05::ld_32x32b_x8(taddr, o8);

        for (int i = 0; i < 8; ++i) {
            o8[i] *= rescale;
        }

        tcgen05::st_32x32b_x8(taddr, o8);
    }

    asm("tcgen05.wait::st...");
    asm("tcgen05.fence::before_thread_sync...");
}

// P production and the later PV proceed as in earlier kernels,
// using kept_rowmax as the rowmax for this tile
```

**实际阈值**

从内核 8 起，指数输入使用以 2 为底的单位。内核 11 使用阈值 8，与官方 FA4 相同。据我理解，8 并不是数学上的突变点。对 BF16 `P`、FP32 累加器路径，12 或 15 这样更大的阈值在数值上也可能合理。8 是保守选择，已经能跳过多数有意义的 `O` 重缩放，并非溢出边界。

```text
exp2(8) = 256
```

因此，只要相对于当前保留 `rowmax` 计算出的最大未归一化 `P` 大致低于 256，就继续使用旧 `rowmax`。“相对于”是指取指数前先减去旧 `rowmax`。超过这一范围后，再切换到新 `rowmax`，并对旧状态改换基准。为建立直觉，看看 `HEAD_DIM` = 128 时，以 2 为底的阈值 8 对应内核中其他单位的什么值：

```text
base-2 exponent gap:  8
natural-exp gap:      8 / log2(e) ~= 5.545
raw QK-score gap:     5.545 * sqrt(128) ~= 62.7
```

62.7 是当前 tile 逐行最大值与 `kept_rowmax` 对应的原始 QK 分数之间的差。内核里没有任何地方使用 62.7，实际阈值是在 log2 基准下的 8。这个换算只是帮助理解：在改换基准前，原始 QK 分数允许多大余量。

### 第 12 章：将修正与 Softmax 分离

![](https://pic2.zhimg.com/v2-a68a3f3b0612855098bd87eb0d0b3947_r.jpg)

此前，同一组行处理 warp 负责：

- 计算当前 tile 的 `rowmax` 和 `O` 重缩放因子。
- 如果新 tile `rowmax` 超过累计 `rowmax` 达到阈值，就对 `O` 重缩放，见内核 11。
- 从 `S` 中减去 `rowmax`，再取指数生成 `P`。

因此，第（2）步延迟整组行处理工作（1）至（3）的完成。`O` 修正与 `P` 生成在同一组 warp 中串行执行。

![](https://pica.zhimg.com/v2-40151bff4914af803edfaed55575d250_r.jpg)

`O` 重缩放（2）不依赖未归一化 `P` 的计算（3），所以可移到独立 warp，与生成 `P` 的行处理 warp 并行。这样从 `P` 生成前移走 `O` 修正，让两条分支重叠，缓解主要瓶颈 `P` 生成。现在行处理 warp 主要做 Softmax，所以之后称为“Softmax warp”。

PV 仍同时需要 `P`-ready 和 `O`-safe。每个 `Q` stage 用 `p_ready_o_safe` 屏障合并这两个条件。PV MMA 等待 8 次到达：4 次来自 Softmax warp，表示 `P` 就绪；4 次来自修正 warp，表示 `O` 安全。两条分支中较慢的一条决定 PV 何时能开始。注意我刻意说 `O`-safe，而非 `O`-rescaled，因为按第 11 章优化，有时跳过 `O` 重缩放，并不总会执行它。

Softmax warp 仍计算 `rescale`，写入 SMEM，发出 `stats_ready`，然后继续生成 `P`。修正 warp 等待该信号，读取因子，检查是否有已发布 scale 不为 1，从而判断是否改换 `O` 基准；如果需要，就重缩放 `O`。

仍由 Softmax warp 计算 `rescale`，而不是让修正 warp 计算，是因为前者的寄存器已经持有旧累计 `rowmax` 和新 tile `rowmax`。否则还得把这些状态传给修正 warp，并在那里重复基准选择逻辑。因此 Softmax 每行只发送一个最终 scale，修正端直接应用到 `O`。同一组 4 个修正 warp 由 `Q0`、`Q1` 共享。对每个 `Q` stage，它们读取 Softmax 发布的逐行 scale，重缩放相应 `O` tile。

### 第 13 章：提前执行 PV

![](https://pic1.zhimg.com/v2-5570dea860f32a84eefa4120446068b2_r.jpg)

记住，由内核 10 的优化决定，`P` 从右向左生成，也就是从 TMEM 区域高端向低端写入。因此，右侧 `P` 比完整 `P` 更早就绪；绿色区域已生成时，红色区域还没有。内核 13 利用这一顺序：高 96 列 `P` 已生成、旧 `O` 安全后，就可以开始部分 PV MMA。无需等整个 `P` 就绪，先做 `p_high96 @ V_slice1`，等 `P_low32` 生成后再做 `P_low32 @ V_slice2`。

其前提是：开始生成 `P` 分块前，已经求出了整个 `S` tile 的 `rowmax`，因此累计 `rowmax`/参考基准固定。后来生成低 32 列 `P` 不会改变 `rowmax`，也就不会改变已经生成的高 96 列 `P`。这个 `P` 的 32/96 切分看起来与第 10 章 `S` 寄存器缓存的 32/96 切分相呼应，但这不是本质要求。两项优化大体正交，只是在本实现中恰好对齐[19]。图中省略了第二个 `Q` stage 的 `P1`，因为逻辑完全相同。

![](https://pic1.zhimg.com/v2-c60a5d3bce094757af6e527cc0e32706_r.jpg)

第一个屏障释放后，全部高 96 列 `P` 已就绪，即其 6 个 micro-tile 都已准备好，`O` 也安全。完整高 96 区域发布后，MMA 不必按 Softmax warp 生成顺序消费 micro-tile；也可以按 k = 7..2 发起，不会造成有意义的数值变化[20]。我保留 k = 2..7 的顺序，只是因为对应 `V` SMEM 描述符递增更简洁，并非本质选择。

![](https://pic2.zhimg.com/v2-5f176999772522c41e736e23ea685e49_r.jpg)

用 `p_high96` 做矩阵乘法时，也要选中对应的 `V` 切片，即将 `P` micro-tile 地址、`V` 描述符各偏移两个 micro-tile，见图中绿色部分。之后，Softmax warp 生成低 32 列 `P`，并发信号表示完整 `P` 就绪。再计算之前跳过的两个 micro-tile，即 `P_low32 @ V_slice2`，见红色部分。两次部分矩阵乘法都累加到同一 `O` tile。我们只是沿归约轴把 `P`、`V` 各拆成两块，合起来仍计算原来的完整 `P`@`V`。

## 第四部分：持久化内核

### 第 14 章：持久化

我们的内核每个 SM 最多驻留一个 CTA，因为每 CTA 消耗的资源使一个 SM 同时只能容纳一个。B200 有 148 个 SM，因此任意时刻最多 148 个 CTA 工作。从第 5 章起，每个 CTA 独立消费两个 `Q` tile、遍历全部 KV tile，并生成两个输出 tile。

![](https://picx.zhimg.com/v2-d9f00f8b3b0ffd61d4a88612e1ac8e07_r.jpg)

把这称为一个“工作项”（work item），并抽象成图中形式。后续图以工作项为粒度。下一项优化改变的是 Attention 主体外部的生命周期，而不是主体本身，因此可以安全将主体抽象掉。

![](https://pic4.zhimg.com/v2-ab24a763f19e46b9528c0c70b982403f_r.jpg)

此前，如果工作项数量大于 SM 数量，即无法一次处理完所有工作，每个 SM 就依次运行多个 CTA：一个完成其工作项并退出调度，另一个处理不同工作项的新 CTA 接替。这些就是工作的“波次”（waves）。可以根据总工作量和每 CTA 处理量计算波次数：以 `SEQ_LEN` = 4096 为例，对单个 batch、head，tile 边长为 128，`Q`、`O` 各有 4096 / 128 = 32 个 tile。每 CTA 处理两个，因此只有 32 / 2 = 16 个工作项。于是：

```text
16 work items per batch-head
8 batches * 16 heads * 16 = 2048 total work items
```

对于 `SEQ_LEN` = 16384，单个 batch、head 的 `Q`、`O` 各有 16384 / 128 = 128 个 tile。每 CTA 处理两个，因此有 128 / 2 = 64 个工作项。

```text
64 work items per batch-head
2 batches * 16 heads * 64 = 2048 total work items
```

对于基准使用的三个形状，都会发起 2048 个独立 CTA，约 148 个能同时驻留，因此大约执行 14 波：ceil(2048 / 148 个 SM) = 14 波。通常称之为波次，但 CUDA 并不会等某一波 148 个 CTA 全部同时完成。某个 CTA 一结束，等待中的另一个就可能进驻空出的 SM，所以各 CTA 的推进时间会错开。

于是每个 SM 大约依次处理 14 个不同 CTA：前一个完成并释放资源，后一个驻留。但这 14 次都重复支付相同开销：TMEM 分配/释放、CTA 生命周期状态设置、指针偏移、屏障初始化、CTA 调度等。

**`SEQ_LEN` 越短，CTA 固定开销越重要**

4K、16K 形状都要“重复 14 次”。来自 FA4 论文的三个基准形状恰好各有 2048 个工作项，因此同样承担 14 波固定成本。但 KV 循环从 4K 的 32 轮增长到 16K 的 128 轮，所以 16K 每波包含 4 倍有效工作：

```text
KV-loop iterations = len_kv / BLOCK_N = 4096 / 128 = 32
KV-loop iterations = len_kv / BLOCK_N = 16384 / 128 = 128
```

输出工作项数量相同，但每项内部热循环工作量不同。短序列仍付 14 次相同初始化成本，KV 循环却更短，因此固定开销占比更高。与长序列相比，上述每 CTA 固定成本在较短的 4K 工作项中占总时间的比例更大。

![](https://pic3.zhimg.com/v2-42cd15a685027d5e603fcc24cc1dcbc2_r.jpg)

如果一个 CTA 不只处理一个工作项，就可以只付一次初始化成本，将它分摊到多项工作，理想情况下分摊越多越好。为尽量摊薄成本，我们让 CTA 一直存活，处理自己大约 14 个工作项的序列。注意，无法摊薄的是：两个 `Q` 的加载、KV 遍历、输出写回、work ID 和指针计算。这些确实因输出工作项而不同；即便同一 CTA 处理多项工作，每一项仍需重新执行。CTA 不会锁步执行，因此图中的箭头长度不同。一个 CTA 中工作项的完成时间可以相对于其他 CTA 的进展发生偏移。

**跨工作项复用屏障**

此前屏障在 CTA 启动时初始化一次，贯穿其生命周期。内核 14 让屏障跨多个工作项继续工作。我最初的朴素实现，在工作项之间停止所有 warp，等待全部工作完成，再将屏障失效并重新初始化，然后才开始下一项。PTX 要求失效这一步，因为对仍有效的屏障调用 `mbarrier`.init 是未定义行为；重新初始化前必须确保没有 warp 仍在使用它。这样正确，却在工作项之间制造硬停顿：所有 warp 等待最慢者，全部工作彻底排空后才能开始下一项。

为避免每个工作项边界都重复失效和初始化，内核 14 仅在 CTA 启动时初始化所有屏障一次，随后跨工作项持续轮转屏障 phase。旧 `work_done` 同步让所有 warp 等最慢者、将当前工作排空，保障重初始化安全，并保守地禁止任何缓冲区在整个工作项排空前复用。内核 14 改为跨工作项沿用已有 `K`/`V` 回收交接，再为 `Q` SMEM 增加 `q_free`。结合不再重初始化屏障，就无需全 warp 的 `work_done` 同步。

因此，每个缓冲区在当前工作项的真正最后消费者用完后，就可释放：

```text
Q SMEM:
    final QK reads Q(i)
    -> q_free
    -> load Q(i+1)

K/V ring:
    final QK reads K stage
    -> refill K stage

    final PV reads V stage
    -> refill V stage
```

这样，不再存在一个统一时刻，宣告 `work_item`(i) 结束、`work_item`(i+1) 开始。Softmax warp 仍在归一化并写 `O`(i) 时，加载 warp 已可加载下一份 `Q`/`K`/`V`；`Q`、`K` 就绪后，MMA warp 就能开始 QK(i+1)。因此，内核 14 同时引入持久化 CTA 生命周期与跨工作项流水线。

![](https://pica.zhimg.com/v2-8dd4cbf9a62c1c68a79bcc82a0841338_r.jpg)

如图所示，内核 14 中每个持久化 CTA 并不处理连续 work ID。代码只是 `work_id += gridDim.x; // 148 CTAs`。静态 grid-stride 分配把每个工作项交给 148 个持久化 CTA 之一。每工作项覆盖相邻两个 `Q`/`O` tile，所以 CTA 前进 148 个工作项时，tile 索引前进 296。CTA 0 先处理 tile 0-1，再处理 296-297，然后 592-593。

我也试过给每个 CTA 分配连续范围的工作项。上述跨步方式整体更快，但结果依赖形状，我尚未单独确定具体原因。我的猜测是，当 CTA 在接近的时间处理相同 batch-head 的不同 `Q` 对时，共享 L2 中的 `K`/`V` 复用会有帮助。图中展示的是每个 CTA 拥有哪些工作项，而非硬执行边界。如前所述，不同 warp 角色仍可让前一工作项的尾部与后一项的开头重叠。

## 小优化

内核 14 是主要 14 阶段演进的终点。剩下四项是较小的局部优化，集中放在这里。仓库仍将它们分别编号为 15-18，方便逐项 diff。合起来，它们带来最后几个百分点的性能。

延迟分数读取等待（[Deferred score acquisition](https://github.com/IaroslavElistratov/b200-attention/blob/master/kernels/5_minor/15_wide_deferred_score_loads.cu)）。此前从 TMEM 读 `S` 使用 16 次加载，每次后面立即等待。现在改用 8 次更宽加载、不立即等待、4 条独立 `rowmax` 依赖链，并将一次统一等待推迟到 `P` 覆盖该 TMEM 区域前，让加载延迟与有效工作重叠。多数收益来自 4 条独立 `rowmax` 链；延迟等待也有帮助，而单独加宽加载几乎无效。

href="[https://github.com/IaroslavElistratov/b200-attention/blob/master/kernels/5_minor/16_split_rowsum_accumulation.cu](https://github.com/IaroslavElistratov/b200-attention/blob/master/kernels/5_minor/16_split_rowsum_accumulation.cu)" data-draft-type="text-link">拆分 rowsum 累加。`P` 已分成两部分生成：寄存器缓存分数产生的 96 列，以及 TMEM 重读分数产生的 32 列。不再让两部分都经过一条长 `rowsum` 依赖链，而是把缓存 96 列累加成两个部分和，重读 32 列用标量求和，最后只合并一次。

[Phase 位掩码](https://github.com/IaroslavElistratov/b200-attention/blob/master/kernels/5_minor/17_phasebits.cu)。每个屏障 stage 只需要 0/1 phase，但把它们放在运行时索引的小数组中，会使编译器将其放入线程局部内存。这里改用整数位掩码打包，让状态留在寄存器，消除 spill。

[TMA L2 promotion](https://github.com/IaroslavElistratov/b200-attention/blob/master/kernels/5_minor/18_tma_l2_promotion.cu)。每次 TMA 行读取只使用一个对齐 256B 区域中的 128B 半区，而邻近读取很快又需要另一半。我们要求 TMA 将完整 256B 取入 L2，使随后所需的另一半更可能已缓存。内核主体本身不变。

### 软件 exp2 如何工作

[第 9 章“软件近似”](https://iaroslavelistratov.github.io/b200-attention/#chapter-9--software-approximations)的可选背景知识。

内核 8 之后，指数输入已经使用以 2 为底的单位，我们计算 `exp2(x)`。数学上，`exp2(x)` = `2^x`。因此，我们希望用 ALU 承担一部分 `2^x` 的计算。把 x 拆成整数部分和小数部分，分别求 2 的相应次幂，再相乘。由于 `2^(a+b) = 2^a * 2^b`，它等价于直接计算 `2^x`。

```text
integer_part = floor(x)
// always between zero and one
// by our definition above
fractional_part = x - integer_part

2^x = 2^integer_part * 2^fractional_part
```

例如：

```text
x                   = -3.25
integer_part        = -4
fractional_part     = 0.75
```

这样拆整数部分很方便，因为 FP32 本来就有以 2 为底的指数位域。因此，只需调整多项式结果的指数位，就能施加 `2^integer_part`。但 `2^fractional_part` 不能像整数部分那么方便地计算，因为 FP32 指数位域只能按整步变化，例如可移动 -4 步，不能移动 0.75 步。因此，对小数部分采用多项式近似。按定义，`fractional_part` 总在 0 与 1 之间，所以只需近似 `2^x` 曲线中 x ∈ `[0,1)` 的一小段。

指数位处理 `2^integer_part`，多项式处理 `2^fractional_part`。使用一个三次多项式近似这段曲线：

```text
2^fractional_part
    ~= 1
    + c1 * fractional_part
    + c2 * fractional_part^2
    + c3 * fractional_part^3
```

可把多项式看成对弯曲程度逐渐增加的形状做加权混合。直线过于简单，二次项仍不够准确；三次多项式既足够灵活，求值又便宜：

```text
1                    constant, flat component
fractional_part      straight-line component
fractional_part^2    quadratic curve
fractional_part^3    cubic curve
```

系数 c1、c2、c3 控制各分量的贡献强度。它们并非简单从指数曲线上采样得到，而是离线拟合选择，使加权曲线在 0 到 1 的区间尽量接近 `2^fractional_part`。这里使用一个小优化。朴素实现会先算 `fractional_part**2`、`fractional_part**3`，再分别乘系数并相加；显式构造这些幂需要两个额外乘法。我们改为将一次乘加的结果连续送入下一次乘加，因此整个三次多项式只需 3 条 FMA 指令。

```text
2^f ~= ((c3*f + c2)*f + c1)*f + 1
```
