## 引言

本人在网络上发现一个项目：[geforce-gpudirect-rdma](https://github.com/mcornea/geforce-gpudirect-rdma)。 这个项目尝试在 GeForce RTX GPU 上实验性启用 GPUDirect RDMA。 接下来对它的实现思路进行解析。

## 前置知识

### RDMA

RDMA 是一种远程直接内存访问技术，它允许一台机器上的网卡直接读写另一台机器上已经注册好的内存区域。 它的高性能主要来自两点：

- bypass 内核，减少上下文开销
- 数据面由 RDMA 网卡卸载执行，减少 CPU 资源占用

RDMA 控制面依旧由 CPU 负责，例如注册内存、创建队列、提交 work request 和处理 completion。 注册内存是把应用 buffer 注册成网卡可以访问的 memory region，接口为：`ibv_reg_mr`。 `ibv_reg_mr` 由以下几个步骤组成：

- 把用户态 buffer 对应的 CPU 内存页 pin 住，避免 RDMA 过程中被换出、迁移或释放。
- 把这些 CPU page 转换成网卡可以 DMA 访问的地址
- 生成访问这段 memory region 的 key。这里的 key 并非指密码学的密钥，而是用来标明 buffer 身份的描述符。
- 网卡根据 MR、key 和权限直接 DMA 读写这段主机内存。

### GPUDirect RDMA：NIC 直接访问 GPU memory

GPUDirect RDMA 是 RDMA 在 GPU 显存上的扩展，它允许 RDMA 网卡直接读写 CUDA 分配出来的 GPU memory。 它和普通 RDMA 的主要区别在于注册对象：

- 普通 RDMA 注册的是 CPU host memory
- GPUDirect RDMA 注册的是 GPU virtual address

RDMA core 不能直接对 GPU VA 进行 pin 和 map 操作。 它需要求助于 GPU 驱动来完成这些步骤。 具体来说，`ibv_reg_mr` 在接收到 GPU VA 后需要额外经过 NVIDIA peer memory 路径：

- RDMA 软件栈发现无法按照 CPU host memory 处理这段地址，会求助于 `nvidia-peermem`
- `nvidia-peermem` 把请求转给 GPU driver
- GPU driver 返回 mapping 信息 之后的过程与普通 RDMA 一致

## GeForce RTX GPU can RDMA?

NVIDIA 官方文档说明：“GPUDirect RDMA is available on both Tesla and Quadro GPUs.” [[NVIDIA GPUDirect RDMA 文档](https://docs.nvidia.com/cuda/gpudirect-rdma/)] GeForce RTX GPU 不在这个官方支持范围内，GeForce RTX GPU 上使用 `ibv_reg_mr(GPU VA)` 会返回 `EFAULT`。

## geforce-gpudirect-rdma 补丁测试与分析

geforce-gpudirect-rdma 项目采用三组补丁来使能 GeForce RTX GPU 的 RDMA 能力。 第一组补丁是使能 GeForce RTX GPU 的 GPU Direct P2P 能力，该补丁最初由知名黑客 geohot 完成。 它的核心原理是绕过内核驱动对显卡能力的检查从而启用 GeForce RTX GPU 的 P2P 能力。 第一组补丁不是本文的分析重点，后文只把它作为已有前提。 关于第一组补丁中 GPU Direct P2P、Mailbox 和 BAR1 相关机制的更细致解析，可以参考已有分析 [[1]](https://zhuanlan.zhihu.com/p/2057515008200816183/edit#ref-1) [[2]](https://zhuanlan.zhihu.com/p/2057515008200816183/edit#ref-2)。

接下来的第二组补丁和第三组补丁是专门针对 RDMA 能力的增强。 从补丁内容来看，GPU 驱动依赖一组软件维护的 RDMA 元数据来实现 RDMA 能力。 这组元数据记录在 `ThirdPartyP2P` 对象中，核心内容包括当前进程、RM client、GPU VA space、vidmem handle、GPU VA range、size 和 offset。 对于 GeForce GPU，GPU 驱动只创建普通 GPU memory mapping，没有同步创建 `nvidia-peermem` 可查询的 `ThirdPartyP2P` 元数据，因此 `ibv_reg_mr(GPU VA)` 无法成功。 第二组补丁负责修复 GPU 驱动中的**查询**动作； 第三组补丁负责**创建**针对 RDMA 的 `ThirdPartyP2P` 元数据。

为了逻辑的顺畅，我们先分析第三组补丁。 第三组补丁创建 `ThirdPartyP2P` 对象（`NV503C`），并向该对象注册 VA space 和 vidmem range。 VA space 表征这段 GPU VA 属于哪个 GPU 地址空间。 vidmem range 表征这段 GPU VA 对应哪个显存对象、起始地址、长度和偏移。 第三组补丁改用 CUDA VMM API，是为了把 GPU VA 分配和物理显存对象创建拆开，使用户态补丁能够在 `cuMemCreate` 和 `cuMemMap` 附近捕获 RM handle。 这些 handle 最终用于构造 `REGISTER_VA_SPACE` 和 `REGISTER_VIDMEM` 请求，从而把这段 GPU VA 登记成 `nvidia-peermem` 可以命中的 RDMA 显存区间。 普通 `cuMemAlloc` 把这些步骤封装在 CUDA 内部，用户态补丁难以稳定拿到创建 `REGISTER_VIDMEM` 所需的 `hMemory` 和 GPU VA 映射关系。 对应到代码，第三组补丁先在 perftest 中加载 CUDA VMM API。

随后它在 `cuda_memory.c` 中创建 `ThirdPartyP2P` 对象，并注册让该对象生效所需的 VA space 与 vidmem。

```text
// src/cuda_memory.c
+#define NV50_THIRD_PARTY_P2P 0x503c
+#define NV503C_FLAGS_TYPE_BAR1 0x00000001
+#define NV503C_CTRL_CMD_REGISTER_VA_SPACE 0x503c0102
+#define NV503C_CTRL_CMD_REGISTER_VIDMEM   0x503c0104
+
+static int enable_gpudirect_rdma(CUdeviceptr dptr, size_t size, uint32_t hMem) {
+    uint32_t hP2P = gd_next_handle++;
+    struct { uint32_t flags; } ap = {NV503C_FLAGS_TYPE_BAR1};
+    if (gd_rm_alloc(gdh.hClient, gdh.hSubdevice, hP2P, NV50_THIRD_PARTY_P2P, &ap) != 0)
+        return -1;
+    struct { uint32_t h; uint32_t p; uint64_t t; } rv = {gdh.hVASpace, 0, 0};
+    if (gd_rm_ctrl(gdh.hClient, hP2P, NV503C_CTRL_CMD_REGISTER_VA_SPACE, &rv, sizeof(rv)) != 0)
+        return -1;
+    struct { uint32_t h; uint32_t p; uint64_t a; uint64_t s; uint64_t o; }
+        vm = {hMem, 0, (uint64_t)dptr, size, 0};
+    if (gd_rm_ctrl(gdh.hClient, hP2P, NV503C_CTRL_CMD_REGISTER_VIDMEM, &vm, sizeof(vm)) != 0)
+        return -1;
+    return 0;
+}
```

这类元数据的关键索引是当前进程和 GPU VA。 而，驱动默认的 legacy P2P API 使用的是 `p2pToken` 和 `vaSpaceToken`，它们是驱动为 `ThirdPartyP2P` 对象和 VA space 分配的查询标识符。 因此，第二组补丁必须切换 API，使 `ibv_reg_mr(GPU VA)` 进入按当前进程和 GPU VA 查找 `ThirdPartyP2P` 的 persistent P2P 查询路径。

## 透明化改动

geforce-gpudirect-rdma 方案已经证明 GeForce GPUDirect RDMA 的关键缺口在 `ThirdPartyP2P` 元数据。 但它仍然要求应用程序侵入式增加创建元数据的逻辑。 这种方式适合验证原理，不适合作为真正透明的使用方式。 本文将尝试将 RDMA 使能逻辑透明化，使得应用程序未经修改就可以在 GeForce GPU 上运行 RDMA 逻辑。 仓库连接：[https://github.com/fengyuanyu1/open-gpu-kernel-modules/tree/geforce-rdma-enable](https://github.com/fengyuanyu1/open-gpu-kernel-modules/tree/geforce-rdma-enable)

### 实现思路

透明化改动把 `ThirdPartyP2P` 元数据的创建过程拆成两个阶段。 第一阶段发生在 UVM external allocation 映射完成后，驱动复用 UVM 已有的 external range tree，把 `hClient`、`hVaSpace`、`hMemory`、GPU VA、长度和 offset 挂到对应 range 节点上。 这一步只补充 RDMA 所需元数据，不立即创建 `ThirdPartyP2P`。 第二阶段发生在 `nvidia-peermem` 收到 RDMA 注册请求时，驱动根据 GPU VA 反查 UVM 中保存的记录，再调用 RM helper 创建或复用 `ThirdPartyP2P` 并注册对应 vidmem range。 这样，应用程序仍然只调用普通 CUDA allocation 和 `ibv_reg_mr`，不需要显式插入 geforce-gpudirect-rdma 原方案中的 P2P 初始化逻辑。

## 7. 实验验证

### 实验环境

实验环境采用双 VM 直通拓扑。 每台 VM 配置 16 个 vCPU 和 31 GiB 内存。 每台 VM 内各有一张 GeForce RTX 3090 和一张 Mellanox MT42822 BlueField-2 integrated ConnectX-6 Dx RoCE 网卡。

VM 内核版本为 Linux `5.15.0-181-generic`。 GPU 驱动版本为 NVIDIA open GPU kernel module `570.133.07`。 CUDA 版本为 `12.8`，PyTorch 版本为 `2.8.0+cu128`，NCCL 版本为 `2.27.3`，sglang 版本为 `0.5.5.post3`。

### perftest

perftest 使用未修改的 `ib_write_bw`，并通过 `--use_cuda=0` 在 GPU buffer 上执行 RDMA Write。 测试消息大小为 65536 B，平均带宽为 21989.48 MiB/s。
