MoE（混合专家）推理的性能讨论，最近两年几乎都围绕「融合」展开：把 all-to-all dispatch、grouped GEMM、combine 塞进一个持久化 kernel，用 warp specialization 让通信 warp 和计算 warp 在同一个 SM 上错峰跑。DeepGEMM 的 Mega MoE 就是这个路线的代表作。

阿里的这篇 GC-MoE 走的是反方向：**不在一个 SM 里挤，而是把 SM 阵列切开**——用 CUDA Green Contexts 在驱动层把 B300 的 148 个 SM 分成 20 个通信 SM 和 128 个计算 SM，让 dispatch 和 grouped GEMM 变成两个独立 kernel、并发执行。decode 场景下 grouped GEMM 本来就是带宽受限的，多 20 个 SM 换不来算术吞吐，但少掉「共享 SM 的挤占」和「每次 replay 的跨 rank 尾屏障」却能实打实降延迟。

结果：8×H20 上 DeepSeek-V4.1-Flash 解码平均 **1.188×**（峰值 1.296×），8×B300 上两个生产级 MoE 平均 **1.106×**（融合 shared expert 后 1.123×，峰值 1.209×），54 个测点全部胜出，精度与基线逐位同量级。代码 MIT 开源。

这篇按「成本结构 → 基线三笔账 → 分区怎么做 → 握手怎么跨分区 → 两代硬件怎么各写一遍 → 实测 → 什么时候不划算」拆解。

## 一、先算清楚 decode 阶段 MoE 的钱花在哪

专家并行（EP）下，一层 MoE 拆成四步：dispatch（all-to-all 把 token、激活 scale、路由元数据送到持有目标专家的 rank）、第一段 grouped GEMM（含 SwiGLU）、第二段 grouped GEMM（down projection）、combine（把 k 份部分和按路由权重加权求和送回源 rank）。

关键在于 decode 的 batch 特征：每个 rank 每层只持有 1–256 个 token。论文举的例子很直观——GLM-5.2 是 256 专家、8 rank、top-8，均衡路由下每个专家平均只收到 T/4 个 token；当每 rank 只有 1 个 token 时，一个专家平均收到 **0.25 个 token**，pad 到 MMA tile 之后整块几乎全是填充。

这带来两个不对称：

- **grouped GEMM 是带宽受限的**：成本主要花在从 HBM 流式读本地专家的 FP4 权重和 scale 元数据，而不是算术。所以给它更多 SM，收益很小。
- **dispatch 是延迟受限的**：关键路径是跨 rank 交换加对等原子计数，而且只需要很少的 SM 就能打满 NVLink。

一个要带宽、一个要延迟；一个不缺 SM、一个不缺算力。既然如此，为什么非要让它们挤在同一批 SM 上？

## 二、基线 Mega MoE 的三笔账

Mega MoE 的做法是：一个持久化 kernel 占住全部 148 个 SM，每个 CTA 里分四类 warp——4 个 dispatch warp（128 线程）、4 个非 epilogue warp（2 个 TMA 装载、1 个 MMA 发射、1 个调度，后两个只在两 CTA 簇的 leader 上跑）、8 个 epilogue warp（256 线程，同时干 combine）。

![](https://picx.zhimg.com/v2-4a19eed134e73f6afcd87b4b3cdf440f_1440w.jpg)

图 1：两条执行时间线对比。(a) Mega MoE 让 dispatch warp 与计算 warp 共享全部 148 个 SM，尾部是 max(combine, clean + tag-2 屏障)；(b) GC-MoE 把 dispatch 放到 20 个 SM 的通信分区，计算放到 128 个 SM 的计算分区，用奇偶双缓冲计数器去掉 tag-2 屏障。

它的关键路径可以写成一个很干净的式子：

**T_mega = t_pro + max(共享 SM 上的拉取, 共享 SM 上的 GEMM) + max(combine, workspace 清理 + tag-2 屏障)**

三笔账就藏在这个式子里。

**第一笔：计算 warp 从来没有独占过 SM。** dispatch warp 和它的 staging buffer 是从**每个** SM 的寄存器文件和共享内存里切出来的。一层 decode 里 GEMM 本来就只有几十到几百微秒，这点挤占直接体现在每 SM 吞吐上。

**第二笔：同步域是整个设备。** kernel 开头的路由计数和 tag-1 屏障、结尾的 grid sync 都覆盖全部 148 个 SM，每个阶段都要等最慢的那个 CTA。更麻烦的是 tag-2 屏障：因为下一次 replay 要复用 workspace 和接收计数器，每次 replay 结束都必须跨 rank 走一趟屏障——这是一次完整的 NVLink 往返，而 combine 只有在它自己比「清理 + 屏障」更慢时才能把它藏住。

**第三笔：资源预算被绑死。** 所有角色共用一份 CTA 预算（约 6.4 万个 32 位寄存器、227 KB 共享内存）。即使某个角色这一层几乎不干活，它的份额也照占。想加深权重流水线、放大 epilogue、或者给 dispatch 换条更便宜的路，都得在这个联合预算里腾挪，还得保证其他角色的屏障和缓冲仍然有效——**局部优化的账单由整个 kernel 一起付**。

论文还顺手否掉了三个「看起来能救」的方案：多 CUDA stream（没有隔离保证，通信 kernel 要么等、要么偷 SM）、单 kernel + warp specialization（就是基线本身，一个 kernel 不能在运行中重新划分 SM）、跨 micro-batch 的软件流水（能藏通信，但不缩短单层关键路径，还改变数值调度顺序）。

## 三、解法：驱动层把 SM 切两半

GC-MoE 的第一性动作是调用 CUDA 12.4 引入的 Green Contexts：

- 查设备的 SM 资源，拿到总 SM 数、最小分区大小、协调度对齐粒度；
- 算计算分区目标数 = ((总数 − 请求的 dispatch 数) / 对齐粒度) × 对齐粒度，然后调 `cuDevSmResourceSplitByCount` 一次切出「计算资源 + 互补的通信资源」；
- 从主 context 拿一个 workqueue 配置资源，把 sharing scope 设成 green context 均衡共享，并让每个 context 的并发上限为 1，这样两个 context 各自拥有独立硬件 workqueue——否则它们可能被放到同一个队列上，**设计上要并发的两个 kernel 会被静默串行化**；
- 每个 context 建一条非阻塞 green stream，成对缓存，销毁时先记录 event 再同步。

在 B300 上，默认请求 16 个 dispatch SM，驱动按对齐粒度给出 **20 / 128** 的切法；H20 上默认请求 4 个。分区在 graph 生命周期内是静态的，所以 replay 是确定性的：没有 kernel 会被迁移，dispatch 分区的 SM 数在 kernel 编译期就定了。

这一步的收益不只是「并行」，更是**把同步域缩小**：role1 的 grid sync（包括 tag-1 屏障周围那些）只覆盖 20 个 SM，role3 的 grid sync 只覆盖它的 finalize grid（每 rank 128 token 以内是 64 个 SM），计算分区的任务调度器只在自己的 SM 内；而基线的 prologue 和 tail grid sync 要覆盖 148 个。

代价是计算分区从 148 个 SM 降到 128 个（少 13.5%）。论文的判断是：decode 时 grouped GEMM 受权重流式和小 M 发射延迟约束，128 个 SM 够用——实测的有效吞吐也证明，这个「更小的计算分区」仍然打赢了基线那个「共享 SM 的 GEMM」。

## 四、三节点 CUDA Graph 与跨分区的握手

一次 layer 执行 = 一次子 CUDA Graph 的 replay，三个 kernel 节点（论文称 role）：

| 角色 | 干什么 | 放在哪个 green context | grid |
| --- | --- | --- | --- |
| role1 | token dispatch（all-to-all 拉取）+ 路由计数 | 通信分区 | dispatch_sms（20），256 或 384 线程 |
| role2 | FP8×FP4 grouped GEMM + SwiGLU + requant + scatter | 计算分区 | compute_sms（128），384 线程，2 CTA 簇 |
| role3 | 信号复位 + combine | 计算分区 | finalize_sms（≤128 token 时 64），384 线程 |

![](https://pic4.zhimg.com/v2-88b9c7ea2109b687ab90fd605652a237_1440w.jpg)

图 2：一次 layer replay 的架构。role1 与 role2 在 graph 里没有依赖边，是两个并发根节点；role3 依赖两者。所有跨 rank 状态放在一份对称内存 workspace 里，同步对象全部设备常驻、跨 replay 有效。

三个设计点值得单独说。

**（1）token ring：把基线的块级握手搬到分区边界。** dispatch 不按专家分配缓冲，所有拉来的 token 落进一个全局复用的 token ring，每块 BM 个 token，块上挂四个常驻信号：`l1_full_count`（dispatch 填满时发布）、`l1_empty_count`（计算侧消费完释放）、`l2_full_mask`（64 位位图，标记 W1 输出 tile 完成）、`l2_empty_count`。计算侧的 TMA producer warp 用 acquire 语义等 `l1_full_count = BM × (generation + 1)`，所以 **GEMM 在第一个 ring block 填满时就开始**，而不是等 dispatch 全部结束。W2 的每个 K128 tile 只等它对应的两个 W1 N128 位——这也是「2I/128 ≤ 64」成为硬约束的原因。

**（2）去掉尾屏障：接收计数器按奇偶双缓冲。** 一次 replay 消费第 N mod 2 代计数，role3 消费完、做完 grid sync 后翻转奇偶，下一次发布就打到另一代。顺序由 tag-1 屏障和 combine 就绪的 release/acquire 链保证，不再需要跨 rank 屏障。这一刀砍掉的是**每次 replay 一次完整 NVLink 往返**。

**（3）partial 直接 scatter。** W2 的 epilogue 不写本地中间缓冲等 combine kernel 来取，而是每 lane 用 16 字节 store 直接把 BF16 片段写到源 rank 的 combine buffer 对应槽位 (topk_slot, src_token)。combine kernel 于是只需要 reduce，不需要 gather。

## 五、同一个算子，两代硬件各写一遍

这是全文工程量最大的部分，也是「双架构」的实质：Blackwell 有原生 FP4 和硬件 block scale，Hopper 没有，两边必须用完全不同的指令路径实现同一个 FP8×FP4 grouped GEMM。

| 维度 | Blackwell（SM103，B300） | Hopper（SM90，H20） |
| --- | --- | --- |
| 编译目标 | sm_103f | sm_90a |
| MMA | tcgen05 mxf8f6f4.block_scale，2-CTA 协同 | register-A WGMMA m64nNk32，E4M3 |
| 权重格式 | 打包 FP4 + UE8M0 K32 scale | MXFP4，按 expert 做窗口重打包 |
| 激活格式 | E4M3 + 打包 UE8M0 K32 scale | E4M3FN + FP32 K128 scale |
| FP4 处理 | 原生 E2M1 操作数（format 5） | 寄存器内解码 FP4 → E4M3 |
| scale 施加 | UTCCP 搬到 TMEM，硬件 block scale | MMA 外做 per-K32 FMA，全局 ×64 抬动态范围 |
| 权重布局 | K128 tile 连续预打包 | 按窗口重打包 + lane 置换 |
| graph 节点 | 3 | 3（融合 shared expert 时 4） |

Blackwell 这条路有个很巧的细节：**操作数交换**。指令的 A 操作数是权重、B 是激活，于是 MMA 的 N 维变成 token 维；N 直接设成「本 tile 有效 token 数向上取整到 16」，而不是补齐后的块大小——半空的块就按比例少花时间。又因为 A 携带变化的 dtype，同一串指令可以服务 FP4 路由权重（format 5）和 FP8 shared 权重（format 0），运行时选 format id 即可。

权重的 K128 tile 预打包是另一个纯带宽优化：原本按行主序 [E, rows, K/2] 存的 FP4 矩阵，被改写成 K128 tile 连续的 [E, kb, rows, 64]，一个 TMA descriptor 描述 (128, 128, 1, 1) 的四维 box，一次 TMA 就搬一个 8 KB 连续区间（FP8 shared 权重是 16 KB），而不是 128 段「每隔一整个权重行」的碎片。这个变换每个权重集只跑一次，可跨 token 数、容量、graph capture 复用。

Hopper 那边没有硬件 block scale，只能软件补：host 侧对每个 expert 算一个窗口基址（最多 11 个指数步），把落在窗口外的 FP4 幅值按精确的 2 的幂下移（用 4 bit 码空间的查找表），记录 per-expert 补偿因子，同时把 tile 字节按寄存器解码器需要的 lane 语义置换；kernel 里用两条 LDS.128 加 PRMT/LOP3 位操作把 FP4 解码成 E4M3，再发 register-A WGMMA，block scale 作为 MMA 外的 per-K32 FMA 施加。**这段代码的存在本身说明：FP4 权重的收益在 Hopper 上是靠位运算和重打包换来的，不是免费的。**

## 六、实测：54 个点，一个不输

测试配置很干净：8×H20（sm_90a）和 8×B300（CC 10.3），基线是 DeepGEMM 2.8.2 的 Mega MoE（B300 用公开的 fp8_fp4_mega_moe；H20 因为公开版只有 SM100 kernel，用作者按同一设计自建的 SM90 移植版）。协议是 CUDA Graph replay、每个窗口 100 次 replay、10 次预热 + 30 次测量窗口、测前清 L2，取八个 rank 里最慢的那个的中位数。token 数扫 T ∈ {1, 2, 4, 8, 16, 32, 64, 128, 256} 每 rank。

| 8×B300 | DSV4.1-Flash，融合 shared | 1.115× | 1.209× @ 1 token |

## 七、精度与带宽：没有偷偷换算术

GC-MoE 用的是调用方已经量化好的输入和基线同一套量化权重，做同样的低位算术，差别只在调度、布局和指令选择。H20 routed 套件 47 个用例 × 8 rank = 376 个 rank-case 全部通过：GC 与 BF16 的 cosine 最小 0.977（阈值 0.97），GC 与 Mega 的 cosine 最小 0.99999976；更硬的证据是两者的最大绝对误差都是 0.109375、最大相对 L2 误差都是 0.00600836286321，连 replay 重复差都是 0。B300 上 94 个用例、752 个 rank 检查同样全过。

吞吐方面（8 GPU 聚合、只计 matmul 工作量）：H20 在 8 token/rank 时从 73.8 提升到 95.6 TFLOPS（+29.5%，接近 1.296× 的峰值点），256 token/rank 时从 1251.4 到 1287.8。B300 上 GLM-5.2 在 256 token/rank 从 7524.8 到 8490.7 TFLOPS（+12.8%），1 token/rank 也从 75.3 到 82.5。

要注意的是，HBM 工作集带宽和 NVLink 载荷带宽都是**解析模型而不是硬件计数器**：前者数每个 owner 唯一活跃的专家权重加打包 scale，后者按每次 assignment 单向 (H + H/32 + 2H) 字节、只算专家在远端的那部分。模型给出的结论是 NVLink 载荷在同样 token 数下字节数不变、但等效带宽随加速比上升（H20 最大 batch 从 239.7 到 246.7 GB/s），也就是说分区并没有额外消耗跨 rank 带宽。

## 八、代码层核对：论文里的参数在仓库里确实是这样

仓库 `Bruce-Lee-LY/gc-moe`（MIT，v0.3.1）与论文同期。本机没有可用 GPU（`nvidia-smi` 报驱动不可用），所以这里只做静态核对，不声称复现了任何性能数字。

`gc_moe/runtime/gc_moe.py` 里分区逻辑与论文一致：`alignment = max(2, smCoscheduledAlignment)`、`compute_target = ((total − requested) // alignment) × alignment`、然后调 `cuDevSmResourceSplitByCount(1, whole, 0, compute_target)`；`GC_MOE_DISPATCH_SMS` 默认 16，B300 上 148 − 16 = 132 按对齐落到 128，互补的通信分区就是 20。

workqueue 那段比论文多一层保险：先要求设备 workqueue 资源的 `wqConcurrencyLimit ≥ 2`（否则直接报「cannot support two Green workers」），再把自己这个 context 的上限设成 1，创建后还用 `cuGreenCtxGetDevResource` 回读校验。这正对应论文那句「否则两个 context 可能落到同一个硬件队列上、静默串行化」——它是被代码显式防住的失败模式，而不是文档里的注意事项。

device code 规模：Blackwell 角色 1935 行、Hopper 角色 1305 行，另有共享的调度器、屏障、TMA、PTX 辅助。

## 九、批判性评估

**（1）没有分区大小的消融，也没有 overlap 开/关的对照。** 20/128 是「请求 16 + 驱动对齐」的产物，不是搜出来的最优点。论文自己把「controlled ablation of partition size」列进 future work，所以「20 个 SM 够用」这个结论目前只有间接证据（128 SM 的 GC-MoE 打赢 148 SM 的基线），没有「给 dispatch 8 个或 32 个会怎样」的曲线。

**（2）只覆盖 decode。** prefill 规模下计算分区而非重叠成为瓶颈，最大的 256 token/rank 点增益已经收到 1.01–1.13×。作者明确说这是 decode 专用算子。

**（3）H20 的基线是自建移植版，且 shared-expert 对比不同等。** 公开 DeepGEMM 只发 SM100 kernel，H20 上跑的是作者按同一设计写的 SM90 版本（单持久 kernel + warp specialization + NVLink 屏障），并且**没有**融合 shared-expert 路径。所以 H20 那组 1.353× 峰值是「融合 vs 未融合」，换到 B300 的同等特性对比里峰值只有 1.209×。跨平台比较这两组数字会高估收益。

**（4）适用范围被硬约束框死。** I ≤ 4096 且是 128 的倍数（64 位完成位图）、H 是 256 的倍数（2-CTA N tile 配对）、k + 1[shared] ≤ 32（一个 warp lane 一个 combine 槽）、全局专家数 ≤ 2048、rank 数 ≤ 72（592 字节 by-value peer descriptor 里 72 个偏移）。这些不是实现细节，是「这套设计只能服务这个形状的模型」。

**（5）workspace 单实例，共享同一 allocation 的调用必须串行。** 论文把它写进 limitations，但对一个要接进 serving 引擎的算子来说，这意味着并发请求要么排队、要么各开一份对称内存——后者在多租户场景里会迅速吃光显存。

**（6）有效吞吐与带宽是模型而非计数器。** TFLOPS 只算 matmul 工作量、HBM/NVLink 是解析式，这不影响「GC-MoE 比 Mega 快」的相对结论（延迟是真测的），但不要把这些数当 roofline 实测值引用。

## 十、对工程实践的启示

**第一，「融合」不是唯一方向，「隔离」也是。** 当一个算子里有两种性质完全不同的工作（延迟受限的通信、带宽受限的 GEMM），把它们塞进一个 kernel 会让资源预算和同步域互相绑死。Green Contexts 提供的是驱动级、零 MPS 守护进程的静态分区，比多 stream 有保证，比 MIG 细。这个原语在别的地方同样能用：prefill/decode 共卡、投机解码的 draft 与 verify、embedding 与 attention 的异构阶段。

**第二，尾屏障往往比你以为的贵。** Mega MoE 的 tag-2 屏障被 combine 遮住的时候看不出来，一旦 combine 变短就暴露成每次 replay 一次 NVLink 往返。用「奇偶双缓冲计数器 + 设备常驻状态」把它换成 release/acquire 链，是这类持久化算子通用的手法。

**第三，指令层的一次交换能省一整轮。** Blackwell 上的操作数交换（A 放权重、B 放激活）让 N 维变成 token 维，于是可以按「有效 token 数向上取整到 16」发指令，半空的块按比例少花时间——这种「让 tile 形状跟着真实工作量走」的技巧，在 decode 这种 M 极小的场景里比任何调度优化都直接。

**第四，低精度不是免费的，代价随架构变化。** 同一份 FP4 权重，Blackwell 上是一条原生指令，Hopper 上要窗口重打包 + 寄存器内解码 + MMA 外 FMA + ×64 抬动态范围。评估「FP4 值不值得」时，必须按目标架构分开算。
