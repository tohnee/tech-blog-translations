## 一、一个看似简单的问题

假设你有一个模型，单张 A100 80G 刚好装下。你买了 4 张卡，想让训练速度提升 4 倍。

最直觉的想法：把 batch 拆成 4 份，每张卡算一份。但问题来了——

每张卡算完自己的 batch 后，模型参数不一样了。如果每张卡各自更新参数，训练就变成了 4 个独立模型，结果不收敛。

那能不能让它们同步？

可以。**同步的本质是：每张卡算完 backward 后，把梯度加起来，求平均，然后每张卡用这个平均梯度更新参数。** 这样所有卡的模型参数始终保持一致。

这正是分布式训练的起点。也引出了第一个核心问题：**怎么把多张卡组织起来，高效地完成梯度同步？**

## 二、核心概念：从世界到 Rank

在 PyTorch 的分布式世界里，有几个你必须理解的基本概念。

### 2.1 四个关键术语

| 术语 | 含义 | 例子（4卡） |
| --- | --- | --- |
| World（世界） | 所有参与训练的进程的集合 | 4 个进程 |
| World Size | 世界中的进程总数 | 4 |
| Global Rank | 进程在全局的唯一 ID | 0, 1, 2, 3 |
| Local Rank | 进程在本地节点内的编号 | 0, 1, 2, 3（单机） |

![](https://pica.zhimg.com/v2-e2f23e97476a58d3cc6ed1f0db4202e4_1440w.jpg)

当你用 `torchrun --nproc_per_node=4` 启动时，PyTorch 会自动帮你创建 4 个进程，每个进程一个 GPU。它们通过 **ProcessGroup**（进程组）建立通信通道。

```python3
import torch
import torch.distributed as dist

# 初始化进程组（每个进程在启动时自动调用）
dist.init_process_group(backend='nccl')

# 获取当前进程的信息
rank = dist.get_rank()          # global rank
world_size = dist.get_world_size()  # 总进程数
local_rank = int(os.environ['LOCAL_RANK'])  # 本地 rank

# 绑定 GPU
torch.cuda.set_device(local_rank)
```

### 2.2 三种 Backend：NCCL、GLOO、MPI

| Backend | GPU 通信 | CPU 通信 | 使用场景 |
| --- | --- | --- | --- |
| NCCL | 🏆 最佳（NVLink/IB） | ❌ 不支持 | GPU 分布式训练（首选） |
| GLOO | ⚠️ 支持（较慢） | ✅ 很好 | CPU 训练、调试 |
| MPI | ✅ 支持 | ✅ 支持 | HPC 集群（需预装） |

**一句话选型**：多 GPU 训练只用 `nccl`，只有 CPU 训练才考虑 `gloo`。

### 2.3 六种集合通信操作

PyTorch 提供了 6 种基础通信原语，它们是所有分布式方案的基石：

```text
# 1. 广播：把 rank=0 的数据发给所有人
dist.broadcast(tensor, src=0)

# 2. 全局求和（最常用——梯度同步！）
dist.all_reduce(tensor, op=dist.ReduceOp.SUM)

# 3. 全收集：收集所有人的数据
dist.all_gather(tensor_list, tensor)

# 4. 先规约再分发：先求和再分片段
dist.reduce_scatter(tensor, input_list)

# 5. 发送（点对点）
dist.send(tensor, dst=1)

# 6. 接收（点对点）
dist.recv(tensor, src=0)
```

> **关键洞察**：`all_reduce(SUM)` 是 DDP 中梯度同步的核心。每张卡把梯度传给其他人，所有人求和后得到全局梯度，再除以 world_size 就是平均梯度。

完整的代码示例见 `pytorch-distributed/code/06_custom_collectives.py`

## 三、从零搭建 DDP：20 行代码跑起来

`DistributedDataParallel`（DDP）是 PyTorch 最成熟、最稳定的分布式方案。**核心思想极其简单**：把模型包装一下，backward 时自动进行梯度 AllReduce。

### 3.1 最小 DDP 示例

```python3
import torch
import torch.distributed as dist
from torch.nn.parallel import DistributedDataParallel as DDP

# 1. 初始化进程组
dist.init_process_group('nccl')
local_rank = int(os.environ['LOCAL_RANK'])
torch.cuda.set_device(local_rank)

# 2. 创建模型 + DDP 包装
model = torch.nn.Linear(1024, 1024).to(local_rank)
ddp_model = DDP(model, device_ids=[local_rank])

# 3. DataLoader 必须用 DistributedSampler 分片数据
dataset = torch.randn(10000, 1024)
sampler = torch.utils.data.DistributedSampler(dataset)
dataloader = torch.utils.data.DataLoader(dataset, sampler=sampler, batch_size=32)

optimizer = torch.optim.SGD(ddp_model.parameters(), lr=0.01)

for epoch in range(10):
    sampler.set_epoch(epoch)  # 每个 epoch 打乱数据
    for data in dataloader:
        data = data.to(local_rank)
        optimizer.zero_grad()
        loss = ddp_model(data).sum()
        loss.backward()    # ✨ 这里自动触发了梯度 AllReduce！
        optimizer.step()
```

**启动命令**：

```text
# 4 卡训练
torchrun --nproc_per_node=4 train.py
```

### 3.2 DDP 背后发生了什么？

在 `loss.backward()` 内部，DDP 做了三件事：

- **梯度注册**：每个参数的梯度计算完成后，Reducer 注册一个钩子
- **Bucketing**：小梯度合并成 ~25MB 的 bucket，减少通信次数
- **AllReduce**：整个 bucket 的梯度就绪后，触发一次 AllReduce

```text
# 可以通过 bucket_cap_mb 调整 bucket 大小
ddp_model = DDP(model, device_ids=[local_rank], bucket_cap_mb=100)
```

> **为什么要分 bucket**？每次 AllReduce 都有固定延迟开销。把 100 个小梯度合并成 1 个大梯度，通信次数从 100 次降到 1 次。大模型提升尤其显著。

### 3.3 DDP vs 老的 DataParallel

|  | DataParallel | DistributedDataParallel |
| --- | --- | --- |
| 机制 | 单进程多线程 | 多进程（每个 GPU 一个进程） |
| 通信 | 主卡串行收集 + 广播 | Ring AllReduce 分布式 |
| GIL | 受 GIL 限制 | 无 GIL |
| 扩展性 | 主卡瓶颈，2-4 卡极限 | 线性扩展到数百卡 |
| 结论 | 已被淘汰 | 生产标准 |

完整 DDP 示例见 `pytorch-distributed/code/01_ddp_minimal.py`

## 四、Ring AllReduce：分布式训练的基石算法

DDP 为什么高效？因为它在底层使用了 **Ring AllReduce** 算法。

### 4.1 直觉理解

想象 4 个人（GPU 0~3），每个人手里有 4 个数字。你想让所有人最终都拥有所有数字的**总和**。

**朴素方法**：所有人都把数据发给 GPU 0，GPU 0 算和，再广播回去。

- 通信量：4 × 3（发送）+ 4（广播）= 16 个单位
- 瓶颈：GPU 0 要接收 3 份数据，带宽受限

**Ring AllReduce**：所有人排成一个环，**每人只和左右邻居通信**。

- 通信量：2 × (N-1) = 6 个单位（N=4）
- 带宽利用率：100%（每张卡都在同时收发）

### 4.2 两阶段详解

![](https://pic2.zhimg.com/v2-5cfffb2f38bf7c4211cb033a1d3010f3_1440w.jpg)

**阶段一：Scatter-Reduce（分散-规约）**

以 4 卡为例，每张卡的梯度数据切成 4 块（A、B、C、D）：

| 步骤 | GPU 0 → GPU 1 | GPU 1 → GPU 2 | GPU 2 → GPU 3 | GPU 3 → GPU 0 |
| --- | --- | --- | --- | --- |
| 1 | 发送 A → 累加 A' | 发送 B → 累加 B' | 发送 C → 累加 C' | 发送 D → 累加 D' |
| 2 | 发送 D→ 累加 D'' | 发送 A → 累加 A'' | 发送 B → 累加 B'' | 发送 C → 累加 C'' |
| 3 | 发送 C→ 累加 C''' | 发送 D→ 累加 D''' | 发送 A → 累加 A''' | 发送 B → 累加 B''' |

3 步后，每张卡持有一个**聚合完成**的数据块。

**阶段二：AllGather（全收集）**

把聚合好的块广播给所有人——同样是 3 步，每张卡发送自己持有的聚合块，最后所有人都拥有完整的聚合结果。

**N 张卡的通信量**：$2 \times (N-1) \times \text{每块大小}$

对比朴素方法的 $2 \times N \times \text{总大小}$，Ring AllReduce 的通信量**与卡数无关**——卡越多，每张卡的通信量反而越少。

### 4.3 代码验证

```python3
import torch
import torch.distributed as dist

dist.init_process_group('nccl')
rank = dist.get_rank()

# 每个 rank 持有不同的值
tensor = torch.tensor([rank + 1.0]).cuda()

# AllReduce 求和
dist.all_reduce(tensor, op=dist.ReduceOp.SUM)

if rank == 0:
    print(f"AllReduce SUM result: {tensor.item()}")  # 输出: 1+2+3+4 = 10
```

完整的 AllReduce 示例见 `pytorch-distributed/code/02_all_reduce_basics.py`

## 五、FSDP：参数分片，打破显存墙

DDP 很好，但有一个前提：**模型必须能完整放进单卡显存**。如果你有一个 70B 的模型（仅参数就 140GB 显存），8 张 A100 80G 加起来也放不下完整副本。

这时你需要 **FSDP（Fully Sharded Data Parallel）**。

### 5.1 核心思想：ZeRO-3

FSDP 的思想来自 DeepSpeed 的 **ZeRO**（Zero Redundancy Optimizer）：

| 阶段 | 分片内容 | 显存节省（4卡） | 通信量 |
| --- | --- | --- | --- |
| ZeRO-1 | 仅优化器状态 | ~4x | 不变 |
| ZeRO-2 | 优化器状态 + 梯度 | ~8x | 略增 |
| ZeRO-3 | 优化器状态 + 梯度 + 参数 | ~Nx | 显著增加 |

![](https://picx.zhimg.com/v2-62e21754d65488d04d381a5fd2fc6ffb_1440w.jpg)

**FSDP = ZeRO-3**：把模型参数、梯度、优化器状态均匀分到 N 张卡上。每张卡只持有 $\frac{1}{N}$。

那前向计算怎么办？参数都不完整怎么做推理？

**答案**：计算到哪层，**AllGather 那层的参数**，算完就释放。这个过程叫 **参数物化（Materialize）**：

```text
前向:
  Layer 0: AllGather 参数0 → 计算 → 释放参数0
  Layer 1: AllGather 参数1 → 计算 → 释放参数1
  ...

反向:
  Layer 1: AllGather 参数1 → 计算梯度 → ReduceScatter 同步 → 释放
  Layer 0: AllGather 参数0 → 计算梯度 → ReduceScatter 同步 → 释放
  ...
```

### 5.2 三种分片策略

FSDP 提供了多个 sharding 策略：

```text
from torch.distributed.fsdp import ShardingStrategy

# FULL_SHARD: 全分片（ZeRO-3），推荐大模型
fsdp_model = FSDP(model, sharding_strategy=ShardingStrategy.FULL_SHARD)

# SHARD_GRAD_OP: 只分片梯度+优化器状态（ZeRO-2）
fsdp_model = FSDP(model, sharding_strategy=ShardingStrategy.SHARD_GRAD_OP)

# HYBRID_SHARD: 节点内全分片，节点间数据并行
fsdp_model = FSDP(model, sharding_strategy=ShardingStrategy.HYBRID_SHARD)

# NO_SHARD: 不分片（等价 DDP），用于调试
```

| 策略 | 显存节省 | 通信量 | 推荐场景 |
| --- | --- | --- | --- |
| FULL_SHARD | 🏆 最大 | 最高 | 单机多卡，模型刚好超显存 |
| HYBRID_SHARD | 中等 | 较低 | 多机训练，节点间带宽有限 |
| NO_SHARD | 无（同 DDP） | 最低 | 调试、对比基线 |

### 5.3 FSDP2：组合式 API

PyTorch 2.4+ 引入了新的 **FSDP2**（composable FSDP），API 更灵活：

```text
from torch.distributed._composable.fsdp import fully_shard

# 对每个 transformer layer 分别分片
for layer in model.layers:
    fully_shard(layer, mp_policy=mp_policy)

# 再对整体分片
fully_shard(model, mp_policy=mp_policy)
```

### 5.4 使用 DistributeSampler + FSDP 的完整示例

```text
from torch.distributed.fsdp import FullyShardedDataParallel as FSDP
from torch.distributed.fsdp.wrap import transformer_auto_wrap_policy

fsdp_model = FSDP(
    model,
    auto_wrap_policy=functools.partial(
        transformer_auto_wrap_policy,
        transformer_layer_cls={TransformerBlock}
    ),
    sharding_strategy=ShardingStrategy.FULL_SHARD,
    device_id=local_rank,
    mixed_precision=MixedPrecision(
        param_dtype=torch.bfloat16,
        reduce_dtype=torch.bfloat16,
        buffer_dtype=torch.bfloat16,
    ),
)
```

完整 FSDP 示例见 `pytorch-distributed/code/03_fsdp_huggingface.py`

## 六、多维并行：TP + PP + DeviceMesh

当模型大到 FSDP 都扛不住时（比如 >100B），就需要更细粒度的并行策略。

### 6.1 张量并行（Tensor Parallelism, TP）

**动机**：单个矩阵乘法的权重太大，放不进一张卡（比如 GPT-3 175B 的中间层 MLP 权重超过 80GB）。

**方案**：把**一个矩阵乘法拆到多张卡上**。

- **列并行（Column Parallel）**：$W$ 按列切开，每卡计算一部分输出，AllGather 合并
- **行并行（Row Parallel）**：$W$ 按行切开，每卡接收完整输入，AllReduce 求和

```text
# PyTorch 2.0+ 内置 TP API
from torch.distributed.tensor.parallel import (
    ColwiseParallel, RowwiseParallel, parallelize_module
)

plan = {
    "in_proj": ColwiseParallel(),   # 列并行
    "out_proj": RowwiseParallel(),   # 行并行
}
model = parallelize_module(model, mesh, plan)
```

### 6.2 流水线并行（Pipeline Parallelism, PP）

**动机**：模型层数太多（>100），按层切分到不同设备。

**方案**：把模型按层切成几个 stage，每个 stage 放在不同卡上。数据以 **micro-batch** 的方式在流水线中推进。

```text
from torch.distributed.pipeline.sync import Pipe

# 将模型切分到 4 张卡上
model = Pipe(model, chunks=4, checkpoint='except_last')
output = model(input)
```

但流水线有**气泡（bubble）**：在流水线填满之前，后面的卡是空闲的。1F1B（One-Forward-One-Backward）调度可以显著减少气泡。

### 6.3 DeviceMesh：统一管理多维并行

![](https://pica.zhimg.com/v2-97369b4d2bd9339643ab796fc1fdd31a_1440w.jpg)

如果同时使用 TP + DP，需要管理两组通信组。PyTorch 2.0+ 引入 **DeviceMesh** 统一管理：

```text
from torch.distributed.device_mesh import DeviceMesh

# 8 卡组织成 4×2 网格
mesh = DeviceMesh("cuda", [
    [0, 1],   # 行 0: 数据并行组
    [2, 3],   # 行 1
    [4, 5],   # 行 2
    [6, 7],   # 行 3
])

# 获取子组
dp_group = mesh.get_group(mesh_dim=0)  # 数据并行组（行方向）
tp_group = mesh.get_group(mesh_dim=1)  # 张量并行组（列方向）
```

### 6.4 DTensor：分布张量就在你手中

结合 DeviceMesh，PyTorch 提供了 **DTensor**——一种"知道自己是怎么分布在多卡上的张量"：

```text
from torch.distributed.tensor import DTensor, Shard, Replicate

mesh = DeviceMesh("cuda", list(range(4)))

# 沿第0维分片（数据并行场景）
dt = DTensor.from_local(tensor, mesh, [Shard(0)])

# 全复制（优化器状态等）
dt = DTensor.from_local(tensor, mesh, [Replicate()])
```

完整 DeviceMesh 示例见 `pytorch-distributed/code/07_device_mesh.py`

### 6.5 3D 混合并行

工业级超大规模训练（如 GPT-4、Llama 405B）通常组合三种并行：

```text
节点集群
     /      |      \
  节点组1  节点组2  节点组3     ← 数据并行 (DP)
   /   \    /   \    /   \
 GPU0 GPU1 GPU2 GPU3 GPU4 GPU5  ← 张量并行 (TP)
   \   /    \   /    \   /
  stage0    stage1    stage2     ← 流水线并行 (PP)
```

这种 **3D 混合并行**方案下，8 张 A100 可能这样分配：

- TP=4（节点内 4 卡做张量并行，利用 NVLink 高速带宽）
- PP=2（2 组 TP 组成流水线）
- DP=N（多组流水线之间做数据并行）

## 七、并行策略选择：决策树与实战经验

面对这么多选择，到底该用哪个？

![](https://picx.zhimg.com/v2-9f151798a6301f295e48373e16e7acb7_1440w.jpg)

### 7.1 决策树

```text
模型能否放入单卡显存？
├── ✅ 是，且显存充裕（<60%） → DDP
│     └── 最简单，性能最佳，线性加速
├── ⚠️ 能放入但显存紧张（>80%） → FSDP FULL_SHARD
│     └── 节省 3-4 倍显存，略微增加通信
├── ❌ 模型超过单卡显存
│     ├── 参数量 < 70B → FSDP HYBRID_SHARD
│     └── 参数量 > 70B → TP + PP + DP（3D 混合并行）
│           └── 需要 Megatron-LM 或 DeepSpeed
```

### 7.2 性能对比表

| 方案 | 参数量范围 | 显存效率 | 通信量 | 实现复杂度 |
| --- | --- | --- | --- | --- |
| DDP | < 5B | ⭐⭐ | ⭐（最低） | ⭐（最简单） |
| FSDP FULL_SHARD | 5B ~ 70B | ⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐ |
| FSDP HYBRID_SHARD | 10B ~ 100B | ⭐⭐⭐ | ⭐⭐ | ⭐⭐ |
| TP（节点内） | > 70B | ⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ |
| PP（流水线） | > 100B | ⭐⭐⭐ | ⭐⭐ | ⭐⭐⭐ |
| 3D 混合并行 | > 175B | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |

### 7.3 学习率的线性缩放法则

这是一个经常被遗忘但极其重要的细节：

> 从单卡扩展到 N 卡时，batch size = N × base_batch，**学习率也要乘以 N**。

```text
# 单卡: batch=32, lr=1e-4
# 4 卡: batch=128, lr=4e-4 (需要 warmup 稳定)
```

如果没有线性缩放，Loss 可能会爆炸或不收敛。

## 八、生产落地：避坑清单 15 条

多年的分布式训练实战中，以下问题反复出现。我整理了一份 checklist，每次发布前对照检查。

### 🔴 进程初始化（卡住 > 检查这 4 条）

| # | 问题 | 症状 | 解决方案 |
| --- | --- | --- | --- |
| 1 | 网卡未绑定 | NCCL 初始化时 Connection refused | export NCCL_SOCKET_IFNAME=ib0,eth0 |
| 2 | 无 IB/RoCE 但 NCCL 试图使用 | 超时或降速严重 | export NCCL_IB_DISABLE=1 |
| 3 | 超时太短 | 大模型首次 AllReduce 超时 | dist.init_process_group(timeout=timedelta(seconds=1800)) |
| 4 | 忘记设置 device | 所有进程都卡在 cuda:0 | torch.cuda.set_device(local_rank)，绝不用 cuda:0 硬编码 |

### 🟡 代码层面（训练异常 > 检查这 5 条）

| # | 问题 | 解决方案 |
| --- | --- | --- |
| 5 | DataLoader shuffle 不一致 | DistributedSampler 必须设置 set_epoch() |
| 6 | 梯度累积时 AllReduce 过多 | 非 step 轮次用 model.no_sync() |
| 7 | find_unused_parameters 未设置 | 有 unused 参数时必须设为 True，否则设为 False 加速 |
| 8 | 未用 torchrun | torchrun 自动注入环境变量，替代已废弃的 launch |
| 9 | 混合精度 + DDP 的 GradScaler | 每卡独立 scaler，Loss 缩放正常 |
