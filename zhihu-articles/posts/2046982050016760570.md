1. 背景介绍

随着大语言模型规模不断增大，模型训练对显存、计算资源、训练框架和数据处理流程的要求越来越高。对于入门实验来说，直接使用 7B、14B 甚至更大模型，往往会同时遇到显存不足、训练速度慢、数据加载复杂、优化器配置不当等问题，不利于理解“模型训练到底怎么做”。

因此，本文选择 Qwen2.5-0.5B-Instruct 作为入门模型，使用 PyTorch + Transformers + DeepSpeed 搭建一个轻量、可复现的训练流程。DeepSpeed 官方文档中给出的核心训练流程也是：先初始化 DeepSpeed engine，然后通过 forward、backward() 和 step() 完成训练循环；DeepSpeed 还可以通过配置文件启用混合精度、优化器和 ZeRO 等能力。

本文重点讲清楚：

1. 数据集怎么准备

2. 模型和 tokenizer 怎么加载

3. 训练样本怎么构造

4. DeepSpeed 怎么配置

5. 训练脚本怎么写

6. 训练怎么启动

7. loss 和 step 日志怎么看

本文不讨论 K8s、网络通信、集群调度和 msprof，只关注模型训练本身。

4. 数据集准备路线

建议按三个阶段准备数据集。

5. 准备 tiny_shakespeare

tiny_shakespeare 是一个纯文本数据集，适合作为第一个 smoke test。

目录示例：

workload/datasets/tiny_shakespeare/input.txt

读取代码：

from datasets import Dataset

data_path = "workload/datasets/tiny_shakespeare/input.txt"

with open(data_path, "r", encoding="utf-8") as f:

text = [f.read](http://f.read/)()

dataset = Dataset.from_dict({"text": [text]})

这个数据集很小，不适合评估模型质量，但非常适合确认训练链路是否完整：

tokenizer 能否加载

模型能否 forward

loss 是否正常

backward 是否能执行

optimizer 是否能更新

训练日志是否能输出

第一轮训练建议就用它。

6. 准备 wikitext-103

wikitext-103 更适合做稳定训练采样。它比 tiny_shakespeare 更接近正常语言建模数据，又不会像 openwebtext 那样太重。

如果本地是 parquet 文件，可以这样读取：

8. Tokenizer 与训练样本构造

Causal Language Modeling 的训练目标是：

给定前面的 token，预测下一个 token

训练样本通常需要三个字段：

input_ids

attention_mask

labels

对于 causal LM，常见做法是：

labels = input_ids.copy()

Hugging Face Transformers 的 causal language modeling 任务文档也将“根据一段 token 序列预测下一个 token”作为核心训练目标。

示例代码：

from transformers import AutoTokenizer

model_path = "workload/models/Qwen2.5-0.5B-Instruct"

tokenizer = AutoTokenizer.from_pretrained(

model_path,

trust_remote_code=True,

)

if tokenizer.pad_token is None:

tokenizer.pad_token = tokenizer.eos_token

def tokenize_fn(examples):

out = tokenizer(

examples["text"],

truncation=True,

max_length=128,

padding="max_length",

)

out["labels"] = out["input_ids"].copy()

return out

tokenized_dataset = [dataset.map](http://dataset.map/)(

tokenize_fn,

batched=True,

remove_columns=dataset.column_names,

)

新手阶段注意四点：

1. max_length 先固定为 128

2. labels 不要漏

3. pad_token 要设置

4. remove_columns 要根据原始字段调整

9. 为什么 seq_len 从 128 开始

seq_len 是影响训练速度和显存占用的重要参数。序列越长，模型每个 step 需要处理的 token 越多，forward 和 backward 都会变慢，显存占用也会上升。

推荐演进顺序：

128 → 512 → 1024 → 2048

每次只改一个变量，然后观察：

step_ms 是否增加

forward_ms 增加多少

backward_ms 增加多少

显存是否足够

loss 是否正常

新手阶段不要一开始就用 2048，否则一旦出现 OOM 或 step 很慢，很难判断问题来自哪里。

10. DeepSpeed 配置

第一版建议用最简单的 DeepSpeed 配置。

ds_config.json：

{

"train_micro_batch_size_per_gpu": 1,

"gradient_accumulation_steps": 1,

"steps_per_print": 1,

"zero_optimization": {

"stage": 0

},

"bf16": {

"enabled": true

}

}

如果环境不支持 bf16，可以改用 fp16：

{

"train_micro_batch_size_per_gpu": 1,

"gradient_accumulation_steps": 1,

"steps_per_print": 1,

"zero_optimization": {

"stage": 0

},

"fp16": {

"enabled": true

}

}

推荐调试顺序：

ZeRO stage 0：最简单，先跑通训练链路

ZeRO stage 1：开始降低 optimizer state 冗余

ZeRO stage 2：进一步处理梯度分区

ZeRO stage 3：参数也参与分区，复杂度最高

入门阶段不要一开始就使用 ZeRO stage 3 或 offload。否则训练变慢时，很难判断是模型计算、数据处理还是优化器策略导致的。

11. 训练代码结构

参考工程化训练脚本的写法，代码可以拆成以下模块：

参数解析

随机种子设置

加载 tokenizer

加载模型

加载数据集

数据预处理

构造 DataLoader

DeepSpeed 初始化

训练循环

保存模型与日志

DeepSpeed 官方文档中，训练循环的核心接口就是 forward、model_engine.backward(loss) 和 model_engine.step()；deepspeed.initialize 会把模型包装成 DeepSpeed engine，并处理分布式、混合精度、优化器等训练细节。

核心训练循环可以这样写：

import time

import json

for step, batch in enumerate(dataloader):

if step >= args.max_steps:

break

batch = {

k: [v.to](http://v.to/)(engine.device)

for k, v in batch.items()

}

step_start = time.time()

forward_start = time.time()

outputs = engine(**batch)

loss = outputs.loss

forward_end = time.time()

backward_start = time.time()

engine.backward(loss)

backward_end = time.time()

optimizer_start = time.time()

engine.step()

optimizer_end = time.time()

record = {

"step": step,

"loss": float(loss.detach().cpu()),

"step_ms": (optimizer_end - step_start) * 1000,

"forward_ms": (forward_end - forward_start) * 1000,

"backward_ms": (backward_end - backward_start) * 1000,

"optimizer_ms": (optimizer_end - optimizer_start) * 1000,

}

print(json.dumps(record, ensure_ascii=False), flush=True)

这部分日志就是后续训练分析的基础。

13. Step 耗时分析方法

训练结束后，不要只看 loss，还要看 step 耗时。

建议统计：

avg_step_ms

p50_step_ms

p90_step_ms

p99_step_ms

avg_forward_ms

avg_backward_ms

avg_optimizer_ms

forward_ratio

backward_ratio

optimizer_ratio

分析顺序：

1. loss 是否正常，不是 nan 或 inf

2. step_ms 是否在 warmup 后趋于稳定

3. forward、backward、optimizer 哪个阶段占比最高

4. 是否有某些 step 异常变慢

5. 异常 step 是否与 checkpoint、数据读取或日志写入有关

你当前训练结果里，稳定阶段大致是：

step ≈ 371 ms

forward ≈ 75 ms

backward ≈ 194 ms

optimizer ≈ 101 ms

所以可以初步判断：

backward 是主要耗时阶段

optimizer 也有明显成本

forward 相对较轻

14. Warmup 处理

训练前几个 step 往往包含首次初始化、缓存构建、优化器状态初始化等额外开销，所以不应该直接纳入稳定性能统计。

建议：

max_steps = 20：丢弃前 5 step

max_steps = 100：丢弃前 20 step

max_steps = 1000：丢弃前 50 step

只分析 stable steps。

例如训练报告里可以写：

stable_steps = 20 ~ 99

avg_step_ms = ...

p90_step_ms = ...

avg_forward_ms = ...

avg_backward_ms = ...

avg_optimizer_ms = ...

15. 常见问题排查

15.1 loss 变成 nan 或 inf

常见原因：

学习率过大

混合精度溢出

labels 构造错误

pad_token 未正确设置

数据中存在异常样本

处理建议：

降低 learning rate

检查 labels 是否等于 input_ids

检查 pad_token 和 eos_token

先用 tiny_shakespeare 做最小复现

15.2 forward 慢

常见原因：

seq_len 太长

batch 太大

padding 太多

dtype 没有正确生效

处理建议：

降低 seq_len

降低 micro_batch_size

检查 padding 策略

确认 bf16/fp16 是否实际生效

15.3 backward 慢

常见原因：

反向传播本身计算量更大

seq_len 或 batch 太大

开启 gradient checkpointing 后发生 recompute

混合精度配置导致额外处理

处理建议：

先关闭 gradient checkpointing 做基线

固定 seq_len 做对比实验

比较 backward / forward 比例

逐步增加 seq_len 看耗时变化

15.4 optimizer 慢

常见原因：

优化器状态更新成本高

ZeRO stage 改变 optimizer 行为

gradient_accumulation_steps 过小

checkpoint 或日志写入过频繁

处理建议：

比较 ZeRO stage 0 / 1 / 2

适当增加 gradient_accumulation_steps

减少 checkpoint 频率

减少过密日志输出

18. 最终总结

本文采用 Qwen2.5-0.5B-Instruct 作为轻量模型，使用 PyTorch、Transformers 和 DeepSpeed 搭建一个可复现的模型训练实验。数据集从 tiny_shakespeare 开始，用于快速跑通训练链路；随后切换到 wikitext-103 做稳定耗时采样；最后使用 openwebtext 做长时间训练测试。

整个流程的关键不是一开始追求模型效果，而是先建立清晰的训练基线：

模型能加载

数据能读取

loss 能下降

step 能稳定

forward / backward / optimizer 耗时能记录

不同数据集和 seq_len 能做对比

一句话总结：

这套训练方案的核心是用 Qwen0.5B 构造一个轻量、真实、可观测的语言模型训练 workload，通过结构化 step trace 分析训练稳定性和阶段耗时，为后续更复杂的训练实验打基础。
