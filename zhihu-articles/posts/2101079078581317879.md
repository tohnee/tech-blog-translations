——从 DeepSeek 的 Super-agent 架构阅读后的思考

在 6 月份的时候，就有字节的同事给我私信，催我再分享分享一些经验和思考。我说好的。可我到了 7 月份离职，也没能攒出一篇文章。

不是我不想写，而是不知道该怎么写。

当时自己用 Codex 和 Claude codex 用的飞起，业内关于 Harness 的实践和设计相关的文章也一堆。那时候感觉一切都是那么美妙。分享点啥都不如让 AI 赶紧给我做出结果来有价值。

然后我就踩坑了。

**我的开发方式是怎样一步步演进过来的**

![](https://pic1.zhimg.com/v2-4183bbeae993df423447414276ca3fda_r.jpg)

熟悉我的朋友都知道，我业余时间一直在做一个 AI Native 的游戏引擎，可以由LLM 驱动，实现玩家自己真实穿越到游戏里的体验。我设想中的，是一个跟现在图像引擎一样的，剧情引擎。可以驱动游戏里的 NPC 和故事的发展一直能随着玩家各种骚操作还能继续正常进行下去。

这个引擎需要处理角色记忆、NPC 自主行为、多 Agent 交互、时间推进，以及世界状态的一致性。最初只是想验证一些玩法，功能慢慢加上去，才发现它已经成了一个需要长期维护、持续演进的软件工程项目。

我最初设想里，按照前期需求，一到两个月的时间肯定能开发出来基础版本，然后我再用 demo 不断打磨。结果我开始遇到第一个问题，我自己的上下文不够了。

我需要同时推进多个 codex 和 Claude code 的 session 进行推进。尤其是前期任务拆分不到位的时候，很多 session 之间还会有耦合开发的情况，需要我不断给出判断和更细致的拆分。我也会在多个 session 之间来回切换的时候搞错一些 session 负责的任务。

于是，我调整了开发模式。我把Claude Code 调整成负责整体规划和任务安排，具体编码交给 Codex，或者由它自己启动 Subagent 完成。

说实话，这套方式已经很强了。给 Claude Code 一个比较完整的目标，它能分析需求、拆分工作，启动多个 Subagent 并行开发，最后把结果汇总回来。

但用了一段时间，我发现我越来越开发过程又开始失控了。

我知道主 Agent 在工作，也知道它启动了几个 Subagent。可从项目的角度看，一共拆了多少任务？哪些正在执行？谁依赖谁？哪些已经完成，哪些还在反复修改？ 我跟主 Agent 对齐了，但subagent执行里有没有违背我想法的方案？有没有我没想到的细节，被 subagent 自以为是的决定了？

这些信息散落在不同的 Session、执行日志和代码提交里。我只能依赖主 Agent 帮我去做追踪。而长期使用一个主 Agent 也会给上下文带来极大的压力，开始对中间部分细节失控，经常会过分关注我最近关注的事情，而对之前讨论清楚的一些问题产生“失忆”。

所以，我决定开始引入 Linear。最初的目的很简单：让 Agent 的开发过程看得见，让我能够从项目的角度管理进度，也可以更方便后续如果要切换主 Agent 的时候，项目过程可以追踪。

Linear 只是我这次选的工具。GitHub Issues、Jira，或者其他具备任务和依赖管理能力的系统，也可以承担类似的角色。我需要的是一个独立于 Coding Agent Session、能够长期保存和更新项目工作状态的协作层。

没想到，这次调整却给我带来了完全不一样的感觉，也让我对未来跟 AI 如何合作有了新的思考。

恰好在这个过程中，我读到了 DeepSeek 的 Super-agent 文章，又有了很多共鸣的地方。于是我想分享一些我自己的思考和经验。

**一个持续48 小时的开发里，Claude code 在忙什么？**

![](https://picx.zhimg.com/v2-3e80e6516f1375af01d024fc8226c2cf_r.jpg)

我回顾了一段最近 Claude Code 的完整开发会话，前后约 48 小时。

根据导出会话的粗略复盘，这段时间涉及约 45 个 Linear 任务。主 Agent 启动了数十次 Subagent，也大量调用 Codex 完成实现，过程中产生了数十份审查和复审报告。主 Agent 自己则经历了多次上下文压缩。它包含了规划、依赖管理、实现、审查、集成和回归验证。

当时的分工是：Claude Code 负责规划、派活和协调，Codex 与 Subagent 负责实现，Opus 或 Astra 负责审查，最终 PR 由我确认合并。

看起来分工已经明确了，但把这些分别完成的工作拼起来，问题才开始出现。

**做完一个任务，和完成一个项目，是两回事**

在这个过程中首先暴露了一个很直接的问题：一个模块使用 `delta`，其他模块使用 `amount`，接口字段的命名没有对齐。

单独看某个模块，可能没有明显问题。一旦接起来，就会发现双方对接口的理解不一致。

![](https://pic3.zhimg.com/v2-9963deba4f7f94c26dfab2f1f7cb2c2e_r.jpg)

**一个任务在局部成立，不代表它能正确地成为整个项目的一部分。**

而且，项目也不是一张定下来就不再变化的任务清单。接口可能调整，需求可能改变，原来看起来合理的设计，也可能在后续开发里暴露问题。

所以，除了完成单个任务，我们还得处理任务之间的依赖、集成和变化。当这些工作跨越多个模块、多个 Session 时，项目管理本身就成了一项需要单独考虑的工作。

**任务怎么拆，比有多少 Agent 更影响有效并发**

这轮开发里，有一件事让我印象很深。

最初制定 Linear 计划时，大量任务都依赖 E1，也就是引擎内核整理和目录迁移。按当时的依赖关系，E1 没完成，后面很多工作就不能开始，整个计划几乎排成了一条串行队列。

![](https://pic1.zhimg.com/v2-7798b5364f4dff48c6944d0bca148d1a_r.jpg)

后来我提出，希望尽量提高并发度。主 Agent 重新分析以后，把部分工作分成了模块内部实现和模块接入主循环两类。

模块内部的工作，可以在独立 Worktree 里并行开发。接入主循环则会修改共享核心代码，需要更谨慎地安排顺序。

Codex 在评审时，又补充了一个很有价值的区分：**下游任务需要等的，究竟是上游接口已经合入，还是上游整个模块已经完成运行时接入？**

这两个条件不一样。

如果下游只需要一份稳定的接口定义，就没必要等上游全部开发和集成完成。经过这轮调整，原来几乎串行的计划，可以提前展开七条工作线。

并发空间很大程度上是从任务边界和依赖关系里产生的。即使有二十个空闲 Agent，如果任务被排成一条不必要的长链，它们也只能等着。反过来，为了并行而忽略真实依赖，最后又可能花更多时间处理集成和返工。

因此，任务规划和任务调度需要分开看。调度器可以按照明确的依赖安排执行，但依赖本身是否合理，仍然需要理解项目架构。

这也是我开始认真定义任务规范的原因。

比如，一个 NPC 记忆功能，不能只写“实现 NPC 记忆系统”。我希望任务至少能说明下面这些事情：

**任务：NPC 记录亲历事件**

- **目标：** NPC 能记录自己亲历的事件，并在后续行为与对话中使用这些记忆。
- **约束：** 不能把 NPC 没有观察到、也没有通过合法途径获知的信息，直接写入它的亲历记忆。
- **依赖：** 已有的事件输入与角色状态接口。
- **验收：** 在指定场景里，在场 NPC 应获得对应记忆；不在场、也没有其他信息来源的 NPC，不应获得这段记忆。
- **交付：** 实现代码、测试结果和对应的变更记录。

这只是任务契约的示意，并不是某条 Linear Issue 的逐字记录。

它的重点也不在于写得多详细，而在于一个新的执行者能否通过任务和关联资料，理解自己要做什么，以及怎样才算完成。

后期的实际开发给了我一些正面反馈。部分任务拆出了不涉及主循环的独立工作，可以交给不同的 Codex 执行。中途还遇到过模型容量不足，原来的模型无法继续，任务便转交给另一个模型处理。

只要任务契约、工作区和必要资料还在，工作就不必完全依赖某个具体 Session。

顺着这个思路，我又产生了一个疑问：如果任务已经具备独立执行的条件，为什么还需要主 Agent 每次亲自分配？

![](https://pic3.zhimg.com/v2-7bcf4097394257cda24853456f48c5dc_r.jpg)

**项目往前走，计划也会跟着变**

最近还有一件事，让我重新想了想，项目管理究竟在管理什么。

我们一直保留一个订婚宴小剧场，用来验证游戏引擎的能力。它承担的是回归验证，并不是最终要重点开发的产品。

此前，我给它定过一项时间规则：订婚宴每两分钟推进一步，另一个列车剧场采用十五秒步长。这个决定是我自己作出的。

但在后续开发里，两分钟步长带来了一系列连锁变化。开场时间需要调整，旧脚本出现兼容问题，已有测试基准需要重新整理，相关适配任务也不断增加。

每一项工作都能拆成明确任务，再交给 Agent 实现、测试和审查。但后来，我重新问了自己一个问题：订婚宴只是用来验证引擎能力，值得为它投入这么多开发资源吗？

重新评估以后，我们发现这些工作并没有直接增加真正需要的引擎核心能力。最后决定让订婚宴恢复一分钟步长，继续承担回归验证的角色。

这里值得注意的是，最初的设计并不是 Agent 擅自作出的。它经过了我的确认，只是执行下去以后，我们发现实际成本比预期更高，于是调整了原来的判断。

项目里的很多决定，都很难在作出时就看清全部影响。有些成本和问题，只有做下去才会暴露出来。

这也是长期项目和单个任务之间更深的一层区别。一个任务通常是在相对确定的目标和约束下寻找实现方式。项目开发过程中，目标、约束、技术方案，甚至我们对问题本身的理解，都可能变化。

这轮开发里，任务依赖重新拆分了，Worker 的停止条件调整了，验证流程补充了新规则，连我自己已经确认的设计，也被后续反馈重新摆到了讨论里。

这些变化不全是错误。有些正是项目逐渐接近正确方向的过程。

**长期项目需要在不断获得新信息的过程中，修正计划并继续推进交付。**

于是，我开始把项目中的工作分成两类。

一类是执行：领取任务、修改代码、运行测试、提交结果、完成集成。

另一类是治理：需求还合理吗？依赖是否需要调整？哪些工作值得继续，哪些应该停止？项目是否仍在朝预期目标前进？

增加 Worker 的并发度，主要改善前一类。如果后一类没有跟上，更快的执行速度也可能只是让资源更快消耗掉。

**原来业内已经有不少类似尝试**

恰好在这轮开发过程中，我读到了 DeepSeek 的《Super-agent 设计探索：迈向更自主的 Agent 系统》。

让我产生共鸣的，除了 Router / Worker 双层架构，还有它对问题的判断：模型越来越能独立执行复杂任务，人不必再干预每一步，但当多个 Agent Session 同时运行时，人的注意力和协调成本又成了限制。

把工作都放在同一个 Session，会受到执行吞吐和上下文干扰的影响；拆到独立 Session，又会出现上下文割裂和协作问题。DeepSeek 因此把全局连续性和局部并发执行分开：Router 负责持续交互、理解事件和协调，Worker 在独立上下文里执行具体任务。

对于责任归属已经明确的工作，后续事件可以通过订阅关系直接送到对应 Worker，不必每次重新让模型判断该交给谁。任务状态、授权和执行生命周期，则由确定性系统管理。

这和我最近思考的问题很接近：哪些事情需要模型理解和判断，哪些可以交给软件系统按明确规则处理？

不过，DeepSeek 的目标更广，还涉及跨渠道交互、主动响应和持久运行，并不是专门从软件项目管理推导出的架构。

再看其他团队，也能找到一些相似的尝试：

| 行业实践 | 公开的设计与实践 | 能够支持的结论 |
| --- | --- | --- |
| DeepSeek Super-agent | Router / Worker、事件订阅、持久化工作对象和确定性运行时；进行了合成事件负载下的初步调度实验 | 多 Session 的连续性与并发调度可以系统化处理；实验尚未验证真实编码质量 |
| OpenAI Symphony | 将 Linear 类任务系统作为控制平面，按工作项和依赖组织 Codex，在独立工作区执行，并保留人工审查 | 外部任务驱动的 Coding Agent 编排已有真实工程应用 |
| Cursor 长程自治开发 | 最初尝试平等 Agent 自主协调，遇到锁竞争和任务责任问题，随后采用 Planner / Worker 分工 | 增加 Agent 数量不一定提高有效吞吐，规划和协调机制很重要 |

放在一起看，一个值得注意的方向是：**工作正在从 Agent Session 中独立出来。**

DeepSeek 用 Ticket 承载持续的工作责任，Symphony 围绕外部任务组织 Codex，Cursor 则通过规划与执行分工，管理大型任务的复杂度。

任务外置、并行执行和多 Agent 编排，已经有了具体实践。但这还不能证明，长期软件项目可以完全无人监督地自主交付。尤其当需求、设计和依赖持续变化时，怎样让参与者依据同一份有效的项目认知工作，仍然值得探索。

比如，所有者修改了一项已经确认的设计。正在执行的任务该怎么调整？哪些可以继续，哪些应该停止？旧设计下通过的测试、已经完成的代码，要不要重新验证？

这些问题和我这轮开发遇到的情况很接近。

我不觉得一定要为此再发明一个更复杂的 Super-agent。先复用任务系统、Git、CI、知识与事件机制，再根据实际瓶颈补充必要的治理能力，可能更值得做。

**回到最初，我为什么还要引入 Linear？**

一开始，我只是想让 Claude Code 的开发过程透明一点。

引入 Linear 以后，为了让任务真正可管理，我开始明确任务边界、验收标准和依赖关系。接着发现，合理拆分依赖，可以让更多工作提前开始，减少不必要的等待。

但这轮开发也让我看到，时间不只花在编码和等待上。验证会重复执行，接口会不一致，任务需要多轮审查。项目计划本身也会变：新的技术约束出现了，之前确认的设计需要重看，一批正在推进的工作可能已经不值得继续投入。

这时，增加 Coding Worker 只能解决一部分问题。我更需要的是一套能随着项目变化，继续组织执行、维持质量和控制方向的协作机制。

Linear 是这次实践里选用的工具。这个角色也可以由其他任务系统，或者专门开发的轻量服务承担。

![](https://pic2.zhimg.com/v2-97e60baeca03d1df7f51ed9ab4e6574f_r.jpg)

最初，我希望有一张能看清进度的看板。后来，希望它能成为 Agent 获取任务的入口。现在，我更关心的是，能否建立一个独立于 Agent Session 的项目协作与控制层。

任务池回答“当前什么工作可以开始”。控制层还要回答“计划变了以后，什么应该继续，什么应该暂停或取消，什么需要重新规划”。

这些能力不用全塞进一个产品里。任务系统保存工作和依赖，Git 管理代码版本，知识库保存经过确认的设计与决策，CI 和审查机制验证交付，调度运行时则把计划转化为任务的启动、暂停、恢复和取消。

Linear 可以替换，调度器也可以替换。**值得留下来的，是任务、代码、设计和验收结果之间能够查证的关系。**

这些关系能长期保存，执行者才有机会在不同 Session 之间切换，而不丢掉工作的连续性。

过去，我们主要关注怎样让一个 Coding Agent 更强：换更好的模型，给更长的上下文，设计更复杂的 Harness。现在，Agent 已经能独立完成相当多的工作，我们还得考虑，怎样让这些分别完成的任务，在不断变化的需求和设计下，最终组成一个正确的软件项目。

就像角色记忆系统通过了测试，不代表 NPC 的行为就合理；时间推进没有出错，也不代表故事就有趣。

到最后，仍然需要有人，或者某种可靠的机制，判断这些局部成果是否真的构成了想要的产品。下一阶段值得优化的，除了 Agent 的认知能力，还有整个开发系统的组织方式。

这又引出了一个更基础的问题：如果暂时不把 Agent 当成数字工程师，而是把大模型看作一种可以按需调用的认知计算资源，软件开发应该怎样组织？

哪些工作需要模型思考，哪些可以交给确定性程序和成熟的工程工具？一个长期软件项目需要持续存在的，究竟是主 Agent，还是项目本身的状态与治理机制？

这些问题，我想留到下一篇继续讨论。
