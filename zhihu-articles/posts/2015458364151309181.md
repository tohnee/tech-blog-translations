> MoE 模型的训练带来了密集模型中所没有的系统级挑战。由于每个 token仅激活一部分专家，这种稀疏性使得模型总参数量的增长速度远超每个 token 的计算量，从而在内存、通信和计算之间产生了耦合约束。优化其中一个维度往往会将压力转移到另一个维度，这就要求跨整个系统栈进行Co-design。

```text
为了应对 MoE 训练的这些挑战，集成优化方案：

- 内存（细粒度重计算、卸载/Offloading 等）
- 通信（优化的调度器/Dispatchers、通信与计算重叠等）
- 计算（分组 GEMM、算子融合、CUDA 图等）
```

### 一、系统架构 (Architecture)

### 1.1 Parallel Folding（并行折叠）的架构演进

### 稠密-稀疏错配 (Dense-Sparse Mismatch) 的根源

传统 Dense 模型使用的同构 3D/4D 并行（TP/PP/CP/DP）在面对 MoE 时失效，核心在于**两种层类型的并行最优配置直接冲突**：

| 维度 | Attention (Dense) | MoE (Sparse) |
| --- | --- | --- |
| TP | 大 QKV 矩阵受益于高 TP | 小 per-expert 维度使高 TP 适得其反 |
| CP | 长序列受益于高 CP | 无序列依赖，CP 无关 |
| EP | 不适用（无专家） | 分布式专家必需 |

**参数-计算错配 (Parameter-Compute Mismatch)** 的量化：DeepSeek-V3 拥有 685B 总参数但仅 37B 激活/Token，**18× 差距**。

- 内存随 *E* 增长，但每 Token 计算仅随 *K* 增长
- 传统框架强制 *EP* ⊆ *DP*，导致 *EP* ≤ *DP* 的约束

### Parallel Folding 的解耦机制

```text
传统约束: World Size = TP × CP × PP × DP, EP ⊆ DP
Parallel Folding: Attention 层 (TP×CP×DP×PP) ⟂ MoE 层 (ETP×EP×EDP×PP)
```

**约束**：Pipeline Parallelism (PP) 必须在两种布局间保持一致，确保梯度正确流动。

![](https://pic4.zhimg.com/v2-456dfdf1352b4a6e6490b8be8bfe36f1_r.jpg)

**打破 *EP* ≤ *DP* 的数学实现**：考虑 Attention 配置 TP=4, CP=2, DP=8, PP=4（256 GPUs）：

- **传统***EP* ≤ 8
- **Parallel Folding**MoE 使用 ETP=1, EP=64, EDP=1，EP 可”折叠”跨越 TP×CP×DP 组，实现 **8× 更高专家并行度**

**主要收益**：

1. 降低最小 GPU 门槛：CP=8 + EP=8 传统需 64 GPUs，Folding 仅需 8 GPUs
2. 独立优化：Attention 高 TP，MoE ETP=1 保持完整专家宽度
3. NVLink 域内通信：CP 与 EP 的 all-to-all 均可留在节点内

### 2.2 负载均衡策略

![](https://pic2.zhimg.com/v2-160a4abc6b8574358ec7a1dcf7d3d969_r.jpg)

| 策略 | 类型 | 优化目标 | 机制 |
| --- | --- | --- | --- |
| Aux-loss | 可导惩罚项 | 软均衡，梯度驱动 | ，=专家负载比例，=路由概率 |
| Sinkhorn | 最优传输 | 硬均衡，双随机矩阵 | Row/Column 归一化迭代至收敛，分配基于最优传输 |
| Expert Bias | 无辅助损失 | 自适应反馈 | 根据历史 Token 计数动态调整 bias，无梯度 |

**Aux-loss**：可微，训练稳定，但为软约束。**Sinkhorn**：理论最优分配，但不可微，需 `no_grad` 路径。**Expert Bias**：无辅助损失开销，自适应但依赖历史统计。

### 2.3 极低精度量化(FP8/NVFP4)

### NVFP4 (E2M1) 双层微缩放

![](https://pic2.zhimg.com/v2-14ddf0de4f6d6cd2a45ac8602b3cec41_r.jpg)

### 随机哈达玛变换 (RHT)

FP4/E2M1 表示范围极窄，**离群点 (Outliers)** 会主导 amax 计算，导致大量值被量化至零。RHT 将梯度通过随机正交变换分散，使离群点能量分布到整个张量，降低单点对 scale 的支配。

**融合实现**：RHT 必须与 NVFP4 量化融合于同一 kernel，否则需额外 BF16 全局内存读写，带宽成本过高。

![](https://pica.zhimg.com/v2-58dc2a3e26a04e9c702be77f8eb7de60_r.jpg)

### 随机舍入 (Stochastic Rounding)

确定性舍入 (deterministic rounding) 引入**系统性偏差 (Bias)**：，梯度累积导致收敛偏移。随机舍入满足 ，在期望上无偏，抵消量化引入的偏差。实现使用 **cuRANDDx** 在 kernel 内生成随机数。

### 三、芯片设计与硬件 (Chip Design & Hardware)

### 3.1 算力碎片化与 Tensor Core 饥饿

### Wave Tail Effect

DeepSeek-V3 的 256 小专家产生 M 维度约 **128 tokens/expert** 的 GEMM，远低于 Tensor Core 峰值利用率所需的数千维度。多 stream 启动的独立 cuBLASLt GEMM 可**重叠 wave tail**：当一个 kernel 的 wave 尾部执行时，另一 kernel 的 wave 已开始，提升 SM 占用率。

### Grouped GEMM 的计算密度提升

- **CUTLASS Grouped GEMM**将多个 GEMM 融合为单 kernel，减少 launch 开销
- **cuBLASLt CUBLASLT_BATCH_MODE_GROUPED**shape 信息在 device，单 kernel 执行，支持 CUDA Graphs

**数据**：Dense Llama-3 405B 中 GEMM 占 ~70% 执行时间，DeepSeek-V3 MoE 中**低于 50%**，其余被 routing、permutation 等小操作消耗。

### 3.3 数据对齐与 Host-Bound 瓶颈

### TMA 对齐要求

FP8/FP4 GEMM 要求张量维度对齐：per-tensor/blockwise 为 **16**，MXFP8/NVFP4 为 **32**。Weight-gradient GEMM 的 dot-product 维度对应 token 维度 M，动态且常不满足对齐，需 **zero-padding**。NVFP4 grouped quantization 进一步要求 **128 tokens/expert** 对齐。

![](https://pic3.zhimg.com/v2-03a1ced7251453365d69110dc4aa44bc_r.jpg)

### Host-Bound 瓶颈

FP8 加速使 GEMM 执行时间缩短，但 **Kernel Launch Overhead** 不变。每 launch 数微秒的 CPU 成本在极速量化计算下无法被重叠，导致 **GPU 在 kernel 间隙空闲**。CUDA Graphs 通过单次 Graph Launch 替代大量 per-op launch，消除此瓶颈。

![](https://pica.zhimg.com/v2-379c910b41f08b5f5953442782a5d0ac_r.jpg)

### 四、软件设计与系统工程 (Software Design & System Engineering)

### 4.1 CUDA Graphs 与动态 Shape 的解决方案

### 三项关键技术

### (1) Device-Initiated Kernels（设备端发起内核）

**挑战**：Host 需 per-expert token counts 来配置 Grouped GEMM 和 dispatch launch，导致 device-to-host 同步。

**解决**：

- **Device-Initiated Grouped GEMM**从 device memory 读取 shape 信息，launch 配置与工作量解耦
- **Sync-Free HybridEP**预估上界预分配 buffer，消除所有同步

![](https://pic1.zhimg.com/v2-be8bfc2b1a2dcd065821084ab3bd5a3e_r.jpg)

### (2) ECHO (Elastic Cloning for Hot Experts)

**问题**：负载不均导致 worst-case buffer 远大于实际使用，显存碎片化。

**Bin-packing 启发式**：

1. 计算每个专家的 spillover（超过平均负载的 token 数）
2. 计算每个 rank 的 spare capacity（低于平均的可用容量）
3. Bin-packing 匹配 spillover 与 spare capacity，生成 hot expert map 和 routing map
4. 最小化 clone 数量同时达到足够负载均衡<br>

![](https://pic2.zhimg.com/v2-1aace93f0af81e223fd873fe7ccd5835_r.jpg)

**收益**：缩小 worst-case 与 actual 的差距，减小静态 buffer 需求；减少 straggler 等待。

![](https://pic4.zhimg.com/v2-3afef9ae4cfdfca0bbdce2d177be076f_r.jpg)

### (3) Paged Stashing（分页暂存机制）

**传统最坏情况**：每层独立分配 worst-case buffer →

**Paged Stashing**：

- **tmp buffer**单块 worst-case 大小，所有层共享用于计算
- **stashing buffer**按页（默认 64 tokens/page）组织，仅存实际 token 数
- **Free list**循环 buffer 实现页分配

**显存复杂度**：

**Stream 重叠**：Forward 时 stash 在 Pack stream 与 Layer N+1 计算重叠；Backward 时 pre-fetch 在 Unpack stream 隐藏 reload 延迟。

![](https://pic1.zhimg.com/v2-f510c45b74c6fc1868e6e5ac67d000c6_r.jpg)

### 4.2 异步重叠 (Asynchronous Overlapping)

### 1F1B Merged FWD-BWD 调度

**Stream 分离**：

- **Compute Stream**Forward/Backward 计算（attention, expert MLP）
- **Comm Stream**All-to-all 通信（token dispatch/combine）

### W/D Split (Weight-Gradient / Data-Gradient Split)

**依赖链**：B/dispatch 依赖 B/mlp 输出。若 F/mlp 过短，无法隐藏 B/dispatch。

**拆分**：

- **W/mlp**权重梯度计算（与 B/dispatch 无关）
- **D/mlp**数据梯度计算（馈入 B/dispatch）

W/mlp 可与 F/mlp 重叠，从而在 F/mlp 较短时仍能隐藏 B/dispatch。

**实测**：DeepSeek-V3 H100 上，EP 通信从 30-40% 降至 **<5%** 迭代时间，**93% overlap ratio**。

![](https://pic2.zhimg.com/v2-6f421a3f256c6bb6ce8345fb6ddd643b_r.jpg)

### 4.3 Dynamic Context Parallelism (Dynamic-CP)

### THD 格式与 Packed Sequences

```text
SBHD: [Sequence, Batch, Heads, Dim]
THD:  [Total_tokens, Heads, Dim]  ← 序列沿 token 维拼接
```

**Cumulative sequence length** 标记各序列起止位置，SDPA 确保不同序列的 Q/K 不互相 attend。

### Dynamic-CP 的轻量调度

调整 CP 仅改变 token 分片方式和 CP 通信组，无需参数重分布或 optimizer 迁移。

**实现**：

1. 初始化时预构建多个 CP 组，（2 的幂）
2. 运行时每 microbatch 选择有效 和对应预构建
3. `data_iterator_wrapper`reschedule + pack sequences，选 per-microbatch ，返回动态 `num_microbatches`
4. 广播 scheduling metadata（num_microbatches, max_seqlen, cu_seqlens）保证 pipeline 一致性

**收益**：高序列长度不平衡场景下 **35-60%** 端到端性能提升。

![](https://pic4.zhimg.com/v2-1fc7372a769715d69ddd0a1791ed17f3_r.jpg)

### 五、总结 (Summary)

**总结**：**软硬件协同设计 (Hardware-Software Co-design)**：从底层硅片物理限制（Tensor Core 粒度、NVLink/IB 带宽差异、TMA 对齐约束），到数学算法重排（Memory-Efficient Permutation 的交换律、RHT 的离群点分散、Stochastic Rounding 的无偏性），再到上层软件调度（Device-Initiated Kernels 消除同步、Paged Stashing 的虚拟内存思想、W/D Split 打破数据依赖、Dynamic-CP 的零开销通信组切换），三者形成闭环。

**数据**：DeepSeek-V3 在 GB200 NVL72 上 EP64 全在 NVLink 域内，无需通信重叠即可达 1048 TFLOPS/GPU；H100 跨节点则需启用 1F1B 重叠，否则通信占 40-60%。同一模型在不同硬件上需采用不同优化栈，针对拓扑、带宽、算力、显存四维约束做权衡。

### 六、扩展

### 6.1 跨架构可移植性

Megatron-Core 当前深度绑定 NVIDIA 栈（CUDA、Transformer Engine、NVLink）。 **问题**：AMD MI300、国产 NPU（如昇腾、海光 DCU）上，EP all-to-all 的带宽拓扑不同，DeepEP/HybridEP 的 TMA/IBGDA 原语如何抽象或替换？跨厂商的 MoE 训练框架是否可能走向统一抽象层（如类似 oneAPI 的异构编程模型）？

### 6.2 MoE 与 Mamba / LatentMoE 的融合

LatentMoE（Nemotron-3）：在 dispatch 前做 down-projection，压缩 all-to-all 通信与专家权重。 **延伸**：MoE + Mamba 的混合架构（如 DeepSeek-R1）中，状态空间模型与 MoE 的串行/并行放置、梯度流与通信组设计，尚未在 Megatron-Core 中系统化。长序列推理下，Mamba 的线性复杂度与 MoE 的稀疏激活如何协同？

### 6.3 推理与训练的解耦

训练侧优化（1F1B、EP overlap、Paged Stashing）针对 backward 与梯度同步。 **推理侧**：无梯度、无 optimizer state，瓶颈更多在 KV cache、批处理调度、专家冷启动。vLLM、SGLang 等推理框架的 MoE 支持与 Megatron-Core 训练栈的 checkpoint 兼容性、权重格式转换。

### 6.4 极低精度与量化路线

NVFP4 已覆盖训练，**推理侧** INT4/INT8 量化、稀疏化（如 MoE 专家 pruning 或结构化稀疏）在报告外。FP4 训练收敛的 scaling law、与 INT4 推理的精度衔接。

### 6.5 多模态与 Agent 场景

多模态 MoE（视觉 + 文本专家）的 token 分配、跨模态路由策略，与纯文本 MoE 不同。Agent 场景下的长轨迹、Tool-use 与 MoE 的 token 复用、动态 batch 调度，对 Dynamic-CP、Packed Sequences 有更高要求。

### 6.6 问题总结

| 方向 | 问题 |
| --- | --- |
| 硬件 | 非 NVIDIA 架构的 EP 通信优化、TMA 等价物 |
| 架构 | MoE+Mamba 混合、LatentMoE 的通用化 |
| 推理 | 训练/推理栈对齐、KV cache 与专家调度 |
| 精度 | FP4 训练与 INT4 推理的精度衔接 |
| 场景 | 多模态路由、Agent 长轨迹调度 |
