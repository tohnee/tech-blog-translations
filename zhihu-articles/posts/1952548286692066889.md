论文原文：[Autellix: An Efficient Serving Engine for LLM Agents as General Programs](https://arxiv.org/pdf/2502.13965)

![](https://picx.zhimg.com/v2-03466c6374cd369b40ef0fa94419509f_r.jpg)

最近 System for LLM Agents 这个领域的关注度也越来越高了，个人感觉这篇文章是所有 Agent Serving System 中最像 [Parrot](https://arxiv.org/pdf/2405.19888) 的了，两者的核心目的完全一样：不要以单 request 为 serving system 的优化目标，而要以一个 agent 应用的 e2e time。现有服务系统通常都是卷前者，导致在后者的场景下是 sub-optimal 的。

不过这两篇文章的侧重点不太一样。首先 Parrot 它想表达的是怎样将这种应用层级的信息暴露给服务端，重点在**抽象与表达能力层面**，至于有了这个抽象能做什么它就做的比较散，Prompt Sharing、基础的 Program-Level FCFS、DAG-aware Scheduling 当时都有搞，但是都不精。而 Autellix 这篇文章就是专精用应用层信息+**更好的调度**减少 Waiting Time，更像一个纯血的 Scheduling 工作。

## 收益在哪？

![](https://pic1.zhimg.com/v2-c2db0abb5e78302f118f928223966a56_r.jpg)

论文第2页就放出了描述收益来源的甘特图，好评！我们来看这个场景，假设四个Program，每个由不同个数的 LLM Call 组成，且每个 Call 的 Decode Step 也不同。然后现在计算它们的 Waiting Time，算法是这样的（以 FCFS 为例子）：A是 (7-4)=3，B是 (4-3)+(10-7)=4，C是(3-0)+(8-4)=7，D是(4-0)=4，总共等待18。同理计算发现 MLFQ 也是 18，PLAS 则为 12，是其中最优的。

有人可能会问：为什么用 Waiting Time 这个 Metrics 呀？明明看整体 e2e latency 的话，最好的岂不是 MLFQ（13 unit 结束所有四个任务）？这个视角也并非完全没道理，但是它更像 Offline Serving 关心的，即完成所有请求所需的总时间。而对于 Online Serving，由于不同 Program 的执行部分都一样（即不管你怎么调度，你都要做这部分事情），所以能优化的部分自然就是 Waiting Time / Queuing Time。而单个 Program 的总时长就是排队时间+执行时间，所以这实际上也就是在优化 Program 的平均时长。

## 动机与挑战

上面其实已经说了基本的动机了。下面展开来讲这篇文章具体观察到的几个地方。上面讲过

$\text{Program_Latency}=\text{Execution_Time} + \text{Waiting Time} + \text{Interceptions}$

其中第三个地方上面没涉及，指的是等待外部工具输入（比如 Human Input）这种，因为和服务系统无关这里就略去。所以重点谈怎样减少前两个部分。

- （Waiting Time优化1）Call-level Blocking. 请求级别的 HoL 在之前的很多研究里都有发现（比如我很久以前写的一篇 [FastServe](https://zhuanlan.zhihu.com/p/648759542)）。问题就是比较长的请求如果卡在头部，后面的请求就得一直排队等着，解决这个问题通常是通过带 preemptive 的调度（如 MLFQ 这种）把 blocking 的请求换下来。虽然这一点看似不需要知道 Agent 信息也能做，但是知道之后可以做的更好。
- （Waiting Time优化2）Program-level Blocking. 由于 Program 本身是由多个请求构成的，且诸如 ReAct 这种的应用往往请求个数不固定，导致每个 Program 也有长短之分，自然也有 HoL 问题。而如果没有 Agent 信息，这一点就是完全无感知的了，完全做不了。
- （Execution Time优化1）Data Locality. 在优化执行上文章里只提到了一点，就是 KV Cache 的 Data Locality。众所周知 Agent 是一个 Prompt 很长且复用率很高的场景，因此这一点也很重要。

这里讲的其实主要就是 Program-aware 调度和 Prompt Cache 两个问题，和 Parrot 关注的大点是一样的，不过讲得更有条理一点（从分别优化 Execution Time 和 Waiting Time 出发），确实是个 Writing 的好角度。

## 实现

![](https://pic3.zhimg.com/v2-8d3b792eabd25e6a710414317d5b9eca_r.jpg)

众所周知，LLM Serving System 里的 Scheduler 是有歧义的，“把 LLM Request 发射到哪个 Engine”和一个 Engine 内本身的 Batch Scheduler 都可以叫这个名字，[Preble](https://arxiv.org/abs/2407.00023) 里叫 Global / Local Scheduler，这里则是叫 Load-Balancer 和 Scheduler。对于架构，我们就按每个组件来简单讲一下：

- Process Table，进程表。这里和 Parrot 的抽象有点像，Process 对应 Program，Thread 对应 LLM Call。这个表应该是放在 Global 的，存了很多有用的信息用来指导 Load Balancer 和 Scheduler。
- Batch Scheduler。讲调度策略主要分为两方面：它的 Priority Function 设计和 Preemptive Scheduling。对于 Priority Function，作者将 Program 类型分类讨论为两种：单线程（据本人理解，应该是 LLM Call 串成链状的 Program，这里描述有点奇怪）和多线程（由 LLM Call 组成的动态 DAG）。

![](https://pic4.zhimg.com/v2-e94a7928fe44ffc8fc8ec6b82c9b3ded_r.jpg)

![](https://pica.zhimg.com/v2-a7b44e8fe6bd6540266005ff7e4e1c94_r.jpg)

- Load Balancer。首先对于一个 Call，如果它对应的 Program 已经被分到某个 Engine，那就直接分；否则，选择一个最少使用的 Engine 分过去。这里和 Parrot 其实是一样的。

总的来说，主要就是 Batch Scheduler 方面设计得很多，PLAS 和 ATLAS 本身也是比较 make sense 的。

## 实验

主要是和 vLLM、vLLM-opt（即 vLLM 开了 chunk-prefill，prefix-caching 和 multi-step scheduling）、MLFQ（约等于[FastServe](https://zhuanlan.zhihu.com/p/648759542)）比，测量了 Single-Engine 和 Multi-Engine。

主要可以关注一下他们测 LLM Program 用的是什么 Workload：分别是 ShareGPT（单纯的 Chat）, BFCL（带 Function Call 的 multi-turn LLM 对话，文章中把它作为一种 ReAct Agent，大体上讲是可以的）, LATS（在 HotpotQA 数据集上跑 MCTS），以及它们混起来。后续做 Agent Serving 工作也可以参考一下这些数据集，不过其实我个人感觉还可以加一些手造的合成数据集以及 Multi-Agent（例如 MetaGPT）那种的数据集。

## 一些碎碎念

从这篇文章里可以读出 Berkeley Sky 组很扎实的系统基础，尤其是对调度这一块的知识积淀，这使得整个文章的写作看上去很舒服，非常值得我这种野路子派学习...

以及"Serving System 和 Agent Frontend" 之间互不理解的 Gap 永远是这类工作的主旋律，也是机会所在。不过现阶段这类工作其实实际意义都比较有限，因为供应商的 Public API 也并非专门为 Agent App 服务，而是要面临世界上成千上万不知道是什么地方过来的请求，这种情况下已经很难说真正要优化的目标是什么了，反而单纯的 Prompt Completion 足够通用。等供应商把自家的 Serving System 和 Agent 坐 Co-locate + Co-design，可能才是这类工作的未来场景吧，不过我觉得随着像 Claude Code 这样的产品不断涌现，未来已经不远了。
