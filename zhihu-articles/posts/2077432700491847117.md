### 开篇导读

**背景**

投机解码是现在大模型推理加速的主流手段：让一个轻量草稿模型先猜几个 token，再让完整目标模型一次前向并行验证，接受对的前缀，数学上不改变模型输出。它长期有两个独立难题：草稿侧，逐个猜质量高但慢，并行猜一次出一块则越靠后越不准；验证侧，高并发下把整块草稿都验证一遍，大量算力花在注定被拒的 token 上。2026 年 7 月，北大与 DeepSeek-AI 的论文 DSpark 同时处理这两个问题，并已在 DeepSeek-V4 生产系统和 SGLang 中落地。

**推荐理由**

- 一个干净的「混合架构」样本：重的草稿骨架保持并行，只加一个极轻量串行头补 token 间依赖，只增加不到 1.5% 的延迟，离线接受长度同时超过自回归路线的 EAGLE3 和并行路线的 DFlash。
- 把「一次该验证几个 token」从固定超参变成随数据难度和引擎负载在线变化的优化问题，还守住了投机解码的无损性约束。
- 论文发布当天 SGLang 就放出配套工程博客，从算法落地到 CUDA Graph、变长验证都给了细节和复现命令。

**原文来源**

- 论文：DSpark: Confidence-Scheduled Speculative Decoding with Semi-Autoregressive Generation，Peking University × DeepSeek-AI，arXiv:2607.05147v1，2026-07-06。
- 工程实现：DSpark in SGLang，SGLang Team，2026-07-06。

### TL;DR

- 投机解码的提速拆成三个杠杆：草稿更快、草稿更准、验证更省。DSpark 同时在后两个上做文章。
- 半自回归草稿：并行骨架一次前向出整块候选，再加一个极轻的串行头（默认低秩 Markov 转移头）补回 token 间依赖，整轮延迟只增加 0.2%~1.3%；离线每轮接受长度比 EAGLE3 高约 27%~31%，比 DFlash 高约 16%~18%。
- 置信度调度：一个置信度头估计每个草稿位置的存活概率，配合预先 profile 的引擎成本表，逐请求决定「验证到第几个 token」，负载轻就多验证、负载重就主动收缩。
- 在 DeepSeek-V4 真实流量上，相对生产基线 MTP-1，相同总吞吐档位下单用户生成速度 Flash 提升 60%~85%、Pro 提升 57%~78%。
- SGLang 主线已支持 DSpark，工程难点在引擎侧：要让「每请求变长验证」在完整 CUDA Graph 下真的少算，补齐了再 mask 掉等于白剪。

### 一、背景：投机解码的三个杠杆和两条路线

大模型自回归生成，每出一个 token 做一次完整前向，延迟和输出长度成正比，单请求下 GPU 大量算力闲置。投机解码利用这一点：草稿模型先给出 γ 个候选，目标模型用一次前向全部验证，按拒绝采样接受最长的一致前缀，再白送一个 bonus token。验证并行、接受规则严格等价于目标模型自身分布，所以不损失输出质量。

把每 token 平均延迟写成 L = (草稿时间 + 验证时间) / 每轮接受数 τ，提速只有三个来源：草稿更快、τ 更高（草稿更准）、验证更省。

草稿模型怎么设计，决定了「草稿更快」和「草稿更准」怎么交换。现有做法分两条路线：

| 路线 | 代表 | 生成方式 | 优势 | 代价 |
| --- | --- | --- | --- | --- |
| 自回归草稿 | EAGLE 系列 | 逐个顺序生成，每个位置能看到之前采样的 token | 建模能力强 | 草稿耗时随块长 γ 线性增长，只能用很浅的网络和较短的块 |
| 并行草稿 | Medusa、DFlash | 一次前向同时吐出全部 γ 个候选 | 耗时几乎和块长无关，可用更深网络、更长块 | 各位置彼此独立，看不到块内其他位置最终采到了哪个 token |

并行草稿的「独立」会带来多模态碰撞：比如「of course」和「no problem」都合理，并行模型第一个位置选 of、第二个位置按 problem 填，拼出「of problem」。结果就是接受率沿块位置快速下滑，论文叫后缀衰减。

验证侧是另一个问题：并行草稿容易吐出很长的块，但全部丢给目标模型验证，高并发下不划算。代码这类结构化文本好猜，开放聊天难猜，后者尾部大概率被拒；负载轻时多验证几个几乎不花钱，负载重时每多验证一个都在挤占 batch 容量。

DSpark 用两个组件分别回应：半自回归生成解决「草稿准」，置信度调度解决「验证省」。

### 二、半自回归：给并行骨架加一个很轻的串行头

DSpark 把一次草稿拆成两级：重的计算全部并行，只把补依赖所必需的一点点计算做成串行。

![](https://picx.zhimg.com/v2-234f7aaeb8169e28b1f1b2674366137f_r.jpg)

**图1：DSpark 的结构与一轮解码循环。**<br>**怎么看：**<br>**左下角①目标模型读到 ABC 后生成锚点 D；**<br>**右侧②是草稿器，并行块一次前向给出四个位置的 Logits，上面的串行块从左到右逐个修正，产出候选 EFGH 和各自的置信度 c1~c4；**<br>**硬件感知前缀调度器保留 EFG、丢掉低置信的 H；**<br>**左上角③目标模型并行验证 EFG，接受 E、F，拒绝 G 并自己生成纠正后的 G′，进入下一轮。**

**图1说明什么：** 算力重的并行块只跑一次，保证草稿耗时不随块长膨胀；串行块只负责在并行结果之上叠加「看到前一个 token」的局部修正，因此可以做得非常小。

具体分两阶段。并行阶段用改造过的 DFlash 当骨架，一次前向产出每个位置的基础 logits；串行阶段从左到右采样，给每个位置叠加一个依赖块内已采样前缀的「转移偏置」。论文给了两种串行头：

- **Markov 头（默认）**：假设当前位置只依赖紧邻的上一个 token，本质是一个词表×词表的一阶转移矩阵。直接存太大，用低秩分解（秩 256）压缩，一半当 embedding 查表、一半当投影，单步计算和存储都很小。一旦第一个位置采到「of」，Markov 头就在第二个位置抬高「course」、压低「problem」，碰撞被消解。
- **RNN 头**：用门控循环状态记住更久的历史。实验显示相对 Markov 头只有边际收益，主要出现在很长的块上，实现更复杂，默认不用。

这个设计的性价比是论文里最漂亮的一组结果。目标模型的验证前向才是一轮里的大头，串行头本身额外耗时极低：块长从 4 拉到 16，整轮延迟只多 0.2%~1.3%，换来的接受长度提升随块长变大，γ=15 时在数学、代码、聊天上分别比 DFlash 高 30%、26%、22%。论文还发现：2 层的 DSpark，接受长度就已经超过 5 层的 DFlash，补一点序列依赖比单纯把并行网络堆深更管用。

为什么并行和自回归能这样互补，论文用一张位置级接受率曲线图讲得很清楚。

![](https://pica.zhimg.com/v2-fca0b8f6c31588b3cecb623854a99538_r.jpg)

**图2：按草稿位置统计的条件接受率。**<br>**目标模型 Qwen3-4B，从左到右分别是数学、代码、聊天三个域；**<br>**蓝三角是并行的 DFlash，黄方块是自回归的 EAGLE3，绿圆圈是 DSpark；**<br>**纵轴是「前面位置都被接受的前提下，当前位置也被接受」的条件概率。**

**图2说明什么：** 三条线的形状对应三种架构的性格。第一个位置上，DFlash 因为网络更深而明显占优（数学 0.88 对 EAGLE3 的 0.81，聊天 0.72 对 0.53），而第一个位置一旦被拒整块作废，杠杆最大。越往后，EAGLE3 凭借顺序依赖反而走平甚至走高（聊天从 0.53 升到 0.74），DFlash 则持续下滑（代码从 0.87 掉到 0.78）。DSpark 的绿线同时拿到了并行的高起点（数学 0.93）和自回归的平稳后段，全程压在另外两条线上。

### 三、置信度调度：把「验证几个」变成在线优化问题

草稿能稳定产出长块之后，第二个问题来了：是不是每个请求都该把整块验证完？论文的答案是否定的，而且必须同时看数据难度和系统负载。整套机制分三层。

### 置信度头（Confidence Head）

- 给每个草稿位置输出一个 0~1 的置信分，表示「前面位置都被接受的前提下，这个 token 也能活下来」的条件概率
- 架构很简单：线性层加 sigmoid，输入是当前隐状态和上一个采样 token
- 训练标签不需要人工标注，可以直接解析计算：草稿分布和目标分布越接近，接受概率越高

### STS 校准（Sequential Temperature Scaling）

- 神经网络的置信度天然偏乐观（论文测到校准误差 ECE 在 3%~8%），而调度器需要的是绝对概率值来算期望接受长度，光排序不够
- 做法是从左到右逐位置做一维搜索找最优温度标量，把前缀连乘概率校准到和真实接受率吻合
- 温度缩放保序，不会打乱原来的高低排名；校准后 ECE 降到约 1%

### 硬件感知前缀调度器（Hardware-Aware Prefix Scheduler）

**核心思想：** 把验证长度选择建模为全局吞吐量最大化问题。

给定 R 个活跃请求，每个请求有置信度序列 $c_{r,1}, \dots, c_{r,\gamma}$：

- **前缀存活概率：**$a_{r,j} = \prod_{i \le j} c_{r,i}$（单调非增）
- **总验证 batch size：**$B = \sum_r (1 + \ell_r)$
- **期望接受 token 数：**$\tau = \sum_r \left(1 + \sum_{j=1}^{\ell_r} a_{r,j}\right)$
- **引擎吞吐量曲线 SPS(B)（steps/s）：** 初始化时 profile 一次，存为轻量查找表。SPS(B) 即推理引擎在 batch size 为 B 时每秒能完成多少个解码 step，B 越大单 step 耗时越长、SPS 越低（但总 token 吞吐可能先升后降）。
- **目标：** 最大化 $\Theta = \tau \cdot SPS(B)$

![](https://pic3.zhimg.com/v2-711cc6193921d24bcdf3ef4868adbdfa_r.jpg)

**图：SPS(B) 曲线示意。** 左图：单步吞吐 SPS(B) 随验证 batch 增大而递减——模型权重读取是固定开销，但每个请求的 KV cache 不共享，B 越大要搬的 KV 越多、单步越慢。右图：总吞吐 B × SPS(B) 先升后趋于平台，超过某个点后多加 token 换不回等比例的吞吐增益。调度器要找的就是这条曲线上「期望接受 token 数 × SPS」最大的位置。曲线为定性模型（参考 Llama 3.1-8B / A100 benchmark 拟合），实际值由引擎初始化时 profile 得到。

**贪心算法：**

1. 全局收集所有 $(r, j)$ 候选，按 $a_{r,j}$ 降序排列
2. 从零开始逐步接纳 token，每次更新 B 和 $\tau$，查表算 $\Theta$
3. 吞吐量首次下降时早停（保证因果性——不依赖未来 token 信息）
4. 返回达到 $\Theta_{best}$ 时各请求的验证长度

**为什么贪心是最优的？**$a_{r,j}$ 单调非增意味着扩展请求 r 从 j-1 到 j 的边际收益恰好是 $a_{r,j}$，全局按存活概率排序自然尊重块内前缀依赖。

**无损保证：** 早停机制确保截断决策仅依赖已处理的前缀，不泄露未来 token 信息，严格保持目标模型分布。

### 真实系统里的两处妥协

- 硬件成本曲线呈阶梯状、并不平滑，CUDA Graph 又要求「当前步还没算完就知道下一步 batch 大小」，于是调度改成异步：用两步之前的置信分定每步截断长度，当前步内部仍按最新置信分排序；这个时间错位反而形成一道因果屏障，让全局搜索不破坏无损性
- 不同请求验证长度不同，底层内核得支持一个 batch 里的变长查询，做法是把所有 token 拍平成独立元素计算，序列归属通过标记张量传给稀疏注意力；在 DeepSeek-V4 上只需要改 index-attention 和 compress 两个内核

### 四、SGLang 是怎么把它真正跑起来的

论文同一天，SGLang 团队发布了配套博客，讲开源引擎如何把这套调度变成墙上时间。SGLang 目前在稠密模型（如 Qwen3）和稀疏 MoE（如 DeepSeek-V4）上都支持 DSpark。

### 三种验证模式

首先是三种验证模式，这是理解实现的钥匙：

- **static**：每步都验证完整草稿块，相当于基线。
- **compact**：只验证调度器给每个请求挑出的窗口，这是生产路径。
- **cap-accept**：整块都验证，但只提交窗口内的部分，输出和 compact 完全一致，额外作用是观测「假如不裁剪，这一步本来能多接受几个」。因为一旦裁剪，你就永远看不到被剪掉的尾部命运，也就无从判断这一刀剪得好不好；cap-accept 专门用来还原这个「裁剪天花板」。

### ragged CUDA Graph：让变长验证真的少算

最难的工程点，是怎么让「每请求变长」和 CUDA Graph 共存。CUDA Graph 要求固定形状，可一个 batch 里这个请求验证 2 个 token、那个验证 6 个，根本没有统一长度；如果图省事把所有人都补齐到整块宽度，等于把调度器省下来的 token 又算了一遍，裁剪白做。

SGLang 的解法是 ragged（紧凑参差）布局：把各请求真正要验证的 token 向前紧凑打包，按总 token 数向上取整到预先捕获的档位（4/8/12/16/18），预算一收缩就重放一个更小的图，真的少算注意力和 MLP 行。紧凑缓冲区用 cu_seqlens 式的变长输入，能直接复用后端已有的变长注意力内核，DeepSeek-V4 走它自带的 flash_mla 路径即可，没有为此新写注意力内核。

![](https://pic2.zhimg.com/v2-dca61b347418ec607ca4b8b856015b35_r.jpg)

**图3：固定形状图和紧凑参差（ragged）图的对比。**<br>**怎么看：**<br>**左图固定形状按「请求数×块宽」算，3 个请求块宽 6，一共算 18 格，其中 8 格是补齐、算完即弃；**<br>**右图把各请求真正要验证的 token 向前紧凑打包，按总 token 数向上取整到预先捕获的档位（4/8/12/16/18，图中落在 12），只算 12 格；**<br>**下方条形对比同样的接受 token 数，ragged 少算 6 格、少 33% 的注意力和 MLP 行。**

**图3说明什么：** SGLang 给图定的键是打包后的总 token 数。预算一收缩，打包总数掉到更小档位，就真的重放一个更小的图，少算注意力和 MLP 行，省去跑等宽图再 mask 的浪费。紧凑缓冲区用的是 cu_seqlens 式的变长输入，因此能直接复用后端已有的变长注意力内核，DeepSeek-V4 走它自带的 flash_mla 稀疏 MLA 路径即可，没有为此新写注意力内核。

### 调度延迟与团队克制

调度延迟方面，DSpark 直接挂进 SGLang 已有的重叠调度器：运行时本来就把「下一步调度」和「当前步前向」放在不同流上并行，DSpark 作为普通任务接入、读两步之前的置信分走同一通道，解码循环没有逐步气泡，比关掉重叠时快约 1.5 倍；配套的融合 Triton 内核，把目标验证之外的杂项耗时在一个 profile 里压下 1.7 毫秒（验证本身 7.3 毫秒）。

### 五、效果：数字和它们的正确口径

### 离线效果：草稿质量全面领先

离线实验为了公平，把 EAGLE3、DFlash、DSpark 放在同一个训练框架 DeepSpec、同一批数据上重训，目标模型覆盖 Qwen3 的 4B/8B/14B 和 Gemma4-12B，统一用 5 层（EAGLE3 按其特性用 1 层）、块长 7，指标是每轮接受长度 τ（含目标模型白送的 bonus token），并且离线时关闭调度器、强制固定块长，以单独考察草稿质量。

结果是 DSpark 在所有目标模型、所有域上都赢：Qwen3 三个尺寸上，宏平均接受长度比 EAGLE3 分别高 30.9%、26.7%、30.0%，比 DFlash 高 16.3%、18.4%、18.3%，换到 Gemma4-12B 上优势依旧。同时能看到明显的领域差异：结构化任务接受长度天然更高（Qwen3-4B 上数学 5.57、代码 5.12），开放聊天只有 3.49，这正是需要按请求动态裁剪的直接原因。置信度头的诊断实验也印证了这点：把置信阈值调高、剪掉注定被拒的尾部，聊天的接受率从 45.7% 升到 95.7%，数学、代码分别从 76.9%、67.6% 升到 92.5%、92.0%。

![](https://pic3.zhimg.com/v2-92a07524ea05d95e64f2440ca3d96be4_r.jpg)

**图：离线草稿质量对比。** 三种草稿模型在 Math / Code / Chat 三个域的每轮平均接受长度，DSpark 在所有域全面领先。Chat 域相对提升最大（比 EAGLE3 高 45%、比 DFlash 高 18%），因为半自回归结构缓解了纯并行的后缀衰减；Math 域绝对值最高，因为结构化输出本身更好猜。

### 在线效果：DeepSeek-V4 真实流量

在线部分跑在 DeepSeek-V4 的真实用户流量上，对照是此前的生产基线 MTP-1。这里有个背景：为什么生产基线是只猜 1 个 token 的 MTP-1，而不是更长的 MTP-3/5？因为静态的多 token 草稿在高并发下验证开销过大，反而会压低总吞吐，所以线上一直保守地用 MTP-1。DSpark 要证明的，正是它能安全地把更长草稿块的潜力释放出来。

![](https://pic2.zhimg.com/v2-d755d95bd12606137679fe191b59dd89_r.jpg)

**图5：真实流量下总吞吐对单用户速度的权衡。**<br>**纵轴是每 GPU token/s，横轴是 token/s/人；**<br>**左 Flash 右 Pro，蓝是 MTP-1、绿是 DSpark；**<br>**散点是原始遥测、实线是拟合的前沿，越靠右上角越好。**

**图5说明什么：** 绿色前沿整体向右上方外扩。在可比的实际吞吐档位，DSpark 的单用户速度 Flash 快 60%~85%、Pro 快 57%~78%；在中等交互档位（Flash 保证每人 80 token/s、Pro 保证 35 token/s），总吞吐分别高 51%、52%。图上还有两个很醒目的 661%、406%，对应 Flash 每人 120、Pro 每人 50 的严格档位。

### 661% 的正确口径

这两个大数字的口径必须讲清楚，论文作者也专门提示了：在这种严格 SLA 下，MTP-1 已经逼近运行边界、只能维持很小的并发，分母极小，所以比值看起来夸张。它要表达的是「可行域被外推」：DSpark 把基线无法稳定支撑的高交互档位变成了可以正常服务的区间，不能读成常态提速六倍。真正能当日常加速比引用的，是前面那组 60%~85%。

### 负载自适应机制

![](https://pica.zhimg.com/v2-dc7f74004eeb148912b608793dc623d4_r.jpg)

**均验证预算随并发的变化；**<br>**蓝线 MTP-1 固定为 2 个 token，绿带是 DSpark。**

**图6说明什么：** 这张图解释了收益从哪来。并发不高时（Flash 少于 200、Pro 少于 150），调度器用足空闲算力，把验证预算从 MTP-1 的固定 2 个扩到平均 4~6 个，每步多接受 token；随着并发升高、目标模型容量趋紧，预算平滑地回落到 3.5 个左右，主动把低置信尾部剪掉，避免抢占 batch。轻载多算、重载让资源，这正是置信度调度相对固定长度的核心优势。

### 局限与后续方向

论文也坦承局限：即便调度能最小化验证浪费，草稿侧用并行骨架生成整块候选的固定开销还在，遇到本身就很难猜、接受率很低的复杂请求，这笔草稿成本收不回来，后续方向是让草稿模型具备难度感知、对这类请求提前退出。
