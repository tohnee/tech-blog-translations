今天，Sakana 实验室[发布了一个模型 Fugu](https://sakana.ai/fugu-release/)，在很多个 Benchmark 上都超越或接近了 Fable/Mythos：

![](https://pic2.zhimg.com/v2-9057eed798992a55e80b3a441585b37b_r.jpg)

但 Fugu 并不是一个独立模型，它是一个调度器，根据问题的特征、复杂度把问题中转给其他大模型去解决。可以理解为一个模型外的 MoE，每个模型都是一个 Expert，Fugu 则是把任务分发给各个 Expert 的路由。这样看起来，上面的成绩就不稀奇了，把 Mythos、GPT、Gemini 都绑在一起，成绩比一个单独的模型更好，也是意料之内的事。

![](https://picx.zhimg.com/v2-be10c8a09a48cacabf27fde771110931_r.jpg)

这样的 Orchestration Model，将会成为一种AI模型的主流应用模式。Factory 前段时间推出的 Factory Router 就是另一个例子：

[模型API智能中转是很有价值的](https://zhuanlan.zhihu.com/p/2045610375702373480)

甚至我觉得，现在主流大模型（GPT/Claude）的API接口后面，可能就藏着一个智能调度器。它根据用户请求的难度把问题分配给不同大小，不同成本的模型去处理。我们看到的模型名字：Opus 4.8,、GPT 5.5，可能只是一个**产品名**，并不代表一个独立的 LLM 模型。当然，这只是个人猜测。

智能调度的好处在于可以物尽其用，对于简单的任务，用高成本的大模型处理就是在浪费算力，且效率低。而且，过于依赖一个模型，就形成了单点故障（Single Point of Failure），比如，最近 Fable 模型突然对所有美国境外用户停止服务，如果一个应用依赖于 Fable，就会出现服务中断。调度器能自动切换到 Fallback 的模型，让服务持续运行。

在我的理解中，Orchestration 并不仅仅包含路由中转的功能，它有三方面的作用：

1. **任务分解（task decomposition）**
2. **路由选择（model routing）**
3. **集成（model ensembling）**

任务分解解锁了模型处理更复杂任务的能力。很多模型都对这个能力做了专门的单项训练。比如Kimi K2.5的论文中，就用了很大的篇幅讲 Agent Swarm 的训练。（参见：[近期三个模型的RL训练总结](https://zhuanlan.zhihu.com/p/2022475677522207756) ）

把任务分解为小块以后，调度器可以分析每一个子任务的复杂度，寻找匹配这个难度的模型，把子任务路由给它。这种任务分配也需要有一个 Fallback 机制，在小模型无法胜任的时候，能回撤到大模型来“救场”（[Advisor模式：遇到难题就求助高级模型](https://www.zhihu.com/pin/2026015266417460858)）。

一个任务除了难度/复杂性这个维度之外，还有另一个独立不相关的维度：确定性。如果不同模型，或者同一个模型的多次推理，会对这个任务给出不同的解答，那这个任务就是具有高不确定性的。在这种情况下，做多个 model 的 ensemble 就是常见的处理方式。视任务的类别，可以采用多模型投票、取数值平均等方式来获得更精确的结果。

以上三个方面，对于 Orchestration 模型的智能要求也是不同的：

- 任务分解需要高智能模型。这一点用 Coding Agent 的都有体会，开发的 plan 阶段必须用高智能模型来做，但是具体的编码任务，很多时候用小模型就足够了。
- 判定一个任务的难度和确定性，更像是一种分类任务，也许并不需要调度器有非常高的智能。一个 Orchestration Model 输入一个 task prompt 可以输出这样的结果：`(complexity, certainty)`

所以，调度器也不一定是一个模型：任务分解仍然由顶尖模型完成，而路由判定、是否需要ensemble，则由经过专门训练的小模型来处理。
