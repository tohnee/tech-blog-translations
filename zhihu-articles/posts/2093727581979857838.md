## 一、Workflows vs Agents：控制流归谁，是一切设计的起点

课程开篇先立起一根轴： **控制流（control flow）归谁** 。

- **单一模型调用** ：流程就是一次前向，没有控制流可言；
- **工作流（Workflow）/ 复合 AI 系统** ：控制流由 **开发者的代码** 预先写死，LLM 只是流水线上的一个工位；
- **Agent** ：控制流由 **LLM 自己** 在运行时决定——调什么工具、走哪条路、什么时候停，都由模型说了算。

这根轴的两端是 **可预测性（predictability）与自主性（agency）** 的交换：越靠工作流，越可预测、可复现、好调试；越靠 agent，越灵活、越能应对开放任务，但成本更高、正确性更难保证。

课堂幻灯片上有一句话值得抄下来贴在工位上：

> Real systems often combine workflows and agents. 
>  真实系统往往是把工作流和 agent 组合起来用的。 
> 

确定性部分交给工作流，开放性部分交给 agent——这不是妥协，是工程。

## 二、五种工作流模式：搭建 compound AI 系统的积木

这一节的骨架来自 Anthropic 的工程博客 **《Building Effective Agents》** 。五种模式，每种都有清晰的适用条件：

![](https://pic1.zhimg.com/v2-647cb52ec3c9b2c50aa508ea45174862_r.jpg)

图：五种工作流模式总览

**1. 提示链（Prompt Chaining）** ：把任务拆成固定的串行步骤，一步一个 LLM 调用，中间可以加 **门控（Gate）** 做 Pass/Fail 检查。适合能干净拆解的流程，比如「先写文案 → 再翻译」，用延迟换准确率。

**2. 路由（Routing）** ：先分类，再分发。不同类型的输入走专门优化的分支，实现 **关注点分离** ——退款请求、技术支持、一般咨询各有各的流程，比一个巨型提示词什么都管要靠谱。

**3. 并行化（Parallelization）** ：多个 LLM 调用同时跑。两种形态—— **切分（Sectioning）** 是把独立子任务拆开并行提速； **投票（Voting）** 是同一任务跑多次取多数，用钱换正确率。

**4. 编排者-执行者（Orchestrator-Workers）** ：中心 LLM **动态** 拆解任务、分派给 worker、再汇总。注意它和并行化的区别：子任务不是预先定义的，而是按输入现场决定的。

**5. 评估者-优化者（Evaluator-Optimizer）** ：一个 LLM 生成、另一个当评委给反馈，循环打磨。它的适用条件最有意思—— **反馈必须能被清晰表达，且 LLM 确实有能力给出这种反馈** 。就像找编辑改稿：编辑得说得出哪里不好，作者才能改。

### 组合演练：STORM 与 Archon

模式不是菜单上的孤立项，是积木。幻灯片给了两个真实案例。

**STORM** （Stanford 出品， [http://github.com/stanford-oval/storm](http://github.com/stanford-oval/storm) ）能从零开始、靠网络检索生成维基百科风格的长文。它的流水线是：调研主题 → 识别典型作者视角 → 模拟多视角作者向文献 **循环提问** → 拆分查询并行检索 → 筛选综合 → 生成大纲与草稿 → 迭代润色 → 整理参考文献。对照一看：整体是 **提示链** 骨架，多视角提问循环带着 **评估者-优化者** 的味道，拆分查询是 **并行化** 。论文（arXiv:2402.14207）里 STORM 的 ROUGE-1 达到 **45.82** ，优于所有消融基线。

**Archon** （arXiv:2409.15254）更进一步：把「模式组件」做成可插拔模块——生成器、评论家、排序器、融合器、验证器、单测生成器、评估器——然后用 **贝叶斯优化** 在组合空间里自动搜索架构。在数学推理任务上搜出来的架构是：4 个生成器并行 → 评论家（Claude 3.5 Sonnet）挑毛病 → 排序器 → 4 个融合器 → 验证器（GPT-4o）把关。性能从起点的 **52.5 一路涨到 76** ，超过 AFlow、ADAS、MoA，逼近 O1。

![](https://pic3.zhimg.com/v2-1ec4f67a91f218d909f8f0230101e9d4_r.jpg)

图：Archon 在数学任务上搜索出的架构：4 个生成器 → 评论家 → 排序器 → 融合器 → 验证器

组合这件事本身，也能被自动化——这是 Archon 最有启发性的地方。

## 三、推理与行动：ReAct 之后的进化树

ReAct 的「思考 → 行动 → 观察」循环，第一篇文章已经精读过了。幻灯片真正有意思的，是它后面那一串进化分支。

**Reflexion（2023）** ：失败之后别急着重试，先用自然语言对自己做一次 **反思** ，把教训存进记忆，下次带上再出发。它由三个角色组成—— **Actor** 执行任务， **Evaluator** 评估轨迹， **Self-Reflection** 生成语言化反思写入记忆。效果：ReAct 在 HotpotQA 上约 0.3，叠加 Reflexion 后到 **0.54** 。

但课程紧接着泼了盆冷水：《LLMs Cannot Self-Correct Reasoning Yet》（arXiv:2310.01798）显示， **没有外部信号的纯自我纠错可能有害** ——GPT-4-Turbo 在 GSM8K 上自我纠错几轮后，从 91.5 反而往下掉。Reflexion 之所以有效，是因为它依赖 **外部环境反馈** ，不是模型凭空自省。

**CRITIC（2024）把这个教训总结成一句口诀：Make an agentic verifier——做一个会用工具的验证者。流程是输出 → 工具验证 → 批评 → 修正，验证手段是 Wikipedia 检索、计算器、代码解释器这些外部工具** 。AmbigNQ 上 F1 从 ReAct 的约 64.5 提到约 **75** ；而一旦去掉工具，跌回约 67。

**CodeAct（2024）** 解决了动作形式的问题：与其一次发一个 JSON 工具调用，不如 **直接写代码** 。查六个国家的手机价格，JSON 方式要六轮往返；Python 一个 for 循环搞定，中间结果存变量， `min()` 直接取最低价。在 8 个模型上，代码动作一致地取得 **更高成功率、更少轮数** （arXiv:2402.01030）。今天主流 agent 框架里的「代码解释器动作」，源头就在这里。

![](https://pic1.zhimg.com/v2-2ef87f9ad4e1a3447fcc44f35b0b9f0a_r.jpg)

图：代码动作：一个 for 循环遍历所有国家，min() 直接取最低价

**先规划再执行** 则是另一族思路，代表是 **ReWOO** 和 **LLMCompiler** ：

- **ReWOO** （Reasoning WithOut Observation）：Planner **一次性** 产出完整计划，中间结果用 `#E1` … `#E4` 占位符引用，Worker 按计划执行，Solver 最后汇总。名字的含义是「规划时看不到观测」——规划与执行解耦后，每次调用不必重放全部历史， **token 消耗远低于 ReAct，准确率反而更高** 。
- **LLMCompiler** （类比编译器）：Planner 产出任务 **DAG** ，Task Fetching Unit 在依赖满足后立刻取任务，Executor **并行** 执行。比 ReWOO 多了两样东西：并行执行、动态重规划。论文数字很齐整：HotpotQA 62.00% 准确率 + **1.80×** 加速；Game of 24 对比 ToT 拿到 **2.89×** 加速（arXiv:2312.04511）。

![](https://pic2.zhimg.com/v2-ef5ed9c0b4097248aedb9b05b36ce011_r.jpg)

图：LLMCompiler：Planner 产出任务 DAG，Executor 并行执行

课程对这一节的回望很精到：ReAct 的推理内化进了今天的 **推理模型** ，Reflexion 的反思也是，CodeAct 成了主流动作形式，ReWOO/LLMCompiler 演化成了今天 agent 系统里的 **并行工具调用** 。2023 年的论文，2026 年的基础设施。

## 四、上下文管理：agent 能力上限的隐形约束

第四部分换了个视角看 agent： **LLM Call 是不变的内核，外面套着一个上下文管理器（Context Manager）** ，决定每一次调用到底把什么放进窗口。agent 的「智能」，很大程度由这个管理器决定。

为什么要管？看经典的大海捞针（Needle In A HayStack）热力图：Claude-2.1 号称 200K 上下文，但文档越长、关键信息埋得越深，检索准确率越低。 **窗口大 ≠ 全都有效** 。

课程给出两条原则：

- **让上下文聚焦（Focus the Context）** ：只放当前任务真正需要的信息，避免稀释注意力；
- **保持连续性（Preserve Continuity）** ：上下文组织尽量稳定，保护 **KV Cache** 命中——前缀不变，缓存就有效，省钱又提速。

### 上下文管理五件套

**1. 持久事件日志（Persistent Event Log）** ——OpenHands（arXiv:2407.16741）的做法：用户界面、agent 与运行时之间的一切交互都以 Action–Observation 事件记录在 **不可变、只追加** 的事件流里，LLM 的输入 **每次从日志重建** ，而不是保存状态。好处是历史原样保留，还能为外部观察者挂 hooks、做回放审计。

**2. 记忆卸载（Memory Offloading）** ——MemGPT（arXiv:2310.08560）用操作系统的思路：内存压力大就写外部存储（ `working_context.append("Birthday is February 7")` ），要用时再检索回来。一句话要旨： **把东西存进记忆或文件，才能腾出上下文去裁剪** ——卸载是裁剪的前提。

**3. 压缩（Compaction）** ——历史变长了，用 LLM 把先前的推理、动作、观测 **总结成摘要** ，保留关键、丢掉细节。压缩本身也可以做成 agentic 的。

**4. 观测遮蔽（Observation Masking）** ——这个模式的依据是一组惊人的数据（arXiv:2508.21433）：原始 agent 的上下文 token 里， **工具输出的观测占 83.9%** ，推理只占 9.6%，动作 6.5%。上下文的大头是又长又旧的工具输出。做法简单粗暴：把旧观测 **直接截断** ，不必费 LLM 调用去摘要。结果：在 Gemini 2.5 Flash Thinking 上遮蔽最省钱，但 Qwen3-Coder 上原始方式反而占优—— **裁剪策略要按模型实测，不能无脑套用** 。

**5. 上下文隔离（Context Isolation）** ——把任务拆给 **子 agent** ，各自独立上下文并行工作，只把最终简短结果带回主线，海量中间细节不进入主上下文。它的另一种形态是 **渐进式披露** ：Anthropic 的 Agent Skills 里， `SKILL.md` 的 frontmatter 只带一句描述（始终可见），正文和参考文件 **按需加载** 。你不必在初始提示里塞进所有东西。

课程特别强调： **这五件套不互斥** 。可以先卸载再压缩，可以事件日志加截断观测——真实系统往往全用。收尾时用 LangChain 的分类学做了归纳： **Write（写入）/ Select（选取）/ Compress（压缩）/ Isolate（隔离）** ，其中「长期记忆」指向下一讲的 Memory 课，「多 agent 分区」指向下周一的 Multi-Agent 课。

## 五、案例研究 Pi：极简主义的取舍

最后十分钟的案例研究是 **Pi** ——一个极简主义的 agent harness，设计哲学就一句话：

> Pi is a minimal agent harness. Adapt Pi to your workflows, not the other way around. 
>  Pi 是极简 harness——让 Pi 适配你的工作流，而不是反过来。 
> 

它刻意「不做」的清单很长：无子 agent、无权限检查、无 Plan Mode、无待办清单、无后台 bash。工具只留四个—— **read、bash、edit、write** ，因为 grep、find、ls 全都是 bash 的子集，留着只会造成工具膨胀、分散模型注意力。

对照本讲的模式清单看 Pi，你会发现一个真实系统的完整取舍：

- agent 循环：标准 **ReAct** 风格，先推理再发 JSON 工具调用，上下文组织成 **树** ，可回到任意先前节点分叉；
- 上下文管理： **三件套齐上** ——事件日志转 LLM 输入（OpenHands 思路）、Skill 文件渐进披露、Compaction 压缩；
- 安全： **零内置防护** 。官方警告写得很直白：Pi 以宿主进程同等权限运行，没有任何权限弹窗，等同于一直开着全自动模式。

极简和安全的张力，在 Pi 身上体现得淋漓尽致——它把权限检查、审批流程留给用户自己搭，意味着默认没有任何护栏。这是设计哲学，不是疏忽。

## 本讲小结

- **控制流归谁是根轴** ：工作流归代码（可预测），agent 归模型（灵活），真实系统组合使用；
- **五种工作流模式** （提示链/路由/并行化/编排者-执行者/评估者-优化者）是积木，STORM 与 Archon 展示了怎么拼——Archon 甚至把「拼」本身自动化了；
- **推理行动模式进化树** ：ReAct → Reflexion（反思要靠外部反馈）→ CRITIC（agentic verifier）→ CodeAct（代码即动作）→ ReWOO/LLMCompiler（规划-执行解耦 + 并行），多数已内化进今天的基础设施；
- **上下文五件套** ：事件日志、记忆卸载、压缩、观测遮蔽、隔离——观测占上下文 83.9%，裁剪空间巨大；所有策略服务于「聚焦 + 连续」两条原则；
- **Pi 案例** ：极简 harness 的完整取舍——ReAct 循环、上下文三件套、零安全护栏。

下一讲（第七讲）主题是 **智能体记忆架构** ——短期 vs 长期记忆、文件系统作为外化记忆，正是本讲上下文管理里「记忆卸载」的全面展开。
