GPU 推理慢，往往不是因为计算量大，而是因为**数据搬运**和**任务提交**的开销大。Kev 的优化可以归纳为三类目标，外加两类”减少无效工作”的手段：

| 目标 | 手段 | 本文小节 |
| --- | --- | --- |
| 算得少 / 算得满 | 横向融合：把并排的矩阵乘法拼成一次 | §2 |
| 搬得少 | 纵向融合：把一串小计算塞进一个 kernel（SwiGLU、RMSNorm、DeltaNet） | §3 §4 §5 |
| 发得快 | CUDA Graph：把几百次 CPU 提交压成一次重放 | §6 |
| 减少无效工作 | 关闭下游不使用的输出；固定编译 key，避免重复 autotune | §5.2 §7 |

接下来的每一节，我都会先分析”朴素做法为什么慢”，然后再介绍”如何进行推理加速”，并且还会配合代码进行解读。

## 0. 认识 Kev

**Jev** 是 TypeSafe 公司的商用闭源决策模型，只通过 API 提供，是效果上限。**Kev** 是 Jared Palmer 的开源决策模型家族（Apache-2.0；0.8B / 4B / 9B / 27B，骨干为 Qwen3.5 / Qwen3.8），接口与 Jev 兼容、可直接替换；我项目里还曾涉及到 JEV-27B（AutoTrust 复现）与 Decision4Rec Kev-0.8B（推荐行为微调）。

### 0.1 模型结构

Kev-0.8B 的骨干是 `Qwen3.5-0.8B-Base`：24 层 = **18 层 Gated DeltaNet（线性注意力）+ 6 层 full attention**，冻结；在其上加 **LoRA**（rank 16，约 11.3M 参数）与**指针头**（对每个选项的结束位置打分，softmax 得概率）。后文组件与模型结构的对应关系：

| Q / K / V | 6 层 full attention 的三个投影，见 §2.4 | 图 1 右上：从同一输入分出的三个 Linear → q / k / v |

### 0.2 结构决定了优化方向

- **混合注意力（18 层 DeltaNet + 6 层 full attention）**：DeltaNet 是递归的、不遵守 attention mask，因此底层高性能 kernel 大量复用 **FLA**（Flash Linear Attention）用 **Triton**（类 Python 语法编写 GPU kernel 的语言/编译器）写的实现。这解释了 §5 为什么要专门处理 DeltaNet 的状态。
- **prefill-only + 多问题共享 state**：决策模型只做一次前向（prefill），不逐 token 生成（decode）；state 只算一次并缓存，问题行彼此独立（推荐场景：7 个信号 = 7 行）。这给了 §5”按业务语义关掉无用输出”和 §6”分桶复用图”的空间，也放大了 §1.2”约 2000 个 kernel”的占比。
- **小模型 + 小 batch**：真实计算量小，于是”提交开销”占比高，CUDA Graph 的收益才显著（§6）。

## 1. 基础概念

后文的每一项优化，都是在针对下面三个概念中的某一个。下面这张图（图 3）是全文的“地图”：上半部分是软件侧（代码如何变成 kernel、如何被启动、CUDA Graph 在哪里介入），下半部分是硬件侧（SM 内部的寄存器/共享内存/L1，共享的 L2，以及显存 HBM）。后文每次提到“启动”“片上”“显存”“tile”，都可以回到这张图的对应位置。

![](https://picx.zhimg.com/v2-696db0b606595766d10ed7c571d3bac5_r.jpg)
*图3  GPU 软件执行路径与硬件层级：编译、启动、线程块、SM、L2 与 HBM*

### 1.1 算子（operator） ≠ 计算内核（kernel）

| 名词 | 是什么 | 例子 |
| --- | --- | --- |
| 算子 | 你在 PyTorch 代码里写的一步计算，是”逻辑概念” | x @ W、F.rms_norm(x)、F.silu(x) |
| kernel | 真正被提交到 GPU 上执行的一段程序，是”物理实体” | 一个 cuBLAS（NVIDIA 官方矩阵乘法库）的 GEMM（GEneral Matrix Multiply，通用矩阵乘，即 C=A@B）kernel；一个 Triton 编译产物 |

两者不是 1:1 的，这正是算子优化的空间所在：

![](https://picx.zhimg.com/v2-ef70848d2a98dc1c04516815ed5f4589_r.jpg)
*图4  算子与 GPU 内核的多对多关系*

对照图 3 的上排：你写的 Triton / CUDA C++ 代码经**编译器**生成 **Kernel（GPU 程序）**，再交给 **CUDA Runtime / Launch** 提交执行；启动时一个 kernel 会被拆分成多个**线程块（Thread Blocks）** 分发给各个 SM。“算子”是左边的源码概念，“kernel”是中间那个“GPU 程序”方框——两者之间隔着编译器与调度，因此不必一一对应。

> 类比：菜谱上写”焯水、爆香、翻炒”三个步骤(算子),厨房里可以一锅连着做完(一个 kernel),也可以每步都洗锅换锅(三个 kernel)。菜一样,效率不同。

### 1.2 GPU 的三种”慢”

下表是理解后文所有优化的基础。

| 瓶颈类型 | 实际发生了什么 | 术语（中文常用叫法） | 对应优化 |
| --- | --- | --- | --- |
| 算得慢 | GPU 的计算单元真的在忙着做海量乘加 | compute-bound（计算受限 / 算力瓶颈） | 更高效的矩阵乘法、提高并行度 |
| 搬得慢 | 计算单元大部分时间在等数据从显存过来，或等中间结果写回去 | memory-bound（访存受限 / 带宽瓶颈） | 算子融合、避免不必要的内存复制 |
| 发得慢 | GPU 早就算完了，在等 CPU 提交下一个任务 | launch-bound / CPU-bound（启动受限 / 提交瓶颈） | CUDA Graph、减少 kernel 总数 |

这三种瓶颈在图 3 上各有对应位置：**算得慢**看 SM 内部的 CUDA Cores / Tensor Cores；**搬得慢**看下半的 Registers/Shared Memory/L1 → L2 → VRAM/HBM 这条缓存—显存链路；**发得慢**看上排的 CUDA Runtime / Launch，而它的解法 CUDA Graph 正是上排最右那个“可选，复用任务流程”的虚线框。

> 类比（后文会反复用到）：<br>

- **算得慢** = 厨师火力不够
- **搬得慢** = 每炒一步都要把菜端到后厨冰箱存起来，下一步再取回来
- **发得慢** = 服务员每上一道菜都要跑回前台重新向厨房下单，厨师炒 1 秒、等下单 3 秒

**Kev 的实测数字**：几百个 token 的一次前向，会启动**约 2000 个 kernel**。

单次 kernel 启动的 CPU 开销大约 5–30 微秒，2000 次就是 10–60 毫秒；而 0.8B 模型这点计算量，在 A800/L4 上可能只需要几毫秒。因此在这个规模下，减少模型参数量对延迟帮助有限，因为瓶颈不在计算上。这就是”0.8B 模型单题却要 311 ms”的根本原因。

### 1.3 为什么搬数据很贵

这是由显存的层级结构造成的。

先定义 **SM**（Streaming Multiprocessor，GPU 的基本计算单元；A100 有 108 个）。每个 SM 自带一小块极快的片上存储。整机的存储层级如下：

![](https://pic4.zhimg.com/v2-ab3b7ed124eb40fd043f468d699301d7_r.jpg)
*图 5  GPU 存储层级：片上存储、L2 与显存*

图 5 将图 3 下半部分的存储层级单独展开：每个 SM 内的 Registers、Shared Memory 和 L1 对应最上层，跨 SM 共享的 L2 对应中间层，VRAM/HBM 对应最下层。图中将寄存器与共享内存分开表示；具体容量、带宽和访问延迟取决于 GPU 型号。读图时记住：**越接近计算单元，存储通常越小、访问越快；越往显存和主存，容量通常越大。**

这里有一个关键事实：

> 对于**逐元素运算**（element-wise，如 sigmoid、乘法、加法），耗时几乎完全由”读写了多少字节”决定，与”做了几次乘法”关系不大。

原因是读一个 fp16 数（2 字节）只做 1 次乘法，GPU 的 Tensor Core 大部分时间在空转。这类运算称为**低算术强度（low arithmetic intensity）**。因此”减少中间结果落显存”是这类运算主要的优化方向——这是 §3、§4 的逻辑基础。

## 2. 优化一：横向融合 —— 拼接矩阵乘法

### 2.1 SwiGLU的gate&up

Kev 骨干里每个 Transformer 层都有一个 **SwiGLU 门控 MLP**（见 §0.1）。它的结构是：同一个输入 `x` 先分别经过两个线性层，得到 `gate` 和 `up`，再做逐元素的门控相乘。`gate` 经过激活后充当”门”，`up` 提供内容，两者相乘实现”选择性通过”。

```python
gate = linear(x, W_gate)   # 分支 1：门
up   = linear(x, W_up)     # 分支 2：内容
```

假设形状如下；图 6 的上半部分是分开计算，下半部分展示合并后的形状：

![](https://pic2.zhimg.com/v2-a74e7b89ea1cd46b1bcbe5934dda04e3_r.jpg)
*图 6  共享输入的两个投影与合并 GEMM*

朴素写法是**两次独立的矩阵乘法 = 两个 GEMM kernel**。

### 2.2 权重拼接

注意 PyTorch 的 `nn.Linear` 把权重存成 `[输出维, 输入维]`，前向时计算 $xW^{\top}$。所以 `[100,1024] @ [2048,1024]` 本身不合法，合法的是 `[100,1024] @ [1024,2048]`（即 $W^{\top}$）。拼接时沿**输出维**（第 0 维）拼：

```python
# ===== 只在加载模型时执行一次 =====
W_combined = torch.cat([W_gate, W_up], dim=0)   # [4096, 1024]

# ===== 每次推理执行 =====
combined = linear(x, W_combined)                # x[100,1024] @ W_combined^T[1024,4096] = [100,4096]
gate, up = combined.chunk(2, dim=-1)            # 各 [100, 2048]，是"视图"，不复制
```

数学上完全等价：

$$ \big[\,XW_1^{\top},\; XW_2^{\top}\,\big] \;=\; X\begin{bmatrix} W_1 \\ W_2 \end{bmatrix}^{\!\top} $$

### 2.3 推理加速分析

这里容易产生疑问：$100\times1024\times2048$ 做两次，和 $100\times1024\times4096$ 做一次，FLOPs 完全相同，为什么还会更快？节省来自四个方面。

1. **少启动一次 kernel。** 直接省掉一次 5–30 µs 的 CPU 提交开销。在小 batch 推理里，这往往就是主要收益。
2. **大矩阵更容易充分利用 GPU（提高占用率）。** GPU 把矩阵乘法切成小块（**tile**，GPU 调度矩阵乘的基本单位，即图 3 图例中的“分块 (Tiling)”）分给各个 SM（图 3 中的 SM 0 / SM 1 / … 方框）执行。以 128×128 的 tile 为例，输出 `[100, 2048]` 能切出的 tile 数为:行方向 $\lceil 100/128\rceil = 1$,列方向 $\lceil 2048/128\rceil = 16$,合计 $1\times16=16$ 个。

- **两次分开：** 输出 `[100, 2048]`，每次有 $\lceil100/128\rceil\times\lceil2048/128\rceil = 1\times16 = 16$ 个 tile；单次最多并行占用 16 个 SM。
- **拼成一次：** 输出 `[100, 4096]`，有 $1\times\lceil4096/128\rceil = 1\times32 = 32$ 个 tile；最多并行占用 32 个 SM。

这里的**占用率（occupancy）** 指 SM 上实际活跃线程占最大可驻留线程的比例。注意 M=100 这一维太小（$\lceil100/128\rceil=1$），这是推理场景（token 少）的通病：矩阵太”瘦”，天然填不满 GPU。拼接能缓解但不能根治——这也是小 batch 推理必然偏向 launch-bound 的原因。

1. **输入 `x` 只从显存读一次。** 两次独立 GEMM 要把 `x` 读两遍；合并后只读一遍。
2. **`chunk` 出来的是视图（view），零拷贝。** 这一点值得展开，见下。

> 类比：两批快递都要送到同一栋楼。派两辆车各跑一趟，与装一辆车一起送，件数相同，但后者少跑一趟、单车装载率更高。

**关于”视图”的说明。** PyTorch 张量 = 一块底层存储（storage）+ 一组描述（shape、stride、offset）。`chunk` / 切片**只修改描述，不触碰存储**，因此不产生复制：

![](https://pic4.zhimg.com/v2-54a4b9698b5ecd9e4160de7614c8364f_r.jpg)
*图 7  gate / up 视图共享 combined 的底层存储*

可以用 `data_ptr()` 验证：`gate.data_ptr() == combined.data_ptr()`，而 `up.data_ptr()` 比它偏移 2048 个元素。两者都不复制数据。

代价是：这样得到的张量**不连续**（`gate.is_contiguous() == False`，因为行与行之间隔着 `up` 的那一段）。某些 kernel 要求输入连续，此时才需要 `.contiguous()` 复制一份——这正是 §3.5 要处理的实际问题。

### 2.4 适用范围

所有”共享输入的并行分支”。

Kev 在 Qwen3.5 上合并了：

- MLP 的 `gate_proj` + `up_proj`（即 §2.1 的 SwiGLU 门控）
- 注意力里的 **Q / K / V 三个投影**（多头注意力中，同一个 `x` 也要分别投影成 Q、K、V 三份，同样可以拼成一次）

这类优化称为**横向融合（horizontal fusion）**：把”并排的、互不依赖的、共享输入的”计算合起来。

> [!warning] 唯一的注意点 拼接**必须在模型加载时做一次**。如果每个请求都现拼一次 `W_combined`，就等于每次复制 4096×1024 个权重，节省的时间会被复制开销抵消。 Kev 里对应 `_concat()` / `fuse()`，在 `fused_qwen35.py` 中。

## 3. 优化二：纵向融合 —— 一个 kernel处理一串计算

### 3.1 SwiGLU

拿到 §2 的 `gate` 和 `up` 之后，MLP 要算：

$$ y = \operatorname{SiLU}(gate)\odot up,\qquad \operatorname{SiLU}(g)=g\cdot\sigma(g) $$

其中 $\sigma$ 是 sigmoid（$\sigma(x)=1/(1+e^{-x})$，把任意实数压到 $(0,1)$），$\odot$ 是逐位置相乘。展开就是一行：

$$ y_i = g_i \cdot \sigma(g_i) \cdot u_i $$

（下标 $i$ 表示”每个元素各算各的”）

朴素实现：

```python
temp1  = torch.sigmoid(gate)   # kernel 1
temp2  = gate * temp1          # kernel 2
output = temp2 * up            # kernel 3
```

朴素实现的中间结果要经过显存中转；图 8 对照了分开执行与融合执行：

![](https://pic2.zhimg.com/v2-0c61d741cdd8be5336834c5d79c97c3f_r.jpg)
*图 8  SwiGLU 分开执行与融合执行的显存读写*

### 3.2 显存流量账

设每个张量有 $N$ 个元素，忽略 cache 命中的理想情况：

| 实现 | 读取 | 写入 | 合计搬运 |
| --- | --- | --- | --- |
| 三步分开 | 5N | 3N | \mathbf{8N} |
| 融合成一个 kernel | 2N | N | \mathbf{3N} |

理论上界是 $8/3 \approx 2.67$ 倍加速。

代入真实数字感受一下（$N = 100 \times 2048 = 204800$，fp16 每元素 2 字节）：

| 实现 | 搬运量 | 按 2 TB/s 折算耗时 | kernel 启动开销 | 总计 |
| --- | --- | --- | --- | --- |
| 三步分开 | 3.3 MB | ~1.6 µs | 3 × ~8 µs = 24 µs | ~26 µs |
| 融合 | 1.2 MB | ~0.6 µs | 1 × ~8 µs = 8 µs | ~9 µs |

> [!important] 这张表说明一个要点 在这个规模下，融合省下来的时间，大部分来自”少启动 2 次 kernel”（约 16 µs），而不是”少搬了 2 MB”（约 1 µs）。<br>

- 张量**大**（长序列、大 batch）→ 省显存流量是主要收益
- 张量**小**（decode 阶段、小 batch 推理）→ 省启动次数是主要收益

而”启动次数”这件事做到极致就是 §6 的 CUDA Graph。融合与 CUDA Graph 不是二选一，而是互补的两层。

为什么这些计算”能”被融合？判断标准很简单：

> 第 $i$ 个输出，是否只依赖第 $i$ 个（或同位置的）输入？

SwiGLU 满足：`output[i]` 只需要 `gate[i]` 和 `up[i]`，不需要看别的元素。因此一个 GPU 线程可以：把 `gate[i]`、`up[i]` 读进**寄存器**（图 3 中 SM 方框内的 Registers）→ 在寄存器里连乘三次 → 直接写出 `output[i]`。中间值 `temp1`、`temp2` 从头到尾没有存在过——它们从未离开 SM 内部，也就从未出现在图 3 底部的 HBM 里。

### 3.3 Triton 代码

```python
@triton.jit
def swiglu_example(G, U, Y, n, BLOCK: tl.constexpr):
    pid   = tl.program_id(0)                      # 1 我是第几个工作块
    idx   = pid * BLOCK + tl.arange(0, BLOCK)     # 2 我负责哪 BLOCK 个元素
    mask  = idx < n                               # 3 边界保护

    g = tl.load(G + idx, mask=mask, other=0).to(tl.float32)   # 4 唯一的"搬入"
    u = tl.load(U + idx, mask=mask, other=0).to(tl.float32)

    y = g * tl.sigmoid(g) * u                     # 5 全部在寄存器里完成

    tl.store(Y + idx, y, mask=mask)               # 6 唯一的"搬出"
```

| 行 | 作用 | 说明 |
| --- | --- | --- |
| 1 | @triton.jit 编译标记 | 这段”像 Python 的代码”会被编译成真正的 GPU 程序（Triton 语法接近 Python，但运行在 GPU 上） |
| 1 | program_id(0) 身份 | GPU 会同时启动成百上千个这样的块，每块负责一小段数据——这就是并行 |
| 2 | tl.arange(0, BLOCK) 向量化 | 一次处理 BLOCK 个连续元素，而不是一个一个来 |
| 3 | mask 越界保护 | 最后一块往往不满 BLOCK 个，mask 防止读到别人的内存或写出界 |
| 4 | tl.load 读显存 | 把数据从”仓库”搬到”手上”；.to(tl.float32) 是为了用高精度做 sigmoid，避免 fp16 溢出 |
| 5 | 中间计算在寄存器 | 不落显存，这是融合的意义所在 |
| 6 | tl.store 写显存 | 只在最后写一次 |

### 3.5 内存布局与 stride

§2 里 `chunk` 出来的 `gate` 和 `up`，是同一块大 buffer 的两个切片，在显存里的排布与行步长如图 9 所示：

![](https://pic3.zhimg.com/v2-93b5353e4cd98ef22a69ae4399af3e00_r.jpg)
*图 9  gate / up 的物理排布与行步长*

也就是说，`gate` 这个张量的行与行之间是不连续的（每行末尾要跳过 `up` 的 2048 个元素）。这里的**stride（步长）** 指张量相邻两行在内存里相隔多少个元素。

如果 kernel 假设输入连续，就必须先调用 `.contiguous()`（PyTorch 方法：把张量重新排成内存连续，会产生一次完整复制）。这一次复制会把融合省下的时间抵消掉。

**FLA 的做法**：kernel 直接接受 `stride` 参数，按步长跳着读，不做复制。（对应 `fla/modules/activations.py`）

> [!tip] 写算子前的两个自检问题<br>

1. 这个张量在显存里到底是怎么摆的？连续吗？stride 是多少？
2. 能不能不复制就直接读？

不少”融合后反而变慢”的情况，都是因为中间偷偷插入了一次 `.contiguous()`。

这类”把前后有依赖的计算串起来合成一个 kernel”的优化，称为**纵向融合（vertical fusion）**。

## 4. 优化三：RMSNorm 融合 —— 跨元素求和

### 4.1 RMSNorm

一句话：把一个向量的数值尺度调整到稳定范围（防止数值越来越大或越来越小，训练与推理才稳定）。

$$ \operatorname{RMSNorm}(x)=\frac{x}{\sqrt{\dfrac{1}{d}\sum_{i=1}^{d}x_i^{2}+\epsilon}}\odot w $$

| 符号 | 含义 |
| --- | --- |
| d | 向量长度（隐藏维度，如 1024 / 4096） |
| w | 训练得到的逐维缩放参数 |
| \epsilon | 防止分母为 0 的小常数，如 1e-6 |

朴素实现会拆成：平方 → 求和 → 加 ε → 开方 → 取倒数 → 乘 x → 乘 w，共五六个 kernel、五六个中间张量。

### 4.2 为什么可以融合

§3.3 的判断标准是”第 $i$ 个输出只依赖第 $i$ 个输入”。RMSNorm 看起来违反了——它要先对整行求和。但关键在于：这个求和只在**一行之内**发生（$d$ 个元素，通常 1024–8192），一行完全装得进一个 block 的片上存储（SRAM/寄存器）。

于是单个 kernel 可以这样完成：

![](https://picx.zhimg.com/v2-cd94521a02f3dd4a09bb48fee5c99299_r.jpg)
*图 10  RMSNorm 在片上完成归约、缩放与相邻操作*

> 类比：一个班 40 人的成绩求平均分，一个老师手里拿着名单就能算完（片上完成）。但如果是”全校 5 万人求平均”，就得先把各班的中间结果交上来（跨块归约），复杂度完全不同。归约的**范围**决定了融合的难易。

更进一步地，还可以把相邻操作一并融合：

FLA 的 `fused_norm_gate.py` 支持把相邻操作直接并进同一个 kernel：

$$ z = x + residual \qquad y = \operatorname{RMSNorm}(z)\odot\operatorname{SiLU}(gate) $$

残差相加 + 归一化 + 门控相乘，本来 4–5 个 kernel，合成 1 个。在源码里能直接看到”读数据 → 求平方和 → 归一化 → 应用门控 → 写出”这条完整链路。

### 4.3 权衡：融合不是越多越好

这是原文里很有价值、也容易被初学者忽略的一点。

融合会让 kernel 里同时”活着”的中间变量变多，每个线程占用的寄存器就变多。而一个 SM 的寄存器总量由硬件固定，图 11 示意了寄存器压力增加时，驻留线程块数量可能减少的情况：

![](https://pic1.zhimg.com/v2-3a027f552a8fa3cfe79fe95de1c50d06_r.jpg)
*图 11  寄存器压力、驻留线程与溢出的权衡*

极端情况下，寄存器不够用，编译器会把变量”溢出”到 **local memory**（物理上就是显存），称为 **register spilling（寄存器溢出）**。这时又回到”搬显存”，融合的意义随之消失。

> 类比：一个厨师手上最多端得下 5 个盘子。把 8 道工序全塞给他，他端不下，只能把菜放回冰箱再取出来——那还不如分两个人做。<br> [!tip] 什么该融、什么不要硬融<br>

- **适合融合**：逐元素运算 + 一行/一块内能完成的归约（RMSNorm、LayerNorm、Softmax、SwiGLU）
- **需要高级技巧才能融合**：跨行、跨块的大范围依赖（完整注意力的 softmax、长程卷积）→ 需要分块 + 在线算法（online softmax、状态传递），复杂度陡增
- **不要硬融**：融完 occupancy 下降太多、或触发寄存器溢出

实践上要靠 `ncu`（Nsight Compute）查看 register 用量与 occupancy，而不是靠估计。

## 5. 优化四：DeltaNet / 线性注意力 —— 让状态”就地续用”

### 5.1 Gated DeltaNet 在做什么

Qwen3.5 的一部分层（Kev-0.8B 中为 18⁄24 层，见 §0.1）用的是 Gated DeltaNet，属于**线性注意力**家族。

|  | 标准 Attention | 线性注意力 / DeltaNet |
| --- | --- | --- |
| 存什么 | 保留全部历史的 K、V | 只维护一个固定大小的状态矩阵 S（形如 [d_k, d_v]） |
| 每来一个 token | KV Cache 变长 | 用新 token 更新 S，大小不变 |
| 显存随序列长度 | O(n) 线性增长 | O(1) 恒定 |

> 一句话理解：标准 attention 是”把每一页笔记都留着，随时翻”；DeltaNet 是”边读边把要点压进一块固定大小的白板，读完只留白板”。这是它在长序列、高并发场景下更有优势的原因——显存不随长度增长。

下面把图 2 右侧模块单独放大，直接对照它区分 Kev 中的两种状态：

![](https://pic3.zhimg.com/v2-f96d2aec452541ff0fd0a7ae7e35bf0a_r.jpg)
*图 12  Gated DeltaNet 模块局部放大：短卷积、递归更新、归一化与输出门控*

从下往上读：粉色 Conv 需要最近几个位置的卷积历史；黄色 Gated Delta Rule 使用累计的递归状态；其上的 Norm 与右侧输出门控对应 §4、§5.2 的融合位置。图上的 α / β 是递归更新的门控参数，不是两块缓存本身。

原图展示的是计算路径；下表补充计算过程中实际需要保留的运行时状态：

| 状态 | 存什么 | 类比 |
| --- | --- | --- |
| 卷积状态（conv state） | 前面少量位置（kernel_size − 1 个）的原始输入 | 短程记忆：刚才那几个字 |
| 递归状态（recurrent state） | DeltaNet 累计出来的记忆矩阵 S | 长程记忆：整段话的要点 |

两者的区别在于”记多久、记多细”。**卷积状态**只保留最近 kernel_size−1 个位置的**原始输入**，供局部滑动窗口使用（看当前字和前几个字的组合），窗口滑过即丢弃，因此是”短程、细粒度”；**递归状态**则把从开头到现在的全部信息**压缩**进一块固定大小的矩阵 $S$，每来一个 token 就地更新、永不增长，因此是”长程、压缩”。§5.2 与 §6 的优化（状态复用、地址固定）正是分别针对这两块存储。

### 5.2 Kev 的三个改写

- **改写 1：卷积直接读旧状态，省掉拼接**

朴素实现（每次 decode 都要做）：

![](https://pic3.zhimg.com/v2-1e7b0169083483ec87c4a83f4ff83dc8_r.jpg)
*图 13  带初始状态的卷积省去拼接与独立激活*

优化后：卷积 kernel 直接接受 `initial_state` 参数。它需要”历史”时从旧状态那块内存读，需要”新数据”时从输入读，并且顺手把 SiLU 激活也算掉。

省掉的内容：一次 `cat` 复制 + 一个临时张量 + 一个独立激活 kernel。（对应 `fla/modules/conv/triton/ops.py`）

- **改写 2：把零碎的预处理塞进对应 kernel**

DeltaNet 每步都要算一些很小的量，比如门控值：

$$ g = -\exp(A_{\log})\cdot\operatorname{softplus}(a+b) $$

外加 sigmoid、Q/K 的 L2 归一化等。这些都是逐元素或逐行的小操作。按 §1.3 的结论，它们单独起 kernel 很不划算——每个都要把整个张量读写一遍显存，而计算量小到可以忽略。Kev 用 FLA 提供的接口把它们并进主 kernel。

同时要了解 FLA 的分块（chunked）思路，这是理解线性注意力实现的关键：

![](https://pic1.zhimg.com/v2-08c0eb3cc716402cb0eaea67af3212f4_r.jpg)
*图 14  分块计算：块内并行与块间状态传递*

这是”既要递归的语义、又要 GPU 的并行度”的标准折中，FlashAttention 的 online softmax 是同一种思想的不同应用。因此 DeltaNet 一次前向仍然是多个 kernel 协作完成的，不是一个大一统 kernel。（对应 `fla/ops/gated_delta_rule/chunk.py`）

- **改写 3：按业务语义，关闭下游不使用的输出**

这一条最”工程”，收益上限也最高。

场景：同一段用户历史，配 3 个不同的问题一起问（推荐系统里典型的”一次请求打多个分”）：

![](https://pic1.zhimg.com/v2-493a9777440fb3b21e62fde8f4b09afe_r.jpg)
*图 15  共享前缀与独立问题分支：关闭无用状态保存*

现在问：算完问题 A 之后，A 分支末尾的那个最终状态 $S_A$，还有人用吗？

- 如果是**自回归继续生成**（还要往下写 token）→ 需要，必须保存
- 如果**只是打个分就结束**（推理/评分场景，Kev 正是 prefill-only，见 §0.2）→ 没有人使用

Kev 的场景是后者，于是它对这些分支直接关闭 final state 的输出。省掉的是：计算 + 写回显存 + 那块内存的分配。

> [!important] 这条优化的意义 前面两类优化是”同样的活干得更省”，这一类是”有些活根本不用干”，后者的收益上限更高。<br> 而能不能省，取决于是否理解上层业务的数据流语义：这个输出下游到底有没有人读。只盯着单层算子的函数签名，是发现不了这个优化点的。<br> 这也是为什么算子优化必须和推理框架设计一起做，不能只优化 kernel。（对应 `fused_qwen35.py` 里的 `deltanet_forward()`）

## 6. 优化五：CUDA Graph —— 仅有融合还不够

### 6.1 融合无法消除提交开销

假设 §2–§5 的融合把 2000 个 kernel 降到了 300 个。但每一个 kernel 仍然要 CPU 走一整套流程：

![](https://pica.zhimg.com/v2-53381adea54a0da8409e54be7b2a4482_r.jpg)
*图 16  逐次启动与 CUDA Graph 整体重放*

（**dispatcher** 指 PyTorch 把算子分发到具体实现的后端。）

在 decode 阶段（一次只生成 1 个 token）情况最糟：单个 kernel 的真实计算时间可能只有几微秒，比启动它的时间还短。GPU 算完就在等 CPU 提交下一单。

> 回到餐厅类比：厨师炒一个菜 1 min，服务员每上一道菜都要跑回前台重新向厨房下单、耗 3 min。已经把三道菜合成一道了（融合），但只要”每道菜都要单独下单一趟”这个机制不变，服务员仍然是瓶颈。CUDA Graph 做的事是：把整桌菜的下单流程一次性记下来，以后一句”照单上菜”即可，不必逐道重新下单。

### 6.2 CUDA Graph

把“这一整套 GPU 操作及它们之间的依赖关系”一次性录制成一张图（graph），之后每次只需一句 `graph.replay()`，由 driver 直接按图执行，CPU 只提交一次。在图 3 上排，这就是最右侧那个虚线框“CUDA Graph（可选，复用任务流程）”：它不改变 Kernel 本身，而是把“反复走 CUDA Runtime / Launch 提交”这条路径替换成“复用已录制的流程”。

**录制（capture）到底录下了什么。** 录制期间 kernel 并不产生有效结果，CUDA Runtime 把每一次“提交动作”记成一个**节点（node）**，节点之间按先后/依赖连成**边（edge）**，最终得到一张有向无环图。每个节点记录的是：

1. 要启动哪个 kernel 函数（函数指针）；
2. 启动配置：grid 维度、block 维度、共享内存大小等（对应图 3 的线程块/线程束划分）；
3. 该 kernel 读写的**显存地址**（参数指针）；
4. 它依赖哪些前置节点（边）。

memcpy / memset 等数据搬运也会被记成节点。所以录下的不是数据、不是结果，而是**一份“施工清单”：做哪些操作、按什么顺序、操作哪几块固定内存**。replay 时 driver 直接按清单批量提交，跳过 CPU 逐个 launch 的开销。这也解释了为什么内存地址必须固定：清单里写死的是地址，张量一旦换位置，清单就指向错误的内存。

```python
# ===== 1) 预热 + 录制：只做一次，比较慢 =====
with torch.cuda.graph(g):
    static_out = model(static_in)     # 走一遍，把所有 kernel 及依赖录下来

# ===== 2) 之后每次请求：极快 =====
static_in.copy_(new_input)            # 1 把新数据写入那块固定地址的内存
g.replay()                            # 2 一次性重放整张图
result = static_out.clone()           # 3 从固定地址取走结果
```

> [!warning] 关于 CUDA Graph 的三个常见误解 **误解 1：”录制 = 缓存了计算结果”。** 不对。每次 replay 仍然完整重算一遍。被固定下来的是**执行结构**（哪些 kernel、什么顺序），不是结果。真正”缓存结果”的是输入前缀缓存（Prefix Cache），是另一回事。<br> **误解 2：”输入变了就不能用”。** 不对。输入**内容**可以随便变，但输入**所在的内存地址**不能变。所以必须用 `copy_` 原地写入，而不是 `static_in = new_input`（后者会换地址，图就指向旧内存了）。<br> **误解 3：”外面套一句 `graph.replay()` 就行”。** 不对，见 §6.3。

### 6.3 工程难点

请求长度是变的，但图是死的。

先解释两个词。**请求的长度**指这次输入的 token 数：用户历史 + 场景 + 候选文本拼成一段 state，再配上若干问题行，总 token 数就是长度；不同用户的长度天然不同（137、142、1500……）。**shape** 指模型里每个张量的维度，它由 token 数决定——token 数一变，中间张量的 shape 就跟着变。**内存地址固定**则指：录制时每个中间张量被分配在某块显存上，图里记的是这块显存的地址；replay 时必须还是同一块地址，否则图就读写到错误位置。

把这两点合起来看难点：图里所有的 shape 和内存地址都被固定了，可线上请求长度各不相同，每个长度都录一张图，图的数量会急剧增加，而且录一张图要几十到几百毫秒。

Kev 为此配了四项配套措施：

| 手段 | 解决什么问题 | 说明 |
| --- | --- | --- |
| 按形状分桶（bucketing） | 长度千变万化 → 图数量爆炸 | 把 137、142、150 全部补齐（padding）到 160，共用同一张图 |
| 预分配缓冲区 | 输入/输出地址必须固定 | 提前开好固定大小的缓冲区，新数据一律写入其中 |
| 缓存原地更新 | KV cache / 递归状态地址必须固定 | 用 copy_ 写回原来那块内存，不新建张量（KV cache 指注意力层缓存的历史 K/V 张量） |
| 择时录制 | 录图本身很贵（几十–几百 ms） | 不每来一个新形状就当场录；安排在预热阶段或低峰期 |

### 6.4 Padding 的正确性问题

补进去的是假 token，它们不能影响真实结果：

- **注意力**：假 token 必须被 mask 掉，不能参与 softmax 的归一化（否则真实 token 的注意力权重会被稀释）
- **递归 / DeltaNet**：假 token 不能让状态 $S$ 发生任何更新（否则记忆被错误写入）

Kev 在输入阶段和问题分支使用了不同的补齐方式，并为两者各自准备了对应的掩码——因为这两处的语义不同（前者是共享前缀，后者是独立分支）。

> [!tip] 为什么说 CUDA Graph 是”系统级工程”而不是”一行代码” 它要求整条链路上每一个张量的地址都稳定。以下情况都会使其失效：<br>

- 动态 shape（→ 需要分桶 + padding + mask）
- 动态 cache（→ 需要预分配 + 原地 `copy_`）
- 数据依赖的分支（`if x > 0: 走 kernel A else 走 kernel B`，图里没法有条件跳转，要么固定分支，要么用 `torch.cond` 之类的特殊支持）

因此：融合减少了 kernel 数量，CUDA Graph 消灭了 kernel 的逐个提交，两者叠加才是 Kev 的完整加速。

## 7. 优化六：避免重复编译和自动调优

这一条不改任何计算逻辑，但在线上服务的 P99 延迟上影响很大。

### 7.1 Triton 编译与 autotune

- **编译（compile）**：Triton 源码是“通用模板”，编译器要把它翻译成针对具体 GPU 的机器码（PTX/cubin）。因为不同 shape / 数据类型 / 常量会生成不同的最优机器码，所以 Triton 会为每一种参数组合生成一个**专用版本**（一份独立的机器码）。**key** 就是“决定要不要重新生成一份机器码的那组参数”（shape、dtype、所有 `tl.constexpr` 的值拼成的一个元组）：key 相同就复用已编译的版本，key 一变就重新编译，耗时几百毫秒到几秒。
- **自动调优（autotune）**：`@triton.autotune` 会对同一个 kernel 尝试多组**执行配置**，实测跑一遍挑最快的；第一次遇到新 key 时所有候选配置都要跑一遍，带来明显卡顿。三个配置的含义（对照图 3 图例）：

> 类比：新菜第一次做，厨师要先试三种火候挑最好的（autotune），还得重新读一遍菜谱（编译）。之后同样的菜就快了。问题在于：如果”这算不算一道新菜”的判断标准定得太敏感，他就会一遍遍重新试火候——哪怕菜其实一模一样。

### 7.2 Kev 发现的具体问题

Kev 作者读 FLA 源码时发现：FLA 的若干 kernel 把一个叫 `NB` 的参数（batch 相关的维数）放进了编译 key 和 autotune key，但 kernel 的函数体里并没有使用它。

后果：

![](https://pica.zhimg.com/v2-50ff8ee62d92c939995041f9b50ea83e_r.jpg)
*图 17  固定无关参数以复用编译与调优缓存*

而实际的计算逻辑完全没变，这部分开销没有对应任何计算收益。

Kev 的做法：用 `_FixedNB` 把这些 kernel 的 `NB` 固定为 1，让 key 中这一项不再随 batch 形状变化。

> 用厨师类比：厨房判断“这是不是一道新菜”的清单上，误写了一项与做法无关的标签（比如“今天第几桌点的”，即 `NB`）。于是哪怕菜谱完全相同，只要桌号一变，厨师就认定是新菜，重新试火候、重新读菜谱。`_FixedNB` 做的就是把这项无关标签从清单上划掉——桌号再变也不影响“这是同一道菜”的判断。代价是这张清单是厨房内部定的（FLA 内部实现），一旦厨房改版、清单格式对不上就可能失效，所以 Kev 严格锁定了适配的 FLA 版本。

它到底改善了什么呢？

|  | 影响 |
| --- | --- |
| 预热好之后的稳态单次耗时 | 基本不变 |
| 新形状出现时的尖刺延迟 | 大幅改善 |

> [!important] 为什么”稳态没变”依然值得做 在线服务考核的是 **P99 / P999**（99 / 99.9 分位延迟），而 P99 恰恰由这些偶发尖刺决定。一个 500 ms 的编译卡顿，在 100 次请求里出现 1 次，就足以让 P99 从 30 ms 变成 500 ms。推荐系统里 batch 形状天然高度可变，这类问题的影响比在对话服务里更大。

## 8. 优化总结

![](https://pic4.zhimg.com/v2-69038aa6d1631f0831e7cb7db1d9c99f_r.jpg)
*图 18  六项优化对应的计算、访存、调度与编译开销*

回看前面测到的数字，就能理解差距从哪来：

| 配置 | 场景 | 耗时 |
| --- | --- | --- |
| 关闭全部加速（我的实测） | 0.8B，7 个信号 | ~311 ms |
| Kev 官方（L4，开启加速） | 短文本 + 6 问，新输入 | 22.7 ms |
| Kev 官方（L4，开启加速） | 2200 token + 5 问，新输入 | 108.6 ms |
| Kev 官方（L4，开启加速） | 2200 token + 5 问，命中输入缓存 | 32.3 ms |

我在 A800 上对同一批 100 个样本、相同输入做了实测，结论与上面一致：开启”融合 + CUDA Graph”后，7 个信号一起生成的 P50 从 311 ms 降到 26.7 ms。

| 推理方式 | 1 个信号 P50/P95/P99 | 7 个信号一起 P50/P95/P99 |
| --- | --- | --- |
| 未加速 | 302 / 324 / 343 ms | 311 / 330 / 339 ms |
| 仅融合计算 | 100 / 103 / 105 ms | 104 / 106 / 107 ms |
| 融合 + CUDA Graph | 15.4 / 18.8 / 58.8 ms | 26.7 / 30.1 / 72.6 ms |

读表要点：**仅融合**已把单信号从 302 ms 降到 100 ms（减少 kernel 数与显存搬运）；**再叠加 CUDA Graph** 后单信号降到 15.4 ms、7 信号 26.7 ms（消灭逐个提交开销）。注意”融合 + CUDA Graph”一行的 P99（58.8 / 72.6 ms）明显高于 P50，这正是 §7 所说的”新形状触发录图/编译”造成的尖刺。

## 9. 术语速查

| 术语 | 一句话解释 |
| --- | --- |
| 算子 (operator) | 模型代码里的一步计算（逻辑概念） |
| kernel（计算内核） | 真正在 GPU 上执行的程序（物理实体） |
| GEMM | 通用矩阵乘，C=A@B；cuBLAS 是 NVIDIA 提供的实现库 |
| 横向融合 | 合并”并排的、共享输入的”计算，如 gate/up、Q/K/V 拼权重 |
| 纵向融合 | 合并”前后相依的”计算，如 sigmoid→乘→乘 塞进一个 kernel |
| Triton | 用类 Python 语法写 GPU kernel 的语言/编译器 |
| FLA | Flash Linear Attention，提供大量线性注意力 Triton kernel 的开源库，Kev 复用了它 |
| element-wise（逐元素） | 第 i 个输出只依赖第 i 个输入；这类运算几乎必然是 memory-bound |
| 归约 (reduction) | 把多个元素合成一个（求和、求最大值）；范围决定融合难度 |
| compute-bound / memory-bound / launch-bound | 计算受限 / 访存受限 / 启动受限，三种瓶颈（§1.2） |
| 算术强度 (arithmetic intensity) | 每读一字节数据做多少次计算；越低越吃带宽 |
| occupancy（占用率） | SM 上实际驻留的线程数 / 最大可驻留数；低了藏不住访存延迟 |
| register spilling（寄存器溢出） | 寄存器不够，变量被赶到显存里的 local memory，性能下降 |
| stride（步长） | 张量相邻元素在内存里隔多远；不连续时要靠它跳读，避免 .contiguous() 复制 |
| view（视图） | 共享底层 storage 的”窗口”，切片/chunk 不复制数据 |
| tile | 把大矩阵切成的小块，GPU 调度矩阵乘的基本单位 |
| SM | Streaming Multiprocessor，GPU 的基本计算单元 |
| prefill / decode | 对输入并行做一次前向 / 逐 token 自回归生成；决策模型只有 prefill |
| pointer head（指针头） | Kev 的输出头，对选项结束位置打分后 softmax 得概率 |
| LoRA | 只训练低秩增量矩阵、冻结主干的微调方法 |
| CUDA Graph | 把一整套 GPU 操作及依赖录成图，之后一次重放，消灭逐个提交开销 |
| bucketing（分桶） | 把不同长度 padding 到少数几个固定规格，共用同一张图 |
| KV cache | 注意力层缓存的历史 K/V 张量 |
| autotune（自动调优） | Triton 实测多组 kernel 配置挑最快的；新 key 会触发重跑 |
| chunked（分块） | 长序列切块：块内并行、块间传状态；兼顾递归语义与 GPU 并行度 |
| conv state / recurrent state | DeltaNet 的短程记忆（卷积历史）/ 长程记忆（状态矩阵 S） |
| P99 | 99 分位延迟；由偶发尖刺（编译、autotune、录图）决定 |
