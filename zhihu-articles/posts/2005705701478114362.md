深度解析智能体架构、工作流与落地实践

将所有职责都交由单个大语言模型承担，本质上是把 **破坏复杂系统灵活性的单体式依赖** ，转嫁到了AI层。即便一个独立对话机器人能力再强，在长期记忆管理（状态）、并行任务执行，以及特定领域的深度专业化上，也会面临结构性局限。

任务过载的智能体会被上下文窗口拖累，沦为 **“样样都能做，却样样不精通”** 的臃肿架构——这不仅会推高运行成本，还会让系统完全失去可扩展性。

突破这一瓶颈的方案，是将智能体设计为 **模块化单元** ，并通过 **A2A（Agent-to-Agent，智能体间）协议** 进行协同。借助A2A协议，我们可以把复杂工作流拆解成多个环节，分配给专业化的智能体处理。

这种架构能让系统的每个模块维护自身状态，同时通过标准化交互与其他智能体协作。最终实现的不再是一个巨型模型，而是一套 **可管控、智能体之间可相互通信的「AI智能体编排体系」** 。

## 一、什么是智能体？

AI 智能体是一种 **软件单元** ，它能够感知自身所处环境，基于接收的数据进行推理，并自主做出决策以完成预设目标。 它与传统聊天机器人的核心区别在于：聊天机器人仅对用户输入做出响应，每次会话都从零开始；而智能体会 **维护状态** ，记住过往交互，并在该上下文基础上规划下一步动作。

智能体具备四大核心能力：

1. **感知** ：从用户输入、API 返回结果、传感器数据等外部渠道收集信息。
2. **推理** ：借助大语言模型（LLM）能力解读所获取的信息，确定执行策略。
3. **执行** ：通过调用工具与外部 API，完成具体操作。
4. **学习** ：评估行动的执行结果，以此优化后续决策。

与简单的函数调用不同，智能体会留存执行历史，且在需要时可将任务 **委托给其他智能体** 。 现代智能体可直接与企业系统集成：拉取数据、触发工作流、更新记录、端到端管理业务流程。

## 二、智能体、工具与工作流的对比

智能体系统的基础组件构成 **三层层级结构** ：

- **工具（Tool）** 赋予智能体对话之外能力的 **原子功能** ，例如对接外部 API、检索信息、执行代码等。 工具只做一件事并返回结果， **不做决策** 。 例如： `search_linkedin(keywords)` 只会执行搜索，而 **由智能体决定使用什么关键词** 。
- **智能体（Agent）** 为特定任务设计的 **基础执行单元** 。 智能体可以使用大语言模型做复杂推理（如 `LlmAgent` ），也可以作为确定性的执行控制器。 最核心的区别： **智能体可以自主决定调用哪个工具、何时调用、用什么参数** 。
- **工作流（Workflow）** 一种让多个智能体协同工作的 **编排模式** 。 ADK 提供三类核心的工作流智能体： `SequentialAgent` （串行）、 `ParallelAgent` （并行）、 `LoopAgent` （循环）。 工作流为可预期的流程提供 **确定性控制** ，而由 LLM 驱动的动态路由则提供自适应行为。

## 三、为何要采用多智能体架构？

无论单个智能体的能力多强大，受 **上下文窗口限制** 、 **串行处理约束** 以及指令复杂度不断提升的影响，性能衰减都将成为必然。根据 Anthropic 多智能体研究系统的实测数据，仅 **令牌用量** 一项，就解释了浏览类任务中 80% 的性能差异。这意味着：给单个智能体堆砌更多任务，会导致性能 **非线性下滑** 。

多智能体架构通过四大核心原则突破这一瓶颈：

1. **专业化** 每个智能体只聚焦一个细分领域。在 Anthropic 系统中，主研究员智能体承担类似项目经理的角色，而子智能体作为独立的研究助理。这种模式不仅提升效率，还能降低单个智能体的认知复杂度。
2. **并行化** 以 **并发执行** 替代串行处理。在 Anthropic 系统中，主智能体会并行启动 3–5 个子智能体，每个子智能体又可同时调用 3 个以上工具。这一优化让复杂查询的研究耗时最多减少 90%。
3. **模块化** 采用 **编排器–工作者** 架构，让工作流具备模块化与可扩展性。它将单一、僵化的自动化流程，转变为由多个智能体协同合作的可组合系统。新增智能体不会破坏整体流程。
4. **上下文分发** 不再共用一个上下文窗口，而是让每个智能体在 **独立的上下文** 中运行。这实现了单个智能体无法企及的并行推理能力。子智能体在各自的上下文里独立工作，只把最关键的结果回传给主智能体。

在 Anthropic 的生产环境实测中， **Claude Opus 4 主智能体 + Claude Sonnet 4 子智能体** 的组合，相比单独运行的 Claude Opus 4， **性能提升了 90.2%** 。

## 四、智能体架构模式

多智能体系统的成功，取决于选用合适的架构模式。谷歌 ADK 为生产可用的工作流智能体提供了四种核心模式。这类模式的关键特点是： **执行流程具备确定性** ，可依据智能体类型与配置保证编排逻辑；同时每个子智能体又可以是任意类型（包括大语言模型智能体）。这种混合方案，将 **结构化控制** 与 **灵活推理能力** 合二为一。

### 4.1 串行模式（线性链）

串行模式将智能体组织成一条 **线性流水线** ，前一个智能体的输出直接作为下一个智能体的输入。该模式常用于 **数据转换与数据增强** 场景，每一步都在上一阶段结果的基础上继续处理。

> 所有子智能体共享同一个 `InvocationContext` ，可以通过 `session.state` 方便地在步骤之间传递数据。

### 核心特点

- 执行顺序 **确定可控** ，无需 LLM 参与编排。
- 智能体之间通过 `output_key` 和共享状态完成数据传递。
- 共享上下文，每个智能体都能访问前面步骤的结果。
- 出错时 **自动中断流水线** （快速失败）。

### 适用场景

- 代码开发流水线：代码编写者 → 代码评审者 → 代码重构者
- 文档处理流程：PDF 解析器 → 内容提取器 → 摘要生成器
- 简历分析流水线：原始数据提取 → 技能分析 → 格式标准化

```text
from google.adk.agents import LlmAgent, SequentialAgent

# CareerAgent: CV Processing Pipeline
# Each agent writes to state via output_key, next agent reads from state

cv_data_extractor = LlmAgent(
    name="CVDataExtractor",
    model="gemini-2.0-flash",
    instruction="Extract personal information, experiences, and education from the CV file.",
    output_key="extracted_cv_data"
)

skill_analyzer = LlmAgent(
    name="SkillAnalyzer",
    model="gemini-2.0-flash",
    instruction="""Analyze the extracted CV data: {extracted_cv_data}
    Identify technical skills, proficiency levels, and industry experience.""",
    output_key="skill_analysis"
)

format_validator = LlmAgent(
    name="FormatValidator",
    model="gemini-2.0-flash",
    instruction="""Validate the skill analysis: {skill_analysis}
    Check JSON schema compliance and convert to standard format.""",
    output_key="validated_output"
)

cv_processing_pipeline = SequentialAgent(
    name="CVProcessingPipeline",
    sub_agents=[cv_data_extractor, skill_analyzer, format_validator],
    description="Processes CV sequentially: data extraction → analysis → validation"
)
```

### 4.2并行模式（并发执行）

并行模式会 **同时运行多个智能体** ，并将所有执行结果合并为一份最终输出。根据谷歌 ADK 文档说明，该模式非常适合 **「追求执行速度、且任务彼此独立、资源消耗较高」** 的场景。 子智能体之间 **不会自动共享状态** ，各自的执行结果会通过 `output_key` 写入状态，再由下一阶段统一汇总。

### 核心特点

- 智能体 **并发执行、互不等待**
- 总耗时等于 **执行最慢的那个智能体** 的耗时（可实现大幅提速）
- 每个智能体通过自身的 `output_key` 将结果写入状态
- 属于「 **分发散集** 」模式：并行执行 → 统一归集结果

### 适用场景

- 多源信息调研：从不同数据源 **并发采集** 信息
- 集群式代码审查：安全扫描器 ∥ 代码风格检查器 ∥ 复杂度分析器并行运行
- 招聘岗位分析：市场调研 ∥ 企业文化分析 ∥ 薪资预估并行处理

```text
from google.adk.agents import LlmAgent, ParallelAgent, SequentialAgent

# CareerAgent: Job Posting Multi-Analysis
# Three specialist agents run concurrently, results merged in synthesis agent

market_researcher = LlmAgent(
    name="MarketResearcher",
    model="gemini-2.0-flash",
    instruction="Analyze industry trends and demand for the position in the job posting.",
    tools=[google_search_tool],
    output_key="market_analysis"
)

company_analyzer = LlmAgent(
    name="CompanyAnalyzer",
    model="gemini-2.0-flash",
    instruction="Research company culture, Glassdoor reviews, and employee satisfaction.",
    tools=[google_search_tool],
    output_key="company_analysis"
)

salary_estimator = LlmAgent(
    name="SalaryEstimator",
    model="gemini-2.0-flash",
    instruction="Determine market salary range for the position and location.",
    tools=[google_search_tool],
    output_key="salary_analysis"
)

# Parallel research phase
parallel_research = ParallelAgent(
    name="JobInsightResearch",
    sub_agents=[market_researcher, company_analyzer, salary_estimator]
)

# Synthesis agent merges parallel results
synthesis_agent = LlmAgent(
    name="InsightSynthesizer",
    model="gemini-2.0-flash",
    instruction="""Combine all research results:
    - Market: {market_analysis}
    - Company: {company_analysis}
    - Salary: {salary_analysis}
    Create a comprehensive job opportunity report.""",
    output_key="final_insight"
)

# Parallel + Sequential hybrid pipeline
job_insight_pipeline = SequentialAgent(
    name="JobInsightPipeline",
    sub_agents=[parallel_research, synthesis_agent]
)
```

### 4.3 循环模式（迭代优化）

循环模式会 **重复执行一条智能体链** ，直到满足终止条件。根据谷歌 ADK 文档说明： “若达到了可选设置的最大迭代次数 `max_iterations` ，或是任意子智能体返回了带有 `escalate=True` 的事件，循环便会停止。” 该模式非常适合追求“极致效果”的智能体——它们可以自主规划、评估并持续优化自身输出。

### 核心特点

- 迭代全过程会保留 `InvocationContext` （从用户单次请求到最终响应、承载全量信息的运行时上下文），实现 **状态持久化**
- 可通过 `max_iterations` 设置 **安全迭代上限** ，避免死循环
- 支持通过 `escalate=True` 事件实现 **提前退出**
- 计数器与状态标记在迭代间保持有效

### 适用场景

- 代码精调：代码优化器 → 质量检查器 →（循环直至质量达标）
- 内容优化：草稿生成器 → 评估器 → 优化器 循环迭代
- 求职信优化：撰写 → 评估 → 修改 的循环打磨

```text
from google.adk.agents import LlmAgent, LoopAgent
from google.adk.tools import FunctionTool

# CareerAgent: Cover Letter Iterative Refinement
# Loop continues until quality standard is met

def exit_loop(quality_approved: bool) -> dict:
    """Terminate loop when quality is approved"""
    return {"escalate": quality_approved}

exit_loop_tool = FunctionTool(func=exit_loop)

cover_letter_writer = LlmAgent(
    name="CoverLetterWriter",
    model="gemini-2.0-flash",
    instruction="""Write or revise cover letter based on job requirements.
    Previous feedback: {critic_feedback}
    Current draft: {current_draft}""",
    output_key="current_draft"
)

quality_critic = LlmAgent(
    name="QualityCritic",
    model="gemini-2.0-flash",
    instruction="""Evaluate the cover letter: {current_draft}
    Check criteria: alignment with job requirements, tone, originality.
    Score from 1-10 and provide improvement suggestions.""",
    output_key="critic_feedback"
)

approval_checker = LlmAgent(
    name="ApprovalChecker",
    model="gemini-2.0-flash",
    instruction="""Review critic evaluation: {critic_feedback}
    If score is 8 or above, call exit_loop(True).
    Otherwise call exit_loop(False).""",
    tools=[exit_loop_tool]
)

cover_letter_loop = LoopAgent(
    name="CoverLetterRefinementLoop",
    sub_agents=[cover_letter_writer, quality_critic, approval_checker],
    max_iterations=5
)
```

### 4.4协调者模式（编排器-工作者模式）

协调者模式采用 **中心化编排** 架构：由一个核心 **编排器智能体** 分析用户请求，将任务拆解为子任务，并动态分发给专业化的 **工作者智能体** 执行。 与其他模式不同，该模式下由大语言模型（LLM）自主做出路由决策—— **调用哪个智能体，在运行时动态决定** 。在我们的职业智能体项目中， `JobOrchestrator` （任务编排器）正是采用了这一模式。

### 核心特点

- 由 LLM 驱动 **动态路由与任务委派**
- 运行时完成 **任务拆解与自适应调度**
- 通过 `transfer_to_agent` 工具调用子智能体
- 编排器在自身指令中预先掌握所有智能体的能力

### 适用场景

- 复杂用户请求：如“帮我找工作、优化简历、撰写求职信”
- 动态调研：根据用户查询内容，灵活调用不同的专业智能体
- 异构智能体协同：统一管理具备不同能力的各类智能体

```text
from google.adk.agents import LlmAgent
from google.adk.tools import agent_tool

# CareerAgent: Job Orchestrator
# Central orchestrator coordinates specialist agents based on user request

job_searcher = LlmAgent(
    name="JobSearcher",
    model="gemini-2.0-flash",
    instruction="Search and list job postings from LinkedIn matching user criteria.",
    tools=[linkedin_search_tool, job_filter_tool]
)

job_analyzer = LlmAgent(
    name="JobAnalyzer",
    model="gemini-2.0-flash",
    instruction="Analyze job posting requirements, tech stack, and company information.",
    tools=[web_scraper_tool, company_info_tool]
)

cv_optimizer = LlmAgent(
    name="CVOptimizer",
    model="gemini-2.0-flash",
    instruction="Optimize user's CV for target job posting and provide recommendations.",
    tools=[cv_parser_tool, keyword_matcher_tool]
)

match_scorer = LlmAgent(
    name="MatchScorer",
    model="gemini-2.0-flash",
    instruction="Calculate match score between user profile and job posting (0-100).",
    tools=[scoring_algorithm_tool]
)

# Orchestrator: Coordinates all sub-agents
job_orchestrator = LlmAgent(
    name="JobOrchestrator",
    model="gemini-2.0-flash",
    instruction="""You are the main orchestrator of CareerAgent.
    Analyze user request and delegate to appropriate agents:
    - For job search: JobSearcher
    - For posting analysis: JobAnalyzer
    - For CV optimization: CVOptimizer
    - For match scoring: MatchScorer
    Decompose complex requests into sub-tasks and process sequentially.""",
    sub_agents=[job_searcher, job_analyzer, cv_optimizer, match_scorer]
)
```

### 4.5A2A 协议：智能体间通信

现代AI系统依托两大核心通信层运行。 第一层是 **MCP（模型上下文协议）** ，用于标准化智能体与工具、数据源的对接方式。 第二层是 **A2A（Agent-to-Agent，智能体间）协议** ，用于定义智能体之间如何协同合作。

Anthropic 提出的 MCP 让智能体可以轻松访问数据库、发起 API 调用；而谷歌提出的 A2A，则能让 **不同框架、不同厂商开发的智能体** ，使用统一的语言相互沟通。

我们可以用 **汽车维修店** 来比喻两种协议的区别： 店里的每位维修技师（智能体）都会使用车辆诊断仪、维修手册、零件目录等专业工具——这就是 **MCP 层** 。 而技师之间还会相互协作：“我已经修好这辆车的发动机，现在需要你检查电路系统”——这种 **任务委派与配合** ，就是 **A2A 层** 。

简单来说： **MCP 管工具调用，A2A 管团队协同。**

### 4.6A2A 核心构建模块

A2A 协议架构基于六大基础概念构建，每个概念在系统中承担不同的职责。

**A2A 客户端** 是发起工作流、将任务委派给远程智能体的发起方。客户端会判断哪个智能体最适合处理对应任务，并将合适的任务发送给该智能体。在职业智能体系统中， `JobOrchestrator` 就作为 A2A 客户端，将岗位分析任务委派给 `AnalyzerAgent` 。

**A2A 服务端** 通过 HTTP 端点接收并处理任务，随后返回结果。每个专业化智能体都会搭载专属的 A2A 服务端，并监听指定端口。例如， `AnalyzerAgent` 运行在 9002 端口， `StorageAgent` 运行在 9004 端口。

**智能体卡片（Agent Card）** 可以理解为智能体的 **数字名片** 。这份 JSON 文档会发布在 `/.well-known/agent.json` 路径下，声明智能体的名称、能力、服务端点地址、支持的通信模式以及身份认证要求。客户端智能体通过读取这些卡片，来寻找合适的任务处理方。

**任务（Task）** 是 A2A 协议中最基础的工作单元。每个任务都拥有唯一 ID，并按照既定状态流转： `已提交` → `执行中` → `已完成` 。 对于耗时较长的任务， `待补充输入` 状态用于处理额外信息请求，而 `失败` 状态则用于异常场景处理。这套状态机机制，让同一协议既能处理毫秒级完成的简单查询，也能支撑耗时数小时的复杂调研任务。

**消息（Message）** 代表客户端与服务端之间的每一次通信交互。每条消息包含一个 **角色** （用户或智能体）与一个或多个 **内容单元** 。 内容单元是信息的载体：

- `TextPart` ：纯文本单元
- `FilePart` ：文件单元（以 Base64 编码或资源 URI 形式）
- `DataPart` ：结构化 JSON 数据单元

**产物（Artifact）** 指智能体生成的 **有形输出结果** 。分析报告、优化后的简历、匹配度评分等，都会以产物形式返回。产物同样由内容单元构成，并在任务完成后发送给客户端。

### 4.7智能体卡片：智能体的数字身份

根据 A2A 官方规范， **智能体卡片（Agent Card）** 是一份 JSON 格式的配置清单，用于定义智能体的身份、能力与通信要求。 每个 A2A 服务端都会在 `/.well-known/agent.json` 端点发布该卡片，客户端智能体通过请求该地址来发现远程智能体。

智能体卡片的关键字段如下：

**身份信息** `name` （名称）、 `description` （描述）、 `version` （版本）和 `protocolVersion` （协议版本）字段，定义了智能体的基础身份。 在职业智能体系统中，编排器智能体以 `career_agent_orchestrator` 为名运行，版本为 `3.1` 。

**能力配置** `streaming` （流式传输）、 `pushNotifications` （推送通知）和 `extensions` （扩展）等字段，指明了智能体支持的通信模式。 在我们的项目中，编排器同时支持 SSE 流式传输与 WebSocket 通信。

**技能清单** `AgentSkill` （智能体技能）数组，定义了智能体可执行的具体任务。 在职业智能体系统中， `search_jobs` （岗位搜索）、 `analyze_jobs` （岗位分析）和 `score_compatibility` （匹配度评分）等操作都属于此类。

**安全方案** A2A 支持五种认证方式：API 密钥、HTTP 认证（Bearer 令牌/基础认证）、OAuth 2.0（四种流程）、OpenID Connect 以及双向 TLS 认证。 在职业智能体系统中，内部通信未启用认证，但生产环境推荐使用 OAuth 2.0。

### 4.8任务生命周期

A2A 官方规范定义了任务会历经 **八种状态** 的生命周期。这套状态机机制，让同一套协议既能处理毫秒级完成的简单查询，也能支撑耗时数小时的复杂调研任务。

- **submitted（已接收）** 服务端已接收并创建任务，为 **初始状态** 。
- **working（执行中）** 任务正在被处理。对于耗时较长的任务，该状态可持续数分钟甚至数小时。
- **input-required（待补充输入）** 智能体需要额外信息才能完成任务，客户端可发送新消息继续流程。
- **completed（已完成）** 任务成功执行完毕，为 **终态** ，不可重新启动。
- **failed（已失败）** 任务因出错而执行失败，为 **终态** 。
- **cancelled（已取消）** 由客户端主动取消任务，为 **终态** 。
- **rejected（已拒绝）** 智能体拒绝执行该任务，为 **终态** 。
- **auth-required（待认证）** 需要进行二次身份验证，用于敏感操作场景。

```text
class TaskState(str, Enum):
    SUBMITTED = "submitted"
    WORKING = "working"
    INPUT_REQUIRED = "input-required"
    COMPLETED = "completed"
    FAILED = "failed"
    CANCELLED = "cancelled"
    REJECTED = "rejected"
    AUTH_REQUIRED = "auth-required"
```

### 4.9 A2A 通信模式

A2A 协议支持三种不同的通信模式，每种模式均针对不同场景做了专项优化。

- **同步请求/响应** 采用 JSON-RPC 2.0 格式的标准 HTTP 请求，适用于简单、快速的任务。 客户端调用 `SendMessage` ，服务端立即返回 `Task` 或 `Message` 。
- **服务器发送事件（SSE）** 面向耗时较长任务的 **实时流式传输** 方案。 客户端通过 `SubscribeToTask` 订阅任务，服务端以 `text/event-stream` 格式推送状态更新。 当任务进入终态时，流传输自动终止。
- **推送通知（Webhooks）** 适用于客户端离线/断开连接场景的 **异步通知** 方式。 客户端提供 Webhook 地址，任务状态发生变更时，服务端主动向该地址发送 HTTP POST 请求。

### 4.10CareerAgent A2A 架构

CareerAgent 是一套 **生产级多智能体系统** ，由四个专业化智能体通过 A2A 协议协同工作。每个智能体都以独立 A2A 服务端的形式运行在专属端口上，在 `/.well-known/agent.json` 端点发布智能体卡片，并通过 JSON-RPC 2.0 接收任务。该架构 **完整实现了谷歌的 A2A 规范** 。

- **编排器智能体（Orchestrator Agent）** 系统的核心协调者。负责接收用户请求、管理工作流，并将任务分发至各专业化智能体。可直接处理领英数据抓取，通过 SSE 推送实时状态更新，并支持基于 WebSocket 的双向通信。
- **分析器智能体（Analyzer Agent）** 基于 Gemini 2.0 Flash 对岗位招聘信息进行分析的专业化智能体。从招聘信息中提取岗位要求、技术栈、职级与公司信息，并通过批处理实现高处理吞吐量。
- **匹配度智能体（Compatibility Agent）** 负责计算简历与岗位匹配度评分的专业化智能体。将用户技能与岗位要求做对比，输出 0–100 分的匹配度分数，并详细呈现优势与不足。
- **存储智能体（Storage Agent）** 基于 PostgreSQL 管理数据持久化的专业化智能体。负责存储原始岗位信息、分析结果与匹配度分数，同时处理数据统计与查询。

### 4.13A2A 任务委派

每个阶段均通过 A2A 处理器，采用 **标准化 JSON-RPC 2.0 协议** 进行通信。 `send_task_to_agent` 方法会从注册中心查找目标智能体，校验其是否支持对应操作，随后下发任务。

```text
# CareerAgent: Task Delegation via A2A
# Each phase follows the same pattern

async def _analyze_jobs(self, jobs_data: List[Dict]) -> List[Dict]:
    """Send job analysis task to Analyzer Agent"""

    a2a = self._get_a2a_handler()

    # Create and send A2A Task
    response = await a2a.send_task_to_agent(
        agent_name="analyzer",           # Target agent
        action="analyze_jobs",           # Action to invoke
        params={
            "jobs": jobs_data,           # Job data
            "api_key": self.api_key,     # Gemini API key
            "language": "en"             # Prompt language
        }
    )

    # Check task status
    if response.get("status") == "completed":
        return response.get("result", {}).get("analyses", [])
    else:
        logger.error("A2A: Job analysis failed", error=response.get("error"))
        return []
```

### 4.14 A2A 事件总线与 SSE 桥接器

A2A 协议定义了 **事件总线（Event Bus）** 机制，用于追踪任务状态的变化。 在 CareerAgent 中，这类事件会通过 SSE（服务器发送事件）推送给前端。 每个阶段启动和完成时，编排器都会发布相应事件。

```text
# CareerAgent: Event-Driven Pipeline Management
# A2A Event Bus with SSE integration

class EventBus:
    """A2A Event Bus - v0.2.0 compliant event management"""

    def __init__(self):
        self._subscribers: Dict[EventAction, List[Callable]] = {}
        self._event_history: List[A2AEvent] = []

    async def publish(self, event: A2AEvent):
        """Publish event and notify all subscribers"""
        self._event_history.append(event)

        for handler in self._subscribers.get(event.action, []):
            if asyncio.iscoroutinefunction(handler):
                await handler(event)
            else:
                await asyncio.to_thread(handler, event)

# Usage within pipeline
async def run_complete_cycle(self, keywords, location, limit):
    cycle_id = f"cycle_{datetime.now().strftime('%Y%m%d_%H%M%S')}"

    # Phase 1 start
    await emit_pipeline_event("phase_started", {
        "cycle_id": cycle_id,
        "phase": 1,
        "name": "LinkedIn Scraping"
    })

    raw_jobs = await self._scrape_jobs(keywords, location, limit)

    # Phase 1 complete
    await emit_pipeline_event("phase_completed", {
        "cycle_id": cycle_id,
        "phase": 1,
        "count": len(raw_jobs)
    })
```

## 结论与未来展望

多智能体系统代表了 **AI应用构建方式的范式转变** 。我们不再将所有功能负载集中在单一的单体模型上，而是通过把复杂工作流分发至可相互通信的专业化智能体，让系统具备 **模块化、可扩展性与高鲁棒性** 。

CareerAgent 正是这一理念的具体落地实践：四大专业化智能体通过 A2A 协议协同工作，实现领英岗位检索、基于 Gemini 的岗位分析、简历-岗位匹配度评分，以及将数据持久化存储至 PostgreSQL 的全流程服务。每个智能体专注于自身核心职责，由编排器统筹整体流程。
