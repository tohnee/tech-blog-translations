## 一、训练时最主要的显存占用

训练时显存通常由下面几部分组成：

### 1. 模型权重参数

也就是 base model 的参数本身。

假设模型有 `N` 个参数：

| dtype | 每个参数占用 |
| --- | --- |
| FP32 | 4 bytes |
| FP16 / BF16 | 2 bytes |
| INT8 | 1 byte |
| INT4 | 0.5 byte |

如果是一个 30B 参数模型，BF16 权重大概就是：

```text
30B × 2 bytes ≈ 60GB
```

### 2. 梯度

训练时要对可训练参数保存梯度。

全参数训练时，每个可训练参数一般需要一份梯度：

```text
gradient ≈ trainable parameters × dtype_size
```

如果全参数 BF16 训练 30B 模型，梯度大概也是：

```text
30B × 2 bytes ≈ 60GB
```

### 3. 优化器状态

这是训练时非常大的显存来源，尤其是 AdamW。

AdamW 通常会为每个可训练参数保存：

```text
参数本身
梯度
一阶动量 m
二阶动量 v
```

如果优化器状态用 FP32，那么每个可训练参数额外需要：

```text
m: 4 bytes
v: 4 bytes
```

全参数训练时，优化器状态可能比模型权重本身还大。

例如 30B 参数全量 AdamW：

```text
m: 30B × 4 bytes ≈ 120GB
v: 30B × 4 bytes ≈ 120GB
```

### 4. 激活值 Activation

训练时，前向传播产生的中间隐藏状态需要保存下来，用于反向传播。

这部分跟下面几个因素强相关：

```text
batch_size
sequence_length
hidden_size
layer 数
是否保存 attention 中间结果
是否开启 gradient checkpointing
```

粗略理解：

```text
activation memory ∝ batch_size × seq_len × hidden_size × layer_num
```

对于大模型训练，激活显存经常也非常大。尤其是长序列、大 batch、不开 gradient checkpointing 的时候。

### 5. 临时 buffer / 通信 buffer / 框架开销

这部分包括：

```text
attention 临时矩阵
matmul workspace
NPU/CUDA kernel workspace
分布式通信 buffer
ZeRO/FSDP/TP 的切分与聚合 buffer
vLLM/transformers/torch_npu 框架额外缓存
```

这些开销不一定稳定，有时你看到“还没开始训练就占了一些显存”，里面除了模型权重，还可能有框架初始化、通信组、kernel 缓存等。

## 二、推理时最主要的显存占用

推理和训练不同，推理没有反向传播，所以一般没有：

```text
梯度
优化器状态
训练用 activation 保存
```

推理显存主要是下面几部分。

### 1. 模型权重

这是推理时最基础的显存占用。

比如 BF16 30B：

```text
30B × 2 bytes ≈ 60GB
```

如果 tensor parallel = 2，理想情况下每张卡大约放一半权重：

```text
每卡 ≈ 30GB 权重
```

实际会更高，因为还会有 embedding、lm_head、专家切分不均、通信 buffer、框架 buffer 等。

如果是 W8A8 或 INT8 权重量化，理论上权重占用可以接近减半：

```text
30B × 1 byte ≈ 30GB
```

但是实际推理显存不会严格减半，因为 KV cache、workspace、反量化 buffer、量化 scale、runtime buffer 仍然存在。

### 2. KV Cache

这是大模型推理时非常关键的一块显存，尤其是 vLLM 这种高并发推理场景。

Transformer 自回归生成时，每生成一个 token，都会缓存每一层的 Key 和 Value。这样后续 token 不需要重新计算历史上下文。

KV cache 大小大致和下面因素成正比：

```text
batch_size / 并发序列数
总上下文长度
layer 数
kv head 数
head_dim
dtype size
```

粗略公式：

```text
KV cache ≈ num_layers × 2(K,V) × num_tokens × num_kv_heads × head_dim × dtype_size
```

假设在 vLLM 里设置：

```text
max_model_len = 2048
max_num_seqs = 320
max_num_batched_tokens = 20000
```

那么对于Qwen3-30B-A3B而言：

每 token KV cache 总量

= num_layers × 2(K,V) × num_kv_heads × head_dim × bytes

= 48 × 2 × 4 × 128 × 2

= 98,304 bytes

≈ 96 KB / token

### 3. Prefill / Decode 临时激活

虽然推理不用保存反向传播激活，但前向计算过程中仍然会产生临时 activation。

尤其是 prefill 阶段，也就是输入 prompt 的整段前向，attention 计算和 MLP 计算会有临时 buffer。

但这部分通常是“临时峰值”，不像训练 activation 那样需要长期保存到 backward。

### 4. Runtime / workspace / 通信 buffer

包括：

```text
attention kernel workspace
NPU/CUDA runtime buffer
tensor parallel 通信 buffer
MoE routing / expert dispatch buffer
vLLM block manager / paged attention metadata
量化反量化临时 buffer
```

## 三、LoRA 在训练时改变了什么

LoRA 的核心做法是：冻结原始权重 `W`，只训练一个低秩增量：

```text
W' = W + ΔW
ΔW = B × A
```

其中：

```text
W: 原始大矩阵，冻结
A: 小矩阵，可训练
B: 小矩阵，可训练
```

假设原始线性层是：

```text
W ∈ R^{d_out × d_in}
```

原始全参数训练需要训练：

```text
d_out × d_in
```

个参数。

LoRA 只训练：

```text
A ∈ R^{r × d_in}
B ∈ R^{d_out × r}
```

参数量变成：

```text
r × d_in + d_out × r
= r × (d_in + d_out)
```

当 `r` 很小，比如 8、16、32 时，LoRA 参数量远小于原始矩阵。

### LoRA 训练时减少的显存

LoRA 明显减少：

```text
可训练参数量
梯度显存
优化器状态显存
部分分布式训练通信量
checkpoint 保存大小
```

尤其是梯度和优化器状态。

比如原来一个大矩阵 `W` 要保存：

```text
W 的梯度
W 的 Adam m
W 的 Adam v
```

用了 LoRA 后，`W` 冻结，只需要保存：

```text
A 的梯度
B 的梯度
A 的 Adam m/v
B 的 Adam m/v
```

这就是 LoRA 训练省显存的根本原因。

### LoRA 训练时没有明显减少的显存

LoRA 不会等比例减少：

```text
base model 权重显存
activation 显存
attention 临时计算显存
KV cache，若用于推理
runtime workspace
```

原因是，虽然 base model 冻结，但前向传播仍然要完整经过 base model。

训练时为了更新 LoRA 参数，也仍然需要反向传播穿过相关路径，所以中间激活仍然要保留。

所以 LoRA 不是把训练显存直接从“全参数训练的 1/100”变成那么小，它主要省的是：

```text
梯度 + 优化器状态
```

不是把整个模型计算图都变小。
