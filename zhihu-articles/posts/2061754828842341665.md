**今日碎碎念**

vLLM v0.25.0 的发布说明里，出现了一句很容易让人误解的话：

> PagedAttention has been removed.

翻译过来就是：PagedAttention 已被移除。

如果只看到这里，很容易得出一个挺吓人的结论：vLLM 当年最出圈的核心技术，难道被自己放弃了？那篇引用量很高的 PagedAttention 论文，难道已经跟不上时代了？

其实并没有，**vLLM删除的是旧的、独立的 PagedAttention CUDA Kernel 和调用入口，并没有删除分页式管理 KV Cache 的思想。**

恰恰相反，`block table`、`slot mapping`、按块分配、前缀缓存这些机制都还在，而且已经下沉到了 vLLM 新架构的基础设施里。以前它是一个名字响亮的独立实现，现在它变成了多个 Attention Backend 共同依赖的底层能力

说白了，拆掉的是老发动机，不是把“汽车用轮子”这个思路也一起扔了

## PagedAttention，一个名字里其实装了两件事

大家如果平时关注大模型推理，应该都听过PagedAttention。

LLM每生成1geToken，都要保存此前Token的Key和Value，也就是KV Cache。请求越长，KV Cache越大；而在线服务中的请求长度又各不相同，有的很快结束，有的会一直生成。

如果给每个请求预留一整块连续显存，会产生两个问题：

- • 预留多了，大量显存用不上；
- • 预留少了，后面扩容和搬运又很麻烦。

PagedAttention借用了操作系统虚拟内存的思路：把KV Cache切成固定大小的块，逻辑上连续的一段上下文，可以分散存放在不同的物理块里，再通过一张块表完成映射

比如某个请求的逻辑块顺序是`0、1、2、3`，实际可能存放在显存块`7、19、4、31`中。模型不需要关心物理块是否连续，只要沿着块表找到对应位置即可

这套设计减少了显存碎片，也让不同请求共享相同的前缀块成为可能

但这里有个特别容易混淆的地方：大家平时说“PagedAttention”，可能同时在说两件事

第二件事是**vLLM早期为这种布局专门编写的CUDA Kernel**，也就是代码里的`paged_attention_v1`和`paged_attention_v2`。

v0.25.0删除的是第二件事，而不是第一件事。

## 那个只有一句“It is time”的删除PR

这次改动对应官方PR#47361，标题非常直接：

> Delete PagedAttention

PR说明里的Purpose更短，只有一句：

> It is time.

颇有一种“是时候送老伙计退休了”的感觉。

从代码差异看，这个PR删除了三份核心CUDA文件：

- •`attention_kernels.cuh`：667行；
- •`paged_attention_v1.cu`：190行；
- •`paged_attention_v2.cu`：202行。

与此同时，CMake中的编译入口、Torch Op注册、Python包装函数和相关测试也被一起移除。

旧版本中的调用链大致是这样的：

```text
Python层 paged_attention_v1/v2
    ↓
torch.ops._C.paged_attention_v1/v2
    ↓
独立的CUDA PagedAttention Kernel

```

比如v0.24.0的`vllm/_custom_ops.py`中，还能看到这样的包装：

```text
defpaged_attention_v1(...):
  torch.ops._C.paged_attention_v1(...)

defpaged_attention_v2(...):
  torch.ops._C.paged_attention_v2(...)

```

到了v0.25.0，这两个Python函数、Torch绑定和底层CUDA实现都没有了。

所以，如果有人说“旧的独立 PagedAttention 实现被删除了”，这是准确的。但如果进一步说“vLLM已经不用分页KV Cache了”，那就完全是另一回事。

这里还要补一个边界：PR没有彻底删除所有平台上带`paged_attention`名字的代码。ROCm侧的`paged_attention_rocm`仍然存在，只是Benchmark已经改成ROCm专用，并明确提示：它默认不再用于vLLM推理。

更准确的说法应该是：**旧CUDA路径中的`paged_attention_v1/v2`被移除，ROCm遗留实现暂时保留，但主流执行路径已经转向新的Attention Backend。**

## 名字没了，块表还在

判断一种架构思想是否消失，不能只搜索它的名字，更应该看数据是怎么组织和流动的。

我们直接看v0.25.0的官方代码。

在`vllm/v1/worker/gpu/block_table.py`中，`BlockTables`仍然存在。它为不同KV Cache Group维护块表，形状依旧是“请求数 × 每个请求可用的最大块数”。

代码里同时保留了`slot_mappings`，用来告诉系统：当前Token的KV到底应该写到物理缓存中的哪个位置。

最能说明问题的是`_compute_slot_mappings_kernel`中的寻址逻辑：

```text
block_indices = positions // block_size
block_offsets = positions % block_size

block_numbers = block_table[request, block_indices]
slot_ids = block_numbers * block_size + block_offsets

```

实际代码还处理了Context Parallelism，但最核心的逻辑就是这四步。

说白了：

1. 1. 根据Token位置算出它属于第几个逻辑块；
2. 2. 从块表查出这个逻辑块对应哪个物理块；
3. 3. 算出Token在块内的偏移；
4. 4. 得到KV Cache中的物理slot。

这不就是PagedAttention最核心的分页寻址思想吗？它不但没消失，甚至已经成为独立于某个具体Attention Kernel的数据组织层。

## KV Cache Manager也没闲着

继续往上看，`KVCacheManager`仍然通过`allocate_slots()`给请求分配新的缓存块。

而且今天的情况比早期复杂得多。这个分配过程不只需要处理普通Token，还要同时考虑：

- • Prefix Cache命中的块；
- • Sliding Window淘汰；
- • 推测解码的Lookahead Token；
- • Prefill/Decode分离中的KV传输；
- • 外部KV Connector返回的缓存；
- • 多种KV Cache Group。

这也是为什么旧的专用Kernel会逐渐显得不够合适。PagedAttention最初解决的是“如何在不连续物理块上高效计算Attention”，但现代vLLM需要解决的已经是整套KV Cache生命周期问题。

它不再只是一个Kernel能包办的事情。

## 真正改变的是：计算交给了新的Backend

在v0.25.0中，分页式KV布局由内存管理层负责，而具体Attention计算交给FlashAttention、Triton等Backend。

例如`flash_attn.py`的Metadata里仍然明确包含：

```text
block_table: torch.Tensor
slot_mapping: torch.Tensor

```

执行Attention时，`block_table`会继续传给FlashAttention调用

在`triton_attn.py`中也是一样：Triton Unified Attention接收`block_table`，写入KV Cache时则使用`slot_mapping`。

新的调用关系更接近这样：

```text
Scheduler / KVCacheManager
    ↓ 分配物理块
BlockTables
    ↓ 生成 block_table 与 slot_mapping
Attention Backend
    ├─ FlashAttention
    ├─ Triton Unified Attention
    └─ 其他平台或模型专用Backend

```

这次变化的重点，是把“缓存如何分页管理”和“Attention如何计算”拆开了

以前，PagedAttention既代表内存布局，也代表一套专用计算Kernel。现在，分页布局成为公共协议，不同高性能Backend可以在这套布局上各自完成计算。

这是一种架构解耦。

## 为什么vLLM现在才删？

官方发布说明给出的理由很简洁：V1和Model Runner V2已经成为标准路径，因此可以删除Legacy Attention Implementation

这里也要避免一个名字陷阱：发布说明中的“V1/MRv2”，指的是vLLM当前的引擎与Model Runner架构；而被删除的`paged_attention_v1/v2`，是两种旧Kernel入口. 两组“V1/V2”不是一回事。

从工程角度看，删除旧实现有几个很现实的好处。

首先是减少重复维护。同一套系统里如果同时存在旧专用Kernel、FlashAttention、Triton和各种硬件后端，每增加一种数据类型、模型结构或并行策略，都可能需要同时适配多条路径。

其次是让职责更清晰。KV Cache Manager负责内存生命周期，BlockTables负责寻址，Attention Backend负责计算。以后替换Kernel，不需要推翻整个缓存管理体系。

最后是适应今天更复杂的模型。MLA、Sliding Window、混合Attention、量化KV Cache、推测解码和多模态前缀，都在不断改变推理系统的需求。把所有逻辑捆在一个“PagedAttention Kernel”中，反而会限制演进。

所以，这次删除更像一次代码库收敛，而不是技术路线反转。

## 官方文档其实已经给出了暗示

有意思的是，vLLM仓库中的`docs/design/paged_attention.md`并没有被删除。

不过文档顶部加了一段很醒目的警告：

> This is a historical document based on the original paper for vLLM. It no longer describes the code used in vLLM today.

也就是说，这份文档现在被明确定位成“历史资料”：它仍然适合理解原始PagedAttention Kernel，但已经不能代表今天vLLM的真实执行路径.

这句话其实比“PagedAttention has been removed”更准确

原始Kernel成为历史，分页KV Cache则继续活在新架构里.

## 升级v0.25.0，谁需要注意？

如果你只是通过OpenAI兼容接口使用vLLM，或者正常启动服务，大概率不用因为这次删除做任何事情。分页KV Cache依旧由系统自动管理。

真正需要检查的是下面几类项目。

### 1. 直接调用旧Custom Op的代码

如果你调用过：

```text
ops.paged_attention_v1(...)
ops.paged_attention_v2(...)

```

升级后这些接口已经不存在，需要迁移到当前Attention Backend或者Unified Attention路径

### 2. 基于旧Kernel修改的研究代码

如果你的项目直接修改`paged_attention_v1.cu`、`paged_attention_v2.cu`，或者用旧Benchmark测试Kernel，v0.25.0会直接影响你。

新的Benchmark在这一PR中已收缩为ROCm Paged Attention测试，而且明确说明它默认不再用于vLLM推理

### 3. 通过函数名阅读源码的人

以后想理解vLLM的“PagedAttention”，不能只搜索`paged_attention`。

更有效的入口是：

- •`KVCacheManager`：看块如何分配、释放和复用
- •`BlockTables`：看逻辑块如何映射到物理块
- •`slot_mapping`：看Token的KV写到哪里
- • Attention Backend：看FlashAttention或Triton如何消费分页布局

技术的名字变了，但数据结构会告诉你它到底还在不在。

## PagedAttention最成功的结局，是不再需要一个独立的PagedAttention

看到一项著名技术的同名实现被删除，第一反应往往是“它过时了”。

但在大型系统里，还有另一种可能：它已经成功到不再需要以独立模块存在

最早的PagedAttention需要同时证明两件事：分页式KV Cache值得做，以及在不连续物理块上也能高效计算Attention

现在第一件事已经成为vLLM的默认基础设施，第二件事则可以交给更成熟、更多样的Attention Backend。

所以，v0.25.0移除旧PagedAttention，不是把论文扔进废纸篓，而是把论文中的核心思想拆开、下沉，再融入新的系统架构。

以后再看到某个著名类名或函数名被删除，先别急着宣布一个时代结束

顺着数据结构和调用链往下看。很多时候，名字退出舞台，恰恰是因为它已经变成了舞台本身。
