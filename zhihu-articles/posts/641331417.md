在前面谈及 GPU 的诸多文章中，有没有发现一个现象：GPU 好像都倚赖 CPU 给它发指令？这是因为 CPU 的指令既可以用于**计算**，也可以做自身的逻辑**控制**，而 GPU 的指令只能用于芯片内部的计算，所以其逻辑控制需要借助 CPU 来完成。

可以说，GPU 就是一个没有感情的计算机器，不会“独立思考”。这大概可以解释为什么 GPU 内一个 kernel 调用另一个 kernel 的功能直到 CUDA-5 才开始实现，为什么其内存管理都要 CPU 侧的程序来帮忙。

在笔者刚接触 GPU 的时候，[曾畅想过 GPU 是否能自己运行 OS](https://zhuanlan.zhihu.com/p/550525823)，不再依附 CPU。现在回过头来看，术业有专攻，让 GPU 发挥它算力的长处就好。

但是 OS 的基本功能它还是应该具备，什么算是 OS 最基础的功能？一是**内存管理**，一是**任务调度**。内存这块之前已经介绍过了，那再来看看 GPU 的调度。

以 Linux 系统为例，对于 CPU 的调度，不管是采用 [RT 还是 CFS](https://zhuanlan.zhihu.com/p/124118220) 策略，OS 都会为每个 core 维护一个（或一组）runqueue，然后 rq 上的线程送到 CPU 执行。因为 OS 本身是在 CPU 上执行的，可以说是“自己调度自己”。

那 GPU 调度呢，也是有一些 runqueue，由 driver 喂给 GPU 执行。因为 driver 是在 CPU 上执行的的，所以GPU 是“被调度”的。

具体怎么个喂法？

## Get to work, you lazy core

在多核 CPU 中，有多个 core，但就单 core 而言，虽然内部有流水线，但对指令的执行是串行的（某一时刻只能执行某条指令），而 GPU 这种高度并行的结构是一个 engine 包含多个 hardware queues。

这种差异也体现在页表上，单 core 的「页表基址寄存器」通常只有一个（x86 的 CR3）或两个（arm 的 TTBR0/TTBR1），而 GPU engine 的 TTBR 是数组形式的。

那么作为 GPU scheduler，就是要以一定的调度策略，把 CPU 发来的指令，以一定的顺序送到 GPU 的 HW queue 上执行。

![](https://pic4.zhimg.com/v2-a62581f530f0ceade6937163a3687bdf_r.jpg)

给 GPU 的指令主要做两件事：**memory copy** 和 **kernel launch**（再次说一下，此 kernel 非 Linux kernel，unfortunate terminology）。这里分别记作 Cx 和 Kx，其中 Ci 代表 Copy In（即 host-to-device）和 Copy Out（即 device-to-host）。

![](https://picx.zhimg.com/v2-178dab9a18e62dc455b4e1134e25361b_r.jpg)

指令被 CPU 组装好后，先放到 software queue 里（CUDA stream），其中的 "copy operation" 被分拣到 CE queue，而 "kernel launch" 被分拣到 EE queue，最后分别被 GPU 的 CE (Copy Engine) 和 EE (Execution Engine) 处理。

举个简单的示例，NVIDIA 的 Fermi 架构（纪念物理学家费米）有 1 个 EE queue，2 个 CE queue，其中一个 CE 用于 Host 向 Device 方向的 DMA 拷贝（H2D），另一个 CE 用于 Host 向 Device 方向的 DMA 拷贝（D2H）。

这是符合 [GPU 的传统工作原理](https://zhuanlan.zhihu.com/p/640161668)的：先拷贝 host memory 到 GPU 侧的 device memory，然后 GPU 执行 kernel，并返回结果到 CPU 侧的 host memory。

![](https://pic3.zhimg.com/v2-87a31d3794be39480f72823c18ae3a50_r.jpg)

对于没有依赖的数据拷贝和 kernel 操作，还可以同时进行，以节约总体的执行时间（有点像 CPU 的“取指->译码->执行”的 pipeline）。

![](https://picx.zhimg.com/v2-601f6b14dda13b19c58296ba4bfc0cbf_r.jpg)

原理大概就是这么个原理，那在 OS driver 中，具体该怎么实现这样的调度呢？下面以 Linux 内核 v5.4 为例，探讨下整个流程运转的细节。

## The devil is in the details

说到 GPU 的 Linux driver，就不得不提 DRM (Direct Rendering Manager)，它是一个专为 GPU 内存管理和调度设计的模块，被 AMD, Nvidia 等 GPU 的 Linux 驱动程序广泛使用。

在 DRM 中，CPU 的封装指令以 "job" 的形式存在，围绕“把 job 送入 HW queue”上执行的目标，来看看我们都需要哪些结构。

job 是有优先级的，所以一个 HW queue 应该对应多个不同优先级的 **runqueue**（由结构体 "drm_gpu_rq" 表示），然后由一个内核线程作为 **scheduler**（由结构体 "drm_gpu_scheduler" 表示），按照优先级去循环遍历，选取 job。

```go
struct drm_gpu_scheduler {
    /* priority wise array of run queues. */
    struct drm_sched_rq  sched_rq[DRM_SCHED_PRIORITY_COUNT];
    /* the kthread on which the scheduler which run */
    struct task_struct  *thread;
    /* the number of jobs in queue in the scheduler */
   atomic_t  num_jobs;
    ...
}

struct drm_sched_rq {
    /* the scheduler to which this rq belongs to */
    struct drm_gpu_scheduler *sched;
    /* list of the entities to be scheduled */
    struct list_head  entities;  
    ...
};

```

CPU 上往往有多个程序都在向同一 HW queue 发指令（比如都要借助 D2H queue 去做拷贝），如何平衡对 HW queue 资源的使用？

![](https://pic4.zhimg.com/v2-35f864de0e520cbc5fb352735034c101_r.jpg)

这就有了 **entity**的概念，同一优先级的不同程序的 job，放在一个 runqueue 链表的不同 entity 里。

![](https://pic3.zhimg.com/v2-685773633dd65bd5ce542d5d2ca9110c_r.jpg)

至此，调度的雏形算是基本建立起来了，颇为类似 Linux 内核曾经使用过的 [O(1) 调度器](https://zhuanlan.zhihu.com/p/124118220)对不对（不过没有 Active Runqueue 和 Expired Runqueue 的区别）。

与 Linux 的 [workqueue 机制](https://zhuanlan.zhihu.com/p/91106844)也有几分相像，job 就相当于 work，scheduler 就相当于 worker，而 entity 和 runqueue 的角色可类比 [pwq](https://zhuanlan.zhihu.com/p/94561631)，都是把 job/work 送给 scheduler/worker（最终分别是 GPU/CPU 执行）的中间媒介。

### 良禽择木而栖

对于一个有追求的调度器，还应该思考下「负载均衡」的问题吧。GPU 中某一类的 HW queue 可能不止一个，它们能完成的功能是一样的，job 放其中任何一个执行都可以。

```c
struct drm_sched_entity {
    /* runqueue on which this entity is currently scheduled */
    struct drm_sched_rq  *rq;
    /* a list of run queues on which jobs from this entity can be scheduled */
    struct drm_sched_rq  **rq_list;
    /* the list of jobs of this entity */
    struct spsc_queue  job_queue;
    ...
}
```

假设 GPU 有 2 个 D2H 方向的 DMA queue，那么优先级为 0 的 [potential runqueue](https://github.com/torvalds/linux/commit/ac0a6cf1c6ef) 就有 2 个。站在 load balance 的角度，一个优先级也为 0 的 entity（包括其中的 job），应该选择 load 更小的那个（依据是 scheduler [既有的 jobs 数量](https://github.com/torvalds/linux/commit/249a07c05a8d)）。

```cpp
drm_sched_entity_select_rq() --> drm_sched_entity_get_free_sched()  // 依据 sched->num_jobs

```

entity 只是手段，job 才是目的，所以选择 runqueue（其实是选择 HW queue），是在 job 准备进入 HW queue 执行时才确定的。

![](https://picx.zhimg.com/v2-30665b2b4708fb48a396559c50a33e4b_r.jpg)

不过 entity 切换 runqueue 是有条件的，即在新的 job 加入之前，该 entity 内部为空，且 entity 送入 HW queue 的 job 都已执行完毕。为什么会有这样的限制，以及如何判断 job 已执行完呢？

## Issue order matters

在图形应用中，GPU 的作用一个是渲染（rendering），一个是输出显示（scanout），且渲染完才能显示到屏幕上。这就要求对于同一 framebuffer，渲染 job 和显示 job 需要建立一个依赖关系。

有执行顺序的依赖怎么办，用同步手段对不对。DRM 里采用的是 **dma fence**机制，每个 job 有两个 fence：表示 job 已经进入 HW queue 的 "scheduled fence"，和表示 job 已完成执行的 "finished fence"。

```c
struct drm_sched_job {
    /* append this struct to the queue of jobs in an entity */
    struct spsc_node  queue_node;
    /* contains the fences for the scheduling of job */
    struct drm_sched_fence  *s_fence;
    ...
}

/* fences corresponding to the scheduling of a job */
struct drm_sched_fence {
    /* signaled by the scheduler when the job is scheduled */
    struct dma_fence  scheduled;
    /* signaled by the scheduler when the job is completed */
    struct dma_fence  finished;
    ...
} 
```

drm_sched_entity 中的 job 是通过单向链表连接的，这保证了 J1 一定在 J2 之前进入 HW queue（J 代表 Job），而 HW queue 是 FIFO queue，所以先进去的 job 会先执行。

![](https://pic4.zhimg.com/v2-3ed973d6aaca16dbf50efeb13c2fc4a7_r.jpg)

所以，假设属于同一 entity 的 J2 依赖于 J1，属于同一 runqueue 的 J1 又依赖 J3，那么在 HW queue 没满的情况下，J3 发出 scheduled fence 后，J1 就可以送入 HW queue 了。

J4 依赖于 J8，它们属于不同的 HW queue，两者可能并行，所以 J4 需要等待 J8 发出 finished fence 后才可以送入 HW queue。

回到之前的问题，只有确保 entity 之前的 job 都已执行完毕，新进入 entity 的 job，才不会因为 runqueue 的切换造成有依赖 job 的并行执行。

```c
amdgpu_job_submit() --> 
drm_sched_job_init(job) --> drm_sched_entity_select_rq(entity)  // 选择 runqueue
drm_sched_entity_push_job(job, entity) --> spsc_queue_push()   // 将 job 加入 entity 链表
```

把 job 放入 HW queue 是 scheduler 做的，属于软件层自己的行为，所以 scheduled fence 可由软件控制。而 job 完成通常需要硬件发送中断告知，所以 finished fence 取决于硬件（此处可对比 Linux workqueue 中软件实现的 [barrier work](https://zhuanlan.zhihu.com/p/648984958)）。

如果出现了 hardware fault，那 job 就可能完不成，因此 scheduler 在送入 job 后，会设置一个 timeout，超时之后尝试通过 reset 等方式来解决。

## 门当户对

CPU 指导 GPU 进行调度的流程，其实也可以套用[“等待 - 唤醒”模型](https://zhuanlan.zhihu.com/p/97107297)，但同 waker/waiter 都是在 CPU 上运行的进程不同（比如 [fanotify 机制](https://zhuanlan.zhihu.com/p/186027813)），GPU 调度中参与的双方是 CPU 和 GPU 这两种异构的处理器，因此需要硬件的参与。

打个比方，CPU + GPU 的组合就像一辆马车，CPU 是前面的马，而 GPU 是后面的车辇。马可以单独跑，也可以拉着车跑，而车虽然有轮子，却不能自己跑。

如果 GPU 的能力较强，而与之配合的 CPU 较弱，那么就像“小马拉大车”，面对 GPU 发过来的密集中断，CPU 这边别说 bottom half 处理不过来，甚至可能连 top half 都招架不住。车辇再豪华，用瘦马来拉也是白瞎。
