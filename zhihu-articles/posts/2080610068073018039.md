## 从提示词工程到 Harness：为什么”怎么说”已经不够了

> Harness 工程系列 · 第 1 篇 系列主线：模型越来越强，但真正决定 Agent 靠不靠谱的，是模型外面那层东西。

### 一个让 CI 变绿的”聪明”办法

先讲个很多团队都遇到过的事。

你给一个 coding agent 派了个活：改个 bug，跑通测试再提交。然后你去开会了。三个小时后回来，CI 全绿，PR 已经躺好了。你大喜过望，点开 diff 一看——它把挂掉的测试用例删了。

测试没了，CI 自然就绿了。从字面上看，它完成了你交代的”让 CI 变绿”；从任何正常人的标准看，这叫糊弄。

有意思的是，这事真不能全怪模型”笨”。换个更强的模型，它可能不删测试了，改去注释掉断言；再换一个，它学会给 flaky test 加重试。问题出在另一个地方： **这是一个会自己动手的系统，而你除了最初那句交代之外，什么都没有管。**

过去三年，整个行业的精力都花在”怎么跟模型说话”上。但 Agent 时代的问题悄悄换了： **怎么管住一个会自己动手的系统。**

这就是这个系列要讲的东西——harness 工程。四篇的安排是：演进史（本篇）→ 工程体系拆解 → 各家对比 → 动手做一个Agent（视情况而定）。

### 第一幕：提示词工程（2023）——”怎么说”

2023 年 ChatGPT 引爆之后，”提示词工程”成了显学。Karpathy 有句话说得很传神：

> “The hottest new programming language is English.” （最火的新编程语言是英语。）

这话当时一点不夸张。为什么那时候全行业只研究”说”？看看当时的模型就明白了：GPT-4 是个纯粹的对话选手——单轮、无状态、上下文窗口只有 4k 到 32k，不会调任何工具，用完即走。你手上唯一能拧动的旋钮，就是输入框里那段话。

这里有个贯穿全篇的规律，先记住它： **每一代范式都不是谁拍脑袋发明的，是被当时的模型能力逼出来的。**

那时候用模型的方式是典型的”一问一答”：你写一段话，它回一段话。输出不好，就换种说法再问一遍。于是大家研究角色设定（”你是一位资深工程师”）、few-shot（给它几个例子照猫画虎）、思维链（”让我们一步一步思考”）。这些技巧的本质都一样： **把任务说清楚。**

提示词工程有个很少被点破的隐含假设： **人在回路里兜底** 。模型输出错了，你一眼就看出来，改改措辞重来。反正它一次只说一段话，最坏的情况无非是这段话没用。

这个假设在 2023 年完全成立，因为模型除了说话什么也干不了。

### 第二幕：上下文工程（2025）——”看到什么”

然后模型变了。2024 到 2025 年，上下文窗口从 32k 一路涨到百万 token 级别，function calling 成了标配，2024 年底 Anthropic 推出 MCP 把工具调用接口统一了——模型第一次能稳定地”看到”外部世界、并伸手去操作它。配合成熟的 RAG，一个新的核心矛盾浮出来：窗口这么大、能塞的东西这么多， **到底该给它看什么？**

2025 年，Shopify 的 CEO Tobi Lütke 说了另一句广为流传的话：

> “Context engineering describes the core skill much better.” （”上下文工程”这个词更好地描述了核心技能。）

关注点从”怎么说”挪到了”看到什么”：往上下文里放哪些文档、代码怎么检索、历史对话怎么压缩、工具返回的一大坨结果怎么取舍。本质是让模型 **看到对的信息** ——垃圾进垃圾出，喂错材料，再强的模型也只能一本正经地胡说。

这是实打实的进步。但如果你盯着它看一会儿，会发现有一串问题它一个都答不上来：

- 模型 **采取了一个行动** （改了文件、发了请求、删了数据），谁来验证这个行动是对的？
- 模型犯了错，系统怎么 **自动纠正** ，而不是干等人介入？
- 模型在循环里跑几个小时，谁防止它 **死循环** 、防止它越界去动不该动的东西？
- 一切正常的时候，谁在 **记录** ？出了事要复盘，日志在哪？

注意，这四个问题没有一个能靠”把话说得更好”或者”把材料喂得更准”来解决。它们全是 **行为问题** ，不是输入问题。开篇那个删测试的 agent，上下文装配得再完美，该删还是删。

### 第三幕：Harness 工程（2026）——”怎么控”

### 命名时刻

这个词的诞生时间点精确得有点罕见。

**2026 年 2 月 5 日** ，Mitchell Hashimoto——HashiCorp 联合创始人、Terraform 的作者，现在在做 Ghostty 终端——发了一篇博客《My AI Adoption Journey》。他写了自己采纳 AI 的五个阶段，在最后一个阶段提出了 **harness engineering** ：

> “Anytime you find an agent makes a mistake, you take the time to engineer a solution such that the agent never makes that mistake again.” （每次发现 agent 犯了错，就花时间工程化一个方案，让它从此不再犯同样的错。）

这句话值得读两遍。注意他说的不是”每次犯错就提醒一下模型”，而是 **工程化一个方案** ——把教训变成系统结构的一部分。他自己的 Ghostty 项目就是最好的例子：项目里那份给 agent 看的 AGENTS.md， **每一行规则背后都对应一次真实的 agent 事故** 。规则不是坐下来拍脑袋写的，是一次次翻车之后长出来的。这个”事故驱动”的思路，我们后面几篇会反复回到它。

**6 天后，2 月 11 日** ，OpenAI 工程团队的 Ryan Lopopolo 发了官方博客，标题就叫《Harness engineering: leveraging Codex in an agent-first world》。这篇文章给了一组相当夸张的数字：一个 3 到 7 人的团队，5 个月， **0 行手写代码** ，产出了约 100 万行代码、约 1500 个 PR——平均每人每天 3.5 个 PR。以及一句很快传开的金句：

> “Agents aren’t hard; the Harness is hard.” （Agent 不难，难的是 Harness。）

**随后几周** ，Martin Fowler 的站点上，Birgitta Böckeler 的长文把这件事理论化了：harness 是 agent 中 **除模型本身之外的一切** ——工具、护栏、反馈回路、编排逻辑、可观测性。

从个人命名到官方定义再到理论框架，前后不到一个月。这可能是 AI 领域”从概念到共识”收敛得最快的一次。这不是巧合：Agent 一进生产环境，”怎么管好它”的问题必然浮上来，大家只是在等一个人先说出那个词。

### 一个公式，一个比喻

OpenAI 给了一个特别简洁的公式（后来 DeepSeek 开源自家 harness 时原样沿用）：

![](https://picx.zhimg.com/v2-21942c1dfcd7d5703addfc18b8d92b3d_r.jpg)

而 harness 这个单词，直译过来是 **马具** ——缰绳、鞍具、轭，那一整套东西。

![](https://pica.zhimg.com/v2-b573fd34b2e264f894e275ef61ade5c2_r.jpg)

这个比喻好就好在它足够诚实：力气是马出的，但没有马具，它不拉车，甚至往哪儿跑都不归你管——看图，马具把蛮力变成了那车货。模型再强，没有外面那层结构，它就只是一个很会说、偶尔乱动的黑盒，产不出一个 **可靠的系统** 。你的工作是当那个造马具的人，而不是站在马旁边喊话的人。

### 为什么是现在？

harness 工程为什么不在 2023 年出现？因为三个条件 2026 年才凑齐：

1. **模型能力到了。** 推理模型（o1、R1 这一代）把”持续想问题”的耐力提了上来，Claude Code、Codex 这类产品则让 agent 第一次能连续几小时自主干活——自主性一上来，”驾驭”就从修辞变成了刚需。2023 年的模型连一步都走不稳，那时候它不需要缰绳，需要拐棍。
2. **对话形态变了。** 从一问一答变成持续数小时的自主循环，人不可能每一步都盯着——盯着的那个也不叫 Agent，叫远程遥控。
3. **长上下文是双刃剑。** 上下文越长，agent 能做的事越多，错误行为的影响面也越大。提示词级别的约束（”请不要删测试”）管不住了，需要系统级别的约束（让 agent 根本 **没有权限** 删测试）。

### 先澄清一下：harness 这个词有三层含义

在你带着这个词去别处之前，有个坑得先填上。”harness”在这些年其实被用在三个不同的场景里，面试和读文章时经常被混着用：

1. **测试 harness（test harness）** ：软件工程的老词，指跑测试的一套脚手架——mock、桩件、驱动器。
2. **评测 harness（eval harness）** ：跑 benchmark 的测试床，比如著名的 lm-evaluation-harness。输入题目，收答案，算分。
3. **Agent harness（运行时 harness）** ：2026 年语境下的主角——agent 运行时除模型外的一切，工具、护栏、循环控制、反馈回路都在这里面。

三者有个共同点：都是”包住某个东西、让它能被使用/测量的外层结构”。区别在 **阶段** ：评测 harness 发生在上线前，回答”这个模型行不行”；agent harness 发生在运行时，回答”这个系统靠不靠谱”。本系列（以及现在大多数讨论 harness 的文章）说的都是第三层。前两层的分工我们到第 2 篇讲评估时再展开。

### 三代范式，一张表收束

| 维度 | 提示词工程 (2023) | 上下文工程 (2025) | Harness 工程 (2026) |
| --- | --- | --- | --- |
| 模型侧背景 | 对话式单轮、4k–32k 窗口、无工具 | 百万级长窗口、function calling、MCP | 推理模型、数小时自主任务 |
| 核心问题 | 怎么说 | 看到什么 | 怎么控 |
| 作用对象 | 单轮输出 | 输入内容 | 整个系统的行为 |
| 纠错方式 | 改措辞，重试 | 换检索、换材料 | 结构性修复，同类错误永不再犯 |
| 人的角色 | 提问者 + 兜底 | 信息策展人 | 环境设计者 |
| 类比 | 跟新员工交代任务 | 给新员工备好资料 | 给新员工建流程、权限和考核 |

最后一行的类比是我觉得最好用的直觉：三代的演进，其实就是把 agent 从”临时工”当”正式员工”管的过程。

还有一个关键澄清： **这三代不是谁杀死谁的关系，是包含关系** 。提示词工程没有死——它降级成了 harness 里最便宜、最便携的一个组件。你今天写的每一句系统提示词依然重要，只是它不再是故事的主角。上下文工程同理：它是 harness 的一条输入管道。Hashimoto 那句”工程化一个方案”里，改提示词只是可选方案之一，而且往往是最不牢靠的那个。

### 什么时候才需要 Harness？

话说回来，也别贩卖焦虑。不是所有场景都需要这套东西，给单层对话套上 harness 属于过度工程。一个简单的自查清单：

- **单轮问答，人盯着输出** → 不需要。提示词工程足矣。
- **多轮、但每一步都由人确认** → 不太需要，上下文工程管好输入质量就行。
- **多步工具调用，有真实副作用** （写代码、发请求、动数据）→ 需要了，至少要有护栏和反馈回路。
- **无人值守跑长任务** （过夜、几小时）→ 非常需要，而且可观测性必须跟上，否则出了事你连它怎么死的都不知道。

一句话判断： **只要 agent 的行动有了你承受不起的副作用，harness 就是必需品，不是锦上添花。**

### 小结与下篇预告

这篇讲了三件事：harness 工程是 2026 年 2 月被命名的，解决的是”怎么管住会自己动手的系统”；它用公式表达就是 Agent = Model + Harness，模型外面那层工具、护栏、反馈回路、循环控制的总和；它和前两代是包含关系，不是替代关系。

用 OpenAI 那篇博客的定义收尾：工程师的核心工作，正在从”写代码”变成 **设计环境、明确意图、构建反馈回路** 。

那这套”马具”具体由哪些零件组成？每个零件长什么样、不管它会出什么事故、主流产品各怎么实现？第 2 篇我们按一次 agent 循环的完整链路——上下文装配、模型调用、动作执行、反馈验证、循环控制、观测评估——逐个拆开看。

### 面试可能怎么问

**基础题**

**Q1：Harness 工程和提示词工程的本质区别是什么？** 提示词工程影响的是 **单次输出** ，手段是措辞；harness 工程约束的是 **系统行为** ，手段是结构。前者的失败模式是”这次回答不好”，后者的失败模式是”系统持续做坏事”。举例：让 agent 别删测试，提示词是”请不要删测试”，harness 是”测试目录设为只读 + 提交前强制跑全量测试”——前者是请求，后者是结构。

**Q2：为什么说 “Agents aren’t hard; the Harness is hard”？** 因为模型能力在快速商品化——GPT、Claude、DeepSeek 都能用 API 调，谁也垄断不了。真正的差异化在模型外面：环境怎么设计、反馈回路怎么搭、约束体系怎么随事故演化。同一个模型，裸跑是玩具，配上好 harness 才是生产系统。

**进阶题**

**Q3：反馈回路具体怎么设计？什么信号才有资格当”反馈”？** 关键是找 **可执行的、客观的、快的** 信号。Martin Fowler 站点那篇长文把质量门禁比作”传感器”：编译器报错、测试失败、linter 告警，都是模型没法狡辩的硬信号——它可以说”我改好了”，但测试红了就是红了。反面教材是把”模型自查一遍”当反馈回路，那等于让考生自己批自己的卷子。设计原则：反馈信号必须来自模型之外，且能在秒内返回。

**Q4：规则写在 AGENTS.md 里和写进 hook 里，有什么本质区别？** **概率性服从 vs 结构性不可能** 。prose（提示词、文档里的规则）是建议——模型大概率遵守，但上下文一长、任务一复杂就会”忘”；hook、权限、沙箱是强制——它不是”说服”模型不做，而是让它 **物理上做不到** 。Claude Code 的权限设计就是三层：deny > ask > allow，deny 永远赢。成熟 harness 的标志，是把越多的规则从 prose 层下沉到强制层。

**Q5：模型升级了，原来的 harness 会过时吗？** 会，而且这是个被低估的问题，可以叫 **harness 负债** 。很多规则是为弱模型写的：弱模型不会自己跑测试，你就写死”每次改完必须跑测试”；强模型本来就会主动跑，这条规则就成了束缚，甚至互相打架。所以 harness 不是建完就一劳永逸的，模型每升一代，都要回头审一遍：哪些约束可以下放给模型自己、哪些必须留在结构层。好的 harness 随模型变强而 **做减法** 。

**Q6：Agent 读了不可信的内容（比如网页、Issue、用户粘贴的文本），被提示注入了怎么办？** 这是 harness 层面的安全问题，提示词层无解。标准答案是最小权限原则：agent 默认没有高危权限；工具返回的文本一律视为 **数据而非指令** ；高危动作（发请求、删数据、推代码）必须过 ask 层或人工确认。核心思路和防 SQL 注入一脉相承： **永远不要相信拼接进来的内容，用结构隔离它。**

**Q7：评测 harness 和产品 harness 是什么关系？** 分工在阶段：评测 harness 在上线前，回答”这个模型/这个配置行不行”，产出是分数；产品 harness 在运行时，回答”这个系统现在靠不靠谱”，产出是护栏和日志。但它们共享同一套语言——很多团队会把线上事故反向沉淀成评测集，让每次生产事故都变成上线前就能拦住的新用例。这和 Hashimoto 那句”永不再犯”是同一个闭环。
