**FlashAttention 1**

Attention 的计算过程可以简单写成：

最直接的实现通常分成三个阶段：

$$$ S = \frac{QK^{\top}}{\sqrt{d}}, \qquad P = \operatorname{softmax}(S), \qquad O = PV $$$

一般来说，最直接的实现分为三个阶段，如下图所示

![](https://pic1.zhimg.com/v2-ccf665fce8a225312ac5aae9ed21e810_r.jpg)

我们知道，S和P都是N*N的矩阵，当sequence length增大时，反复在HBM中读取会造成巨大的memory traffic。为了解决这个问题，FA1诞生，下图是伪代码

![](https://pica.zhimg.com/v2-cee64f4c07799e97bb2e6bbf98d2c0fe_r.jpg)

我们可以研究一下上图算法，从具体来说，FlashAttention 会将 $Q$、$K$、$V$ 划分成多个 tile。对于一个 $Q$ tile，每次只处理一个 $K/V$ tile，并为每一行维护三个状态：

- $m$：目前见过的最大 attention score；
- $\ell$：当前所有指数权重之和，即 softmax 的分母；
- $O$：当前已经累积并归一化的输出。

当第 $j$ 个 score tile $S_j$ 到来时，首先更新每一行的最大值：

$$ m_j = \max\left( m_{j-1}, \operatorname{rowmax}(S_j) \right). $$

然后更新 softmax 的分母：

$$ \ell_j = e^{m_{j-1}-m_j}\ell_{j-1} + \operatorname{rowsum} \left( e^{S_j-m_j} \right). $$

由于最大值从 $m_{j-1}$ 更新到了 $m_j$，之前已经计算出的输出也需要转换到新的指数尺度，再与当前 tile 的结果合并：

$$ O_j = \frac{ e^{m_{j-1}-m_j}\ell_{j-1}O_{j-1} + e^{S_j-m_j}V_j }{ \ell_j }. $$

这里，$m_j$ 和 $\ell_j$ 都是按行维护的，因此在与矩阵进行运算时会沿列方向广播。

通过这种在线 softmax 更新方式，每个 score tile 在使用完成后就可以被直接覆盖。Kernel 不需要将完整的 $S$ 和 $P$ 写入显存，但最后得到的仍然是精确的 Attention 结果，而不是近似 Attention。

**FlashAttention 2**

FA1诞生后，大家发现虽然已经解决了最主要的 HBM问题，但是仍然效率不够高，原因是非矩阵乘操作太多；thread block 数量不够，GPU 没有跑满；以及warp 之间的任务划分不合理，需要频繁通过 shared memory 通信。因此FA2诞生

![](https://pic2.zhimg.com/v2-1338dae9028ceb3db5668dda7c7f5527_r.jpg)

仔细观察上图算法，主要有几处改进，

**第一项改进：推迟 O 的最终归一化**

FA1 每处理完一个 $K/V$ block，都需要使用新的 $\ell_j$ 对输出进行归一化。

FA2 发现，这个除法没有必要在每一轮中都执行。我们可以维护一个尚未除以 softmax denominator 的 output accumulator：

$$ \widetilde{O}_j = \ell_j O_j. $$

原来的输出更新公式为：

$$ O_j = \frac{ e^{m_{j-1}-m_j}\ell_{j-1}O_{j-1} + e^{S_j-m_j}V_j }{ \ell_j }. $$

将

$$ \widetilde{O}_{j-1} = \ell_{j-1}O_{j-1} $$

代入后，可以得到：

$$ \widetilde{O}_j = e^{m_{j-1}-m_j}\widetilde{O}_{j-1} + e^{S_j-m_j}V_j. $$

在所有 $K/V$ blocks 都处理完成以后，最后只需要做一次归一化：

$$ O = \frac{\widetilde{O}}{\ell}. $$

这里需要注意，FA2 并不是到最后才更新 $\ell$。每一轮仍然需要更新 running max $m$ 和 running sum $\ell$，只是将

$$ O_j = \frac{\widetilde{O}_j}{\ell_j} $$

这一步推迟到了最后。

这个改变减少了大量 FP32 除法和逐元素乘法。由于 A100 上 Tensor Core 的低精度矩阵乘吞吐量远高于普通 FP32 运算，所以即使非矩阵乘 FLOPs 在总 FLOPs 中占比不高，也可能消耗相当多的执行时间。

**第二项改进：交换 Q 和 K/V 循环，并沿 sequence length 增加并行度**

我们会发现 FA1的循环大致如下:

```python3
for K_block, V_block:
    load K_block, V_block

    for Q_block:
        load Q_block, O_block, m, l
        update O_block, m, l
        write O_block, m, l
```

也就是说， $K/V$ loop 在外层， $Q$ loop 在内层。

这样做的优点是，每个$K/V$ tile 只需要从 HBM 加载一次；但问题是，同一个 $Q、O、m、\ell$ 会随着不同的 $K/V$ blocks 被反复读写。

FA2 将循环顺序交换：

```text
for Q_block:
    load Q_block
    initialize O, m, l on chip

    for K_block, V_block:
        load K_block, V_block
        update O, m, l

    write O and L
```

现在，每个 Q tile 对应一个独立任务。不同的 Q tiles 之间不需要通信，因此可以分别交给不同的 CTAs 执行。

FA2 通过交换循环，将 Q、O 和 softmax 状态保留在片上，同时获得了 query sequence 方向的 CTA 并行度。

**第三项改进：从 split-K 改为 split-Q**

这是图中最直观的变化。

在 FA1 中，同一个 Q tile 会被所有 warps 使用，而 K/V tile 会沿 K/V 的行方向分配给不同 warps：

```text
Warp 0：处理一部分 K/V rows
Warp 1：处理一部分 K/V rows
Warp 2：处理一部分 K/V rows
Warp 3：处理一部分 K/V rows
```

这样，每个 warp 最后只能得到同一组 output rows 的一部分贡献。

在计算 PV 后，不同 warps 的 partial outputs 必须写入 shared memory，进行同步，再将这些 partial results 加起来。这就是论文所说的 split-K work partition。

FA2 将其改成了 split-Q：

```text
Warp 0：负责一部分 Q rows
Warp 1：负责另一部分 Q rows
Warp 2：负责另一部分 Q rows
Warp 3：负责另一部分 Q rows
```

K 和 V 可以被所有 warps 访问，但每个 warp 从一开始就拥有不同的 Q rows，因此也拥有最终 O 中不同的 rows。

因此，每个 warp 都可以独立完成：

$\[ Q_{\text{warp}}K^\top \longrightarrow \operatorname{softmax} \longrightarrow P_{\text{warp}}V \longrightarrow O_{\text{warp}}. \]$

不同 warps 不再产生同一行输出的 partial sums，自然也不需要通过 shared memory 进行 warp 间 reduce。

**FlashAttention 3**

到了 Hopper H100，GPU 的硬件执行模型又发生了变化，FA3在FA2上进行了升级。

Hopper 提供了两个非常重要的异步硬件路径：

- TMA 负责在 HBM 和 shared memory 之间搬运 tiles；
- WGMMA 负责异步执行 warpgroup 级矩阵乘。

TMA、Tensor Core 和普通 CUDA Cores 是不同的硬件单元。理论上，它们可以同时工作，所以从FA3开始就使用了warp specialization，将一个 CTA 内的 warps 分成不同角色。

Producer warpgroup 主要负责：

```text
使用 TMA 加载 Q、K、V
维护 circular shared-memory pipeline
通知 consumer 数据已经准备完成
```

Consumer warpgroups 主要负责：

```text
发起 QKᵀ WGMMA
执行 softmax
发起 PV WGMMA
维护 output accumulator
```

Producer 发出 TMA 指令以后，不需要自己一直等待数据搬完，而是可以继续准备后续 tiles。Consumer 则只需要在真正使用某个 shared-memory stage 前等待对应 barrier。

FA3 还使用 `setmaxnreg`，让 producer 释放不需要的 registers，再把更多 registers 分配给执行 softmax 和保存 accumulator 的 consumer warps。

但是，即使数据搬运可以与计算重叠，Attention 里面还有一条看起来很难打破的依赖：

```text
QKᵀ GEMM
   ↓
softmax
   ↓
PV GEMM
```

Softmax 必须读取 QKᵀ 的结果，PV 又必须读取 softmax 的结果，所以同一个 tile 内部确实存在顺序依赖。

FA3 的办法是跨不同 tiles 做流水，同时处理两个 Q tiles：

```text
Warpgroup 0：执行 tile 0 的 softmax
Warpgroup 1：执行 tile 1 的 GEMM
随后交换：
Warpgroup 0：执行 tile 0 的下一段 GEMM
Warpgroup 1：执行 tile 1 的 softmax
```

这就是ping-pong scheduling。

因为 exponential 由 MUFU 执行，而矩阵乘由 Tensor Core 执行，所以一个 warpgroup 运行 softmax 时，另一个 warpgroup 可以让 Tensor Core 继续执行 WGMMA。两者使用不同的硬件资源，便有机会真正重叠。

FA3 还进一步在同一个 warpgroup 内跨 K/V iterations 构造两阶段 pipeline，让当前 block 的 softmax 与其他 block 的 QKᵀ 或 PV GEMM 交错执行。

**FlashAttention 4**

到了 Blackwell，问题又发生了变化。

B200 的 BF16 Tensor Core 吞吐量相比 H100 大幅提高，但 shared-memory bandwidth、exponential unit 和普通浮点计算单元并没有以相同速度增长。

**第一项改进: 使用 TMEM 重新组织整条 Pipeline**

由于Blackwell 新增了 TMEM。`tcgen05.mma` 可以异步执行，并将 accumulator 直接写入 TMEM，而不再像 Hopper 的 WGMMA 一样主要将 accumulator 保存在 registers 中。<br><br>这使 FA4 的整体数据流变成：<br>Q、K：

```text
GMEM → SMEM → QKᵀ MMA → S in TMEM
```

计算 Softmax

```text
S：
TMEM → registers → softmax
  → P in registers
  → P in TMEM
```

计算 PV

```text
P、V：
P in TMEM + V in SMEM
  → PV MMA
  → O in TMEM
```

必要时修正输出 accumulator

```text
O：
TMEM → registers → rescale → TMEM
```

在当前教程中的 TIRx Kernel 里，一个 CTA 使用四个 warpgroups：

```text
WG0：负责 Q stage 0 的 softmax
WG1：负责 Q stage 1 的 softmax
WG2：负责 O correction 和 epilogue
WG3：发起 TMA、QKᵀ MMA、PV MMA 和 TMA store
```

其中一个重要变化，是将 output rescaling 从 softmax warpgroup 中拆分出来。

在 FA3 中，softmax、P 和 O accumulator 都与 consumer warpgroup 的 register 状态紧密绑定。而FA4 将 P 和 O 放入 TMEM 后，可以把 O rescale 交给独立的 correction warpgroup。这样，output rescaling 就可以从 softmax 的关键路径中移走，并与其他 tiles 的 MMA、softmax 和数据搬运交错执行。

**第二项改进: Conditional Softmax Rescaling**<br><br>传统 online softmax 每处理一个 K/V block，都会更新 running maximum：<br><br> $$$ m_j = \max\left( m_{j-1}, \operatorname{rowmax}(S_j) \right). $$$ <br><br>一旦最大值发生变化，旧的 denominator 和 output accumulator 都需要乘以：<br><br> $$$ e^{m_{j-1}-m_j}. $$$ <br><br>但在 FA4 中， $\(\widetilde{O}\)$ 位于 TMEM。每次 rescale 都需要执行：<br><br>TMEM → registers → multiply → TMEM

而 $\(\widetilde{O}\)$ 通常是一个完整的 $\(\widetilde{O}\)$ tile。仅仅因为最大值略微增大，就搬运并缩放整个 tile，代价很高。

FA4 的关键观察是：softmax 使用的 exponential reference 不必始终等于真实最大值。

设当前 reference 为 $r_{\mathrm{old}}$ ，候选新 reference 为 $r_c$ ，代码计算：

$\[ \delta = \left( r_{\mathrm{old}}-r_c \right) \frac{\log_2 e}{\sqrt d}. \]$

当 $\[ \delta \ge -8 \]$ 时，继续使用旧的 reference，并令：

$\[ \operatorname{acc\_scale}=1. \]$

这样就可以跳过对 $\widetilde{O}$ 的 rescale。

即使部分 exponential 的值大于 1，也不会影响结果。只要 numerator 和 denominator 始终使用相同的 exponential reference，最终归一化得到的结果仍然完全正确。

只有当：

$\[ \delta < -8 \]$

时，才更新 exponential reference，并使用：

$ \operatorname{acc\_scale} = 2^\delta $ 修正已有的 denominator $\ell$ 和 output accumulator $\widetilde{O}$ ：

$\[ \ell \leftarrow \ell\cdot\operatorname{acc\_scale} + \operatorname{rowsum}(P), \]$

$\[ \widetilde{O} \leftarrow \widetilde{O}\cdot\operatorname{acc\_scale} + PV. \]$

这项优化避免了大量不必要的 TMEM 读写，也是 FA4 forward 中最重要的改进之一。

**第三项改进：按 Warp 跳过不必要的 Correction**

softmax warpgroup 会为每一行生成 `acc_scale`，并交给负责 correction 的 WG2。WG2 中每个 warp 负责 32 行，各个 lane 先判断：

```text
should_rescale = acc_scale < 1.0
any_needs_rescale = any_sync(should_rescale)
```

如果 32 行的 `acc_scale` 全部等于 1，说明整个 warp 都不需要修正，于是可以直接跳过：

```text
TMEM 读取 O
O *= acc_scale
O 写回 TMEM
```

只有至少一行需要 rescale 时，warp 才执行这段 TMEM load-multiply-store。

需要注意，这并不是“跳过整个 correction warp”。即使无需修改 O，该 warp 仍然要等待 `acc_scale`、参与 barrier arrival，并归还相关 buffer。它跳过的只是昂贵的 TMEM 数据路径。

判断以 warp 为单位进行。如果 32 行中只有一行需要 correction，整个 warp 仍会执行相同指令：需要修正的行乘以小于 1 的 `acc_scale`，其余行乘以 1，从而避免 warp divergence。

因此，这与前面的 conditional rescaling 构成了一条连续优化：

```text
延迟更新 reference
    ↓
更多 acc_scale 等于 1
    ↓
整个 warp 都无需 correction
    ↓
跳过 O 的 TMEM → registers → TMEM
```

**第四项改进：混合使用硬件 Exp2 与软件近似**

Softmax 需要计算：

$ e^{x/\sqrt d} = 2^{x\frac{\log_2 e}{\sqrt d}}. $

因此，Kernel 会预先计算：

$ \operatorname{scale\_log2} \frac{\log_2 e}{\sqrt d}$

再使用 `exp2` 计算 exponential。但 FA4 的优化并不只是将 `exp` 换成 `exp2`，而是让 **MUFU.EX2 和 FP32 FMA units 共同承担 exponential 计算**。

Blackwell 的 Tensor Core 吞吐量提升很快，但负责 `exp2` 的 MUFU 并没有同比例增长。如果所有 exponential 都交给 MUFU，它就会成为 softmax 的瓶颈。

因此，FA4 使用两条路径：

```text
大部分元素 → 硬件 MUFU.EX2
少部分元素 → FP32 FMA 多项式近似
```

软件路径先进行 range reduction：

$ 2^x= 2^{\lfloor x\rfloor} 2^{x-\lfloor x\rfloor}$

其中整数部分通过构造浮点数的 exponent bits 得到，小数部分则使用三次多项式近似：

$2^{x_{\mathrm{frac}}} \approx p_0+p_1x_{\mathrm{frac}} +p_2x_{\mathrm{frac}}^2 +p_3x_{\mathrm{frac}}^3. $

FA4 并不会让所有元素都走软件路径，因为这会增加 FMA 指令、register pressure 和依赖链。论文中只让大约 (10%) 到 (25%) 的 exponential 使用多项式近似，其余仍由 MUFU 执行。这样，MUFU pipeline 和 FP32 FMA pipeline 可以并行工作，从而缓解 exponential throughput 不足造成的 softmax bottleneck。

1. 考虑一个 query row，设 `scale_log2=1`、`rescale_threshold=8`、`row_max=2`、`row_sum=3`、`O=[4,6]`。下一个 block 的 `S=[5,4]`，`V=[[1,0],[0,1]]`。计算 `candidate_max`、`delta`、`new_ref`、`acc_scale`、`P`，以及更新后的 `row_sum` 和 `O`。再将 `S` 改为 `[11,10]` 重算，并解释为什么只有第二种情况需要重缩放旧状态。

答：这道题把一个 score row 简化为两个 key positions。`row_sum` 是此前权重的总和，`O` 是此前尚未归一化的加权和。

对于 `S=[5,4]`：

```text
candidate_max = max(2, 5) = 5
delta = (2 - 5) × 1 = -3
```

因为 `-3 >= -8`，继续使用旧参考值：

```text
new_ref = 2
acc_scale = 1
P = exp2([5,4] - 2) = [8,4]
```

由于 V 是单位矩阵，`P @ V=[8,4]`：

```text
row_sum_new = 3 + 8 + 4 = 15
O_new = [4,6] + [8,4] = [12,10]
```

再从原始状态计算 `S=[11,10]`：

```text
candidate_max = 11
delta = (2 - 11) = -9
```

因为 `-9 < -8`，需要切换参考值：

```text
new_ref = 11
acc_scale = exp2(-9) = 1/512
P = exp2([0,-1]) = [1,1/2]
```

因此：

```text
row_sum_new = 3/512 + 1 + 1/2 = 771/512
O_new = [4,6]/512 + [1,1/2]
      = [129/128, 131/256]
```

第二种情况切换了指数参考值，所以必须先将旧的 `row_sum` 和 `O` 转换到新尺度。

2. 分别追踪以下四段数据路径：Q/K SMEM → S TMEM、S TMEM → P TMEM、P TMEM + V SMEM → O TMEM，以及 O TMEM → O GMEM。对每一段列出执行角色、源和目标存储位置、tile primitive 与硬件路径，并指出其中哪些步骤在前面的 GEMM kernel 中不存在。

答:

| 路径 | 执行角色 | 存储变化 | 硬件路径 |
| --- | --- | --- | --- |
| Q/K → S | WG3 warp 0 | Q、K：SMEM；S：TMEM | QKᵀ tcgen05.mma |
| S → P | WG0 或 WG1 | S：TMEM → registers；P：registers → TMEM | tcgen05.ld、CUDA cores、tcgen05.st |
| P/V → O | WG3 warp 0 | P：TMEM；V：SMEM；O：TMEM | PV tcgen05.mma |
| O → GMEM | WG2、WG3 warp 2 | TMEM → registers → SMEM → GMEM | tcgen05.ld、CUDA cores、TMA store |

GEMM 中已有 SMEM operands → TMEM accumulator 和 TMEM → GMEM writeback。FA4 新增的是 `S → softmax → P`、以 TMEM 中的 `P` 作为 MMA operand，以及对已有 `O` 的按需重缩放。

3. 根据 fp16 view 中的 column $c$ 对应物理 32-bit column $\lfloor c/2 \rfloor$，推导 `S0`、`S1`、`P0`、`P1`、`O0` 和 `O1` 的物理 column ranges。哪些 regions 会发生重叠？哪些 waits 或 barriers 能防止重叠区域被过早读取或覆盖？

答: 物理位置为：

```text
S0: [  0,128)
P0: [ 64,128)   与 S0 后半部分重叠

S1: [128,256)
P1: [192,256)   与 S1 后半部分重叠

O0: [256,384)
O1: [384,512)
```

`P` 使用 fp16 view，因此两个 fp16 columns 对应一个物理 32-bit column。

安全性来自以下顺序：

1. `s_ready` 确认 QKᵀ MMA 已经写完 `S`。
2. softmax 完成 TMEM load，将完整 `S` 保存到 registers。
3. softmax 才用 `P` 覆盖不再需要的后半部分 `S`。
4. `tcgen05.wait.st` 确认 `P` 写完，再通知 `p_o_rescale` 或 `p_ready_2`。
5. PV MMA 等待相应 barrier 后才读取 `P`。

因此，重叠表示分时复用，并不表示 `S` 和 `P` 同时有效。

4. 追踪一个 K/V block 依次经过 `s_ready`、`p_o_rescale`、`p_ready_2` 和 `o_ready` 的过程。对每个 barrier，说明谁执行 wait、谁贡献 arrivals，以及随后哪块 tile 可以安全使用。为什么 `p_o_rescale` 需要等待 256 次 arrivals？将 `P` 按 96 columns 和 32 columns 分两段交给 PV MMA，又获得了什么重叠机会？

答：

- `s_ready`：WG3 warp 0 提交 QKᵀ MMA 的完成通知；WG0/WG1 等待；完成后可以读取 `S`。
- `p_o_rescale`：softmax 写完 `P[:,0:96]` 后贡献 128 次 arrivals，WG2 让 `O` 准备好后再贡献 128 次，共 256 次。WG3 warp 0 等待它发起第一段 PV MMA。
- `p_ready_2`：softmax 写完 `P[:,96:128]` 后贡献 128 次 arrivals，放行第二段 PV MMA。
- `o_ready`：最后一次 PV MMA 完成后报告通知；WG2 等待它进入 epilogue。

拆成 96+32 后，第一段 PV MMA 可以和最后 32 columns 的 `P` writeback 重叠。若等待全部 128 columns，Tensor Core 只能等 softmax 完全结束后再开始。

5. 负责发起 TMA 和 MMA 指令的 WG3 将每个 thread 的 register 上限降到 48，两个 softmax warpgroups WG0/WG1 将上限提高到 200，WG2 则使用 64。计算四个 128-thread warpgroups 的 register 总预算，再与 CTA 中所有 threads 都使用 200 个 registers 的情况比较。Softmax 角色为什么需要最大的配额？降低 WG3 的上限又如何使这项分配成为可能？

答: 当前总预算是：

```text
128 × (200 + 200 + 64 + 48)
= 65,536 个 32-bit registers
```

若所有 512 个 threads 都保留 200 个 registers：

```text
512 × 200 = 102,400
```

Softmax thread 需要同时保存 128 个 fp32 scores 和计算临时值，因此 WG0/WG1 需要最大的配额。WG3 主要负责发出异步指令，不保存大块中间结果，所以可以将上限降到 48。

这里不是 WG3 将某几个具体 registers 直接交给 WG0/WG1，而是 WG3 释放 CTA 的 register 配额，使 softmax warpgroups 可以提高自己的上限。

6. Kernel 已经将自然指数改写为 base-2 `exp2`，为什么 hardware exponential path 仍可能成为 softmax 的瓶颈？说明将元素分配给硬件 `exp2` 和基于 FMA 的三次多项式近似后，执行单元的利用方式发生了什么变化，以及哪些 online-softmax 公式保持不变。

答: 将自然指数改写为 `exp2`，只是把计算映射到了 base-2 exponential path。如果所有元素仍使用硬件 `exp2`，这条执行路径仍可能饱和，而 FP32 FMA units 没有得到充分利用。

FA4 将一部分元素交给硬件 `exp2`，另一部分使用 FP32 FMA 计算三次多项式近似，使两类执行单元同时工作。

改变的是指数的实现方式，online-softmax 的数学更新保持不变：

```text
P = exp2((S - reference) × scale_log2)
row_sum = row_sum × acc_scale + rowsum(P)
O = O × acc_scale + P @ V
```

7. 设 `SEQ_LEN_Q=6`、`SEQ_LEN_KV=8`，并采用右对齐 causal mask。Query positions 0 和 5 分别可以访问到哪个最大 key index？若 `BLK_N=4`，它们各自需要处理哪些完整、部分有效或完全跳过的 K/V blocks？这会怎样影响 causal tasks 的工作量和调度顺序？

答: 右对齐时：

```text
最大 key index
= min(i + SEQ_LEN_KV - SEQ_LEN_Q, SEQ_LEN_KV - 1)
```

这里 `SEQ_LEN_KV-SEQ_LEN_Q=2`：

| Query | 最大 key index | Block 0：keys 0–3 | Block 1：keys 4–7 |
| --- | --- | --- | --- |
| 0 | 2 | 部分有效：0–2 | 完全跳过 |
| 5 | 7 | 完全有效 | 完全有效 |

靠后的 query positions 需要处理更多 K/V blocks，因此对应 task 更重。Causal scheduler 会优先安排这些较重的 tasks，减少执行末尾只剩少数长任务的情况。

8. 设 `num_qo_heads=32`、`num_kv_heads=8`、`BLK_M=128`。求 `GQA_RATIO` 和 `SEQ_Q_PER_TILE`；当 `kv_head_idx=3` 时，分别将 packed rows 0、5 和 127 映射到 `(sequence` `offset,` `query` `head)`，并说明为什么这 128 行可以共享同一份 K/V tile。

答：

```text
GQA_RATIO = 32 / 8 = 4
SEQ_Q_PER_TILE = 128 / 4 = 32
```

`kv_head_idx=3` 对应 query heads：

```text
3 × 4 + {0,1,2,3} = {12,13,14,15}
```

映射结果：

```text
row 0:
  seq_offset = 0 // 4 = 0
  q_head = 3×4 + 0 = 12

row 5:
  seq_offset = 5 // 4 = 1
  q_head = 3×4 + 1 = 13

row 127:
  seq_offset = 127 // 4 = 31
  q_head = 3×4 + 3 = 15
```

这 128 行表示 32 个 sequence positions 与 4 个 query heads 的组合。四个 query heads 都属于同一个 `kv_head_idx=3`，所以可以共同使用该 K/V head 的同一份 K/V tile。
