## 2.6→4.6 tok/s，15.8→2.7 GB——RTX 4080S 16G 上的 MoE 推理极限挑战

### 摘要

本文系统性地研究了消费级 GPU（16 GB 显存）约束下 MoE 语言模型的专家卸载策略。以 DeepSeek-V2-Lite（15.7B 参数，BF16，27 层，每层 64 个路由专家 + 2 个共享专家）为对象，在 RTX 4080 SUPER + 128 GB DDR5 平台上，从 HuggingFace 默认 `device_map="auto"` 的 2.6 tok/s 出发，经历五个主要迭代版本，最终以共享槽池架构（V9）实现 2.7 tok/s / 2.7 GB VRAM，以全固定槽架构（V6 K=6）达到物理上限 4.6 tok/s（+77%）。我们记录了四条失败优化路径的定量根因分析，推导了 RTX 4080 717 GB/s 显存带宽决定的速度天花板，并投影到 DeepSeek-V4-Flash（284B MoE）的 INT4 量化可行性。

---

### 1. 引言

MoE 架构（Shazeer et al., 2017; Fedus et al., 2022）通过每 token 仅激活部分参数来降低计算量。DeepSeek-V2-Lite（DeepSeek-AI, 2024）在此基础上引入多头潜注意力（MLA）和每层 64 个路由专家，以 15.7B 总参数在仅激活 2.4B 参数的前提下取得强劲性能。

然而模型总大小 29.3 GB（BF16）超出了消费级显卡的显存容量。HuggingFace 默认的 `device_map="auto"` 会将整层 offload 到 CPU，把层内所有参数一视同仁。对 MoE 模型而言，这导致每 token 都要用的 attention 权重被错误地 offload，造成大量无效 PCIe 搬运。

本文的核心问题：**给定 16 GB 固定显存预算，MoE 推理的最优设备映射和专家缓存策略是什么？**

---

### 2. 背景

### 2.1 模型架构

DeepSeek-V2-Lite 共有 27 层 Transformer。其中第 1-26 层为 MoE 层，每层包含：

- **Self-attention**（MLA）：压缩 KV 潜空间 512 维 + RoPE 64 维
- **路由专家**：64 个 DeepseekV2MLP（gate_proj, up_proj, down_proj [1408, 2048]），每个 16.5 MB（BF16），总计 26.8 GB
- **共享专家**：2 个 DeepseekV2MLP，总计 0.8 GB
- **Gate**：小型线性层 [2048, 64]，将每个 token 路由到 6 个专家

LM head [102400, 2048]（400 MB）和 embedding [102400, 2048]（400 MB）跨层共享。

### 2.2 硬件约束

| 组件 | 规格 |
| --- | --- |
| GPU | RTX 4080 SUPER，16 GB GDDR6X，717 GB/s 带宽 |
| CPU | i9-14900K（8P+16E），128 GB DDR5 |
| PCIe | 4.0 x16，理论 ~25 GB/s |

### 2.3 测量协议

所有实验使用 30 条中文 prompt（10 个领域，各 3 条），每条生成 50 个新 token。解码策略为 Greedy Decoding（do_sample=False，temperature=1.0），确保 30⁄30 输出可复现。测量指标：生成速度（tok/s）、TTFT（首 token 耗时）、TPOT（每 token 生成时间）、峰值显存（peak VRAM）、缓存命中率（hit rate）、输出一致性。

---

### 3. 优化路径

### 3.1 起点：Phase 1 基线（accelerate device_map）

```text
model = AutoModelForCausalLM.from_pretrained(snapshot, device_map="auto")
```

**结果**：2.6 tok/s，TTFT 1.1s，VRAM 15.8 GB。

**分析**：accelerate 将第 11-26 层整层分配到 CPU，每生成一个 token 触发 608 次 hook 进行设备间传输。根本问题是范畴错误——attention 参数（每 token 必用）被等同于 expert 参数（稀疏访问）处理。

### 3.2 路线 A：手动设备映射

我们将参数手动分为两类：

- **GPU 常驻**：所有非专家参数（attention 投影矩阵、norm 层、embedding、共享专家、LM head）= 2.5 GB
- **CPU 常驻**：所有 MoE 层的 64 个路由专家 = 26.8 GB

**实现方式**：

```text
# 1. 全 CPU 加载模型（不加 device_map）
# 2. 建立专家参数 ID 集合（仅路由专家）
# 3. 其余参数搬到 GPU: p.data = p.data.to("cuda:0")
```

**结果**：2.6 → 4.1 tok/s（+58%），VRAM 基线降至 2.5 GB。

**关键洞察**：MoE 模型的 GPU 常驻参数仅 2.5 GB。大量参数（路由专家 26.8 GB）只需按需加载，不必预先占用显存。

### 3.3 专家缓存与保险柜

我们在每层建立 LRU 缓存（容量 K），并引入”保险柜”机制：

- **首次加载**：将专家权重克隆到 CPU（`_cpu_backup[eid] = p.data.cpu().clone()`）
- **淘汰时**：直接恢复 CPU 引用（`p.data = cpu_backup[eid]`，纯 Python 操作，零 PCIe 拷贝）
- **加载时**：从 CPU 保险柜 `copy_()` 到预分配 GPU 槽位（`non_blocking=True`）

“保险柜”的关键在于淘汰方向——不执行 `expert.to("cpu")`，而是替换 Python 引用。这消除了 Bug 1：`non_blocking` 的 GPU→CPU 卸载因 CUDA 调度器延迟释放导致新旧显存叠加的问题。

**版本演进**：

| # | 版本描述 | tok/s | VRAM 峰值 | 命中率 |
| --- | --- | --- | --- | --- |
| V1 | non_blocking 无同步（显存泄露） | 5.0* | 15.8 GB | 29.8% |
| V2 | + 同步修复 | 3.8 | 15.8 GB | 30.4% |
| V3 | + 逐子模块加载粒度 | 3.9 | 15.8 GB | 30.4% |
| V4 | + 保险柜（消除淘汰方向拷贝） | 4.8 | 15.8 GB | 30.4% |

*V1 使用 temperature=0.7 采样，其余均为 Greedy Decoding。V1 显存不安全。

### 3.4 固定卡槽：消除 PyTorch 缓存池

保险柜仍会在 prefill 阶段通过 `expert.to("cuda")` 创建临时 GPU tensor（超出缓存容量的专家）。每次分配喂给 PyTorch CUDA 缓存池，在 Windows WDDM 下永不归还操作系统。

**解决方案**：每层预分配 K 个固定 GPU 槽位（`torch.empty`），加载时 `copy_()` 到槽内，淘汰时仅标记槽位空闲，不调用 `cudaFree`。运行时零 cudaMalloc 调用。

**结果**：显存 15.8 → 6.9 GB（-57%），速度 4.8 tok/s（持平）。

**分批发**：Prefill 每层激活 20+ 专家（vs. decode 的 6 个）。K 个槽装不下时溢出的走 `expert.to("cuda")` 临时分配。将 prefill 专家列表切分为 ceil(N/K) 批，每批独立计算并在批间释放槽位，彻底消除 prefill 的 fallback 分配。

**结果**：Prefill 尖峰消除（残余 ~15.7 GB 来自 KV cache 分配本身）。

| 版本 | tok/s | Decode 显存 | Prefill 显存 |
| --- | --- | --- | --- |
| V5 | 4.8 | 6.9 GB | 15.8 GB |
| V6 | 4.7 | ~7.0 GB | ~15.7 GB* |

*Prefill 尖峰来源从 expert fallback 变为 KV cache 分配。

### 3.5 V9：共享槽池

**动机**：V6 的 78 个固定槽（26 层 × K=3）占用 1.29 GB GPU 显存，但同一时刻仅一层在计算，其余 75 个槽处于闲置。能否跨层共享槽位，以更少的槽数维持命中率？

**设计**：用全局池替换每层固定槽。N 个槽位被 26 层轮流借用，compute 时借、`on_layer_done()` 回调时还、下一层复借。

**实现**（expert_cache.py，新增约 100 行）：

```text
SharedSlotPool:
  - N 个预分配 GPU tensor（gate_proj + up_proj + down_proj）
  - acquire() / release() 借还接口
  - owner 追踪: slot_idx → (layer_idx, eid)

ExpertCache 修改:
  - _acquire_slot(): 有池 → pool.acquire(); 无池 → 本地 _free_slots
  - _release_slot(): 有池 → pool.release(); 无池 → _free_slots
  - _load_to_slot(): 使用 _get_slot_data() 统一池/本地数据访问
  - release_all_slots(): 归还本层所有借用槽（on_layer_done 调用）

预取:
  - _prediction: 记录当前 token 每层 gate 输出（按权重排序的 6 个专家 ID）
  - 新 token 启动: _prediction_prev = _prediction; _prediction = {}
  - 每层加载前: 从 _prediction_prev[当前层] 预取 top-3 专家到池槽
  - 过滤: 仅记录 decode 阶段 gate（≤6 专家），忽略 prefill（20+ 专家）
```

**Prefill 处理**：分批发中 K = min(len(pool_slots), len(active))，30 槽时尽可能一批全装。

**共享专家决策**：共享专家保持 GPU 常驻（0.8 GB）。尝试移 CPU 计算导致速度 -35%（PyTorch CPU BF16 3.3ms/专家 vs. PCIe 0.66ms/专家），放弃。

**结果（N=9 槽）**：

| 指标 | V6（78固定槽） | V9（9共享槽） |
| --- | --- | --- |
| 槽位数 | 78（26×3） | 9（池化） |
| 基线显存 | 2.5 GB | 2.66 GB |
| 峰值显存 | 3.8 GB | 2.7 GB |
| tok/s | 4.1 | 2.7 |
| 命中率 | 30% | 18% |
| Fallback | 偶有 | 零 |
| 输出一致性 | 30⁄30 | 30⁄30 |

速度下降（-34%）是 PCIe 带宽冲突的代价：每层约 4.9 个 miss 专家 × 0.66 ms PCIe = 3.2 ms/layer，而 V6 的 PCIe 搬运量近乎为零。

### 3.6 物理上限：4.6 tok/s

额外 8 GB 显存预算下，部署 V6 K=6（156 固定槽，所有专家 GPU 常驻）：

| 指标 | 数值 |
| --- | --- |
| tok/s | 4.6 |
| 峰值显存 | 5.1 GB |
| 命中率 | 29% |
| 手动 decode 循环 | 4.4 t/s（vs. generate() 4.6） |

手写 decode 循环（绕过 HuggingFace `generate()` 开销）无提升，确认瓶颈在硬件而非软件。

**显存带宽分析**：

- 27 层 × 6 专家 × 16.5 MB = 2.7 GB 权重数据（每 token 纯读取）
- 717 GB/s 带宽下：2.7⁄717 = 3.8 ms 最小权重读取时间
- Attention（MLA 解压缩 + 计算）≈ 4 ms/layer
- 每层总开销：~8 ms；27 层：~216 ms → 天花板 ~4.6 tok/s

### 4. 失败路径分析

### 4.1 CPU 计算专家

**假设**：PCIe 带宽饱和时，CPU 可从内存直接计算专家，无需搬运。

**实验**：i9-14900K 上单个专家 forward（BF16，PyTorch CPU backend）。

**结果**：3.3 ms/专家（vs. PCIe 搬运 0.66 ms/专家）。CPU 慢 5 倍。

**根因**：PyTorch CPU BF16 矩阵乘法在 batch-1 推理下未充分利用 AVX2。理论单核 ~100 GFLOPS，17M FLOPs 预期 ~0.17 ms，实测 3.3 ms——为理论的 1/19。不借助 Intel IPEX 或 MKL 专项优化，CPU 无法分担 GPU 计算。

此外，GPU+CPU 混合方案（4 miss 时 GPU 搬 3 + CPU 算 1）在实现中遇到 prefill/decode 边界检测困难，多次触发设备不匹配错误，最终放弃。

### 4.2 专家权重 Delta 压缩

**假设**：专家 E1 在 L1 和 L13 有共同基底，存差值即可，省内存。

**实测数据**（E1_L1 gate_proj，2,883,584 参数）：

| 指标 | 数值 |
| --- | --- |
| L1 vs L13 余弦相似度 | 0.0003 |
| E1 vs E2（同 L1）余弦相似度 | 0.0012 |
| E1 vs 随机高斯噪声 | -0.0003 |
|  | Δ |

**结论**：全部 1,664 个路由专家两两正交。MoE 训练使每个专家在每层完全特化，无可复用基底。

### 4.3 LM Head 搬 CPU

**假设**：lm_head [102400, 2048]（400 MB）仅最后 token 使用一次，留 CPU 可省显存。

**结果**：显存 -0.36 GB，速度 -18%。hidden→CPU→logits→GPU 往返每 token 增加约 3 ms 延迟。

**结论**：省下的显存与速度代价不成比例，回滚。

### 4.4 KV Cache 搬 CPU

**实测**：KV cache = 5.3 MB/token（MLA 压缩后：kv_lora_rank=512 + qk_rope_head_dim=64，27 层）。

**分析**：1000 token 时 KV cache = 5.2 GB。搬 CPU 则每层 attention 需全量 PCIe 扫描（5.2 GB / 25 GB/s = 208 ms/层 × 27 层）。不可行。

### 5. 讨论

### 5.1 CPU 何时能帮忙？

对于专家计算，当专家大到 PCIe 搬运时间超过 CPU 计算时间时，CPU 端计算才有意义。在 i9-14900K + 当前 PyTorch CPU backend 条件下，这个临界点约 50 MB/专家。V2-Lite 的 16.5 MB 专家远低于此。V4-Flash 的 48 MB 专家接近但尚未超越。

### 5.2 槽数的甜点值

N 个共享槽时，命中率的理论近似：

```text
命中率 ≈ (N / (L × K)) × gate_overlap
```

其中 L=26 层，K=6 激活专家，gate_overlap≈0.3。N=9 时理论命中上限 ≈17%（实测 18%）。N=78（等同 V6 每层固定槽）时 ≈30%（匹配 V6 实测）。

权衡是连续的——每个额外槽位以递减边际改善命中率。V2-Lite 的 Pareto 前沿：

| 槽数 | 显存 | tok/s | 适用场景 |
| --- | --- | --- | --- |
| 9 | 2.7 GB | 2.7 | 极限省显存 |
| 15 | 2.8 GB | 3.1 | 平衡 |
| 78 | 4.0 GB | 4.1 | 速度优先 |
| 156 | 5.1 GB | 4.6 | 物理上限 |

### 5.3 Windows vs. Linux

所有实验在 Windows 11 WDDM 环境下进行。PyTorch CUDA 缓存分配器在 WDDM 下无法向操作系统归还显存，导致 `reserved` 内存（14+ GB）远高于 `allocated`（5 GB）。同一代码在 Linux 上，峰值显存测量值会更接近实际分配量。

### 5.4 量化评估

INT8 量化可将 V2-Lite 从 29 GB 压至 14 GB，平均误差 0.1%，推理精度几乎无损。INT4 进一步压至 7 GB，平均误差 3.1%。当前 16 GB 卡恰好够用 BF16，量化收益在 V2-Lite 上不显著，但在 V4-Flash（295 GB → 74 GB INT4）上是必需品。

---

### 6. 对 V4-Flash 的投射

DeepSeek-V4-Flash（284B 总参数，13B 激活，256 路由专家/层 × 42 MoE 层，48 MB/专家 BF16）：

| 约束项 | V2-Lite | V4-Flash |
| --- | --- | --- |
| 专家大小 | 16.5 MB | 48 MB（2.9×） |
| PCIe 搬运/专家 | 0.66 ms | 1.9 ms |
| K（每 token 激活） | 6 | 6（假设） |
| 最小显存（Route A） | 2.5 GB | ~8 GB |
| 总模型（BF16） | 29 GB | 295 GB |
| 总模型（INT4） | 14 GB | 74 GB |

**可行性**：INT4 量化是 16 GB 卡的唯一入口。搭配 128 GB 主机内存和 INT4 模型，共享槽池（N=12-24）在 A6000 48G 上可达 3-5 tok/s。我们在代码中预留的 `_load_to_slot(stream=...)` 异步预取接口，在 V4 更大的专家尺寸（1.9 ms 搬运 vs. 更长的 GPU 计算时间）下将产生有效重叠。

---

### 7. 结论

消费级 GPU 上的 MoE 推理需要：

1. **手动设备映射**：将 attention（GPU 常驻）与路由专家（CPU 常驻）分离，通用方案不可用
2. **槽池预分配**：通过 `torch.empty` 预分配 + `copy_()` 加载消除 PyTorch 缓存池膨胀
3. **分批发**：防止 prefill 阶段的显存尖峰
4. **基于 gate 历史的预取**：在共享槽架构中恢复命中率

物理上限由显存带宽而非算力决定。V2-Lite 在 RTX 4080 上为 4.6 tok/s。该架构可平滑迁移至更大的 MoE 模型，适配 INT4 量化后即可在消费级硬件上运行。
