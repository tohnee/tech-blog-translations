本文主要聚焦严格延迟预算（例如 `P99 ≤ 200ms`）下 GR（Generative Recommendation）在线推理的结构性瓶颈，并介绍 xGR 的三块核心组件（xAttention / xBeam / xSchedule）如何分别从算子、算法与系统层面工程化解决这些问题。

术语与记号（本文默认）：

- `prompt_tokens`：prefill 阶段输入 token 数
- `decode_step`：decode 的步数（输出 token 数；GR 场景通常为小常数，例如 `3`）
- `beam_width`：beam search 每步保留的 beam 数
- `top_k`：每条 beam 每步扩展候选数；单步候选池大小为 `beam_width × top_k`
- `SLO`：在线服务延迟预算（本文主要关注 P99）

1. 背景：GR 推理服务的结构性瓶颈
2. xGR 总览：算子 、算法 与系统三层协同
3. xAttention 、xBeam 与xSchedule 的实现要点
4. 实验结果

## 背景：生成式推荐推理服务打破通用 LLM serving 的默认假设

生成式推荐（Generative Recommendation）在模型结构上仍是 Transformer，也同样遵循 `prefill → decode`。但在线推理的负载形态与通用 LLM serving 存在显著差异：在 `prompt_tokens` 较长、`decode_step` 为很小、且 `beam_width` 较大的典型配置下，系统瓶颈在“HBM 带宽 + KV 数据搬运 + CPU与设备端协同开销”。因此直接复用通用 LLM serving 的默认实现（PagedAttention、常规 beam search、continue batching），通常难以在严格 `SLO` 下达到目标 P99。

### 负载特征：长 prompt、短输出、大 beam

在我们的生成式推荐推理设定中，item id 由固定长度 token 序列表示，因此 `decode_step` 是已知的小常数（例如 `3`）。一次请求的推理流程可以概括为：

- 一次 prefill：输入为长序列（用户历史上下文）
- `decode_step` 次 decode：每步生成 1 个 token，最终组合为 item id

难点不在 decode 的步数，而在单步 decode 的单位开销：为了召回与多样性，生成式推荐通常需要较大的 `beam_width`；同时每条 beam 还要扩展 `top_k` 个候选，再在全局候选池 `beam_width × top_k` 上选择新的 beam 集合（最终 beam 集合大小固定为 `beam_width`）。<br>例如 `beam_width=512`、`top_k=512` 时，单步候选池大小为 262144（约 2.6×10^5）。

因此 decode 的步数虽然不多，但每步的搜索选择与 KV 访问开销仍然不低。

### 瓶颈拆解：带宽、KV 搬运与调度

我们把生成式推荐推理服务的主要瓶颈拆成三类，并在 xGR 中分别用 xAttention 、xBeam 和 xSchedule 去解决：

- **Attention 的冗余带宽消耗**：shared prefix 未被显式建模为可复用结构<br>在 beam较大的场景下，所有 beam 都共享同一段长 prompt。但通用实现往往以“每条 beam 一条完整序列”的视角组织 KV，导致 Shared KV 在 beam 维度被重复触发加载，attention kernel 的有效算术强度下降，最终受限于 HBM 带宽。
- **KV cache 的复制与碎片**：beam 分叉与 block 级管理存在结构性冲突beam search 会频繁 fork与retire 并触发 beam 重排。对于 block-based 的 KV 管理（PagedAttention 一类），“重排 + block 对齐”往往意味着 block copy、碎片化，以及额外的空间浪费，显存与带宽都会被放大。
- **调度开销成为关键瓶颈**：kernel 启动与同步等开销主导尾延迟GR 模型规模通常小于通用 LLM（我们覆盖的范围大致在 100M–10B），因此 kernel 启动、CPU 侧调度、同步点、H2D 拷贝等非计算开销更容易成为尾延迟的主导项，直接影响 P99。

把上面三点表述为优化目标就是：

1. **KV 组织**：显式区分 shared 与 unshared，把 shared prefix 的复用落实到显存布局
2. **beam 分叉与重排**：优先实现低拷贝与低碎片，避免在通用 KV 结构上强行适配
3. **调度与执行**：将图化执行作为默认路径，降低 CPU与设备端协同开销对 P99 的影响

## xGR 总览：算子 、算法与系统三层协同

![](https://pic2.zhimg.com/v2-75ec5ecdef52b1840c1470a257c4b6f1_r.jpg)
*图 1：xGR 总览：算子/算法/系统三层协同*

xGR 的拆分是典型的工程化co-design：算子内核层（xAttention）、算法层（xBeam）、系统层（xSchedule）共同指向同一目标：在 P99 约束下把吞吐与成本做到可扩展。

| 瓶颈 | 直接表现 | xGR 模块 | 核心手段 |
| --- | --- | --- | --- |
| shared prefix 冗余带宽 | attention 撞上memory wall | xAttention | Separated KV + staged attention + OnlineSoftmax 合并 |
| beam 分叉的 KV 复制 | 显存随 beam_width 非线性膨胀 | xAttention 、 xBeam | token 级 Unshared KV 管理 + 原地重排（in-place reorder） |
| CPU与设备端协同开销 | kernel launch 和 同步抬升 P99 | xSchedule | 重叠执行（overlap）+ 图执行（graph dispatch）+ 多流并发（multi-stream） |

下面按 xAttention → xBeam → xSchedule 逐块展开实现细节。

## xAttention：把 shared prefix 复用落实到 KV 组织与计算路径

这一部分我们讨论的不是“再造一个 FlashAttention”，而是围绕 GR 的固定结构，把 KV cache 的组织方式与 attention 的计算和并行策略一起重新设计，将shared prefix 在显存层面只存一份，同时beam 的分叉与重排不再触发高代价的数据拷贝。

### KV cache 拆分：显式区分 shared与unshared

![](https://pic1.zhimg.com/v2-69917b5e55f602db5c42480e2d6f240c_r.jpg)
*图 2：Separated KV cache：Shared KV / Unshared KV 拆分*

xAttention 的第一步是把 KV cache 按“是否共享前缀”拆成两类：

- Shared KV：prefill 阶段生成的 prompt KV，所有 beam 共享同一份物理存储
- Unshared KV：decode 阶段每条 beam 新生成 token 的 KV，按 token 粒度管理

关键点在于 decode_step 是已知且为小常数，因此 Unshared KV 不需要沿用 block 对齐的“通用解”，可以直接按 token 预分配容量：

- Unshared KV 容量约为 `beam_width × decode_step` 个 token
- 显存开销可分解为两部分：Shared KV 随 `prompt_tokens` 线性增长；Unshared KV 随 `beam_width × decode_step` 线性增长

工程上，这个拆分同时带来两类收益：

1. 带宽：Shared KV 作为单一连续区域被访问，更容易形成跨 beam 的缓存与访存复用
2. 显存：Unshared KV 只为 decode 新 token 付费，且避免 block copy

### 原地重排：Unshared KV 的重排

beam search 每轮都会选择新的 beam 集合（大小固定为 `beam_width`），并据此对 beam 做重排，Unshared KV 需要随 beam 一起重排，否则后续 decode 会读取到错误的历史。<br>如果直接原地写，会遇到典型的写后读覆盖风险：目的位置先被写入，源位置还没读取就被覆盖。

我们的做法是引入一个低成本的辅助信息（写入方向标记），把写入划分为两类：

- 向上写入：`src > dst`
- 向下写入：`src < dst`

然后用两次遍历选择安全的写入顺序：

1. 处理向上写入：按 `dst` 从大到小写入
2. 处理向下写入：按 `dst` 从小到大写入

原因是：向上写入时，先写高地址可避免覆盖尚未读取的高地址源；向下写入同理。这样可以在不引入额外 KV 缓冲区的前提下完成重排。

收益：用“写入顺序”替代“额外缓冲区去做复制”，从而降低 beam 分叉带来的数据搬运与同步开销。

### 分段 attention：分段计算与 OnlineSoftmax 合并

![](https://pic2.zhimg.com/v2-5b610dcb9d1732dee656fa617207af95_r.jpg)
*图 4：分段 attention：Shared与Unshared 独立统计 + OnlineSoftmax 合并*

为了避免把 Shared与Unshared KV 直接拼接成一个逻辑长序列，以及由此带来的访存与拷贝问题，xAttention 把一次 attention 拆成三个阶段：

1. shared stage：仅对 Shared KV 计算局部 softmax 统计量与部分输出
2. unshared stage：仅对 Unshared KV 计算局部统计量与部分输出
3. merge stage：用 OnlineSoftmax 把两段结果稳定合并

并行化层面我们会把 shared、unshared与merge 分配到不同的执行单元与队列上形成流水线，目标是让 Shared 与 Unshared 的计算尽量重叠执行，同时把同步点压缩到最少。

## xBeam：约束解码与快速候选选择

### 约束解码：用 mask 剪枝无效 item

GR 的输出不是自然语言，而是结构化的 item id。token 组合空间巨大，但真实有效的 item id 占比低。 在我们的负载中，如果不做约束，beam 扩展过程中无效 item 的比例会接近 50%，这会把单步 beam_width × top_k 候选池上的计算与带宽预算浪费接近一半。

![](https://pica.zhimg.com/v2-b5e11c241f4addb322a63988992491f8_r.jpg)
*图 5：约束解码：mask 剪枝无效 item*

xBeam 采用约束解码（constraint decoding）：对 logits 叠加 item mask，把无效 token 的 logit 置为 -∞，从而在 softmax 后其概率为 0。

### 提前终止排序：最小堆与 beam 内早停

每一步要从 `beam_width × top_k` 候选中保留新的 beam 集合（size=`beam_width`）。若做全排序，时间复杂度与内存访问开销都较大。<br>我们利用一个关键不变量：每条 beam 内的 `top_k` 候选已按 `log_prob` 降序（或可在生成 `top_k` 时保证这一性质）。

![](https://pic3.zhimg.com/v2-48f4a6e88af5d3662030c3ccb1ba29e0_r.jpg)
*图 6：提前终止排序：最小堆与 beam 内早停*

据此可以用一个容量为 `beam_width` 的全局最小堆做候选选择，并在 beam 内做提前终止：

- 维护全局最小堆（size=`beam_width`）
- 逐 beam 遍历候选：若当前候选不优于 `heap.min()`，则该 beam 的后续候选不会超过当前阈值，可直接终止遍历

伪代码（工程实现常用形态）：

```text
heap = MinHeap(capacity=beam_width)
for beam in beams:
  for cand in beam.candidates_sorted_desc:
    if heap.not_full() or cand.log_prob > heap.min().log_prob:
      heap.push(cand); heap.pop_if_overflow()
    else:
      break
return heap.items_sorted_desc()
```

在实际负载中，早停会显著减少实际遍历的候选数（远小于 `top_k`），从而降低选择阶段的整体开销。

### 缓存复用：固定 step 下的资源复用

beam search 如果每轮都频繁分配与释放，在严格 `SLO` 下会显著抬升 P99。<br>利用 `decode_step` 固定的事实，我们会在请求以及批次级别预分配临时缓冲区，并在每轮把新结果写回原有区域，实现资源复用，从而降低资源管理与数据搬运开销。

### xSchedule：缩短尾延迟关键路径，减少 CPU 参与

![](https://pica.zhimg.com/v2-99d822217e31beed0159e4783fb05b5a_r.jpg)
*图 7：xSchedule：双缓冲重叠、图执行与多流并发*

在 GR 的固定结构中，`prefill` 与固定次数的 `decode`（`decode_step` 为小常数）的阶段边界清晰；但在 `decode` 阶段，beam 选择与状态更新高度耦合，跨阶段的流水并行空间有限。因此系统侧的优化重点是缩短 `decode` 的尾延迟关键路径，并通过异步拷贝与双缓冲把必要的 CPU 侧准备与设备端计算重叠。

### 单步 decode 的关键路径拆解

一次 decode（第 t 步）可以抽象为以下串行依赖链：

1. xAttention：基于 Shared KV 与已有 Unshared KV 计算 logits
2. 有效性过滤：对 logits 叠加 mask
3. 每 beam 生成 `top_k` 候选：保持降序
4. 全局选择：从 `beam_width × top_k` 候选中保留新的 beam 集合（size=`beam_width`）
5. 状态更新：beam 重排、Unshared KV 索引与内容更新、为 t+1 准备元数据

xSchedule 的目标是让 2、4、5 尽量在设备端完成，并把必要的 H2D 更新做成异步、可重叠的操作。

### CPU与设备端重叠：双缓冲与异步 H2D

我们把 CPU 侧不可避免的准备工作（例如 sparse mask 更新、少量控制参数）做成双缓冲，并用异步拷贝把它与设备端计算重叠：

- 设备端执行第 t 步 xAttention 的同时，CPU 准备第 t+1 步的 sparse 更新
- 通过异步 H2D 把更新写入预先约定的设备端缓冲区
- 设备端在下一个边界点消费该 buffer，避免全局同步

目标是把 CPU与设备端同步点从尾延迟关键路径上尽量移除，避免 CPU 侧阻塞而造成 P99升高。

### 图执行：减少每步 decode 的 CPU 交互

我们把一串 kernel 与必要的内存拷贝捕获成图（例如 CUDA Graph 与 Acl Graph），以“批量提交”的方式降低 kernel 启动与 CPU 交互开销。 这在轻量模型场景下尤为关键：计算量较小，但启动和调度开销并不会同比例下降；图回放能明显减少关键路径里的 CPU 参与。

### SLO 感知批处理：动态 batching 与多流并发

动态批处理（dynamic batching）需要同时满足两类约束：

- token 容量：请求 token 数波动较大，batch 大小需按容量动态调节
- `SLO` 时间窗：为了不牺牲尾延迟，批处理间隔必须受预算约束；超过配额即触发发射 另外，为避免小模型在单个 batch 下无法充分占用设备，我们使用多流并发多个 batch，由调度器动态把就绪 batch 分配到空闲 stream，以提高总体利用率。

## 实验结果：端到端吞吐、显存与内核

### 端到端：严格延迟约束下的稳态吞吐

- 在 `P99 ≤ 200ms` 约束下，xGR 可支持更高的稳态吞吐
- 在我们的端到端结果中，吞吐提升下界为 ≥ `3.49×`
- 随 `beam_width` 增大，基线实现（baseline）的延迟增长更非线性，差距扩大

### 显存占用：KV 分离带来的近线性伸缩

在 Qwen3-4B、单 Ascend NPU、RPS=4 的实验中我们观察到：

- `beam_width` 从 128 → 512：xGR 峰值显存维持在约 `10GB`
- `beam_width=512`：xLLM `46.3GB`，xGR `10.6GB`
- `beam_width=256`、输入长度到 3k：xGR 峰值 `12.0GB`，xLLM 约 `30GB`

在 `beam_width=512` 场景下我们测到：

- xAttention kernel 延迟约 `6.6×` 降低
- 吞吐（throughput）约 `7×` 提升
- memory profiler 观测：PagedAttention 的内存访问为 `93.4%`，xAttention 约 `52%`

### 小结

xGR 推理服务的关键不是“把模型算得更快一点”，而是围绕beam search会进行fork与retire这点，把 KV 组织、beam search 与系统调度联合优化：否则瓶颈会稳定落在带宽、KV 复制与内存碎片，以及 CPU与设备端同步上。
