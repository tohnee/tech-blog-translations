先讲件让我印象很深的事。

那天我改了一版 **Query Rewrite 的 Prompt** 。原因很明确：有个用户问” **上次那个政务云方案，服务器用的啥型号** “，系统答不上来——指代消解没做好。我调完 Prompt，这个问题当场就好了，特别爽。

**三天后，客服转来四条投诉。**

一查，全是新冒出来的：以前答得挺好的几个问题，现在答偏了。原因是那版 Prompt 里我加了一句” **要主动扩展同义词** “，本意是帮”网线→超六类非屏蔽双绞线”这类问题，结果它开始 **过度发挥** ——把” **怎么收费** “扩展成了” **计费规则 费率 价格 报价** “，反而把一批不相关的报价文档召了进来。

我修好了 1 个，弄坏了 4 个。而 **我当时手测的那 3 个问题，恰好全是它擅长的那类** ——这不是运气差，这是幸存者偏差。

那一刻我彻底明白一件事：

> **在 RAG 里，”我改完试了几个问题，感觉更好了”——这句话几乎等于没说。因为你试的那几个，测不出你弄坏的那几个。**

后来我把评测接进了 CI。这篇就把这件事讲透。

---

### 一、先认清：RAG 的 CI，比普通软件的 CI 难得多

普通软件做 CI 很舒服：改完代码 `npm test` ，红的绿的清清楚楚。RAG 为什么不行？因为它有 **6 个普通软件没有的特殊性** ：

| 特殊性 | 具体表现 | 后果 |
| --- | --- | --- |
| ① 没有编译错误 | 代码写错编译不过；RAG 写错照样跑，只是”答得烂” | 没红灯，你就以为没事 |
| ② 输出非确定 | 同一个问题，两次跑出两个答案 | assert 输出 == 标准答案 直接失效 |
| ③ 多环节耦合 | 改切片影响召回、改召回影响生成 | 牵一发动全身，改了 A 必测 B |
| ④ 判分要靠 LLM | 质量得让大模型当裁判 | 用一把”会漂的尺子”，量一个”会漂的系统” |
| ⑤ 数据会变 | 知识库一更新，昨天的对题可能变错题 | 基线本身在走，绝对阈值靠不住 |
| ⑥ 又贵又慢 | 全量跑一次要花钱花时间 | 不可能每个 PR 都全量跑 |

**接地气类比** ：普通软件的 CI 像 **机械零件的出厂检测** ——卡尺一量，合格就是合格，不合格就是不合格，又快又准。RAG 的 CI 像 **面试评分** ——主观、需要标尺、面试官当天的状态都会影响分数，而且候选人（知识库）换一批，尺子可能就不准了。

所以给 RAG 做 CI， **不能照抄普通软件”跑测试用例看红绿”那一套** ，得专门设计。

---

### 二、核心思路：把”问答质量”变成一条能返回退出码的命令

别被上面那 6 条吓住，本质其实特别朴素，就三步：

```text
① 一份固定评测集（几十到几百条真实提问）
② 一个跑的脚本，输出一堆指标（Recall@5、Faithfulness……）
③ 拿指标和基线/阈值比，不达标就 exit 1
```

**这最后一步 `exit 1` 才是灵魂。** 它把”质量”这件事，翻译成了流水线唯一听得懂的语言—— **退出码** 。

看一段伪代码，核心逻辑就这么点：

```python
# eval/run.py —— RAG 回归脚本的骨架
baseline = load_baseline("main")              # 拿主分支的基线
current  = run_eval(golden_set, rag_pipeline) # 跑当前改动

diff = compare(baseline, current)             # 算指标差分
gate = judge_gate(diff, RULES)                # 门禁判定

write_report(diff, "reports/eval.json")       # 存档 + 给 PR 评论用
sys.exit(0 if gate.passed else 1)             # ← 就是这一行，让 CI 认识"质量"
```

**接地气类比** ：这就是 **考试** 。每次提交，都拿同一份卷子考一遍，及格线卡在流水线上。考不过，代码就别想合进去。

而且关键是—— **门禁必须写在流水线里，不能写在规范文档里。** 写在文档里的规则，最后的结局几乎都是”这次赶进度，先跳过一下”。

---

### 三、分四层跑：不是所有测试都值得每次跑

全量跑一次又贵又慢，但只跑冒烟又测不出质量。解法是 **分层** ，像汽车出厂检测线一样——快的工位每个零件都过，全面的检测定期做。

| 层级 | 跑什么 | 耗时 | 何时跑 | 卡门禁吗 |
| --- | --- | --- | --- | --- |
| L0 冒烟 | 15~30 条金用例：链路通不通、有没有崩、有没有空答、格式对不对 | 秒 ~ 1 分钟 | 每个 PR | ✅ 硬门禁 |
| L1 组件级（不调 LLM judge） | 检索 Recall@5 / NDCG、改写前后差分、融合 ablation | 几分钟 | 每个 PR | ✅ 硬门禁 |
| L2 端到端（LLM judge） | Faithfulness、Answer Correctness | 10~20 分钟 | 合并前 / 夜间 | ⚠️ 软门禁（阈值放宽） |
| L3 全量 + 系统级 | 完整评测集 + P95 延迟 + 单请求成本 + 覆盖率 | 较久 | 夜间定时 | 📊 只报告 + 告警 |

为什么这么分？因为 **便宜且稳定的指标（L0/L1）才敢卡硬门禁，贵且会漂的指标（L2）只敢软卡** 。这个原则记住，后面第五、六节全用得上。

> **顺带说一句** ：L1 里的”改写前后差分”“融合 ablation”，正是我前两篇文章（Query Rewrite、混合召回的配比）里做决策用的那套指标。 **它们不只是调参工具，本身就是可以直接搬进 CI 的回归项。**

---

### 四、最难的一关：怎么给”非确定性”做断言

这一节是全篇最费脑子的地方。传统单元测试是 `assert 结果 == 预期` ，可 RAG 的输出 **天生就不相等** 。怎么办？

**第一，能降随机就降随机。** 温度设 0、固定 seed，能压掉一部分波动——但别指望它保证一致，语言模型不承诺这个。

**第二，把”等号断言”换成”阈值断言”。** 别比”答案一不一样”，比”指标够不够好”：

```python
# ❌ 这么写必挂，因为输出天生不同
assert answer == "该方案采用 2 颗 Xeon Gold 6338"

# ✅ 这么写才稳：比指标，不比字符串
assert result["recall@5"]      >= 0.90
assert result["faithfulness"]  >= 0.85
assert result["p95_latency_ms"] < 2500
```

**第三，用”多次采样”把运气平均掉。** 同一批问题跑 3 次取多数（majority vote），或者看 pass@k——比”跑一次看结果”稳得多。

**第四，管好那把”会漂的尺子”。** 用 LLM 当裁判，就得防裁判自己漂：

- **锁死 judge 的模型版本和 Prompt** ，别让它偷偷升级（我今天用 GPT-4o，明天变了个小版本，分数波动算谁的？）；
- **judge 本身也要被评测** （元评测）：拿一批人工标好的样本，看 judge 判得准不准；
- **Pairwise 比 Pointwise 稳** ：让 judge 判”新版比旧版好还是差”，比让它打绝对分更不容易漂；
- **人工定期抽样校准** ，别让 judge 和人类越走越远。

**接地气类比** ：这就是面试。你不能因为面试官今天心情不好、给了低分，就判定”候选人退步了”。所以正经的公司会—— **固定面试官、用评分区间而不是精确分、多个面试官取多数意见** 。RAG 的 CI 一模一样。

### 五、一条流水线到底长什么样

把上面几节拼起来，就是一条真正能跑的流水线。我按 GitHub Actions 写（云效、GitLab CI 同构，改语法而已）：

```yaml
name: rag-regression
on:
  pull_request:
    paths:                      # 只要碰了这几类东西，就必须回归
      - 'rag/**'
      - 'prompts/**'            # 改 Prompt 也要跑！
      - 'config/chunking.yaml'  # 改切片参数也要跑！
      - 'config/fusion.yaml'    # 改融合配比也要跑！

jobs:
  l0_smoke:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pip install -r requirements.txt
      - run: python eval/run.py --layer l0 --report reports/l0.json
      # 脚本内部不达标就 exit 1，这一步自然变红

  l1_component:
    needs: l0_smoke
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: python eval/run.py --layer l1 --baseline main --report reports/l1.json
      - uses: actions/upload-artifact@v4
        if: always()
        with: { name: eval-report, path: reports/ }

  l2_e2e:
    if: github.event.pull_request.draft == false
    needs: l1_component
    runs-on: ubuntu-latest
    steps:
      - run: python eval/run.py --layer l2 --judge gpt-4o-2024-08-06 --report reports/l2.json
```

跑完产出一份 **结构化报告** ，直接贴到 PR 里给评审人看：

```json
{
  "layer": "l1",
  "commit": "a1b2c3d",
  "baseline": "main@f9e8d7c",
  "metrics": {
    "recall@5": 0.89,
    "ndcg@5": 0.78,
    "rewrite_gain": 0.16,
    "p95_latency_ms": 2380
  },
  "regressions": ["q_014", "q_031", "q_055"],
  "improvements": ["q_007", "q_088"],
  "gate": { "passed": false, "reason": "recall@5 相对基线 -0.04，超过 0.02 阈值" }
}
```

看到没—— **报告里最有价值的不是那个总分，而是 `regressions` 和 `improvements` 这两份名单** 。下一节就讲为什么。

### 六、回归检测的精髓：别只看总分，要看”谁退步了”

这是我最想强调的一节，也是很多人做错的地方。

### 6.1 相对基线，而不是绝对阈值

只卡绝对阈值（”Recall 必须 ≥ 0.9”）有个致命问题： **知识库一更新，基线自己就动了** 。今天 0.9 达标，明天新文档一进来变成 0.88，你都不知道该怪谁。

正确做法是 **两个都看** ：

- 绝对阈值守底线（”再差也不能低于 0.85”）；
- **相对基线看退化** （”不能比上一个版本掉超过 2%“）。

### 6.2 逐条 diff：找出”退步的学生”

总分掉 1%，可能是”50 条里错 1 条”的正常波动，也可能是”某类问题整体崩了，被其他类的进步盖住了”。

**所以一定要做逐条 diff** ，把名单拉出来：

```text
regressions（从对变错）: q_014, q_031, q_055
improvements（从错变对）: q_007, q_088
```

**接地气类比** ：老师看班级成绩，不能只盯着平均分。平均分没变，不代表没人退步——可能前 10 名掉了分、后 10 名涨了分，平均下来刚好持平。 **真正该做的是把”退步的那 5 个同学”找出来，一个个问原因。**

### 6.3 分片断言：别让总分骗了你

最坑的情况是： **总分只掉了 1%，但某个子集掉了 15%。**

比如我那个项目，专有名词类问题（型号、品牌）就特别容易被一次”语义化改造”带崩——因为这类问题恰恰不靠语义。所以评测要 **分片** ：

```text
总体            recall@5 = 0.89   (基线 0.90，-0.01 ✅)
├─ 专名/型号子集  recall@5 = 0.76   (基线 0.91，-0.15 ❌ 门禁挂在这)
├─ 口语/长尾子集  recall@5 = 0.94   (基线 0.88，+0.06 ✅)
└─ 多跳子集      recall@5 = 0.83   (基线 0.86，-0.03 ⚠️)
```

**总分在绿区，专名子集已经红得发紫。** 如果只卡总分，这次退化就漏过去了——而它恰恰是最贵的那种错（型号认错 = 报价错）。

所以我自己定的规矩是： **总体过 + 每个关键子集也过，才算过。**

### 七、三个最容易被忽略的工程细节

### 7.1 评测集要进 Git，和代码同版本

评测集不能放在某个人电脑里，也不能随手改。它要 **和代码一起进版本库** ，改了什么、什么时候改的、谁改的，都要能追溯。

**类比** ：考卷也要版本管理。你每次换一份新卷子考，还怪成绩忽上忽下，那没法分析。

### 7.2 知识库快照必须可复现

这是 RAG 独有的坑： **如果你的 CI 跑的是生产库，那今天跑和明天跑，基线根本不是一个东西。**

所以 CI 里要拉一个 **固定的测试索引快照** ，锁死版本。否则你测出来的差分，一半来自代码改动，一半来自数据漂移，混在一起没法归因。

### 7.3 Bad Case 要回流成测试用例

线上每发现一个答错的问题，处理完就 **把它补进评测集** 。这样同一个坑，这辈子只踩一次。

**接地气类比** ：这就是防疫——每发现一个病例，就把这个毒株加进疫苗库。 **评测集是会自己长大的。**

### 八、成本和速度：怎么让 CI 跑得起

理想很美，钱包很现实。几个我在用的省法：

| 手段 | 做法 | 省什么 |
| --- | --- | --- |
| 组件级不调 LLM | L1 的检索指标全是纯计算，零 LLM 成本 | 省钱又稳定 |
| 缓存 judge 结果 | 相同 (问题, 答案, 上下文) 不重复判 | 大幅省 judge 调用 |
| 抽样 | PR 跑分层抽样的子集，夜间跑全量 | 省时间 |
| 廉价 judge 粗筛 | 便宜模型先判，只有”边界 case”才交给贵模型 | 省贵模型 token |
| 只测受影响部分 | 改了融合配比，就优先跑召回相关子集 | 省全量跑 |

核心原则： **把贵的测试（LLM judge）留给真正需要判断质量的场景，其余全用纯计算指标扛。**

---

### 九、门禁的”人性”：阈值定不好，团队会把你绕过

这一节特别容易被工程师忽略，但它是 **成败关键** 。

门禁阈值定得太严 → CI 天天红 → 团队要么集体无视，要么偷偷加 `--no-verify` 绕过 → **门禁形同虚设** 。 定得太松 → 什么都放行 → 也是形同虚设。

我的做法是 **先松后紧，分两步走** ：

1. **头两周只记录、不拦人** （warn-only）。让流水线静静跑，收集”正常波动到底有多大”。
2. **摸清波动区间后，再收紧硬门禁** ——只卡”绝对底线”（崩溃、空答、Recall 掉超过 5%），小幅波动只发警告。

**接地气类比** ：新装的监控要是天天误报，最后没人看报警。 **报警阈值是要根据真实噪声调出来的，门禁也一样。**

一句话： **一个天天红的门禁，等于没有门禁。**

### 十、它保证不了什么？（防吹篇）

1. **CI 只保证”不比基线差”，不保证”绝对好”。** 如果基线本身就烂，你只是在”稳定地烂”。
2. **评测集没覆盖的，CI 测不出。** 就像体检只查你列进套餐的项目——不在套餐里的毛病，查不出来。
3. **开放型问题很难自动断言。** “给我推荐一套机房配置”这种没有唯一答案的问题，自动判分很难做准，还得靠人工。
4. **它替代不了线上真实反馈闭环。** 离线评测再全，也模拟不了真实用户的千奇百怪。CI 是”守门员”，不是”教练”。

**记住：把评测接进 CI，解决的是”改动会悄悄弄坏东西”这个工程问题，不是”让 RAG 变聪明”这个能力问题。** 后者得靠数据、切片、检索、Prompt 一点点抠——而 CI 的价值，是保证你抠的时候 **不会把已经好的东西抠坏** 。

---

### 十一、结语：一句话带走

回到开头那件事——我改一版 Prompt，修好 1 个、弄坏 4 个，三天后才知道。

现在再发生同样的事，会是这样：

```text
我提交 PR
  → CI 自动跑 L0 + L1
  → 报告显示：rewrite_gain +0.16（好）
              但 专名子集 recall@5 -0.15（坏）
              regressions: q_014, q_031, q_055
  → 门禁红灯，代码合不进去
  → 我当场就知道"过度扩展同义词"把型号类问题带崩了
```

**从”三天后靠用户投诉发现”，变成”提交后 3 分钟自己发现”。** 这就是把评测接进 CI/CD 的全部意义。

最后记三句话：

> **① 把”质量”翻译成退出码** —— `exit 1` 那一行，才是 CI 听得懂的语言； **② 分层跑、分级卡** ——便宜稳定的硬卡，贵且会漂的软卡； **③ 别只看总分** ——逐条 diff + 分片断言，才能抓住”总分绿、子集红”的隐性退化。

一句话总结：

> **CI/CD 之于 RAG，不是让它更聪明，而是让它”聪明的部分不会悄悄变傻”。质量门禁写进流水线，比写进任何一份规范文档都管用一百倍。**
