> 原文： [https://elarazju.github.io/deepinfer-illustrated/](https://elarazju.github.io/deepinfer-illustrated/)

借着DeepSeek 开源推理框架 DeepInfer，一起来学一学推理系统的一些知识。

同一个大模型，为什么有时迟迟不出第一个字，有时开头很快、后面却越写越慢？

为什么加了更多 GPU，吞吐量也未必按比例增长？为什么缓存命中了，系统还可能需要重新计算？

这些问题都落在模型公式之外： **一次请求能多快完成，取决于计算、数据搬运和调度怎样配合。**

本文先讲文字怎样变成模型能计算的数字，再沿着一次请求的路径，把生成、缓存、多卡协作和调度串起来。

读完之后，再看到一个推理优化方案，你可以先问三件事：它省掉了哪一段计算，减少了哪些数据读取，又把什么等待藏进了流水线？

## 00 模型究竟怎样生成一段回答

### 从文字到数字

这里说的“推理”，是用训练好的模型计算输出，和日常说的“逻辑推理能力”不是一回事。训练阶段学到的参数叫 **权重** ；对话推理时权重保持不变，模型用它们处理新的输入。

用户的问题、系统指令和之前的对话，会被拼成模型的输入，也就是 **prompt** 。模型并不直接读文字，而是先由 **分词器（tokenizer）** 把文本切分成 token，再转换成编号。

token 可以是一个字、一个词，也可以是词的一部分，所以“1,000 token”并不等于“1,000 个汉字”。比如“我喜欢学习”可能被切成 `[我] [喜欢] [学习]` 三块，具体怎么切由分词器决定。[6]

编号随后经过 **embedding（嵌入）** 变成一串数字，也就是向量。向量是模型内部表示信息的方式，单个数字不一定对应某种人能理解的含义。

这些向量经过一层层运算，在上下文的影响下不断更新，层与层之间传递的内部表示叫 **hidden state（隐藏状态）** 。最后一层的结果用来给下一个位置的每个候选 token 打分，再换算成概率。从输入走完全部层、得到这组概率，称为一次 **前向计算** 。[7]

### 每次选出下一个 token

假设已有文本是“我喜欢”，模型给“学习”“旅行”等候选分配了不同的概率。可以直接选概率最高的，也可以按概率随机抽一个，后者叫 **采样** 。temperature 等参数会调整概率分布，所以同一个问题可能得到不同的回答。

选出的 token 被追加到序列末尾，成为下一轮的输入：选中“学习”后，下一轮就基于“我喜欢学习”继续预测。这样一步步追加，直到遇到结束标记或达到长度上限，就是 **自回归生成** 。[7][8]

![](https://pica.zhimg.com/v2-0f68f9b142e4a63e4d4eab7d0e828c84_r.jpg)
*图1｜橙色是输入，绿色是逐步追加的输出，紫色是后面要讲的 K/V 缓存。刚选出的 token 要到下一次前向计算时，才会算出自己的 K/V。*

这也是一段回答没法一次算完的原因：问题里的 token 一开始就全部已知，而回答的每个 token 都要等前一个选出来才能确定。

### Attention 怎样读取上下文

预测下一个 token 时，模型需要用到前文。 **注意力（Attention）** 让当前位置按相关程度，从前面各个位置汇总信息。比如在“小猫跳上桌子，它……”里，接下来写什么，要结合前面的“小猫”和“桌子”。这种相关程度由向量计算得出，不是人写的语法规则。

Attention 里有三个常见的字母 Q、K、V：

- **Q（Query，查询）** ：当前位置拿来匹配上下文的向量。
- **K（Key，键）** ：每个位置提供给别人匹配的向量。
- **V（Value，值）** ：匹配之后，真正被加权汇总的信息。

可以借用查资料来理解：Q 像检索条件，K 像索引，V 像资料内容。只不过它们都是从内部表示算出来的向量。

在因果语言模型中，一个位置只能看到它前面的位置，看不到后面的，这叫 **因果约束** 。实际的模型有很多层，每层有多个注意力头；Attention 之后还有前馈网络等变换，结果再交给下一层。[7]

### KV Cache 省掉哪些工作

在因果注意力里，往句尾追加一个 token，不会改变前面已经算过的位置。所以旧位置的 K 和 V 可以存下来，下一步直接拿来用，这份存下来的状态就是 **KV Cache** 。[9]

有两点要注意。第一，缓存存的是中间计算结果，不是“这个问题的标准答案”。第二， **省掉的是重新计算旧 K/V，而不是读取旧 K/V** ：在普通全注意力中，每生成一个新 token，仍要把全部历史位置的 K/V 读一遍。

所以上下文越长，要存、要读的数据就越多。对普通全注意力来说，一条序列的 KV Cache 大小和 token 数成正比：上下文从 4,000 token 变成 8,000 token，KV Cache 也大约翻倍。[9]

具体大小可以这样算：

> 单序列 KV 字节数 = 2（K 和 V）× token 数 × 层数 × 每层 KV 头数 × 每头维度 × 每个数的字节数 
> 

其中“头数”是保存多少组 K/V，“维度”是每个向量有多少个数。这个公式适用于普通全注意力；DeepSeek V4.1 Flash 对缓存做了压缩和跨层共享，实际占用要小得多。

### GPU 算得快，也要数据供得上

模型的主要工作是大量矩阵计算，适合交给 GPU 等加速器并行执行；CPU 负责管理请求、准备批次和下发任务。理解后面的性能问题，要区分三种限制：

- **算力** ：单位时间能完成多少运算。
- **显存容量** ：能装下多少权重、缓存和临时数据。
- **显存带宽** ：单位时间能把多少数据送到计算单元。

可以把计算单元想成加工台，显存想成仓库：仓库放得下，不代表送料够快；送料跟不上，加工台再多也只能等。多卡之间还要交换数据，跨卡通信又有自己的带宽和延迟。

所以遇到“模型慢”，先要判断是算不过来、装不下、数据读不动，还是任务没有及时交给设备。后面介绍的各种优化，都是针对其中一种或几种。

## 01 从点击发送到出现第一个字

假设我们发出一个带图片的请求：“解释这张架构图，并指出可能的性能瓶颈。”

请求先要从 API 协议（客户端和服务端约定的请求、响应格式）转换成模型的输入：文本编码成 token，图片交给视觉编码器 **Vision Encoder** 转成向量。如果这段上下文之前处理过，系统还要查一查哪些计算结果可以直接复用。

随后，Prefill 阶段处理全部输入，Decode 阶段逐个生成输出；生成的 token 流最后被解析成正文、思考内容或工具调用，返回给用户。[2，pp.2、10]

![](https://picx.zhimg.com/v2-eb208b5f5935780832e93f9e45f0d0df_r.jpg)
*图2｜沿箭头看请求经过的各个环节，其中一些环节可以并行。灰色虚线框是这一版本尚未开源的线上服务。*

从用户角度看，这段旅程有两种等待：等第一个字出现，以及等后面的字陆续出现。

前者用首 token 延迟 **TTFT** 衡量，后者用相邻两个 token 的间隔 **TBT** 衡量；另一个常见指标 **TPOT** 是首个 token 之后，平均每个 token 花的时间。TTFT 包含排队、编码、查缓存和 Prefill 等所有环节，不只是 Prefill 本身的耗时。

举个例子：请求发出 1 秒后出现第一个 token，之后每 0.05 秒输出一个，那么 TTFT 是 1 秒，生成速度约为每秒 20 token。如果系统同时服务 10 个这样的请求，总吞吐约为每秒 200 token，但每位用户看到的仍是每秒 20 token。

**延迟衡量一位用户等多久，吞吐衡量整个系统做了多少工作。** 只统计满足延迟目标的那部分吞吐，叫 goodput（有效吞吐）。把请求攒成大批次能提高总吞吐，代价可能是一部分用户等得更久。[10]

性能报告常用“吞吐—延迟”曲线比较方案，曲线上每个点对应一种配置。那些“不增加延迟就无法再提高吞吐”的点连起来，叫 **Pareto 前沿** ，沿着它移动，就是在吞吐和延迟之间取舍。比较两条曲线前，先确认输入输出长度、缓存命中率和硬件是否一致；吞吐最高的点，也不一定适合在线对话。

所以说“推理更快”，要讲清楚是第一个字出来得更早、后续生成更流畅，还是同样的资源服务了更多请求。

## 02 同一个模型为什么要分 Prefill 和 Decode

回到生成过程。输入的所有位置一开始就已知，模型可以在遵守因果约束的前提下，把它们一起送进计算。这个处理输入、建立初始 KV Cache 的阶段叫 **预填充（Prefill）** ，它最后一个位置的输出用来选出第一个回答 token。

之后，模型每次把刚选出的 token 送入计算，复用已有的 KV Cache，再选下一个。这个逐步推进的阶段叫 **解码（Decode）** 。不使用投机解码时，每个请求每轮只前进一个位置。

![](https://picx.zhimg.com/v2-07d7605291e9014756b676d810f65069_r.jpg)
*图3｜以单个请求为例，对比两个阶段每次计算多少位置、读取多少数据。条形长度表示相对大小。*

Prefill 一次处理许多位置，读进来的权重被反复使用，计算量大，瓶颈通常在算力。Decode 每轮只处理一个新位置，却要把权重和全部历史 KV 都读一遍，瓶颈更常落在显存带宽上。具体情况还取决于批量、上下文长度、注意力结构和硬件。

这也回答了开头的问题：为什么开头很快、后面越写越慢？回答越长，每步 Decode 要读的历史 KV 就越多；同一批里的其他请求也在变长，每轮的执行时间随之增加。

**批量（batch）** 是指把多个请求放在一起执行。单个请求每轮只前进一步，但一个批次可以同时推进很多请求，一次读入的权重能服务更多计算。不过每个请求的历史 KV 仍要各自读取，批次越大、上下文越长，这部分读取压力也越大。组批只是一起计算，各请求的上下文仍然相互隔离。

请求的回答有长有短。如果要等整批都结束才能放新请求进来，先结束的位置就会空着。 **连续批处理（continuous batching）** 让已完成的请求在每一轮结束时退出、新请求随时加入，提高了设备利用率，但单个请求仍然要一步一步生成。[11]

长输入还可以做 **chunked prefill** ：把长文档的 Prefill 切成若干块，每块和其他请求的 Decode 拼进同一批执行，避免一个长 Prefill 卡住正在生成的请求。[10][11]

两个阶段的瓶颈不同，同一套资源配置很难同时兼顾。DeepSeek 的线上架构因此把 Vision Encoder、Prefill、Decode 分开部署，各自配置资源，分别优化首字延迟和生成速度。代价是 Prefill 算好的 KV Cache 要传给 Decode 机器，中间也多了一层调度。[2，p.2]

**分离部署的收益，要和搬运 KV 的成本一起算。** 如果传输拖慢了后续生成，Prefill 算得再快，用户也未必等得更少。

## 03 GPU 没有满负荷时先看时间线

假设 GPU 计算已经很快，为什么两轮计算之间还会有空白？

GPU 不会自己挑任务。CPU 上的调度器要决定这一轮处理哪些请求、准备好输入，再把计算任务提交给 GPU。GPU 上执行的单个计算任务叫 **kernel（内核）** 。提交是异步的：CPU 把任务放进队列就可以继续往下走，不必等 GPU 算完；但要用到计算结果时，就必须等。

同步的 Decode 流程是这样的：CPU 组好批次，GPU 做前向计算并采样，CPU 取回结果、判断哪些请求已经结束，再组织下一轮。CPU 做后处理和调度的这段时间里，GPU 没有活干。

DeepInfer 的异步调度把这两部分工作重叠起来：GPU 执行第 N 轮的前向计算和采样时，CPU 已经在准备第 N+1 轮，同时处理第 N−1 轮的结果。[2，p.9]

![](https://pic4.zhimg.com/v2-4273fbb4e7dc72de3100638a88b1f68f_r.jpg)
*图4｜上下两条时间线的计算量相同。同步调度时 GPU 要等 CPU；异步调度进入稳定状态后，GPU 可以连续工作。*

这里有个容易忽略的问题： **相邻两轮的批次，请求顺序可能已经变了。** 有的请求结束退出，有的新请求加入，同一个请求不一定还在批次的同一行。

所以提前调度时，必须正确对应上一轮的结果。DeepInfer 的输入准备逻辑按序列编号建立一张 **remap（重映射）** 表，把这一轮的每个请求对应到上一轮 GPU 输出中的位置；新加入的请求没有上一轮结果，就用自己的输入。就像换了座位之后，按学号把作业发回给每个人。[3]

画出“CPU 和 GPU 并行”很容易，难点在于工作提前之后，数据还得交到正确的请求手里。

这类调度器常被称为 zero-overhead scheduler，意思是把调度开销藏进 GPU 执行的时间里。即便如此，启动、收尾、负载变化和通信等环节，仍会让 GPU 出现空闲。

顺带一提，监控里的“GPU 利用率高”也不代表算力用满了。 `nvidia-smi` 的 GPU 利用率统计的是采样期间有 kernel 在运行的时间比例；kernel 在运行，也可能正卡在等数据。[12]

## 04 专家分得更散之后还要解决热点

Transformer 的每一层，大致由读取上下文的 Attention 和对每个位置单独加工的前馈网络组成。 **混合专家（Mixture of Experts，MoE）** 把前馈网络拆成许多组参数，每组叫一个“专家”。

专家不是一个个独立的聊天机器人，也不一定对应“数学专家”“编程专家”这样的分工。每个 token 到来时， **路由器（门控）** 根据它的内部表示给所有专家打分，选出得分最高的 k 个参与计算（即 top-k），再把它们的输出按权重合并。有些架构还设有每个 token 都会经过的共享专家。[13]

![](https://pic2.zhimg.com/v2-abb58d977089409c59da0671d2475d15_r.jpg)
*图5｜绿色路径是这次被选中的专家。图中只画了路由专家，没有画共享专家。*

这样，模型的总参数量可以很大，而每个 token 只用到其中一小部分。代价是所有专家都要存着；一个批次里不同 token 选中的专家各不相同，合起来往往会用到很多专家。

如果专家分布在不同的卡上，token 的表示就要发到所选专家所在的卡，算完再送回来，这就是 **专家并行（EP）** 。

多卡分工常见三种方式：

- **数据并行 DP** ：每张卡放一份相同的权重，各自处理不同的请求。
- **张量并行 TP** ：把同一层的矩阵计算切开，多张卡各算一部分，再通信合并。
- **专家并行 EP** ：把不同专家放在不同的卡上，token 被送到所选专家那里计算。

这些方式可以组合。DeepInfer 的做法是 Attention 部分用 DP、MoE 部分用 EP：同一张卡在 Attention 阶段处理自己的请求，到了 MoE 阶段又负责自己那几个专家。EP 阶段每张卡都要和其他所有卡互相收发数据，这叫 **all-to-all 通信** ，卡越多，通信开销越要算清楚。[2，p.2][14]

![](https://pic4.zhimg.com/v2-f79fd73f2da994f2506ec533e37f63e7_r.jpg)
*图6｜每一列代表一张卡，从上往下看：Attention 阶段各算各的请求，MoE 阶段按专家所在位置交换 token 表示。*

**Wide-EP** 是把专家并行扩展到更多卡上（DeepSeek 线上的 Decode 用 64 到 128 张卡），每张卡分到的专家更少，每步要读的专家权重也更少。但每张卡专家数一样，不代表工作量一样：路由可能总是选中少数几个热门专家。

一张卡总是最晚完成，其他卡就都得等它。 **要均衡的是每张卡实际承担的 token 计算量，而不只是专家个数。**

热门专家忙不过来时，不能让空闲的专家代班：不同专家的权重不同，换人就改变了模型的计算结果。能分担工作的，只有同一个专家的副本。

DeepInfer 的专家并行负载均衡 **EPLB** 就是这样做的：统计各专家的负载，给热门专家多放几份副本，再重新安排专家在各卡上的位置。模型看到的逻辑专家没有变，只是同一个专家多了几份物理副本，分给它的 token 可以分摊到这些副本上。[2，pp.3–4][4]

![](https://picx.zhimg.com/v2-6d3a5232955bf66ee8412ac4bae1f157_r.jpg)
*图7｜上半部分区分“模型选中了哪个逻辑专家”和“由哪个物理副本执行”；下半部分是官方 Q&A 给出的 Prefill 与 Decode 配置参数。*

图中的 `moe_lb` 是最慢那张卡的负载与平均负载之比，越接近 1 越均衡。这里的 **rank** 是分布式系统对参与计算的进程的编号，通常一个 rank 对应一张卡，和“排名”无关。

均衡也有代价：副本占用显存，重排要搬运权重，负载统计也会滞后于流量变化。所以 EPLB 每隔一段时间才重排一次，在重排频率和收益之间权衡。

## 05 缓存命中了为什么还可能重算

“缓存命中”听起来像一个开关，实际上涉及好几种状态。

先区分两件事：同一个请求在生成过程中复用自己的历史 KV，以及不同请求之间复用相同开头的计算结果。后者叫 **前缀缓存** ，需要共享存储和前缀索引，有时还要跨机器取数据。

比如两个请求都以同一份长文档开头，只是后面问的问题不同。只要开头的 token 序列完全一致，第一次算好的结果就可以给第二次用。必须是 token 完全相同，意思相近但措辞不同并不算命中。[15]

### 全注意力与滑动窗口

**全注意力** 的每个位置都能直接看到前面所有位置； **滑动窗口注意力（SWA）** 只让当前位置直接看到最近的一段。比如窗口大小为 4，当前位置是第 10 个时，它直接看第 7 到第 10 个；往后走一步，窗口也跟着往后移一格。

![](https://pic3.zhimg.com/v2-bd7af1587931543bbde561ce516b3330_r.jpg)
*图8｜绿色是当前位置能直接看到的范围。*

窗口固定，这一层要存、要读的状态也就固定了，不会随上下文变长。但这不等于模型只记得最近几个 token：更早的信息可以经过多层逐级传递，模型也还有全局注意力这条路径。窗口限制的只是 **这一层直接看到哪里** 。[16]

### 两类状态，两种存法

DeepInfer 服务的 DeepSeek V4.1 Flash 同时用到两类注意力状态。

一类是全局注意力的缓存（Main KV 与 Indexer K），按 128 个 token 一块组织，下文称为 **Block KV** 。它覆盖完整的历史（经过压缩），体积随上下文增长，最值得在请求之间共享。

另一类是 SWA 状态，只覆盖最近一个窗口，大小固定：每条序列需要保存的部分约 1.4 MB（20 层 × 134 token × 528 字节）。[2，pp.5–7]

两类状态的存放方式也不同。Block KV 存进独立的 **3FS 分布式文件系统** ，任何一台 Prefill 机器都能读到已缓存的前缀，请求不必为了命中缓存而只能发往某一台机器。SWA 状态则留在生成它的那台机器的内存里，由一个目录记录位置，需要时再跨机器取回。[2，pp.5–7]

![](https://pic1.zhimg.com/v2-991edce1da629202d3c6b24ddc21b5a0_r.jpg)
*图9｜Block KV 与 SWA 状态的保存和恢复路径。灰色虚线框中的存储和目录服务尚未随引擎开源。*

图中的数据从存储盘到主机内存，再到 GPU 显存：SSD 是固态硬盘，shm 是主机共享内存，HBM 是 GPU 上的高带宽显存。从内存搬进显存时按层进行，好让搬运和前向计算同时进行；这一步用的是 GDR（GPUDirect RDMA），由网卡直接把数据写进显存，不占用 GPU 的计算单元。图中的 TTL 是缓存保留时间，官方线上的 Agent 流量为 3 天，聊天流量为 7 天。

另一组数字 `10+2` 说的是纠删码：数据切成 10 份，再加 2 份冗余编码，同时坏掉 2 个节点也能恢复。读取时同时向 11 个节点发请求，只要收到其中 10 个响应就能还原数据，不必等最慢的那一个。[2，pp.3–4]

### 命中之后为什么还要回放

命中长度由 Block KV 决定，但接着往下算，还需要命中位置对应的 SWA 状态。如果 Block KV 命中了，SWA 状态却不在，就要 **回放** ：把命中部分末尾的一小段 token 重新算一遍，恢复出 SWA 状态。已经命中的 Block KV 照常复用，不用重算。

所以同一个请求里，完全可能一部分结果直接复用，另一部分需要重建。

### 模型结构也在帮忙省计算

V4.1 Flash 采用 **CED（Causal Encoder-Decoder，因果编码器—解码器）** 结构，灵感来自 **YOCO** （You Only Cache Once）：把 **同一个 Transformer** 的下半部分层当作 encoder，上半部分层当作 decoder。这里的 encoder 是语言模型内部的一组层，和前面处理图片的 Vision Encoder 是两回事。

关键在于数据怎么流动：encoder 处理完输入，得到最后一层的 hidden state；decoder 各层需要的 Block KV，直接由这份 hidden state 经过投影（一次线性变换）得到。

因此 Prefill 只需把 encoder 部分完整算一遍，decoder 各层不必再对整个 prompt 重算，官方技术报告称这能省下近一半的 Prefill 计算。decoder 各层的 SWA 状态仍要自己算，这部分靠回放 prompt 末尾的一小段来准备。[2，p.7][17]

![](https://picx.zhimg.com/v2-5cb666aa0c26e07d617286285f5318fb_r.jpg)
*图10｜紫色路径是 Block KV 的复用，绿色路径是 SWA 状态的重建。图中的 encoder 指模型内部的下半部分层。*

这样就有两种回放：encoder 的回放只在命中前缀、但缺少 SWA 状态时发生，重算的是命中部分的末尾；decoder 的回放每次 Prefill 都会发生，重算的是 prompt 的末尾，结果只给后续 Decode 使用，不存进前缀缓存。[2，p.7]

只回放最后一小段，得到的 SWA 状态是近似的，和从头精确计算并不完全相同。回放窗口是 128 个 token；实际保留的长度还要再多几个，因为下一节要讲的投机解码可能需要回退几个 token。[1][2]

## 06 DSpark 为什么有时少验证反而更划算

普通自回归生成，每轮只能前进一个 token。 **投机解码（speculative decoding）** 先用成本较低的方法一次猜出多个候选 token（称为草稿），再交给目标模型验证，争取一轮前进多个位置。草稿可以来自一个小模型，也可以来自主模型里专门的预测模块。DeepInfer 使用的投机解码方案叫 **DSpark** ，它的特点是根据置信度决定每轮验证多少个草稿。[1]

为什么验证可以一次看多个位置？因为有了草稿，这些位置的输入就都“已知”了，目标模型可以像 Prefill 一样并行计算。验证从前往后进行，一旦某个位置没通过，它后面的草稿全部作废，由目标模型在这个位置给出自己的结果，再继续生成。[8]

这里的“通过”是指符合目标模型的预测，和内容是否正确无关。投机解码能不能加速，取决于每轮平均能接受多少 token，以及起草加验证总共花了多少时间。

问题在于，越靠后的草稿越不值得验证，因为它要被接受，前面每一个都得先通过。举个例子，假设三个草稿各自的通过概率（在前面都通过的前提下）是 0.9、0.8、0.2，那么前 1 个、前 2 个、前 3 个全部通过的概率分别是 0.9、0.72、0.144。验证第 3 个草稿，平均只多换来 0.144 个 token。

DSpark 用一个 **Confidence Head（置信度预测模块）** 估计每个草稿的通过概率，再结合硬件的实测吞吐，决定把验证算力花在哪些位置上。官方配置每轮生成 5 个草稿，但不一定 5 个都验证。[2，pp.8–9]

背后的道理很简单： **比较一轮预计能产出多少 token，和这一轮要花多少时间。** 多验证一个位置，可能多产出一点，也一定多花一点。

实际调度时，验证预算在整个批次的请求之间统一分配：把所有请求的草稿按累计通过概率排序，优先验证最有希望的那些。[5]

和异步调度配合时还有个麻烦：CPU 提前安排下一轮时，这一轮的置信度还没算出来。DeepInfer 的办法是让 CPU 只定下总预算，每个请求具体验证几个，由 GPU 拿到最新置信度后再算，并顺便完成 remap 对应。[2，p.9]

可见优化之间会互相牵制：调度提前了，做决策需要的信息就来晚了，实现上必须补上这段时间差。

## 07 请求分配和输出返回也在性能链路上

计算、缓存和调度都安排好之后，还要决定把请求发给哪台机器。这时也不能简单地给每台机器分一样多的请求。

一个短问题和一篇长文档都算一个请求，Prefill 的计算量却可能相差很大。Decode 的负担既取决于并发请求数，也取决于这些请求的历史 KV 总长度。图片会被切成小块 **patch** 来编码，编码工作量取决于 patch 数，而不是图片张数。

DeepSeek 的线上方案因此为每个阶段选了不同的负载指标：Prefill 按上下文长度分档，按计算预算分配；Decode 同时看请求数和 KV 总长度；Vision Encoder 看正在处理的 patch 数。这部分负载均衡服务尚未开源，和前面已经开源的 EPLB 是两回事。[2，pp.4–5]

![](https://pic4.zhimg.com/v2-d0a6514f75c3510e11e2850f7b2994dd_r.jpg)
*图11｜三个阶段各用各的负载指标。Decode 的“并发数 × KV 总长”表示两个维度要一起考虑。*

模型生成 token 之后，还要变成用户能看到的回答。 **流式输出** 是边生成边返回，而不是等整段写完再显示。推理后端每次返回的一小段叫 chunk，一个汉字、一个分隔标记或一段工具参数，都可能被拆到两个 chunk 里。

DeepInfer 配套开源了 DeepSeek Recipe 组件，负责协议转换、编码和流式解析。解析器要记住上一个 chunk 解析到了哪里，已经确定的内容立即输出；还要分清哪些是普通正文，哪些是思考内容或工具调用。[2，p.10]

如果业务要求输出 JSON 等固定格式，可以用 **结构化输出** ：系统跟踪当前写到了格式的哪一步，在采样前把不合法的 token 排除掉。比如该写字段名的位置，就不可能冒出一段闲聊。它保证格式正确，但字段内容对不对，仍取决于模型本身。

## 08 再读推理代码时可以从这些问题出发

学习 DeepInfer，可以先沿数据流建立全貌，再挑一条机制深入：

- 想知道等待从哪里来，看异步调度和跨轮 remap；
- 想知道多卡为什么忙闲不均，看逻辑专家、物理副本和权重重排；
- 想知道缓存为什么不能只看命中率，看 Block KV、SWA 状态和回放条件；
- 想知道草稿为什么不是越长越好，看 DSpark 的累计通过概率和验证预算。

读到任何一个优化时，都可以追问三个问题：

1. 它减少的是计算、数据读取，还是关键路径上的等待？
2. 它依赖什么条件，又新增了什么状态、通信或调度成本？
3. 最后改善的是首 token 延迟、持续生成速度，还是满足延迟目标时的总吞吐？

这些问题同样适用于其他推理框架。把模型计算、状态复用和系统调度连起来看，性能数字背后的原因就清楚了。

想动手试一试，可以打开 [图解 DeepInfer](https://elarazju.github.io/deepinfer-illustrated/) ：调整异步时间线、DSpark 和 SWA 窗口的参数，看看结果怎么变，再回到代码里验证自己的理解。
