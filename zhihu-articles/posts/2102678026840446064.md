*算法系列 01 · 从训练到设备部署*

拿到 `best.pt`，或者已经导出一个能在电脑上运行的 ONNX，还不能说明模型已经能在摄像头上运行。后面需要核对芯片工具链、模型输出格式、设备 runtime 和类别映射，最后再看设备是否确实运行了这个模型。

这篇以 Hi3516CV610 为例，把数据、训练、导出、转换、打包和设备验证连起来。示例是 `person` 单类别、640×640 输入，使用 Endless 配套模型打包及设备管理流程。文中涉及我们自己的 IPC 工程，适用范围限于具备匹配运行时和工具链的设备，不代表所有摄像头都能直接照搬。

**这是一份操作模板，尚未完成本文所述的一轮定向训练及真机验收。文中不把既有截图、历史实验或说明图写成本次模型的成功结果。**

### 先分清手里的文件到了哪一步

![](https://pic3.zhimg.com/v2-c353274533afb1629dfd32f523f4306a_r.jpg)

- `best.pt`：本次训练保留的权重，要能追到对应数据和参数。
- `best.onnx`：用于主机基线对比的普通 ONNX，还不是本例 CV610 runtime 所需的最终模型。
- `person-new-rpn.onnx`：用匹配 SDK 的 YOLO/new-RPN 工具从本次权重导出，不能靠改文件名获得。
- `person-cv610.om`：完成芯片转换后的载荷，还要核对输入、输出和类别。
- `.emodel`：由配套打包器封装后的设备模型包；上传、启用及现场效果仍要分别检查。

开始前先备好训练环境、匹配芯片的 SDK 导出和转换工具、Endless Model Packager，以及支持对应 runtime 的设备。缺少某一步的工具时，先停下来补齐，不用其他格式的文件冒充产物。

### 一、先把图片和标注准备好

从实际机位采集有人、无人、遮挡、逆光和夜间画面。先按采集会话划分训练、验证与最终测试，再抽帧、标注；保留来源和允许用途。

用标注工具框出人员，导出 YOLO 检测格式。每张图片对应同名标签文件，无人图片使用不含目标的标签；类别统一为 `0=person`。

![](https://pic2.zhimg.com/v2-10c62b24cb16d876f762a096dbbd88ad_r.jpg)

目录按下面组织，`train`、`val`、`test` 各有对应的图片和标签：

```text
person-data/
├── images/{train,val,test}/
└── labels/{train,val,test}/
```

新建 `person.yaml`，把 `path` 换成自己的绝对路径：

```yaml
path: /absolute/path/person-data
train: images/train
val: images/val
test: images/test
names:
  0: person
```

**检查：** 类别只有人员；图片与标签对应；同一连续事件没有跨集合重复。

### 二、训练后留下能追溯的权重和参数

在已准备的 Ultralytics 环境中执行。以下主机命令按 8.3.0 版本资料组织，基础权重、依赖和数据版本一并记录；芯片导出环境另按 SDK 要求准备。

```bash
yolo detect train \
  model=yolov8n.pt data=person.yaml \
  imgsz=640 epochs=50 batch=4 device=cpu \
  seed=42 project=runs/person name=train
```

这里使用 CPU 演示命令结构，轮次与批大小按资源和验证结果调整。运行后找到本次实际输出目录中的：

```text
weights/best.pt
args.yaml
results.csv
```

**检查：** 本次日志对应哪份数据、基础权重和参数。若目录被自动加了序号，后续命令使用实际路径。

### 三、先检查模型，再导出主机基线 ONNX

先在验证集检查漏检、误检和框的位置，再选择权重和阈值：

```bash
yolo detect val \
  model=runs/person/train/weights/best.pt \
  data=person.yaml split=val
```

导出固定输入、batch 为 1 的 ONNX：

```bash
yolo export \
  model=runs/person/train/weights/best.pt \
  format=onnx imgsz=640 batch=1 \
  dynamic=False opset=13 simplify=False
```

保留 `best.onnx`，用同一批验证图片对比 PT 与 ONNX 的人员类别和坐标。最终测试集留到版本固定后再用。

**检查：** ONNX 输入尺寸、颜色与归一化方式、输出及类别顺序有记录。这个普通 ONNX 先用于主机基线，进入 CV610 前还要完成下一步适配。

### 四、用匹配的工具链完成 CV610 转换

在与目标设备匹配的 SVP NNN PC 工具环境中，按配套 YOLO/new-RPN 示例加载本次 `best.pt`，导出 `person-new-rpn.onnx`。具体导出命令取自该版本 SDK 的 `README_yolov8.md`，类别设为本次的人员类别，输入与训练约定一致。

这一步需要实际的配套导出工具；把 `best.onnx` 改名不能得到 new-RPN 模型。缺少导出器或尚未核对输出契约时，先停在这里补齐。

准备同版本 AIPP 配置和代表性校准图片列表，使用 ATC 转换。下面的输入名、ArgMax 节点和文件路径必须按实际模型核对：

```bash
atc --model=/absolute/path/person-new-rpn.onnx \
  --framework=5 --soc_version=Hi3516CV610 \
  --input_format=NCHW \
  --input_shape="images:1,3,640,640" \
  --input_type="images:UINT8" \
  --insert_op_conf=/absolute/path/insert_op_yvu.cfg \
  --image_list="images:/absolute/path/image_ref_list.txt" \
  --out_nodes="/model.22/ArgMax:0" \
  --output_type="/model.22/ArgMax:0:U16" \
  --batch_num=1 --online_model_type=0 --compile_mode=0 \
  --output=/absolute/path/person-cv610
```

应得到 `person-cv610.om`。校准数据不使用最终测试集。

**检查：** 转换无错误；OM 满足设备的 new-RPN 输出契约；同一输入的类别和框没有异常变化。保存转换器版本、命令、日志及 PT、ONNX、OM 的 SHA-256，确认它们确实属于同一条转换链。

### 五、把芯片模型打包成设备可管理的 `.emodel`

打开配套的 Endless Model Packager，按本次真实模型填写：

![](https://pic1.zhimg.com/v2-c45f773740d3836559516bac62fe8b42_r.jpg)

选择 CV610 runtime 和刚生成的 OM；输入宽高与模型一致；本例只有类别 `0`，映射目标为 `person`，然后生成 `.emodel`。

如果你取得的是包含 `tools/model_packager` 的配套源工程，也可先构建工具：

```bash
cmake -S tools/model_packager \
  -B out/host/model-packager -G Ninja \
  -DCMAKE_BUILD_TYPE=Release
cmake --build out/host/model-packager
```

在该工程根目录用同一工具打包：

```bash
out/host/model-packager/endless-model-packager --build \
  --runtime hisilicon.yolov8_new_rpn.v1 \
  --model /absolute/path/person-cv610.om \
  --output /absolute/path/person-cv610-1.0.0.emodel \
  --package-id person-cv610 --name "人员检测" \
  --package-version 1.0.0 \
  --input-width 640 --input-height 640 \
  --target-key person
```

**检查：** 包里的类别映射与实际模型一致，记录包的大小和 SHA-256。打包器处理已转换载荷，不负责把 PT 或普通 ONNX 转为芯片模型。

### 六、上传、安装和启用要分别确认

登录设备 Web，进入“目标检测”页面，确认设备支持 CV610 runtime 且有可用的模型上传空间，然后选择“上传模型包”，上传本次 `.emodel`。

![](https://pic2.zhimg.com/v2-e352025207ebb5e684606493d6d3db13_r.jpg)

*既有界面示例，图中页面标题为“模型管理”。容量、内置模型与暂停状态以自己的固件和设备为准，不是本篇模型的部署结果。*

等安装完成，打开新模型的详情，核对名称、版本、输入尺寸和人员类别，再对这一个新模型点击“启用”。无签名包按界面要求确认来源；如果提示资源被占用，先按现场业务约定处理占用的智能功能。

**检查：** 上传完成、安装完成和运行中分别确认。换模型通常沿模型管理流程处理，不把上传模型包当作固件升级。

### 七、最后用实际输入和现场画面验证

打开预览，用同一机位检查清晰人员、遮挡、远处人员和无人干扰，保留原图、输出框、模型版本与时间。

先比较主机与设备对同一输入的结果，再恢复实时画面检查比例、坐标和时延；确认推理由目标芯片执行。最后对已固定的版本使用独立最终测试，并记录漏检、误报与资源占用。

**完成标志：** 你能从数据与训练记录追到最终包，设备确实运行了这个模型，并且成功、失败和未测条件都能查到依据。

### 判断进度时，别只看文件后缀

有了 ONNX，不代表完成芯片适配；有了 OM，不代表设备 runtime 已接受它；页面显示上传完成，也不代表模型已经启用，更不代表现场漏检和误报达标。每一步都留下对应文件、版本和检查记录，遇到问题才知道该回到训练、转换还是设备端排查。

本文命令按 2026 年 11 月 7 日核对的工程资料整理。输入名、输出节点、SDK 版本和设备页面要按自己的环境确认；工具、基础权重和数据分别按其来源条件使用。

如果你正在做同类部署，可以在评论区说明设备芯片、模型格式和卡住的步骤。请先移除日志中的账号、密钥和客户信息。
