一张 H100 有 80 GB 显存，`allocated`（实际分给 tensor 的字节数）只用了一半，训练却 OOM 了。这个「一半」通常不是峰值瞬间的数值，而是采样没采到峰值点，或者峰值把 `reserved` 抬高之后留下来的常态值。<br> 问题几乎总出在同一件事上：某一瞬间，好几类显存恰好同时占用同一张卡。难点不在某一类占得多，而在它们各自的峰值不在同一个时刻：哪两类在哪一瞬重叠，决定那一瞬的字节数上限。<br> weights、gradients、optimizer states 这一项从 step 0 分配出来就没有释放窗口，单卡占用 68.5 GB，约占 80 GB 的 85%，留给所有动态显存周转的空间只剩 11.5 GB。后面所有手段都是同一类取舍——把快要超出容量的 HBM 字节移到当前还有富余的另一种资源上：用时间换（重算）、用通信换（分片到多卡）、用数值精度换（降位宽）、用 PCIe 搬运换（offload），或者直接用 fused kernel 让中间量不在 HBM 上保存。每一种都有不划算的临界点——换来的空间耗尽，或换出去的资源反而成为关键路径瓶颈。训练显存按生命周期分四类，就能看清谁在哪段窗口里驻留、该用哪种资源把它移走。<br> `reserved` 是 allocator 从显卡驱动一次性申请到的显存总量：驱动一次分配一大块连续显存，叫一个 segment。`allocated` 是 allocator 再把 segment 切成小块（block）、真正分给存活 tensor 占用的那部分。两者永远满足 `reserved ≥ allocated`，差出来的那块是 allocator 持有的、暂时既不还驱动也没分出去的空闲显存，即「碎片」。

### 训练显存的四类开销

> 训练显存的主要增量来自反向传播。推理时一张卡的 HBM 上基本只有 weights，加一份随生成长度增长的 KV cache；训练多出的十几倍几乎都来自反向传播——chain rule 要求前向中间结果和梯度副本一直驻留到反向用完，于是激活缓存、梯度、optimizer state、重算中间值才同时占用卡上的 HBM。下面四类是同一个反向需求在不同生命周期上的分布；去掉反向（即推理）它们全部消失。

按「哪一项占得多」去划分，加起来是总占用，却看不出 OOM 卡在哪一环。改按生命周期划分，关注每一类显存什么时候分配、什么时候释放、有没有可能跨 step 还被保留。

四类按占用从高到低排列：当前最高的那类降下来后，下一类就成为主导项。

### 恒定占用：weights / gradients / optimizer states

生命周期跨 step 不变：从初始化那一刻分配出来，持续保留到训练结束。每一步前向 / 反向 / optimizer 都要读它们，没有任何释放窗口。

体现在 reserved 曲线上：训练启动后几个 step 内，reserved 分几次跳到一个稳定值，此后整段训练再不变，这一段即恒定占用。

必须提前一次性分配：DDP（Distributed Data Parallel）下，模型刚 build 出来就占满。FSDP（Fully Sharded Data Parallel）和 ZeRO（Zero Redundancy Optimizer）是个特例，把 weights / gradients / optimizer states 按 rank 分片到多张卡上。除了沿 DP 副本维度分片的 FSDP / ZeRO，TP（按 head / hidden 划分）、PP（按层划分）、EP（按 expert 划分）也都在削减这条恒定基线，只是各占一个不同的维度。

每张卡常驻只持有切片，需要某层时通过 all-gather 把该层全量参数临时聚合出来。但这块拼出来的 buffer 前向、反向各在算到该层时 all-gather 一次、算完即释放（FSDP2 下 reshard_after_forward 默认为 None：非根模块 True、根模块 False），不属于恒定占用。

### Activation：前向累积、反向释放

生命周期由 chain rule 决定：前向算到第 i 层时产生的中间结果，要保留到反向传播回第 i 层、读取完成后才释放。中间隔着「forward 跑完剩下层 + backward 倒回这一层」几十毫秒到秒级的窗口——跨 kernel 却不跨 step。

allocated 曲线上是随 forward 单调累积、随 backward 单调消费的单峰曲线——前向到达峰值时全部 activation 都保留在 HBM 上，backward 每过一层释放一份。这段累积-释放曲线是 Activation Checkpointing 的优化目标。

每个 micro-batch 临时申请：每一步开始前 activation 都不存在；前向算到哪层，那层中间结果就被 allocator 划出 block；分配路径仍留在 caching allocator 内部。

上一个 micro-batch 释放的同档 block 留在池里复用。warmup 之后几乎所有 activation 分配都在 allocator 内部命中已有 block，驱动那条较慢的路径只在分桶不匹配（请求大小不落进任一现成 block 的尺寸区间）或 segment 已用尽时才走。

这一类激活缓存的压缩手段主要有：recompute（前向丢弃中间值、反向到那层再算一遍）、offload 到 CPU 内存、序列并行（按 sequence 维度分片到多卡；Megatron SP（Sequence Parallel）与 Context Parallel / Ring Attention 两类）。

### 单个 kernel 内的瞬态峰值

进入 kernel 时申请、退出 kernel 立刻释放，存在时间只有毫秒甚至微秒级。MoE（Mixture of Experts）的 expert FFN intermediate、FlashAttention（以下简称 FA）backward 的 work tensor、cuBLAS GEMM（General Matrix Multiply）的 workspace 都属于这一类。

在 MemTrace（显存随时间变化的快照时间线图）上，它表现为一道 kernel 刻度宽的尖峰，按时间平均下来几乎看不出来，瞬时却常常达到单层 GiB 级。因为存在时间太短、不进入前向保存的激活，手算 saved activation（前向存下、留到反向消费的中间值）时容易漏掉。

常驻还是临时：看上去是临时的，kernel 跑完就标记为空闲。但 caching allocator 的 free 只把 block 退回池里复用、并不向驱动退还，整段 segment 全部空闲才有资格归还；瞬态峰值那几块大 block 常常和长寿命块（激活缓存、通信预留）位于同一 segment，始终无法同时空出来，于是 reserved 只升难降——它记录的不是此刻用了多少，而是训练至今某一瞬间最多需要过多少连续显存。（固定 shape、`empty_cache`、`expandable_segments` 可使 reserved 回落，属于 allocator 内部机制。）

`allocated` 曲线规律地起落，`reserved` 却是台阶式抬升。「allocated 不高却 OOM」通常就是这道 reserved 台阶造成的。

这类瞬时峰值的解决办法是 fused kernel，把多个 kernel 的中间结果保留在 SRAM、不写回 HBM，单次数据量不会产生几 GiB 的瞬态 buffer。

### 通信 buffer：集合通信的中转缓冲

训练一开始就预分配，此后一直占用。NCCL 按上限一次性预留每条通道的发送 / 接收缓冲、ring（环形逐跳传递的集合通信拓扑）上的中转 buffer、reduce 算法的工作区。

### 通信 stream：overlap 与显存池分裂的取舍

同一条 stream 上的 kernel 严格按提交顺序串行执行，通信和计算共用同一条 stream 时，allreduce 一发就阻塞后面的 GEMM，GEMM 算完才能再发 allreduce，重叠执行也就无从谈起。

为了 overlap，NCCL 的集合通信通常跑在独立的通信 stream 上：集合通信 kernel 独立排队执行，主计算 stream 同时还能发 GEMM。这不是强制要求——集合通信留在 default stream 一样能跑通，只是退化成串行，但 buffer 进入主池反倒不分裂、碎片更少。只有真正存在数据依赖的关键点才用 `wait_event` 显式同步，比如 backward 算到 dW 那一刻等待上一步 allreduce 的 event（stream 级依赖：本 stream 在 GPU 侧排队等待 event，不阻塞 CPU 线程）。

副作用是显存池跟着分裂。caching allocator 按「一个池只服务一条 stream」的规则过滤空闲 block（隔离用于保证正确性：A stream 的 kernel 可能还没读完这块 block，B stream 拿去写会发生数据竞争）。主计算 stream 的池占满之后，通信 stream 名下整段 segment 即便全部空闲也无法被主计算 stream 复用，OOM 由此产生。

反过来，通信 stream 上要是没多少计算 / 通信可重叠，或显存已经紧张到池分裂的额外开销划不来，就不要分出去——让通信留在主 stream，用一点串行换回不分裂的显存池更划算。

### 预分配避开运行时 cudaMalloc 阻塞

通信 buffer 的尺寸由四个因素共同决定：message size、rank 数、NCCL 选定的算法（ring / tree / NVLS）、bucket 聚合（把多个小消息合并成一个大消息发集合通信）。

若是等训练主循环跑起来之后才临时申请，`cudaMalloc` 会阻塞发起它的 CPU 线程，并触发 device-wide 同步：整卡所有 stream 已入队的工作要先排空，卡在集合通信的关键路径上。

中后期 reserved 已接近上限，驱动这一刻可能分配不出连续的几百 MiB，等到通信发不出去才发现显存不够，训练 hang 在集合通信上。预分配在启动时一次性解决这些不确定性，跑起来之后通信 buffer 占用恒定不变，不再与主计算争用驱动。

### 四类合计：以 DeepSeek V3 为例的建模占用

这四类合计对 V4 同样成立。下表 per-GPU 数字取自 NVIDIA Megatron Core MoE 报告对 V3 配置的建模（报告设 256 GPU、PP4×VPP4×EP64，对标 H100 80 GB 容量）：

| 类别 | per-GPU 占用 | 生命周期 |
| --- | --- | --- |
| 恒定占用（weights + gradients + optimizer states） | 68.5 GB | 全程恒定 |
| Activation（forward saved，未压缩） | 131 GB | 单峰 |
| 计算峰值（MoE 专家 FFN（Feed-Forward Network）中间值等单 kernel 瞬态） | 单层 GiB 级 | μs 尖峰 |
| 通信 buffer（NCCL EP（Expert Parallelism）all-to-all + DP（Data Parallelism）allreduce 预留） | 数百 MiB ~ 1 GB 量级 | 全程恒定 |

表中通信 buffer 只计 EP all-to-all + DP allreduce 预留；再加上 PP（Pipeline Parallelism）send/recv（点对点，非集合通信）预留，整体 ≈ 3 GB。

第一行给出恒定基线 68.5 GB，只剩 11.5 GB 供动态显存使用。第二行 Activation 131 GB 是这点余量的十倍有余——recompute、FP8 storage、offload 都是要把它压缩到 11.5 GB 以内；压缩不下去，就只能继续划分恒定基线，腾出更多余量。

未优化前合计 199.5 GB ≈ 2.5× H100。目标是把 per-GPU 总占用压回 80 GB；131 GB 的 activation 是首要压缩目标，可由 fine-grained recompute / FP8 storage / Memory-Efficient Permutation 等手段削减。activation 自身不需要单独降到 80 GB，关键是连同恒定基线一起压进 80 GB。

真实峰值不是各类最大值的简单相加，因为各类的峰并不在同一时刻。判断某套配置会不会超出容量，要逐时刻看占用：四类显存放在同一根时间轴上，恒定占用与通信 buffer 是两条水平线，activation 是一个单峰，计算峰值是一个尖峰。某一刻的占用，就是把那一刻各类的瞬时值相加；真峰值则是这个逐时刻之和在整个 step 里取到的最大值。峰值时刻 t* 会随配置变化。不开 recompute 时，activation 单峰停在 forward 末端，t* 位于那里。开 full recompute 后，forward 末端那段保存的激活被削平，但 backward 早期出现一个新窗口：层间保存的激活还没卸掉几层、当前层 recompute 重算出的 forward intermediate、当前层新分配的 grad buffer 三类在同一窗口叠加，t* 从 forward 末端移到 backward 早期。这只是把它推迟到反向、并非删除，重算那一瞬该层中间量仍要全部在场。峰值是否下降取决于移入窗口的高度：低于被削平那段就降低（V3 full recompute 即把峰值从 199.5 GB 压到 ~85 GB），要是比削平那段还高，反而会更早 OOM。失效条件也由此判断：改 recompute 粒度，等于调整哪几层进入 backward 叠加窗口，t* 往哪移动、各分量的主次，随之确定。

还要再加上那一刻 backward 临时分配的 grad buffer——当前层算到一半的临时量，用完即弃，与恒定基线里那份跨 step 不动的 gradients 不是同一份。

同一时刻的占用分解里，这六项是：恒定占用 68.5 GB，通信 buffer 3 GB（PP send/recv（P2P）和各集合通信预留池也算进来），Activation 保存的激活 12 GB（还没被反向消费完），recompute forward intermediate 2 GB，grad buffer 3 GB，allocator overhead 5 GB（reserved 与 allocated 之间的碎片余量）。恒定占用 68.5 GB 是已切分后的 per-GPU 数（按 Megatron 报告 Table 3 拆为 BF16 weights+gradients 36.4 GB + FP32 main weights+optimizer states 32.1 GB）。不进一步切分，单卡容纳不下。

这六类与开头四类并非一一对应：Activation 在峰值处拆成层间保存的激活和 recompute intermediate（计算峰值瞬态归入后者的重算窗口），另起 grad buffer 与 allocator overhead；恒定占用与通信 buffer 在占用分解里保持不变。

开了 recompute + 1F1B（做一个 micro-batch 的前向、接着另一个的反向，交替）后，峰值位于 backward 早期那个叠加窗口，底下加上恒定占用与通信 buffer，合起来就是 MemTrace 上的峰值。

各分量字节量可以静态估到 ±数 GB；真正无法静态预测的只有两样——峰值落点 t*（取决于运行时 stream 交错、各 kernel 时长、MoE 路由逐 step 波动）和 allocator 碎片余量，都只能事后从 snapshot 里分析出来。

- **恒定占用 / 通信 buffer 两条水平线**：恒定段靠 FSDP / ZeRO 缩减，通信段先看 bucket 合并与拓扑选择。
- **Activation 单峰曲线**：峰值大小取决于同时保留在 HBM 上的 micro-batch 数，以及每个 micro-batch 累积的整段层间保存激活。
- **瞬态峰值**：高度由 kernel shape 决定。代表手段是 fused kernel / FlashAttention 和 tiling，降低的是瞬时峰值，平均占用基本不动。
- **allocator overhead**：来自 reserved 与 allocated 之间的空隙。对应 `PYTORCH_ALLOC_CONF` 里的 `expandable_segments`（虚拟地址预留 + 物理页按需 map，默认未开）、`max_split_size_mb`（限制大空闲块被小请求切碎）。还要保持 batch 与 sequence shape 稳定，减少 segment 反复 split / merge。

snapshot 还能说明峰值那一刻哪些 tensor 同时持有——每个 tensor 都带一段 Python stack trace，直接指到是哪个模块哪一行 forward 分配的、哪个梯度 hook 还在持有它。 OOM 触发时，通常只能拿到两个数字：reserved 和 allocated。先看这两者的差值。

reserved 和 allocated 都接近上限时，空间已经用尽，瓶颈在峰值时刻各类的同时占用量。看峰值时刻哪一类（恒定基线、层间激活缓存、瞬态、还是 allocator 空隙）的量级最大，针对最大的那类优化。这种时候开 recompute 才有意义，它压缩的层间激活缓存正是触及上限的主因。

第二种情况，reserved 已达上限，allocated 却低出好几 GB。这说明可用字节并没有真的被填满，实际是 reserved 被虚高抬起，allocator 占着却没分给谁。抬高 reserved 的三种成因都不靠多用显存：瞬态峰值被抬进 reserved 后不再回落形成的那道台阶、shape 变化造成的碎片、多 stream 分池后一条 stream 的空闲填不进另一条的请求。这三种情况下 allocated 本就不高，再开 recompute 去压缩 allocated 没有收益——压缩的那一维根本不是瓶颈。

> OOM 判断要同时看峰值占用分解（时间维：某一刻同时被持有多少）和 allocator 碎片状态（空间维：池能不能凑出这一刻要的连续大块）。低于上限的峰值遇到碎片化的池照样 OOM；等于上限的峰值若 shape 固定、池无碎片，反而能分配成功。

这套判断准则的失效条件：一次 snapshot 只是某个 step、某张 rank 的快照。MoE 路由逐 step 波动，负载最重的那张 rank 也不固定在同一张卡上——这一回没碰到峰值，不能推导出下一个 step、另一张卡也安全。要做出判断，得在几个高负载 step、几张可疑 rank 上各采样分析一次，看差值是稳定接近上限还是偶发接近上限。

### 四类显存的优化手段

> **符号约定**：`B`=micro-batch、`S`=sequence 长度、`H`=attention head 数、`D`=hidden 维、`L`=总层数（单层索引用 `i`）；小写 `s/b` 与大写 `S/B` 同义；小写 `h` 是 hidden 维（对应这里的 `D`），不是 attention head 数 `H`（沿用各自论文记法）。<br> 字节按 BF16（2 bytes/元素）算，所以一份 `[B,S,D]` 激活 = `2BSD` 字节。`5BHS²`、`10sbh`、`6bch` 的系数已含每元素字节数（如 `5BHS²` 的 5 = softmax 输出 2 字节 + softmax dropout mask 1 字节 + attention-over-V 的 dropout 输出 2 字节；式中 `H` 为 attention head 数，QK^T 的 Q/K 另计入线性项 `4sbh`，不在这 5 里），乘维度后直接得字节，不要再乘一次 2。`5BHS²` ∝ S²，随序列长度平方增长。<br> 并行度记号：`t`=TP（Tensor Parallelism，张量并行）度、`p`=PP 度、`e`=EP（Expert Parallelism，专家并行）度、`N`=切分总卡数、`m_v`=每个 PP rank 的 virtual chunk 数、`P`=Ulysses 序列并行度、`c`=Ring Attention 的 block size、`m`=一个 step 内的 micro-batch 总数、`m_inflight`=1F1B 同时在飞的 micro-batch 数（=p）；`V`=vocab size（词表大小）。

### 恒定占用：分片、降精度、offload

V3 配置下，恒定占用这三块不分片的话，单 rank 要装 weights 36.4 GB + gradients 36.4 GB + Adam FP32 optimizer state（m + v）145.6 GB ≈ 218 GB，远超单张 H100 80 GB 的容量。注意这 218 GB 只算了 BF16 weights(2) + BF16 gradients(2) + m/v(8) = 12 bytes/param；混合精度还要一份 FP32 master weight（4 bytes/param），完整是 16 bytes/param ≈ 291 GB。

这 218 GB（计入 master 则约 291 GB）是完全不分片、单卡承载全量参数状态的量级。前面表里的 68.5 GB 则是 Megatron 报告口径下 V3 配置的 per-GPU 值，按报告 Table 3 拆为 BF16 weights+gradients 36.4 GB + FP32 main weights+optimizer states 32.1 GB（main weights 即 FP32 master，已计入）。

**分片**（多 rank 分担，每加一份并行维度即 /N）：

- **FSDP**：默认把这三类按 sharding 组均匀分片，forward / backward 算到某层时再 all-gather 把全量 weights 拼回来，算完立刻释放——拼出来的临时 buffer 归入激活缓存一类。FSDP 若把 sharding 组开满 256 卡，per-GPU 这三类各占 0.14 / 0.14 / 0.57 GB，总共 0.85 GB。每层都要 all-gather 拼全量、反向 reduce-scatter 归还梯度。组越大，ring 跳数和跨节点份额越多，latency 越容易进入关键路径。
- **ZeRO-1 / ZeRO-2 / ZeRO-3**（DeepSpeed 中的同类机制）：ZeRO-1 只分片 optimizer state，ZeRO-2 加上分片 gradients，ZeRO-3 三类全分片（对应 FSDP 全分片模式）。越往后分片得越多，省下的显存越多，代价是 all-gather（把分片拼回全量参数）和 reduce-scatter（把全量梯度 reduce 后按 rank 切回分片、每卡只留自己那片）——分片越深，每步要重新拼回、归还的量越大。
- **Megatron TP**（Tensor Parallelism）：按 head / hidden 维切分 attention 和 MLP 权重。TP 同时划分这层的 forward 输出 activation（attention head 维 + MLP 中间维），所以 TP 既划分恒定占用又划分激活缓存。原因是权重 `[D, H·d_head]`（`d_head` 为单 head 维，`D = H·d_head`）和它产出的 activation `[B,S,H,d_head]` 共用同一根 head 维度：把权重的 head 列分给 t 张卡，下游 activation 自然只位于本卡持有的那几列 head 上。权重、梯度、optimizer state、这层激活缓存四样被同时按 `/t` 缩减，不必再为 activation 单独配一种划分方式。每层前向 2 次 + 反向 2 次共 4 次 all-reduce、带宽消耗大，所以 TP 通常限制在节点内 NVLink、最多 8-way。一旦超出这个 NVLink 域，每层 all-reduce 会把 IB（InfiniBand）latency 带进关键路径。
- **PP**：把 L 层按 p 段切开，每个 PP rank 只放 `L/p` 层，这一段的 weights / gradients / optimizer state 各 `/p`。划分的维度是层数，只能省恒定占用——同一时刻本 rank 持有的激活缓存仍是本段那几层的占用分解，对激活缓存峰值没有帮助。
- **EP**（Expert Parallelism）：把 MoE 的 expert 按 e 份分到不同 rank，每个 EP rank 只放自己那批 expert，expert 权重 `/e`。MoE 里 expert 权重是参数的主要部分，对恒定占用而言这一维削减幅度最大。 四种切法各对应一个维度，互不争用同一维度，可以相乘：per-GPU 恒定占用 = 全量 / 各相关并行维之积。

**降精度**（位宽减半，显存减半）：

- **FP8 weight（native FP8 param / fp8-param-gather）**：混合精度训练里 weights 通常保留一份 BF16（forward / backward 用）+ 一份 FP32（optimizer 更新精度，又叫 master weight）。这里降低的是前者——把 forward / backward 实际计算、并参与 DP all-gather 的那份工作权重从 BF16 降到 FP8，单 weights 一项再省 2×；FP32 master weight 仍保持高精度（Megatron 仍把 optimizer 的 master / main 参数保持在 FP32 等高精度、不用 FP8；当前 Megatron-FSDP 的 main params dtype 可选 fp32 / bf16 / fp16 / auto）。TransformerEngine（NVIDIA 的 FP8 训练库）和 Megatron 的公开版本已提供支持。它改变的是 forward / backward 的计算精度与 all-gather 的通信精度，optimizer 更新仍在 FP32 计算：FP8 用动态范围换字节数，per-tensor scaling 把数值先缩放进 FP8 能表示的窗口再计算，把丢掉的范围补偿回来——activation storage 这种一次性写、一次性读的量，配上 scaling 就够了。但 master weight、m / v 这类「极小增量反复累加进一个大基数」的量，仅靠 scaling 还不够：每步要加的更新值比基数小几个数量级，量化后落在基数尾数能分辨的台阶之下，加法被整个舍去，即 swamping（大基数把小增量淹没），表现为参数实际不更新、loss 曲线无报错却不再下降。所以这类累加量必须保留一份高精度累加器（占用一部分省下来的字节）。
- **FP8 optimizer state**：Megatron Core MoE 论文里给出的方案，把 Adam 的 m / v 两个 momentum buffer 也降到 FP8，optimizer state 按每参数字节数降到 1⁄4 左右（145.6 GB 是完全不分片的全量估算；报告 Table 3 里已分片后是 32.1 GB）。同样需要保留高精度累加器（swamping 失效条件同上）。

**外移**（移到 CPU 内存 / NVMe）：

- **Optimizer state offload → CPU**：optimizer 那 145.6 GB 通过 PCIe Gen5（≈ 64 GB/s 单向）移到 CPU 内存。Weights 还能再往后退一档到 NVMe（PCIe + filesystem，≈ 7 GB/s 单向）。

降精度只在划分完之后单项仍占几 GB 以上时才划算。FSDP 划分到 256 rank 后 per-GPU optimizer state 已经只有 0.57 GB，再降到 FP8 也只节省约 0.4 GB，不值得为这点字节数增加复杂度。

**带宽是瓶颈**：从 NVMe 把 weights 拉回 GPU 计算一层比 HBM 直接读取慢两个数量级，MFU（Model FLOPs Utilization）会大幅下降，所以只在「单卡资源严重受限、必须容纳大模型」的场景才用，常规预训练几乎不走这条路径。

### Activation 缓存的压缩手段

Activation 缓存是峰值的大头，V3 配置下未压缩前每卡就有 131 GB（约 1.6× 一张 H100）。 **Recompute**（时间换空间）：

- **Full layer recompute**：每层只 save 一个 layer-input `2BSD`，反向把整层 forward + backward 一并跑。按 forward∶backward ≈ 1∶2 估算，原本一个 step 是 1（forward）+ 2（backward）= 3 份算力，full recompute 变成 1 +（1 + 2）= 4 份，整个 step 的 wall-time 增加 ~33%。
- **Selective recompute**：只对 attention / MLP / LayerNorm 某几种 op 重算，节省的缓存少、付出的 wall-time 也少。Megatron selective recompute（Korthikanti et al. 2022）最初做的是只重算 attention 的 `5BHS²` 项。但 FA 已经把这一项从 HBM 消除，`5BHS²` 不再是瓶颈。所以 selective recompute 如今更多按 module 粒度组合决定是否重算，attention 只是候选模块之一。
- **模块级混合 recompute 策略**（module-level hybrid checkpointing）：按 nn.Module 边界标记 checkpoint，不同 module 独立决定是否 recompute。常见的组合是 attention 全 recompute、MoE expert 不 recompute、LayerNorm 选择性 recompute。在 V3/V4 这种 MoE 主导的架构里，它通常比 full layer recompute 更省时间，缓存占用接近全部划分后的水平。

**Offload**（把缓存移到 CPU / NVMe，反向再移回 GPU）：

- **Activation → CPU offload**：走 PCIe Gen5 ≈ 64 GB/s 单向，把每层产出的缓存 DMA（Direct Memory Access）到 CPU pinned memory（锁页内存，不会被换出，GPU 才能直接 DMA）。
- **Activation → NVMe offload**：再慢 10× 以上，预训练中几乎不用。

必须把 PCIe DMA 和 forward / backward 计算 overlap：移下去要赶在下一层 forward 还没需要缓存之前完成，移回来要在反向使用缓存之前预取完。两个方向都得对准时序，任一边没与计算重叠 MFU 就下降——recompute 只在反向单点插入一段重算，offload 要双向与计算重叠，调度余量小得多。

**序列并行**（按 sequence 维切到多 rank 上），长上下文训练靠它削减缓存——序列越长、`S` 相关的那几项越主导，把 `S` 划分到多 rank 是唯一随长度同步缩小数据量的方式。

- **Megatron SP**：补充 TP，划分 TP 没覆盖、原本在每个 rank 上整份复制的那部分激活（`10sbh`——这里的 `10sbh` 指 TP 未划分的 LayerNorm、attention/MLP 两处 dropout 及 block 输入激活，不含 residual）；
- **CP（Context Parallel）/ Ring Attention** 和 **DeepSpeed-Ulysses**：按 sequence 维切，让 attention 数据量随之缩小。CP 每卡只见 `S/N`，Ulysses 用两次 all-to-all 在 sequence ↔ head 间交换维度。再加 **TPSP**（TP 与 SP 配套同开）、**USP**（Ulysses + Ring-Attention 同时叠加；Fang et al. 2024，arXiv:2405.07719），是 long-context 训练目前的常见组合。

**FP8 storage**：NVIDIA Megatron MoE 报告把 FP8 storage 与 fine-grained recompute 并列为压缩 activation 的手段。降低的是前向保存下来的中间值每元素的字节数，activation 是一次性写、一次性读的量，配 scaling 和反量化即可。

**算子融合**（fused kernel，中间 tensor 留在 SRAM、不写入 HBM）。融合的代价分两类：recompute 型（FA、fused norm、fused cross-entropy）不保存中间量、反向重算换取 HBM——FA 反向靠 `Q/K + LSE` 重算 softmax / score（`O` 另用于求 dV 与修正项），fused norm 反向重算逐元素归一化；搬运型与 elementwise 型（MoE permute / dispatch、bias + add 等）节省的只是 forward 写 HBM 的带宽与中间量落地，反向是逆向搬运、不付出重算算力。但融合不是越多越好，也无法把所有 op 全融成一个 kernel：中间量要留在片上，就得占 SM 的寄存器与 shared memory，而这份片上状态预算固定且极小——融合的边界由它限定。 下面几类 fuse 共用同一个机制。SRAM 和 HBM 的容量、带宽都差一个数量级，中间量每在 HBM 上往返一趟就消耗一份带宽。fuse 把数据量沿某个维度划分成小到能整个放进 SRAM 的 tile，逐 tile 算完只把最终结果写回 HBM，中间 tensor 始终留在片上、既不占 HBM 也不付往返带宽——FA 沿 attention 的 `S` 维切、fused norm 沿 token 维（`B·S` 行，行内 `D` 维归约留在 SRAM）切、fused MoE FFN 沿 `C_local`（本卡上落到该 expert 的 token 数）切、fused cross-entropy 沿 vocab 维按行切，是同一机制在不同维度上的四个实例。

失效条件不是「tile 溢出 SRAM」：per-tile 的片上占用是 kernel 设计期确定、必然不超容量的常量，整张中间量本就远大于 SRAM，shared memory 也不像 cache 那样会自动把超出容量的部分回写 HBM。真正卡住边界、也决定「为什么不把所有 op 全融成一个 kernel」的，是两类硬件约束。

一是片上状态预算。中间量留片上要占 SM 的寄存器（256 KB/SM、单线程上限 255 个）与 shared memory（每 block 可配上限约 164–228 KB），还要和 occupancy 抢同一份预算；融合链每拉长一个 op，每 tile 的活跃中间量就多一份，迟早寄存器 spill 回 HBM（融合失效），或驻留 warp 数被压低、藏不住访存延迟，边际收益转负处就是该断开的边界。

二是片上局部性。一个 block 只看得到本 SM 的片上状态加全局 HBM，跨 block（跨 SM）的数据交换只能过 HBM（pre-Hopper 模型；Hopper 起 thread block cluster + DSMEM 让同 GPC 内可走片上 SM-to-SM 直连，跨 GPC 才必过 HBM）。凡是消费者要跨 block 才能凑齐输入处（全局归约、转置、两个 GEMM 间跨 contraction 维的归约、MoE all-to-all），中间量必须整张落回 HBM、融合在此必断——这也是 FA 能沿 KV 轴在线归约把 `QK^T → softmax → PV` 融成一个 kernel，而一般「GEMM → 跨维归约 → GEMM」给多大预算都融不动的原因。任一类约束被触发，已节省的 HBM 占用与带宽就随之恢复。

GEMM 的 epilogue 为什么能留片上？给输出加 bias、做激活，只读这个 CTA 自己刚算出的那块输出，不必读别的 CTA 的数据。判据就在这里——不看中间量是否瞬时，而看 consumer 要的每个输出 tile，是不是只依赖产出它的那一个 CTA（一个 thread block）。

依赖都在本 CTA 就留片上，分两种：逐元素 pointwise，或归约轴整条留在 CTA 内 streaming。除上面的 epilogue（bias、GELU·SwiGLU、scale、residual、dropout 在写回前一并完成），还有 FA 的 `S/P`（沿 KV 在 CTA 内流式）、RMSNorm/LayerNorm(+residual)（归约轴 `D` 整条留在 CTA 内、一个 CTA 一行 token）。要跨 CTA 读取就必须物化——也就是在 producer 已切散到多 CTA 的那根轴上做 reduction / transpose / shuffle：两个堆叠 GEMM（FC2 沿 `F` 归约、而 `F` 已被 FC1 切散到多 CTA）、split-K GEMM、转置、MoE 的 all-to-all / dispatch-combine、不做 online-softmax 的朴素 attention（被迫 materialize 整张 `[S,S]`）都属此类。

归约本身不必然导致物化：只要归约轴留在 CTA 内 streaming（FA 的 KV、norm 的 `D`，running state 小到进寄存器），归约也能片上；物化只在归约轴被 tile 到多个 CTA 时才出现。

tiling 对不对齐、跨不跨 SM、片上还是物化，其实是同一件事：CTA 跑在一个 SM 上，数据在本 CTA 就不跨 SM、留片上，要从别的 CTA 读取就跨 SM、走 HBM。Hopper 起，cluster + DSMEM 让同一 GPC 内的 SM 片上直连，「同 GPC 那一小块」从必过 HBM 变成可走片上；跨 GPC 仍要过 HBM。边界没动，只移了一点。

- **FlashAttention 系**（FA1-4）：把 `S = QK^T`、`P = softmax(S)`、`dS`、`dP` 全部留在 SRAM tile 内。HBM 上只剩 `O ∈ [B,S,D]` 和 LSE `∈ [B,H,S]`。LSE（Log-Sum-Exp）是每行 softmax 的对数归一化因子，反向重新载入 Q/K 配上 LSE 即可在 SRAM 里重算 score 与 softmax（O 用于求 dV 和修正项），不必存整块 score。attention 这部分原本要在 HBM 上 materialize 的是 score / probs / dropout mask 这几块 `[B,H,S,S]`（∝ S²，对应 `5BHS²` 这一项）。参考参数（`B=4, H=32, S=8192, D=4096`、BF16）下，这几块约 40 GiB；FA 后只剩 `O + LSE` 的 0.254 GiB。
- **fused LayerNorm / RMSNorm + residual**：norm 和 residual add 在一个 kernel 内完成，中间 `[B,S,D]` 不写入 HBM。
- **fused dropout + bias + add**：三个相邻小 op 合为一个 kernel，dropout mask（`BHS²`，FA 没启用时几 GiB）和中间 `[B,S,D]` 都不必写入 HBM。
- **fused MoE token permute**：路由后的 token 重排（permute / unpermute）融进 grouped-GEMM 的数据准备路径，permuted 张量不再单独 materialize 到 HBM。Megatron Core MoE 的开关是 `moe_permute_fusion`（底层 TE permute/unpermute kernel）。注意它与报告里的 Memory-Efficient Permutation 是两件事：后者指把路由权重 p_i 吸收进激活、挪到第二个 linear 之前，不是这里的 permute kernel 融合。
- **fused cross-entropy**（长 vocab）：V ≥ 128k 时 logits 这一份 `[B,S,V]` 本来要写入 HBM。把 logits 和 NLL（Negative Log-Likelihood）loss 合并到一个 kernel 内，按 row 流式计算、不 materialize 整张 logits，节省的字节量随 V 线性增长。

### 计算峰值瞬态的压缩手段

瞬态是 kernel 执行中临时占用的 HBM，规模 = f(B, 每卡 token 数, dtype 位宽)。前三类方法按比例缩减规模：缩小 micro-batch B 最直接，CP 把每卡 token 数从 S 切到 S/N，Ulysses 在 attention 外划分到 S/P、attention 内改划分 head 维（H/P），FP8 storage 把位宽从 16 bit 降到 8 bit。fused kernel / tiling 走的是另一条路：不去缩小数据量的尺寸，而是让中间量根本不写进 HBM。recompute 和 offload 对瞬态均无效：瞬态是 kernel 内 μs 级的瞬时量，recompute 针对的是跨 kernel 存下来给反向用的 saved activation，削减它反而新开一个重算窗口、又产生一份瞬态；offload 走 PCIe，搬运延迟比 μs 慢几个数量级，根本来不及在 kernel 算完前把数据量移出。这四类 fused kernel 都走「不 materialize」这条路：

- **FlashAttention 系**：前向要存给反向的 score / probs / mask，和反向自己产生的 dS / dP，FA 都不写 HBM——这些中间量（前向的 `S / P`、反向的 `dS / dP`）都是 tile 内 `[Br, Bc]` 的小块。有两个量容易被误当成 `S²` 瞬态，其实不是：`D = rowsum(dO ∘ O) ∈ [B, H, S]` 反向会先算出来并落 HBM，但它每行只一个标量（`O(S)` 量级），不是 `S²`；`dQ` 在 FA2/3 里（外层并行放 KV 块、让 `dK / dV` 在块内干净累加）要跨 KV 块 atomicAdd 到 HBM，但那是**最终梯度**在汇总，也不是中间瞬态。
- **fused MoE expert FFN**：把 expert 内部的 up_proj + gate_proj + activation（SwiGLU / GELU 等门控激活）+ down_proj 几步在 expert 内 fuse。记号：`C_local` = 路由到该 expert、落在本卡上的 token 数（≈ `T·K·φ`）；`n` = 单 expert 中间维（V3 取 2048），SwiGLU 走 gate/up 两路上投影、中间激活宽 `2n = 4096`，约 0.57× hidden。

这份中间激活 `[C_local, 2n]` 能不能留片上、不写 HBM，取决于 kernel 怎么 tile，而不取决于「融没融」。标准实现（Megatron-Core grouped GEMM、V3 同理）下它实际会落 HBM：FC1 grouped GEMM →（激活可融进 FC1 的 epilogue）→ FC2 grouped GEMM，中间的 `[tokens, 2n]` / `[tokens, n]` 仍要落 HBM。各 expert 权重 shape 相同、只是分到的 token 数不同——GEMM 的 M 维不等，variable-M 一次调用批量算完、省去逐 expert 启动 kernel；`moe_permute_fusion` 融的是 permute、不是这份中间激活。

落 HBM 的根因是 tiling、不是 kernel 边界：FC1 把输出按 N 维切散到多个 CTA，FC2 又要沿同一维（FC1 的输出维 F）跨 CTA 归约。这正是前面判据里「跨 CTA 读取就得物化」那种情形，只能过 HBM/L2。所以即便把 FC1 + 激活 + FC2 强融进一个 megakernel 也没用：一个 kernel 不等于一个 CTA，各 stage 间仍要在 global memory 上会合、激活照样落 HBM；融合省的是 launch 与重读，省不掉这道跨 CTA 依赖。要真留片上，得换成每个 CTA 独占 token 行块、自己做完整 `F` 归约的 FA 式 tiling，代价是降低 GEMM 并行度 / 吞吐。

V3 训练路径同理走 grouped GEMM、这份激活照样落 HBM：按 V3 配置（`B=1, S=4096`）静态估算，`[C_local, 2n]` 单层约 0.3 GiB / 卡，不是单层峰值主导项；主峰是随路由数 K 放大的进出口张量（`[C_local, D]` 量级、随 K 累加）。（估算用负载不均上界系数 1.2 作 C_local 的代理；V3 实际 aux-loss-free、训练全程不丢 token。）

- **cuBLAS workspace shrink**：cuBLAS GEMM 会为每个 handle 申请一块 workspace（大小随 GPU 架构与所选算法变化）。用 `CUBLAS_WORKSPACE_CONFIG` 固定 workspace 上限（如 `:4096:8`，官方口径约增加 24 MiB footprint，多 stream 共享 handle 时还能换取确定性）。但某些 SplitK / 多阶段 GEMM 算法用不了，吞吐可能下降一点；好处是能省下一份瞬态，大模型训练里几十个 cuBLAS handle 同时存在时这部分能累积到几 GiB。
- **Triton / TileLang / CUTLASS 自定义 kernel**：按需 fuse 特定 op 链。FlexAttention 用 Triton 把 mask / bias / attention 一并 fuse。<br> 通信 buffer：减少 staging 份数与尺寸

NCCL 在每个 GPU 上为每条通信 stream 注册一段 staging buffer，尺寸按最坏情况一次预分配，注册后整段常驻、step 内不随消息大小伸缩。V3 配置下每卡每方向 EP all-to-all staging 约百 MiB 级（某配置下估算约 230 MiB，由 buffer 配置算出、非固定常数），加上 FSDP / ZeRO 的 reduce-scatter / all-gather bucket 等，单卡通信 buffer 一两 GiB 起步。

**调度**（bucket 聚合，把多个小消息合并成一个大消息发，一次 collective 用一份 staging）：

- **FSDP / ZeRO reduce-scatter bucket & DDP all-reduce bucket**：把同一层多个参数的 gradient 合并成一次 collective（reduce-scatter 或 all-reduce）。25 MiB 这个默认值只属于 DDP（`bucket_cap_mb`）；FSDP 没有 MiB 级阈值、合并粒度由 `fully_shard` 包裹的 module 单元决定，DeepSpeed ZeRO 的 `reduce_bucket_size` 默认是 5e8 个元素（≈ 1 GB）。bucket 小则小消息多、staging 总量大、带宽利用率低。bucket 大则单次 staging 大、还要等更多 grad 准备好才发，反向关键路径等待时间长。

**配置**（NCCL 环境变量直接调 staging 尺寸）：

- `NCCL_BUFFSIZE` × channel 数（channel 是 NCCL 把一次 collective 拆成的并行通道，每条各占一份 staging）= 每个 rank 预留的总 staging（Simple 默认 4 MiB/channel）；`NCCL_NTHREADS` 调每 channel 线程数、决定 staging 复用速度。
- `NCCL_ALGO` / `NCCL_PROTO` 选算法（ring/tree/collnet/nvls）与协议：协议确定单 staging 块粒度——LL（8 字节原子写 = 4 字节数据 + 4 字节 flag，故有效带宽仅约 50%、超低延迟）、LL128（128 字节 = 120 字节数据 + 8 字节 flag，约 95% 带宽）、Simple（整块、靠 memory fence，带宽最高但高延迟）。

**算法 / 拓扑**（让 staging 走最短路径）：

- **Ring vs Tree vs Collnet vs NVLS**：Collnet（基于 SHARP）借交换机 / fabric 做 in-network aggregation，NVLS 走 NVLink SHARP、把 reduction offload 到 NVSwitch 域。Ring 上 staging 每跳一份，N 卡 ring 一共 N 份 staging，带宽最优但 latency 随 N 线性涨。tree 按二叉树聚合，latency log(N)。NVLS 几乎不在 GPU 显存里留 staging，节点内 8 卡 all-reduce 场景下 staging 压力最低。前提是硬件有 NVSwitch + NVLink SHARP。跨节点或没有 NVSwitch 时退回 ring / tree。
- **拓扑感知**：节点内 NVLink / NVSwitch 走共享内存模型，GPU 能直接读写对方 HBM、不必先拷贝到本地 staging（带宽 900 GB/s 双向）。跨节点 IB（InfiniBand NDR，400 Gbps）要 staging 把数据从 HBM 移到 IB NIC 的 RDMA（网卡直读显存）寄存器再发出去。让 TP 在节点内、PP 跨节点。TP 通信量最大但走 NVLink，staging 占用很低。PP 走 P2P send/recv（不是集合通信）、还容易藏进 1F1B 调度的计算里，通信/计算比低，所以能承受跨节点 latency。EP 看 expert 数、节点数和带宽决定放节点内还是跨节点。

**复用**（直接写远端显存，把中转 staging 换成有界常驻的对称内存 buffer）。对称内存（symmetric memory）是各 PE（此处即各 rank）提前按最大对象 size 申请、地址对称的一块固定预留，用来替换 ring / tree 随跳数翻倍的 staging 和两侧拷贝。代价是单边写要自己管同步和完成语义，且依赖 GPUDirect RDMA 硬件：

- **NVSHMEM**（NVIDIA OpenSHMEM 实现）：rank A 可以直接 `nvshmem_put` 把数据写到 rank B 的显存上、不需要 rank B 主动 recv。省去本地 staging（数据从 producer 的 register / shared memory 直接发出去）+ 远端 staging（数据直接落到目标 tensor）。
- **DeepEP**：早期 / legacy 版本用 NVSHMEM 省去 EP all-to-all 两侧的中转拷贝（收发 buffer 由配置算出，某配置下每卡每方向 ≈ 230 MiB；较新的 DeepEP 已可走 NCCL 后端）。

### 显存类型与优化手段对照表

「优先级」一列表示当前配置下的收益/代价排序：先动富余资源，后动紧缺资源。它会随配置变：通信已是反向关键路径瓶颈时再做恒定占用的拆分反而不划算，算力打满时 recompute 省下的激活缓存得用 step 时间来抵消。

| 显存类型 | 典型手段顺序 | 取舍逻辑 |
| --- | --- | --- |
| 恒定占用 | FSDP / ZeRO > FP8 master + opt state > offload | 先按 rank 摊薄常驻状态；分片收益耗尽后，再考虑降精度或 offload |
| Activation 激活缓存 | recompute > FP8 storage / offload（视代价）> 序列并行类（长上下文 / 负载不均场景）> fused kernel | 通常先用 recompute；FP8 storage / offload 取决于数值风险和带宽；固定 Global Token 时，CP / Ulysses 主要改善负载均衡 |
| 计算峰值 瞬态 | fused kernel（FA / MoE FFN）> kernel 内 tiling | 中间量留 SRAM，省 HBM 往返 |
| 通信 buffer | bucket 调度 > algorithm 选择 > NVSHMEM | bucket 调度通常先改；算法/拓扑依赖硬件；NVSHMEM 用有界对称内存替换随跳数增长的 staging |

Full recompute 用约 33% 的额外重算时间换掉大段层间激活缓存。若激活移出去和取回来的时间能被计算完全覆盖，且 pinned memory 也够用，offload 的边际算力开销反而低于 full recompute。

各手段的失效条件：FSDP / ZeRO 在 sharding 组扩大到 all-gather 慢于反向计算时就不再划算——通信从「藏在计算后面」变成关键路径瓶颈，再分片下去省下的 bytes 抵不过等通信的时间；FP8 storage 失效在反复累加那一类量（swamping），只有一次性读写的激活才换得安全；offload 一旦搬运时间藏不进计算就反过来拖慢，PCIe 来回的延迟进入关键路径，换来的 HBM bytes 抵不过多出来的 step 时间；fused kernel 的 `[C_local, 2n]` 在 backward / recompute 窗口仍可能落回 HBM——反向要把它整张 fan-out 给多个梯度 GEMM，forward 那种「逐 tile 流过、从不整张落地」的办法用不上；融合「不落 HBM」在标准 grouped-GEMM 实现下对反向基本失效；NVSHMEM 用单边写替换掉随跳数增长的 staging，但同步和完成语义要自己管，换取 HBM 字节的同时多出正确性维护的代价。

### 训练峰值量化：FA 之后 HBM 上的残留

今天主流训练框架默认用 FlashAttention，标准 attention 那个 `[B, H, S, S]` 不再 materialize 到 HBM。

峰值主要来自 FA 之后还留在 HBM 上的：MoE 层的 dispatch / permute / expert FFN 中间值，以及 Full Recompute 重算窗口里的中间值。

FA 那段的参考参数（`B=4, H=32, S=8192, D=4096`、BF16）是单 EP rank、单层、单 micro-batch 的尺度——真实训练里还要再乘上 PP、EP 和 micro-batch 数。

未启用 fused expert kernel 的配置下，MoE FFN intermediate `[C_local, 2n]` 会成为主导项之一。启用 fused kernel（把 SwiGLU 融进 FC1 epilogue）后，2n 宽的 pre-activation `H` 在 forward 不再单独落 HBM——逐 tile 在 epilogue 里算完即被消费（FC2 仍要读 n 宽的 post-activation，即 FC1→FC2 跨 CTA rendezvous）。但这条收益对反向容易失效：反向算 expert FFN 梯度时，forward intermediate `[C_local, 2n]` 必须在场——无论是 save-for-backward 存下来的，还是 full recompute 现算出来的——它本来就得写出去。此刻还要同时生成它同形状的梯度 `dH`（同样 `[C_local, 2n]`）；forward 那份中间量加上这份梯度，2n 宽这一项要同时驻留两份（上游 `dY`、本层 `dX` 都只有 `D` 宽，不是这里翻倍的来源）。forward 不必把它整张落地（随算随被下一段消费、逐 tile 流过片上），backward 却要整张物化在 HBM 上 fan-out 给多个梯度 GEMM——失效的根因是这道刚性物化边界，不是「tile 超过 SRAM 容量」的问题（一份完整 `[C_local, 2n]` 本就远超 SRAM，forward 也容纳不下，区别只在它不必整张物化）；若重算与求梯度又拆成两个 kernel，现算出的 `[C_local, 2n]` 还得借 HBM 中转。

### Full Recompute 之后峰值仍达 80 GB：差值来自哪几项

上面 MemTrace 占用分解那 93.5 GB，是部分 recompute（层间激活缓存还残留 12 GB）时截下来的快照；这里改为分析 full recompute 把层间激活缓存降到下界后，峰值还剩多少、能不能回到 80 GB 以内。三个配置档的峰值依次递减：未优化 199.5 GB、部分 recompute 削到 93.5 GB、full recompute 继续降低。每减一档，消去的是仍有优化空间的量，留下的接近无法再削减的下界。

把 Activation Checkpointing 开到 full layer 粒度（每层只 save layer-input、反向时整层重算）之后，layer-input 一份只有 `2BSD`。下面用 DeepSeek V3 部署配置。

DeepSeek V3 配置（PP=16、L=61、S=4096、B=1、D=7168，BF16）下，整段层间激活缓存（特指 full recompute 后仍保留的 layer-input）的上界也就约 3.5 GiB（2BSD×61 计算为 3.34 GiB、3.58 GB），看起来 80 GB 该够。

但逐项相加得到的峰值仍在 80 GB 附近，超出 H100 容量。3.5 GiB 只是峰值里层间激活缓存这一项，跟总峰值不是同一口径；剩下那七十多 GB 由哪几类合计而成？

按 per-GPU 视角逐项算（EP 路由波动下最重 rank 只会更吃紧），六类分量与前面占用分解相同（恒定 68.5 GB、通信 3 GB、allocator overhead 5 GB 不变），只有层间激活缓存从 12 GB 换成 full recompute 下的 3.5 GiB：

- **层间激活缓存**：每层 save 一个 input `2BSD`；1F1B 下总激活缓存和 PP 大小 p 无关。V3 量级 ≈ 3.5 GiB。
- **当前正在被重算那一层的 forward intermediate**：autograd（PyTorch 的反向自动微分）算梯度时必须有 forward 中间结果在场。recompute 换来的是时间、不是让这部分消失——重算的那一瞬间该层所有中间产物都保留在 HBM 上。FlashAttention 已消去 attention `S²` 项；V3 用 MLA，attention 这边 recompute 出的 Q/O 各约 `[B,S,D]`（V3 配置下单份 56 MiB），KV 走低秩 latent（kv_lora_rank=512）远小于 `[B,S,D]`，连同 dO/dQ/dK/dV 与 LSE 一并写回 HBM，单层不过几百 MiB。大头在 MoE：expert FFN 的中间 `[C_local, 2n]`（约 0.3 GiB），以及按路由复制的进出口张量（`[C_local, D]` 量级、随 K 累加，是 V3 细粒度下的单层主导项），再加各 LayerNorm 输入，单层瞬间合计约 2 GB。
- **当前层 backward 的 grad buffer**：入 grad（dY）+ 出 grad（dX）+ 当前层正算出的权重梯度 dW（用完即并入梯度存储），合计约 3 GB，是「当前层算到一半的瞬态量」，与跨 step 常驻、供 optimizer 消费的那份 gradients / FP32 master grad（全精度累计副本，防 BF16 累加舍入）不是同一份：后者属恒定基线、随 N 分片、已计入 68.5 GB，不在这里重复计。
- **allocator overhead**：`reserved − allocated`，取决于 shape 稳定性和 segment 碎片率。V3 预训练 shape 稳定、碎片率低，按几个百分点估约 5 GB。 六项相加（3.5 GiB 折 3.76 GB 统一单位）：68.5 + 3 + 3.76 + 2 + 3 + 5 ≈ **85 GB**。

这组分量可代入估算。恒定基线 ≈ 218 GB ÷（FSDP×TP×PP×EP 各相关维之积）。层间激活缓存 ≈ `2BSD × (L/p) × multiplier × recompute_factor`，其中 `multiplier` 是 PP 调度系数（1F1B≈1×、VPP≈1.23×），`recompute_factor` 是该粒度下每层的保留比例（full recompute 取 1，不开则是整层中间结果的倍数）。重算 intermediate 与 grad buffer 正比于当前层 shape，allocator overhead 按 reserved 的几个百分点估。

若峰值超出容量 5 GB，同一时刻占用最大的是恒定那 68.5 GB，该动的就是它：用 FSDP / ZeRO（或 TP / PP / EP）进一步分片，或用 FP8 压低 master weight / optimizer state。层间激活缓存只剩 3.5 GiB，再加大重算，收益已经很小。

### CP/SP/PP/TP 各分片哪一段显存

**想降低恒定 68.5 GB：用 FSDP / ZeRO**。这三类里 weights 仍是单卡全量、梯度与 optimizer 只做了初步分片，冗余还在。FSDP / ZeRO-3 全部分片后 per-GPU ≈ 218/N（前面已算过 256 路分片到 0.85 GB）。PP（按层划分）、EP（按 expert 划分）同样把这部分降到这条恒定基线。

每个 step 都要 all-gather + reduce-scatter，再往下分片省下的显存会被新增的通信开销抵消。这时要退回到 HSDP（hybrid sharding，组内分片、组间用 DDP）或限制 sharding 组大小。

**层间激活缓存靠什么分片：CP/Ulysses 划分 sequence 维，Megatron SP 只补 TP 没覆盖、每 rank 各存一份的那部分**。

设每 step 的 Global Token Size = G，切 sequence 后每个 rank 持有 `G/N` 个 token，attention 数据量总和没变。固定训练目标下这只是负载均衡（把最长样本横向切开分摊到多卡）。

Global Batch Size 固定时，划分序列会让 Local Batch Size 上涨，省下的又被原样涨回：总卡数固定，新拿去划分 sequence 的卡只能从 DP 维分出，DP 度一降，`global_batch = DP × local_batch` 里每个 DP rank 摊到的 local batch 就成倍上涨。这种抵消对所有 activation 项都成立：CP 沿 sequence 维把每项都切到 `1/N`、batch 又涨回 `N` 倍，二者精确抵消，单卡峰值净变化趋近零。但抵消假设涨上来的 local batch 由并发 micro-batch 承担——峰值激活只由同时在飞的 micro-batch 数决定；若改用梯度累积让多出来的 batch 串行跑，峰值激活并不回弹，CP 切出的 `S/N` 不被抵消、仍净省。例外条件是：当训练目标是训更长 context、要容纳单卡放不下的 sequence 时，CP 这时加卡用来容纳更长 `S`、不从 DP 分卡，local batch 不回弹——此时相对「不切 sequence 直接训练同样长度」，划分 sequence 才真正压低单卡 activation。长 context 触发这个例外：序列越长，随 S 增长的 activation 整体越大，到某个长度单卡就容纳不下，除了沿 sequence 维切开已无别的办法。

- **Megatron SP**：把 TP 没覆盖、原本每 rank 各存一份的 `10sbh` 也沿 sequence 维切掉（`10sbh` 是 SP 之前的复制量，SP 后 `/t`），不动 attention。
- **Context Parallel / Ring Attention**（Liu et al. 2023, arXiv:2310.01889）：切 sequence 维，每卡只持有 sequence chunk `S/N`，attention kernel 内的数据量随 S/N 缩小。论文 Table 1 给出每 host 单层 attention activation = `6bch`（c 是 block size，与总 sequence 长度 s 解耦）。
- **DeepSpeed-Ulysses**（Jacobs et al. 2023, arXiv:2309.14509）：用两次 all-to-all 把表征从「全 S + 部分 head」轮换到「部分 S + 全 head」。原始约束是并行度 `P` 受 attention head 数整除关系限制；GQA grouped-query / MQA multi-query attention 下（KV head 比 query head 少）实践上限常受限于 KV head 数，但新实现可经 KV replication 放宽到 `P > KV head`。

**反向当前层的临时量和 kernel 数据量：TP 或 fused kernel**。峰值窗口里的动态量分两种：一类是 chain rule 决定的反向临时量：重算出的 forward intermediate、与它同形状的中间量梯度（MLP/MoE 这档宽 `2n`，V3 = 4096，与 forward intermediate 同形状双份，是峰值大头），以及 dY、dX、dQ、dK、dV 这类宽 D 的边界梯度，生命周期覆盖当前 backward / recompute 窗口；另一类是真正 μs 级的 kernel workspace。前者不能删，只能用 TP 减少每卡持有的 head / hidden 切片——attention / MLP 数据量同样划分 /t，代价是每层前向 2 次 + 反向 2 次 all-reduce、对 NVLink 带宽敏感。后者能靠 fused kernel 或 workspace 配置缩小。

**PP 对激活缓存帮助有限：分片层数和 micro-batch 数互相抵消**。PP 大小 p 在激活缓存公式里被直接约掉：1F1B 第一阶段同时在飞 `m_inflight = p` 个 micro-batch（m ≥ p 时；m 更小则只在飞 m 个，抵消不完全）。原因：1F1B 启动时先逐级跑完 p 个 micro-batch 的前向、把 p 级流水线填满，才轮到第一个 micro-batch 的反向，同时驻留 p 份激活缓存，正好与 PP 度 p 约掉。

Korthikanti et al. 2022（arXiv:2205.05198 §4.2.3）给出的最优 schedule，bubble（流水线里各 stage 互相等待造成的 GPU 空闲）最小化的代价是内存压力集中在 pipeline 第一个 stage。每个 PP rank 分到 `L/p` 层，总激活缓存 = `p × L/p = L 层的量`。

PP 调大不能数量级地降低激活缓存，schedule 选择只能微调 multiplier。1F1B 的 multiplier 是 1×。VPP（Virtual Pipeline Parallelism，把每个 stage 拆成 `m_v` 个 virtual chunk 交替跑以降低 bubble）≈ `1 + (p-1)/(p · m_v)`，p=16、m_v=4 时 ≈1.23×（按 VPP 内存公式代入）。DualPipe（DeepSeek V3 双向流水线，forward / backward 从两端对进，峰值激活缓存仍接近 1F1B、只多出约 1/PP）≈ `1 + 1/PP`（这里只比激活缓存；DualPipe 另需双份模型参数副本，是一项独立的恒定占用代价，V3 靠大 EP 摊薄）。V3 量级（PP≥8）下三者的 multiplier 都落在 1× ~ 1.25×。

schedule multiplier 讨论只在不开 recompute 时才显著：那时激活缓存是整层中间结果，V3 未压缩前每卡 131 GB，1× 与 1.25× 能差出三十多 GB。开启 Full Recompute 后，每层只 save 一个 layer-input `2BSD`，激活缓存缩到 3.5 GiB（V3 量级），multiplier 差异不到 1 GiB，与反向当前层的临时量相比差了一个数量级。此后降低显存主要看反向当前层的临时量与 kernel 数据量（TP + fused kernel）。

**分片维度对照**

| 工具 | 划分对象 | 量级效果 |
| --- | --- | --- |
| Activation Checkpointing | 层间激活缓存 | 缩减到只剩 layer-input 2BSD |
| Activation Offload | 层间激活缓存（移到 CPU） | 受 PCIe 带宽限制，覆盖不了 μs 级 kernel workspace |
| FSDP / ZeRO | 恒定占用 | 按 DP 度数 N 划分，每卡 /N |
| PP（pipeline） | 恒定占用（按层 L/p 摊） | 每 stage 参数 /p；不划分激活缓存（一卡放 L/p 层、激活缓存 ∝ L/p × m_inflight，p 在两头约掉） |
| EP（expert parallel） | 恒定占用里的 expert 权重 | 每卡 expert /e；划分的是 MoE 参数大头，dense 部分不动 |
| TP（Megatron） | 恒定 + 激活缓存 + kernel 数据量（按 head / hidden 维划分） | attention 数据量 /t、MLP 中间 /t；受 NVLink 带宽限制，最多 8-way |
| Megatron SP | TP 未覆盖的 sequence 维 | 10sbh（每 rank 各存一份）/t；不动 attention |
| CP / Ring Attention | 全局 sequence 维 | 每卡 S/N；Global Token 固定时作用是负载均衡 |
| DeepSpeed-Ulysses | sequence + head 两次 all-to-all | 同 CP，但 P 受 attention head 整除限制（GQA/MQA 下常受限于 KV head 数，可经 KV replication 放宽） |
| 小 micro-batch B | B | 瞬态量随 B 降低；代价是单 kernel 数据量变小、算力利用率下降，且 PP 下 m 会变大（激活缓存总量不变） |
| FlashAttention | attention 的 S² 项 | 移到 SRAM，HBM 只剩 2BSD（O）+ 4BHS（LSE，FP32） |

### Hopper → Blackwell：PP 依赖随硬件扩容下降

之前讨论的前提是单卡 HBM 容量与 NVLink 域大小固定不变；这两项参数一旦变了，最先受影响的就是 PP。

PP 主要解决两件事：一是单卡 HBM 容纳不下整个模型，只能按层把恒定占用分摊到多卡；二是模型必须跨节点划分时，PP 的跨 stage 通信量比 TP/EP 小得多，能用较低带宽的连接承载——代价是流水线 bubble。V3 当年 PP=16 配 DualPipe，就是针对跨节点流水线受限的连接设计的。

单卡 HBM 从 H100 80 GB 到 H200 141 GB 再到 B200（HGX B200 常见可用 180 GB HBM3e，物理口径 192 GB），一张卡能容纳的层数随之上升，容量约束首先放宽。更关键的是 NVLink 域的扩张：Hopper 一域 8 卡，到 NVL72 一域 72 卡。原来必须跨节点、只能交给 PP 走低带宽连接的那部分 TP/EP，现在能整块放进同一个高带宽 NVLink 域里，低带宽连接的约束也随之消失。这两条约束都放宽后，PP 那份 bubble 代价就不再划算，对 PP 的依赖会逐步下降。
