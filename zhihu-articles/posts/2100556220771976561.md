最近面试了几家公司，发现有些公司对 AI Agent 的热情，已经到了近乎迷信的程度。

仿佛只要招几个懂 Agent 的人，传统研发就可以打包送走了。

![](https://pic4.zhimg.com/v2-e51a39b6ea75ac26744f08be6c788cfb_r.jpg)

那架势，像是终于找到了软件行业的永动机，老板负责提需求，Agent 负责干活，程序员负责交接工牌。

我倒不是反对 Agent，Agent 确实很有用，但**有用和万能之间，恐怕还隔着一整个软件工程。**

## **什么都上 Agent，图什么？**

我对 Agent 的理解比较简单：

> **相当于给传统软件装上一个能思考、能自主决策的大脑。**

以前很多事情，程序员得提前写好规则和流程，现在可以让 Agent 理解任务、选择工具，甚至自己决定下一步怎么做。

这确实是很大的进步。

但问题来了，**难道所有业务都需要一个大脑？**

比如一个简单的优惠计算，几行代码就能搞定，非要请 Agent 来思考一下，算完还得找另一个 Agent 复核。

代码没省几行，Token 倒是花不少。

**能用普通代码解决的，就没必要硬上 Agent。**

流程明确、需要模型参与的，可以采用 Workflow（工作流），真正需要自主判断、动态选择工具的，再考虑 Agent，复杂场景也完全可以组合使用。

技术选型不是赶时髦，更不是看谁的架构图里 AI 方框多。

## **给软件装了大脑，还得装刹车**

Agent 最厉害的地方，恰恰也是它最需要注意的地方。

传统软件的业务逻辑大多由程序员事先定义，而 Agent 可以把部分决策交给模型。

这意味着，**即便程序没有 Bug，Agent 也可能做出不符合业务预期的判断。**

比如让 Agent 帮用户查询订单，完全没问题。

但如果它还能自主退款、修改账户、操作数据库，那就得好好设计了。

毕竟它一本正经地胡说八道，最多让人笑话两句，一本正经地执行错误操作，可能就得有人掏钱了。

当然，现在 LangGraph 等框架的工程能力已经相当成熟，状态管理、人工审批、执行追踪都有现成方案。

> **问题不是有没有刹车，而是什么时候该踩刹车，不能全听大脑自己的。**

退款资格、金额限制、权限校验这些确定性的规则，该由代码把关的还是得由传统业务代码把关，这也是 Agent 开发规范的一部分。

以前常说，用人不疑，疑人不用。

到了 Agent 这里，我觉得最好反过来：

> **用归用，疑归疑。**<br>**既要相信它有能力办事，又要做好它办错事的准备。**

## **Agent 越能干，工程能力越不能丢**

Agent 确实给软件带来了新的能力，但并不意味着传统软件工程就可以扔了。

它要查数据，得有可靠的数据源；要操作业务，得有可靠的接口；要完成交易，背后还得有完整的业务系统支撑。

权限、成本、数据一致性、异常处理，这些老问题不会因为引入 Agent 就自动消失。

有些公司想靠 Agent 省掉传统研发，我总觉得这逻辑有点奇怪。

好比招了个特别聪明的员工，就觉得财务、审计、风控都可以裁了。

理由也很充分：他这么聪明，应该不会犯错吧？

**问题是，聪明和可靠，从来不是一回事。**

我一直在实践 AI 开发，也认可 Agent 的价值，但越是实际使用，越觉得没必要把它神化。

该用 Agent 的地方大胆用，该写代码的地方老老实实写代码。

> **毕竟软件是拿来解决问题的，不是拿来证明自己跟上 AI 时代的。**
