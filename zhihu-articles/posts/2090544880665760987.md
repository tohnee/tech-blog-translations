现在，我们希望将数据集转换为文档对象列表。为此，我们将遍历数据库中的所有电影。对于每部电影，我们将提取要作为元数据添加的属性。在某些情况下，没有可用的属性，此时我们必须确保我们得到的是字符串，而不是 `None` 值。

另一个特殊情况是 `genres` 。在本数据集中，类型以字符串列表的形式提供。不幸的是，我们无法将字符串列表存储为元数据，因此我们必须用分号分隔符连接不同的类型，这是一个设计决策。处理此问题的另一种方法是为每部电影和类型的组合添加一个文档。

你在此阶段做出的设计决策将对后续的数据处理产生重大影响。在许多情况下，你可能会在之后意识到需要返回数据处理步骤。

属性 `fullplot` 在我们的文档中用作 `page_content` ，并将用于创建嵌入向量。只有当 `fullplot` 可用时，才会将文档添加到列表中，如代码清单 5.54 所示。

```python
# %% Create List of Documents
docs = []

for doc in dataset:
    title = doc['title'] if doc['title'] is not None else ""
    poster = doc['poster'] if doc['poster'] is not None else ""
    genres = ';'.join(doc['genres']) if doc['genres'] is not None else ""
    imdb_rating = doc['imdb']['rating'] if doc['imdb']['rating'] is not None else ""
    meta = {'title': title, 'poster': poster, 'genres': genres, 'imdb_rating': imdb_rating}

    if doc['fullplot'] is not None:
        docs.append(Document(page_content=doc["fullplot"], metadata=meta))
```

```python
# Display the results
st.header(f"Most Similar Movies: ")
st.subheader(f"Query: '{user_query}'")

cols = st.columns(3)

# Check if there are duplicate results
unique_results = []
seen_titles = set()

for doc, score in similar_movies:
    if doc.metadata['title'] not in seen_titles:
        unique_results.append((doc, score))
        seen_titles.add(doc.metadata['title'])

# Display only unique results
for i, (doc, score) in enumerate(unique_results):
    if i >= len(cols):
        break
    with cols[i]:
        if doc.metadata['poster']:
            try:
                st.image(doc.metadata['poster'], width=150)
            except:
                st.write("No poster available")
        else:
            st.write("No poster available")
        st.markdown(f"**{doc.metadata['title']}**")
        st.write(f"Genres: {doc.metadata['genres']}")
        st.write(f"IMDB Rating: {doc.metadata['imdb_rating']}")
        st.write(f"Similarity Score: {score:.4f}")

if len(unique_results) < len(similar_movies):
    st.warning(f"Note: {len(similar_movies)-len(unique_results)} duplicate result(s) were removed.")
```

## 6 检索增强生成

一个重要的方面是，第 5 章中介绍的向量数据库，通常构成了 RAG 系统的骨干。为了指导模型如何创建最终输出，我们将回到提示工程，并重用我们在第 4 章中学到的概念。最后，数据将被传递给 LLM，在那个阶段，我们将回到在第 4 章中获得的知识。在这方面，RAG 是一座只有在掌握了这三个不同学科的体能后才能攀登的山峰。

我们将在第 6.1 节中介绍 RAG 的概念来开始本章。在获得一般性理解之后，我们将深入探讨检索、增强和生成的各个流程步骤。

我们首先将在第 6.2 节中开发一个简单的 RAG 系统。这个系统将运行得出奇地好，但并不完美。因此，我们将在第 6.3 节中概述高级 RAG 技术。这些改进可以发生在 RAG 系统的不同阶段。高级的检索前阶段技术在第 6.3.1 节中介绍。检索阶段的技术将在第 6.3.2 节中展示；检索后阶段的技术将在第 6.3.3 节中展示。

RAG 的一个替代方案，称为提示缓存，是我们第 6.4 节关注的焦点。当你开发一个 RAG 系统并想要改进它时，你需要评估和量化这些改进的指标。因此，我们将第 6.5 节专门用于 RAG 评估技术。

让我们从 RAG 是什么、为什么需要它以及它如何工作开始。

### 6.1 引言

在我们深入探讨 RAG 如何工作之前，让我们暂停一下，思考一下为什么需要它。想象一下，你正在处理一个大型知识源（例如，一份长文档），并且你想与它“聊天”。

最简单的方法是进行一次 LLM 调用，你将你的问题以及完整的文档作为上下文传递。这种方法通常不可行，因为大型文档可能超过 LLM 的上下文窗口，并且/或者在每个请求中发送完整文档效率不高。请求将花费相对较长的时间才能收到答案，而且也可能相当昂贵，因为每个请求中都发送了许多不必要的令牌。

一个特殊的解决方案是使用提示缓存，我们将在第 6.4 节中详细讨论。但提示缓存更多是针对边缘情况的解决方案。更常见的方法是使用 RAG。通过 RAG，在每次 LLM 请求中，只有最相关的文档会与用户查询一起传递给 LLM。因此，RAG 提供了一种高效快速的解决方案，同时也克服了 LLM 的一些局限性。使用 RAG，你将获得以下能力：

- 访问公司内部信息
- 访问在 LLM 训练知识截止日期之后创建的最新信息
- 获得更基于事实的结果

现在你有了一个大致的概念，让我们深入了解细节：

1. 检索过程

在检索过程中，用户查询会导致对某个数据源的搜索。用户查询至少需要一个文本和一个限制条件，表明应返回多少文档。查询可以在各种不同的知识源中进行搜索。知识源代表大量文档。在这个知识源中，所有文档都根据其与用户查询的相似性进行排名。

[https://github.com/OpenDocCN/geekdoc-dl-zh/tree/master/docs/generative-ai-with-python/img/img-f6.3.html](https://github.com/OpenDocCN/geekdoc-dl-zh/tree/master/docs/generative-ai-with-python/img/img-f6.3.html)

**图 6.3** 检索过程

用户查询被嵌入，其嵌入与知识源中所有文档的嵌入进行比较。基于余弦相似度等相似性度量，文档被排名。提取预定义数量的最相关文档并传递到下一阶段——增强。

1. 增强过程

在增强步骤中，检索到的信息与原始查询相结合，以创建增强的提示。此阶段从整合检索步骤已呈现的相关文档或段落开始。

通常，检索到的信息与用户的查询有明确区分。在这个阶段，提示工程发挥作用并至关重要。我们需要指导 LLM 如何处理信息。传递明确的指令，要求其停留在所提供信息的范围内以避免幻觉。同时，我们应该明确说明如果信息无法回答用户查询时应如何响应。

结果是一个提示，它为语言模型提供了生成准确响应所需的上下文，以及有效使用该上下文所需的指导。增强的提示作为生成与用户查询相关且基于检索信息的响应的基础。在下一步中，我们将更仔细地了解生成过程。

1. 生成过程

RAG 中的生成过程代表了语言模型将增强提示转化为连贯且上下文相关响应的最终关键阶段。与传统语言模型中的标准 LLM 输出生成不同，基于 RAG 的生成在保持自然语言流畅性的同时，整合了检索到的信息。

当语言模型接收到增强提示时，它开始分析检索到的上下文和原始查询的过程。

生成过程中的一个关键挑战是在避免幻觉的同时，保持与检索信息的一致性。模型必须在纯粹的提取式答案（如直接引用检索内容）和更抽象的、综合并重新表述信息的响应之间取得良好平衡。这种平衡通常涉及一些技术，其中模型的生成被明确引导，以停留在所提供上下文的边界内。

虽然这一切听起来相当复杂，但实际上并非如此，正如我们将在下一节开始实现 RAG 时所看到的。

### 6.2.4 生成

### 6.2.5 RAG 函数创建

我们的函数 `simple_rag_system` 将接受一个 `question` 并返回一个字符串。其他步骤与之前完全相同：

1. 检索相关文档
2. 基于这些相关文档创建上下文
3. 创建一个详细的提示，告诉模型如何应用上下文以及用户问题
4. 创建一个将提示、模型和输出处理器捆绑在一起的链

清单 6.8 展示了我们的 `simple_rag_system` 函数的定义，该函数接受 `question` 作为输入参数，并返回 RAG 系统的 `answer` 。

```python
# %% 将所有内容打包到一个函数中

def simple_rag_system(question: str) -> str:

    relevant_docs = retriever.invoke(question)

    context = "\n".join([doc.page_content for doc in relevant_docs])

    messages = [

        ("system", "You are an AI assistant that can answer questions about the history of human civilization. You are given a question and a list of documents and need to answer the question. Answer the question only based on these documents. These documents can help you answer the question: {context}. If you are not sure about the answer, you can say 'I don't know' or 'I don't know the answer to that question.'"),

        ("human", "{question}"),

    ]

    prompt = ChatPromptTemplate.from_messages(messages=messages)

    model = ChatGroq(model_name="gemma2-9b-it", temperature=0)

    chain = prompt | model | StrOutputParser()

    answer = chain.invoke({"question": question, "context": context})

    return answer
```

### 6.3 高级技术

尽管我们简单的 RAG 系统令人印象深刻，但仍有很大的改进空间。改进的机会可以在流程的不同阶段找到。例如，可以对索引流程进行一些改进。

### 数据清洗

RAG 系统中的数据清洗涉及准备和精炼源文档，以优化其检索和生成。这个关键的预处理步骤从基本操作开始，如删除重复内容、标准化格式和处理特殊字符。

然后，文本通常被分割成适当的块，以平衡上下文保留和检索粒度——块太大可能包含无关信息，而块太小可能丢失重要上下文。（我们在第 5 章中详细介绍了这些主题。）高级清洗步骤可能包括以下内容：

- 删除样板内容
- 标准化日期格式
- 解析缩写
- 处理多语言内容

清洗过程通常还涉及元数据丰富，即为块添加相关标识符、时间戳或分类标签，以提高检索准确性。干净的数据是有效 RAG 性能的基础，因为它直接影响检索匹配的质量和生成响应的连贯性。

### 元数据增强

RAG 系统中的元数据增强涉及用超出原始文本内容的额外上下文信息来丰富文档块。此过程包括为文档添加属性标签，如创建日期、作者、主题和分类。

更复杂的增强可能涉及为语义搜索生成嵌入向量、计算可读性分数，或提取关键实体和关系。一些系统实现自动主题建模或分类来添加主题标签，而另一些系统则维护块之间的层次关系以保留文档结构。

这层丰富的元数据不仅提高了检索准确性，还使得在生成阶段能够进行更细致的过滤和上下文理解。这最终带来更相关、来源更充分的回答。

### 块大小优化

RAG 系统中的块大小优化需要仔细平衡多个相互竞争的因素，以最大化检索效果。虽然较小的块提供更精确的检索并减少令牌消耗，但它们可能有割裂重要上下文和打断连贯思想的风险。

另一方面，较大的块保留更多上下文，但可能在检索结果中引入噪声和无关信息，从而可能稀释生成回答的质量。正如第 5 章所探讨的，最佳块大小通常因内容性质而异。技术文档可能受益于更小、更聚焦的块，而叙事内容可能需要更大的块来保持连贯性。

### 上下文丰富

RAG 系统中的上下文丰富涉及用额外信息增强基础内容，以提高其实用性和可检索性。此过程超越了基本的元数据标记，通过整合相关信息、交叉引用和衍生见解，使内容对检索和生成更有价值。

高级丰富可能包括链接相关概念、为技术术语添加定义，或整合领域特定知识。例如，在处理医疗文档时，系统可能自动扩展缩写、添加标准化医疗代码，或链接到相关研究论文。

实际应用可能包括为基于位置的内容添加地理坐标、为基于事件的信息添加时间关系，或添加特定行业的分类体系。

丰富的上下文有助于检索系统进行更智能的匹配，并为生成模型提供更丰富、更细致的信息来处理，最终带来更全面、更准确的回答。

### 嵌入模型微调

RAG 系统中的嵌入模型微调旨在调整通用嵌入模型，以更好地捕捉领域特定的语义关系和细微差别。此过程通常从选择一个基础嵌入模型开始，如 `BERT` （来自 Transformer 的双向编码器表示）或 `句子 Transformer` ，然后在领域特定数据上进一步训练，以更好地理解专业词汇、技术概念和行业特定关系。

微调过程需要精心策划训练对，这些对代表了对特定用例最重要的语义相似性类型——例如，在法律应用中，微调可能包括匹配同一法律概念的不同表述，而在技术文档中，微调可能专注于将问题描述与其解决方案联系起来。

### 6.3.2 高级检索技术

在本节中，我们将介绍几种高级检索技术。我们简单 RAG 解决方案的一个局限性是它不太适合查找特定关键词。对于关键词搜索，有几种不同的算法可用。了解这些算法后，我们将在混合 RAG 系统中使用它们。我们还将介绍倒数排名融合，这是一种通过合并多个检索结果来提高相关性的排序技术，无需复杂的加权方案。在混合搜索的实际实现中，我们将结合向量搜索和基于关键词的方法来增强文档检索。你还将了解查询扩展，这是一种增强用户查询的技术。最后，你将了解上下文丰富。通过这些技术，你可以通过整合额外的基于文档的上下文来精炼和扩展检索到的段落。

### 关键词搜索算法

对于关键词搜索，有多种算法可用，如 `TF-IDF` （词频-逆文档频率）和 `BM25` （最佳匹配 25）。关键词搜索也称为稀疏向量搜索，与我们熟知的嵌入向量（通常称为稠密向量搜索）形成对比。

最流行的稀疏向量搜索是 `TF-IDF` 或 `BM25` 。两者都是信息检索中使用的数值统计方法。它们的目的是评估一个词在文档中相对于文档集合的重要性，如下所示：

- **词频-逆文档频率（ `TF-IDF` ）**

`TF-IDF` 是词频和逆文档频率的乘积。词频（ `TF` ）表示一个词在文档中出现的次数。逆文档频率（ `IDF` ）衡量一个词在整个语料库中的独特性或稀有性。一个词出现的文档越多，其 `IDF` 值就越低。

像“the”或“is”这样的词几乎出现在每个文档中，因此它们的 `IDF` 值很低。其他在多个文档中稀有的词（即它们只出现在少数文档中）因此具有较高的 `IDF` 值。

具有高 `TF-IDF` 值的词表明该词在特定文档中频繁出现，但在文档语料库中并不常见。这些词被认为与识别文档的关键主题更相关。

`TF-IDF` 是一种流行的搜索算法，用于根据文档与用户查询的相关性对文档进行排序。其思想是给在文档中重要但在语料库中稀有的词赋予更高的权重。

- **最佳匹配 25（ `BM25` ）**

基于 `TF-IDF` 构建的一个相关概念是 `BM25` ，它引入了一种基于词频、文档长度和词饱和度的复杂加权方式。

`BM25` 引入了词频饱和的概念。在 `TF-IDF` 中，一个词的重要性随其频率线性增加。 `BM25` 则使用饱和函数。换句话说，在达到某个点之后，一个词在文档中额外的出现不会进一步增加其相关性。这种方法背后的原理是，如果一个词在文档中多次出现，它会产生一定影响，但超过某个阈值后，其影响会减弱。

另一个应用的概念是文档长度归一化。 `TF-IDF` 没有平衡长文档和短文档。为了克服这一不足， `BM25` 对文档长度进行了调整。其原理是，较长的文档自然会有更多词的出现，因此 `BM25` 对分数进行归一化，以防止偏向较长的文档。

`BM25` 在现代搜索引擎中被广泛使用，因为它克服了 `TF-IDF` 的多个局限性。通过饱和度，它更好地模拟了真实文本，其中词频最终会停止增加一个词的相关性。此外，它通过文档长度归一化来补偿较长的文档。

总结一下，我们有两个不同的世界：稀疏向量搜索和稠密向量搜索。现在，你知道如何单独使用它们。然而，我们希望结合两者的优点进行搜索。因此，我们需要一种方法来合并来自稀疏搜索和稠密搜索的结果。

### 倒数排名融合

倒数排名融合是一种用于将多个排序列表合并为单一、统一排序的算法。

其他用于排序融合的算法包括 `CombSUM` 、 `CombMNZ` 或 `Borda Count` 。但倒数排名融合因其简单性、鲁棒性以及处理不完整排序的能力而脱颖而出。让我们来了解它的工作原理。对于不同排序列表中的每个项目，倒数排名融合根据以下公式计算分数：

[https://github.com/OpenDocCN/geekdoc-dl-zh/tree/master/docs/generative-ai-with-python/img/rrfd_1.png](https://github.com/OpenDocCN/geekdoc-dl-zh/tree/master/docs/generative-ai-with-python/img/rrfd_1.png)

对于文档集合 `D` 中的每个文档 `d` ，会根据其在不同列表中的排名计算分数。 `k` 是一个常数，通常设置为 60。因此，公式中唯一的变量部分是 `r(d)` ，即文档在给定列表中的排名。然后，对所有列表的分数求和。

让我们看一个实际例子。图 6.6 展示了倒数排名融合如何对四个文档进行操作，并显示了它们在密集搜索和稀疏搜索中产生的排名。

[https://github.com/OpenDocCN/geekdoc-dl-zh/tree/master/docs/generative-ai-with-python/img/img-f6.6.html](https://github.com/OpenDocCN/geekdoc-dl-zh/tree/master/docs/generative-ai-with-python/img/img-f6.6.html)

**图 6.6** 倒数排名融合：排名计算（左）与融合（右）

左侧显示了两个列表和四个文档的排名。排名被递增显示，相应的倒数排名就是 `1 ÷ 排名` 的结果。在此示例中，文档 `D` 在密集搜索结果中排名第 1，在稀疏搜索结果中排名第 4。

聚合两个结果的方法很简单。将倒数排名相加。以文档 `D` 为例：它从密集搜索获得 `1/1` 的倒数排名，从稀疏搜索获得 `1/4` 的倒数排名。两者相加得到 `1.25` 。对所有其他文档应用相同的方法。

随后，文档根据其倒数排名总和按降序排序。因此，文档 `A` 是最相关的文档，其次是文档 `D` ，依此类推。

倒数排名算法具有有益的数学特性，即收益递减。分数随着排名的增加而非线性减少。直观地说，这种关系是合理的，因为低排名之间的差异（如 1 和 2，或 2 和 3）比排名 1000 和 1001 之间的差异重要得多。

现在，我们有两个相似度列表，需要将它们聚合成一个最终列表。此时，倒数排名融合就派上用场了，如代码清单 6.20 所示。

```python
def reciprocal_rank_fusion(filtered_docs_indices_sparse, filtered_docs_indices_dense, alpha=0.2):
    # Create a dictionary to store the ranks
    rank_dict = {}

    # Assign ranks for sparse indices
    for rank, doc_index in enumerate(filtered_docs_indices_sparse, start=1):
        if doc_index not in rank_dict:
            rank_dict[doc_index] = 0
        rank_dict[doc_index] += (1 / (rank + 60)) * alpha

    # Assign ranks for dense indices
    for rank, doc_index in enumerate(filtered_docs_indices_dense, start=1):
        if doc_index not in rank_dict:
            rank_dict[doc_index] = 0
        rank_dict[doc_index] += (1 / (rank + 60)) * (1 - alpha)

    # Sort the documents by their reciprocal rank fusion score
    sorted_docs = sorted(rank_dict.items(), key=lambda item: item[1], reverse=True)

    # Return the sorted document indices
    return [doc_index for doc_index, _ in sorted_docs]
```

**代码清单 6.20** 混合搜索：倒数排名融合函数（来源： `06_RAG/20_hybrid_search.py` ）

代码清单 6.20 展示了实现：该函数接收两个索引列表——一个来自稀疏搜索，另一个来自密集搜索。此外，我们可以添加一个权重参数 `alpha` ，它为不同的搜索分配不同的权重。

结果 `rank_dict` 被初始化为空列表。有两个循环，每个索引列表一个。每次迭代都会遍历这些列表中的所有文档。对于文档索引，根据公式 `(1 / (rank + 60)) * alpha` （用于稀疏搜索）和 `(1 / (rank +60)) * (1 - alpha)` （用于密集搜索）添加排名值。

因此，我们得到一个按降序排列的聚合文档索引列表。第一个列表元素代表基于倒数排名融合的最相似文档。

此时，我们可以将此函数应用于我们的数据。当 `alpha` 值为 0.2 时，我们在最终结果中给予稀疏搜索 20% 的权重，密集搜索获得 80% 的权重，如下所示：

```python
reciprocal_rank_fusion(filtered_docs_indices_sparse, filtered_docs_indices_dense, alpha=0.2)
[8, 7, 0]
```

最终结果与密集搜索相同。但尝试调整权重因子，你会发现在某个点上顺序会发生变化。

这种混合搜索可以集成到混合 RAG 系统中。然后，这些索引对应的文档将作为上下文信息与用户查询和额外指令一起传递给 LLM。然而，可以想象的是，通常你不需要自己实现像倒数排名融合这样的功能；这些能力已经集成到向量数据库中。

在本节中，我们实现了一个基于 TF-IDF 稀疏搜索的混合搜索。另一种改进检索的方法是查询扩展，我们接下来将讨论这个。

### 上下文丰富

如果你处理的是包含多个不同文档的语料库，区分不同文档可能很困难。例如，如果你处理的是财务文档，一项基本任务可能是区分季度和公司。普通的分块技术可能难以处理这类问题。

图 6.7 展示了概念检索背后的原理，它可以克服这个问题。每个块都通过其自身的上下文得到增强。此上下文提供了关于该块在特定文档中位置的有用信息。例如，增强后的块可能指代所研究公司的前一个和下一个季度。

[https://github.com/OpenDocCN/geekdoc-dl-zh/tree/master/docs/generative-ai-with-python/img/img-f6.7.html](https://github.com/OpenDocCN/geekdoc-dl-zh/tree/master/docs/generative-ai-with-python/img/img-f6.7.html)

**图 6.7** 上下文检索（来源：改编自 `www.anthropic.com/news/contextual-retrieval` ）

上下文检索是如何工作的？来自更大语料库的每个文档都被分块。完整的语料库，或语料库中的相关文档，与一个块一起传递给 LLM，以提取该特定块的上下文信息。

可以想象，将完整的相关文档与每个块一起发送给 LLM 可能会变得极其昂贵。现在，提示缓存的概念就派上用场了。由于提示缓存是 RAG 的一种替代方案，我们将在第 6.4 节中更详细地介绍它。但为了预告这个主题，只需知道提示缓存是解决此问题的一种廉价方案。使用此技术，完整的相关文档会被缓存一段时间，而无需每次都发送给 LLM。

最终，所有块都被处理，并且每个块都通过上下文信息得到了增强。这个新块（上下文加上原始块）现在可以存储在某个向量数据库中。研究发现，这种方法可以显著优于简单的 RAG 系统和混合 RAG 系统。

### 高级检索后技术

文档检索后，你仍然可以改进你的 RAG 系统。一个有趣的方法是提示压缩。想象一下，经过检索过程所有上下文增强的提示变得很长。结果，LLM 必须处理增加的噪声，这降低了 LLM 的性能。此外，由于你需要为 token 付费，成本很高。你能做些什么来节省成本？你可以压缩上下文的长度，同时保持其基本信息，这就是提示压缩背后的思想，如图 6.8 所示。

[https://github.com/OpenDocCN/geekdoc-dl-zh/tree/master/docs/generative-ai-with-python/img/img-f6.8.html](https://github.com/OpenDocCN/geekdoc-dl-zh/tree/master/docs/generative-ai-with-python/img/img-f6.8.html)

**图 6.8** 提示压缩

增强后的用户查询（可能已经变得相当长）被发送给 LLM，以一种保持其含义的方式进行缩短。但是，如果我们把增强后的查询发送给 LLM 来缩短它，那么我们需要把它发送给“最终”的 LLM 来获取 RAG 响应。我们甚至需要两次 LLM 调用——那么意义何在？

这种方法只有在你将长的、增强后的提示发送给一个小型、快速且廉价的 LLM 进行缩短时才有意义。对于 RAG 响应，然后你可以将提示发送给你选择的 LLM。

如果你有大量的大语言模型调用和庞大的上下文，这种方法可以显著降低成本、提升性能并增强效率。

### 编码：提示缓存

提示缓存是 Anthropic 开发的一种新方法，目前仅作为测试版功能提供。回想一下，每次请求都将完整文档传递给大语言模型是低效的。虽然这仍然是事实，但 Anthropic 开发了一种解决此问题的方法。图 6.9 展示了提示缓存概念的工作原理。

[https://github.com/OpenDocCN/geekdoc-dl-zh/tree/master/docs/generative-ai-with-python/img/img-f6.9.html](https://github.com/OpenDocCN/geekdoc-dl-zh/tree/master/docs/generative-ai-with-python/img/img-f6.9.html)

**图 6.9** 提示缓存

使用提示缓存时，用户向大语言模型发送请求。在此请求中，用户将查询与完整文档一起传递。等等，什么？我们不是刚说过发送完整文档极其低效吗？

是的，但用户也告诉模型缓存该文档。大语言模型提供商在首次传递时缓存完整文档。文档并非永久缓存，仅缓存有限时间。在撰写本文时，文档缓存时间为 5 分钟。在此时间间隔内，后续发送给大语言模型的每个用户查询，只要附带完整文档，都不需要新的缓存。相反，系统会从缓存中取出文档来生成答案。

该技术的一些具体用例如下：

- 重复性任务
- 运行大量示例
- 长对话
- 使用 RAG 作为上下文检索器（如第 6.3.2 节前面所讨论的）

在这些用例中，我们想重点关注最后一个。这项技术是实现一种称为上下文检索器技术的关键，它可以显著改善你的 RAG 结果。目前，我们将专注于如何实现提示缓存。提示缓存实现了一种称为上下文检索的技术，这超出了本书的范围。你可以在 `www.anthropic.com/news/contextual-retrieval` 阅读更多关于此主题的内容。

我们将开发一个与大语言模型的持续对话。对话基于一些固定的上下文。在我们的示例中，我们将使用《巴斯克维尔的猎犬》全书。此上下文信息会缓存有限时间，因此我们只在对话开始时创建一次缓存令牌。使用普通的 RAG，我们会将此上下文作为输入令牌随每个请求发送。但由于文档现在已缓存，我们可以获得一些推理增益（更快的模型响应），同时大幅降低成本。

创建缓存比发送普通输入令牌稍贵（大约贵 25%）。其理念是，由于读取缓存令牌比读取输入令牌便宜 90%，因此可以抵消这部分额外开销，从而大幅降低总成本。

```python
        model="claude-3-haiku-20240307",
        max_tokens=1024,
        system=[
            {
                "type": "text", 
                "text": "You’re a patent expert. You’re given a patent and will be asked to answer questions about it.\n",
            },
            {
                "type": "text", 
                "text": f"Initial Context: {self.initial_context}",
                "cache_control": {"type": "ephemeral"}
            }
        ],
        messages=self.messages,
    )

    # 将模型响应添加到消息中
    self.messages.append({"role": "assistant", 
                          "content": self.context.content[0].text})
    return self.context
```

**清单 6.25** 提示缓存：运行模型方法（来源： `06_RAG/40_prompt_caching.py` ）

大语言模型通过系统消息调用。但系统提示不仅包含模型应如何行为和回答的信息。此外，还传递了初始上下文，以及一个将启用缓存的 `cache_control` 参数。此参数需要类型 `ephemeral` 。

还需要传递 `messages` 。模型的响应存储在对象 `self.context` 中。一旦模型输出可用，消息就会被追加。

很好！但我们希望用户能与之交互，因此我们需要获取 `user_query` 并调用我们的 `run_model` 方法。如清单 6.26 所示，我们的下一个方法 `user_turn` 将 `user_query` 作为输入。

```text
def user_turn(self, user_query: str):
    self.messages.append({"role": "user", "content": user_query})
    self.context = self.run_model()
    return self.context
```

### 6.5 评估

RAG 系统运行得出奇地好，但“好”到底意味着什么？我们如何比较不同 RAG 方法的有效性、准确性和效率？因此，RAG 评估技术试图衡量以下参数：

- 有效性：我们的 RAG 系统是否检索并使用了相关知识？
- 准确性：生成的响应质量如何？它们是否基于事实且连贯？
- 效率：我们的系统在不同场景下的表现如何？

为了使所有这些都可衡量和可比较，可以应用不同的指标。存在的指标如此之多，只能介绍其中一小部分。

首先，我们将探讨 RAG 系统面临的一些挑战。基于这些发现，我们将讨论一些指标以及它们如何使这些挑战变得可衡量。

在介绍了几个指标之后，我们将在 Python 中实现它们。让我们首先仔细看看 RAG 系统面临的一些挑战。

### 6.5.1 RAG 评估中的挑战

我们如何衡量答案的质量？一些硬性事实可以检查，例如，从知识源检索到的数据质量如何。我们将关注两个挑战：

- 检索质量：如果检索器获取了不正确或不相关的文档，RAG 系统很可能是不正确的。会发生级联效应，因为 RAG 质量本质上与检索数据的质量相关。幸运的是，有几种指标可用于确定检索质量。
- 主观性：如果你询问多个评估者，他们会对 RAG 响应给出不同的评分。每个人对简洁性和风格都有个人偏好。例如，技术专家可能优先考虑精确性和事实准确性，而外行可能更喜欢可读性和简单性。始终牢记系统的目标用户，并确保评估者经过培训以获得一致的结果。

### 检索器指标：上下文精确度

上下文精确度是一个检索器指标，用于评估真实标签项，并确定它们是否属于上下文信息。在理想情况下，检索器返回的所有相关块都应位于排名靠前的位置。

上下文精确度使用用户查询、真实标签和上下文信息进行计算。所得分数在 0 到 1 之间，值越高表示精确度越高：
