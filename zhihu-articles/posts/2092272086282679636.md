这份报告的核心判断是：**新一代 GLM、Kimi、DeepSeek 的推理优化，已经从单个算子加速，发展为模型架构、量化格式、内存管理、调度和通信的协同设计。** 基于 SGLang/vLLM 做部署时，应先识别实际瓶颈，再选择优化组合；把所有优化开关同时打开，往往得不到最佳性能。

资料核对日期为 **2026-09-30**。本文依据官方模型仓库、推理框架文档和算子库资料，结合性能建模给出工程建议。**本文没有进行实机压测；公式估算、官方公布结果和工程判断会分别说明。**

**一、研究对象：最新模型有哪些变化，为什么影响推理性能。**

本次核实到的代表性模型如下。“开源”在这里主要指可获取权重并自行部署，具体使用权限仍以各模型许可证为准。

| 模型 | 已核实的架构与规格 | 推理优化重点 |
| --- | --- | --- |
| GLM-5.3 | 744B 总参数、40B 激活参数；与 GLM-5.2 使用相同基座；提供 FP8/BF16 权重 | 大规模 MoE、稀疏注意力、长上下文、MTP |
| GLM-5.3-Flash | 320B 总参数、18B 激活参数；稀疏与线性混合注意力；采用 mHC | 降低长上下文成本、混合状态管理、低延迟服务 |
| Kimi-K3 | 2.8T 总参数、104B 激活参数；93 层，其中 69 层 KDA、24 层 Gated MLA；896 个路由专家，每 token 选择 16 个；1M 上下文 | MXFP4/MXFP8、超大规模专家并行、线性注意力状态、长上下文 |
| DeepSeek-V4.1-Flash | 官方 FlashMLA 已明确提供 V4.1 的稀疏注意力和 FP8/FP4 KV 算子 | 稀疏注意力、压缩缓存、算子融合、硬件适配 |
| 对照：Kimi-K2.5 | 1T 总参数、32B 激活参数；MLA；384 个专家、每 token 选择 8 个；256K 上下文；原生多模态 | MLA、MoE 通信、视觉编码与文本推理协同 |
| 对照：DeepSeek-V3/V3.2-Exp | V3 系列的 MoE/MLA，以及 V3.2-Exp 引入的 DSA | 用于解释 MLA、DSA、FP8 和专家通信的技术演进 |

GLM 和 Kimi 的最新规格来自官方 README。[1][2][3] DeepSeek 的最新确认来自官方 FlashMLA 对 V4.1 的明确支持说明；由于本次没有完整核实 V4.1 模型卡，本文不填入未经核实的总参数、激活参数和完整上下文规格。[4]

这几类模型体现了三个趋势：

- **MoE 越来越大**：计算由少量激活专家承担，但所有专家权重仍然需要存放或调入。
- **注意力不再只有全量 KV**：MLA、稀疏注意力、线性状态可能同时存在。
- **低精度进入模型设计过程**：例如 Kimi-K3 从 SFT 阶段开始进行量化感知训练，采用 MXFP4 权重和 MXFP8 激活，而非部署时简单做一次 INT4 转换。[2]

**二、先建立性能模型：推理到底慢在哪里。**

一次请求可以拆成：

```text
flowchart LR
    A[请求与排队] --> B[分词或多模态编码]
    B --> C[Prefill：处理输入]
    C --> D[Decode：逐步生成]
    D --> E[采样与输出]
    F[权重与缓存管理] --> C
    F --> D
    G[跨卡通信] --> C
    G --> D
```

Prefill 和 Decode 的瓶颈差异很大。

| 阶段 | 工作特征 | 常见瓶颈 | 优先优化 |
| --- | --- | --- | --- |
| Prefill | 同时处理大量输入 token，矩阵较大 | Tensor Core 计算、长序列注意力、临时显存 | 高效 GEMM、FlashAttention/稀疏注意力、前缀缓存、上下文并行 |
| 低并发 Decode | 每条序列每轮通常处理一个 token | 权重读取、KV 读取、小算子启动、通信延迟 | 量化、MLA、CUDA Graph、投机解码 |
| 高并发 Decode | 多条序列合批 | 计算、显存容量、MoE 通信和负载不均衡 | Continuous batching、专家并行、负载均衡、调度 |
| 超长上下文 | 历史缓存或状态很大 | KV 容量与读取、索引器、跨卡搬运 | 压缩/稀疏/线性注意力、KV 量化、上下文并行 |
| 多模态请求 | 图像/视频编码后进入语言模型 | 编码器、视觉 token 数量、预处理 | 编码批处理、编码缓存、编码与生成分离 |

一个简化的 Roofline 模型是：

$$ T_{\text{step}} \gtrsim \max\left( \frac{F}{P_{\text{effective}}}, \frac{D_{\text{HBM}}}{BW_{\text{HBM}}}, \frac{D_{\text{network}}}{BW_{\text{network}}} \right) +T_{\text{launch/sync}} $$

其中：

- $F$：计算量。
- $D_{\text{HBM}}$：显存读写量。
- $D_{\text{network}}$：跨卡、跨节点数据量。
- $T_{\text{launch/sync}}$：算子启动、CPU 调度、同步等成本。

这个公式假设部分工作可以重叠；若通信和计算串行，实际时间会更接近各项之和。

**关键区别是：MoE 激活参数少，不代表权重读取量永远只等于激活参数量。** 随着 batch 增大，不同 token 可能覆盖越来越多的专家，但每个专家也能获得更多 token，提升权重复用和 GEMM 效率。MoE 的性能需要同时看“覆盖了多少专家”和“每个专家收到多少 token”。

评估时至少记录：

| 指标 | 含义 |
| --- | --- |
| TTFT | 从请求发出到首个 token 的时间，包含排队、编码、Prefill 等 |
| TPOT / ITL | 每个输出 token 的平均时间或相邻 token 间隔 |
| E2E latency | 完整请求耗时 |
| Output tokens/s | 实际输出吞吐，避免与输入吞吐混淆 |
| P95/P99 | 尾延迟，反映生产体验 |
| SLO goodput | 满足延迟要求的有效吞吐 |
| 成功任务成本 | 完成一个正确任务所需费用，比单纯 tokens/s 更接近业务目标 |

对于长推理和 Agent 模型，**生成速度与完成任务速度也要分开**：更快的模型如果输出更多思考 token、进行更多工具调用，任务总耗时仍可能增加。

**三、计算优化：减少数据搬运、提升矩阵效率、压低执行开销。**

**1. FlashAttention：保留标准注意力语义，减少中间矩阵读写。**

标准注意力：

$$ \operatorname{Attention}(Q,K,V) = \operatorname{softmax}(QK^T/\sqrt d)V $$

朴素实现会产生大规模注意力分数矩阵。FlashAttention 通过分块、片上存储和在线 Softmax，避免把完整中间矩阵写入 HBM。

主要收益：

- 降低中间显存需求。
- 减少 HBM 流量。
- 提升长输入 Prefill 效率。

需要明确：**FlashAttention 通常没有改变全量注意力的二次计算复杂度。** 它优化的是计算组织和数据搬运；真正减少参与注意力的历史 token，需要稀疏或其他架构。

SGLang/vLLM 会依模型、硬件、dtype 和阶段选择 FlashAttention、FlashInfer、FlashMLA、Triton 等后端。[4][5]

**2. MLA 专用算子：避免把压缩表示重新膨胀成完整 KV。**

MLA 将历史信息保存在低维 latent 中，并通过代数变换，把部分投影吸收到查询或输出侧。

部署收益取决于执行路径：

- 如果 Decode 始终使用压缩 latent，能减少缓存容量和读取量。
- 如果运行时将 latent 展开成完整 K/V，部分收益会消失。
- Prefill 与 Decode 的最优路径可能不同：大矩阵计算更适合展开后的高吞吐 GEMM，小 batch Decode 更适合压缩缓存路径。

因此，不能只检查配置中是否写着 MLA；还应检查实际 attention backend 和缓存布局。

**3. GEMM 优化：选择与矩阵形状相匹配的实现。**

主要技术包括：

- FP8、FP4、INT8/INT4 Tensor Core 路径。
- CUTLASS、CuTeDSL、Triton、DeepGEMM 等内核。
- TMA/异步拷贝、双缓冲、多级流水。
- 合适的 tile、寄存器和共享内存分配。
- 权重预排布和量化 scale 布局。
- 小 batch 专用 GEMV/GEMM。

需要避免只看某个大矩阵的峰值 TFLOPS：Decode 的矩阵可能很小，实际瓶颈可能是读取和启动开销。

**4. MoE Grouped GEMM：把很多专家计算组织成少量高效内核。**

MoE 的执行过程通常为：

$$ \text{Router} \rightarrow \text{Dispatch} \rightarrow \text{Expert GEMM} \rightarrow \text{Activation} \rightarrow \text{Expert GEMM} \rightarrow \text{Combine} $$

每个专家收到的 token 数不同。逐专家启动算子会产生大量小 GEMM，效率较低。

优化方式：

- 根据专家重排 token。
- Grouped GEMM 联合处理多个专家。
- Prefill 使用适合可变 token 数的连续布局。
- Decode 使用 GPU 侧计数、masked layout 等路径，减少 CPU 同步。
- 融合 gate/up projection、激活函数及量化。
- 调整 padding，避免对齐造成大量无效计算。

DeepGEMM 官方提供了连续布局与 masked grouped GEMM，并明确对应 Prefill 和 CUDA Graph Decode 等场景。[6]

**5. 更大范围的融合：把通信和计算放到同一条流水线。**

最新 DeepGEMM 的 Mega MoE 可融合 EP dispatch、两次线性变换、SwiGLU 和 combine，并重叠 NVLink 通信与 Tensor Core 计算。[6]

这种优化可以减少：

- 中间张量落地。
- 多次 kernel launch。
- 通信与计算之间的等待。

但融合范围越大，越依赖拓扑、数据布局、对称内存和特定硬件，不能假定对所有 GPU、所有模型均有收益。

**6. CUDA Graph 与编译：降低每轮 Decode 的固定成本。**

CUDA Graph 预先记录执行流程，减少逐算子 CPU 启动成本；`torch.compile` 和图变换还可消除冗余操作、融合小算子。

收益通常在短上下文、低 batch Decode 更明显。

限制包括：

- 动态 batch 需要多个捕获档位或 padding。
- 图捕获和 workspace 占用显存。
- MoE 动态路由、投机验证、混合注意力可能限制完整图捕获。
- 编译和 warmup 会影响冷启动。

应分别测量冷启动与稳态性能，避免把编译时间混入服务吞吐。

**四、内存优化：权重、KV、线性状态和临时空间需要一起规划。**

总显存可以写成：

$$ M_{\text{total}} = M_{\text{weights}} +M_{\text{KV}} +M_{\text{recurrent state}} +M_{\text{workspace}} +M_{\text{graphs}} +M_{\text{communication}} $$

**1. MoE 的容量规划仍然看总参数量。**

忽略 scale、元数据和混合精度层时：

$$ M_{\text{weights}}\approx N_{\text{total}}\cdot b/8 $$

理论裸权重体积如下，使用十进制 GB/TB：

| 模型 | BF16 | 8 bit | 4 bit |
| --- | --- | --- | --- |
| GLM-5.3，744B | 1.488 TB | 744 GB | 372 GB |
| GLM-5.3-Flash，320B | 640 GB | 320 GB | 160 GB |
| Kimi-K3，2.8T | 5.6 TB | 2.8 TB | 1.4 TB |
| Kimi-K2.5，1T | 2 TB | 1 TB | 500 GB |

这是容量下界，**不是实际 checkpoint 大小，也不表示这些精度均存在可部署版本**。实际还包括 scale、保留高精度层、padding、冗余专家及运行时空间。

尤其对 Kimi-K3，即使 4 bit 权重，仍是 TB 级容量问题，需要认真规划多卡或多节点。

**2. PagedAttention：解决缓存分配和碎片问题。**

分页 KV 将逻辑序列映射到物理缓存块，避免为每条请求预留完整最大长度的连续空间。

主要收益：

- 减少显存碎片。
- 支持请求长度变化和动态释放。
- 便于共享前缀及 copy-on-write。
- 提高可容纳并发数。

分页不会直接减少每个 token 的 KV 内容大小，也不会自动降低注意力计算量。[5][7]

**3. Prefix caching / RadixAttention：复用已经计算过的前缀。**

适合：

- 固定 system prompt。
- 相同工具定义。
- 多轮 Agent。
- 同一代码仓库或文档上的连续提问。
- 多个请求共享输入前缀。

vLLM 提供 prefix caching；SGLang 的 RadixAttention 以树结构管理前缀共享。

工程关键：

- 复用依赖实际 token 前缀一致。
- 时间戳、随机字段、工具顺序变化可能破坏命中。
- 负载均衡需要考虑缓存位置。
- 缓存占用可能挤压新请求容量。

建议测量“复用 token 比例”，而不仅是“命中请求比例”：命中短前缀与命中几十万 token 的价值完全不同。

**4. MLA 的缓存容量收益。**

传统 MHA/GQA 的粗略缓存量：

$$ M_{\text{KV}} = 2LBSH_{\text{KV}}d_{\text{head}}s $$

其中 $L$ 为层数、$B$ 为序列数、$S$ 为长度，$s$ 为每元素字节数。

MLA 可粗略写为：

$$ M_{\text{MLA}} \approx LBS(d_{\text{latent}}+d_{\text{RoPE}})s $$

举一个**说明性估算**：若有 61 层，每层每 token 保存 512 维 latent 和 64 维 RoPE，使用 BF16：

$$ 61\times576\times2 = 70,272\text{ bytes/token} $$

单条 128 Ki-token 序列约为 **8.58 GiB**。

若对照一个同为 61 层、8 个 KV head、head dimension 128 的 BF16 GQA：

$$ 61\times2\times8\times128\times2 = 249,856\text{ bytes/token} $$

同样长度约为 **30.5 GiB**。

以上不包含分页对齐、索引缓存、workspace 和跨卡复制，不是最新模型的显存实测。它说明：**缓存结构的改变，往往比单纯调低精度更有决定性。**

**5. 线性注意力：将部分历史 KV 替换为递归状态。**

KDA 类机制可抽象为：

$$ S_t=f(S_{t-1},k_t,v_t,g_t),\qquad o_t=h(q_t,S_t) $$

历史信息被压缩进固定维度状态。对这些层而言，Decode 状态容量和更新成本通常不会随历史长度线性增长。

但 Kimi-K3 是 **69 层 KDA + 24 层 Gated MLA**，因此：

- KDA 层可以使用递归状态。
- MLA 层仍需要历史缓存。
- 全模型显存与延迟不会完全独立于上下文长度。

混合模型还带来新问题：

- Prefix caching 需要保存对应前缀边界的递归状态。
- 投机解码拒绝草稿后，需要正确回滚状态。
- 分支生成需要复制或检查点。
- Prefill 需要高效 scan/chunk 算法，不能逐 token 串行执行。

**6. 分层缓存与 Offload。**

SGLang 的生态包含 HiCache、Mooncake、LMCache 等，用于 GPU、主机内存及外部存储之间的 KV 管理。[8]

适合复用价值高、会话间存在停顿的 Agent 场景：

- 热缓存留在 GPU。
- 温缓存放在主机内存。
- 冷缓存放在外部存储。
- 提前预取，隐藏加载延迟。

是否有收益取决于：

$$ T_{\text{restore}}+T_{\text{coordination}} < T_{\text{recompute}} $$

权重 offload 则不同：专家权重若每轮都需要跨 PCIe 或网络搬运，会直接进入 Decode 关键路径。它更适合容量受限或低并发部署，需要单独评估尾延迟。

**五、量化优化：必须区分权重、激活、KV 和通信。**

| 对象 | 主要目标 | 常见技术 | 主要风险 |
| --- | --- | --- | --- |
| 权重 | 降低容量与读取量 | FP8、INT4、AWQ、GPTQ、MXFP4、NVFP4 | 反量化成本、质量下降、内核不匹配 |
| 激活 | 提高计算吞吐、减少流量 | INT8、FP8、MXFP8 | 动态量化和异常值处理 |
| KV | 提高并发、降低历史读取量 | FP8、专用 FP4 格式 | 长上下文误差、后端限制 |
| 通信张量 | 降低 EP 网络流量 | FP8 dispatch 等 | scale 元数据、数值与格式兼容 |

**1. FP8：现代数据中心 GPU 上的重要基线。**

FP8 相比 BF16 的理论数据体积约减半；如果计算和存储路径都使用低精度，可能同时改善容量、带宽和 GEMM 吞吐。

关键技术：

- per-tensor、per-channel、per-token 或 block scale。
- 处理激活异常值。
- 动态量化融合到前序算子。
- 维持 scale 的正确布局。
- 保留敏感层为高精度。

**权重以 FP8 存储，不等于所有计算均以 FP8 执行。** 若后端先展开成 BF16，收益主要在存储；若动态量化和布局转换单独启动多个内核，小 batch 下还可能抵消收益。

**2. INT4/AWQ/GPTQ：首先解决权重容量。**

- **AWQ**：利用激活信息保护重要权重方向。
- **GPTQ**：通过近似二阶信息补偿量化误差。
- **W4A16**：权重 4 bit、激活保持 FP16/BF16。

典型适用场景是显存受限、低 batch、权重带宽受限的 Decode。

但在大 batch Prefill 中，W4A16 可能因反量化和 Tensor Core 路径不佳，慢于成熟 FP8。选择应依据最终算子路径，而不是只依据位数。

**3. MXFP4、NVFP4 与 QAT：低位浮点的收益依赖训练和硬件。**

这些格式与传统 INT4 的编码、分块 scale 和硬件指令不同。

Kimi-K3 官方明确采用：

- MXFP4 权重。
- MXFP8 激活。
- 从 SFT 阶段开始量化感知训练。[2]

这体现了训练与部署协同：模型在训练时适应低精度误差，通常比把现有模型直接压成 4 bit 更有潜力。

不过，原生低精度 checkpoint、兼容加载器和原生低精度计算支持是三个条件；需要同时满足，才能拿到理想收益。

**4. KV 量化：先关注容量，再验证速度。**

BF16 KV 转 FP8 的理论数据体积约减半，但实际还包括 scale 和布局开销。

收益可能有两条路径：

- 相同显存下容纳更多请求。
- 注意力读取更少字节，降低 Decode 延迟。

vLLM 文档提供 per-tensor 和特定后端下的 per-head 校准，并建议使用数据集校准 scale；直接使用默认 scale 不应被视为质量验证。[9]

DeepSeek-V4.1 的专用格式更说明了不能泛化：

- FP8 缓存条目为 **528 bytes/token**：512 字节数据及 16 字节 scale。
- FP4 条目为 **288 bytes/token**。
- 官方说明该 FP4 格式仅在主 `k_cache` 为 V4.1 FP8 格式时，用于 `extra_k_cache`。[4]

因此，不能据此声称“V4.1 全部 KV 都是 4 bit”，或“全模型 KV 占用恰好减半”。

**5. 量化验证应覆盖长任务。**

建议覆盖：

- 数学推理和长思考。
- 代码生成与测试通过率。
- 工具调用及 JSON/schema 合规。
- 长文精确检索。
- 多轮历史一致性。
- 多模态理解。

MoE 还需要关注 router 误差：路由改变可能影响选中专家，不能仅用普通线性层的平均误差判断质量。

---

**六、并行计算：TP、EP、DP、PP、CP 解决的问题不同。**

| 并行方式 | 切分对象 | 主要价值 | 主要代价 |
| --- | --- | --- | --- |
| TP，张量并行 | 单层矩阵/head | 分担权重和计算 | 逐层 collective，低 batch 延迟明显 |
| EP，专家并行 | MoE 专家 | 容纳超大模型，保留专家完整矩阵 | Dispatch/combine、负载不均衡 |
| DP，数据并行 | 不同请求 | 增加总吞吐 | 权重复制、缓存分散 |
| PP，流水线并行 | 模型层 | 扩展容量、降低部分跨节点 TP | 流水线气泡、单请求逐阶段传递 |
| CP，上下文并行 | 序列位置 | 支持长输入，分担缓存和注意力工作 | KV/状态交换与结果合并 |

**1. TP：并行度越大，不一定越快。**

TP 能降低单卡权重和计算负担，但每层会出现 all-reduce、all-gather 或 reduce-scatter。

优化原则：

- 优先放在高速 NVLink 域内。
- 在显存允许时，实测较小 TP。
- 低并发 Decode 特别关注通信延迟。
- 注意 MLA 缓存可能存在复制，不能假设 TP 倍增就让单卡 KV 等比例缩小。

**2. EP：超大 MoE 部署的核心。**

EP 把不同专家放在不同设备上，token 按路由发送到对应设备，计算后再合并。

性能取决于：

- 每个专家的 token 数。
- 专家分布是否均衡。
- 跨节点 token 比例。
- 网络带宽与消息延迟。
- 通信、计算重叠程度。

DeepEP 提供 MoE dispatch/combine、FP8 dispatch 等通信能力；当前版本的接口、依赖和硬件要求与早期版本已有明显变化。[10]

通信量可粗略表示为：

$$ D_{\text{dispatch}}\propto N_{\text{tokens}}kd_{\text{transfer}}s $$

$k$ 为选中专家数，$d_{\text{transfer}}$ 为实际传输向量维度。专家共置、节点内聚合、latent 表示和 combine 格式都会改变真实字节数。

因此，Kimi-K3 每 token 选择 16 个专家，不能只与 K2.5 的 8 个做简单倍数比较；还要考虑 LatentMoE、表示维度和拓扑。

**3. Expert load balancing：改善最慢设备决定的尾延迟。**

推理中的专家负载可能随业务内容变化，训练时均衡不代表线上始终均衡。

可采用：

- 统计每专家 token 数和每卡负载。
- 重新放置专家。
- 为热点专家增加副本。
- 根据负载选择等价副本。
- 避免迁移过于频繁。

代价是额外显存、权重搬运和控制复杂度。应同时比较负载改善与缓存容量损失。

**4. Attention DP + MoE EP：混合并行更适合部分 MLA/MoE 工作负载。**

其思路是：

- Attention 按请求或请求组分摊，降低部分 TP 通信。
- MoE 通过 EP 在更大的设备组内共享专家。

这种模式可减少 attention 的跨卡切分，并给 MoE 聚集更多 token。SGLang 的 DeepSeek 示例包含 DP attention 配置。[11]

但这属于模型层面的混合并行，不能将 TP、DP、EP 参数直接相乘来推算 GPU 数；必须确认它们对应的进程组关系。

**5. CP：长上下文不能只靠增加显存。**

CP 将序列分布到多卡，可分担 Prefill 与缓存压力。但：

- 全量注意力需要跨分片交换或合并结果。
- 稀疏注意力需要找到远程缓存位置。
- KDA 需要处理递归状态与前缀扫描的边界依赖。

全量、稀疏、线性注意力的 CP 实现并不相同。对混合模型，应分别检查各类层的支持和通信成本。

**6. PP：适合容量扩展，但要测单请求延迟。**

PP 可把模型分成多个层段，适合权重过大、跨节点 TP 成本较高的部署。

高并发时可以让多个 microbatch 填满流水线；单请求低并发时，每个 token 仍需经过所有阶段，容易增加延迟。

**7. Prefill/Decode 分离：按阶段独立配置资源。**

P/D 分离可让：

- Prefill 节点偏向大矩阵、长输入和 CP。
- Decode 节点偏向带宽、持续 batching 和低延迟。
- 两阶段分别扩缩容，降低长 Prefill 对 Decode 的干扰。

代价是传输请求状态：

$$ T_{\text{transfer}} \approx \frac{M_{\text{KV/state}}}{BW_{\text{effective}}} +T_{\text{setup}} $$

长输入能放大 P/D 分离价值，也能放大状态搬运成本。MLA/量化压缩有助于减少传输；混合模型还必须携带递归状态、索引等数据。

**七、算法创新：哪些优化真正减少了必须做的工作。**

**1. DSA：只对选中的历史位置执行昂贵注意力。**

DeepSeek Sparse Attention 通过轻量 indexer 给历史位置评分，选择 top-k，再执行稀疏注意力。V3.2-Exp 官方公开了 indexer 与稀疏 attention 的实现路径。[11]

粗略复杂度：

| 路径 | Prefill 核心注意力 | Decode 核心注意力 |
| --- | --- | --- |
| 全量注意力 | O(S^2d) | O(Sd) |
| 固定 top-k 稀疏注意力 | O(Skd) | O(kd) |

但这是**核心 attention**，全链路还包含：

$$ T_{\text{DSA}} = T_{\text{indexer}} +T_{\text{top-k}} +T_{\text{gather}} +T_{\text{sparse attention}} $$

indexer 可能仍扫描历史位置；稀疏 gather 也可能产生不规则内存访问。不能直接用 $S/k$ 作为整机加速比。

此外，**每步只读取部分 KV，不意味着可以永久删除其他 KV**：后续查询可能再次选中它们。

**2. IndexShare：减少跨层重复索引。**

GLM-5.2 官方介绍 IndexShare，每四个稀疏注意力层复用同一个 indexer，并报告在 1M 上下文下每 token FLOPs 降低 2.9 倍。[1]

其意义是：主 attention 稀疏化之后，索引工作可能成为新瓶颈，可以通过跨层复用减少重复计算。

官方的 FLOPs 收益不能直接等同为：

- 整机吞吐提升 2.9 倍。
- TTFT 降低 2.9 倍。
- 任意上下文长度均有相同收益。

短上下文、MoE 和通信占比都会影响最终效果。

**3. KDA 与混合线性注意力：改变历史信息保存方式。**

KDA 对 gated delta rule 使用更细粒度门控，以有限递归状态表达历史信息。

混合架构的目的：

- 多数层使用成本较低的状态更新。
- 少量全局注意力层保留精细历史访问能力。

Kimi Linear 官方报告其特定实验设置下最高约 75% KV 缓存减少，以及 1M 上下文下最高约 6 倍 Decode 加速。[12] 这些结果属于 Kimi Linear 的实验，不能直接移植为 Kimi-K3 的性能结论。

Kimi-K3 和 GLM-5.3-Flash 表明，这条路线已经进入最新开放权重模型，而其部署要求也扩展到了状态管理、回滚和 scan 算子。

**4. 投机解码：一次目标模型验证多个候选 token。**

投机解码通常包含：

1. 低成本 proposer 生成多个草稿 token。
2. 目标模型批量验证。
3. 接受合法前缀。
4. 对拒绝位置进行正确处理。

技术路线包括：

- 独立 draft model。
- EAGLE 类特征预测。
- 模型原生 MTP。
- N-gram、suffix 等历史匹配。
- 并行草稿模型。

简化收益模型：

$$ \text{Speedup} \approx \frac{\mathbb E[N_{\text{committed}}]T_{\text{baseline step}}} {T_{\text{draft}}+T_{\text{verify}}+T_{\text{overhead}}} $$

必须同时看接受长度、草稿时间、验证时间和额外显存。

通常更适合低至中等 QPS、带宽受限的 Decode；高并发下额外验证计算可能降低吞吐。vLLM 官方也按工作负载讨论了这些取舍。[13]

严格无损依赖正确的验证与拒绝采样。启发式接受、量化误差、数值差异和模型状态回滚错误，不能被统称为“无损加速”。

**5. MTP：训练与推理共同优化接受率。**

MTP 为模型提供多 token 预测能力，可以作为原生 proposer。

优势是可能共享模型特征，减少额外草稿模型成本；GLM 官方也报告了对 MTP 接受长度的改进。[1]

但启用前需要核实：

- checkpoint 是否包含所需权重。
- 框架是否支持该模型的 MTP。
- 是否兼容 TP/EP、量化、图捕获和混合状态。
- 在实际温度、代码或工具调用流量上的接受率。

**6. LatentMoE、mHC、AttnRes：需要区分能力效率与运行时加速。**

| 技术 | 主要方向 | 推理层面需要关注 |
| --- | --- | --- |
| LatentMoE | 在低维表示中组织专家计算 | 实际 GEMM 与传输维度、额外投影 |
| mHC | 改善大模型连接与训练扩展 | 混合、归一化等新增小算子及融合 |
| AttnRes | 改变残差信息聚合方式 | 中间表示保存、聚合成本和专用内核 |

Kimi-K3 官方的“约 2.5 倍 scaling efficiency”属于架构和扩展效率描述，[2] **不应改写为服务 tokens/s 提升 2.5 倍**。同理，改善模型能力的结构可能引入额外执行成本，需要推理内核共同优化。

**7. 推理预算与上下文工程：直接减少任务工作量。**

可采用：

- 按任务难度分配 reasoning effort。
- 控制重复尝试和分支采样。
- 检索相关文件，而非持续累积完整仓库。
- 对工具结果做有依据的压缩。
- 复用编码与文本前缀。

不过要遵守模型的历史输入要求。Kimi-K3 官方要求保留完整 assistant 返回，包括 `reasoning_content` 和 `tool_calls`。[2] 不能为了减少输入，直接丢弃模型依赖的思考历史。

**八、SGLang 与 vLLM：如何选择与落地。**

两者都已覆盖大量共同能力，不能简单归纳为“一个低延迟、另一个高吞吐”。

| 维度 | SGLang 的关注点 | vLLM 的关注点 |
| --- | --- | --- |
| KV 与前缀复用 | RadixAttention、HiCache 及缓存生态 | PagedAttention、prefix caching 及缓存集成 |
| 执行优化 | 模型专用路径、图执行、融合和调度 | CUDA/HIP Graph、编译、广泛 attention/GEMM 后端 |
| MoE | EP、DP attention、专家负载均衡等模型路径 | TP/PP/DP/EP/CP 与 MoE 部署路径 |
| 投机解码 | SpecForge 和模型对应 proposer | MTP、EAGLE、draft、n-gram、suffix 等 |
| 分离服务 | P/D 分离及 Mooncake/Dynamo 等生态 | Prefill、Decode、Encode 分离 |
| 选择依据 | 精确模型和硬件组合的支持与实测 | 精确模型和硬件组合的支持与实测 |

两者官方资料均明确覆盖新模型服务和优化生态。[5][8]

**建议分三层核实兼容性：**

1. **加载支持**：能否正确识别架构并读取 checkpoint。
2. **功能支持**：多模态、工具调用、推理解析、MTP、缓存是否正确。
3. **性能支持**：是否真正使用期望的低精度、稀疏、融合和通信后端。

模型能启动，不代表第三层已经完成。

还需要固定：

- 模型 revision。
- 框架版本或 commit。
- FlashMLA/DeepGEMM/DeepEP 等版本。
- CUDA/ROCm/CANN、驱动和 collective 库。
- quantization 和 KV 格式。

一个现实例子是：**FlashMLA 2026-09-30 版本移除了 Hopper 及 V3/V3.2/V4.0 支持，并更改了 FP8/FP4 KV 格式**；官方要求旧模型或旧格式使用指定旧 commit。[4] 因此不应直接把所有组件升级到 `main`。

**十、可复现的研究与压测方案。**

**1. 建立三种基线。**

- **正确性参考**：模型允许的高精度路径，或官方推荐的数值参考。
- **官方推荐部署**：保留原生量化，使用官方模型 recipe。
- **当前生产配置**：用于衡量实际迁移价值。

对原生 QAT 模型，不必为了构造 BF16 基线而做成本极高且不必要的转换。

**2. 使用真实工作负载分布。**

| 工作负载 | 示例输入 | 示例输出 | 重点 |
| --- | --- | --- | --- |
| 短问答 | 1K | 256 | ITL、启动和调度成本 |
| RAG | 8K–32K | 512–2K | TTFT、前缀复用 |
| 代码 Agent | 多轮 8K–128K | 每轮长度不一 | 缓存、工具调用、任务完成时间 |
| 长推理 | 2K–16K | 8K–32K | Decode、投机、预算 |
| 超长文档 | 128K–1M，按模型能力 | 1K–4K | 注意力、CP、缓存容量 |
| 图像/视频 | 以视觉 token 和分辨率描述 | 按任务 | 编码、预处理、输入膨胀 |

压测应同时使用：

- 固定并发，观察容量和吞吐。
- 固定请求到达率，观察排队和尾延迟。
- 突发流量，观察缓存、抢占与恢复。

只用客户端“收到回复再发下一条”的闭环测试，可能低估过载时的排队问题。

**3. 按瓶颈进行消融实验。**

建议顺序：

1. 确认正确的 attention 和 GEMM backend。
2. 调整 TP/EP/DP 配置。
3. 调整 batch token budget 与 chunked prefill。
4. 测量 prefix cache 冷/热两种情况。
5. 验证 KV 量化。
6. 验证图捕获与融合。
7. 扫描投机长度与 proposer。
8. 测量负载均衡、CP 或 P/D 分离。

每次实验都记录完整配置；验证单项效果后，再测试关键组合的交互。例如 KV 量化释放显存后可能允许更大 batch，这时吞吐收益并不完全来自 attention 本身变快。

**4. Profile 需要看这些证据。**

| 观测结果 | 可能原因 | 下一步 |
| --- | --- | --- |
| 大 GEMM 占主导、Tensor Core 利用率高 | 计算受限 | 低精度 GEMM、并行和 tile 优化 |
| HBM 带宽高、计算利用率低 | 权重/KV 读取受限 | 权重量化、缓存压缩、合批 |
| GPU 时间线上有大量空隙 | CPU 调度、同步、小算子 | CUDA Graph、异步调度、融合 |
| 通信占比高 | TP/EP 拓扑或分组不佳 | 调整并行、压缩、重叠 |
| 某些 rank 持续更慢 | 专家或序列不均衡 | EPLB、长度感知调度 |
| indexer/top-k 占比随上下文上升 | 稀疏路径中的索引瓶颈 | IndexShare、索引器内核、分块 |
| TTFT 差但 Decode 良好 | Prefill 或排队受限 | 缓存、chunked prefill、CP/P/D |
| 平均值好、P99 很差 | 突发、抢占、迁移或恢复 | admission control、队列策略、预取 |

GPU 上可使用 Nsight Systems 观察时序和重叠，Nsight Compute 分析内核；其他硬件使用对应 profiler。

**十一、最值得投入的研究方向与实施顺序。**

近期容易落地的优化是：**官方原生低精度路径、正确算子后端、连续合批、chunked prefill、前缀复用、合理并行和 CUDA Graph**。这些通常无需重新训练模型。

对于已有模型且低并发延迟明显受限，值得进一步研究：

- 适配业务数据的 MTP/EAGLE proposer。
- 动态投机长度和高负载自动降级。
- FP8 KV 校准及敏感层保护。
- 缓存感知路由和预取。

对于超大 MoE、多节点场景，投入重点应放在：

- 专家负载均衡。
- 专家放置与网络拓扑协同。
- FP8 dispatch。
- 通信与 Grouped/Mega MoE 重叠。
- Prefill/Decode 的不同并行配置。

需要模型训练配合的长期方向是：

- 稀疏索引器及跨层共享。
- KDA 等混合线性注意力。
- LatentMoE。
- 面向低位浮点的 QAT。
- 在任务质量约束下减少思考和重复尝试。

这些架构技术通常不能通过修改 SGLang/vLLM 启动参数，把已有 checkpoint 直接转换得到。

**部署决策应遵循“瓶颈—技术—验证”的关系：短上下文低并发重点压低读取和固定开销；长上下文重点减少历史访问与缓存；超大 MoE 重点解决权重容量、专家分布和通信；Agent 场景重点复用前缀并降低完成任务所需的总工作量。**
