2024 年初，我做法律 AI 的第一件事，是写 prompt。

这个选择看起来很自然——当时所有人都在说，用好大模型的关键是写好提示词。角色设定、few-shot 示例、思维链引导、输出格式控制——我把市面上能找到的 prompt 工程技术全试了一遍。到 2024 年中，我的模板库里有 87 个法律场景的 prompt 模板，覆盖了合同审查、案件分析、法规检索、合规检查——你能想到的法律 AI 应用场景。

效果最好的时候，我甚至觉得问题已经解决了——同样的法律分析任务，好的 prompt 输出像一位三年级律师，差的 prompt 输出像一位大一法学生。差距巨大。

然后我做了一个测试，这个测试改变了我对 prompt 工程的看法。

同样一个劳动争议分析任务，同样的 prompt，跑了 10 次。8 次输出基本合格——法条引用正确，分析结构完整，结论没有明显错误。2 次输出有严重问题——一次编造了一条不存在的司法解释，另一次漏掉了案件中最关键的一个事实节点。

**8 次合格，2 次跑偏。而且你不知道哪次会跑偏。**

如果你是一个律师，你愿意在开庭前一天，用一个“80% 概率正确”的工具来准备你的代理意见吗？

---

### 提示词工程做到了什么——先给荣誉，再谈边界

我不是来否定 prompt engineering 的。事实上，好的 prompt 和坏的 prompt 之间的差距，比很多人想象的都大。

提示词工程在法律场景中真正做到了三件事。

**第一，角色约束。** 告诉模型“你是一位精通中国公司法的资深律师，请以法律意见书的格式输出”——这比什么都不说强太多了。角色约束能把模型的输出从“闲聊模式”切换到“专业模式”，语言风格、引用习惯、推理深度都会显著改变。这本质上是在利用模型的 in-context learning 能力——它见过的律师写作风格比任何人都多，你只需要告诉它“现在用这个风格”。

**第二，输出格式控制。** Few-shot 示例可以让模型按照特定结构输出——“请按照以下格式回答：1. 事实概述 2. 法律分析 3. 风险提示 4. 行动建议”。这种结构化的输出对于后续处理非常关键——比如你要把分析结果嵌入一份正式的法律意见书，结构化输出可以直接用。

**第三，思维链引导。** Chain-of-thought prompting——“请一步一步推理，先确定适用的法律，再分析事实是否符合法律要件，最后得出结论”——可以显著提升模型在法律推理任务上的准确性。因为它迫使模型在“得出结论”之前先“展示推理过程”，而推理过程本身就是一种自我校准。

这三件事，prompt engineering 做到了最好。没有任何争议。

但问题在于——**这三件事没有一件能解决“8 次合格，2 次跑偏”的问题。** 因为它们解决的，是正确的 prompt 能提取模型多少能力。它们不解决的，是模型的能力本身有结构性缺陷。

### 天花板一：模型不知道自己何时在编造

这是最根本的天花板。

你可以在 prompt 里写——“请只引用真实存在的法条，不要编造”——写十遍，加粗，用红色标注。模型仍然会编造。

不是因为模型“不听话”。是因为**“编造”对模型来说不是一个有意义的分类。**

大语言模型的工作方式是：给定一段上下文，预测下一个最可能的 token。它没有“我真记得这个法条”和“我不记得这个法条，但我觉得这个法条应该长这样”之间的区分——这两个状态在模型的概率分布中，落在同一个高概率区域。**“看起来像真实法条”的序列和“确实是真实法条”的序列，在概率分布上无法被区分。**

你可以在 prompt 里告诉模型“不要编造”。但这个指令只是在说——“请降低那些’看起来像真的但实际上不是’的序列的采样概率”。问题是，模型自身没有能力判断哪些序列属于这一类。如果它能判断，它一开始就不会生成那些序列。

这就是为什么“更好的 prompt”不能从根本上解决幻觉问题。prompt 是一个语言指令，幻觉是一个概率属性。语言指令无法改变概率分布的结构——它只能在这个分布上做一个偏移。偏移之后，幻觉概率从 X% 降到了 Y%。但 Y 永远不会是 0。

而在法律领域，任何非零的幻觉概率都是一个麻烦。

### 天花板二：规则冲突时的优先级判断——prompt 无法编码条件化逻辑

法律分析中一个非常常见的情况是：两条规则同时适用，但它们指向不同的结论。

上位法和下位法冲突。一般法和特别法冲突。法条字面含义和司法解释精神冲突。不同省份的裁判口径冲突。

律师处理这种冲突时，用的不是“选哪一条”的简单逻辑——是条件化的优先级判断：**“在 A 场景下优先规则甲，在 B 场景下优先规则乙，但如果出现了 C 情况，两条规则都需要让步给原则丙。”**

这种条件化逻辑，prompt 无法可靠地编码。

你可以在 prompt 里写——“当《民法典》第 X 条和《XX 司法解释》第 Y 条发生冲突时，请优先适用司法解释，除非涉及以下三种情况……”这段话模型看到了。但它在生成答案时，不一定会遵守这个优先级——因为在它的概率分布中，“上位法优先”和“特别法优先”和“新法优先”是多个互相竞争的文本模式，而你的 prompt 指令只是其中一个信号，不是最高优先级的信号。

这就是为什么同一个 prompt、同一个问题，不同的运行可能给出不同的冲突处理结果。不是因为模型“忘记”了你的指令——是因为几个竞争性的文本模式在输出层博弈，而你的 prompt 指令没有绝对的胜出保证。

### 天花板三：不可复现性——一个在法律领域致命的属性

同样的 prompt，同样的输入，同样的模型，两次运行——输出不同。

这在很多领域是可以接受的。你用 ChatGPT 写一封邮件，两次输出有细微差异——无所谓。你用 ChatGPT 写一段代码，输出不同但都能跑——也没问题。

但在法律领域，不可复现是一个原则性问题。

如果两个法务同事用同一个 AI 工具查同一个法律问题，得到不同的答案——哪个是对的？如果你昨天用 AI 审了一份合同、结论是“风险可控”，今天重新审同一份合同、结论变成了“需要修改”——你信哪一个？

你会发现，**你用 AI 省下的时间，全都花在了“验证 AI 的输出是否可靠”上。**

而且那个验证过程，本质上需要你把 AI 没做的事重新做一遍——检索法条、查找案例、交叉核对。你原本想用 AI 来跳过这些步骤，但因为输出不可复现，你不敢跳过。

这就形成了一个悖论：**AI 越快，你对它的输出越不信任。你对它的输出越不信任，你的验证成本就越高。验证成本越高，AI 省下的时间就越少。**

prompt 工程无法解决这个悖论。因为不可复现性是概率性文本生成的固有属性——它不是一个可以通过“更好的指令”来消除的 bug，它是这个技术路线的 defining feature。

### 天花板之上——架构层做了什么

写了三个天花板，你可能感觉“那岂不是无解了？”

不是无解。是解不在 prompt 层，在架构层。

架构层解决这三个天花板的方式，不是“更好的 prompt”——是**把 prompt 不擅长的事情，交给 prompt 之外的机制来处理。**

**针对天花板一（模型不知道自己何时在编造）**：不在生成后“检查”——在生成前就堵住编造的路径。法条引用不是让模型从记忆中调取——是让模型调用一个外部的法条检索工具，只使用工具返回的真实法条文本。案例引用也不是让模型“凭记忆”——是让模型调用案例检索工具，然后只使用工具返回的真实案例信息。**模型不是被“告诉不要编造”，是被“剥夺了编造的可能性”。** 它无法编造法条，因为它没有权限凭空生成法条引用——所有引用都必须经过外部验证。

**针对天花板二（规则冲突时的优先级判断）**：不在 prompt 里写“请优先适用特别法”——用一个独立的规则引擎来执行优先级逻辑。规则引擎不是语言模型——它是确定性代码。当《民法典》和某部司法解释冲突时，规则引擎按照预设的冲突处理逻辑（上位法 vs 下位法、一般法 vs 特别法、旧法 vs 新法）给出判定——这个判定是确定性的，无论跑多少次结果都一样。**模型的职责是理解案件事实和适用法律，规则引擎的职责是解决规范冲突。两个系统各司其职，不互相干扰。**

**针对天花板三（不可复现性）**：不是让模型的每次输出都一样——是在模型的输出之上，加一层确定性验证。法条引用是否正确？案例引用是否真实？逻辑是否自洽？关键事实是否被遗漏？——这些验证不是模型自己做的，是独立的验证模块做的。如果验证不通过，输出被阻断，系统返回“这个问题我无法给出可靠的分析”。**宁可沉默，不要胡说。** 而这个“沉默 vs 胡说”的切换，不是依赖模型的判断——是代码门控强制执行。

这三件事——**外部验证取代内部记忆、确定性规则引擎取代语言指令、独立门控取代模型自审**——合在一起，就是“架构”的含义。

它不替换 prompt engineering。好的 prompt 仍然有价值——它决定了模型在“被约束的框架内”能发挥多少能力。但约束框架本身，不在 prompt 里。它在 prompt 之外。

### 从 87 个模板到放弃——一段个人经历

2024 年底，我做了一个在团队内部争议很大的决定：不再把时间花在优化 prompt 上。

当时我的模板库已经积累了 87 个精细调校过的 prompt，覆盖了绝大多数法律场景。平均每个 prompt 经过了至少 5 轮人工测试和迭代。效果不能说不好——比裸模型好太多了。

但那个“8 次合格，2 次跑偏”的问题，在我的所有优化尝试下，纹丝不动。

不是没有尝试。我试过在 prompt 里加更多的约束条件——结果模型反而更容易在某个约束上“遗忘”。我试过用更复杂的 few-shot 示例——结果模型在某些 case 上过拟合了示例的风格，丢失了灵活性。我试过用不同的角色设定——从“资深律师”到“法学院教授”到“法官”——结果不同的角色在同样的法律问题上有不同的偏差方向，但没有一个角色能消除偏差。

到某个时刻，我必须承认一件事：**如果你在一个不可靠的基础上叠加优化，你得到的不是一个更可靠的系统——你得到的是一个更不可靠的系统加上一套更复杂的优化。** 基础不可靠，上层建筑再精致也无济于事。

那个时刻之后，我们的开发重心从 prompt 层全面转到了架构层。后面的故事——门控链、Creator-Critic 分离、Python 裁决器、多 Agent 辩论——都是这个转向的产物。

而那些 87 个 prompt 模板呢？大部分还在用。但它们的角色变了——它们不再是“质量保障机制”，只是“输出风格和结构的引导”。真正决定系统可靠性的，不是它们。

### 一个判断

如果你正在使用或评估法律 AI 产品，这条规律值得记住：

**prompt 的质量决定了 AI 的上限——它能做多好。但架构的质量决定了 AI 的下限——它最差能做到多差。** 在法律领域，下限比上限重要得多。因为一次跌出下限的事故——一次编造的法条引用、一个遗漏的关键风险——可能比十次“做得漂亮”都更致命。

所以评估一个法律 AI 产品时，不要问“你们用的什么 prompt”。问这三个问题：

1. **法条和案例引用是来自模型记忆还是外部检索？** 如果是前者，不管 prompt 多好，迟早会编造。
2. **谁来验证输出的正确性？** 如果是模型自审，不管你告诉它多少次“请仔细检查”，它发现不了自己的盲区。
3. **同一个问题问两次，输出一样吗？** 如果不一样——你要知道每次输出都是独立的，你无法依赖它。

这三个问题的答案，不在 prompt 里。在架构里。
