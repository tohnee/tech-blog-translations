2026 年 9 月 20 日，veRL 发布 v0.9.1。

这次更新中，有一条很容易被忽略的 Breaking Change：

**原来的 Fully Async Policy Trainer 和 One-Step-Off-Policy 实验模块，正式被新的 V1 Trainer 取代，进入弃用阶段。**

这件事情非常有意思。

因为就在一年多以前，异步强化学习还是 veRL 最重要的新功能之一。

2025 年 7 月，v0.5 第一次将 One-Step-Off-Policy 作为实验性训练方案引入。

2025 年 11 月，v0.6.1 又正式提供 Fully Async Policy Trainer 的实验实现。

但到 2026 年 8 月的 v0.9，研究者开始将同步训练、同机异步训练和分离式异步训练统一到新的 Trainer 架构中。

一个曾经被作为重要创新引入的实验性系统，最终被更一般的基础设施所取代。

而这已经不是 veRL 第一次推翻自己的设计。

2024 年底，veRL 还主要是一套面向 PPO/RLHF 的分布式训练框架。

2025 年，它开始支持 GRPO、DAPO，以及越来越大的 MoE 模型。

同年夏天，AgentLoop 的出现让它能够训练具有多轮工具调用能力的 Agent。

但很快，原有的 SPMD Rollout 又难以适应 Agentic RL 的异步交互。

于是，v0.6 开始向 Rollout Server 迁移。

v0.7 进一步删除了旧的 SPMD Rollout。

然而，此时早期的 FSDPWorker、MegatronWorker 与 ShardingManager 又开始显得过于复杂。

于是，v0.6 提出的 Model Engine 逐步取代旧 Worker 抽象，直到 v0.8 开始正式弃用遗留实现。

与此同时，On-Policy Distillation 开始进入主框架。

一种原本主要优化环境奖励的训练系统，开始同时承担多教师知识迁移、Token-Level KL、异步策略更新与复杂模型权重同步。

从 2024 年 12 月的 v0.1，到 2026 年 9 月的 v0.9.1，veRL 的版本演进几乎可以被看成一部缩小版的大模型强化学习基础设施发展史。

每个阶段，都有一个鲜明的矛盾。

最初的问题是：

怎样灵活地组织 PPO 中的多个分布式模型？

后来变成：

怎样高效训练不需要 Critic 的 GRPO？

再后来是：

怎样训练拥有工具调用、长程交互和不同环境执行时间的 Agent？

最后，问题进一步变成：

**怎样让持续生成的轨迹、不断更新的模型、多种训练算法和数百张 GPU，在同一套基础设施中协同工作？**

而 veRL 的每一次重要版本更新，几乎都在回答当时最突出的一项矛盾。

### 第一部分：2024 年，v0.1 为什么首先解决的是分布式 RLHF 的编程模型？

### 一、HybridFlow 的起点：为什么 PPO 不应该和分布式训练代码绑死？

2024 年，字节跳动 Seed 团队公开 HybridFlow。

后来，这项研究被 EuroSys 2025 接收。

HybridFlow 的开源实现就是 veRL。

最初，这套系统需要解决一个已经困扰 RLHF 研究者很久的问题。

一次 PPO 训练涉及多个模型和多个计算阶段。

例如：

```text
Actor Rollout
      ↓
Reward Model
      ↓
Reference Log Probability
      ↓
Critic Value
      ↓
Advantage
      ↓
Actor / Critic Update
```

这张数据流图本身并不复杂。

但在大语言模型时代，每一个模型都可能拥有几十亿甚至上百亿参数。

Actor 可能使用 FSDP。

Critic 可能使用另外一组 GPU。

生成阶段则使用 vLLM。

这些不同计算之间，既有数据依赖，也有复杂的分布式通信。

研究者如果想修改 PPO 算法，难道还必须同时理解每一张 GPU 如何切分参数、如何执行 Collective Communication？

HybridFlow 认为不应该这样。

它提出 Hybrid Controller Programming Model。

将高层算法控制与底层分布式计算分开。

例如：

```python
rollouts = actor_rollout_wg.generate_sequences(batch)

rewards = reward_fn(rollouts)

advantages = compute_advantage(
    rollouts,
    rewards,
)

actor_rollout_wg.update_actor(
    rollouts,
    advantages,
)
```

这是一段抽象化的示意调用，而不是某一版本的完整可运行训练代码。

它表达的是：

高层 Trainer 只描述应该执行什么计算，以及计算之间的先后关系。

至于 Actor 如何在多张 GPU 上计算，由底层 Worker Group 负责。

### 二、2024 年 12 月 11 日：veRL v0.1 正式发布

2024 年 12 月，veRL v0.1 作为 Python Package 正式发布。

这个版本最重要的意义，不是支持了多少种 RL 算法。

而是建立了后续框架长期使用的基本抽象。

`RayPPOTrainer` 负责高层训练循环。

`RayWorkerGroup` 负责管理分布式 Worker。

`ResourcePoolManager` 负责组织 GPU 资源。

`DataProto` 负责在计算阶段之间传递 Tensor 与非 Tensor 数据。

而 FSDP、Megatron 和 vLLM 等系统，负责实际模型计算。

这里已经出现了 veRL 未来几乎所有架构争论的核心。

**高层算法与底层 Model Engine 应该怎样解耦？**

2024 年的回答是：

通过 Single Controller、Worker Group 和分布式 Dispatch 机制，将复杂计算包装成可调用的方法。

这让 PPO 不必直接操作每个 GPU Rank。

它也使得未来加入新的 RL 算法时，研究者可以尽量复用已有的分布式 Worker。

但当时的设计仍然明显围绕传统 RLHF 工作负载展开。

例如：

一个 Prompt。

一个完整 Response。

Reward。

Advantage。

Policy Update。

这种结构对于 PPO 很自然。

但 2025 年，DeepSeek-R1 与 GRPO 的兴起，很快改变了训练数据流。

### 第二部分：2025 年 2 月，v0.2 为什么迅速转向 GRPO 与高效推理？

### 三、GRPO 为什么成为 veRL 的第一次重要算法扩展？

2025 年 2 月 15 日，veRL 发布 v0.2。

这次更新将：

GRPO。

ReMax。

REINFORCE++。

以及 PRIME 中使用的奖励验证与 Sandbox 机制，纳入框架。

这里最重要的不是算法数量增加。

而是大模型强化学习正在改变自己的主要工作负载。

传统 PPO 通常需要 Critic。

但 GRPO 通过同一个 Prompt 的多条采样轨迹构造组相对 Advantage，可以不再训练独立的 Value Model。

例如：

```text
Prompt A
   ├── Rollout 1 → Reward 0
   ├── Rollout 2 → Reward 1
   ├── Rollout 3 → Reward 0
   └── Rollout 4 → Reward 1
```

随后使用组内奖励构造 Advantage。

这在系统层面带来两个变化。

第一，可以不再训练一个大型 Critic。

第二，同一个 Prompt 往往需要生成多条 Rollout。

于是，Rollout 的吞吐量开始直接影响整个训练系统。

如果模型每次更新需要生成大量回答，训练 GPU 再快也没有用。

因为大部分时间可能都在等待数据生成。

这就解释了 v0.2 为什么不仅增加 GRPO，还同时大规模优化 Rollout 和训练 Batch。

### 四、为什么 v0.2 开始认真处理 Padding 与动态 Batch？

假设两个训练样本长度分别是：

100 Token。

1000 Token。

如果直接 Padding 到相同长度，短样本就可能携带大量无效 Padding Token。

如果一个 Batch 包含大量不同长度的回答，Padding 浪费就会更加严重。

veRL v0.2 因此开始强调：

Remove Padding。

Dynamic Batch Size。

Ulysses Sequence Parallelism。

其中，一个重要的配置是：

```yaml
actor_rollout_ref:
  model:
    use_remove_padding: true
```

另一个方向，是不再简单用固定的样本数量决定每张 GPU 的工作负载，而是按照 Token 数量组织 Micro-Batch。

例如：

```yaml
actor_rollout_ref:
  actor:
    ppo_max_token_len_per_gpu: 8192
```

这类机制在后来长上下文、多模态和 Agentic RL 训练中变得越来越重要。

因为 Agent 的轨迹长度可能相差几十倍。

按照样本数量平均分配任务，并不意味着按照实际计算量平均分配。

v0.2 同时开始集成 vLLM v0.7 及其 CUDA Graph 优化。

发布说明中报告，在特定 Qwen2 PPO 配置下，相比旧版本 vLLM，Rollout 时间可以降低约 25%，启用 CUDA Graph 后可以降低约 45%。

这次更新揭示了一项重要变化：

**veRL 不再只是追求 Trainer 的高效执行，而开始将 Rollout 吞吐量视为强化学习系统的核心性能指标。**

不过，当时 veRL 的主场仍然是文本推理任务。

下一版本开始，研究者又将目光投向更加复杂的模型和硬件。

### 第三部分：2025 年 3 月，v0.3 为什么开始同时拥抱 SGLang、Megatron 与多模态？

### 五、v0.3 为什么引入第二个重要推理引擎？

2025 年 3 月 30 日，veRL 发布 v0.3.0.post0。

这次更新最重要的系统变化之一，是：

**SGLang Rollout 作为 Preview 功能进入 veRL。**

在此之前，vLLM 已经是 veRL 的重要推理后端。

但不同推理引擎在调度、内存管理和模型支持上具有不同特点。

如果强化学习框架深度依赖某一种推理引擎，就可能受到其性能和功能边界限制。

于是，veRL 开始将 Rollout 后端进一步模块化。

用户可以在配置中选择：

```yaml
actor_rollout_ref:
  rollout:
    name: sglang
```

这个看似简单的选项，背后是复杂的系统适配。

因为训练中的 Actor 权重，必须能够转换成推理引擎使用的参数布局。

模型还需要从训练环境切换到推理环境。

并在更新之后同步最新权重。

对于 FSDP、Megatron 与不同推理引擎，这些过程都可能不同。

所以，加入新的 Rollout Engine，并不像普通 Python 程序更换一个 API Client 那么简单。

### 六、v0.3 为什么还需要升级 Megatron？

同一时期，大模型开始广泛使用更复杂的分布式并行策略。

veRL v0.3 升级了 Megatron 后端，开始提供更完善的 Qwen、GRPO 和 Checkpoint 支持。

它也加入了 AMD ROCm 支持，并继续优化 Ulysses Sequence Parallelism。

此外，v0.3 开始提供初步的 Vision-Language RL 功能。

例如：

Qwen2.5-VL GRPO。

这带来了另一个问题。

训练样本不再只是 Token ID。

它还可能包含图像与对应的多模态信息。

数据传递、Batch 组织和模型 Forward，都必须适应不同模态。

在算法方面，v0.3 还加入了 PRIME、RLOO、FIRE Sampling 等能力。

不过，从架构史角度看，v0.3 最重要的意义是：

**veRL 开始从某几种 RLHF 配方的执行器，发展成能够组合多种训练后端、推理后端和模型架构的平台。**

但这只是开始。

接下来的 v0.4，需要面对一个更大的挑战。

几千亿参数的 MoE。

### 第四部分：2025 年 6 月，v0.4 为什么同时迎来大型 MoE 与工具调用？

### 七、DeepSeek-V3 的 671B 参数，为什么迫使 veRL 扩展并行策略？

2025 年 6 月 9 日，veRL 发布 v0.4。

这次发布说明的标题非常直接：

*Large MoEs, Tool Calling, and Low Resource Friendly.*

三个方向并列在一起。

但其中的第一项，代表着规模上的一次巨大变化。

veRL 开始正式预览对：

DeepSeek-V3 671B。

Qwen3-235B。

Mixtral。

Moonlight。

等大型 MoE 模型的强化学习支持。

MoE 不只是普通 Dense Model 的参数数量变多。

它包含大量专家网络。

每个 Token 可能根据 Router 选择不同专家。

因此，分布式训练系统还需要考虑：

Expert Parallelism。

Context Parallelism。

专家之间的通信。

以及大型分布式 Checkpoint。

例如，普通 Tensor Parallel 主要切分模型计算。

但在 MoE 中，专家可能被分配到不同 GPU。

Token 必须根据路由结果发送到对应专家。

于是，一次前向传播可能包含复杂的 All-to-All 通信。

对于强化学习来说，这些问题更加困难。

因为 Actor 不仅需要训练，还需要反复将参数送入 Rollout Engine。

而且，MoE Router 在训练和推理中的行为必须足够一致。

veRL v0.4 开始通过 Megatron 后端处理这些问题。

这让框架第一次拥有了面向数千亿参数 MoE 的正式技术路线。

### 八、为什么 v0.4 已经开始支持工具调用，而不是等到 v0.5？

这是阅读 veRL 历史时很容易写错的一点。

很多介绍会把 Agentic RL 的出现直接归到 v0.5。

但 v0.4 已经通过 SGLang 提供了：

Sample-Level Tool Calling。

Multi-Turn RL。

以及 Search-R1 的训练 Recipe。

它还引入了 Sandbox Fusion。

也就是说，到 2025 年 6 月，veRL 已经开始让模型在 Rollout 期间与外部工具交互。

例如：

```text
Prompt
   ↓
LLM
   ↓
Search Tool
   ↓
Observation
   ↓
LLM
   ↓
Answer
```

然而，这时多轮交互仍然较强地依赖特定的调度实现。

虽然能运行，但如何让任意 Agent Harness 自然地接入 Rollout，仍然不是一个十分通用的问题。

这就是 v0.5 将要解决的矛盾。

### 九、为什么 v0.4 又强调低资源训练？

同一个 v0.4 还推出了几项面向低资源场景的重要能力。

LoRA RL。

Fused Cross Entropy Kernel。

FSDP2。

Activation Offloading。

发布说明指出，在其特定配置下，可以使用单节点 8 张 A100 GPU 对 70B 以上模型进行 LoRA RL 训练。

这反映了 veRL 在扩展过程中面临的两种不同需求。

一部分研究者需要在数百张 GPU 上训练大型 MoE。

另一部分研究者只有几张 GPU，希望进行可复现的 RL 实验。

因此，veRL 不能只向最大规模训练发展。

它还需要降低算法研究的进入门槛。

这一时期，DAPO、Dr.GRPO、Dual-Clip PPO 等算法和 Recipe 也进入框架。

v0.4 于是同时推动了三件事：

更大的模型。

更复杂的环境。

更低的实验成本。

但这些方向最终会共同增加框架复杂度。

### 十、v0.4.1 为什么开始对齐 OpenAI Tool Calling 与 MCP？

2025 年 6 月 27 日，v0.4.1 发布。

这次更新虽然是 Patch Release，但其中有一项非常值得写进技术思想史。

它开始提供：

OpenAI Function Calling Schema。

SGLang MCP Client。

以及更加完善的多轮工具交互支持。

为什么要这样做？

因为 Tool Calling 如果只在某个特定 Search-R1 Demo 中有效，就很难复用到其他环境。

真实 Agent Harness 可能使用不同工具。

例如搜索。

代码执行。

浏览器。

外部 MCP Server。

如果框架需要为每种工具手写解析和执行逻辑，Agentic RL 的扩展成本就会很高。

因此，veRL 开始尝试让工具调用更接近已有的标准化接口。

值得注意的是，MCP 不是模型原生 Tool Call Token 格式。

它主要负责 Agent 与外部工具服务之间的通信。

而 OpenAI Tool Calling Schema 则用于表达函数名、参数和调用结果。

这些不同接口开始一起进入 veRL，意味着 Agentic RL 正在从固定工具任务，走向更加开放的工具生态。

v0.4.1 还修复了 PPO Value Loss 系数的问题，改进 KL 数值稳定性，并优化 MoE Checkpoint 与 SGLang 显存使用。

这说明随着功能数量增加，系统正确性也开始成为越来越重要的维护成本。

而一个月后，veRL 决定重新抽象整个多轮执行流程。

### 第五部分：2025 年 7 月，v0.5 为什么是 Agentic RL 的真正转折？

### 十一、AgentLoop：为什么不能继续把 Tool Calling 写死在 Rollout Engine 中？

2025 年 7 月 23 日，veRL 发布 v0.5。

这次更新最重要的功能是：

**AgentLoop Abstraction。**

它的目的不是第一次让 veRL 调用工具。

v0.4 已经能够做到。

v0.5 真正解决的是：

怎样让研究者编写自己的多轮 Agent 交互逻辑，而不需要重新实现整套分布式 Rollout？

例如，一个 Coding Agent 的轨迹可能是：

```text
LLM → Bash → LLM → Bash → LLM → Final
```

一个 Deep Research Agent 可能是：

```text
LLM → Search → Read Page → Search → LLM
```

一个浏览器 Agent 可能是：

```text
LLM → Click → Screenshot → LLM → Type → ...
```

这些任务都具有多轮交互。

但它们的环境状态、工具类型和停止条件完全不同。

如果将交互逻辑写死在 Rollout Engine 内部，框架就会越来越复杂。

于是，v0.5 将多轮交互抽象成独立的 AgentLoop。

例如：

```python
class CustomAgentLoop(AgentLoopBase):

    async def run(self, sampling_params, **kwargs):
        ...
```

AgentLoop 负责定义：

什么时候调用模型。

什么时候调用工具。

如何处理 Observation。

什么时候结束轨迹。

而底层推理服务器负责高效生成 Token。

这让 Agentic RL 的扩展方式发生了变化。

**研究者不需要先理解 veRL 内部全部分布式 Worker 实现，就能够定义一个新的 Agent 环境交互流程。**

### 十二、为什么 v0.5 必须采用异步 Rollout？

假设有三个 Coding Agent 正在运行。

Agent A 执行 `ls` ，1 秒完成。

Agent B 执行 `grep` ，2 秒完成。

Agent C 执行 `pytest` ，需要 3 分钟。

如果所有 Rollout 都必须按照固定 Batch 同步推进，那么前两个 Agent 就可能被第三个 Agent 阻塞。

但在 Server-Based Rollout 中，每个 AgentLoop 可以独立等待自己的工具。

模型推理请求则由 vLLM 或 SGLang Server 动态调度。

因此：

A 完成工具执行后，立即继续生成。

B 完成后，也可以继续生成。

C 仍然等待自己的测试进程。

这让推理服务器能够持续处理已经准备好的请求。

v0.5 开始正式将这种 Server-Based Asynchronous Rollout 用于 Agentic RL。

同时还提供 LangGraph Agent 等示例。

这是一项非常重要的抽象变化。

**Rollout 不再只是一次 `generate()` ，而开始是一段独立运行的 Agent Session。**

### 十三、为什么 v0.5 又引入 One-Step-Off-Policy？

在这次发布中，veRL 还引入了 One-Step-Off-Policy 异步训练原型。

这是一个与 AgentLoop 不同、却会在未来逐渐融合的方向。

传统同步 RL 训练往往按照：

```text
Rollout with π₀
       ↓
Update → π₁
       ↓
Rollout with π₁
       ↓
Update → π₂
```

组织数据。

但这种方式意味着，训练和 Rollout 之间存在等待。

如果训练 GPU 正在更新模型，Rollout GPU 可能没有足够工作。

如果 Rollout 很慢，训练 GPU 又可能等待新数据。

于是，研究者尝试让训练与采样运行在不同资源池。

例如：

```text
Rollout GPU: π₀ 生成轨迹
Training GPU: 使用旧轨迹更新到 π₁

Rollout GPU: 继续生成
Training GPU: 继续更新
```

这会提高硬件利用率。

但也意味着：

Rollout 数据可能由比当前 Actor 更旧的模型生成。

v0.5 的实验性 One-Step-Off-Policy Recipe，将策略版本延迟限制在一步左右。

发布说明报告，在小规模实验中，这种分离式异步训练比同步 On-Policy 基线提高约 20%—40% 吞吐量。

但这不是免费的加速。

因为当用于训练的轨迹来自旧策略时，数据分布与当前策略之间就出现了差异。

这也是后来 veRL 必须引入更复杂的 Off-Policy Correction、Staleness Control 和 Replay Buffer 管理的原因。

另外，v0.5 还针对 GRPO 做了一项重要的负载均衡改动。

此前可以先将 Prompt 分配给 Rollout Worker，再在 Worker 内重复采样。

而 v0.5 改为先在 Driver 端重复样本，再分发到不同 Worker。

这样，同一个 Prompt 的多个 Rollout 就有机会分散到不同 Worker，减少部分计算负载不均衡。

**v0.5 已经清楚地展示：当 RL 训练开始依赖大量独立生成的轨迹，系统优化的重点就会从训练 Batch 扩展到整个轨迹生产过程。**

---

### 第六部分：2025 年 10 月，v0.6 为什么决定重新建设 Model Engine？

### 十四、当 FSDP、Megatron、VeOmni 不断增加，旧 Worker 抽象为什么不够了？

2025 年 10 月 16 日，veRL v0.6 正式发布。

它的标题非常明确：

*Model Engine, Rollout Server, Composability.*

其中，Model Engine 是这次更新的核心。

为什么需要一个新的 Model Engine？

在早期 veRL 中，FSDPWorker 和 MegatronWorker 分别包含大量特定于训练后端的逻辑。

例如：

初始化模型。

构造优化器。

执行 Forward。

执行 Backward。

更新参数。

处理权重和 Checkpoint。

但随着后端数量不断增加，很多功能开始重复。

例如，不管底层使用 FSDP 还是 Megatron，高层算法都需要：

计算 Log Probability。

训练 Actor。

训练 Critic。

保存和恢复状态。

如果每增加一种后端，都需要写一套新的大规模 Worker 实现，就会很难扩展。

于是，v0.6 提出统一的 Model Engine API。

让训练逻辑面对一个更加稳定的接口。

而具体后端负责执行实际分布式计算。

重要的是，v0.6 的 Model Engine 当时仍然是 Prototype。

官方明确说明：

这一版本首先使用新 Model Engine 实现 SFT Trainer。

未来才逐步迁移 RL Trainer。

也就是说，v0.6 并没有一夜之间完成整个训练系统的重构。

它只是开始为下一代架构建立新的基础。

### 十五、v0.6 为什么还要重新设计分布式 Dispatch？

早期 veRL 的 Dispatch 机制存在一些明确的规则类型。

例如：

`ONE_TO_ALL`

`DP_COMPUTE_DATA_PROTO`

`MEGATRON_COMPUTE_DATA_PROTO`

这些规则直接对应某类分布式计算策略。

但问题也很明显。

当训练后端不断增加，未来可能同时出现：

Data Parallel。

Tensor Parallel。

Pipeline Parallel。

Expert Parallel。

Context Parallel。

以及各种混合策略。

如果每一种分布式组合都需要专门编写 Dispatch 规则，抽象就难以扩展。

因此，v0.6 开始引入基于 Device Mesh 的 nD Dispatch。

例如：

```python
@register(
    dispatch_mode=make_nd_compute_dataproto_dispatch_fn(
        mesh_name="..."
    )
)
```

核心思想，是将数据如何分发和收集，与底层分布式 Mesh 绑定，而不是为每一种后端手写单独的 Dispatch Mode。

这又是一种抽象的重新划分。

**研究者不再希望每增加一种模型并行方式，就重写一套 Worker Group 通信规则。**

### 十六、为什么 v0.6 的 Rollout Server 也要重构？

v0.5 已经引入 Server-Based AgentLoop。

但底层 vLLM 和 SGLang 的执行方式仍然存在历史包袱。

v0.6 因此进一步调整两大推理后端。

SGLang 的推理进程与 Trainer 进程分离，通过 Server Adapter 同步权重，并逐步迁移到 SGLang Native Server Mode。

vLLM 也开始向 Native Server Mode 迁移，不过当时部分 Model Runner 仍保留在训练进程中。

这种重构的意义，在于尽可能利用推理系统已经具备的在线服务能力。

例如：

Dynamic Batching。

并发请求调度。

长程多轮对话。

KV Cache 管理。

以及更灵活的请求进入和退出。

到这里，veRL 已经在两条线上同时重建自己。

训练侧：

新的 Model Engine。

推理侧：

新的 Rollout Server。

而高层 AgentLoop 负责连接环境交互。

但是，异步训练仍然缺少一套稳定的统一实现。

---

### 第七部分：2025 年 11 月，v0.6.1 为什么开始正面研究 Fully Async？

### 十七、One-Step-Off-Policy 为什么还不够？

2025 年 11 月 14 日，veRL v0.6.1 发布。

这次版本在算法和实验系统中提出了两项重要能力。

Fully Async Policy Trainer。

TransferQueue Data System。

为什么需要 Fully Async？

v0.5 的 One-Step-Off-Policy 已经允许训练与采样部分重叠。

但如果希望最大限度提高 GPU 利用率，就可能需要让两条流水线更加独立。

例如：

Rollout 资源池持续生成轨迹。

训练资源池持续从缓冲区取数据更新模型。

二者不必每一步都严格同步。

这样做有明显的吞吐量优势。

但风险也更大。

假设当前 Actor 已经更新到：

$$
 \pi_5 
$$

而缓冲区里仍然存在：

$$
 \pi_2 
$$

生成的轨迹。

那么训练使用的数据就可能具有明显的策略陈旧性。

这时，系统需要决定：

是否丢弃旧轨迹？

是否使用重要性采样修正？

允许最多落后几个版本？

如果缓冲区没有足够数据，是否暂停训练？

如果 Rollout 长时间无法完成，如何处理？

这些问题已经明显超出了普通 PPO Trainer 的职责。

于是，Fully Async 开始成为一个需要独立研究的执行系统。

### 十八、TransferQueue 为什么出现？

在传统同步训练中，Trainer 可以一次性收到一个完整 Batch。

但在异步环境中，样本可能陆续到达。

不同样本来自不同时间。

可能具有不同策略版本。

甚至拥有不同模态和不同环境来源。

因此，简单的 Python List 或固定 Batch Pipeline 已经难以满足要求。

TransferQueue 尝试提供一种异步流式数据管理机制。

它负责在不同计算阶段之间传输和组织数据。

这里的思想非常重要。

**当 Rollout 与 Trainer 不再严格同步，训练数据就需要一个独立于算法控制流的生命周期。**

这将成为 v0.8 和 v0.9 Trainer 重构的重要基础。

v0.6.1 还重新整理了 Rollout Correction 系统。

这个名字也值得理解。

因为 Rollout 可能由不同的推理后端生成。

训练引擎计算的 Log Probability，可能与推理引擎采样时使用的分布存在数值或实现差异。

此外，异步训练又会引入策略版本差异。

因此，框架需要明确区分：

推理—训练数值不一致。

以及策略更新造成的 Off-Policy 数据差异。

它们都可能需要修正，但并不是同一个问题。

到 2025 年底，veRL 已经逐渐从传统 RLHF Trainer，转向同时包含推理服务、异步数据队列和分布式训练引擎的复杂系统。

而下一次更新，将开始删除那些不再适应这种结构的旧实现。

---

### 第八部分：2026 年 1 月，v0.7 为什么开始正式告别旧架构？

### 十九、v0.7 为什么彻底移除 SPMD Rollout？

2026 年 1 月 5 日，veRL 发布 v0.7。

在官方 Release Notes 中，有一条非常重要的变化：

**Remove SPMD Rollout Mode。**

这里不能误解为：

veRL 不再使用 SPMD 进行分布式训练。

被移除的是旧式 Rollout 执行模式。

底层训练仍然可以使用复杂的分布式并行。

真正改变的是模型生成的组织方式。

在早期框架中，Rollout 常常与训练 Worker 紧密结合。

而在 Agentic RL 中，模型生成需要响应大量动态请求。

不同轨迹具有不同长度。

工具调用会造成不规则等待。

如果继续依靠旧式 SPMD Rollout，就很难充分发挥推理服务器的动态调度优势。

因此，v0.7 正式选择了 Server Mode。

这是 veRL 历史上第一次相当明确地删除整个旧执行方向。

它不只是增加新的推理功能。

而是承认：

**曾经适合传统 RLHF 的 Rollout 执行模型，已经不再是未来 Agentic RL 最合适的默认架构。**

### 二十、v0.7 为什么宣告 Model Engine 逐渐进入生产可用阶段？

与 v0.6 的 Prototype 不同，v0.7 已经开始提供较成熟的 FSDP 和 Megatron Model Engine 实现。

其中包括：

TrainingWorker。

Model Engine 形式的 Critic。

统一的 ActorRolloutRefWorker。

更丰富的 TensorDict 支持。

以及不同后端在同一个 Worker 中组合的能力。

这里尤其值得注意的是 `TrainingWorker` 。

它开始提供类似 Tinker 风格的训练 API。

例如，外部系统可以通过相对统一的接口调用训练能力，而不必直接依赖每一种具体后端的 Worker 实现。

这意味着 veRL 正在改变自己的定位。

它不只是提供一个预先写好的 PPO 训练循环。

还希望成为一个能够被其他系统调用的分布式模型训练服务。

同时，v0.7 还加入了更加灵活的 Reward Manager。

支持：

Rule-Based Reward。

Discriminative Reward Model。

Generative Reward Model。

以及这些奖励方式的组合。

这对于复杂 Agentic RL 很重要。

因为真实环境的 Reward 不一定都是一个简单的二元测试结果。

它可能来自：

外部 API。

代码测试。

模型评分。

多个 Verifier。

或者复杂的任务分级。

### 二十一、为什么 v0.7 已经开始出现 OPD？

在 v0.7 的贡献记录中，已经可以看到 One-Step-Off-Policy 与 Fully Async 场景下的 On-Policy Distillation Recipe。

这很重要。

因为 OPD 并不是 v0.8 或 v0.9 才突然出现的想法。

它首先以更实验性的方式进入 veRL。

但当时还没有形成后续 v0.8 那种跨 FSDP、Megatron 和 VeOmni 的完整 OPD 支持体系。

因此，如果按技术史追溯，应该区分：

v0.7 附近的实验性 OPD Recipe。

和 v0.8 正式扩展的统一 OPD 能力。

这种区分，恰好展示了 veRL 很多功能的典型发展方式。

**先在 Recipe 中证明能运行，再逐步抽象成可复用的主框架能力。**

### 二十二、2026 年 3 月：v0.7.1 又为什么引入更多 Engine？

2026 年 3 月 16 日，v0.7.1 发布。

这次版本进一步扩展模型执行后端。

包括：

VeOmni。

TorchTitan。

TensorRT-LLM Rollout。

以及新的 Checkpoint Engine 管理机制。

同时支持更复杂的 Router Replay、MTP 训练与 Qwen3.5 模型。

这里的变化很值得注意。

当模型架构越来越多样化，一个框架已经很难依赖单一的训练引擎。

Dense Transformer。

MoE。

带有特殊路由机制的模型。

多模态模型。

不同硬件架构。

它们对执行后端的需求都不一样。

但高层 RL 算法并不应该因此被重写。

于是，v0.7.1 开始进一步落实 Model Engine 抽象的价值。

此外，它还统一了部分异步训练中的 Checkpoint Engine，并增加 Partial Rollout 的自动恢复支持。

这表明：

异步训练已经不再只是一个“训练与生成并行”的吞吐量问题。

它还需要处理执行中的任务状态和恢复机制。

例如，一条 Agent 轨迹可能生成到一半。

模型权重更新了。

推理服务器暂停进行权重同步。

恢复后，原来的 Agent 应该怎样继续？

这种问题会在 v0.9 变得更加突出。

### 第九部分：2026 年 6 月，v0.8 为什么又是一场架构重构？

### 二十三、v0.8 为什么开始弃用旧 FSDPWorker 和 MegatronWorker？

2026 年 6 月 1 日，veRL 发布 v0.8。

这次版本有三项特别值得关注的变化。

第一：

**正式弃用 Legacy FSDP 和 Megatron Workers，推动统一 Model Engine。**

第二：

引入新的 Sync Trainer，并使用 TransferQueue 解耦数据流和控制流。

第三：

将 OPD 扩展成跨多种后端的完整能力。

这三项变化实际上存在共同的技术动机。

随着算法和模型种类增加，框架已经不能继续依赖大量专门定制的 Worker 类与 Trainer。

如果每引入一个模型后端，就重新实现一套训练方法。

每引入一个新 RL 算法，就重新组织一次数据流。

veRL 将很难长期维护。

因此，v0.8 开始真正将之前几版开发的抽象整合起来。

### 二十四、TransferQueue 为什么开始进入新的 Sync Trainer？

v0.8 引入：

`main_ppo_sync.py`

新的 Sync Trainer 通过 TransferQueue 组织数据流。

其核心目标，是将：

Trainer 的控制逻辑。

与训练数据的传输、分发和收集。

进一步解耦。

在传统同步训练中，可以简单把一个 Batch 从 Controller 传给 Worker。

但当模型拥有不同长度的轨迹、多模态输入和多种并行方式时，数据传输本身会变得复杂。

于是，TransferQueue 将数据生命周期变成一个相对独立的基础设施问题。

发布说明还报告，在特定 128 GPU 多模态训练配置中，这种改造带来了最高约 2 倍的性能提升。

不过，v0.8 的新 Trainer 当时还没有成为默认训练入口。

旧的：

`main_ppo.py`

进入弃用阶段。

而新的：

`main_ppo_sync.py`

开始承担未来统一 Trainer 的基础。

到了 v0.9，这项工作会继续推进。

### 二十五、v0.8 为什么正式将 On-Policy Distillation 纳入主架构？

v0.8 的另一项重大变化，是完整的 OPD 支持。

此前，veRL 的主要任务仍然是利用 Reward 优化 Policy。

例如：

GRPO。

PPO。

DAPO。

这些算法可以根据环境奖励，鼓励模型生成更高成功率的轨迹。

但当模型遇到复杂任务时，环境奖励通常较稀疏。

例如一个 Coding Agent 执行了 100 个步骤。

最终没有修好 Bug。

Reward 可能只有 0。

这很难告诉模型：

究竟哪一个 Token 或哪一个局部决策最值得改变？

OPD 提供了另一种训练信号。

学生模型在自己的状态分布上采样。

教师模型则在这些状态上提供更细粒度的概率信息。

因此，教师可以为学生在 Token Level 提供监督。

v0.8 将 OPD 扩展到：

FSDP。

Megatron。

VeOmni。

同时支持：

单教师。

多教师。

文本和多模态。

同步和 Fully Async Trainer。

以及不同类型的 KL Loss。

例如，它支持两类具有不同训练机制的 OPD。

**PG-OPD。**

一种典型配置是：

```yaml
distillation:
  distillation_loss:
    loss_mode: k1
    use_policy_gradient: true
```

它将教师与学生在采样 Token 上的 Log Probability 差异，构造成 Policy Gradient 使用的蒸馏信号。

**Direct Distillation。**

例如：

```yaml
distillation:
  distillation_loss:
    loss_mode: k3
    use_policy_gradient: false
```

它直接对逐 Token 的蒸馏 Loss 反向传播。

如果使用 Teacher Top-k 分布，也可以采用：

`forward_kl_topk`

这样的分布匹配形式。

这些方法之间的区别，并不只是换一个 KL 估计器。

还涉及：

使用 Policy Gradient 还是直接反向传播。

是否使用 PPO-style Clipping。

是否利用 Full-Vocabulary 或 Top-k 信息。

以及如何与 Task Reward Loss 结合。

veRL 的实现还允许：

$$
 L = L_{\mathrm{task}} + \lambda L_{\mathrm{distill}} 
$$

其中，蒸馏项自身仍然可以采用 PG 形式。

所以，“外层 Loss 相加”和“蒸馏项内部使用 Policy Gradient”并不是互斥关系。

这项设计让 veRL 不再只是一套 Outcome Reward Optimization Framework。

它开始支持通过教师知识，为学生的 On-Policy 轨迹提供额外训练信号。

### 二十六、为什么 v0.8 又将 Uni-Agent 放进生态？

v0.8 的官方 Release Notes 还介绍了：

`verl-project/uni-agent`

这个项目旨在让 veRL 更容易接入通用 Agent Harness。

例如 Coding Agent。

Search Agent。

GUI Agent。

这是 v0.5 AgentLoop 的自然延伸。

v0.5 允许研究者自行编写 AgentLoop。

但真实世界里已经有很多成熟的 Agent Harness。

例如 mini-swe-agent。

Claude Code。

以及各种使用 OpenAI-Compatible API 的 Agent。

如果为了训练这些 Agent，必须把原有 Harness 重写成 veRL 的内部 AgentLoop，工程成本就很高。

因此，Uni-Agent 试图建立一个更通用的接口层。

让外部 Agent Harness 可以继续按照自己的工作方式运行，而 veRL 负责模型生成和训练。

这意味着 veRL 的角色正在发生变化。

**它不再要求所有 Agent 都围绕 veRL 设计，而是开始尝试让现有 Agent 系统接入 veRL 的强化学习基础设施。**

但这种外部 Harness 接入，会进一步放大异步运行、权重同步和会话管理问题。

于是，v0.9 必须重新组织整个 Trainer。

---

### 第十部分：2026 年 8 月，v0.9 为什么要统一同步与异步 RL？

### 二十七、为什么此前的多个 Trainer 已经开始难以维护？

2026 年 8 月 14 日，veRL 发布 v0.9。

这是一个非常重要的版本。

它正式将：

**Unified V1 Trainer**

设为默认实现。

新的 Trainer 统一支持三种主要模式。

`sync`

`colocate_async`

`separate_async`

它们之间的区别，主要在于 Rollout 与 Trainer 怎样分配资源、是否重叠执行，以及如何管理样本到达和参数更新。

`sync` 更接近传统同步训练。

`colocate_async` 允许在共享或协同资源条件下重叠调度。

`separate_async` 则让 Rollout 和 Training 运行在更加独立的资源池上。

在此之前，veRL 已经分别维护：

同步 PPO。

One-Step-Off-Policy。

Fully Async Policy。

以及其他特殊 Recipe。

但随着这些训练模式逐渐成熟，它们开始包含大量相同的逻辑。

例如：

Replay Buffer。

Reward。

Advantage。

Policy Update。

Checkpoint。

Validation。

Metrics。

如果继续维护多个独立 Trainer，每修复一个 Bug，就可能需要修改多个实现。

因此，v0.9 将这些模式统一到：

`verl/trainer/ppo/v1`

中。

这次更新与 2024 年最初的 HybridFlow 有着很强的思想联系。

HybridFlow 希望把高层算法与底层分布式模型计算解耦。

而 v0.9 则进一步尝试：

**把不同训练时序下共享的数据生命周期与算法逻辑重新统一。**

### 二十八、异步训练最大的困难，为什么不是并发，而是 Staleness？

假设当前 Actor 已经更新到：

$$
 \pi_8 
$$

但 Rollout Server 上仍然存在由：

$$
 \pi_5 
$$

生成的部分轨迹。

这条轨迹还能不能用于训练？

如果可以，应该怎样计算 Importance Sampling Ratio？

如果不可以，是直接丢弃，还是等待更多数据？

这已经是一个需要训练系统明确管理的问题。

v0.9 为此提供了 Staleness Control。

例如：

`max_off_policy_threshold`

以及：

`drop`

`wait`

等策略。

这里的 Staleness 指的是采样策略版本与当前训练策略版本的差距，不是工具调用次数，也不是 Agent 已经运行了多少分钟。

因此，在异步 Agentic RL 中，系统可能需要管理：

轨迹开始时使用的 Policy 版本。

轨迹继续生成时使用的 Policy 版本。

训练更新时的 Current Policy。

以及 Replay Buffer 中每条样本的版本信息。

如果一条长程 Agent 轨迹运行了很久，期间模型更新了多次，那么这些问题就尤其复杂。

**异步训练真正困难的地方，是数据不再天然来自同一个版本的 Policy。**

### 二十九、v0.9 为什么引入 Continuous Token？

v0.9 还有一项很有意思的设计：

**Continuous Token。**

它最初默认关闭。

为什么需要这种机制？

因为一次 Agent Rollout 可能包含多轮：

Assistant。

Tool。

Assistant。

Tool。

如果每一轮都独立通过 Chat Template 重新构造 Prompt，就可能出现 Token 序列边界不连续的问题。

例如：

模型已经生成了一段 Assistant 输出。

Runtime 将工具结果加入历史。

随后重新通过 Chat Template 渲染整个上下文。

但新的 Token 序列，未必与上一轮生成时使用的前缀在所有边界细节上完全一致。

对普通用户而言，可能只是多了一个换行或少了一个分隔符。

但对于强化学习训练而言，问题更加严重。

因为训练需要知道：

模型实际生成了哪些 Token。

对应的 Log Probability 是什么。

哪些 Token 属于环境 Observation。

哪些 Token 应该被 Policy Loss 更新。

如果生成时和训练时的 Token 序列不一致，就可能影响 Log Probability 和 Importance Sampling 的正确性。

因此，Continuous Token 希望使多轮 Agent 交互中的 Token 序列更加连续和可追踪。

它也开始专门处理 Qwen、GLM、MiniMax 等模型的不同消息边界。

这又与大模型工具调用格式的技术史产生联系。

不同模型拥有不同的 Chat Template、Tool Call Token 和消息结束标记。

这些差异不仅影响推理解析器。

也会影响强化学习如何准确重建原始生成序列。

### 三十、v0.9 为什么需要新的 Checkpoint Engine？

异步 RL 还有一项非常昂贵的操作。

**权重同步。**

假设训练 Actor 拥有几百亿参数。

训练进程刚刚完成一次更新。

现在需要将新权重同步给 Rollout Server。

如果每次都传输完整模型，就可能消耗大量网络带宽。

更麻烦的是，训练进程可能使用：

FSDP。

Megatron。

Expert Parallelism。

而推理服务器又使用另一套参数布局。

因此，权重同步涉及的不只是复制 Tensor。

还需要：

分片转换。

参数映射。

MoE Expert Placement。

以及通信调度。

v0.9 开始提供更加完善的 Checkpoint Engine，并引入：

`delta_sharded`

这种面向分片参数差分传输的方案。

其核心思想是：

不要求每次都发送完整权重。

而是根据已保存的分片快照，计算需要传输的变化部分。

发送后，再在 Rollout 侧应用更新。

官方 Release Notes 在特定 H100、GSM8K GRPO、SGLang 的分离式异步训练设置下，报告了相对完整 NCCL Broadcast 的加速。

例如：

Qwen2.5-7B：2.4 倍。

Qwen2.5-32B：1.9 倍。

Qwen2.5-72B：3.1 倍。

这些并不是对所有模型都成立的固定加速比例。

但它们揭示了一项重要变化。

**在现代异步 RL 中，模型权重从训练引擎流向推理引擎，已经成为一条需要单独优化的数据通道。**

这条通道的重要性，正在接近 Rollout 数据本身。

### 三十一、为什么 v0.9 还要支持最新的大型 MoE？

v0.9 的发布说明还包括：

DeepSeek-V4 GRPO。

Megatron-Bridge。

Megatron Lite。

FP8 / MXFP4 Weight Transfer。

动态 Context Parallel Scheduling。

Muon Optimizer。

以及针对 GLM、Kimi 等模型的训练支持。

其中一些示例已经扩展到 256 GPU。

这说明 2026 年的 veRL 已经不仅要适配几十亿参数的 Dense Model。

还需要管理大型 MoE、长上下文、不同参数量化格式和复杂的训练—推理权重转换。

在这类模型中，训练和 Rollout 的一致性更加困难。

例如，MoE Router 可能影响哪些 Expert 被激活。

量化后的推理权重可能与训练权重存在数值差异。

Context Parallel 布局也可能改变实际计算组织。

因此，v0.9 的大规模模型支持，与前面提到的 Rollout Correction、Checkpoint Engine 和 Continuous Token 并不是彼此独立的功能堆叠。

它们都在解决同一类问题：

**怎样让模型生成、训练和同步所使用的不同执行系统，尽可能准确地表示同一个正在学习的 Policy？**

---

### 第十一部分：2026 年 9 月，v0.9.1 为什么开始优化异步系统的细节？

### 三十二、v0.9.1 为什么允许训练 GPU 暂时参与 Rollout？

2026 年 9 月 20 日，veRL 发布 v0.9.1。

这次更新不再主要依靠增加新的 RL 算法来展示进步。

很多功能集中在已经存在的异步训练系统上。

其中一个非常有意思的设计是：

`separate_async.enable_switch`

这是一个默认关闭、需要显式启用的功能。

它允许 Trainer 在某些阶段，将空闲 GPU 资源暂时用于 Rollout。

为什么需要这样做？

因为即使采用 Separate Async Training，也不意味着两种资源始终满负荷运行。

例如：

Rollout Server 正在等待某些 Agent 工具调用。

Trainer 则暂时没有足够可采样的数据。

或者某次训练阶段结束后，Trainer 需要等待 Replay Buffer 积累下一批样本。

如果这些 GPU 只能固定承担一个角色，就可能出现空闲。

于是，v0.9.1 开始尝试更加动态的资源调度。

当某些 Trainer GPU 暂时没有训练任务时，可以让它们参与生成。

在缓冲区积累足够样本之后，再切回训练。

这实际上重新触及了最初 HybridFlow 的核心问题：

**训练和推理到底应该完全共用 GPU，还是使用独立资源池？**

veRL 最初的 3D-HybridEngine 强调同机资源复用。

后来，异步 RL 开始强调资源分离。

现在，v0.9.1 又尝试在分离式架构中动态借用空闲资源。

因此，这不是简单地从 Colocate 走向 Disaggregate。

而是在两者之间不断寻找更合适的资源调度策略。

### 三十三、v0.9.1 为什么进一步扩展 Delta Weight Sync？

v0.9 的 `delta_sharded` 最初在相关路径中主要面向 SGLang。

而 v0.9.1 进一步增加了 vLLM Consumer。

并扩展 TorchTitan 等后端的差分权重同步。

在一个特定的 A800、GSM8K GRPO、Qwen3-8B、32 GPU 的实验配置下，官方报告：

从完整同步的约 34.26 秒，降低到差分同步的约 3.34 秒。

约 10.3 倍加速。

这再次说明，随着异步 RL 的规模增长，权重同步已经不再是一个可以忽略的实现细节。

如果 Actor 每次更新都需要暂停 Rollout 数十秒，那么即使推理本身很快，整个训练系统仍然可能受到同步瓶颈限制。

### 三十四、为什么 v0.9.1 还要继续修复 Continuous Token 和多模态问题？

v0.9.1 将 Continuous Token 进一步扩展到多模态。

它新增了类似：

`VLContinuousTokenBuilder`

的机制。

用于处理多轮 Agent 交互中的图像与文本内容。

例如：

模型读取一张图像。

调用工具。

工具返回新的图像或者文本。

模型继续生成。

这里不仅要保证文本 Token 的连续性。

还需要正确恢复：

图像占位符。

Pixel Values。

Image Grid 信息。

以及模型自身的多模态 Chat Template 规则。

因此，v0.9.1 不只是提高推理速度。

它还继续修复多轮 Agent 生成与训练之间的数据一致性。

这类问题在普通数学 RL 中并不突出。

但当 Rollout 开始包含多模态环境和复杂工具交互时，就可能成为训练正确性的基础。

### 三十五、为什么 v0.9.1 开始弃用此前的 Fully Async 实验系统？

回到本文开头。

v0.9.1 明确将：

`verl/experimental/fully_async_policy`

和：

`verl/experimental/one_step_off_policy`

标记为由 V1 Trainer 取代的旧路径。

它们预计会在后续版本迁移到 Recipe 仓库。

这项改动其实代表着一条从 2025 年开始的长线终于形成阶段性结果。

v0.5：

One-Step-Off-Policy Prototype。

v0.6.1：

Fully Async Policy Trainer Prototype。

v0.7：

部分权重同步与异步训练机制继续成熟。

v0.7.1：

更统一的 Checkpoint Engine 和 Partial Rollout 恢复。

v0.8：

TransferQueue 与新的 Sync Trainer。

v0.9：

Unified V1 Trainer。

v0.9.1：

旧实验性异步 Trainer 进入弃用阶段。

这条历史说明，真正成功的框架扩展并不是不断增加新的 Trainer。

而是让已经经过实验验证的能力，逐渐进入一套更通用的执行架构。

**功能先作为实验出现，后来被抽象、融合，最终旧实现被删除。**

这才是 veRL 版本更新中非常值得写出的工程思想。

### 第十二部分：从 v0.1 到 v0.9.1，veRL 的技术主线究竟是什么？

### 三十六、第一次重构：从固定 PPO 到算法可组合

v0.1 建立 HybridFlow 的基本框架。

v0.2 加入 GRPO、ReMax 和 REINFORCE++。

v0.3 支持更多算法、模型和推理后端。

v0.4 进一步容纳大型 MoE、DAPO 和多轮工具调用。

这条路线解决的是：

**如何让新的 RL 算法不必重新实现整套分布式训练系统。**

它强调高层 Controller 与底层 Worker Group 的解耦。

### 三十七、第二次重构：从 Batch Generation 到独立 Agent Session

v0.4 开始支持多轮工具调用。

v0.5 引入 AgentLoop。

v0.6 迁移到更成熟的 Rollout Server。

v0.7 删除旧式 SPMD Rollout。

这条路线解决的是：

**当模型生成不再是一次完整 Response，而是包含工具等待、环境反馈和多轮推理的 Agent Session 时，应该怎样组织 Rollout？**

答案逐渐从固定 Batch，转向动态请求和异步调度。

### 三十八、第三次重构：从多个后端专用 Worker 到统一 Model Engine

v0.6 提出新的 Model Engine。

v0.7 将 FSDP 和 Megatron Engine 推向生产可用阶段。

v0.7.1 继续扩展 VeOmni、TorchTitan 与 Checkpoint Engine。

v0.8 开始正式弃用 Legacy Worker。

这条路线解决的是：

**当 Dense、MoE、VLM、不同硬件与不同分布式并行策略不断增加时，怎样避免每种模型架构都需要一套专门的 RL Trainer？**

答案是进一步统一 Model Engine API，并将执行后端的复杂性封装在内部。

### 三十九、第四次重构：从同步更新到统一异步数据流

v0.5 引入 One-Step-Off-Policy。

v0.6.1 引入 Fully Async 与 TransferQueue 原型。

v0.8 推出新的 Sync Trainer。

v0.9 将同步和多种异步训练统一到 V1 Trainer。

v0.9.1 则继续优化资源动态切换，并弃用早期异步实验模块。

这条路线解决的是：

**当 Rollout 和 Training 不再严格同步，怎样管理数据缓冲、策略版本、权重更新与资源利用？**

这是 veRL 近年来最重要的系统演进之一。

### 四十、第五次扩展：从单一 Task Reward RL 到教师、环境和多 Agent 协同训练

随着 v0.8 的 OPD 和 Uni-Agent，veRL 开始拥有更开放的外部训练信号和 Agent Harness 接入方式。

v0.9、v0.9.1 又继续处理 Continuous Token、复杂会话、权重同步和多模态轨迹。

这条路线的关键问题是：

**如果模型既可以从环境 Reward 学习，也可以在自己访问到的状态上从教师模型学习，同时还要与长期运行的外部 Agent Harness 交互，训练系统究竟应该如何组织？**

这时，veRL 已经很难再被简单描述成一个 PPO 实现。

它逐渐成为一个可以执行复杂 LLM 后训练数据流的基础设施。

---

### 最后：为什么 veRL 的历史，实际上是一场不断重新划分系统边界的过程？

如果只看 2024 年的 HybridFlow，很容易认为：

veRL 最重要的贡献，是设计了一套高效的 Hybrid Controller，使 PPO 更容易在大模型上扩展。

但之后的版本发展证明，这只是整个故事的起点。

v0.2 发现，强化学习的主要数据流已经开始从传统 PPO 转向 GRPO。

于是，Critic 不再是所有算法的必需组件，大量 Group Rollout 的吞吐量开始成为核心问题。

v0.3 和 v0.4 发现，基础模型架构正在快速变化。

于是，SGLang、Megatron、MoE、FSDP2 和多模态支持开始进入主框架。

v0.5 发现，Agentic RL 不能只通过一次模型 Generate 表达。

于是，AgentLoop 成为独立抽象。

v0.6 和 v0.7 发现，旧式 SPMD Rollout 已经不适合大量异步工具交互。

于是，Rollout Server 开始取代旧执行模式。

同一时期，模型后端不断增加，又迫使 veRL 重新设计 Model Engine。

v0.8 发现，训练算法已经不只需要稀疏环境 Reward。

于是，OPD 和多教师监督开始进入主框架。

但这些新能力又增加了 Trainer、Model Engine 与 Rollout 之间的数据依赖复杂度。

最终，v0.9 重新统一同步和异步 Trainer。

v0.9.1 则进一步优化权重同步、GPU 动态调度和多模态 Agent Session 的正确性。

从这个角度看，veRL 的版本史中最重要的事情，不是它支持的算法越来越多。

而是它反复发现：

**过去某项设计中被认为理所当然的系统边界，已经无法适应新的模型和任务。**

最初，研究者认为 Rollout 可以作为 PPO Trainer 的一个计算阶段。

后来，Rollout 变成独立的推理服务器。

再后来，它变成能够运行大量 Agent Session 的执行系统。

最初，训练 Worker 与 FSDP、Megatron 的具体实现紧密关联。

后来，Model Engine 开始将它们统一起来。

最初，训练按照完整 Batch 同步更新。

后来，Rollout 和 Training 分离成独立的数据流水线。

最终，Trainer 又必须重新组织这些异步数据的生命周期。

这是一条不断增加抽象、又不断删除旧抽象的历史。

而不是简单的功能累积。

如果说 2024 年 HybridFlow 试图回答的是：

**怎样高效执行一个大语言模型 PPO 训练循环？**

那么到 2026 年的 veRL v0.9.1，问题已经变成：

**怎样让数百张 GPU 持续运行大量不同长度的 Agent 轨迹，让模型不断从环境和教师获得训练信号，并在策略持续变化的同时高效、正确地完成参数更新？**

这两个问题仍然属于强化学习。

但它们需要的基础设施，已经不再处于同一个复杂度层次。

也正因如此，veRL 的技术史最值得关注的不是某一个最终版本。

而是它为什么一次次重构自己。

**当模型能力、任务形态和训练算法持续变化时，强化学习系统不能假设自己的计算图永远不变。**

从 HybridFlow 到 AgentLoop。

从 SPMD Rollout 到 Server Mode。

从专用 Worker 到 Model Engine。

从同步 PPO 到 Unified Async Trainer。

从稀疏 Task Reward 到多教师 OPD。

veRL 的发展，实际上记录了大模型强化学习的核心工程问题如何不断变化。

而到 2026 年，它甚至还没有进入 1.0 时代。
