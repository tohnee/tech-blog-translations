### 一、DeepSeek v4.1 RL 训练踩坑日记：主机内存才是最大瓶颈

> sallon88 ｜ 赞同 442 ｜ [https://zhuanlan.zhihu.com/p/2093494438676927321](https://zhuanlan.zhihu.com/p/2093494438676927321) ｜ 全文来源：知乎搜索摘要

训练 DeepSeek v4.1 这一级别的大模型做 RL，显存之外更要盯**主机内存**。作者沉淀出三个只在多机 RL 场景才会踩到的坑：

### 1. Engram 的主机内存布局：单机 shared，跨机必须 private

Engram（记忆模块）通常放在主机内存里，它的 host 内存布局默认是 **shared**——即本机一块全局共享内存、多卡共用。**单机这没问题，但跨机时这套就不成立了**，必须显式将 Engram 布局设置成 private（sharded 模式），让每个 rank 各自 load 自己负责的那一部分。

### 2. R3 专家回放的主机内存是 KV cache 的 8 倍

SGLang 启用专家回放（R3）时，需要提前为每个 token 预留内存存放 routed experts。在 dsv4.1 场景下**每个 token 需要 960B（40×6×4）**，而 dsv4.1 对 KV cache 的显存占用做了极致优化，每个 token 的 kv cache 占用差不多也是这个量级。换句话说：

> 你如果每张卡预留 20G 显存放 kv cache，就得同时预留 20×8=**160G 主机内存**存放 routed expert。

共置部署（colocate）时如果不小心把 kv cache 池开得很大，开启 R3 后主机内存占用会跟着水涨船高（8 倍），最后**不是显存 OOM，而是主机 OOM**。作者团队的做法是在配置中显式指定 `max_total_tokens`，把 kv cache 池的大小明确下来。

### 3. CPU 优化器：6 机 H20 跑 dsv4 可以、跑 dsv4.1 必挂

训练 dsv4.1 级别的模型基本都会开启 CPU optimizer，把优化器状态放到主机内存以节省显存。但 Engram（SGLang 一份、Megatron 也得有一份）加上 R3 的叠加影响，更容易踩到主机内存 OOM。实测：**原本可以正常跑 dsv4 的 6 机 H20（单机 2T 内存），无法正常跑 dsv4.1**，每次都会挂在 CPU optimizer 的更新权重环节。

最终用 Megatron 最新的 **chunked_optimizer_state_offload** 机制才能跑起来（当前仅存在于 Megatron 的 dev 分支）：同样把优化器状态放主机内存，但峰值占用可以从 18N 降到 12N（N 为参数量：主权重 4N + 主梯度 4N + 动量相关 8N + bf16 权重的 pin memory 2N → 12N）。

另外建议在 `PYTORCH_ALLOC_CONF` 中配上 `pinned_max_cached_size:32`。

### 三、【infra 复盘】0：slime 为什么这样设计

> 打怪升级灯芯草 ｜ 赞同 210 ｜ [https://zhuanlan.zhihu.com/p/2078219523187011887](https://zhuanlan.zhihu.com/p/2078219523187011887) ｜ 全文来源：知乎搜索摘要

slime 的三个核心设计决策，各自对应多机 RL 的一类痛点：

1. **Rollout 服务化（SGLang as a service）** → 解决「agentic rollout 难写」：生成变成普通 HTTP 调用，用户爱怎么编排怎么编排；
2. **训练端坚持 Megatron** → 解决「MoE 大规模并行」：TP/PP/EP/CP 全套保留；
3. **Buffer 做中间人** → 解决「长尾 + 时序耦合」：生成和训练节奏解耦，还能顺带做样本过滤、partial rollout 缓存。

### 三模块架构与一次 RL 迭代的数据流

系统拆成三个角色，用 Ray 编排（Ray 负责跨节点的进程调度、资源分配与 actor 间通信）：

1. Data Buffer 从数据集取出 prompt，交给用户自定义的 rollout 函数；
2. rollout 函数通过 Router 向 SGLang Server 发起生成请求（可能多轮、带工具调用），拿到回答 + token 级 logprob；
3. reward/verifier 打分后，样本写回 Data Buffer；
4. Buffer 攒够一个训练 batch（过滤、打包、padding、loss mask），交给 Megatron；
5. Megatron 完成一次梯度更新后，把新权重同步回所有 SGLang Server，进入下一轮。

### 为什么训练端必须 Megatron

- Megatron 承担 Actor 更新 + Reference 模型 log-prob 计算（GRPO 里用于 KL 正则）；
- 保留完整并行能力：TP / PP / EP / CP / VPP；
- 这是 slime 相对很多 FSDP-only 框架的硬优势：**FSDP 以数据并行为主，对 MoE 的专家并行（EP）支持很弱，而 EP 恰恰是 MoE 模型训练的刚需**——每个专家只放在部分卡上，All-to-All 通信调度由 Megatron 成熟实现；
- 后续也加入了 FSDP 后端作为轻量选项，方便中小模型快速上手；
- slime 的设计理念是「参数直通」：Megatron 的参数直接透传，SGLang 的参数以 `--sglang-` 前缀暴露，上游引擎的新优化可以直接用，框架本身不做一层「最大公约数」式的封装。

### 四、Agentic RL 训练系统基础设施调研：训推不一致的量化证据

> 薛磊 ｜ 赞同 109 ｜ [https://zhuanlan.zhihu.com/p/2031679243713819973](https://zhuanlan.zhihu.com/p/2031679243713819973) ｜ 全文来源：知乎搜索摘要

调研报告中最有价值的两条：

### SGLang 与 Megatron MoE 路由不一致的实证

> 约 **10% 的 Router 在两个引擎间选择不同专家，94% 的 Token 至少在一层选择了不同专家**。

这就是训推一致性（train-inference mismatch）问题的量化规模——不是精度噪声，是系统性偏差。

### R3（Rollout Routing Replay）解法

1. Rollout 阶段（SGLang）：记录每层每 Token 的 Top-K 专家索引；
2. Training 阶段（Megatron）：回放这些路由决策，在 softmax 门控中强制激活相同专家；
3. Router 权重仍然可训练——只是强制选择与 Rollout 一致的专家；
4. 结果：高差异 Token 数量级降低，KL 散度大幅下降。

### 关键工程数据

- 权重同步：BF16 约 48 秒，FP8 约 100 秒（FP8 传输量小但当前实现开销大）；
- 最大验证规模：GLM-4.5-355B-A32B（64×H100）、DeepSeek-R1（128×H100）；
- APRIL 端到端加速：40% 吞吐提升，Rollout 加速 49.5%；
- FP8+DeepEP 推理 6-7x（GLM4.5-355B）；
- MILES 端到端 FP8 洞见：**仅 Rollout FP8（Training 保持 BF16）比端到端 FP8 不一致性更差**；FP16 的 10-bit 尾数比 BF16 的 7-bit 更鲁棒；INT4 QAT（W4A16）下 1TB 模型可在单机 H200 上推理，2x Rollout 效率。

### 五、R3 落地：居然有这么多坑

> 房佳月圆 ｜ 赞同 108 ｜ [https://zhuanlan.zhihu.com/p/2061482430742239187](https://zhuanlan.zhihu.com/p/2061482430742239187) ｜ 全文来源：知乎搜索摘要

R3（Rollout Router Replay）在真实多机环境中落地时的三个隐蔽 bug，每一个都具备”单机看不出、不 crash、只表现为训练异常”的特征：

### 5.1 Bug：Draft head 路由 allreduce 污染（投机解码叠加）

- **触发条件苛刻**：只在 RS（replay scheduler）+ 投机解码 + CUDA Graph 三者同时启用时出现；
- **Rank 0 恰好正确**（offset=0 的 buffer 数据就是全局前 N 个 token），单卡调试看不出；
- 错误的 routing ID 仍在合法范围内，不会 crash；
- 表现为”不稳定的 log_prob diff”，易被误认为数值精度问题。
- **修复**：Draft head 的 LogitsProcessor 设置 `skip_routing_allreduce=True`。

### 5.2 Bug：RoPE type 映射错误（mbridge）

- **发现过程**：log_prob diff 在长序列尾部显著增大；
- **根因**：HuggingFace config 中 `rope_scaling.rope_type = "deepseek_yarn"`，mbridge 直接透传给 Megatron，但 Megatron 只认 `"yarn"`，导致 Megatron 训练侧的 YaRN position encoding 解析异常，长序列位置的 attention pattern 完全错误；
- **影响**：RoPE 错误影响所有 layer 的表征，是 R3 能正确工作的前提条件——即使 routing 完全一致，如果 hidden state 本身就因 RoPE 错误而不同，Megatron 的 router scores 也会偏离 SGLang。

### 5.3 Bug：Denominator Collapse（renormalize 不一致）

- **发现过程**：`[DenomCollapse]` 诊断报告大量 token 的 sigmoid score sum < 0.05，放大倍数超过 100x；
- **根因**：SGLang 使用 `probs = sigmoid_scores * scaling_factor`（不做归一化），Megatron 默认 `probs = scores / (scores.sum() + 1e-20) * scaling_factor`。强制 replay 时，SGLang 选中的 expert 在 Megatron sigmoid 视角下可能 score 很低（选择标准不同），归一化后分母趋于 0，权重爆炸；
- **修复**：新增 `moe_router_renormalize` 配置项对齐两侧行为。

### 5.4 辅助工具

`dump_single_sequence_r3`：dump 单条序列在训推两侧的完整路由决策，用于逐层对比定位。

### 六、FSDP2 后端：data packing 与严格训推一致

> Chayenne Zhao ｜ 赞同 159 ｜ [https://zhuanlan.zhihu.com/p/1979141713449742500](https://zhuanlan.zhihu.com/p/1979141713449742500) ｜ 全文来源：知乎搜索摘要

### Data Packing 消除 padding 浪费

FSDP actor 每轮从 rollout 侧拿到 balanced rollout sequence 后按 DP rank 拆分，然后在 `slime/backends/fsdp_utils/data_packing.py` 中做 pack_sequences：根据每条序列的长度和 `max_tokens_per_gpu` 估算需要多少个 pack（即 micro-batch 数量），把长短不一的 sequence 分到不同 pack 中，使每个 pack 内 token 总数尽量接近；pack 内将多条序列摊平成一条长 tokens 向量，并构建 `cu_seqlens` 记录各条序列的起止位置。这样每个 pack 的 token 总量高度一致，消除了传统 padding 的算力浪费。

### True On Policy：训推 log_prob 绝对一致

针对 training-inference mismatch 问题，在 FSDP 上实现同一个 policy model 在训练/推理两个 backend 的 log_prob 绝对一致：

- Training 和 Inference 都使用 **FlashAttn3** 作为 backend，实现 bitwise equal；
- 使用 **DeepGEMM** 做矩阵乘法，Batch-invariant Kernels 保证批次不变性。

即从系统层面把 training-infer KL 压到 0，而不是靠 KL 正则兜底。

### 七、slime + Qwen3.5 多模态采坑记系列（colocate → 异步训练）

> 李先生 ｜ 赞同 70 / 28 / 7 / 19 ｜ 系列 4 篇 ｜ [https://zhuanlan.zhihu.com/p/2035676751683122438](https://zhuanlan.zhihu.com/p/2035676751683122438) 、 [https://zhuanlan.zhihu.com/p/2037859838840067278](https://zhuanlan.zhihu.com/p/2037859838840067278) 、 [https://zhuanlan.zhihu.com/p/2043718678114472259](https://zhuanlan.zhihu.com/p/2043718678114472259) 、 [https://zhuanlan.zhihu.com/p/2071329262267797890](https://zhuanlan.zhihu.com/p/2071329262267797890) ｜ 全文来源：知乎搜索摘要

### 7.1 同步训练阶段的基础坑（第 1 篇）

1. **保存模型时 invalid_argument**：异步保存优化器状态时发生，怀疑显存或内存不够，解决方法是不保存优化器状态（`--no-save-optim`）；
2. **`The actor is temporarily unavailable: RpcError: RPC error: Socket closed`**：可能在每步训练中出现。解决方法是加 `--no-offload-train`（推理过程不把训练参数放到 CPU）。原因可能是特定情况下触发 actor 将权重 offload 之后没有成功加载，导致 actor 训练中断、程序终止；
3. **too many open files**：句柄数限制（摘要到此截断，后续问题未获取）。

背景：作者先用 swift 框架，MoE 模型强化时 vllm infer 采样会随机 hang（多个版本均出现），因此迁移到 slime。

### 7.2 colocate → 异步训练（第 2 篇）

colocate 模式下训练阶段存在较严重的等待问题，**整体等待时长占比一度超过 60%**；且受显存限制，计算 logits 的 chunk size 只能设得很小。异步训练模式（训练与推理各占独立 GPU，解耦运行）遇到的新坑：

- **update weight 时权重 shape 不一致**：`update_weight_from_distributed.py` 路径下 `buffer_size` 计算环节报错（训练侧 Megatron 分片形状与推理侧 SGLang 期望形状不匹配，摘要到此截断）。

### 7.3 升级 Megatron 后的 gated_delta_net 断言（第 3 篇）

升级 Megatron 后报错：

```text
AssertionError: Experimental attention variant is not supported with
get_gpt_decoder_layer_specs, but got config.experimental_attention_variant='gated_delta_net'
```

旧版 Megatron + slime 没有此问题，升级后触发。需要对 `slime/utils/megatron_bridge_utils.py` 等 bridge 文件做兼容 patch（unwrap_model 导入兜底、gpt_decoder_block_spec patch、automapping compat 注册），作者用 vibe coding 方式完成修复。

### 7.4 最隐蔽的性能 bug：通信探针拖慢一切（第 4 篇）

- **现象**：权重同步时长每步暴涨（143→363→966→1596s），每个 micro-batch 训练 ~14s，单步 ~57min；
- **根因**：`slime/utils/reloadable_process_group.py` 的 `_wrap_low_level_call` 里调用 `available_memory()` 做显存探针，挂在每一次集合通信调用上。TP 的 `_allgather_base` 和梯度 allreduce 全部被拖慢；
- **修复后**：权重同步平稳 ~7–20s，每 micro-batch ~1.5s，每步 ~9min。py-spy 复采：探针从热路径消失，采样落在真实计算（custom_backward / MoE grouped_gemm / TE forward）；
- **自查方法**：看 `_wrap_low_level_call` 是否还在调 `available_memory()`；若已换成 `torch.cuda.mem_get_info()`、且 `_COMM_MEMORY_CHECK_SKIP_OPS` 里含 broadcast/_allgather_base 之类，说明已修；
- **适用范围易误读**：训练变慢是普适的（任何权重同步方式都会中招）；权重同步变慢是分布式 nccl transport 特有的——`update_weight_from_distributed` 是逐参数 `dist.broadcast(param, async_op=True)`，逐次触发探针；colocate 路径（`update_weight_from_tensor`）走 CUDA IPC，不触发这半症状。

环境：8×B300 单机，slime main@681b3ad / v0.3.1 + Megatron-LM + SGLang，Qwen3.5-35B-A3B（MoE + gated-delta-net）异步 GRPO，`--update-weight-transport nccl`。

### 八、grounding 能力从 89% 跌到 43.6%：一次 RL 能力退化的完整排查链

> 李先生 ｜ 赞同 12 ｜ [https://zhuanlan.zhihu.com/p/2076401110785471102](https://zhuanlan.zhihu.com/p/2076401110785471102) ｜ 全文来源：知乎搜索摘要

一次多模态 RL 训练中，模型的视觉定位（grounding）能力从 89% 跌到 43.6%，继续训继续掉。输出不是乱码、格式完全正常，就是”框画错了地方”。先后怀疑过数据、奖励函数、权重转换、图像预处理、版本回归……连续证伪十多个假设，最终根因钉在 SGLang 一个很少有人看的角落：**注意力层里新引入的融合 RoPE 内核，对 Qwen3.5 的 partial + interleaved M-RoPE 处理错误**。一个补丁，grounding 命中率从 26% 修回 81.7%。

### 第一层解释（后来被证明只是下游症状）：奖励代理 + 巨框策略

1. 训练日志显示 grounding 样本的训练奖励没有崩、反而略涨，但评测真实能力在跌——”奖励涨、能力跌”的 gap 指向奖励代理与真实能力不对齐；
2. 奖励是稠密 IoU、无命中门槛：框和真值沾一点边就有分；
3. 关键数据：同样的探针，历史 rollout 命中率 75.8%，这次只有 15.8%——命中率太低时，稠密 IoU 下唯一够得着的正信号就是”沾边”；
4. GRPO 组内标准化会抹掉幅度（IoU 0.001 和 1.0 的优势相同）→ 模型学会”画巨框保证沾边”，实测预测框面积比从 4.5x 一路膨胀到 88x；
5. 加上 `kl_coef=0`（无参考模型锚），策略自由漂移，SFT 学到的 grounding 被磨掉。

这套解释完全自洽，但修掉 SGLang 的 RoPE 内核 bug 后命中率立刻回升——说明”巨框策略”很大程度是在**推理引擎 rollout 本身就把坐标算错**的前提下被迫学出来的生存策略。教训：RL 训练中模型”变笨”，先排除 rollout 引擎与训练引擎的数值不一致（RoPE/attention 实现），再谈奖励设计。

环境：Qwen3.5-35B-A3B（MoE + GDN 混合注意力 + 视觉塔），slime（Megatron 训练 + SGLang rollout），SGLang 0.5.15.post1，B300。

### 九、RL修炼第三弹：SWE Agent 从头训到能用的四类坑

> 大海无量 ｜ 赞同 3 ｜ [https://zhuanlan.zhihu.com/p/2094117487826810559](https://zhuanlan.zhihu.com/p/2094117487826810559) ｜ 全文来源：知乎搜索摘要

训一个 SWE Agent（给代码仓库 + issue，自己读代码、改文件、跑测试，改对了给奖励）。技术栈 Megatron + SGLang + Ray，跑了快一个月，崩了十几次。坑分四类：基础设施 → 推理引擎 → 训推一致性 → 训练崩溃（NaN）。

### 9.1 基础设施：一大半时间花在”把机器凑齐”

- **计算节点创建超时**：十几台机器起训经常卡在创建节点超时。调大超时能缓解，但真正坑人的是**超时之后的异常捕获逻辑写错，错误被吞掉不往上报**——排查时只看到程序莫名停住，最后才发现是建节点那一步；
- **资源不足连环坑**：节点一直 pending（IP 或配额不够）、调度过于集中（没配反亲和，一堆任务挤同一台机）、打散了又撞上子网 IP 耗尽。本质都是算力和配额没对齐。教训：**训练前就把配额、调度策略（反亲和、最大打散）、各种超时一次性配好**；
- **共享内存不足**：NCCL 通信直接失败，报错信息很有迷惑性（只说通信挂了，不说根因）。最后发现是容器的 `/dev/shm` 太小，**从 32G 调到 300G 才稳**。

### 9.2 显存：response 越训越长，然后就爆了

RL 的 OOM 原因和 SFT 不一样。关键认知：**SWE 任务的 response 会越训越长**——模型学会多想几步、多试几次，生成长度水涨船高，显存跟着一路涨：

- 换更大模型后，晚上跑着跑着 OOM，把单卡最大 token 数往下压才稳住；
- 跑到 20 来步 OOM 退出，根因还是 response 长度持续增长；
- 最隐蔽的：就算设了单卡最大 token 数，**分 pipeline、切 micro-batch 的时候，单个 micro-batch 的实际 token 数还可能超过这个上限**，照样爆。

### 十、权重同步的工程账：Miles 的 Shared Bucketed Pipeline 与 P2P RDMA

> 岭南 ｜ 赞同 3 ｜ [https://zhuanlan.zhihu.com/p/2081484430598846106](https://zhuanlan.zhihu.com/p/2081484430598846106) ｜ 全文来源：知乎搜索摘要

Miles（生产级后训练系统，slime 企业级分支的姐妹项目）对”每步都要把训练权重同步给 rollout 引擎”这一 RL 特有环节的优化：

### 10.1 Shared bucketed pipeline

- Megatron 路径先将 tensor-parallel shards 在各 pipeline stage 内 all-gather，转换成 SGLang 需要的 HuggingFace 命名/布局，放入默认 **512 MB buffer**；bucket 满后一次 flush 给 broadcast 或 P2P，**避免数千 tensor 各自调用**通信原语；
- **MoE routed experts 需要第二个 expert pass**：因为 expert parallel rank 持有的是不同 experts，而不是同一个 tensor 的 shards；
- 各 pipeline stage 可独立准备和发送自己的权重，但 broadcast flush 有共享锁，阶段边界还有 trainer-wide barriers，**慢 stage 仍会在这些位置拖住整体**。

### 10.2 P2P RDMA vs Broadcast

P2P 让多个 training source 并行，只把目标 rank 需要的 shard 写入其内存：每个 sender 在 CPU 内存构造一个与目标 SGLang rank 布局一致的 model replica，用 SGLang 自己的 weight loader 做重排（避免复制 sharding 规则）；共享 pinned buffer 反复注册复用，控制 host memory 随 fleet 扩张。

H100 集群、trainer/rollout 两侧节点数相同、1 GB bucket 的实测：

| 模型 | 每侧节点数 | Broadcast | P2P | 变化 |
| --- | --- | --- | --- | --- |
| Qwen3-30B-A3B | 2 | 2.67 s | 2.16 s | -19.1% |
| GLM-5 744B-A40B | 16 | 58.30 s | 8.48 s | -85.5% |
| Kimi K2 1T-A32B | 32 | 53.28 s | 7.23 s | -86.4% |

结论：**收益主要随 fleet width 增长，而不只是随模型大小增长**。单节点没有额外聚合带宽，却仍承担 host reshaping 和 pinned staging，作者测得 P2P 最多比 broadcast 慢约 70%，所以 broadcast 保持默认。另外若 trainer 与 rollout colocate 在同一 GPU，交接是本地操作，不需要网络 transport。

### 十一、RL-Kernel：GRPO 的 logprob 显存爆炸与算子级解法

> Vensen ｜ 赞同 40 / 36 / 14 ｜ [https://zhuanlan.zhihu.com/p/2046532827441898083](https://zhuanlan.zhihu.com/p/2046532827441898083) 、 [https://zhuanlan.zhihu.com/p/2047635945990760318](https://zhuanlan.zhihu.com/p/2047635945990760318) 、 [https://zhuanlan.zhihu.com/p/2045985049229760399](https://zhuanlan.zhihu.com/p/2045985049229760399) ｜ 全文来源：知乎搜索摘要

### 11.1 问题根源：GRPO 的 logprob 中间张量

GRPO 的 logprob 计算会临时分配一个 **[G × SeqLen × Vocab]** 的中间张量。以 Llama-3-8B 为例，Vocab=128,256，G=128 时这一步就要额外占用 **62 GB**，直接把 A100 80GB 打满：

- TRL 在 G=64 就崩了；
- PyTorch native 在 G=256 崩了。

### 11.2 解法

- **预分配 chunking**：把额外显存开销从 O(G·L·V) 降到 O(chunk)，与 G 的大小彻底解耦；
- 集成 FlashInfer fused kernel 把采样延迟压到 sub-2ms；
- 自研 Sampling、Prefix-shared Attention、基于 TMA 的高性能 Kernel，实测部分高频计算节点提速高达 163 倍。

### 11.3 训推一致性的算子层视角

标准 RL pipeline 中 Rollout 跑 vLLM/sglang、Training 跑 Megatron/FSDP，两边底层算子实现、显存布局、浮点舍入差异极易导致 **Log-Prob 漂移和 KL 散度爆炸**。RL-Kernel 的路线是在 Triton/CUDA 层面用 Fused Kernels 强行拉齐数值一致性：Batch-invariant 算子套件保证无论 batch size 和 chunked prefill 如何变化输出严格一致、SM90+ TMA-accelerated Online Softmax Fused LogP、为 GRPO logprob 设计的 Prefix-Shared Fused Attention。

### 十二、Rollout 引擎的三种”死法”：RL 采样侧显存问题定位

> chouheiwa ｜ 赞同 341 ｜ [https://www.zhihu.com/question/1993781500349539243/answer/2030665166598174331](https://www.zhihu.com/question/1993781500349539243/answer/2030665166598174331) ｜ 全文来源：知乎搜索摘要

RL 训练的 rollout 阶段跑在 vLLM/SGLang 上，其显存 OOM 有三种成因、三条完全不同的修复路径。诊断时先看症状落在哪条路径，再下药：

1. **配置性死亡（静态问题）**：vLLM V1 启动时按 `max-model-len × max-num-seqs` 把整个 KV 池子 greedy 预分配，无法动态 reclaim——服务 128K context 用户哪怕只有 1 个，也要压将近 37 GB。修复：`--max-model-len` 降到实际 P99、`--max-num-seqs` 压到实际并发、开 `--kv-cache-dtype fp8_e5m2` 让 KV 体积减半（Red Hat blog 实测 DeepSeek 8×H200 token 容量从 54,560 涨到 512,000）；
2. **时间性死亡（越跑越差）**：PyTorch allocator 碎片化。典型症状 `torch.OutOfMemoryError: Tried to allocate 1.09 GiB ... 6.48 GiB reserved by PyTorch but unallocated`——总显存够但连续段不够（这个坑训练圈已磨合多年，推理圈才刚开始踩）。修复：`export PYTORCH_ALLOC_CONF=expandable_segments:True`，或把 `--block-size` 从 16 增大到 32 降低每 block metadata overhead；
3. **平台性死亡（ROCm only）**：SGLang `--mem-fraction-static` 在 ROCm 上不被遵守——Qwen2.5-7B 在 MI210 上设 0.8，实际占 61.8⁄64 GB（97%+）HIP OOM。根因是 ROCm allocator 加 Triton kernel 的 temp buffer 不算在 static fraction 里。

> 注：RL 场景中 rollout 引擎与训练引擎共置时，第 1 类的”预分配不能回收”会和训练侧显存需求直接冲突——这也是 slime 用 TorchMemorySaver/sleep 机制做 offload 的原因（见第二节问题 1 的 TorchMemorySaver vs expandable_segments 冲突，两者不能同时启用）。

### 十三、算法侧细节：entropy 监控与 PPO 数据流

### 13.1 verl 的 actor entropy 是怎么算的

> tomsheep ｜ 赞同 62 ｜ [https://www.zhihu.com/question/1933940678922072713/answer/1934292063551197389](https://www.zhihu.com/question/1933940678922072713/answer/1934292063551197389) ｜ 全文来源：知乎搜索摘要

- **跟 prompt 有关**：计算熵时通常会把 prompt 部分用掩码盖掉（不必须，也可保留），只对 response 部分的 token 计算熵，但 response 由 prompt 决定——换了任务，熵就换了条曲线；
- **计算链路**：`verl/workers/actor/dp_actor.py` 的 `compute_log_prob` → `entropy_from_logits`（`verl/utils/torch_functional.py`）逐 token 计算熵 → 再按配置的 loss 聚合方式聚合（token level 平均：`H(t) = -Σ p_t,i · log p_t,i`，对 batch 内所有 response 的所有 token 求平均，或 sample level 先平均再平均）。

> 李先生 ｜ 赞同 30 ｜ 同问题另一回答 ｜ [https://www.zhihu.com/question/1933940678922072713/answer/1942210838690767222](https://www.zhihu.com/question/1933940678922072713/answer/1942210838690767222)

熵基于一个 batch 下采样生成的所有 response 计算。模型越自信，会把最大概率赋给某一个 token；越不自信，每个 token 预测概率越相近；熵最大时每个 token 被预测的概率为 1/V。**监控意义**：entropy 持续下降=策略越来越确定；RL 后期 entropy 崩到接近 0 通常意味着策略塌缩（exploitation 极化），是判断该停训的信号之一。

### 13.2 slime 的 PPO 数据流

> Black Ghost ｜ 赞同 2 ｜ [https://zhuanlan.zhihu.com/p/2030422663622022713](https://zhuanlan.zhihu.com/p/2030422663622022713) ｜ 全文来源：知乎搜索摘要

1. 拿到 rollout 生成的数据，做一次”只前向、不更新参数”的 value 预测，放入 `rollout_data["values"]`；
2. critic 预热结束后，进行 actor 和 critic 的数据同步：actor 算出动作概率（`log_probs` / `ref_log_probs`），critic 算出状态价值（`values`）；
3. 计算优势与目标回报，使用 GAE（广义优势估计）；
4. 执行正式的训练与参数更新（critic 侧 `loss_type = "value_loss"`）。

注意 actor/critic 分离时，两侧数据同步走的是与权重同步相同的分布式通道，多机下同样受带宽约束。

### 十五、CUDA Graph 专题：rollout 引擎”录制一次、重放万次”的机制与坑

RL 训练的 rollout 每步要跑成千上万次前向，kernel launch overhead 必须用 CUDA Graph 压掉——但 Graph 也是 B200 实录（第二节）里 capture 失败、replay illegal memory access 两类问题的源头。三篇文章拼出完整图景：

### 15.1 入门与避坑指南：四组坑与实测

> xinxinxinxinxin ｜ 赞同 11 ｜ [https://zhuanlan.zhihu.com/p/2078596776500671325](https://zhuanlan.zhihu.com/p/2078596776500671325) ｜ 全文来源：知乎搜索摘要

性能收益（H100 80GB / CUDA 12.9 实测）：逐 kernel 提交 vs 一次 replay = **42.2 → 1.2 µs/步**，kernel 间隔 1.95 → 0.096 µs。代价是四组坑：

- **A 组（参数与地址固化）**：capture 时把 kernel 参数和输出地址写死进图，改宿主变量无效（旧参数写旧地址，新地址未被触碰）。修复：参数走 device 内存 + pinned 做图的数据入口；或用 `cudaGraphExecKernelNodeSetParams` 每步换参数/输出地址，互不波及；
- **B 组（同步与 CPU 逻辑进图）**：显式同步进图 → capture 作废报错；**CPU 逻辑（loss 检查、早停决策）进图 → 静默失效**，三步停在旧输入。修复：CPU 在图外，pinned 缓冲做图的 I/O 口；
- **B6 撕裂**：pinned 输入缓冲是图的数据入口，但上一次 replay 可能还在读它。修复：两次 replay 之间同步，或双缓冲轮换；
- **B 组（依赖）**：无显式依赖时进图后 race 现形（全量旧值）。修复：显式 event 边串行化；
- **C 组（工程）**：反复录制——capture+instantiate 实测 1.78ms 是一次性开销，图要跨步复用，每步重建比不用图还慢；图太大——把前向+检查+早停整段录进一张图就没有 CPU 决策点了，拆图（前向一张、优化器一张）；忘了喂新数据——**图能跑通不代表算的是新数据，replay 前先刷新静态输入缓冲**。

> stream 是任务队列（CPU 逐个提交），图是录好的整段宏（一次提交）。有 stream 为什么还要图，答案在此。

### 15.2 vLLM v1 的 FULL vs PIECEWISE 与运行时分派

> Allen ｜ 赞同 2 ｜ [https://zhuanlan.zhihu.com/p/2083249513037411659](https://zhuanlan.zhihu.com/p/2083249513037411659) ｜ 全文来源：知乎搜索摘要（源码索引为主）

- 图的键是 `BatchDescriptor`（num_tokens / num_reqs / uniform / LoRA 两字段）；分派器维护”运行时可分派图的唯一事实源”；
- **桶填充**：batch size 向上 pad 到预定义档位，capture 降序进行——**大尺寸先捕，小尺寸复用池段**；
- FULL 与 PIECEWISE 两种模式：FULL 等长批才启用、attention metadata 只在 FULL 下补齐；PIECEWISE 松弛键给分段捕获（FA3 精确键是例外）；
- 捕获期 `gc.freeze`（受 `VLLM_ENABLE_CUDAGRAPH_GC` 控制）防 GC 搬移对象；投机解码开启时 `input_ids clamp min 0` 防查表越界；块表补齐行填 `NULL_BLOCK_ID` 让假请求指向空块；
- ROCm 平台引擎关闭时调 `clear_all_graphs` 提前释放图，避免延迟析构报 HSA fault——跨平台同一套机制，故障形态不同。

### 15.3 投机解码整段捕获：draft→verify→accept 一张图

> 注意力机制不集中 ｜ 赞同 36 ｜ [https://zhuanlan.zhihu.com/p/1964668286156378807](https://zhuanlan.zhihu.com/p/1964668286156378807) ｜ 全文来源：知乎搜索摘要

EAGLE E2E runner 的核心思想：预分配投机流程所有读写显存（input_ids / KV 稀疏索引 / hidden_states / out_cache_loc / draft_tokens / accept_length 等固定 buffer），用固定形状构造一次性 capture 输入，把完整 draft→verify→accept 序列录成一张图；运行时只做一次数据填充（或 triton 一次性写入），然后 `cudagraph.replay()` 直接返回结果。关键手法：**把主机控制流全部转成 GPU 数据流（mask 驱动）**，消灭多次 kernel 启动与 host↔device 同步。这解释了第二节 B200 实录里”EAGLE draft cuda graph replay illegal memory access”为什么难查——buffer 布局、索引表任何一处与 capture 时不一致就会踩非法访问。

### 16.2 适用边界：FlashInfer 不解决什么

> Hardy ｜ 赞同 11 ｜ [https://zhuanlan.zhihu.com/p/2069375949867689231](https://zhuanlan.zhihu.com/p/2069375949867689231) ｜ 全文来源：知乎搜索摘要

它只做推理场景的 attention 与 KV Cache 算子族：不做请求调度/continuous batching（引擎 scheduler）、不管 KV 全局内存池分配（只消费 page table）、采样策略归引擎、**不做跨卡 all-reduce（归引擎并行层 + NCCL/自定义 all-reduce）**、不做训练前反向（无 autograd）、非 attention 算子交给 CUTLASS/Triton。同一个 online softmax，在训练里服务反向传播，在推理里服务 split-K decode；同一个间接寻址，在 FlashInfer 里是 Paged KV Cache 的地基。

### 16.3 Attention 后端选型：同一层换的是哪把刀

> 上古 ｜ 赞同 3 ｜ [https://zhuanlan.zhihu.com/p/2093799185225199652](https://zhuanlan.zhihu.com/p/2093799185225199652) ｜ 全文来源：知乎搜索摘要

- **FlashAttention**：不物化完整注意力矩阵——8K 序列的分数矩阵就是 8K×8K×2B=128MB；tiling 进 SRAM 边算边累加 softmax。同一后端内部 prefill 与 decode 走不同 kernel（`flash_attn_varlen_func` 变长拼接一次算 vs 分页解码按 block table 收集 KV）；
- **FlashInfer**：特性最全（supported_kv_cache_dtypes 更长，多 fp8_e5m2/nvfp4），Blackwell SM100 上 TRTLLM 因果注意力的默认后端；代价是自维护一块 workspace 缓冲，且某些组合下与 prefix caching + batch-invariant 不兼容——**这正是 RL 训推一致性方案（第六节 FSDP2 batch-invariant）要注意的选型约束**；
- **Triton**：可移植性最好，不依赖厂商预编译库；XPU + batch-invariant 模式的强制默认后端。

### 十七、训推一致性的极端方案：纯 CUDA 从零复刻整个 RL 栈

> KJL0508 ｜ 赞同 103 ｜ [https://zhuanlan.zhihu.com/p/2027367874008814836](https://zhuanlan.zhihu.com/p/2027367874008814836) ｜ 全文来源：知乎搜索摘要

RL.cu 项目：无 PyTorch、无 Python，纯 C++/CUDA 复刻完整 RL 训练（vLLM 风格推理引擎 + GRPO 循环）。动机正是训推不一致：

> 即使权重完全相同，由于不同的 CUDA kernel、不同的 batch size 导致不同的浮点累加顺序，rollout（SGLang/vLLM）与训练（Megatron/FSDP）产生的 log-probability 存在差异。**这个差异在 dense 模型上是 1e-5 到 1e-3 的 K3 KL，在 MoE 模型上可以达到 1e-1，严重时导致训练崩溃。**

根治思路：**Rollout 的 forward 和 training 的 forward 是同一个函数调用 `qwen3_forward()`**——同样的 kernel、同样的归约顺序、同样的内存。共 18 个手写 CUDA kernel（含 FlashAttention-2 前向+反向、GQA、WMMA tensor core、online softmax、cp.async 双缓冲），统一规范 FP16 I/O / FP32 累加，每个 kernel 有 standalone test 与 CPU/PyTorch 参考实现对比。

对照阅读：第六节 FSDP2 的 batch-invariant 路线（两边都用 FlashAttn3 + DeepGEMM 拉齐）与第十一节 RL-Kernel 的算子层路线是同一命题的三种解法——框架级对齐、算子库级对齐、从零同一 kernel。

### 十八、PyTorch 显存分配器六步链路：碎片型 OOM 的完整解释

> 廖一桥 ｜ 赞同 17 ｜ [https://www.zhihu.com/question/410996386/answer/2051340106032845487](https://www.zhihu.com/question/410996386/answer/2051340106032845487) ｜ 崇<紫老头 ｜ 赞同 1 ｜ [https://zhuanlan.zhihu.com/p/2076070720422016190](https://zhuanlan.zhihu.com/p/2076070720422016190) ｜ 全文来源：知乎搜索摘要

第十二节”时间性死亡”的底层机制，一次 alloc 的完整链路：

1. **分桶**：按 1 MiB 阈值进 small/large pool，segment 2 MiB / 20 MiB 档；`roundup_power2_divisions` 时 N 先取整到 2 的幂分档（如 divisions=4 时 1.1MiB→1.25MiB 而非跳 2MiB），避免 shape 小幅波动就开新档；分档越激进，块内无用空间越多；
2. **池内过滤**：① block.stream == 当前流（跨 stream 空闲块不可见）、② size ≥ 请求、③ **event 已完成**——关联未完成 event 的 block 暂跳过。`process_events` 不是后台线程，是每次 alloc 顺带用 `cudaEventQuery`（非阻塞）做的扫描；free 时只有跨 stream 的 block 附加 event。**CUDA Graph capture 期间跳过这一步**；
3. **max_split_size_mb 阈值**：候选块大于阈值而本次是小请求 → 视为未命中不拆分，保护大块；否则切 R 返回、剩余回池——大部分 alloc 在此结束，全程用户态；
4. **cudaMalloc 开新 segment**：池里没有候选才向 driver 要，reserved 上涨；开 expandable_segments 时走 VMM 路径（虚拟地址可增长）；
5. **回收重试**：cudaMalloc 报物理显存不够时，先 cudaFree 完全 inactive 的 segment 再重试，不立即 OOM；
6. **OOM**：错误信息列出 reserved/allocated/请求大小/max_split_size_mb——**用这组数字判断是真没显存还是碎片化过高**。

碎片无法彻底消除的根源：**合并只能发生在同一 segment 内部，不同 cudaMalloc 拿到的段即使地址相邻也不合并 ⇒ 「有空闲却 OOM」**。三层显存数字层层递增属正常：allocated（张量实际占用）< reserved（池总量）< nvidia-smi（还要加 CUDA context 等）。

排查工具速查：`memory_allocated / memory_reserved / max_memory_allocated / memory_stats / memory_summary`；逐次分配调用栈 `torch.cuda.memory._record_memory_history()` + `_dump_snapshot()`（pytorch.org/memory_viz 可视化）；`empty_cache()` 仅在需要给其他进程腾地方时用。

### 十九、显存账本与精度估算：训练/推理两侧的基础算术

> 哒哒 ｜ 赞同 4 ｜ [https://zhuanlan.zhihu.com/p/2083492155214000917](https://zhuanlan.zhihu.com/p/2083492155214000917) ｜ Leeyis ｜ 赞同 1 ｜ [https://zhuanlan.zhihu.com/p/1986431564494701627](https://zhuanlan.zhihu.com/p/1986431564494701627) ｜ 全文来源：知乎搜索摘要

### 训练侧：16P 账本的适用条件

经典混合精度显存账本 2P（低精度权重）+ 2P（低精度梯度）+ 4P（FP32 主权重）+ 8P（Adam 两状态）= **16P——它未计入激活等开销，且依赖具体训练实现，不是通用总显存公式**（对照第一节 sallon88 的 CPU 优化器账本 18N→12N，offload 后的 N 是另一套）。

两种不同的”数值丢失”要分清：梯度太小变零（下溢，Loss Scaling 缓解，**无法修复前向已发生的溢出**）；更新量相对权重太小被舍入掉（`w_new = w_old - ηg` 中 ηg 可表示但加上去看不出变化，靠保留 FP32 主权重精细累积）。BF16 适合训练是因范围宽通常不需要 loss scaling——但仍可能溢出，不保证稳定。FP8 常见混合策略：前向 E4M3（重精度）、反向 E5M2（重范围），配合缩放——是策略不是硬性限制。

### 推理侧（rollout 引擎显存预估）

显存 ≈ 参数量(B) × 单参数字节数 × **1.2**（20% 增量核心是预留 KV Cache）。Qwen3-8B：FP16 约 19.2GB（16GB 卡极限、易 OOM）；FP8 约 9.6GB；FP4 约 4.8GB（需 Blackwell 原生支持）。FP16 与 BF16 的区别一句话：**FP16 刻度细但尺子短（超 65504 即 NaN），BF16 牺牲一点精度换 FP32 同款量程——”不报错”比”过度精确”重要**。
