## llama.cpp 架构

```text
pytorch训练框架 → 导出HuggingFace格式模型 
→ llama.cpp 转换 → ( F16/BF16/F32)GGUF模型 
→ llama.cpp 量化 →  ( Q4/Q6/Q8)GGUF模型  
→ llama.cpp 推理
```

1. 读入 GGUF 模型文件
2. 建立 tokenizer，把文本切成 token
3. 构造系统 prompt
4. 把 token 送进模型做Prefill（上下文预计算）
5. 更新 KV cache，记住已经看过的上下文
6. 得到 logits，也就是“下一个 token 的分数表”
7. 做 sampling（选择下一个 token），从分数表里选出下一个 token
8. 把 token 反解码成文本，一边生成一边输出
9. 把 token 加回输入序列并Decode（逐 token 推理），重复4-8步，循环预测下一个token
10. 停止条件，如：EOS token
11. 最终输出文本：所有生成token拼接

**代码架构：**

llama.cpp 是一个：

- LLM 推理库
- 外加一组 CLI 工具
- 再外加一个 HTTP server / OpenAI 风格接口
- 再外加一堆模型转换、量化、拆分工具

```text
工具层 / 应用层 (包括模型转换和量化)
    tools/cli  tools/server  tools/perplexity  examples/
            ↓
模型推理层
    include/llama.h  +  src/
            ↓
张量计算层
    ggml/
            ↓
CPU / CUDA / Metal / Vulkan / SYCL 等后端
```

## 模型转换和量化（简述）

### GGUF 模型格式

`GGUF` 是 `llama.cpp` 的模型容器格式：

- 既可以放`F32` /`F16` / `BF16` 浮点数权重
- 也可以放 `Q4_K`、`Q5_K`、`Q8_0` 这类量化权重

### GGUF 转换

```text
# convert the model to ggml FP16 format
python3 convert_hf_to_gguf.py ./models/mymodel/
```

1. 读取 HuggingFace<br>model.safetensors/config.json/tokenizer
2. 重排 tensor<br>QKV 合并/transpose/block reshape
3. 写入 GGUF<br>tensor/metadata/tokenizer

### GGUF 量化

```text
# quantize the model to 4-bits (using Q4_K_M method)
./llama-quantize ./models/mymodel/ggml-model-f16.gguf ./models/mymodel/ggml-model-Q4_K_M.gguf Q4_K_M
```

### 权重量化

1. `llama-quant.cpp` 决定“这个 tensor 要量化成什么类型”
2. `llama_tensor_quantize_impl()` 把 tensor 切成 chunk，准备好多线程参数<br>不是一次性量化整个 tensor，而是按 chunk、多线程调用量化函数
3. 对每个 chunk 调用 `ggml_quantize_chunk()`
4. `ggml_quantize_chunk()` 再按 `type` 分发到 `quantize_q4_0()`、`quantize_q4_K()` 之类
5. 上层再把 `dst` 写进新的 GGUF
6. 后端使用量化权重进行计算<br>在 matmul / vec_dot / MMQ 等路径里，直接读取量化 block，边解码边参与乘加计算

### tensor 级混合精度规则

- tensor 名称：比如 `output.weight`、`token_embd.weight`、`attn_v.weight`、`attn_k.weight`、`attn_q.weight`、`ffn_down`、`attn_output.weight`
- 层位置：某些前层、后层，或者每隔几层，会被认为更值得保留更多 bit
- 模型结构：例如是不是 `Falcon`、是不是 `70B`、是不是 `MoE`、`n_gqa` 和 `n_expert` 有多大
- 是否有 imatrix：某些低比特 `IQ` 类型如果没有 imatrix，就会退回到更稳妥的类型
- 用户覆盖项：如 `output_tensor_type`、`token_embedding_type`

可以把它理解成：

1. 先由 llama_ftype 给出一个全局默认类型，比如 Q4_K_M -> GGML_TYPE_Q4_K
2. 再由 llama_tensor_get_type(...) 检查“这个 tensor 是不是关键部位”
3. 如果是关键部位，就把它抬到更高精度；如果是特殊结构，也可能换成另一种更适合的格式

## 生命周期API

1. 拿默认模型参数`llama_model_params`和上下文参数`llama_context_params`
2. 加载模型 `llama_model_load_from_file`
3. 创建 context `llama_init_from_model`
4. 推理 `llama_decode`
5. 释放模型 `llama_model_free` 和上下文 `llama_free`

**推理API**

- 外部调用 `llama_decode()`
- 内部进入 `ctx->decode()`
- 再往里是 `model.build_graph()`
- 最后交给 `ggml` 执行图 `graph_compute`

**其他API**

- logits ：`llama_get_logits`
- tokenize ：`llama_tokenize`
- detokenize：`llama_detokenize`
- sampler：`llama_sampler_chain_init`
- memory / session / state：`llama_memory_seq_rm`、`llama_memory_seq_pos_min`等

## llama.cpp 模型加载

1. CLI 解析参数
2. 打开 GGUF
3. 识别架构
4. 读取 hparams / vocab / stats
5. 建立 `weights_map`
6. 按 backend 策略分配 tensor buffer
7. 初始化 `llama_context`，把本次运行的上下文窗口、batch、线程和 memory 配置固定下来
8. 进入 graph build 与实际推理阶段

### **模型配置读取**

先识别架构、再读 hparams、再读 vocab、再做 stats、最后装 tensors

模型加载真正开始时，`llama_model_load()` 首先创建 `llama_model_loader`。这个加载器的职责是把 GGUF 中的 metadata、tensor 目录和文件数据定位信息整理成后续模型装配可直接使用的索引结构。

在创建完加载器之后，接下来的顺序固定为：

1. `model.load_arch(ml)` <br>从加载器取出架构枚举，并据此确定后续所有分支的入口。
2. `model.load_hparams(ml)`
3. `model.load_vocab(ml)` <br>模型张量和 graph 构建只解决了“怎么算”，词表和 tokenizer 语义则决定了输入 token 和输出 logits 如何对应真实词元空间

这三步把 GGUF 的 KV 从“二进制 metadata”恢复成 `llama_model` 可以直接使用的结构化语义。

`llama_model` 已经知道它属于哪个架构、每层的超参是什么、MoE 和 SSM 需要哪些额外结构、词表如何映射。下一步`load_tensors()`进入的是“这些语义如何变成运行时张量壳，并最终挂上来自 GGUF 的权重字节”。

### **Tensor 命名与映射**

GGUF 打开后，`src/llama-model-loader.cpp` 会扫描 GGUF 里的所有 tensor，把“tensor 名称 -> 对应文件/偏移/元数据”统一放入 `weights_map`。如果是多分片模型，还会把多个 shard 的 tensor 一起合并进同一张映射表里。

从这一刻开始，`llama.cpp` 内部可以通过 tensor 名称查到：

1. 该 tensor 属于哪个 GGUF 文件或 shard。
2. 它在对应文件中的偏移与长度。
3. 它在 GGUF 中声明的 `ggml_type` 和 shape。

这一步把 GGUF 中松散的目录项整合成运行时统一索引，后面的张量注册、数据挂载、buffer 分配都依赖这张索引表。

**实测日志：**

### 权重加载

模型语义恢复之后，`load_tensors()` 开始真正把“GGUF 中的张量目录”接成“`llama_model` 中各字段持有的权重张量”。这一步包含两层动作：

1. 按架构和超参创建张量壳。
2. 把 GGUF 文件中的真实字节挂到这些张量上。

`model.load_tensors(ml)` 并不是简单“把 tensor 读进来”，它同时决定：

- 各层是在 CPU 还是 GPU 还是其他 backend
- 这些张量最终放在哪个 backend buffer
- 需要创建多少个 `ggml_context`

ggml 用来创建 tensor 元数据和图对象的内存池 / 对象容器，不是模型上下文 `llama_context`。<br>它主要负责：

- 创建 `ggml_tensor`
- 保存 tensor 的元信息
- 组织图里的节点对象

**实测日志：**

```text
[llama-debug] cli start: ... n_gpu_layers=8 ...
[llama-debug] model load success: layers=40 devices=1 vocab_only=0
[sched-debug]   split[1]: backend=CUDA0 range=[72,73) n_nodes=1 n_inputs=2
```

- `n_gpu_layers=8`：启动参数里明确要求把一部分层放到 GPU
- `devices=1`：模型加载后已经存在 GPU device 参与
- `backend=CUDA0`：scheduler 在真正拆图执行时，已经把部分 split 派发到 `CUDA0`

这一章结束后，链路推进到“磁盘字节已经挂进运行时 tensor”。模型已经拥有正确的架构语义、正确的张量字段、正确的权重数据地址。下一步进入的就是 graph 构建，也就是“这些张量在一次前向中如何被连接成计算图”。

### Context 初始化

“推理会话的运行现场”，把“这次运行要怎么用这份模型”固定下来，例如：

- 实际使用多大的上下文窗口 `n_ctx`
- 一次大 batch 最多多少 token `n_batch`
- 一次 ubatch 最多多少 token `n_ubatch`
- 线程数是多少
- KV cache / graph scheduler / memory 模块要按什么配置创建

## llama.cpp 推理流程

### 0-进程启动与输入组织层

把一条 CLI 请求一步步整理成 `decode()` 能接收的 `llama_batch batch_inp`。

- 进程启动，解析 `model / n_batch / n_ubatch / prompt`
- 把用户消息套进 `chat template`
- 把完整 prompt tokenize 成 `server_tokens`
- 再把 `server_tokens` 落成 `llama_batch`，并按本轮窗口切成 `batch_view`

第 `0` 层回答的是“这个进程是怎么启动的、模型先收到了什么文本、这些文本又是如何先变成 `server_tokens`，最后再变成 `llama_batch` 并按本轮窗口送进 `decode()` 的”；第 `1` 层回答的才是“这份 `batch_inp` 进入 `decode()` 以后，如何被校验、标准化、准备 memory/scheduler，再继续变成 `ubatch` 并进入构图与执行”。

### 1-请求入口层

```text
llama_context::decode(const llama_batch & batch_inp)
```

接收上一层已经整理好的 `llama_batch batch_inp`，先校验并补齐内部状态，再把 scheduler、memory、ubatch 这些真正跑图前必须准备好的东西全部就位。

1. 检查 batch_inp 输入本身有没有问题 token id 合不合法、`seq_id` 有没有越界、`n_seq_max` 是否超过上限、一些缺省字段是不是需要自动补齐
2. batch_inp 补齐格式， `pos`、`seq_id`、`logits` 这些字段 把“已经 tokenization 的输入”补齐成“llama.cpp 内部可以稳定处理的标准化 batch”。
3. 准备 scheduler 环境 在 prompt token 真正送去构图前，先把“工位、缓存区、搬运路线、可容纳的最大图规模”准备好。 这样后面真正跑 `ubatch` 时，就不容易临时 realloc 或 split 失配。
4. memory_update，把旧 cache 里的待处理动作先结清 处理旧 memory 状态里还挂着的更新动作。 例如某些 slot shift、copy、整理动作，必须先做完，新的 batch 才能安全放进去。
5. ubatch 切块&初始化
6. 逐个执行 ubatch 取 `ubatch`，交给后面的 `process_ubatch()`

通俗理解，`batch` 更像“这一轮总共要处理多少货”，而 `ubatch` 更像“底层执行时一次真正搬进去的一小车货”。 切 `ubatch`，是为了让后面的 memory / graph / backend 更容易处理。

### 2-ubatch 执行入口层

### 3-模型构图&执行层

如果 `process_ubatch()` 决定这轮不能复用旧图，就会进入：

```text
llama_model::build_graph(const llm_graph_params & params)
```

![](https://pic2.zhimg.com/v2-d8d9d12f8c1c250624c6772beeb8a5b9_r.jpg)

构图时，网络是一层一层往后接的。上一层的输出 `inpL` 会作为下一层输入，所以从网络语义上看是串行的。

执行时，`llama.cpp` 先把这一轮需要的计算组织成一张 ggml 计算图，再交给 backend/scheduler 执行。因为层与层之间有数据依赖，所以主干上的先后关系仍然会被保持；但同一层内部、以及一些彼此独立的节点，可能会被调度器并行、融合或异步执行。

**层级关系：**

1. `src/*` 层负责“编排/构图决策”：决定先后顺序、分支选择、状态读写、哪些 `ggml_*` 调用会被放进图里
2. `ggml core` 层负责“建图”：创建张量对象、创建算子节点、记录节点之间的依赖关系
3. `ggml scheduler`：拿整图做分配buffer、子图切分、copy / event / sync、分配子图给backend。
4. `concrete backend`：拿到一张整图或子图，做本 backend 内部的执行与可能的 graph 级优化

**完整流程**

1. src遍历和按顺序构建图，调用 ggml 层创建和初始化ggml节点对象，生成一个ggml计算图
2. src把ggml计算图交给scheduler 调度和执行这张图
3. backend 拿到子图做优化和最终执行节点

### 数据结构

`ggml_tensor` 不只是“数据容器”,是“图节点对象”

```cpp
// 当 `op != GGML_OP_NONE` 且 `src[]` 被填上以后，它就是一个真正的计算节点
struct ggml_tensor {
    enum ggml_type type;
    struct ggml_backend_buffer * buffer;
    int64_t ne[GGML_MAX_DIMS]; // 张量形状
    size_t  nb[GGML_MAX_DIMS]; // 张量步长
​
    enum ggml_op op;           // 这个 tensor 如果是计算节点，对应的算子类型
    int32_t op_params[GGML_MAX_OP_PARAMS / sizeof(int32_t)];
    int32_t flags;
​
    struct ggml_tensor * src[GGML_MAX_SRC]; // 指向上游输入节点
    struct ggml_tensor * view_src;          // 如果它是 view，这里指向原张量
    size_t               view_offs;
    void * data;                            // 数据地址
    char name[GGML_MAX_NAME];
    void * extra;                           // 留给 backend 的附加信息
};

```

`ggml_cgraph` = 节点数组 + 依赖图容器

```cpp
struct ggml_cgraph {
    int size;    // 这张图当前预留的最大容量：最多能装多少 nodes / leafs / grads / grad_accs
    int n_nodes; // 图里实际已有多少个“计算节点”
    int n_leafs; // 图里实际已有多少个“叶子节点”
​
    // `nodes` 是前向计算图里的主节点数组。
    // 1. 这些 ggml_tensor 已经带有 `op` 和 `src[]`，因此是“真正的计算节点”。
    // 2. 执行时 backend 主要就是遍历这一组节点。
    struct ggml_tensor ** nodes;
    // `leafs` 是叶子节点数组。一般表示图的输入、常量、参数权重这类“作为源头被引用，但本身不是由别的 op 算出来”的 tensor。
    struct ggml_tensor ** leafs;
​
    // `grads` 主要服务于反向传播/求梯度场景。可以理解为：“对某个已访问节点求出来的梯度张量”。做普通推理时，通常不会重点用到这一组。
    struct ggml_tensor ** grads;
    // `grad_accs` 是梯度累加器。一个节点的梯度可能从多条下游路径回传回来，需要一个额外位置把这些梯度逐步累加起来。
    struct ggml_tensor ** grad_accs;
​
    // 这个哈希表用来记录构图过程中已经访问过哪些 tensor，避免同一个节点被重复加入图里，也方便建立 use_count / grad 等辅助信息。
    struct ggml_hash_set visited_hash_set;
​
    // 图的遍历/求值顺序配置，例如从左到右或从右到左。
    enum ggml_cgraph_eval_order order;
}

```

### 构图

1. 根据 `arch` 选择对应模型 builder<br>例如 Qwen3.5 进入 `llm_build_qwen35moe`
2. 再逐层调用 `build_layer_attn_linear()`、`build_layer_attn()`、`build_layer_ffn()`
3. 这些 `build_*` 再继续调用 `ggml_*` / `build_lora_mm(...)` / `build_moe_ffn(...)`
4. 最终把这一轮需要的节点组织成一张 `ggml_cgraph`

### 拆 split 子图

```text
ggml_backend_sched_split_graph(...)
```

把一张整图，切成若干段更适合具体 backend 执行的小图。

1. 先给 leaf / node 分配初始 backend
2. 再扩展和修正这些 backend 归属
3. 最后形成多个 split

### scheduler

scheduler 不是“算子执行者”，更像“总调度台”：

- 负责决定这段子图交给谁
- 负责保证输入已经搬到位
- 负责处理 split 之间的同步依赖
- 然后才调用 backend 去执行

### backend 执行

```text
`llama_context::graph_compute(...)` > `ggml_backend_sched_graph_compute_async(sched.get(), gf)`
```

把构图层构好的 `ggml_cgraph * gf`，拆成 scheduler 可调度的 split，并最终把执行结果落回输出 buffer。

1. 遍历当前 split 里的 nodes
2. 按 `node->op` 找到对应实现
3. 调用 matmul / rope / softmax / norm / copy 等底层 kernel

从 backend 接口看出来，至少包含这些能力：

- graph optimize
- tensor set/get/copy
- synchronize
- graph compute
- event 记录/等待

**backend 节点类型**

- kernel ： backend 自己实现的计算核函数，如 CUDA 的 `ggml_cuda_mul_mat_f(...)`、`ggml_cuda_mul_mat_q(...)`，本质上是在 GPU 上发起自定义 CUDA kernel
- copy ：数据拷贝或布局转换，不是计算节点，但同样是合法节点，要被 backend 处理
- activation ：激活函数类算子，通常来自 `GGML_OP_UNARY` 或 GLU 类节点，backend 会根据具体激活类型再分发到对应实现
- 还有一类单独看待：

### build_lora_mm

`build_lora_mm(...)` 把高层“线性层”翻译成 `ggml_mul_mat(...)`

```text
// src/llama-graph.cpp
ggml_tensor * llm_graph_context::build_lora_mm(
          ggml_tensor * w,
          ggml_tensor * cur) const {
    // 这一行是核心：高层“线性层”先落成一个 ggml_mul_mat 节点。
    ggml_tensor * res = ggml_mul_mat(ctx0, w, cur);

    // 如果当前权重上还挂了 LoRA 适配器，这里会再额外挂若干个 matmul/add 节点。
    // 所以 build_lora_mm(...) 不是简单别名，而是“主 matmul + 可选 LoRA 增量子图”的封装。
    for (const auto & lora : *loras) {
        llama_adapter_lora_weight * lw = lora.first->get_weight(w);
        if (lw == nullptr) {
            continue;
        }

        ggml_tensor * ab_cur = ggml_mul_mat(
                ctx0, lw->b,
                ggml_mul_mat(ctx0, lw->a, cur)
                );

        ab_cur = ggml_scale(ctx0, ab_cur, scale);
        res = ggml_add(ctx0, res, ab_cur);
    }

    return res;
}
```

### 创建ggml节点对象

`ggml_mul_mat(...)` 真正创建一个 `GGML_OP_MUL_MAT` 节点对象

- 填节点对象的 `op = GGML_OP_MUL_MAT`
- 填 `src[0]`、`src[1]` 把输入边连起来

```text
// ggml/src/ggml.c
struct ggml_tensor * ggml_mul_mat(
        struct ggml_context * ctx,
        struct ggml_tensor  * a,
        struct ggml_tensor  * b) {
    // 先创建结果 tensor；这一步只是分配节点对象。
    struct ggml_tensor * result = ggml_new_tensor(ctx, GGML_TYPE_F32, 4, ne);

    // 再把它标记成一个真正的 matmul 节点。
    result->op     = GGML_OP_MUL_MAT;
    result->src[0] = a; // 第一个输入边：通常是权重
    result->src[1] = b; // 第二个输入边：通常是激活/输入

    return result;
}
```

`build_lora_mm(gate_inp, cur)` 到这里，已经变成了一条真实的 `ggml` 节点

### 节点并入ggml计算图

节点被并入最终 `ggml_cgraph`

- `ggml_build_forward_expand(...)` 负责把这批节点收进最终 `ggml_cgraph`

以 Qwen3.5 最后的 LM head 为例，模型 builder 会先构出最后一个 matmul，然后把它并进 `gf`：

```text

// 这一步非常关键：从当前输出 cur 反向追踪依赖，把整段前向子图都并进 gf。
// 也就是说，前面 build_lora_mm(...) / ggml_mul_mat(...) 创建的 matmul 节点，
// 会在这里通过依赖追踪真正进入这张待执行的 ggml 计算图。

    // 从输出 tensor 出发，把它依赖到的整段前向子图并入 cgraph。
    ggml_build_forward_impl(cgraph, tensor, true, true);
}
```

1. src 把图交给 scheduler
2. scheduler 分配buffer
3. scheduler 把整图分块成 split graph
4. scheduler 把 split graph 交给对应 backend 执行

graph_compute： src 把图交给 scheduler

ggml_backend_sched_graph_compute_async：scheduler 接手之后，先分配buffer，然后进入 split 执行阶段

```text
// ggml/src/ggml-backend.cpp
enum ggml_status ggml_backend_sched_graph_compute_async(ggml_backend_sched_t sched, struct ggml_cgraph * graph) {
    if (!sched->is_alloc) {
        // 先给这张整图分配执行所需的 buffer。
        if (!ggml_backend_sched_alloc_graph(sched, graph)) {
            return GGML_STATUS_ALLOC_FAILED;
        }
    }

    // 然后进入 split 执行流程。
    return ggml_backend_sched_compute_splits(sched);
}
```

### backend 执行子图

concrete backend 拿到子图后，再按 `node->op` 遍历执行

1. 读取 `ggml_tensor` 节点里的 `op`、`src[]`、shape、type、buffer
2. 决定该用哪条 backend 实现路径 `GGML_OP_MUL_MAT` -> `ggml_compute_forward_mul_mat`
3. 最终调用具体 kernel / cuBLAS / copy / activation 实现函数

CPU backend 入口：

```text
static enum ggml_status ggml_backend_cpu_graph_compute(ggml_backend_t backend, struct ggml_cgraph * cgraph) {
    // CPU backend 拿到的是一张 cgraph子图
    struct ggml_cplan cplan = ggml_graph_plan(cgraph, cpu_ctx->n_threads, cpu_ctx->threadpool);
    return ggml_graph_compute(cgraph, &cplan);
}
```

而在更底层的 CPU 执行里，才会真正遍历 `cgraph->nodes[i]`：

```text
// ggml/src/ggml-cpu/ggml-cpu.c 
struct ggml_cplan ggml_graph_plan(
    const struct ggml_cgraph * cgraph,
    int   n_threads,
    struct ggml_threadpool * threadpool) {
    for (int i = 0; i < cgraph->n_nodes; i++) {
        // backend 此时取到的是这张子图里的某一个 ggml_tensor 节点。
        struct ggml_tensor * node = cgraph->nodes[i];

        // 根据 node->op 决定调用哪种具体实现。
        switch (node->op) {
            case GGML_OP_MUL_MAT:
                // MatMul 节点最终分发到 CPU 的 matmul 实现。
                ggml_compute_forward_mul_mat(params, node);
                break;
            case GGML_OP_CPY:
                // copy 节点最终分发到 CPU 的 copy 实现。
                ggml_compute_forward_cpy(params, node);
                break;
            case GGML_OP_SOFT_MAX:
                // softmax 节点最终分发到 CPU 的 softmax 实现。
                ggml_compute_forward_soft_max(params, node);
                break;
        }
    }
}
```

CUDA backend 本质也一样，也是先拿整张/子张 `cgraph`，然后在 backend 内部决定是否做 graph capture

```text

    // CUDA backend 在这里把 matmul 节点分发到 ggml_cuda_mul_mat(...)。
    ggml_cuda_mul_mat(ctx, dst->src[0], dst->src[1], dst);
    break;
case GGML_OP_CPY:
    // copy 节点则分发到 CUDA 的拷贝实现。
    ggml_cuda_cpy(ctx, dst->src[0], dst->src[1]);
    break;
case GGML_OP_UNARY:
    // unary 节点还会继续按具体子类型二次分发。
    // 例如 SiLU / Sigmoid / ReLU 都属于这一大类。
    switch (ggml_get_unary_op(dst)) {
        case GGML_UNARY_OP_SILU:
            ggml_cuda_op_silu(ctx, dst);
            break;
        case GGML_UNARY_OP_SIGMOID:
            ggml_cuda_op_sigmoid(ctx, dst);
            break;
    }
    break;
```

### matmul核函数

### cpu版本

`ggml_compute_forward_mul_mat()`

1. 从 `dst->src[0]`、`dst->src[1]` 取出 matmul 的两个输入
2. 根据 `src0` 的数据类型，选择合适的 `vec_dot` 实现、目标中间类型和量化转换函数
3. 再把任务切成 chunk，交给 `ggml_compute_forward_mul_mat_one_chunk(...)` 去做真正的块状计算

```text
// ggml/src/ggml-cpu/ggml-cpu.c
void ggml_compute_forward_mul_mat(
        const struct ggml_compute_params * params,
              struct ggml_tensor * dst) {
    // 这里从当前节点 `dst` 回到它的两个输入边。
    const struct ggml_tensor * src0 = dst->src[0];
    const struct ggml_tensor * src1 = dst->src[1];

    // 后面会根据权重类型 src0->type 选择具体的 vec_dot 实现。
    ggml_vec_dot_t    the_vec_dot;
    enum ggml_type    the_vec_dot_type;
    ggml_from_float_t the_from_float;
    int64_t           the_vec_dot_num_rows;

    // 例如 Q4_K、F16、F32 等不同类型，会走不同的 vec_dot / 量化转换路径。
    the_vec_dot          = type_traits_cpu[src0->type].vec_dot;
    the_vec_dot_type     = type_traits_cpu[src0->type].vec_dot_type;
    the_from_float       = type_traits_cpu[the_vec_dot_type].from_float;
    the_vec_dot_num_rows = type_traits_cpu[src0->type].nrows;

    // 真正计算时，不是一次把整个大矩阵生算完，
    // 而是继续切成 chunk / tile，交给下层 one_chunk 实现。
    ggml_compute_forward_mul_mat_one_chunk(
        params, dst, the_vec_dot, the_vec_dot_type, the_vec_dot_num_rows,
        ir0_start, ir0_end, ir1_start, ir1_end);
}
```

`ggml_compute_forward_mul_mat_one_chunk(...)`

```text
// 外层先给当前线程分到一个 chunk。
const int64_t ir0_start = dr0 * ith0;
const int64_t ir0_end   = MIN(ir0_start + dr0, nr0);
const int64_t ir1_start = dr1 * ith1;
const int64_t ir1_end   = MIN(ir1_start + dr1, nr1);

// 某些 dot kernel / mmla kernel 一次能处理 2 行，
// 但如果边界不整齐，就退回到一次 1 行，避免跨界。
int64_t num_rows_per_vec_dot = vec_dot_num_rows;
if ((nr0 % 2 != 0) || (ne11 % 2 != 0) || ((ir0_end - ir0_start) % 2 != 0) || ((ir1_end - ir1_start) % 2 != 0)) {
    num_rows_per_vec_dot = 1;
}

// 然后把这个 chunk 真正交给 one_chunk 去算。
ggml_compute_forward_mul_mat_one_chunk(
    params, dst, the_vec_dot, vec_dot_type, num_rows_per_vec_dot,
    ir0_start, ir0_end, ir1_start, ir1_end);
```

`one_chunk` 内部本体：

```text
// ggml/src/ggml-cpu/ggml-cpu.c
static void ggml_compute_forward_mul_mat_one_chunk(
    const struct ggml_compute_params * params,
    struct ggml_tensor * dst,
    const ggml_vec_dot_t vec_dot,
    const enum ggml_type vec_dot_type,
    const int64_t num_rows_per_vec_dot,
    const int64_t ir0_start,
    const int64_t ir0_end,
    const int64_t ir1_start,
    const int64_t ir1_end) {

    // 从当前 matmul 节点回到两个输入 tensor。
    const struct ggml_tensor * src0 = dst->src[0];
    const struct ggml_tensor * src1 = dst->src[1];

    // 如果 src1 不是当前 vec_dot 所需的连续布局，
    // 前面会先把它整理到 params->wdata；这里统一选真正要读的那块内存。
    const void * wdata = (src1->type == vec_dot_type) ? src1->data : params->wdata;

    // one_chunk 内部还会继续按小 tile 遍历，
    // 不是“一次把整个 chunk 整块算掉”。
    const int64_t blck_0 = 16;
    const int64_t blck_1 = 16;

    for (int64_t iir1 = ir1_start; iir1 < ir1_end; iir1 += blck_1) {
        for (int64_t iir0 = ir0_start; iir0 < ir0_end; iir0 += blck_0) {
            for (int64_t ir1 = iir1; ir1 < iir1 + blck_1 && ir1 < ir1_end; ir1 += num_rows_per_vec_dot) {
                // 定位当前输出列对应的 src0/src1 数据地址。
                const char * src0_row = (const char *) src0->data + (0 + i02 * nb02 + i03 * nb03);
                const char * src1_col = (const char *) wdata + ...;
                float * dst_col = (float *) ((char *) dst->data + (i1 * nb1 + i2 * nb2 + i3 * nb3));

                for (int64_t ir0 = iir0; ir0 < iir0 + blck_0 && ir0 < ir0_end; ir0 += num_rows_per_vec_dot) {
                    // 这里才真正调用底层 vec_dot / mmla 内核，
                    // 把一小块 row x col 的结果算出来。
                    vec_dot(ne00, &tmp[ir0 - iir0], ..., src0_row + ir0 * nb01, ..., src1_col, ..., num_rows_per_vec_dot);
                }

                // 把这个 tile 的临时结果写回当前输出张量 dst。
                memcpy(&dst_col[iir0], tmp, (MIN(iir0 + blck_0, ir0_end) - iir0) * sizeof(float));
            }
        }
    }
}
```

### cuda版本

`ggml_cuda_mul_mat`

```text
// ggml/src/ggml-cuda/ggml-cuda.cu
static void ggml_cuda_mul_mat(ggml_backend_cuda_context & ctx, const ggml_tensor * src0, const ggml_tensor * src1, ggml_tensor * dst) {
    // 先根据 dtype 过滤：这里只接受非量化权重侧（F32/F16/BF16）+ F32 activation + F32 输出。
    bool use_mul_mat_vec_f = (src0->type == GGML_TYPE_F32 || src0->type == GGML_TYPE_F16 || src0->type == GGML_TYPE_BF16)
        && src1->type == GGML_TYPE_F32 && dst->type == GGML_TYPE_F32;

    // 再结合当前 GPU 架构、warp_size、矩阵形状、stride 布局判断：
    // 这个 matmul 是否适合用 MMVF 这条自定义 vector kernel 路径。
    use_mul_mat_vec_f = use_mul_mat_vec_f
        && ggml_cuda_should_use_mmvf(src0->type, cc, src0->ne, src0->nb, src1->ne[1]);

    if (!split && use_mul_mat_vec_f) {
        // 条件满足，就不走通用 cuBLAS，而是走 backend 自己的 CUDA kernel。
        ggml_cuda_mul_mat_vec_f(ctx, src0, src1, nullptr, dst);
    } else {
        // 条件不满足，再退回更通用的 op/cublas 路径。
        ggml_cuda_op_mul_mat(ctx, src0, src1, dst, ggml_cuda_op_mul_mat_cublas, nullptr);
    }
}
```

src0 是 F16/F32/BF16，src1 是 F32，而且 shape / layout / device 条件都适合 `MMVF` 路径时，就会走 ggml_cuda_mul_mat_vec_f(…)。ggml_cuda_mul_mat_vec_f(…) 自己并不做逐元素乘加，它更像 host 侧的 launch 包装器：

## 总结：层数据流图

- `CPU-only`：前 4 层里，第 `4` 层基本表现为 `1 backend + 1 split + 无跨设备 copy`<br>图构好以后，scheduler 基本只是把整图交给 CPU backend 跑
- `CPU+GPU`：前 3 层仍然一样，但第 `4` 层会变成 `2 backends + 多 split + CPU<->CUDA0 copy` 图构好以后，scheduler 还要继续做“拆更多 split、决定哪些段跑 CPU、哪些段跑 CUDA、以及它们之间怎么搬输入和中间结果”
