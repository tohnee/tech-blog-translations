### 2.2 msprof 算子分解（512in/256out × 16 并发）

kernel 总耗时 35.46s / 窗口 40s，设备利用率 ~89%：

| 算子 | 占比 | 备注 |
| --- | --- | --- |
| MatMulV3（aclnn bf16 GEMM） | 64.1% | Cube 利用率 92%，计算 bound，已打满 |
| FusedInferAttentionScore | 15.3% | Cube 56.4%，有优化空间 |
| GDN 线性注意力栈（RGDR + CausalConv1d + gating） | 6.2% | 混合架构特有 |
| 数据搬运（Slice/TensorMove 等） | 4.9% | 框架侧冗余 |

结论：bf16 下 GEMM 已接近上限（Cube 92%），这是做 FP8 的动机—— decode 是权重带宽 bound，FP8 权重字节减半。

### 2.3 完整矩阵（bs × isl）与 bs=1 分解

bs ∈ {1..1024} × isl ∈ {512, 4096}：bf16 吞吐在 isl=512 时 bs=128 见顶 626.7 tok/s，isl=4096 时 bs=32 见顶 131.9 tok/s，之后进入排队主导的平台期。

bs=1 msprof 分解：MatMulV3 占 85.6%、32.85ms/token，有效带宽 ~1.6TB/s——**单流 decode 的 TPOT 基本等于搬一遍权重的时间**，这是全文最重要的事实基座。

### 三、FP8 Block-Scale GEMM kernel 实现

vllm-ascend 官方在 950PR 上还没有 block-scale FP8 GEMM 的对应算子，我们使用 AscendC 开发了这个算子并集成进 vllm-ascend 的量化推理路径（`torch.ops._C_ascend.block_fp8_gemm`）。

### 3.1 量化语义与对齐

对齐 vLLM 上游 `per_token_group_quant_fp8` 与 DeepSeek 系 block-scale 方案：

- 权重：128×128 块级 FP8（e4m3），每块一个 fp32 scale（`weight_scale_inv`）
- 激活：per-token-group-128 动态量化，SFA 为 `[M, K/128]` fp32
- 计算：`C[m,n] = Σ_kb SFA[m,kb] · SFB[kb,n/128] · (A_fp8 · B_fp8 的部分和)`——k 方向每 128 元素（一个 kb）必须把部分和乘上 scale 再累加，**不能在 GEMM 结束后统一乘**，这是整个 kernel 设计的核心约束

### 3.2 Mix kernel 架构（AIC + AIV 协同）

单 kernel 内 cube 与 vector 分工，AIC 做 GEMM、AIV 做 scale 累加：

```text
AIC（cube 侧）                          AIV（vector 侧，每 AIC 带 2 个）
GM --MTE2--> L1(Nd2Nz, B 驻留复用)      GM --MTE2--> SFA scale (UB)
L1 --MTE1--> L0A/L0B (granule 流水)     UB part0/part1 (pingpong)
L0 --Mmad--> L0C (bufC0/bufC1 双缓冲)   Load broadcast 读 scale（VL=64 广播到 128）
L0C --fixpipe--> UB (fp32 部分和)       VF: 部分和 × scale 累加到 acc（fp32）
                                        结束后 acc --MTE3--> GM（cast bf16 输出）
```

关键设计点：

- **dualDstCtrl 按 M 切分**：fixpipe 把 L0C 的 M×N 部分和按 M 劈半同时写两个 AIV 的 UB（`2'b01` 模式），两个 AIV 各管 64 行，N 方向不切——每行只读自己那份 scale，避免了 N 切分下 scale 重复读和跨 AIV 协调
- **跨核握手**：RDY 方向模式 2（AIC set / 两个 AIV wait，精确 pipe：set=PIPE_FIX、wait=PIPE_V），FREE 方向模式 4（AIV0/AIV1 各自 set，AIC 双等 flag f 与 f+16）；握手 flag 做 pingpong 防止单 flag 计数器溢出（同一 flag 最多置 15 次的硬件约束）
- **核内同步**：全部走 GetBuffImpl/ReleaseBuffImpl 硬件 buffer 锁，不用 HardEvent
- **VF 向量化 scale 累加**：Load 用 broadcast 模式从 UB 读 scale（VL=64，一个 scale 管 128 列，N 循环手动 unroll ×2），地址用 post-update，核心就是两条 `Axpy`——acc = part × scale + acc

### 3.3 两级流水线改造（23decc2）

仿真 trace（CA 指令级，转 chrome tracing JSON 分析）驱动了两轮优化：

1. **L0C ping-pong**：L0C 拆 bufC0/bufC1（parity = kb&1），`Mmad(kb)` 只等 `fixpipe(kb−2)`——此前 Mmad 与 fixpipe 严格串行，cube 利用率仅 ~12%
2. **L0 granule 级 4-slot**：LoadData 从每 chunk（4 granule）一发改为每 granule（A+B 各 16KB）一发，prefetch 距离 3，`LoadData(kb+3)` 只等 `Mmad(kb−1)` 释放 slot，拷贝藏进 fixpipe/VF 阴影里

### 3.4 性能演进与 fixpipe 墙

nbuf=8 排除 L2 常驻、iters=30、wall clock：

| case（N=5120, K=5120） | 改造前 | 最终 | 幅度 |
| --- | --- | --- | --- |
| decode M16 | 0.0343 ms | 0.0348 ms | 持平（带宽 bound） |
| M128 | 0.0541 | 0.0434 | −19.8% |
| M256 | 0.0757 | 0.0596 | −21.3% |
| M512 | 0.1355 | 0.1004 | −25.9% |
| M8193 | 1.7757 | 1.2801 ms = 336 TFLOPS | −27.9% |

瓶颈定位（msprof PipeUtilization + 双证据）：

- decode M16 瓶颈是 MTE2（GM→L1 搬权重，带宽 bound，85.1%）；M≥128 起 **FIX pipe（L0C→UB 搬 fp32 部分和）成为第一瓶颈**（M8193 时 94.1%）
- 证据 1（CA 仿真）：`FIX_L0C_TO_DST` 64KB/次中位 514 tick → 127.5 B/cycle
- 证据 2（真机归一化）：case_010 单核 201.9GB/s ÷ 1.65GHz ÷ 94.1% busy ≈ 130 B/cycle
- **fixpipe 数据通路 128 B/cycle 是硬墙**：FIX 字节数 = KB×M×N×4 不随 tiling 变化，fp32 部分和方案天花板 ~372 TFLOPS；要摸到 757T 规格需 258 B/cycle，物理不可达。部分和降 bf16（天花板 ~745T）是破墙方向，但 k-block 强抵消下的精度方案未解决

### 3.5 与 aclnn bf16 同口径对照

| M | FP8（本 kernel） | bf16（aclnn） | 结论 |
| --- | --- | --- | --- |
| 16 | 0.0348 ms | 0.0378 ms | FP8 快 8% |
| 128 | 0.0434 | 0.0419 | 慢 3.5% |
| 256 | 0.0596 | 0.0502 | 慢 19% |
| 512 | 0.1004 | 0.0829 | 慢 21% |
| 8193 | 1.2801（336T） | 1.1741（365.9T ≈ bf16 峰值 97%） | 慢 9% |

差距已从改造前的 1.8–2.1× 收窄到 1.09–1.21×，剩余为 fixpipe 墙的结构性差距。

### 3.6 融合量化算子

per-token-group-128 激活量化从 torch 组合 op 链（reshape/amax/clamp/div/cast，0.046ms/层）下沉为单个融合 AscendC 算子 `torch.ops._C_ascend.per_token_group_quant`（Abs + 两级 vcgmax 求 per-group amax，广播 scale + vdiv + CAST_RINT 出 fp8，**0.0116ms/层**）。这一步直接让 FP8 e2e 从”高并发落后 bf16”翻为领先（见 4.2）。

| --- | --- | --- | --- |
| GSM8K test（1319 题） | 89.08% | 89.01% | −0.07pp（1 题） |
| C-Eval 数学 val（37 题） | 91.89% | 89.19% | −2.70pp（1 题，噪声内） |

### 4.2 性能（融合量化版，vs bf16）

| 场景 | bf16 | FP8 | 变化 |
| --- | --- | --- | --- |
| 512in/256out conc16 吞吐 | 210.3 tok/s | 302.4 tok/s | +43.8% |
| 256in/256out conc64 吞吐 | 650.5 | 735.3 | +13.0% |
| 32in/512out conc8 TPOT | 48.7ms | 40.6ms | −16.6% |
| bs=1 单流 TPOT | 37.02ms | 27.14ms | −26.7% |
| bs=1 输出吞吐 | 26.9 tok/s | 36.7 tok/s | +36.2% |

bs=1 msprof 对账：每 token 27ms 中 FP8 GEMM 18.1ms（65%，~1.6TB/s 带宽 bound）、量化 2.0ms、attention 1.4ms、lm_head（仍 bf16）2.0ms、GDN 栈 1.7ms、搬运 2.6ms（其中 PadV3 1.2ms 是可消除的附属开销）。host 侧空隙 ≈ 0（ACL Graph + 异步调度完全隐藏）。

已知弱区：bs≥32 高并发下 chunked-prefill 的大 M 分块落在 FP8 kernel 弱区（isl=4096 时惩罚放大），落地需 decode-FP8 / prefill-bf16 混合路径。

### 五、MTP 投机解码（官方 MTP 头实测）

模型自带 1 层官方 MTP（`mtp_num_hidden_layers=1`，fc + 1 个 full-attention decoder layer，共享 embedding/lm_head；FP8 checkpoint 里 MTP 权重同样量化）。启用仅需：

```text
--speculative-config '{"method":"mtp","num_speculative_tokens":2}'
```

gsm8k 真实文本（256 条 few-shot prompt，~512 token）实测：

| bs | bf16 无 MTP | bf16 nst=2 | FP8 无 MTP | FP8 nst=2 |
| --- | --- | --- | --- | --- |
| 1 | 37.44ms / 26.4 tok/s | 18.05 / 53.6 | 27.37 / 35.7 | 13.99 / 67.1 |
| 8 | 53.49 / 141.7 | 27.11 / 261.7 | 54.62 / 134.0 | 26.35 / 257.5 |
| 32 | 71.68 / 398.2 | 43.74 / 606.6 | 80.30 / 345.7 | 47.85 / 522.1 |
| 128 | 179.68 / 626.7 | 70.23 / 678.6 | 271.79 / 412.3 | 188.35 / 363.5 |

- 接受率：nst=1 约 79%；nst=2 第 1⁄2 个 token 分别 ~79%/~62%，平均每步产出 2.4 token
- 真实文本比 random 输入接受率高 10~15 个百分点（random 口径会系统性低估 MTP）
- 唯一例外：FP8 bs=128 nst=2——verify 每步 384 token 落在 FP8 GEMM prefill 弱区，吞吐反噬；FP8 高并发留 nst=1 即可
- 代价：MTP draft 吃 Mamba cache，max-num-seqs 从 625⁄865 降到 554/781（bf16/FP8）

### 六、局限与后续方向

1. **混合路径集成（优先级最高）**：serve 侧按 M 分发——小 M（decode/小批量）走 FP8 kernel、大 M（prefill 分块、MTP verify）回退 aclnn bf16，可同时拿 decode 带宽收益、消掉 prefill 惩罚、补上 FP8+MTP nst=2 高并发短板
2. **fixpipe瓶颈，这里主要是因为Qwen官方的这个FP8是为了迁就NVIDIA Hopper系列过低精度，需要K=128的tile做一次软件的累加，如果用MXFP8，那不应该有这么多fixpipe的流量**
3. **bs=1 残余优化**：PadV3（1.2ms/token）消除、lm_head 量化（1.6ms/token）
4. **注意力侧**：FusedInferAttentionScore Cube 利用率 56%，等 vllm-ascend 后续版本调优

### 附：复现方法

代码在 vllm-ascend 的 `qwen3.8-950` 分支上（基于 releases/v0.23.0，本文工作目录 `/workspace/qwen3.8/vllm-ascend`）。在 950PR 上从零复现的流程如下。先装 vllm 和 vllm-ascend 源码（vllm 从 gitcode 镜像 `git@gitcode.com:GitHub_Trending/vl/vllm.git` 拉 v0.23.0，或直接用 GitHub 原仓）：

```text
git clone -b v0.23.0 https://github.com/vllm-project/vllm.git
cd vllm && VLLM_TARGET_DEVICE=empty pip install -e . && cd ..

git clone -b qwen3.8-950 https://github.com/lenLRX/vllm-ascend
cd vllm-ascend
source /usr/local/Ascend/ascend-toolkit/set_env.sh
export SOC_VERSION=ascend950pr_9579
pip install -e .
```

权重用 ModelScope 下载（bf16 52GB，FP8 29GB）：

```text
pip install modelscope
modelscope download --model Qwen/Qwen3.8-27B --local_dir ./models/Qwen3.8-27B
modelscope download --model Qwen/Qwen3.8-27B-FP8 --local_dir ./models/Qwen3.8-27B-FP8
```

起服务并压测（注意 vllm 命令不要在源码目录里跑，cd 到别处，避免遮蔽已安装的包）：

```text
cd /tmp
vllm serve /path/to/Qwen3.8-27B-FP8 --port 8000          # 换 bf16 路径即测 bf16
# 开 MTP 投机解码只需加：--speculative-config '{"method":"mtp","num_speculative_tokens":2}'

vllm bench serve --model /path/to/Qwen3.8-27B-FP8 --tokenizer /path/to/Qwen3.8-27B-FP8 \
  --dataset-name random --random-input-len 512 --random-output-len 256 \
  --num-prompts 64 --max-concurrency 16 --endpoint /v1/completions --ignore-eos
```

FP8 GEMM kernel 的单测和回归在 `vllm-ascend/csrc/block_fp8_gemm/` 下：`ref/gen_data.py` 生成 11 个 case 的输入和 golden，`cmake --build build -j8` 编译（机器内存小，并发别开高），`./build/block_fp8_gemm <case目录> <输出目录> 30 8` 跑 30 次迭代取均值（nbuf=8 排除 L2 缓存影响），`python3 ref/compare.py <case目录> --kernel-y <输出目录>/y.bin` 和 golden 比对。本文全部测试数据见 `bench/REPORT.md`，逐 cell 原始结果在 `bench/results/`。[HiDevLab](https://hidevlab.huawei.com/online-develop)

bs ∈ {1..1024} × isl ∈ {512, 4096}：bf16 吞吐在 isl=512 时 bs=128 见顶 626.7 tok/s，isl=4096 时 bs=32 见顶 131.9 tok/s，之后进入排队主导的平台期。

bs=1 msprof 分解：MatMulV3 占 85.6%、32.85ms/token，有效带宽 ~1.6TB/s——**单流 decode 的 TPOT 基本等于搬一遍权重的时间**，这是全文最重要的事实基座。

### 三、FP8 Block-Scale GEMM kernel 实现

vllm-ascend 官方在 950PR 上还没有 block-scale FP8 GEMM 的对应算子，我们使用 AscendC 开发了这个算子并集成进 vllm-ascend 的量化推理路径（`torch.ops._C_ascend.block_fp8_gemm`）。

### 3.1 量化语义与对齐

对齐 vLLM 上游 `per_token_group_quant_fp8` 与 DeepSeek 系 block-scale 方案：

- 权重：128×128 块级 FP8（e4m3），每块一个 fp32 scale（`weight_scale_inv`）
- 激活：per-token-group-128 动态量化，SFA 为 `[M, K/128]` fp32
- 计算：`C[m,n] = Σ_kb SFA[m,kb] · SFB[kb,n/128] · (A_fp8 · B_fp8 的部分和)`——k 方向每 128 元素（一个 kb）必须把部分和乘上 scale 再累加，**不能在 GEMM 结束后统一乘**，这是整个 kernel 设计的核心约束

### 3.2 Mix kernel 架构（AIC + AIV 协同）

单 kernel 内 cube 与 vector 分工，AIC 做 GEMM、AIV 做 scale 累加：

```text
AIC（cube 侧）                          AIV（vector 侧，每 AIC 带 2 个）
GM --MTE2--> L1(Nd2Nz, B 驻留复用)      GM --MTE2--> SFA scale (UB)
L1 --MTE1--> L0A/L0B (granule 流水)     UB part0/part1 (pingpong)
L0 --Mmad--> L0C (bufC0/bufC1 双缓冲)   Load broadcast 读 scale（VL=64 广播到 128）
L0C --fixpipe--> UB (fp32 部分和)       VF: 部分和 × scale 累加到 acc（fp32）
                                        结束后 acc --MTE3--> GM（cast bf16 输出）
```

关键设计点：

- **dualDstCtrl 按 M 切分**：fixpipe 把 L0C 的 M×N 部分和按 M 劈半同时写两个 AIV 的 UB（`2'b01` 模式），两个 AIV 各管 64 行，N 方向不切——每行只读自己那份 scale，避免了 N 切分下 scale 重复读和跨 AIV 协调
- **跨核握手**：RDY 方向模式 2（AIC set / 两个 AIV wait，精确 pipe：set=PIPE_FIX、wait=PIPE_V），FREE 方向模式 4（AIV0/AIV1 各自 set，AIC 双等 flag f 与 f+16）；握手 flag 做 pingpong 防止单 flag 计数器溢出（同一 flag 最多置 15 次的硬件约束）
- **核内同步**：全部走 GetBuffImpl/ReleaseBuffImpl 硬件 buffer 锁，不用 HardEvent
- **VF 向量化 scale 累加**：Load 用 broadcast 模式从 UB 读 scale（VL=64，一个 scale 管 128 列，N 循环手动 unroll ×2），地址用 post-update，核心就是两条 `Axpy`——acc = part × scale + acc

### 3.3 两级流水线改造（23decc2）

仿真 trace（CA 指令级，转 chrome tracing JSON 分析）驱动了两轮优化：

1. **L0C ping-pong**：L0C 拆 bufC0/bufC1（parity = kb&1），`Mmad(kb)` 只等 `fixpipe(kb−2)`——此前 Mmad 与 fixpipe 严格串行，cube 利用率仅 ~12%
2. **L0 granule 级 4-slot**：LoadData 从每 chunk（4 granule）一发改为每 granule（A+B 各 16KB）一发，prefetch 距离 3，`LoadData(kb+3)` 只等 `Mmad(kb−1)` 释放 slot，拷贝藏进 fixpipe/VF 阴影里

### 3.4 性能演进与 fixpipe 墙

nbuf=8 排除 L2 常驻、iters=30、wall clock：

| case（N=5120, K=5120） | 改造前 | 最终 | 幅度 |
| --- | --- | --- | --- |
| decode M16 | 0.0343 ms | 0.0348 ms | 持平（带宽 bound） |
| M128 | 0.0541 | 0.0434 | −19.8% |
| M256 | 0.0757 | 0.0596 | −21.3% |
| M512 | 0.1355 | 0.1004 | −25.9% |
| M8193 | 1.7757 | 1.2801 ms = 336 TFLOPS | −27.9% |

瓶颈定位（msprof PipeUtilization + 双证据）：

- decode M16 瓶颈是 MTE2（GM→L1 搬权重，带宽 bound，85.1%）；M≥128 起 **FIX pipe（L0C→UB 搬 fp32 部分和）成为第一瓶颈**（M8193 时 94.1%）
- 证据 1（CA 仿真）：`FIX_L0C_TO_DST` 64KB/次中位 514 tick → 127.5 B/cycle
- 证据 2（真机归一化）：case_010 单核 201.9GB/s ÷ 1.65GHz ÷ 94.1% busy ≈ 130 B/cycle
- **fixpipe 数据通路 128 B/cycle 是硬墙**：FIX 字节数 = KB×M×N×4 不随 tiling 变化，fp32 部分和方案天花板 ~372 TFLOPS；要摸到 757T 规格需 258 B/cycle，物理不可达。部分和降 bf16（天花板 ~745T）是破墙方向，但 k-block 强抵消下的精度方案未解决

### 3.5 与 aclnn bf16 同口径对照

| M | FP8（本 kernel） | bf16（aclnn） | 结论 |
| --- | --- | --- | --- |
| 16 | 0.0348 ms | 0.0378 ms | FP8 快 8% |
| 128 | 0.0434 | 0.0419 | 慢 3.5% |
| 256 | 0.0596 | 0.0502 | 慢 19% |
| 512 | 0.1004 | 0.0829 | 慢 21% |
| 8193 | 1.2801（336T） | 1.1741（365.9T ≈ bf16 峰值 97%） | 慢 9% |

差距已从改造前的 1.8–2.1× 收窄到 1.09–1.21×，剩余为 fixpipe 墙的结构性差距。

### 3.6 融合量化算子

per-token-group-128 激活量化从 torch 组合 op 链（reshape/amax/clamp/div/cast，0.046ms/层）下沉为单个融合 AscendC 算子 `torch.ops._C_ascend.per_token_group_quant`（Abs + 两级 vcgmax 求 per-group amax，广播 scale + vdiv + CAST_RINT 出 fp8，**0.0116ms/层**）。这一步直接让 FP8 e2e 从”高并发落后 bf16”翻为领先（见 4.2）。

### 4.2 性能（融合量化版，vs bf16）

| 场景 | bf16 | FP8 | 变化 |
| --- | --- | --- | --- |
| 512in/256out conc16 吞吐 | 210.3 tok/s | 302.4 tok/s | +43.8% |
| 256in/256out conc64 吞吐 | 650.5 | 735.3 | +13.0% |

### 五、MTP 投机解码（官方 MTP 头实测）

模型自带 1 层官方 MTP（`mtp_num_hidden_layers=1`，fc + 1 个 full-attention decoder layer，共享 embedding/lm_head；FP8 checkpoint 里 MTP 权重同样量化）。启用仅需：

```text
--speculative-config '{"method":"mtp","num_speculative_tokens":2}'
```

gsm8k 真实文本（256 条 few-shot prompt，~512 token）实测：

| bs | bf16 无 MTP | bf16 nst=2 | FP8 无 MTP | FP8 nst=2 |
| --- | --- | --- | --- | --- |
| 1 | 37.44ms / 26.4 tok/s | 18.05 / 53.6 | 27.37 / 35.7 | 13.99 / 67.1 |
| 8 | 53.49 / 141.7 | 27.11 / 261.7 | 54.62 / 134.0 | 26.35 / 257.5 |
| 32 | 71.68 / 398.2 | 43.74 / 606.6 | 80.30 / 345.7 | 47.85 / 522.1 |
| 128 | 179.68 / 626.7 | 70.23 / 678.6 | 271.79 / 412.3 | 188.35 / 363.5 |

- 接受率：nst=1 约 79%；nst=2 第 1⁄2 个 token 分别 ~79%/~62%，平均每步产出 2.4 token
- 真实文本比 random 输入接受率高 10~15 个百分点（random 口径会系统性低估 MTP）
- 唯一例外：FP8 bs=128 nst=2——verify 每步 384 token 落在 FP8 GEMM prefill 弱区，吞吐反噬；FP8 高并发留 nst=1 即可
- 代价：MTP draft 吃 Mamba cache，max-num-seqs 从 625⁄865 降到 554/781（bf16/FP8）

### 六、局限与后续方向

1. **混合路径集成（优先级最高）**：serve 侧按 M 分发——小 M（decode/小批量）走 FP8 kernel、大 M（prefill 分块、MTP verify）回退 aclnn bf16，可同时拿 decode 带宽收益、消掉 prefill 惩罚、补上 FP8+MTP nst=2 高并发短板
2. **破 fixpipe 墙**：部分和降 bf16（天花板 ~745 TFLOPS），需解决分裂累加的精度问题，需另行立项
3. **bs=1 残余优化**：PadV3（1.2ms/token）消除、lm_head 量化（1.6ms/token）
4. **注意力侧**：FusedInferAttentionScore Cube 利用率 56%，等 vllm-ascend 后续版本调优

| M8193 | 1.7757 | 1.2801 ms = 336 TFLOPS | −27.9% |

瓶颈定位（msprof PipeUtilization + 双证据）：

- decode M16 瓶颈是 MTE2（GM→L1 搬权重，带宽 bound，85.1%）；M≥128 起 **FIX pipe（L0C→UB 搬 fp32 部分和）成为第一瓶颈**（M8193 时 94.1%）
- 证据 1（CA 仿真）：`FIX_L0C_TO_DST` 64KB/次中位 514 tick → 127.5 B/cycle
- 证据 2（真机归一化）：case_010 单核 201.9GB/s ÷ 1.65GHz ÷ 94.1% busy ≈ 130 B/cycle
- **fixpipe 数据通路 128 B/cycle 是硬墙**：FIX 字节数 = KB×M×N×4 不随 tiling 变化，fp32 部分和方案天花板 ~372 TFLOPS；要摸到 757T 规格需 258 B/cycle，物理不可达。部分和降 bf16（天花板 ~745T）是破墙方向，但 k-block 强抵消下的精度方案未解决

### 3.5 与 aclnn bf16 同口径对照

| M | FP8（本 kernel） | bf16（aclnn） | 结论 |
| --- | --- | --- | --- |
| 16 | 0.0348 ms | 0.0378 ms | FP8 快 8% |
| 128 | 0.0434 | 0.0419 | 慢 3.5% |
| 256 | 0.0596 | 0.0502 | 慢 19% |
| 512 | 0.1004 | 0.0829 | 慢 21% |
| 8193 | 1.2801（336T） | 1.1741（365.9T ≈ bf16 峰值 97%） | 慢 9% |

差距已从改造前的 1.8–2.1× 收窄到 1.09–1.21×，剩余为 fixpipe 墙的结构性差距。

### 3.6 融合量化算子

per-token-group-128 激活量化从 torch 组合 op 链（reshape/amax/clamp/div/cast，0.046ms/层）下沉为单个融合 AscendC 算子 `torch.ops._C_ascend.per_token_group_quant`（Abs + 两级 vcgmax 求 per-group amax，广播 scale + vdiv + CAST_RINT 出 fp8，**0.0116ms/层**）。这一步直接让 FP8 e2e 从”高并发落后 bf16”翻为领先（见 4.2）。

### 4.2 性能（融合量化版，vs bf16）

| 场景 | bf16 | FP8 | 变化 |
| --- | --- | --- | --- |
| 512in/256out conc16 吞吐 | 210.3 tok/s | 302.4 tok/s | +43.8% |
| 256in/256out conc64 吞吐 | 650.5 | 735.3 | +13.0% |
| 32in/512out conc8 TPOT | 48.7ms | 40.6ms | −16.6% |

bs=1 msprof 对账：每 token 27ms 中 FP8 GEMM 18.1ms（65%，~1.6TB/s 带宽 bound）、量化 2.0ms、attention 1.4ms、lm_head（仍 bf16）2.0ms、GDN 栈 1.7ms、搬运 2.6ms（其中 PadV3 1.2ms 是可消除的附属开销）。host 侧空隙 ≈ 0（ACL Graph + 异步调度完全隐藏）。

### 五、MTP 投机解码（官方 MTP 头实测）

模型自带 1 层官方 MTP（`mtp_num_hidden_layers=1`，fc + 1 个 full-attention decoder layer，共享 embedding/lm_head；FP8 checkpoint 里 MTP 权重同样量化）。启用仅需：

```text
--speculative-config '{"method":"mtp","num_speculative_tokens":2}'
```

gsm8k 真实文本（256 条 few-shot prompt，~512 token）实测：

| bs | bf16 无 MTP | bf16 nst=2 | FP8 无 MTP | FP8 nst=2 |
| --- | --- | --- | --- | --- |
| 1 | 37.44ms / 26.4 tok/s | 18.05 / 53.6 | 27.37 / 35.7 | 13.99 / 67.1 |
| 8 | 53.49 / 141.7 | 27.11 / 261.7 | 54.62 / 134.0 | 26.35 / 257.5 |
| 32 | 71.68 / 398.2 | 43.74 / 606.6 | 80.30 / 345.7 | 47.85 / 522.1 |
| 128 | 179.68 / 626.7 | 70.23 / 678.6 | 271.79 / 412.3 | 188.35 / 363.5 |

- 接受率：nst=1 约 79%；nst=2 第 1⁄2 个 token 分别 ~79%/~62%，平均每步产出 2.4 token
- 真实文本比 random 输入接受率高 10~15 个百分点（random 口径会系统性低估 MTP）
- 唯一例外：FP8 bs=128 nst=2——verify 每步 384 token 落在 FP8 GEMM prefill 弱区，吞吐反噬；FP8 高并发留 nst=1 即可
- 代价：MTP draft 吃 Mamba cache，max-num-seqs 从 625⁄865 降到 554/781（bf16/FP8）

### 六、局限与后续方向

1. **混合路径集成（优先级最高）**：serve 侧按 M 分发——小 M（decode/小批量）走 FP8 kernel、大 M（prefill 分块、MTP verify）回退 aclnn bf16，可同时拿 decode 带宽收益、消掉 prefill 惩罚、补上 FP8+MTP nst=2 高并发短板
2. **破 fixpipe 墙**：部分和降 bf16（天花板 ~745 TFLOPS），需解决分裂累加的精度问题，需另行立项
3. **bs=1 残余优化**：PadV3（1.2ms/token）消除、lm_head 量化（1.6ms/token）
4. **注意力侧**：FusedInferAttentionScore Cube 利用率 56%，等 vllm-ascend 后续版本调优

### 附：复现方法

代码在 vllm-ascend 的 `qwen3.8-950` 分支上（基于 releases/v0.23.0，本文工作目录 `/workspace/qwen3.8/vllm-ascend`）。在 950PR 上从零复现的流程如下。先装 vllm 和 vllm-ascend 源码（vllm 从 gitcode 镜像 `git@gitcode.com:GitHub_Trending/vl/vllm.git` 拉 v0.23.0，或直接用 GitHub 原仓）：

```text
git clone -b v0.23.0 https://github.com/vllm-project/vllm.git
cd vllm && VLLM_TARGET_DEVICE=empty pip install -e . && cd ..

git clone -b releases/v0.23.0 https://github.com/vllm-project/vllm-ascend.git
cd vllm-ascend
source /usr/local/Ascend/ascend-toolkit/set_env.sh
export SOC_VERSION=ascend950pr_9579
pip install -e .
```

权重用 ModelScope 下载（bf16 52GB，FP8 29GB）：

```text
pip install modelscope
modelscope download --model Qwen/Qwen3.8-27B --local_dir ./models/Qwen3.8-27B
modelscope download --model Qwen/Qwen3.8-27B-FP8 --local_dir ./models/Qwen3.8-27B-FP8
```

起服务并压测（注意 vllm 命令不要在源码目录里跑，cd 到别处，避免遮蔽已安装的包）：

```text
cd /tmp
vllm serve /path/to/Qwen3.8-27B-FP8 --port 8000          # 换 bf16 路径即测 bf16
# 开 MTP 投机解码只需加：--speculative-config '{"method":"mtp","num_speculative_tokens":2}'

vllm bench serve --model /path/to/Qwen3.8-27B-FP8 --tokenizer /path/to/Qwen3.8-27B-FP8 \
  --dataset-name random --random-input-len 512 --random-output-len 256 \
  --num-prompts 64 --max-concurrency 16 --endpoint /v1/completions --ignore-eos
```

FP8 GEMM kernel 的单测和回归在 `vllm-ascend/csrc/block_fp8_gemm/` 下：`ref/gen_data.py` 生成 11 个 case 的输入和 golden，`cmake --build build -j8` 编译（机器内存小，并发别开高），`./build/block_fp8_gemm <case目录> <输出目录> 30 8` 跑 30 次迭代取均值（nbuf=8 排除 L2 缓存影响），`python3 ref/compare.py <case目录> --kernel-y <输出目录>/y.bin` 和 golden 比对。本文全部测试数据见 `bench/REPORT.md`，逐 cell 原始结果在 `bench/results/`。
