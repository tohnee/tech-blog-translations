## MLOps 学习路线

---

### 一、什么是 MLOps

MLOps = Machine Learning + DevOps。

它解决的核心问题是：**如何把一个 Jupyter Notebook 里跑通的模型变成一个可靠运行的生产系统。**

学术界关注的是模型精度（accuracy 提高 0.5%），工业界关注的是系统可靠性（SLA 99.9%、延迟 P99 < 200ms、模型每周自动更新）。MLOps 就是连接这两个世界的工程体系。

### 和 DevOps 的区别

| 维度 | DevOps | MLOps |
| --- | --- | --- |
| 核心产物 | 代码 | 代码 + 数据 + 模型 |
| 版本管理 | Git 管代码 | Git 管代码 + DVC 管数据 + MLflow 管模型 |
| 测试 | 单元测试/集成测试 | 数据验证 + 模型评估 + A/B 测试 |
| 部署 | 容器 + CI/CD | 容器 + CI/CD + 模型服务化 |
| 监控 | 系统指标 | 系统指标 + 数据漂移 + 模型性能衰减 |
| 迭代触发 | 需求变更 | 需求变更 + 数据变化 + 模型退化 |

MLOps 比 DevOps 多了两个维度：**数据**和**模型**，这两者都是活的——数据分布会变，模型性能会衰减。这决定了 MLOps 不只是部署一次就完事，而是一个持续运转的闭环。

一个完整的 MLOps 系统包含以下几个层面：

```text

```

### 三、学习路线（分四个阶段）

### 阶段一：基础设施与工程基本功

这一阶段不涉及 ML，但决定了你后面能走多远。

**必修内容：**

- **Python 工程化**：不是 Jupyter Notebook 里的脚本，而是可维护的项目结构。学会用 Poetry/uv 管理依赖，用 pytest 写测试，用 mypy 做类型检查。
- **Git 工作流**：分支策略、代码评审、CI 触发。这是所有工程协作的基础。
- **Docker**：学会写 Dockerfile、理解镜像分层、多阶段构建。ML 项目的环境复杂度远高于普通 Web 项目（CUDA 驱动、Python 版本、C++ 依赖），Docker 是唯一可靠的环境一致性方案。
- **Linux 基础**：会看日志、会用 tmux、会配 SSH、理解文件权限和进程管理。
- **云平台入门**：AWS/GCP/阿里云任选一个，理解 EC2/ECS/S3 等基本服务。不需要精通，但要知道什么东西放在什么地方。

**推荐工具：**

| 工具 | 用途 |
| --- | --- |
| Docker + Docker Compose | 容器化 |
| GitHub Actions / GitLab CI | CI/CD |
| Terraform / Pulumi | 基础设施即代码 |
| AWS / GCP / 阿里云 | 云平台 |

**验收标准**：能把一个 Python 项目打包成 Docker 镜像，通过 CI 自动构建并推送到镜像仓库。

### 阶段二：数据管理与实验跟踪

ML 的特殊性在于：数据是第一等公民。代码不变但数据变了，结果就不一样。

**必修内容：**

**1. 数据版本管理**

用 DVC（Data Version Control）或 LakeFS 对数据集进行版本控制。核心概念：数据和代码一起版本化，任何时候都能精确还原”哪个版本的代码 + 哪个版本的数据 → 哪个模型”。

```text
dvc init
dvc add data/training_set.parquet
git add data/training_set.parquet.dvc
git commit -m "add training data v1"
dvc push  # 推送到远程存储（S3/OSS）
```

**2. 数据质量验证**

用 Great Expectations 或 Pandera 定义数据质量规则，在 pipeline 中自动校验。

核心检查项：

- Schema 是否一致（字段名、类型）
- 值域是否合理（年龄不能为负、价格不能为零）
- 分布是否漂移（新数据和训练数据的分布差异）
- 缺失值比例是否超标

**3. 特征工程与特征仓库**

特征仓库（Feature Store）解决的问题是：训练和推理用同一套特征计算逻辑，避免 training-serving skew。

主要方案：

- **Feast**（开源）：轻量级特征仓库，支持离线/在线特征服务
- **Tecton**（商业）：企业级特征平台
- **Hopsworks**（开源+商业）：全功能 ML 数据平台

**4. 实验跟踪**

每次训练实验需要记录：超参数、指标、模型产物、数据版本、代码版本、环境信息。

| 工具 | 定位 | 特点 |
| --- | --- | --- |
| MLflow | 开源标准 | 轻量、易部署、社区大、与主流框架集成好 |
| Weights & Biases | SaaS + 开源 | 可视化强、团队协作好、实验对比直观 |
| Neptune.ai | SaaS | 元数据存储强大 |
| ClearML | 开源 | 功能全面、自带编排 |

MLflow 是首选。它覆盖了实验跟踪、模型注册、模型部署三个环节，生态最成熟。

```text
import mlflow

mlflow.set_experiment("text-classification")

with mlflow.start_run():
    mlflow.log_param("model", "bert-base")
    mlflow.log_param("lr", 2e-5)
    mlflow.log_param("epochs", 3)
    
    # ... 训练 ...
    
    mlflow.log_metric("accuracy", 0.92)
    mlflow.log_metric("f1", 0.89)
    mlflow.sklearn.log_model(model, "model")
```

**验收标准**：能用 DVC 管理数据集版本，用 MLflow 跟踪实验，任意两次实验可以精确对比差异。

### 阶段三：模型部署与服务化

训练好的模型如何变成一个可调用的 API？

**必修内容：**

**1. 模型打包**

模型需要和它的预处理逻辑、后处理逻辑打包在一起。常用格式：

- ONNX：跨框架通用格式，推理优化好
- TorchScript：PyTorch 原生导出
- MLflow Model：带签名和依赖的标准化打包

**2. 模型服务框架**

| 框架 | 适用场景 | 特点 |
| --- | --- | --- |
| BentoML | 通用 ML | 打包+部署一体化，支持批处理，API 简洁 |
| Seldon Core | Kubernetes 环境 | 企业级、支持 A/B 测试和金丝雀发布 |
| TorchServe | PyTorch 模型 | 官方出品，支持模型版本管理 |
| Triton | 高性能推理 | NVIDIA 出品，多框架支持，动态批处理 |
| vLLM | LLM 推理 | 专为大语言模型优化（PagedAttention） |
| TGI | LLM 推理 | HuggingFace 出品，生产级 LLM 服务 |

对于传统 ML 模型，BentoML 是最易上手的选择。对于 LLM，vLLM 和 TGI 是当前标准。

```text
# BentoML 示例
import bentoml

@bentoml.service
class TextClassifier:
    model = bentoml.models.get("text-clf:latest")
    
    @bentoml.api
    def predict(self, text: str) -> dict:
        result = self.model.predict(text)
        return {"label": result.label, "score": result.score}
```

**3. 容器化部署**

模型服务 → Docker 镜像 → Kubernetes 部署。需要理解：

- Pod / Deployment / Service / Ingress 的关系
- HPA（水平自动扩缩容）：根据 QPS 或 GPU 利用率自动伸缩
- GPU 调度：node selector、device plugin
- 健康检查：readiness probe（模型加载完成）和 liveness probe

**4. CI/CD for ML**

传统 CI/CD 只管代码。ML 的 CI/CD 需要额外处理：

- 数据变更触发重新训练
- 模型评估通过后自动部署（评估指标 > 阈值 → 自动发布）
- 金丝雀发布：新模型先接 5% 流量，观察指标无异常后全量切换
- 回滚机制：新模型效果变差时一键回退

**验收标准**：能把一个模型打包成 Docker 容器，部署到 K8s，配好自动扩缩容，通过 CI/CD 实现模型的自动评估和发布。

### 阶段四：监控、治理与持续迭代

模型上线只是开始。线上模型会随着数据分布变化而逐渐退化，这是 ML 系统和传统软件最大的区别。

**必修内容：**

**1. 模型监控**

需要监控三个层面：

```text
基础设施指标    → 延迟、吞吐、CPU/GPU 利用率、内存
模型性能指标    → 准确率、F1、AUC（需要标注回流）
数据质量指标    → 特征分布漂移、缺失率、异常值比例
```

数据漂移（Data Drift）是最常见的模型退化原因。用 PSI（Population Stability Index）或 KL 散度检测输入特征的分布变化。模型预测分布的偏移（Prediction Drift）也需要监控——即使你没有真实标签，预测分布的突然变化也是危险信号。

**核心工具：**

| 工具 | 定位 |
| --- | --- |
| Evidently AI | 开源数据/模型监控，可视化报告 |
| Whylogs / WhyLabs | 数据 profiling + 漂移检测 |
| Prometheus + Grafana | 基础设施监控 |
| Arize AI | 商业 ML 可观测平台 |
| Fiddler AI | 模型性能监控 + 可解释性 |

**2. 模型治理**

- 模型注册表（Model Registry）：所有模型的版本、谱系、状态（staging/production/archived）集中管理
- 模型血缘（Lineage）：从原始数据 → 特征 → 训练代码 → 模型 → 部署端点，全链路可追踪
- 审批流程：模型从 staging 到 production 需要评审和签批
- 公平性与偏见检测：确保模型不会在受保护属性（性别、种族、年龄）上产生歧视

**3. 持续训练（CT）**

传统 CI/CD 是代码变更触发构建。ML 系统还需要：

- **定时重训**：每天/每周用最新数据重新训练
- **漂移触发重训**：数据漂移超过阈值时自动触发
- **反馈闭环**：线上推理结果 → 人工标注 → 回流为新训练数据

这三者组成了 MLOps 的 **CT（Continuous Training）** 能力，是区别于 DevOps 的核心特征。

**4. Pipeline 编排**

端到端 ML Pipeline 需要编排工具来管理各环节的依赖和执行：

| 工具 | 特点 |
| --- | --- |
| Kubeflow Pipelines | Kubernetes 原生，大规模训练首选 |
| Apache Airflow | 通用工作流引擎，生态丰富 |
| Prefect | 现代 Python 工作流，开发体验好 |
| ZenML | ML Pipeline 专用框架，集成丰富 |
| Metaflow | Netflix 开源，专为数据科学设计 |

**验收标准**：能搭建一个完整的 ML Pipeline（数据采集 → 验证 → 训练 → 评估 → 部署 → 监控），在数据漂移时自动触发重训。

### 四、LLMOps：大模型时代的新 MLOps

2023 年之后，LLM 应用爆发式增长，催生了 LLMOps 这个新领域。它和传统 MLOps 有显著差异：

### LLMOps vs 传统 MLOps

| 维度 | 传统 MLOps | LLMOps |
| --- | --- | --- |
| 模型来源 | 自己训练 | 调用 API 或微调开源模型 |
| 核心工作 | 特征工程 + 模型训练 | Prompt 工程 + RAG + Agent 编排 |
| 评估方式 | 准确率/F1 等固定指标 | LLM-as-Judge + 人工评估 |
| 数据管理 | 特征仓库 | 向量数据库 + 知识库 |
| 成本结构 | GPU 训练成本 | Token 消耗成本（推理为主） |
| 监控重点 | 数据漂移 | 幻觉率、延迟、Token 成本、安全性 |

### LLMOps 核心工具链

**Prompt 管理与评估：**

- Langfuse：开源 LLM 工程平台，tracing + prompt 管理 + 评估
- promptfoo：开源 prompt 测试与评估
- Braintrust：Prompt playground + 评估

**RAG 系统：**

- LangChain / LlamaIndex：RAG 应用框架
- Chroma / Milvus / Pinecone / Weaviate：向量数据库
- Cohere Rerank / BGE Reranker：重排序模型

**LLM 推理服务：**

- vLLM：高性能 LLM 推理引擎
- Ollama：本地 LLM 部署
- LiteLLM：统一 LLM API 网关（100+ 模型提供商）

**Agent 框架：**

- LangGraph：基于图的 Agent 编排
- CrewAI：多 Agent 协作
- AutoGen：微软开源多 Agent 框架

**可观测性：**

- Langfuse / Langsmith：LLM 调用链追踪
- OpenLIT：基于 OpenTelemetry 的 GenAI 可观测性
- Portkey：AI 网关 + 可观测性

### LLMOps 学习建议

如果你已经有 MLOps 基础，从以下路径切入 LLMOps：

1. 用 LangChain 或 LlamaIndex 搭一个 RAG 应用
2. 用 Langfuse 做全链路追踪和 prompt 版本管理
3. 学习 LLM 评估方法（自动评估 + 人工评估）
4. 搭建 LLM 应用的 CI/CD：prompt 变更 → 自动评估 → 部署
5. 了解 LLM 微调（LoRA/QLoRA）和模型服务（vLLM/TGI）

### 六、职业路径

MLOps 工程师通常从以下方向转入：

- **ML 工程师 → MLOps**：有模型训练经验，补齐工程化能力
- **后端/DevOps → MLOps**：有部署运维经验，补齐 ML 知识
- **数据工程师 → MLOps**：有数据 Pipeline 经验，补齐模型服务化能力

三条路径各有优势，核心是补齐另一半的能力。

**岗位薪资参考（2025 年）：**

- 国内一线互联网：40-80 万/年（中高级）
- 海外（美国）：$150K-$250K/年
- 远程岗位：$120K-$200K/年

这个领域的需求增长很快，但合格候选人相对稀缺——因为它需要同时理解 ML 和工程化，这两个能力在传统培养路径中是分开的。

### 七、给不同背景的人的建议

**如果你是算法工程师 / 数据科学家：**

你的 ML 基础已经够了，重点补：Docker、K8s 基础、CI/CD、API 设计、系统监控。不需要成为运维专家，但要能和平台团队对话。

**如果你是后端 / DevOps 工程师：**

你的工程能力已经够了，重点补：ML 基础概念（训练/推理/评估/过拟合）、数据漂移原理、模型服务化的特殊需求（GPU 调度、批处理、模型加载）。推荐先跑通一个 sklearn/PyTorch 的端到端 pipeline 来建立直觉。

**如果你是学生 / 刚入行：**

按阶段一到阶段四的顺序走。别跳阶段——阶段一的基础看起来无聊但会让后面的学习快三倍。先求面到（每个环节都有概念），再求点到（在某个环节做深做透）。

---

### 八、一句话总结

MLOps 的本质是让机器学习从”能跑”变成”可靠地跑在生产环境中”。它不是一个工具，而是一套工程实践体系。学习路线的核心逻辑是：**先打好工程基本功 → 学会管理数据和实验 → 学会部署和服务化 → 学会监控和持续迭代**。别在工具选型上纠结太久——先用 MLflow + DVC + Docker 搭一个最小系统跑通，再根据实际需求替换。
