### 先说结论

LLM推理的弹性伸缩和传统微服务完全不同，不能直接用HPA。核心原因有三个：**GPU利用率指标不准、扩容时GPU资源不够、新实例就绪太慢（镜像+模型加载动辄几分钟）**。对应的解决方案是三件套：**Knative KPA（基于并发量的快速弹性）+ ResourcePolicy（异构GPU优先级调度与抢占）+ Fluid（模型本地缓存加速加载）**。三者协同，分别解决”怎么扩”、”扩了有没有资源”、”扩了能不能快速就绪”三个问题。

下面逐层拆解。

### 一、为什么传统HPA搞不定LLM推理弹性伸缩？

在讲方案之前，先搞清楚问题的本质。LLM推理服务和传统微服务在弹性伸缩上有三个本质差异：

### 差异一：弹性指标失效

传统HPA默认用CPU和内存作为伸缩指标，这对跑在CPU上的微服务没问题。但LLM推理跑在GPU上，问题来了：

- GPU利用率这个指标**无法准确反映实际负载**。GPU利用率高可能是在算，也可能是在等数据加载、等内存拷贝，看起来忙其实没在产出
- 即使有GPU exporter提供显存占用、SM利用率等指标，也往往不足以准确判断是否需要扩容
- LLM推理的负载特征是”请求级”的——一个请求占多少资源取决于输入输出长度，用资源利用率衡量很不准确

### 差异二：扩容资源无保障

GPU是稀缺资源。传统CPU服务扩容时，节点上通常还有富余CPU资源，新Pod能很快调度起来。但GPU不一样：

- 集群中GPU总量有限，高峰时可能所有卡都被占着
- 占着GPU的不一定是在线推理任务，可能是训练任务、离线推理任务
- 集群中通常有多种异构GPU（不同型号、不同显存、不同算力），K8s原生调度器不支持按GPU类型设置优先级和抢占

结果就是：需要扩容时，新Pod因为没有GPU资源一直Pending，扩容等于没扩。

### 差异三：就绪时间太长

这是最致命的差异。传统微服务扩容，新实例几秒到几十秒就能就绪。LLM推理服务呢？

| 环节 | 耗时原因 | 典型耗时 |
| --- | --- | --- |
| 拉取镜像 | 推理镜像通常5GB+ | 几十秒到几分钟 |
| 加载模型 | 7B模型约15GB，从网络存储读到GPU显存 | 几十秒到几分钟 |
| 初始化 | 推理引擎初始化、显存分配 | 几秒到几十秒 |
| 总计 |  | 几分钟量级 |

等新实例就绪，流量高峰早就过去了，用户请求也超时了。这就是LLM推理弹性伸缩的核心痛点。

### 二、LLM推理弹性伸缩的三个前提

要实现LLM推理的自动弹性伸缩，必须同时满足三个前提，缺一不可：

### 前提一：科学合理的自动化弹性扩容机制

需要找到适合LLM推理的弹性指标和伸缩机制。K8s原生的两种机制都有短板：

| 机制 | 原理 | 优点 | 缺点 |
| --- | --- | --- | --- |
| HPA | 基于CPU/内存指标自动扩缩 | 简单通用 | 弹性滞后、不支持GPU指标、突发流量响应慢 |
| CronHPA | 按时间定时扩缩 | 可预测、稳定 | 需要明确周期性、手动调策略、无法应对突发 |

针对LLM推理，**并发量（concurrency）**是比GPU利用率更合适的指标——它直接反映当前有多少请求在处理，和推理服务的负载高度相关。同时需要支持突发流量的快速扩容机制。

### 前提二：扩容时刻的计算资源保障

在固定GPU节点的情况下，通过工作负载的弹性伸缩和资源抢占来最大化资源利用率：

- 扩容时通过**抢占低优先级任务**（训练、离线推理）来释放GPU资源
- 支持**异构GPU优先级配置**，高优推理优先用高性能卡
- 这种按优先级调度和抢占的能力，K8s原生调度器不支持，需要自定义扩展

### 前提三：扩容过程对用户体验SLA的保障

核心是缩短新实例的就绪时间。镜像和模型太大是根本原因，需要通过**数据加速**手段让模型加载更快，同时通过**流量缓存**机制在新实例就绪前暂存请求，避免丢失。

### 三、整体架构设计：三件套协同

针对三个前提，整体方案由三个核心组件协同：

```text
┌──────────────────────────────────────────────────────┐
│                   LLM推理弹性伸缩架构                    │
├────────────────┬────────────────┬────────────────────┤
│   弹性伸缩层     │   资源调度层     │     数据加速层       │
│                │                │                    │
│  Knative KPA   │ ResourcePolicy │      Fluid         │
│                │                │                    │
│ · 并发量指标     │ · GPU优先级排序  │ · 弹性数据集抽象     │
│ · Panic快速扩容 │ · 高优抢占低优   │ · 分层本地缓存       │
│ · 流量缓存      │ · 逆序缩容释放   │ · 亲和性调度        │
│ · 缩容至0      │ · CRD定义策略    │ · 缓存集群自动弹性   │
├────────────────┴────────────────┴────────────────────┤
│              K8s 调度器 + 容器运行时                    │
└──────────────────────────────────────────────────────┘
```

三个组件的对应关系：

- **Knative KPA** → 解决前提一（科学合理的扩容机制）
- **ResourcePolicy** → 解决前提二（扩容时刻的资源保障）
- **Fluid** → 解决前提三（扩容过程的SLA保障）

下面逐个深度解析。

### 四、组件一：Knative KPA——基于并发量的弹性伸缩

### 4.1 为什么是并发量而不是GPU利用率？

GPU利用率的问题前面已经讲过，它无法准确反映推理服务的实际负载。而**并发量（concurrency）**直接统计当前正在处理的请求数，和推理服务的处理能力直接挂钩：

- 并发量低 → 服务空闲，可以缩容
- 并发量达到阈值 → 需要扩容
- 并发量突然飙升 → 触发快速扩容

这个指标对LLM推理特别合适，因为推理服务的处理能力本质上就是”同时能处理多少个请求”。

### 4.2 Knative KPA的核心机制

Knative的KPA（Knative Pod Autoscaler）相比传统HPA有几个关键优势：

**1. Panic模式快速扩容**

- 正常模式下，KPA根据并发量趋势平滑扩容
- 当并发量突然飙升（超过Panic阈值），立即进入Panic模式，**立即扩容**而不是等下一个评估周期
- 这对LLM推理的流量突发场景至关重要

**2. Activator + Queue-proxy流量缓存**

- 当实例数为0或新实例未就绪时，**Activator**组件会缓存进来的请求
- 新实例就绪后，Activator将缓存的请求转发过去，**避免请求丢失**
- **Queue-proxy**在每个Pod前代理流量，统计并发量，同时实现请求排队和限流

这套机制解决了”新实例还没起来，请求就丢了”的问题。

**3. 缩容至0**

- 没有流量时，可以自动缩容到0个实例，彻底释放GPU资源
- 这对GPU这种昂贵资源来说意义重大——低谷时不占卡，高峰时快速拉起

### 4.3 Knative vs HPA 对比

| 对比维度 | K8s HPA | Knative KPA |
| --- | --- | --- |
| 弹性指标 | CPU/内存（可自定义） | 并发量（concurrency） |
| 突发响应 | 滞后（等评估周期） | Panic模式立即扩容 |
| 流量缓存 | 无（请求直接失败或排队） | Activator缓存请求 |
| 缩容至0 | 不支持（最少1个） | 支持 |
| GPU场景适配 | 差（指标不准） | 好（并发量天然适合） |

### 五、组件二：ResourcePolicy——异构GPU优先级调度与抢占

### 5.1 解决什么问题？

K8s原生调度器在GPU场景下有两个不足：

1. 不支持按GPU型号设置调度优先级——A100和T4在调度器眼里只是不同的资源，无法定义”优先用A100”
2. 不支持基于业务优先级的GPU抢占——在线推理和训练任务抢GPU时，无法自动让训练任务让出资源

ResourcePolicy就是为了解决这两个问题。

### 5.2 核心功能

**排序（Priority Ordering）**

- 定义GPU类型的优先级顺序，比如 A100 > V100 > T4
- 调度推理任务时，优先分配高优先级GPU
- 保证高优推理任务获得最好的推理性能

**抢占（Preemption）**

- 高优先级推理任务可以抢占低优先级任务（训练、离线推理）的GPU
- 被抢占的任务被驱逐，资源让给推理任务
- 这是扩容时刻资源保障的核心机制

**回收缩容（Reverse Scale-in）**

- 缩容时按逆序释放Pod——先释放低优先级GPU上的实例
- 保留高优先级GPU上的实例，保证剩余实例的性能

### 5.3 典型场景

| 时段 | 资源状态 | ResourcePolicy行为 |
| --- | --- | --- |
| 高峰 | GPU资源紧张 | 优先用高性能GPU，不够时抢占训练任务的GPU |
| 平峰 | GPU资源够用 | 按优先级分配，高优任务用好卡 |
| 低谷 | 推理流量小 | 推理缩容，释放GPU给训练和离线任务 |

### 5.4 实现方式

基于K8s调度器扩展，通过**ResourcePolicy CRD**（自定义资源定义）来描述优先级策略：

```yaml
apiVersion: scheduling.example.com/v1
kind: ResourcePolicy
metadata:
  name: llm-inference-policy
spec:
  priorityOrder:
    - gpuType: A100
      priority: 100
    - gpuType: V100
      priority: 80
    - gpuType: T4
      priority: 60
  preemption:
    enabled: true
    lowPriorityWorkloads:
      - training
      - offline-inference
  scaleInOrder: reverse
```

调度器在调度Pod时读取ResourcePolicy，按策略进行排序和抢占决策。

### 六、组件三：Fluid——模型数据加速加载

### 6.1 问题本质

LLM推理新实例就绪慢的最大瓶颈是**模型加载**。模型文件存在网络存储（如NAS、对象存储）上，并发加载时：

- 网络存储延迟高、带宽有限
- 多个实例同时拉模型，互相抢带宽，更慢
- 15GB的模型从网络存储读到GPU显存，可能要几分钟

### 6.2 Fluid的核心思路

Fluid是一个开源的数据集编排和缓存加速框架，它的核心思路是**把模型数据缓存到计算节点本地，让Pod调度到有缓存的节点上**。

**弹性数据集（Dataset）抽象**

- 把模型文件抽象为K8s中的Dataset资源
- 统一管理数据集的缓存、生命周期、访问权限

**分层本地性缓存 + 亲和性调度**

- 将模型缓存到节点本地（内存或SSD）
- 调度Pod时，优先调度到已经有该模型缓存的节点
- 新实例启动时直接从本地缓存读模型，而不是从远端网络存储拉

**缓存集群自动弹性**

- 缓存节点可以根据负载自动扩缩容
- 高并发时增加缓存节点，保证IO吞吐
- 减轻中央存储的压力

### 6.3 加速手段

**数据分流（Data Offloading）**

- 热数据（常用模型）缓存到本地，冷数据留在中央存储
- 大部分请求命中本地缓存，减少对中央存储的访问

**弹性IO吞吐（Autoscaling Cache）**

- 根据并发加载需求自动调整缓存集群规模
- 保证多个实例同时加载模型时的IO带宽

### 6.4 效果

通过Fluid加速，模型加载时间可以从”几分钟”缩短到”几十秒甚至几秒”，新实例就绪时间大幅降低，SLA得到保障。

### 七、落地实践流程

完整的落地步骤：

1. **环境准备**：K8s集群，安装Knative Serving、Fluid、自定义调度器
2. **准备模型数据**：模型上传到共享存储，创建Fluid Dataset和缓存配置
3. **Fluid加速验证**：测试模型加载速度，确认缓存命中率和加载时间
4. **ResourcePolicy配置**：定义GPU优先级、抢占规则、缩容顺序
5. **KPA弹性配置**：设置并发量目标、Panic阈值、最小/最大副本、缩容至0策略
6. **资源降配配置**：低谷时自动缩容，资源释放给低优先级任务
7. **性能测试**：模拟流量突发，验证扩容延迟、SLA达标率、资源利用率

### 八、常见误区

**误区一：用GPU利用率做弹性指标就够了。** 错。GPU利用率无法准确反映推理负载，并发量更合适。GPU利用率高可能是在等数据，不是在算。

**误区二：扩容慢是因为K8s调度慢。** 不完全是。调度本身很快，慢在拉镜像和加载模型。Fluid解决模型加载，镜像可以用预拉取或P2P分发加速。

**误区三：GPU不够就加机器。** 不一定。很多时候GPU被低优先级任务占着，通过ResourcePolicy抢占机制可以释放资源，提高整体利用率。

**误区四：Knative只能用于无状态服务。** 不完全对。Knative本身管理无状态Pod，但LLM推理服务可以做成无状态的（模型从Fluid缓存加载，请求无状态），完全可以用Knative管理。

**误区五：Fluid只是个缓存工具。** 不止。Fluid提供数据集抽象、缓存编排、亲和性调度、弹性缓存等完整能力，是K8s原生的数据编排框架。

### 九、总结

LLM推理场景的弹性伸缩是一个系统工程，不是换个指标就能解决的。需要从三个层面协同设计：

- **弹性伸缩层（Knative KPA）**：用并发量替代GPU利用率作为指标，Panic模式应对突发，Activator缓存请求保障SLA，缩容至0节省GPU资源
- **资源调度层（ResourcePolicy）**：异构GPU优先级排序，高优推理抢占低优任务资源，解决扩容时GPU不足的问题
- **数据加速层（Fluid）**：模型本地缓存+亲和性调度，大幅缩短新实例就绪时间

三个组件分别对应”怎么扩”、”扩了有没有资源”、”扩了能不能快速就绪”三个核心问题，协同实现LLM推理场景的高效弹性伸缩。

对于正在做LLM推理服务落地的团队，这套架构提供了一个完整的参考思路。弹性伸缩的本质不是”自动加机器”，而是”在正确的时间、用正确的资源、以正确的速度响应负载变化”。
