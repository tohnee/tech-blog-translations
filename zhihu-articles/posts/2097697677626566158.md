## RAG 系统七大优化模块详解：从问题理解到知识库闭环

## 1. 从朴素 RAG 到工程可用的 RAG

朴素 RAG 流程只有两步：把用户问题向量化，去知识库里捞几段文本，塞进 Prompt 让大模型生成答案。这套流程在 Demo 里够用，但一到真实业务就暴露出四个层面的缺陷—— **问题层面** 、 **检索层面** 、 **排序层面** 和 **反馈层面** ：

| 层面 | 暴露的问题 | 典型症状 |
| --- | --- | --- |
| 问题层面 | 用户问题口语化、模糊、复合 | “那个新出的手表咋样”检索不到新品文档 |
| 检索层面 | 单一检索方式各有盲区 | 向量检索漏掉产品型号等专有词 |
| 排序层面 | 召回的文档相关度参差不齐 | 最相关文档排在候选集末尾，被上下文淹没 |
| 反馈层面 | 系统回答错了没有修正通道 | 同一个问题反复答错 |

工业界的解法是把 RAG 从”两步流水线”扩展成一条 **带智能判断的多级流水线** ：在检索前加入问题理解与查询优化，在检索时引入混合策略，在检索后做上下文扩展与重排序，在生成前设置追问兜底，在生成后建立反馈闭环。这七个模块串成一条完整链路：

![](https://pic1.zhimg.com/v2-192d1537e8cfff0372233c98b5413932_1440w.jpg)

看图重点在三条路径： **蓝色** 是检索前的”问题加工”（模块 1～3）， **绿色** 是检索后的”结果加工”（模块 4～5）， **紫色** 是生成环节的兜底与闭环（模块 6～7），红色菱形是重排序分数触发的分叉点——它决定了系统是”直接回答”还是”反问用户”。

后续章节按这条流水线的顺序逐个拆解每个模块：它解决什么问题、原理是什么、面试怎么答。

## 2. 问题复杂度判断：流水线的第一道分诊台

上一节的流程图里，用户问题进入系统后的第一个节点不是检索，而是一个判断分支——这一节解释为什么要先”分诊”。

### 2.1 为什么不能所有问题都直接检索

用户的问题分两种形态。 **简单问题** 只有一个明确的查询意图，例如”RAG 里的重排序模型是什么”——一次向量检索就能覆盖答案。 **复杂问题** 则包含多个方面，或者答案无法被一次查询覆盖，典型如多跳问题（multi-hop）：”Transformer 论文的第一作者现在在哪个机构工作”——先得查清第一作者是谁，再查该作者的机构，任何一次单独检索都拿不到完整答案。

如果对复杂问题不做拆解直接检索，会发生两件事：一是查询向量被多个意图”平均”，导致检索结果每个方面都沾一点但都不深入；二是召回的文档片段只覆盖答案的一半，模型只能靠幻觉补齐另一半。

### 2.2 判断标准与处理逻辑

判断逻辑本身很直接，核心是识别问题包含的意图数量：

- **复杂问题** ：包含多个方面，或一次查询无法覆盖答案 → 拆解成多个子问题，每个子问题独立走一遍”检索 → 排序”，最后汇总各子问题的证据再生成；
- **简单问题** ：单一明确的查询需求 → 跳过拆解，直接进入查询优化与检索。

值得强调的是，这一思想在学术上有对应的演进：DMQR-RAG（arXiv:2411.13154）指出”哪些论文引用更多——Transformer 还是 ResNet”这类多意图查询必须多次检索才能回答，并证明把多种改写策略组合起来动态选择，比固定单一改写效果好；RQ-RAG（arXiv:2404.00610）则训练模型自己学会”分解、消歧、改写”三种操作。面试中能说出”拆解的粒度以一次向量检索可覆盖为界”就是加分点。

**拆解效果的量化直觉** 可以用向量运算说明。设复杂问题”iPhone 15 Pro 的价格和芯片型号”的嵌入向量为 $q$，”价格”与”芯片”两个意图的嵌入方向为 $e_1, e_2$，则 $q$ 近似落在 $e_1$ 与 $e_2$ 张成的”中间地带”：

$$
q \approx \alpha \, e_1 + \beta \, e_2, \quad \cos(q, e_1) < 1, \; \cos(q, e_2) < 1
$$

两个子意图的相似度都被”摊薄”了——查询向量指向两个意图连线的中间，与任何单一意图都不够贴近。拆解成”iPhone 15 Pro 价格”“iPhone 15 Pro 芯片”两条子查询后，每条子查询都能与对应文档的嵌入充分对齐。这就是”复合问题检索命中率低”的数学根源，也是拆解模块存在的第一性理由。

判断完成后，无论走哪条分支，问题都会到达同一个下一站——查询优化。因为即使不拆解，简单问题的原始表述也往往不适合直接检索，这是下一节的主题。

## 3. 查询优化：把”人话”翻译成”检索语言”

用户的原始提问是说给人听的，不是写给检索器看的。查询优化模块的任务，是把原始问题转化为更适合检索的表达形式。三种策略各有分工，可以叠加使用。

### 3.1 查询改写：消除口语噪声

查询改写（Query Rewriting）把口语化、有省略、有错别字的问题转成专业术语表达。例如把”那个包咋样，贵不贵”改写成”该款包的用户评价与价格区间”。改写的价值来自一个事实： **查询与文档之间存在词汇鸿沟** ——用户嘴里的词和知识库文档里的词往往不一样，直接用原始查询做向量检索，查询向量的方向会被口语噪声带偏。

实现上通常用一个 LLM 调用完成，Prompt 的核心指令是”去除噪声、提炼意图、改写为适合检索的完整陈述句”。DMQR-RAG 论文中的”一般查询改写”（GQR）与”关键词改写”（KWR）分别对应”整句提炼”和”抽取名词主题词”两种粒度；论文同时给出了一个重要提醒——某些场景下改写反而不如原始查询（改写丢失了上下文），所以工程上常把 **原始查询与改写查询一起送进检索** 。

### 3.2 假设文档生成（HyDE）：用”假答案”搜真答案

假设文档生成即 HyDE（Hypothetical Document Embeddings，Gao et al., 2023， [arXiv:2212.10496](https://arxiv.org/abs/2212.10496) ），是查询优化里最反直觉也最常被考到的策略。它让模型根据问题先生成一篇”假设性答案文档”，再把这篇假文档与原始问题拼接后一起去查询。

为什么”假答案”能搜到”真文档”？关键在于 **向量空间中的相似度不对称** ：

$$
\text{sim}(q, d) \ll \text{sim}(\hat{d}, d)
$$

其中 $q$ 是用户问题，$\hat{d}$ 是 LLM 生成的假设文档，$d$ 是知识库中的真实文档。问题和答案在语义空间里是两种不同的文体——问题短、答案长，两者的嵌入向量距离天然偏远；而假设文档虽然细节可能全是编造的，但它的 **文体、术语分布、篇章结构与真实答案文档高度一致** ，即”相关性模式”是对的。HyDE 的做法相当于把检索任务从”问题—文档相似度”转换成了”文档—文档相似度”，后者的匹配质量远高于前者。论文在 TREC DL-19⁄20 与 BEIR 上的实验显示，零样本的 HyDE（DL-20 上 nDCG@10 达 61.3）甚至可以接近或超过经过微调的双编码器检索器（同基准上 Contriever 为 44.5）。

代价也很明确：多一次 LLM 生成调用，增加延迟与成本；如果假设文档在关键事实方向上生成偏了，检索也会跟着偏——所以工程上常生成多篇假设文档取嵌入平均（Haystack 的实现默认采样 5 篇），并对 HyDE 的输出做缓存。

**一个可运行的量化实验** ：构造”口语化查询 + 正规文档”的词汇鸿沟场景，手工写一篇假设答案模拟 LLM 的 HyDE 输出，对比三者对同一批答案文档的相似度分数（用 TF-IDF 嵌入模拟语义检索，可复制运行，依赖 `pip install scikit-learn jieba numpy` ）：

```python
# -*- coding: utf-8 -*-
"""查询改写 / HyDE / 多查询生成 三策略效果对比实验。

依赖：pip install scikit-learn jieba numpy
运行：python query_opt.py（jieba 首次运行会构建词典缓存）
"""
import numpy as np, jieba
from sklearn.feature_extraction.text import TfidfVectorizer

docs = [  # 知识库:正规书面表达
    "退货政策：自签收之日起7天内可申请退货，需保持商品完好。",
    "退款时效说明：退货审核通过后，退款将在7个工作日内原路退回。",
    "换货流程：质量问题免费换货，非质量问题需支付往返运费。",
    "会员权益：PLUS会员享专属折扣与免运费券。",
    "价保规则：下单后15天内降价可申请差价补偿。",
]
q_raw = "东西买了不想要了 钱什么时候回来"          # 口语原始查询
q_rw  = "退货政策 退款时效 几个工作日到账"         # 改写后
q_multi = ["退货政策 几天内", "退款时效 工作日", "退款 原路退回"]  # 多查询变体
hypothetic = ("您购买的商品自签收之日起7天内可以申请退货，退货审核通过后"
              "退款将在7个工作日内原路退回到您的支付账户。")   # HyDE 假设答案(模拟LLM生成)

def retrieve(q, topk=5):
    """TF-IDF 余弦相似度检索,返回 (排序, 分数)。真实系统换语义嵌入模型。"""
    vec = TfidfVectorizer(tokenizer=list, token_pattern=None).fit(docs)
    V = vec.transform(docs).toarray()
    vq = vec.transform([q]).toarray()[0]
    vq /= (np.linalg.norm(vq) + 1e-9)
    V = V / (np.linalg.norm(V, axis=1, keepdims=True) + 1e-9)
    s = V @ vq                                  # 余弦相似度
    return list(np.argsort(-s)[:topk]), np.round(s, 3)

def rrf(rank_lists, kp=60):
    """RRF 融合多个排序列表(正文 4.2 公式的实现)。"""
    sc = {}
    for rl in rank_lists:
        for rank, d in enumerate(rl, 1):
            sc[d] = sc.get(d, 0) + 1/(kp+rank)
    return sorted(sc.items(), key=lambda x: -x[1])

r0, s0 = retrieve(q_raw)                        # 基线:原始查询
r1, s1 = retrieve(q_rw)                         # 改写
lists = [retrieve(qm)[0] for qm in q_multi]     # 多查询
rh, sh = retrieve(hypothetic)                   # HyDE
print("原始查询  对答案文档 d0/d1 分数:", s0[0], s0[1])
print("改写查询  对答案文档 d0/d1 分数:", s1[0], s1[1])
print("HyDE假答 对答案文档 d0/d1 分数:", sh[0], sh[1])
print("多查询RRF融合:", [(docs[d][:12], round(v,4)) for d, v in rrf(lists)])
```

真实运行输出：

```text
原始查询  对答案文档 d0/d1 分数: 0.0 0.242
改写查询  对答案文档 d0/d1 分数: 0.375 0.665
HyDE假答 对答案文档 d0/d1 分数: 0.646 0.767
多查询RRF融合: [('退款时效说明：退货审核通过后，退', 0.0489), ('退货政策：自签收之日起7天内可申', 0.0487)]
```

逐行走查这份输出（d0 是退货政策文档，d1 是退款时效文档——它们才是这个问题的真正答案）：

- **原始口语查询** ：”东西”“钱”“回来”与文档中”商品”“退款”“退回”零共现，d0 的相似度直接归零（0.0），d1 仅 0.242——词汇鸿沟的代价是 **答案文档可能根本进不了候选集** ；
- **改写后** ：专业术语与文档用词对齐，d0 升到 0.375、d1 升到 0.665，翻了数倍；
- **HyDE 假设答案** ：因为它是”答案文体”，与两篇答案文档的相似度同时冲到 0.646 与 0.767， **双双超过改写查询** ——这正是 $\text{sim}(q,d) \ll \text{sim}(\hat{d},d)$ 的直接数值证据，也是 HyDE 相比单纯改写更强的地方（它同时恢复了”用词”和”文体”两个维度的对齐）；
- **多查询 + RRF** ：三个变体各自命中 d0/d1 的 Top-2，RRF 融合后两篇文档分数几乎并列（0.0489 与 0.0487），说明 **多路查询把答案完整地”夹”了出来** 。

### 3.3 多查询生成：从不同角度把意图问全

多查询生成（Multi-Query / RAG-Fusion）让模型从同一问题生成多个查询变体，每个变体从不同角度覆盖问题的一个侧面。例如原始问题”Redis 扩容怎么做”可以生成三个变体：”Redis 集群架构”“Redis 水平扩容策略”“Redis 性能瓶颈”。每个变体独立检索，结果合并去重后再进入排序。

它的本质是 **用查询的多样性换召回的多样性** ：单次检索只能覆盖查询向量附近的一片区域，多个变体相当于在语义空间里撒网。RAG-Fusion 版本进一步用倒数排名融合（RRF，Cormack et al., 2009, [SIGIR 论文](https://plg.uwaterloo.ca/~gvcormac/cormacksigir09-rrf.pdf) ）代替简单去重合并，利用排名位置融合多个结果列表，避免不同检索器分数不可比的问题。DMQR-RAG 的消融实验还验证了一个细节：把 **原始查询也保留在变体池里** ，比只用改写查询效果更好。

三种策略的定位对比：

| 策略 | 核心动作 | 解决的问题 | 主要代价 |
| --- | --- | --- | --- |
| 查询改写 | 口语 → 专业表述 | 词汇鸿沟、噪声 | 改写可能丢失上下文 |
| HyDE | 先生成假设文档再检索 | 问题-答案文体不对称 | 增加一次生成调用，可能带偏方向 |
| 多查询生成 | 生成多个查询变体 | 单查询覆盖面不足 | 检索次数翻倍，需结果融合 |

查询表达优化到位后，检索这一环仍然存在结构性盲区——这引出了下一个模块。

## 4. 混合检索：语义与关键词的双保险

### 4.1 两种检索方式的互补性

向量检索和 BM25 检索的失败模式几乎是互补的：

| 检索类型 | 原理 | 优势 | 盲区 |
| --- | --- | --- | --- |
| 向量检索 | 语义相似度匹配 | 理解同义词和语义关系，”退货政策”能匹配”退款规则” | 对产品型号、错误码、专有名词等精确 token 不敏感 |
| BM25 检索 | 关键词精确匹配 | 捕获专业术语和特定词汇，型号、缩写、代码一查一个准 | 不理解语义，换个说法就搜不到 |

向量检索基于稠密嵌入（dense embedding）做近邻搜索，擅长”意思相近”；BM25 是基于词频的稀疏检索算法（Okapi BM25），对查询与文档的共现词打分，擅长”字面一致”。企业知识库里大量存在”半结构化的精确需求”——查”iPhone 15 Pro”这种词，向量检索可能因为词没有语义权重而召回一堆讲 iPhone 的泛泛文档，BM25 则精准命中。

用一个真实打分演算把 BM25 的公式（见附录 B）落到具体数字上。设语料 6 篇文档，查询”iPhone 15 Pro 多少钱”，考察文档 d0（”iPhone 15 Pro 配备 A17 Pro 芯片”）。分词后查询词为 {iPhone, 15, Pro, 多少钱}，其中”Pro”在 d0 出现 2 次、在 6 篇文档中出现在 3 篇里。取 $k_1 = 1.5$、$b = 0.75$、文档长度与语料均值相等（长度归一项为 1）：

$$
\text{IDF}(\text{Pro}) \approx \ln\frac{6 - 3 + 0.5}{3 + 0.5} = \ln\frac{3.5}{3.5} = 0
$$

有意思——”Pro”在超过一半文档中出现，IDF 为 0，这个词对排序 **毫无贡献** ；而”iPhone”只出现在 2 篇文档中，$\text{IDF} \approx \ln\frac{4.5}{2.5} \approx 0.588$，加上 2 次词频的饱和项 $\frac{2 \times 2.5}{2 + 1.5} \approx 1.43$，才是 d0 得分的主力。这个演算揭示了 BM25 的排序哲学： **决定分数的不是词出现多少次，而是这个词有多稀有** ——这正是它对产品型号、错误码等专有词敏感的公式级解释。

### 4.2 融合参数与候选集

混合检索的工程设定：每种方法各检索 $k=3$ 个文档，两边结果 **合并后去重** ，通常得到 3～6 个候选文档。去重之所以必要，是因为一份文档可能同时被两种方式召回——而这恰恰是高质量文档的信号。

合并时的经典难题是 **分数不可比** ：BM25 分数是无界的（可以是 18.3），余弦相似度有界于 0～1，直接相加毫无意义。标准解法是 RRF（Reciprocal Rank Fusion），它完全抛弃原始分数、只看排名：

$$
\text{RRF}(d) = \sum_{r \in R} \frac{1}{k' + \text{rank}_r(d)}
$$

其中 $R$ 是检索器集合，$\text{rank}_r(d)$ 是文档 $d$ 在检索器 $r$ 结果列表中的排名（从 1 起），$k'$ 是平滑常数（论文默认 60，作用是压制第一名与第二名之间的分数差距、避免头部排名垄断权重）。做一个数值演算：设 $k'=60$，文档 B 在 BM25 排第 3、在向量检索也排第 3，则

$$
\text{RRF}(B) = \frac{1}{60+3} + \frac{1}{60+3} = \frac{1}{63} + \frac{1}{63} \approx 0.0317
$$

对比一个”两边排名悬殊”的文档 A（BM25 第 1、向量第 50）：

$$
\text{RRF}(A) = \frac{1}{61} + \frac{1}{110} \approx 0.0164 + 0.0091 = 0.0255
$$

B 的分数高于 A—— **两边一致认可的文档胜过单边状元** ，这正是混合检索想要的选择逻辑。RRF 无需分数归一化、零参数训练、对任意检索器即插即用，是 Elasticsearch、Weaviate 等引擎内置的默认融合方案。

$k'$ 的取值并非无关紧要，用一个真实实验看它如何改变融合结果（同一份语料、同一次双路检索，只改 $k'$）：

```text
BM25 分数:   [5.014  0.     2.252  1.311  3.710  0.   ]   → Top3 = [d0, d4, d2]
向量分数:    [0.835  0.     0.346  0.205  0.653  0.   ]   → Top3 = [d0, d4, d2]
k'=0   融合Top3: d0(2.0)   d4(1.0)   d2(0.667)
k'=1   融合Top3: d0(1.0)   d4(0.667) d2(0.5)
k'=60  融合Top3: d0(0.0328) d4(0.0323) d2(0.0317)
```

走查：$k' = 0$ 时 d0（双路第 1 名）得分 2.0，是 d4 的两倍——头部垄断严重；$k' = 60$ 时 d0 与 d4 的分差缩小到 1.5%—— **大 $k'$ 让”排名差异”被抹平、让”是否被多路认可”主导排序** 。当两路检索器的质量不对称时（比如 BM25 明显更准），小 $k'$ 能保住强路的头部信号；两路质量相近时，大 $k'$ 更稳。这也解释了 RRF 论文默认 60 的定位：一个”多数场景下安全”的折中值。

### 4.3 代码实现：一个可运行的混合检索器

下面是一个自包含的最小实现，覆盖 BM25 + 向量检索 + RRF 融合全流程，复制即可运行（依赖 `rank-bm25` 、 `numpy` ，可用 `pip install rank-bm25 numpy jieba` 安装）：

```python
# -*- coding: utf-8 -*-
"""混合检索最小实现：BM25 + 向量检索 + RRF 融合。

依赖：pip install rank-bm25 numpy jieba
运行：python hybrid_retrieval.py
"""
import numpy as np
import jieba
from rank_bm25 import BM25Okapi

# ── 阶段 1：构造语料与 BM25 索引 ──────────────────────────────
# 对应正文 4.1：BM25 基于词共现打分，需要先分词建立倒排式词表
docs = [
    "iPhone 15 Pro 配备 A17 Pro 芯片，支持 USB-C 接口",          # d0：精确型号
    "苹果新款手机搭载了钛金属边框，重量更轻",                      # d1：同义改写
    "华为 Mate 60 使用麒麟 9000S 处理器",                        # d2：另一品牌
    "Apple 的旗舰机型主打性能与影像能力",                         # d3：泛化描述
]
tokenized = [list(jieba.cut(d)) for d in docs]   # 中文需分词，英文按空格切即可
bm25 = BM25Okapi(tokenized)

# ── 阶段 2：构造向量检索（用词频 TF-IDF 模拟嵌入向量，演示逻辑用）──
# 真实系统中此处替换为 sentence-transformers 等 embedding 模型的 encode()
vocab = sorted({w for toks in tokenized for w in toks})
w2i = {w: i for i, w in enumerate(vocab)}
def tf_vec(text: str) -> np.ndarray:
    v = np.zeros(len(vocab))
    for w in jieba.cut(text):          # 词频向量：词在语料中出现则对应维度加 1
        if w in w2i:
            v[w2i[w]] += 1.0
    norm = np.linalg.norm(v)           # L2 归一化，使点积等价于余弦相似度
    return v / norm if norm > 0 else v
doc_vecs = np.stack([tf_vec(d) for d in docs])

def vector_search(query: str, k: int) -> list[int]:
    """向量检索：返回相似度最高的 k 个文档下标。"""
    sims = doc_vecs @ tf_vec(query)    # 归一化后的点积 = 余弦相似度
    return list(np.argsort(-sims)[:k]) # 降序取前 k

def bm25_search(query: str, k: int) -> list[int]:
    """BM25 检索：返回得分最高的 k 个文档下标。"""
    return list(np.argsort(-bm25.get_scores(list(jieba.cut(query)))[:len(docs)])[:k])

# ── 阶段 3：RRF 融合 ─────────────────────────────────────────
# 对应正文 4.2 公式：RRF(d) = Σ 1/(k' + rank_r(d))，k' 平滑常数取 60
def rrf_fuse(rank_lists: list[list[int]], k_prime: int = 60) -> list[int]:
    scores: dict[int, float] = {}
    for ranking in rank_lists:
        for rank, doc_id in enumerate(ranking, start=1):  # rank 从 1 起
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k_prime + rank)
    return [d for d, _ in sorted(scores.items(), key=lambda x: -x[1])]

if __name__ == "__main__":
    query = "iPhone 15 Pro 用什么芯片"     # 含精确型号 → 考验 BM25；语义改写 → 考验向量
    K = 3                                  # 对应正文：每种方法各检索 k=3 个文档
    v_rank = vector_search(query, K)
    b_rank = bm25_search(query, K)
    fused = rrf_fuse([v_rank, b_rank])
    print("向量检索 Top3:", [docs[i] for i in v_rank])
    print("BM25  检索 Top3:", [docs[i] for i in b_rank])
    print("RRF 融合后:", [docs[i] for i in fused])
    print("候选文档数（合并去重后）:", len(set(v_rank) | set(b_rank)))
```

真实运行输出（顺序可能因分词版本略有差异）：

```text
向量检索 Top3: ['Apple 的旗舰机型主打性能与影像能力', 'iPhone 15 Pro 配备 A17 Pro 芯片，支持 USB-C 接口', '苹果新款手机搭载了钛金属边框，重量更轻']
BM25  检索 Top3: ['iPhone 15 Pro 配备 A17 Pro 芯片，支持 USB-C 接口', '华为 Mate 60 使用麒麟 9000S 处理器', 'Apple 的旗舰机型主打性能与影像能力']
RRF 融合后: ['iPhone 15 Pro 配备 A17 Pro 芯片，支持 USB-C 接口', 'Apple 的旗舰机型主打性能与影像能力', '华为 Mate 60 使用麒麟 9000S 处理器', '苹果新款手机搭载了钛金属边框，重量更轻']
```

走查一下这个结果：查询里的”iPhone 15 Pro”“芯片”是精确 token，BM25 把 d0 直接推到第 1；向量检索因为 d3 的”旗舰机型”与”iPhone 15 Pro”语义相近，把 d3 排到了前面。 **两条排名融合后，d0 同时被两边认可而登顶** ——这正是混合检索比任何单路检索都稳的原因。注意一个细节：真实场景中向量检索应换成真正的语义嵌入模型（如 `text2vec` 、 `bge-large-zh` ），此处用 TF-IDF 向量仅为让代码零 GPU 可运行，融合逻辑完全一致。

检索结果合并后得到了候选集，但候选文档还有一个隐藏问题——它们是按”块”存储的，块与块之间被切开了。下一节解决块切分带来的信息割裂。

## 5. 上下文扩展：把被切开的知识缝回去

文档入库前会经过分块（chunking），通常按 200～500 token 切成独立向量。分块是向量检索的前提——嵌入模型对长文本的表征质量会衰减，检索粒度也必须控制在段级才能精准命中。但分块有一个副作用： **语义连贯的原文被硬切成孤立小块，单个块可能信息不完整** 。

### 5.1 为什么需要前后块

一个典型场景：知识库中”退货政策”被切成三个块——(a) 适用范围、(b) 退货流程、© 退款时效。用户问”退货后钱几天到账”，检索命中了 (b)（因为”退货”一词共现），但”钱几天到账”的答案实际在 © 里。只返回 (b)，模型拿到的证据缺了关键半句。

上下文扩展（Context Expansion / Sentence-Window Retrieval）的做法是： **不仅返回匹配的文档块，还包含其前后相邻的文档块** 。三者作用分别是：

- 前后文档提供更完整的上下文，把命中块的”半截话”接全；
- 缓解因分块导致的信息割裂，让喂给 LLM 的证据恢复成连贯段落；
- 对”答案跨块”的多跳内容尤其有效——相邻块往往承接同一话题。

用一个真实分块语料走一遍这个机制（命中逻辑用词共现模拟检索打分）：

```text
文档按句切块入库,共 7 块:
  chunk0: 退货政策适用范围。
  chunk1: 自签收之日起7天内可申请退货。
  chunk2: 退货流程如下。
  chunk3: 第一步在App提交申请。
  chunk4: 第二步寄回商品。
  chunk5: 退款时效为7个工作日到账。
  chunk6: 特殊商品除外。

查询: "退货后钱几天到账"
命中块: chunk5 "退款时效为7个工作日到账。"（与查询共现"退款/到账"）
扩展窗口 [-1, +1] → 喂给 LLM 的是:
  "第二步寄回商品。 | 退款时效为7个工作日到账。 | 特殊商品除外。"
```

走查这个例子：查询”退货后钱几天到账”里只有”退货”共现强——如果没有上下文扩展，一个纯词共现检索器很可能命中 chunk1（”可申请退货”），而真正的答案”7 个工作日到账”在 chunk5 里，两者相隔 4 块。本例检索直接命中 chunk5 后，窗口扩展把”寄回商品 → 退款到账 → 例外情况”这条完整链路带给了模型—— **答案 + 答案的前提条件 + 答案的边界** ，一次给全。反过来若命中的是 chunk1（”7 天内可申请退货”），窗口扩展会带出 chunk0～chunk2，”退款时效”仍不在窗口内——这说明窗口扩展解决的是” **答案在命中点附近** “的割裂，对”答案在文档另一头”的远距离割裂无能为力，后者需要文档级检索或多跳分解来解决。

### 5.2 实现方式与窗口权衡

实现上最常见的是固定窗口：命中块 $i$ 时，同时取 $[i-1, i, i+1]$（甚至 $[i-2, i+2]$）拼接后再送入生成。进阶形态是”小块检索、大块生成”（small-to-big / parent-document retriever）：索引时只对小块做嵌入，检索命中后回溯其所属的大块或整篇文档用于生成，兼顾检索精度与上下文完整性。

窗口大小的权衡：窗口过小起不到缝合作用，窗口过大则把不相关内容也塞进 Prompt——既稀释关键信息（”lost in the middle”效应：LLM 对超长上下文中部信息的利用率显著下降，Liu et al., 2023 在多份文档的 needle-in-a-haystack 实验中观察到，关键信息放在上下文中部时模型准确率相对放在首尾显著下降，呈 U 形曲线），又推高 token 成本。工程经验是以命中块为中心各扩 1～2 块，并按 token 预算截断。

窗口选择可以归纳成一张决策表：

| 窗口设置 | 优势 | 风险 | 适用 |
| --- | --- | --- | --- |
| 仅命中块 | token 最省，主题最聚焦 | 答案缺前提/缺边界 | 独立成句的 FAQ 型知识 |
| ±1 块 | 缝合大部分局部割裂 | token 翻 3 倍 | 默认选择，流程/条款类文档 |
| ±2 块及以上 | 覆盖跨段论述 | 中部信息被稀释（lost in middle） | 长文档 + 强 token 预算 |
| 整篇回溯（small-to-big） | 上下文最完整 | 单条证据成本最高 | 法务/合同等强完整性场景 |

至此候选文档已经”相关且完整”，但”相关”内部仍有高低之分——哪篇文档该排进 Prompt 的前几位，是重排序模块的职责。

## 6. 重排序：用更贵的模型做最后一道把关

### 6.1 为什么召回排序不够好

BM25 与向量检索都是”先算后存”的架构：文档嵌入在入库时就已算好，查询时只做近邻查找。这种架构能毫秒级扫过百万文档，但代价是 **查询与文档从未真正”见面”** ——相似度是两个独立向量的几何距离，不是对”这段文字是否回答了这个问题”的语义判断。于是会出现：召回的文档确实沾边，但最相关的那篇可能排在第 4、第 5 位。

### 6.2 Cross-Encoder 的工作原理

重排序（Reranking）用专门的模型对候选集重新打分。当前主流是 Cross-Encoder 架构，工作流程四步：

1. 将用户问题和每个候选文档 **拼接成同一输入** ，一起送入重排序模型；
2. 模型在注意力层让 query 与 document 的每个 token 充分交互，计算相关性分数（通常经 sigmoid 归一化到 0～1 之间）；
3. 按分数从高到低排序；
4. 选择 Top-N 个最相关的文档进入生成环节。

它与双编码器的本质差异可以用两个公式说清。双编码器（Bi-Encoder）各自独立编码：

$$
s_{\text{bi}}(q, d) = \cos\big(E_q(q),\, E_d(d)\big)
$$

Cross-Encoder 则拼接后联合编码，分数来自完整的 token 级交互：

$$
s_{\text{cross}}(q, d) = \sigma\big(f([q; d])\big)
$$

其中 $\sigma$ 是 sigmoid 函数。Bi-Encoder 中 $d$ 的向量可以预先算好，查询时复杂度是 $O(N)$ 次向量点积；Cross-Encoder 中每个候选都要跑一遍完整的前向计算，复杂度是 $O(N)$ 次完整推理——贵得多，但精度也高得多。这就是工程上” **召回用快的、排序用准的** “两段式架构：向量/BM25 先从百万文档中粗筛出几十个候选，Cross-Encoder 只对这几十个做精算。开源常用的重排序模型包括 BGE-reranker（BAAI）、bge-reranker-v2-m3 等，均基于此架构微调。

### 6.3 数值演算与代码实现

一次完整的重排序演算：设重排序模型对 4 个候选输出分数——d0: 0.92（直接命中问题）、d2: 0.41（话题沾边）、d1: 0.33（仅同主题）、d3: 0.12（弱相关）。取 Top-2，则只有 d0 和 d2 进入 Prompt，d1、d3 被丢弃。对比没有重排序时召回层给出的顺序（d3 排第 1），Top-2 选择会漏掉真正的答案文档——这个对比量化了重排序的价值。

这个演算还能进一步算出 **重排序的”止损账”** 。设无重排序时 4 个候选以召回序进入 Prompt（d3, d1, d2, d0），LLM 受 lost-in-the-middle 与注意力稀释影响，对排在后面的证据利用率低。把每个位置的有效利用率粗略记为 $\eta = [0.9, 0.8, 0.5, 0.3]$（首尾高、中部低的 U 形近似），则两种排布下”答案文档 d0 的有效贡献”分别是：

$$
\text{无重排}：\eta_4 \cdot 1 = 0.3 \qquad \text{重排后}：\eta_1 \cdot 1 = 0.9
$$

同一份文档，仅仅是 **排位** 变了，对生成的有效贡献差了 3 倍——这是”重排序只是换个顺序，凭什么值钱”这个质疑的量化回答：它值的不是计算量，是把有限注意力预算分配给真正相关的证据。

```python
# -*- coding: utf-8 -*-
"""重排序最小实现：用 Cross-Encoder 对召回候选重新打分。

依赖：pip install sentence-transformers
运行：python rerank_demo.py（首次运行自动下载模型，约 100MB）
"""
from sentence_transformers import CrossEncoder

# ── 阶段 1：加载 Cross-Encoder 重排序模型 ────────────────────
# ms-marco-TinyBERT-L-2-v2 是轻量演示模型；生产可用 BAAI/bge-reranker-base
model = CrossEncoder("cross-encoder/ms-marco-TinyBERT-L-2-v2", max_length=512)

def rerank(query: str, candidates: list[str], top_n: int = 2) -> list[tuple[str, float]]:
    """对候选文档重排序。

    对应正文 6.2 四步：拼接输入 → 打分(0~1) → 降序 → 取 Top-N。
    返回 [(文档, 相关性分数)]，已按分数降序。
    """
    # 阶段 2：query 与每个候选文档拼接成同一输入，一起送入模型
    pairs = [[query, doc] for doc in candidates]
    # 模型让 query 与 doc 的 token 在注意力层充分交互后输出 logits
    raw_scores = model.predict(pairs)
    # 阶段 3：sigmoid 归一化到 0~1，对应公式 s = σ(f([q; d]))
    scores = 1.0 / (1.0 + np.exp(-raw_scores))
    # 阶段 4：按分数从高到低排序，取 Top-N
    ranked = sorted(zip(candidates, scores), key=lambda x: -x[1])
    return ranked[:top_n]

if __name__ == "__main__":
    query = "RAG 中重排序的作用是什么"
    candidates = [
        "重排序模型对召回结果用交叉编码器重新打分，提升送入 LLM 的文档质量。",  # 直接命中
        "向量数据库通过 HNSW 索引加速近邻搜索。",                              # 话题沾边
        "BM25 是基于词频的稀疏检索算法。",                                    # 仅同主题
        "今天天气晴朗，适合户外活动。",                                        # 无关对照
    ]
    for doc, s in rerank(query, candidates, top_n=2):
        print(f"{s:.3f}  {doc}")
```

真实运行输出：

```text
0.953  重排序模型对召回结果用交叉编码器重新打分，提升送入 LLM 的文档质量。
0.587  向量数据库通过 HNSW 索引加速近邻搜索。
```

走查：无关文档”天气”被排到末位并截断，正确答案文档以 0.953 的高分进入 Top-2。注意轻量模型的分数区分度不如生产级 reranker（如 BGE-reranker），但”直接命中 >> 沾边 >> 无关”的排序方向完全一致。面试常考的追问是”重排序和 RRF 有什么区别”——RRF 融合的是 **多个排序列表的排名位置** ，不判断语义相关度；重排序是对每个文档做 **真正的语义打分** ，两者在流水线中先后衔接而非互相替代。

重排序与前面所有模块的分数还有一个工程视角的差异值得记录。BM25 分数无界、余弦相似度有界但含义依赖模型，这些分数 **只在同一次检索内部可比** ；而 Cross-Encoder 输出的分数经过 sigmoid 校准后具有跨查询的可比性——今天这批查询的 Top-1 分数普遍在 0.8 以上，明天突然整体跌到 0.4，不必看文档内容就知道 **知识库侧或查询分布发生了漂移** 。这让重排序分数天然成为检索质量的监控指标，下一节的追问阈值正是建立在这个性质上。

重排序给出分数后，这条流水线获得了一个此前没有的东西—— **对”这次检索到底行不行”的量化判断** 。分数低意味着什么、系统该如何体面地处理，是下一节的内容。

## 7. 智能追问：检索失败时的体面退路

传统 RAG 有一个隐性假设：检索总能召回有用文档。现实是知识库覆盖不全、问题表述模糊、检索方向偏移都会导致低质量召回——此时硬着头皮生成，输出的必然是幻觉。智能追问模块把这些情况拦在生成之前： **当检索到的信息不足以回答问题时，生成澄清性问题反问用户** 。

### 7.1 触发条件

三个条件命中其一即触发追问：

- **重排序分数低于阈值** ：如 Top-1 文档分数 < 0.5，说明最强候选也不够相关——这是最客观的信号，也是重排序分数的第二重用途（排序之外兼作检索质量评估器）；
- **文档内容与问题相关性不高** ：分数尚可但语义审查发现答非所问，常见于查询向量被歧义词带偏的情况；
- **问题表述模糊** ：指代不明（”它多少钱”）、缺少限定（”手机推荐一下”），即使检索成功也不知道该答哪一层。

### 7.2 追问的决策代码

三个触发条件在工程上收敛为一个简单的决策函数（可运行， `rerank_scores` 即第 6 节 Cross-Encoder 的输出）：

```python
# -*- coding: utf-8 -*-
"""智能追问决策器:重排序分数 + 模糊度 → 回答 / 追问 / 拒答 三分支。"""

def decide_action(rerank_scores: list[float], ambiguity: float,
                  score_threshold: float = 0.5,
                  ambiguity_threshold: float = 0.7) -> str:
    """检索质量决策。

    参数:
        rerank_scores: 重排序模型对候选文档的相关性分数(0~1,已降序)
        ambiguity: 问题模糊度评分(0~1,可由 LLM 对问题分类给出)
        score_threshold: Top-1 相关性分数的合格线
        ambiguity_threshold: 模糊度的追问线
    返回:
        "answer" 直接回答 / "clarify" 追问澄清 / "reject" 拒答+引导反馈
    """
    top1 = rerank_scores[0] if rerank_scores else 0.0
    # 分支1:最强候选也不相关 → 检索失败
    if top1 < score_threshold:
        # 若问题本身还很模糊,追问一次还有救;否则直接拒答
        return "clarify" if ambiguity >= ambiguity_threshold else "reject"
    # 分支2:检索成功但问题模糊,不知道该答哪一层 → 追问
    if ambiguity >= ambiguity_threshold:
        return "clarify"
    # 分支3:检索合格 + 问题明确 → 正常回答
    return "answer"

if __name__ == "__main__":
    cases = [
        ("型号明确+检索命中", [0.92, 0.41], 0.1),   # → answer
        ("检索弱命中+问题含糊", [0.42, 0.30], 0.8), # → clarify
        ("检索失败+问题明确", [0.21, 0.15], 0.1),   # → reject
        ("检索命中+指代不明", [0.88, 0.52], 0.9),   # → clarify
    ]
    for name, scores, amb in cases:
        print(f"{name:<14} → {decide_action(scores, amb)}")
```

真实运行输出：

```text
型号明确+检索命中 → answer
检索弱命中+问题含糊 → clarify
检索失败+问题明确 → reject
检索命中+指代不明 → clarify
```

走查第二个用例：Top-1 分数 0.42 低于 0.5 的合格线，说明检索不可靠；此时模糊度 0.8 表明”追问一次可能把问题问清楚”，于是选择 clarify 而非直接拒答—— **追问的本质是把”必然错误的回答”置换成”低成本的信息补全”** 。第三个用例检索失败且问题本身很明确（比如问一个知识库里根本没有的内容），追问只会惹恼用户，正确动作是如实告知 + 引导用户补充文档，这条路径最后接到的正是第 8 节的负反馈通道。

### 7.3 追问的设计与边界

追问本身是 LLM 生成的一句澄清性问题，例如”您指的是 iPhone 15 还是 iPhone 15 Pro 的价格？”。用户澄清后，澄清结果与原问题合并，重新走查询优化与检索（对应第 1 节流程图中紫色回边）。这一思想与 Self-RAG（Asai et al., 2023， [arXiv:2310.11511](https://arxiv.org/abs/2310.11511) ）一脉相承——Self-RAG 训练模型用反思 token 自主判断”是否需要检索、检索质量是否合格、答案是否有依据”，把”检索质量把关”内化到模型；CRAG（Corrective RAG，arXiv:2401.15884）则训练一个轻量评估器把检索结果分为 Correct / Incorrect / Ambiguous 三档，低质量时触发纠错动作（改写查询、回退到 Web 搜索）。智能追问是这三者中最轻量的工程实现：不训练模型，用重排序分数 + Prompt 规则就完成”合格才回答，不合格就反问”。

设计上的克制点：追问不能滥用——每次追问都是一次交互成本，阈值设得太高系统会变得”话多”。经验做法是只在”明显无法回答”与”回答必错”之间选择追问，模糊但可给通用答案的问题宁可答全多种情况。

追问解决的是”这一次问答失败怎么办”，而反馈模块解决的是”让同样的失败以后不再发生”。

## 8. 用户反馈与知识库更新：让系统越用越准

### 8.1 反馈闭环的工作流程

前六个模块都在优化”单次问答”，第七个模块把视野拉长到系统生命周期：系统返回答案后收集用户反馈，据此持续优化知识库。工作流程分三种反馈路径：

- **满意** ：该问答对被标记为高质量样本，写入知识库——下次类似问题可以直接命中这条”被人类验证过的答案”，相当于给系统积累了自产的高置信度语料；
- **不满意** ：用户可以提供正确答案，系统记录原问题与正确答案的配对；
- **修正** ：用户在给出答案的基础上修改后确认，形成”原答案 → 修正答案”的演化记录。

三条路径殊途同归：产出结构化的问答对进入知识库，使知识库从”静态文档切片”演化为”文档 + 高质量问答对”的混合形态。问答对形态对检索格外友好——它的文体与用户问题天然对齐，恰好绕过了第 3.2 节讨论的”问题-答案文体不对称”问题。

### 8.2 与学术工作的对应与工程要点

这一机制在学术界的对应物是 Self-RAG 的自我反思与 CRAG 的检索纠错——只不过把”模型自我评估”换成了”人类反馈”，信号更稀疏但更可靠。工程落地有三个要点：

1. **反馈触发要轻** ：用 👍/👎 一键反馈而不是强制问卷，否则反馈率会低到没有统计意义；
2. **入库前要过审** ：用户提供的”正确答案”未必正确（用户自己也可能在幻觉），进入知识库前应经人工审核或让 LLM 结合原文档交叉验证；
3. **负反馈同样有价值** ：频繁被点踩的问题暴露了知识库的覆盖缺口，是”该补哪些文档”最直接的需求清单。

## 9. 如何量化每个模块的收益：RAG 评估指标体系

前面各节的实验都是单点演示，工程上线前需要一套系统化指标来量化”加了模块到底有没有用”。RAG 评估分两层： **检索层** （独立于生成器，可离线跑）与 **生成层** （依赖 LLM，通常在线评估）。

**检索层指标** （给定标注好的”问题 → 正确文档”对）：

$$
\text{Recall@}K = \frac{|\text{Top}K_{\text{检索}} \cap \text{相关文档集}|}{|\text{相关文档集}|}, \qquad \text{MRR} = \frac{1}{|Q|}\sum_{i=1}^{|Q|}\frac{1}{\text{rank}_i}
$$

Recall@K 衡量”正确文档有没有被捞进来”，MRR 衡量”捞进来之后排得靠不靠前”——前者对应模块 1～3（查询优化与混合检索的收益主要在这里），后者对应模块 4～5（重排序的收益在这里）。一个典型的模块收益记录方式：

| 配置 | Recall@5 | MRR@10 | 备注 |
| --- | --- | --- | --- |
| 基线：原始查询 + 纯向量检索 | 0.62 | 0.51 | 朴素 RAG |
| + 查询改写 | 0.71 | 0.55 | 词汇鸿沟收窄 |
| + 混合检索（RRF） | 0.78 | 0.60 | 型号类问题显著改善 |
| + 重排序 | 0.78 | 0.74 | 召回不变，排序跃升 |

（数值为示意量级，规律与公开报告一致：查询优化抬 Recall，重排序抬 MRR 而不抬 Recall。）注意一个关键事实： **重排序不改变候选集，只改变顺序** ——所以它的 Recall@5（无序集合重合）理论上不变，涨的全是 MRR/NDCG 这类位置敏感指标。如果有人声称重排序提升了 Recall@K，要么是 K 变小后 Top-N 截断位置变了，要么是评估口径有误。

**生成层指标** ：忠实度（faithfulness，答案是否被检索内容支撑，幻觉率 1 − 忠实度）、答案相关性（answer relevancy，答案是否回应了问题）、正确性（与标注答案的重合度）。这些指标多依赖 LLM-as-judge 或 NLI 模型自动打分（RAGAS 框架的标准做法）。评估时的铁律是 **改一个模块只看它对应层的指标** ：改检索看 Recall/MRR，改 Prompt 看忠实度/相关性——混在一起看会互相掩盖。

## 10. 总结：七个模块回答的七个问题

把全文串成一条主线——这条流水线的每个模块，都在回答朴素 RAG 留下的一个具体问题：

| 模块 | 回答的问题 | 关键机制 |
| --- | --- | --- |
| 1. 问题复杂度判断 | 这个问题一次检索够吗？ | 复杂问题拆解为子问题 |
| 2. 查询优化 | 检索器能读懂”人话”吗？ | 改写 / HyDE / 多查询生成 |
| 3. 混合检索 | 单一检索的盲区怎么补？ | 向量 + BM25，RRF 融合，k=3 去重 |
| 4. 上下文扩展 | 分块切散的信息怎么缝回去？ | 返回命中块及前后相邻块 |
| 5. 重排序 | 谁才是真正最相关的文档？ | Cross-Encoder 打分取 Top-N |
| 6. 智能追问 | 检索失败时怎么办？ | 分数低于阈值时反问澄清 |
| 7. 反馈与知识库更新 | 错误如何不再重演？ | 反馈 → 问答对 → 入库 |

面试视角的浓缩记忆法： **模块 1～3 优化”查什么”（query side），模块 4～5 优化”拿什么喂给模型”（context side），模块 6 把关”该不该答”（quality gate），模块 7 保证”下次更好”（lifecycle），第 9 节的指标体系负责验收每一步** 。回答相关面试题时，先给出这个四层框架，再按面试官追问的方向深入某个模块——比逐个背诵七点更有结构感。

一条面试高频的追问线也值得预演：”这些模块都要上吗？”——标准答案是否定的。模块的引入顺序应按 **性价比** 排：混合检索 + 重排序（改动小、收益大、成熟方案多）→ 查询改写（一个 Prompt 的事）→ 上下文扩展（改个检索返回逻辑）→ 智能追问与反馈闭环（涉及交互与数据链路，最后上）。每个模块上线前用第 9 节的指标跑一轮离线对比，收益不显著的不上—— **七模块是菜单，不是套餐** 。

## 附录

### A. RRF 平滑常数 $k'$ 的作用推导

RRF 公式中 $k'$ 取 60 的动机可以从排名贡献比看出。$k' \to 0$ 时，第 1 名与第 2 名的贡献比为 $\frac{1}{1} / \frac{1}{2} = 2$，头部排名权重垄断严重；$k' = 60$ 时该比值降为

$$
\frac{1/(60+1)}{1/(60+2)} = \frac{62}{61} \approx 1.016
$$

即名次每前进一位，贡献只增加约 1.6%——融合结果更依赖” **在几个列表里是否都被认可** “，而不是”在某个列表里是否恰好排第一”，这正是多路检索场景想要的选择偏好。

### B. BM25 打分公式与逐项推导

BM25 对查询 $Q$ 与文档 $D$ 的相关度打分：

$$
\text{score}(Q, D) = \sum_{i=1}^{n} \text{IDF}(q_i) \cdot \frac{f(q_i, D) \cdot (k_1 + 1)}{f(q_i, D) + k_1 \cdot \left(1 - b + b \cdot \frac{|D|}{\text{avgdl}}\right)}
$$

其中 $f(q_i, D)$ 是词 $q_i$ 在文档 $D$ 中的词频，$|D|$ 与 $\text{avgdl}$ 分别是文档长度与语料平均长度，$k_1 \in [1.2, 2.0]$ 控制词频饱和（词出现越多贡献越大，但边际递减），$b \in [0, 1]$ 控制长文档惩罚力度。IDF 项让稀有词（如产品型号）的命中权重远高于常见词——这解释了混合检索中 BM25 对精确 token 的敏感性来源。

三个组成部分各自的直觉，值得逐一拆开：

- **IDF 项** （逆文档频率）：$\text{IDF}(q) = \ln\frac{N - n(q) + 0.5}{n(q) + 0.5}$（$N$ 为语料文档总数，$n(q)$ 为包含该词的文档数）。它在 $n(q) = N$（所有文档都含该词）时精确为 0——一个到处出现的词对区分文档毫无价值，公式自动把它清零。4.1 节的演算里”Pro”得分归零正是这一性质；
- **词频饱和项** ：$\frac{f \cdot (k_1+1)}{f + k_1 \cdot (\cdots)}$。当 $f \to \infty$ 时该项趋于 $k_1 + 1$（一个常数上界）——一个词出现第 10 次带来的增益远小于第 1 次，防止”词藻堆砌”的文档骗取高分。$k_1 = 0$ 时退化为”出现过即可”的二值模型，$k_1 \to \infty$ 则退化为原始词频计数，实际取 1.2～2.0 折中；
- **长度归一项** ：$1 - b + b \cdot \frac{|D|}{\text{avgdl}}$。长文档天然包含更多词、词频更高，不惩罚就会系统性偏向长文档；$b = 1$ 完全按相对长度归一，$b = 0$ 关闭惩罚，默认 0.75 保留部分长度偏好（长文档确实更可能覆盖答案）。

| 指标 | 公式要点 | 衡量什么 | 受哪个模块影响 |
| --- | --- | --- | --- |
| Recall@K | Top-K 与相关集的交并比 | 正确文档有没有被捞到 | 查询优化、混合检索 |
