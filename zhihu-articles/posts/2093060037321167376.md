> 2025 年 9 月，Anthropic Applied AI 团队发布上下文工程文章，讨论 Agent 在长任务中怎样筛选、维护和使用信息。文章从上下文的有限容量出发，解释工具设计、即时检索、压缩、笔记与子 Agent 分工如何配合。

应用 AI 的关注点，正从提示词工程扩展到 **上下文工程** 。

使用语言模型构建应用，越来越少是在寻找提示词里最合适的字句，越来越多是在回答一个更广的问题：怎样组织模型接收到的信息，最有可能让它做出预期的行为？

上下文，可以理解为模型作答时能看到的全部材料；从技术上说，它是一次大语言模型推理时包含的全部 token，也就是模型处理的文本与信息单元。工程问题在于：在模型自身限制下，提高这些信息的效用，让预期结果能够稳定出现。

有效地使用模型，需要从上下文的整体状态出发思考：模型在某个时刻能看到什么，这种信息配置又可能产生什么行为？上下文工程要解决的，正是如何让 Agent——能调用工具、连续推进任务的 AI 系统——更可控、更有效。

### 提示词工程之外，还有整个上下文

Anthropic 将上下文工程视为提示词工程的自然延伸。提示词工程关注如何编写和组织模型指令； [相关文档](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview) 介绍了常用方法。

上下文工程则关注推理期间如何筛选、维护最合适的信息集合，其中还包括提示词之外进入模型的信息。

早期，除日常对话之外，许多应用都是单次分类或文本生成，提示词优化尤其是系统提示词，构成了 AI 工程的主要工作。现在，Agent 要跨越多轮推理、持续更长时间，工程师必须管理完整的上下文状态：系统指令、工具、 [MCP（模型上下文协议）](https://modelcontextprotocol.io/docs/getting-started/intro) 、外部数据与消息历史。

循环运行的 Agent 会不断生成可能与下一轮相关的数据。这些内容需要反复整理。上下文工程，就是从持续变化的信息世界中，挑选哪些内容进入有限上下文窗口的 [方法与实践](https://x.com/karpathy/status/1937902205765607626?lang=en) 。

![](https://pic1.zhimg.com/v2-42765f3180ff7907bd6c8f19e2c6b430_r.jpg)
*写一份提示词可以是独立任务；上下文工程是迭代过程，每次决定传给模型什么，都要重新筛选。*

更大的窗口，也有注意力限制

模型能快速处理越来越多数据，但 Anthropic 团队观察到，它们也会像人一样，在一定程度上失去重点或产生混淆。“大海捞针”式评测揭示了 [上下文退化](https://research.trychroma.com/context-rot) ：窗口中的 token 增加时，模型准确找回其中信息的能力会下降。

有些模型退化得更缓慢，但这种特点在不同模型中都存在。因此，上下文应被视为有限且边际收益递减的资源。类似人类有限的工作记忆，模型解析大量信息时也有一份“注意力预算”；每增加一些信息，就更需要认真筛选。

这与模型架构有关。Transformer 是主流语言模型采用的架构，它让每个 token 能关注上下文中的其他 token：n 个 token 之间有 n² 级别的成对关系。上下文变长，模型捕捉这些关系的能力受到更多牵制，信息容量与注意力集中度之间出现张力。

训练数据中，短序列往往比长序列更常见，模型对贯穿整个长上下文的依赖关系，经验和专门适配也相对少。 [位置编码插值](https://arxiv.org/pdf/2306.15595) 等技术能让模型从原来训练过的较小窗口扩展到长序列，但对位置信息的理解仍可能损失精度。

这通常是一段逐渐变化的性能曲线，而不是越过某个长度就突然失效。长上下文中的模型仍很强，只是信息检索和远距离推理，可能不如短上下文时精确。

### 有效上下文应该怎样组成

既然注意力有限，好的上下文工程就要找到尽可能精简、信息价值高的内容，使预期结果最有可能出现。原则简单，落实起来却不容易。

**系统提示词需要清楚、直接，并处于合适的抽象层级。** 一端是把复杂、脆弱的分支逻辑硬编码进提示词，试图精确控制每一种行为，结果越来越难维护；另一端是只有含糊的高层建议，没有具体信号，甚至误以为模型与人共享未说出口的背景。

合适的层级，既足以指导行为，又允许模型依据有效的判断原则处理新情况。

![](https://pic2.zhimg.com/v2-da960ecca8c6e1bd6545e98fafb349f3_r.jpg)
*一端是僵硬的 if-else 式指令，另一端是过度笼统、假定共享背景的指令。*

一个可行的做法是，将提示词分成背景、指令、工具使用、输出要求等明确部分，可以使用 XML 标签或 Markdown 标题，如 `<background_information>` 、 `<instructions>` 、 `## Tool guidance` 、 `## Output description` 。随着模型增强，具体排版方式可能越来越不重要。

无论采用哪种格式，目标都应是用尽量少的信息完整说明预期行为。“精简”并不必然是“短”，模型仍需要足够信息才能遵守要求。

更好的起点，是先用当前最好的模型测试最小可行提示词，再根据实际失败模式添加明确指令和例子。

**工具让 Agent 与环境交互，并获得新信息。** 工具定义了 Agent 与信息、动作空间之间的契约，因此既要提供精简的信息，也要引导高效行为。

Anthropic 在 [《为 AI Agent 编写工具》](https://www.anthropic.com/engineering/writing-tools-for-agents) 中讨论过，工具应容易被模型理解，功能尽量不重叠。类似职责清楚的函数，工具需要职责完整、能妥善处理错误、用途清晰；参数应有明确描述，避免歧义，并适应模型擅长的使用方式。

常见失败是工具集合过大，功能覆盖过宽，或让模型在“到底该用哪个”上产生歧义。如果人类工程师都无法明确选择，不能指望 Agent 做得更好。精简的必要工具集合，也有助于长对话中的上下文维护与清理。

**示例仍然很重要。** 少量示例提示，即 few-shot prompting，仍是 Anthropic 推荐的方法。但不建议把所有边缘情形都塞进提示词，试图穷尽每条规则。应选择多样、有代表性的例子，准确展示预期行为。对模型来说，一个好例子可以抵得上大量抽象说明。

系统提示词、工具、示例和消息历史，都需要兼顾信息充分与内容紧凑。接下来要解决的是：运行时怎样取得新上下文？

### 按需检索，让 Agent 逐步探索

在 [《构建有效的 AI Agent》](https://www.anthropic.com/research/building-effective-agents) 之后，Anthropic 越来越倾向于一个 [简单定义](https://simonwillison.net/2025/Sep/18/agents/) ：Agent 是在循环中自主使用工具的大语言模型。

在与客户的合作中，Anthropic 团队看到行业逐步汇聚到这个思路。底层模型越聪明，就越能独立探索复杂问题并从错误中恢复，Agent 的自主程度也可以提高。

许多 AI 原生应用目前会在推理前，通过向量嵌入检索取得相关材料，也就是把内容转成数值表示，再按相似程度寻找相关信息。随着应用更具自主性，团队开始在此基础上增加“即时按需”的上下文策略。

Agent 不必预先处理所有相关数据，而是保留文件路径、已存查询、网页链接等轻量引用，运行时再通过工具读取内容。

[Claude Code](https://www.anthropic.com/claude-code) 就这样分析大型数据库：模型编写有针对性的查询，保存结果，用 `head` 、 `tail` 等 Bash 命令查看重点，无须把完整数据对象都装进上下文。人通常也不会记住整套资料，而会用文件系统、收件箱和书签组织信息，按需找回。

引用的元数据还可以指导行为。同样叫 `test_utils.py` 的文件，放在 `tests/` 与放在 `src/core_logic/` ，用途很可能不同。目录层次、命名和时间戳，都会帮助人和 Agent 判断何时、怎样使用材料。

自主导航与检索支持逐步披露信息：每次交互为下一次决定提供线索。文件大小提示复杂程度，名字提示用途，时间戳帮助判断相关性。Agent 可以一层层建立理解，仅保留工作记忆所需的内容，并用笔记保存其他重要信息，避免淹没在全面却不相关的材料中。

代价也很明确：运行时探索比读取预先算好的结果更慢。工程师需要认真设计工具与导航原则，否则模型可能误用工具、追逐死路，或找不到关键信息，反而浪费上下文。

某些场景更适合混合策略：先提供部分材料以提高速度，剩余内容由 Agent 决定是否继续探索。Claude Code 就会预先放入 `CLAUDE.md` ，再通过 `glob` 、 `grep` 等基础工具按需找文件，减少索引过时和复杂语法树带来的问题。

法律、金融等内容变化相对较少的场景，也可能适合混合方法。正确的自主程度取决于任务。随着能力提高，设计会逐步减少人为筛选，让聪明的模型自行作出合理行为。对基于 Claude 构建 Agent 的团队，Anthropic 的建议仍是：选择能够解决问题的最简单方案。

### 跨越上下文窗口的长任务

大型代码迁移或深入研究，可能持续几十分钟乃至数小时，行动序列的信息量超过一个窗口。Agent 仍需保持目标、状态与前后连贯性。

等待更大的窗口看似直接，但在可预见的未来，无论窗口多大，为了获得最佳表现，都要面对信息污染与相关性问题。Anthropic 采用几种直接处理这些限制的技术：压缩、结构化笔记、多 Agent 架构。

### 压缩：整理记录后继续

压缩是把接近窗口上限的对话提炼成摘要，再以摘要开启新的上下文。它通常是提高长任务连贯性的第一步，关键是尽可能保真地留下重要内容，使继续工作时性能损失最小。

Claude Code 会让模型总结消息历史，保留架构决策、未解决的 bug 与实现细节，丢弃重复工具输出和消息。随后，Agent 用压缩后的记录，加上最近访问的五个文件继续工作，用户无需自行处理窗口限制。

真正困难的是决定保留和舍弃什么。压缩过度，会丢掉当时不起眼、后来却很关键的细节。设计压缩系统时，应在复杂的 Agent 执行记录上调试提示词：先尽量提高召回率，确保相关信息没有漏掉，再提高精确率，删去多余内容。

清理较早的工具调用及结果，是一种较轻量的办法。工具已经调用很久后，未必仍需要原始返回全文。工具结果清理也是较稳妥的压缩形式之一，2025 年 9 月已在 [Claude Developer Platform](https://www.anthropic.com/news/context-management) 推出。

### 结构化笔记：将状态放到窗口之外

结构化笔记也可称为 Agent 记忆：Agent 定期把笔记写到上下文之外的持久存储，之后需要时再读取。

这种模式开销小，却能提供持续记忆。Claude Code 的待办清单，或自建 Agent 的 `NOTES.md` ，都能记录复杂任务的进展、关键上下文与依赖，避免它们在几十次工具调用之后丢失。

[Claude 玩《宝可梦》](https://www.twitch.tv/claudeplayspokemon) 展示了记忆在编程之外的价值。它跨越数千步游戏行动，精确跟踪目标，比如：“过去 1,234 步都在一号道路训练，皮卡丘已经升了 8 级，目标是升 10 级。”

即使没有人规定笔记结构，它也会绘制已探索区域的地图，记住重要进度，并记录战斗策略，逐渐了解哪些招式适合哪些对手。

上下文重置后，它读取笔记，继续数小时的训练或地牢探索。这种跨摘要的连贯性，支持了仅靠单个窗口无法维持的长期策略。

2025 年 9 月，随着 Sonnet 4.5 推出，Anthropic 还在开发者平台公开测试了 [记忆工具](http://anthropic.com/news/context-management) 。它通过文件系统帮助 Agent 存储、查询窗口之外的信息，逐步积累知识库，跨会话保持项目状态，并引用过去工作。

### 子 Agent：把深入探索放到独立上下文

主 Agent 不必独自维护整个项目的所有细节。专门的子 Agent 可以带着干净的窗口处理聚焦任务：主 Agent 负责高层计划与协调，子 Agent 深入技术问题，或用工具查找资料。

子 Agent 可以探索数万 token 甚至更多，最后只交回浓缩摘要，通常为 1,000—2,000 token。细节检索留在子 Agent，主 Agent 聚焦结果整合与分析，职责因此清楚分开。

Anthropic 在 [多 Agent 研究系统](https://www.anthropic.com/engineering/multi-agent-research-system) 中讨论过这种模式，它在复杂研究任务上，相比单 Agent 系统有明显提升。

方法的选择取决于任务：需要大量来回对话的任务适合压缩；有清晰里程碑的迭代开发适合笔记；并行探索能带来收益的复杂研究和分析适合多 Agent。

即使模型继续进步，长时间交互中的连贯性仍会是有效 Agent 的核心问题。

### 把有限上下文当成需要管理的资源

上下文工程改变了使用语言模型构建应用的方式。工程师要在每一步认真选择进入有限注意力预算的信息：无论是压缩长任务、设计精简的工具返回，还是让 Agent 按需探索环境，都遵循同一原则——用尽可能精简的高价值信息，提高预期结果出现的概率。

这些方法会随模型进步演化。Anthropic 的观察是，更聪明的模型需要更少的细致规定，可以拥有更多自主性。但把上下文当成宝贵而有限的资源，仍然是构建可靠 Agent 的重要基础。

可以通过 Claude Developer Platform 开始实践，并参考 [记忆与上下文管理示例集](https://platform.claude.com/cookbook/tool-use-memory-cookbook) 。
