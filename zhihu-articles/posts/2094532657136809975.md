2023 年 6 月 20 日，UC Berkeley 的 Woosuk Kwon、Zhuohan Li、Siyuan Zhuang、Ying Sheng、Lianmin Zheng 等研究者公开了一篇技术博客：

**vLLM: Easy, Fast, and Cheap LLM Serving with PagedAttention。**

他们宣布发布一个新的开源大语言模型推理系统：

vLLM。

在当时的测试条件下，vLLM 相比 Hugging Face Transformers 可以取得最高约 24 倍的吞吐提升。

几个月后，这项工作以论文形式发表于 SOSP 2023。

论文题目是：

**Efficient Memory Management for Large Language Model Serving with PagedAttention。**

其中报告，相比当时的 FasterTransformer、Orca 等系统，vLLM 在相应工作负载下获得了约 2～4 倍的吞吐提升。

但如果仔细阅读论文，会发现一个非常奇怪的地方。

vLLM 并没有提出新的 Transformer 架构。

没有发明新的 Attention 数学公式。

没有改变语言模型的训练目标。

没有减少模型参数数量。

甚至没有要求重新训练模型。

它最重要的创新，竟然来自几十年前操作系统中的一种思想：

**Paging，分页。**

在传统操作系统中，分页主要用于解决进程的逻辑地址空间与物理内存之间的映射问题。

而 vLLM 把这种思想用在了大模型的 KV Cache 上。

这就有意思了。

为什么一种操作系统的内存管理思想，竟然可以让原本昂贵的大模型推理大幅加速？

为什么 Transformer 已经拥有 FlashAttention 等高效 Attention Kernel，仍然需要 PagedAttention？

为什么显存中只是出现了一些碎片，就可能让整个 GPU 的吞吐下降？

更奇怪的是，vLLM 后来的演化并没有停留在 KV Cache。

2024 年 9 月，vLLM v0.6.0 开始大规模减少 CPU 调度开销。

2025 年 1 月，vLLM 宣布 V1 架构重构。

2026 年 3 月，vLLM 又发布 Model Runner V2。

到了 2026 年 9 月，Model Runner V2 已经成为大多数模型的默认执行路径。

2026 年 10 月，vLLM 甚至开始专门优化：

长程 Agent 的跨轮 KV Cache。

Prefill 与 Decode 的分离。

MoE 的复杂并行执行。

以及 RL Rollout 与训练 Forward 的数值一致性。

也就是说，一个最初以 PagedAttention 闻名的项目，逐渐发展成了一整套大模型推理系统。

但这段历史不能简单写成：

```text
PagedAttention
    ↓
Continuous Batching
    ↓
Prefix Caching
    ↓
Speculative Decoding
    ↓
vLLM V1
```

因为其中有些思想早在 vLLM 出现以前就已经存在。

有些功能也不是 vLLM 首创。

而且，vLLM 自己曾经选择的架构，后来又被它自己主动推翻。

要理解这段历史，我们首先需要回到一个看似简单的问题：

**如果有一张非常昂贵的 GPU，我们究竟应该怎样让它同时服务尽可能多的语言模型用户？**

### 一、首先理解：vLLM 到底是什么？它与 PyTorch、Transformers、veRL 有什么区别？

### 1. 大模型推理不等于大模型训练

假设我们已经拥有一个训练好的语言模型：

```text
Qwen
Llama
DeepSeek
Kimi
GLM
```

它的参数已经存在于 Checkpoint 中。

我们现在只想输入：

```text
请解释什么是梯度下降。
```

然后获得：

```text
梯度下降是一种通过梯度信息优化目标函数的方法……
```

这个过程主要属于：

**Inference，推理。**

它通常不需要执行：

```python
loss.backward()
```

也不需要调用：

```python
optimizer.step()
```

因为我们不是在更新模型参数。

我们只是利用已有参数计算输出。

### 2. 那么 vLLM 负责什么？

vLLM 主要负责：

**让已经训练好的模型，更高效地执行推理和对外提供服务。**

例如：

```text
用户 A：
解释 PPO。

用户 B：
写一段 Python 代码。

用户 C：
总结一篇论文。

用户 D：
分析一个代码仓库。
```

如果四个人同时提交请求，vLLM 需要决定：

哪些请求一起执行？

每个请求应该占用多少显存？

什么时候开始处理新请求？

哪个请求应该优先生成？

哪些历史 KV Cache 可以复用？

如果显存不够，应该暂停哪个请求？

怎样把多个 GPU 组织成一个模型实例？

怎样通过 HTTP 把结果返回用户？

这些已经超出了普通 Transformer 数学公式的范围。

它们属于：

**LLM Serving。**

即大模型推理服务系统。

### 3. 它与其他框架的职责区别

| 工具 | 主要职责 |
| --- | --- |
| PyTorch | 张量运算、自动微分、模型执行基础 |
| Transformers | 模型架构、权重加载、Tokenizer、生成接口 |
| vLLM | 高性能模型推理与 Serving |
| SGLang | 高性能推理与复杂 LLM 程序执行 |
| veRL | 强化学习后训练、Rollout 与 Trainer 编排 |

这只是主要职责的区分，不表示它们之间没有功能重叠。

例如：

Transformers 本身也能推理。

vLLM 也能提供部分模型评分能力。

veRL 的训练流程会调用 vLLM 进行 Rollout。

所以更准确的关系是：

```text
veRL
                  │
           组织强化学习训练
                  │
        ┌─────────┴─────────┐
        ▼                   ▼
   Training Engine      Rollout Engine
        │                   │
   FSDP / Megatron      vLLM / SGLang
                            │
                            ▼
                         GPU 推理
```

这也说明：

vLLM 并不是一个新的强化学习算法。

它负责的是 RL 系统中极其重要的推理执行部分。

### 二、2022 年：Continuous Batching 的重要前驱，其实是 Orca

### 4. 最简单的 Batch Inference 是怎样工作的？

假设我们有四个请求。

```text
Request A：生成 10 个 Token

Request B：生成 100 个 Token

Request C：生成 20 个 Token

Request D：生成 50 个 Token
```

一种简单方案是：

把四个请求放进一个 Batch。

然后一起执行。

```text
Batch：
[A, B, C, D]
```

问题在于：

四个请求的输出长度不同。

A 只需要 10 个 Token。

B 却需要 100 个。

### 5. 静态 Batch 为什么会浪费资源？

在一种简单的同步 Batch 方案中：

```text
Step 1：
A B C D

Step 2：
A B C D

...

Step 10：
A B C D
```

到了第 10 步：

A 已经完成。

但其他请求还在继续生成。

如果系统要求整个 Batch 完成后才统一释放资源或者开始新 Batch，就会出现：

已经完成的请求占据 Batch 位置。

新请求无法及时加入。

长请求拖慢短请求。

这种问题可以称为：

**Head-of-Line Blocking。**

即队头阻塞。

一个比较慢的任务，拖住了其他任务。

### 6. 2022 年 Orca 提出了什么？

2022 年 7 月，Gyeong-In Yu 等研究者在 OSDI 2022 发表：

*Orca: A Distributed Serving System for Transformer-Based Generative Models*。

Orca 提出了：

**Iteration-Level Scheduling。**

中文可以理解为：

按生成迭代进行调度。

核心思想非常简单。

以前：

```text
以一个完整 Request 为调度单位。
```

现在：

```text
以一次模型生成迭代为调度单位。
```

例如：

```text
Step 1：
A B C D

Step 2：
A B C D

...

Step 10：
A 完成
```

下一轮：

```text
Step 11：
B C D E
```

新请求 E 可以加入。

而 A 已经离开。

这就是后来普遍所说的：

**Continuous Batching，连续批处理。**

### 7. 为什么它比静态 Batch 更合理？

因为 LLM 的生成天然是迭代式的。

每次 Decode 通常只向每条请求推进一个 Token。

因此，在两次 Decode 之间重新组织 Batch，是很自然的调度方式。

例如：

```text
时间 t0：
A B C

时间 t1：
A B C D

时间 t2：
A C D E

时间 t3：
C D E F
```

Batch 不断变化。

已经完成的请求退出。

新请求动态进入。

GPU 不需要一直等待最长的那个请求结束。

### 8. Orca 还提出了 Selective Batching

这点也不能忽略。

Transformer 的不同操作，并不都适合用完全相同的方式 Batch。

例如：

某些线性层可以高效地批量计算。

但 Attention 需要处理每个 Request 不同的历史长度和 KV Cache。

Orca 因此提出：

**Selective Batching。**

不同算子可以采用不同的批处理策略。

在论文测试中，Orca 相比当时的 FasterTransformer，在对应 GPT-3 175B 服务工作负载上取得显著吞吐改善。

所以：

**vLLM 没有发明 Iteration-Level Scheduling。**

它继承了这一重要方向。

那么，既然 2022 年的 Orca 已经能够动态组织请求，vLLM 在 2023 年到底创新了什么？

答案是：

KV Cache。

### 三、为什么 KV Cache 会成为大模型 Serving 的显存瓶颈？

### 9. 先从 Attention 公式讲起

Transformer Attention 的基本形式是：

$$ \operatorname{Attention}(Q,K,V) = \operatorname{softmax} \left( \frac{QK^\top}{\sqrt{d_k}} \right)V $$

这里：

- $Q$：Query。
- $K$：Key。
- $V$：Value。

假设我们已经生成：

```text
我 喜欢 人工 智能
```

现在需要预测下一个 Token。

当前 Token 的 Query，需要与历史 Token 对应的 Key 进行 Attention。

所以模型必须使用过去的 Key 和 Value。

### 10. 为什么要缓存 K 和 V？

如果不缓存：

每生成一个新 Token，都需要重复计算此前所有 Token 的 K、V。

例如：

```text
生成 Token 1：
计算历史 1000 个 Token。

生成 Token 2：
重新处理历史 1001 个 Token。

生成 Token 3：
重新处理历史 1002 个 Token。
```

这会浪费大量计算。

于是我们使用：

**KV Cache。**

已经计算过的历史 K、V 保存下来。

下一次只需要计算新 Token 的 K、V。

然后与历史缓存共同执行 Attention。

因此：

```text
过去的 K、V：
直接读取缓存。

新 Token 的 K、V：
本轮计算。
```

这能显著降低重复计算。

但代价是：

必须保存越来越多的 KV Cache。

### 11. KV Cache 到底有多大？

对于普通 Full Attention 模型，可以近似写成：

$$ M_{\mathrm{KV}} = 2LTH_{\mathrm{kv}}d_hb $$

其中：

- $L$：Transformer 层数。
- $T$：缓存的 Token 数量。
- $H_{\mathrm{kv}}$：KV Head 数量。
- $d_h$：每个 Head 的维度。
- $b$：每个元素的字节数。
- 前面的 2：分别保存 K 和 V。

假设一个模型：

$$ L=32 $$

$$ H_{\mathrm{kv}}=32 $$

$$ d_h=128 $$

使用 BF16：

$$ b=2 $$

那么每个 Token 的 KV Cache 大约是：

$$ 2\times32\times32\times128\times2 $$

得到：

$$ 524288\text{ Bytes} $$

也就是：

$$ 512\text{ KiB} $$

一个 Token 就需要约 512 KiB 的 KV Cache。

如果上下文长度是：

$$ T=16384 $$

那么：

$$ 16384\times512\text{ KiB} = 8\text{ GiB} $$

也就是说：

**单条请求的 KV Cache 就可能占用约 8 GiB 显存。**

当然，这是一个假设采用 32 个 KV Head 的模型。

实际采用 GQA、MLA、KV Quantization 或其他 Attention 结构的模型，KV Cache 大小可能显著降低。

例如，将 KV Head 数量从 32 降到 8：

$$ H_{\mathrm{kv}}=8 $$

其他参数不变。

那么同样 16K Token 的 KV Cache 就约为：

$$ 2\text{ GiB} $$

这说明，KV Cache 大小与具体模型架构高度相关。

但不管怎样，当服务同时面对几十、几百条长上下文请求时，KV Cache 仍然可能非常昂贵。

### 四、2023 年：为什么 KV Cache 的问题不只是太大，而是显存分配方式不合理？

### 12. 传统方案为什么要提前预留空间？

假设 Request A 当前只有：

```text
100 个 Token
```

但系统允许它最终生成到：

```text
4096 个 Token
```

一种直接的内存管理策略是：

提前为它预留可以容纳 4096 Token 的连续 KV Cache 空间。

例如：

```text
Request A：

[已使用 100 Token]
[预留但尚未使用 3996 Token]
```

这样做的好处是：

管理简单。

不用频繁重新分配显存。

KV 地址比较容易计算。

但缺点也很明显。

**绝大多数预留空间，在当前时刻可能完全没有被使用。**

### 13. 为什么会出现 Internal Fragmentation？

Internal Fragmentation：

内部碎片。

可以简单理解为：

系统已经把一块内存分配给某个请求，但请求没有真正使用完。

例如：

```text
分配：
4096 Token 容量。

实际使用：
100 Token。
```

如果不能把剩余容量给其他请求使用，那么这些空间就被浪费了。

### 14. External Fragmentation 又是什么？

External Fragmentation：

外部碎片。

假设显存中有多个空闲区域：

```text
[空闲 1 GB]
[占用 2 GB]
[空闲 1 GB]
[占用 2 GB]
[空闲 1 GB]
```

总空闲显存有：

$$ 3\text{ GB} $$

但没有一块连续的：

$$ 3\text{ GB} $$

区域。

如果某个操作需要申请一块连续 3 GB 的内存，就可能失败。

这就是典型的外部碎片问题。

### 15. 为什么 Continuous Batching 会放大问题？

因为不同请求的生命周期非常不规则。

例如：

```text
A：
很快结束。

B：
继续生成 3000 Token。

C：
突然被用户取消。

D：
需要更长上下文。

E：
新加入。
```

KV Cache 不断增长、释放和重新分配。

如果内存管理方式要求大块连续空间，系统就很容易出现碎片化。

而且，显存一旦被低效占用，能够同时容纳的 Request 就会下降。

例如：

原本可以服务 32 个请求。

但因为预留和碎片浪费，只能同时服务 12 个。

即使 GPU 还有计算能力，也无法增加 Batch。

这就是 vLLM 最初希望解决的问题。

### 五、PagedAttention 为什么要借鉴操作系统的 Paging？

### 16. 操作系统中的虚拟内存是什么？

假设某个程序认为：

自己拥有一段连续的内存地址。

例如：

```text
0x0000
0x0001
0x0002
...
```

但真实物理内存未必按照相同顺序排列。

操作系统可以通过：

Page Table。

把逻辑页面映射到不同的物理页面。

例如：

```text
Virtual Page 0 → Physical Frame 7

Virtual Page 1 → Physical Frame 2

Virtual Page 2 → Physical Frame 11
```

对于程序来说：

逻辑地址空间是连续的。

但物理存储位置可以不连续。

这样就提高了内存管理灵活性。

### 17. vLLM 把这种思想用在 KV Cache 上

假设 Request A 拥有 40 个 Token。

我们把它按：

$$ B=16 $$

个 Token 划分成 Block。

于是：

```text
Logical Block 0：
Token 0～15

Logical Block 1：
Token 16～31

Logical Block 2：
Token 32～39
```

总共需要三个逻辑 Block。

但物理 KV Cache 并不要求这三个 Block 连续。

例如：

```text
Logical Block 0 → Physical Block 7

Logical Block 1 → Physical Block 3

Logical Block 2 → Physical Block 20
```

这张映射关系就是：

**Block Table。**

### 18. Attention 怎样通过 Block Table 找到真正的 KV？

假设当前 Token 需要读取历史位置：

$$ t=35 $$

Block Size：

$$ B=16 $$

那么对应逻辑 Block：

$$ b_{\mathrm{logical}} = \left\lfloor\frac{35}{16}\right\rfloor = 2 $$

Block 内部偏移：

$$ o=35\bmod16=3 $$

如果：

```text
Block Table[2] = 20
```

那么实际应该读取：

```text
Physical Block 20
Offset 3
```

因此：

```text
Logical Token Position
          ↓
Logical Block Index
          ↓
Block Table
          ↓
Physical Block ID
          ↓
Offset
          ↓
KV Data
```

这就是 PagedAttention 的基本访问逻辑。

### 19. 这样到底节省了什么？

以前可能要为 Request A 提前预留：

```text
4096 Token
```

现在只需要根据实际增长分配：

```text
16 Token Block
```

当第 17 个 Token 出现时，再申请第二个 Block。

当第 33 个 Token 出现时，再申请第三个。

例如：

```text
16 Token：
1 Block

17 Token：
2 Blocks

32 Token：
2 Blocks

33 Token：
3 Blocks
```

如果一个请求最终需要：

$$ T $$

个 Token，那么分配的容量约为：

$$ B\left\lceil\frac{T}{B}\right\rceil $$

额外浪费少于一个 Block：

$$ W<B $$

对于 $B=16$，最多浪费 15 个 Token 的空间。

这个结论对应单一逻辑序列、标准固定 Block 分配的简化模型。

它不意味着整个实际系统没有其他缓存冗余、元数据或内存浪费。

但相较为每条请求预留很大的最大长度，它已经是非常显著的改进。

### 20. 这是不是意味着 vLLM 把 KV Cache 放到了 CPU 内存？

不是。

**PagedAttention 不等于把 KV Cache 从 GPU 换出到 CPU。**

在最经典的 PagedAttention 设计里，KV Cache Block 仍然可以位于 GPU HBM。

Paging 的关键是：

逻辑位置与物理位置解耦。

它不要求物理 Block 必须在磁盘或 CPU 内存里。

当然，vLLM 后来又发展了：

KV Cache Offloading。

CPU Memory Tier。

远程 KV Cache。

分布式 KV Pool。

但它们属于后来增加的存储层次和传输机制。

不能把这些能力误认为 PagedAttention 原本的定义。

### 六、为什么 PagedAttention 还能让多个请求共享 KV Cache？

### 21. 假设两个请求有相同的 Prefix

例如：

```text
Request A：

System Prompt
+
同一份长文档
+
问题 A
```

以及：

```text
Request B：

System Prompt
+
同一份长文档
+
问题 B
```

它们前面的大部分 Token 完全相同。

如果分别执行 Prefill，就会重复计算：

同一份 System Prompt。

同一份文档。

对应的 Key 和 Value。

这显然有些浪费。

### 22. 为什么不能共享这部分 KV？

其实可以。

因为在满足相同模型权重、位置、相关配置和确定计算条件的前提下，相同 Prefix 对应的 KV 表示可以复用。

所以：

```text
Request A ──┐
            ├── Shared Prefix KV Blocks
Request B ──┘
```

后续不同的 Token 则使用各自的 KV Block。

### 23. Copy-on-Write 为什么重要？

假设两个请求共享某个历史 Block。

如果后续 Request A 需要修改其独有的逻辑状态，就不能直接覆盖共享内容，影响 Request B。

因此，经典 vLLM 设计借鉴了：

**Copy-on-Write。**

即：

在需要写入共享状态时，创建独立副本。

但对于 V1 的 Automatic Prefix Caching，还需要注意：

完整、已缓存的 KV Block 通常可以被当作不可变的共享对象。

后续请求只需要为新的 Token 分配其他 Block。

因此，不应该把 Copy-on-Write 理解成每次生成新 Token 都必须完整复制全部历史 KV。

真正的共享与复制粒度，是由具体 Block 组织和缓存策略决定的。

### 24. 这为什么会提高吞吐？

因为如果多个请求共享历史 Prefix：

就可以减少重复 Prefill 计算。

减少重复存储。

让同样显存容纳更多有效请求。

因此，PagedAttention 的价值并不只是：

减少 Fragmentation。

它还使：

**以 Block 为单位的 KV Sharing**

成为一种更自然的系统能力。

---

### 七、PagedAttention 与 FlashAttention 到底有什么区别？

这是 vLLM 技术史中最容易被误解的地方。

### 25. FlashAttention 在解决什么？

2022 年，Tri Dao 等研究者提出：

*FlashAttention: Fast and Memory-Efficient Exact Attention with IO-Awareness*。

它主要关注：

Attention 计算过程中，GPU HBM 与片上 SRAM 之间的数据搬运成本。

普通 Attention：

$$ \operatorname{softmax}(QK^\top)V $$

如果直接物化很大的 Attention Score Matrix，就可能产生大量 HBM 读写。

FlashAttention 通过：

Tiling。

Kernel Fusion。

Online Softmax。

等技术，减少中间数据的物化与搬运。

它主要优化的是：

**Attention 的实际计算过程。**

### 26. PagedAttention 在解决什么？

PagedAttention 更关注：

不同请求的 KV Cache 怎样分配。

怎样索引。

怎样共享。

怎样支持动态增长。

它主要优化的是：

**Attention 所需 KV 数据的内存布局与访问管理。**

因此：

|  | FlashAttention | PagedAttention |
| --- | --- | --- |
| 主要问题 | Attention 计算的 IO 效率 | KV Cache 的动态存储与访问 |
| 典型对象 | Attention Kernel | Block Table、Paged KV |
| 核心思想 | Tiling、减少 HBM IO | 虚拟内存式 Block 映射 |
| 是否改变数学 Attention | 不改变精确 Attention 结果 | 不改变 Attention 的数学定义 |
| 能否组合 | 可以 | 可以 |

### 27. 为什么现代 vLLM 可以同时使用两者？

因为它们不在同一层解决问题。

vLLM 可以：

使用 Paged KV Block Table 管理缓存。

再调用支持相应 KV 布局的高效 Attention Backend 执行计算。

例如：

FlashAttention。

FlashInfer。

或者特定模型优化的 Attention Kernel。

所以这不是：

```text
FlashAttention
     VS
PagedAttention
```

而更接近：

```text
KV Cache Manager
      ↓
Block Table / Physical KV Layout
      ↓
Attention Backend
      ↓
高效执行 Attention
```

这也是 vLLM 后来能够不断集成新 Attention Kernel 的原因。

PagedAttention 的贡献不要求整个系统永久使用 2023 年那一版 Attention Kernel。

---

### 八、2023 年 vLLM 的真正贡献，为什么不应该简单概括成“发明了 Continuous Batching”？

### 28. 把 Orca、FlashAttention 和 vLLM 放到同一条时间线

2022 年 5 月：

FlashAttention 公开。

它主要解决 Attention 内存读写效率问题。

2022 年 7 月：

Orca 发表于 OSDI。

它提出 Iteration-Level Scheduling 和 Selective Batching。

2023 年 6 月：

vLLM 正式公开发布。

它把 PagedAttention 和动态 Serving 组织成一个高吞吐推理系统。

2023 年 9 月：

PagedAttention 论文公开于 arXiv。

2023 年 10 月：

论文发表于 SOSP 2023。

### 29. 为什么 vLLM 的创新仍然很重要？

因为：

有了迭代级调度，不意味着显存就能够高效管理。

有了高效 Attention Kernel，不意味着可以同时容纳更多请求。

有了 KV Cache，不意味着它就不会产生碎片。

vLLM 的贡献是把：

动态请求调度。

分页式 KV 内存管理。

缓存共享。

高效 Attention 执行。

组织成一套有效的 Serving 系统。

因此，vLLM 的创新并不只是一个独立算法。

它更像一种：

**系统级组合创新。**

这也解释了为什么，PagedAttention 本身并没有改变模型参数，却能够在真实服务场景中获得显著吞吐提升。

原始 SOSP 2023 论文报告的约 2～4 倍改善，是在指定模型、硬件、负载和基线下得到的。

不能把它理解成：

使用 vLLM 后，任何模型都必然快 4 倍。

但它确实证明：

**内存管理可以成为大模型推理系统的核心性能瓶颈。**

### 九、从用户发出请求到 GPU 生成 Token，vLLM 究竟经历了什么？

理解了历史以后，我们开始进入实际源码架构。

### 30. 先看最简单的 Python 调用

```python
from vllm import LLM, SamplingParams

llm = LLM(
    model="Qwen/Qwen3-0.6B"
)

params = SamplingParams(
    temperature=0.7,
    top_p=0.95,
    max_tokens=128,
)

outputs = llm.generate(
    ["请解释什么是强化学习。"],
    params,
)

print(outputs[0].outputs[0].text)
```

这段代码属于：

Offline Inference。

即直接通过 Python 调用 vLLM。

不需要单独启动 HTTP Server。

但背后仍然会创建完整的模型执行和调度机制。

### 31. 一个逻辑请求的完整调用链

可以抽象为：

```text
用户 Prompt
    │
    ▼
Input Processor
    │
    ├── Tokenization
    ├── 参数检查
    └── 生成 Request
    │
    ▼
EngineCore
    │
    ▼
Scheduler
    │
    ├── Waiting Queue
    ├── Running Queue
    └── Token Budget
    │
    ▼
KV Cache Manager
    │
    ├── Prefix Cache Lookup
    ├── KV Block Allocation
    └── Block Table
    │
    ▼
Model Executor
    │
    ▼
GPU Worker
    │
    ▼
Model Runner
    │
    ├── 准备 Input IDs
    ├── 准备 Positions
    ├── 准备 Attention Metadata
    ├── 执行 Forward
    └── 计算 Logits
    │
    ▼
Sampler
    │
    ▼
New Token IDs
    │
    ▼
EngineCore
    │
    ├── 更新 Request 状态
    ├── 检查 EOS / Stop
    └── 下一轮调度
    │
    ▼
Output Processor
    │
    ▼
最终文本
```

这是理解 vLLM V1 的一张核心逻辑图。

其中最重要的组件有三个：

**Scheduler。**

决定本轮执行哪些请求、处理多少 Token。

**KV Cache Manager。**

决定历史状态保存在哪里、是否可以复用。

**Model Runner。**

真正准备张量并驱动 GPU Forward。

### 32. 为什么 Scheduler 和 Model Runner 必须分开？

因为它们解决不同的问题。

Scheduler 决定：

```text
Request A：
本轮执行 1 个 Token。

Request B：
本轮执行 1 个 Token。

Request C：
本轮执行 512 个 Prefill Token。
```

而 Model Runner 需要把这个调度结果转换为真实 GPU 计算。

例如：

```text
input_ids

positions

block_table

query_start_loc

seq_lens
```

然后调用模型。

所以：

Scheduler 负责资源分配。

Model Runner 负责执行。

两者分离，使系统能够独立优化：

调度策略。

与：

计算 Kernel。

### 十、vLLM V1 的 Scheduler 为什么不再严格区分 Prefill 和 Decode？

### 33. Prefill 与 Decode 原本有什么区别？

Prefill：

处理用户已经提供的 Prompt。

例如：

```text
输入 4096 Token
```

通常需要对大量 Token 执行 Forward。

Decode：

在已有 KV Cache 基础上，生成新的 Token。

例如：

```text
新增 1 个 Token
```

两者的计算特征不同。

Prefill 通常更偏向 Compute-Bound。

Decode 在一些低并发设置下更偏向 Memory-Bound。

### 34. vLLM V0 为什么曾经分别处理？

早期系统中：

Prefill。

和：

Decode。

可以拥有不同的调度路径。

这种设计比较容易理解。

但随着功能越来越多，问题出现了。

例如：

Chunked Prefill。

Speculative Decoding。

Prefix Caching。

Async Scheduling。

它们不断模糊原来两个阶段的边界。

### 35. 2025 年 V1 的重要变化

V1 将调度统一为：

**每个 Request 在这一轮需要计算多少新的 Token。**

可以写成：

```python
num_scheduled_tokens = {
    "request_A": 1,
    "request_B": 1,
    "request_C": 512,
}
```

这就是 V1 Scheduler 最重要的设计思想之一。

它不需要在调度输出层面强行写成：

```text
Prefill Batch
```

或者：

```text
Decode Batch
```

而是：

统一描述每个 Request 的计算进度。

### 36. 一个具体例子

假设每轮最多处理：

$$ 1024 $$

个 Token。

也就是：

```python
max_num_batched_tokens = 1024
```

现在：

```text
Request A：
正在 Decode。

Request B：
正在 Decode。

Request C：
还需要 Prefill 4096 Token。
```

Scheduler 可以决定：

```text
A：1 Token

B：1 Token

C：1022 Token
```

这样总共：

$$ 1+1+1022=1024 $$

刚好达到这一轮的 Token Budget。

### 37. 为什么这比严格分开两种 Batch 灵活？

因为同一轮模型执行可以同时包含：

已有请求的 Decode Token。

新请求的部分 Prefill Token。

甚至投机解码产生的候选验证 Token。

因此，Scheduler 不需要把所有请求强行归入相同生命周期阶段。

它只需要回答：

**在当前资源限制下，哪些 Token 值得被计算？**

当然，真实 V1 Scheduler 比这个例子复杂得多。

还涉及：

Priority。

KV Block 可用性。

请求暂停。

LoRA。

多模态输入。

Hybrid Attention。

Speculative Decoding。

外部 KV Connector。

但统一的 Token Scheduling 表达，确实让这些功能更容易被组合起来。

---

### 十一、Chunked Prefill 为什么是一个重要设计？

### 38. 假设一个请求突然带来 100K Token

例如：

```text
Request A：
正在逐 Token 生成回答。

Request B：
突然提交 100K Token 的长文档。
```

如果系统直接一次执行 B 的完整 Prefill，就可能占用比较长的 GPU 执行时间。

这期间：

A 的 Decode 被推迟。

用户可能感觉：

模型原本正在快速输出。

突然停顿了一下。

### 39. 为什么要将 Prefill 切成 Chunk？

Chunked Prefill：

把很长的 Prefill 分成若干较小的计算块。

例如：

```text
100K Token Prompt
        │
        ▼
Chunk 1
        │
        ▼
Chunk 2
        │
        ▼
Chunk 3
        │
        ▼
...
```

这样每一轮可以混合处理：

部分 Prefill。

以及其他请求的 Decode。

### 40. 但 Chunked Prefill 会不会增加开销？

可能。

因为更多执行轮次意味着：

更多调度。

更多 Kernel Launch。

更多中间状态管理。

并且 Attention 仍然需要访问已有 Prefix 的 KV。

所以不能认为：

Chunk 越小越好。

如果 Chunk 太小：

Prefill 吞吐可能下降。

如果 Chunk 太大：

Decode 的尾部延迟可能增加。

因此，Chunk Size 和 Token Budget 需要结合目标负载进行调整。

这是典型的：

**吞吐与延迟之间的权衡。**

### 十二、Automatic Prefix Caching：为什么同一个 Prompt 不应该反复计算？

### 41. 一个很常见的 Agent 场景

假设 Coding Agent 执行：

```text
User：
修复代码仓库中的 Bug。
```

第一轮：

```text
System Prompt
+
Repository Context
+
Assistant Tool Call
```

第二轮：

```text
System Prompt
+
Repository Context
+
Assistant Tool Call
+
Tool Observation
+
新的 Assistant 请求
```

第三轮：

```text
System Prompt
+
Repository Context
+
全部已有历史
+
新的 Observation
```

可以发现：

每一轮都会重新发送大量相同历史。

如果每次都完整 Prefill：

就会不断重复计算已经处理过的 Prefix。

### 42. Prefix Caching 的基本思想

假设两个请求分别是：

```text
Request A：

[A B C D] [E F G H] [X]
```

以及：

```text
Request B：

[A B C D] [E F G H] [Y]
```

假设每个 Block 存四个 Token。

那么：

```text
Block 0：
A B C D

Block 1：
E F G H
```

完全相同。

只有后面：

```text
X
```

和：

```text
Y
```

不同。

因此，前两个 Block 的 KV Cache 可以复用。

### 43. vLLM 怎样确定两个 Prefix Block 相同？

使用 Hash。

可以将其抽象为：

$$ h_i = H(h_{i-1},\mathrm{tokens}_i,\mathrm{metadata}_i) $$

其中：

- $h_{i-1}$：前一个 Block 的 Hash。
- $\mathrm{tokens}_i$：当前 Block 的 Token IDs。
- $\mathrm{metadata}_i$：必要的附加信息。

为什么需要 Parent Hash？

因为：

仅仅当前 Block 的 Token 一样，不代表它们前面的历史一样。

例如：

```text
Prefix A：
天气很好。今天我们讨论模型。

Prefix B：
昨晚下雨。今天我们讨论模型。
```

最后一段 Token 可能相同。

但它们的历史上下文不同。

Attention 得到的 KV 也未必相同。

因此，需要将此前 Prefix 的身份一起编码进 Block Hash。

### 44. 为什么还需要 Metadata？

因为现代模型输入不只是纯文本。

例如：

多模态图片。

LoRA Adapter。

Cache Salt。

甚至其他会影响 KV 计算的配置。

如果两条请求包含不同图片，但使用相同 Placeholder Token：

那么仅 Hash Placeholder Token 会错误地认为它们相同。

所以必须将图片内容身份等信息纳入缓存键。

### 45. 2026 年的 vLLM 为什么真的使用 SHA-256？

这是一个与你前面讨论过的 GPT 喜欢 SHA-256 很有意思的连接。

根据 vLLM 当前的 Automatic Prefix Caching 文档：

从 v0.11 开始，默认缓存 Hash 算法为：

```text
sha256
```

还提供：

```text
sha256_cbor

xxhash

xxhash_cbor
```

等选项。

例如：

```bash
vllm serve MODEL \
  --prefix-caching-hash-algo sha256
```

这里的 SHA-256 不是为了装饰工程。

它有明确的用途：

为 Prefix KV Block 建立内容指纹。

降低缓存键碰撞风险。

尤其在多租户环境中，错误复用其他用户的 KV Cache 可能带来严重问题。

因此，这里采用可靠的 Hash 具有明确的工程意义。

它与 Coding Agent 不分场合地给每个文件添加 SHA-256 校验，不是同一种使用场景。

**好的工程实践不是避免使用复杂工具，而是在真正需要它的地方使用它。**

### 46. Prefix Cache 为什么不能无限增长？

因为 GPU 显存有限。

假设：

```text
Block A
Block B
Block C
```

已经没有活跃 Request 使用。

但系统希望暂时保留它们，以便未来请求复用。

如果显存还足够，就可以继续缓存。

但当新请求需要空间时，就必须回收一部分 Block。

因此，vLLM 使用：

Free Block Queue。

Reference Count。

以及 LRU 风格的缓存回收机制。

### 47. Reference Count 是什么？

假设两个请求共享：

```text
Physical Block 7
```

那么：

```text
ref_cnt = 2
```

如果 Request A 完成：

```text
ref_cnt = 1
```

Request B 仍然在使用。

所以不能回收。

如果 B 也完成：

```text
ref_cnt = 0
```

这个 Block 就可以进入可回收状态。

但它不一定会立刻被物理清空。

如果后续有相同 Prefix 到来，而且 Block 尚未被覆盖，就可以直接复用。

### 48. 为什么 LRU 也不一定适合所有 Agent？

因为 Agent 的下一轮请求可能隔很久才到达。

例如：

```text
LLM 生成工具调用。
       ↓
Sandbox 执行 30 秒。
       ↓
LLM 再次生成。
```

在这 30 秒内，如果 GPU 处理了大量其他请求，那么上一轮的 KV Block 可能已经被回收。

下一轮又需要重新 Prefill。

这就引出了 2026 年 vLLM 的一个重要研究方向：

**跨轮、跨节点的 KV Cache 管理。**

### 十三、2024 年：为什么 vLLM 的瓶颈从 GPU 显存，又转移到了 CPU？

### 49. 2024 年 9 月，vLLM v0.6.0 发生了什么？

vLLM 官方发布：

*vLLM v0.6.0: 2.7x Throughput Improvement and 5x Latency Reduction*。

它对比了：

v0.5.3。

和：

v0.6.0。

在相应 H100 与 Llama 模型的测试设置下，报告了明显的吞吐和延迟改善。

但最有意思的不是加速数字本身。

而是：

**这次优化的主要对象之一，已经从 GPU Kernel 转向了 CPU 侧的请求管理。**

### 50. 为什么 CPU 会成为大模型推理瓶颈？

考虑一次 Decode：

```text
CPU：
准备 Batch。

CPU：
准备输入。

GPU：
执行 Forward。

CPU：
处理输出。

CPU：
更新请求状态。

CPU：
准备下一轮。
```

当 GPU Forward 很慢时，CPU 的这些操作可能不明显。

因为 GPU 本身就需要较长时间。

但随着：

更快的 GPU。

更高效的 Attention Kernel。

Quantization。

CUDA Graph。

模型运行时间越来越短。

CPU 可能来不及及时准备下一轮输入。

于是出现：

```text
GPU 完成计算。
      ↓
等待 CPU 准备下一轮。
      ↓
GPU 空闲。
```

这就很尴尬。

我们本来在努力提高 GPU 性能。

结果 GPU 变快以后，系统却被 CPU 调度拖住了。

### 51. v0.6.0 为什么引入 Multiprocessing？

一个重要方法是：

将 API Server 和推理 Engine 的控制职责拆到不同进程中。

并通过 ZeroMQ 等机制通信。

这样：

HTTP 请求处理。

Tokenization。

输出处理。

Engine 执行。

可以获得更多并行机会。

但这次改造仍然没有彻底解决问题。

因为随着更多功能加入，早期架构的复杂度还在增加。

于是，2025 年的 V1 出现了。

### 十四、2025 年：为什么 vLLM 成功以后，反而决定重新设计 V1？

### 52. 2025 年 1 月 27 日，V1 Alpha 发布

官方博客标题：

*vLLM V1: A Major Upgrade to vLLM’s Core Architecture*。

这次更新不是单纯添加某个新模型。

而是重新设计：

Scheduler。

KV Cache Manager。

Worker。

Sampler。

API Server。

以及 Engine 的执行结构。

### 53. 为什么原来的 V0 不够了？

vLLM V0 在一年多时间里不断增加：

PagedAttention。

Continuous Batching。

Prefix Caching。

LoRA。

Multimodal。

Speculative Decoding。

不同模型架构。

不同 Quantization Backend。

多 GPU 并行。

这些功能单独看都很有价值。

但问题是：

它们往往在不同时间由不同开发者实现。

随着数量增加，功能之间开始产生复杂的耦合关系。

例如：

某种 Speculative Decoding 是否兼容 Prefix Caching？

某种 Model Runner 是否兼容新的 Multimodal Input？

某种异步执行是否兼容特定 KV Cache 布局？

如果每加入一种功能，都需要在多个特殊路径上修改代码，系统就会越来越难维护。

因此，V1 的目标之一是：

**让不同优化机制能够自然地组合，而不是不断添加特殊分支。**

### 54. V1 为什么要把 EngineCore 独立出来？

可以用一张图理解：

```text
API Server Process
        │
        ├── HTTP Request
        ├── Tokenization
        ├── Multimodal Processing
        └── Response Streaming
        │
        ▼
      ZMQ / IPC
        │
        ▼
EngineCore Process
        │
        ├── Scheduler
        ├── KV Cache Manager
        └── Model Executor
                │
                ▼
           GPU Workers
                │
                ▼
           Model Runner
                │
                ▼
             GPU
```

EngineCore 不需要直接负责全部 HTTP 处理工作。

API Server 也不需要在每一步管理 GPU 的 KV Block。

这样可以让：

CPU 的输入输出处理。

Engine 的调度。

GPU 的执行。

更有效地重叠。

### 55. 为什么要使用 Persistent Batch？

假设这一轮：

```text
Batch：
A B C D
```

下一轮：

```text
Batch：
A B D E
```

只有：

C 离开。

E 加入。

其他请求没有变化。

如果每一轮都重新创建全部输入张量、Block Table 和元数据，就会产生不必要的 CPU 开销。

Persistent Batch 的思想是：

保留已有状态。

只更新发生变化的部分。

例如：

```text
上一轮：
A B C D

这一轮：
A B D E

Diff：
Remove C
Add E
```

因此，V1 开始减少每轮重复构造完整 Batch 的开销。

这也成为 2026 年 Model Runner V2 的重要前驱。

### 十五、2026 年：为什么 V1 发布一年以后，又出现 Model Runner V2？

### 56. 2026 年 3 月 24 日，Model Runner V2 发布

官方文章：

*Model Runner V2: A Modular and Faster Core for vLLM*。

这次重构非常有意思。

因为 vLLM V1 本来就是为了减少复杂度。

但 V1 运行一年以后，Model Runner 又积累了新的技术债务。

这说明：

一个推理系统的复杂度并不会因为经历过一次重构，就永远消失。

### 57. Model Runner V1 主要遇到了什么问题？

官方总结了几个问题。

第一：

Persistent Batch State 过于复杂。

第二：

异步执行是后续不断加入的能力。

第三：

大量输入准备仍然依赖 CPU。

第四：

不同模型架构的特殊逻辑不断进入公共执行路径。

尤其是：

Async Scheduling。

Speculative Decoding。

Multimodal。

不同 Attention Backend。

这些功能组合起来，让代码越来越难维护。

### 58. Model Runner V2 的第一个变化：稳定的 Request State

早期 Persistent Batch 的一些状态与当前 Batch 排列绑定得比较紧密。

例如：

```text
Row 0：Request A

Row 1：Request B

Row 2：Request C
```

如果 Request B 完成：

就可能需要重新排列一些张量状态。

但 MRV2 选择：

**将 Request 的长期状态，与每一步真正需要的计算输入分开。**

例如：

```text
Persistent State Table：

Row 0：A
Row 1：B
Row 2：C
Row 3：D
```

每个活跃请求在其生命周期内拥有稳定的状态位置。

当前执行步骤需要什么顺序，就通过 Gather 操作构造对应输入。

这样不需要为了每一轮 Batch 的变化，频繁重排全部持久状态。

### 59. 第二个变化：GPU-Native Input Preparation

以前：

CPU 计算：

```text
input_ids

positions

query_start_loc

seq_lens
```

再复制到 GPU。

MRV2 则尝试直接使用 Triton Kernel 在 GPU 上构造这些输入。

这意味着：

CPU 不必反复执行大量小型 Tensor 操作。

GPU 可以根据已保存的请求状态，直接准备下一轮计算需要的数据。

### 60. 第三个变化：Async-First

MRV2 将异步执行当作基本设计前提。

例如：

```text
CPU：
调度 Step N+1。

GPU：
正在执行 Step N。
```

两者可以重叠。

更重要的是：

某些 Speculative Decoding 的 GPU 输出，可以直接被下一步 GPU 输入准备逻辑消费。

不一定需要先把中间结果同步回 CPU，再重新提交 GPU。

这有助于减少：

CPU-GPU Synchronization。

### 61. 第四个变化：Triton-Native Sampler

例如使用：

Gumbel-Max Sampling。

它可以避免某些场景下显式物化完整 Softmax 概率张量。

还可以优化：

Top-k Logprobs。

Prompt Logprobs。

Speculative Sampling。

这些都与 Model Runner 的实际延迟和显存峰值有关。

### 62. MRV2 为什么不仅仅是代码清理？

2026 年 3 月的官方实验中：

Qwen3-0.6B。

单张 GB200。

MRV2 的吞吐比旧 Runner 提高约 56%。

但这里研究者特意使用一个很小的模型。

因为小模型的 GPU Forward 很快，更容易暴露 CPU Overhead。

因此：

不能将这 56% 当作所有大模型的普遍收益。

### 63. 到 2026 年 10 月，MRV2 已经发展到什么程度？

根据 vLLM v0.29.0 的 Release Notes：

2026 年 9 月，Model Runner V2 已经成为所有模型的默认路径。

不过，部分 ROCm 模型或尚未覆盖的功能仍可能保留旧 Runner 路径。

到 2026 年 10 月 5 日的 v0.31.0，vLLM 继续加强对复杂 MoE、压缩 KV、异构 Attention 和新模型架构的支持。

因此，现在研究 vLLM，不能再简单把：

2025 年 V1 Alpha。

当作当前完整架构。

更准确的技术演化是：

```text
2023：
PagedAttention / V0

2024：
CPU 调度与 Serving 优化

2025：
V1 EngineCore 重构

2026：
Model Runner V2

2026 后期：
更复杂的 MoE、Hybrid Model、
异步执行和 Agentic Serving
```

### 十六、为什么现代 vLLM 的 KV Cache Manager 又变复杂了？

### 64. 因为现代大模型已经不都是 Full Attention

2023 年的 PagedAttention 主要面向典型 Transformer Attention。

但后来出现：

Sliding Window Attention。

Mamba。

Gated DeltaNet。

MLA。

Chunked Attention。

以及多种 Hybrid Architecture。

它们对历史状态的需求不同。

### 65. Full Attention 需要什么？

标准 Causal Full Attention 通常需要访问：

全部仍在有效上下文中的历史 Key、Value。

因此，随着 Token 数量增加，KV Cache 需要持续增长。

### 66. Sliding Window Attention 又需要什么？

假设窗口大小是：

$$ W=4096 $$

那么某一层可能只需要最近：

4096 个 Token。

更早位置的 KV 可以根据该层的机制释放或不再参与当前 Attention。

因此，不能像 Full Attention 一样，为所有历史 Token 永久保留同样的 KV。

### 67. Mamba 为什么又不同？

Mamba 类状态空间模型通常维护一种递归状态。

它的状态组织方式，并不是简单的每 Token 一组 K/V。

因此，Mamba 与 Full Attention 混合时：

不同层的缓存粒度、生命周期和复用条件可能不同。

### 68. 这为什么迫使 KV Manager 改变？

以前可以假设：

```text
所有 Attention Layer
使用相似的 KV Cache 规则。
```

现在：

```text
Full Attention：
保存较完整的历史 KV。

Sliding Window：
主要保存当前窗口。

Mamba：
保存递归状态及必要的辅助状态。

MLA：
可能保存压缩后的潜在表示。
```

因此，vLLM 后来发展了 Hybrid KV Cache Manager。

它需要根据不同层类型，管理不同的状态布局与回收规则。

这说明：

**PagedAttention 的基本分页思想可以保留，但缓存系统必须随着模型架构变化不断演化。**

### 十七、2024—2026 年：为什么 Prefill 和 Decode 开始被拆到不同 GPU？

### 69. 再看两者的计算区别

Prefill：

处理大量 Prompt Token。

通常更强调计算吞吐。

Decode：

连续生成少量新 Token。

往往更强调低延迟、显存带宽和缓存访问。

这两个阶段的硬件利用特征不同。

### 70. 为什么把它们放在同一组 GPU 上会相互干扰？

假设：

Request A 正在 Decode。

每隔几十毫秒需要一次新 Token。

此时 Request B 突然提交 100K Token Prompt。

如果系统让 B 的大规模 Prefill 占用大量 GPU 计算资源，A 的下一 Token 可能被推迟。

这会使：

Time Per Output Token。

出现抖动。

### 71. 2024 年 DistServe 提出了什么？

2024 年，Yinmin Zhong 等研究者发表：

*DistServe: Disaggregating Prefill and Decoding for Goodput-optimized Large Language Model Serving*。

它明确研究：

将 Prefill 和 Decode 放在不同 GPU 资源中。

例如：

```text
Prefill GPU Pool
        │
        │ 计算 Prompt KV
        ▼
     KV Transfer
        │
        ▼
Decode GPU Pool
        │
        ▼
生成后续 Token
```

这样可以分别优化：

TTFT。

和：

TPOT / ITL。

同时减少两种计算之间的干扰。

### 72. 但是为什么不能无条件认为 P/D 分离更快？

因为需要传输 KV Cache。

假设 Prompt 为：

$$ 10000 $$

Token。

每个 Token 的 KV Cache 需要数百 KiB。

那么 Prefill 完成以后，就可能需要将数 GB 的状态传给 Decode 节点。

这个数据传输不是免费的。

所以：

P/D Disaggregation 可能降低计算干扰。

但也增加了网络传输。

到底是否有收益，需要结合：

网络带宽。

模型大小。

上下文长度。

P/D 资源比例。

以及负载情况。

评估。

vLLM 官方文档也专门提醒：

不能把 P/D 分离简单理解成必然提高吞吐。

它最直接的价值之一，是允许分别优化 TTFT 和 ITL，并控制尾部延迟。

### 73. Mooncake 为什么重要？

2024 年，Mooncake 论文公开。

它提出一种：

**KVCache-Centric Disaggregated Architecture。**

即以 KV Cache 为核心组织推理服务。

它不仅分离 Prefill 与 Decode。

还利用 CPU DRAM、SSD 和分布式资源保存大量 KV Cache。

后来 vLLM 逐渐支持 Mooncake 等 Connector。

这使 vLLM 不再只是：

在单张 GPU 上安排 KV Block。

而是开始管理：

**跨 GPU、跨节点、跨存储层次的 KV 生命周期。**

### 十八、2026 年：为什么 Agentic Serving 让 KV Cache 再次成为核心问题？

### 74. 普通聊天与长程 Agent 的区别

普通聊天可能是：

```text
Prompt
   ↓
生成长回答
   ↓
结束
```

而长程 Agent 更接近：

```text
System Prompt
      ↓
LLM Generate
      ↓
Tool Call
      ↓
Tool Observation
      ↓
LLM Generate
      ↓
Tool Call
      ↓
Tool Observation
      ↓
...
```

每一轮都会重新提交一段包含大量历史的 Context。

但真正新增的 Token 可能只有：

几百。

或者几千。

### 75. 为什么这会让 Prefix Cache 特别有价值？

假设第一轮：

```text
Context：
20000 Token
```

第二轮：

```text
Context：
22000 Token
```

其中前：

20000 Token。

基本不变。

如果能够复用对应 KV Cache，那么第二轮主要需要处理新增的：

2000 Token。

而不是重新计算全部：

22000 Token。

第三轮也是类似情况。

因此，Agentic Workload 往往具有非常高的 Prefix Reuse 潜力。

### 76. 2026 年 5 月，vLLM × Mooncake 的实验发现了什么？

vLLM 官方发表：

*Serving Agentic Workloads at Scale with vLLM x Mooncake*。

研究者分析了一组 Coding Agent 轨迹。

其中包含：

610 条轨迹。

每条轨迹中位数约 33 轮。

观察到：

约 94.2% 的 Cache Hit Rate。

输入与输出 Token 比例约为：

$$ 131:1 $$

中位数上下文从约 12K 增长到 80K Token。

这说明：

Agentic Serving 的计算结构，与普通短对话有很大区别。

大量输入 Token 是可以复用的历史。

而每轮真正需要新增的内容比较少。

### 77. 为什么单机 Prefix Cache 又不够？

因为真实系统通常有多个 vLLM Replica。

例如：

```text
Replica A
Replica B
Replica C
Replica D
```

第一轮请求进入：

```text
Replica A
```

它保存了一份历史 KV Cache。

第二轮由于负载均衡，被转发到：

```text
Replica C
```

但 C 从未处理过此前的 Prefix。

于是发生：

Cache Miss。

即使整个集群中已经有一份可用 KV，C 仍然可能重新计算。

### 78. 分布式 KV Pool 解决什么？

Mooncake Store 等机制允许多个实例访问共享的 KV 存储池。

例如：

```text
Replica A ──┐
            │
Replica B ──┤
            ▼
    Distributed KV Pool
            ▲
Replica C ──┤
            │
Replica D ──┘
```

这样，当请求迁移到另一 Replica 时，系统可以尝试从共享池加载历史 KV。

但它又引入新的权衡：

重新计算 KV。

还是通过网络读取 KV。

哪种更快？

如果 KV 很大、网络很慢，传输也可能非常昂贵。

因此，现代 vLLM 需要决定：

缓存放在哪里。

何时迁移。

何时预取。

何时重新计算。

这已经不只是一个普通 Block Allocator 的问题。

### 十九、2026 年 10 月：为什么 P/D 分离又开始支持双向 KV Transfer？

### 79. 传统 P/D 分离存在一个不容易发现的问题

传统流程：

```text
Prefill Node
      │
      │ 计算 Prompt KV
      ▼
Decode Node
      │
      │ 生成新 Token
      ▼
完成本轮
```

Prefill Node 将 KV 传给 Decode Node。

但 Decode Node 随后生成了新的 Token。

这些 Token 对应的新 KV，可能只存在于 Decode Node。

下一轮 Agent 再次请求时：

Prefill Node 未必拥有上一轮生成 Token 的 KV。

于是可能需要重新计算这些部分。

### 80. 为什么双向 KV Transfer 有意义？

2026 年 10 月 12 日，vLLM 发布：

*Improve TTFT for Multi-Turn Agentic Workloads with Bi-Directional KV Transfer in vLLM*。

它允许 Decode Node 保存的历史 KV，在后续轮次中被 Prefill Node 复用。

例如：

```text
Turn 1：

Prefill ──KV──▶ Decode
                  │
                  ▼
             Generate Tokens
                  │
                  ▼
             保存新 KV

Turn 2：

Prefill ◀──历史 KV── Decode
   │
   ▼
只处理新增部分
```

在指定的多轮测试中：

Qwen3-32B 的 TTFT 改善最高约 1.6 倍。

GLM-5-FP8 的 TTFT 改善最高约 3.3 倍。

但这些结果是在具体的 1P1D 部署、网络和缓存配置下测得的。

不能认为所有 Agent 都会获得相同收益。

### 81. 2026 年 10 月 14 日又发生了什么？

vLLM 继续发布：

*Push-Based KV Transfer to Improve TTFT and TPOT for Disaggregated Inference in vLLM*。

它研究：

从传统的 Pull-Based KV Transfer，转向一种 Push-Based 实现。

Pull-Based：

```text
Prefill 完成。
      ↓
Decode 获得源地址信息。
      ↓
Decode 分配目标 Block。
      ↓
Decode 发起读取。
```

Push-Based：

```text
Decode 提前准备目标空间。
      ↓
Prefill 计算完成。
      ↓
Prefill 主动推送 KV。
```

这样可以减少部分串行协调开销。

但它也有代价。

例如：

需要更早确定 Decode 目标节点。

而某些负载均衡策略，可能希望在 Prefill 完成以后才决定 Decode 放在哪里。

因此：

Push 和 Pull 也不是简单的新旧替代。

它们适合不同的部署和路由需求。

### 二十、2026 年 vLLM 为什么开始直接参与 Agentic RL 的数值一致性问题？

### 82. 推理服务对普通聊天来说，只要输出合理就够了吗？

在普通 Serving 中，我们通常主要关心：

速度。

输出质量。

显存。

稳定性。

但强化学习还有一个额外问题：

**Rollout 时执行的 Policy，是否与训练时计算 Log Probability 的 Policy 一致？**

假设：

Rollout 使用 vLLM。

训练使用 Megatron。

虽然两边模型权重相同，但可能使用：

不同 Kernel。

不同 Precision。

不同 Parallel Layout。

不同 MoE Routing 实现。

甚至不同的数值舍入方式。

因此：

$$ \pi_{\mathrm{rollout}} $$

未必严格等于：

$$ \pi_{\mathrm{train}} $$

这就是 Train–Inference Mismatch。

### 83. 为什么这种差异可能影响 RL？

例如，某个 Token 在 Rollout 端的 Log Probability 为：

$$ \log\pi_{\mathrm{rollout}}(a\mid s) $$

但训练端重算得到：

$$ \log\pi_{\mathrm{train}}(a\mid s) $$

如果存在差异：

$$ \Delta = \log\pi_{\mathrm{rollout}} - \log\pi_{\mathrm{train}} $$

那么即使参数没有发生更新，某些 Importance Ratio 也可能偏离 1。

对于 PPO/GRPO，这会影响：

概率比率。

Clipping。

KL。

以及梯度估计。

### 84. 2026 年 10 月 14 日的工作为什么重要？

vLLM 官方发布：

*Finish RL Training Faster: Bitwise-Consistent, High-Performance, Agent-Driven*。

它研究让：

推理侧 Forward。

和：

训练侧 Forward。

在特定模型和配置下产生 Bitwise-Identical Log Probability。

也就是：

$$ \Delta=0 $$

研究者针对 DeepSeek-V4-Flash 和 Nemotron 等模型进行了实验。

在特定 DeepSeek-V4-Flash 训练设置中，报告：

保持 Log Probability 差异为 0。

同时保留约 91.3% 的高性能 Rollout Baseline 吞吐。

但是这里必须注意：

这不是说 vLLM 所有模型、所有 GPU、所有分布式布局都已经默认实现严格 Bitwise Consistency。

这是一项模型相关、Kernel 相关的工程研究。

论文也承认，完整端到端训练时间收益仍然需要更长期实验验证。

### 85. 为什么这对 vLLM 的技术史非常重要？

因为 vLLM 的目标正在发生扩展。

2023 年：

怎样让更多请求共享 GPU？

2025 年：

怎样减少调度和运行开销？

2026 年：

怎样让长程 Agent 高效复用历史？

怎样让不同节点共享 KV？

怎样让 RL Rollout 的数值行为与训练保持一致？

这些问题已经超出了最初的 PagedAttention。

但它们具有一条共同主线：

**将推理执行过程中原本容易被视为工程细节的状态、调度与数值行为，提升为系统设计的核心问题。**

### 二十一、为什么 vLLM 并不总比 SGLang、Transformers 或其他推理系统更快？

### 86. 一个非常常见的误解

有人认为：

vLLM 使用了 PagedAttention。

所以一定比其他框架快。

这当然不成立。

因为推理性能取决于：

模型架构。

GPU 型号。

Batch Size。

上下文长度。

输出长度。

KV Cache Hit Rate。

Quantization。

Speculative Decoding。

通信。

Attention Backend。

以及请求到达分布。

### 87. SGLang 为什么同样非常重要？

2023 年 12 月，Lianmin Zheng、Ying Sheng 等人公开 SGLang。

后来发表于 NeurIPS 2024。

它的重要贡献之一是：

**RadixAttention。**

它更加直接地针对：

复杂 LLM Program 中的 Prefix Sharing。

特别是：

多轮生成。

分支调用。

结构化输入输出。

以及动态复用历史上下文。

因此，SGLang 并不是一个简单的“另一个 vLLM”。

它拥有不同的历史出发点和系统抽象。

但经过不断发展，vLLM 和 SGLang 的功能已经高度重叠。

两者都支持：

高吞吐推理。

Prefix Caching。

分布式 Serving。

Speculative Decoding。

结构化生成。

复杂模型架构。

### 88. 那么到底应该选择哪个？

不应该只看某篇论文中最大的 Speedup。

而应该针对真实工作负载测试。

例如：

如果你要训练 Coding Agent RL，可能需要关心：

多轮工具调用的请求形状。

Prefix Cache 命中率。

Train–Inference Mismatch。

权重同步。

GPU Colocation。

Rollout Throughput。

以及特定模型的推理 Kernel。

如果你只做离线 Batch 推理，则可能更关注：

整体 Tokens / Second。

GPU 利用率。

总成本。

因此：

**推理系统的选择，已经越来越像一个真实工作负载下的系统工程决策，而不只是比较两个框架的宣传 Benchmark。**

### 二十二、vLLM 的性能到底应该怎样评价？为什么不能只看 Tokens/Second？

### 89. TTFT：Time To First Token

用户提交请求以后，到第一个输出 Token 返回所需时间。

例如：

```text
Request Arrival：0 ms

First Token：500 ms
```

那么：

$$ TTFT=500\text{ ms} $$

它通常受到：

Queueing。

Tokenization。

Prefill。

KV Transfer。

以及首次生成开销影响。

### 90. TPOT：Time Per Output Token

可以理解为：

生成阶段每个输出 Token 的平均耗时。

例如：

一个请求首 Token 以后，又生成 99 个 Token。

花费 1980 ms。

那么后续平均：

$$ TPOT = 1980/99 = 20\text{ ms} $$

不同 Benchmark 对 TPOT 的具体统计可能略有区别，应以测试工具定义为准。

### 91. ITL：Inter-Token Latency

相邻输出 Token 之间的时间间隔。

例如：

```text
Token 1：500 ms
Token 2：520 ms
Token 3：540 ms
Token 4：600 ms
```

对应 ITL：

```text
20 ms
20 ms
60 ms
```

虽然平均速度可能不错，但第三次间隔明显偏长。

用户就可能感觉输出发生了卡顿。

### 92. Throughput：吞吐

例如：

```text
整个系统每秒输出 10000 个 Token。
```

但需要注意：

这是所有请求合计的吞吐。

不等于单个用户每秒能够看到 10000 个 Token。

### 93. Goodput：满足 SLA/SLO 的有效吞吐

假设系统每秒能够处理 100 个请求。

但其中只有 60 个能够在目标延迟内完成。

那么真正满足服务质量要求的请求数，可能只有：

60 个。

因此，Goodput 更关心：

**在延迟约束得到满足的情况下，系统究竟能完成多少有效工作？**

这也是后来 DistServe、Mooncake 和大规模 vLLM Serving 越来越重视的问题。

### 94. 为什么优化吞吐，有时会损害单用户体验？

因为更大的 Batch 可能提高 GPU 利用率。

但同时：

等待队列可能变长。

Prefill 和 Decode 可能相互干扰。

某些用户的 TTFT 或 TPOT 可能上升。

所以系统优化并不只有一个方向。

通常需要在：

Latency。

Throughput。

GPU Cost。

KV Cache Hit Rate。

SLO。

之间进行权衡。

### 二十三、怎样在本地真正运行 vLLM？

### 95. 最简单的在线 Serving

假设已经正确安装 vLLM，并准备好了兼容的 GPU 环境。

可以执行：

```bash
vllm serve Qwen/Qwen3-0.6B \
  --host 127.0.0.1 \
  --port 8000
```

这个命令会启动一个推理服务。

模型会被加载到相应设备上。

vLLM 启动 EngineCore 和 Worker。

并通过兼容 OpenAI API 的接口对外提供生成服务。

### 96. 为什么它可以使用 OpenAI-Compatible API？

因为 API 规范和底层模型实现不是同一回事。

例如客户端可以调用：

```text
POST /v1/chat/completions
```

请求体中包含：

```json
{
  "model": "Qwen/Qwen3-0.6B",
  "messages": [
    {
      "role": "user",
      "content": "解释什么是 PPO"
    }
  ]
}
```

vLLM 接收请求后：

处理 Chat Template。

进行 Tokenization。

调用模型推理。

再将结果包装成兼容的响应结构。

这并不表示使用了 OpenAI 的远程模型。

它只是提供类似的服务接口。

### 97. 如何使用 Python 客户端？

```python
from openai import OpenAI

client = OpenAI(
    base_url="http://127.0.0.1:8000/v1",
    api_key="EMPTY",
)

response = client.chat.completions.create(
    model="Qwen/Qwen3-0.6B",
    messages=[
        {
            "role": "user",
            "content": "解释什么是 PPO",
        }
    ],
    max_tokens=256,
)

print(response.choices[0].message.content)
```

这里：

```python
base_url
```

指向本地 vLLM Server。

客户端使用 OpenAI SDK，只是为了复用通用 API。

### 98. 怎样控制 GPU 资源和 Batch？

例如：

```bash
vllm serve Qwen/Qwen3-0.6B \
  --gpu-memory-utilization 0.85 \
  --max-num-seqs 64 \
  --max-num-batched-tokens 4096
```

这里：

`gpu-memory-utilization`

控制 vLLM 为自身使用的 GPU 显存预算比例。

`max-num-seqs`

限制一次模型执行中允许的 Sequence 数量上限。

`max-num-batched-tokens`

限制一次调度步骤能够安排的 Token 数量上限。

这些都是资源与调度参数。

它们不能直接理解成：

设置越大，速度越快。

例如：

较大的 Token Budget 可能提高 Prefill 效率。

但也可能增加某些场景下的 Decode 尾部延迟。

因此，真实参数需要根据工作负载调整。

### 二十五、结语：vLLM 的历史，为什么最终不再只是一个 KV Cache 的故事？

回头看这段历史，会发现 vLLM 的发展比它最初的 PagedAttention 论文复杂得多。

2022 年，Orca 已经指出：

大语言模型的请求不应该永远以完整 Request 为单位调度。

因为自回归生成天然具有迭代结构。

于是，Iteration-Level Scheduling 开始改变传统 Batch Serving 的方式。

但动态调度又暴露出新的问题。

当请求不断加入、完成和增长时，KV Cache 会持续变化。

如果依然使用传统的连续大块分配方式，就会出现显著的内存浪费。

于是，2023 年的 vLLM 借鉴操作系统的 Paging 思想。

将逻辑 KV Block 与物理 KV Block 分离。

让请求可以按需增长。

让多个请求共享历史。

让有限显存容纳更多并发任务。

这项工作证明：

**大模型推理的性能，不只由 Transformer 的数学计算复杂度决定，还受到内存管理和请求生命周期的深刻影响。**

但 vLLM 成功以后，新问题又出现了。

GPU Kernel 越来越快。

CPU 调度、输入准备和请求管理却开始成为新的瓶颈。

因此，2024 年的 v0.6.0 开始重新组织 CPU 与 GPU 之间的执行关系。

2025 年的 V1，又进一步将 Scheduler、KV Cache Manager、Model Runner 和 API Server 重新拆分与统一。

原本分散实现的优化机制，开始被纳入更加一致的系统架构。

但 V1 也并没有一劳永逸地解决全部问题。

随着 Async Scheduling、Speculative Decoding、Hybrid Model 和复杂 Sampling 功能增加，Model Runner 再次积累技术债务。

于是，2026 年的 MRV2 又把大量输入准备从 CPU 移到 GPU，并以异步执行和模块化状态管理为基础重新设计计算路径。

与此同时，LLM 的应用场景也发生了变化。

过去，一次推理通常是：

```text
一个 Prompt
    ↓
一段 Response
    ↓
结束
```

现在，越来越多模型被放进长程 Agent 系统：

```text
Prompt
    ↓
Generate
    ↓
Tool
    ↓
Observation
    ↓
Generate
    ↓
Tool
    ↓
Observation
    ↓
...
```

一次 Agent 任务可能持续几十分钟。

Context 不断增长。

但每一轮真正新增的 Token 可能只是历史的一小部分。

于是，历史 KV Cache 逐渐不再只是单次 Request 的内部缓存。

它开始成为：

跨轮。

跨进程。

跨 GPU。

跨节点。

甚至跨存储层次。

的一种可管理计算资源。

2026 年的 Mooncake Integration、AgentX Optimization、Bi-Directional KV Transfer 和 P/D Disaggregation，正是这种变化的具体体现。

更有意思的是，当 vLLM 被用于 Agentic RL 时，它还开始进入另一个过去容易被当成训练算法内部问题的领域：

Train–Inference Consistency。

因为在强化学习中，模型实际采样过什么，以及训练时计算的概率是否忠实于这一采样过程，直接关系到 Policy Gradient 的正确性。

这意味着：

vLLM 已经不只是负责让模型尽快输出 Token。

它还在越来越多地参与决定：

真实运行的推理策略究竟是什么。

因此，vLLM 的技术史不能简单写成：

一项 PagedAttention Kernel 从 2023 年一直优化到今天。

它真正的发展路线更接近：

```text
2022：
解决请求的迭代级调度
          ↓
2023：
解决 KV Cache 的动态内存管理
          ↓
2024：
解决 CPU 与 GPU 的执行协调
          ↓
2025：
统一 Scheduler、Model Runner 和 KV 管理
          ↓
2026：
进一步减少 CPU Overhead，
支持复杂模型状态，
发展跨轮与跨节点 KV 管理，
并开始处理 RL 的数值一致性
```

每一次变化，背后都不是抽象地追求更好的软件架构。

而是新的模型、新的硬件和新的任务结构，让上一代系统的某个默认假设不再成立。

最初，研究者以为：

只要 GPU 的 Attention 算得足够快，大模型 Serving 就能足够快。

后来发现：

即使 Attention 很快，KV Cache 的碎片也能限制吞吐。

解决显存问题以后，又发现：

CPU 调度可能成为瓶颈。

解决 CPU 调度以后，又发现：

长程 Agent 的历史 KV 不能一直局限在一个 GPU 实例里。

再进一步，当推理被用于 RL，研究者又发现：

推理的数值实现本身，可能影响真正正在优化的 Policy。

所以，如果一定要给 vLLM 的技术思想史留下一个结论，我认为应该是：

**vLLM 最初证明了操作系统的内存管理思想可以决定大模型推理性能，而它后来的演化进一步证明：当模型越来越大、任务越来越长、执行越来越复杂时，真正需要优化的已经不只是一次 Forward，而是整个智能体计算过程中的状态、调度、通信与数值一致性。**

PagedAttention 仍然重要。

但它已经不再足以定义今天的 vLLM。

今天的 vLLM，更像一套不断演化的大模型执行系统。

它试图回答的核心问题，也已经从：

**怎样让更多 Token 放进 GPU？**

扩展成：

**怎样让昂贵的计算资源，尽可能少地重复已经做过的工作，同时又能够可靠、高效地完成新的工作？**

这或许才是 vLLM 从一项系统论文，逐渐成为前沿大模型基础设施的重要原因。
