在本系列的第二篇文章中介绍了两类经典的流水线并线算法：GPipe 和 PipeDream。在 GPipe 和 PipeDream 中，它们对流水线调度的最小单元是单个 micro-batch（或 batch）中的 Forward Pass 和 Backward Pass。但实际上，我们可以将 Backward Pass 拆分的更细以设计更细粒度的调度算法。

![](https://pic3.zhimg.com/v2-03e33e9ca4f7ddbc94246db86b5dc27a_r.jpg)
*图 1 MLP 的 Forward 和 Backward 示意图*

图 1 是一个单层 MLP 的 Forward 和 Backward 示意图。$\boldsymbol x$ 是该 MLP 的输入，$\boldsymbol W$ 是参数矩阵，$\sigma$ 是激活函数。记 Forward 输出 $\boldsymbol y = f(\boldsymbol W,\boldsymbol x) = \sigma(\boldsymbol W \boldsymbol x)$，那么在 Backward 阶段，我们需要计算两个梯度：

- $\nabla_x L$：这是关于输入 $\boldsymbol x$ 的梯度，用于将梯度回传到前一层，对应于图 1 Backward Pass 中直线回传的橙红色部分（将其称为 **B**）。
- $\nabla_{\boldsymbol W} L$：这是关于参数 $\boldsymbol W$ 的梯度，用于更新参数 $\boldsymbol W$，对应于图 1 Backward Pass 中右侧参数更新的部分，将其称为 **W**。

在标准的 Backward 计算实现中，一般是先计算完上述两个梯度，然后再将 $\nabla_x L$ 回传到前一层。但这种做法产生了完全没有必要的依赖关系：上一层的 Backward 计算原本只依赖于 $\nabla_x L$，但实现中必须要等 $\nabla_{\boldsymbol W} L$ 也计算完后才能拿到 $\nabla_x L$。

本文要介绍的 Zero Bubble 算法将 Backward Pass 拆分为两个独立的部分：**B** 和 **W**，并且在调度时让上一层的 B 不再依赖于当前层的 W。因此整个流水线的调度粒度就从之前的 Forward + Backward 变成了 Forward + **B** + **W**，粒度上更细，也就更容易进行极致优化。

本文的主要内容包括：

- **PART 1**：介绍 Zero Bubble 算法，该算法通过将 Backward Pass 拆分为粒度更细的 **B** 和 **W** 两个部分，实现了相比于 GPipe 和 PipeDream 更细粒度的调度策略，在理想情况下可以达到几乎无 Bubble 的性能表现（所以称为 Zero Bubble）。
- **PART 2**：介绍 DeepSeek-V3 提出的 DualPipe 算法。该算法结合了 Zero Bubble 的细粒度拆分思想与双向流水线设计，针对 MoE 架构中的专家并行（EP），实现了计算与跨节点 All-to-All 通信的极致重叠。

## 1. Zero Bubble

作为对比，先将之前介绍过的 1F1B PipeDream 的调度策略绘制如下。

![](https://pic3.zhimg.com/v2-880b91cd385555780fdf2316e5a04c10_r.jpg)
*图 1.1 1F1B PipeDream 示意图*

1F1B PipeDream 的基本思路是只要当 Backward 的前置条件满足时（上一层的梯度计算完成），就立即开始进行 Backward 的计算，这样可以尽可能减少 Activation 保存的时间，降低显存开销。注意在图 1.1 中，一般会假设 Backward 的耗时是 Forward 的 2 倍，这是因为每一层的 Backward 包含两次矩阵乘法计算，而 Forward 只包含一次矩阵乘法计算，因此可以初略的按照两倍来估计（参考图 1）。从图 1.1 可以看出，1F1B PipeDream 的调度单元是 Forward（蓝色块）和 Backward（橙色块），并且即使整个流水线在进入稳定状态后，也会存在 Bubble。

Zero Bubble 将 Backward Pass 拆分为 **B** 和 **W** 两个部分，实现了更细粒度的调度策略，如图 1.2 所示。

![](https://pic1.zhimg.com/v2-b07fb44c17eb2531f4af0bbb58481216_r.jpg)
*图 1.2 Zero Bubble 示意图*

图 1.2 的上图调度策略称为 ZB-H1，下图调度策略称为 ZB-H2。ZB-H1 的基本思路就是 1F1B，只不过这里的 B 不再是整个 Backward，而是图 1 中的 **B** 那部分。因为 **W** 这一部分即使计算不及时，也不会对前一层的 **B** 计算产生影响，所以可以先放一放，专门用来“填空”，降低整个流水线中的 Bubble。ZB-H1 的策略和 1F1B 非常相似，因此它们的显存开销也大体接近。

ZB-H2 则是以更高的显存开销来换取更少的 Bubble，它的核心策略是**尽可能将 $W$ 放在最末端进行计算**，这样可以保证整个流水线在进入稳定阶段后几乎没有 Bubble。但是因为 ZB-H2 会在 Backward 之前进行更多的 Forward，所以需要保存的 Activation 也会更多，因此显存开销更大。

ZB-H1 和 ZB-H2 都是基于 Forward、B 和 W 的时间开销相同的假设而人工手动设计得到。但实际中该假设并不成立。因此 Zero Bubble 提供了自动化设计调度策略的方法，这两种方法分别是：

- 一种基于规则的启发式方法。
- 一种基于动态规划的方法。

因为这两种方法都太过**特例化**，所以本文不再详细介绍。

## 2. DualPipe

DualPipe 是 DeepSeek V3 中提出的一种流水线并行算法，它利用了 Zero Bubble 的主要思想，并着重针对 MoE 模型进行了优化。下面从 MoE 模型并行化的一些特殊问题开始讲起。

### 2.1 MoE 模型中的专家并行

本小节以 DeepSeek V3 为例，来介绍 MoE 模型中专家并行的基本思路和一些与 Dense Model 并行相比存在的不同问题。DeepSeek V3 中的 Expert 包含 $N_s$ 个共享 Expert 和 $N_r$ 个路由 Expert（路由 Expert 就是指需要被选择的 Expert）。共享 Expert 是对所有 Token 始终都会激活的 Expert，而路由 Expert 会由门控机制来根据当前 Token $\mathbf{u}_t$ 进行选择性激活：

$s_{i,t} = \text{Sigmoid} (\mathbf{u}_t^T \mathbf{e}_i) \tag{2.1} $

其中 $\mathbf{e}_i$ 是第 $i$ 个 Expert 的门控向量。$s_{i,t}$ 可以看作是第 $i$ 个 Expert 对当前 Token $\mathbf{u}_t$ 的“**适应度**”。基于 $s_{i,t}$ 从高到低排序，可以从中选择 $K_r$ 个适应度最高的路由 Expert:

$g'_{i,t} = \begin{cases} s_{i,t}, & s_{i,t} \in \text{Topk}(\{s_{j,t} \vert{} 1 \leqslant j \leqslant N_r\}, K_r), \\ 0, & \text{otherwise}, \end{cases} \tag{2.2} $

再通过 $g'_{i,t}$ 来计算归一化概率 $g_{i,t}$：

$g_{i,t} = \frac{g'_{i,t}}{\sum_{j=1}^{N_r} g'_{j,t}} \tag{2.3} $

最后得到完整输出：

$\mathbf{h}'_t = \mathbf{u}_t + \underbrace{\sum_{i=1}^{N_s} \text{FFN}_i^{(s)} (\mathbf{u}_t)}_{\text{Shared experts}} + \underbrace{\sum_{i=1}^{N_r} g_{i,t} \text{FFN}_i^{(r)} (\mathbf{u}_t)}_{\text{Routed experts}} \tag{2.4} $

MoE 模型的一种并行化策略是将 Expert 放到不同的计算节点上以此来降低单卡/单个节点的显存开销。例如在 DeepSeek V3 中，每个网络层包含 256 个 Routed Experts，它们被划分到了 8 个计算节点上，每个节点包含 32 个 Routed Expert。每个节点上的 32 个 Routed Expert 又平均分到每张 GPU 上，每个 GPU 上有 4 个 Routed Expert。这就是 DeepSeek V3 原文中提到的 64 路（8节点 * 8 卡） Expert 并行的策略。

对于上述 64 路 Expert 并行的策略，每个 GPU 上都会存放所有 256 个 Routed Expert 的门控向量 $e_{i}$。因此任一 GPU 都可以对它当前的 Token $\mathbf{u}_t$ 独立计算 $g_{i,t}$，而不依赖其它 GPU。当每个 GPU 计算完它们 Token 所对应的 Expert 后，就需要将 Token 的 Hidden State 发送给对应的 Expert 进行计算。从宏观视角来看，这意味着每个 GPU 都需要将一些数据（Token 的 Hidden State）发送给其它多个 GPU（Expert 所在的 GPU），这种通信模式通常被定义为 All-to-All。

从逻辑上看，我们可以将这一次通信看作是多个**点对点**通信。例如 GPU1 会将 Token 的 Hidden State 发送给 GPU2、GPU3，而 GPU2 会将 Token 的 Hidden State 发送给 GPU4，诸如此类。如果按照这种点对点通信模式，我们通常只能手动去写一个串行的通信逻辑，来保证整个通信过程不会因为资源抢占（每个 GPU 都抢着发送数据）、大流量等问题导致通信效率低下。而 All-to-All 是一个底层的通信原语，它专门用来应对这种存在**全局交叉数据传输的极端情况**。

理解了 All-to-All 通信模式后，容易看到在专家并行中存在两次 All-to-All 通信：

- Dispatch（分发阶段）：All-to-All 通信发生在每个 GPU 计算完它们 Token 所对应的 Expert 后，需要将 Token 的 Hidden State 发送给对应的 Expert 进行计算。
- Combine（合并阶段）：All-to-All 通信发生在每个 Expert 完成计算后，需要将计算结果发送回对应的 GPU 进行合并。

在大规模跨节点的集群中，All-to-All 都是灾难级的通信模式，因此要尽可能避免 All-to-All。

### 2.2 Computation-Communication Overlap

![](https://pic1.zhimg.com/v2-c55920dd226d4e7a0b3802f6148e5008_r.jpg)
*图 2.1 Computation-Communication Overlap 示意图*

虽然 All-to-All 通信成本非常高，但在 MoE 模型中却很难能够将它彻底消除。为了缓解这一问题，一种常见的策略是 Computation-Communication Overlap，即在通信的同时进行计算，从而尽可能隐藏通信延迟。

DualPipe 中将 Forward 的计算在逻辑上分成了四个独立部分：

- Attention：计算 Attention 的输出。
- All-to-All Dispatch：将 Token 的 Hidden State 发送给对应的 Expert 进行计算。
- MLP：计算 Expert 的输出。
- All-to-All Combine：将 Expert 的计算结果发送回对应的 GPU 进行合并。

对于 Backward 部分，则借鉴了 Zero Bubble 中细粒度的调度方法，将 Attention 和 MLP 进一步拆分成了 Attention for Input（**B**） 和 Attention for Weight（**W**）。下面结合图 2.1 来对 Computation-Communication Overlap 的策略进行说明。

以计算流的视角来看（图 2.1 中上面那一行），当前的 Backward 和 Forward 针对的是两个不同的 Micro-batch。为了简化表述，假设 Backward 对应的批次为 c，forward 对应的批次为 d。那么整个 Computation-Communication Overlap 的过程如下：

- **Computation 1 & Computation 2**：对 Micro-batch c 的 MLP 依次执行 **B** 和 **W** 的 Backward 计算，对应于图 2.1 中的 $\text{MLP(B)}$ 和 $\text{MLP(W)}$。
- **Communication 1**：对 Micro-batch d 的 Token 进行 Dispatch，将各个 Token 发送给对应的 Expert，对应于图 2.1 中的 $\text{DISPATCH(F)}$。
- **Computation 3**：在 Computation 2 的 $\text{MLP(W)}$ 完成后，因为此时对于 Micro-batch d 而言，它的 Token 都已经分配给了对应的 Expert（Communication 1 已完成），所以可以立即执行 Micro-batch d 的 MLP，对应于图 2.1 中的 $\text{MLP(F)}$。
- **Communication 2**：在 Communication 1 结束后，因为 Micro-batch c 的 MLP 中对输入的 Backward 计算已经完成（Computation 1 的 $\text{MLP(B)}$），因此可以将梯度 Dispatch 回对应的 GPU，对应于图 2.1 中的 $\text{DISPATCH(B)}$。
- 在上述三个 Computation 步和两个 Communication 步结束后，会插入一个强制的同步操作（图 2.1 中的红色区域），来确保后续的时序依赖不会出问题。
- **Computation 4 & 5**：因为模型的前向计算是先 Attention 再 MLP，所以反向过程就是先 MLP 再 Attention。此时 MLP 的梯度已经回传至对应的 GPU（Communication 2 已完成），所以计算上可以依次执行 Micro-batch c 的 Attention 部分的 Backward 计算，对应于图 2.1 中的 $\text{ATTN(B)}$ 和 $\text{ATTN(W)}$。
- **Communication 3**：在完成 Micro-batch d 的 MLP 计算后，需要进行一次 Combine 操作，对应于图 2.1 中的 $\text{COMBINE(F)}$。注意到，因为 Communication 3 严格依赖于 Computation 1，所以需要在它们之间插入一个同步操作，确保 Communication 3 在执行之前，Computation 1 已经完成。Computation 4 与 Communication 2 的关系类似。
- **Communication 4**：对于一个 Transformer Block 的计算，它始于 Attention，结束于 MLP 之后的 Combine。因此对于 Micro-batch d，当它对应的 Communication 3 结束后，这意味着 Micro-batch d 在某个 Transformer Block 的计算就结束了。在流水线并行下，因为不同的 Layer 组放在不同的机器上，所以某些 Transformer Block 之间会存在 PP（Point-to-Point）通信，这对应于图 2.1 中的 PP 紫色块部分。
- **Computation 6**：在 Communication 4 完成后，Micro-batch d 被送到下一个 Transformer Block，从 Attention 开始进行新的 Block 计算，对应于图 2.1 中的 $\text{ATTN(F)}$。
- **Communication 5**：因为在一个 Block 前向计算中，完整流程是 Attn、Dispatch、MLP、Combine，而图 2.1 中的反向是从 MLP 开始的，所以当 Attn 反向结束后，自然就是 Combine 的反向，对应于图 2.1 中的 $\text{COMBINE(B)}$。

上述 Computation-Communication Overlap 过程是人工精心设计的模式，它和模型结构、硬件性能都有很大关系，并不具备严格意义上的通用性。在实际中，需要通过控制 CUDA 算子的计算行为来精细化控制计算时间与通信时间的关系，从而拼凑出如图 2.1 所示的模式。

### 2.3 DualPipe 的调度策略

![](https://pica.zhimg.com/v2-e1f7827b306b5b157d87ed0d5715925a_r.jpg)
*图 2.2 DualPipe 的调度策略示意图*

DualPipe 的完整调度策略如图 2.2 所示，其中有两个比较关键的设计：

- 首先，除了一个从 Device 0 到 Device 7 的流水线进程外，还有一个从 Device 7 到 Device 0 的反向流水线进程，从而实现双向流水线，这也是 DualPipe 中 “Dual” 一词的由来。在图 2.2 中，正向流水线中的 Micro-batch 使用了通常的数字编号，而反向流水线因为和正向流水线完全对称，所以忽略了它的编号。双向流水线的好处在于它有完全对称的两个 Micro-batch 在运行，因此更容易凑出图 2.1 所示的 Computation-Communication Overlap（注意图 2.1 中是有两个 Mircro Batch，如果只有单向流水线，拼凑 图 2.1 的 overlap 就比较困难）。
- 其次，DualPipe 调度中充分利用了 Computation-Communication Overlap 的策略，将 Forward 和 Backward 的计算与 All-to-All 通信进行重叠，从而尽可能隐藏通信延迟，提高整体训练效率。图 2.2 中的无黑色实线分割的黄色块和绿色块表示一个 Computation-Communication Overlap 的整体单元（即图 2.1 所示的计算与通信重叠的模式；因图较小，所以需要放大看）。

综合上述两点来看，DualPipe 在策略上相比于 Zero Bubble 粒度更细了（不仅在流水线的粒度上进行了优化，还在计算与通信的重叠上做了精细的调度）。

### 2.4 跨节点 All-to-All 的通信优化

最后这部分将简要介绍 DeepSeek-V3 中对跨节点 All-to-All 通信的优化方法。DeepSeek-V3 使用的是 H800 GPU 集群，单个节点内 GPU 之间的单向通信（NVLink）速率为 160GB/s，而跨节点的 IB 通信速率只有 50GB/s，NVLink 约为 IB 的 3.2 倍。

因此，在跨节点 All-to-All 通信中，通信瓶颈主要集中在 IB 链路上。DeepSeek-V3 通过以下几种方式对跨节点 All-to-All 通信进行了优化：

- 限制跨节点路由数。在 DeepSeek-V3 中，每个 Token 会从 256 个 Routed Experts 中选择 8 个进行路由。在极端情况下，如果这 8 个 Expert 分布在不同的节点上，就会产生大量的跨节点通信。因此一种直接的解决方案强制约束每个 Token 选择的 Expert 尽量集中在同一节点上，从而减少跨节点通信的数量。在 DeepSeek-V3 中，每个 Token 的 Expert 选择被限制最多分布在 4 个节点上。
- IB 直连。如果节点 A 的 GPU0 需要将数据传输给节点 B 的 GPU2，那么 DeepSeek-V3 的做法是首先让节点 A 的 GPU0 通过网卡 0 直接将数据发送给节点 B 的 GPU0，然后在节点 B 内部再通过 NVLink 由 GPU0 转发给 GPU2。这样做的一个直观好处是：如果节点 A 的 GPU0 有一个 Token 要同时发给节点 B 上的 3 个不同专家（分别在节点 B 的 GPU1、GPU2、GPU5），通过这种两级转发设计，节点 A 的 GPU0 只需要通过 IB 向节点 B 的 GPU0 发送 1 次该 Token，随后在节点 B 内部利用高带宽的 NVLink 广播给 GPU1/2/5。这样可以大幅降低 IB 链路的通信量。

## 3. 总结

本文介绍了细粒度的流水线并行算法 Zero Bubble 和 DeepSeek V3 中基于 Zero Bubble 思想设计的 DualPipe。当流水线并行算法开始涉及需要像 DualPipe 那样做极致的 Computation-Communication Overlap 时，算法本身其实更偏重策略，并且和硬件、模型结构、算力通信分配等方面都高度相关。

因此，越细致的流水行并行算法，它的通用性就越差，这也是为什么很多框架中流水线并行算法的实现相对朴素的核心原因。
