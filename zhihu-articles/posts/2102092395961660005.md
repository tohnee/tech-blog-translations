TLDR

- 随着智能体承担起更宏大的目标，它们需要在同时推进多项长任务的过程中，始终保持对用户的响应能力。
- 异步子智能体将智能体拆分为一个始终对用户保持可用的编排器，以及若干在后台运行任务、并在完成后向编排器汇报的子智能体。
- 后台工作正逐渐成为智能体基础设施的常态，从 Claude Code 这类编码智能体到 OpenAI 的 dots 这类个人智能体皆是如此。

设想一位幕僚长，每当你交给他一个大项目时他就消失不见，直到项目完成才回来。你大概会立刻解雇他。一位优秀的幕僚长会让项目在后台持续推进，同时保持可联系状态，并在此过程中不断向你汇报进展。当我们要求智能体朝着更宏大的目标努力时，它们同样需要具备这两项特性。智能体必须保持响应性，能够结合此前所有上下文立即执行新的指令；同时必须保持生产力，能够同时推进多项大型任务。

我们长期以来用于构建智能体的架构*无法*同时满足这两项要求。在标准的 ReAct 循环中，每一次耗时的工具调用都会阻塞该循环，其他所有任务都只能在其后排队等待。因此，我们看到整个生态系统正趋于形成一种分工：一个智能体始终陪伴用户，而由后台工作器承担耗时的工作。[Claude Code](https://code.claude.com/docs/en/sub-agents) 默认在后台运行子智能体，OpenAI 的 [dots](https://learn.chatgpt.com/docs/dots) 将工作交给后台工作器以同时推进多项事务，而 [DeepSeek Harness](https://x.com/DeepSeekHarness/status/2116857257245987236) 则围绕一个负责与人对话的路由器以及并行运行任务的后台工作器来构建其超级智能体。

我们正通过[异步子智能体](https://docs.langchain.com/oss/python/deepagents/async-subagents)将这一模式引入[Deep Agents](https://www.langchain.com/deep-agents)。编排器始终对用户保持可用，并持续整理对话的上下文；而异步子智能体则作为后台工作器运行，并在完成时汇报结果。这样一来，智能体所能承担的工作量便随后台工作器数量的增加而增长，而不再受限于单一循环的长度。

## **异步子代理的工作方式**

智能体在一个循环中运行。模型调用工具、等待结果，然后决定下一步做什么。过去，工具和子智能体会阻塞该循环，直到它们返回结果，就像依次等待每一次慢速调用的代码一样。异步子智能体的工作方式类似于用 `asyncio.create_task` 启动的任务，或一个你尚未 await 的 `Promise`。调用会立即返回，工作在后台独立运行，结果稍后返回。

![](https://picx.zhimg.com/v2-32f42453873d63edbff46b4f7c658397_r.jpg)

编排器将工作交给异步子智能体，并保持空闲以与用户对话。

异步工作依赖于系统的两项特性：

- **用户可以联系到编排器。**编排器是用户直接交互的智能体。子智能体不再占用其循环，因此只要编排器自身的循环不繁忙，用户便可随时联系到它，而无需等待每一个子智能体完成。
- **任务并行运行且互不阻塞。**编排器在工作到来时即启动子智能体，而不是等待整批任务返回。

编排器通过五个工具管理异步子智能体：

- `start_async_task` 在独立线程上启动子智能体并立即返回。
- `check_async_task` 获取任务状态，并在任务完成后获取其结果。
- `update_async_task` 向正在运行的任务发送新指令。
- `cancel_async_task` 停止正在运行的任务。
- `list_async_tasks` 列出所有任务及其状态。

对运行中的子智能体进行引导与联系编排器是两回事。当编排器通过 `update_async_task` 发送后续指令时，该子智能体定义中的 `update_strategy` 字段决定会发生什么：

- `"interrupt"`（默认值）停止当前运行，并以新指令重新启动子智能体。适用于诸如“改用 Postgres”之类的更正。
- `"enqueue"` 暂存后续指令，直到当前运行结束。适用于诸如“完成后运行测试”之类的补充。

## **通知的工作方式**

每个未完成的任务都会列在编排器的系统提示中，因此它始终清楚有哪些任务正在进行中。它可以通过 `check_async_task` 进行轮询，任务也可以[自行汇报结果](https://docs.langchain.com/langsmith/python/managed-deep-agents-subagents#get-notified-when-a-subagent-finishes)：

- 如果编排器**繁忙**，它会在每次模型调用前检查未完成的任务，并在运行过程中接收结果。
- 如果它处于**空闲**状态，子代理会通过一次新的运行将其唤醒。
- 如果它因等待审批而处于**暂停**状态，则该审批将保持不变，结果会在用户答复后送达。

![](https://pic1.zhimg.com/v2-09ea92c5fc060e6669f65aa5e7a4b9cc_r.jpg)

异步子代理会回报编排器是处于忙碌、空闲，还是因等待审批而暂停的状态。

需要审批的子代理会显示为`waiting`，用户可在子代理自身的线程上作答，而不会中断编排器。在 Slack 上的 Managed Deep Agents 中，该请求会[回帖至原始线程](https://docs.langchain.com/langsmith/python/managed-deep-agents-subagents#answer-approvals-in-channels)。

我们预计这一模式将不仅适用于子代理，还将推广至各类工具。OpenAI 近期新增了对[异步工具调用](https://developers.openai.com/api/docs/guides/async-tool-calling)的支持，即模型在调用工具后继续工作，而您的应用会在后续请求中回传结果。

## **使用异步子代理**

异步子代理已在 [Python](https://docs.langchain.com/oss/python/deepagents/async-subagents) 和 [JavaScript](https://docs.langchain.com/oss/javascript/deepagents/async-subagents) 版的 Deep Agents 中提供，也在 [Managed Deep Agents](https://docs.langchain.com/langsmith/python/managed-deep-agents-subagents) 中提供；在该产品中，只需设置一个字段即可将子代理设为异步：

```python
from managed_deepagents import define_deep_agent
 
agent = define_deep_agent(
    name="research-assistant",
    model="openai:gpt-5.5",
    subagents=[
        {
            "name": "researcher",
            "description": "Researches a topic in the background.",
            "system_prompt": "Research the topic and report your findings.",
            "async": True,
        },
    ],
)
```

在 Managed Deep Agents 中，每个已服务的代理还会获得 `general-purpose` 子代理的异步副本，因此它可以在运行时决定是在前台还是后台执行委派的工作。

任务通知功能处于测试阶段，因此 API 仍可能发生变化。[async-deep-agents](https://github.com/langchain-ai/async-deep-agents) 仓库中提供了一个可运行的监督器，包含 Python 和 TypeScript 编写的研究员与编码员子代理。
