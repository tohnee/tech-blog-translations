### <br>1.2 triton编译的重要性

<br>结合我们前面画的架构图来看，Triton 处于**编译层的 Kernel 级**位置——夹在 PyTorch/torch.compile 这类图级框架和底层硬件（GPU）之间，**是连接"算法研究者写的 Python 代码"和"硬件上跑的高性能机器码"的关键一环**。这个定位决定了它在整个 infra 里承担的是**性能可移植性与开发效率的核心枢纽**角色。

1. **解决 AI Infra 的核心矛盾：算法迭代速度 vs. Kernel 优化速度**

这是 Triton 从 infra 角度最本质的价值：

- **算法侧**：LLM 结构、Attention 变体、量化方案、MoE 路由策略几乎每季度都在变化（如 GQA、MLA、FlashAttention v1→v3、各种线性 Attention）。
- **Kernel 侧**：厂商手写库（cuDNN/cuBLAS）的更新周期以年为单位，且往往只覆盖主流算子。

在 Triton 出现之前，这个"剪刀差"意味着新算法提出后，往往要等数月甚至更久才有对应的高性能实现，期间只能用低效的算子拼接方式跑，训练/推理成本极高。Triton 让**算法团队自己就能写出接近手写 CUDA 性能的 kernel**，能够快速的实现算法实现高性能落地。

1. **作为 torch.compile 的核心代码生成后端**

这是 Triton 工程化落地最大的价值——支撑 PyTorch 2.x 的 `torch.compile`：

- **算子融合**：TorchDynamo 捕获计算图后，TorchInductor 用 Triton 生成融合后的单一 kernel，减少中间结果的显存读写（HBM 带宽是大模型训练/推理的主要瓶颈之一）。
- **覆盖长尾算子**：对 elementwise / reduction / normalization 类算子自动生成代码，不需要每个都手写 CUDA。
- 让 infra 团队不用为每个新模型结构单独开发定制 kernel，编译器自动生成"足够好"的版本，人力集中在真正的性能热点上。

1. **支撑推理引擎的自定义高性能 Kernel**

在推理侧，Triton 已成为主流推理框架的标配能力：

- **vLLM**：**attention及其变体、量化 kernel 大量使用 Triton 实现**，便于快速适配新模型结构与新硬件。
- **SGLang**：RadixAttention 相关实现同样依赖 Triton 编写的各种算子。
- 对于 MoE 架构（Mixtral、DeepSeek 系列）中高度定制化、没有现成库支持的 expert 路由和分组 GEMM，**Triton 几乎是唯一能快速实现且性能可接受的方案**。（ps: 最近TileLang等新型DSL也开始火起来了）

1. **硬件抽象与多硬件适配能力**

从长期战略看，Triton 的 IR 设计具备一定的跨硬件潜力：

- AMD 已基于 Triton 构建 ROCm 生态下的算子支持（vLLM 在 AMD MI300 上很多 kernel 复用 Triton 代码而非重写 HIP）。
- 国产 AI 芯片厂商也在适配 Triton 后端，以复用社区已有算子生态，降低"CUDA 生态锁定"风险。

基于triton编译的重要性，本章将详细介绍triton编译流程。

### <br>2.2 triton开源项目文件结构分析

<br>Triton（[https://github.com/triton-lang/triton](https://github.com/triton-lang/triton)）是一个以 Python 前端 + MLIR/C++ 编译器后端 为核心的 GPU 编程语言与编译器。整体设计高度模块化：C++ 负责高性能 IR 转换与优化，Python 负责语言前端、JIT、runtime 与后端插件发现。

### <br>2.2.1 顶层构建与打包入口<br>

```text
triton/
├── CMakeLists.txt          # 顶层 CMake：构建 C++ 编译器 + libtriton.so
├── setup.py                # Python 打包入口（CMakeExtension / CMakeBuild）
├── pyproject.toml          # 现代 Python 构建元数据（已切换到 nanobind）
```

**CMakeLists.txt** 是 C++ 世界的入口。它负责：

- 编译整个 MLIR dialect / conversion / analysis 体系。
- 生成共享库 libtriton.so（Python 扩展）。

### <br>2.2.2 C++ 编译器核心（include/ + lib/）

<br>lib和include这两个文件夹下子目录如图所示，可以观察到它们的目录结构类似，都包含Analysis、Conversion、Dialect、Target、Tools等文件夹。

![](https://picx.zhimg.com/v2-93c5d38b7d8f9c1bd49e994ee6e669ef_r.jpg)

- include文件夹：主要存放了编译器核心功能的.h头文件，通常没有具体的实现代码，更多的是提供一种约定和规范，指导如何调用或实现某些功能。
- lib文件夹：通常以.cpp或者.cc为后缀，包含了功能实现的具体算法、函数和逻辑，这些实现文件直接对应于在include文件夹中声明的函数和类。

![](https://pic2.zhimg.com/v2-f24a20c7af26453d708e2d085342c19d_r.jpg)

```text
├── include/triton/    # 公开头文件
│   ├── Analysis/      # AxisInfo、Membar、Allocation 等分析
│   ├── Conversion/    # Triton → TritonGPU → LLVM 等转换接口
│   ├── Dialect/       # Triton、TritonGPU、TritonNvidiaGPU等
│   ├── Target/        # 目标相关（LLVM 等）
│   └── Tools/
└── lib/               # 实现主体（与 include 一一对应）
    ├── Dialect/
    ├── Conversion/    # TritonToTritonGPU、TritonGPUToLLVM …
    └── Analysis/
```

<br><br>这是 Triton 编译器的心脏，基于 MLIR：

- **Dialect 层**：定义 IR 原语。各级中间表示Dialect的定义以及在对应Dialect上进行的优化遍pass。<br>
- **Conversion 层**：主要负责dialect之间的转换。多阶段 lowering pipeline（Triton-IR → TritonGPU-IR → LLVM-IR → PTX/HSACO 等）。<br>
- **Analysis 层**：轴信息、内存屏障、分配等，为自动并行化与优化提供数据。<br>

CLI 工具（bin/）直接依赖这些库，可独立运行 triton-opt 做 IR 转换与调试，无需 Python。

## 3. 编译流程总览

以01-vector_add.py为例，介绍从python写的DSL Triton kernel到ttir的转换过程。<br>add_kernel:

```text
@triton.jit
def add_kernel(x_ptr, y_ptr, output_ptr,n_elements, BLOCK_SIZE: tl.constexpr, ):
    pid = tl.program_id(axis=0)
    block_start = pid * BLOCK_SIZE
    offsets = block_start + tl.arange(0, BLOCK_SIZE)
    mask = offsets < n_elements
    x = tl.load(x_ptr + offsets, mask=mask)
    y = tl.load(y_ptr + offsets, mask=mask)
    output = x + y
    tl.store(output_ptr + offsets, output, mask=mask)
```

kernel调用：

```text
def add(x: torch.Tensor, y: torch.Tensor):
    output = torch.empty_like(x)
    assert x.is_cuda and y.is_cuda and output.is_cuda
    n_elements = output.numel()
    grid = lambda meta: (triton.cdiv(n_elements, meta['BLOCK_SIZE']), )
    add_kernel[grid](x, y, output, n_elements, BLOCK_SIZE=1024)
    return output

//定义函数接收两个torch张量x和y作为输入参数
//创建一个与张量 x 形状和数据类型相同的空张量output，用于存储结果
```

### <br>3.1 生成Triton IR (TTIR)

### <br>3.1.1 Triton IR 介绍

<br>Triton IR 是 Triton 编译器的高级中间表示，用于表示深度学习模型的计算图，并且是硬件无关的。Triton IR 有以下几个特点：

- 高级抽象：Triton IR 提供了高级抽象，使得开发者可以用接近于高级深度学习框架的方式来描述计算图。
- 操作表示：它包含了一系列的操作（ops），如矩阵乘法、卷积、激活函数等，这些都是深度学习模型中常见的操作。
- 优化：在 Triton IR 层面，编译器可以应用一些高级优化，如死代码消除、常量折叠等。
- 转换：Triton IR 可以被转换为更接近硬件的 Triton GPU IR，以便进行进一步的优化。

### 3.1.2 Triton IR 转换流程

<br>**调用 Triton Python 编写的 Kernel 函数，到生成 TTIR（Triton IR）.**<br>首先调用triton kernel，之后会在JIT中的self.compile()处调用编译器，接着会调用make_ir，接着会调用ast去生成ttir，逻辑位于triton/compiler/code_generator.py文件中，具体进行代码生成codeGen的遍历，从而完成Triton Python kernel到Triton IR（ttir）的转换。<br>

![](https://pic4.zhimg.com/v2-2fbf00bc331f8122c316c21a8c8b3103_r.jpg)

**第 1 层：用户侧入口 —— 调用 Triton Kernel**

- **调用triton kernel:**调用了`01-vector-add.py`文件中被`@triton.jit`装饰器修饰的内核函数 `add(x, y)`，这是整个编译流程的触发起点。
- **核心动作：**执行`add(x,y)`不会立刻运行 GPU 计算，**而是先走 JIT 编译流程**。

第 2 层：JIT 运行层启动编译器

- 对应源码文件：Triton 运行时模块 `triton/runtime/jit.py`（JIT 装饰器的核心实现文件）
- 核心动作：**被 jit 装饰的函数执行时，会执行实例方法 `self.compile()`，正式拉起整套 Triton 编译流水线**，生成可执行的 kernel 对象。

**第 3 层：编译入口构建顶层 IR 容器**

- 对应源码文件：编译器主入口文件 `triton/compiler/compiler.py`
- 核心动作：**`compile()`内部调用`make_ir`方法**，依托用户编写的 Triton Python 源码对象`src`，执行`src.make_ir()`，**开启从源码构建中间表示 IR 的流程**。

**第 4 层：AST 遍历，完成 Triton Python 源码 → TTIR 转换（编译器前端核心步骤）**

- 顶层调用入口：依旧在`triton/compiler/compiler.py`中调用函数 `ast_to_ttir()`；
- 实际实现载体：`ast_to_ttir` 的全部编译逻辑存放于 `triton/compiler/code_generator.py`；
- 底层执行机制：依靠CodeGen（代码生成器）遍历 Python 抽象语法树 AST，对 Triton 自定义语法、内置算子、线程 / 块调度语法做语义解析、语法翻译；
- **最终产出：**把高层的 Triton Python 代码，翻译成编译器的第一层中间表示 TTIR（Triton Intermediate Representation）

### <br>3.2.1 **JITFunction 与编译触发（jit.py）**

- Triton kernel的编译总入口为triton.jit装饰器，triton.jit将以triton.language写好的kernel function包装成JITFunction对象。
- 被triton.jit装饰后的函数kernel会成为一个JITFunction，**JITFunction被调用的时候，是以fn[grid](*args*,***kwargs)的形式被调用的， 即Kernel的入参**。因此，JITFunction的父类KernelInterface定义了__getitem__函数，**调用self.run()函数**。<br>

**JITFunction类：**

- JITFunction是 Triton 运行时最核心的组件之一，是用户使用 `@triton.jit` 装饰器修饰内核函数后实际得到的对象。

核心流程如下所示：

- 缓存没有命中时：

```text
总调度入口：run()（整条链路最核心中枢）

执行链路时序：
1. 获取当前激活的硬件设备 和 CUDA 流
2. 注入全局调试、插桩相关开关，执行 pre_run_hooks 前置钩子

       └─ 缓存缺失 → 调用 _do_compile()
                      ↓
    ========================================================

    ========================================================

       - 打包 Python AST、签名、常量为 ASTSource 对象
    2. 编译模式分发

    3. 收尾回调
       - 编译产物写入 device_cache 内存缓存
       - 触发 jit_post_compile_hook 通知外部
    ========================================================
                      ↓
5. 校验全局变量值未被篡改（编译时捕获的值运行时不能变更）
    ↓
6. warmup 分支判断：
   ├─ warmup=False（正常调用）→ 规整 grid 三维维度 
   │   → 生成 launch_metadata (参数封装/协同启动标志)
   │   → 触发 launch_enter_hook
   │   → kernel.run 底层调用 CUDA Driver 提交 GPU 执行
   │   → 触发 launch_exit_hook
   │
   └─ warmup=True（预热调用）→ 只编译写入缓存，跳过 GPU Launch
```

```text
# JITFunction：实际承载内核JIT编译、缓存管理、内核Launch执行的实现类
# 多重继承：JITCallable（基础可调用抽象） + KernelInterface（提供__getitem__/run/warmup接口规范）
class JITFunction(JITCallable, KernelInterface[T]):
    def run(self, *args, grid, warmup, **kwargs):
        """
        【整个JIT最核心主流程】重写父类KernelInterface的抽象run方法
        完整链路：前置钩子执行 → 实参绑定&特化生成 → 查询内核缓存 → 缺失则编译内核 → 校验全局变量一致性 → 非预热则Launch GPU内核
        :param args: kernel计算入参(张量指针、数值等)
        :param grid: 线程网格维度
        :param warmup: True=仅编译缓存、不执行GPU计算；False=编译+真实GPU运行
        :param kwargs: 编译配置(num_warps/num_stages等)
        :return: CompiledKernel编译内核对象
        """
        # 注入全局调试、插桩相关开关
        kwargs["debug"] = kwargs.get("debug", self.debug) or knobs.runtime.debug
        kwargs["instrumentation_mode"] = knobs.compilation.instrumentation_mode
        kwargs["fpsan_homomorphic_casts"] = knobs.compilation.fpsan_homomorphic_casts

        # 获取当前激活GPU设备 + CUDA流
        device = driver.active.get_current_device()
        stream = driver.active.get_current_stream(device)

        # 顺序执行所有注册的运行前置钩子
        for hook in self.pre_run_hooks:
            hook(*args, **kwargs)

        # 取出当前设备专属缓存、硬件目标、后端、参数绑定器
        kernel_cache, kernel_key_cache, target, backend, binder = self.device_caches[device]
        # binder解析实参：绑定实参值、生成当前实参对应的特化标签、解析编译配置
        bound_args, specialization, options = binder(*args, **kwargs)

        # 自定义编译流水线插桩，追加哈希到特化信息中
        if knobs.runtime.add_stages_inspection_hook is not None:
            inspect_stages_key, inspect_stages_hash = knobs.runtime.add_stages_inspection_hook()
            specialization.append(f'("custom_pipeline", {inspect_stages_hash})')

        # 根据特化信息 + 编译配置计算全局唯一缓存key
        key = compute_cache_key(kernel_key_cache, specialization, options)
        # 从当前设备缓存读取已编译内核
        kernel = kernel_cache.get(key, None)

        # 缓存未命中：执行编译流程
        if kernel is None:
            # 规整打包编译所需的配置、签名、常量、属性
            options, signature, constexprs, attrs = self._pack_args(backend, kwargs, bound_args, specialization, options)
            # 调用实际编译逻辑（同步/异步编译）
            kernel = self._do_compile(key, signature, device, constexprs, options, attrs, warmup)
            if kernel is None:
                return None

        # 安全校验：内核编译时捕获的全局变量不能被运行时修改，防止计算逻辑错乱
        not_present = object()
        for (name, _), (val, globals_dict) in self.used_global_vals.items():
            if (newVal := globals_dict.get(name, not_present)) != val:
                raise RuntimeError(
                    f"Global variable {name} has changed since we compiled this kernel, from {val} to {newVal}")

        # 非预热模式：真实向GPU提交内核执行
        if not warmup:
            assert grid is not None
            # grid支持传入函数动态计算网格大小
            if callable(grid):
                grid = grid(bound_args)
            # 规整三维grid维度，缺失维度默认填充1
            grid_size = len(grid)
            grid_0 = grid[0]
            grid_1 = grid[1] if grid_size > 1 else 1
            grid_2 = grid[2] if grid_size > 2 else 1
            # 构造内核Launch元数据（显存地址、参数封装等）
            launch_metadata = kernel.launch_metadata(grid, stream, *bound_args.values())
            # 底层调用CUDA驱动，提交内核到GPU硬件执行计算
            kernel.run(
                grid_0, grid_1, grid_2, stream, kernel.function, kernel.packed_metadata, launch_metadata,
                knobs.runtime.launch_enter_hook, knobs.runtime.launch_exit_hook, *bound_args.values()
            )
        return kernel

    def _do_compile(self, key, signature, device, constexprs, options, attrs, warmup):
        """
        真实编译执行入口：同步编译 / 异步编译二选一
        1. 执行编译前置全局钩子
        2. 构造ASTSource（封装用户函数AST、签名、常量）
        3. 根据全局开关选择同步编译 or 后台异步编译
        4. 编译完成写入缓存，并执行编译后置钩子
        """
        kernel_cache, _, target, backend, _ = self.device_caches[device]
        # 执行jit缓存前置钩子，钩子返回True直接终止本次编译
        if self._call_hook(knobs.runtime.jit_cache_hook, key, signature, target, device, constexprs, options, [attrs],
                           warmup):
            return None
        # 封装用户AST源码对象，传入编译器顶层compile函数
        src = self.ASTSource(self, signature, constexprs, attrs)

        # 判断是否开启异步编译
        async_mode = _async_compile.active_mode.get()
        if async_mode is not None:
            env_vars = get_cache_invalidating_env_vars()
            cache_key = get_cache_key(src, backend, options, env_vars)
            # 定义异步编译闭包
            def async_compile():
                return self.compile(src, target=target, options=options.__dict__, _env_vars=env_vars)
            # 编译完成后的回调：写入缓存 + 执行后置钩子
            def finalize_compile(kernel):
                kernel_cache[key] = kernel
                self._call_hook(knobs.runtime.jit_post_compile_hook, key, signature, target, device, constexprs,
                                options, [attrs], warmup)
            # 提交异步任务到线程池
            kernel = async_mode.submit(cache_key, async_compile, finalize_compile)
            kernel_cache[key] = kernel
        else:
            # 同步阻塞编译（默认行为），调用上一节讲解的 compiler.compile() 顶层函数
            kernel = self.compile(src, target=target, options=options.__dict__)
            kernel_cache[key] = kernel
            # 编译完成执行后置钩子
            self._call_hook(knobs.runtime.jit_post_compile_hook, key, signature, target, device, constexprs, options,
                            [attrs], warmup)
        return kernel
```

### <br>3.2.2 compile总接口

<br>`compile` 函数的主要职责是：**接收输入源码（Python AST 或中间表示 IR），经过一系列的编译阶段，最终生成可在指定 GPU 上运行的二进制内核**，并在此过程中实现了强大的缓存、覆盖和调试钩子机制。

- `compile` 函数是最顶层编译总入口，承接 `jit.py` 中 `self.compile()` 调用，串联：缓存管理 → AST 转 TTIR → 全阶段 IR 编译流水线 → 产物落地持久化 → 编译内核封装返回
- 核心过程：

**上下游对接关系：**

- 上游调用方：`triton/runtime/jit.py` 的`self.compile()`
- 上游输入：ASTSource（用户 @jit 修饰的函数 AST） / IRSource（外部 IR 文件）
- 内部核心产出：ttir → ttgir → llir → ptx → cubin 整套编译产物 + metadata.json
- 下游输出：`CompiledKernel` 对象，交给 Triton Runtime 做显存绑定、Grid 配置、GPU 任务提交

**三套调试开关：**

- `TRITON_KERNEL_DUMP=1`：导出所有阶段 ttir/ttgir/llir/ptx 文件，查看每一步 IR 变换
- `TRITON_KERNEL_OVERRIDE=1`：使用本地修改后的 IR 文件替换编译生成的 IR，不用改动 Python 源码调试 IR 层级问题
- `TRITON_ALWAYS_COMPILE=1`：关闭缓存，每次调用都完整重编，排查缓存污染问题

**AST 生成原始 TTIR：**

- 调用 `src.make_ir`，这是将 Python AST 转换为 Triton IR 的地方
- compile函数接受的src为ASTSource对象，ASTSource主要作用是将JITFunction从ast tree转换为Triton IR：

```text

module_map = backend.get_module_map()
try:

except Exception as e:
```

```text
#triton/compiler/compiler.py 
def compile(src, target=None, options=None):
    """
    Triton 编译顶层入口函数，完整实现：编译缓存校验 → 全编译流水线执行 → 产物持久化 → 返回编译后的内核对象
    :param src: 源码对象，二选一：ASTSource(用户Python内核抽象语法树) / IRSource(外部导入的TTIR/TTGIR等IR文件)
    :param target: GPU硬件目标描述对象（GPU架构、算力、厂商NVIDIA/AMD），为空自动取当前激活GPU
    :param options: 用户传入的编译配置（块大小、 warp数量、优化等级、编译标志等）
    :return: CompiledKernel：封装了所有编译产物、元数据、文件路径的内核句柄对象
    """
    # 1. 补齐GPU编译目标，校验目标类型必须是GPU目标
    if target is None:
        target = driver.active.get_current_target()
    assert isinstance(target, GPUTarget), "target must be of GPUTarget type"
    # 根据GPU目标(NVIDIA/AMD)创建对应后端处理器（NVIDIABackend / AMDBackend）
    backend = make_backend(target)

    # 标记输入源是否为IR文件（True=外部.ttir/.llir文件；False=用户Python代码AST）
    ir_source = not isinstance(src, ASTSource)

    # 场景分支：输入是磁盘上的IR文本文件，包装为IRSource对象管理
    if ir_source:
        assert isinstance(src, str), "source must be either AST or a filepath"
        context = ir.context()  # 创建MLIR全局上下文（管理Dialect、内存、线程池）
        src = IRSource(src, context, backend)

    # 合并编译配置：源码内置编译参数 + 用户外部传入options
    extra_options = src.parse_options()
    options = backend.parse_options(dict(options or dict(), **extra_options))

    # ====================== 编译缓存哈希计算（核心：JIT缓存命中逻辑） ======================
    # 获取会导致缓存失效的环境变量（环境变更需要重新编译内核）
    env_vars = get_cache_invalidating_env_vars()
    # 构造缓存哈希原始因子：triton版本 + 源码哈希 + 后端(硬件)哈希 + 编译参数哈希 + 环境变量
    key = f"{triton_key()}-{src.hash()}-{backend.hash()}-{options.hash()}-{str(sorted(env_vars.items()))}"
    # 计算sha256作为缓存根目录hash值
    hash = hashlib.sha256(key.encode("utf-8")).hexdigest()
    # 根据hash获取缓存管理器，管理该内核所有编译产物文件(ttir/ttgir/llir/ptx/cubin/json)
    fn_cache_manager = get_cache_manager(hash)

    # 读取3个调试开关环境变量
    enable_override = os.environ.get("TRITON_KERNEL_OVERRIDE", "0") == "1"    # 是否使用外部文件覆盖编译生成的IR
    enable_ir_dump = os.environ.get("TRITON_KERNEL_DUMP", "0") == "1"        # 是否导出各阶段IR文件到本地
    store_only_binary = os.environ.get("TRITON_STORE_BINARY_ONLY", "0") == "1"# 缓存是否只保存最终cubin二进制，丢弃中间IR文件

    # 覆盖IR文件管理器、IR导出管理器（按需创建）
    fn_override_manager = get_override_manager(src.hash()) if enable_override else None
    fn_dump_manager = get_dump_manager(src.hash()) if enable_ir_dump else None

    # 文件名截断至150字符：规避Linux/macOS文件名255字符长度限制，防止缓存文件创建失败
    file_name = src.name[:150]
    metadata_filename = f"{file_name}.json"  # 元数据文件名
    metadata_group = fn_cache_manager.get_group(metadata_filename) or {}
    metadata_path = metadata_group.get(metadata_filename)  # 读取已存在的元数据文件路径

    # 强制重新编译开关：TRITON_ALWAYS_COMPILE=1 则不走缓存，强制全量编译
    always_compile = os.environ.get("TRITON_ALWAYS_COMPILE", "0") == "1"
    # ============ 缓存命中分支：直接返回已编译好的内核对象，跳过整套编译流水线 ============
    if not always_compile and metadata_path is not None:
        # cache hit!
        return CompiledKernel(src, metadata_group, hash)

    # ====================== 缓存未命中：正式执行完整编译流程 ======================
    # 初始化编译元数据（后续会写入json持久化到缓存）
    metadata = {
        "hash": hash,
        "target": target,
        **options.__dict__,
        **env_vars,
    }
    metadata["triton_version"] = __version__  # 记录triton版本，版本升级自动失效旧缓存
    stages = dict()
    # 后端注入整套编译阶段流水线：key=文件后缀(ttir/ttgir/llir/ptx/cubin)，value=对应阶段编译函数
    backend.add_stages(stages, options)
    # 找到当前输入源对应的起始编译阶段下标
    first_stage = list(stages.keys()).index(src.ext)
    # 输入是外部IR文件：跳过该IR对应前置编译阶段，从下一阶段开始执行
    if ir_source:
        first_stage += 1

    # 非IR文件（用户Python AST源码）：初始化MLIR上下文、加载Triton自定义Dialect + GPU后端Dialect
    if not isinstance(src, IRSource):
        context = ir.context()
        ir.load_dialects(context)
        backend.load_dialects(context)

    # 获取代码生成实现、MLIR模块映射表，调用AST -> TTIR生成入口
    codegen_fns = backend.get_codegen_implementation(options)
    module_map = backend.get_module_map()
    try:
        # 【对应前面链路stage4】执行CodeGen遍历AST，生成初始TTIR MLIR Module
        module = src.make_ir(options, codegen_fns, module_map, context)
    except Exception as e:
        filter_traceback(e)  # 过滤冗余堆栈，精简报错信息
        raise

    use_ir_loc = os.environ.get("USE_IR_LOC", None)
    # 从起始阶段开始，串行遍历所有编译阶段（ttir → ttgir → llir → ptx → cubin）
    for ext, compile_ir in list(stages.items())[first_stage:]:
        # 执行当前阶段的编译逻辑，输入上一阶段module，输出本阶段处理后的IR Module
        next_module = compile_ir(module, metadata)
        ir_filename = f"{file_name}.{ext}"

        # 开启IR覆盖：读取用户指定的外部IR文件，替换当前编译产出的module
        if (fn_override_manager is not None and (full_name := fn_override_manager.get_file(ir_filename)) is not None):
            print(f"\nOverriding kernel with file {full_name}")
            next_module = parse(full_name, ext, context)

        # 缓存存储策略：仅开启二进制存储时，只保存cubin/hsaco硬件二进制+json元数据，丢弃中间IR
        if (not store_only_binary) or (ext in ("cubin", "hsaco", "json")):
            metadata_group[ir_filename] = fn_cache_manager.put(next_module, ir_filename)
        # 开启IR Dump：把每个阶段IR写入dump目录，用于调试编译流程
        if fn_dump_manager is not None:
            fn_dump_manager.put(next_module, ir_filename)

        # 调试功能：使用指定阶段IR文件覆盖源码位置信息，方便定位IR报错对应原始代码行
        if use_ir_loc == ext:
            ir_full_name = fn_cache_manager.get_file(ir_filename)
            next_module.create_location_snapshot(ir_full_name)
            print(f"Creating new locations for {ir_full_name}")

        # 迭代更新module，作为下一编译阶段的输入
        module = next_module

    # 将完整metadata字典序列化为json，存入缓存组
    metadata_group[metadata_filename] = fn_cache_manager.put(json.dumps(metadata, default=vars), metadata_filename,
                                                             binary=False)
    # 把本批次所有文件(各阶段IR、cubin、json元数据)写入磁盘缓存目录
    fn_cache_manager.put_group(metadata_filename, metadata_group)

    # 关闭MLIR上下文多线程：规避进程fork时线程池失效导致子进程崩溃/卡死的问题
    # ASAN地址检测模式下禁用此逻辑，会造成符号解析进程挂死
    if not os.environ.get("TRITON_ENABLE_ASAN", "0") == "1":
        context.disable_multithreading()

    # 封装所有缓存资源，返回编译完成的内核对象，供runtime加载执行
    return CompiledKernel(src, metadata_group, hash)
```

```text
// ==============================================================
// 前置说明：该段为【经过TTIR全套优化Pass之后、进入TTIR→TTGIR降级Pass之前】的标准TTIR文本
// 对应算子：最经典的向量相加 add_kernel，BLOCK_SIZE = 1024
// 四个入参：arg0(x向量指针)、arg1(y向量指针)、arg2(out输出指针)、arg3(总元素个数 n_elements)
// 每条指令末尾 loc(#locX) 绑定原始Python代码行号，用于报错溯源调试
// tt Dialect = Triton高层IR，只描述计算语义，不含warp/smem/硬件调度等GPU底层细节
// ==============================================================
// -----// IR Dump Before ConvertTritonToTritonGPU (convert-triton-to-tritongpu) ('builtin.module' operation) //-----
module {
  // 定义顶层GPU kernel函数，对外公开可见
  // 三个f32显存指针参数，挂载 tt.divisibility=16 属性：指针满足16字节对齐，用于显存合并访存优化
  // arg3：int类型，全局向量总长度；noinline = false 允许函数内联优化
  tt.func public @add_kernel(
    %arg0: !tt.ptr<f32> {tt.divisibility = 16 : i32},
    %arg1: !tt.ptr<f32> {tt.divisibility = 16 : i32},
    %arg2: !tt.ptr<f32> {tt.divisibility = 16 : i32},
    %arg3: i32 {tt.divisibility = 16 : i32}
  ) attributes {noinline = false} {

    // 常量定义：BLOCK_SIZE = 1024（编译期常量）
    %c1024_i32 = arith.constant 1024 : i32

    // 获取当前线程块的program_id.x → 对应CUDA blockIdx.x，代表当前块的编号
    %0 = tt.get_program_id x : i32

    // block_id * 1024 = 当前线程块负责数据区间的起始全局索引
    %1 = arith.muli %0, %c1024_i32 : i32

    // 生成一维数组 [0, 1, 2 ... 1023]，对应一个block内部1024个线程的局部偏移量
    %2 = tt.make_range {end = 1024 : i32, start = 0 : i32} : tensor<1024xi32>

    // 将块起始标量 %1 广播平铺为 1024 长度张量，块内所有线程共用同一个块起始地址
    %3 = tt.splat %1 : i32 -> tensor<1024xi32>

    // 全局索引 = 块起始索引 + 块内线程局部偏移 → 得到该线程对应的全局数组下标
    %4 = arith.addi %3, %2 : tensor<1024xi32>

    // 将总元素个数n_elements做广播，生成1024长度张量，用于边界判断
    %5 = tt.splat %arg3 : i32 -> tensor<1024xi32>

    // 边界掩码：global_idx < n_elements → 有效位置为true，越界位置为false，防止数组越界访问
    %6 = arith.cmpi slt, %4, %5 : tensor<1024xi32>

    // ===== 读取向量x数据 =====
    // 将x的基地址指针平铺为1024个指针，每个线程持有一份基址
    %7 = tt.splat %arg0 : !tt.ptr<f32> -> tensor<1024x!tt.ptr<f32>>
    // 基址 + 全局索引偏移，计算每个线程真正的显存访问地址
    %8 = tt.addptr %7, %4 : tensor<1024x!tt.ptr<f32>>, tensor<1024xi32>
    // 带掩码加载：mask为true才读取显存数据，越界位置填充默认值
    %9 = tt.load %8, %6 : tensor<1024x!tt.ptr<f32>>

    // ===== 读取向量y数据 =====
    %10 = tt.splat %arg1 : !tt.ptr<f32> -> tensor<1024x!tt.ptr<f32>>
    %11 = tt.addptr %10, %4 : tensor<1024x!tt.ptr<f32>>, tensor<1024xi32>
    %12 = tt.load %11, %6 : tensor<1024x!tt.ptr<f32>>

    // 浮点向量加法：z = x + y，张量级并行运算
    %13 = arith.addf %9, %12 : tensor<1024xf32>

    // ===== 将相加结果写回out显存 =====
    %14 = tt.splat %arg2 : !tt.ptr<f32> -> tensor<1024x!tt.ptr<f32>>
    %15 = tt.addptr %14, %4 : tensor<1024x!tt.ptr<f32>>, tensor<1024xi32>
    // 带掩码存储：只在有效下标位置写入结果，越界位置不执行写操作
    tt.store %15, %13, %6 : tensor<1024x!tt.ptr<f32>>

    // 内核函数正常返回
    tt.return
  }
}
```

<br>转换完成后，**可以观察到Triton kernel与生成的Triton IR是对应的**，以下图划线的这几条语句为例：

- 黄色线条：指向的kernel中用于防止越界访问的mask这条语句，对应到ttir中就是arith.cmpi 进行条件比较。
- 红色线条：指向的两条tl.load指令，在ttir中对应是用tt.load从指定的内存地址加载数据。
- 白色线条：指向的执行加法的这条指令，在ttir中对应的是用arith.addf进行计算。
- 最后红色线条：指向的用于存储计算结果的tl.store，在ttir中对应的是用tt.store将结果存储回内存。

```text
def ast_to_ttir(fn, specialization, context, options, codegen_fns):
    """
    【编译器前端核心入口】将 Triton 内核 Python AST 转换成 TTIR(Triton 高层MLIR) Module
    上游调用方：src.make_ir() → compiler.py
    输入：
        fn：JITFunction 内核对象，持有原始函数AST、函数名、源码文件行号、入参名等元信息
        specialization：本次调用的特化快照（签名dtype、constexpr常量、参数硬件属性attrs）
        context：MLIR全局上下文，管理Dialect、内存、位置信息、线程池
        options：编译配置（num_warps/num_stages/fp融合等）
        codegen_fns：外部注入的代码生成自定义回调函数组
    输出：填充完成TTIR逻辑的MLIR Module对象
    """
    # 取出当前特化版本绑定的参数硬件属性（对齐、等值常量标记等）
    attrs = specialization.attrs

    # 构造常量映射：把constexpr的key统一映射为参数下标
    # cst_key：兼容两种入参形式（参数名字符串 / 参数数字下标），统一转为形参索引
    cst_key = lambda i: fn.arg_names.index(i) if isinstance(i, str) else i
    # 组装【参数下标 : 常量值】字典，存放用户代码中tl.constexpr编译期常量
    constants = {cst_key(key): value for key, value in specialization.constants.items()}

    # 拷贝内核运行时全局命名空间快照，CodeGenerator遍历AST时解析全局变量引用
    gscope = fn.__globals__.copy()
    # 生成内核在IR中的可读名称，包含num_warps/num_stages等编译配置标识
    function_name = fn.repr(specialization)
    # 提取所有形参对应的类型字符串
    tys = list(specialization.signature.values())

    # 规则1：标记等于字面量1的参数，填充布尔常量true(i1类型)
    new_constants = {k: True if k in tys and tys[k] == "i1" else 1 for k in attrs.equal_to_1}
    # 规则2：对要求内存按16字节对齐的参数，挂载 tt.divisibility=16 MLIR属性（用于后续内存合并访问优化）
    new_attrs = {k: [("tt.divisibility", 16)] for k in attrs.divisible_by_16}

    # 合并用户手写constexpr常量 + 框架自动推导的常量标记
    all_constants = constants.copy()
    all_constants.update(new_constants)

    # 过滤掉constexpr常量形参，只保留运行时传入的张量/数值参数，并转为MLIR类型对象
    arg_types = [str_to_ty(v) for k, v in specialization.signature.items() if k not in specialization.constants]

    # 读取内核源码所在文件路径、函数起始行号，用于IR绑定源码位置，报错精准映射代码行
    file_name, begin_line = get_jit_fn_file_line(fn)

    # 构建顶层函数原型：无返回值，入参类型集合为解析后的arg_types（GPU内核统一无返回值，结果靠显存指针写出）
    prototype = language.function_type([], arg_types)

    # 实例化AST遍历核心：CodeGenerator 访问者对象（整个AST→TTIR的实际遍历、节点翻译执行者）
    generator = CodeGenerator(
        context=context,                # MLIR上下文
        prototype=prototype,           # 函数签名原型
        gscope=gscope,                 # 全局变量快照
        constants=all_constants,       # 全部编译期常量集合
        function_name=function_name,   # IR内函数标识名
        jit_fn=fn,                     # 原始JITFunction对象
        attributes=new_attrs,          # 内存对齐等硬件属性
        is_kernel=True,                # 标记这是GPU顶层kernel函数
        file_name=file_name,           # 源码文件路径（调试报错溯源）
        begin_line=begin_line,         # 源码起始行号
        options=options,               # 全局编译配置
        codegen_fns=codegen_fns        # 自定义代码生成钩子函数
    )

    # 【核心动作】解析内核源码AST抽象语法树，递归遍历所有AST节点，逐条翻译成TTIR指令，填充到module中
    generator.visit(fn.parse())

    # 取出生成完毕的TTIR MLIR模块
    ret = generator.module
    # 绑定MLIR上下文归属关系，module生命周期绑定context
    ret.context = context
    # 返回封装完整TTIR代码的MLIR Module，供给后续TTIR优化Pass流水线处理
    return ret
```

### <br>3.4.1 make_ttir

<br>**`make_ttir` 阶段**主要是对高层 Triton IR 进行架构无关的通用优化（如内联、公共子表达式消除、死代码消除）以及Triton 语言特定的图变换（如算子合并、广播重排），并为特定硬件架构（如老款 GPU 不支持 TMA）做好底层适配准备。<br>

```text
    @staticmethod
    def make_ttir(mod, metadata, opt, capability):
        pm = ir.pass_manager(mod.context)
        pm.enable_debug()
        passes.common.add_inliner(pm)
        if capability // 10 < 9:
            passes.ttir.add_rewrite_tensor_descriptor_to_pointer(pm)
        passes.common.add_canonicalizer(pm)
        passes.ttir.add_combine(pm)
        passes.ttir.add_reorder_broadcast(pm)
        passes.common.add_cse(pm)
        passes.common.add_symbol_dce(pm)
        passes.ttir.add_loop_unroll(pm)
        pm.run(mod, 'make_ttir')
        return mod
```

<br>分为【通用公共 Pass（common）】、【Triton 专属 TTIR Pass（ttir）】两大类。<br>

| Pass 名称 | 作用与收益 |
| --- | --- |
| add_inliner | 将被调用的函数体直接展开到调用处，消除函数调用开销，并暴露更多跨函数边界的优化机会。 |
| add_rewrite_tensor_descriptor_to_pointer | 硬件架构适配：仅在 GPU 计算能力 < 9.0（如 Ampere 及更早架构）时执行。将高层的 Tensor Descriptor 抽象降级为底层指针操作，因为老架构不支持原生 Tensor Memory Access (TMA) 硬件单元。 |
| add_canonicalizer | 将 IR 转换为标准的、简化的规范形式。例如消除冗余表达式、合并常量计算、简化控制流，为后续 Pass 提供更清晰的 IR 结构。 |
| add_combine | 将相邻的、可合并的 Triton 算子融合为一个复合操作，减少指令发射数量和中间结果的访存开销。 |
| add_reorder_broadcast | 调整 Broadcast（广播）算子在计算图中的位置，通常将其推迟到真正需要扩展维度时，以此缩减中间张量的尺寸，节省内存并提高数据局部性。 |
| add_cse | 识别计算图中多次出现的相同计算表达式，只计算一次并将结果复用，从而减少冗余的计算开销。 |
| add_symbol_dce | 移除 IR 中定义但从未被引用的符号（如未使用的函数、全局变量等），保持 IR 精简，减小编译产物体积。 |
| add_loop_unroll | 将 tl.range 等循环结构展开为线性的指令序列。牺牲部分指令缓存空间，换取消除循环控制开销（如条件跳转、循环计数器更新）和提升指令级并行度（ILP）的收益。 |

### <br>3.4.2 make_ttgir

<br>**`make_ttgir()` 是TTIR → TTGIR（Triton GPU IR）的入口总函数**

1. 输入：经过`make_ttir()`优化完毕的纯算法语义 TTIR
2. 第一步执行核心 Pass：**`convert_to_ttgpuir`**，完成 TTIR 方言 → TTGIR 方言的语法降级，注入 GPU 硬件原语（Block/CTA、Warp、SharedMem/SMEM、TensorMem/TMEM、寄存器、异步拷贝、MMA 矩阵单元等）
3. **后续一长串分层 Pass**：基于显卡算力（8xx=Ampere、9xx=Hopper、10xx=Blackwell）**执行架构专属硬件优化、流水线排布、内存布局优化、指令调度、MMA/TMA 硬件指令下发**
4. 输出：**携带完整 GPU 硬件调度信息、内存层级规划、流水线配置的TTGIR Module，交给下一阶段转为 LLVM IR**
5. 运行阶段：编译流水线的 `stages["ttgir"]` 绑定此方法

整个 make_ttgir 的本质：

- **把与硬件无关的 TTIR 计算语义，翻译成绑定 GPU 真实硬件资源（SM/CTA/Warp/SMEM/TMEM/ 寄存器 / TensorCore）的 TTGIR，并完成 GPU 架构深度性能优化**。

```text
@staticmethod
def make_ttgir(mod, metadata, opt, capability):
    """
    功能：优化后TTIR 转换 + 硬件层全套优化 → 生成TTGIR
    :param mod: 输入 = 优化完成的TTIR MLIR Module
    :param metadata: 编译元数据(grid、num_warps、num_ctas、num_stages等运行配置)
    :param opt: 编译参数：maxnreg、num_warps、num_stages、instrument插桩配置
    :param capability: GPU算力编号 80/86(Ampere),90/91(Hopper),100+(Blackwell)
    :return: 硬件感知的TTGIR Module
    """
    # 1. 全局寄存器上限配置：给整个模块挂载 ttg.maxnreg 属性，限制编译器分配的最大通用寄存器数量
    # 用来控制寄存器溢出到local memory，缓解寄存器压力、调控 occupancy
    if opt.maxnreg is not None:
        mod.set_attr("ttg.maxnreg", ir.builder(mod.context).get_int32_attr(opt.maxnreg))

    # 初始化MLIR Pass管理器，串行执行所有注册Pass；开启Debug保留IR源码位置信息
    pm = ir.pass_manager(mod.context)
    dump_enabled = pm.enable_debug()
    # 算力 >=80(Ampere) 硬件原生支持TF32浮点格式
    emuTF32 = (capability // 10 >= 8)

    # ============ 【最核心转换Pass：TTIR → TTGIR 方言转换】 ============
    # 参数说明：cuda:算力架构、num_warps(每个CTA的warp数量)、warp_size固定32、num_ctas
    # 作用：把纯计算语义的TTIR算子、访存语句，映射为GPU硬件资源模型（CTA/Block、Warp、寄存器、SharedMemory）
    passes.ttir.add_convert_to_ttgpuir(pm, f"cuda:{capability}", opt.num_warps, 32, opt.num_ctas)

    # ====================== 通用TTGIR基础优化（所有架构共用） ======================
    # 1. add_coalesce：全局内存访问合并优化，重排load/store地址，让warp内访存连续，提升显存带宽利用率
    passes.ttgpuir.add_coalesce(pm)
    # 2. f32_dot_tc：将普通f32点积运算映射到Tensor Core硬件单元，emuTF32为True时启用TF32加速
    passes.ttgpuir.add_f32_dot_tc(pm, emuTF32)
    # 3. PlanCTA：CTA(Block)资源规划：SM资源分配、SharedMemory尺寸预留、寄存器预算、CTA排布策略(NVIDIA专属Pass)
    nvidia.passes.ttnvgpuir.add_plan_cta(pm)
    # 4. 删除冗余的张量Layout格式转换指令，精简IR
    passes.ttgpuir.add_remove_layout_conversions(pm)
    # 5. 优化线程局部数据访问：提升寄存器复用、就近访问，减少内存往返开销
    passes.ttgpuir.add_optimize_thread_locality(pm)
    # 6. 矩阵乘法专用优化：瓦片划分、访存预取、计算流水线对齐，强化MMA执行效率
    passes.ttgpuir.add_accelerate_matmul(pm)
    passes.ttgpuir.add_remove_layout_conversions(pm)
    # 7. 优化MMA点积操作数排布，适配TensorCore硬件输入格式（算力>=80才生效）
    passes.ttgpuir.add_optimize_dot_operands(pm, capability >= 80)
    # 8. 优化TensorDescriptor描述符编码格式，压缩描述符占用的寄存器资源（NVIDIA）
    nvidia.passes.ttnvgpuir.add_optimize_descriptor_encoding(pm)
    # 9. 循环感知的CSE：识别循环内重复计算表达式，提升循环内部计算复用率
    passes.ttir.add_loop_aware_cse(pm)

    # ====================== 按GPU架构分支差异化优化 ======================
    # 分支1：cap 8xx(Ampere) / 9xx(Hopper)
    if capability // 10 in [8, 9]:
        # 嵌套循环融合：多层小循环合并为单层循环，消除循环控制开销
        passes.ttgpuir.add_fuse_nested_loops(pm)
        passes.common.add_canonicalizer(pm)
        # LICM：循环不变量外提，把循环内不会变化的计算提到循环外部执行
        passes.ttir.add_triton_licm(pm)
        passes.common.add_canonicalizer(pm)
        # 张量选择算子与if分支结构合并化简
        passes.ttgpuir.add_combine_tensor_select_and_if(pm)
        # Hopper专属：Warp Specialize（warp分工：一部分负责访存、一部分负责计算，访存计算流水线重叠）
        nvidia.passes.hopper.add_hopper_warpspec(pm, opt.num_stages, dump_enabled)
        # 根据流水线stage数目标记每条指令的硬件延迟，为后续调度提供依据
        passes.ttgpuir.add_assign_latencies(pm, opt.num_stages)
        # 指令重排调度：按照硬件延迟排布指令顺序，填充流水线气泡
        passes.ttgpuir.add_schedule_loops(pm)
        # 软件流水线Pipeline核心Pass：基于num_stages拆分访存/计算阶段，做流水线预取+计算重叠（GEMM/FlashAttention核心优化）
        passes.ttgpuir.add_pipeline(pm, opt.num_stages, dump_enabled)

    # 分支2：cap >=10 新一代Blackwell架构
    elif capability // 10 >= 10:
        passes.ttgpuir.add_fuse_nested_loops(pm)
        passes.common.add_canonicalizer(pm)
        passes.ttir.add_triton_licm(pm)
        # 优化累加器初始化逻辑，消除冗余清零指令
        passes.ttgpuir.add_optimize_accumulator_init(pm)
        # TMEM(Tensor Memory)内存分配提升作用域，减少频繁申请释放开销
        passes.ttgpuir.add_hoist_tmem_alloc(pm, False)
        # 将左值计算数据提升至TMEM存放，利用片上高速张量内存
        nvidia.passes.ttnvgpuir.add_promote_lhs_to_tmem(pm)
        passes.ttgpuir.add_assign_latencies(pm, opt.num_stages)
        passes.ttgpuir.add_schedule_loops(pm)
        # 通用Warp特化，比Hopper版本更通用
        passes.ttgpuir.add_warp_specialize(pm, opt.num_stages)
        passes.ttgpuir.add_pipeline(pm, opt.num_stages, dump_enabled)
        # 自动划分warp分区，均衡SM内硬件负载
        passes.ttgpuir.add_optimize_partition_warps(pm)
        passes.ttgpuir.add_combine_tensor_select_and_if(pm)
        # 再次上浮TMEM分配，支持if分支内的分配语句外提
        passes.ttgpuir.add_hoist_tmem_alloc(pm, True)
        # 清理无用的TMEM资源令牌
        nvidia.passes.ttnvgpuir.add_remove_tmem_tokens(pm)

    # 分支3：更早的老旧算力架构，仅执行基础LICM循环不变量外提
    else:
        passes.ttir.add_triton_licm(pm)

    # ====================== 全架构通用后置统一优化 ======================
    passes.common.add_canonicalizer(pm)
    passes.ttir.add_loop_aware_cse(pm)
    # Ampere专属：全局内存数据预取Prefetch，提前把数据加载到L2缓存
    if capability // 10 == 8:
        passes.ttgpuir.add_prefetch(pm)

    passes.ttgpuir.add_optimize_dot_operands(pm, capability >= 80)
    # 合并异步SharedMem拷贝指令，精简异步拷贝硬件事务
    passes.ttgpuir.add_coalesce_async_copy(pm)
    # 优化TMEM数据排布格式，提升片上张量内存访问效率
    nvidia.passes.ttnvgpuir.add_optimize_tmem_layouts(pm)
    # TMEM加载规约运算优化，规约计算下沉至片上内存完成
    nvidia.passes.ttnvgpuir.add_tmem_load_reduce(pm)
    # Hopper及以上架构：将高层张量描述符 lowered 为硬件原生TMA异步加载指令
    if capability // 10 >= 9:
        nvidia.passes.ttnvgpuir.add_tma_lowering(pm)

    passes.ttgpuir.add_remove_layout_conversions(pm)
    # TMEM数据交错排布优化，适配多Warp并发访问模式
    nvidia.passes.ttnvgpuir.add_interleave_tmem(pm)
    # 消除数据冗余拷贝，复用寄存器/TMEM数据
    passes.ttgpuir.add_reduce_data_duplication(pm)
    # 依据硬件延迟重新排序指令，减少流水线停顿
    passes.ttgpuir.add_reorder_instructions(pm)
    passes.ttir.add_loop_aware_cse(pm)
    # DCE死代码消除：删掉无用指令、未使用数值
    passes.common.add_symbol_dce(pm)
    # 自动插入GPU内存屏障Fence，保证SharedMem/TMEM访存读写顺序一致性
    nvidia.passes.ttnvgpuir.add_fence_insertion(pm, capability)
    # 将高层MMA算子降级为GPU硬件原生MMA汇编指令
    nvidia.passes.ttnvgpuir.add_lower_mma(pm)

    # SCCP：稀疏条件常量传播，编译期解析常量分支、折叠常量计算
    passes.common.add_sccp(pm)
    passes.common.add_cse(pm)
    passes.common.add_canonicalizer(pm)

    # 开启FPSAN浮点校验插桩时，注入浮点错误检测逻辑
    if "fpsan" in opt.instrumentation_mode:
        passes.ttgpuir.add_fp_sanitizer(pm, opt.fpsan_homomorphic_casts)
        passes.ttgpuir.add_remove_layout_conversions(pm, True)
        passes.common.add_canonicalizer(pm)
        passes.common.add_cse(pm)

    # 执行整条TTGIR Pass流水线
    pm.run(mod, 'make_ttgir')
    # 提取张量描述符元数据，存入编译元数据结构，后续LLVM编译阶段使用
    metadata["tensordesc_meta"] = mod.get_tensordesc_metadata()
    return mod

```

<br>重要pass详解：

<br>**基石必备】convert_to_ttgpuir（TTIR → TTGIR 方言转换 Pass）**

- passes.ttir.add_convert_to_ttgpuir(pm, f"cuda:{capability}", opt.num_warps, 32, opt.num_ctas)
- **语法域切换：**将 TTIR Dialect 全部算子合法转为 TTGPUIR (TTGIR) Dialect，是整个 TTGIR 所有后续 Pass 运行的基础，没有这一步，后面所有 TTGPUIR 专属 Pass 无法匹配任何 IR 节点。
- **注入 GPU 硬件抽象模型:**<br>

<br>**【带宽生命线】add_coalesce 全局内存访存合并 Pass**

- passes.ttgpuir.add_coalesce(pm)
- 核心原理：GPU 的 Warp 内 32 线程如果访存地址分散，会被硬件拆分为多次 DRAM 事务，连续对齐地址则被合并为一次总线传输（合并访存 coalesced access），带宽可提升数倍～数十倍。
- 具体工作：
- 地位：显存带宽是绝大多数算子的性能瓶颈，该 Pass 是 Triton 内核默认带宽优化最核心的兜底方案。<br><br>**【极致性能核心】软件流水线 Pipeline + Warp Specialize 两大王牌 Pass**<br>**add_pipeline 软件流水线 Pass（全架构通用，num_stages 控制）**<br>
- passes.ttgpuir.add_pipeline(pm, opt.num_stages, dump_enabled)
- GPU 执行存在明显延迟差异：Global 内存访问 (几百 cycle) > SMEM 访问 > ALU 计算 (几 cycle)。
- Pipeline 将循环拆分为「访存阶段、计算阶段」，多阶段重叠执行：当前迭代计算的同时，预取下一轮迭代的数据，用计算延迟掩盖访存长延迟。<br>
- 这是让 Triton 内核从“能跑”变成“跑得快”的最核心优化。它使得 GPU 不再受制于显存延迟，性能直接逼近硬件峰值算力。

**Warp Specialize（Hopper 专属 + 通用版 warp_specialize）**<br># Hopper架构 nvidia.passes.hopper.add_hopper_warpspec(pm, opt.num_stages, dump_enabled) # Blackwell新架构通用版本 passes.ttgpuir.add_warp_specialize(pm, opt.num_stages)

- 角色解耦：
- 彻底做到数据搬运与矩阵计算完全硬件并行执行，把访存延迟彻底隐藏，是 Hopper 及以上显卡压榨硬件极限性能的关键技术（FlashAttention3、vLLM 核心内核重度依赖）。
- 影响：彻底消灭了计算单元在等待内存时的空闲时间，实现了真正的“生产-消费”流水线，性能实现代际飞跃。<br><br>**硬件指令落地闭环】MMA Lower + TMA Lower 指令生成 Pass**<br>**add_lower_mma：高层矩阵运算降级为硬件 MMA 指令**
- nvidia.passes.ttnvgpuir.add_lower_mma(pm)
- 为何最重要：GPU 的算力神话全部建立在 Tensor Core 上。这个 Pass 是将抽象的矩阵乘法真正翻译成硬件物理指令的最后一环。
- 指令匹配：将高层的 `dot` 操作降级为特定架构的 MMA 硬件指令语义。<br>

**add_tma_lowering（Hopper 及以上生效）**<br>if capability // 10 >= 9: nvidia.passes.ttnvgpuir.add_tma_lowering(pm)

- 为何最重要：在 Ampere 及之前的架构中，加载内存需要占用宝贵的线程寄存器去计算复杂的偏移地址。Hopper 引入的 TMA 引擎改变了游戏规则。

**Hopper 架构新增TMA 硬件批量加载单元**，替代传统的`ld.global`指令：硬件自动完成地址计算、对齐、批量数据传输、填充 SMEM，极大降低 SM 内核的指令开销与寄存器占用。该 Pass 把张量描述符加载逻辑转为硬件原生 TMA 指令，是新一代显卡访存提速的核心。

- 描述符替代指针：将高层 IR 中的多维张量访存操作，降级为对 TMA 硬件引擎的调用。不再由线程计算地址，而是由编译器生成张量描述符，告诉 TMA 引擎：“帮我搬一个 `[128, 64]` 的数据块到 Shared Memory”。
- 解放寄存器与带宽：TMA 是一个独立的硬件 DMA 引擎，单条指令即可搬运大块数据。这彻底解放了线程的地址计算寄存器，同时也保证了 100% 的内存对齐和带宽利用率。
- 影响：与 `add_hopper_warpspec` 配合，构成了 Hopper 架构高性能计算的基石。它让 Triton 能够以最低的指令开销、最高的带宽利用率将数据喂给 Tensor Core。<br><br>IR变换分析：<br>ConvertTritonToTritonGPU：

```text
def make_llir(self, src, metadata, options, capability):
    # 根据编译配置 + GPU架构，匹配对应PTX版本号
    ptx_version = get_ptx_version_from_options(options, self.target.arch)

    mod = src  # 入参：优化完成的TTGIR MLIR Module
    # ====================== 阶段1：初始化PassManager，开启调试位置信息 ======================
    pm = ir.pass_manager(mod.context)
    pm.enable_debug()  # 保留loc源码行列号，用于报错、性能profile、IR dump溯源

    # ========== 可选工具插桩：GSan 全局内存检测（调试工具，生产关闭） ==========
    if "gsan" in options.instrumentation_mode:
        # 写入GSAN所需PDL调度参数属性
        mod.set_attr("tti.gsan_launch_pdl", ir.builder(mod.context).get_int32_attr(int(options.launch_pdl)))
        passes.ttgpuir.add_global_sanitizer(pm)

    # ====================== 【TTGIR预处理Pass序列】 ======================
    # 合并张量select选择语句与if分支结构，精简控制流
    passes.ttgpuir.add_combine_tensor_select_and_if(pm)
    # 分配warp分组资源，consan为内存越界检测工具开关
    passes.ttgpuir.add_allocate_warp_groups(pm, "consan" in options.instrumentation_mode)
    # SCF结构化控制流 → 原始CF跳转分支（MLIR结构化循环/if转为底层跳转指令形式）
    passes.convert.add_scf_to_cf(pm)
    # Gluon内核代码内联展开
    passes.gluon.add_inliner(pm)
    # Consan内存捕获预处理（仅调试检测使用）
    if "consan" in options.instrumentation_mode:
        passes.ttgpuir.add_prepare_consan_captures(pm, "nvidia")

    # ========== 关键硬件内存分配：TTGIR声明 → 真实内存布局分配 ==========
    # 1. 分配静态SharedMemory：计算每个CTA块SMEM实际字节大小、排布、bank冲突规避对齐
    nvidia.passes.ttgpuir.add_allocate_shared_memory_nv(pm, capability, ptx_version)
    # 2. 分配Tensor Memory(TMEM)片上张量内存（Hopper+架构），分配TMEM空间与地址映射
    nvidia.passes.ttnvgpuir.add_allocate_tensor_memory(pm)
    # 检查矩阵乘法双CTA协同计算相关合法性与资源校验
    nvidia.passes.ttnvgpuir.add_check_matmul_two_cta(pm)

    # 外部注入自定义IR改写钩子（框架层埋点，用户/上层可注入自定义Pass）
    if CUDABackend.instrumentation:
        CUDABackend.instrumentation.patch("ttgpuir_to_llvmir", pm, mod.context)

    # ========== 内存同步屏障插入：保证异步访存、TMEM/SMEM读写可见性 ==========
    # 代理栅栏插入：处理流水线、异步拷贝的内存顺序
    nvidia.passes.ttnvgpuir.add_proxy_fence_insertion(pm, capability)
    # TMEM硬件屏障插入，保障多Warp对TMEM的读写同步
    nvidia.passes.ttnvgpuir.add_tmem_barrier_insertion(pm)

    # ====================== 核心降级1：TTGPUIR 方言 → NVVM Dialect(MLIR层) ======================
    nvidia.passes.ttgpuir.add_to_llvmir(pm, capability, ptx_version, "consan" in options.instrumentation_mode)
    # 初始化Warp Cluster集群屏障（Hopper多CTA集群通信硬件原语）
    nvidia.passes.ttnvgpuir.add_initialize_ws_cluster_barriers(pm, capability, ptx_version)

    # 对刚生成的NVVM IR做规范化整理
    passes.ttgpuir.add_canonicalize_llvm_ir(pm)
    passes.common.add_cse(pm)  # 公共子表达式消除，精简冗余计算

    # Warp特化相关逻辑下沉映射到NVVM指令
    nvidia.passes.ttnvgpuir.add_warp_specialize_to_llvm(pm)
    # ====================== 核心降级2：NVVM Dialect → 标准LLVM Dialect(MLIR) ======================
    nvidia.passes.ttnvgpuir.add_nvgpu_to_llvm(pm)

    # 两轮规范化 + CSE + 死代码清扫，规整LLVM MLIR格式
    passes.common.add_canonicalizer(pm)
    passes.common.add_cse(pm)
    passes.common.add_symbol_dce(pm)
    # MLIR NVVM Dialect 彻底翻译成原生LLVM IR Dialect
    passes.convert.add_nvvm_to_llvm(pm)

    # ========== 源码调试信息DI：行号、变量映射（用于gdb、Nsight调试） ==========
    if not knobs.compilation.disable_line_info and not knobs.compilation.dump_ir_extract_di_local_variables:
        passes.llvmir.add_di_scope(pm)

    # 第二层自定义注入点：LLVM MLIR阶段外部修改
    if CUDABackend.instrumentation:
        CUDABackend.instrumentation.patch("llvmir_to_llvm", pm, mod.context)

    # 执行整条TTGIR->LLVM MLIR Pass流水线
    pm.run(mod, 'make_llir')

    # ========== 分离执行局部变量DI信息（注释说明：合并执行会触发MLIR/pybind段错误，必须拆分两个PassManager运行） ==========
    if knobs.compilation.dump_ir_extract_di_local_variables:
        # 第一步：先构建DI文件/函数作用域
        if not knobs.compilation.disable_line_info:
            pm = ir.pass_manager(mod.context)
            pm.enable_debug()
            passes.llvmir.add_di_scope(pm)
            pm.run(mod, 'make_llir.disable_line_info')

        # 第二步：插入本地变量调试元数据（变量名、类型、源码位置）
        pm = ir.pass_manager(mod.context)
        pm.enable_debug()
        passes.llvmir.add_di_local_variable(pm)
        pm.run(mod, 'make_llir.dump_ir_extract_di_local_variables')

    # ====================== 阶段2：MLIR LLVM Dialect → 原生LLVM C++ Module对象 ======================
    llvm.init_targets()  # 初始化NVPTX目标后端
    context = llvm.context()
    # AMD后端才支持ASAN，NVIDIA不支持，直接抛错拦截
    if knobs.compilation.enable_asan:
        raise RuntimeError(
            "Address Sanitizer Error: Address sanitizer is currently only supported on the AMD backend")
    # MLIR LLVM Dialect 转换成LLVM原生Module
    llvm_mod = llvm.to_module(mod, context)

    # Blackwell sm_107 向下兼容映射为llvm识别的100架构标识
    if capability == 107:
        cap_llvm = 100
    else:
        cap_llvm = capability
    # 将数字capability转为LLVM识别的sm_xx字符串(sm_80/sm_86/sm_90)
    proc = sm_arch_from_capability(cap_llvm)
    # 解析当前架构对应的LLVM硬件Feature（TensorCore、TMA、WarpCluster、FP8等指令集开关）
    features = get_features(options, cap_llvm)
    triple = 'nvptx64-nvidia-cuda'  # NVIDIA PTX固定target triple
    nvidia.set_short_ptr()  # 开启nvptx短指针优化
    # 绑定数据布局DataLayout + 目标架构 + 硬件特性，LLVM后端生成指令依赖此配置
    llvm.attach_datalayout(llvm_mod, triple, proc, features)
    # FTZ(Flush To Zero)浮点冲刷置零反射属性配置
    if options.enable_reflect_ftz:
        nvidia.set_nvvm_reflect_ftz(llvm_mod)

    # 链接外部第三方库（算子依赖的外部obj库）
    if options.extern_libs and nvidia.has_extern_deps(llvm_mod):
        paths = [path for (name, path) in options.extern_libs]
        llvm.link_extern_libs(llvm_mod, paths)

    # ========== LLVM O3最高级别优化 ==========
    # 修复ptxas已知bug：sm_80下LLVM SLP向量化生成的PTX会被ptxas拒绝，因此Ampere强制关闭SLP
    llvm.optimize_module(llvm_mod, llvm.OPTIMIZE_O3, disable_slp_vectorizer=capability == 80)

    # ====================== 提取内核硬件资源元数据存入metadata字典 ======================
    # warp特化会改写num_warps数值，从TTGIR属性读取真实值
    total_num_warps = src.get_int_attr("ttg.total-num-warps")
    if total_num_warps is not None:
        metadata["num_warps"] = total_num_warps
    metadata["shared"] = src.get_int_attr("ttg.shared")                # 单个Block占用SMEM字节
    metadata["tmem_size"] = src.get_int_attr("ttg.tensor_memory_size") # TMEM片上内存大小
    metadata["global_scratch_size"] = src.get_int_attr("ttg.global_scratch_memory_size") or 0
    metadata["global_scratch_align"] = src.get_int_attr("ttg.global_scratch_memory_alignment") or 1
    metadata["profile_scratch_size"] = src.get_int_attr("ttg.profile_scratch_memory_size") or 0
    metadata["profile_scratch_align"] = src.get_int_attr("ttg.profile_scratch_memory_alignment") or 1

    # 将LLVM Module导出为纯文本LLVM IR字符串，作为函数返回值
    ret = str(llvm_mod)
    # 手动释放底层C++对象，避免内存泄漏
    del llvm_mod
    del context
    return ret

```

<br>重要pass详解：<br>**物理内存落地的总调度：`add_allocate_shared_memory_nv`**

- 为何最重要：在 TTGIR 阶段，所有对 Shared Memory 的使用都是逻辑概念——IR 中只写着"这里需要一块共享内存"，但没有任何物理地址。如果没有这个 Pass，后续生成的 LLVM IR 中的访存指令将没有地址可用，Kernel 根本无法启动。
- 核心原理：
- 核心计算过程：

**跨越两个世界的桥梁：`add_to_llvmir`（TTGPUIR → NVVM MLIR）**

- passes.ttgpuir.add_to_llvmir(pm, capability, ptx_version, "consan" in options.instrumentation_mode)
- 为何最重要：这是整个 `make_llir` 函数的灵魂步骤。它完成了从"Triton 专用 IR"到"通用 LLVM IR"的彻底翻译。跨过这一步，Triton 的所有高级抽象将不复存在。<br>
- 核心原理：将 Triton GPU IR 中特有的操作，逐一翻译为标准 LLVM IR 指令或 NVVM intrinsic 调用：

| TTGIR 中的操作 | 降级后的 LLVM IR |
| --- | --- |
| tt.load | llvm.load 或 @llvm.nvvm.cp.async |
| tt.store | llvm.store |
| tt.dot → MMA (已降级) | @llvm.nvvm.mma.sync(...) / @llvm.nvvm.wgmma(...) |
| tt.barrier | @llvm.nvvm.barrier0() |
| 线程索引 program_id | @llvm.nvvm.read.ptx.sreg.tid.x() |

- 同时，它将 GPU 的线程模型（CTA → Warp → Lane）映射到 LLVM 的 NVVM 抽象层，使得后续 LLVM 后端能够理解"这是一个 GPU Kernel"。<br><br>**`add_warp_specialize_to_llvm` + `add_nvgpu_to_llvm`（NVVM → 标准 LLVM Dialect）**<br>**硬件级异步并行的终极翻译：`add_warp_specialize_to_llvm`**
- nvidia.passes.ttnvgpuir.add_warp_specialize_to_llvm(pm)
- 为何最重要：Hopper 架构的 Warp 特化（Producer/Consumer 模型）是性能飞跃的关键。但在 TTGIR 阶段，这只是一种逻辑标注——IR 中标记了"这些 Warp 是 Producer，那些是 Consumer"，但没有任何同步指令。此 Pass 负责将这些抽象标注翻译为真实的硬件同步原语。
- 核心原理：

### <br><br>3.4.4 make_ptx

```text
def make_ptx(self, src, metadata, opt, capability):
    # 根据编译配置 + GPU硬件架构，解析对应的PTX版本号（如 78 → PTX 7.8）
    ptx_version = get_ptx_version_from_options(opt, self.target.arch)

    # NVIDIA PTX固定目标三元组：64位NVPTX架构、nvidia厂商、cuda系统
    triple = 'nvptx64-nvidia-cuda'

    # 架构兼容映射：sm_107 统一映射为LLVM识别的100架构标识
    if capability == 107:
        cap_llvm = 100
    else:
        cap_llvm = capability

    # 将数字capability转为sm_xx字符串（80 → sm_80、90 → sm_90）
    proc = sm_arch_from_capability(cap_llvm)
    # 获取当前GPU架构对应的LLVM硬件特性集（TMA、MMA、FP8、WarpCluster等指令开关）
    features = get_features(opt, cap_llvm)
    # LLVM nvptx后端编译flag：开启mad宽操作优化，提升乘累加指令效率
    flags = ["nvptx-mad-wide-opt"]
    # 开启FPSAN浮点检测时，对GEP全局地址表达式做规范化处理
    canonicalize_gep = "fpsan" in opt.instrumentation_mode

    # ==================== 核心调用：LLVM将LLVM IR文本编译为PTX汇编 ====================
    # src：上一级make_llir输出的标准LLVM IR字符串
    # 入参含义：LLVM_IR、triple、架构、硬件特性、编译标记、是否开启浮点融合、禁用内嵌汇编、是否规范化GEP
    ret = llvm.translate_to_asm(
        src, triple, proc, features, flags,
        opt.enable_fp_fusion, False, canonicalize_gep
    )

    # 正则匹配提取PTX中的内核entry函数名，一个文件只会存在单个kernel入口
    names = re.findall(r".visible .entry ([a-zA-Z_][a-zA-Z0-9_]*)", ret)
    # 强制校验只能存在一个内核函数
    assert len(names) == 1
    # 将内核名称写入元数据，上层运行时加载cubin需要kernel name
    metadata["name"] = names[0]

    # ==================== PTX文本后处理：替换版本号、目标架构 ====================
    # 数值拆分：ptx_version=78 → "7.8"
    ptx_version = f'{ptx_version//10}.{ptx_version%10}'
    # 替换PTX文件头部 .version 字段为编译指定的PTX版本
    ret = re.sub(r'\.version \d+\.\d+', f'.version {ptx_version}', ret, flags=re.MULTILINE)
    # 替换 .target sm_xx 为真实硬件capability对应的架构标识
    ret = re.sub(r'\.target sm_\d+', f'.target sm_{capability}', ret, flags=re.MULTILINE)

    # 未开启局部变量调试信息导出时，移除PTX内debug标记
    # 作用：去掉debug属性后ptxas会执行更强的优化；代价：cuda-gdb无法查看源码变量名与类型
    if not knobs.compilation.dump_ir_extract_di_local_variables:
        ret = re.sub(r",\s*debug|debug,\s*", "", ret)

    # 全局开关开启时，控制台打印完整PTX汇编代码（调试查看汇编使用）
    if knobs.nvidia.dump_nvptx:
        print("// -----// NVPTX Dump //----- //")
        print(ret)

    # 返回处理完成的纯文本PTX汇编代码
    return ret

```

## 4. 国产芯片Triton编译路线

- 各家芯片厂商 Triton编译路径选择深度分析：
- FlagTree之各家芯片triton Lower 过程整理：

| 芯片厂商 | 硬件架构 | 编译路径 | 流水线 | 最终产物 | 核心优化层 |
| --- | --- | --- | --- | --- | --- |
| NVIDIA | GPGPU（SM+Tensor Core） | TritonGPU | ttir→ttgir→llir→ptx→cubin | cubin | make_ttgir（Hopper warpspec/Blackwell tmem） |
| AMD | GPGPU（CU+MFMA） | TritonGPU | ttir→ttgir→llir→amdgcn→hsaco | hsaco | make_ttgir（stream_pipeline/pingpong） |
| 摩尔线程 | GPGPU（MUSA，CUDA兼容） | TritonGPU | ttir→ttgir→llir→mubin | mubin | make_ttgir（SQMMA/TME） |
| 海光 | GPGPU（DCU，HIP兼容） | TritonGPU | ttir→ttgir→llir→amdgcn→hsaco | hsaco | make_ttgir（stream_pipeline/warp_spec） |
| 天数智芯 | GPGPU（CUDA兼容） | TritonGPU | ttir→ttgir→llir→asm→cubin | cubin | make_ttgir（Hopper warpspec/tmem） |
| 燧原 | NPU（GPGPU-like） | TritonGPU+自定义 | ttir→ttgir→gcuir→llir→fatbin | fatbin | make_gcuir（TritonGCU Dialect） |
| 寒武纪 | NPU（MLU，NRAM/WRAM/SRAM） | Linalg | ttir→linalg→linalgopt→mluir→mluiropt→mlisa→cnbin | cnbin | make_linalg+make_optimized_linalg+make_mluir |
| 华为昇腾 | NPU（达芬奇，Cube/Vector/Scalar） | Linalg | ttir→ttadapter→npubin | npubin | ttir_to_linalg（HIVM/hfusion/DAG调度） |

<br>FlagTree 作为 fork 自 triton-lang/triton 的统一编译器，支持**两条核心编译路径：TritonGPU dialect 路径和 Linalg dialect 路径**。这种双路径设计是 FlagTree 多后端支持的核心，也是各家芯片厂商接入 Triton 生态时面临的第一个也是**最关键的架构决策**。<br>

- TritonGPU 路径继承自上游 Triton，面向 GPGPU 架构芯片，编译流程为 **Triton Python → TTIR → TTGIR → LLVM IR → 后端特定机器码**；
- Linalg 路径是 FlagTree 为非 GPGPU 架构芯片新增的编译路径，通过 FLIR（FlagTree IR，fork 自 microsoft/triton-shared）**将 TTIR 转换为 Linalg dialect，再由各厂商的后端编译器处理**。

这种路径分化的根本原因是硬件架构的差异。<br>

- GPGPU 架构（如 NVIDIA、AMD、摩尔线程 MUSA）的编程模型基于**线程块、warp、共享内存等 GPU 概念**，可以直接复用 **TritonGPU 的编译流水线**；
- 而非 GPGPU 架构（如华为昇腾达芬奇、寒武纪 MLU）的编程模型与 GPU 差异较大，需要通过 Linalg dialect 进行中间转换。
- 值得注意的是，燧原（Enflame）作为 NPU 厂商，却选择了 TritonGPU 路径，这在 NPU 厂商中是独特的，值得深入分析。
