## SGLang：结构化语言模型程序的高效执行

### 摘要

大型语言模型（Large Language Models, LLMs）正越来越多地被用于需要多次生成调用、高级提示技术（advanced prompting techniques）、控制流以及结构化输入/输出的复杂任务。然而，目前缺乏高效的编程和执行此类应用的系统。我们提出 SGLang，一个用于高效执行复杂语言模型程序的系统。SGLang 包含前端语言（frontend language）和运行时（runtime）两部分。前端通过提供生成和并行控制的原语（primitives）简化编程过程。运行时则通过新颖的优化技术加速执行，例如用于键值缓存（KV cache）复用的 RadixAttention 以及用于加速结构化输出解码的压缩有限状态机（compressed finite state machines）。实验表明，在多种大型语言和多模态模型上，针对智能体控制（agent control）、逻辑推理（logical reasoning）、少样本学习基准（few-shot learning benchmarks）、JSON 解码、检索增强生成（retrieval-augmented generation, RAG）流水线以及多轮对话（multi-turn chat）等任务，SGLang 的吞吐量相比最先进的推理系统最高可提升 6.4 倍。代码已开源在

[https://github.com/sgl-project/sglang](https://github.com/sgl-project/sglang)

## 1 引言

近年来，大语言模型（LLMs）能力的提升拓展了其应用范围，使其能够处理更广泛的通用任务，并充当自主智能体[35, 6, 36, 52, 46]。在此类应用中，LLMs 参与多轮规划、推理以及与外部环境的交互。这通过工具使用[41, 38]、多输入模态[47, 2]以及多种提示技术[30]（如少样本学习[5]、自一致性[53]、思维骨架[33]和思维树[56]）得以实现。所有这些新用例都需要多次（通常是相互依赖的）LLM 生成调用，显示出使用多调用结构完成复杂任务的趋势[57, 21]。这些模式的出现标志着我们与 LLMs 交互方式的转变，从简单的聊天演变为更复杂的 LLMs 程序化使用形式，即通过程序来调度和控制 LLMs 的生成过程。我们将这些程序称为”语言模型程序”（Language Model Programs, LM Programs）[4, 20]。上述高级提示技术和智能体工作流均属于 LM 程序的范畴。LM 程序具有两个共同特性：（1）LM 程序通常包含多次 LLM 调用，其间穿插控制流。这对于完成复杂任务和提升整体质量是必要的。（2）LM 程序接收结构化输入并产生结构化输出。这对于实现 LM 程序的组合以及将 LM 程序集成到现有软件系统中是必要的。

尽管 LM 程序（LM programs）已被广泛使用，但当前用于表达和执行这些程序的系统仍然效率低下。我们识别出与高效使用 LM 程序相关的两个主要挑战：首先，由于 LLM 的非确定性（non-deterministic）特性，编写 LM 程序既繁琐又困难。开发一个 LM 程序通常需要大量的字符串操作、提示词（prompt）的实验性调优、脆弱的输出解析、处理多种输入模态以及实现并行机制。这种复杂性显著降低了即使是简单程序的可读性（第 2 节）。

其次，也是重要的是，由于冗余计算和内存使用，执行 LM 程序的效率低下。最先进的推理引擎（例如 vLLM [23]、TGI [16] 和 TensorRT-LLM [34]）已针对降低延迟和提高吞吐量进行了优化，但缺乏对工作负载的直接了解。这使得这些系统通用且鲁棒，但也导致任何给定工作负载下出现显著的效率低下问题。一个突出的例子是键值缓存（Key-Value cache，KV cache）的重用（第 3 节）。KV 缓存由可重用的中间张量（intermediate tensors）组成，这些张量对于生成式推理至关重要。在 LM 程序的典型批量执行过程中，存在大量机会在共享公共前缀的多个不同 LLM 调用之间重用 KV 缓存。然而，当前系统缺乏有效的机制来促进这种重用，导致不必要的计算和内存浪费。另一个例子是针对结构化输出（例如 JSON 模式）的约束解码（constrained decoding），其中 LLM 的输出被限制为遵循由正则表达式（regular expression）定义的特定语法规则（第 4 节）。在这些约束下，通常可以一次解码多个词元（token）。然而，现有系统一次只解码一个词元，导致解码速度欠佳。

为了解决这些挑战，我们提出了 SGLang，一种用于 LLM 的结构化生成语言（Structured Generation Language）。核心思想是系统地利用 LM 程序中的多调用结构（multi-call structure）以实现高效执行。如图 1 所示，它包含两个部分：一个前端语言和一个后端运行时。前端简化了 LM 程序的编程，运行时加速了其执行。这两个部分可以协同工作以获得更好的性能，但也可以独立运行。

我们将 SGLang 作为一种嵌入在 Python 中的领域特定语言（domain-specific language）引入。它提供了用于生成（例如 extend、gen、select）和并行控制（例如 fork、join）的原语。SGLang 与 Python 的控制流和库兼容，因此用户可以轻松地使用原生 Python 语法开发高级提示词工作流。我们提供了一个解释器和一个编译器。解释器（Interpreter）将提示状态（prompt state）作为流（stream）进行管理，并将原始操作（primitive operations）提交到该流中以供异步执行，从而确保对同步（synchronization）和程序内并行性（intra-program parallelism）的适当控制。此外，SGLang 程序可以被追踪（traced）并编译，以实现更多优化。

在运行时（runtime）方面，我们提出了几种新颖的优化方法，以加速 SGLang 程序的执行。第一种技术是 RadixAttention，它能够实现跨多个生成调用（generation calls）的 KV 缓存（KV cache）的自动重用。在现有的推理引擎中，一个请求的 KV 缓存在处理完成后即被丢弃，这阻止了 KV 缓存在多个调用之间重用，并显著降低了执行速度。相反，我们的系统在基数树（radix tree）内维护所有请求的 KV 缓存的 LRU 缓存（LRU cache）。这种方法将 KV 缓存作为传统缓存进行管理，并使用基数树进行高效匹配、插入和驱逐。它允许运行时通过缓存感知调度策略（cache-aware scheduling policy）高效地处理各种重用模式。第二种技术是压缩有限状态机（compressed finite state machine），它能够实现对结构化输出（structured outputs）的更快的约束解码（constrained decoding）。现有系统仅通过屏蔽不允许标记（tokens）的概率来遵循下一个标记的约束，这使得它们一次只能解码一个标记。相反，我们的系统分析约束并构建一个压缩有限状态机来表示该约束。这种方法尽可能地将多标记路径（multi-token path）压缩为单步路径（single-step path），从而允许一次解码多个标记，以实现更快的解码速度。最后，SGLang 还支持仅 API 模型（API-only models），例如 OpenAI 的 GPT-4，我们引入了第三种技术，即 API 推测执行（API speculative execution），以优化仅 API 模型的多调用程序。

使用 SGLang，我们实现了各种 LLM 应用，包括智能体控制（agent control）、逻辑推理（logical reasoning）、少样本学习基准（few-shot learning benchmarks）、JSON 解码（JSON decoding）、检索增强生成流水线（retrieval-augmented generation pipelines）、多轮对话（multi-turn chat）和多模态处理（multi-modality processing）。我们在包括 Llama-7B/70B [49]、Mistral-8x7B [17]、LLaVA-v1.5-7B（图像）[28] 和 LLaVA-NeXT-34B（视频）[62] 的模型上，在 NVIDIA A10G 和 A100 GPU 上测试了性能。实验结果表明，与现有的编程和推理系统（包括 Guidance [13]、vLLM [23] 和 LMQL [4]）相比，SGLang 在广泛的工作负载、模型和硬件设置上实现了高达 6.4 倍的吞吐量提升。

### 2 编程模型

本节通过一个运行示例介绍SGLang编程模型，描述其语言原语和执行模式，并概述运行时优化机会。该编程模型通过提供灵活且可组合的原语，简化了多调用工作流中的繁琐操作（例如字符串操作、API调用、约束指定、并行处理）。

**运行示例**。 该语言是嵌入在Python中的领域特定语言（Domain-Specific Language）。图2展示了一个使用分支-求解-合并提示方法[40]评估关于图像的论文的程序。函数`multi_dimensional_judge`接受三个参数：`s`、`path`和`essay`。`s`管理提示状态，`path`是图像文件路径，`essay`是论文文本。可以使用`+=`运算符将新字符串和SGLang原语附加到状态`s`以执行。首先，函数将图像和论文添加到提示中。然后，它使用`select`检查论文是否与图像相关，并将结果存储在`s["related"]`中。如果相关，提示被分叉为三个副本，用于从不同维度进行并行评估，使用`gen`将结果存储在`f["judgment"]`中。接下来，它合并判断结果，生成摘要，并分配一个字母等级评分。最后，它按照正则表达式约束`regex`定义的架构，以JSON格式返回结果。SGLang极大地简化了这个程序，获得更好的评分。最后，它按照由正则表达式约束（regex）定义的架构，以 JSON 格式返回结果。SGLang 极大地简化了这一程序，因为使用类似 OpenAI API 接口的等效程序，由于需要手动进行字符串操作和并行控制，其代码行数将是 SGLang 的 2.1 倍。

**语言原语（Language Primitives）**。 SGLang 提供了用于控制提示状态（prompt state）、生成（generation）和并行性（parallelism）的原语。它们可以与 Python 语法和库一起使用。以下是这些原语：

- `gen`：调用模型进行生成，并将结果存储在其第一个参数指定的变量中。它支持一个 `regex` 参数，用于约束输出遵循由正则表达式定义的语法（例如，JSON 架构）。
- `select`：调用模型从列表中选择概率最高的选项。
- 运算符 `+=` 或 `extend`：将字符串追加到提示中。
- 运算符 `[variable_name]`：获取生成的结果。
- `fork`：创建提示状态的并行分支。
- `join`：重新合并提示状态。
- `image` 和 `video`：接收图像和视频输入。

### 3 通过 RadixAttention 实现高效的 KV 缓存复用

> RadixAttention 是论文最核心的贡献，最重要的一部分

SGLang 程序可以链式调用多个生成调用（generation calls），并通过 “fork” 原语创建并行副本。此外，不同的程序实例通常共享一些公共部分（例如系统提示词）。这些场景在执行过程中会产生许多共享的提示词前缀（prompt prefixes），从而带来大量复用 KV 缓存的机会。在大语言模型推理过程中，KV 缓存存储了前向传播（forward pass）产生的中间张量（intermediate tensors），用于解码后续的令牌（tokens）。它们以自注意力机制（self-attention mechanism）中的键值对（key-value pairs）命名 [51]。KV 缓存的计算仅依赖于前缀令牌（prefix tokens）。因此，具有相同提示词前缀的请求可以复用 KV 缓存，从而减少冗余计算和内存占用。更多背景信息和一些示例见附录 A。

鉴于 KV 缓存复用的机会，优化 SGLang 程序的一个关键挑战是在多个调用和实例之间复用 KV 缓存。虽然一些系统探索了某些 KV 缓存复用场景 [23, 58, 18, 12]，但它们通常需要手动配置，并且无法处理所有复用模式（例如动态树结构）。因此，大多数最先进的推理系统（state-of-the-art inference systems）会为每个请求重新计算 KV 缓存。我们将在第 7 节中讨论它们的局限性以及我们方法的差异。

本节介绍 RadixAttention，这是一种在运行时实现自动化和系统性 KV 缓存复用的新技术。与现有系统在生成请求完成后丢弃 KV 缓存（KV cache）不同，我们的系统将提示词和生成结果的缓存保留在一棵基数树（radix tree）中，从而实现高效的前缀搜索、复用、插入和驱逐。我们实现了一种 LRU 驱逐策略（LRU eviction policy）和一种缓存感知调度策略（cache-aware scheduling policy），以提高缓存命中率。RadixAttention 与连续批处理（continuous batching）[60]、分页注意力（paged attention）[23] 和张量并行（tensor parallelism）[44] 等技术兼容。此外，在无缓存命中的情况下，它仅引入可忽略不计的内存和时间开销。

**RadixAttention**。基数树是一种数据结构，可作为经典字典树（trie，前缀树）的空间高效替代方案。与典型树不同，基数树的边不仅可以标记为单个元素，还可以标记为长度各异的元素序列，从而显著提升效率。在我们的系统中，我们利用基数树来管理令牌序列（token sequences）与其对应 KV 缓存张量（KV cache tensors）之间的映射。这些 KV 缓存张量以非连续的分页布局（non-contiguous, paged layout）存储，其中每页的大小相当于一个令牌。由于 GPU 内存很快会被 KV 缓存填满，我们引入了一种简单的 LRU 驱逐策略，该策略优先驱逐最近最少使用的叶节点。通过优先驱逐叶节点，我们能够复用其共同祖先节点，直到这些祖先节点也变为叶节点并被驱逐。

在连续批处理设置中，我们无法驱逐当前运行批次所使用的节点。因此，每个节点维护一个引用计数器（reference counter），指示有多少正在运行的请求正在使用它。当节点的引用计数器为零时，该节点可被驱逐。请注意，我们并未预分配固定大小的内存池作为缓存。相反，我们让缓存的令牌和当前正在运行的请求共享同一内存池。因此，系统会动态地为缓存和运行请求分配内存。当有足够的等待请求运行时，系统将驱逐所有缓存的令牌，以支持更大的批次大小。图 3 展示了如何为多个传入请求维护基数树。

图3：采用LRU驱逐策略的RadixAttention操作示例，展示了九个时间点的状态。该图展示了基数树（radix tree）在响应各种请求时的动态演化过程。这些请求包括两个聊天会话、一批少样本学习（few-shot learning）查询以及一次自一致性采样（self-consistency sampling）。每条树边带有一个标签，表示一个子字符串或一个令牌序列。节点通过颜色编码反映不同状态：绿色表示新添加的节点，蓝色表示在该时间点被访问的缓存节点，红色表示已被驱逐的节点。在步骤(1)中，基数树初始为空。在步骤(2)中，服务器处理传入的用户消息”你好”，并以LLM输出”嗨”作为响应。系统提示”你是一个乐于助人的助手”、用户消息”你好！”和LLM回复”嗨！”被合并到树中，作为连接到新节点的一条边。在步骤(3)中，一个新的提示到达，服务器在基数树中找到该提示的前缀（即对话的第一轮），并重用其KV缓存。新的一轮作为新节点附加到树中。在步骤(4)中，一个新的聊天会话开始。来自(3)的节点”b”被拆分为两个节点，以允许两个聊天会话共享系统提示。在步骤(5)中，第二个聊天会话继续。然而，由于内存限制，来自(4)的节点”c”必须被驱逐。新的一轮附加在(4)中节点”d”之后。在步骤(6)中，服务器收到一个少样本学习查询。处理它，并将其插入树中。由于新查询与现有节点没有任何共同前缀，根节点被拆分。在步骤（7）中，服务器接收到一批额外的少样本学习（few-shot learning）查询。这些查询共享同一组少样本示例，因此我们从步骤（6）中拆分节点 ‘e’ 以实现共享。在步骤（8）中，服务器接收到来自第一个聊天会话的新消息。它驱逐了第二个聊天会话中的所有节点（节点 “g” 和 “h”），因为它们最近最少使用。在步骤（9）中，服务器接收到一个请求，要求为步骤（8）中节点 “j” 内的问题采样更多答案，这可能是为了自一致性提示（self-consistency prompting）。为了给这些请求腾出空间，我们驱逐了步骤（8）中的节点 “i”、”k” 和 “l”。

前端解释器将完整的提示（prompts）发送给运行时（runtime），运行时执行前缀匹配和重用。树结构存储在中央处理器（CPU）上，维护开销可忽略不计。在执行分叉（fork）原语期间，前端首先发送前缀作为提示，确保前缀正确插入树中，然后再发送剩余的提示。这种“前端提示”（Frontend Hint）简化了运行时的调度和匹配，体现了前端-运行时协同设计（frontend-runtime co-design）的优势。

**缓存感知调度（Cache-aware scheduling）**。我们将缓存命中率（cache hit rate）定义为 $\frac{\text{缓存的提示令牌数}}{\text{提示令牌总数}}$。当等待队列中有许多请求时，它们的执行顺序会显著影响缓存命中率。例如，如果请求调度器频繁在不同且不相关的请求之间切换，可能导致缓存抖动（cache thrashing）和低命中率。我们设计了一种缓存感知调度算法来提高缓存命中率。在批处理（batch-processing）设置中，我们对这 5 个请求进行排序。

根据匹配的前缀长度对请求进行排序，优先处理匹配前缀较长的请求，而非采用先到先服务的调度策略。附录中的算法 1 展示了采用连续批处理（contiguous batching）的缓存感知调度（cache-aware scheduling）伪代码。该算法采用最长共享前缀优先（longest-shared-prefix-first）顺序。在对延迟更敏感的场景中，我们可能仍能容忍有限的批处理重排序以提升缓存复用率。此外，我们针对离线情况下的最优调度证明了以下定理。

**定理 3.1.** 对于一批请求，通过以深度优先搜索（depth-first search）顺序遍历请求的基数树（radix tree），且缓存大小 ≥ 最大请求长度时，我们可以实现最优缓存命中率（cache hit rate）。最长共享前缀优先顺序等价于深度优先搜索顺序。

证明见附录 A.3 节。在线情况下，深度优先搜索顺序会被打乱，但我们的调度仍能近似模拟完整基数树新增部分上的深度优先搜索行为，详见附录 A.3 节。虽然贪婪的缓存感知调度能实现高吞吐量，但可能导致饥饿问题。我们将其与其他公平调度方法 [42] 的集成留作未来工作。

**分布式场景（Distributed Cases）**。 RadixAttention 可扩展至多个 GPU。对于张量并行（tensor parallelism），每个 GPU 维护一个分片的 KV 缓存（sharded KV cache）。由于树操作相同，无需额外的同步。多工作节点的数据并行（data parallelism）在附录 A.4 节中讨论。

### 4 基于压缩有限状态机的高效约束解码

在语言模型程序中，用户通常希望约束模型输出遵循特定格式，例如 JSON 模式。这可以提高可控性和鲁棒性，并使输出更易于解析。SGLang 提供了正则表达式参数，通过正则表达式来强制执行此类约束，而正则表达式足以应对许多实际场景。现有系统通过将正则表达式转换为有限状态机（Finite State Machine, FSM）[54] 来支持此功能。在解码过程中，它们维护当前 FSM 状态，从后续状态中检索允许的 Token，并将无效 Token 的概率设为零，逐 Token 进行解码。然而，这种逐 Token 的方法在有机会一次性解码多个 Token 时效率低下。例如，图 2 中的常量序列 {“summary”: “ 在普通解码过程中跨越多个 Token，如图 4(c) 所示，需要多个解码阶段，尽管解码时只有一个有效的下一个 Token。因此，整个序列可以一步解码（即前向传播（forward pass）。然而，现有系统每次只能解码一个令牌（token），因为有限状态机（FSM）与模型运行器（model runner）之间缺乏集成，导致无法进行多令牌处理，从而造成解码速度缓慢。

SGLang 通过创建一个带有压缩有限状态机（compressed FSM）的快速约束解码运行时（constrained decoding runtime）克服了这一限制。该运行时分析 FSM，并将其中的相邻单转移边（singular-transition edges）压缩为单一边，如图 4 (b) 所示，从而能够识别何时可以同时解码多个令牌。在图 4 (d) 中，压缩转移边上的多个令牌可以在一次前向传播中完成解码，这极大地加速了解码过程。该方法具有通用性，适用于所有正则表达式（regular expressions）。关于背景和实现的更多细节见附录 B。

### 5 使用 API 推测执行（API Speculative Execution）的高效端点调用

前几节介绍了针对开放权重模型（open-weight models）的优化，这些优化需要对模型推理过程进行修改。此外，SGLang 也适用于仅提供 API 访问的模型（API-access-only models），例如 OpenAI 的 GPT-4。然而，对于这些模型，我们只能调用黑盒 API 端点（black-box API endpoint）。

本节介绍一种针对黑盒 API 模型的新优化方法，该方法通过使用推测执行（speculative execution）来加速多调用 SGLang 程序的执行并降低 API 成本。例如，一个程序可能要求模型通过多次调用来生成一个角色的描述。

模式：`s += context + "name:" + gen("name", stop="\n") + "job:" + gen("job", stop="\n")`。简单来说，两个 `gen` 原语（primitives）对应两次 API 调用，这意味着用户需要为上下文支付两次输入令牌（input token）费用。在 SGLang 中，我们可以在第一次调用时启用推测执行（speculative execution），并通过忽略停止条件（stop condition）让其继续生成更多令牌。解释器（interpreter）会保留额外的生成输出，并将其与后续的原语进行匹配和重用。在某些情况下，通过精心设计的提示工程（prompt engineering），模型能够以高准确率正确匹配模板，从而节省一次 API 调用的延迟和输入成本。

### 6.1 实验设置

**模型**。 我们测试了密集型的 Llama-2 模型 [49]、稀疏混合专家模型 Mixtral [17]、多模态 LLaVA 图像 [27] 和视频模型 [62]，以及 API 模型 OpenAI 的 GPT-3.5。对于开源权重模型，参数数量从 70 亿到 700 亿不等，我们使用 float16 精度。

**硬件**。 我们在 AWS EC2 G5 实例上运行了大部分实验，这些实例配备了 NVIDIA A10G GPU（24GB）。我们在单个 A10G GPU 上运行 7B 模型，在多个 A10G GPU 上使用张量并行（tensor parallelism）[44] 运行更大的模型。我们还在 A100G（80GB）GPU 上进行了一些额外的实验。

**基线方法**。 我们将 SGLang 与使用各自语言和默认运行时的高级编程系统，以及使用标准类似 OpenAI 的 Completion API 的低级推理引擎进行了比较。除非另有说明，我们不会开启会改变计算结果的优化，以确保所有系统计算出相同的结果。基线方法包括：

- Guidance[13]，一种用于控制 LLM 的语言。我们使用 Guidance v0.1.8 和 llama.cpp 后端。
- vLLM[23]，一个高吞吐量推理引擎。我们使用 vLLM v0.2.5 及其默认 API 服务器³。
- LMQL[4]，一种查询语言。我们使用 LMQL v0.7.3 和 Hugging Face Transformers 后端。

**工作负载**。 我们测试了以下内容：5-shot MMLU [14] 和 20-shot HellaSwag [61] 基准测试。对于 MMLU，我们解码一个 token；对于 HellaSwag，我们使用原始的 select 操作来选择概率最高的答案。对于 ReAct 智能体（agent）[57] 和生成式智能体（generative agents）[36]，我们从原始论文中提取轨迹并重放。我们使用思维树（Tree-of-thought）[56] 解决 GSM-8K 问题，使用思维骨架（Skeleton-of-thought）[33] 生成提示。我们使用 LLM 评判器（judges）结合分支-求解-合并（branch-solve-merge）[40] 技术；使用正则表达式指定模式的 JSON 解码；进行 4 轮的多轮对话，每轮输入在 256-512 个 token 之间随机采样。多轮对话（短）表示短输出（4-8 个 token），多轮对话（长）表示长输出（256-512 个 token）；以及 DSPy 检索增强生成（RAG）管道（pipeline）[20] 的官方示例。

**指标**。 我们报告两个性能指标：吞吐量（throughput）和延迟（latency）。对于吞吐量，我们运行足够大的程序实例批次来计算最大吞吐量，比较每秒执行的程序实例数量（程序/秒，p/s）。对于延迟，我们一次只执行一个程序而不进行批处理，并报告多个实例的平均延迟。

在 MMLU 上，SGLang 通过 RadixAttention 复用了 5-shot 示例的 KV 缓存。RadixAttention 同时提升了吞吐量（throughput）和延迟（latency）。RadixAttention 通过共享 KV 缓存减少了总内存使用量，从而允许更大的批处理大小（batch size）以提高最大吞吐量。RadixAttention 还减少了预填充（prefill）的计算量，从而降低了首令牌延迟（first token latency）。在 HellaSwag 上，SGLang 复用了少量示例和多个选项的公共问题前缀的 KV 缓存，实现了两级共享。对于 ReAct 和生成式智能体（generative agents），SGLang 复用了智能体模板和先前调用的 KV 缓存。在思维树（Tree-of-thought）和思维骨架（Skeleton-of-thought）上，SGLang 在单个程序内并行化生成调用，并尽可能复用 KV 缓存。在 JSON 解码上，SGLang 通过压缩有限状态机（compressed finite state machine）一次解码多个令牌来加速解码。在多轮对话（multi-turn chat）中，SGLang 复用了聊天历史的 KV 缓存。对于短输出，加速效果更为明显，因为 KV 缓存复用主要有助于减少前缀时间。对于长输出，由于不同聊天会话之间共享较少且解码时间占主导地位，几乎没有加速效果。在 DSPy RAG 流水线中，SGLang 复用了公共上下文示例的 KV 缓存。在这些基准测试中，缓存命中率（cache hit rate）范围为 50% 到 99%。图 13（附录）列出了所有基准测试的实现和最优缓存命中率，表明我们的缓存感知调度（cache-aware scheduling）平均接近最优命中率的 96%。由于性能缓慢和功能缺失，我们将 LMQL 和 Guidance 排除在最后五个基准测试之外。LMQL 的问题源于缓慢的令牌级处理（token-level processing）和未优化的后端，而 Guidance 缺乏批处理（batching）和并行性（parallelism）支持。

我们在一个没有任何 KV 缓存重用机会的基准测试上测试了 RadixAttention 的开销。该基准测试衡量的是 ShareGPT 数据集上的吞吐量。运行 100 个请求需要 74.3 秒；然而，用于管理 RadixAttention 数据结构的时间仅为 0.2 秒，这是一个可以忽略不计的开销，不到 0.3%。这是因为树操作的复杂度是线性的且规模较小。因此，我们可以默认开启 RadixAttention。

**压缩有限状态机的有效性**

我们在 JSON 解码基准测试上测试了压缩有限状态机（compressed finite state machine）及其组件的有效性。实验结果表明，压缩有限状态机将吞吐量提高了 1.6 倍，因为它可以一次解码多个令牌。此外，我们需要对状态机进行预处理，并在一批请求中重用它。否则，为每个请求重新进行预处理会使吞吐量降低 2.4 倍。

### 7 相关工作

已有多种工作探索了 KV 缓存（KV cache）的重用，其中许多与我们的工作同期进行。独特的是，我们的 RadixAttention 首次提出将 KV 缓存视为基于树的 LRU 缓存（tree-based LRU cache）。它是首个支持多级共享（multi-level sharing）、缓存感知调度（cache-aware scheduling）、前端-运行时协同调度（frontend-runtime co-scheduling）以及分布式场景的解决方案。vLLM [23] 和 ChunkedAttention [58] 探索了一些简单的重用场景（例如系统提示共享），但未涵盖多级树形结构共享或 LRU 缓存。PromptCache [12] 提出了超越前缀的 KV 缓存模块化重用，但可能导致准确率下降高达 43%。HydraGen [18]、FlashInfer [59] 和 ChunkedAttention [58] 专注于 CUDA 内核优化，并未包含 LRU 缓存的概念。API Serve [1] 和 LLM-SQL [29] 研究了特定应用场景下的 KV 缓存重用，例如与外部 API 调用和关系数据库的交错使用，但它们不具备我们的基数树（radix tree）或缓存感知调度功能。

目前存在多个 LLM 编程和智能体框架（agent framework），例如 Guidance [13]、LMQL [4]、DSPy [20]、LangChain [24]、AutoGen [55] 和 LLM Compiler [21]。Guidance 和 LMQL 与 SGLang 最为相似，我们在第 2 节中对它们进行了比较。我们的创新在于通过新颖的运行时优化来加速所提出的编程模型。SGLang 与其他框架兼容，并能够加速它们（例如我们评估中的 DSPy 示例）。此外，SGLang 还与许多其他常见的推理优化方法兼容 [60, 39, 3, 23, 59, 10, 26, 15, 19, 32, 31, 11]。

### 8 未来方向与结论

未来方向。 尽管 SGLang 取得了进展，但仍存在若干局限性，这些局限性揭示了未来研究的有前景方向。这些方向包括：扩展 SGLang 以支持更多输出模态；使 RadixAttention 能够跨内存层次结构（memory hierarchy）的多个层级（例如 DRAM、磁盘）运行 [43]；在 RadixAttention 中实现模糊语义匹配（fuzzy semantic matching）；在 SGLang 之上提供更高级的原语；解决缓存感知调度中的饥饿问题（starvation）[42]；以及增强 SGLang 编译器以执行高级静态优化，例如调度和内存规划。

结论。我们介绍了 SGLang，这是一个用于高效编程和执行结构化语言模型程序（structured language model programs）的框架。SGLang 通过新颖的优化技术（如 RadixAttention、压缩有限状态机（compressed finite state machines）和语言解释器）显著提升了复杂语言模型程序的吞吐量和延迟性能。它是开发高级提示技术（prompting techniques）和智能体工作流（agent workflows）的重要工具。源代码已公开提供。
