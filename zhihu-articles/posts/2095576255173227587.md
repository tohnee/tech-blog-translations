先说核心判断：

- vLLM 定义了第一波 LLM 推理系统范式：用 PagedAttention 解决 KV Cache 的显存碎片和动态分配问题。
- SGLang 定义了第二波范式：用 RadixAttention 解决多轮对话、Agent、RAG 等场景中“哪些历史计算可以跨请求复用”的问题，并把结构化生成与运行时联合设计。
- 到 2026 年，两者已经高度趋同：都支持连续批处理、前缀缓存、Chunked Prefill、投机解码、结构化输出、量化、PD 解耦、DP/TP/PP/EP、多硬件和多模态。
- 因此今天已经不能简单说“谁更快”。更准确的结论是：vLLM 偏广覆盖、标准化和通用生产基础设施；SGLang 偏 Agent/共享前缀、前沿模型联合优化和快速性能攻坚。

几个值得注意的 Git 信号：

- vLLM 起步更早，2023 年已经完成 Block Manager、Cache Engine、Scheduler、Tensor Parallel 和 PagedAttention 基础结构。
- SGLang 虽晚约八个月，但追赶速度极快：2026 年内提交量已经高于 vLLM。
- 两边都从“少数研究者主导”转向大规模多组织协作。vLLM 当前文档列出 11 名 Project Leads、57 名 Active Committers；SGLang 则形成 Scheduler、KV Cache、PD、Parallelism、Kernel、Spec Decode、硬件等分区的 Codeowner 和 Merge Oncall 制度。
- 版本号不可横向比较。vLLM 的 v0.32 不表示比 SGLang v0.5“成熟六倍”，只是两边发布编号策略不同。

### 二、两支团队其实同宗同源

vLLM 与 SGLang并不是完全独立的竞争团队，而是 Berkeley/LMSYS 系统研究社区中前后相继、持续交叉的一组人。

两篇奠基论文有五位共同作者：

- Lianmin Zheng
- Ying Sheng
- Cody Hao Yu
- Joseph E. Gonzalez
- Ion Stoica

vLLM 最初由 UC Berkeley Sky Computing Lab 开发，Woosuk Kwon 是首个提交者；SGLang 则是 Berkeley、Stanford、LMSYS 等研究者合作的结果，首个提交来自 Ying Sheng，初始公开代码主要由 Lianmin Zheng、Liangsheng Yin 推进。

技术传承也是双向的：

- SGLang 初始博客明确感谢并复用了 vLLM、LightLLM、FlashInfer、Outlines 等项目的设计。
- vLLM V1 官方博客又明确表示，新架构吸收了 SGLang、LMDeploy、LightLLM、TGI、TensorRT-LLM 等系统的经验。
- 所以更合适的描述不是“两个互不相干的死对头”，而是同一技术谱系里持续竞赛、互相吸收的两条路线。

### 四、vLLM 的高光时刻

**PagedAttention 把操作系统分页思想带入 KV Cache**

原始系统常因连续预留和碎片化浪费 60%–80% 的 KV Cache 显存。PagedAttention 将逻辑 Token 块映射到不连续的物理块，使浪费降到 4% 以下，并支持 Copy-on-Write、并行采样和 Beam Search 共享。

论文口径是相同延迟下较 FasterTransformer、Orca 提高 2–4 倍吞吐；发布博客针对 Hugging Face Transformers 和 TGI 的特定实验则给出最高 24 倍和 3.5 倍。二者基线不同，不能混为一个数字。

**在 Chatbot Arena 中完成真实流量验证**

2023 年公开发布前，vLLM 已经为 Vicuna Demo 和 Chatbot Arena 服务两个月。项目报告称：

- 相对早期 HF 后端内部测试最高提高 30 倍吞吐；
- 将所需 GPU 数量减少约 50%；
- 当时平均每天处理 3 万请求，峰值 6 万。

这让 vLLM 不是停留在论文原型，而是在发布时就有真实生产证据。

**迅速成为开放模型生态的默认底座**

2024 年 Llama 3.1 发布时，Meta 的 10 家实时推理合作伙伴中有 8 家使用 vLLM。2024 年底：

- GitHub Star 从 1.4 万增长到 3.26 万；
- Contributor 从 190 增长到 740；
- 月下载量从 6,000 增长到 27,000；
- 已用于 Amazon Rufus、LinkedIn AI 等场景。

2025 年 5 月加入 PyTorch Foundation 时，官方统计为 4.65 万 Star、1,000 多名贡献者；当前文档称贡献者已经超过 2,000。

**v0.6 和 V1 连续完成两次自我重构**

2024 年 SGLang 发起性能挑战后，vLLM v0.6 很快交付：

- Llama 8B：吞吐最高提高 2.7 倍，TPOT 最多降低 5 倍；
- Llama 70B：吞吐提高 1.8 倍，TPOT 降低约 2 倍。

2025 年 V1 又重写 Scheduler、KV Cache Manager、Worker、Sampler 和 API Server：

- 将 Prefill 与 Decode 统一为 Token Budget；
- Prefix Cache 零命中时开销控制在 1% 以下，因此默认开启；
- 通过独立 EngineCore、Persistent Batch、torch.compile、Piecewise CUDA Graph 等降低 CPU 开销；
- 对 V0 最高取得 1.7 倍吞吐提升。

**从单机引擎扩展到生产级 MoE 集群**

2025 年底，vLLM 在 DeepSeek 风格 Wide-EP 集群上报告了每张 H200 持续 2.2k tokens/s，形成 llm-d、Dynamo、Ray Serve 等多条部署路径。2026 年 MRV2 又在 1×GB200、Qwen3-0.6B 场景把输出吞吐从 16K 提高到 25K tokens/s，提升 56%。

### 五、SGLang 的高光时刻

1. **RadixAttention 把“共享前缀”变成一等系统资源**

PagedAttention主要解决 KV Cache 如何放置；RadixAttention主要解决哪些 KV Cache 值得跨请求保存和复用。

SGLang 将 Prompt 和生成历史组织成 Radix Tree，自动完成最长前缀匹配、插入、分裂和 LRU 淘汰。这天然适合：

- 多轮对话；
- 共享 System Prompt 和工具定义的 Agent；
- Few-shot；
- Self-consistency；
- Tree-of-Thought；
- 重复访问相同上下文的 RAG。

原论文报告最高提高 6.4 倍吞吐、降低 3.7 倍延迟；首发博客在当时的 Llama/Mixtral 工作负载上给出相对 Guidance 和 vLLM 最高 5 倍吞吐。

**很早就占领结构化生成高地**

2024 年 1 月刚公开代码时，SGLang 已经支持 JSON 和正则约束生成。2 月的 Compressed FSM 能在确定路径上一次跳过多个 Token：

- 相对 Guidance + llama.cpp、Outlines + vLLM，延迟最高降低 2 倍；
- 吞吐最高提高 2.5 倍。

v0.4 集成 XGrammar 后，项目在特定 JSON Decode 测试中给出最高 10 倍提升。虽然今天 vLLM 也已经有成熟的 Structured Output，SGLang 在这一方向的先发优势很明显。

**2024 年直接推动整个行业处理 CPU 调度开销**

SGLang v0.2 在 Llama-70B 特定场景宣称比 vLLM 0.5.2 高至 3.1 倍；随后 v0.4 将 Scheduler 放到 GPU 前一批运行，用 CPU/GPU Overlap 隐藏调度和 Radix Cache 操作，并通过 Nsight 展示连续 Decode Batch 之间没有 GPU 空洞。

这场竞争也促成 vLLM v0.6 和 V1 快速降低 CPU 开销。历史上最有意思的不是某一次谁赢，而是两边交替把对方的瓶颈变成下一版的重点。

**抓住 DeepSeek MLA/MoE 浪潮**

SGLang 对 DeepSeek 的联合优化贯穿多个阶段：

- v0.3：MLA 优化相对基线提高 3–7 倍；
- v0.4：DP Attention 避免 MLA KV Cache 在 TP Rank 间重复，Decode 吞吐提高约 1.9 倍；
- 2025 年 5 月：在 12 节点、96 张 H100 上实现 PD 解耦和大规模 EP；
- 报告每节点 52.3K 输入 tokens/s、22.3K 输出 tokens/s，接近 DeepSeek 官方系统；
- 2025 年成为 SemiAnalysis InferenceMAX 在 NVIDIA、AMD 上运行 DeepSeek 的默认推理引擎。

这是 SGLang 最具辨识度的一段高光：从单个 Kernel 优化扩张到完整的模型—并行策略—通信—调度联合设计。

**从 LLM Runtime 扩张到生成与训练生态**

SGLang 现在已经不只是最初的“Structured Generation Language”：

- SGLang Diffusion 被放进同一仓库和 Python 包，覆盖图像、视频生成，官方测试给出 1.2–5.9 倍加速；
- SpecForge 负责训练投机解码 Draft Model；
- Miles、slime、AReaL、verl、Tunix 等用于 RL Rollout；
- SGL-JAX、未来的 SGL-torchtpu 扩展到 TPU；
- HiCache、HiSparse 把 KV Cache 从 GPU 扩展到 CPU、存储和稀疏层级。HiSparse 在特定长上下文测试中最高达到约 5 倍吞吐提升。

### 六、技术异同

| 维度 | vLLM | SGLang |
| --- | --- | --- |
| 最初解决的问题 | 降低 KV Cache 显存碎片，提高可批处理请求数 | 自动复用复杂程序、多轮请求之间的公共 KV 前缀 |
| 核心数据结构 | 固定大小 Block/Page、Block Table；V1 Prefix Cache 为 Hash + LRU | Token Prefix Radix Tree + LRU，底层 KV 同样采用分页布局 |
| PagedAttention 与 RadixAttention关系 | 关注“KV 放在哪里、如何分配” | 关注“哪些 KV 能被后续请求复用”；不是 PagedAttention 的直接替代 |
| 调度路线 | V1 用统一 Token Budget 混排 Prefill/Decode；独立 EngineCore；MRV2 GPU-native、Async-first | Overlap Scheduler 提前准备下一批；Radix Cache 与 Cache-Aware Router 更深耦合 |
| 用户入口 | OpenAI/Anthropic 等兼容 API、LLM Python API，标准服务基础设施定位更强 | 起源于 Python DSL 的 gen/fork/control flow；现在实际重心也已转向 OpenAI API 和 SRT |
| 结构化生成 | V1 Structured Output Manager、Grammar/XGrammar 等 | Compressed FSM 和 XGrammar 起步更早，是历史强项 |
| 分布式推理 | TP/PP/DP/EP、Wide-EP、DBO、EPLB、PD、KV Connector；与 llm-d/Dynamo/Ray 深度集成 | TP/PP/DP/EP、DP Attention、DeepEP、EPLB、PD、HiCache；DeepSeek 等 MoE 联合优化尤其激进 |
| 硬件策略 | “任意模型、任意硬件”的平台化路线，插件系统和 PyTorch Foundation 生态更成熟 | NVIDIA/AMD 优化很深，同时迅速拓展 TPU、Ascend、Intel、Apple、Moore Threads |
| 多模态 | 主仓库支持 VLM；vLLM-Omni 作为独立生态项目扩展图像、音频、视频和 DiT | VLM、Diffusion 已直接进入主仓库；音频通过 SGLang Omni 等生态项目扩展 |
| RL/Post-training | Sleep/Pause、Collective RPC、原生权重同步 API，强调成为通用 Rollout Engine | 与 slime、Miles、AReaL、verl 等深度结合，当前社区叙事更强调 Frontier Model Post-training |
| 工程风格 | 通用能力、兼容性、可插拔和长期治理优先，同时开始建设模型专用 Fast Path | 更愿意为特定模型、硬件、通信拓扑做端到端联合优化，但也在补齐通用平台能力 |

最重要的一点是：今天两边的功能清单已经不能很好地区分它们。区别更多体现在“默认优化什么”和“遇到新模型时怎样组织性能攻坚”。

### 七、团队与治理差异

### vLLM

vLLM 的治理更正式、基金会化：

- 2025 年成为 PyTorch Foundation Hosted Project；
- 11 名 Project Leads 组成类似 TSC 的 Core Maintainers；
- 当前有 57 名 Active Committers，并按 Engine、KV Cache、模型、量化、硬件、API、Spec Decode、RL 等划分 Area Owner；
- Committer 归属于个人而非公司，强调长期贡献、RFC、评审与子系统维护；
- 核心贡献组织包括 UC Berkeley、Red Hat/Neural Magic、Anyscale、AMD、Intel、NVIDIA、IBM、Roblox 等。

### SGLang

SGLang 当前由非营利组织 LMSYS 托管，RadixArk 是主要维护方之一，治理更偏高强度工程项目：

- 角色分为 Merge Oncall、Codeowner、Write、CI Oncall；
- Scheduler、KV Cache、PD、Parallelism、Kernel、Spec Decode、硬件等都有明确负责人；
- Merge Oncall 可以在特殊情况下绕过不稳定 CI，但必须负责 Revert/Hotfix，违规会暂停权限；
- Lianmin Zheng、Ying Sheng负责重要权限提名和内部评审；
- 贡献力量已经扩展到 NVIDIA、AMD、Intel、Google、Oracle、阿里云、蚂蚁、Mooncake 等组织。

总体上，vLLM 更像一个基金会化的通用基础设施联盟；SGLang 更像围绕少数技术主线、高频攻坚和模型联合优化组织起来的性能工程社区。两者都已远远超出“实验室项目”阶段。

### 八、现在应该怎样选择

最新的第三方概括是“二者总体相当，胜负随负载翻转”。Red Hat 在 2026-10-14 汇总 Modal 的单张 H100、Llama 3.1 8B 默认配置测试：

| 输入/输出 | vLLM | SGLang | 结果 |
| --- | --- | --- | --- |
| 1024/128，RAG/摘要 | 17.08 req/s | 16.88 req/s | vLLM 略高 |
| 128/1024，代码生成 | 5.34 req/s | 6.50 req/s | SGLang 更高 |
| 2048/2048，长对话 | 1.23 req/s | 1.25 req/s | 基本持平 |

而且该测试使用随机文本，几乎没有共享前缀，因此并未充分体现 RadixAttention 或 vLLM Prefix Caching 在 Agent、多轮对话里的收益。

实际选型可以这样理解：

- 优先选择 vLLM：需要最大范围的模型/硬件/API 兼容、正式基金会治理、成熟生产生态，或者希望采用更保守的通用默认方案。
- 优先选择 SGLang：工作负载有大量公共前缀、Agent 循环、结构化生成，或正在追逐 DeepSeek/Kimi 等前沿 MoE 模型的极致性能和快速 Day-0 优化。
- 大规模生产：不要凭历史博客中的“最高 X 倍”决定。固定模型、精度、硬件、输入输出长度、并发、SLA、缓存命中率和框架提交，分别测 TTFT、TPOT、吞吐与正确性。

最后一句概括：vLLM 的历史高光是把“高效 KV 内存管理”变成行业标准；SGLang 的历史高光是把“前缀复用和结构化程序执行”变成系统级优化对象。今天二者都在朝完整 AI 推理平台演进，竞争已经从单个算法进入模型、Kernel、调度、缓存、通信和集群部署的全栈竞赛。
