1. **方案概述**

本文介绍如何基于 AWS EC2、EBS、EFS、NLB、Auto Scaling Group 等基础设施，使用开源 Kubernetes 组件搭建一套生产级、高可用、可扩展的 Kubernetes 集群。

整体方案采用 kubeadm + Calico + AWS Cloud Controller Manager + Cluster Autoscaler 的技术组合，不依赖 Amazon EKS，由团队自主管理 Kubernetes 控制平面、网络、存储和节点生命周期。

### 1.1 技术选型

| 技术组件 | 主要职责 |
| --- | --- |
| kubeadm | Kubernetes 集群初始化和控制平面管理 |
| AWS NLB | Kubernetes API Server 高可用入口 |
| Calico | Pod 网络、路由和 NetworkPolicy |
| AWS Cloud Controller Manager | AWS 云资源与 Kubernetes 集成 |
| AWS Auto Scaling Group | Worker Node 自动扩缩容 |
| Cluster Autoscaler | 根据 Pod 调度需求动态调整 ASG |
| Custom AMI | 预构建 Kubernetes Worker Node 运行环境 |
| EBS CSI Driver | 提供 Kubernetes 块存储 |
| EFS CSI Driver | 提供 Kubernetes 共享文件存储 |
| ingress-nginx | 集群 HTTP/HTTPS 流量入口 |

### 1.2 整体架构

整体架构分为四个主要层次：

1. Infrastructure Layer：AWS EC2、VPC、Subnet、NLB、EBS、EFS、ASG。
2. Control Plane Layer：kube-apiserver、etcd、kube-scheduler、kube-controller-manager。
3. Cluster Networking Layer：Calico、AWS Cloud Controller Manager、Ingress Controller。
4. Storage & Scaling Layer：EBS CSI、EFS CSI、Cluster Autoscaler。

推荐部署方式：

- 3 台 EC2 Master Node，部署在不同的 Availability Zone。
- 通过 AWS NLB 提供 Kubernetes API Server 的统一访问入口。
- Worker Node 部署在多个 Availability Zone。
- 每个 Worker Node Group 对应一个 AWS Auto Scaling Group。
- Cluster Autoscaler 根据集群资源需求自动调整 ASG。
- EBS 提供有状态应用的块存储，EFS 提供共享文件存储。

### 2. Kubernetes Control Plane：kubeadm + NLB

### 2.1 架构设计

使用 kubeadm 初始化 Kubernetes 集群，控制平面采用 3 节点 HA 架构。

控制平面组件包括：

- kube-apiserver
- kube-controller-manager
- kube-scheduler
- etcd

采用 Stacked etcd 架构，即每个 Master Node 同时运行一个 etcd 实例。

3 个 Master Node 分别部署在不同的 AWS Availability Zone，以降低单 AZ 故障对整个 Kubernetes Control Plane 的影响。

例如：

| 节点 | Availability Zone | 私有 IP |
| --- | --- | --- |
| Master-1 | ap-southeast-1a | 10.0.1.10 |
| Master-2 | ap-southeast-1b | 10.0.2.10 |
| Master-3 | ap-southeast-1c | 10.0.3.10 |

### 2.2 使用 AWS NLB 实现 API Server 高可用

Kubernetes API Server 默认监听 TCP 6443 端口。

为了避免客户端直接访问某一台 Master Node，可以使用 AWS Network Load Balancer 作为统一入口。

架构：

 Kubernetes Clients

|

AWS NLB

TCP : 6443

|

+-------------+-------------+

| | |

Master-1 Master-2 Master-3

API Server API Server API Server

TCP 6443 TCP 6443 TCP 6443

| | |

+-------------+-------------+

|

etcd Cluster

NLB 主要负责：

1. 接收 Kubernetes API 请求。
2. 将请求转发到健康的 API Server。
3. 通过 Health Check 检查 Master Node 的健康状态。
4. 当某个 Master Node 不可用时，将其从可用目标中移除。

建议配置：

| 配置项 | 建议值 |
| --- | --- |
| Load Balancer | Network Load Balancer |
| Listener | TCP 6443 |
| Target Group | Master EC2 Instances |
| Health Check | TCP 6443 |
| Cross-zone Load Balancing | 根据流量与成本需求开启 |
| Scheme | Internal |
| Availability Zones | 至少 3 个 AZ |

注意：NLB 只解决 API Server 的访问入口高可用，并不意味着 etcd 自动具备高可用能力。etcd 仍然需要独立保证 3 节点成员健康、数据备份和仲裁能力。

### 2.3 kubeadm 初始化

首先在每台 Master Node 上安装：

- containerd
- kubelet
- kubeadm
- kubectl

然后在第一台 Master Node 上执行初始化：

kubeadm init \

--control-plane-endpoint "[http://k8s-api.internal.example.com:6443](http://k8s-api.internal.example.com:6443)" \

--upload-certs \

--pod-network-cidr=192.168.0.0/16

其中：

- control-plane-endpoint：NLB 对应的 DNS 名称。
- upload-certs：将控制平面证书加密上传，方便其他 Master Node 加入。
- pod-network-cidr：Pod 网络地址范围，需要与 AWS VPC CIDR、Calico 配置合理规划，避免地址冲突。

其他 Master Node 通过以下命令加入集群：

kubeadm join \

[http://k8s-api.internal.example.com:6443](http://k8s-api.internal.example.com:6443) \

--token <token> \

--discovery-token-ca-cert-hash sha256:<hash> \

--control-plane \

--certificate-key <certificate-key>

Worker Node 则使用普通的 kubeadm join 命令加入。

### 2.4 etcd 高可用和备份

对于 3 节点 etcd 集群：

- 允许最多 1 个成员发生故障。
- 至少需要 2 个成员保持正常，才能维持多数派。
- 如果同时失去 2 个成员，集群将无法正常提交新的数据变更。

生产环境建议：

- etcd 使用独立的高性能 EBS 卷。
- 定期执行 etcd snapshot。
- 将快照备份到 S3。
- 定期进行恢复演练。
- 监控 etcd DB Size、Commit Latency、Leader Changes 和 Peer RTT。

### 3. Kubernetes Networking：Calico

### 3.1 为什么选择 Calico？

Calico 是 Kubernetes 生态中非常成熟的网络解决方案，主要提供：

- Pod-to-Pod 网络通信。
- Pod-to-Service 网络通信（通常由 kube-proxy 实现 Service 转发）。
- NetworkPolicy 网络访问控制。
- IP 地址管理。
- 网络路由与数据转发。

Calico 支持多种网络实现模式：

| 模式 | 工作原理 | 适用场景 |
| --- | --- | --- |
| BGP | 通过 BGP 分发 Pod 路由 | 具备可达路由网络的环境 |
| IP-in-IP | 通过 IP 隧道封装流量 | 跨节点 Pod 通信 |
| VXLAN | 通过 VXLAN Overlay 网络 | 云环境、多节点集群 |
| Policy-only | 使用其他 CNI 提供网络，Calico 负责策略 | AWS VPC CNI 等场景 |

### 3.2 AWS 环境下的 Calico 部署模式

AWS EC2 网络与传统物理服务器网络有所不同。

AWS VPC 使用 ENI（Elastic Network Interface）提供网络连接，EC2 实例通过 VPC 路由表进行网络通信。

在 AWS 上使用 Calico，主要有两种方案。

方案 A：Calico 作为主要 CNI

 Kubernetes Pod

|

Calico CNI

|

Linux Network

|

VXLAN Tunnel

|

Linux Network

|

Calico CNI

|

Kubernetes Pod

Calico 负责：

- Pod IP 地址分配。
- Pod 网络路由。
- 跨节点 Overlay 网络。
- NetworkPolicy。

优点：

- 网络架构相对统一。
- 不依赖 AWS ENI 的 Pod IP 分配能力。
- 支持灵活的 NetworkPolicy。
- 对 Pod 数量的扩展不直接受 ENI Pod IP 配额限制。

缺点：

- VXLAN/IP-in-IP 会增加封装开销。
- 需要考虑 MTU。
- 需要处理 Overlay 网络的路由和故障排查。

方案 B：AWS VPC CNI + Calico Policy

 Kubernetes Pod

|

AWS VPC CNI

|

ENI / VPC

|

AWS VPC Routing

Calico NetworkPolicy

负责网络访问控制

这种方案中：

- AWS VPC CNI 负责 Pod 网络和 IP 地址分配。
- Calico 主要负责 NetworkPolicy。
- Pod 可以直接使用 VPC 网络地址。

优点是 Pod 网络与 AWS VPC 原生集成，网络路径比较直接。

缺点是 Pod IP 容量会受到 ENI 数量和每个 ENI 可分配 IP 数量的限制。

### 3.3 Calico 核心组件

| 组件 | 职责 |
| --- | --- |
| calico-node | 每个 Node 上运行，管理网络和路由 |
| calico-kube-controllers | 管理 Calico 相关 Kubernetes 资源 |
| Felix | 配置路由、接口及网络策略 |
| BIRD | BGP 路由分发（启用 BGP 时） |
| Typha | 减少大规模集群中 Kubernetes API Server 的连接压力 |
| IPAM | 管理 Pod IP 地址分配 |

### 3.4 NetworkPolicy 示例

假设一个应用包含 frontend 和 backend 两种 Pod，希望只允许 frontend 访问 backend 的 TCP 8080 端口。

apiVersion: [http://networking.k8s.io/v1](http://networking.k8s.io/v1)

kind: NetworkPolicy

metadata:

name: backend-policy

namespace: production

spec:

podSelector:

matchLabels:

app: backend

policyTypes:

- Ingress

ingress:

- from:

- podSelector:

matchLabels:

app: frontend

ports:

- protocol: TCP

port: 8080

Calico 会根据 NetworkPolicy 配置，在 Node 上下发相应的网络访问控制规则。

方案建议： 如果希望使用 Calico 作为唯一 CNI，可以优先考虑 VXLAN 模式；如果希望充分利用 AWS VPC 原生 Pod 网络，则考虑 AWS VPC CNI + Calico Policy。两者不要同时承担 Pod IPAM 和主网络路由职责。

### 4. AWS Cloud Controller Manager

### 4.1 CCM 的作用

Kubernetes 原本是一个与底层基础设施相对解耦的容器编排系统。

但在 AWS 环境中，Kubernetes 需要感知底层 EC2、EBS、VPC、Load Balancer 等云资源。

AWS Cloud Controller Manager（AWS CCM）就是连接 Kubernetes 与 AWS 基础设施的组件。

其主要职责包括：

1. Node Controller：识别 AWS EC2 实例信息。
2. Route Controller：管理云环境路由（如果启用）。
3. Service Controller：根据 Kubernetes Service 创建 AWS Load Balancer。
4. Instance Controller：获取 EC2 实例信息和状态。

架构：

 Kubernetes API Server

|

AWS Cloud Controller

Manager

|

AWS API / SDK

|

+------------+------------+

| | |

EC2 ELB VPC

| | |

Instances NLB/CLB Route Table

### 4.2 为什么需要独立部署 CCM？

传统 Kubernetes 中，部分云厂商逻辑直接集成在 Kubernetes Controller Manager 中。

随着 Kubernetes 架构演进，云厂商相关逻辑被拆分到独立的 Cloud Controller Manager。

对于 AWS 环境，需要部署 AWS CCM，并使用：

--cloud-provider=external

让 Kubernetes 控制平面将云资源相关职责交给外部 CCM。

例如 kubelet 启动时也需要配置：

--cloud-provider=external

在 CCM 完成 Node 初始化之前，Node 可能带有：

[http://node.cloudprovider.kubernetes.io/uninitialized=true:NoSchedule](http://node.cloudprovider.kubernetes.io/uninitialized=true:NoSchedule)

CCM 成功识别 EC2 实例后，会完成云相关 Node 初始化并移除该 Taint。

### 4.3 AWS CCM 如何识别 EC2 Node？

CCM 可以通过 EC2 Metadata Service 和 AWS API 获取实例信息。

例如：

- EC2 Instance ID
- Private IP
- Availability Zone
- Instance Type
- Region

最终这些信息会体现在 Kubernetes Node 对象中。

kubectl get nodes -o wide

### 4.4 AWS IAM 权限

CCM 需要访问 AWS API，因此必须具备相应 IAM 权限。

常见权限涉及：

- ec2:DescribeInstances
- ec2:DescribeInstanceStatus
- ec2:DescribeTags
- ec2:DescribeAvailabilityZones
- elasticloadbalancing:DescribeLoadBalancers
- elasticloadbalancing:DescribeTargetGroups

如果启用了 Route Controller，还需要相应的 VPC Route Table 管理权限。

生产环境建议使用 IAM Roles for Service Accounts（IRSA）或者适用的 AWS IAM Web Identity 机制，为 CCM 提供最小权限，而不是直接使用长期 Access Key。

### 4.5 CCM 与 Kubernetes Service

AWS CCM 最常见的使用场景之一是通过 Service 创建 AWS Load Balancer。

例如：

apiVersion: v1

kind: Service

metadata:

name: my-service

namespace: production

annotations:

[http://service.beta.kubernetes.io/aws-load-balancer-type:](http://service.beta.kubernetes.io/aws-load-balancer-type:) external

[http://service.beta.kubernetes.io/aws-load-balancer-nlb-target-type:](http://service.beta.kubernetes.io/aws-load-balancer-nlb-target-type:) ip

spec:

type: LoadBalancer

selector:

app: my-app

ports:

- port: 80

targetPort: 8080

这里需要特别注意：

AWS CCM 与 AWS Load Balancer Controller 并不是同一个组件。

如果需要通过 Kubernetes Ingress 对接 AWS ALB，通常需要 AWS Load Balancer Controller。

如果使用 ingress-nginx，则可以通过 AWS NLB 将流量转发给 ingress-nginx Service，不需要为了这一场景额外部署 ALB Controller。

### 5.2 Cluster Autoscaler 的工作原理

Cluster Autoscaler 主要处理两类场景。

场景一：Scale Up

假设当前集群有 3 台 Worker Node，每台节点有 8 vCPU 和 32GB 内存。

此时用户提交一个 Deployment：

apiVersion: apps/v1

kind: Deployment

metadata:

name: web

spec:

replicas: 30

selector:

matchLabels:

app: web

template:

metadata:

labels:

app: web

spec:

containers:

- name: nginx

image: nginx:latest

resources:

requests:

cpu: "2"

memory: "2Gi"

如果现有节点资源不足，部分 Pod 就会进入 Pending 状态。

Cluster Autoscaler 会：

1. 监控 Kubernetes 中的 Unschedulable Pods。
2. 分析哪些 Node Group 可以容纳这些 Pod。
3. 调用 AWS Auto Scaling API。
4. 增加对应 ASG 的 Desired Capacity。
5. AWS 创建新的 EC2 实例。
6. 新 EC2 启动后执行 Bootstrap。
7. 通过 kubeadm join 加入 Kubernetes。
8. Scheduler 将 Pending Pod 调度到新节点。

场景二：Scale Down

当集群负载下降，部分 Node 的资源使用率降低时，Cluster Autoscaler 会分析节点是否可以安全移除。

如果节点上的 Pod 可以迁移到其他 Node，并且符合缩容条件：

1. Cluster Autoscaler 标记节点准备缩容。
2. 执行 Pod Eviction。
3. Kubernetes Scheduler 将 Pod 重新调度。
4. Cluster Autoscaler 调用 AWS ASG。
5. ASG 减少 Desired Capacity。
6. EC2 实例被终止。

Scale Down 不只是看 CPU 使用率，还要考虑 PodDisruptionBudget、DaemonSet、Local Storage、节点利用率以及调度约束。

### 5.3 AWS ASG 配置

建议按照不同业务负载建立多个 Node Group。

例如：

| Node Group | EC2 类型 | 最小节点 | 最大节点 | 用途 |
| --- | --- | --- | --- | --- |
| general | m7i.large | 2 | 20 | 通用应用 |
| compute | c7i.xlarge | 2 | 30 | CPU 密集型 |
| memory | r7i.xlarge | 1 | 10 | 内存密集型 |

每个 Node Group 对应一个独立的 ASG。

ASG 需要配置以下标签：

[http://k8s.io/cluster-autoscaler/enabled](http://k8s.io/cluster-autoscaler/enabled) = true

[http://k8s.io/cluster-autoscaler/](http://k8s.io/cluster-autoscaler/)<cluster-name> = owned

Cluster Autoscaler 通过这些标签发现和管理 ASG。

同时，需要配置对应的 IAM 权限，例如：

autoscaling:DescribeAutoScalingGroups

autoscaling:DescribeAutoScalingInstances

autoscaling:DescribeLaunchConfigurations

autoscaling:DescribeScalingActivities

autoscaling:SetDesiredCapacity

autoscaling:TerminateInstanceInAutoScalingGroup

实际部署时还需要根据版本和功能配置完整权限，尤其注意资源级权限与条件限制。

### 5.4 使用 Custom AMI 加速 Node 启动

如果每次扩容都需要从零开始安装 containerd、kubelet、kubeadm、Calico 等组件，会增加节点启动时间。

因此建议使用自定义 AMI。

AMI 可以提前安装：

- Ubuntu / Amazon Linux
- containerd
- kubelet
- kubeadm
- AWS CLI
- 必要的系统依赖
- 监控 Agent
- 日志 Agent

节点启动时，通过 EC2 User Data 完成初始化。

例如：

#!/bin/bash

set -e

systemctl enable containerd

systemctl start containerd

systemctl enable kubelet

systemctl start kubelet

kubeadm join \

[http://k8s-api.internal.example.com:6443](http://k8s-api.internal.example.com:6443) \

--token <token> \

--discovery-token-ca-cert-hash sha256:<hash>

AMI 应该预装通用软件，但不应该固化集群的动态 Join Token、证书密钥或长期有效凭据。

建议使用 SSM Parameter Store、Secrets Manager 或受控的 Bootstrap 服务，在启动过程中安全地获取短期加入凭证。

此外，AMI 中预装的 kubelet、kubeadm 版本必须与集群版本兼容。

### 5.5 Cluster Autoscaler 与 ASG 的关系

| 组件 | 职责 |
| --- | --- |
| Kubernetes Scheduler | 决定 Pod 应该运行在哪个 Node |
| Cluster Autoscaler | 决定是否需要增加或减少 Node |
| AWS ASG | 创建和终止 EC2 实例 |
| EC2 Launch Template | 定义 EC2 实例的启动配置 |
| Custom AMI | 提供预安装 Kubernetes 运行环境 |

核心理解：Cluster Autoscaler 不直接创建 EC2，它通过 AWS Auto Scaling API 调整 ASG，由 ASG 负责实例生命周期管理。

### 6. Kubernetes Storage：EBS CSI + EFS CSI

Kubernetes 通过 CSI（Container Storage Interface）实现存储系统与容器编排系统之间的解耦。

在 AWS 环境中，推荐同时部署 EBS CSI Driver 和 EFS CSI Driver，满足不同类型应用的存储需求。

### 6.1 EBS CSI Driver

Amazon Elastic Block Store（EBS）提供块存储能力，适合数据库、消息队列以及其他需要持久化磁盘的应用。

典型特点：

- 支持动态创建 EBS Volume。
- 支持 PVC 自动绑定 PV。
- 支持 Volume Snapshot。
- 支持扩容。
- 支持多种 EBS Volume 类型，例如 gp3、io2。

EBS CSI Driver 主要包含两个部分：

| 组件 | 部署方式 | 职责 |
| --- | --- | --- |
| ebs-csi-controller | Deployment | 创建、删除、扩容 EBS Volume |
| ebs-csi-node | DaemonSet | 将 EBS Volume 挂载到 Worker Node |

工作流程：

 Application Pod

|

PersistentVolumeClaim

|

StorageClass

|

EBS CSI Controller

|

AWS API

|

Create EBS Volume

|

PersistentVolume

|

EBS CSI Node Plugin

|

Mount EBS Volume

|

Application Pod

StorageClass 示例：

apiVersion: [http://storage.k8s.io/v1](http://storage.k8s.io/v1)

kind: StorageClass

metadata:

name: gp3

provisioner: [http://ebs.csi.aws.com](http://ebs.csi.aws.com)

parameters:

type: gp3

fsType: ext4

volumeBindingMode: WaitForFirstConsumer

allowVolumeExpansion: true

reclaimPolicy: Delete

PVC 示例：

apiVersion: v1

kind: PersistentVolumeClaim

metadata:

name: mysql-data

spec:

accessModes:

- ReadWriteOnce

storageClassName: gp3

resources:

requests:

storage: 100Gi

这里有一个非常重要的参数：

volumeBindingMode: WaitForFirstConsumer

因为 EBS Volume 具有 Availability Zone 属性。

例如：

- Pod 被调度到 ap-southeast-1a。
- EBS Volume 创建在 ap-southeast-1a。
- 如果 Pod 后续被调度到 ap-southeast-1b，原来的 EBS Volume 不能直接跨 AZ 挂载。

WaitForFirstConsumer 可以让 Kubernetes 在确定 Pod 调度位置后，再创建对应 AZ 的 EBS Volume。

这可以有效减少 Pod 与 EBS Volume 的 AZ 不匹配问题。

EBS 的重要限制：

- 普通 EBS Volume 通常采用单节点读写模式。
- 不适合作为多个不同 EC2 实例同时读写的共享文件系统。
- EBS Volume 和 EC2 Node 必须满足 AWS 的 AZ 挂载约束。
- 节点故障后，EBS 重新挂载可能需要一定时间。

### 6.2 EFS CSI Driver

Amazon Elastic File System（EFS）提供共享文件系统能力，适合需要多个 Pod 同时读写同一份数据的场景。

与 EBS 不同，EFS 基于 NFS 协议，可以让不同 EC2 实例上的 Pod 访问同一个文件系统。

典型应用：

- 多副本 Web 应用共享静态文件。
- 多个 Pod 共享上传文件。
- 内容管理系统。
- 需要共享文件目录的应用。

这里：

EFS CSI Driver 可以通过 EFS Access Point 为不同 PVC 创建独立的访问目录，并管理 POSIX 用户和目录权限。

### 6.3 EBS 与 EFS 对比

| 对比维度 | EBS CSI | EFS CSI |
| --- | --- | --- |
| 存储类型 | Block Storage | File Storage |
| 协议 | 块设备 | NFS |
| 访问模式 | 通常 RWO | 支持 RWX |
| 跨 AZ 访问 | 普通 EBS 不支持跨 AZ 挂载 | 支持多 AZ 访问 |
| 性能 | 低延迟、高 IOPS | 适合共享文件访问 |
| 典型应用 | MySQL、Redis 等 | 共享文件、Web 上传目录 |
| Kubernetes | StatefulSet | Deployment / StatefulSet |

实际项目中可以同时使用两种存储：

- 数据库使用 EBS gp3 或 io2。
- 多副本 Web 应用使用 EFS。
- 临时缓存使用 Node Local Storage 或 EmptyDir。

### 7. Ingress：ingress-nginx

### 7.1 为什么需要 Ingress？

Kubernetes Service 提供 Pod 的服务发现和流量转发能力。

但对于生产环境中的 HTTP/HTTPS 服务，通常需要统一入口，提供：

- 域名路由。
- HTTPS/TLS 终止。
- Path 路由。
- HTTP 重定向。
- 请求超时。
- 连接管理。
- 限流。
- 访问控制。

Ingress 是 Kubernetes 提供的 HTTP/HTTPS 路由 API，而 ingress-nginx 是其中一种具体实现。

### 7.5 Ingress 高可用

生产环境建议：

- ingress-nginx 至少部署 3 个副本。
- 使用 Pod Anti-Affinity 分散到不同 Node。
- 配置 PodDisruptionBudget。
- 配置 HPA。
- 使用 NLB 提供入口高可用。
- 配置合理的 readinessProbe 和 livenessProbe。
- 对 NLB、Ingress、Service 和 Pod 进行监控。

注意：社区维护的 ingress-nginx 已于 2026 年 3 月 24 日正式退役，不再提供安全补丁和 Bug Fix。因此，在 2026 年新建生产系统时，不建议把 ingress-nginx 作为长期默认选择。可以将它作为现有系统兼容方案，同时评估 Gateway API 实现，例如 Envoy Gateway。

### 8. 集群安全与可观测性

### 8.1 安全设计

| 层次 | 安全措施 |
| --- | --- |
| AWS Network | Security Group、Private Subnet、NACL |
| Kubernetes API | RBAC、TLS、API Audit Log |
| IAM | IAM Role、最小权限、IRSA |
| Pod Network | Calico NetworkPolicy |
| Container | Image Scanning、镜像签名 |
| Secret | Kubernetes Secret、AWS Secrets Manager |
| Storage | EBS/EFS 加密、KMS |
| Node | SSH 限制、SSM、系统补丁 |

建议：

- Master Node 不开放公网访问。
- Kubernetes API Server 只允许可信网络访问。
- Worker Node 使用 Private Subnet。
- 禁止应用直接使用 AWS 长期 Access Key。
- 使用 IAM Role 为各个 Kubernetes 组件提供 AWS 权限。
- 通过 Calico NetworkPolicy 限制不同 Namespace 之间的通信。

### 8.2 监控体系

推荐部署：

- Prometheus：指标采集。
- Grafana：监控仪表盘。
- Alertmanager：告警管理。
- Node Exporter：EC2 系统指标。
- kube-state-metrics：Kubernetes 对象状态。
- Fluent Bit：日志采集。
- CloudWatch：AWS 基础设施监控。

重点监控指标：

| 监控对象 | 关键指标 |
| --- | --- |
| Control Plane | API Server Latency、Request Rate |
| etcd | DB Size、Commit Latency、Leader Changes |
| Worker Node | CPU、Memory、Disk、Network |
| Kubernetes | Pod Pending、Pod Restart、Node NotReady |
| Calico | Packet Drop、BGP Status、Network Errors |
| Cluster Autoscaler | Unschedulable Pods、Scale Up/Down |
| EBS CSI | Volume Attach/Detach Errors |
| EFS CSI | Mount Errors、NFS Latency |
| NLB | Healthy Host Count、Target Response |

尤其需要关注：

1. etcd 是否存在较高的提交延迟。
2. API Server 是否出现大量请求超时。
3. Cluster Autoscaler 是否因为 ASG 配额或 EC2 容量不足而无法扩容。
4. EBS 是否出现 Volume Attach 失败。
5. Calico 是否存在跨节点网络丢包。

### 9. 完整部署顺序

实际实施时，建议按照依赖关系进行部署，而不是同时安装所有组件。

| 顺序 | 部署阶段 | 主要工作 |
| --- | --- | --- |
| 1 | AWS Infrastructure | 创建 VPC、Subnet、Route Table、Security Group、EC2、NLB、IAM Role |
| 2 | Control Plane | 创建 3 台 Master Node，配置 containerd、kubeadm，初始化 etcd 和 Kubernetes Control Plane |
| 3 | High Availability | 配置 NLB，使用统一 DNS Endpoint 接入 Kubernetes API Server |
| 4 | CNI Networking | 安装 Calico，配置 Pod CIDR、Overlay 网络及 NetworkPolicy |
| 5 | AWS Cloud Integration | 部署 AWS Cloud Controller Manager，配置 IAM 权限及 AWS Node 信息 |
| 6 | Worker Node | 构建 Custom AMI，配置 Launch Template、ASG，通过 kubeadm join 加入集群 |
| 7 | Storage | 部署 EBS CSI Driver 和 EFS CSI Driver，创建 StorageClass |
| 8 | Auto Scaling | 部署 Cluster Autoscaler，关联 AWS ASG，实现 Worker Node 自动扩缩容 |
| 9 | Ingress | 部署 Ingress Controller，通过 NLB 暴露 HTTP/HTTPS 服务 |
| 10 | Observability | 部署 Prometheus、Grafana、日志系统和告警系统 |

### 10. 生产环境需要重点考虑的问题

### 10.1 Control Plane 高可用不等于集群整体高可用

3 个 Master Node 可以保证控制平面具有一定的故障容忍能力，但并不能保证整个集群不会发生故障。

还需要考虑：

- Master Node 所在 AZ 故障。
- etcd 数据损坏。
- Worker Node 批量故障。
- AWS 区域级故障。
- NLB 故障或配置错误。

特别是 etcd，建议独立建立备份与恢复机制。

### 10.2 AWS CCM 与 Calico 的职责边界

如果 Calico 使用 Overlay 网络，那么 Pod 网络由 Calico 自己管理。

如果启用了 AWS CCM Route Controller，则可能涉及 AWS VPC Route Table 的路由管理。

因此需要明确：

- 谁负责 Pod IP 分配？
- 谁负责 Pod 网络路由？
- 是否需要 AWS VPC Route Controller？
- 是否存在不同组件同时管理同一条路由的情况？

不要让 Calico 和 AWS CCM 对同一套 Pod 网络路由产生管理冲突。

### 10.3 EBS 与 ASG 的生命周期问题

这是 Stateful Workload 在 AWS 上经常遇到的问题。

例如：

 EC2 Node A

|

MySQL Pod

|

EBS Volume

|

Node A 故障

|

ASG 创建 Node B

|

EBS 重新挂载

|

这里需要注意：

- EBS 必须在相同 AZ 中重新挂载。
- Kubernetes Volume Attach/Detach 需要时间。
- ASG 不能简单地认为 EC2 实例终止后，所有存储资源也应该删除。
- StatefulSet 的数据恢复需要考虑应用自身的数据一致性。

对于 GPU、AI 推理等业务，建议考虑：

- 节点预热。
- 最小节点数量。
- 多种 Instance Type。
- 多 AZ 容量规划。
- EC2 On-Demand 与 Spot 混合部署。

### 10.5 关于 ingress-nginx 的技术选型

截至 2026 年 11 月，社区维护的 ingress-nginx 已正式退役。因此，如果这是一个新的生产项目，建议评估：

| 原方案 | 建议评估的替代方案 |
| --- | --- |
| ingress-nginx | Envoy Gateway |
| Kubernetes Ingress | Gateway API |
| NLB | AWS NLB，继续作为外部流量入口 |

如果是学习、实验或维护已有系统，仍然可以研究 ingress-nginx 的架构和配置，但不建议在新生产环境中继续采用已经退役的版本。

- AWS 负责计算、网络、负载均衡和存储基础设施。
- CCM 负责 Kubernetes 与 AWS 云资源之间的集成。
- Cluster Autoscaler 负责根据 Kubernetes 调度需求动态调整 AWS 计算资源
