边端场景越发重要的今天，分析一下边端最牛的公司在做什么软件栈

### 1. 一句话定位

**TensorRT Edge-LLM 是 NVIDIA 面向 Jetson / DRIVE 等嵌入式边缘平台的高性能 C++ LLM/VLM 推理运行时**。它提供 Python 脚本把 HuggingFace checkpoint 转成 ONNX，再在边缘设备上把 ONNX build 成 TensorRT engine，最后由轻量 C++ runtime 完成端到端推理；官方说明里强调“engine build and end-to-end inference runs entirely on Edge platforms”。([GitHub](https://github.com/NVIDIA/TensorRT-Edge-LLM))

它不是传统意义上的“云端 LLM serving 框架”，也不是主要面向 H100 集群吞吐量优化的 TensorRT-LLM 替代品。它的核心场景更像：**车载座舱、自动驾驶/机器人、边缘多模态助手、离线 ASR/LLM/TTS、低 batch、强实时、强功耗约束、少依赖 C++ 部署**。NVIDIA 的博客把边缘负载特征概括为：少用户或单用户、低 batch、生产关键、离线/本地，并要求低且可预测的延迟、低磁盘/内存/算力占用和可靠性。([NVIDIA Developer](https://developer.nvidia.com/blog/accelerating-llm-and-vlm-inference-for-automotive-and-robotics-with-nvidia-tensorrt-edge-llm/))

### 2. 孵化背景与目的：为什么需要它

### 2.1 背景：Physical AI 需要“端侧能跑”的 LLM/VLM

Physical AI，也就是机器人、自动驾驶、智能座舱、工业边缘设备等，不适合完全依赖云端大模型推理：网络不可控、时延不可控、隐私和安全要求高，而且设备功耗和显存都有限。NVIDIA 在技术博客中明确说，TensorRT Edge-LLM 是为了在 **DRIVE AGX Thor** 和 **Jetson Thor** 这类边缘平台上做实时 LLM/VLM 推理而设计，并强调最小依赖、C++ runtime、EAGLE-3 speculative decoding、NVFP4 量化、chunked prefill 等面向边缘的能力。([NVIDIA Developer](https://developer.nvidia.com/blog/accelerating-llm-and-vlm-inference-for-automotive-and-robotics-with-nvidia-tensorrt-edge-llm/))

### 2.2 目的：把 HuggingFace 模型变成可部署的边缘 TensorRT runtime

它想解决的是一条很具体的工程链路：

`HF checkpoint → 量化/导出 ONNX → 边缘设备 build TensorRT engine → C++ runtime 推理`

官方 overview 也把项目拆成三个关键组件：Python Export Pipeline、Engine Builder、C++ Runtime，分别负责导出/量化、TensorRT engine 构建、以及实际的自回归解码推理。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/developer_guide/getting-started/overview.html))

### 2.3 Roadmap 暴露出的真实战略方向

H1 2026 roadmap 写得很清楚：项目目标包括月度发布节奏、扩展模型支持以满足 Physical AI 需求、降低延迟和内存 footprint、保持模块化 C++ runtime，并继续做 EAGLE3、FP8 KV cache、kernel 探索、环境兼容等优化。([GitHub](https://github.com/NVIDIA/TensorRT-Edge-LLM/issues/32))

换句话说，它的“孵化目标”不是单纯跑通一个 LLM demo，而是做一个 **NVIDIA 端侧 AI 推理软件栈的 LLM/VLM 运行时基础层**。

### 3. 生态定位：它和 TensorRT-LLM / vLLM / llama.cpp 的区别

| 维度 | TensorRT Edge-LLM |
| --- | --- |
| 核心场景 | Jetson / DRIVE 边缘端、低 batch、实时/离线、C++ 集成 |
| 部署目标 | 嵌入式平台，尤其 Jetson Thor、DRIVE Thor |
| 模型来源 | HuggingFace checkpoint，先转 ONNX |
| Runtime | C++，官方强调 no Python runtime dependency |
| 优化重点 | TensorRT engine、CUDA kernel、量化、KV cache、EAGLE speculative decoding、VLM/audio/TTS |
| 不擅长的方向 | 大规模云端多租户 serving、跨 GPU 数据中心吞吐调度、类似 vLLM 的高并发 paged attention 服务层 |

官方 supported models 页面也提醒：开发 GPU 可用于开发验证，但如果是在 dGPU 上追求高性能推理，应参考 TensorRT-LLM。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/developer_guide/getting-started/supported-models.html))

### 5. 从使用角度看：端到端流程

官方 Quick Start 的思路非常清晰：**x86 host 上导出，edge device 上 build engine 和推理**。安装文档也明确把环境分成两个部分：Python Export Pipeline 跑在 x86 host + GPU 上，C++ Runtime 跑在 Edge device 上。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/developer_guide/getting-started/installation.html))

### 5.1 Host 侧：量化与导出 ONNX

以 Qwen3-0.6B FP8 为例，官方 quick start 给出的流程是：

```text
# x86 host
git clone --recursive https://github.com/NVIDIA/TensorRT-Edge-LLM.git
cd TensorRT-Edge-LLM
pip3 install .

# 量化
tensorrt-edgellm-quantize-llm \
  --model_dir Qwen/Qwen3-0.6B \
  --output_dir ./Qwen3-0.6B-fp8 \
  --quantization fp8

# 导出 ONNX
tensorrt-edgellm-export-llm \
  --model_dir ./Qwen3-0.6B-fp8 \
  --output_dir ./Qwen3-0.6B-fp8/onnx
```

官方安装文档建议在 x86 Linux Ubuntu 22.04/24.04、CUDA 12/13、Python 3.10+、GPU compute capability 8.0+ 上跑 export pipeline，并提醒 7B/8B 模型尤其 FP8 ONNX export 可能需要很高 CPU/GPU 内存。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/developer_guide/getting-started/installation.html))

### 5.2 传输 ONNX 到边缘设备

```text
scp -r ./Qwen3-0.6B-fp8/onnx \
  <device_user>@<device_ip>:~/tensorrt-edgellm-workspace/Qwen3-0.6B-fp8/
```

官方 quick start 就是把 ONNX 目录传到 Thor 设备，再在设备端 build TensorRT engine。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/developer_guide/getting-started/quick-start-guide.html))

### 5.3 Edge 侧：build TensorRT engine

```text
# edge device
cd ~/TensorRT-Edge-LLM

./build/examples/llm/llm_build \
  --onnxDir ~/tensorrt-edgellm-workspace/Qwen3-0.6B-fp8/onnx \
  --engineDir ~/tensorrt-edgellm-workspace/Qwen3-0.6B-fp8/engine \
  --maxBatchSize 1 \
  --maxInputLen 1024 \
  --maxKVCacheCapacity 4096
```

`--maxBatchSize`、`--maxInputLen`、`--maxKVCacheCapacity` 非常关键：它们决定 TensorRT engine 的最大 shape、KV cache 分配、可支持的上下文和生成长度。官方 quick start 里也给了这些参数，并说明 build 通常需要几分钟。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/developer_guide/getting-started/quick-start-guide.html))

### 5.4 Edge 侧：跑推理

输入 JSON 类似 OpenAI Chat Completions 格式，支持 `messages`、`temperature`、`top_p`、`top_k`、`max_generate_length` 等字段。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/developer_guide/getting-started/input-format.html))

```text
{
  "batch_size": 1,
  "temperature": 0.7,
  "top_p": 0.8,
  "top_k": 20,
  "max_generate_length": 256,
  "requests": [
    {
      "messages": [
        {"role": "system", "content": "You are a helpful assistant."},
        {"role": "user", "content": "Explain TensorRT Edge-LLM in one paragraph."}
      ]
    }
  ]
}
./build/examples/llm/llm_inference \
  --engineDir ~/tensorrt-edgellm-workspace/Qwen3-0.6B-fp8/engine \
  --inputFile ./input.json \
  --outputFile ./output.json \
  --dumpProfile \
  --warmup 3
```

示例程序的 CLI 支持 `--engineDir`、`--multimodalEngineDir`、`--inputFile`、`--outputFile`、`--dumpProfile`、`--warmup`、`--eagle`、`--eagleDraftTopK`、`--eagleDraftStep`、`--eagleVerifyTreeSize` 等参数；源码里也注明 sampling 参数如 temperature/top_p/top_k 主要从 input JSON 指定。([GitHub](https://github.com/NVIDIA/TensorRT-Edge-LLM/raw/refs/heads/main/examples/llm/llm_inference.cpp))

### 6. 功能支持全景

### 6.1 标准 LLM 推理

标准 LLM 推理就是：tokenize → embedding lookup → prefill → sample first token → decode loop → sample → EOS/长度停止 → decode token ids 成文本。官方 runtime 文档说明 C++ runtime 负责从 tokenization 到 final text 的 autoregressive decoding loop。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/developer_guide/software-design/cpp-runtime-overview.html))

### 6.2 VLM 多模态推理

VLM 流程多了一个 visual engine：先 export LLM，再 export visual encoder；在 edge 上分别 build language engine 和 visual engine；推理时 JSON 的 content 可以包含 image 和 text，`llm_inference` 使用 `--multimodalEngineDir` 载入视觉 encoder。官方 examples 对 Qwen2.5-VL-3B 给出了完整流程。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/developer_guide/getting-started/examples.html))

### 6.3 ASR

官方 ASR 示例支持 Qwen3-ASR-0.6B：导出 audio encoder 与 language model，设备端分别 build LLM engine 和 audio encoder engine；音频先预处理成 mel-spectrogram safetensors，再通过 JSON 中的 `{"type": "audio", "audio": "..."}` 输入。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/user_guide/examples/asr.html))

### 6.4 TTS

官方 TTS 示例支持 Qwen3-TTS-12Hz-1.7B-CustomVoice，流程比 LLM 更复杂：Talker、CodePredictor、Code2Wav 三个 engine 分别构建；文档还提醒 Qwen3-TTS 的 ONNX export 固定 batch size 为 1，所以 build 时 `--maxBatchSize` 必须为 1。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/user_guide/examples/tts.html))

### 6.5 MoE

官方 MoE 示例当前支持 Qwen3-30B-A3B-GPTQ-Int4，并说明 MoE export 只能使用 CPU `--device cpu`，无需 GPU；build 和 inference 仍然复用普通 `llm_build` 和 `llm_inference`。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/user_guide/examples/moe.html))

### 6.6 EAGLE speculative decoding

EAGLE 是它的核心加速能力之一。官方示例中需要分别处理 base model 和 draft model：base export 时带 `--is_eagle_base`，draft model 也要 quantize/export，然后 build base/draft engine，推理时加 `--eagle`。示例文档称 generation 可获得约 1.5–3x 加速，但 EAGLE 的收益强依赖 draft/base 匹配度和 acceptance rate。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/developer_guide/getting-started/examples.html))

### 6.7 LoRA

LoRA 支持两种思路：**static merge** 和 **dynamic runtime LoRA**。static merge 简单，适合单 adapter；dynamic runtime 允许多个 adapter 运行时切换，但需要先 `insert-lora` 生成支持 LoRA 的 ONNX，再 `process-lora` 处理 adapter，并在 build 时设置 `--maxLoraRank`。官方文档说明同一 batch 内所有 request 必须使用同一个 LoRA adapter。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/developer_guide/features/lora.html))

### 6.8 System Prompt KV Cache

System prompt cache 会把重复 system prompt 的 KV cache 缓存在内存中，下次相同 system prompt 和相同 LoRA adapter 命中时复用，从而降低 TTFT。官方说明 cache key 是 `(system_prompt_text, lora_weights_name)`，必须精确字符串匹配，且只在 runtime 生命周期内保存在内存里。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/developer_guide/features/system-prompt-cache.html))

### 6.9 Vocabulary Reduction

Vocabulary reduction 通过缩小 LM head 输出词表来减少 LM head 计算，只适合输出空间可控的任务。官方文档强调它只加速 LM head，用户要负责 token mapping，`vocab_map.safetensors` 必须包含 EOS；EAGLE 场景还必须包含 draft `d2t.safetensors` 涉及的 token。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/developer_guide/features/reduce-vocab.html))

### 6.10 FP8 KV Cache

FP8 KV cache 把 K/V cache 用 FP8 E4M3 存储，官方称可把 KV memory 大约减半；scale 来自 calibration amax，runtime 存 FP8 KV，attention 前按 scale dequant 到 FP16 参与计算。文档也提醒 Qwen2.5-7B / Qwen2.5-VL-7B 等模型可能有 accuracy issue，需要实测，必要时退回 FP16 KV。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/developer_guide/features/FP8KV.html))

### 7. 软件架构：三段式 pipeline

### 7.1 Python Export Pipeline

Python 部分负责把 HF 模型转成可被 TensorRT builder 消化的 ONNX。官方 software design 说它的阶段包括：model loading、可选 quantization、ONNX export、graph surgery、config generation。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/developer_guide/software-design/python-export-pipeline.html))

官方列出的 CLI 工具有：

| CLI | 作用 |
| --- | --- |
| tensorrt-edgellm-quantize-llm | LLM 权重量化 |
| tensorrt-edgellm-export-llm | 导出 LLM ONNX |
| tensorrt-edgellm-export-visual | 导出视觉 encoder |
| tensorrt-edgellm-quantize-draft | EAGLE draft 模型量化 |
| tensorrt-edgellm-export-draft | EAGLE draft 模型导出 |
| tensorrt-edgellm-insert-lora | 在 ONNX 图中插入 LoRA 结构 |
| tensorrt-edgellm-process-lora | 处理 LoRA adapter 权重 |

([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/developer_guide/software-design/python-export-pipeline.html))

### 7.2 Engine Builder

C++ builder 把 ONNX 转成 TensorRT engine。官方 design 文档把 builder 责任写成：解析 ONNX、设置 dynamic profiles、编译 TensorRT engines、生成 runtime configs、处理 EAGLE/VLM/LoRA。它的流程包括 plugin loading、config parsing、network creation、model type detection、ONNX parsing、profile setup、engine compilation、file management；EAGLE 场景会对 base 和 draft 分别 build。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/developer_guide/software-design/engine-builder.html))

一个很重要的点：**ONNX / engine 不能跨 TensorRT Edge-LLM 或 TensorRT 版本随便复用**。官方文档写明升级 TensorRT Edge-LLM 或 TensorRT 后要 re-export / rebuild。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/developer_guide/software-design/engine-builder.html))

### 7.3 C++ Runtime

C++ runtime 是最终执行层。官方 runtime overview 说标准 runtime 由 `LLMInferenceRuntime`、`LLMEngineRunner`、Tokenizer、MultimodalRunner、Linear KV Cache、Sampling Kernels、TensorRT Engine 等组成；`LLMEngineRunner` 使用单个 TensorRT execution context 切换 profile，管理 KV cache、CUDA Graph、dynamic LoRA 等。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/developer_guide/software-design/llm-inference-runtime.html))

### 8. 代码实现细节：真正运行时怎么串起来

下面用源码和官方设计文档一起解释。

### 8.1 目录心智图

官方 overview 把主要代码位置列为：

| 路径 | 作用 |
| --- | --- |
| tensorrt_edgellm/ | Python export / quantization / LoRA / multimodal 工具链 |
| cpp/ | C++ builder、runtime、kernels、plugins |
| examples/ | llm_build、llm_inference、VLM/EAGLE/LoRA 示例 |

([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/developer_guide/getting-started/overview.html))

结合 API 目录，C++ 侧可以粗分为：

| 模块 | 关键点 |
| --- | --- |
| cpp/builder | LLM / visual / audio builder |
| cpp/runtime | LLMInferenceRuntime、LLMInferenceSpecDecodeRuntime、LLMEngineRunner、EagleDraftEngineRunner、LinearKVCache |
| cpp/kernels | embedding、KV cache、EAGLE accept、MoE、Mamba、FMHA/XQA、INT4 GEMM 等 |
| cpp/plugins | Attention、INT4 GEMM、INT4 MoE、Mamba、VIT Attention 等 TensorRT plugin |
| cpp/multimodal | Audio runner、Qwen/Intern/Phi visual runner、Code2Wav runner |
| cpp/sampler | top-k/top-p/temperature sampling |

官方 API 目录也能看到这些模块和 kernel/plugin 项。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/user_guide/examples/asr.html))

### 8.2 标准 LLM 的 runtime 初始化

`LLMInferenceRuntime` 构造函数大致做这些事：

1. 在 `engineDir` 找 `.engine` 文件；
2. 读取 `config.json`；
3. 加载 `embedding.safetensors`；
4. 创建 `LLMEngineRunner`；
5. 按 max batch / max input / hidden size 分配 GPU tensor；
6. 加载 tokenizer；
7. 如果用了 reduced vocabulary，则加载 `vocab_map.safetensors`；
8. 如果配置了 multimodal engine，则尝试加载 audio / visual runner。

这些细节可以直接在 `cpp/runtime/llmInferenceRuntime.cpp` 看到：源码中先找 `.engine`，加载 `embedding.safetensors`，创建 `mLLMEngineRunner`，分配 `mSamplingWorkspace`、`mInputIds`、`mInputsEmbeds`、`mOutputLogits` 等 tensor，再加载 tokenizer 和可选 multimodal runners。([GitHub](https://github.com/NVIDIA/TensorRT-Edge-LLM/raw/refs/heads/main/cpp/runtime/llmInferenceRuntime.cpp))

### 8.3 `LLMEngineRunner` 的关键职责

`LLMEngineRunner` 负责真正驱动 TensorRT engine。源码中它解析 `config.json`，反序列化 CUDA engine，分配 TensorRT execution context device memory，并且显式写了当前 LLM engine 只使用两个 optimization profiles：`kPREFILL_PROFILE_INDEX = 0` 和 `kGENERATION_PROFILE_INDEX = 1`。([GitHub](https://github.com/NVIDIA/TensorRT-Edge-LLM/raw/refs/heads/main/cpp/runtime/llmEngineRunner.cpp))

这意味着 engine build 时的 profile 设计很关键：

| Profile | 用途 |
| --- | --- |
| Prefill / Context | 一次性吃完整 prompt，生成 KV cache 和首 token logits |
| Generation / Decode | 每轮吃 1 个 token，复用并更新 KV cache |

官方 engine builder 文档也明确说明 LLM builder 使用 dual optimization profiles：Context/Prefill 和 Generation/Decode。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/developer_guide/software-design/engine-builder.html))

### 8.4 标准 `handleRequest` 调用链

`LLMInferenceRuntime::handleRequest` 的调用链可以概括为：

```text
handleRequest
  ├─ examineRequest
  ├─ applyChatTemplate
  ├─ 可选 save system prompt KV cache
  ├─ multimodal preprocess + visual/audio infer，或纯文本 tokenizer encode
  ├─ setUpForPrefillExecution
  │    ├─ 检查 system prompt KV cache 命中
  │    ├─ pack input ids
  │    ├─ reset LinearKVCache
  │    └─ switch LoRA weights
  ├─ embeddingLookup / embeddingLookupWithImageInsertion / embeddingLookupMultimodal
  ├─ executePrefillStep
  ├─ topKtopPSamplingFromLogits
  ├─ while not finished:
  │    ├─ embeddingLookup(selected token)
  │    ├─ executeVanillaDecodingStep
  │    └─ sample token
  └─ tokenizer.decode
```

源码里可以看到它先 apply chat template，检查音频/视觉输入，纯文本时用 tokenizer encode；随后 `setUpForPrefillExecution` 做 input packing、KV cache reset、LoRA switch；prefill 后调用 `topKtopPSamplingFromLogits`；decode loop 里每轮对 selected token 做 embedding lookup，再执行 `executeVanillaDecodingStep`，最后 decode 输出文本。([GitHub](https://github.com/NVIDIA/TensorRT-Edge-LLM/raw/refs/heads/main/cpp/runtime/llmInferenceRuntime.cpp))

### 8.5 System Prompt KV Cache 在源码里的实现方式

源码里 `setUpForPrefillExecution` 会用 `(systemPrompt, loraWeightsName)` 做 key，命中后把预先保存的 KV cache instantiate 到当前 batch 的 KV cache buffer 中，然后把已经缓存的 system prompt token 从本次 input ids 中切掉，只计算后续部分。源码还检查 token ids 是否和 cached prompt 对齐，不对齐会 warning。([GitHub](https://github.com/NVIDIA/TensorRT-Edge-LLM/raw/refs/heads/main/cpp/runtime/llmInferenceRuntime.cpp))

这解释了为什么官方文档强调 system prompt 必须“精确字符串匹配”，而且 LoRA adapter 不同会分开缓存。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/developer_guide/features/system-prompt-cache.html))

### 8.6 EAGLE runtime 的实现方式

EAGLE 不是简单在标准 runtime 上加一个 flag，而是有独立的 `LLMInferenceSpecDecodeRuntime`。官方 design 文档说标准 runtime 和 spec-decode runtime 互斥，SpecDecode runtime 里有 `mBaseEngineRunner` 和 `mDraftEngineRunner`，分别管理 base/draft engine。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/developer_guide/software-design/cpp-runtime-overview.html))

源码中 `LLMInferenceSpecDecodeRuntime` 构造函数会加载共享 `embedding.safetensors`，然后固定读取：

```text
eagle_base.engine
base_config.json
eagle_draft.engine
draft_config.json
d2t.safetensors
```

其中 `d2t.safetensors` 是 draft vocab 到 base vocab 的映射表。源码还会根据 base/draft engine 的 max batch 取最小值作为 runtime batch size，并检查 `draftingStep * draftingTopK` 和 `verifyTreeSize` 是否超过 draft engine 能力。([GitHub](https://github.com/NVIDIA/TensorRT-Edge-LLM/raw/refs/heads/main/cpp/runtime/llmInferenceSpecDecodeRuntime.cpp))

EAGLE 的 handle loop 大致是：

```text
base prefill
while not finished:
  if generationRound == 0:
      draft prefill
  else:
      draft accept-token step
  construct draft tree
  base model verify tree
  accept tokens
  batch eviction for finished samples
decode outputs
```

源码里能看到 `runBaseModelPrefill`、`runDraftModelPrefill`、`runDraftModelAcceptToken`、`constructDraftTree`、`runBaseModelVerification`、`performBatchEvict` 等流程；官方设计文档也说明：draft 提出候选 token tree，base 并行验证，只有与 base top-1 匹配的 draft token 被接受，最终输出仍来自 base 模型。([GitHub](https://github.com/NVIDIA/TensorRT-Edge-LLM/raw/refs/heads/main/cpp/runtime/llmInferenceSpecDecodeRuntime.cpp))

### 9. 性能优化怎么做

### 9.1 先区分 TTFT 和 decode speed

端侧 LLM 优化要分两类：

| 指标 | 主要瓶颈 | 对应优化 |
| --- | --- | --- |
| TTFT / 首 token 延迟 | prompt prefill、VLM encoder、system prompt 重复计算 | system prompt cache、chunked/prefill profile、短 prompt、VLM token 控制 |
| tokens/s / 生成速度 | decode loop、KV cache、LM head、sampling、kernel launch | EAGLE、CUDA Graph、INT4/NVFP4、vocab reduction、FP8 KV cache |

官方 runtime 文档也明确把 prefill 和 decode 区分开：prefill 并行处理输入序列并生成 KV cache，decode 是顺序自回归，每步更新 KV cache 和采样。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/developer_guide/software-design/llm-inference-runtime.html))

### 9.2 精度选择策略

实战上建议这样选：

| 阶段 | 建议 |
| --- | --- |
| 首次跑通 | FP16，先确认 tokenizer、chat template、输出正确 |
| Thor 上性能版 | 优先试 NVFP4，官方把它列为 SM100+ / Thor 推荐 |
| Ada / SM89+ | FP8 是较稳的性能/内存折中 |
| 显存非常紧 | INT4 AWQ/GPTQ，但要做精度回归 |
| 长上下文 | 叠加 FP8 KV cache，但注意模型特定精度风险 |

官方 best practices 也建议：先从 FP16 baseline 开始，FP8 作为平衡选择，INT4 适合 short-prefill / decode-critical，NVFP4 在 Thor 上适合追求最佳 prefill/decode 表现。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/developer_guide/software-design/python-export-pipeline.html))

### 9.3 EAGLE：看 acceptance rate，不要盲开

EAGLE 的收益来自 draft 一次提出多个候选，base 一次验证多 token，减少 base decode 次数。收益高的前提是：

1. draft 模型必须针对 exact base model 训练；
2. draft 与 base 的 token 分布接近；
3. `draftTopK`、`draftStep`、`verifyTreeSize` 设置合理；
4. acceptance rate 足够高。

官方文档说明 draft 必须为精确 base model 训练；示例里默认 `draftTopK=10`、`draftStep=6`、`verifyTreeSize=60`；源码和 CLI 中也把这些作为 EAGLE 参数暴露。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/developer_guide/software-design/python-export-pipeline.html))

一个细节：早期 examples 中 EAGLE 示例强调 batch size 1；但最新 SpecDecode runtime 文档与源码已经有 dynamic batching / batch eviction 设计。因此工程上不要只看示例，要以当前 release、engine build 参数和自己的 benchmark 为准。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/developer_guide/getting-started/examples.html))

### 9.4 CUDA Graph：降低 decode loop launch overhead

官方 runtime 文档说 CUDA Graph 可把 decode 这类重复小 kernel 的 launch overhead 降低约 10–30%；源码中 `captureDecodingCUDAGraph` 会按 batch size 捕获 vanilla decoding graph，如果启用 LoRA，还会对不同 LoRA weights 分别捕获。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/developer_guide/software-design/llm-inference-runtime.html))

这意味着：如果你做动态 LoRA、多 batch、多 shape，要注意 graph capture 数量、warmup 时间和显存开销。

### 9.5 KV cache 容量要精打细算

`maxKVCacheCapacity` 不是越大越好。它决定最大 `prompt + generation` token 容量，也决定 KV buffer 大小。源码中如果 `input length + maxGenerateLength > maxKVCacheCapacity`，runtime 会降低 max generation length 并 warning。([GitHub](https://github.com/NVIDIA/TensorRT-Edge-LLM/raw/refs/heads/main/cpp/runtime/llmInferenceRuntime.cpp))

经验策略：

```text
maxKVCacheCapacity >= maxInputLen + maxGenerateLength
```

但不要把它设到远大于实际需求，否则会浪费边缘设备上非常宝贵的显存/统一内存。

### 9.6 batch size：边缘交互优先 1–2

官方 builder best practices 建议 interactive 场景用 batch 1–2，batch processing 用 4–8。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/developer_guide/software-design/engine-builder.html))

端侧经常不是“越大 batch 越好”，因为用户感知更看重首 token 延迟和功耗；batch 过大还会放大 KV cache、workspace、TensorRT profile 的内存占用。

### 9.7 VLM 优化重点：控制 image tokens

VLM 的成本不只在 LLM，还在 visual encoder 和插入到 LLM 的 image tokens。官方 visual builder 文档提到 Qwen VL 支持 dynamic patches，InternVL/Phi-4 则涉及 image tokens 的范围和倍数约束。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/developer_guide/software-design/engine-builder.html))

落地建议是：先固定分辨率、固定最大 image token 数，测 TTFT；不要一开始就上多图、高分辨率、长文本、EAGLE、LoRA 全开。

### 9.8 用 profiling 拆瓶颈

`llm_inference` 支持 `--dumpProfile` 和 `--warmup`，官方文档说明 profiling 输出包含 per-token latency、prefill time、generation time、KV-cache usage、memory allocation stats。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/developer_guide/getting-started/examples.html))

建议每次优化只改一个变量：

```text
FP16 baseline
→ FP8/NVFP4
→ FP8 KV cache
→ EAGLE
→ system prompt cache
→ vocab reduction
→ CUDA Graph / warmup / batch tuning
```

否则很难判断收益来自哪里。

### 10. 输入 JSON 与 chat template：容易踩坑的地方

TensorRT Edge-LLM 的 input JSON 支持文本、多轮、多模态、LoRA、system prompt cache、disable speculative decode 等字段。官方文档列出全局字段包括 `batch_size`、`temperature`、`top_p`、`top_k`、`max_generate_length`、`apply_chat_template`、`enable_thinking`、`available_lora_weights`；request 级字段包括 `messages`、`lora_name`、`save_system_prompt_kv_cache`、`disable_spec_decode`。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/developer_guide/getting-started/input-format.html))

Chat template 不是直接运行 Jinja，而是在 export 时从 HF template 转成轻量 JSON 的 `processed_chat_template.json`；Qwen3 的 thinking / no-thinking 模式由 `enable_thinking` 控制，支持时会选择不同 generation prompt。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/developer_guide/getting-started/chat-template-format.html))

工程注意点：

| 点 | 说明 |
| --- | --- |
| apply_chat_template | 生产中建议固定为 true，除非你自己完全掌控 raw prompt |
| enable_thinking | Qwen3 等模型要明确测试 true/false 的输出、延迟和 token 数 |
| system prompt cache | system prompt 字符串必须完全一致 |
| LoRA | 同一 batch 必须同一个 adapter |
| multimodal path | 图片/音频路径必须是 device 可访问路径 |
| EAGLE disable | 如果 batch 中任何 request disable spec decode，官方文档说明整个 batch 会 disable |

([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/developer_guide/getting-started/input-format.html))

### 11. 已知限制和风险

这个项目很新：公开 release 节奏从 2026 年 1 月 v0.4.0 到 2026 年 4 月 v0.6.1，非常活跃。v0.6.0 release 还在 GTC 2026 被 featured，并展示 Jetson AGX Thor 上 ASR/LLM/TTS 后端能力。([GitHub](https://github.com/NVIDIA/TensorRT-Edge-LLM/releases?utm_source=chatgpt.com))

主要风险：

1. **版本兼容性**：ONNX / engine 不能跨 TensorRT Edge-LLM 或 TensorRT 版本随便复用，升级要 re-export / rebuild。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/developer_guide/software-design/engine-builder.html))
2. **内存压力**：安装文档说 7B/8B export，尤其 FP8 ONNX export，可能需要很高 CPU/GPU 内存；已知问题页面还提到 7B–8B 可能遇到 `cudaMallocAsync` 问题，需要增加 huge pages。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/developer_guide/getting-started/installation.html))
3. **TensorRT 版本差异**：0.6.0 known issues 写到 TensorRT 10.15 对部分模型 NVFP4 可能造成 accuracy degradation，建议用 JetPack 7.1 搭载的 TensorRT 10.13.3.9。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/user_guide/getting_started/limitations.html))
4. **batch size 陷阱**：known issues 里也写到 `--maxBatchSize=1` 可能导致部分模型精度下降或 engine build failure，设为 2 可能解决；还有 Cutedsl kernels 在 runtime batch > 1 时可能 hang，因此只在 runtime batch = 1 时启用。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/user_guide/getting_started/limitations.html))
5. **FP8 KV cache 精度风险**：部分 Qwen2.5 模型可能因 last-layer KV 大值带来 accuracy issue，需要回归测试。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/developer_guide/features/FP8KV.html))
6. **EAGLE 依赖 draft/base 匹配**：draft model 必须与 base model 精确匹配，否则 acceptance rate 低，甚至不如普通 decode。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/developer_guide/software-design/python-export-pipeline.html))
7. **TTS 特殊流程**：Qwen3-TTS 当前还需要单独 qwen-tts 环境，官方文档提示它可能破坏当前环境里的 transformers/torch 版本，因此建议单独 virtualenv。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/user_guide/examples/tts.html))

### 12. 实战落地建议

### 12.1 最稳的起步路线

先不要一上来就跑 7B/30B/MoE/EAGLE/VLM。建议：

```text
Qwen3-0.6B FP16
→ Qwen3-0.6B FP8 或 NVFP4
→ Qwen3-1.7B / 4B
→ 加 system prompt cache
→ 加 FP8 KV cache
→ 加 EAGLE
→ 再上 VLM / ASR / TTS / MoE
```

官方 quick start 本身也是以 Qwen3-0.6B 为入门模型，并给出约 15 分钟跑通的路径。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/developer_guide/getting-started/quick-start-guide.html))

### 12.2 生产化 checklist

| 项 | 建议 |
| --- | --- |
| 版本固定 | 固定 TensorRT Edge-LLM commit、TensorRT、CUDA、JetPack/DriveOS |
| 模型签名 | 官方 best practices 建议做 model signing / verification |
| 精度回归 | FP8、INT4、NVFP4、FP8 KV 都要测任务集 |
| 性能回归 | 分别记录 TTFT、tokens/s、峰值内存、功耗 |
| engine 参数 | 记录 maxBatchSize、maxInputLen、maxKVCacheCapacity、LoRA rank、EAGLE tree size |
| cache 策略 | system prompt cache 适合固定角色/固定长指令场景 |
| 异常保护 | input JSON 长度、图片数量、音频时长都要设上限 |
| rebuild 纪律 | 升级 TensorRT / Edge-LLM 后重新 export/build |

官方文档里也提到 model signing/verification、校准数据质量、监控内存、缓存下载、记录配置等实践。([NVIDIA GitHub](https://nvidia.github.io/TensorRT-Edge-LLM/latest/developer_guide/software-design/python-export-pipeline.html))

### 13. 最核心的理解

TensorRT Edge-LLM 的设计哲学是：

> **把大模型推理从“Python + 云端服务框架”压缩成“ONNX/TensorRT engine + C++ runtime + CUDA kernels”，服务于低 batch、低延迟、低内存、可嵌入的边缘 Physical AI 场景。**

它的价值不在于“又一个能跑 LLM 的 demo”，而在于把 **量化、TensorRT engine 构建、VLM/audio/TTS、多 LoRA、EAGLE、FP8 KV cache、system prompt cache、CUDA Graph、profiling** 这些工程能力集中在一个端侧 C++ runtime 里。真正用好它的关键不是只会跑 `llm_inference`，而是要掌控：

```text
模型选择
→ 量化策略
→ ONNX export
→ engine profile
→ KV cache 容量
→ prefill/decode 拆分
→ EAGLE acceptance rate
→ LoRA / VLM / audio 的额外路径
→ profiling 驱动优化
→ 版本和精度回归
```

这套链路一旦打通，它就很适合做 Jetson/DRIVE 上的实时智能体、多模态助手、车载/机器人语音交互、端侧视觉问答和离线语音理解。
