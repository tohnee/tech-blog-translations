## FSDP1 wrap 与 ignore 机制详解：多模态模型冻结视觉塔的完整方案

本文是 FSDP 源码解析系列的工程实践篇。前几篇已梳理了 FSDP 的初始化、前向反向链路与预取机制，本文聚焦一个在多模态模型训练中反复出现的工程问题：**视觉塔冻结时，如何正确配置 `wrap_policy` 与 `ignored_modules`，在保住分片收益的同时，消除冻结参数带来的冗余通信与计算开销**。

![](https://pic3.zhimg.com/v2-10f204fb0696b35767c7c551f1a0c51e_r.jpg)

相关参考文档如下：

- [FSDP 源码解析（一）：初始化与显存分配](https://zhuanlan.zhihu.com/p/2014097067107182088)
- [FSDP 源码解析（二上）：前向与反向——执行链路全解析](https://zhuanlan.zhihu.com/p/2014783611962943132)

## 0. 三个机制的本质

讨论具体方案之前，先把 `wrap_policy`、`ignored_modules`、`use_orig_params` 的底层语义厘清——后续所有取舍都从这里出发。

### wrap_policy：参数的"组织方式"

`wrap_policy` 决定哪些模块被包装为独立的 FSDP Unit。每个 Unit 内部的所有参数会被打平、拼接成一个 `FlatParameter`，统一参与 AllGather/ReduceScatter 调度。未被任何 policy 捕获的参数，**全部落入 Root Unit 的 `FlatParameter`。**

以 Qwen2.5-7B 为例，默认 wrap 配置下的 flat 边界如下：

```powershell
root FSDP
├── _fsdp_wrapped_module.model.layers.0 FSDP
│     FlatParameter_layer0   ← 包含：
│                               self_attn.q/k/v/o_proj 的 weight/bias
│                               mlp.gate/up/down_proj 的 weight
│                               input_layernorm/post_attention_layernorm 的 weight
│
├── _fsdp_wrapped_module.model.layers.1 FSDP
│     FlatParameter_layer1   ← （参数组成与 layers.0 完全一致）
...
└── FlatParameter_root        包含：
model.embed_tokens.weight（Embedding 层）
model.norm.weight（Qwen2RMSNorm 层）
lm_head.weight（Linear 层）
```

Root Unit 有一个关键特性：**豁免前向后置 reshard**。判断逻辑位于 `_post_forward_reshard`：

```python
# _runtime_utils.py: _post_forward_reshard
free_unsharded_flat_param = (
    not state._is_root   # 根节点直接短路为 False，不释放完整参数
    and handle._sharding_strategy in RESHARD_AFTER_FORWARD_HANDLE_STRATEGIES
)
_reshard(state, handle, free_unsharded_flat_param)
```

非根节点前向结束后，控制权交回父节点，父节点不再需要子节点的完整参数，立即 reshard 合理。

![](https://pic2.zhimg.com/v2-728dd3d35576f94d5a32391ac87afb9d_r.jpg)

在默认的 FSDP 配置下，`lm_head` 通常归属于 **Root Unit**。`lm_head` 是前向传播的**最后一个**算子。紧接着 `loss.backward()`，`lm_head` 又是反向传播计算梯度的**第一个**算子。如果在 `forward` 结束时立即 Reshard（释放）`backward` 就要立即重新 AllGather。为了**消除这一冗余的通信开销**，FSDP 豁免了 Root Unit 的前向后置 Reshard。

```text
# _runtime_utils.py: _should_free_in_backward
def _should_free_in_backward(state, handle):
    if not handle.uses_sharded_strategy:
        return False
    return (
        state._sync_gradients
        or handle._sharding_strategy in RESHARD_AFTER_FORWARD_HANDLE_STRATEGIES
    )
```

在正常训练模式下，由于 `_sync_gradients=True` 满足了释放判定条件，Root Unit 的 `_full_param_padded` 只有在**整个反向传播彻底结束**后才触发 Reshard。这导致 Root Unit 的完整参数在显存中呈现出“**长效常驻**”特性。默认情况下，**Embedding 层通常也归属于 Root Unit，那么其生命周期横跨了从前向起始到反向终点的完整时钟窗口，如下图所示：**

![](https://pic4.zhimg.com/v2-1f1d4aed7371ece85a896d71e75079b3_r.jpg)

💡 显存受限时的包装策略：在 lm_head 与 embedding 参数不共享的前提下，若显存资源极度紧张，应尽可能通过 wrap_policy 将 embedding 层移出 Root Unit。

### ignored_modules：从 FSDP 生命周期名单中彻底剔除

`ignored_modules` 中的模块，FSDP 初始化时直接跳过，其参数不会进入任何 `FlatParameter`。这一"跳过"体现在三处关键路径：

![](https://pic2.zhimg.com/v2-af912f12048afc28f4b49f0a7a7919a5_r.jpg)

**校验阶段**（`_check_orig_params_flattened`）：ignored 参数直接 `continue`，不做任何合法性检查。

**实化阶段**（`_init_param_handle_from_module` 第 4 步）：`_materialize_with_param_init_fn` 与 `_materialize_meta_module` 均显式跳过 `state._ignored_modules`，Meta Tensor 不会被 `param_init_fn` 实化。

**同步阶段**（`_init_param_handle_from_module` 第 9 步）：`sync_module_states=True` 同步的是 `managed_params`，后者通过 `_get_orig_params(module, state._ignored_params)` 生成，已过滤 ignored 参数，广播不覆盖它们。

**💡三处跳过带来一个直接后果**：**ignored 模块的设备迁移、参数初始化、跨 rank 同步，全部需要开发者手动处理**。这是使用 `ignored_modules` 必须承担的开发者责任，后面会给出ignore参数处理的case。

### use_orig_params：混合 requires_grad 的应急补丁

`use_orig_params` 的本意是保留原始参数引用以支持按参数名访问，但在实际工程中，它常被用作处理混合梯度（Mixed Gradients）的**应急补丁**。

在参数打平前，FSDP 的 `_validate_tensors_to_flatten` 函数设有一条硬约束：当 `use_orig_params=False` 时，同一 FSDP Unit 内所有参数的 `requires_grad` 必须严格一致。若尝试将冻结参数与可训练参数混装，将直接触发 `ValueError`。

```python
# flat_param.py: _validate_tensors_to_flatten
if (
    not self._use_orig_params
    and flat_param_requires_grad is not None
    and tensor.requires_grad != flat_param_requires_grad
):
    raise ValueError(
        "Must flatten tensors with uniform `requires_grad` when "
        "`use_orig_params=False`"
    )
```

开启 `use_orig_params=True` 可以强制绕过此校验，允许 Unit 内共存混合梯度。然而，这并非免费的午餐：**其底层代价是 `FlatParameter` 的 `requires_grad` 采用“逻辑或”聚合。只要 Unit 内存在一个可训练参数，整个 Unit 都会被标记为需要梯度。**这意味着被冻结的参数也会被迫参与 AllGather/ReduceScatter 通信流，并导致相关的 Backward Kernel “连坐”执行，白白浪费计算与带宽资源。

💡 **三者的本质差异一句话**：`ignored_modules` 是物理隔离，参数根本不进 `FlatParameter`；`use_orig_params=True` 是逻辑补丁，参数仍在 `FlatParameter` 中，只是绕过了校验，通信与计算的额外开销依然存在；`wrap_policy` 决定哪些参数进哪个 Unit，是问题的根源，也是解决方案的起点。

## 1. 多模态模型的典型坑点：以 Qwen3VL 为例

在厘清 FSDP 机制后，我们剖析多模态训练中的实际问题。以 **Qwen3VL (8.77B)** 为例，其复杂的异构结构是显存管理的重灾区：

```powershell
Qwen3VLForConditionalGeneration
└── model: Qwen3VLModel
    ├── visual: Qwen3VLVisionModel          # 视觉塔，训练时冻结
    │   ├── patch_embed: Qwen3VLVisionPatchEmbed
    │   │   └── proj: Conv3d(3, 1152, kernel=(2,16,16))       ~180 万参数
    │   ├── pos_embed: Embedding(2304, 1152)                   ~265 万参数
    │   ├── rotary_pos_emb: Qwen3VLVisionRotaryEmbedding       无可训练参数
    │   ├── blocks: 27 × Qwen3VLVisionBlock                   ~每块 1570 万参数  ← 应 wrap
    │   ├── merger: Qwen3VLVisionPatchMerger                   ~8100 万参数       ← 应 wrap
    │   └── deepstack_merger_list: 3 × Qwen3VLVisionPatchMerger ~每块 8100 万参数 ← 应 wrap
    └── language_model: Qwen3VLTextModel    # 语言侧，正常训练
        ├── embed_tokens: Embedding(151936, 4096)              ~6.2 亿参数  ← 应 wrap
        ├── layers: 36 × Qwen3VLTextDecoderLayer              ~每块 2.0 亿参数  ← 应 wrap
        └── norm: Qwen3VLTextRMSNorm(4096)
└── lm_head: Linear(4096→151936)                              ~6.2 亿参数  ← 应 wrap
```

从参数分布来看，视觉侧的 4 个 PatchMerger（约 3.2 亿参数）体量不小，应独立成 Unit；语言侧的 `embed_tokens` 和 `lm_head`（各约 6.2 亿参数）同理。这些模块若未被 wrap_policy 捕获，全部落入 Root Unit，是后续两个问题的共同根源。

### 问题一：wrap_policy 配置不完整，大量参数堆积 Root Unit

![](https://pic2.zhimg.com/v2-378679ce7d980ff083ddfaba9b581943_r.jpg)

verl 默认从模型的 `_no_split_modules` 自动获取需要 wrap 的类。Qwen3VL 的 `_no_split_modules = ["Qwen3VLTextDecoderLayer", "Qwen3VLVisionBlock"]`，这导致 `merger`、`deepstack_merger_list`（共 4 个 Merger）、`patch_embed`、`pos_embed`、`embed_tokens`、`lm_head` 全部落入 Root Unit，累计超过 2.5 GB。从实际的 `param_infos` 日志可以清晰看到堆积情况：

```powershell
# 默认策略下的 Root Unit（节选）
ParamInfo(module=Conv3d(...),     module_name='model.visual.patch_embed.proj')
ParamInfo(module=Embedding(...),  module_name='model.visual.pos_embed')
ParamInfo(module=Linear(...),     module_name='model.visual.merger.linear_fc1')
ParamInfo(module=Linear(...),     module_name='model.visual.merger.linear_fc2')
ParamInfo(module=Linear(...),     module_name='model.visual.deepstack_merger_list.0.linear_fc1')
# ... deepstack_merger_list 0/1/2 的全部参数 ...
ParamInfo(module=Embedding(...),  module_name='model.language_model.embed_tokens')
ParamInfo(module=Linear(...),     module_name='lm_head')
```

BF16 精度下，Root Unit 堆积的 2.5 B 参数对应 5 GB 的 `_full_param_padded` 显存占用。由于 Root Unit 豁免 reshard，这 5 GB 在整个 forward-backward 窗口内常驻显存，构成持续的显存底噪。

更严重的问题在于显存压力的叠加：反向传播时，系统需为 Root Unit 额外申请 BF16 梯度缓冲区（5 GB），若 `reduce_dtype=float32` 则进一步膨胀至 10 GB。常驻参数与瞬时梯度申请的时间窗口高度重叠，极易触发 OOM。

### 问题二：冻结参数混入 Root Unit 带来的通信与计算连坐

执行 `vision_tower.requires_grad_(False)` 后，Root Unit 变为一个 `requires_grad` 状态混杂的容器——冻结的视觉参数（`patch_embed`、`merger` 等）与可训练的语言参数（`language_model.norm`）共存于同一个 `FlatParameter`。

**校验层面：从报错到性能空转。** `use_orig_params=False` 时，`_validate_tensors_to_flatten` 会检测到混合的 `requires_grad` 状态并直接抛出异常。开启 `use_orig_params=True` 能绕过报错，但代价是 `flat_param_requires_grad` 以逻辑或聚合——只要 Unit 内存在任一可训练参数，整个 `FlatParameter.requires_grad=True`，冻结参数被迫参与全套 AllGather 与 ReduceScatter 通信。

![](https://pic1.zhimg.com/v2-45bdb21b8061280b763c60c01dd2a35a_r.jpg)

**显存层面：冗余梯度缓冲区。** 正常情况下，Root Unit 只需为 `embed_tokens` 和 `lm_head` 申请约 2.5 GB 的梯度空间（对应 12.4 亿参数）。但 `use_orig_params=True` 导致 FSDP 为 Unit 内所有参数统一申请连续的 flat gradient 缓冲区，已冻结的视觉参数也被纳入其中，产生大量本不应存在的冗余梯度显存占用。

![](https://pic3.zhimg.com/v2-d635f7c64d27b5987774cfcca762b028_r.jpg)

**计算层面：反向传播路径强制延伸。** 以 `patch_embed` 为例：它与语言侧参数同属 Root Unit，`requires_grad` 被强制置为 True，Autograd 引擎会额外为其分配参数梯度缓冲区。更严重的代价在于梯度流的传播路径本身——为了将梯度从 `lm_head` 一路传回 `patch_embed`，中间所有冻结 VisionBlock 的 backward kernel 必须逐层执行。值得注意的是，这些冻结层的参数梯度 dW 本不需要计算，backward kernel 在此唯一的目的是计算激活梯度 dX 并向下传递——换言之，花费了完整的反向计算代价，却只做了其中最廉价的一步。冻结层本应是梯度流的天然截断点，而此时却沦为纯粹的梯度中转站，从视觉塔顶层到底层逐层接力，既消耗了 backward kernel 的计算资源，又占用了 AllGather/ReduceScatter 的通信带宽，产生了全链路的无效开销。

以qwen3vl 模型为例，可以看到在冻结Vision模块的训练场景，调用栈中出现了VisionBlock部分的冗余重计算：

![](https://pic2.zhimg.com/v2-60ffda4d0c7fc48046f083e5715b9cc5_r.jpg)

## 2. 三种方案的取舍

| 方案 | 机制 | 优点 | 缺点 |
| --- | --- | --- | --- |
| use_orig_params=True | 逻辑补丁，绕过混合校验 | 一行代码，零改动 | 冻结参数参与 AllGather/ReduceScatter；backward kernel 连坐执行 |
| 整个 vision_tower ignore | 物理隔离，每卡完整副本 | 简单直接 | 视觉塔参数量大，FP32 下每卡显存代价不可接受 |
| 精确筛选 + ignore | 物理隔离，只 ignore 流浪参数 | 显存/计算双优 | 需要正确的筛选逻辑 |

**方案一** 是 verl 的原始选择。冻结场景下强制开启 `use_orig_params=True`，跳过混合校验，实现简单，但治标不治本：`flat_param_requires_grad` 逻辑或聚合后为 True，冻结参数随可训练参数一同走 AllGather/ReduceScatter，反向时 backward kernel 连坐执行，通信与计算的冗余开销持续存在。

**方案二** 对于 Qwen3VL，视觉塔包含 27 个 VisionBlock + 4 个 Merger，actor 训练时参数以 FP32 存储，整体 ignore 后每卡需保留完整副本，显存代价不可接受。此外，冻结参数无梯度，每卡只需存储参数本身，没有梯度侧的额外开销——但参数量本身已足够大。

**方案三** 是最终选择。`VisionBlock` 与 `VisionPatchMerger`（含 `deepstack_merger_list` 中的 3 个）由 `wrap_policy` 正常处理，继续走 FSDP 分片；只将真正"流浪"的小参数（`patch_embed`、`pos_embed`）移出 FSDP 管辖，每卡保留完整副本但总量仅约 445 万参数（FP32 下约 17 MB），代价完全可接受。

💡 **一句话总结**：方案一能让代码跑起来，方案二代价过高，方案三是在分片收益与显存代价之间找到的精确平衡点。

## 3. 正确的 wrap_policy 配置

处理 `ignored_modules` 之前，先把 `wrap_policy` 配齐——Root Unit 参数堆积的根源之一正是 wrap_policy 不完整。

### 策略设计：类名匹配与规模阈值并行生效

多模态场景下需要两套策略协同，分别针对不同性质的模块：

`transformer_auto_wrap_policy`（类名匹配）适合有明确类型的结构性模块。`Qwen3VLVisionPatchMerger` 是典型例子——它是核心的跨模态投影单元，参数量虽未达 5 亿阈值，但必须独立成 Unit 以获得独立的通信生命周期。

`size_based_auto_wrap_policy`（规模阈值）适合无具名类型的巨型参数。`embed_tokens` 和 `lm_head` 本质上是普通的 `Embedding` 和 `Linear`，这两个类在模型中广泛复用，按类名匹配会误伤其他同类小模块，规模阈值（500M）才是正确的捕获方式。

```python
# verl fsdp_config.wrap_policy
{
    "transformer_layer_cls_to_wrap": [
        "Qwen3VLTextDecoderLayer",      # 语言解码层，36 个，每个 ~2.0 亿参数
        "Qwen3VLVisionBlock",            # 视觉特征层，27 个，每个 ~1570 万参数
        "Qwen3VLVisionPatchMerger",      # Patch 融合层（含 merger 和 deepstack_merger_list 共 4 个）
                                         # 默认不在 _no_split_modules，需显式指定
    ],
    "min_num_params": 500000000,         # 5 亿阈值，兜底 embed_tokens/lm_head
}
```

### 优化效果验证

配置生效后，通过 `param_infos` 日志可以直接验证拆分结果：

```python

ParamInfo(module=Linear(...),     module_name='linear_fc1')
ParamInfo(module=Linear(...),     module_name='linear_fc2')

# 优化后：lm_head 独立 Unit（500M 阈值触发）
ParamInfo(module=Linear(4096→151936), module_name='')

# 优化后：Root Unit 仅剩未被 wrap_policy 覆盖的小参数

ParamInfo(module=Embedding(...),  module_name='model.visual.pos_embed')
```

这里也给出怎么打印FSDP初始化后Root Unit的参数信息的方法：

```text
def print_fsdp_info(fsdp_model):
    """Print parameter distribution across FSDP Units for diagnosing wrap_policy configuration."""
    if torch.distributed.get_rank() != 0:
        return
    for name, module in fsdp_model.named_modules():
        if isinstance(module, FSDP):
            handle = module._handle
            if handle and not name: # 默认只打印root
                total = handle.flat_param.numel()
                print(f"[FSDP Unit] {'ROOT'}: {total / 1e6:.1f}M elements")
                print(handle.flat_param._param_infos)
```

### 关键 Bug 修复：if/elif 互斥导致策略静默失效

原始 verl 代码中两套策略以 `if/elif` 组织——一旦配置了 `min_num_params`，类名匹配策略就会静默失效，所有显式指定的 `transformer_layer_cls_to_wrap` 形同虚设，对应模块全部回落至 Root Unit：

```text
# ❌ 原始代码：开启 min_num_params 后，类名匹配策略静默失效
if min_num_params > 0:
    policies.append(size_policy)
elif transformer_layer_cls_names is not None:   # ← elif 导致互斥
    policies.append(transformer_policy)

# ✅ 修复：改为独立 if，两套策略并行生效
if transformer_layer_cls_names is not None:
    policies.append(transformer_policy)
if min_num_params > 0:                          # ← 独立 if，不再互斥
    policies.append(size_policy)
```

> ⚠️ **注意**：若不修复此逻辑而同时配置了 `min_num_params` 和 `transformer_layer_cls_to_wrap`，类名匹配策略会被完全跳过。`Qwen3VLVisionPatchMerger` 等显式指定的模块将全部回落至 Root Unit，问题一中分析的显存堆积问题依然存在。

### 小结

`wrap_policy` 配齐后，Root Unit 的参数堆积问题得到了大幅缓解，但有两点遗留问题需要清醒认识。

**第一，`lm_head` 独立成 Unit 引入了新的通信开销。** Root Unit 的豁免机制本质上是一种"免费午餐"——根节点的 `_full_param_padded` 横跨整个 forward-backward 窗口，不需要在前向结束后立即 reshard。**`lm_head` 从 Root Unit 拆出后，这个豁免随之失效：**前向结束后参数立即释放，反向开始时再重新 AllGather。对于 `lm_head` 这种 6.2 亿参数的巨型模块，这意味着额外引入了一次完整的 AllGather 通信，在反向传播的关键路径上增加了通信开销。这是用通信换显存的必要代价，需要在实际训练中结合吞吐量数据权衡。

**第二，两个根本性问题尚未解决。** 其一，Root Unit 中仍然混有视觉塔的小参数（`patch_embed`、`pos_embed`）和语言侧的 `language_model.norm`——前者在 `vision_tower.requires_grad_(False)` 后处于冻结状态，后者可训练，`requires_grad` 的混杂问题依然存在，`use_orig_params` 的校验报错或连坐开销并未消除。其二，视觉塔的流浪参数与语言侧参数共存于同一个 `FlatParameter`，根本矛盾没有变——`wrap_policy` 解决了"大模块堆积"，但没有解决"冻结参数混入"。这正是下一节引入 `ignored_modules` 的原因。

---

## 4. ignored_modules 的精确筛选

解决冻结参数混入 Root Unit 的问题，核心是把"流浪参数"从 FSDP 管辖中彻底移出。实现上分两步：先确定哪些模块需要 ignore，再手动补全 FSDP 跳过的初始化流程。

### 4.1 筛选策略

**手动指定**是最直接的方式：打印模型的 `param_infos` 日志，直接把需要 ignore 的模块路径写入配置。对 Qwen3VL，`wrap_policy` 配齐后 Root Unit 中剩余的流浪参数只有两个：

```text
model.visual.patch_embed.proj   # Conv3d，~180 万参数
model.visual.pos_embed          # Embedding，~265 万参数
```

这种方式要求开发者对模型结构有一定了解，且模块路径随模型变化需要手动维护，适合结构稳定、模块数量少的场景。

**我个人实现的时候使用的是一种自动筛选的逻辑，比较省事，但是不太灵活，这里仅供参考。**

**自动筛选**则通过 `auto_ignore_vision_tower: true` 开启，无需手动维护模块路径。筛选逻辑从 `transformer_layer_cls_to_wrap` 出发，把 `vision_tower` 内未被任何 `wrapped_cls` 覆盖、且自身直接持有参数的模块自动识别为流浪参数：

```yaml
fsdp_config:
  wrap_policy:
    auto_ignore_vision_tower: true
    transformer_layer_cls_to_wrap:
      - "Qwen3VLTextDecoderLayer"
      - "Qwen3VLVisionBlock"
      - "Qwen3VLVisionPatchMerger"
```

这里有一个关键陷阱：不能仅凭 `isinstance(module, tuple(wrapped_cls))` 做判断。`blocks` 和 `deepstack_merger_list` 都是 `ModuleList`，它们本身不是 `wrapped_cls` 实例，但内部装的全是应当分片的 `VisionBlock` 和 `VisionPatchMerger`。若不排除这些容器，它们整体会被加入 `ignored_modules`，内部所有参数全部不分片，显存代价退回方案二的水平。

正确做法是**预先收集所有 `wrapped_cls` 实例内部的模块 id，再全量遍历筛选**，用 `id()` 而非对象引用以规避 `__eq__` 被重写导致的误判。完整实现见 `get_vision_tower_ignored_modules`。

对 Qwen3VL，自动筛选结果与手动指定完全一致：

```text
[ignore] patch_embed.proj: Conv3d (1806336 params)
[ignore] pos_embed: Embedding (2654208 params)
[ignore] total ignored params: 4.5M
```

`blocks`、`merger`、`deepstack_merger_list` 中的各 `Qwen3VLVisionPatchMerger` 实例均被正确排除，走 FSDP wrap 路径。

### 4.2 初始化补全

FSDP 在校验、实化、同步三个阶段均跳过 `ignored_modules`（详见第 0 节流程图），因此必须在 FSDP 初始化之前手动补全三步。理解这三步的必要性，需要先看 verl 的初始化上下文：

```python
def init_fn(x: torch.nn.Module):
    if torch.distributed.get_rank() != 0:
        x = x.to_empty(device=get_device_id(), recurse=False)
        get_torch_device().empty_cache()
    return x

# rank 0：cpu_init_weights，以 CPU 实体加载
# 其他 rank：init_empty_weights，生成 Meta Tensor 占位
init_context = init_empty_weights if rank != 0 else cpu_init_weights
```

`init_fn` 在模型构造时对每个子模块调用，将其他 rank 的 Meta Tensor 原地替换为空 GPU Tensor。**`ignored_modules` 被 FSDP 跳过，`init_fn` 不会对其执行**——其他 rank 的流浪参数会一直停留在 Meta Tensor 状态，直到手动处理。

**第一步：设备迁移。** 对齐 `init_fn` 的行为，对每个 ignored 模块手动执行：

- rank 0：`m.to(device)`，将 CPU 实体搬到 GPU
- 其他 rank：`m.to_empty(device)`，将 Meta Tensor 替换为空 GPU Tensor，**每个模块迁移后立即调用 `empty_cache()`**——这一点与 `init_fn` 的逐模块清理行为对齐，避免多个大模块连续 `to_empty` 期间 Meta Tensor 碎片在显存中堆积

**第二步：barrier 同步。** 设备迁移完成后，所有 rank 在此处同步，确保广播开始时每个 rank 的参数槽位都已就绪。单机多卡环境下通常不会触发问题，多机场景下这一步是防止竞态的关键。

**第三步：广播。** 有两个容易踩坑的细节：

- `to_empty` 原地替换参数对象，迁移后之前持有的引用已失效，必须重新遍历 `m.parameters()` 和 `m.buffers()` 收集引用，而不能复用迁移前的列表
- 广播顺序必须在所有 rank 上完全一致，不能用 `set`（无序）组织待广播的 tensor 列表——顺序不一致会导致 rank 0 广播 tensor A 时其他 rank 等待 tensor B，造成死锁

### 4.3 调用逻辑

核心改动见 `verl/workers/fsdp_workers.py`，决策路径如下：

```text
freeze_vision_tower=true
    ├── auto_ignore_vision_tower=true
    │     ├── 筛选成功 → ignored_modules 传入 FSDP，use_orig_params 保持配置值
    │     └── 筛选为空 → 回退 use_orig_params=True
    └── auto_ignore_vision_tower=false（默认）
          └── 回退 use_orig_params=True（与旧行为一致）
```

`freeze_vision_tower: true` 时冻结视觉塔；若同时开启 `auto_ignore_vision_tower: true`，调用 `get_vision_tower_ignored_modules` 自动完成筛选与初始化补全，将结果传入 FSDP 的 `ignored_modules` 参数。筛选结果为空时自动回退到 `use_orig_params=True` 兜底，未开启时同样回退，与旧配置完全兼容。

开启ignore后，从调用栈中可以看到指定的模块如patch_embed走的是原生transformers的前向，并没有fsdp的wrap。

## 5. 总结

以下是 verl FullAsync 模式下，Qwen3VL 模型上优化方案与基线的实测对比：

| 指标 | 优化方案 | 基线 | 变化 |
| --- | --- | --- | --- |
| Actor 更新耗时 (s) | 185.30 | 206.23 | −11.3% |
| 最大已分配显存 (GB) | 21.99 | 25.01 | −3.0 GB (−13.7%) |
| 最大预留显存 (GB) | 29.72 | 35.26 | −5.5 GB (−18.6%) |

Qwen3VL 的视觉塔参数量相对较小，收益已较为可观。对于 ViT 结构更大、视觉侧流浪参数更多的模型（如 GLM 系列），实测下来`wrap_policy` 精确配置与 `ignored_modules` 物理隔离带来的收益会进一步放大。

💡 **一句话总结**：`wrap_policy` 解决"参数怎么分组"，`ignored_modules` 解决"哪些参数彻底不归 FSDP 管"，`use_orig_params=True` 是两者都未配好时的应急补丁——它能让代码跑起来，但冻结参数的通信与计算连坐代价依然存在。两者配合得当，Root Unit 的常驻显存开销才能真正降下来。
