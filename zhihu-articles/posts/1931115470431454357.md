你是不是在使用大语言模型时，有过这样的疑惑：

**“我已经把问题发过去了，它怎么还不说话？”**

**“刚开始回复就等好久，然后刷刷刷一大段……这是为什么？”**

**因为大模型脑子真的很大，它“说出”每个字，都要经过一个复杂又谨慎的过程。整个过程大致分为四个阶段：输入处理（将用户文本转为 token）、预填充（一次性理解上下文并生成首个输出 token 的分布）、解码（逐步生成每个输出 token）、以及输出后处理（将 token 还原为文本）。本文以通俗方式解释了这四个阶段，并引入了三个常见耗时指标（TTFT、TPOT、ITL），帮助用户更清晰理解模型“为什么慢”，以及如何合理优化使用场景。**

## **大语言模型4 大推理步骤：**

大语言模型（LLM）基础的推理（inference）过程可分为四大阶段： **输入处理** 、 **预填充（Prefill）** 、 **解码（Decode）和输出后处理（Post-processing）** 。

![](https://pic3.zhimg.com/v2-bcf2fa1df334bdafc158811c87325d18_r.jpg)
*图：模型推理的 4 大阶段*

### **1. 输入阶段（Input Encoding/Tokenization)**

![](https://picx.zhimg.com/v2-3a46cf7c9f8c90eddb37010f6e0acd9f_r.jpg)
*图：输入阶段*

将用户输入的原始文本（人类使用的自然语言文字）转化为模型可用格式

- 用户输入一段文本（ 自然语言文字组成的prompt）
- 系统将这段文字 分解为Token ( 子词、字符、或 Byte 片段），这个过程与“ **分词** ”非常相似。
- 利用模型的“词表vocabulary”文件，每个 Token 可以直接映射到1 个整数 ID。一串 Token 就变成了模型可以处理的 整数 ID 序列。

如：

用户输入：

> 我想学习关于大语言模型的知识

Token分解后 的内容

> "我"，“想”，“学习”，“关于”，“大语言模型”，“的”，“知识”

在词表中对应的 整数 ID

> [40, 1390, 311, 4048, 922, 445, 11237]

### **2. 预填充阶段(Prefill)**

![](https://picx.zhimg.com/v2-1f7559336914f7a3e93decdcbcac9239_r.jpg)
*图：预填充阶段*

对整段输入做一次完整前向计算，生成首个输出 token。

- 开始处理输入的 Token 序列，一次性将所有输入 Token 送进模型处理
- 每个 Token 的整数ID 都会被映射为一个向量，所有向量 一次性交给模型处理
- 输出的是最后一层的 每个位置的 **预测分布**

> 这个阶段 一次性处理完所有输入 token，并输出 下一个 token 的概率分布。 
>  
>  预测分布：计算出词表中 所有 Token 可能成为下一 输出Token的概率值，所有概率值相加等于 1。

### **3 解码阶段（Decoding Loop)**

![](https://pic1.zhimg.com/v2-9bc6e728e8c919260650e97940786778_r.jpg)
*图：解码阶段*

此时正式开始 输出大模型给我们的答案。

这个过程是 **一个 token 一个 token 地生成输出**

每轮 Token 的解码都包含一下过程：

- 选取下一个Token

- 拼接到已有 序列

- 再做一轮推理

> 这个过程反复执行，直到： 
> 

- 达到 max token 限制
- 生成特殊的 <eos> 结束符号

kv cache用于一次推理请求内部加速：大模型每次计算一个新Token 时，内部矩阵乘法运的中间结果，会有部分和输前面token计算的结果一致。 而kvcache就是缓存了这部分矩阵运算结果，减少了“矩阵乘法”的运算量

### **4. 输出阶段（Post-processing）**

![](https://pic2.zhimg.com/v2-00c68e1fbe806d23683ef093d7122201_r.jpg)
*图：输出阶段示*

- 将模型输出的 token ID 序列转换为文字（Detokenization）
- 返回给用户或 API 调用方

> 在 第3 步的解码阶段时，每生成一个新 Token就可以进行一次 “输出阶段”，将 Token 转为文字，以便实现“流式输出(stream)”的效果，让用户实时直观感受模型的推理进展。

## **大模型推理几个耗时指标**

![](https://pic1.zhimg.com/v2-1ca3c813dba7488612a0ffff513a1de4_r.jpg)
*图：耗时指标在 4 个步骤 中的位置*

### **1. 什么是 TTFT（Time To First Token）？**

![](https://picx.zhimg.com/v2-8865b21bdeeea95977ab24282f1eee59_r.jpg)

**TTFT = 大模型开始说话前的思考时间**

想象一下你去问一位博学的老师一个复杂问题，比如：

**“请帮我写一个 Python 程序，实现快速排序算法，并分析时间复杂度。”**

这位老师会在开口前，先思考一下：

- 你在问什么？
- 需要回答到什么程度？
- 要怎么组织语言？

同样， **大模型在你发出请求后，也需要** ：

- 解析输入 Prompt；
- 加载或准备模型上下文（特别是你传了很多对话历史时）；
- 在 GPU 上运行 **前向计算** ，推理出第一个“合适的词”。

这段“准备工作”就是 **TTFT** ，一般是推理过程里 **耗时最多** 的一步，尤其当输入内容多、模型参数大时。

---

### **2. 什么是 TPOT（Time Per Output Token）？**

![](https://pic1.zhimg.com/v2-5d63488faa03a9ee8970999158ca5a02_r.jpg)

**TPOT = 模型每“说”一个字/词的时间。**

大模型并不是“一口气说完所有话”的，它是 **一个词一个词慢慢“编”出来的** ，每一个词（token）的生成过程如下：

1. 看看目前上下文说了什么；
2. 预测下一个最可能出现的词；
3. 选出得分最高的词输出；
4. 把这个词加入上下文，继续预测下一个……

这就像你在和一个即兴诗人聊天，他每说一句话都要“即兴创作”，不能预先写好台词！

所以：

- **TPOT 越低，响应越流畅。**
- 但 **模型越大，TPOT 越高** ；
- GPU 负载越高、token越复杂，TPOT 也会变慢。

---

### **3. 什么是 ITL（Inference Time Latency）？**

![](https://pic3.zhimg.com/v2-5e7bde54b44ab98ad5835147a4d2c92a_r.jpg)

**ITL = 从你提问到回答完整输出的总耗时。**

它 = TTFT + n × TPOT

（其中 n 是输出的 token 数）

打个比方，如果：

- TTFT = 2秒（模型思考时间）
- TPOT = 100ms（每个词说话时间）
- 模型输出了 30 个 token

那么 ITL 就是：

```text
ITL = 2 + 0.1×30 = 5 秒
```

---

## **为什么“推理型”模型更慢？**

用户在选择了推理模型后，常常反馈“ **工作流执行时间太长，拿不到输出结果** ”。

除了前面提到的 Prompt 长、输出多、模型大等原因，还有一个很多用户 **容易忽略** 但 **非常关键** 的原因：

**你用的模型，不只是回答问题，而是先思考，再回答。**

---

**举个例子：你想问一个复杂的逻辑题**

比如你输入的问题是：

**“张三比李四高，王五比张三矮，谁最高？”**

普通语言模型可能会直接尝试基于表层信息回答，但 **推理模型（Reasoning Model）** ，比如内置了 Chain-of-Thought、ReAct、Tool-Use、函数执行等机制的大模型，会这样做：

### **它背后实际流程是这样的：**

**Step 1：分析问题结构**

**Step 2：展开推理链条**

**Step 3：将这些“隐性步骤”组织起来**

**Step 4：最终输出一句话**

---

### **所以这段时间发生了什么？**

这时候你看到的体验是：

**“怎么我问题一发出去，模型半天没反应？”**

**“一开始还以为卡住了。”**

其实模型并没“卡”，而是在“ **默默写草稿** ”，一边思考，一边计算，在脑海中列清楚逻辑链条，再把最后一句输出给你。

---

### **推理模型让 TTFT 更高**

- 比起直接生成答案，推理型模型 **在输出第一个 token 前要做更多计算** ；
- 这会让 **TTFT（Time To First Token）** 变得明显更长；
- 即使 **TPOT（Time Per Output Token）** 不高，总耗时 ITL 也会上升。

---

### **用户可以怎么优化？**

1. **给出足够的上下文线索** ，让模型少“猜”一点；
2. **明确要求输出 reasoning chain** （如：“请逐步解释你的推理过程”），避免模型内部“默默推理”后再输出；
3. **缓存 reasoning-heavy 的查询结果** ，避免重复计算；
4. **尽量将复杂逻辑下沉为代码执行** （如 tool-use agent），让模型少走逻辑弯路。

---

## **怎么让模型“快一点”？**

### **场景优化建议：**

**1. Prompt 越短越好**

**2. 控制输出长度**

**3. 批量请求而非频繁请求**

**4. 避开高峰时间使用**

**5. 考虑使用“小模型 + 缓存”策略**
