过去一年，AI Agent 和工具调用的生态推进得很快，但如果你主要写 C++，大概率会有一种割裂感。

上层应用在讲 Agent、MCP、工具编排、上下文管理；底层系统里真正有大量能力的地方，却仍然是 C++：数据库、仿真、音视频、图形、工业软件、设备控制、交易系统、嵌入式服务、本地高性能计算。

很多时候，最有价值的工具能力并不在一个 Python 脚本里，而在一个已经运行多年、接口复杂、性能敏感、状态很重的 C++ 系统里。 

问题是，把这些能力接到大模型生态里，并不只是“包一层 HTTP 接口”这么简单。 

MCP，也就是 Model Context Protocol，解决的是模型和外部上下文、工具、资源之间的标准化连接问题。它的意义不在于又发明了一个 RPC 协议，而在于给 Agent 生态提供了一条相对统一的边界：模型侧可以用一致的方式发现工具、调用工具、读取资源；工具侧也不用为每个客户端、每个应用重新设计一遍协议。

对应用层来说，MCP 是“让模型能用工具”的协议。

对工程侧来说，MCP 更像是一条边界：模型世界和本地系统之间，需要一个稳定、可组合、可维护的连接层。

这也是我做 cxxmcp 的原因。

项目地址：

[https://github.com/caomengxuan666/cxxmcp](https://github.com/caomengxuan666/cxxmcp) 

cxxmcp 是一个 C++ MCP SDK，用来在 C++ 项目里构建 Model Context Protocol 的 client 和 server。

先说清楚：它现在是社区项目，不是官方 MCP SDK。目标也不是做一个“看起来很酷的 demo”，而是尽量把 C++ 接入 MCP 这件事做成正常工程能接受的形态。

### 为什么不是“直接写个 HTTP 接口”？

如果只是让模型调用一个函数，当然可以直接写 HTTP。

但 MCP 解决的不是“怎么发一个请求”这么窄的问题。它关心的是工具发现、工具调用、资源访问、prompt、completion、sampling、elicitation、task、progress、cancellation，以及 client/server 在协议边界上的交互方式。

换句话说，它不是一个“接口格式”，而是一套模型和外部系统之间的连接边界。

对脚本语言来说，早期先快跑很正常。Python / TypeScript 生态里，MCP 的落地速度也确实更快。

但 C++ 这边的问题不一样。

C++ 项目更关心这些东西：

- 怎么嵌进已有工程
- CMake target 怎么导出
- 依赖怎么走包管理器
- 协议层和业务层怎么分开
- transport 能不能换
- client/server 生命周期怎么控制
- 能不能只用 SDK 层，不被 runtime 或 CLI 绑架
- 能不能在 CI 里稳定复现构建

如果这些问题没处理好，最后就会变成：demo 很好看，项目不敢用。

cxxmcp 想解决的就是这个问题。

### cxxmcp 的结构

目前核心 SDK 表面主要是这些层：

- protocol
- transport
- handler
- peer
- service
- client
- server
- 这些名字不花哨，但我觉得对 C++ 来说是必要的。

protocol 处理 MCP 协议模型和 JSON-RPC 序列化，同时保留 raw JSON-RPC escape hatch。

transport 处理 stdio、process stdio、Streamable HTTP，以及 legacy SSE 兼容路径。

client / server 是可嵌入的 SDK 层。

peer / service 更偏应用侧组织方式，用来把角色、生命周期和 handler 边界收束起来。

也就是说，你不是只能拿一个黑盒 server 跑起来。你可以按自己的工程复杂度选择切入层级。

如果只是快速暴露一个 MCP server，用 server / service 就够。

如果你要接已有进程、已有 IO 模型，可能会更关心 transport。

如果你在做更底层的兼容或扩展，可以直接碰 protocol。

### 一个最小 server 大概长这样

比如写一个最简单的 echo tool：

```text
#include <iostream>
#include <memory>
#include <utility>

#include <cxxmcp/peer.hpp>
#include <cxxmcp/server.hpp>
#include <cxxmcp/service.hpp>
#include <cxxmcp/transport/stdio_transport.hpp>

int main() {
    mcp::server::ServerBuilder builder;

    builder.name(「demo-server」)
        .version(「1.0.0」)
        .add_tool(
            mcp::protocol::ToolDefinition{
                .name = 「echo」,
                .description = 「Echo the incoming payload」,
                .input_schema = mcp::protocol::Json{{「type」, 「object」}},
            },
            [](const mcp::server::ToolContext& context) {
                mcp::protocol::ToolResult result;
                result.structured_content = context.arguments;
                return result;
            });

    auto server = builder.build();
    if (!server) {
        return 1;
    }

    mcp::ServerPeer peer(std::move(*server));
    peer.add_transport(
        std::make_unique<mcp::transport::ServerStdioTransport>(
            std::cin, std::cout));

    auto running = mcp::serve(std::move(peer));
    if (!running) {
        return 1;
    }

    return running->wait().has_value() ? 0 : 1;
}
```

这里有几个点是我比较在意的。

第一，tool 是 typed 的，不是到处裸写 JSON 字符串。

第二，server 的构造、peer 的运行、transport 的绑定是分开的。stdio 只是一个 transport，不是整个 SDK 的中心。

第三，业务代码不会被迫塞进某个全局 runtime 里。你可以把它嵌进已有程序，也可以自己管理生命周期。

### client 侧也不是只能“请求一下”

client 侧可以直接连 Streamable HTTP transport：

```text
#include <memory>
#include <utility>

#include <cxxmcp/peer.hpp>
#include <cxxmcp/service.hpp>
#include <cxxmcp/transport/http_transport.hpp>

int main() {
    auto transport =
        std::make_unique<mcp::transport::StreamableHttpClientTransport>(
            mcp::transport::StreamableHttpClientTransportOptions{
                .endpoint = 「HTTP://127.0.0.1:8000/mcp」,
            });

    mcp::ClientPeer peer(std::move(transport));

    auto running = mcp::serve(std::move(peer));
    if (!running) {
        return 1;
    }

    running->peer().initialize();
    running->peer().list_all_tools();
    running->peer().call_tool(
        「echo」,
        mcp::protocol::Json{{「value」, 「hello」}});

    return 0;
}
```

这个例子不复杂，但能说明 cxxmcp 的定位：它不是只做 server，也不是只包协议对象，而是希望把 C++ 作为 MCP client / server 都需要的那层 SDK 补出来。

### 为什么现在要做包管理器？

C++ 库如果不能被包管理器装，其实会劝退很多人。

尤其是这种 SDK，如果每个使用者都要手动拉源码、调 CMake、处理依赖，那项目越大越不会愿意试。

所以我最近也在推进两个主流包管理器：

vcpkg PR： [https://github.com/microsoft/vcpkg/pull/51972](https://github.com/microsoft/vcpkg/pull/51972)

Conan Center Index PR： [https://github.com/conan-io/conan-center-index/pull/30267](https://github.com/conan-io/conan-center-index/pull/30267)

这两个 PR 还在走流程，但方向很明确：让 cxxmcp 变成一个能被正常 C++ 工程消费的包，而不是只能从 README 里复制构建命令。

核心 SDK 是 C++17；runtime、gateway、CLI、examples 这些更上层的东西可以单独开关，不强塞进 SDK 叙事里。

### 我不想把它吹成“已经事实标准” 

现在还没到那个阶段。 

MCP 本身还在演进，C++ 侧的最佳实践也还没完全固定。cxxmcp 也还有很多工程细节要继续补，比如更多真实场景的接入反馈、跨平台构建覆盖、包管理器 CI、和其他 SDK 的互操作证据。 

但我觉得有一件事已经比较确定：

C++ 不应该在 Agent 生态里只扮演“被调用的二进制”。

很多本地能力、系统能力、高性能能力，本来就在 C++ 里。与其让每个项目临时写一层脆弱的胶水，不如把 MCP 的协议、transport、client/server、handler/service 这些边界整理成一个 C++ SDK。 

这就是 cxxmcp 现在在做的事。 

如果你在做 C++ 工具、桌面软件、本地服务、设备控制、仿真平台、游戏引擎、数据库或其他系统组件，并且想把这些能力接到 Claude、Cursor、Agent 框架或内部大模型平台里，可以看看这个项目。 

项目还早，但方向我觉得值得做。

C++ 在 AI Agent 生态里，应该有自己的 SDK、自己的抽象和自己的工程入口。
