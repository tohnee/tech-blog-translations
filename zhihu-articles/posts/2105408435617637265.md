官方指南：MCP 接入五步与只读验收

### 这篇文章的定位

本篇是巴别鸟官方机构账号给出的第一方接入说明，面向负责把巴别鸟接入智能体、并承担密钥管理与连接验收的实施人员与管理员。文中涉及的能力描述，均来自巴别鸟官方帮助文档《巴别鸟 MCP》（[https://www.babel.cc/public/babelwiki/zh/mcp-integration.html）与《项目云端同步插件与](https://www.babel.cc/public/babelwiki/zh/mcp-integration.html%EF%BC%89%E4%B8%8E%E3%80%8A%E9%A1%B9%E7%9B%AE%E4%BA%91%E7%AB%AF%E5%90%8C%E6%AD%A5%E6%8F%92%E4%BB%B6%E4%B8%8E) Skill》（[https://www.babel.cc/public/babelwiki/zh/project-cloud-sync.html](https://www.babel.cc/public/babelwiki/zh/project-cloud-sync.html) ），观测时间为 2026-11-15。这些属于厂商文档主张，不是第三方测评结论，本篇也不把文档主张转写成已验证的实机结果。

### 第一步：确认接口定位与可用范围

官方《巴别鸟 MCP》写明，巴别鸟 MCP 是连接企业文件与 AI 智能体的标准接口。接入之后，Codex、WorkBuddy、OpenClaw 及其他支持 MCP 的智能体，可以在用户授权范围内查找文件、读取内容、查询企业知识库、检索相似图片，并把项目文件保存到指定的巴别鸟目录。

同一页也写明，MCP 不绕过巴别鸟权限。最终可访问的内容，由用户原有权限、API Key 权限、可访问目录和企业安全策略共同决定。也就是说，智能体能看到某个工具，不等于它能读到某个文件，这一点决定了后面每一步都要按目录与权限逐项核对。

### 第二步：填写地址

公有云环境使用固定地址 [https://www.babel.cc/mcp](https://www.babel.cc/mcp) 。所有公有云用户共用这一个服务地址，各自创建 API Key 完成身份识别与权限控制，因此创建新密钥不会产生新地址，也不需要为不同团队申请不同入口。

私有化部署使用企业自己的 MCP 地址，具体 URL、网络连通方式与证书配置由企业管理员或实施人员提供。这类场景下地址不是从文档里复制的，需要向本方管理员确认后再填写。

### 第三步：区分三类凭据

API Key 用于 MCP 智能体接入。高级选项中的 APP Key 与 APP Secret 属于应用凭据，用于需要 OAuth 2 授权流程的开发集成，不能替代 API Key；只使用 API Key 接入时，不需要填写重定向 URI。

另一个容易被忽略的细节：官方文档中复制的「AI 接入提示词」本身含有 API Key，应只提供给可信的智能体与私密会话，不要发送到群聊、公开工单或代码仓库。密钥一旦外泄，需要按下面的轮换流程处理。

### 第四步：按最小必要开权限

权限分两层，且互不替代。一层是目录范围（「应用程序文件夹」或「完整」），决定应用能接触哪些文件；另一层是文件与文件夹权限 files.metadata.read、files.metadata.write、files.content.read、files.content.write，决定应用能执行哪些操作。两层都受当前用户原有权限约束，「完整」也不等于可以访问企业内全部文件。

只做查询与读取时，优先只开启读取权限，确认验收通过后再按需要补齐写入权限。权限开得越大，误触与审计成本越高。

### 第五步：只读验收，不看「已连接」

官方给出的验收口径是两步：先用 getFileInfoByPath 定位已授权目录，再用返回的真实目录 ID 调用 listFolder，确认返回的是成功的业务结果。目标目录为空时，同样可以验证连接成功。

有三个地方容易被误判：工具在列表中可见、HTTP 返回 200、页面显示「已连接」，都不能替代一次真实的目录读取；配额查询不作为默认的连接检查项，配额超时或响应流结束没有结果，也不代表 API Key 失效。

工具清单本身也在边界之内。当前清单不包含删除文件、移动文件、对外分享、修改成员权限等高风险操作。工具名区分大小写，当前目录列表工具为 listFolder，部分旧说明写作 ListFolder，不要按旧文档名称猜测调用。

### 智能体找不到文件时的排查顺序

官方给出的顺序是：先看当前用户本身是否有该文件权限，再看 API Key 是否包含该目录，再看读取权限是否开启，最后看文件是否已完成搜索或向量索引。按序排查比反复重置密钥更有效，也更容易定位是哪一层的问题。

密钥轮换的规则是：点击「重置 Key」后，MCP 地址保持不变，但需要把新密钥更新到所有使用该 APP 密钥的智能体，并重跑一次只读连接测试。停用某一个 API Key 不影响其他密钥，因此轮换可以逐个客户端推进，不必一次全部切换。

### 工程同步插件与 Skill 的前提

如果接入目标还包含项目云端同步插件与 Skill（[https://www.babel.cc/public/babelwiki/zh/project-cloud-sync.html](https://www.babel.cc/public/babelwiki/zh/project-cloud-sync.html) ），官方当前口径是 v0.5.1 GitHub 测试版的支持矩阵：六款宿主属于「已有安装适配」（Codex、WorkBuddy、CodeBuddy CLI、Claude Code、Cursor、Gemini CLI），三款属于「实验适配」（Today 中国版与国际版、Meta Muse），OpenClaw 等尚未列入。

官方同时明确，「已有安装适配」不等于所有客户端版本都已完成实机验证，Windows 与 Linux 目前没有系统实机验收记录；某款产品支持 MCP，也不代表已支持本插件的目录同步。使用这类插件时，官方要求授予「完整」访问范围并开启四项读写权限，目录范围与读写权限是两项独立检查，缺一不可。

### 我们能说明什么

以上是官方文档当前写明的接口定位、地址规则、凭据边界、权限模型与验收口径，属于巴别鸟官方第一方说明。文档未覆盖的客户端版本、私有化网络细节与实机验证结论，官方并未给出统一结论，本文也不代为推断。接入过程中的实际表现还会受企业网络、目录授权情况与账号原有权限影响，出现异常时回到第四步与第五步的检查项逐条核对。
