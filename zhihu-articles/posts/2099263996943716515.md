**引言**

我们有一类 agent 业务，**平均每个请求输入约 17 万 token**，输出较短。在 H20 上跑这类流量，瓶颈首先是 prefill：**H20 的算力约为 H100 的七分之一，但 NVLink 仍是 900 GB/s**，适合把一条长请求拆到多张卡上算。

这个分支基于 SGLang 社区 main（2026 年 10 月 27 日的 `5884e4fec6`，下同），主要做了三件事：**长输入的 prefill 分摊到 8 张卡**；**decode 时去掉各卡的重复计算**；**优化都放在一个开关后面**，关闭即为上游实现（修上游 bug 的提交除外），方便社区逐项合入。

**结果**

- **单机（8×H20-3e）**：长输入首字比社区 main **快 4–10 倍**，解码吞吐是它的 **1.9–2.3 倍**。
- **冷启动（8×H20，全新容器）**：到可以接请求的时间从 **31 分钟缩短到 5.3 分钟**。
- **每卡每小时谷价收入**：用内部业务数据采样搭的 34 卡最小复现 demo（2E3P1D，固定 3:1 配比），每用户吐字约 50 和 100 token/s 两档分别是 **¥26.8** 和 **¥14.4**（100 TPS 档 P 只用到一半）；按内部系统水位，每用户吐字 100 token/s 时约 **¥24.5**。

- **代码**：[github.com/antgroup/sglang](https://github.com/antgroup/sglang/tree/dsv41-flash-h20)，分支 `dsv41-flash-h20`（head `6e6d5d9e13`）。

### 冷启动：31 分钟到 5.3 分钟

冷启动不影响稳态性能，但每起一个新实例都要等一次。两边都从全新容器启动：JIT 缓存是空的，checkpoint 也不在页缓存里。8×H20（96 GB）上，社区 main 到 READY 用了 1850 s，READY 后第一个 128K 请求的首字是 364 s；本分支分别是 316 s 和 1.8 s。

![](https://pic3.zhimg.com/v2-787933f13508d1482177d42f415a9520_r.jpg)

图 2｜冷启动对比（8×H20，TP8 + prefill CP8 + DSpark，全新容器，checkpoint 不在页缓存）。

社区 main 的时间主要花在两处：

- 捕获 CUDA graph 用了 1395 s，绝大部分花在 DeepGEMM 对每种 GEMM 形状把 M 从 1 到 32768 全部预编译一遍上。READY 后第一个 128K 请求又遇到两种只在长 prefill 里出现的形状，各再编译一轮，所以首字要等 6 分钟。
- 加载权重用了 340 s，其中约 200 s 是加载阶段的 mHC 预热编译。

本分支默认关闭全 M 预编译，改为抽样预热；随代码发布一份 JIT 清单，加载权重的同时用 32 个进程并行编译清单里的 kernel；页缓存保留不丢。加载权重 133 s，捕获 CUDA graph 86 s。READY 之后 JIT 缓存目录里没有新增文件，第一个 128K 请求的首字和稳态（1.74 s）基本一样。

说明：

- 社区提供了 `python3 -m sglang.compile_deep_gemm`，可以事先把 DeepGEMM 编译好，这样冷启动会短很多。这里比的是不做任何准备、直接拉起的情况。

### 最小复现 demo：34 张 H20 的 2E3P1D

这个 demo 是最小复现：验证 V4.1 的 PD / EPD 链路，并测出 P、D 的单卡能力，不代表实际业务的部署方式和负载。流量是从内部业务数据中采样构造的多轮会话，约 47 分钟，平均输入约 168K token，按原始顺序回放，只把到达率调到目标值。社区 main 目前不支持 V4.1 的 EPD，这组没有对照。

部署为 2E3P1D（P 3 台共 24 卡、D 1 台 8 卡、E 2 卡），测了两档：50 TPS 档每用户吐字约 50 token/s；100 TPS 档把到达率减半，吐字接近 100 token/s，首字也快得多。

| 阶段 | 指标 | 50 TPS | 100 TPS |
| --- | --- | --- | --- |
| prefill | 每卡吞吐（不含缓存命中） | 6.8K token/s | 3.6K token/s |
|  | 每卡吞吐（含缓存命中） | 94K token/s | 51K token/s |
|  | 平均输入缓存命中率 | 92.8% | 93.0% |
|  | 首字时延（TTFT）平均 | 6.2 s | 1.3 s |
|  | 首字时延（TTFT）p99 | 15.5 s | 9.0 s |
|  | 平均输入长度 | 168K token | 168K token |
| decode | 每卡吞吐 | 1.5K token/s | 829 token/s |
|  | 吐字速度（每用户 p50） | 51 token/s | 95 token/s |
| 整体 | 系统并发（平均在途请求） | 约 290 | 约 75 |
|  | 其中正在解码 | 约 200 | 约 65 |
|  | 实际吞吐 | 13.4 req/s | 7.3 req/s |
|  | 请求成功 | 4000 / 4000 | 4000 / 4000 |
|  | 谷价收入（每卡每小时） | ¥26.8 | ¥14.4 |

说明：

- 前缀缓存：内部部署的 P 接的是蚂蚁内部的 KV cache 系统，开源版本没法集成，这里用 SGLang HiCache 的 L2（主机内存，每个 rank 100 GB）代替，启动参数见文末“复现”。表中约 93% 的缓存命中率就是在这个配置下测得的。
- D 开启了唯一的有损选项 `fp8_lm_head_target`。
- 系统并发：发送期间每 0.5 秒统计一次已发出、未结束的请求数，取平均；“正在解码”指已收到首字、仍在输出的请求。50 TPS 档同时解码的请求最多到 256，即 D 的上限（`--max-running-requests 256`）。
- 每卡吞吐 = 发送期间每秒完成的请求数 × 请求的平均输入（或输出）长度 ÷ 卡数。含缓存命中的吞吐 = 不含命中的吞吐 ÷（1 − 命中率），命中部分不需要重算，所以两者差十几倍。
- 收入按 DeepSeek 官方谷价计算（每百万 token：缓存命中输入 ¥0.02、未命中输入 ¥1、输出 ¥4），分摊到含 E 在内的 34 张卡。
- 回放中 DSpark 平均每步接受约 3.6 个 token。

![](https://pica.zhimg.com/v2-b44b1ec243b1f855a67d070cd7dad632_r.jpg)

图 3｜demo 两档负载的关键指标。

100 TPS 档里，要让每用户吐字保持在约 100 token/s，D 每卡只能输出约 829 token/s，P 只用了一半左右（每卡 3.6K，50 TPS 档是 6.8K），所以每卡收入只有 ¥14.4。这是固定的 3:1 配比造成的；内部系统里 P、D 按负载分别扩缩，没有这个限制。

### 内部系统水位与 DeepSeek 线上对比

内部系统里 P、D 按负载分别扩缩。按内部系统水位，每用户吐字 100 token/s 时，每张卡上 prefill 处理未命中输入约 7.4K token/s，decode 输出约 930 token/s，按 DeepSeek 谷价折算，每卡每小时收入约 ¥24.5。

DeepSeek 发布 DeepInfer 时公开过线上统计：decode 用 64–128 张卡做 Wide-EP，KV 缓存放在约 100 PiB 的 3FS 上，平均输入 77K token，缓存命中率 96%。卡型没有公开，我们推测是 GB200；按单卡 FP8 稠密算力，H20 约是 GB200 的 1/17。

**需要注意的是，这个比较对 DeepSeek 并不公平。** DeepSeek 每用户吐字 230 token/s，我们只有 100。吐字速度和每卡吞吐此消彼长：demo 里吐字从 51 提到 95，D 每卡吞吐就从 1.5K 降到 829，DeepSeek 的吞吐是在快得多的吐字速度下取得的。他们的 decode 用 64–128 张卡做 Wide-EP，KV 缓存命中率也更高。在 H20 上，吐字速度我们确实追不上 DeepSeek，这个对比只看量级。

我们的结论是：长输入、以 prefill 为主的业务，在该模型上，H20 仍然可用；50–100 token/s 的吐字速度用户也能接受，[Artificial Analysis](https://artificialanalysis.ai/) 上 Anthropic 官方 API 的 [Claude Sonnet 5](https://artificialanalysis.ai/models/claude-sonnet-5-high/providers) 约 71 token/s，[Sonnet 5.5](https://artificialanalysis.ai/models/claude-sonnet-5-5-high) 约 118 token/s（2026 年 10 月查询）。

GB200 的 FP8 稠密算力按 NVL72 整柜 720 PFLOPS（含稀疏）÷ 72 ÷ 2 估算，约 5 PFLOPS；H20 是 296 TFLOPS。DeepSeek 的 38 美元也是谷价，按官方价目表的人民币、美元报价之比（约 6.67）换算。

### 怎么测的

单机数字在 8×H20-3e（141 GB）上测得；冷启动、PD 和 EPD 用的是 8×H20（96 GB）节点。

TTFT 是冷 prefill：不命中前缀缓存，输出 32 个 token，预热 1 次后测 3 次取中位数。解码吞吐用固定的 4K 输入、1K 输出。两边在同一台机器上用同一个客户端测，社区 main 测 1 轮，本分支测 2 轮取平均。

社区 main 开了相同的 TP8、prefill CP8 和 DSpark，但没开 `--enable-decoder-swa-bounded-replay`：这几项同时开启，第一个请求就会崩溃（第 2 个提交修复了这个问题）。社区 main 另有 14 个默认关闭的 DSpark / CUDA graph 开关，全部打开后解码吞吐提高 4–7%；此时本分支在单会话、32 并发、64 并发下仍分别是它的 1.79、2.11、2.21 倍。

冷启动：两边都从新建的容器启动，JIT 缓存为空；启动前用 `posix_fadvise(DONTNEED)` 把 checkpoint 移出页缓存，并用 `mincore` 确认驻留为 0。计时从执行启动命令到 `/health` 返回 200。

### 一个开关，关掉就是上游

分支只新增了三个环境变量：

| 变量 | 作用 |
| --- | --- |
| SGLANG_OPT_DSV41_SM90=1 | 对 SM90 上的 deepseek_v41 模型启用全部优化；其他模型和架构不受影响 |
| SGLANG_OPT_DSV41_SM90_DISABLE=<子系统,...> | 按名称关掉部分子系统 |
| SGLANG_OPT_DSV41_SM90_LOSSY=fp8_lm_head_target | 唯一的有损选项，需要显式打开 |

开关下分 14 个子系统：`mhc`、`moe`、`fp8_gemm`、`attn_proj`、`lm_head`、`startup`、`indexer`、`cp`、`prefill_graph`、`decode`、`mix_decode`、`runtime`、`pd`、`epd`。开关在进程启动时解析一次，各模块构造时记下结果，运行中不再判断；子系统名写错会在启动时报错。

开关关闭时执行的是上游代码。例外是修上游 bug 的改动：第 2 个提交整体不受开关控制，可以单独打到基线上；其他提交中不受开关控制的修复和注册，在提交说明里单独列出。

数值上，大部分改动与被替换的 kernel 逐比特一致。不一致的有以下几处，提交说明里也逐条列出：

- 按模型参考实现，在 wo_a 之前对 attention 输出做 per-32 FP8 舍入；
- 部分小行数 GEMM 用 split-K，FP32 的求和顺序变了；
- mHC 改用 tf32x3；
- CP 下 MoE 的归约改成 FP32 求和、只舍入一次；
- decode 的 head 交换改变了 FlashMLA 的切分；
- prefill indexer 改用 FP8 打分，分数和 torch 路径在容差内一致；
- FlashMLA 的调度选了非默认切分时，输出和原版相差不超过 2 个 bf16 ulp；
- DSpark 的 draft 改用 FP8 LM head。

这些路径都是确定性的，相同输入的输出不变。

### Prefill：把一条长请求摊到 8 张卡上

### CP 通信

prefill CP8 按 interleave 把一条请求的 token 分到 8 张卡上。上游实现能跑，但多余开销不少：每层的行搬运都走 NCCL；压缩器先汇聚完整的 hidden 行，再在每张卡上投影全部行；MoE 输出先 all-reduce 再切片。CP 下每层还有约 4 ms 与行数无关的 host 开销，短输入的瓶颈反而在 host。

这些通信都改走 NVLink 对称内存。SWA KV 和压缩器的汇聚在 q_b 之前由 copy engine 发出，与计算重叠。压缩器只投影本卡的行，再汇聚投影结果：尾部压缩器从 16384 行 GEMM 加一次全量汇聚，变为 2048 行 GEMM 加一次输出汇聚。每卡 2048 行起，MoE 输入也由 copy engine 拉取，路由专家的加权和直接写进各 rank 的对称缓冲区，再按 rank 顺序做 FP32 求和，省掉 NCCL all-reduce 和切片。输入 embedding 和 Engram 查表同样由分片属主直接写给目标 rank。

### 稀疏 prefill 与晚层跳过

上游在 CP 下把 query 行送进分页的 decode kernel，我们改回 `flash_mla_sparse_fwd`。8×H20 上一个冷 128K 请求的 attention 时间从 222.8 ms 降到 199.1 ms。

晚层跳过建立在社区的 bounded replay（[#38798](https://github.com/sgl-project/sglang/pull/38798)）之上。V4.1 的第 21–39 层复用第 20 层的 KV，但每层还有自己的 128 token 滑动窗口。开启 bounded replay 后，第 20 层及之后的层只为每块 prefill 的最后一个窗口计算，滑动窗口在这个窗口的起点被截断，所以它是一项近似：社区文档写明它与完整 prefill 数值上不等价，并建议 logprob 要与训练端一致的 RL 场景关掉它（[V4.1 cookbook](https://github.com/sgl-project/sglang/blob/5884e4fec6c0f4453940605896154f5fba4badd9/docs/cookbook/autoregressive/DeepSeek/DeepSeek-V4_1.mdx)）。社区在 [#44403](https://github.com/sgl-project/sglang/pull/44403) 中把它设为不开 CP 时的默认，PR 里开、关两组的评测结果接近（AIME 2026 不限输出时都是 97.71%，DeepSWE 为 69.03% 对 68.14%），但 PR 也说明单次运行不能证明精度等价。本分支在 CP8 下显式打开了它（第 2 个提交修复了这几项同时开启时的崩溃），精度对比见“精度”一节。

在此之上，如果这一块之后，每个请求都还至少有一个窗口没填，这个窗口迟早会被后面的块覆盖，算了也不会被读。这时我们让整块在第 20 层（共 40 层）停下，CP 下 logits 和 DSpark 要用的行布局照常保留，结果与 bounded replay 本身逐位一致。为保证被读到的晚层数据都来自完整的前向，调度器也做了配合：落在最后一个窗口内的续块必须包含整个窗口；命中 radix 缓存的请求要重新 prefill 最后一个窗口。

### prefill CUDA graph

每层约 4 ms 的 host 开销用 CUDA graph 消除。图按本卡的精确行数懒捕获，不做 padding：某个行数第二次出现时才捕获，每段最多保留 32 个图，按 LRU 淘汰。CP 的 KV 汇聚、indexer 和 attention 核心仍然 eager 执行。捕获完成后、注册 custom all-reduce 的图输入之前，所有 rank 先投票；任一 rank 捕获失败，就一起丢弃这次捕获，退回 eager。

### 稀疏注意力 indexer

V4.1 的 ratio-1⁄2 层先由 indexer 为每个 query 选出 top-k 个 KV 位置，再做稀疏注意力。上游 prefill 的 indexer 用 torch 实现：把 index key 反量化为 BF16，做一次 einsum，再调用 `torch.topk`。

我们在 prefill 时把每个请求的 FP4 key 只解包一次，转为 E4M3，用 FP8 tensor core 打分；打分规模到 2M 后，在 H20 上改用 keys-major 的 Gluon kernel。top-k 用 top-k v2，同分时固定保留位置靠前者，不再取决于原子操作的先后。分数与 torch 路径在容差内一致。

decode 和 verify 时直接从请求表读 FP4 key 打分。同一请求的多个 verify 行共用已解码的 key tile；候选窗口足够多时，consumer 层只给候选块打分，不再扫描整段上下文。

### MoE：Humming W4A8

V4.1-Flash 的路由专家权重是 FP4（MXFP4），而 H20 属于 Hopper，没有 FP4 tensor core。这部分用的是**蚂蚁开源**的 Humming（[github.com/vllm-project/humming](https://github.com/vllm-project/humming)），一个 JIT 编译的量化 GEMM 库。它在 kernel 内把 FP4 权重转为 FP8，权重的 E8M0 scale 预先折进操作数，再与 FP8 激活一起送进 FP8 tensor core（W4A8）。权重在显存里仍是 4 bit，读取量小，计算时又能用上 FP8 的算力。SGLang 已把它接入为 MoE 后端（[#23754](https://github.com/sgl-project/sglang/pull/23754)）；FlashInfer 近期为 Hopper 加的 MXFP4×FP8 MoE 路径，也沿用了 Humming 的权重预处理和反量化方法（[flashinfer #3738](https://github.com/flashinfer-ai/flashinfer/pull/3738)）。

Humming 在 H20 上的效率很高。我们早前剖析过一个 128K 冷 prefill（TP4 + CP4）：路由专家的两个 GEMM 占 GPU 时间的三分之一以上；按 kernel 实测时间和形状折算，w13 和 w2 分别达到 FP8 稠密峰值的 84% 和 83%。

本分支对 Humming 的用法做了这些改动：

- 关闭 stream-K：它按到达顺序累加 K 切片，短输入的第一个 token 会随运行变化。
- 每个 rank 的权重填充从 256⁄128 缩到 64/64，TP8 下 w13 的 N 从 768 降到 576。
- SwiGLU 与 W2 输入的 FP8 量化融合为一个 kernel；路由专家的加权求和推迟到与共享专家合并时做。
- 增加一层 Humming 头文件 overlay，并按角色加载 H20 调优表。

### mHC 与 FP8 GEMM

mHC 的主要问题是结果不稳定。上游在 Hopper 上对 32 行以上的 mHC 用 bf16x3，在 H20 上结果会随运行次数和 batch 大小变化，相对 fp64 的误差也大 5–10 倍。我们改用 tf32x3 split-K 加 TileLang 写的 sinkhorn，结果确定，2 行及以上也不随 batch 变化。每个 post 与下一个子层的 collapse 融合，行数多时连同 RMSNorm 一起融合，结果与 FlashInfer 的 RMSNorm 逐比特一致。

FP8 GEMM 方面，block32 线性层的激活直接量化为 DeepGEMM 需要的 scale 布局；小行数 GEMM 按调优表选择 swap-AB 或 split-K kernel；wo_a 保持 FP8，inverse RoPE 融进舍入 kernel。DSpark 的 draft 用 LM head 的 FP8 副本；target 默认仍为 BF16，量化 target 属于有损选项。

### Decode：去掉每张卡上的重复计算

单机配置的 decode 用 CP decode attention TP，8 张卡都持有全部解码行。上游实现中，每张卡都在重复同样的逐行计算：每张卡只有 8 个注意力头，FlashMLA 却要 padding 到 64 个；mHC 和 Engram 在每张卡上都算全部行；TP all-reduce 全部交给 FlashInfer。

我们按行分摊这些计算。96 行起使用 head↔row 交换，每张卡只处理 1⁄8 的行，但用全部 64 个头算注意力；8×H20-3e 上 64 并发时，FlashMLA 单次调用从 257 μs 降到 47 μs。64 行起再加 TP-SP，每张卡只保留 1⁄8 的残差流，mHC、Engram 和 DSpark 的捕获都只算这些行，结果与原路径逐比特一致。

通信和调度方面：

- TP all-reduce 改用 custom all-reduce v2，8×H20-3e 上 64 并发时单次从 63 μs 降到 22 μs。
- CUDA graph 按实际 batch 大小捕获。上游保留了 CP 对齐，单会话会重放 bs=4 的图，算 24 行而不是 6 行。
- FlashMLA 的 tile 调度由一个在 H20 上拟合的代价模型选择，调度器改写自 FlashMLA 的 `get_decoding_sched_meta`（MIT 许可）。

DSpark 方面，draft 行打包成一行送进 FlashMLA；verify 的 greedy argmax 和 draft 的候选选择直接在词表分片上做，省掉 logits 的全量汇聚，结果与汇聚后相同；draft 准备不再把长度拷回 host，这一步原来每步阻塞 CPU 2.8–2.9 ms。

PD 中的 decode 角色用 attention DP，MoE 前要 gather，之后要 combine。gather 从 NCCL 换成 NVLink all-gather，combine 从“all-reduce 后切片”换成直接 reduce-scatter。在 8×H20 的 D 上、batch 256（输入 61440、输出 8192 的合成请求）时，这部分每步从 6.60 ms 降到 5.31 ms。

### 服务层

第 9 个提交处理服务层的问题。

decode 的 DP 分发：上游的 DP 控制器每 20 ms 刷新一次负载快照，刷新时会丢掉已发出、但 rank 还没收到的请求，突发流量于是继续涌向已满的 rank。我们把在途请求计入负载，并跳过已满的 rank。128 个请求同时发到 8 个 rank（每个上限 16）时，上游的分配是 [25, 25, 13 × 6]，现在是 [16 × 8]。

准入等待：DSpark 有一条规则，空闲槽少于 4 个时暂缓 prefill，以便凑批。突发流量过后，最后几个请求会因此空等一整轮 decode，64 并发时 TTFT 约 10 s。直接删掉这条规则会让 TPOT 变差、吞吐下降 11%，所以我们把这种等待限制在 32 个调度轮以内。

SWA 前缀复用：bounded replay 只写最后一个窗口的晚层行，上游因此每次前缀匹配都要回退一整个窗口。我们在 radix 树上记录哪些区间的晚层行确实算过，有记录的部分直接复用。

HiCache：上游不允许 DeepSeek V4 使用 `--hicache-size`，现在可以按 GB 设置每个 rank 的 host 缓存。

PD 失败处理：

- prefill 失联时，decode 不再立即释放可能仍在写入的 KV 页，而是先隔离，等到迟到的 ACK 或失联满 300 s 后再回收；
- prefill 某个 rank 停止上报或调度循环卡住超过 180 s 时，bootstrap 服务的 `/health` 返回 503，decode 的心跳据此判定它失联；
- prefill 在交接前放弃请求时，会立即把原因告诉 decode，decode 不必等到超时。

以下修复对上游同样适用：

- CP + DSpark + bounded replay 时，第一个请求就会因为尾部汇聚的布局不对而崩溃；
- SM90 上 hc-prenorm 的 split-K 在 split 数不能整除 K 块时与 WGMMA 发生竞争，H20 上相对误差可达 10–18%；
- cluster top-k 的阈值桶溢出时，候选会被任意截断；
- PD 交接中有几处并发读写竞争。

### EPD：编码、prefill、解码三段分开

社区 main 还不支持 V4.1 的 EPD 部署，第 10 个提交补齐了这条链路：

- E 只加载视觉部分（48 个权重分片只读 2 个）；P 和 D 不加载视觉塔，prefill 照常用 CP。
- CP 下先把图像特征合入完整输入再切分，修复了图像问答全部出错的问题。
- D 只向 E 请求预处理元数据，不再等图像 embedding。
- encoder 之间通过 `/dev/shm` 共享 embedding 缓存；同时修复了多个 tokenizer worker 注册冲突导致的 503。
