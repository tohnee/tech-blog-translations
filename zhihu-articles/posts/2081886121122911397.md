## KV Cache 优化全景：12 种技术各自省了什么、代价是什么

把模型权重加载进显存，只是 GPU 内存规划的第一步。

推理过程中权重基本不变，KV cache 却一直在变：序列每生成一个 token，缓存就长大一点；默认情况下，每条活跃序列还要各自持有一份。以 Llama 3.1 70B 为例，一条 128K token 的序列在 BF16 精度下需要约 40 GB 的 KV cache；四条满长序列就是 160 GB——还没算模型权重和推理框架自身的开销。

![](https://pica.zhimg.com/v2-333599759485edd2a2d5c2dfef95731c_1440w.jpg)

**图 1：KV cache 随 token 数增长，且每条活跃序列各持一份；Llama 3.1 70B 单条 128K 序列约 40 GB，四条叠加 160 GB**

由此产生两种独立的成本：缓存占用 GPU 显存；注意力层在生成每个新 token 时还要反复读取缓存。

市面上的"KV cache 优化"技术，解决的其实是不同环节的问题。有的改变模型存什么，有的少存 token、少用位数，有的不动逻辑缓存、只优化引擎对缓存的读取、分配、共享与搬移。本文按"每种技术改动了缓存公式里的哪一项"把 12 种技术组织起来，说明各自省的是什么、代价是什么，并给每一节配一个可以独立运行的小例子。

## 先看缓存公式

每一层注意力为每个保留的 token 存一份 key 和一份 value。单条序列的原始缓存大小是：

> 缓存字节数 = 2 × 层数 × KV 头数 × 头维度 × 序列长度 × 每值字节数

开头的 2 计 key 与 value 两份；BF16 每个值 2 字节，FP8 每个值 1 字节。代入 Llama 3.1 70B：80 层、8 个 KV 头、头维度 128，128K 上下文下得到 2 × 80 × 8 × 128 × 131072 × 2 ≈ 40 GB，与开头的数据对得上。

这个公式也给技术分组提供了坐标轴：

- GQA / MQA 与跨层注意力分别减少 **KV 头数** 和 **独立缓存的层数**；
- MLA 压缩 **存储表示的宽度**，量化减少 **每个值占用的位数**；
- 滑动窗口、驱逐、混合循环与压缩稀疏注意力都减少 **保留的 token 数**，其中混合循环干脆把增长的缓存换成固定状态；
- 分页、前缀复用与卸载优化引擎对缓存的 **分配、共享与移动**；
- Quest 式的稀疏读取只减少 **每步读取量**，不动驻留内存。

## 1. GQA 与 MQA：少存几个 KV 头

在每个 transformer 层内部，每个 token 产生三种表示：

- **query** 表达当前 token 需要什么；
- **key** 描述每个历史 token 能与什么匹配；
- **value** 携带匹配命中后要返回的信息。

生成时，当前 token 的 query 与缓存的 key 逐个比较，比较结果形成注意力权重，再对缓存的 value 加权求和。层会把 key 和 value 留下来供后续解码步使用，query 用完即弃。

注意力把这些表示切成更小的"头"。一个 query head 只是 token 的 query 表示的一个切片——它既不是用户的 prompt，也不是一次独立的模型请求。不同的头可以在同一条序列上学到关注不同的关系。

三种布局的区别只在于一层存多少个 KV head：

- **MHA（标准多头注意力）**：每个 query head 配一个 key head 和一个 value head。8 个 query head 的层产生 8 个 key head 和 8 个 value head。每一层独立做投影、独立持有自己的 KV cache。
- **MQA（多查询注意力）**：保留全部 8 个 query head，但只产生一个 key head 和一个 value head，所有 query head 共用这对 KV。共享不跨层。
- **GQA（分组查询注意力）**：介于两者之间。把 query head 分组，每组配一对 KV。8 个 query head、2 个 KV head 时，每 4 个 query head 共享一对 KV。

GQA 论文把这种布局描述为 MHA 与 MQA 之间的中间点。

![](https://pic4.zhimg.com/v2-fcbc97a9d5e3a2f903c03fa11a5e6cd9_1440w.jpg)

**图 4：三种共享方式——从一对一到分组共享再到全体共享，缓存标量数 768 → 192 → 96**

下面的代码用 8 个 query head 演示映射关系，并统计 6 个 token 需要缓存的标量数：

```text
query_heads = 8
tokens = 6
head_size = 8

for name, kv_heads in [("MHA", 8), ("GQA", 2), ("MQA", 1)]:
    queries_per_kv_head = query_heads // kv_heads
    mapping = [head // queries_per_kv_head for head in range(query_heads)]
    cached_scalars = 2 * kv_heads * tokens * head_size

    print(name, "mapping:", mapping)
    print(name, "cached scalars:", cached_scalars)

MHA mapping: [0, 1, 2, 3, 4, 5, 6, 7]
MHA cached scalars: 768
GQA mapping: [0, 0, 0, 0, 1, 1, 1, 1]
GQA cached scalars: 192
MQA mapping: [0, 0, 0, 0, 0, 0, 0, 0]
MQA cached scalars: 96
```

mapping 给每个 query head 列出它读的 KV head 编号。MHA 每次用不同的 KV head；GQA 让前四个 query 共享 0 号、后四个共享 1 号；MQA 把全部 query 都映射到 0 号。缓存计数含 key 和 value，再乘 6 个 token 和每个头 8 个标量。

Llama 3.1 70B 有 64 个 query head、8 个 KV head。在 128K 上下文下，这个形状的 BF16 缓存约 40 GB；若沿用 MHA 的 64 个 KV head，将是约 320 GB。

GQA 论文把现有 MHA checkpoint 转换后，用原始预训练算力的 5% 做恢复训练，得到的模型质量接近 MHA、速度接近 MQA。注意：上面这段代码只证明了存储比，不涉及质量——共享头会改变模型学到的东西，质量只能在训练后评估。

## 2. 跨层注意力：层与层之间共享缓存

GQA 在一个层内部跨头共享 KV；跨层注意力（CLA）则在相邻层之间共享。共享因子为 2，意味着两层注意力共用一份缓存的 key 和 value，模型只需要存一半数量的独立层缓存。

下面的脚本用两层指向同一个缓存对象来表示共享：

```text
tokens = 32
kv_heads = 2
head_size = 8

one_layer_cache = 2 * tokens * kv_heads * head_size
shared_cache = {"stored_scalars": one_layer_cache}
layer_caches = [shared_cache, shared_cache]

separate_total = 2 * one_layer_cache
shared_total = shared_cache["stored_scalars"]

print("layers point to same cache:", layer_caches[0] is layer_caches[1])
print("two separate layer caches:", separate_total, "scalars")
print("one shared layer cache:", shared_total, "scalars")

layers point to same cache: True
two separate layer caches: 2048 scalars
one shared layer cache: 1024 scalars
```

单层在这里要存 1024 个标量（开头的 2 计 key 和 value），两层各自持有就是 2048。layer_caches 里的两个元素指向同一个 Python 对象：逻辑上两层都在用，物理上仍只有 1024 个标量。

CLA 与 GQA 可以叠加，因为它们减的是不同的项：GQA 减每层内部的 KV 头数，CLA 减整个模型的独立层缓存数。CLA 论文在 1B 和 3B 模型上训练，报告相对 MQA 基线再 2 倍的 KV cache 缩减，精度接近基线。

为什么 CLA 不能作为运行时开关？标准 checkpoint 的每一层都学习了自己独立的 KV 投影，每一层都期待使用自己的权重产生的缓存，把它重定向到别的层的缓存会改变模型的计算。CLA 模型在训练时就带着共享模式，让每个依赖层适应共享缓存；推理引擎必须复现同样的"哪层拥有哪份缓存"的所有权关系。checkpoint 与引擎必须就此达成一致，所以它不是一个通用的推理 flag。

## 3. MLA：压缩存储的表示

CLA 减少独立缓存的层数。多查询头潜注意力（MLA）换一个维度：压缩每个 token 缓存的宽度。

MLA 不给每个头都存完整的 key 和 value，而是把隐状态压缩成一个更小的潜表示（latent）存下来。解码时，模型用学到的投影恢复注意力所需的信息。实现上可以把部分投影吸收进 query 路径和输出路径，从而避免在内存中重建完整的 KV 张量。

DeepSeek-V2 引入了这个设计：论文报告相比 DeepSeek 67B 减少 93.3% 的 KV cache，最大生成吞吐提升 5.76 倍。

真实 MLA 层用学习矩阵创建和使用潜表示，矩阵运算会掩盖内存差异，所以下面的例子把维度设小，让两种布局的差异直接可见：

```text
kv_heads = 4
head_size = 8

standard_keys = kv_heads * head_size
standard_values = kv_heads * head_size
standard_total = standard_keys + standard_values

mla_latent = 8
mla_rotary_key = 4
mla_total = mla_latent + mla_rotary_key

print("standard cache:", standard_keys, "key +", standard_values, "value")
print("MLA cache:", mla_latent, "latent +", mla_rotary_key, "rotary key")
print("stored scalars per token:", standard_total, "->", mla_total)
print(f"example reduction: {standard_total / mla_total:.2f}x")

standard cache: 32 key + 32 value
MLA cache: 8 latent + 4 rotary key
stored scalars per token: 64 -> 12
example reduction: 5.33x
```

4 个 KV head 各 8 个标量，key 占 32，value 再占 32，标准注意力每 token 存 64 个标量。示例的 MLA 布局存 8 个潜表示加 4 个旋转位置标量，共 12 个。64 除以 12 得到 5.33 倍——这个数字只属于这个示例，真实 MLA 模型会选不同的潜维度和位置维度。

MLA 同样不是标准 checkpoint 的推理开关：投影权重和缓存布局属于训练好的模型，转换现有模型仍需要训练。

## 4. 量化：用更少的位存每个值

MLA 压缩宽度。量化更直接：每个值用更少的位来存。

KV 缓存里存的是浮点数。BF16 每个数 16 位，FP8 只有 8 位，裸载荷约为一半；4 位格式把载荷压到 25%。量化把许多原始数值映射到一组更小的允许值上，一个 scale 控制这些值之间的间距；引擎存储小整数码和足以解释它的 scale 信息。

scale 的选择影响精度：一个极端值就能把共享 scale 撑得过宽，让大多数普通值被舍入得过狠。

KIVI 对 key 和 value 区别对待：key 按**通道**分组（不同 token 的同一特征归一组），value 缓存按**token** 分组。论文报告 2-bit 缓存带来 2.6 倍的峰值内存下降，batch 最多扩大 4 倍。

下面的例子展示基本映射：把 6 个 BF16 风格的值转成 4 位有符号码，再从码还原出近似值：

```text
import numpy as np

values = np.array([-1.0, -0.55, -0.10, 0.25, 0.60, 1.0])
bits = 4
largest_code = 2 ** (bits - 1) - 1
scale = np.max(np.abs(values)) / largest_code

codes = np.rint(values / scale)
codes = np.clip(codes, -largest_code, largest_code).astype(np.int8)
restored = codes * scale

print("original values:", values.tolist())
print("4-bit codes:", codes.tolist())
print("restored values:", np.round(restored, 3).tolist())
print("raw payload:", len(values) * 16, "bits ->", len(values) * 4, "bits")

original values: [-1.0, -0.55, -0.1, 0.25, 0.6, 1.0]
4-bit codes: [-7, -4, -1, 2, 4, 7]
restored values: [-1.0, -0.571, -0.143, 0.286, 0.571, 1.0]
raw payload: 96 bits -> 24 bits
```

有符号 4 位存储提供 -7 到 7 的码值。原值除以 scale 映射为码，再乘同一个 scale 还原出注意力里实际用的近似值。可以看到还原值接近但不完全相同——这个舍入差就是量化误差。最后一行只数了 6 个存储值；真实缓存还要存 scale 元数据。

这个例子给全部 6 个值共用一个 scale。KIVI 用更小的分组，让每组贴合自己的数值范围，通常舍入误差更小，代价是需要更多 scale 元数据。

用 vLLM 可以直接开启 FP8 缓存：

```text
MODEL_ID=Qwen/Qwen2.5-7B-Instruct
vllm serve "$MODEL_ID" --kv-cache-dtype fp8
```

第一条定义模型名，第二条启动 vLLM 并把 KV cache 存为 FP8。较新的 vLLM 还允许把选定的层留在原生类型，适合滑动窗口层更敏感的情况：

```text
MODEL_ID=google/gemma-3-4b-it
vllm serve "$MODEL_ID" \
  --kv-cache-dtype fp8 \
  --kv-cache-dtype-skip-layers sliding_window
```

这个版本把滑动窗口层留在原格式，其余缓存层量化。量化保留全部 token 位置——接下来几节的技术反其道而行，从 token 数量上动手。

## 5. 滑动窗口：只保留最近的 token

全自注意力里，每个新 token 都可以关注所有历史 token，因此每层都必须为整条序列保留 key 和 value——序列越长，每层的缓存都跟着长。

滑动窗口注意力把某一层限制在最近的 token 上。窗口 1024 时，该层只保留最近 1024 个位置的 KV；窗口填满后，每来一个新条目就丢掉最旧的。缓存从此固定在 1024 个位置。

这样的层叫**局部层**，因为它只看邻近上下文；**全局层**仍可关注所有历史 token，它的缓存持续增长直到序列结束。很多模型混用两种层：局部层贡献大部分内存节省，偶发的全局层保住对 prompt 远处内容的访问。总缓存仍在增长，但比全层全注意力慢得多。

Gemma 3 采用"5 个局部层 + 1 个全局层"的重复模式：局部窗口 1024 个 token，全局层支持完整的 128K 上下文。

下面的例子跟踪一个 4 token 窗口各时刻保留的位置：

```text
window_size = 4
retained_positions = []

for position in range(10):
    retained_positions.append(position)

    if len(retained_positions) > window_size:
        retained_positions.pop(0)

    print(f"after token {position}: {retained_positions}")

print("maximum retained positions:", window_size)

after token 0: [0]
after token 1: [0, 1]
after token 2: [0, 1, 2]
after token 3: [0, 1, 2, 3]
after token 4: [1, 2, 3, 4]
after token 5: [2, 3, 4, 5]
after token 6: [3, 4, 5, 6]
after token 7: [4, 5, 6, 7]
after token 8: [5, 6, 7, 8]
after token 9: [6, 7, 8, 9]
maximum retained positions: 4
```

列表先用 0 到 3 填满。位置 4 到达后列表超长，弹出第一个元素丢掉位置 0。之后每一步都重复这个动作。生产引擎通常用环形缓冲区实现，直接覆写最旧的槽位而无需搬动其余条目。

注意节省比例随上下文长度变化：序列短于窗口时，局部层和全注意力保留的位置数相同，节省要在序列超过窗口后才出现。

## 6. 驱逐：给 token 位置设预算

滑动窗口按位置一刀切地丢最旧的 token。驱逐（eviction）更精细：给缓存设一个位置预算，再决定哪些位置最值得留。

难的是决定**哪些位置不能丢**：最近的 token 通常重要，因为它们承载当前对话；较早的 token 也可能带着稍后要用的指令、事实或工具结果。

H2O 保留最近位置和更早的"重击手"（heavy hitter）——在先前步骤中积累了高注意力的 token。一旦 H2O 驱逐某个 token，它的 KV 条目就永久不可用了。

其他方法用不同的方式估计重要性：SnapKV 观察输入 prompt 末尾附近的注意力，用这个观察窗在生成开始前选定要保留的 prompt 位置；PyramidKV 按作者报告的注意力模式，给较低层更大的预算、较高层更小的预算。

SnapKV 报告 16K 输入下内存效率提升 8.2 倍、生成提速 3.6 倍；PyramidKV 在 LongBench 上以 12% 的缓存保留量匹配全缓存的性能。

下面的例子在 10 个 token 之后做一次快照。scores 表示此前解码步中积累的注意力，缓存只保留 6 个位置，其中最近 2 个必留：

```text
scores = [9.0, 0.2, 4.0, 0.1, 0.3, 6.0, 0.2, 0.4, 0.1, 0.2]
budget = 6
recent_count = 2

positions = list(range(len(scores)))
recent = positions[-recent_count:]
older = positions[:-recent_count]

heavy_hitter_count = budget - recent_count
heavy_hitters = sorted(
    older,
    key=lambda position: scores[position],
    reverse=True,
)[:heavy_hitter_count]

retained = sorted(heavy_hitters + recent)

print("heavy hitters:", sorted(heavy_hitters))
print("recent positions:", recent)
print("retained positions:", retained)
print("cache entries:", len(retained), "of", len(scores))

heavy hitters: [0, 2, 5, 7]
recent positions: [8, 9]
retained positions: [0, 2, 5, 7, 8, 9]
cache entries: 6 of 10
```

位置 8、9 因最新而被保留，剩下 4 个名额；排序选出旧 token 中分数最高的 0、2、5、7。两组并集构成最终的 6 位置缓存，1、3、4、6 被丢弃。真实 H2O 在生成过程中持续更新重击手统计，这个小例子从已积累的分数出发，让选择规则保持可见。

驱逐需要谨慎评估。重要性会跨轮次变化：一个现在没得到多少注意力的工具结果，几次调用后可能变得必不可少；系统指令和分隔符也可能不成比例地重要。驱逐评测应使用完整的 agent 轨迹与延迟引用，还要覆盖结构化 prompt——一个好的大海捞针（Needle-in-a-Haystack）分数覆盖不了这些场景。

## 7. 混合模型：用固定状态替换增长的缓存

驱逐仍在注意力框架内挑位置。混合模型更进一步——干脆不为每个历史 token 存 KV，而是更新一个固定大小的状态。

Mamba 和循环线性注意力层正是这么做的。纯循环模型的内存几乎不随上下文增长，但全注意力在许多场景下仍更擅长精确检索。最近的模型把两者组合起来：Qwen3-Next 有 48 层，排成 12 个重复块，每块含 3 个 Gated DeltaNet 层和 1 个全注意力层。只有那 12 个全注意力层产生标准的增长型 KV cache；模型卡给出的注意力形状是 16 个 query head、2 个 KV head、头维度 256。

下面的例子对比两者的内存增长。注意力层每个 token 存 64 个值的 key 和 value；循环层只维护一个固定的 64×64 状态：

```text
width = 64
bytes_per_value = 4

attention_values_per_token = 2 * width
recurrent_state_values = width * width

for tokens in [128, 4096]:
    attention_kb = tokens * attention_values_per_token * bytes_per_value // 1024
    recurrent_kb = recurrent_state_values * bytes_per_value // 1024

    print(f"{tokens} tokens")
    print("  attention KV:", attention_kb, "KB")
    print("  recurrent state:", recurrent_kb, "KB")

128 tokens
  attention KV: 64 KB
  recurrent state: 16 KB
4096 tokens
  attention KV: 2048 KB
  recurrent state: 16 KB
```

注意力部分的计算乘了序列长度，循环部分的计算完全不涉及 token 数——状态在两个长度下都是 16 KB。注意力缓存在两个序列长度之间增长了 32 倍，循环状态纹丝不动。混合模型的缓存只在全注意力层线性增长。

以 Qwen3-Next 的注意力形状计，128K 上下文下 12 个全注意力层需要约 3 GB 的 BF16 KV；如果 48 层全是全注意力，增长部分将膨胀到 12 GB。Jamba 用另一种比例做同样的设计：1 个注意力层间隔 7 个 Mamba 层，论文报告 256K 上下文下 KV cache 为 4 GB，而 Mixtral 需要 32 GB。

注意这个例子只跟踪内存，没有实现 Mamba 或 Gated DeltaNet——那些架构用学习到的更新规则决定固定状态里保留什么。层布局也属于训练好的模型，推理引擎不能在运行时把任意注意力层换成循环层。

## 8. 压缩稀疏注意力：少存，也少读

循环层用固定状态换内存，代价是精确检索能力下降。压缩稀疏注意力（CSA）保留注意力，同时对存储和读取两头下手。

先看它要对付的成本：全注意力做两件昂贵的事——为每个历史 token 存一条 KV，生成下一个 token 时又把所有条目都读一遍。普通的稀疏注意力只改第二件事：每次读更少的条目，但完整缓存仍留在内存里，这让生成更快而不缩小常驻缓存。

CSA 两件事都改：

1. 先把相邻的几个 token 条目合并成一条**压缩条目**，存储压缩后的短序列，而不是每个 token 一条长程条目；
2. 每个新 token 到来时，一个**选择器**只挑出看起来最相关的压缩条目，注意力只读这个子集。一个小型滑动窗口单独保留最近 token 的细粒度细节。

DeepSeek V4 用的就是这种设计。若压缩因子为 m，每 m 条 token 条目变成一条存储条目，n 个 token 的上下文产生约 n/m 条压缩条目；注意力再从其中选 k 条读取。

![](https://picx.zhimg.com/v2-52294e83184fe301f56cc8032ada1fcf_1440w.jpg)

**图 5：CSA 先压缩、再选择——相邻 token 合并为压缩条目，选择器只挑最相关的几条给注意力，小窗口保留最近细节**

DeepSeek 报告，在 100 万 token 下，V4-Pro 的 KV cache 是 DeepSeek V3.2 的 10%、单 token 推理 FLOPs 是 27%；V4-Flash 更进一步，缓存 7%、FLOPs 10%。这些是整模型结果，包含 V4 的混合注意力布局与精度选择，不应读作压缩单独带来的效应。

下面的代码把两种缩减分开算。把 32 条长程条目按 4 个一组压缩，剩下 8 条存储条目；若注意力从中选 2 条，则这一步只读 2 条压缩条目：

```text
full_token_entries = 32
tokens_per_group = 4
selected_entries = 2

compressed_entries = full_token_entries // tokens_per_group

print("full token entries:", full_token_entries)
print("compressed entries stored:", compressed_entries)
print("compressed entries read:", selected_entries)
print("storage reduction:", f"{full_token_entries / compressed_entries:.0f}x")

full token entries: 32
compressed entries stored: 8
compressed entries read: 2
storage reduction: 4x
```

32 条除以每组 4 条得到 8 条压缩条目，这是存储缩减；从中选 2 条是独立的读取缩减。缓存现在持有 8 条长程条目而非 32 条，注意力只读其中 2 条，小局部窗口另行保留最近 token 的细节。

这项技术内建在模型和训练过程中——推理引擎无法通过改缓存设置把现有全注意力模型转换成压缩稀疏注意力。

## 9. 分页：解决跨请求的分配碎片

前面八种技术都在改变模型存什么、读什么。分页不碰缓存的内容，解决的是另一个问题：引擎如何把缓存内存分配给许多请求。

朴素的分配器给每个请求预留一段连续内存，而且常常按请求的最大长度预留。较短的请求用不完这段区域；请求结束后，空闲空间又被切成碎片。

PagedAttention 把 GPU 缓存内存切成**等大的块**，每块容纳固定数量 token 的 KV 条目。请求可以从共享池的任意位置取块，块的物理位置不必相邻：

![](https://pic2.zhimg.com/v2-98a513deabe704eba2d1c32755227b41_1440w.jpg)

**图 6：PagedAttention 的块池——请求从共享池任意取块，块表记录逻辑顺序，碎片与预留浪费随之消失**

请求结束时，分配器把它的块还给池子，其他请求立即可复用。PagedAttention 论文报告接近零的 KV cache 浪费，吞吐比测试的基线系统高 2 到 4 倍。

一个固定大小的池子还会掩盖量化的效果：引擎在开启 FP8 前后可能都预留同样的 8 GB。更小的条目只是提高了池子能容纳的 token 数，nvidia-smi 显示的已分配内存可能纹丝不动。

下面的例子从 6 个空闲块开始：请求 A 取 3 块，B 取 2 块，A 完成后归还，请求 C 再取：

```text
free_blocks = [0, 1, 2, 3, 4, 5]

request_a = free_blocks[:3]
free_blocks = free_blocks[3:]

request_b = free_blocks[:2]
free_blocks = free_blocks[2:]

free_blocks.extend(request_a)
free_after_a = free_blocks.copy()
request_c = free_blocks[:2]
free_blocks = free_blocks[2:]

print("request A blocks:", request_a)
print("request B blocks:", request_b)
print("free after A finishes:", free_after_a)
print("request C blocks:", request_c)

request A blocks: [0, 1, 2]
request B blocks: [3, 4]
free after A finishes: [5, 0, 1, 2]
request C blocks: [5, 0]
```

A 结束后，空闲池里是块 5 加上 A 归还的块。请求 C 取走块 5 和块 0——编号不相邻，但块表为 C 记录了它们的顺序。这就是分页的核心：分配器复用可用的块，而不是寻找一大段连续区域。vLLM 还跟踪每个块的归属，注意力代码能按逻辑顺序读取不相邻的块；这个小例子只隔离了分配与复用。

量化依然改变池子的**容量**：8 GB 池在每 token 320 KB 时容纳 26,214 个 token，在 160 KB 时容纳 52,428 个。两种情况下总分配的 GPU 内存都是 8 GB。

## 10. 前缀复用：共享相同开头的块

分页在请求结束后复用块；前缀缓存在多个请求同时活跃时共享块——前提是这些请求以完全相同的 token 开头。

系统提示和工具定义经常满足这个条件。没有前缀缓存时，引擎为每个请求重新计算并存储一份 KV，重复的前缀既耗内存，又重复了产生它的 prefill 计算。

自动前缀缓存把每个已完成的前缀块以查找键的形式存起来。当另一个请求拥有相同的 token 前缀时，直接指向现成的 KV 块，只有请求分叉后才开始新计算。vLLM 用当前块及其前置块构造查找键，并在影响兼容性时纳入 adapter 标识等细节。

下面的例子用 4 token 一块，每个查找键包含到该块为止的完整前缀——这是 vLLM 链式哈希的可读替身：

```text
def prefix_keys(tokens, block_size):
    block_ends = range(block_size, len(tokens) + 1, block_size)
    return [tuple(tokens[:end]) for end in block_ends]

first = [10, 11, 12, 13, 20, 21, 22, 23, 30, 31, 32, 33]
second = [10, 11, 12, 13, 20, 21, 22, 23, 40, 41, 42, 43]

cache = set()
first_keys = prefix_keys(first, block_size=4)
first_hits = sum(key in cache for key in first_keys)
cache.update(first_keys)

second_keys = prefix_keys(second, block_size=4)
second_hits = sum(key in cache for key in second_keys)

print("first request reused:", first_hits, "of", len(first_keys), "blocks")
print("second request reused:", second_hits, "of", len(second_keys), "blocks")
print("second request computes:", len(second_keys) - second_hits, "new block")

first request reused: 0 of 3 blocks
second request reused: 2 of 3 blocks
second request computes: 1 new block
```

第一个请求没有可复用的缓存，为前 4、8、12 个 token 各加一个键。第二个请求前 8 个 token 相同，前两个键命中；最后 4 个 token 不同，最后一个前缀键改变，于是只计算 1 个新块。

用完整前缀做键防止了假匹配：两个请求不会因为中间某处恰好有 4 个 token 相同就复用一块——它们的前置上下文必须也相同。

前缀复用依赖**精确的 token 化前缀**。系统提示里一个时间戳、工具 schema 里重排的 JSON 键、聊天模板里不同的空白，都能破坏命中。稳定的 prompt 模板因此直接提高命中率——模型和缓存格式都不必变，重复存储就下降了。

## 11. 卸载：把冷块移到 CPU 内存

前缀复用适用于引擎已经处理过相同开头 token 的情况。卸载处理另一个问题：把暂时不用的 KV 块从 GPU 显存移到大得多但更慢的存储层级，通常是 CPU 内存。

这些块可能属于被调度器暂停的序列，或为复用而保留的缓存前缀。引擎需要它们时再拷回 GPU。

有一个重要的限制：一个全新的 OpenAI 兼容 API 请求不会自动从上一次请求恢复 KV cache。复用只在引擎仍然跟踪着这条序列、识别出精确的前缀缓存命中、或通过外部存储系统恢复缓存时发生。

卸载在不删除 KV 数据的前提下释放 GPU 显存，但**不减少** GPU 与 CPU 内存合计持有的字节数。代价在引擎必须先把块搬回来才能继续计算时显现。

下面的例子给 GPU 两个会话的容量：会话 C 到来时把最旧的 A 移到 CPU 内存；A 恢复时回来，把 B 换出去：

```text
gpu_cache = ["cache-a", "cache-b"]
cpu_cache = []

# 缓存 C 需要 GPU 空间，缓存 A 移入 CPU 内存。
cpu_cache.append(gpu_cache.pop(0))
gpu_cache.append("cache-c")

print("GPU after cache C arrives:", gpu_cache)
print("CPU after cache C arrives:", cpu_cache)

# 缓存 A 再次被需要，回到 GPU。
cpu_cache.remove("cache-a")
cpu_cache.append(gpu_cache.pop(0))
gpu_cache.append("cache-a")

print("GPU after cache A returns:", gpu_cache)
print("CPU after cache A returns:", cpu_cache)

GPU after cache C arrives: ['cache-b', 'cache-c']
CPU after cache C arrives: ['cache-a']
GPU after cache A returns: ['cache-c', 'cache-a']
CPU after cache A returns: ['cache-b']
```

第一次搬移后 B、C 留在 GPU，A 在 CPU 内存里随时可取；A 再次被需要时回来，B 换出。列表里装的是缓存名字而非张量——真实引擎对 KV 块执行这个操作，并跟踪每块属于哪个请求或哪个可复用前缀。

例子假设引擎保留了足够信息、稍后能认出缓存 A。向同一个"标签"发一个无关的 API 请求，不会自动恢复它。

vLLM 可以直接启用一个 16 GB 的 CPU 卸载缓冲：

```text
MODEL_ID=Qwen/Qwen2.5-7B-Instruct

vllm serve "$MODEL_ID" \
  --kv-offloading-size 16 \
  --kv-offloading-backend native
```

第一个选项以 GB 为单位设置 CPU 缓冲大小，第二个选择 vLLM 的原生 CPU 后端。卸载用 GPU 容量换传输时间——启用大卸载层之前，先测恢复延迟和 CPU 带宽。

## 12. 按查询选读：Quest 的页级稀疏读取

分页、前缀复用与卸载都在引擎层面腾空间，但不减少单个请求在 GPU 上驻留的缓存总量。想少读缓存、又改不了模型架构时，Quest 提供了一条路。

回忆生成过程：新 token 产生一个 query，像搜索信号一样与每条存储的 key 比较。长 prompt 会迫使 GPU 一遍遍加载整份大缓存。Quest 不删任何 KV 条目，只减少读取量：

- 把缓存分成**页**，一页是一小组相邻的 token 条目；
- 每页额外保存页内 key 的**最小值与最大值**摘要。

对每个新 query，Quest 先给这些很短的页摘要打分——用 min/max 估计一页可能达到的最高注意力得分——只加载得分最高的页。完整缓存仍然全部保留：现在被忽略的页，未来可能再次变得重要。

Quest 论文报告自注意力延迟最高降低 7.03 倍，完整推理系统提速最高 2.23 倍。

下面的例子用 4 个页、每页 2 个 key，每个 key 只有两个数，让打分过程一目了然：

```text
import numpy as np

pages = np.array([
    [[1, 0], [2, 1]],
    [[5, 1], [4, 2]],
    [[0, 6], [1, 5]],
    [[-2, -1], [-1, 0]],
])
query = np.array([1.0, 0.5])

page_min = pages.min(axis=1)
page_max = pages.max(axis=1)
page_scores = np.maximum(query * page_min, query * page_max).sum(axis=1)
selected_pages = np.argsort(page_scores)[-2:]

for page, score in enumerate(page_scores):
    print(f"page {page} score: {score:.1f}")

print("selected pages:", np.sort(selected_pages).tolist())
print("KV entries read:", len(selected_pages) * 2, "of", pages.size // 2)
print("KV entries still stored:", pages.size // 2)

page 0 score: 2.5
page 1 score: 6.0
page 2 score: 4.0
page 3 score: -1.0
selected pages: [1, 2]
KV entries read: 4 of 8
KV entries still stored: 8
```

pages 数组共 8 个 key。紧接着两行给每页算出最小值与最大值摘要；这里的 query 偏好两个 key 维度上数值都大的条目，1 号和 2 号页得分最高，于是这一步读取它们的 4 个 key，其余 4 个 untouched。

注意最后一行：这一步读了 4 条，但 8 条全都驻留内存。Quest 减少缓存流量和注意力计算，**不减少**容纳完整缓存所需的内存。实际实现使用高维 key 和专用 GPU kernel，并且对每个 query 重复选择过程。

## 如何组合与选择

这些技术里有不少可以叠加，因为它们减的是公式里的不同项。架构级方法仍取决于 checkpoint 是如何训练的。

以开头那个 40 GB 的 GQA 缓存为例：

- 共享因子为 2 的 CLA 把独立层数减半，得 20 GB；
- FP8 把每值字节数减半，约 10 GB；
- 再保留一半 token 位置，常驻缓存约 5 GB。

这个乘法适合做容量规划，却掩盖了模型质量与内核支持：CLA 需要训练，FP8 引入量化误差，驱逐丢弃上下文，引擎还得支持叠加后的布局。

下面这张决策图对应五种常见情况：

![](https://picx.zhimg.com/v2-6f9b81acc58201f49ee5bc2bb5b2942f_1440w.jpg)

**图 7：从约束出发选择技术——换模型看架构；服务现有模型先 FP8 与标准化前缀，再按质量测试决定是否驱逐**

对应的五种做法：

- **要选模型时**——检查 KV 头数、局部层与全局层的比例、潜注意力维度、循环层数量。这些参数决定部署前的起始缓存，而不是部署后能调多少。
- **服务现有模型时**——先测 FP8，再标准化前缀；两者都保留全部 token。只有通过针对自身工作负载的质量测试后，才引入驱逐。
- **显存占用看起来没变时**——查缓存容量与块数：固定池可能把节省全部吸收，总分配的 GPU 内存自然保持平坦。
- **延迟是瓶颈时**——测缓存读取量与注意力耗时。Quest 式的稀疏读取不腾容量，却可能显著降延迟。
- **不活跃会话占着 GPU 时**——测试卸载与调度。把冷块搬走，往往比继续压榨活跃块更划算。

## 十二种技术一览

| 技术 | 改动 | 主要节省 | 代价与未覆盖 |
| --- | --- | --- | --- |
| GQA / MQA | 每层的 KV 头数 | 缓存头数 | 需训练或微调恢复，共享改变模型能力 |
| 跨层注意力（CLA） | 独立缓存层数 | 层数 | 需按共享模式训练，不能作为运行时开关 |
| MLA | 每 token 存储宽度 | 表示维度 | 需训练，布局属于模型权重 |
| 量化（FP8 / KIVI） | 每值位数 | 字节数 | 量化误差，需精度评估 |
| 滑动窗口 | 局部层保留的 token | token 数 | 窗口外上下文丢失，需全局层兜底 |
| 驱逐（H2O / SnapKV / PyramidKV） | 保留位置预算 | token 数 | 丢弃上下文，需负载级评测 |
| 混合循环层 | 增长缓存 → 固定状态 | 增长量 | 需训练，精确检索弱于全注意力 |
| 压缩稀疏注意力（CSA） | 存储条目与每步读取 | 存储与计算 | 需训练，不能运行时转换 |
| 分页（PagedAttention） | 缓存分配方式 | 碎片与浪费 | 不减少单请求缓存总量 |
| 前缀复用 | 重复前缀的存储 | 重复块 | 仅精确 token 前缀命中 |
| 卸载 | GPU 驻留量 | 显存占用 | 总字节不变，恢复延迟与带宽成本 |
| Quest 稀疏读取 | 每步读取的 KV | 带宽与计算 | 不减少驻留显存 |

把上面的讨论收成一句话：先从你要解决的约束出发——显存容量、读取带宽还是分配浪费——再挑处理那一项的技术。约束不变时，更快的 kernel 也腾不出容纳下一条序列的空间。
