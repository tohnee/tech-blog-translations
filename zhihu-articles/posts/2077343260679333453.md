到了开始找工作的阶段，为了应对找工作中的面试，需要对 agent 的基础知识进行重新梳理，下面作为我对 agent 梳理的记录吧。

Agent 是为了拓展传统 LLM 只能进行问答的功能而设计出的概念。Agent 可以理解为把 LLM 作为大脑，借助上下文（context）作为眼睛对环境进行感知，使用工具（tools）作为手脚来进行与现实世界的交互。Agent 的另一个定义是 Agent = LLM + Plan + Memory + Tools。在这个定义中把 Plan 作为了 LLM 的一个功能，在实际设计上 Plan 也是由 LLM 进行的，因此我认为第一个定义更加准确形象。

很多 LLM 在基准测试中有着非常亮眼的表现，但是如果放到实际业务中却会让人失望，这是因为在基准测试中会为 LLM 提供完整的信息，而在实际业务中一些背景信息 （例如业务规则、内部约定、紧急处理指导等）LLM 却无法获取，这也使得 LLM 无法做出合适的决策。因此对于两个采用相同能力 LLM 的 Agent，上下文决定了 Agent 能力的上限。因此，上下文工程变得尤为重要。

上下文工程负责对 Agent 的上下文进行设计与管理，决定 Agent 应该看到哪些信息来进行决策和调用工具。一个设计良好的 Agent 的上下文一般包含几个部分：系统提示词，用户消息，模型回复，工具执行结果以及工具定义。系统提示词一般由 Agent 的开发者编写，用来定义 Agent 的身份，行为规则以及需要遵守的约束等。用户消息则是来自于用户在终端的输入。模型回复是模型对于用户消息的回复，包含文本回复和工具调用请求。工具执行结果则是根据模型回复中的工具调用请求来进行工具调用，并把调用的结果返回到模型中。工具定义则是告诉 LLM 有哪些工具可以使用。其中，系统提示词和工具定义为静态提示词；用户消息、模型回复以及工具执行结果则为动态提示词。

对于使用大模型调用的 API，一般 API 的格式也包含四个角色，分别是：system，user，assistant 以及 tool。其中这四个分别对应于系统提示词，用户消息，模型回复以及工具执行结果。对于工具定义则是有一个专门的 tools 字段。下面这段伪代码是一个 Agent 的最小骨架，方便理解：

```python
stable_prefix = system_message
stable_tools = core_tool_schemas
trajectory = load_message_history(session)
status_message = make_status_message(derive_current_state(trajectory))

if estimated_tokens(stable_prefix, trajectory, status_message) > budget:
    trajectory = compress_old_evident(
        trajectory, preserve = [decisions, constraints, failures, citations])
request.messages = [stable_prefix] + trajectory + [status_message]
request.tools = stable_tools
response = call_model(request)
```

从代码中也可以看出，系统提示词和工具定义是静态的，只在最开始进行编写。用户消息、模型回复以及工具执行结果则会在每次使用后加入到历史信息里，使得 LLM 能够了解之前执行的结果。这样能够使得 Agent 更加智能，有对话的记忆。但是同时也会引入新的问题：越来越长的提示词会使得模型推理变得繁重，也会对提示词中包含的重要信息进行稀释，使得模型忽略掉重要信息。

针对模型推理繁重的问题，一个常用的解决方法是采用 KV cache 友好的上下文设计。其核心思想是把前文的中间计算结果缓存下来，下一轮只需要计算新增的 token 部分，但要保证复用的上下文的 token 前缀保持不变。具体来说，需要遵守下面三个规则：

1. 系统提示词和工具定义一旦确立就不要进行修改。
2. 动态信息永远加入到末尾。
3. 使用标准的 API 格式，不要自行拼接消息。

因为在之前计算时 KV 向量都已经进行了计算，所以可以保存起来复用，但如果对前面的文本进行了修改，即使是少量几个字节的修改也需要重新计算。与 KV Cache 相似的还有 Prompt Cache，其前提都是要保持前缀相同。但是其作用范围不同。Cache 是加速单次请求内的 token 生成，而 Prompt Cache 是减少跨请求的重复计算成本。Prompt Cache 是 API 服务商对请求的前缀进行匹配，如果多次请求前缀都相同，则直接复用之前计算好的 KV Cache。

随着 Agent 能做的事情越来越多，所需要使用的工具也会越来越多。在一些 Agent 中，单单是工具的注册就占用了上下文的很大一部分。由于在静态提示词中需要定义所有的工具，这导致很多与当前任务无关的工具也被定义，这浪费了很多 token。并且上下文中很多无关的信息会稀释模型对关键内容的注意力，导致会忽略一些关键信息。因此提出了 Agent Skill，不是把所有知识一次性地塞给 Agent，而是可以按需加载。

每个 Skill 相当于一个单独的知识包，本质上是一个专业的提示词集合。Skill 采用了渐进式披露的方式，先给 Agent 看一份目录，再按需加载完整的内容。一个 Skill 一般包含三个层次，分别是：元数据，核心流程，细则。元数据一般在 Skill.md 文件的头部，通常为 YAML 格式，包含两个部分，分别是 name 和 description，用来描述这个 Skill 的作用，让模型判断是否需要加载。name 是 Skill 的名称，description 则应该足够简短，明确何时使用这个 Skill ，并给出几条不适用的反例。核心流程则是在判断需要使用这个 Skill 时才完整地加载到模型中。细则则是更详细的子文档，Agent 会根据具体需求来选择性地深入阅读子文档。Skill 的设计应该包含下面这四个部分：

- 角色与读者说明这份 Skill 服务于谁，面向什么任务，以及输出应达到什么标准；
- 核心原则只保留三到五条最重要的判断，并为关键原则配正例和反例；
- 禁止清单记录高频错误、越权动作和容易误解的表达，同时写清合法例外；
- 参考资料放术语表、模板、范文和更详细的子文档。规则应尽量写成“作用域+动作+例外+验证方式”，避免把所有可能的情况堆成一张越来越长的禁用词表。

工具也可以加载到 Skill 中，这样就不用都定义在静态提示词中，并且可以做到按需加载。

上下文通过多轮对话一直在累积，虽然上下文包含对话的所有信息，但是由于 LLM 模型的一个特性：上下文学习更像检索而并非推理，模型擅长从已有内容中查找信息，但不擅长主动归纳和总结。这导致例如 Agent 已经调用了三次工具，但是它通过上下文很难知道，可能会陷入一直执行工具的循环。因此，为了缓解这个问题，可以通过维护一个状态栏的方式来进行优化。Agent 的状态栏包含下面几种类型的信息：

1. 任务规划：也就是 TODO list
2. 事件的测信道信息：为每个事件附加元数据--精确的时间，地理位置，上次回复的时间间隔等。侧信道信息是指不在主要数据通道中传递、但对理解事件很有帮助的辅助信息。
3. 当前环境状态的观察摘要：动态的环境信息（系统时间、工作目录等）、异常操作提醒等。

Agent 状态栏信息一般是加入到用户消息的末尾，而不是系统提示词后面，这是为了符合 KV Cache 友好的设计。其次，状态栏尽量使用代码维护，这是为了能够保证信息的准确，因为模型会无条件地相信状态栏。

面对上下文爆炸的问题，上下文压缩也是一个有效的解决方法。上下文压缩通常有几种策略：

1. 非任务感知压缩：为每一个个体生成 2-3 条摘要或者将所有结果合并后生成一份综合摘要。为每个个体生成摘要的缺点是如果多个个体描述的是同一个事件，会导致摘要重复。而组合压缩则存在输入过长时丢失末尾信息的问题。这两种压缩方式都缺乏语义理解，无法区分信息的相关性。
2. 上下文感知压缩：把当前查询的意图和已经累积的信息纳入压缩的决策过程。
3. 带有引用的上下文感知压缩：与上下文感知压缩的区别是带有信息源，能够溯源原本的信息。
4. 自适应窗口压缩：任务初期空间充足，无需压缩，只有接近容量时再进行压缩。并且对压缩后的内容进行标记，不会对压缩后的内容进行二次压缩。

压缩策略的设计原则：

1. 信息价值的非均匀分布：关键的决策点的价值高于支撑性的证据。
2. 语义完整性：“小明与 2024 年 3 月 2 日从深圳市南山医院出院”不能压缩为“小明出院”
3. 任务相关性：不同的任务压缩的方式应该不同，其需要保留的信息也不同。
4. 压缩即理解：有效的压缩需要理解语义的深层信息。

还有一种有效的压缩方式是采用子 Agent 来执行任务。大量的信息由子 Agent 来处理，只返回结论给主 Agent。这样主 Agent 就不会存在窗口不够的问题。但是也存在子 Agent 无法看到全部信息的问题。本质是隔离代替压缩。
