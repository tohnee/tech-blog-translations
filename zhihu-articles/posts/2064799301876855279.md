## 
 二、阶段性格局 

### 1. 闭源顶层：

- GPT-5.6 Sol、Claude Opus 5、Fable 5 共同构成新一轮顶层闭源竞争；Opus 4.8 仍可作为稳定性/成本基线。
- 海外闭源模型继续把 **“Agent + 长任务交付”** 作为核心卖点，叙事都从单轮问答/单项跑分转向 **复杂软件工程、科研、网络安全、工具调用和长时间自治任务** 。

### 2. 开源顶层：

- Kimi K3（规模+产品）、GLM-5.2（长程 Coding）、DeepSeek-V4（长上下文效率）、Qwen3.8（预览中的多模态旗舰）多线并行。
- 国内开放权重路线明显加速， **大规模 MoE、1M 级上下文、代码/Agent 与开放权重成为标配议题** 。

### 3. 使用建议：

- 要最强长程交付：选 Fable 5 / GPT-5.6 Sol，能力天花板；
- 要企业默认稳妥选择：Opus 4.8 依然是是性价比与合规平衡点；
- 要自部署/开源：GLM-5.2（长程 coding）、DeepSeek-V4（长文效率）、Kimi K3（规模+产品）、Qwen3.8（预览中的多模态旗舰）；
- 评估时别只看榜单：结合长程工程、工具调用稳定性、百万上下文下质量是否掉点、单位有效产出的 token 成本，选择最适合的模型（成本和需求的权衡）。

## 二、关键能力点

> Long Context 长上下文（装得下） + Coding/工具环境（做得对） + Agent 编排与 effort（撑得久） = 可交付的工作代理

### 1. Agent：从单轮工具调用 → 长程自治执行

> Agent 的胜负手，是长程可靠性 + 工具闭环，不是单次智商峰值。 
>  共同方向不是再堆一个聊天窗口，而是让模型能跨小时/跨天、多工具、多子任务地推进。

- 努力档位（effort）成为标配：Opus 4.8、GPT-5.6、GLM-5.2、Kimi K3、DeepSeek-V4 都把 thinking/effort 做成可调旋钮，用更多 token 换更高成功率。
- 多 Agent / 子 Agent 编排：Claude Code Dynamic Workflows、GPT-5.6 multi-agent、Kimi Work 等，把大任务拆成并行子代理再汇总。
- 产品形态从 Chat 变成 Work/Code：ChatGPT Work、Kimi Work、QoderWork——模型直接接文件、应用、终端，目标是产出文档/代码/结果，而不只是回复。
- 安全与准入并行：Fable/Mythos、GPT-5.6 受限预览说明了，能力越像「自主执行者」，越要配分类器、政府/信任访问机制。

### 2. Coding：从补全/写函数 → 工程级交付

> 目前几乎都把 Coding 作为 Agent 能力的主考场，目前更多比的是复杂任务的端到端交付。

- 指标从 SWE-bench 短任务，扩到长程工程榜：FrontierSWE、SWE-Marathon、PostTrainBench、Terminal-Bench——测的是「几小时到几十小时能不能做完」。
- 仓库级、迁移级、编译器/kernel 级任务进入官方叙事：Fable 的大规模迁移、Kimi K3 的 MiniTriton/芯片设计、GLM-5.2 的多端全链路开发。
- Harness 与模型绑定：Claude Code / Codex / Kimi Code 各自优化，成绩高度依赖执行环境；模型厂商开始自己做「能跑起来的编码产品」。
- 开源平替：GLM-5.2、Kimi K3、DeepSeek-V4 都明确把「可用编程 Agent」当主宣传点。

### 3. 长文：从「号称百万上下文」→「百万上下文真能用」

> 长文不再是规格参数，而是长程 Agent 的基础设施，百万 token 已成标配。

- 架构侧降长文成本：DeepSeek-V4 的 CSA/HCA 压 KV；GLM-5.2 的 IndexShare；Kimi K3 的 KDA/AttnRes——都在解决「上下文越长越贵、越慢、越糊」。
- 训练侧对准 Agent 轨迹：不是塞更多书，而是训超长 coding-agent trajectory、工具调用历史、compaction 后的子轨迹（GLM、DeepSeek 都很强调）。
- 推理侧保留跨轮 thinking：长任务中思考历史不能丢，否则 Agent 会中途失忆（Kimi/DeepSeek 都点过这个问题）。
- 产品侧用记忆/笔记/文件记忆补上下文：Fable 等开始强调 persistent memory，而不只靠裸 context window。
