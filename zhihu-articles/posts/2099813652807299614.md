### 一、场景：周三下午的选型会，和三个人的三个问题

周三下午三点，7B 模型的训练任务在 8 张卡上 OOM 了。选型会上，三个人分别抛出三个问题：

> **算法同学**：我把卡从 8 张加到 64 张，为什么显存一点没省？还是装不下。<br> **Infra 同学**：我试着开了 ZeRO-3，显存是够了，但跨机训练一步明显变慢。多出来的通信费到底花在哪一步？<br> **负责人**：那到底该开哪一档？多付的那 50% 通信，换回来的是什么？

这三个问题，对应本文要算的三笔账：**通信账（为什么必须搬、搬多少）、显存账（冗余在哪、能切多少）、交易账（多付的通信换回哪块显存）**。

为什么模型加到 8 张卡，显存却没省多少？为什么 ZeRO-3 能省到极致，却要多付 50% 的通信费？这篇文章用同一组小数字，把这三笔账从头算一遍。**开头那三个问题，在第十二节统一回答。**

### 1.3 先认识几个词

| 符号 / 术语 | 一句话解释 |
| --- | --- |
| Ψ（读”普西”，psi） | 一份完整模型参数的总量。70 亿参数的模型，Ψ 就是 70 亿个参数占的通信量 |
| N | GPU 的数量 |
| 前向传播 | 模型根据输入算出输出，并产生中间结果（激活值） |
| 反向传播 | 根据输出和答案的差距，算出每个参数”该怎么调”，即梯度 |
| 梯度 | “敏感度”：某参数稍微变一点，损失会变多少。梯度为正说明该调小，为负说明该调大 |
| 数据并行（DDP 的 D） | 每张卡一份完全相同的模型副本，喂不同的数据批次，N 张卡吞吐量放大 N 倍 |

Reduce-Scatter、All-Gather 这些通信术语**不在开头解释**——等到第五节它们首次登场时再给定义，那时你已经有足够的问题感。

### 1.4 两个用词约定，后文严格遵守

- “**规约**“统一指把多份数据合成一份（求和或求平均），不混用”汇总 / 求和”；
- “**归属卡**“指负责某一片数据的卡。梯度的归属（谁规约这片梯度）和参数的归属（谁更新这片参数）在 ZeRO 里**恰好是同一张卡**——这是设计的刻意对齐，不是天然如此。

### 1.5 贯穿全文的玩具例子

> **4 张卡（N=4），训练一个 800 万参数的小模型** 混合精度下 Ψ = 800 万 × 2 字节 = **16MB**，切成 4 块后每块 **4MB**

后面每一笔通信账都用这组数字，可以随时拿计算器验证。涉及显存的账会换成真实尺寸（75 亿参数模型），每次切换都会点明。

> **口径先说清**：本文所有通信量数字基于三个前提——Ring 环形算法、混合精度训练、不开通信-计算重叠（均与 ZeRO 原论文一致）；且一律指**每张卡在一个训练步里累计收发的数据量**，不是全网总量。完整说明见附录 C。

### 二、为什么非得通信不可：规约 + 分发

**本节回答算法同学的问题的前半**：加卡之前，先搞清多卡之间到底在同步什么——不然”加卡不省显存”这件事根本无从解释。

假设你有 4 张 GPU，每张卡放一份完整的模型，各自分到不同的数据，各算各的。这是数据并行最直接的做法。

但这里有个问题：每张卡看到的数据不一样，算出来的梯度也不一样。**每张卡的梯度只反映它自己那份数据的”局部视角”**。如果每张卡拿着自己那份梯度直接更新模型，一步之后参数就不一致了，4 张卡会越走越远，最后变成 4 个不同的模型。

而我们希望的是：**4 张卡并行训练，效果等价于用全部数据在单卡上训练**。

要做到这一点，每一步都必须做两件事：

- **规约**：把 4 份局部梯度合成一份全局梯度。解决”**梯度对不对**“——只有用全局梯度更新，才等价于用全部数据训练。
- **分发**：把全局梯度送到需要它的卡手里。解决”**梯度在谁手里**“——规约结果只停在一张卡上，其他卡拿不到，更新照样没法做。

放进一个完整训练步里看：

| 阶段 | 每张卡在做什么 | 需要通信吗 |
| --- | --- | --- |
| 前向传播 | 用自己的数据算损失和激活值 | 不需要，各算各的 |
| 反向传播 | 算出局部梯度 | 不需要，各算各的 |
| 梯度规约 | 把 N 份局部梯度合成全局梯度 | 必须，否则各卡模型分叉 |
| 结果分发 | 把全局梯度送到需要更新的卡 | 必须，否则有梯度的卡 ≠ 需要更新的卡 |
| 参数更新 | 用全局梯度更新参数 | 不需要，更新后所有卡保持一致 |

**规约和分发是目的，后面所有通信操作都只是实现这两步的手段。** 两者合起来，才让”多卡并行等价于单卡全量训练”这个承诺成立。

> **本节带走**：通信不是可选优化，是数据并行正确性的前提；规约管”对不对”，分发管”在谁手里”。

### 三、为什么要关心”通信量是几 Ψ”

**本节回答 Infra 同学的问题的前半**：他说”开了 ZeRO-3 一步变慢”，慢在哪里、慢多少，得先有一把尺子。

通信不是免费的。每搬一次数据，都要占用 GPU 之间的网络带宽（NVLink、InfiniBand 等），时间直接加在训练步上。通信量越大，训练越慢；当 GPU 数量从 4 张扩展到几百张时，通信开销可能成为整个训练的主要瓶颈。

所以”通信量是几 Ψ”本质上是在问：**为了保持多卡同步，每张卡要额外花多少数据搬运的代价？** 这个代价决定了训练能不能顺利扩展到上百张卡。

再强调一次口径：本文说的通信量，一律指**每张卡在一个训练步里累计收发的数据量**，不是全网总量。

> **本节带走**：Ψ 是尺子；”几 Ψ”问的是每卡每步的搬运代价，它决定能不能扩到上百卡。

### 四、先建立框架：计算阶段和通信操作是两个维度

**本节为后面所有小节打底**：初学者最容易在这里踩坑，先把两个维度分开。

- **计算阶段**（前向传播、反向传播）回答”**现在在算什么**“；
- **通信操作**（All-Gather、Reduce-Scatter）回答”**为了算下去，需要搬什么数据**“。

两者**不是一一对应**。同一个计算阶段里可能做 0 次、1 次或 2 次通信；同一种通信操作也可能出现在前向或反向里。所以”前向就是 All-Gather、反向就是 Reduce-Scatter”这个说法是错的。

判断某个场景该用什么通信，只需要问两个问题：

1. **这个阶段需要完整数据，还是只需要自己那份？** 需要完整 → All-Gather；只需要自己那份 → Reduce-Scatter。
2. **这个阶段手里有没有完整数据？** 没有 → 需要先 All-Gather 拼出来。

带着这个框架往下读，后面每一节都会标明”这里的通信发生在哪个阶段、搬的是什么”。

> **本节带走**：先问”要算什么”，再问”要搬什么”；两个问题决定用哪种通信。

### 五、最笨的做法，和一个环形机制的两种用法

**本节回答 Infra 同学的问题**：2Ψ 这个”底价”是怎么来的，为什么它和卡数几乎无关。

现在问题变成：**怎么用最低的通信代价，完成”规约 + 分发”？**

**先看最笨的做法。** 4 张卡，每张卡有一份完整的梯度（16MB），目标是让每张卡都拿到 4 份梯度加总后的完整结果。最笨的做法：每张卡把完整梯度发给其他 3 张卡，同时收 3 份完整梯度，各自加总——每张卡要发 3Ψ、收 3Ψ（玩具例子里 48MB 进 48MB 出），大量搬运是重复的。卡越多越爆炸，量级是 N×Ψ。

**关键洞察**：把完整数据切成 N 块，每块”归”一张卡负责（块 i 归卡 i），然后用**环形传递**——N 张卡围成一圈，每轮每张卡把手里的一块发给下一张卡（卡 i 发给卡 i+1，模 N），同时收上一张卡发来的一块。

完成”规约 + 分发”的两个通信操作，就是 **Reduce-Scatter** 和 **All-Gather**。**它们共用同一种环形传递机制，区别只有一处——收到数据后做什么**：

- **Reduce-Scatter**：收到后**加到本地对应的块上**（做累加）。传 N−1 轮后，块 i 的全局和只留在卡 i 上——规约完成，但结果分散在各归属卡手里。
- **All-Gather**：收到后**直接存下来**（不累加，只收集）。传 N−1 轮后，每张卡都集齐全部 N 块——分发完成，人人拿到完整结果。

理解了”同一个环，收到后累加还是直存”这一个开关，两个操作就都理解了。

### 5.1 Reduce-Scatter 的 N=4 轮次表

统一方向：卡 i 发给卡 i+1；每轮转发的是”刚累加过的那块”。

| 轮次 | 卡 0 发出 | 卡 1 发出 | 卡 2 发出 | 卡 3 发出 |
| --- | --- | --- | --- | --- |
| 第 1 轮 | 块 3 | 块 0 | 块 1 | 块 2 |
| 第 2 轮 | 块 2 | 块 3 | 块 0 | 块 1 |
| 第 3 轮 | 块 1 | 块 2 | 块 3 | 块 0 |

拿笔跟着走一遍：第 1 轮卡 1 把自己的块 0 发给卡 2，卡 2 累加（手里块 0 = 卡 1 + 卡 2 两份）；第 2 轮卡 2 把这个部分和转发给卡 3，卡 3 累加（三份）；第 3 轮卡 3 转发给卡 0，卡 0 加上自己那份——**块 0 的四卡全局和完成，且恰好留在归属卡 0 上**。其余三块同理，各自回到归属卡。

```text
每轮每卡只发一块 = 4MB
传 3 轮 → 每卡累计收发 3 × 4MB = 12MB
严格公式：每轮传 Ψ/N、传 N−1 轮 → 累计 (N−1)/N × Ψ，N 大时 ≈ Ψ
```

打个比方：4 个人各自统计了一份全国各省数据。第 i 个人只负责”第 i 个省”的最终汇总，那他只需要让其他人在”第 i 个省”上的数据流到自己这里加总，不需要收其他省的数据。

### 5.2 All-Gather 的 N=4 轮次表

同一方向；每轮转发的是”上一轮收到的那块”，第 1 轮发自己手里已完成的那块。

| 轮次 | 卡 0 发出 | 卡 1 发出 | 卡 2 发出 | 卡 3 发出 |
| --- | --- | --- | --- | --- |
| 第 1 轮 | 块 0 | 块 1 | 块 2 | 块 3 |
| 第 2 轮 | 块 3 | 块 0 | 块 1 | 块 2 |
| 第 3 轮 | 块 2 | 块 3 | 块 0 | 块 1 |

现在每张卡手里只有自己规约好的那块。第 1 轮卡 0 把块 0 发给卡 1；第 2 轮卡 1 把收到的块 0 转发给卡 2；第 3 轮卡 2 转发给卡 3——3 轮后**每张卡都集齐 4 块**，拼出完整结果。这次收到后只存不加。累计收发同样是 3 × 4MB = **12MB** ≈ Ψ。

比方：4 个人各自汇总完一个省，但每个人最终都要一份全国汇总表，于是把自己的省结果沿环传阅一遍，最后人人一份完整全国表。

【配图位 ①：环形传递示意图。4 卡围环、顺时针箭头（卡 i → 卡 i+1）；左右两栏分别画 Reduce-Scatter（收到累加）与 All-Gather（收到直存）三轮次，标注每轮每卡收发 4MB。两栏轮次编号必须与 5.1 / 5.2 两张表逐格对齐。】

### 5.3 合起来：2Ψ 是怎么来的

| 步骤 | 收到后做什么 | 每卡搬运量 | 结果 |
| --- | --- | --- | --- |
| Reduce-Scatter | 加到本地块上（累加） | Ψ（12MB） | 每卡持有自己那块的全局和 |
| All-Gather | 直接存下来（只收集） | Ψ（12MB） | 每卡持有完整结果 |
| 合计 |  | 2Ψ（24MB） |  |

**为什么这样拆**：朴素做法每卡搬 N×Ψ 量级；拆成两步环形传递后每卡只搬 2Ψ，**与卡数 N 几乎无关**——卡越多，每块越小、轮数越多，乘积不变。这就是这两个原语存在的根本理由，也是数学上 **All-Reduce = Reduce-Scatter + All-Gather** 的来历。

**最核心的一句话**：Reduce-Scatter 和 All-Gather 之所以存在，是因为每张卡最终需要”完整的、同步后的数据”，但直接让每卡都收完整数据通信量太大；拆成两步，是为了让每卡每轮只搬”自己该搬的那一份”，但通过环形传递，仍然保证最后人人拿到完整结果。

> **本节带走**：一个环形机制、一个开关（累加 vs 直存）= 两个操作；两步各搬 Ψ，合计 2Ψ，与卡数无关。

### 六、DDP：2Ψ 全花在梯度上，显存一分不省

**本节回答算法同学的问题**：为什么加卡不省显存——因为 DDP 从头到尾没打算省。

DDP（分布式数据并行）的设定：**参数和梯度都不分片**，每张卡有完整模型，也需要**完整的全局梯度**来更新完整副本。

用第四节的两个问题判断：反向算完梯度后，每卡需要完整数据（全局梯度）吗？**需要**——因为要更新完整模型。手里有吗？**没有**——只有局部梯度。所以要先规约、再人人拿完整：正好是一次 **All-Reduce**，即 Reduce-Scatter（Ψ）+ All-Gather（Ψ）。

再用两个问题核对前向：前向需要完整参数吗？需要；手里有吗？有（参数没分片）。**所以前向零通信。**

DDP 的两个特征：

- **2Ψ 全部花在梯度上**，且集中在反向传播结束后；
- **显存上没有任何节省**——每卡存着完整模型和全部训练状态。

这就是算法同学那台机器的真相：从 8 卡加到 64 卡，加的是**吞吐量**，不是**显存**。装不下的模型，加多少张卡都还是装不下。

> **本节带走**：DDP 的 2Ψ = Ψ 梯度规约 + Ψ 梯度分发，全在反向结束后；加卡加的是吞吐，不省显存。

### 七、ZeRO 要省的显存账：120GB 里的 90GB 是纯冗余

**本节回答算法同学的问题的后半**：既然 DDP 不省，那冗余到底在哪、能切多少。

玩具例子算通信账够用，但显存冗余的痛感要用真实尺寸才体会得到。这一节换成 ZeRO 论文用的 **75 亿（7.5B）参数模型**算显存账；通信账继续用 4 卡 16MB。

训练时显存里放三样东西（Adam + 混合精度）：

| 组成 | 每参数字节 | 7.5B 总量 | 8 卡 DDP 下每卡占用 |
| --- | --- | --- | --- |
| 参数（fp16） | 2 | 15 GB | 15 GB（冗余） |
| 梯度（fp16） | 2 | 15 GB | 15 GB（冗余） |
| 优化器状态（fp32 主权重 + 动量 + 方差） | 12 | 90 GB | 90 GB（冗余） |
| 合计 | 16 | 120 GB | 每卡 120 GB |

看到问题了吗：8 张卡，**每张都存完整的 120GB**，其中 90GB 的优化器状态是绝对大头，8 份一模一样，纯冗余。

ZeRO（Zero Redundancy Optimizer）的思路简单粗暴：**既然是冗余，就切开，每卡只存 1/N，需要时再临时通信拼回来**。切多少分三档：

| 阶段 | 切了什么 | 每卡显存（7.5B、64 卡） | 通信量 |
| --- | --- | --- | --- |
| ZeRO-1 | 优化器状态 | ≈ 31.4 GB | 2Ψ（与 DDP 持平） |
| ZeRO-2 | + 梯度 | ≈ 16.6 GB | 2Ψ |
| ZeRO-3 | + 参数 | ≈ 1.9 GB | 3Ψ（1.5 倍） |

（显存列为论文 Table 2 在 64 卡下的数字。）现在收益和成本都摆上桌了：**显存是 ZeRO 赚的，通信是 ZeRO 花的**。下面逐档看这笔交易。

【配图位 ③：交易账对照图。横轴三档 ZeRO-1/2/3，左纵轴柱状为每卡显存（31.4 / 16.6 / 1.9 GB，递减），右纵轴折线为通信量（2Ψ / 2Ψ / 3Ψ，前两档平、第三档跳升 1.5 倍）。视觉重点：前两档”柱子掉、线不动”= 免费午餐；第三档”柱子掉到底、线跳起来”= 收费。】

> **本节带走**：单卡训练态 120GB、大头是 90GB 优化器状态；前两档切分免费，第三档收 1.5 倍通信费。

### 八、ZeRO-1：切了东西，通信为什么还是 2Ψ

**本节回答负责人的问题的前半**：有没有不花钱的省法。

ZeRO-1 只切**优化器状态**。优化器状态是用来更新参数的——第 i 张卡只持有第 i 份优化器状态，就意味着**它只负责更新第 i 份参数**，也就**只需要第 i 份参数的全局梯度**。

用第四节的问题判断：反向后需要完整梯度吗？**不需要**——只要自己那片。所以 All-Reduce 降级为 Reduce-Scatter：

**① 反向传播后：Reduce-Scatter 梯度 = Ψ。** 玩具例子：每卡把 16MB 局部梯度参与环形规约（累计收发 12MB ≈ Ψ），只收回自己那 4MB 全局梯度。

**② 更新参数后：All-Gather 参数 = Ψ。** 每卡只更新了自己那 4MB 参数，但下一步前向需要完整模型——用问题判断：需要完整数据吗？需要；手里有吗？没有（只有一片新参数）。于是把 4 张卡各自的 4MB 拼回 16MB（累计收发 ≈ Ψ）。

合计 **Ψ梯度 + Ψ参数 = 2Ψ，和 DDP 一分不差**。这就是”免费午餐”：每卡显存 120GB → 约 31GB（省下的正是 90GB 大头），通信零增加。

两个易混细节：

- 和 DDP 的 2Ψ **构成不同**：DDP 两笔都在梯度上；ZeRO-1 是”Ψ 梯度 + Ψ **参数**“。总量相同，钱花在不同地方。
- All-Gather 发生在**参数更新之后**，是分片存储的配套动作，不属于反向传播本身。

> **本节带走**：ZeRO-1 用”参数 All-Gather”替换了 DDP 的”梯度 All-Gather”，总量仍 2Ψ，白省 90GB。

···

### 九、ZeRO-2：梯度也切了，为什么还是 2Ψ

**本节继续回答负责人的问题**：第二档要不要花钱。

ZeRO-2 把**梯度也分片**：反向中每算出一块梯度，就规约发给归属卡，然后**立刻丢掉不属于自己的部分**——反正只有归属卡要用它更新参数。

直觉上会担心：梯度边算边发、不能攒齐了一次规约，通信会不会变贵？原论文 Section 7.2.1 专门证明了不会，机制是 **bucket（分桶）策略**：每张卡的每块梯度在整个反向过程中**只被发送一次**（发给归属卡规约），总发送量仍是 Ψ；规约完成后各卡手里正是自己那片全局梯度，不需要再广播完整结果。

一步的账：**Ψ（梯度发送规约）+ Ψ（更新后 All-Gather 参数）= 2Ψ**。显存进一步降到约 16.6GB，通信依然持平。

到这里可以总结一条规律：**只要参数不分片，无论优化器状态和梯度怎么切，通信量都钉在 2Ψ**。打破这个平衡的，是 ZeRO-3。

> **本节带走**：bucket 让每块梯度只发一次；参数不分片 = 通信不涨价。

### 十、ZeRO-3：最绕的 3Ψ，多出的 Ψ 在哪

**本节回答 Infra 同学的问题**：他观察到”一步变慢”，慢的就是这一节的那 1Ψ。

ZeRO-3 走到极致：**连参数也切成 1/N，每卡平时只存自己那份**。

新问题：计算某一层时需要这一层的完整参数，但每卡手里只有 1/N。用第四节的问题判断：需要完整数据吗？需要；手里有吗？没有。所以只能**临时拼**——走到哪层 All-Gather 哪层，**算完立刻扔掉不属于自己的部分**。

逐层时序：

> **前向**：拼层 1 参数 → 算层 1 激活 → 丢弃；拼层 2 参数 → 算层 2 → 丢弃；……逐层推进<br> **反向**：再拼层 N 参数 → 算层 N 梯度 → 丢弃；……逐层回退；最后 Reduce-Scatter 梯度 → 各卡更新自己那片参数

【配图位 ②：ZeRO-3 逐层时序图。前向 / 反向两行，每层”拼参数 → 计算 → 丢弃”小方块；三色标出前向 All-Gather（Ψ）、反向 All-Gather（Ψ）、Reduce-Scatter（Ψ），图例注明合计 3Ψ = 1.5 × 2Ψ。】

三笔账（玩具例子，每笔 ≈ 16MB）：

**① 前向：All-Gather 参数 = Ψ。** 所有层走一遍，逐层拼、逐层丢，累计搬一遍整个模型。

**② 反向：再 All-Gather 一次 = Ψ。** 反向算梯度又需要每层完整参数——但前向算完就扔了，只能**再拼一次**。

**③ 反向结束：Reduce-Scatter 梯度 = Ψ。** 每卡只留自己那片，逻辑同前两档。

```text
合计 = Ψ + Ψ + Ψ = 3Ψ ≈ 48MB
3Ψ ÷ 2Ψ = 1.5 倍
```

**多出的那 1Ψ，就是”反向时把参数再拼一次”的代价。** 前向拼的为什么不留着？留着等于每卡又存完整参数，分片就没意义了。”拼完即用、用完即丢”是 ZeRO-3 显存收益的前提。

一个必须澄清的高频误解：**“通信量 Ψ”是累计搬运量，不是显存占用**。前向时显存里任意时刻只多出”当前这一层”的完整参数，其余时间只有自己的 1/N 分片。搬运是流水般累计的，占用是瞬时且很小的——这正是”显存省到极致”和”通信多花 50%“能同时成立的原因。

（小提醒：实际实现中参数 All-Gather 和释放按层 / 按 module 进行，还有 prefetch、bucket 等优化。这里只讲通信量主账。）

ZeRO-3 本质是一笔交易：**多付 50% 通信，买”一堆单卡装不下模型的卡，合力训一个巨大模型”的能力**（每卡显存降到约 1.9GB）。

> **本节带走**：3Ψ = 前向拼参数 + 反向再拼一次 + 梯度规约；多的 1Ψ 全因参数分片；搬运量 ≠ 显存占用。

### 十一、总览：通信发生在哪、花在哪

**本节把三笔账摊在一张表上**，三个人的问题在这里已经能各自找到对应格子。

| 方案 | 前向 | 反向 | 更新后 | 账本 |
| --- | --- | --- | --- | --- |
| DDP | 无 | RS + AG 梯度 | 无 | Ψ+Ψ = 2Ψ |
| ZeRO-1 | 无 | RS 梯度 | AG 参数 | Ψ+Ψ = 2Ψ |
| ZeRO-2 | 无 | 梯度边算边规约 | AG 参数 | Ψ+Ψ = 2Ψ |
| ZeRO-3 | AG 参数（逐层） | AG 参数 + RS 梯度 | 无 | Ψ×3 = 3Ψ |

（RS = Reduce-Scatter，AG = All-Gather。公众号排版建议此表做成长图。）

配合第四节的两个问题，可以提炼两条通用规律：

- **All-Gather 出现在”需要完整数据、手里只有分片”时**：ZeRO-3 前向反向各一次；ZeRO-1⁄2 更新后一次；DDP 零次。
- **Reduce-Scatter 出现在”算完局部梯度、要合成全局梯度、但每卡只需自己那片”时**：四种方案各一次，都在反向。

特别注意账本之外还有一列隐含的账：**通信多花多少，换来的是哪一部分显存被省掉**——这才是选型时真正要权衡的。

> **本节带走**：一张表看清”哪个阶段搬什么”；AG 看”要不要完整数据”，RS 看”要不要合成全局梯度”；表外还有一列”换回哪块显存”。

### 12.1 选型顺序

### 十三、收束：三层逻辑与单页速查

**第一层，目的**：每卡数据不同、梯度不同，但模型必须一致。规约保证”梯度对不对”，分发保证”梯度在谁手里”——不可省略。

**第二层，手段**：Reduce-Scatter 和 All-Gather 是同一个环形机制的两种用法（收到累加 vs 收到直存），把通信量从 N×Ψ 压到每步 ≈ Ψ。

**第三层，交易**：切优化器状态（ZeRO-1）和梯度（ZeRO-2）是免费午餐，通信钉在 2Ψ；连参数一起切（ZeRO-3），代价是反向重拼一次参数，通信涨到 3Ψ，换来多卡合力装下大模型。

一句话记住全文：

> **2Ψ 是”梯度规约 + 结果分发”的底价；ZeRO-3 多付的那 1Ψ，是为”参数分片”买的单。**

**最核心的三句话**

1. **通信是正确性前提，不是优化**：规约管”对不对”，分发管”在谁手里”。
2. **一个环形机制、一个开关**：收到累加 = Reduce-Scatter，收到直存 = All-Gather；各搬 Ψ，合计 2Ψ，与卡数无关。
3. **参数分片是唯一收费项**：ZeRO-1⁄2 白省显存，ZeRO-3 多付 1Ψ 买”合力装下大模型”。

### 十四、常见误解（八条）

| 误解 | 纠正 |
| --- | --- |
| “前向就是 All-Gather，反向就是 Reduce-Scatter” | 计算阶段和通信操作是两个维度。DDP 前向零通信；ZeRO-3 反向同时有 AG 和 RS。判断依据是”需不需要完整数据、手里有没有” |
| “Reduce-Scatter 之后每张卡还有完整梯度” | 之后每卡只有自己那片。所以 DDP 才需要再 All-Gather 梯度；ZeRO-1 不需要，因为它只更新自己那片参数 |
| “ZeRO-1 和 DDP 通信完全一样” | 通信量一样（都 2Ψ），搬的东西不同：DDP 搬”梯度 + 梯度”，ZeRO-1 搬”梯度 + 参数” |
| “ZeRO-3 反向要重新*计算*一遍参数” | 是重新搬运（All-Gather），不是重新计算。参数没变，只是前向用完丢了，反向再拼回来 |
| “ZeRO-3 每卡只存 1/N 参数，通信量应该按 1/N 算” | Ψ 始终是完整模型参数总量。存储量按 1/N 算，通信量按 Ψ 算，两者不要混 |
| “2Ψ 是整个集群一共搬了 2Ψ” | 口径是每张卡累计收发 ≈ 2Ψ（严格系数 (N−1)/N，N 大时约等于） |
| “加卡就能解决 OOM” | DDP 加卡加的是吞吐量；显存要靠 ZeRO 切冗余，或靠激活重计算压激活那本账 |
| “通信量越小越好，所以尽量用 DDP” | 通信量只是账的一边，另一边是显存。单卡装不下时 DDP 直接跑不起来，必须用 3Ψ 换显存 |

### 附录 A：自测答案与推导

**1.** DDP 的 2Ψ = Ψ 梯度 Reduce-Scatter（规约成全局梯度）+ Ψ 梯度 All-Gather（把全局梯度分发回每张卡），两笔都在**梯度**上，都发生在反向结束后。ZeRO-1 的 2Ψ = Ψ 梯度 Reduce-Scatter + Ψ **参数** All-Gather（更新后把各卡那片新参数拼回完整模型）。总量相同，第二笔钱花在不同东西上——因为 ZeRO-1 每卡只更新自己那片参数，不需要完整梯度，但下一步前向需要完整参数。

**2.** 因为 bucket 策略保证每张卡的每块梯度在整个反向过程中**只被发送一次**（发给归属卡规约），总发送量仍是 Ψ；规约完成后各卡手里正是自己那片全局梯度，而它只更新自己那片参数，**不需要再广播完整结果**。所以账是 Ψ（梯度规约）+ Ψ（更新后 All-Gather 参数）= 2Ψ。规律：**只要参数不分片，通信量就钉在 2Ψ**。

**3.** 多出的 1Ψ 是**反向传播时对参数的第二次 All-Gather**。DDP 里不存在，因为 DDP 参数根本不分片，每卡手里始终有完整参数，不需要拼。前向拼完必须丢，是因为留着等于每卡又存了一份完整参数，分片的显存收益就没了——”拼完即用、用完即丢”是 ZeRO-3 省显存的前提，代价就是反向得再搬一次。

**4.** 错在把”计算阶段”和”通信操作”当成一一对应。用两个问题反驳：反向阶段需要完整数据吗？DDP 需要（要更新完整模型），所以 DDP 反向是 RS + AG 两步，不是只有 RS；ZeRO-1⁄2 反向只需要自己那片，才只有 RS；ZeRO-3 反向既要 AG 参数又要 RS 梯度，一次反向里两种操作都有。**决定用哪种通信的是”需不需要完整数据、手里有没有”，不是”前向还是反向”。**

**5.**

```text
Ψ       = 7e9 参数 × 2 字节 = 14 GB
DDP     = 2Ψ = 28 GB
ZeRO-3  = 3Ψ = 42 GB
```

口径：**每张卡在一个训练步里累计收发**的量（严格系数 (N−1)/N = 7/8，即 DDP 约 24.5GB、ZeRO-3 约 36.75GB；N 较大时约等于 2Ψ / 3Ψ），且基于 Ring 算法、混合精度、不开 overlap 三个前提。注意 N=8 在这里不改变 Ψ 的数值——Ψ 只由参数量和字节数决定。

**6.** ZeRO-1 ≈ **31.4GB**、ZeRO-2 ≈ **16.6GB**、ZeRO-3 ≈ **1.9GB**（论文 Table 2，7.5B、64 卡）。ZeRO-1 和 ZeRO-2 是免费午餐：通信都钉在 2Ψ，与 DDP 持平。ZeRO-3 收费：通信从 2Ψ 涨到 3Ψ，即 **1.5 倍（多付 50%）**，换来每卡显存降到 1.9GB、多卡合力装下单卡装不下的模型。

### 附录 B：公式速查

```text
Ψ = 参数量 × 每参数字节数（混合精度取 2 字节）
  例：7B × 2 字节 = 14 GB；800 万 × 2 字节 = 16 MB

环形传递：每轮每卡发 Ψ/N，传 N−1 轮
        → 每卡累计 (N−1)/N × Ψ ≈ Ψ（N 大时）
朴素做法：每卡累计 ≈ N × Ψ（要避开的就是它）

All-Reduce = Reduce-Scatter + All-Gather

DDP    = Ψ(梯度 RS) + Ψ(梯度 AG)          = 2Ψ
ZeRO-1 = Ψ(梯度 RS) + Ψ(参数 AG，更新后)   = 2Ψ
ZeRO-2 = Ψ(梯度分桶规约) + Ψ(参数 AG)      = 2Ψ
ZeRO-3 = Ψ(前向 AG) + Ψ(反向 AG) + Ψ(梯度 RS) = 3Ψ = 1.5 × 2Ψ

训练态显存 = 16 字节/参数 × Ψ
          = 2(BF16 权重) + 2(BF16 梯度) + 4(FP32 主权重) + 4(m) + 4(v)
  例：7.5B → 15 + 15 + 90 = 120 GB

开通信-计算重叠（overlap）时：通信量 = KΨ（K 为参数分片份数）
```

### 附录 C：口径与前提（三个前提假设）

本文通信量数字的适用边界：

1. **Ring 环形算法**：All-Reduce 按 Reduce-Scatter + All-Gather 的环形实现计算；树形 / 层次化实现的常数不同。
2. **混合精度**：Ψ 按 fp16 / bf16 参数字节数计（每参数 2 字节）。
3. **不开通信-计算重叠（overlap）**：原论文证明开启后通信量为 KΨ（K 为参数分片份数）；本文 2Ψ / 3Ψ 对应论文的 non-overlap 基准。

另外三条口径：

- 通信量一律指**每张卡一个训练步累计收发量**，不是全网总量；严格系数为 (N−1)/N，N 大时约等于 1。
- 玩具例子（4 卡、800 万参数、Ψ=16MB、每块 4MB）用于通信账；显存账换用论文的 7.5B 模型，两套尺寸不混用，每次切换正文都会点明。
- 每卡显存 31.4 / 16.6 / 1.9GB 为论文 Table 2 在 64 卡下的数字，不含激活值；激活是另一本账（见本系列《一次大模型训练的一生》）。

### 附录 E：默写清单（十句话，标回章节）

1. 通信不是优化，是数据并行正确性的前提；规约管”梯度对不对”，分发管”梯度在谁手里”。（二）
2. 通信量口径 = 每张卡一个训练步累计收发量，不是全网总量。（三）
3. 计算阶段和通信操作是两个维度；判断用”需不需要完整数据、手里有没有”两个问题。（四）
4. RS 与 AG 共用一个环形机制，唯一区别是收到后累加还是直存。（五）
5. 每轮传 Ψ/N、传 N−1 轮 → 每卡累计 (N−1)/N × Ψ ≈ Ψ，与卡数无关；All-Reduce = RS + AG。（五）
6. DDP 的 2Ψ 全花在梯度上、全在反向结束后，且显存一分不省——加卡加的是吞吐。（六）
7. 7.5B 单卡训练态 120GB = 参数 15 + 梯度 15 + 优化器 90，优化器那 90GB 是纯冗余。（七）
8. 只要参数不分片，通信量就钉在 2Ψ；ZeRO-1 的第二笔 Ψ 花在参数 AG，ZeRO-2 靠 bucket 不涨价。（八 / 九）
9. ZeRO-3 = 前向 AG + 反向 AG + 梯度 RS = 3Ψ；多出的 1Ψ 是反向重拼参数，是搬运不是重算。（十）
10. 搬运量 ≠ 显存占用；选型看”显存缺口 + 网络带宽”，先 ZeRO-1、再 2、单卡装不下参数才 3。（十 / 十二）
