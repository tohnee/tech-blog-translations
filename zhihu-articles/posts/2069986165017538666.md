最近在看 Cursor 开源的 **Mixture-of-Kittens（MoK）**，以及把它接入 [NVIDIA NeMo AutoModel](https://github.com/NVIDIA-NeMo/Automodel) 的工作。

MoK 有意思的地方在于，它并不是再做一个更快的 `all-to-all`，而是试图重新定义 MoE layer 的执行方式：不再把 dispatch、expert GEMM、SwiGLU、combine 当成几个独立 kernel，而是把通信和计算一起塞进一个 GPU megakernel，并主动安排哪些 SM 做通信、哪些 SM 做计算。目前MoK支持DSV3 style MoE。

在把 MoK 接到真实训练框架之后，又出现了一系列 standalone benchmark 中很容易看不到的问题：padding、packed THD、state dict、shared expert，以及 DeepSeek-V4 使用的 clamped SwiGLU。这篇文章主要讨论MoK bf16的集成。mxfp8正在进行中～

## 一、MoK：把 MoE 通信和计算塞进一个 Megakernel

Mixture-of-Kittens（MoK）是 Cursor 开源的一个 MoE megakernel，目标是在 NVLink 机器上把 Expert Parallelism 的通信和 expert computation 更紧密地融合起来。

MoE 的执行通常包括：

```text
dispatch
  ↓
Gate / Up GEMM
  ↓
SwiGLU
  ↓
Down GEMM
  ↓
combine
```

现有的 DeepEP / HybridEP 已经可以通过异步通信和流水线把 communication 与 computation overlap。MoK 的不同之处，不是“第一次做 overlap”，而是进一步把这种 overlap **下沉到一个统一的 GPU megakernel 内部**。

也就是说，MoK 不再把 dispatch、expert GEMM 和 combine 看成几个彼此独立的 operator，而是在一个持续运行的 kernel 中同时安排。

为了做到这一点，MoK 在 kernel 内部显式管理几件事情：

```text
哪些 SM 用来通信
哪些 SM 用来做 GEMM
token 按什么顺序到达 expert
什么时候可以开始计算
什么时候可以复用通信 buffer
```

因此 MoK 的核心可以概括成一句话：

> **把 MoE 的 communication、expert compute 和 pipeline scheduling 一起放进一个 megakernel，让 NVLink 和 Tensor Core 尽可能同时工作。**

后面的 TMA、communication SM、schedule、minibatch 和 macrobatch ring buffer，基本都是围绕这个目标设计的。

---

## 二、为 Megakernel 设计的通信：Pull Dispatch + Push Combine

如果 MoK 想把整个 MoE 放进一个 megakernel，首先要解决的问题就是token怎样在GPU之间移动，而且通信和计算能在同一个kernel里协调起来。MoK 的一个关键设计，是把 routing 结果进一步编译成 megakernel 可以直接消费的 schedule。每个 schedule row 同时确定 expert-local 的计算位置，以及对应的 source rank 和 source route index。这样通信的目的地、expert 的计算顺序和后续 buffer layout 使用的是同一套 schedule，而不需要在独立的 dispatch、expert compute 和 combine operator 之间反复转换 layout。

这张 schedule 可以理解成一组 `[src_rank, src_index]`, 例如

```text
src_rank = 2
src_index = 381
```

表示：当前这个 routed row 的输入，需要从 rank 2 的第 381 个位置取。

因此 forward dispatch 是一种 **pull** 模式：不是 source GPU 主动把所有 token 先打包、再统一发送，而是 expert 侧根据已经生成好的 schedule，知道自己应该从哪个 peer、哪个位置读取 activation。

expert 算完以后，方向反过来。每个 routed expert output 最终还要回到 token 原来的 rank，才能做 router weighted sum。所以 forward combine 采用 **push。**backward 可以复用同一套 routing schedule。

## 三、如何把通信和计算流水起来：Minibatch + Macrobatch Ring Buffer

有了 schedule，还不代表 communication 和 computation 自然就能 overlap。

如果执行方式仍然是：

```text
把所有 token dispatch 完
        ↓
所有 expert 开始计算
        ↓
所有结果 combine
```

那本质上还是三个大阶段。

MoK 进一步把 routed token 切成较小的 **minibatch**，让整个 MoE 以流水方式推进。也就是说：

```text
MB0 正在做 expert compute
MB1 正在 dispatch
前一批结果正在 combine
```

这些工作可以同时存在。

所以 `minibatch_size` 这个参数本质上控制的是：**communication-computation overlap 的粒度。**粒度太小虽然能更早开始计算，但每次 expert grouped-GEMM 获得的 token 太少，容易产生 partial wave，并频繁在少量 MMA 后等待下一批数据，导致 Tensor Core 无法充分利用；粒度太大则需要等待更多 token 到齐才开始计算，增加 pipeline 的启动和收尾延迟。因此最优值通常位于两者之间。

但是这里又有另一个问题。

假设一个 MoE layer 一共要处理几十万 routed rows。如果为所有 routed rows 一次性分配完整的 receive/staging buffer显存开销会非常大。而且很多位置只是暂时等待被计算，并不需要整个 layer 生命周期都保留。

MoK 的做法是使用一个固定大小的 **ring token buffer**，也就是配置里的 `macrobatch_size`。

例如：

```text
macrobatch_size = 131072
```

可以把它理解成 GPU 上的一块循环 staging space：

```text
┌────────┬────────┬────────┬────────┐
│ slot 0 │ slot 1 │ slot 2 │ slot 3 │
└────────┴────────┴────────┴────────┘
```

通信把新的 token 写进去，compute 消费完以后，后面的 routed rows 又可以重新占用这块位置。这就是 ring buffer。它的作用不是改变训练 batch size，而是：**限制 MoK 为通信 staging 预留的最大物理空间，同时允许逻辑上处理远多于这块 buffer 容量的 routed tokens。**

MoK还有另一个参数`schedule_capacity_multiplier`:给 destination rank 的 schedule table 预留多少容量。因为 routing 不可能永远完全平衡，schedule 必须提前留够空间。

## 四、Standalone MoK 很漂亮，接进真实训练框架以后事情开始复杂了

这也是我觉得 AutoModel integration 最有意思的地方。因为一个 standalone kernel benchmark 可以假设：

```text
输入 shape 很漂亮
每个 rank token 数一样
没有 checkpoint
没有 padding
权重 layout 已经符合 kernel
```

真实训练框架不能这么假设。

[AutoModel PR #3422](https://github.com/NVIDIA-NeMo/Automodel/pull/3422) 增加了完整的：

- **MoK backend 接入**：支持通过 `dispatcher="mok"` 直接切换到 MoK megakernel。
- **Custom Autograd**：将 MoK 显式的 `forward/backward` 接入 PyTorch autograd，并兼容 activation checkpoint。
- **EP / FSDP 参数适配**：按 expert dimension 正确进行 EP sharding，同时适配 MoK-native expert weight layout 和初始化逻辑。
- **Checkpoint / State Dict 兼容**：训练时使用 MoK-native 权重布局，对外仍保持 AutoModel 原有 checkpoint layout，可直接加载已有模型权重。
- **Shared Expert Fusion**：复用 AutoModel 原有 shared-expert 参数，将 shared expert computation 一起交给 MoK megakernel，而不额外复制参数或单独执行 shared MLP。
- **Packed THD / Padding 支持**：padding token被当成正常token一样送入kerel。
- **MoK runtime 生命周期管理**：在 GPU rank 绑定完成后 lazy-load CUDA extension，并根据 EP mesh 初始化 process group、workspace 和 schedule。
- **模型约束与错误检查**：对 dtype、hidden/intermediate dimension、shared expert、SwiGLU、LoRA 等当前 MoK kernel 的支持范围做显式校验。

### 第一个问题：MoK 要求每个 EP rank 有相同的 dense token rows

MoK 使用 symmetric memory。这些 peer buffer 的 shape 必须一致。但真实 packed/SFT 数据可能是：

```text
rank0: 3500 valid + 596 pad
rank1: 2800 valid + 1296 pad
rank2: 4010 valid + 86 pad
rank3: 3200 valid + 896 pad
```

如果还需要满足 256 alignment，再在尾部补 alignment rows。

MoK 的 source-side buffer 按固定 `N × top-k` route slots 组织，后续 router weight reduction会按这一固定布局消费结果，因此 padding row 也需要对应到合法 route。这个 route 会做 communication 和 GEMM。

### 然后遇到了 DeepSeek-V4：原版 MoK 的 SwiGLU 不一样

AutoModel integration 做到这里以后，又出现了一个模型语义问题。

MoK 原本实现的是普通 SwiGLU：

$g=W_gx$ <br> $u=W_ux$ <br> $h=\operatorname{SiLU}(g)\odot u$ <br>但是 DeepSeek-V4 使用的是 **clamped SwiGLU**。

对于 `limit=10`：

```text
gate = clamp(gate, max=10)
up   = clamp(up, min=-10, max=10)

hidden = silu(gate) * up
```

因此：<br> $g_c=\min(g,10)$ <br> $u_c=\operatorname{clip}(u,-10,10) $ <br> $h=\operatorname{SiLU}(g_c)\odot u_c $

这不是一个 inference-only tweak。如果 forward 不 clamp，算出来的 activation 就已经不是同一个模型。而训练时问题更明显，因为 clamp 还改变 backward。所以MoK只能说能跑dsv4的shape而不是实际训练。

随机初始化 benchmark 的 gate/up activation 通常也是 O(1) 量级，而 clamp limit 是 10。

所以大量 synthetic 数据甚至根本不会触发：`gate > 10` `|up| > 10`

benchmark 可以跑得非常漂亮，但真实 pretrained/training workload 才会暴露这个 mismatch。

为了让 AutoModel 能真正验证 pretrained DeepSeek-V4-Flash，又需要继续修改 MoK 本身。

目前 [cursor/mixture-of-kittens PR #11](https://github.com/cursor/mixture-of-kittens/pull/11) 增加了 `swiglu_limit`

`swiglu_limit=0` 保持原来的普通 SwiGLU；正数启用 DSV4-style clamped SwiGLU。

使用 DSV4 MoE shape,只改变：`swiglu_limit = 0` 和：`swiglu_limit = 10` 结果：

| MoK path | Forward + Backward |
| --- | --- |
| 普通 SwiGLU | 4.0805 ms |
| Clamped SwiGLU | 4.0933 ms |
| overhead | 0.31% |

也就是说，对整个 MoE forward+backward 来说，加入 DSV4 clamp 的代价只有 **0.31%**，基本落在 run-to-run noise 范围内。

## 五、实验结果

实验主要分成两类：第一类只测单个 MoE layer 的 forward + backward，用来观察不同 routing pattern 下 kernel 本身的表现；第二类直接跑完整模型训练，看 MoK 接入 AutoModel 后能否带来真正的 end-to-end 收益。实验细节可移步[Automodel PR](https://github.com/NVIDIA-NeMo/Automodel/pull/3422).

### 1. MoE Module-level Benchmark

首先在 EP32、32 张 GB200、每卡 4096 tokens 上测试完整 MoE layer 的 forward + backward。

### DeepSeek-V3 MoE Shape

配置为 H=7168、I=2048、256 routed experts、Top-8。

| Routing | HybridEP | MoK | HybridEP / MoK |
| --- | --- | --- | --- |
| Perfectly balanced | 9.060 ms | 9.406 ms | 0.963× |
| Trainable router | 11.245 ms | 9.776 ms | 1.150× |

在完全均衡的 routing 下，两者基本持平；随着 routing imbalance 增大，MoK 更快。

### Smaller MoE Shape

另一个更小的配置为 H=4096、I=1024、128 routed experts、Top-8。

| Routing | HybridEP | MoK | HybridEP / MoK |
| --- | --- | --- | --- |
| Perfectly balanced | 3.577 ms | 3.348 ms | 1.068× |
| Trainable router | 6.123 ms | 3.513 ms | 1.743× |

因此从 module-level benchmark 可以看到，MoK 的优势并不主要体现在理想的 perfectly balanced routing 上，而是在真实 router 更容易出现的 **load imbalance** 场景下更加明显。

### 2. Full-model Training Benchmark

相比单层 MoE benchmark，更重要的是 MoK 接入完整训练栈之后是否还能保留收益。这里将完整模型实验分成两组：GLM-4.7 / Qwen3.5 这类约 30B 级 MoE，以及 DeepSeek-V3 / V4 这类大规模 MoE。

### 30B 级 MoE：GLM-4.7 与 Qwen3.5

下面统一使用真实 pretraining data 的step time结果：

| Model | Topology | HybridEP | MoK | Speedup |
| --- | --- | --- | --- | --- |
| GLM-4.7-Flash 30B-A3B | EP4, 1 node | 1.341 s | 0.894 s | 1.50× |
| GLM-4.7-Flash 30B-A3B | EP16, 4 nodes | 1.210 s | 0.885 s | 1.37× |
| GLM-4.7-Flash 30B-A3B | EP32, 8 nodes | 1.180 s | 0.899 s | 1.31× |
| GLM-4.7-Flash 30B-A3B Packed SFT, THD | EP4, 1 node | 1.630s | 1.243s | 1.31x |
| Qwen3.5-35B-A3B | EP4, 1 node | 1.919 s | 1.395 s | 1.38× |
| Qwen3.5-35B-A3B | EP16, 4 nodes | 1.887 s | 1.356 s | 1.39× |
| Qwen3.5-35B-A3B | EP32, 8 nodes | 1.785 s | 1.370 s | 1.30× |

在这两个约 30B 级的 MoE 模型上，从单节点 EP4 扩展到 8 节点 EP32，MoK 都能稳定获得 **1.30×–1.50×** 的 end-to-end training speedup。随着 EP scale 增大，收益有所下降，但在 EP32 下仍然保持约 30% 的 throughput improvement。

注意：截止发文Qwen3.5需要修改MoK支持gated shared experts。依赖branch <u>`huiyingl/feat/qwen35-shared-gate`</u> （将来可能upstream）

我也同时做了packed SFT的实验。在真实 packed SFT 场景中，AutoModel 需要额外处理 padding，将其转换成 MoK 可接受的 zero-weight dummy routes。相比 full-length sequence，这会引入额外的无效 dispatch / expert compute，因此会削弱部分性能收益。

在 GLM-4.7 + `tulu-3-sft-mixture`、EP4、4096-token THD packing 下，HybridEP 为 1.630 s/step，MoK 为 1.243 s/step，二者的loss保持一致证明MoK路径的正确性，同时MoK获得 **1.31× speedup**。

### 大规模 MoE：DeepSeek-V3 与 DeepSeek-V4

进一步把模型规模扩大到 DeepSeek-V3 / V4：

| Model | Topology | HybridEP | MoK | Speedup |
| --- | --- | --- | --- | --- |
| DeepSeek-V3 671B-A37B | EP64, 16 nodes / 64×GB200 | 6.943 s | 6.485 s | 1.071× |
| DeepSeek-V4-Flash | EP32, 8 nodes / 32×GB200 | 3.573 s | 3.337 s | 1.071× |

DeepSeek-V3 使用完整的 61-layer 671B-A37B architecture，在 EP64、64 张 GB200 上训练；MoK 将 iteration time 从 **6.94 s 降到 6.48 s**。DeepSeek-V4-Flash 则使用官方 pretrained model，在 EP32、32 张 GB200 上将 iteration time 从 **3.57 s 降到 3.34 s**。

两组超大模型上的收益都非常接近 **1.07×**。相比 30B 级模型，这个提升幅度更小。

综合来看，MoK 在 30B 级 MoE 上可以带来约 **1.3×–1.5×** 的 full-model speedup；扩大到 DeepSeek-V3/V4 这样的超大 MoE 后，仍然能够保持约 **1.07×** 的 end-to-end 收益。

## 最后，MoK 不是免费午餐，mxfp8 MoK in Automodel coming soon

从当前 integration 也能看到几个非常明确的 trade-off：

- target DSV3 moe结构，支持model有限
- EP size 最大64
- equal token extent
- shared-expert structure
- peak memory 略高
