## overview

相较NV/AMD的gpu设计，950给笔者一个最直观的印象是其更加的asic化，有更多专用buffer，更多专用数据移动单元，专用化一定程度上限制了灵活性，但也可以带来功能单元设计上的简化和高性能

- 取消了GM->L0A/L0B 的直通路径
- 有较多专用单元用来完成 Cube/Vector之间的数据互传 -> asic 化
- layout transform 是计算 pipeline 的一等公民,data movement engine 本身承担了一部分 datatype/layout epilogue

## wave specailization

[fp8_dequant_gemm.hpp at main · deepseek-ai/DeepGEMM-Ascend](https://github.com/deepseek-ai/DeepGEMM-Ascend/blob/main/deep_gemm/include/deep_gemm/fp8_dequant_gemm.hpp?utm_source=chatgpt.com)

AIV0 : input preprocess / dequant / layout<br>AIC : Cube GEMM<br>AIV1 : output epilogue

这是一个很有意思的地方，NV/AMD的设计中和相关框架越来越明显的体现出warp specialization重要性，从而更加方便的实现软件流水的灵活控制。而nv/amd的指令架构下，是一个统一指令级，dma/vector/tensor 全部在scheduler加码并分发， wave/warp specialization 本质上是通过显示控制将其将work load 放在不同的执行队列中(参见[warp/wave specailization的本质](https://zhuanlan.zhihu.com/p/2086508110651437427))。他们是共享前段的！

在950架构下，tensor、vector指令天然是两套指令解，各自的分发和执行有自己的scalar负责。在这种情况下，从DeepGEMM-Asend的实现可以看出，其是将软件流水显示的编排到两个VIC上，也实现了同样的功能，不过这里的控制粒度更粗 core级，且两个VIC各自有自己的分发，调度，加码前段。调度上也完全需要软件的显示编排。但这个流水因为是完全独立的多套硬件，所有可供完全并发执行！在通过各专用数据搬移单元，强化了vector/tensor之间的数据通路，**我好想看到了一个可重构硬件pipeline！**

而在nv/AMD 形式的 wave/warp specialization 框架下，多个wave/wrap 天然是时分复用执行单元的，但其调度有硬件scheduler实现自动切换，所有这里更适合相对轻量级的软件流水。

而在较大负载的软件流水中，NV/AMD 都不约而同的走向了 cluster 中多 SM/WGP的独立task分配，这个场景下每个task对于一个SM/WGP，是完全独立的硬件，可以并发执行。但这个相较950的2个AIV+AIC的流水编排更重一些。一个原因是虽然在nv/AMD的单 SM/WGP中有多个 subcore (cuda core/ simd)， 但如前面所说，其共享调到，实际那个任务分配到那个 subcore上是纯硬件行为，目前是黑盒完全不可控！因为没有包括 coda core id 、 simd id给软件，仅暴露了wave id， 因而只能走wave/warp specialization!

而这其实也给了我们一个启示：暴露硬件执行单元id，在nv/amd架构下，可以通过 介于 wave specialization， cluster specialization 之间的控制力度！

FlashMLA / deepGEMM-Asend 中很多都涉及到vector 在数据预处理中的关键作用！
