**文章名字:**Efficient Memory Management for Large Language Model Serving with PagedAttention

**作者与机构:**Woosuk Kwon (UC Berkeley), Zhuohan Li (UC Berkeley), Siyuan Zhuang (UC Berkeley), Ying Sheng (Stanford University), Lianmin Zheng (UC Berkeley), Cody Hao Yu (Independent Researcher), Joseph E. Gonzalez (UC Berkeley), Hao Zhang (UC San Diego), Ion Stoica (UC Berkeley)

**期刊与会议:**ACM Symposium on Operating Systems Principles (SOSP '23) - 计算机系统顶级会议

**论文类型:**System / Method

**一句话定位:**大语言模型服务系统中划时代的显存管理优化方案，奠定了高并发LLM推理服务底座。

## 一、 完整摘要 (The Perfect Abstract)

**问题：**大语言模型（LLM）的高吞吐服务要求在同一批次（Batch）中处理足够多的请求。然而，现有的推理引擎因KV Cache（键值缓存）占用空间巨大且动态增长，面临严重的显存碎片化与重复冗余拷贝问题，导致批处理量（Batch Size）受到极大限制。

**方法：**提出PagedAttention算法，其灵感源于经典操作系统中的虚拟内存与分页机制。PagedAttention将请求的KV Cache划分为非连续的物理显存块，并在其上构建了vLLM分布式LLM推理引擎，以实现准零浪费的显存管理以及跨请求的灵活显存共享。

**贡献：**1. 定量分析并指出了现有系统由于 contiguity（连续存储）约束导致的严重碎片浪费；2. 提出了在非连续物理内存上进行注意力计算的PagedAttention算法；3. 设计并实现了支持Megatron-LM风格张量并行的分布式推理系统vLLM；4. 实现了块级别的写时复制（Copy-on-Write）以及前缀共享技术。

**结果：**在相同的延迟水平下，vLLM将主流大模型（如OPT、LLaMA）的吞吐量提升了2至4倍。在大模型、长序列以及复杂解码策略（如束搜索 Beam Search、多样本采样）的场景下，性能提升尤为显著。

## 二、 知识背景全景 (Background & Context)

**前置概念：**1.**KV Cache：**在自回归Transformer模型的解码阶段，每个生成Token都要与其历史Token of Query进行注意力运算。为了避免重复计算，系统会将历史Token的Key and Value向量缓存起来。2.**自回归生成阶段（Autoregressive Phase）：**LLM生成是以Token为单位顺序进行的，每次迭代仅生成一个新Token并产生新的KV Cache，这导致该阶段呈强烈的Memory-bound（显存带宽瓶颈）特性。3.**迭代级调度（Iteration-level Scheduling）：**传统的请求级批处理效率极低。迭代级调度（如Orca系统）在每个Step计算结束时动态移除已完成请求并加入新请求，极大地提升了GPU利用率。

**赛道全景：**在LLM部署成本高企的行业背景下，提高单卡推理吞吐量是核心诉求。当前优化路线主要分为两派：一派侧重于算子融合与计算硬件级优化（如FasterTransformer、FlashAttention）；另一派则侧重于动态调度与流水线管理（如Orca）。这篇论文正处于调度派与显存优化管理派的结合点上。vLLM并不改变注意力运算的数学本质，而是重构了显存分配逻辑，使得更细粒度的迭代级调度能够真正落地。

**出现契机：**随着大模型商用落地的爆发（如ChatGPT等应用），云服务商面临着极高的硬件成本。GPU算力的提升（如从A100到H100，算力提升2倍以上）远快于显存容量的增长（最大显存依旧为80GB）。显存容量（Memory Wall）而非算力成为了限制大模型并发吞吐的最大瓶颈，亟需底层系统级别的内存管理革命。

## 三、 痛点与动机 (Problem & Motivation)

现有主流方案面临的核心技术瓶颈在于**显存的连续性限制与序列长度的不可预测性**。由于深度学习框架（如PyTorch）默认要求张量存储在连续的显存空间内，先前的系统（如FasterTransformer和Orca）不得不为每个请求预先分配一块足以容纳模型最大输出长度（如2048）的连续显存。

图 2：主流大模型推理服务引擎在运行过程中的各类显存浪费占比定量分析（包含已预留、内部碎片与外部碎片）。

这种粗暴的静态分配引入了三大显存浪费痛点：

1. **预留显存浪费（Reservation）：**即使实际只生成了几个Token，系统也必须提前占有未来全部Token所需的显存，导致大量槽位长期空闲且无法被其他请求利用。
2. **内部碎片（Internal Fragmentation）：**由于请求的实际生成长度往往远小于最大预测长度，多余预配的连续空间在请求结束前成为无法回收的物理死区。
3. **外部碎片（External Fragmentation）：**不同长度请求频繁动态申请与释放大小不一的连续显存块，会导致内存分配器产生大量无法被再次拼接的显存碎片。

图 3：传统LLM推理系统由于连续存储空间（Contiguous）约束所导致的Reserved、Internal及External显存碎片化浪费机制示意。

正如系统分析图2所示，在现有大模型推理系统中，真正用于存储 Token 显存状态的有效物理显存仅占**20.4% - 38.2%**，其余近 60% 至 80% 的宝贵显存均被这三种碎片垃圾白白吞噬。这促使作者借鉴操作系统的虚存管理方案来根治此系统顽疾。

### 3. 多种解码场景下的显存共享与写时复制（Copy-on-Write）

在并行采样（Parallel Sampling）和束搜索（Beam Search）等高级解码场景中，vLLM 的非连续映射发挥了巨大威力。因为不同候选序列共享相同的 Prompt，系统通过将它们的逻辑块映射到同一个物理块上来实现显存共享。

图 8：在并行采样（Parallel Sampling）解码模式下，共享 Prompt 的逻辑块通过写时复制（Copy-on-Write, CoW）进行物理分裂的动态过程。

每个物理块都具有一个引用计数（Reference Count）。如图8所示，当样本序列 A1 试图修改某个被共享的物理块时（例如新生成 Token 写入），如果该块引用计数大于1，系统将触发 Copy-on-Write 机制：在 GPU 内存中分配一个新的物理块，复制原块内容，将旧块引用计数减 1，并更新 A1 的块表映射指向新物理块。而 A2 则可以无影响地继续写入原物理块。

图 9：在束搜索（Beam Search）多分支解码策略下，逻辑块的物理共享树结构与引用计数（Reference Count）变化轨迹。

### 4. 共享前缀（Shared Prefix）机制

在少样本提示词（Few-shot Prompting）或固定系统说明的场景下，不同的请求通常包含完全相同的系统提示词前缀。vLLM 允许服务提供商提前将这些共享提示词的 KV Cache 缓存并在物理显存块上锁定（类似于 OS 加载共享动态链接库的形式），新进入的请求只需将自身的头部逻辑块指向这些锁定物理块即可，省去了对前缀的重复计算和物理显存浪费。如图10展示了机器翻译中多序列共享前缀的物理映射。

图 10：机器翻译等少样本/系统提示词场景中，多条不同请求链对公共提示词前缀的物理显存块共享与复用机制。

### 5. 换入换出（Swapping）与重计算（Recomputation）抢占机制

当突发流量超出物理显存池时，vLLM 会对请求进行抢占。由于推理请求具有“全或无（All-or-nothing）”的执行属性，抢占在序列组（Sequence Group）粒度上整体发生。vLLM 包含两种抢占策略：一是将淘汰块交换（Swapping）到主机 CPU 内存的物理块中；二是直接丢弃，在调度重新就绪时重新计算（Recomputation）KV Cache。

### 6. 分布式执行与张量并行集成

大语言模型在多 GPU 分布式部署时采用 Megatron-LM 风格的张量并行（Tensor Parallelism）。各 GPU 进程独立计算其负责的注意力头（Attention Heads）。但由于每张卡上处理的 Token 位置和批次是完全对齐的，vLLM 将显存映射管理器集中在 Scheduler 中，各物理 GPU Worker 共享同一套块表索引，各自维护分片头部的物理显存。

## 五、 实验 (Highlights & Key Takeaways)

**实验配置：**实验基于 Google Cloud Platform 上的 A2 虚拟机（配备 NVIDIA A100 GPU）。测试模型涵盖 OPT (13B/66B/175B) 和 LLaMA (13B)，数据源来自真实的对话数据集 ShareGPT 和指令生成数据集 Alpaca。Baselines 包括高带宽延迟优化的 FasterTransformer 以及业界领先的吞吐量调度引擎 Orca（细分为 Oracle、Pow2、Max 三个版本）。

**定量分析与局限性评估：**从表1的参数分布可以看出，虽然大模型的层数和尺寸在剧烈扩张，但单卡可供 KV Cache 驻留的空间非常紧凑。在 13B 模型中，仅有 12GB（30%）的显存分配给 KV Cache；而在 66B 的多卡环境下，由于模型并行通信与切片开销，仅有 21GB（13.1%）的显存可用，这使得对这些剩余空间的精细化管理显得尤为迫切。同时需要注意到：vLLM 的高吞吐特性高度依赖于对“剩余 KV 缓存”的频繁动态分配与垃圾回收逻辑。若请求并发极端异常或内存耗尽，系统频繁触发物理块的 Recomputation，将引入可达 20% 左右的延迟，产生一定的长尾延迟抖动。

在大批量基础单样本采样生成中，由图12可以看出，在 ShareGPT 数据集上，vLLM 的推理服务吞吐能力达到了 Orca (Oracle) 的**1.7x - 2.7x**，是 Orca (Max) 的**2.7x - 8x**。由于 FasterTransformer 缺乏细粒度调度和内存回收策略，vLLM 相比 FT 实现了高达**22x**吞吐速度提升。

### 2. 内存共享节省量化

在支持高级解码场景时，共享 KV 块能够极大地降低系统开销并提高吞吐性能。图14展示了在并行生成（Parallel Generation）与束搜索（Beam Search）模式下，vLLM 相比基线系统取得了多倍的吞吐速率改善。

## 六、 极客评分 (Geek Evaluation)

**创新性 (9/10)：**将经典的操作系统虚存分页机制直接迁移应用于当前前沿的大模型 KV Cache 痛点。这种用跨学科经典系统理论重谱推理底层边界的思路极具美感，摆脱了单纯在计算库算子级别进行微调的传统思维局限。

**️ 实用性 (9.5/10)：**由于解除了连续空间约束，vLLM 完全屏蔽了显存碎片问题，将单卡并发吞吐直接拉升数倍。虽然在单个 Attention 核上带来 20%+ 的开销，但在全局并发批处理的压倒性优势下这微不足道。该方案极其易于工程实现，并具有优秀的易用性，目前已被整个开源大模型社区广泛采用，成为了 LLM 推理事实标准底座。

**️ 行业价值 (10/10)：**作为解决“大模型落地显存墙”的核心敲门砖，vLLM 极大地降低了大模型在云端线上服务的部署硬件门槛。它为多采样交互式 Chatbot、并行 Agent 派生等多条技术链条的生产落地打通了显存资源瓶颈，直接推动了行业大模型推理商业化变现与平民化普及进程。
