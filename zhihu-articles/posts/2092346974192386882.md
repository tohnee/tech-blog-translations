## 一、概述

人们经常会问， **agent-skills** 与另外两个广为人知的“面向编程智能体的 Skills 集合”有什么关系： **Superpowers** （Jesse Vincent / obra）和 **Matt Pocock's skills** 。

这三个项目都很优秀，具有许多共同的设计理念，也都值得学习。

本文旨在客观梳理它们在整体设计上的差异，帮助你选择最适合自己工作方式的框架，或者从三个项目中分别借鉴有价值的实践。

### 核心结论

三个框架针对软件开发过程中的不同需求进行了优化。

- **agent-skills** ：围绕完整产品生命周期组织 Skills，覆盖定义（Define）、规划（Plan）、构建（Build）、验证（Verify）、评审（Review）和发布（Ship）。它引入了专业评审角色、防止智能体为跳过流程寻找借口的约束机制，以及内置的评测框架（Eval Framework），用于检查 Skills 是否被正确触发、路由和执行。
- **Superpowers** ：侧重于自主运行和深度推理，采用子智能体（Subagents）、严格的开发流水线，以及 Git Worktree 工作区隔离机制，适合长时间运行的复杂开发任务。
- **Matt Pocock's skills** ：源于一位资深工程师的日常 Claude Code 工作实践，是一套针对性强、具有鲜明个人方法论的工具集。其标志性能力是 `grill-me` ，即通过持续、深入的提问澄清需求。

从抽象意义上说，没有哪个框架绝对最好。选择取决于当前工作的性质。

## 二、三个框架一览

| 对比维度 | agent-skills | Superpowers | Matt Pocock's skills |
| --- | --- | --- | --- |
| 核心理念 | 将资深工程师的完整开发生命周期编码为 Skills | 基于可组合 Skills 构建完整的软件开发方法论 | 将个人 Claude Code 工作流开源，并持续迭代 |
| 组织原则 | 按软件开发生命周期（SDLC）阶段组织，由元 Skill 负责路由 | 单一、严格的循环：头脑风暴、规划、执行、评审 | 精心筛选、可组合的专用命令工具箱 |
| Skills 数量 | 25 个，覆盖完整生命周期 | 约 14 个，深入开发内部循环 | 约 30 个，分为工程、生产力、开发中、已弃用等类别 |
| 生命周期覆盖 | 广泛：需求完善、API/UI 设计、安全、性能、CI/CD、可观测性、弃用管理、架构决策记录、发布 | 深入但范围较窄：TDD、调试、规划、评审、Skill 编写 | 侧重定义和构建：需求追问、PRD、Issue、TDD、架构、Bug 分类、知识管理 |
| 入口方式 | /spec、/plan、/build、/test、/review、/code-simplify、/ship、/webperf，以及完整计划自动执行模式 /build auto | Skills 串联的流水线：brainstorming、writing-plans、subagent-driven-development | /grill-me、/tdd、/to-prd、/diagnosing-bugs、/grill-with-docs |
| 独特机制 | 防止合理化借口的约束表、红旗警示、并行评审角色、参考检查清单、三级评测框架 | 子智能体驱动开发、任务评审、修复闭环、Git Worktree 隔离、经过压力测试的 Skill 编写方法 | 逐题深度追问、基于系统边界的 TDD、用户主动调用与模型自动调用的 Skills 区分、Issue 跟踪集成 |
| 质量衡量 | 对触发、路由和行为进行评测，部分在 CI 中执行 | 压力测试是核心理念，评测套件现已移至独立仓库 | 仓库内未提供评测体系 |
| 工具兼容性 | Claude Code、Cursor、Gemini CLI、Antigravity、OpenCode、Windsurf、Copilot、Kiro、Codex、Command Code，以及 npx skills CLI | Claude Code、Codex、Cursor、Copilot CLI、OpenCode、Kimi、Factory Droid、Antigravity、Pi 等，兼容范围广且更新频繁 | 以 Claude Code 为主，通过 npx skills add 分发，其他智能体的兼容程度不一 |
| 治理方式 | 主动评审并合并社区贡献，每个 Skill 都附带评测 | 主要由个人维护，积压了较多尚未合并的社区 PR | 个人维护、个人合并，公开开发 |
| 最适用场景 | 推动一个功能经过完整开发生命周期，每阶段设置人工检查点 | 长时间运行、自主性高、需要深度推理或探索的工作 | 经过实践验证的日常开发工作流，尤其擅长需求澄清和 TDD |

## 三、从项目自身的角度理解三种框架

### 3.1 Superpowers（obra）

Superpowers 是一套基于可组合 Skills 构建的完整软件开发方法论。它的核心理念是： **自主执行与前置深度推理** 。

一个完整开发会话按照精心设计的线性流水线运行。

**第一阶段：苏格拉底式头脑风暴**

通过持续提问澄清需求，形成一份带日期的需求规格文档，并且只允许一次明确的任务交接。

**第二阶段：详细规划**

将需求转化为详细、可执行的开发计划。其规划标准非常有代表性：

> 要让一个“充满热情、审美很差、完全没有上下文的初级工程师”也能够执行这份计划。

这意味着计划必须足够具体，尽量消除模糊空间。

**第三阶段：子智能体驱动执行**

每项任务都由一个全新的子智能体负责实现。任务完成后，由评审智能体同时检查两个方面：

1. 是否符合需求规格。
2. 代码质量是否达标。

如果发现问题，则进入修复循环，直到通过评审。

**第四阶段：整分支评审**

全部任务完成后，使用能力最强的模型对整个代码分支进行最终评审。

Superpowers 还使用 Git Worktree 隔离并行工作，防止多个任务互相干扰。

其 `writing-skills` Skill 甚至把测试驱动开发（TDD）理念应用到了文档和 Skill 编写本身： **任何 Skill 在发布前，都必须先有一个会失败的测试。**

### 优势与代价

Superpowers 的优势非常明确：你可以将一个规模较大的开发任务交给它，之后拿到经过规格符合性和代码质量评审的结果。它也通过严格的流程约束，降低智能体为跳过必要步骤寻找理由的风险。

但这种纪律性也带来了代价：

- 覆盖范围相对有限，主要面向开发内部循环，尚未形成从安全审查到上线发布的完整生命周期体系。
- 单一流水线对小型修改可能显得过于繁重。
- 最近的演进方向之一，就是降低这些流程成本。例如，将多个评审环节合并为单一任务评审者，使速度大约翻倍，Token 消耗降低约一半。

社区呼声最高的能力之一是 **多智能体团队协作执行** ，但目前尚未作为框架内置能力提供。

**项目仓库** ： [https://github.com/obra/superpowers](https://github.com/obra/superpowers)

### 3.2 Matt Pocock's skills

Matt Pocock 将自己实际使用的 Claude Code Skills 开源，逐步形成了一套覆盖面较广、具有鲜明个人风格的工具箱。

整个项目在公开环境中持续演进，还保留了清晰的 `in-progress/` （开发中）和 `deprecated/` （已弃用）目录。这些目录本身也体现了 Skills 所倡导的工程纪律。

它的核心并非 TDD，而是 **Grilling（深度追问）** 。

这是一套可复用的需求追问机制：

1. 每次只提出一个问题。
2. 沿着设计决策树逐个分支深入。
3. 按照依赖关系顺序解决问题。
4. 每个问题都提供一个推荐答案。
5. 优先阅读现有代码库，而不是直接询问用户。
6. 在双方确认理解一致之前，不进入下一阶段。

`grill-me` 和 `grill-with-docs` 实际上是这一机制的轻量封装。

其 TDD Skill 也具有鲜明特点，甚至有些不遵循传统做法。例如，它认为：

> 重构不属于 TDD 循环，而应放在代码评审阶段。

此外，该项目明确区分：

- 用户主动调用的 Skills（User-invoked Skills）。
- 模型自动调用的 Skills（Model-invoked Skills）。

这种区分体现出一个重要设计原则： **智能体的上下文窗口是一种稀缺资源，必须合理管理。**

### 优势与代价

Matt Pocock's skills 的优势在于真实性和针对性。它体现的是一位优秀工程师实际如何交付软件，而非由委员会设计出来的一套理论框架。尤其值得肯定的是，它的需求深度追问机制非常出色。

局限性包括：

- 实际上优先面向 Claude Code，其他智能体可能存在兼容性和稳定性问题。
- 仓库内没有评测体系，无法自动检测 Skills 的行为回归。
- 对 Build（构建）之后的软件生命周期覆盖较少。
- 某些 Skills 与作者个人的初始化向导及任务跟踪约定存在耦合。

近期的工作正尝试从单会话 Skills 走向跨会话编排。例如，正在开发中的 `wayfinder` ，尝试通过 Issue Tracker（问题跟踪系统）支持多会话任务协调。

项目仓库： [https://github.com/mattpocock/skills](https://github.com/mattpocock/skills)

相关项目： [https://github.com/mattpocock/agent-rules-books](https://github.com/mattpocock/agent-rules-books)

### 3.3 agent-skills（本文所属项目）

agent-skills 将 **整个产品生命周期** 组织为一组 Skills，并通过元 Skill `using-agent-skills` 将任务路由到正确的 Skill。

每个 Skill 都包含两类特殊机制。

**第一类：Common Rationalizations（常见合理化借口）**

记录智能体可能用来跳过某一步骤的理由，并为每一种理由提供反驳。

**第二类：Red Flags（红旗警示）**

列出执行过程中需要警惕的行为或信号。

Slash Commands（斜杠命令）与生命周期阶段一一对应。例如：

- `/spec` ：需求规格
- `/plan` ：实施规划
- `/build` ：构建
- `/test` ：测试
- `/review` ：评审
- `/ship` ：发布

其中， `/build auto` 可以在一次运行中执行整个已批准的计划。

`/ship` 会并行启动多个专业评审角色：

| 评审角色 | 职责 |
| --- | --- |
| code-reviewer | 代码评审 |
| security-auditor | 安全审计 |
| test-engineer | 测试工程 |
| web-performance-auditor | Web 性能审计 |

这些评审结果最终会被合并，形成 **Go / No-Go（允许发布 / 不允许发布）** 决策。

agent-skills 默认在每个阶段保留人工检查点。项目还包含七份参考检查清单，其中包括 Definition of Done（完成定义，DoD）。

它可以运行在大多数主流智能体工具上，并支持在多个平台通过单条命令安装。

### 核心差异：三级评测框架

目前较新的设计，也是 agent-skills 的主要差异化能力，是仓库内置的三级 Eval（评测）框架。

| 层级 | 类型 | 评测内容 |
| --- | --- | --- |
| Tier 1 | 结构评测 | 确认 Skill 的结构符合要求。 |
| Tier 2 | 描述与路由评测 | 检查 Skill 描述是否包含用户真实使用的表达方式，以及两个 Skills 是否存在路由冲突。这一层采用确定性评测，在持续集成（CI）中执行。 |
| Tier 3 | 行为评测 | 根据每个 Skill 的预期行为，对智能体的真实执行轨迹进行评分。 |

目前，另外两个框架都没有在自身仓库内提供这种覆盖整个 Skills 目录的评测体系。

当然，agent-skills 也有自身的权衡。与 Superpowers 相比，它缺少一套同样鲜明、统一且高度约束的完整执行流程。此外，三个框架都尚未很好地解决持久化跨会话记忆问题。

## 四、真实对比实验：Superpowers vs. agent-skills

Om Mishra 曾进行过一项受控实验。

实验中，他在 Claude Code 中保持以下条件一致：

- 相同的模型。
- 相同的代码仓库。
- 相同的提示词。

唯一改变的变量是 Skill 框架。

实验记录发表在文章： [Superpowers vs Agent-Skills: Faster Shipping, Safer Reasoning](https://www.linkedin.com/pulse/superpowers-vs-agent-skills-faster-shipping-safer-reasoning-om-mishra-dzakf/) 。

中文标题：《Superpowers 与 agent-skills：更快的交付与更稳健的推理》。

### 实验结果

| 指标 | agent-skills | Superpowers |
| --- | --- | --- |
| 进入编码阶段所用时间 | 约 8 分钟 | 约 12 分钟 |
| 验证轮次 | 7 次 | 5 次 |
| 验证范围 | 更广，包含完整测试套件 | 更侧重当前功能 |
| 架构推理 | 相对较少 | 更重视前置架构思考 |
| Token 效率 | 基本相同 | 基本相同 |
| 重新规划次数 | 1 次 | 1 次 |

agent-skills 更快进入编码阶段，并执行了更多轮验证。更广泛的验证还发现了一个当前功能之外的兼容性问题，而仅针对该功能的测试并未发现这一问题。

因此，实验作者认为，在该任务中，agent-skills 在 **验证深度** 方面更有优势。

另一方面，Superpowers 在开发前投入了更多架构推理。作者本人仍然更倾向于将 Superpowers 作为日常主力工具，尤其是在演进生产系统、或者探索没有既定模式可遵循的任务时。

需要明确的是： **这只是一个开发者针对单项任务开展的实验，不能视为标准化基准测试（Benchmark）。**

但它具体展示了两种方法之间的核心权衡： **广泛而严格的验证，与投入更多前置架构推理。**

## 五、如何决定使用哪个框架

概览表说明了三个框架的基本设计差异。下面进一步讨论如何在实践中做出选择。

### 5.1 首先判断工作类型

**场景一：开发一个完整功能，从需求到发布**

推荐： **agent-skills** 。

在三个框架中，它是唯一能够从需求规格一路覆盖安全、性能和发布的框架。每个阶段都设置检查点，避免评审或上线前检查被悄悄跳过。

**场景二：一个大型、模糊的任务，希望交给智能体自主完成**

推荐： **Superpowers** 。

其开发流水线和子智能体评审机制专门支持长时间运行，并最终交付已经对照规格完成评审的结果。

**场景三：快速、聚焦的日常开发，尤其需要在编码前明确需求**

推荐： **Matt Pocock's skills** 。

其 Grilling 深度追问机制是三个框架中最突出的需求澄清工具，而且整体工具箱对工作流程的干扰较少。

### 5.2 其次，按照真正关心的能力进行选择

| 重点关注能力 | 推荐框架 | 原因 |
| --- | --- | --- |
| 生命周期覆盖广度 | agent-skills | 覆盖安全、性能、CI/CD、可观测性和发布 |
| 长时间自主运行 | Superpowers | 从设计之初就针对这一需求优化 |
| 小型修改的低流程负担 | Matt Pocock's skills | 最轻量 |
| 验证 Skills 自身是否有效 | agent-skills | 仓库内具备覆盖整个目录的评测机制 |
| 需求深度追问 | Matt Pocock's skills | Grilling 是代表性实现 |
| 跨平台兼容 | agent-skills、Superpowers | 两者都支持广泛的智能体工具 |
| 每阶段人工检查 | agent-skills | 默认设置人工检查点 |
| 减少执行过程中的人工干预 | Superpowers | 有意减少运行中途的反复确认 |

对于小型修改：

- Matt Pocock 的工具箱负担最轻。
- agent-skills 提供了中间方案，例如直接执行 `/test` 和 `/review` 。
- Superpowers 的流程相对最重。

关于 Skills 自身的可靠性：agent-skills 是三个框架中唯一在仓库内提供整个目录级评测的项目。因此，如果某个 Skill 的描述或路由出现回归问题，可以通过 CI 失败及时发现，而不用等到用户困惑地询问：“为什么这个 Skill 没有被触发？”

关于需求深度追问：Matt Pocock 的 Grilling 是参考实现。agent-skills 中的 `interview-me` 在理念上非常接近，而且正在增加可选的协作模式。

### 5.3 具体场景

| 实际任务 | 推荐选择 | 理由 |
| --- | --- | --- |
| 发布一个带身份认证的新 API 接口，要求合并前完成测试和安全检查 | agent-skills | 从 /spec 到 /ship，最后并行启动安全审计和测试角色 |
| 对一个复杂子系统进行大规模重构，次日检查结果 | Superpowers | 交付计划后，由子智能体执行并完成任务评审 |
| 只有一个模糊想法，智能体经常自行猜测需求 | Matt Pocock's grill-me，或 agent-skills 的 interview-me | 编码前先明确真实意图 |
| 修复一个明确的 Bug，并且采用测试先行方式 | 三者均可 | 优先使用已经安装的最轻量工具 |
| 在团队内统一智能体开发标准 | agent-skills | 阶段命令、评审角色、共享清单和评测形成统一标准 |
| 自己开发 Skills，并希望确保能够正确触发 | agent-skills | 可结合 Superpowers 的压力测试方法强化关键 Skills |

### 5.4 个人开发与团队开发的差异

对于个人开发者而言，个人偏好和工作节奏更重要。选择默认行为与你现有工作方式最契合的框架即可。通常，流程负担最低的方案，也更容易被频繁使用。

但对于团队而言，选择标准会发生变化。

团队更需要共享的结构和可强制执行的约束机制，例如：

- 命名统一的开发阶段。
- 专门的评审角色。
- 标准化检查清单。
- 能够使 CI 失败的自动评测。

这些机制可以保证五位工程师以及他们各自使用的智能体遵循相同标准，避免演变为五套互不兼容的私人工作流。

这正是 agent-skills 的主要设计目标。不过，团队也完全可以在 agent-skills 体系内采用 Superpowers 的评审纪律，或者 Matt Pocock 的需求追问机制。

### 5.5 三个框架共同面临的前沿问题

三个框架都尚未很好地解决 **Durable Cross-session Memory（持久化跨会话记忆）** 。

智能体在一个会话中学到的内容，往往无法可靠地传递到下一个会话。

三个项目都在探索相关方案，包括：

- Learnings Files（经验学习文件）。
- Handoff Artifacts（任务交接产物）。
- Tracker-backed Planning Maps（由任务跟踪系统支撑的规划映射）。

如果跨会话记忆正是你的主要瓶颈，那么你需要意识到：目前三个框架提供的能力都尚不完整，你可能需要自行整合一部分基础设施。

## 六、组合使用三个框架

你不一定必须三选一，但组合使用时需要谨慎。

这些框架本质上是 Markdown Skills 集合，并非独立的运行时（Runtime）。因此，选择性地组合 **单个 Skills** 通常是可行的。

例如：

- 从 Matt Pocock 的工具箱中引入 `grill-me` 。
- 借鉴 Superpowers 的工作区隔离模式。
- 在主框架中加入某个具体的检查清单。

### 不推荐的组合方式

**不要同时启用两个框架的主路由器（Active Router）。**

原因包括：

1. 多个元 Skills 可能争夺相同命令名称，例如两个框架都定义了 `/tdd` 。
2. 不同框架的任务路由逻辑可能互相冲突。
3. 各框架可能采用不同的 TDD 方法论。

最终容易产生不可预测的行为，无法获得预期中的最佳组合效果。

### 推荐方案

**选择一个框架作为主要路由器，再有选择地引入其他框架的独立 Skills。**
