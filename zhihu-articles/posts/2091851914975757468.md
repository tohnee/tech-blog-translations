> 摘要：2026 年 10 月的云栖大会上，千问办公 CEO 陈宇森把 AI 办公的下一个赛点概括成一句话——“Context is All You Need（上下文即一切）”。这不是造词运动，而是一次范式交接：提示词工程管"说什么"，上下文工程管"知道什么"，环境工程管"在什么环境里做事"。本文讲透中间这一环：为什么 100 万 Token 的大窗口在 25.6 万左右就开始"腐败"、上下文工程和提示词工程的本质区别、Anthropic 官方博客给出的三大策略，以及笔者写了一个可复现的对比实验——同样 50 份文档，全量塞入的信噪比只有 6.7%，分层装配拉到 64.6%，Token 直接省下 89.7%（附完整运行截图和代码）。这是"Agent 系统三部曲"的第三篇：第一篇讲 Skill（能力怎么装进来），第二篇讲 Harness（活怎么干起来），这一篇讲它们背后共同的底层逻辑——模型每一步到底"看见了什么"。

## 一、战场变了：从"谁的模型强"到"谁更懂你"

先看三条新闻，它们发生在同一个月里。

10 月云栖大会千问办公专场，阿里宣布"企业上下文"战略——把企业散落在各处的数据、流程和经验，连接、压缩成 AI 能直接调用的知识图谱；千问办公上线首月用户突破 3000 万，完成 120 次版本更新，平均一天迭代 4 次。往前推一个月，腾讯把所有 AI 办公能力收拢进 WorkBuddy，打通企业微信、腾讯文档、腾讯会议、QQ 邮箱；字节的飞书团队并入豆包，TRAE 和扣子一并收编。

三家路径不同，共识却完全一致。千问办公副总裁束骏亮说得更直白：“Agent 行业发展到现在，很多技术已经在趋同。决定一个 Agent 能走多远的核心，是推理时给它多少上下文。”

这句话值得反复读。过去两年，行业的焦点是"谁的模型更强"；到了 2026 年，头部模型的能力差距已经缩小到普通用户感知不到的程度，真正决定胜负的变成了模型外面那套东西。三家巨头用行动投了票：**模型可以换，记忆不能丢。**中国互联网下一阶段的竞争，正在从"模型智能"向"模型 + Harness + 用户语境"迁移。

而"用户语境"这个词，翻译成工程语言，就是本文的主角——上下文工程。

有人会说：这不就是 RAG 换了个马甲？区别在于格局。RAG 只回答"检索什么文档"这一个问题，上下文工程回答的是一整类问题：系统指令放多少、工具描述怎么瘦身、历史压到什么粒度、检索结果截不截断、子 Agent 带回什么——每一个环节都在决定模型那一次推理的质量。RAG 是上下文工程的一个零件，而不是它的全部。理解了这层包含关系，你才能看懂为什么巨头们把宝押在"语境"而不是"检索"上。

## 二、范式三部曲：说什么、知道什么、在什么环境里做事

要理解上下文工程的位置，得先看过去三年行业底层逻辑的三次切换。

**第一段（2023-2024）：提示词工程。**信念很朴素——问对问题，就能拿到好答案。大家在措辞上反复打磨，“你是一个资深专家"式的角色扮演提示词满天飞。这在聊天场景确实成立，但 AI 一旦从"回答问题"进化到"独立干活”，光靠一条指令就不够了。

**第二段（2025 年中）：上下文工程。**Karpathy 提出了 Context Engineering 这个词，Shopify CEO 迅速认同。大家的注意力从"这句话怎么写"转向"怎么动态组装 RAG、对话历史、工具输出"——模型每走一步，它"看见"的东西决定了它下一步的判断。

**第三段（2026 年）：环境工程。**HashiCorp 联合创始人 Mitchell Hashimoto 在 2 月的博客里给最后一块拼图命了名，还留了一句简洁到可以刻在墙上的话："每当你发现 Agent 犯了一个错误，你就花时间设计一个解决方案，使 Agent 永远不再犯同样的错误。“人类的角色从"直接干活的"变成了"设计赛道的”。

![](https://pica.zhimg.com/v2-ecddda328b155316c35305a0a09100f0_1440w.jpg)

这个三部曲不是文字游戏，每一层都在解决上一层解决不了的问题。有一个真实数据可以佐证这种"换层"的威力：LangChain 今年三月发布的《The Anatomy of an Agent Harness》里对比过，同一个大语言模型，权重一个字节没改，只把外面的架构换得更精巧，Terminal Bench 2.0 的通过率就从 52.8% 拉到 66.5%——从三十名开外飙进前五。层选对了，努力才不白费。

## 三、Context Rot：为什么 100 万的窗口只有 25 万可用

先给上下文下一个精确的定义。Anthropic 在《Effective context engineering for AI agents》里说得很清楚：上下文就是模型采样时包含的全部 Token 集合——不只是你输入的提示词，还有系统指令、对话历史、检索来的文档、工具的返回结果。上下文工程要做的，就是在窗口大小和注意力长度的双重约束下，优化这堆 Token 的效用。

听起来像是"窗口越大越好"，但实践给出的是一个反直觉的结论： **上下文窗口在物理上很大，在"有效注意力"意义上很小。**

2025 年下半年暴露的数据让人清醒：即便模型支持 100 万 Token，性能衰减在 25.6 万左右就出现了。更吓人的是，有人的 Agent 陷入无限循环，一次事故烧掉 5 万美元。这个现象有个专门的名字——Context Rot（上下文腐败）：和人类一样，模型会随着上下文增长而注意力涣散，准确回忆信息的能力下降，推理速度变慢，而且所有模型都逃不掉。

腐蚀从哪来？把上下文按内容拆开看就明白了：

| 上下文类型 | 装什么 | 典型的腐败源 |
| --- | --- | --- |
| 指令层（Instructions） | 系统提示词、任务要求、工具描述、输出格式 | 工具描述越堆越多，模型记混"该用哪个" |
| 知识层（Knowledge） | RAG 检索文档、领域知识、记忆文件 | 矛盾文档互相打架，模型开始编造 |
| 工具层（Tools） | 工具返回结果、执行状态、报错信息 | 一次cat 大文件，几千行日志淹没任务 |
| 历史层（History） | 对话记录、中间结论 | 数百轮累积，早期结论被后期噪声覆盖 |

一个典型的翻车现场：把 50 份互相矛盾的退款政策文档一次性塞进 system prompt，模型直接开始编造条款。单轮对话里它头头是道，放进需要连续调用几十次工具的循环里，跑到二三十步就开始答非所问，甚至把前面已经确认过的结论推翻重来。这不是模型变笨了，是它"看见"的东西出了问题。

这四类里最容易被忽视的是指令层的"工具描述膨胀"。一个真实案例：某个接了十几个 MCP 服务的 Agent，光工具说明书就吃掉三万 Token，结果模型频繁把相似工具搞混——明明该查数据库，它去调了文档搜索。把工具从十三个砍到五个、描述压到一行以内，同样的任务准确率明显回升。指令层不是越详细越保险，每一句描述都在消耗模型有限注意力里的"带宽"。

理解了这一点，上下文工程的目标就清晰了：**不是往窗口里装得更多，而是让模型在每一步恰好看见它需要的东西。**用最少的、信号最强的 Token 集合，最大化期望输出的概率。

从机制层面看，腐败至少有三个来源。其一是位置偏置：模型对上下文中部和尾部的信息敏感度不同，埋在长文本中间的关键约束经常被"视而不见"；其二是重复污染：同样的规则在指令、文档、工具描述里出现多次且措辞不一致，模型不知道听谁的；其三是浓度稀释：无关内容越多，每个关键 Token 被"真正看到"的概率越低——和化学里的浓度一个道理，溶剂多了，溶质就被稀释了。三个来源指向同一个解法：装配，而不是堆叠。

## 四、三大策略：检索、压缩、隔离

怎么做到"恰好看见"？Anthropic 的博客里给了一套经过生产验证的方法论，可以归纳成三个动作。

**策略一：Just-in-Time 检索——不预装，按需拉取。**传统做法是把所有可能的资料预先塞进上下文，代价是 Token 暴涨和信噪比暴跌。更好的做法是只在需要时拉取：把知识存放在文件系统或数据库里，用 grep、SQL 这类轻量工具按需检索。这个思路有个更广为人知的变体——渐进式披露：第一层只给名字和一句话描述，模型判断相关后再展开细节，最后才加载完整内容。Claude Code 的工作方式就是典型：启动时它只看见一个文件系统的轮廓，需要什么再去读什么。

**策略二：Compaction——压缩历史，保住状态。**对话越滚越长是必然的，压缩就是定期把早期历史折叠成摘要，只保留最近几轮的原文。关键在于摘要压什么、保什么：过程可以丢，状态必须留——处理到哪个订单、做过什么承诺、确认过什么口径，这些是任务连续性的命脉。

**策略三：Sub-Agent 隔离——各查各的，只带回结论。**让子 Agent 带着独立上下文去做深度调研，主循环只接收最终摘要。Anthropic 内部一个多 Agent 系统通过这种隔离方式，把 Token 消耗降低了 90%。这和第二篇 Harness 文章里说的"子 Agent 是被单循环瓶颈逼出来的部件"完全对上了。

三个策略不是并列的选择题，而是有清晰的适用边界：资料静态且用户查询多样，用检索；对话长而状态少，用压缩；调研型任务耗时且相互无依赖，用隔离。多数生产系统是三者的组合拳——先用隔离控制爆炸半径，再用检索控制单步信噪比，最后用压缩控制长期成本。

这三个策略落到代码上，核心就是一个分层装配器。下面是笔者简化后的模板，语义与实验代码一致：

```text
def est_tokens(text: str) -> int:
    """极简估算：中文约1字1token，其他按0.3折算"""
    cn = sum(1 for c in text if ord(c) > 0x2E80)
    return cn + int((len(text) - cn) * 0.3)

def assemble_layered(system, retrieved_docs, task):
    """分层装配：指令层 + 检索层 + 任务层，各层职责单一"""
    return (
        f"[system] {system}\n"                 # 指令层：角色与规则，永远在场
        + "[retrieved]\n"                       # 检索层：只放 top-k 相关片段
        + "\n---\n".join(d["text"] for d in retrieved_docs)
        + f"\n[task] {task}"                    # 任务层：当前目标放最末，离采样点最近
    )

def compact(history, keep_last=4):
    """压缩：早期历史折叠成摘要，只留状态，不留过程"""
    kept = "\n".join(history[-keep_last:])
    summary = summarize(history[:-keep_last])   # 摘要生成（可调模型或规则）
    return f"[summary] {summary}\n{kept}"

```

三段代码没有一行是"高级技术"，但这正是上下文工程的本质——它不是算法突破，而是一套关于"信息该不该出现在模型眼前"的纪律。

## 五、动手实录：信噪比从 6.7% 到 64.6%

概念讲多了容易飘，跑一遍最有说服力。笔者写了一个可复现的对比实验（完整代码随文附带，不依赖任何模型 API，Python 直接跑）：构造 50 份客服文档，其中只有 3 份和"退货政策里运费谁出"这个问题相关，分别用两种策略组装上下文，统计 Token 消耗和信噪比（相关 Token 占总 Token 的比例）。另加一组 Compaction 演示：80 条模拟对话历史做压缩。运行结果如下：

![](https://pic4.zhimg.com/v2-a0ed945c0226f3416ed13be2dbc57201_1440w.jpg)

三个数字值得展开看。

**信噪比 6.7% 对 64.6%，差了 9.7 倍。**全量塞入时，模型要在一千五百多个 Token 里大海捞针，真正和任务相关的只有那 104 个——这还只是 50 份文档的规模，生产环境动辄几千份，信噪比会掉到 1% 以下。分层装配后，上下文从 1556 Token 缩到 161，模型几乎每一眼都看在点子上。这就是"窗口物理上很大、注意力意义上很小"的量化版。

**Token 省了 89.7%，成本是乘法关系。**按 Token 计费的模式下，这个数字直接写进账单。更隐蔽的收益在延迟：上下文短了，首 Token 响应时间显著下降——束骏亮在云栖大会专门提过 Token 计费的两面性，成本结构正在倒逼工程优化。

**压缩率 92.3%，但订单结论一条没丢。**80 条历史压成"最近 4 条原文 + 一段摘要"，摘要里保留了关键状态：36 个订单各自的处置结论、无升级投诉。过程被丢弃了，任务连续性完好无损。这就是策略二里"保状态不保过程"的具体形态。

必须诚实说明：Token 统计是本地估算（中文约一字一 Token），实验里的"检索"也是按关键词重合度模拟的，没有接真实模型跑质量对比——这个实验度量的是上下文组装策略本身的效用差异，而不是模型能力。但恰恰因此，任何人都可以在本地复现它， `random.seed(42)` 锁死了结果。

四条实战经验，是这次实验之外更值钱的部分：

**第一，先测信噪比，再谈优化。**把"当前任务真正需要的 Token / 上下文总 Token"做成一个监控指标，接进你的 Agent。这个数字长期低于 10% 的系统，性能问题大概率不在模型，在装配。

**第二，检索宁缺毋滥。**实验里 3 份相关文档是理想情况，现实检索经常"宁多勿漏"，于是噪声回流。笔者的原则是：给模型看 3 份高相关，胜过 30 份半相关——拿不准的宁可让模型自己说"资料不足"，也别用噪声喂出幻觉。

**第三，摘要写"状态"，不写"剧情"。**压缩时最常见的错误是把摘要写成流水账。对下一轮推理有用的只有状态：做到了哪一步、确认过什么、还差什么。判断标准很简单——摘要里任何一句话，都应该能改变模型下一步的行为。

**第四，分层是稳定压舱石，把改动限制在层内。**指令层的措辞调整不应该影响检索层的召回逻辑，任务层的切换更不该动系统提示词。层与层解耦后，每一次上下文改动都可以独立验证、独立回滚——这也是下文验收方法论的前提。

把这四条经验收敛成一个可执行的动作，就是在 Agent 里加一个信噪比监控器。实现不需要十行代码：

```text
def monitor_snr(ctx_tokens: int, relevant_tokens: int, task_id: str):
    """每次推理调用后记录信噪比，低于阈值告警"""
    snr = relevant_tokens / max(ctx_tokens, 1)
    log.append({"task": task_id, "ctx": ctx_tokens, "snr": snr})
    if snr < 0.15:   # 经验阈值：长期低于15%说明装配在失效
        alert(f"[{task_id}] 信噪比 {snr:.1%}，检查检索层与历史层")
    return snr

```

上线之后你会拿到一张此前从未见过的体检报告：哪些任务的上下文在膨胀、哪些检索源常年贡献噪声、哪类对话从不触发压缩。优化有了靶子，改动有了对照——上下文工程从此从"玄学调参"变成"看数施工"。

## 六、上下文工程的产物形态：Skill 与能力市场

写到这里可以给三部曲收个口了。上下文工程成熟之后，它的最佳实践需要一种可分发的形态——总不能每个团队都从零写装配器。于是 Skill 出现了：把"某个领域该给模型看什么、按什么顺序看"打包成带元数据的模块，让渐进式披露的机制标准化。

用上下文工程的语言重新定义 Skill，它就是 **一份精心设计的信息披露计划** ：入口处的几十个 Token 描述能力边界，需要时展开操作流程，最后才加载脚本和模板。同一个 Agent，装不装 Skill、装多少 Skill，直接决定了它在特定任务上的上下文质量——这也解释了为什么能力市场开始爆发：大家买的不是功能，是被验证过的"信息装配方案"。

想直观感受这种产物长什么样，可以逛一逛 [DeepSkill 的作品展厅](https://www.deepskill.market/creations/?ref=zxy) ，两百多个创作者晒出了真实作品：有人把一本书压缩成可长期调用的知识 Skill——本质上是替你做好了"这本书在什么时机披露什么内容"的装配计划；有人把 100 条动效规范做成前端 Skill，让 Agent 生成带"手感"的界面——那 100 条规范什么时候出现在模型眼前、以多大的粒度出现，全是上下文设计。每一个都附源码，拆开看结构比读十篇教程有收获。

动手的读者，建议按这个顺序检验 Skill 的上下文设计质量：先看它的描述层——只靠名字和一句话，你能不能判断该不该用它；再看它的展开层——加载的指令是不是只包含"做这类任务需要的最小信息"；最后做个对照实验——同一个任务，手动把 Skill 的关键信息写进提示词对比效果，差距大的说明它的披露时机设计有问题。除了 [作品展厅](https://www.deepskill.market/creations/?ref=zxy) 里那些被真实使用过的成品，判断任何 Skill 都可以用这套"披露三问"。

照例是三任务验收，这是本系列的传统： **典型任务** ，给它一个你每天真实在干的活，看一次成功率； **边界任务** ，故意塞一份和任务矛盾的文档，看它是声明冲突还是编造调和； **缺参任务** ，模糊地下指令，看它会不会先确认口径再动手。三关全过才算真的能用，任何一关靠"自由发挥"混过去的，都要降权使用。

## 七、总结：注意力才是新的稀缺资源

回到云栖大会那句"Context is All You Need"。它的真正含义不是"上下文越多越好"，恰恰相反——正因为模型的有效注意力远小于物理窗口，"给模型看什么"才成了一门必须严肃对待的工程。

三部曲到这里可以合上了：提示词工程解决"说什么"，上下文工程解决"知道什么"，环境工程解决"在什么环境里做事"。第一篇的 Skill 是信息披露的标准化产物，第二篇的 Harness 是让这一切安全运转的操作系统，而这一篇的上下文工程，是贯穿两者的那条主线——Agent 系统的质量，最终取决于模型每一步"看见了什么"。

对开发者的启示朴素得近乎反高潮：别再追逐更大的窗口了，去测量你系统的信噪比，去审查每一条进入上下文的信息是否"有资格"占用那本就有限的注意力。模型能力的边际收益在递减，上下文工程的边际收益才刚刚开始。窗口越造越大，注意力越来越贵——这大概就是 2026 年 AI 工程师最重要的认知升级。
