## 1. 论文结构

大致分为两个层面：

- Control plane: 负责系统层面的资源管理和全局协调，决定如何分配计算资源、部署模型以及制定调度策略。
- Data Plane:负责具体推理请求的调度和执行，关注请求如何分配到不同模型实例、实例内部如何组织 Batch 和执行计算，以及 KV Cache 如何管理。

## 2.控制层面(Control plane)

![](https://pic3.zhimg.com/v2-24cddc6369eeedf147693fb039cf5882_r.jpg)

### 2.1 AutoScaler

这部分主要是根据负载增加或减少资源：

- Horizontal Scaling：增加或减少模型实例，或者独立扩展 Prefill、Decode 等阶段的实例数量。
- Vertical Scaling： 增加或减少单个实例可使用的计算资源，例如增加 GPU 数量、调整 TP 并行规模，或者动态分配 SM。
- Scaling Decision Techniques：这部分是决定何时进行实例的增加，以及增加多少。目前是分为三类：Threshold-based(根据 GPU 利用率、请求队列等指标触发扩缩容)；Predictive(预测未来负载，提前扩容)；Reinforcement Learning(通过强化学习寻找更优的资源分配策略)。
- Scaling Acceleration / Optimization ：解决扩缩容过程中的额外开销，包括模型权重加载、GPU 初始化、通信配置等冷启动问题，这些部分会非常耗时。

**总结** 文章认为当前LLM仍然面对下面的问题：

- Scaling Responsiveness：Horizontal Scaling可能因为资源重新配置出现短暂的性能下降；Vertical Scaling需要重新启动。
- Scaling Granularity：以TP为主的部署，通常是多个GPU为一个单位，突增的请求会导致资源浪费；PD分离为主的部署，需要协调PD实例的比例，协调会产生额外的开销。
- Resource Fragmentation： 在异构集群中，不同GPU的计算和显存都是有差异的。即使资源足够，也可能无法满足特定模型或并行配置的部署要求。

文章认为未来工作应该从：负载预测；分发策略(dispatch policies);model residency方面考虑

### 2.2 Model Management

主要针对多模型、多节点的分布式推理服务中模型的管理。因为GPU资源是有限的，可能某些模型不咋使用，又有新的模型需要进入。在这种视角下做模型的管理。大致分为三类：

- Model-aware Scheduling： 调度器需要维护各节点的模型驻留信息，优先将请求分配给已经加载目标模型的节点，减少模型加载开销。
- Demand-driven Preloading：针对上面那种调度方式中，模型加载的开销问题。根据历史数据，在请求到达前，提前加载模型到GPU中。
- Eviction Policies： 由于 GPU 显存有限，当需要加载新模型时，需要淘汰部分低价值模型以释放空间。常用方法是通过看最近访问时间，没有考虑访问频率和模型大小等。

**总结** 文章认为目前可以探究的方向：

- model-aware scheduling：调度器不能仅考虑模型驻留等，还需要考虑GPU 计算负载、I/O 带宽以及不同请求的 Qualityof-Service (QoS) 要求
- learning-based：基于观测到的流量和性能反馈，通过强化学习的方式确定模型的驻留。

### 2.3 Hardware Resource Manager

底层硬件资源管理，包括 GPU 计算资源划分、显存管理、数据传输和计算资源虚拟化。核心目标是在多任务共享 GPU 的情况下，提高资源利用率，同时保证任务隔离性和性能稳定性。

- Fine-Grained GPU Management： 传统 GPU 调度通常以整张 GPU 为单位分配资源，容易造成资源利用率低。细粒度 GPU 管理进一步将GPU资源划分
- Memory and Attention Offloading: 将部分模型数据、KV Cache 和中间计算结果从 GPU 显存卸载到 CPU 内存或外部存储，缓解 GPU 显存压力。
- Data Movement Optimization:主要优化 CPU、GPU 和存储设备之间的数据传输，减少模型初始化、权重加载等操作的时间。
- Resource Virtualization and Isolation: 主要解决训练、推理等不同任务共享 GPU 时的资源隔离和切换开销。

**总结** 文章认为目前可以探究的方向：

- 研究重点是加强请求调度、显存分配和加速器抽象之间的协同，尤其是在 CPU、GPU、ASIC 等异构计算设备共同参与推理的场景下，实现更灵活的资源分配和管理。

### 2.4 Orchestration

主要负责推理系统控制平面的工作负载编排，包括请求路由、批处理、队列管理和系统状态监控。根据实时负载、延迟要求、GPU 资源和 KV Cache 状态，动态决定请求的执行位置和调度方式。

- Cache-aware Routing and Request Management:请求到达时，不仅考虑模型副本的负载情况，还需要考虑 KV Cache、Adapter 等缓存资源的驻留情况，优先将请求分配给能够复用已有缓存的实例，减少重复计算和请求延迟。
- Dynamic Scheduling and Queueing: 根据请求优先级、负载情况和 SLO 要求，动态调整请求的执行顺序、批处理方式以及不同模型之间的资源分配。
- Serverless-Aware Orchestration: 针对 Serverless 推理环境中的实例冷启动和无状态执行问题，优化请求重定向、Checkpoint 迁移和分层调度。
- Queueing Theory：利用排队模型分析请求到达、等待和执行过程，为调度策略提供理论依据。

**总结** 文章认为目前可以探究的方向：

- 实现面向动态负载的自适应请求编排

## 3. Data Plane

![](https://pic2.zhimg.com/v2-8eb913b5143f23e86817d81a1fbc92cb_r.jpg)

### 3.1 Cluster-Level Dispatching Strategies

核心任务是在多个 GPU 节点或模型实例之间决定请求分配到哪里，以及什么时候执行，同时考虑节点负载、显存与 KV Cache 余量、请求长度和延迟要求。将现有工作分为四类：

- Per-Request Load Balancing and Routing： 根据各节点的实时负载情况分配请求，部分方法还支持将正在执行的请求迁移到其他节点，以缓解负载不均衡。
- SLO-Aware Global Optimization： 从整个集群的角度统筹请求队列和计算资源，根据不同请求的延迟要求，合理安排请求执行和资源分配。
- Energy and Cost-Aware Dispatching ：在保证推理性能的同时，考虑 GPU 功耗、温度和运行成本，动态调整请求分配和集群资源。
- Resource-Aware Scheduling： 综合考虑 GPU 利用率、请求长度、模型复用和 KV Cache 局部性等因素，提高资源利用率，减少不必要的计算和资源开销。

**总结**

- 将全局优化与局部快速响应结合，并进一步考虑成本和能耗。

### 3.2 Instance-Level Scheduling

通过上面的调度后，请求被分到一个节点。节点负责请求在执行端的调度。这里节点负责考虑batch策略，请求执行顺序等。尽可能提高GPU利用率和降低延迟。大致分为两方面的工作：

- Fairness and Quality of Service：主要解决多个用户或应用共享 GPU 时的资源分配问题，避免请求长期占用资源，导致交互式请求得不到及时响应。
- SLO-Aware Scheduling：根据延迟和吞吐量要求调整请求执行策略。包括根据请求长度优化 Batch、调整 Prefill 和 Decode 的执行顺序、减少两个阶段之间的资源冲突，以及根据不同请求的性能要求动态调整执行策略。

**总结**

- 实例级调度从早期简单的规则判断和请求长度预测，逐渐发展到同时考虑 Prefill、Decode、显存管理和不同请求之间资源竞争的复杂调度方法。未来需要将请求优先级、公平性和 KV Cache 利用率结合起来，在保证请求响应速度的同时提高整体吞吐量。

### 3.3 Model Runtime

针对模型本身如何执行得更快、更充分地利用 GPU。现有工作分为三类：

- Parallelism and Execution Adaptivity：根据请求负载和硬件资源，动态调整模型并行程度、Batch 组成以及 Prefill/Decode 的执行方式，同时通过算子融合、显存管理和 CPU/GPU 协同提高执行效率。
- Speculative and Disaggregated Execution Models：这部分讨论了PD分离和Speculative Decoding方面的工作
- Model Loading and Context Switching：模型加载太慢，以及多个模型共享 GPU 时，切换模型的开销太大。目前工作分为两类：优化加载(不用一次性加载完，需要了再从CPU取)；切换优化(多个模型共享GPU)

**总结**

- 未来的方向包括将运行时调度器与缓存管理器和AutoScaler集成，在整个推理生命周期中进行优化。

### 3.4 KV Cache Management

KV Cache 管理主要解决缓存复用、缓存淘汰和跨设备传输三个问题，目标是减少重复计算，同时控制有限显存下的缓存开销。

- Reuse and Sharing Mechanisms：让不同请求、不同对话轮次，甚至不同模型之间共享已经计算过的 KV Cache，减少重复计算
- Prefetching and Transport Optimization： 提前预测可能需要使用的 KV Cache，并通过优化GPU、节点之间的数据传输，减少缓存读取和迁移时的等待
- Unified and Hybrid Cache Designs：将 KV Cache 与其他中间计算状态统一管理，或者让多个模型共享缓存空间，在提高缓存复用率的同时减少显存占用
- Compression, Recompute, and Transfer Efficiency：通过减少 KV Cache 存储量、适当重新计算部分 KV

**总结**

- 长上下文、多模态和多用户场景下的缓存复用、跨节点共享与压缩问题
