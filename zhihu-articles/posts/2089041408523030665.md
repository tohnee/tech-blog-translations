## 引子

这是系列的第二篇。第一篇（《一文吃透 PyTorch 自定义 C++/CUDA 算子》）讲的是 PyTorch 官方的自定义算子路径：`TORCH_LIBRARY` 定义 schema、调度器按调度键路由、`register_fake` 支持编译。那套机制是"地基"。

但真实世界里，大多数人不会直接拿 PyTorch 写算子——你用的很可能是**推理框架**，而 vLLM 是其中最主流的一个。第一次读 vLLM 源码的人，几乎都会被三样东西同时砸晕：

- 模型代码里好好的 `RMSNorm`，怎么在昇腾机器上就变成了 `AscendRMSNorm`？
- `torch.ops._C.silu_and_mul` 这种调用是什么？`_C` 是谁注册的？
- 到处出现的 **OOT** 是个什么缩写？

这三样东西对应 vLLM 算子体系的三块拼图：**CustomOp**（模型层的多后端分发）、**Platform**（硬件抽象与插件发现）、**torch.ops._C**（vLLM 自家的 PyTorch 算子库）。本篇把这三块拼图逐一拆开、拼成一张地图——下一篇讲 vllm-ascend（昇腾插件）实战时，会直接踩着这张地图走。

本文所有代码均出自 vLLM 与 vllm-ascend 仓库 main 分支的真实源码。

## 一、先看问题：一个层，多种硬件

vLLM 是高性能 LLM 推理引擎（PagedAttention、continuous batching 都是它的招牌）。它的模型实现层（`vllm/model_executor/layers/`）提供了一批标准层：`RMSNorm`、`SiluAndMul`、`RotaryEmbedding`、`LinearBase`、`MoERunner`……各家模型（Llama、Qwen、DeepSeek……）都用这批层搭出来。

问题来了：**同一个层，在不同硬件上要用不同实现**。拿最简单的激活函数 `SiluAndMul` 来说：

- NVIDIA GPU 上：vLLM 自带 CUDA 融合 kernel（一次读写完成 SiLU + 乘法）；
- AMD GPU（ROCm）上：多数 CUDA kernel 能直接复用，个别不行；
- CPU 上：纯 PyTorch 组合就挺好，还能吃到编译优化；
- Intel XPU、TPU 上：又是另一套；
- 昇腾 NPU 上：应该调 CANN 的算子。

最朴素的写法是在每个层里堆 if/else：`if 平台 == "cuda": ... elif 平台 == "npu": ...`。层一多、硬件一多，这个判断会渗透到每一处代码里，无法维护。

vLLM 的解法优雅得多：**把"按硬件选实现"从代码里抽出来，变成类的方法约定**。这就是 CustomOp。

## 二、CustomOp：把平台 if/else 变成类的方法

先看骨架。`vllm/model_executor/custom_op.py` 里的 `CustomOp` 是个 `nn.Module` 基类，它为每种平台预留了一个同名方法（源码节选）：

```python
class CustomOp(nn.Module):
    """Base class for custom ops.
    Dispatches the forward method to the appropriate backend.
    """

    def forward(self, *args, **kwargs):
        return self._forward_method(*args, **kwargs)

    def forward_native(self, *args, **kwargs):
        """PyTorch-native implementation of the forward method.
        This method is optional. If implemented, it can be used with compilers
        such as torch.compile or PyTorch XLA. Also, it can be used for testing
        purposes."""
        raise NotImplementedError

    def forward_cuda(self, *args, **kwargs):
        raise NotImplementedError

    def forward_hip(self, *args, **kwargs):
        # By default, we assume that HIP ops are compatible with CUDA ops.
        return self.forward_cuda(*args, **kwargs)

    def forward_xpu(self, *args, **kwargs):
        # By default, we assume that XPU ops are compatible with the
        # PyTorch-native implementation.
        return self.forward_native(*args, **kwargs)

    # forward_cpu / forward_tpu / forward_oot 同理，默认都落到 forward_native
```

注意这个设计里的**回退链**：没写 `forward_hip` 就默认复用 CUDA 实现（AMD 用户大多白捡）；没写 `forward_xpu`/`forward_cpu`/`forward_tpu`/`forward_oot` 就退回纯 PyTorch 实现。一个层只需要实现"我有讲究"的那几个方法。

`__init__` 时，基类调用 `dispatch_forward()` 把"选方法"这件事一次性做完（源码节选）：

```python
def __init__(self, *, enforce_enable: bool = False, compile_native: bool = False):
        super().__init__()
        self._forward_method = self.dispatch_forward(compile_native=compile_native)

    def dispatch_forward(self, compile_native: bool):
        compilation_config = get_cached_compilation_config()
        enabled = self._enforce_enable or self.enabled()   # 用户开关，见第三节

        if not enabled:
            # 被禁用时走 forward_native（还会按需 torch.compile，见第六节）
            return self.maybe_compile(self.forward_native, enable=compile_native)

        if current_platform.is_rocm():
            return self.forward_hip
        elif current_platform.is_cpu():
            return self.forward_cpu
        elif current_platform.is_tpu():
            return self.forward_tpu
        elif current_platform.is_xpu():
            return self.forward_xpu
        elif current_platform.is_out_of_tree():   # ← 插件平台走这里
            return self.forward_oot
        else:
            return self.forward_cuda
```

也就是说：**实例化时就绑定好 `_forward_method`，之后每次 `forward()` 直接调用它**——没有运行时的反复判断，if/else 只在构建期发生一次。`current_platform` 是谁、怎么来的，第四节讲。

### 一个完整的例子：SiluAndMul

`vllm/model_executor/layers/activation.py`（真实源码，略有删节）：

```python
@CustomOp.register("silu_and_mul")          # ★ 注册进算子注册表，见第三节
class SiluAndMul(CustomOp):
    """An activation function for SwiGLU.

    The function computes x -> silu(x[:d]) * x[d:] where d = x.shape[-1] // 2.
    """

    def __init__(self, *, compile_native: bool = True):
        super().__init__(compile_native=compile_native)
        if current_platform.is_cuda_alike() or current_platform.is_xpu():
            self.op = torch.ops._C.silu_and_mul      # ← vLLM 自家算子，第五节讲

    @staticmethod
    def forward_native(x: torch.Tensor) -> torch.Tensor:
        """PyTorch-native implementation equivalent to forward()."""
        d = x.shape[-1] // 2
        return F.silu(x[..., :d]) * x[..., d:]       # 纯 torch 组合，谁都能跑

    def forward_cuda(self, x: torch.Tensor) -> torch.Tensor:
        d = x.shape[-1] // 2
        output_shape = x.shape[:-1] + (d,)
        out = torch.empty(output_shape, dtype=x.dtype, device=x.device)
        self.op(out, x)                               # ← 调融合 kernel
        return out

    def forward_xpu(self, x: torch.Tensor) -> torch.Tensor:
        return self.forward_cuda(x)                   # XPU 直接复用 CUDA 路径
```

`forward_cuda` 里调的 `torch.ops._C.silu_and_mul`，正是第一篇讲过的 `TORCH_LIBRARY` 注册出来的算子——vLLM 自己就是个"教材级用户"，第五节细说。

### forward_cuda 里未必是 CUDA C

看同文件的另一个层 `SwigluStepAndMul`，它的 CUDA 实现用的是 **Triton kernel**（真实源码节选）：

```python
def forward_cuda(self, x: torch.Tensor) -> torch.Tensor:
        d = x.shape[-1] // 2
        output_shape = x.shape[:-1] + (d,)
        out = torch.empty(output_shape, dtype=x.dtype, device=x.device)
        swiglustep_and_mul_triton(out, x, self.limit)   # ← Triton 写的 kernel
        return out
```

这说明 CustomOp 体系的边界很清楚：**它只负责"这层代码在哪种硬件上跑"，不关心实现用什么技术**——CUDA C、Triton、flashinfer、cuBLAS 调用、纯 PyTorch，都可以。

三个要点总结：

1. 写层时继承 `CustomOp`，按平台实现 `forward_xxx` 方法；
2. 没实现的方法有默认回退（HIP→CUDA，其余→native）；
3. 实例化时一次性绑定 `_forward_method`，运行时零分发开销。

> **范围说明**：注意力（Attention）不走 CustomOp——vLLM 为它设计了独立的 attention backend 体系（由 Platform 的 `get_attn_backend_cls` 选择后端类）。本文聚焦 CustomOp 这条主线。

## 三、注册与替换：register / register_oot

`custom_op.py` 的模块级里挂着两张注册表（真实源码）：

```python
# Dictionary of all custom ops (classes, indexed by registered name).
op_registry: dict[str, type["CustomOp"] | type["PluggableLayer"]] = {}
op_registry_oot: dict[str, type["CustomOp"] | type["PluggableLayer"]] = {}
```

**第一张表（树内）**：vLLM 主仓库的层用 `@CustomOp.register("名字")` 装饰器登记，比如上面见过的 `@CustomOp.register("silu_and_mul")`。这张表主要服务于用户开关（马上讲）。

**第二张表（树外/OOT）**：给插件用的。而它生效的方式相当巧妙——藏在 `__new__` 里（真实源码节选）：

```python
class CustomOp(nn.Module):
    def __new__(cls, *args, **kwargs):
        op_name = cls.__name__                      # 拿当前类名，如 "RMSNorm"
        if op_name not in op_registry_oot:
            op_cls_to_instantiate = cls             # 没有替身 → 正常创建
        else:
            op_cls_to_instantiate = op_registry_oot[op_name]   # ★ 有替身 → 换类！
            logger.debug("Instantiating custom op: %s using %s",
                         op_name, str(op_cls_to_instantiate))
        return super().__new__(op_cls_to_instantiate)
```

这就是本文开头第一个谜题的答案：**vLLM 模型代码里写的是 `RMSNorm`，但如果某个插件在 `op_registry_oot` 里注册了名为 `"RMSNorm"` 的替身类，那么 `RMSNorm(...)` 实际创建出来的就是替身**。vLLM 主库一行代码都不用改，插件的替身自动接管。

注册替身的 API 是 `CustomOp.register_oot`，支持两种用法（真实源码节选）：

```python
# 用法一：装饰器（插件仓库里直接装饰自己的类）
@CustomOp.register_oot(name="RMSNorm")
class AscendRMSNorm(RMSNorm):
    ...

# 用法二：函数式调用（适合批量注册，vllm-ascend 就这么干）
CustomOp.register_oot(_decorated_op_cls=AscendRMSNorm, name="RMSNorm")
```

> **命名考古：OOT 是哪来的词？** OOT = **out-of-tree**（"树外"）。这个词借自 **Linux 内核社区**：内核模块分两类——**in-tree**（代码合入内核主仓库，随内核一起编译发布）和 **out-of-tree**（在独立仓库维护，装好内核后再编译加载）。软件工程里把"代码进主仓库"叫 in-tree、"代码留在主仓库之外"叫 out-of-tree，是很通行的黑话。 vLLM 借用了这对术语：CUDA/ROCm/CPU/XPU/TPU 这些平台的支持代码就在 vLLM 主仓库里（in-tree）；昇腾、寒武纪这类硬件的支持放在**独立仓库**（如 `vllm-project/vllm-ascend`），通过插件接口接入（out-of-tree）。所以你会看到：`op_registry_oot`（树外注册表）、`forward_oot()`（树外平台的 forward）、`PlatformEnum.OOT`（树外平台枚举值）——名字里带 oot 的，说的都是"插件"这回事。

### PluggableLayer：CustomOp 的兄弟

同文件里还有个 `PluggableLayer` 基类，解决另一类替换需求。它的 docstring 写得很清楚（要点转述）：

- `CustomOp`：提供**按平台分发**的 `forward_xxx`，替身只需覆写对应方法；
- `PluggableLayer`：**不做**按平台分发，而是支持在实例化时**整类替换**——替身可以自己组织 `__init__`、自己组合子模块（"module-composing"）。

从官方设计文档的清单看，两者的分工很清晰：**"计算性"的层是 CustomOp**——`RMSNorm`、各类激活函数、`GroupedTopk`、`QuantFP8`；**"结构性"的层是 PluggableLayer**——Linear 家族（`ColumnParallelLinear`/`RowParallelLinear`/`ReplicatedLinear`）、`VocabParallelEmbedding`、`ParallelLMHead`、`LogitsProcessor`、Mamba 的 `MambaMixer`、MLA 的包装层等。两者的 `__new__` 替换机关一模一样，查的是同一张 `op_registry_oot`。

### 用户开关：custom_ops 配置

每个注册过的层都可以被用户单独开关。CLI 用法：

```bash
vllm serve <model> --compilation_config.custom_ops '["all"]'                # 全启用（默认）
vllm serve <model> --compilation_config.custom_ops '["none"]'               # 全禁用
vllm serve <model> --compilation_config.custom_ops '["all", "-rms_norm"]'   # 除 rms_norm 外全启用
vllm serve <model> --compilation_config.custom_ops '["none", "+silu_and_mul"]'  # 只启用 silu_and_mul
```

规则藏在 `enabled()` 和 `default_on()` 里（真实源码节选）：

```python
@classmethod
    def enabled(cls) -> bool:
        compilation_config = get_cached_compilation_config()
        custom_ops = compilation_config.custom_ops
        enabled = f"+{cls.name}" in custom_ops     # "+silu_and_mul" 强制启用
        disabled = f"-{cls.name}" in custom_ops    # "-silu_and_mul" 强制禁用
        if enabled and disabled:
            raise ValueError("custom_ops cannot both enable and disable "
                             "the same operation...")
        return (CustomOp.default_on() or enabled) and not disabled

    @staticmethod
    def default_on() -> bool:
        """... On by default if 'all', off by default if 'none'.
        When PyTorch Inductor is used, 'none' is the default value,
        otherwise 'all'."""
        count_none = compilation_config.custom_ops.count("none")
        count_all = compilation_config.custom_ops.count("all")
        if count_none + count_all != 1:
            raise ValueError("custom_ops must contain exactly one base mode: 'all' or 'none'")
        return not count_none > 0 or count_all > 0
```

三条规则：列表里必须**恰好含一个**基础模式（`"all"` 或 `"none"`）；`+名字` 强制开、`-名字` 强制关；同一层既 `+` 又 `-` 直接报错。

`default_on` 的 docstring 还透露了一个很有味道的设计哲学：**用 PyTorch Inductor 编译时，默认值是 `none`（禁用融合算子），否则默认 `all`**。为什么？因为一旦走编译路线，编译器需要"看见"原生算子序列（`F.silu(x) * y` 这样的组合）才能跨算子做融合优化；预编译好的融合 kernel 反而是一堵墙，编译器看不到墙里是什么。融合 kernel 和编译器融合，是两条互斥的优化路线——vLLM 用一个默认值切换表达了这个权衡。用官方设计文档的原话说：被禁用的自定义算子，"Inductor 会为它们生成（融合的）Triton kernel"。

顺带一提：CustomOp 还有个 `enforce_enable=True` 参数，可以在对象级强制启用自己（无视 custom_ops 配置）——vLLM 对多模态模型的 ViT 编码器部分就用它强制启用了若干算子，保证拿到深度优化的 kernel。

## 四、Platform：硬件抽象与插件发现

第二节埋了个伏笔：`dispatch_forward` 里判断平台的 `current_platform` 是什么？

它是 `vllm/platforms/__init__.py` 里一个**惰性初始化的单例**——第一次被访问时，vLLM 会探测当前机器是什么硬件，并实例化对应的 Platform 类。Platform 是 vLLM 对"一种硬件"的完整抽象：设备类型、通信后端、注意力后端选择、内存管理、编译配置……CustomOp 的平台判断只是它众多职责中的一个。

### 内置平台：探测式发现

内置平台就五个，每个配一个探测函数（真实源码）：

```python
builtin_platform_plugins = {
    "tpu": tpu_platform_plugin,     # 试 import libtpu
    "cuda": cuda_platform_plugin,   # 用 pynvml 数显卡
    "rocm": rocm_platform_plugin,   # 用 amdsmi 数 A 卡
    "xpu": xpu_platform_plugin,     # 查 torch.xpu.is_available()
    "cpu": cpu_platform_plugin,     # 查 vllm 是否 CPU 构建 / macOS
}
```

每个探测函数返回"平台类的全限定名"（如 `"vllm.platforms.cuda.CudaPlatform"`）或 `None`（硬件不存在）。以 CUDA 探测为例，核心就是调 pynvml 数一遍 GPU 数量——有卡就激活，没卡返回 None。**vLLM 是"探测"出硬件的，不靠用户声明**（所以 `--device cpu` 这类参数只是辅助覆盖手段）。

激活规则（`resolve_current_platform_cls_qualname`，要点转述）：

- 内置平台至多激活一个（同时检测到两种内置硬件会直接报错）；
- **树外插件（OOT）也至多一个，且一旦激活就优先于内置平台**；
- 一个都没有 → `UnspecifiedPlatform`。

### 树外平台怎么进来：Python entry points

最关键的问题：vllm-ascend 是独立仓库、独立 pip 包，vLLM 怎么"知道"它的存在？答案是 **Python 的 entry points 机制**——pip 包可以声明"我注册了某个入口点组下的某个函数"，装了这个包，其他程序就能通过标准接口发现它。

vllm-ascend 的 `setup.py`（真实源码节选）：

```python
setup(
    name="vllm_ascend",
    ...
    entry_points={
        "vllm.platform_plugins": ["ascend = vllm_ascend:register"],   # ★ 平台插件
        "vllm.general_plugins": [
            "ascend_kv_connector = vllm_ascend:register_connector",
            "ascend_model_loader = vllm_ascend:register_model_loader",
            ...
        ],
    },
)
```

它在 `vllm.platform_plugins` 这个入口点组下注册了一个名为 `ascend` 的探测入口。而探测函数本身简单到只有一行（`vllm_ascend/__init__.py`，真实源码）：

```python
def register():
    """Register the NPU platform."""
    return "vllm_ascend.platform.NPUPlatform"
```

于是整条发现链是：**pip install vllm-ascend → 声明入口点 → vLLM 启动时用 `load_plugins_by_group` 扫描该组的所有入口点 → 逐个调用 → 拿到平台类路径 → 导入并实例化 → 成为 `current_platform`**。

平台的"自我介绍"则写在类属性里。看 `NPUPlatform`（`vllm_ascend/platform.py`，真实源码节选）：

```python
class NPUPlatform(Platform):
    _enum = PlatformEnum.OOT              # 树外平台
    device_name: str = "npu"
    device_type: str = "npu"
    simple_compile_backend: str = "eager"  # Disable torch.compile()
    ray_device_key: str = "NPU"
    device_control_env_var: str = "ASCEND_RT_VISIBLE_DEVICES"   # 相当于 CUDA 的 CUDA_VISIBLE_DEVICES
    dispatch_key: str = "PrivateUse1"      # ★ 又见这个键！
```

`dispatch_key = "PrivateUse1"`——第一篇反复强调的那个"PyTorch 预留给第三方后端的调度键"，在这里以平台属性的形式再次出现。NPU 张量在 PyTorch 分发器里走 `PrivateUse1` 键，vllm-ascend 的算子也注册在这个键上——这是通往第三篇的桥。

这套插件体系如今已经是 vLLM 官方推荐的硬件接入方式，生态相当热闹（摘自官方设计文档的清单）：**官方插件**有 vllm-ascend（华为昇腾）、vllm-gaudi（Intel Gaudi）、vllm-neuron（AWS Neuron）、vllm-metal（Apple Silicon）、vllm-spyre 等；**社区插件**有 vllm-metax（沐曦）、vLLM-Kunlun（百度昆仑芯）、vllm-musa（摩尔线程）等。它们全都走本文描述的同一条路：独立仓库 + entry points + Platform 子类。

Platform 接口的职责可以粗略分成几类：

| 类别 | 代表方法/属性 | 作用 |
| --- | --- | --- |
| 身份声明 | device_type、dispatch_key、device_name | 我是什么硬件、走哪个调度键 |
| 设备管理 | set_device、get_device_name、get_device_total_memory | 对应 torch.cuda 的那些事 |
| 算子与后端选择 | get_attn_backend_cls、import_kernels | 选注意力后端、加载自家 kernel |
| 编译与图模式 | simple_compile_backend、get_compile_backend、get_static_graph_wrapper_cls | 告诉 vLLM 用什么编译后端、图捕获包装器 |
| 配置适配 | check_and_update_config、pre_register_and_update | 按硬件特性修正/校验用户配置 |
| 通信 | get_device_communicator_cls、ray_device_key | 分布式通信后端 |

插件要接入 vLLM，就是把这张表里的钩子按需实现。vllm-ascend 的 `NPUPlatform` 实现了几乎全部：`get_attn_backend_cls` 返回昇腾的注意力后端、`get_compile_backend` 返回自研的 `AscendCompiler`、图模式包装器是 `ACLGraphWrapper`……这些名字在第三篇都会再见到。

## 五、torch.ops._C：vLLM 自家的 PyTorch 算子库

现在拆最后一块拼图。第二节 `SiluAndMul.forward_cuda` 里的 `torch.ops._C.silu_and_mul` 从哪来？

答案是：**vLLM 主仓库的 `csrc/` 目录里有几百个手写 CUDA kernel，用的正是第一篇讲的 `TORCH_LIBRARY` 机制**。看 `csrc/torch_bindings.cpp`（真实源码节选）：

```cpp
#ifdef USE_ROCM
TORCH_LIBRARY_FRAGMENT(CONCAT(TORCH_EXTENSION_NAME, _custom_ar), custom_ar) {
  // Quick Reduce all-reduce kernels (ROCm-only; stays on legacy _C).
  custom_ar.def(
      "qr_all_reduce(int fa, Tensor inp, Tensor out, int quant_level, bool "
      "cast_bf2half) -> ()");
  custom_ar.impl("qr_all_reduce", torch::kCUDA, &qr_all_reduce);
  ...
}
#endif

REGISTER_EXTENSION(TORCH_EXTENSION_NAME)   // vLLM 自封装的注册宏（csrc/core/registration.h）

```

眼熟吗？`m.def` 定义 schema、`m.impl` 绑定实现、调度键 `torch::kCUDA`——和第一篇逐行拆解的注册代码一个模子。`TORCH_EXTENSION_NAME` 在构建时被定为 `_C`，于是这些算子就出现在 `torch.ops._C` 命名空间下。`REGISTER_EXTENSION` 则是 vLLM 把"pybind11 模块初始化 + 算子库注册"打包成的一个宏。

把这个认知推而广之：

```text
vLLM 模型层（SiluAndMul 等 CustomOp）
    │  forward_cuda
    ▼
torch.ops._C.silu_and_mul(...)          ← Python 侧调用
    │
    ▼
PyTorch 分发器（CUDA 调度键）            ← 第一篇的主场
    │
    ▼
vLLM csrc/ 里的 C++ wrapper + CUDA kernel
```

**这条链和第一篇讲的完全同构**——vLLM 只是个大规模实践者。甚至文件开头的注释还提到，一部分 cache 算子已经搬到 `_C_stable_libtorch`（Stable ABI 扩展，第一篇结尾提过的那个方向），说明这套体系仍在持续演进。

## 六、与编译、图模式的关系

推理框架对"算子"的折腾不止于分发，还有编译。vLLM 这边有四件事值得知道：

**1. piecewise 编译是默认姿势。** vLLM 默认把模型按算子边界切成若干段：可编译段交给 Inductor 生成代码，不适合编译的段保持 eager。默认的切图边界正是一批注册在 `vllm::` 命名空间下的 torch 自定义算子（`CompilationConfig._attention_ops`，如 `vllm::unified_attention_with_output`、`vllm::mamba_mixer`）——attention 这类带 KV cache 的复杂计算，单独包成第一篇讲的 `torch.library` 自定义算子，既是编译边界，也是图捕获的边界。

**2. CustomOp 的启停和编译策略联动。** 还记得第三节那个默认值设计吗——走 Inductor 时默认 `none`（禁用融合算子，让编译器看见并融合原生算子序列）；不走编译时默认 `all`（直接上预编译融合 kernel）。同一套机制的两挡速度来源。

**3. 被"藏"在自定义算子里的 CustomOp 会被局部编译。** `maybe_compile` 的 docstring 写明（真实源码）：vLLM 把 `fused_moe`、`unified_attention` 这类复杂计算包装成了 **opaque torch custom op**（就是第一篇的 `torch.library`/`custom_op` 那套）——外面的 dynamo 看不进它的内部。这时如果里面用到的某个 CustomOp 被用户禁用了，它的 `forward_native` 就享受不到模型级编译了，于是 vLLM 会**就地用 `torch.compile` 把这个 native 实现单独编译一遍**（用平台的 `simple_compile_backend`），免得性能断崖。

**4. 图模式（CUDA Graph / aclgraph）是推理的另一件大事。** 图捕获时算子只被"录"不被"算"，所以每个算子都得有"只推形状"的元数据实现——这正是第一篇 `register_fake` 的用武之地，vLLM 源码里到处是 `register_fake`，vllm-ascend 则注册了一整套 Meta 键实现来支撑 aclgraph（第三篇展开）。另外 NPUPlatform 里 `simple_compile_backend = "eager"` 的注释写得很直白：昇腾上默认不跑 torch.compile，走的是自己的编译/图体系。

## 七、全景图

把三块拼图拼起来。一台机器装了 vllm-ascend 时，一次 forward 的全貌：

```text
vLLM 模型代码（Qwen2DecoderLayer 里的 RMSNorm、SiluAndMul…）
                              │
                     实例化某个层（如 RMSNorm）
                              │
              ┌─── CustomOp.__new__ 查 op_registry_oot ───┐
              │ 找到替身                            │ 没有替身
              ▼                                     ▼
   vllm-ascend 的 AscendRMSNorm           vLLM 树内的 RMSNorm
   （替身类，实现 forward_oot）            （dispatch_forward 按平台选方法）
              │                                     │
              ▼                                     ▼
   torch.ops._C_ascend.npu_add_rms_norm   forward_cuda → torch.ops._C.silu_and_mul
              │                                     │
              ▼                                     ▼
   PyTorch 分发器：PrivateUse1 键          PyTorch 分发器：CUDA 键
              │                                     │
              ▼                                     ▼
   vllm_ascend_C 扩展 → CANN aclnn        vLLM _C 扩展 → CUDA kernel
   → AscendC kernel（NPU 上执行）          （GPU 上执行）
```

左右两条路完全对称：**插件做的事，就是把 vLLM 树内的整条右链复制一份**，只是调度键、算子库、kernel 语言全部换成昇腾生态的对应物。第三篇会把左链一节一层地拆开。

最后用一张表对齐三块拼图与第一篇的概念：

| 概念 | 归属 | 一句话 |
| --- | --- | --- |
| TORCH_LIBRARY / schema / 调度键 | PyTorch（第一篇） | 算子的"身份证 + 分发规则"，一切的地基 |
| CustomOp（forward_xxx / register / register_oot） | vLLM | 模型层的多后端分发 + 插件替身机制 |
| Platform（current_platform / entry points） | vLLM | 硬件抽象 + 插件的发现与接入 |
| torch.ops._C / torch.ops._C_ascend | vLLM / vllm-ascend | 各自仓库的算子库，都用第一篇的机制注册 |
| forward_oot | vLLM | 树外插件平台的 forward 入口 |
| register_fake / Meta 实现 | PyTorch / 两家都在用 | 编译与图捕获的"形状推演"配套 |

## 八、常见问题与坑

**1. 最大混淆点：CustomOp 不是 PyTorch 的 custom op。** `CustomOp` 是 vLLM 的**层分发框架**（一个 Python 基类）；PyTorch 的自定义算子是 `TORCH_LIBRARY` 那套（第一篇）。两者在 `torch.ops._C` 这个点上相接：CustomOp 的 `forward_cuda` 里面调用的，才是 PyTorch 意义上的算子。

**2. 怎么看当前启用了哪些算子？** 每个层实例化时，`dispatch_forward` 会把结果写进 `compilation_config.enabled_custom_ops` / `disabled_custom_ops` 两个集合——打印 vllm_config 里这两个集合即可。类替换发生时也有 debug 日志（`Instantiating custom op: RMSNorm using AscendRMSNorm`）。

**3. custom_ops 语法错误。** 列表必须恰好含一个 `"all"` 或 `"none"`（多了少了都 ValueError）；`+名字` 和 `-名字` 不能同时出现同一层上。注意 `["all", "-rms_norm"]` 是**两个**列表项，别写成 `["all,-rms_norm"]`。

**4. 插件版本必须与 vLLM 严格对齐。** CustomOp 的替身机制、Platform 钩子都依赖 vLLM 内部 API，小版本间也常有变动。vllm-ascend 的 README 维护着与 vLLM 的版本对应矩阵，升级前先查。

**5. 插件忘了实现 `forward_oot` 会静默走慢路径。** 默认回退是 `forward_native`——功能正常、性能打折，且没有任何报错。性能莫名变差时，先确认有没有落到默认回退上。

**6. 想给某个平台换一层实现？** 路径：继承 vLLM 对应层 → 实现 `forward_oot`（或对应平台方法）→ `CustomOp.register_oot(name="层类名")`。不需要写 C++，除非你要调的算子不存在——那就要进入下一篇文章的世界了。

## 九、总结

vLLM 的算子体系是三层同心圆：

- **外层，CustomOp**：把"按硬件选实现"从 if/else 变成方法约定；`__new__` + OOT 注册表让插件无侵入地替换整层；用户用 `custom_ops` 配置在"预编译融合 kernel"与"编译器自由融合"之间切换。
- **中层，Platform**：硬件的完整抽象，探测式发现 + entry points 接入插件；`current_platform` 是所有平台判断的唯一入口。
- **内层，torch.ops._C**：vLLM 自家的算子库——就是第一篇那套 `TORCH_LIBRARY` 机制的大规模应用。

第一篇的核心洞见——"定义一次签名，按场景各注册一份实现"——在 vLLM 里被用了两遍：PyTorch 分发器用调度键选算子实现（内层），CustomOp 用平台选层实现（外层）。**同一个模式，嵌套了两层。**

下一篇，我们沿着本文全景图的左链往下钻：vllm-ascend 如何用 `PrivateUse1` 调度键、aclnn 算子和 AscendC kernel，把这条链在昇腾 NPU 上完整实现。
