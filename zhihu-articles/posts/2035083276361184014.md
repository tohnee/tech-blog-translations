### 动机

最近在云平台租了一个双卡 **NVIDIA RTX 2080 Ti**（Turing 架构，sm75） 机器用来开发和学习。在学习过程中，想实际上手了解一下 SGLang。因此我试着用 SGLang 部署 Qwen3.5-4B 模型做推理：

```text
python -m sglang.launch_server --model-path Qwen/Qwen3.5-4B --host 0.0.0.0 --port 30000
```

结果：

```text
RuntimeError: GemmaRMSNorm failed with error code no kernel image is available for execution on the device
```

[https://github.com/sgl-project/sglang/issues/24302](https://github.com/sgl-project/sglang/issues/24302)

### 背景：SGLang 与 sgl-kernel

SGLang 是一个高性能 LLM 推理框架，核心组件：

| 组件 | 类型 | 说明 |
| --- | --- | --- |
| sglang | 纯 Python | 模型加载、调度器、HTTP 服务、attention 后端 |
| sgl-kernel | C++ / CUDA | 高性能算子库：RMSNorm、Flash Attention、MoE、量化 GEMM |
| FlashInfer | CUDA + Python JIT | 注意力计算、采样、归一化（可选） |

`sgl-kernel` 的 CMakeLists.txt 控制 CUDA 架构列表，官方只有 `sm_80, sm_89, sm_90, sm_90a, sm_100a, sm_120a`，当前**没有 sm_75**。

---

### 整体思路

在 CMakeLists.txt 加 `sm_75` gencode，重新编译。但遇到了一系列问题：

1. **编译太重** — 全套 7 个架构需 2+ 小时，产物 315 MB
2. **ABI 兼容性** — .so 链接 libtorch，PyTorch 大版本间 C++ ABI 不兼容
3. **FlashInfer JIT** — sm_75 不支持，需绕过
4. **Flash Attention 3** — 需 sm_80+，编译不了
5. **Qwen3.5 Mamba** — causal_conv1d 内核在 fp16 下有 dtype 冲突
6. **Triton 内核** — bf16/fp16 类型推断冲突

最终通过 **5 项改动 + 精简编译**，产出两个共 42.8 MB + 24 MB 的 wheel。diff 在 [https://github.com/sgl-project/sglang/compare/v0.5.10...QingGo:sglang:qinggo/sm75-v0.5.10](https://github.com/sgl-project/sglang/compare/v0.5.10...QingGo:sglang:qinggo/sm75-v0.5.10)

---

### 解决方案详解

**改动 1：CMakeLists.txt — sm_75 only，精简编译**

砍掉全部高架构 gencode，只保留 sm_75。同时移除 sm_90 构建变体、禁用 FA3（需 WGMMA/cp.async.bulk 等 sm_80+ 特性）。

```text
# 原始（7 个架构）→ 改为：
-gencode=arch=compute_75,code=sm_75
```

**效果**：

| 指标 | 全架构 | sm_75-only |
| --- | --- | --- |
| 编译时间 | ~2 小时 | ~15 分钟 |
| common_ops.so | 184 MB | 28 MB |
| wheel 总大小 | 315 MB | 24 MB |

**改动 2：flash_attn.py — FA3 缺失容错**

FA3 不在编译范围，但 `flash_attn.py` import 时硬要求 `flash_ops` 模块。改为 graceful fallback：

```python
# 改动后：
try:
    from sgl_kernel import flash_ops
    _has_flash_ops = True
except ImportError:
    _has_flash_ops = False
    flash_ops = None
```

**改动 3：elementwise.py — 绕过 FlashInfer JIT**

FlashInfer Python 包的 JIT 编译器（Cutlass DSL/NVVM）不支持 sm_75。检测到 GPU compute capability < 8.0 时，跳过 FlashInfer 路径，使用 sgl_kernel AOT 内核：

```python
if _has_flashinfer and torch.cuda.is_available():
    _has_flashinfer = torch.cuda.get_device_capability()[0] >= 8
```

**改动 4：causal_conv1d.py — Mamba dtype 自动转换**

Qwen3.5 是混合 Mamba 模型，在 sm_75 上用 float16，但 Mamba 缓存的 conv_state 可能被分配为其他 dtype。内核严格检查 dtype 一致。

**关键 bug**：最初把 dtype cast 放在了 AOT 内核调用前，但代码可能走 Triton 分支，跳过了 cast。**移到分支之前**才彻底修复：

```python
# 在 use_triton 判断之前加（确保两种路径都生效）：
if conv_states is not None and conv_states.dtype != x.dtype:
    conv_states = conv_states.to(x.dtype)
```

**改动 5：causal_conv1d_triton.py — Triton 内核类型修复**

Triton kernel 中有一个 if/else 分支，then 分支从 `conv_states` 加载数据（可能是 bf16），else 分支创建 zeros（原本用 `x_ptr.dtype` 是 fp16）。Triton 编译器要求两边类型一致，直接报错。

修复：else 分支的 zeros 用 `conv_states_ptr.dtype` 而非 `x_ptr.dtype`：

```text
# 改动前：dtype=x_ptr.dtype.element_ty  → fp16
# 改动后：dtype=conv_states_ptr.dtype.element_ty  → 与 then 分支一致
```

> 顺便踩坑：Triton 会缓存编译结果。改完代码后必须 `rm -rf /root/.cache/triton` 清缓存，否则跑的仍是旧内核。

### 打包安装

目前编译还是很耗时间，因此我把 sglang 和 sglang-kernel 打包发到了 [Github Release](https://github.com/QingGo/sglang/releases/tag/v0.5.10-sm75-only) 上，**方便我自己后续重复使用，目前只在 Qwen3.5-4B 上成功运行过，各位有需要也可以在自己的模型上试试**。sglang 的 wheel 的 `pyproject.toml` 声明了对 GitHub Release 上 sm_75 kernel wheel 的依赖，因此用 uv/pip 安装时，只需安装 sglang，sglang-kernel 会被自动解析安装。

```text
pip install https://github.com/QingGo/sglang/releases/download/v0.5.10-sm75-only/sglang-0.5.10+sm75-py3-none-any.whl
```

或者

```text
uv add "https://github.com/QingGo/sglang/releases/download/v0.5.10-sm75-only/sglang-0.5.10+sm75-py3-none-any.whl"
```

下面的库会被一起安装：

- `sglang-0.5.10+sm75`（42.8 MB，包括 sglang 侧补丁）
- `sglang_kernel-0.4.1+sm75`（24 MB，sm_75 only 编译）

版本号用 `+sm75` 后缀区分（PEP 440 local version），标识这是基于 0.5.10 的 sm_75 专用版本。

仓库：[https://github.com/QingGo/sglang/tree/v0.5.10-sm75-only](https://github.com/QingGo/sglang/tree/v0.5.10-sm75-only)，如果对你有用，还请打一颗星星～
