## 仓库身份：11 天仓龄，单人 49 次提交，一套围着 llama.cpp 的补丁集

2026 年 10 月 29 日，GitHub 仓库 synchopate/llama-modchip 创建，当前版本 v2.4.0，Apache-2.0 许可。11 月 8 日它登上 HN（story 50411961），拿到 350▲ 和 145 条评论。标题只有一句话：284B DeepSeek 跑在 64GB 内存上，不用 GPU。这是「声称实现」，不是本文背书的事实。

README 第 70 行给出的自我定位很克制：这是一套 ggml/llama.cpp 内核补丁、量化转码器和运行时工具，目标是让稀疏 MoE 模型完全在系统内存里运行，覆盖 x86_64（AVX-512/AVX2）和 ARM64（NEON/SVE/Metal）。目标模型两个：DeepSeek-V4-Flash-0731（仓库口径 284.33B 总参/13.17B 激活，43 层 MLA 加 256 个路由专家）和 Nemotron-3.5-30B-A3B（30.2B/3.0B，Mamba-2 混合架构）。它不是独立推理引擎，形态判断放在实测一节展开。分发做了三层：install.sh 一键装、GitHub Release 挂预编译 Linux x86_64 二进制（自称零外部 .so 依赖）、Hugging Face 提供模型加二进制的零编译下载路径；仓库里还备了 windows、fedora、apple-silicon、systemd 四个平台目录。README 末尾挂了社区 leaderboard，通过 issue 模板提交，M4 Max、Ryzen 9950X、EPYC 7402P、i9-11950H、Ryzen 5700U 等七种硬件的真实用户数据在列（issue #7-#12，本地克隆可见），这对一个 11 天仓龄的项目来说不常见。

## 声称机制拆解：四件套逐个看

第一件，Fractal-64 量化转码。README 第 93 行给出配方：以 Unsloth UD-IQ1_S（76.87 GiB）为输入，嵌入层、第 0 稠密层、43 个共享专家和 MLA 的 kv_a/q_a/wkv_b 保留在 Q4_K/Q5_K/F32；MLA 的 wq_b 和注意力输出转成自定义的 Fractal-64 块（GGML_TYPE_Q2_0，64 权重一块、8 个子缩放加 BF16 缩放）；256 个路由专家主体用 IQ1_S（1.5625 bpw），配「解析式二阶 SwiGLU-H2 缩放匹配」，敏感边界层保留 IQ2_XXS。输出 56.56 GiB，整体 1.71 bpw，自称 256K 上下文峰值 VmRSS 57.61 GiB、零 NVMe swap。代价写在第 109 行：自定义张量类型 ID 40，未打补丁的 llama.cpp、Ollama、LM Studio 一律报「unknown tensor type 40」拒载，只能用它的预编译二进制。

第二件，4 级缓存 tiling 内核补丁。README 第 73 行：把 prefill 阶段的单列量化矩阵向量循环，换成寄存器（ZMM，AVX-512BW）+L1D（32KB）+L2（1MB）+L3（64MB）四级、多列 {8,4,3,2} 的 tiling 调度；MQA8 FlashAttention 做寄存器驻留；MoE 冷专家权重走 _MM_HINT_NTA 非临时读取，避免把 L3 里的热 KV 缓存行挤出去。自称 16 核 Zen5 上 prefill 从 25.0 提到 44.36 tok/s（+77%），decode +53%。ARCHITECTURE.md 还配了两条系统层手段：2MB 透明大页对付 MoE 权重在 4KB 页下的 TLB 抖动（自称单进程 6.14GB 的 L2 STLB 覆盖），双 CCD 拓扑下 OpenMP 按物理核 1:1 绑核；文中给出 perf stat 的 PMU 计数器对照表来自证。以上均为项目自述。

第三件，Zobrist n-gram 自推测解码。speculative/ROUTECRACK_TECHNIQUES.md 写得最细：drafter 叫 Stockfish-PVS v2，借国际象棋引擎的置换表思路，用 SplitMix64 Zobrist 哈希给 5-gram/4-gram/3-gram 后缀建三张各 64KB 的表，总预算 1.64MB，能塞进 L2/L3；命中记录沿用 Stockfish 的 history gravity 公式（h += bonus - h*|bonus|/512）；被否决的候选进 refuted 表做即时拦截。不加载任何小神经草稿模型，全靠统计级联，这是它敢叫「自推测」的原因。项目自述在 dsv4 上做到 94.5% 草稿接受率、11.5-14.7 tok/s 峰值。

第四件，/dev/shm KV 快照。ARCHITECTURE.md 3.8 节：HARP-Cache 用 FNV-1a 滚动哈希按 32 token 分块，建前缀基数树加内容寻址表，物理落地靠 llama-server 的 --slot-save-path /dev/shm；配套 gateway/sse_gateway.py（实测 1944 行）在转发请求前检查 Slot 0，冷了就把 85MB 的 40-tool Claude Code 提示词快照（22,237 token）自动灌回内存盘。项目自述恢复耗时 18.9-32.6ms，对 agent 循环意味着每轮对话省掉一次几万 token 的 prefill。四件套之外还有两个配角：KV 侧的 EAKV 熵引导非对称量化（kv_cache/eakv_quantizer.py，项目自述 Nemotron 256K 上下文的 KV 只占 432MB），以及一个 15.5KB 的 modchip CLI，把 quantize、chat、服务管理收进一个入口，chat 模式直接显示 tok/s、TTFT 和 PVS 接受率遥测。Fractal 系也有两档：3.75bpw 的 Fractal-64 和 4.25bpw 的 Fractal-MXFP4，后者配 Vulkan 着色器走 GPU 混合，README 自述能到 80.8 tok/s。

## 本地实测核对：三个补丁一个 MD5，11 天长成的仓

11-09 本地克隆只读核验（全程未运行仓库任何代码）。文件分布：25 个 py、20 个 md、8 个 cpp、4 个 h、4 个 patch、9 个 sh；行数 py 8189、cpp 3789、h 1998、md 2424。顶层四份大文档合计约 180KB：ARCHITECTURE.md 82.5KB（679 行，arXiv 风格，paper/ 里还有配套 LaTeX 源码）、FAQ.md 39KB、RELEASE_NOTES.md 30KB、README.md 27.7KB。文档体量和代码体量在同一量级，是典型的「重文档工程」。

patches/ 下四个补丁有个扎眼细节：dsv4-64gb-cpu、deepseek-v4-flash-fractal-256k、llama-modchip-dsv4-10tps 三个文件 7708 行、MD5 完全相同，是同一份补丁的三个改名副本；真正独立的只有 zen5-nemotron 那份 1337 行。补丁本体动的都是 llama.cpp 的关键路径：common/ngram-map.cpp 从 536 行改写到 974 行，ggml-cpu 的 quants.c/ops.cpp、llama-kv-cache-dsv4.cpp、llama-model.cpp 等十余个文件。提交记录：depth-50 窗口内 49 条全部署名 synchopate，日期从 10-31 到 11-08 共 7 个提交日，最高单日 13 条，conventional commits 规范格式。结合补丁形态可以下判断：这不是新引擎，是「llama.cpp 补丁集 + 转码脚本 + 网关 + CLI」的组合拳，核心创新集中在量化配方和 n-gram drafter 两处。工程完成度比一般周末项目高：转码器有独立的 C 实现（scripts/transcode_dsv4.c，148 行），kv_cache 目录带两组测试文件，gateway 在 11-08 的 commit a9635a5 里刚加了 root 级 /chat/completions、/models、/messages 等 OpenAI/Anthropic 兼容端点，注释写明是给 OpenCode 用的。单人、一周多、文档代码双高的产出节奏，评论区由此引出「AI 生成」的猜测，本文只记录不定性。

## 争议与质疑：位宽、口径、README 可信度、antirez 的参照系

HN 评论区火力集中在四点。其一，位宽换体积的质量代价。akie 第一句就问量化位宽，怀疑 2bit 输出质量；walrus01 拿 unsloth 官方 GGUF 对照，认为这个尺寸「需要 150GB 内存才能正经跑」，压到 56GiB 必然比 Q2XS 更差；armcat 引用 TUM 的量化可靠性论文，指出尺寸性能比峰值一般在 4bit，再低会显著滑坡；Youden 随即提醒这篇论文不含量化感知训练，对现代激进量化的适用性存疑，pu_pe 则给出经验反例：DeepSeek v4.1 flash 在 2bit 下依然能打，机器本来跑不动 4bit 时，用质量换速度是笔划算的买卖。Tepix 的抱怨代表了另一派情绪：Reddit 被「某某 tok/s on my light switch」式标题刷爆，全是 4bpw 以下的量化，大多没用；jazzypants 补刀说 Colibri 等项目几个月前就覆盖过这块地；GypsyKing716 一句话点题，「能加载不等于该加载」。其二，76.87GiB 的口径。adrian17 发现 README 一处写「标准 IQ2_XXS 76.87GiB」，而 unsloth 官方 IQ2_XXS 是 91GB、最小 IQ1_S 是 82.5GB，不知道数字指哪个档位。这里笔者补一个换算：76.87GiB 恰等于 82.5GB，README 主表写的输入正是 UD-IQ1_S，两个数大概率是同一文件的 GiB/GB 两种写法，争议更多来自 README 里量化档名称混用。其三，README 可信度。intoXbox、dofm、robotswantdata 等多人给出「AI slop」定性（此为评论区定性，本文不作结论），dofm 甚至说「不借助 LLM 摘要几乎读不了」。更硬的质疑来自 aappleby 和 ar-nelson：前者在 7945HX 上实测 Nemotron，速度和普通 llama.cpp 差不多；后者按 README 装 DeepSeek 直接报张量形状错误，换预编译二进制又 core dump。也有正面样本：sparse-Matrix 在 Ryzen 5700U/64GB DDR4 上拿到稳定 12-14 tok/s、整机 15W，说「够做个人工作」；boricj 的 homelab 体验与 ARCHITECTURE.md 前两节吻合。其四，antirez 参照系。Redis 作者本人现身，说 128GB 统一内存的 Mac 跑同类模型「甚至更快」，自称 prefill 约 300 t/s；embedding-shape 和 kgeist 立刻反问：视频里处理 43 个输入 token 花了约 4 秒（另一说 116 秒），300 t/s 的出处在视频和推文里都找不到，kgeist 直说这个速度「基本不可用」，并给出对照：同一个简单翻译请求，RTX 6000 加 GLM5.3-Flash 用 1.8 秒，RTX 5090 加 Qwen3.6-27B 用 12.5 秒。

## 与 llama.cpp 原生路线、Apple 统一内存路线的差异

对 llama.cpp 原生路线，差异在取舍方向。上游已有 unsloth UD-IQ1_S 这类激进量化，但 82.5GB 塞不进 64GB 机器；modchip 用自定义张量类型再砍 20GiB，代价是彻底脱离官方生态位，Ollama、LM Studio 全部拒载。SillyUsername 在评论区点出这类 fork 泛滥的结构性原因：llama.cpp 上游积压 1.7K 个 PR，Bonsai 特性从提交到评审花了三周，优化者等不起，只能自己开分支。对 Apple 统一内存路线，差异在硬件假设。antirez、liuliu（M5 128GB，decode 约 30 tok/s、prefill 约 400 tok/s）说明大内存 Mac 用 Metal 带宽就能拿到可比甚至更好的体验；modchip 的主战场是带宽更紧张的 x86 双通道 DDR，所以才需要 NTA 流式读取、2MB 大页、CCD 绑核这些微架构手段抠性能。它自己也带 apple-silicon 目录，README 给 M4 Max 的方案是零拷贝统一内存 Metal 着色器加 NEON/AMX（自述 238.9 GB/s 内存带宽、256K 上下文零 swap），等于承认两条路线并存。同期还有 Bonsai、Strata、Pulsar 等一批 llama.cpp 分叉各做流式权重或特殊量化，SillyUsername 的解法是用 llamaswap 在多个推理引擎之间按需切换，这类「分叉并存」的格局短期内不会消失。

## 判断与适用建议

值得试的人：手里有 64GB 以上内存、没有像样 GPU、想尝鲜 284B 级模型，且能接受 9-15 tok/s 和 1.7bpw 质量风险的玩家；以及做隔夜长任务的自动化场景，Aurornis 的说法有代表性，「跑 1 小时还是 10 小时不重要，早上干完就行」。不值得的人：需要交互式 coding agent 速度的（kgeist 的 116 秒质疑没被回应）、内存低于 64GB 的、对输出质量敏感的。验证清单五条：先跑 Nemotron-30B 档验证安装路径，绕开 ar-nelson 式张量错误；用自己的真实任务测质量，别只信自述的 100/100 quality gate；跑长上下文时用 htop 盯 VmRSS 和 swap，核对「零 swap」声称；同机对照 unsloth IQ1_S 加原版 llama.cpp，量化补丁带来的增益和损失；最后确认补丁能对自己锁定的 llama.cpp 版本复现构建。后续值得盯三件事：76.87GiB 的口径争议是否在 README 修订后消失（11-08 已有一条 commit 专门对齐 bpw 表述，说明作者在读评论区）；ar-nelson 报告的张量形状错误是否修复，这决定「按文档能装上」是否成立；leaderboard 能否长出更多机型和独立的复测数据。核心一句话：llama-modchip 展示的是「补丁集 + 重文档」的极限压榨路线，机制拆解处处有料，但所有性能数字都还是项目自述，评论区既有 15W 稳定运行的正面样本也有 core dump 的翻车记录，试之前先想清楚自己属于哪一类。
