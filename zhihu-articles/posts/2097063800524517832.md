### 两个端口

openclaw gateway 默认使用 18789，而 openclaw mcp host sandbox 使用 18790。因此两个端口都得放行。

其中，openclaw mcp host 会去 3245 端口的服务拉取 mcp apps 的 ui:/ 资源来渲染。

下述是解决问题的流程，关个流水账，即前一个问题修订完，后续暴露新问题接着解决。

### 问题1: 为何 --detach 仍没有常驻

```text
vx --no-config --from cadgen==0.7.26 cadgen viewer --host 127.0.0.1 --detach --json
```

`--detach` 确实设计成让查看器常驻。源码 `main.py` 里的 `launch_detached()` 也说明了这一点：子进程使用 `start_new_session=True` ，并设置 `stdin=DEVNULL` ，输出写入日志文件，因此正常终端里关闭 shell 不会导致它退出。

但它逃不出 openclaw 这个 agent shell 的进程组。 `--detach` 只是新建了一个 session，而 OpenClaw 每次执行 `exec` 时，都会把整棵进程树的清理权限统一放在自己的 cgroup 里。命令结束后，子进程被一并终止。这不是 `cadgen` 的 bug，而是 openclaw 调用它的方式不对。实测：命令返回后再过 20 到 30 秒请求它，连接就会被拒绝，进程也消失了。

解决，使用 systemctl 来自动启用此服务

/home/h/.config/systemd/user/cadgen-viewer.service

```text
[Unit]
Description=CAD Viewer (cadgen) on 127.0.0.1:3245
After=network.target

[Service]
Type=simple
ExecStart=/home/h/.local/bin/uvx --no-config --managed-python --python 3.13 --from cadgen==0.7.26 cadgen viewer --host 127.0.0.1 --json
WorkingDirectory=/home/h/.openclaw/workspace

# OpenClaw kills leftover descendants in the exec cgroup. If a viewer is
# started from an agent shell, move it into this service's cgroup so it
# outlives that command; reassign happens via `systemctl --user set-property`.
KillMode=process
Restart=on-failure
RestartSec=2

[Install]
WantedBy=default.target
```

### 问题2: 反代 3245 端口访问受限

```text
192.168.2.3:3245 {
        bind 192.168.2.3
        tls internal
        reverse_proxy 127.0.0.1:3245 {
                header_up X-Forwarded-For {http.request.remote.host}
                header_up X-Real-IP {http.request.remote.host}
        }
}
```

访问： [https://192.168.2.3:3245/](https://192.168.2.3:3245/)

```text
{"error":"Host header '192.168.2.3' is not a local name; refusing (DNS-rebinding defense)"}
```

这是 `cadgen` 自带的一个限制，并非证书问题。

报错原因

`http_app.py` 中的 `host_is_allowed()` 有一层 DNS-rebinding 防护：

- 当 viewer 绑在 `127.0.0.1` 时，它只接受 Host 为 `127.0.0.1` 、 `localhost` 或 `::1` 的请求。
- 当走 Caddy 代理时，Caddy 会把原始 Host 头 `192.168.2.3` 原样交给 viewer，于是它触发 403 并返回你看到的那条提示。
- 源码中写明：只要绑定的地址不是 loopback 地址，防护就整体跳过。

解决：修改为 添加 `header_up Host 127.0.0.1:3245`

```text
192.168.2.3:3245 {
 	bind 192.168.2.3
 	tls internal
 	reverse_proxy 127.0.0.1:3245 {
		header_up Host 127.0.0.1:3245
 		header_up X-Forwarded-For {http.request.remote.host}
 		header_up X-Real-IP {http.request.remote.host}
 	}
 }
```

### 问题3: mcp apps 仍没显示 [mcp-app] failed to prepare ui

> Deepseek没查这个Log，按qwen3.8-max分析出此问题。

各服务都起来了，但 gateway log’s error message:

```text
[mcp-app] failed to prepare ui://cad/.../app.html from "cadmcp": MCP App resource exceeds 2097152 bytes
```

原因 ：

> The 2 MiB upper limit is still hardcoded even in the beta version — upgrading OpenClaw 2026.10.6 won’t solve it. The problem has been identified as a compatibility issue between the cadgen 0.7.26 app page (2.47 MB) and OpenClaw’s hard 2 MiB MCP App resource limit.

如何:

**结论:没有配置项可以调。** 这个 2 MiB 上限是 OpenClaw 代码里的硬编码常量,不是配置:

- `mcp.apps` 的 schema 只有 `enabled` / `sandboxOrigin` / `sandboxPort` 三个字段( `additionalProperties: false` ),没有任何大小相关项
- 常量 `MCP_APP_RESOURCE_MAX_BYTES = 2097152` 写死在 `dist/mcp-ui-resource-*.mjs` 里,无环境变量覆盖

cadgen 0.7.26 的 MCP app 页面是自包含 HTML,实测 **2,477,769 字节** ,超过 2 MiB 上限,gateway 准备 ui resource 时直接拒绝。日志铁证:

```text
[mcp-app] failed to prepare ui://cad/5cdcb02ef480d752/app.html from "cadmcp":
MCP App resource exceeds 2097152 bytes
```

代价:这个常量是防超大 resource 吃内存的硬边界,改 dist 属于非官方补丁,下次 OpenClaw 升级会被覆盖,

```text
set -e
D=/home/h/.nvm/versions/node/v24.22.1/lib/node_modules/openclaw/dist
F=$D/mcp-ui-resource-CIh9bVXM.mjs
B=/home/h/.openclaw/workspace/tmp/openclaw-dist-backup
mkdir -p $B
cp -n $F $B/mcp-ui-resource-CIh9bVXM.mjs.orig
grep -c "MCP_APP_RESOURCE_MAX_BYTES = 2097152" $F
sed -i 's/MCP_APP_RESOURCE_MAX_BYTES = 2097152/MCP_APP_RESOURCE_MAX_BYTES = 8388608/' $F
grep -oE "MCP_APP_RESOURCE_MAX_BYTES = [0-9]+" $F
echo "backup: $(ls -la $B)"
```

### 问题4: mcp apps 仍无显示，MCP App unavailable: MCP App initialization timed out

Console 里的关键报错找到了,是第二道关卡: **内层 app 文档的 CSP 把 blob: 模块脚本拦了** 。

```text
Loading the script 'blob:null/…' violates Content Security Policy directive:
"script-src 'self' 'unsafe-inline'"  →  Failed to fetch dynamically imported module
```

cadgen 的 app 页把 worker/模块内联成 blob URL 再动态 import,而 OpenClaw 给内层 srcdoc 文档生成的 CSP 里 `script-src` 只有 `'self' 'unsafe-inline'` ,没有带上 cadgen 在 resource 元数据里声明的 `blob:` (它声明了 `resourceDomains: ["data:","blob:"]` )。于是 app 初始化超时。

The CSP generation logic has been found. The mechanism is now completely clear:

- OpenClaw sandbox’s `normalizeSandboxHostCsp` **only accepts http/https/ws/wss** for `resourceDomains` ( `blob:` / `data:` are directly filtered out; only `mediaDomains` lets `blob:` through)
- The `resourceDomains: ["data:", "blob:"]` declared by cadgen gets normalized to an **empty list** , so what ultimately gets generated is `script-src 'self' 'unsafe-inline'` (with the blob part missing)
- As a result, the app’s inline blob module’s dynamic import gets blocked by CSP → initialization times out → “MCP App unavailable”

解决：

OpenClaw 的 sandbox CSP 规范化器把 cadgen 声明的 `resourceDomains: ["data:","blob:"]` 整个过滤掉了(只认 http/https/ws/wss),导致内层文档 `script-src` 缺 `blob:` ,app 内联的 blob 模块 import 被拦、初始化超时。补丁让 `resourceDomains` 走 `allowMediaSchemes` 通道保留 `blob:`

```text
set -e
D=/home/h/.nvm/versions/node/v24.22.1/lib/node_modules/openclaw/dist
F=$D/sandbox-host-C4L4QQ2a.mjs
B=/home/h/.openclaw/workspace/tmp/openclaw-dist-backup
[ -f $B/sandbox-host-C4L4QQ2a.mjs.orig ] || cp $F $B/sandbox-host-C4L4QQ2a.mjs.orig
echo "occurrences: $(grep -c 'resourceDomains: normalizeDomains(record.resourceDomains),' $F)"
sed -i 's/resourceDomains: normalizeDomains(record.resourceDomains),/resourceDomains: normalizeDomains(record.resourceDomains, { allowMediaSchemes: true }),/' $F
grep -oE "resourceDomains: normalizeDomains\(record.resourceDomains[^)]*\)" $F
ls -la $B
```

### 问题5: 终于 line 渲染窗口显示，但渲染内容未加载

![](https://pic1.zhimg.com/v2-afc8a3558af69cba96c3e1285f070554_r.jpg)

app 已经能加载了(CSP 补丁生效),但卡在下一层: **surf worker failed** —— 这是 STEP 曲面细分 worker。最大嫌疑:该 worker 要编译 WebAssembly,而 sandbox CSP 的 `script-src` 没有 `wasm-eval` ,WASM 实例化被拒。

这次失败的根子找到了,又补了两处补丁并重启:

**根因** : `surf worker failed` 不是模型文件问题——cadgen 的曲面细分 worker 是 **WASM blob worker** (我把 app 页里的 gzip+base64 内联块解压验证过,含 `WebAssembly` 调用),而 sandbox CSP 的 `script-src` 没有 `'wasm-eval'` ,CSP 直接禁止 worker 里编译 WASM → worker 崩溃 → 报 “Couldn’t load model”;日志里那一片 `MCP App request rate limit reached` 是失败后的重试风暴撞上了每视图限额(并发 4 / 120 次每分钟),属次生症状。

**补丁 #3** :CSP `script-src` 加入 `'wasm-eval'` (只放行 WASM 编译,不放开 eval)。 **补丁 #4** :每视图请求限额放宽(并发 4→16、120→1200 次/分、工具调用 30→300 次/分),cadgen 的正常加载突发就会超 4 并发,不放宽还会偶发断流。

还是不行，
