继扒拉 [DeepSpeed](https://zhuanlan.zhihu.com/p/668181423) 推理代码之后，最近又扒拉了扒拉 llama.cpp，当然其实最近还有好几个类似的框架，比如 mlc 、tgi、lightllm、vllm 等等，目不暇接。（如果时间比较充裕确实可以都读一读）

其实，这个感觉很熟悉，很像 16、17 年那时候，keras、theano、caffe、mxnet、tensorflow 等等，其中有些可能现在不提都想不起来，这些框架都是可以即训练又推理的一体化大框架。不过后来大家也都知道了，pytorch 还是几乎实现了大一统。同时，针对 CNN 的推理尤其是轻量级芯片环境还出现了很多专门的推理框架，比如 ncnn、mnn、tnn、tensorrt 等等。

当时还有一个很小众的框架，叫做 **darknet**，它是当时 yolov1、2，还有 yolo9000 这几个yolo 原版作者自己写的框架，这个项目非常的简洁优雅，c/c++ 的实现，麻雀虽小五脏俱全，依赖极少。编译和运行时的效率都极高。

很快，Transformer 结构就带来了深度学习领域的一次革命，同时也会给训练推理框架领域带来一次革命，pytorch 还在延续强大生命力的同时，又有新的框架乘势而上完成新的轮子的制造。llama.cpp 就是这些新晋之秀。

不同于 DeepSpeed ，llama.cpp 不依赖于 Torch。所以，怎么说呢，在我看来，llama.cpp 有点像 darknet 的感觉，简练，直接。

虽然简练直接，但是 llama.cpp 功能还是非常强大的，毕竟代码总量还是很大的。10000+ 行以上的文件还是有好几个，但是总体结构看起来却很直观，总共也没几个文件。抛开没有用的结构，需要什么就写什么，代码可读性极好极好的。

所以可以说，llama.cpp 其实是一个非常适合通过阅读代码来学习整个 LLM 推理技术的样本项目。

**PS.***Andrew Karpathy 还出品了一个*[llama2.c](https://github.com/karpathy/llama2.c)*，专注于极简和简洁性。回头也一起研究研究。*

llama.cpp 对 llama2 的支持还是比较直接的，毕竟人家把支持都写名字里面了。它基于 LLaMA/2 模型手写的纯 C/C++ 版本：支持 CPU 推理，当然也支持各种底层库推理（CUDA/OpenCL），具有 FP16 和 FP32 的混合精度、支持8/4bit量化等等。

这里有一个小的情况，**NOTICE**：就是 bin/main 中**-ngl**这个参数，它代表：n_gpu_layers，这个参数默认是 0，所以如果不设置为一个比较大的数字，整个模型就会到 CPU 上面跑，即便你用了 cublas 等各种编译参数也是在 CPU 上。

### 并行机制：

和[读 DeepSpeed 时关注的问题](https://zhuanlan.zhihu.com/p/668181423)一样，比如相对较大的模型推理时放不下的时候是如何处理的。这就是涉及多卡支持与模型并行的底层逻辑是怎么做的了。

核心问题就是怎么切分模型和切分运算，因为 $W_k W_q W_v$ 是需要和输入 $X$ 进行矩阵乘得到 $K Q V$ 张量的。

ggml-cuda.cu 中的 ggml_cuda_op_mul_mat 函数就很有代表性了。

```text
ggml_graph_compute_helper -> 
ggml_compute_forward -> 
ggml_cuda_compute_forward -> 
ggml_cuda_mul_mat -> 
ggml_cuda_op_mul_mat ->
ggml_cuda_op_mul_mat_cublas / ggml_cuda_op_dequantize_mul_mat_vec
```

这个函数只有 300+ 行的代码，放在这个 8000 多行的 cu 文件中也不起眼。mul_mat 这个 op 在所有的 op 中是最费时的，其他的 op 在 llama.cpp 工程中，大部分因为计算量较小基本都没有采用多卡并行实现。

mul_mat 主要完成了对 src0 （参数数组），src1（运算数组）两者的矩阵乘法，并存入 dst（结果数组）之中。代码（ggml_cuda_op_mul_mat）中，运算逻辑会被拆分为三层，batch、device、tilling 三个层面三个循环。最后的矩阵才会交给 cublasGemmEx、cublasSgemm （ggml_cuda_op_mul_mat_cublas） 或者作者自己手写的 cuda kernel （ ggml_cuda_op_dequantize_mul_mat_vec），最后的矩阵一定是在单一设备中集中计算完成的。而多卡并行就是在 device 一层来完成的，核心逻辑就是会将运算拆分到不同的设备上面去，算完之后再把结果同步到下一次用的设备（gpu 或者 cpu），以完成每一层的多卡模型并行机制。

（Llama2 模型中 tilling 层面的循环暂时大部分矩阵运算时并没有展开）

device 拆分的逻辑简单说就是矩阵分块，和参数 load 时保持一致的位置关系即可。这块和 DeepSpeed infer 的并行逻辑其实是一样的。

一般的，ggml_cuda_op_dequantize_mul_mat_vec 和 ggml_cuda_op_mul_mat_cublas 主要处理 QKV 参数矩阵乘和 FFN 前馈网络线性层的计算。参数矩阵和前馈网络都是前一步张量和参数进行矩阵乘积。ggml_cuda_mul_mat_mat_batched_cublas 主要计算 KQV Attention 部分的计算，是 KQV 三个张量的互计算，不依赖模型参数。而加速这块的 KV Cache 在后续后续会进行另外的介绍。

对于矩阵分块计算，算是基础的矩阵知识，可以参考：[大师姐：矩阵分块相乘](https://zhuanlan.zhihu.com/p/133330692) 等博文。以及 Megatron-LM arXiv:1909.08053v4 中的配图。

### KVCache：

这里单独再分析一下 kv cache 部分的逻辑。[图示来源](https://medium.com/@joaolages/kv-caching-explained-276520203249)

![](https://pic4.zhimg.com/v2-1098293d800e6fe7845eb38c11b2356b_r.jpg)

![](https://pic4.zhimg.com/v2-7e017365d463842a7b73f6068684443f_r.jpg)

![](https://pic2.zhimg.com/v2-26c97ac74bf7fe2ec3aef84bb2a2766d_r.jpg)

![](https://pic3.zhimg.com/v2-d5b9b88379eefe0f933fb5fdcd15d0b6_r.jpg)
*KV Cache w/wo 对比图*

为了方便理解上图，需要先理解 LLM 推理的过程是一个自回归的过程，每次生成一个 token 的时候需要结合前面所有的 token 做 attention 操作。也就是说前 i 次的token会作为第 i+1 次的预测数据送入模型，才能得到第 i+1 次的推理 token。

KV Cache 核心节约的时间有三大块：**1）**前面 n-1 次的 Q 的计算，当然这块对于一次一个 token 的输出本来也没有用；**2）**同理还有 Attention 计算时对角矩阵变为最后一行，和 1）是同理的，这样 mask 矩阵也就没有什么用了；**3）**前面 n-1 次的 K 和 V 的计算，也就是上图紫色部分，这部分是实打实被 Cache 过不需要再重新计算的部分。

这里还有个 softmax 的问题，softmax 原本就是针对同一个 query 的所有 key 的计算，所以并不受影响。

*以下描述有部分不严谨，深入研究后还需要修改：*

kv cache 部分的逻辑在代码中主要的在流程逻辑中实现的，而不是矩阵乘法部分完成的（这和前文并行部分是没有关系的）。也就是说在矩阵乘法运算逻辑部分，其实它是看不到哪些数据是从 cache 中拿出来的哪些是新算的，它只需要做好运算即可。逻辑流程部分是在 main.cpp（llama2 推理流程）中维护了 kv_cache 的 struct ，以及相关的支持操作函数（如 llama_kv_cache_seq_shift、llama_kv_cache_seq_rm 等）。

这里的 kv_cache 结构在代码注释中说是一个 ring-buffer 的设计（猜测应该为一个序列，序列 id 超限之后循环取模即可）。但是在结构体定义时并没有具体的代码，所以是存疑的。某个 [issue](https://github.com/ggerganov/llama.cpp/issues/4251) 也提到了这个问题，并结合这个 [pr](https://github.com/ggerganov/llama.cpp/pull/3228) 的更新日志推测理解，llama_kv_cache_??? 等操作 cache 的 cell 的 seq_id 完成一个循环空间的复用。

再进一步，我们看一下 llama 网络结构中下图红色框部分。这里的 Mask 就是对应“KV Cache w/wo 对比图”中without cache 中的半对角线矩阵。所以，我们在回到实际计算部分，如果开启 KVCache 的话，每次实际计算的 Q 为 [**1**, emb_size]，K 为 [emb_size, **k**] ，不开启的话 Q 则会变为 [**k**, emb_size]。

![](https://pic1.zhimg.com/v2-6eddbabe0877eb43b2e46d1e7367bf42_r.jpg)
*llama/2 结构图*

在矩阵乘法部分，这部分运算不依赖预训练的参数，在代码实现中（ggml_cuda_mul_mat_mat_batched_cublas） 和参数矩阵乘法部分不同，同时还要兼顾多头处理，一般的张量尺寸是 [128, k, 32]， k = max(k, 32) 也就是当 k < 32 时会统一按 32 计算。实测这块的耗时也是比较高的，会放到后续的[解读笔记](https://zhuanlan.zhihu.com/p/672289691)中再进行详细讲解。

这里随着 K 会越来越长，计算量就越来越大，同时越来越长的 K 也会在计算更大的矩阵时被显存空间限制。

同时，这里作者暂时没有对其进行多卡并行加速，暂时是放在单卡上执行的。

因此有[评论](https://www.zhihu.com/question/591646269/answer/3246726206)会讲：Decoding 阶段以难以优化而臭名昭著。因为每次只能解码一个token，计算量本来就很小，还需要访问一个随着解码步数增加而不断累计 KVCache，因此严重受限于加速卡的片上带宽。
