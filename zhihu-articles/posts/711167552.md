本文结合SGLang论文与SGLang代码库，分析了SGLang技术的原理。

## 1. 整体脉络

本篇是SGLang v2版本，SGLang V1版本提出了2个技术，分别为前端编译器部分和RadixAttention，RadixAttention类似的技术更有数十篇文章介绍。SGLang v2版本在V1版本的基础上增加了fast constrained decoding和API Speculative Execution。下面详细介绍这三块技术。

![](https://pic4.zhimg.com/v2-a58502a10657d62701d64b1c7cbc9531_r.jpg)

如上图所示为SGLang的整体架构，模块上分为前端和后端，**整体功能上有4个大的功能分别为前端SGLang语言、RadixAttention、fast constrained decoding和API Speculative Execution。**

### 前端部分

- 提供一个LLM应用程序编写的DSL语言；

使用方式如下：

```python
from sglang import function, system, user, assistant, gen, set_default_backend, RuntimeEndpoint

@function
def multi_turn_question(s, question_1, question_2):
    s += system("You are a helpful assistant.")
    s += user(question_1)
    s += assistant(gen("answer_1", max_tokens=256))
    s += user(question_2)
    s += assistant(gen("answer_2", max_tokens=256))

set_default_backend(RuntimeEndpoint("http://localhost:30000"))

state = multi_turn_question.run(
    question_1="What is the capital of the United States?",
    question_2="List two local attractions.",
)

for m in state.messages():
    print(m["role"], ":", m["content"])

print(state["answer_1"])
```

### 后端部分

- RadixAttention，针对prefix share或者多轮会话场景；
- fast constrained decoding；
- API Speculative Execution；

使用方式如下：

和vLLM等类似，启动服务端之后，客户端发送请求单到服务端。

服务端：

```bash
python -m sglang.launch_server --model-path meta-llama/Meta-Llama-3-8B-Instruct --port 30000
```

客户端：

```bash
curl http://localhost:30000/generate \
  -H "Content-Type: application/json" \
  -d '{
    "text": "Once upon a time,",
    "sampling_params": {
      "max_new_tokens": 16,
      "temperature": 0
    }
  }'
```

我们可以看出，对于后端来说，使用方式和vLLM类似，前端来说，提供了自己的DSL，目标是替代LangChain这种框架。利用解释执行DSL的方式进行性能优化。

### 与传统大模型推理引擎区别

到此我们总结一下SGLang和传统的大模型推理引擎如vLLM不同之处。

1. 后端部分，使用上和vLLM等推理引擎类似，均可以部署服务端，后端的3个核心技术，目前RadixAttention类似的技术在其他推理引擎已经广泛使用或者被研究了。压缩FSM以及API Speculative Execution目前在其他推理引擎中没有使用。
2. 前端部分，提供一个DSL语言，用户基于该语言编写程序，该语言是解释执行的，这部分用于替代如传统LangChain的。
3. 换句话说，如果使用SGLang，原来用户LangChain + 推理服务的模式转换成了 SGLang DSL + SGLang服务的模式。

接下来，分为几章详细介绍一下本文相关的技术。

### SGLang的4个技术的个人看法

**RadixAttention**：树的结构维护历史的kv cache，从而减少prefix kv cache的计算，达到减少prefill计算的效果，这个是未来推理框架的标配；

**fast constrained decoding**：本质上是一次decode生成多个token，和lookahead那种投机采样，但是看起来没有检验阶段，依赖结构化语言场景（LLM产生的句子有结构化，如json类场景），可以认为是业务场景的lookahead，这种；

**API Speculative Execution**：文中举的例子，其实RadixAttention已经起到了一些优化的作用了，暂时没看懂这个的额外意义；

**SGLang前端语言**：看起来是可以替代LangChain，个人对这一点还是持保留态度的。

- 首先某一个领域有DSL是没问题的，最好有如下特点即优势：
- DSL领域一般用于相对成熟的业务领域如SQL语言、工作流引擎，大模型应用这个领域目前还不成熟，发展非常的快；
- DSL可以简化简化应用开发，如Hive SQL替代Map Reduce；
- DSL可以通过编译或解释执行的技术提升性能，如Pytorch的命令式python写法没有tensorflow的声明式写法效率高（tensorflow 1 也可以认为是一种DSL）；
- 新的DSL会有一些学习的成本；
- 如果同时满足前3点，且第4点成本低，笔者认为DSL即可替代原来的命令式方式；
- 可能笔者对大模型应用领域的了解程度还不够，所以暂时无法去理解该优势；

## 2. RadixAttention

RadixAttention首先介绍主要原因是，在本文中，该技术更容易理解一些，属于大模型推理技术中attention常用优化之一。

### 多轮会话KV缓存

当今使用的大多数 LLM（例如 GPT-3 [5]、PaLM [9] 和 LLaMA [49]）都基于自回归 Transformer 架构 [51]。这些模型根据前一序列预测序列中下一个标记的概率。在推理期间，模型首先通过前向遍历来处理一段输入标记（该过程称为“预填充”）。接下来，按顺序对输出标记进行解码，每个标记都取决于先前的标记（该过程称为“解码”）。我们把采取序列的输入标记并生成序列的输出标记的过程称为单一生成调用。在这个过程中，每个标记会生成一些中间张量，用来解码进一步的标记。这些中间张量称为“KV 缓存”，以自注意力机制中的键值对而命名。在本文中讨论优化时的一个重要观察是，KV 缓存的计算仅仅取决于所有先前的标记，所以前缀相同的不同序列可以重复使用前缀标记的 KV 缓存，避免冗余计算。

在 LLM 程序中，通常会将多个文本段和生成调用追加到单个提示符。缓存先前的标记在多个链式调用中计算出的 KV 缓存可以减少冗余计算。然而，这种优化既不免费也不简单，因为它需要额外的存储和更复杂的内存管理。此外，在 LLM 程序中，通常会从单个提示符生成多个输出，或者从当前状态中分叉一个新的提示符 [25]。基本的前缀共享已在 vLLM [23] 中得到研究。还可以采用更高级的共享模式，如不规则树形结构共享。下图展示了在多个调用中 KV 缓存共享的四种典型模式；没有一个现有的系统可以自动处理所有模式。相反，本文提出RadixAttention 可以自动处理所有模式，而且可以在运行时处理。

![](https://pic4.zhimg.com/v2-bda4773138f206a697d70b2de9d23bd1_r.jpg)

上图是KV缓存共享示例。蓝色框表示可共享提示部分，绿色框表示不可共享部分，黄色框标记不可共享的模型输出。可共享元素包括小样本学习示例、自一致性问题 [53]、多轮聊天中的聊天记录以及思维树中的搜索记录。

### RadixAttention

**上述多轮会话不同的程序实例通常会共享一些常见部分（例如系统提示、历史会话）。这些场景在执行过程中会创建许多共享的提示前缀，从而为重复使用 KV 缓存提供大量机会**。

鉴于存在 KV 缓存重复使用机会，本部分介绍了RadixAttention（基数注意力），这是一种用于在运行时自动且系统地重复使用 KV 缓存的新颖技术。与在生成请求完成后丢弃 KV 缓存的现有系统不同，我们的系统会将缓存保留在基数树中的提示和生成结果中，从而实现高效的前缀搜索、重复使用、插入和驱逐。我们实施了 LRU 驱逐策略和缓存感知调度策略以提高缓存命中率。基数注意力与持续批量化 [60]、分页注意力 [23] 和张量并行 [44] 等技术兼容。此外，当没有缓存命中时，它只引入了可以忽略不计的内存和时间开销。

**RadixAttention**。Radix树是一种数据结构，用作经典树（前缀树）的空间高效替代方案。与典型树不同，Radix树的边不仅可以标记为单个元素，还可以标记为长度可变的元素序列，从而显著提高了效率。在我们的系统中，我们利用Radix树来管理令牌序列和它们相应的KV缓存张量之间的映射。这些KV缓存张量存储在非连续、分页布局中，其中每个页面的大小相当于一个令牌。由于GPU内存被KV缓存快速填满，我们引入了简单的LRU驱逐策略，该策略首先驱逐最近最少使用的叶。通过首先驱逐叶，我们能够重新使用它们的公共祖先，直到这些祖先成为叶并也被驱逐。

在连续分批设置中，我们无法驱逐当前运行批次使用的节点。因此，每个节点都维护一个引用计数器，表示有多少正在运行的请求正在使用它。如果节点的引用计数器为零，则该节点可被驱逐。请注意，我们不会预先分配固定大小的内存池作为缓存。相反，我们让已缓存的令牌和当前运行的请求共享同一内存池。因此，系统会动态地为缓存和正在运行的请求分配内存。当有足够的等待请求运行时，系统将驱逐所有已缓存的令牌，以支持更大的批处理大小。图 3 展示了为多个传入请求维护基数树的方式。前端解释器将完整的提示发送至运行时，而运行时执行前缀匹配和重用。树结构存储在 CPU 上，维护开销可以忽略不计。在 fork 原语执行期间，前端会首先将前缀作为提示进行发送，确保前缀已正确插入树中。然后，它会发送剩余的提示。此“前端提示”简化了运行时的调度和匹配，很好地举例说明了前端运行时协同设计的优势。

**图 3解释说明**：具有 LRU 驱逐策略的 RadixAttention 操作示例，跨越九个时间点进行了说明。该图展示了基数树在响应各种请求中的动态演变。这些请求包括两个聊天会话、一批小样本学习查询和自我一致性采样。每个树边都带有表示子串或标记序列的标签。节点以颜色编码以反映不同的状态：绿色表示新添加的节点，蓝色表示在时间点内访问的高速缓存节点，红色表示已驱逐的节点。

- 在步骤 (2) 中，服务器处理传入的用户消息“你好”并使用 LLM 输出“嗨”进行回复。系统提示“您是一位有用的助手”，用户消息“你好！”，以及 LLM 回复“嗨！”被合并到树中，作为链接到新节点的单个边。

- 在步骤 (4) 中，开始新的聊天会话。将 (3) 中的节点“b”拆分为两个节点，以允许两个聊天会话共享系统提示。

**具有缓存感知的调度**。我们将缓存命中率定义为已缓存提示标记数除以提示标记数（number of cached prompt tokens / number of prompt tokens）。当等待队列中有许多请求时，执行请求的顺序会显著影响缓存命中率。例如，如果请求调度程序频繁地在不同的、不相关的请求之间进行切换，则会导致高速缓存抖动和较低的命中率。我们设计了一个具有缓存感知的调度算法来提高缓存命中率。在批处理设置中，我们按匹配的前缀长度对请求进行排序，并优先处理具有较长匹配前缀的请求，而不是使用先到先服务的调度。算法 1（附录）显示了具有连续批处理的缓存感知调度的伪代码。该算法使用最长共享前缀优先顺序。在更注重延迟的设置中，我们仍然能够容忍有限的批次重新排序来提高缓存重用。此外，我们为离线情况中的最优调度证明了以下定理。

**定理 3.1**。对于一批请求，我们可以通过以深度优先搜索顺序访问请求的基数树，在缓存大小≥最大请求长度的情况下获得最优缓存命中率。最长共享前缀优先顺序等效于深度优先搜索顺序。

证明在附录中的 A.3 节中。在在线情况下，DFS 顺序将被中断，但我们的时间表仍近似于在全基数树的扩充部分上执行 DFS 行为，如 A.3 节中所述。虽然贪婪的缓存感知时间表能够实现高吞吐量，但它可能导致饥饿。我们将它与其他公平调度方法 [42] 的集成留待以后的工作中完成。

分布式案例。RadixAttention 可以扩展到多 GPU。对于张量并行度，每个 GPU 都维护一个分片的 KV 缓存。没有额外的同步需求，因为树操作相同。在附录中的 A.4 节中讨论了具有多个工作负载的数据并行度。

**对于RedixAttention设计，目前的趋势是结合GPU、CPU、SSD对kv cache做多级缓存。**

## 3. fast constrained decoding

本节名为fast constrained decoding，核心加速原理是在**受限制约束条件下，可以一次解码多个 token。**所以看下面细节的时候，带着这两个关键问题去看，个人认为这个在某些场景加速效果会非常明显，毕竟直接减少了LLM generate执行过程中forward的次数。

1. 目的是一次性解码多个token；
2. 怎么样才能一次性解码多个token（本节举的例子是json类的正则表达式，由于json类的格式是具体结构化的，故很多场景是不需要借助LLM去生成下一个词的，如下图4所示，{"summary之后如果需要满足json格式，那么下面的几个词必然是 " : 空格 这三个词，就能达到一次解码多个），即利用FSM；
3. 本文的FSM涉及了一些编译原理相关的基础知识如DFA、NFA，需要详细学习的可以看编译原理课程的词法分析部分；

LLM中对结构化输出（例如 JSON 模式）的受限解码，其中 LLM 的输出被限制为遵循由正则表达式定义的特定语法规则（第 4 节）。**在这些约束条件下，通常可以一次解码多个 token**。然而，现有系统一次只解码一个 token，导致解码速度不理想。它支持对结构化输出来进行更快的约束解码。现有系统仅通过掩盖不允许的令牌的概率来对下一个令牌遵循约束，使它们一次只能解码一个令牌。**相反，我们的系统分析约束并构建一个压缩有限状态机来表示该约束**。此方法在任何可能的情况下将多令牌路径压缩成单步路径，允许一次解码多个令牌以实现更快的解码速度。最后，SGLang 还支持仅 API 模型，例如 OpenAI 的 GPT-4，我们引入了第三种技术，API 预推测执行，以优化仅 API 型模型的多调用程序。<br>

![](https://pic1.zhimg.com/v2-d1afc4087e53405b5f5c748f87eb777a_r.jpg)

在 LM 程序中，用户常常想制约模型的输出以遵循特定的格式，例如 JSON 概览。这可以改善控制能力和健壮性，以及让输出更易于解析。SGLang 提供了一个正则参数以使用正则表达式强制此类制约，而这些正则表达式对许多实际案例来讲都足够具有表达性。现有系统通过将正则表达式转换为有限状态机 (FSM) 来支持这一过程 [54]。在解码过程中，它们维护当前 FSM 状态，从下一个状态中检索允许的词法单元，并且将无效词法单元的概率设置为零，逐个词法单元解码。然而，这种逐个词法单元的方法效率低下，因为有时可以同时解码多个词法单元。例如，常量序列 {“summary”: " 在图 2 中跨越正常解码过程中的多个词法单元，如在图 4 (c) 中所示，它需要多个解码阶段，即使在解码它时只有一个有效的后继词法单元。因此，整个序列可以在一个步骤中解码（即前向通过）。然而，现有系统一次只能解码一个词法单元，因为现有系统中的 FSM 和模型执行器之间缺乏集成，这阻止了多词法单元处理，导致解码缓慢。

SGLang 通过在压缩 FSM 中创建一个快速受限解码运行时环境，克服了这一限制。此运行时环境会分析 FSM，并将 FSM 中相邻的单一过渡边压缩为单个边（如图 4 (b) 所示），这样它便能够识别何时可以同时解码多个标记。在图 4 (d) 中，压缩过渡边中的多个标记可以在一次前向传递中解码，这极大地加速了解码过程。它还适用于一般情况和所有正则表达式。有关背景和实现的更多详细信息，下面进行分析。

针对更快速受约束解码而配置的有限状态机的背景和实现细节。我们的目标是让 LLM 跟随正则表达式（regex），它提供更高的表达性，并可用于表示 JSON 架构等常见格式。为了达成这一目标，我们将正则表达式转化为一个有限状态机（FSM），以便在解码期间指导生成过程 [54]。FSM 本质上是一个带有节点（状态）和边（带有字符串/字符的转换）的图表。从一个初始状态开始，每个转换会附加边上的字符串以根据一组最终状态移动到下一个状态，从而完成该过程。这种机制会指导 LLM 的解码，根据 FSM 的当前状态转换来过滤无效标记，如图 10 所示。该解码过程可能包含在 FSM 中执行多次转换，直至达到一个最终状态。

![](https://pica.zhimg.com/v2-dd745898bc1b6135b6e5b128ecab070a_r.jpg)

受限解码的挑战源自于限制通常以自然语言格式表达这一事实，即 regex 由字符/字符串描绘，而 LLM 被设计为以标记的形式对这些进行解释和处理。这创造了一个复杂的场景，因为字符串和标记之间的映射错综复杂，并且缺乏一一对应的关系 [22]。

### Compressed Finite State Machine

为了简化压缩 FSM 的构建，我们基于字符/字符串而非标记来构建原始 FSM。我们正式定义以下奇异转换边和压缩边的概念：

- 奇异转换边：一条边是奇异转换边，如果 1) 其源节点仅有一个后继节点，且 2) 其上仅有一个可接受的字符/字符串。
- 压缩边：一条边压缩了若干个连续相邻的边 (e0, e1, . . . , ek) 当且仅当 e1, . . . , ek 为奇异转换边。压缩边的文本是 e0、e1、. . . 、ek 文本的连接。

从基于字符的 FSM 开始，我们递归地将奇异转换边合并到其前一个边，直至无法进一步压缩，从而得到压缩 FSM。这种方法加快了解码过程，如 SGLang 在使用压缩 FSM 时的运行时效率所示，见图 11。

### Handling Tokenization Artifacts with Retokenization

**当生成一个新令牌时，我们可以获取该令牌的字符串，并搜索当前状态的所有出边，找到一个以刚解码的字符串开头的出边，然后继续前进**。**然而，当转换出边是一个经过良好压缩的边，并包含了一个非常长的字符串时，我们也可以预见到下一轮的解码字符串。这就是加速发生的地方，我们把这个过程称为跳跃前行**。然而，我们仍然需要将字符串转换为令牌，以便进行下一阶段的解码，而由于 LLM 特定的预训练和词条化方法，这并不是一件容易的事；直接划分可能会改变预期含义 [50]。例如，图 2 中压缩文本的正则表达式是 {"summary": ", which can only be tokenized as {", summary, ": and _"，根据词条化工具而不是随意将其划分为例如 {", summa, ry, and ":_"}。为了解决这个问题，我们使用原始的词条化工具对之前的全部文本以及压缩边的文本进行重新词条化，以确保与 LLM 的原始输入格式保持一致。而这只会带来较小的重新词条化开销。

### Future Extension: Addressing Distorted Probability

字符串和令牌之间的差距带来的挑战也带来了概率分布偏移的问题 [50]。例如，在图 2 中，正则表达式 “[ABCD][+-]?” 表明了从 A+ 到 D- 的等级，但是如果用卓越 | 良好 | 一般 | 低于平均线等更宽泛的术语替换，运行时可能会由于术语高于平均线处于压缩过渡而错误地将 A 映射到高于平均线，从而错误地表示等级层级。这是因为 LLM 无法识别具体的选择范围，从而导致不恰当的令牌序列。计算每个选择的准确概率需要对所有导致每个选择的所有令牌序列的概率进行求和，这使解码复杂化并增加了开销。一种解决方法是将选择或正则表达式直接包含在预填充提示中，指导 LLM 了解其选择并以适当的令牌序列输出决策。但是，这种方法无法解决概率扭曲的根本问题，突显了对进一步研究以提高压缩 FSM 的准确性的需求。

## 4. API Speculative Execution

前一节介绍了对开放式权重模型的优化，该模型需要对模型推理过程进行修改。此外，SGLang 还适用于仅限于 API 访问的模型，例如 OpenAI 的 GPT-4。但是，对于这些模型，我们只能调用黑盒 API 端点。

本节介绍了一种针对黑盒 API 模型的新优化，它通过使用推测执行来加速执行并降低多调用 SGLang 程序的 API 成本。例如，一个程序可能会要求模型针对一个角色生成描述，**方法是使用多调用模式：s += context +“name：”+ gen(“name”，stop=”\n”) +“job：”+ gen(“job”，stop=”\n”)。从本质上讲，两个 gen 原语对应于两个 API 调用，这意味着用户需要二次支付上下文的输入标记费用**。在 SGLang 中，我们可以对第一次调用启用推测执行，并忽略停止条件，让它继续生成更多标记。解释器将保留额外的生成输出，并使用它匹配和重用于之后的原语。在某些情况下，通过精心的提示工程，模型可以高精度正确地匹配模板，从而为我们节省一个 API 调用的延迟和输入成本。

## **5. SGLang前端编译器**

### **关于DSL介绍**

DSL即领域特定语言，是特定领域内提供的一些变成语言和脚本，用于在该领域更高效或者高性能的完成代码编写工作，我们平时使用的shell，算是一个。这玩意国内比较少的使用，但是国外是比较的流行的，很多复杂的软件都提供自己的DSL。DSL本质上也是一个编译技术。在大模型训练推理领域，比较流行的是triton。triton可以认为是CUDA算子领域特定语言（也可以其他语言了）。本文的SGLang可以认为是大模型应用开发的领域特定语言。

所以想学懂这部分呢，编译技术是非常关键的。

### **本文SGLang**

LLM 参与多轮规划、推理，并与外部环境交互，这是通过工具使用 [41, 38]、多种输入模态 [47, 2] 和广泛的提示技术 [30]（如小样本学习 [5]、自洽性 [53]、思维骨架 [33] 和思维树 [56]）实现的。所有这些新用例都需要进行多个 LLM 生成调用（通常是相关的），以上表明使用多调用结构来完成复杂任务的趋势。

这些模式的出现标志着我们与 LLM 的交互已经从简单的聊天转变为更复杂的 LLM 的编程式使用，这意味着使用程序来安排和控制 LLM 的生成过程。**上述高级提示技术和代理工作流属于 LM 程序的范畴。**

LM 程序有两个共同属性：

1. **LM 程序通常包含多个穿插有控制流的 LLM 调用。这是为了完成复杂任务和提高整体质量所必需的。**
2. **LM 程序接收结构化输入并生成结构化输出。这是为了支持 LM 程序的组合并将 LM 程序集成到现有的软件系统中所必需的。**

针对上述特性，本文前端部分提供了SGLang。

它为生成（例如，扩展、生成、选择）和并行性控制（例如，分叉、连接）提供了基础功能。SGLang 与 Python 的控制流和库兼容，因此用户可以轻松地使用本机 Python 语法开发高级提示工作流。我们为 SGLang 提供了一个解释器和一个编译器。解释器将提示状态管理为一个流，并将基础操作提交到流中以进行异步执行，确保对同步和程序内并行性的适当控制。此外，可以跟踪并编译 SGLang 程序以进行更多优化。

本部分以一个正在运行的示例介绍 SGLang 编程模型，描述其语言基本体和执行模式，并概述运行时优化机会。通过提供灵活且可组合的基本体，此编程模型可以简化多调用工作流中的繁琐操作（例如字符串操作、API 调用、约束规范、并行性）。

![](https://pica.zhimg.com/v2-eeb2754a981f9c5c120bda9d0e0cc784_r.jpg)

**一个正在运行的示例。**该语言是一种嵌入在 Python 中的特定领域语言。图 2 展示了一个使用分支求解合并提示方法评估图像随笔的程序 [40]。函数 multi_dimensional_judge 采用三个参数：s、path 和 essay。s 管理提示状态，path 是图像文件路径，essay 是随笔文本。可以使用 += 运算符将字符串和 SGLang 基本体追加到状态 s 以执行。首先，此函数将图像和随笔添加到提示。然后，它使用 select 检查随笔是否与图像相关，并将结果存储在 s["related"] 中。如果相关，则将提示分叉为三个副本，以从不同的维度进行并行评估，使用 gen 将结果存储在 f["judgment"] 中。接下来，它合并判断，生成摘要，并指定字母等级。最后，它按照正则表达式约束 regex 定义的架构，以 JSON 格式返回结果。SGLang 极大地简化了此程序，因为由于手动字符串操作和并行控制，使用类似 OpenAI API 的接口的等效程序将需要多 2.1 倍的行代码。

**语言基本体**。SGLang 提供用于控制提示状态、生成和并行性的基本体。它们可以与 Python 语法和库一起使用。以下是这些基本体：“gen” 调用模型进行生成，并将结果存储在变量中，变量的名称在模型的第一个参数中指定。它支持“regex”参数，以约束输出遵循由正则表达式定义的语法（例如 JSON 架构）。“select” 调用模型从列表中选择概率最高选项。运算符“+=”或“extend”将字符串追加到提示。运算符“[variable_name]”获取生成的结果。“fork”创建提示状态的并行分叉。“join”重新连接提示状态。“image”和“video”采用图像和视频输入。

**执行模式**。执行 SGLang 程序最简单的方法是通过解释器，其中一个提示被视为一个异步流。Extend、gen 和 select 之类的基元向流提交以异步执行。这些非阻塞调用允许 Python 代码继续运行，而无需等待生成完成。这类似于异步启动 CUDA 内核。每个提示都由一个后台线程中的流执行器管理，从而实现程序内并行。获取生成结果将阻塞直到它们准备就绪，确保正确的同步。或者，可以将 SGLang 程序编译为计算图，并使用图执行器执行，从而允许进行更多优化。本文默认使用解释器模式，并在附录 D 中讨论编译器模式结果。SGLang 使用其自己的 SGLang 运行时 (SRT) 支持开放权重模型，还支持 OpenAI 和 Anthropic 模型等 API 模型。

![](https://pic2.zhimg.com/v2-de1d5a53014dd0f360f3e80f0373b2d5_r.jpg)

**对比**。LLM 的编程系统可分为高级（例如 LangChain、DSPy）和低级（例如 LMQL、Guidance、SGLang）。高级系统提供预定义或自动生成的提示，例如 DSPy 的提示优化器。低级系统通常不会更改提示，但允许直接操纵提示和原语。SGLang是与LMQL和Guidance类似的低级系统。表1比较了它们的功能。SGLang更注重运行时效率，并配有自己协同设计的运行时，允许在以后引入新的优化。高级语言（例如DSPy）可以编译为低级语言（例如SGLang）。我们在第6节中演示了将SGLang集成作为DSPy的后端，以提高运行时效率。
