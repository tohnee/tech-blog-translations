当一个 AI Agent 需要连续调用几十次大模型时，推理引擎的性能问题就会变得非常明显。

比如让 AI 完成一个复杂的软件开发任务，它可能需要先阅读代码、分析依赖、生成修改方案，再调用工具执行命令，最后根据结果继续推理。

整个过程并不是一次长文本生成，而是大量交错发生的模型请求。

这些请求有的输入很长，有的输出很短；有的需要快速返回，有的会因为工具执行而暂时中断。

这给大模型推理系统带来了一个问题：

当 GPU 已经足够强大时，推理引擎本身的调度、资源管理和执行开销，会不会反过来限制 GPU 的性能？

最近看到一个值得研究的开源项目：TokenSpeed。

它由 LightSeek Foundation 推动，定位是一套面向 Agent 工作负载的高性能大模型推理引擎。

项目希望同时兼顾 TensorRT-LLM 的高性能和 vLLM 的易用性。

但真正让我感兴趣的，是它采用了一种不同的架构设计：

把推理系统的控制平面放到 C++，把模型执行平面保留在 Python，并通过有限状态机管理请求生命周期和 KV Cache。

这意味着，它试图从推理引擎的架构层面重新处理性能、正确性和开发效率之间的关系。

### 一、为什么已经有 vLLM 和 TensorRT-LLM，还需要新的推理引擎？

目前的大模型推理生态中， 和 都是非常重要的项目。

vLLM 的优势在于易用性、模型生态和高效的推理服务能力。

TensorRT-LLM 则更加重视底层优化，能够利用 NVIDIA GPU 的硬件特性获得高性能。

两者都有成熟的技术路线。

但随着 AI Agent 的普及，推理负载正在发生变化。

传统聊天应用的请求相对容易理解：

用户输入一段文本，模型生成一段回答。

Agent 工作负载则复杂得多。

一次任务可能涉及：

- 多轮模型推理与工具调用。
- 不同长度的 Prefill 和 Decode 阶段。
- 大量短请求和连续生成请求。
- 不断变化的并发数量。
- KV Cache 的频繁分配、复用与释放。

尤其是在多 Agent 并行运行时，推理系统需要持续处理大量处于不同状态的请求。

这时候，性能瓶颈未必只存在于 Attention Kernel 或矩阵计算。

请求调度、状态转换、缓存资源管理以及 CPU 与 GPU 之间的协同，同样可能影响整个系统的吞吐量和响应延迟。

TokenSpeed 正是围绕这些问题重新设计推理引擎。

### 二、TokenSpeed 最重要的设计：C++ 控制平面 + Python 执行平面

传统推理框架通常需要在同一个运行系统中处理大量不同职责。

例如：

请求什么时候进入执行队列？

哪些请求可以组成一个 Batch？

KV Cache 由谁持有？

请求完成后什么时候释放缓存？

GPU 当前应该执行哪些计算？

这些操作之间存在复杂的依赖关系。

TokenSpeed 选择把它们拆成两个相对独立的部分。

TokenSpeed 核心架构示意

请求入口

Rust / SMG / Dynamo

C++ 控制平面

请求生命周期 · 有限状态机 · KV Cache 所有权 · 调度时序

Python 执行平面

模型执行 · 推理逻辑 · 快速迭代

模块化 Kernel 系统

GPU 算子 · MLA · 异构加速器

概念示意，突出各组件的职责划分，并非完整运行时调用图。

### 1. C++ 负责控制平面

TokenSpeed 使用 C++ 实现核心调度逻辑。

控制平面负责管理：

- 请求的生命周期。
- KV Cache 的所有权。
- 请求与资源的状态转换。
- 计算与调度之间的重叠时序。

为什么选择 C++？

因为这些操作需要较强的执行确定性和资源管理能力。

尤其是 KV Cache。

它保存 Transformer 推理过程中已经计算过的 Key 和 Value，可以避免在生成后续 Token 时重复计算历史内容。

但 KV Cache 也是有限的 GPU 显存资源。

如果缓存被错误释放、重复复用，或者仍有计算依赖时就被重新分配，可能造成严重的正确性问题。

TokenSpeed 希望把这类约束直接放进调度系统的设计中。

### 2. Python 负责执行平面

这里有一个很有意思的选择。

既然追求极致性能，为什么不把整个推理引擎都用 C++ 实现？

因为模型执行逻辑需要持续变化。

新的模型架构、新的算子实现、新的推理优化方法，都需要开发者快速验证。

Python 与 PyTorch 生态在这方面具有明显优势。

如果整个系统都依赖底层语言，研究人员修改执行逻辑的成本可能会更高。

TokenSpeed 因此保留 Python 执行平面。

C++ 负责那些需要严格控制状态和资源的部分，Python 负责需要快速开发和迭代的模型执行部分。

这种分工的价值，并不是简单地认为 C++ 一定比 Python 快，而是让不同职责运行在更合适的技术层中。

### 三、用有限状态机管理推理请求，是一个很关键的设计

TokenSpeed 的另一个技术特点，是使用有限状态机管理请求生命周期。

有限状态机，也就是 Finite-State Machine，简称 FSM。

它的核心思想是：

一个对象只能处于预先定义的状态，并按照允许的规则发生状态转换。

例如，我们可以用一个简化的推理请求流程来理解：

`请求进入    |    v 等待调度    |    v 资源分配    |    v 模型执行    |    v 请求完成    |    v 资源释放`

这只是帮助理解的概念流程，并不代表 TokenSpeed 的完整状态定义。

真实的推理调度会复杂得多。

例如，执行中的请求可能需要继续生成 Token，也可能因为调度策略发生状态变化。

KV Cache 的状态又与请求生命周期相互关联。

如果所有状态都依赖运行时的条件判断，很容易出现难以发现的资源管理错误。

TokenSpeed 的设计重点，是将请求生命周期、KV Cache 所有权以及执行重叠时序编码进有限状态机。

更进一步，它利用 C++ 类型系统，在编译阶段约束部分资源管理操作。

这意味着，某些不合法的资源使用方式可以在编译时被发现，而不必等到线上执行时才暴露问题。

这种设计对高并发推理系统尤其有意义。

因为推理引擎最难排查的问题，往往不是某一次计算速度慢，而是在复杂并发条件下偶发的状态错误。

当然，类型系统不能保证整个推理系统完全没有 Bug。

它能够提供的是特定资源管理约束下更强的正确性保障。

### 四、Kernel 不再与推理引擎紧密绑定

除了调度系统，TokenSpeed 还把 Kernel 设计成独立、可扩展的子系统。

在大模型推理中，Kernel 负责具体的底层计算。

例如 Attention 相关计算。

这些操作往往需要针对不同 GPU 架构进行专门优化。

问题在于，不同硬件的性能特性差异很大。

一套在某种 GPU 上表现良好的 Kernel，不一定适合另一种 GPU。

TokenSpeed 采用了分层、可插拔的 Kernel 架构，包含：

1. 统一的公共 API

上层执行逻辑通过相对稳定的接口使用 Kernel，减少与具体底层实现之间的耦合。

1. 集中式 Kernel 注册与选择机制

不同 Kernel 实现可以通过统一的注册和选择机制接入。

这为不同硬件、不同计算场景选择合适的实现提供了基础。

1. 可扩展的插件机制

Kernel 可以作为独立子系统进行扩展，支持面向异构加速器的优化。

从仓库结构也能看到这种设计思路：

`tokenspeed-engine/ tokenspeed-scheduler/ tokenspeed-kernel/ tokenspeed-kernel-amd/ tokenspeed-kernel-npu/ tokenspeed-mla/ python/`

这些模块体现了引擎、调度器、Kernel 和 Python 层之间的职责划分。

其中，MLA 是一个值得关注的方向。

MLA 全称 Multi-head Latent Attention，是部分大模型采用的注意力机制。

TokenSpeed 针对 NVIDIA Blackwell 架构上的 Agent 工作负载，提供了专门优化的 MLA 实现。

这说明它的性能优化并没有停留在调度层，而是延伸到了 GPU 计算内核。

### 五、请求入口也在减少对 Python 的依赖

还有一个容易被忽略的细节：

TokenSpeed 的请求入口并不要求 Python 参与每次请求的处理路径。

它支持通过 SMG 和 Dynamo，由 Rust 组件通过 msgpack 通信协议驱动推理引擎。

这里需要区分两个概念。

一个是请求路径，负责接收、传递和协调请求。

另一个是模型执行路径，负责真正的推理计算。

TokenSpeed 让请求路径避免经过 Python，同时保留 Python 作为模型执行平面。

这与前面 C++ 控制平面的设计是一致的。

目的都是减少控制逻辑与模型执行逻辑之间不必要的耦合。

不过，这并不意味着 TokenSpeed 完全不使用 Python，也不能据此推断它在所有请求场景下都没有 CPU 开销。

更准确地说，它把 Python 的职责限制在适合 Python 的执行层，而不是让 Python 承担整个请求生命周期的管理。

### 六、性能究竟怎么样？

讨论推理引擎，最终还是绕不开性能。

TokenSpeed 的目标是达到与 TensorRT-LLM 相当的性能水平，同时保留接近 vLLM 的开发体验。

项目提供了针对 Agent 工作负载的性能对比，包括在 NVIDIA B200 上运行 Kimi K2.5 时，与 TensorRT-LLM 的 Pareto 曲线比较。

此外，项目也持续针对 Blackwell、GB200、GB300 和 AMD Instinct 等硬件平台进行优化。

但分析这些性能结果时，需要特别注意测试条件。

大模型推理性能不是一个简单的 TPS 数字就能说明的。

至少需要考虑：

| 指标 | 关注的问题 |
| --- | --- |
| TTFT | 用户等待首个 Token 的时间 |
| TPOT | 连续生成 Token 的平均间隔 |
| 吞吐量 | 单位时间内处理多少 Token |
| 并发能力 | 多个请求同时执行时的表现 |
| 显存效率 | KV Cache 等资源的利用情况 |
| 延迟分布 | 高负载下尾部请求是否明显变慢 |

尤其是 Agent 工作负载，单个用户的 Token 生成速度和系统总体吞吐量可能存在取舍。

如果一个引擎通过增加 Batch 提高吞吐量，却让单个 Agent 的每次响应明显变慢，那么实际任务完成时间未必会缩短。

所以评价 TokenSpeed，应该结合具体模型、硬件、输入输出长度和并发规模，而不是简单认为它在所有场景都比现有框架更快。

### 七、开发者应该如何使用 TokenSpeed？

TokenSpeed 已经提供了独立的文档体系，覆盖入门、启动服务、模型配置和并行推理等内容。

可以从以下几个部分了解它的使用方式。

第一步：确认运行环境。

推理引擎涉及 GPU、驱动、模型权重和底层 Kernel，首先需要确认目标硬件与模型是否受到支持。

第二步：选择模型配置。

不同模型可能需要不同的执行配置和算子支持。

项目提供了 Model Recipes，用于组织模型相关的运行配置。

第三步：启动推理服务。

TokenSpeed 提供了专门的服务启动文档，以及 Server Parameters 和 Compatible Parameters 配置说明。

第四步：根据部署规模配置并行策略。

对于需要多 GPU 执行的大模型，可以进一步了解其 Parallelism 配置。

相关文档入口包括：

- [Getting Started](https://lightseek.org/?utm_source=chatgpt.com)
- [项目代码仓库](https://github.com/lightseekorg/tokenspeed?utm_source=chatgpt.com)

对于首次接触这个项目的开发者，我更建议先验证单个模型能否稳定运行，再逐步测试并发和性能。

因为这类推理引擎真正复杂的部分，往往不在启动服务，而在硬件适配、模型兼容性以及不同负载下的性能调优。

### 八、TokenSpeed 适合什么场景？

从架构定位来看，它比较适合以下几类工作负载。

### 1. 高并发 AI Agent 服务

例如多个 Agent 同时执行任务，持续向推理服务提交请求。

这类场景中，请求状态变化频繁，调度器需要协调大量并发任务。

TokenSpeed 的 C++ 控制平面和状态机设计，正是针对这类复杂调度需求。

### 2. 对 Token 生成速度敏感的应用

对于需要连续多轮模型调用的 Agent，每轮生成延迟都会影响最终任务完成时间。

如果底层 Kernel 和调度器能够减少不必要的开销，就有机会改善整体执行体验。

实际收益仍然需要在具体模型和硬件上验证。

### 3. 需要针对硬件深度优化的推理平台

如果团队需要在 NVIDIA 或 AMD 等不同硬件平台上进行推理优化，模块化 Kernel 架构具有一定吸引力。

开发者可以将底层算子优化与上层执行逻辑分开考虑。

### 4. 研究新模型与推理优化技术

Python 执行平面为模型逻辑的修改和实验提供了便利。

同时，C++ 调度器承担核心状态管理职责。

这种设计能够让研究人员更专注于模型执行，而不必每次都深入修改底层调度系统。

### 九、架构有吸引力，但不意味着迁移没有成本

TokenSpeed 的设计思路很清晰，不过它也有需要权衡的地方。

首先，系统复杂度并没有消失，而是被重新分配了。

C++ 控制平面、Python 执行平面、Rust 请求入口和独立 Kernel 系统，让不同组件可以各自优化，但也意味着开发者需要理解跨语言边界和组件间的协作关系。

其次，硬件与模型兼容性需要具体确认。

一个模型能否运行，与它是否已经具备充分优化的 Kernel，并不是同一回事。

再者，TokenSpeed 的目标工作负载比较明确。

如果只是部署一个低并发的简单聊天应用，使用已有的成熟推理框架可能更加直接。

对于这种场景，迁移到新架构所带来的配置和维护成本，未必能够通过性能收益抵消。

最后，推理引擎的生产可用性不能只看峰值性能。

还需要评估监控、故障恢复、版本升级、稳定性和团队维护能力。

这些因素都会影响最终的技术选型。

### 十、从 TokenSpeed 看大模型推理引擎的下一步

我认为 TokenSpeed 最有意思的地方，并不是单纯追求更高的 Token 生成速度。

而是它重新划分了推理系统内部的职责。

过去讨论大模型推理优化，大家经常关注量化、Attention Kernel、Batching 和 KV Cache。

这些技术当然重要。

但当 AI Agent 开始产生大量交错、动态、连续的推理请求时，调度系统本身也必须跟着演进。

TokenSpeed 给出的方案是：

让 C++ 管理请求生命周期和资源状态，让 Python 保持模型执行的灵活性，让 Kernel 成为独立的性能优化模块，并让请求入口尽量减少不必要的语言运行时依赖。

这种架构并不能自动保证所有模型、所有 GPU、所有并发场景都获得最佳性能。

但它提供了一个值得关注的技术方向：

未来的大模型推理性能竞争，可能不只是比谁的 GPU Kernel 更快，还要比谁能更高效、更安全地组织整个推理执行过程。

对于正在建设 AI Agent 平台、研究推理调度或者优化大模型服务的开发者来说，TokenSpeed 值得关注的正是这一点。
