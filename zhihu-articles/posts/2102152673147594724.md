最近在整理 AI 模型保护实验时，我重新检查了一个已经训练好的钢材缺陷分类模型。它可以读取图片，在 Jetson 本地完成推理，输出缺陷类别。

模型转成 TensorRT Engine 后，我原本以为：文件已经是二进制格式，结构也经过优化，别人拿到它，应该不容易看懂。

![](https://pic4.zhimg.com/v2-cc8de01d5ab75147afaddf0bfd981bd9_1440w.jpg)

实际检查后发现，文件中仍然保留着卷积层、激活层、池化层和部分执行参数。更直接的问题是：**对方拿到明文模型后，可能根本不需要还原训练代码，在兼容环境中加载就能使用。**

这篇文章以 `steel_defect_fp16.engine` 为例，整理模型为什么需要加密、已有模型如何加密、密钥如何保护，以及加密能解决到哪一步。

文件加密部分可以在普通 Linux 主机复现；TensorRT 加载部分需要与 Engine 兼容的 Jetson 环境。

## 模型文件里，真正需要保护的是什么

训练结束后，模型会以不同格式进入部署流程。

| 文件或格式 | 通常包含什么 | 泄露后可能发生什么 |
| --- | --- | --- |
| PyTorch 检查点，如 .pth、.pt | 取决于保存方式，可能包含权重、模型对象或训练状态 | 获取训练结果，继续训练或重新导出 |
| ONNX | 计算图及权重，权重也可能保存在外部数据文件中 | 分析网络，在其他运行时部署 |
| TensorRT .engine、.plan | 优化后的网络表示、权重及执行所需数据 | 在兼容环境中运行，或进一步分析 |
| RKNN .rknn | 面向 Rockchip 平台的部署数据 | 在兼容运行时中使用，或进一步分析 |

对于采用公开网络结构的项目，经过业务数据训练得到的权重，往往是主要资产。前处理方式、类别映射、阈值和自定义算子，也可能包含项目经验。

**模型保护并不只针对大模型。** 一个几 MB 的工业分类模型，同样可能承载数据标注、训练、调参和现场验证的投入。

这里还需要区分兼容性与安全性。

一个 Engine 在另一块板子上加载失败，可能是 GPU 架构、操作系统或 TensorRT 版本不兼容。它不能证明模型已经加密，也不能证明模型已经绑定设备。NVIDIA 的支持矩阵对这些兼容条件有单独说明。[NVIDIA TensorRT](https://docs.nvidia.com/deeplearning/tensorrt/latest/getting-started/support-matrix.html?utm_source=chatgpt.com)

## 一个明文 Engine，能暴露多少信息

在我的实验中，首先执行：

```text
strings -n 8 original/steel_defect_fp16.engine | grep 'ONNX Layer'

```

输出中可以看到这些内容：

```text
[ONNX Layer: node_conv2d]
[ONNX Layer: node_relu]
[ONNX Layer: node_max_pool2d]
[ONNX Layer: node_conv2d_1]
[ONNX Layer: node_relu_1]
[ONNX Layer: node_max_pool2d_1]
[ONNX Layer: node_conv2d_2]
[ONNX Layer: node_relu_2]
[ONNX Layer: node_max_pool2d_2]
[ONNX Layer: node_linear]
[ONNX Layer: node_linear_1]

```

部分输出还包含 `padding`、`strides`、池化尺寸、输入输出名称等信息。结合项目中的模型定义，可以对应到三组卷积、激活和池化，以及后面的全连接层。

这个实验说明：

> **转成 Engine 后，部分模型信息依然可能以可读形式保留。**

但结论需要停在证据支持的位置。

`strings` 只提取可读字符串，没有提取出权重，也不能证明已经完整恢复网络。Engine 经过融合、精度转换和布局优化后，恢复训练框架中的原始表示，需要额外分析和验证。

实际部署中，更值得先考虑的是直接复制。兼容条件满足，而且应用没有额外授权限制时，别人可能直接使用这个 Engine。保护模型不能只依赖文件格式复杂。

对于随设备交付的私有模型，可以先明确三个目标：

- **保密性**：拿到文件后，不能直接读取或使用模型内容。
- **完整性**：文件被修改、截断后，加载程序能够发现。
- **来源与授权**：确认模型由可信发布方提供，并允许在当前设备使用。

文件加密主要处理前两项。发布方身份、设备授权和运行时内存保护，还需要相应机制配合。

## 已经训练好的模型，应该怎么加密

已有模型可以直接增加加密封装，通常不需要重新训练，也不需要为了加密修改网络。

以 Jetson 部署为例，先完成 ONNX 到 Engine 的转换、精度检查和性能验证，再加密最终交付的 Engine。设备运行时，先认证和解密，得到原来的 Engine 字节，再交给 TensorRT。

**只要解密后的字节与加密前完全一致，加密本身不会改变权重和推理精度。**

加密、解密会增加发布或加载阶段的开销，具体耗时需要在目标设备测量。

如果产品在首次启动时从 ONNX 构建 Engine，还需要保护 ONNX，以及构建后生成的 Engine 缓存。只加密其中一个文件，另一个明文副本仍可能泄露模型。

### 用 AES-GCM 同时处理保密和篡改检测

本例选择 **AES-256-GCM**。

AES 是对称加密算法，加密和解密使用同一把密钥；GCM 提供认证加密，能够在解密时校验数据完整性。它属于 NIST 定义的带关联数据认证加密机制。[CSRC](https://csrc.nist.gov/pubs/sp/800/38/d/final?utm_source=chatgpt.com)

使用时，需要理解四个输入或输出：

| 名称 | 本例中的设置 | 是否需要保密 |
| --- | --- | --- |
| Key | 32 字节随机密钥，即 AES-256 | 需要 |
| Nonce | 12 字节，每次加密重新生成 | 不需要，但同一密钥下不能重复 |
| Tag | 16 字节认证标签，由库自动生成 | 不需要 |
| AAD | 参与认证但不加密的数据，本例使用文件格式标识 | 不需要，但解密时必须一致 |

**同一把密钥下不能重复使用 Nonce。**

本例每次加密都生成新的随机 Nonce；大量、长期发布模型时，还应设计密钥轮换和 Nonce 管理策略，控制碰撞风险。`cryptography` 官方文档明确要求避免 Nonce 重用，并说明认证失败会抛出 `InvalidTag`。[Cryptography 50.0.2 documentation](https://cryptography.io/en/stable/hazmat/primitives/aead/?utm_source=chatgpt.com)

RSA 等公钥算法可以用于保护数据密钥；模型本体通常交给适合处理大块数据的对称算法。

### 一份可以运行的加密脚本

先准备 Python 环境：

```text
python3 -m venv .venv
source .venv/bin/activate
python -m pip install cryptography

```

将下面代码保存为 `model_crypto.py`：

```text
import argparse
import hashlib
import os
from pathlib import Path

from cryptography.exceptions import InvalidTag
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

MAGIC = b"AIENC001"  # 8 字节格式标识，同时作为 AAD
NONCE_SIZE = 12
TAG_SIZE = 16

def write_new(path, data):
    # 不覆盖已有文件；新文件仅允许当前用户读写。
    fd = os.open(path, os.O_WRONLY | os.O_CREAT | os.O_EXCL, 0o600)
    with os.fdopen(fd, "wb") as f:
        f.write(data)

def read_key(path):
    key = Path(path).read_bytes()
    if len(key) != 32:
        raise ValueError("本例要求 32 字节 AES-256 密钥")
    return key

def decrypt_model(path, key):
    blob = Path(path).read_bytes()
    header_size = len(MAGIC)

    if len(blob) < header_size + NONCE_SIZE + TAG_SIZE:
        raise ValueError("加密文件长度不足")

    if blob[:header_size] != MAGIC:
        raise ValueError("加密文件格式不匹配")

    nonce = blob[header_size:header_size + NONCE_SIZE]
    ciphertext = blob[header_size + NONCE_SIZE:]

    # 认证失败时抛出异常，不返回未通过认证的明文。
    return AESGCM(key).decrypt(nonce, ciphertext, MAGIC)

def main():
    parser = argparse.ArgumentParser()
    parser.add_argument("action", choices=["keygen", "encrypt", "check"])
    parser.add_argument("source", nargs="?")
    parser.add_argument("output", nargs="?")
    parser.add_argument("--key", default="demo_model.key")
    args = parser.parse_args()

    if args.action == "keygen":
        write_new(args.key, AESGCM.generate_key(bit_length=256))
        print("已生成实验密钥，请妥善保存")
        return

    if not args.source:
        parser.error("需要指定输入文件")
    key = read_key(args.key)

    if args.action == "encrypt":
        if not args.output:
            parser.error("需要指定输出文件")

        plaintext = Path(args.source).read_bytes()
        nonce = os.urandom(NONCE_SIZE)
        ciphertext = AESGCM(key).encrypt(nonce, plaintext, MAGIC)

        write_new(args.output, MAGIC + nonce + ciphertext)
        print("已生成加密文件")
    else:
        plaintext = decrypt_model(args.source, key)
        print("认证与内存解密成功")
        print("SHA-256:", hashlib.sha256(plaintext).hexdigest())

if __name__ == "__main__":
    try:
        main()
    except InvalidTag:
        raise SystemExit("认证失败：密文、密钥、Nonce 或 AAD 不匹配")
    except (OSError, ValueError) as exc:
        raise SystemExit(str(exc))

```

执行加密和验证：

```text
python model_crypto.py keygen

python model_crypto.py encrypt \
    original/steel_defect_fp16.engine \
    model.enc

python model_crypto.py check model.enc

sha256sum original/steel_defect_fp16.engine

```

`check` 输出的 SHA-256 应与原文件一致，说明解密得到了相同的模型字节。它只在内存中解密，不生成明文模型文件。

本例的封装包含：

| 内容 | 长度 |
| --- | --- |
| 格式标识 | 8 字节 |
| Nonce | 12 字节 |
| 模型密文 | 与原模型等长 |
| Tag | 16 字节 |

因此，加密文件比原文件多 **36 字节**。

这个封装用于讲清楚文件加密流程。正式模型包还应认证模型标识、版本、目标平台和密钥标识，并由加载程序核对。仅认证格式标识，不能阻止替换成同一密钥下的其他合法模型。

**`demo_model.key` 是主机实验用的明文密钥文件，不应随模型一起交付。** 文件权限也不能阻止设备管理员读取它。产品中的密钥获取方式，需要换成安全密钥服务。

另外，这个脚本一次读取整个模型，适合本例几 MB 的文件。大型模型需要考虑分块认证加密、内存占用和运行时接口限制。分块设计还必须认证块顺序、总长度和结束标记，不能简单地独立加密后任意拼接。

### 同时验证正常路径和失败路径

先翻转加密文件中的一个比特，生成新的测试文件：

```text
python - <<'PY'
from pathlib import Path

data = bytearray(Path("model.enc").read_bytes())
data[-1] ^= 1

with open("model.bad.enc", "xb") as f:
    f.write(data)
PY

python model_crypto.py check model.bad.enc

```

预期结果是认证失败，程序以非零状态退出。使用错误密钥、截断文件，也应被拒绝。

还可以做一个直观对比：

```text
strings -n 8 model.enc | grep 'ONNX Layer'

```

通常不会再找到原来的层名。但这个结果只能说明关键词不再可见，不能作为密码学安全证明。安全性仍取决于算法、密钥保护、Nonce 管理和实现是否正确。

SHA-256 在这里用于比较实验前后的字节。单独把哈希值与文件放在一起，不能抵抗同时替换两者的攻击。正式加载时，仍应依赖可信的认证标签、签名或受保护的清单。

## 密钥放在哪里，决定了文件加密有没有意义

文件加密跑通后，马上会遇到一个实际问题：模型解密需要密钥，设备又必须能够使用这个密钥。

把密钥写进源码、放进配置文件，或者与 `model.enc` 一起保存，都会给文件提取和程序分析留下入口。接下来需要处理密钥管理。

### 分清 DEK、KEK 和 EKB

| 名称 | 含义 | 在模型保护中的作用 |
| --- | --- | --- |
| DEK | Data Encryption Key，数据加密密钥 | 直接加密模型 |
| KEK | Key Encryption Key，密钥加密密钥 | 加密或封装 DEK |
| EKB | Encrypted Key Blob，加密密钥数据包 | Jetson 用来保护用户密钥和敏感数据的机制 |

最简单的方案可以把 DEK 直接放入安全存储，**两层密钥不是必需条件**。

需要独立管理模型发布、设备授权和密钥轮换时，可以增加 KEK，形成信封加密结构：模型由 DEK 加密，DEK 再由 KEK 保护。这也是成熟密钥管理系统采用的基本方法。[AWS Key Management Service](https://docs.aws.amazon.com/kms/latest/developerguide/kms-cryptography.html?utm_source=chatgpt.com)

下面是主机上演示密钥封装关系的核心代码，其中 `dek` 和 `kek` 都是已经生成的密钥字节：

```text
aad = b"steel-defect/dek/v1"
nonce = os.urandom(12)

wrapped_dek = nonce + AESGCM(kek).encrypt(
    nonce, dek, aad
)

# 反向操作：认证并解封 DEK。
recovered_dek = AESGCM(kek).decrypt(
    wrapped_dek[:12],
    wrapped_dek[12:],
    aad
)

```

这里的 Nonce 与模型加密时独立生成，同样必须避免在相同密钥下重复。

采用两层密钥后，在更换 KEK、且 DEK 尚未泄露的情况下，可以只重新封装 DEK，不必重新加密整个模型。

**如果 DEK 已经泄露，就需要更换 DEK 并重新加密模型；只更换外层 KEK，无法收回泄露的 DEK。**

我此前的主机实验采用 32 字节 DEK 加密模型、16 字节 KEK 加密 DEK。后者属于 AES-128-GCM。两层密钥长度不同可以正常工作，但整条保护链的强度需要一起评估，不能只看模型这一层用了 AES-256。

### 在 Jetson 上，EKB 保护的是密钥

EKB 是保存在 EKS 分区中的加密数据包。它的明文内容由安全世界处理，并不是一块放在芯片内部、可以直接存放大模型的存储区。

NVIDIA 官方提供了 EKB 和 OP-TEE 用户密钥服务，可以把业务密钥纳入硬件支持的密钥保护体系。在本文的设计中，可以让 EKB 保护 KEK，再由 KEK 解封模型 DEK。

这里有两个容易混淆的地方：

- **KEK 是按用途命名的业务密钥。** 它不自动等于 NVIDIA 用来加密 EKB 本身的 `EKB_EK`。
- **EKB 并非只能保存 16 字节密钥。** 官方格式包含密钥标签和长度字段；某个示例要求 16 字节，需要检查具体工具、条目和服务实现。[NVIDIA Jetson Linux Developer Guide](https://docs.nvidia.com/jetson/archives/r39.2/DeveloperGuide/SD/Security/OpTee/Ekb.html?utm_source=chatgpt.com)

对于 Orin 和 Thor，熔丝名称、密钥层级和工具参数也有区别。应使用与当前 BSP 匹配的实现，不能直接把 Orin 的 EKB 命令复制到 Thor。

在接口设计上，应让 KEK 留在安全世界，由 TA 提供受控的解封服务。NVIDIA 文档也强调，EKB 用户密钥不应离开安全世界；虽然提供了获取原始密钥的接口，也不推荐随意使用。[NVIDIA Jetson Linux Developer Guide](https://docs.nvidia.com/jetson/archives/r39.2/DeveloperGuide/SD/Security/OpTee/SampleApplications.html?utm_source=chatgpt.com)

一种便于逐步验证的加载方式如下：

![](https://pic2.zhimg.com/v2-a86222601201827a17cd5a6d856bfbcf_1440w.jpg)

这条路径中，KEK 留在安全世界，DEK 和解密后的模型会进入普通世界内存。

若要减少 DEK 的暴露，可以把模型解密也放入 TA，但仍需评估大块数据传输、TEE 内存和性能。交给普通 TensorRT 使用的模型内容，依然会越过这条边界。

此外，**设备绑定需要单独设计**。多台设备共用相同 KEK 和相同解封策略，并不会因为使用 EKB 就自动实现一机一授权。可以结合设备独有密钥、每台设备的 DEK 封装或授权服务，控制密钥发放和调用权限。

开发测试时还要留意默认密钥。官方实现允许在未配置生产熔丝密钥时使用测试密钥跑通 EKB 流程；这只能用于验证功能，不能作为量产保密性的依据。[NVIDIA Jetson Linux Developer Guide](https://docs.nvidia.com/jetson/archives/r39.2/DeveloperGuide/SD/Security/OpTee/Ekb.html?utm_source=chatgpt.com)

## 解密后，如何交给 TensorRT

TensorRT 支持从内存中的序列化数据反序列化 Engine，因此不必先把解密结果写成临时 `.engine` 文件。[NVIDIA TensorRT](https://docs.nvidia.com/deeplearning/tensorrt/latest/inference-library/python-api-docs.html?utm_source=chatgpt.com)

沿用前面的 `model_crypto.py`，加载部分可以写成：

```text
import tensorrt as trt

from model_crypto import decrypt_model, read_key

# 实验使用文件密钥；产品中替换为受控的密钥服务。
key = read_key("demo_model.key")
model_bytes = decrypt_model("model.enc", key)

logger = trt.Logger(trt.Logger.WARNING)
runtime = trt.Runtime(logger)

engine = runtime.deserialize_cuda_engine(model_bytes)
if engine is None:
    raise RuntimeError("Engine 加载失败，请检查平台和运行时兼容性")

context = engine.create_execution_context()
if context is None:
    raise RuntimeError("执行上下文创建失败")

# 后续沿用原推理程序的预处理、GPU 缓冲区和执行逻辑。

```

这段代码展示的是安全加载入口，完整推理还需接入原项目的输入输出缓冲区和执行代码。

应先在目标设备确认原 Engine 能正常运行，再加入加密加载，并用同一批图片比较输出。

**GCM 认证失败时必须停止加载。** 不能为了兼容旧文件，自动把失败的输入当明文 Engine 再尝试一次。

Engine 本身也应来自可信构建和发布流程。NVIDIA 将反序列化视为明确的信任边界，要求只加载自己构建或通过可信渠道获得的 Engine。[NVIDIA TensorRT](https://docs.nvidia.com/deeplearning/tensorrt/11.4.0/reference/security.html?utm_source=chatgpt.com)

“不主动写明文文件”减少了临时文件泄露，但普通进程内存仍可能受到调试、转储、交换和崩溃收集的影响。

Python 中执行 `del model_bytes`，也不等于安全擦除了底层数据，TensorRT 仍可能持有模型的其他表示。

## 商业平台是否也这样做

公开资料中，已经能找到模型加密和密钥保护的产品能力。但不同平台保护的范围差别很大，不能只看到“模型加密”四个字，就认定它们实现了同一套方案。

| 平台或方案 | 官方公开能力 | 需要注意什么 |
| --- | --- | --- |
| Rockchip RKNN-Toolkit2 | 官方更新日志列出了模型加密能力 | 需要核对 SDK 版本、芯片、接口和密钥管理，不能直接认定使用本文的 AES-GCM 与 EKB 组合 |
| Realtek AmebaPro2 | 文档描述了 AES-256-CBC、OTP 密钥及独立的模型签名验证 | 加密说明主要针对模型固定头部，不能据此宣称整个权重区都被加密 |
| Jetson EKB 与 OP-TEE | 提供用户密钥保护与安全服务基础 | 模型封装、访问策略和 TensorRT 加载，需要开发者集成 |
| NVIDIA 机密计算参考架构 | 模型加密保存，环境通过远程证明后才释放模型密钥 | 依赖匹配的机密计算硬件与软件，不能直接等同于普通 Jetson 上运行 OP-TEE |

Rockchip 官方更新日志可以证明工具链具有模型加密能力，但具体安全边界仍需继续核对。Realtek 的文档则明确展示了模型认证、加密和 OTP 密钥的组合，同时也说明了其加密范围。[GitHub](https://github.com/airockchip/rknn-toolkit2/blob/master/CHANGELOG.md?utm_source=chatgpt.com)

NVIDIA 的机密计算参考架构进一步要求：模型保持加密，只有硬件和软件环境通过远程证明后，密钥服务才向可信环境释放模型密钥。它对运行时保护的要求，比普通应用中的文件解密更完整。[docs.nvidia.com](https://docs.nvidia.com/enterprise-reference-architectures/deploying-proprietary-models-confidential-compute-self-hosted-vms/latest/architecture-summary.html?utm_source=chatgpt.com)

这些资料支持一个工程判断：

> **模型加密、安全密钥管理和受控加载，已有公开的平台能力和参考架构可供采用。**

至于某款摄像头或工业设备是否这样量产，需要厂商披露或可验证证据。

AES-GCM 是本文选择的实现方式。其他平台使用 CBC 并配合正确的认证或签名设计，也可以构建有效方案；单独使用 CBC、CTR 加密，不提供完整的篡改检测。

## 做到哪一步，才能说模型得到保护

结合这次实验，我更倾向于按验证结果描述进度。

| 验证项目 | 能说明什么 |
| --- | --- |
| 明文中找到层名和参数 | 部分模型信息可直接观察 |
| 加密后搜索不到原关键词 | 直观展示可读信息消失，不能单独证明安全 |
| 解密后 SHA-256 与原文件一致 | 字节恢复正确 |
| 错误密钥、翻转比特、截断被拒绝 | 相应失败路径能被检测 |
| 解密后在目标设备完成同样的推理 | 加密加载接入原部署链路 |
| 导出密钥、越权调用受到限制 | 密钥服务与授权策略发挥作用 |

我目前的主机实验已经验证了密钥封装后的恢复、模型解密后的哈希一致，以及被篡改数据的认证失败。

EKB 配置、板端 TA 调用和 TensorRT 加载，需要继续在匹配的设备环境中逐项验收，不能用主机实验替代这些结果。

进入产品部署前，还需要沿着实际泄露路径检查几个问题：

- **明文副本是否还在**：`.pth`、ONNX 外部权重、Engine 缓存、旧安装包和调试目录都应纳入检查。
- **密钥是否被导出**：避免把 KEK 返回 Linux，也要评估 DEK 在进程中的暴露。
- **是否允许旧模型回退**：旧密文仍可能通过 GCM 校验，防回退需要可信版本策略和受保护状态。
- **是否验证发布方**：持有对称密钥的一方也能生成合法 Tag，需要独立验证发布方时，应增加数字签名。
- **运行时明文由谁保护**：把密钥放入 TEE，不会自动把普通 TensorRT 的 CPU 和 GPU 数据都纳入安全世界。

对于我当前的钢材缺陷项目，可以先用已有图片和已有模型完成这条实验链：观察明文、加密、验证失败路径、保护密钥、内存加载，再分析运行时暴露。这个过程中补充模型格式、权重、量化和算子的知识，都能直接对应到实际问题。

最终验收时，需要分别回答：**拿走文件能否使用，篡改能否被拒绝，未授权设备能否取得密钥，以及运行时明文仍会在哪里出现。** 回答清楚这些问题，模型保护方案的作用和边界才是可检查的。
