### **前言**

如果你跑过 `vllm serve`，大概率会遇到这样一个场景：服务空载时一切顺滑，TTFT（首 token 延迟）几十毫秒，ITL（token 间延迟）稳定。可一旦并发上来，延迟曲线就开始抖。

最典型的现象是，当一条很长的提示词混进一堆正在生成的请求里，所有正在流式输出的回复都会“卡顿”一下，像被人按了暂停键。

很多人的第一反应是调参数：加 `max-num-seqs`、调 `max-num-batched-tokens`、开 Chunked Prefill。调一调确实能好一点，但治标不治本。因为这不是配置问题，而是**架构的先天矛盾**：一个 vLLM 进程同时在干三件性质完全不同的活，它们天然会互相抢资源。

一条完整的推理流程可以拆分成三个主要部分：

- **Prefill（预填充）**： 当一个请求进来，模型要先把整段 prompt 过一遍，计算出每个 token 的注意力键值（KV Cache）。这一步是**计算密集型**的，大量矩阵乘法吃满了 GPU 的算力。Prefill 跑多快，直接决定了用户多久能看到第一个字，也就是 **TTFT（Time To First Token）**。prompt 越长，Prefill 越慢，TTFT 越高。
- **Decode（解码）**： Prefill 完成后，模型开始一个 token 一个 token 地生成输出。这一步和 Prefill 正好相反，它是**访存密集型**的。每生成一个 token，都要把整套模型权重从显存里读一遍，算力反而不是瓶颈。Decode 的快慢决定了 **ITL（Inter-Token Latency）**，也就是两个 token 之间的间隔，直接影响用户看到文字输出的流畅度。
- **CPU 杂活**：聊天模板渲染、分词（把文字转成 token ID）、反分词（把 token ID 还原成文字）、推理链解析、工具调用解析，这些全是纯 CPU 工作。它们不直接产生 token，却实实在在地占着 CPU 和内存，间接拖慢整个调度。

把 Prefill 和 Decode 放在同一张 GPU 上，意味着两个流程是交替进行的，需要调度器来决定当前迭代步是跑prefill还是deocoding。那么也就意味着，只要一条长 prompt 的 Prefill 跑起来，这张 GPU 上所有正在进行的 Decode 流都得停下来等。

Chunked Prefill 确实能缓解一部分。它把长 prompt 切成小块，见缝插针地塞进 Decode 间隙里。但“合适的 chunk 大小”高度依赖流量分布，流量一变就得重新调，很难一劳永逸。

Prefill 要算力、Decode 要显存带宽、CPU 杂活要 CPU 核。硬塞在一个进程里，只会让它们互相拖累。**分离式服务（Disaggregated Serving）**的核心思路就一句话：**别让一个进程干所有的事，把不同性质的工作拆到不同的实例上，各跑各的。**

### **分离的两种主要方式**

vLLM 提供了两个可以拆分的切入点，而且它们可以组合使用。

### **Prefill / Decode 分离**

这是分离式服务最核心、最常用的一种拆分。Prefill 和 Decode 各自跑在独立的 vLLM 实例上，两者之间传递的是 **KV Cache**。

什么是 KV Cache？简单说，就是模型在 Prefill 阶段为每个 prompt token 计算出来的注意力键值。Decode 要生成下一个 token，必须先拿到这些键值，否则它“看不到”之前的上下文。所以 KV Cache 就是 Prefill 交给 Decode 的“接力棒”。

这根接力棒有多大？以 BF16 精度的 Llama-3.1-70B 为例，每个 token 要存 320 KiB。一条 10k token 的 prompt，KV Cache 就有约 3 GB。在 400 Gb/s 的网络线速下，光传输就要约 65 毫秒，这还没算任何协议和拷贝开销。这笔时间，全部算在用户感知的 TTFT 头上。

所以 P/D 能不能跑得好，**关键看 KV Cache 传得快不快**。

vLLM 生态里已经有十多种 KV Connector（KV 传输连接器），各有侧重：

- **NIXL**：基于 RDMA 的高性能传输，是目前最常用的选择；
- **LMCache、Mooncake**：在传输之上还提供了 KV Cache 的共享和复用能力；
- **FlexKV、AMD 的 MoRI-IO**：针对特定硬件做了优化；
- **MultiConnector**：可以把多个连接器串起来组合使用。

简单梳理一下，P/D 的完整流程是这样的：Prefill 实例算完 KV Cache 后，把它“持有”在显存里，同时返回一个标识；Decode 实例拿着这个标识，通过 KV Connector 把 KV Cache 拉过来，然后开始逐 token 生成。中间需要一个 **Proxy**来协调两者的调用顺序。

### **前端分离（Render Tier）**

另一种拆分是把 CPU 工作从 GPU 机器上彻底挪走。vLLM 新增了两个接口：

- `/render`：把一个 OpenAI 请求（文字、消息列表）转换成 token ID；
- `/derender`：把模型输出的 token ID 还原成标准的 OpenAI 响应，把 `content`、`reasoning`（推理内容）、`tool_calls`（工具调用）分别拆好。

这样一来，GPU 引擎只做 **token 进、token 出**，不再跑聊天模板和各种解析器，把昂贵的 GPU 时间还给真正的矩阵运算。

这一层可以纯 CPU 部署，独立扩缩容。

### **收益与代价**

**收益一：TTFT 和 ITL 可以独立调优**

在聚合模式下，你只有一组并行度配置（TP、PP、DP），但 Prefill 和 Decode 对并行度的诉求完全不同：

- Prefill 是计算密集型，更吃**张量并行（TP）**——把模型切成多片，让多张 GPU 一起算，加速单次前向；
- Decode 是访存密集型，更适合**按 batch 扩容**——多放几个 Decode 副本，每个副本处理一批请求，靠并发堆吞吐。

聚合模式下，你只能在两者之间取一个折中值，要么 Prefill 不够快，要么 Decode 副本数上不去。拆开之后，Prefill 池和 Decode 池各自配各自的并行度，互不牵扯。改 Prefill 的 TP 大小，不会影响 Decode 的 batch 配置，反之亦然。

**收益二：尾延迟随负载上升保持稳定**

这是分离式服务最核心、最不可替代的价值。

博客里用两台 NVIDIA L40S（48 GB，PCIe，无 NVLink）跑了一组对比测试：模型 Qwen2.5-7B-Instruct，约 8k token 输入，256 token 输出，100 条泊松到达的请求。聚合模式用的是 `vllm serve --data-parallel-size 2`（两张 GPU 各跑一个副本），P/D 模式是一个 Prefiller 加一个 Decoder，中间走 NIXL，两套配置用的是同样两张 GPU。

结果非常直观：

![](https://picx.zhimg.com/v2-b11c1466f2862e0f118392f513660a43_r.jpg)

- **聚合模式**：p99 ITL 在 0.4 req/s 时就从 23 ms 飙到 169 ms，到 2 req/s 时达到 263 ms；
- **P/D 模式**：p99 ITL 始终保持在 25–52 ms 之间，几乎不随负载上升。

值得注意的是，在 0.4–0.6 req/s 区间，两者的**中位数延迟几乎一样**（都是 21–24 ms），但聚合模式的 p99 是 P/D 的约 6 倍。这说明问题不在平均延迟，而在**尾延迟**。

也就是说，那 1% 最倒霉的请求，正好撞上了一条长 prompt 的 Prefill。

**收益三：Goodput 显著提升（前提是传输够快）**

当 KV 传输足够快时，Goodput 的提升非常可观。博客引用了两组来自硬件厂商和社区的数据：

- **AMD 的单机 MoRI-IO 基准测试**：在 8 张 MI300X 的单节点上跑 Qwen3-235B，设定 1 秒 TTFT + 50 ms ITL 的目标。P/D 模式下 100 个请求里有 73 个同时达标，聚合模式只有 30 个——**同样硬件下 Goodput 约 2.4 倍**。
- **llm-d 的集群级数据**：在 16 张 H200 上跑 gpt-oss-120b，相比把同样的 GPU 作为聚合副本运行，平均端到端延迟降低 59%，P95 延迟降低 67%。

这些数字的前提都是 KV 传输走 RDMA（InfiniBand 或 RoCE）或者单机内的 NVLink / GPU P2P。传输一慢，这些收益就会被吃掉，下面代价部分会详细说。

**收益四：CPU 层极便宜**

把分词和解析挪到 Render 层后，你不再用 GPU 机器的 CPU 来跑分词器了，而是用便宜得多的 CPU 实例来承载，并且可以按 CPU 负载独立扩缩容。

博客里给了一个具体的测量：对 Qwen2.5-7B 渲染一条 9k token 的聊天 prompt，只花了约 15 ms 的 CPU 时间；单个 render 服务用默认配置就能跑到 73 req/s，只占了一个核出头。回想一下，在聚合模式 p99 崩溃的那个 0.4 req/s 负载下，render 层的占用不到一个核的 1%——几乎可以忽略不计。

这意味着 Render 层几乎不会成为瓶颈，而且成本极低。长 prompt、多模态预处理、推理链解析、工具调用解析这些 CPU 重活，都可以放心地扔给 Render 层，而不用心疼 GPU 时间。

但服务分离也不是免费的午餐。最大的代价就是**每个首 token 都要为传输买单**。而且除了KV Cache传输的耗时，还有其他容易被忽略的因素，比如 Decode 只能在自己前向步骤的间隙轮询，才能发现传输已经完成，而不是传输一完成就立刻被通知。因此一定要确认服务分离的方案是否满足TTFT指标。

博客中给出的决策表，供大家参考：

| 场景 | 建议 |
| --- | --- |
| 生产负载下 ITL p99 达不到 SLO | 拆。这是最主要的使用场景。 |
| 高并发 + 长 prompt | 拆，前提是 KV 传输够快。Prefill 干扰在这里最严重。 |
| 聊天或 Agent 循环，上下文不断增长 | 拆，配合双向 KV 传输，并搭配 KV 卸载或共享 KV Cache（如 LMCache、Mooncake）。 |
| GPU 节点的 CPU profile 里出现模板、分词或解析 | 拆出 Render 层。 |
| TTFT 是主要瓶颈 | 先保持聚合或先测量。传输开销会落在每个首 token 上。 |
| KV 传输慢（看 Decode 的 KV Transfer metrics） | 修好或保持聚合。它会拖慢 TTFT 并限制吞吐。顺便检查网络，配置不当的网络通常也会拖慢集合通信。 |
| 低流量、突发或对延迟不敏感 | 保持聚合。 |

### **实战**

**Prefill/Decode 分离怎么跑**

P/D 需要三个进程：**Prefiller、Decoder、Proxy**。

- **Prefiller**：负责计算 KV Cache，生成一个 token，然后把 KV 块“持有”在那里；
- **Decoder**：通过 KV Connector（通常是 NIXL，走 RDMA）把 KV 块拉过来，然后开始生成；
- **Proxy**：串联两者。对每个请求先调 Prefill（带上 `do_remote_decode: true`），Prefill 返回指向 KV 块的参数，Proxy 再把原始请求连同这些参数转发给 Decode。

对客户端来说，Proxy 看起来就是一个普通的 OpenAI 端点。注意 vLLM 仓库里 `tests/`下的 toy proxy 只适合开发，生产环境请用 llm-d 或 Dynamo。

三个重要参数：

- `VLLM_NIXL_SIDE_CHANNEL_PORT`：同一台机器上每个 worker 必须唯一；
- `kv_lease_duration`：Prefiller 持有 KV 块等 Decoder 来取的超时时间，默认 30 秒，高负载下这是你要调的关键超时；
- `kv_load_failure_policy`：传输失败时怎么办。默认 `fail`直接报错，设为 `recompute`则让 Decode 自己重算缺失的 KV，慢一点但请求能活下来。

还有一个小优化。如果你走 `/v1/chat/completions`，Prefill 阶段已经分过词了，Decode 没必要再来一遍。可以在 Prefill 请求里带上 `return_token_ids`，然后把 token ID 通过 `kv_transfer_params`直接传给 Decode。

**多轮对话别再重复计算上下文**

标准 P/D 只把 KV Cache 从 Prefill 传到 Decode，是单向的。这对多轮对话很浪费：第二轮的时候，Decode 手里还握着上一轮回答的 KV，但 Prefill 从来没算过，于是 Prefill 只能从头重算一遍。

开启 `bidirectional_kv_xfer`后，Prefill 可以把 Decode 已有的 KV 块**拉回来**，只计算新增的 token。Proxy 通过客户端传来的 `conversation_id`来追踪哪些块属于哪个会话。

注意有一个关于推理模型的坑。Decode 的 KV 块里包含了它生成的思考链（thinking traces）。如果下一轮的 prompt 里把这些思考链去掉了（比如 Qwen3 的 chat template 会自动这么做），那么 Prefill 的 prompt 就和 Decode 的 KV 块对不上了。目前 vLLM 还不会自动检测这种不匹配，所以开启双向传输前，务必检查你的 chat template。

**无 GPU 前端，让 GPU 只算 token**

一旦引擎只接收 token ID、只输出 token ID，它就不再需要聊天模板和解析器了。

启动方式是两个服务：

- **Render 层**（无 GPU）：负责 `/render`和 `/derender`，以及推理解析、工具调用解析；
- **引擎**（GPU）：用 `--tokens-only`模式启动，只跑 token-in / token-out。

完整的请求变成三跳：**render → generate → derender**。

除了省 GPU，这样做还有额外好处：

- 路由层可以基于**真实 token**判断 prefix cache 命中，而不是靠文本去猜；
- RL 和评测管线能拿到模型实际看到和产出的 token ID（解码后的文本重新分词不一定和原来一致）

### **结语**

简单来说，分离式服务的本质是让**不同性质的工作互不干扰**，从而在延迟目标下榨出更多有效吞吐。当你的**ITL p99 在生产负载下突破 SLO**，分离式服务就是最直接、最有效的解法。

但分离式服务不是银弹，因为 KV 传输开销会落在每个首 token 上，导致TTFT指标不佳。此外系统复杂度增加还会带来运维难度上升。对于低流量、突发或对延迟不敏感的场景，聚合模式依然简单可靠。
