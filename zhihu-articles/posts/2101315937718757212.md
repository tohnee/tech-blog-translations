## vLLM v0.33.0 推测解码重大特性技术报告

### 第一部分：前置背景——推测解码的底层数学原理

大语言模型（LLM）传统的自回归解码速度极慢，因为每生成一个 token 都需要把完整的模型参数从显存中读取一遍。**推测解码（Speculative Decoding）** 的核心思想是：用一个极小的“草稿模型”（Draft Model）一次性猜出后续的几个 token，然后让大模型（目标模型，Target Model）**进行一次前向传播（Forward Pass），并行验证这串猜测**。

为了确保输出质量不下降，这一机制依赖于严格的**拒绝采样（Rejection Sampling）** 算法。

### 1.1 核心概念与符号定义

- **$q(x)$**：草稿模型预测下一个 token 为 $x$ 的概率。
- **$p(x)$**：目标大模型预测下一个 token 为 $x$ 的概率。
- **$u$**：一个服从 $[0, 1)$ 区间**均匀分布的随机数**（Uniform Distribution），即 $u \sim U(0, 1)$。
- **无损性（Losslessness）**：推测解码的终极要求——无论草稿模型猜得多离谱，最终输出的文本分布在数学上必须与**完全只用目标模型逐字生成**的结果**完全一致**。

### 1.2 核心公式：“猜对”与“猜错”的判断标准

当草稿模型提出了一个 token $x$ 时，接受概率 $\alpha$ 定义为：

$$ \alpha = \min\left(1, \frac{p(x)}{q(x)}\right) $$

- **当 $p(x) \ge q(x)$ 时**：$\alpha = 1$。目标模型比草稿模型更倾向于生成这个 token，**无条件接受**。
- **当 $p(x) < q(x)$ 时**：$\alpha = \frac{p(x)}{q(x)} < 1$。草稿模型“过度自信”，系统**以 $\alpha$ 的概率接受它**。

**如何实现概率接受？系统会引入随机数 $u$：**

- 如果 **$u < \alpha$**：判定为**“猜对”**，接受该草稿 token。
- 如果 **$u \ge \alpha$**：判定为**“猜错”**，拒绝该草稿 token。

### 1.3 深入剖析：随机数 $u$ 究竟是怎么来的？

$u$ 绝对不是通过公式“计算”出来的，而是由 **GPU 上的伪随机数生成器（PRNG，如 Philox 算法）在运行时“掷骰子”掷出来的**。 在底层代码中，系统会瞬间生成一个形状为 `[Batch_Size, 草稿长度]` 的随机数矩阵。**为什么必须用随机数？** 只有引入纯随机的 $u$，才能保证宏观上这个 token 被接受的真实概率精确等于 $p(x)/q(x)$。如果没有随机数（直接比较 $p$ 和 $q$ 的大小），输出分布就会发生偏移，模型就会“变笨”。

### 1.4 拒绝后的修正采样（Reject 后怎么办？）

如果 $u \ge \alpha$，草稿 token 被拒绝。系统会构建一个**修正后的概率分布**：

$$ p_{\text{corrected}}(x) = \text{normalize}(\max(0, p(x) - q(x))) $$

它的直观含义是：目标模型分布 $p$ 中，比草稿模型分布 $q$ 多出来的那部分概率质量。系统会从这个修正分布中**重新采样**一个 token 作为最终输出。一旦在某个位置发生拒绝，该位置之后的所有草稿 token 都会被丢弃。

### 1.5 贪心解码下的特殊情况

如果温度参数为 0（纯贪心解码），无需随机数 $u$。判断标准变为**确定性的 argmax 比较**：如果目标模型在该位置概率最大的 token 与草稿 token 完全相同，则接受；否则拒绝。

### 第二部分：vLLM v0.33.0 六大技术方案详解

vLLM v0.33.0 将优化重心放在了**推测解码（Speculative Decoding）**的“质量与效率”深度协同上。推测解码依赖两大指标：**接受长度**（一轮验证中平均接受多少个草稿 token，越长越快）和**验证开销**（目标模型验证草稿所需的计算资源）。以下六大方案正是围绕这两点展开。

### 方案一：XPress refiner——为“块扩散草稿器”补上因果关系

### 1. 技术背景

DFlash、DSpark 是**块扩散草稿器**，能一次性生成一整块候选 token，速度极快。但它们生成时，块内 token 是**独立采样**的。这导致草稿分布 $q(x)$ 是一堆散乱的边缘分布，连在一起往往违背因果逻辑，目标模型验证时极易发生**早拒（Early Rejection）**：前面一个 token 被拒绝，后面的即使单独合理也无法通过。

### 2. 技术方案

XPress 是一个轻量级（约 **8000 万参数**）的**因果精炼头**。它将前一个块的 token、草稿器的隐藏状态、块的全局摘要三者因果地混合，计算出一个 **Logit Bias（逻辑值偏置）** 修正原始概率。它使用 **K 步并行的 Jacobi 迭代** 求解（利用上一轮所有值同时更新所有位置），在不丢失并行速度的前提下，把缺失的因果性“灌回”块内每个 token。

### 3. 效果

- 接受长度提升约 **30%**（最高 56%）。
- 端到端吞吐量提升 **1.3 倍至 1.7 倍**（对比原始 DFlash）。
- 在 Qwen3-8B 上，对比裸 DFlash 带来 **18.5%** 的吞吐提升。

### ⚠️ 缺陷与边界

- **与 Adaptive Verification（AV）的协同存在严重缺陷（PR #65175 修复前）**：AV 对 XPress 完全无效，导致每个草稿在第一个之后都被裁剪。修复后，在低并发（1和8）时开启 AV 仍有 8% 的吞吐损失；并发度 32 及以上才转为净收益。**低并发场景不建议开启 AV**。
- **优势并非普适**：在 H200 上对比 DSpark，XPress 仅有 +4.1% 吞吐，且在部分 batch 64 的测试中输给 DSpark。其收益高度依赖于草稿器本身的质量基线。
- **种子质量与截断限制**：Jacobi 迭代从草稿器的预测出发，如果初始预测严重偏离，收敛结果仍受限。且精炼只对 Top-C 候选评分，若草稿器将正确 token 留在了 Top-C 之外，精炼器永远无法触达。

### 方案二：FLy——有损验证，用“可控质量折损”换吞吐

### 1. 技术背景

标准推测解码的验证是无损的，但在**高熵位置**（目标模型也很犹豫，概率分布分散的地方），草稿 token 很容易被拒绝，导致整条草稿链中断。

### 2. 技术方案

FLy 是一种**有损**策略。包含两步：

- **第一步：熵门控**：计算 $H(p) = -\sum_{i} p_i \log p_i$，只关注极不确定的高熵位置（Top-k，默认 k=3）。
- **第二步：前瞻窗口**：如果向后看 W 个后续 token 原本都能通过，FLy 就会延迟当前高熵位置的拒绝，硬着头皮接受草稿。

### 3. 效果

- 吞吐提升 **1.04~1.31 倍**。
- 质量保留率最低为 **97.9%**（用不到 2.1% 的质量折损换速度）。

### ⚠️ 缺陷与边界

- **本质是有损的**：不保留目标分布，**默认关闭**（需设置 `rejection_sample_method="fly"` 开启）。不适合对分布保真度有严格要求的场景（如评估、审计）。
- **参数约束严格**：要求至少 2 个投机 token；`fly_window_size` 必须小于 `num_speculative_tokens`；违反会导致行为未定义。
- **兼容性限制**：MRV2 下需要 MTP/EAGLE/DFlash 等受支持的 proposer，独立的 draft_model 仍需 MRV1。质量折损的下界（97.9%）是统计性的，不代表所有任务都保证不低于此值。

### 方案三：DFlash/DSpark 释放 token budget 预留的 draft slot

### 1. 技术背景与旧逻辑的“幽灵占座”

vLLM 采用基于 token 预算的调度。旧版调度器会**按照最坏情况强制扣除草稿槽位**（DSpark 扣除 K-1 个）。在预算 512、并发上限 64、K=5 的配置下，每个请求账面被扣 10 个 token（1 基础 + 5 草稿 + 1 额外）。$512 \div 10 = 51.2$，导致**最多只能运行 51 个请求**，并发被死死卡住。

### 2. v0.33.0 的条件性豁免与两层安全机制

PR #59468 引入**条件性豁免**：当 `max_num_seqs × (1 + K) ≤ max_num_batched_tokens`（如 $64 \times 6 = 384 \le 512$）时，豁免生效，调度器不再预扣草稿槽位。

- **第一层：静态安全闸门**：保证纯 Decode forward pass 的最坏情况（64个请求全满额接受K个草稿，总query 384）不会撑爆物理上限（512）。
- **第二层：动态预算裁剪（AV）**：运行时根据存活概率裁剪低质量槽位，节省计算。

### 3. 混合调度（Prefill + Decode）的真相

**关键结论**：在 vLLM 0.33.0 中，只要当前 Batch 包含任何处于 Prefill 阶段的请求，调度器就不会为 Batch 中的任何请求调度投机 token。所有 Decode 请求都会**降级为非投机解码**。因此，“Prefill 占用预算导致满额验证不够”的情况**在架构上就不会发生**，满额验证的 query 只会在纯 Decode 的 forward pass 中执行。

### 4. 满额接受 K 的场景

如果 K 个草稿全部通过，目标模型在验证第 K 个草稿时会自然产生第 K+1 个预测，被**无条件接受为 Bonus Token**，单步产出 $K+1$ 个 token。静态条件中的 $1+K$ 已按此最坏情况设计，Bonus Token 是副产物，不额外占用独立槽位。

### 5. 效果数据（DeepSeek-V4.1-Flash + DSpark，GB300）

- 最大运行请求数：51 → **64**
- 输出吞吐：1354 tok/s → **3448 tok/s**（**+154%**）
- TPOT p50：29.0ms → **15.8ms**（**-45%**）
- 接受长度：4.74 → 4.76（几乎不变，证明吞吐爆发纯靠调度释放）

### ⚠️ 缺陷与边界

- **静态条件失效**：如果 `max_num_seqs` 很大而 `max_num_batched_tokens` 较小，豁免直接失效，系统退回旧逻辑。
- **KV Cache 硬约束**：草稿 token 会占用每请求的 KV Cache。显存紧张时，实际可运行请求数可能低于 token budget 允许的数量。
- **计算资源竞争**：在高并发下，草稿 token 与真实 token 争夺计算资源。方案三释放了**调度记账层面**的并发上限，但计算竞争的边界仍然存在，需 AV 配合。
- **混合批次代价**：在 Prefill 与 Decode 频繁交替的工作负载中，投机解码被禁用的时间比例很高，吞吐收益会被稀释。

### 方案四：draft_lm_head 量化——把草稿步骤中最重的内核变小

### 1. 技术背景

EAGLE/MTP 等草稿器与目标模型共享最重的 `lm_head`（词表投影层）。BF16 下该矩阵可能占用 **1.27 GB** 显存。草稿器每猜一个 token 都要完整读取一遍，造成内存带宽瓶颈。

### 2. 技术方案

引入 `draft_lm_head_quantization`（支持 FP8 / NVFP4），为草稿器创建一份**私有的、量化后的 `lm_head` 副本**。目标模型仍用原始 BF16 head 验证，输出不受影响。

### 3. 适用范围与效果

- **EAGLE / MTP**：通过该配置创建私有量化 head。
- **DFlash / DFlash2**：直接使用目标 `lm_head`，支持量化**目标模型的 head**（但 DFlash2 拒绝量化目标 head，会报错）。
- **DSpark**：自带 `ParallelLMHead`，量化目标 head 对它无关紧要，自有 head 量化需看具体实现。
- **效果**：并发度为 1 时，解码速度提升约 **18%**（39.4 → 46.5 tok/s）。

### ⚠️ 缺陷与边界

- **大小比率依赖**：7B INT4 搭配 13B 验证器，加速比可能仅 1.1–1.3 倍；搭配 70B 才能达到 2.8–3.2 倍。
- **Weight-only 陷阱**：仅权重量化可能使拒绝率升高（如从 25% 跳到 15%–25%），抵消加速效果。
- **拒绝率阈值**：若草稿拒绝率 > 20%，验证器成为瓶颈，量化吞吐乘数完全丧失。需监控 `speculative_tokens_accepted / speculative_tokens_proposed`。
- **MoE 离散退化**：NVFP4 可能引起 MoE 路由器决策边界附近的**离散翻转**，导致接受率断崖式下跌。
- **TP>1 风险**：在张量并行下，草稿 head 量化的验证路径可能无法完全保护输出正确性。

### 方案五：EAGLE/MTP 前缀缓存 lookahead block hash

### 1. 技术背景

EAGLE/MTP 草稿器有个特殊依赖：缓存块最后一个位置的 KV，依赖该块**之后的下一个 token**。标准做法是保守地丢弃最后一个匹配块，导致缓存命中少一块（在混合模型上损失 544–1600 token）。

### 2. 技术方案

把“块之后的下一个 token”纳入缓存键。只有当后续 token 也匹配时，才复用最后一块。v0.33.0 默认开启，可通过 `disable_lookahead_block_hashes` 关闭。

### 3. 效果数据（Qwen3.6-27B + MTP，GB200）

- 前缀缓存命中率：72.7% → **85.0%**
- 请求吞吐：9.09 → **12.43 req/s**（**+37%**）
- Median TTFT：304ms → **226ms**（**-26%**）
- 接受长度基本不变。

### ⚠️ 缺陷与边界

- **并非所有模型正收益**：在 DeepSeek-V4 上，lookahead hashes **降低了接受长度**（5.69 → 5.66–5.67），因此 DSpark 在该模型上不启用。
- **兼容性限制**：仅在未配置 KV Connector 时默认启用；multi-module MTP 下保持关闭。
- **外部消费者对齐**：如果外部系统消费 KV 缓存事件，两边必须运行相同的 lookahead 设置，否则哈希不一致。
- **哈希就绪延迟**：在混合模型（如 Qwen3.8）上，块大小可达 800–1616 token，大块首个缓存键的可用时间被推迟。
- **Mamba 回滚**：需区分可逆的 token KV 和不可逆的 Mamba/GDN 状态。

### 方案六：MRV2 自动跳过“无请求可用”的 draft 步骤

### 1. 技术背景

在 MRV2 架构下，预填充（Prefill）阶段或分块预填充的非最后块，本质上只是上下文计算，不需要草稿候选。但标准流程依然会调起草稿器（K=0），造成浪费。

### 2. 技术方案

MRV2 检测当前步骤是否有“可使用草稿的请求”，没有则**跳过草稿采样和解码步骤**。（注意：EAGLE/MTP 仍须执行草稿 prefill pass 保持 KV 同步）。

### 3. 效果

- 预填充吞吐：EAGLE3 +1.9%（512预算），DFlash +7.3%（512预算）。
- 2048 预算下分别降至 +1.4% 和 +2.7%。

### ⚠️ 缺陷与边界

- **增益有限**：官方描述为“modest”，因为草稿 prefill pass 无法跳过。
- **覆盖范围特定**：主要针对非最终 Prefill 分块和确定会达到 `max_tokens` 的请求。
- **调度簿记开销**：即使草稿计算跳过，投机路径的调度簿记开销并未消失（V2 比 V1 曾多出 7.29%–16.64% 的额外开销）。
- **仅限 MRV2**：V1 Runner 不生效。

### 第三部分：技术总结与逻辑归纳

vLLM v0.33.0 的推测解码优化不是“开得越多越好”的堆叠，而是围绕“**草稿质量**”“**验证效率**”与“**系统调度**”三条主线的精准打击。每一项优化都有明确的收益区间和边界。

| 特性 | 优化对象 | 核心机制 | 关键收益 | 核心边界 / 注意点 |
| --- | --- | --- | --- | --- |
| XPress refiner | 草稿质量 | 并行因果精炼，恢复块内因果依赖 | 接受长度 +30%，吞吐 ~1.3–1.7× | AV 低并发下负收益；对比 DSpark 边际收益窄；种子质量与 Top-C 截断构成上限 |
| FLy 验证 | 验证保守性 | 熵门控 + 前瞻窗口，延迟高熵位置的拒绝 | 吞吐 1.04–1.31×，质量保留 ≥97.9% | 有意有损，默认关闭；参数约束严格；MRV2 下独立 draft_model 不可用 |
| Draft slot 释放 | 系统调度 | 静态安全阀放行豁免；混合批次主动禁用投机 | 吞吐 1354→3448 tok/s（+154%），请求数 51→64 | 静态条件不满足则失效；KV Cache 物理容量仍是硬约束；混合批次投机完全禁用；高并发下计算资源竞争仍存在 |
| draft_lm_head 量化 | 内存带宽 | 为草稿器创建私有量化 head 副本 | 解码 +18%（c=1） | 依赖草稿/验证器大小比；weight-only 可能适得其反；拒绝率 >20% 增益消失；MoE 离散退化；DFlash2 拒绝量化目标 head；TP>1 有输出安全边界 |
| Lookahead block hash | 缓存复用 | 将后继 token 纳入缓存键，安全多复用一块 | 命中率 72.7%→85.0%，吞吐 +37% | DeepSeek-V4 上降低接受长度；KV Connector / multi-module MTP 不生效；外部消费者需哈希对齐；大块哈希就绪延迟；Mamba 回滚需特殊处理 |
| MRV2 跳过空 draft | 计算浪费 | 运行时检测无请求状态，跳过草稿采样/解码 | 预填充 +1.9%–7.3% | 草稿 prefill pass 仍须运行，增益有限；预算越大相对增益越小；调度簿记开销未消除；仅适用于 MRV2 |

**一个贯穿性的结论**：XPress 需要 AV 的并发感知配合，FLy 需要接受质量折损，draft slot 释放需要配置和显存的同时满足，量化需要监控拒绝率，lookahead hash 需要模型验证，MRV2 跳过需要接受调度开销的存在。每一项优化的实际收益，都取决于部署场景是否落在它的**有效边界之内**。

### 第四部分：升级注意事项与破坏性变更

vLLM v0.33.0 是一个 **major release**，包含以下破坏性变更，升级前需确认现有部署不依赖已移除的组件：

- **CUDA 12.9 构建已移除**：仅发布 CUDA 13.0 wheel 和镜像，需要 PyTorch 2.14。
- **Medusa 和 MLP speculator 已移除**：两种较旧的投机解码方法不再支持。
- **旧版 Ray 编译图执行器已移除**。
- **`--mamba-cache-mode` 已弃用，不再生效**。
- **生成暂停期间发送的请求现在返回 HTTP 503**。
- **NIXL connector 需要 NIXL 1.5 或更新版本**。
