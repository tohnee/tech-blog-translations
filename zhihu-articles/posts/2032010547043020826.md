## 推理框架选择

对于本地部署，用的比较多的是Ollama，llama.cpp和LM Studio。其中LM Studio是有GUI的，上手难度是最低。Ollama是命令行，但操作类似docker，上手也非常容易，llama.cpp需要编译，但是性能最好，听说Ollama和LM Studio的底层都依赖它。这次的目的是探索本地模型部署的极限，那么就还是使用llama.cpp。在阿里云社区有很好的总结文档

[本地 LLM 部署工具（写给小白的 LLM 工具选型系列：第一篇）-阿里云开发者社区](https://developer.aliyun.com/article/1724001)

## Llama.cpp部署方法

上次是下载代码进行编译，这样配置很麻烦，因为还需要配置nvcc，这个对于推理场景，是过于繁琐的。这次就去官网详细看看有没有更好的办法

[https://github.com/ggml-org/llama.cpp](https://github.com/ggml-org/llama.cpp)

发现可以用brew安装，那么这个就方便了。不过发现这个安装的cpu版本的，没有直接安装gpu版本的办法。听说这个在mac上能够直接安装metal加速的版本，可能也是因为mac上用brew本来就多，那么brew对mac的适配也是最好。

官网给出的第二个办法是docker镜像

[https://github.com/ggml-org/llama.cpp/blob/master/docs/docker.md](https://github.com/ggml-org/llama.cpp/blob/master/docs/docker.md)

这个办法倒是会方便一些，不过会有一些额外的cpu和ram开销，如果主机系统有冗余性能，还是可以使用这个方案的。但是当我细看和尝试，才开始发现这个方案的不靠谱之处，比如在docker hub上找不到对应的org和image。手动pull下来查看

```text
sudo docker pull ghcr.io/ggml-org/llama.cpp:light-cuda
sudo docker inspect ghcr.io/ggml-org/llama.cpp:light-cuda
```

这里竟然没有对镜像做日期戳，查看了镜像是当天生成的，也就是说没有release版本。看来和本地编译差别还真不大。

官网给出的第三个方法是使用预编译的镜像

[https://github.com/ggml-org/llama.cpp/releases](https://github.com/ggml-org/llama.cpp/releases)

但是看这些编译的文件，版本号也没有，linux的cuda版本也没有，感觉就不是太靠谱。

那么第四个方案，就是下载代码本地编译了。鉴于前三个方案都没有那么完美，那么这次还是选择这个方案。整体说来，llama.cpp做的上手难度确实不小，同时因为ollma已经把llama.cpp包在里面，绝大部分用户应该都是直接使用ollama，所以llama.cpp团队也缺乏动力去把易用性这个事情做好。同时也大概能才到，这个项目的核心团队，也是比较硬核科技的工程师类型。

### 编译环境准备

首先是驱动安装

```text
sudo apt install nvidia-driver-580-open
```

成功之后使用nvidia-smi确认。

接下来是nvcc配置，虽然conda也可以配置nvcc，但是在编译的时候还需要设置路径，比较容易出问题，这里选在在系统上安装cuda-toolkit。

[https://developer.nvidia.com/cuda-downloads?target_os=Linux&target_arch=x86_64&Distribution=Ubuntu&target_version=24.04&target_type=deb_network](https://developer.nvidia.com/cuda-downloads?target_os=Linux&target_arch=x86_64&Distribution=Ubuntu&target_version=24.04&target_type=deb_network)

安装cuda-toolkit-13-0之后，配置环境变量

```text
echo 'export PATH=/usr/local/cuda-13.0/bin:$PATH' >> ~/.bashrc
echo 'export LD_LIBRARY_PATH=/usr/local/cuda-13.0/lib64:$LD_LIBRARY_PATH' >> ~/.bashrc
source ~/.bashrc
```

使用nvcc --version确认配置环境。

### 进行编译

参考

[https://github.com/ggml-org/llama.cpp/blob/master/docs/build.md#cuda](https://github.com/ggml-org/llama.cpp/blob/master/docs/build.md#cuda)

下载源代码

```text
git clone https://github.com/ggml-org/llama.cpp
cd llama.cpp
```

进行编译，[注意这里要把conda环境的libcuda.so](http://%E6%B3%A8%E6%84%8F%E8%BF%99%E9%87%8C%E8%A6%81%E6%8A%8Aconda%E7%8E%AF%E5%A2%83%E7%9A%84libcuda.so) 路径添加到链接器搜索路径

```text
cmake -B build -DGGML_CUDA=ON
cmake --build build --config Release -j12
```

等待几分钟，编译完成，会在build/bin目录下生成llama-cli，llama-server这些binary。

### 不同的量化方法

就是对于Q4量化，也有不同的方法。总结如下

![](https://pic4.zhimg.com/v2-28756cf5fe069371e3ec75d09159c0c9_r.jpg)

首先是最legacy的格式，它们解码简单，老旧硬件兼容性好。但缺点是4位下精度明显落后于现代格式。

然后是K-Quant格式（Q4_K_S / Q4_K_M / UD-Q4_K_XL），它是llama.cpp创建的，采用两级分块量化：小分组→超级块，配合双重量化缩放因子 。

- Q4_K_S（Small）：大部分权重保持4位，文件更小，精度略低
- Q4_K_M（Medium）：对敏感层（如attention输出、最终层）使用5-6位，社区最推荐的4位默认选择
- UD-Q4_K_XL：Unsloth定制版，进一步保留高精度权重，精度最高但文件最大

这种格式的精度/体积平衡优秀，现代硬件推理速度快，当然还是比Legacy格式解码略复杂。

之后还有I-Quant格式（IQ4_NL / IQ4_XS），这个是相对新出的。基于重要性矩阵（imatrix）校准 + 非线性重建，专为极限压缩设计 。它4位区间内有最佳质量/体积比，适合显存紧张场景。但是需要imatrix校准数据，无校准则精度下降，而且需要比较新的硬件支持快速解码。

### 基本使用

参考这个资料：[https://unsloth.ai/docs/models/qwen3.5#llama.cpp-guides](https://unsloth.ai/docs/models/qwen3.5#llama.cpp-guides)

```text
# in ~ dir
export LLAMA_CACHE="models/unsloth/Qwen3.5-4B-GGUF"
./Code/llama.cpp/build/bin/llama-cli \
    -hf unsloth/Qwen3.5-4B-GGUF:Q4_K_M \
    --ctx-size 16384 \
    --temp 0.7 \
    --top-p 0.8 \
    --top-k 20 \
    --min-p 0.00
```

这些模型会自动下载到~/models/unsloth/Qwen3.5-4B-GGUF/models--unsloth--Qwen3.5-4B-GGUF/snapshots/xxxxx/

会有这么两个文件

```text
mmproj-BF16.gguf  Qwen3.5-4B-Q4_K_M.gguf
```

这个mmproj-BF16.gguf是系统自动下载的，用于处理图像数据。如果只是处理文本，其实也用不上。

因为这个文件里面，没有设置chat的模版，thinking的mode也没有关闭，所以说出来的有些胡言乱语，这里主要看性能，就没有细看这个部分。

### 显存使用分析

在程序退出的时候，会显示显存使用

```text
| memory breakdown [MiB]  | total    free    self   model   context   compute    unaccounted |
|   - CUDA0 (RTX 5070 Ti) | 15839 = 11037 + (3655 =  2603 +     562 +     490) +        1147 |
```

这里模型本身，是占用2603MiB显存，这个是由模型本身决定的，选用Q4_K_S会略微减小这个数值，实测可以减少到2459MiB。Context到562MiB是上下文占用，主要就是存储KV cache。因为设置了ctx-size为16k，如果设置更长，这个数值就会等比例增加。这个数值还是比较大的，算下来如果设置64k的上下文大小，那么kv cache所占用的显存就和模型大小差不多了。这个部分也是可以调整的，默认是fp16存储kv cache，如果是用量化模式，或者bf16，可以调整大小和精度。

在接下来是compute部分，就是推理过程中的激活值。这个部分和模型architecture相关，context变化也不会改变。在之后是unaccounted部分，这个占用还不少。不过也是nvidia的runtime相关，不容易去调整。

### 速度分析

对于这个4B的Q4模型，5070ti的速度还是很快的。[ Prompt: 6642.3 t/s | Generation: 179.8 t/s ]。如果只看推理部分，可以粗略估算一下这个是否符合预期。5070ti的显存带宽是896.0 GB/s，模型权重大小是2.5G，那么理论上是可以达到350 t/s。那么看来这个计算的瓶颈不在显存带宽，可能在别的地方。


模型大小是5.68G，查看显存情况，这里kv cache的大小不变，激活参量的显存略微增加，系统runtime开销也增加。

```text
| memory breakdown [MiB]  | total   free    self   model   context   compute    unaccounted |
|   - CUDA0 (RTX 5070 Ti) | 15839 = 8524 + (5916 =  4861 +     562 +     493) +        1398 |
```

直觉来说，kvcache的大小应该随着模型参数增大，但实际上没有。这里可以详细看下context的kv计算方法

```text
KV Cache 大小 = 2 × num_layers × num_kv_heads × head_dim × seq_len × bytes_per_element
                ↑    ↑            ↑              ↑          ↑         ↑
              K+V   层数       KV头数(GQA)    每头维度   序列长度   精度字节数
```

对于Qwen3.5的4B和9B，他们的layer数是不变的，都是32层，KV的头数也不变。主要是每个head内部的dim变化，那么这个并不影响kv cache的计算。

## Qwen3.5 27B模型测试

从Qwen3.5这一代开始，就没有14B的模型。大概是9B以下的模型，可以用Q4量化装进8G的主流显卡中。同时9B模型和14B没有太大差距，所以Qwen精简产品线。那么，对于27B的模型，能否用16G的显卡来装载运行呢。

### Qwen3.5 27B模型3bit量化

```text
export LLAMA_CACHE="models/unsloth/Qwen3.5-27B-GGUF"
./Code/llama.cpp/build/bin/llama-cli \
    -hf unsloth/Qwen3.5-27B-GGUF:Q3_K_S \
    --ctx-size 16384 \
    --temp 0.7 \
    --top-p 0.8 \
    --top-k 20 \
    --min-p 0.00
```

这里选用3bit的量化，同时用更精简的S版（而不是M版）。这里也是为了性能做出的一些妥协。这个3bit的量化，精度损失应该是不少的，之前看的4bit是个损失比较少的极限位置。那么这里就主要做性能测试。

即使如此，模型的大小也已经是12.3GB，内存情况如下，基本也是贴近极限。

```text
| memory breakdown [MiB]  | total   free     self   model   context   compute    unaccounted |
|   - CUDA0 (RTX 5070 Ti) | 15839 = 1570 + (12857 = 11188 +    1173 +     495) +        1411 |
```

这里的上下文，还是选取的16k，如果要更大的上下文，这里可以扩展到32k。那么再大，就是要爆显存的。可以说，16G运行这个模型，容错空间是非常小的，可以说随便想改个什么东西，就会爆显存。

速度来说，倒是还可以，接近50token/s，还是很舒适的区间。

[ Prompt: 202.6 t/s | Generation: 48.8 t/s ]

## Qwen3.5 35B-A3B模型4bit量化测试

对于27B的模型已经到极限了，为什么我这里还来尝试35B的模型呢。因为这个是MoE的模型，计算量会小一些，那么就有机会通过llama.cpp的CPU混合推理模式，把一部分参数交给CPU来推理。

### 模型加载

```text
export LLAMA_CACHE="models/unsloth/Qwen3.5-35B-A3B-GGUF"
./Code/llama.cpp/build/bin/llama-cli \
    -hf unsloth/Qwen3.5-35B-A3B-GGUF:Q4_K_M \
    --ctx-size 16384 \
    --temp 0.7 \
    --top-p 0.8 \
    --top-k 20 \
    --min-p 0.00
```

模型的整体大小是22GB，显卡是装不下的，这里llama-cli，自动的把一些weight给offload到主机，使用cpu推理。

```text
| memory breakdown [MiB]  | total   free     self   model   context   compute    unaccounted |
|   - CUDA0 (RTX 5070 Ti) | 15839 =   60 + (14384 = 13505 +     382 +     497) +        1394 |
|   - Host                |                 20626 = 20586 +       0 +      40                |
```

可以看到，这个llama-cli的自动offload是很智能的，基本把显存压缩到了极限。然后在host上使用了20G。这里重新运行以上的cmd，加上--verbose，从这些log里看看具体细节

### 自动分配流程

模型加载时候，并没有设置多少层放到GPU（比如--n-gpu-layers 28）。而是使用了llama-cli的自动适配流程，不止是把每一层全部做分离，甚至能够对每一层内部的模块进行分离。

查看llama-cli的verbose日志，可以看到它最开始尝试把所有层放到GPU，发现不够。然后尝试了全层溢出overflow_type=4，再尝试把MoE 专家权重全部移至 CPU，发现GPU空闲很多，再尝试把部分层放到CPU。

最终的分配策略，大部分weight还是在GPU里，但是从25到40层，它们的ffn的部分层，分配到CPU中，类似log如下

```text
create_tensor: loading tensor blk.39.ffn_gate_inp.weight
tensor blk.39.ffn_down_exps.weight (176 MiB q5_K) buffer type overridden to CUDA_Host
create_tensor: loading tensor blk.39.ffn_down_exps.weight
tensor blk.39.ffn_gate_exps.weight (144 MiB q4_K) buffer type overridden to CUDA_Host
create_tensor: loading tensor blk.39.ffn_gate_exps.weight
tensor blk.39.ffn_up_exps.weight (144 MiB q4_K) buffer type overridden to CUDA_Host
```

这个也是很有讲究的，因为对于MoE的稀疏模型，FFN层会有很多的参数（experts），但是只有少量激活。那么它们会占用较多的显存空间，但是计算量相对较少。这些部分，offload给CPU简直是完美操作。另外这个offload没有动Attention层，因为attention层的计算，GPU可以高效优化，而且kvcache存在GPU也更加合理。

当然，这么做也有一定的副作用，就是计算时候，会来回在CPU和GPU之间传输数据。这个需要性能实测来看效果。5070ti，offload 16层的MoE，得到如下效果

[ Prompt: 94.6 t/s | Generation: 75.2 t/s ]

这个生成速度，是非常不错的，不过prompt处理速度，是比较慢。后来发现这是因为输入的input比较短，如果使用长的输入，我得到了这个结果

[ Prompt: 1222.2 t/s | Generation: 77.9 t/s ]

### 增加上下文测试

刚才尝试的是16k的上下文，kv cache的使用是382M。如果设置128k的上下文，同时把offload的层数设置为21，那么可以load起来

```text
| memory breakdown [MiB]  | total   free     self   model   context   compute    unaccounted |
|   - CUDA0 (RTX 5070 Ti) | 15839 =  620 + (13842 = 10726 +    2622 +     493) +        1377 |
|   - Host                |                 11309 = 11045 +       0 +     264                |
```

这个可以运行，不过如果要做多个session，会比较困难。因为每个session都需要独立的上下文空间，和activation空间。对于128k长上下文的情况，大概就是到2个session。不过这个应用场景也是有限，下面是Deepseek说的上下文场景

短上下文 (4K - 8K tokens)

- 典型应用：文本分类、情感分析、简单问答、极短的代码补全。
- 主要特点：成本极低、响应极快。适合高频、机械的确定性任务。

中上下文 (16K - 32K tokens)

- 典型应用：多轮对话、文档摘要、中型代码文件重构、邮件撰写。
- 主要特点：可处理较长对话或完整文档，多数模型在此范围能保持较好性能。

长上下文 (64K - 128K tokens)

- 典型应用：长合同分析、整本书总结、大型代码库理解、深度研究。
- 主要特点：能一次性处理大部头内容，但延迟增加显著。需注意除顶级模型外，多数模型在此范围性能衰减严重，可能出现“迷失中间”问题。

如果我设置32K的token，应对大部分人任务是足够的，而且能够支持到多个session，比如8个session。这个对于本地的应用是足够的。

### 性能观察

在MoE模型运行的时候，GPU功耗大概是100W，CPU是200%，说明是双核运行。从nvtop看到显卡的IO速度是100M 每秒。整体来说，这个系统开销并不大，比之前的一些稠密模型要更加省资源。

但是这里什么是bottleneck很奇怪，因为这个传输速度100M，没有到PCIE和内存的极限。CPU的200%，也没有到多核的极限。自己去测了几个方法，比如设置-t 8, nommap，都没有变化。看之后有没有机缘，来解决这个问题。

### llama-cpp服务器模式运行

刚才都是使用llama-cli做本地模式进行聊天，这里使用server模式，让llama-cpp在后台运行。

```text
export LLAMA_CACHE="models/unsloth/Qwen3.5-35B-A3B-GGUF"
./Code/llama.cpp/build/bin/llama-server \
    -hf unsloth/Qwen3.5-35B-A3B-GGUF:Q4_K_M \
    --ctx-size 32768 \
    --temp 0.7 \
    --top-p 0.8 \
    --top-k 20 \
    --min-p 0.00 \
    --chat-template-kwargs '{"enable_thinking":false}' \
    --n-cpu-moe 18 \
    --parallel 2 \
    --host 0.0.0.0
```

接着打开localhost:8080就可以访问一个chat页面。这样就实现了自己host一个chatGPT。同时这个支持openai格式的http访问，暂时不支持anthropic格式。可以说自己本地部署，就相当方便了。

## 小结

这次的探索很有收获，主要是体验了一把MoE模型。这个MoE的设置，简直是为GPU和CPU混合推理量身定做，太香了。这样子即使是8G的显卡，也能够自己本地部署35B-A3B这样的模型。随着大模型技术的发展，如果开源模型还能够跟得上闭源SOTA，那么本地部署会越来越成为趋势。现在是用台式机本地部署，可能之后是用笔记本，甚至手机来进行本地部署。
