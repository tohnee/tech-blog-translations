## 一、Kubernetes 到底解决了什么问题？

在没有 Kubernetes （k8s）之前，容器在生产环境主要面临几个问题：

- 容器如何**调度**到合适的机器？
- 容器挂了，如何**自动恢复**？
- 服务如何**发现与负载均衡**？
- 配置、存储、升级如何**标准化管理**？

**一句话总结：**<br>Kubernetes（K8s）解决了**在大规模集群中自动化地管理、调度和保护容器化应用**的问题。

具体来说，它通过以下三点彻底改变了运维方式：

- **从“人盯机器”转为“系统自愈”**：以前需要运维手动重启挂掉的服务，现在 K8s 发现容器状态不对会**自动重启或替换**。
- **从“指定计算资源”转为“抽象资源池”**：你不再需要关心应用跑在哪个具体的服务器上，K8s 会像**操作系统的调度器**一样，自动帮你找最合适的空闲节点。
- **从“手动扩缩”转为“按需弹性”**：面对流量激增，K8s 能根据 CPU 或内存使用率**自动增加副本数量**，并在流量回落时释放资源以节省成本。

## 二、Kubernetes 的核心工作原理

- Kubernetes（简称 K8s）的核心工作原理可以概括为：**基于“声明式 API”的“控制循环（Control Loop）”机制**。它通过不断对比“期望状态”与“实际状态”，并自动化地消除两者之间的差异，实现集群的自我修复与管理。<br>K8s 并不直接“执行命令”，而是通过一系列独立的控制器（Controllers）运行在一个永不停歇的循环中：
- **期望状态（Desired State）**：用户通过 YAML 文件定义的配置（如“我要运行 3 个 Pod”），存储在 etcd 数据库中。
- **观测（Observe）**：各组件持续监控集群的当前实际状态。
- **对比与修正（Diff & Act）**：如果实际状态（如只有 2 个 Pod）与期望不符，控制器会自动触发操作（如新建 1 个 Pod）来恢复一致。

基本流程如下：

1. **用户提交期望状态**：通过 YAML 或 API 声明应用的最终样子。
2. **API Server 接收**：作为唯一入口，进行认证、校验和准入控制。
3. **状态持久化**：将期望状态写入 **etcd** 这个“事实数据库”。
4. **控制循环**：各类**控制器**不断对比 etcd 中的“期望状态”与实际的“当前状态”。
5. **驱动收敛**：通过调用 API Server 创建、更新或删除资源，使系统状态不断向“期望状态”收敛。

这就是所谓的“**声明式**”系统。你只告诉它“我要什么”，而不必关心“如何做”。

## 三、Kubernetes 核心组件解析

K8s 采用 **Master-Node（控制平面-工作节点）** 架构实现资源调度：

- **控制平面 (Master Node)**：大脑

- **工作节点 (Worker Node)**：员工

![](https://picx.zhimg.com/v2-885cd42e60bdbe8eed1e27e458a6256d_r.jpg)

### **1. 控制平面**

- **API Server**<br>它是整个系统的“大脑”，是所有组件交互的唯一中枢。它本身不做逻辑，只负责**状态读写**和**准入控制**，是系统一致性的核心保障。
- **etcd**<br>Kubernetes 的“记忆”，存储所有集群元数据。它的**稳定性和I/O延迟**是集群扩展的天花板。生产环境务必使用 SSD，并与 Master 节点分离部署。
- **Scheduler**<br>它是集群的“决策者”。当要运行一个新 Pod 时，调度器会根据资源需求、亲和性、污点容忍等策略，在数百个节点中选出“最合适”的那一个。**它只负责“选”，不负责“做”**。
- **Controller Manager**<br>它运行着大量“**控制循环**”，是系统的“执行者”。Deployment Controller 确保副本数，Node Controller 监控节点健康，它们永不停歇地工作，确保现实符合你的期望。

### 2. 工作节点

- **kubelet**<br>节点上的“管家”，负责 Pod 的生命周期。它接收调度器指派，调用**容器运行时**启停容器，调用**CNI插件**配置网络，调用**CSI插件**挂载存储，并定期向 Master 汇报节点健康状况。
- **kube-proxy**<br>服务发现的基石。它监听 Service 变化，在节点上配置 **iptables/ipvs** 规则，将流量智能地转发到后端的 Pod 上，实现四层负载均衡。
- **Container Runtime**<br>如 containerd 或 CRI-O，负责底层容器的运行和管理，是“真正干活”的组件。

### 3. 三大关键抽象

- **Pod**：K8s 中最小的调度单位，可以包含一个或多个紧密关联的容器。
- **Service**：为一组 Pod 提供稳定的 IP 和负载均衡，解决容器 IP 经常变动的问题。
- **Deployment**：定义应用的副本数量和更新策略，是管理无状态应用最常用的方式。

## 四、CNI / CSI / LB：Kubernetes 的三大“插件体系”

### CNI：容器网络互联

CNI 定义了容器网络的标准接口。Kubelet 在创建 Pod 网络命名空间后，会调用 CNI 插件来完成网络配置。<br>**核心职责**：为 Pod 分配 IP，建立节点间网络通道。<br>**常见实现**：<br>**Overlay 网络**：如 Flannel 的 VXLAN 模式，适合大多数云环境，性能有轻微损耗。<br>**Underlay/BGP 网络**：如 Calico 的 BGP 模式，性能好，但需要底层网络支持。<br>**大规模挑战**：Pod 数量激增时，需关注网络策略的性能、路由表规模及 IP 地址管理。

### CSI：容器存储抽象

CSI 将存储供应商的逻辑与 Kubernetes 解耦，让动态供给、快照、扩容等功能成为可能。<br>**核心流程**：用户创建 PVC -> CSI Driver 在存储后端创建磁盘 -> 挂载到指定节点 -> 最终挂载进 Pod。<br>**实践经验**：关注**拓扑感知调度**，确保 Pod 与存储卷位于同一可用区，以降低延迟。快照功能是数据库等有状态服务数据保护的利器。

### LB：负载均衡与服务暴露

负载均衡是服务对外提供能力的桥梁。

**集群内**：**Service** 是基础抽象，通过 kube-proxy 的 iptables/IPVS 规则实现。IPVS 模式在连接数巨大时性能更优。

**集群外**：

**Ingress Controller**：如 Nginx Ingress，提供七层（HTTP/HTTPS）路由、SSL 卸载等高级功能，是现代微服务的首选。

**LoadBalancer**：与云厂商深度集成，一键创建云负载均衡器，但需注意成本和出向流量管理。

## 五、Kubernetes 性能调优的关键点

### 1. 控制平面：

**API Server**：合理配置 `--max-requests-inflight`等参数，防止突发流量将其打垮。多副本部署并前置负载均衡器。<br>**etcd**：**使用SSD硬盘**。定期进行压缩 (`etcdctl defrag`) 以回收存储碎片。分离部署，避免与 Master 组件竞争 IO。<br>**调度器**：通过 `--percentageOfNodesToScore`参数在大规模集群中启用**部分节点抽样**，提升调度性能。

### 2. 节点与工作负载：

**资源管理**：必须为 Pod 设置合理的 `requests`和 `limits`。尤其注意，不恰当的 `CPU limits`可能导致节流，影响应用性能。<br>**镜像回收**：配置 kubelet 的 `imageGCHighThreshold`和 `imageGCLowThreshold`，防止节点被无用镜像占满磁盘。<br>**Pod 密度**：单节点 Pod 数过多会增加 kubelet 和 Docker Daemon 的压力，需根据节点规格找到平衡点。

### 3. 网络与存储：数据通道的优化

**网络模式**：在可管理底层网络时，优先选择 **Calico BGP** 等 Underlay 模式，避免 VXLAN 封包开销。<br>**内核参数**：调整 `net.core.somaxconn`、`net.ipv4.tcp_tw_reuse`等参数，优化网络连接性能。<br>**存储选型**：根据 IOPS、吞吐量和延迟需求选择块存储、文件存储或对象存储。对于数据库，本地 SSD 盘可能是更好选择。

## 六、大规模 Kubernetes 集群运维实践

当集群规模达到**数百节点、上万 Pod** 时，挑战从“功能实现”转变为“**规模化稳定性**”。

**可观测性先行**：在出问题之前，建立完善的监控体系。核心指标包括：API Server 延迟、etcd 写入延迟、节点资源利用率、Pod 启动成功率。

**变更即风险**：所有升级、配置修改都必须有**灰度发布和回滚方案**。可以按节点、按命名空间逐步推进。

**混沌工程**：定期主动注入故障（如随机驱逐 Pod、模拟节点宕机、制造网络分区），验证系统的弹性和应急预案的有效性。

**多租户与资源隔离**：使用 **Namespace**、**ResourceQuota**、**NetworkPolicy** 等机制，确保不同业务团队互不干扰。

**控制平面也需要容量规划**：Master 节点和 etcd 集群的规格需随着集群规模增长而提升，不能一成不变。
