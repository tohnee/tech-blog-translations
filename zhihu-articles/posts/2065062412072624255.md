## 一、NCCL

NCCL（Nvidia collective communications Library）是英伟达为GPU和多节点通信优化的通信库，是现代分布式深度学习背后的核心底座。它屏蔽了底层的网络拓扑（PEIe、NVLink、InfiniBand、以太网）细节，提供类似MPI的高级集合通信接口。

### 1. NCCL 的基本使用流程

- **生成全局 ID**：主节点（Rank 0）生成一个全局唯一的 ID，并通过外部通信机制（如 MPI、Socket）广播给所有参与通信的进程。
- **建立通信器 (Communicator)**：每个进程（或 GPU）拿着这个统一的 ID 以及自己的全局序号（Rank），在设备上初始化通信器。此时 NCCL 会探测网络拓扑，建立最佳的环形（Ring）或树形（Tree）组网结构。
- **执行异步通信**：调用具体的通信函数，将其挂载到指定的 CUDA Stream 中。GPU 内核会与 CPU 上的 Proxy 线程协同完成数据搬运。
- **同步与销毁**：通过 cudaStreamSynchronize 等待通信完成，程序结束后销毁通信器以释放资源。

### 2. 常用核心函数

NCCL 的核心 API 设计非常精简，主要分为**管理**、**集合通信**和**点对点通信**三类。

**通信器管理 (Management API)**

- ncclGetUniqueId(ncclUniqueId* uniqueId)：生成一个集群唯一的“邀请码”（Unique ID），用于构建控制面通信网络的监听。
- ncclCommInitRank(ncclComm_t* comm, int nranks, ncclUniqueId commId, int rank)：最常用的分布式初始化函数。传入总节点数 nranks、组网 ID commId 以及当前节点的序号 rank。
- ncclCommInitAll(...)：单机多卡的快捷初始化函数，可以在一个进程内直接为多块 GPU 初始化通信器。
- ncclCommDestroy(ncclComm_t comm)：销毁通信器。

**集合通信操作 (Collective Operations)**

这是 NCCL 提供的主要功能。以下函数均需要传入发送缓冲区、接收缓冲区、数据量、数据类型、操作类型（如 ncclSum, ncclMax）和 CUDA Stream。

- **ncclAllReduce (全局归约**)：分布式训练中最常用的操作（用于同步梯度）。它将所有 GPU 上的数据进行聚合操作（如求和），然后将最终的完整结果广播回组内的每一个 GPU。
- **ncclReduce (归约)**：将所有 GPU 的数据聚合操作，但结果只保存在指定的**某一个 Root GPU 上**。
- **ncclBroadcast (广播)**：将指定 Root GPU 上的数据完整发送给组内的所有其他 GPU。
- **ncclAllGather (全局收集)**：将每个 GPU 上的数据片段收集起来，最终每个 GPU 都会得到一份来自所有节点的数据拼接组合。
- **ncclAllToAll（全到全）**：把数据**精准切块**，第 i 块只发给第 i个人；
- **ncclReduceScatter (归约散射)**：先对所有 GPU 的数据做归约，然后把结果切分为 N 份，将不同片段分散保存到不同的 GPU 上。

**点对点与分组操作 (P2P & Group API)**

- ncclSend / ncclRecv：用于明确指定发送方和接收方的点对点数据传输。
- ncclGroupStart() / ncclGroupEnd()：这两个函数必须配对使用。用于将多个通信操作合并成一个单一的逻辑事务提交，这对于避免复杂通信拓扑中的死锁非常重要。

如果使用 PyTorch，基本不需要手写上述的 C API。PyTorch 的 torch.distributed 包直接将 NCCL 封装为了后端引擎。只需调用 init_process_group(backend="nccl")，然后使用 dist.all_reduce() 或直接套用 DistributedDataParallel (DDP)，PyTorch 会自动在底层调度 CUDA Stream 并调用对应的 NCCL 函数。

## 二、基础架构并行策略

### 1. TP

**问题**

- 超大模型单层参数量巨大，单卡显存放不下权重与激活；
- PP 流水线并行只能切整层，无法解决**单层本身过大**的瓶颈；
- TP 在**层内拆分计算**，分摊单层权重显存，实现超大 Transformer 层分布式执行。

**核心思想**

张量并行将线性层权重张量沿特征维度切分到多张 GPU；分为两种基础切分模式：

- **列并行（ColumnParallel）**：权重沿输出维度切分；
- **行并行（RowParallel）**：权重沿输入维度切分；

遵循「列并行后跟行并行」配对范式，尽可能减少集合通信次数；依靠 AllReduce/AllGather 合并分片结果。在 LLM 中，QKV、Up/Gate 使用列并行；Attention 输出投影 Wo、MLP Down 使用行并行。

**具体实现**

（1）Multi-Head Attention

- Q/K/V 投影：**列并行（输出维度切分）**数学上沿输出维度切分，落地等价于按注意力头划分；每张 GPU 仅持有部分 head 对应的 QKV 权重，独立计算局部 head 注意力，head 之间无依赖，注意力计算阶段不需要通信。
- Attention 输出投影 Wo：**行并行（输入维度切分）**各 GPU 输出局部结果，执行一次 AllReduce 聚合得到完整 Attention 输出。

（2）MLP（SwiGLU）

- Gate/Up 投影：**列并行**，输入 X 全量广播，各卡计算分片激活；
- Down 投影：**行并行**，直接接收分片激活做局部矩阵乘；
- 只在 MLP 末尾执行一次 AllReduce 汇总输出；

**通信约束**

TP 通信量大，高度依赖 NVLink 高速互联，**适合单机内多卡，不推荐跨节点**；TP 规模尽量能整除 head 数量、intermediate 维度。

**应用场景**

- 70B/400B 等超大 LLM 训练、推理，单层权重超出单卡显存；
- 单机配备 A100/H100，具备 NVLink 高速互连；
- 和 DP、PP 组合形成 3D 并行 DP+TP+PP；
- vLLM/TensorRT-LLM 大模型推理，依靠 TP 实现超大模型加载。

### 2. PP

**问题**

- 大模型整体层数很深，完整模型无法放入单卡显存；
- 张量并行 TP 只能拆分单层，无法解决**整模型过大**问题；

**核心思想**

- 把模型网络纵向切分成多个阶段（Stage），每个 GPU 只承载一部分连续网络层；
- mini-batch 进一步切分数据成更小微批次（micro-batch），像流水线一样依次流经各个 GPU；
- 利用流水线执行掩盖部分计算与通信延迟，实现分层分布式执行。

**具体实现**

- 模型分层切分：将 Transformer 层划分为多个 stage，GPU0 负责前若干层，GPU1 承接后续层，依次传递中间激活。
- 微批次拆分：把一个 batch 拆成多个 micro-batch，串行送入流水线。
- 执行流程（经典 1F1B 一正一反调度，主流 Megatron 方案）
- 前向：micro-batch 依次流过各个 stage，相邻 GPU 点对点发送激活；
- 反向：梯度沿流水线反向传递；
- 1F1B 调度用来减少流水线气泡（idle 空闲时间），相比简单串行大幅提升利用率。
- 权重：每个 GPU 仅保存自身 stage 对应的权重，显著降低单卡显存占用。

**通信约束**

- 通信方式：**相邻 GPU 点对点通信（Send/Recv）**，不需要集合通信；
- 通信量只传递层间激活，通信总量小于 TP；
- 天然存在**流水线气泡**：首尾 GPU 会出现空闲，micro-batch 数量越少，气泡越严重；
- 支持跨节点部署，不强制要求 NVLink，但节点间网络带宽会影响激活传输速度。
- 大多数中小模型推理一般不常用，因为实时推理对延迟非常敏感，tp能减少单层计算时间，但是pp会额外增加通信，性价比低。

**应用场景**

- 跨节点部署超大模型；
- 离线高吞吐批处理；
- 没有nvlink的设备；

### 3. DP

**问题**

- 单卡（单个实例）算力有限，无法快速处理大批量训练数据；
- TP、PP 只是切模型，无法并行处理样本；
- 需要把训练样本分散到多张 GPU，同时保证各卡模型参数保持一致；
- 为训练而生，推理层面常说的 DP 扩容，一般指启动多套独立 TP 模型副本。

**核心思想**

- 多卡**保存完整模型副本**，每张 GPU 分配不同训练样本独立前向反向；
- 计算完成后汇总梯度、同步梯度，保证所有副本参数更新完全相同。

**具体实现**

- 将全局 batch 切分，分发到各个 DP rank；每张 GPU 持有一份完整模型。
- 各 GPU 独立执行前向传播、反向传播，生成本地梯度。
- **DDP（分布式数据并行，主流实现）**
- 前向无通信；
- 反向传播完成后，执行 AllReduce 聚合所有 rank 梯度；
- 梯度取平均后，每张 GPU 使用相同梯度更新权重；
- 区别于早期 DP：DDP 梯度通信放在反向传播末尾，并且做梯度 bucket 打包，通信效率更高。

**通信约束**

- 通信原语：AllReduce，传输梯度张量；
- 通信量和模型参数量正相关，模型越大，梯度通信开销越高；
- 支持跨节点，对带宽要求低于 TP，但超大模型下梯度同步会成为瓶颈；
- 每张卡完整保存权重，显存冗余高。

**应用场景**

- 需要扩大训练 batch、提升吞吐，充分利用多卡算力；
- 和 TP、PP 搭配组成**3D 并行 DP+TP+PP**；
- 中小模型训练可以单独使用 DDP；
- 大模型训练中，DP 作为最外层并行维度。
- **推理场景中：单机8卡，tp=2即可部署，可以设置dp充分利用资源；moe模型ep的情况下，attention等使用dp生成权重副本。**

### **4. EP**

**问题**

MoE模型有大量的专家，单卡保存所有专家压力大，TP切分会存在大量AllReduce通信开销，EP将专家加载到不同卡上来缓解显存压力。

**核心思想**

将MoE模型中完整的专家部署到不同的卡上，router对每个token选择不同的专家，通过all-to-all将token分发到对应专家所在的卡上，计算完成后通过all-to-all将结果收集回去。

**具体实现**

- 权重分配：总专家数 / EP 并行度 = 单卡本地专家数量；每张 GPU 存放若干**完整专家**，不对专家内部矩阵切分。Attention、Router、Norm 等稠密层一般复用 TP 并行。Attention、Router、Norm在不同group机器上会保存dp副本。<br>
- MoE 四层标准流程<br> ① **路由 Router**：计算 gate logits，选出每个 token Top-K 目标专家，生成路由映射表；<br> ② **Dispatch（分发）**：All-to-All 通信，把 token 发送到持有目标专家的 GPU；<br> ③ **专家计算**：GPU 使用本地专家处理收到的 token，常用 Grouped-GEMM 提升利用率；<br> ④ **Combine（合并）**：再次 All-to-All，将计算结果传回原始 token 所在 GPU，恢复序列顺序。<br>
- 训练额外逻辑<br> 反向传播对称执行 All-to-All；同时引入负载均衡辅助 loss，缓解专家冷热不均。

**通信约束**

- 核心通信原语：**All-to-All**，通信量和 token 数量正相关，和专家总数无关；
- All-to-All 属于密集双向通信，带宽压力大，对网络延迟敏感；
- 天然风险：路由不均衡会造成 GPU 负载倾斜，部分卡空闲；
- 支持单机 NVLink 或跨节点 RDMA；跨节点带宽不足时性能暴跌；
- 优化手段：通信与计算重叠、token 重排融合、无丢弃路由 (dMoE)。

**适用场景**

- moe模型训练与推理；
- 推理场景常用DP+EP架构：attention走DP，MoE走EP，减少kv cache冗余，模型副本没有dp的情况下，dp（dense）=ep数。

## **三、长上下文策略**

### **1. SP**

**问题**

- TP 张量并行会分摊权重显存，但激活张量依旧持有完整序列；
- 长序列场景下，LN、MLP 激活显存占用高；
- 需要在 TP 组内，对无序列依赖算子的激活做序列维度分片，降低激活显存。
- SP**无法解决 Attention 阶段 KV 显存问题**。
- 超长序列场景下，激活和kv cache随着序列长度的增加呈现二次方增长；
- TP、DP都只能分担权重，无法有效降低单卡的序列维度显存压力，所以容易触发OOM；

**核心思想**

- 依托 TP 进程组，沿 seq_len 维度切分激活张量；
- 仅在 LayerNorm、Dropout、MLP 这类 token 独立计算的算子维持分片；
- 进入 Attention 前通过 AllGather 恢复完整序列；
- 本质是 TP 配套激活优化方案，不改造自注意力计算逻辑。

**具体实现**

- 输入序列沿 seq 维度切分，每张 GPU 持有局部序列分片；
- LN、MLP 使用分片激活计算；
- **进入 Attention QKV 计算前执行 AllGather，拼接完整序列**；
- 执行标准单机 Attention，每张 GPU 持有完整 QKV；
- Attention 输出后，ReduceScatter 重新切回分片，送入下一层。

**通信约束**

- 通信原语：AllGather / ReduceScatter（集合通信）；
- 强制依赖 TP 进程组，**无法脱离 TP 单独运行**；
- 序列长度最好能被 SP 并行度整除（解决方法padding补齐、非均匀切分）；
- Attention 内部不做分片，长序列场景 KV 依旧是显存瓶颈。

**使用场景**

- 中等长度上下文训练；
- 模型已经开启 TP，想要降低 FFN、LN 激活显存；
- 不适合超大超长序列（64k+），无法缓解 KV 显存压力。

### **2. CP**

**问题**

- 超长序列场景，单纯 Megatron SP 只能优化 FFN 激活；
- Attention 阶段必须恢复完整序列，单卡仍要存放全部 KV，极易 OOM；
- 需要一套方案，让 Attention 计算全程维持序列分片，分布式计算注意力。

**核心思想**

- 沿 seq_len 切分整条序列，**全 Transformer 块维持分片状态**；
- 引入分布式注意力算法（RingAttention/Ulysses），不需要一次性聚合完整 KV；
- 每张 GPU 只保存本地 token 对应的 KV 分片，大幅降低 Attention 峰值显存。
- 全程不执行全局 AllGather 拼接完整序列；反向传播对称执行。

**通信约束**

- 通信原语：点对点 Send/Recv 环形通信；
- 通信轮次更多，但峰值显存远优于 SP；
- 可以独立运行，也可以叠加 TP；无强制绑定关系；
- 跨节点部署延迟上涨明显，优先单机 NVLink；
- 可配合 Zigzag 锯齿切分缓解因果 LM 负载不均。

**适用场景**

- 超长上下文训练、百万 token 长 prefill 推理；
- KV 显存成为首要瓶颈，SP 不足以满足显存需求；
- 推理侧分布式 KV 缓存底层大量复用 CP 思想；
- sp对于线性层可以all reduce转成reduce scatter，attention依旧all gather；cp全程分片，线性层复用sp的思想。

### **3. PCP&DCP**

针对LLM推理的prefill和decode场景设计的。

**问题**

超长上下文推理存在双重瓶颈：

- Prefill 阶段：复杂度 O (N²)，长 prompt TTFT 极高，单卡算力不足；
- Decode 阶段：传统 TP 架构，每张卡完整复制全部 KV Cache，显存严重冗余；
- 原生一维 CP 无法同时兼顾「加速 Prefill」+「节省 Decode 显存」，因此拆分为 PCP+DCP 二维并行。

**核心思想**

把 CP 并行维度拆成两组独立并行域：

- **PCP 维度**：面向 Prefill，沿序列切分 prompt，多卡多副本并行计算 prefill，降低 TTFT；独立通信域；**解决的是加快计算。**
- **DCP 维度**：面向 Decode，复用 TP 通信域，沿序列分片 KV Cache，消除 TP 组内 KV 冗余；**解决的是显存问题。**

整体架构：WorldSize = TP × PCP

Prefill：TP + PCP；

Decode：TP + DCP；

prefill 产出的分片 KV 平滑移交到 DCP 维度供解码使用。

**具体实现**

（1）PCP（Prefill Context Parallel）

- 长输入 prompt 沿 seq 切分为多段，分配到 PCP 组内不同 GPU 并行执行 prefill；
- KV Cache**生成分片存储**，不需要在 prefill 阶段全局拼接完整序列；
- 可选实现：AllGatherKV / RingAttention；
- PCP 拥有独立通信域，**会额外占用 GPU，不能复用 TP 的硬件资源**。

（2）DCP（Decode Context Parallel）

- **不新增 GPU，直接复用 TP 进程组硬件**；
- 传统 TP 缺陷：所有 TP rank 保存完整 KV；DCP 沿 seq 维度交错分片 KV Cache；
- Decode 时，每张 GPU 只持有一部分历史 KV；计算注意力时 AllGather 远端 KV 分片；
- 新生成 token 的 KV 按轮询方式写入各个 DCP rank，持续维持分片状态；
- 核心收益：**TP 组内 KV 显存直接降低 DCP 倍**。

（3）Prefill → Decode 切换逻辑

PCP 并行完成 prefill，输出分片 KV；将分片 KV 重排布，映射到 DCP 分片布局，无缝进入解码阶段。

或者采用pd分离部署，无需切换。

**通信约束**

- PCP：独立通信域，通信量巨大，建议单机 NVLink，跨节点性能暴跌；
- DCP：复用 TP 通信组，Decode 每步需要序列维度 AllGather KV；序列越长，单次通信张量越大；
- 硬件约束：PCP 会扩张总 GPU 数量；DCP 不增加卡数，属于现有 TP 资源内部优化；
- 短板：短请求场景，通信开销收益不明显，不建议开启。

**适用场景**

- 超长上下文推理（64K/128K+），同时存在长 prompt Prefill + 长对话 Decode；
- 诉求既要压低 TTFT，又要缓解 KV Cache 显存压力；
- vLLM、昇腾 vLLM 主流长上下文推理方案；
- 单机多卡、具备 NVLink 环境最佳。

## **四、生产落地策略**

### **1. PD分离**

**问题**

传统推理引擎（vLLM 默认共置），Prefill、Decode 混跑在同一组 GPU：

- Prefill 计算密集（O (N²)），会抢占算力，阻塞正在运行的 Decode 流，造成 ITL（token 间延迟）毛刺；
- Decode 访存密集，大量占用 HBM 带宽，拖慢新请求 Prefill，抬高 TTFT；
- 两个阶段最优并行策略、硬件选型不一样，混部署无法单独调优；
- 无法独立扩缩容 Prefill 集群、Decode 集群，流量波动场景资源浪费严重。

**核心思想**

把一条请求的两个生命周期阶段**物理拆分到两套独立 GPU 集群**：

- Prefill 集群：只负责处理完整 prompt，生成初始 KV Cache；
- Decode 集群：接收 KV Cache，持续自回归生成 token；
- 两者之间通过高速 RDMA/NCCL 传输 KV Cache；
- 两大集群可以**独立选型、独立设置并行策略、独立弹性扩缩**，消除阶段资源抢占干扰。

**具体实现**

- 集群划分
- 请求完整流程
- 工程细节

**通信约束**

- 核心开销：Prefill→Decode 的**KV Cache 跨实例传输**；prompt 越长，传输张量越大；
- 对网络要求极高，单机优先 NVLink，多机部署必须 RDMA（EFA/InfiniBand）；普通以太网极易出现传输瓶颈；
- 引入额外一跳延迟，短 prompt 场景，传输开销可能抵消收益；
- 两套集群各自保存完整模型权重，**权重显存存在双倍冗余**；
- 不存在跨集群共享 KV；一条请求的 KV 一旦传输完成，生命周期内固定在对应 Decode 实例。<br>

**适用场景**

- 混合负载：大量长输入 prompt + 长输出对话，prefill 和 decode 流量波峰错峰；
- 对尾部 ITL 稳定性要求极高，不能容忍 token 输出卡顿；
- 流量具备明显潮汐特征，可以分别扩容 Prefill/Decode 集群；
- 超长上下文业务，希望 prefill 启用 PCP 加速、decode 启用 DCP 优化显存；
- 具备高速 RDMA 集群硬件条件。

### **2. chunk prefill**

**问题**

传统连续批处理调度存在严重**Prefill-Decode 相互干扰**：

- Prefill 是计算密集（Compute-bound，O (N²) 注意力）；Decode 访存密集（Memory-bound）；两者资源特征完全相反；
- 长 Prompt 一次性完整 Prefill 会长期独占 GPU，大量正在生成的 Decode 请求被阻塞，引发 TPOT/ITL 剧烈抖动；
- 单纯优先 Decode 会抬高新请求 TTFT；优先 Prefill 会恶化对话流畅度，两者难以兼顾；
- 一次性超大 Prefill 还会带来瞬时显存峰值，容易触发 OOM。

**核心思想**

- 不再一次性完整计算整条 Prompt，将长输入切分为固定长度小块（Chunk）；
- 每一轮迭代，**混合执行若干 Prefill Chunk + 批量 Decode 请求**，交替推进长 Prompt 计算与 token 生成；
- 在**同一组 GPU 实例内部完成调度**，不拆分硬件，以调度手段平滑两种负载冲突。

**具体实现**

- Prompt 分片：长输入按预设 chunk_size 切分成多段；每一轮只处理其中一段，逐段生成、累积 KV Cache。
- 混合 Batch 构建调度器设置全局 token 预算，每个 forward batch 同时容纳：多个活跃 Decode 请求（各 1token）+若干 Prefill 分片 chunk；
- 请求推进流程：
- KV Cache 机制：每一块 chunk 计算完成后增量写入 KV Cache；全部分片处理完毕，拥有完整 KV，开始生成 token；依托 PagedAttention 块管理，支持增量追加 KV。
- 算子特点次执行 Attention，相比一次性 Prefill，增加 kernel 启动开销；chunk 大小是核心调参。

**通信约束**

- **无额外跨卡通信**，纯调度层优化；TP 组内部原有通信逻辑不变；
- 只影响单实例内部批构建，不引入 RDMA、跨实例数据传输；
- 若开启 TP/DCP/PCP，Chunked Prefill 可以和它们叠加，互不冲突；
- 分片粒度越小，kernel 调用次数越多，Prefill 总耗时会轻微上升。

**适用场景**

- 混合负载：长 Prompt RAG / 文档总结 + 持续对话生成并存；
- 对对话流畅度（稳定 ITL）有要求，不想出现输出卡顿；
- 硬件资源有限，不希望部署 PD 分离、维护两套模型副本；
- vLLM、SGLang 默认开启，是线上标准基础优化；
- 劣势场景：全部都是短 prompt 场景，收益极低。

### **3.多副本**

在实际的大模型推理生产落地中，**“外置网关/路由 + 独立多副本（Multi-Replica）”** 是绝大多数团队的首选，而很少在单个推理引擎进程内部拉起一个庞大的多卡 DP（Data Parallelism）。

这背后的根本原因在于：**训练追求的是“全局状态强同步”，而推理追求的是“高可用、高隔离与弹性调度”。**

主要有以下 5 个核心考量：

**（1）致命的故障隔离问题 (Fault Isolation)**

这是生产环境不选原生单引擎 DP 的最核心原因。

- **多副本模式**：副本 A、副本 B、副本 C 完全独立。如果副本 A 因为遇到畸形 Prompt、超长输入或者 CUDA 偶发 Error 导致显存溢出（OOM）崩溃，外置网关（如 Envoy、Nginx 或 SGLang Router）通过健康检查会**瞬间切断副本 A 的流量**，将后续请求无缝转发给副本 B 和 C，整个系统服务不中断。
- **单引擎原生 DP**：DP 组内的多张卡在底层绑在同一个 Python 进程/NCCL 通信组中。一旦其中一个 DP Worker 发生显存爆炸或 C++ 基层报错，**整个推理引擎进程通常会直接 Crash 崩溃**，导致当时正在处理的所有用户的请求全部断开。

**（2）KV Cache 管理与智能前缀路由 (Prefix-Aware Routing)**

LLM 推理的性能命门在于 **KV Cache**。

- **多副本模式**：可以在外置网关层做“聪明”的路由（如 Cache-Aware Routing）。网关在拿到请求后，先检查 Prompt，把使用了相同 System Prompt 或长上下文（如同一个 PDF 稳档）的请求，**精准分发给已经缓存了该 KV Cache 的特定副本**，直接实现 80%+ 的 Prefill 命中率。
- **单引擎原生 DP**：引擎内部的 DP 调度机制通常比较简单（如按卡空闲状态轮询或随机分发），很难在跨 DP 节点之间做到高效率的前缀缓存（Prefix Cache）复用。

**（3）云原生弹性扩缩容 (K8s & HPA)**

- **多副本模式**：天然契合 K8s 的容器化运维。白天业务高峰期 QPS 激增，K8s 的 HPA（Pod 自动扩缩容）可以直接把推理 Pod 的副本数从 5 个拉高到 20 个；晚上业务低谷期再自动缩回。每个副本拉起和销毁都是独立的。
- **单引擎原生 DP**：分布式通信（如 NCCL init_process_group）要求卡数和 Rank 在初始化时就固定好。如果要在引擎内部从 DP=4 动态扩容到 DP=8，往往需要**停掉整个引擎重新建立通信组**，这在在线服务中是无法接受的。

**（4）零停机滚动更新 (Rolling Update)**

- **多副本模式**：当需要发布新版本的模型权重、更新 vLLM/SGLang 镜像或部署代码 Patch 时，可以采用 K8s 的**滚动更新（Rolling Update）**——先切断 Pod 1 的流量，更新 Pod 1，成功后再更新 Pod 2，整个过程对终端用户完全透明，实现 0 Down Time（零停机维护）。
- **单引擎原生 DP**：如果要更新，必须把整个全局 DP 进程杀掉重拉。

**（5）避免多卡进程间的不必要同步开销**

在训练中，DP 需要在反向传播后调用 AllReduce 强行把所有卡的梯度拉平（必须等待最慢的那张卡）。 而在推理中，各个请求的生成长度完全不同（请求 A 吐 10 个字就结束了，请求 B 要吐 2000 个字）。如果强行用原生 DP 在引擎内部统筹，进程间复杂的同步锁和状态维护反而会带来额外的软件栈开销。

**什么时候才会用到引擎内部的 DP？**

虽然绝大多数集群都采用多副本，但在以下两种特殊场景下，引擎内部的 DP 依然有用武之地：

- **单节点内部多卡充分利用**：比如单台机器有 8 张卡，如果跑 TP=2，那么单机可以跑 4 组 TP=2。此时可以在单机引擎内部配置 TP=2 + DP=4，让这个引擎进程内部自己管理这 8 张卡，简化单机内的部署。
- **MoE 模型的特殊架构 (EP + DP 结合)**：在 DeepSeek-V3 等 MoE 模型推理中，Attention 模块可能使用 DP，而 MLP 专家模块使用 EP（专家并行），这种细粒度的算子级 DP 是必须由推理引擎内部框架深层次支持。
