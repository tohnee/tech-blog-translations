在上一篇中的「KV Cache引入的显存管理问题」一节提到，KV Cache的管理是一个复杂的问题。我们需要解决诸如：连续分配导致的显存碎片与浪费问题、批量处理效率低下、无法跨请求资源共享等问题。

实际上，上述大部分问题的<u>本质是传统 "静态连续内存分配" 范式与大模型推理 "动态变长请求" 特性之间的根本不匹配</u>。而PagedAttention、Continuous Batching、Prefix Caching则是来解决这些问题的，它们可以称得上是推理系统软件架构的基石。

## 1. PagedAttention - vLLM

PagedAttention由加州大学伯克利分校著名的 Sky Computing Lab 提出并实现，包含在vLLM框架中，该实验室也是Spark和Ray的诞生地。PagedAttention主要是解决KV Cache的显存管理问题，其解决思路和操作系统的内存管理非常相似。

PagedAttention之所以叫xxxAttention，是因为它修改了 Attention 计算的访存逻辑，后续要介绍的RadixAttention也是类似的。

### 1.1 原始做法

类似于操作系统没有内存管理的早期阶段，在KV Cache的早期阶段，推理阶段使用「最长连续内存申请」，比如基于最大可能序列长度（如2048），或者改进为使用prompt长度和最长可生成token数的和。这种原始方式的问题和操作系统早期内存管理如出一辙：

1. 内部内存碎片，即一次性申请的显存用不完导致浪费；
2. 外部内存碎片，随着不断申请和释放，导致最终即使有空闲且空间足够的显存，但不连续导致申请失败。（类似于在停车场不同长度的车停放问题，会导致可用空间不连续）；

### 1.2 虚拟内存与分页机制

回顾一下，操作系统在处理物理内存时，采用了虚拟内存与分页（Paging）策略：

- **虚拟内存**：虚拟地址连续，但映射到物理内存的任意位置，即物理内存地址不连续；
- **分页**：按固定大小（通常4KB）分页，按需分配；通过页表维护映射关系，灵活高效；

![](https://picx.zhimg.com/v2-ae3b48321ea546c5bc138de4a4275be7_r.jpg)

如上图所示，PagedAttention引入分页Page机制，将显存切分为固定大小的块Block，每个Block存放固定个数的tokens的KV Cache，其在物理内存中不连续。每个块的大小=*`Tokens per block (16)`* *×* *`Num Layers`* *×* *`Num KV Heads`* *×* *`Head Dim`* *×* *`2 bytes (for FP16)`* *×* *`2 (for both K and V)`。*上述参数对于一个固定模型，每个block的大小是可以计算出来的，所以每个Block的大小也是固定的。

假如输入序列的长度是100，每个block会包含16个token，那么在prefill初始阶段会申请ceiling(100/16)=7个block，在decode阶段，每生成一段token后发现block已经不够了，就会继续申请。

PagedAttention的其余特性如虚拟内存、按需申请等都和传统操作系统的内存管理机制没有很大的差别，此处不多做介绍。

### 1.3 运行模式与状态管理

- CPU作为大脑进行管理和调度，相当于分布式系统中的Master或者Control Plane模块，主要有两大组件
- GPU作为肌肉执行，类似于分布式系统中的Executor模块，提供具体的资源和执行"Master"的调度指令。

![](https://pic3.zhimg.com/v2-5ec7768f7986fb14476c28f60f5e1356_r.jpg)

整个PagedAttention都是有状态的，比如保存block的生命周期状态、保存显存block物理映射。当发生崩溃时，正在进行中的推理会直接失败，还在队列中等待的推理请求会被路由到其他controller。

### 1.4 Block-Level显存共享与Beam Search

PagedAttention是通过Block来管理显存，其Blocked KV Cache也可以进行共享复用。

存储块共享机制实际上在很多地方都有应用，比如操作系统的物理内存共享，让多个进程都指向同一个物理内存帧（memory frame）；再比如文件系统和数据湖中的<u>**写时复制（Copy-On-Write，COW**</u>）思想。其<u>本质是通过只读复用底层存储块，仅在写入时才创建副本，从而消除冗余拷贝、显著降低存储和内存开销</u>。

在大语言模型推理过程中，块级显存共享有多个典型应用场景，最具代表性的就是 Beam Search（束搜索）解码中的前缀 KV Cache 共享。Beam Search 适用于对生成质量有较高要求的各类序列生成任务（如机器翻译、代码生成、文本摘要）。

如下图所示，Beam Search 会设定超参数 K（束宽），用来规定每一步修剪后保留的候选分支数。

下述例子中取 3，模型用于生成前缀 "The" 之后的两个 token。

1. 第一步，模型基于前缀 "The" 生成第一个位置的 3 个候选 token，这 3 个候选分支会完全共享前缀 "The" 对应的 KV Cache 块。
2. 下一步中，模型会对每个保留的 beam 分支分别生成词表大小的候选 token，然后计算所有候选分支的累计得分（前缀历史得分 + 当前 token 得分），最终选取得分最高的 3 个分支进入下一轮。

这种生成模式本质上是一个宽度受限的树状搜索结构，所有分支在分叉点之前的所有公共前缀 token，都可以共享对应的 KV Cache 存储块。

## 2. Continuous Batching连续批处理

### 2.1 科普：推理过程的Prefill和Decode

在模型推理过程中通常分为两个阶段，如下图所示

- Prefill：将用户输入的完整 token 序列一次性输入模型，计算因果注意力下每个位置的注意力分数，生成第一个输出 token，并保存所有位置的 KV Cache。该阶段计算量随输入长度平方增长，属于计算密集型，计算模式与训练过程相似。
- Decode：每次仅输入上一步生成的 1 个新 token，计算其对应的 K、V 向量并追加到历史 KV Cache 末尾，然后利用完整的 KV Cache 计算注意力，生成下一个 token。该阶段每次计算量极小，但需要频繁访问大量 KV Cache 数据，属于内存密集型。

![](https://pic4.zhimg.com/v2-64e48422ee6189348fff21e41ce60b8b_r.jpg)

### 2.2 连续批处理的做法

为了提高GPU的利用率，推理阶段都是攒批进行的。早期推理采用静态批处理（Static Batching），调度逻辑是：推理引擎以完整批次为调度单位，必须等批次内全部请求完成生成后，才统一返回结果、释放所有请求的 KV Cache 显存。

这显然会有“木桶效应”，即最慢的会拖累整个batch的执行，并且最早执行完成的请求对应的KV Cache仍旧会占据显存，造成显存浪费。

Continuous Batching的解决方案实际上很直观，采用更细粒度的调度，将调度粒度从batch粒度改为迭代粒度（iteration level）或者叫token level，它能够保证推理batch size始终是满的。具体来说：

1. Token-by-Token检查：调度器会在每个推理迭代结束后进行检查。
2. 即时驱逐：若检测到某条请求完成序列生成，立刻将该请求从当前批次移除，同步释放其占用的 KV Cache 显存；
3. 即时填充：调度器从等待队列取出新请求，执行 Prefill 计算，并将新请求放入刚空出的计算槽位 Slot；
4. 阶段混跑（In-flight Mixing）：在原始实现中，Prefill 计算与 Decode 计算是串行交替进行的。现代推理框架通过 Chunked Prefill 等技术实现了两者的交错执行，最大限度地减少了 GPU 闲置时间。

<u>Continuous Batching 的思想类似于操作系统中的 IO 多路复用机制（比如 epoll）。类比早期阻塞式 IO 中一个线程只能服务一个请求，未完成的 IO 仍然占用线程资源（造成内存开销和上下文切换开销），而 IO 多路复用允许一个线程同时管理多个请求，只处理那些已经就绪的请求。再类比于丰田精益制造、HTTP2 多路复用（一个连接同时处理多个请求）。它们的核心本质是：打破 "批量同步等待" 的枷锁，在最细粒度的单元上实现资源的动态调度和复用。</u>

### 2.3 Prefill和Decode冲突导致的延迟尖刺

在早期的 Continuous Batching 实现中，Prefill 和 Decode 只能严格串行交替执行，无法并行。具体来说，接收到一批请求后，调度器会把 Prefill 和 Decode 拆分，将所有 Prefill 请求打包成一个大批次执行，执行完成后再批量执行 Decode。

由于 Prefill 的执行时间通常比单个 Decode 长 10-100 倍（一个 1024 token 的 Prefill 大约需要 15ms，而单个 Decode 仅需 1ms），这会导致所有正在进行的 Decode 请求被长时间阻塞，用户会感觉到明显的卡顿。虽然后续也有一些小的优化，但本质上差别不大。

对于这种问题，当前有两种解法：Chunked Prefill、Prefill-Decode 分离式部署。

1. **Chunked Prefill**

Chunked Prefill是将一个长的prompt切分为多个chunk，比如按照256 token size来切分。切分后的chunk的prefill会随着decode阶段同时执行，以避免decode请求的延迟尖刺，但会引起prefill的TTFT(Time to First Token)延迟。由此可避免单条超长 Prompt 独占 GPU 算力，防止其他并发请求出现突发性推理延迟。

Chunked Prefill有点类似于分时调度，为了避免其他进程饥饿，将进程的执行切分为时间片，类比于Chunked Prefill将Prefill序列切分为多个，避免Decode请求饥饿。

**2. Prefill-Decode分离式部署**

指的是部署独立的Prefill集群专门进行Prefill计算，在Prefill计算完成后，将Prefill生成的KV Cache传输至Decode集群，所以会引入KV Cache的传输成本。通常两个集群的GPU卡类型也不一样。

虽然Chunked Prefill在某种程度上解决了decode的卡顿问题，但prefill和decode的不可预测性导致在生产环境的利用率很难调优，会出现很多不可预测的波动，所以在要求更为严格的生产环境中，分离式部署更为常见。当前业界超大规模集群和有严格 SLO 要求的场景大多数采用Prefill-Decode分离式部署。

### 2.4 科普：传统推理过程中的Kernel Launch通信开销

![](https://pica.zhimg.com/v2-f8f4e7082835a8ce054e1cf7557d4a1c_r.jpg)

GPU Kernel（内核函数） 是运行在 GPU 上的一段并行计算函数。其由 CPU 发起调用，然后在 GPU 的大量核心上同时被成千上万个线程各自执行一次。如上图所示，蓝色块表示 CPU 发起调用和接收返回，绿色块表示 GPU 的 Kernel 执行。

在LLM推理中，GPU中没有一个叫做“generate_next_token()”的方法，它只能执行细粒度的计算kernel，而一个模型由多层组成，每层又包含不同的矩阵乘法、LayerNorm、激活函数等多个独立操作，每个操作在未优化时都会对应一个单独的kernel launch。那么<u>**在传统推理过程中，一个token的推理需要启动上百个kernel。**</u>

### 2.5 连续批处理下的CPU调度开销问题

1. **Kernel Launch开销与CUDA Graph**

现代GPU速度超乎寻常的快，但GPU的计算执行（一次Kernel launch）需要CPU下达指令，这会耗费数微秒，即Kernel Launch开销，约占总推理时间的 5%-20%。

Kernel Launch 的开销不仅包括 CPU 通过 PCIe 向 GPU 发送命令的通信成本，还有 CPU 端的驱动调度开销和 GPU 端的资源分配开销，每个 kernel launch 的总延迟可达 1-10 微秒。

为了减少数百个Kernel launch的开销，通常采用一种CUDA Graph的技术，即将一系列Kernel launch录制为一个图，然后一次性重放，虽然kernel的总数不变，但消除了CPU端重复的kernel launch调度开销。

需要注意CUDA Graph和Kernel Fusion的区别。Kernel Fusion 的核心思想是将多个数据依赖的连续操作合并成一个大 kernel，这不仅大幅减少了 kernel launch 的数量，更重要的是消除了中间结果的全局内存读写，极大地节省了内存带宽，这是它的最大价值。CUDA Graph 只是将一系列 kernel launch 录制下来一次性重放，不会改变 kernel 的数量和执行逻辑，只能消除 CPU 端的重复调度开销。<br>

![](https://pic2.zhimg.com/v2-cec70bdd370e9d96f9d90ca762a65ba5_r.jpg)

<br>CUDA Graph 要求静态 batch size，因此需要提前录制多个不同 batch size 的 bucket（如 16、32、64）。比如当实际 batch size 为 28 时，使用 32 batch size 的 bucket，剩余位置使用零填充占位符，浪费少量内存。

CUDA Graph 几乎只用于 decoding 阶段，因为 decoding 阶段的计算模式高度统一，都是根据 KV Cache 推理下一个 token。而 Prefill 阶段的 prompt 长度千差万别，很难为每个可能的长度录制 CUDA Graph。

**2. Batch请求的检查和更新**

由于Continuous Batching中在每一个token生成后（10ms左右），CPU要频繁检查、更新内存指针、动态调整批次，这使得CPU本身的执行成为瓶颈。解决方案主要有两个：

1. 异步Pipelining：让 GPU 计算和 CPU 调度并行执行。当 GPU 正在计算第 N 个 token 时，CPU 同时准备好第 N+1 个 token 的所有 kernel 命令并推入 GPU 命令队列，从而完全隐藏 CPU 调度的延迟。
2. 多步调度：每执行 N 步（通常为 4 - 16 步）才进行一次全局调度，将调度开销分摊到多个 token 上，大幅降低 CPU 负载。该技术主要用于高吞吐量场景，会轻微增加请求延迟。

### 2.6 与 PagedAttention 的协同机制

连续批处理的落地难点在于动态申请、释放 KV Cache 显存：传统连续式 KV 缓存布局下，频繁创建销毁请求会产生严重显存碎片。PagedAttention 的分页内存架构恰好补齐了这一短板：它把 KV Cache 拆分为独立、可复用的显存物理块，支持任意请求按需引用、释放分页块。

## 3. Prefix Caching & Radix Attention

Prefix Caching和Radix Attention实际上比较类似，只是SGLang最先提出Radix Attention，然后vLLM又按照自己的想法实现了一遍，称为Prefix Caching。

它们的动机非常自然，线上Serving环境下有大量请求共享相同的system prompt（比如“你是一个代码编写助手”），重复prefill纯属浪费算力和KV Cache显存。

对于这种重复计算，缓存共用的前缀KV Cache是一个非常直观的解法，做好之后不仅可以降低显存占用，还可以降低TTFT (Time To First Token)。但有几个核心问题需要解决：

1. <u>采用什么样的数据结构来存储和查找公共前缀KV Cache；</u>
2. <u>显存满了之后如何淘汰；</u>
3. <u>不同的GPU保存了不同的前缀KV Cache，如何进行路由；</u>

### 3.1 Radix Attention

Trie的数据结构被广泛用于公共前缀的场景，比如搜索系统的query自动补全、拼写检查与纠正、IP路由匹配等等。

SGLang也使用了一棵类似Trie的基数树（Radix Tree）跟踪所有请求token序列的前缀关系，其保存在CPU内存中，如下图所示。

![](https://pic3.zhimg.com/v2-da0dcf6a0d42d5658ea3efe686a8161a_r.jpg)

<br>Radix Attention所使用的Radix Tree和Trie在结构上的区别在于：

1. Radix Tree是一个带有“压缩”功能的Trie。如果一个node只有一个子节点，Radix Tree会把这个node和其子节点merge起来。
2. 在Radix Tree中，一个node不仅仅保存了token，还保存了指向Memory Block的指针、用于淘汰的引用计数和时间戳。

在淘汰方面，RadixAttention基于Node中的引用计数和时间戳采用LRU进行淘汰。如果Radix树过大，遍历驱逐和匹配查询会耗费很长的时间，要避免此时CPU成为瓶颈。

### 3.2 Prefix Caching

vLLM的Prefix Caching设计上受 SGLang 的 RadixAttention 启发，但走了不同的工程路线，其数据结构采用Hash Table而不是Trie树，并且很好地和其PagedAttention做了集成。其设计思路比较清奇，值得探讨一番。

假如PagedAttention的block token数量是2，并假设用户的Prompt是：*“Write a Python function that fetches data from a database”*。如下图所示：<br>

![](https://picx.zhimg.com/v2-c27a2b5f1d0745846c2df69dd4710f4f_r.jpg)

1. Block Level共享：和Radix Attention不同的是，Prefix Caching不是token级别的共享，而是Block级别的共享，假如另外一个Prompt是"Write a Python code xxx"，那么就只能共享第一个Block的KV Cache，无法共享"Python"对应的KV Cache。
2. 连环Hash：每个block的hash是（parent_hash, tokens in block），以此来实现“树状”的前缀匹配。这种链式 Hash（父块 hash + 当前块 token）本质也是构建树形前缀关系。
3. Map+双向链表的LRU策略：采用经典的Map+双向链表的LRU淘汰策略，实现O(1)复杂度的淘汰。

这种结构使得vLLM在匹配时是逐块匹配的，即找到第N块后，用第N块的hash_value和第N+1块的tokens做整体hash。工程实现上更简洁，与既有架构融合更顺，但代价是**末尾不完整块的命中率低于radix tree的精确前缀匹配。**

### 3.3 和PagedAttention Block Level 共享的区别

Prefix KV Cache共享和PageAttention Block KV Cache共享的动机都是一样的，都是为了提高 KV Cache 的利用率，避免重复存储和浪费。两者不是并列关系，而是底层内存机制 + 上层缓存调度的层级关系。这里提一下两者的一些细微差别：

- 从范围来看：Prefix Caching是做请求粒度的KV Cache共享，而PagedAttention则属于底层的内存管理机制，独立来看更多的是做请求内部的Block Level的共享；
- 从生命周期来看：Prefix Caching的KV Cache的生命周期不和请求绑定，当GPU显存不够用时，才会进行驱逐，而PagedAttention的则是绑定请求的生命周期。

## 4. 为什么这些方法现在看起来是那么理所当然

本文介绍的这些优化，不像前面的内容和大模型的结构强相关（比如张量并行、FlashAttention），它们更多的是从系统层面进行优化。现在回头再看这些优化，似乎都是理所当然的优化，它们都不是全新的发明，没有新数学，没有新架构，但为什么是别人先做出来、先考虑到呢？

比如PagedAttention就是把OS 101的概念认认真真搬到了GPU上，Continuous Batching类似于操作系统的时间片轮转调度，Prefix Caching的思想更是在各种缓存系统上都能看到。

<u>这恰恰是这个故事最好看的部分。真正的洞察力往往不是发明新东西，而是将原有的经验迁移到新的领域，创造出全新的系统。这才是技术工程师所要磨练的能力。随着工作时间的积累，那些犄角旮旯的编程语言细节、或者某个特定领域的技巧都不是那么重要了，而能够从以往的知识和经验里抽象出high level的精华，在遇到新环境、解决新问题时，能够将这些精华进行成功迁移，才是更重要的。</u>
