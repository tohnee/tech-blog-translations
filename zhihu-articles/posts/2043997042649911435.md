## **引言**

这篇文章来自 HAMi 社区贡献者 Mesut Oezdil 的一次真实工程实验。他把 HAMi 已经暴露出来的 GPU 指标，通过一个 Go 编写的 MCP Server 转换成 AI Agent 可以调用的工具，让一个本地 3B 小模型能够直接理解 GPU 集群当前状态。

这类实践很有启发性：HAMi 不只是 GPU 虚拟化和调度组件，它也可以成为 AI Agent 理解 Kubernetes GPU 资源状态的数据入口。随着 MCP、Agent Tool、GPU Observability 与 Kubernetes 控制面的结合，AI Infra 正在从“人读指标、人写查询”走向“Agent 读取基础设施状态并给出解释”。

下面是原文翻译，保留作者的实验过程、命令输出、踩坑记录和复现方式。

一个 K8s 节点，一张 [NVIDIA L40S](https://www.nvidia.com/en-us/data-center/l40s/)。中间是 [HAMi](https://project-hami.io/)。另一端是一个 30 亿参数模型。我想问一个本地 LLM：“我的 [GPU](https://github.com/mesutoezdil/Systematic-CUDA-Learning) 现在发生了什么？”然后得到一个合理的回答。不需要 PromQL，也不需要 SSH。

缺少的部分是一个翻译器。HAMi 已经通过 [Prometheus](https://prometheus.io/) 在 31993 端口发布了我需要的一切。LLM 不会说 Prometheus 的语言。所以我用 [Go](https://go.dev/) 写了一个小 server，放在中间，并让它使用 [Model Context Protocol](https://modelcontextprotocol.io/docs/getting-started/intro)。完整源码以及构建和运行说明都在我的 [repo](http://github.com/mesutoezdil/hami-mcp) 里。

这篇文章会介绍我构建了什么、过程中遇到了哪些问题，以及如何在你自己的集群上复现。

## **我为什么要折腾这个**

主要是出于好奇，再加上一个老习惯。我总是会发现一些彼此还不认识的项目组合，然后想看看它们相遇后会发生什么。[HAMi](http://github.com/Project-HAMi/HAMi) 已经运行在我使用的集群里。[MCP](http://modelcontextprotocol.io/) 最近这个月则出现在我浏览器的每一个标签页里。把一个适配到另一个，比再读一篇关于二者之一的教程更适合打发一个下午。

这项工作大多是试错。一路上遇到的 bug，并不是我付出的代价，它们本身就是我把这些东西写下来的半个原因。

```text
在进入细节之前，我还在 Nebius GPU 实例上复现了同样的设置，用来验证它在云环境中的表现。目标是比较我的本地 NVIDIA L40S 环境与按需 GPU 实例，并验证 provisioning、NVIDIA runtime 配置和 GPU observability 是否能在不做额外调整的情况下保持一致。实例在几分钟内就准备好了，驱动和 runtime 支持也开箱即用，因此我可以按照完全相同的步骤执行，并确认不同环境中的行为是一致的。
```

## **我们要构建什么，用一张图说明**

这篇文章里有两个 client 会接触 HAMi。一个是 Go 程序，它从命令行端到端运行整个链路。另一个是 MCP Inspector，这是一个官方的、基于浏览器的 MCP server 调试器。它们中间共享同一个 `hami-mcp-server` 二进制文件，并读取 HAMi 已经暴露出来的同一个 `:31993/metrics` endpoint。整体形态如下。

![](https://pica.zhimg.com/v2-fbb702191289c863b8c526525294f5e2_r.jpg)

中间的 Go binary 在两条路径里是同一个。变化的只是由谁来启动它。在命令行路径里，启动它的是我们自己的测试 client。在浏览器路径里，启动它的是 MCP Inspector。它所使用的协议（*stdio JSON-RPC*）在两种情况下都不会变化。

为什么需要两条路径？命令行路径证明了：LLM 可以在没有人工手动接线的情况下读取 HAMi。浏览器路径证明了：这个 server 是一个通用 MCP server，对我们没有编写的工具也有用。

## **机器上有什么**

我先检查了 GPU 和 HAMi pods。第一个命令会向 NVIDIA driver 查询每张 GPU 的空闲显存和总显存。

```text
$ nvidia-smi --query-gpu=name,memory.free,memory.total --format=csv
name, memory.free [MiB], memory.total [MiB]
NVIDIA L40S, 45458 MiB, 46068 MiB
```

一张 L40S，46 GiB 总显存，45 GiB 空闲。没有任何东西在使用这张卡。

第二个命令列出 system namespace 中的 k8s pods，并过滤出 HAMi 运行的 pod。

```text
$ kgp -n kube-system | grep hami
​
hami-device-plugin-5n2mv           2/2     Running   0   15m
hami-scheduler-7bbbfc4f7f-d6n29    2/2     Running   2   40h
```

两个 pod 都已经启动。device plugin 就是即将被我们抓取 metrics endpoint 的组件。

## **第一次查看 HAMi metrics**

这个命令会从 device plugin 拉取原始 Prometheus 文本，并打印前十行。

```text
$ curl -s http://localhost:31993/metrics | head -10
# HELP GPUDeviceCoreAllocated Device core allocated for a certain GPU
# TYPE GPUDeviceCoreAllocated gauge
GPUDeviceCoreAllocated{deviceidx=”0”,deviceuuid=”GPU-4cdfc14a...”,nodeid=”nebius-tarantula”,zone=”vGPU”} 0
# HELP GPUDeviceCoreLimit Device memory core limit for a certain GPU
# TYPE GPUDeviceCoreLimit gauge
GPUDeviceCoreLimit{deviceidx=”0”,deviceuuid=”GPU-4cdfc14a...”,nodeid=”nebius-tarantula”,zone=”vGPU”} 100
```

每一行都是一个 metric。只要你多读两遍，这些名称其实都还算合理。在一个安静的集群里，大概有八组 metric families。真正有点狡猾的是 labels，不过我后面会再讲。

如果你的集群不是本地的，可以把 `localhost:31993` 替换成正确的 host，或者对 device plugin pod 执行 kubectl port-forward。

## **四个“工具”**

我想要四个 tool calls。

(i) 集群摘要。多少个节点，多少张 GPU，多少 vGPU 显存已被占用，多少还空闲，谁用得最多。

(ii) 每个 device 的数字。同样的数据按 GPU 拆开，并支持可选的 node filter。

(iii) 每个 pod 的归属关系。哪个 pod 位于哪张 GPU 上，占用了多少资源。

(vi) 自由形式的 metric query。给我一个 metric 和一个 label filter。

每个 tool 都只是一个 Go 函数。它抓取 HAMi endpoint，解析 Prometheus 文本，然后返回 JSON。上层的 MCP library 负责处理 stdio 上的 JSON-RPC framing。这就是整个架构。

完整实现都在 repo 里的 `main.go` 中。大约 500 行，四个 handlers，没有 caching。

## **两个坑到我的 bug**

我不是第一次就做对了。有两件事值得指出，因为它们很可能也会坑到其他尝试的人。

### **Prometheus parser 在正常构造时 panic**

我写了最直观的代码。声明一个 `TextParser`，把 response body 传给它，然后取回 metric families。第一次调用时，程序 panic 了，错误是：`Invalid name validation scheme requested: unset`。

原因在 `prometheus/common` v0.67 中。parser 保留了一个 private validation scheme，默认值是一个没用的 zero value。有一个全局变量叫 `model.NameValidationScheme`，看起来像是能帮上忙。但实际上没用，parser 并不会读取它。

修复是一行代码。不要 zero initialize，而是通过 `expfmt.NewTextParser(model.UTF8Validation)` 来构造 parser。repo 中 `main.go` 的 `scrape()` 顶部附近有可工作的版本。

### **两组看起来一样但其实不同的 label families**

这个更隐蔽。我的第一版 cluster summary 用 `(nodeid, deviceuuid)` 作为 device key。这很合理。然后我部署了一个向 HAMi 申请 vGPU 的 pod，再次 scrape，结果 device count 翻倍了。

```text
"device_count": 2,
"devices": [
  {"node": "nebius-tarantula", "device_uuid": "GPU-4cdfc14a...", "memory_allocated_mb": 8192},
  {"node": "",                 "device_uuid": "GPU-4cdfc14a...", "memory_allocated_mb": 0}
]
```

这个 phantom device 的 node 是空的。这就是线索。当我 diff pod 落下前后的 raw metrics 时，出现了两个新的 series。

```text
vGPUCoreAllocated{containeridx="0",deviceuuid="...",nodename="nebius-tarantula",podname="hami-demo-workload",...} 30
vGPUMemoryAllocated{containeridx="0",deviceuuid="...",nodename="nebius-tarantula",podname="hami-demo-workload",...} 8.589934592e+09
```

注意 label key。device level metrics 使用的是 `nodeid`。新的 per pod metrics 使用的是 `nodename`。逻辑上是同一个东西，但 key 不同。我的代码在一个 per pod sample 上读取 `s.Labels["nodeid"]`，得到的是空字符串，然后这个空字符串进入了 dedup tuple，被当成了一个新的 device。

修复很小。只对白名单中的 metric names 做 cluster summary，把 per pod metrics 交给另一个 tool 处理。白名单和其余修复都在 `main.go` 的 `handleGetClusterSummary` 里。

我会记住的教训是：当一个 Prometheus exporter 使用两套 label dialect 时，不要写一个横跨两者的统一 dedup key。

另外一个收获是，per pod series 也是我第一次意识到 HAMi 已经发布了 pod attribution 的地方。当共享 GPU 上有东西出问题时，pod label 才是 operator 真正想要的东西。

## **创建一个 workload，让 metrics 变得有意思**

一个干净的集群到处都会显示为零。为了让这些 tools 真正做点事情，你需要一个持有 HAMi reservation 的 pod。repo 中有一个 manifest：`k8s-vgpu-workload.yaml`。它会请求一个 GPU、8 GiB 显存和 30% core，然后 sleep 半小时。

第一个命令告诉 Kubernetes 根据 manifest 创建 pod。第二个命令检查这个 pod 是否真的在运行。

```text
$ k apply -f k8s-vgpu-workload.yaml
pod/hami-demo-workload created
​
$ kgp hami-demo-workload
NAME                 READY   STATUS    RESTARTS   AGE
hami-demo-workload   1/1     Running   0          8s
```

现在看看 HAMi 在 pod 上记录了什么。下一个命令会打印 pod 的完整 spec，并过滤出以 HAMi annotation prefix 开头的行。

```text
$ k describe pod hami-demo-workload | grep hami.io
hami.io/bind-phase:              success
hami.io/vgpu-devices-allocated:  GPU-4cdfc14a-c633-e61e-9235-56118c547d80,NVIDIA,8192,30:;
hami.io/vgpu-node:               nebius-tarantula
```

中间那行信息最多。读取这些逗号分隔字段可以看到：HAMi 分配了 GPU UUID `GPU-4cdfc14a...`，类型为 `NVIDIA`，显存为 `8192` MiB，core 为 `30` percent。这个 annotation 是 HAMi 用来让 device plugin 和 scheduler 保持同步的方式。

当你用完这个 pod，可以通过 `k delete -f k8s-vgpu-workload.yaml` 删除它。

## **选择一个本地 LLM**

我一开始用的是 vLLM 和 NVIDIA 的 [Nemotron Nano 8B](https://huggingface.co/nvidia/Llama-3.1-Nemotron-Nano-8B-v1)。在镜像下载到磁盘之前就暴露出两个问题。第一，`vllm/vllm-openai` 压缩后大约 10 GiB，解压后大约是两倍。主机只有 17 GiB 空闲。第二，即便它能装下，L40S 现在已经被 HAMi 切片了，而另一个运行在 HAMi accounting 之外的 inference engine 需要调整 `--gpu-memory-utilization`，以便给 demo pod 的 reservation 留出空间。

于是我换成 Ollama 和量化到 Q4 的 `llama3.2:3b`。镜像大约 6 GiB，模型大约 2 GiB。Ollama 暴露 OpenAI compatible chat completions endpoint，所以 test client 并不关心另一端实际使用的是哪个 engine。

下面这个命令以 Docker container 的方式启动 Ollama，并提供完整 GPU 访问。我们特意将它绑定到 127.0.0.1:11434。Ollama 没有认证，因此如果绑定到 public 地址，互联网上任何 host 都可以调用你的本地模型。e2e client 只需要从同一台 host 访问 Ollama，所以 localhost 就够了。

```text
$ docker run -d --name ollama --gpus all --network host -e OLLAMA_HOST=127.0.0.1:11434 -v ollama-models:/root/.ollama ollama/ollama:latest
```

这个十六进制字符串就是新的 container ID。Docker 会打印它，因为我们使用了 `-d`（detached）。下一个命令告诉运行中的 container 拉取模型权重。

```text
$ docker exec ollama ollama pull llama3.2:3b
pulling dde5aa3fc5ff: 100%  2.0 GB
...
success
```

2.0 GB 那层是模型权重。更小的 blobs 是 tokenizer、chat template 等等。success 之后，Ollama 已经在磁盘上拥有这个模型，并准备好提供服务。

最后一个命令询问 OpenAI compatible endpoint 它可以提供哪些模型，用来确认 pull 成功。

```text
$ curl -s http://localhost:11434/v1/models
{"object":"list","data":[{"id":"llama3.2:3b","object":"model",...}]}
```

Ollama logs 确认它通过 NVIDIA container runtime 直接看到了 L40S，并且可以使用完整的 45 GiB。这是因为 Docker 完全绕过了 HAMi。HAMi 只会统计 Kubernetes scheduler 分配出去的内容。那个请求 8 GiB 的 demo pod 会出现在 HAMi metrics 里。Ollama container 不会。这是正确行为，但第一次看到时很容易让人困惑。

## **同样的 plumbing，这次放到浏览器里**

端到端 Go client 是一个不错的 smoke test，但它内置了一个 LLM 和一个 prompt。日常调试时，你会希望手动试探 tools，并看到原始 JSON。MCP Inspector 是官方的、基于浏览器的 MCP debugger，正好可以做到这一点。它是一个小型 Node.js app。你把它指向 binary，它会打开一个浏览器 tab，每个 tool 都会变成一个你可以点击的按钮。

下面这个命令启动 Inspector，并把它指向我们的 binary。`HOST=0.0.0.0` 让它监听所有网络接口，这样不同机器上的浏览器也能访问。`ALLOWED_ORIGINS` 是它的 `CORS` allow list，也就是浏览器加载的 URL。`MCP_AUTO_OPEN_ENABLED=false` 跳过本地浏览器自动打开，因为这台 VM 没有图形会话。`npx -y` 会下载 package 并运行，不会要求确认。

运行之前先提醒一句。把 Inspector 绑定到 `0.0.0.0`，等于把一个 debug tool 放到了公网。默认启用的 token authentication 有帮助，但真正的部署应该放在 VPN 或 SSH tunnel 后面。下面这种方式适合在一次性 demo 或临时 VM 上使用。

```text
$ HOST=0.0.0.0 \
  ALLOWED_ORIGINS="http://YOUR_VM_IP:6274" \
  MCP_AUTO_OPEN_ENABLED=false \
  npx -y @modelcontextprotocol/inspector ./hami-mcp-server
​
Starting MCP inspector...
✓ Proxy server listening on 0.0.0.0:6277
✓ Session token: <64 hex chars, regenerated on every restart>
✓ MCP Inspector is up and running at:
   http://0.0.0.0:6274/?MCP_PROXY_AUTH_TOKEN=<token>
```

（你不会以为我会在这里分享我的个人信息吧？）

两个端口，各自有一个角色。`6274` 是浏览器加载的 React UI。`6277` 是 UI 随后调用的 proxy。proxy 会把 `hami-mcp-server` 作为 subprocess 启动，并通过 stdio 与它通信。session token 是启动时打印的一次性 secret，请把它当作密码处理，不要粘贴到公开聊天里。

在浏览器中打开打印出来的 URL，把 `0.0.0.0` 替换成你的 VM IP。你会看到一个表单，其中包含 Command 字段和 Arguments 字段。把 binary 的绝对路径粘贴到 Command，Arguments 留空，然后点击 `Connect`。右侧面板会列出 server 注册的四个 tools。

![](https://pic2.zhimg.com/v2-96587b74f25b7497574d58cd09314a5b_r.jpg)

MCP Inspector 已连接到 hami-mcp-server。左下角显示 server 为 “Connected”——版本 0.1.0。

![](https://pica.zhimg.com/v2-8893a866c196829df4271221ef02cfb6_r.jpg)

四个 tools：get_cluster_summary、get_gpu_metrics、get_vgpu_allocation、run_promql。每个 tool 的 description 都直接来自 Go source。

点击 `get_cluster_summary`，metadata pairs 留空，然后点击 `Run Tool`。Inspector 会向 binary 转发一个 JSON-RPC `tools/call`。binary 抓取 HAMi 并返回 JSON。面板会渲染结果。在我们的 demo pod 运行时，结果中会有 `memory_allocated_mb: 8192`、`core_allocated: 30`、`shared_containers: 1`。执行 `k delete pod hami-demo-workload`，再次点击 `Run Tool`，所有数字都会回到零。

![](https://pic2.zhimg.com/v2-ee57b8b35993c215cd9f5b8049bd5c5b_r.jpg)

demo pod 运行时的 get_cluster_summary 结果：8192 MB 已分配，30 cores，17.78% memory utilization，HAMi v2.8.1。

`get_vgpu_allocation` 是更有意思的一个。pod 运行时，它会返回一条 allocation entry。这条 entry 包含 namespace、pod、device UUID、8 GiB 显存以及 30% core。调用时传入 `pod_name: hami-demo-workload`，会返回同一行。传入一个不存在的名字，会得到一个空列表，并附带说明：没有匹配的 pod 拥有 active vGPU reservation。

![](https://picx.zhimg.com/v2-2a78a6a21727e3c3d7688709e4dd4fc3_r.jpg)

get_vgpu_allocation 结果显示 default namespace 中的 hami-demo-workload：GPU-4cdfc14a...，8192 MB，30 cores。

`run_promql` 允许你写一个 metric name，加上可选的 label matchers。把 `nodeGPUMemoryPercentage{nodeid="nebius-tarantula"}` 放入 query 字段，响应会返回一个 sample，`value: 0.17782...`，这与 cluster summary 报告的 17.78% 是同一个数字，只是小数位更多。

![](https://pic3.zhimg.com/v2-7eae3434e2b4a2eebee655a26f8e5bf2_r.jpg)

使用 `nodeGPUMemoryPercentage{nodeid="nebius-tarantula"}` 运行 run_promql：匹配到一个结果，value 为 0.17782408613354173。

这个实验证明的事情很小，但很有用。我们写的 MCP server 并没有绑定到某一个 client。任何支持 MCP 的工具，只要指向这个 binary，都会看到同样的四个 tools 和同样的 JSON shapes。

![](https://picx.zhimg.com/v2-66a980b5b55caaac3e90f1d018035903_r.jpg)

完整 Inspector 视图，其中 history panel 展示了当前 session 中的所有 tool calls。

我有意采用这种工作方式。把两个真实系统适配到一起，比从零开始构建 greenfield 更让我感兴趣。一个真实的 bug story，也比 marketing pitch 更有用。你刚刚读到的这篇文章就是这样一次练习。其余内容在 [github.com/mesutoezdil](https://github.com/mesutoezdil/hami-mcp)。

## **结尾**

现在，任何支持 MCP 的 client 都可以读取这个集群。clients 不需要知道 HAMi 是如何工作的，它们只需要调用 `get_cluster_summary` 或另外三个 tools 中的某一个，然后拿到小型 JSON。

在一个单节点 home lab 上，这对问题本身来说可能有点大材小用。真正的价值会出现在你拥有多个 GPU 节点、这些节点被多个团队共享，并且你希望用一种统一方式询问它们状态的时候。server 本身大约 500 行 Go。困难部分是两套 label families 和 parser 的坑。其余部分只是机械工作。

GPU Usage Monitor 让这一能力能够在几分钟内快速落地。
