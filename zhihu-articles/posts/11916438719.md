### 简介和免责声明

编译器总是笼罩着一层神秘和魔幻的色彩。这导致我们许多人误以为编译器能（很好地）做到一些实际上做不到的事情，或者认为它们做不好一些实际上能做好的事情。[1]

本文是上一篇关于[编译器优化](https://sbaziotis.com/compilers/compiler-opt.html)的文章的后续内容。在这里，我收集了多年来我遇到的一些误解（其中许多是我自己的），尽我最大的努力来消除任何困惑。需要注意的是，本文仅涉及大规模、主流、通用编译器，例如 LLVM、GCC 和 ICX。有些陈述不适用于例如特定于领域的编译器[2]或中小型编译器[3]。如果您想查看有关其他类别编译器的文章，请告诉我。

由于这篇文章有点*长*，根据朋友的建议，以下是目录（见左侧）。

### 优化为我们提供了最佳方案

首先，所谓最优（optimal）是根据哪种度量标准来衡量的？举例来说，代码大小就是一种度量标准。但通常编译器所针对的度量标准是运行时间（即程序单次运行的延迟）。不过无论如何，优化这个说法其实并不准确。编译器甚至不会尝试去寻找最优的程序。相反，它们首先会以一种非常[简单的方式](https://sbaziotis.com/compilers/compiler-opt.html#unoptimized-builds)降低（lowering）程序，然后仅仅试图去“改进”这个结果。改进（improving）比优化（optimizing）这个说法要弱得多，但却更准确。

但为什么我们得不到最优程序呢？这是因为这个过程非常困难且耗时。对于代码大小这个目标来说，将来也许有希望在合理的时间内生成最优程序，因为代码大小作为一个度量标准具有许多良好的特性。例如，我们可以非常准确和可靠地测量代码大小，基本上就是生成程序的文件大小。此外，不同次测量会得到完全相同的值（也就是说，如果你现在测量大小，一分钟后再测，得到的值是一样的）。最后，代码大小具有[最优子结构](https://en.wikipedia.org/wiki/Optimal_substructure)。**更新：实际上，我似乎推翻了自己在这里的论述。详见此[评论](https://news.ycombinator.com/item?id=42375191)。希望我能找到时间重新探讨这个问题。**让我们通过一个实际例子来理解这意味着什么：假设你有一个函数`A`，你想要最小化它的大小（即找到最小的大小）。现在，假设你把这个函数分成两部分，并独立地找到它们各自的最小值。最优子结构告诉我们，如果你只是把这两部分合并，你就会得到整个函数的最小版本。换句话说，组合个别的最小值会给你一个全局最小值。

另一方面，运行时间则完全不具备这些特性。首先，你无法准确测量它。同一程序的不同运行会有轻微的时间差异。更糟糕的是，影响运行时间的因素[很多且微妙](https://doi.org/10.1145/1508284.1508275)。此外，提高运行时间并没有最优的子结构。例如，您分别拥有两个循环的最佳版本，但全局最小值可能需要融合这两个循环。最后，[“我们绝对没有我们正在编译的机器的正确模型”](https://youtu.be/p15qRHZ_Leg?t=951)。这是最近的学术工作艰难发现的事情。[goSLP](https://dl.acm.org/doi/abs/10.1145/3276480) 生成全局优化的 SLP 矢量化代码。但根据什么来优化呢？根据硬件型号。因为这些模型很糟糕[4]，作者发现生成的程序不仅*不是*最优的，而且可能[比 LLVM 慢](https://youtu.be/wiwloa0g02g?t=1946)！

### **分支权重和 CPU 的分支预测器**

在大多数现代编译器（包括 GCC、LLVM 和 ICX）中，条件分支可以具有权重。这基本上是分支是否被采用的概率。这些权重可以通过配置文件引导优化（PGO）添加，也可以由程序员使用`__builtin_expect`等内在函数添加：

```c
if (__builtin_expect(x == 0, 1)) { // The branch is likely to be taken
}
```

这里的误解是，对于 x86 架构，编译器会为*CPU*的分支预测器生成分支提示。直到最近，情况并非如此。尽管 Intel 在 Pentium 4 中引入了分支提示，但他们发现实际上并没有任何性能优势，只是增加了代码大小。[^5]你仍然可以在程序集中包含分支提示，但 CPU 会忽略它们。

那么，这些提示/权重有什么用呢？它们是*编译器”*分支预测器“的提示，它主要用于有效地放置代码块。例如，如果可能出现分支，编译器会将其目标块直接放置在当前块的下方，以便执行会直接转移到该块，以增加指令缓存局部性。

但是，英特尔最近推出了一种架构 Redwood Cove，在这种架构中分支提示又变得重要起来。[^6]因此，理论上编译器将为该架构生成这些提示。

然而，在实践中很难看到它。我无法举出任何例子，能向编译器提供一个 C 语言的示例代码，并通过某种标志组合使其生成带有分支提示的 x86 汇编；无论是 GCC、LLVM 还是 ICX 都不行。我甚至不知道如何专门针对Redwood Cove 生成代码。但是，我们*可以*直接生成提示。用这个 LLVM IR 代码：[^7]

```llvm
; Source C code:
;
; void foo(int x, int y, int *p) {
;   if (__builtin_expect(x == 0, 1)) {
;     *p = y;
;   }
; }

define void @foo(i32 %x, ptr %p) {
entry:
  %cmp = icmp eq i32 %x, 0
  br i1 %cmp, label %if.then, label %if.end, !prof !0

if.then:                                          ; preds = %entry
  store i32 %x, ptr %p
  br label %if.end

if.end:                                           ; preds = %if.then, %entry
  ret void
}

!0 = !{!"branch_weights", i32 49, i32 51}
```

并将其传递给`llc`[8]：

```text
llc < test.ll -mtriple=x86_64 -mattr=+branch-hint -enable-branch-hint
```

我们会得到（[godbolt](https://godbolt.org/z/95KE4eTYY)）：

```text
foo:                                    # @foo
        test    edi, edi
        ds  # <--- x86 分支提示
        jne     .LBB0_2
        mov     dword ptr [rsi], edi
.LBB0_2:                                # %if.end
        ret
```

可以看到第 3 行有分支提示。

其他架构的情况可能有所不同，但我最熟悉 x86。

### **-O3 生成的代码比 -O2 快得多**

2019 年（对编译器领域来说并不算太久远）Emery Berger 在 Strange Loop 大会上做了一场演讲。在那次演讲中，他展示了证据支持这个令人震惊的说法：在 Clang 中，`-O2`和`-O3`没有统计意义上的差异！[^9]这也与我的经验相符，特别是在使用 Clang 的时候。GCC的`-O2`比 Clang 的不那么激进，所以确实存在一些差异，但差异并不大。另外`-O3`几乎完全忽略了代码大小，这可能会导致指令缓存的问题。

故事的寓意是：这不是一个规则。这是一个需要进行基准测试的情况，因为它值得这么做。

### **JavaScript 解释器在运行时进行 JIT 编译，因为它们无法提前知道哪些路径是热点**

仅仅知道 JavaScript 字节码中哪些路径是热点路径是不足以生成优化代码的；你还需要知道类型信息。而类型只能在运行时才可获知。这就是即时编译器（JIT编译器）在运行时编译代码的主要原因。

### **如果有编译器，就不需要解释器**

这在很大程度上取决于具体情况。是的，对于 C/C++流水线，几乎在任何地方，解释器都不会非常有用，而且很难实现一个。但有些情况下，解释器是有用的。一个有趣的情况是 WebAssembly。

最近，Ben Titzer 发布了一篇论文，标题为：[A Fast In-Place Interpreter for WebAssembly](https://dl.acm.org/doi/pdf/10.1145/3563311)。在这篇论文中，蒂泽特向我们讲述了一个关于 WebAssembly 实现的故事。

你看，对于非原生语言来说，通常是先开发一个解释器，然后*再*开发（即时）编译器。这是因为解释器通常更容易开发和使用，而编译器则是为了提升性能才需要的。然而有趣的是，在 WebAssembly 生态系统中，即时编译器反而是最先被开发出来的。据我的理解，这是由以下三个因素造成的：

- **为编译设计。**WebAssembly 为编译设计，这是因为它以性能为核心目标，而不仅仅是附加考虑。这里的性能意味着生成代码的性能，也包括编译的效率。例如，WebAssembly 可以在一次遍历中进行类型检查。
- **说服力。**尽管 WebAssembly 从一开始就有“政治”权力[^10]，但设计者仍然希望说服人们并提供证据，证明 WebAssembly 确实是关心性能的用户的一个可行选择。而没有编译器，你无法提供这样的证据。
- **不适合解释。**编译设计带来了一些特性，使得实现解释器变得困难。最显著的是结构化的控制流程。在论文中，Titzer 非常好地描述了这些痛点。

然而，人们最终意识到解释器有许多优势。Titzer 在论文的第 1.1 节中详细描述了六点优势。事情的关键在于，虽然通常无法击败编译二进制文件的性能，但也有其他实际原因需要使用解释器。

### **中端与目标/平台无关**

LLVM 是最流行的中端（middle-end），但它却并不是与目标/平台无关的。我写了一整篇[文章](https://sbaziotis.com/compilers/how-target-independent-is-your-ir.html)来讨论这个话题。

### **编译器针​​对数据局部性进行优化**

几乎可以肯定不是！[11]是的，编译器将针对*指令*缓存局部性进行优化；我们[之前](https://sbaziotis.com/compilers/common-misconceptions-about-compilers.html#branch-weights-and-the-cpus-branch-predictor)看到过。编译器对缓存优化的研究也有着悠久的历史[^12]；它们都没有进入主流编译器。[Polly](https://polly.llvm.org/) 是我所知的最严肃的数据局部性优化框架[13]之一，并成功成为一个主流大型编译器的一部分。不过，它在 LLVM 中仍未默认启用。

Mike Acton 在 CppCon 大会上的演讲 [Data-Oriented Design and C++](https://www.youtube.com/watch?v=rX0ItVEVjHc) 获得了约 69 万次观看，这在很大程度上是因为他强调了一个重要观点：C++ 编译器无法为你优化缓存局部性（cache locality）。这次演讲基本上开启了面向数据设计（data-oriented design）的运动[14]，其主要目标是编写充分利用缓存的代码。

但是，您可能会问*为什么*编译器不为您做这件事。不幸的是，它做不到。首先，优化数据局部性需要对程序进行大规模的侵入性更改。例如，假设有一个开放寻址哈希表——更具体地说，LLVM`DenseMap`的数据布局如下所示：

```cpp
class DenseMap {
  struct BucketT { KeyT Key; ValueT Value; };
  unsigned NumBuckets;
  BucketT *Buckets; 
...

```

这意味着我们有一个数组，其中每个条目都有一对键值。但是，在查找过程中，我们只关心键。按照当前的数据结构，我们会不断地将值加载到缓存中，这浪费了缓存空间和计算周期。改进的一种方法是将其拆分成两个数组：一个用于存储键，另一个用于存储值。

为了保持代码行为相同，我们必须更改使用此原始数组的*每个*位置：分配、获取键的位置、设置值的位置等。在 C/C++ 中，要可靠地完成这项工作非常困难。但最重要的是，编译器显然不允许这样做。通常来说，C/C++ 编译器是不允许重新排列结构体字段的。[15]

最后但并非最不重要的一点是，即使允许编译器这样做，C/C++ 程序中的抽象信息也太贫乏，编译器无法识别此类机会。[16]简而言之，编译器对程序的内存访问的了解非常不精确，无法很好地了解布局优化的好处。

### **-O0 编译得很快**

主流编译器如 Clang 和 GCC 的编译速度都很慢，所以更准确的理解是：`-O0` 选项会给你可调试和行为可预测的代码，而不是说它会快速地生成代码。

一般来说，是的`-O0`比`-O2`更快，尽管我没有大规模的实验来支持这一点。但例如，编译一个`Release` [zstd](https://github.com/facebook/zstd)的构建大约需要 34 秒，而`Debug` 构建大约需要 11 秒。[我的一个项目](https://github.com/baziotis/minijava-cpp)也有类似的情况：它使用统一构建并具有大约 5K 行代码。然而，即使说 `-O0`总是比`-O2`快的说法是不正确的。举个例子，在我的桌面上，编译 LLVM 的`Debug`版本大约需要 25 分钟，而编译`Release`版本大约需要 23 分钟。[17]

重点是，如果你真的想要快速编译，你就需要设法绕过标准的编译管道，尤其是当你使用 C++ 的时候。一种选择是使用更小的编译器，因为这些编译器通常更快（比如 TinyCC）。另一种选择是至少跳过*一些*编译阶段。一种方法是直接生成 LLVM IR，数据库研究人员也观察到了这一点。在一篇 2011 年[18]流行的查询编译论文[^19]中，作者说：

> 为每次查询 [编译 LLVM IR] 通常只需要几毫秒，但 C 或 C++ 编译器则需要几秒钟

查询编译是快速编译很重要的用例之一，因为它是在线的。

如果我们使用的是 Clang 编译器的话，很容易理解为什么这句话是对的，因为 Clang 无论如何都需要经过 LLVM IR 这个阶段。另外，C/C++ 没有二进制格式（这本可以加快处理速度），只有文本格式。而 LLVM IR 却同时具有这两种格式。

### **模板编译得很慢**

并非如此... *C++*模板（templates）编译速度很慢，因为 C++ 的编译模型很糟糕。[^20]模板当然会增加编译复杂性，但不会使其变得不切实际。

一个典型的例子是 Dlang 的标准库，[Probos](https://github.com/dlang/phobos)。在我的速度不是特别快的笔记本电脑中，编译它只花了大约 12 秒——即使它有超过 25 万行充满了模板的代码，而且还是在优化构建中。[21]请注意，D 的主编译器 DMD 并没有做任何特别奇特的事情。当然，Walter Bright（D 和 DMD 背后的策划者）是有史以来最好的编译器工程师之一，他对如何使编译器快速运行肯定了解不止一两件事。但 DMD 并不会做出任何疯狂的事情；它甚至不是多线程的。

### **分离编译总是值得的**

分离编译（Separate compilation）的想法是为每个源文件编译不同的目标文件。[22]这样做的好处在于，如果您更改一个源文件，您只需重新编译该文件并“仅”将其与其他目标文件链接；您不必重新编译整个项目。

这听起来很有吸引力，并已成为计算机科学教育中的某种神圣信条[23]，并从那里渗透到生产环境中。问题在于，实践中，链接过程非常慢。遗憾的是，我对链接的研究还不够深入，无法评论这个问题是否是固有的[24]。但那并不重要；现实就是这样。

所以，对于*很多*项目来说，分离编译是不值得的。相反，**统一构建**（Unity Build）——指的是只需将所有内容都包含到一个文件中——通常是更好的选择。让我举一些例子。首先我确信，对于我编写的*每个*C/C++ 项目来说，这是不值得的。这里说的是单个项目大约有 20K 行代码的情况。例如，[minijava-cpp](https://github.com/baziotis/minijava-cpp) 是一个用 C++ 编写的 MiniJava 编译器，其中包含一些相当繁重的代码。在我的笔记本电脑中，它的编译时间约为 0.7 秒，而链接所有这些单独的文件则需要更长的时间。简而言之，我在项目中从未遇到过单独编译比统一构建更好的情况。

除了个人经验之外，[据说](https://youtu.be/qYN6eduU06s?t=601)育碧也使用 Unity 构建来缩短游戏的编译时间[^25]。SQLite 也将所有内容编译到单个`.c`程序中。

除了编译时间，统一构建还有其他优点。例如，你可以获得全程序优化，而不需要应用链接时优化（见下文）。此外，所有代码只编译一次，这不仅大大提高了编译速度，还能产生更清晰的错误日志。在 C++ 的编译模型下（见上文），如果你在不同的编译单元（为简单起见，可以理解为文件）中包含（include）同一个文件，它会在每个单元中都被编译一次。如果再加上模板会生成同一段代码的多个版本这一点，你就会发现相同的代码被反复重新编译。

总之，我不能说单独编译永远没有用，因为我没有证据支持这一点。但是，我从未发现它在我的项目中是成功的，对于一些大型项目来说似乎也是如此。所以，不妨尝试一下统一构建。

### **为什么链接时优化（LTO）发生在链接时？**

讲个故事。两年前，我在旁听Vikram Adve[26]的《高级编译器构造》课程。在课堂上的某个时刻，Vikram 提出了价值百万美元的问题：为什么链接时优化发生在链接时？这听起来可能有点矛盾，但实际上问题是：为什么全程序优化（whole-program optimization）发生在链接时？

这是一个非常合理的问题，因为实际上没人真正关心链接时优化；人们关心的是全程序优化。而且链接器通常不是优化器，这不是它们的工作。事实上，从理论上讲，全程序优化在中端进行更有意义。首先，中端的工作*就是*优化。其次，中端操作的是为优化而设计的中间表示（IR），这与目标文件通常包含的汇编代码不同。此外，没有什么能阻止编译器获得程序的全局视图。它可以简单地把所有输入的 C/C++ 文件转换成 LLVM IR，然后就能看到整个程序的全貌。那么，天啊，为什么它要在链接时进行呢？我得说，当时没人知道答案。感谢上帝，我们终于开悟了。

Vikram 解释道（好吧，我在转述他的话）答案在于 C/C++ 构建系统那令人遗憾的现实。在大型项目中，要想找到源 C/C++ 文件并弄清楚什么调用什么，那简直是太难了。C++ 工具链就不是为此而设计的。另一方面，链接器必须能够找到所有的目标文件。所以，工具链被设计成链接器*能够*收集项目的所有代码。当然，通常目标文件包含的是汇编代码，没人愿意处理这个。因此，编译器就会把比如说 LLVM IR 也塞进目标文件中，以供编译器访问。

### **内联之所以有用主要是因为它消除了调用指令**

避免一个函数调用（call）指令（序列）是有好处的，但即便如此，这种好处部分是来自于指令缓存的局部性，而不是因为这个指令本身很慢。但最重要的是，内联最大的好处（而且远超其他好处）在于它是一个启用性转换，这意味着它能够启用其他优化。我在[这里](https://youtu.be/I4Iv-HefknA?t=1084)有更详细的解释，但让我重点说明内联的一个经常被忽视的效果。

内联可以实现过程间优化，实际上不需要任何过程间编译器技术（除了内联本身）。过程间优化（Interprocedural optimization）技术是那些涉及多个过程（即函数）的技术，即它们*跨*函数进行优化。过程间优化很难准确实现，因为它们涉及多个函数。无论如何，优化通常很难扩展到一小组基本块或单个循环之外，更不用说超出函数边界了。然而，内联实际上允许过程间优化的发生。例如，假设您有以下代码：

```cpp
int sat_div(int num, int denom) {
  if (denom == 0) {
    return (num > 0) ? INT_MAX : INT_MIN;
  }
  return num / denom;
}

int foo(int a) {
  int b = sat_div(a, 3);
  return b;
}

```

优化后，`foo`的代码如下所示（ [godbolt](https://godbolt.org/z/Gfr1rjMvj) ）：

```cpp
// ... sat_div 保持不变

int foo(int a) {
  // 生成的代码很奇怪，因为编译器把除法变成了乘法
  return a / 3;
}

```

因此，编译器执行常量传播，把常数`3`传递到了参数`denom`，它消除了无用的`if`分支（因为在这种情况下条件恒为假），并将除法变成了乘法。但它是怎么做到的呢？好吧，不是通过常量传播[27]、死代码消除或指令组合的过程间版本。恰恰相反，这种效果是因为编译器首先内联了对`sat_div` ( [godbolt](https://godbolt.org/z/4TdaG9Wz7) ) 的调用，然后*启用了*这些转换的过程内[28]版本。换句话说，内联将所有内容都放入一个函数中，这使得传统的转换能够发挥作用。这就是为什么内联被许多人（例如 [Chandler Carruth](https://youtu.be/FnGCDLhaxKU?t=1580) ）认为是优化编译器中最重要的优化。[29]

这是否意味着内联是过程间优化的唯一方法？一方面，有大量关于过程间优化的文献，其中一些已经进入生产编译器。[^30]另一方面，对于大多数主流编译器来说，几乎所有的过程间工作都是通过内联完成的。这也是为什么最近几乎所有与过程间优化相关的编译器成本模型研究都以内联为目标。[^31]

### **inline 关键字的作用**

我正在谈论这件事（[cppreference](https://zh.cppreference.com/w/cpp/language/inline)）：

```cpp
#ifndef EXAMPLE_H
#define EXAMPLE_H
 
// 在头文件中定义的，被多个源文件包含的函数，必须定义为 inline 的
inline int sum(int a, int b) {
  return a + b;
}

#endif

```

关于此关键字的大多数文档都专门介绍其在链接中的作用。事实上，这就是语义上重要的地方。但我在这里要回答的问题是：它与内联优化有什么关系吗？

这本来应该是一件容易的事。毕竟，Chandler Carruth [告诉我们](https://youtu.be/FnGCDLhaxKU?t=1560)“C++ 中的`inline`关键字可能与优化无关”。[32]但故事并不那么简单。一方面，cppreference 告诉我们：

> inline 关键词的本意是作为给优化器的指示器，以指示优先采用函数的内联替换而非进行函数调用，即并不执行将控制转移到函数体内的函数调用 CPU 指令，而是代之以执行函数体的一份副本而无需生成调用。

然后我们看看[最新的](https://open-std.org/jtc1/sc22/wg21/docs/papers/2024/n4993.pdf)C++ 标准草案[33]，它说[34]：

> *The inline specifier indicates to the implementation that inline substitution of the function body at the point of call is to be preferred to the usual function call mechanism. An implementation is not required to perform this inline substitution at the point of call. （*内联说明符向实现表明，在调用时函数体的内联替换优先于通常的函数调用机制。在调用时执行此内联替换不需要实现。）

另一方面，cppreference 又告诉我们：

> [...] 由于关键词 inline 对于函数的含义从 C++98 起已经变为“容许多次定义”而不是“优先内联”，因此这个含义也扩展到了变量。

看看这些来自可信来源[35]的相互矛盾的说法，感到困惑是很正常的。那么，真相是什么？与 C++ 中的许多事情一样，“真相”取决于具体实现所做的选择。因为我最熟悉 LLVM，所以我们来看看它。

所以，LLVM 确实会关注`inline`关键字，这至少从 2010 年就开始了。LLVM IR 有一个`inlinehint`[^36]属性。如果你添加了 `inline` 关键字，Clang 就会将这个属性添加到你的函数定义中[^37]。例如，在此[代码片段](https://godbolt.org/z/jfo35vvzf)中，Clang 为 `int_run` 添加了 `inlinehint` 属性。根据 LLVM IR 参考文档关于 `inlinehint` 的说明：

> 此属性表示源代码包含了一个提示，表明内联此函数是可取的（例如 C/C++ 中的 "inline" 关键字）。这只是一种提示，不会对内联器施加任何要求。

确实，优化器会增加具有`inlinehint`属性的函数的内联阈值[^38]。但变化相对较小。所以，是的，`inline`关键字与优化有关，而且优化器会关心你是否添加了它，但也没有太大影响（抱歉！）。如果你真的想要内联一个函数，我想你应该添加`always_inline`说明符，这是完全不同的情况：除非完全不可能，否则编译器将始终内联这些函数。

### **最好研究的生产级编译器是 LLVM**

看，我喜欢 LLVM！[^39]从很多方面来说，它都非常有教育意义。但这是一个怪物！这是因为 LLVM 应用于*如此多的*用例。 从嵌入式系统到 Google 数据中心，从 JIT 编译器到激进的高性能场景，从 Zig 到 Rust 到 *<下一个新的编程语言>*——这些地方都会用到 LLVM！因此，如果您学习 LLVM，您将不可避免地遇到*许多*它试图处理的边缘和特殊情况，而这些情况几乎没有教育价值。您还将看到一堆高级算法。例如，标准的[Lengauer-Tarjan 算法](https://sbaziotis.com/compilers/semidominators-proof.html)已经很难理解了，但 LLVM 甚至使用了最近推出的更先进的[算法](https://www.youtube.com/watch?v=bNV18Wy-J0U)。

因此，虽然我绝对建议您在某个时候认真研究 LLVM 内部结构，但我不建议您从那里开始。需要说明的是：这是针对那些对编译器*开发*感兴趣的人。如果你只是用户，LLVM 可能是最佳选择。所以，要*学习*编译器，正如我在 Reddit [评论](https://www.reddit.com/r/Compilers/comments/1h4qscz/comment/m02plue/)中建议的那样，你可以看看 [Go 编译器](https://www.youtube.com/watch?v=bNV18Wy-J0U)。它是一个生产编译器，背后有一些*非常*厉害的人，但它不像 LLVM 那样庞大复杂。我还从 [LDC](https://github.com/ldc-developers/ldc) 和 [DMD](https://github.com/dlang/dmd) 的开发者那里学到了很多东西。

### **未定义行为只会开启优化**

不，未定义行为（undefined behavior）也会禁用优化。我就此写了一篇[文章](https://sbaziotis.com/compilers/definedness-removing-optimization-limitations-of-undefined-behavior.html)。

### **编译器可以“简单地”定义未定义行为**

一般来说，编译器总是被允许为未定义行为给出定义。[40]例如，编译器可以定义将一个指向 `NULL` 的 `int*` 指针解引用的结果为 `0`。但是，这会对性能产生影响，因为这会要求编译器在每个指针解引用中插入`if` 。

一个更微妙的论点是，编译器可以将所有未定义的行为定义为平台（platform）的行为。这相当于一石二鸟：首先，编译器不需要添加任何额外的代码，因为它选择的行为本来就是目标平台要做的事情。因此，不会有任何额外开销。其次，作为程序员，你突然就能*准确*知道会发生什么。虽然这个论点听起来不错，但实际上并不那么简单。我写了一篇[文章](https://sbaziotis.com/compilers/defining-all-undefined-behavior-and-leveraging-compiler-transformation-apis.html)认真、详细地审查了这一建议。

### 99%的**正确率就可以了**

最近人工智能（AI）的爆炸式增长并没有让编译器免受影响。在许多情况下，这是有充分理由的。例如，成本模型（cost models）是机器学习的一种合理应用。简单来说，成本模型的工作原理是这样的：它会在可能的解决方案空间中选择其中一个。比如说，假设你有一个循环可以按 16、32 或 64 的因子进行分块。那么，你可能会有一个成本模型，它需要在四个选项中做出选择：完全不分块，或者按这三个因子中的任一个进行分块。

长期以来，成本模型一直是手工编写和维护的。然而，手动调优的成本模型通常既枯燥乏味，又难以扩展（尤其是在架构数量不断增加的情况下）。再加上硬件供应商对其架构披露的信息非常有限，因此手动调优的成本模型（就像基于机器学习的模型一样）简直是黑魔法——它们既不可解释，也不直观。换句话说，这正是机器学习和神经网络大显身手的绝佳案例，因为它们可以自动化这一过程。事实上，过去十年中出现了大量关于机器学习成本模型的研究，其中一些甚至已经投入了实际生产。例如，谷歌最近为其 XLA 编译器采用了一个基于神经网络的[成本模型](https://proceedings.mlsys.org/paper_files/paper/2021/file/6bcfac823d40046dca25ef6d6d59cc3f-Paper.pdf)。

但这里有一个问题。成本模型是神经网络的一个很好的应用，因为你不需要严格的保证。具体来说，可以这样理解：成本模型被提供了一组正确的程序供其选择。因此，无论成本模型做出哪种选择，生成的代码都是正确的！[41]所以，即使神经网络目前存在这样一个“小问题”——我们完全不知道它们是如何工作的，也没有任何保证——这仍然可以接受，比如对于成本模型问题。不过这对于代码生成（code generation）来说完全不行！[42]这在过去是显而易见的，但最近我的印象是，这似乎不再那么显然了。例如，我们最近收到了一位 [Dias](https://sbaziotis.com/compilers/dias.html) 论文审稿人的评论，基本上是问道：“你为什么不直接使用大型语言模型（LLM）？”不！请允许我花点时间来解释，为什么目前将 LLM 用于代码生成完全不可行。

归根结底的问题是：如果编译器生成的代码在 99% 的情况下是正确的，这样可以接受吗？我们需要稍微澄清一下。这是否意味着，在生成的 100 个程序中，有 99 个是完全正确的，而 1 个几乎完全是废代码？显然不是，这不现实。更现实的情况可能是：在 100 行代码中，编译器对其中 99 行生成了正确的代码。我知道这个假设仍然相当简化，但我认为它已经足以支撑这个论点。那么，这样可以接受吗？

我希望你的答案是否定的。从编译器开发者的角度来看，这简直是绝对的垃圾。这样的编译器基本上无法使用。充其量，它只能作为一种研究工具，用于探索某些想法。但用于生产？根本不可能。甚至连调试都不行。为了说明这一点，我们可以考虑一个小型项目，比如有 5000 行代码。在 99% 的正确率下，这意味着每次编译都会有 50 行代码是错误的。五十行！而最糟糕的是：你不知道是哪 50 行，并且每次代码更改后可能还会不一样。你可能有过追踪单行代码中的错误的经历，这既令人沮丧又耗费时间。想象一下，调试 50 行不断变化的错误代码会是什么样子！现在，再想象一下将这种情况扩展到一个可能包含数百万行代码的大型项目。[43]谢谢，不要了。

最后一点：即使LLMs能够生成正确的代码，他们目前与编译器相比*非常慢*。我知道，我在前面的章节中说过编译器没有那么快。但是，与LLMs相比，主流编译器的速度非常快。因此，尽管LLMs拥有光明的未来，并且已经拥有光明的现在，但仍有一些问题他们目前无法解决。其中之一是（在线）代码生成。
