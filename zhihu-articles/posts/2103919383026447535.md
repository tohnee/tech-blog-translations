## 1 医疗大模型训练方案结论

本方案面向医疗问答、患者教育与安全分诊等任务，目标是让模型更会理解问题、给出有依据且边界清楚的回答；模型微调不能替代医生诊断，也不能代替上线前的临床审核。训练框架建议以 LLaMA-Factory 和 ms-swift 为两套主方案：前者适合用配置文件稳定组织 SFT、DPO 和 Reward Model，后者适合 Qwen/ModelScope 生态以及更多 RLHF/GRPO 任务。OpenRLHF 只作为在线 PPO 或 GRPO 的备选方案，不作为 SFT 和 DPO 的默认入口。

方案选择要沿着一条线判断：医疗助手要改善哪类回答，手头数据能否支持这种训练，目标模型和显卡能否承载，最后再看是否需要多机。数据量主要影响训练时长和扩容价值；模型参数量、上下文长度和优化器主要影响显存；DDP、DeepSpeed、FSDP 则决定多卡如何保存和同步模型。

| 训练目标 | 推荐框架 | 推荐后端 | 医疗项目中的优先级 |
| --- | --- | --- | --- |
| SFT | LLaMA-Factory 或 ms-swift | DDP；显存不足时 DeepSpeed ZeRO-2 | 必需 |
| DPO | LLaMA-Factory 或 ms-swift | DDP / DeepSpeed ZeRO-2 | 推荐的第二阶段 |
| Reward Model | LLaMA-Factory 或 ms-swift | DeepSpeed ZeRO-2/3 或 FSDP | PPO 前需要 |
| PPO / GRPO | ms-swift 主选；OpenRLHF 备选 | Ray + vLLM + DeepSpeed | 后续研究阶段 |

全文按“医疗数据与目标—训练组件—训练顺序—模型和显卡—集群与启动”展开。先明确模型该学什么、怎样评价回答是否安全，再判断单卡或多机配置，避免把增加 GPU 误当作提升医学正确性的办法。

## 2 医疗训练数据地图与样例映射

医疗项目的数据通常不是一种格式，而是由“知识数据、对话数据、偏好数据、安全数据和评估数据”共同组成。不同数据适合的训练方式不同，不能把所有问答都直接丢给 SFT，也不能把普通问答直接当成 PPO 数据。

| 医疗数据类型 | 典型内容 | 适合做什么 | 关键处理要求 |
| --- | --- | --- | --- |
| 患者—医生对话（CMCQA、MedDialog） | 多轮问诊、追问、解释、分诊 | 筛选后做 SFT；审核后可构造 DPO prompt | 来源质量不一；脱敏、过滤短答和危险建议，并保留上下文 |
| 六科室中文问答 | 疾病知识、用药、检查、科室问答 | SFT 候选；也可作为离线评估 | 长度去重不等于医学金标准；高风险答案要人工复核 |
| FAQ 候选（cMedQA2） | 问题、正向答案及候选答案 | 主要做检索、重排和 FAQ 评估；筛选后可整理问答 SFT | 候选正负表达相关性，不等于临床安全偏好；不能直接当 DPO 对 |
| 候选回答偏好（MedicalGPT Reward、Medical Evidence DPO） | 同一问题的 chosen / rejected 或评分 | DPO；审核后训练 Reward Model | 核对 chosen/rejected 的医学正确性、安全性与证据一致性 |
| 医学实体与关系标注（CMeEE、CMeIE） | 疾病、症状、药物实体及关系 | 独立做实体抽取或结构化关系任务 | 不要未经转换就混入普通问答 SFT |
| 医学证据与引用 | 指南、论文、药品说明书、证据片段 | 证据问答 SFT、DPO 和 RAG 评估 | 保留出处、版本与适用范围，区分事实和推断 |
| 安全与拒答样本 | 急症、禁忌、隐私、越权和危险建议 | SFT、DPO、Reward Model | 医生或规则审核，覆盖过度拒答与漏拒答 |
| 在线 RL Prompt | 只有问题或任务环境 | PPO、GRPO 等在线 RL | 必须配 Reward Model、规则或医学评估器 |

本项目的数据对应关系也按这个边界处理：CMCQA、MedDialog 和六科室问答是生成式 SFT 候选，但社区对话及自动清洗结果都需要医学审核；cMedQA2 优先用于 FAQ 检索/重排，正负候选不能直接改名为 DPO 的 chosen/rejected。MedicalGPT Reward 与 Medical Evidence DPO 进入偏好训练前也要核验标注含义。Zhongjing 不纳入本方案。

| 样例数据用途 | 训练集 | 验证集 | 测试集 | 在通用医疗方案中的位置 |
| --- | --- | --- | --- | --- |
| SFT 全量候选（medical_alpaca_full） | 605,784 | - | - | 六科室合并候选；不是医学金标准，先按科室和风险复核 |
| SFT 小样本运行集 | 1,140 | 60 | - | 用于先跑通医疗问答格式、训练流程和安全评估 |
| DPO 样例 | 5171 | 128 | 100 | MedicalGPT Reward 与 Medical Evidence DPO 的偏好数据 |
| PPO Prompt 样例 | 5171 | - | - | 只有 prompt，仍需 Reward Model 或评估器 |

当前目录里约60.6万条是处理后 SFT 候选，训练脚本实际使用的1,140条训练样本和60条验证样本是小样本流程集，两者用途不同。表中数量是当前项目文件统计，不是通用医疗项目的推荐比例；正式评估还应按患者/病例、科室、疾病、风险等级和时间隔离，避免数据泄漏。

这张数据地图先回答“模型从什么样本里学什么”。下一章再把样本处理、训练任务、分布式计算和集群调度拆开，说明每一层分别负责什么，医疗审核则贯穿数据准备和结果评估。

## 3 技术分层与各组件职责

| 组件 | 所在层 | 解决什么问题 | 在通用医疗方案中的位置 |
| --- | --- | --- | --- |
| LLaMA-Factory | 训练框架层 | 通过 YAML 和 CLI 组织 SFT、DPO、RM、PPO | 主方案之一 |
| ms-swift | 训练框架层 | 面向 Qwen/ModelScope 的 SFT、DPO、RM、GRPO 等 | 主方案之一 |
| OpenRLHF | 在线 RL 框架层 | 组织 Actor、Critic、Reward、vLLM Rollout | PPO/GRPO 备选 |
| DDP | 分布式训练层 | 每张 GPU 放完整模型，切分数据并同步梯度 | 小模型 LoRA 首选 |
| DeepSpeed | 分布式训练层 | ZeRO 分片、显存优化、多机多卡、offload | 大模型/全参数首选 |
| FSDP | 分布式训练层 | PyTorch 原生切分参数、梯度和优化器状态 | 大模型的替代方案 |
| Ray | 调度与运行时层 | 协调多个训练角色和 GPU 资源 | OpenRLHF 的多角色运行时 |
| vLLM | 推理与生成层 | 高速生成回答，服务于 RL Rollout | PPO/GRPO 使用 |
| Slurm/Kubernetes | 集群调度层 | 分配机器、GPU、rank、任务和日志 | 多机训练外围 |
| PAI-DLC/TI-ONE | 云训练平台层 | 创建资源、挂载数据、启动容器和任务 | 阿里/腾讯云方案 |

可以把它看成医疗训练流水线：先把脱敏且经审核的病例问答整理成训练样本，再由训练框架组织 SFT 或 DPO，分布式后端安排 GPU 计算，集群平台准备机器、网络和存储。各层解决的问题不同，也都不能代替医学审核。下面先用白话解释组件，再据此选择适合的单卡和多卡方式。

### 3.1 医疗训练数据怎样进入训练

SFT 数据就是“题目和标准答案”。模型按照这些样本学习怎么理解问题、怎么组织回答、什么时候拒答。医疗项目的 SFT 数据量即使不大，最重要的也不是堆机器，而是检查答案是否医学上正确、格式是否统一、是否包含不该泄露的个人信息。

DPO 数据就是“同一道题的两个回答，告诉模型哪个更好”。chosen 是希望模型学习的回答，rejected 是不希望模型采用的回答。DPO 不需要在线生成，也不需要先训练 Reward Model，因此比 PPO 更适合当前已有的 MedicalGPT Reward 和 Medical Evidence DPO 数据。

PPO 或 GRPO 的 prompt 只有问题还不够。训练时模型要在线生成回答，再由 Reward Model、规则或医学评估器打分，最后根据分数更新模型。因此 PPO 的数据准备、显卡占用和工程复杂度都明显高于 SFT 和 DPO。

例如，患者问“胸痛需要马上就医吗”，SFT 可以教模型识别急症信号并给出及时就医建议；DPO 可以用医生审核过的安全回答作 chosen；在线 RL 则还需要可靠的医学评分规则，不能只凭回答长短或语气打分。

### 3.2 医疗训练框架负责什么

LLaMA-Factory 可以理解成“训练任务控制台”：你把模型路径、数据集、学习率、batch size、LoRA 和分布式配置写进 YAML，再用 llamafactory-cli 启动。它适合把 SFT、DPO 和 Reward Model 做成可复现的配置文件，作为多数医疗项目的主训练入口。

ms-swift 更像“面向 Qwen 和 ModelScope 的训练工具箱”：它提供 swift sft、swift rlhf 等入口，覆盖 SFT、DPO、Reward Model、GRPO 等任务，并且和 ModelScope 的模型、数据和部署生态衔接更自然。它与 LLaMA-Factory 一起构成医疗项目的两套主方案，可以先用其中一套跑通，再用另一套做对照验证。

OpenRLHF 主要解决“在线强化学习怎么组织”的问题：它需要把 Actor、Reference Model、Reward Model、Critic 和 Rollout 等角色分配到不同 GPU，再用 Ray 协调任务，用 vLLM 加速在线生成。它不作为当前 SFT、DPO 的主方案，只在在线 RL 的工程需求明确、Reward Model 稳定后作为备选。

以六科室问答为例，框架负责把已审核的问答样本接成 SFT 任务；若要优化患者沟通语气，再准备同一问题的优劣回答做 DPO。框架能执行训练，但不会自动判断建议是否符合临床规范。

### 3.3 分布式后端怎样承载医疗模型

DDP 的思路最直观：每张 GPU 都放一份完整模型，每张卡读不同的医疗问答样本，算完梯度后互相同步。它的优点是稳定、配置简单；缺点是每张卡都要装下完整模型和优化器状态。因此小模型、LoRA 和科室数据的快速验证优先用 DDP。

DeepSpeed 的核心是 ZeRO 分片：把参数、梯度和优化器状态分散到多张 GPU，不让每张卡重复保存全部内容。ZeRO-2 主要分片梯度和优化器，ZeRO-3 连模型参数也分片，所以更省显存，但通信和配置成本更高。DeepSpeed 是后端，不是 SFT 或 DPO 的任务框架。

FSDP 是 PyTorch 原生的大模型分片方案，作用和 DeepSpeed ZeRO-3 类似：训练过程中按需聚合参数，计算完成再释放或重新分片。比如医疗机构要对更大的患者对话模型做全参数微调时，才可能需要这类参数分片；已有 PyTorch/FSDP 经验时可以选择它，如果项目更依赖现成的 YAML 和 DeepSpeed 配置，则优先 DeepSpeed。

### 3.4 医疗训练中的调度与运行时组件

Slurm 和 Kubernetes 不负责“模型学什么”，它们负责“哪台机器、哪张 GPU、什么时候启动、失败后怎么办”。PAI-DLC 和 TI-ONE 是云上的托管调度平台，除了调度 GPU，还会帮助创建节点、挂载数据、启动容器、注入 rank 和收集日志。医疗项目还要把脱敏数据、模型权重和训练日志放到经过授权的存储与访问范围内。

Ray 适合在线 RL 的多角色协作：一组 GPU 放 Actor，一组 GPU 放 Reward Model，一组 GPU 运行 vLLM Rollout。例如系统可让模型生成患者问题的回答，再由医学评估器检查安全性。vLLM 负责快速生成回答，NCCL 负责 GPU 间通信，RDMA 或高速互联负责跨机器通信。它们属于运行时和基础设施，不应和 LLaMA-Factory 画在同一层。

LoRA 和 QLoRA 是“少训练一点参数”的方法，能显著降低显存和 checkpoint 成本；梯度检查点是用计算换显存；梯度累积是用多次小 batch 模拟大 batch；BF16 是在支持的 GPU 上减少显存和提升吞吐的数值格式。这些是训练策略，不是集群调度器。Unsloth 可作为单机 LoRA/QLoRA 快速试验的可选优化工具，医疗项目的主训练方案仍以 LLaMA-Factory 或 ms-swift 为主。

## 4 DeepSpeed、DDP 与 FSDP 的区别

选完训练任务后，才轮到分布式后端。DDP、DeepSpeed 和 FSDP 都能支持多卡、多机训练，但它们保存和同步医疗语言模型状态的方式不同；先分清“多卡提高数据吞吐”与“多卡切分模型”，就不会把几张卡的显存直接当作一张大卡。

| 维度 | DDP | DeepSpeed | FSDP |
| --- | --- | --- | --- |
| 模型参数 | 每张卡一份完整模型 | ZeRO-3 时分片保存 | 分片保存 |
| 梯度 | 每张卡完整保存 | ZeRO-2/3 分片 | 分片保存 |
| 优化器状态 | 每张卡完整保存 | ZeRO-1/2/3 分片 | 分片保存 |
| 显存占用 | 最高 | 低到中等 | 低到中等 |
| 通信开销 | 相对较少 | 中等到较高 | 较高 |
| 配置难度 | 低 | 中等 | 中等到较高 |
| 适合场景 | 小模型、LoRA、快速验证 | 大模型、全参数、多机 | PyTorch 原生大模型分片 |

医疗微调的简单判断是：4B/9B LoRA 若单卡放得下，可用 DDP 把多个科室的训练样本并行处理；模型放不下或做全参数微调时，再考虑 DeepSpeed ZeRO-3 或 FSDP。

这里要特别留意：增加 GPU 数量不一定会增加“单个模型可用的显存”。如果使用 DDP，增加卡主要是让更多医疗样本并行处理；只有使用 ZeRO-3、FSDP 或模型并行，模型状态才会在多卡间切分。下一章回到医疗项目本身，按审核、训练和评估顺序把这些选择串起来。

## 5 医疗模型训练微调主流程

![](https://pica.zhimg.com/v2-2168f4ec34806c3ac7b01f732245ab6e_r.jpg)
*图 3  从医疗数据到 SFT、DPO、Reward Model 和在线 RL 的流程*

最稳妥的主线是 SFT → DPO → 评估。Reward Model 和 PPO 是扩展路线，不应在没有医学审核和可靠奖励信号时直接启动。

| 阶段 | 输入数据 | 输出 | 关键风险 |
| --- | --- | --- | --- |
| SFT | instruction / input / output | 医疗助手初始模型 | 数据重复、医学事实错误、格式不一致 |
| DPO | prompt / chosen / rejected | 更符合偏好的模型 | chosen/rejected 质量不高会放大错误 |
| Reward Model | prompt / chosen / rejected | 奖励函数或奖励模型 | 奖励偏差、过度拒答、奖励黑客 |
| PPO/GRPO | prompt + 在线生成 + reward | 在线策略优化模型 | 训练不稳定、幻觉和奖励投机 |

医疗项目的训练顺序通常是：脱敏与去重，医生或规则审核，按患者/病例隔离训练集与评估集，先做 SFT，再用高质量偏好对做 DPO，最后评估事实准确性、急症升级、拒答边界和证据引用。Reward Model 与在线 RL 是进阶路线。明确流程后，再按模型和显存挑硬件；下面的显存建议是规划起点，不是保证值，实际还看上下文长度、batch、模型结构、量化实现和训练器的临时峰值。

## 6 医疗 SFT、DPO 与在线 RL 的框架选择

框架选择要跟医疗训练阶段对应：先用主训练框架把经审核的问答做成 SFT；有稳定偏好对时再做 DPO；只有需要模型在线生成、且已有可靠医学奖励信号时，才考虑在线 RL。以下工具负责执行训练，临床质量仍要靠独立评估。

| 框架 | 主要入口 | 最适合的任务 | 不适合直接承担的事情 |
| --- | --- | --- | --- |
| LLaMA-Factory | llamafactory-cli train | 主方案：SFT、DPO、Reward Model，配置清晰 | 不负责云资源创建 |
| ms-swift | swift sft / swift rlhf | 主方案：Qwen、ModelScope、多种 RLHF 与分布式训练 | 不替代集群调度平台 |
| OpenRLHF | OpenRLHF CLI + Ray | 备选：PPO、GRPO、在线 Rollout、多角色 RL | 不作为当前 SFT/DPO 主线 |

安装包本身都不大，真正占空间的是 PyTorch、CUDA、DeepSpeed、vLLM、Flash-Attention、模型权重和 checkpoint。医疗训练还应给脱敏后的数据、评估集和可恢复 checkpoint 留足受控存储空间。

| 工具 | 安装包量级 | 实际环境的主要空间来源 |
| --- | --- | --- |
| LLaMA-Factory | wheel 约 483 KB | PyTorch、Transformers、训练依赖和模型 |
| ms-swift | wheel 约 1.4 MB | PyTorch、ModelScope、DeepSpeed、可选推理组件 |
| OpenRLHF | wheel 约 198 KB | Ray、DeepSpeed、Flash-Attention、可选 vLLM |

框架决定医疗 SFT、DPO 或在线 RL 怎样配置和启动；真正能训练多大模型，还要看每张卡的显存和是否做分片。下一章先给出模型规模的起步配置，再把单卡、单机多卡和多机多卡拆开说明。

## 7 医疗模型规模与单卡/多卡配置

模型规模要和医疗任务一起看：较小模型可先验证格式统一的科室问答；中等模型可验证多轮患者沟通和风险提示；更大模型适合评估长上下文下的证据整合，但参数更多本身并不保证医学更准确。表中“GPU 数×单卡显存”表示卡数与每张卡显存，例如“4卡×24GB”；默认先用同型号卡，单机装不下再看是否扩到多机，具体显存分配见 7.2。

| 模型规模 | QLoRA（卡数×单卡显存） | BF16 LoRA（卡数×单卡显存） | 全参数微调（卡数×单卡显存） | 建议后端 |
| --- | --- | --- | --- | --- |
| 0.8B | 1卡×8/16GB | 1卡×16GB | 1卡×16/24GB 试跑 | DDP |
| 4B | 1卡×16/24GB | 1卡×24/48GB | 2卡×48GB，需分片 | ZeRO-3 / FSDP |
| 9B | 1卡×24GB | 1卡×48/80GB | 4卡×80GB 起步，需分片 | ZeRO-3 或 FSDP |
| 32B | 1卡×48/80GB | 1～2卡×80GB，需试跑 | 8卡×80GB 起步，需分片 | ZeRO-3 / FSDP |

| 模型 | SFT 怎么做 | DPO 怎么做 | Reward Model | 在线 RL |
| --- | --- | --- | --- | --- |
| 0.8B | LoRA/QLoRA；单机 DDP 或 Unsloth | 同一套单机配置 | 先不做或离线评估 | 适合先验证数据和链路 |
| 4B | LoRA/QLoRA；DDP | DDP；显存不足用 ZeRO-2 | 可用 ZeRO-2 | 有可靠 RM 后再试 |
| 9B | LoRA/QLoRA；DDP 或 ZeRO-2 | ZeRO-2 更稳妥 | ZeRO-2/3 或 FSDP | ms-swift 主选；OpenRLHF 备选 |
| 32B | QLoRA/LoRA；ZeRO-2/3 | ZeRO-2/3 或 FSDP | ZeRO-3/FSDP；需医学审核 | 多机 ms-swift；OpenRLHF 备选 |

以上是以 2048～4096 上下文、batch size 1、开启梯度检查点为前提的启动级估计。实际显存还取决于模型结构、优化器、LoRA rank、梯度累积和量化方式。

对 32B 医疗问答模型，先用 QLoRA 或 LoRA 看验证集上的事实准确性、证据引用和急症建议；只有这些指标有提升且资源充足，再评估全参数微调。全参数方案对网络和 checkpoint 的要求也更高。

### 7.1 医疗模型的单卡显存怎么选

先估算模型权重，再给训练过程留空间。BF16 权重本身大约是每个参数 2 字节，所以 4B、9B、32B 模型的权重约占 8GB、18GB、64GB；这还没有算激活、梯度、优化器和 CUDA 临时空间。4-bit QLoRA 的底座权重约为每个参数 0.5 字节，但量化元数据、激活和训练缓存仍会增加占用。

| 单卡显存 | 建议先试的模型与方法 | 典型设置 | 使用边界 |
| --- | --- | --- | --- |
| 16GB | 0.8B～4B QLoRA；9B 只做压缩配置试跑 | batch 1；短上下文；梯度检查点；4-bit | 9B 可能因上下文或模型实现 OOM；不要按标称 16GB 用满 |
| 24GB | 4B LoRA/QLoRA；9B QLoRA | batch 1；先 2k，再尝试 4k 上下文 | 32B 单卡不作为常规方案；先做一小段真实数据试跑 |
| 48GB | 9B BF16 LoRA；32B QLoRA | batch 1；按显存逐步增加上下文和累积步数 | 32B 的上下文、量化实现会明显影响能否稳定运行 |
| 80GB | 32B QLoRA/LoRA；更大的上下文余量 | 先用目标上下文做单步峰值测试 | 80GB 仍不足以保证 32B 全参数训练单卡完成 |

映射到医疗任务时，16GB 可先做短上下文的小科室问答验证；24GB 是 4B/9B QLoRA 的实用起点；48GB 可试 9B 患者对话或 32B 短上下文 QLoRA；80GB 给 32B 留出更多训练余量。显存刚好够装权重不等于训练就能启动，实际要降低上下文长度和 batch、开启梯度检查点并做单步峰值测试。

![](https://pic3.zhimg.com/v2-750af7ce7a35743fc17edf76d5ab4488_r.jpg)
*图 5  按单卡显存容量选择医疗微调配置，并区分数据并行与参数分片*

### 7.2 单卡、单机多卡和多机多卡怎样区分

先按“机器台数×每台 GPU 数×单卡显存”读配置，再看训练方式。DDP 是每卡各放一份模型，让多个医疗样本并行处理；ZeRO-3/FSDP 会切分模型训练状态，帮助模型跨卡放置。总装机显存只是硬件总量，不等同于一张卡可用的显存，也不自动等于模型训练时可用的显存。

| 机器拓扑（台数×每台卡数×单卡显存） | 训练方式 | 显存实际含义 | 医疗任务示例 | 判断要点 |
| --- | --- | --- | --- | --- |
| 1台×1卡×24GB | 单卡 LoRA/QLoRA | 模型、激活和训练状态都由这张24GB卡承载 | 4B 科室 FAQ 或短上下文问答试跑 | 先确认权重、上下文和 batch 的峰值 |
| 1台×4卡×24GB（总装机96GB） | DDP | 每卡仍是24GB，四卡各有完整模型副本；96GB不等于单卡 | 4B/9B 样本并行训练，提高吞吐 | 适合模型单卡放得下、想加快处理时 |
| 1台×4卡×24GB（总装机96GB） | ZeRO-3/FSDP | 模型状态分片到四卡；激活仍占每卡空间，需通信聚合 | 试做较大患者对话模型或全参数微调 | 先确认模型/训练器支持并实测峰值 |
| 2台×每台4卡×80GB（总装机640GB） | 跨机 DDP | 每卡保留完整模型副本，单卡预算仍按80GB算 | 多科室问答数据量大、单机吞吐不足 | 主要增加并行吞吐，需稳定高速网络 |
| 2台×每台4卡×80GB（总装机640GB） | 跨机 ZeRO-3/FSDP | 模型状态分布在8卡；跨机通信和 checkpoint 都要规划 | 32B 全参数训练的起步评估配置 | 不是保证能跑；按模型、序列长度和优化器试跑 |

最重要的对照是：单卡看这张卡能否独立承载训练；单机多卡 DDP 看每卡能否装下模型，卡数主要带来吞吐；单机或多机的 ZeRO-3/FSDP 才把模型状态切分。跨机训练还要把网络和存储算进去。

特别注意 ZeRO-2 和 ZeRO-3 的边界：ZeRO-2 可以切分梯度和优化器状态，但模型参数仍通常在每张卡保留完整副本；模型权重本身装不进单卡时，要看 ZeRO-3、FSDP 或其他模型并行方案。

### 7.3 混合显存显卡怎样安排医疗训练

同一训练作业里的 GPU 不只是把显存加总。DDP 下每张卡都持有同一个模型副本；分片训练下，各 rank 还要按相同的通信节奏交换参数和梯度。显存大小、算力和网络差异过大时，小卡容易先 OOM，慢卡则会让其余 rank 等待。

| 机器与显存拓扑 | 主要限制 | 推荐的医疗训练安排 |
| --- | --- | --- |
| 1台：1×16GB + 1×24GB | 16GB 卡限制模型、上下文和 batch；同步任务也会受慢卡影响 | 分开跑小型科室问答和 4B QLoRA；必须同跑时按16GB配置并实测 |
| 1台：1×48GB + 1×80GB | DDP 按48GB卡配置；80GB多出的空间不会转给另一张卡 | 48GB卡跑9B LoRA，80GB卡单独验证32B QLoRA；不要误当成128GB单卡 |
| 2台资源池：1台×8卡×80GB；1台×8卡×24GB | 合并成一个16卡作业后，小卡或慢节点会限制整组 | 80GB节点做大模型或长上下文，24GB节点做小模型/短上下文任务，分作业提交 |
| 多台机器分别有16/24/48/80GB卡 | 显存、算力和跨机网络差异叠加；每步可能等待最慢 rank | 按卡型建资源池，同一次医疗训练尽量使用同型号、同显存卡 |
| 混卡作业 + ZeRO-3/FSDP | 标准分片通常按 rank 切分，不会自动按显存大小分配不同分片 | 只有明确支持异构分片时才联合；先测每个 rank 的峰值显存和步时 |

例如一台医疗研发服务器有1张80GB、2张24GB和1张16GB卡，可以把80GB卡留给较大的证据问答模型，把24GB和16GB卡用于不同科室的小型 QLoRA 实验。跨机器混卡并非绝对不能通信，但框架、驱动、CUDA、NCCL 和网络必须兼容；如果目标只是完成常规微调，按 GPU 类型拆成独立作业池通常更省心。

### 7.4 医疗数据量、模型量和机器量要一起判断

这三个“规模”解决的是不同问题。模型参数量和上下文长度决定单步训练需要多少显存；数据量决定训练要跑多少步、是否值得扩到多机；GPU 数量和网络决定这些显存与计算能否被分摊。不能因为数据有几千条，就直接推导出要上几十台机器。

如果一个医疗项目只有几千条高质量样本，且基座模型在 0.8B～4B，最大的风险通常是数据质量和训练格式，而不是吞吐不足。此时应先用单机多卡或单卡完成小规模试跑，确认 loss、验证集和医学安全指标，再决定是否扩大模型。

| 数据与任务规模 | 模型规模 | 优先方案 | 什么时候升级 |
| --- | --- | --- | --- |
| ≤1 万条或少于约 5000 万 token；离线 SFT/DPO | 0.8B～4B | 单机；QLoRA/LoRA；DDP 或 Unsloth；LLaMA-Factory/ms-swift | 单步试跑稳定但训练时间过长时，再增加 GPU |
| 1 万～10 万条；需要反复实验 | 4B～9B | 单机 2～8 卡；LoRA/QLoRA；DDP，显存不足用 ZeRO-2 | 吞吐或显存成为瓶颈时扩到 2～8 台 |
| 10 万条以上或超过约 10 亿 token；正式生产训练 | 9B～32B | DeepSpeed ZeRO-2/3 或 FSDP；共享存储；断点续训 | 需要稳定多机网络、统一镜像和监控 |
| 在线生成、奖励打分、持续采样 | 任意，通常 9B 以上更复杂 | ms-swift 主选；OpenRLHF + Ray + vLLM 备选 | 只有 Reward Model 和评估器可靠后再启动 |

![](https://pic1.zhimg.com/v2-293ef77c9492535556c794a5fa7c91f2_r.jpg)
*图 6  根据医疗任务 数据 模型和硬件条件选择训练方案*

因此，医疗项目可以先按模型和 GPU 显存定一个安全配置，再根据样本数量与训练时长决定要不要加机器。多机扩容主要解决吞吐和分片问题；如果数据本身只有几千条，盲目增加机器并不会让医学答案更可靠。

## 8 医疗训练该选单卡、单机多卡还是多机集群

显存方式清楚后，再决定要不要把医疗训练放到集群。单卡适合小规模数据管线和基线验证；单机多卡可提高吞吐，或用 ZeRO/FSDP 分片；只有显存、吞吐或训练时间确实需要跨节点时，才引入多机通信。若样本含有真实患者信息，应先完成脱敏、权限和存储环境审核，再选择自建或云端资源。

![](https://pic4.zhimg.com/v2-eeda341bdbd3530285d3f2040b92d59d_r.jpg)
*图 7  医疗训练在不同机器规模下的推荐技术路线*

| 资源拓扑 | 推荐架构 | 医疗任务示例 | 关键注意点 |
| --- | --- | --- | --- |
| 1台×1卡 | LLaMA-Factory/ms-swift + 单卡 LoRA/QLoRA | 小批量 cMedQA2 或科室问答基线 | 先核对单卡显存；只用脱敏/获批数据 |
| 1台×2～8卡 | LLaMA-Factory/ms-swift + DDP 或 DeepSpeed | 多科室 SFT/DPO；9B/32B QLoRA | 说明是提吞吐还是做分片；checkpoint落到持久存储 |
| 2～8台×每台多卡 | Slurm/PAI-DLC/TI-ONE + DeepSpeed/FSDP | 正式 SFT/DPO；32B 全参数试训 | 同镜像、共享存储、NCCL；跨机优先高速网络 |
| 几十台 | Slurm/Kubernetes + DeepSpeed/FSDP/Megatron | 多模型、多科室批量训练或大模型实验 | 统一镜像、配额、容错、断点续训和审计日志 |
| 约200台 | Slurm/Kubernetes/KubeRay + ms-swift；OpenRLHF备选 | 大规模在线 RL 或超大模型训练 | 先核算数据与任务价值，再建设RDMA和集群运维 |

这里的“单机多卡”和“多机多卡”不是同一件事：单机多卡主要走本机 GPU 互联；多机多卡还要考虑节点间网络、共享数据和调度器。医疗数据质量与医生审核仍是模型效果的基础，集群只负责把既定训练任务跑起来。

## 9 医疗训练在阿里云与腾讯云的调配方式

确定医疗数据的存放位置和训练是否跨机后，再选择调度入口。PAI-DLC 和 TI-ONE 负责申请 GPU、创建节点、挂载数据、启动容器、注入分布式环境变量和收集日志；SFT/DPO 任务仍由 LLaMA-Factory 或 ms-swift 执行。项目上线前还需确认数据访问权限、日志脱敏和 checkpoint 的保存范围。

| 平台 | 适合的调配方式 | 训练入口 | 更适合的场景 |
| --- | --- | --- | --- |
| 阿里云 PAI-DLC | 配置资源配额、节点数、镜像、数据集挂载和启动命令 | torchrun / DeepSpeed / MPI / LLaMA-Factory | 托管多机 SFT/DPO、DeepSpeed 训练 |
| 腾讯云 TI-ONE | 配置资源组、实例组、镜像、存储和 DDP/MPI/Ray 模式 | DDP / MPI / Ray / ms-swift；OpenRLHF 备选 | 托管多机训练和 Ray 在线 RL |
| 自建 Slurm | 一份 sbatch 提交脚本，调度器自动生成 rank | torchrun / DeepSpeed / ms-swift | 固定集群、多人共享、反复训练 |
| Kubernetes/KubeRay | 提交 Job 或 Ray 集群 YAML | ms-swift 在线 RL；OpenRLHF + Ray + vLLM 备选 | 弹性资源、在线 RL、多角色训练 |

多机医疗训练至少需要：相同容器环境、相同代码版本、获准访问的脱敏模型训练数据、可写的 checkpoint 路径、开放的通信端口和稳定的 NCCL 网络。大规模训练优先选择 RDMA 或同等能力的高速互联，并限制训练日志中不必要的患者信息。

## 10 按医疗任务规模确定机器数量

机器数量是最后一步的选择。先用单卡显存确定可行的医疗微调方式，再看同规格 GPU 能否提供足够吞吐；如果机器规格不一致，优先按资源池拆分科室实验，不要为了凑卡数把所有节点硬拼在一起。

| 机器规模 | 训练方案 | 调度方式 | 建议 |
| --- | --- | --- | --- |
| 1台×1卡 | 单卡 LoRA/QLoRA | 直接运行训练入口 | 小型科室问答基线、格式验证 |
| 1台×2～8卡 | 模型单卡能放下用 DDP；放不下再看 ZeRO/FSDP | torchrun/DeepSpeed | 多科室离线 SFT/DPO，优先同型号卡 |
| 2～8台×每台多卡 | DeepSpeed ZeRO-2/3 或 FSDP | Slurm、PAI-DLC 或 TI-ONE | 正式 SFT/DPO；跨机时确认数据和网络 |
| 几十台 | DeepSpeed/FSDP/Megatron；在线 RL 用 Ray | Slurm 或 Kubernetes | 多模型和多科室任务；建设统一镜像、监控与审计 |
| 约200台 | 大模型并行或 ms-swift 在线 RL；OpenRLHF 备选 | Slurm/Kubernetes/KubeRay | 仅在数据、模型与训练目标都证明需要时扩容 |

约200台机器能提供更高并行度，但对只有几千条样本的医疗项目通常不应作为起点。先用单卡或单机多卡验证医学数据、评估指标和训练流程；只有训练时间、模型状态或在线采样规模成为明确瓶颈，再逐步扩到多机。

## 11 医疗训练作业的启动方式

单卡任务只需指定医疗模型、经审核的数据和训练配置；单机多卡再启用分布式启动；多机时由 Slurm 或云平台为各节点注入 rank、节点数和主节点地址。下面的多机变量是启动结构示意，不能把 NODE_RANK=0 原样复制到每个节点。

FORCE_TORCHRUN=1 \<br>NNODES=2 \<br>NODE_RANK=0 \<br>MASTER_ADDR=192.168.0.1 \<br>MASTER_PORT=29500 \<br>llamafactory-cli train config.yaml

在 Slurm 中，MASTER_ADDR、NNODES 和 NODE_RANK 应由 sbatch/srun 环境自动生成；在 PAI-DLC 或 TI-ONE 中，平台通常会注入对应的 rank、节点数和主节点地址。

# 通用医疗项目的入口示意<br>MODEL_PATH=/path/to/medical-model \<br> llamafactory-cli train configs/medical_sft.yaml<br><br>MODEL_PATH=/path/to/medical-model \<br> swift sft --dataset data/medical_sft.jsonl

医疗在线 RL 主方案优先考虑 ms-swift；如果需要更强的多角色 Rollout 编排，再把 OpenRLHF 作为备选。两者都要额外准备 Ray、vLLM、Reward Model 和医学评估器，不能只把普通 DPO 数据直接替换成 PPO。

## 12 医疗项目的分阶段落地建议

先用单卡或 AutoDL 单机多卡完成 4B/9B 的 SFT 和 DPO，检查患者问答、科室覆盖、急症建议和拒答边界；再用 32B QLoRA/LoRA 判断更大模型是否改善证据整合；只有显存、吞吐或数据规模确实要求跨机时，才迁移到 PAI-DLC、TI-ONE 或 Slurm。Reward Model 和在线生成链路通过医学评估后，再投入 PPO/GRPO。

| 阶段 | 模型与资源 | 技术选择 | 验收重点 |
| --- | --- | --- | --- |
| 阶段一 | 4B/9B；单机1～4卡 | LLaMA-Factory 或 ms-swift + DDP | 医生审核、医学准确性、患者安全边界 |
| 阶段二 | 9B/32B；单机4～8卡 | ms-swift 或 LLaMA-Factory + DeepSpeed | 显存、吞吐、证据引用、checkpoint |
| 阶段三 | 32B；多机2～8台 | DeepSpeed ZeRO-2/3 或 FSDP | NCCL、断点续训、脱敏数据权限 |
| 阶段四 | 在线 RL；多机 | ms-swift 主选；OpenRLHF + Ray + vLLM 备选 | 医学奖励信号、训练稳定性、急症安全评估 |

至此，方案从医疗数据、训练目标一路落到显卡拓扑、云端调度和医学验收。真正训练前仍要在目标平台验证工具版本、单步显存、吞吐、断点续训和医学安全评估；技术方案说明本身不等于云上训练已经完成。
