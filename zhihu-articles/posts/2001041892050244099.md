论文：[MiniCPM4: Ultra-Efficient LLMs on End Devices](https://arxiv.org/pdf/2506.07900)

![](https://pica.zhimg.com/v2-a28a8e1a633174fe0cb69e6a173747e8_r.jpg)

这篇论文 MiniCPM4 的核心贡献是：如何在极其有限的端侧资源（手机 和 PC）上，跑得动长上下文、强推理能力的模型，且性能不输云端大模型。

他们不仅发布了模型（8B 和 0.5B），更重要的是公开了一整套从架构、数据、训练到推理系统的优化方案。

---

## 1. 核心亮点

MiniCPM4-8B 在仅使用 8T tokens 训练的情况下（相比 Qwen3-8B 的 36T 数据，仅用了 22% 的数据量），达到了与之相当的性能。在端侧设备上处理 128k 长文档时，速度提升了 7倍。

**关键技术栈：**

- **架构：** InfLLM v2（可训练的稀疏注意力机制）。
- **数据：** UltraClean（高效预训练数据清洗） & UltraChat v2（推理密集型合成数据）。
- **训练：** ModelTunnel v2（超参搜索）、Chunk-wise Rollout（RL 训练加速）、BitCPM4（三值化模型 QAT）。
- **推理：** FR-Spec（词频感知的投机采样）、P-GPTQ（前缀感知的量化）。

## 2. 架构创新：InfLLM v2

![](https://picx.zhimg.com/v2-7661612e94de2bae0661b649b75cd469_r.jpg)

这是模型变快的核心。传统的 Attention 是 $O(L^2)$ 的复杂度，长文推理显存和计算都扛不住。

MiniCPM4 提出了 InfLLM v2，实现了 Prefill 和 Decoding 两部分的加速。

### 2.1 核心机制

它将 KV Cache 分成 Block，并通过两个阶段计算注意力：

1. **Contextual Block Selection（上下文块选择）：** 动态选择与当前 Query 最相关的 KV 块。
2. **Sparse Attention Computation（稀疏注意力计算）：** 只算选中的块 + 初始块 + 局部窗口块。

### 2.2 关键技术点

为了高效计算块的相关性分数 $r_{block}$，它引入了 Semantic Kernels。

- **语义核：** 将 KV 序列切得更细（大小 $p$，步长 $s$），用 Mean Pooling 计算表示。
- **相关性公式：** Query $q_i$ 与 Block $B_j$ 的相关性，由与该 Block 相交的所有语义核的最大相关性决定：

$r_{block}(q_i, B_j) = \max r_{kernel}(q_i, S_{\hat{j}}), \quad S_{\hat{j}} \in \mathcal{S} \text{ and } B_j \cap S_{\hat{j}} \neq \emptyset$

$r_{kernel}(q_i, S_{\hat{j}}) = \text{softmax}(q_i \cdot \text{Mean}(K_{\hat{j}s:\hat{j}s+p}))$

- **Top-K 共享：** 为了减少显存访问，同一个 Query Group 内的 Heads 共享同一组 Top-K 块。

> **为什么是可训练？** 虽然 Top-K 选择本身不可导，但 Semantic Kernel 的表示是基于 Key 的 Mean Pooling，这保持了与 Token 空间的一致性，可以通过优化 Token-level Key 向量间接优化选择过程。

## 3. 数据工程：以质换量

![](https://picx.zhimg.com/v2-75e6e96c2285eb22999d741100bedcbf_r.jpg)

MiniCPM4 用很少的数据训练出强模型，靠的是极高的数据质量。

### 3.1 UltraClean：高效预训练数据过滤

传统的做法是用一个小模型跑一遍数据算 Loss 来过滤，但验证成本太高（验证一次通常需要跑 100B tokens）。

- **高效验证策略：** 他们发现不需要从头训练。先训练一个 1B 模型到稳定阶段，然后利用 WSD Scheduler 的 Decay 阶段，混入待验证数据进行退火训练。这样只需要跑 10B tokens 就能验证数据质量，效率提升 10 倍。
- **流程：** 验证种子数据 $\rightarrow$ 训练 FastText 分类器 $\rightarrow$ 全网清洗。

### 3.2 UltraChat v2：合成数据增强

针对 SFT 阶段，重点构建了推理密集型数据：

- **数学/代码：** 通过 LLM 改写、生成多解法、多测试用例验证。
- **长文本：** Small-to-Big 检索。给定一个文档，检索相关和不相关的文档混合，强迫模型在长 Context 中大海捞针。
- **工具调用：** 包含代码解释器和 Function Calling 数据。

## 4. 训练算法优化

4.1 ModelTunnel v2 & $\mu P$

如何在小模型上调参，直接迁移到大模型？

- 使用 $\mu P$ (Maximal Update Parametrization) 架构。
- **改进指标：** 不再只看 Language Modeling Loss，而是构建了 ScalingBench，发现 ScalingBench 的 Loss 与下游任务性能呈 Sigmoid 关系，预测更准。

### 4.2 RLHF 训练：Chunk-wise Rollout

这是一个针对长 CoT训练的工程优化。 在 RL 训练（如 GRPO）中，Rollout 阶段如果有的样本长、有的短，GPU 会有大量空转。

- **策略：** 设定一个固定的 Chunk 长度（如 4k）。
- **稳定性技巧：** 为了解决分块生成导致的数据分布偏移（不同 Chunk 可能来自不同版本的 Policy），引入了 Chunk-level Importance Sampling 和 Dual-clip 策略。
- **目标函数（修正版 GRPO）：**

$\mathcal{J}(\theta) = \mathcal{J}_{clip}(\theta) - \beta \cdot D_{KL}(\pi_\theta || \pi_{ref})$

其中引入了 Token 级别的 Advantage 计算，而不是整句平均，鼓励更细粒度的奖励。

### 4.3 BitCPM4：三值化模型

训练 1.58-bit ({-1, 0, 1}) 模型通常需要从头训练。MiniCPM4 发现可以用 FP 模型初始化，然后通过 QAT 微调。

**结论：** 只需要原本 Decay 阶段 2 倍的数据量，就能把 FP 模型转成高性能的三值化模型，比从头练 BitNet 节省 90% 的 Tokens。

## 5. 推理系统

为了在端侧极致加速，他们不仅改了模型，还手写了 CUDA 内核。

### 5.1 FR-Spec (词频排序投机采样)

投机采样需要一个草稿模型。通常草稿模型的瓶颈在于最后一层 LM Head 的词表太大（比如 100k+），导致计算慢。

- **发现：** 自然语言符合长尾分布，Top-25% 的高频词覆盖了 95% 的情况。
- **做法：** 草稿模型的 LM Head 只预测高频词。
- **效果：** 既然草稿模型只是用来猜的，猜不准低频词没关系（Target Model 会修正），但速度大大提升。

### 5.2 P-GPTQ (前缀感知量化)

在做 PTQ 时，通常需要计算 Hessian 矩阵 $H = X^T X$。

- **问题：** 句子开头的几个 Token（BOS 等）激活值异常大（Outliers），会主导 Hessian 矩阵的计算，导致量化参数对后续 Token 不准确。
- **P-GPTQ：** 计算 Hessian 时，直接扔掉前 $s$ 个 Token（例如前 4 个）。这简单的一步操作，显著提升了量化模型的 PPL。

## 6. 实验结果与应用

### 6.1 性能评估

- **基准测试：** MiniCPM4-8B 在 MMLU、GSM8K 等榜单上与 Qwen3-8B、Llama3.1-8B 互有胜负，但训练成本大幅降低。
- **长文本：** 在 RULER 基准测试中，即使使用了 81% 稀疏度的 Attention，性能几乎没有下降（加权平均分 88.93 $\to$ 85.84）。

### 6.2 应用场景

- **MiniCPM4-Survey：** 这是一个端侧的学术综述生成 Agent，利用了模型的长文本能力，采用 Plan-Retrieve-Write 流程。
- **MiniCPM4-MCP：** 适配了MCP。这是一个标准化的 Agent 协议，让模型能以统一的方式连接本地和远程工具（如读取本地文件、操作 GitHub 等）。

## 个人感受

1. **架构即效率：** InfLLM v2 证明了可训练的稀疏注意力是解决端侧长文瓶颈的可行路径。
2. **数据质量 > 数量：** 8T 数据打平 36T 数据，再次验证了 Data-Centric AI 的核心论点。
3. **系统与算法协同：** FR-Spec 和 P-GPTQ 这种优化，必须结合具体的推理系统实现才有意义，算法设计必须考虑硬件特性。

对于想要在移动端部署 GenAI 应用的开发者来说，MiniCPM4 提供了一个非常有价值的参考范本。
