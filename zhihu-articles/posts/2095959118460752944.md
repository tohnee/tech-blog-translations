## 1.背景

vllm的变化确实是很快，这几个月因为忙其它的，都没怎么看太多代码，最近一看，又是天差地别了。想更新一下vllm的kv cache管理这块内容。上一篇 [vllm v1代码走读-kv cache管理](https://zhuanlan.zhihu.com/p/1931739777427829216)讲了kv cache的初始化、block pool和prefix caching。vllm会先分配好物理内存，运行时根据请求需要分配block id，请求结束后再释放回block pool。如果两个请求有相同的前缀，还可以复用已经计算好的kv。

之前主要考虑的是各层都保存历史kv的情况，用一张请求的block table就可以把分配和回收过程讲清楚。但是现在很多模型在不同层上使用了不同的attention，有的需要保存全部历史，有的只需要最近一个窗口，还有的保存的是不断更新的状态。同一个请求在这些层上需要多少空间、什么时候可以释放，就不一样了。因此，vllm针对kv cache的管理又做了很多变化。

这篇先看KVCache分组和递推状态，再看初始化时的一整块内存是怎么分配的，各层数据有哪些排列方式，以及分组后的prefix caching。最后用DeepSeek V4/V4.1的例子，把缓存组成、分组分配和前缀恢复放在一起看。下面讨论的是单个EngineCore下的普通GPU缓存池，开启hybrid管理。

## 2.KVCache分组

### 2.1 全局缓存与SWA

以DeepSeek V4.1 Flash为例，它的attention会用到SWA和global KV两部分缓存。SWA保存窗口内token的kv，随着请求往后执行，退出窗口的旧块就可以释放。Global KV保存供全局检索使用的历史记录，这些记录后面的token还可能用到，不能跟着SWA窗口一起释放。

在vllm的实现中，每层的SWA单独保存，global KV由来源层保存，使用它的后续层直接读取同一份内容。也就是说，一个层可能同时使用不同类型的缓存，各种缓存需要分别记录block和判断回收时间。如果都保留全部历史，SWA就占着用不到的空间；如果都按窗口释放，global KV后面还要读取的历史就丢了。

这里的global KV还涉及压缩、索引选择和跨层共享，第6节再展开，它和普通full attention逐token保存、读取全部历史kv的方式不同。Gemma 3则是另一种组合：一部分层使用full attention，另一部分层使用SWA。这种情况下，full层保留历史kv，SWA层按窗口回收，同样需要分开管理。

### 2.2 KVCacheGroup

每个缓存模块都维护一张block table当然也可以，但如果很多模块的分配和回收规则相同，就没有必要重复记录这些信息。vllm把这类缓存放到一个KV cache group中，同一组的缓存模块共用请求的block table。

例如两个full attention层都使用`[7, 21, 44]`这几个block id。每个id会给组内每一层各留一页，两个层的kv仍然分别存放。也就是说，共用的是block id列表，每层在这些id对应的位置上保存自己的数据。

一个缓存模块属于哪个group，要先看它返回的`KVCacheSpec`。Spec里包括block size、每页字节数、窗口大小或状态类型。初始化时根据这些信息分组，页大小相同的模块也不一定能放到一起，还要满足窗口、block size和缓存类型的要求。同一种类型也可能因为内存打包需要拆成多个group，打包方式在第4.5节介绍，第6.5节再看具体分组。

分组后，每个group会创建自己的manager。下面是 KVCacheCoordinator 中这部分代码，其他构造参数合并到了`common_args`：

```text
self.single_type_managers = tuple(
    get_manager_for_kv_cache_spec(
        kv_cache_spec=group.kv_cache_spec,
        kv_cache_group_id=i,
        block_pool=self.block_pool,
        role=group.role,
        **common_args,
    )
    for i, group in enumerate(kv_cache_config.kv_cache_groups)
)
```

（1）`group.kv_cache_spec`决定使用哪一种manager，例如full、SWA和递推状态会有不同的处理方式。

（2）`kv_cache_group_id`记录组号，每个manager维护本组的`request_id → blocks`，判断请求需要增加或释放哪些block。

（3）这里传入的是同一个`self.block_pool`。各组从同一个池里申请id，一组释放的id可以再分配给另一组。

Scheduler仍然通过`KVCacheManager`申请空间，由coordinator收集各组的需求，再交给各组manager处理。

### 2.3 block分配与回收

先用一个普通full group和一个SWA group看下回收过程，假设两组的block size都是32，SWA的窗口大小是128。这里用的是简化参数，具体模型的分组和block size后面再看。

现在请求已经处理完token 0～159，两组都用到了逻辑block 0～4，接下来要处理token 160。对于full group，前面的kv都要保留，还需要为逻辑block 5申请一个新的id。

SWA group需要的窗口则是33～160。逻辑block 0存的是token 0～31，已经全部退出窗口，可以释放；逻辑block 1存的是32～63，其中33～63还要读取，所以这块仍然要保留。释放block 0后，再准备逻辑block 5的空间。

如下图，假设旧的逻辑block 0使用id 5，释放后，新的逻辑block 5又从block pool中申请到了id 5。

![](https://pic4.zhimg.com/v2-13c65399c0b86da47f61eecb396b8a13_r.jpg)

这两次使用发生在不同时间，full group此时使用的是其他id。同一个id在同一时刻只会分给一个group。Manager会把已释放的旧位置替换成`null_block`，保留块表中的逻辑下标，这样后面的下标仍然对应原来的token区间。Worker块表的旧列即使还留着数字，也已经不在有效读取范围内。

释放时还要等之前安排的读取完成，才能把空间交给后面的写入。对于一次处理很多token的prefill，中间步骤也要读取各自窗口内的数据，因此可能暂时需要比最终窗口更多的页。这部分由 SlidingWindowManager处理。

## 3.递推状态管理

### 3.1 Gated DeltaNet

Qwen3-Next同时使用Gated DeltaNet和gated attention，其中Gated DeltaNet层需要保存递推状态，下一步的状态由上一步的状态和新的输入计算得到，简单表示就是`S_t = update(S_(t-1), x_t)`。这个式子只表示更新关系，具体计算还要看Gated DeltaNet的实现。

普通attention每处理一个token，就增加一份历史kv。递推层则是在原来的状态上更新，状态的形状由模型确定。例如上下文从1K增加到10K，这份状态不会跟着增加到十倍；模型还可能另外保存短卷积需要的历史状态。

这类层的内存大小要根据状态张量计算，不能再直接用token数乘每个token的kv大小。

### 3.2 MambaSpec

vllm的Gated DeltaNet实现继承了`MambaBase`，使用其中的状态缓存接口，通过`MambaSpec`描述要保存的张量。Gated DeltaNet和Mamba的模型算法不同，这里共用的是状态的分配、保存和恢复代码。

下面看下`get_kv_cache_spec()`，只保留状态大小和缓存模式相关的字段：

```text
def get_kv_cache_spec(self, vllm_config):
    cache_config = vllm_config.cache_config
    return MambaSpec(
        shapes=tuple(self.get_state_shape()),
        dtypes=self.get_state_dtype(),
        block_size=cache_config.mamba_block_size,
        mamba_cache_mode=cache_config.mamba_cache_mode,
    )
```

（1）`shapes`和`dtypes`记录各个状态张量的形状和类型，用来计算一份状态占多少字节。

（2）`block_size`用来对齐状态检查点对应的token位置。这里一页保存的是状态，不能按普通attention理解成每个token各有一份kv。

（3）`mamba_cache_mode`决定状态怎么保存和复用。计算容量时还要考虑padding、投机解码和额外检查点。

例如`align`模式的容量上限会计入两份基础状态，再加上配置要求的speculative/checkpoint blocks；其他模式的基础持有量不同。所以一份状态的大小固定，并不表示一个请求只需要一个block，具体计算在MambaSpec中。

### 3.3 状态检查点

假设请求A已经处理完200个token，现在来了请求B，它的前128个token与A相同。对于full attention，前128个token的kv还在就可以复用。递推层需要的则是处理完128个token时的状态`S128`，A当前的`S200`不能直接拿来用。因此A在继续更新工作状态之前，需要把某些位置的状态另外保存下来，供后面的请求恢复，这些保存下来的状态就是检查点。`S128`中的128表示已处理的token数，与物理block id无关。

vllm不会在每个token位置都留一份检查点。先看前面`MambaSpec`里的`block_size`，它来自`mamba_block_size`，可以通过`--mamba-block-size`传入。开启prefix caching且没有指定时，这个值先跟随attention的`block_size`。对于混合模型，初始化还会根据状态页大小和backend要求调整block size，在相应的`align`路径中同步修改`mamba_block_size`。

不同组还要能从同一个token位置继续计算。不开启细粒度命中时，混合模型使用`scheduler_block_size`作为公共对齐粒度，它是各组有效block size的最小公倍数。下面都假设开启prefix caching，采用`align`模式，不使用EAGLE和块内细粒度命中，初始化后的状态块大小和公共对齐粒度都是128个token。

有了对齐粒度，还要决定在哪些位置保留状态。这部分由`prefix_cache_retention_interval`控制，命令行参数是`--prefix-cache-retention-interval`。默认值0表示不额外按固定间隔保留检查点，vllm会根据已知的prompt长度和缓存查询结果选择位置，主要有下面两种情况。

（1）相同prompt再次请求。假设A的prompt有200个token，再次请求时最后一个token需要重算以得到logits，因此最多复用前199个token。按128对齐，得到`199 // 128 * 128 = 128`，vllm就选择保留`S128`。这里由`replay_boundaries()`提供prompt末尾的位置，`MambaManager.reachable_block_mask()`向下对齐并选中对应的状态块。如果prompt有300个token，对齐粒度仍然是128，保留的位置则是`299 // 128 * 128 = 256`，对应`S256`。

（2）查缓存时发现共享前缀。再看一个更长的请求：full attention可以命中已有缓存的前384个token，递推层却只能找到`S128`。vllm由此知道384这个位置缺少可复用的状态，把它记到请求的`shared_prefix_boundary`。这次请求仍要从128继续计算；调度器在符合条件的位置切分计算，生成并保留`S384`，后面共享这段前缀的请求才有机会从384恢复。这里用到的是已经观察到的共享前缀，vllm无法提前知道未来请求会在哪里分叉。

上面的两种情况如下图所示。灰色空心圆表示对齐位置，绿色圆点表示实际保留的检查点。

![](https://pic2.zhimg.com/v2-d73691b895d8333b62bebd1a333dcb19_r.jpg)

如果还想为其他可能的前缀保留检查点，可以设置`prefix_cache_retention_interval`。例如上面的对齐粒度为128，设置`--prefix-cache-retention-interval 1024`，就会在前面两类位置之外，再选择1024、2048等周期边界保留状态。这个间隔必须是`scheduler_block_size`的整数倍。设成`None`则按可缓存边界密集保留，也不表示每个token都存一份。

### 3.4 状态复用与copy-on-write

回到前面的例子，假设128是允许保存检查点的位置，而且`S128`已经保存、尚未淘汰，B就可以用它作为接下来计算的初始状态。

如果A和B的前150个token相同，但可用的检查点只有`S128`，没有`S150`，只看递推层，就需要先从`S128`恢复，再计算剩下的22个token，得到当前工作状态`S150`。保留更多检查点，可能省下的重算就更多，但也会多占缓存空间。

A和B在共同前缀之后会继续处理各自的token，状态也会分别更新。如果直接修改共享的`S128`，就会破坏其他请求要复用的内容，因此继续写入时要使用各自的工作状态，如下图所示。

![](https://pic2.zhimg.com/v2-4885942c805bc4d7c58b00bc349b8ba3_r.jpg)

当后续写入需要修改命中的共享块时，vllm会先做copy-on-write。下面看下`MambaManager`的`align`路径中新请求命中块内前缀检查点的分支，把新块分配和`_apply_cow()`放在一起，省略块数量计算、断言及其他分支：

```text
new_blocks = self.block_pool.get_new_blocks(num_new_blocks)
if partial_hit is not None and not blocks_allocated:
    block_idx, source_block = partial_hit
    cow_block = new_blocks[0]
    self._apply_cow(request_id, block_idx, source_block, cow_block)

def _apply_cow(self, request_id, block_idx, source_block, cow_block):
    req_blocks = self.req_to_blocks[request_id]
    req_blocks[block_idx] = cow_block
    self._pending_cow_copies.append((source_block, cow_block))
    cow_block.ref_cnt += 1
```

（1）`partial_hit`记录需要复制的命中块，`blocks_allocated`为False表示请求还没有进入持续运行的分支。新块数量已经把这次copy-on-write算进去，从中取出`cow_block`作为请求自己的状态块。

（2）把请求块表中原来指向`source_block`的位置改成`cow_block`，再把源块和目标块加入待复制列表。这里还没有复制状态，实际复制由worker在forward读取新块之前完成。

（3）源块保留命中时取得的引用，目标块则在请求持有的引用之外再加一次引用。这样即使请求在同一调度步被释放，两块空间也不会提前回到池里供其他请求使用。复制完成后，再释放这部分临时保留的引用。

## 4.KVCache初始化与内存布局

### 4.1 block数量计算

上一篇计算block数量的公式如下：

`num_blocks = available_memory // page_size // num_layers`

各层的page size相同，每个block id都要给每层各准备一页，所以用可分配内存除以page size，再除以层数，就得到总的block数量。现在不同缓存模块的page size可能不同，而且full、SWA和状态缓存申请的block数量也不同，需要根据group的组成重新计算。

如果每种缓存都分一块固定大小的池，可能会出现full的池已经用完，SWA的池还空着，但full不能申请这部分空间的情况。前面说过，hybrid管理下各组共用一个block pool。初始化时，要给这个池的每个id安排好实际的字节位置。下面看内存怎么分配、数据怎么排，以及一个id需要多少字节。

### 4.2 内存分配

上一篇讲到，vllm会在初始化的时候给每一个layer分配一块连续的内存。现在这部分实现有了变化，会先给当前worker的kv cache申请一整块内存，再根据各层的布局构造tensor view。各层拿到的还是各自的tensor，但是底下用的是同一块内存。

初始化时，根据KV cache可用内存、各组spec和选定的布局，计算出`num_blocks`以及每个id需要的字节数。最终申请大小是`size = num_blocks × bytes_per_block`。

下面看下`allocate_kv_cache()`中这部分代码。这里把逐层查找spec简化成`specs`字典，只保留需要通用层view的分支，省略了平台对齐和kernel block细分参数：

```text
sizes = {tensor.size for tensor in kv_cache_config.kv_cache_tensors}
assert len(sizes) == 1
buf = torch.zeros(sizes.pop(), dtype=torch.int8, device=device)

kv_caches = {}
for tensor in kv_cache_config.kv_cache_tensors:
    spec = specs[tensor.layers[0]]
    views = create_kv_cache_views(
        buf,
        spec,
        kv_cache_config.num_blocks_of(tensor),
        layout,
        tensor,
    )
    kv_caches.update(zip(tensor.layers, views))
```

（1）`kv_cache_tensors`里的`KVCacheTensor`是布局描述，记录`layers`、`offset`、`layer_stride`和`block_stride`。这些描述的`size`都是整个底层buffer的大小，因此先取出这个大小，再调用一次`torch.zeros()`。

（2）Buffer用`int8`申请，方便按字节计算偏移。`create_kv_cache_views()`内部通过`torch.as_strided()`创建视图，再用spec中的dtype解释数据。这些view共用原来的storage，没有复制整份缓存；实际KV的类型也不受这里的`int8`限制。

（3）各层的view准备好以后，请求运行时申请的是block id，块表决定了当前请求可以访问哪些位置。请求释放block后，底层buffer还在，后续请求可以继续使用。

假设同一group内的两个层各需要16 B，可以先申请32 B，再给两个层分别创建view。如下图，先按层排列，每层有两个8 B的block；请求拿到id 1后，访问的是layer0的字节8～15和layer1的字节24～31。图中省略了保留块和padding。

![](https://pic4.zhimg.com/v2-d46e151ecedb6adc22528bb4c21e19a5_r.jpg)

两个层也可以把相同block id的数据交错放在一起，具体取决于下面讲的布局。View的offset和stride会随布局调整，使用的仍然是初始化时申请的底层buffer。

### 4.3 内存布局

同一块内存里，各层的数据可以有不同的排列顺序。这里用`[L, B, H, N, C]`描述逻辑维度，再根据布局计算每一维的stride，也就是这个维度的下标增加1时，地址需要前进多少。

这几个字母分别表示：

（1）`L`是参与打包的层或缓存模块，`B`是block。

（2）`H`通常是KV head，也可能是backend定义的head slot。

（3）`N`是一页中实际保存的记录数，`C`在原始字节视图中表示每个head slot、每条记录的内容字节数。

下面不考虑把一个管理block进一步拆成kernel block的情况。布局名称从左到右表示从外到内的排列，最右边的维度在地址递增时最先变化。例如`LBNHC`先放某一层的所有block，再放下一层；`BLNHC`则先放block 0的各层数据，再放block 1的各层数据。

`KVCacheLayout`中定义了六种顺序：

| 布局 | 排列顺序 | 某层某块的一页 |
| --- | --- | --- |
| LBNHC | 层 → 块 → 记录 → 头 → 内容 | 连续 |
| LBHNC | 层 → 块 → 头 → 记录 → 内容 | 连续 |
| BLNHC | 块 → 层 → 记录 → 头 → 内容 | 连续 |
| BLHNC | 块 → 层 → 头 → 记录 → 内容 | 连续 |
| BHLNC | 块 → 头 → 层 → 记录 → 内容 | 多头、多层时分成不同头段 |
| LHBNC | 层 → 头 → 块 → 记录 → 内容 | 多头、多块时分成不同头段 |

`LBNHC`和`LBHNC`都按层放置，区别在页内先排记录还是先排头，kernel访问数据的方式也会跟着不同。`BHLNC`把整个block放在一起，但每个head下面才是各层的数据，所以其中某一层的一页可能分成几段。

下面用32 B数据画一下这几种排列：2层、2块、2个头，每页每个头保存2条记录，每条记录2 B，不考虑页尾padding。

![](https://pic2.zhimg.com/v2-be96dbaae4a1105c17adc8004adce3e9_r.jpg)

图中框出来的都是`L1/B0`，也就是第1层、第0块的数据。在`LBNHC`中是字节16～23，在`BLHNC`中是8～15，在`BHLNC`中则分成4～7和12～15两段。内容都是8 B，只是位置和stride不同。

图中一条记录对应一个token。压缩缓存需要按`tokens_per_state`换算，例如128个原生token、压缩比为2时，页内实际只保存64条记录。`C`中还可能包含量化数据和scale，计算时要按实际存储格式，不能直接当成原始head dimension。

### 4.4 布局选择

模型能使用哪些布局，要看attention backend支持哪些stride，也要看各个spec的页形状。首次初始化时，worker先汇总各backend支持的布局及偏好顺序，引擎检查各worker的结果一致，再根据模型的spec筛选。

例如参与通用层view的spec有不同的H、N或页大小时，就要求某层某块的一整页连续存放，`BHLNC`和`LHBNC`会被排除。多个group混合不同页大小时，还需要把块放在最外层，使用`BLNHC`或`BLHNC`这样的排列。

下面看下resolve_kv_cache_layout中选择布局的部分。这里的`candidates`已经按backend支持和spec约束筛选过，并按偏好排序；省略候选列表的构造、日志和结果写回，简化报错文字：

```text
if (requested := envs.VLLM_KV_CACHE_LAYOUT) is not None:
    layout = _layout_from_name(requested)
    if layout not in candidates:
        raise ValueError("指定的布局不在候选列表中")
elif (connector := get_kv_connector_cache_layout(vllm_config)) is not None:
    layout = _layout_from_name(connector)
    if layout not in candidates:
        layout = candidates[0]
else:
    layout = candidates[0]
```

（1）显式设置`VLLM_KV_CACHE_LAYOUT`时，指定的布局必须在候选列表中，否则直接报错，不会自动换成其他布局。`_layout_from_name()`也处理旧配置名，`NHD`和`HND`分别对应`LBNHC`和`LBHNC`。

（2）没有显式配置时，再看连接器偏好的布局。偏好不满足约束就退回`candidates[0]`，原实现还会记录一条warning；连接器没有偏好时，也取这一项。

（3）这段代码用于首次选择。若`cache_config.kv_cache_layout`中已有解析结果，函数会在前面直接返回，继续使用原来的布局。

分组完成后，validate_kv_cache_layout还会检查这个布局能否放下各层的页。下面的`page_sizes`是从所有group逐层收集到的页字节数集合，报错文字做了简化：

```text
if len(page_sizes) == 1:
    return
if not layout.is_block_compact or (
    len(kv_cache_groups) > 1 and layout.is_layer_compact
):
    raise ValueError("当前布局无法容纳混合页大小")
```

（1）页大小相同时，这项打包检查直接通过；backend支持范围等约束已经在选择阶段检查过。

（2）页大小不同时，`is_block_compact`要求某层某块的一页连续，因此排除`BHLNC`和`LHBNC`。若还有多个group，就不能让L位于最外层，进一步排除`LBNHC`和`LBHNC`，剩下`BLNHC`和`BLHNC`。这里负责校验，条件不满足就报错，不会重新选择布局。

所以即使共用一整块底层buffer，也可以选择`LBNHC`这种按层的排列；DeepSeek V4.1 Flash则使用`BLHNC`。

### 4.5 group packing

按块排列时，同一个group内的各层都要保存自己的数据，所以需要把各层的页并排放好。不同group从block pool取得不同的id，不会同时写同一个id，因此同一段字节空间可以按不同group的要求解释。

例如某个group的一组页需要100 KiB，另一个需要132 KiB，那么一个id至少要准备132 KiB，才能供其中任意一组使用。再考虑stride对齐，就可以计算出一个id的实际字节大小。

下面是`_get_kv_cache_bytes_per_block()`在块位于最外层时的简化计算，其中`page_bytes`和`stride_alignment`是示意用的辅助函数，分别表示读取每层spec的页字节数和stride对齐要求：

```text
group_bytes = [
    sum(page_bytes(group, layer) for layer in group.layer_names)
    for group in groups
]
alignment = math.lcm(*[
    stride_alignment(group, layer)
    for group in groups
    for layer in group.layer_names
])
block_stride = round_up(max(group_bytes), alignment)
num_blocks = available_memory // block_stride
```

（1）先把每个group内各层的页大小相加，得到这一组需要多少字节。

（2）取最大的group，再按各模块的stride要求对齐，得到统一的`block_stride`。

（3）可分配内存除以这个大小，就是block数量。其中还包括`null_block`等保留用途，实际可分配给请求的数量要扣除这些部分。

不同group的放置方式如下图所示，图中的五组分别保存历史KV、两类局部状态和两组SWA，只用于说明overlay，不对应某个模型的实际分组，也省略了对齐。

![](https://pic1.zhimg.com/v2-3b7160b2178b64b6d25aa3ef5cc85d46_r.jpg)

假设group 0现在使用id 40，group 1就只能使用其他空闲id。等40释放后，group 1才可能拿到它，并按自己的页布局写入。因此两个group可以使用相同的offset，但不能同时占有同一个id。如果较小的group拿到一个id，剩下的字节也不能再分给其他请求，因为block pool按完整id分配。

上面的计算对应按块排列的路径，其他布局的stride要按各自规则计算，具体见 _get_kv_cache_bytes_per_block。对于`BLHNC/BLNHC`，一层的页起点可以写成：

`address = backing_base + block_id × block_stride + layer_offset`

`layer_offset`包含该spec区域的`offset`，以及区域内层编号乘`layer_stride`。Kernel通过层view访问这个位置，再根据页内各维度的stride找到记录。换成其他布局时，要使用对应的stride，不能继续套用这里统一的块跨度。

### 4.6 P/D传输

在prefill/decode分离的场景中，prefill worker需要把kv传给decode worker，布局也会影响这部分搬运。如果要传某个block的跨层内容，按层排列时就需要分别找到每层对应的页；按块排列时，这些页可以放在一个连续范围里。

以前面的32 B例子来说，`LBNHC`的block 0在0～7和16～23两段，`BLHNC`的block 0则在0～15。统一的底层buffer可以方便注册共享storage，按块排列又可以减少这次传输需要描述的离散范围。

实际传输仍然由连接器处理。例如NIXL会检查是否共用storage、block stride是多少、页是否连续，再选择按层区域或共享块区域描述数据。如果有group间的overlay，还要根据当前持有的block id确定内容，同一个块不会同时保存各组的数据。

这种排列提供了减少离散传输操作的机会，实际收益还受连接器、并行配置和传输粒度影响。它对attention kernel计算性能的影响，需要单独测量。

## 5.prefix caching

### 5.1 group前缀匹配

上一篇讲过，block的hash包含前面block的信息，查找公共前缀时，从第一个block开始依次匹配。分组以后，每个group可能保存不同的内容，查找缓存时还要带上group id。同一段token在full、SWA和状态组中各有自己的缓存，不能只匹配到其中一组就直接跳过这段计算。

下面只检查`prefix_cacheable=True`的组。不参与前缀共享的工作状态不会进入匹配循环，恢复它们所需的计算仍要单独处理。

假设full group匹配到了前512个token，但SWA在512这个位置需要读取的窗口已经被淘汰，后续计算就缺少SWA的数据。如果模型还有递推层，也要检查有没有处理完512个token后的状态。

这里full group需要从开头连续命中的历史块；参与普通prefix caching的SWA，需要保留恢复位置附近足够的窗口数据；递推层则需要这个位置对应的状态检查点，能够使用哪些检查点还受缓存模式限制。请求最终能复用到哪里，要把这些组一起检查。

### 5.2 公共前缀长度计算

公共前缀长度决定了新请求可以跳过多少个token。例如命中长度为256，就跳过前256个token，从第257个token继续计算。这要求所有参与匹配的group，都有从256继续计算所需的数据。

假设模型同时包含full attention、SWA和递推层，三个group都参与prefix caching。下面把token从1开始编号，block大小和命中对齐粒度都设为64，SWA窗口大小为128，不考虑投机解码。当前能够查到的缓存如下，假定两个状态检查点都允许命中，而且尚未被淘汰：

| group | 当前缓存 |
| --- | --- |
| Full attention | token 1～512的全部KV |
| SWA | token 129～256、385～512的KV块；257～384的块已经被回收 |
| 递推层 | 检查点S256和S384 |

这些缓存可以来自此前不同的请求。SWA只需要保留相应窗口的数据，并不要求从第一个token开始的所有块都还在。

现在来了一个超过512个token的新请求，它的前512个token与上面缓存对应的前缀相同，先尝试复用512个token。

第一轮从512开始。Full attention的1～512都在，可以从512继续。SWA在这个位置需要检查385～512的两个窗口块，它们也都在。但递推层没有`S512`，只能找到`S384`，于是把候选长度缩到384。

此时还不能直接从384继续。SWA能从512恢复，不代表它能从384恢复：从384继续时，需要检查的是257～384的窗口块，而这些块已经被回收了。这里的区间是按block检查的数据范围，不是attention精确读取的token范围。

第二轮按384重新检查。Full attention仍然满足要求，但SWA缺少257～384的块，需要继续向前找。129～256的两个窗口块还在，因此SWA把候选长度缩到256。后面的递推层找到`S256`，也可以从256继续。

第三轮按256检查，full attention有1～256的KV，SWA有129～256的窗口块，递推层有`S256`，候选长度不再变化。最终跳过前256个token，从第257个token继续计算。

如下图所示，候选长度经过`512 → 384 → 256`才确定下来。如果只对各组最初的最大命中长度取一次最小值，得到的384就缺少SWA恢复所需的数据。

![](https://picx.zhimg.com/v2-98c8ccc0f4cdd9f5d8eafce673e5f213_r.jpg)

下面用伪代码表示`HybridKVCacheCoordinator.find_longest_cache_hit()`中的这个过程，省略了fast path、投机解码边界和结果裁剪：

```text
candidate = max_cache_hit_length
while True:
    previous = candidate
    for group in prefix_cacheable_groups:
        candidate = group.find_recoverable_prefix(candidate)
    if candidate == previous:
        break
```

`find_recoverable_prefix`是这里为了说明过程使用的名称，实际调用的是各manager的`find_longest_cache_hit()`。

（1）`candidate`是当前尝试复用的前缀长度，例子中从512开始。每个group查找不超过这个长度的可恢复位置，更新`candidate`；后面的group使用更新后的值。

（2）`previous`保存这一轮开始时的长度。只要一轮结束后长度变短，就按新的位置重新检查。例子中递推层把512缩到384后，下一轮才发现SWA在384处缺少窗口块。

（3）一轮结束后长度不变，表示各组都能从这个位置恢复，循环结束。长度只能缩短，最小为0，所以不会一直循环。

实际实现不会每轮都重新查询full attention的缓存。已经确认1～512连续命中，后面缩到384或256时，直接沿用查询结果并缩短命中范围即可。对于只有一个full attention类型和另一个缓存类型的简单组合，full先检查，后者缩短的位置也一定满足full，因此源码中有一轮就结束的fast path。

### 5.3 hash粒度

上一篇按一个block计算一个hash来解释公共前缀。现在不同group的block size可能不同，计算hash的粒度也可以和实际分配的block分开。

例如两个group的block size分别是128和32，在启用hashing且没有触发其他回退规则时，Scheduler的基础对齐取最小公倍数128，默认hash粒度可以取最大公约数32。也可以通过`prefix_match_unit`在允许范围内指定匹配单位。

但是每32个token计算一个hash，不代表所有模型组合都能每32个token命中一次。Coordinator还会检查各组是否支持细粒度命中，支持时可以按hash对齐，否则仍按Scheduler对齐。压缩记录的边界和Mamba缓存模式也会限制允许命中的位置。

在支持的路径中，一个物理block内部可以按hash边界登记可复用的内容，不需要为每个hash另外分配一个物理block。如果后续写入会修改共享块，就需要copy-on-write，先处理共享内容的保护，再继续写入。

## 6.DeepSeek V4/V4.1的缓存管理

前面分别看了group、状态、内存布局和prefix caching，下面用DeepSeek V4/V4.1看一下这些缓存是怎么组合起来的。先看模型需要保存什么，再用V4.1 Flash的配置计算分组和内存占用，最后看命中前缀以后怎样恢复状态。

### 6.1 缓存组成

DeepSeek V4中，同一个attention层还可能需要几种不同的缓存。以C4层为例，近期token的kv保存在SWA中，更早的历史按压缩后的记录保存；indexer需要保存自己的K，用来从历史中选择候选位置。压缩过程还会产生中间状态，需要留到后面的步骤继续使用。

各类层的缓存组成如下图所示：

![](https://picx.zhimg.com/v2-b8620982aa37aa23b14202ba239d8ff5_r.jpg)

图中main的逻辑block size使用256个原生token。C4每4个token产生一条压缩记录，C128每128个token产生一条。两种压缩历史都可以继续增长，SWA才是只保留局部窗口的数据。

每个缓存模块分别返回自己的spec，再根据要求分组。所以统计缓存大小时，需要数清楚实际有哪些缓存模块，不能直接拿模型层数来代替模块数或group数。

### 6.2 压缩率与block size

压缩之后，block size该怎么算？假设C4和C128都按64条压缩记录分一块，C4这一块对应256个原生token，C128却对应8192个token，同一个请求在两种层上的处理位置就不好直接对应了。

vllm仍然用原生token数定义逻辑block size，再根据压缩率计算这一页实际放多少条记录。下面是DeepSeek V4中`MLAAttentionSpec`的几个字段，省略了量化和对齐参数：

```text
spec = MLAAttentionSpec(
    block_size=vllm_config.cache_config.block_size,
    num_kv_heads=1,
    head_size=self.head_dim,
    dtype=self.kv_cache_torch_dtype,
    tokens_per_state=self.compress_ratio,
    model_version="deepseek_v4",
)
```

（1）`block_size`表示这一块覆盖多少个原生token。

（2）`tokens_per_state`表示几个原生token对应一条存储记录。对于这里的压缩历史，一页的记录数就是`block_size / tokens_per_state`。

（3）上面展示的是自然dtype路径。每条记录的字节数还要根据实际格式、scale和对齐计算，量化后端会补充相应的字段。

假设逻辑block size为256，C4在一页中存64条记录，C128只存2条记录，Scheduler看到的都是256个原生token。

这里和MLA对kv的压缩也要区分一下。MLA改变的是一条记录的表示大小，C4/C128还减少了token方向上的记录数。计算内存时，需要同时考虑每页有多少条记录，以及每条记录占多少字节。

### 6.3 compressor state

压缩需要把一组token放在一起处理，在这一组尚未处理完时，中间结果也要保存下来。这部分状态跟着请求走，请求被抢占、恢复或复用前缀时，都需要一起处理。

DeepSeek V4的`CompressorStateCache`返回`SlidingWindowMLASpec`，这样就可以使用已有的窗口管理代码。两类compressor state的参数如下：

| 类型 | 逻辑block size | 状态窗口 |
| --- | --- | --- |
| C4 compressor state | 4 | 8 |
| C128 compressor state | 8 | 128 |

超过窗口的旧状态块可以释放，满足前缀缓存条件时也可以保留检查点。这部分使用SWA的分配和回收方式，页中存放的仍然是压缩中间状态。

### 6.4 跨层共享与ring buffer

V4.1 Flash中的一部分层负责产生global KV，后面的层直接读取这些层生成的内容。对于读取已有global KV的层，`get_kv_cache_spec()`返回`None`，不再单独申请global KV空间；每层自己的SWA仍然分别保存。

这和前面的group共用block table有区别。Group内各层虽然使用相同的id列表，通常仍有各自的kv；这里后面的层直接读取来源层的同一份kv。

V4.1的compressor state则使用固定的ring buffer，通过`CircularBufferSpec`描述。下面是`CircularBufferManager`中申请block的代码，省略了新块清零的记录：

```text
def _claim_ring_block(self, request_id):
    req_blocks = self.req_to_blocks[request_id]
    if req_blocks:
        return []
    new_blocks = self.block_pool.get_new_blocks(1)
    req_blocks.extend(new_blocks)
    return new_blocks
```

（1）先检查这个请求在ring group中有没有block，有了就直接返回，不再申请新的。

（2）如果没有，就从block pool中申请一个id。组内各模块在这个id对应的位置有各自的状态页。

（3）后续在页内循环写入。这里不增加投机层时，每页有8行，写入位置是`token_position % 8`；配置投机token后，行数还会相应调整。

V4的compressor state随着窗口移动申请和释放block，V4.1则一直使用请求持有的这一页，在页内循环覆盖，直到请求完成后再归还id。

如下图，上半部分只画了一份来源层的global KV，读取层共用这份内容，各层SWA仍然各自保存。下半部分展开请求A在一个ring模块中的状态页，token位置从0开始编号：写完位置0～7后，位置8、9回到行0、行1，覆盖原来的中间状态，使用的仍是同一个block id。图中的层名、模块名和id仅作示意，ring按没有投机token时的8行容量绘制。

![](https://picx.zhimg.com/v2-63b7d5e719799512d4ed2e593a191b1d_r.jpg)

### 6.5 V4.1 Flash容量计算

有了这些缓存模块，就可以算一下分组和内存占用。使用40层主干，不增加投机层，不启用PP/CP，`bounded_replay=False`。Global KV使用NVFP4，SWA使用MXFP8，index K使用FP8，按SM100 Mega Attention对应的`BLHNC`布局放置。

这个配置有40份SWA、4份global KV、4份index K和3份ring，一共51个缓存模块。每个模块的一页需要多少空间，如下表所示：

| 页类型 | 数量 | 每页记录数 | 每条记录大小 | 每页大小 |
| --- | --- | --- | --- | --- |
| SWA | 40 | 32 | 528 B | 16.5 KiB |
| 压缩比为2的global KV | 3 | 64 | 288 B | 18 KiB |
| 压缩比为1的global KV | 1 | 128 | 288 B | 36 KiB |
| 压缩比为2的index K | 3 | 64 | 132 B | 8.5 KiB，含对齐 |
| 压缩比为1的index K | 1 | 128 | 132 B | 16.5 KiB |
| Ring | 3 | 8行 | 4096 B | 32 KiB |

这里`1 KiB = 1024 B`。压缩index页原本是`64 × 132 = 8448 B`，补齐到512 B的整数倍后是8704 B，也就是8.5 KiB。

Global和index都按128个原生token管理一页，可以放到同一组。压缩比为2的模块在这一页里只存64条记录。这一组的页大小相加得到：

`3 × 18 + 36 + 3 × 8.5 + 16.5 = 132 KiB`

分组时用这个大小安排其他组。每张SWA页是16.5 KiB，一组可以放8张，40份SWA就分成5组；3份ring合计96 KiB，另外形成一组，如下图所示。

这样一共是5个SWA group、1个global/index group、1个ring group，每个id需要132 KiB，也就是135168 B。

这里SWA的32-token页和global的128-token页可以放在同一个池里，是因为一个SWA group的id要同时放八层的页。每层32条记录，八张页加起来刚好也是132 KiB，空间已经用满了。

再假设一个请求首次处理71个token，没有前缀命中，也不额外预留block。每个SWA group需要3个id，global/index需要1个，ring需要1个，总共是`5 × 3 + 1 + 1 = 17`个id。占用空间就是`17 × 132 = 2244 KiB`。这里先把各组的id数量加起来，再乘统一的大小，各group共用的是同一个池。

量化格式改变后，分组结果也可能不同。例如只把global KV改成本例的MXFP8格式，global/index组就变成207 KiB，SWA则分成四组，每组十页。所以比较两种格式的内存用量时，也要重新计算分组，不能只看4 bit和8 bit的比例。
