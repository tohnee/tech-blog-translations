**Kubernetes（简称 K8s）是一个开源的容器编排平台，用于自动化部署、扩展和管理大规模的容器化应用程序**。之所以简称为 K8s，是因为首字母 K 和尾字母 s 之间恰好有 8 个字母。

如果把 **Docker** 比作一个个标准化的**“集装箱”**，那么 **K8s** 就是掌控整个现代自动化码头的**“超级智慧调度中心”**。

---

📜 一、 K8s 是怎么诞生的？（巨人的肩膀）

K8s 并不是凭空想象出来的，它流淌着 Google 内部十几年最顶级运维经验的血液：

1. **前身（Borg 系统）**：早在 2003 年左右，Google 内部就已经在用容器技术支撑谷歌搜索、Gmail 和 YouTube 了。为了管理全球数百万台服务器上的几十亿个容器，Google 秘密研发了一套名为 **Borg** 的内部集群管理系统。
2. **开源降维打击（2014 年）**：到了 2014 年，Docker 刚刚火遍全球，大家发现虽然打包容器变简单了，但一旦容器数量达到几百上千个，管理起来简直是噩梦。于是 Google 工程师基于 Borg 的设计理念，用 Go 语言重写了一套开源系统，正式命名为 **Kubernetes** 并捐赠给了云原生计算基金会（CNCF）。
3. **一统江湖**：凭借着 Google 踩过无数大坑积累下来的架构设计，K8s 迅速击败了当时所有的竞争对手（如 Docker Swarm、Mesos），成为今天云计算领域绝对的“操作系统”。

---

💥 二、 有了 Docker Compose，为什么还需要 K8s？

你之前学过 **Docker Compose**，它非常优秀，但它有一个致命的局限：**它只能管理“同一台电脑/服务器”上的容器**。

当你面对真实的企业级业务时，Docker Compose 就会瞬间抓瞎，而这正是 K8s 解决的 **4 大核心痛点**：

| 业务痛点 | 单机 Docker Compose 的无奈 | 集群王者 K8s 的破局之道 |
| --- | --- | --- |
| 1. 机器半夜宕机（高可用） | 跑着容器的那台服务器突然主板烧了、断电了，网站直接彻底瘫痪，必须半夜爬起来手动换机器重启。 | 故障自动自愈：K8s 时刻盯着所有服务器。一旦发现 1 号机死机，几秒钟内自动在健康的 2 号、3 号机上重新拉起一模一样的容器，用户完全无感知。 |
| 2. 流量暴增暴跌（弹性伸缩） | 遇到突发流量，只能手动修改配置、手动加服务器、手动启动新容器，黄花菜都凉了。 | 自动扩缩容：只要设置一条规则（如 CPU 超过 70%），流量一来 K8s 自动瞬间分裂出 50 个容器扛压；半夜没人访问时自动销毁 48 个容器省钱。 |
| 3. 升级新版本会断网 | 更新代码重启容器的那几秒钟，用户访问网站会报错（502 Bad Gateway）。 | 滚动更新与一键回滚：K8s 像“换轮胎不停车”一样，先启动 1 个新版容器、再杀掉 1 个旧版容器，逐步替换，全程零停机。一旦发现新版本有 Bug，一条命令瞬间回滚到上一版。 |
| 4. 几百台机器资源分配 | 程序员每次部署都要自己算：“A 机器内存还剩多少？B 机器 CPU 够不够？”极其痛苦。 | 智能资源调度：K8s 把 100 台服务器合并成一个“超级大资源池”。你只需说“我要跑 10 个爬虫”，K8s 自动挑选最空闲的机器把容器塞进去。 |

🧩 三、 K8s 的 4 个核心概念（小白必懂）

要看懂 K8s 是怎么指挥干活的，只需要记住这 4 个核心积木：

1. **Node（节点 / 工人机器）**：就是一台台真实的物理服务器或云服务器，负责提供实打实的 CPU 和内存来干活。
2. **Pod（豆荚 —— K8s 最小的调度单位）**：**注意！K8s 不直接管理单个 Docker 容器，而是把容器包进一个叫 Pod 的“豆荚”里**。通常一个豆荚里只放 1 个核心容器（比如你的 Python 爬虫），但如果两个容器关系极度亲密（比如爬虫 + 日志收集器），也可以放进同一个豆荚里共享网络和硬盘。
3. **Deployment（部署控制器 —— 监工）**：你不需要手动去一个个创建 Pod，而是写一份 Deployment 说明书告诉监工：“**我希望我的爬虫 Pod 永远保持 3 个在运行**”。只要死掉 1 个，监工立刻补上 1 个，永远维持你期望的数量。
4. **Service（服务网关 —— 固定门牌号）**：因为 Pod 随时可能死掉并在别的机器上复活，它的 IP 地址天天变。Service 负责给这组动态变化的 Pod 提供一个**永远不变的固定入口和内部域名**（类似你之前学的 Nginx 反向代理），外部请求只要找 Service，它自动把流量分发给后面健康的 Pod。

---

🏗️ 1. 四兄弟的真实角色分配

- **Node（节点）**：园区里真实买下来的 **1 号土地、2 号土地、3 号土地**（对应你买的三台阿里云/腾讯云服务器）。没有土地，集装箱只能飘在天上。
- **Deployment（部署控制器）**：园区里坐在办公室吹空调的 **“智能总调度官”**。他手里拿着你的指令单。
- **Pod（豆荚）**：真正放在土地上干活的 **“集装箱工坊”**（里面装着你的 Python 爬虫容器）。
- **Service（服务网关）**：园区大门口唯一的 **“总接待处与顺丰驿站”**。

---

🔄 2. 它们是如何配合工作的？（完整全流程演示）

假设你现在要部署你的 Python 爬虫系统，看看这四者是如何联动起来的：

第一步：铺好土地（准备 Node）

你在云服务商那里买了 3 台服务器，把它们加入 K8s 集群。现在园区里有了 **Node 1**、**Node 2**、**Node 3** 三块实打实的土地，每块土地都有 8 核 CPU 和 16G 内存。

第二步：下达指令（Deployment 登场）

你写了一份 YAML 配置文件交给 **Deployment（总调度官）**，上面只写了一句话：

> *“给我保证园区里随时都有 **3 个** 装有 Python 爬虫的 Pod 在运行！”*

第三步：挑地建房（调度分配到 Node 上）

**Deployment** 收到指令后，立刻生成 3 个 **Pod** 的创建任务。K8s 的大脑（调度器）会像扫描仪一样检查三块土地（Node）：

- 它发现 **Node 1** 最空闲，于是把 **Pod-A** 派到 **Node 1** 上，消耗 Node 1 的 CPU 和内存正式启动容器。
- 它把 **Pod-B** 派到 **Node 2** 上启动。
- 它把 **Node 3** 派给了 **Pod-C**。

*(此时，3 个 Pod 分别在 3 台不同的真实服务器上跑起来了，各自获得了临时的内部 IP。)*

第四步：统一对外接客（Service 登场）

外部的用户（或者你的前端网页）现在想访问你的 Python 接口。

- **痛点**：用户根本不知道你的 Pod 被分配到了 Node 1 还是 Node 2，更记不住那 3 个随时会变的 Pod IP 地址。
- **配合方式**：你创建一个 **Service（总接待处）**，给它起个固定的名字叫 `python-service`（分配一个永远不变的固定 IP）。
- 外部请求全部发给 `Service`，`Service` 就像一个智能分流器，自动把第 1 个请求转给 **Node 1 上的 Pod-A**，第 2 个请求转给 **Node 2 上的 Pod-B**，实现负载均衡。

---

💥 3. 巅峰时刻：当突发灾难发生时，四兄弟如何配合自愈？

假设半夜 3 点，**Node 2 这台服务器突然主板烧毁、彻底断电宕机了！** 看看这四个角色是如何实现“无人值守自愈”的：

1. **灾难发生**：**Node 2** 失联，躺在它上面的 **Pod-B** 瞬间灰飞烟灭。园区里只剩下 2 个 Pod 在干活了。
2. **Service 瞬间止损**：大门口的 **Service** 立刻察觉到 Pod-B 没心跳了，毫秒级把 Pod-B 从名单里踢出去，接下来的所有用户请求全部转发给健康的 Pod-A 和 Pod-C，**用户完全没有感觉到网站挂过**。
3. **Deployment 发现异常**：总调度官 **Deployment** 每秒都在数数：“老板要求 3 个 Pod，现在怎么只剩 2 个了？不行！”
4. **重新寻找土地（Node）**：Deployment 立刻下令重新创建一个新的 **Pod-D**。K8s 扫描土地发现 Node 2 已经死了，于是直接把新的 **Pod-D** 塞进了还有剩余内存的 **Node 1** 里启动！
5. **恢复满血**：几秒钟后，新 Pod-D 启动完毕，**Service** 自动把它重新纳入接待名单。**Node 1 上现在跑着 2 个 Pod，Node 3 上跑着 1 个 Pod**，系统重新恢复 3 个 Pod 的满血状态！

🎯 总结

- **Node** 是干苦力的**硬件底座**（没有它，容器没法运行）。
- **Pod** 是干活的**具体工人**（里面装着 Docker 容器）。
- **Deployment** 是管工人的**监工**（负责招人、补位、升级）。
- **Service** 是对外的**销售窗口**（负责接待客户并分配给工人）。

在单机用 Docker 时，你只需要懂 `镜像`、`容器`、`网络`、`数据卷` 这 4 个词就能干活了。<br>但 K8s 为了把机器集群管理的方方面面都做到极致解耦，创造了几十个全新的核心概念。刚入门时，光是为了跑通一个带数据库的简单网页，你就必须同时理解并配置：

- **调度层**：Pod、Deployment、StatefulSet（有状态应用）、DaemonSet（守护进程）
- **网络层**：Service、Ingress（对外网关）、NetworkPolicy（网络防火墙）
- **配置与存储**：ConfigMap（配置文件）、Secret（密码密钥）、PV（持久化存储卷）、PVC（存储申请单）
- **安全权限**：ServiceAccount、Role、RoleBinding

概念之间一环套一环，漏掉任何一个，整个应用就跑不起来。

---

在 K8s 的调度体系中，**Pod 是最基础的最小执行单元，而 Deployment、StatefulSet 和 DaemonSet 则是管理 Pod 的三大核心“控制器”**。

如果把 **Pod** 比作一个个干活的“工人”，那么后面这三个控制器，就是针对不同工种定制的**“三种不同管理制度的包工头”**。

---

1. Pod（豆荚）—— 干活的“基本工人单元”

在 K8s 里，调度系统从不直接指挥单个 Docker 容器，而是把容器装进 **Pod** 里统一管理。

- **为什么多此一举包一层？** 有些辅助程序必须和主程序“贴身肉搏”。例如，你的 **Python 爬虫容器**（主工人）旁边，可能需要配一个**日志收集容器**（小助理）。把它们装进同一个 Pod，它们就能共享同一个 IP 地址和同一块本地磁盘，配合起来毫无隔阂。
- **宿命**：Pod 是“短命”的。一旦它所在的服务器死机，或者它自己崩溃了，K8s 会直接销毁它，并在别处重新造一个名字和 IP 全新的 Pod。

---

这是我们之前聊过的最标准控制器，专门用来管理**“谁来干活都一样、不保存个人数据”的无状态应用**（如网页前端、Python 爬虫节点、API 接口服务）。

| 控制器名称 | 管理对象定位 | Pod 命名方式 | 启动/销毁顺序 | 硬盘存储方式 | 典型代表应用 |
| --- | --- | --- | --- | --- | --- |

| DaemonSet | 节点级守护进程（每台机器必须有） | 随机哈希后缀（如 log-x7k9） | 随服务器（Node）增减自动启停 | 直接读取宿主机本地目录 | 系统监控探针、全机日志收集器 |

看清了这三种包工头的管理制度后，你就彻底理解了 K8s 调度层是如何做到“既能大规模批量克隆无状态应用，又能小心翼翼呵护数据库，还能顺手管理每一台底层服务器”的。<br>

在 K8s 的网络体系中，因为 Pod 随时可能死掉并在别的服务器上复活，导致它的 IP 地址天天变，所以 K8s 必须构建一套层层递进的“交通导航与安保系统”。

**Service、Ingress 和 NetworkPolicy 分别扮演了“内部总机”、“园区大门总网关”和“内部安全防火墙”的角色**。

---

1. Service（内部总机与分流器）—— 解决“内部找不到人”

在 K8s 内部，假如你的 `Python 爬虫 Pod` 想去连接 `MySQL 数据库 Pod`，它绝对不能直接写死 MySQL 的 IP（因为万一 MySQL 重启换了 IP，代码就瘫痪了）。

- **核心作用**：Service 会为一组提供相同功能的 Pod 绑定一个**永远不变的固定内部 IP** 和一个**固定内部域名**（比如 `mysql-service`）。
- **工作方式**：
- **局限性**：普通的 Service（默认叫 `ClusterIP`）**只能在 K8s 集群内部通电话**，外面的互联网用户根本访问不到。

---

2. Ingress（对外总网关）—— 解决“外部用户怎么进门”

既然 Service 只管内部通信，那外部的普通用户通过浏览器输入 `https://xn--6qq176gc3czuf.com` 时，怎么才能穿过层层隔离访问到里面的 Pod 呢？这就需要请出 **Ingress**（它底层通常就是由你之前学过的 **Nginx** 驱动的）。

- **为什么不用 Service 直接对外暴露？** 虽然 Service 也有对外暴露端口的模式（如 `NodePort`），但就像单机 Docker 一样，它会在每台服务器上开一堆奇葩端口号（如 `30081`、`30082`），既难记又不安全，还无法统一配置 HTTPS 证书。
- **Ingress 的破局之道（园区正门总接待）**：

1. **统一域名与路径路由**：Ingress 牢牢守住标准的 `80` 和 `443` 端口。它根据你写的网址规则精准分流——比如访问 `://xxx.com` 转发给后端的 `Python Service`，访问 `://xxx.com` 转发给 `前端网页 Service`。
2. **统一 HTTPS 加密（SSL 卸载）**：你只需要在 Ingress 这道大门上配置好 HTTPS 安全证书，后面成百上千个微服务 Pod 全部自动享受加密保护，不需要在每个容器里单独折腾证书。

---

3. NetworkPolicy（网络防火墙）—— 解决“内部安全隔离”

在默认情况下，K8s 集群内部是一个“毫无秘密的开放小区”：**任何一个 Pod 都可以随意去访问集群里的其他任何 Pod**。

- **安全隐患**：假设你为了做测试，在集群里跑了一个第三方的开源小工具 Pod，结果这个工具存在黑客漏洞被攻破了。黑客就可以直接以这个 Pod 为跳板，顺着内部网络长驱直入，去扫描并盗取你核心 `MySQL Pod` 里的数据！

🎯 总结

- **Ingress** 管**南北向流量**（外部互联网进出集群的大门，负责域名分流与 HTTPS）。
- **Service** 管**东西向导航**（集群内部微服务之间互相调用，解决 Pod IP 乱变的问题）。
- **NetworkPolicy** 管**内部安保**（定义谁能访问谁，防止黑客在集群内部横向渗透）。

在 K8s 中，**ConfigMap** 和 **Secret** 负责解决“程序配置与代码分离”的问题，而 **PV** 和 **PVC** 则负责解决“容器随时生灭，但硬盘数据必须永久保留”的存储难题。

我们可以把这四个概念分成两组，用最日常的生活场景来彻底看透它们：

---

📝 第一组：配置管家（ConfigMap vs Secret）

回想你最开始发给我的那段 Python 脚本，里面把文件夹路径写死在了代码里。在现代开发中，**绝对禁止把配置信息（如数据库地址、密码、超时时间）写死在代码或 Docker 镜像里**。否则每次改个密码，都要重新打包镜像、重新上线，极其痛苦。

K8s 发明了两个专门存放配置的“外部配置中心”：

1. ConfigMap（明文配置文件）

- **核心作用**：用来存放**普通、不敏感的配置参数**（如：网站的标题、爬虫每次请求的间隔秒数、MySQL 的连接地址 `mysql-service`、Nginx 的路由规则文件）。
- **工作方式**：你把这些配置写进 ConfigMap 里。Pod 启动时，K8s 会自动把这些配置变成**环境变量**塞进容器，或者直接变成一个**配置文件**挂载到容器的指定目录里。
- **爽点**：如果哪天你想把爬虫间隔从 5 秒改成 10 秒，只需修改 ConfigMap 里的数字并重启 Pod，**根本不需要重新编写代码或重新打包 Docker 镜像**。

2. Secret（加密保险箱）

- **核心作用**：专门用来存放**高度机密的敏感信息**（如：MySQL 数据库密码、第三方支付的 API 密钥、HTTPS 证书私钥）。
- **与 ConfigMap 的区别**：ConfigMap 里的数据在 K8s 后台是完全明文可见的；而 Secret 会对数据进行编码（默认 Base64，并可配合后台强加密存储），且在权限控制上极其严格——**只有被明确授权的 Pod 才能读取对应的 Secret**，其他无关人员或容器连看都看不到。

---

💾 第二组：硬盘大管家（PV vs PVC）

之前我们聊过，单机 Docker 可以用 `-v` 参数把容器目录直接挂载到真实电脑的硬盘上。

但在 K8s 里有几十台服务器，容器今天在 1 号机运行，明天崩了可能漂移到 8 号机复活。如果把数据存在 1 号机的本地硬盘上，容器漂移到 8 号机后数据就全丢了！

为了实现“**容器跑到哪，数据就自动跟到哪**”，K8s 必须引入集中式的网络存储（比如云盘），并把存储拆分成 **PV** 和 **PVC** 两个角色：

1. PV（PersistentVolume，持久化存储卷）—— “物理硬盘资源池”

- **角色定位**：这是**运维工程师（房东）**提前准备好的实打实的存储空间。
- **工作方式**：运维人员在后台对接好阿里云云盘、腾讯云硬盘或公司机房的存储服务器，然后把它们切分成一块块标准的“虚拟硬盘”登记进 K8s（例如：1 号盘 50GB，2 号盘 100GB，3 号盘 500GB）。这些切分好的真实存储资源，就叫做 **PV**。

2. PVC（PersistentVolumeClaim，存储申请单）—— “开发人员的租房合同”

- **角色定位**：这是**开发人员（租客）**写给 K8s 的一张“存储需求申请表”。
- **为什么多此一举搞个申请单？** 因为写业务代码的程序员根本不想关心底层用的是阿里云盘、华为云盘还是自己机房的硬盘，他只关心业务需要多大容量、读写速度要多快。
- **工作方式**：程序员在启动 `MySQL Pod` 时，附带提交一张 **PVC 申请单**，上面写着：*“我需要一块 **40GB** 大小、支持高速读写的硬盘”*。
- **自动撮合（绑定）**：K8s 收到这张 PVC 申请单后，自动去 PV 资源池里扫描，发现 1 号盘（50GB）满足要求，立刻把 **PVC 和 1 号 PV 牢牢绑定在一起**，并挂载给 MySQL Pod 使用。

---

🔄 它们是如何实现“数据永不丢失”的？

假设某天，运行着 `MySQL Pod` 的 1 号服务器突然死机了：

1. **容器销毁**：1 号服务器上的 MySQL 容器灰飞烟灭。
2. **数据安然无恙**：因为数据全部通过 **PVC -> PV** 写在了远端的网络云盘里，1 号服务器死机对云盘里的文件**毫发无损**。
3. **跨机复活与重连**：K8s 立刻在健康的 5 号服务器上重新拉起一个新的 `MySQL Pod`。新 Pod 依然带着那张原本的 **PVC 申请单**，K8s 顺着申请单瞬间把原本绑定的那块 **PV 云盘**重新插在新 Pod 上。
4. **无缝恢复**：新 MySQL 启动后，直接读取到了原本的数据库文件，业务完美恢复！

📊 一张表总结这四个核心概念

| 概念名称 | 形象比喻 | 管理谁？ | 解决的核心痛点 |
| --- | --- | --- | --- |
| ConfigMap | 公开公告栏 / 菜单 | 普通配置参数、配置文件 | 修改配置无需重新打包代码镜像 |
| Secret | 银行密码保险箱 | 数据库密码、API 密钥、证书 | 防止机密信息明文泄露，严格权限隔离 |
| PV | 房东手里建好的毛坯房 | 底层真实的存储硬件（云盘/网络硬盘） | 屏蔽底层不同云厂商存储硬件的差异 |
| PVC | 租客填写的租房申请单 | Pod 对存储容量和速度的具体需求 | 让开发与运维彻底解耦，实现跨服务器数据跟随 |

在 K8s 的安全体系中，**ServiceAccount、Role 和 RoleBinding 共同组成了著名的 RBAC（基于角色的访问控制）权限管理系统**。

如果把整个 K8s 集群比作一家高度机密的高科技公司，那么这三个概念就是一套极其严密的**“工牌 + 权限清单 + 行政发卡处”**门禁制度，用来严格控制：**“谁（哪个程序）可以在集群里查看或修改哪些资源”**。

---

💥 一、 为什么需要这套权限体系？

在真实的生产环境中，有很多自动化工具（比如你前面学过的 **Jenkins** 自动化部署工具，或者 **Prometheus** 监控系统）本身也是作为一个 Pod 跑在 K8s 集群里的。

- **Jenkins Pod** 需要向 K8s 大脑发号施令：“*帮我把旧的 Python Pod 删掉，并创建新的 Pod！*”
- **监控 Pod** 需要向 K8s 大脑请求：“*把所有正在运行的 Pod 列表和状态发给我看看！*”
- **普通的业务爬虫 Pod** 只需要安安静静爬数据，**绝对不能让它有权限去查看 Secret 密码箱，更不能让它随随便便删掉别人的 Pod**（万一爬虫代码存在漏洞被黑客攻破，黑客就会利用这个 Pod 的权限把整个公司的服务器全删光）。

🧩 二、 三兄弟的真实角色分配

1. Serviceccount（服务账号 —— 员工的“空白工牌”）

- **角色定位**：这是专门发给 **Pod（程序）** 用的身份账号（区别于发给人类运维工程师的 User 账号）。
- **作用**：当你创建一个新的 Pod 时，你可以给它挂一张专属的 `ServiceAccount` 工牌（比如叫 `jenkins-sa` 或 `spider-sa`）。K8s 会自动往这个 Pod 内部塞入一张加密的临时身份证（Token）。当这个 Pod 去向 K8s 大脑请求操作时，就会自动亮出这张工牌证明自己的身份。
- **注意**：**刚办下来的 ServiceAccount 是一张“白板工牌”**，没有任何权限，连查看一个 Pod 列表都不被允许。

2. Role（角色 —— “权限说明书/门禁列表”）

- **角色定位**：这是一张纯文本的权限清单，里面清清楚楚地写着：**允许对哪些资源，执行哪些动作**。

- **角色定位**：它是一根“红线”，负责把 **“空白工牌（ServiceAccount）”** 和 **“权限说明书（Role）”** 正式绑定在一起！

- **结果**：从这一秒开始，所有佩戴 `jenkins-sa` 工牌的 Pod，就正式拥有了创建和删除其他 Pod 的至高权限；而佩戴 `spider-sa`（未绑定任何高危角色）的爬虫 Pod，一旦尝试偷看密码或删除容器，K8s 大脑会瞬间拦截并无情返回 `403 Forbidden（权限拒绝）`！
