## **DMuon：Muon 想进大规模分布式训练，真正要过的是系统这一关**

大家好，我是居丽叶。

最近，自变量机器人（X Square Robot）团队发布了论文《DMuon: Efficient Distributed Muon Training with Near-Adam Overhead》，讨论的正是 Muon 真正进入大规模分布式训练后，怎么把系统开销压到接近 AdamW。

![](https://pica.zhimg.com/v2-d72f75bacca316229e1fa7236d97e592_r.jpg)

这两年很多同学看优化器，常会纠结一个问题：**Muon 到底能不能在真实训练里跑赢 AdamW？**

> 在回答这个问题之前，先用一句话讲清楚 Muon 是做什么的。<br>Muon 是面向神经网络二维权重的矩阵正交化优化器。它不像 AdamW 将权重矩阵展平、以独立标量元素为单位逐元素自适应更新，而是先累积动量矩阵，再通过 Newton-Schulz 迭代近似正交化整块动量矩阵，从权重的二维矩阵几何结构重塑更新方向，目标是让模型用更少训练步数实现更快收敛、更好训练效果。

很多人只盯着 “Muon 能不能跑赢 AdamW” 这一点，其实这个思路本身就有片面性。

如果只看优化器公式，Muon 的确很有吸引力。AdamW 更接近对每个元素独立更新，Muon 则把权重矩阵当成矩阵来处理，通过 Newton-Schulz 迭代对 momentum-smoothed gradient 做近似正交化，让更新方向带有更强的矩阵结构信息。

**但把它落地到大模型分布式训练场景后，一系列工程层面的短板就会暴露出来。**

真实的大模型训练不会把完整参数放在一张 GPU 上慢慢算。参数、梯度、优化器状态会被切成 shard，分散到很多张卡上。AdamW 天生适配分布式分片训练逻辑：它的更新逻辑是逐元素独立计算，每张显卡只需处理自身分到的参数分片，就能独立完成更新。

Muon 麻烦的地方就在这里。

它的 Newton-Schulz 迭代需要看到完整矩阵。训练栈给它的是分片，它要的是整块矩阵。这个冲突如果处理不好，Muon 在数学上省下的时间，会被系统层的通信和重复计算吃掉。

自变量这次发布的 DMuon，值得看的地方也在这里：它处理的是现代分布式训练栈里 Muon 和 sharding 之间的工程冲突，底层完整沿用 Muon 原本的矩阵正交化算法。

这篇文章我们就从这个冲突讲起。

## **先把 Muon 讲清楚：它为什么会碰到分片训练的墙**

AdamW 的工作方式可以粗略理解成“逐元素更新”。

对于某个参数分片，只要这个分片自己的梯度、动量和二阶矩状态在本地，优化器就能完成更新。它不需要知道别的 rank 上那一块参数长什么样。

所以 AdamW 和 ZeRO、FSDP 这类 sharded training stack 很合拍。

Muon 的工作方式不一样。

Muon 面向的是二维权重矩阵，比如 Linear 层、Attention projection、MLP projection 里的矩阵参数。它会对 momentum 聚合后的梯度矩阵做 Newton-Schulz 迭代，近似得到一个正交化后的更新方向。

直觉上，你可以把它理解成：AdamW 更像是每个元素自己调步子，Muon 更像是先看整块矩阵的几何结构，再决定更新方向。

这个设计带来的问题是，矩阵结构不能从单个 shard 里完整恢复。

假设一个权重矩阵被切到多个 rank 上，每个 rank 只拿到其中一部分。对于 AdamW，这没问题；对于 Muon，Newton-Schulz 要计算的对象是完整矩阵，局部切片不够。

最朴素的做法是 gather-then-compute：

1. 每个 rank 先把完整矩阵梯度收集回来。
2. 每个 rank 都在本地跑一遍同样的 Newton-Schulz。
3. 每个 rank 只保留自己负责的那一块更新结果。

这个方案语义正确，但工程上很贵。

贵在两件事。

第一，完整矩阵要在每一步优化器 step 里被重建。这带来 AdamW 没有的额外通信。

第二，每个 rank 都重复运行同样的正交化计算。矩阵只需要被正交化一次，但朴素方案会让多个 rank 各算一遍。

论文里把这个问题叫 granularity mismatch：训练系统按 shard 暴露参数，Muon 按 matrix 消费参数。粒度不一致，直接导致了后续全部额外工程开销。

![](https://pic4.zhimg.com/v2-ffc35b6fabfca169d8b2c2cd3723e3a9_r.jpg)
*论文 Figure 2，Muon 与 sharded training 之间的粒度错配*

这也是为什么 DMuon 这篇论文更像一篇分布式系统论文，而不只是优化器论文。

它真正回答的问题是：

> 当优化器的数学对象是完整矩阵，而训练系统只愿意给你分片时，怎样保留 Muon 的更新语义，同时把系统开销压回 AdamW 附近？

## **DMuon 的第一层设计：每个矩阵只让一个 owner 算**

DMuon 最直观的一步，是把“每个 rank 都算一遍”改成“每个矩阵只交给一个 owner rank 算”。

每个矩阵参数会被分配给一个唯一 owner。这个 owner 保存该矩阵的权威优化器状态，负责接收完整梯度，运行 Muon 更新，然后把更新后的参数发布给后续计算需要它的 rank。

这样做有一个非常直接的收益：重复正交化被消掉了。

过去是数据并行组里多个 rank 对同一矩阵跑同样的 Newton-Schulz。现在同一个矩阵只有 owner 跑一次。

![](https://pic3.zhimg.com/v2-7ba863a1042f9402d4c44cf6fdb5e9ca_r.jpg)
*论文 Figure 3，左侧每个 rank 都重建完整梯度并重复执行 Muon；右侧每个矩阵只由一个 owner 更新*

但这一步只解决了重复计算，还没有解决全部问题。

因为 owner 方案会引入新的系统压力：

- 梯度要路由到对应 owner。
- 更新后的参数要及时发布给非 owner rank。
- 不同矩阵大小差异很大，owner 分配不好会导致有的 GPU 忙死，有的 GPU 等着。
- Newton-Schulz 本身还是很重，owner 上的 kernel 必须足够快。

所以 DMuon 的设计不会停在一个“owner trick”上，还要继续围绕 owner 执行处理通信、kernel 和调度。

一轮 DMuon training step 可以概括成四个阶段：

1. 参数物化：某层执行前，把 owner 上的矩阵参数发布到需要它的 rank，填进前向计算使用的 buffer。
2. 梯度路由：反向传播时，梯度先进入对应 buffer，再规约到矩阵 owner。
3. owner-side Muon update：owner 对自己负责的矩阵执行 Muon 更新；非矩阵参数仍然走宿主训练栈的优化器路径。
4. 异步发布：owner 更新后，把新参数异步发布给下一步会用到它的 rank。

这里最重要的工程判断是：DMuon 没有要求训练框架整体改造成一种全新的并行模式。它把 Muon 的矩阵需求包进一个可以和 FSDP/HSDP 这类 sharded stack 协作的运行时里。

这也是它能强调 drop-in 的原因。

论文里的接口示例只有三行：

```python
import dmuon
dmuon.dedicate_params(model, mesh)
opt = dmuon.Muon(model)
```

三行代码本身只是入口。真正有含金量的是，这三行背后要把参数归属、通信调度、梯度路由、owner 更新、异步发布和非矩阵参数路径都处理好。

## **第二层设计：通信不能只减少，还要错开**

很多分布式训练优化，第一反应都是“减少通信量”。

但 DMuon 面对的问题更麻烦。

owner 方案虽然消掉了重复正交化，但参数和梯度仍然要在 rank 之间移动。如果通信集中爆发，就会抢带宽、抬高峰值显存，还会把前向和反向卡住。

所以 DMuon 选择的方向是：把通信拆细、提前、错峰，并尽量和有效计算重叠。

在前向阶段，参数的使用顺序是按 layer 来的。某一层真正执行前，系统已经知道后面哪些矩阵将要被用到。DMuon 会利用这个 lookahead window，提前发起跨节点广播。

这里不会让所有广播一起冲出去。DMuon 通过更细粒度的布局，把相邻矩阵分散到不同通信组，让多个 broadcast 可以并发推进，减少 collective-level contention。

在反向阶段，通信任务更密集。

一方面，当前层反向计算前需要先 materialize 参数；另一方面，计算完以后梯度要 reduce 回 owner。如果这两类通信撞在一起，就会互相干扰。

DMuon 的处理方式是重新编排顺序：把下一层所需参数的 broadcast 和当前层梯度 reduce 错开，让通信流量不要在同一个时间点挤到一起。

这部分其实很像做流水线调度。

![](https://pica.zhimg.com/v2-67f27e99ebf33dcebcaa9cdb2637768c_r.jpg)
*论文 Figure 5，前向与反向阶段的通信—计算流水*

你要继续追问：

- 什么时候发？
- 走哪一组链路？
- 会不会和下一层的计算撞车？
- 会不会制造峰值显存？
- 能不能藏在前向/反向的空档里？

很多同学面试讲分布式训练，只会说 all-gather、reduce-scatter、all-reduce。更好的讲法是把通信放进 step timeline 里看：哪一段是 critical path，哪一段可以 overlap，哪一段会造成 contention。

DMuon 这篇论文正好是一个例子。

## **第三层设计：Newton-Schulz 也要按矩阵形状重新做 kernel**

owner 负责算 Muon 更新以后，Newton-Schulz 本身就成了 owner 侧的主要计算压力。

问题在于，大模型里的矩阵形状并不统一。

有些矩阵很大，单独就能吃满 GPU；有些矩阵比较小，单独跑一次 kernel 会让 GPU 吃不饱，launch overhead 和调度成本会显得很重；还有一些矩阵是长方形，直接在原始矩阵空间里迭代并不划算。

DMuon 在这里做了几件事。

第一，用 Gram space 来跑 Newton-Schulz。

对于某些形状，原始矩阵是 `m x n`，如果 `m < n`，把主要计算搬到 `m x m` 的 Gram 矩阵空间里，可以把主要计算量从 `O(m^2 n)` 降到 `O(m^3)`。

第二，利用 Gram 矩阵的对称性。

既然要算的是类似 `G G^T` 这样的结构，就可以使用 symmetric GEMM，避免按一般矩阵乘法付出完整代价。论文的 ablation 里，这个对称 Gram kernel 贡献了最大的优化份额：48%。

第三，把小矩阵 batching。

小矩阵单独跑容易吃不满设备。DMuon 会把形状相近的小矩阵打包到一起执行，摊薄 launch overhead，提高设备利用率。论文 Figure 7 里可以看到，越是小的、接近方阵的矩阵，batching 后每个矩阵的耗时下降越明显。

![](https://pic2.zhimg.com/v2-d96307297001ab185749e34f40f6d79b_r.jpg)
*论文 Figure 7，小而接近方阵的矩阵从 batching 中获得的收益更明显*

第四，用 DSL-driven autotuning 选 kernel。

不同矩阵形状、tile 配置、block size、software pipeline 配置之间没有一个永远最优的固定选择。DMuon 会为新的 workload shape 展开候选 kernel，实际 benchmark，选吞吐最高的配置，并把结果存进 kernel cache。后面遇到相同特征的 workload，就直接复用。

![](https://pic3.zhimg.com/v2-4bb38c9ed8fab5c77569a35204bf18da_r.jpg)
*论文 Figure 6，从 workload 展开搜索空间，经 JIT、实测排序后缓存最优 kernel*

这部分的工程含义是：Muon 的问题不能只在优化器 API 层解决。只要 Newton-Schulz 还在 critical path 上，底层 kernel 和 shape-aware execution 就会影响最终 step time。

## **第四层设计：owner 分配要看真实耗时，不能只看参数大小**

Owner 方案还有一个不太显眼但很致命的问题：怎么分配 owner？

如果只是把矩阵按数量平均分给每个 GPU，很容易翻车。

因为不同矩阵形状的计算成本差距很大。一个大矩阵可能比一堆小矩阵更重；某些形状可以被 batching 吃掉，某些形状会独占较长时间；kernel 选择和 autotuning 结果也会改变真实耗时。

所以 DMuon 没有只按参数量或矩阵数量做静态均分。它会在初始化时先测量每类矩阵形状的真实执行成本，再用混合整数线性规划来做 owner assignment，目标是降低所有 owner 里最慢那个的完成时间。

这里的判断很工程化：

> 分布式系统里，平均负载好看不够，拖慢 step 的往往是最慢的那张卡。

如果 owner 分配不均，其他 rank 都算完了，最后还是要等 straggler。DMuon 通过 measured-cost assignment，把“谁来负责哪类矩阵”变成一个调度问题，避免拍脑袋均分。

## **实验结果该怎么看**

论文的实验在 A800-SXM4-80GB 集群上进行，每节点 8 张 GPU，节点内 NVLink，节点间 200 Gb/s InfiniBand，数据精度为 bf16。

对比对象有两个：

- AdamW：同配置下的常规优化器 baseline。
- Muon-AG：朴素 gather-then-compute 的分布式 Muon baseline。

工作负载包括 Wall-OSS、Pi0、Wall-WM 和 Qwen2.5-7B。

主结果可以抓三组数字。

第一，和朴素分布式 Muon 相比，DMuon 的端到端单步时间提升 1.48x 到 3.01x。

第二，优化器 step 本身提升更明显，达到 6.85x 到 163x。

第三，和 AdamW 相比，DMuon 的平均端到端 step time overhead 在 +2% 以内。

![](https://pica.zhimg.com/v2-eda01f6feae6b54a02e567027807ad1c_r.jpg)
*论文 Table 1。Optim. 和 Step 的单位均为毫秒，Speedup 为朴素分布式 Muon 相对 DMuon 的倍数*

注意这里的表达要严谨。

这里不能推导出“DMuon 在所有训练任务上都比 AdamW 快”，也不能推导出“Muon 可以无成本替代 AdamW”。

更准确的说法是：在论文测试的这些生产级训练 workload 上，DMuon 把朴素分布式 Muon 的系统开销大幅压低，让 Muon 的 per-step 成本接近 AdamW。这样，Muon 原本在收敛或 token efficiency 上的潜在收益，才有机会转化成真实 wall-clock 收益。

![](https://pic4.zhimg.com/v2-810c31871b108cd13503c74c15408907_r.jpg)
*论文 Figure 8，随着 GPU 数量增加，DMuon 的优化器计算开销下降，端到端吞吐逐渐接近 AdamW*

论文 Table 2 也给了一个很有用的加速来源拆解：

![](https://picx.zhimg.com/v2-8a124f13a0e8ebd5a35ec8a29f273c49_r.jpg)
*论文 Table 2，Symmetric Gram kernel 贡献 48%，owner 调度与负载均衡贡献 32%，自动调优与 NS batching 贡献 16%*

这个拆解很好，因为它说明 DMuon 的收益来自一组系统改造，不来自某个单点魔法。

最大的收益来自 kernel，第二块来自 owner 调度和负载均衡，第三块来自 autotuning 和 batching。也就是说，它是算法等价重写、通信编排、kernel 优化和调度共同作用的结果。

## **这件事对具身模型训练为什么更敏感**

DMuon 的 brief 里提到具身模型训练提速约 30%。这个数字不要孤立看，要放到具身模型训练的 step 结构里理解。

论文里有一个判断：相比很多 LLM/VLM 预训练，VLA 训练通常 temporal context 更短，前向和反向计算在单步时间里的占比更小。这样一来，优化器开销就更难被大量前后向计算摊薄。

换句话说，在某些具身模型训练设置里，优化器 step 的系统开销更容易暴露出来。

这也是为什么 Muon 在这里很尴尬：它可能带来更好的收敛表现，但如果每一步为了完整矩阵和 Newton-Schulz 支付太高系统成本，训练 wall-clock 不一定划算。

DMuon 的价值就是把这笔系统成本降下来。

如果优化器 step 不再比 AdamW 贵很多，Muon 的收敛收益才有空间变成端到端训练收益。

这也是这篇工作对具身智能公司有意思的地方。

过去很多底层优化器、训练系统和 kernel 层面的改造，更多出现在大语言模型公司或通用大模型基础设施团队里。自变量作为具身模型团队，把问题打到优化器分布式执行和训练基础设施这一层，说明具身模型训练已经不只是“拿现成框架跑模型”的阶段了。

当数据、模型结构、训练规模和硬件预算都进入竞争区，优化器 step 这种看似底层的环节，也会变成训练效率的一部分。
