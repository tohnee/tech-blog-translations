> 作为字节跳动从去年到今年最火的开源项目 [DeerFlow](https://github.com/bytedance/deer-flow) (59k+Star) 的贡献者，笔者基于实际经验独立设计了 TinyFlow——一个 ~3000 行代码的多智能体编排引擎。本文深度解析其四路自动路由、洋葱模型中间件、双线程池并发、增量记忆等核心架构设计。

去年年底，笔者开始深入研究字节跳动开源的 DeerFlow 项目——一个功能丰富的超级智能体框架。在阅读源码的过程中，笔者发现了一个多 Agent 并发操作文件时的竞态条件问题，并提交了 [PR #1714](https://github.com/bytedance/deer-flow/pull/1714) 来解决它。这次贡献经历让笔者深刻体会到：深入研究一个开源项目，你总能发现一些细微但真实的问题——而这往往就是开始贡献代码的最佳切入点。

不过，随着对 DeerFlow 架构的深入理解，笔者也发现了一个有趣的张力：为了支持 sandbox 沙箱执行、IM 集成、Skills 市场、多租户等大量场景，DeerFlow 的核心编排逻辑正在被非核心模块逐渐稀释。这并不是说 DeerFlow 的设计有问题——恰恰相反，它作为一个面向生产的多场景框架，这种复杂度是必要的。但笔者想回答一个更纯粹的问题： **一个 multi-agent 编排引擎的核心骨架到底长什么样？**

于是有了 TinyFlow。它不是 DeerFlow 的精简分叉，而是从零重写的独立项目，用约 3000 行代码（含测试）聚焦三个核心工程问题：Graph 编排的状态管理、并发执行模型、以及增量记忆系统。

## 架构全景

TinyFlow 的整体架构可以用一张图来概括：

```text
用户
 |
 v
+------------------+     SSE 事件流     +------------------+
|    前端           | ◀───────────────── |   API 网关        |
|    Next.js 16    | ──── REST ────────▶|   FastAPI        |
|    React 19      |                    |   /chat /threads |
+------------------+                    +--------+---------+
                                                 |
                                          +------v-------+
                                          |  图引擎       |
                                          | (LangGraph)   |
                                          +------+-------+
                                                 |
                         +-----------+-----------+-----------+
                         |           |           |           |
                       路由器      规划器       执行器      反思器
                         |           |           |           |
                         +-----+-----+-----------+-----------+
                               |
                    +----------+-----------+
                    |          |           |
                  记忆引擎   中间件链      技能注册
```

整个系统分为三层：前端负责 SSE 流式渲染和多线程管理，API 网关处理 REST 和 SSE 协议转换，核心引擎则是一个基于 [LangGraph](https://github.com/langchain-ai/langgraph) 的状态机，将用户请求智能路由到四种执行模式。

技术选型上有几个值得展开的决策。

编排框架选了 [LangGraph](https://github.com/langchain-ai/langgraph) 而非 AutoGen 或 CrewAI。multi-agent 编排本质上是一个状态管理问题——AutoGen 的消息传递模型灵活但难以调试和复现，CrewAI 的角色扮演模式更适合固定流程，而 LangGraph 是显式状态机，每个节点的输入输出和状态转移都是确定性的。对编排引擎来说，显式优于隐式。

前后端通信用了 SSE 而非 WebSocket。LLM 应用的通信本质是单向流式（服务端→客户端），SSE 基于 HTTP、自带重连、与 HTTP/2 multiplexing 天然兼容，WebSocket 的双向全双工在这里属于多余的复杂度。

记忆存储用了 JSON 文件而非向量数据库。TinyFlow 的记忆系统基于结构化 Fact 而非语义检索， `difflib.SequenceMatcher` 足以完成相似度判断，向量数据库只会增加部署复杂度而不带来实质收益。

## 四路路由器：让系统自己决定怎么回答

TinyFlow 与 DeerFlow 在用户交互上最大的区别在于路由策略。DeerFlow 让用户手动选择执行模式（Flash / Thinking / Pro / Ultra），TinyFlow 则把这个决策交给了 Router 节点。

```text
┌─→ [Respond] ──────────────────→ END     (Flash: 直接回答)
                │
                ├─→ [ThinkRespond] ─────────────→ END     (Thinking: 深度推理)
                │
[Router] ──────┤
                ├─→ [Plan] → [Execute] → [Reflector] → END  (Pro: 规划执行)
                │
                └─→ [Plan] → [Dispatch] → [Merge] → END     (Ultra: 并行研究)
```

四种模式各有明确的分工。Flash 处理简单问答，一次 LLM 调用直出结果，延迟最低。Thinking 处理需要分析推理但不需要外部工具的问题，会输出可见的思考链。Pro 处理需要工具调用的任务（搜索、代码生成等），按计划顺序执行。Ultra 处理可并行的多子任务，由多个 subagent 并发执行后合并结果。

Router 的决策机制是笔者在开发过程中迭代最多的部分。最初笔者使用纯 LLM Function Calling 做路由——定义四个 Pydantic Schema，让 LLM 通过 function calling 返回结构化的路由决策：

```text
class RouteFlashArgs(BaseModel):
    """简单问答，一句话能答完"""
    pass

class RouteProArgs(BaseModel):
    """需要工具调用，可分解为有序步骤"""
    task_description: str
    estimated_steps: int = 3

class RouteUltraArgs(BaseModel):
    """多个独立子任务，需要并行执行"""
    subtasks: list[str]
```

这个方案在 GPT-4 级别的模型上运作良好，但换到弱一些的模型（如 GLM-4-Flash）后，路由准确率骤降到 60% 以下。弱模型经常不产生 `tool_call` ，导致所有查询都默认走 Flash。

解决方案是加入 Keyword Fallback 作为第二层保障。即使 LLM 返回了 flash，系统也会通过关键词检测来验证这个决策是否合理。比如检测到"分别""同时""对比"等并行信号词，就会将 flash 或 pro 升级为 ultra；检测到"分析""为什么""原因"等推理词，就会将 flash 升级为 thinking。这个 fallback 逻辑只有约 60 行代码，零额外延迟，但将弱模型的路由准确率从 60% 提升到了 95% 以上。

Plan 节点还有一个有趣的设计：它会分析生成的 TODO 步骤之间的依赖关系，如果发现步骤之间互相独立（比如"搜索 React 技术栈"和"搜索 Vue 技术栈"），会自动将 Pro 模式升级为 Ultra 模式进行并行执行。这意味着即使 Router 选了 Pro，系统也能在规划阶段发现并行优化的机会。

## 中间件洋葱模型：横切关注点的优雅解法

在设计 TinyFlow 的过程中，笔者面临一个架构选择：TODO 状态管理、循环检测、上下文压缩这些横切关注点，是放进 Graph 节点还是单独抽取？

如果把所有逻辑塞进节点，每个节点都要处理"注入 TODO 状态""检测循环""压缩上下文"等与核心逻辑无关的事情，节点会变得臃肿且难以测试。更关键的是，不同执行模式需要不同的横切关注点组合——Flash 不需要任何额外处理，Thinking 只需要上下文压缩，Pro 和 Ultra 则需要完整的 TODO 管理和循环检测。

最终笔者借鉴了 Koa 的洋葱模型，设计了一套中间件系统：

```text
class Middleware:
    def before_node(self, state, node_name):
        """节点执行前拦截，可修改 state"""
        return state

    def after_node(self, state, node_name, output):
        """节点执行后拦截，可修改 output"""
        return output
```

中间件链的执行顺序遵循洋葱模型： `before_node` 按正序执行（mw1 → mw2 → mw3）， `after_node` 按逆序执行（mw3 → mw2 → mw1）。每条执行路径拥有独立的中间件栈配置：

```text
MIDDLEWARE_STACKS = {
    "flash":    [],
    "thinking": [ContextCompactionMiddleware],
    "pro":      [TodoMiddleware, ContextCompactionMiddleware, LoopDetectionMiddleware],
    "ultra":    [TodoMiddleware, ContextCompactionMiddleware, LoopDetectionMiddleware],
}
```

三个中间件各自解决一个明确的问题。

**TodoMiddleware** 负责将执行计划的当前状态注入到 LLM 上下文中。它在 `before_node` 时将 TODO 列表格式化为易读的文本（用 ○/◉/✅/❌ 标记状态）追加到消息中，让 LLM 知道"你现在做到哪一步了"。在 `after_node` 时，它从节点输出中读取 `completed_todo_ids` 和 `failed_todo_ids` ，更新对应项的状态。这是一种"约定优于配置"的设计——节点不需要知道 TodoMiddleware 的存在，只需按约定在输出中包含 ID 列表。

还有一个容易被忽略的细节：当 ContextCompactionMiddleware 压缩了消息历史后，之前注入的 TODO 信息可能随之丢失。TodoMiddleware 会检测这种情况，在下一次 `before_node` 时自动重新注入完整的 TODO 状态，确保 LLM 不会因为上下文压缩而"忘记"执行计划。

**ContextCompactionMiddleware** 解决长对话的上下文溢出问题。当消息数超过阈值（默认 30 条）时，它保留前 2 条消息（系统提示 + 用户原始请求）和最近的 N 条消息，丢弃中间部分。前 2 条消息之所以不能丢，是因为系统提示定义了 LLM 的行为，原始请求定义了任务目标——丢失任何一个都会让 LLM "迷失方向"。

**LoopDetectionMiddleware** 提供双重循环保护。硬限制是 `max_iterations = 3` ，到达后强制终止。软限制是比较本轮输出与上一轮输出的文本相似度（使用 `difflib.SequenceMatcher` ），如果超过 0.9 则视为无实质性改善，提前终止。这里选 SequenceMatcher 而非余弦相似度，是因为它基于最长公共子序列，更擅长捕捉"内容几乎相同但措辞微调"的情况——而这正是 LLM 陷入循环时的典型表现。

中间件系统还有一个重要的韧性设计：任何中间件的异常都会被捕获并记录日志，但不会中断 Graph 的执行。中间件是"增强"而非"必需"，它的失败不应该影响核心编排流程。

## 并发执行：双线程池与 Per-Thread Stream

并发是 TinyFlow 中工程挑战最集中的领域，它同时涉及后端的多任务并行执行和前端的多线程流式渲染两个难题。

## 后端：Scheduler + Execution 双线程池

LangChain 内部大量使用同步阻塞 I/O，直接在 asyncio 事件循环中运行会导致死锁。笔者的解决方案是采用双线程池架构：

```text
Scheduler Pool (3 workers)     Execution Pool (3 workers)
  - 超时监控                      - 实际 LLM 调用
  - 生命周期管理                   - 工具执行
       │                               ▲
       └─── submit() ──────────────────┘
             通过 Future 通信
```

为什么需要两个池？假设只用一个线程池：Scheduler 提交任务后调用 `future.result(timeout=300)` 等待执行完成，而 Execution 也在同一个池中运行。当所有 worker 都在执行任务时，新的 Scheduler 调度请求就无法获取 worker——死锁。双线程池通过职责隔离彻底避免了这个问题，Scheduler 和 Execution 各自拥有独立的资源，通过 Future 通信。

Pro 模式和 Ultra 模式在执行策略上有明确的区分。Pro 模式采用顺序执行——每次图调用只执行第一个 pending 任务，完成后由 Reflector 决定是否继续。这样的好处是每个 TODO 都能通过 SSE 事件实时更新状态，用户能看到清晰的执行进度。Ultra 模式则将所有任务并发提交到 Execution Pool，使用 `as_completed()` 非阻塞收集结果，最后由 Merge 节点合成综合回复。

SubagentRunner 的内部还采用了两阶段执行模式：Phase 1 是确定性搜索（生成查询词 → 调用 web_search），不依赖 LLM，确保基础数据获取的可靠性；Phase 2 是 LLM 报告生成，基于搜索结果合成结构化报告。如果 Phase 2 失败，系统会 fallback 到原始搜索结果，不至于整个任务失败。这种"确定性优先"的设计哲学贯穿了 TinyFlow 的多个模块。

## 前端：从串流噩梦到 Per-Thread Stream 架构

前端的并发问题是笔者在 TinyFlow 开发中踩过的最痛的坑。

初版 `useChat` Hook 使用全局共享的 SSE 状态—— `isStreaming` 、 `messages` 、 `steps` 都是全局的。问题在于，当用户在线程 A 发送消息后切换到线程 B 时，线程 A 的后续 SSE 数据会错误地渲染到线程 B 的界面。更糟糕的是，当线程 A 在后台完成时，它的数据因为 React 状态已被线程 B 覆盖而彻底丢失——切换回线程 A 时一片空白。

这个问题的根因是将"数据持久化"和"UI 渲染"耦合在了一起。 `setState` 既是数据的存储，也是 UI 的驱动，而 React 状态同一时刻只能属于一个线程。

解决方案是 Per-Thread Stream 架构，核心思路可以概括为一句话： **先写 buffer，再条件同步** 。

每个线程拥有独立的 `ThreadStream` 对象，包含一个持久 buffer（存储完整的 messages / steps / todos / mode）、一个 AbortController（用于取消请求）和一个 running flag。SSE 事件始终写入对应线程的 buffer，而非直接 `setState` 。只有当 `isCurrent(threadId)` 为 true 时——也就是该线程正是用户当前正在查看的线程——才将 buffer 的数据同步到 React 状态驱动 UI 更新。

```text
SSE Event → 写入 ThreadStream.buffer (始终执行)
                ↓
         isCurrent(threadId)?
           ├─ Yes → setState 同步到 UI
           └─ No  → 静默，数据安全保存在 buffer 中
```

切换线程时，从目标线程的 buffer 中恢复全部状态，耗时不到 16ms（一帧）。这里用 `useRef` 而非 `useState` 来存储 `activeThreadId` ，是为了避免闭包过期问题——SSE 回调函数中需要读取最新的活跃线程 ID，而 `useState` 在闭包中会捕获旧值。

这个架构的本质是将数据持久化与 UI 渲染彻底解耦：buffer 是"真相来源"（source of truth），React 状态只是 buffer 的一个视图。这种模式不仅解决了串流和数据丢失问题，还天然支持 N 个线程同时并发运行、互不干扰。

## 记忆系统：让 Agent 记住用户但不膨胀 Context

LLM 应用的一个常见痛点是"金鱼记忆"——每次对话都从零开始。TinyFlow 的记忆系统试图解决这个问题，同时避免记忆数据膨胀 context window 导致性能下降和成本增加。

整个系统是一个四阶段 Pipeline：

**Extract** （提取）：每轮对话结束后，LLM 从对话中提取四类事实——preference（用户偏好）、context（背景信息）、behavior（行为模式）、knowledge（知识储备）。比如从"我是做前端的，主要用 React"中提取出一条 preference 类型的 Fact。提取在后台异步执行，不阻塞对话响应。

**Score** （评分）：每条 Fact 通过三个维度评分，最终置信度公式为：

```text
confidence = 0.3 × explicitness + 0.4 × repetition + 0.3 × consistency
```

其中 explicitness 衡量用户陈述的直接程度（明确说出的 0.9，间接推断的 0.5），repetition 衡量重复提及的频率（每找到一条语义相似的已有 Fact 就 +0.3），consistency 检查与已有 Fact 是否矛盾（通过 LLM 判断）。

**Merge** （合并）：新 Fact 与已有 Fact 的合并策略基于字符序列相似度。相似度 ≥ 0.75 视为语义重复，合并并取较高置信度。相似度在 0.5 到 0.75 之间且同类别，可能是矛盾——调用 LLM 做一次判断，确认矛盾则新 Fact 替换旧 Fact（旧 Fact 不删除，标记为 `replaced` ，保留审计轨迹）。相似度 < 0.5 视为全新内容，直接追加。

**Inject** （注入）：每轮对话开始时，从 Fact 库中选取最相关的 Fact 注入到 LLM 上下文中。选取排序的依据是置信度与时间衰减的乘积：

```text
sort_key = confidence × (1.0 / (1 + days_since_verified / 30))
```

同时设置了 500 token 的硬性预算——使用 tiktoken 做精确计数，按排序依次加入直到用完预算，最后按 category 分组格式化。

时间衰减还有一处设计取舍：只有 `access_count < 3` 的 Fact 才会衰减。如果一条 Fact 被频繁访问（比如用户多次提到的偏好），说明它是重要的长期记忆，不应因时间流逝而降低置信度。

## 技能系统与 SSE 流式协议

## 两阶段技能路由

TinyFlow 的技能系统采用 YAML frontmatter 格式定义技能，支持文件变更热重载：

```text
---
name: deep-research
triggers: [research, 研究, 调研, deep research]
execution_mode: subagent
tools: [web_search]
priority: 15
timeout: 300
---
你是一个深度研究专家...
```

技能路由分两阶段。Phase 1 是关键词预过滤——O(n) 扫描所有技能的 triggers，筛选出 3-5 个候选。Phase 2 是 LLM 语义精选——仅对候选集调用 LLM，选择最匹配的技能。全量 LLM 路由的成本太高（假设 30 个技能 × 50 tokens = 1500 tokens/次），两阶段路由在精度和成本之间取得了平衡。

技能还区分两种执行模式： `prompt_injection` 将技能内容注入当前 agent 的 system prompt，零隔离开销，适合轻量技能； `subagent` 为技能创建独立 subagent，拥有专属工具集和超时控制，适合需要复杂工具调用的场景。

## 12+ SSE 事件的层次化设计

SSE 流式协议是连接后端编排引擎和前端渲染的桥梁。TinyFlow 定义了 12+ 种事件类型，覆盖了从路由决策到执行进度到最终输出的完整生命周期：

```text
mode_selected  → 告诉前端当前选择了哪种执行模式
thinking       → 推理过程的可视化
todo_update    → 执行计划的状态变更
tool_call      → 工具调用开始（查询词 + 150 字符预览）
tool_result    → 工具调用完成
subagent_status → 并行任务创建
subagent_result → 并行任务完成
content        → LLM 输出的逐 token 流式内容
context_compacted → 上下文被压缩的提示
loop_warning   → 循环检测触发
done / error   → 流结束或异常
```

这里有一个实现上绕了弯的地方：LangGraph 原生的 `astream` 方法只能在节点完成后输出完整结果，无法做到逐 token 流式。笔者最终通过 `astream_events(version="v2")` 替代 `astream` ，监听 `on_chat_model_stream` 事件获取逐 token 输出，将首 token 延迟降到了 200ms 以内。同时，并非所有节点的 token 都需要流式推送——Router 节点的输出是内部决策，不应暴露给用户，因此 SSE 层会按节点名称过滤，只转发 respond、think_respond、reflector 等用户可见节点的输出。

## 总结：开源贡献教会笔者的事

从 DeerFlow 贡献者到 TinyFlow 独立作者，这个过程让笔者对"如何参与开源"和"如何做架构设计"有了更真切的认识。

带着"这个设计为什么这样做"的问题去读源码，你看到的不只是代码，而是一系列工程决策的权衡。笔者发现 DeerFlow 的并发文件冲突问题，就是在追踪一个看似简单的功能时，碰到了多 agent 共享文件系统的隐含假设。深入到这个程度，贡献代码其实是水到渠成的事。

PR review 中 maintainer 的反馈也让笔者受益良多。他们看到的不仅是你改的那几行代码，还有这些改动对整个系统的潜在影响——这种全局视角是靠自己读代码很难获得的。要做的就是放下"自己已经想清楚了"的执念，认真吸收这些反馈。

至于 TinyFlow 本身，它的 ~3000 行代码不是对 DeerFlow 做减法，而是回到"multi-agent 编排引擎到底要解决什么问题"这个原点，重新做了一次除法。删减是去掉不需要的东西，而精简是找到那个最本质的"1"。

TinyFlow 已在 [GitHub](https://github.com/venaissance/tiny-flow) 开源，欢迎 Star 和贡献。
