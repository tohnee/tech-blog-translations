Gemini 2.5 在玩《宝可梦》的时候，曾经反复犯过一个毛病：它认准了自己必须去给门卫找茶喝。

玩过这游戏的人知道，在 1996 年 Game Boy 上的原版《红》里，想要通过关卡，得给饥渴的守卫带柠檬水；而到了 2004 年 GBA 上的复刻版《火红》，游戏把道具改成了冰茶。模型在玩原版游戏时，权重里的《火红》记忆被勾了出来，硬生生把“去找茶”塞进了自己的待办清单。一旦写进了上下文，它就再也绕不过去，整整几个小时都在原地打转。

用过各种 coding agent 的人对这种场面不会陌生：模型认准了一个根本不存在的依赖、咬死了一个早被推翻的假设，在上下文里绕圈子，任你发再多消息也拉不回来。

这类问题这三年里换了三个名字：2023 年叫提示词工程（prompt engineering），2025 年叫上下文工程（context engineering），到了 2026 年，大家又开始叫它 harness 工程（harness engineering）。

这番梳理出自 Drew Breunig 最近在 AGNTCon 上的演讲《Context Fails & Fixes》。文字版发出来后，在 Hacker News 首页拿到了 182 分。他目前正在写一本 O'Reilly 的上下文工程手册。这篇盘点最清醒的地方在于：他没有顺着厂商宣传的长上下文鼓吹奇迹，而是指出不管名字怎么变，大家面对的一直是同一道题——这一轮，模型到底该看什么，不该看什么。

2023 年做提示词工程，核心是人在聊天框里敲敲打打，为单次模型调用精挑细选词句和几个少样本示例。

到了 2025 年改叫上下文工程，事情没变，只是这一过程自动化了（except that now it was more automated）。你不再手动复制粘贴背景资料，而是由系统通过检索、模版动态拼装上下文。

到了 2026 年，大家发现工具光塞进上下文不行，必须搬进代码，于是名字变成了 harness 工程。Breunig 给出的总结很准：

> "We're moving more and more of the work of assembling context from probabilistic model calls to deterministic code."<br>（我们正把拼装上下文的工作，越来越多地从概率性的模型调用，挪进确定性的代码里。）<br>

所谓 harness，本质上就是包在模型外面的那个脚手架程序。这道判断题从来不是“该用什么玄学提示词”，而是“什么该写进确定性的代码，什么该交给概率性的模型”。

很多人的直觉是模型不行就换更大的底座，或者调高思考时间（thinking tokens）。但 Breunig 给了一句非常务实的提醒：与其指望模型自己变聪明，不如先把上下文改干净，“其中一个是又便宜又快的”（One of those is cheap and fast）。

要改好上下文，得先看它是怎么坏掉的。

## 上下文是怎么坏掉的：四种坏法

长上下文从来不是免费的午餐，窗口越大，能装的毛病就越多。Breunig 把失败归纳为四类：

第一种是**中毒（Poisoning）**：不该进来的东西进来了（something gets into the context that shouldn't be there）。开头的宝可梦冰茶就是典型例子。哪怕只是历史记录里进了一条错误的命令、一个假想的文件路径，模型就会死咬着不放。

第二种是**分心（Distraction）**：上下文太长，模型开始盯着上下文的历史，反而丢掉了自己的底座知识（the context grows so long that the model starts to focus on the context over its base knowledge）。

Google 在 Gemini 2.5 的技术报告附录里写过一个观察：当上下文显著超过大约 100K token 时，agent 会表现出一种倾向——反复机械重复历史里做过的动作，而不再构思新的方案。学者 Camassa 和 Shiller 在论文《Do as I Say, Not as I Do》里做过一个实验：给模型一个明确指令“把所有问题都翻成俄语”，但在历史对话里放进一堆用法语回答的矛盾示例。测试了 13 个模型，最多加到 50 轮矛盾示例。结果很残酷：像 Gemma 3 12B 这种小模型，几个矛盾示例一加，遵守原指令的概率就掉到一半以下；Claude Opus 4.6 算坚持得久的，但轮数多了照样飘移。Breunig 的评价是：“这毛病每个模型都有！”（this affects every model!）你在做前端调整时和 agent 来回拉扯留下的几十轮废弃代码，本质上就是在给它投毒和分心。

第三种是**混淆（Confusion）**：无关的事实混了进来，以我们理解不了的方式影响模型。Breunig 举过自己的例子：如果 ChatGPT 或 Claude 的全局记忆开着，往往会把工作对话和他跟儿子一起做的手工项目搅在一起，模型基于这些杂乱记忆擅自假设“你是谁”，回答立刻就变味了。

第四种是**冲突（Clash）**：脚手架里的各种工具调用、skill 和外部说明互相打架，彼此抵消。

这四种坏法串在一起说明了一件事：模型越强，它的失败越不是因为“不会”，而是因为“看到了太多不该看的东西”。

## 往窗口里塞什么：增补与精选工具

为了对付这些问题，工程上逐渐沉淀出六个基本手段：增补（augmentation）、精选工具（tool loadout）、隔离（quarantine）、修剪（pruning）、卸载（offloading）、摘要（summarization）。

先看输入端：往窗口里放什么。

最常见的误区是觉得模型既然支持 1M 甚至 2M token，那就全塞进去。Breunig 提到一家企业，他们的内部软件在启动时会给每位工程师的 agent 一口气加载 600 个 skill，结果模型能力直接崩塌。他的建议很朴素：老老实实写个 loadout 过滤函数，按需加载。

我们在 10 月份为了把公司知识从各家 agent 的私有记忆里抽出来，做过一轮深度调研，当时的几个硬数字正好能印证这个结论：

1. **SkillsBench 的评测**：人工精选整理的 skill 能把平均通过率从 33.9% 提升到 50.5%（v4 数据，净增约 16 个百分点；v1 数据提升 16.2 个百分点）。但 v1 的摘要里写了一句很硬的话：“模型自己生成的 skill 平均而言没有任何收益”（Self-generated Skills provide no benefit on average）。而且，只有 2 到 3 个模块的高度聚焦型 skill 明显优于大而全的文档包。在软件工程领域，skill 的提升只有区区 4.5 个百分点，84 个任务里甚至有 16 个带来了负收益。
2. **苏黎世联邦理工学院（ETH Zurich）对 AGENTS.md 的评测**：作为上下文的常驻文件，整体上并不能提高任务成功率，反而让推理成本平均增加了 20% 以上。很多人喜欢在里面写大段的仓库架构概述，但这根本没用，只有非常规的特定编码约定才起效。
3. **Vercel 的评测**：在 56% 的测试用例里，提供的 skill 根本就没被模型调用过。默认给 skill 的通过率只有 53%，跟什么文档都不给完全一样。最后他们把约 40KB 的文档索引硬压到 8KB 直接塞进 AGENTS.md，通过率才达到 100%。

看到这些数字，再看我们自己的机器，病根就一目了然了。

10 月中旬我们盘点这台用来跑全公司业务的 Mac 时，发现 Claude Code、Codex、Gemini、Grok 的全局指令位置全是空的。“tmux 怎么给另一个窗格发消息”这件小事，在 5 个地方被记了 5 遍，写法互相冲突（有的要求 Enter 键单独发，有的把字符和回车打在同一行）；“回中文、讲大白话”这类偏好，被 3 个项目各自学了一遍。知识不是太少，而是没分发出去，越记越乱。

于是我们定了几条死规矩：

- **常驻文件必须极简**：公司级 AGENTS.md 定了不超过 120 行、不超过 8KB 的预算（这是我们定的预算约束，不是什么测算出来的物理最优值）。仓库概述一律不写，只写模型从代码里推不出来的东西：偏好、机器级事实、入口命令、硬性红线。那些从对话里推断出来的规则，一律先进候选区，可以查，但不常驻，等我每周看报告回一个“行”字才生效。
- **Skill 要少而克制**：公司级 skill 起步不超过 15 个，description 全写成具体的触发场景。这里有个大坑：项目里放在 `.agents/skills` 目录下的 skill，Claude Code 原生根本扫不到（它只看 `.claude/skills`），装了不等于看得到，看得到也不等于会用。
- **测一测有没有被调用**：Anthropic 内部用 PreToolUse hook 记录 skill 的每一次调用，专门揪出那些“比预期触发得少”的 skill。我们也打算照这个思路做调用计数，没有触发的数据做支撑，写再多 skill 都只是在自我感动。

## 把什么隔开，把什么拿出去：隔离、卸载、修剪与摘要

决定了放什么之后，剩下的动作就是怎样把东西隔开，或者移出上下文。

**隔离（Quarantine）**是让子 agent 从一张白纸开始。我们在做跨模型讨论的“会议室”工具时，主干调用（`claude -p`、`codex exec`）全部采用独立的一次性进程。每一轮模型之间的互看，都是另起一个全新的会话把必要材料喂进去，绝不接着第 0 轮的原会长聊。把旧历史隔绝在外面，才能拿到不受污染的独立意见。

**卸载（Offloading）**是把状态存进文件或数据库。我们把长文岗设计成一个用 git 管理的目录，里面包含章程、标准 skill、JSON 契约和追加式的 JSONL 账本。不管是 Claude Code 跑还是 Codex 跑，谁来都是接手这个文件夹，而不是在某个平台里捏一个绑死的人格。

为什么一定要把状态卸载到普通文本文件里？因为“文件活得比编排器久”。Devin 原生自带的 Knowledge 已经标为 deprecated，转向通用的插件；红极一时的 Vibe Kanban 也在 4 月停服了。我们自己盘点过 190 个记忆文件，发现里面有 27 条其实是重要的技术决策，但其中 20 条没指向任何仓库文件，只活在某家 agent 的私有存储里。现在我们改成每晚自动扫一遍，硬把这类决定捞出来写进仓库。

至于**修剪（Pruning）与摘要（Summarization / Compaction）**，现在的 Claude Code 和 Codex 已经在后台默默做了，经常发生在你没留意的时候。Breunig 的建议是在做摘要之前，先用轻量级规则按相关度过滤一遍，别把所有垃圾一股脑打成摘要包。

但这里有一个致命盲区：摘要治不好模型的执念。

## 模型变强之后的新毛病：打架与惯性

当模型和 harness 变得越来越深，老毛病还没除干净，两个新毛病又冒了出来。

第一个毛病是**和权重打架（Fighting the weights）**。

模型在预训练和后训练时接触过特定的工具格式，你换一套它就极度别扭。Breunig 举了 Playwright MCP 的例子：像 Haiku 或 Luna 这类较小的模型，第一次调用这个工具时经常会把参数搞砸。你看很多工具的系统提示词里喜欢用全大写字母咆哮，比如 Claude Code 系统提示里写着 "you MUST send a single message with multiple tool use blocks"。如果在你的项目规则里，也密密麻麻写满了大写的 "MUST" 和 "NEVER"，往往说明你正在跟模型的内在权重较劲。

第二个毛病更隐蔽，也更要命，叫做**上下文惯性（Context Inertia）**。

模型会死死盯住上下文里的某个假设、子任务或思路，哪怕证据已经表明走不通，它该停的时候也停不下来。微软研究院在论文《Fork-and-Flush》里指出了这个现象：在长时间运行的任务里，模型的成绩往往在早期跳升，随后很快进入漫长的平台期。此时 agent 并没有闲着，但它做的改动越来越细碎微小（tinier and tinier changes），完全被最初的思路锁死。同一个配置跑 8 次，最终分数能从 68.3 波动到 100。

很多人以为跑一次 compaction 压缩一下上下文就好了。Breunig 在 10 月中旬的文章里特别提醒：**压缩摘要根本治不了上下文惯性**。因为摘要的逻辑是提取“当前进行中的关键任务”，这正好把导致执念的那份工作原汁原味地保留了下来，模型读完摘要，接着回去钻牛角尖。

## 学会遗忘：长会话该在哪重置，200K 怎么用

既然压缩没用，唯一的解法就是让它遗忘。

Anthropic 在关于模型自复制能力的研究里，公布过他们做的一个叫 Memento 的脚手架。它的运行机制非常暴力：每隔 1.5 小时（单任务上限 6 小时），让 agent 写一份简短的笔记本，列出自己试过了什么策略、遇到了哪些失败、当前的成绩如何。然后，**直接杀掉这个实例，重新开一个全新的 agent 跑**。新实例继承工作区的代码环境和这份笔记本，而之前的整段长会话彻底灰飞烟灭（the running conversation is gone）。

加州大学伯克利分校和斯坦福大学的 Matei Zaharia、Alex Dimakis 等人，在 10 月中旬提交的论文《Scaling Discovery Requires Forgetting》里得出了几乎完全相同的结论：不管是让单个 agent 跑更久、让多个 agent 并行，还是让并行 agent 互相通信，这三种扩展方式最终都会撞上平台期。agent 会被自己过去的尝试锚定，陷入内耗。论文给出的数据是：定期丢掉历史搜索状态、只带着当前最好的候选重新出发，效果比并行 agent 团队高出最多 15%，比单个 agent 跑到底高出最多 39%。在 Breunig 演讲展示的幻灯片说明里，带遗忘机制的 4 人 agent 团队测试分数一路攀升到了 1,144,695，而没有遗忘的并行团队停在 1,007,073，单 agent 只有 961,136。

这彻底颠覆了“上下文越长越好”的直觉。Breunig 给出的实操经验是：

> "Around 200,000 tokens is my warning point."<br>（大约 200,000 个 token 是我的警戒线。）<br>

一旦 agent 表现开始怪异，先别忙着改提示词，问问自己：你试过重置上下文了吗？

我们自己账本上的教训比论文来得更痛。今年 7 月我们跑视频流水线 contentagent 的时候，第 4 关渲染和收尾阶段图省事，顺着第 3 关的长会话继续聊。结果 92 次工具调用，每次都拖着大概 180K 的臃肿上下文，光这一截就烧掉了 16.5M token，占了整单总消耗的 23%。

复盘之后我们立了一条硬规则：每个关键阶段结束，必须强制切断、另起新会话。改掉之后，同等规模任务的总消耗从 106.9M 降到了 72.5M，直接省了 32% 的 token。即便这样，由于基础常驻文档当时膨胀到了 33KB，每轮平均消耗仍有 113K–128K，逼得我们又专门立项给文档瘦身。

结合这些教训，在日常写代码和开长任务时，可以守住三条习惯：

1. **把 200K 当成报警线，而不是硬撑到底的目标**。真正该重置上下文的节点，是自然的阶段边界：一个子任务完成了、一个 PR 提了、或者发现模型开始在同一个 bug 上改来改去的时候。
2. **重置前把东西落盘**。会话可以丢，工作成果不能丢。交接文件（比如 `HANDOFF.md`）要整篇重写覆盖，而不是一路往下追加（实测追加式交接不仅读得慢，还会产生陈旧冲突）。交接文件里附上一句切换原因，加一句可以直接复制到新窗口的开工指令。
3. **规则和记忆通常只在开工时读一次**。你在外面改了规则文件，老会话往往根本感知不到。我们设置了机制，让空闲超过 30 分钟的窗格自动重启，就是为了让它能重新读入最新的规则。

## 另一面：学出来的记忆，但必须有人判对错

聊到这里，事情似乎推向了一个极端：模型生成的记忆全不可信，长上下文全该砍掉，越干净越好。

但 IBM Research 在 10 月 20 日发布的 ALTK-Evolve 拿出了一个完全相反的实验结果：**记忆不仅有用，还能全靠模型自己总结出来，甚至能直接打榜拿第一。**

在客服基准 τ²-bench 上，他们用较老的基座模型 gpt-4.1，完全不微调权重，只是分析 agent 在训练任务里的轨迹，让模型自己提炼出一套简短的行为规则（比如“在做任何订单操作前先验证用户身份”）。每条规则带一个命中次数统计，直接贴在系统提示词后面。

结果很惊人：在 10 月 12 日的排行榜快照里，在完整的 base split 上，这个带学来记忆的 gpt-4.1 在零售域拿到了 67.5% 的 Pass^4，登顶第一，甚至压过了专门在合成数据上微调的领域模型 RAFT-30B-A3B（61.4%）；在航空域把模型换成 gpt-5.5 后，更是打出了 82.0% 的高分。

更有意思的反转在于规则数量：在零售域的测试集里，他们保留了全部提取出的 292 条规则（lossless 版本），各项指标全面碾压只保留 31 条高频规则的精选版（IBM 原文写道：more is better on every metric）。但在航空域，保留较少规则的版本表现反而更好。IBM 自己的结论是：保留多少记忆，是个需要按业务领域具体微调的旋钮（a knob worth tuning per domain）。

这怎么和前面 SkillsBench“模型自写 skill 没有收益”的结论对得上？

关键在于有没有**可靠的判决信号**。τ²-bench 的评分极其苛刻，它是以最终数据库的状态做严格的二元判定（对就是对，错就是错），提取规则时背后有实打实的任务成功数在支撑。关于这一机制，前人的研究 ACE 也是同样结论：在有执行环境真实反馈时，累积记忆能提 10 到 17 分；一旦失去可靠信号，记忆库很快就会退化成垃圾场。

这一点我们踩过完全相同的坑。10 月下旬我们让模型自动从历史报告里抽沉淀结论卡，抽出来的 65 张卡交给 Codex 逐张回放核对，结果只有 42 张是立得住的，整整 23 张存在过时、断章取义或把话说得太满。从那以后我们立了规矩：模型抽取的经验卡必须经由另一个模型逐张审核，只有对齐原文事实的才打上“已核对”标签。同时，公司的全局知识库绝不允许程序自动提交，因为一旦把没经过验证的推断同步出去，它会在下一次会话时污染所有的 agent。

另外也得说明 ALTK-Evolve 的局限：测试集的规模其实很小（零售 40 题、航空 20 题），只是单一基准，数据也是作者自报；而且保留 292 条规则让单次对话的成本直接暴涨了 65%。

## 结尾

回过头看 Breunig 在演讲最后说的那句话：

> "As we focus more on memory, we also need to think about strategic forgetting. Over time, overly precise memories become conflicted and messy, and nobody has yet figured out how to handle this."<br>（当我们越来越关注记忆时，我们也必须考虑有策略的遗忘。随着时间推移，过度精确的记忆会变得冲突而混乱，而至今还没有人真正解决这个问题。）<br>

我们在自己的 Mac 上排查出的那 5 份互相打架的 tmux 经验，无非就是这句话在单机环境下的一个缩影。

从提示词工程，到上下文工程，再到 harness 工程，三年换了三次叫法。但剥开那些不断翻新的名词，我们面对的问题没有变过：这一轮，模型该看什么。

唯一的区别在于，大家终于从“大模型能吞下整片互联网”的幻觉里醒了过来，开始老老实实写代码，做过滤，做隔离。而比“该让模型看什么”更难、也更见功力的那一半，恰恰是：

想清楚该在什么时候，让它彻底忘掉。
