## 写在前面

$\mathbf{\color{purple}{归根结底，当前的同步机制在性能上依然存在不少硬伤。如果我们能在硬件层面同时支持增强版 mbarrier 与异步同步引擎的乱序能力，就能真正把开发者从繁重的同步性能分析中解放出来，实现“好写”与“高效”兼得的极致泛化能力}}$

这一篇文档想把 AI 芯片中同步（sync）设计的优缺点、以及它在具体场景里的细节讲清楚。

首先说明一点：**同步的不同设计方式和上层提供的编程范式是强相关的**。而这篇聚焦 "同步本身怎么做"，而我认为比较好的编程范式[**怎么解决数据流架构的编程问题**]，会单独用一篇文章来讲，这里先不展开。

我这里会从**功能**和**性能**两个方面，介绍同步的实现和优化方式。

## 同步的本质：AI 芯片里的 scoreboard

AI 芯片中的 sync，和cpu一样，都是用来解决**多个异步执行单元之间的数据依赖关系**。

本质上，它和 CPU 中的 scoreboard 是**相同的定位**。如果这样类比的话，scoreboard 中遇到的各种问题，sync 也都会遇到 —— 这一点是我们后面讨论性能问题的前提。

## 各家厂商的同步方案，大致分几类

目前看了这么多厂商的 sync 处理方式，主要分为几类：

**1. CUDA 为代表的细粒度同步（mbarrier）** 吸取c++的理念的融合同步范式。

> 用户在 CUDA-C 这个粒度上，可以随意调用。这个新 sync 模式，本身就是为了解决引入 TMA（Tensor Memory Accelerator，纯异步 DMA）之后带来的同步控制问题。通过适配 NVIDIA 最新的 warp-specialization 编程方式，很好地实现了类似的功能。

**2. AMD 这种上一代的同步模式** 主要是 "花式地通过 barrier" 的方式来实现，**个人感觉后续应该也会参考 NVIDIA 的方式来演进**。

3. **大量npu采用的精简同步方案：**

> **华为，google-tpu 都是采用的这种方案。 通过类atomic的同步方式来实现单向的数据依赖。这种同步方式遇到多对多的生产消费关系就捉襟见肘了。同时还会受到循环翻转的影响。**

## 为什么需要 独立的sync语义：

引入独立的sync编程方式，也是为了提升性能，而引入的两个核心变化：**异步执行单元** & **基于内存的数据依赖**。

**异步执行单元：**

> 将超长指令独立处理，降低cpu的等待负载。

**基于内存的数据依赖：**

为什么底层编译器搞不定 `__shared__` 内存的同步呢？

> 对于 NVIDIA 来说，处理 `__shared__` 上的资源同步问题，存在各种离散的数据判断、动态的排布，底层编译器基本上**不大可能实现基于静态分析的同步处理**。<br>注意，这里说的是**底层编译器**。高层编译链路 —— 比如 Ascend-TIK、Triton 这类高层编译语言 —— 还是有可能实现相应功能的。<br>而底层编译器解决不了的核心问题，归根结底是：**`__shared__` 在编程粒度层面，就是一块内存。**

**解决办法：**

既然 `__shared__` 必须是内存，那**如果非要做到“让软件完全不管同步”，硬件/架构上有什么路可以走？** 仔细想一下，无非就三种可能：

1. **硬件动态分配（像 TCGCN05 方案）**：硬件提供 alloc/dealloc 指令，底自由维护一个简单的线性分配器。每次异步任务发起时，去分配器里查地址。这相当于把 CPU 的 Scoreboard 查表机制搬到了内存上，拿一个唯一的 Handle/ID 来做匹配。
2. **纯软件维护分配表**：编译器或者 Runtime 在软件层维护一个分配表，每次执行都去查表拿 Task ID，类似于 Linux 里的 malloc/free。但这种纯软件的方案太繁琐了，运行期开销（Runtime Overhead）极大，在算子性能要求极其苛刻的场景下**基本不可用**。
3. **放弃存储/内存概念**：直接不当 Memory 了，当成一个巨大的 Register File 来用。但这样一搞，非对齐访问和动态数据的灵活性就全废了。

**结论很明显**：既要兼容内存语义的灵活性，又要降低同步的编程复杂度，目前看下来最接地气的解法，依然是**提供一个硬件层面的同步能力，让软件显式去显式调用（类似于 CUDA 的 mbarrier）**。

## mbarrier 的原理：MPMC 环形队列的槽位控制

mbarrier 的实现原理，本质上也是 follow C++ 中通用的实现方式 ——**多生产者多消费者（MPMC）环形队列的槽位控制**，就是采用这个方式的。它用来解决的是 "错位" 问题：**过渡生成（over-produce），或者过渡消费（over-consume）**。

> （顺带一提，mbarrier 中有一些功能我个人感觉意义并不大，比如其中的 tx-count。）

$\mathbf{\color{red}{但这里要指出一个关键问题：这种串行的 barrier 功能，在实际的动态场景下，会存在一个非常明显的性能问题 —— 串行任务阻塞资源队列的超发。}}$

## 一种通用的，类mbarrier的同步扩展：

AI 芯片里的 Sync，本质上就是解决各种异步执行单元（DMA、Tensor Core、Vector Core）之间的数据依赖。这和 CPU 里的 Scoreboard 定位完全一样。

NV 的 `mbarrier` 确实给全行业做了一个很好的示范。但在实际使用中,（比如 `tx-count`）略显繁琐，实际场景用处没那么大。

要实现一个逻辑完备的多对多（Many-to-Many）生产消费同步，硬件底层的存储里，其实只需要固定这 **5 个核心位域**：

![](https://pic2.zhimg.com/v2-139421f6ee9fa97e0f0837ca77b7c68d_r.jpg)

简单通俗地解释一下这几个字段是干嘛的：

- **`phase_bit`**：**阶段位**。专门用来解决乒乓/环形 Buffer 里的数据踩踏问题。生产-消费完成一圈，它就翻转一次。
- **`arrive_count` / `arr_expected_count`**：**多生产者控制**。所有参与同步的生产者（比如多个 DMA 搬运通道），干完活了就往 `arrive_count` 上加 1。当 `arrive_count == arr_expected_count`，说明数据凑齐了，统一喊下游来消费。
- **`release_count` / `rel_expected_count`**：**多消费者控制**。上游数据好了，下游多个 Consumer（比如多个 Tensor Core 线程）开始读数据。每人读完一次，`release_count` 加 1。当 `release_count == rel_expected_count` 时，说明所有人都吃干抹净了。
- **状态复位**：消费完成后，`phase_bit` 翻转，`arrive_count` 和 `release_count` 直接清零，迎接下一轮生产。

就这么简单的 5 个字段，就构建出了一个极其完备的**多对多生产消费同步机制**。

## 性能杀手：现在的 Sync 机制卡在哪？

原理很完美，但回到真实的芯片和算子场景，性能问题往往暴露得非常惨烈。

**串行 Barrier 导致的“资源队列超发阻塞”**

虽然用 Sync 解决了数据依赖，但大家常常忽略了另一个性能大头：**指令执行序**。

传统的 Sync 处理，本质上只是实现了**串行的资源绑定**。这就像是一个单发射的 CPU，所有资源的执行，同时受到了 **指令序列** 和 **Sync 关系** 的双重约束。

在实际的动态场景下，这会引发一个很严重的性能问题：**串行任务阻塞了资源队列的超发（Issue-ahead）**。

当上游任务因为动态数据抖动稍有延迟，后面的指令因为串行 Barrier 的死板卡位，全部被死死扣在发射阶段，无法提前发到具体的执行 Queue 里。硬件的并行能力根本拉不满。

**如下图这个实际的flash-attention的典型场景：**

![](https://pic4.zhimg.com/v2-ed0f4723b94705e9a41166715cb2a987_r.jpg)

这里的任务执行是完全依赖执行序列的，就**造成了 matrix 和 vector单元之间只能串行执行**。虽然有很多编程技巧可以缓解这个问题。[***人为改变执行序列的数据依赖关系，但这个方式还是太繁琐了***]

## 写在最后：Sync 模块的未来演进

怎么破局？

既然 Sync 本质上是硬件版的 Scoreboard，那我们完全可以在 `mbarrier` 的基础上，**给 Sync 模块赋予“乱序（Out-of-Order）”的能力**。

> 多线程也能解决这个问题，但多个执行线程会大大降低matrix的并行度，对性能会有负收益。

通过硬件 Sync 模块在底层的乱序解耦，不仅能把发射单元从串行等待中解放出来，大幅提升硬件的超发吞吐，还能极大降低上层软件和编译器的写代码/调度复杂度。

> **这个乱序模块，不用设计的像 传统cpu那么复杂， 因为有几个cpu复杂功能不存在：**<br>1. **同步的槽位，用户会自己绑定**。不用资源的动态分配。<br>2. **不需要分支预测。**任务的下发和执行是解耦的，通过执行单元的快速执行来解决传统cpu的提前发射问题。<br>3. **不用处理流水线恢复。**因为所以给到sync单元的任务都是确定性的，就省掉了这个功能。

$\mathbf{\color{red}{如果不考虑以上几点，纯sync模块的OoO还是很好实现的}}$
