这篇文章来自 Anthropic 官方博客，在技术圈传得挺广。

讲的是怎么搭 AI Agent 这件事。

如果你在做 AI 相关的产品，或者只是好奇 AI 系统到底是怎么运作的，这篇很值得读一读。

Anthropic 的工程师们做了大量企业级项目，然后把踩过的坑和摸出来的经验写成了这篇文章。核心结论有点反直觉：你以为越复杂的架构越好，他们说，很多时候简单反而更强。

## 一、为什么大家都爱搭复杂架构，但这往往是个坑

一家公司要做一个能处理所有事情的 AI，产品部有产品部的 AI Agent，客服有客服的 AI Agent，研究部有研究部的 AI Agent，最后再搭一个总调度员把它们串起来。

听起来分工很合理，每个团队管好自己那一块。

但实际运行起来，这套架构会引发一连串麻烦。

先说第一个，信息传递的损耗。每个sub Agent 完成任务之后，要把结果报告给总调度员（主 Agent），总调度员再传给下一个。每传一次，细节就丢一点，就像开会时转述别人的发言，转着转着就变味了。

然后是第二个，sub Agent 泛滥。每个团队造自己的 AI Agent，最后公司里堆了几百个 AI 模块，没有统一标准，没人知道哪些在用哪些在闲置，管理起来一团乱。

第三个，提示词变成了科学怪人。每个团队往系统提示词里加自己的规则，加到最后，指令互相矛盾，AI  Agent 不知道该听谁的。他们管这叫 Frankenprompt，东拼西凑拼出来的怪物。

还有速度问题。有一家企业实测了一下，同样的任务，多 Agent 架构跑完，比单 Agent 慢了整整一倍。

## 二、Anthropic 的结论：一个 Agent 往往就够了

他们发现，现在的 AI 模型已经强到一个程度，很多过去必须拆成多个 AI 来处理的任务，一个 AI 就能搞定了。

关键是一种叫“渐进式披露”的做法。

说白了就是：不要把所有信息一股脑塞给 AI，等它需要用到某个工具或者某条知识的时候，再把它加载进来。就像你出门不用把家里所有东西都打包带走，需要什么再取什么。

这样做的好处，是 AI 的工作记忆始终保持清爽，不会被用不到的信息塞满。

更重要的是，单个 AI Agent 的记忆是连续的。它能把自己做过的每一步都记住，前面的结果和后面的判断可以互相联系，推出更有深度的结论。而多 Agent 系统里，总调度员收到的只是各个sub Agent 的摘要，细节在传递中已经丢掉了。

他们还提了一个背景：从 Claude Opus 4.5 开始，模型已经能在单轮循环里管好远比以前多的任务，甚至能自己边做边检查。很多原来需要专门搭框架来处理的事，模型自己就能干了。

## 三、当然，有些情况下多 Agent 还是有必要的

Anthropic 没有说多 Agent 完全没用，他们给出了三种情况，这三种情况下，分开来做还是合理的。

第一，任务实在太长，单个 AI 的记忆装不下，性能开始明显下降。

第二，很多任务可以同时并行处理，分开来跑能节省时间。

第三，工具太多，一个 AI 面对几十个工具时开始搞不清楚该用哪个。

除了这三种情况，大多数场景，一个 AI 加上合理设计的工具和技能，就能覆盖了。

## 四、如果你已经有多 Agent 系统，怎么往回迁移？

文章也给了一个实操路径，不是让你推倒重来，而是一步一步来。

第一步，先搭一套评测。设计一组测试任务，让 AI 做，记录下来作为基准线。后面每次改架构，都拿这套测试跑一遍，看性能是变好了还是变差了。

第二步，把子 Agent 一个一个折叠进主 Agent 里。把子 AI 原来的提示词变成技能，把 API 调用变成工具。每折进一个，就跑一遍评测。如果分数降了，就保留原来的子 Agent；分数持平或者提升了，就继续折。

不用着急，测一个，决定一个，慢慢来。

他们还专门做了一个迁移工具包放在 GitHub 上，里面有帮你搭评测、审查提示词、优化成本的几个工具，有兴趣可以直接去试试。

## 读完之后的一点感想

文章里提到了一个东西叫“康威定律”，说一个系统的架构往往会自然长成跟设计它的组织一样的形状。产品部有一个 Agent，技术部有一个 Agent，这不是最优设计，只是最自然、阻力最小的分法。

细想起来有点扎心。很多复杂的系统，最初并不是因为复杂才有用，只是因为这是各方都能接受的妥协方案。

还有一点，文章一直在强调“先测，改一个，再测，看结果”。这个思路适用范围比 AI Agent 宽得多。很多人改东西喜欢一次改一堆，最后根本不知道是哪步起了作用。一次只动一个变量，才能真正搞清楚每一步发生了什么。
