### **引子：**

上个月在一个饭局上，和我一个做计算机体系结构研究的师兄交流。他说觉得目前大模型虽然能用来写RTL了，但是做不了架构设计。

我当时反驳说，我经常用大模型来研究架构设计，我觉得LLM（当然主要是Opus，gpt 在这块差很多意思）对体系结构的理解其实是超越一般的工程师和研究人员的。

但是后面仔细想一想，“做架构设计” 本身要考虑的事情确实太多了，各种tradeoff 其实不仅需要考虑上层的需求点（OR）如何落实，也要考虑到软件侧支撑复杂度（生态）、后端的实现、良率工程、供应链、验证复杂度、工期、甚至在大厂里面还得考虑团队/部门的饭碗问题等等。如果讲的是这些端到端的流程，那必然是做不了的。

但是毕竟架构设计有太多可以抽象出来的复杂问题，是理论的，系统的，完备的，可验证的。我认为在这些问题上，LLM 替代架构师并无问题。

为了证明这一点，我举一个完整的例子： **用大模型设计PTX兼容的，弱一致性的GPU内存系统和对应的微架构。**

我一直觉得内存一致性模型是体系结构里面十分复杂的概念，理解是一个level，知道怎么硬件去实现是另一个level，知道怎么实现并且能写出严谨的文档，那必然是十分高超的技艺了。

### 第 1 章 参考实现参数与术语

### 1.1 设计目标

本 spec 描述的硬件需要在 **硬件契约** 层面完整支持 NVIDIA PTX (Volta+) 定义的 scoped weak memory consistency model：

- **Ordering 修饰符** ： `.relaxed` / `.acquire` / `.release` / `.acq_rel` / `.volatile` / `.sc`
- **Scope 修饰符** ： `.cta` / `.cluster` / `.gpu` / `.sys`
- **Fence** ： `fence.acq_rel.<scope>` / `fence.sc.<scope>` / `membar`
- **Atom/Red** ： `atom.<op>.<ord>.<scope>` 支持 `.acquire` / `.release` / `.acq_rel`

### 1.4 Scope ↔ Point of Ordering (PoO) 映射

PTX 的 scope 语义本质上是"该 ordering 对哪些 thread 可见"。硬件实现上每个 scope 对应一个 **物理同步点** （Point of Ordering, PoO）。本设计的映射如下：

| PTX Scope | 包含的线程集合 | 硬件 PoO | 物理实现 |
| --- | --- | --- | --- |
| .cta | 同一 CTA 内所有 thread | 同 SM 内 LSQ + L1 | Per-warp scoreboard + L1 controller |
| .cluster | 同一 cluster 内的所有 CTA | Cluster Coherence Engine (CCE) | CCE + DSMEM fabric |
| .gpu | 同芯片所有 thread | L2 (chip-wide) | L2 Ordering Engine（per-bank） |
| .sys | 系统内所有 agent (其它 GPU/CPU) | System Coherence Bridge (SCB) | SCB + NVLink ordering sequencer |

> **关键观察** ：scope 越大，PoO 越远，drain/invalidate 成本越高。微架构必须保证 **每个 scope 的 ack 由对应的 PoO 单独返回** ，避免错误地"用 L2 的 ack 当作 sys ack"。

### 1.5 术语表

| 缩写 | 全称 | 含义 |
| --- | --- | --- |
| PoO | Point of Ordering | 某 scope 的物理同步/可见性边界点 |
| PoC | Point of Coherence | 跨 cache 一致性的边界点（本设计 PoC == PoO 在 L2/SCB） |
| LSU | Load/Store Unit | 每 sub-core 一个，处理访存 |
| LSQ | Load/Store Queue | SM 级别访存乱序与排序结构 |
| MSHR | Miss Status Holding Register | L1/L2 中 in-flight miss 跟踪 |
| WCB | Write-Combining Buffer | 合并 relaxed write 的小缓冲 |
| CCE | Cluster Coherence Engine | cluster scope 排序硬件 |
| DSMEM | Distributed Shared Memory | cluster 跨 SM 暴露 shared memory |
| SCB | System Coherence Bridge | .sys scope 桥接硬件 |
| OE | Ordering Engine | L2 bank 内排序逻辑 |
| VC | Virtual Channel | NoC 虚拟通道 |
| PO | Program Order | 同一 thread 内指令顺序 |

### 1.6 时序假设（参考估算）

| 操作 | 估算周期（typ.） | 备注 |
| --- | --- | --- |
| L1 hit | 4 cycle | sub-core → LSU → L1 → return |
| L1 miss → L2 hit | 80 cycle | NoC 跨芯一次往返 |
| L2 hit → HBM | 350 cycle | 含 row miss |
| st.release.gpu 完整 ack | 90 cycle | L2 入队即 ack |
| ld.acquire.gpu 完整完成 | 90 cycle | L2 bypass 或 epoch miss |
| fence.sc.gpu 全 chip 完成 | ≈400 cycle | 取决于 in-flight 数量 |
| fence.sc.sys 全系统完成 | ≈2000 cycle | NVLink 往返 + 远端 drain |

## 第 2 章 内存模型与可观察性 (Hardware Contract)

本章把 PTX MCM 的可观察行为翻译成硬件必须维护的不变量。所有后续章节的微架构都是对这些不变量的具体实现。

### 2.1 PTX MCM 核心概念（简版）

PTX MCM 是一个 **scoped, axiomatic, non-multi-copy-atomic** 的内存模型。其核心由四个关系定义：

- **PO (program order)** ：同一 thread 内的指令次序。
- **Synchronizes-with (sw)** ：release op `r` 与 acquire op `a` 之间形成 `r → a` 当且仅当：
- **Happens-before (hb)** ： `hb = (po ∪ sw)+` 。
- **SC-fence** ： `fence.sc.<scope>` 在 scope 内提供一个全局可见的总序点。

**关键属性** ：

- 没有 `acq/rel/sc` 标记的访存是 **relaxed** ，硬件几乎可以任意重排，只需保留同地址 PO。
- `acquire` 是"sink for past releases"：早于它的 release 在它之后 **对它所在 thread** 可见。
- `release` 是"source of future acquires"：晚于它的 acquire 在它之后 **对它所在 thread** 可见的写包含 release 的写。
- **Cumulative release** ：release 不仅同步本 thread 的写，也同步 PO 之前的 acquire 链所观察到的写。
- **Scope 限制** ：超出 scope 的 thread 看不到这个 ordering 保证（但允许看到，只是不保证）。

### 2.2 硬件必须维护的不变量 (Invariants)

下面是本 spec 在所有微架构设计中都会满足的不变量。每条用 **[INV-N]** 编号，后续章节会指出每条由哪个部件强制。

| 编号 | 不变量 | 主要负责部件 |
| --- | --- | --- |
| INV-01 | 对同一地址 X，同一 thread 的两次访存按 PO 完成（无论 ord/scope） | LSU + LSQ |
| INV-02 | st.release.<S> retire 时，PO 之前所有写已经达到 scope S 的 PoO | LSQ + WCB + L1 + NoC + 对应 PoO |
| INV-03 | ld.acquire.<S> retire 时，PO 之后所有访存对 S 内 thread 的"之前 release 链"可见 | L1 epoch + LSQ dep_mask |
| INV-04 | atom.acq_rel.<S> 满足 INV-02 + INV-03，且 atomicity 在 PoO 处保证 | L2 OE 或 CCE 原子 ALU |
| INV-05 | fence.acq_rel.<S> 等价于"在该位置完成 INV-02 的 drain + 之后 acquire 的 epoch tick" | scoreboard + PoO drain |
| INV-06 | fence.sc.<S> 在 scope S 内形成全序：S 内任意两个 SC op a, b，要么 a hb b 要么 b hb a | L2 SC sequencer（或 CCE/SCB 对应实现） |
| INV-07 | NoC per-source per-address per-VC in-order：同 source 同 VC 同地址的 message 不重排 | NoC routing/arbitration |
| INV-08 | Release 在 PoO 入队即可 ack，但不得在入队前 ack（否则违反 INV-02） | PoO 排序逻辑 |
| INV-09 | Acquire 的"observed value"决定 sw 关系，硬件必须保证 acquire 数据回传之前所有 PoO-earlier release 已对该 thread 可见 | PoO acquire-gate |
| INV-10 | Speculative load 即使预取到数据，未 retire 前不构成 sw；squash 时不得让其它 thread 已观察到该 load 的副作用 | LSU 投机回滚 |
| INV-11 | Page fault / TLB miss 不破坏 ordering：重试后 epoch 单调递增 | TLB + L1 controller |

### 2.3 同步点 (Synchronization Point) vs 一致性点 (Coherence Point)

本设计将两个概念 **解耦** ：

- **Coherence Point (PoC)** ：保证"一份数据只有一个权威副本"或"所有副本最终一致"的位置。本设计的 PoC = L2（chip 内） + SCB（system）。
- **Synchronization Point (PoO)** ：保证 release-acquire 配对在该处建立 sw 关系的位置。

**两者关系** ：PoO 必须等于或位于 PoC 之上（不能晚于 PoC）。本设计满足：

- `.cta` PoO == LSQ/L1（PoC 在 L1，因为 L1 是 CTA 内 thread 共享的视角）
- `.cluster` PoO == CCE（PoC 也在 CCE，DSMEM 由 CCE 串行化）
- `.gpu` PoO == L2 OE（PoC == L2）
- `.sys` PoO == SCB（PoC == SCB + 远端 L2）

> **结论** ：本设计是"weakly coherent at L2, strongly ordered at PoO"。L1 不维护跨 SM coherence；跨 SM 的可见性靠 epoch invalidate (acquire 侧) + write-through to L2 (release 侧) 实现。

### 2.4 Cumulativity 处理

PTX MCM 的 release/fence 是 **cumulative** 的：一个 release 不仅把本 thread 的 PO-earlier 写传递给 acquirer，还把它 **已经看到的** 所有 release 写也传递过去。

硬件实现：

- LSU 维护 `last_observed_release_epoch[scope]` —— 本 thread 最近 acquire 到的 release 的 PoO 序号。
- 当本 thread 发出 release 时，PoO 在 retire 该 release 时， **必须保证比该 release 早的所有"已被本 thread 观察到的 release"都仍然可见** 。
- 在本设计中，因为 L2 是 **单一线性化点** （per-address per-bank），cumulativity 自然成立：只要 acquire 取到了某 release 写的值，意味着该 release 已经过 L2，后续 acquire 看到的也是 L2 view。

### 2.5 Multi-copy-atomicity (MCA)

PTX 是 **non-MCA** ：允许同一 write 在不同 thread 看到的时间点不同（即 IRIW 不保证 SC）。

**本设计的 MCA 行为** ：

- 在 **per-bank** 内（L2 单 bank），所有 thread 看到的 write 顺序一致（bank 是串行化点）。
- 跨 bank：不保证 MCA，必须靠 `fence.sc.<S>` 强制。
- `fence.sc.gpu` 通过 L2 SC sequencer 在所有 bank 之间建立总序（第 9 章详述）。

### 2.6 编程模型契约

软件层（CUDA / PTX 编译器）必须遵守的硬件契约：

1. 任何跨 thread 同步 **必须** 用 acq/rel/sc 显式标记；relaxed 仅保证同地址 PO。
2. Scope 必须 **至少覆盖** 通信的 thread 集合；scope 不足 → undefined behavior。
3. `fence.sc` 比 `fence.acq_rel` 严格更贵，编译器应只在 IRIW 类场景使用。
4. `volatile` 蕴含 `acq_rel.sys` （最严，禁止 cache，禁止重排）—— 仅用于 MMIO。

## 第 3 章 指令编码与解码

本章定义内存访问指令的微码字段，它们由 Decode 阶段填充并贯穿 LSU/LSQ/L1/NoC/L2 整条链路。下游硬件不会"重新解释" PTX 汇编，所有 ordering/scope 都用统一的微码字段表示。

> **重要澄清** ：本章描述的 `op/ord/scope/...` 是 **decode 之后的内部 uop 表示** 。硬件真正取指/decode 的是 **SASS/NSA 原生 ISA** （PTX 只是虚拟 ISA，由 ptxas/JIT 编译成 SASS）。原生 ISA 用「strength + scope + 方向隐含 acq/rel」编码，decode 时才展开成下表的 `ord[3]` 。

### 3.1 访存微码字段总览

每条 issue 给 LSU 的访存 uop 携带如下字段：

| 字段 | 宽度 | 取值 | 说明 |
| --- | --- | --- | --- |
| op | 3 | LD=0, ST=1, ATOM=2, RED=3, FENCE=4, MEMBAR=5, PREFETCH=6 | 主操作类型 |
| ord | 3 | RELAXED=0, ACQUIRE=1, RELEASE=2, ACQ_REL=3, VOLATILE=4, SC=5, RSV0=6, RSV1=7 | ordering 修饰符 |
| scope | 2 | CTA=0, CLUSTER=1, GPU=2, SYS=3 | scope 修饰符 |
| sem | 3 | CA=0, CG=1, CS=2, CV=3, LU=4, WT=5, WB=6, RSV=7 | 缓存提示 (cache hint) |
| width | 3 | 0..7 → 1/2/4/8/16/32/64/128 B | 单 lane 数据宽度 |
| mask_en | 1 | 0/1 | 是否使用 32-bit lane mask |
| addr_space | 3 | GLOBAL=0, SHARED=1, LOCAL=2, CONST=3, PARAM=4, DSMEM=5, MMIO=6 | 地址空间 |
| atom_op | 4 | ADD/MIN/MAX/AND/OR/XOR/CAS/EXCH/INC/DEC/... | 仅 ATOM/RED 有效 |
| dst_reg | 8 | regfile 索引 | LD 的目的寄存器 |
| src_reg | 8 | regfile 索引 | ST 的数据来源 |

合法性检查由 Decode 阶段做：

- `ord=ACQUIRE` + `op=ST` → illegal instruction
- `ord=RELEASE` + `op=LD` → illegal instruction
- `ord=VOLATILE` 强制 `scope=SYS` ，并且禁止 cache（ `sem=CV` or 不分配）
- `scope=CLUSTER` 仅在 `addr_space=GLOBAL` 或 `DSMEM` 合法
- `op=ATOM` / `RED` 仅在 `addr_space=GLOBAL` / `SHARED` / `DSMEM` 合法

下表给出"PTX 汇编 → 硬件 uop 字段"的映射，覆盖了所有有意义的组合：

| PTX 形式 | op | ord | scope | sem | 备注 |
| --- | --- | --- | --- | --- | --- |

| ld.relaxed.gpu.b32 | LD | RELAXED | GPU | CA | 显式 relaxed |

| ld.acquire.sys.b32 | LD | ACQUIRE | SYS | CV | sys acquire 必须 bypass L1 |
| ld.volatile.b32 | LD | VOLATILE | SYS | CV | 用于 MMIO |
| st.global.b32 | ST | RELAXED | CTA | WB | 默认 |
| st.release.gpu.b32 | ST | RELEASE | GPU | WT | release 必须 write-through 到 L2 |
| st.release.sys.b32 | ST | RELEASE | SYS | WT | release 必须达到 SCB |
| atom.add.acquire.gpu.b32 | ATOM | ACQUIRE | GPU | - | RMW 在 L2 bank 原地执行 |

### 3.3 Decode 阶段约束传递

Decode 阶段除了填字段，还要做：

1. **重排禁令传递** ：把"该 uop 与 PO-prev/next 不可重排"的信息编码进 issue tag（实际控制由 scoreboard 完成）。
2. **scope 单调上提** ：若 fence 之前未完成的 release 是 `.cta` ，而该 fence 是 `.gpu` ，则该 release 的 in-flight ack 等待 **升级到 .gpu PoO** （重新发起 .gpu drain）。这避免软件用 `.cta` release 后接 `.gpu` fence 漏 drain。
3. **Predicate-off 处理** ：predicate off 的 lane 不参与 ordering 计算（其位在 `lane_mask` 中清 0）。

## 第 4 章 Sub-core 前端 — Warp Scheduler + Memory Scoreboard

Sub-core 是 SM 内独立调度的最小单元。每个 sub-core 拥有：

- 1 个 warp scheduler（最多 16 个驻留 warp）
- 1 个 32-lane LSU
- 1 个共享的 Memory Scoreboard（与 ALU scoreboard 分离）
- 1 个 fence sequencer

### 4.1 Sub-core 结构

*图 4：Sub-core 前端结构*

### 4.2 Memory Scoreboard 表结构

Memory Scoreboard 是 warp scheduler 决定能否 issue 下一条访存的核心。每 sub-core 一份，按 warp 组织：

**Per-sub-core Scoreboard** ：16 warp × 1 entry，每 entry 字段：

| 字段 | 宽度 | 说明 |
| --- | --- | --- |
| valid | 1 | warp 是否驻留 |
| warp_id | 6 | 全 SM 唯一 |
| acq_pending | 1 | 是否有 acquire load 在 fly（其后续指令需检查 dep） |
| rel_pending_cnt | 4 | in-flight release 数（≤15） |
| acqrel_pending_cnt | 4 | in-flight acq_rel 数 |
| fence_pending | 1 | 正在执行 fence，stall issue |
| fence_id | 8 | 当前 fence sequencer 分配的 ID |
| fence_scope | 2 | fence 的 scope |
| fence_state | 3 | IDLE/DRAIN/WAIT_ACK/SC_P1/SC_P2/DONE |
| outstanding_loads | 5 | LD 在 fly 数（≤31） |
| outstanding_stores | 5 | ST 在 fly 数（≤31） |
| last_acq_age | 6 | 上一次 acquire 的 LSQ age tag |
| last_rel_age | 6 | 上一次 release 的 LSQ age tag |
| dep_shadow_mask | 32 | bit i = 1 表示 PO 位置 i 的指令需等 last_acq 完成 |

> `dep_shadow_mask` 的物理实现：硬件维护 program-order ring 上的 sliding window；当 acquire issue 时，"它之后所有 in-flight uop"在该 mask 上置 1；每条 uop retire 时清自己的 bit。Issue gating 检查"我之前 PO-window 内是否还有 mask 置位的 uop"。

### 4.3 Issue Gating 规则

Warp scheduler 在 issue 一条 uop 时按下表 gate：

| Uop 类型 | Gate 条件 |
| --- | --- |
| ld.relaxed | 无 ordering gate（仍受同地址 RAW 限制） |
| ld.acquire.<S> | 之前所有 PO-earlier release/acq_rel/fence 在 scope-S 上必须完成；同时把自己的 last_acq_age 写入 |
| st.relaxed | 无 ordering gate（仍受同地址 WAW/RAW） |
| st.release.<S> | PO-earlier 所有 write uop 必须已 commit at PoO(S)（通过 last_rel_age 等待 LSQ 排干） |
| atom.acq_rel.<S> | 同时满足上面两条 |
| fence.acq_rel.<S> | 暂停 issue 直到 fence_state == DONE |
| fence.sc.<S> | 同上，但 fence_state 走 SC_P1→SC_P2 路径 |
| volatile load/store | 等同 acq/rel.sys，且禁止与任何其它 in-flight 访存合并 |

> **关键设计选择 [D-FE-01]** ：acquire 不阻塞 issue 它 **自己** 之后的 relaxed load —— 我们用 `dep_shadow_mask` 让"之后的 load"只在 retire 阶段等 acquire 的 epoch tick 完成，而不是在 issue 阶段 stall。这在 GPU 高 in-flight 度下显著降低 fence 成本。详见第 5 章 LSQ 排序规则。

### 4.4 Fence Sequencer 状态机

每 sub-core 一个 fence sequencer，处理本 sub-core 所有 fence/membar。

![](https://pic1.zhimg.com/v2-362502ccefcdd427d3fe04fe17c3fcf6_r.jpg)
*图 5：Fence Sequencer 状态机*

**状态解释** ：

- `DRAIN_LSQ` ：等待本 warp 所有 PO-earlier write 在 LSQ 上 commit；具体通过 `last_rel_age` watermark 实现。
- `WAIT_POO_ACK` ：drain 到 PoO 后，PoO 回 ack。 `.cta` 是本地立即 ack； `.gpu` 由 L2 OE 回； `.sys` 由 SCB 回。
- `EPOCH_TICK` ：fence 完成时把 SM 的 `epoch[S]` 加 1（用于第 6 章的 lazy invalidate）。
- `SC_P1` / `SC_P2` ：2-phase SC，第 9 章详述。

### 4.5 SC Token 与 cumulative ordering

`fence.sc.<S>` 需要在 scope S 内建立全序。本设计采用 **L2 (或 SCB) 集中式 SC sequencer** ：

- 每 sub-core 持有一个 `sc_local_counter[S]` （16-bit），每发出一个 SC 操作（fence.sc 或 atom.sc）+1。
- SC token 格式： `{src_sm[7], src_subcore[2], local_counter[16], scope[2]}` 。
- PoO 的 SC sequencer 收到 token 后，把它插入一个 chip-wide（或 system-wide）的 SC log，按 token arrival 时间戳分配全局 SC sequence number。
- Phase-1 ack 返回该 global sn；phase-2 commit 在 PoO 处把这条 SC 在所有 bank 上"原子地"插入 commit point。

### 4.6 Sub-core 与 LSU 的接口

每周期最多 issue 1 条访存到 LSU。Issue 时传递：

- 完整的 uop 微码字段（第 3 章）
- `warp_id` , `sub_id` , `lane_mask[32]` , `addrs[32 × 64-bit]` , `data[32 × 256-bit]` (store)
- Scoreboard 分配的 `age[6]` （PO 序号 mod 64）
- `dep_mask[16]` ：表示对本 sub-core LSQ 中哪些 entry 有 ordering 依赖

LSU 回 sub-core 的信号：

- `lsq_full` （issue 反压）
- `retire_age[6]` + `retire_warp_id[6]` （scoreboard 清 bit）
- `fence_ack[fence_id]` （fence sequencer 推进状态）

**状态说明** ：

### 5.6 数据通路 stripe 化

LSU 是 32-lane × 8B = 256 B 宽，但单个 LSQ entry data 域只有 256 bit (32B)。当 lane 数据宽度 > 1B 时，单 entry 装不下整个 warp 的 data，需要做 **stripe** ：

- 一个 LD/ST 的"逻辑 entry"按 64-bit chunk 拆为最多 16 个 stripe（32 lane × 8B / 64-bit chunk = 4 chunks，但更大 width 需要更多）。
- 实际实现：data SRAM 是分开的"LSQ data array" 64 KB/SM；entry 中 `data` 域是 **指针** 。

> 简化起见，后续章节直接说 entry 持有 data。data array 容量按 1 KB × 64 entry = 64 KB 取整。

### 5.7 Coalescer 规则

Coalescer 把 32 lane 的访存合并为最少的 NoC transaction，规则：

1. **合并条件（必须全部满足）** ： 
 - 同 cacheline（128B 对齐） 
 - 同 `op` , 同 `ord` , 同 `scope` , 同 `sem` , 同 `addr_space` 
 - 同 page（不跨页）
2. **拆分条件** ： 
 - 跨 cacheline → 拆成多个 sub-request， **保持 PO order** （同 lane 内） 
 - 跨 page → 强制拆分
3. **不允许跨 ordering 合并** ： 
 - `acquire` 与 `relaxed` 即使同地址也不合并（避免一个 lane 的 acquire 把 relaxed lane 提前可见） 
 - `release` 与 `relaxed` 同理 
 - 不同 `scope` 不合并
4. **Atomic 不参与 coalescing** （除非是 same-address RED，按 PTX 规则可合并为单 RMW，但本设计保守不合并）。
5. **Write-combining** （与 coalescer 互补）：见第 6 章 WCB。

### 5.8 排序具体执行：dep_mask 与 pre_release_mask

### 5.8.1 dep_mask 的填充与清除

- 当一个 acquire/acq_rel/fence uop **进入 LSQ** 时，把它的 age 记到 sub-core 的 `last_anchor_age[scope]` 。
- 之后每个新 issue 的访存 entry，在 ALLOC 阶段查询 `last_anchor_age[*]` ，把"在 acquire/fence 之后 issue"的所有 entry 的 `dep_mask[i] = 1` ，其中 i = anchor 的 age bit index。
- 每条 anchor entry retire 时广播 "anchor age = K retired"，所有 entry 的 `dep_mask[K] = 0` 。

> 这样的好处： `dep_mask` 是 16-bit 位图，可同时跟踪 16 个未 retire 的 anchor。Issue rate 高时每周期可清多 bit。

### 5.8.2 pre_release_mask 的填充

- 每条 store/atom-write 进入 LSQ 时分配 `wr_age[6]` 。
- 当一条 release/acq_rel uop 进入 LSQ 时，把当前所有 in-flight write 的 wr_age **打包** 为 16-bit `pre_release_mask` （取 wr_age 低 4 位，配合 16-entry 滑窗）。
- release entry 在 ORD_CHECK 阶段持续监视 `pre_release_mask` ：每条 PO-earlier write 在到达 PoO(release.scope) 并 ack 后清自己的 bit。
- 当 `pre_release_mask == 0` AND release 自己的写也 ack 时，进入 COMMIT。

### 5.9 投机访存与回滚

GPU 通常 **不做** OOO 投机像 CPU 那样深度。但本设计支持：

- 多 warp 间乱序：不同 warp 的指令任意交织。
- 同 warp 内 LSU pipeline 内乱序：不同 age 的 entry 可能乱序到达 ORD_CHECK，但 commit 必须按 dep_mask 守序。
- **预取** （prefetch / cp.async）：预取数据先进 L1，但不 retire 到 regfile；若中途 squash，丢弃即可， **不破坏 ordering** （因为没有 anchor）。

回滚规则：

- 异常（page fault）：仅 squash 该 entry 及 PO-later entry；scoreboard 把 `dep_mask` 中对应 age 清掉。
- Branch misprediction：GPU 罕见，但若存在，所有 in-flight LSQ entry 仅在它们"未对外 commit"前可丢弃；release/atom 一旦 ack_received==1 不可回滚。

### 5.10 LSQ 满处理与压力控制

- 当 sub-core 的 LSQ 满 → issue stall。
- 优先抢占 retire：retire 端每周期最多 2 条。
- 长尾 release ack 等待会卡住 LSQ → 用 **head-of-LSQ prioritization** ：release 在 ORD_CHECK 排在最前。

### 5.11 与 scoreboard 的协同总结

| 事件 | LSQ 动作 | Scoreboard 动作 |
| --- | --- | --- |
| Issue ld.relaxed | alloc entry, dep_mask 拷贝 | outstanding_loads++ |
| Issue ld.acquire | alloc + is_anchor=1, last_anchor_age 更新 | acq_pending=1, last_acq_age 更新 |
| Issue st.release | alloc + pre_release_mask 填充 | rel_pending_cnt++ |
| Retire release | 清自己 + broadcast wr_age 到其它 entry | rel_pending_cnt-- |
| Retire acquire | 清 dep_mask bit, tick L1 epoch[scope] | acq_pending=0 |
| Retire fence | 通知 fence_sequencer DONE | fence_pending=0 |

## 第 6 章 L1 / Shared Memory 子系统

L1 是 acquire 侧的"过滤器"和 release 侧的"漏斗"。本设计的 L1 **不参与跨 SM 一致性** （无 directory，无 snoop），但通过 **epoch-based lazy invalidate** 与 **strict write-through on release** 提供 PTX 要求的可见性。

### 6.1 容量与组织

| 项 | 数值 |
| --- | --- |
| 总容量/SM | 128 KB |
| 分区策略 | 软件可配：L1$ 与 shared memory 在 0/32/64/96/128 KB 间动态切换 |
| L1$ 数据 array | 最大 96 KB（取 96+32 配置） |
| 关联度 | 8 way |
| Line size | 128 B |
| Sector size | 32 B（每 line 4 sector，独立 V/D） |
| Tag array | 8 way × 96 set = 768 tag |
| MSHR | 32 entry（per L1） |
| WCB | 16 entry × 128 B |
| 读端口 | 4（每 sub-core 1） |
| 写端口 | 4 |

### 6.2 Cacheline 状态位（扩展）

每个 cacheline tag entry 字段：

| 字段 | 宽度 | 说明 |
| --- | --- | --- |
| tag | 36 | PA 高位 |
| V | 1 | line valid |
| D[4] | 4 | per-sector dirty bit |
| secV[4] | 4 | per-sector valid（用于 sectored allocate） |
| R[1] | 1 | RRIP / LRU pseudo bit（或 4-bit RRIP） |
| LineEpoch[scope=GPU] | 8 | line 的 GPU-epoch tag |
| LineEpoch[scope=CLUSTER] | 8 | line 的 CLUSTER-epoch tag |
| LineEpoch[scope=SYS] | 8 | line 的 SYS-epoch tag |

| WaitAck | 1 | 有 in-flight release 写该 line，未 ack |

> 注意： `.cta` scope 不需要 epoch tag —— `.cta` PoO 是 SM 内部，L1 的所有内容对同 CTA thread 当然可见。

### 6.3 关键决策 [D-01]: Epoch-based Lazy Invalidate

### 6.3.1 三种方案对比

| 方案 | 描述 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A. Eager full invalidate | acquire 触发 walk 整个 tag array，全部 V=0 | 简单 | 严重浪费带宽；每个 acquire 都热 walk → 数千周期 |
| B. Epoch-based lazy invalidate（本设计选用） | SM 维护 sm_epoch[scope]；line 携带 line_epoch[scope]；hit 条件加 epoch 比较；acquire 时只 ++ epoch | O(1) acquire 成本；scope 隔离；适配 sectored cache | 需要每 line 额外 epoch tag（本设计 3 × 8 = 24-bit） |
| C. Precise directory invalidate | 跨 SM directory 精确通知 | 数据复用最好 | 面积/带宽/复杂度高，不适合 ≈128 SM 规模 |

### 6.3.2 Epoch 机制详细规范

**SM 全局状态** （每 SM 一份）：

```text
sm_epoch[GPU]: 8-bit counter
sm_epoch[CLUSTER]: 8-bit counter
sm_epoch[SYS]: 8-bit counter
```

**Line 命中判定（每次 L1 probe）** ：

```text
hit_for_scope(scope=s):
  return V==1 AND secV[sector]==1 AND LineEpoch[s] == sm_epoch[s]
```

对于 `.cta` 的 LD，仅检查 `V==1 AND secV==1` （不查 epoch）。

**写入时的 epoch 标记** ：

- 当 L1 接收远端数据填充（fill from L2），把 **所有 scope 的 LineEpoch** 设为当前 `sm_epoch[*]` ，意味着”此数据相对本 SM 当下的 epoch 是 fresh”。
- 当 SM 本地写入（store 命中 line），保持原 LineEpoch（本地写不会让本地 stale）。

**acquire tick** ：

```text
on retire ld.acquire.<S>:
  sm_epoch[S] += 1
  if S == SYS: sm_epoch[GPU] += 1; sm_epoch[CLUSTER] += 1
  if S == GPU: sm_epoch[CLUSTER] += 1
```

> Scope 升级蕴含：acquire.sys 必然蕴含 acquire.gpu 的可见性，因此连带 tick。Scope 单调性体现在 epoch 上。

**acquire 不需要”必须 miss”** ：如果 acquire 自己的目标 line 在 L1 命中且 epoch fresh，直接用即可（数据是它自己之前 fetch 的）。但 acquire 的 **副作用** 是 tick，让 **后续** load 在此 line 仍 fresh、但其它 line 全部失效。

**Epoch wraparound** ：8-bit 计数器在 256 次 acquire 后回卷。本设计采用” **回卷触发 eager flush** “：当 `sm_epoch[s]` 即将回卷到等于任一活跃 line 的 `LineEpoch[s]` 时（极罕见，≈256 个 acquire 之后），触发一次 L1 invalidate（walk + V=0）。

> 实际可把 epoch 加宽到 16-bit（仅 +8-bit/line × 3 scope = 24 bit 额外），避免回卷。下文按 8-bit 描述以体现回卷处理。

### 6.3.3 与 LSU 的协作

LSU 在 L1_PROBE 阶段做：

```text
load_probe(ord, scope, va):
  if ord != ACQUIRE and not fresh_required(ord):
    # relaxed load 也要查 epoch！否则会读到 stale
    # 但 PTX 允许 relaxed 读到任意旧值；因此本设计 relaxed 也校 epoch
    pass
  hit = (V && secV[sec] && LineEpoch[scope] == sm_epoch[scope])
  if not hit:
    goto MISS_PEND
  else:
    return data
```

**重要细节** ： **relaxed load 也校 epoch** ？ 
 PTX 允许 relaxed 读到陈旧值（不破坏 INV-03，因为 relaxed 不是 acquire）。但本设计 **统一所有 load 都查 epoch** ，原因：

- 简化硬件：单一命中逻辑。
- 不损失正确性（仍是 PTX 允许的行为，因为我们只是”更新”得更勤）。
- 性能影响小：epoch miss 只在 acquire 之后才发生，而且会很快被 refill。

但是 **`.cta` scope 的 load 不查 epoch** ：CTA 内部 L1 永远是 coherent 的（SM 内单写者）。这样 `.cta` 通信完全免费。

### 6.4 写策略

### 6.4.1 全局存储的写策略矩阵

| ord × scope | L1 行为 | WCB 行为 | 等 L2 ack？ |
| --- | --- | --- | --- |
| RELAXED, CTA | write-allocate + dirty (write-back allowed at evict) | 不进 WCB | 否 |
| RELAXED, GPU/SYS | write-through L1 | 进 WCB（可合并） | 否 |
| RELEASE, CTA | write to L1, mark D | 不进 WCB | 否（PoO=L1） |
| RELEASE, GPU | write-through + L1 line WaitAck=1 | 进 WCB（但 release 强制 close & flush） | 是 |
| RELEASE, SYS | 同上 + SCB drain | 同上 | 是 (SCB ack) |
| ATOM/RED, * | bypass L1 (除非 .cta) | 不进 WCB | 视 ord/scope |
| VOLATILE | bypass L1 完全 | 不进 WCB | 是 (SYS) |

### 6.4.2 L1 dirty 与 evict

- **CTA-scope dirty line** 可以 write-back evict。Evict 时把 dirty sector 写回 L2。
- **GPU/SYS-scope 写过的 line** 一律 write-through，line 永远不持有 unique-dirty 数据 → evict 时直接丢弃。
- 一条 line 在生命周期中既被 CTA 写又被 GPU 写：第二次写时所有 D bit 通过 write-through 同步到 L2，line 变成 “shared”，evict 时仍 silent。

### 6.4.3 Release 流程

`st.release.<S>` 进入 L1 controller：

1. 查 line：若 hit（无关 epoch），把数据写入 line 且 `D[sector]=1` , `WaitAck=1` 。若 miss， **不** allocate（避免 fill miss 阻塞 release），直接走 WCB。
2. 把数据复制到 WCB entry，标记 `flush_required=1` , `wait_ack=1` 。
3. 立即把 WCB entry 推送到 NoC（不等其它合并）。
4. NoC → L2，L2 OE 入队后回 ack。
5. L1 controller 收到 ack，清 WCB entry，清 line 的 `WaitAck` ，通知 LSU `ack_received=1` 。

> **关键** ：release 写 **不等 L1 line 被 fill** 才发送。WCB 是它的”出口”。

### 6.5.1 结构

| 项 | 数值 |
| --- | --- |
| Entry 数 | 16 |
| Entry 大小 | 128 B 数据 + 16 B mask + meta |
| 端口 | 1 写、1 flush 读、1 CAM |
| 替换策略 | 满则 oldest flush；release 触发强制 close |

| 字段 | 宽度 | 说明 |
| --- | --- | --- |
| valid | 1 |  |
| addr | 52 | line-aligned |
| mask | 16 | per-4B mask（128B / 4 = 32 byte mask 简化为 4-bit per 16B = 16 bit）— 实际 spec 取 32-bit per-4B |

### 6.5.2 合并规则（[D-02] 详化）

- 新写到来时 CAM `addr` 寻找已存在 entry。
- 若命中且 **`closed==0` 且 ord/scope 兼容** （要求新写 ord ≤ ord_locked，scope ≤ scope_locked，否则 **升级 ord_locked/scope_locked** ），合并 data + mask。
- 若新写是 `release` ： **立即把该 entry close，加入 flush 队列** ；新到的 relaxed 不能再合并入。
- 若 WCB 满 → stall 新写（产生 LSU back-pressure），同时启动 oldest flush。

### 6.5.3 Flush 触发条件

WCB 何时 flush（发 NoC）：

| 触发 | flush 哪些 entry |
| --- | --- |
| release/acq_rel 到来 | 该 entry close 后立即 flush；并触发”所有 PO-earlier WCB entry flush”（保 PO） |
| fence.acq_rel.<S> | flush 所有 scope ≤ S 的 entry，并等 ack |
| fence.sc.<S> | 同上，但走 SC 通道 |
| WCB full | flush oldest |
| volatile 写 | flush 所有，且自己不进 WCB |
| Page 切换 | 不影响（按 PA 索引） |
| Time-based | 256 周期未 flush → 自动 flush（避免 dead write） |

### 6.7 Shared Memory (Scratchpad) 部分

Shared memory 是 SM 内 32 banked SRAM（同 L1 共享 128 KB physical store）。它 **只有 .cta scope** 才有 PTX 意义（同 CTA thread 可见）；从 cluster 视角通过 DSMEM 暴露（第 7 章）。

- 因为 shared memory **只在单 SM 内** ，不存在跨 SM coherence 问题。
- 同一 CTA 内 thread 的 ordering 由 LSQ 完成。
- `bar.sync` / `barrier.cluster.sync` 等同步原语在 sub-core scheduler 中实现，跨 sub-core 状态用 SM-level barrier RAM (一个 64 × 16-bit 的 barrier state)。
- `ld.shared.acquire.cta` 在 L1 controller 内是 trivial：scope=CTA 时直接 hit 即可。

### 6.8 Sector & MSHR 协同

L1 MSHR：32 entry，关键字段：

| 字段 | 宽度 |
| --- | --- |
| valid | 1 |
| addr_line | 52 |
| mask_secs | 4 |
| req_lsq_id | 6 |
| req_warp_id | 6 |
| ord | 3 |
| scope | 2 |
| is_release_ack | 1 |
| is_acquire_probe | 1 |
| state | 3 (PEND/SENT/DATA_BACK/ACK_BACK/DONE) |
| noc_tid | 8 |

MSHR 合并规则：

- 同 line 同 scope 的多个 miss 可合并（merge → 同一个 NoC request）
- 但 acquire 的 miss **不与 relaxed miss 合并** （acquire 需要 ack，relaxed 不需要）
- release 写不进 MSHR，走 WCB
- atomic 不合并

### 6.9 L1 对 INV 不变量的贡献

| 不变量 | L1 的具体机制 |
| --- | --- |
| INV-01 | 同地址 load forward from WCB / hit ordering |
| INV-02 | release WT + WCB flush + ack 等待 |
| INV-03 | epoch invalidate 让 acquire 之后的 load 重新走 L2 取最新 |
| INV-08 | release ack 只在 L2 OE 入队后才被 L1 转发，不会”提前” ack |
| INV-09 | acquire 的 epoch tick 在数据 retire 后才进行，保证它”看到”的 release 链已对本 SM 起效 |
| INV-11 | TLB miss 重发的 acquire/release，epoch 序号继续递增（不复用旧 sm_epoch） |

### 第 7 章 Cluster 域 — DSMEM 与 Cluster Coherence Engine

`.cluster` scope 是 Hopper 引入的中间 scope，介于 `.cta` 和 `.gpu` 之间。它对应 **Thread Block Cluster** （同一 cluster 内的多个 CTA 可在不同 SM 上执行，但共享一个 cluster ID 与一段 DSMEM 视图）。

### 7.1 Cluster 域物理边界

| 项 | 数值 |
| --- | --- |
| Cluster 数/GPC | 1（每 GPC 一个 cluster 域） |
| 最大 SM 数/Cluster | 16 |
| 物理 SM ID 编码 | gpc_id[3] : cluster_id[0] : local_sm[4] |
| Cluster fabric | 全互联 crossbar，每 SM 2 read + 2 write port，128-bit data |
| DSMEM 容量 | 每 SM 暴露 0–64 KB 给同 cluster |

### 7.2 DSMEM 物理实现

DSMEM 不是新增的物理存储，而是把每 SM 的 **shared memory** 通过 cluster fabric 暴露给同 cluster 其它 SM 读写。

地址布局：

```text
DSMEM virtual address (per cluster):
  [target_sm_in_cluster:4][offset_in_smem:14]    (18-bit, 256 KB cluster view)
```

LSU 在 AGEN 阶段检测 `addr_space == DSMEM` ，把目标 SM 拆出来，请求路由到 cluster fabric。

### 7.3 Cluster Coherence Engine (CCE)

每 cluster 一个 CCE，物理位置贴近 GPC mesh 上行口。功能：

1. **路由与仲裁** ：DSMEM 读写跨 SM 的路由器。
2. **`.cluster` scope 排序** ：维护 cluster 内的 release/acquire 顺序契约。
3. **Cluster barrier** ：实现 `barrier.cluster.sync` / `barrier.cluster.arrive` 等。
4. **Cluster fence engine** ：处理 `fence.acq_rel.cluster` 和 `fence.sc.cluster` 。

### 7.3.1 CCE 内部结构

![](https://picx.zhimg.com/v2-4c7a91a5847795b939c527e61e1dca6f_r.jpg)
*图 9：CCE 内部结构*

### 7.3.2 Per-source Ordering Scoreboard

每条 source SM 有一个 16-entry token table：

| 字段 | 宽度 | 说明 |
| --- | --- | --- |
| valid | 1 |  |
| token_id | 4 | source-local token ID |
| op_kind | 2 | REL_W / ACQ_R / FENCE_DRAIN / ATOM_RMW |
| target_sm | 4 | 目标 SM（DSMEM 写的 owner） |
| addr_line | 18 | DSMEM 内地址 |
| state | 3 | PEND/IN_FABRIC/AT_DEST/ACKED |
| ts | 16 | 入 CCE 时刻 |

### 7.3.3 release.cluster 流程

1. LSU 发 `st.release.cluster` → 走 cluster fabric（不走 L1）。
2. CCE 接收，分配 token，放入该 source 的 scoreboard，转发到 target SM 的 DSMEM 端口。
3. Target SM 的 shared memory 控制器写入，回 ack 给 CCE。
4. CCE 把 token state 设为 ACKED， **按 same-source FIFO 顺序** 对外 ack。
5. ack 回到 source SM 的 LSU，清 LSQ entry。

> **关键不变量** ：CCE 保证 **same-source 的 release 按 PO 顺序对所有 target SM 可见** 。即使发往不同 target，先发的 release 必须先 ack 给 source。

### 7.3.4 acquire.cluster 流程

1. LSU 发 `ld.acquire.cluster` 到 cluster fabric。
2. CCE 接收， **先 query OSB** ：是否还有来自任意 source、与本 SM 目标地址有交集的 in-flight release token 未 ACKED？
3. 若有，stall acquire 直到这些 token ACKED；否则放行到目标 SM 的 DSMEM 端口读。
4. 返回数据时一并触发 source SM 的 `epoch[cluster]++` （通过 L1 controller 接收 epoch tick 信号）。

> **简化** ：实际硬件不需要”精确判断地址交集”。本设计采用保守策略 —— `ld.acquire.cluster` 等待 **所有 source** 的 in-flight release 都 ACKED。这是和 PTX `.cluster` scope 兼容的”非过度同步”实现，因为 release 是 cumulative。

### 7.4 Cluster Fence Engine 与 fence.sc.cluster

`fence.acq_rel.cluster` 的硬件流程：

1. 本 SM 的 fence sequencer 通知 CCE：source=本 SM，request DRAIN。
2. CCE 查 OSB：等本 source 所有 token ACKED + 所有发往本 SM 的 in-flight write ACKED。
3. CCE 回 ack 给本 SM；fence sequencer tick `sm_epoch[cluster]` 。

`fence.sc.cluster` ：CCE 内有一个 mini-SC sequencer：

1. **Phase 1 (Freeze)** ：本 SM 发 SC token 给 CCE；CCE 把当前 OSB 的所有 in-flight token 标记为 “must drain before SC commit”。CCE 把”我准备好 commit”的 ack 回给本 SM。
2. **Phase 2 (Commit)** ：本 SM 发 SC commit；CCE 等所有被标记的 token ACKED + 同时向其它 cluster member 广播”本 SM 的 SC sn 已到 X”。所有 member 收到后回 ack；CCE 收齐回 ack 给本 SM。

> 因为 cluster 最大 16 SM，broadcast 成本可接受（O(16)）。L2/SCB 的 SC 实现见第 9⁄11 章。

### 7.5 Cluster Barrier (硬件加速)

`barrier.cluster.sync arrive.wait, count` 在硬件上：

- CCE 内 Barrier RAM：64 × 32-bit barrier state（最多 64 个 cluster barrier）。
- 每 entry： `{valid[1], count_expected[12], count_arrived[12], generation[4], pending_wait_mask[16]}`
- arrive：count_arrived++；若 == count_expected，递增 generation，唤醒 pending_wait_mask 对应 SM。
- wait：把本 SM 加入 pending_wait_mask；若 generation 已变则立即唤醒。
- barrier.cluster.sync 蕴含 **fence.acq_rel.cluster** （barrier 实现时自动调用 fence engine）。

### 7.6 .cluster scope 的硬件契约总结

| 契约 | 实现位置 |
| --- | --- |
| Same-source release PO 保持 | CCE OSB FIFO |
| Different-source release 之间无序（可乱） | 允许 |
| acquire 等待所有 source release ACKED | CCE OSB query |
| cluster fence 等同 cluster drain + epoch tick | CCE Fence Engine + L1 epoch |
| cluster SC 全序 | CCE SC sequencer (2-phase) |

### 7.7 资源估算

| 资源 | 数值 |
| --- | --- |
| CCE 面积（参考） | ≈0.5 mm² @ 5nm |
| CCE 频率 | 同 SM 时钟（≈1.8 GHz） |
| Cluster fabric 双向带宽 | 16 SM × 2 ports × 128-bit × 1.8 GHz = ≈922 GB/s |
| OSB 存储 | 16 src × 16 entry × ≈64 bit = ≈16 Kb |

### 第 8 章 NoC — 片上互连

NoC 是把 SM/CCE 连到 L2 bank、L2 bank 连到 MC/SCB 的总线网络。它必须支持高吞吐 **和** 严格的 ordering 保证。本设计采用 **两级 mesh + 5 个 VC** 的拓扑。

### 8.1 拓扑

![](https://pic3.zhimg.com/v2-8f9fed659aebbae8cd3b0ae794d30d76_r.jpg)
*图 10：NoC 拓扑*

层级：

- **L0：GPC 内 mesh** （4×4，含 GPC gateway router）
- **L1：跨 GPC ring** 或 8x1 mesh
- **L2：L2 bank 接入网** （每 bank 有自己的 router）

物理参数：

- 每 router 端口宽度：512 bit（请求方向） / 512 bit（响应方向），总 256 B/cycle 单向。
- 频率：1.5 GHz NoC clock。
- 单 hop 延迟：2 cycle（不含 router stage）。

### 8.2 关键决策 [D-04]: 5 VC 划分

每条 NoC 物理链路上有 5 个虚拟通道（VC），相互 **不阻塞** （独立 buffer）：

| VC | 用途 | 单向 buffer/router | 备注 |
| --- | --- | --- | --- |
| VC0 | Read Request (LD/ATOM/PRF) | 8 entry × 64B | 含 acquire LD（acquire 自带 ack-on-data） |
| VC1 | Write Request (relaxed, no-ack) | 8 entry × 144B | data 144B = 16B header + 128B payload |
| VC2 | Write Request (release/sys, ack-required) | 8 entry × 144B | 与 VC1 物理分离，避免 release 被 relaxed 排队阻塞 |
| VC3 | Response Data | 8 entry × 144B | LD 返回、L1/L2 fill |
| VC4 | Ordering Ack / Inv Ack / Fence Ack | 16 entry × 32B | 小消息独立通道，关键保证 INV-09 |

> **为什么 VC4 必须独立？** 设想：一个 release 已到 L2 OE，OE 发出 ack 想回 L1。如果 ack 与 response data 共用一个 VC，那么当 VC3 反向通路被 fill data 塞满时，ack 会被 head-of-line block，release 永远 commit 不了 → 死锁可能。独立 VC4 + 独立 buffer 避免该死锁。

### 8.3 关键不变量 [INV-07] 的实现

> **per-source, per-address, per-VC in-order** ：来自同一 source（SM）的同一地址的同一 VC 的所有 message 不会被 NoC 重排。

实现方式：

1. **路由算法选择** ：本设计采用 **dimension-order routing (DOR)** ，加 source-id 旁系扰动（避免热点），但 **同 source 同 destination 路径固定** 。
2. **VC 内 FIFO** ：每个 VC 在 router 中是 FIFO，不允许 VC 内重排。
3. **Per-address ordering** ：由于路径固定（DOR），同 src/dst pair 的同 VC message 顺序物理保持。
4. **不同 destination** ：不同 dst 走不同 path，不要求保序（这是为什么 cumulativity 必须 explicit ack）。

**Edge case** ：当 router 的 adaptive bypass 启用时，可能让”短包绕过长包”，会破坏 per-VC FIFO。本设计 **禁用** VC0/VC1/VC2/VC3 的 adaptive bypass；VC4 允许 adaptive（ack 是无序的，靠 token id 重组）。

### 8.4 Credit-based 反压

每个 VC 用 credit-based 流控：

- 上游 router 每发一个 flit 消耗 1 credit。
- 下游 router 释放 buffer 时回 credit（用一个独立的”credit return channel”或在 ack VC 上 piggyback）。
- Credit 初始值 = 下游 buffer 深度（VC0–3 = 8，VC4 = 16）。

### 8.5 死锁避免

死锁来源：

1. **协议死锁** ：请求-响应链。VC 分层（request VC0/1/2 → 不能阻塞 response VC3 → 不能阻塞 ack VC4）。
2. **路由死锁** ：DOR 本身无 cycle。
3. **流控死锁** ：response 在 reverse path 也走 DOR，response 不依赖 request 的 credit。
4. **Atomic 链** ：atom.cas 在 L2 内可能 stall，但 NoC 上它表现为 1 个 request + 1 个 response，不构成依赖环。
5. **Fence drain 等待** ：fence drain 时 source 持有 LSQ entry 等 ack，ack 来自 VC4 独立通道，不会被 source 自己的反压阻塞。

### 8.6 Message 格式

每个 NoC packet 由 header flit + payload flit 组成。

### 第 9 章 L2 — GPU-Scope Point of Ordering

L2 是本设计的核心同步点：所有 `.gpu` scope 的 acquire/release/atom 在这里被串行化与 ack。L2 是 **96 MB，64 bank** 的 chip-wide 共享 cache。每 bank 内部含一个 **Ordering Engine (OE)** ，是本章的重点。

### 9.1 Bank 物理布局

| 项 | 数值 |
| --- | --- |
| Bank 数 | 64 |
| 单 bank 容量 | 1.5 MB |
| 关联度 | 16-way |
| Line / Sector | 128 B / 32 B |
| Tag array | 16 way × 768 set = 12K tag/bank |
| MSHR | 32 entry/bank |
| 输入 port | 1 request (from NoC VC0/VC1/VC2) + 1 ack-out (VC4) |
| 输出 port | 1 response (VC3) + 1 ack (VC4) |
| 频率 | 1.5 GHz |
| 含原子 ALU | 是 (per-bank, 32-bit + 64-bit width) |

地址 hash： `bank_id = hash(PA[6:51])` ，避免 stride pattern 热点。

### 9.3 关键决策 [D-07]: Release Ack 在 OE 入队即 Ack

> **Release ack 的语义** ：本设计采用 “in-queue ack”。release 写到达 L2 OE 后，OE 把它入”全局可见 commit queue”， **此时即可对 source 回 ack** （不等数据写到 SRAM、不等写到 HBM）。

为什么这是正确的？

- 只要 OE 已把该 release 入队， **任何后续到达此 bank 的请求** 在它 retire 之前都会先看到该 release 的写（OE 按入队顺序处理）。
- 这就是 PoO 的本质：物理”成为可见”的时刻 = OE 入队时刻。
- 等到真正写入 SRAM/HBM 才 ack 会无谓延长 release fence ≈300 cycle。

唯一例外是 `.sys` release：它需要等 SCB 进一步 ack（因为 .sys PoO 在 SCB，不在 L2）。

### 9.4 Ordering Engine (OE) 详细微架构

每 bank 一个 OE。它管理 4 个核心结构：

### 9.4.1 Per-bank Release Queue (RQ)

类似一个 reorder-buffer，保证 commit 顺序：

| 字段 | 宽度 | 说明 |
| --- | --- | --- |
| valid | 1 |  |
| txn_id | 12 | NoC 全局 ID |
| src_sm_id | 7 |  |
| addr | 52 |  |
| mask | 4 | sector mask |
| data_ptr | 8 | 指向 data buffer |
| ord | 3 |  |
| scope | 2 |  |
| state | 3 | ENQ / WRITING_RAM / DONE_LOCAL / WAIT_SCB / RETIRED |
| ack_sent | 1 | local ack 已发回 source |
| sc_token | 16 | (仅 SC) |
| is_atom | 1 |  |
| atom_op | 4 |  |
| age | 6 | per-source FIFO age |

RQ 深度：64 entries/bank。

**Commit 规则** ：

- 同 src 的 RQ entry 必须按 `age` 顺序进入 RAM。
- 不同 src 之间可以并行 commit。
- ack 在 ENQ 完成（state ≥ ENQ）就可以发出 **当且仅当** ：

- `.sys` scope entry 必须等 SCB ack 回来后才 retire。

### 9.4.2 Per-source Outstanding Counter (POC)

| 字段 | 宽度 |
| --- | --- |
| src_sm_id | 7 (索引) |
| outstanding_releases | 6 |
| outstanding_atoms | 6 |
| last_ack_age | 6 |

128 SM × ≈26 bit = 大约 3.3 Kb 存储/bank。

`fence.gpu` drain 时，source SM 发 FENCE_TOK 到所有 L2 bank：

- 每 bank 检查 POC：若 `outstanding_releases == 0 && outstanding_atoms == 0` ，立即回 FENCE_ACK。
- 否则等 POC 归 0 后回 ack。
- Source SM 在 fence sequencer 收集 64 个 FENCE_ACK 即完成 drain。

### 9.4.3 Acquire Gate (AG)

acquire LD 到达 bank 后的处理：

1. 入 RQ（与 release 共用 RQ，但 op 标记 ACQ）。
2. AG 检查：从该 bank 的 RQ 中，所有 **PO-earlier than this acquire** 的 same-source entry 必须已经 ENQ（保证 cumulative）。 
 实际上 acquire 不依赖 same-source 之前的 op；它依赖的是”它要观察的 release 已经入队”。这点 **自然满足** ：只要 acquire 后到达 bank，它就在 RQ 中排在所有先到 release 之后；OE 按入队顺序处理它。
3. 数据读出 → DATA_RESP via VC3。
4. **同时** 通过 VC4 发一个 ACQ_ACK（让 source 的 L1 epoch 进入 EPOCH_TICK 状态——但实际本设计中 epoch tick 是在 LSU retire 时本地完成，不需要 L2 ack；只有 data 回到就够了）。

**[D-09]** 简化决策：acquire LD **不需要单独的 ack** ，因为它 inherently 等数据返回。 `ld.acquire.<S>` 的 ack 语义在 LSU 端就是 “data 到达 + 之前 PoO drain 完成 + epoch tick”。L2 OE 只要按 RQ 顺序处理它即可保证 INV-03/09。

### 9.4.4 SC Sequencer 接口

每 bank 的 OE 连接到 **chip-level SC sequencer** （位于 L2 中心仲裁器）：

- 当 OE 收到 `SC_TOK` 包，把 token 转发给 chip-level sequencer 并暂存当前 RQ 状态（”freeze”）。
- chip-level sequencer 收齐 **所有相关 bank** 的 freeze ack 后，分配全局 SC sn 并广播 SC commit。
- 各 bank OE 在 commit phase 中，按 sn 顺序把 SC op 插入全局 commit point。

### 9.5 关键决策 [D-06]: fence.sc.gpu 两阶段提交

### 9.5.1 Phase 1: Freeze

```text
Source SM:
  1. fence sequencer 进入 SC_P1
  2. 发出 SC_TOK 给所有 64 L2 bank (multicast VC2 high-prio)
     - token: {src_sm, sub_id, local_counter, scope=GPU}

Each L2 bank OE:
  3. 收到 SC_TOK，把当前 RQ 中所有 in-flight 操作"冻结"（不可再被新 op 越过）
  4. 在 RQ 末尾插入一个 SC marker entry，标 sc_token = token
  5. 向 chip-level SC sequencer 发"freeze ready"
```

### 9.5.2 Chip-level SC Sequencer 操作

```text
SC Sequencer:
  6. 等待 64 个 bank 的 "freeze ready"
  7. 分配全局 SC sn = (global_counter++)
  8. 广播 SC_COMMIT(sn, sc_token) 到所有 64 bank
```

### 9.5.3 Phase 2: Commit

```text
Each L2 bank OE:
  9. 收到 SC_COMMIT，在 RQ 中找到对应 SC marker，把它标为 "SC commit point sn=X"
  10. 当 SC marker 自然 retire 时，发出 SC_ACK_P2 给 source SM
  
Source SM:
  11. fence sequencer 收齐 64 个 SC_ACK_P2，进入 EPOCH_TICK，然后 DONE
```

### 9.5.4 为什么是正确的

- Phase 1 保证：在所有 bank 的 view 中，SC token 之前的所有 op 都已经在 RQ 中”确定 commit”了（不会被后到的非 SC op 越过）。
- Phase 2 保证：所有 bank 看到的 SC sn 一致，于是所有 SC op 在 sn 维度上构成全序 → INV-06 满足。

### 9.5.5 性能

- 估算：64 bank multicast ≈50 cycle；freeze ready 汇聚 ≈50 cycle；commit broadcast ≈50 cycle；retire 平均 ≈100 cycle；NoC 来回 ≈150 cycle。
- 总 fence.sc.gpu latency ≈ 400 cycle。这是设计目标，比 fence.acq_rel.gpu (≈100-200 cycle) 贵 2-3 倍，符合 SC 是”大锤”的预期。

### 9.6 Atomic 操作

`atom.<op>.<ord>.<scope>` 在 L2 bank 内执行（除非 `.cta` 在 SM 内）：

1. NoC 收到 ATOM_REQ → 入 RQ。
2. OE 等到 PO-earlier same-src 操作 ENQ。
3. **Atomic ALU 操作** ：从 DataRAM 读旧值 → 算新值 → 写回 → 把旧值放进 DATA_RESP。
4. 整个 RMW 在 bank 内是 atomic（持 line lock，≈3 cycle）。
5. 根据 `ord` ：

- `relaxed` ：发 DATA_RESP 即可，无 ack。
- `acquire` ：同 acquire LD，inherently ack via data。
- `release` ：发 ACK via VC4。
- `acq_rel` ：发 DATA_RESP（带 ack 语义） + ACK via VC4。

### 9.7 Miss 处理与 MSHR

L2 MSHR：32 entries/bank。结构与 L1 MSHR 类似但加了 ordering 字段：

| 字段 | 宽度 | 说明 |
| --- | --- | --- |
| 同 L1 MSHR | - |  |
| req_list | 16 × 16-bit | 多请求合并队列（保留各 src 的 req） |
| ord_max | 3 | 该 MSHR 上聚合请求的最严 ord |
| scope_max | 2 |  |
| pending_acq_cnt | 4 | acquire 数（用于 ack 触发） |
| is_dirty_miss | 1 | 写 miss 是否需要先 fill |

合并规则：同 line 的 fill 请求合并；但 **acquire miss 不与 relaxed miss 合并** （acquire 需要”按 RQ 顺序”对待，relaxed 可以乱）。

### 9.8 L2 Coherence with L1

本设计 L2 是 **inclusive of L1 metadata** 的弱版本：

- L2 tag 不跟踪 L1 是否有副本（没有 directory）。
- L1 evict line 不通知 L2（silent eviction）。
- L1 epoch invalidate 是 self-invalidate，不需要 L2 配合。
- 这是非 multi-copy-atomic 的代价：靠 acquire 主动重 fetch 实现可见性。

### 9.9 L2 对 INV 不变量的贡献

| INV | 机制 |
| --- | --- |
| INV-02 | RQ ENQ 顺序 + ack 在 ENQ 后发出 |
| INV-04 | atomic 在 bank 内 line-locked + RQ ordered |
| INV-05 | FENCE_TOK 驱动 POC 计数清零后 ack |
| INV-06 | 2-phase SC commit + global SC sn |
| INV-07 | 不破坏；接收和发出严格按 NoC VC FIFO |
| INV-08 | release 不在 ENQ 之前 ack |
| INV-09 | acquire 数据返回前，PoO 内 RQ 已串行化所有先到 release |

### 9.10 L2 资源估算

| 资源 | 数值 |
| --- | --- |
| 单 bank 面积 | ≈3 mm² @ 5nm |
| 总 L2 面积 | ≈190 mm² |
| 单 bank 带宽 | 128B/cycle @ 1.5 GHz = 192 GB/s |
| 总 L2 带宽 | 12 TB/s |
| OE 控制逻辑 | ≈0.3 mm²/bank |
| SC Sequencer 中心逻辑 | ≈0.2 mm² |

### 第 10 章 Memory Controller / HBM

MC 不直接参与 acq/rel ordering 语义（PoO 是 L2 或 SCB），但它必须保证 **L2 委托给它的写入顺序不被乱排** 。

### 10.1 MC 参数

| 项 | 数值 |
| --- | --- |
| MC 数 | 12 |
| 每 MC HBM channel | 1（每 MC 控制一个 HBM3 stack 的一组 channels） |
| 频率 | 1.6 GHz I/O，core 0.8 GHz |
| 写 buffer/MC | 64 entry × 64 B |
| 读 buffer/MC | 32 entry × 64 B |
| Bank scheduler | open-page + FR-FCFS |

### 10.2 MC 与 L2 的接口

L2 bank 到 MC 的请求：

- WRITE request： `{addr, data, mask, src_l2_bank, ack_required}` 。
- READ request： `{addr, dst_l2_bank, txn_id}` 。

MC 对 L2 的响应：

- READ_RESP： `{txn_id, data}` 。
- WRITE_ACK：（仅 `ack_required=1` 时，对应 `.sys` 写或 SCB 转下来的写）

### 10.3 Ordering 与 MC

L2 OE **已经** ack 了普通 `.gpu` release（在 RQ ENQ 即 ack）。MC 之后做的写入 HBM 只是”持久化”，不需要再回 source SM。

但是有几个 ordering 需求：

1. **Same-address PO 内** ：MC 必须保证 same-address 的写按到达顺序持久化（INV-01 的延伸）。实现：MC 写 buffer CAM 检测同地址，若已存在则覆盖或串行化。
2. **Refresh / scrub 不引起虚假 ordering** （INV-11 的 corollary）：refresh 是 HBM 内部行为，MC 不会因此重排请求；scrub 用单独通路。
3. **ECC 错误处理** ：单 bit 修复透明；多 bit 不可修复 → 通过 interrupt 通知 host，不影响 ordering（中断点之前数据保留 commit 顺序）。

### 10.4 .sys 写的特殊路径

若 L2 OE 接收到一个 `.sys` release 写，它的路径是：

1. L2 bank 内 OE ENQ → 写 DataRAM → 同时投递到 **SCB** （而非 MC）。
2. SCB 把这条写通过 NVLink 推到远端， **等远端 ack** 。
3. SCB 收到远端 ack 后回 L2 bank → L2 bank 给 source SM 发 final ack。

> 关键： `.sys` release 不在 L2 入队就 ack；它”借用” L2 的存储和 RQ，但 ack 决策权在 SCB。

### 10.5 MC 写完成语义

| Source | Ack 来源 | 何时持久化 |
| --- | --- | --- |
| relaxed write | 无 | best-effort，可能在 buffer 中合并 |
| .gpu release | L2 OE（不等 MC） | MC 后台异步持久化 |
| .sys release | SCB ack 后 source 视为完成 | MC 持久化与 ack 解耦 |
| volatile write | SCB ack 后 | MC 在 SCB 推下来后立即写入（关 buffer 合并） |

### 第 11 章 NVLink / 系统域 — .sys Scope

`.sys` scope 是最大的 scope，覆盖整个系统的所有 GPU/CPU/Accelerator。其 PoO 在 **System Coherence Bridge (SCB)** 。本章描述 SCB 微架构与 NVLink 协议层。

### 11.1 设计前提

- 系统拓扑：本设计支持 8-GPU 全互联 NVLink ring/torus。
- CPU 接口：CXL.mem (或 PCIe ATS+coherence)。
- 本 spec 不深入 CPU 侧实现，但假设 CPU 也是 PTX- `.sys` -兼容的（即支持 release/acquire 语义对应 CXL 的 PRD/RD/WR + ordering flag）。

### 11.2 SCB 顶层结构

![](https://pic1.zhimg.com/v2-c903f761442dad9ba1c20c797310feb8_r.jpg)
*图 13：System Coherence Bridge 顶层结构*

### 11.3 SCB 内主要结构

### 11.3.1 Sys Release Queue (SRQ)

| 字段 | 宽度 | 说明 |
| --- | --- | --- |
| valid | 1 |  |
| src_chip_id | 4 | 本系统中 GPU/CPU 编号 |
| src_sm_id | 7 | 本芯片 SM |
| dst_chip_id | 4 | 目标芯片 |
| dst_addr | 52 | system PA |
| data_ptr | 8 |  |
| op | 3 |  |
| ord | 3 |  |
| state | 4 | LOCAL_ENQ / NVL_OUT / REMOTE_ACK_WAIT / GLOBAL_VIS / DONE |
| txn_id | 16 | global txn id |
| age | 8 | per (src,dst) FIFO age |

容量：256 entry/SCB。

### 11.3.2 Per-(src,dst) FIFO 保序

`.sys` ordering 的关键 invariant： **来自同一 src 到同一 dst 的 release 必须 FIFO** 。SCB 用 per-(src_chip, dst_chip) FIFO（最多 8×8 = 64 个 FIFO，每个 8 entry）维护顺序。跨 dst 之间可乱。

### 11.3.3 Sys SC Engine

类似 L2 的 SC sequencer，但工作在 chip-level：

- `fence.sc.sys` token 从本 SM 经 L2 → 转发到本芯片 SCB。
- 本芯片 SCB 通过 NVLink **broadcast** SC_TOK 到所有其它芯片 SCB。
- 所有 SCB 收到后做”freeze”（同 L2 SC sequencer，但是 chip-level），回 SC_ACK_P1。
- 本 SCB 收齐 7 个其它 chip 的 ACK_P1 → 分配 global system-SC sn。
- broadcast COMMIT；其它 SCB 完成 commit retire 后回 ACK_P2。
- 本 SCB 收齐 → 回 source SM。

### 11.4 NVLink 协议层

NVLink-class 链路提供：

- 64B flit、CRC 保护。
- 每方向 25 GB/s × 8 lane = 200 GB/s。
- 协议层支持 packet 类型：READ/WRITE/ACK/INV/SC_TOK/SC_COMMIT/SC_ACK。

**关键性质** ：NVLink 链路本身在物理层是 in-order 的（per-lane CRC + retransmit），所以 SCB 不需要在链路上重新做 reorder buffer。

### 11.5 .sys release 完整流程

```text
1. SM LSU 发 st.release.sys 给 L1 → WCB → NoC VC2
2. L2 bank OE 收到，识别 scope=SYS，把它放进 RQ 但标 state=WAIT_SCB
3. L2 把该 write 推送给 SCB (Local NoC)
4. SCB SRQ 入队，分配 txn_id，按 (src,dst) FIFO age
5. SCB Tx Engine 通过 NVLink 推送 WRITE packet 给 dst chip
6. dst chip SCB 收到，把 write 转给本地 L2 bank（视为远端发起的 .sys 写）
7. 远端 L2 OE ENQ，回 ACK 给远端 SCB
8. 远端 SCB 经 NVLink 回 ACK 给 source SCB
9. source SCB 把对应 SRQ entry state=GLOBAL_VIS，发 ACK 给 source L2 bank
10. source L2 bank 把 RQ entry state=RETIRED，发 ACK 经 NoC VC4 给 source SM
11. source SM LSU 看到 ack_received=1，retire LSQ entry
```

总延迟估算：≈2000 cycle（含 NVLink 往返 ≈1000 cycle + 两端 L2/SCB 处理）。

### 11.6 .sys acquire 流程（更简单）

```text
1. SM LSU 发 ld.acquire.sys → 强制 bypass L1，进 NoC VC0
2. L2 bank 收到，识别 scope=SYS：
   a. 把 acquire 放 RQ 但要先等所有"该地址相关的远端 in-flight write"清空
   b. 实际实现：L2 把 acquire 也转给 SCB（SCB 是 .sys 的 PoO）
3. SCB 收到 acquire，检查 SRQ 上是否有 PO-earlier-than-this-acquire 的 inbound write 在 pending；如有则等
4. SCB 一旦放行，向远端 SCB 发 READ request（远端 L2 / HBM 返回 data）
5. 数据回到 source SCB → source L2 → source LSU
6. LSU retire 时 tick sm_epoch[SYS] += 1 (并连带 GPU/CLUSTER epoch tick)
```

> 优化：很多 `.sys` acquire 实际只是要”对方的写已经被本机看到”——可以通过本地 SCB 缓存的 inbound write log 直接验证，不必每次都发远端 READ。具体实现见 11.7。

### 11.7 SCB Inbound Stream

为了让 `.sys` acquire 高效，SCB 维护 **inbound write log** （小型 CAM-like 结构，256 entry）：

| 字段 | 宽度 | 说明 |
| --- | --- | --- |
| addr | 52 |  |
| src_chip | 4 |  |
| age | 16 |  |
| state | 2 | RECEIVED / FORWARDED_TO_L2 / VISIBLE |

当 acquire.sys 到 SCB，SCB 查 inbound log：

- 若没有 in-flight pending 远端写到本地区域，acquire 可立即 ack（且数据从本地 L2 / HBM 读）。
- 若有 in-flight，等其 VISIBLE 后再 ack。

### 11.8 CXL.mem / CPU 兼容性

CXL.mem 的 `MemWr` 不携带 release 语义；CXL 上 ordering 由 host 软件 fence 保证。SCB 充当”语义翻译器”：

- 来自 CPU 的 `MemWr` → 本设计视为 `relaxed .sys write` 。
- 来自 CPU 的 fence/flush 指令 → 本设计视为 `fence.acq_rel.sys` ，触发 SCB drain。
- 本 GPU 发的 `.sys release` 写 → 通过 CXL.mem 推送给 host；host 端的 acquire 等价于 CPU 的 `acquire load` 。

> 实际 CXL 版本的兼容（CXL 3.1+）有 `BIRsp` / `Snp` 流程，可承载 release/acquire 语义。本 spec 不展开 CXL 细节，但 SCB 留有协议适配层。

### 11.9 .sys scope 的硬件 INV 贡献

| INV | 机制 |
| --- | --- |
| INV-02 (sys) | SCB SRQ FIFO + 远端 ack 等待 |
| INV-04 (sys) | atom.acq_rel.sys 在 SCB 串行化（SCB 内含原子 ALU 处理 cross-chip atomic） |
| INV-05 (sys) | fence.acq_rel.sys 触发 SCB drain（per-(src,*) FIFO 清空） |
| INV-06 (sys) | SCB 2-phase SC，含 NVLink broadcast |
| INV-09 (sys) | acquire.sys 等待 SCB 入站写排空 |

### 11.10 SCB 资源估算

| 资源 | 数值 |
| --- | --- |
| SCB 面积 | ≈8 mm² @ 5nm |
| SRQ 存储 | 256 × ≈96 bit = 24 Kb |
| Inbound log | 256 × ≈74 bit = 19 Kb |
| NVLink PHY | 16 lane (8 send + 8 recv) |
| SCB 频率 | 1.5 GHz core，25 GHz I/O |
| Sys SC Engine 延迟 | ≈2000 cycle (含 NVLink RTT) |

### 第 13 章 异常与边界情况

本章覆盖那些”主流程之外”但必须严格设计的场景。任何一处漏掉都会引入正确性漏洞或死锁。

### 13.1 投机执行与 squash

| 场景 | 行为 |
| --- | --- |
| Branch mispredict 导致 LSQ entry 需要 squash | 仅 squash 未 commit 的 entry；已 commit 的不可回滚（已对外可见） |
| acquire LD 投机执行 (e.g. 预取) | 不允许提前 tick epoch；epoch tick 只在 retire 时 |
| release ST 投机执行 | 禁止：release ST 不能在 commit 前发到 NoC；LSU 只在 dep_mask 清零且非投机才发包 |
| atom 投机执行 | 禁止：atom 有副作用，必须非投机 |
| prefetch 失败 | prefetch 是 hint，不影响 ordering；squash 即丢弃 |

### 13.2 Page fault / TLB miss

- TLB miss：LSQ entry 进入 `TLB_WAIT` ，hardware page walker 完成后填 PA，继续 L1_PROBE。
- Page fault：触发异常，sub-core 进入 trap handler。

- 远端访问（DSMEM/SCB）的 page fault 与本地等价。

### 13.3 ECC 错误

- L1 single-bit：透明修复，对外无影响。
- L1 multi-bit：触发异常，整 line 标 invalid + 通过 interrupt 上报；epoch 不受影响。
- L2 ECC 错误：同上，但若错误在已发 ack 的 entry → 系统级 fatal（数据已被声明可见）。
- NoC ECC：包 parity 校验 + 重发；重发不破坏 ordering（因为 same-pkt-id 重发，下游去重）。

### 13.4 Power gating SM 时的 in-flight rel-token

挑战：某 SM 想 power gate，但它还有 in-flight `.gpu` release 在 L2 RQ 未 retire。

策略：

1. SM 进入 “power-down request” 状态，停止 issue。
2. 触发本地 `fence.sc.sys` 等价的 drain：等 LSQ 排空 + WCB 排空 + 所有 in-flight release 在 L2/SCB 都 retire。
3. drain 完成后，本 SM 的 epoch 与外界 sync 完成。
4. 进入 power gate。

唤醒后：epoch 重新初始化为 0（因为外界没人会用旧 epoch tag 跟它通信，所有 in-cache 数据已 flushed/invalidated）。

### 13.5 Epoch wraparound 同步问题

如 6.3.2 所述，sm_epoch 8-bit 在 256 acquire 后回卷。回卷处理：

1. 当 `sm_epoch[s]` 即将回卷（即将等于某活跃 line 的 LineEpoch[s]），L1 controller 触发 **forced flush** ：walk tag array 把所有 LineEpoch[s] != 当前值的 line 设 V=0。
2. 这个 forced flush 是后台任务，可在 sub-core idle 周期渐进完成。
3. 若强制必须立即完成：用阻塞式 walk，单 SM 最多 ≈10000 cycle 完成。

**简化** ：把 epoch tag 加宽到 16-bit 即可避免实际部署中遇到回卷（典型 inner-loop ≈10万次 acquire 才会回卷 16-bit）。

### 13.6 同 thread 同地址相邻 release/acquire

代码：

```text
st.release.gpu [X], v1
ld.acquire.gpu r1, [X]   // 自己读自己刚发的 release
```

LSU 中：

- release 发出后进入 LSQ。
- acquire 跟在后面。acquire 的 dep_mask 包含 release 的 anchor bit。
- LSU 内 **store-to-load forward** ：acquire LD 检查 LSQ 是否有同地址未 commit 的 release ST → 命中即 forward。

> 这是合法的：release 的写已经在 LSQ 里，acquire 可以从本地”自己的”角度立即看到。但 forward **不** 让 acquire 跳过 epoch tick；acquire 仍执行 epoch++。

### 13.7 多个 release 写同地址

```text
st.release.gpu [X], v1
st.release.gpu [X], v2
```

- 两个 release 在 LSU 都进入 LSQ。
- 各自 `pre_release_mask` 包含对方？v2 的 pre_release_mask 必须包含 v1（v1 是 PO-earlier write）。
- 两次写都进 WCB。 **WCB 不允许两条 release 合并** （D-02 中 close 后不可再写）。
- L2 OE 接收两条 ST_REQ_ACK，按 NoC 同 src 同 VC FIFO 顺序 ENQ。
- ack 也按 FIFO 返回。LSU 按 age 顺序 retire。

最终 X 在 L2 上是 v2。任何观察者只要它的 acquire 看到 v2，就 cumulative-implies 看到了 v1 之前所有 release 链。

### 13.8 跨 cluster 的非 .cluster 访问

代码（在 cluster A 内 SM）：

```text
ld.acquire.cta [Y]   // Y 是某个其他 SM (in cluster B) 写的
```

- `.cta` scope 不蕴含跨 SM 同步保证；硬件 **不** 等 cluster B 的 in-flight release ack。
- 这是 PTX 允许的（软件错误，不在 scope 内）。可能读到 stale 数据，但不破坏不变量。

### 13.9 .volatile 与 MMIO

- `.volatile` 强制 bypass L1 + 强制 SYS scope + acq_rel。
- MMIO 地址空间用 `addr_space=MMIO` ，所有 op 自动按 .volatile 处理。
- MMIO 不进 L2 cache（L2 看到 addr_space=MMIO 直接转给 SCB/HBM controller），保留写顺序。
- MMIO 写的 ack 必须等远端设备真正接受（SCB 处理）。

### 13.10 死锁场景排查

| 潜在死锁 | 已防御机制 |
| --- | --- |
| WCB 满 + LSU stall + release ack 等待 → 又来新 release | 优先 flush oldest；release 优先 issue 到 NoC（不进 WCB 末尾） |
| NoC VC0 满阻塞 VC3 | VC 独立 buffer + credit |
| L2 RQ 满 → 拒绝新 release → NoC 反压 → SM 卡住 | RQ 满时反压；上游通过 credit 看到容量；不死锁，仅 stall |
| fence.sc.gpu 等待 → 但某 bank 自己也在等同 SM 的 release ack | 不会：fence drain 与 release 走同 FIFO，先到的 release 先 ack；fence 一定在它之后 ACK |
| Cluster fabric 满阻塞 cluster fence | CCE OSB 有 backpressure；fence 用高优先级 token |

### 13.11 复位与启动

- Reset 时：所有 sm_epoch=0，LineEpoch=0（自然 hit），所有 LSQ/MSHR/RQ/SRQ valid=0。
- Cold start：第一个 acquire tick epoch=1，line 全部 stale → 必 miss 到 L2 fetch，正确。

### 第 14 章 验证 (DV) — 属性、Litmus、Traceability

本章定义 DV 团队验证本设计正确性的三个层面：形式属性（SVA-like 断言）、litmus tests、以及一致性追踪表。

### 14.1 形式属性（SystemVerilog Assertion 风格）

下列属性可在 RTL 与 reference model 上 prove / simulate。每条对应一个 INV。

**P1 (INV-02)** ：release retire 之前，PO-earlier 写已到 PoO。

```text
property p1_release_drain;
  @(posedge clk)
  retire(rel) |-> 
    foreach (w in PO_earlier(rel) where is_write(w)):
      had_visible_at_PoO(w, scope_of(rel)) before retire(rel);
endproperty
```

**P2 (INV-03)** ：acquire retire 之后，所有 PO-later 访存看到 sw 链。

```text
property p2_acquire_visibility;
  @(posedge clk)
  retire(acq) |-> 
    foreach (op in PO_later(acq)):
      sees_releases_synced_by(acq, op);
endproperty
```

**P3 (INV-06)** ：fence.sc.在 scope S 内构成全序。

```text
property p3_sc_total_order;
  forall (sc_a, sc_b in scope_S):
    happens_before(sc_a, sc_b) || happens_before(sc_b, sc_a);
endproperty
```

**P4 (INV-07)** ：NoC 同 src/dst/VC/addr 不重排。

```text
property p4_noc_ordering;
  m1.send_time < m2.send_time AND 
  same_src(m1, m2) AND same_dst(m1, m2) AND 
  same_vc(m1, m2) AND same_addr(m1, m2) 
  |-> m1.deliver_time < m2.deliver_time;
endproperty
```

**P5 (INV-08)** ：release 入 PoO RQ 之前不 ack。

```text
property p5_ack_not_premature;
  ack_sent(rel) |-> RQ_enq_done(rel);
endproperty
```

**P6 (INV-10)** ：投机 squash 不留 sw 副作用。

```text
property p6_no_speculative_sw;
  squashed(op) |-> 
    !ever_committed(op) AND !ever_acked(op);
endproperty
```

### 14.5 验证策略

1. **Unit level** ：每个模块独立 testbench（LSQ、L1、WCB、NoC router、L2 OE、CCE、SCB）。
2. **Subsystem** ：SM + L1 + NoC + 1 L2 bank 端到端跑 MP/SB litmus。
3. **Chip** ：全 chip 模型跑全套 litmus + random stress（cuMemcheck-like trace replay）。
4. **System** ：多 chip 模型跑 .sys 套（含 NVLink 模型）。
5. **Formal** ：每条 INV 在合理抽象层 prove；特别是 NoC 顺序、L2 OE 2-phase SC。
6. **Performance regression** ：fence.acq_rel.gpu < 200 cycle, fence.sc.gpu < 500 cycle, fence.sc.sys < 4000 cycle 作 perf target。
