## TensorRT 在 Hopper（H100/H200）上的新特性

Hopper 相比 Ampere 引入了不少底层硬件能力，TensorRT（8.5+，TRT-LLM 1.0+）围绕这些能力做了系统性支持：

### 1. FP8 推理（最重要的新特性）

- **支持 FP8 Tensor Core**：`E4M3`（动态范围大）和 `E5M2`（精度更高）两种格式，与 FP16 相比吞吐约翻倍
- **量化感知训练（QAT）和校准两种路径**：

- **FP8 KV Cache**（TRT-LLM）：推理时 KV cache 也存成 FP8，显存和带宽都减半，decode 阶段提速明显
- **FP8 GEMM + 量化反量化融合**：reformat（cast）操作被融合进相邻 kernel，减少额外开销
- **PaddlePaddle/PyTorch QAT 模型的直接导入支持**

### 2. Transformer Engine（TE）集成

- TensorRT 8.6 起与 Transformer Engine 打通：FP8 训练的模型可以**直通 TensorRT 推理**，不用手动处理量化参数
- TRT-LLM 复用 TE 中的 fused kernel（LayerNorm、RoPE、Attention 等），并针对 Hopper 调优

### 3. Hopper 硬件指令级支持

- **TMA（Tensor Memory Accelerator）**：硬件级的异步 tensor 拷贝单元，替代软件实现的 cp.async。TensorRT 的 GEMM kernel（基于 CUTLASS 3.x）在 H100 上默认启用 TMA 做全局显存 ↔ shared memory 的搬运，让 Tensor Core 计算和拷贝完全重叠
- **WGMMA（Warpgroup MMA）指令**：一组线程（warpgroup）协作执行矩阵运算，是 Ampere `mma.sync` 的下一代，吞吐显著提升。TensorRT 的 Hopper 专用 GEMM kernel 都基于 wgmma 构建
- **Thread Block Cluster（线程块簇）**：跨 SM 协作的更大调度单元，TensorRT 在部分 kernel 中用于优化多 SM 间的数据共享（如 flash attention）
- **DSMEM（Distributed Shared Memory）**：Cluster 内 SM 之间直接访问 shared memory，Attention kernel 利用它减少 HBM 往返

### 4. 大显存与高带宽利用

- H100 有 80GB HBM3（H200 141GB HBM3e）和 3.35TB/s 带宽，TensorRT 优化了 **memory pool 的显存复用策略**，支持在 H 卡上塞下更大 batch 的模型
- **量化到 4bit（INT4/FP8 混合）+ KV cache 优化**，让长上下文推理的可行性大幅提升

### 5. 软件栈配套

- **Triton 推理服务器 + TRT-LLM 后端**：Hopper 上支持 in-flight batching、paged KV cache、disaggregated serving（prefill/decode 分离）
- **Multi-GPU**：Hopper 的 NVLink 4（900GB/s）+ Tensor Parallel 优化，专家并行（MoE）的 all-to-all 通信针对 NVLink 调优
- **CUDA Graph 增强**：Hopper 上录制更大的 graph 更稳定，decode 阶段的 launch 开销进一步降低
- **H100 SXM vs PCIe 区分调优**：builder 对两者选择不同 kernel

### 简单总结

Hopper 上 TensorRT 的升级主线就三件事：

> **FP8 计算 + TMA/wgmma 的硬件级 kernel + 大显存下的显存管理优化**

实际收益上，Llama 70B 级别的模型在 H100 上用 TRT-LLM（FP8 权重 + FP8 KV cache）相比 FP16 模式，吞吐可提升约 **1.5–2 倍**，能服务的并发数也近似翻倍。

想继续深入的话，可以讲 FP8 的量化原理（为什么 E4M3 够用）、wgmma 相比 mma.sync 的架构差异，或者 TRT-LLM 在 H100 上的具体部署参数调优。

## 下面详细介绍硬件级kernel

## TMA / WGMMA 深度讲解

先建立整体认识：Ampere 的矩阵计算流水线里，数据搬运（cp.async）是**线程自己干**的，指令发射也是**线程级别**的；Hopper 把这两件事都”硬件化”了——TMA 把搬运外包给专用硬件单元，wgmma 让一个线程组发射一条矩阵指令。这个变化直接导致了 kernel 结构的彻底重写（CUTLASS 3.x 那套新抽象）。

### 一、WGMMA（Warpgroup MMA）

### 1. 什么是 wgmma

一条 `wgmma` 指令 = **一组 4 个 warps（128 线程，称为一个 warpgroup）协作完成一次大矩阵运算**。

对比：

```text
Ampere (mma.sync)：  1 个 warp 发射，warp 内 32 线程各自喂数据
                     m16n8k16，tile 小，指令发射频繁

Hopper (wgmma)：     1 个 warpgroup 发射（1 号线程发出指令）
                     m64nNk8，N 可达 256，单次完成 64×256×8 的矩阵块
                     其余 127 个线程不用管发射，只管提供数据
```

### 2. 为什么更快——从”喂饭”到”自助餐”

**Ampere 的问题**：`mma.sync` 要求每个线程用寄存器显式提供 A/B 矩阵的片段（fragment）。寄存器是稀缺资源：你想算 128×128 的大 tile，寄存器根本不够同时存 A、B、累加器 C。所以只能用小 tile 多发射，Tensor Core 经常因为等数据而空转。

**wgmma 的关键设计**：

- **B 矩阵可以直接从 shared memory 读**（SS 模式），不占用寄存器
- **A 矩阵也可以从 shared memory 读**（SS 模式），或留在寄存器（RS 模式）
- **累加器 D 留在寄存器**，归这 128 个线程的寄存器 collectively 持有

```text
寄存器需求对比（算一个 128×256×32 的块）：

Ampere mma.sync：
  A fragment 需要占用寄存器 + B fragment 需要占用寄存器
  → 寄存器爆炸，只能小 tile 反复循环

Hopper wgmma.mma_async：
  A、B 都在 shared memory，寄存器只存 D（累加器）
  → 寄存器够用了，可以发一条巨大的指令
```

### 3. 为什么叫 async——异步是灵魂

`wgmma.mma_async` 发射后**立即返回**，不阻塞发射线程。它的完成由后续指令同步：

```cuda
// 伪代码：wgmma 的异步流水
wgmma.mma_async 指令1   // 发射后立即返回
wgmma.mma_async 指令2   // 接着发射
wgmma.mma_async 指令3
wgmma.commit_group     // 打包这一组
wgmma.wait_group 0     // 等全部完成（或留 1 组不等待，继续流水）
```

这样一个 warpgroup 可以连续发射多条 wgmma，Tensor Core 连续不停地算；同时**多个 warpgroup 还能并行**——比如 2 个 warpgroup，一个算当前 tile 的同时另一个已经用 TMA 预取下一批数据。

### 4. 实际例子：CUTLASS 风格的 GEMM 主循环

```cuda
// Hopper GEMM 主循环的典型结构（简化）
// 一个 CTA 有 2 个 warpgroup（256 线程），各自负责 D 的一半

for (int k = 0; k < K; k += 32) {
    // TMA 异步把下一块 A、B 从 HBM 搬到 shared memory
    // —— 由 1 个线程发射，不占计算资源
    tma.load_async(A_shared[next], A + k);
    tma.load_async(B_shared[next], B + k);

    // 当前 warpgroup：发射一串 wgmma
    // A、B 都从 shared memory 读，累加器 D 在寄存器
    wgmma.mma_async(D, A_shared[cur], B_shared[cur]);
    wgmma.mma_async(D, A_shared[cur] + 8, B_shared[cur] + 8);
    // ... K 维循环 ...

    tma.wait();  // 等数据到齐
    wgmma.wait_group(0);
    __syncthreads();  // 换 shared memory buffer
}
```

关键点：**搬运、发射、计算三者完全解耦**，这正是”硬件化”带来的结构红利。

### 二、TMA（Tensor Memory Accelerator）

### 1. 解决什么问题

**Ampere 的 cp.async**：每个线程负责搬运 16 字节，一个 CTA 搬一个大 tile 需要几百条指令 + 几百个线程参与。线程本身要算地址、要发射、要等待，**搬运消耗的是宝贵的计算线程**。

**TMA**：只需 **1 个线程**发射一条指令，描述”把这块数据的这块形状搬到这块 shared memory 的这个位置”，然后一个专用硬件引擎接管全部工作：地址生成、边界处理、搬运、写完成标志。

### 2. 一次 TMA 搬运的本质

TMA 指令的核心是一个 **TensorMap 描述符**（64 字节，提前创建好，放在 constant memory）：

```cuda
// 创建一个 TensorMap：描述一个 [M, K] 的 FP16 矩阵
CUtensorMap tensormap;
cuTensorMapEncodeTiled(
    &tensormap,
    CU_TENSOR_MAP_DATA_TYPE_FLOAT16,
    2,                    // 2 维
    ptrA,                 // 全局显存基址
    {M, K},               // 全局形状
    {128, 64},            // 每次搬运的 box（tile）形状
    ...
);

// kernel 内：一条指令搬走一个 tile
// tid==0 发射，整个 CTA 的 shared memory 都被填满
asm volatile(
    "cp.async.bulk.tensor.2d.shared::cluster.global.mbarrier::complete_tx::bytes"
    " [%0], [%1, {%2, %3}], [%4];"
    :: "r"(smem_addr), "l"(&tensormap), "r"(coord_x), "r"(coord_y), "r"(mbar)
);
```

这条指令的语义：

```text
"把全局显存里坐标 (x, y) 处的 128×64 FP16 tile，
 搬到我的 shared memory，
 搬完后自动向 mbarrier（完成标志）报告字节数。"
```

### 3. TMA 的三个杀手锏

**① 一条指令搬走一个 tile**：Ampere 需要 256 线程 × 多条 cp.async；Hopper 一条指令搞定。发射开销降低两个数量级。

**② 硬件做边界处理（out-of-bounds clamping）**：矩阵的边界通常不对齐（如 K=3840，box 宽 64 时最后一列只有 32 有效）。Ampere 要线程自己判断边界、写 predicated load；TMA 由硬件自动填零或钳制，kernel 代码里没有边界分支。

**③ 直接写 shared memory 的最优 layout（swizzle）**：TMA 可以把数据以硬件乱序但 swizzle 优化的方式写入 shared memory，恰好匹配 wgmma 读 shared memory 的 bank-conflict-free 要求。数据落地即最优布局，省掉 Ampere 里那一步显式 layout transform。

### 4. mbarrier：搬运和计算的同步语言

TMA 完成怎么通知计算线程？通过 **mbarrier**（shared memory 里的硬件同步原语）：

```cuda
// 生产者（1 号线程）：发射 TMA，说"搬完后给这个 barrier 记一笔账"
mbarrier.arrive.expect_tx(bar, bytes);
tma.load_async(..., bar);   // TMA 完成后自动 complete_tx

// 消费者（所有线程）：等 barrier 的账结清
mbarrier.try_wait(bar);
// 数据到齐，开始 wgmma
```

这是经典的 **producer-consumer 异步流水**：一个 warpgroup（甚至一个线程）专职发射 TMA，另一个 warpgroup 专职算 wgmma，通过 mbarrier 交接，互不阻塞。

### 三、两者如何配合：完整的 Hopper GEMM kernel 长什么样

把上面的零件组装起来，一个 H100 上的高性能 GEMM kernel 的骨架：

```cuda
// 简化版：单 CTA 视角
__shared__ float smem_A[3][128][64];   // 3-stage 流水
__shared__ float smem_B[3][256][64];
__shared__ uint64_t mbar[3];

// ===== 角色划分 =====
if (warp_idx == 0) {
    // 生产者线程：只发 TMA，一个线程干完全 CTA 的搬运
    for (int k = 0; k < K/64; k++) {
        mbarrier.expect_tx(mbar[k%3], tile_bytes);
        tma.load_async(smem_A[k%3], A + k*64, mbar[k%3]);
        tma.load_async(smem_B[k%3], B + k*64, mbar[k%3]);
    }
} else {
    // 消费者：两个 warpgroup 各算 D 的一半
    for (int k = 0; k < K/64; k++) {
        mbarrier.wait(mbar[k%3]);                    // 等数据
        wgmma.mma_async(D, smem_A[k%3], smem_B[k%3]); // 连发
        wgmma.mma_async(D, smem_A[k%3]+8, smem_B[k%3]+8);
        wgmma.commit();
        wgmma.wait_group(0);
        // 通知生产者：这个 buffer 用完了，可以覆盖
        mbarrier.arrive(empty_bar[k%3]);
    }
}
```

流水线的实际效果：

```text
时间轴 →

warp0:  [发TMA k0][发TMA k1][发TMA k2][发TMA k3] ...   ← 几乎不耗时
warp1-8:      [等k0][wgmma×N][等k1][wgmma×N][等k2][wgmma×N] ...
                    ↑ 数据早已搬好，wgmma 连续发射
```

Tensor Core 的利用率逼近峰值——这就是 H100 FP16 标称 989 TFLOPS 在 GEMM 上能跑到 90%+ 的原因。

### 四、TensorRT / TRT-LLM 里的实际体现

这些机制不是你要手写的东西，而是 TensorRT builder 在 H100 上选 kernel 时的”底层弹药”：

- TensorRT 的 Hopper GEMM kernel 就是基于 **CUTLASS 3.x SM90 kernel**（上面这套结构的工业级实现，加了 multistage 流水、cluster 级协同、FP8 wgmma 等）
- Builder 的 timing 阶段在 A100 和 H100 上会选出完全不同的 kernel——这就是”engine 绑定 GPU 架构”的根本原因
- TRT-LLM 的 Attention kernel（Context FMHA）同样用 TMA 搬 Q/K/V、用 wgmma 算分块 attention，并利用 **thread block cluster + DSMEM** 在 2 个 SM 间共享 KV tile，减少对 HBM 的重复读取

### 五、一个量化对比

以 `4096×4096×4096` 的 FP16 GEMM 为例：

| 维度 | Ampere 方案 | Hopper 方案 |
| --- | --- | --- |
| 数据搬运 | 256 线程 × cp.async 多指令 | 1 线程 × TMA 单指令 |
| 矩阵计算 | mma.sync，warp 级，寄存器喂数 | wgmma，warpgroup 级，SMEM 直读 |
| 发射开销 | 高（指令多、线程忙） | 极低（硬件单元接管） |
| 实际可达峰值 | ~80–85% | ~90–95% |
