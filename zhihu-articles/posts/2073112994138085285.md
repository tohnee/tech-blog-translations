**先说结论：** 大多数 RAG 教程止步于”切 512 字 → Embedding → 向量检索 → 拼 Prompt”，而腾讯开源的 WeKnora 向我们展示了企业级 RAG 的真实复杂度——分块要做策略链和校验降级，检索要做并行召回和补偿兜底，召回之后还有近十个文件专门做去重、合并、父块回填。这篇文章带你逐段读它的核心源码（基于 v0.7.2，Go 实现），看看功夫到底下在哪。

### 一、分块：不是固定切 512，而是”策略链 + 校验降级”

教科书式的分块是固定窗口切分，WeKnora 的 chunker（ `internal/infrastructure/chunker/` ）则实现了一套 **分层自适应分块策略** ：先用文档画像器（profiler）扫描全文结构，自动选择 `heading → heuristic → legacy` 的策略链，每一层产出后经过校验器验收，不合格自动降级到下一层，永远有 legacy 兜底。

策略选择的依据是一份文档”体检报告”（ `profiler.go` ）：

```text
// SelectStrategy returns the ordered tier chain to attempt for this document.
// The first tier is the primary choice; subsequent tiers are fallbacks if
// validation rejects the previous output.
func SelectStrategy(p *DocProfile) []StrategyTier {
	if p == nil {
		return []StrategyTier{TierLegacy}
	}
	var chain []StrategyTier

	// Tier 1 candidate: Markdown heading-aware
	if p.MdHeadingTotal >= 3 && p.HeadingDensity() > 0.005 && p.DominantHeadingLevel() > 0 {
		chain = append(chain, TierHeading)
	}

	// Tier 2 candidate: heuristic boundary detection
	if p.HeuristicMarkerTotal() >= 5 || p.FormFeedCount > 0 ||
		p.GermanChapterCount+p.EnglishChapterCount+p.ChineseChapterCount > 0 {
		chain = append(chain, TierHeuristic)
	}

	// Legacy is the ultimate fallback: always returns chunks even when
	// validation fails, so callers never get an empty result.
	chain = append(chain, TierLegacy)
	return chain
}
```

关键设计在于 **每一层的产出都要过质检** （ `strategy.go` + `validator.go` ）。校验器只拒绝”明显坏掉”的结果——比如大文档只切出一个块、碎块过多、块大小严重超标——但容忍合理的变化，避免在不同策略之间震荡：

```text
// strategy.go：逐层尝试，ValidateChunks 不通过就降级
for i, tier := range chain {
	out := runTier(tier, text, cfg, profile)
	if v := ValidateChunks(out, totalChars, cfg.ChunkSize); v.OK {
		return out
	} else {
		logger.Debugf(context.Background(), "chunker: tier %s rejected: %s", tier, v.Reason)
	}
	...
}
// validator.go 中的几条典型拒收规则
// 大文档只产出一个块 → 说明策略根本没切动
if len(chunks) == 1 && totalChars > 2*chunkSize {
	return ValidationResult{Reason: "single chunk for large document"}
}
// 超过 1/4 的块是碎渣（<50 字符，尾块除外）
if tinyCount > len(chunks)/4 && tinyCount > 2 {
	return ValidationResult{Reason: "too many tiny chunks"}
}
// 所有块都不到目标大小的 1/4 → 切得太碎
if maxLen < chunkSize/4 && totalChars > chunkSize {
	return ValidationResult{Reason: "all chunks far below target size"}
}
```

这套”画像 → 选链 → 校验 → 降级”的机制，本质上把分块从”一刀切参数”变成了”带反馈的决策过程”，对格式混杂的企业文档（PDF 转出来的 Markdown、扫描件 OCR 文本）尤其有价值。

### 二、流水线：把 RAG 拆成事件驱动的插件链

WeKnora 的问答流水线（ `internal/application/service/chat_pipeline/` ）被建模为 **事件类型 + 插件注册** ，完整事件序列是：

```text
load_history → memory_recall → query_understand → chunk_search(+parallel)
→ entity_search → chunk_rerank → web_fetch → chunk_merge
→ data_analysis → into_chat_message → chat_completion(_stream) → filter_top_k
```

每个环节都是一个实现 `Plugin` 接口的插件，挂在 `EventManager` 上。插件之间用 **洋葱模型** （类似 Koa 中间件）串联， `buildHandler` 把同一事件的多个插件包成嵌套调用链：

```text
// Plugin defines the interface for chat pipeline plugins
type Plugin interface {
	OnEvent(
		ctx context.Context,
		eventType types.EventType,
		chatManage *types.ChatManage,
		next func() *PluginError,
	) *PluginError
	ActivationEvents() []types.EventType
}

// buildHandler constructs a handler chain for the given plugins
func (e *EventManager) buildHandler(plugins []Plugin) func(...) *PluginError {
	next := func(context.Context, types.EventType, *types.ChatManage) *PluginError { return nil }
	for i := len(plugins) - 1; i >= 0; i-- {
		current := plugins[i]
		prevNext := next
		next = func(ctx context.Context, eventType types.EventType, chatManage *types.ChatManage) *PluginError {
			return current.OnEvent(ctx, eventType, chatManage, func() *PluginError {
				return prevNext(ctx, eventType, chatManage)
			})
		}
	}
	return next
}
```

好处很直接：每个环节（改写、检索、重排、合并、生成）都可以独立插拔、独立观测（全链路接了 Langfuse），错误也按环节结构化（ `ErrSearchNothing` 、 `ErrRerank` 等预定义 PluginError），排查 badcase 时能精确定位到流水线哪一环出了问题。

### 三、索引构建：那些 Demo 里永远不会写的工程细节

向量索引构建在 `keywords_vector_hybrid_indexer.go` ，三个细节值得单独说。

**1. 入库前的”消毒”（sanitize）。** base64 内嵌图片先用正则替换成 `[image]` 占位（避免一张图撑爆 Embedding 输入）；超过 20000 字符的输入主动截断，避免被 Embedding API 静默截断：

```text
const safetyMaxChars = 20000

func sanitizeForEmbedding(ctx context.Context, content string) string {
	sanitized := content
	// 无 base64 时跳过正则，保持常见路径的开销最低
	if strings.Contains(content, "base64,") {
		for _, pattern := range embeddingImagePayloadPatterns {
			sanitized = pattern.ReplaceAllString(sanitized, "[image]")
		}
	}
	if utf8.RuneCountInString(sanitized) <= safetyMaxChars {
		return sanitized
	}
	runes := []rune(sanitized)
	logger.Warnf(ctx, "embedding input truncated: %d runes -> %d", len(runes), safetyMaxChars)
	return string(runes[:safetyMaxChars])
}
```

**2. 批量 Embedding 的指数退避重试** ，5 次、200ms 起步翻倍：

```text
// batchEmbedWithBackoff calls BatchEmbedWithPool with exponential backoff on
// transient failures (200 / 400 / 800 / 1600 / 3200 ms).
func batchEmbedWithBackoff(ctx context.Context, embedder embedding.Embedder, contentList []string) ([][]float32, error) {
	delay := embedRetryBaseDelay
	for attempt := 0; attempt < embedRetryAttempts; attempt++ {
		embeddings, err = embedder.BatchEmbedWithPool(ctx, embedder, contentList)
		if err == nil {
			return embeddings, nil
		}
		if attempt+1 < embedRetryAttempts {
			select {
			case <-time.After(delay):
			case <-ctx.Done():
				return nil, ctx.Err()
			}
			delay *= 2
		}
	}
	return embeddings, err
}
```

**3. 批量写库限流** ：40 条一批、信号量限制最多 5 路并发，用 `errgroup` 收敛错误：

```text
batchSize := 40
chunks := utils.ChunkSlice(indexInfoList, batchSize)
const maxConcurrency = 5
...
g, ctx := errgroup.WithContext(ctx)
sem := make(chan struct{}, maxConcurrency)
for i, indexChunk := range chunks {
	g.Go(func() error {
		select {
		case sem <- struct{}{}:
			defer func() { <-sem }()
		case <-ctx.Done():
			return ctx.Err()
		}
		...
		return v.indexRepository.BatchSave(ctx, indexChunk, params)
	})
}
```

这些代码不性感，但正是”能跑”和”能扛住企业文档批量导入”之间的差别。

### 四、检索：并行召回 + 召回不足自动补偿

![](https://pic1.zhimg.com/v2-8249e1a5f1b0ece3d6faa7c192931914_r.jpg)

`search.go` 中的 `PluginSearch` 有两个值得注意的设计。

**知识库检索和联网检索并行执行** ，用 WaitGroup + 互斥锁汇总：

```text
wg.Add(2)
// Goroutine 1: Knowledge base search using SearchTargets
go func() {
	defer wg.Done()
	kbResults, err := p.searchByTargets(ctx, chatManage)
	...
}()
// Goroutine 2: Web search (if enabled)
go func() {
	defer wg.Done()
	webResults := p.searchWebIfEnabled(ctx, chatManage)
	...
}()
wg.Wait()
```

**召回不足时自动触发关键词导向的二次召回** （召回补偿）：

```text
// If recall is low, attempt query expansion with keyword-focused search
if chatManage.EnableQueryExpansion && len(chatManage.SearchResult) < max(1, chatManage.EmbeddingTopK) {
	expResults := p.runQueryExpansion(ctx, chatManage)
	if len(expResults) > 0 {
		chatManage.SearchResult = append(chatManage.SearchResult, expResults...)
	}
}
```

另外，多知识库检索时还会 **按 Embedding 模型分组** ——同一个物理模型（名称 + endpoint）服务的多个知识库合并成一次检索调用，query embedding 只算一次；Embedding 失败时还能降级为纯关键词检索而不是直接报错。这些都是在”多知识库、多租户”场景下才会逼出来的优化。

### 五、召回后处理：被严重低估的”第二战场”

WeKnora 里 `merge*.go` 有将近十个文件，专门处理召回结果的清洗。 `merge.go` 头部注释把整条 merge 流水线写得明明白白：

```text
// The merge pipeline is:
//  1. Select input (rerank or search fallback)
//  2. Deduplicate by ID and content signature
//  3. Inject relevant history references
//  4. Resolve parent chunks (child → parent content)
//  5. Group by knowledge source + chunk type, merge sequential current bodies
//  6. Populate FAQ answers
//  7. Expand short contexts with neighboring chunks
//     7.5. Re-merge sequential or contained bodies introduced by expansion
//  8. Final deduplication (ID + signature + partial content overlap)
```

其中”部分重叠去除”处理的是跨知识库的近重复块：子串包含直接删短块，词元重叠系数 ≥ 0.85 也视为冗余，同分时保留内容更长的（ `removePartialOverlaps` ）。

重排阶段除了调多家 Rerank 模型，还有两个精巧设计。一是 **复合打分** ——不完全信任 Rerank 模型分数，融合原始召回分并对联网结果降权：

```text
func compositeScore(sr *types.SearchResult, modelScore, baseScore float64) float64 {
	sourceWeight := 1.0
	switch strings.ToLower(sr.KnowledgeSource) {
	case "web_search":
		sourceWeight = 0.95
	default:
		sourceWeight = 1.0
	}
	composite := 0.6*modelScore + 0.3*baseScore + 0.1*sourceWeight
	...
}
```

二是可选的 **MMR（最大边际相关性）多样性筛选** ，用 Jaccard 相似度惩罚与已选结果重复的候选，避免 TopK 被同一内容刷屏：

```text
mmr := lambda*relevance - (1.0-lambda)*redundancy
if mmr > bestScore {
	bestScore = mmr
	bestIdx = i
}
```

### 六、存储层：10 种检索后端可插拔

最后值得一提的架构决策：检索存储被抽象成统一的 `RetrieveEngineRepository` 接口（ `KeywordsRetrieve` / `VectorRetrieve` ），底下有 PostgreSQL(pgvector)、Milvus、Qdrant、Weaviate、Elasticsearch v7/v8、OpenSearch、Doris、SQLite、腾讯云 VectorDB 共 10 种实现，外加 Neo4j 承载 GraphRAG 图谱检索。小团队用 pgvector 起步，量大了换 Milvus，业务代码零改动。

### 写在最后

通读 WeKnora 源码最大的感受是： **RAG 的效果差距，80% 不在模型，在这些”脏活累活”里** ——分块的质量反馈、索引的健壮性、召回的补偿兜底、结果的去重合并。如果你正在自研企业知识库问答，它的 chunker 策略链和 chat_pipeline 插件架构，是我认为最值得”抄作业”的两块。
