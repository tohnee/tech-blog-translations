## 1. 梯度累积

[12. Gradient Accumulation | 梯度累积 | 大模型算法实战教程](https://datawhalechina.github.io/llm-algo-leetcode/02_PyTorch_Algorithms/12_Gradient_Accumulation.html)

**1. 它解决什么问题？**

**显存放不下一个大 batch，就分多次计算小 batch，累积梯度后只更新一次参数。** 梯度累积改变的是“一次更新如何分批完成”，而不是每个小批次都更新参数。

例如，希望每次用 **32 条样本**更新参数，但显存一次只能处理 **8 条**：

```text
第 1 批：8 条 → 前向、反向 → 保留梯度
第 2 批：8 条 → 前向、反向 → 累加梯度
第 3 批：8 条 → 前向、反向 → 累加梯度
第 4 批：8 条 → 前向、反向 → 累加梯度
                           ↓
                     只更新一次参数
```

因此，单卡情况下：

$$ \boxed{\text{有效 batch size}=\text{micro-batch size}\times\text{累积次数}} $$

这里的 **micro-batch** 是一次前向、反向实际处理的小批次；**有效 batch** 是一次参数更新使用的样本总量。

**2. 最关键的机制：`backward()` 不等于更新参数**

PyTorch 默认会把新计算的梯度**累加到参数的 `.grad` 中，而不是覆盖它**。梯度累积正是利用这个机制。

| 操作 | 作用 | 梯度累积时的调用时机 |
| --- | --- | --- |
| optimizer.zero_grad() | 清除旧梯度 | 开始一轮累积前 |
| loss.backward() | 计算梯度并累加 | 每个 micro-batch 都调用 |
| optimizer.step() | 根据梯度更新参数 | 整轮累积完成后调用一次 |

**累积期间既不能反复清梯度，也不能提前更新参数。**

**3. 为什么通常需要把 loss 除以累积次数？**

假设分成 $K$ 个**等大的小批次**，每个小批次的损失 $L_k$ 已经取平均，那么完整 batch 的平均损失为：

$$ L=\frac{L_1+L_2+\cdots+L_K}{K} $$

利用求导的线性性质：

$$ \nabla L=\sum_{k=1}^{K}\nabla\left(\frac{L_k}{K}\right) $$

所以每个小批次应执行：

```python
(loss / accum_steps).backward()
```

**不除以 $K$，累积得到的是梯度之和，而不是平均梯度。** 上述简单除法要求各小批次在损失平均中的权重相同。

**4. 最小实现：分批反向，一次更新**

下面完成**一次逻辑 batch 的参数更新**。示例采用均方误差损失，要求 batch 能等分，且 `x`、`y` 与模型位于同一设备。

```python
import torch.nn.functional as F

def train_one_update(model, optimizer, x, y, accum_steps: int = 4):
    n = x.size(0)
    if not isinstance(accum_steps, int) or accum_steps <= 0:
        raise ValueError("accum_steps 必须是正整数")
    if n == 0 or n != y.size(0) or n % accum_steps != 0:
        raise ValueError("x、y 的 batch 大小须一致、非空且能等分")

    model.train()
    optimizer.zero_grad(set_to_none=True)  # 累积前清空旧梯度
    mean_loss = 0.0

    for xb, yb in zip(x.chunk(accum_steps), y.chunk(accum_steps)):
        loss = F.mse_loss(model(xb), yb, reduction="mean")
        (loss / accum_steps).backward()    # 只累积，不更新
        mean_loss += loss.detach().item() / accum_steps

    optimizer.step()                      # 全部累积后更新一次
    return mean_loss
```

注意缩进：**`backward()` 在循环内，`step()` 在循环外。** 返回的 `mean_loss` 是这一整个逻辑 batch 的平均损失，可用于日志记录。

**5. 必须记住的边界与易错点**

显存主要省在“激活”，不是模型本身

分批前向、反向降低的是**单次计算需要保存的中间激活峰值**。模型参数、梯度缓冲区和优化器状态并不会因此按累积次数缩小。

因此，**累积 4 次，不代表总显存变成原来的 $1/4$**。

变长文本不能机械地“每批 loss 除以 K”

当各批次参与计算的有效 token 数不同时，“各批次平均 loss 再平均”不等于“所有 token 的平均 loss”。正确目标应是：

$$ \boxed{ L=\frac{\text{所有微批次中有效 token 的损失总和}} {\text{所有微批次中的有效 token 总数}} } $$

尾部不足一个完整累积窗口时，也要按实际样本数或有效 token 数处理，不能照搬完整窗口的除数。

更新节奏和验证方法要对齐

按优化器更新步数设计的学习率调度器，应跟随 `optimizer.step()`，而不是每次 `backward()` 都推进。

验证实现时，应从**相同初始模型、相同优化器状态和同一批数据**出发，对比“大 batch 一次更新”与“梯度累积一次更新”后的参数。随机层或其他受分批影响的计算可能破坏严格等价，因此不能认为所有模型都会得到完全相同的结果。

> 核心理解：计算梯度，不等于更新参数，梯度可以分多次计算，参数可以等最后再更新<br>梯度累积主要缓解激活显存压力

## 2. 激活检查点

[19. Activation Checkpointing and Activation Offload | 激活检查点 | 大模型算法实战教程](https://datawhalechina.github.io/llm-algo-leetcode/02_PyTorch_Algorithms/19_Activation_Checkpointing_and_Activation_Offload.html)

**1. 它们解决什么问题？**

**训练时，反向传播需要使用前向计算的部分中间结果。这些中间结果通常称为激活，占用显存。** 这里的“激活”不只是 ReLU 等激活函数的输出，也包括其他需要为反向保存的中间张量。

例如：

$$ h=Wx,\qquad \frac{\partial L}{\partial W} =\frac{\partial L}{\partial h}x^\top $$

计算权重梯度需要用到前向输入 $x$。因此，前向结束后，不能把所有中间结果都直接丢掉。

解决激活显存压力，有三种思路：

| 方法 | 如何处理反向需要的激活？ | 主要代价 |
| --- | --- | --- |
| 普通训练 | 保留在 GPU，反向直接使用 | 占用显存 |
| Checkpoint：激活检查点 | 少保存，反向时重新计算 | 增加计算量 |
| Offload：激活卸载 | 暂存到 CPU 内存，需要时搬回 | 增加数据传输与同步 |

**2. Checkpoint 的核心：少存中间结果，需要时重算**

**前向时，保留区段输入及必要状态，减少内部激活的保存；反向时，重新执行所需的前向计算，恢复激活，再计算梯度。** 它不是“完全不保存激活”，也不是“跳过反向传播”。

可以把它理解为：**只记下计算的起点，不长期保存每一步的草稿；以后需要草稿时，再从起点算一遍。**

最重要的代码

假设 `blocks` 是按顺序执行的模型模块，`x` 是输入：

```python
from torch.utils.checkpoint import checkpoint

for block in blocks:
    # 普通写法：x = block(x)
    x = checkpoint(block, x, use_reentrant=False)
```

后面仍然正常计算 loss、调用 `backward()` 和更新参数。`checkpoint` 会处理反向时的重计算；PyTorch 官方推荐显式使用 `use_reentrant=False`。注意传入的是**模块 `block` 和输入 `x`**，不是提前计算好的 `block(x)`。

**3. 检查点粒度：一次包住多少个 Block？**

**逐 Block 检查点**：每个 Block 单独包一层 `checkpoint`。

**分段检查点**：把连续几个 Block 合成一个区段，再对整个区段使用 `checkpoint`。

例如，5 个 Block，每段放 2 个，可以划分为：

```python
[(0, 2), (2, 4), (4, 5)]  # 左闭右开，最后一段可以不足 2 个
```

**区段变大，通常意味着保存的边界更少，但单次重算范围更大。不能简单认为“越细越好”或“越粗越省”。** 同时：在循环中定义区段函数时，应绑定当前区段，例如 `def segment_forward(x, segment=segment)`，避免反向时错误地引用最后一个区段。

**4. Offload 的核心：不重算，而是换地方存**

**把暂时不用、但反向还需要的张量保存到 CPU 内存，反向需要时再搬回原设备。** 它消耗的是主机内存和 CPU–GPU 传输资源，而不是通过重算恢复激活。

PyTorch 提供了一个直接的用法。假设模型、数据、优化器和损失函数已经准备好：

```python
import torch

optimizer.zero_grad(set_to_none=True)

with torch.autograd.graph.save_on_cpu(pin_memory=True):
    loss = criterion(model(x), y)

loss.backward()
optimizer.step()
```

这个上下文管理器处理的是**其中运算为反向保存的张量**，不是把整个模型搬到 CPU 上计算。它也不保证所有 GPU 张量都会立即释放。

**5. 核心**

① 省的是激活显存，不是所有显存

Checkpoint 不会自动缩小模型参数、梯度或优化器状态。因此，**激活减少一半，不等于总显存减少一半**；当激活本来占比不高时，收益可能有限。

② 重算必须与原来的计算保持一致

检查点区段不要依赖前后会变化的全局变量，也要避免不受控的状态修改。对于 Dropout 等随机操作，PyTorch 默认会保存、恢复相关随机数状态；随意关闭这一机制，可能导致重算与原前向不一致。

③ 不能只看“是否省显存”

先比较普通版本与优化版本的**输出、输入梯度和参数梯度**，确认结果一致到允许误差内；再在相同模型、数据规模和精度设置下，比较**峰值显存、每步耗时和吞吐量**。Checkpoint 的重算和 Offload 的搬运都可能拖慢训练，收益必须实测。

## 3. 激活卸载

[42. Activation Offload | 激活卸载 | 大模型算法实战教程](https://datawhalechina.github.io/llm-algo-leetcode/02_PyTorch_Algorithms/42_Activation_Offload.html)

**这一节的重点是：搬哪些激活、能省多少显存、搬运需要多久。原文代码是“预算模拟”，不是真实的 CPU↔GPU 搬运实现。**

**1. 核心思想：暂时不用，就换个地方存**

训练时，一些中间张量需要保留到反向传播。**激活卸载把这些张量暂存到 CPU 内存，反向需要时再搬回 GPU，从而减少它们在 GPU 上的驻留。**

与上一节的 Checkpoint 对比：

| 方法 | 反向需要的激活从哪里来？ | 主要代价 |
| --- | --- | --- |
| Checkpoint：检查点 | 重新计算得到 | 额外计算 |
| Offload：卸载 | 从 CPU 内存搬回来 | 额外传输、同步和主机内存 |

**检查点是“少存、重算”，卸载是“换地方存、再取回”。**

**2. 第一笔账：搬完以后，显存够不够？**

设总激活量为 $A$，GPU 给激活预留的预算为 $B$，实际搬出的量为 $O$。

理论上，至少需要释放：

$$ \boxed{O_{\min}=\max(A-B,\,0)} $$

搬出后，GPU 上剩余的激活量为：

$$ K=A-O $$

**只有 $K\le B$，这份激活驻留计划才满足预算。**这里的 $B$ 是激活预算，不是显卡的全部显存；原文中的 `feasible` 表示这项预算检查通过，并不保证整个训练过程不会显存不足。

优先搬哪些？

原文采用一个简单策略：**从允许卸载的激活中，优先搬“距离下一次使用更远”的块，直到剩余量满足预算。**

`offloadable` 表示能否搬运；`reuse_delay_layers` 越大，表示预计越晚才会再次使用。它只是教学中的冷热近似，不是真实调度器的完整规则。

**3. 第二笔账：搬出去、搬回来，需要多久？**

基本公式是：

$$ \boxed{\text{传输时间}=\frac{\text{数据量}}{\text{有效带宽}}} $$

当数据量 $O$ 用 **byte**、带宽 $bw$ 用 **GiB/s** 表示时：

$$ t_{\text{单程}}=\frac{O}{bw\times2^{30}}\times1000 \quad(\text{ms}) $$

假设搬出、搬回的数据量相同，两向带宽也相同，则：

$$ \boxed{t_{\text{往返}}=2t_{\text{单程}}} $$

示例：

总激活 **736 MiB**，预算 **384 MiB**，示例计划搬出 **352 MiB**。假设有效带宽为 **8 GiB/s**：

$$ t_{\text{单程}} =\frac{352}{8\times1024}\times1000 \approx42.97\text{ ms} $$

$$ t_{\text{往返}}\approx85.94\text{ ms} $$

**原文文字示例漏写了 MiB→GiB 的换算；正确结果约为单程 42.97 ms、往返 85.94 ms，与其测试代码一致。**

另外，**传输总时间不等于训练步增加的时间**：部分传输可能与计算重叠，但同步和调度也会引入等待。不能直接把上述往返时间当成实际训练减速量。

**4. 怎样判断“值不值得卸载”？**

先判断能否满足预算，再比较显存收益与时间代价。一个直观指标是：

$$ \boxed{ \text{收益效率} =\frac{\text{节省的显存}}{\text{额外耗时}} } $$

**注意原文的比较函数用的是 Offload 的单程理论时间，因此它只是教学评分，不能直接证明 Offload 比 Checkpoint 更快。**工程比较应使用相同工作负载下的实际峰值显存、每步耗时和吞吐量。

不能预设“卸载一定更好”：Checkpoint 付出重算成本，Offload 付出搬运成本，哪种更合适取决于实际计算与传输开销。

**5. 真实 PyTorch 卸载：记住这个接口**

原文只模拟预算；真正接入训练时，可以使用 `save_on_cpu`。下面假设模型、数据和优化器已经准备好，模型与数据位于 GPU：

```python
import torch

optimizer.zero_grad(set_to_none=True)

with torch.autograd.graph.save_on_cpu(pin_memory=True):
    loss = criterion(model(x), y)

loss.backward()
optimizer.step()
```

**它改变的是上下文内部运算“为反向保存张量”的方式，不是把整个模型搬到 CPU 计算。**也可以只对部分模块使用，以控制卸载范围。

`pin_memory=True` 使用锁页主机内存，但**不代表传输自动与计算完全重叠**；有效重叠还需要合适的 CUDA stream、硬件支持和依赖安排。

> **先算能否放下，再算往返代价；检查点靠重算，卸载靠搬运。**

## 4. 检查点与卸载

**本节的重点是把前面学过的技术串起来：先确定显存瓶颈，再选择策略，最后验证显存收益是否值得付出的性能代价。**

**1. 三种方法，分别改变什么？**

| 方法 | 核心做法 | 主要代价 |
| --- | --- | --- |
| 缩小 micro-batch＋梯度累积 | 一次少处理一些数据，多次反向后再更新参数 | 更多微批次，吞吐可能下降。 |
| Checkpointing：激活检查点 | 少保存中间激活，反向需要时重新计算 | 增加计算量。 |
| Activation Offload：激活卸载 | 激活暂存到 CPU，需要时搬回 GPU | 增加传输、同步和 CPU 内存占用。 |

可以分别记成：**少算一批、少存一些、换地方存。**

这里优化的是**激活显存**，不会自动减少参数、梯度和优化器状态。因此，不能把激活节省比例当成总显存节省比例。

**2. 遇到显存不足，按什么顺序考虑？**

先确认主要压力确实来自激活，再按下面的顺序开展实验：

**单次输入太大 → 调整 micro-batch 和累积次数 → 测试 Checkpoint → 测试 Offload → 必要时组合使用。**

计算余量较充足时，可以优先测试重算；CPU 内存和传输带宽充足时，可以考虑卸载。**这是排查顺序，不是固定的性能排名；组合方案也不一定最好。**

**3. 每种方法，先检查什么？**

梯度累积：是否仍然完成相同的参数更新？

单卡、完整累积窗口下：

$$ \boxed{\text{有效 batch}=\text{micro-batch}\times\text{累积次数}} $$

比较方案时，要保持每次更新使用的数据量一致，并检查 loss 归一化、梯度和更新次数。**有效 batch 相同，不代表一次前向处理的数据量相同。**变长文本还应按整个累积窗口的有效 token 数归一化。

Checkpoint：重算是否与原前向一致？

检查输出和梯度是否与基线接近，尤其注意区段边界、随机操作和状态变化。比如，重算依赖的全局变量发生变化，就可能产生错误梯度。PyTorch 推荐显式使用 `use_reentrant=False`。

Offload：搬回来的张量是否正确？

卸载不能破坏反向需要的数值。其基本要求是：

$$ \boxed{\operatorname{unpack}(\operatorname{pack}(x))\ \text{应恢复与 }x\text{相同的数值}} $$

也就是：**保存到 CPU，再恢复到原设备后，反向计算仍应得到正确结果。**这不是把整个模型改成在 CPU 上训练。

**4. 实验怎么比，才有意义？**

**先保留基线，再一次只改变一个策略。**固定模型、精度、序列长度、数据和有效 batch，并统一预热、测量次数与随机种子。重点记录：

**峰值显存、每步耗时、吞吐量、训练质量、是否发生显存不足（OOM）。**

这里建议把“每步耗时”统一为**完成一次参数更新的时间**。例如，累积 4 次的方案应统计这 4 次前向、反向及最后更新的总时间，不能只拿其中一个微批次与基线比较。

实际测量时还要分清两个细节：**`max_memory_allocated()` 观察张量占用峰值，`max_memory_reserved()` 观察缓存分配器管理的显存峰值；二者不是同一个指标。**GPU 运算是异步的，计时需要正确同步，或使用 CUDA Event。

**5. 最重要的判断原则**

**理论卸载量不等于真实峰值下降量，理论传输时间也不等于训练步增加的时间。**CPU 上的练习可以验证梯度和预算逻辑，但真实显存、重算成本、搬运等待及吞吐必须在 GPU 上测量。

最终判断不是“谁最省显存”，而是：

$$ \boxed{ \text{显存不超预算} \quad+\quad \text{吞吐达到要求} \quad+\quad \text{训练质量达标} } $$

满足这些条件后，再选择代价合适的方案；不能因为组合策略显存最低，就直接接受它。

> **先找瓶颈，再选分批、重算或搬运；先验正确，再测显存、速度和质量。**
