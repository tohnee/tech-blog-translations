## 有grep就够了吗？RAG死了吗？

这里说的 RAG（检索增强生成），指在生成过程中从外部知识源检索相关信息，并让这些信息作为上下文或证据参与回答。检索可以是关键词、全文、向量或别的式，不一定预先切块，也不一定要用向量数据库。

给 Agent 一个目录，加上 `grep` 和读取文件的工具，似乎也能完成不少工作。编程 Agent 在仓库里找函数、读配置、改代码；研究助手翻 Markdown 笔记，搜索关键词，再写一份带出处的总结。文件就在眼前，找到什么、读过什么、改了什么，都比较容易追查。索引流水线可以暂时省掉。

这里说的“文件优先”，其实是文件、目录结构、命名规则、Git 和搜索工具共同组成的一个工作台。光把文件扔进一个目录，并不构成它。有了这套工作台，技术选型确实可以重新考虑，但仍不足以说明文件能替代所有检索和数据管理工具。 `grep` 能不能找到材料，取决于你是否已经知道该搜什么；当你只知道某件事“大概被讨论过”、却不知道它被怎么称呼时，字面匹配就可能漏掉——这正是全文检索和语义检索要补的位置。至于订单、库存这类需要精确判定和更新的数据，则属于另一类问题，后面再说。

### 文件为什么适合 Agent

代码、配置、测试和说明文档原本就在文件里。要找 `MAX_RETRY_COUNT` 的定义，或者查看某个旧 API 还在哪里被调用， `grep` 通常很直接：先找到位置，再读上下文，需要修改时打补丁、运行测试、查看 diff。没必要为了这些定位任务，把每份文件都先转成向量。

个人或小团队的研究工作也类似。资料、会议纪要、项目决策和报告草稿，经常需要人和 Agent 一起阅读、修改。目录表达范围，文件名提示主题，Markdown 方便审阅，Git 留下修改记录。文件既是材料，也是交付物。

如果资料范围可控、查询量不高，一套清楚的目录和命名规则，加上 Git 与精确搜索，就可能够用了。当然，前提是目录真的整理过；一堆随手命名、内容重复的文件，不会因为交给 Agent 就自动变成好用的知识库。

### 搜得到关键词，不代表找全了资料

查一个函数名， `grep` 很合适。换成下面的问题，事情就没那么简单了：

> 过去哪些方案讨论过高峰期服务变慢，但没有直接使用“高峰期变慢”这个说法？

相关文档可能写的是“流量突增”“线程池耗尽”或“尾延迟抖动”，但没有直接使用“高峰期变慢”的语句。Agent 可以换几个词继续搜，但字符串匹配本身并不知道这些表述之间的关系，仍可能漏掉材料。 `grep` 的效率也建立在某种程度的可检索性之上：用户或 Agent 得知道该搜什么。问题一旦变成“我不知道材料叫什么，只知道它大概讨论过某件事”，关键词搜索的优势就会下降。

字符串匹配的局限说明了：搜得到关键词，不代表找全了资料。归根结底，关键词是用户或 Agent 先想出来的；它搜不到那些自己还不知道该叫什么的东西。既然关键词有缺口，下一步自然是问其他检索方式能不能补上。

### 为什么说 grep 不够

从「模式匹配」到「全文检索」再到「语义相似度检索」，技术是沿着一条「旧的不够用」的轨迹一步步长出来的——每一代都在解决上一代留下的具体短板。

`grep` 属于第一代：模式匹配。它按你给出的字面或正则，在文本里逐行扫描、命中即返回。机制决定了效果：它没有索引、没有分词、没有排序，只知道「字符串相不相同」，不知道「意思相不相关」。当你事先知道要找一个确切的标识符（ `MAX_RETRY_COUNT` 、某函数名）时，它干净利落；可材料一旦变多、查询变多，或者你想找的是「谈过某件事但没用同一个词」的资料，它没有索引可借，只能靠你把每个想得到的说法都试一遍。

于是有了第二代：全文检索。它先把文本分词（切词、去停用词、词干化），建立倒排索引——一个「词 → 出现在哪些文档」的反向映射。倒排索引正是机制上的关键改进：查一个词不必从头扫描全文，而是直接定位到包含该词的文档，再用 BM25/TF-IDF 这类打分来排序，短语查询、字段过滤、高亮和大语料下的稳定延迟也由此成立。但它本质上仍按「词」匹配：你搜「高峰期变慢」，它不会自动知道「流量突增」「尾延迟抖动」讨论的是同一件事。词义、改写、语言这道词汇鸿沟，它跨不过去。

近几年又长出第三代：语义相似度检索。做法是用预训练编码器把文本映射成稠密向量，让含义相近的文本在向量空间里彼此靠拢，再用近似最近邻召回距离最近的内容。它不再是「字面命中」而是「语义相近」，因此能在「用词不同但话题相同」时把相关材料召回来，也顺带支持了跨语言。但新方法也有新代价：相似度是近似，给不了分毫不差的确定性——订单号、制度版本、访问权限这类必须精确的事实，它不能「确认」。

由此回头想选型，其实是在问「我的需求用到了哪一代的短板」。本地代码库和 Markdown 笔记，查询量不高、多数时候知道要找什么， `grep` 往往够用，不必急着上新一代；只有文档量变大、要给多人提供稳定的全文查询时，才值得引入倒排索引；只有反复出现「措辞不同却找不到材料」时，语义检索才值得评估。用到哪一层，取决于材料和查询量，不取决于「该不该用向量库」这类先入为主的标签。

实际使用中，把几代工具合起来往往最顺手：用关键词锁定编号、术语和版本，用语义检索补足表达差异，再回到原文核对。索引可能更新不及时，摘要可能过期，切块也可能把限制条件留在另一个片段里——检索返回的内容需要验证，不能直接当成结论。

### 订单和库存，不适合靠读文件来判断

再换一个问题：

> 找出最近一个月付款成功、交付失败，而且尚未退款的订单。

这需要明确的状态定义、时间范围和关联查询。让 Agent 扫描一批文本文件，自行推断哪些订单符合条件，既费力，也难以检查是否漏算。

如果任务是创建订单、扣减库存，还要保证失败后不会重复扣款，要求就更高了。事务、并发控制、幂等和审计，都需要业务系统提供保证。Prompt 写得再仔细，也替代不了这些机制。

判断该不该用数据库，看的是它是否需要事务、约束、并发更新、复杂查询，以及有没有一个系统为这些事实负责。文章、笔记和报告通常可以直接保存在文件中；用户权限、订单状态、支付记录和审批过程，则要交给具备这些能力的结构化系统或业务系统。用不用数据库，和文件扩展名没有关系。

对单机或低并发的本地 Agent，SQLite 可以保存结构化状态，并通过 FTS5 提供全文检索。它解决不了语义召回，也不适合所有多用户高并发场景，但可以作为从文件方案走向专业检索系统的实用中间层，不必一开始就部署独立的数据库服务。

NoSQL 同样没有因为 Agent 的出现而失去用途。文档数据库、键值存储、图数据库、时序或宽列系统，处理的数据形态和访问模式并不相同。是否采用它们，要看查询方式、吞吐和一致性要求。

文件里可以保存订单或权限的快照，方便阅读。但涉及判定和更新时，应查询权威业务系统，不能只凭快照操作。

### RAG 变了，还是没用了？

按前面的定义，切块、Embedding、向量数据库这条流水线，只是文档型 RAG 的一种常见实现，代表不了 RAG 的全部。切块丢失上下文、召回错误版本、引用与结论不对应，都可能让系统看起来完成了检索，实际却没有找到可用证据。

Agent 使用 `grep` 搜索文档，读取相关段落，再依据原文回答，仍然可以构成 RAG。它只是换了检索方式，检索增强本身没有变。数据库查询也可以成为 RAG 的检索环节，前提是查询结果被用来支持后续生成；调用支付接口扣款属于执行操作，不会因为用了工具就变成 RAG。

Agentic RAG 仍然属于 RAG。它保留了“检索外部知识来支持生成”的基本过程，只是让 Agent 参与组织检索：根据问题拆分任务、选择检索方式、改写查询、检查证据是否足够，必要时继续搜索。检索因此可以随着任务推进反复进行，不必局限于固定的一次“取回几个片段”。

例如，用户问某个项目为什么更换数据库。Agent 先搜索决策记录，再根据记录中的线索查会议纪要，发现时间不一致后继续核对版本，最后依据这些材料回答。这是 Agentic RAG，即使全程使用 `grep` 和文件读取，也不需要向量数据库。

Agent 能做的事情比 RAG 更多。它还可以调用业务 API 查询实时状态或执行操作，但这些能力不必都算作 RAG。

Agent 带来的变化，是可以根据任务选择不同的信息获取方式。代码符号可以交给 `grep` 、语言服务器或代码索引；相关资料可以用全文与向量混合检索；统计问题交给数据库查询；最新业务状态通过 API 获取。写报告时，可能需要多路检索、去重、回读原文，并保留引用。

工具怎么选可以灵活，权限和操作边界不行。身份验证、事务、审批和审计，仍应由系统强制执行，不能让 Agent 临时决定是否遵守。未授权材料也应在检索阶段就被过滤掉，而不是先交给模型，再要求它不要透露。

### 什么时候需要加组件

对个人编程或研究助手，可以先用文件系统、Git 和 `grep` 。如果材料找得到、延迟能接受、修改冲突很少，暂时没有必要部署搜索平台。

出现具体问题后再加工具，会更容易判断投入是否值得：

- 任务状态需要可靠保存，元数据筛选越来越多，可以考虑 SQLite；需要本地全文检索时，再用 FTS5。
- 用户常用与原文不同的词提问，导致相关材料反复漏掉，可以评估语义检索。
- 多人开始共享和更新状态，需要考虑关系数据库及相应的并发控制。文档内容仍可保留在文件和 Git 中。

到了部门或企业级场景，只证明 Agent 能读到文件还不够。还要确认它读到的内容是否有效、是否有权访问、引用能否追溯；多人工作是否会覆盖状态；索引更新失败怎样恢复；外部操作由谁审批。

这时通常会把职责拆开。文档系统管内容，权威事实交给业务系统和数据库，发现材料靠搜索索引，Agent 则在受控工具之上做规划和执行。

升级的依据应是实际问题：召回经常遗漏，查询延迟不稳定，并发冲突开始出现，权限规则变复杂，或者一次错误已经会造成较大的损失。文件方案轻巧，但维护一套正确的业务状态，并不会因此变简单。

### 回到最初的问题

RAG 仍然有用，向量数据库也有适合它的场景。需要放弃的是“做知识助手就先建向量库”的习惯。文件搜索可以替代某些 RAG 系统里的向量检索环节，却不等于替代 RAG；Agentic RAG 改变的是检索的组织方式。

对一个以代码和 Markdown 为主要材料的个人 Agent，文件、目录、Git 和搜索工具可能是很好的起点。对需要语义发现、多用户搜索或交易处理的系统，仅靠读文件往往不够。文件方案减少了索引基础设施，却不会消除治理成本；目录设计、命名规范、元数据、链接维护和版本清理，都需要有人负责。

选型时先看任务：要定位一段内容、发现相关资料、查询确定的事实，还是更新业务状态？分清这些要求，再决定使用 `grep` 、全文检索、向量检索、数据库或业务 API，比争论 RAG 是否已死更有帮助。
