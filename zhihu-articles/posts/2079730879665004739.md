### 写在前面

做深度学习的人，对下面这个命令应该都非常熟悉：

```bash
nvidia-smi
```

对于很多实验室来说，它可能不仅是查看 GPU 状态的工具，甚至还是整个实验室最主要的“GPU 调度系统”。

想跑实验？

先 SSH 登录服务器。

```bash
ssh user@server-a
```

然后：

```bash
nvidia-smi
```

没卡？

退出，再看看另外一台。

```bash
ssh user@server-b
nvidia-smi
```

还是没卡？

再换一台。

如果终于看到一张 GPU 只占了几 GB 显存，却不知道上面的程序是谁跑的，还可能要去群里问一句：

> “XX 服务器 2 号卡是谁在用？”

这大概是很多高校实验室里 GPU 服务器的真实使用状态。

从技术上说，我们可能已经拥有了好几台服务器、几十张 GPU、共享存储、高速局域网……

但从使用体验上说：

**这些服务器仍然只是“一台一台的服务器”。**

它们并没有真正成为一个统一的计算集群。

这就是我开发 **NebulaGrid** 最主要的原因。

---

## 一、为什么我要做 NebulaGrid？

随着深度学习实验逐渐增多，我越来越明显地感觉到：

**GPU 数量增加，并不会自动降低科研人员使用计算资源的成本。**

恰恰相反，当服务器越来越多之后，管理这些服务器本身也开始成为一项工作。

一套典型的实验流程可能是这样的：

```text
准备运行实验
    ↓
登录第一台服务器
    ↓
查看 GPU
    ↓
没有空闲资源
    ↓
登录第二台服务器
    ↓
继续查看 GPU
    ↓
找到空闲 GPU
    ↓
检查代码
    ↓
检查 Conda 环境
    ↓
检查依赖
    ↓
启动训练
    ↓
挂后台 / tmux / screen
    ↓
隔几个小时重新 SSH
    ↓
查看日志
    ↓
发现程序挂了
    ↓
重新运行……
```

这些步骤单独拿出来都不复杂。

问题在于，当每天都要重复很多次之后，它们会消耗相当多的时间。

而且随着实验室规模扩大，还会继续出现新的问题。

### 1. GPU 到底在哪里？

一台服务器还好。

五台服务器以后，就很难一眼知道整个实验室目前还有多少 GPU 可以使用。

### 2. 谁正在使用 GPU？

单纯执行 `nvidia-smi`，通常只能看到 PID、显存占用等信息。

但对于其他用户来说，更希望知道的是：

**“这是谁的任务？”**

### 3. 任务应该提交到哪里？

如果一个实验需要：

```text
2 × GPU
显存至少 20 GB
```

用户往往需要自己判断哪台服务器满足要求。

而机器数量越多，这件事越不应该交给用户手工完成。

### 4. 环境怎么管理？

科研代码的运行环境尤其复杂。

今天复现一篇 2026 年的论文，可能需要：

```text
Python 3.12
PyTorch 2.6
CUDA 12.x
```

明天复现几年前的项目，可能又变成：

```text
Python 3.8
PyTorch 1.x
较旧的 CUDA / cuDNN
```

再加上每篇论文自己的依赖，实验环境很快就会越来越多。

### 5. 代码和数据到底放在哪里？

当服务器数量越来越多以后，很容易出现：

```text
A 服务器上的代码更新了
B 服务器还是旧版本

C 服务器有数据集
D 服务器没有

某个实验结果在某台机器上
但是过了几个月已经忘记放在哪里了
```

### 6. 任务跑到哪里了？

程序启动之后，我们通常还需要关心：

```text
现在是不是还在运行？
运行在哪台机器？
用了哪几张 GPU？
日志在哪里？
什么时候启动的？
什么时候结束的？
为什么退出？
```

如果这些信息完全依赖 SSH、`ps`、`nvidia-smi` 和日志文件，那么随着任务数量增加，管理难度会越来越高。

### 所以，我希望把这些事情统一起来

最终，我给 NebulaGrid 定下来的目标其实非常简单：

> **尽可能把实验室里分散的服务器、GPU、用户、文件、环境和任务统一起来。**

让科研人员真正需要关心的事情从：

```text
我要登录哪台服务器？
哪张 GPU 是空闲的？
环境在哪？
日志在哪？
程序挂后台了吗？
```

变成：

```text
我要运行什么代码？
使用什么环境？
需要多少 GPU？
```

至于任务究竟运行在哪一台服务器、使用哪几张 GPU，则尽可能交给系统完成。

## 二、从 DDLTM 到 NebulaGrid

NebulaGrid 并不是我第一次尝试解决这个问题。

早在 **2023 年5月**，我就开发过一个名为：**DDLTM（Distributed Deep Learning Task Management）**的分布式深度学习任务管理系统。

当时的 DDLTM 使用传统的 **C/S 架构**，主要由 PyQt 客户端、Master 主节点和 GPU 计算节点组成。

![](https://pica.zhimg.com/v2-0fc34ee4e41372d68e494ef7ab6b405e_r.jpg)
*DDLTM任务管理界面*

![](https://pic4.zhimg.com/v2-b717158ece0885e452a83f72f9a24057_r.jpg)
*DDLTM节点监控界面*

![](https://pic3.zhimg.com/v2-cdf43975bf1604b5d2d1816986a3aafc_r.jpg)
*基于Grafana的所有节点可视化界面*

DDLTM 已经能够完成 GPU 状态查看、节点管理以及基本的训练任务提交和调度，并真正投入到了后续科研实验中。

但随着实际使用时间增加，我逐渐发现：

> **GPU 调度只是科研计算管理中的一部分。**

用户、文件、代码、数据、环境、任务、日志、服务器状态……

这些东西其实是相互关联的。

与此同时，C/S 架构也意味着每个用户都需要安装客户端，升级时还要考虑客户端版本同步。

最终，DDLTM迭代了两个大版本。

而在**2026年5月**，我基于DDLTM，重新设计了整个系统。

最终形成了今天的：

## **NebulaGrid**

如果简单概括两者之间的区别：

> **DDLTM 更关注“这个任务应该在哪张 GPU 上运行”。**<br> **NebulaGrid 更关注“实验室里的计算资源应该怎样被统一使用”。**

## 三、NebulaGrid 是什么？

NebulaGrid 是一个面向：

- 高校实验室；
- 科研团队；
- 中小规模 GPU 集群；
- AI / 深度学习开发环境；

设计的轻量级科研计算管理平台。

它采用 **B/S 架构**。

也就是说，普通用户不需要安装专门客户端。

打开浏览器，登录 NebulaGrid 即可。

![](https://pic2.zhimg.com/v2-fb06ab0b50f453d760635162af38d2f5_r.jpg)

在 NebulaGrid 中，用户可以通过统一 Web 页面管理：

```text
用户信息
节点
GPU
文件
Conda 环境
训练任务
运行日志
```

从而将原本分散在多个服务器中的科研计算流程统一起来。

## 四、NebulaGrid 的核心设计思路

### 1. 尽量降低使用门槛

NebulaGrid 的目标用户首先是科研人员，而不是专业运维人员。

因此，我不希望用户为了“使用 GPU”，还需要先学习一整套复杂的集群技术。

理想状态下，一名刚进入实验室的同学，只需要知道：

```text
Python
Conda
基本 Linux 命令
深度学习训练代码
```

就能够比较顺利地使用 NebulaGrid。

### 2. 尽可能兼容原来的科研习惯

很多科研平台喜欢重新设计一整套工作流。

例如要求所有项目按照统一规范组织、所有程序必须封装成容器、所有数据必须按照特定方式导入。

这些设计对于大型生产环境当然非常合理。

但科研环境具有明显不同的特点。

我们经常需要：

- 下载论文作者的 GitHub 仓库；
- 直接修改代码；
- 临时安装 Python 包；
- 进入环境调试；
- 修改超参数；
- 运行各种年代和依赖完全不同的项目；
- 保存大量中间结果；
- 手动分析 Checkpoint 和日志。

因此，NebulaGrid 尽量建立在原有科研习惯之上，而不是要求所有人重新适应一套工作方式。

## 五、为什么是 Miniconda，而不是强制 Docker？

如果按照更加标准化的云计算平台设计方式，Docker 显然是一种很自然的环境隔离方案。

Docker 有很多优势：

环境隔离更加彻底，可复现性也很好，同时拥有完善的镜像生态。

但 NebulaGrid 当前主要服务的是实验室科研环境。

科研代码本身往往非常灵活。

例如今天下载的一篇论文可能要求：

```bash
conda create -n paper_a python=3.10
```

另外一个项目则可能要求：

```bash
conda create -n paper_b python=3.8
```

用户还经常需要：

```bash
conda activate paper_a
pip install xxx
```

然后直接进入项目目录修改和调试代码。

而 Conda 本身已经是当前 Python 与深度学习科研中非常普遍的环境管理方式。

因此，NebulaGrid 当前选择：

> **以 Miniconda 为基础管理用户环境。**

而不是强制所有科研项目 Docker 化。

这样做最大的好处就是：

**用户原来的科研工作流几乎不需要改变。**

以前可能是：

```bash
conda activate myenv
python train.py
```

现在只是把这个过程交给 NebulaGrid：

```text
选择环境：myenv

运行命令：
python train.py

GPU 数量：
2

提交任务
```

其背后的 Python 环境仍然是用户熟悉的 Conda 环境。

我认为对于实验室内部系统而言，这种设计能够在**环境管理能力**和**使用门槛**之间取得一个比较合适的平衡。

## 六、NebulaGrid 目前能够做什么？

接下来正式看看 NebulaGrid 当前已经实现的主要功能。

## 1. 集群总览

用户登录 NebulaGrid 之后，首先可以从 Web 页面了解当前整个集群的大体状态。

![](https://pic1.zhimg.com/v2-e0101ee7b03125402c6b558e312b7e0a_r.jpg)
*所有用户的NebulaGrid总览界面*

用户可以在页面中查看不同服务器的运行状态，并进一步了解其 GPU 情况。

相比逐台 SSH 登录服务器，这里更重要的是提供一个：

> **“整个实验室现在是什么状态？”**

的统一视角。

用户不需要记住实验室到底有多少台服务器，也不需要关心每台机器的 IP。

打开页面，就能够开始寻找自己需要的计算资源。

## 2. 节点管理

NebulaGrid 会将加入系统的计算服务器统一作为 **Node** 管理。

![](https://pic4.zhimg.com/v2-e60f3c1e20ea09a3378da206fa4f6a1d_r.jpg)
*管理员的节点管理页面*

对于管理员而言，这里也提供了一个集中观察整个集群状态的入口。

传统方式可能需要：

```bash
ssh server-a
nvidia-smi

ssh server-b
nvidia-smi

ssh server-c
nvidia-smi
```

NebulaGrid 希望最终把它变成：

```text
打开浏览器
       ↓
进入节点页面
       ↓
查看整个集群
```

特别是对于拥有不同型号 GPU 的实验室，这种统一视图会方便很多。

## 3. GPU 状态查看

GPU 是 NebulaGrid 最核心的计算资源。

系统会将节点中的 GPU 状态呈现在 Web 页面中。

用户可以更直观地判断当前资源是否充足，而不需要在多台服务器之间反复执行：

```bash
nvidia-smi
```

当任务通过 NebulaGrid 提交之后，GPU 与任务之间也可以建立更加明确的关联。

![](https://pic1.zhimg.com/v2-a11f3f6b2573869786c649e8ac7b71f8_1440w.jpg)
*总览界面的GPU状态显示卡*

![](https://pic3.zhimg.com/v2-7b4e23128917b549cc76b8dfa2ad32da_r.jpg)
*任务的GPU占用信息*

相比只看到一个 Linux PID：

```text
PID 192837
GPU Memory 20134 MiB
```

系统更希望告诉用户：

```text
这是哪个任务
属于哪个用户
什么时候提交
当前是什么状态
```

这也是统一任务管理相比单纯服务器监控更有价值的地方。

## 4. 用户管理

当一个系统真正开始被实验室多人共同使用之后，用户管理就变得不可避免。

NebulaGrid 为不同使用者建立独立账号。

![](https://pic4.zhimg.com/v2-b48b14875494aa0151a4124e283840f3_r.jpg)
*管理员的用户管理页面*

用户登录系统以后，可以看到属于自己的文件、环境以及任务。

管理员则可以统一维护系统用户。

相比整个实验室共用一个 Linux 账号，这种方式能够让：

```text
用户
环境
文件
任务
日志
```

之间建立更加清晰的对应关系。

## 5. 文件管理

科研计算还有一个非常重要的问题：

**代码和文件。**

NebulaGrid 提供了 Web 文件管理功能。

![](https://pic4.zhimg.com/v2-0ed21f6bad34291e6512ffc5ce3f293d_r.jpg)
*文件管理页面*

用户可以直接通过浏览器完成常见的文件操作，例如：

- 浏览目录；
- 上传文件；
- 下载文件；
- 预览文件；
- 编辑文本文件。

例如对于 Python 脚本，可以直接在网页中查看甚至进行简单修改。

![](https://picx.zhimg.com/v2-c659ea05883bc4311223192fd32beff1_r.jpg)

当然，我并不打算让 NebulaGrid 重新实现一个完整 IDE。

对于大型代码修改，VS Code、PyCharm 等工具显然仍然更加适合。

这里的 Web 文件管理主要解决的是：

> **查看一下配置文件、修改一个参数、检查日志、上传一个脚本时，不必专门重新 SSH。**

## 6. 环境管理

这是 NebulaGrid 当前比较重要的模块之一。

对于深度学习科研而言，计算环境几乎和 GPU 本身一样重要。

一个完整环境可能涉及：

```text
Python
PyTorch
TensorFlow
CUDA
cuDNN
timm
transformers
numpy
opencv
……
```

不同项目之间又可能互相冲突。

因此，NebulaGrid 将 Miniconda 环境纳入统一管理。

用户只需要把自己在Linux系统中创建的 anaconda3/minicoda3 虚拟环境打包成zip文件，然后上传至系统并导入，即可在系统中使用自己的环境。

如果环境需要改动，则可以通过离线方式安装pip或conda包，不需要重新打包上传环境。

![](https://pic3.zhimg.com/v2-1c0fe3c3c72ed1bc36de766f147d4bfa_r.jpg)
*环境管理页面*

用户可以查看所有的 Conda 环境，并了解环境相关信息，同时管理自己创建的 Conda 环境。

系统还可以围绕 Python、PyTorch / TensorFlow 与 CUDA 等信息进行检查，从而帮助用户判断环境是否满足任务需求。

## 7. 任务提交

最终，所有前面的功能都会汇聚到 NebulaGrid 最核心的功能之一：

## **提交训练任务。**

![](https://pic2.zhimg.com/v2-a5789b52f7b90b9861a8b75e4a1d3285_r.jpg)
*任务管理-添加单个任务界面*

一个训练任务本质上需要描述几件事情：

```text
运行什么？
在哪里运行？
使用什么环境？
需要多少计算资源？
```

因此，在 NebulaGrid 中，一次典型任务可以表示为：

```text
项目目录：
/home/user/<user_name>/demo/

运行环境：
myenv

运行命令：
python train.py --batch-size 128 --epochs 300

GPU 需求：
2 × GPU
```

用户不需要先找到某台服务器，再登录进去启动程序。

而是：

```text
定义任务
   ↓
提交任务
   ↓
系统根据资源情况进行调度
   ↓
任务运行
```

这实际上改变的是整个 GPU 的使用模式。

传统模式更像：

> **“我要去找一张 GPU。”**

NebulaGrid 希望变成：

> **“我提交一个需要 GPU 的任务。”**

GPU 从需要用户主动寻找的“设备”，逐渐变成系统统一管理的“计算资源”。

## 8. 任务队列

如果当前 GPU 已经全部被占用，并不意味着用户一定要过几个小时之后重新登录服务器查看。

任务可以进入等待状态。

```text
Task A ── Running
Task B ── Running
Task C ── Waiting
Task D ── Waiting
```

当满足条件的计算资源释放后，再继续运行后续任务。

![](https://pic1.zhimg.com/v2-a7c686e04ae1f9fffbcf55f18c9c7c14_r.jpg)
*位于等待区的任务*

![](https://pic3.zhimg.com/v2-3a231edfe58e759a217b67f27dffd334_r.jpg)
*位于执行区的任务*

![](https://picx.zhimg.com/v2-131f0c725b646a08f665a055c8eef55b_r.jpg)
*位于历史区的任务*

这种机制对于长时间深度学习训练尤其有价值。

例如晚上睡觉之前，一次性提交若干实验：

```text
baseline

ablation_1

ablation_2

ablation_3
```

而不必守着前一个任务结束以后再手工启动下一个。

**值得注意的是，学生用户只能查看自己的任务；导师用户除了可以查看自己的任务以外，还可以查看他名下所有学生的任务；管理员可以查看所有任务。**

## 9. 批量实验

深度学习论文中大量实验本质上具有高度重复性。

例如消融实验：

```text
Model A
Model B
Model C
Model D
```

或者学习率实验：

```text
lr = 1e-3
lr = 5e-4
lr = 1e-4
lr = 5e-5
```

又或者不同随机种子：

```text
seed = 0
seed = 1
seed = 2
seed = 3
```

![](https://pic3.zhimg.com/v2-142cfe47811ce8fade149eb0e9502258_r.jpg)
*任务管理-批量添加任务界面*

如果每一个实验都需要：

```text
SSH
修改参数
启动
挂后台
等待
```

实际上会消耗大量无意义的时间。

因此，将这些实验直接提交给任务管理系统排队，是一种更加自然的使用方式。.

进一步，系统可以自动识别其中的注释符号，对于被注释的内容会自动跳过。

用户可以直接把sh文件中的一系列命令直接粘贴进执行命令框里，系统会自动解析。

![](https://pic4.zhimg.com/v2-f79a8241d90c3302453fdfd8648129b7_r.jpg)
*可以直接复制粘贴的sh文件*

## 10. 日志查看

训练任务运行以后，用户最关心的事情通常变成：

> **“现在跑到哪了？”**

NebulaGrid 会保存任务对应的运行日志。

![](https://pic2.zhimg.com/v2-51c3badebce0f98a2184a3d0c275817d_r.jpg)
*用户双击执行区或历史区的任务后，系统会弹出该任务的日志*

用户可以直接在 Web 页面查看程序输出。

例如：

```text
Epoch: [100]
Loss: 0.4321
Acc@1: 81.53
Acc@5: 95.27
```

如果任务异常退出，也可以根据日志进一步分析：

```text
CUDA out of memory
```

或者：

```text
ModuleNotFoundError
```

这样用户就不需要专门进入服务器寻找：

```bash
nohup.out
```

或者某个已经忘记保存到哪里去的日志文件。

## 七、一次完整的 NebulaGrid 使用流程

前面介绍了不少功能。

实际上对于普通用户而言，真正使用 NebulaGrid 的流程并不复杂。

假设现在有一个 PyTorch 项目：

```text
CIFAR10-Transformer
```

目录中包含：

```text
train.py
test.py
models/
dataset/
requirements.txt
```

我们希望使用两张 GPU 进行训练。

### 第一步：登录 NebulaGrid

打开实验室提供的 NebulaGrid 地址，进入登录页面。

![](https://pic1.zhimg.com/v2-75cff3eb351e3dbedae5194cbcdf9ff6_r.jpg)

输入自己的账号和密码即可进入系统。

### 第二步：准备项目文件

进入文件管理。

将自己的代码放入个人项目目录。

如果项目规模较小，可以通过 Web 页面直接上传。

如果已经通过其他方式将代码同步到共享存储，则可以直接使用对应目录。

例如：

```text
/home/user/user_name/Code/CIFAR10-Transformer
```

### 第三步：准备 Conda 环境

进入环境管理。

导入或者选择一个已经存在的环境。

例如：

```text
cifar10
```

环境中已经安装：

```text
Python 3.12
PyTorch
torchvision
timm
```

如果缺少依赖，则离线安装项目所需要的软件包。

### 第四步：确认训练命令

假设原本在终端中运行的是：

```bash
torchrun --nproc_per_node=2 train.py --batch-size 128 --epochs 300 --lr 1e-3
```

那么在 NebulaGrid 中仍然使用这条命令即可。

这也是系统比较重要的一点：

> **NebulaGrid 并不会强制改变原有训练代码的使用方式。**

原来怎样运行，现在基本仍然怎样运行。

### 第五步：提交任务

进入任务提交页面。

填写：

```text
任务名称：
CIFAR10-Transformer

工作目录：
/home/user/user_name/Code/CIFAR10-Transformer

Conda 环境：
cifar10

命令：
torchrun --nproc_per_node=2 train.py --batch-size 128 --epochs 300 --lr 1e-3

GPU 数量：
2
```

然后提交。

### 第六步：等待系统分配资源

如果当前存在满足条件的 GPU，任务即可进入运行状态。

如果当前没有合适资源，则任务进入等待状态。

对于用户来说，不需要再每隔十分钟：

```bash
nvidia-smi
```

看看别人有没有跑完。

### 第七步：查看日志

任务运行后，直接双击该任务进入日志。

即可观察：

```text
Epoch
Loss
Accuracy
Learning Rate
Training Time
```

等程序输出。

训练结束之后，任务会进入历史记录。

至此，一次完整实验结束。

## 八、对于管理员，NebulaGrid 又解决了什么？

前面更多是在用户视角介绍。

实际上对于实验室服务器管理员来说，NebulaGrid 同样能够解决不少问题。

没有统一平台的时候，服务器管理经常会变成：

```text
谁的程序把 GPU 占满了？

为什么这台机器一直高负载？

这个 PID 是谁的？

服务器为什么掉线？

谁创建了这个文件？

这个环境是谁装的？

现在还有多少 GPU 可以使用？
```

NebulaGrid 通过统一用户、节点和任务信息，能够让管理员更容易了解整个系统正在发生什么。

特别是：

```text
用户
 ↓
任务
 ↓
节点
 ↓
GPU
```

之间建立关联之后，很多原本需要逐台服务器调查的问题会简单很多。

## 九、NebulaGrid 不是什么？

介绍到这里，我觉得同样有必要说明：

**NebulaGrid 并不是想替代所有现有计算平台。**

如果一个机构拥有：

```text
几百台服务器
数千张 GPU
复杂租户体系
严格资源配额
容器编排
大规模分布式作业
云原生基础设施
```

那么显然应该优先考虑：

```text
Slurm
Kubernetes
专业 AI 计算平台
商业 GPU 云平台
```

这些成熟方案。

NebulaGrid 当前更加适合：

```text
几台到几十台 GPU 服务器
数名到数十名科研人员
以 PyTorch / TensorFlow 为主要负载
主要使用 Conda 环境
拥有局域网和共享存储
希望降低 GPU 使用和管理成本
```

这样的环境。

换句话说：

> **NebulaGrid 并不试图把一个实验室变成大型云计算中心。**

它想解决的是一个更加具体的问题：

> **如果实验室已经拥有一批 GPU 服务器，怎样才能让大家更方便地使用它们？**

---

## 十、从“服务器”到“计算资源池”

我认为 NebulaGrid 真正想改变的，其实不是某一个具体操作。

而是用户对于 GPU 服务器的认知方式。

以前，我们习惯说：

```text
我要去 01 服务器跑实验。

02 服务器还有一张卡。

03 服务器现在有人在用。

这个环境只有 04 服务器上有。
```

这时候，我们思考的是：

## **服务器**

而我希望 NebulaGrid 最终能够让用户逐渐习惯另一种方式：

```text
我要 2 张 GPU。

我要一个 Python 3.12 环境。

我要运行这个项目。

我要提交 8 个实验。
```

至于它们究竟运行在：

```text
Node 01
Node 02
Node 03
```

中的哪一个节点，对于普通用户而言不应该那么重要。

真正重要的是：

## **计算资源**

这也是 NebulaGrid 中 **Grid** 所代表的意义。

实验室里一台台原本独立存在的服务器，通过网络、共享存储以及统一管理系统连接起来。

最终成为一个整体。

回过头来看，这个系统其实已经经历了一个比较长的演变过程。

DDLTM 最开始更多是为了满足我自己的科研需求。

很多功能并不是一开始就设计好的。

而是在真正使用过程中不断遇到：

> “这里是不是可以再方便一点？”

然后一点点增加进去。

我觉得这种开发方式也很符合科研工具本身的特点。

**先解决真实问题，再逐渐完善系统。**

## 十二、目前的 NebulaGrid

截至目前，NebulaGrid 已经完成了核心系统开发，并部署到了真实 GPU 服务器环境中运行。

这些实际反馈也正在推动 NebulaGrid 从一个“能够工作的系统”，继续向一个“真正好用的科研工具”演进。

## 十四、最后

最开始做这个项目的时候，我想解决的问题其实非常朴素：

> **我不想每次跑实验之前，都先把所有服务器 SSH 一遍；**<br>**确认哪台服务器有空闲GPU；**<br>**然后检查代码版本，检查环境；**<br>**最后nohup python**xxx.py & 。

后来慢慢发现，这件事情背后其实还有很多问题。

GPU 要管理。

服务器要管理。

用户要管理。

环境要管理。

文件要管理。

任务要管理。

日志也要管理。

于是，从最初的 DDLTM，到现在的 NebulaGrid，这个系统也一点点变成了今天的样子。

NebulaGrid 当然还远没有到“最终形态”。

它也不是什么用来挑战 Slurm、Kubernetes 或商业 AI 云平台的东西。

它只是试图在一个很具体的场景中：

**让高校实验室里的 GPU 服务器更容易被使用。**

如果最后，一名用户提交深度学习实验的时候，只需要思考：

> **我要运行什么代码？** **我要使用什么环境？** **我要多少 GPU？**

而不用再花时间思考：

> **我要去哪台服务器？** **哪张卡现在没人用？** **程序怎么挂后台？** **日志放在哪里？**

那么对我来说：

## **NebulaGrid 就已经完成了它最重要的任务。**
