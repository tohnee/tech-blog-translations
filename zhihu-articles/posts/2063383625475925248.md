## L1 是什么 · 支付 ML 的 MLOps 定位

### 1.1 一句话定义

**MLOps** = 把支付 ML 的 **代码、数据、特征、模型** 变更纳入 **可审计、可回滚、可自动重训** 的工程体系——核心是 **CI（变更测试）+ CD（Canary 部署）+ CT（漂移/定时触发重训）** 闭环。

### 1.2 Google 三级成熟度（支付域映射）

![](https://pic2.zhimg.com/v2-9f9bc5c1346aa8349d6552d226872eb3_1440w.jpg)

| 级别 | 特征 | 支付域实例 |
| --- | --- | --- |
| L0 | 手动训练部署 | 风控工程师 Jupyter 导出 pkl |
| L1 | 训练 pipeline 自动化 | 日更 Airflow DAG |
| L2 | 训练+部署+监控+重训全自动 | CT 漂移触发 + Canary + 自动回滚 |

### 1.3 ML CI vs 传统 CI

| 维度 | 传统 CI | ML CI（支付） |
| --- | --- | --- |
| 测试对象 | 代码 | 代码 + 数据质量 + 模型 KS/AUC |
| 产物 | Binary | ONNX + metrics + feature_view digest |
| Gate | 单元测试 | 数据验证 + 相对 prod 基线 + smoke |

### 2.3 数据验证 Gate

```text
import great_expectations as ge

df = ge.from_pandas(training_data)
df.expect_column_values_to_not_be_null("user_id")
df.expect_column_values_to_be_between("amount", 0, 1_000_000)
df.expect_column_distinct_values_to_be_in_set("currency", ["CNY", "USD", "EUR"])
df.expect_column_mean_to_be_between("amount", 50, 500)
df.expect_table_row_count_to_be_between(100_000, 50_000_000)
df.expect_column_kl_divergence_to_be_less_than("amount", ref_dist, 0.1)

```

**CI Pipeline Data Gate Checklist**：

```text
□ 行数 ±20% 历史
□ Schema 不变（列名+类型）
□ 空值率 < 阈值/列
□ 关键特征 PSI < 0.25
□ 标签正样本率 ±30%
□ 无 env=qa 数据（支付域关键！）
□ 时间连续无缺口
□ 无重复 transaction_id

```

### 2.4 Model Registry

| 能力 | 支付域要求 |
| --- | --- |
| 不可变 artifact | ONNX digest + 签名 |
| 阶段 | None→Staging→Production→Archived |
| 元数据 | feature_view、data_snapshot、git_sha、metrics |
| Lineage | 数据→特征→训练→部署 全链 |
| 审批 | Production 需 ML Lead + 风控合规 |

### 2.5 上线 Gate（相对阈值 · 核心）

```text
自动上线条件（全部满足）:
□ KS ≥ prod_KS - 0.005
□ AUC-PR ≥ prod_AUC-PR - 0.003（不均衡场景）
□ infer_p99 < 15ms（性能）
□ 数据验证通过
□ Smoke 100 条：score ∈ [0,1]，非全零
□ feature_view 兼容（superset）
□ offline_online_skew < 1%
□ 公平性：各 MCC 群组 KS 降 < 0.01

不满足 → 阻断 + PagerDuty

```

**为何不用绝对阈值 AUC>0.75？** → QA 数据混入时 AUC=0.79 仍「通过」但劣于 prod 0.83（真实事故，见 §6）。

## L3 边界陷阱 · Staff 才知道的坑

### 3.1 绝对 vs 相对 Gate

| 类型 | 风险 | 支付实例 |
| --- | --- | --- |
| 绝对 AUC>0.75 | QA 数据污染仍过 | 漏放率 +30% |
| 相对 KS≥prod-0.005 | 安全 | 退化必阻断 |

### 3.2 Schema 演进 silent bug

- CI schema 契约：**只增列、不改类型**
- 新列默认 **不可被模型读取** 直到特征注册
- silent cast string→float → NaN 洪水

### 3.3 CT 频率与集群保护

| 模型 | 频率 | 集群保护 |
| --- | --- | --- |
| XGBoost | 日更 | 单卡 job，max 2 并发 |
| NN | 周更 | 4 卡 gang，独占 queue |
| 漂移触发 | 按需 | 冷却 24h，防打爆 |

### 3.4 标签延迟（Chargeback T+30）

```text
训练标签滞后 30 天 → 线上分布已变
对策: 短期 proxy 标签（拒付 T+7）+ 长期校准
CT 双模型: proxy 日更 + full 月更

```

### 3.5 合规与审批

- Production 推进需 **风控合规 sign-off**
- Model Card：训练数据范围、公平性指标、已知限制
- 审计日志：谁、何时、哪版本、为何推进

## L4 架构师视角 · 平台设计与 FinOps

### 4.1 日更 Pipeline 架构（Airflow）

```text
DAG fraud_daily_ct (02:00 UTC):
  T1: ge_validate_raw (10min)
  T2: feast_materialize (45min)
  T3: export_train_parquet (20min)
  T4: xgb_train_gpu (30min)
  T5: eval_vs_prod (5min)
  T6: mlflow_register (2min)
  T7: triton_canary_5pct (auto)
  T8: human_approve_or_auto (08:00 UTC)

总时长 ~2h；失败 T4 重试 2 次；T5 失败阻断 T7

```

### 4.2 监控反馈闭环

| 信号 | 阈值 | CT 动作 |
| --- | --- | --- |
| psi_daily | >0.25 | 触发重训 ticket |
| ks_weekly | 降 >0.02 | 紧急 CT |
| fraud_miss_rate | +5% | 自动回滚 + 暂停 CT |

### 4.3 权限模型（Registry）

| 角色 | Staging | Production | 回滚 |
| --- | --- | --- | --- |
| ML Engineer | 注册 | ❌ | ❌ |
| ML Lead | 注册 | 审批推进 | ✅ |
| SRE | 读 | 读 | ✅ 紧急 |
| 自动化 | 注册 | Gate 满足则 Canary | 熔断回滚 |

### 4.4 Tekton / Kubeflow 选型（支付域）

| 框架 | 优势 | 支付域用法 |
| --- | --- | --- |
| Airflow | 成熟 DAG、调度 | CT 日更主 orchestrator |
| Tekton | K8s native、GitOps | 模型 build+push 容器 |
| Kubeflow Pipelines | ML 组件丰富 | 实验 pipeline |
| Argo Workflows | 大规模并行 | 批量 backfill 评估 |

### 4.5 Model Card 必填（支付合规）

```text
model_card:
  name: fraud-detection-xgb-v12
  intended_use: 实时授权欺诈评分
  training_data:
    snapshot: iceberg.payment@20260520
    period: 2024-01 to 2026-05
    excluded: [qa_env, test_cards]
  metrics:
    ks: 0.42
    fairness_by_mcc: { retail: 0.41, travel: 0.39 }
  limitations:
    - 新商户 <7d 冷启动精度低
    - 加密货币 MCC 样本不足
  approvers: [ml_lead, risk_compliance]

```

### 4.6 漂移触发 CT 的冷却与防抖

```text
规则:
  PSI > 0.25 持续 2 天 → 触发 CT
  KS 周降 > 0.02 → 紧急 CT（绕过冷却）
  冷却: 同一模型 24h 内最多 1 次 CT
  并发: 全平台 CT job ≤ 4（防 GPU 抢光）

防抖: 单次 PSI 尖刺不触发；需 48h 滑动均值

```

## 5. 真实面试现场题（5 道带公司风格标记）

### 5.1 🟦 字节：日更自动重训+部署 Pipeline

**(1) 标准答案**

Airflow 02:00 触发：GE 验证 → Feature Store 物化 → XGBoost GPU 30min → **KS≥prod-0.005** → MLflow Staging → Triton Canary 5% → 08:00 人工或自动全量。失败 Slack + 阻断。

**(2) walk**

```text
T1-T8 见 §4.1；关键 Gate 在 T5 eval_vs_prod
Smoke: 100 条 score range + skew check

```

**(3) 量化**：日更算力 0.5 GPU-h；Pipeline SLA **2h**；失败率目标 **<2%**

**(4) 落地**：Airflow SLA alert；MLflow model stage webhook

**(5) 追问**：大促封网期 pause CT；manual override 需 ticket。

### 5.2 🟧 阿里：CT 频率怎么定？

**(1) 标准答案**

看 **标签延迟 + 漂移速度**。欺诈 velocity：**日更**；Chargeback T+30：**周更+漂移触发**；PSI 达 0.1 天数 ≈ 重训周期（风控实测 **5~7 天**）。

**(2) walk**：画 PSI 时间序列；交叉验证 KS 衰减

**(3) 量化**：日更 vs 周更：日更算力 **7×** 但 miss_rate 低 **8%**

**(4) 落地**：冷却 24h 防 CT 风暴

**(5) 追问**：proxy 标签 + full 标签双轨。

### 5.3 🟪 蚂蚁：线上模型变差排查

**(1) 标准答案**

四步：**输入 PSI** → **offline/online skew 1% 对账** → **smoke 模型加载** → **Lineage 查数据/特征/代码变更**。60% 数据、30% skew、10% 真实演化。

**(2) walk**

```text
Decision tree:
  PSI>0.25? → 数据问题 → 查上游 MCC/BIN 表
  skew>1%? → Feature Store → 查 Flink lag
  else → 模型/部署 → Triton 日志

```

**(3) 量化**：MTTR 目标 **<30min**（有 Lineage）

**(4) 落地**：runbook + 预置 dashboard

**(5) 追问**：多模型同时退化 → 共性上游（Kafka 格式变更）。

### 5.4 🔵 Google：ML 代码 CI 怎么测？

**(1) 标准答案**

三层：**单元测试**（特征函数固定输入）；**集成**（小数据集训练 tiny 模型，metrics 范围）；**回归**（prod 模型 golden set KS 不降）；**数据验证**（GE sample）。PR **<5min**。

**(2) walk**

```text
pytest tests/features/  (30s)
pytest tests/train_smoke/ (3min, 1e4 rows)
ge checkpoint on sample (1min)

```

**(3) 量化**：CI **<5min**；nightly full **2h**

**(4) 落地**：GitHub Actions + GPU runner 可选

**(5) 追问**：flaky metrics → 容忍 band ±0.002。

### 5.5 🟢 AWS：Registry 权限模型

**(1) 标准答案**

ML Engineer→Staging；ML Lead→Production 审批；SRE→紧急回滚；自动化→Staging + Gate 满足 Canary。**审计**全 stage 变更。

**(2) walk**：IAM role + MLflow permission；Separation of duties

**(3) 量化**：未授权 Production 推进 **0 容忍**（合规）

**(4) 落地**：Slack 审批 bot；8h 观察窗

**(5) 追问**：break-glass 双人在场。

## 6. 真实事故复盘（电商交易场景 · STAR-M-P）

### 6.1 「CT 静默部署退化模型，漏放率升 30%」

- **S (Situation)**：风控 XGBoost **周更 CT**，覆盖 **1.2 亿月活** 交易，prod KS=0.83。
- **T (Trigger)**：训练集误混入 **QA 环境模拟交易**（env=qa 未过滤），新模型 KS=0.79，仍 **>绝对阈值 0.75** → 自动 Production。
- **A (Approach)**：<br>

1. `fraud_miss_rate` +30% 告警（T+2 天）
2. Lineage：data_snapshot 含 qa 分区；对比 prod 训练集分布
3. Gate 复盘：绝对阈值无 **相对 prod** 检查

- **R (Resolution)**：<br>

- **M (Metrics)**：2 天额外漏放 **~8400 笔**；回滚 MTTR **10min**；Gate 改造后 **0** 类似事故（18 月）
- **P (Prevention)**：数据契约 CI；QA 数据物理隔离 bucket；CT 报告强制 diff prod metrics

## 10. 大厂面试题 · 长答 `[L5]`

### 10.1 蚂蚁：「CI 和 CT 边界？」

**结论**：**CI = 每次变更可验证**；**CT = 漂移/日历触发重训**，共用制品规范但 **不同触发器**。

**展开**：CI 跑单测+小样本集成+数据契约；CT 监控 PSI/KS 越界或每周 schedule；CT 不得绕过 CD 的 Canary。

### 10.2 字节：「如何做可复现训练？」

**结论**：**数据快照 + git sha + seed + 容器镜像 digest** 四元组锁死。
