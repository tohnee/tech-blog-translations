这场整体是“项目深挖 + Attention 基础 + 推理系统”的组合。面试官比较喜欢从项目里一个具体优化，一路追到背后的算法和系统原理。

### 1. deterministic FlashAttention backward

我先介绍了最近做的一个 Attention backward 性能优化。

问题主要出现在 deterministic dQ。为了保证固定累加顺序，原实现中不同 cluster 存在比较明显的等待和串行化。

我的优化主要涉及：

- 调整执行顺序，减少重复 cache / memory 搬运；
- 重新划分 tile，提高多个 cluster 的并行度；
- 在改变累加顺序后重新验证 deterministic 和数值正确性。

面试官重点追问了：

**为什么倒序会快、tile 重排为什么有收益、改变顺序以后 deterministic 怎么验证。**

这里对确定性的要求并不是必须和旧 baseline bitwise 完全一致，而是新实现多次运行能够稳定复现，并且误差满足训练侧要求。

### 2. FlashAttention：为什么普通 GEMM 优化还不够

随后问题从项目转到了 FlashAttention 最基本的原理。

我最开始回答了 tiling、producer-consumer、TMA 等后续版本的优化，但面试官继续追问：

> GEMM 本身就会做 tiling，为什么还需要 FlashAttention？

核心还是 Attention 中存在：

QKᵀ → Softmax → 乘 V

如果按照独立算子执行，会产生较大的中间结果和额外 HBM 读写。

因此 FlashAttention 的重点不只是“分块”，还包括如何在分块场景下完成 Softmax，并尽量避免完整中间矩阵反复写回。

这部分暴露的问题比较明显：我对 FA2/FA3/FA4 的硬件特性比较熟，但对最原始 FlashAttention 的算法逻辑准备得不够扎实。

### 3. PagedAttention 和 Prefix Cache

后半程开始问 vLLM。

PagedAttention 主要围绕 KV Cache 的 page/block 管理展开，包括动态分配、减少连续大块 buffer 带来的浪费，以及请求长度增长时的内存管理。

随后问题很快进入 Prefix Cache：

- 什么样的请求可以复用 KV；
- token 怎么按 block 切；
- block hash 怎么生成；
- 新请求怎么寻找最长公共 prefix；
- 后一个 block 的 hash 是否应该依赖前面的 prefix。

我的回答思路是按固定 block 切 token，并让当前 block 的 hash 与前一个 block 建立依赖，这样只有前缀完整一致时才能继续命中。

这一段比较能体现一个特点：

**面试官不会停在“知道 Prefix Cache”，而是会继续问它的数据结构。**

### 4. 在线推理和离线推理的目标并不一样

反问阶段，面试官介绍了团队的主要业务：淘宝、天猫内部大量商品数据需要通过大模型做 Embedding、内容理解和定制化推理。

这类场景偏大规模离线推理。

在线 serving 更关注 TTFT、ITL 和单请求 latency；

离线任务更关注整体 throughput、GPU 利用率、容错，以及一整批任务多久能够完成。

所以优化目标并不完全一样。

团队后续工作也会涉及推理引擎适配、内部模型支持，以及特殊模型结构下的算子优化。

### 5. 这场面试暴露的问题

这次比较明显需要补的有三个方向：

- FlashAttention 要从 FA1 的算法原理重新梳理，而不是只熟悉 FA3/FA4；
- PagedAttention 要明确“内存管理”和“Attention 计算量”是两个问题；
- Prefix Cache 不仅要知道作用，还要了解 block、hash 和匹配过程。

整场最大的感受是：

**AI Infra 面试很容易从 What 一直追到 Why 和 How。**

一个技术名词知道用途，只能回答第一层；能不能把算法、数据结构和实际执行路径接起来，才决定后面能不能继续聊下去。
