MNN 3.3.0 版本推出了多项大语言模型（LLM）相关特性（详情可参考 [MNN 3.3 版本发布（NPU 运行 LLM / 投机采样 / SME 支持）](https://zhuanlan.zhihu.com/p/1968638385603195647)），其中最核心的更新之一是新增 LLM 的 NPU 运行支持，显著提升了 Prefill 阶段的推理性能。此前官方发布的 MNN-LLM 论文（[HTTPS://dl.acm.org/doi/pdf/10.1145⁄3700410.3702126](https://dl.acm.org/doi/pdf/10.1145/3700410.3702126)），已系统阐述了内存优化（如 embedding 磁盘存储、混合精度量化、KV Cache 管理等）与计算优化（如访存优化、多核负载均衡等）方案。

本文将聚焦 MNN 框架**如何基于高通 NPU 实现 LLM 加速，围绕模型导出、NPU 适配转换、异构计算架构及性能测试**四大核心环节展开详细解析，为相关技术实践提供参考。

## 一、模型导出为 MNN 格式

MNN 官方提供了完整的 LLM 模型导出文档（[大语言模型 — MNN-Doc 2.1.1 documentation](https://mnn-docs.readthedocs.io/en/latest/transformers/llm.html)），核心导出工具为 MNN 仓库中的 [llmexport.py](https://github.com/alibaba/MNN/blob/master/transformers/llm/export/llmexport.py) 脚本，可直接将 Hugging Face 生态的 LLM 模型转换为 MNN 可运行的格式。

### 1.1 转换原理与核心步骤

MNN 的 LLM 模型转换通过标准化建模与分层处理实现多模型适配，核心步骤如下：

1. 算子与流程建模：基于 PyTorch 实现常见 LLM 的核心算子及运行流程，相关代码位于 `transformers/llm/export/utils/transformers.py`，为不同架构模型提供统一的计算逻辑支撑；
2. 模型结构抽象与映射：通过 `transformers/llm/export/utils/model_mapper.py` 建立统一的模型抽象层，将不同命名规范、不同架构的 LLM（如 LLaMA、Qwen、DeepSeek 等）映射到标准化架构，解决多模型适配问题；
3. ONNX 中间格式拆分导出：为规避单文件过大导致的处理效率问题，导出过程中会将模型结构与权重数据分离——通过 `unload_param` 函数将所有 Linear 算子替换为 FakeLinear 层，权重数据单独存储于 `llm.onnx.data` 文件，再将结构部分导出为 ONNX 格式；
4. ONNX 转 MNN：通过 MNN 的模型转换工具，将拆分后的 ONNX 结构与权重文件进一步转换为 MNN 原生格式。

### 1.2 转换后生成的文件清单

模型转换完成后，指定输出目录会生成以下核心文件，涵盖模型结构、权重、配置等全量信息：

- `llm.mnn`：模型计算图结构文件；
- `llm.mnn.weight`：模型核心权重文件；
- `tokenizer.txt`：模型对应的词汇表，用于文本 tokenize 与 detokenize；
- `embeddings_bf16.bin`：Embedding 层权重文件，后缀（bf16/int8/int4）由 Embedding 层的量化方式决定；
- `llm_config.json`：LLM 专属配置文件，包含 hidden_size、注意力头数、Embedding 量化方式等模型相关参数；
- `config.json`：MNN 运行时配置文件，指定运行精度、计算后端（CPU/GPU）等执行参数。

### 1.3 常见问题与使用注意事项

### （1）模型不支持或转换缺失组件

该问题大概率是由于目标模型的架构映射未被纳入 `model_mapper.py` 所致，解决方案为在该文件中补充对应模型的组件映射规则，将其对齐到 MNN 的标准化 LLM 架构；小概率是因为模型包含特殊算子（与主流 LLM 算子差异较大），需修改 `transformers.py` 中的建模逻辑，添加自定义算子的实现。

### （2）混合精度量化配置

MNN 为 LLM 提供了精细化的混合精度量化支持，可对 Embedding 层、LLM Decoder 层、LM Head 层分别指定量化位宽。实际应用中，采用 int8 分块量化（块大小 128）即可满足多数场景的精度需求；若需进一步优化内存占用，可针对不同组件配置 int4 量化——实际测试表明，部分小型 LLM（如 0.5B 量级）全链路采用 int4 量化仍能保证可用的推理精度。

### （3）QNN 推理适配的量化方式

当前 QNN 对 LLM 量化的原生支持较弱，MNN 通过自定义的 Smooth Quant 方法实现 QNN 兼容的量化。导出模型时需添加如下参数，确保生成 QNN 支持的 w4a16 量化格式：

```text
--smooth --act_bit=16 --quant_block=0 --lm_quant_bit=16 --quant_bit=4 --seperate_embed --sym --act_sym
```

## 二、模型转换为 QNN 格式

为适配高通 NPU，需将导出的 MNN 模型进一步转换为 QNN 格式，核心转换脚本为 `transformers/llm/export/npu/generate_llm_qnn.py`，整个转换过程分为样例生成、异构子图拆分、QNN 模型转换三个关键阶段。

### 2.1 阶段 1：样例输入生成

为确保 QNN 模型转换的准确性，需先生成两类标准化样例输入数据，分别适配 LLM 的 Prefill 和 Decode 两个推理阶段：

- Prefill 阶段样例：序列长度等于分块大小（Chunk Size），因 MNN 在 QNN 后端的 Prefill 阶段采用分块计算策略；
- Decode 阶段样例：序列长度为 1，对应推理过程中逐 token 生成的场景。

### 2.2 阶段 2：异构子图拆分

即使指定 QNN 为计算后端，MNN 也不会将所有计算逻辑全量卸载到 NPU，而是采用“QNN+CPU”协同计算的异构架构——将 LLM 中动态变化的计算部分（如 KV Cache 管理、变长序列处理）卸载到 CPU，静态计算部分交由 QNN（NPU）处理。核心拆分逻辑位于 `tools/cpp/compilefornpu.cpp`，关键代码如下：

```text
static bool _npuSupportOp(const Op* op) {
    if (gMaxKVSize > 0) {
        return true;
    }
    if (op->type() == OpType_Attention) {
        auto attn = op->main_as_AttentionParam();
        if (nullptr != attn && attn->kv_cache()) {
            return false;
        }
    }
    return true;
}

static bool isBreakOp(const Op* op) {
    bool isWhileControlflow = false;
    if (op->type() == OpType_While && op->main_as_WhileParam() != nullptr) {
        isWhileControlflow = true;
    }
    if (op->type() == OpType_If || isWhileControlflow || op->type() == OpType_Where || op->type() == OpType_Segment || op->type() == OpType_Unique || op->type() == OpType_NonMaxSuppressionV2) {
        return true;
    }
    if (!_npuSupportOp(op)) {
        return true;
    }
    return false;
}
```

从代码逻辑可知，MNN 以“QNN 不支持的算子”为拆分点，将整个计算图划分为多个独立子图。其中，若启用 KV Cache 机制，Attention 算子会被标记为 QNN 不支持，进而卸载到 CPU 执行，确保动态 KV Cache 的高效管理。

### 2.3 阶段 3：QNN 模型转换与权重共享

该阶段核心逻辑位于 `source/backend/qnn/npu_convert.py`，通过调用 QNN 工具链生成 QNN Context Bin 文件，具体流程如下：

1. 生成 Graph.cpp：通过 `source/backend/qnn/convertor` 将各子图的节点信息、量化参数等写入 C++文件，利用 QNN API 完成子图的计算图构建；
2. 量化策略：从生成的 Graph.cpp 可观察到，仅 Linear 层采用量化计算（与前文 w4a16 量化配置对应），其余层均采用 FP16 精度计算，在性能与精度间取得平衡；
3. 子图权重聚合：针对 Prefill 和 Decode 阶段中权重相同的子图，利用 QNN 的权重共享机制进行聚合，最终生成单个 Context Bin 文件。典型的聚合配置如下：

```text
{
  「type」: 「QNN」,
  「merge」: {
    「qnn/graph0.bin」: [ 「qnn/graph0」, 「qnn/graph1_0」 ],
    「qnn/graph1.bin」: [ 「qnn/graph1」, 「qnn/graph1_1」 ],
    「qnn/graph10.bin」: [ 「qnn/graph10」, 「qnn/graph1_10」 ],
    「qnn/graph11.bin」: [ 「qnn/graph11」, 「qnn/graph1_11」 ],
    「qnn/graph12.bin」: [ 「qnn/graph12」, 「qnn/graph1_12」 ],
    ...
  }
}
```

最终，转换过程会根据计算图拆分结果生成多个 QNN 子图 Bin 文件。例如，针对 Qwen2.5-0.5B 模型，转换后会生成 26 个 Bin 文件，分别对应不同的计算子图。

## 三、QNN 与 CPU 异构计算架构

MNN 基于高通 NPU 的 LLM 推理，核心是“QNN 子图（NPU）+ CPU 子图”的异构协同计算，其单个 Decoder 层的计算分工如下：

![](https://pic1.zhimg.com/v2-38edd9b80fa187de94e68b15fd7996ba_r.jpg)

如上图所示，计算图中标记为“plugin”的模块为 QNN 子图（运行于 NPU），而 Attention 算子（含 KV Cache 管理）则运行于 CPU。下图进一步展示了单 Decode 层的异构分工：蓝色区域为 NPU（QNN）计算部分，绿色区域为 CPU 计算部分。

![](https://pic1.zhimg.com/v2-262cb9d28d037412f0389b077483ef1c_r.jpg)

### 3.1 Prefill 阶段异构计算逻辑

Prefill 阶段针对长序列输入（如 Prompt）采用分块（Chunk）计算策略：假设 Prompt 长度为 300，设置 Chunk 大小为 128，则会分 3 次完成计算（前两次各处理 128 个 token，第三次处理剩余 44 个 token 并进行 Padding 补齐）。其中，固定长度的分块计算由 NPU（QNN）承担，而变长序列的拆分、Padding 以及 KV Cache 的初始化与合并等动态逻辑由 CPU 处理。

### 3.2 Decode 阶段异构计算逻辑

Decode 阶段为逐 token 生成过程，输入序列长度固定为 1，其异构分工逻辑与 Prefill 阶段一致：核心的静态计算（如线性变换、激活函数等）由 NPU（QNN）执行，而 KV Cache 的更新、下一个 token 的生成判断等动态逻辑由 CPU 负责。

## 四、性能测试结果与分析

为验证 MNN 基于高通 NPU 加速 LLM 的效果，选取 Qwen2.5-0.5B 模型进行实测，测试设备为小米 14（搭载高通骁龙 8 Gen3 芯片），测试场景为 350 个 token 的 Prompt 输入，分别对比 CPU 单后端与“NPU+CPU”异构后端的 Prefill 和 Decode 阶段性能。

### 4.1 测试结果

| 计算后端 | Prefill性能（token/s） | Decode性能（token/s） |
| --- | --- | --- |
| CPU | 437.5 | 52 |
| NPU+CPU（异构） | 813.9 | 43 |

### 4.2 结果分析

从测试数据可得出以下核心结论：

1. Prefill 阶段加速显著：“NPU+CPU”异构后端的 Prefill 性能达到 813.9 token/s，较 CPU 后端提升约 86%。这是因为 Prefill 阶段以静态的批量计算为主，能够充分发挥 NPU 的并行计算能力，大幅降低长序列输入的处理耗时；
2. Decode 阶段性能略低于 CPU：异构后端的 Decode 性能为 43 token/s，较 CPU 后端的 52 token/s 下降约 18%。推测原因是 Decode 阶段输入序列长度仅为 1，NPU 的并行计算优势无法充分发挥，同时异构架构下的子图调度、数据传输等开销抵消了部分计算收益，导致整体性能略低于 CPU 单后端。
