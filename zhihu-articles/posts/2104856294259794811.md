值得升级，但别在主力那台上直接替。先在一台测试机把启动脚本过一遍，能启动、能带图、工具调用还能用，再动真正在跑的那台。

llama.cpp 十一月十三日打了 v1.0.0 这个标签。项目从二〇二三年起天天出 nightly 构建，三年半都是 b 加五位数字的编号，一号版本号是头一回。跟着版本号出来的，是一批真被删掉的东西。

我把这次影响自己这边的原因和边界分开说。

## 版本号为什么现在才到 1

官方在发布里把规矩写清了。改了公开的 C 接口，第一位往上跳；加功能、加模型支持、改后端，跳第二位；只修 bug，跳第三位。

这条规矩对不用命令行的人有什么关系？关系在「你用的那份引擎，是谁装上去的」。

直接用官方发布包、或者自己编译的人，升级这件事自己说了算。走 apt、conda、Homebrew 装的人，什么时候换版本取决于打包的人。还有相当大一部分人根本不直接碰这个引擎，用的是包装了它的软件，比如各种本地客户端、给 Python 用的绑定库。这些人连版本号都看不见，只看客户端什么时候更新。

第一位数字跳了，说明这一批改动里确实有对不上的地方。

## 最先出事的是那一行参数

`-dt` 和 `--defrag-thold` 在旧版里一直打警告，说它没必要填了，然后照常启动。很多人当年就是从某个教程里抄了这一行，一直没删。

v1.0.0 把它删干净了。填着它就退出，报一句 `error: invalid argument: --defrag-thold`，模型还没开始加载。

我踩的位置写在下面，你可以照着过一遍。

systemd 的服务文件里，看 ExecStart 那一行。docker compose 里，看 command 字段。自己写的启动脚本里，grep 一下 `-dt ` 和 `defrag` 两个词。

还有一种情况容易漏。设了环境变量 `LLAMA_ARG_DEFRAG_THOLD` 的，新版不会报错，默默忽略，服务照样起来。同样是「启动参数里有 defrag」，写成命令行的会炸，写成环境变量的不会炸，排查时两处都得看。

删掉就行，旧版那句警告已经说了它没必要，删了不影响缓存怎么工作。

## 用别人打包的库，会先撞上名字变了

引擎对外暴露了 255 个以 llama_ 开头的函数，v1.0.0 之后剩 237 个。被删的是 35 个带过时标记的函数，外加热身函数。

改名清单里最常撞的几个，`llama_load_model_from_file` 改成 `llama_model_load_from_file`，`llama_new_context_with_model` 改成 `llama_init_from_model`，`llama_n_ctx_train` 那一组统一改成 `llama_model_n_*`。

好消息是这些改名大多已经预告了好几版，还在维护的绑定库基本都跟上了。没跟上的，症状是编译报未定义符号，或者加载时报错，不会悄悄给你错误答案。

另一件比函数名更难发现。库的 soname 从 libllama.so.0 变成了 .so.1。

这意味着系统不会把新库装到旧库的位置上，旧程序直接找不到动态库。好处是旧程序不会莫名其妙按新规矩跑。麻烦在打包这一侧，三条安装线的节奏各不相同。

## 开了工具的服务，现在会拒绝启动

以前把服务绑在 0.0.0.0 上，让局域网里另一台机器连，同时开着工具调用，旧版只打警告。

现在直接退出，日志里写三种解法。设一个 api key，或者把地址改回 127.0.0.1，或者显式加 `--allow-unauthenticated-tools`。

第三种我建议只用在完全隔离的实验网络上。开了之后，工具清单里有执行命令和写文件两项。

单人笔记本改回 127.0.0.1 最省事。家里确实要让另一台机器连进来，设 api key 是对的，它还顺带把工具调用挡在了密码后面。

同一处改动还收紧了两样。浏览器跨域代理现在只能连公网地址，局域网里那个内网的网页界面连不上了。带视觉的模型要读一张挂在 NAS 上的图片，也会收到一条「主机不是公网地址」的错误，得加 `--media-allow-private-urls` 才放行，而这个开关对这台服务器上所有调用方一起放开。

## 参数表上多出来的几项，先别急着开

新版参数表多了 `--shard`、`--ple`、`--moe-cache-cpu-share`、`--moe-cache-mib`。

`--shard` 和 `--ple` 让主模型和词表分片放在不同硬盘上，随机读多的一侧放固态更划算。

后面两个是专家缓存的调节项，控制未命中的部分有多大比例交给处理器直接算。默认 0，也就是全部上传显卡。

这两个都有实测数字，但都是在别人的机器上测的。作者在一张 RTX 5090 上跑 260 亿参数、每次激活 40 亿的模型，缓存给 2650MB 时把分担调到 0.95，每秒从 90.1 涨到 93.2。换成内存映射加载的那个组合，幅度更大，从 58.8 到 60.0。

这类参数最怕拿别人的数字直接抄。先按显存的七成上下设缓存，分担保持 0，跑一段自己平时常做的任务，看命中率和速度，再决定要不要动。

## 我不会在这几种情况下升级

主力那台正在对外提供服务、又没有备用机器的，先别动。那行参数带来的是一次启动失败，而这台机器重启之后才会暴露。

跑的是别人替你打包的整包安装，也先别动。库里 soname 变了，整包更新顺序要对得上，等打包那边先跟上。

反过来，自己有测试机、启动脚本是自己维护的、或者本来就跟着 nightly 跑的人，这版值得升。它多了三个模型架构的支持，还有几项安全加固，其中一部分正是靠「拒绝启动」来生效的。

## 发布页没给什么数

官方发布页对 Windows 这次只写了一行，说把 Linux 已有的直读方式搬了过去。两个平台谁快谁慢，页面上没有对照数字。

第三方有一篇实测，但环境是一台没有显卡的 4 核虚拟机，EPYC、内存 16G、跑十亿参数的小模型，作者自己也说这些数字只能当工具链的验证，不能拿来推显卡上的表现。

官方也没有升级前后的速度对照。想证明快了多少，还是得用原来那套测试题跑一遍，两边对比。
