SGLang 的 Scheduler 每一轮都要决定两件事：这一轮执行 Prefill 还是 Decode，以及哪些请求能进入这一轮的 Batch。

本文先介绍基础的 Prefill-first 调度，再逐步加入 Chunked Prefill、`prefill_decode_interval` 和 Mixed Chunk。重点放在请求如何在容器之间流动，以及几个机制分别改变了哪一步，不展开模型执行和 Attention Kernel 的实现。

### 1. 整体调度思想

SGLang 的基础逻辑是 **Prefill-first：这一轮如果能构造出 Prefill Batch，就优先执行它；否则尝试执行已有请求的 Decode。** 这里先假设 interval 和 Mixed Chunk 都关闭。

注意，判断条件是“能不能构造出 Prefill Batch”，并不是“`waiting_queue` 是否为空”。即使还有请求等待，如果请求槽位、KV cache 或其他接纳条件不满足，也可能无法构造 Prefill Batch，这时仍然会进入 Decode 分支。

从请求生命周期看，可以先理解为：

![](https://pic3.zhimg.com/v2-2cff75535dea8d8319f3c241423f922a_r.jpg)

这是 Continuous Batching：新请求完成 Prefill 后可以加入正在生成的请求，已经生成结束的请求则退出。它不需要等待同一批请求全部完成，才接纳下一批请求。

这个基础策略也带来一个问题：如果连续多轮都能构造 Prefill Batch，已有请求的 Decode 就可能连续等待。后面介绍的 Chunked Prefill、interval 和 Mixed Chunk，分别从单轮 Prefill 工作量、轮次安排和 Batch 混合方式三个角度改变这种行为。[基础调度入口](https://github.com/sgl-project/sglang/blob/16e353d93e4e6d870623bee3fe1ea62936475886/python/sglang/srt/managers/scheduler.py#L3637)

下面将基础调度、Chunked Prefill、interval 和 Mixed Chunk 放到同一张图中。图中省略专用执行分支；“资源与预算检查”包含请求槽位、KV 空间和 token 预算，不代表只有一个判断条件。

### 2. 调度中的重要容器

理解调度时，先区分“长期保存请求状态的容器”和“本轮临时构造的 Batch”。

| 容器或对象 | 是否为临时容器 | 保存什么 | 在调度中的作用 |
| --- | --- | --- | --- |
| waiting_queue | 否，跨轮维护 | 等待接纳的请求，也可能包括资源不足后退回来的请求 | 为新的 Prefill 提供候选请求 |
| running_batch | 否，跨轮维护 | 已完成 Prefill、还需要继续decode的活跃请求 | 没有新的 Prefill Batch 时，作为 Decode 的基础 |
| last_batch | 是，短期保留到后续轮次处理 | 上一轮执行的 Batch | 把上轮完成 Prefill 且未结束的请求接入 running_batch |
| PrefillAdder.can_run_list | 是，仅用于本轮组批 | 本轮已经通过接纳检查的请求 | 临时列表，用来构造本轮 Prefill Batch |
| chunked_req | 否，跨轮保留到续跑完成 | Prefill 尚未全部完成、后面还要继续处理的请求 | 保存长请求的续跑状态；它是单个请求引用，不是等待队列 |
| ScheduleBatch | 视用途而定，它是 Batch 类型 | 请求集合及本次执行需要的 token、位置和 KV 映射等信息 | Prefill、Decode 和 Mixed Batch 使用的批次表示 |

`running_batch` 保存等待继续生成的活跃请求，不代表本轮一定在 GPU 上执行。下一轮调度时，`last_batch` 通过 `filter_batch()` 排除已结束和未完成 Prefill 的请求，再通过 `merge_batch()` 合入 `running_batch`。

对应的流转关系是：**Prefill Batch → `last_batch` → 过滤 → 合入 `running_batch`**。[过滤与合并位置](https://github.com/sgl-project/sglang/blob/16e353d93e4e6d870623bee3fe1ea62936475886/python/sglang/srt/managers/scheduler.py#L3648)

### 3. 基础调度过程

本节先关闭 Chunked Prefill、interval 和 Mixed Chunk，只看普通请求如何从等待走到生成结束。

### 3.1 请求进入 waiting_queue

Scheduler 通过 `process_input_requests()` 分发收到的请求。普通生成请求完成必要的初始化后，经 `_add_request_to_queue()` 放进 `waiting_queue`。

进入 `waiting_queue` 只表示请求已经等待调度，还没有为它执行 Prefill。每轮调度回来后，Scheduler 都有机会把新收到的请求加入等待队列，而不是等当前 `running_batch` 全部结束才接收新请求。[入队位置](https://github.com/sgl-project/sglang/blob/16e353d93e4e6d870623bee3fe1ea62936475886/python/sglang/srt/managers/scheduler.py#L3264)

### 3.2 先接入上一轮完成 Prefill 的请求

`get_next_batch_to_run()` 先处理上一轮 Batch 的状态。如果上一轮是 Prefill，就将其中已经完成 Prefill、且仍需继续生成的请求合入 `running_batch`。

这里需要区分两种“完成”：

- **Prefill 完成**：prompt 已处理完，可以继续生成后续 token。
- **请求完成**：已经满足停止条件，例如生成 EOS 或达到输出长度限制，不再需要继续 Decode。

普通 Prefill 完成时通常已经采样出第一个输出 token。如果此时请求就满足停止条件，它会结束，不需要再进入后续 Decode。

### 3.3 尝试构造新的 Prefill Batch

接下来，`get_next_batch_to_run()` 调用 `get_new_batch_prefill()` 尝试组批。当前版本由它调用 `_get_new_batch_prefill_raw()` 完成主体工作，并把选出的 Batch 和更新后的 `running_batch` 一起返回。

如果成功选出至少一个请求，本轮优先执行这个 Prefill Batch。即使 `running_batch` 非空，也不代表本轮一定会 Decode。

如果没有构造出 Prefill Batch，才调用 `update_running_batch()` 准备 Decode。这个函数会过滤已结束请求、检查 Decode 的 KV 空间，并通过 `prepare_for_decode()` 准备本轮输入。如果最后没有活跃请求，这一轮就没有本地模型计算可执行。

KV 空间不足时，`update_running_batch()` 还可能通过 `retract_decode()` 撤回部分请求，再经 `_add_request_to_queue()` 放回等待队列。撤回不是正常生成结束；请求之后需要重新经过 Prefill 路径，复用或重建继续生成所需的 KV。[Decode 更新与撤回](https://github.com/sgl-project/sglang/blob/16e353d93e4e6d870623bee3fe1ea62936475886/python/sglang/srt/managers/scheduler.py#L4176)

### 3.4 执行并处理结果

选出的 Batch 由 `run_batch()` 执行，结果通过 `process_batch_result()` 分发给对应的 Prefill 或 Decode 结果处理函数，更新输出 token、结束状态和缓存状态。

未结束的 Decode 请求继续留在活跃集合里。结束请求释放请求相关资源；其中可复用的前缀 KV 可以由缓存机制保留，不等于请求结束就把所有 KV 无条件清空。[结果分发](https://github.com/sgl-project/sglang/blob/16e353d93e4e6d870623bee3fe1ea62936475886/python/sglang/srt/managers/scheduler.py#L4747)

### 3.5 用一个例子串起来

假设 A、B 已经完成 Prefill，正在 Decode，之后 C、D 先后到来，资源都足够，表格中的请求暂时都不结束。

| 轮次 | 调度前的变化 | 本轮执行 | 请求状态 |
| --- | --- | --- | --- |
| 1 | 没有新请求 | Decode A、B | A、B 各推进一个 token |
| 2 | C 进入 waiting_queue | Prefill C | A、B 等待；C 完成 Prefill |
| 3 | C 合入 running_batch，D 又到来 | Prefill D | A、B、C 本轮不 Decode |
| 4 | D 合入 running_batch，无新 Prefill | Decode A、B、C、D | 四条请求一起推进 |

这个例子说明：**不是每次 Prefill 后都必然跟一次 Decode。** 下一轮如果又能构造 Prefill Batch，基础策略仍然会优先 Prefill。

### 4. Prefill Batch 是怎么构造的

Prefill 组批可以分成两个问题：先考虑谁，以及这个请求能不能放进来。

### 4.1 SchedulePolicy 决定候选顺序

`SchedulePolicy.calc_priority()` 对 `waiting_queue` 中的请求安排优先顺序。常见策略包括：

| 策略 | 主要考虑什么 |
| --- | --- |
| FCFS | 按先来先服务的顺序考虑请求 |
| LPM | 优先考虑匹配到较长缓存前缀的请求 |
| shortest-prefill-first | 优先考虑未缓存 Prefill 工作量较少的请求 |

这里的 policy 主要决定候选请求的顺序；排在前面不意味着一定能运行，还要经过资源检查。本文后面的例子使用 FCFS，不展开其他 policy 的额外规则。

### 4.2 PrefillAdder 决定能否接纳

Scheduler 创建一个本轮专用的 `PrefillAdder`，再按顺序调用 `add_one_req()` 尝试接纳候选请求。它会综合考虑：

- 请求槽位和 Batch 请求数限制，是否还能加入新的请求。
- KV cache 空间，是否能容纳输入及后续生成的空间需求。
- 本轮输入 token 预算，以及开启 Chunk 后的共享 Chunk 预算。

通过接纳检查的请求进入 `can_run_list`，同时扣减本轮预算。

### 4.3 从 can_run_list 形成 ScheduleBatch

如果 `can_run_list` 非空，Scheduler 将入选请求从 `waiting_queue` 中移除，通过 `ScheduleBatch.init_new()` 创建 Batch，再通过 `prepare_for_extend()` 准备 Prefill 所需的输入和 KV 映射。

如果某个候选请求放不下，不代表已经选中的请求都要继续等待。只要 `can_run_list` 中已经有请求，就可以用它们构造本轮 Batch。只有一个请求都没有选出来时，这次 Prefill 组批才返回空结果。

数据流可以概括为：

```text
waiting_queue
  → calc_priority() 排序
  → init_next_round_input() 准备输入、匹配前缀
  → PrefillAdder.add_one_req() 检查与接纳
  → can_run_list
  → ScheduleBatch.init_new() / prepare_for_extend()
  → 本轮 Prefill Batch
```

因此，Prefill 组批不是简单地从队首拿固定数量的请求，也不保证能把预算恰好填满。[Batch 构造位置](https://github.com/sgl-project/sglang/blob/16e353d93e4e6d870623bee3fe1ea62936475886/python/sglang/srt/managers/scheduler.py#L4046)

### 5. Chunked Prefill 机制

### 5.1 把长 Prefill 拆成多轮

不开启 Chunk 时，一个长 prompt 的未缓存部分通常要在一次 Prefill 中处理完。这一轮可能耗时较长，期间已有 Decode 请求需要等待。

Chunked Prefill 允许把待计算部分拆到多个调度轮次。假设长请求 C 还有 10000 个 token 需要 Prefill，`chunked_prefill_size = 4096`，没有其他 Prefill 请求、Mixed Chunk 关闭且 KV 充足，忽略页对齐，则可以分成：

| 轮次 | C 本轮处理的 token 数 | 剩余待处理 token 数 |
| --- | --- | --- |
| 1 | 4096 | 5904 |
| 2 | 4096 | 1808 |
| 3 | 1808 | 0 |

前两轮只完成 prompt 的一部分，不能当作 C 已经进入正常 Decode。最后一轮完成整个 Prefill 后，C 才能进入后续生成阶段。中间 Chunk 的临时采样结果不会作为正常输出 token 发给用户。[中间 Chunk 的结果处理](https://github.com/sgl-project/sglang/blob/16e353d93e4e6d870623bee3fe1ea62936475886/python/sglang/srt/managers/scheduler_components/batch_result_processor.py#L344)

### 5.2 chunked_req 如何续跑

某个新请求因为本轮预算不足而被截断时，`PrefillAdder` 用 `new_chunked_req` 记录它，Scheduler 再把它保存到 `chunked_req`。

下一轮调度时，`stash_chunked_request()` 整理已经完成的 Chunk 的缓存状态；这个尚未完成 Prefill 的请求会从 `last_batch` 的待合并集合中排除，不会被误放进普通 Decode Batch。

下一次允许构造 Prefill Batch 时，Scheduler 先对 `chunked_req` 调用 `init_next_round_input()` 和 `PrefillAdder.add_chunked_req()`，再尝试接纳 `waiting_queue` 中的新请求。也就是说，**续跑请求先使用本轮共享预算，新请求使用剩余部分**。

如果续跑后仍然没处理完，继续保留 `chunked_req`；如果这一轮已经安排了它的最后一块，则清除续跑标记。此时它还要真正执行完这一轮，才算完成 Prefill。当前普通路径用一个 `chunked_req` 跟踪未完成请求，并不是每个等待请求都拥有一份独立的 Chunk 调度预算。[续跑入口](https://github.com/sgl-project/sglang/blob/16e353d93e4e6d870623bee3fe1ea62936475886/python/sglang/srt/managers/scheduler.py#L3921)、[续跑接纳](https://github.com/sgl-project/sglang/blob/16e353d93e4e6d870623bee3fe1ea62936475886/python/sglang/srt/managers/schedule_policy.py#L1060)

### 5.3 两个容易混淆的参数

`max_prefill_tokens` 和 `chunked_prefill_size` 都会影响 Prefill 组批，但它们并不是“总预算”和“每个请求的预算”这样一组关系。

| 参数 | 对应预算 | 主要作用 |
| --- | --- | --- |
| max_prefill_tokens | rem_input_tokens | 本轮输入接纳预算，影响还能否继续添加 Prefill 请求 |
| chunked_prefill_size | rem_chunk_tokens | 本轮共享 Chunk 计算预算，决定长请求本轮能处理多少，以及何时截断 |

**`chunked_prefill_size` 是 batch-wide、per-iteration 的共享预算，不是每条请求各自拥有的上限。**

[SGLang Chunked Prefill — 原理与代码实现 | AI Fundamentals](https://forceinjection.github.io/09_inference_system/sglang/chunked_prefill.html)这篇blog认为是每条请求的上限是不对的。

所以当开启chunk机制时：

- chunked_prefill_size几乎与max_prefill_tokens是一个意思
- 最多只会有一条请求处于chunk状态

### 5.4 Chunk 不会自动让 Prefill 和 Decode 交替

只开启 Chunked Prefill，改变的是一轮 Prefill 的工作量和长请求的续跑方式，基础的 Prefill-first 顺序仍然存在。

假设 A、B 正在 Decode，C 的 Prefill 需要三个 Chunk。在关闭 interval 和 Mixed Chunk 的情况下，可能出现：

```text
Prefill C 第 1 块 → Prefill C 第 2 块 → Prefill C 第 3 块 → Decode A、B、C
```

虽然每个 Chunk 之间都回到了 Scheduler，但下一轮仍然能从 `chunked_req` 构造 Prefill Batch，于是继续优先执行 Prefill。Chunk 提供了更细的调度边界，**并不单独保证已有请求在这些边界之间获得 Decode 机会**。

### 6. prefill_decode_interval 与 Mixed Chunk

### 6.1 interval：在 Prefill 后留出 Decode 轮次

`prefill_decode_interval = N` 的含义是：一次包含 Prefill/Extend 工作的 Batch 被选出后，接下来的 N 个调度轮次暂缓 Prefill，让调度器进入 Decode 或空闲分支。设为 0 表示关闭这项间隔。

A、B 正在 Decode，C 需要三个 Chunk。假设 `prefill_decode_interval = 2`、Mixed Chunk 关闭，且 A、B 始终未结束：

| 轮次 | 本轮执行 | C 的状态 |
| --- | --- | --- |
| 1 | Prefill C 第 1 块 | 仍需续跑 |
| 2 | Decode A、B | interval 阻止 C 续跑 |
| 3 | Decode A、B | interval 阻止 C 续跑 |
| 4 | Prefill C 第 2 块 | 仍需续跑，重新设置 interval |
| 5 | Decode A、B | interval 生效 |
| 6 | Decode A、B | interval 生效 |
| 7 | Prefill C 最后一块 | C 完成 Prefill |
| 8 | Decode A、B、C | C 已合入 running_batch |
| 9 | Decode A、B、C | interval 生效 |

interval 的判断发生在 Prefill 组批之前，所以也会挡住 `chunked_req` 的续跑。所谓“优先续跑”，是在这一轮允许 Prefill 的前提下，相对于普通等待请求的优先。

### 6.2 Mixed Chunk：把 Prefill 和 Decode 放进同一个 Batch

interval 调整的是轮次顺序。Mixed Chunk 调整的是一轮 Batch 的组成：开启 `enable_mixed_chunk`、Chunked Prefill 有效且满足混合条件时，可以把新的 Prefill 工作和已有请求的 Decode 放到同一次模型执行中。

Scheduler 先构造 Prefill Batch，再对 `running_batch` 做过滤和 `prepare_for_decode()`，通过 `mix_with_running()` 将 Decode 请求合入新 Batch，并用 `decoding_reqs` 记录哪些请求来自 Decode。原来的 `running_batch` 被替换为空 Batch，避免重复持有并重复合并这些请求；之后仍通过 `last_batch` 的过滤与合并回到后续调度。[Mixed Chunk 组批位置](https://github.com/sgl-project/sglang/blob/16e353d93e4e6d870623bee3fe1ea62936475886/python/sglang/srt/managers/scheduler.py#L4113)

例如 A、B 正在 Decode，C 还有 10000 个 token 需要 Prefill。`chunked_prefill_size = 4096`，输入预算充足、interval 为 0，忽略页对齐和额外限制：

| 轮次 | 同一个 Batch 中的工作 | C 剩余待 Prefill token 数 |
| --- | --- | --- |
| 1 | A Decode 1 + B Decode 1 + C Prefill 4094 | 5906 |
| 2 | A Decode 1 + B Decode 1 + C Prefill 4094 | 1812 |
| 3 | A Decode 1 + B Decode 1 + C Prefill 1812 | 0 |
| 4 | Decode A、B、C | C 已进入生成阶段 |

### 6.3 三个机制如何配合

在有可 Decode 请求、资源充足、持续有 Prefill 工作且允许混合时，可以这样对比：

| 配置 | 典型轮次安排 | 改变什么 |
| --- | --- | --- |
| 只开启 Chunk | Prefill Chunk → Prefill Chunk → … | 限制单轮 Prefill 工作量，但不保证插入 Decode |
| Chunk + interval = 1 | Prefill Chunk → Decode → Prefill Chunk → Decode | 在独立轮次中给 Decode 机会 |
| Chunk + Mixed，interval = 0 | Mixed → Mixed → … | Prefill 轮本身也携带已有请求的 Decode |
| Chunk + Mixed + interval = 1 | Mixed → Decode → Mixed → Decode | 混合轮之间，再留出纯 Decode 轮次 |

Mixed Batch 也包含 Extend 工作，因此会触发 interval 的计数设置。下一轮在间隔内时，不再构造新的 Prefill/Mixed Batch，而是进入 Decode 分支。三个机制分别回答：**这一轮 Prefill 做多少、下一轮是否允许 Prefill、这一轮能否同时推进 Decode。**
