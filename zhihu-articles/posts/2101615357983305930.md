生产代码改动很小，核心却是一个明确的契约：**有效专家 ID 可以重新映射，无效路由必须保持无效（也就是padding）。**

![](https://pic3.zhimg.com/v2-6e8114f9f98f781e8ce0671e5b976fdc_r.jpg)

## 🔍 问题：-1 被当成了数组下标

MoE router 为每个 token 选择 top-k 个专家及对应权重。`topk_ids` 中，非负 ID 表示有效专家，`-1` 则表示无效或 padding 路由槽位。

在 EP 中，逻辑专家编号与通信后端使用的物理编号可能不同，因此需要 `global_to_physical` 映射。它转换编号空间，不重新选择专家，也不改变路由权重。

例如：

```text
mapping = torch.tensor([0, 2, 4, 6, 1, 3, 5, 7])
topk_ids = torch.tensor([3, 0, -1, 5])

mapping[topk_ids]
# tensor([6, 0, 7, 3])
```

期望结果应该是 `[6, 0, -1, 3]`，但 `-1` 变成了真实专家 `7`。

![](https://pic4.zhimg.com/v2-c2d6029658d4da13c26d74aa1c727b49_r.jpg)

Python 的 list 等序列支持负索引，`-1` 表示最后一个元素；这里的 PyTorch Tensor 也有同样行为。

于是，**代码没有报错，路由语义却静默丢失了。** 这里的 `7` 只是示例映射表的末项，不是所有表都会映射到 `7`。

![](https://pic1.zhimg.com/v2-c20701a47058ef97d088721dc8f7ae38_r.jpg)

## 📌 什么时候触发？

必须同时满足：

- `global_to_physical` 不为 `None`；
- 输入 `topk_ids` 中存在 `-1`。

没有映射表时，原代码直接返回输入；只有有效 ID 时，原查表行为也正常。默认 linear placement 不使用这张表，因此不能把这个问题描述成默认模型配置普遍出错。

![](https://pica.zhimg.com/v2-9bae53d6ca3f1f6b00634d6cf8db4568_r.jpg)

## 🛠️ 修复：让无效哨兵保持无效

NIXL 的修复位于共享给 dispatch/combine 使用的映射 helper：

```python
- return self.global_to_physical[topk_ids]
+ return torch.where(topk_ids >= 0, self.global_to_physical[topk_ids], -1)
```

有效 ID 保留查表结果，`-1` 的最终输出仍为 `-1`。例如，`[-1, 6]` 从错误的 `[7, 5]` 变为 `[-1, 5]`。

一个细节是：**`torch.where` 不是惰性 `if`。** 在 eager 模式下，查表表达式仍先求值，再根据 mask 选择输出。因此，这里修复的是最终输出语义，并不是通用的越界 ID 检查器。

![](https://pic4.zhimg.com/v2-2919b428b2fbd515ffa58d5585975bb5_r.jpg)

DeepEP LL 存在同类路径，#64340 将相同规则应用到该后端，并复用参数化回归测试。

两个后端各有自己的生产 helper；“共享”指每个后端内部的 dispatch/combine 共享映射逻辑，以及测试覆盖两个后端。

![](https://pic2.zhimg.com/v2-5be3e677f0428dcbf834d9428a28e3b1_r.jpg)

## 🔄 为什么 dispatch/combine 都要验证？

dispatch 前，需要把逻辑专家编号转换为后端编号，并取得后续 combine 使用的 handle。

专家计算后，combine 路径也会转换原始路由 ID，再结合权重与 handle 合并结果。这里仍是 global-to-physical 转换，不能误称为反向映射。

因此，测试应检查两个阶段实际收到的 ID。

## 🧪 CPU regression 如何证明修复？

测试使用**真实 vLLM adapter 和 CPU PyTorch Tensor**，只把外部 transport 替换为记录参数的 `_RecordingTransport`，覆盖三个场景：

- **混合输入**：有效 ID 正确映射，`-1` 保持无效；
- **全无效输入**：所有 `-1` 保持不变；
- **无映射表**：输入原样返回。

每个场景都断言 dispatch 和 combine 收到的 ID。

据 PR 记录，NIXL 三例修复前为 **2 failed、1 passed**，修复后为 **3 passed**。扩展为两个后端 × 三个场景后，共 **6 passed**；仅缺 DeepEP guard 时为 **2 failed、4 passed**，该基线已经包含 NIXL 修复。

对于这个局部映射 bug，确定性输入、真实 adapter 调用路径，以及修复前失败／修复后通过，就是直接回归证据。**端到端测试不是证明该修复成立的必要条件。**

![](https://pic1.zhimg.com/v2-88263f719a1ccc880e468429db906ffc_r.jpg)

## 📊 修复带来了什么？

准确的收益是：**恢复有映射表路径中的无效路由语义，同时保留已覆盖的有效映射与无映射行为。**

它不改变 collective 调用顺序或路由权重。新增比较和选择操作的 GPU 成本没有量化，因此不能宣称零开销或吞吐提升。
