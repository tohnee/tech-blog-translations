## 背景-FlashAttention V2

本文以JayShah 在GPU Mode上的分享展开，介绍FlashAttention V3采用的优化技术。

![](https://pic3.zhimg.com/v2-2774d8789c9b1734d28e360fa8ae7812_r.jpg)

![](https://pic3.zhimg.com/v2-a69b309dc3a0203a82482bc3a1b88cd0_r.jpg)

这部分讲的是Attention的计算背景，首先介绍Attention的计算公式，然后告诉你这部分在AI Infra在GPU是怎么计算的，比如当前的朴素方法是先把Q和K从HBM以分块的方式读进来，然后计算Q与K的转置的乘法（GEMM-I)，计算得到中间变量S，然后把S写会到HBM，写回之后会从HBM在读取S，之后计算S中每行的最大值，然后算S减去最大值，更新S，之后再计算softmax(S)，这一步得到P，然后把P写入HBM中，写入后，再把P和V以分块的方式加载到共享内存中，然后计算O=PV（GEMM-II)之后再把计算完的结果写入到HBM中。

## FlashAttention V2的问题

![](https://pic2.zhimg.com/v2-6ef752f2003551559353d99fe94a057f_r.jpg)

![](https://pic4.zhimg.com/v2-9b51e9ebd1021ce42c45dbbc991baad1_r.jpg)

<br>然后两页PPT开始讲问题，在GPU的存储层次里面，分为共享内存和HBM存储，共享内存的读写速度是HBM的一个量级以上，因此在现有的这种Attention实现逻辑中，对S的大量读写是非常不高效的，因此有有没有办法设计一种IO感知的机制，来尽可能减少数据在HBM上的搬运。FlashAttention V2的解决办法是：<br>1、不把分数矩阵S写入HBM，并且使用online-softmax，对Q的一个分块，逐块加载K，V，增量式地累加对应输出O分块，用“在线”计算的方式边算边修正softmax统计量。<br>2、重计算：前向计算的时候不存注意力矩阵，反向时重新算一遍，用计算换显存IO。<br>

![](https://pic3.zhimg.com/v2-4e5b263fe6f7ad5c30519358ebf61ef8_r.jpg)

实现成算法就是这样：

- 外层循环遍历Q的分块，把一个 bM×d 的 Q 块调入片上 共享内存SRAM，初始化输出累加器 O、行最大值 m 和行和 当前行所有元素的和rowsum
- 内层循环遍历 K/V 的分块：使用online-softmax的方式计算Attention
- 最后把计算结果写入到HBM里面

![](https://pic1.zhimg.com/v2-2e2ad04d6e632e4d96b2f962a635bec0_r.jpg)

注意，这里和FlashAttention V1的区别是，V1的外循环是加载KV，内循环是加载Q，这样的缺点是处理外层循环的时候，对每一块KV，都需要把Q全部加载一遍，这样就导致了Q被重复加载了，因此V2针对这点进行了优化。

![](https://picx.zhimg.com/v2-f01ac57bf66ad2d5e334b2a6e1386369_r.jpg)

但是FA2 存在的问题是在H卡上的MFU太低了，只有35%-40%，原因就是V2并没有考虑到H卡新引入的特性，比如TMA(Tensor Memory Access)和WGMMA。因此就有了FA 3的优化工作。<br>

![](https://pic3.zhimg.com/v2-5b8ef6e17fea77402aa38f452209627e_r.jpg)

最后实现的效果就是与FA2相比，取得了1.6-3倍的加速。<br>**优化点一：利用H100新指令**<br>与A100相比，H100多了WGMMA和TMA的支持，A100上TensorCore上计算矩阵乘用的指令是mma.sync(每个warp独立搬运数据进TensorCore）在H100上只能跑到峰值算力的2/3。只有换用WGMMA，也就是由整个warpgroup协作、异步执行的矩阵乘法才能喂饱H100的TensorCore。另外就是TMA可以实现数据从全局内存HBM到共享内存的拷贝，并且还不需要依赖寄存器计算地址空间，极大的降低了线程的开销。<br>

![](https://picx.zhimg.com/v2-8ed54b5b4617f90ed8fed715bafb10d7_r.jpg)

算法实现：<br>CTA视角的算法流程：

- **一个线程块CTA里面的warpgroup分成两种角色，分别是生产者和消费者，他们的比例大致是1:2**
- 生产者分支（负责数据加载）
- 消费者分支（负责数据计算）

**优化点二：使用重叠和异步**<br>上面优化实现了数据加载与计算的重叠，下面这页PPT解释了为什么要把Softmax和GEMM重叠起来。Attention里面有两种不同的计算类型，跑在两种不同的硬件上面

- GEMM（矩阵乘 QKᵀ 和 PV）跑在 Tensor Core（专用矩阵单元）上
- Softmax 的 exp（EX2 指令）跑在 CUDA Core 上的特殊函数单元 MUFU 上

FA2里面，这两者是串行的，也就是先得等矩阵做完乘法，再算softmax，互相等待，纸面上的数据是，以head_dim=128，block size=128x192来看，FP16的WGMMA需要3072个时钟周期就可算完，但是MUFU.EX2也就是Softmax需要1536个时钟周期。可见Softmax占WGMMA的一半的周期，也就是说，如果串行执行，CUDA Core有一半的时间在闲置；反过来Softmax完成后也要干等TensorCore。而且FP8的情况更加糟糕，因为FP8的WGMMA算的更快。

![](https://pic1.zhimg.com/v2-22f69c76bdc294c97b269085127c5c22_r.jpg)

<br>因此FA设计的异步策略如下：

- 第一类是WarpGroup之间的GEMM计算与Softmax计算的重叠

在消费者warpgroup里面，实现了warpgroup之间的计算与计算重叠，把warpgroup1的softmax计算与warpgroup2的GEMM计算进行重叠，如图所示：

- Warpgroup 1 在做 GEMM 时，Warpgroup 2 在做 Softmax
- Warpgroup 1 轮到做 Softmax 时，Warpgroup 2 正好切到 GEMM<br>这样从**整个 SM 的视角看，Tensor Core 和 CUDA Core（MUFU）在任意时刻都有活干，两套硬件单元不再互相等待——这就是“乒乓”：你打过来我打过去，轮流占用两类计算单元。**

![](https://picx.zhimg.com/v2-b794d051db62d8b05f3d728e30b950e7_r.jpg)

- 第二类是Warpgroup内部的GEMM与Softmax之间的重叠

乒乓调度靠的是“两个 warpgroup 互相错开”，需要占用两个 warpgroup。这页的思路是：只看一个 warpgroup 内部，把处理第 j 块的三个阶段——WGMMA0（算分数 S=QKᵀ）、Softmax、WGMMA1（算 O+=P̃V）——像流水线一样错位排开，而不是等第 j 块全部做完才开始第 j+1 块。

![](https://pic4.zhimg.com/v2-6c8b311769b441ce2e43e211cc986d39_r.jpg)

算法实现：<br>准备工作(第1-3行）

- 第1行：按消费者warp数量重新分配寄存器（拿走生产者省出的份额）
- 第2行：片上初始化累加器 Oᵢ=0、mᵢ=−∞、ℓᵢ=0
- 第 3 行：等第一批 Q、K₀ 被生产者 TMA 搬进共享内存

流水线注入阶段（第 4–6 行）

- 第 4 行：算 S_cur = QᵢK₀ᵀ（WGMMA），提交并等待——**第一块没有东西可重叠，必须老老实实等完**
- 第 5 行：用完立即释放 K 的第 0 段缓冲，还给生产者
- 第 6 行：对 S_cur 做在线 Softmax 得 mᵢ、P̃_cur、ℓᵢ，并按需缩放 Oᵢ

主体循环（第 7–17 行）：错位流水开始了，进入第 j 轮时，手上握着的是上一轮算好的 S_cur（块 j−1 的分数）和 P̃_cur，然后：

- 第 8–9 行：等 Kⱼ 到位，立刻发起 S_next = QᵢKⱼᵀ 的 WGMMA，提交但不等待——Tensor Core 在后台默默算，CPU 侧继续往下走
- 第 10–11 行：等 Vⱼ₋₁ 到位，发起 Oᵢ += P̃_cur Vⱼ₋₁ 的 WGMMA，同样不等待（注意 V 落后 K 一拍，这就是流水图的错位）
- 第 12 行：现在才回头等第 9 行那个后台 WGMMA 完成——在这期间，MUFU（CUDA Core）上一轮的 Softmax 等工作已经在和它并行了
- 第 13 行：对刚算完的 S_next 做 Softmax——此刻 Tensor Core 正忙着跑第 11 行的 PV 矩阵乘，两类硬件同时满载，这正是“趁 Tensor Core 忙 WGMMA 时做 EX2”
- 第 14 行：等 PV 的 WGMMA 完成，按新最大值缩放 Oᵢ（在线 Softmax 修正）
- 第 15 行：释放 Kⱼ 和 Vⱼ₋₁ 的缓冲段还给生产者
- 第 16 行：S_next → S_cur，滚动进入下一轮

![](https://picx.zhimg.com/v2-08b86b3cccfe425a1a91c1a9a717d9db_r.jpg)

收尾（第 18–21 行）<br>最后一块没有“下一块”可重叠了：等 V 的最后一块、做最后一个 PV 矩阵乘并等待，然后用 mᵢ 缩放 Oᵢ、算出 logsumexp Lᵢ = mᵢ + log ℓᵢ，把 Oᵢ 和 Lᵢ 写回 HBM。<br>优化点三：使用FP8<br>使用FP8低精度优化会有内存（LayOut）布局不匹配的问题，问题的根源是硬件要求和现实习惯相悖；

- 硬件要求：FP8的WGMMA有个硬性规定，即操作数在共享内存里面必须沿内层维度K连续存放，即k-major，也就是列主序
- 现实习惯：但Q、K、V在显存里的标准布局是BSHD，按照（batch_size, seq_len, num_head, head_dim)，它是沿着head_dim维度连续的，也就是行主序，不是沿着K维的
- 还有一个问题：TMA改变不了连续模式，它只会“照原样搬运”，搬进来后连续的方向还是head_dim维，不会帮你转置

逐个GEMM分析

- GEMM0（Q·Kᵀ）：没问题。因为乘法本身要做的就是 Q 和 K 在 d 维上做内积，K 转置后恰好“错有错着”，k-major 的要求刚好被满足
- GEMM1（P·V）：出问题了。V 的连续方向在head_dim维，但这个 GEMM 需要它沿 k 维（也就是V矩阵的N 维）连续，因此必须把 V 转置

解决方案：<br>不用搬出共享内存去CPU或者单独Kernel转置，那样访存开销直接爆炸，所以只能做Kernel内转置，而且放在生产者warpgroup里去做，好处就是生产者本身就在搬运数据，把转置融合进搬运环节，消费者完全无感知，也不占用计算时间。

- 用LDSM(从共享内存加载）和STDM(存回共享内存）指令配合自定义布局
- **中间用字节置换（byte permute）完成重排**——FP8 每元素只有 1 字节，32 个寄存器线程可以整体重排

![](https://pic2.zhimg.com/v2-f5202c18071e33e5947a11b2fc401b85_r.jpg)

![](https://pic3.zhimg.com/v2-ffb4bf6a09833bad131f3f28a2ec9a46_r.jpg)

<br>下面这张图很好解释了GEMM1的FP8的布局问题，P是GEMM0的FP32累加器输出，就在寄存器里面放着，按照下图的Figure3的方式分配给各个线程，但是GEMM1要把它当做FP8操作数A用，而FP8 WGMMA要求寄存器按照Figure4的方式分配，同一份数据、两种“线程↔元素”的对应关系。Figure 3（FP32 累加器布局）怎么读看第 0 行和第 8 行、元素 d0–d7 的归属：T0–T3 四个线程共同覆盖同一个列对（都持有 {d0,d1}），而且列对的推进和行是交错的——{d0,d1} 在第 0 行、{d2,d3} 却在第 8 行、{d4,d5} 又回到第 0 行……即“线程换得慢、行列穿插”。Figure 4（FP8 操作数 A 布局）怎么读

同一个 T0 一口气持有 {a0,a1} 和 {a2,a3}（第 0 行连续 4 个元素），然后 {a4,a5}、{a6,a7}（第 8 行）；换到 T1 才轮到下一组。即“每个线程独占一段连续元素，行先走完再换线程”<br>

![](https://pic1.zhimg.com/v2-057b8f72a6d2d4ef35f4b8fefeb0dcb0_r.jpg)

### <br>优化点四：持久化内核

核心思想：传统 CUDA 启动方式是一个工作任务（work tile）对应一个 CTA（线程块），硬件调度器在任务之间切换时会产生间隙。持久内核的做法是：只启动固定数量的 CTA（通常等于 SM 数量），让每个 CTA 轮流处理多个工作任务。好处之一是：当前任务的收尾工作（epilogue，比如归一化、写回）可以和下一个任务的装载数据（prologue，TMA 搬运）重叠起来，SM 不空转。

![](https://pic3.zhimg.com/v2-02358115feee581cb72bee6f6a7b57b4_r.jpg)

具体例子算账

- 场景：SeqLen=4096，Heads=8，Batch=4，BlockM=128
- 沿序列方向切分：4096/128 = 32 个 m 块；总共 32×8×4 = 1024 个工作任务

两种做法对比：

- 不用持久内核：启动 grid 维度 (32, 8, 4)，一次性launch 1024 个 CTA，一个 CTA 对应一个任务，做完即退
- 用持久内核（H100 SXM5）：H100 有 132 个 SM，就只启动 132 个 CTA，每个 CTA 循环领取约 1024/132 ≈ 8 个任务逐个处理

额外收益：动态负载均衡<br>持久内核可以在运行时动态把任务分配给下一个空闲的 CTA。这对 causal masking（因果掩码）场景特别重要——三角形的掩码让靠前的 query 块的有效计算量远小于靠后的块，如果静态平均分配，先干完的 CTA 只能干等；动态分配则让空闲 CTA 自动接活，消除长尾。<br>定位：这是在 warp/warpgroup 级别优化（前面几页）之上的kernel 级别优化——之前解决的是“一个 CTA 内部怎么跑得满”，这页解决的是“任务怎么喂给 CTA 才不空转”，两者互补。<br>结果

<br>FA3在解码场景上的优化<br>对于解码场景，query的长度往往比较短，可能只有几个token，但是上下文长度会比较长，而且解码场景不是Compute Bound而是memory bound。解码场景有两个优化：<br>

- 按照KV序列维度进行切分；由于Query很短，所以你切Query收益肯定不大，那就把长长的 KV 序列切成很多段，每段分给不同的 CTA 并行算，最后把各段的部分结果（带各自的 logsumexp）合并起来——这正是 FA2 时代就有的 Flash-Decoding 算法，FA3 直接复用。
- GQA packing，把多个 query 头打包进一个 query tile，现在的模型普遍用 GQA，多个 query 头共享同一份 KV。解码时本来一个 query 头的任务太小，FA3 就把共享同一 KV 头的多个 query 头堆进同一个 Q 分块一起算——一次 KV 加载喂给多个 query，KV 的读取次数成倍下降，任务块也变大了，GPU 吃得更饱
