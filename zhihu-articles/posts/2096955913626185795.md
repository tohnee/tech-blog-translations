一个模型刚加载时能放进显卡，聊到几千个 token 却突然显存不足；同样的模型，短问题很快，长文档的首字却迟迟不来。这两个现象不需要用“模型在思考”解释，沿着张量的形状和生命周期就能看清。

这篇文章以采用因果自注意力、标准稠密 KV Cache 的 decoder-only Transformer 为例，拆解一次生成：输入怎样变成向量，Q/K/V 各做什么，首字之前与后续逐字生成有什么区别，缓存到底有多大，以及 GQA、RoPE、FlashAttention 分别解决哪一层问题。文中的容量数字都是可复算的理论估算，不是特定显卡的性能实测。

## 1. 模型生成的是 token，界面才把它们拼成文字

Tokenizer 把输入映射成整数序列。一个 token 可能对应一个汉字、一个词片段、标点或一段字节，不能把“8192 tokens”直接当成“8192 个汉字”。同一段内容在不同词表下长度也可能不同。

假设 batch 为 B，当前输入长度为 T，隐藏维度为 D，词表大小为 V。输入 ID 形状是 `[B,T]`；查嵌入表以后得到 `[B,T,D]`。经过多层 Transformer，最后的词表投影通常给出 `[B,T,V]` 的 logits；实际生成实现可只保留需要的位置，避免分配全部位置的输出。

logits 是未归一化分数。生成器可以取最大值，也可以在温度、top-k、top-p 等处理后采样；这些是解码策略，并不等于模型内部又多训练了一次。模型参数在普通推理中保持不变。

因果语言模型在位置 t 的输出用于预测下一个 token。训练时，已经知道整段文本，所以可以把许多预测位置并行计算；在线生成时，第 t+1 个 token 尚未产生，标准自回归路径就必须等待上一步。训练能并行，不意味着普通生成也能一次得到所有未来 token。

## 2. Q、K、V 是同一输入的不同投影

在一层注意力里，可以先用最简写法描述：

```text
Q = X Wq
K = X Wk
V = X Wv
Attention = softmax(Q K^T / sqrt(d) + M) V
```

这里的小写 d 是一个注意力头的维度，M 是加性掩码：允许的位置加 0，不允许的位置加负无穷。softmax 沿 key 的维度归一化，所以每个 query 得到一组“看哪些位置、各占多少”的权重，再对 V 加权求和。

Q 可以理解为当前位置发出的查询；K 参与计算匹配分数；V 提供被聚合的内容。它们不是数据库里人为录入的三个字段，而是由参数矩阵学习出来的向量。称它们“问题、索引、答案”能帮助入门，却不能把注意力理解成精确搜索一条知识记录。

例如某个 query 对三个可见 key 的缩放分数为 `[2,1,0]`，softmax 权重大约是 `[0.665,0.245,0.090]`。如果第三个位置是未来位置，它的分数必须在 softmax 前被掩为负无穷，此时权重变成约 `[0.731,0.269,0]`。先算完 softmax 再把第三项设为零、却不重新归一化，会改变结果。

多头注意力为不同头保留不同的表示空间。一个完整层还包括残差、归一化、前馈网络等，不能把整个 Transformer 简化成一次 QK 点积。原始 Transformer 采用 Encoder–Decoder 结构；本文讨论的 decoder-only 路径通常没有那套独立 Encoder 和 Cross-Attention。[原始论文：Attention Is All You Need](https://arxiv.org/abs/1706.03762)

## 3. Prefill 和 Decode：首字延迟与输出速度是两件事

假设提示词有 5 个 token，位置是 0 到 4。

Prefill 阶段一次处理这 5 个输入位置。每个位置仍受因果掩码约束，但不同位置的矩阵运算可以并行执行。最后一个提示词位置的 logits 用来采样位置 5 的 token。

这里有一个常见的计数错误：采样出了位置 5，并不表示它的 K/V 已经存在于缓存里。它尚未作为输入走过模型。下一次 Decode 才把这个刚采样出的 token 输入各层，计算位置 5 的 Q/K/V，并将新的 K/V 加到历史缓存中；这一轮 logits 再预测位置 6。

因此通常分别观察：

- 首 token 延迟：包含请求排队、预处理、prefill 和首次解码等成本。
- token 间延迟：后续输出相邻 token 的间隔。
- 请求吞吐与 token 吞吐：单位时间完成多少请求或多少 token。

长提示词往往增大 prefill 工作量；大量并发、内存带宽和调度则会影响 decode。哪一项是瓶颈需要测量，不能仅凭“GPU 利用率不高”就断定模型没有正确用到显卡。不同 batch 和上下文长度下，计算与内存访问的相对成本也会变化。

## 4. KV Cache 保存历史中间结果，不是聊天记录数据库

在因果注意力中，历史位置不能看到将来的 token。在相同模型、相同前缀和位置处理方式下，新增后缀不会改变已经计算好的历史 K/V，因此可以缓存它们。

第 l 层有自己的一份 K 和 V。对标准多头配置，常见缓存布局可以写成：

```text
K_l: [B, Hkv, S, d]
V_l: [B, Hkv, S, d]
```

S 是已经进入缓存的长度，Hkv 是 KV 头数。新 token 的 query 读取历史加当前的 key，按所得权重聚合对应 value。旧位置的 Q 通常不需要跨解码步骤保存，因为后续生成主要需要当前位置的新 query。

这份缓存服务于某次推理的复用，不会自动更新模型参数，也不等于把用户问题训练进模型。普通的对话历史可能先被拼成提示词；KV Cache 则是模型对这些 token 计算出的各层中间结果。删除聊天记录、清理服务端缓存和修改模型权重是三种不同操作。[Hugging Face 官方缓存说明](https://github.com/huggingface/transformers/blob/main/docs/source/en/cache_explanation.md)

## 5. 用一条公式把显存算明白

假设各层 KV 头数与维度相同、所有请求缓存长度相同，且只统计稠密 K/V 张量本身：

```text
KV bytes = 2 × L × B × S × Hkv × d × e
```

2 对应 K 和 V；L 是层数；e 是每个元素占用的字节。FP16 或 BF16 在这里都按 2 字节计算。它们数值表示不同，但单元素存储量相同。

设 L=32、B=1、S=8192、Hkv=8、d=128、e=2：

```text
2 × 32 × 1 × 8192 × 8 × 128 × 2
= 1,073,741,824 bytes
= 1024 MiB
= 1 GiB
```

这一配置每增加一个缓存 token，所有层合计增长 131072 bytes，也就是 128 KiB。若 4 个请求分别都缓存 8192 token，KV 载荷就是 4 GiB；上下文再翻倍，载荷也再翻倍。

这能解释“权重放得下，服务仍然 OOM”：显存里不只有权重，还有 KV、临时张量、算子工作区、运行时开销，以及内存分配器的保留空间。静态缓存可能按最大长度预分配；分页缓存还有块粒度与元数据；不同请求长度也不一定相同。上面的公式是基准账，不是显卡监控中总占用的承诺。

再看权重：70 亿参数按每参数 2 字节计算约 14 GB，即约 13.04 GiB；如果理想地只用 4 bit 存每个参数，原始载荷约 3.5 GB。但实际量化还有 scale、分组元数据、未量化层与工作区。“4 bit 模型”并不自动意味着 KV 也按 4 bit 存。拿量化后的模型文件大小直接推导可支持的并发数，容易低估显存。

## 6. MHA、MQA、GQA：看清共享的是谁

设 query 有 32 个头。在其他尺寸不变时：

| 结构 | Query 头数 | KV 头数 | 8192 token 的 KV 载荷 |
| --- | --- | --- | --- |
| MHA | 32 | 32 | 4 GiB |
| GQA | 32 | 8 | 1 GiB |
| MQA | 32 | 1 | 128 MiB |

这个表使用上一节的 32 层、单请求、头维 128、每元素 2 字节，只改变 KV 头数。

GQA 中多个 query 头共用一组 KV。32 个 query 头、8 个 KV 头时，每组有 4 个 query 头；并不是把所有 query 合成一份，也不是只保留第一个头的输出。

更少的 KV 头可以减少缓存载荷与相应读取量，但模型结构、训练和内核实现需要匹配。不能在已有 MHA 权重上随便删掉 24 个 KV 头，就声称免费获得相同质量。GQA 论文研究了从多头检查点转换并继续训练的路线，效果与开销属于其具体实验设置，不能套成所有模型的保证。[GQA 原论文](https://arxiv.org/abs/2305.13245)

## 7. RoPE 解决位置表达，不负责把缓存变小

如果只把 token 的内容向量送进普通注意力，模型还需要获得顺序信息。RoPE 对 Q/K 的二维子空间施加随位置变化的旋转，让点积能够表达相对位置关系。

在一个二维子空间中可写为：

```text
R(a) = [[cos(a), -sin(a)],
        [sin(a),  cos(a)]]
(R(pθ) q)^T (R(sθ) k) = q^T R((s-p)θ) k
```

右侧出现了位置差 s-p。真实实现会对多对维度使用不同频率，布局也可能采用相邻配对或分半配对，需要和模型检查点保持一致。常见实现把经过位置旋转的 K 写入缓存，读取旧 K 时不应再重复旋转。

对缓存解码，位置编号尤其关键。前面已有 100 个 token，新 token 不应该把位置重置为 0；否则 query 和历史 key 的相对位置关系被破坏。分页、滑动窗口和 padding 下，逻辑位置与物理存储槽位还要分别管理。RoPE 可计算更大位置的旋转，不代表未经适配的模型可以无限外推并保持质量。[RoFormer 原论文](https://arxiv.org/abs/2104.09864)

## 8. FlashAttention 与 PagedAttention 解决的是不同问题

FlashAttention 通过分块和在线 softmax 等方式减少 GPU 高带宽内存与片上存储之间的数据搬运，避免把完整注意力分数矩阵都物化到显存。它计算的是精确注意力算法，浮点计算顺序不同仍可能产生数值差异。它并没有让标准全注意力的算术工作量突然变成线性，也不会自动消除每层需要保留的历史 KV。[FlashAttention 原论文](https://arxiv.org/abs/2205.14135)

PagedAttention 则关注服务时的缓存管理：用块映射组织 KV，减轻大块连续预留、碎片及重复复制造成的浪费。它改善的是缓存如何分配和共享，不会让同一组未压缩 K/V 数值凭空少占字节。真实收益取决于请求长度、并发、共享前缀及调度策略。[PagedAttention 原论文](https://arxiv.org/abs/2309.06180)

可以这样检查优化方案是否对症：GQA 影响 KV 头数；KV 量化影响每元素字节；分页关注分配利用率；FlashAttention 关注注意力计算的内存访问。这些技术能够组合，但它们不会彼此替代。

## 9. 缓存后的因果掩码，不能简单套一个左上三角

已经缓存 P=5 个位置，再一次处理 N=3 个新 token，query 长度是 3，key 长度是 8。三个新 query 的绝对位置分别是 5、6、7，正确可见关系如下，1 表示允许：

```text
key 位置: 0 1 2 3 4 5 6 7
query 5:  1 1 1 1 1 1 0 0
query 6:  1 1 1 1 1 1 1 0
query 7:  1 1 1 1 1 1 1 1
```

若直接对 3×8 矩阵取从左上角开始的普通下三角，第一行可能只能看第 0 个 key，显然错了。单步 decode 只有一个新 query，且 key 张量只包含历史与当前有效位置时，它应能看到全部这些位置；静态缓存未使用槽位、padding 和滑窗限制仍然要额外屏蔽。

不同 API 的布尔掩码语义也可能相反。写自定义生成循环时，应核对所用版本、算子和非方阵对齐规则，而不是只看到 `is_causal=True` 就认为所有缓存布局都正确。[PyTorch SDPA 官方接口](https://docs.pytorch.org/docs/stable/generated/torch.nn.functional.scaled_dot_product_attention.html)

## 10. 可运行代码：复算显存并检查掩码

下面只用 Python 标准库。运行 `python3 kv_demo.py`，可以复现上述三种头配置的载荷，并验证缓存偏移后的可见范围。它是正确性与容量演示，没有执行 GPU 推理，也不是性能基准。

```text
def kv_bytes(layers, batch, tokens, kv_heads, head_dim, item_bytes=2):
    dims = (layers, batch, tokens, kv_heads, head_dim, item_bytes)
    if any(not isinstance(x, int) or isinstance(x, bool) or x <= 0 for x in dims):
        raise ValueError("all dimensions must be positive integers")
    return 2 * layers * batch * tokens * kv_heads * head_dim * item_bytes

def causal_rows(past, new):
    if past < 0 or new <= 0:
        raise ValueError("past >= 0 and new > 0 required")
    return [
        [key <= past + row for key in range(past + new)]
        for row in range(new)
    ]

for name, heads, expected_mib in [
    ("MHA", 32, 4096), ("GQA", 8, 1024), ("MQA", 1, 128)
]:
    size = kv_bytes(32, 1, 8192, heads, 128)
    assert size == expected_mib * 2**20
    print(f"{name}: {size / 2**20:.0f} MiB")

mask = causal_rows(5, 3)
assert [sum(row) for row in mask] == [6, 7, 8]
assert causal_rows(5, 1) == [[True] * 6]
for row in mask:
    print(" ".join("1" if item else "0" for item in row))
print("All checks passed.")
```

## 11. 从现象回到可测量的问题

模型载入就 OOM，先查权重、精度、设备切分与基础运行时开销；载入正常、长上下文才 OOM，查 KV 预算、最大上下文和临时工作区；单请求正常、并发后 OOM，查每个请求的实际缓存长度与分配策略。

首字慢时，把排队时间和 prefill 时间分开；后续 token 慢时，同时看 batch、历史长度、KV 读取和调度等待。不要把所有慢都归因于参数量，也不要用一项优化的名称替代真实的 profile。

最后做一个实现核对：logits 是否在预测下一 token，新增 K/V 的时间点是否正确，位置编号是否连续，mask 是否包含历史偏移，容量计算用的是 KV 头数还是 query 头数。把这五件事核对好，比盲目切换多个“加速开关”更容易定位错误。
