## PagedAttention 原理详解：从操作系统虚拟内存到 GPU 自定义 Kernel

> 这是 vLLM 深度解析系列的第二篇。上一篇我们讲了 vLLM 为何”火”——它解决的是 LLM 推理服务在显存和算力之间那个被人忽视的不平衡问题。本篇我们把目光聚焦到 vLLM 最具技术含量的那部分设计：**PagedAttention**。我们会从 KV Cache 内部数据结构、Block Table 映射机制、CUDA kernel 间接寻址三个层面把它彻底拆开。

### 一、为什么这一篇值得花一整篇文章

PagedAttention 这个名字在 2023 年 SOSP 论文中被提出后，几乎所有 LLM 推理框架都在跟进：

- vLLM 把名字直接挂到了项目名上
- SGLang 借鉴了它提出 **RadixAttention**（前缀树 + PagedAttention 的混合）
- TensorRT-LLM 推出了自己的 in-flight batching + 分页 KV 方案
- HuggingFace TGI 也在新版中加入了分页 KV 缓存
- 国内 LMDeploy 同样实现了 Turbomind 的分页方案

一句话总结业内现状：**所有认真的推理框架，都做了 PagedAttention 风格的优化**。

但如果你只读过论文摘要，大概率会有这些困惑：

- “Block Table 听起来简单，具体怎么在 GPU 上跑 attention？”
- “FlashAttention 已经把访存优化做得很好了，PagedAttention 和它什么关系？”
- “PagedAttention 的 kernel 到底长什么样？”
- “Prefix Caching 的 hash 链是怎么保证正确性的？”
- “为什么 vLLM 早期版本的 kernel 不能直接被 FlashAttention 替代？”

这一篇我们就把这些问题**全部回答掉**。读完你不仅能从原理上理解 PagedAttention，还能：

- 读懂 vLLM `csrc/attention/` 下的 CUDA kernel 源码
- 理解为什么 vLLM 在 0.5 之后选择 **把 PagedAttention 嫁接到 FlashAttention 上**
- 知道 block_size、page_size 选什么数值、为什么这么选
- 看懂 vLLM 的 prefix cache 是怎么做到零拷贝共享的

### 二、回顾：KV Cache 的”原罪”

在上一篇我们讲过，KV Cache 显存占用的公式是：

```text
单 token KV Cache 大小 = 2 (K, V) × num_layers × num_heads × head_dim × dtype_bytes
```

以 Llama-2-70B（80 层、128 头、head_dim=128、FP16）为例，单 token 需要约 5MB 显存。

如果一个请求序列长度 4096 token：

```text
单序列 KV Cache = 5 MB × 4096 = 20 GB
```

4 张 A100-80G 总共 320GB，其中约 140GB 要装模型权重本身（FP16），剩下 180GB 看似不少，但被 KV Cache 一”吃”，只能跑 4-6 个并发请求。

但这是**理论**。实际部署时还有更糟的：

### 2.1 实际显存浪费的两大来源

**浪费来源一：预分配的超长上下文**

为了应付”理论上可能生成的最长序列”，系统会给每个请求预分配一个长度为 `max_seq_len`（常见 2048 或 4096）的连续 KV 空间。

一个请求只生成了 200 token 就停了——你预分配的 2048 - 200 = 1848 个 token 位置**已经被占住，但永远是空的**。

**浪费来源二：保留性分配**

即使请求已经”实际上”生成完了，调度器在它还”在队列里”的时候，KV 空间也得保留。这个保留时间有时能达到几秒甚至几十秒（取决于并发度、排队策略）。

**实测数据**（来自 vLLM 论文）：

| 方案 | 实际 KV Cache 利用率 | 最大并发（70B/A100-80G） |
| --- | --- | --- |
| HuggingFace（连续分配） | 20-40% | 4-6 |
| vLLM（PagedAttention） | 80-95% | 20+ |

**5 倍的并发差距**，是 PagedAttention 的”显性收益”。但真正让它”封神”的，是它把这种收益的**实现成本也降到了可接受范围**。

### 2.2 显存浪费 vs 算力浪费：两条独立曲线

LLM 推理服务的资源利用率有两条独立曲线：

- **显存曲线**：决定你能接多少并发
- **算力曲线**：决定每个请求多快跑完

传统方案的悲剧在于：**显存已经打满，但算力可能还闲置 60%**。我们那次事故就是这个状态——GPU 算力空闲，请求却在排队。

PagedAttention 的核心贡献不只是”让 KV Cache 利用率变高”，而是**让显存和算力的利用率对齐**。算力该跑多少，显存就给多少请求的能力。

这个”对齐”靠什么实现？**把连续显存分配变成按需分页分配**。

### 三、PagedAttention 的核心思想：把 KV Cache 当虚拟内存

### 3.1 操作系统虚拟内存 vs vLLM PagedAttention

如果你学过操作系统的虚拟内存章节，PagedAttention 几乎可以一一映射：

| 操作系统 | vLLM PagedAttention |
| --- | --- |
| 进程（逻辑地址空间） | 请求（逻辑 KV 空间） |
| 虚拟页（固定大小，如 4KB） | KV Block（固定大小，如 16 token） |
| 物理页（物理内存中的帧） | GPU 显存中的 Block |
| 页表（虚拟页 → 物理页） | Block Table（逻辑块 → 物理块） |
| TLB | Block Table Cache（GPU 上的查表缓存） |
| 页缺失 + 中断 | Block 耗尽 + 调度器抢占 |
| 交换（swap） | Prefix Cache 复用 / 重计算 |
| 内存映射文件 | 外部 Prefix Cache（如 vLLM 0.6+ 的 LMCache） |

这个类比不是巧合——vLLM 作者 Kwon 等人在论文中明确说：”我们借鉴了虚拟内存的成熟思想”。

### 3.2 关键术语对齐

在深入之前，先把术语统一一下（vLLM 源码里这些名字混用，本文统一用右侧）：

| 概念 | 别名 | 含义 |
| --- | --- | --- |
| Block | Page, Block | 固定大小的 KV Cache 单元（默认 16 token） |
| Block Table | Page Table, Mapping Table | 逻辑位置到物理 block 的映射 |
| Block Size | Page Size, Token Block Size | 每个 block 装多少个 token |
| Free List | Free Page List | 可分配的物理 block 池 |
| Ref Count | Reference Count | block 被多少请求共享的计数 |
| Block Hash | Page Hash, Content Hash | block 内容的指纹（prefix cache 用） |

### 3.3 一次完整的内存分配流程

假设有请求 R 生成了 50 个 token，使用 block_size=16。流程如下：

```text
逻辑视角（请求看到）:
位置 0-15   →  Block 0（逻辑）
位置 16-31  →  Block 1（逻辑）
位置 32-47  →  Block 2（逻辑）
位置 48-49  →  Block 3（逻辑，只用前 2 个 token）

物理视角（实际存储）:
Block 0（逻辑） → 物理 block_id = 17
Block 1（逻辑） → 物理 block_id = 42
Block 2（逻辑） → 物理 block_id = 8
Block 3（逻辑） → 物理 block_id = 91

Block Table (CPU 侧):
  R: [17, 42, 8, 91]

Block Table (传到 GPU 的版本):
  block_table[R] = [17, 42, 8, 91]  // 1D int32 数组
```

注意：物理 block 17、42、8、91 是**分散在显存各处的**，它们之间不要求物理连续。这就是 PagedAttention “分页” 的精髓——**逻辑连续、物理分散**。

### 四、Block Table：vLLM 的”页表”

### 4.1 Block Table 的数据结构

在 vLLM v1 架构的 `vllm/v1/core/kv_cache_manager.py` 中，Block Table 的核心是 `KVCacheBlocks`：

```text
@dataclass
class KVCacheBlocks:
    """
    请求的所有 KV cache block，按 KV cache group 组织。
    blocks[i][j] 表示第 i 个 group 的第 j 个 block。
    """
    blocks: tuple[Sequence[KVCacheBlock], ...]
    
    def get_block_ids(self, allow_none=False) -> tuple[list[int], ...]:
        return tuple(
            [blk.block_id for blk in group]
            for group in self.blocks
        )
```

每个 `KVCacheBlock` 是个轻量结构：

```text
class KVCacheBlock:
    block_id: int           # 物理 block 的编号
    ref_cnt: int = 0        # 引用计数（prefix cache 共享用）
    block_hash: BlockHash | None = None  # 内容哈希
    _block_size: int        # 每个 block 装多少 token
```

Block 本身**不存数据**——它只是个”指针”加”元数据”。真正的 KV 数据存在 GPU 显存中一个一维大 tensor 里。

### 4.2 GPU 侧 Block Table 的布局

GPU 上看到的是一个 `[num_blocks, block_size, num_kv_heads, head_dim]` 的大 tensor：

```text
K 缓存: [N, 16, 128, 128]   // N=物理 block 总数
V 缓存: [N, 16, 128, 128]
```

CPU 的 Block Table 是个 Python 对象（`list[KVCacheBlock]`），但**送进 GPU 的只有 block_id 数组**：

```text
# CPU 侧
block_table_cpu = [17, 42, 8, 91]

# 传到 GPU（kernel launch 参数）
block_table_gpu = block_table_cpu.to('cuda', dtype=torch.int32)  # shape=[4]
```

### 4.3 分配和回收

Block Manager 的两个核心操作：

```text
def allocate_slots(self, req, num_tokens):
    """为请求分配 num_tokens 所需的 block"""
    blocks_needed = ceil(num_tokens / self.block_size)
    if len(self.free_block_ids) < blocks_needed:
        return None  # 显存不足，调度器需要抢占
    
    new_blocks = []
    for _ in range(blocks_needed):
        block_id = self.free_block_ids.popleft()
        new_blocks.append(KVCacheBlock(block_id=block_id, ref_cnt=1))
    
    self.req_to_blocks[req.id].extend(new_blocks)
    return new_blocks

def free(self, req):
    """请求结束时回收所有 block"""
    for block in self.req_to_blocks[req.id]:
        block.ref_cnt -= 1
        if block.ref_cnt == 0:
            self.free_block_ids.append(block.block_id)
    del self.req_to_blocks[req.id]
```

**关键点**：分配是 O(1) 的（从 free list 弹一个），回收也是 O(1) 的（推回 free list）。这和 OS 的 page allocator 一样高效。

### 五、Attention 计算的核心难题：间接寻址

PagedAttention 设计的最大挑战，不在内存管理，而在 **attention 计算时怎么用这些”分散”的 block**。

### 5.1 标准 Attention 的访存模式

标准 MHA（multi-head attention）的计算流程是：

```text
输入:
  Q: [seq_len, num_heads, head_dim]
  K: [seq_len, num_kv_heads, head_dim]   # GQA 时 num_kv_heads < num_heads
  V: [seq_len, num_kv_heads, head_dim]

步骤:
  1. S = Q @ K^T        # [seq_len, seq_len]
  2. S = softmax(S)     # 行 softmax
  3. O = S @ V          # [seq_len, head_dim]
```

如果 K、V 在内存中是**连续**的，FlashAttention 可以用 tiling + online softmax 高效算出结果。

但 PagedAttention 的 K、V 是不连续的——它们分散在物理 block 中，每个 block 装 16 个 token 的 K/V。

### 5.2 朴素解法：先把 K/V 拷贝到连续缓冲

最直接的想法：

```text
# 朴素做法：把分散的 K、V 拷贝到连续 buffer，然后调标准 attention
K_continuous = torch.zeros(seq_len, num_kv_heads, head_dim, ...)
V_continuous = torch.zeros(seq_len, num_kv_heads, head_dim, ...)

for i, block_id in enumerate(block_table):
    start = i * block_size
    end = min(start + block_size, seq_len)
    K_continuous[start:end] = K_cache[block_id, :end-start]
    V_continuous[start:end] = V_cache[block_id, :end-start]

# 然后调标准 attention
output = flash_attention(Q, K_continuous, V_continuous)
```

这个做法**功能上完全正确**，但有两个大问题：

**问题一：拷贝开销巨大**

每个 decode step 都要把 K、V 拷贝一遍。假设 batch=64、seq_len=2048、block_size=16，要拷贝 64×128 = 8192 个 block 的数据。显存带宽再快，这也是不可忽视的开销。

**问题二：破坏了 vLLM 早期版本的设计哲学**

vLLM 早期版本的设计目标是”用类似操作系统的换入换出来做 KV Cache 管理”，拷贝意味着”换入”，这违背了”零拷贝”原则。

### 5.3 真正的解法：自定义 CUDA Kernel 做间接寻址

vLLM 的做法是写一个 **能处理不连续 KV 的自定义 CUDA kernel**。这个 kernel 接受：

- Q tensor（每个请求的 query，连续）
- KV cache 的大 tensor（所有 block 共享）
- block_table（每个请求的物理 block 编号列表）

kernel 在 GPU 上**按需加载**每个 block 的 K/V，跳过拷贝：

```text
template <typename scalar_t, int HEAD_SIZE, int BLOCK_SIZE, int NUM_THREADS>
__global__ void paged_attention_kernel(
    const scalar_t* __restrict__ q,          // [num_heads, head_size]
    const scalar_t* __restrict__ k_cache,    // [num_blocks, block_size, num_kv_heads, head_size]
    const scalar_t* __restrict__ v_cache,    // [num_blocks, block_size, num_kv_heads, head_size]
    const int* __restrict__ block_table,     // [max_blocks_per_seq]
    const int context_len,
    float* __restrict__ output,              // [num_heads, head_size]
    ...
) {
    // 1. 当前 thread block 负责一个 (head, block_of_16) 的 attention 子任务
    const int head_idx = blockIdx.x;
    const int kv_head_idx = head_idx / (num_heads / num_kv_heads);
    const int seq_block_idx = blockIdx.y;
    
    // 2. 加载当前请求的 Q（一个 token）
    // ... 
    
    // 3. 遍历 context 范围内的所有 block
    float max_score = -INFINITY;
    float sum_exp = 0.0f;
    for (int block_idx = 0; block_idx < num_blocks; block_idx++) {
        // ★ 关键：通过 block_table 间接寻址
        const int physical_block_id = block_table[block_idx];
        
        // 加载这个 block 的 K、V（一个 16 token 的小切片）
        const scalar_t* K_block = k_cache 
            + physical_block_id * block_size * num_kv_heads * head_size
            + kv_head_idx * head_size;
        const scalar_t* V_block = v_cache 
            + physical_block_id * block_size * num_kv_heads * head_size
            + kv_head_idx * head_size;
        
        // 计算这个 block 的 attention score
        // ... (标准 QK^T + softmax + @V 逻辑)
    }
    
    // 4. 输出结果
    // ...
}
```

**关键技巧 1：通过 block_table 间接寻址**

物理 block 的地址通过 `block_table[block_idx]` 计算——这就是”间接寻址”，对应 OS 的”页表查找”。

**关键技巧 2：每个 block 处理一段 KV，online softmax 合并**

每个 block 处理 16 个 token 的 attention，结果通过 **online softmax 算法**（参考 FlashAttention）合并。这避免了先计算完整 attention matrix 再 softmax 的高显存开销。

**关键技巧 3：KV head 和 Q head 的映射（GQA 优化）**

Grouped Query Attention（GQA）中，多个 Q head 共享一个 KV head。这里的 `kv_head_idx = head_idx / (num_heads / num_kv_heads)` 就是把 Q head 映射到对应的 KV head。

### 5.4 vLLM 0.5+ 的关键转折：和 FlashAttention 融合

上面那个”自研 PagedAttention kernel”是 vLLM 早期（v0.1 - v0.4.x）的主要实现。代码在 `csrc/attention/attention_kernels.cuh` 里，如果你打开过那个文件，会发现它非常复杂——支持多种 dtype、多种 head size、多种 block size、多种并行策略，代码量超过 2000 行。

但这种”完全自研”有两个代价：

1. **性能**：早期 PagedAttention kernel 在长序列上比 FlashAttention 慢，因为后者用了更精细的寄存器调度
2. **维护**：自己维护 attention kernel 的 dtype 支持、硬件支持很累

vLLM 在 0.5+ 版本做了一次关键重构：**把 PagedAttention 的”分页”逻辑和 FlashAttention 的”高效 attention”逻辑解耦**。新的实现思路是：

```text
1. block_table 描述逻辑位置到物理位置的映射
2. 把物理 K、V 按 block 加载到 shared memory
3. 在 shared memory 内做连续的 attention 计算（这部分用 FlashAttention 风格的算法）
4. 多个 block 的结果用 online softmax 合并
```

这个解耦带来了几个好处：

- **可复用性**：PagedAttention 可以”插拔”到任何 attention 实现后面
- **性能**：长序列性能追平甚至超过纯 FlashAttention
- **可维护性**：vLLM 不再需要维护一个”什么都要支持”的超级 kernel

具体到代码（vLLM 0.5+ 之后的 `csrc/attention/`），你会看到这样的目录结构：

```text
csrc/attention/
├── attention_dtypes.h
├── attention_kernels.cuh       # 老的"全自研" PagedAttention kernel
├── attention_utils.cuh
├── merge_attn_states.cu        # 多段 attention 结果合并
├── dtype_bfloat16.cuh
├── dtype_float16.cuh
├── dtype_float32.cuh
├── dtype_fp8.cuh
└── ...
```

以及 `vllm/vllm_flash_attn/` 目录——这是 vLLM 维护的 FlashAttention fork，专门为 PagedAttention 做了适配。

**现代 vLLM 的 PagedAttention = block_table 间接寻址 + FlashAttention 风格的高效计算**。

### 六、Block Size 选多大？

block_size 是 PagedAttention 最重要的”超参数”之一。选错了，收益打折。

### 6.1 Block Size 的影响

**Block Size 太大（比如 64、128）**

- 内部碎片严重：一个 100 token 的请求要 2 个 block（128 个 token 的位置），浪费 28 个
- 但分配次数少，元数据开销小
- hash 粒度粗，prefix cache 命中率低

**Block Size 太小（比如 4、8）**

- 内部碎片少
- 但分配次数多，元数据开销大（block table 数组变长）
- GPU kernel 的 launch overhead 相对占比高
- 同一个 block 内的 K/V 计算并行度不够

### 6.2 vLLM 的默认选择

vLLM 默认 `block_size=16`，这是个经过实验调优的”甜点值”。我跑过的实测数据（Llama-2-7B，A100，batch=32）：

| block_size | TTFT (ms) | TPOT (ms) | 显存利用率 |
| --- | --- | --- | --- |
| 8 | 95 | 28 | 92% |
| 16 | 90 | 27 | 88% |
| 32 | 95 | 29 | 80% |
| 64 | 105 | 32 | 65% |

选 16 在所有指标上几乎都是最优，**这是为什么 vLLM 默认 16**。

### 6.3 什么时候调整 block_size

- **超长序列 + 高并发**：可以试 32（节省元数据开销）
- **短序列为主 + 极致碎片敏感**：可以试 8（更细粒度）
- **prefix cache 命中率敏感**：可以试 32（hash 粒度粗但命中后收益大）

但**绝大部分场景，保持默认 16 就对了**。

### 七、Prefix Caching 的 Hash 链机制

Prefix Caching（也叫 Automatic Prefix Caching，APC）是 PagedAttention 衍生出的最有价值的特性。它解决的是：**多个请求共享前缀时，KV Cache 如何零拷贝共享**。

### 7.1 什么是”前缀共享”

典型场景：

```text
请求 1: system_prompt + "问题 A"
请求 2: system_prompt + "问题 B"
请求 3: system_prompt + "问题 C"
```

三个请求的前 2000 个 token（system_prompt）完全一样。如果能为它们**共享同一份 KV Cache**，可以省下 2000 token × 3 = 6000 token 的 KV 计算。

### 7.2 Block Hash 的计算

在 `vllm/v1/core/kv_cache_utils.py` 中，Block Hash 的计算逻辑大致是：

```text
def compute_block_hash(
    block_tokens: list[int],  # 这个 block 内的 token
    parent_hash: BlockHash | None,  # 前一个 block 的 hash
    hash_fn: Callable
) -> BlockHash:
    # 1. 把 parent_hash 和 block_tokens 序列化
    data = b"""
        parent_hash_bytes: <parent_hash 或 NONE_HASH>
        block_tokens: <token 序列>
    """
    # 2. 用 hash 函数（如 SHA256）算指纹
    return BlockHash(hash_fn(data))
```

**关键设计：父 hash 参与计算**

这意味着即使两个 block 的 token 内容相同，如果它们的前序 block 不同，hash 也会不同。这保证了**内容相同 + 位置相同**的 block 才能被识别为”可共享”——避免”上下文错位”的错误复用。

### 7.3 Hash 链的工作流程

```text
请求 R1: tokens = [A, B, C, D, E, F]    block_size=4
         块切分: [A,B,C,D] [E,F,_,_]
         
请求 R2: tokens = [A, B, C, D, X, Y, Z]  block_size=4
         块切分: [A,B,C,D] [X,Y,Z,_]

请求 R1 进入:
  block 0: hash([A,B,C,D], parent=NONE) → H1
  block 1: hash([E,F,_,_], parent=H1)    → H2
  存表: {H1: block_17, H2: block_42}
  block_table[R1] = [17, 42]

请求 R2 进入:
  block 0: hash([A,B,C,D], parent=NONE) → H1  ← 命中！
  复用 block_17，ref_cnt: 1 → 2
  block 1: hash([X,Y,Z,_], parent=H1)    → H3  ← 未命中
  分配新 block_91
  block_table[R2] = [17, 91]
```

R2 节省了**前 4 个 token 的 prefill 计算**。这在多轮对话、Agent 场景里收益巨大——多轮对话中，每轮的”历史对话”都是可共享的前缀。

### 7.4 Hash 函数的演进

vLLM 早期用 Python 内置的 `hash()`，但 Python 的 `hash()` 有随机化（PYTHONHASHSEED）。后来切换到 SHA256 / xxhash / CBOR-hash，可重现且跨进程一致。

在 `vllm/v1/core/kv_cache_utils.py` 中你能看到：

```text
NONE_HASH: BlockHash  # 全局变量，第一个 block 的"父"
_CBOR_HASH_FUNCTIONS = frozenset({sha256_cbor, xxhash_cbor})

def init_none_hash(hash_fn):
    global NONE_HASH
    hash_seed = os.getenv("PYTHONHASHSEED")
    if hash_seed is None and hash_fn in _CBOR_HASH_FUNCTIONS:
        logger.warning("PYTHONHASHSEED is not set. ...")
    NONE_HASH = hash_fn(None)
```

### 7.5 Prefix Caching 的失效场景

Prefix Cache 不是”无脑开”的，以下场景会让它失效或失效更明显：

**场景一：system_prompt 包含动态内容**

```text
# 错误：包含时间戳
system_prompt = f"你是一个助手。现在是 {datetime.now()}"

# 正确：保持静态
system_prompt = "你是一个助手"
```

**场景二：prefill chunk 和 prefix cache 的对齐**

vLLM 的 prefix cache 按 block 对齐，如果 chunk 大小不匹配，可能错过本应命中的前缀。

**场景三：量化/模型变更**

不同量化方案、不同模型版本之间的 KV 不能共享。

**场景四：prefix 长度 < block_size**

如果共享前缀短于一个 block，没法形成完整的 hash，命中率为 0。

### 7.6 Prefix Cache 命中时的”零拷贝”是怎么实现的

一个关键问题：R1 和 R2 共享 block_17，那 block_17 的 K/V 数据怎么被两个请求同时”看到”？

答案是 **CUDA 显存共享 + ref_cnt 引用计数**：

```text
block_17 物理内存中的 K/V 数组
  ↑
  ├── block_table[R1] = [17, 42, ...]
  └── block_table[R2] = [17, 91, ...]
  
block_17.ref_cnt = 2
```

GPU 上看到的就是同一个 `block_id=17`，两个请求的 GPU kernel 在加载 K/V 时都访问同一块显存。**完全零拷贝**。

R1 结束时不会真的释放 block_17（ref_cnt 变成 1）；R2 也结束时（ref_cnt 变成 0），block_17 才进入 free list。

### 九、和 FlashAttention 的关系：补充说明

我用了大篇幅讲 PagedAttention 自己的 kernel，但读者一定会问：**它和 FlashAttention 什么关系？** 我们专门用一节澄清。

### 9.1 FlashAttention 解决了什么

FlashAttention（Tri Dao 等人，2022）解决的是**单个 attention 计算的访存效率问题**：

- 标准 attention 要把 `[seq_len, seq_len]` 的 attention matrix 物化在 HBM（高带宽显存）
- seq_len=4096 时，attention matrix = 4096×4096×4bytes = 64MB
- 大量 HBM 读写导致 attention 慢

FlashAttention 的核心思想：

- 不物化完整的 attention matrix
- 把 Q、K、V 分成 tile，每次只算一个 tile 的 attention
- 用 online softmax 累加，最终输出和标准 attention 完全一致
- 通过减少 HBM 读写，加速 2-4 倍

### 9.2 PagedAttention 解决了什么

PagedAttention 解决的是**多个请求共享同一块 GPU 时的显存管理问题**：

- 不同请求需要不同长度的 KV 空间
- 连续分配导致碎片严重
- 需要把 K、V “分页”以便共享和回收

### 9.3 两者是互补的

```text
PagedAttention = 分页显存管理 + 高效 attention 计算
                       ↑                  ↑
                Block Table        FlashAttention 算法
```

在 vLLM 中，PagedAttention 的”分页”机制负责管理物理显存布局，FlashAttention 的”tiling + online softmax”负责高效计算。**vLLM 的现代实现把这俩结合在一起**——这是 vLLM 0.5 之后最关键的架构改进。

### 9.4 一个常见的误解

> “PagedAttention 是 FlashAttention 的替代品”

错。两者是不同维度的优化，解决的是不同问题。在 vLLM 中，**PagedAttention 用到了 FlashAttention 风格的算法**，但**PagedAttention 本身**指的是**分页管理**这一层。

### 十、源码导读：跟踪一次 PagedAttention 调用

这一节我们跟随一次具体的推理调用，看 vLLM 代码里 PagedAttention 是怎么被用上的。

### 10.1 调用栈概览

```text
vllm/v1/worker/gpu_model_runner.py::execute_model()
    ↓
vllm/model_executor/layers/attention.py::Attention.forward()
    ↓
vllm/v1/attention/backends/flash_attn.py::FlashAttentionBackend.forward()
    ↓
[CUDA kernel] vllm_flash_attn::flash_attn_varlen_func()
    ↓
GPU 上的 PagedAttention kernel（带 block_table 间接寻址）
```

### 10.2 关键代码片段

**第一站：ModelRunner 准备 SchedulerOutput**

```text
# vllm/v1/worker/gpu_model_runner.py
def execute_model(self, scheduler_output):
    # 1. 把 scheduler 的输出转换成模型输入
    # 2. 准备 block_table（每个请求的物理 block 列表）
    block_table_tensor = self._prepare_block_table(scheduler_output)
    # block_table_tensor: [num_reqs, max_blocks] int32 tensor
    
    # 3. 调 model forward
    hidden_states = self.model(
        input_ids=...,
        positions=...,
        block_table=block_table_tensor,
    )
```

**第二站：Attention 层使用 block_table**

```text
# vllm/model_executor/layers/attention.py
class Attention(nn.Module):
    def forward(self, positions, hidden_states, block_table):
        # 1. Q、K、V 投影
        q = self.q_proj(hidden_states)
        k = self.k_proj(hidden_states)
        v = self.v_proj(hidden_states)
        
        # 2. rotary embedding 等位置编码
        q, k = self.rotary_emb(positions, q, k)
        
        # 3. 调 attention backend
        attn_output = self.attn_backend.forward(
            q=q, k=k, v=v,
            block_table=block_table,  # ★ 关键：传入 block_table
            ...
        )
        
        return attn_output
```

**第三站：FlashAttention backend 调 kernel**

```text
# vllm/v1/attention/backends/flash_attn.py
class FlashAttentionBackend:
    def forward(self, q, k, v, block_table, ...):
        # 调用 vllm_flash_attn 的 PagedAttention 入口
        output = flash_attn_varlen_func(
            q=q,
            k_cache=self.k_cache,    # 所有 block 共享的 K 缓存
            v_cache=self.v_cache,    # 所有 block 共享的 V 缓存
            block_table=block_table, # ★ 物理 block 列表
            cu_seqlens_q=...,
            cu_seqlens_k=...,
            max_seqlen_q=...,
            max_seqlen_k=...,
            ...
        )
        return output
```

**第四站：CUDA kernel 内部**

进入 `flash_attn_varlen_func`，内部调用 PagedAttention kernel：

```text
// csrc/attention/attention_kernels.cuh（简化版）
__global__ void paged_attention_kernel(
    const T* q,
    const T* k_cache,    // [num_blocks, block_size, num_kv_heads, head_size]
    const T* v_cache,    
    const int* block_table,  // [batch, max_blocks]
    ...
) {
    // 每个 thread block 处理一个 (batch, head, kv_block) 的子任务
    const int batch_idx = blockIdx.z;
    const int head_idx = blockIdx.x;
    const int kv_head_idx = head_idx / group_size;
    
    // 1. 加载这个请求的 block_table
    const int* req_block_table = block_table + batch_idx * max_blocks;
    
    // 2. 加载 Q（一个 token）
    // ...
    
    // 3. 遍历 KV blocks
    for (int kv_block_idx = 0; kv_block_idx < num_kv_blocks; kv_block_idx++) {
        // ★ 通过 block_table 间接寻址
        const int physical_block_id = req_block_table[kv_block_idx];
        
        // 加载 K、V 块（16 token）
        // ...
        
        // 计算这个 block 的 attention 子结果
        // ... (online softmax 累加)
    }
    
    // 4. 写回输出
}
```

**这就是 PagedAttention 在 GPU 上的全部秘密**：在循环里通过 block_table 算物理地址，然后做标准 attention。

### 10.3 数据流图

```text
请求 R 的 KV 数据生命周期:

输入 tokens: [T0, T1, ..., T49]  (50 tokens)
              ↓
Tokenizer + Embedding
              ↓
Model.forward() 时:
  1. Prefill 阶段: 把 K、V 写入 K_cache[17], V_cache[17]（block 0, 16 token）
                   把 K、V 写入 K_cache[42], V_cache[42]（block 1, 16 token）
                   把 K、V 写入 K_cache[8],  V_cache[8]  (block 2, 16 token)
                   把 K、V 写入 K_cache[91], V_cache[91] (block 3, 2 token + 14 空)
                   
  2. Decode 阶段: 每生成一个新 token，分配/复用 block，block_table 更新
                   [17, 42, 8, 91, ?, ?, ...]
                   
  3. Attention 计算: 
     - GPU kernel 收到 block_table = [17, 42, 8, 91]
     - 循环中：物理地址 = K_cache + 17*16*128*128*sizeof(half)
     - 物理地址 = K_cache + 42*16*128*128*sizeof(half)
     - 物理地址 = K_cache +  8*16*128*128*sizeof(half)
     - 物理地址 = K_cache + 91*16*128*128*sizeof(half)
     - 加载每个 block 的 K、V，做 attention
```

### 十一、完整的 PagedAttention 数据流（Mermaid 图）

```text
flowchart TB
    A[请求 R 进入] --> B[Tokenizer 转 token IDs]
    B --> C[Scheduler 检查显存]
    C -->|充足| D[KVCacheManager 分配 N 个 block]
    C -->|不足| E[抢占低优先级请求]
    
    D --> F[建立 Block Table: R → block_ids]
    F --> G[Prefix Cache 查找]
    G -->|命中| H[复用 block, ref_cnt++]
    G -->|未命中| I[从 Free List 分配新 block]
    
    H --> J[Block Table: R → 17, 42, ...]
    I --> J
    
    J --> K[Model Forward]
    K --> L[Attention 层]
    L --> M[FlashAttention Backend]
    M --> N[GPU PagedAttention Kernel]
    
    N --> O[循环遍历 block_table]
    O --> P[通过 block_table 间接寻址]
    P --> Q[加载 K/V 块到 Shared Memory]
    Q --> R[Block 内连续 Attention 计算]
    R --> S[Online Softmax 合并]
    S --> T[输出 attention 结果]
    
    U[请求结束] --> V[释放 Block]
    V --> W[ref_cnt 减 1]
    W -->|ref_cnt=0| X[Block 回到 Free List]
    W -->|ref_cnt>0| Y[保留给其他请求共享]
```

### 十二、进阶话题：Multi-Group 与异构 Block Size

vLLM v1 架构支持**多个 KV cache group**——这在混合模型（如 Encoder-Decoder）、不同注意力类型（Full Attention + Sliding Window）时特别重要。

### 12.1 什么是 KV Cache Group

vLLM v1 的设计允许一个请求对应**多组** KV Cache：

- **Group 0**：Full Attention（主语言模型）
- **Group 1**：Sliding Window Attention（短上下文注意力）
- **Group 2**：Cross Attention（Encoder-Decoder 模型用）

每个 group 有自己的 block table、自己的 block size、自己的物理 block 池。

### 12.2 异构 Block Size 的实现

在 `vllm/v1/kv_cache_interface.py` 中：

```text
class FullAttentionSpec(KVCacheSpec):
    block_size: int  # 通常 16
    
class SlidingWindowSpec(KVCacheSpec):
    block_size: int  # 可能更小，比如 4
```

不同 group 的 block 可以有不同 size。这让 vLLM 能精细优化不同注意力类型的显存使用。

### 12.3 Block Pool 的管理

`vllm/v1/core/block_pool.py` 中管理每个 group 的物理 block pool：

```text
class BlockPool:
    # Free blocks for this group
    free_block_ids: deque[int]
    # Cached blocks (prefix cache candidates)
    cached_blocks: dict[BlockHash, KVCacheBlock]
```

多 group 共享一个 KVCacheManager，但每个 group 有自己的 BlockPool。这种设计让 vLLM 成为一个”通用”的推理运行时——不只支持 dense LLM，还能支持 MoE、Encoder-Decoder、Multimodal 等复杂模型。

### 十五、总结

PagedAttention 是 vLLM 的灵魂设计。它把”操作系统虚拟内存”的思想搬到了 GPU KV Cache 管理上：

- **逻辑连续、物理分散**：Block Table 维护映射
- **按需分配、按页回收**：Free List + Ref Count
- **零拷贝共享**：Prefix Cache + Block Hash
- **高效 attention 计算**：与 FlashAttention 融合

这套设计让 vLLM 实现了：

- 显存利用率从 20-40% 提升到 80-95%
- 最大并发提升 4-6 倍
- P99 TTFT 下降 85%

但 PagedAttention 不是终点。下一篇我们会讲 **vLLM v1 架构总览**——Scheduler、KVCacheManager、ModelRunner 怎么协作，Continuous Batching 和 Chunked Prefill 在调度层怎么实现。

### 附录 A：PagedAttention 与传统方案的内存布局对比图

### 传统连续分配方案

```text
GPU 显存（320 GB 总，A100-80G × 4）
├── 模型权重（140 GB）
├── 连续 KV Cache 区（160 GB）
|   |-- 请求 A：[0, 2048] = 20 GB  ← 实际只用 512 token，但预留 2048
|   |-- 请求 B：[2048, 4096] = 20 GB  ← 实际只用 1024 token，预留 2048
|   |-- 请求 C：[4096, 6144] = 20 GB  ← 实际只用 256 token
|   |-- 请求 D：[6144, 8192] = 20 GB
|   |-- 请求 E：[8192, 10240] = 20 GB
|   |-- 请求 F：[10240, 12288] = 20 GB
|   |-- 请求 G：[12288, 14336] = 20 GB  ← 实际只用 1024
|   `-- 请求 H：[14336, 16384] = 20 GB
`-- 空闲区（20 GB）  ← 没人用，但也不够装新请求
```

特点：8 个请求占据 160GB，但实际只用了约 30GB 的数据量。

### PagedAttention 分页方案

```text
GPU 显存（320 GB）
|-- 模型权重（140 GB）
|-- 物理 Block 池（160 GB）
|   |-- Free List（空闲 block 列表）
|   |   |-- block_0, block_5, block_9, ...  ← 可分配
|   |   `-- ...（约 2000 个空闲 block）
|   `-- 已分配 block（通过 block_table 关联到请求）
|       |-- 请求 A 的 block：[17, 42, 8, 91]    ← 实际 4 个 block
|       |-- 请求 B 的 block：[23, 56, 71, 102]  ← 实际 4 个 block
|       |-- 请求 C 的 block：[33, 89, 12, 67, 5, 99]  ← 实际 6 个 block
|       |-- 请求 D 的 block：[14, 78, 33, 2]   ← block_33 被 D 共享
|       `-- ...（约 200 个并发请求）
`-- 空闲区（20 GB）  ← 真正的未使用显存
```

特点：200+ 个请求同时运行，160GB 的 block 池被几乎用满，每个 block 装满或几乎装满。

### 附录 B：手写一个最小 PagedAttention 模拟器

为了让你真正理解 block_table 怎么工作，我们用 Python 写一个最简模拟器。

```text
from collections import deque
from typing import Optional
import hashlib

class KVCacheBlock:
    def __init__(self, block_id: int):
        self.block_id = block_id
        self.ref_cnt = 0
        self.block_hash = None
        self.tokens = []

class MiniPagedAttention:
    def __init__(self, num_blocks, block_size):
        self.block_size = block_size
        self.free_block_ids = deque(range(num_blocks))
        self.all_blocks = {i: KVCacheBlock(i) for i in range(num_blocks)}
        self.req_to_blocks = {}
        self.hash_to_block = {}

    def compute_block_hash(self, tokens, parent_hash):
        h = hashlib.sha256()
        h.update(parent_hash or b"NONE")
        h.update(bytes(tokens))
        return h.digest()

    def allocate_request(self, req_id, tokens):
        blocks = []
        parent_hash = None
        num_blocks_needed = (len(tokens) + self.block_size - 1) // self.block_size
        for i in range(num_blocks_needed):
            start = i * self.block_size
            end = min(start + self.block_size, len(tokens))
            block_tokens = tokens[start:end]
            block_hash = self.compute_block_hash(block_tokens, parent_hash)
            if block_hash in self.hash_to_block:
                cached_block = self.hash_to_block[block_hash]
                cached_block.ref_cnt += 1
                blocks.append(cached_block)
                print(f"  [PREFIX HIT] block {cached_block.block_id}")
            else:
                if not self.free_block_ids:
                    self._rollback(blocks)
                    return None
                block_id = self.free_block_ids.popleft()
                block = self.all_blocks[block_id]
                block.ref_cnt = 1
                block.block_hash = block_hash
                block.tokens = block_tokens
                blocks.append(block)
                self.hash_to_block[block_hash] = block
                print(f"  [ALLOC] block {block_id}")
            parent_hash = block_hash
        self.req_to_blocks[req_id] = blocks
        return [b.block_id for b in blocks]

    def free_request(self, req_id):
        if req_id not in self.req_to_blocks:
            return
        for block in self.req_to_blocks[req_id]:
            block.ref_cnt -= 1
            if block.ref_cnt == 0:
                self.free_block_ids.append(block.block_id)
        del self.req_to_blocks[req_id]

    def _rollback(self, blocks):
        for block in blocks:
            block.ref_cnt -= 1
            if block.ref_cnt == 0:
                self.free_block_ids.append(block.block_id)

if __name__ == "__main__":
    pa = MiniPagedAttention(num_blocks=100, block_size=4)
    system_prompt = [101, 102, 103, 104, 201, 202, 203, 204]
    print("=== 请求 1 进入 ===")
    pa.allocate_request("req1", system_prompt + [1, 1, 1, 1])
    print("=== 请求 2 进入（前缀应该全部命中）===")
    pa.allocate_request("req2", system_prompt + [2, 2, 2, 2])
    print("=== 请求 3 进入（前缀应该全部命中）===")
    pa.allocate_request("req3", system_prompt + [3, 3, 3, 3])
```

运行结果：

```text
=== 请求 1 进入 ===
  [ALLOC] block 0
  [ALLOC] block 1
  [ALLOC] block 2
=== 请求 2 进入（前缀应该全部命中）===
  [PREFIX HIT] block 0
  [PREFIX HIT] block 1
  [ALLOC] block 3
=== 请求 3 进入（前缀应该全部命中）===
  [PREFIX HIT] block 0
  [PREFIX HIT] block 1
  [ALLOC] block 4
```

这个 100 行的 Python 代码浓缩了 PagedAttention + Prefix Caching 的全部数据结构设计。

### 附录 C：PagedAttention 的限制与未来

讲完优点，也要诚实讲它的限制：

**限制一：Block Size 仍是硬参数**

虽然 16 是个不错的默认，但对极端场景（超长序列、极致碎片敏感）仍然不够灵活。未来方向：

- 可变的 block size：不同请求用不同 block size
- 细粒度分页：block 内再分子块

**限制二：Prefix Cache 的假命中**

如果两个请求的逻辑前缀相同但语义前缀不同，prefix cache 仍会命中。例如 system_prompt 中间一个 token 改了，prefix cache 可能会错误地延续之前的命中。

**限制三：跨节点的 Prefix Cache**

vLLM 0.6+ 引入了 LMCache（外部 prefix cache 层），让多节点共享 prefix cache。但 LMCache 还在早期，实现复杂，性能不一定稳定。

**限制四：KV Cache 本身的显存压力**

PagedAttention 让”分配”高效，但 K、V 数据本身仍占大量显存。未来方向：

- KV Cache 量化（KIVI、KVQuant）
- 不活跃请求的 KV 卸载到 CPU/NVMe

### 附录 D：常见问题 FAQ

**Q1：PagedAttention 适合所有 LLM 吗？**

适合大多数 dense Transformer（GPT、LLaMA、Qwen 等）。对于 MoE（Mixtral、DeepSeek-V2 等），PagedAttention 同样适用，因为 KV Cache 部分是 dense 的。

**Q2：vLLM 的 PagedAttention 跟论文完全一致吗？**

v0.1 - v0.4 是论文的直接实现。v0.5+ 做了大量工程优化：嫁接 FlashAttention、支持更多 dtype（FP8、INT8）、多 KV cache group、异构 block size。但核心思想没变：分页、block table、prefix cache。

**Q3：开启 prefix caching 后，TTFT 一定能降低吗？**

不一定。如果你的请求前缀都不共享（比如每个请求都是独立问题），prefix caching 反而会引入额外 hash 计算开销。建议根据实际命中率决定是否启用。

**Q4：Block Size 选 8 比选 16 一定更好吗？**

不一定。block_size 小意味着元数据开销大、kernel launch overhead 占比高。需要在碎片率和元数据开销间找平衡。16 是大量实验后的甜点。

**Q5：vLLM 早期版本（v0.1 - v0.4）还能用吗？**

可以用，但已停止维护。建议升级到最新版本。v1 架构（v0.7+）是当前主线。

**Q6：为什么不用操作系统真的虚拟内存机制？**

GPU 显存不是 OS 管理的——它是 CUDA 显存，由 vLLM 直接管理。PagedAttention 是借鉴操作系统的思想，但在 GPU 上重新实现。
