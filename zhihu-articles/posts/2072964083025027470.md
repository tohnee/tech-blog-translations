最近系统地梳理了一遍大模型推理系统——vLLM、SGLang、KV Cache、Prefix Caching、PD 分离、RDMA、分层存储——梳理完之后，一个感受越来越强烈：

> **大模型推理优化的核心，很多时候并不是”把计算做得更快”，而是让数据更少搬、更近、更有效地复用。**

如果把 GPU 看成一座算力极强的工厂，那么 KV Cache 就是它旁边那个越来越大的”半成品仓库”。模型越大、上下文越长、并发越高，这个仓库越容易成为真正的瓶颈。

从 KV Cache 出发，可以把整条推理系统的链路串起来：

> **Attention → KV Cache → PagedAttention → Prefix Caching → Cache-aware Scheduling → PD Disaggregation → RDMA → HBM / DRAM / NVMe → 分布式 KV Cache Service**

这条链路，也是理解现代 LLM 推理系统非常好的入口。

### 一、为什么 Decode 阶段越来越像”内存系统”问题？

先回到 Attention 本身：

$$ \mathrm{Attention}(Q,K,V)=\mathrm{softmax}\!\left(\frac{QK^{T}}{\sqrt{d}}\right)V $$

**Prefill 阶段**一次处理成百上千个 token，矩阵规模大、算术强度高，Tensor Core 能被喂饱，是典型的 compute-bound。

**Decode 阶段**则完全是另一回事。假设已经有 10000 个 token：

```text
已有 tokens:
t1 t2 t3 ... t10000

现在生成:
t10001
```

新 token 只产生一个 Q：

```text
Q10001
```

但它必须和此前所有 token 的 K、V 做 Attention：

```text
K1 ... K10000
V1 ... V10000
```

于是数据流变成这样：

![](https://picx.zhimg.com/v2-d475477c26af033745d2ccbb5938fea3_r.jpg)

**每生成一个 token，都要把巨大的 KV Cache 完整读一遍**，而真正的计算量却只有一行向量与矩阵相乘。算术强度极低。

所以 Decode 的瓶颈通常不是：

> GPU 算力不够。

而是：

> **GPU 在等数据。**

这就是 LLM Decode 天然 memory-bandwidth bound 的根本原因。

### 二、KV Cache 到底有多大？

单个请求的 KV Cache 大小可以粗略估算为：

$$ \text{Size} = 2 \times L \times S \times H_{KV} \times D \times \text{Bytes} $$

| 符号 | 含义 |
| --- | --- |
| L | Transformer 层数 |
| S | 序列长度 |
| H_{KV} | KV head 数（GQA/MQA 下远小于 Q head 数） |
| D | head dimension |
| 2 | K 与 V 两份 |
| Bytes | 数据类型字节数（FP16 = 2，FP8 = 1） |

代入一组典型配置：

```text
Layers       = 80
Sequence     = 128K
KV heads     = 8
Head dim     = 128
dtype        = FP16
```

计算得：

```text
2 × 80 × 131072 × 8 × 128 × 2 Bytes
≈ 43 GB
```

也就是说：

> **一个 128K 上下文的请求，KV Cache 就可能吃掉几十 GB。**

只要同时存在十几个长上下文请求，KV Cache 立刻超出单卡 HBM 容量。这也是为什么今天的 KV Cache 已经不能再被简单理解为：

```text
request → 一块 GPU 显存
```

它越来越像一个独立的内存系统。

### 三、为什么 vLLM 要做 PagedAttention？

最朴素的 KV Cache 管理方式是给每个请求分配一整块连续显存：

```text
Request A → 一整块连续显存
Request B → 一整块连续显存
Request C → 一整块连续显存
```

但 LLM 请求有一个绕不开的特点：

> **序列长度是动态增长的，而且事先不知道会长到多少。**

```text
Request A
开始：1000 tokens

生成之后：
1001
1002
1003
...
```

要求连续存储，就必然带来：

- 内存碎片
- 按最大长度预留造成的浪费
- 动态扩容困难
- 请求之间无法共享

**PagedAttention 的做法是把 KV Cache 切成固定大小的 Block**，并用一张 Block Table 把逻辑位置映射到物理位置——本质上就是操作系统的分页机制。

以 vLLM 默认的 block size = 16 为例：

```text
Token 0~15     → Block 0
Token 16~31    → Block 1
Token 32~47    → Block 2
Token 48~63    → Block 3
Request
   │
   ├── Block 0
   ├── Block 1
   ├── Block 2
   └── Block 3
```

物理上这些 Block 可以散落在显存的任意位置，Attention kernel 通过 Block Table 间接寻址即可。

这里特别容易产生一个误解：

> **“16 个 token 是不是就是一个 request？”**

不是。16 只是一个 Block 的逻辑粒度。一个 request 可以由上百个 Block 组成；反过来，同一个 Block 也可能被多个 request 通过 Prefix Caching 共享。

### 四、Prefix Caching：KV Cache 真正开始”复用”

看两个请求：

```text
Request A                 Request B
─────────────             ─────────────
System Prompt             System Prompt
100K 文档                  100K 文档
问题 A                     问题 B
```

前面那一大段完全相同的 token，没有理由算两遍。

切成 Block 之后：

```text
Request A:                Request B:

Block 0                   Block 0
Block 1                   Block 1
Block 2                   Block 2
Block 3                   Block 3
Block 4                   Block 4
Question A                Question B
```

Block 0~4 可以直接共享，B 的 Prefill 只需要算最后一小段。

于是 KV Block 的身份从：

```text
request_id
```

变成了：

```text
hash(prefix tokens)
        ↓
    KV Block
```

一个容易被忽略的实现细节：**Block 的 hash 必须是前缀链式的**，即

```text
block_hash = H(prev_block_hash, tokens_in_this_block)
```

否则两个内容相同但前文不同的 Block 会被错误地复用——KV 的值依赖于它之前的全部上下文。

vLLM 的 Prefix Caching 与 SGLang 的 RadixAttention 都在回答同一个问题，只是数据结构不同（哈希表 vs. 基数树）：

> **如何识别”已经算过的上下文”，并让新请求直接复用这份计算结果。**

### 五、再往前一步：KV Cache 本质上就是一个 Cache

到这里，一件很有意思的事情发生了。

我们原本把 KV Cache 理解成”推理过程中产生的临时数据”。但 Prefix Caching 出现之后，它已经具备了传统 Cache 的全部要素：

```text
Key            Value
 ↓               ↓
prefix hash → KV Block
```

于是所有经典缓存问题会原封不动地找上门：

- 什么时候淘汰？
- 哪些 Block 最值得保留？
- 哪些 Block 最可能被再次使用？
- HBM 满了怎么办？
- 能不能跨请求共享？
- 能不能跨 GPU 共享？
- 能不能跨节点共享？

这一刻起，KV Cache 就从”模型实现细节”变成了”系统设计问题”。

### 六、HBM 不够怎么办？分层存储

最直接的方案是往下溢出：

```text
HBM → DRAM
```

DRAM 也不够，就继续往下：

```text
HBM → DRAM → NVMe
```

形成三级存储：

![](https://pic3.zhimg.com/v2-f62f3afab6aa73b07094f7e0af3b59b8_r.jpg)

这个结构和操作系统的虚拟内存几乎是一一对应的：

```text
操作系统                    KV Cache
─────────────              ─────────────
Virtual Memory             Context
      ↓                          ↓
    Page                     KV Block
      ↓                          ↓
     RAM                        HBM
      ↓                          ↓
    Disk                    DRAM / NVMe
```

某种意义上：

> **KV Cache Block 就是 LLM 推理系统里的 “Page”。**

### 七、于是就有了 KV Cache 版的 Page Fault

假设 Block 123 此刻躺在 NVMe 上，而新请求恰好需要它：

```text
GPU
 ↓
HBM 未命中
 ↓
查 DRAM
 ↓
未命中
 ↓
查 NVMe
 ↓
命中 Block 123
```

然后逐级搬回来：

```text
NVMe → DRAM → HBM → GPU Attention
```

这就是一次 Page Fault。

但 LLM 推理**不能真的像操作系统那样”缺页了再慢慢读”**：Decode 的单步预算只有几毫秒甚至更短，一次同步的 NVMe 读取足以把整批请求的 TPOT 拖垮。

所以必须再进一步：

> **Prefetch。**

### 八、Prefetch：趁 GPU 在算的时候搬数据

假设 GPU 正在处理 Block 10，而系统已经知道接下来大概率要用 Block 11、12、13，那么就可以让搬运和计算重叠：

```text
GPU:     [Compute 10][Compute 11][Compute 12]

Memory:            [Load 11]
                             [Load 12]
                                       [Load 13]
```

也就是：

> **计算与数据搬运并行，用计算时间把 I/O latency 藏起来。**

在 PD 分离的场景里，这个思路还有一个更漂亮的版本：**KV 传输可以按 layer 流水化**——Prefill 节点算完第 0 层就立刻开始传第 0 层的 KV，而不是等整个 Prefill 结束再一次性发送。

因此一个成熟的 KV Cache 系统需要的是完整的数据流动策略：

```text
Promotion   （冷 → 热）
Demotion    （热 → 冷）
Prefetch    （提前搬）
Eviction    （腾空间）
```

而不只是：

```text
put()
get()
```

### 九、那到底该淘汰谁？

假设 HBM 共 80 GB，已用 78 GB，此时来了一个需要 10 GB 的长上下文请求——必须淘汰一批 Block。

最简单的策略是 LRU：

> 最久没有被访问的 Block 优先淘汰。

但对 KV Cache 来说，纯 LRU 未必够用：

```text
Block A：刚刚被访问 1 次
Block B：历史上被访问 10000 次，但几秒钟没动了
```

A 可能只是偶然命中；B 很可能是一个被全站共享的 System Prompt，淘汰它的代价要大得多。

所以可以给淘汰引入一个综合评分：

$$ \text{EvictionScore} = \alpha \cdot \text{Recency} + \beta \cdot \text{Frequency} + \gamma \cdot \text{RefCount} + \delta \cdot \text{ReloadCost} $$

- **Recency**：最近访问时间
- **Frequency**：访问频率
- **RefCount**：当前有多少请求正在引用
- **ReloadCost**：重新加载 / 重新计算的代价

另外还有一个 KV Cache 特有的约束：**同一条前缀链上的 Block 存在依赖关系**。淘汰中间某个 Block 会让它后面的所有 Block 失去复用价值，所以淘汰通常应该从前缀树的叶子往根做，而不是随意挑选。

到这一步，它已经是一个货真价实的缓存系统了。

### 十、RefCount 很关键：不能淘汰正在被使用的 KV

这是工程实现中最容易出 bug 的地方。

```text
Request A
   ↓
正在 Decode
   ↓
使用 Block 123
```

如果此时 Cache Manager 只看到”Block 123 很久没被访问”就把它换出到 DRAM，Request A 下一步就会访问到一块已经失效的显存——轻则结果错乱，重则直接崩溃。

因此每个 Block 至少需要携带一组元数据：

```text
Block 123
├── hash
├── location      (HBM / DRAM / NVMe)
├── size
├── ref_count
├── access_count
├── last_access
└── state
```

只有当：

```text
state     = IN_USE
ref_count = 1
```

变成：

```text
ref_count = 0
state     = EVICTABLE
```

之后，它才能进入淘汰候选集合。

这也说明：一个真正的 KV Cache 系统，远不只是”写几个 tensor”，它需要完整的

> **生命周期管理。**

### 十一、PD 分离让问题进一步复杂

现代推理系统还有一个重要架构：

> **Prefill-Decode Disaggregation（PD 分离）**

原因在于两个阶段的计算特征完全相反：

|  | Prefill | Decode |
| --- | --- | --- |
| 输入 | 长序列，一次性 | 每次一个 token |
| 特征 | 大矩阵运算 | 反复读取 KV |
| 瓶颈 | Compute-bound | Memory-bound |
| 关键指标 | TTFT | TPOT |

把它们混在同一批里，长 Prefill 会周期性地阻塞 Decode，尾延迟很难控制。于是拆开：

```text
                Request
                   │
                   ↓
            ┌──────────────┐
            │   Prefill    │
            │    Nodes     │
            └──────┬───────┘
                   │
                KV Cache
                   │
                   ↓
            ┌──────────────┐
            │    Decode    │
            │    Nodes     │
            └──────────────┘
```

新问题立刻出现：

> Prefill 节点产生的 KV，怎么送到 Decode 节点？

如果走传统路径：

```text
GPU → CPU → Network → CPU → GPU
```

会产生大量无谓的拷贝和额外延迟。所以现代系统普遍采用：

```text
GPU HBM
   ↓
GPUDirect RDMA
   ↓
  NIC
   ↓
Network
   ↓
  NIC
   ↓
GPU HBM
```

这也是为什么做 KV Cache 的人，最后都得去理解这些看起来和 Transformer 毫无关系的东西：

- RDMA / GPUDirect RDMA
- PCIe 拓扑
- NUMA
- NIC affinity
- memory registration

### 十二、Cache-Aware Scheduling：调度器也必须懂 Cache

传统调度器只看负载：

```text
GPU 0：负载 70%
GPU 1：负载 40%
GPU 2：负载 80%
```

按这个逻辑，请求会被丢给 GPU 1。

但如果实际情况是：

```text
GPU 0：已缓存该请求 80% 的 prefix
GPU 1：完全没有缓存
```

那么把请求送到 GPU 0，省下来的 Prefill 计算可能远远超过那 30% 负载差带来的损失。

于是调度目标从：

```text
Load Balancing
```

变成：

```text
Load Balancing + Cache Locality
```

可以构造一个简单的打分函数：

$$ \text{Score} = \alpha \cdot \text{CacheHit} - \beta \cdot \text{HBMUsage} - \gamma \cdot \text{QueueLength} + \delta \cdot \text{Priority} $$

调度流程也随之变化：

```text
Request
   ↓
Prefix Hash
   ↓
查询各 GPU 的 Cache 命中情况
   ↓
GPU 0：80% hit
GPU 1：10% hit
GPU 2： 0% hit
   ↓
优先 GPU 0
```

这就是 **Cache-Aware Scheduling**。它和 CPU Cache 亲和性调度、NUMA-aware 调度、大数据里的数据本地性调度，思想完全同源。

### 十三、最终，KV Cache 可以独立成一个服务

如果 KV Cache 永远绑死在推理进程里：

```text
vLLM
 └── KV Cache
```

那么：

```text
vLLM 挂掉 → KV Cache 全部消失
```

而且不同实例之间无法共享，扩缩容时缓存要从头预热。

自然的演进方向是把它抽出来：

```text
                Scheduler
                      │
          ┌───────────┴───────────┐
          ↓                       ↓
       Prefill                  Decode
          │                       │
          └──────────┬────────────┘
                     ↓
              KV Cache Service
                     │
          ┌──────────┼──────────┐
          ↓          ↓          ↓
         HBM        DRAM       NVMe
```

对外提供一组类似存储系统的接口：

```text
PUT
GET
EVICT
PREFETCH
MIGRATE
REPLICATE
```

这样：

```text
vLLM
SGLang
自研推理引擎
其他 inference runtime
```

都能共享同一套 KV Cache 基础设施。Mooncake、LMCache、NVIDIA Dynamo 等项目，走的都是这个方向；vLLM 也已经把 KV Connector 抽象成了可插拔的接口。

到这一步，KV Cache 已经不再是：

> 推理引擎里的一个 tensor。

而是：

> **LLM 推理基础设施中的一种分布式缓存资源。**

### 十四、为什么我觉得 KV Cache 是个很好的系统研究方向

只看 Transformer 的时候，世界是这样的：

```text
模型 → Attention → 生成 token
```

但把推理系统做大之后，真实的地图长这样：

![](https://picx.zhimg.com/v2-15c40fa5fb5f31ce7b17237772bd83e9_r.jpg)

它同时牵扯到：

Transformer、GPU 架构、CUDA、内存管理、分布式系统、网络、存储、调度、缓存策略。

一个很典型的交叉领域。

### 十五、现代 LLM 推理优化，其实是在回答四个问题

### 1. 能不能少算？

```text
Prefix Caching
Speculative Decoding
Context Reuse
```

> 算过的东西不要再算。

### 2. 能不能少搬？

```text
FlashAttention
PagedAttention
Kernel Fusion
Memory Layout Optimization
```

> 数据搬运往往比计算更贵。

### 3. 能不能把数据放在正确的位置？

```text
HBM / DRAM / NVMe
NUMA-aware / GPU-aware / Cache-aware
```

> 热数据靠近计算，冷数据远离计算。

### 4. 能不能让不同节点共享？

```text
RDMA
PD Disaggregation
Distributed KV Cache
```

> 不要让每个实例重复保存、重复计算、重复搬运同一份数据。

### 十六、未来的推理系统，可能越来越像”数据库 + 操作系统”

这是我梳理完 KV Cache 之后最强烈的感受。

传统视角关注的是：

```text
GPU / CUDA / Tensor Core / Attention
```

但随着上下文从 4K → 32K → 128K → 1M+，并发不断上升，系统需要回答的问题变成了：

> 数据在哪里？谁在使用？谁应该复用？谁应该淘汰？ 什么时候预取？从哪里搬？搬到哪里？ 哪个 GPU 最适合执行这个请求？跨节点怎么传？节点挂了怎么办？

这些已经不是模型问题，而是彻头彻尾的**系统问题**——它的形态越来越接近：

```text
Database + Operating System + Distributed Cache + GPU Runtime
```

### 结语

如果只学 Transformer，很容易停在：

```text
QKV → Attention → FFN → Transformer
```

但真正走进推理系统，会看到另一张完全不同的地图：

```text
Transformer
   ↓
KV Cache
   ↓
PagedAttention
   ↓
Prefix Cache
   ↓
Block Manager
   ↓
Cache-aware Scheduler
   ↓
PD Disaggregation
   ↓
RDMA
   ↓
HBM / DRAM / NVMe
   ↓
Distributed KV Cache
```

这条路线把**算法、GPU、内存、网络、存储、分布式系统和调度**全部串了起来。

而这恰恰是今天 LLM Systems 最有意思的地方：

> **大模型推理的下一阶段，可能不只是让 GPU 算得更快，而是让整个系统知道——什么数据值得保存、什么数据值得复用，以及什么数据应该在什么时候、以什么代价、移动到什么地方。**

从这个角度看，KV Cache 早已不只是 Transformer 的一个缓存。

**它正在成为大模型推理系统的核心数据层。**
