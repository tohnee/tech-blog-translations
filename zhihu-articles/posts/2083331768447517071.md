### 简介

一个大型语言模型由两个文件组成。以 Meta.ai 发布的 Llama2 70B 模型为例，这是 Llama 系列语言模型的第二代产品，拥有 700 亿个参数。Llama2 系列包含多个不同规模的模型，分别是 70 亿、130 亿、340 亿和 700 亿参数的版本。

Llama2 70B 模型受到广泛欢迎，因为它可能是目前最强大的开源权重模型。Meta.ai 发布了模型的权重、架构和相关论文，使得任何人都可以轻松地使用这个模型。 在 Llama2 70B 模型的情况下，它实际上就是文件系统上的两个文件：一个包含参数的文件，以及一段运行这些参数的代码。

这个神经网络实际上是一个下一个词预测网络。您给它一些单词，它就会给出下一个单词。从训练中得到的结果实际上是一种神奇的工具，因为尽管下一个单词预测任务看似简单，但它实际上是一个非常强大的目标。它迫使神经网络学习到大量关于世界的信息，并将这些信息编码在参数中。

### LLM scaling law 规模化定律

随着 **网络中的参数数量（n）** , **训练的文本量（d）** ,预测的准确性提高

事实证明，这些大型语言模型在下一个单词预测任务的准确性方面的表现是一个非常平滑、行为良好且可预测的仅两个变量的函数。你需要知道的是网络中的参数数量（n）和你要训练的文本量（d）。仅给出这两个数字，我们就可以非常有信心地预测你在下一个单词预测任务中将达到的准确度。

### LLM 类型

以 claude 为例，按效果与速度的折衷有 opus、sonnet、haiku 三类模型。所有大模型都接受了海量文本训练，它们都拥有基础的“直觉推理”（System 1）。但 haiku 不具有“逻辑链推导”。为什么同一个架构，能力差这么多？主要有三个原因：

- 参数容量：Opus 的参数规模远大于 Haiku。更大的“神经网络”意味着更宽的“思维带宽”，能同时记住并处理更多的中间变量。小模型在处理第 3 步逻辑时，可能已经把第 1 步的信息“遗忘”在神经元的激活边缘了。
- 训练数据的“深度”：训练 Opus 时，工程师会投入大量高质量的逻辑推理链（Chain-of-Thought）数据进行微调。而 Haiku 的训练更侧重于广泛的常识和流畅对话。
- 计算预算（推理时的耗时）：Opus 在生成每个词时，计算量更大、搜索路径更广。Anthropic 甚至可能利用“自洽性（Self-Consistency）”等技术，让 Opus 在内部生成多条推理路径，再投票选出最优解。Haiku 为了保持速度，通常会砍掉这些“内部纠错”环节。

- tokenization：切分 token
- embedding：将 token 映射到向量空间
- contextualization：根据上下文调整 embedding
- generation：经过输出层生成下一个 token。此处不一定选择概率最大的 token，而是结合概率与随机性，从而生成更多样化的回答

### system prompting

system prompt 可以用于定制模型回应的风格和语气

- 权限：system prompt 拥有最高优先级。即使你在后续的 User Prompt 里试图让它“放弃人设”或“执行非法指令”，模型会优先遵循 System Prompt 的约束，将你的后续指令视为“干扰项”。它是开发者锁定的“上帝模式”。
- 上下文持久性：在注意力机制（Attention）中，System Prompt 通常被单独存放在缓存的最前端（或特殊处理）。它在每一轮生成回答时，都会被模型作为“基础背景”重新激活一次。它会贯穿整个对话生命周期，无论聊多久，AI 永远不会忘记自己的人设。大模型对长文本有“Lost-in-the-Middle（中间迷失）”现象。若只写在 user prompt 开头，随着对话增长可能丢失设定
- 安全：Claude 等模型的对抗训练，会特别强化 System Prompt 中的安全规则。它把“用户的要求）”和“模型的自我认知”在训练逻辑上做了绝对隔离，极大地降低了模型被恶意用户洗脑的概率。

### temperature

temperature 是调用 llm 时可以传入的一个介于 0-1 之间的参数，它影响概率的确切分布。当 temperature=0 时，模型总是选择初试概率更高的词元，当 temperature=1 时，它增加了选择初始概率较低的词元的机会。

- low temperature：适用于确定性、重复性的任务，例如数据分析，代码辅助等
- high temperature：适用于创造性强的任务，例如电影创意、广告营销等

### prompt engineering

- clear & direct： prompt 的第一行是很重要的，用简洁的语言直接写出要完成的任务，带“动词”
- specific：提供一些指导原则(guide lines)或步骤(steps)。复杂问题、批判思考等场景下，可以使用 step 强制模型从更多角度思考。
- 使用 xml 标签包裹结构：可能存在需要插入的大块内容，可以使用 xml 标签包裹（eg. ` mmy code` ）,使结构更清晰
- 提供示例(one-shot,multi-shot prompting):可以单独列出一些需要注意的边缘案例。可以提供选择理想示例的理由

### RAG(retrieval augmented generation)

如果需要分析长文本，直接将 文本拼接在 prompt 可能存在以下问题

- 模型存在硬性的输入文本长度限制
- 文本过长模型效率降低
- 耗时
- 耗 token

RAG:将文本切分成块(chunk),搜索和用户问题相关的块，只将相关的块放入 prompt 中

1.text chunking 对文档分块

- 基于大小(size based)：根据字符长度分块.为了避免分割单词，可以采用“重叠”的方式
- 基于结构(structure based): 根据标题、章节等分块。实践中需要文档是强结构化的
- 基于语义(semantic based):使用 nlp 根据句子的语义相关性切分

2.text embedding

![](https://picx.zhimg.com/v2-65f9a0e074f3f4eb55b9746963101709_r.jpg)

embedding model 选型：Voyage embedding -> normalization ->

3. 创建向量数据库并存入向量

4. 计算用户问题的 embedding

5. 根据用户的问题搜索到相关的 x 块：计算 query 向量与向量库中向量的 cos 相似度

![](https://pic1.zhimg.com/v2-a553c4f80ef5b5066dec02aad2332cca_r.jpg)

优化方案：

- 结合文本检索与语义检索

![](https://pic3.zhimg.com/v2-727f6f4577221931f4b2c43347afd45a_r.jpg)

BM25: best match 25 (表现最好的 25 变种)

![](https://pic3.zhimg.com/v2-102f14de536ceb0257a8c41a8e28d1be_r.jpg)

### prompt cache

模型收到用户请求后，需要先做以下处理。由于这条 prompt 可能和第二轮消息一起传入，这部分计算结果可以先存入缓存，提高效率，降低成本。

1. tokenize 切分 prompt
2. 为每个 token 生成 embedding
3. 根据临近文本增添上下文
4. 产出输出文本

![](https://pic3.zhimg.com/v2-6a84728f5d56484b4e7501490d5e1a04_r.jpg)

- 缓存断点：可以添加多个缓存断点。只要内容不变更，断点所在内容及之前都会被缓存。一般可以在 tool、system prompt 加断点。
- claude 至少 1024 token 才支持缓存

agent 可以组合 tool 来完成各种各样的任务。通常这些 tool 都是很通用抽象的。例如 claude 支持的 tool 如下：

- bash
- glob：find file
- grep
- ls: list file
- read
- write
- edit
- WebFetch

### environment inspection

环境检查，指智能体在行动前或行动过程中，主动查询、探测、读取运行环境的信息，以便理解当前状态、可用资源、约束条件和行动后果。例如，定时截图、验证。
