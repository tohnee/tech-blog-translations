做了十多年游戏客户端和引擎开发，最近开始学习 AI，也在补 CUDA。为了理解 LLM 推理中的计算和访存，我把几个常见算子手写了一遍：matmul、softmax、LayerNorm，最后是一个采用 FlashAttention 思路的 attention kernel。

这次跑出来的结果很有意思：

**Nsight Compute 实测 DRAM 读写量从约 503 MB 降到 21 MB，减少到原来的约 1/24；但 attention 整段 GPU 耗时只从 20.46 ms 降到 10.62 ms，加速约 1.9 倍。**

减少了这么多显存访问，为什么没有换来同等幅度的加速？

继续看 profiler，两个值得优先处理的问题浮了出来：**achieved occupancy 只有 7.24%，同时记录了大量 shared-memory bank conflict。**

这篇记录的是一次学习实现的性能复盘。重点是如何从指标走到可验证的优化方向；这些数字不代表官方 FlashAttention 实现的性能。

## 一 实验条件与结果

| 项目 | 配置 |
| --- | --- |
| GPU | RTX 3060 12GB，sm_86 |
| 系统与工具链 | Windows 11，CUDA 13.2 |
| 数据类型 | FP32 |
| 输入规模 | seq = 4096，head_dim = 64 |
| 计时方式 | cudaEvent，100 次平均 |
| 耗时口径 | 未开启 profiling 时的 attention GPU 路径 |

先把耗时放在一起：

| 实现 | 耗时 |
| --- | --- |
| CPU 参考实现 | 911.03 ms |
| Naive GPU | 20.46 ms |
| 手写 FlashAttention | 10.62 ms |

FlashAttention 相对 naive GPU 加速约 1.93 倍。CPU 数字仅作背景，后面的分析聚焦两条 GPU 路径。

**需要先说明：naive 基线比较弱，尤其是 softmax 使用了每个 block 只有一个线程的版本。** 因此，这是一份实现分析，不能把加速比直接推广到优化过的 attention 基线。

## 二 Naive attention 把时间花在了哪里

这份 naive 实现分成三个 kernel：

1. 计算 QKᵀ，生成 score 矩阵 S。
2. 对 S 的每一行做 softmax。
3. 将 softmax 结果与 V 相乘，得到 O。

问题在于，中间的 seq × seq 矩阵需要写入全局内存，再被后续 kernel 读回来。

```text
S 的大小 = 4096 × 4096 × 4 B
         = 64 MiB
         ≈ 67.1 MB
```

相比之下，按单个 4096 × 64 矩阵计算，Q、K、V、O 各自只有 1 MiB。

中间矩阵的逻辑读写至少包括：

```text
QKᵀ：写 S
softmax：读 S，写归一化结果
SV：读归一化结果
```

具体实现还可能多次扫描同一行。矩阵越大，中间结果的搬运就越值得关注。

FlashAttention 的核心思路，是把 attention 按 tile 计算，在片上存储中生成并立即消费局部 score，避免将完整的 N × N 中间矩阵写回显存。

难点在于：每次手里只有一部分 score，怎样得到与整行 softmax 一致的结果？

这里需要 online softmax。对一行中的新 tile，可以维护最大值 m、指数和 l，以及未归一化的输出累积量 o_acc：

```text
m_new = max(m, max(scores_tile))
alpha = exp(m - m_new)
p = exp(scores_tile - m_new)

l_new = alpha × l + sum(p)
o_acc_new = alpha × o_acc + p × V_tile

最后：O = o_acc / l
```

新 tile 改变最大值时，旧的累积结果也按同一因子缩放。这样就可以逐块处理，而不必保存完整的一行 score。

这也是 [FlashAttention 原论文](https://arxiv.org/abs/2205.14135) 中减少显存 IO 的关键思路。

## 三 DRAM 流量确实降到了约二十四分之一

讨论“访存量”时，最好先分清三个口径：

| 口径 | 含义 |
| --- | --- |
| 逻辑读写量 | 算法或代码逻辑要求读取、写入的数据量 |
| 缓存层级流量 | 在特定接口上经过 L1、L2 的实际流量 |
| DRAM 流量 | 实际到达显存的读写字节数 |

缓存命中、合并访问和重复读取，会让这几个数字明显不同。DRAM 字节数反映显存侧的数据搬运，但 L1、L2 和 shared memory 同样有自己的带宽与延迟成本。

这次直接采集：

```text
dram__bytes_read.sum
dram__bytes_write.sum
```

naive 路径的三个 kernel：

| Kernel | DRAM 读取 | DRAM 写入 | 合计 |
| --- | --- | --- | --- |
| qk_dot | 3.2 MB | 67.2 MB | 70.4 MB |
| softmax | 199.7 MB | 133.7 MB | 333.4 MB |
| sv_dot | 98.1 MB | 1.3 MB | 99.4 MB |
| 合计 | 301.0 MB | 202.2 MB | 503.2 MB |

以上按展示到一位小数的数据相加；未舍入的原始计数求和可能略有差异。表中 DRAM 流量使用十进制 MB，前面的矩阵容量使用 MiB。

fused kernel 的结果：

| Kernel | DRAM 读取 | DRAM 写入 | 合计 |
| --- | --- | --- | --- |
| flash_attn_kernel | 18.4 MB | 2.7 MB | 21.1 MB |

**约 503 MB → 21.1 MB，减少到原来的约 1/24。**

不过，这不意味着 K、V 只被读取了一遍。

当 Q tile 的行数 Br = 32 时，4096 行 Q 被分成 128 个 block。若每个 block 都扫描完整的 K、V，仅这部分的逻辑读取量就约为：

```text
128 × (1 MiB + 1 MiB) = 256 MiB
```

这远高于测得的 DRAM 读取量，说明逻辑读取没有全部转化成显存流量，缓存复用起了作用。

但仅凭这个差值，不能进一步断言“绝大部分都由 L2 服务”。要区分 L1 和 L2 的贡献，还需要核对各层级的请求、sector 和命中指标。

## 四 为什么流量降了二十四倍却只快了一点九倍

先纠正一个容易产生的直觉：**流量减少比例，不等于耗时加速比。**

只有在两条路径都主要受 DRAM 带宽限制、有效带宽也接近时，才适合用字节数近似推断时间。

这里的 fused kernel 还要完成矩阵乘、指数运算、归约、shared-memory 访问，以及 online softmax 的状态更新。显存流量下降以后，这些成本不会自动消失。

所以，不能把 24 ÷ 1.9 理解成“还有约 12 倍性能丢了”。真正的问题是：**当前实现的主要限制在哪里，哪些修改能缩短实际耗时？**

下面是 fused kernel 的采集结果。部分名称沿用报告中的简写，精确含义需要结合完整 metric 名称和后缀理解。

| 指标 | 结果 |
| --- | --- |
| Block size | 32 |
| Grid size | 128 |
| 每 block 动态 shared memory | 24,576 B |
| Achieved occupancy | 7.24% |
| SM throughput | 10.56% |
| 报告中的 Memory throughput 汇总值 | 54.27% |
| Shared-memory bank conflict 计数 | 234,937,634 |
| Shared load 指令计数 | 25,165,824 |
| Shared store 指令计数 | 2,105,344 |
| Short scoreboard stall | 66.00% |
| MIO throttle stall | 0.00% |

其中，Memory throughput 的汇总值不能直接当成 DRAM 带宽利用率。接下来更值得关注的是 occupancy、shared-memory 访问，以及相关的依赖等待。

## 1 一个 block 只有一个 warp

block size 为 32，意味着一个 block 只有一个 warp，却要处理一个 32 × 64 的 Q tile。

sm_86 每个 SM 最多支持 48 个驻留 warp，shared-memory 容量上限为 100 KiB。若按每 block 约 24 KiB、并采用足够大的 shared-memory carveout 粗算：

```text
每 SM 约可驻留 4 个 block
每 block 只有 1 个 warp

occupancy 上限粗估 = 4 / 48 ≈ 8.33%
```

这与实测 7.24% 在同一量级。具体的理论上限仍要结合寄存器、静态 shared memory、资源分配粒度和实际 carveout，通过 Launch Statistics 或 Occupancy Calculator 确认。

**低 occupancy 的直接问题，是可供调度的 warp 太少，延迟更难隐藏。**

当这些 warp 都在等数据或依赖时，调度器缺少其他就绪 warp 来填补空隙。不过，7.24% 的 occupancy 并不等于“GPU 有 92.76% 的时间完全空转”，也不能据此推算潜在加速比。

硬件上限可参考 [NVIDIA Ampere Tuning Guide](https://docs.nvidia.com/cuda/ampere-tuning-guide/index.html)。

## 2 Shared memory 的访问模式值得优先检查

报告记录了约 2.35 亿次 bank conflict，同时 short scoreboard stall 达到 66%。

这组指标把 shared-memory 访问推到了排查列表前面，但需要注意两个解释边界。

首先，bank conflict 计数和 shared load/store 指令数不一定采用同一统计口径，不能直接相除，得出“每次访问平均几路冲突”。更合适的做法，是结合 shared-memory wavefront、理想 wavefront，以及具体指令的源代码映射分析。

其次，short scoreboard 表示对 MIO 操作结果的依赖等待，常见来源是 shared-memory 操作，也可能涉及特殊数学指令或动态分支。它不能笼统解释成“等待 shared/L1”，其中 global/local 等 L1TEX 访问依赖通常要看 long scoreboard。

因此，**66% 不能直接翻译为整个 kernel 总耗时的 66% 都花在 shared memory 上，更不能承诺消除冲突就能收回这部分时间。**

MIO throttle 为 0%，则表示这次采集中没有观察到明显的 MIO 队列满等待。它不能单独排除所有 MIO 相关成本。

结合这些数据，我会优先检查 shared-memory 冲突与相关依赖，再通过修改前后的对照实验确认收益。指标定义可参考 [Nsight Compute Profiling Guide](https://docs.nvidia.com/nsight-compute/ProfilingGuide/)。

## 3 怎样从地址推导 bank conflict

一个值得检查的模式是：同一 warp 中，相邻 lane 读取某个二维 float 数组的同一列，而行跨度是 64 个 float。

以 32 个 bank、每个 float 占一个 32-bit word 的标量访问为例：

```text
bank(lane) = (base + lane × 64 + column) % 32

64 % 32 = 0
```

如果这些 lane 访问的是同一 bank 内的不同地址，就会形成 32 路冲突。

这里有两个关键条件：**确实是这个 lane 到地址的映射，而且访问的是不同地址。** 如果多个 lane 读取同一个 word，可能走广播，不能按冲突处理。

所以，不能只根据“计算了 K 的转置”或“用了 24 KiB shared memory”，就断定冲突一定发生在 K 的列访问上。最终要回到具体的索引表达式和指令。

这是当前最值得验证的假设，而不是已经定位到某一行代码的结论。

## 五 下一步按三个方向分别验证

每次只改变一个主要因素，先检查输出正确性，再比较未 profiling 的耗时和对应指标。这样才能知道收益来自哪里。

## 1 调整发生冲突的 shared-memory 布局

如果确认问题来自前面那种按列的标量访问，可以先尝试 padding：

```cpp
// 原布局
float tile[32][64];

// 候选布局
float tile[32][65];

```

行跨度从 64 变成 65 后：

```text
65 % 32 = 1
```

在上述访问模式下，相邻 lane 会落到不同的 bank。对动态 shared memory，还要同步修改分区偏移、索引跨度和 launch 时申请的字节数。

如果使用了 float4，不能简单地说“为了对齐，把 +1 换成 +4 就行”。行跨度 68 虽然是 4 的倍数，但对同样的标量列访问：

```text
68 % 32 = 4
```

仍然会出现 4 路冲突。向量化对齐和 bank 分布需要一起设计，必要时调整布局或采用 swizzle。

Padding 消除冲突的典型示例，可参考 [CUDA Best Practices Guide](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html)。具体收益要以修改后的指标和耗时为准。

## 2 让多个 warp 协作处理一个 Q tile

当前每 block 只有一个 warp，可以尝试重新划分工作，让 128 或 256 个线程协作处理同一个 tile。

这里需要改的是线程到计算任务的映射，不能只修改 launch 参数。shared-memory 数据交换、归约、online softmax 状态的所有权，都要跟着重新梳理。

同步也需要按数据依赖设计：

- Warp 内线程通过 shared memory 交换数据时，按需使用 __syncwarp()，不能依赖隐式同步。
- 跨 warp 交换数据时，需要 block 范围的同步，例如所有线程正确参与的 __syncthreads()。
- 覆盖下一轮 tile 前，也要确认上一轮读取已经完成。

归约是否需要跨 warp，取决于一行数据是否被拆给多个 warp。如果每行仍由单个 warp 负责，就未必需要跨 warp 归约。

## 3 尝试把线程独占的 Q 数据放进寄存器

如果每个线程可以独立持有它负责的 Q 数据，不需要其他线程读取，就可以考虑将这部分数据放进寄存器，减少 shared-memory 占用和访问。

一个 32 × 64 的 FP32 tile 占 8 KiB。若确实能完整移走，动态 shared memory 有机会从 24 KiB 降到约 16 KiB。

但“省下 8 KiB”不等于“每个 SM 一定能从 4 个 block 增加到 6 个”。寄存器占用、spill、block size 和其他资源限制，都可能改变结果。

这一步需要一起观察寄存器数量、local-memory 流量、occupancy 和实际耗时。

## 六 Online softmax 单独测没有明显收益

另一个独立的 softmax benchmark 中，结果是：

| 版本 | 耗时 |
| --- | --- |
| Naive | 0.415 ms |
| V2 合并访存与树形归约 | 0.036 ms |
| V3 Online softmax | 0.037 ms |

V2 相对 naive 加速约 11.5 倍。V3 与 V2 很接近，单从这组均值看，没有体现出额外优势。

不过，0.036 ms 和 0.037 ms 只差 1 μs。在缺少多轮分布与误差信息时，不宜把它写成已经确认的性能退化。

Online softmax 能把最大值和指数和的计算合并到一次扫描中，但生成全部归一化输出通常仍需要再次访问输入，或者保留中间数据。它也引入了缩放与状态更新开销，因此独立 softmax 是否受益，取决于实现和输入规模。

**它在这份 attention 实现中的价值，是支持分 tile 的数值稳定累积。** 单独 benchmark 没有明显变快，不影响它在融合计算中的作用。

从这个实验也不能推出“online softmax 本来就不能优化独立 softmax”。更准确的结论是：这份 V3 在当前配置下，没有表现出相对 V2 的明显收益。

## 七 这些数字应该怎样解读

有几处实验边界，会直接影响上面的结论。

**第一，naive softmax 明显偏弱。**

它使用每个 block 一个线程的实现，DRAM 总流量约 333.4 MB，占 naive 路径的约三分之二。

199.7 MB 的读取量约为一个 64 MiB score 矩阵容量的三倍，但不能仅凭这个比例，把额外流量全部归因于非合并访存；多轮扫描、缓存和具体访问方式都需要一起核对。

另一个模块中更快的 softmax 尚未接入这条基线。替换后，加速比需要重测；DRAM 流量比也取决于新实现实际减少了多少读写，不能直接由独立 softmax 的加速比推算。

**第二，没有成熟库对照。**

目前没有 cuBLAS 或 PyTorch SDPA 的结果。这些数据只能说明两份手写实现之间的差异，不能据此评价相对成熟库的性能水平。

**第三，缓存命中率出现了异常值。**

采集中的 lts__t_sector_hit_rate.pct 曾出现 115.70%。这不应被当作有效命中率，也不足以说明该指标本身不适用。还需要排查采集稳定性、replay、聚合口径和工具行为。

因此，这里只保留“逻辑读取量高于 DRAM 读取量，存在缓存复用”的判断，不给出精确的 L2 命中率结论。

**第四，profiling 下的程序耗时没有用于计算加速比。**

同一份程序，开启 profiler 后观察到 naive 约 318 ms、flash 约 136 ms；未开启时分别约 20.5 ms、10.6 ms。采集会扰动执行，本文耗时均使用未开启 profiling 的运行。

同时，profiler 采集时的缓存状态也可能与普通计时不同。因此，DRAM 字节数和耗时用于互相辅助分析，不能假定它们来自完全相同的执行条件。

**第五，目前只覆盖单卡和 FP32。**

换用 FP16、BF16、Tensor Core 路径或其他 GPU 后，需要重新判断瓶颈。正式比较时，还应保持相同的 attention 语义与数值精度要求，并报告正确性误差。

## 八 先确认指标属于哪个 kernel

多 kernel 程序中，一个很容易踩的坑，是把不同 kernel 的指标看串。

尤其在 Nsight Compute UI 中切换多个 launch 时，拿错一次数据，就可能得到一套看似自洽、实际归属错误的解释。

我的核对顺序是：

1. 确认 Kernel Name 和 launch 编号。
2. 核对 block size、grid size。
3. 核对动态 shared memory 和 shared-memory 指令计数。
4. 再阅读 occupancy、bank conflict 和 stall reason。

对于这份明确使用动态 shared memory 做 tiling 的实现，如果报告里 shared-memory 占用和相关指令都是零，就应该先核对 kernel 是否选对。

用 --metrics 指定指标、通过 --csv 导出，再按 Kernel Name 和 launch 分组核查，也比只在 UI 中切换更容易复核。

## 九 这次复盘得到的结论

这次实验能确认的是：**这份 fused 实现大幅减少了 DRAM 读写，但实际加速只有约 1.9 倍；它同时存在很低的 achieved occupancy，以及大量 shared-memory bank conflict。**

这些指标给出了明确的排查顺序：先定位冲突访问并调整布局，再重新分配 warp 的工作，最后评估 Q 数据放入寄存器后的资源变化。

至于每一步能快多少，需要改完、确认正确性，再测。现有数据还不能把耗时精确拆分到每一种原因上。

对我来说，这次补 CUDA 最有价值的地方，是把以前做图形性能优化时熟悉的一件事重新走了一遍：**从 profiler 找到具体访问和依赖，再用修改后的数据验证判断。**
