## 张量并行（Tensor Parallelism）与流水线并行（Pipeline Parallelism）

---

### 一、模型放不下一张卡，怎么办？

### 显存的硬约束

以 **Llama-3-70B** 为例：

```text
参数量：70B
FP16 存储：70B × 2 = 140 GB

H100 单卡显存：80 GB
A100 单卡显存：40 GB / 80 GB

140 GB > 80 GB → 单张 H100 放不下！
```

如果再考虑推理时的 KV Cache（每个并发请求约 160-670 MB）和激活值，显存需求更大。

**解决思路**：把模型分散到多张 GPU 上，每张 GPU 只存和计算一部分。这就是**模型并行（Model Parallelism）**，有两种主要方式：

### 二、张量并行（Tensor Parallelism）：切分权重矩阵

### 核心思想

Transformer 的每一层都由大量矩阵乘法构成，矩阵乘法天然可以被拆分：

如果 $Y = X \cdot W$，可以把 W 按**列**切分，每张 GPU 只计算一部分列的结果：

$$ Y = X \cdot [W_0 | W_1 | W_2 | W_3] = [XW_0 | XW_1 | XW_2 | XW_3] $$

每张 GPU 只持有 $W_i$，分别计算 $XW_i$，然后合并（concat 或 all-reduce）得到完整的 $Y$。

### 列并行（Column Parallel Linear）

**用于**：QKV 投影、FFN 的 Up/Gate 投影

```text
原始计算：
  X [seq, H]  ×  W [H, 4H]  =  Y [seq, 4H]

TP=4 后，W 按列切分为 4 份（每份 [H, H]）：

  GPU 0: X × W[:, 0:H]    =  Y₀ [seq, H]
  GPU 1: X × W[:, H:2H]   =  Y₁ [seq, H]
  GPU 2: X × W[:, 2H:3H]  =  Y₂ [seq, H]
  GPU 3: X × W[:, 3H:4H]  =  Y₃ [seq, H]

  ← 每张 GPU 各自计算，X 在每张 GPU 上都有完整副本 →
  ← 无需通信即可完成！（输入相同，权重不同，各算各的）→

合并：Y = concat([Y₀, Y₁, Y₂, Y₃], dim=-1) = [seq, 4H]
（通常不马上合并，Y₀/Y₁/Y₂/Y₃ 直接传给下一层的行并行）
```

### 行并行（Row Parallel Linear）

**用于**：O 投影（注意力输出）、FFN 的 Down 投影

```text
原始计算：
  H [seq, 4H]  ×  W [4H, H]  =  Y [seq, H]

TP=4 后，W 按行切分（每份 [H, H]）：
每张 GPU 持有不同行的权重，也持有对应的输入片段（来自上层列并行的输出）：

  GPU 0: H₀[seq, H] × W[0:H, :]   =  Y₀ [seq, H]  （部分结果）
  GPU 1: H₁[seq, H] × W[H:2H, :]  =  Y₁ [seq, H]  （部分结果）
  GPU 2: H₂[seq, H] × W[2H:3H, :] =  Y₂ [seq, H]  （部分结果）
  GPU 3: H₃[seq, H] × W[3H:4H, :] =  Y₃ [seq, H]  （部分结果）

  Y = Y₀ + Y₁ + Y₂ + Y₃  ← 需要 All-Reduce！（每张 GPU 的结果相加才是完整结果）
```

### 三、一层 Transformer 的 TP 通信模式全图

把列并行和行并行组合起来，一层完整 Transformer 的 TP 模式如下：

```text
初始状态：所有 GPU 持有相同的 X [seq, H]

                      ① 无需通信
  ┌──────────────────────────────────────────────────┐
  │            QKV 投影（列并行）                      │
  │  GPU 0: X × W_QKV[:, 0:H/4]  → Q₀,K₀,V₀         │
  │  GPU 1: X × W_QKV[:, H/4:H/2]→ Q₁,K₁,V₁          │
  │  GPU 2: X × W_QKV[:, H/2:3H/4]→ Q₂,K₂,V₂         │
  │  GPU 3: X × W_QKV[:, 3H/4:H] → Q₃,K₃,V₃          │
  └──────────────────────────────────────────────────┘
  ← 每张 GPU 负责不同的 attention heads →
                      ↓ 无需通信
  ┌──────────────────────────────────────────────────┐
  │            注意力计算                             │
  │  GPU 0: Attention(Q₀,K₀,V₀) → A₀（部分heads）    │
  │  GPU 1: Attention(Q₁,K₁,V₁) → A₁                │
  │  GPU 2: Attention(Q₂,K₂,V₂) → A₂                │
  │  GPU 3: Attention(Q₃,K₃,V₃) → A₃                │
  └──────────────────────────────────────────────────┘
                      ↓ 无需通信（A₀/A₁/A₂/A₃ 直接作为行并行的输入）
  ┌──────────────────────────────────────────────────┐
  │            O 投影（行并行）                        │
  │  GPU 0: A₀ × W_O[0:H/4, :] → O₀（部分结果）      │
  │  GPU 1: A₁ × W_O[H/4:H/2, :]→ O₁                │
  │  GPU 2: A₂ × W_O[H/2:3H/4,:]→ O₂                │
  │  GPU 3: A₃ × W_O[3H/4:H, :] → O₃                │
  └──────────────────────────────────────────────────┘
               ② All-Reduce（第1次通信）
               O = O₀ + O₁ + O₂ + O₃
               → 每张 GPU 得到相同的 O [seq, H]
                      ↓ 无需通信
  ┌──────────────────────────────────────────────────┐
  │            FFN（Gate + Up 列并行，Down 行并行）     │
  │  Up/Gate: 每 GPU 算不同部分 → 列并行结果          │
  │  Down: 行并行 → 部分结果                          │
  └──────────────────────────────────────────────────┘
               ③ All-Reduce（第2次通信）
               FFN_out = 各 GPU 结果相加
               → 每张 GPU 得到相同的输出 [seq, H]
```

**结论：每层 Transformer 只需 2 次 All-Reduce。**

### 四、All-Reduce 的开销与限制

### All-Reduce 是什么？

All-Reduce 是一种集合通信操作：所有参与的 GPU 都把自己的局部结果贡献出来，每张 GPU 最终得到所有局部结果的总和。

```text
All-Reduce 示意（4张 GPU，每张有大小为 D 的张量）：

发送前：
  GPU 0: [a₀, a₁, a₂, a₃]
  GPU 1: [b₀, b₁, b₂, b₃]
  GPU 2: [c₀, c₁, c₂, c₃]
  GPU 3: [d₀, d₁, d₂, d₃]

发送后：每张 GPU 都有：
  [a₀+b₀+c₀+d₀, a₁+b₁+c₁+d₁, a₂+b₂+c₂+d₂, a₃+b₃+c₃+d₃]
```

All-Reduce 的通信量 ≈ $2(N-1)/N \times D$（其中 N 是 GPU 数，D 是数据大小）。

### 网络带宽决定 TP 上限

```text
NVLink 带宽（同节点）：H100 NVLink ~900 GB/s（双向）
InfiniBand 带宽（跨节点）：400 Gbps ≈ 50 GB/s（双向）

Llama-70B 每层 All-Reduce 的数据量（TP=8）：
  = 2 × seq_len × hidden_size × dtype_bytes
  = 2 × 1024 × 8192 × 2 ≈ 33 MB（一次 All-Reduce）

NVLink 时延：33 MB / (900 GB/s × 0.5) ≈ 0.07 ms（可忽略！）
IB 时延：   33 MB / (50 GB/s)          ≈ 0.66 ms × 2次/层 × 80层 = 105 ms（灾难性！）
```

**结论：TP 必须在同节点、NVLink 互联的 GPU 之间使用。跨节点不能用 TP，要用 PP。**

### 五、Attention 层的 TP：Head 如何分配

### GQA（Grouped Query Attention）下的 TP 分配

现代大模型几乎都用 GQA：Q head 数量多，K/V head 数量少（如 Llama-3-70B：64 Q heads，8 KV heads）。

TP=8 时的分配：

```text
Llama-3-70B TP=8 的 head 分配：

  GPU 0: Q heads [0,8,16,24,32,40,48,56], KV head 0
  GPU 1: Q heads [1,9,17,25,33,41,49,57], KV head 1
  GPU 2: Q heads [2,10,18,26,34,42,50,58], KV head 2
  ...
  GPU 7: Q heads [7,15,23,31,39,47,55,63], KV head 7

  每张 GPU 独立计算自己的 heads，结果是完整的 attention 输出的 1/8
```

这意味着：**KV Cache 也是按 TP 切分的**——每张 GPU 的 KV Cache 只存这张 GPU 负责的那些 KV heads 的数据，每张 GPU 的 KV Cache 大小是未切分时的 1/TP。

### 六、流水线并行（Pipeline Parallelism）：跨节点的解法

### 基本思路：按层切分

```text
Llama-3-70B，80 层，PP=4（4 个节点，每节点 8×H100）：

节点 0: 嵌入层 + Layer  0~19
节点 1: Layer 20~39
节点 2: Layer 40~59
节点 3: Layer 60~79 + LM Head

数据流向：
  输入 → [节点0] → 激活值 → [节点1] → 激活值 → [节点2] → 激活值 → [节点3] → 输出
                   ↑ P2P 传输（每段间一次）
```

### 流水线气泡（Pipeline Bubble）问题

PP 最大的问题：数据只能从节点0流向节点1，再流向节点2……**串行执行**。

```text
朴素流水线（PP=4，单个 batch）：

时间 →    T0   T1   T2   T3   T4   T5   T6   T7
节点 0:   [B1 计算] ─── ─── ─── ─── ─── ─── ───  ← 算完就等
节点 1:          [B1 计算] ─── ─── ─── ─── ───   ← 等节点0
节点 2:                  [B1 计算] ─── ─── ───   ← 等节点1
节点 3:                          [B1 计算] ───   ← 等节点2

气泡（浪费）：节点0 有 3/4 的时间在等待！
```

**Micro-batch 流水**：把一个大 batch 切成多个 micro-batch，让节点之间的空隙被填满：

```text
1F1B（One Forward, One Backward）流水（推理时简化为纯前向）：

时间 →    T0   T1   T2   T3   T4
节点 0:   [m1] [m2] [m3] [m4] ─── ─── ─── ─── ···
节点 1:        [m1] [m2] [m3] [m4] ─── ─── ─── ···
节点 2:              [m1] [m2] [m3] [m4] ─── ─── ···
节点 3:                    [m1] [m2] [m3] [m4] ···

节点1 处理 m1 时，节点0 同时处理 m2 → GPU 利用率大幅提升！
气泡只存在于最开始（预热）和最末尾（排空）
```

### 七、TP + PP + EP 的组合使用

大规模部署通常需要 TP、PP、Expert Parallel 三者组合：

```text
Llama-3-70B × 8 节点（64 × H100）：

推荐配置：TP=8（同节点），PP=8（跨节点）

                     PP Stage 0       PP Stage 1  ... PP Stage 7
  节点 0（Layer 0~9）: [TP=8的8张GPU]
  节点 1（Layer10~19）:              [TP=8的8张GPU]
  ...
  节点 7（Layer70~79）:                                [TP=8的8张GPU]

通信拓扑：
  节点内（TP）：NVLink，900 GB/s，通信几乎免费
  节点间（PP）：InfiniBand，50 GB/s，但每两层只有一次 P2P 传输（可以 pipeline）
```

对于 MoE 模型（如 DeepSeek-V3）还会加入 Expert Parallel：

```text
不同节点 → 不同的专家（Expert Parallel）
同节点内 → TP 处理 Attention 层
跨节点间 → All-to-All 传输（token 发往对应专家所在节点）
```

### 八、Custom All-Reduce：小数据的高效通信

NCCL（NVIDIA Collective Communications Library）是标准的 GPU 集合通信库，但它针对大数据传输优化，对**小 tensor**（decode 阶段 batch 小时，每次 All-Reduce 的数据量可能只有几 MB）延迟较高，有固定的启动开销。

vLLM 实现了自己的 Custom All-Reduce kernel（`csrc/custom_all_reduce.cu`），针对小 tensor 场景：

```text
对比（TP=4, 数据量 = 4 MB）：

NCCL All-Reduce：
  延迟 ≈ 基础延迟（~50μs）+ 传输时间（4MB / 900GB/s × 2 = 0.009ms）
  总延迟 ≈ 0.05 + 0.009 ≈ 0.06 ms

Custom All-Reduce（基于共享内存）：
  延迟 ≈ 0.01 ms（无额外启动开销，直接通过 NVLink 共享内存操作）

节省：约 0.05 ms/次 × 2次/层 × 80层 = 8 ms/step
对 Decode 阶段 40ms/step 来说，节省 ~20%！
```

Custom All-Reduce 只在数据量较小时使用（≤ 一定阈值，通常几十 MB），大数据量仍回退到 NCCL。
