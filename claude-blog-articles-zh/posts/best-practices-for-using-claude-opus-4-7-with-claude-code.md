# 在 Claude Code 中使用 Claude Opus 4.7 的最佳实践

> 原文：[Best practices for using Claude Opus 4.7 with Claude Code](https://claude.com/blog/best-practices-for-using-claude-opus-4-7-with-claude-code/) · Claude 博客

[Opus 4.7](https://www.anthropic.com/news/claude-opus-4-7) 是我们迄今公开发布的最强模型，适用于编码、企业工作流和长时间运行的智能体任务。它比 Opus 4.6 更善于处理歧义，在查找 bug 和审查代码方面能力强得多，跨会话保持上下文也更加可靠，并且在更少的指引下就能对模糊任务展开推理。

在[发布公告](https://www.anthropic.com/news/claude-opus-4-7)中，我们提到过两处变化——更新后的分词器（tokenizer），以及在更高努力等级（effort level）下更倾向于多思考、尤其在较长会话的后半段如此——会影响 token 用量。因此，把 Opus 4.6 替换为 Opus 4.7 时，可能需要一些调校才能达到最佳表现。对提示和执行框架（harness）做几处小调整，就能带来很大的不同。

本文将梳理有哪些变化，以及如何在 Claude Code 中最有效地使用 Opus 4.7。

## 组织交互式编码会话

Opus 4.7 的 token 用量与行为，会因你部署的是「单轮用户输入、更自主的异步编码智能体」，还是「多轮用户输入、更交互的同步编码智能体」而有所不同。在交互式场景中，它会在每轮用户输入之后进行更多推理：这提升了它在长会话中的连贯性、指令遵循和编码质量，但也往往会消耗更多 token。

为了在 Claude Code 中充分发挥 Opus 4.7 的实力，我们发现把 Claude 更多当作一位你委派任务的能力出众的工程师，而不是一位需要你逐行指导的结对程序员，会更有帮助：

- **在第一轮就把任务讲清楚。** 包含意图、约束、验收标准和相关文件位置的、描述完备的任务说明，能为 Opus 4.7 提供交付更强输出所需的上下文。跨许多轮次逐步传达的模糊提示，往往会同时降低 token 效率，有时还会降低整体质量。
- **减少必需的用户交互次数。** 每一轮用户输入都会增加推理开销。把问题打包在一起，给模型提供持续前进所需的上下文。
- **适时使用[自动模式](https://claude.com/blog/auto-mode)。** 对于你信任模型可以安全执行、无需频繁确认的任务，自动模式能缩短周期时间。对于你已在一开始就提供完整上下文的长周期任务，它尤其合适。自动模式现已面向 Claude Code Max 用户开放研究预览——你可以用 Shift+Tab 开启。
- **为完成的任务设置通知**。让 Claude 在完成任务时播放提示音，它可以自行创建基于 hooks 的通知。

## Opus 4.7 推荐的努力等级设置

Opus 4.7 在 Claude Code 中的默认努力等级现在是 `xhigh`。这是一个介于 `high` 和 `max` 之间的新等级，让用户在困难问题上能更细致地把控推理与延迟之间的权衡。对大多数智能体编码工作，我们推荐 `xhigh`，尤其适合那些对智能水平敏感的任务，比如设计 API 与 schema、迁移遗留代码，以及审查大型代码库。

以下是对各个努力等级的补充建议：

- **`medium` 与 `low`**：适合对成本敏感、对延迟敏感或范围严格限定的工作。在更难的任务上，模型的表现会不及更高努力等级时的水平，但它仍然优于运行在相同努力等级下的 Opus 4.6——有时消耗的 token 还更少。
- **`high`**：在智能水平与成本之间取得平衡。如果你在并行运行多个会话，或想在质量不大幅下滑的前提下少花一些，就选 high。
- **`xhigh`（默认，推荐）**：对大多数编码与智能体用途而言的最佳设置。它具备很强的自主性与智能水平，又没有 `max` 在长时间智能体运行中可能产生的失控 token 消耗。
- **`max`**：能在真正困难的问题上再挤出一些性能，但收益递减，也更容易过度思考。请审慎地把它用于特定任务，比如在评估中测试模型的能力上限，以及对智能水平极其敏感、对成本不敏感的用途。

如果你正在升级到新模型，我们建议你针对努力等级做些实验，而不是直接照搬旧设置。你可以在同一个任务中切换努力等级，从而更有效地管理 token 用量与推理。

我们把 Opus 4.7 的默认努力等级设为 `xhigh`，因为我们相信这是对大多数编码任务而言的最佳设置。如果你是 Claude Code 的老用户但从未手动设置过努力等级，你会被自动升级到 `xhigh`。你仍然可以手动调整。

## 与自适应思考协作

**Opus 4.7 不再支持带固定思考预算的扩展思考（Extended Thinking）。** 取而代之，Opus 4.7 提供自适应思考（adaptive thinking）。这让思考在每一步都成为*可选项*，并允许模型根据上下文决定何时进行更多思考。它可以快速响应简单查询，在某一步无需思考时跳过思考，并把思考 token 投入最有可能派上用场的地方。在一次智能体运行中，这可以累积为更快的响应和更好的用户体验。

自适应思考在本次发布中有显著改进——尤其是，Opus 4.7 更不容易过度思考。

如果你想要对思考频率有更多控制，可以直接在提示中说明：

- **想要更多思考**，可以试试这样的话：「回复之前请仔细地逐步思考；这个问题比看上去更难。」
- **想要更少思考**，可以试试这样的话：「优先快速响应，而不是深入思考。拿不准时，直接作答。」这会节省 token，但在较难的步骤上可能损失一些准确性。

## 值得了解的行为变化

从 Opus 4.6 到 4.7，有一些默认行为发生了变化。如果你曾为旧模型精心调校过提示或执行框架，这些变化值得了解。

**回复长度会根据任务复杂度校准。** Opus 4.7 不像 Opus 4.6 那样默认啰嗦。简单的查询你会得到更短的回答，开放式的分析则会更长。如果你的用例依赖特定的长度或风格，请在提示中明确说明。我们发现，给出你想要的语气的正面示例，比负面的「不要这样做」式指令更有效。

**模型调用工具的频率降低，推理增多。** 这在许多情况下带来更好的结果。如果你想要*更多*的工具使用（比如在智能体工作中进行更激进的搜索或文件读取），请提供明确描述何时、为何使用该工具的指引。

**默认派生的子智能体更少。** Opus 4.7 在决定何时把工作委派给子智能体（subagent）时更加审慎。如果你的用例受益于并行的子智能体（例如跨文件或跨独立条目展开扇出），我们建议你明确写出来。例如：

不要为你在单次回复中就能直接完成的工作派生子智能体（例如重构一个你已经能看到的函数）。在跨条目扇出或读取多个文件时，在同一轮中派生多个子智能体。

## 接下来可以尝试什么

Opus 4.7 在长时间运行的任务上比以往模型表现更好。这使它非常适合那些过去受制于人工监督的任务，比如复杂的多文件修改、模糊的调试、跨服务的代码审查，以及多步骤的智能体工作。

我们建议你把努力等级保持在 `xhigh`，看看第一轮输入能带你走多远。
