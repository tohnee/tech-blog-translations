# AI 智能体的常见工作流模式

> 原文：[Common workflow patterns for AI agents](https://claude.com/blog/common-workflow-patterns-for-ai-agents-and-when-to-use-them/) · Claude 博客

[AI 智能体](https://www.anthropic.com/research/building-effective-agents)自主做出决策，而工作流（workflow）就是你对这种自主性施加结构的方式。它们建立执行模式，把智能体的能力引导向那些需要协调步骤、可预测结果与精心编排时序的复杂问题。

当你需要多个智能体协同工作时，真正的决策在于哪种模式适合你的问题。

我们与数十个构建 AI 智能体的团队合作过，而在生产环境中，三种模式覆盖了绝大多数使用场景：顺序式（sequential）、并行式（parallel）与评估者-优化者（evaluator-optimizer）。

每一种解决的是不同的问题，选错了就会在延迟、token 或可靠性上付出代价。本文逐一拆解这三种模式，并说明各自适用的场景与组合方式。

## **工作流与智能体如何协作**

如果你管理过团队，你就已经理解工作流了。

想想制造业的流水线：每个工位都有一位熟练工人在为自己的具体任务做决策，但整体流程是事先设计好的——即使个别步骤包含路由或重试这类动态决策。

智能体工作流的运作方式与此相同。

### **理解工作流与自主智能体的区别**

工作流不会取代智能体的自主性；它塑造的是智能体在何处、以何种方式施展这种自主性。

**完全自主的智能体决定一切**：使用哪些工具、以什么顺序执行任务、何时停止。

**工作流提供结构**：它确立整体流程、定义检查点，并为智能体在每一步如何运作设定边界，同时仍允许在边界之内进行动态行为。

工作流中的每一步仍然可以利用智能体的推理与工具使用，但整体编排遵循一条既定路径。工作流模式让你在每一步之内拥有智能体智能，而一个可预测的流程贯穿整个任务。

## **智能体工作流模式**

在生产环境中，我们看到三种工作流模式出现得最为频繁。把它们视为积木，而非僵化的模板——随着需求演进，你常常会组合或嵌套它们：

1. **顺序式工作流（Sequential workflows）** — 用于按固定顺序执行任务
2. **并行式工作流（Parallel workflows）** — 用于跨智能体同时运行独立任务
3. **评估者-优化者工作流（Evaluator-optimizer workflows）** — 用于需要迭代打磨的输出

每种工作流类型解决特定的问题，并在复杂度、成本与性能上带来明确的权衡。

|  | 解决的问题 | 何时使用 | 权衡 | 收益 |
|---|---|---|---|---|
| **顺序式（Sequential）** | 任务存在依赖：步骤 B 需要步骤 A 的输出 | 多阶段流程、数据管道、草稿-审阅-打磨循环 | 增加延迟（每一步都要等待上一步） | 让每个智能体专注于单一事务，从而提升准确性 |
| **并行式（Parallel）** | 任务彼此独立，但逐个处理太慢 | 多维度评估、代码审查、文档分析 | 成本更高（多个并发 API 调用），且需要聚合策略 | 可以更快完成，并实现工程团队间的关注点分离 |
| **评估者-优化者（Evaluator-optimizer）** | 首稿质量不够好 | 技术文档、客户沟通、按特定标准生成代码 | token 用量成倍增加，并拉长迭代时间 | 通过结构化反馈回路生成更好的输出 |

从能解决问题的最简单模式起步。默认用顺序式。当延迟成为瓶颈且任务彼此独立时转向并行式；只有当你能度量质量改进时，才加入评估者-优化者回路。

### **顺序式工作流**

顺序式工作流按预先确定的顺序执行任务。

每个阶段的智能体处理输入、做出决策、按需调用工具，然后把结果传递给下一个阶段。其结果是一条清晰的操作链，输出沿系统线性流动。

**何时使用**：当任务天然分解为依赖清晰的多个阶段时，顺序式工作流表现出色。你用一部分延迟换取更高的准确性，因为每个智能体都专注于一个特定的子任务，而不是试图一次处理所有事情。

在以下情况使用顺序式工作流：

- 每一步都依赖上一步输出的多阶段流程
- 每个阶段都增添特定价值的数据转换管道
- 因固有依赖而无法并行化的任务
- 草稿-审阅-打磨这类迭代改进循环

**何时避免**：当单个智能体能有效处理整个任务时，或当智能体需要协作而非按顺序交接工作时，跳过顺序式工作流。如果你强行把一个并不天然契合这种结构的任务塞进顺序步骤，那就是在增加不必要的复杂度。

**示例**：当每一步涉及真正不同的工作时，顺序式工作流效果很好：

- 先生成营销文案，再翻译成多种语言；或从文档中提取数据、对照 schema 校验，然后载入数据库
- 内容审核流水线也很适合顺序执行：提取内容、分类、应用审核规则，然后适当地路由

**专业提示**：先尝试把你的管道当作单个智能体来跑，各步骤只是提示的一部分。如果这样已经足够好，你就在没有引入额外复杂度的情况下解决了问题。只有当单个智能体无法可靠处理时，才拆分成多步骤工作流。

### **并行式工作流**

并行式工作流把独立的任务分发给多个同时执行的智能体。不必等一个智能体完成再启动下一个，而是同时运行多个智能体，然后合并它们的结果。

当任务彼此不依赖时，这种模式可以带来速度提升。

这一方法类似于分布式系统中的扇出/扇入（fan-out/fan-in）模式。你把相同或相关的工作发送给多个智能体，各自独立处理，然后你对它们的输出进行聚合或综合。

智能体之间不互相交接工作——它们自主运行，产出对整体任务有所贡献的结果。

**何时使用**：当你能把工作划分为受益于同时处理的独立子任务时，或当你需要从多个视角审视同一个问题时，并行化是合理的。它还能实现关注点分离：不同的工程师可以独立拥有并优化各自的智能体，工作互不干扰。对于复杂任务，用一个独立的 AI 调用处理每个考量，往往胜过在单次调用中面面俱到。

在以下情况考虑并行式工作流：

- 分段式（sectioning）方法：不同智能体处理不同侧面（比如一个处理查询，另一个筛查安全问题）
- 评估场景：每个智能体评估不同的质量维度
- 投票模式：多个智能体分析同一内容，你聚合它们的评估结果

**何时避免**：当智能体需要累积上下文或必须在前者工作之上继续构建时，不要使用并行式工作流。当 API 配额这类资源约束让并发处理效率低下时，或当你缺乏处理不同智能体之间矛盾结果的清晰策略时，跳过这种模式。如果结果聚合变得过于复杂或降低了输出质量，并行化就不值得。

**示例**：并行式工作流适用于：

- 自动化评估（每个智能体检查不同的质量指标）或代码审查（多个智能体检查不同的漏洞类别）
- 文档分析是另一个强用例：并行执行关键主题提取、情感分析与事实核查，然后合并洞察

**专业提示**：在实现并行智能体之前，先设计好你的聚合策略。你会采用多数票？平均置信度分数？还是听从最专业的那一个？对结果综合有一份清晰计划，能避免你收集到一堆互相冲突、却无从裁决的输出。

### **评估者-优化者工作流**

评估者-优化者工作流让两个智能体进入一个迭代循环：一个生成内容，另一个按特定标准评估它，生成者根据反馈打磨。如此持续，直到输出达到你的质量阈值或触及最大迭代次数。

关键洞察在于：生成与评估是不同的认知任务。把它们分开能让每个智能体各司其职——生成者专注于产出内容，评估者专注于一致地应用质量标准。

**何时使用**：当你拥有清晰、可度量、AI 评估者能够一致应用的质量标准，且首稿质量与最终质量之间的差距大到足以抵消额外的 token 与延迟时，这种模式行之有效。

在以下情况考虑评估者-优化者工作流：

- 有特定要求的代码生成（安全标准、性能基准、风格指南）
- 语气与精确度都很重要的专业沟通
- 首稿质量始终达不到要求的任何场景

**何时避免**：当首稿质量已经满足需求时，跳过评估者-优化者工作流——你是在为不必要的迭代烧 token。不要把这种模式用于要求即时响应的实时应用、基础分类这类简单例行任务，或评估标准太过主观、AI 评估者无法一致应用的场景。如果存在确定性工具（比如检查代码风格的 linter），改用它们。当资源约束的分量超过质量改进时，也要避免这种模式。

**示例**：评估者-优化者工作流适用于：

- 生成 API 文档（生成者撰写文档，评估者对照代码库检查完整性、清晰度与准确性）
- 撰写客户沟通（生成者起草邮件，评估者评估语气与政策合规性）
- 生成 SQL 查询（生成者编写查询，评估者检查效率与安全问题）

**专业提示**：在开始迭代之前就设定明确的停止标准。定义最大迭代次数和具体的质量阈值。没有这些防护栏，你可能陷入昂贵的循环：评估者不断挑出细枝末节的问题，生成者不断微调，而质量早在你停止迭代之前就已进入平台期。要知道何时「足够好」就真的够了。

## **选择合适的工作流模式**

合适的工作流模式取决于你的任务结构、质量要求与资源约束。

在选择模式之前，先尝试把任务作为单次智能体调用来完成。如果这达到了你的质量标准，就到此为止。如果没有，找出差距在哪里——这会告诉你该选哪种模式。

下面几个问题帮你决定：

- 单个智能体能有效处理这个任务吗？如果能，就完全不要用工作流。
- 任务有清晰的顺序依赖吗？用顺序式工作流。
- 子任务能够独立、同时地处理吗？更快完成会有帮助吗？考虑并行式工作流。
- 迭代打磨能带来有意义的质量提升吗？考虑评估者-优化者模式。

选定模式之后，还要考虑：

- **失败处理**：为每一步定义回退行为与重试逻辑。
- **延迟与成本约束**：它们决定你能运行多少个智能体、负担得起多少次迭代。
- **度量改进**：用单个智能体建立基线，这样你才能判断工作流是否真的有帮助。

**组合模式**：这些模式并不互斥。随着复杂度需要，你可以嵌套它们。

- 评估者-优化者工作流可以采用并行评估，让多个评估者同时评估不同的质量维度。
- 顺序式工作流可以在某些阶段包含并行处理，让多个独立操作在进入下一步之前完成。

关键在于让模式复杂度匹配实际需求。不要因为「可以」就加并行处理——只有当并发执行带来明确收益时才加。除非评估者-优化者回路能以可度量的方式提升输出质量，否则不要实现它。

## **审慎地演进你的工作流**

我们最好的建议：从能工作的最简单模式开始。如果顺序式工作流能应付你的用例，就不要加并行化。如果首稿质量已经足够好，就跳过评估者-优化者回路。

这三种模式为需求变化提供了清晰的升级路径。顺序式工作流可以在瓶颈阶段引入并行处理。智能体式的方法可以在质量标准收紧时加入评估。而且因为这些模式是模块化的，你不需要完全重写。
