# 运营一家 AI 原生的工程组织

> 原文：[Running an AI-native engineering org](https://claude.com/blog/running-an-ai-native-engineering-org/) · Claude 博客

多年来，工程人力一直是构建应用过程中最昂贵的部分。我们过去围绕软件规划与交付建立的每一套流程——先是瀑布式，后是敏捷——都是围绕这一成本构建的。

我的职业生涯始于 2000 年代初，当时我在做 Visual Studio。那个年代我们通过 CD-ROM 发布软件，制造截止日期是硬性的。一旦可以在线分发软件，我们便逐渐转向持续发布更新。如今我们再次改变工作方式，这一次是围绕编写软件所需的时间和人力。

在 Claude Code 团队，写代码、写测试和重构几乎不再拖慢我们的脚步。但当智能体编码（agentic coding）免去了亲手敲代码的必要后，瓶颈并没有消失，取而代之的是验证、代码审查和安全。

现在我们都能非常快速地生成大量代码，但这也带来了新的问题：这些代码正确吗？如何维护？还有我经常从工程管理者同行那里听到的一个问题：“你们是怎么让人类跟得上代码审查节奏的？”

## 那些悄然失效的流程

我们建立流程总有其原因：弥合某个缺口，或让某件事运转得更好。但当缺口不复存在、流程变得过时之后，它们很少会自行消失。当 Claude Code 团队开始把智能体编码作为默认工作方式时，我们的许多既有流程随之失效。下面是我们重写的那些规范，以及重写的原因。

### 规划：把路线图转向即时制定

旧规范是花大量时间做前期规划，因为编写代码的时间成本很高。我刚加入 Claude Code 团队时，我们制定了一份相当不错的六个月路线图，然后*恰恰因为* Claude Code，很多事情发生了变化，到第三个月它就已经过时了。

如今工程速度和吞吐量已经不同，所以我们规划冲刺（sprint）的方式也变了。我称之为即时规划（just-in-time / JIT planning），有点像 JIT 编译：如何在恰当时机做恰好适量的事？我们的规划仪式从设计文档转向了 PR 讨论或原型。这个领域变化太快，所以我们不做太多产品评审。现在的流程是：先做原型，让大量内部用户用起来，然后根据他们的反馈行动。

### 获取上下文：问 Claude，而不是问作者

过去工程师写代码时，回答大多数问题的第一步是找到写这段代码的人。如今我们所有的 PR 都有 Claude 协助，“这是谁改的？”这个问题已不再足够。我们的新规范是再深入一层：你真正需要知道的是什么？比如：你是在找谁引入了回归（regression）？找一位能回答客户问题的专家？还是想了解某个决策的来龙去脉？把这个问题抛给 Claude，并考虑 Claude 能否直接回答，包括借助更多数据和上下文来回答。

在 Claude Code 团队，无论问题是什么，我们的流程都会追加一句：“有没有办法把它自动化？”例如，让 Claude 每天早晨汇总客户反馈渠道，过去是我边喝咖啡边手动完成的例行公事，现在则变成我在后台自动运行的任务。

### 代码审查：信任但要验证

我们大量使用 [Code Review](https://code.claude.com/docs/en/code-review)。Claude 包揽了所有风格和 lint 检查、PR 反馈请求、在完整提交前抓出并修掉 bug，以及补充测试。而我们仍然明确需要人类的地方，是专业判断。

新规范是在关键之处保留人工审查：法律审查方面，我总是希望法务伙伴参与风险容忍度的判断；涉及信任边界和安全敏感代码时，我需要领域专家；产品经理和设计师也需要凭借产品感觉和品味参与进来。

不过，持续评估非常重要，因为随着模型不断改进，“信任”与“验证”之间的正确平衡也在不断变化。今天需要人类做的事，到了下一代模型可能就长得不一样了。

### 团队构成：角色边界日渐模糊

Claude 和 AI 重塑了整个团队的角色。我们的产品经理（PM）现在写很多代码，这看起来很有意思。有了 Claude，非传统意义上的程序员能够承担更多工程工作，而工程师也开始接手内容、设计这类传统上不属于技术侧的工作。

在 Claude Code 工程团队，我特别看重两类人才画像。一类是有产品感觉的创造性构建者：那些对交付能解决问题的产品怀有深切好奇与热情的梦想家。另一类是拥有深厚系统专业知识的工程师。举例来说，我刚加入团队时注意到我们缺少系统背景的专家，而构建 [Claude Code on the Web](https://www.anthropic.com/news/claude-code-on-the-web) 时正需要他们，以确保我们能让 Claude 在任何地方运行。

另一方面，我不太看重的是原始吞吐量——模型会搞定它。更重要的问题是你仍然需要人类专长的地方，那才是我应该关注的焦点。

|  | 之前 | 之后 |
|---|---|---|
| 规划 | 六个月的产品路线图。 | 即时规划（JIT planning）：做原型，让内部用户用起来，并根据反馈行动。 |
| 获取上下文 | 找到写代码的人，向他们请教。 | 先问 Claude，再想想所问之事能否自动化。 |
| 代码审查 | 人类审查一切。 | Claude 负责风格、bug 和测试，人类在领域专业知识重要的地方进行审查。 |
| 团队构成 | 固定角色：工程师写代码，PM 做规划，设计师做设计。 | 角色模糊：PM 做原型，工程师承担设计与上下文。招聘时看重创造性构建者和深厚的系统专业能力。 |

## 我们如何推行新规范

随着这些规范的变化，其中一些被定为团队原则强制执行，另一些则交由小型子团队（pods）自行摸索。Claude Code 核心团队有一组不容妥协的“必做之事”：

- **毫不松懈地“吃自己的狗粮”（dogfood）**：Claude Code 团队的每一位成员，包括跨职能合作伙伴，都使用 Claude Code（以及 Claude Cowork）。我们总是在思考如何让 Claude 帮助我们更快、更高效地完成工作。
- **尽可能保持团队扁平。** 我加入 Claude Code 时，希望每位管理者都先从 IC（个人贡献者）做起，通过实际交付学会如何在团队中成为一名高效的工程师，真切体会并理解在 Anthropic 当工程师是什么感觉。Claude Code 和 Claude Cowork 共享同一个团队总使命。管理者支持各个工作 pods，同时保持团队的敏捷性，让人们可以流向工作所在之处。
- **对不再有效的流程果断叫停：** 最后，我们会不断追问为什么事情要按现在的方式做。当某件事不再合理时，团队成员获得明确授权，可以质疑并废除旧流程。

不过，在这几条规则之内，每个 pod 都有很大的自主权。他们可以自行调整如何用 Claude 做分诊（triage）、如何运行规划仪式或站会，以及哪些工作流优先被“Claude 化”。

## 如何判断新流程已经落地

每位工程管理者在推行变革时，都应立刻开始跟踪以下三个数字。

- **新人上手时间在下降：** 一位工程师、设计师或 PM 多久能开始发挥作用？在我们团队，这比一年前快得多，工程师现在第一周就能交付真正的代码。
- **PR 周期时间在下降：** 这一项值得深入挖掘，因为它能帮你定位流水线在哪些环节难以扩展。当我们生成的代码多得多时，构建系统和持续集成（CI）有时会跟不上。
- **Claude 辅助的提交在上升：** 对我们而言，默认情况下每次提交都有 Claude 协助。过去四个月里，我印象中没见过任何一次没有 Claude 协助的提交。

关于第三点，不要把吞吐量与成功混为一谈。吞吐量只是一个指标，真正的指标是衡量你试图解决的那个问题本身。方向对齐得当，吞吐量才能帮助你更快地解决问题。

## 开始行动

如果只留给你一句话，那就是：**挑出你最吵闹的那条工作流。** 它可能是成本最高的那条，可能是你最畏惧的那条，也可能是团队最不期待的那条。然后问自己：它还在发挥应有的作用吗？如果是，能否将它自动化？

我曾待过一个团队，每周有一次代价高昂的评审会，一大群人挤在会议室里。我注意到除了轮到自己汇报状态时，每个人都在用笔记本电脑。他们会抬起头，说完状态，又低下头继续看电脑。我问了一个简单的问题：“我们为什么还要开这个会？这看起来是在昂贵地消耗大家的时间。”就是这一个问题让所有人意识到这个会并不必要，于是我们取消了它。

那么，问问你自己：你的工程工作流中，哪一部分可以考虑自动化，甚至干脆砍掉？
