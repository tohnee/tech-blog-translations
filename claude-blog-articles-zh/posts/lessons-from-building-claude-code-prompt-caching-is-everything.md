# 构建 Claude Code 的经验教训：提示缓存就是一切

> 原文：[Lessons from building Claude Code: Prompt caching is everything](https://claude.com/blog/lessons-from-building-claude-code-prompt-caching-is-everything/) · Claude 博客

工程界常有人说「缓存主宰我身边的一切（cache rules everything around me）」，对智能体来说，这条规律同样成立。

Claude Code 这类长时间运行的智能体产品之所以可行，靠的是[**提示缓存**](https://x.com/RLanceMartin/status/2024573404888911886)（prompt caching）——它让我们能够复用此前往返的计算结果，显著降低延迟和成本。

在 Claude Code 团队，我们把整个执行框架（harness）都围绕提示缓存来构建。高的提示缓存命中率能降低成本，也让我们能为订阅套餐提供更宽松的速率限制，所以我们为提示缓存命中率设置了告警，一旦过低就宣布 SEV（严重事故）。

以下是我们在大规模优化提示缓存过程中学到的（往往反直觉的）经验。

## **围绕缓存来编排你的提示**

Claude Code 的系统提示经过精心组织，让稳定的部分保持缓存命中，只有对话本身逐轮增长。

提示缓存的工作方式是前缀匹配——API 会缓存请求从开头一直到每个 `cache_control` 断点之间的所有内容。这意味着内容摆放的顺序至关重要：你要让尽可能多的请求共享同一个前缀。

提示的组织方式不仅影响缓存命中，也影响输出质量——[提示工程基础](https://claude.com/blog/best-practices-for-prompt-engineering)是这门功课的另一半。

最佳做法是静态内容在前，动态内容在后。对 Claude Code 来说，结构如下：

1. **静态系统提示**与工具（全局缓存）
2. **CLAUDE.md**（项目内缓存）
3. **会话上下文**（会话内缓存）
4. **对话消息**

这样我们就能最大化共享缓存命中的会话数量。

但这种方式可能出奇地脆弱。我们曾因各种原因破坏过这个顺序，比如：把精确的时间戳放进静态系统提示、以非确定性的方式打乱工具定义的顺序，以及更新工具的参数（例如 Agent 工具可以调用哪些智能体）。

## **用消息来传递更新**

有时你放进提示里的信息会过时，比如时间变了，或者用户修改了某个文件。直接更新提示看似诱人，但那会导致缓存未命中（cache miss），最终可能让用户付出相当高的代价。

不妨考虑改为在智能体的下一轮中通过消息传入这些信息。在 Claude Code 中，我们会在下一条用户消息或工具结果里加入一个 <system-reminder> 标签，携带更新后的信息提供给模型，这有助于保住缓存。

## **不要在会话中途更换模型**

提示缓存是按模型隔离的，这会让提示缓存的账变得相当反直觉。

举例来说，如果你与 Opus 的对话已经进行到 100k token，想问一个相当简单的问题，切换到 Haiku 反而比让 Opus 来回答更贵，因为我们需要为 Haiku 重建提示缓存。

如果你确实需要切换模型，最好的方式是使用子智能体（subagent）；延续上面的例子，你可以派一个子智能体让 Opus 就它需要完成的任务准备一条「交接」消息给另一个模型。我们经常对 Claude Code 的 Explore 智能体这样做，它们使用的正是 Haiku。

## **绝不在会话中途增删工具**

在对话中途更换工具集，是人们破坏提示缓存最常见的方式之一。这看起来很直觉——只把模型当前需要的工具给它就好。但由于工具是缓存前缀的一部分，增删任何一个工具都会让整段对话的缓存失效。

**用计划模式（Plan Mode）围绕缓存做设计**

[计划模式](https://code.claude.com/docs/en/common-workflows)是围绕缓存约束设计功能的绝佳范例。直觉上的做法是：当用户进入计划模式时，把工具集换成只包含只读工具——但那样会破坏缓存。

我们的做法是始终在请求中保留*全部*工具，并把 EnterPlanMode 和 ExitPlanMode 本身作为工具。当用户开启计划模式时，智能体会收到一条系统消息，说明它正处于计划模式以及相关指令：探索代码库、不要编辑文件、计划完成后调用 ExitPlanMode。工具定义从未改变。

这还带来一个额外的好处：由于 EnterPlanMode 是模型可以自行调用的工具，当它检测到一个难题时，可以自主进入计划模式，而不会破坏任何缓存。

**用工具搜索做延迟加载，而不是移除**

同样的原则也适用于我们的 [Tool Search Tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)。Claude Code 可能加载了几十个 MCP 工具，把所有工具都放进每个请求会很昂贵，但在对话中途移除它们又会破坏缓存。

我们的解法是 `defer_loading`。我们不移除工具，而是发送轻量存根（stub）——只有工具名，并带上 `defer_loading: true`——模型可以在需要时通过工具搜索「发现」它们。完整的工具 schema 只在模型选中它们时才加载。由于同样的存根始终以同样的顺序存在，缓存前缀得以保持稳定。

你也可以通过我们的 API 使用 [Tool Search Tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool) 来简化这一过程。

## **在不破坏缓存的前提下压缩上下文**

当上下文窗口被填满时，Claude Code 会 fork 出一个带缓存的调用来总结对话，然后用摘要替换原始消息继续运行。

[上下文压缩](https://platform.claude.com/docs/en/build-with-claude/compaction)（compaction）发生在上下文窗口用尽之时。我们总结目前为止的对话，然后带着这份摘要开启新的会话。

压缩与提示缓存的交互方式很容易踩坑。要压缩一段对话，你必须把完整对话发给模型，它才能写出摘要。最简单的做法是发起一个单独的 API 调用，带上自己的系统提示（类似「请总结这段对话」）且不附加任何工具——但这恰恰是成本陷阱所在。提示缓存只有在请求的前缀与已缓存内容从头开始逐字节一致时才会生效。你的主对话是在某个系统提示和工具集下缓存的；而总结调用使用不同的系统提示且没有工具，两者的前缀从第一个 token 就分道扬镳，任何缓存都用不上。结果就是，你要为发进去的整段对话支付完整、无缓存的输入费率——而且对话越长（也就是说，你越需要压缩），这一次调用的代价就越高。

**解法：缓存安全的 fork**

执行压缩时，我们使用与父对话*完全相同*的系统提示、用户上下文、系统上下文和工具定义。我们把父对话的消息放在前面，再把压缩提示作为新的用户消息追加在末尾。

从 API 的视角看，这个请求与父对话的上一个请求几乎一模一样——相同的前缀、相同的工具、相同的历史——因此缓存前缀得以复用。唯一新增的 token 就是压缩提示本身。

不过这也意味着我们需要预留一个「压缩缓冲区」，确保上下文窗口里有足够的空间容纳压缩消息和摘要的输出 token。

压缩固然棘手，但幸运的是你不必亲自踩这些坑——基于我们从 Claude Code 学到的经验，我们已把[上下文压缩](https://platform.claude.com/docs/en/build-with-claude/compaction#prompt-caching)直接内建到 API 中，你可以在自己的应用里直接套用这些模式。

## **经验总结**

以下是我们发现的、在构建智能体时优化提示缓存很有用的一些模式：

1. **提示缓存是前缀匹配。**前缀中任何位置的改动都会使其后的一切失效。围绕这一约束设计你的整个系统。把顺序摆对，大部分缓存收益就白送。
2. **用消息，而不是改系统提示。**你可能想通过编辑系统提示来做进入计划模式、更新日期之类的事情，但更好的做法是把它们插入对话中的消息里。
3. **不要在对话中途更换工具或模型。**用工具来建模状态转换（比如计划模式），而不是更换工具集。用延迟加载代替移除工具。
4. **像监控可用性一样监控你的缓存命中率。**我们对缓存失效设置告警，并当作事故处理。缓存未命中率几个百分点的变化，就能对成本和延迟产生巨大影响。
5. **fork 操作必须共享父对话的前缀。**如果你需要运行一次旁路计算（压缩、总结、技能执行），请使用完全一致的缓存安全参数，这样才能在父对话的前缀上命中缓存。

Claude Code 从第一天起就是围绕提示缓存构建的；为了在构建智能体时获得最佳效果，我们也建议你这样做。
