# Anthropic 日本业务拓展代表如何用 Claude Managed Agents 安排一天的工作

> 原文：[How an Anthropic BDR in Japan runs his day with Claude Managed Agents](https://claude.com/resources/articles/how-an-anthropic-japan-business-development-representative-runs-his-day) · Claude 博客

*一位业务拓展代表如何用 Claude Managed Agents 和 Claude Tag 清空他的入库线索队列，并起草双语客户邮件。*

作为 Anthropic 日本团队的业务拓展代表（BDR），我的工作是向日本企业展示 Claude 如何简化和自动化他们的工作流；但直到今年早些时候，我自己的工作大部分还是手工完成的。每天早上，我要花上几个小时分派线索、做线索资格审查，然后用日语或英语写邮件。剩下的时间用来更新 CRM，而且经常滞后一天甚至更久。现在，我的智能体会在我一天开始之前把大部分工作准备好，我只需要审阅。

我搭建的第一个由 Claude 驱动的工作流相当粗糙，但确实管用。我会把工作一件一件交给 Claude，纠正它做错的地方，并把这些纠正保存下来。渐渐地，它长成了几个智能体，各自负责一项例行工作。

消息很快传开了，同事们开始向我索要提示词和技能，好搭建他们自己的。我能发给他们的只有一个 zip 压缩包，里面是我的技能和知识库里的几个 Markdown 文件；他们得把文件上传到 Claude，再回答一轮配置问题，才能让东西跑起来。我自己的配置也越来越难以追踪。每个智能体都由一个技能、一个定时任务和一个共享文件夹组成，而我改动它们的方式是在随手打开的任何对话里让 Claude 去改，于是同一个技能会被许多不同的对话反复编辑。

我想在一个地方一次性定义好每个智能体，并且能看清我对它做过的每一次改动。于是我决定试试 [Claude Managed Agents（在新标签页中打开）](https://platform.claude.com/docs/en/managed-agents/overview)（beta）——我们在 Claude Platform 上的托管智能体基础设施。

一开始我有些犹豫。文档里讲的是调度、工具和凭据保管库，而我是个销售，所以我想当然地认为 Managed Agents 是给那些能搭建并维护所需基础设施的开发者用的。我还是试了，因为我的智能体已经存在，我只需要把它们迁移过去。

结果发现我并不需要成为开发者。我用平实的语言描述每个智能体的职责，Claude 写了几个简短的配置脚本，我在笔记本电脑的终端里把它们跑起来。（如果你要从零开始，Console 里还有一个 [quickstart](https://platform.claude.com/workspaces/default/agent-quickstart)，提供现成的智能体模板。）从那以后，我再没有什么基础设施需要照看。

在这篇文章里，我会讲讲我是如何设计和搭建这支智能体团队的原型、为什么把它迁到 Managed Agents、Claude Tag 如何接手一切例行之外的事情、这一切如何改变了我的每周工作，以及我想对希望自建智能体来自动化手工重复工作流的销售人员说些什么。

## 设计我的智能体团队

我把工作流拆分到几个智能体上，给每个智能体一个明确的职责。单一职责让每个智能体都容易推理、容易追踪，尤其是在出问题的时候。我还给每个智能体取了日语名字，因为它们的日常工作主要用日语。它们合起来叫 *Nakama*，意思是"伙伴们"（the crew）；更字面地说，就是与你并肩工作的同伴：

* ***Furiwake***（"分派"）最先启动：它读取当天的入库线索队列，把每条线索分派给团队里合适的销售代表，平衡各人的线索数量与优先级，并核对当天谁在岗，从而在我们任何人开始工作之前就让每条线索都有归属。每次运行结束时，它会向一个专门的 Slack 频道发布报告（进来了哪些线索、各自分派给了谁），方便我追踪交接情况。
* ***Sabaki***（"处理"）负责分诊分配给我的线索：对每条线索做资格审查，按预设标准归类，执行该类别的既定下一步（起草一封引导对方使用自助服务的回信，或撰写一封定制化的首封邮件），更新 Salesforce 中的线索记录，并起草首次触达邮件。草稿内容来自 Nakama 共享的知识库——一个所有智能体都会读写的[记忆存储（在新标签页中打开）](https://claude.com/resources/articles/claude-managed-agents-memory)（后文详述）。
* ***Henji***（"回复"）每小时扫描一次我的收件箱，找出需要回复的客户邮件，并根据邮件线程的语言，用日语或英语准备回复草稿，同样取材于 Sabaki 所用的知识库。我可以审阅、编辑并发送草稿。
* ***Shoudan***（"商机"）读取近期的客户互动，把更新推送到 [Salesforce](https://claude.com/resources/articles/salesforce-in-claude)，让商机记录无需手工录入也能保持最新。
* ***Nokori***（"剩余事项"）在一天结束时运行：扫描我的日历，读取附带的会议转录稿，为每场会议生成摘要，并起草跟进事项——同样来自那个共享知识库。

每个智能体都按[计划](https://claude.com/resources/articles/whats-new-in-claude-managed-agents)运行。第六个智能体是 Nakama 的协调者，相当于这支团队的运营经理。它在各智能体的运行间隙更新它们的指令和共享知识库。当我想改变某个智能体的工作方式时，我就在 Nakama 的 Slack 频道里用平实的语言写下要求。只有我才能提交修改智能体指令和系统提示的请求。协调者大约每 15 分钟检查一次那个频道，领取请求并完成更新。

## 在 Claude 中搭建团队原型

起步阶段并不需要 Managed Agents。我先在 Claude 里搭出了整个团队的原型，用的是下面这几样东西：

* 每个智能体一个技能：一项工作的指令。
* 每个技能配一个定时任务，省得我手动运行。
* 笔记本上的一个共享文件夹作为知识库，每个技能把学到的东西写回去：它起草的内容与我实际发出的内容之间的差异，以及过程中挖到的任何新信息。

在 Managed Agents 上，技能变成了智能体的系统提示，定时任务变成了[智能体部署上的调度（在新标签页中打开）](https://platform.claude.com/docs/en/managed-agents/scheduled-deployments)，共享文件夹变成了记忆存储。我仍然用平实的语言提修改要求，但现在都在同一个 Slack 频道里进行，而且对智能体指令的每次修改都会保存为新版本，因此每个智能体都保留着自己指令的编号历史。我的建议是：先在 Claude 里起步，等智能体多到你实在顾不过来时，再把它们迁到 Managed Agents。

## 在 Claude Managed Agents 上运行团队

在 Managed Agents 上，对我的工作流最重要的有三件事：

**智能体可以在后台运行**

不管我的笔记本是否开着，甚至离线，智能体都会按计划运行。调度是每个智能体部署的一部分。我在 Claude 里也能给技能配定时，但那些调度都是在自己的应用里设置的任务。在 Managed Agents 上，我在 Console 里设置频率和时区，就放在已部署智能体的指令和工具旁边，不用额外维护任何 cron 任务。如果某次运行出了问题，我可以在 Console 里打开它，看到智能体走过的每一步。而且当我试用某个改动时，计划中的运行仍会使用已部署的版本，半成品编辑不会混进明天的运行。

**Nakama 共享同一份记忆，并从我的修改中学习**

每个智能体读写同一个[记忆存储（在新标签页中打开）](https://claude.com/resources/articles/claude-managed-agents-memory)，所以任何智能体都能利用其他智能体的学习成果。智能体会把它们写的草稿与我实际发出的邮件做对比，把每一处差异保存成一条关于我如何措辞的笔记。它们也会保留在查找答案过程中从内部文档和官方网站里挖到的任何新信息。我在 Henji 的草稿里修正过一次措辞，Sabaki 和 Nokori 就不会再犯同样的错误。

**凭据存放在带作用域权限的托管保管库中**

我的智能体可以访问我的邮箱和我们的 Salesforce 记录，但这些都是客户对话和公司记录，我希望这种访问是受控的。凭据存放在[托管保管库（在新标签页中打开）](https://platform.claude.com/docs/en/managed-agents/vaults)中，用来保护智能体登录外部服务时使用的凭据，例如 OAuth 访问令牌和刷新令牌、API 密钥以及个人访问令牌。每个智能体的部署只使用其职责所需的保管库，智能体本身永远看不到凭据，而我可以一步撤销访问权限。

## 把后续步骤交给 Claude Tag

对 Nakama 产出的大部分内容，我只需要在收件箱里读一下草稿然后发送，或者扫一眼更新后的 Salesforce 记录。但有些事项还需要后续步骤，比如弄清楚升级路径或采购流程，或者把问题上报给其他团队。

遇到这类情况，智能体不会停下来等我。它们会把事项交给 [Claude Tag（在新标签页中打开）](https://www.anthropic.com/news/introducing-claude-tag)（beta）。Claude Tag 是把 Claude 设置成我们 Slack 工作区的一名成员：在它加入的任何频道里，无论是人还是我的某个智能体，都可以 @Claude 提出请求，它会接下请求并在该线程中处理。在你的工作区里配置好之后，就没有什么新东西要学了。你像 @ 一位同事那样 @ Claude 就行。

在我的配置里，流程是这样的。某个智能体把待办事项发到 Nakama 的 Slack 频道并 @ Claude。Claude 阅读线程，核对我们的规则和适用的条款，列出各种选项，并起草所需内容。当某个步骤需要我审阅或签字时，它会 @ 我。如果必须等客户或其他团队先回复，Claude 会给自己设置提醒，在指定日期回来查看。在下面的线程里，它设了一个周二的提醒，用来检查客户是否已回复、交易审核团队（deal desk）是否已处理工单。提醒到期时，Claude 会核查这两件事，并在同一线程里发布进展。如果有人需要催促，它会起草消息并 @ 我去发送。

![一段人类、Claude 与智能体之间对话的界面示意图](https://assets.claude.com/407d1a67eadd3ebd1d4ec34fd1fabebb42b64829.png)

Claude 还会发布一份关于产品和定价更新的晨报。Nakama 的协调者会领取这份简报，并把必要的改动写进共享知识库。

## 我的一周发生了哪些变化

既然 Claude 能在没有我手工介入的情况下准备入库线索的回复、（基本上）让 CRM 记录保持最新，我的角色就变成了审阅一切需要人来判断的事情。一份成文的规则手册界定了每个智能体的职责边界，而定价问题、敏感客户或含糊的请求之类的事项会转到我这里。来自 Henji、Sabaki 或 Nokori 的每一封邮件草稿，顶部都附有一段简短摘要说明情况，这样我就不必追溯整个邮件线程来了解背景：我读摘要、确认、做修改，然后发送。

![一封由 Claude 起草、供人工审阅的邮件截图](https://assets.claude.com/209fde33711300fd8cfb2f1fc7005f21bca2a20d.png)

翻看 Nakama 每周完成工作的日志，把每项任务按我手工完成所需的时间折算，这支团队每周帮我省下大约 60 小时的工作。我把腾出来的时间用在智能体（目前）还无法有效完成的事情上：与客户的交谈、外呼策略、跨职能项目，以及帮助同事搭建他们自己的智能体团队。

## 把智能体设计得更高效

计划运行的智能体每天都在跑，不管我有没有盯着，所以浪费会累积起来——无论是成本还是可靠性。最常见的错误包括：在原有指令上不断追加而不是更新，给智能体超过任务所需的上下文，以及所有任务都用最大的模型、最高的努力等级来跑。

让这些智能体保持高效的主要因素，在于我设计团队的方式：每个智能体只有一个职责，所以它的指令始终聚焦于此；每个工作型智能体按调度运行，醒来、完成一轮处理、然后停止；智能体共享记忆，所以一次纠正能在各处复用。

另一个重要因素是每个智能体运行在哪个模型上。一旦某个智能体的职责定义清楚，它可能并不需要我们最强的模型。Furiwake 和 Shoudan 依照成文的规则手册办事，所以运行在较小的 Sonnet 上。Sabaki、Nokori 和协调者运行在较大的 Opus 上，因为它们的判断要求更高。协调者的需求最强，因为它编辑其他智能体的指令，一次糟糕的编辑会波及所有智能体。Henji 的判断需求与 Sabaki 相当，因为每个客户的邮件都不一样，但它的运行频率高于任何其他智能体，整个工作日都在跑。每次都让 Opus 来跑会是最贵的选择，因此我在 Managed Agents 里用了[顾问策略（在新标签页中打开）](https://claude.com/resources/articles/the-advisor-strategy)：Henji 运行在 Sonnet 上，当遇到自己无法做出的决定时，它向 Opus 征询意见。顾问读取 Henji 到目前为止的工作，返回一个计划、一处纠正或者一个停止信号，然后由 Henji 完成草稿供我审阅。我还把每个智能体的努力等级（effort level，模型回答前思考多久）与模型分开设置，只在推理较难的地方调高，比如 Henji 的回复。

## 我的收获

有三点我想转告给任何准备搭建自己智能体团队的人。

1. **不必每次都写详细提示词。** 把职责描述一次，让 Claude 起草，修正草稿，并让它把修正记住。
2. **知识库比提示词更重要。** 每一次修正、每一次过往互动都保存在所有智能体都能读写的地方，这样 Claude 的上下文来自知识库而不是更长的提示词。经过几百轮成本很低的"起草—修正—保存"，草稿才开始听起来像我。
3. **更早地给 Claude 更多空间。** 起初我一直做那些我以为非我不可的事：更新知识库，或者手工编辑每个智能体的指令。一旦我放手，两件事都运转良好。现在智能体自己把学到的东西写进知识库，协调者在我用平实英语提出要求后更新其他智能体的指令。对于那些本可放心交给智能体的工作，我过去太谨慎了。
