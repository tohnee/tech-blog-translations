# Slack 中的自助式数据分析：Anthropic 如何部署 Claude Tag 回答临时性问题

> 原文：[Self-service data analytics in Slack: how Anthropic deploys Claude Tag for ad-hoc questions](https://claude.com/resources/articles/self-service-data-analytics-in-slack-how-anthropic-deploys-claude-tag-for-ad-hoc-questions) · Claude 博客

在[上一篇博文](https://claude.com/resources/articles/how-anthropic-enables-self-service-data-analytics-with-claude)中，我们介绍了如何通过三类主要交付物，让 Claude 以约 95% 的准确率回答数据分析问题：

* 一份受治理的语义层（semantic layer）；
* 一组把我们的分析惯例编码进去的 skill 文件；以及
* 一套用来衡量表现的评估套件。

那篇文章聚焦于 [Claude Code](https://claude.com/product/claude-code)（我们数据科学家和数据工程师的主要开发界面），以及提升智能体准确率的最佳实践。

本文讨论 Anthropic 数据团队如何把这套基础延伸到公司其他同事工作的地方——用的是 [Claude Tag](https://claude.com/product/tag)（公开测试版），它是我们 Slack 数据分析智能体的基础。任何人都可以向它提出与数据相关的问题，并得到由**分析师所用的同一套受治理定义**支撑的答案。

## 在 Slack 中部署数据分析智能体的最佳实践

让智能体变得*准确*，和让它*部署到非分析师也能使用的地方*，后来被证明是两件相当不同的事。上一篇关于准确率的建议在这里依然适用，我们不再重复。

本文将介绍过去一年里我们最重要的五点经验：如何在 Slack 中部署数据分析智能体，以及应当如何考虑分发、权限、数据新鲜度和可观测性。

### 像刷新数据模型一样频繁地刷新 skills

你可以用一个 [skill](https://claude.com/resources/articles/steering-claude-code-skills-hooks-rules-subagents-and-more) 教 Claude 按照你的风格和需求完成任务——skill 是一个 markdown 文件，内含自然语言指令，以及 Claude 在需要时可以引用的文件。

我们做的最重要的一项架构决策，是把 skill 文件当作**持续刷新的服务化内容**，而不是发布一次就束之高阁的东西。

数据模型一天可能变好几次。比如某个列被重命名、某个指标定义被修正、某张表被废弃。每一次变更都需要在相当短的时间内落到 skill 文件里。如果 Claude 读到的是上周二那份 skill，它就会带着十足的自信给出上周二的错误答案。

这种倾向尤其危险，因为数据消费者如今与他们判断答案准确性所需的上下文完全分离了。他们不是在看着一张带趋势线或相关指标的仪表盘来做“嗅探测试”。在 Slack 里，他们可能只收到一两个数据点；如果那不是他们经常看的数据，他们很可能就会接受那个自信却错误的答案。

为了驾驭这种不断变化的环境，Claude Tag 的运行时挂载了我们数据仓库的 skills/ 目录，并且**在每次对话时重新读取**。skill 文件不过是磁盘上的 markdown，智能体读它们的方式与读取任何项目文件相同。

### 给智能体的 skills 不应止于“知道该查什么”

我们最初用 Claude Tag 部署数据分析智能体时的直觉，是创建一个“知识 skill”，教 Claude 该用哪些表、我们的语义层如何组织，然后就收工。我们很快发现，这种做法能给出*正确的数字*，却止步于*有用的洞察*。

大多数数据消费者倾向于提出开放式、模糊的问题，比如“这次下滑是什么造成的？”“你能预测一下月底会落在哪吗？”“把这份数据做成漏斗图给我看看。”要回答这些问题，智能体不仅要知道*数据在哪里*，还要知道*分析师会如何使用这些数据*。

因此，在这份知识 skill 之外，我们还给 Claude Tag 挂载了额外的分析类或 runbook 类 skills，包括：

* **预测**：何时以及如何拟合简单的趋势、季节性假设，以及何时应当拒绝——因为序列太短或噪声太大。
* **队列与留存分析**：标准的队列定义、向管理层汇报所用的留存曲线模板，以及会绊倒朴素实现的各种陷阱（左删失、幸存者偏差）。
* **漏斗分析**：关键产品漏斗的权威阶段定义，让“用户在 onboarding 的哪一步流失？”在不同回答中保持一致。
* **图表**：可视化惯例，比如哪个问题该用哪种图、配色方案，以及什么时候表格比图表更清楚。
* **分析写作**：如何组织一项发现（先给 TL;DR，再给数字、机制、注意事项），以及在给定置信度下应当采用何种程度的保留表述。

每个数据团队大概都已经有这些惯例，只是它们通常活在某个人的脑子里，偶尔才被记录下来。把它们写成 skills，能确保 Claude 像你的数据科学家一样一致地应用它们。

### 连接业务上下文，而不只是数据仓库

即便是知识 skills 与 runbook skills 的组合，也不总能回答一个问题。当有人问“周二注册量为什么下降了？”，答案往往不在数据模型里，而是散落在 Slack 线程、故障跟踪器、发布说明和文档中。

为了填补这些缺口，我们把 Claude Tag 接入内部知识索引——它编目了全公司的文档、讨论和事件。当智能体看到某个指标发生变化，它可以在这个索引中搜索*同时期的上下文*：当天早上开启的故障工单、被翻转的功能开关、某人在频道里分享的竞品公告。

此时的答案就会变成：“周二注册量下降 12%：当天上午 9 点到 11 点有一个支付服务故障，下滑集中在受影响的地区。”

![](https://assets.claude.com/142616e5c6d1549e829ef9b439f759032222cb6b.png)

如果你的组织有知识图谱、内部搜索，甚至只是组织良好的故障与变更日志 feed，把它们接入 Claude Tag 是你在数据仓库本身之外能添加的杠杆最高的信息。你也可以[让 Claude Tag 读取 Slack 中关键频道并从中获取上下文](https://claude.com/docs/claude-tag/admins/attach-to-scope#attach-to-a-channel)。

### 有意识地设定服务账号权限

Claude Tag 是以服务账号的身份查询你的数据仓库的，而不是以提问的那个人的身份。这本身是正确设计（你总不希望每个 Slack 用户都需要直接的数据仓库凭据），但**[每个能 @ 到这个 bot 的人，都拥有这个 bot 的数据访问权限](https://claude.com/resources/articles/agent-identity-access-model)**。这里没有按用户的行级安全：服务账号能读什么，频道里任何人就能问什么。

我们从五个方面应对（我们建议你认真对待，因为它很容易做错，且很难撤回）：

**1. 把服务账号的范围限定在受治理数据内。** 在 Anthropic，Claude Tag 的服务账号可以读取语义层的输出表和支撑它们的精选数据集（curated marts）。它不能读取原始事件流、staging schema，或任何个人沙箱中的东西。如果某个问题需要边界之外的数据，智能体会直接说明，而不是猜测。这也是正确的用户体验，因为受治理层之外的数据尚未经过验证。

**2. 在列级别对 PII 分类，并拒绝授予服务账号相应许可。** 受治理数据并不自动等于 PII 安全数据（例如，一张精选表仍可能带有电子邮箱地址）。我们维护一份带列级血缘（column-level lineage）的数据目录，因此每一列的来源和下游流向都是已知的。当新列进入时，Claude 会扫描它们，标出可能是 PII 的候选，交由人工复核。随后由人在列的元数据中应用分类，血缘会把该标签传播到派生表。由于 Claude Tag 的服务账号不持有 PII 许可，数据仓库的列级访问控制会让智能体看不到任何 PII 列。它可以查询那张表，但敏感列就是不可读。

**3. 在 skill 本身中记录连接路径。** 我们的数据仓库 skill 有一节专门讲智能体*如何*连接（是通过 CLI、直连 API，还是 MCP server），以及每条路径的鉴权究竟如何工作。这个不起眼的功能让我们能区分两种情况：智能体干净地失败（“我无法从这个界面访问数据仓库，原因如下”），还是令人困惑地失败（查询静默地跑在了错误的项目上，或鉴权提示被转发到了不该去的地方）。当连接机制写在 skill 里，智能体就能解释自身的约束。

**4. 把 Claude 的频道成员资格视为一种访问授权。** 把 Claude Tag 加进一个 Slack 频道，实际上就是把该频道成员的读取权限，授予了智能体能查询的一切。我们把这一点明确化：Claude 由数据团队成员加入频道，频道清单归数据团队所有。

**5. 为每一次查询打标签。** 对每一次数据仓库查询，Claude Tag 都会带上标签，标明界面、对话以及发起请求的用户（在 Slack 提供该信息的地方）。这在查询时并不强制执行任何规则，但提供了成本归因和审计追踪（事后你可以确定是谁提出了那个扫描了 4 TB 数据的问题）。

我们的总体姿态是：Slack 中的数据分析智能体是你受治理数据仓库的**共享只读副本**，我们也尽量按这个定位来划定它的范围。

### 为每个答案加上监测

判断智能体是否给出了充分的答案，不是靠肉眼能看出来的。

我们为 Claude Tag 处理的每个问题记录一条结构化事件。其中包括：

* 加载了哪些 skill 文件、版本是什么；
* 用户是否用 👍/👎 作出反应，或回复了更正；以及
* 它触及的表上存在的任何数据质量警告。我们还会在答案页脚中显示数据质量警告，这样数据过期的告警会出现在数字旁边，而不是隐身不见。

这些遥测数据支撑两个视图。一个跟踪**采用率**，即按界面和领域划分，有多大比例的智能体查询走的是受治理层而不是临时 SQL。另一个跟踪**正确性**，按领域用 👎 反应和更正的比例衡量。这是两次评估运行之间对准确率的在线代理指标。

![](https://assets.claude.com/6b2efdbb4fb54c3220f5c57ab7db76ec0e2fdf38.png)

采用率指标后来成了我们跟踪的最具行动指导意义的数字。当某个领域的采用率下降，几乎总是意味着两种情形之一：某个 skill 文件发生了漂移，或者出现了一类语义层尚未覆盖的新问题。

## 这如何加速自助式分析的普及

### Claude Tag 线程成了新的会议

我们最喜欢、也最有效的 Claude Tag 线程，通常有多个人在里面。在这些场景中，我们看到人们贡献想法和上下文，而 Claude 承担跑腿的活。

例如，一位数据团队成员问 Claude，为什么某个收入仪表盘比平时多花了几分钟才加载出来。Claude 发现查询结果没有被缓存，并且有一个 bug 拖慢了结果到达页面的速度。

Claude 通知了仪表盘负责人，后者决定立刻修复缓存，同时把 bug 作为另一条线并行处理。

这位负责人接着问还有哪些仪表盘变慢了，结果发现有几十个受同一个缓存错误影响。Claude 编写了缓存修复，数据团队成员做了审查，不到一小时，所有受影响的仪表盘都恢复了满负荷运转。

![](https://assets.claude.com/0b59bec1e5baa7be2549ac7f12603714efbfb922.png)

这些线程是公开的，这在多个方面都有帮助。旁读的人能顺带获得上下文（什么坏了、为什么、怎么修好的），而不需要有人专门为他们写总结。更重要的是，他们不必保持被动阅读者的身份。任何知道有用信息的人都可以跳进来贡献，就像上面例子中的团队成员那样。

所以，把智能体留在共享频道里，把工作留在线程里而不是 DM 里，因为线程可以充当一份可供审阅的历史记录。

### Claude Tag 处理重复性任务

很多数据工作是周期性的：管道健康检查、KPI 监控等等。你可以[让 Claude 创建 loops](https://www.youtube.com/watch?v=SlGRN8jh2RI)，按计划或在出现异常变化时处理周期性任务。我们实现过的一些数据相关例子包括：

* **主动播报**：Claude 在每周站会前提供摘要：上周发生了什么变化、与前一周相比如何、有什么值得注意。
* **测试监控**：当我们监控一次发布或实验时，Claude 一天多次提供播报。在最近一次实验中，它注意到设置在过程中发生了变化，帮我们及早发现并修复。
* **可观测性**：其他 loops 监控我们的管道和仪表盘。如果管道失败，Claude 会开始排查、起草修复方案，并提醒值班人员。如果某个 KPI 出现意外变动，Claude 会给出可能的解释——假期效应？上游数据变更？——并在任何人打开仪表盘之前先行核验。
* **分诊**：另一个 loop 跟踪我们的数据问题频道。对于每个新问题，它会做出判断：直接回答、启动更深入的调查，还是引入人工。等数据团队有人来看的时候，大部分工作已经做完了。

Claude 也可以帮你设计这个 loop。@Claude 问它在你频道里见过哪些重复性工作，以及它能如何帮忙。

### 在需要时主动介入

你可以让自己选择的任何频道中的 Claude 更主动：旁读，并在需要时介入帮忙。过去一个月，在我们的一个数据频道里，Claude Tag 回答了人们提出的 75% 以上的问题，通常在一两分钟内完成，甚至无需被点名。

例如，一位 Anthropic 团队成员在公开频道里问，某个仪表盘是否包含了一个新的用量类别。90 秒内，Claude 回答了数据是如何定义的、确认新细分确实缺失、提出修复方案，并起草了一个 PR。一位数据科学家审查并批准。随后 Claude 合并了 PR 并刷新了仪表盘。

## 上手

如果你已经完成了[第一篇博文](https://claude.com/resources/articles/how-anthropic-enables-self-service-data-analytics-with-claude)里的工作，Slack 部署基本上就是管道工程，不过顺序很重要：

1. **权限优先。** 在写第一行智能体代码之前，先决定服务账号能读什么。事后扩大权限比收回权限容易得多。
2. **其次是分发。** 选择挂载仓库，还是通过 MCP 提供 skills，并端到端验证新鲜度：改一个 skill 文件，确认 Claude Tag 在你的 SLA 内读到它。
3. **从第一天就开始遥测。** 你不会回头去给一个月前的对话补埋点。从第一个问题起就记录结构化事件。
4. **条件允许时接入知识索引。** 数据仓库回答*是什么*；内部文档和故障 feed 回答*为什么*。数据路径稳定后，尽快把它们接进来。
5. **分析类 skills 放在最后。** 先创建数据访问 skill，然后让真实问题来告诉你，同事们实际需要哪些分析师技能（预测、队列、漏斗）。
