# 为每个任务打造执行框架：Claude Code 中的动态工作流

> 原文：[A harness for every task: dynamic workflows in Claude Code](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code/) · Claude 博客

上周，我们在 Claude Code 中发布了[动态工作流](https://code.claude.com/docs/en/workflows)。Claude 现在可以临场编写自己的[执行框架](https://code.claude.com/docs/en/glossary#agentic-harness)（harness），为手头的任务量身定制。

默认的 Claude Code 执行框架是为编码而构建的，但它对许多其他类型的任务同样有用，因为事实证明，很多任务都与编码任务类似。不过，对于某些类别的任务，我们必须在 Claude Code 之上构建定制化的执行框架才能达到巅峰性能，例如[研究（Research）](https://support.claude.com/en/articles/11088861-using-research-on-claude)、[安全分析](https://support.claude.com/en/articles/11932705-automated-security-reviews-in-claude-code)、[智能体团队](https://code.claude.com/docs/en/agent-teams)或[代码评审（Code Review）](https://code.claude.com/docs/en/code-review)。

有了工作流（workflows），你可以动态创建构建在 Claude Code 之上的执行框架，让 Claude 更原生地解决上述所有问题。你还可以与他人共享和复用这些工作流。

在本文中，我会分享我最初使用工作流的经验与心得，帮助你充分用好它。请记住，最佳实践仍在演进：动态工作流通常会消耗更多 token，最适合复杂、高价值的任务。

## 示例提示

在深入技术细节之前，我想先给出几个示例提示，让你感受一下工作流的可能性：

"这个测试大约每 50 次运行才失败一次。搭建一个工作流来复现它。针对这个竞态条件（race condition）提出多个相互竞争的理论，直到有一个理论经受住证据的检验才停下来。"

"用工作流翻阅我最近 50 个会话，挖掘我一直在反复纠正的问题，并把其中反复出现的那些转化为 `CLAUDE.md` 规则。"

"用工作流深挖 Slack 里 #incidents 频道过去六个月的内容，找出那些反复出现、却还没人提工单的根本原因。"

"拿我的商业计划书跑一个工作流，让不同的智能体分别从投资人、客户和竞争对手的视角把它拆个粉碎。"

"这里有一个文件夹，里面是 80 份简历，用工作流给后端岗位的候选人排序，并对前十名做复核。用 AskUserQuestion 工具采访我，制定评分标准（rubric）。"

"我要给这个 CLI 工具起个名字。用工作流头脑风暴出一堆候选，然后办一场锦标赛选出前 3 名。"

"用工作流把我们的 User 模型在所有地方重命名为 Account。"

"用工作流逐条对照代码库，验证我博客草稿中的每一个技术论断——我不想发布任何错误内容。"

## 动态工作流的运作方式

动态工作流会执行一个 JavaScript 文件，其中包含若干特殊函数，用于派生和协调[子智能体](https://code.claude.com/docs/en/sub-agents)（subagent）：

动态工作流还包含 JSON、Math、Array 等标准 JavaScript 函数，用于辅助处理数据。

特别值得了解的是：动态工作流可以决定智能体使用哪个模型，以及子智能体是否在各自的 worktree 中运行，从而让 Claude 自行选择所需的智能水平和隔离程度。

如果工作流被中断，例如由于用户操作或退出终端，恢复会话即可让工作流从中断处继续。

## 为什么需要动态工作流

当你让默认的 Claude Code 执行框架执行任务时，它需要在同一个上下文窗口中同时完成规划和执行。对许多编码任务来说，这非常高效；但对于长时间运行、大规模并行、高度结构化和/或对抗性的任务，它可能会失效。

这是因为 Claude 在单个上下文窗口中处理复杂任务的时间越长，就越容易陷入几种特定的失败模式：

- **智能体惰性（agentic laziness）**：指 Claude 在面对特别复杂的多部分任务时中途停止，在只取得部分进展的情况下宣布任务完成，例如一个安全审查的 50 个条目只处理了 35 个。
- **自我偏好偏差（self-preferential bias）**：指 Claude 倾向于偏爱自己的结果或发现，尤其在被要求依照评分标准对它们进行验证或评判时。
- **目标漂移（goal drift）**：指经过许多轮对话后对原始目标的保真度逐渐下降，尤其在上下文压缩（compaction）之后。每一次摘要都是有损的，诸如边缘情况需求或"不要做 X"之类的约束可能被丢掉。

创建工作流有助于对抗这些问题：它编排多个各自拥有独立上下文窗口、目标聚焦且相互隔离的 Claude 子智能体。

## 动态工作流与静态工作流

你可能曾经用 Claude Agent SDK 或 `claude -p` 创建过静态工作流，让多个 Claude Code 实例协同工作。

但由于静态工作流必须覆盖所有边缘情况，它们通常更加通用。有了 [Claude Opus 4.8](https://www.anthropic.com/news/claude-opus-4-8) 和动态工作流，Claude 已经足够聪明，可以为你的用例量身定制一个专属执行框架。

## 使用动态工作流的实用模式

你可以直接让 Claude 创建一个工作流，或者使用触发词 "`ultracode`" 来确保 Claude Code 创建工作流。

但建立一套关于动态工作流如何运作的心智模型，会帮助你理解何时该用它们，以及如何通过提示去引导 Claude。

Claude 在构建工作流时常会用到并组合以下几种常见模式：

### 先分类再行动（Classify-and-act）

用一个分类器智能体决定任务的类型，然后根据任务路由到不同的智能体或行为。也可以在结尾使用分类器来确定输出。

### 扇出再综合（Fan-out-and-synthesize）

把任务拆成许多更小的步骤，在每个步骤上运行一个智能体，然后综合这些结果。当存在大量小步骤，或者每个步骤都需要一个干净、互不干扰、避免交叉污染的上下文窗口时，这尤其有用。综合步骤是一道屏障（barrier）——它会等待所有扇出的智能体完成，再把它们结构化的输出合并成一个结果。

### 对抗性验证（Adversarial verification）

对每个派生出的智能体，再运行一个单独派生的智能体，依照评分标准或准则以对抗的方式验证它的输出。

### 生成再过滤（Generate-and-filter）

围绕某个主题生成大量想法，然后按评分标准或验证来过滤它们，去重后只返回质量最高、经过测试的想法。

### 锦标赛（Tournament）

不拆分工作，而是让智能体在同一项工作上竞争。派生 N 个智能体，各自用不同的方法尝试同一任务。然后由提示或模型通过一个裁判智能体以两两对决的方式评判结果，直到决出胜者。

### 循环直至完成（Loop until done）

对于工作量未知的任务，循环派生智能体直到满足停止条件（没有新发现，或日志中不再有错误），而不是执行固定轮数。

## 使用场景

请创造性地思考何时、如何让 Claude Code 创建动态工作流。我发现工作流有时对非技术性工作甚至更有用。

### 迁移与重构

[Bun](https://bun.com/) 就是用工作流从 Zig 重写为 Rust 的。你可以在 [Jarred 的 X 帖子](https://x.com/jarredsumner/status/2060050578026189172)中读到更多细节，或了解我们如何在百万行代码库上开展 [AI 代码迁移](https://claude.com/blog/ai-code-migration)。

关键在于把任务分解为一系列需要逐个处理的对象，例如调用点（callsite）、失败的测试、模块等。为每一处修复在 worktree 中派生一个子智能体去完成，再让另一个智能体进行对抗性评审，然后合并。可以考虑告诉智能体不要使用资源密集型命令，这样你就能最大程度并行而不会耗尽机器资源。

### 深度研究

我们在 Claude Code 内发布了一个使用动态工作流的深度研究技能（`/deep-research`）。具体来说，它会扇出网络搜索、抓取信息源、对抗性地验证其中的论断，并综合出一份带引用的报告。

不过你可以把这类研究用在网络搜索之外的地方。例如，让 Claude 根据 Slack 中的上下文汇编一份状态报告，或通过深入探索代码库来研究某个功能是如何实现的。

### 深度验证

反过来，如果你手头有一份报告，希望核查并溯源它引用的每一个事实论断，你可以生成一个工作流：先由一个智能体找出所有事实论断，再为每一条派生一个子智能体做详细核查。你还可以让一个验证智能体去检查溯源子智能体，确保其来源质量够高。

### 排序

你可能有一批条目想按某种定性标准排序，而你相信 Claude Code 擅长评估这种标准，例如：按缺陷严重程度排序支持工单。但如果试图在一个提示里对 1000 多行做排序，质量会下降，而且装不进上下文。更好的做法是运行一场锦标赛、一条由两两比较智能体组成的流水线（比较判断比绝对打分更可靠），或者先并行做分桶排名再合并。每一次比较都是一个独立智能体，因此确定性循环掌管着对阵表，上下文里只需保留运行顺序。

### 记忆与规则遵从

如果你发现 Claude 总是忽略或难以遵守某组特定规则，即使已经写进 `CLAUDE.md`，也可以创建一个工作流：列出必须核查的规则，由验证者智能体逐条把关——每条规则一个验证者。再创建一个"怀疑者"人设的子智能体来评审这些规则本身是否合理，有助于避免过多的误报。

反方向同样可行：挖掘你最近的会话和代码评审意见中反复出现的纠正，用并行智能体聚类，对每个候选规则做对抗性验证（这条规则本可以避免某次真实的犯错吗？），然后把幸存下来的规则蒸馏回 `CLAUDE.md`。

### 根因调查

调试的最佳方式是提出多个相互独立的假设并逐一检验，但如果你只有一个上下文窗口，Claude 可能陷入自我偏好偏差。

工作流可以从结构上防止这一点：派生多个从互不重叠的证据中生成假设的智能体。例如，分别负责日志、文件和数据的智能体。然后让每个假设接受一个由验证者和反驳者组成的评审团。

这不仅适用于代码。工作流还可以用于销售（为什么三月份销量下滑？）、数据工程（为什么这条流水线失败了？），或任何事后复盘（post-mortem）。

### 大规模分诊

每个团队都有一个支持队列、缺陷报告或其他人力无法完全处理积压事项。

分诊工作流会对每个条目分类、对照已跟踪的事项去重，并采取行动。行动可以是尝试修复，也可以是上报给人类用户。

分诊工作流的一个实用模式是隔离（quarantine）：禁止读取不受信任的公开内容的智能体执行高权限操作，这些操作改由负责依据信息采取行动的智能体来完成。

把分诊工作流与 /loop 搭配使用，可以让 Claude 持续不断地做这件事。

### 探索与品味

在为解决方案探索不同思路时，工作流也很有用，尤其是那些依赖品味的场景，比如设计或命名，并且可以受益于一套评分标准。

试着让 Claude 探索一大批解决方案，并给评审智能体一份描述"好方案长什么样"的评分标准。当评审智能体认为方案已满足标准时，任务即告完成。还可以基于评分标准通过锦标赛对方案排序或挑选。

### 评估（Evals）

你可以在 worktree 中派生独立智能体来为特定任务运行轻量评估（evals），再派生比较智能体依照评分标准对具体输出进行对比和打分。例如，针对特定标准对你创建的某个技能进行评估并加以打磨。

### 模型与智能水平路由

创建一个针对你的任务调优的分类器智能体，由它决定使用哪个模型。当任务涉及大量工具调用时这会很有帮助，而在执行前先做研究可以找出最适合该工作的模型。

例如，"解释 auth 模块如何工作"这个任务的最佳模型，取决于 auth 模块里有多少文件以及代码库的形态。分类器智能体可以先做这项研究，再根据任务的预期复杂度路由到 Sonnet 或 Opus。

## 何时不要使用动态工作流

工作流还很新。虽然在许多使用场景中它能带来超预期的成果，但并非每个任务都需要它，而且最终可能会消耗多得多的 token。

最好创造性地使用工作流，把 Claude Code 推向你此前未曾尝试的方向。对于常规编码任务，试着问问自己：它真的需要更多算力吗？例如，大多数传统编码任务并不需要一个由 5 位评审者组成的评审团。

同样的判断在上一层——架构层面——同样适用：[多智能体还是单智能体](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)的决策遵循相似的逻辑——并行化和专业化必须配得上它们的协调成本。

## 构建动态工作流的技巧

### 提示

使用上文介绍的具体技巧、为动态工作流编写详尽的提示，能带来最佳结果。

工作流不只适用于大型任务。你可以提示模型使用"快速工作流"。例如，你可以对某个假设做一次快速的对抗性评审。

### 与 `/goal` 和 `/loop` 搭配

当使用可重复的工作流时，例如分诊、研究或验证，把它们与 `/loop` 搭配以按固定间隔运行，并用 /goal 设定硬性的完成条件。

### token 用量预算

你可以为动态工作流设置显式的 token 用量预算，限制一个任务消耗多少 token。你可以用类似"用 10k token"的预算提示来设定上限。

### 保存与共享动态工作流

在工作流菜单中按"s"即可保存工作流。你可以把它们提交到 `~/.claude/workflows`，或者通过技能（skill）分发。

要通过技能共享，把你的 JavaScript 工作流文件放进技能文件夹，并在 [SKILL.MD](http://skill.md) 中引用它们。为了更灵活，你可以提示 Claude 把技能中的工作流视为模板，而不是必须逐字执行的脚本。
