# 如何为 AI 驱动的代码现代化项目做好准备

面向关键系统与受监管企业，如何组织 AI 驱动的现代化项目。

*在我们的 **Notes from the Field**（一线笔记）系列中，Anthropic 的前置部署工程师（forward deployed engineer）分享源自真实客户部署的最佳实践。本文分享我们管理大型代码现代化项目的经验。*

[代码现代化](https://claude.com/resources/articles/how-ai-helps-break-cost-barrier-cobol-modernization)曾经需要按多年、全员投入来规划，如今几个月（甚至[几周](https://claude.com/resources/articles/ai-code-migration)）就能完成；但项目两端的组织工作往往还是老样子。

举例来说，对关键银行系统的每一次变更都必须经过变更管理、评审和审批。这套流程之所以稳固，是因为监管机构、审计师和业务方都要求如此。

正是这些流程让关键系统变得可信，而它们建立在一个假设之上：每一处变更都由人编写，每个 diff 也都由人评审。一旦智能体加速了变更的编写，"瓶颈"就从产出变更转移到了"围绕变更调动组织"。

本文讨论企业在现代化真正开始之前必须完成的工作：定义"完成"的含义、一处变更必须携带哪些证据、经过认证的变更如何抵达生产环境，以及必须提前准备好哪些条件才能让项目启动。

我们把这一过程拆成六个步骤：

1. **确定目标（target）**：现代化后的代码必须符合的技术栈与行为。
2. **制定合格凭证（certificate）**：变更必须满足哪些条件，才能在目标状态下被视为正确。
3. **设定晋级策略（promotion policy）**：经过认证的变更以何种路径、按产出速度进入生产环境。
4. **落实前置条件**：环境、CI/CD、评审能力与审批。
5. **构建并打磨智能体工作流**：即自定义的 Claude Code [动态工作流](https://claude.com/resources/articles/introducing-dynamic-workflows-in-claude-code)，把现代化任务拆分到许多更小的并行子智能体工作流中产出变更。它围绕目标、凭证和晋级策略来构建。
6. **运行现代化**：在代码库的一小部分上端到端验证工作流，然后再扩展。

## **第 1 步：确定目标**

**目标（target）**是现代化的终态。期望的终态决定了你要做三种现代化中的哪一种，详见下表。

### **确定现代化类型**

| 类型 | 是什么 | 何时选择 | 目标是 |
| --- | --- | --- | --- |
| **升级（Uplift）** | 同栈版本升级（如 C++11 → C++20）。 | 技术栈没问题，但版本已落后：运行时停止支持、安全漏洞未修补、依赖无法再升级。 | 一个运行时版本与依赖包集合。 |
| **改造（Transform）** | 跨栈重写，保持行为不变（如 COBOL → Java）。 | 问题出在技术栈本身，而现有行为是可信的。 | 升级所需的一切，外加新代码必须遵循的语言、框架与架构约定。 |
| **重塑（Reimagine）** | 在新架构上做全新构建，并修改行为。 | 行为需要随代码一起改变。 | 改造所需的一切，外加一份为新系统编写的书面行为规格（behavioral spec）。 |

该做哪种现代化，往往是组织内部争论的焦点。以我们的经验，离生产最近的人希望只换技术栈、行为保持不变，以控制风险（即改造式现代化）。另一侧通常是长期与技术债共处的工程师，他们希望借现代化之机偿还技术债；此外还有希望趁机提出新需求的业务方（即重塑式现代化）。

两种立场都有其道理，但这个问题若悬而未决，日后就会以"某个变更是否'正确'"的争论形式重新浮现。就算就选哪条路达成共识会在开头增加摩擦，也会让整个项目更顺畅。

### **梳理代码库并编写行为规格**

理解现有系统，通常是定义目标的好起点。把旧代码的实际行为提取出来、建立当前行为清单，就更容易判断哪些部分应当修改或舍弃，从而决定这次现代化是改造还是重塑。这项工作还常常揭示出无人知晓的业务逻辑与边界情况。

Claude 可以承担其中大部分发现工作：例如[梳理依赖关系，并为那些已经没人记得是谁构建的工作流编写文档](https://claude.com/resources/articles/how-ai-helps-break-cost-barrier-cobol-modernization)。[代码现代化插件](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/code-modernization)的 *assess*、*map* 与 *extract-rules* 命令能挖掘业务规则并附上源码引用，供工程师复核。

不过，仅靠 Claude 的发现未必能完整刻画遗留系统的行为。与业务用户和开发者的访谈、内部文档可以补齐这些缺口。上下文收集在前期可能花些时间，但上下文的质量会塑造工作流后续做出的每一个决定。

对于重塑式现代化，定义目标还需要额外工作：应编写一份详细的行为规格，并与用户群体确认一致。

### **确立项目的立项依据与目标**

在定义目标的同时，组织还应当思考：这场现代化究竟为何值得做。对遗留系统做现代化可以降低持续的维护与运营成本；但以我们的经验，降低成本并不是大多数现代化项目的主导目标。

> "降低风险往往才是现代化最重要的收益。在争论是否要做这个项目时，不妨先考虑不做现代化的风险。"

例如，一个带有未修补漏洞的系统，可能意味着一次网络入侵，或一次严重到让企业本身陷入危险的停机。运行时不再受支持、懂这套系统的工程师越来越少，这些都在加剧风险。

像 Claude Code 这样的智能体编程工具已经缩短了现代化的时间线，但预算仍然难以估算，这导致了行动的惰性。我们公开过若干[大规模现代化](https://claude.com/resources/articles/ai-code-migration)的成本，[其他公司](https://claude.com/customers/lg-cns)也公开过。这些可以作为粗略的基准；本指南末尾还给出了预算预测方面的补充指引。

启动这类项目的主要挑战，通常是在拥有该系统的团队与依赖该系统的团队之间建立内部共识和承诺。把商业论证做扎实、设定项目目标（往往在领导层层面完成），能让这一步更顺利。这也有助于为后续的凭证与晋级策略中的权衡定下基准。当利益相关者在"一处变更能承担多少风险"上争执不下时，不进行现代化的风险就是那枚配重砝码。

## **第 2 步：制定合格凭证**

**合格凭证（certificate）**是每一项现代化变更都必须满足的一组条件或测试。挑选那些能提供最强累积证据、证明变更相对于目标是正确的条件。

每个条件都应能在无人介入的情况下自动检查，这样智能体工作流就能反复迭代某个变更，直到它满足凭证；若无法满足，则标记出来交由人工评审。

凭证里包含什么取决于目标，但通常会取自以下清单：

* 原有测试套件全部通过
* 现代化过程中由 Claude 编写的测试全部通过
* 测试覆盖率满足商定阈值
* 性能基准保持在商定边界内
* Claude 在各自全新的上下文窗口中独立进行对抗性评审，未发现阻断性问题
* 对于用户界面，Claude 驱动的计算机使用（computer use）未发现回归
* 当前版本与目标版本对相同输入产生相同输出——输入可以是实时的、录制的，或由 Claude 生成的
* 持久化状态与传输格式（wire format）能在当前版本与目标版本之间往返
* 变更在预发环境运行约定时长，错误率、延迟与告警均无回归
* 静态分析与安全扫描未发现新增问题
* 对于编译型目标，构建干净且类型检查通过

> "请和那些将负责评审、并将变更推入生产的人一起编写凭证。在凭证与智能体工作流仍在设计阶段时，就让当前依赖该代码库的开发者、用户群体和业务负责人参与进来。"

他们的专业判断塑造了凭证衡量什么；他们早期的参与，正是变更进入评审时赢得他们支持的原因。检验成品凭证的一个好方法，是看他们是否愿意仅凭凭证提供的证据就同意合并。如果他们在其中看到了自己的标准，第 3 步的晋级策略就可以更轻量。

凭证以什么为对照、如何对照，取决于现代化类型。

* **对于升级式现代化**，对照的是原有代码库，原有测试套件可以作为凭证的核心。
* **对于改造式现代化**，对照的同样是原有代码库，但原有测试套件很少能在新栈上运行。真正承担主要工作的是：重放生产流量、在新旧系统之间做差分测试，以及生产并行（prod-parallel）部署。
* **对于重塑式现代化**，凭证锚定在行为规格上。这是最难的场景。规格不像现有系统那样可以客观地做 diff 对照，因此会涉及更多模型判断，结果也可能更不稳定。此时凭证更依赖：依据规格编写的测试、由 Claude 进行的独立对抗性评审（将每个变更对照规格逐一检查），以及在新系统保留旧系统行为部分的差分检查。要预期凭证会随着规格澄清而修订：规格中的缺口会最先在这里暴露。

老旧系统往往测试覆盖薄弱、测试不稳定、遥测稀少。定义凭证的一部分工作就是识别这些缺口。如果很难支撑一个强凭证，这一步最有用的做法之一，就是用 Claude 补齐缺失的证据——无论是搭建生产并行环境、构建重放测试框架，还是补写更多测试。

## **第 3 步：设定晋级策略**

智能体产出变更的速度，将远超任何人类团队逐一评审 diff 的速度。晋级策略是一条事先书面约定好的分层评审路径，用以规定每个变更需要多深的人工评审，让现代化能在可接受的时间线内完成。

与凭证一样，这一步要和评审人一起完成，并尽可能嵌入组织现有的变更管理流程。具体细节会因组织和其所面临的风险权衡而异，但有几条规则普遍适用：

* **按影响范围（blast radius）与智能体置信度对变更分层。** 如果组织已有变更或风险分级，就沿用。关键路径仍保留完整的人工评审。
* **在源头修复反复出现的标记。** 长期对被打上标记的变更做归组与分析。当同类标记反复出现时，应修复智能体工作流或凭证中的根因，而不是逐个评审。
* **与评审人共同设计输出格式。** 就"哪些信息和格式能让评审最快"、"哪些信号比其他信号更能带来信心"达成一致。在第 5 步让他们评审早期样本输出。
* **高效分配领域专家（SME）时间。** SME 不会阅读每一个最终 diff，但他们的判断仍是最稀缺的输入。要让他们能直接跳到最高风险层级的变更，以及每个变更中被标记的智能体决策，而不必在庞大的 diff 中跋涉。这样少量专家工时就能覆盖风险最大的变更。

这些规则中有许多都通过让 SME 尽早参与，把他们的工时前移。他们的反馈会在全面现代化开始之前，先调校凭证与智能体工作流。

他们对样本的签字确认，也会成为在置信度高的地方采用更轻评审路径的进一步依据。这与传统的、非智能体的模式恰好相反——后者的评审发生在末端。

![](https://assets.claude.com/ca2355ee2906019de90e80ea46e03a38cd88c140.png)

一个变更从生成到生产的路径。

晋级策略还应体现这次现代化在"速度"与"评审深度"这条光谱上的位置。一场赶硬性截止日期的现代化（例如某个运行时即将失去支持），需要更快的策略、更轻的人工评审，并明确约定每个变更接受更多风险。

时间线更长的现代化则可以承担更深的人工评审与更慢的切换。利益相关者会依据各自的风险偏好与约束落在光谱的不同位置，所以值得在开工前就把这一点锁定。

在受监管环境中，对任何变更采用更轻的人工评审路径都可能引起实实在在的不适。审批人不愿签字，因为坏变更的风险由他们承担；而领导层承担的则是系统老化的更大风险。

以我们的经验，最好让晋级策略的指令来自组织最高层。最好也事先达成一致，这样当 bug 进入生产时，责任是共担的，而不是钉在批准该变更的人头上。

> "这一切仍取决于两点：凭证要详细到能作为真正的证据；评审人要足够理解 Claude 是如何得出某个变更的，从而能够信任它。"

## **第 4 步：落实前置条件**

这一步的很多工作都要经过现代化团队之外的部门：主机相关的平台或基础设施团队、负责测试容量的 QA 或发布工程团队、负责审批的安全与合规团队。这些团队通常各有自己的待办队列或审批流程，所以一旦明确需求就要尽早开启沟通——往往在第 1 至第 3 步仍在进行时就开始。

### **环境**

* 一台专用的远程主机，用于运行工作流，并让 Claude 能访问代码库及其他相关来源
* 凭证所要求的测试容量
* 一切能强化凭证的东西：生产遥测、生产并行环境，或用于重放的生产数据

### **代码库与 CI/CD**

* 一份基于构建与编译日志、import 分析或运行时追踪的代码库依赖图。注意：插件的 *map* 命令是很好的起点，但视代码库的规模与年代，可能还需要做更多前期工作
* 作为目标定义的一部分，规划好对任何依赖或包的处理方式
* 如需，准备好加入 CI/CD 的兼容性检查
* 如果是在原地做现代化，商定代码冻结策略
* 面向活跃开发者的沟通计划，涵盖代码冻结与新的兼容性要求

### **团队与评审**

* 与依赖该代码库的其他团队达成一致：他们如何参与，例如签署凭证或在晋级策略下评审，并预留出评审时间

### **安全与合规**

* 一条已获准用于源代码的 Claude Code 模型访问路径
* 智能体工作流的最小权限：只对现代化分支有写权限，且不持有生产凭证
* 从现代化分支中清除或掩蔽密钥与 PII
* 每个变更都可追溯，PR 关联到智能体会话记录（transcript）与凭证证据
* 对新依赖做许可证与漏洞检查

## **第 5 步：构建并打磨智能体工作流**

使用 Claude Code 开发一个用于现代化该代码库的定制[动态工作流](https://claude.com/resources/articles/introducing-dynamic-workflows-in-claude-code)。

我们建议从[代码现代化插件](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/code-modernization)入手，并把工作流可能需要的一切放到文件系统上或通过 MCP 暴露，让 Claude 能访问。这包括目标、凭证、晋级策略、代码库、文档，以及凭证所需的任何数据源或工具。你也可以把本文作为上下文交给 Claude。这构成了项目的中央知识库。

有了这些，[构建现代化工作流](https://claude.com/resources/articles/ai-code-migration)就是容易的部分了。按需让 SME 评审 Claude 的工作，包括任何与特定代码库相关的技能或提取出的规则——要在下游任何东西依赖它们之前完成评审。

把已构建的东西应用到代码库的小部分上，让 SME 评审它产出的变更、智能体的过程，以及凭证已满足的证据，从而打磨它。

> "当问题浮现时，你应该改工作流，而不是逐个改变更。目标是获得信心：一旦扩展，变更几乎处处都能满足凭证，评审人也愿意在晋级策略下合并。"

## **第 6 步：运行现代化**

先在代码库的一小部分上端到端完成现代化，包括通过晋级策略完成变更的评审与落地。趁代价还小的时候修好一切不奏效的地方，重复这一过程直到你有信心，然后扩展到整个代码库。

改造式与重塑式现代化都涉及在构建目标系统的同时保留现有系统，并在完成后一次性切换；而升级式现代化还有第二种选择：在活跃代码库上原地现代化，开发照常进行。

当系统不能停机，或代码库变化太快、难以维持一份独立的现代化副本时，通常就会选这条路。我们在这种情况下看到的有效做法是：把代码库按"从叶子向内"的方式切成逻辑分区；一次冻结并现代化一个分区；并对 CI/CD 设卡，使新提交无法撤销已完成现代化的分区。

## **关于成本的一点说明**

我们常被问到，这样一场现代化要花多少 token。每次现代化都不相同，但主要的成本驱动包括：

* 代码库中有多少部分必须被读取而不是被修改；
* 凭证有多复杂（在受监管环境中，验证通常比编写变更占更大份额）；
* 凭证要求补写多少新测试、修复多少测试；以及
* 运行期间其他团队在你周边合并代码带来了多少协调（reconciliation）工作。

> "在代码库的一小部分上完成现代化时，测量 token 用量，并据此外推整场运行。把试点看不到的任何东西——例如活跃代码库上的协调工作——当作未知项。这样你就能得到整场现代化的成本下限估计。"

试点的测量数据也会告诉你，该在哪里优化智能体工作流的成本。找出工作流中消耗 token 最多的部分，思考如何让它们更高效。把算力密集的验证信号放到更便宜的关卡之后，让它们只在更容易的检查通过后才运行。

对于凭证能完全检查的机械性、高体量工作，可以考虑使用 Sonnet 这类在成本与能力之间平衡的模型。把更聪明的模型留给困难的转换，以及验证正确性的对抗性评审。

你也可以在较便宜的模型未能满足凭证时，升级到更贵的模型；但试点期间要仔细分析重试率，因为多次便宜尝试的成本可能高于一次昂贵尝试。如果你把工作流和试点数据都交给 Claude，它可以和你一起完成大部分分析。

## **现代化之外**

现代化后的代码库只是产出之一。其他产出还包括：产出它的那套工作流、一份写明"何为正确"的凭证、一套已被你的变更管理流程接受的晋级策略，以及每个已落地变更的证据链。把这套打法固化为可复用资产，下一次升级或重写时，模式就已经就位了。
