# CodeRabbit 如何用 Claude 构建智能体编排系统

> 原文：[How CodeRabbit used Claude to build an agent orchestration system](https://claude.com/resources/articles/how-coderabbit-used-claude-to-build-an-agent-orchestration-system) · Claude 博客

CodeRabbit 在 Claude 上构建了一层系统，位于编码请求与编码智能体之间，先生成结构化的编码计划，供团队在任何代码生成之前进行评审。

AI 编码工具大幅压缩了从想法到可运行原型的时间。AI 代码审查平台 CodeRabbit 注意到，与这种吞吐量一同上升的还有另一种趋势：代码能够编译、通过测试，但并没有实现团队真正想要构建的东西。

CodeRabbit AI 副总裁 David Loker 认为，问题的根源在模型的上游。经验丰富的开发者常常默认编码智能体理解着与自己相同的上下文，因此不会写下那些对自己而言显而易见的需求。编码智能体随后便用它认为合理的内容填补空白。

为弥合这一鸿沟，CodeRabbit 用 Claude 设计并构建了一套智能体编排系统，在任何代码生成之前先运行结构化的规划阶段。团队的工作假设是：规划质量决定产出质量；代码生成变得越便宜，走错方向的代价就越高。

## **直面 AI 编码中的内部知识鸿沟**

当 CodeRabbit 团队研究其客户群中 AI 生成的拉取请求时，最常见的失败模式是：代码能够编译、通过测试，却仍然没有解决它本该解决的问题。

“随着开发者经验增长，我们会把知识内化，”Loker 说，“所有这些都在我们脑中，我们默认其他开发者也懂。然后我们对 AI 系统也做了同样的假设，认为它也能隐式地理解。我们甚至没有意识到自己在做这些假设。”

模糊的提示词迫使底层系统用它认为合理的内容填补空白。而这种猜测往往偏离开发者原本的想法。

Loker 举了一个自己的例子。他在一个副业项目中构建记忆系统时，与编码智能体反复迭代了好几个小时，直到一切都能跑起来。当他问智能体该如何使用时，说明里让他传入一个用户 token。但项目里并没有登录页面。他规定系统需要用户，却从未说明用户需要一个登录入口。智能体填补了这个空白，几个小时的工作最终落在一个缺少正门的产品上。

“最终发生的情况是，你在它上面又构建了很多东西，然后很久之后才发现有问题，”Loker 说，“在 AI 工作流中，迟到的验证可能非常昂贵。”

## **在 AI 编码方案之前运行的编排层**

CodeRabbit 的对策是在代码生成之前插入一套规划系统。它协调多个 Claude 模型分析需求、把假设显式化，然后产出一份结构化的执行计划，明确应该构建什么、需要满足哪些约束。

“这套规划系统并不是要取代 Claude Code 的 Plan Mode，”Loker 说，“它是在 Claude Code 之前发生的更高层编排，把它指向一个非常狭窄且正确的方向，让所有需要显式化的东西都显式化，并让我们清楚正在做出哪些假设。”

输出是一份协作式的产品需求文档（PRD）：在完整上下文中创建、由团队各利益相关方验证、并在实施开始前经过评审的计划。Claude Code 接手该计划，并据此生成细粒度的实施计划。计划成为一份共享产物，记录了决定了什么以及为什么，这不仅帮助团队避免返工、在事后验证输出符合最初意图，也有助于新工程师上手。

## **在 Claude 模型家族之间路由**

CodeRabbit 将每个模型层级与任务复杂度匹配，以优化成本和延迟。Opus 驱动编排循环，以及理解问题、设定总体方向等更高层的战略工作。Sonnet 接收其输出，并将其编排为结构化的规划步骤。Haiku 负责范围明确的操作，比如上下文蒸馏和有针对性的工具使用，这些场景的问题足够具体，较小的模型也能很好地回答。

“如果 Haiku 在某个任务上表现得和 Sonnet 一样好，我们就用 Haiku，”Loker 说，“如果评测 harness 告诉我们给 Opus 更多空间能提升计划质量，我们就给它更多空间。我们不靠猜。”

## **为计划质量构建评测 harness**

CodeRabbit 已经有一套成熟的代码审查评测系统，但在评估规划输出方面还是空白。构建这套基础设施本身成了一个独立项目。

系统从手工调校的示例和人工检查开始。团队开发了一个 LLM 评判器库，对计划质量的特定维度进行打分。由于计划最终会产出代码，团队还可以衡量生成的代码是否可用、是否包含额外范围，以及达到目标花费了多少 token。对同一任务分别在有规划步骤和无规划步骤的情况下运行，让他们能够分离出规划本身的价值。

“我们一开始并不知道那份计划合适的详细程度是多少，”Loker 说。过于细碎的计划会在代码库一变就过时。过于高层的计划则给智能体留下填补假设的空间，而这正是规划层原本要解决的问题。找到可行的抽象层级需要反复迭代，而评测 harness 让这件事成为可能。

## **在写出任何代码之前捕获错误**

在 AI 原生的编码工作流中，过去在代码审查时才浮现的许多决策，现在提前在规划层做出。构建一份团队能在代码生成开始前评审并对齐的计划，可以尽早捕获错误。

“我们用 Claude 生态构建出来的，是一套团队级的规划系统，”Loker 说，“计划本身就成了一道质量门禁。如果我们能确保计划质量在前期就足够好，下游效应会非常明显。最终你会得到好得多的代码。”
