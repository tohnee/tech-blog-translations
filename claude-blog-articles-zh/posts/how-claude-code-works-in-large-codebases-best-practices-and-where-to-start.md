# Claude Code 如何在大型代码库中工作：最佳实践与起步指南

> 原文：[How Claude Code works in large codebases: Best practices and where to start](https://claude.com/blog/how-claude-code-works-in-large-codebases-best-practices-and-where-to-start/) · Claude 博客

Claude Code 正在生产环境中运行于数百万行的单体仓库、有几十年历史的遗留系统、横跨数十个仓库的分布式架构，以及拥有数千名开发者的组织之中。这些环境带来了更小、更简单的代码库所没有的挑战：可能是每个子目录的构建命令都各不相同，也可能是遗留代码散落在没有共同根目录的各个文件夹里。

本文介绍了我们观察到的、成功大规模采用 Claude Code 的模式。我们所说的"大型代码库"涵盖广泛的部署形态：数百万行的单体仓库、历经数十年建成的遗留系统、分散在多个独立仓库中的数十个微服务，或以上情况的任意组合。其中也包括运行在团队通常不会与 AI 编码工具联系在一起的语言之上的代码库，例如 C、C++、C#、Java、PHP。（在这些场景下，Claude Code 的表现好于大多数团队的预期，尤其是在最近的模型发布之后。）虽然每一次大型代码库部署都受其特定的版本控制、团队结构和长期积累的约定所塑造，但本文的模式在它们之间具有普适性，对考虑采用 Claude Code 的团队而言是一个很好的起点。

## Claude Code 如何在大型代码库中导航

Claude Code 像软件工程师一样在代码库中导航：它遍历文件系统、读取文件、用 grep 精确找到所需内容，并沿着引用在整个代码库中追踪。它在开发者的本地机器上运行，不需要构建、维护代码库索引，也不需要把索引上传到服务器。

基于 RAG 的 AI 编码工具的做法是把整个代码库做嵌入（embedding），在查询时检索相关分块（chunk）。在大规模场景下，这类系统会失灵，因为嵌入流水线跟不上活跃的工程团队。等开发者查询索引时，它反映的还是数周、数天甚至数小时之前的代码库。检索返回的可能是团队两周前就已改名的函数，或引用了上个冲刺（sprint）就已删除的模块，而不会有任何提示表明这些信息已经过期。

智能体式搜索（agentic search）避免了这些失败模式。当数千名工程师提交新代码时，没有需要维护的嵌入流水线，也没有集中式索引。每个开发者的实例都直接基于实时的代码库工作。

但这种方式有一个权衡：只有当 Claude 拥有足够的起始上下文、知道该往哪里看时，它才最有效。这意味着 Claude 导航的质量取决于代码库搭建得好不好，也就是用 CLAUDE.md 文件和 skills 分层叠加上下文。如果你让它在十亿行的代码库里查找某个模糊模式的所有实例，工作还没开始你就会撞上上下文窗口上限。在代码库搭建上投入的团队会得到更好的结果。

## 执行框架与模型同样重要

关于 Claude Code 最常见的误解之一，是认为它的能力完全由所用的模型决定。团队盯着模型的基准测试成绩和它在测试任务上的表现。而在实践中，围绕模型构建的生态——执行框架（harness）——对 Claude Code 表现的影响比模型本身更大。

执行框架由五个扩展点构成——CLAUDE.md 文件、hooks、skills、plugins 和 MCP 服务器——各自承担不同的功能。团队构建它们的顺序很重要，因为每一层都建立在前一层之上。另外两项能力——LSP 集成和 subagents——补全了整套配置。下面我们解释这些组件和能力各自的作用：

[**CLAUDE.md**](https://code.claude.com/docs/en/memory)** 文件是第一步。**这些是 Claude 在每次会话开始时自动读取的上下文文件：根文件负责全局图景，子目录文件负责局部约定。它们为 Claude 提供了把任何事情做好的代码库知识。由于无论任务是什么，它们都会在每次会话中加载，因此让内容聚焦于普遍适用的信息，能避免它们成为性能拖累。

[**Hooks**](https://code.claude.com/docs/en/hooks-guide)** 让配置具备自我改进能力。**大多数团队把 hooks 看作防止 Claude 犯错的脚本，但它们更有价值的用途是持续改进。一个 stop hook 可以复盘会话中发生的事情，并在上下文还新鲜时提出 CLAUDE.md 的更新建议。一个 start hook 可以动态加载团队专属的上下文，让每位开发者无需手动配置就能获得适合自己模块的设置。对于 lint 和格式化这类自动化检查，hooks 以确定性方式执行规则，比依赖 Claude 记住某条指令能得到更一致的结果。

[**Skills**](https://code.claude.com/docs/en/skills)** 让恰当的专业知识按需可用，又不会撑爆每一次会话。**在一个有数十种任务类型的大型代码库中，并非所有专业知识都需要在每次会话中出现。Skills 通过[渐进式披露（progressive disclosure）](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)解决这个问题：把那些原本会争夺上下文空间的专业工作流和领域知识卸载出去，只在任务需要时才加载。例如，当 Claude 评估代码是否存在漏洞时加载安全评审技能；当一次代码改动需要同步更新文档时，加载文档处理技能。

Skills 还可以限定作用路径，只在代码库的相关部分激活。拥有一个支付服务的团队可以把他们的部署技能绑定到该目录，这样当有人在单体仓库的其他地方工作时，它绝不会自动加载。

[**Plugins**](https://code.claude.com/docs/en/plugins)** 分发有效的东西。**大型代码库的一个挑战是，*好的*配置可能只停留在小圈子里。插件把 skills、hooks 和 MCP 配置打包成一个可安装的包，新工程师第一天装上这个插件，就立刻拥有与已经在使用 Claude 的同事相同的上下文和能力。插件更新可以通过[托管市场（managed marketplaces）](https://support.claude.com/en/articles/13837433-manage-claude-cowork-plugins-for-your-organization)分发到整个组织。

例如，与我们合作的一家大型零售组织构建了一个把 Claude 连接到其内部分析平台的技能，让业务分析师无需离开自己的工作流就能拉取绩效数据。在向业务部门大规模推广之前，他们就把它作为插件分发出去。

**语言服务器协议（LSP）集成让 Claude 拥有与开发者在 IDE 中相同的导航能力。**大多数面向大型代码库的 IDE 里本来就跑着一个 LSP，支撑"转到定义"和"查找所有引用"。把这些能力开放给 Claude，它就获得了符号级（symbol-level）精度：可以沿着函数调用找到定义、跨文件追踪引用，并区分不同语言里同名的函数。没有它，Claude 只能对文本做模式匹配，可能落在错误的符号上。与我们合作的一家企业软件公司在推广 Claude Code 之前，就在全组织范围部署了 LSP 集成，目的就是让 C 和 C++ 的导航在大规模场景下可靠。对于多语言代码库，这是回报最高的投入之一。

**MCP 服务器扩展一切。**MCP 服务器是 Claude 连接内部工具、数据源和 API 的方式，否则它无法触达这些资源。最成熟的团队构建了 MCP 服务器，把结构化搜索暴露为 Claude 可以直接调用的工具。另一些团队则把 Claude 连接到内部文档、工单系统或分析平台。

[**Subagents**](https://code.claude.com/docs/en/sub-agents)** 把探索与编辑分开。**子智能体（subagent）是一个拥有自己上下文窗口的隔离 Claude 实例，它接下一个任务、完成工作，然后只把最终结果返回给父智能体。执行框架就位后，一些团队会启动一个只读子智能体去梳理某个子系统并把发现写入文件，然后让主智能体带着完整图景去做编辑。

*Claude Code 扩展层一览。*

下表总结了每个组件的作用、加载时机，以及我们在每一种上最常看到的误用：

| 组件 | 它是什么 | 何时加载 | 最适合 | 常见误解 |
|---|---|---|---|---|
| CLAUDE.md | Claude 自动读取的上下文文件 | 每次会话 | 项目专属约定、代码库知识 | 把本该放进技能的可复用专业知识写进它 |
| Hooks | 在关键时刻运行的脚本 | 由事件触发 | 自动化一致的行为、沉淀会话经验 | 用提示词去做本该自动运行的事 |
| Skills | 针对特定任务类型的打包指令 | 按需加载，相关时 | 跨会话、跨项目的可复用专业知识 | 反而把所有东西都塞进 CLAUDE.md |
| Plugins | 打包好的 skills、hooks、MCP 配置 | 配置后始终可用 | 把有效的配置分发给整个组织 | 让好的配置停留在小圈子里 |
| 语言服务器协议（LSP）* | 通过语言专用服务器提供实时代码智能 | 配置后始终可用 | 类型化语言中的符号级导航与自动错误检测 | 以为它是自动开启的 |
| MCP 服务器 | 与外部工具和数据的连接 | 配置后始终可用 | 让 Claude 访问它原本无法触达的内部工具 | 在基础还没跑通时就先建 MCP 连接 |
| Subagents* | 面向特定任务的独立 Claude 实例 | 被调用时 | 把探索与编辑分开、并行工作 | 在同一个会话里既探索又编辑 |

*\*LSP 通过插件层访问。Subagent 是一种委托能力，而非配置化的扩展点。*

## 成功部署中的三种配置模式

如何为大型代码库配置 Claude Code，很大程度上取决于代码库本身的结构。不过，在我们观察到的部署中，有三种模式反复出现。

### 让代码库在大规模下可导航

Claude 在大型代码库中提供帮助的能力，受限于它找到正确上下文的能力。每次会话加载太多上下文会降低性能，加载太少又让 Claude 盲目摸索。最有效的部署会提前投入，让代码库对 Claude 可读。以下几种模式反复出现：

- **保持 CLAUDE.md 文件精简并分层。**Claude 在代码库中移动时以叠加方式加载它们：根文件负责全局图景，子目录文件负责局部约定。根文件应该只放指针和关键的坑点；其余一切都会逐渐漂移成噪声。
- **在子目录中初始化，而不是在仓库根目录。**当 Claude 的作用范围限定在与任务真正相关的代码库部分时，它工作得最好。在单体仓库中这可能违反直觉，因为工具往往默认从根目录访问；但 Claude 会自动沿目录树向上走，并加载沿途找到的每一个 CLAUDE.md 文件，所以根目录的上下文不会丢失。
- **按子目录限定测试与 lint 命令。**当 Claude 只改了一个服务却运行完整测试套件时，会导致超时并把上下文浪费在无关输出上。子目录层级的 CLAUDE.md 文件应当写明适用于该部分代码库的命令。这对服务导向的代码库非常有效，因为每个目录都有自己的测试和构建命令。在具有深层跨目录依赖的编译型语言单体仓库中，按子目录限定更难实现，可能需要项目专属的构建配置。
- **使用 `.ignore` 文件排除生成文件、构建产物和第三方代码。**把 `permissions.deny` 规则提交到 `.claude/settings.json`，意味着这些排除项进入了版本控制，团队里每个开发者都能获得同样的降噪效果，而无需各自配置。在某些代码库中，生成文件本身就是开发对象。做代码生成器的开发者可以在本地设置里覆盖项目级排除，而不影响团队其他人。
- **当目录结构本身说明不了问题时，构建代码库地图。**对于代码没有按常规目录结构归拢的组织，可以在仓库根目录放一个轻量的 markdown 文件，列出每个顶层文件夹及其一行内容说明，这就给了 Claude 一份可以在打开文件之前浏览的目录。对拥有数百个顶层文件夹的代码库，分层做法效果最好：根文件只描述最高层的结构，子目录 CLAUDE.md 文件提供下一层的细节，随着 Claude 在目录树中移动按需加载。对更简单的情况，用 @ 提及（@-mention）Claude 应参考的具体文件或目录也能达到同样效果。
- **运行 LSP 服务器，让 Claude 按符号搜索而不是按字符串搜索。**在大型代码库中 grep 一个常见函数名会返回成千上万个匹配，Claude 会为了搞清哪个才是所需的而烧掉上下文去打开文件。LSP 只返回指向同一符号的引用，过滤发生在 Claude 读取任何内容之前。要进行这项设置，需要为你的语言安装一个[代码智能插件](https://code.claude.com/docs/en/discover-plugins#code-intelligence)以及相应的语言服务器二进制文件；Claude Code 文档涵盖了可用的插件与故障排查方法。

**一点提醒**：在某些边缘情况下，即使是分层的 CLAUDE.md 方案也会失效，例如拥有数十万个文件夹和数百万个文件的代码库，或运行在非 git 版本控制之上的遗留系统。我们将在本系列的后续篇章中讨论这些挑战。关于遗留系统，请参阅 AI 如何[*打破 COBOL 现代化的成本壁垒*](https://claude.com/blog/how-ai-helps-break-cost-barrier-cobol-modernization)。

### 随着模型智能的演进，持续维护 CLAUDE.md 文件

随着模型演进，为你当前的模型编写的指令可能会与未来的模型相抵触。那些曾引导 Claude 度过它曾经难以应对之处的 CLAUDE.md 文件，在下一个模型发布时可能变得多余，甚至成为主动的限制。例如，一条要求 Claude 把每次重构拆成单文件改动的 CLAUDE.md 规则，可能曾帮助较早的模型保持正轨，却会妨碍更新的模型进行它已能胜任的跨文件协同编辑。

为弥补特定模型局限而构建的 skills 和 hooks——无论局限出在模型的推理还是 Claude Code 自身的工具——一旦局限不复存在，就会变成开销。例如，在 Perforce 代码库中拦截文件写入以强制执行 p4 edit 的一个 hook，在 Claude Code 增加原生 Perforce 模式后就成了冗余。

团队应当预期每三到六个月做一次有分量的配置评审；此外，每当大版本模型发布后感觉性能进入平台期，也值得做一次评审。

### 为 Claude Code 的管理与推广指派负责人

仅靠技术配置无法推动采用。做对了的组织同样在组织层面进行了投入。

推广得最快的那些案例，都在开放大范围使用之前进行了专门的基础设施投入。一个小团队，有时甚至只是一个人，把工具链搭好，让开发者在第一次接触 Claude 时，它就已经融入了他们的工作流。有一家公司，几位工程师构建了一整套插件和 MCP，第一天就可供使用。在另一家公司，一个专门负责管理 AI 编码工具的完整团队在推广开始前就把基础设施准备就绪。在这两个案例中，开发者的第一次体验是高效的而非令人沮丧的，采用从此扩散开来。

如今做这项工作的团队通常隶属于开发者体验（developer experience）或开发者效能（developer productivity）部门——即通常负责新工程师入职和构建开发者工具的职能。一些组织中正在出现一个新角色：智能体管理员（agent manager），一个专门管理 Claude Code 生态的 PM/工程师混合职能。对于没有专职团队的组织，最小可行版本是一个 DRI（直接负责人）：一个人对 Claude Code 配置拥有所有权，有权就设置、权限策略、插件市场和 CLAUDE.md 约定做出决断，并负责让它们保持最新。

自下而上的采用能激发热情，但如果没有人把有效的东西集中起来，就会走向碎片化。你需要有一个人或一个团队来汇集并推广正确的 Claude Code 约定（例如标准化的 CLAUDE.md 层级，或一套精选的 skills 和 plugins）。没有这项工作，知识会停留在小圈子里，采用会进入平台期。

在大型组织，尤其是受监管行业的组织中，治理问题很早就会出现，比如：谁控制哪些 skills 和 plugins 可用？如何防止数千名工程师各自重复造同一个轮子？如何确保 AI 生成的代码走与人工生成的代码相同的评审流程？为了及早应对这些问题，我们建议从一套明确的已批准技能清单、强制的代码评审流程和有限的初始访问开始，随着信心建立再逐步扩展。

我们观察到，最顺畅的部署出现在那些及早建立跨职能工作组的组织：把工程、信息安全和治理代表聚在一起，共同定义需求并制定推广路线图。

## 将这些模式应用于你的组织

Claude Code 围绕常规的软件工程环境设计：工程师是代码库的主要贡献者，仓库使用 Git，代码遵循标准目录结构。大多数大型代码库都符合这个模式，但非传统环境——例如带有大量二进制资源的游戏引擎、使用非常规版本控制的环境，或有非工程师向代码库贡献内容——需要额外的配置工作。我们的指导以常规环境为前提，这里描述的模式已经在我们的许多客户那里得到验证。任何剩余的复杂性，都需要针对你的代码库、工具链和组织做出判断。这正是 Anthropic 的 Applied AI 团队与工程团队直接合作的地方——把这些模式转化为你组织的具体需求。
