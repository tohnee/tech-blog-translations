# Claude Fable 5 实战指南：找出你的未知项

> 原文：[A field guide to Claude Fable 5: Finding your unknowns](https://claude.com/resources/articles/a-field-guide-to-claude-fable-finding-your-unknowns) · Claude 博客

在用 Claude Code 工作时，我常常会想到「地图与疆域」（the map and the territory）之间的差别。

地图是对待完成工作的一种表征——它是我的提示、[技能](https://claude.com/resources/articles/skills-explained)和上下文，是我交给 Claude 的东西。疆域则是工作真正要发生的地方：代码库、真实世界，以及它实际的约束条件。

![](https://assets.claude.com/0c9ef5f6d0bb96e0267b77ae7ec4ee3249a71778.png)

地图与疆域之间的差距，就是我所说的*未知项*（unknowns）。当 Claude 遇到一个未知项时，它需要基于「我认为你想要什么」的最佳猜测做出决策。要做的工作越多，Claude 可能遇到的未知项就越多。

Claude Fable 是我遇到的第一个这样的模型：工作质量受制于我发现并澄清它的未知项的能力。

重要的是，仅靠提前规划并不总是够用。你可能到实现深处才会发现未知项，或者你的未知项可能指向一个事实：你其实应该用完全不同的方式来解决这个问题。

我发现，与 Fable 协作是一个在实现之前、实现之中和实现之后不断发现未知项的迭代过程。

## 认识你的未知项

你的未知项是什么？当我带着一个问题来找 Claude 时，我倾向于把它拆成四类：

* **已知的已知（Known Knowns）：** 这基本上就是我的提示里写的东西。我告诉智能体我想要什么？
* **已知的未知（Known Unknowns）：** 哪些是我还没弄明白、但我清楚自己还没弄明白的？
* **未知的已知（Unknown Knowns）：** 哪些东西显而易见到我根本不会写下来，但一看到就能认出来？
* **未知的未知（Unknown Unknowns）：** 哪些是我完全没想到的？哪些知识是我并未意识到的？我是否知道一件事能好到什么程度？

最出色的智能体编码者的未知项相对较少。看 [Boris](https://www.linkedin.com/in/bcherny) 或 [Jarred](https://www.linkedin.com/in/jarred-sumner-a8772425) 这类人写提示，我能明显感觉到他们对自己想要什么了如指掌。他们与代码库和模型行为都高度同步。

![](https://assets.claude.com/c0977293cee11764842764e05ae2802892000439.png)

但他们也会预设未知项的存在。从很多方面说，减少并为未知项做规划，正是[智能体编码](https://claude.com/resources/articles/introduction-to-agentic-coding)的**核心技能**。幸运的是，这是一项可以通过与 Claude 协作来提升的技能。

## 帮 Claude 更好地帮你

![](https://assets.claude.com/55cc5d145a4c9a517e6bc1e7d94240c230b4120f.png)

指挥 Claude 是一场微妙的平衡。如果你过于具体，Claude 会严格遵循你的指令，即使此时改换方向更合适。如果你过于模糊，Claude 往往会依据行业最佳实践做出选择和假设，而这些未必适合你的任务。

如果你没有把未知项纳入考虑，那么两个方向都会失败。你不知道哪条路会布满障碍，也不知道哪条路其实畅通无阻，但你仍然希望 Claude 能及时转向。

Claude 能帮你更快地发现未知项。它可以在你的代码库和互联网中极快地检索，而且对一般主题的了解远多于你。它从失败中迭代的速度也更快。

这个过程中最重要的一点，是给 Claude 提供关于你起点的上下文。例如，告诉它你在思考过程中的位置；说明你在该问题和代码库方面的经验；让它像一个思考伙伴一样与你协作。

本文会详述我用来发掘这些未知项的一些模式，包括：

**实现之前：**

* 盲区扫描（blind spot pass）
* 头脑风暴与原型
* 访谈
* 参考实现
* 实现计划

**实现过程中：**

* 实现笔记

**实现之后**

* 提案与说明材料
* 小测验

## 实现之前

### 盲区扫描（Blind Spot Pass）

开始一项工作时，最有用的做法之一就是弄清自己的盲区。例如，如果你正在代码库中一个陌生的部分开发功能，或者用 Claude 处理不熟悉的工作，比如迭代一个设计方案，那你很可能有大量**未知的未知**。

你可能不知道该问哪些问题、不清楚「好」是什么样子、不了解历史上做过哪些工作，也不知道哪些坑要避开。

在这类情况下，你可以让 Claude 帮你找出你的未知的未知，并向你解释它们。我喜欢直接使用「blind spot pass」和「unknown unknowns」这两个词。向它说明你是谁、你了解什么，通常对 Claude 理解如何以最佳方式与你开始协作很重要。

**示例提示：**

* 「我正在添加一个新的认证提供方，但我对这个代码库里的认证模块一无所知。你能做一次盲区扫描，帮我找出相关的未知的未知，并帮我更好地给你写提示吗。」
* 「我不知道调色（color grading）是什么，但我需要给这个视频调色。你能教我去理解我在调色方面的未知的未知，好让我能写出更好的提示吗？」

### 头脑风暴与原型

当我在一个充满**未知的已知**的领域工作时——这类工作涉及只有看到才能说出标准的东西——我喜欢让 Claude 和我一起头脑风暴、做原型。

在原型阶段尽早识别并说出未知的已知，价值极高，因为在实现阶段才发现它们（相对而言）代价更高。功能或规格上的一点小变化，就可能让代码实现大不相同，而且让智能体回退之前的改动会更困难。

例如，你可能只是想看看在某个画框里加一个按钮是什么效果，而不想为此接一条后端路由，或在前端维护额外的状态。

另一个例子是视觉设计：对我来说，这属于难以言说、但看到就知道想要什么的事。在这种情况下，我会要求针对一个产物给出几种不同的设计方向。

我几乎每次编码会话都以一个探索或头脑风暴阶段开场。这帮助我带着明确的意图去界定项目范围。Claude 常常能发现我会错过的高价值路径，有时也会因只见树木不见森林而漏掉全局。头脑风暴能防止我把范围定得太窄或太宽。

**示例提示：**

* 「我想要一个这份数据的仪表盘，但我没有视觉品味，也不知道能做到什么程度。给我做一个 HTML 页面，包含 4 个差异极大的设计方向，好让我能对它们做出反应。」
* 「在接入任何东西之前，先用假数据做一个单文件 HTML，把新的编辑器工具栏做出来。我想在你碰真实应用之前先对布局做出反应。」
* 「我的问题大致是这样：用户在新手引导后就流失了。搜索代码库，头脑风暴出 10 个我们可以介入的地方，从成本最低到最有野心排列。我会告诉你哪些有共鸣。」

### 访谈

即使做足了头脑风暴，我大概率仍然有未知项。

这时，我会让 Claude 就任何未知或含糊之处来访谈我。让 Claude 访谈你时，尽量给它关于你问题的上下文，以引导它提问。

**示例提示：**

* 「就任何含糊之处一次问我一个问题，优先问那些我的回答会改变架构的问题。」

### 参考实现

有时你无法详细描述你想要什么。比如，你可能缺乏相应的词汇，或者事情复杂到描述起来要花很长时间。

这种情况下，最好的办法是给一个参考。你可以放示意图、文档或图片，但绝对最好的参考是*源代码*。

如果你有一个以某种方式实现某个功能的库，或一个你很喜欢的设计组件，直接把 Fable 指向那个文件夹并告诉它要找什么就好，即使那是另一种语言写的。与截图之类的方式相比，这能为 Claude 提供关于标记（markup）和结构丰富得多的细节。

**示例提示：**

* 「vendor/rate-limiter 里的这个 Rust crate 实现了我想要的完全一致的重试退避（backoff）行为。读一下它，并在我们的 TypeScript API 客户端里重新实现相同的语义。」

### 实现计划

当我自认为准备好实现时，我倾向于让 Claude 整理一份实现计划供我审阅。计划聚焦在最有可能改动的部分，例如数据模型、类型接口或 UX 流程。这样能让 Claude 把那些我可能实际需要调整的东西摆到台面上。

**示例提示：**

* 「用 HTML 写一份实现计划，但开头先讲我最可能会调整的决策：数据模型改动、新的类型接口，以及任何面向用户的部分。把机械式的重构埋在最后，那部分我信你。」

## 实现过程中

### 实现笔记

一旦我对计划满意，我会新开一个会话，把各种产物一并放进提示里。这让 Claude 拥有一个全新的上下文窗口，同时带着它在规划过程中汇总的全部信息。例如，我可能会传入一个规格文件和一个原型，然后让智能体去实现它。

但事实是，无论你做多少规划，总有未知的未知潜伏着。智能体可能在工作中发现，由于代码里遇到了某个边界情况，它需要换一条路走。

我会让 Claude Code 维护一个临时的 implementation-notes.md（或 .html）文件，记录它做出的决策，以便我们为下一次尝试积累经验。

**示例提示：**

* 「维护一个 implementation-notes.md 文件。如果遇到某个边界情况迫使你偏离计划，选保守的那个选项，把它记在“Deviations”下面，然后继续。」

## 实现之后

### 提案与说明材料

把东西真正交付出去，最重要的环节之一是获得认可与批准。在最终文档里构建提案和说明性产物，有助于：

* 当审阅者一开始和你有同样的未知项时，加快他们的理解
* 当专家希望看到你已把他们能预见到的未知项和常见失败点考虑在内时，加快批准

**示例提示：**

* 「把原型、规格和实现笔记打包成一份文档，让我可以直接丢到 Slack 里争取支持。开头放演示 GIF。」

### 小测验

经过一次长时间的工作会话，Claude 可能完成的工作远比我意识到的多。读代码 diff 只能让我对发生了什么有个浅层理解，因为很多行为取决于既有的代码路径。

在给我大量上下文之后，让 Claude 就这次改动来考我，能帮助我理解实际发生了什么。只有在完美通过测验之后，我才会合并。

**示例提示：**

* 「我想确保自己理解这次改动中发生的一切。给我一份关于这些改动的 HTML 报告，包含上下文、直觉解释、做了什么等等，让我读并理解，然后在底部附一个关于这些改动的测验，我必须通过它。」

## 这些方法如何走到一起：发布 Fable

[Fable 的发布视频](https://x.com/ClaudeDevs/status/2064399512664526853)是全程用 Claude Code 剪辑完成的。这对我来说是一个全新的领域，我也绝不是专家。

所以我从自己确实知道的东西入手。我知道 Claude 可以用代码剪辑视频并做转写，但不确定准确度是否够用。于是我让 Claude 给我讲像 Whisper 这样的转写是如何工作的，以及我能否用 ffmpeg 准确剪掉「嗯」这类口头语或大段停顿。

我想让 Claude 做一个与我所说的话同步计时的 UI，但不确定是否可行，于是让 Claude 用 Remotion 加一份转写做一个原型视频，看看行不行得通。

最后，视频本身看起来有点灰暗，我知道这是调色的结果，但我并不真正了解调色是什么。我最初的尝试是让 Claude 做几个变体供我挑选，但我意识到，在调色这件事上我根本不知道「好」是什么样子。于是我改为让 Claude 教我调色，以发现自己的未知项。

## 让地图与疆域相合

模型越强，用对方法能达成的就越多。当一个长周期任务的结果不对时，很可能你需要花更多时间去界定你的未知项，或者去制定一份允许你和 Claude 一起穿过这些未知项的实现计划。

每一份说明材料、每一次头脑风暴、访谈、原型和参考，都是在「修正变得昂贵」之前，低成本地发现自己不知道什么的方式。

所以，下一个项目就从让 Claude 帮你找出你的未知项开始吧。
