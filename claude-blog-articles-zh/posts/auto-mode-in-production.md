# 在生产环境中运行自动模式

> 原文：[Running auto mode in production](https://claude.com/blog/auto-mode-in-production/) · Claude 博客

[自动模式现已成为默认设置](http://claude.com/blog/auto-mode-default-in-claude-code)。它不再要求你批准智能体想运行的每一条命令，而是由分类器评估每个动作，并拦截那些看起来可能有危害的动作。

自动模式的设计解决了智能体编码中一个常见的权衡：速度与安全。逐条审查每条命令能让人保持在回路中，但一旦会话延长到数小时或成倍并行增加，这种监督就会成为瓶颈。完全跳过权限检查更快——但这也正是提示注入、范围漂移（scope drift）和偶尔误删生产资源得以溜进来的原因。

自动模式弥合了这两者之间的大部分差距。在内部评估中，分类器捕获的危险动作多于开发者手动点击权限提示时捕获的数量，并且其表现在第三方红队测试下依然稳固。而且由于会话暂停的次数更少，在整个 Claude Code 的使用范围内，Claude 在两次打断之间的工作时长达到了此前默认设置下的 9 倍。

为了了解自动模式在生产环境中的实际表现，我们与 Nuro、Gusto 和 Garner Health 的团队聊了聊他们如何以及为何把自动模式作为日常主力，在生产环境中平衡速度与安全。

### 在 Nuro 驱动运行更久的自主智能体

Nuro 是一家研发通用 Level 4 自动驾驶技术的具身智能（physical AI）公司，于 2025 年底采纳了 Claude Code，到 3 月它已成为公司内最受欢迎的智能体编码工具。

在自动模式发布之前，资深软件工程师 Kai Zhou 就已经开始原型化一个内部替代方案：一个 hook，把每个待执行的动作发送给一个小模型，90% 的常规情况自动批准，敏感的则路由到 Slack 交由人工审查。这个原型回应了一个真实的矛盾：工程师讨厌守着批准提示，但从公司安全与法务的角度看，完全跳过权限又危险到无法认可。当自动模式发布时，Kai 把这个业余项目搁置了。

如今，Kai 写的所有东西都用自动模式运行。

“我不想坐在那里一直点批准，”Kai 说，“我 100% 的编码工作都用自动模式。大多数时候，我会同时开三四个并行运行自动模式的会话，只在需要的时候去看一眼。”

例外是涉及其他团队的工作。例如，当 Claude Code 代表他审查一个 Pull Request 时，Kai 会切回交互模式，在它发出之前逐个审查。

自动模式的运行也并非毫无约束。Nuro 大量使用 [skills](https://agentskills.io/home)，工程师会在设置中直接拒绝最危险的命令，比如递归删除。分类器在这些防护栏之内做出它的判断。

不过，自动模式更大的解锁之处，在于能够启动工程师下班后仍在持续运行的工作。具体来说，Kai 的团队用自动模式驱动长时间运行的研究智能体，对其自动驾驶技术栈背后的评估指标做爬山式优化：这类任务有清晰、可度量的信号，智能体可以自行对照着迭代。

过夜里，一个智能体可以研究评估套件标记出的漏报（false negative），起草提案，运行实验，并继续根据结果迭代。这一方法适用于任何有明确评估方法的任务——Nuro 的另一个团队就用它来缩减某个二进制文件的内存占用——因为指标本身就会告诉智能体它是在进步还是退步。

“前几天，我在晚上 10 点启动了一个智能体，它一直运行到凌晨 5 点——早上它交给我三个 PR，”Kai 说，“我觉得这相当了不起。只有自动模式才能支撑这样的工作负载。”

### 在 Gusto 更快、更安全地交付 PR

在领先的小型企业（SMB）科技公司 Gusto，转向自动模式最初是一次主动的安全升级。

在公司 AI Dev Tools 团队工作的 Martin Emde 亲眼看着权限疲劳拖慢了团队。自动模式给了他们同样的速度，却不牺牲控制力或安全性；自采纳在工程团队铺开以来，整体的权限负担已明显下降。

自 12 月以来，Martin 已经启动了 2,425 个 Claude Code 会话，自动模式是他的日常主力。过去因文件夹访问审批而停滞的跨仓库工作现在可以不间断地运行，而无人值守的任务，比如从 GitHub、Slack 和 Jira 汇编每日简报，也都自行运转。在团队自己的分析中，自 2026 年 5 月中旬以来大约 10% 的会话记录包含一次自动模式拒绝——这证明分类器确实在做实际工作，同时没有拖累合法任务。

“自动模式为我们提供了速度与控制之间更安全的平衡，”Martin 说，“我们得以移除重复出现的提示并提升生产力，同时不牺牲安全性。我们可以看到自动模式在正确的时机进行拦截，这让我们有信心快速推进。”

Gusto AIT Cloud Engineering 团队的 Chad Kunsman 从另一个方向得出了同样的结论。他的工作——端点调查、日志审计、连接器管理、跨一整套 MCP 服务器的文档摄取——以每次约二十分钟的短促爆发进行，而不是过夜马拉松。他要的不是更长的运行时间；他想要 bypass permissions 那种无需操心的节奏，同时不必暴露在一条恶意提示或提示注入溜进来的风险之下。

“鉴于它对提示注入的防护，以及它检查你正在做的事是否真的与你的请求相符的方式，它是比 bypass permissions 更好的选择，也比权限提示快得多，”Chad 说。

在分类器偶尔介入时，Chad 说它都切中要害。“当它拦下我时，拦截是有道理的，而且解释了原因。我当时正偏离最初的要求，它就过来确认了。它完全没有跑偏。”

在最敏感的工作上，Chad 仍会切出自动模式。当一个会话深入生产基础设施——Terraform、AWS、对线上 API 的直接 POST 调用——他会切换到 accept edits 模式，逐个人工验证每次工具调用。“你必须权衡省下的时间与它可能合理犯错的地方，以及那样的错误会有多灾难性，”他说，“归根结底，发生了什么你仍然要负责。”

这一判断运行在一个更广泛的纵深防御体系之内：Gusto 将其 MCP 流量经由一个带工具防护与提示检查的受治理代理层路由，因此在自动模式介入之前，智能体就已经在严格限定范围的权限下工作。

### 在 Garner Health 加速软件开发生命周期（SDLC）

医疗科技公司 Garner Health 在 2 月向全体 550 名员工、覆盖所有职能推广了 Claude Code。该工具接入包括 Salesforce、Zendesk 和 Snowflake 在内的所有核心系统，公司鼓励员工每周花大约两小时把自己工作中最可重复的部分自动化。

在自动模式之前，这种规模化伴随着开销。Garner 的平台工程经理 Evan Magnussen 把权限管理描述为一个乏味的循环：手工维护已批准命令列表，然后眼看着管道命令被拒绝。

如今，Evan 和他的大多数同事在所有会话中都使用自动模式，从研究代码库到通过 MCP 管理外部集成。

“我们为整个工程组织构建了一套标准化的软件开发生命周期，而这真的只有在自动模式下才可能实现，”Evan 说，“员工们把它视为卸下了一副重担。他们再也不用连续几个小时盯着自己的智能体了。”

这套生命周期以标准化 skills 的插件形式运行。智能体接手一个任务，探索它能访问的上下文，把上下文文件提交到仓库，运行 Evan 所说的「对抗性研究」（antagonistic research）来压力测试自己的假设，然后进入实现阶段——只有在自己找不到所需上下文时才会停下来找人工。Evan 指出，这些以研究为主的阶段在自动模式之前是不可能实现的。

开箱即用，分类器几乎不需要调优。Evan 唯一的一次调整与 Kai 在 Nuro 的做法如出一辙：他配置自动模式不批准与其他人通信的动作，比如发送 Slack 消息或电子邮件。

“我个人不喜欢 Claude 在我和另一个人通信时擅自替我做主，”他说。负责核心知识产权的团队——在自动模式之前对跳过权限最持怀疑态度的团队——学会了调整分类器注入的提示，让它们对各自的工作更严格或更宽松。

对于其他正在推广它的企业，他的建议是？积极投入并构建正确的控制，让你在赋能工程师的同时确保部署安全。“如果我们说，大家各自去建自己的工作流，而我们没有任何遥测，那会非常危险，”Evan 说，“正因为我们有遥测，正因为我们构建了相对标准化的工作流，我们才有大得多的信心。”
