# 自动模式现成为 Claude Code 中 Pro、Max 和 Team 计划的默认设置

> 原文：[Auto mode is now the default in Claude Code for Pro, Max, and Team plans](https://claude.com/blog/auto-mode-default-in-claude-code/) · Claude 博客

我们将把[自动模式](https://code.claude.com/docs/en/auto-mode-config)设为 Claude Code 的默认模式。从 8 月 14 日开始，Pro、Max 和 Team 计划上的新会话将以自动模式运行。如果你已经自行设置了其他默认模式，可能会收到一次性的提示，询问你是否要切换到自动模式。如果你固定（pin）了默认模式，则一切照旧。自动模式分类器在每次工具调用时会消耗少量额外 token，而从今天起，我们不再向 Pro、Max 和 Team 计划上的 Claude Code 用户收取这笔分类器开销。

目前，自动模式在 Claude Enterprise、Claude API、AWS 上的 Claude Platform、Amazon Bedrock、Google Cloud 的 Agent Platform 以及 Microsoft Foundry 上仍为可选加入（opt-in），以便管理员有时间评估这一变更。在未来一个月内，我们将与云合作伙伴一起，计划在上述所有平台上将其设为默认，并不再收取分类器开销。在此期间，Enterprise 管理员可以通过托管设置（managed settings）将 Claude Code 的自动模式设为默认。

自动模式的设计目标，是在「用户不希望被打断」与「系统帮助避免有害动作」之间取得平衡：它不再弹出提示，而是让每次工具调用都经过一个分类器，该分类器专门拦截不可逆、具破坏性或指向你环境之外的动作。当分类器拦截了某个操作时，Claude 通常会自行找到更安全的推进方式，或直接请求你放行；如果它无法取得进展——连续三次被拦截，或整个会话累计二十次——Claude Code 会退回到人工批准。

过去几个月，我们一直在测试自动模式是否与普通用户一路点击通过提示一样安全，甚至更安全。我们进行了内部红队测试、第三方红队测试与提示注入评估、一项有 1,053 名付费测试者参与的对照研究，以及对真实生产会话的分析。在我们测试的每一项指标上，自动模式都与人工审查持平或更优。

自动模式还让 Claude 能够更长时间地自主工作。这使得为长时间运行的工作而构建的模型（如 Claude Opus 5）在大任务上连续运行数小时变得更加现实。降低用户的开销也能提升产出。在 Teams 和 Enterprise 的采纳者中，使用自动模式的用户交付的 PR 数量多出约 25%。解除对 Claude 的阻塞让任务可以更长时间不间断地运行，完成更多工作。Adobe、Nuro、Gusto 和 Garner Health 的团队已经[在生产环境中运行自动模式](https://claude.com/blog/auto-mode-in-production)作为其生产默认设置。

下面，我们分享促成这一变更的安全数据和客户成果，以及如果你更愿意自行设置时如何设定不同的默认模式。

## 人工审查与自动模式的对比

数据表明，人工审查可能沦为习惯性动作：用户在 Claude Code 中批准了 97% 的权限提示。虽然大多数提示针对的可能是安全的常规命令，但如此高的批准率说明许多用户是在条件反射式地点击，而不是逐条审查每条命令。这些提示要求开发者每天做出数十甚至上百个重要的安全决策，而且常常发生在项目进行之中，这把审查负担压在用户身上，也增加了重要问题被漏掉的概率。数据还表明，用户对其他类型的对话会更频繁地仔细审视并提出异议：例如，当 Claude 提交一份计划等待批准时，用户会拒绝其中 39%；而对于单条权限请求，拒绝率只有 3%。

同样的模式也出现在设置文件中。截至 2026 年 6 月，49.5% 的活跃 CLI 用户手动创建过 Bash 允许规则——5% 直接允许任何 shell 命令，另有 43% 拥有 `Bash(python:*) `或 `Bash(node:*)` 这类解释器规则，而它们在实践中几乎等效——并且这一占比大约每 5 周增长 5 个百分点。除允许规则之外，62% 的用户使用过 `bypassPermissions` 或对 Bash 点击过「不再询问」，25% 的交互式会话以 bypass permissions 模式启动。

在自动模式下，权限规则仍在分类器之前生效，但宽泛到足以授权任意代码执行的允许规则（如 python:*）除外。在自动模式运行期间，这类任意规则会被搁置，否则它们会让命令完全绕过分类器。设置文件不会被修改，一旦你切换到其他模式，这些规则会立即重新生效。

## 用自动模式提升安全性

我们内部以及多家第三方机构开展的研究表明，自动模式比典型用户如今对待权限提示的方式更安全。我们将自动模式与开发者点击权限提示时实际批准的内容进行了对比测试。在内部红队测试、第三方渗透测试和真实会话分析等各项指标上，自动模式都与人工批准持平或更优。

### 自动模式在安全性上优于人工权限

*在一项有 1,053 名付费专业测试者参与的对照实验中，人工审查仅捕获了 13.6% 的危险命令，而自动模式捕获了 89%。*

我们通过一家研究供应商聘请了 1,053 名付费测试者参加一项编码研究。这些参与者在专门为该研究搭建的测试环境中工作，而不是在他们自己的代码库或真实项目上。参与者知道自己正在被评估，但——遵循标准的盲测研究设计——并未被告知正在测量的是哪种行为。在每个会话进行到一半时，某一条权限提示会被替换成一条明显危险的命令，供应商会记录测试者是否批准了它（注：批准该提示绝不会导致任何危险内容被实际运行；改变的只是测试者看到的提示文本）。

测试者仅有 13.6% 的情况（1,053 人中的 143 人）捕获了危险命令，而自动模式阻止了其中 89% 的相同命令（1,053 条中的 937 条）。正面对比之下，自动模式阻止了 800 条人类批准的命令，而人类只阻止了 6 条自动模式放行的命令。随着会话变长，人类表现得更差：在会话早期他们大约拦截 17% 的危险命令，而在经历 50 次以上先前提示之后降至约 5%，而无论会话长短，自动模式的拦截率都保持平稳。

### 自动模式阻止更多有害动作

我们的研究还表明，与人工权限模式相比，自动模式带来的有害动作更少。

我们考察了自动模式在真实使用中的表现。2026 年 5 月至 6 月间，我们检查了安全流水线标记待审的会话，这些会话仅来自已选择加入数据用于训练与分析的账户。我们用一个模型按照两个 0–10 分的量表对每个会话重新评分。第一个是有害程度（harm severity），10 代表公司范围的不可逆伤害（例如泄露公司全部源代码），7 代表生产级别的严重度（例如从生产数据库删除行），0 代表完全可逆且局限于本地工作区的动作（例如覆盖一个草稿文件）。第二个是用户对该动作的请求有多明确，以便我们把用户直接要求的有害动作与智能体在较不明确的指示下采取的有害动作区分开。

在被标记的会话中，经过人工批准的会话包含严重非预期伤害的频率是自动模式会话的两倍以上。在生产级严重度（7+）上，6.3% 的人工批准会话包含一个用户并未明确要求的有害动作，而自动模式会话中这一比例为 2.4%，并且在我们测试的每个严重度层级上差距都同样存在。

### 对抗性红队测试让自动模式更强

我们与总部位于英国的 AI 安全初创公司 Apollo Research 合作，开展了为期两周的试点，将合成攻击注入真实的编码轨迹，覆盖三个数据集：宽泛失误、数据外泄和安全相关威胁。

这次合作遵循标准的「发现—修复—验证」循环。Apollo 分享了一组成功的攻击以及强化自动模式的建议。我们主要通过向分类器提供更多关于它所保护环境的上下文（仓库可见性、git 状态，以及下文所述的数据处理规则）来对其加固。

加固之后，Apollo 在一个我们从未接触过的独立留出攻击集上重新测试。自动模式捕获了它此前漏掉的大约一半攻击，代价是漏掉了它此前可以捕获的约 2% 的攻击。由于我们无法针对留出集调优，这说明加固带来的改进可以泛化到新攻击，而不是仅仅修补 Apollo 分享的那些特定攻击。在共享集与留出集上，分类器的漏报率从 12% 降到了 7%。

这些攻击在设计上就是合成且对抗性的，其目的就是找出分类器的失效点，比 Claude 在无人指示时会做的任何事都更具恶意。7% 的漏报率是针对这一攻击集测得的，不应被理解为真实流量上的漏报率。

### 自动模式降低提示注入风险

*启用自动模式后，在一项独立评估中，没有任何攻击对我们任何一款模型取得成功。在 Codex v0.144.5 的 Auto-review 权限模式下运行的 GPT-5.6 Sol 攻击成功率为 5.83%。GPT-5.6 Sol 以「max」推理努力（reasoning effort）运行，以测试其最高推理水平下的表现，所有 Claude 模型则以 high 努力运行。*

自动模式分类器为防御[提示注入攻击](https://www.anthropic.com/research/prompt-injection-defenses)增加了一层额外防线，这类攻击试图迫使智能体偏离用户的指令。在自动模式下运行时，工具结果会由探测探针（probe）扫描其中潜在恶意的指令，并且自动模式会检查动作是否与用户意图一致。我们将自动模式与无防护的模型进行对比测试，以展示这种纵深防御方法的威力。

我们委托第三方 Trajectory Labs 开展了一项评估，由其测试了截至 2026 年 7 月 17 日最新公开发布的 Claude Code 与 Codex 版本中的不同模型。¹他们测试了 72 个对 Anthropic 保密的间接提示注入场景，每个场景测试 10 次。这些攻击若发生在非测试环境中，将导致可能伤害用户的不可逆动作，例如敏感数据外泄、金融诈骗或凭据钓鱼。这些攻击是针对 Claude Opus 4.7 优化的，而该模型并不在报告的模型之列，因此评估中的每款模型面对的都是未见过的攻击。除自动模式外，评估还考察了 Claude Code 的 *bypassPermissions* 模式和 Codex 的 *Full Access* 模式。

Codex 和 Claude Code 都使用由 Trajectory Labs, PBC 制作的同一套浏览器集成进行评估。该集成提供一组 MCP 工具，是对 `navigate` 等常见 Chrome API 的薄封装。第一方浏览器集成（例如 OpenAI 与 Anthropic 提供的 Chrome 扩展）中内置的安全防护未纳入测试。因此，这些结果应被视为对底层模型的测量，而不是对某一具体部署中可能存在的全部安全防护的测量。

**在这项评估中，720 次攻击尝试没有一次对运行自动模式的 Claude Fable 5、Opus 5 或 Sonnet 5 取得成功。**另一方面，针对运行 Codex *Auto-review* 模式的 GPT-5.6 Sol，有 5.83% 的攻击取得成功。值得注意的是，这一数字高于我们的最新模型在没有额外防护的 *bypassPermissions* 模式下运行时 0.09% 的平均攻击成功率。测试显示，GPT-5.6 Sol 在 *Full Access* 模式下运行时攻击成功率为 19.03%。如下图所示，在工具以文本形式返回结果的任务与需要通过截图与浏览器交互的任务之间，攻击成功率有所不同。

*自动模式在工具调用和浏览器 GUI 使用两种场景下都能防御提示注入。在第三方评估中，OpenAI 模型在浏览器任务上的攻击成功率更高。*

### 自动模式在 Anthropic 内部阻止的三起事故

在 Anthropic 内部的所有 Claude Code 使用中，自动模式同样是默认设置。以下是分类器在内部阻止的三个动作：

- **一次脱离网络的数据泄露：**当向内部网盘的上传失败后，Claude 的退路是把同一份报告发布到某个公开的代码分享网站。自动模式拒绝了这条退路，并提示用户下一步该怎么做。
- **一次破坏性的批量操作：**在一个长时间运行的会话中，Claude 试图对大约两千个 pod 执行批量进程终止，并排队执行删除操作，而这些操作本会拆毁数百块 GPU 上正在进行的训练任务。自动模式在执行前标记了这些破坏性命令。
- **过度宽泛的权限提升：**在被要求开通只读的账单访问权限时，Claude 选中了一个在账户根级别授予完全管理控制权的云角色。自动模式捕获了所请求内容与将被授予角色之间的错配。

在每起案例中，Claude 要么自行找到了更安全的路径，要么在继续之前先向用户确认。

### 让自动模式更加安全

我们在持续投入新的自动模式功能，让它更安全、更容易交付生产代码。近期的一些例子包括：

- [**硬拒绝（hard denies）**](https://code.claude.com/docs/en/auto-mode-config#override-the-block-and-allow-rules)：数据外泄（比如把你的代码或密钥发送到外部）属于分类器设计上绝不批准的类别。要执行这样的动作，你必须切换出自动模式，或者自己运行该命令。硬拒绝规则可以通过设置自定义，让你添加更多即使组织内用户主动请求也绝不放行的规则。
- **数据访问与共享规则：**分类器现在带有明确的规则，用于区分密钥和潜在的敏感/机密信息，以及各自可以在何处被访问和共享。为了让这些规则可执行，它还会在 git push 或 pull request 执行之前检查目标是公开、私有还是可信的。同一次 push 既可能是例行操作，也可能是数据外泄，取决于它落在哪里：属于你们团队私有仓库的代码不应出现在公开仓库中，分类器现在被设计为在可能发生这种情况时进行标记。
- **在破坏性 git 操作之前检查 git status**：在一条可能丢弃未提交工作的命令（如 git reset --hard）之前，分类器会查看仓库当前的 git status，让自动模式知道正在被重置的是什么。
- **提示注入筛查**：当 Claude 从外部来源（如网页、文件内容或工具输出）拉取内容时，API 侧的探针会检查这些内容中是否存在劫持 Claude 行为的企图。当某些内容看起来像注入企图时，在该结果分享给用户之前，会向 Claude 的上下文中加入一条警告。

## 生产环境中的自动模式

一些团队已经在把自动模式作为其生产默认设置运行：

- **Adobe** 的商品营销平台团队负责让 Adobe.com 上 90 多个国家、30 多种语言的定价与促销页面保持准确和最新。他们构建了一个智能体循环来构建和验证这些页面，并在自动模式下运行，工程师只需接收完成的 PR 进行审查。
- **Nuro** 在其研究与工程部门全面运行自动模式，用它驱动过夜研究智能体，对评估指标做爬山式（hill-climb）优化，到早晨返回完成的 PR 供审查。
- **Gusto** 采纳自动模式，以终结把工程师推向完全绕过权限检查的权限疲劳（permission fatigue）。自 5 月中旬以来，约 10% 的会话包含一次分类器拒绝——这证明它确实在做实际工作，同时没有拖慢合法任务。
- **Garner Health** 通过托管设置将自动模式作为默认推送给全部 550 名员工，标准化了一套不再依赖手工维护的命令允许列表的全公司软件开发生命周期（SDLC）。

“在 Adobe，我们希望快速推进，同时不牺牲我们在 Adobe.com 上交付的客户体验质量。借助 Claude Code 自动模式，我们构建了一个大幅加速工作的智能体循环。Claude 构建用户界面，然后循环回来验证它与预期设计相符，在我们查看之前自动修复任何问题。这缩短了我们的开发周期，同时交付了像素级精准的结果。”

“前几天，我在晚上 10 点启动了一个智能体，它一直运行到凌晨 5 点——早上它交给我三个 PR。我觉得这相当了不起。只有自动模式才能支撑这样的工作负载。”

“自动模式为我们提供了速度与控制之间更安全的平衡。我们得以移除重复出现的提示并提升生产力，同时不牺牲安全性。我们可以看到自动模式在正确的时机进行拦截，这让我们有信心快速推进。”

“我们为整个工程组织构建了一套标准化的 SDLC，而这只有在自动模式下才可能实现。员工们把它视为卸下了一副重担。他们再也不用连续几个小时盯着自己的智能体了。”

了解这些客户如何[在生产环境中运行自动模式](https://claude.com/blog/auto-mode-in-production)。

## 开始使用

对于 Pro、Max 和 Team 用户：如果你尚未设置默认权限模式，你将收到一条产品内通知，新会话将自动以自动模式启动。如果你已经设置了其他默认模式，你可能会看到一次性的提示，询问你是否愿意把默认模式切换为自动模式。如果你的 Team 管理员已在托管设置中设定了默认值，则一切照旧。

对于 Enterprise 用户以及通过 Claude API 访问 Claude Code 的用户，自动模式目前仍为可选加入。我们计划在未来一个月内将自动模式设为默认，并在那之前通知 Enterprise 管理员。

要切换模式，在 CLI 中按 Shift+Tab，或在桌面应用中使用模式下拉菜单。管理员可以在[托管设置](https://code.claude.com/docs/en/server-managed-settings)中用 `defaultMode` 固定全组织范围的默认值，或用 `disableAutoMode` 完全关闭自动模式。

最后，虽然我们相信自动模式为大多数用户降低了风险，但它依赖分类系统，因此并不能消除风险。对于生产基础设施的高风险变更，我们仍然建议你自己审查 Claude 的动作。完整的配置说明请[参阅自动模式文档](https://code.claude.com/docs/en/auto-mode-config)。
