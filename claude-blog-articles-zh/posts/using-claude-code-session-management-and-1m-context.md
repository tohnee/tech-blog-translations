# Claude Code 使用心得：会话管理与 1M 上下文

> 原文：[Using Claude Code: session management and 1M context](https://claude.com/blog/using-claude-code-session-management-and-1m-context/) · Claude 博客

我们发布了 **`/usage`**，这是一个新的斜杠命令（slash command），帮助你了解自己在 Claude Code 中的使用情况。这一功能源于我们与大量客户的交流。

在这些沟通中反复出现的一点是：用户管理会话的方式差异很大，尤其是在 Claude Code 新近更新支持 100 万 token 上下文之后。

你是只用一个会话，还是在终端里同时开着两个会话？你是每发一条提示就新开一个会话吗？你什么时候会使用 [compact](https://platform.claude.com/docs/en/build-with-claude/compaction)、回退（rewind）或[子智能体](https://code.claude.com/docs/en/sub-agents)？又是什么导致了一次糟糕的 compact 或糟糕的会话？

其中的细节之多出人意料，而这些细节能实实在在地影响你使用 [Claude Code](https://claude.com/product/claude-code) 的体验——几乎所有细节都归结于[上下文窗口的管理](https://code.claude.com/docs/en/how-claude-code-works)。

## **上下文、压缩与上下文腐化快速入门**

上下文窗口是模型在生成下一条回复时能够一次性"看到"的全部内容，包括系统提示、迄今为止的对话、每一次工具调用及其输出，以及读过的每一个文件。Claude Code 拥有 100 万 token 的上下文窗口。

遗憾的是，使用上下文会对性能产生轻微影响，这通常被称为上下文腐化（context rot）。上下文腐化指的是这样一种现象：随着上下文增长，模型性能会下降，因为注意力被分散到更多 token 上，较旧的、无关的内容开始干扰当前任务。

上下文窗口是一个硬性截止点，因此当你接近上下文窗口的尽头时，你正在处理的任务会被自动摘要成一段更简短的描述，模型随后在新的上下文窗口中继续这项工作。我们称之为压缩（compaction）。你也可以自行触发压缩。

## **每一轮都是一个分支点**

假设你刚让 Claude 完成了一件事——现在上下文里已经有了一些信息（工具调用、工具输出、你的指令），而接下来可供选择的动作之多同样出人意料：

- **继续（Continue）**——在同一个会话中再发一条消息
- **`/rewind`（连按两次 Esc）**——跳回之前某条消息，从那里重新尝试
- **`/clear`**——开启一个新会话，通常附带一份从刚才所学内容中提炼出的简报
- **压缩（Compact）**——对目前的会话进行摘要，并在摘要的基础上继续
- **子智能体（Subagents）**——把下一块工作委派给一个拥有独立干净上下文的智能体，只把其结果取回来

最自然的做法当然就是继续，但其余四个选项的存在都是为了帮助你管理上下文。

## **何时开启新会话**

什么时候该维持一个长期运行的会话，什么时候该新开一个？我们大致的经验法则是：开始一项新任务时，就应该开启一个新会话。

1M 上下文窗口意味着你现在可以更可靠地完成更长的任务，比如从零构建一个全栈应用，但上下文腐化仍可能出现。

有时你要做的相关任务仍需要部分上下文，但并非总是如此。例如，为你刚实现的功能撰写文档。这时你虽然可以新开一个会话，但 Claude 就不得不重读你刚刚实现的那些文件，这样更慢也更贵。

## **用回退代替纠正**

在 Claude Code 中，连按两次 Esc（或运行 `/rewind`）可以跳回任意一条先前的消息，并从那里重新发出提示。该点之后的消息会从上下文中丢弃。

纠错时，回退往往是更好的方式。举例来说，Claude 读了五个文件，尝试了一种做法，结果行不通。你的直觉可能是输入"那不行，改用 X 试试"。但更明智的动作也许是回退到刚读完文件之后，带着你学到的东西重新提示："不要用方案 A，foo 模块没有暴露那个接口——直接上方案 B。"

你还可以使用*"summarize from here"*（从这里开始总结）或 `/rewind` 斜杠命令，让 Claude 总结它学到的东西并生成一条交接消息，有点像"未来的 Claude"在尝试某事失败之后，写给"过去的 Claude"的一封留言。

## **压缩还是另起新会话**

会话一旦变长，你有两种办法甩掉多余的上下文：`/compact` 或 `/clear`（然后重新开始）。它们感觉相似，行为却大相径庭。

**压缩（Compact）**让模型总结迄今为止的对话，然后用这份摘要替换历史记录。它是有损的，但你不必亲自写任何东西，而且 Claude 在纳入重要经验或文件方面可能更为周全。你还可以通过传入指令来引导它（`/compact focus on the auth refactor, drop the test debugging`）。

使用 `/clear` 时，*由你*来写下什么才重要（"我们在重构 auth 中间件，约束条件是 X，关键文件是 A 和 B，我们已经排除了方案 Y"），然后干净起步。这要多花些功夫，但得到的上下文正是你认定相关的内容。

## **是什么导致了一次糟糕的自动压缩？**

如果你经常运行长时间的会话，可能已经注意到过一些压缩效果特别差的时刻。在这种情况下，我们发现糟糕的压缩往往发生在模型无法预测你工作走向的时候。

在上面的例子中，自动压缩（autocompact）在一长段调试会话结束后触发，总结了排查过程，而你接下来的消息是"现在修复我们在 bar.ts 里看到的另一个警告"。

但由于会话的焦点是调试，另一个警告可能已经被从摘要中丢掉了。

这一点尤其棘手，因为受上下文腐化影响，模型在压缩时正处于它最"迟钝"的时刻。有了 100 万上下文，你有更充裕的时间主动执行 /compact，并附上描述你接下来想做什么的说明。

## **子智能体与全新的上下文窗口**

当你预先知道某块工作会产生大量之后不会再用的中间输出时，[子智能体](https://claude.com/blog/subagents-in-claude-code)通常能表现很好。

当 Claude 通过 Agent 工具生成一个子智能体时，该子智能体会拥有自己全新的上下文窗口。它可以根据需要做尽可能多的工作，然后综合其结果，最终只有报告返回给父智能体。

我们在 Anthropic 使用的心理测试是：*这个工具的输出我之后还会用到吗，还是只需要它的结论？*

虽然 Claude Code 会自动调用子智能体，但你也可以明确地让它这么做。例如，你可以这样告诉它：

- "启动一个子智能体，根据下面这份规格文件验证这项工作的结果"
- "派生一个子智能体，通读另一个代码库，总结它是如何实现 auth 流程的，然后由你自己以同样的方式实现"
- "派生一个子智能体，根据我的 git 改动为这个功能撰写文档"

**综合运用**

为了帮你选择该用哪种上下文管理功能，我们整理了下面这张实用的表格，列出常见情形、该用哪个工具，以及原因。

| 情形 | 可以考虑使用 | 原因 |
|---|---|---|
| 同一任务，上下文仍然相关 | 继续（Continue） | 窗口里的一切仍然举足轻重；没必要花代价重建它。 |
| Claude 走上了错误的路 | 回退（连按两次 Esc） | 保留有用的文件读取，丢弃失败的尝试，带着你学到的东西重新提示。 |
| 任务进行到一半，但会话被过时的调试/探索内容撑得臃肿 | `/compact <提示>` | 省时省力；由 Claude 决定什么是重要的。必要时可用指令加以引导。 |
| 开始一个真正的新任务 | `/clear` | 零腐化；由你精确掌控什么会被带入新会话。 |
| 下一步会产生大量你只需要其结论的输出（代码库搜索、验证、文档撰写） | 子智能体 | 中间的工具噪声留在子智能体的上下文里；只有结果返回。 |
