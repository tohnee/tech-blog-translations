# 多智能体协作模式：五种方法及适用场景

> 原文：[Multi-agent coordination patterns: Five approaches and when to use them](https://claude.com/blog/multi-agent-coordination-patterns/) · Claude 博客

在之前的文章中，我们探讨了多智能体系统何时能带来价值、何时单智能体才是更好的选择。本文面向已经做出这一判断、现在需要决定哪种协作模式适合自己的问题的团队。

我们见过一些团队按「哪个听起来更高大上」来选模式，而不是看哪个适合手头的问题。我们建议从最简单的可行模式入手，观察它在哪些地方吃力，再据此演进。本文将剖析五种模式的运作机制与局限：

- **生成者-验证者**（Generator-verifier）：适用于有明确评估标准、对输出质量要求苛刻的场景
- **编排者-子智能体**（Orchestrator-subagent）：适用于任务分解清晰、子任务有边界的场景
- **智能体团队**（Agent teams）：适用于可并行、相互独立、长时间运行的子任务
- **消息总线**（Message bus）：适用于事件驱动的流水线，且智能体生态不断壮大的场景
- **共享状态**（Shared-state）：适用于智能体在彼此发现之上继续构建的协作式工作

## 模式 1：生成者-验证者（Generator-verifier）

这是最简单的多智能体模式，也是部署最广的模式之一。我们在上一篇文章中把它称为验证子智能体模式，这里采用外延更广的生成者-验证者提法，因为生成者未必要由编排者来担任。

### 工作原理

生成者接到一个任务后产出初始输出，并把它交给验证者评估。验证者检查输出是否满足要求的标准，要么判定合格予以接受，要么附上反馈予以驳回。若被驳回，反馈会被回传给生成者，生成者据此做出修订后的尝试。这一循环持续进行，直到验证者接受输出，或达到最大迭代次数为止。

### 适用场景

设想一个为客户工单生成邮件回复的客服系统。生成者依据产品文档和工单上下文产出初始回复；验证者对照知识库核查准确性，依据品牌准则评估语气，并确认回复覆盖了提出的每一个问题。未通过的检查会连同指明具体问题的反馈一起返回给生成者，比如把某个功能归到了错误的定价档位，或者工单中的某个问题没有回应。

当输出质量至关重要、且评估标准可以显式化时，就适合使用这种模式。它对代码生成（一个智能体写代码，另一个写测试并运行测试）、事实核查、量规评分（rubric-based grading）、合规校验等场景都很有效——凡是一次错误输出的代价高于多跑一轮生成的领域，都适用。

### 局限所在

验证者的水平取决于其标准。一个只被要求「检查输出好不好」、没有任何进一步标准的验证者，只会对生成者的输出照单全收。团队最常见的失败方式，就是在没有定义「验证」到底意味着什么的情况下就把循环搭起来，这会制造出质量控制的假象，却没有实质。（我们在上一篇文章中讨论过这种「早期胜利」问题。）

这种模式还假设生成与验证是两种可以分开的能力。如果评估一个创造性方案和提出这个方案一样难，验证者未必能可靠地发现其中的问题。

最后，迭代循环可能陷入停滞。如果生成者无法解决验证者的反馈，系统就会来回震荡、无法收敛。设置最大迭代次数并配备兜底策略（升级给人工处理，或附上保留意见返回最佳的一次尝试），可以避免它变成死循环。

## 模式 2：编排者-子智能体（Orchestrator-subagent）

层级结构是这种模式的灵魂。一个智能体充当团队负责人，负责规划工作、分派任务并综合结果；子智能体承担具体职责并汇报。

主智能体接到任务后决定如何处理，可能亲自完成一部分子任务，同时把另一些分派给子智能体。子智能体完成各自的工作并返回结果，由编排者综合成最终输出。

[Claude Code](https://claude.com/product/claude-code) 用的就是这种模式。主智能体亲自写代码、改文件、执行命令；当需要搜索大型代码库或调查相互独立的问题时，它会在后台派出子智能体，让自己手头的活继续干、结果流式传回。每个子智能体都在自己的上下文窗口中运行，只返回提炼后的结论。这样，探索在并行进行的同时，编排者的上下文始终聚焦于主任务。

设想一个自动化代码评审系统。当有 pull request 到达时，系统需要检查安全漏洞、核实测试覆盖率、评估代码风格，并审视架构一致性。每项检查彼此独立，需要不同的上下文，也产出明确的结果。编排者把每项检查分派给专门化的子智能体，收集结果后综合出一份统一的评审意见。

当任务分解清晰、子任务之间几乎不相互依赖时，就适合使用这种模式。编排者保持对总体目标的连贯把握，子智能体则专注于各自的职责。

编排者会成为信息瓶颈。当某个子智能体发现了与另一个子智能体的工作相关的信息时，这条信息必须经由编排者中转。如果安全子智能体发现了一个影响架构子智能体分析的认证缺陷，编排者必须识别出这层依赖，并把信息路由到位。经过几次这样的交接之后，关键细节往往丢失，或在摘要过程中被抹掉。

顺序执行也限制了吞吐量。除非显式地并行化，子智能体只能一个接一个地运行，这意味着系统付出了多智能体的 token 成本，却没有换来速度上的收益。

## 模式 3：智能体团队（Agent teams）

当工作可以分解成能够长期独立推进的并行子任务时，编排者-子智能体模式就会显得约束过多。

协调者把多个工作者智能体作为独立进程启动。队友从共享队列认领任务，自主地多步推进，完成后发出信号。

与编排者-子智能体模式的差异在于工作者的持久性。编排者为单个有边界的子任务生成一个子智能体，子智能体返回结果后即终止。而队友会跨越多项任务持续存活，不断积累上下文与领域专门知识，随时间推移提升自己的表现。协调者只负责分派工作、收集成果，不会在任务之间重置工作者。

设想把一个大型代码库从一个框架迁移到另一个框架。每个队友可以独立迁移一个服务，服务各自带着自己的依赖、测试套件和部署配置。协调者把每个服务分派给一个队友，队友自主完成整个迁移：更新依赖、修改代码、修复测试、验证。协调者收集已完成的迁移，并在整个系统上运行集成测试。

当子任务相互独立、并且能从持续的多步骤工作中获益时，就适合使用这种模式。每个队友都会积累自己领域的上下文，而不是每次分派都从零开始。

独立性是关键前提。编排者-子智能体模式里编排者可以在子智能体之间调停并路由信息，而队友各自独立运作，难以共享中间发现。如果一个队友的工作会影响另一个队友，双方都无从知晓，它们的输出就可能冲突。

完成检测也更难。由于队友自主工作、耗时各不相同，协调者必须处理部分完成的情况——一个队友两分钟就干完了，另一个要花二十分钟。

共享资源会放大这两个问题。当多个队友操作同一个代码库、数据库或文件系统时，两个队友可能编辑同一个文件，或做出互不兼容的修改。这种模式要求细致的任务划分和冲突解决机制。

## 模式 4：消息总线（Message bus）

随着智能体数量增加、交互模式日趋复杂，直接协调会变得难以管理。消息总线引入了一个共享的通信层，智能体在其中发布和订阅事件。

智能体通过两个原语交互：发布（publish）与订阅（subscribe）。智能体订阅自己关心的主题，路由器负责投递匹配的消息。具备新能力的新智能体可以直接开始接收相关工作，无需重新调整现有连接。

一个安全运营自动化系统展示了这种模式的用武之地。告警从多个来源涌入，一个分诊智能体按严重程度和类型对每条告警分类：高严重度的网络告警路由给网络调查智能体，凭证类告警路由给身份分析智能体。每个调查智能体都可能发布「信息增补」请求，由一个上下文采集智能体来完成。调查发现随后流向响应协调智能体，由它决定合适的处置动作。

这条流水线很适合消息总线：事件从一个阶段流向下一个阶段；随着威胁类别的演化，团队可以随时加入新的智能体类型；各个智能体也可以独立开发和部署。

当流水线由事件驱动、工作流从事件中涌现而非遵循预定顺序，且智能体生态可能持续增长时，就适合使用这种模式。

事件驱动通信的灵活性让追踪变得更难。当一条告警在五个智能体之间触发一连串事件时，要弄清发生了什么，需要细致的日志记录与关联分析。调试比跟读编排者的顺序决策难得多。

路由准确性同样关键。如果路由器错误分类或丢弃了某个事件，系统会静默失效——什么都不处理，却也从不崩溃。基于 LLM 的路由器提供了语义层面的灵活性，但也引入了自身的失效模式。

## 模式 5：共享状态（Shared state）

前面几种模式中的编排者、团队负责人和消息路由器都在集中管理信息流。共享状态则去掉了中间人，让智能体通过一个人人可直接读写的持久化存储来协作。

智能体自主运行，读写同一个共享数据库、文件系统或文档。没有中央协调者。智能体到存储里查找相关信息，根据所获采取行动，再把自己的发现写回去。工作通常从初始化步骤开始——向存储中写入一个问题或数据集；当满足终止条件时结束：可以是时限、收敛阈值，或由指定智能体判定存储中已包含足够好的答案。

设想一个研究综合系统，多个智能体从不同角度调查一个复杂问题：一个探索学术文献，一个分析行业报告，第三个研究专利文件，第四个监测新闻报道。每个智能体的发现都可能为其他智能体的调查提供线索。学术文献智能体可能发现某位关键研究者，其所在公司正值得行业报告智能体进一步深挖。

在共享状态下，发现直接写入存储。行业报告智能体可以立即看到学术智能体的发现，不必等协调者来中转信息。智能体们在彼此的工作之上继续构建，共享存储也随之成为一个不断演进的知识库。

共享状态还消除了协调者这个单点故障。任何一个智能体停摆，其他智能体仍继续读写。而在编排者和消息总线系统中，协调者或路由器一旦故障，一切都会停摆。

没有显式协调，智能体可能重复劳动，或走上相互矛盾的路线。两个智能体可能各自独立地调查同一条线索。系统行为来自智能体之间的交互，而非自上而下的设计，这让结果更难预测。

更棘手的失效模式是反应式循环（reactive loops）。比如智能体 A 写入一条发现，智能体 B 读到后写入一条跟进，A 看到 B 的跟进又做出回应……系统就这样在无法收敛的工作上持续烧 token。重复劳动和并发写入都有成熟的工程化解决方案（加锁、版本化、分区）。反应式循环则是行为层面的问题，需要把终止条件作为一等公民来对待：时间预算、收敛阈值（连续 N 轮没有新发现），或者指定一个智能体专职判断存储中何时已有足够好的答案。把终止条件当作事后补丁的系统，往往要么无限循环，要么在某个智能体的上下文被填满时戛然而止。

## 在模式之间选择与演进

选对模式取决于关于系统结构的几个关键问题。在上一篇文章中，我们主张以上下文为中心的分解（context-centric decomposition）：按每个智能体需要什么上下文来划分工作，而不是按工作类型来划分。这一原则在这里同样适用。各模式的差异，正在于它们如何管理上下文边界和信息流。

### 编排者-子智能体 vs. 智能体团队

两者都由协调者把工作分派给其他智能体。问题在于工作者需要把上下文维持多久。

- **选编排者-子智能体**：当子任务短小、聚焦、产出明确时。代码评审系统就很适合，因为每项检查都在一次有边界的调用内完成分析、生成报告并返回，子智能体无需跨多轮携带上下文。
- **选智能体团队**：当子任务受益于持续的多步骤工作时。代码库迁移就很合适，因为每个队友会对自己负责的服务建立起真正的熟悉度——依赖图、测试模式、部署配置。这种积累起来的上下文带来的性能提升，是一次性分派无法复制的。

当子智能体需要跨调用保留状态时，智能体团队是更好的选择。

### 编排者-子智能体 vs. 消息总线

两者都能处理多步骤工作流。问题在于工作流结构的可预测程度。

- **选编排者-子智能体**：当步骤顺序可以事先确定时。代码评审系统遵循固定流水线：接收 PR、运行检查、综合结果。
- **选消息总线**：当工作流从事件中涌现、且可能随发现而变化时。安全运营系统无法预知会有什么告警到来、需要怎样的调查路径。可能出现需要全新处理方式的新型告警。消息总线通过把事件路由给具备相应能力的智能体来容纳这种变化，而不是遵循预定顺序。

当编排器中处理日益繁多情况的条件逻辑不断堆积时，消息总线能让这些路由逻辑变得显式且可扩展。

### 智能体团队 vs. 共享状态

两者都让智能体自主工作。问题在于智能体是否需要彼此的发现。

- **选智能体团队**：当智能体在互不交互的独立分区上工作时。代码库迁移属于这种情况，每个队友负责自己的服务，最后由协调者汇总结果。
- **选共享状态**：当智能体的工作是协作性的、发现需要在它们之间实时流动时。研究综合系统更匹配这种模式，因为学术智能体发现的关键研究者会立刻与行业智能体的调查产生关联。

一旦队友之间需要相互沟通，而不只是分享最终结果，共享状态会让这一切更自然。

### 消息总线 vs. 共享状态

两者都支持复杂的多智能体协作。问题在于工作是以离散事件的形式流动，还是积累成一个共享知识库。

- **选消息总线**：当智能体对流水线中的事件做出响应时。安全运营系统逐段处理告警，每个事件都会在完成之前触发下一个。这种模式擅长把事件路由给具备相应能力的智能体。
- **选共享状态**：当智能体在时间推移中不断在已有发现之上构建时。研究综合系统持续地汇聚知识，智能体反复回到存储中，看看别人发现了什么，再调整自己的调查方向。

消息总线仍然存在路由器，意味着由一个中心组件决定事件的去向。共享状态则是去中心化的。如果把消除单点故障列为优先事项，共享状态在这方面做得更彻底。

如果消息总线系统中的智能体发布事件只是为了共享发现，而不是触发动作，那么共享状态是更好的选择。

## 上手建议

生产系统常常把多种模式组合使用。一种常见的混合方式是：整体工作流用编排者-子智能体，协作密集的子任务用共享状态。另一种是：事件路由用消息总线，每类事件由智能体团队式的工作者处理。这些模式是积木，不是互斥的选择。

下表总结了各模式分别适用于什么情形。

| 情形 | 模式 |
|---|---|
| 对输出质量要求极高，评估标准明确 | 生成者-验证者（Generator-Verifier） |
| 任务分解清晰，子任务有边界 | 编排者-子智能体（Orchestrator-Subagent） |
| 并行负载，子任务独立且长时间运行 | 智能体团队（Agent Teams） |
| 事件驱动流水线，智能体生态不断壮大 | 消息总线（Message Bus） |
| 协作式研究，智能体共享发现 | 共享状态（Shared State） |
| 要求无单点故障 | 共享状态（Shared State） |

对大多数用例，我们建议从编排者-子智能体入手。它能以最小的协调开销覆盖最广的问题范围。观察它在哪里吃力，随着具体需求的浮现再向其他模式演进。
