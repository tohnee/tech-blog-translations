# 为 AI 加速的攻击做好安全计划准备

AI 正在改变漏洞被发现和利用的速度。基于我们自己的发现与安全实践，我们发布一组初步建议，帮助你加固防御。

本周早些时候，我们宣布了 Project Glasswing——这是我们的一项紧迫尝试：把最新前沿模型 Claude Mythos Preview 强大的网络安全能力用于防御目的。在[公告](https://www.anthropic.com/glasswing)与[配套技术博文](https://red.anthropic.com/2026/mythos-preview/)中，我们描述了 AI 模型如何快速降低发现并利用软件漏洞所需的资源、时间和技能门槛。

着眼于 AI 闪电般的进展，我们也指出：具备类似能力水平的模型很快就会广泛可得。在未来 24 个月内，大量可能已潜伏数年、无人注意的 bug 将被 AI 模型发现，并被串联成可用的利用链。事实上，目前公开可得的、低于 Mythos 水平的模型，就已经能够[发现严重漏洞](https://www.anthropic.com/news/mozilla-firefox-security)——这些漏洞被传统审查长期遗漏。

所幸这件事是双向的：攻击者可以用 AI 跑得更快，防御者同样可以采用 AI 工具来保护自己。本文中，我们基于安全团队与研究人员在使用前沿 AI 模型保护真实代码库和系统时的观察与经验，给出安全建议与实操提示。我们希望安全团队及其他读者在迈入 AI 驱动的网络安全时代时，能觉得这些建议有用。

下面的许多建议本已属于现有安全共识；我们按"哪些控制我们已经看到站得住、哪些正在退化"对其做了优先级排序。如果你的组织按 SOC 2 和 ISO 27001 做合规报告，这些内容可以直接映射到你已经在跟踪的控制项上。

随着我们和 Project Glasswing 合作伙伴继续推进网络安全工作，我们会持续更新这份指引。

## **现在就该做的事**

### **1. 补齐你的补丁缺口**

AI 模型非常擅长在未打补丁的系统中识别已知、已修补漏洞的特征。把补丁逆向成可用的利用程序，恰恰是这类模型最擅长的机械性分析。这意味着"补丁发布"到"利用程序可用"之间的窗口正在缩短。

* *立即修补 [CISA 已知被利用漏洞（KEV）目录](https://www.cisa.gov/known-exploited-vulnerabilities-catalog)上的所有内容。* 该目录收录的是已确认正在被活跃利用的漏洞。清单中任何可从网络触达的东西，都应当作紧急事件处理。
* *用 [EPSS](https://www.first.org/epss/) 对其余项做优先级排序。* 漏洞利用预测评分系统（EPSS）给出某个通用漏洞与暴露（CVE）在未来 30 天内被利用的每日更新概率。先打 KEV 清单，再打所有高于选定 EPSS 阈值的项，能帮你把成千上万个未决 CVE 变成一条可管理的队列。
* *缩短暴露于互联网的系统的补丁时延。* 我们建议：面向互联网的应用在利用程序出现后 24 小时内完成修补，其他漏洞在数天内完成。
* *把补丁部署与重启自动化*——前提是自动更新导致停机的风险可以接受。人工审批环节会引入延迟，而延迟现在就是首要风险。

**实操提示：** 大多数云和操作系统厂商已经提供补丁自动化，启用它通常只是一次简单的配置变更。对于容器镜像和依赖清单，已有若干开源扫描器可以作为单个持续集成步骤运行，并用 KEV 目录与 EPSS 的数据标注 CVE，从而内置优先级排序。

### **2. 准备好处理数量多得多的漏洞报告**

在未来大约两年内，你用来接收、排序和修复漏洞（包括自己代码中的漏洞，以及从供应商处购买的软件中的漏洞）的流程，将承受远大于今天的压力。你的漏洞管理流程应当为来自供应商和上游的大量补丁做好准备。

* *按"发现量增加一个数量级"来做规划。* 受理、分诊和修复跟踪等环节都需要跟上被暴露漏洞数量的增长。如果你的安全会议还围绕一张电子表格和每周例会展开，那大概率跟不上。值得考虑一定程度的自动化——当然要有人参与，以应对这里的绝对体量。
* *检查开源依赖的安全性。* 大多数软件供应链主要是开源的。多数开源项目没有服务等级协议，也没有维持高水平安全的承诺。[OpenSSF Scorecard](https://securityscorecards.dev/) 会就分支保护、模糊测试覆盖率、签名发布、维护者活跃度等信号，对每个依赖自动评分。它可在 CI 中运行，有助于识别无人维护的包。
* *对你的供应商应用同样的期望。* 你的第三方风险管理流程应当询问供应商：他们自己在为加速的利用时间线做哪些准备，以及是否在扫描自己的代码。

**实操提示：** 研究一下能评估"漏洞代码可达性"的开源软件与第三方服务。构建自动化流程，持续把新的软件更新交付到 IT 与生产基础设施：通过对更新做回归测试，获得"可以快速部署"的信心。

上面我们提到这些流程的自动化。AI 可以在若干重要方面提供帮助：

* *加速分诊。* 分诊是瓶颈，因为它需要专家审查和分类。前沿模型可以对现有积压去重、利用对你的资产的知识来估计暴露程度，并在受影响代码路径已预先识别的情况下起草修复工单。
* *检查依赖是否冗余。* 大型代码库大多会积累多个做同一件事的库（好几个 HTTP 客户端、好几个 JSON 解析器）。这给了攻击者更多机会，而你这边没有得到任何功能收益。把 lockfile 丢给 LLM，问它哪些依赖有重叠（以及迁移与合并会是什么样），是个一小时的练习，往往很划算。
* *AI 升级自动化。* 前沿模型越来越能生成补丁，与漏洞报告一并给出。当报告清晰完整——甚至附有概念验证（PoC）时——模型可以直接测试补丁，确认利用路径已被封堵。它还能直接自动化"接受上游补丁"的流程，验证升级不会破坏测试或内部系统。
* *AI vendoring（用 AI 自研替代依赖）*。一些小依赖在 OpenSSF Scorecard 上得分很低——也许是因为没有活跃维护。你不应继续依赖它们；可以考虑让 LLM 自己写代码，重新实现你实际用到的那部分功能。

### **3. 在发布之前发现 bug**

预防总是好于治疗。你应当假设进入生产的 bug 终将被发现，因此安全测试必须远远提前。

* *把静态分析和 AI 辅助代码评审加入持续集成流水线*，并对高置信度的发现阻断合并。如果误报让这变得不切实际，你应该保留这项检查，但去解决工具问题。[OWASP 应用安全验证标准](https://owasp.org/www-project-application-security-verification-standard/)定义了在三个不同严格等级下"通过"测试是什么样。
* *把自动化渗透测试加入持续交付流水线。* 攻击者会对你的生产系统跑的扫描，你也可以对预发环境跑一遍。
* *保护构建流水线。* 能在提交与部署之间注入代码的攻击者，根本不需要找漏洞。[SLSA](https://slsa.dev/) 安全框架提供了一条分级路径：较低等级确立"哪个提交产出了哪个产物"，较高等级则让构建本身可验证。
* *采纳 [Secure by Design](https://www.cisa.gov/securebydesign) 实践。* CISA 的承诺项（默认启用多因素认证、无默认密码、透明披露漏洞）是一个合理的最低标准。
* *新代码优先选择内存安全语言。* 相当大比例的严重漏洞是不会在 Rust、Go 或托管运行时中出现的内存安全问题。CISA、NSA 和 [NCSC](https://www.ncsc.gov.uk/) 已[发布实用的路线图](https://www.cisa.gov/resources-tools/resources/case-memory-safe-roadmaps)。现有 C/C++ 代码不必重写，但新的 C/C++ 代码应当需要理由。AI 辅助的重写也越来越可行。

**实操提示：** 以 CI action 形式运行、带 OWASP Top 10 和语言特定规则集的静态应用安全测试（SAST）工具已广泛可得，既有开源的，也有内置于代码托管平台的（GitHub 上的 CodeQL 是最常见的起点）。要评估构建来源，OpenSSF 发布了一个[可复用工作流](https://github.com/slsa-framework/slsa-github-generator)，可从 GitHub Actions 产出 SLSA Level 3 认证声明；采用它比 SLSA 规范暗示的工作量小得多。

一如既往，用 AI 加速这些工作也有一些明确机会：

* *AI 漏洞扫描。* 逻辑很直接：你应当在攻击者之前，用他们会用的同类模型扫描自己的代码和系统。这个做法只需要一个隔离的智能体、一个用于过滤噪音的验证步骤，以及一条接入现有分诊流程的路径。今天你就可以用 LLM 做到。***如果你要从这一节只落地一件事，就落地这件。***
* *补丁生成。* 当 SAST 或扫描器产生一个发现时，前沿模型通常能为其提出补丁。这并不消除评审的必要，但它把开发者的工作从"理解 bug 并写出修复"变成"验证提议的修复是否正确"。后者更快。同样的方法适用于内存安全迁移：LLM 可以把一个自包含的 C 模块连同测试移植到 Rust；评审者只需验证等价性，而不必从头写一遍。

### **4. 找出代码中已经存在的漏洞**

打补丁解决的是你所依赖软件中的已知漏洞。但你自己的代码库里还有未知漏洞。大多数长期运行的生产代码被人反复审查过许多次，却从未被前沿模型检查过，而这类分析[往往会揭示新的、此前被忽视的问题](https://www.youtube.com/watch?v=_IDbFLu9Ug8)。主动扫描可以在攻击者自己发现之前，找出落在现代 LLM 能力范围内的漏洞。

* *按暴露程度排优先级。* 从解析不可信输入、执行认证或授权判定、或可从互联网触达的代码开始。这些路径上的发现最有可能真正要紧。
* *把遗留代码纳入进来。* 早于当前审查实践的代码，或原作者已经离开的代码，往往受审查最少。这里你能从一次新的通读中获益最多。
* *为修复预留预算。* 对较老代码做一次结构良好的模型扫描，产生的发现通常少于 SAST 全面铺开，但其中"真问题"的比例更高。要规划好修复这些 bug 的工程时间。

**实操提示：** 挑一个当前负责人很少的、面向互联网的服务，扫描它的输入处理和认证逻辑。在隔离环境中运行智能体，并加上验证步骤，确保你依据的是已确认的发现。把一个服务做实，是估算更大范围计划成本的合理依据。

### **5. 为"已被入侵"而设计**

攻击者总会试图在某处取得立足点。你需要限制他们从那里能触达什么。

那些价值来自"摩擦"——让攻击变得*繁琐*——而非硬性屏障的缓解措施（额外的跳板路径、速率限制、非标准端口、基于短信的 MFA），在面对能够耐着性子磨穿这些繁琐步骤的对手时，效果要差得多。下面我们的建议偏向那些即便攻击者有无限耐心也依然成立的控制：绑定硬件的凭证、会过期的令牌，以及"根本不存在的网络路径"，而不是"只是不方便的路径"。

* *采用零信任架构。* 把服务之间的每一次请求都当作来自互联网来认证和授权。CISA 的[零信任成熟度模型](https://www.cisa.gov/zero-trust-maturity-model)与 NCSC 的[零信任原则](https://www.ncsc.gov.uk/collection/zero-trust-architecture)都提供了分阶段采用路径。
* *把访问绑定到经过验证的硬件，而不是凭证。* 生产系统与敏感内部工具应只能从具备硬件身份认证的受管员工设备访问，并配合抗钓鱼双因素认证（FIDO2 或 passkey）。仅凭窃取的凭证绝不应足以获得访问权。即便是生产服务之间的调用，也应以硬件身份为根。
* *按身份隔离服务。* 一台被攻破的构建服务器不应能查询生产数据库。一台被攻破的笔记本电脑不应能触达构建基础设施。要在接收端强制执行这一点：每个工作负载都应携带自己的密码学身份，每个服务只接受其策略名单中特定调用方的连接。网络分段仍能减少影响范围和噪音，但它是兜底手段。
* *用短期令牌替代长期密钥。* 静态 API key、硬编码凭证、共享服务账户密码，是拥有模型辅助代码分析能力的攻击者最先会找到的东西之一。改用由身份提供商签发的短时效、窄作用域令牌。

**实操提示：** 完整的零信任是多年期计划，但一个具备身份感知的访问代理，就能在不根本改变内部服务架构的前提下，把"设备验证 + MFA 把关"的访问放到它们前面。每家主要云厂商都提供原生选项，本地部署或多云环境也有若干开源与商业替代品。至于密钥，每家主要云都有托管密钥库；把最广泛共享的那一个凭证迁进去并轮换，是对其余部分很好的推动力。

### **6. 减少并清点你暴露的东西**

本节基于两条重要原则。第一，你无法防御你不知道存在的系统。第二，暴露面越小，可供攻击的东西越少。

* *维护一份最新的清单*，覆盖你系统中每一个面向互联网的主机、服务和 API 端点。攻击者可以跑自动化侦察；你的清单至少应当同样准确。要把这些系统纳入渗透测试与红队演练。
* *下线不用的系统。* 没有明确负责人的遗留服务，通常也没打补丁。
* *尽量减少每个服务暴露的内容。* 入站网络默认拒绝，把 API 面收敛到真正必需的部分。

***实操提示：*** 全网扫描索引是公开可查询的；拿你自己的 IP 段和域名去查一下，你就能看到攻击者侦察时会看到什么。云资产方面，原生清单工具（AWS Config、Azure Resource Graph、GCP Asset Inventory）已经存在，工作在于去查询它们。

AI 在这里也能直接帮忙：

* *清理陈旧代码与系统。* 识别未使用代码很繁琐——但正如上面所说，AI 模型擅长繁琐任务。一个能读取代码库和流量日志的模型，可以列出没有调用方、也没有收到流量的端点；在此基础上，它还能解释移除每一个会影响什么。
* *自主外部红队。* 从外部把一个 AI 攻击智能体指向你自己的边界，不给凭证、不给源码访问权。然后让它做攻击者会做的事：搞清楚什么可触达、做指纹识别，并尝试把找到的东西串成立足点。这种自动化红队能捕捉源码扫描看不到的东西：被遗忘的主机、暴露的管理界面、默认凭证、配置错误的存储。按与你刷新清单相同的节奏运行它。

### **7. 缩短事件响应时间**

利用程序可能在补丁发布后数小时内出现。以"天"为单位的响应流程太慢了。以下是一些缩短事件响应时间的思路：

* *把模型放在告警队列的最前端。* 每条进来的告警都应在人看到之前先经过一轮自动化初查。这种"分诊智能体"对安全信息与事件管理（SIEM）平台有只读访问权，并配有一组作用域明确的查询工具，可以把你的注意力引向最需要人类判断的告警。
* *把驻留时间与覆盖率的度量放在首位。* 这两个指标是 AI 自动化最有能力推动的；而当利用窗口缩短时，它们也最重要。
* *把事件相关的簿记工作自动化。* 在活跃事件期间，模型应当做记录、采集证据、并行推进多条调查线，并起草复盘与根因分析。另一方面，*人*应当做遏制决策、披露决策和客户沟通决策。事件期间人的决策速度，绝不应被那些更适合交给 AI 的环节拖慢，比如证据收集或撰写材料。
* *让模型驱动检测飞轮。* 摄入[威胁情报](https://platform.claude.com/cookbook/tool-use-threat-intel-enrichment-agent)、生成候选检测规则、狩猎匹配项、调校触发条件，这些现在都在前沿模型的能力范围内，它们可以端到端地跑完整个流程。
* *做一次"五起事件同时发生"的桌面演练。* 标准演练假设周一发生一个带可用利用程序的关键 CVE。鉴于我们看到的 AI 能力提升，这可能不够明智。要真正压测你的响应，你应当跑"五起事件在同一周爆发"的版本。
* *对照 [MITRE ATT&CK](https://attack.mitre.org/) 映射检测覆盖。* ATT&CK 提供了攻击者技术的标准词汇表，大多数检测工具已经在用。知道你能检测哪些技术（以及不能检测哪些），比"提升检测能力"这种笼统目标更有用。应优先覆盖横向移动与凭据访问。
* *提前建立紧急变更程序。* 对生产补丁走两周的变更审批周期，本身就是一种安全风险。紧急遏制操作（如让服务下线、轮换凭证、封堵网络路径）同理。应事先决定谁能授权这些操作，以及能有多快。

**实操提示：** 挑一条噪音大、已知误报率高的规则。把一个前沿模型接入其告警流，给它对底层数据的只读访问权，让它对每次触发产出结构化处置结论。连续两周测量它与人工评审的一致率。如果一致率可接受，就扩展到下一条规则。不值得一次性把整个队列都自动化。另外，[Atomic Red Team](https://atomicredteam.io/) 是一个开源库，收录了映射到 ATT&CK 技术的小型安全测试；跑上几个，检查现有日志实际检测到了哪些，是一个下午就能完成的练习，能产出一张具体的覆盖图。

以下是 AI 在响应时间方面可以提供帮助的一些方式：

* *100% 覆盖的初查分诊。* 一个作用域明确的分诊智能体可以调查每一条告警（而人可能只看高于某个严重度阈值的那部分），并产出结构化处置结论，供人接受、否决或升级。让它奏效的机制是：给模型一组最小工具（查询、思考、报告），让它自己选择调查策略，并用运营指标衡量输出。
* *事件记录员与并行调查员。* 在活跃事件期间，模型可以实时记录、在证据被采集时打上时间戳、推进响应者尚未顾及的独立调查线，并在事件结束后依据记录起草复盘。这是前沿模型在安全工作上最不起眼的应用——但很可能是影响最大的一个。
* *针对自身环境的主动狩猎。* 能在源代码中发现漏洞的同类智能体，也能在你的遥测中狩猎配置错误与入侵指标。你可以按与外部攻击面扫描相同的节奏运行它。

## **向他人提交漏洞报告的建议**

如果你在扫描代码——自己的依赖、开源项目或供应商产品——并向上游报告发现，这些报告的质量决定了是否有人会采取行动。开源维护者已经在收到大量低质量的自动化报告，许多人开始忽略一切看起来像 AI 生成的东西。在没有增加信号的情况下增加这种体量，会让每个人（包括你）的问题变得更糟。

只有在人已经验证过、并且愿意署名时，才应发出报告。具体来说：

* *用平实语言说明 bug 及其影响。* 维护者应当能在第一段就理解哪里有问题、为什么重要，而不必运行任何东西。
* *走一遍代码路径。* 展示输入从哪里进入、在哪里被错误处理、后果在哪里发生。这正是"真实发现"与"模式匹配"的区别所在。
* *提供可运行的复现。* 维护者能跑的概念验证，或一个会失败的测试用例，比任何解释都更有说服力。
* *附上"如果你就是维护者也会接受"的补丁建议。* 补丁证明报告者足够理解这个代码库，能以符合项目惯例的方式修复问题。
* *一开始就披露 AI 的参与。* 如果 bug 是模型发现的、或报告由模型起草，在第一行就说明。维护者反正会知道；隐瞒比披露损失更多信誉。
* *尊重维护者的判断。* 如果他们拒绝报告，你应当接受。易于合作带来的善意，比在某个 bug 上赢下一场争论更有价值。

**实操提示：** 发送漏洞报告前有个有用的自检：关掉编辑器，凭记忆解释这个 bug。如果你不能在不回看模型输出的情况下说清楚哪里出了问题，那你就理解得不够好，还不够格去报告它。

## **如果你没有安全团队**

上面大多数建议都假设你的组织有专职安全职能。如果你是小组织、独立开发者或开源维护者，风险相同，但行动更简单：

* *打开自动更新*——操作系统、浏览器以及每个提供该功能的应用程序。这是最有效的单一行动，且不需要持续投入。
* *优先使用托管服务，而非自托管。* 让有安全团队的提供商来运行数据库、认证和邮件，就把打补丁的负担转移给了他们。这类托管服务的成本几乎总是低于一次事件的成本。
* *在所有支持的账户上使用 passkey 或硬件安全密钥。* 短信验证码可以被拦截，密码会被重复使用；硬件密钥无法被钓鱼。
* *启用代码托管平台上的免费安全工具。* GitHub 的 Dependabot、密钥扫描和 CodeQL 对公开仓库免费，能捕捉到企业级工具所捕捉的相当一部分问题。启用它们只需几分钟。

*如果你维护一个开源项目，请发布一份 `SECURITY.md`*，写明该联系谁、联系后可以期待什么。AI 辅助的扫描意味着你会收到比以前更多的漏洞报告。有些有价值，有些是自动化噪音。清晰的受理流程能帮你区分二者，也向善意报告者表明他们的努力不会被浪费。
