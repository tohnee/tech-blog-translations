# 智能体编码正在压垮 CI：我们如何在 Anthropic 扩展测试影响分析

> 原文：[Agentic coding is straining CI. Here's how we scaled test impact analysis at Anthropic](https://claude.com/resources/articles/agentic-coding-is-straining-ci-heres-how-we-scaled-test-impact-analysis-at-anthropic) · Claude 博客

我们的 CI 任务量在 6 个月内增长了 25 倍。在找到可持续的解决方案之前，我们对测试选择服务打了三次补丁。

## AI 正在重塑 CI

Anthropic 工程师现在平均每季度交付的代码量，是他们在 2021—2025 年间的 [8 倍](https://www.anthropic.com/institute/recursive-self-improvement)。这些代码中有 [80% 由 Claude 编写](https://www.anthropic.com/institute/recursive-self-improvement)，Claude 在[审查和批准 PR](https://claude.com/resources/articles/how-anthropic-secures-its-ai-native-software-development-lifecycle) 方面同样扮演着重要角色。

![](https://assets.claude.com/d9ed8b937d3a3a58b07f5158bc49614e6f260936.png)

写代码不再是约束条件；而一旦 PR 审查被加速，CI 就开始感受到压力。

更何况，我们代码库中的测试总量增长了 10 倍，工程师人数却只增加了象征性的一点。这一切使 CI 任务量在六个月内增长了 25 倍（如果你正试图把账算平：并非每个测试都会在每个 PR 上运行，后文我会解释）。

这曾多次让我们的测试影响分析服务面临过载风险。为了避免它成为下一个瓶颈，我们索性把整个东西推倒重来，重新构想了这个服务的架构。但走到那一步的路很颠簸：起点是三次快速修补，它们分别只撑了 70 天、29 天，然后是不到一天。

随着智能体持续加速代码生成与审查，扩展 CI 是越来越多工程团队很快就会面对的挑战。关于合并（merge）的姊妹篇，请见 [Redesigning source control at Anthropic](https://www.anthropic.com/engineering/redesigning-source-control)。我预计，随着运行智能体的团队同时产出更多 PR 和更多测试，水平扩展的测试选择架构将成为行业标准。

![](https://assets.claude.com/16c9a571f85e5fb9e323c5b751b325ff664973d3.png)

本文将讨论我们如何在 Anthropic 扩展测试影响分析服务，以及我以惨痛代价换来的教训：永远按指数增长来做规划。那些具体的扩展手段——买更大的机器、并行化进程，或者重启服务（没错，这一招至今仍然出奇地管用）——都很常见，**但它们并不是本文要提供的洞见**。

关键在于：这些手段如今争取到的时间，只有一年前的几分之一。另一方面，彻底改造并完整重新设计一个服务所需的时间同样只有过去的一小部分，而且在写代码不再是瓶颈的今天，这种方式可持续得多。

你越是能预判这种压力、越早规划架构将如何随之演进，浪费在权宜之计上的时间就越少。

## 测试影响分析的架构

我的许多同行所在的组织里，每个测试**仍然**会在每次变更时全量运行。这在某一点之前还行得通，但无法扩展：CI 门禁会变得越来越耗时、昂贵且不可信。

此外，人类很擅长判断哪些测试失败与自己无关，而智能体则需要更多上下文与指引。当它们拿到一组具体且有效的测试时，就能更有效地自我验证和迭代。

在 Anthropic，我们构建了一个确定性的测试影响分析（test impact analysis，也就是测试选择，test selection）服务：它基于历史表现和包相关性，决定每次变更要运行哪些测试。这种做法并不罕见，市场上已有一类厂商提供相关产品。

我们的服务依赖两个保持同步的确定性组件：

* **“监听器”（listener）** 记录每一次 CI 运行的测试结果。
* **“选择器”（selector）** 读取测试结果历史，决定哪些已开启的 PR 上要运行哪些测试。

这套机制有效，但当每秒都有多个 CI 任务在运行时，监听器就会越来越落后于 PR 队列。对于 [AI 原生的 SDLC](https://claude.com/resources/articles/the-ai-native-sdlc-playbook) 来说，一点小小的滞后也可能造成巨大影响。举例来说，监听器滞后 20 分钟，就可能意味着数万条测试更新没能应用到选择器上。

* **如果一次糟糕的变更被合并**，某个测试就会开始对其他人持续失败，引发多次不必要的排查。
* **如果某个依赖开始偶发失败（flaking）**，偶发的红色状态就会开始阻塞合并。
* **如果某个测试被修复，或有新测试被添加**，在监听器追上来之前它都不会运行，从而带来回归风险。

这一切原本都跑在单个进程中，因为要维护每个测试的持续历史，就必须由一个单一写入者来应用结果。这个 v0 设计使我们无法做水平分片。

## 通往重设计的颠簸之路

到去年 10 月，这个服务已经显出不堪重负的迹象，我们连续两天被呼叫（paged）。

### 补丁 1：更大的机器

第一个修复很简单：我们把运行该服务的核数翻了一倍。我们也清楚，这只是权宜之计。

![](https://assets.claude.com/2d86c48166db5529d133483caefba4a58b144850.png)

对话为重新还原，基于真实事件。

即便趋势线已经一目了然，责任归属却依然模糊。没人愿意再接手一块基础设施。而且，CI 团队还有更重要的事要忙。

### 补丁 2：分片

到这时，我们已经因为该服务监听器中不断累积的滞后而频繁被呼叫。为了推动一些长期修复，我在内部版 Claude Tag 中开启了一个长期会话，专门监控这个服务。一旦监听器滞后超过 50,000 个任务，Claude 就会 ping 我，并接着我们关于下一步的对话往下聊。

这样持续了几个月，好处是我不用反复提醒它过去的努力或上下文。Claude 经常主张做一次彻底改造，但我们通常还是选择再打一个补丁。

![](https://assets.claude.com/efc323a9636207ad3921fe8073d999d25151f207.png)

与内部版 Claude Tag 的逐字对话，部分内容已做删节。

到了 2 月，CI 任务的指数增长再次让服务吃紧。这一次，我们决定并行化。

监听器并不需要一个单一写入者来正确排序全部测试结果，它需要的是**每个包**一个单一写入者，来正确排序代码库各部分对应的测试结果。Claude 为我们生成了代码，把每个包的状态拆分成一个分片，各自拥有独立的 worker。

我们也知道这个修复只是权宜之计，但没想到它只为我们争取了 29 天。

### 补丁 3：每日重启

![](https://assets.claude.com/c7477bb6a3bbf0c94e307a6792b5fb8ea3e19aa9.png)

到了 3 月，该进程在大多数工作日的下午三点左右就会触及内存上限。我们再次寻找快速修复，但是：

* 我们只找到了四个 bug。
* 作为权宜之计替换内存分配器毫无效果。我们试图优化垃圾回收，但那并不是真正的解法。
* 我们不想冒险对一个已经在高负载下运行的单实例做内存剖析（memory profiling）。
* 重启也只争取到不到一天。

我们还发现，每日重启导致服务逐渐越落越远。当它滞后超过一小时（这发生过好几次）时，大量任务结果没有被监听器记录下来。

需要说明的是，这并不意味着那些 PR 上的 CI 从未运行过，也不意味着未经测试的代码被推上了生产环境。它的含义是：监听器没有采集到部分结果，导致我们的测试选择组件在使用过期数据来决定 PR 上该运行、不该运行哪些测试。多数情况下，这表现为我们运行了一些本来就极度不稳定、或在整个代码库范围内广泛失败的测试。

### 重新设计

（早就）该重新设计这个服务了。我们采纳了 Claude 的建议：给测试选择服务配一个数据库——准确地说，是一个内存数据存储。这样一来，我们有效地把单实例原先承担的一大块内存内处理工作卸载了出去。

现在，任意一个监听器 worker 都可以处理任意一条结果，把它追加到内存存储中的一份 journal（追加式日志）里，然后继续处理下一条，而无需在内存中保留任何东西——无状态，因而可以水平扩展。一个独立的小型消费进程每隔几秒把 journal 汇总成按测试划分的历史记录，选择器则可以快速查询相关的历史结果。

![](https://assets.claude.com/a3e6f1f6d7c313312c62c7df417de297ae7a3079.png)

这种分布式架构的运行成本更高，但相比摇摇欲坠的单实例，它要容易扩展和做内存剖析得多。这个项目由一位工程师花了三周完成。一年前，这大概需要一个季度。

![](https://assets.claude.com/5e6a25ec5ab4c71131f6395fc8d1eecdb37b00f5.png)

排队中、未处理的任务结果事件，按小时取最大值。改造前：大多数日子都会积压，且逐周增长。切换并调优后：持平。

随后还做了一些精细调优（确定 journal 的容量和 worker 数量），这些主要由 Claude 自主完成。此后我们的服务一直保持稳定。

## 我会如何做得不同

如果把我送回 2025 年 10 月，以我现在的认知，我会以不同的方式处理这个项目和其他项目。

第一个不同之处是，我会把 AI 的指数增长考虑在内。随着每位工程师平均拥有的智能体数量上升、加速后的 PR 审批变得更加成熟，CI 任务量会呈指数增长。

随着时间推移，这也改变了 Anthropic 内部 PR 的形态，因为 Claude 偏好更小、粒度更细的 PR（这是不要对每个 PR 运行全部测试的又一个好理由）。这转化为每天更多的 CI 任务。同时，活动量的下限被抬高了：智能体会在夜间和周末提交代码；但由于人类工程师仍然驱动并批准着相当大比例的 PR，整体负载依然呈突发式。

我对工程团队的建议是：无论自研还是采购，都假设你的架构在两个季度内会承受 25 倍的负载。过度设计这个概念正在逐渐淡去，或者说，门槛已经被抬得高得多。只要预算允许，你现在就可以在 v0 设计中按预期规模的 10—20 倍来做规划。

为你的服务加上可观测性，让它们成为 Claude 的眼睛和耳朵。这能让 Claude 以远超我们手动方式的效果和速度，做爬坡式（hill-climb）的增量修复。尤其要确保：流入的 CI 任务数量与流出的数量相等。

从一开始就把状态从进程中剥离出去。我还会避免把任何关键服务作为单实例运行，除非你能对它做度量，并能通过金丝雀变更来验证。CI 演进得太快，别无他法。
