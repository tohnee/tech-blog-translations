# Claude Code 使用心得：HTML 不可思议的有效性

> 原文：[Using Claude Code: The unreasonable effectiveness of HTML](https://claude.com/blog/using-claude-code-the-unreasonable-effectiveness-of-html/) · Claude 博客

Markdown 已经成为智能体与人类交流时使用的主导文件格式。它简单、可移植、具备一定的富文本能力，而且易于编辑。Claude 甚至出人意料地擅长在 Markdown 文件里用 ASCII 绘制图表。

但随着智能体变得越来越强大，我发现 Markdown 已经成为一种愈发受限的格式。具体来说，超过一百行的 Markdown 文件我读起来很吃力；我希望用 Claude 生成更丰富的可视化、色彩和图表；我也希望能更轻松地分享这些输出。

此外，我越来越不是亲自编辑这些文件，而是把它们当作规格说明和参考文件来用。当我确实需要修改时，通常是让 Claude 来改，这也就抵消了 Markdown 最大的一项优势。

相反，我开始更倾向于用 HTML 而不是 Markdown 作为输出格式，并且越来越多地看到 Claude Code 团队的其他成员也在采用这一模式。在这篇文章中，我将分享我们的团队为什么以及如何使用 HTML 来产出更丰富、更易读的 Claude Code 输出。如果你想跟着做，也可以在常见用例中开始使用这些 [HTML 文件模板](https://thariqs.github.io/html-effectiveness/#code-review)。

# 为什么用 HTML？

有几点让 HTML 比 Markdown 更适合我现在用 Claude Code 做的那类工作，包括那些需要或涉及以下内容的任务：

## 信息密度

与 Markdown 相比，HTML 能传达丰富得多的信息。它当然可以处理标题和格式化这类简单的文档结构，但还能表示各种其他信息，例如：

- 用表格表示表格数据
- 用 CSS 表示设计数据
- 用 SVG 绘制插图
- 用 script 标签承载代码片段
- 用 HTML 元素配合 javascript + CSS 实现交互
- 用 SVG 和 HTML 表达工作流
- 用绝对定位和画布表示空间数据
- 用 image 标签嵌入图像

在我看来，几乎没有哪种 Claude 能读到的信息是你无法用 HTML 高效呈现的。这使得它成为一种极其高效的方式，既便于模型向你传达深入的信息，也便于你审阅这些信息。

我发现，在无法做到这一点时，模型可能会在 Markdown 里做一些效率更低的事情，比如 ASCII 图表，或者——我最喜欢的一个——用 unicode 字符来模拟颜色。

## 视觉清晰，易于阅读

随着 Claude 有能力处理更复杂的工作，它也能写出越来越大的规格说明和计划。我发现超过 100 行的 Markdown 文件我往往不会真的去读，当然也没办法让我组织里的其他人去读。

但 HTML 文档读起来容易得多，因为 Claude 可以在视觉上组织结构，配合标签页、插图和链接，实现理想的导航体验。它甚至可以做到移动端自适应，让你根据设备形态以不同方式阅读。

## 易于分享

Markdown 文件相当难分享，因为大多数浏览器并不能原生地良好渲染它们。你往往得把它们作为附件加进电子邮件或消息里。

只要上传 HTML 文件，你就可以轻松分享链接。同事可以在任何他们喜欢的地方打开它，并方便地加以引用。

如果你的规格说明、报告或 PR 说明是 HTML 格式，别人真正去读的概率会高得多。

## 双向交互

HTML 还能让你[与文档交互](https://x.com/trq212/status/2017024445244924382)；例如，你可以让它加上滑块或旋钮来调整设计，或者让你调整算法中的不同选项看看会发生什么。你还可以让它提供一个复制功能，把这些改动复制成提示，再粘贴回 Claude Code。

在有用时，这可以让你为手头的具体问题创建专门的编辑环境。

## 数据摄取

用 Claude Code 而不是 claude.ai 或 Claude Design 来生成 HTML 文件，最大的理由之一就是 Claude Code 能摄取的上下文之丰富。例如，在撰写这篇文章时，我让 Claude Code 通读我的代码文件夹，找出我生成过的所有 HTML 文件，对它们分组归类，然后生成一个 HTML 文件，用图表呈现每一种类型。你在本文中看到的图表正是这样直接产出的。

除了文件系统之外，Claude Code 还能借助你的 MCP 连接（如 Slack、Linear 等）、你的网页浏览器（通过 Claude in Chrome）以及你的 git 历史来获取更多上下文。

# 上手指南

值得注意的一点是：要让 Claude 生成这样的 HTML，你不需要做太多。你只需提示它"*做一个 HTML 文件*"或"*做一个 HTML artifact*"即可。关键在于想清楚你希望这个 artifact 做什么，以及你会怎么用它。随着时间推移，针对反复出现的模式构建一个技能（skill）可能是值得的，但从零开始用提示摸索，是感受它在不同用例中如何运作的好办法。

## 用例

为了让这一方法更具体，下面是一些[示例用例](https://thariqs.github.io/html-effectiveness/)，在我看来这些场景用 HTML 文件比用 Markdown 更合理。你也可以通过这个 [GitHub 示例库](https://github.com/anthropics/html-effectiveness)跟随操作。

### 规格、计划与探索

HTML 是 Claude 深入钻研一个问题时的丰富画布。当我着手处理一个问题时，我期待的不是一个简单的 Markdown 计划，而是一张由 HTML 文件构成的网。例如，我可以先让 Claude Code 头脑风暴，为不同选项创建一些探索方案；然后让它就其中一个进一步展开，也许做些 mockup 或这类界面的示例；最后，当我感觉不错时，我会让它撰写一份实现计划。等我对计划满意了，我会新开一个会话，把这些文件全部传入，让它去实现。

验证时，我也会让验证智能体读取这些文件，它对所需内容的理解会宽泛得多。

**示例提示：**

- *我不确定新手引导界面该往哪个方向走。生成 6 种明显不同的方案——在布局、风格和密度上做变化——并把它们排进一个网格布局的单个 HTML 文件里，方便我并排比较。为每个方案标注它所做的取舍。*
- *在一个 HTML 文件里创建一份详尽的实现计划，务必做一些 mockup，展示数据流，并附上我可能需要审阅的重要代码片段。要做到易于阅读和理解。*

**适用于：**

- 探索用代码实现某个功能的其他方式
- 一次性试验多种视觉设计

### 代码评审与理解

代码在 Markdown 文件里可能很难读，但借助 HTML，我们可以渲染 diff、注释、流程图和模块。用 HTML 来理解智能体写出的代码、评审代码，或者向正在评审你代码的人解释一个 PR。

**示例提示：**

*帮我评审这个 PR，做法是创建一个描述它的 HTML artifact。我对流式处理/背压（backpressure）逻辑不太熟悉，所以请重点讲解这部分。渲染实际的 diff，在旁边加上内联注释，按严重程度给发现的问题标色，再加上其他有助于讲清概念的任何内容。*

- 创建 PR
- 评审 PR
- 理解代码中的某个主题

### 设计与原型

Claude Design 以 HTML 为基础，因为 HTML 在设计上的表现力极强，即便你的最终界面并不是 HTML。Claude 可以先用 HTML 勾勒出一个设计，再用你选择的语言把它写出来，无论是 React、Swift 还是别的。

你还可以为交互制作原型，比如动画、动作等。不妨让 Claude 做些滑块、旋钮之类的东西，精确调出你想要的效果。

我想为一个新的结账按钮制作原型：点击时先播放一段动画，然后迅速变成紫色。创建一个 HTML 文件，带上若干滑块和选项，让我可以尝试这个动画的不同参数组合，并给我一个复制按钮，用来复制效果好的参数。

- 创建设计系统制品
- 调整组件
- 可视化组件库
- 制作动画原型

### 报告、研究与学习

Claude Code 非常擅长综合多个数据源的信息，并将其转化为便于阅读的报告。你可以让 Claude 搜索你的 Slack、你的代码库、git 历史或互联网，用它来生成易于阅读的报告。

你可以把它组织成一篇长 HTML 文档、一个交互式讲解页，甚至一套幻灯片。可以让 Claude 用 SVG 绘制图表来辅助可视化。

*我不明白我们的速率限制器（rate limiter）到底是怎么工作的。阅读相关代码，生成一个单独的 HTML 讲解页：一张令牌桶（token-bucket）流程图、3 到 4 段带注释的关键代码片段，以及页面底部的一个"注意事项"版块。请为只读一遍的读者优化排版。*

- 撰写功能摘要
- 生成讲解材料
- 起草每周状态报告
- 撰写事故报告
- 制作 SVG 插图、流程图和技术图表

### 定制编辑界面

有时，你很难纯靠一个文本框描述清楚自己想要什么。对于这种用例，我常会让 Claude 为我手头正在处理的东西构建一个用完即弃的编辑器：不是产品，也不是可复用的工具，而是一个单独的 HTML 文件，专为这一份数据而造。

诀窍始终是：以一个导出功能收尾——一个"复制为 JSON"或"复制为提示"按钮，把我在界面里做的一切转换回可以粘贴进 Claude Code 或提交到文件的东西。你仍然留在环路里，只是这个环路变得更紧凑了。

- *我需要重新排列这 30 个 Linear 工单的优先级。给我做一个 HTML 文件，每个工单是一张可拖拽的卡片，分布在 Now / Next / Later / Cut 四栏之间。先按你的最佳判断预排序。加一个"复制为 Markdown"按钮，导出最终排序，并为每个栏位附上一行理由。*
- *这是我们的功能开关（feature flag）配置。为它做一个基于表单的编辑器，按区域给开关分组，展示它们之间的依赖关系，如果我要启用的开关其前置条件未开启就警告我。加一个"复制 diff"按钮，只给我发生变化的键。*
- *我在调这个系统提示。做一个并排编辑器：左边是可编辑的提示，变量槽位高亮显示；右边是三个示例输入，实时重新渲染填充后的模板。加一个字符/token 计数器和一个复制按钮。*

- 对任何东西（工单、测试用例、反馈）进行重排、分诊或归类
- 编辑结构化配置（功能开关、环境变量、带约束的 JSON/YAML）
- 带实时预览地调优提示、模板或文案
- 策展数据集——批准/拒绝行、给示例打标签、导出选定内容
- 为文档、转录文本或 diff 加注释并导出这些注释
- 挑选那些用文字表达起来很费劲的东西：颜色、缓动曲线、裁剪区域、cron 计划、正则表达式

### 常见问题

这些是我在"在 Claude Code 中使用 HTML"这个话题上被问得最多的问题，配上我自己沉淀下来的实用日常习惯：

**这样不是效率更低吗？**

虽然 Markdown 通常消耗的 token 更少，但我发现 HTML 额外的表现力，加上我会真正去读它的可能性大大提高，意味着我总体上能得到更好的输出。有了 Opus 4.7 的 100 万（1MM）上下文窗口，token 用量的增加在上下文窗口里并不明显。

**那你现在什么时候还用 Markdown？**

说实话，几乎在所有事情上我都已经完全不用 Markdown 了，不过我在"HTML 最大化主义者"这条路上可能走得相当远。

**这就是你替代规划的方式吗？**

我发现，我不会只有一个计划，而是倾向于为计划的不同部分/阶段准备几个不同的 HTML 文件。例如，我可能先用 HTML 做一份实现计划，再另做一个文件用于 UI 探索，最后再做一个 HTML 组件列出所有设计。我往往把这些文件留着，作为日后的参考，也用于验证环节。

## 与 Claude 保持同步

综上所述，我用 HTML 而不是 Markdown 的真正原因在于：它让我感觉自己与 Claude 的同步程度大大提高了。随着 Claude 承担越来越多的工作，我注意到自己对计划的阅读越来越不细致，我想要一种方式，让我持续参与它的选择，而不是直接把工作甩手交给它。HTML 恰好就是这样一种方式。我现在感觉自己比以往任何时候都更"在环上"。

立即开始使用 [Claude Code](https://claude.com/product/claude-code)。
