# 用大语言模型保护源代码安全

> 原文：[Using LLMs to secure source code](https://claude.com/blog/using-llms-to-secure-source-code/) · Claude 博客

模型能力正在快速但不均衡地进步。我们一直在[与安全团队合作](https://www.anthropic.com/glasswing)，在他们自己的代码和开源软件中查找并修复漏洞，这项工作让我们更好地理解了如何用模型来保护源代码安全。**我们的核心结论是：漏洞发现（discovery）现在已经可以轻松并行化，瓶颈已经转移到了验证、分诊和修补环节**。

为了说明这种落差：作为[我们对开源软件自行扫描](https://www.anthropic.com/research/glasswing-initial-update)的一部分，截至 2026 年 5 月 22 日，我们已披露 1,596 个漏洞。据我们所知，其中 97 个已被修复。

本指南将带你了解如何与 Claude Opus 协作，构建威胁模型、发现代码库中的漏洞，然后对它们进行验证、分诊和修补。虽然我们并未掌握全部答案，但我们会分享各团队如何扩展漏洞发现的规模，以及在后段环节中哪些做法行之有效。*今天就从[配套仓库](https://github.com/anthropics/defending-code-reference-harness)开始吧，其中包含用于交互式工作流的技能（skills）和一个用于自主扫描的演示 harness；阅读过程中我们会逐一指出实现每个步骤的技能。*

## **"查找-修复"循环**

找到并修复漏洞最多的团队，最终都收敛到现有最佳实践的某种变体上。我们把它提炼成六个步骤的序列：

1. **威胁模型：** 在开始扫描之前，先决定什么算作漏洞。
2. **沙箱：** 构建一个沙箱环境，用于隔离智能体并证明漏洞可被利用。
3. **发现（Discovery）：** 让模型在你的源代码中寻找漏洞。
4. **验证（Verification）：** 独立确认哪些发现真正可被利用。
5. **分诊（Triage）：** 对发现去重、评定严重程度，并排定修复优先级。
6. **修补（Patching）：** 应用修复，确认漏洞已失效，并搜索同类变体。

在威胁建模和沙箱搭建上的一次性投入，能为防御者的循环提供动力——这是一个由发现、验证、分诊和修补组成的反复循环——其中的瓶颈不是找到漏洞，而是找到之后的一切。

前两个步骤——构建威胁模型和沙箱——是其余循环的准备。它们通常每个代码库做一次，并在底层系统变化时重新审视。后四个步骤则是你要对源代码反复运行的循环：发现、验证、分诊、修补。

对一个代码库的首次运行通常发现的漏洞最多。后续运行发现的往往更少——但也通常更复杂——因为较简单的漏洞已在之前的运行中被修复。不过，不要指望第 *n* 次运行会没有任何新发现。模型是随机的，大型代码库可能有一条很长的漏洞长尾，即使代码没有变化，漏洞仍会不断冒出来。

在对一个代码库的第一次迭代中，你应该把循环运行多次，并根据净新增发现的数量和你对该系统的风险容忍度来决定何时停止。第一次迭代之后，继续扫描：(1) 定期扫描，或 (2) 每当代码发生实质性变化时扫描。

接下来，我们将逐一详解每个步骤，说明它为什么重要、产出是什么，以及如何实现。

## **1. 威胁模型：定义什么算作漏洞**

误报最常见的原因是模型对你的信任边界缺乏良好理解。模型可能把某段代码标记为有漏洞，因为它假设客户端可能发送损坏的值，或攻击者可能控制配置——尽管这些输入在你的环境中是*受信任的*。反过来，模型也可能假设一个面向互联网的服务仅限内部使用，从而漏报真实存在的漏洞。在这两种情况下，模型弄错的是威胁模型，而不是代码。

> *一个团队在他们的发现中注意到了一个规律：当系统拥有记录完善的威胁模型、系统设计文档、需求和约束时，模型的表现最好。当威胁模型定义清晰时，模型的发现"90% 的情况下都是可利用的"。*

你可以通过两个步骤与 Claude 一起构建威胁模型：

**第一步，从代码、文档和漏洞历史中自举（bootstrap）。** 把你第一天会交给新入职安全工程师的东西喂给模型：架构文档、wiki、入口点、git 历史和过往漏洞。这有助于克服仅凭代码推断隐性知识、权衡取舍和设计决策的难题。然后，让模型创建一个包含系统上下文、资产、入口点和信任边界的威胁模型。最后，让模型对过往 bug 进行聚类，并列出相关的漏洞类别。务必让威胁模型写明你在乎和不在乎哪些漏洞，以及为什么。

> *一个团队审查了数百个过往的 CVE 和安全修复提交，把它们提炼成"bug 形态"提示，然后问模型两个问题：修复是否完整？它是否在所有其他地方也被应用了？他们在一小时内发现了三个可利用的问题。用他们的话说：""人们过去利用过什么"有时是一条比"帮我找出这个代码库中的漏洞"容易得多的通关秘籍。"*

**第二步，让模型访谈一位熟悉系统的人。** 可以参考 [Shostack 的四个问题](https://github.com/adamshostack/4QuestionFrame)：*我们在构建什么？可能出什么问题？我们在为此做什么？我们做得好吗？*先运行自举步骤，这样受访者就不用从零开始。这样一来，他们不必花几个小时从零研究和构建威胁模型，而是可以从一份草稿出发。访谈这一步虽是可选的，但它补充了模型无法从代码或文档中获得的上下文，从而改进威胁模型。

一些实践能带来很大改观：

- **考虑你依赖项的安全策略。** 许多开源项目都会发布安全策略。例如 vLLM 的 [`security.md`](https://docs.vllm.ai/en/latest/usage/security.html)、SQLite 的 ["Defense Against the Dark Arts"](https://www.sqlite.org/security.html) 和 [ImageMagick 的安全策略](https://github.com/ImageMagick/ImageMagick/security/policy)。你的威胁模型应当直接参考它们，而不是从零重建一套策略。
- **写明什么是受信任的。** 如果你信任配置文件或已认证的客户端，请在威胁模型中写明。这些假设有助于把不可利用的 bug 与真实可利用的漏洞区分开。
- **随代码附带一份 `THREAT_MODEL.md`。** 把它放进仓库，并随代码变化更新它。这样发现智能体就可以在搜索之前先读它，跳过已知无需关注的问题。

你会在两个地方用到威胁模型。在发现阶段，它充当范围：对代码进行分区、排定目标优先级，并跳过超出范围的部分。这对你无法完整扫描的大型代码库很有帮助。在分诊阶段，它充当过滤器：在广泛扫描之后，利用威胁模型把严重程度更好地校准到你的系统和环境上。

> *一个扫描大型项目的团队遇到了 40% 的误报率，于是深挖原因。这些发现是可以复现的，PoC 也证明了可利用性。但负责这段代码的开发团队把它们当作误报驳回了，因为这些 bug 不符合项目的威胁模型。另一个团队的 CISO 说得简洁："[模型]对代码的上下文很了解，但对我们的上下文不甚了解。"*

**试试[threat-model 技能](https://github.com/anthropics/defending-code-reference-harness/tree/main/.claude/skills/threat-model)。** 它会带你走完本节描述的两个步骤——`bootstrap` 从你的代码、CVE 和 git 历史中推导出草稿，interview 则带着系统负责人过一遍 Shostack 的四个问题以完善它。输出是一个 `THREAT_MODEL.md` 文件，供发现和分诊步骤使用。

## **2. 沙箱：安全地运行智能体并验证可利用性**

**沙箱的目的之一是保护你的系统。** 要让模型安全、自主地运行，你需要一个强隔离层。没有它，智能体可能用力过猛，做出意料之外的事情。

> *一个团队告诉模型它没有网络访问权限——实际上有——结果模型发现它照样可以从 GitHub 拉取内容。另一个团队观察到某个智能体在扫描中途回复了一个 GitHub issue。这两个行为都不是恶意的，但都说明必须通过代码和配置来强制执行约束。*

让隔离级别与你的威胁模型相匹配。对于只读代码的发现智能体，容器就够了；但要在 microVM（如 Firecracker）或一台出口被锁死的完整虚拟机中运行目标及其 PoC，确保没有任何东西能触及你的生产系统。并且绝不要让智能体接触到凭据（`~/.aws`、`~/.ssh`、`.env`）。

只在搭建沙箱时给它网络访问权限。拉取依赖、构建、安装工具、部署目标，并运行现有测试以确认一切正常。然后对环境做快照，并移除其网络访问。扫描期间，只允许发往模型 API 的流量，并经由本地代理路由。每次运行开始时加载快照，让每一次扫描都从同样干净的起点出发。

**沙箱的另一目的是证明可利用性。** 在静态扫描时，模型阅读代码并推测哪里可能出问题，但它无法测试某条路径是否可达、是否存在补偿性控制。结果是，模型可能标记出你实际上并不在乎的、不可利用的代码正确性 bug。当各团队搭建了让智能体可以编译代码、运行测试并引爆概念验证（PoC）的沙箱后，不可利用的发现显著减少。

> *一个进攻性安全团队构建了一个为智能体提供试验台（test bed）的 harness，并定了一条简单的验证规则：只有当智能体能够构建概念验证并在试验台上运行它时，才算真阳性。六周后他们的评估是："最大的效力杠杆就是给模型提供试验台、真实的运行系统，并实际运行 PoC。"*

搭建沙箱时，尽可能把一切固定（pin）下来，让每次运行都在同一环境中使用同样的代码：镜像标签、commit SHA、依赖和构建命令。缓存一份本地副本，使构建不需要网络；并力求容器持久可用，让多个测试循环可以直接加载它。

> *一个团队的扫描标记出了一个漏洞，结果发现这是智能体下载了某个库的旧版本而非实际部署版本所导致的副产品。这个问题是一位工程师阅读会话记录（transcript）时注意到下载的依赖不对才被抓住的。他们现在构建 Docker 容器时把依赖固定为与生产环境一致，让发现智能体和验证智能体处理的是攻击者会面对的同一批制品（artifact）。*

构建足够忠实于生产的沙箱很重要。排除依赖（比如队列或数据存储）可能导致漏报生产环境中可能存在的 bug；反之，忽略生产防御（比如 WAF 或认证网关）则会让模型报告出你的生产环境早已缓解的、不可利用的发现。

尽管如此，如果由于云依赖、数据存储或其他现实复杂性，构建一个有代表性的沙箱并不现实，那就先从（下文介绍的）发现步骤开始。你不一定非要在沙箱里运行 PoC。前沿模型仅凭分析源代码就能很好地发现漏洞，包括我们自己在内的多个团队都发现这样行之有效。代价体现在验证阶段：没有运行中的目标，我们就无法用 PoC 证明发现，因此要为验证预留更多时间。你也可以稍后再投入建设沙箱，等发现量证明其必要性时再说。

**参考[harness 的 `README.md`](https://github.com/anthropics/defending-code-reference-harness/tree/main/harness)了解参考沙箱。** 在这一实现中，智能体和目标运行在 gVisor 隔离的容器里，出口流量被锁定为只能访问模型 API。目标由固定到特定 commit 的 Dockerfile 构建，由 [`setup_sandbox.sh`](https://github.com/anthropics/defending-code-reference-harness/blob/main/scripts/setup_sandbox.sh) 负责搭建阶段。

## **3. 发现：提供丰富的上下文、更短的提示和有用的工具**

让发现智能体能够按需加载上下文，比如威胁模型、架构文档和过往扫描的结果。当智能体理解你的信任边界以及系统实际的部署方式时，它就能更好地识别你的系统特有的漏洞。

我们发现，前沿模型在发现阶段受益于越来越简单的提示。有点反直觉的是，越是规定性的提示越会让发现效果变差——冗长的检查清单往往会削弱模型的创造力，产生更少的新颖漏洞。以下是一些在发现阶段有帮助的提示技巧：

- **提供目标与上下文。** 说明"为什么"和"是什么"——你为什么要扫描、有价值的发现长什么样、扫描的是什么系统——把"如何扫描漏洞"留给模型。前沿模型在安全任务上越来越出色，过度规定反而会收窄它们的尝试空间。
- **尝试指定某一类漏洞。** 如果你想依据过往 CVE 或代码库的语言聚焦某一特定类型的漏洞，就直说。描述这类漏洞的行为和常见藏身之处，让模型能在你的代码库中认出它。
- **定义输出格式。** 要求一份带预定义字段的结构化报告，并安排字段顺序，让模型的推理逐层递进。示例字段包括理由（rationale）、发现、影响、严重程度等。要留一个退出通道，让模型可以提前放弃较弱的发现。

给模型提供搜索和阅读代码库的工具，比如 grep、glob 等。也让模型可以使用你们团队可能会用的安全专用工具，比如 SAST 扫描器或模糊测试器（fuzzer）。问模型完成特定任务需要哪些工具，并把它们提供给它。最后，让模型按需构建工具：近期的前沿模型越来越擅长编写自己需要的工具。

> *除了源代码，一个渗透测试团队还给发现智能体提供了发送请求、检查响应和查询流量日志的工具。这样一来，智能体不必猜测某条路径是否可达，而是可以边走边对照运行中的应用逐个测试候选点，把真阳性率提高到接近 100%。*

让模型对系统做一次初扫，划分搜索空间，比如按攻击面、端点或组件划分。然后把这些分区喂给并行的发现智能体，避免它们都收敛到同样浅层的 bug 上。最后，跑一遍系统级扫描，把分区级别的发现作为上下文来搜索漏洞。

> *试图暴力推进发现的团队很快遇到了边际收益递减。一个团队说："我们最初试着单纯横向扩展、派出更多智能体，但收益递减。"另一个团队增加了重点领域和并行智能体的数量，得到了"海量问题"，其中大部分彼此重复。*

如果你有可以运行目标的沙箱，让发现智能体为每个发现构建一个 PoC，比如一段脚本、一个导致崩溃的输入或一个失败的测试。构建 PoC 有助于智能体迭代并钉牢这个发现，而这个制品也为验证智能体提供了可评估的具体证据。尽管如此，智能体无法复现的发现仍可以上报，标记为未证实，以保持较高的召回率。

[**`vuln-scan` 技能**](https://github.com/anthropics/defending-code-reference-harness/tree/main/.claude/skills/vuln-scan)在这一阶段很有用。它会读取你的 `THREAT_MODEL.md`，把目标划分成重点领域，并按领域分发并行评审智能体。输出是结构化的发现，供后续步骤直接使用。

## **4. 验证：过滤掉不可利用的发现**

发现为召回率优化；验证为精确率优化。换言之，发现应该尽可能找出所有漏洞——哪怕看起来不太可能的——而验证应该排除那些实际不可利用的发现。当智能体试图在同一步骤里*两者兼顾*时，它可能自我审查，把可利用的真阳性也排除掉。这是我们用教训换来的：让发现智能体同时验证发现，导致它们过滤掉了一些本可以由独立验证步骤确认的真阳性。

验证智能体应当独立于发现智能体。在一个全新的容器中运行验证者，不共享文件系统或对话历史。如果验证者接触到发现智能体的推理过程，它可能只是简单附和，而不是去检验该结论。因此，只给验证者两样东西：(1) 概念验证或书面发现，(2) 代码库，让它可以寻找发现者遗漏的缓解措施（比如上游校验、认证门禁、类型约束或不可达代码）。

如果单次验证仍然放行了太多不可利用的发现，可以尝试运行多个相互独立的验证者。它们可以从不同角度考量，或使用不同模型运行。然后取多数票。也可以考虑引入一个单独的裁判，在发现与验证智能体的结果之间做出裁决。

提示验证智能体去推翻发现智能体的结论。让验证者假设每个发现都是误报，并寻找该发现站不住脚的理由。同时给出明确的标准，供验证智能体判断某个发现是否为真阳性。在发现智能体的输出不含 PoC 时，这一点尤为重要。目标是尽可能多地排除不可利用的发现，以减少人工评审的工作量。

> *在我们合作过的各团队中，加入一个对抗性验证者，大致把发现阶段产出中不可利用发现的比例砍掉一半。再要求该验证者构建证实漏洞的概念验证，误报率就降到了接近零。这两个步骤加在一起，显著减轻了下游分诊和修补的负担。*

如果你能在沙箱中充分复现生产环境（见第 2 步），可以让验证智能体构建并执行一个可复现的概念验证（PoC）。如果 PoC 跑通了，你就可以断定该发现可被利用。注意反过来并不成立——未能做出可用的 PoC 并不能证明这是误报。

> *一个扫描开源软件包的团队构建了一个帮助闭环的验证步骤：扫描软件包、生成概念验证，然后部署一个使用该软件包并触发 PoC 的模拟应用。他们的体会是："验证是最大的卡点，而 PoC 就是验证本身。"*

## **5. 分诊：按根本原因去重，按前置条件和影响排序**

验证确认某个发现可被利用，分诊则评估修补的优先级。过去，当发现漏洞还很费人力时，找到 bug 的工程师也会顺手给它分诊。如今，模型一个上午就能找出一百个候选漏洞，分诊成了瓶颈。

妥善分诊有助于防止警报疲劳。如果你提交太多重复或严重程度虚高的 bug，产品工程师可能会不再阅读它们，包括那些需要立即修复的。开源维护者尤其容易被未经分诊的发现淹没，因为他们会收到来自众多依赖其软件的不同用户的报告。

> *多个团队分享了同样的教训：如果我们发给产品工程师一堆发现、其中大半不可利用，他们就会对这些报告失去信任并放弃阅读。他们还会对 critical 和 high 级别的发现排定优先级，避免让下游工程师不堪重负。另一些团队则找到了一条捷径：让模型处理他们已有的积压——来自此前扫描器、此前模型的未决发现和漏洞赏金提交——几天内清掉了数百条陈年积压。*

给发现去重时，要考虑根本原因。扫描器常常在多个调用点标记同一个 bug，或者报告同一根本原因的多种症状。下面是一种实用做法：先用一个廉价的确定性 pass：同一文件、同一类别、漏洞行号彼此相差不到十行。然后让模型对剩下的部分应用定性规则：

- **视为重复**：同一根本原因换了个说法；同一漏洞在多个调用点被报告；一个全局性防护缺失（比如缺少认证检查）被逐端点报告；或者同一代码路径上的原因与其后果被分别标记。
- **视为不同**：同一文件中的不同漏洞类别；不同变量到达不同的汇聚点（sink）；同一个辅助函数内的两个独立 bug；两个端点上都缺少同一个检查，但各自需要单独修复。

如果你的 harness 会为每个发现生成 PoC 和补丁，另一种去重方法是检查某个发现的补丁是否同时也化解了其他发现的 PoC。

去重之后，基于以下几点为每个发现评定严重程度：

- **可达性。** 攻击者能否从真实入口点到达这段代码，还是只有内部代码和端点才能触达它？
- **攻击者可控性。** 不可信输入能否原封不动地到达汇聚点，还是上游有某种东西对它做了清洗或约束？
- **前置条件。** 触发这个 bug 需要哪些条件就位：一个非默认设置、一个特定的功能开关，还是攻击者必须命中的狭窄时间窗口？
- **认证。** 未认证的攻击者能否触发它，还是需要已登录用户甚至管理员？
- **读与写。** 攻击者只能读取数据，还是也能修改它？
- **波及范围。** 如果 PoC 引爆，谁会受影响？一个用户还是所有用户，一个租户还是整个平台，用户态还是内核？

要把这套评分标准变成分数，先让模型把每个问题的答案写出来，再评定严重程度。先过一遍证据，可以避免模型锚定在漏洞类别上（"SQL 注入，所以是 critical"），然后为了自圆其说而抬高严重程度。作为起点：零前置条件且可未认证远程访问，为 critical 或 high；一到两个前置条件，或需要认证路径，为 medium；三个及以上前置条件，或仅限本地触发，为 low。请根据你的系统调整这些阈值。

模型可能因为上下文不足而抬高严重程度。它们可能不知道攻击者实际能控制哪些输入，或者看不到补偿性控制。就前者举例：一个 SQL 注入如果由未认证请求触发就是 critical，但如果只能由仅管理员可改的配置文件触发就根本不算问题。就后者而言，上游阻止漏洞利用的 WAF 或认证，可能仅凭源代码看不出来。

解决办法是在分诊时提供一份威胁模型，告诉模型你在乎和不在乎哪些类型的漏洞。例如，澄清"我们信任已认证的客户端"，就能简化甚至消除一整类 critical 级别的发现。

> *一个团队发现，除非有可验证的东西作为依据，或者对某事是否属于威胁模型预期有更多上下文，模型往往会过度自信。他们的解决办法是给分诊智能体提供与发现智能体相同的威胁模型。*

**试试[`triage` 技能](https://github.com/anthropics/defending-code-reference-harness/tree/main/.claude/skills/triage)。** 它同时承担验证和分诊：对每个发现进行多票验证、跨运行去重，并按推导出的可利用性重新排序。输出是一份简短、已排序、有归属的清单，而不是一次原始倾倒。

## **6. 修补：闭环并为下一轮循环改进上下文**

修补是你闭环并修复漏洞的环节。根据已验证的发现改进威胁模型也很有帮助——更新信任边界或需要更多审视的组件——并把过往发现喂进下一次扫描的上下文。每一轮循环都会加固代码库，让下一次扫描更有依据。

修补之前，先写一个在现有代码上会失败的新测试。然后实现修复，确认同一个测试现在通过，且没有破坏其他任何东西。（是的，这就是测试驱动开发。）如果不加测试，修复可能悄悄回退，而且事后很难证明这个 bug 确实存在过。

> *一位渗透测试工程师发现，他们生成的补丁质量不稳定——有的好有的差——直到 harness 让模型通过对打过补丁的代码重跑概念验证来校验补丁。给模型一个可供迭代的反馈之后，补丁质量大幅提升，为人工评审节省了时间。*

模型可能只狭隘地处理特定调用点上的发现，而不触及根本原因。直接提示模型识别并修复根本原因，就可能有效。然后，让模型在两个层面查找变体：(1) 同一模式——其他调用点或别处还复制着同样有 bug 的代码；(2) 同一类别——一个存在一个 SQL 注入漏洞的代码库往往还有更多 SQL 注入漏洞。用已验证的发现和补丁更新威胁模型，完成闭环。

发布补丁之前，先做一次对抗性检查。让一个新的发现智能体以攻击者的身份试探补丁，确认补丁足够全面。然后，简化生成的补丁，处理那些过于大动干戈的补丁。最小化补丁更容易评审，也更不容易引入新 bug。提示模型做出能修复根本原因的最小改动——不重构、不顺手清理、不重新排版。

> *一个团队谈到他们最常见的补丁失败模式："推荐的补丁往往过于保守，保守到会切断与其他服务的连接。问题确实解决了，但把让服务原本得以运转的依赖也弄坏了。"*

你可以用一个由廉价到昂贵的检查阶梯来验证每个补丁：

1. **构建。** 补丁能编译通过，新测试通过。
2. **尝试复现。** 原始 PoC 应当不再生效。这能抓住无效补丁。
3. **检查回归。** 原有测试套件仍然全部通过。这能抓住破坏性或过度保守的补丁。
4. **再次攻击。** 一个全新的发现智能体执行对抗性检查。这能抓住不完整的补丁。

最后，虽然补丁可以由模型来写，但仍需要人来负责。生成的补丁会以可预见的方式失败——治标不治本、拦截合法输入，或切断对某个依赖服务的访问。目标是尽可能充分地验证每个补丁，让人工评审省时省力；让开发团队只需最少的评审和补丁更新，就能专注于模型可能意识不到的细节（比如即将合入的改动、代码风格）。

**试试[`patch` 技能](https://github.com/anthropics/defending-code-reference-harness/tree/main/.claude/skills/patch)。** 它消费分诊的输出，为每个发现生成一个候选 diff，并由一个独立的评审智能体逐一检查。

## **开始上手**

试着亲自运行这个循环。克隆 [`defending-code-reference-harness`](https://github.com/anthropics/defending-code-reference-harness)，并在 Claude Code 中运行 `/quickstart`。它会带你在演示目标上走完从威胁建模到扫描再到分诊的交互式工作流。该仓库还包含一个自主运行 harness 和一个 /customize 技能，用于针对你的环境更新 harness。

然后，把它跑在你自己的代码上。挑选一个服务或软件包。从代码和文档自举一份威胁模型，并完成访谈。投入建设你所在环境的沙箱。扫描。用独立智能体验证发现。按你的标准分诊，并人工审阅所有评为 high 及以上的条目。修补。然后定期重新扫描。

你的首次扫描会浮现出比你预期更多的发现，其中大多数都需要验证和分诊。在为更多扫描做预算之前，先为扫描*之后*的流水线做预算。

一些你可能会觉得有用的资源：

- [`defending-code-reference-harness`](https://github.com/anthropics/defending-code-reference-harness)：配套仓库，包含用于交互式工作流的技能和用于自主运行的演示 harness。
- [`claude-code-security-review action`](https://github.com/anthropics/claude-code-security-review)：一个 GitHub action，让 Claude 担任每个拉取请求的安全评审者。
- [威胁情报富化智能体](https://platform.claude.com/cookbook/tool-use-threat-intel-enrichment-agent)：一份 Cookbook，教你构建一个将失陷指标（IOC）与威胁情报源比对富化的智能体。
- [漏洞检测智能体](https://platform.claude.com/cookbook/claude-agent-sdk-06-the-vulnerability-detection-agent)：一份 Cookbook，教你构建一个能构建威胁模型、扫描漏洞，并把发现分诊成结构化报告的智能体。

## **向前看**

我们相信，模型[发现并利用代码中的漏洞](https://red.anthropic.com/2026/exploit-evals)正变得越来越容易。因此，作为防御者，我们的工作是在对手利用漏洞之前，找到并修复我们代码中的漏洞。一些团队甚至把 harness 接入了事件流：漏洞赏金报告触发自动化的变体分析，一次安全评审触发扫描并挂上候选发现，或者一个已验证的漏洞推动更新静态分析工具，以防患于未然。

这项工作至关重要、风险极高。但只要做得对，它就是一场更大、更有希望的转变的开端：我们将*能够*在攻击者利用漏洞之前就找到并修复它们。
