# 构建全天候智能体

> 原文：[Building always-on agents](https://claude.com/resources/articles/building-always-on-agents) · Claude 博客

全天候智能体可以无限期运行，在许多会话之间自行决定以何种方式、在何时行动。本指南将逐一介绍它们的核心原语，以及这些原语如何相互配合。

* 分类：[最佳实践](/resources/best-practices)
* 产品：Claude Platform
* 作者：William Hu
* 日期：2026 年 11 月 13 日
* 阅读时长：14 分钟

过去几个月里，我们看到全天候（always-on）智能体重新兴起。

全天候智能体是有状态且主动式的：它们跨会话管理上下文，无需直接监督即可采取行动。在底层，它们与其他智能体运行在同一个[核心循环](https://www.anthropic.com/research/building-effective-agents)之上。区别在于外围架构——它由若干原语构成，分别控制智能体何时被唤醒、两次运行之间保留什么，以及它们的工作成果如何送达用户。

这轮复兴在很大程度上归功于近期的模型进展，它让全天候智能体的实际运行变得更加可行。首先，最新模型具备更好的判断力：它们在理解用户意图、判断何时该主动询问方面更加可靠。其次，智能的成本正在下降，而长程任务受益最大。例如，在[某一长程编码基准](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)上，Opus 5.5 每解决一个任务的成本比 Opus 5 低 78%，而在典型工作负载上这一降幅为 40%。

客户已经开始询问我们，如何把这类体验集成到自己的产品中。一些公司希望让现有智能体更具主动性，另一些则希望从零开始构建。

本文将拆解全天候智能体背后的原语，并说明它们如何协同工作。

## 全天候智能体背后的循环

全天候智能体实际上并非真的「全天候在线」。这只是对用户体验的一种描述。

在现实中，智能体的大部分时间都在休眠，只是周期性地醒来工作。每一段工作称为一次**运行（run）**：智能体接收一个事件，完成任务，然后保存关于所发生之事的信息。一次运行在一个**会话（session）**内进行，会话是消息与工具调用的记录。运行结束后，智能体重新进入休眠，这个循环无限重复。

![全天候智能体时间线的动画示意图：长时间休眠、不消耗任何 token，其间穿插着短暂运行。每次运行包含四个步骤：事件到达、会话开始、智能体循环执行，运行将结果写回可在多次运行之间延续的存储状态。](https://assets.claude.com/5dc803bf06d6e92e4aecae762da096626e2fa9ec.gif)

## 核心原语

全天候智能体的外围架构包含五个核心原语：事件收件箱、定时器、记忆、权限，以及发件箱。我们逐一来看。

### 事件收件箱

大多数 AI 智能体只在用户发送消息时才运行。相比之下，全天候智能体可以由多种类型的事件触发，包括 webhook、定时任务和后台作业。

一种颇有诱惑力的做法是让每个事件源直接调用智能体，但这存在几种失效模式。例如，两个同时到达的事件可能启动相互竞争的运行，而一次崩溃则可能让某个事件彻底丢失。

这正是事件收件箱的用武之地。每个来源不再直接调用智能体，而是把事件发送到一个收件箱，由工作进程（worker）接手处理。

最简单的版本包含三个组件：

* 一份持久化的事件列表，通常是一张数据库表；
* 一个处理器（handler），通常是一个 HTTP 端点，负责把事件写入该列表；以及
* 一个工作进程（worker），通常是一个后台服务，负责从该列表中读取事件。

收件箱应当跟踪每个事件的状态，并可以依据来源提供的唯一标识符对事件去重。关系型数据库很适合用作收件箱，每个事件作为新行追加即可。我们建议从每个用户一个收件箱开始，如果需要更高的并行度，可以进一步拆分。

![事件收件箱示意图。处理器（HTTP 端点）把每个事件写入收件箱——一张跟踪状态并丢弃重复项的数据库表——并唤醒工作进程。工作进程读取待处理事件，启动运行，等待其结束，然后把事件标记为完成。](https://assets.claude.com/bb08543a505cea3a24c88c718ceec4405e9c0a79.png)

新事件到来时，处理器把事件写入收件箱并唤醒工作进程。工作进程读取所有待处理事件并启动一次运行。延续先前工作的事件（例如用户的回复）会恢复现有会话，其余事件则开启新会话。

随后，工作进程把事件交给智能体循环，等待运行结束，再把对应事件标记为完成。实现细节可能颇为棘手，以下是几条最佳实践：

* **处理器应快速确认收到事件**。某些来源（例如 webhook 提供商）会把缓慢的响应视为失败。处理器仍可执行轻量检查，但更深入的验证（例如检查提示注入）应在运行期间完成。
* **收件箱应当是唯一事实来源**。工作进程被唤醒后，应首先从收件箱拉取最新事件。这样，如果工作进程在运行中途挂掉，新的工作进程可以接手同一事件并重试。
* **一个收件箱在同一时间只应有一个活跃的工作进程**。这可以防止两次运行重复工作或相互覆盖。当运行中途出现新事件时，你可以把它推给下一次运行、并入当前运行，或者中断并重启。
* **工作进程应把待处理事件批量合并**。例如，如果用户连续发送多条消息，工作进程可以把它们合并为一次运行，让智能体只需回复一次。

### 定时器

与事件收件箱配合，定时器让全天候智能体具备主动式能力。定时器通常分为两类：跟进任务或周期计划。跟进任务（follow-up）是智能体为自己设定的截止时间，例如跟进某个回复。周期计划（schedule）则是按已知节奏重复发生的任务，例如每日简报。

定时器存放在自己独立的持久化存储中，通常是另一张数据库表，与收件箱分开。收件箱只应保存已准备好处理的事件。跟进任务与周期计划可以共用相似的 schema，但周期计划还需要跟踪其重复规则。

![定时器示意图。一次运行在数据库表中设置定时器，可以是由智能体设定的跟进任务，也可以是由用户设定的周期计划。调度器找出到期项，并向事件收件箱添加一个事件，从而启动下一次运行。](https://assets.claude.com/c16694e6d979a2ace84d03da0544297b7245c0a8.png)

定时器不会自行发起运行。相反，由调度器（scheduler，通常是后台服务）按固定间隔轮询存储，并触发所有到期项。每一轮轮询时，调度器会：

1. 扫描存储，找出已到期的定时器。
2. 按类别更新每个定时器。
   1. 跟进任务应标记为完成。
   2. 周期计划应把到期时间更新为下一次发生的时间。
3. 向收件箱添加一个事件，并唤醒工作进程。

调度器既可以自建服务，也可以使用持久化执行引擎。

### 记忆

全天候智能体跨越许多彼此不相连的运行，依靠记忆来保持连续性。

与事件收件箱和定时器类似，记忆也应有自己的存储。在我们的产品中——例如 Claude Code 的[自动记忆](https://code.claude.com/docs/en/memory)和 Messages API 的[记忆工具](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)——这一能力以文件目录的形式实现。对全天候智能体而言，这些目录应映射到持久化存储，通常是数据库或对象存储。这样记忆的生命周期就能长于工作进程。

一条经验法则是：记忆只应保存智能体无法再次查到的内容。如果某些内容已经存在于其他系统中（例如 issue 跟踪器），应当改为保存一个指针。下面是全天候智能体应当保存的记忆类型：

* **用户指令：** 用户关于智能体行为的任何指令都应保存在单独文件中，并在每次运行开始时加载。用户不会总在身边引导智能体，因此这些指令必须在多次运行之间延续。
* **用户笔记：** 智能体应保存它了解到的关于用户的信息，例如用户的角色、偏好，或用户给出的任何纠正。可以先用一个文件，随着笔记增多再拆分为多个小文件。在后一种情况下，每次运行开始时只加载一个索引，但当智能体需要更多细节时，可以把各个文件拉入上下文。
* **历史消息：** 智能体应跟踪自己已经告诉过用户什么，以免重复。它可以将其存放在单独文件中、在每次运行开始时加载，也可以由工作进程加载智能体与用户最近几条消息。
* **任务进度：** 对于每个进行中的任务，智能体应维护一个进度文件，记录已完成和剩余的工作。任何新的运行都可以读取该文件，从上次运行停下的地方继续。与用户笔记类似，每次运行开始时只加载索引，需要更多细节时再把具体文件拉入上下文。

下图展示了一种示例配置。

![示例记忆配置示意图，以文件目录形式组织。instructions.md、index.md 与 reported.md 在每次运行开始时加载，而 notes/ 与 progress/ 文件夹则在需要时读取。智能体在运行期间写入记忆。](https://assets.claude.com/e5d209d7ef9b3455dec8a27b777dc12bdf806699.png)

以上描述的都是运行期间保存的记忆。你还可以加入 dreaming：它会回顾过去的会话，对记忆进行筛选整理。dreaming 可以替换过时条目，并发现只有跨越多次运行才会显现的模式。如果你想进一步了解，我们[关于智能体记忆的文章](https://www.anthropic.com/research/components-of-agent-memory)对此有更详细的讨论。

#### 上下文窗口内部

在开始任何工作之前，智能体会加载系统提示、工具定义和记忆文件。这部分初始上下文「开销」会包含在每次运行中，因此我们建议保持精简，并使用[提示缓存（prompt caching）](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)来降低成本。

新会话只带着这部分上下文开销以及触发本次运行的事件开始。而现有会话则会带回其先前各次运行中的消息与工具调用。

如果会话变得过长，你可以[对较早的消息做上下文压缩（compaction）](https://platform.claude.com/docs/en/build-with-claude/compaction)，或开启新会话。两种做法都会丢失细节，因此任何需要持久保留的内容都应在过程中保存到记忆。

![上下文使用量随时间变化的动画图表。系统提示、工具和记忆构成固定条带，出现在每次运行中。现有会话会带回完整记录并不断增长，直到上下文压缩（compaction）把较早的记录转为摘要。](https://assets.claude.com/48757f0a147acfe841c943674c6214d34ed4405a.gif)

### 权限

权限是全天候智能体风险最高的环节。一次运行持有用户的访问权限，并且按设计在无人值守的情况下操作。对于每次工具调用，智能体都需要判断：是自行继续、阻止该调用，还是等待批准。

权限所用的组件与其他智能体相同：

* **凭据存储：** 全天候智能体往往需要密码或访问令牌等敏感的用户凭据才能发挥作用。[推荐的做法](https://code.claude.com/docs/en/agent-sdk/secure-deployment#credential-management)是在智能体环境之外设置一个代理，由它把凭据添加到出站请求中。智能体发送不带凭据的请求，代理在转发前注入真实凭据。
* **自动模式（auto mode）：** 全天候智能体应能在没有用户持续输入的情况下工作。我们已在 Claude Code 中通过 [auto mode](https://www.anthropic.com/research/claude-code-auto-mode) 处理过这类问题的一个版本。自动模式使用分类器审查风险较高的操作，并拦截被判定为危险的操作，以便 Claude 找到更安全的做法。不过，对于最重要的决策，仍然需要用户审查。
* **延迟工具调用（deferred tool calls）：** 在 Claude Code 中，[hook 可以延迟一次工具调用](https://code.claude.com/docs/en/hooks#defer-a-tool-call-for-later)，等待用户提供更多输入。同样的模式也适用于全天候智能体，因为它们可能需要在采取某些操作前获得澄清或批准。当一次调用被延迟时，本次运行结束，会话在调用中途被保存。请求会展示给用户（例如通过用 [MCP Apps](https://modelcontextprotocol.io/extensions/apps/overview) 构建的交互式卡片），用户的回答则作为收件箱中的一个事件返回。该事件会启动一次新的运行，带着用户的输入恢复已保存的会话。在延迟调用等待响应期间，工作进程可以接手其他事件，因此智能体不会被阻塞。

### 发件箱

对大多数 AI 智能体而言，响应会在生成的同时流式呈现给用户，让他们能跟随 Claude 一步步推理问题、调用工具并写出答案。

而全天候智能体的大部分工作都在后台完成。用户得到的是结果和少量细节，而不是完整的逐步拆解。

![发件箱示意图。一次运行可能以无话可说、调用发送工具，或发起询问用户的延迟工具调用而结束。消息进入发件箱——一张数据库表——由分发器投递给用户。延迟请求既可以经过发件箱，也可以显示在你自己的界面中。](https://assets.claude.com/700b5f3a446f22493c0307ec65751b6b2f82ccb7.png)

一次运行可以以三种方式之一结束：

* 智能体向发件箱发送一条消息，
* 智能体判断无需发送任何内容，或
* 智能体使用延迟工具调用请求权限或额外输入。

大多数全天候智能体只需一个把消息直接送达用户的「发送」（send）工具即可。只有当你希望控制智能体消息的节奏，或允许智能体从错误中恢复时，才需要正式的发件箱。

发件箱是一张单独存放出站消息的表，类似于事件收件箱。另有一个分发器（dispatcher，通常是后台服务），类似于工作进程。分发器读取待发送的消息，决定要投递哪些，然后把它们发送给用户。来自延迟工具调用的请求既可以经过发件箱，也可以直接显示在界面中。

除了投递之外，调节智能体发送多少消息也很重要。发送太多的智能体会变得嘈杂，而发送不够的智能体则会漏掉用户需要知道的事情。我们建议构建评估（evals）来找到合适的平衡点。在实践中，智能体最好先保持安静，再随时间赢得用户更多的注意力。

## 各部分如何拼合在一起

下图展示了五个原语如何协同工作：

![五个原语如何协同工作的动画示意图。定时器与事件收件箱启动一次运行，运行在会话内使用记忆与权限，发件箱把消息投递给用户，用户的回答又作为事件返回。](https://assets.claude.com/9f8df7b2dcc9d4637d27f37dae6e40a2a5851c8a.gif)

每次运行都始于收件箱中的一个事件，无论它是用户消息、webhook 还是定时器。工作进程接手事件后便启动一次运行，并在新会话或现有会话中唤醒智能体。智能体读取记忆以建立基线，在权限范围内采取行动，然后把学到的任何内容更新到记忆中。运行结束后，智能体向发件箱推送一行记录，分发器把消息投递给用户。

这些环节共同构成一个循环。一次运行可以设置一个稍后再次唤醒智能体的定时器；当用户回复某条消息时，其回答会作为收件箱中的一个事件返回。每次运行都很短暂，但这个循环会无限持续下去——正是这一点让智能体感觉像是全天候在线的。
