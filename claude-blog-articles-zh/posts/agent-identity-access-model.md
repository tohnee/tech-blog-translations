# 智能体身份：面向自主、全团队 AI 的新型访问模型

> 原文：[Agent identity: a new access model for autonomous, team-wide AI](https://claude.com/blog/agent-identity-access-model/) · Claude 博客

要让 AI 智能体在人机团队中发挥最佳水平，它需要拥有与人类相同的工具、文档和上下文访问权限。

在"单人"AI 体验中（一个人与一个助手对话），这很简单：你连接自己的账户，智能体代表你行事。但在像 [Claude Tag](http://anthropic.com/news/introducing-claude-tag) 这样的"多人"AI 体验中，Claude 与许多人一起待在一个共享频道里，它调用的是属于*工作区*（workspace）而非任何个人的工具和上下文。

要让多人体验运转起来，Claude 需要这些工具的专属账户，由管理员设置并绑定到工作区。我们把这种访问模型称为***智能体身份***（agent identity）。

在这篇文章中，我们会解释智能体身份如何运作、它如何把权限从"按用户"变为"按频道"，以及如何在你自己的工作区里把它划定到合适的范围。

## **"代表用户行事"为何会失效**

当你把 AI 当作个人助理使用时，你可以连接 Google Drive、GitHub 和日历等平台，让模型使用*你的*访问权限在其中读写。

这个模型对 Claude Tag 行不通，原因有二：

- **智能体自主性不断增强。** AI 智能体能够可靠独立完成的任务时长[大约每四个月翻一倍](https://www.anthropic.com/institute/recursive-self-improvement)。智能体现在会自行安排稍后执行的任务，并在提出请求的人早已下线很久之后响应事件。虽然用户会设置在特定情形下触发行动的例行任务（routines），但智能体在很大程度上是自主工作的。

- **多人团队。** Claude Tag 把 Claude 放进团队已经在协作的共享空间——例如一个由三名工程师和一名产品经理共同调试问题的频道。但当多个人同时在指挥时，该以谁的权限为准？不存在一个在任何时刻都正确的唯一人选。智能体身份让管理员能够独立于参与者定义智能体在 Slack 中能做什么，并对 Slack 中发生的行为进行独立追踪。

### Claude 以自己的身份行事

在启用了 Claude Tag 的频道里，Claude 并不代表任何单个用户。它在接触到的每个系统中都有自己的账户：在 Slack 里以 Claude 应用发帖，以 Claude GitHub App 的身份发起 pull request，并在管理员配置的服务账户（service account）下查询你的数据仓库。

而且由于不涉及任何个人用户凭证，共享频道永远不可能成为通向某人私人文档的旁门。

### 继承权限

在智能体身份模型中，管理员在工作区层面定义一个身份——即 Claude 在所有地方持有的连接与技能（Skills）基线集合，每个频道默认继承它。随后，在有意义的地方，管理员可以在频道层面覆盖它，例如授予工程频道访问 GitHub 和数据仓库的权限，或把 CRM 连接限制在某个私人频道内。

除了凭证之外，管理员还可以定义：

- **仓库访问权限：** Claude 可以读写哪些仓库。
- **连接器（connectors）：** Claude 完成工作所用的工具与 API 密钥。在整个组织中，不同的 API 密钥可以以不同的权限级别连接同一个服务（例如，在普通频道中 Claude 可能只获得只读的仓库访问权限，而在数据团队的私人频道中获得写入权限）。
- **技能与插件：** Claude 动态加载的指令、脚本和资源文件夹，用于提升其在专门任务上的表现。
- **长期指令：** 每个频道各自的自定义指令与上下文。

由于这个模型围绕彼此独立的 Claude 身份运转，撤销某个身份即可终止 Claude 在该身份使用过的所有地方的访问权限。这比审计散落在数十个用户账户中的单个智能体行为要省力得多。

## 智能体身份模型如何运作

智能体身份把"这个用户能做什么？"的问题替换为"这个智能体能在这个隔间里做什么？"。这与按用户的访问控制列表（Access Control List）是一种背离：它意味着，对某个仓库没有直接访问权限的频道成员，只要频道的配置（profile）授予了 Claude 该权限，就可以让 Claude 去读取那个仓库。

这确实不寻常，但我们认为，它是迈向一个适用于自主、多人智能体的访问模型的必要一步。下面我们简要说明应该如何思考划定这些边界。

### 身份边界如何运作

Claude Tag 为每个私人频道创建一个独立的身份；工作区中的公共频道共享一个工作区级身份。Claude 在法务频道中的身份无法触及未在该频道授权的代码，它在工程频道中的身份也无法读取未在该频道授权的法务文档。记忆和访问权限同样尊重这些边界：Claude 在私人频道中学到的东西，绝不会出现在更大的工作区中。

身份属于频道，因此默认任何频道成员都可以 @ 提及（tag）Claude，管理员则可以把每个频道的配置限定到该频道中权限最低的成员。在企业（Enterprise）方案上，基于角色的访问控制（RBAC）让管理员可以更进一步，决定哪些成员根本能够调用 Claude，这样一个频道既约束智能体能触达什么，也约束谁能提出请求。

### 对工具与上下文默认放宽访问

各团队在 Claude Tag 中这样划定 Claude 的工具访问范围：低风险的大众化集成在共享频道中以智能体身份运行，而个人或特定团队专用的工具则留在私信（DM）中并以用户身份运行。

在 Anthropic 内部运行 Claude Tag 的经验是：它的价值会随工具和上下文访问权限而复利增长。每一个接入的系统都让其他系统更有用，因为 Claude 能够跨系统组合上下文——从 Slack 抽取一条讨论串、从 Drive 取来一份文档、从跟踪器抓取一张工单、从数据仓库取出一次查询结果，融合成一个任何单一工具都无法给出的答案。

从 Claude 中获益最多的团队，是那些从一开始就授予它充分访问权限、再依据组织管理员偏好逐步收紧的团队。智能体身份为管理员提供了足够宽的范围让 Claude 做有用的跨系统工作，同时边界又足够牢固，访问权限绝不会流向未被授权的地方。我们的建议是：先在少数几个频道中启用基线配置，阅读审计记录，然后在确实有工作需要的地方逐步扩展权限，一次只做一个审慎的授予。

对于需要更细粒度控制的组织，管理员可以在特定频道中禁用 Claude Tag。管理员还可以应用基于角色的访问控制（RBAC），把 Claude Tag 的使用限制在特定用户。

### 私信

在 Claude Tag 中，私信的工作方式与共享频道不同。私信运行在用户各自的 claude.ai 账户上——使用他们的连接器、凭证，结果也署他们的名字。这让私信成为与 Claude 协作处理那些永远不该出现在频道里的任务和工具的合适场所，例如邮件草稿，或只有你持有许可的软件。

### 安全与审计

当管理员向某个频道的配置中添加连接时，凭证会被独立存储并映射到该频道的身份，然后在请求时于网络边界注入。对任何管理员未允许的主机的出站流量会被直接阻断。在审计方面，使用智能体凭证执行的每一次例行任务、每一次记忆写入和每一次网络调用都会被记录；而且由于 Claude 以自己的服务账户行事，这些行为也会落入每个接入系统自身的日志中。

## 接下来

智能体身份是 Claude Tag 访问模型的基础。未来，我们计划强化 Claude Tag 的安全能力，包括即时凭证授予（just-in-time credential grants）——让用户可以当场批准单次敏感操作，而不必永久扩大智能体的权限范围——以及面向拥有更复杂许可层级的组织的身份感知叠加层。这会在智能体的权限范围之上增加用户级检查，只有当频道配置和发起请求用户的自身权限都允许时，Claude 才会行动。

从单人 AI 到多人 AI 的转变，让长时间运行、以团队为单位的工作成为可能。智能体身份确保 Claude 对工具的访问足够宽泛以致有用，又足够受限以致在企业规模下依然安全。
