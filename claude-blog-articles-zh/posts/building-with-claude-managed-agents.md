# 智能体界面的演进：用 Claude 托管智能体构建

> 原文：[The evolution of agentic surfaces: building with Claude Managed Agents](https://claude.com/resources/articles/building-with-claude-managed-agents) · Claude 博客

随着模型智能与智能体执行框架（agentic harness）不断演进，Anthropic 的 Claude 托管智能体（Claude Managed Agents）让团队能够可靠地、规模化地在生产环境中构建和部署智能体。以下是团队为什么要用它，以及是怎么用的。

把智能体送进生产环境，光有一个好的提示词远远不够。智能体需要有一个地方运行它写出的代码，需要有凭据去访问你的数据，需要可观测的会话，还需要能随用量扩展的基础设施。在应用 AI（Applied AI）团队，我们的工作处在产品、研究与基于 Claude 构建的客户的交叉点上——我们反复看到同一个模式：基础设施才是原型与生产级智能体之间的分界线。太多时候，团队把开发周期消耗在安全、状态管理、权限和执行框架（harness）调优上。

[Claude 托管智能体](https://platform.claude.com/docs/en/managed-agents/overview)是我们用于构建和部署生产级智能体的一套可组合 API，它把经过性能调优的智能体执行框架与生产基础设施结合在一起，让团队能在几天而不是几个月内从原型走到上线。本文将介绍 Anthropic 智能体构建模块的演进、我们为什么要构建 Claude 托管智能体，以及团队今天如何在生产中使用它。

## **演进智能体架构**

2023 年我们向开发者开放 Claude 时，API 刻意设计得很简单：token 进，token 出。你发送一个提示，Claude 返回一个补全，而执行框架和底层基础设施由你自己搭建。

这些年来 API 不断变丰富，但底层的约定从未改变：一次请求、一个模型回合，接下来发生什么由你的应用决定。在很长一段时间里，这已经够用了。总结一份文档、给一张支持工单分类、重写一段文字——这类工作天然适合放在单个回合里完成。

但随着时间推移，人们想交出去的任务开始装不进这个模型了。他们希望 Claude 把一个任务从头跟到尾：查资料、采取行动、看看发生了什么变化、决定下一步做什么。他们还希望 Claude 在*工作本身已经运行其上的系统里*操作，比如代码库、内部 wiki 或工单系统。

用 API 把 Claude 变成智能体，意味着你要自己实现一个循环：问模型该做什么、运行工具、把结果喂回去、重复。你需要负责构建和部署智能体脚手架，而随着模型演进，这套脚手架可能还需要不断调优。对于需要完全定制的智能体，这种做法是合理的。但对于更可预测、复杂度更低的智能体负载，随着模型和产品演进不断优化执行框架就变得很繁琐。

![](https://assets.claude.com/fe30ad015136d78e5367ec44d8fca508f184104e.png)

我们在 2025 年推出的 [Claude Code](https://claude.com/product/claude-code) 是一款智能体编码工具，让 Claude 可以直接与你的代码库交互，它内部就包含我们自己版本的这套执行框架：循环、工具执行、子智能体、上下文管理，以及一系列让 Claude Code 成为有效智能体的丰富能力。开发者自然也希望在自己各领域的智能体里用上同样的执行框架机制。

为了让团队能在 Claude Code 的执行框架之上构建智能体，我们发布了 [Claude Agent SDK](https://code.claude.com/docs/en/agent-sdk/overview)。Claude Agent SDK 让开发者可以基于运行 Claude Code 的同一套机制构建自己的智能体，而不必维护自研的循环。对很多团队来说，智能体正是从这时开始变得实用：执行框架出厂时就已针对 Claude 调优，并带有基础设施原语，而且它会跟随 Claude Code 一起持续改进。

不过，即便有了执行框架，在生产环境中部署智能体仍然困难重重，原因有以下几点：

* **托管与扩展。** 智能体在哪里运行？一个进程能存活多久，以支撑持续数小时的任务？用量增长时靠什么来扩展？
* **会话管理。** 智能体的历史和进度存在哪里？一次运行能否在中断后存活并顺利恢复？你能否回溯查看此前会话中发生了什么？
* **文件系统管理。** 真正干活意味着产出工件：修改代码、写文件、构建输出。智能体从哪里获得一个可操作的工作区？两次运行之间，这个工作区会怎样？
* **执行隔离。** Claude 写的代码总得有地方执行。如果代码写错了，影响范围（blast radius）有多大？在生产环境中，什么样的边界是你真正敢信任的？
* **凭据。** 智能体需要访问你的系统。它如何获得这种访问权限，同时又不会把专有信息暴露给它生成的代码？
* **可观测性。** 当一个智能体自主工作了一小时、并做出了出人意料的举动，你能否重建它走过的每一步？

使用 Agent SDK 时，上述生产基础设施中的许多要素都由 Claude Code 的机制提供。智能体获得了真实可用的文件系统，会话状态持久化在本地或外部存储上，可观测性数据可以通过 OpenTelemetry 导出到你已经在用的任何监控栈中。

![](https://assets.claude.com/df5faaa1a40adae1b9607307078bd88e7c636dae.png)

然而，随着团队构建的智能体越来越多地从本地开发走向生产环境，他们需要一种能够规模化部署、并且由托管基础设施承载的方式。而随着模型及其周边执行框架变得更加强大——运行更久、执行更多代码、触及更多系统、采取更多行动——扩展、安全和沙箱化也变得更难。

其中若干障碍源自一个共同的架构选择：智能体执行框架往往与它所操作的文件系统*运行在同一个容器里*。容器必须先启动（付出启动成本），Claude 才能开始思考；智能体和代码执行与你的凭据紧挨着；容器一旦消亡，这次运行也随之消亡。

托管智能体通过[把“大脑”与“双手”解耦](https://www.anthropic.com/engineering/managed-agents)解决了这些问题。调用 Claude 的执行框架与执行代码的沙箱分开运行，而会话——一份只追加的日志，记录每一次模型调用、工具调用和结果——将两者连接起来。Claude 可以在任何容器存在之前就开始推理，沙箱与你的凭据远远隔开，而整次运行在任何时刻都可以从它的会话中重建。

![](https://assets.claude.com/b715041a8258b4c9b675a42f047aa4202c30b851.png)

## **何时以及为何使用 Claude 托管智能体**

使用托管智能体构建时，用户定义任务、工具和防护栏，Anthropic 在我们的基础设施上运行智能体，并处理底层的智能体循环：如何为智能体提供调用工具的执行环境、出错时如何恢复、多智能体编排等等。

如果执行框架不与模型智能同步演进，[智能体就会失灵](https://www.anthropic.com/engineering/harness-design-long-running-apps)。在 Claude Sonnet 4.5 上，智能体在接近上下文末端时会急于收尾，把事情草草结束，而不是用掉剩余的空间——这种模式被称为“上下文焦虑”（context anxiety）。我们的解决办法是在执行框架里加入上下文重置，把“Claude 在接近上限时需要帮助才能保持连贯”这一假设固化了下来。可这个假设没能活过下一代模型。在 Claude Opus 4.5 上，这种行为消失了，我们加的重置只剩下额外开销。

对大多数组织而言，维护执行框架是一种并不能让产品产生差异化的开销。执行框架必须针对特定模型行为进行调优；压缩、工具执行、缓存这些原语在 Claude 上的工作方式与其他模型不同。使用 Claude 托管智能体，执行框架会随模型一起演进，团队得以专注于真正让他们的智能体产生差异化的东西：**上下文管理与领域专业知识。**

为了让开发者能够配置构建有效智能体所需的上下文和工具，托管智能体围绕三种主要资源构建：智能体、环境和会话。*智能体*（agent）是一份配置：一个模型、一个提示、一组工具，以及围绕它们的防护栏。*环境*（environment）是智能体运行所处的执行上下文：沙箱容器、它的网络规则、预装的软件包，托管在我们的云上，或托管在你掌控的基础设施上。每一次运行都是一个*会话*（session），它把一个智能体与一个环境配对，并获得自己独立的沙箱实例。会话把完整的事件历史、沙箱状态和输出持久化在服务端，因此长周期工作可以暂停、干净地恢复，也可以在事后被逐步追溯。使用托管智能体，你可以只定义一次智能体和环境，然后随着负载增长，针对同一份配置运行许多会话。

![](https://assets.claude.com/c06d2e0399c4172fcb6de31bd538749d03e6c68b.png)

## **在托管智能体上为生产与规模而构建**

在应用 AI 团队内部，我们既看到 Anthropic 内部、也看到客户系统中，智能体在编码、金融、客服、法务以及十几个其他领域从原型走向生产。这让我们清楚地看到，是什么把演示（demo）与生产级智能体区分开来，以及团队常常卡在哪里。

下面是我们总结的最常见的、应当构建在 Claude 托管智能体这类托管服务之上的理由：

**1. 凭据被隔离在沙箱之外。** 当所有东西都跑在一个容器里时，Claude 生成的代码就紧挨着你的凭据，于是提示注入可能诱使模型读取自己的环境，从而泄露 token。我们可以在同一个容器内设置健壮的防护栏来防住这一点，但把架构解耦能带来安全得多的方案：把凭据完全挡在沙箱之外。MCP、CLI、GitHub 仓库等工具的 token 存放在一个独立的保险库中，由代理按需获取并解密。托管智能体提供开箱即用的 [Vaults](https://platform.claude.com/docs/en/managed-agents/vaults) 来处理凭据，因此你无需自己运行密钥存储、无需在每次调用时传输 token，也不会弄不清某次智能体是代表哪个终端用户行事。Vault 中的凭据在存储前会用信封加密保护，取回时需要通过签名的请求 token 进行验证。

![](https://assets.claude.com/46c77d9f7b059194123c719f3aee706e647dc4ed.png)

**2. 消除沙箱开销带来的更低延迟。** 延迟是许多企业团队最关心的指标之一，因为用户在等待 Claude 响应时的体感非常强烈。没有托管智能体这套架构时，每个会话都必须启动一个容器——哪怕这个会话里智能体只需要思考、从不运行工具。启动时间被浪费掉了，用户则把它感受为首次响应前的延迟。使用托管智能体，Claude 立即开始推理，同时环境并行启动；从不运行工具的会话完全跳过容器。这意味着用户无需等待容器启动就能看到第一个 token，而在智能体需要运行东西时环境已经就绪。在我们的测试中，这把首 token 时间在中位数情况下（p50）缩短了约 60%，在最慢的情况下（p95）缩短了 90% 以上。

**3. 可靠且持久的会话，带来会话管理、可观测性与记忆。** 托管智能体不按请求/响应的方式思考，而按*事件*思考。会话是一条持续的事件流：每一次模型调用、工具调用和结果都被追加到一份日志中，而这份日志位于运行智能体的进程之外。有了这种架构，智能体工作时事件会流式传入，你因此能获得实时更新；此后你可以随时恢复任何会话，无需管理数据库或保存点。除非你删除会话，否则历史会在多次交互之间保留；会话空闲时，它的容器会被打上检查点，所以你可以从暂停处干净地继续。而因为整次运行本身就是一份事件记录，可观测性和记忆也随之而来：Claude Developer Console 提供智能体会话的原生可视化时间线视图，以及一个可以深入检查任意对话记录的调试体验。托管智能体还提供 Memory 与 Dreaming 等功能，同样受益于这种会话持久性。[Dreaming](https://platform.claude.com/docs/en/managed-agents/dreams) 是一个定时进程，它会审视你的智能体会话和记忆存储，提取模式，整理记忆，让你的智能体随时间不断改进。Dreaming 在会话之间提炼记忆，通过读取持久的会话日志，从反复出现的错误和用户偏好中学习改进。

**4. 在 Anthropic 托管或自托管云容器之间灵活选择。** 默认情况下，使用托管智能体时，你可以把编排和工具执行都委托给 Anthropic 托管的云容器。这让托管和扩展变得简单轻松，提供了一条更快的通往生产的路径。由于托管智能体中“大脑”与“双手”是解耦的，“双手”可以放在任何地方，包括你的虚拟私有云（VPC）内部。因此我们也为希望掌控工具执行的团队提供[自托管沙箱](https://platform.claude.com/docs/en/managed-agents/self-hosted-sandboxes)，让智能体的代码、文件系统和网络出站流量永远不离开他们的环境。我们还提供 [MCP 隧道](https://platform.claude.com/docs/en/agents-and-tools/mcp-tunnels/overview)，让你把 Claude 连接到运行在你私有网络内的 Model Context Protocol（MCP）服务器。也就是说，自托管沙箱控制*智能体的代码在哪里执行*，MCP 隧道控制*Anthropic 如何访问你网络中的 MCP 服务器*，让你能够精确掌控什么东西留在你的边界之内。

![](https://assets.claude.com/0231cd39f02075d990e6ab76b64cadef9fbdf7fe.png)

Claude 托管智能体的内置可观测性控制台会记录每一个事件，因此你可以拖动时间线、打开任意一步、读取它的原始负载数据。

除这些功能之外，其他能力还包括：outcomes——让智能体对照评分标准给自己的工作进行打分；多智能体编排；权限策略；以及 webhooks。详见[此处](https://platform.claude.com/docs/en/managed-agents/overview)。

### **客户今天如何在托管智能体上构建**

各行各业中，客户已经用 Claude 托管智能体在生产环境交付智能体。以下是一些例子：

* [Notion](https://claude.com/customers/notion) 在托管智能体上运行它的 Custom Agents：团队直接从任务板把工作指派给 Claude，Claude 收集与每个任务相关的文档、会议纪要和已连接的数据，完成的代码、演示文稿和网站会回到工作区等待评审。数十个任务并行运行，据其团队描述，一个早期原型把大约十二小时的工作变成了二十分钟。
* [乐天（Rakuten）](https://claude.com/customers/rakuten) 使用托管智能体在产品、销售、市场和财务各条线交付了专精智能体，每一个都在大约一周内上线。
* [Sentry](https://claude.com/customers/sentry) 把它的 Seer 调试智能体与一个负责编写补丁并提交 PR 的 Claude 智能体配对，由一名工程师在数周内（而非数月）建成。
* [Asana](https://claude.com/resources/articles/claude-managed-agents) 构建了 AI Teammates，在项目内接手任务；[Atlassian](https://claude.com/resources/articles/claude-managed-agents) 则把开发者智能体放进了 Jira 工作流。

## **开始使用 Claude 托管智能体**

我们构建托管智能体，是为了让你通过 Claude Code 和 [platform.claude.com](http://platform.claude.com) 上的 Claude Developer Console，尽可能轻松地创建智能体。例如，控制台的快速入门既可以从智能体模板开始，也可以用平实语言描述一个智能体，然后把它变成一个可加固、可在几分钟内部署的生产级智能体。

![](https://assets.claude.com/6bc461ffa26f0c016da3ebc70ca51960b1b5f747.png)

platform.claude.com 上的智能体快速入门：从模板开始，或描述你想构建什么。

![](https://assets.claude.com/7e0ae5e2a7b2c0fc5d1b44bcb9306e218172379b.png)

几步之后：智能体已创建，环境已配置，一个会话已经跑起来。控制台会实时流式展示运行过程。

在 Claude Code 中，[/claude-api 技能](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/claude-api-skill)默认提供，为 Claude 提供构建 Claude 托管智能体应用的详细、最新的参考资料。我们强烈建议你利用它来了解搭建托管智能体应用的最佳实践。运行 `/claude-api managed-agents-onboard` 即可开始，它会以访谈式引导带你从零搭建一个新的托管智能体。

## **构建托管智能体的未来**

随着团队分享他们用托管智能体构建的东西，我们看到，他们过去花在生产基础设施上的时间，现在转向了让智能体产生差异化的地方：管理上下文，以及为用户量身定制体验。如今，当新模型发布时，你只需要把智能体更新到新模型、重跑评估，然后交付这次改进，完全不必改动底层的架构。
