# 高效商务智能体解剖指南

> 原文：[A guide to the anatomy of effective commerce agents](https://claude.com/resources/articles/the-anatomy-of-effective-commerce-agents) · Claude 博客

让在线买卖更轻松的智能体：架构、延迟与成本技巧，以及 eval 实践。

过去一年，我们与商务行业的各类团队合作——零售商、市场平台、旅游、娱乐和电信运营商——用 Claude 构建商务智能体。

这些智能体已投入生产，企业客户在使用中看到了更大的购物车和更高效的卖家运营。它们还共享一套简单的架构：Claude 处在智能体循环中，配备一组技能、工具和一套强有力的 eval。

本文面向正在构建这类（或其他面向消费者）智能体的工程师与工程负责人。第 1 部分讲架构——这是你只需决定一次的。第 2 部分讲延迟与成本。第 3 部分讲生产环境：记忆、安全、eval，以及如何在组织内扩展这项工作。

## 01 架构

一个标准智能体循环中的单一模型，用技能覆盖长尾，用工具调用你已在运行的系统。这个决定只需做一次。

### 什么是商务智能体？

我们把商务智能体定义为：简化在线商品目录中买卖过程的智能体。

有些智能体面向消费者：搜索、比较、替代、组装订单。这可能是一个零售购物车、一份旅行行程、一次手机套餐变更，或为某场演出锁定座位。有些智能体面向企业：回答销售相关问题、执行促销和营销活动、管理库存与定价。

![](https://assets.claude.com/47781bb901a117a56bcb301ad769a405a42dba62.png)

核心架构是[标准智能体循环](https://www.anthropic.com/engineering/building-effective-agents)中的一个模型：围绕目标推理、探索上下文、通过工具采取行动、通过技能学习流程、提出澄清问题、观察结果，直到目标达成。

它前面没有把对话分段的意图路由器，后面也没有一组领域专用智能体。

### 工程上下文

#### 用技能，而不是子智能体

商务智能体必须覆盖众多品类和意图的广泛能力，这让人很想去为每个领域创建一个子智能体。

实践中这被证明并非最优，因为一段商务对话是横跨多个意图和轮次、高度耦合的单一会话，需要大量共享上下文。

在子智能体架构中，编排器持有购物车或暂存变更、用户偏好和对话历史。

每次向子智能体交接都是有损状态传递，常常影响子智能体回答的质量，进而影响整体回答。除此之外，每次交接可能多花数倍 token，并增加数秒延迟。

领域之间也很少能干净地分开。退货流程可能需要订单历史、当前购物车和商品目录，这意味着"一领域一子智能体"的做法要么在各处重复这些访问，要么在任务中途交接。

随着模型变得更聪明，它们也能处理更长的上下文、更多技能和更多工具，因此今天这些分配规则背后的限制，会随每一代模型而放宽。

相反，[智能体技能](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview)能提供类似的按领域模块化和上下文控制，却没有交接的代价，因为技能指令加载进那个已经持有完整历史的主智能体。

在多个企业部署的对比中，带技能的单一智能体在质量上稳定优于"一个提示词包打天下"的设计和子智能体设计，而且往往每个任务的成本和延迟更低。

子智能体真正有一席之地的地方，是当编排器可以把它当作工具调用，去处理一个狭窄或自足、且能从独立上下文窗口中获益的任务。

一个常见的生产例子是深度研究子智能体：它搜索和阅读文档、编写并运行代码、遍历数据模型、撞上死胡同。所有工作都在一个或多个子智能体内部发生，只有一份精简的答案回到编排器。

另一个例外是已经拥有专用智能体的领域。如果你的药房或金融服务体验运行着一个带自身合规面的专用智能体，正确做法可能是交接（hand-off）：由那个智能体接管任务，通过自己的循环直接与用户协作，直到任务完成。

区别在于对话的所有权。交接让领域智能体成为用户的对话对象；而委托保留编排器，让领域智能体在单个轮次内反复进出，每次交互都会损失信息。

#### 系统提示词还是技能：按频率决定

决定一组指令放在系统提示词还是技能里，主要因素是智能体需要它的频率。加载技能要花一个模型轮次，所以智能体在大多数轮次都需要的内容一般放在系统提示词里。

不过，这取决于你的流量分布，以及 eval 显示出的智能体行为。一个好的起点是：任何与三分之一或更多流量相关的内容，无论上线前预判到的还是生产中观察到的，都放进系统提示词；其余放进技能。

如果一个技能可以从你已有的信号预判出来，例如用户来自哪个页面，我们建议在第一次模型调用前由 harness 注入，省掉加载技能的那一个额外轮次。

关键指令——安全与法律规则、品牌约束、关键用户事实（如过敏史）——始终放在系统提示词里。

对商务智能体来说，这意味着商品搜索放在提示词里，因为几乎每个会话都会用到它；技能则承载长尾功能。

在我们的[参考实现](https://github.com/anthropics/commerce-agents)中，购物智能体的提示词包含 grounding、购物车与结账语义、呈现规则，其余由以下技能覆盖：search-discovery、purchase-research、planning-goals、customer-care 和 memory-personalization。

商家智能体也以同样方式拆分，其技能为 performance-insights、catalog-listings、inventory-operations、pricing-promotions 和 marketing-campaigns，每个运营领域一个。

|  |  |  |
| --- | --- | --- |
| **在提示词中** | 购物智能体 | Grounding、购物车与结账语义、呈现规则，以及商品搜索。 |
| **购物技能** | 长尾 | search-discovery · purchase-research · planning-goals · customer-care · memory-personalization |
| **商家技能** | 每个运营领域一个 | performance-insights · catalog-listings · inventory-operations · pricing-promotions · marketing-campaigns |

### 工程层面的智能体工具

我们关于[为智能体编写高效工具](https://www.anthropic.com/engineering/writing-tools-for-agents)的文章讲了一般性的工具设计。在商务领域，有两点最为重要：

**把智能体工具建在你的核心系统与逻辑之上。**

一家商务公司已经有搜索与排序、购物车、偏好与档案存储、库存系统、促销与营销引擎、销售分析等等，每一个都编码了多年调校的逻辑，并看到模型永远不会看到的信号。

智能体的工具应当调用这些系统，而不是重新实现它们；工具边界正是这些逻辑结束、模型判断接手的地方。

例如，当智能体调用 `search_products` 时，结果应当已经排好序；它的职责是判断哪些结果服务于用户目标、展示多少条、如何呈现。

**工具结果就是上下文。**

只返回模型据以推理的字段，其余丢弃。每条搜索结果都带图片 URL 是常见的罪魁祸首。

必要时在工具内部重塑原始响应，包括在下一步从数据中看不出来时附加提示。

这在错误场景中尤为重要：模型从指令中获益，而不是从错误码。例如加一句错误指令"查询可用性时请包含产品 ID"，而不是返回一个泛泛的 403。

#### UI 组件就是工具

商务智能体的大多数响应是 UI 组件而非散文——商品轮播、行程、座位图或图表。这意味着智能体必须输出 schema 而不是文本。

团队有时一开始会让模型输出自定义标签，在客户端解析。随着界面变复杂，这种做法会失效，因为：

* 模型对你的标记语言的训练程度不如对工具调用，因此随着嵌套组件增加，可靠性下降。仅靠提示词并不能保证数据格式良好。
* 标签定义放在系统提示词里，于是每个新组件都会让上下文膨胀，每次编辑都有在提示词其他部分引发回归的风险。
* 过去的对话最终以一种只有你的解析器能读的格式存储，于是加载历史要么在客户端解析原始消息，要么以非模型 API 原生格式另存一份副本。

经得起考验的做法是：把每个 UI 组件做成一个工具。模型用带类型的参数调用 `present_products`、`present_itinerary` 或 `present_plan_comparison`；你的服务器校验并补全该调用，发出一个事件；客户端负责渲染。

由于组件就是工具调用，它们已经以原生格式存在于 messages 数组中，因此重新加载旧对话时无需再解析。下面和[参考仓库](https://github.com/anthropics/commerce-agents)中展示了一个呈现工具契约的示例。

![](https://assets.claude.com/3f245cfa642f8d8c7a9f7f5841f127d67f27f5dc.gif)

代价是流式输出的粒度。工具调用的每个顶层参数都要在服务器缓冲以做校验，所以即使开启流式，呈现工具的子组件也会分步到达。这会影响感知延迟。

要获得 token 级流式，在工具定义上设置 `eager_input_streaming:` 为 true，这会跳过缓冲，同时也跳过服务端的 schema 保证。

在我们的 eval 中，Claude Sonnet 级及以上模型的 schema 违规非常罕见，但对漏网的情况，还是把该调用包在重试里。

呈现工具还给智能体留下屏幕内容的记录。当客户说"第一家酒店"或"左边往下第三个"时，布局就在 messages 数组中、在上一次呈现调用的参数里。

要让这一点成立，参数必须反映渲染后的布局，因此要按 UI 的结构来组织它们：有序的行与轮播，而不是一个由客户端重新排列的扁平列表。

## 02 让它又快又便宜

从端到端和感知两个方向进攻延迟，让缓存承担成本，而这一切都不该以牺牲智能为代价。

延迟在商务中很重要，消费级界面最不宽容。然而在智能体界面上，我们反复看到真正推动留存、参与度和购物车规模等指标的，是结果的质量。

与边际的延迟改善相比，答案是否切题、任务是否真正完成，对这些指标更为关键。

所以要两面夹击延迟。用良好的工程最小化端到端延迟，同时降低感知延迟（因为看着智能体干活的时间，会被读作进展）。

每个用户都有一个延迟预算，下面的技巧能让智能体留在这个预算之内，而不牺牲智能。

### 最小化任务完成延迟

任务完成延迟，是各模型轮次的"到最后一个 token 的时间 + 工具处理时间"之和。这给你三个可调杠杆：更少轮次、更快工具、更快 token。这些杠杆有时相互竞争，所以要最小化的是总和，而不是其中任何一项。

|  |  |
| --- | --- |
| **更少轮次** | 预先加载可能的上下文，提升模型智能，让模型并行调用互相独立的工具。 |
| **更快工具** | 优化工具自身的后端，并在参数就绪时立即派发工具。 |
| **更快 token** | 通过扫描 eval 套件来选择模型及其配置。 |

#### 更少轮次

查询复杂度会增加轮次，这通常不在你掌控之中。模型智能和相关上下文能帮智能体用更少轮次完成任务。我们在这一领域的关键经验包括：

* **预先加载可能的上下文。** 如果用户从商品页打开助手，或商家从活动仪表盘打开它，就把该页面的数据放进会话上下文。对话很可能就是关于它的，而从上下文回答不额外消耗轮次。
* **提升模型智能。** 更聪明的模型能减少完成任务的总轮次，因为智能体能更高效地规划和发起工具调用。这往往能抵过它们更慢的 token。如果你的查询偏复杂，或生产显示每个任务超过约五个轮次，那么"更快"的模型常常就是"更聪明"的那个。具体是哪个取决于你的流量，所以要按下面"选择模型"一节所述，通过扫描来决定。
* **让模型并行调用互相独立的工具。** 商务用例常需要并行执行许多操作：搜索多个商品、查询多份政策文档，或从多个销售数据源获取记录。并行工具能确保多个独立查询不额外消耗轮次。提示模型在一个轮次内调用多个工具，并把结果作为一个 tool results 数组在一条用户消息中返回（参见[并行工具使用文档](https://platform.claude.com/docs/en/agents-and-tools/tool-use/parallel-tool-use)）。

#### 更快工具

* **优化工具自身的后端。** 有时工具确实需要展开——商家智能体的"获取今日快照"查询会以三次独立调用读取销售、库存和活动状态。但我们经常看到工具边界变成拼凑缺失后端逻辑的地方：一次可用性检查先调用商品目录查 SKU，再调用各门店的库存服务，再调用履约服务查截单时间，然后在工具自己的代码里应用替代规则和自提资格，最后才回答。这个工具现在已经塞满领域知识，规则一变就难以保持正确，还承载着本应位于上游系统的逻辑。当你发现自己在工具里写这类逻辑时，解决办法就是一个能回答该问题的后端端点，然后用一个智能体工具去调用它。
* **立即派发工具。** 工具参数会像其他 token 一样从模型流出，因此 harness 可以在某个工具的参数完成时就执行该调用，并在模型仍在流式输出其他并行工具或内容块时处理它。我们见过这能把数秒的空档压缩到几百毫秒，[Claude Agent SDK](https://code.claude.com/docs/en/agent-sdk/overview)默认就这么做。为了最大化延迟收益，你应当提示模型先发出它最慢的那个调用。

![](https://assets.claude.com/6d1b82ec4129e3eae6932ab4dea06dd3fc1c274e.gif)

### 感知延迟

感知延迟是用户感到"屏幕有反应"之前的时间。它在面向消费者的用例中尤为关键，因为任何交易摩擦都会影响结账率和收入。有两种技巧可以在不触碰模型的情况下缩短它：

* **组件一成形就流式下发。** 一个渲染出来的商务响应通常是 500–700 个输出 token，不开流式就是五秒以上的转圈。把呈现工具的每个参数在流式过程中发给客户端，渐进式渲染页面。
* **展示过程。** 智能体收集上下文时，用大白话为每一步渲染一行简短进度（例如"正在寻找水边的酒店"）。你可以从工具的现有参数构建它（比如商品搜索的查询），或额外加一个 user_facing_message 参数，提示模型来写这一行。

![](https://assets.claude.com/0a23449decd51d4ed8785a700a1e117db2d3f39f.gif)

上面两个面板运行的是同一个智能体、同样的工具和提示词，只有 harness 不同。总时间差不多，但用户看到"有东西"的时间差别很大。

### 提示词缓存

提示词缓存是你最大的降本候选，而商务流量非常适合它。缓存输入 token 的读取成本是全新 token 的十分之一；虽然缓存写入有约 1.25 倍的溢价，但一个被缓存的前缀在第二次使用时就已经回本。在流量巨大的面向消费者应用中，你有独特的机会用最便宜、默认 5 分钟的缓存过期时间，达到非常高的缓存命中水平。

我们见过的最佳商务部署运行在 90–99% 的缓存命中率，这就是你应当从一开始就按之设计的区间。我们的经验还显示，在约 10 万 token 规模下，缓存 token 的读取大约快 1.5 到 2 倍，而且 token 越多，这种加速基本呈线性扩展。

缓存是基于前缀的。一个请求会从缓存中读取，直到第一个与先前请求不同的字节为止，所以重要的不只是上下文里有什么，还有它的顺序。把请求想成三段，按变化频率排序：

* **全局段**：系统提示词和工具定义的大部分，在每个会话中完全相同。这是你最热的缓存，在规模下很可能不会过期。让它在各轮次、各会话之间保持字节级一致，并在其末尾放一个缓存断点。
* **会话段**：按用户的上下文和对话历史，在不同会话间不同，但在一个会话内保持稳定。这一段位于全局段之后。
* **易变段**：会话内会变化的任何内容，例如当前时间或当前页面。把它放在请求的最末尾：可以作为最新一轮用户消息中的带标签块，或者在支持[对话中途系统消息](https://platform.claude.com/docs/en/build-with-claude/mid-conversation-system-messages)的模型上，作为追加到 messages 数组的 system 角色消息。我们见到最常见的错误，是把时间戳或当前页面放在系统提示词顶部，这会悄无声息地在每个请求上破坏缓存。

![](https://assets.claude.com/e6fbdecfcdda588a29d70f54cde5c09d17a921aa.png)

这里有两点实现细节要记住。第一，技能应当作为工具结果加载，而不是附加到系统提示词。这样技能正文落在对话前缀中，并随之被缓存。

第二，每轮把断点向前滚动：一个请求允许的断点数量有限，所以要把最新的断点移到每一轮用户消息末尾。这样每一轮都能从缓存读取累积的历史，包括搜索响应这类很长的工具结果。

![](https://assets.claude.com/bdf3f158eeed3dc122c1bb2d04eee5343405ca93.png)

### 选择模型及其配置

[模型规模和 effort 设置](https://claude.com/resources/articles/claude-model-and-effort-level-in-claude-code)是同一个权衡——智能对延迟与成本——两者都应当通过测量来选择：

1. **选定指标和底线。** 选定你业务所依赖的质量指标（任务完成率、答案相关性、有据准确率），你不会低于的 eval 分数，以及你的 p50、p99 延迟和成本预算。
2. **扫描。** 把你整个 eval 套件跑遍你考虑的*每一个*模型和 effort 等级。我们建议商家智能体从 Opus 起步，因为其任务偏重分析；消费者智能体从 Sonnet 起步，因为延迟权重更高。如果你有生产流量，按真实查询构成对结果加权。然后让数字来决定。有时 Opus 5 在驱动购物车的任务上的提升，足以证明它相对 Sonnet 的成本差是值得的；有时则不然。
3. **仔细读结果。** 有两件事经常让团队意外。第一，提示词是针对某个模型调校的，所以用同一份提示词做扫描，可能会让并非为它编写的其他模型表现不佳。更小的模型通常需要当前模型能自行推断的指令，而更大的模型会严格照做更小模型原本忽略的指令。在排除任何一个候选之前，对它的失败案例做几轮迭代是很便宜的一步。第二，更智能的配置有时在延迟上反而胜出（最常见于 p90 和 p99），尽管它的 token 更慢，因为它能更好地规划工具调用，在最复杂的请求上需要的轮次更少。

衡量"每个已完成任务"的成本，而不是每次模型调用的成本，因为一个需要更多轮次、或失败更频繁的便宜模型并不便宜。当结果接近，且成本符合你按任务的经济模型和延迟要求时，选更智能的那个。质量才是驱动采用和留存的东西，也为未来 6 个月随模型变强而构建留出空间。

## 03 在生产环境中运行

记忆、安全、eval，以及如何在组织内扩展这项工作：这些决定了一个智能体能否走进生产，并留在生产。

最后，我们谈谈什么能让智能体通过生产考验：记忆、安全、eval，以及如何在组织内扩展这项工作。

### 能穿越会话的记忆

你与客户的关系和互动很重要。记忆让智能体从上一次对话中断的地方继续，而不是从零开始。一位在三月提到过坚果过敏的购物者，不该在六月再重复一遍；一位每周一查看同三个活动数据的商家，也不该每次都重新点名。长期记忆——应当跨会话存续的事实——是一个你要构建的系统，包含三部分：事实如何存储、如何写入、如何读取。

#### 存储记忆

记忆属于你的系统，而不是模型。

当档案很小、且智能体是唯一读者时，一个扁平的 markdown 档案就够了。大多数生产级商务智能体会很快超出这种规模，实际可行的替代方案就是你已经在运营的数据库。一条事实就是一条小型的带类型记录：一个 key（例如 shoe_size、default_store、preferred_report_cadence）、一个简短的值、一个类别，以及它来自哪个会话。有些 key 你事先定好，每个用户都有；其余由提取器发现。数据库在存储增长时仍可查询，让你能针对特定属性构建确定性行为，并与你已有的用户数据关联。

对面向商家的智能体，记忆要按人而非按账号索引。商家登录账号常常在多个操作员之间共享，因此每个操作员都需要自己的档案，读取时必须遵守该操作员的权限：门店经理的智能体不应回忆起区域经理陈述的事实。

在商务领域，智能体记忆包含个人数据。值得记住的事实往往正是受监管最严的那些，而不同司法辖区的规则各异。要把记忆当作一个数据处理设计问题，而不只是存储问题。实践中这意味着四件事：

* **决定你愿意持有哪些类型的记忆。** 在写入路径上强制执行——每次保存都要通过一个校验器——而不是只写在提示词里。
* **给用户查看、更正和删除已存内容的途径。** 把删除接入你的账号注销和数据请求流程。
* **设定保留期。** 几年前的偏好很可能已经过时，保留期有助于让记忆中的事实保持新鲜。
* **记忆应当是可按部署关闭的开关。** 这让无法承担这些义务的地区可以在不启用记忆的情况下运行。

#### 写入记忆

异步写入记忆。在每轮结束时，或在长会话中每隔几轮，一个运行在独立线程或进程中的智能体读取对话，在存储中创建、更新或删除事实，并在会话推进过程中维护自己的工作上下文。

它不给对话延迟增加任何负担，并在我们内部的商务记忆 eval 套件上实现了高出 13% 的事实召回。

显而易见的替代方案——让智能体调用一个工具来保存事实——对延迟敏感的商务智能体来说是错误的选择。每次保存都是面向用户的轮次里的一个工具调用；除非整个存储都在上下文中，否则一次保存需要先读取以便更新或去重，而这又是单独的一轮。

这还会在每一轮把一个额外的决策摆到智能体面前，而在我们的 eval 中，这种对注意力的竞争表现为漏记记忆。

把提取器分离出来，还能让你精确地为它写提示词。它只读用户和助手的文本，从不读工具结果，因此商品描述或评论不会变成关于用户的事实。它的提示词说明什么算事实——用户声明的尺码、饮食限制、履约偏好、商家常用的物化视图——什么不算，比如任何来自商品条目的内容或一次性细节。

![](https://assets.claude.com/516a22932c1a2eea15f8ad38c385e479e1b37408.png)

#### 读取记忆

记忆分三层读取。

|  |  |
| --- | --- |
| **始终在上下文中** | 一小组固定的事实每轮都进入上下文：几乎每个请求都依赖的那些，例如购物者的默认门店和履约偏好，或操作员所属门店与角色。 |
| **按轮次预取** | 与当前请求相关的事实每轮预取，信号与预加载技能相同：一次鞋子搜索会拉取尺码和品牌偏好，一个活动相关问题会拉取该操作员常用的指标。 |
| **放在查询工具之后** | 其余一切都放在一个查询工具之后。 |

由于记忆是按用户的上下文，它全部位于会话段，处于全局缓存断点之下。

### 安全：执行发生在 harness 里

提示词是安全行为的起点，但在商务领域，它不能是安全被执行的地方。这里的失败是财务性的，而且往往不可逆；一条提示词规则，只差一次注入或一个坏样本就会被跳过。下面每条规则都在代码中强制执行，同时作用于消费者智能体和商家智能体，并且只定义一次，让每个运行时共享。

#### 模型只暂存；由人或策略来执行

没有任何模型工具调用能移动资金或改变业务。下单、支付、退款、改价和活动启动，最终都落在由 harness 而非模型控制的动作上。

在消费者一侧，这是结构性的：结账工具渲染购物车并附带一个下单按钮，而智能体调用的后端接口根本没有扣款方法。

在商家一侧，每个写工具都会产生一个带服务器生成 ID 的暂存变更，而 `apply_change` 只对经过真实界面批准的 ID 生效：操作员门户里的按钮、CLI 中的确认，或当智能体运行在 Claude Managed Agents（托管智能体）上时平台自带的工具批准提示。

这些护栏在 apply 时按当前限制重新检查，而不是按变更暂存时生效的限制。无论界面是什么，形态都一样：模型能做的最危险动作是提出建议，而批准走的是你业务中此类变更本就在用的 maker-checker 流程。

#### 写入与渲染只接受服务端签发的 ID

harness 按会话记录服务器交给模型的每一个 ID，而这份记录是任何写入或渲染唯一接受的键。

购物车只接受服务器返回给本会话的商品 ID；商家工具只接受智能体实际读过的商品条目和活动 ID。以任何其他方式出现的 ID——幻觉出来的、用户粘贴的、埋在评论里的——都会在后端看到它之前被拒绝。

同一条规则覆盖 UI。呈现工具接收 ID，由服务器自己填充商品、订单或变更记录，因此卡片只会渲染服务器自己填充的记录。

它也覆盖受托方：商家分析子智能体可以读数据，但永远不会扩充智能体可写入的 ID 集合。

对于费用、披露声明和其他受监管内容，模型只选择要披露哪个产品，服务器从已批准的文案中提供每一个字。相同的费用字段在商家智能体的保护清单上，因此柜台两侧都无法更改或改写它们，而 eval 会逐字节检查渲染出的字符串。

#### 有上限的交易必须能顶住重复请求

大多数商务界面都对单个用户可购买某项商品的数量设了上限——为了票务配额、促销定价或反欺诈——而智能体会以人类点击按钮时从未有过的方式重试、改写和并行。

因此上限按"写入之后"的行来执行，这样第二次"再加两个"就无法叠加越限；同时一个会话的购物车写入是串行的，因此单个轮次内并行的工具调用无法合起来超过上限。

商家变更也以同样方式检查：价格变动幅度、折扣深度、补货数量和活动预算的上限，再加上一份任何变更都不得触碰的保护字段清单。这条规则可以泛化：对结果状态而非请求本身执行每一项限制，并按会话串行化写入。

#### 第三方内容经过净化

在商务中，大部分上下文由不是你的人写成——卖家、评论者、竞争对手——所以每次后端读取都是不可信输入，都要经过同一个净化器。

每一个由第三方编写的工具结果——商品条目、评论、政策、卖家消息和已存记忆——都会在模型看到之前被净化，并包裹在带固定标签的围栏中。

净化器会剥离控制字符和双向字符，移除任何模仿围栏标记的内容，拆解模仿对话轮次或工具调用的文本，并限制大小——目的是阻止恶意商品条目冒充系统或塞满上下文。

提示词承载契约的另一半：围栏内的文本是供汇报的材料，永远不是行动依据。

### eval：发布一个非确定性系统

从一处小的提示词改动到一个新工具，任何东西都可能以难以预测的方式改变智能体行为，而真正导致回归的往往不是你以为在发布的那项改动。eval 就是你在部署之前发现这一点的方式。我们此前关于[智能体 eval](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)的博客文章讲了一般做法。本节讲商务智能体的具体要点。

**评估快照，而不是对话**

模型的 API 是无状态的，因此智能体输出是系统提示词、工具和 messages 数组的函数。这意味着商务对话能到达的任何状态都可以被直接构造出来。所以创建一个 eval 用例，就是构造测试状态、追加测试用户消息，然后让智能体从那里开始运行。

然后评估结果：最终状态和渲染出的响应，包括最后一次写入的参数。在大多数情况下，我们不建议评估智能体到达该结果的路径，因为这类测试用例很脆弱，而且限制太强。

模拟用户 eval——由第二个模型扮演用户、再由一个裁判模型给整段对话打分——是很差的测量工具。两个非确定性系统交互需要更大样本、每次试验成本更高、更难评判，产生的失败也难以归因。它们适合用来发现覆盖缺口、对智能体做整体的"体感检查"，所以用它们来发现用例，然后把每个用例写成快照。

![](https://assets.claude.com/ec6ed374de1ca7aef245c7994c762aed2f709319.png)

#### 评估在困难条件下的行为

大多数团队没有正确测试注入的状态。一个用例应当编码失败的前置条件，而不仅是任务本身。如果某种行为只在经历了带有多个工具调用的繁忙首轮之后才出现，或在会话早些时候出现矛盾之后才出现，那么一个从干净状态开始的用例在任何配置下都会通过，提供不了有意义的数据。

我们观察到大多数套件都严重偏向这类干净状态用例，所以要确保你有一部分用例从冗长、杂乱或互相矛盾的历史开始。

#### 覆盖不同类型的商务智能体 eval

有效的评估要求同时测试期望行为和不期望行为。

为每个正例写下它的反例：每一个"应该拒绝"都配一个"应该服务"，每一个"应该先问"都配一个"应该直接做"。缺少反例是我们在套件中发现的最常见缺口。

评估以下内容：

* **构成你大部分流量的核心请求**，因为这里失败会影响大多数会话。包括简单查询、多约束请求、商品与套餐问题、多意图消息。对于问题类请求，检查每一个价格、可用性和属性都能追溯到返回的数据，并检查智能体在数据缺失时会说明，而不是编造。
* **依赖上下文的请求**，例如引用屏幕上内容、延续自早前轮次的约束、针对已有购物车的写入。评估记忆也属于这一类。检查记忆是否被提取、被检索，并改变了答案。
* **安全与品牌用例**，失败会损失金钱或信任。包括注入尝试、读取其他用户数据的尝试，以及受监管措辞——后者逐字节检查。把注入拆成两类：用户自撰注入，指令来自用户自己的消息；数据面注入，指令埋在通过工具结果到达的商品名、评论或网页片段里。
* **界面评估**，确保渲染了正确的组件、尊重了数量上限、面向用户的文本里没有内部标识符。也要测试超时和空结果。
* **同时属于多个能力的请求。** 一位操作员问："如果我把这个降价 15%，我的库存够覆盖需求吗？"这既是定价问题，也是库存问题。正确答案会暂存降价并附上库存预测；错误答案只做一半、跳过另一半。按能力分别编写的 eval 抓不到这种情况，因为每个只评自己那一半。为需要两个相邻能力协同的请求编写用例，并评估答案的两半。

#### 与领域专家一起写 eval，并使用真实事故

与亲眼看到失败的一线领域专家（SME）合作设计测试用例，比如产品、法务、商家运营、客户服务和品类管理团队的成员。真实失败是最好的 eval，每个用户流程 50–100 个 eval 用例是一个不错的起点。

确保用例多样，如上面所述。生产转写文本是获取新用例——尤其是那些棘手用例——的绝佳来源。编码智能体擅长生成额外用例和对抗变体。[参考仓库](https://github.com/anthropics/commerce-agents)包含一个 Claude Code 插件，其中有一个按我们推荐方法构建的 eval 编写技能。

#### 在大型组织中发布

在商务企业中，智能体由许多工程团队共同构建。搜索、结账、定价、营销技术、客户服务和商品目录平台各自拥有智能体所依赖的系统，各有自己的发布节奏，每个团队都想新增或修改一个工具、一个技能或一条提示词规则。

与普通服务不同，智能体没有严格的模块边界来保护其他部分：定价团队做的一处改动，与结账共享同一个上下文窗口。

诱人的解法是把系统拆成许多子智能体，每个业务单元一个。如第 1 部分所述，出于质量原因我们不推荐这样做。作为替代，我们给出一个降低多团队协作风险的流程：

* **所有权跟随系统。** 每个技能和工具都有唯一的负责团队。例如，定价团队拥有促销工具和定价技能，客户服务团队拥有订单与退货工具以及 customer-care 技能。共享提示词由单一平台级负责人负责通用部分，由领域负责人负责领域特定段落。
* **变更随其用例一起发布，CI 运行为之选定的一组用例。** 贡献技能的团队也要贡献它的用例，包括反例和与相邻技能的边界用例。每个 pull request 都跑全量套件太慢、太贵，无法长期维持，所以从中构建一个 CI 子集。该子集由一组核心用例（最高流量的请求）加上全部安全用例组成。在此之上，再运行变更所触及部分的用例。对技能而言，是它自己的用例和相邻技能的边界用例。对工具而言，是每一个调用它的用例。对共享提示词而言，是完整的 eval 套件，因为一切都读系统提示词。我们建议把关时看多次试验的通过率、缓存命中率以及每轮成本。每晚以及每次发布前跑全量套件也是好做法。跨团队回归会在这些运行中被抓住。
* **智能体也应当进入发布日历。** 它是一个部署单元，所以一个坏变更会立刻触达所有用户。提示词和技能变更先向金丝雀用户组灰度，保留一个无需部署即可关闭某个技能的开关，并在高峰期之前像冻结其他系统那样冻结智能体。

关于这种安排中人的一面，参见[构建高效的人机团队](https://claude.com/resources/articles/building-effective-human-agent-teams)。

## 04 展望

本文描述的大部分内容与模型无关。工具调用你已在运行的系统，技能编码你已在遵循的流程，eval 是你的产品需求文档写成了测试，harness 执行的是你对任何客户端都会执行的政策。模型会持续变好，当更好的模型发布时，我们描述的架构只需一次配置变更加上一轮 eval 扫描就能采纳它。其余部分继续照常工作。

同样重要的是思考你的产品界面路线图。这套架构会比聊天面板活得更久。同一个智能体可以运行在语音之上，也可以在票价下跌时、用户开口之前主动行动。对于已经拥有 eval 和工具的团队来说，这些是表现层项目。再往前看，你店铺的一部分流量将来自代用户购物的智能体。正是那些让你的智能体不越界的来源校验、暂存与批准规则，让你能够安全地把工具开放给这些智能体。

商务一直奖励那些把购买过程做得尽可能顺滑的人。智能体让这件事容易得多。去看[完整的参考实现](https://github.com/anthropics/commerce-agents)，其中包含消费者智能体和商家智能体，以及面向零售、旅游、电信和娱乐的可运行示例。
