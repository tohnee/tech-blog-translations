# 构建智能体：何时把子智能体并入主智能体循环

> 原文：[Building agents: When to fold subagents into your main agent loop](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop) · Claude 博客

在 Claude Platform 上构建智能体时，少用子智能体、改用渐进式披露的上下文和工具，可以在降低成本与延迟的同时提升质量。以下是何时迁移、以及如何迁移。

*如果你在 Claude Platform 上构建的智能体包含多个子智能体，可以借助我们的[迁移工具包](https://github.com/anthropics/single-agent-loop-kit)看看哪些子智能体适合并入主智能体循环。它会以引导式工作流识别你的模式、评估替代方案并验证最佳做法。其中还包含一个演示，你可以在模拟系统上先试，再对自己的智能体运行。*

子智能体——拥有自己的上下文窗口、工具和指令、[由协调者编排](https://claude.com/resources/articles/multi-agent-coordination-patterns)的智能体——是智能体设计的核心组件。它们在验证、并行工作和模块化权限管理方面很有效。我们在自己用 Claude Platform 构建的许多智能体中都在使用它们，例如我们的[多智能体研究系统](https://www.anthropic.com/engineering/multi-agent-research-system)。

然而最近，应用 AI 团队发现有一类企业智能体部署，能从把路由器、规划器和领域子智能体并入主智能体循环中获益。在[我们对多个企业部署的对比](https://claude.com/resources/articles/the-anatomy-of-effective-commerce-agents#:~:text=In%20our%20comparisons%20across%20several%20enterprise%20deployments,latency%20per%20task)中，[一个带技能的单一智能体](https://claude.com/resources/articles/building-agents-with-skills-equipping-agents-for-specialized-work)在质量上经常胜过“一个提示应对一切”的设计和子智能体设计，而且往往每任务成本更低、延迟更低。

例如，有一家公司发现，其面向客户的智能体中的十几个专家子智能体，让保持一致的品牌体验变得困难，还增加了损害用户体验的延迟。

我们也经常看到一些提案中的智能体设计遵循一种熟悉的递进：意图分类器、固定的多步推理流水线、用户分群桶、各自独立的推荐分支，最上面再压一个多智能体编排器。

在这些情况下，我们通常给出的反馈是：这套结构的大部分都在做模型已经不再需要别人替它做的工作；一个清晰的系统提示、4–5 个轻量的数据工具，再加上严格的输出防护栏，就能覆盖大部分用例。

![子智能体设计](https://assets.claude.com/a7cb2cf08bfcef461166310c0c55f28b72c33b0d.gif)

需要说明的是，子智能体仍有自己的位置，包括在研究前沿。在以下情况下使用它们：

* 单一智能体循环因上下文膨胀而出现可测量的性能下降；或
* 多个任务需要并行处理，且各自使用全新的上下文窗口、任务完成后即可丢弃；或
* 单一智能体难以选出合适的工具，或系统提示中存在相互冲突的指令。

但我们太常看到企业给每个团队或每类问题都配一个自己的子智能体，结果智能体架构变成了组织架构图的复制品（康威定律在起作用）。

本文结合我们在大组织中构建智能体的经验，说明何时应考虑把子智能体并入主智能体循环，并给出最佳实践。

## 大型组织的智能体构建失败模式

公司常常想要构建一个智能体，把多个产品和能力统一到同一个客户界面里。

通常每项能力由一个独立团队负责，于是公司先让各个团队分别构建自己的智能体，再由一个中央平台团队在最上面构建编排器。这可能有几种结构，包括编排器-子智能体，或一个单一智能体把特定智能体以 MCP 工具的形式暴露出来。

这看起来是最简单的方案，但会立刻在以下几方面引入复杂性：

* **上下文管理：** 你需要决定智能体之间交换哪些上下文，而在来回传递中常常丢失细节。
* **子智能体泛滥**：每个团队都交付自己的子智能体，于是公司最终拥有数百个相互重叠、没有强制执行标准、也没有明确归属的子智能体。
* **弗兰肯提示词（Frankenprompt）**：每个团队都往系统提示里加一句，结果规则互相冲突、没有一致的语气。
* **未经审核、过度本地化的评估**：每个人都加自己的评估，且过度针对自己的子任务优化。没有人拥有或维护整套评估，而管理层却基于被稀释、过度本地化的分数做决策。
* **延迟**：多智能体架构的复杂性会增加延迟。一位客户用单一智能体循环对比其多智能体执行框架，结果后者的运行时间约快 2 倍。

## 使用带渐进式披露的智能体循环

上文描述的编排器-子智能体设计，是协调跨团队构建的专家能力的一种合理方式，但通常更有效的做法是**通过技能渐进式披露上下文**，以及**通过工具搜索（tool search）渐进式披露工具**。换句话说，智能体看到的只是技能和工具的简短描述，只有需要时才完整加载。

这种做法合理，原因有三：

* **共享上下文能产生更好的答案：** 对运行时间较长的智能体，我们希望来自几个不同任务的上下文都留在主上下文窗口里。一个见过前面每一步结果的智能体可以把它们连接起来，从而产出比“由子智能体交回一组摘要”更丰富的结果、更好的洞见。这也意味着[更少的上下文窗口、更少的有损交接](https://claude.com/resources/articles/building-multi-agent-systems-when-and-how-to-use-them)。
* **渐进式披露能防止上下文膨胀：** 这种技术让团队可以构建能够完成多种任务的单一智能体，而不必把所有上下文立刻塞进一个长长的系统提示里。这就消除了团队过去把工作拆给子智能体的主要原因。事实上，我们[把面向更先进模型的 Claude Code 系统提示缩减了 80% 以上](https://claude.dev/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models/)，其中就包括与渐进式披露技能和工具相关的削减。
* **模型能力更强了：** 从 Opus 4.5 开始，模型在单个循环中能管理的东西远超大多数团队的预期。Opus 5.5 和 Fable 5.1 的思考无法关闭，而最近的模型越来越会边做边叙述进展、边做边自查，这让某些执行框架要素变得多余。每一个新模型都让你能把更多决策从执行框架移到模型本身。更简单的循环也更容易迁移到下一个模型；在我们帮助客户完成的迁移中，僵化的多智能体结构常常正是阻碍新模型承担更多工作的原因。

单一智能体循环的设计需要自律：精心管理的系统提示、能在恰当时机触发的技能与工具描述，以及对上下文窗口、记忆和记笔记的刻意处理。本文后续章节会深入讨论迁移和设计方面的考量。

应当由一个中央团队负责端到端质量和系统提示，并在每个新工具和评估上线前进行审核。让这个中央团队保持精简，有助于快速迭代，并降低大组织内部的协调成本。

如果你选择多智能体路线，就从可能可行的最简单模式开始（生成器-验证器、编排器-子智能体，或其他）。要有效地划分边界，可以**按上下文划分：给每个子智能体一块几乎不需要系统其余部分的工作，并让它交回一个紧凑的结果**（合适的候选包括独立的研究路径、接口清晰的独立组件，或黑盒验证）。当智能体按问题类型拆分时，它们会玩起“传话游戏”，信息来回传递，每一次交接都降低保真度。

## 如何把子智能体并入主智能体循环

许多团队已经在生产环境中有一个编排器和一组专家智能体。以下是我们建议逐步靠拢的单一循环设计：

* 一个模型、一个上下文窗口，运行一个开放式的工具循环，各项限制（回合与成本预算、写入闸门）在执行框架中设置。
* 每个回合，模型发出一批工具调用。执行框架并行运行它们，并把原始结果返回给同一个模型，由模型决定下一步：再发一批、向用户提问，或给出答案。
* 当模型给出答案或触及[预算](https://platform.claude.com/docs/en/build-with-claude/task-budgets)时循环停止。答案之后可以选择运行一次目标检查或验证器检查。
* 模型在第一个回合就把计划写进上下文，并在结果到来时修订它。这是相对编排器加专家智能体架构的主要变化：写计划的模型同时也是执行计划的模型，因此它可以在回合中途改变计划。
* 上下文仍然会被加载，但由智能体自己管理：
  + 不再需要“按规则目录重写计划”的代码步骤，因为每一步都由模型决定。
  + 排序和领域流程移入**技能**。
  + 硬性限制（校验、审批闸门）以及对话中途出现的其他事项（例如记忆查找）移入**工具**。
  + 代码仍然可以用于加载那些成本低、几乎总是相关的东西（例如实体解析步骤），也可以在循环调用的工具内部处理任何机械性的部分（负载构造、流解析、恢复澄清流程）。

这种单一循环设计也有助于实现许多团队正在追求的终态（一个能理解用户高层目标并代表其行事的智能体），因为它把智能体学到的一切都留在一个上下文里。

下面的建议说明了团队如何分阶段地从多智能体系统走向单一智能体循环，以及多个团队如何在过程中持续为该智能体做贡献。

### 任务完成度评估

第一步是建立一套评估集，用来判断某个子智能体是否应该并入主智能体循环。我们见过有效的评估结构是这样的：一套由中央团队拥有的共享端到端评估集，加上每个技能由所属团队随技能一起交付的较小评估集。哪怕只有 10 个黄金示例，也足以起步。

按评分标准给智能体的最终消息打分，是跟踪答案质量的好起点。在你还拥有编排器时，还应跟踪路由准确率（它是否选对了子智能体？）。一旦某个子智能体被并入，就改为检查智能体是否加载了正确的技能、或调用了正确的工具。逐步走向任务完成度评估是有帮助的，因为在比较不同架构时，这一点最重要。

在内部系统难以重放、用户参与难以模拟的环境中，这会很复杂。我们在内部行之有效的一种做法是：给重要事件记录时间戳，以便日后重放，作为针对性的评估来运行。

### 逐步减少子智能体

向单一智能体循环演进，意味着把子智能体并入工具和技能。这可以通过合并领域子智能体、把它们作为工具调用，或用技能和工具替换它们来实现。

![并入子智能体](https://assets.claude.com/ed6bd97496ffdab88763806d9e14f1ec61ed9255.gif)

### 合并领域智能体

在第一次合并之前先构建一套小型的端到端评估。然后**按共享上下文并入，从使用最多的子智能体开始。**

[合并那些](https://claude.com/resources/articles/building-multi-agent-systems-when-and-how-to-use-them)彼此串联在对方输出之上、触及同一份数据、或经常被一起调用的专家。例如，如果生产流量中有相当一部分是某个专家之后紧跟另一个专家，那就是一对紧耦合的组合，可以作为合并成一个领域智能体的候选。

### 以工具形式调用子智能体

当上述三个条件之一成立、而你选择保留某个子智能体时，让主智能体以工具形式调用子智能体往往很有效，这样主智能体可以继续与用户保持对话。

我们只推荐在子智能体需要直接与用户交谈时做完整交接——由子智能体接管对话。其他一切都可以是主循环中的一个技能加若干工具。

这样你就可以为子智能体定义[共享的响应 schema](https://claude.com/resources/articles/structured-outputs-on-the-claude-developer-platform)，由主智能体用真实数据验证结论，并为任何最终的汇总步骤裁剪输入。这是一个很好的第一步，因为你不需要**重写**这些子智能体。它还能在决定把任何子智能体并入主智能体之前，给你一个任务完成度评估的**基线**。

不过，有些失败模式仍会存在：

* 每个专家都有自己的提示、上下文、归属团队和评估
* 每次调用仍然交回一份有损摘要
* 每次调用都是一个嵌套的模型循环，会增加延迟

### 通过技能和工具把子智能体并入主智能体

一次一个地把子智能体并入主智能体：把每个子智能体的提示变成技能，把它的 API 调用变成 MCP 工具。对比有该子智能体和没有该子智能体时的评估表现，再决定保留哪些。

做对比时，不要只看最终分数，还要看哪些任务的结果翻转了。我们在一个示例客服智能体上测试时，把一个子智能体并入另一个子智能体降低了延迟，但也弄坏了一个原本通过的流程：主智能体自己握着订单查询工具就直接作答了，没有向物流专家询问送达日期。

在每次改动之前，确保你的评估覆盖了生产环境中会一起运行的每一条智能体链路，以及智能体绝不能违反的每一条规则；并且每个任务要运行不止一次——因为像刚才这种破坏，两次运行里只出现了一次。

## 多个团队如何为一个智能体做贡献

领域推理可以从知识库、技能和 MCP 工具中获取。各个团队可以把归属对象从智能体转为技能和工具，由一个小型中央团队保留对系统提示和端到端质量的归属。这涉及在每个新技能、工具和评估上线前进行审核。

### MCP 工具

当智能体需要采取行动、从系统读取实时数据，或以固定形状返回结果时，工具就是合适的选择。在迁移过程中，你也可以用工具来继续调用子智能体。我们建议按用户意图对工具分组（而不是每个 API 一个工具），因为一旦系统提示中的工具定义超过 30–50 个，工具选择往往就会退化。

使用带延迟加载的[工具搜索](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)，限制硬性前置条件，并把任何需要的前置条件移入工具内部。例如，如果 Y 需要 X 的输出，Y 的工具就检查它是否存在，并返回一条模型可以据此行动的指令。按用户的权限也是同样的道理：每个工具检查调用用户可以看见什么、可以做什么，并返回一条模型能读懂的明确拒绝，因此一个循环就能服务不同访问权限的用户，而不必为每个权限级别单独配一个智能体。

### 技能

当智能体需要知道某个团队如何工作时——比如过去由专家子智能体的提示所承载的步骤、规则和判断——技能就是合适的选择。

我们扩充技能库的做法，是把维护工作交还给编写技能的人。Claude 可以借助那些能够构建、测试和裁剪其他技能的技能，承担繁重的部分。

为防止技能泛滥，可以让每个团队的直接负责人（DRI）拥有自己的技能，并确保它们制作精良、彼此不重复，且随附合适的评估。

* **`/skill-creator`** 让你编写一开始就格式良好的新技能，并审计现有技能以进行裁剪、去重和重构。
* **`/skill-doctor`** 让你看到技能库中每个技能的代价以及它实际被使用的频率，并删掉无用负担。

### 知识库

当智能体只是偶尔需要某些参考资料时，知识库就是合适的选择。事实和参考资料（政策、指标定义、产品规格）可以放在模型会调用的搜索或查找工具之后，也可以作为参考文件随技能一起交付。要[避免让代码去检索这些上下文并粘贴进提示里](https://claude.com/resources/articles/seeing-like-an-agent)。

## 加速这项工作的工具

我们最近[发布](https://code.claude.com/docs/en/commands)了一组 Claude API 技能，可以协助完成上述大部分工作。我们的[迁移工具包](https://github.com/anthropics/single-agent-loop-kit)把这些技能串联成一个引导式工作流，用于评估多智能体系统并将其迁移到单一智能体循环。其中包含一个演示，你可以在对真实系统运行之前先试一试：

* **`/claude-api build-eval`**：可以帮助创建第一套由中央团队拥有的端到端评估集，或各团队随技能交付的小型评估集
* **`/claude-api prompt-audit`**：可以标记出你的提示、技能和工具描述中那些为旧模型编写的指令，并以 diff 形式提出修改建议。你可以把它跑在系统提示上，找出那些为更早的模型添加、如今却让智能体更慢或更僵化的规则。各团队的 DRI 也可以对自己的技能和工具描述运行它。
* **`/claude-api hillclimb`**：可以针对现有评估迭代改进应用。它可用于“并入 vs 保留”的对比（把一个子智能体并入技能加工具之后，让它在技能和工具描述上迭代，看并入版本能否追平或超过该子智能体），也可用于你的系统提示。
* **`/claude-api cost-optimize`**：分析你的调用都花在哪些地方，并从提示缓存、裁剪不需要的输入与输出 token、努力等级、模型选择等选项中提出节省建议，一次只改一项。它有助于在给定设计下降低成本和延迟。

随着模型演进，我们对如何最好地使用它们的理解、以及围绕最佳实践的指导也在演进。因此，任何单一架构都没有它背后的原则重要：度量、一次只改一项、保留经得起检验的东西。

眼下正是这样一种情况。随着模型能力提升、智能体运行时间变长，你越来越多的子智能体可以变成技能和工具。不过你不必一步到位。先构建一套小型的端到端评估，并入一个子智能体；只有当并入版本得分更差时，才把它保留为子智能体。然后重复这一过程。
