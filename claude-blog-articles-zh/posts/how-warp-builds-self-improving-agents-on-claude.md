# Warp 如何基于 Claude 构建自我改进的智能体

*在本系列中，我们聚焦初创公司如何用 AI 变革各自的行业。本文将分享 Warp 如何把无状态的用户反馈转变为智能体的自我改进回路。*

智能体需要可靠且高效地处理重复性任务。一个只能把任务做对 80% 的初版提示，可能给用户带来嘈杂而恼人的体验。Warp 在惨痛教训中认识到了这一点，并以此指导其产品策略，为全球近 100 万开发者打造了更好的体验。

Warp 是一个 AI 驱动的终端和智能体开发环境，构建于 Claude Platform 之上。团队在其内部代码审查智能体上就遇到了这种「嘈杂体验」问题。工程师们抱怨智能体给出毫无帮助的评论，产出质量低下。

团队起初尝试了一些权宜之计，比如根据观察到的代码审查失败案例手动重写提示。这让产出更可用，但无法扩展。改进 AGENTS.md 之类的上下文文件也有帮助，但远算不上彻底的修复。

最终他们意识到，真正的问题在于：无论智能体用于什么目的，对它的反馈通常都会在会话结束时消失，关键上下文就此脱离了智能体循环。他们的解决方案是：一个基于 [Agent Skills](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview) 的框架，用来创建自我改进的智能体——反馈随时间不断累积，持续打磨和增强智能体的产出。

请继续阅读，了解他们如何在 Claude Platform 之上用 Skills 构建这套机制。

## **基于 Skills 的智能体自我改进回路**

核心技术是一个使用 [**Skills（技能）**](https://support.claude.com/en/articles/12512176-what-are-skills) 的自我改进回路——Skills 是以文件形式编码的知识，让指令不必直接写进原始提示里。Warp 逐步演化出一种自我改进的智能体架构，由两个 Skills 组成，中间以人类反馈相连。

**内层/基础 Skill（inner/base skill）**承载功能性的领域知识和指令。例如，当一个 PR 被打开时，Warp 的代码智能体会基于这个基础 Skill 和相关上下文执行，产出代码审查。

对智能体产出的**人类反馈**是自我改进回路的关键组成部分。对代码审查来说，它可以简单到一个点赞，但反馈越明确越好。

「人可以肯定地说『这是一条好的、有用的评论』，」Warp 创始人 Zach Lloyd 解释道，「但人也可以详细说明一次代码审查为什么不好。比如『你建议重命名这个变量，但我们代码库的惯例是这类全局变量使用这种特定的命名上下文』这样的具体细节，会告诉智能体下次怎么做才对。」

**外层/改进 Skill（outer/improver skill）**充当一个观察者智能体，按调度周期运行，而非逐任务运行。它拉取累积的人类反馈，把智能体的建议与人类的回应进行对比，然后对基础 Skill 提出一处小而聚焦的修改。

由于 Skills 就是普通文件，智能体特别擅长更新它们。这些更新可审查、可批准、可合并，可以走正常的 PR/代码审查工作流；一旦合并，内层 Skill 的下一次运行就会继承这项改进。

Warp 如今在其整个开源仓库中运行这一模式：规格编写、审查和分类（triage）智能体各自独立，每一个都带有自己的自我改进回路。

「基于文件的 Skills 是一种为智能体编码知识的方式，它不把知识直接放进提示里，而是让智能体在工作过程中按需查找，」Zach 说。「这个框架其实非常简单：有一个特定领域的基础 Skill，还有一个负责打磨这个基础 Skill 的改进 Skill。简单正是这套方法的精妙之处。」

## **如何为智能体编写自我改进的 Skills**

以下是 Warp 团队沉淀的一些经过实战检验的技巧，用于为智能体循环编写自我改进的 Skills：

- **写原则，而不是规则。**「把 Skill 写得像在指导一个聪明人，而不是在给计算机编程，」Zach 说。「在 Skill 里写上『留意重复代码』这样的方向性指引，比罗列详尽无遗的变量命名规则效果更好。」
- **解释为什么。**给出规则背后的理由，能让智能体对问题进行推理，而不是机械执行僵硬的指令，这同样能带来更好的泛化能力。
- **让反馈毫不费力。**在人们已经在工作的地方收集反馈，比如直接在 PR 或 issue 上评论。而且要让这一切自动发生，不需要额外的提交步骤。「低摩擦才能让信号持续流动，」Zach 指出。「如果把门槛设得太高，你就得不到反馈，也就无法改进 Skill。」
- **保持 Skills 精简，并使用渐进式披露（progressive disclosure）。**[一个好的 Skill](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices) 文件并不大；它引用资源文件和脚本，而不是把所有内容一次性塞进上下文。
- **反馈质量重于数量，但数量也有帮助。**一位资深工程师给出的少量详细、贴合领域的反馈，可能比大量敷衍的反馈更有价值，因为非黑即白的赞/踩并没有说明*为什么*。「只要反馈足够详细、来自掌握特定领域知识的人——那些智能体原本无从获知的知识——即使是相对较小的样本量也能得到非常好的信号，」Zach 继续说道。「话虽如此，高质量信号的语料库越大越好。在 Warp，我们用一个回路管理整个开源仓库。我们有数百名贡献者，进行的代码审查数以千计。」
- **在改进 Skill 上多下功夫。**在编写改进 Skill（即观察者智能体）上多投入一些，回报会超出眼前的这个智能体循环，因为改进 Skill 在不同用例之间高度可复用。「除掉特定领域知识的部分，这是一个相当可复用的机制——代码审查智能体的改进 Skill 和其他任何智能体的改进 Skill 没有多大差别。」

## **回路实战：Warp 的 issue 分类智能体**

[Warp 的 issue 分类智能体](https://github.com/warpdotdev/warp-agents-demo-github-issue-triage)展示了这套自我改进的智能体 Skills 框架。每当有人提交一个新的 GitHub issue，这个模式就会被触发：一个 GitHub Action 启动智能体，分析该 issue 的复杂度和可行性，分配标签，并给出修复方向的建议。这个分类智能体由一个内层 Skill 文件驱动，其中承载着领域知识：每个标签的含义，以及行动之前该如何调研代码库。

在一个示例 issue 上，第一阶段的内层 Skill 表现不错，但漏掉了一个标签 ready to spec——它表示贡献者可以开始围绕该 issue 构建产品和技术规格。Warp 团队的一位维护者发现了这个疏漏，直接在 issue 上留下反馈——恰好在工作发生的地方。关键在于，他既说明了自己的期望，也解释了抱有这种期望的原因：这样的可执行反馈，智能体之后很容易吸收。

外层改进 Skill 运行在 [Oz——Warp 的智能体编排平台](https://docs.warp.dev/)之上，作为一个按调度运行的「update triage」智能体。该智能体完成 GitHub 身份验证后，运行随 Skill 打包的一个 Python 脚本，拉取近期带反馈的 issue，把它们汇总成一个 JSON 文件，再读回上下文。随 Skill 捆绑脚本本身就是一条最佳实践；Skills 可以引用资源文件，而不必每次运行都现写新代码。

接着，智能体从维护者的评论中识别出具体的反馈信号，并提出了能涵盖这些信号的最小修改。它发起了一个 PR 来编辑内层 Skill：当一个 issue 描述的是一个真实问题时——即便确切的 UI 或 UX 形态尚未确定——也应用「ready to spec」标签。

由于整个更新就是一个 Skill 文件，它可以通过正常的代码审查工作流流转。这个 PR 附带描述，说明了哪些信号促成了此次修改、改动了什么。由人来审查、批准并合并，分类 Skill 的下一次运行便继承了新知识。最后这一步人工环节闭合了回路，也确保真正改动什么始终由人掌控。

这正是 Warp 如今在其开源仓库中大规模运行的同一套机制：规格编写智能体、审查智能体和分类智能体，各自带着自己的自我改进回路。

任何智能体，无论任务是什么，只要从一开始就内置这样一个回路——捕获人类反馈信号、把它们转化为 Skill 更新——都会随时间越变越好，并从一次性的帮手成长为能在整个组织中复利积累的强大系统。

| Warp 团队的最佳实践 |
| 你是否把 Skills 和记忆混为一谈了？ | Skills 是程序性且稳定的——「如何做 X」，与单次运行无关，只经深思熟虑后修改。记忆则由智能体在推理时自动写入，且永不停歇地变化。 |
| 你需要一个改进回路，还是每个智能体各一个？ | 折中处理：用一个模板化的基础回路捕捉各智能体之间的共性，再叠加特定领域的权重。少数几个改进器可以各管一个；上百个就应该共享。 |
| 反馈出错时怎么办？ | 默认它一定会出错。别让智能体盲目接受反馈——给它用于合理性检验的上下文，过滤掉不该算数的意见，并在过滤环节或最终审查环节保留人工参与。 |
| 你的领域可验证吗？ | 先搭建验证执行框架（harness），再让智能体对着它调优：生成参考语料库，把输出与参考对比，修复，再重复。 |
| 如果领域不可验证呢？ | 凡是存在黄金输出（golden outputs）的地方，都依靠确定性的评估（evals）。不得不使用人类反馈时，把它限制在领域专家范围内——不要大开闸门。 |
| 你怎么知道整个系统在变好？ | 追踪人类本来就会盯着的全局指标——合并时长、贡献者数量、成本——并把它们回喂给改进智能体。部署上遵循爬-走-跑（crawl-walk-run）的节奏。 |
