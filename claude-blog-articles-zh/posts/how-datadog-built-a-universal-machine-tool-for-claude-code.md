# Datadog 如何为 Claude Code 打造「通用机床」

Datadog 让智能体编写规格说明，再由一个确定性内核据此编写应用代码。

*智能体、机械化与工业化*

Datadog 的所有工程师都在用 AI 编码工具编写生产代码，其中至少三分之二由 Claude Code 驱动。借助 Claude Code，他们在软件开发生命周期中生成个性化的流程，可分为四大类：

* **定向修改**：数十个棘手的 bug 修复、性能优化，以及对接现有服务的桥接层。
* **大型重构**：三天内重构一个自研 protobuf 解析器，以及在不到三个月内把一套指标控制系统从 FoundationDB 重写到 Postgres。
* **替换大型组件**：新的分片算法与自动扩缩容的重新设计。
* **构建整套系统**：用 Postgres 替换 MongoDB、BYOC 控制平面，以及从零搭建的数据摄取管道。

然而，随着工作沿着这张图谱流动，他们发现：在一个维度上，生成变得越来越复杂；在另一个维度上，验证变得越来越模糊。

## 流（flow）的问题

对工程师而言，flow 过去意味着意图与代码之间的直接关系：你理解问题、写代码、测试、评审、发布、运维，如此循环。有了智能体之后，这层抽象正在快速改变。

> “你不再是在写代码，而是在塑造工作本身。你在决定智能体该看到什么、该拥有哪些工具、什么算成功、失败该如何被检测……就好像每个人都被连升三级进了管理层，而这并不是他们当初作为工程师想做的事，”Datadog 工程副总裁 Sesh Nalla 说。

借助 [Claude Managed Agents](https://platform.claude.com/docs/en/managed-agents/overview) 这类方案，Datadog 的会话运行得更久，有时持续数天。每个智能体都会自行发明工具、自己的胶水代码和自己的约定。智能体因此显著更有用，但仍需要人来弥合「智能体执行」与「为人类设计的工具」之间的落差。

机床（machine tools）是制造业中的夹具、工装、量具和铣床。它们生产精确、可重复的零件，你再把这些零件组装成更大、更复杂的机器，比如发动机、飞机、核反应堆和登月舱。它们曾是工业化的突破口：零件由此变得可组合、可检验、可替换。

Temper 就是 Sesh 所说的、Datadog 对「面向智能体系统的通用机床」的尝试。换句话说，它是让智能体以安全、精确的方式构建所需之物所必需的最小内核。

> “这时我觉得我们需要更具结构性的东西，”Sesh 说。“如果智能体要构建并运维我们系统的大片区域、我们的数据库——这些都是关键任务——它们就需要相当于机床这样的概念。Temper 就是 Datadog 的那台机床。”

## 通往 Temper 之路

机械化意味着智能体现在承担了更多工作；工业化意味着工作变得可重复、可验证、可控制、可扩展。在 Datadog，这一切并不是一步到位的：通往 Temper 的路经过另外三个项目——Courier、BitsEvolve 和 Helix。每一个都暴露出下一个项目的瓶颈，也让他们的野心不断生长。

2024 年，他们推出了 [**Courier**](https://www.datadoghq.com/blog/engineering/formal-modeling-and-simulation/)，一个分布式队列系统。完全从零纯手工构建，花了一年时间。

> “难点不在于构建各个部件，而在于让部件之间的交互变得可观测、可测试、可验证，”Sesh 说。“所以我们对形式化建模与仿真非常严格……找出那些一旦出错代价高昂或难以回退的部分，并在[那里]提高严谨度。”

2025 年 9 月，他们构建了 [**BitsEvolve**](https://www.datadoghq.com/blog/engineering/self-optimizing-system/)，一个闭环的进化式优化框架。由一组模型组成的「议会」生成代码变体，再由[基准测试](https://www.datadoghq.com/blog/ai/production-grounded-code-optimization/)、测试套件和生产可观测性的层层筛选决定哪些变体得以留存。

> “这是我第一次看到，软件的某些部分可以像生物体一样被培育——通过带反馈的变异与适应生长出来，”Sesh 说。

问题在于：进化的效果取决于它所适应的环境，而 BitsEvolve 的瓶颈正是这个反馈回路。随后他们构建了 [**Helix**](https://www.datadoghq.com/blog/ai/fully-autonomous-optimization/)，一个可与 Kafka 相媲美的流式服务。大部分构建工作由 Claude Code 完成，只有一个人负责把控方向。

> “令我们难以置信的是，几天之内我们就有了一个功能完整的、可与 Kafka 媲美的系统，”Sesh 说。“[构建速度很快]，我们开始影子运行它，并看到了它有望便宜 2 到 5 倍的机会。”

不过，要把它推到生产环境，还需要多得多的打磨：运维层面的加固只能靠时间和不止一个人来积累，而这一过程目前仍在推进中。

> “瓶颈又转移了：智能体可以构建系统的大片区域……但人类仍然必须通过为人类构建的工具和机制，协调着把工作交付到生产环境，”Sesh 说。

Datadog 需要一种方式，让智能体能在经过验证、由策略驱动的运行环境中自行构建工具。这个运行环境就是 [**Temper**](https://github.com/nerdsane/temper)。

## Temper

智能体产出代码的速度超过任何团队手工评审的速度，但它们也会犯错。

在 Sesh 看来，智能体生成的内容与通过验证的内容之间的落差，正是失效模式累积之处。然而，单纯把智能体包在一个传统代码库外面，只是把它当成吞吐量问题来处理，并没有真正弥合验证的落差。

Temper 把这个等式反转过来：智能体不再产出应用代码，而是产出规格说明（specification）。内核读取每一份规格，经四层分析验证后，部署规格所描述的那个运行中的系统。由于规格既是那个被证明的产物，也是那个被执行的产物，已验证的内容与正在运行的内容之间不存在漂移。

![](https://assets.claude.com/0bf277022a64a64601b56303d9cbf8c0a5243308.png)

> “Temper 改变了系统的**中心**。智能体不再需要为每一个局部需求不断发明互不相通的工具；相反，它产出精确的描述，作为对意图与问题域的规格说明。它之所以是机床，其意义与夹具或 CNC 机床相同——你给它们的是螺纹加工要求的规格。它极度可重复。你可以运行它们，用它们造飞机以及诸如此类的复杂事物，”Sesh 说。

所以在这种情况下，智能体不是每次都即兴发挥出最终机制。它可以产出一份精确描述，与 Temper（或类似 Temper 的机制）迭代，先让某个东西跑起来，再把它变成可重复、可检验、可复用的东西，从而真正围绕你的代码库建起一座软件工厂。

每一项能力由三份契约来描述：

* **行为**：状态、迁移、前置条件，以及必须成立的安全性质。
* **数据契约**：实体类型、其属性，以及每种类型支持的操作，以机器可解析的形式发布，使智能体无需文档即可发现完整的 API。
* **授权**：默认拒绝、基于作用域的审批；被拒绝的请求会记录为待决事项，可由人工批准并热加载进策略引擎。

每份规格都要通过四层独立检验，内核才会加载它。符号推理证明每个守卫条件可满足、每条不变式具有归纳性；穷尽式状态探索访问每一个可达状态。

确定性仿真在注入带种子的故障（丢包、延迟、乱序、崩溃）的情况下运行真实的生产代码路径，因此同样的种子下故障可以精确复现。

随机化性质测试运行约一千条伪随机动作序列，并把任何违反性质的情况收缩为最小反例。对于一份小规格，整条串联检验在远不到一秒内跑完。

## Helix 的「黑灯工厂」

Simon Willison 普及了「黑灯工厂」（dark factory）一词，指一种软件流程：智能体在虚拟车间里无需人类介入即可持续工作。在 Helix 的黑灯工厂中，Temper 扮演三重角色。

它是托管智能体的**智能体控制平面**——会话、角色、工作队列、生命周期。它是**工具构建层**，让智能体用小型 Temper 应用把 SDLC 工具链（Git、CI、部署）桥接起来。它还是 **Helix 控制 API**，即围绕数据平面、承载工作负载的生命周期接口。

> “令人意外的是，它开始显得比智能体基础设施更通用。很多软件，眯起眼睛看，无非是围绕数据库 API 的控制逻辑：状态、围绕变更的策略、生命周期迁移、与外部系统的集成。Temper 之所以可能是通用的，是因为它可以应用到任何具有我所描述形态的软件上，”Sesh 说。

## 为什么不直接做一个 CRUD 应用？

> “Claude Code 能非常好地[用 TypeScript 或 Python 构建 CRUD 应用]。然而在普通的 CRUD 应用中，控制逻辑分散在路由、数据库约束、服务代码、后台任务和文档之中。它也许有不错的测试与覆盖率，但运行模式——通常以状态机的形式存在——在代码库中是隐式的，”Sesh 说。

> “Temper 让那个状态机显式化。智能体产出的是精确描述，而非任意代码。编译步骤在 LLM 之外，就像你把 Rust 代码交给 Rust 编译器一样。迁移表是数据，而不是埋藏在服务方法里的面条式控制流。智能体可以安全地动态修改它，并绕过 CI 热加载，”他解释道。

## 这条路将通向何方

Temper 背后的理念是：每个产物都应小到能装进你的脑子里。像航空和金融系统这样的高保障软件几十年来就是这样构建的，但在智能体登场之前，靠人力达到那种严谨度的成本对通用软件来说太高了。

工业革命之所以成为可能，是因为机床让零件变得可组合、可检验、可替换，于是我们才能造出越来越大、越来越复杂的机器。

> “如果智能体能在工厂里以这种纪律自主构建软件，也许我们不必止步于黑灯工厂。以这种方式构建的软件，开始像是一个我们可以通过反馈、选择与适应来生长、培育和演化的有机体，”Sesh 说。

| Datadog 团队的最佳实践 | 建议 |
| --- | --- |
| 你真正的瓶颈是生成还是验证？ | 假定是验证。智能体产出代码的速度已超过任何团队能评审的速度；生成的内容与已证明的内容之间的落差正是失效模式堆积之处。要往那里投资，而不是追求更高吞吐。 |
| 智能体究竟应该产出什么？ | 控制逻辑的规格（而非代码），以及针对任意代码的携带证明（proof carrying）。把编译与证明放在 LLM 之外——把规格交给确定性内核，让被验证的产物就是被运行的产物。 |
| 你的控制逻辑是显式的，还是散落在代码库各处？ | 把状态机从路由、服务方法和后台任务中抽出来，使其成为数据：一张智能体可读、可改、可在策略下热加载的迁移表。 |
| 人能把每个产物装进脑子里理解吗？ | 如果不能，你就回到了原点。让每个生成的部件都小到足以被推理。 |
