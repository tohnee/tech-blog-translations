# 如何在 Claude Code 中使用子智能体，以及何时使用

> 原文：[How and when to use subagents in Claude Code](https://claude.com/blog/subagents-in-claude-code/) · Claude 博客

[Claude Code](https://claude.com/product/claude-code) 能够很好地处理复杂的多步骤项目，但长时间的会话会不断累积负担。每一次文件读取、每一条探索过的岔路、每一个未完成的想法都会留在上下文窗口里，拖慢响应速度并推高 token 成本。

设想你正在一个大型 TypeScript 单体仓库中构建新功能。主要工作是实现本身，但各种支线任务不断冒出来：追查某个现有服务如何处理认证、找到日期格式化的共享工具函数、确认设计系统里是否已有接近你需求的组件。这些任务都不需要完整的项目上下文，而在主会话里运行它们只会增添噪声。如果你能并行运行它们呢？

这时就轮到[子智能体（subagent）](https://code.claude.com/docs/en/sub-agents)登场了。子智能体是一个拥有独立上下文窗口的隔离 Claude 实例。它接手一项任务，完成工作，然后只返回结果。可以把子智能体想象成 Claude Code 会话中的浏览器标签页：一个让你追索支线而不丢掉主线的地方。

在本文中，我们将讨论何时适合使用子智能体、如何调用它们，以及什么时候开销并不值得。

## 什么是子智能体？

子智能体是自包含的智能体，运行在各自的上下文窗口中。当 Claude 派生（spawn）出一个子智能体时，它会独立地读取文件、探索代码或进行修改。任务完成后，子智能体只把相关结果返回给主对话。

每个子智能体都是全新启动的，不受对话历史或已调用技能的拖累。多个子智能体可以并行运行，且各自可以拥有不同的权限：研究型子智能体可能只有只读访问权限，而实现型子智能体则拥有完整的编辑能力。

Claude Code 内置了若干子智能体类型，包括：

- **通用智能体（general-purpose agents）**，用于复杂的多步骤任务
- **计划智能体（Plan agents）**，在给出实现策略之前先研究代码库
- **探索智能体（Explore agents）**，针对快速的只读代码搜索做了优化

Claude Code 经常会自行派生子智能体来处理分配的任务。你也可以显式地指定这种行为，并定义可复用的专家角色供 Claude 自动委派。知道什么时候该动用子智能体，才能让这个功能真正发挥作用。

## 什么时候应该使用子智能体？

某些类型的工作从子智能体委派中获益明显。学会识别它们能让这个功能的效果大幅提升。

### 研究密集型任务

当理解某个东西的运作方式是修改它的前提时，子智能体可以去探索代码库并返回一份摘要，而不是把几十个文件一股脑倒进对话里。

**信号：**收集上下文需要阅读几十个文件。

**收益：**主对话保持干净，抵达的是综合后的结论而不是原始内容。

### 多个相互独立的任务

当你要修复横跨多个文件的错误、在多个组件中更新某种模式，或者进行彼此不依赖的修改时，并行的子智能体能更快完成任务。

**信号：**子任务之间没有依赖关系。

**收益：**三个子智能体同时工作，通常能用更短的时间完成任务。

### 需要全新视角

当目标是对某个实现做一次无偏见的评审时，子智能体提供了一张白纸，因为它不会继承主对话中的假设、上下文或盲点。

**信号：**需要验证，且不希望对话历史影响分析。

**收益：**更干净、更客观的反馈。

**专业提示：** /clear 命令同样会重置上下文与对话历史，提供类似的白纸状态，但代价是彻底丢失那段历史。子智能体能在主对话完整保留的情况下获得同样的全新视角。

### 提交前验证

在最终敲定修改之前，一个独立的子智能体可以验证实现是否过度拟合了测试，或者遗漏了边界情况。

**信号：**提交代码之前需要第二意见。

**收益：**捕捉那些可能被对代码的熟悉感所掩盖的问题。

### 流水线式工作流

当任务有明显的阶段划分（即先设计，再实现，再测试）时，每个阶段都受益于专注的处理。

**信号：**顺序执行的阶段，交接点清晰。

**收益：**每个子智能体专注于自己的阶段，其他阶段的上下文不会制造噪声。

**专业提示：**当一个任务需要探索十个以上的文件，或者包含三个以上相互独立的工作单元时，这就是让 Claude 转向子智能体的强烈信号。

## 如何指示子智能体的使用

调用子智能体有多种方式，从简单的对话到自动化工作流不一而足。正确的起点取决于你的工作流，随着模式逐渐清晰，可以再层层加码。

### 对话式调用

最灵活的方式就是直接在对话中请 Claude 使用子智能体。这适用于所有 Claude Code 界面：终端、VS Code、JetBrains、网页端和桌面应用。

能够可靠触发子智能体的自然语言模式包括：

- "用一个子智能体探索这个代码库中认证是如何实现的"
- "让一个独立的智能体审查这段代码的安全问题"
- "并行研究这个。同时检查 API 路由、数据库模型和前端组件"
- "派生若干子智能体来修复各个包中的这些 TypeScript 错误"

明确表达很重要。指明范围，在任务相互独立时请求并行执行，并描述期望的输出。

高效对话式调用的技巧包括：

- **清晰地界定任务范围。**"探索支付功能是如何工作的"胜过"探索一切"。
- **显式请求并行化。**说"这些可以并行运行"或"同时处理这三个"。
- **指明应该返回什么。**摘要、具体发现或建议。说出输出格式能帮助 Claude 按此交付。
- **在需要无偏分析时要求全新上下文。**"用一个看不到我们之前讨论的子智能体"可以确保评估干净。

**专业提示：**当某个子智能体耗时较久时，Ctrl+B 可以把它转入后台。对话可以继续进行，子智能体完成后结果会自动浮现。/tasks 命令可以查看所有后台运行的内容。

### 自定义子智能体

当同一种子智能体被反复请求时（安全审查员、测试编写者、文档校对员），可以把它一次性定义为自定义子智能体（custom subagent）。

此后每当任务与其描述匹配，Claude 就会自动委派给它，无需任何提示。

### CLAUDE.md 指令

自定义子智能体定义的是"专家是谁"。CLAUDE.md 文件定义的则是"Claude 何时应该动用他们"的规则。如果每次代码评审都应该经过一个只读子智能体，或者每个架构问题都应该先触发一轮研究，CLAUDE.md 就是存放这些策略的地方。Claude 会在每次对话开始时读取它，因此行为在各个会话和团队成员之间保持一致，无需任何人记得主动要求。

当出现以下情况时，CLAUDE.md 很适合用来存放子智能体指令：

- 代码评审应始终使用只读子智能体
- 项目有 Claude 应遵循的特定研究模式
- 需要在团队成员和各个会话之间保持行为一致

### Skills（技能）

对于需要反复运行的复杂多步骤工作流，Skills（技能）提供了可复用的接口。在 `.claude/skills/` 中定义一次技能，然后用 /skill-name 调用它，或者让 Claude 在任务与其描述匹配时自动加载。

Skills 与 CLAUDE.md 文件的区别在于作用域。CLAUDE.md 文件始终被加载，影响每一次交互。而技能是按需加载的——要么被显式调用，要么因为 Claude 把当前任务匹配到了技能的 description 字段。这使 Skills 成为那些"应当可用，但不该套用到每个提示词上"的工作流的最佳归宿。

Skills 适合以下场景：

- 某些操作会被定期执行
- 不同团队成员需要使用同一个复杂操作
- 跨团队统一某些任务的执行方式很重要

### Hooks

Hooks（钩子）是用户定义的 shell 命令、HTTP 端点或 LLM 提示，会在 Claude Code 生命周期的特定时点自动执行。[Hooks](https://code.claude.com/docs/en/hooks-guide) 可以基于事件自动化子智能体工作流。Hooks 由特定动作触发，无需手动调用即可运行子智能体任务。

以下情况 Hooks 是正确的工具：

- 每次提交都应在创建前被自动审查
- 安全检查应该无需任何人记得主动要求就能运行

## 什么时候不应该使用子智能体？

子智能体虽然是个有用的功能，但也有开销。每一个都要启动自己的上下文、消耗 token，并在开发者与工作之间增加一层间接性。只有当上下文隔离、并行或全新视角确实带来帮助时，这份成本才值得付出。

对于较小或严格顺序执行的任务，坚持使用主对话通常更简单，例如：

- **顺序的、有依赖的工作。**当第二步需要第一步的完整输出，第三步又需要前两步时，用单个会话处理整条链，通常比让一串子智能体通过文件传递状态更干净。
- **同一文件的编辑。**两个子智能体并行编辑同一个文件是制造冲突的配方。这种场景下，把紧耦合的修改留在同一个上下文窗口里。
- **小任务。**对于一个快速修复或聚焦的问题，委派的开销大于收益。直接在主对话里提问即可。
- **过多的专家智能体。**为所有事情都定义一个自定义子智能体很诱人，但用过多选项轰炸 Claude 会让自动委派变得不可靠。大多数团队最终会收敛到少数几个范围清晰的智能体，而不是一张冗长的名册。
- **需要智能体彼此协调的工作。**子智能体向主对话汇报结果，但无法相互交谈。如果任务需要子智能体之间通信，请使用[智能体团队（agent teams）](https://code.claude.com/docs/en/agent-teams)。在智能体团队中，子智能体跨独立会话协调而非局限于单个会话，这也让它们更重、更昂贵。关于何时使用子智能体、何时使用 Agent Teams 的更多指引，请查阅我们的 [Claude Code 智能体团队文档](https://code.claude.com/docs/en/agent-teams)。

前文描述的那些信号（即需要第二意见、子任务之间无依赖、以及大规模研究）清楚地表明了什么时候委派给子智能体是值得的。

## 先从对话开始，之后再自动化

子智能体在有意识地使用时才能发挥全部价值。Claude 提供的自动调用固然有帮助，但知道何时该委派研究、何时该并行工作、何时该请求全新视角，比听天由命能产出更好的结果。

使用子智能体时，从对话式提示开始。留意哪些请求反复出现，并在模式清晰后逐步构建自动化。目标是让子智能体委派变得毫不费力，让你的注意力保持在真正重要的工作上。
