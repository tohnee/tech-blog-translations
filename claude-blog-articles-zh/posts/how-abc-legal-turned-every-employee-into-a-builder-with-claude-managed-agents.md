# ABC Legal 如何借助 Claude 托管智能体让每位员工都成为构建者

> 原文：[How ABC Legal turned every employee into a builder with Claude Managed Agents](https://claude.com/resources/articles/how-abc-legal-turned-every-employee-into-a-builder-with-claude-managed-agents) · Claude 博客

ABC Legal 借助 Claude，把组织内零散的 AI 实验转变为一支受治理的专用智能体舰队。

ABC Legal 是一家总部位于美国的法律文书送达公司。今年早些时候，公司 CTO Brandon Fuller 向全公司 1,100 名员工推广 [Claude Enterprise](https://claude.com/solutions/enterprise)，立刻就产生了化学反应。公司各部门——诉讼文书送达、电子立案、出庭律师运营，以及市场、合规、财务等——都开始自发地构建自动化，无需任何人指派。

"用户真的很买账，"Fuller 回忆道。"他们看到了连接器和工具的易用性，突然间，组织里到处都有人在把自己每天被吞噬掉的任务自动化掉。"

这正是任何一位 CTO 都期望看到的采用程度。但 Fuller 看到了更进一步的机会：如果 ABC Legal 还能运行一支有版本管理、可观测、始终在线的 AI 智能体舰队呢？

这个雄心最终落到了基础设施上。早期的智能体寄居在构建者随手放置的地方——个人桌面上的计划任务。把它们从个人电脑上移走，就能让它们无人值守地运行，并让 Fuller 对"构建了什么、花了多少钱、昨晚有没有跑"有一个统一视图。

于是他部署了 [Claude 托管智能体（Claude Managed Agents）](https://platform.claude.com/docs/en/managed-agents/overview)：统一的部署结构、共享工作区、单一的审计与计费入口，以及运行在云端而非个人笔记本上的始终在线智能体。

截至 2026 年 7 月，Fuller 和 ABC Legal 团队统计到：

* 生产环境中有 50+ 个用托管智能体构建的智能体
* 在尚未做深度优化的情况下，部分智能体所覆盖的人工任务成本最多降低约 50%
* 各部门约 310 名员工在日常工作中使用 Claude

以下是他们如何走到这一步，以及在这个过程中学到了什么。

## 从热情到工程：把每个智能体都当作软件对待

首次部署 Claude 托管智能体时，Fuller 要求团队把每个智能体都定义为代码。他认为这才是智能体应有的自然形态。他解释道："智能体本质上就是结构化文本——一段提示词加配置，而任何文本化的东西都可以放进仓库，让全公司看得到、审得了、改得好。"智能体的提示词、工具清单、调度计划、凭据和记忆全部写入配置文件，与公司软件一起保存在 git 仓库中。智能体的任何改动都必须经由有人批准的拉取请求，这让每个智能体都拥有版本历史、代码评审、回滚能力和审计追踪。

他花了一周时间搭建了一个入门套件，包含两个模板，存放在专用的 git 仓库中。一个用于事件驱动型智能体——事情一发生就启动，比如新工单到达或文书从法院返回；另一个用于定时型智能体——按小时、每天或每周运行。每个智能体都有自己的文件夹和标准结构：一个 JSON 配置文件、一段 Markdown 格式的系统提示词、部署脚本和运维文档。把变更合并到主分支就会自动部署该智能体。构建者完全不需要写软件：他们克隆仓库、复制一个起始模板、告诉 Claude Code 智能体应该做什么，就能拿回智能体所需的一切——配置、提示词、凭据存储和记忆。

## 弥合技术鸿沟

Fuller 召集了公司 15 人组成的指导委员会——成员来自财务、市场、运营和开发部门，没有一个是软件开发者——让他们克隆仓库并用 Claude Code 构建托管智能体。

目标是要证明非开发者也能自己构建生产级智能体。如果每个智能体都得走开发团队，这个瓶颈就会限制整个公司的推进速度。而让这件事安全可行的原因在于：他们并不是在写软件，而是在填写配置和提示词，运行时由托管智能体提供。

"我得跟他们解释什么是 PR。很多（非软件工程师）以为 PR 是指跑步，就是你能跑多快，"他说。【译者注：PR 在此指跑步中的 personal record，即个人最好成绩。】"现在他们都在发 PR、互相评审了。"

一周之内，15 名员工全部拥有了可用的智能体。这些构建者回到各自团队，又培训了其他人。一个月内，ABC Legal 全公司约有 50+ 个智能体在运行。每个智能体都有名字、负责人，以及单一明确的职责。

## 覆盖法律文书流程大多数环节的智能体

如今在 ABC Legal，法律立案流程及其周边运营的大多数环节都有对应的智能体。

AI Code Reviewer 会审查四个代码库中的每个拉取请求，运行多模型分析，捕捉安全漏洞、性能回退和被提交进代码的凭据。工程师如今在合并前会等它审完。

EvidenceChain™ Delivery Agent 接手了一位客户经理过去每周手工完成的琐事。ABC Legal 运营着一个专有网站 EvidenceChain.com，法院、原告和被告可以在上面查询现场送达完成的记录，包括送达员是谁、何时尝试送达，以及文书交付的照片。有个客户希望持续从网站上提取特定记录。现在这个智能体每天为匹配的工单拉取数据库报告，用托管智能体内置的浏览器逐个取回 PDF，再投递到客户的 FTP 服务器。搭建它的客户经理从未做过任何自动化，只是向 Claude Code 描述需求，大约一小时就做出来了。

eFiling Rejection Diagnoser 会在法院驳回立案时自动触发，读取工单详情、核对法院规则，并在一分钟左右把诊断结果发到 Slack——这项工作过去要占用员工一天中的好几个小时。一个工单核验智能体负责把每个新进工单与法院信息核对：它在浏览器中访问法院网站，确认听证或案件已正确立案、并且确实会在所述日期进行，然后根据核验结果调整工单，同时标记司法辖区、法院和诉讼时效时间窗。

Attorney Coverage Agent 在律师网络中协调出庭覆盖：查询律师的空档、发送邮件，并阅读关于可用性和报价的回复，让协调员确认覆盖安排。

在财务方面，一个应收账款（AR）汇款处理智能体解析汇款邮件，生成 NetSuite 付款申请文件，发到 Slack 供一键审批，随后导入；另有一个每日运行的智能体，对每张工程工单给出"资本化还是费用化"的判定。市场团队运行着一个 Google Ads 分析师，每周向渠道负责人发布建议。运营部门有一个名为 Charvis 的复核智能体，检查已完成的送达工单，如今与合规团队的一致率约为 98%。

Service-Overdue-Nudger 处理 ABC Legal 运营积压中的第一层——本需人工完成的重复性初筛——并起草分级的每日外联消息，交由人工批准。

## 让智能体更聪明：收集、调优、重复

ABC Legal 的智能体在人类监督下工作：它们把做过的事或给出的建议发到 Slack，人们则在话题串中回复、用 emoji 表态。

![](https://assets.claude.com/8f900037eb2f484fefedada30cfe8e50e744453b.png)

Hank 是内部代码评审智能体，它把每次评审都发到共享 Slack 频道。每条记录都写明对应的拉取请求以及由此得出的计数，让智能体的决策轨迹公开可查。

Fuller 认为，这些反应数据本是一种白白浪费掉的训练信号。但并非每个智能体都需要这个信号。舰队中的大多数是单任务执行者，输出无人评分，独立工作。对于那些确实会收集评分反馈的智能体，ABC Legal 采用三角色架构：多个彼此独立、共享同一工作区、环境和凭据保险库、但按不同节奏运行的智能体。这一模式把 Slack 里的消息转化为经过人工批准、带版本记录的智能体变更：

1. **初始智能体（Initial Agent）** 负责干活，通常在工单进来或文书返回时实时执行，并记录每一步操作的审计追踪。
2. **收集器（Harvester）** 按小时或按天运行，从 Slack 收集人类反馈——以话题串回复和 emoji 反应的形式到来。每一条都成为一个带标签的数据点。
3. **调优器（Tuner）** 每周运行，一次纵观全部数据，提出对提示词或配置的修改，而不是改动模型权重。它只负责起草，由人审阅并合并拉取请求。

![](https://assets.claude.com/be80e667d16bcafbeda2800fafdcc97e780547f2.png)

在 ABC Legal 的自我改进智能体闭环中，初始智能体实时完成工作，收集器按小时清扫 Slack 中的人类反馈，每周运行的调优器则把提示词和配置变更作为拉取请求提出。智能体通过开发者早已在用的同一套工作流自我改进。

一个例子是"deliveries-as-code（交付即代码）"——Fuller 用来调优工作路由方式的智能体系统，它起源于 ABC Legal 旗下 50 人的姊妹公司 Docketly。Docketly 以"交付（delivery）"来组织工作，每个交付都有自己的路由和处理规则集。约 145 个规则集全部是 git 中的单个 YAML 文件，而不是后台管理界面里的记录，因此调优一个交付就意味着编辑一个文件并提交拉取请求。

这个闭环由四个智能体组成：一个每周把结论发到 Slack；收集器把反应转化为人类反馈驱动的标签；调优器对 YAML 发起拉取请求；第四个智能体把合并后的配置推送到生产数据库。第四个智能体只执行人类已经审阅并批准的内容。在实践中，一个标记"交付路由错误"的 emoji 反应，可以在一周之内变成该交付路由规则的已合并变更。人工评审是这个闭环中唯一的手动步骤。

## 为什么选择 Claude 托管智能体

Fuller 评估了多个框架，最终选择 Claude 托管智能体作为组织的智能体执行框架。他的标准很具体：平台必须具备版本管理、可观测的会话、工作区计费、模型选择、记忆原语、MCP 接入，而最关键的是——无需照看的底层基础设施。

平台的责任划分与 Fuller 想要的运行方式高度契合。Anthropic 的托管基础设施负责让智能体运行起来的一切：执行循环、会话、记忆、控制台以及模型本身。ABC Legal 则拥有提示词、工具清单、触发逻辑、审计追踪和基于结果的反馈闭环。

有几项能力在规模化后显得尤为重要：

* **版本管理：** 每次推送都会以乐观锁机制创建一个新的智能体版本，回滚轻而易举。
* **模型灵活性：** 大多数智能体默认使用 Claude Sonnet；高并发、快速任务使用 Claude Haiku；需要更深推理且成本划算时使用 Claude Opus。切换模型只需改一行。
* **MCP 接入与凭据保险库：** 智能体可连接 ABC Legal 自有平台（可用工具超过 100 个）、用于报表的 Metabase、用于人工在环交互的 Slack，以及用于项目管理的 Atlassian。
* **定时部署：** 周期性智能体通过 Bitbucket Pipelines 按 cron 计划运行，该管道本就负责仓库访问、密钥和计费。

ABC Legal 追踪 AI 支出的每一美元，并按厂商、工具、团队和用例拆分。随着智能体舰队在春季陆续上线，支出随之攀升；到了 7 月，在使用量持续增长的同时支出开始下降——这是下文所述效率优化的结果：许多智能体覆盖的任务成本降低约 50%，各部门约 310 名员工在使用 Claude。

公司对成本的态度是刻意为之：把支出推向垂直的、运营类工具和智能体——它们的回报可以量化；同时让通用的聊天和头脑风暴用法保持广泛、成本受控。大多数智能体从人工在环起步：智能体查看工单或任务，给出建议，由人复核后才采取行动。建议要么存进工单、以横幅提示的方式呈现，让员工在日常工作流中直接接受或拒绝；要么发到 Slack 频道，供大家在话题串里回复。这些回应积累成"判断对错"的带标签数据集，喂给收集器—调优器闭环，也让团队能够编写评估（eval）并跨前沿模型对智能体做基准测试。一旦某个智能体证明自己在特定任务上达到或超过人类水平，它就切换到自动化模式自主行动，之后仍留在同一套度量框架内，以便持续观察性能是否有变化。

ABC Legal 追踪的指标是效率比：智能体交付的价值与其运行成本的比值。每个托管智能体在每次运行时都会以小时数和美元为单位，把自己的价值回报给数据仓库。智能体的收益曲线呈 J 型：新上线、跑着更大模型时往往一开始是亏的，随着团队编写评估、切换到更便宜更快的模型、精简 token 用量，曲线随即转正。

## 部署智能体舰队的最佳实践

Fuller 在部署 AI——具体来说是 Claude 托管智能体——的过程中，总结出几条使用这项技术的工作原则：

* **把一切都当作代码。**"代码不过是结构化文本，LLM 是文本引擎，"他说。"你能把越多的业务转化为仓库里的文本，智能体给你的杠杆就越大。"这既适用于传统软件，也同样适用于提示词、schema、派单规则、通知模板和业务配置。
* **从人工在环开始。** 每个智能体都从发布建议、供人复核起步。只有在证明自己与人类决策持续一致之后，它才有资格独立行动。"每个智能体都是先赢得信任，才独立行动的。它不会一开始就这样。"
* **把 PR 当作控制面。**"如果你想让智能体参与某个决策，就把这个决策做成拉取请求的样子。"逐行评论、审批工作流和不可篡改的审计追踪都是版本控制自带的能力，并且能与 AI 评审和人类评审自然组合。
* **投资于反馈闭环。** 收集器—调优器模式意味着智能体无需重训就能改进。Slack 回复和 emoji 反应变成结构化信号，反哺提示词和配置变更，全程走的是人类早已在用的同一套拉取请求工作流。
* **跳过计划任务这段弯路。** 在转向托管智能体之前，ABC Legal 确实花了不少时间构建计划任务和本地例行任务，主要因为当时该产品才刚发布 beta。Fuller 如今建议：直接上托管智能体。
* **要预期的是 git 这道坎，而不是 AI 这道坎。** 真正的难点在于让业务用户习惯克隆仓库、在 Git 和拉取请求中工作，而不是 AI 本身。这件事成功了，而且很快，但它确实是一道实打实的坎，Fuller 希望工具本身能把它变得更容易。
* **并非每项任务都值得上智能体。** 成本是实打实的，所以每个团队都必须以"价值高于成本"的视角思考。真正的工作是挑选那些确实能省时间或实现自动化的、可攻克的问题，并且愿意说出"这项任务不值得用智能体"。

团队还在寻找更多"X-as-code"候选对象：通知模板、事件路由规则，以及可以搬进仓库、让智能体阅读、推理并提出改进的派单逻辑。
