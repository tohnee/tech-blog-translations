# Getafix：Facebook 的工具如何学会自动修复 bug

> 原文：[Getafix: How Facebook tools learn to fix bugs automatically](https://ai.meta.com/blog/getafix-how-facebook-tools-learn-to-fix-bugs-automatically) · Meta AI（Wayback 存档）

2018 年 11 月 6 日

Facebook 构建了一个名为 Getafix 的工具，它能自动找出 bug 的修复方案并提供给工程师审批。这让工程师工作更高效，也促进了整体代码质量的提升。我们相信 Getafix 是首个在 Facebook 规模上部署到生产环境的此类工具，为数十亿人使用的应用的稳定性和性能做出了贡献。Getafix 为 Sapfix 提供支持——后者为我们的 Sapienz 测试工具发现的 bug 建议修复方案。Getafix 还为我们的静态测试工具 Infer 发现的 bug 提供修复。由于 Getafix 从工程师过去的代码修复中学习，它的建议对工程师而言直观易懂。

Getafix 通过使用更强大的技术从过去的代码变更中学习修复模式，改进了以往的自动修复技术：它采用了更强大的聚类算法，并分析问题代码行周围的上下文来找到更合适的修复方案。

现代生产代码库极其复杂且不断更新。为了构建一个无需工程师帮助即可自动找到 bug 修复方案的系统，我们构建了一个从工程师以往对代码库的变更中学习的工具。它发现隐藏的模式，并利用这些模式为新的 bug 识别最可能的补救措施。这个名为 Getafix 的工具已在 Facebook 部署到生产环境，为数十亿人使用的应用的稳定性做出贡献。

Getafix 与另外两个 Facebook 工具协同工作，不过其技术可用于处理来自任何来源的代码问题。它目前为 Infer——我们的静态分析工具，可识别 Android 和 Java 代码中的空指针异常等问题——发现的 bug 建议修复方案。它还通过 SapFix 为 Sapienz——我们的智能自动化应用测试系统——检测到的 bug 建议修复方案。此前我们已对 SapFix 和 Sapienz 做过概览介绍，现在我们将深入剖析 Getafix 如何学会修复 bug（这里的「bug」是广义的，泛指任何代码问题，而不仅仅是会导致应用崩溃的问题）。

Getafix 的目标是让计算机处理例行工作——尽管仍需在人的监督之下，由人来判断某个 bug 何时需要复杂的、非例行的补救。该工具对工程师们做出的成千上万次历史代码变更应用一种新的层次聚类方法，同时考察变更本身及其上下文。这种方法使它能够检测出以往自动修复工具无法察觉的 bug 底层模式及对应的修复。Getafix 还能缩小为找到 bug 修复而需要搜索的可能程序变更空间，从而更快地选出合适的补丁，避免暴力搜索和基于逻辑的技术所需的高昂计算时间。这种更高效的方法使 Getafix 得以部署到生产环境。同时，由于 Getafix 从历史代码变更中学习，它生成的修复也易于人类工程师理解。

Getafix 已在 Facebook 部署，用于自动为 Infer 报告的空解引用（null dereference）bug 建议修复，也为 Sapienz 标记的与空解引用相关的崩溃错误建议修复。它还被用于解决用更新版本 Infer 重新检查既有代码时发现的代码质量问题。

## Getafix 与更简单的自动修复工具的区别

在当前的工业实践中，自动修复主要用于修复方式一目了然的基础问题。例如，分析器可能警告「dead exception」——开发者可能忘了在 new Exception(...) 之前加上 throw。对这一改动的自动修复很简单，可以由 lint 规则的作者定义，无需了解应用时的具体上下文。

## 关键技术细节深入剖析

Getafix 组织为下图所示的工具链。本节将介绍三个主要组件各自的功能与挑战。

### 树差分器（Tree differencer）：在树的层面识别变更

首先使用一个基于抽象语法树的差分器来识别一对源文件（例如同一文件的先后版本）之间所做的具体编辑。例如，它会检测到细粒度的编辑：用 if 包裹一条语句、添加 @Nullable 注解或 import、在既有方法体前插入条件提前返回，等等。在下面的例子中，「若 dog 为 null 则提前返回」的插入、public 改为 private 的重命名以及一个方法的移动，都被检测为具体编辑。基于行的 diff 工具会把其中一个方法整体标记为删除再插入，而树差分器能检测到移动，因此还能检测到被移动方法内部的插入，作为具体编辑。

树差分器的一个挑战是高效且精确地对齐「改动前」和「改动后」两棵树的部分，以便发现正确的具体编辑及其从前树到后树的映射。

### 一种挖掘修复模式的新方法

Getafix 使用一种新的层次聚类技术，配合反统一（anti-unification）——一种在不同符号表达式之间进行泛化的既有方法——来执行模式挖掘。它创建一个可能相关的树差异集合，并使用能代表该集合中最常见程序变换的修复模式。这些模式可以是抽象的，在程序变换有差异之处包含「空洞（hole）」。

下图展示了一个由一组编辑得到的层次结构（称为树状图/dendrogram）。（此例展示的是上面上一个示例中的编辑。）每行展示一个编辑模式——「前」为紫色，「后」为蓝色——外加一些元数据。每根竖直黑条对应层次中的一级，黑条顶端的编辑模式是由该层级中所有其他编辑反统一得到的模式。其余编辑通过较细的黑线连接。反统一将上一个示例中「若 dog 为 null 则提前返回」的编辑与另一个仅 dog 喝的东西不同的编辑合并，结果是一个表达共性的抽象修复模式。由反统一引入的符号 h0 表示一个可根据上下文实例化的「空洞」。该编辑模式随后可以与其他变量名变化更大但整体结构相同的编辑模式结合。随着向树上攀升，这一过程产生越来越抽象的编辑模式。例如，它可以把这个编辑与一个与猫相关的编辑结合，得到图中靠近顶部的抽象编辑。

更重要的是，这种层次化匹配过程为 Getafix 提供了一个强大的框架，用于发现代码变更中可复用的模式。下图展示了将一段时间内修复我们代码库中 Infer 报告的空指针错误的全部 2288 个编辑合并后得到的树状图（横排并缩小展示）。我们要挖掘的修复模式就藏在这张树状图中。

基于反统一的模式挖掘思想并不新，但要挖掘出能用来为一个新的 bug 生成（并排序）数量适中的修复方案的模式，需要若干增强。其中一项改进是把一段未因编辑而改变的周围代码包含进来。这一改动让我们不仅能发现人们所做变更中的模式，还能发现变更应用场景中的模式。例如，在上面第一张树状图中，我们注意到模式 if (h0 == null) return; h0.h1(); 中的 h0.h1(); ——尽管 dog.drink(...); 本身没有改变，它仍被包含在模式的「前」「后」两部分中，作为告诉我们该修复应用于何处的上下文。在编辑层次的更高层，dog.drink() 上下文与其他上下文合并成抽象上下文 h0.h1()，从而限制了该模式的适用位置。下一节将给出一个更真实的例子。

过往自动修复文献中建议的贪心聚类算法不太可能学到这种上下文。这是因为贪心聚类算法为每个簇只维护单一表示，如果训练数据中的编辑并非全部包含额外上下文，该表示就不会包含它。例如，若一个在 do(list.get()); 之前插入 if (list != null) return; 的编辑与上面的 dog.drink() 例子合并，贪心聚类将丢失关于在哪里插入提前返回的全部上下文。Getafix 的层次聚类方法在每一层尽可能保留上下文，结构越高越泛化。到了某一层，连我们希望学到的通用上下文也会丢失，但它仍会保留在结构中较低的层级。

除了周围代码，我们还将编辑与最初触发它们的 Infer bug 报告关联起来，这让我们能够学习编辑模式与相应 bug 报告之间的关系。Infer 在 bug 报告中归咎的变量在上面第一张树状图中显示为「errorVar」，它参与反统一，最终成为空洞 h0。这使我们在面对一份新的 Infer bug 报告时，可以把被归咎的变量代入 h0，让修复模式更具针对性。

## Getafix 如何创建补丁

最后一步接收有 bug 的源代码和模式挖掘步骤得到的修复模式，并生成修补后的源代码版本。可供选择的修复模式通常很多（如上面的树状图所示），因此这一步必须解决的挑战是为特定 bug 选对模式。如果模式适用于多个位置，Getafix 还必须选对匹配。以下示例说明我们的总体方法以及 Getafix 如何应对这一挑战。

**示例 1.** 考虑我们上面挖掘到的模式：

`h0.h1(); → if (h0 == null) return; h0.h1();`

我们简要说明为以下未见过代码生成补丁的步骤：`mListView.clearListeners();`。Getafix 按以下步骤创建补丁：

1. 找到与「前」部分匹配的子 AST：`mListView.clearListeners();`
2. 实例化空洞 h0 和 h1
3. 用实例化后的「后」部分替换子 AST

注意，「后」部分中的 h0 因为包含了未修改的上下文 `h0.h1();` 而被绑定，这有助于限制模式的适用位置。若没有这一未修改上下文，模式就会变成 `<空> → if (h0 == null) return;`。这个模式会应用在意料之外的位置，比如 `mListView.clearListeners();` 之后，甚至 `mListView = null;` 之后。这个仅含插入的模式实际上也会出现在树状图的更高层，在那里带上下文 `h0.h1();` 的模式与在另一条语句前插入 return 的模式被反统一。

下一个示例说明 Getafix 如何处理似乎适用于过多位置的模式。

**示例 2.** 考虑以下模式：

`h0.h1() → h0!=null && h0.h1()`

通常，这个补丁会从 if 条件或 return 表达式内的修复中挖掘得到，因此我们也预期它应用于这些位置。但它也会匹配其他场景，例如上面示例中出现的调用语句：`mListView.clearListeners();`。

Getafix 的排序策略试图估计一个模式确实是一个修复、且它是给定上下文下最可能修复的概率。这一策略使系统减少对后续验证步骤的依赖，从而节省时间。上述模式将与其他模式竞争，例如更具体的 `if (h0.h1()) { ... } → if (h0!=null && h0.h1()) { ... }`，或示例 1 中只适用于调用语句而非表达式的模式。更具体的模式匹配的位置更少，因而被认为对场景更专精，Getafix 给它们更高的排名。

## 实现与性能

Getafix 已在 Facebook 部署，用于自动为我们的静态分析工具 Infer 报告的空解引用 bug 建议修复，也为 Sapienz 发现的与空解引用相关的崩溃 bug 建议修复。它还被用于解决过去遗留的 Infer bug。

在一项实验中，我们在一个包含约 200 个小改动（改动少于五行）的数据集上，将 Getafix 计算的修复与人类为相同 Infer null method call bug 实际编写的修复进行对比。在约 25% 的案例中，Getafix 排名最高的补丁与人工补丁完全一致。

另一项实验考察 Instagram 代码库的一个子集，尝试批量修复约 2000 个 null method call 问题。Getafix 能够为约 60% 的 bug 尝试生成补丁。这些尝试中约 90% 通过了自动验证，即可以编译且 Infer 不再发出警告。总体而言，Getafix 成功自动修补了 1077 个（约 53%）null method call bug。

除了为新引入的 Infer bug 建议修复之外，我们还在使用同一套基础设施清理那些逃过代码审查进入代码库的历史 Infer bug。作为这项工作的一部分，我们已清理了数百个 return not nullable 和 field not nullable 的 Infer bug。有意思的是，在 return not nullable 和 field not nullable bug 旁展示自动修复建议，使修复率分别从 56% 提升到 62%、从 51% 提升到 59%。总体上，由于 Getafix 展示了这些建议，过去三个月多修复了数百个 bug。

Getafix 还向 SapFix 提供修复，以处理 Sapienz 检测到的崩溃。过去几个月里，Getafix 提供了 SapFix 所用且认为有效（通过全部测试）的修复候选的约一半。在 Getafix 提供给 SapFix 的全部修复候选中，约 80% 通过了全部测试。

## 扩大 Getafix 的影响力

Getafix 帮助我们朝着让计算机处理例行 bug 修复工作的目标迈进。随着我们持续完善测试与验证工具，我们预计 Getafix 将能防止更大比例的部署后故障。我们注意到，Getafix 挖掘的修复模式并非只能来自对 Infer 的修复，它们同样可以来自响应人工代码检查所做的修复。修复模式的这一额外来源，开启了自动化重复性代码评审的激动人心的可能。换言之，过去在代码库中被多次标记并修复的 bug，未来可以在代码提交时自动标记——无需人来做这件事。

Getafix 是我们构建依赖大规模代码语料统计分析及相关元数据的智能工具这一整体努力的一部分。这类工具有潜力改进软件开发生命周期的方方面面，包括代码发现、代码质量和运营效率。我们从 Getafix 中获得的洞见，将帮助我们在这一领域构建和部署更多工具。
