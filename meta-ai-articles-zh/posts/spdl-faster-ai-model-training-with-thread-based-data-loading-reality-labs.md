# SPDL 介绍：用基于线程的数据加载加速 AI 模型训练

> 原文：[Introducing SPDL: Faster AI model training with thread-based data loading](https://ai.meta.com/blog/spdl-faster-ai-model-training-with-thread-based-data-loading-reality-labs) · Meta AI（Wayback 存档）

2024 年 11 月 22 日

**要点：**

- 我们推出 SPDL——一个面向 AI 模型训练的新数据加载解决方案。
- SPDL 是一个框架无关的数据加载解决方案，利用多线程，在常规 Python 解释器（构建时未启用 free-threading 选项）中实现高吞吐量。
- 与传统的基于进程的方案相比，SPDL 在使用更少计算资源的情况下实现 2–3 倍吞吐量。
- SPDL 兼容自由线程（Free-Threaded，FT）Python。我们的实验表明，在禁用 GIL 的 FT Python 中运行 SPDL，比在启用 GIL 的同一 FT Python 中吞吐量高 30%。
- 该库可在 https://github.com/facebookresearch/spdl 获取。

大规模训练 AI 模型带来许多挑战。随着模型规模增长，反向传播的计算量增加，拟合模型所需的数据量也随之增加。GPU 的使用加速了计算——然而 GPU 越快，就需要以更高吞吐量向 GPU 供给数据，才能让它们始终忙于计算。在 Reality Labs，我们的研究者和工程师训练各种 AI 模型，在空间计算领域进行创新。为此，我们常常需要多次迭代想法。快速训练 AI 模型至关重要，而要做到这一点，我们需要最大限度地利用 GPU。然而，现有的数据加载解决方案既不允许我们精细调优性能，也无法提供性能洞察。为了实现更好的 GPU 利用率并提升模型训练速度，我们开发了一种新的数据加载解决方案——可扩展高性能数据加载（Scalable and Performant Data Loading，SPDL）。SPDL 拥抱基于线程的并行，与传统的基于进程的并行相比内存占用更小。SPDL 实现了与现有 Python 版本中这种基于线程的并行互补的基础媒体处理操作。

## AI 模型训练效率中的问题

Reality Labs 的 GPU 效率团队与多个团队合作，诊断训练低效并讨论解决方案。低效的成因和解决方案跨越许多不同的子领域，不限于数据加载。这里我们总结设计 SPDL 时所着手解决的数据加载主要问题。

### 并发执行性质不同的操作

用大量数据训练模型时，数据从远程存储获取、由 CPU 预处理，然后传输到 GPU 设备。这些阶段的性能受不同因素约束：数据获取主要受网络带宽约束，预处理受 CPU 约束，传输受内存总线约束。理想的流水线应并发执行这些操作，所有阶段都应在等待上游或下游阶段时保持执行。这需要分别调整各阶段的并发度。

### 用于诊断和优化数据加载的工具

根据我们的经验，几乎所有训练流水线都有与数据相关的问题。让这些问题难以解决的原因，是缺乏对数据加载器行为的洞察，以及缺乏调优性能的合适参数。PyTorch 的 DataLoader 类通过抽象内部机制提供了简单的用户体验，但这种抽象也让性能分析变得困难。PyTorch Profiler 只有在没有 worker 进程时才能提供 Python 调用栈的洞察，这在实际训练流水线中并不适用。由于 dataset 接口完全抽象了内部机制，DataLoader 能为性能提供的支持很有限。通常，增大 num_workers 和启用 pin_memory 是仅有的选项。然而，增加 worker 进程的数量会带来不受欢迎的副作用。

### 启动子进程带来的资源占用增加

以 spawn* 方式启动子进程时，会启动一个新的 Python 解释器并加载其依赖。然后，dataset 和数据加载器的实例从主进程复制到子进程。我们见过这种内存消耗在每个子进程中累计达到数 GB 量级的情况。这让提高数据加载并发变得困难。除了静态内存消耗，子进程的使用还增加动态内存消耗。例如，当一个批次 Tensor 在后台进程中创建并发送到主进程时，它先被序列化并写入这些进程共享的内存区域——然后主进程取回数据并反序列化回批次 Tensor。因此，当批次 Tensor 在后台进程中创建时，它在被主进程使用之前至少被复制两次。与进程间 CPU 内存边界类似，GPU 内存在进程之间也是隔离的。子进程无法访问主进程使用的 GPU 内存空间，因此数据只有在被发送到主进程之后才能被送到 GPU 内存。

*另一种方法是在创建子进程时 fork 主进程，但由于库初始化方式的某些微妙问题，这常常导致段错误，所以 spawn 是唯一安全的选项。

### 全局解释器锁

传统数据加载解决方案之所以使用子进程——尽管有许多阻碍吞吐量扩展的副作用——原因在于 Python 的全局解释器锁（GIL）。GIL 保护代码免受竞态条件影响，这阻碍了线程的有效使用。目前有大量工作致力于让 GIL 变为可选，不久之后在 Python 中使用多线程将成为标准。从子进程切换到线程应该能解决我们上面提到的问题。于是我们问自己：如果没有 GIL 施加的约束，数据加载解决方案会是什么样？我们能否在 free-threading 广泛可用之前，把它的好处带到当前的 Python 环境？有许多为高性能计算构建的 Python 库，它们通过释放 GIL 来实现高性能。我们能否把这一技术应用于数据加载流水线的最大瓶颈？

## SPDL 登场

我们开发了 SPDL——一个解决大规模训练低效的新数据加载解决方案。由于使用子进程有上述许多缺点，我们借此机会探索了 free-threading Python 中数据加载的设计。

### 设计考量

以下是 SPDL 的关键设计标准，反映了上述训练流水线中的问题：

- **高吞吐量：** SPDL 解决的最根本问题是数据加载成为训练流水线的瓶颈。为了让 GPU 忙于计算，SPDL 必须实现高吞吐量。
- **性能易于推理：** 数据加载由多个具有不同约束因素的阶段组成。能够分别测量每个阶段的性能至关重要。
- **不封装预处理操作：** 封装是面向对象编程中的强大概念。但在优化数据处理流水线时，我们需要能够分别调优每个阶段。如果一个 Dataset 类包含解码和预处理的全部逻辑，我们就得替换整个 Dataset 类。这导致现有组件的复用性差。
- **没有领域特定语言（DSL）：** SPDL 的目标受众是研究者和 ML 工程师，他们的目标是开发新的 AI 模型。我们希望把他们学习工具的时间降到最低，让他们专注于 AI 建模，因此 SPDL 不引入 DSL。此外，维护和扩展 DSL 需要大量工作，而且随着 DSL 增长，工作量呈指数级增长。我们希望把 SPDL 的维护成本保持在最低。
- **无缝整合异步工具：** 我们假设数据存储在网络存储中，而许多网络工具提供异步 API 以获得更好性能。我们想利用原生异步函数可以在不受 GIL 约束的情况下并发执行这一事实。
- **灵活：** 数据准备的方式因流水线而异。有时数据是归档格式，必须下载整个归档。有些流水线必须从不同来源收集数据。为支持这些不同需求，SPDL 需要灵活。
- **简单直观：** 当我们询问团队他们的数据处理流水线时，他们用高层抽象来解释流水线，而不是逐个讲解其中使用的 API 调用。理想情况下，他们可以直接在代码中表达这个过程，而且代码读起来就是那个样子。
- **容错：** 通过网络获取数据可能因各种原因失败。媒体数据常常格式错误，解码格式错误的数据可能失败。流水线需要对这类失败保持稳健，还需要记录失败并向流水线所有者发出错误信号。

### 执行引擎的架构

SPDL 由以下组件构成：

- 任务执行器（流水线抽象）
- 便于构建流水线的工具
- 高效、线程安全且释放 GIL 的媒体处理操作

SPDL 任务执行引擎的核心是一个异步事件循环。异步事件循环负责调度新任务并对任务完成做出反应。它提供了一组 API，通过把同步操作的执行委托给线程来异步运行它们。这使得异步事件循环成为在线程池中运行同步函数的代理。（如前所述，为了实现真正的并发，同步函数在线程中执行时必须释放 GIL。）由于运行异步事件循环本身是阻塞操作，它在后台线程中运行。主线程与后台线程使用线程安全队列传递数据。通过改变队列大小，我们可以调整在主线程消费前缓冲的预处理数据量。

如果数据获取、预处理和数据传输的操作都释放 GIL（或被 asyncio 原生支持），那么 SPDL 的任务执行引擎可以在后台线程中执行它们，而不依赖子进程。（如果某些操作持有 GIL，那部分可以独立地在进程中执行。）在我们调查的流水线中，当数据加载是瓶颈时，真正的瓶颈往往是媒体处理——即图像/视频解码、缩放和组批。这类操作不依赖 Python 解释器的任何功能，因此可以无副作用地释放 GIL。而媒体解码需要绑定 C 等其他语言编写的第三方库，我们可以在零运行时开销下释放 GIL。由于媒体处理是一些性能最关键的代码，我们从头实现了媒体解码功能，在开发的所有阶段仔细测量性能，同时确保这些功能线程安全且释放 GIL。

### 流水线与并发

如上所述，把数据从远程存储加载到 GPU 要经过多个具有不同约束因素的阶段。这些阶段需要不同的扩展策略，所以能够分别调整各阶段的并发度很重要。因此，我们把数据加载流水线设计成用户可以显式地分别指定每个阶段的并发度。每个阶段的任务由异步事件循环并发调度。

### 媒体处理模块

处理多媒体常常是数据加载的瓶颈，但也是提升性能的机会。对于底层操作（如解码音频、图像、视频和缩放），我们依赖不依赖 Python 的外部库。这意味着我们可以在释放 GIL 的同时执行它们，而一旦 GIL 被释放，这些函数就可以在 Python 的线程池中并发执行。为了实现高性能，避免引入不必要的操作和内存拷贝很重要。常见的做法是把单个媒体样本加载为 Tensor 再组批，但这会创建多个随即被释放的中间副本。此外，如果批次 Tensor 在子进程中创建并传输到主进程，还会产生额外拷贝。下图展示了一批图像如何创建，以及沿路发生了多少次内存分配。在 SPDL 中，我们实现的 IO 函数可以直接传递底层解码库使用的数据，而无需转换为 Tensor。这避免了创建中间 Tensor。这些解码后的数据可以直接拷贝到批次 Tensor，而不必为批中每个样本创建中间 Tensor。此外，当媒体数据被拷贝到批次时，数据可以直接写入页锁定（page-locked）内存，让 GPU 可以直接访问。下图对此做了说明。

**初始化后的吞吐量**：下图比较了初始化之后 PyTorch 与 SPDL 的吞吐量。一旦初始化完成，PyTorch DataLoader 的子进程 worker 不再受 GIL 约束，其性能扩展良好。SPDL 的基于线程的并行仍受 GIL 约束，因此在 worker 数量较高时不如 PyTorch 扩展得好。不过，在最多 16 个 worker 时，它表现出相近甚至有时更好的性能。

## 在生产系统中

在生产环境中训练模型时，情况更加复杂。训练流水线有与系统交互的额外依赖，其中一些在子进程启动时会执行额外的初始化。训练数据从网络下载，因此网络延迟会影响性能。我们把 SPDL 集成到一个内部模型训练流水线中，看到了显著改进。我们实验的流水线训练一个处理视频和音频的模型。训练数据从网络存储获取。原本的数据加载基于 PyTorch DataLoader，并用 TorchAudio 的 StreamingMediaDecoder 处理视频和音频。使用 SPDL，我们可以独立调整网络传输和视频处理的并发度。SPDL 的视频处理函数比 TorchAudio 使用更少内存。SPDL 分别报告下载和视频处理的吞吐量，因此很容易知道瓶颈在哪里并调整参数。数据加载（从远程存储到 GPU 测量）的吞吐量用 SPDL 快了 3 倍。这将瓶颈转移到了模型计算上。我们对模型应用了各种优化，最终把模型训练速度提高了一倍。内存消耗降低到不到一半。节省的内存大部分来自执行静态初始化的额外平台相关依赖。通过摆脱子进程，初始化的时间和内存被完全消除。

## 自由线程 Python

随着我们在内部推出该解决方案，我们越来越多地听到关于自由线程 Python 的讨论。我们预计自由线程 Python 要达到稳定和生产可用还需要一些时间。不过，理想的路径是 SPDL 与 FT Python 无缝协作，让用户无需额外迁移工作即可享受其好处。我们在 SPDL 开发过程中学到的一件事是：简单地把子进程 worker 池替换为线程 worker 池并不会自动提升性能。软件架构需要针对基于线程的并行进行量身定制。那么问题是「SPDL 在 FT Python 中性能会提升吗？」为回答这个问题，我们做了一个实验，看 SPDL 是否与 FT Python 兼容、性能是否提升。两个问题的答案都是肯定的。用 SPDL 构建的数据加载流水线无需任何代码改动即可在 FT Python 上工作，而且性能有所提升。下图展示了加载 ImageNet 数据集的吞吐量。可以看到禁用 GIL 时吞吐量有所提升。

## 结论

SPDL 由 Reality Labs 开发，用于提升模型训练性能。它从底层设计就注重高效。它使用受 GIL 约束的基于线程的并行，但可以在消耗更少内存的情况下胜过基于进程的并行。它提供对数据加载性能的洞察和优化旋钮。它适用于许多多模态模型训练，包括不使用 PyTorch 的场景。SPDL 兼容自由线程 Python，并在禁用 GIL 时获得进一步的性能提升。SPDL 为自由线程 Python 成为标准的时代铺就了 AI 开发之路。
