# 如何微调：聚焦高效数据集

> 原文：[How to fine-tune: Focus on effective datasets](https://ai.meta.com/blog/how-to-fine-tune-llms-peft-dataset-curation) · Meta AI（Wayback 存档）

2024 年 8 月 7 日

这是关于适配开源大语言模型（LLM）系列博客的第三篇。本文探讨策划一份优质训练数据集的一些经验法则。[第一篇](1)我们考察了把语言模型适配到领域数据的流行方法；[第二篇](2)我们讨论了如何判断微调是否是适合你用例的方法。

## 引言

微调 LLM 是艺术与科学的结合，该领域的最佳实践仍在不断涌现。本文将重点介绍微调的设计变量，并就我们迄今在资源受限条件下微调模型所见的最佳实践给出方向性指引。我们建议把下面的信息作为规划微调实验的起点。

## 全量微调 vs. 参数高效微调（PEFT）

在学术和实际场景中，无论全量微调还是 PEFT，在应用到新领域时都展现了下游性能的提升。二者的选择归结为：可用算力（GPU 小时数和 GPU 显存）、目标下游任务之外其他任务上的表现（学习-遗忘权衡），以及人工标注成本。

全量微调更容易出现两个问题：模型崩溃（model collapse）和灾难性遗忘（catastrophic forgetting）。模型崩溃指模型输出收敛到有限的输出集合，原始内容分布的尾部消失。灾难性遗忘如本系列第一篇所讨论的，会导致模型丧失既有能力。一些早期实证研究表明，与 PEFT 技术相比，全量微调技术更容易出现上述问题，不过仍需更多研究。PEFT 技术在设计上天然起到微调正则化项的作用。PEFT 训练下游模型所需的算力通常相对更少，对于数据集规模有限的资源受限场景更为可用。在某些情况下，全量微调在特定目标任务上表现更好，但往往以遗忘原模型部分能力为代价。特定下游任务性能与其他任务性能之间的这种「学习-遗忘」权衡，在论文中对 LoRA 与全量微调的比较里有深入探讨。在资源受限的前提下，PEFT 技术很可能比全量微调提供更佳的性能提升/成本比。如果在资源受限时下游性能至为关键，全量微调将最有效。无论哪种情形，关键都是遵循以下核心原则，创建高质量数据集。

## 数据集策划

在文献中的微调实验里，数据集对于收获微调收益至关重要。这里比「质量更好、数量更多」更有讲究，你可以在资源受限的微调实验中，聪明地投资数据集收集以换取性能提升。

### 数据质量/数量

- **质量至上**：我们观察到的总体趋势是质量比数量更重要——也就是说，一小批高质量数据胜过一大批低质量数据。质量的关键原则是：标注一致、无错误、无误标数据、无带噪输入/输出，以及与总体相比具有代表性的分布。微调时，LIMA 数据集几千条精选样本的性能优于 5 万条机器生成的 Alpaca 数据集。OpenAI 微调文档提示，哪怕 50 到 100 条的数据集也可能带来改变。
- **更难的语言任务需要更多数据**：文本生成和摘要等相对更难的任务更难微调，需要比分类、实体抽取等较容易任务更多的数据。这里「更难」可以指多种情况：输出 token 更多、所需人类能力更高、存在多个正确答案。
- **高效收集高质量数据**：由于数据收集昂贵，建议采用以下策略提高样本效率并降低成本：
  - **观察失败模式**：观察既有 ML 能力失败的样本，添加针对这些失败模式的示例。
  - **人在回路（Human in the loop）**：这是一种更便宜的数据标注扩展方式。我们用 LLM 自动化生成基础回复，人工标注员可以用更少时间完成标注。

### 数据多样性

简单来说，如果你用某一类特定回复过度训练模型，它会偏向于给出那种回复，即便那并不是最恰当的答案。这里的经验法则是：尽你所能确保训练数据反映模型在真实世界中应有的行为。

- **去重**：重复已被发现是微调和预训练中模型退化的原因之一。通过去重实现多样性往往带来性能指标的改善。
- **输入的多样性**：通过改写输入带来多样性。微调 SQLCoder2 时，团队对 SQL 查询附带的自然语言文本进行了改写，以引入句法和语义多样性。类似地，「指令回译」（Instruction Backtranslation）被用于人工撰写的文本：通过向 LLM 提问「这段文字可能是哪些问题的答案？」来生成问答数据集。
- **数据集的多样性**：为更通用的下游任务（例如多语言适配）微调时，使用多样化数据集已被证明能改善「遗忘模型原有能力」与「学习新能力」之间的学习-遗忘权衡。面向印地语、奥里亚语等不同语言的微调模型，使用了加入语言特定富集数据的 FLAN、Alpaca、Dolly 等指令微调数据集来诱导多样性。
- **标准化的输出**：从输出中去除空白字符等格式花招已被证明有帮助。SQLCoder2 从生成的 SQL 中去除空白，让模型专注于学习重要的 SQL 概念，而非空格和缩进之类的花招。如果你希望回答带有特定语气，例如「客服聊天机器人……」，就把这些加进每条示例数据中。

### 基于 LLM 的数据流水线

为策划高质量多样化数据集，数据流水线常使用 LLM 来降低标注成本。实践中观察到以下技术：

- **评估**：用高质量数据集训练一个模型，再用它为较大规模的数据集标注，以筛选出高质量样本。
- **生成**：以高质量样本为种子，提示 LLM 生成类似的高质量样本。合成数据集的最佳实践正在成形。
- **人在回路**：用 LLM 生成初始输出集，再由人工通过编辑或表达偏好来提升质量。

### 调试你的数据集

- **为不良输出评估数据集**：如果模型在某些方面仍然不佳，添加直接向模型展示如何正确完成这些方面的训练示例。如果你的模型有语法、逻辑或风格问题，检查你的数据是否也有同样问题。例如，如果模型现在会说「我来帮你安排这次会议」（而它不应该这样说），看看既有示例是否教会了模型宣称自己能做实际上做不了的新事情。
- **审视正负类别的平衡**：如果数据中 60% 的助手回复说「我无法回答这个问题」，但推理时只有 5% 的回复应该这样说，你很可能得到过多的拒绝。
- **完备性与一致性**：确保训练示例包含回答所需的全部信息。如果我们希望模型基于用户的个人特质赞美用户，而某条训练示例包含了对前文对话中并未出现的特质的赞美，模型可能学会幻觉信息。确保所有训练示例格式一致，与推理时的期望一致。审视训练示例间的一致性与吻合度。如果训练数据由多人创建，模型性能很可能受限于人与人之间的一致性和吻合度。例如，在文本抽取任务中，如果人们对抽取片段的吻合度只有 70%，模型很可能无法做得更好。

## 结论

微调是 LLM 开发的关键一环，需要在艺术与科学之间精妙平衡。数据集的质量与策划对微调的成功举足轻重，经过良好微调的小型 LLM 常在特定任务上超越更大的模型。一旦做出微调决定，Llama 微调指南提供了扎实的起点。微调数据集配方的专有属性阻碍了最佳实践的共享和开源进步。随着领域持续演进，我们期待通用最佳实践的出现，同时保留微调的创造性与适应性。
