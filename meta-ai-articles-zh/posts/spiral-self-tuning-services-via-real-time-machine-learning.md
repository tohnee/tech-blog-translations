# Spiral：通过实时机器学习实现服务自调优

> 原文：[Spiral: Self-tuning services via real-time machine learning](https://ai.meta.com/blog/spiral-self-tuning-services-via-real-time-machine-learning) · Meta AI（Wayback 存档）

2018 年 6 月 28 日

对于使用 Facebook 的数十亿人来说，我们的服务可能看起来像一个单一的、统一的移动应用或网站。从公司内部看，景象则不同。Facebook 由数千个服务构建而成，功能从平衡互联网流量、转码图像到提供可靠存储。Facebook 整体的效率是其各个服务效率之和，而每个服务通常以自己的方式优化，所用的方法可能难以泛化，也难以在快速变化面前适应。为了更有效地优化我们的众多服务，并具备适应不断变化的内部服务互联网络的灵活性，我们开发了 Spiral。Spiral 是一个在 Facebook 规模上自调优高性能基础设施服务的系统，使用利用实时机器学习的技术。用 Spiral 取代手工调优的启发式规则后，我们可以在几分钟而不是几周内优化更新后的服务。

## 应对规模挑战的新方法

在 Facebook，变化节奏非常快。作为持续部署流程的一部分，Facebook 代码库每几小时就推送一次到生产环境——例如前端的新版本。在这个动态世界里，试图手工微调服务以维持峰值效率是不切实际的。手工重写缓存/准入/淘汰策略和其他手工调优的启发式规则实在太难了。我们必须从根本上改变对软件维护的思考方式。为了高效应对这一挑战，系统需要变成自调优的，而不是依赖人工硬编码的启发式规则和参数。这一转变促使 Facebook 工程师以新方式开展工作：工程师不再通过查看系统产生的图表和日志来验证运行正确且高效，而是用代码表达「系统正确且高效地运行」意味着什么。今天，我们的工程师不再指定如何计算对请求的正确响应，而是编码向自调优系统提供反馈的手段。传统的缓存策略可能像一棵树，分支考虑对象的大小、类型和其他元数据来决定是否缓存它。自调优缓存的实现方式则不同。这样的系统可以查看某个条目的访问历史：如果这个条目从未被访问过，那么缓存它可能是个坏主意。用机器学习的语言来说，一个使用元数据（特征）和相关反馈（标签）来区分条目的系统就是「分类器」。这个分类器将用于对进入缓存的条目做决策，而系统会被持续再训练。正是这种持续再训练，使系统即使环境变化也能保持与时俱进。

从概念上讲，这种方法类似于声明式编程。SQL 是这种方法的流行例子：工程师无需指定如何计算复杂查询的结果，只需指定需要计算什么，引擎就会找出最优查询并执行。对系统使用声明式编程的挑战在于确保目标被正确且完整地指定。就像上面的自调优图像缓存策略一样，如果关于什么应该和不应该被缓存的反馈不准确或不完整，系统会很快学会给出错误的缓存决策，从而降低性能。（这篇由几位 Google 工程师撰写的论文详细讨论了这一问题及与使用闭环机器学习相关的其他问题。）根据我们的经验，精确地为自调优定义期望的结果是接入 Spiral 最难的部分之一。不过我们也发现，工程师经过几次迭代后往往会收敛到清晰且正确的定义。

## Spiral：轻松集成与实时预测

为了让 Facebook 的系统工程师跟上不断加快的变化节奏，我们在 Facebook 波士顿办公室的工程师构建了 Spiral——一个依赖极少的小型嵌入式 C++ 库。Spiral 使用机器学习为资源受限的实时服务创建数据驱动、反应式的启发式规则。与手工编码的替代方案相比，该系统支持快得多的开发以及免维护的运行。与 Spiral 的集成只需在代码中添加两个调用点：一个用于预测，一个用于反馈。预测调用点是智能启发式规则的输出，用于做决策，例如「这个条目是否应该被准入缓存？」预测调用实现为快速的本地计算，可在每次决策时执行。反馈调用点用于提供偶尔的反馈，例如「这个条目从未被命中就从缓存中过期了，所以像这样的条目我们可能不该缓存。」该库可以完全嵌入式模式运行，也可以把反馈和统计信息发送到 Spiral 后端服务——后者可以为调试可视化有用信息、把数据记录到长期存储以备后续分析，并承担那些在嵌入式模式下训练过于耗资源（但运行不那么耗资源）的模型的训练和选择等重活。发送到服务器的数据经过反偏差采样，以避免样本中渗透类别不平衡偏差。例如，如果一段时间内我们收到的负样本是正样本的 1000 倍，我们只需向服务器记录千分之一的负样本，同时标明其权重为 1000。服务器对数据全局分布的可见性通常能带来比任何单个节点本地模型更好的模型。除链接库和使用上述两个函数外，这一切都不需要任何设置。在 Spiral 中，学习在反馈到来的瞬间开始。随着更多反馈产生，预测质量逐步改善。在大多数服务中，反馈在数秒到数分钟内即可获得，因此开发周期非常短。领域专家可以添加一个新特征，并在几分钟内看到它是否有助于提升预测质量。与硬编码的启发式规则不同，基于 Spiral 的启发式规则能适应变化的条件。例如在缓存准入策略中，如果某些类型的条目被请求的频率降低，反馈将再训练分类器以降低准入此类条目的可能性，无需任何人工干预。

## 案例研究：自动化反应式缓存启发式规则

Spiral 的第一个生产用例完美契合 Phil Karlton 的名言：「计算机科学只有两件难事：缓存失效和命名。」（我们的项目已经有了一个贴切的名字，所以我们实际上立刻用 Spiral 攻克了缓存失效。）在 Facebook，我们推出了一个反应式缓存，允许 Spiral 的「用户」（我们的其他内部系统）订阅查询结果。从用户的角度看，这个系统提供查询结果和对该结果的订阅。每当外部事件影响该查询时，它会自动把更新后的结果发送给客户端。这免除了客户端轮询的负担，并降低了计算查询结果的 Web 前端服务的负载。当用户提交查询时，反应式缓存先把查询发送到 Web 前端，然后创建订阅，缓存并返回结果。除了原始结果外，缓存还会收到在计算结果时被触及的对象和关联的列表。然后它开始监控查询所访问的任何对象或关联的数据库更新流。每当它看到一个可能影响某个活跃订阅的更新，反应式缓存就重新执行该查询并与缓存中的结果比较。如果结果确实变了，它就把新结果发送给客户端并更新自己的缓存。

这个系统面临的一个问题是：数据库更新的量极其庞大，但只有极小一部分会影响查询输出。如果一个查询关心的是「我的哪些朋友点赞了这条帖子？」，那么持续获得诸如该帖子最近何时被查看之类的更新就是不必要的。这个问题类似于垃圾邮件过滤：给定一条消息，系统应把它归类为 spam（不影响查询结果）还是 ham（影响查询结果）？第一个解决方案是手工创建静态黑名单。这是可行的，因为反应式缓存工程团队发现超过 99% 的负载来自很小的一组查询。对于低流量查询，他们干脆假设所有更新都是 ham，并对查询引用的每个对象的每次更新都重新执行查询。对于那一小组高流量查询，他们通过 painstakingly 观察查询执行来确定每个对象中哪些字段真正影响查询输出，从而创建黑名单。这个过程通常每个黑名单要花掉工程师几周时间。更复杂的是，高流量查询集合在不断变化，所以黑名单很快就会过时。每当使用该缓存的服务改变它执行的查询，系统就得更改垃圾过滤策略，这需要更多工程工作。

### 更好的解决方案：Spiral 垃圾过滤

重新执行查询后，只需把新的查询结果与旧的查询结果比较，就能很容易地判断观察到的更新是 spam 还是 ham。这一机制被用来向 Spiral 提供反馈，让它为更新创建分类器。为确保采样无偏，反应式缓存只维护并只从一小部分订阅提供反馈。缓存不过滤这些订阅的更新；只要相关对象或关联被修改，查询就会被重新执行。它把新的查询输出与缓存版本比较，然后用它向 Spiral 提供反馈——例如告诉它更新「最近查看时间」不影响「点赞数」。Spiral 从所有反应式缓存服务器收集这些反馈，并用它为每种不同的查询类型训练分类器。这些分类器被周期性地推送到缓存服务器。为新查询创建过滤器或更新过滤器以响应 Web 层变化的行为，不再需要工程团队的任何人工干预。随着新查询的反馈到来，Spiral 自动为这些过滤器创建新的分类器。

## 更快的部署与 Spiral 的更多机会

有了基于 Spiral 的缓存失效机制，在反应式缓存中支持一个新查询所需的时间从几周缩短到几分钟。在 Spiral 之前，反应式缓存工程师必须通过运行实验和手工收集数据来检查每个新查询的副作用。而有了 Spiral，大多数用例（映射到查询）在几分钟内就被本地模型自动学习，因此本地推理立即可用。对大多数用例，服务器能够在 10 到 20 分钟内用来自多台服务器的数据训练模型。一旦发布到所有单台服务器，这个更高质量的模型即可用于更高保真度的推理。当查询被改变时，服务器能够适应变化，并在收到更新后的查询时重新学习新的实质性模式。

我们将继续致力于自动化后端服务并应用机器学习以获得更好的运营体验。Spiral 未来的潜在应用包括：使用贝叶斯优化的持续参数优化、基于模型的控制，以及面向高 QPS 实时服务和离线（批处理）系统的在线强化学习技术。我们将在未来的帖子中继续分享我们的工作和成果。
