# 击败 LLM 推理中的非确定性

> 原文：[Defeating Nondeterminism in LLM Inference](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/) · Thinking Machines Lab

可复现性（reproducibility）是科学进步的基石。然而，要从大语言模型那里得到可复现的结果却出奇地困难。

例如，你可能会观察到，向 ChatGPT 多次提出同一个问题会得到不同的结果。这本身并不令人意外，因为从语言模型得到结果的过程涉及「采样」——一个把语言模型的输出转换成概率分布、再按概率选取某个 token 的过程。

可能更令人意外的是：即使我们把 temperature 调低到 0（这意味着 LLM 总会选择概率最高的 token，也就是所谓的贪婪采样），从而使采样在理论上具有确定性，LLM API 在实践中仍然**不是**确定性的（参见过往讨论：[这里](https://152334h.github.io/blog/non-determinism-in-gpt-4/)、[这里](https://community.openai.com/t/a-question-on-determinism/8185/2)、[这里](https://cookbook.openai.com/examples/reproducible_outputs_with_the_seed_parameter)）。即便在自己的硬件上用 vLLM 或 SGLang 这类开源推理库运行推理，采样依旧不是确定性的（参见[这里](https://docs.vllm.ai/en/v0.7.0/getting_started/faq.html)或[这里](https://docs.sglang.ai/references/faq.html)）。

但 LLM 推理引擎为什么*不*是确定性的？一个常见的猜想是：浮点非结合性与并发执行的某种组合，导致结果取决于哪个并发核心先完成，从而产生非确定性。我们将其称为 LLM 推理非确定性的「并发 + 浮点」假说。例如，[一篇最近的 arXiv 预印本](https://arxiv.org/abs/2506.09501)写道：

> GPU 中的浮点算术表现出非结合性，即由于有限精度和舍入误差，(a+b)+c ≠ a+(b+c)。这一性质直接影响 transformer 架构中注意力分数与 logits 的计算：跨多个线程的并行操作可能因执行顺序不同而给出不同的结果。

你还可以在别处看到「并发 + 浮点」假说被反复提及，例如[这里](https://community.openai.com/t/a-question-on-determinism/8185)（*「这存在速度上的权衡。为了让端点足够快，人们使用了 GPU，而 GPU 做的是并行的[非确定性]计算。任何现代 GPU 上的神经网络计算都会受此影响。」*），或[这里](https://x.com/hosseeb/status/1773146428594090473)（*「由于 GPU 高度并行化，加法或乘法的执行顺序每次可能不同，进而级联成输出上的微小差异。」*）。

这个假说并非完全错误，但它没有揭示全貌。例如，即使在 GPU 上，对相同数据反复运行同一个矩阵乘法，总会得到按位相同（bitwise equal）的结果。我们确实在用浮点数，我们的 GPU 也确实有大量并发。为什么在这个测试中看不到非确定性？

```
A = torch.randn(2048, 2048, device='cuda', dtype=torch.bfloat16)
B = torch.randn(2048, 2048, device='cuda', dtype=torch.bfloat16)
ref = torch.mm(A, B)
for _ in range(1000):
    assert (torch.mm(A, B) - ref).abs().max().item() == 0
```

要理解 LLM 推理非确定性的真正原因，我们必须看得更深。

遗憾的是，就连*定义* LLM 推理何为确定性都很困难。也许令人困惑的是，以下说法同时成立：

1. GPU 上的某些内核（kernel）是**非确定性的**。
2. 然而，语言模型前向传播中用到的所有内核都是**确定性的**。
3. 此外，LLM 推理服务器（如 vLLM）的前向传播也可以被声称是**确定性的**。
4. 尽管如此，从任何使用推理服务器的人的视角来看，结果却是**非确定性的**。

在这篇文章中，我们将解释「并发 + 浮点」假说为何没有命中要害，揭开 LLM 推理非确定性背后的真正元凶，并说明如何击败非确定性、在 LLM 推理中获得真正可复现的结果。

## 原罪：浮点非结合性

在谈论非确定性之前，先解释一下数值差异为什么会存在，这很有帮助。毕竟，我们通常把机器学习模型看作遵循交换律、结合律等结构规则的数学函数。机器学习库难道不应该给我们一个「数学上正确」的结果吗？

罪魁祸首是**浮点非结合性**。也就是说，对浮点数而言：

(a+b)+c ≠ a+(b+c)

```
(0.1 + 1e20) - 1e20
>>> 0
0.1 + (1e20 - 1e20)
>>> 0.1
```

颇具讽刺意味的是，正是打破结合律，浮点数才变得有用。

浮点数之所以有用，是因为它们允许一种「动态」的精度水平。为了便于解释，我们使用十进制（而非二进制），其中浮点数的格式为「尾数 × 10^指数」。我们还使用 3 位尾数和 1 位指数。

例如，对于数值 3450，我们可以将其精确表示为 3.45 × 10³。我们也可以表示小得多的数值，比如把 0.486 表示为 4.86 × 10⁻¹。这样，浮点让我们既能表示很小的值，也能表示很大的值。在科学上我们可以说，浮点使我们能维持恒定数量的「有效数字」。

如果你把两个指数相同的浮点数相加，其过程类似于整数加法。例如，123（1.23 × 10²）+ 456（4.56 × 10²）的结果是 579（5.79 × 10²）。

但当我们把两个指数不同的浮点数相加时会怎样，比如 1230 和 23.4？此时精确结果是 1253.4。然而，我们一次只能保留 3 位精度。浮点加法因此会*舍弃*最后 2 位，得到 1.25 × 10³（即 1250）。

1.23 × 10²

+

3.45 × 10¹

=

1.575 × 10²

精确值：1575

表示 1230 需要 3 位精度，表示 23.4 也需要 3 位精度。然而把这两个数相加的结果（1253.4）需要 5 位精度才能表示。于是我们的浮点格式必须把末尾的 34 舍去。在某种意义上，我们实际上在相加之前就把原来的 23.4 舍入成了 20.0。

此时，信息已经被销毁了。注意，每次把两个「尺度」（即指数）不同的浮点数相加时，这种情况都可能发生。而把指数不同的浮点数相加是家常便饭。事实上，如果我们能保证永远不需要不同的指数，那直接用整数就行了！

换句话说，每次以不同顺序把浮点数相加，都可能得到完全不同的结果。举个极端的例子，对这个数组求和，依相加顺序不同可能得到 102 种不同的结果。

```
import random

vals = [1e-10, 1e-5, 1e-2, 1]
vals = vals + [-v for v in vals]

results = []
random.seed(42)
for _ in range(10000):
    random.shuffle(vals)
    results.append(sum(vals))

results = sorted(set(results))
print(f"There are {len(results)} unique results: {results}")

# Output:
# There are 102 unique results: [-8.326672684688674e-17, -7.45931094670027e-17, ..., 8.326672684688674e-17]
```

虽然这是输出不一致的底层原因，但它并没有直接回答非确定性从何而来。它无法帮助我们理解浮点数为什么会以不同顺序相加、这发生在什么时候、以及如何避免。

答案藏在内核（kernel）的实现方式里。

## 为什么内核不总是按相同顺序做加法？

如上所述，对「内核为什么以不同顺序做加法」的一个常见解释是「并发 + 浮点」假说。该假说认为：如果并发线程完成的顺序是不确定的，而累加顺序又取决于并发线程完成的顺序（例如原子加法，atomic add），那么我们的累加顺序也将是不确定的。

令人困惑的是，尽管这确实可能导致非确定性的内核，并发（和原子加法）最终与 LLM 推理的非确定性毫无关系！为了解释真正的元凶，我们首先要理解为什么现代 GPU 内核很少需要原子加法。

## 什么时候需要原子加法？

通常，GPU 会把一个程序并发地发射到许多「核心」（即 SM）上。由于核心之间没有内在的同步机制，如果核心之间需要通信，这就成了一个挑战。例如，如果所有核心都必须向同一个元素累加，可以使用「原子加法」（有时被称为「[fetch-and-add](https://en.wikipedia.org/wiki/Fetch-and-add)」）。原子加法是「非确定性的」——结果累加的顺序完全取决于哪个核心先完成。

具体来说，想象你用 100 个核心对一个 100 元素的向量做归约（例如 `torch.sum()`）。虽然你可以并行加载全部 100 个元素，但我们最终必须归约到单个元素。实现这一点的一种方式是某种「原子加法」原语：硬件保证所有加法都会被处理，但不保证顺序。

原子加法确保每个核心的贡献都会体现在最终的总和中。然而，它对贡献按什么*顺序*累加没有任何保证。顺序完全取决于哪个核心先完成，这是一个非确定性的属性。因此，多次执行同一个并行程序可能得到非确定性的输出。

这通常就是人们所说的「非确定性」——你把同一个内核用完全相同的输入执行两次，却得到不同的结果。这被称为*运行间非确定性（run-to-run nondeterminism）*：你把同一个 python 脚本用完全相同的依赖运行两次，却得到不同的结果。

尽管并发的原子加法**确实**会使内核非确定，*但绝大多数内核根本不需要原子加法。*事实上，在 LLM 的典型前向传播中，通常*一个原子加法都不存在*。

这也许令人意外，毕竟并行化一个归约操作可以受益于原子加法。原子加法最终不需要的原因主要有两个。

1. 「batch」维度上往往已经有足够的并行度，我们不需要沿归约维度并行化。例如，假设我们不是归约单个 100 维向量，而是并行归约 500 个向量。这种情况下，我们可以在单个核心内归约整个向量，让每个核心处理不同的向量。
2. 随着时间推移，大多数神经网络库采用了各种在不牺牲性能的前提下实现确定性的策略。例如，我们可以执行「split」（或树状）归约：把 100 元素的归约拆成五个 20 元素的归约（从而获得五路并行）。然后，为合并剩下的五个结果，我们既可以执行单独的「收尾」归约（不并行，但操作的元素足够少、代价很小），也可以使用信号量（semaphore）确保每个并发线程块以确定的顺序累加。（信号量策略的描述见[这里](https://github.com/NVIDIA/cutlass/issues/1421#issuecomment-2016942675)。）

由于这两个因素，对绝大多数神经网络操作而言，避免原子加法的性能代价可以忽略不计。

仍有少数常见操作在避免原子加法时会有明显的性能损失。例如 PyTorch 中的 `scatter_add`（`a[b] += c`）。不过，LLM 中常用的只有一个：FlashAttention 反向传播。（趣闻：你知道吗，广为使用的 FlashAttention 反向 Triton 实现在算法上其实与 Tri Dao 的 FlashAttention-2 [论文](https://arxiv.org/abs/2307.08691)不同？标准 Triton 实现在反向传播中做了额外的重计算，避免了原子操作，但多花了 40% 的 FLOPs！）

然而，LLM 的前向传播*不涉及任何需要原子加法的操作*。因此，LLM 的前向传播实际上是「运行间确定」的。

![](svgs/deterministic.svg)

从推理服务器的视角看，它*确实是*确定性的。给定完全相同的用户请求，它总会提供相同的确定性输出。

维基百科写道：「确定性算法是那种给定特定输入时总会产生相同输出的算法。」而在本例中，给定完全相同的输入（即推理服务器正在处理的确切请求），前向传播总是产生完全相同的输出。

然而，前向传播本身「确定」并不足以保证包含它的整个系统是确定的。例如，如果我们请求的输出依赖于并行的其他用户请求（比如 batch-norm）呢？由于每个单独的请求无法知道并行的请求会是什么，从它们的视角看，我们整体的 LLM 推理也是非确定性的！

事实证明，我们请求的输出*确实*依赖于并行的用户请求。不是因为我们以某种方式跨批次泄露了信息——而是因为我们的前向传播缺乏「批不变性（batch invariance）」，导致我们请求的输出依赖于前向传播的**批大小（batch size）**。

### 批不变性与「确定性」

为了解释批不变性，让我们简化系统，只看矩阵乘法（matmul）。你可以假设所有 matmul 实现都是「运行间确定的」。（这并不完全正确，但最常见的 matmul 实现确实具备这一性质。）然而，它们不是「批不变的（batch-invariant）」。换句话说，当批大小改变时，批次中的每个元素可能得到不同的结果。

从数学角度看，这是一个相当反常的性质。矩阵乘法应当对批次中的每个元素「独立」——批次中的其他元素、以及批次有多大，都不应影响批次中特定元素的计算结果。

然而，正如我们可以通过实验观察到的，事实并非如此。

```
import torch
torch.set_default_device('cuda') 

B = 2048
D = 4096
a = torch.linspace(-1000, 1000, B*D).reshape(B, D)
b = torch.linspace(-1000, 1000, D*D).reshape(D, D)
# Doing a matrix vector multiplication by taking
# the first element of the batch
out1 = torch.mm(a[:1], b)
# Doing a matrix matrix multiplication and then taking
# the first element of the batch
out2 = torch.mm(a, b)[:1]
print((out1 - out2).abs().max()) # tensor(1669.2500, device='cuda:0')
```

注意，这*确实*是「运行间确定的」。如果你多次运行该脚本，它会确定性地返回相同结果。（它不是「硬件/软件版本不变的」——你的 GPU/PyTorch 版本可能返回不同的值，但应当确定性地返回同一个值。）

然而，当非批不变的内核被用作更大推理系统的一部分时，系统就可能变得非确定。当你向一个推理端点发起查询时，服务器承受的负载从用户视角看实际上是「非确定的」。负载决定了内核运行时的批大小，从而改变了每个单独请求的最终结果！

![](svgs/nondeterministic.svg)

虽然推理服务器本身可以被声称是「确定性的」，但对单个用户而言情况不同。从单个用户的视角看，其他并发用户不是系统的「输入」，而是系统的一种非确定属性。这使得 LLM 推理从每个用户的视角看都是「非确定的」。

如果你把内核不具备不变性的某个性质（即批大小），与该性质本身的非确定性（即服务器承受的负载）组合起来，就得到一个非确定的系统。

换句话说，**几乎所有 LLM 推理端点非确定性的首要原因在于：负载（以及由此而来的批大小）在非确定地变化！**这种非确定性并非 GPU 独有——用 CPU 或 TPU 服务的 LLM 推理端点同样存在这一非确定性来源。

因此，如果我们想避免推理服务器中的非确定性，就必须让内核具备批不变性。为了理解如何做到这一点，先来看看内核为什么本来不具备批不变性。

## 我们如何让内核具备批不变性？

为了让一个 transformer 实现具备批不变性，必须让每个内核都具备批不变性。幸运的是，我们可以假设每个逐元素（pointwise）操作都是批不变的。（尽管对 PyTorch 中的所有内核而言这是对的，但它并非天然成立。例如，CPU 上有些内核实现对数组的一部分使用向量化 intrinsics、对另一部分使用非向量化 intrinsics，而这些 intrinsics 的数值未必总是按位相同。）因此，我们只需要担心涉及归约的 3 种操作——RMSNorm、矩阵乘法和注意力。（与并行相关的归约不在本文讨论范围内，但相同的原则同样适用。一个可能有用的冷知识：NVLink-Sharp 的交换机内归约在 Blackwell 以及 CUDA 12.8+ 的 Hopper 上都是确定性的。与许多事情一样，这一信息可以在 NCCL 的 [GitHub issues](https://github.com/NVIDIA/nccl/issues/1497#issuecomment-3210819243) 上找到。）

方便的是，这三者的难度恰好依次递增。每一个都需要一些额外的考量，才能在合理性能下实现批不变性。先谈 RMSNorm。

### 批不变的 RMSNorm

![](svgs/rmsnorm-01.svg)

**数据并行 RMSNorm** 理想情况下，我们希望并行化策略能避免核心间通信。实现这一点的一种方式是给每个核心分配一个批次元素，从而保证每个归约都完全在单个核心内完成。这就是所谓的「数据并行（data-parallel）」策略，因为我们只是沿一个不需要通信的维度做并行。本例中有四行和四个核心，使核心得到充分利用。

RMSNorm 可以实现为：

```
# x: [batch_size, hidden_dim]
# weight: [hidden_dim]
def rms_norm(x, weight):
    return x * torch.rsqrt(torch.mean(x ** 2, dim=-1, keepdim=True)) * weight
```

批不变性的要求是：**每个元素的归约顺序必须固定，与内核的批大小无关。**注意，这并不意味着我们必须始终使用相同的归约策略。例如，如果我们改变了参与归约的元素数量，即使归约策略改变了，我们仍然可以是批不变的。（[The Quack](https://github.com/Dao-AILab/quack/blob/main/media/2025-07-10-membound-sol.md) 博文中有一些不错的示例，展示了各种归约策略的层级，如线程归约、warp 归约、block 归约、cluster 归约。）

因此，只有当批大小影响到归约策略时，我们才破坏批不变性。

来看 RMSNorm 的标准并行化策略。一般而言，并行算法受益于最小化跨核心通信。在本文的讨论中，你可以假设我们提到「核心」时指的是 SM。更准确地说，这里重要的性质是内核发射的线程块数量多于 SM 数量。于是，我们可以从这样的策略入手：如上图所示，把每个批次元素分配给一个核心。

增大批大小不影响我们的归约策略；如果批大小 200 能给内核提供足够的并行度，那么批大小 2000 *肯定*能提供足够的并行度。

![](svgs/rmsnorm-02.svg)

**更大批次的数据并行 RMSNorm** 把数据并行策略扩展到更大的批次相当直接——不再让每个核心只处理一行，而是让每个核心按顺序处理多行。这*保持了批不变性*，因为每个批次元素的归约策略保持不变。

另一方面，减小批大小可能带来挑战。由于我们把每个批次元素分配给一个核心，减小批大小最终会导致核心数多于批次元素数，使一些核心闲置。

遇到这种情况时，优秀的内核工程师会采用前一节提到的解决方案之一（原子加法或 split 归约），维持良好的并行度和性能。遗憾的是，这改变了归约策略，使内核无法保持批不变。

![](svgs/rmsnorm-03.svg)

**Split 归约 RMSNorm** 如果批大小很小，数据并行策略可能不再有足够的并行度来填满核心。此时，把一个归约「拆分」到多个核心上可能更高效，让我们能充分利用 GPU。然而，这*失去*了批不变性，因为我们不再以相同的顺序归约每个元素。

最简单的解决方案是完全忽略这些情形。这并非完全*不合理*——小批大小意味着内核本来就可能很快执行完，因此变慢未必是灾难性的。

如果我们*被迫*优化这种用例，一种办法是始终使用一种即使对很小的批大小也有足够并行度的归约策略。这样的归约策略在大批大小下会产生过量的并行度，但能让我们在所有尺寸范围内都取得不错（虽非峰值）的性能。

### 批不变的矩阵乘法

![](svgs/matmul-01.svg)

**数据并行 Matmul** 与 RMSNorm 类似，matmul 的标准并行化策略也是「数据并行」策略，把整个归约保留在单个核心内。最直接的思路是把输出张量切分成 2D tile，并把每个 tile 分配给不同的核心。每个核心随后计算属于该 tile 的点积，同样在单个核心内完成整个归约。

与 RMSNorm 不同，围绕算术强度和利用 tensor core 的额外约束，迫使我们切分 2D tile 而非单个输出元素，才能得到高效的 matmul 内核。

本质上，你可以把矩阵乘法看作先做逐元素操作、再做归约。那么，如果我们通过把**输出**切块来并行化矩阵乘法，就得到了类似的「数据并行」内核策略，把每个归约保留在单个核心内。

与 RMSNorm 类似，我们的「批」维度（M 和 N）也可能变得太小，迫使我们沿归约维度（K）切分。尽管有两个「批」维度，matmul 还要求每个核心有更多的「工作量」才能有效利用 tensor core。例如，对于一个 [1024, K] x [K, 1024] 的 matmul 和标准的 [128, 128] 2D tile 尺寸，数据并行策略只能把这个 matmul 拆分到 64 个核心，不足以填满 GPU。

沿归约维度切分 matmul 被称为 [Split-K Matmul](https://github.com/NVIDIA/cutlass/blob/main/media/docs/cpp/efficient_gemm.md#parallelized-reductions)。与 RMSNorm 一样，使用该策略会破坏批不变性。（matmul 另一种有趣的并行策略是 stream-k。stream-k 之所以有趣，是因为它比典型 matmul 的不变性*更少*。如前所述，大多数 matmul 库不是批不变的，但至少可以说是「批位置不变的（batch-position-invariant）」——即改变元素在批次*内部*的位置不影响数值。而 stream-k 连批位置不变性也不具备！其核心洞见是：对不同的输出 tile 沿 k 以不同方式切分可以获得更干净的负载均衡，但利用这一点就会使内核不再具备批位置不变性。）

![](svgs/matmul-03.svg)

**Split-K Matmul** 如果批维度相当小，我们可能没有足够的并行度，需要 split-k matmul。本例中，我们把每个归约拆到两个核心上，分别累加，最后合并结果。不过，把每个归约拆到两个核心上让我们仍能利用八个核心。

matmul 还有一层额外的复杂性——tensor core 指令。归约可以一次只处理一行，而高效的矩阵乘法内核必须一次处理一整个「tile」。

每条 tensor core 指令（例如 [`wgmma.mma_async.sync.aligned.m64n128k16`](https://docs.nvidia.com/cuda/parallel-thread-execution/#asynchronous-warpgroup-level-matrix-instructions-wgmma-mma)）内部可能有不同的归约顺序。使用不同 tensor core 指令的一个原因可能是批尺寸非常小。例如，如果我们使用一条作用于长度 256 tile 的 tensor core PTX 指令，而批大小只有 32，我们几乎浪费了全部算力！在批大小为 1 时，最快的内核通常根本不用 tensor core。

![](svgs/matmul-02.svg)

**填充的 Tensor-Core 指令** 如果批尺寸太小，我们可能处于连一个 2D tile 都塞不进输出的境地。此时，切换到更小的 tensor core 指令、或干脆不用 tensor core 是最高效的！然而，这两种选择都使内核无法保持批不变。

所以，确保 matmul 批不变性最简单的办法是编译一个内核配置并用于所有形状。虽然会损失一些性能，但这在 LLM 推理中通常不是灾难。特别是，split-k 只在 M 和 N **都**小时才最需要，而幸运的是在我们的场景中，N（即模型维度）通常相当大！

尽管获得了批不变性，我们相比 cuBLAS 也只损失了约 20% 的性能。注意，这也不是一个优化过的 Triton 内核（例如没有 TMA）。不过，性能中的一些模式可以说明批不变性要求在哪里损失性能。首先，注意在非常小的批大小下，由于指令过大和并行度不足，我们损失了大量性能。其次，随着批大小增大，会出现由量化效应（tile 量化与 wave 量化）导致的「拼图」模式，这些通常通过改变 tile 大小来缓解。你可以在[这里](https://www.thonking.ai/p/what-shapes-do-matrix-multiplications)读到更多关于这些量化效应的内容。

### 批不变的注意力

![](svgs/attention-01.svg)

**FlashAttention2 策略** 我们沿 Q 并行，同时沿 K/V 归约。这意味着整个归约可以保留在单个核心内，使它同样是一种数据并行策略。

在让 matmul 获得批不变性之后，注意力带来了两个新的难点——恰如其分，因为它包含两个 matmul。

1. 与 RMSNorm 和 matmul 只在特征维度上归约不同，我们现在要在特征维度*和*序列维度上归约。
2. 由于上述原因，注意力必须应对各种影响序列处理方式的推理优化（分块 prefill、前缀缓存等）。

因此，为了在 LLM 推理中实现确定性，我们的数值必须同时对「一次处理多少请求」**以及**「每个请求在推理引擎中如何被切分」保持不变。

先来过一遍注意力的标准并行化策略，它最初由 FlashAttention2 引入。与 RMSNorm 和 Matmul 类似，默认策略是「数据并行」策略。由于我们沿 key/value 张量归约，数据并行策略只能沿 query 张量并行。

例如，取决于推理引擎的选择，一个序列可能被分成几部分处理（如分块 prefill），也可能一次处理完（如果 prefill 不被拆分）。为了实现「批不变性」，*给定 token 的归约顺序必须不依赖于它的序列中有多少其他 token 正被同时处理*，这一条件是必要的。如果你把 KV cache 中的 K/V 值与当前正在处理的 token 的 K/V 值分开归约（比如 vLLM 的 [Triton attention 内核](https://github.com/vllm-project/vllm/blob/0ae43dbf8cb28a299ae724fc742b0c5bcddea868/vllm/attention/ops/prefix_prefill.py#L36)），就无法做到这一点。例如，在处理序列中第 1000 个 query token 时，无论 KV cache 中有 0 个 token（prefill）还是有 999 个 token（解码），归约顺序都必须一致。

![](svgs/attention-02.svg)

**带 KV Cache 的 FlashAttention** 为什么显式地把 KV cache 与当前 K/V 值分开处理会破坏批不变性？这有点微妙，与「边界条件」有关。具体来说，想象你的块大小是 32，而当前 KV cache 中有 80 个元素。我们再计算 48 个未缓存的元素。此时，计算「P cache」需要三个块（两个完整、一个带掩码），计算「P」又需要两个块（一个完整、一个带掩码）。这样总共用了五个块来完成归约，而我们总共只有四个块（即 128 个）的元素要计算，这必然改变我们的归约顺序。

例如，如果换一种情形：KV cache 中没有元素、且我们一次性处理 128 个元素——要确保注意力的「批不变性」，这两种情形下的数值必须完全一致。

为了解决这个问题，我们只需在注意力内核运行之前先更新 KV cache 和页表，确保无论正在处理多少 token，key 和 value 的布局始终一致。

加上这个细节（以及前一节提到的所有内容，如一致的 tile 尺寸），我们就能实现一个批不变的注意力！

然而，这里有一个重大问题。与矩阵乘法不同，LLM 推理中的注意力形状经常确实需要 split 归约内核，通常称为 Split-KV 或 FlashDecoding。这是因为：如果不沿归约维度并行，我们只能沿批维度、头维度和「query 长度」维度并行。在注意力的解码阶段，query 长度非常小，因此除非批大小非常大，我们往往无法填满 GPU。

不幸的是，这个情形不像 RMSNorm 和 Matmul 那样容易被忽略。例如，如果 KV cache 非常长，注意力内核即使只处理一个请求也可能耗时很久。

![](svgs/attention-03.svg)

**固定 Split 数的 Split-KV 策略（即 FlashDecode）** 如果 query 长度变得很小（解码时就是这样），我们可能陷入内核几乎没有并行度的境地。这些情况下，我们需要再次沿归约维度切分——这次是 KV 维度。沿 KV 维度切分的典型策略是先算出需要多少并行度，再把 KV 维度均分。例如，如果 KV 长度是 1000 而我们需要 4 个 split，每个核心就处理 250 个元素。

不幸的是，这同样破坏批不变性，因为我们具体的归约策略取决于在给定请求中处理该序列的多少个 query token。

此外，注意力常用的 split 归约策略也给批不变性带来挑战。例如 FlashInfer 的「均衡调度算法」会选择仍能填满 GPU 所有核心的最大 split 尺寸，从而使归约策略不是「批不变的」。然而，与 RMSNorm/Matmul 不同，仅仅选择与批大小无关的固定 split 数量是不够的。

相反，要实现批不变性，我们必须采用「固定 split 尺寸」策略。换句话说，我们不固定 split 的数量，而是固定每个 split 的大小，最终得到数量可变的 split。这样，无论正在处理多少 token，我们都能保证始终执行相同的归约顺序。这需要对 FlexAttention 内部做一些改动，这些改动未包含在我们的代码发布中。我们将在不久后把它们上游化！

![](svgs/attention-04.svg)

**固定尺寸的 Split-KV 策略** 该策略与前一策略的唯一区别是：我们的 split 现在是「固定尺寸」的。例如，如果 KV 长度是 1000，我们不再把它拆成四个长度 250 的均等 split，而是拆成三个长度 256 的固定尺寸 split 和一个长度 232 的 split。

这让我们能够*保持*批不变性，因为我们的归约策略不再依赖于一次处理多少个 query token！

## 实现

我们在 vLLM 之上提供了一个确定性推理的演示，利用了它的 FlexAttention 后端以及 torch.Library。借助 torch.Library，我们能以无侵入的方式替换掉大部分相关的 PyTorch 算子。你可以在 [thinking-machines-lab/batch-invariant-ops](https://github.com/thinking-machines-lab/batch_invariant_ops) 找到这个「批不变」内核库，以及以「确定性」模式运行 vLLM 的示例。

## 实验

### 补全结果到底有多不确定？

我们使用 `Qwen/Qwen3-235B-A22B-Instruct-2507`，在 temperature 0 下以提示词 "Tell me about Richard Feynman"（非思考模式）采样 1000 条补全，每条生成 1000 个 token。令人惊讶的是，我们生成了 *80* 条不同的补全，其中最常见的一条出现了 78 次。

观察补全在哪里出现分歧，我们发现这些补全的前 102 个 token 实际上完全相同！第一个出现分歧的位置在第 103 个 token。所有补全都生成了序列 "Feynman was born on May 11, 1918, in"。然而，992 条补全接着生成了 "Queens, New York"，而 8 条补全生成了 "New York City"。

另一方面，当我们启用批不变内核后，1000 条补全完全一致。这正是我们从数学上对采样器的预期，但没有批不变内核，我们无法取得确定性的结果。

### 性能

我们没有投入大量精力优化这些批不变内核的性能。不过，让我们跑一些实验来验证性能仍然可用。

我们将搭建一个单 GPU、运行 Qwen-3-8B 的 API 服务器，请求 1000 条输出长度在 90 到 110 之间的序列。

| 配置 | 时间（秒） |
| --- | --- |
| vLLM 默认 | 26 |
| 未优化的确定性 vLLM | 55 |
| + 改进的注意力内核 | 42 |

减速的很大一部分来自 vLLM 中的 FlexAttention 集成尚未经过深度优化。尽管如此，我们看到性能并非*灾难性*的。

### 真正的 on-policy RL

正如[研究者们指出的](https://fengyao.notion.site/off-policy-rl)，训练与推理之间的数值差异会隐式地把我们的 on-policy RL 变成 off-policy RL。

当然，如果我们连两次相同的推理请求都无法得到按位相同的结果，那么想在训练与推理之间得到按位相同的结果是不可能的。而确定性推理使我们还能改造训练栈，在采样与训练之间获得按位相同的结果，从而实现真正的 on-policy RL。

我们在 [Bigmath](https://arxiv.org/abs/2502.17387) 上以 RLVR 设置运行实验，RL 策略从 Qwen 2.5-VL instruct 8B 初始化，最大 rollout 长度为 4096。

如果我们训练时不做 off-policy 校正（即重要性加权），奖励会在训练中途崩溃；而加入 off-policy 校正项后，训练可以顺利进行。但，如果我们在采样器与训练器之间取得按位相同的结果，我们就完全 on policy（即 KL 散度为 0），同样能平稳训练。

我们还可以绘制采样器与训练器之间 logprobs 的 KL 散度，三次运行的行为明显不同。使用重要性加权时，它保持在 0.001 附近，偶有尖峰。然而，*不*使用重要性加权运行，最终会在奖励崩溃的大致同一时间出现 KL 散度尖峰。当然，在运行「真正的 On-Policy RL」时，我们的 KL 散度保持在 0，表明训练策略与采样策略之间*没有*任何分歧。

注意，不使用重要性加权的那次运行在 Step 318 附近有明显的损失尖峰，并伴随 logprobs KL 散度的相应尖峰。与此同时，无论是使用 off-policy 校正还是以「真正的 On-Policy」运行，RL 都能继续平稳进行。显示「True On-Policy」的蓝线不是 bug——它就是一条位于 0 处的平线。

## 结论

现代软件系统包含许多层抽象。在机器学习中，当我们遇到非确定性和微妙的数值差异时，把它们掩盖过去往往很有诱惑力。毕竟，我们的系统本来就是「概率性」的，再多一点非确定性又有什么关系呢？把失败单元测试的 atol/rtol 调大一点又有什么问题？训练器与采样器之间 logprobs 的差异大概不是真正的 bug，对吧？

我们拒绝这种失败主义。只需一点工作，我们*确实可以*理解非确定性的根本原因，甚至解决它们！我们希望这篇博文能让社区扎实理解如何解决推理系统中的非确定性，并激励其他人获得对自身系统的完整理解。
